Cmder PATH and Explorer Menu Solve Different Launch Problems

Launching cmder by name and opening it in Explorer's current folder are separate tasks. Learn how PATH, Cmder Here, /REGISTER USER|ALL, permissions, and moving an install affect them.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-27 · Estimated read 19 min
Translations
zh-CN en

Article

Key takeaways

  • PATH finds executables; the Explorer menu passes the selected folder to Cmder.
  • Cmder injects its own bin into its shell; that does not mean its entire vendor tree belongs in system PATH.
  • /REGISTER USER and /REGISTER ALL have different scopes; choose based on who needs the menu.
  • After moving an installation, check whether the registered shell command still points to the current cmder.exe.

Use PATH when Windows should find an executable by name. Use the Explorer context menu when you want Cmder to open in the folder currently shown in File Explorer. Those integrations change different parts of the system, so choose one from the launch action you need. If you only want a terminal in Explorer's current directory, you do not need to add every Cmder directory to the global PATH; if you only want to launch cmder.exe from a command window, you do not need to register an Explorer menu.

First decide which action you want to simplify

The old setup question actually contains two requests: launch Cmder by name from Win+R or a new command window, and open a terminal at a project directory from Explorer. The first depends on how Windows finds an executable. The second depends on Cmder registering a “Cmder Here” command with the Windows Shell.

This distinction changes the scope of the fix. PATH is an ordered list of executable search directories; if the same program name occurs in more than one directory, order can determine which copy is found. The Explorer menu stores a launch command and passes the selected location as an argument. One setting changes “which program is found”; the other changes “where it opens.” Combining them into one installation recipe can turn a small per-user convenience into a machine-wide PATH or registry change.

Ask which action you actually need. Do you need to type cmder from different working directories, or only to open it from the folder displayed in Explorer? For the second case, registering the menu is the shorter reversible route. For the first, a user-level command entry is usually a narrower option. A portable installation also has to account for a folder that may move later.

PATH changes executable lookup

Microsoft describes the Windows PATH as a set of directories the command interpreter searches for executable files. Because Cmder.exe is usually in the installation folder, adding that folder to the current user's PATH can let a newly started command interpreter try to resolve the name. It does not complete an installation, identify the desired version, or make a menu appear in Explorer.

Keep Cmder's own shell PATH separate from Windows user or system PATH. The current Cmder repository README says that tools placed in %cmder_root%\bin are injected into shells started by Cmder. A shared installation can also use a separate per-user configuration directory: its bin is included by the documented default, while opt is not automatically injected. This lets Cmder carry tools while remaining relatively portable; it is not a reason to add every executable under %cmder_root%\vendor to Windows PATH.

On a personal machine with a fixed installation location, adding the folder that contains Cmder.exe to the user's PATH may make sense if you truly need to start it by name from a new cmd.exe. If you keep the archive on a USB drive, move the folder, or maintain multiple Cmder versions, a fixed absolute directory can instead become a stale entry that launches an older copy. Adding bundled Git, Perl, or other executable directories to system PATH can also change which same-named tool another program finds. These are tradeoffs inferred from PATH search behavior and Cmder's portable design; they do not mean that every computer will encounter a collision.

Processes inherit environment variables from their launch context, so an already-open command window does not normally acquire a later PATH change by itself. For verification, open a new command prompt and run where cmder to see which locations match. A result proves which path the search found, not that the installation is complete or that Cmder's own shell configuration is correct. If there is no match, check the user PATH entry, spelling, separators, and whether the process is new before adding more Cmder subdirectories at random.

“Cmder Here” is a separate Shell registration

The current Cmder README lists /REGISTER USER and /REGISTER ALL for registering a Windows Shell menu, along with matching /UNREGISTER options. Its example changes into the Cmder folder and runs Cmder.exe /REGISTER ALL from an Administrator command prompt. After registration, Explorer can show “Cmder Here” when you right-click in or on a directory. If the menu is only for the current Windows account, the documented USER scope is available; do not default to an all-users change just to give yourself a shortcut.

The launcher source makes the scope concrete. USER writes beneath HKEY_CURRENT_USER\Software\Classes, while ALL calls HKEY_CLASSES_ROOT. Windows documents that HKCR is a merged view of HKEY_LOCAL_MACHINE\Software\Classes and the interactive user's Classes settings; the exact write destination can also depend on existing keys and permissions. Do not mistake the root-key name alone for proof that Cmder always writes to a separate machine-only store. Cmder documents ALL as the all-users option and its example calls for an Administrator prompt. Registration reads the launcher executable's current path and stores it in the shell command, with Explorer's selected directory passed as an argument. Therefore, when /REGISTER ALL reports “Access Denied,” first ask whether every user on the machine needs the menu. For a personal menu, the USER scope is usually narrower. For a managed device where everyone needs the entry, follow the repository's administrator instructions for ALL, then check visibility from another intended account on that Windows version.

The following is an unexecuted example based on the current repository documentation. Check the installed package's own help and version-specific notes before using it:

cd /d D:\Tools\Cmder
Cmder.exe /REGISTER USER

To remove a current-user entry, the corresponding documented direction is Cmder.exe /UNREGISTER USER. After registration, open Explorer, right-click a regular folder or its background, and confirm the terminal starts in the folder you selected. A command returning or printing a message is not a substitute for that interactive check. These commands were not run on a Windows device during this rewrite.

A failure path after moving a portable folder

Suppose you move Cmder from D:\Tools\Cmder to E:\Apps\Cmder. A command-window launch may still find the old copy because PATH still contains the first folder. The Explorer menu may also call the old executable path that was stored when you registered it. Both symptoms can look like “Cmder is broken,” but their evidence differs: where cmder checks PATH resolution in a new process, while a failed Explorer launch requires checking the executable path recorded for the shell entry.

A more controlled repair is to choose the new install location first, then unregister and register from the new location using the same scope. Open a new command prompt afterward and separately test Explorer at a chosen folder. If you also rely on user PATH, remove the old installation folder and retain only the intended executable directory. Do not change PATH temporarily inside the current Cmder session and conclude that the persistent Windows setting has been updated; a process-local change affects only that process and its children.

Avoid leaving both an old and a new menu registration behind. The launcher source records the path of the executable that performs registration, which is why a later move can leave a stale entry; this is an inference from code, not an observed failure on a user's PC. If /UNREGISTER appears not to remove the old entry, check whether it was registered as USER or ALL and inspect the same scope before repeating any elevated operation.

Version boundaries matter

Cmder retains a 1.x maintenance line. As checked on 27 November 2026, the top entry on its official Releases page is Cmder 2.0.0 RC 1, explicitly marked as a pre-release. The RC description lists packages with Windows Terminal, ConEmu, or a launcher, with different Git-inclusion variants, and says the release is available for community testing. Check the specific release assets and upgrade guide for the terminal, launcher, and Git that are actually inside your archive. Do not assume every 1.x shortcut, configuration path, and RC package has the same interface.

If /REGISTER USER does not work in the package you have, check that version's bundled help and release notes before copying a .reg file from an unrelated tutorial. A separate Cmder issue involves a malformed JDK entry in the environment PATH; see the JDK PATH troubleshooting guide. That is a bad variable value; this guide concerns two different launch integrations. Editing PATH is not a fix for a missing Explorer menu.

The decision can be reduced to three checks: for command-name lookup, inspect the user PATH and where cmder; for launching from the current folder, choose /REGISTER USER or /REGISTER ALL according to the intended scope; for a portable install, treat moving its directory as a reason to re-check both entries. Change only the integration that meets the need, then verify the real target from a new command window or Explorer. This keeps the configuration aligned with its purpose and leaves a clear rollback path.
