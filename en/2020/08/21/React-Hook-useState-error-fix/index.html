React says useState is called from a non-React function: identify the call site first

Diagnose this Hooks error by separating component naming, ordinary functions, conditional calls, custom Hooks, and class components, then verify the actual render path.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-27 · Estimated read 17 min
Translations
zh-CN en

Article

When React reports that useState is called in a function that is neither a React function component nor a custom Hook, do not assume that changing one lowercase letter fixes the whole problem. Hooks may be called only at the top level of a function component that React is rendering or at the top level of a custom Hook. A lowercase function used in JSX is normally treated as a host tag, while a function invoked as ordinary JavaScript does not become a component just because it returns JSX. Identify the caller first, then check that the Hook call order is stable.

Why a lowercase name can produce this message

Suppose the code is function newDeviceForm() { const [name, setName] = useState(''); return <input value={name} onChange={e => setName(e.target.value)} />; }. Even though the function returns JSX, <newDeviceForm /> is interpreted as a lowercase host element. React component names begin with a capital letter, so a component would be NewDeviceForm and be rendered as <NewDeviceForm />. Calling newDeviceForm() directly is still an ordinary JavaScript call. Naming is a recognition convention used by JSX and static tooling; it is not a permission switch that makes every function a valid Hook owner.

Renaming is appropriate only if this function really owns a rendered part of the interface and React renders it as a component. Rename both the declaration and its references, then check that callers use <NewDeviceForm /> instead of NewDeviceForm(), invoking it in a callback, or passing it to a helper that calls it as an ordinary function during render. If the function only validates data or handles a click, it should not own Hook state. Keep state in a component above it and pass values and callbacks as arguments.

Decide whether the function is a component, a custom Hook, or a helper

A component starts with an uppercase name, returns UI, and is created by React through JSX or createElement. A custom Hook starts with use, such as useDeviceForm; it may call other Hooks, but it must itself be called at the top level while a component or another Hook is rendering. An ordinary helper must not call useState. Those roles suggest different fixes: a component owns UI state, a custom Hook packages reusable state logic, and a pure helper receives input and returns a result.

Changing newDeviceForm to useNewDeviceForm is not automatically a fix if the function only handles submission. A custom Hook still has to be called at the top level of a component or another Hook. For example, function NewDeviceForm() { const [name, setName] = useState(''); function submit() { return saveDevice(name); } return <button onClick={submit}>Save</button>; } creates state at the component's top level. Clicking the button runs an ordinary submit function that uses existing state. If several components need the same form-state logic, extract useDeviceForm, call it at the top level, and pass its returned values to event handlers.

Uppercase names do not fix conditional or nested calls

function NewDeviceForm({ visible }) { if (!visible) return null; const [name, setName] = useState(''); ... } still violates the Rules of Hooks. The component name is valid, but one render may call zero Hooks and another may call one. React relies on the same Hook call order on every render to associate state with the correct call site. Move the Hook above the early return, or express the condition in the returned JSX.

Likewise, do not call Hooks inside an if, loop, try/catch, event handler, ordinary nested function, or a callback passed to useMemo or useEffect. For conditional UI, call the Hook at the top level and conditionally use its result. A click handler may call a setter such as setName; it must not call useState for the first time after the click. Class components cannot call function-component Hooks; keep class state or move the state-owning portion to a function component.

A misleading near-fix is to rename the function to NewDeviceForm but continue calling NewDeviceForm() directly from another function. A linter may stop reporting the lowercase-name problem, yet React still has no component boundary controlling that invocation. Compose components with <NewDeviceForm /> so React manages their rendering. If the caller needs a value rather than UI, keep a regular pure function and supply the necessary data as parameters.

Diagnose with lint and a minimal reproduction, not guesses

Inspect the declaration, nearby Hook calls, every call site, and the component tree around the reported line. After renaming, search for all old references so JSX, exports, routes, and tests are not missed. Confirm that the Hook sits at the function body's top level, before conditional returns, and that the function is actually rendered as a component. If the call path is unclear, temporarily reduce the component to one top-level useState and a small JSX result. Preserve the real invocation path in that reproduction; otherwise it may hide the bug.

React recommends the rules-of-hooks rule from eslint-plugin-react-hooks. Run the lint command already defined by the project (this article does not assume every project uses the same script name) and read whether the finding concerns component recognition, nesting, or a conditional path. A clean lint result means the static rule did not identify that violation; it does not prove the UI behaves correctly. Also inspect the component on initial render, across condition changes, and after interaction. If a conditional branch removes and later remounts a component, state may reset because the component instance changed, which is different from a Hook-order error.

Verify the state behavior, not only the disappearance of the warning

For a hypothetical form, verify three layers: the input component appears in the React tree as <NewDeviceForm />; useState is called in the component body in the same order on every render; and the submit handler reads or updates existing state without invoking a Hook during the event. Then run the project's lint command and relevant component tests, and inspect input, submission, and hide/show behavior. These are verification steps, not a claim that this repository's original React application was executed during this rewrite.

Keep the fixes distinct. If a lowercase component name caused the rule failure, rename it and fix its JSX call site. If a Hook is in a helper or event callback, move state ownership or extract a valid custom Hook. If calls are conditional or in a loop, restore an invariant order. If the code is a class component, keep class state or migrate the relevant UI to a function component. Do not convert every component to a class or change a dependency version merely because this message appeared. The decision depends on whether the function owns a UI lifecycle, whether state logic is shared, and which React component should own that state.

If the warning remains after the rename, inspect the actual render path, the installed React and lint-plugin configuration, and any ESLint configuration boundaries in a monorepo. A small diff that shows the reported line, call sites, and lint output is more useful than suppressing the warning. If the name, top-level placement, and React render path are all correct yet the warning remains, preserve that evidence for further diagnosis instead of continuing to rename functions mechanically.

For a related but separate concern, see the site's guide to React external-store snapshots and subscriptions. It addresses reading external state during concurrent rendering; it does not replace the Rules of Hooks.
