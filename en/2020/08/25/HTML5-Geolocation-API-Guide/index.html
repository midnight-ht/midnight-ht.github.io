A Browser Returned Coordinates. Why Might They Still Be Too Inaccurate?

A successful browser Geolocation callback does not prove that a position is accurate. Learn how HTTPS, permissions, accuracy, caching, timeouts, and watch cleanup fit together, with failure diagnosis and user fallbacks.

Updated 2026-11-27 · Estimated read 25 min
Translations

Article

Key takeaways

  • Geolocation returns a position estimate, not a promise of GPS or a real street address.
  • Interpret accuracy, timestamp, and maximumAge against the task's tolerance.
  • Secure context, user permission, operating-system location, and iframe policy are separate gates.
  • Continuous tracking requires clearWatch and a user-controlled fallback.

A successful Geolocation callback means the browser supplied a position object. It does not prove that the coordinates came from GPS, are fresh, or identify a street address. Check coords.accuracy, timestamp, and the task's tolerance before accepting the result, requesting another fix, falling back to a broader area, or asking the user to choose manually. Treating “received coordinates” as “precise location found” confuses a sensor estimate with a product decision.

The API returns an estimate, not a sensor promise

navigator.geolocation is the browser's interface for location. Call getCurrentPosition() for a one-time result; call watchPosition() to request subsequent updates, then stop them with clearWatch(). Its interface is source-agnostic: underlying information can come from GPS, network signals, or other system capabilities. The API does not prescribe a source order and does not guarantee that the returned position is the device's actual location. “We use Geolocation” therefore does not mean “we read a precise GPS fix from the phone.” The current W3C document is a Candidate Recommendation Draft published on 18 November 2026 and remains subject to change; the W3C Recommendation dated 13 June 2024 is the published Recommendation baseline.

Read at least three fields together: latitude and longitude are WGS84 coordinates; accuracy is a position-accuracy radius in meters; and timestamp represents when the position was acquired. Plausible-looking coordinates may still be unsuitable if the radius is too large or the fix is too old. The latest draft also changes probability wording for accuracy. That is draft material, not evidence that every deployed browser has adopted the same interpretation. At product level, treat accuracy as metadata about estimate quality, not proof of ground truth.

For example, a store finder might accept a coarse position to list nearby areas and let the user confirm a store. An address form should not submit an address solely because it received browser coordinates. “Accurate enough” depends on the task: centering a map, filtering by city, and recording a precise attendance point have different tolerances. The API does not choose that threshold for the product. The application must define it together with its fallback behavior.

Permission shown as allowed, but another gate can still fail

Separate the secure context, user permission, operating-system location setting, and embedding policy. Geolocation is exposed only in secure contexts; ordinary deployments should use HTTPS, with localhost being a common local-development exception. A non-secure context can fail with PERMISSION_DENIED, so that code alone does not prove the user clicked “deny.” MDN's Navigator.geolocation page also marks the property as requiring a secure context.

Browser permission and operating-system permission are different switches. A note in the 2024 Recommendation explains that a user may permit the browser site to use Geolocation while denying the browser access to system location services. If the page is inside a cross-origin iframe, Permissions-Policy can also block the API. The default policy is self; the parent must grant access according to the actual embedding relationship, and the iframe element must allow geolocation as well. User permission cannot override a policy that the server forbids. Diagnose these layers by checking HTTPS, iframe origin, response headers, and browser or operating-system settings instead of repeatedly calling the API. See MDN's geolocation Permissions-Policy guide.

Trigger the request from an explicit user action and explain the purpose and alternative before the browser prompt—for example: “Used to show nearby stores; precise location is not saved. You can choose a city instead.” The W3C requires express permission and advises recipients to request location only when needed, limit it to the stated purpose, and explain retention, use, and sharing. Permission to locate is not blanket authorization to store or forward coordinates forever. These are engineering and specification recommendations, not a substitute for reviewing the privacy laws that apply in the target jurisdiction.

enableHighAccuracy is only a hint

enableHighAccuracy: true is not a command to turn on GPS and does not guarantee a smaller error. This option is a hint the user agent may consider. A high-accuracy attempt may increase power use or response time; the device may have no better data, and the user agent can ignore the hint. For a page that only filters content by city, a lower-cost request is usually closer to the product's purpose. Ask for high accuracy only when a finer position changes the task and the user understands why.

maximumAge is the maximum age, in milliseconds, of a cached position the page is willing to accept. It is not a server cache duration and does not guarantee that the browser retains a cached value. A nearby-list feature might accept a position from tens of seconds ago; attendance or route recalculation should also inspect timestamp and reject a result that is too old for that task. timeout limits the position-acquisition phase. It does not include the time while a user is deciding whether to grant permission or while a hidden document waits to become visible. Setting a five-second timeout therefore does not guarantee that the entire button interaction will finish within five seconds.

Derive all three settings from the cost of the task: how old can the coordinates be and remain useful? How long should the application wait before showing a manual option? What decision can high accuracy change? If those answers are unclear, blindly shortening the timeout or enabling high accuracy by default is not a design decision.

A one-shot example and its state boundaries

The following example has not been run in a real browser or on a device. It shows one way to wrap the callback API in a Promise and distinguish an unavailable API, a failed request, an estimate outside the application's tolerance, and an old result. The thresholds are product assumptions, not standard requirements. The code does not send coordinates to a server.

function requestPosition() {
  if (!("geolocation" in navigator)) {
    return Promise.reject({ kind: "unsupported" });
  }

  return new Promise((resolve, reject) => {
    navigator.geolocation.getCurrentPosition(
      resolve,
      error => reject({ kind: "geolocation", code: error.code }),
      {
        enableHighAccuracy: false,
        timeout: 12000,
        maximumAge: 30000
      }
    );
  });
}

async function chooseNearbyArea() {
  try {
    const position = await requestPosition();
    const { latitude, longitude, accuracy } = position.coords;
    const ageMs = Date.now() - position.timestamp;

    if (ageMs > 30000 || accuracy > 1500) {
      return { state: "coarse-or-manual", accuracy, ageMs };
    }

    return { state: "usable-estimate", latitude, longitude, accuracy, ageMs };
  } catch (error) {
    return { state: "manual", reason: error.kind, code: error.code };
  }
}

The 30-second and 1,500-meter thresholds above are hypothetical. A real component should map usable-estimate, coarse-or-manual, and manual to visible states such as “Locating,” “Showing an approximate area,” and “Choose a city.” Even after success, the application need not upload precise coordinates. If the feature needs only a region, it can transform the result into a coarser area under an explicit rule and avoid retaining the precise original. If precise transmission is necessary, explain the purpose, recipients, retention period, and deletion path, then protect the transfer and storage according to the system design.

Read error codes without showing the raw message

Geolocation has three standard error codes: PERMISSION_DENIED (1) means the request was not permitted or ran in a non-secure context; POSITION_UNAVAILABLE (2) means a position could not be acquired; and TIMEOUT (3) means acquisition exceeded the requested limit. A denial at the operating-system layer can also surface as a permission error. These codes identify a failure stage, not necessarily one unique root cause. In development, record the code, whether the page is secure, the frame origin, and whether a success callback occurred—without logging coordinates—then decide whether to inspect policy or device settings.

Do not show error.message directly as user-facing copy. For legacy reasons, this developer-oriented field may be English-only; applications are advised to localize messages from code. For a denied request, explain how the user can change settings or enter a place manually. For temporary unavailability or timeout, offer a retry and an alternative. A retry must not pretend to reverse the user's explicit refusal. Error handling should not add coordinates to logs when the failure path has no need for them.

watchPosition needs an explicit stop condition

Use watchPosition() only when the product needs to observe movement over time. It returns a watch ID; call clearWatch(watchId) when a component unmounts, the user leaves the map, or continuous location is turned off. In component frameworks such as React, bind cleanup to the ID created by that subscription so that an old page cannot accidentally clear a newer watch. Starting a watch to obtain one current position adds permission and power cost, and can create repeated renders or repeated backend requests.

The permission or location capability may change during a watch. Present an update error as a recoverable state, and continue checking age and accuracy for each successful update; a later callback is not automatically more useful to the task. If the page records a movement history, design consent, retention, and deletion separately. For a feature that does not need a track, storing the user's selected store or area may fit the domain better than retaining precise coordinates. That is a data-modeling choice, not a Geolocation API requirement.

Verify simulated inputs separately from real-device results

Build a state matrix: API unavailable; insecure HTTP page; HTTPS; user accepts and denies; operating-system location is disabled; cross-origin iframe policy allows and blocks; acquisition succeeds but accuracy exceeds the business threshold; a cached result has an old timestamp; acquisition times out; and a watch is stopped. For each state, verify the visible copy, fallback, and whether any network request occurs. Automation can use the specification's geolocation emulation to supply fixed coordinates or error cases. That verifies the code's response to those inputs; it does not establish a real phone's system settings, sensor quality, or indoor accuracy.

Where possible, separately test the target browsers and devices, recording browser version, device location setting, permission choice, page protocol, embedding origin, reported accuracy, and timestamp. Do not generalize one device result to all devices. Test cross-origin iframe and Permissions-Policy behavior against the browser versions you support; MDN notes that browser support for this policy directive is incomplete. When accuracy is insufficient, showing a broader result or asking the user to confirm is often the correct response. Unconditionally changing enableHighAccuracy to true is not.

If the browser says permission is allowed but the call still fails, inspect secure context, frame origin, and Permissions-Policy first; then check the site's browser permission and the operating-system location service; finally inspect timeout, cache, and location-source availability. This ordering prevents unrelated layers from collapsing into “the browser does not support it.” Geolocation can return an estimate whose source is not exposed, with an acquisition time and an accuracy radius. The application must decide whether that estimate is sufficient for attendance, navigation, or nearby search. The related article on the Permissions Policy lifecycle boundary for camera access also separates embedding policy, user permission, and resource lifecycle.

Verification note: The code is an explanatory example and was not executed in a real browser, phone, or operating-system permission environment. Test the state matrix on the browsers and devices you actually support before deployment.
