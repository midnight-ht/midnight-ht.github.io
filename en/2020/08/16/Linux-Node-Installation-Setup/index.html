Node.js Is Installed on Linux, So Why Does a Service Run Another Version?

A Linux login terminal, systemd service, and cron job can have different PATH values. Choose an installation model per process, then verify lifecycle, architecture, checksums, and npm prefix.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-27 · Estimated read 27 min
Translations
zh-CN en

Article

When Node.js is installed but a service reports node: command not found or starts an old version, inspect the PATH inherited by that process before reinstalling Node. A Linux login terminal, cron, and systemd do not necessarily share the same environment; node -v after login proves only that the current shell can find a runtime. A developer workstation may need different major versions across projects, making a version manager a good fit. A server with one approved runtime may instead use a versioned directory and controlled entry point, or a distribution package. This article follows the decision from version selection through process environment and executable verification. It did not install Node.js on a Linux server, and it does not reuse the old Node.js 14 download command as current guidance.

Start with the usage boundary: how many Node versions does the machine need?

An installation method is also a version-switching policy. On a workstation with several repositories, project A may still require an older major version while project B has moved on. A single /usr/local/bin/node pointing to one fixed directory makes “run Node in this project” depend on hidden machine-wide state. After switching projects, forgetting to switch the runtime can produce a mismatch where dependency installation succeeds but the build runs under another major version. A per-user version manager stores files in the user’s home directory and selects an active version when a shell starts. For example, the nvm project documentation describes it as a per-user tool loaded by a shell. That works well for developers and CI version matrices. Its boundary is non-interactive services: cron or systemd may not load the same shell profile, so a successful node -v in a login terminal does not prove that a service can find Node.

A fixed installation under a versioned directory such as /opt/node/<version>, selected through a controlled current symlink or service configuration, suits a single runtime that must be auditable and reversible. Before switching, check whether services still use the old path. Replacing /usr/local/node in place can make old processes, new processes, and operational scripts observe different states during the change, and makes rollback harder. Distribution packages integrate with system upgrades and permissions, but their version may not match the project’s requirements. Check .nvmrc, engines, CI configuration, and the lockfile before choosing a source rather than simply choosing “the latest.”

The Node.js release table identifies Current, LTS, Maintenance LTS, and EOL lines. The project recommends Active LTS or Maintenance LTS for production applications. After a version reaches EOL, it no longer receives security fixes from the project. These statuses change, so this article does not hard-code one version as the right choice today. Return to the official release status page, choose a supported line, and check compatibility with the project’s dependencies. If a dependency has not adopted the newest major release, record that constraint and an upgrade plan instead of quietly treating an EOL runtime as a long-term solution.

Check the platform, architecture, and source before downloading

First identify the operating system and CPU on the target machine:

uname -s
uname -m
getconf GNU_LIBC_VERSION 2>/dev/null || true

x86_64 usually maps to an official Linux x64 build, and aarch64 usually maps to arm64. However, the distribution’s libc, dynamic loader, and ABI can also determine whether the executable starts. A seemingly correct filename can still lead to Exec format error, a missing shared library, or GLIBC_x.y not found. For those errors, inspect the downloaded asset’s platform label and the system ABI first; changing a symlink will not fix an incompatible binary. The official downloads page lists assets by platform, version status, and verification guidance. If the system is not covered by an official prebuilt asset, consider a distribution package or a maintained build process, and document who owns its toolchain and upgrades.

Do not trust the filename alone after downloading. Official release records provide SHASUMS and signature-verification instructions. For example, the Node.js 24.22.3 release record lists Linux x64, arm64, and musl assets plus a signed SHA-256 manifest. This is an example of a verifiable release record, not a recommendation that every system or project use that version. Obtain the required asset and its checksum manifest from the official release directory, verify the signature according to the official instructions, and then compare a locally calculated archive digest with the manifest. Comparing a hash downloaded from the same unverified mirror can detect transfer corruption, but does not prove that the manifest itself is authentic. For a server installation, record the version, platform asset name, verification result, download source, and operator in the change record. This article did not download or verify an installation archive, so it does not provide invented checksum output. Use the exact verification procedure currently published by Node.js.

What problem do the extraction directory and symlink solve?

If you choose an official tar archive, place the version in a separate directory such as /opt/node-v26.x.y-linux-x64 and check its owner and permissions. An untrusted ordinary account must not be able to modify a node or npm executable that root has placed on the system PATH; otherwise a later privileged script could run a replaced program. Whether sudo is needed should follow from directory ownership, not from adding it to every installation command.

A symlink is a simple entry point for a fixed installation:

sudo ln -s /opt/node-v26.x.y-linux-x64/bin/node /usr/local/bin/node
sudo ln -s /opt/node-v26.x.y-linux-x64/bin/npm /usr/local/bin/npm

Before doing this on a real host, check whether either target already exists. ln -s fails when a target is present, and deleting an old entry blindly can damage a file managed by the distribution’s package manager. Use command -v node and readlink -f "$(command -v node)" to identify the current executable before changing the policy. node, npm, and npx should come from the same installation. If Node is replaced while npm still points to another directory, version information and global package behavior become difficult to explain. Keeping each version in a separate directory and pointing a controlled link to it makes rollback a matter of switching the entry point. A service manager may retain an old environment, however, so restart the relevant service and inspect the executable path of its process after a switch.

Which profile file should receive PATH depends on how the program starts

Interactive Bash, login Bash, Zsh, and non-interactive shells read different startup files. The GNU Bash Reference Manual section on startup files distinguishes login shells, interactive non-login shells, and non-interactive scripts affected by BASH_ENV; therefore, a PATH entry in /etc/profile does not imply every service will read it. Appending export PATH="/opt/node-v26.x.y-linux-x64/bin:$PATH" only to /etc/profile does not guarantee that a systemd service or cron job loads it. Writing configuration only to a personal ~/.bashrc does not guarantee that a service running as another user inherits it. Prefer an absolute path in the service unit’s ExecStart, or provide a reviewed PATH in the service’s own environment configuration. For an interactive login terminal, choose among ~/.profile, ~/.bash_profile, or ~/.bashrc based on the shell’s startup mode, and avoid appending the same directory to several files.

An absolute path makes runtime selection explicit and reviewable. PATH is more convenient, but its order determines which executable with a given name is called. After changing configuration, do not rely only on the current shell: open a new login shell and check type -a node npm, command -v node, node --version, and npm --version. Then perform equivalent checks under the target service account. If that service cannot log in interactively, use its service configuration or a one-off diagnostic task to print process.execPath and the environment PATH. These are verification steps, not results from a real service; this article did not run them on a production host.

Why can global npm installs cause permission problems?

The Node runtime path and npm’s global package prefix are separate settings. npm’s folder documentation distinguishes project-local node_modules from global package and executable locations under the prefix. Running npm install -g as root writes executables and packages into root-owned directories, which an ordinary user may then be unable to update. Recursively changing permissions to “fix” this can break the boundary between the distribution and manually installed files. Check npm config get prefix and npm root -g, and confirm that the PATH includes the bin directory under that prefix. If only one user needs a global CLI, choose a prefix writable by that user and add its bin directory to that user’s PATH. For a server process, it is often better to pin tools in a deployment manifest than to depend on a global package in an administrator’s home directory.

Many projects do not need global build tools at all. If a repository has a lockfile, use a compatible npm version and run npm ci, then invoke local dependencies through a script declared by the repository and run with npm run. This connects package versions to repository state. When switching Node major versions, native extensions may need to be reinstalled because their binaries depend on the runtime ABI. Do not copy a developer’s global node_modules directory to a server; build and verify on the target platform using the lockfile. The distinction between a lockfile and the complete build input set is covered in the site’s npm ci build-input article. Exact npm commands depend on the repository scripts, and this article does not claim to have run installation or build commands for a sample project.

Finish with mutually consistent checks

The goal of verification is to confirm that the executable being called is the executable you intended to install. First check that command -v node resolves according to the chosen policy, then confirm with readlink -f that it points to the expected version directory. Run node --version and npm --version; inspect the global write scope with npm config get prefix; finally, run the project’s version constraint check and lockfile installation process. If node -v is right but npm -v resolves from another prefix, the installation is not complete. If the interactive terminal works but systemd fails, investigate environment inheritance or the service’s absolute path rather than repeating the download.

A reviewable change record should contain at least the intended major version and support status, distribution and architecture, reason for the installation method, artifact verification basis, before-and-after directory and link state, where PATH takes effect, verification commands, and rollback entry point. Replace the example version string with the exact version approved for the project; do not copy the placeholder from this article. For a low-privilege user, install in that user’s home directory and avoid sudo npm. For one machine-wide version, let an administrator manage separate versioned directories and explicitly select one in the service configuration. For multiple projects requiring concurrent versions, use per-user version management or containerized runtimes and make sure automated jobs also select the version explicitly. There is no single installation command suitable for every Linux host.

If Node is installed but a command says “not found,” which process is looking for it?

Distinguish an interactive terminal from SSH non-interactive commands, cron, and systemd. Inspect each process’s actual PATH and check command -v node. If only a login shell can find Node, add PATH to the right startup environment or use an explicit executable path. Reinstalling immediately will not fix a service that never loads the shell profile. If the path is correct but a shared-library error remains, inspect architecture and ABI. If the wrong version runs, inspect PATH order or the project version switcher. Locating the failing environment layer avoids replacing a valid system installation to solve an environment inheritance problem.

Release lifecycle and download mechanisms described here come from current Node.js official pages; npm directory behavior and Bash startup-file rules link to their respective official documentation. Advice about choosing an installation method is editorial judgment. Command snippets are configuration examples; they were not run on a production server. Before a real change, recheck release status, package format, signature verification instructions, and service startup environment for the target distribution.
