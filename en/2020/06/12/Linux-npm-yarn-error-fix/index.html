npm or Yarn reports ENOSPC on Linux: identify the inotify limit that ran out

Diagnose Node development-server watcher failures by separating watch, instance, queue, and file-descriptor limits, then verify the responsible process before changing a kernel setting.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-27 · Estimated read 17 min
Translations
zh-CN en

Article

When an npm or Yarn development command reports Error: ENOSPC: System limit for number of file watchers reached, the disk is usually not full and the package manager is not necessarily at fault. Linux inotify may have refused another watch because the real user reached max_user_watches, but max_user_instances, an instance's event queue, file-descriptor limits, and container or host policy can produce related failures. Diagnose the exhausted resource and the process creating watches before deciding whether to narrow the watched tree or raise a kernel limit. Copying a large number from a forum only hides where the resource is going.

Why npm and Yarn encounter kernel watchers

Installing packages does not normally keep watching the entire project. The error more often appears after starting npm run dev, a test watcher, a build service, or an editor language server. Such processes watch source files so they can rebuild on changes. Workspaces, generated directories, dependency trees, and several simultaneous projects can cause a tool to create many watches. inotify is the Linux kernel interface for filesystem events. User-space programs create inotify instances and add watch descriptors to them. Limits are managed across a real user ID and other kernel scopes; they are not simply a per-project maximum file count. An editor, language server, test runner, and multiple development servers under the same user may all contribute.

That is why stopping one terminal process may not help: an editor or another repository can still hold watches. Conversely, a repository with many files does not consume the entire quota merely by existing when no process is watching it. A watcher may also follow a configured tree that includes generated output or mounted directories, making the monitored set larger than the source folder visible in the editor. Turn “this project is large” into evidence about processes and file descriptors before treating directory size as a quota measurement.

Read the three inotify limits separately

On many Linux distributions, inspect:

cat /proc/sys/fs/inotify/max_user_watches
cat /proc/sys/fs/inotify/max_user_instances
cat /proc/sys/fs/inotify/max_queued_events

max_user_watches limits the watches a real user may create. max_user_instances limits how many inotify instances that user may create. max_queued_events limits events queued for each instance; excess events may be dropped and reported through queue-overflow handling. It is not another spelling of “too many watches.” These values tell you the configured ceilings, not how much capacity is currently used. The Linux man-pages documentation describes these /proc/sys/fs/inotify parameters as controls on inotify resource consumption.

Also separate ordinary file-descriptor limits. A process's ulimit -n or a systemd LimitNOFILE affects how many file descriptors it can open; that is not the same limit as the number of watches. An application may fail to create another inotify instance or open a descriptor, then wrap the underlying error in a confusing message. Use the complete stack trace, process logs, and relevant kernel messages. Do not route every ENOSPC through a watch-limit increase.

Find the process holding watches and the tree it monitors

Stop known development servers and test watchers, then see whether a new watcher can start. This is a useful controlled comparison: if stopping one long-lived process changes the result, inspect that process's watch scope and lifecycle. If nothing changes, check other sessions, containers, and services under the same UID. Inotify file-descriptor information can provide clues:

for p in /proc/[0-9]*; do
  for fd in "$p"/fdinfo/*; do
    grep -q '^inotify ' "$fd" 2>/dev/null && printf '%s %s\n' "$p" "$fd"
  done
done

This example scans the /proc entries visible to the current process. Permissions, PID namespaces, and host configuration can hide processes, so it is not a complete system-wide ledger. An inotify entry in /proc/<pid>/fdinfo/<fd> can show watch descriptors associated with that descriptor; map the PID to its command and parent process for context. Several of the relevant processes may be children of an editor, and closing one editor window does not guarantee that its watcher has exited.

If each development-server start quickly exhausts the limit, inspect the configured root and ignore rules. Are node_modules, dist, generated code, build caches, or a large mount included in recursive monitoring? Are several dev servers running? Does a test or reload process release watches when it exits? Narrowing the scope with the tool's supported ignore settings is often easier to explain, roll back, and verify than raising a global ceiling. Option names differ between tools; do not copy an unverified --no-watch flag.

When increasing max_user_watches is justified

Consider changing fs.inotify.max_user_watches only when evidence points to the watch ceiling, the monitored tree is reasonable, and the development tools have a clear concurrent-monitoring need. A temporary experiment can use:

sudo sysctl -w fs.inotify.max_user_watches=131072
cat /proc/sys/fs/inotify/max_user_watches

131072 is an illustrative candidate, not a universal recommendation or a value tested on the target machine. Start from the current value, raise it in a measured step, and observe the processes and kernel memory instead of blindly setting 524288. Watches consume resources. A higher ceiling permits more watches; it does not release leaked ones or correct an overly broad watch tree.

If a persistent change is necessary, use the distribution's supported sysctl configuration mechanism, such as a dedicated file under /etc/sysctl.d/, and record the reason, rollback value, and owner. Apply it through the loading method for that distribution. Do not describe sysctl -p as a required reboot; it reads a configuration file (commonly /etc/sysctl.conf by default), while loading files from other directories depends on system services and distribution behavior. In a container, you may not have permission to change a host kernel parameter. Editing a file inside the container may not alter the host limit; an administrator with authority over the relevant kernel namespace and policy may need to act.

Verify a fix instead of just checking a larger number

Record the original error, limit values, and relevant processes. Change one condition at a time: for example, stop a second watcher, or raise only the watch ceiling. Restart the command that failed and confirm that it can create its watches; then observe normal use for a while. Shut down the watcher and check that resource use does not keep increasing through repeated starts. If the failure remains, inspect the instance limit, descriptor limits, queue-overflow handling, and container boundaries instead of repeatedly increasing the same setting.

Different evidence calls for different remedies. If failure occurs only in one large workspace, inspect monitored roots and generated directories. If several projects under one user fail, look for UID-wide shared consumption. If the container's visible values differ from the host's, determine which namespace and policy apply. If a burst of filesystem events causes queue overflow, check whether the program drains events promptly and rescans state correctly. Inotify notifications do not promise a distinct event for every underlying change; applications must account for coalescing and recover from overflow by reconciling filesystem state.

The commands above were not run on the target Linux host during this rewrite. The number and shell loop are explanatory examples. Before changing a real system, confirm its distribution, systemd or container limits, runtime user, and rollback path. The site also has a guide to Node fs.watch behavior when a watched file is replaced. That article covers a watch remaining tied to an old file object after replacement, which is a different failure from exhausting inotify capacity.

Sources and limits: The Linux man-pages entry for inotify(7) was checked for the definitions of the three /proc/sys/fs/inotify limits. The commands are not presented as tested on a particular distribution. npm and Yarn are common ways to launch development watchers, but each watcher's implementation, ignore options, and container limits must be checked in the actual tool and distribution documentation.
