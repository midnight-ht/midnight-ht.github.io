webpack 5 Cannot Find config-yargs: Check the CLI and dev-server Pair

This error often comes from a dependency importing an internal webpack-cli path. Trace the stack and lockfile before choosing a CLI rollback or dev-server migration; switching to webpack serve alone is not a universal fix.

Key takeaways

  • A module-resolution failure is not the same as a webpack compilation failure; locate the caller in the stack.
  • `webpack serve` is a CLI entry point, not an automatic repair for private imports or incompatible packages.
  • Validate webpack, webpack-cli, dev-server, Node, and migrated configuration as one change set.

When Cannot find module 'webpack-cli/bin/config-yargs' appears, do not immediately conclude that “webpack 5 changed the command.” The error usually means that some startup code is trying to load a CLI internal path that is absent from the installed package. First identify which package is loading it, then choose a repair from the actual versions of webpack, webpack-cli, and webpack-dev-server. webpack serve is a development-server command provided by webpack-cli, but changing the command does not by itself repair a broken deep import.

The historical case discussed here comes from a public webpack-dev-server issue. The reporter listed Kali 2020, Node 10.21.0, npm 6.14.7, webpack ^5.0.0, and webpack-dev-server ^3.11.0, and said that the CLI directory layout had changed after an update. The report did not include a complete project manifest, lockfile, or reproducible repository. The CLI 4.0.0 version was described by the reporter as a recent update, not established by a lockfile attached to the issue. Treat it as a bounded incident report, not a root cause reproduced by this article. The official CLI documentation, webpack 5 migration guide, and dev-server v4 migration requirements are discussed separately below; modern compatibility constraints cannot be projected backward as proof of the dependency tree used in 2020.

The error points to an import edge, not a compilation result

Cannot find module is a Node.js module-resolution failure: running JavaScript tried to load a module identifier, but resolution could not find it from the current dependency location. Webpack may not yet have read an entry, run a loader, or produced a bundle. A stack frame inside webpack-dev-server/bin/webpack-dev-server.js directs attention to the dev-server startup code and local CLI package layout. A frame in a project script or configuration suggests a direct application-level dependency. A stack path narrows the search better than the broad label “webpack 5.”

When a dependency uses an import such as require('webpack-cli/bin/config-yargs'), it relies on the package’s directory layout rather than a stable public CLI interface. A major CLI release can adjust its files and folders. A caller that assumes an older private path exists can fail at startup. This differs from a webpack configuration-validation error: changing loaders, entries, or mode cannot make a missing CLI-internal file appear.

Record the resolved package tree from the failing project root instead of relying only on version ranges in package.json:

node --version
npm --version
npm ls webpack webpack-cli webpack-dev-server
npx webpack --version

These commands are diagnostic examples and were not run in the original incident project. A range such as ^4 describes a range of allowed versions, not necessarily the one currently installed. The lockfile, package manager, workspace hoisting, and nested dependencies all affect the resolved tree. Also preserve the complete stack trace, package.json scripts, lockfile changes, duplicate CLI copies, and whether startup uses the project-local binary or a global install. A global webpack version is not proof of which local version the build script resolves.

Identify the dependency edge that broke

Draw the startup chain: project script → webpack-dev-server command → webpack-cli → webpack compiler. The original issue report shows dev-server 3.11 and webpack 5 in the same environment and says the CLI layout changed after CLI 4.0.0 appeared. Given the failing path, a plausible explanation is that older startup code expected a private CLI file that the updated CLI no longer exposed at that location. That explanation fits the symptom, but it remains a diagnosis based on the report because the original lockfile and reproduction repository are unavailable.

That is why “install the latest webpack-cli” is not a complete fix. The CLI, development server, Node, and webpack each have support ranges. The current webpack-dev-server v4 migration guide lists Node.js 12.13.0, webpack 4.37.0 or later, and webpack-cli at least 4.7.0 for the documented v4 migration. The current webpack CLI documentation also changes its compatibility matrix as major releases change. Those constraints describe the cited v4 migration version; they do not establish that early CLI 4.0.0 or every historical package combination satisfies them. Updating one package can replace the missing-module error with an incompatible dev-server option, an unsupported Node version, or a CLI command that is not available in that installation.

The repair sequence should therefore be: identify which installed package owns the failing import, consult the migration guidance for that package version, and then select a supported set of versions together. For example, if a project must retain an older dev-server v3 configuration, do not upgrade only the CLI to a version that changes its internal layout. Check the CLI range declared by that dev-server version; either restore a previously working CLI from the lockfile or plan an explicit dev-server v4 migration. Do not infer a universal fixed version from one public issue.

webpack serve addresses command entry selection

The current webpack CLI documentation lists serve as the command for running webpack-dev-server, with npx webpack serve as an example. This differs from invoking a webpack-dev-server binary directly, but that difference does not prove that a command name caused this module-resolution error. If the local CLI starts normally and the missing import occurs only in an older dev-server execution path, switching to the CLI’s serve command may change the invoked entry point. Whether it removes that old internal import must be verified against the installed versions. One CLI example is not a substitute for checking the package graph.

A modern project can express its local entry points explicitly in npm scripts:

{
  "scripts": {
    "build": "webpack --config webpack.config.js",
    "dev": "webpack serve --config webpack.config.js"
  }
}

This shows script entry points; it is not a drop-in fix for every historical webpack-dev-server combination. Webpack’s installation guide recommends installing a local webpack-cli when command-line builds are needed, so each project can upgrade independently. A real migration must also check whether dev-server configuration changed between major versions, including option names, minimum Node, and CLI requirements. The webpack serve command does not automatically convert configuration.

If a project only needs a production build and not a local development server, the failing script may be trying to start the wrong tool. Keep a webpack --config ... build command separate from a webpack serve ... development command. A successful build only proves the production configuration worked; it does not prove the dev-server chain is fixed. Conversely, a running dev server does not prove production mode or asset output is correct. Keep separate acceptance steps for both paths so a startup repair does not blur their meanings.

Update dependencies in a reversible way

Preserve the failure context first: commit or copy package.json and the lockfile, and save npm ls output and the full stack trace. If a previously working environment changed after a lockfile or dependency-range update, compare against the last known install in an isolated branch and use npm ci; do not start by deleting the lockfile. npm ci requires the lockfile and manifest to agree and installs from the locked dependency graph. If the same failure remains, the known graph may already include the conflict. Compare the resolved package versions rather than treating a cache clean as a root-cause fix.

For an upgrade, treat webpack, webpack-cli, webpack-dev-server, and Node as a compatibility group. Read the target versions’ minimum requirements and migration changes before updating. Then adapt the configuration and run the build and dev server separately. In the browser, check the features the project actually uses: served assets, hot updates, proxies, and fallback routing. Bind each check to an observable result: module loading, compilation, page delivery, and expected HMR behavior. Running npx webpack --version alone does not show that the application is repaired.

A rollback should restore the changed versions and configuration as a set. If you revert only webpack-cli but retain options migrated for dev-server v4, the older server may reject those new fields. If you restore only the lockfile while package.json still requires the newer major, the next installation can resolve a different tree again. Review the manifest, lockfile, scripts, and config together, and use lockfile-based installs in CI to stabilize results.

A diagnostic path with explicit failure branches

Start with the first project dependency in the stack trace. A webpack-dev-server frame trying to load webpack-cli/bin/... calls for comparing the installed dev-server and CLI. A project-owned script points instead to searching for a direct import of a CLI-private path. When the command is webpack-dev-server, check the local CLI and server versions for their supported entry points. Only after selecting a compatible set and adapting its config should you decide whether to change the script to webpack serve. Afterward, install from the lockfile, start the dev server, and run a separate production build. Each step tests a specific hypothesis rather than issuing a blind sequence of install commands.

Keep the next error distinct. If npm ls shows multiple CLI copies, Node may resolve a different one than the root package suggests. If webpack serve says the command is unavailable, verify that the local CLI is installed and that the installed version provides that command. If the missing-module error disappears but an unknown devServer option follows, that is a separate migration-compatibility issue. If webpack build succeeds while the dev server fails, the two scripts traverse different paths. A new error during an upgrade does not prove the first diagnosis wrong; continue from the new stack instead of rewriting the entire configuration at once.

Webpack’s v5 migration guide recommends upgrading the CLI, plugins, and loaders in use and checking new errors and deprecations. It does not say that “Webpack 5 universally renamed the webpack-dev-server command to webpack server.” The current CLI documentation lists serve|server|s as aliases, but availability depends on the installed CLI. This article addresses module resolution, using the opened official migration documents and one historical public issue. The original project manifest is unavailable, so no code sample was executed and no fixed version combination is claimed to work for a particular application.
