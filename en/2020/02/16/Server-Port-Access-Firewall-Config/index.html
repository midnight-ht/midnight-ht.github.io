A service is running but unreachable publicly: trace listeners, routes, and access rules

Diagnose an unreachable ECS service from its listening socket through Alibaba Cloud security groups, firewalld, network ACLs, and the return path, without exposing management ports broadly.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-27 · Estimated read 18 min
Translations
zh-CN en

Article

A process reporting “started” does not mean an internet client can reach it. A TCP request crosses the client's route, the cloud public-address mapping, the security group attached to the ECS network interface, any subnet network ACL, the Linux host firewall, the process's listening socket, and the response path. First confirm on the server that a process listens on the intended address and port; then test from the host, from another VPC machine, and from an external network. Change one rule at a time, use the narrowest source range, and verify that the rule applies to the intended interface and zone. A security group cannot substitute for starting the service, and allowing every IPv4 source should not be the default authorization for every port.

Layer one: is a process listening on the right address and protocol?

Inspect the process before changing a cloud rule:

sudo ss -lntup
sudo ss -lntp 'sport = :8080'

The loopback address accepts connections only from the local host. A packet that reaches a network interface will not be accepted by that socket. An IPv4 wildcard listener binds all local IPv4 addresses, while an IPv6 wildcard listener may or may not also accept IPv4, depending on socket configuration. Typical forms are shown below; replace the example port with the one used by the service:

127.0.0.1:8080   loopback only
0.0.0.0:8080     all local IPv4 interfaces
[::]:8080         IPv6 wildcard

Confirm the protocol too. A browser's HTTP request uses TCP, while a UDP service needs a UDP test. Reaching a TCP port says nothing about whether a UDP listener is open. If the process runs in a container or a separate network namespace, the host's ss view may not show the container listener; inside the container, the loopback address refers to the container's own interface.

Test the service's health endpoint locally and then through the server's private address. If the loopback test succeeds but the private-address test fails, examine the bind address and host-local filtering. If neither works locally, return to the process, port, protocol, and service logs instead of adding more cloud allows. The address below is only an example:

curl -v http://127.0.0.1:8080/health

ss is a snapshot of sockets; it does not prove that the application handles the expected path or that a public route exists.

Layer two: does the cloud security-group rule match the inbound flow?

An Alibaba Cloud ECS security group is virtual access control attached to an interface. A rule must match the traffic direction, protocol, destination port, and source address. When an instance has multiple security groups, their rules and priorities are evaluated together. Confirm which groups are actually associated with the target ECS instance or ENI, and check the region and VPC before reviewing inbound rules. A TCP 8080 example should explicitly name TCP, destination port 8080/8080, the allowed source, and the allow policy. If the application is only for an office or bastion host, use a fixed-address /32, an administrative subnet, or an appropriate security-group source instead of authorizing every public address.

In the console, 80/8080 denotes a port range, not just ports 80 and 8080. For several discrete ports, use a supported port list or separate rules and check quota limits. Inbound is the direction for a client connecting to ECS; adding the rule only to outbound traffic will not fix an inbound connection. Alibaba Cloud security groups are stateful for established connections, so a matching response rule is normally unnecessary. That does not automatically satisfy unrelated outbound dependencies of the application.

From a controlled external machine, test a TCP web port with curl -v --connect-timeout 3 http://PUBLIC_ADDRESS:8080/ or nc -vz PUBLIC_ADDRESS 8080, while capturing packets on the server with sudo tcpdump -ni any 'tcp port 8080'. If no external SYN appears in the server capture, suspect public-address mapping, routing, cloud rules, or an ACL. If a SYN arrives but the server sends no SYN-ACK, inspect the host firewall, listener address, and kernel routing. If the handshake completes but the application returns an error, network traffic has reached the application path; continue with HTTP/TLS, virtual-host, and application logs. A packet capture shows what reached the observed interface; it does not by itself identify which policy dropped traffic elsewhere.

Layer three: firewalld runtime rules and permanent rules

If the system uses firewalld, inspect its state, active zones, and the interface's zone:

sudo firewall-cmd --state
sudo firewall-cmd --get-active-zones
sudo firewall-cmd --zone=public --list-all

Checking only --list-ports can miss a service-based allow rule or inspect the wrong zone. A port rule must be in the zone that handles the traffic. These commands first add TCP 8080 to the runtime public zone, then to the permanent configuration and reload it:

sudo firewall-cmd --zone=public --add-port=8080/tcp
sudo firewall-cmd --permanent --zone=public --add-port=8080/tcp
sudo firewall-cmd --reload
sudo firewall-cmd --zone=public --query-port=8080/tcp

These are examples, not commands reported as executed on a production host. The firewalld documentation distinguishes runtime changes from permanent configuration: a runtime-only change can disappear after reboot or service restart. Check both states. If firewalld is not running, do not start it merely to make a command return output. First determine whether the host uses nftables, another host firewall, or cloud-side controls. Starting a previously disabled firewall can also block SSH; have an out-of-band console or a clear rollback path before changing it.

Treat the route as hypotheses that can be disproved

Suppose the application listens on all local IPv4 interfaces and a local health check works, but a home network times out. Do not restart the service, open a wide port range, and disable the firewall at once. Record evidence in order: did the external capture see a SYN; is there a TCP 8080 inbound allow with a source that includes the test client's public IP; does a subnet ACL allow both the request and return traffic; is the active host zone the one attached to the interface; does the kernel send a SYN-ACK? Test on each side of a boundary. This turns “the port is closed” into hypotheses that can be falsified and avoids changing the wrong layer.

If the public IP is provided through an EIP/NAT, load balancer, or reverse proxy rather than directly configured on the ECS interface, the client-facing port can differ from the backend port. Check the forwarding target, health check, listener, and backend security-group source. Behind a load balancer, the backend should often accept traffic only from the load-balancer instance or its security group rather than expose the application port directly to the internet. IPv6 clients need an IPv6 address, route, and IPv6 CIDR rule; allowing every IPv4 source does not automatically allow every IPv6 source. The CIDR examples below distinguish those two broad ranges:

0.0.0.0/0   all IPv4 sources
::/0        all IPv6 sources

Limit exposure when opening a port

Public websites commonly need public clients to reach HTTP/HTTPS on ports 80 and 443. SSH, RDP, databases, and administration panels should usually be limited to an administrative egress address, a VPN, a bastion host, or an internal VPC source. If a database serves only application machines in the VPC, prefer referencing the application security group or its private network. Review allow and deny rules in light of rule priority and the combined set of groups. Record the existing rules, make one change at a time, and test from both an intended and an unintended source. “It connects” is not sufficient acceptance: if an untrusted source also connects, the authorization is too broad.

Rollback should remove the exact rule added for the change or restore the prior zone configuration; it should not flush the whole host firewall. For production, validate first in a test environment with a similar network structure and retain console access to the instance. Security groups, ACLs, host firewalls, and process listeners are separate boundaries; an allow at one layer cannot override a deny at another. Without access to the target instance and packet evidence, this article provides a diagnostic method and does not claim that a real ECS port was opened or publicly accepted.

Sources and scope: Checked Alibaba Cloud ECS documentation for “Security group rules” and “Security groups”, plus the firewalld guide “Open a Port or Service”. Default security-group behavior, rule priority, and console steps depend on security-group type, ENI, region, and product UI; use the rules attached to the target instance and current documentation. The site's inotify watcher limit guide concerns filesystem-event resources, not network port filtering.
