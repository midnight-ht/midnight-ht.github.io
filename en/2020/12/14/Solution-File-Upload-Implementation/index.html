FormData or Base64 for a Browser File Upload?

For an ordinary file endpoint, append the File to FormData; use Base64 only when a text-only contract requires it. This guide explains multipart boundaries, encoding overhead, and the gap between transfer progress and server persistence.

Key takeaways

  • Send File directly through FormData for ordinary multipart endpoints; leave the boundary header to the browser.
  • Base64 is text encoding, not compression; an assumed 8 MiB file yields about 10.67 MiB of encoded payload.
  • A browser reaching 100% transfer still needs the HTTP response and business validation result.

For an ordinary browser upload, input.files is a FileList, not a stream or an array of file bytes. Each selected File carries metadata such as a name and modification time and exposes the binary-data behavior of Blob. The usual path is to append that File directly to FormData and send it with XMLHttpRequest or fetch. Convert it to Base64 only when the receiving contract requires text, such as a JSON field. Those approaches solve different protocol constraints; mixing them can increase memory use and can make a multipart request unparsable if its boundary parameter does not match the body.

The examples and size calculation below explain mechanisms. They were not run against a business application or a particular browser version. RFC 7578 defines the multipart/form-data structure and its boundary. A browser constructing a FormData request generates a boundary that corresponds to the body, so application code should append fields and send the request; it should not hand-build multipart syntax or set a bare multipart/form-data request header without the boundary. Regardless of transport, the server must validate authorization, size, type, and content. A client filename, MIME value, and progress percentage do not prove that the server has completed its work.

A file picker returns a FileList

A minimal picker looks like this:

<label for="attachment">Choose an attachment</label>
<input id="attachment" name="attachment" type="file" accept="image/png,image/jpeg">

accept helps the chooser present relevant options. It is not a security check. After a selection, input.files is a FileList; a selected File can be read by index. The object is not a JavaScript array and does not start a network stream. File describes a selected file and exposes read-only information such as its name and last-modified time. Blob represents immutable raw binary data. The browser standards allow XHR to send a File or Blob directly, without first turning the contents into a string.

When the control allows multiple files, define whether each file gets a separate form field or whether the same field name repeats. Server frameworks can interpret repeated field names differently, so the API contract should state ordering, maximum count, and partial-failure behavior. A single-file control still needs to handle no selection, cancellation, choosing a different file with the same name, and resetting the form after selection. Equal names do not imply equal bytes; using the name as an object identifier makes overwrites, caching, and audit trails ambiguous.

Multipart upload: let the browser create the boundary

For a normal form upload, FormData carries files and a few related fields. This XHR example shows a request with upload progress. It is structural sample code and was not connected to this site or a real backend:

function upload(file, url, onProgress) {
  const data = new FormData();
  data.append('file', file, file.name);
  data.append('purpose', 'avatar');

  return new Promise((resolve, reject) => {
    const xhr = new XMLHttpRequest();
    xhr.open('POST', url);
    xhr.upload.addEventListener('progress', (event) => {
      if (event.lengthComputable) onProgress?.(event.loaded, event.total);
    });
    xhr.addEventListener('load', () => {
      if (xhr.status >= 200 && xhr.status < 300) resolve(xhr.responseText);
      else reject(new Error(`HTTP ${xhr.status}`));
    });
    xhr.addEventListener('error', () => reject(new Error('network error')));
    xhr.addEventListener('abort', () => reject(new Error('aborted')));
    xhr.send(data);
  });
}

There is deliberately no setRequestHeader('Content-Type', 'multipart/form-data'). The boundary parameter in the request header must match the delimiters in the body. If application code supplies a header without a boundary, the browser may still serialize the body with a generated boundary while the server parser does not know which value to expect. A mismatch can produce a “missing boundary” error, empty fields, or a body the parser cannot split. To diagnose it, inspect both the request header and the raw payload in the network panel. A valid request has a multipart/form-data; boundary=... header and uses the same boundary between its parts. If they differ, remove the manual header before inferring that the file itself is corrupt.

A filename can be passed as the third argument to FormData.append, but it remains client-supplied metadata. RFC 7578 defines a Content-Disposition for each part and permits a filename parameter; a receiver must not treat it as a trusted filesystem path. On receipt, generate a server-owned storage key, safely handle any displayed name, and apply authorization and content checks. accept, the extension, and the MIME value reported by the browser can improve usability or serve as inexpensive filters; none proves that the bytes are safe. For object states, version binding, and download authorization, see this site’s file-upload quarantine and validation boundaries.

When Base64 is appropriate

Base64 encodes arbitrary bytes as text. It is useful when an existing contract accepts only text, such as a JSON field, or when a small value must be embedded or stored as text. It does not compress a file. RFC 4648 groups 24 input bits into four output characters, so the encoded payload is about four-thirds the original byte count, plus padding and any JSON quoting or envelope. For an assumed 8 MiB file, the Base64 body is about 10.67 MiB. That is a calculation from the encoding ratio, not a measured request. A request path may simultaneously retain the original File, an encoded string, a JSON string, and a decoded server-side copy; peak memory depends on browser and runtime implementations.

When the contract calls for a data URL, FileReader.readAsDataURL(file) can read it. The result is not a bare Base64 string: it includes a prefix such as data:image/png;base64,. The receiving contract determines whether that prefix must be removed; do not assume every endpoint accepts a data URL. Handle read errors and allow cancellation when a component is destroyed. Repeated full-string copies of a large file can create high memory peaks on mobile devices. Even if the network transfer would succeed, the Base64 path may require reading the whole file before the upload begins.

Do not use btoa(atob(value)) === value as a general Base64 validator. atob decodes Base64 to a byte string; it is not UTF-8 text decoding. Unicode text needs an explicit character-encoding conversion. More fundamentally, syntactically decodable Base64 only says something about alphabet and padding. It does not establish the file’s business type, completeness, or safety. On the server, cap the input size, decode strictly, and validate the resulting bytes. If the goal is simply to upload a file, sending the File directly avoids an unnecessary complete string copy.

Converting Base64 back to a Blob

If an existing API returns bare Base64 or a data URL, determine the MIME value’s trust source from the contract and decode the Base64 portion into bytes. The atob result is a binary string whose character codes represent byte values; it is not arbitrary Unicode text. This illustrative conversion was not executed in a project:

function dataUrlToBlob(dataUrl) {
  const comma = dataUrl.indexOf(',');
  if (comma < 0) throw new Error('data URL is missing a comma');
  const header = dataUrl.slice(0, comma);
  if (!/^data:.*;base64$/i.test(header)) throw new Error('expected base64 data URL');
  const mime = header.slice(5).replace(/;base64$/i, '') || 'application/octet-stream';
  const binary = atob(dataUrl.slice(comma + 1));
  const bytes = new Uint8Array(binary.length);
  for (let i = 0; i < binary.length; i++) bytes[i] = binary.charCodeAt(i);
  return new Blob([bytes], { type: mime });
}

Its purpose is to illustrate byte conversion, not strict Base64 validation or file security. If the input is a JSON field rather than a data URL, parse the exact contract instead of guessing a prefix. If the target runtime lacks atob, use a decoder that has been verified for that runtime. A Blob’s type is a label; it does not inspect the bytes or change them. If a named File object is necessary, new File([blob], name, { type }) can express it, although passing the filename as FormData.append’s third argument is often simpler for an upload.

One hundred percent transferred does not mean saved

XHR exposes an upload object that can emit progress events. When lengthComputable is true, loaded / total can support a percentage display. Transfer progress describes the browser’s perspective; it says nothing about whether malware scanning, format parsing, object-storage writes, or a database transaction have finished. After the display reaches 100%, the page still needs to wait for XHR load, check the HTTP status, and interpret the API response. HTTP 413 means a request body exceeded a limit at some layer; 415 means a media type was not accepted. Either can occur after the progress display completes. Timeout, error, abort, a non-2xx response, and a business response such as “pending review” should be distinct outcomes, not one generic upload-success flag.

If the product must show upload progress, XHR is a direct option. If it only needs to submit and read the result, the Fetch interface may be simpler, but do not assume from shorter code that it supplies the same upload-progress events. Verify the capabilities of the target browser and runtime. Whatever transport is used, define cancellation, retries, and duplicate-submission behavior. If the server accepted an object but the response was lost, a blind retry can create a duplicate. A request ID, idempotency key, or business-object constraint is more reliable than merely disabling the button in the browser.

Choose the transport by following the failure path

Start with the API contract. If the backend accepts multipart, use File → FormData → request and avoid Base64. If it accepts only JSON text for a legacy integration, record the encoding, reading, and memory cost, then consider whether the contract should change. For example, under the assumed 8 MiB file above, the Base64 body is about 10.67 MiB. If an upstream proxy limit was designed around the original file size, the encoded request may be rejected before business code runs. In that case, base64ToBlob is not the problem; the protocol and upstream body limit disagree. Conversely, if a client already holds JSON Base64 and an adapter must produce multipart, converting it to a Uint8Array/Blob before appending can preserve byte semantics, but size limits and avoidable copies still matter.

A practical upload investigation can follow four observation points. At selection, record file count, expected size, and cancellation. At serialization, inspect the boundary and part structure. At transfer, distinguish browser progress, network interruption, and HTTP response. At persistence, inspect the server object ID, validation state, and whether the object is retrievable. If the multipart header lacks a boundary, fix request construction first. If the request is complete but receives 413, compare proxy, framework, application, and storage limits. If progress reaches 100% and the business API rejects the object, the interface should say “transferred; server validation failed,” not pretend no file was selected. These steps are a diagnostic design, not a claim that this article tested a backend or real upload.

Transport choice and security policy are separate layers. Browser-reported filename, MIME, and size are untrusted claims. The server should impose byte limits, validate actual content, constrain parser resource use, and when appropriate place the object in quarantine before deciding whether it can be made public or downloaded. XHR progress describes only the network phase; a successful object-storage write does not prove downstream checks have finished. This site’s file-upload quarantine and validation boundaries discusses pending objects, processing results, and download authorization.

References and verification limits

  • W3C File API Editor’s Draft: FileList, Blob, File, FileReader, and their relationship to XHR. The current page labels itself an Editor’s Draft; it is work in progress, not a final Recommendation.
  • WHATWG XMLHttpRequest Living Standard: sending FormData, upload events, ProgressEvent, status codes, and error events.
  • RFC 7578: the 2015 multipart/form-data standard, including boundary and per-part disposition.
  • RFC 4648: the 2006 Base-N encoding standard, including Base64 groups, padding, and canonical encodings.

The cited specifications establish the format and API facts. Choosing direct upload or Base64, setting limits, and designing status behavior are engineering judgments based on the interface contract and runtime. The examples were not executed in a browser, backend, or device. Before implementation, inspect the real multipart request in the target browser and verify server-side limits and persistence behavior.
