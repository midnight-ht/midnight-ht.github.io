Before Cleaning Up Commits with Git Rebase, Set the Shared-History Boundary

Use git rebase -i to reorder, combine, or edit commits that are not yet shared; verify the range, conflicts, patch series, and remote-collaboration boundary.

Updated 2026-11-27 · Estimated read 17 min
Translations
zh-CN en

Article

Key takeaways

  • Rebase rebuilds commits and changes their IDs; first establish whether anyone else has consumed the branch.
  • Squash, fixup, and drop change the sequence, so review the todo range and order.
  • Validate conflicts with tests and patch comparison; a force push is not a default final step.

Interactive rebase is useful for organizing a sequence of commits that has not yet been shared: it lets you reorder commits, fold a correction into its parent, edit messages, split a change, or remove an accidental patch. It rebuilds commits and changes their IDs. Once other people have based work on those commits, rewriting is no longer a private cleanup. A safer workflow identifies the base and sharing boundary first, reviews the todo list, inspects each replayed result, and compares the old and new patch series. For a mistake already present in shared history, an additional corrective commit such as git revert is usually safer than treating a force push as the standard final step.

Decide which part of history needs editing

Imagine a feature branch forked from origin/main and then accumulated three commits: “add export entry point,” “fix filename,” and “add tests.” Before delivery, inspect the graph and ensure the worktree is clean:

git status --short
git fetch origin
git log --oneline --decorate --graph --boundary origin/main...HEAD

These commands inspect repository state; this article did not run the rewrite examples in the current repository. If the branch has already been shared, fetching is not enough to determine the correct range. Find out whether teammates fetched it and whether anyone has pushed further commits on top. Choosing the wrong upstream causes rebase to replay more commits than intended. Treating HEAD~3 as a permanent boundary can also select the wrong range after new commits arrive.

After confirming the branch sequence and its base, an explicit upstream is easier to review than a remembered count:

git rebase -i origin/main

To edit commits after a particular commit, you can name its parent, for example git rebase -i ^. The important question is not which spelling is more sophisticated; the first entry in the todo list must be the first commit you intend to include. Before starting, inspect git merge-base origin/main HEAD and the graph. If the topic branch has not incorporated the current base, decide whether to merge first or replay the topic onto the newer base. Interactive rebase can reorder, combine, and remove commits, so an incorrect range can discard useful work.

Treat the todo list as an operation plan

The interactive list normally begins with pick. Common actions include reword (keep the patch and edit its message), edit (stop to change the commit), squash (combine with the previous commit and edit the combined message), fixup (combine with the previous commit and discard this commit’s message), and drop (do not replay the patch). Abbreviations are valid, but full words make a shared operation record easier to read.

Here is a hypothetical list: the first commit introduces a coherent feature, the second corrects the same behavior, the third adds a distinct test, and the fourth clarifies documentation:

pick   a1b2c3d Add CSV export
fixup  e4f5a6b Fix filename on Windows
pick   1122334 Cover export naming with tests
reword 5566778 Update export documentation

Use fixup only when the patch truly belongs with the preceding commit and the correction’s separate message is not needed. If the second commit fixes an independent defect, keep it as a separate pick; folding it away would erase a useful review or rollback boundary. Squash lets you edit the combined message. Do not change every line to squash: the first line has no preceding commit to combine with. Do not remove the commit IDs at the ends of todo lines; Git executes actions against those object IDs, while the descriptions are for people.

The original demonstration used HEAD~2, changed the second action to s, and then edited the combined message in another editor. That illustrates the mechanics, but its final instruction, git push origin master -f, should not be copied as a general rule. A personal branch that has not been pushed can usually be pushed normally after the rewrite. Rewriting a public branch forces downstream collaborators to repair their commit relationships. In shared history, prefer an additional corrective commit. If a private remote branch truly must be replaced, coordinate a pause in pushes, record the expected remote SHA, and evaluate an explicit lease check. Do not use --force by habit.

Separate continuing from skipping when conflicts occur

Rebase replays commits one by one. If a new base has different changes to the same lines, Git stops at a commit it cannot apply automatically and leaves conflict markers. Check git status to see which step is active, then inspect each conflicted file. Determine whether the changes describe the same requirement, different requirements, or a patch that the upstream has already implemented. After resolving the conflict, stage the files, run suitable checks, and continue:

git add path/to/file
git rebase --continue

The meaning of --continue is “the current commit is resolved; replay the remaining sequence,” not “ignore the conflict.” git rebase --skip discards the current commit from the replay and can lose its only copy of a business change. Use it only after confirming that the new base implements an equivalent patch or the team has decided the change is no longer needed. If the range, base, or resolution direction was wrong, git rebase --abort returns the branch to its state before the operation began. Git’s manual describes these as separate choices: resolve and continue, return to the original state, or skip the problematic commit. When many conflicts occur, checking the cause commit by commit is more useful than merely seeking a green exit status.

Verify that the intended patches remain

A successful command does not prove the resulting series is correct. Inspect the new graph, worktree, diff, and relevant tests:

git status --short
git log --oneline --decorate --graph origin/main..HEAD
git diff origin/main...HEAD

To compare the old and rewritten patch series, use git range-diff . It pairs commits by patch similarity and helps expose a missing commit, changed patch, or reordered sequence. It does not prove semantic equivalence and cannot replace code review or tests. For each edit, conflict resolution, and reordered logical step, check that the commit still tells a coherent story and that the project can build or pass the relevant tests at that point. If collaborators check out intermediate commits individually, interactive exec commands can run project checks during replay. The commands must make sense for each intermediate state; a test of only the final state does not validate every historical step.

The final push depends on whether the commits are shared, not on whether a rebase command was used. Ordinary git push requires a fast-forward update. If a rewrite makes the update non-fast-forward, stop and establish who may have built on the old commits. Git’s --force-with-lease=: can require that a remote ref still equals the explicitly recorded commit, but it still replaces history and still requires coordination. The default --force-with-lease relies on remote-tracking refs, so background fetches may make the expected value less obvious than an explicit SHA. “Rebase always requires force push” is therefore a bad rule: unpublished personal branches, shared feature branches, and protected main branches have different policies.

Conditions and limits

History rewriting improves patch organization and reviewability. It does not automatically improve code, restore missing product context, or fix inadequate tests. Rebase normally linearizes history. If the original branch contains merge topology that must be retained, study --rebase-merges; recreated merge commits may require you to reapply conflict resolutions manually. Signed commits, audit requirements, published tags, and deployed build references can also depend on commit IDs and need separate assessment.

A verifiable completion condition is: the selected range and base are recorded; the todo list combines only related fixes; the final graph and patch comparison are understandable; the worktree is clean; relevant tests pass; and the push method matches the branch’s sharing policy. If the goal is to undo a change that is already shared, see Using git revert to restore shared history instead of copying the old article’s force-push command. Primary references: git-rebase manual, git-push manual, and git-range-diff manual.
