Handwriting a Promise: Semantics You Cannot Skip from `resolve` to Chaining

See why `resolve(1)` and `resolve(otherPromise)` differ, then trace reaction jobs, derived promises, and failure paths to define a teaching implementation’s limits.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-27 · Estimated read 23 min
Translations
zh-CN en

Article

Key takeaways

  • Separate a locked-in resolution from final settlement.
  • `then` registers a reaction and returns a new Promise.
  • Use thenables, exceptions, and ordering to test implementation boundaries.

A minimal Promise that prints 1 after resolve(1) does not prove that it handles resolve(otherPromise) correctly. The first call stores an ordinary value. In contrast, the other call asks the current Promise to adopt another object’s eventual outcome. The hard part of implementing a Promise is not flipping a field to fulfilled; it is deciding who now controls the outcome, when reactions run, and how the next link in the chain receives a return value or an exception.

This article uses the Promise semantics in ECMAScript 2026 to explain those boundaries. The snippets are explanatory fragments, not a complete specification implementation, and they are not presented as independently executed code. A deliberately limited teaching subset is useful for learning. Replacing the native Promise requires much more, including constructor-generic behavior, subclassing, Symbol.species, rejection tracking, and other specification details. A simplified sketch should not be called a complete implementation.

Separate state from a locked-in resolution

A Promise has three states: pending, fulfilled, and rejected. Fulfilled and rejected are settled; pending means the outcome has not settled. One distinction is easy to miss: resolved does not mean settled. A Promise can be resolved but still pending because it has been locked in to follow another Promise or thenable that has not completed. “Locked in” says who controls the eventual outcome; “fulfilled” or “rejected” says that the outcome has already settled. The ECMAScript 2026 Promise Objects clause explicitly distinguishes the terms. Specification text

Suppose an executor first calls resolve(inner), where inner is still pending, then calls reject(error). It may seem that the second call should reject outer because no success has been printed yet. But the deciding fact is not merely the current state field: the first resolve has already handed outer’s resolution fate to inner. A later reject call from the executor cannot take control back. outer becomes fulfilled when inner fulfills and rejected when inner rejects. Therefore, setting status = FULFILLED immediately on the first resolve merges “accept a resolution request” with “settle the outcome,” which is incorrect.

An implementation can use a separate alreadyResolved guard at the resolve/reject entry points and use the Promise state to represent the final outcome. That is a useful teaching design, not a verbatim copy of the specification’s internal fields. When resolution receives an object, it must also inspect that object’s then property. If then is callable, the Promise adopts the thenable’s outcome. If reading then throws, resolution becomes rejection. An object without a callable then is fulfilled as an ordinary value.

A thenable does not need to be a native Promise. Any object with a callable then property can participate in resolution. Its then getter may have side effects or throw; its then method may call resolve or reject more than once. The resolution process must prevent these paths from settling the same Promise multiple times. Under §27.2.1.3, resolving functions share a one-shot guard and reject self-resolution, which would otherwise create an unfinishable reference.

A then callback is not a method on the source Promise

then(onFulfilled, onRejected) does at least two things: it registers a pair of reactions on the source Promise and creates a new Promise to return. If the source is pending, the reactions are stored. If it is already settled, the reaction is still enqueued as a Promise job rather than called synchronously. The abstract PerformPromiseThen operation receives a promise capability that carries the result; this is the basis of chaining. Promise.prototype.then and PerformPromiseThen

Consider this explanatory snippet:

const next = source.then(value => {
  return value + 1;
});

next is not source. A handler that returns 3 resolves the downstream Promise with 3; returning another Promise or thenable makes the downstream adopt that outcome. Throwing from the handler rejects the downstream Promise. No explicit return means undefined, so the downstream fulfills with undefined. This is why an implementation that merely stores callbacks in an array and invokes them on settlement demonstrates callback order, but does not implement Promise chaining.

These settlement distinctions also matter when composing APIs. The site’s Promise.any analysis shows that “first fulfilled” is not “first to finish” and does not mean “business-valid result.” Understanding how resolution adopts a thenable helps clarify what kind of candidate result any receives.

Rejection handlers use the same result pipeline. When onRejected returns normally, the downstream Promise usually becomes fulfilled with that value. Returning a Promise makes the downstream adopt its result. A new throw leaves the downstream rejected with that exception. When one handler is missing, the corresponding value or rejection reason must pass through; the chain should not lose it simply because no function was supplied. Keep the source Promise’s state separate from the downstream Promise’s resolution so a handler’s return value cannot overwrite the source.

Two small counterexamples expose structural mistakes

The first counterexample registers two handlers on one pending Promise:

pending.then(first);
pending.then(second);

If the object has only one successCallback field, the second assignment overwrites the first; only second runs on fulfillment. An array or reaction list preserves both subscriptions, but that is not the whole design: each reaction must also be associated with its own downstream promise capability. If one handler throws, it should reject only its own downstream Promise. It should not change the source Promise or prevent other reactions from being enqueued.

An already fulfilled Promise exposes a different defect:

let finished = false;
Promise.resolve(1).then(() => console.log(finished));
finished = true;

Promise reactions run asynchronously through jobs, so the handler observes true. A teaching implementation that invokes the handler immediately when it sees the fulfilled state would print false. The original synchronous example is useful for showing that an executor runs during construction, but it is not evidence about then scheduling. One qualification matters: Promise jobs are a specification abstraction; how browsers and Node.js integrate them with other queues belongs to the host environment.

Split a teaching implementation into responsibilities

A readable implementation sketch can have four modules instead of making resolve do everything. First, state storage handles pending/fulfilled/rejected and the final result; a settled state is irreversible. Second, resolvePromise accepts a resolution value: fulfill with ordinary values; reject self-resolution; for objects, read then once, handle a read exception, and arrange adoption when then is callable. Third, then creates a downstream Promise and packages the fulfillment and rejection handlers, the target Promise, and one-shot resolve/reject functions into reactions. Fourth, when a reaction job runs, it catches handler exceptions and passes the returned value to the downstream resolvePromise; if a handler is absent, it forwards the value or reason as required.

A code sketch may have three deceptively similar entry points: fulfill(value), reject(reason), and resolve(value). They are not interchangeable. fulfill changes the state directly; reject records a rejection; resolve decides whether the input is an ordinary value, Promise, thenable, or self-reference, and how the outcome will eventually settle. Renaming a function resolve while making it immediately execute status = FULFILLED is a dangerous shortcut in many simplified tutorials.

Thenable adoption also raises a reentrancy concern. Calling a third-party object’s then synchronously may invoke callbacks before the outer resolution process has recorded its guard state, creating surprising interleavings. The NewPromiseResolveThenableJob operation places thenable adoption in a Promise job. That scheduling is not only about making behavior “look asynchronous”; it also avoids synchronous re-entry while calling the thenable’s then. Reading the then property and calling it are separate steps: the specification first obtains the property, then a later job invokes it with one-shot resolving functions. CreateResolvingFunctions and NewPromiseResolveThenableJob

If the learning goal is state transitions, start with ordinary fulfillment, rejection, asynchronous reactions, and multiple subscriptions. Next add the downstream Promise’s return-value and exception handling. Then add thenable adoption, self-resolution protection, and duplicate-call protection. Keep an explicit list of unsupported behavior at each stage. A fragment that only works for native Promises and fixed callbacks should not appear standards-compliant just because it is named MyPromise.

Use a test matrix, not only a success example

At minimum, cover these inputs: resolve with an ordinary value; reject and then attach catch; resolve with a pending Promise; resolve with an already fulfilled Promise; a thenable fulfills; a thenable rejects; reading a then getter throws; a thenable calls both callbacks; a Promise resolves with itself; multiple then subscriptions; a handler returns an ordinary value; a handler returns a Promise; a handler throws; and the ordering of a then attached after settlement. For each case, write the expected result and expected order instead of merely checking that the console says “success.”

Include failure assertions. When a second then would overwrite the first, assert that both handlers receive one result. When a callback might run synchronously, compare a marker set later in the same call stack. When a thenable resolves and then rejects, verify that the downstream Promise follows only the first valid resolution path. When a handler throws, verify that the source remains fulfilled while its derived Promise rejects. This separates “state did not break,” “the chain propagated,” and “the callback order was correct” into different checks.

None of the code fragments here were executed, so this matrix is a proposed verification design, not a test report. The ECMAScript specification describes the algorithms for native Promise objects; it does not prove that a handwritten implementation conforms to every detail. A compatibility implementation needs separate work against the full specification and test suite. For a teaching implementation, documenting its supported subset beside the code makes it clearer what the reader has actually learned.

The useful lesson in implementing a Promise is not that a few lines can recreate the native object. It is that resolution, fulfillment, reaction scheduling, and downstream propagation are separate responsibilities. When those responsibilities remain mixed inside one state branch, an ordinary success example gives an overly optimistic impression. Define the teaching subset first, then use failure paths to test each boundary.
