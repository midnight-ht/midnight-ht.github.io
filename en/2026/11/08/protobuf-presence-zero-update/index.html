Why did setting quota to zero have no effect? Check Protobuf presence

Compare explicit presence, implicit merging and older reserialization across unchanged, zero and nonzero quota updates.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-08 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • Distinguish zero from an omitted update.
  • Older reserialization can discard default-value presence.
  • Verify merging along the actual forwarding route.

A quota starts at nine and an update reads as zero, yet merging may leave nine. With implicit presence for a Protobuf scalar, zero can mean either an explicit request to reset the quota or a field that was never set. A reliable update needs field presence, or a separate update mask that the actual handler honors.

This concerns message merging and reserialization. Application code can assign zero directly. However, a handler that always overwrites the stored value from the getter can turn an omitted quota into an unintended reset. The protocol needs to express three distinct requests: leave nine unchanged, set zero, and set four. Check those requirements before choosing a merge implementation.

Why can zero be absent from a merge?

The official field-presence note distinguishes implicit and explicit presence. Ordinary proto3 basic scalars use implicit presence: default values are not serialized or merged from the source. An optional basic scalar tracks whether it was set, including a default value explicitly set by its caller. These rules concern proto3; message fields, oneofs and Editions require their own presence rules.

A getter answers what value can be read. An update handler also needs to know whether the caller specified that value. If the message discarded that distinction, reading zero cannot recover the original intent. Renaming zero as “clear” in a comment does not add information to the encoding. The protocol needs a distinguishable operation or presence information.

This complete teaching probe has not been compiled or executed. In an isolated directory, provide a compatible protoc and Python protobuf runtime, generate quota_pb2.py, and then run the script. No installation or RPC execution is claimed. Different message names with the same field number let the example model an older definition that parses and reserializes the bytes.

// quota.proto
syntax = "proto3";
message ImplicitQuota { int32 quota = 1; }
message ExplicitQuota { optional int32 quota = 1; }

protoc --python_out=. quota.proto
python probe.py

# probe.py — unexecuted; requires generated quota_pb2.py
from quota_pb2 import ExplicitQuota, ImplicitQuota

# Each literal oracle contains final value and presence where supported.
cases = [
    (ExplicitQuota, ExplicitQuota(quota=0), (0, True)),
    (ExplicitQuota, ExplicitQuota(), (9, True)),
    (ImplicitQuota, ImplicitQuota(quota=0), (9, None)),
    (ImplicitQuota, ImplicitQuota(quota=4), (4, None)),
]
for message_type, update, expected in cases:
    target = message_type(quota=9)
    target.MergeFrom(update)
    presence = target.HasField("quota") if message_type is ExplicitQuota else None
    assert (target.quota, presence) == expected

for sent_value, expected in [(0, (0, False)), (4, (4, True))]:
    sender = ExplicitQuota(quota=sent_value)
    old_forwarder = ImplicitQuota()
    old_forwarder.ParseFromString(sender.SerializeToString())
    receiver = ExplicitQuota()
    receiver.ParseFromString(old_forwarder.SerializeToString())
    assert (receiver.quota, receiver.HasField("quota")) == expected

Write the oracle independently of the script: merging an explicitly present zero produces zero; merging an implicit zero leaves nine; merging an absent explicit field also leaves nine. Four should retain presence through the intermediary. Zero should still read as zero after the intermediary, but its presence should be false. Checking only the numeric result would miss the last failure.

Add a nonzero control: merging an implicit value of four should produce four, not nine. This distinguishes a merge that never ran from a default value omitted from the source. Every table oracle gives the value and presence where supported; None means the implicit API has no such query, not that the field was observed absent. If nonzero updates also fail, inspect the schema, call path and business overwrite logic rather than attributing every failure to default omission.

How can readable bytes lose update intent?

The official note describes round trips between explicit and implicit definitions. A change can be compatible at the binary level while a present default value disappears after reserialization under implicit presence. The intermediary need not fail parsing to change what a downstream update means.

A new-client/new-server test therefore covers only one route. Inspect gateways, consumers and batch jobs that decode and rebuild messages. A proxy that forwards the original bytes is different from a program that reconstructs them using generated code. Identify which nodes own a schema definition before claiming that an older client makes every route unsafe.

The November 5 article on retiring field numbers addresses a different compatibility problem: reassigning an old identity to a new meaning. Here the quota keeps its number and meaning. The missing information is that it was explicitly set. A reserved declaration cannot restore that information, and changing the field number is not the required remedy.

Should the handler use presence or an update mask?

When the protocol can control its effective readers and writers, explicit presence lets the handler distinguish an absent scalar from a present zero. The handler must actually use that distinction. For an existing implicit protocol, the official merging discussion describes external mechanisms such as FieldMask: the caller explicitly identifies the fields to change, and the handler applies their values even when those values are defaults.

For example, a zero getter plus quota in the mask can request a reset. The same getter without quota in the mask can leave the stored value unchanged. Validate the allowed mask paths; a client-controlled mask must not become permission to update administrative fields. This is a design recommendation, not an implemented mask service. An older intermediary’s treatment of the mask still needs a route-specific test.

Optional does not mean that the business may never require the field. It records presence; the API decides when presence is mandatory. Repeated fields and maps do not provide the same absent-versus-empty distinction. Clearing a collection needs a separate update contract rather than a copied scalar HasField check.

Can zero updates work before an older forwarder is upgraded?

An explicit update mask can carry the intent if the actual update handler honors it. Adding a mask field alone does not change an older handler. Verify that each rebuilding intermediary preserves the mask, then check present, missing, unknown and forbidden paths. Otherwise the design merely moves the information loss to a different field.

An acceptance record should retain schemas, compiler and runtime versions, all three inputs and the bytes at each effective node. Start the target at nine for each test and check both its final value and field presence, directly and through the older definition. Until those probes run, the outputs remain documented expectations. The handler’s first decision should be whether the field is to change; only then should it read the replacement value.
