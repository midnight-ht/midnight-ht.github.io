Validate logical migration through rows, schema, and the next write

PostgreSQL 18 logical replication does not cover DDL, sequence state or large objects. A complete read-only inventory and independent numeric cases separate read-subscriber evidence from write-cutover readiness.

Article

Key takeaways

  • Replicated identity values do not synchronize their sequence allocator.
  • DDL and large objects need checks outside logical row replication.
  • Read-only inventory and matching row counts do not certify writable cutover.

Caught-up table rows do not establish that a PostgreSQL logical subscriber can take over writes. Validate schema, identifier allocation and objects outside replication separately; a zero-lag signal does not cover all three.

Suppose both databases contain order IDs 1 and 100 with matching row counts, but the first new order on the destination conflicts. One possible explanation is that identity column values replicated while the destination's sequence state did not. This article uses PostgreSQL 18 documentation. No publication or subscription was created, traffic switched or sequence modified.

Replicated values do not carry their allocator's state

The PostgreSQL 18 logical-replication restrictions explicitly distinguish serial or identity values stored in rows from the sequence itself. Row values replicate; sequence state does not. This is typically unimportant for a read-only subscriber, but a writable switchover needs appropriate sequence updates. A row containing 100 cannot certify that the next local allocation will exceed 100.

Do not turn that into a universal max(id)+1 reset recipe. Sequences can have different increments, caching, cycling, previously allocated values and other consumers. If the old database still accepts writes, a computed boundary can immediately become stale. The positive-integer example demonstrates insufficient evidence; it is not an online reset script for every sequence.

The version-18 pg_sequences reference also explains that last_value is the last sequence value written to disk and can exceed the last value handed out when caching is used. NULL can mean the sequence has not been read, that the observer lacks the necessary privilege, or an unlogged sequence on a standby under the documented condition. Neither NULL nor last_value alone is a universal next-allocation oracle.

Schema changes have a separate handoff

The restriction document says DDL and schema changes do not replicate. If new publisher data does not fit the subscriber's schema, application of replication errors until that schema is updated. Applying additive changes to the subscriber first can often avoid the gap. That is not a universal instruction to reverse the order of every DDL operation.

For example, a publisher changes from id alone to id plus note while the subscriber still has only id. Previously caught-up rows cannot certify that subsequent changes with the new structure will apply. Record both schema versions, rollout order and recovery after an apply error rather than comparing a single row count. The staged-constraint article concerns scanning and validation within a database; it does not establish synchronized structures across two databases.

Large objects require another inventory. PostgreSQL explicitly excludes them from logical replication. A regular table column containing an object identifier can arrive without proving that the object's contents migrated. Large object here means the specific PostgreSQL object facility, not every large text or bytea value. “Large fields do not replicate” would be a different and incorrect claim.

What a read-only inventory can establish

This complete SQL has not been executed. Its read-only transaction performs no nextval, setval or schema change. editorial_example is a deliberately chosen teaching-schema placeholder, not a discovered application schema. Check permissions, database identity and connection before interpreting any results.

-- Unexecuted PostgreSQL18 read-only inventory. No sequence allocation/reset.
-- Restrict to a schema explicitly selected for the exercise; change name deliberately.
BEGIN READ ONLY;
SELECT current_database(), current_setting('server_version');
SELECT schemaname, sequencename, sequenceowner, start_value, increment_by,
       min_value, max_value, cycle, cache_size, last_value
FROM pg_catalog.pg_sequences
WHERE schemaname = 'editorial_example'
ORDER BY sequencename;
SELECT c.relname, a.attname, a.attnum, a.attidentity,
       pg_catalog.format_type(a.atttypid, a.atttypmod) AS column_type
FROM pg_catalog.pg_attribute a
JOIN pg_catalog.pg_class c ON c.oid = a.attrelid
JOIN pg_catalog.pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'editorial_example'
  AND c.relkind IN ('r','p') AND a.attnum > 0 AND NOT a.attisdropped
ORDER BY c.relname, a.attnum;
SELECT count(*) AS large_objects_seen FROM pg_catalog.pg_largeobject_metadata;
-- An illustrative VALUES case; this does not assert a live sequence next value.
WITH cases(label, rows_equal, allocated_next_candidate, max_id) AS (
 VALUES ('caught_up_but_unsafe', true, 1::bigint, 100::bigint),
        ('candidate_only', true, 101::bigint, 100::bigint)
)
SELECT label, rows_equal,
       allocated_next_candidate > max_id AS clears_this_numeric_example
FROM cases ORDER BY label;
-- Expected: candidate_only true/true; caught_up_but_unsafe true/false.
-- Even candidate_only is NOT a full cutover certificate: increments, writer fencing,
-- cached allocations, cycles, permissions and application behavior remain unverified.
COMMIT;

The first part lists sequence properties, column definitions and large-object metadata count. The official version-18 pg_attribute source says ordinary columns have positive attnum values and dropped columns can retain catalog entries, so the query excludes system and dropped columns. Type and identity information help compare structures, but these queries do not cover every grant, extension, function or dependency. They cannot certify a whole-database migration.

The pg_largeobject_metadata definition in that official catalog source distinguishes metadata from actual content. Matching metadata counts do not prove matching bytes or references. Interpret last_value with its permission and caching qualifications too. An inventory identifies further checks; a count is not a completeness certificate.

The VALUES section supplies two independent hypothetical cases. caught_up_but_unsafe has equal rows but candidate 1 does not exceed maximum ID 100, so its numeric check is false. candidate_only supplies 101 and passes that comparison without satisfying every cutover condition. The expected results are specified in comments. They are neither observed replication output nor predictions of a real sequence.

Write authority needs its own completion point

A write cutover needs a plan to fence old writers before final replication, allocator handling and application routing are accepted. Include background tasks and other sequence consumers; disabling a frontend button is insufficient. Execution, interruption duration and reversal depend on the target system, not on these read-only queries.

Choose representative application paths from the inventory of identity columns, independent sequences, structural changes and large-object dependencies. Retain instance, database, application version and authorized write scope. Verify that the application writes to the new authority and reads back related content while old paths no longer create conflicting facts. If both databases receive writes, returning to the old connection address requires an additional data-handling plan.

The UNLOGGED standby-content article concerns logging and standby contents, whereas this question concerns ordinary tables' logical-replication contract. The sequence-gap article describes values not reclaimed after rollback; that differs from sequence state being outside logical replication altogether.

Must sequence state be synchronized for a permanently read-only subscriber?

It is typically irrelevant when no local path allocates sequence values, a qualification retained by the official restrictions. A future write cutover or background writer changes the condition and requires explicit planning. Past read-only use does not certify future writable readiness.

A proposed exercise uses two isolated version-18 instances, replicates identity rows and inspects row values separately from actual sequence state. Test additive-schema order in a controlled case. After explicitly fencing old writes, follow an approved allocator plan and verify an authorized application write with its related content. Neither the SQL nor these exercises was run here. No zero-downtime, complete-copy or successful-cutover claim follows. Approval needs evidence for each dependency, not a replication-lag number that once displayed zero.
