An expired start-limit window does not schedule a systemd retry

Explain restart policy, start-rate limits and new triggers with a bounded three-start unit, separating counter reset, process launch and business readiness.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-08 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • Restart=always remains subject to unit start limits, including manual-start limits.
  • Window expiration alone does not issue a new automatic start request.
  • Counter reset, successful launch and business readiness each need evidence.

When a service stops after hitting a start limit, elapsed time alone does not issue a new start request. A later manual, timer or socket trigger may start it, after the persistent failure is addressed. Restart=always does not remove either the start budget or the need for a new trigger.

Always still passes through rate limiting

The systemd.service Restart documentation explicitly subjects restarts to unit start-rate limits. The rolling latest pages checked on 8 November 2026 identify systemd 262. That does not establish the reader’s installed version or available options. Retain the manager version, effective unit and drop-ins rather than relying on one repository file.

Restart policy determines whether an exit calls for another attempt. Unit rate limiting determines whether that start is permitted. Both can work correctly while the process stays down: it failed, Restart requests another attempt, but the current window’s budget is exhausted. The absence of a replacement process does not establish that configuration was ignored, and always is not an unlimited loop.

The systemd.unit StartLimit documentation also applies limits to manual starts, not only attempts driven by Restart. Repeated operator requests can encounter the same gate. Manager configuration supplies defaults, while units can set explicit values. Verify effective values rather than treating a published default as a fact about this host.

Window expiration changes permission, not scheduling

The manual says units configured for Restart stop automatic attempts after reaching the limit. A later manual, timer or socket activation can start them after the interval passes. That permission does not mean a start job has already been scheduled for window expiration. Without another trigger, waiting alone produces no new attempt.

This affects incident ownership. A dependency can cause repeated process failures until the application reaches its limit. The dependency later recovers while the application remains stopped. Watching only the dependency’s healthy state misses the application’s condition. Preserve the unit signal and an owner for recovery: establish the cause, choose an activation and validate the business path rather than treating “wait longer” as an action plan.

Conversely, a successful manual start does not prove limiting was disabled. The window might have elapsed, state or counters might have been reset, or unit garbage collection might have affected retained counts. Tie the explanation to this unit’s references and history instead of generalizing from one result.

A bounded three-start fixture

This unit was neither installed nor started. It prints one local Python marker and exits with status one, without contacting services or changing business data. It requires isolated Linux and an existing /usr/bin/python3. No unit or service state was changed in the current environment.

[Unit]
Description=Bounded restart teaching fixture
StartLimitIntervalSec=60s
StartLimitBurst=3

[Service]
Type=simple
ExecStart=/usr/bin/python3 -c "print('ATTEMPT', flush=True); raise SystemExit(1)"
Restart=always
RestartSec=1s

The prediction explicitly requires all three failures to occur inside sixty seconds. If scheduling or other delays invalidate that premise, do not retain the same count expectation. There must also be no extra manual, timer or socket requests, exit-status overrides or unload-and-reload history changes. There is no Install section; boot enablement is outside the fixture.

The independent expectation is three actual ExecStart markers under these bounded inputs, followed by a refused new start and stopped automatic attempts. Correlate invocation identities, exit results, unit state and raw journal entries rather than counting identical terminal lines alone. Logging policy can suppress markers; missing entries require checking evidence completeness before concluding an execution never happened.

After hitting the limit, observe through the interval’s end without introducing another start request. Check that elapsed time alone does not create a fourth launch, rather than requiring a particular field to retain one string indefinitely. Save actual Result, ActiveState and restart-related counts. No run is claimed, and no NRestarts value is prefilled: scheduled retries and actual entry into the main command are different events.

Use a separate recovery phase. Replace the deliberate exit with an explainable normal long-running teaching process, then wait for the budget or reset counters according to the plan and explicitly request a start. Retain the request and actual process evidence, followed by the relevant business probe. Keep this phase distinct from the original failing group instead of retaining only the final success.

Counter reset cannot repair persistent exits

If the program still exits immediately, repeated reset-failed and start operations open another failure cycle. Cleaner counters do not restore missing configuration, permissions or dependencies. Increasing limits, extending intervals or disabling rate limiting with zero needs a capacity and failure-policy basis. Available options are not automatically appropriate repairs.

Using systemctl stop as the failure input is another mistake. Restart has exceptions for stops initiated by the manager, so an operator stop is not equivalent to spontaneous process failure. This fixture deliberately returns one to specify its input. Real investigations must also check settings such as SuccessExitStatus and RestartPreventExitStatus to establish how the effective unit interprets an exit.

ExecCondition exit handling addresses continuing, skipping or failing conditional commands. Unit conditions and ExecCondition are distinct; the manual’s rule about failing unit conditions not consuming the rate limit must not be extended to every preparation script by name alone. The fixture fails directly in its main command without relying on that analogy.

Does a successful reset-failed mean the service has recovered?

No. It can clear failure state and the rate counter, but recovery still needs a new start and business-readiness evidence; an unchanged failure cause merely begins another cycle.

The manual explicitly says reset-failed flushes the service’s start-rate counter. Report the management action, subsequent launch and final business result separately. A new process may still be preparing or waiting for dependencies. The readiness-notification discussion addresses when startup completion can be promised; clearing markers cannot establish that result.

Proposed validation retains effective configuration, manager version, each failure, the limiting point, the observation interval, the repair and the new trigger’s identity. This distinguishes an unavailable budget, a missing trigger, another failed start and a running process whose business path is not ready. No recovery run or production availability is claimed. Determine why attempts stopped, then arrange an observable recovery rather than treating elapsed time as completed incident handling.
