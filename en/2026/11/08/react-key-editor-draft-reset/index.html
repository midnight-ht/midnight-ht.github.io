Why does a React editor keep the previous record’s draft?

Changing record props need not reset an editor at the same tree position. A complete editor and A/B/A expectations explain keyed subtree recreation, draft retention and separate backend work.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-08 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • A stable record key expresses component identity within a parent.
  • Recreating a subtree can clear more than one input state.
  • Restoring a draft requires a longer-lived retention owner.

An editor at the same tree position can receive a new record while retaining its old local state. Decide whether switching should discard or preserve drafts before aligning component and record identity. A record key can recreate a subtree; it does not archive drafts or save unsent content for the user.

React’s official state-preservation documentation associates state with render-tree position and explains how component type and keys participate in identity. The retrieved page displays v19.3. It does not provide an article-specific update date, so the version navigation is not evidence that every paragraph was recently revised.

A changed business record need not change tree identity

Suppose the details page always renders Editor at the same position and changes record from A to B. The application sees a different customer, while React can still see the same component type at the same position. The heading can show B while the input retains A’s unsaved text.

Passing record.name as a useState initial value does not request reinitialization on every prop change. Initialization and later synchronization are separate contracts. An unconditional Effect can create another error by overwriting an active draft when the same record refreshes. Visual agreement between a heading and input is insufficient grounds for discarding local work.

The existing derived-state article recognizes a draft as legitimate independent state. The addition here is an identity boundary: which record change creates a new editor instance, which descendant states leave with it, and who retains content for a return visit.

A complete editor with deliberate discard

This complete client component remains unexecuted in a React runtime. It has no save operation, API or persistence. Its teaching policy deliberately discards local unsaved edits when switching records. That policy must fit the product; implementation behavior does not establish user consent to discard work.

import {useState} from 'react';
const records = [{id: 'a', name: 'Alpha'}, {id: 'b', name: 'Beta'}];
function Editor({record}) {
  const [draft, setDraft] = useState(record.name);
  return <label>{record.id}: <input value={draft}
    onChange={e => setDraft(e.target.value)} /></label>;
}
export default function App() {
  const [id, setId] = useState('a');
  const [renders, setRenders] = useState(0);
  const record = records.find(item => item.id === id);
  return <main>
    <button type="button" onClick={() => setId('a')}>A</button>
    <button type="button" onClick={() => setId('b')}>B</button>
    <button type="button" onClick={() => setRenders(n => n + 1)}>
      Parent update {renders}</button>
    <Editor key={record.id} record={record} />
  </main>;
}

Specify acceptance independently: initially A shows Alpha; type A-draft; update the unrelated parent counter and retain A-draft; select B and see Beta; type B-draft; return to A and see Alpha. The absence of A-draft on return follows the discard policy rather than indicating a failed save.

For the failure control, remove only the record key while retaining position and type. The documented rules predict that selecting B can change the label to b while preserving A-draft in the input. Inspect both identity and text; checking the new heading alone misses the mismatch. These are expectations, not captured browser results.

The reset boundary extends beyond one field

React documents that a changed key recreates the component, descendant state and DOM. An editor’s expansion state, selections and validation can reset too. Changing a key on an entire workspace merely to clear one field may discard unrelated state.

Place identity at the subtree with the intended shared lifetime. Record-specific form state can change identity while workspace filtering and layout preferences remain above it. Classify ownership before choosing where the key belongs.

A server refresh for the same record is another path. With the same ID, a stable key does not force the draft to reset. Decide whether an untouched editor accepts a refresh and how an active edit handles conflict. Including a modification timestamp in the key turns every refresh into a recreation policy, potentially destroying the input that should remain.

Can a key alone restore the draft when the previous record is selected again?

No. A draft needs a longer-lived owner after its component unmounts. The official page discusses lifting drafts into the parent and indexing them by record. A and B can then retain separate content even when their editors leave the tree. Keys express instance identity while the parent owns retention.

Recovery after page closure needs a further storage, account-isolation, expiry and version policy. Browser storage is not server confirmation, and the fixture implements neither. Keeping every editor hidden in the tree is another possible retention strategy, but its DOM, subscription and permission costs need consideration.

The useId discussion separates page-association identifiers from data keys. Here too, use a stable business identity within the parent rather than generating a random key on every render. Random keys can reset the editor after unrelated parent updates.

Resetting state does not cancel backend work

If the old editor has already started autosave, a new key changes frontend identity without reversing a server write. Requests still need record IDs, versions and result ownership. Otherwise a late A response can contaminate shared state currently displaying B.

Also inspect component definitions. Defining Editor inside the parent’s execution can give it unstable type identity and cause unrelated resets. A stable definition and a stable record key address separate conditions.

Proposed checks cover the A/B/A round trip, same-record refreshes, unrelated parent rendering, descendant reset scope and the chosen retention policy. Add late-response cases separately when autosave exists. Local input clearing does not prove a server operation stopped. Each state should have an identifiable owner, discard condition and instance-creation trigger.
