Why an Iceberg file absent from the latest snapshot may still be needed

Use a two-snapshot reference graph to distinguish Iceberg snapshot expiration from orphan removal, accounting for retained history, active writers and path representations.

Key takeaways

  • A file absent from the latest snapshot can still support retained history.
  • Expiration and orphan removal address different file histories.
  • Writer duration and path identity belong in cleanup conditions.

An Iceberg file absent from the latest snapshot can still support retained history. Before deletion, inspect table references and distinguish snapshot expiration from orphan removal. File age and a successful current query cannot establish the same thing.

Suppose compaction replaces older data files and current queries look correct, but object storage remains large. First decide which historical versions must remain usable. A directory policy that keeps only current files can remove that history. The official documentation selector observed for this article displayed Latest 1.12.0; latest URLs are mutable, so the consulted source bytes were retained with hashes. No lake was connected, maintenance operation run or file deleted.

Use retained references to decide whether a file is still needed

The Iceberg reliability guide describes snapshots that track the table's data-file set and share metadata and files across versions. Commits atomically change the current metadata reference, and readers use a consistent snapshot. New files therefore do not automatically make all older files disposable: a valid retained snapshot can still depend on them.

A storage listing is not the sole authority for table contents. An object may belong to the current snapshot, historical snapshots or an unfinished writer. Conversely, a file omitted from the current query may still have retained references. Querying data and selecting deletion candidates require different evidence.

The maintenance guide's snapshot-expiration section explains that expireSnapshots removes old snapshots from time-travel history. Data files remain while needed by snapshots retained for time travel or rollback. Expiring one snapshot is consequently not equivalent to deleting every file that appeared in it.

Two snapshots expose the wrong deletion set

This complete, unexecuted Python 3 example has two hypothetical snapshots. s1 uses a and b; current snapshot s2 uses b and c. Independently specified targets are a,b,c when both snapshots remain, and b,c when only s2 remains. Shared file b does not become garbage when s1 expires.

"""Unexecuted local set example. It never enumerates or deletes real files.
Not an Iceberg maintenance implementation. Real refs/branches/tags need tooling.
"""
snapshots = {'s1': {'a', 'b'}, 's2': {'b', 'c'}}
def reachable(retained):
    return set().union(*(snapshots[name] for name in retained))
listed = {'a', 'b', 'c', 'pending-x', 'orphan-y'}
active_writer_files = {'pending-x'}
ages_hours = {'pending-x': 2, 'orphan-y': 96}
expected_before = {'a', 'b', 'c'}
expected_after = {'b', 'c'}
expected_orphan_candidates = {'orphan-y'}
if __name__ == '__main__':
    assert reachable(['s1', 's2']) == expected_before
    assert reachable(['s2']) == expected_after
    candidates = {p for p in listed - reachable(['s1', 's2'])
                  if ages_hours[p] >= 72 and p not in active_writer_files}
    assert candidates == expected_orphan_candidates
    print(sorted(candidates))

File a is the tempting mistake. It is absent from current s2 but remains necessary while s1 is retained. Keeping only current files would break that historical reference. After successful expiration of s1, a loses its snapshot reference in this two-snapshot teaching graph. Real branches, tags and other retained references require the actual version's maintenance rules; the set function does not implement them.

The listing also includes pending-x and orphan-y. The first is assumed to have been uploaded by an active, uncommitted writer two hours earlier. The second is assumed to be an unreferenced remnant of a failed job four days earlier. The example selects only orphan-y as a candidate and deletes nothing. Its 72-hour threshold illustrates the documented three-day default, not a guarantee that every older object is safe to remove.

Passing the local assertions would establish only those teaching sets. It would not prove the absence of omitted references, path mismatches or concurrent writers in real storage. Use Iceberg operations supported by the selected engine and version, inspect their reference coverage and retain their conditions. This article supplies no generic rm script that bypasses table metadata.

Expiration and orphan removal address different storage histories

The maintenance guide describes deleteOrphanFiles for objects not referenced by table metadata, including files left by failed jobs. Expiration manages retained historical references. Orphan removal addresses objects outside that reference history. Running one does not necessarily address the other's storage use, but an unchanged size is not a reason to make deletion more aggressive.

The longest write duration matters. The guide explicitly warns that orphan retention shorter than a write can remove in-progress files and corrupt the table. A four-day writer is not protected merely by using a three-day default. Inspect real task durations, retries and pauses before choosing the retention and maintenance coordination policy.

Name the capacity objective too. Shortening time-travel history calls for a snapshot-retention decision. Cleaning failed-job remnants calls for investigating orphan production. Reducing small-file overhead calls for another operation, compaction. No storage-saving percentage is claimed here. The article on reusable database space versus file shrinkage concerns a different mechanism but illustrates why an operation's success and a capacity objective need separate measurements. Its PostgreSQL commands do not apply to an Iceberg table.

Can orphan removal proceed after file path representations change?

First investigate the mismatch rather than treating an unmatched listing as disposable. The maintenance guide warns that changing a path's authority can make historical URLs disagree with filesystem listings even when they refer to the same file. A longer retention interval does not repair an identity mismatch.

For example, a filesystem migration could list an object under a new HDFS authority while metadata still contains the old representation. String comparison may then treat the new listing as unreferenced. This explains the documented warning; it is not a claim that every storage migration behaves that way. Compare the representations actually used by the target filesystem and tool. Stripping prefixes and comparing filenames is not a substitute.

A proposed acceptance exercise creates two snapshots sharing files in a disposable table and records their IDs and references. Verify historical reads while history remains retained. After approved expiration, inspect current and historical query behavior alongside reference changes. Create a separate failed-writer remnant for the orphan case and establish that no active writer needs it. If the engine offers a preview facility, verify support in that precise version rather than inventing a safety flag.

Retain the operation version, policy, reference sets, actual query results and storage observations. A disappearing file does not prove the table remains correct; a successful current query does not prove historical recovery remains available. The recovery-rehearsal article discusses that evidence distinction. None of these checks was executed here. The deliverable is a reference calculation and a basis for choosing maintenance operations.
