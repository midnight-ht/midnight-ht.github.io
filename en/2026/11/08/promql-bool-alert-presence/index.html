Why can a PromQL result of zero still activate an alert?

Bool comparisons retain zero-valued elements, while alerts activate by result presence. Two targets distinguish filtering, waiting periods and missing data.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-08 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • A zero-valued element can activate an alert for its label set.
  • For delays persistent activity rather than correcting the selected set.
  • Bool does not create zero-valued series for missing targets.

up == bool 0 can return zero for a healthy target while keeping that series in the result. Used directly as a Prometheus alert expression, it can make the healthy target active. Alert activity depends on whether a vector element with that label set exists, rather than converting the sample value to a Boolean again.

Comparisons can filter or retain zero and one

The PromQL comparison-operator documentation explains that vector comparisons filter false elements by default. With bool, matched false comparisons remain with value zero and true comparisons receive one. This article checked the rolling latest documentation on November 7, 2026. Its examples use float samples compared with a scalar, without generalizing to every native-histogram operation.

A status display can need a zero or one for every known target. A failure list instead needs healthy members removed. Reusing a display expression in an alert can turn “show this healthy state” into “an alertable member exists.” The problem is the result-set contract, not incorrect arithmetic on zero.

The alerting-rules documentation defines an alert as active for label sets present in the expression’s result vector. Without for, the first evaluation can activate it immediately; with for, the element must remain active through the waiting period. Notification delivery involves later components and cannot be inferred from an active state.

Two targets and three complete results

This teaching input is unexecuted; no monitoring server was queried. Assume the following float samples exist at the same evaluation timestamp. The labels show only job and instance for readability. Real queries may carry additional identity labels that must be retained in the evidence.

up{job="demo",instance="a"} = 1
up{job="demo",instance="b"} = 0

Target a was successfully scraped and b was not. Up is a collection signal, not a direct assertion about user-facing availability. Consider three queries:

up{job="demo"} == bool 0
up{job="demo"} == 0
(up{job="demo"} == bool 0) == 1

The first retains a=0 and b=1, so both elements can activate an alert when that result is used directly. The second retains only b=0. It can still activate b because a nonzero value is not required. The third creates the Boolean mapping and then applies a default filtering comparison, leaving only b=1. These are independent expected results from the stated input, not captured query output.

The first two intentions can be placed in a complete teaching rules file. It has no for, keep_firing_for or extra labels, so membership selection remains visible. Production duration, identity and routing require separate decisions. This YAML has not been loaded into any server.

groups:
  - name: presence-demo
    rules:
      - alert: BoolPresence
        expr: up{job="demo"} == bool 0
      - alert: FilteredFailure
        expr: up{job="demo"} == 0

Given the specified inputs and successful evaluation, BoolPresence has active results for both a and b; FilteredFailure has only b. Actual alert labels also include each alertname, so counting instances without their rule identity is insufficient. The correction removes the healthy member from the first result. There is no need to change the second result’s zero into one to make it “really alert.”

Will adding for remove the healthy zero-valued target?

No. If a’s zero-valued element remains present, it can satisfy the waiting period. A longer duration delays the same incorrect set rather than removing its healthy member. First establish which label sets belong in the alert, then choose how long they should persist.

This changes the validation method. Seeing an alert that is not firing during its waiting period can look like a successful fix while it remains pending. Retain the raw expression output, active or pending state and eventual firing state at comparable evaluation times. A newly edited query cannot be paired with a state screenshot from several minutes earlier.

Bool does not fill an empty result with zero

The comparison clauses also explain that unmatched elements and invalid histogram comparisons can still produce no result. If target c does not exist in this input, bool does not create c. Detecting a missing expected target requires a reliable expected set and a separate absence condition. Values for the two existing targets do not establish collection coverage.

The missing-data article distinguishes absent data from measured zero. This question goes further: even a correctly computed zero is an existing element for alert evaluation. Those decisions cannot be exchanged or repaired by converting every unknown into zero.

Which expression belongs at the alert boundary?

Bool has a valid role when a display or calculation needs zero-and-one series. At an alert boundary, filter out elements that do not satisfy the intended condition. Mapping and then filtering is another valid representation, but explain why the intermediate form is needed and inspect its final labels rather than adding conversions mechanically.

If the Boolean mapping is already stored as a recording rule, for example demo:target_down:bool, correcting an alert does not require deleting the intermediate series used by a display. Keep that display input and filter with demo:target_down:bool == 1 at the alert boundary. Given a current recorded result of a=0 and b=1, only b=1 remains. If the recording rule has no fresh result, inspect its evaluation state rather than approving this selection from an old display value. Reuse of intermediate data and final failure membership remain separate contracts, with the recording rule’s actual labels checked for matching dimensions.

Other failures can arise from label matching, evaluation errors or rule limits. The rule-limit article describes all output being discarded, the opposite of this fixture retaining an unwanted healthy member. Preserve inputs and expression results at the same timestamp before explaining a state transition or calling it recovery.

Proposed verification starts with a=1 and b=0, then fails a, recovers b and removes an expected target. Check labels, values, element counts and rule states separately. Notification delivery needs its own receipt. Record the Prometheus version and effective rules. No server was started, promtool was not run and no delivery was verified here; the conclusions are document semantics and expected sets for the complete stated inputs.
