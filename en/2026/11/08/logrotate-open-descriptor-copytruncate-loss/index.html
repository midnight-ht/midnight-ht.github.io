After rotation leaves an empty log, check which file the writer still holds

Use a local file-sequence exercise to explain retained writers and the copytruncate loss window, without presenting it as a real logrotate run.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-08 · Estimated read 16 min
Translations
zh-CN en

Article

Key takeaways

  • Rename and new-path creation do not change an existing open descriptor.
  • Records added between copy and truncation may be lost; create has no effect with copytruncate.
  • Validate application reopening, file contents and collection outcomes separately.

Renaming app.log and creating a new file with that name does not redirect an open writer. Rotation also needs a reopen contract, or the writer may continue appending to the old file. When the new log is empty, identify the file the process actually holds before deciding that it produced no logs.

A changed name does not replace an open file

The Linux rename manual says open file descriptors are unaffected by rename. The checked page belongs to Linux man-pages 6.19, with a manual date of 8 February 2026 and HTML rendering dated 9 September. This analysis uses local POSIX file semantics, without claiming verified network-filesystem failure behavior or defaults on other operating systems.

An application opening app.log holds a descriptor. Rotation renames that path to app.log.1 and creates a new file at the original pathname. There are now two names and two file objects, while the original descriptor still identifies the original object. Further appends enter the renamed file. Reading only the new pathname can make the application appear silent even as its old file grows.

The pinned upstream logrotate manual source says create makes the same-named new file after rotation and before postrotate. This article pins the file commit dated 4 March 2026. It remains an upstream template containing a version placeholder, not evidence of an installed distribution release. A created pathname does not prove the application closed its old descriptor and reopened that path.

Establish content expectations with a fixed sequence

The following complete Python example is unexecuted. It uses an automatically cleaned temporary directory, calls no logrotate executable, sends no process signals and touches no production logs. The first section demonstrates rename and reopen. The second deliberately inserts a record between copying and truncation, without depending on a chance race.

from pathlib import Path
from tempfile import TemporaryDirectory
import shutil

def emit(stream, record):
    stream.write(record + "\n")
    stream.flush()

with TemporaryDirectory() as directory:
    root = Path(directory)
    active = root / "app.log"
    rotated = root / "app.log.1"

    def state():
        return tuple(path.read_text() for path in (rotated, active))

    observed = {}
    with active.open("a") as writer:
        emit(writer, "A")
        active.rename(rotated)
        active.write_text("")
        emit(writer, "B")
    observed["renamed"] = state()
    with active.open("a") as reopened:
        emit(reopened, "C")
    observed["reopened"] = state()

    active.write_text("A\n")
    shutil.copyfile(active, rotated)
    with active.open("a") as late_writer:
        emit(late_writer, "B")
    with active.open("w"):
        pass
    observed["truncated"] = state()
    assert observed == {
        "renamed": ("A\nB\n", ""),
        "reopened": ("A\nB\n", "C\n"),
        "truncated": ("A\n", ""),
    }

A candidate command is python3 rotation_probe.py after saving the file in an isolated directory. Retain the interpreter version and actual exit result. Assertions are not passing evidence without execution. This fixture does not emulate a daemon’s reopen interface: closing writer and opening active again simply makes the object change explicit.

emit keeps record append and flush together. state reads a complete old-file/new-file snapshot; observed names the three checkpoints renamed, reopened and truncated for comparison with predetermined contents. Opening and closing the original in w mode explicitly performs the final truncation. The first section’s independent expectation is an old file containing A and B, an empty new file before reopening and C alone in that new file afterward. B uses the original descriptor, while C uses a newly opened path. Checking only that both files exist misses the handoff. Identical contents could instead indicate a preparation or path error; preserve the input sequence.

The second section copies a file containing A, appends B and truncates the original. The copy contains A and the original is empty, leaving B in neither. This is a deterministic ordering model, not a measurement of lost records on a server or a concurrent stress test. Successful copy and successful truncation can coexist with loss between those operations.

Which coordination does copytruncate replace?

The upstream manual describes copytruncate as copying and then truncating the original file in place, useful when a program cannot be told to close its log. It explicitly warns that records may be lost in the short interval between the operations. The create directive has no effect because the original file remains. Combining them does not provide both retained descriptors and a new-file handoff.

This handles retained writers without providing lossless coordination. Measuring the interval and observing loss under a specific workload requires real execution. A short interval is not permission to lose one business record. Diagnostic-log tolerance depends on investigation needs; a potentially lossy file should not be the sole record establishing an order’s state.

The alternative is rename, create and the application’s documented reopen operation. Some applications expose a command or signal; others do not. HUP is not a universal reopen instruction: it may do nothing relevant, terminate the program or have another effect. Check version-specific documentation, target process, completion timing and failure results before connecting the operation to rotation.

Will fixing permissions redirect an existing writer to the new file?

Not automatically. Permissions affect whether a later open succeeds; an existing descriptor still refers to the old file, so verify the actual reopen action and its failure outcome.

This adds a failure path: postrotate notified the application, but the application cannot open the new file because of ownership or permissions. A finished rotation script does not establish writer handoff. Check actual permissions, the reopen outcome and where subsequent unique sequence markers land. Do not turn later success after a permission repair into a claim that the first rotation never failed.

Compressing or moving the old file while the application still writes it also needs review. A collector may retain an old descriptor as well. Coordinate retention with both parties’ handoffs. No universal compression delay or filename-based deletion policy is provided here. Establish that writers and readers have completed the transition before choosing retention actions.

Connect writer identity to validation

An isolated validation plan gives each bounded event a run identifier and sequence number before, during and after rotation. Record paths, file identities, process descriptors and both files’ contents, alongside separate exit results for rotation and reopening. A decrease in app.log size alone cannot distinguish a successful handoff, continued old-file writes or data loss.

Also establish whether collection received the records. File presence is not query visibility, and missing query results need not originate in the rotation window. journald rate limiting addresses another ingestion loss point, while Docker logging configuration addresses which settings an existing instance uses. Those conclusions are not interchangeable.

Choose based on reliable reopen support, acceptable record loss and observable handoff. When reopening is supported, assess that coordinated path. Otherwise explicitly accept the copytruncate window or change the output arrangement rather than describing convenience as a lossless guarantee. No logrotate run, production configuration change or complete logging-chain verification is claimed. Account for pathnames, descriptors and each test record’s destination before declaring writer handoff complete.
