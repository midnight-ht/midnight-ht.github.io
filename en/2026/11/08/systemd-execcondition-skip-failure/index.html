Why does ExecCondition exit 1 skip a service without marking it failed?

ExecCondition distinguishes continuing, skipping and failure. A complete teaching unit retains the effects of SuccessExitStatus and ExecStopPost.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-08 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • By default, one through 254 skip without failure; 255 or abnormal exits fail.
  • Review SuccessExitStatus with the complete effective unit.
  • ExecStopPost must handle a main command that never ran.

An ExecCondition command that exits with one can skip subsequent startup commands without marking the systemd unit failed. That is the condition command’s exit protocol, not proof that business work succeeded. Operators need to distinguish “not applicable this time” from “unable to check,” or both will look like an absent main process.

A nonzero exit has more than one meaning

The ExecCondition entry in systemd.service places condition commands before ExecStartPre. By default, exit codes one through 254 skip the remaining startup commands without marking the unit failed. Exit 255 or abnormal termination, such as a timeout or signal, fails the unit. Zero and exits matching SuccessExitStatus allow execution to continue.

This article checked the rolling latest manual on November 7, 2026. The entry says the option was added in version 243. That does not establish the target host’s installed behavior or the absence of configuration overrides. Read the manager version, effective unit and drop-ins. A script ending in exit 1 is not a complete description of the activation transaction.

Suppose a local job should run only when a pending-work list contains entries. A verified empty list can be legitimately inapplicable. An unreadable or corrupt list can mean the applicability check failed. If the script returns one for both, the manager receives the same skip protocol. Failure-only alerting may miss the latter while business work remains unhandled. The decision is who has enough evidence to say the job is unnecessary.

A teaching unit without business effects

The complete unit text below is uninstalled and unexecuted. It uses local Python exits and printf markers, without reading a work list, contacting services or changing business data. It assumes those absolute paths exist in an isolated Linux environment supporting ExecCondition. Before considering activation, validate paths, arguments and version with that environment’s unit parser. No system-directory installation or activation procedure is supplied here.

[Unit]
Description=Condition exit teaching fixture

[Service]
Type=oneshot
ExecCondition=/usr/bin/python3 -c "import sys; sys.exit(1)"
ExecStart=/usr/bin/printf "MAIN-ENTERED\n"
ExecStopPost=/usr/bin/printf "POST-ENTERED\n"

One is the displayed input. Prepare two independent variants changing only sys.exit to zero and 255. There are no Restart, SuccessExitStatus, SuccessAction or RemainAfterExit settings. Their absence is a fixture choice, not a recommendation for every real service. Each group observes scheduling and manager state rather than producing a report.

For zero, the condition should permit the main command and its MAIN-ENTERED marker; normal oneshot completion also allows observation of cleanup. For one, the main command is skipped, the condition does not mark the unit failed, and ExecStopPost runs. For 255, the main command is skipped but activation fails, and cleanup also runs. These are document-based expectations, not journal captures, systemctl output or passed tests.

The Python exit value is insufficient evidence by itself. It describes a command, not the activation job, unit state and business result together. Proposed observations include the condition result, MAIN and POST markers, job outcome, Result and ActiveState. Preserve the fields actually returned by that run instead of preparing a success log in advance.

Does skipping the main command also skip ExecStopPost?

There is no such guarantee. The manual explicitly says nonzero or abnormal ExecCondition exits also run ExecStopPost. Cleanup must tolerate a main process that never started and resources that were never created. A cleanup script that assumes a temporary directory exists can introduce a second failure on a legitimate skip.

This adds a side-effect boundary: no MAIN marker does not mean that the whole transition was action-free. POST only prints local text here. Real cleanup might release resources or send a message and needs its own scope, authorization and repeatability contract. Skipping business startup does not automatically authorize cleanup’s external actions.

The current manual also distinguishes an ExecCondition skip from an unmet Unit-level Condition check. The former participates in the activation transition and can honor SuccessAction; the latter prevents activation and does not trigger that same success action. Moving a condition between these mechanisms can change lifecycle consequences, not merely syntax.

Who decides an error may become a skip?

The condition script needs an explicit exit table. It should identify inputs that establish inapplicability and inputs that invalidate the check itself. A verified empty list can skip; a permission error that prevents reading it should retain an error and follow the project’s failure policy. This article does not assign universal business exit codes. It rejects an unconditional exit one after a broad exception handler as adequate classification.

SuccessExitStatus requires another review of that table, because matching results can allow startup to continue. Applying the default range without reading the effective override can label a result as skipped when the host actually enters its main command. Bind the decision to the complete effective configuration and script version.

The readiness article concerns when an application reports startup complete. The persistent-timer article concerns catch-up activation after missed periods. Neither decides whether this condition is applicable or proves old work completed when the main command did not run.

Evidence for the next operator

Proposed verification covers zero, one and 255 in an owned isolated environment, then adds configured overrides and abnormal termination. Retain the effective unit, manager version, script identity, job result and both markers. Record cleanup failures separately so later errors do not erase the original condition outcome. Parsing the unit would not establish that these runtime paths were exercised.

Recovering pending work also requires linking the list identity, applicability decision and processing results. A unit that was not marked failed only shows how the manager classified its transition under the current contract. It does not establish that the list was empty or the work completed. Decide what evidence permits a skip before making script exits and monitoring depend on it.
