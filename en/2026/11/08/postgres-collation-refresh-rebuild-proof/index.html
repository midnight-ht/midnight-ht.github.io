Does a vanished collation warning mean old indexes are repaired?

Use a two-index ledger and read-only catalog queries to distinguish a vanished warning, restored dependencies and workload validation.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-08 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • Version refresh does not verify rebuilding.
  • Keep restoration evidence for each affected object.
  • Version proxies do not exclude distribution backports.

REFRESH VERSION can silence a collation warning without checking whether dependent objects were rebuilt under the new rules. After an OS or ICU upgrade, identify the changed rules and affected objects, restore those objects, and then acknowledge the version. A vanished warning is metadata evidence, not sufficient evidence that an old index is repaired.

Suppose a maintenance window ends with a version-mismatch warning for a named collation. An operator runs the refresh command, sees no warning on the next query, and closes the upgrade. The missing work can be the recovery of structures organized under the old comparison rules. This discussion follows PostgreSQL 18 documentation; no OS upgrade, REINDEX or ALTER has been executed.

Why can recorded versions and stored structures diverge?

The PostgreSQL 18 ALTER COLLATION documentation explains that the provider version is recorded when a collation is created and checked when it is used. A change in collation definitions can invalidate ordering assumptions in stored objects, including indexes. Existing structures are not automatically rebuilt on every comparison.

The prescribed sequence directs maintainers to rebuild all affected dependent objects, for example with REINDEX, before refreshing the version. Refresh updates the catalog but does not check that rebuilding was completed correctly. Command success, matching catalog versions and restored structures therefore require separate evidence. A single green status hides which step was actually completed.

Conversely, an OS upgrade alone does not prove that every ordering relation changed. Retain the actual system package, provider library and version identities and use their changes and the dependency inventory to determine scope. Without exact environments, inventing a pair of characters whose ordering supposedly reversed is not a valid check.

How do two indexes form a recovery ledger?

Consider a hypothetical app.name_sort collation recorded as v-old while the runtime reports v-new. customer_name_idx depends on it; customer_email_idx uses C instead. These version labels represent no specific ICU release. Determine actual dependencies rather than assuming that indexes on the same table share the affected named rule.

Object Dependency in this example What does refresh alone establish?
customer_name_idx app.name_sort No rebuild or validation receipt
customer_email_idx C No direct inclusion in the first named dependency set

The independent expectation is that refreshing can remove the warning while leaving the first object’s rebuild evidence empty. Whether the second object is affected by some other system change needs its own scope analysis. Acceptance requires a restoration and check record for every affected object, rather than a green icon beside every index regardless of what happened.

This unexecuted read-only inventory places versions and direct dependencies on the same row, making receipts easier to associate with their rule. The schema distinguishes same-name objects. LEFT JOIN retains a collation with no direct dependency; the dependency-type condition belongs in ON, because placing it in WHERE would discard those rows. Actual rows and counts are unknown.

SELECT n.nspname AS schema_name, c.oid, c.collname,
       c.collprovider, c.collversion,
       pg_collation_actual_version(c.oid) AS actual_version,
       pg_describe_object(d.classid, d.objid, d.objsubid) AS dependent_object
FROM pg_collation AS c
JOIN pg_namespace AS n ON n.oid = c.collnamespace
LEFT JOIN pg_depend AS d
  ON d.refclassid = 'pg_collation'::regclass
 AND d.refobjid = c.oid
WHERE c.collname = 'name_sort'
ORDER BY schema_name, dependent_object;

For an actual operation, select the intended schema and identity and restrict the inventory to the approved scope. Catalog queries start a ledger; they are not automatic recovery tools. Extensions, default collations and special dependencies still require examination. The documentation describes an analogous database-default refresh command. One named-collation dependency query does not establish coverage of every database-default effect.

What evidence should recovery retain?

A ledger can keep before-and-after provider identities, the reason each object is affected, the restoration action, its result and workload checks. Recovery can mean returning to the intended provider or rebuilding under the new one. The upgrade objective, available window and actual dependencies determine that choice. Neither route justifies declaring recovery complete from a catalog update alone.

Rebuilding also needs a plan. The October 9 article on concurrent index construction explains waiting, resource cost and failure states. This discussion supplies no environment-independent REINDEX script. Choose execution procedures from the actual version’s command restrictions, object types and maintenance conditions.

Validation can cover representative ordering queries, relevant equality or uniqueness constraints, and business reads and writes. Preserve statements, parameter classes and the provider version so the checks address this change. Seeing an index in a plan proves that the optimizer used it; a valid flag alone is not independent proof of comparison correctness. If the new rules make previously distinct values conflict, resolve that against the actual identity policy rather than hiding it with refreshed metadata.

The October 16 discussion of multilingual ordering policy separates display order from identity. An upgrade adds a temporal distinction: stored structures may reflect old rules while new comparisons use the new library. Acceptance must explain how those states became consistent again.

Can matching version strings eliminate the need to inspect collation changes?

No guarantee follows from that alone. For the libc provider, the note explains that glibc versions are a proxy, and distributions can backport collation changes. Retain actual library and package identities in upgrade evidence. This is a limitation of that provider’s version proxy, not an assertion that version information is useless.

A completion record should identify the rules examined, objects requiring recovery, receipts that cover them and the evidence preceding version acknowledgement. Keep unexecuted inventory or recovery work explicitly pending. This example has no live catalog output or rebuild receipt; it provides a way to distinguish a removed warning from repaired objects.
