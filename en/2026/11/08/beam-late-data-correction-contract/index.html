Before applying late data, choose replacement totals or deltas

Work through five, twelve and an incorrect seventeen to define late-data corrections in Apache Beam event-time windows, separating replacement totals, additive contributions and audited backfills.

Updated 2026-11-08 · Estimated read 16 min

Article

Key takeaways

  • Event time assigns windows; watermark progress determines lateness.
  • Accumulating totals need a replacement contract rather than blind addition.
  • Corrections beyond retained window state need a separate audited workflow.

Late events can revise a window that has already emitted a result, but the sink must know whether each output replaces a cumulative total or adds a new contribution. A window that emits five and later twelve must not become seventeen merely because both versions were added.

Suppose orders are grouped by their occurrence time into one-minute totals. A dashboard wants early numbers and accepts corrections for another two minutes. The contract must cover event assignment, emission, retention and sink updates together. This design follows the current Apache Beam Programming Guide. No Beam SDK, TestStream or runner was executed.

A watermark does not choose the sink's write operation

The Beam guide's windowing and late-data sections distinguish event time, carried by an element's timestamp, from processing time, determined by the processing system. Events need not arrive in occurrence order. Windows assign elements by event time. A watermark describes the system's notion of input progress; an element for a window arriving after that watermark passes its end is late.

That is not a universal rule that a wall-clock minute proves permanent completeness. Sources and pipelines determine watermarks. The guide's simplified lag example is not an algorithm to impose on every source. An order received at 10:01 but timestamped 10:00:40 can still belong to the preceding minute. Substituting arrival time changes the reporting question.

The trigger sections explain that default windowing allows no late data. A correction strategy needs allowed lateness and a trigger that can emit the relevant results. Increasing retention without examining whether the trigger can still respond does not establish that a report will receive corrections. Pin the SDK and runner used for implementation and verify their support. An unversioned guide is not a runtime acceptance record.

Accumulating and discarding panes require different sink contracts

Beam calls the contents emitted at a trigger firing a pane. Accumulating mode includes previously emitted elements in later panes. Discarding mode excludes those already emitted elements from subsequent panes. This is more than an internal storage setting: it changes whether the receiver should replace an earlier total or add a contribution.

Use the half-open window [0,60), with amounts expressed in integer cents. Event a occurs at second 10 and contributes 2. Event b occurs at second 30 and contributes 3. When the watermark advances to 61, their total is 5. Event c then arrives, timestamped second 40 with amount 7. It belongs to the same window but is now late. If the strategy accepts it within 120 seconds of allowed lateness and fires for it, the accumulating total is 12. A discarding pane containing only its new contribution would instead total 7.

The sink contract must therefore say whether an output replaces the current value for the window and grouping key, or represents an independently additive contribution. Window boundaries alone cannot establish that. An additive protocol also needs pane identity or another duplicate-handling scheme if outputs can be redelivered. Discarding mode does not make an external database update exactly once.

This complete Python 3 file evaluates only the accumulating replacement contract. Events and watermark advances are explicit inputs rather than guesses from the local clock. It neither simulates a runner nor claims to reproduce Beam's internal trigger scheduling. The expected values are independently calculated as 2+3 and then 2+3+7. The final event contributes 11 cents; none of these numbers is a production observation.

"""Unexecuted arithmetic fixture, not Beam SDK/runner validation.
Window [0,60), lateness120; explicit watermark advances are inputs.
Output policy is accumulating replacement; expiry threshold is watermark>180.
"""
inputs = [('event', 10, 2), ('event', 30, 3), ('watermark', 61),
          ('event', 40, 7), ('watermark', 181), ('event', 50, 11)]
def evaluate(events):
    watermark = -1
    total = 0
    emitted = []
    rejected = []
    on_time_fired = False
    for event in events:
        if event[0] == 'watermark':
            watermark = event[1]
            if watermark > 60 and not on_time_fired:
                emitted.append(total)
                on_time_fired = True
        else:
            _, timestamp, value = event
            if not 0 <= timestamp < 60:
                raise ValueError('Fixture only owns one window')
            if watermark > 180:
                rejected.append(value)
                continue
            total += value
            if on_time_fired:
                emitted.append(total)
    return emitted, rejected
expected = ([5, 12], [11])  # 2+3; then2+3+7; never add5+12.
if __name__ == '__main__':
    assert evaluate(inputs) == expected
    print(evaluate(inputs))

Event d is timestamped second 50 and contributes 11. Before it arrives, the supplied watermark advances to 181, beyond the window end plus the 120-second retention allowance. The teaching contract therefore puts d in its expired-input collection. This does not claim that a real runner automatically writes such an element to an external channel named rejected. Capturing and reconciling expired input is a separate implementation responsibility.

Choose a revisable dashboard or a finalized settlement

A dashboard can store accumulating versions by window and grouping key and disclose when a number remains revisable. Twelve replaces five. Adding both creates seventeen, a concrete double-counting error that can occur even if the pipeline handles each input event only once.

A finalized settlement needs a definition of finalization and a route for older business facts discovered afterward. Extending allowed lateness retains more state without forcing an uncontrolled source to promise that no later event can ever arrive. Early results and subsequent corrections trade latency and retention cost against a chosen completeness policy; they do not eliminate uncertainty.

The October 21, 2026 article on CQRS read-side confirmation also uses the term watermark, but there it certifies relevant revisions have been applied. An event-time watermark describes input progress. A maximum order revision is not interchangeable with the boundary used to close a time window.

Can an order be corrected after allowed lateness has expired?

Yes, through a separate audited backfill or adjustment process. Do not assume that the streaming window still retains state for direct revision. Associate the correction with the original order, reporting interval and reason, so downstream systems can distinguish rebuilding history from appending an adjustment.

In the fixture, d was excluded from the accumulating twelve, but the business could later confirm that it belongs to that period. Recompute and publish a new period version, or create a defined adjustment. Either approach must prevent counting both the source order and its adjustment twice. A final-value interface needs a replacement/version rule and an explanation of retained historical results. Missing facts should not quietly become zero; the empty-input aggregate article explains that separate reporting distinction.

The proposed implementation check feeds these timestamps into a real Beam TestStream and explicitly advances its watermark. Fix the window, allowed lateness, trigger and accumulation mode. Inspect pane contents and the sink's final row, not just the number of firings. With cumulative outputs five and twelve, the receiver should retain twelve; a deliberate additive receiver exposes the incorrect seventeen. Include expired elements, redelivery and separate grouping keys. Only retained SDK, runner, configuration and actual output records would support a runtime claim. This article supplies an unexecuted contract and independently calculated targets.
