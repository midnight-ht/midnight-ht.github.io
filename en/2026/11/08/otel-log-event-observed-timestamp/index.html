Choose log timestamps separately for incident and collection questions

Timestamp and ObservedTimestamp describe source events and collection observations. Three complete records show fallback selection, missing provenance and clock-difference limits.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-08 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • State which timestamp serves event investigation and collection diagnosis.
  • A recommended fallback does not make missing event time known.
  • A difference across clocks is not automatically network latency.

Use a known source-event timestamp to investigate when an event happened, and an observation timestamp to investigate when collection saw it. OpenTelemetry’s Timestamp and ObservedTimestamp express those separate facts. Preserving both is only the first step: queries and displays must identify which one they actually use before a newly arrived log becomes a claim that an error just occurred.

Equal units do not imply a shared clock

The OpenTelemetry Logs Data Model defines Timestamp as event time measured by the source clock. It may be absent when the source timestamp is unknown. ObservedTimestamp records when the collection system observed the event using the observer’s clock. The specification checked on November 7, 2026 identifies itself as version 1.62.0 and marks the logs model Stable. That does not validate any SDK or backend mapping.

For events originating in OpenTelemetry, observation time is typically set at generation and equals event time. For externally collected events, such as file records, it is when OpenTelemetry code observed them. Calling this the final database-ingestion time would overstate the field: queues, export and storage can still follow and need separate observations.

Suppose an application writes an error in the morning and a collector reads the file in the afternoon. An event-time query addresses its occurrence window. An observation-time query reveals the afternoon collection activity. A display using only observation time can make the old error look new. This is an unexecuted hypothetical, not a production log or an investigated incident.

Three records with explicit choices

This complete local example is unexecuted. It can be saved as timestamp_probe.py and uses standard-library Python. The hypothetical integer nanoseconds near the epoch make independent arithmetic easy. They are not OTLP JSON, and the field spelling must not be treated as a wire-encoding example. Id is merely a teaching identity.

records = [
    {"id": "late", "Timestamp": 1000000000,
     "ObservedTimestamp": 6000000000},
    {"id": "unknown", "ObservedTimestamp": 7000000000},
    {"id": "skew", "Timestamp": 9000000000,
     "ObservedTimestamp": 8000000000},
]

def one_timestamp(record):
    if "Timestamp" in record:
        return record["Timestamp"], "event"
    if "ObservedTimestamp" in record:
        return record["ObservedTimestamp"], "observed-fallback"
    return None, "unknown"

expected = [
    (1000000000, "event"),
    (7000000000, "observed-fallback"),
    (9000000000, "event"),
]
assert [one_timestamp(item) for item in records] == expected

The ObservedTimestamp clause recommends preferring Timestamp when converting to a format with one timestamp, otherwise using ObservedTimestamp. The function expresses that selection and returns its provenance. It does not manufacture a missing event time. The expected list is independently specified from the inputs rather than copied from the function’s result.

Late selects the event time of one second; its raw observation-minus-event difference is five seconds. Unknown selects the observed fallback at seven seconds and has no computable difference. Skew selects the event time at nine seconds and has a raw difference of minus one second. These are paper expectations. The function does not parse date strings, infer zones or validate nanosecond ranges and is not a complete log converter.

Why five seconds is not necessarily network latency

The fields can come from different machines’ clocks. Their difference can contain file backlog, a collection interval, a process pause, transport and clock offset. A positive five seconds cannot be attributed entirely to the network from these fields alone. A negative value need not mean the application corrupted record order. First inspect clock synchronization assumptions, observation locations and unit conversion.

Measuring a particular transport segment requires explicit start and end observations, identity and comparable clocks. Existing fields can guide investigation without satisfying that entire measurement contract. Clamping negative differences to zero removes clues about clock or mapping problems. If a display requires special handling, retain the original value and explanation rather than calling the adjusted number actual elapsed time.

Sorting by observation time can also mislead causal analysis. Buffering, concurrency and replay can alter arrival order, while source clocks might not provide strict ordering across machines. Connect events through request, task or other reliable identities instead of asserting causality from proximity on a chart.

Can observation time replace an unknown event time?

It can be selected as the fallback for a single-timestamp output, but that does not make the source-event time known. A seven-second display should retain its observation-time provenance. This record still lacks evidence for an exact event window. Writing the fallback back into Timestamp would conceal the original absence from later consumers.

This follow-up determines what conversion must preserve. A backend with extra attributes may retain provenance or raw values. A backend with only one time field needs its loss documented in the interface contract and export evidence. The storage choice is backend-specific, not a new universal attribute standard. If both fields are absent, silently inserting the current time would likewise invent an observation.

Correct fields can still feed the wrong query

A converter can preserve both fields while a default search filters only observation time, missing the morning error. Verification must inspect the real backend’s filter and displayed column, checking event and observation windows separately. Replay and retention policies also need to explain where older events appear.

The severity article separates source text from a common comparison scale. The trace-correlation article separates an identifier from visible complete trace data. Two timestamps similarly require evidence for semantics, conversion and downstream use. Correct-looking field names do not select the right query.

Proposed verification covers known event time, missing event time, delayed observation and clock offset. Preserve original records, converted fields, collector version and selected-field provenance. Then inspect the same record identity in both backend windows. No collector was started, no logs were exported and no latency was measured here. Establish who observed each timestamp before using it to narrate an incident.
