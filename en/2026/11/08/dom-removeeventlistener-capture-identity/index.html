Cleanup ran, so why does the old widget still receive events?

Listener removal requires the correct target, event type, callback identity and capture value. A complete counting probe distinguishes mismatches and signal cleanup across remounts.

zh-CN en

Article

Key takeaways

  • A fresh function with identical source is not the registered callback.
  • A new options object can match when capture is correct.
  • An aborted signal cannot reset for a remounted lifetime.

A removal call can return normally without matching a registration. Match its target, event type, callback object and capture flag before declaring the widget disconnected. Executing a cleanup function proves that control reached it, not that the browser found a listener to remove.

The DOM Living Standard’s removal algorithm reads capture and matches type, callback and capture in the current target’s listener list. The checked standard was updated on November 4, 2026. This contract concerns native EventTarget, rather than arbitrary library subscriptions or Node EventEmitter.

Identical source does not mean the same function object

A widget may install an arrow function and construct an identical-looking arrow during cleanup. The latter is a different object. Repeated bind calls also create different function identities. Cleanup must retain the callback actually used during installation rather than manufacture a similar replacement.

The target matters too. Removing from document cannot remove a listener installed on window. A wrapper may select a different target from the one a developer expects; inspect the actual installation path instead of only searching for the handler definition.

The passive-listener diagnostic article emphasizes finding the real registration. This question adds the precise matching contract. Type, callback identity and capture identify the registration; passive affects cancellation behavior but is not a removal-matching field.

A new options object can match; a different capture value cannot

An installation with capture true is not matched by removal that omits options and therefore uses false. Conversely, a new options object containing the same capture value can match. Callback identity requirements should not be generalized into a requirement to reuse every argument object.

The listener-addition algorithm also prevents another registration with equal type, callback and capture. Readding the same callback with a different passive value does not establish that the existing registration was updated. Remove and reinstall deliberately when changing options, or follow the wrapper’s documented interface.

This complete JavaScript probe remains unexecuted. It can be checked in a target browser supporting the native interfaces. It requires no genuine click, scrolling or server, and is not an application-unmount result. Each removal case creates its own target. signalCounts separately retains the cumulative count for one shared lifetime.

function removalCase(label, chooseCallback, options) {
  const target = new EventTarget();
  let calls = 0;
  function handler() { calls++; }
  target.addEventListener('probe', handler,
    {capture: true, passive: true});
  target.dispatchEvent(new Event('probe'));
  target.removeEventListener('probe', chooseCallback(handler), options);
  target.dispatchEvent(new Event('probe'));
  return {label, calls};
}
const cases = [
  removalCase('fresh callback', () => () => {}, true),
  removalCase('wrong capture', original => original, false),
  removalCase('matching capture', original => original,
    {capture: true, passive: false})
];
const target = new EventTarget();
const controller = new AbortController();
const signalCounts = [];
let signalCalls = 0;
function signalHandler() { signalCalls++; }
function install() {
  target.addEventListener('probe', signalHandler,
    {signal: controller.signal});
}
function fire() {
  target.dispatchEvent(new Event('probe'));
  signalCounts.push(signalCalls);
}
install();
fire();
controller.abort();
fire();
install();
fire();
console.log({cases, signalCounts});

The independent expected calls for the three removal cases are [2,2,1]. Each first dispatch proves installation. A fresh callback and a wrong capture leave the registration active for the second dispatch; correct capture removes it despite a new options object. The signal fixture separately expects [1,1,1]. These are specification-derived expectations, not captured output.

Deleting a page element would not provide the same test. Tree removal and listener registration are separate contracts; code retaining a node can still dispatch to it. A window listener is not even owned by the removed descendant’s listener list. The disappearance of a widget does not establish that subscriptions on longer-lived targets ended.

Rule out other reasons for silence

Each removal case owns a fresh target so one failed cleanup cannot contaminate another case. Dispatch once to prove installation, then attempt removal and dispatch again. Silence after cleanup alone is insufficient: the listener may never have been installed, the event type may be wrong, or the test may not have reached its target.

A real remount should also change the bound record. Mount for record A, clean up, then mount for B; the next event should affect only B. One invocation can still be wrong if its closure retains A. Matching controls notification eligibility, while business identity controls which record receives its effects. Check both.

A dedicated signal can own a shared lifetime

The signal steps in listener addition remove an associated listener when its signal is aborted. An already aborted signal prevents addition. The signal case invokes once before abort, adds no call afterward, and installs nothing when the aborted signal is reused before its third dispatch.

A dedicated controller can express one mount’s ownership of several native listeners. Sharing it across unrelated widgets, however, can disconnect one when another exits. Common cleanup should be intentional rather than an incidental consequence of reducing declarations.

Signals cannot reset. Remounting requires a new appropriate lifetime owner, not another use of an aborted signal. Explicit removal may remain clearer when replacing one listener while keeping others. Signal grouping and precise removal are alternatives rather than a mandate to rewrite every cleanup in one style.

If one callback is registered with capture true and false, does removing one remove both?

No. They are distinct registrations. Remove each with its corresponding capture value, or deliberately associate both with the same dedicated signal. Removing one does not establish that the entire subscription ended.

Ending future notification also differs from undoing work already started by a handler. Removal and signal abort do not automatically cancel a request previously sent or reverse saved business state. Asynchronous results need their own ownership and exit policy.

Proposed acceptance checks dispatch after mounting, after cleanup and after remounting, verifying actual invocation counts and business-object binding. Add incorrect targets, fresh callbacks, wrong capture values and aborted signals as failure controls. The collection and reference article separates tree connection from retained objects. No heap analysis or universal leak-removal result is claimed here. The evidence sought is when a particular registration stops receiving notification.
