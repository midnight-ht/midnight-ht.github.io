Why revoke the new refresh token when the old one is already invalid?

Separate old-token rejection from active-token revocation with a three-step state exercise, including concurrent refresh, lost responses and access-token limits.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-08 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • Rotation retains the grant relationship; reuse detection cannot identify which party is the attacker.
  • Concurrency and an unknown refresh outcome can make legitimate clients reuse an old value.
  • Revoking refresh capability and invalidating existing access tokens require separate checks.

Refresh-token rotation does more than replace a string. When an old value is reused, the server cannot identify which party reused it, so it must deal with the active refresh token under that grant. Rejecting only the old value may leave refresh capability with whichever party obtained the new value first.

Rejecting a value and ending refresh capability are separate actions

RFC 9700’s refresh-token section describes the tradeoff: issue a new refresh token for each refresh, invalidate the old one and retain their relationship. If an attacker and the legitimate client both use a stolen token, one eventually presents an invalidated value. The server detects reuse but cannot identify the attacker from that event, so it revokes the active refresh token. The legitimate client must obtain a fresh grant too. This discussion uses the RFC published in January 2025; no real identity provider was exercised.

Suppose the attacker uses the old value first and obtains its successor. The legitimate client then presents the old value. Merely returning “invalid token” can leave the attacker’s successor usable. Rejecting an incorrect request has not necessarily stopped the compromised refresh chain. If the legitimate client wins the race and the attacker reuses the old value afterward, the same response applies. The server observes relationships and token state, not proof that the first arrival was legitimate.

Keeping only the current value and discarding every predecessor is therefore insufficient for this explanation. An invalidated value must remain attributable to its grant so the server can determine which active token to revoke. Storage need not be a table of plaintext tokens: the RFC allows grant information to be encoded in an integrity-protected token. Leakage protection, concurrency and retention still need design decisions. The table below is not a complete credential-storage design.

Check one grant with three submissions

This is an unexecuted state exercise. F1, R0 and R1 are teaching identifiers, not credentials. The server uses rotation, and each transition completes before the next step. Access-token contents, signature algorithms and exact HTTP status codes are outside the table.

Step Submitted value and starting state Independent expectation
One R0; F1 currently uses R0 Accept, issue R1, invalidate R0 and retain the relationship
Two R0 again; F1 currently uses R1 Reject R0, detect reuse and revoke active refresh token R1
Three R1; F1 is revoked Reject refresh and require fresh authorization under the service contract

These expectations come from the protocol before implementation or execution. An error response at step two is insufficient: an authorized isolated inspection should verify active-token state, and step three should establish that R1 cannot refresh again. Use an isolated identity and grant. Reports should keep anonymous correlation identifiers, steps and outcomes rather than token contents. No requests, state inspections or passing results are claimed here.

A useful negative case is a rejected R0 at step two followed by a successful R1 refresh at step three. Invalid-value rejection exists, but the active-token response to reuse does not satisfy this rotation contract. Another failure is revoking F1 for every unknown string. That could attribute unrelated invalid input to the current grant. Add a value that never belonged to F1 and verify that it does not become evidence of reuse within that family.

Concurrency needs separate treatment. If two requests both read “R0 is active” and then issue different successors, a sequential table cannot establish correctness. A transaction, conditional update or another arbitration mechanism must govern use of the predecessor and make the outcome explainable. No concurrency-safe implementation is provided here, and no particular database lock is prescribed by the RFC. The acceptance goal is a successor relationship consistent with the chosen contract.

Legitimate clients can also submit an old value

Two browser requests can independently discover an expired access token and initiate refresh. One response saves R1 while the other request still carries R0. That does not establish theft; legitimate concurrency has produced the same input as reuse. A client can share one in-flight refresh operation among waiting callers and save the new access and refresh tokens consistently. Check whether tabs, processes or devices share a credential before treating a lock inside one function as a complete answer.

Client serialization does not excuse omitting server-side reuse detection. An attacker will not honor the client’s lock. Conversely, accepting old values indiscriminately to hide concurrent sign-outs changes leakage detection. If a provider documents a grace or recovery policy, test its actual conditions. A general explanation cannot assign an arbitrary grace period to every provider.

Can a client retry the old token after losing a refresh response?

Not unconditionally. The server may already have rotated it; follow the provider’s documented recovery contract for the unknown result, or reuse may revoke the active token and require a fresh grant. A timeout establishes that the client lacks the result, not that the token endpoint made no change.

The additional issue is recovery and save order. If R0 became R1 but the response was lost, the client still holds R0 and cannot derive R1 reliably. Preserve the unknown outcome and use a supported recovery or fresh authorization path rather than retrying forever. The discussion of request retries and business idempotency explains why unknown results need a contract. It does not imply that an OAuth endpoint implements that article’s application idempotency design.

Rotation is one method, with a limited scope

RFC 9700 requires sender-constrained refresh tokens or rotation for detecting refresh-token replay by malicious actors for public clients. It does not prescribe rotation as the only choice. Sender constraints require appropriate cryptographic material associated with a client instance and have deployment and recovery costs. A public client cannot supply that constraint merely by submitting its client identifier. PKCE and API authorization address adjacent stages rather than replacing refresh-token handling.

Existing access tokens also need separate checks. Revoking refresh capability does not immediately withdraw every previously issued access token across all token formats, caches and resource servers. Expiration, introspection and revocation propagation have their own contracts. Password changes or logout at the authorization server may justify automatic refresh-token revocation; the RFC’s permission is not evidence that every provider implements it. Record the actual policy, then verify old-value rejection, reuse detection, active-token revocation and subsequent resource access separately.
