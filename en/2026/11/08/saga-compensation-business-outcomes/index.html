Record Saga compensation outcomes beyond the failure arrow

Define uncertain compensation, authoritative lookup and manual intervention through Saga traces involving a confirmed reservation, rejected payment and timed-out release.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-08 · Estimated read 18 min
Translations
zh-CN en

Article

Key takeaways

  • A later failure does not undo earlier committed actions.
  • A compensation timeout remains unknown until authoritative confirmation.
  • Irreversible actions need business corrections rather than a generic inverse operation.

Saga compensation can fail or remain unknown. A failure arrow does not establish that an earlier committed reservation was released. Completion needs an authoritative outcome for each business action, rather than the orchestrator's final exception alone.

Suppose order O-17 obtains reservation R-8 and the payment step subsequently returns a definite rejection. The orchestrator must address that reservation, but it must not invent a refund for a rejected charge. If release times out, the order cannot immediately be labeled fully reversed. This article uses AWS's Saga orchestration guidance to explain the pattern, then proposes an explicit outcome contract. No AWS, inventory or payment service was called.

A later exception does not erase earlier commits

The AWS Saga orchestration guide describes a coordinator organizing local transactions and compensating transactions after a later failure. Participants need idempotency so execution can repeat after crashes or orchestrator failures. Compensation is a subsequent business action, rather than a way to place every service inside one database rollback.

For inventory, “restore the old stock number” is dangerous. Another order may have legitimately reserved inventory after R-8 was created. Writing an earlier total back can overwrite that change. A more appropriate contract releases the specific reservation and prevents repeated release of that identity from increasing availability twice. The inventory service needs its own transactions and constraints to implement this; they are not implemented here.

The same guidance says Saga lacks transaction isolation and lists semantic locking as a consideration. That must not become a vague claim that one global orchestrator lock solves the problem. Services must agree which operations are permitted while an order is reserved or canceling. A state check at one entry point does not protect another entry point that can still dispatch inventory.

Preserve compensation uncertainty as a state

This example uses pending, reserved, compensating, compensation_unknown and compensated. They are an editorial teaching contract, not AWS standard enumerations. Reserved means the specific reservation was confirmed. A definite payment rejection creates release responsibility. A release timeout remains unknown. An authoritative lookup confirming that R-8 was released permits compensation completion.

There are separate exits for other outcomes. Confirmed payment reaches completed. A release error that cannot be handled automatically reaches manual_review with the reservation identity and an owner; it does not loop forever. A payment timeout reaches charge_unknown, not rejected. A client timeout alone justifies neither inventing a refund nor initiating another charge.

This complete Python 3 file evaluates supplied outcomes without sending commands or implementing a service idempotency store. Five independent traces cover uncertain compensation, lookup-confirmed release, manual handling, normal completion and unknown payment. Expected states are written independently. A printed state would not be a real service receipt.

"""Unexecuted local contract reducer. No services, AWS or payment calls.
Events describe already established outcomes; timeout does not establish rejection.
Only the modeled order/reservation is owned. This is not an idempotency store.
"""
def reduce_trace(trace):
    reservation, state = None, 'pending'
    for event, identity, outcome in trace:
        if event == 'reserve' and outcome == 'confirmed' and state == 'pending':
            reservation, state = identity, 'reserved'
        elif event == 'charge' and state == 'reserved':
            state = {'confirmed': 'completed', 'rejected': 'compensating',
                     'timeout': 'charge_unknown'}[outcome]
        elif event == 'release' and identity == reservation and state == 'compensating':
            state = {'released': 'compensated', 'timeout': 'compensation_unknown',
                     'permanent_error': 'manual_review'}[outcome]
        elif event == 'lookup_reservation' and identity == reservation and state == 'compensation_unknown':
            state = {'released': 'compensated', 'held': 'compensating'}[outcome]
        else:
            raise ValueError('Outside modeled contract; do not invent a result')
    return state

prefix = [('reserve', 'R-8', 'confirmed'), ('charge', 'P-9', 'rejected')]
cases = [
 prefix + [('release', 'R-8', 'timeout')],
 prefix + [('release', 'R-8', 'timeout'), ('lookup_reservation', 'R-8', 'released')],
 prefix + [('release', 'R-8', 'permanent_error')],
 [('reserve', 'R-8', 'confirmed'), ('charge', 'P-9', 'confirmed')],
 [('reserve', 'R-8', 'confirmed'), ('charge', 'P-9', 'timeout')],
]
expected = ['compensation_unknown', 'compensated', 'manual_review',
            'completed', 'charge_unknown']
if __name__ == '__main__':
    assert [reduce_trace(trace) for trace in cases] == expected
    print(expected)

The first trace stops after release timeout and must retain compensation_unknown. The second adds an authoritative released result before becoming compensated. The third reaches manual intervention without establishing that inventory was restored. The fourth confirms payment normally. The fifth stops at charge_unknown; its later payment-lookup protocol is outside the function.

Lookup semantics matter too. “R-8 not found” can mean a wrong tenant, archival or a reservation that never existed. It does not automatically certify release. The business service should expose an understandable authoritative outcome or audit evidence and define permission and retention. This is an additional proposed contract requirement, not a claim that AWS specifies these fields.

Choose Saga only when the boundaries warrant it

If order and inventory rules can be handled reliably in one local database transaction, splitting services just to use a pattern may add unnecessary work. Existing independent stores and lifecycles, together with meaningful compensation, can justify evaluating orchestration. Include retries, ownership and isolation costs. Saga is not a switch that supplies local atomicity, cross-service isolation and arbitrary reversibility at once.

The transactional outbox article addresses a local commit and delivery intent. An outbox can help send the next action without defining how to compensate a reservation that already succeeded. The transaction-isolation article concerns concurrent decisions within a database. Its isolation level does not reverse an external action. These mechanisms can support an implementation without answering the compensation-completion question for it.

Operational records should connect order identity, original action, compensating action, attempts and confirmed outcomes. Recovery workers need to distinguish confirmed actions from commands merely sent and outcomes awaiting lookup. One final error string cannot explain whether to retry release, query payment or hand the case to an operator. This makes the guide's observability and repeat-execution considerations actionable.

Should compensation delete a notification that was already sent?

Do not assume a sent notification is reversible. Define a correction correlated with the original order and message, or defer the irreversible action until the business can accept it. Deleting a local sending record cannot make the recipient unsee the content or establish an external retraction.

Other irreversible actions define similar boundaries. Shipment can require a return process rather than a generic inverse method. A human decision can require an audited correction. Decide whether compensation is possible and what it means before implementation; eventual consistency is not an answer to those questions. The API idempotency guide addresses repeated intent, but idempotency does not make an irreversible action reversible.

The proposed acceptance exercise interrupts execution after each confirmed step, retains authoritative state and checks that recovery assumes responsibility only for the associated action. Releasing R-8 repeatedly must not affect another reservation. Release timeout cannot become success. Unknown payment needs a query route, while permanent errors need an accountable handoff. Neither the code nor its five expected results was executed. They do not establish compliance by any actual service, payment provider or orchestration deployment.
