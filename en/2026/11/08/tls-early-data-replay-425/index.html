Connect HTTP 425 to business side effects before enabling TLS 0-RTT

Connect TLS early-data rejection, HTTP 425 retry conditions and independent business-state readings. The POST ledger is an isolated negative rejection test.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-08 · Estimated read 15 min

Article

Key takeaways

  • Encryption of early data does not establish application-level non-replayability.
  • A 425 retry must leave early data, and rejection must precede business side effects.
  • End-to-end validation needs trusted intermediary facts and persistent outcomes, beyond a manually supplied field.

A server can reject early requests with 425 when replay risk is unacceptable. A retry must leave the early-data path, and rejection must precede business side effects. Enabling TLS 1.3 0-RTT requires checking handshake state, intermediary signals and business outcomes together, alongside encryption.

Encrypted requests can still be reused

TLS 1.3’s replay section explains the distinct replay risks of early data. An attacker may copy it to another receiving instance without decrypting the body. Client retries and differences among nodes can also combine into duplicate processing. The RFC requires clients to send only early data they consider safe to replay and requires server defenses. This discussion uses RFC 8446, published in August 2018; no real TLS traffic was captured, copied or sent.

Certificate checks remain necessary. Certificates, encryption, integrity and whether early application work happens once answer different questions. An unchanged request may still arrive again. A node remembering a handshake does not establish that other nodes share the record. The TLS diagnostic verification article addresses chains, names and exit results; this article concerns replay acceptance across handshake stages.

RFC 8446 also notes that operations considered idempotent can still cause trouble under large numbers of replays. A read-only report may create no orders yet repeatedly consume query capacity. Deduplicating writes does not make an unlimited number of early replays acceptable. Node count, ticket-state sharing and application cost need deployment-specific assessment. A protocol name cannot determine a universal enablement percentage.

A 425 decision must precede business processing

The HTTP early-data specification defines 425 as a refusal to risk processing a potentially replayed request. A client using early data must retry after this response, and the retry must not use early data again. This is not a generic timeout code or a statement that business processing already finished.

If a handler decrements an allowance and then returns 425, a compliant retry may decrement it again. The status looks correct while the ordering defeats the design. Before business work, distinguish two cases. Early data on the currently receiving connection can be delayed until that connection’s handshake completes under the specification. A request carrying Early-Data: 1, however, was early data on a previous hop; waiting for the origin hop cannot make it safe. Section 5.1 of the same RFC 8470 requires a marked request that cannot be safely processed to be rejected with 425. Check where this decision belongs in the gateway/origin arrangement. A log saying “early request rejected” does not establish that rejection preceded the write.

The specification also constrains when 425 is appropriate. A server cannot assume every client understands the retry contract; it should generally use the response when the request arrived in early data or carries Early-Data: 1. Intermediaries must preserve relevant facts. A field supplied arbitrarily by an Internet client does not prove that a gateway observed early data, and it must not directly determine business authorization.

A negative test ledger for the rejection policy

This is an unexecuted isolated test plan. The tester controls a teaching gateway and a counter resource, confirming that ingress actually used early data. Alternatively, a handler unit test can inject a trusted early-data state through a controlled interface. That alternative tests handler policy, not end-to-end TLS. The counter starts at zero and represents no real transaction.

The POST below is a negative injection for a server rejection test. It is not advice for an ordinary client to send unsafe methods in early data without other information. The client requirements in section 4 of the same RFC 8470 permit safe methods in the absence of other information and prohibit unsafe or unknown-safety methods in that situation. Constructing a protocol test needs authorized isolated tooling and explicit additional conditions; it is not a production client default.

These values follow from the contract that only the second row may enter the write. They are not logs. After each row, read persistent state independently and retain the response and input identity. A counter of one after the first row exposes a defect even if a later final total happens to look correct. Repeat groups with isolated resources so leftovers cannot make an incorrect implementation match another row’s expectation.

An intentionally faulty handler can move the update before the early-state decision. The first row should immediately expose the side effect. This checks whether the test detects incorrect ordering; it is not an exercise in attacking a live service. Without tool receipts, gateway negotiation evidence and resource readings, execution remains unperformed.

What if the intermediary does not preserve early-data state?

An origin cannot infer the browser-to-edge handshake from its own connection alone. Even if the edge finishes its handshake before forwarding, the request may already have been accepted as early data. Identify which trusted node knows this fact, how it reaches the decision point and how client-supplied fields with the same name are handled. Adding a string field does not establish a trust chain.

Validation should correlate ingress negotiation, intermediary hops, origin decisions, the client’s retry stage and persistent outcomes. An origin-only 425 may test no more than a manually supplied field. A final client success may hide a write before the first rejection. If the gateway disables early data entirely, verify that the setting applies to this hostname and ingress rather than another configuration file.

Is allowing only GET enough?

Check actual endpoint semantics and cost as well. A GET that writes state already violates the safe-method contract; an expensive read can still amplify resource use when replayed. Evaluate the actual operation’s repeated effects and cost alongside its method.

This does not require deduplicating every access-log entry. Repeated diagnostic entries and duplicate orders have different consequences. Define business side effects and tolerable extra work before choosing a policy. A post-handshake retry can still encounter an unknown outcome after a network failure, so the application’s idempotency and query contract remains necessary.

A cautious starting point is to disable early data on intolerant endpoints and assess specific eligible reads separately. Waiting concerns the currently receiving early-data connection; a prior-hop marked request that cannot be processed safely must be rejected, rather than made acceptable by waiting at the origin. A successful connection or one 425 screenshot cannot establish the entire chain’s safety. The deliverable here is acceptance conditions, independent outcome expectations and an observation plan, without a gateway rollout, client compatibility or fault-injection pass.
