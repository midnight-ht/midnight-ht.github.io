Why does nth-child striping break after rows are hidden?

Hidden rows can remain in structural indexing. A complete four-row fixture compares external filtering with nth-child’s of subset, including exact memberships, state changes and unsupported syntax.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-08 · Estimated read 16 min
Translations
zh-CN en

Article

Key takeaways

  • External filtering does not redefine nth-child indexing.
  • The of clause applies an explicit selector rather than all visibility states.
  • Verify matched identities and the unsupported-syntax branch separately.

Hiding a row changes layout without automatically removing it from sibling indexing. Striping the retained records requires defining the set being counted. A condition outside nth-child and the same condition inside its of clause can select different elements.

The Selectors Level 4 definition indexes matching element siblings from one; without an of selector, all element siblings are considered. The retrieved document is the Working Draft dated January 22, 2026. A specification definition and support in a target browser are separate evidence.

Hidden does not mean absent from structural indexing

Suppose a table has four records and the second carries hidden. The displayed records are the first, third and fourth, but their full sibling positions remain one, three and four. Odd-position striping selects the first and third, giving adjacent displayed rows the same background.

The problem need not be an overridden color declaration. Check membership before checking which declaration wins. The cascade-layer article concerns competing matched declarations; adding specificity cannot change the siblings nth-child counts.

nth-of-type does not understand business membership either. Data rows, hidden rows and notice rows that are all tr remain in the same type sequence. Type indexing can help with mixed tag names, but it does not mean “retained records only.”

Index then filter, or filter then index

With tr:not([hidden]):nth-child(odd), oddness still refers to the full element-sibling sequence. The other conditions then require the element to be an unhidden tr. With :nth-child(odd of :not([hidden])), indexing happens within the subset lacking hidden. The source explains that selectors of these forms can have equal specificity but different membership.

This is an attribute contract, not a universal visibility test. A row hidden elsewhere by display, occlusion or opacity still matches not([hidden]) if the attribute is absent. Use the application’s explicit filtering state in the indexed subset, or derive striping from filtered data.

This complete HTML remains unexecuted. It names all four rows, checks syntax support before issuing the of query, and reports unsupported syntax without executing the unsupported query in the fallback branch. No browser screenshot or performance result is claimed.

<!doctype html>
<meta charset="utf-8"><title>Filtered row indexing</title>
<style>
[hidden] { display: none !important; }
@supports selector(:nth-child(odd of :not([hidden]))) {
  #rows > :nth-child(odd of :not([hidden])) { background: #e0e7ff; }
}
</style>
<table><tbody id="rows">
<tr id="r1"><td>One</td></tr>
<tr id="r2" hidden><td>Two</td></tr>
<tr id="r3"><td>Three</td></tr>
<tr id="r4"><td>Four</td></tr>
</tbody></table><pre id="out"></pre>
<script>
const rows = document.getElementById('rows');
const ids = selector => [...rows.querySelectorAll(selector)].map(n => n.id);
const report = {outside: ids(':scope > tr:not([hidden]):nth-child(odd)')};
if (CSS.supports('selector(:nth-child(odd of :not([hidden])))')) {
  report.inside = ids(':scope > :nth-child(odd of :not([hidden]))');
} else {
  report.inside = 'syntax unsupported; no DOM query attempted';
}
document.getElementById('out').textContent = JSON.stringify(report, null, 2);
</script>

Derive the independent oracle from the written sequence. The odd elements of r1,r2,r3,r4 are r1,r3. After excluding hidden, the sequence is r1,r3,r4, whose odd elements are r1,r4. outside should return the former; inside should return the latter when supported. The oracle does not rely on a screenshot or feed query output back into the same query.

Which result needs refreshing after an attribute change?

Removing hidden from r2 makes both selectors match r1,r3. Hiding it again makes a new of query return r1,r4. CSS follows current matching. The DOM definition of querySelectorAll specifies a static result, so a previously saved result retains its original membership.

The collection-membership article explains that observation boundary. Here ids issues a fresh query each time. A cached NodeList cannot establish current striping membership after attributes change.

Whitespace text between rows should not alter element-sibling indexing. Adding a notice tr can. Without a hidden attribute, that notice also enters the fixture’s of subset. If only business records should count, refine the explicit membership condition rather than equating “not hidden” with “record.”

Why test deletion separately from hiding?

If r2 is removed rather than hidden, the full sibling sequence becomes r1,r3,r4. Default odd indexing then also matches r1,r4. The displayed content can look identical while the structural contract differs. A deletion-only test therefore cannot establish behavior for filtering that retains hidden nodes.

Also check an empty result and a single retained row. The empty subset has no stripe target. A sole retained row is position one within the subset even if it was originally the fourth row, so it is odd after filtering. This catches renderer fallback classes that accidentally retain original positions. These are structural expectations, not executed page observations.

Can records alternate separately when notice rows are also tr elements?

Yes, but include explicit business-record membership inside the of subset rather than merely excluding hidden. Consider a separate, unexecuted input: all five elements below are direct tr children of a container named mixed, in the listed order. record and notice are literal class names, not classifications inferred from text.

Element ID class hidden attribute
m1 record absent
note notice absent
m2 record present
m3 record absent
m4 record absent

With :nth-child(odd of :not([hidden])), the indexed sequence is m1,note,m3,m4, so the independent expected matches are m1,m3. With :nth-child(odd of .record:not([hidden])), the sequence is m1,m3,m4, giving m1,m4. The notice no longer consumes an even position among records. Scope either query to direct children of mixed so cells or other tables do not enter the result.

This adds record eligibility as a condition separate from hidden state. Not every row lacking hidden is a business record. The new input leaves the earlier four-row expectations intact and supplies no captured browser result. If notices are intentionally part of the stripe pattern, choose the broader subset instead; the tr tag does not decide that product policy.

For unsupported target browsers, the renderer can assign alternating classes after filtering the data. It then owns recalculation after insertion, sorting and pagination. Classes assigned once to the original unfiltered data will not automatically reindex when rows are hidden.

Choose CSS or renderer ownership based on support requirements and where membership state already lives. Preserve record identities for acceptance. Reordering the DOM merely to produce alternating decoration can introduce a reading-order problem. Striping should also not be the only success, failure or permission cue.

Proposed checks compare exact ID lists, then cover hidden toggles, whitespace, notice rows and unsupported syntax. The goal is agreement among membership, structural position and current observation, rather than a single attractive screenshot. These are pending browser checks, not reported execution results.
