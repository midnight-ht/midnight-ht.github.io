Why can autospec execute a real property before the test calls it?

Autospec can read real attributes while constructing a spec. A local sentinel and a narrow interface distinguish inspection, signature checks and real behavior.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-08 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • Inspecting a spec can execute a getter before business calls.
  • A narrow interface retains signature checks but still needs a real-interface check.
  • Class specs do not automatically expose fields created only by initialization.

Creating an autospec from a client instance can raise an error in a real property before the test calls a business method. The mock has not made every read passive: unittest.mock inspects the original object to construct its spec. A getter that connects, reads configuration or initializes a resource can therefore become an execution point during test preparation.

Why a replacement still reads the original

Python’s Autospeccing documentation describes recursive API restrictions and callable signature checks. Obtaining those restrictions involves accessing the spec object. Traversing attributes on the mock can also traverse the corresponding original attributes. The page checked on November 7, 2026 identifies itself as Python 3.15.2 documentation; it does not establish the reader’s installed interpreter version.

An ordinary Mock can manufacture attributes on demand, allowing tests that use an obsolete API to keep passing. Autospec narrows that acceptance set by learning the original API. Distinguish the inspection that obtains the constraints from the subsequent call to the replacement. The absence of the latter does not prove the former never ran. Lazy recursive speccing also does not promise that initial creation never reads a getter.

Suppose a client exposes connection as a property and opens a connection on its first read. A test wants only read(key), but supplies the complete initialized instance to create_autospec. Introspection can reach connection during setup. What a real connection does depends on that client. The fixture below uses a local exception sentinel instead of contacting any service.

A complete local comparison

This single-file example is unexecuted. It can be saved as autospec_probe.py in an independent directory and run with standard-library Python after recording the interpreter version. The first group deliberately supplies an unsafe instance to inspect. The second supplies a narrow interface describing read. It performs no network access, reads no secrets and constructs no production client.

from unittest.mock import create_autospec

class LiveShape:
    @property
    def connection(self):
        raise RuntimeError("inspection reached getter")

try:
    create_autospec(LiveShape(), spec_set=True)
except RuntimeError as error:
    assert str(error) == "inspection reached getter"
else:
    raise AssertionError("getter was not observed on this interpreter")

class ReadPort:
    def read(self, key):
        raise NotImplementedError

safe = create_autospec(ReadPort, instance=True, spec_set=True)
safe.read.return_value = 7
assert safe.read("item-1") == 7
try:
    safe.read()
except TypeError:
    pass
else:
    raise AssertionError("missing key was accepted")

The first group’s independent expectation is the specified RuntimeError, despite no explicit connection read or business call. Its else branch exposes differing interpreter behavior as a failure. Removing that branch would hide an unmet expectation. The fixture makes no assertion about exactly how many times the getter is accessed; that count is not the contract under test.

The second group returns the configured seven and should reject an omitted key through signature checking. Seven is a test setting, not a result from a data service. This checks an API restriction and a configured return value together. It does not establish data correctness or prove that ReadPort remains aligned with production. An integration check is still needed to detect drift between them.

Change the spec or remove autospec?

Start with the calls that the test actually needs to constrain. If the consumer uses read(key), a visible interface without inspection side effects can describe that boundary. ReadPort’s implementation is not invoked here; its name and signature supply the constraint. Whether the production dependency should adopt that interface is a separate design decision.

Disabling autospec can avoid one inspection path while also accepting more behavior from the replacement. If a test relied on it to reject obsolete method names or incorrect arguments, identify what will catch those mistakes afterward. Conversely, enabling autospec indiscriminately ignores the behavior of objects supplied as specs. Judge the visible interface, inspection safety and retained assertions together.

The same official section explains that fields created only in init may not exist on the class. A class spec avoids inspecting that particular live instance but cannot discover invisible instance fields. Possible choices include a safe explicit spec, deliberately configured attributes or a narrower dependency boundary. Initializing a production client merely to expose fields can reintroduce the action the test was trying to avoid.

Spec_set does not make dynamic fields visible either. It restricts assignment to attributes absent from the spec. Establish which fields belong to that spec before relying on its read and write restrictions. If the real client gains fields in particular runtime states, document the state represented by the test interface; one static shape does not cover the entire lifecycle.

Can catching the getter exception make inspection safe?

Broad exception handling does not substitute for safe inspection. A getter may have written a file or sent a request before raising. Suppressing the exception cannot undo those actions. Catching the precise RuntimeError in this fixture is appropriate because it is a deliberately local sentinel. For a real client, first establish what the getter did, then select an inspectable spec.

This adds a setup-failure decision rather than restating the main question: an exception does not reveal how far execution progressed. Preserve its stack, the inspected object’s type and any initialization that preceded spec creation. Avoid printing credentials held by that client. The type, attribute name and local sentinel can identify the inspection stage without exposing its stored data.

What the verification should establish

Retain the file, Python version and immediate command exit status. Check the sentinel, configured seven and missing-argument rejection separately. If the first group does not raise, preserve that output and inspect the current interpreter’s behavior. A stack from a different run cannot explain this one. Keep a separate real-interface check for the consumer so its test spec does not silently fall behind.

The patch lookup article determines which name to replace. The patch scope article addresses lifetime and restoration. This question adds another piece of evidence: what was read while constructing the replacement. Make the spec safe to inspect before depending on its signature restrictions.
