A Go parent test function can return before its test tree finishes

Distinguish parent-function return from test-tree completion with complete expected-failure and expected-success controls, including Setenv’s process-wide limit.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-08 · Estimated read 18 min
Translations

Article

Key takeaways

  • Direct Run can return when the child calls Parallel, before resource use is complete.
  • Parent Cleanup waits for the test and all children; defer follows function return.
  • Process-wide state remains shared; Setenv still excludes parallel ancestors.

A Go parent test function can return while its parallel children still await resumption. Defer follows that function boundary; parent t.Cleanup follows completion of the test and its children. Shared resources need the latter lifetime when children still use them. A returned t.Run call alone does not establish that every child has finished its work.

Function return and test completion are different boundaries

The Go specification’s defer section binds deferred calls to the surrounding function’s return, rather than a test tree managed by a framework. The inspected specification identifies language version go1.27, dated 26 May 2026. Read that language rule alongside testing’s scheduling contract; a function named Test does not automatically wait for every child before returning.

The official subtest explanation says a subtest calling Parallel suspends until its calling parent test function returns. A test itself completes only after its function returns and all subtests finish. The article was published on 3 October 2016. This discussion uses its scheduling explanation without importing unrelated historical loop-variable code. The parent function returns first and the child continues afterward, allowing the parent’s defer to close a resource too early.

The testing Run and Cleanup documentation supplies the precise waiting condition. Run blocks until its child function returns or calls Parallel. In the latter case, the child’s business assertions need not have finished. Registered cleanup functions run after the current test and all its subtests complete, in last-added, first-called order. The checked package page identifies go1.27.3, published on 20 October 2026, and warns that it is not the module’s latest version. This is not an inspection of the local toolchain.

Keep the same resource-use requirement in both controls

The complete teaching project below is unexecuted. Local atomic flags represent a resource’s closed state; no file, network connection or database is created. The two named paths share one open-resource assertion. Their only cleanup-policy difference is parent defer versus parent registration; the defer path deliberately violates the requirement and should fail. Changing its assertion to accept an already closed resource would not repair the lifecycle.

// go.mod
module example.test/cleanupdemo

go 1.19

// cleanup_test.go
package cleanupdemo

import (
    "sync/atomic"
    "testing"
)

func TestResourceLifetime(t *testing.T) {
    cases := []struct {
        name       string
        useCleanup bool
    }{
        {"defer", false},
        {"cleanup", true},
    }
    for _, tc := range cases {
        tc := tc // capture for the declared Go 1.19 language version
        t.Run(tc.name, func(parent *testing.T) {
            var closed, used atomic.Bool
            closeResource := func() {
                closed.Store(true)
            }
            if tc.useCleanup {
                parent.Cleanup(func() {
                    if !used.Load() {
                        parent.Error("child never used resource")
                    }
                    closeResource()
                })
            } else {
                defer closeResource()
            }
            parent.Run("child", func(child *testing.T) {
                child.Parallel()
                if closed.Load() {
                    child.Error("resource closed before child used it")
                }
                used.Store(true)
            })
        })
    }
}

The table names the two paths with name and useCleanup. Capturing tc before the closure preserves the intended iteration under the module’s Go 1.19 language version. The outer case callback does not call Parallel, so its Run waits for that case’s children before the next row. The inner parent.Run can return when its child calls Parallel. closeResource retains the actual atomic Store; both paths share the same open check, and the good parent cleanup still checks used.

The example needs a Go version supporting atomic.Bool. Its official type documentation marks it as added in 1.19, with false as its zero value, and says it must not be copied after first use. Each case retains its own variables without copying used atomic values. The cleanup method itself was introduced in 1.14; the example’s use of a 1.19 type does not change that API’s introduction version.

Save the files as go.mod and cleanup_test.go in one isolated directory, then run the candidate commands separately, selecting the top-level test, case and child by slash-separated patterns. No output is supplied as execution evidence. Preserve each actual command’s exit result immediately rather than substituting the success of a later directory listing. Running the whole project together should still fail because the first case is deliberately negative; that does not establish that the second case never ran.

go test -count=1 -run '^TestResourceLifetime$/^defer$/^child$' -v
go test -count=1 -run '^TestResourceLifetime$/^cleanup$/^child$' -v

The independent expectation for the first command is failure: after Parallel resumes, the child reads closed as true and reports a failed open-resource requirement. The second should pass: the child reads false and marks the resource used; parent Cleanup then checks used and closes it. Both outcomes follow from one business requirement and the scheduling rules, rather than being inferred from current output. They do not establish real connection closure, file durability or freedom from all concurrency defects.

A four-step order without sleeps

In the first case, the child pauses at Parallel and the direct Run can return. The parent reaches its end, and defer sets the closed flag. Only afterward does the child resume its read and assertion. Adding a short sleep to let the child “finish first” would obscure a lifecycle error as a machine-speed problem.

In the second case, the child pauses at the same point, but returning from the parent function does not immediately run parent Cleanup. The framework still waits for the child. After the child checks openness and sets used, cleanup begins. Checking used makes premature cleanup or a missing use step visible; merely not noticing a close is insufficient. Atomic flags avoid adding an unrelated shared-boolean data race to the illustration. They do not make arbitrary real resources safe by converting them into atomic state.

Also identify which t owns the registration. A parent resource shared by siblings cannot be assigned the lifetime of an arbitrary shorter-lived child without further reasoning. List acquisition, all users and the final use boundary before registering cleanup on the node that covers them.

Where is defer still appropriate?

Defer remains suitable for a resource whose use ends with its function. Another valid structure places parallel children inside a group subtest that does not itself call Parallel. The official example’s outer Run waits for those descendants before returning, allowing teardown outside the group. That differs from directly running a child that calls Parallel. Neither case supports an unconditional slogan that Run always waits.

For a genuinely parent-owned resource, parent Cleanup often expresses the intended lifetime directly without requiring readers to reconstruct a grouping premise. It controls timing, not external deletion, authorization or duplicate-close contracts. The discussion of setup failure before yield covers a different interval: a resource exists before cleanup responsibility is established. Here both already exist, but the parent function’s lifetime is shorter than its parallel child’s use.

Does registering cleanup permit t.Setenv in a parallel test?

No. Setenv affects the whole process and is prohibited in parallel tests or tests with parallel ancestors. Registered cleanup controls restoration timing, not process-global isolation; use a separate process, explicit configuration or a different parallel scope as appropriate.

This also rules out the assumption that eventual restoration makes concurrent mutations harmless. Before restoration, two users may still read the same process state. A correct teardown does not eliminate interference during use. Nesting another function does not remove a parallel ancestor; inspect the actual test tree. Fixture isolation relates to lifetime but needs a distinct state-sharing check.

Acceptance should retain the toolchain version, module file, complete source, both isolated commands and actual exit results. Real-resource integration additionally needs acquisition, usage, close-error and residual-state checks. A passing atomic-flag fixture cannot establish successful business-resource cleanup. This project has not been compiled or run; its deliverable is an expected-failure example, an expected-success control and the scheduling explanation that distinguishes them.
