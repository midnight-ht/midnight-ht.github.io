RabbitMQ acknowledged the publish. Why is the queue empty?

Separate unroutable returns, publisher confirms and unknown outcomes under RabbitMQ 4.1 AMQP 0-9-1, using complete local traces that preserve a return after a later ACK.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-08 · Estimated read 16 min
Translations
zh-CN en

Article

Key takeaways

  • An unroutable publish can still receive a broker confirm.
  • A later ACK must not erase a correlated return.
  • Publishing, routing and consumer completion need separate evidence.

RabbitMQ can confirm a publish even when no queue matches it. If an ACK arrives but the expected message is absent, inspect routing before treating the acknowledgement as proof of queue storage or consumer completion.

Consider an order event sent to an existing direct exchange with a misspelled routing key. The publisher waits for a confirm and marks its outbox record delivered. There need not be a network error: the broker handled the publication but found no destination queue. This discussion uses RabbitMQ 4.1 documentation for AMQP 0-9-1. Its minimal case has no alternate exchange. No broker was connected and no messages were published.

An unroutable publish can still be confirmed

The RabbitMQ 4.1 confirmation-timing reference distinguishes routable and unroutable messages. An exchange can confirm after determining that no queue matches. For a mandatory publish, basic.return is sent before basic.ack; the return also precedes a negative acknowledgement.

An ACK alone therefore cannot establish that a matching queue exists. In this branch it follows the exchange's routing decision. For a routable message, the reference says confirmation follows acceptance by all destination queues, with additional conditions for persistent messages, durable queues and quorum queues. Keep those conditions attached to the claim rather than translating ACK into an unconditional retention promise.

Mandatory publishing exposes the missing route. The versioned publisher guide explains that the default false setting lets an unroutable message be discarded or sent to a configured alternate exchange. With true, the message is returned, and the publisher needs a return handler. Setting the flag without retaining return events can leave the application's log with only a positive confirm.

Excluding alternate exchanges makes the example unambiguous. In a real deployment, inspect fallback routing too. A catch-all queue may satisfy an operational policy without satisfying delivery to the order-processing queue. The business contract must decide whether that outcome completes the handoff.

Do not let a later ACK erase a return

A publish record needs distinct broker-rejected, returned and unknown outcomes. Retain channel identity and publication sequence for confirms, and a stable message_id for returned content. A sequence number reused after reconnection cannot by itself connect an old channel's confirm to a new attempt.

This complete Python 3 example has not been executed. It classifies explicitly supplied contract traces; it is not an AMQP client. It assumes one channel and one publication in flight. The ACK and return inputs are teaching data, not observed broker receipts. A real adapter still needs client callbacks, connection handling and durable records.

"""Unexecuted local contract fixture. No AMQP connection or broker simulation.
Single channel, one publication in flight; returns correlated by message_id.
ACK correlation is channel+sequence; real asynchronous client needs full adapter.
"""
def classify(message_id, publish_key, events):
    acked = returned = False
    for kind, key in events:
        if kind == 'return' and key == message_id:
            returned = True
        elif kind == 'ack' and key == publish_key:
            acked = True
        elif kind == 'nack' and key == publish_key:
            return 'broker_rejected'
        elif kind == 'disconnect':
            break
    if returned:
        return 'returned_unroutable'
    return 'broker_accepted_no_return' if acked else 'outcome_unknown'

cases = [
    ('p1', ('ch1', 1), [('ack', ('ch1', 1))]),
    ('p2', ('ch1', 2), [('return', 'p2'), ('ack', ('ch1', 2))]),
    ('p3', ('ch1', 3), [('disconnect', None)]),
]
# Independently specified oracle. None certifies consumer completion.
expected = ['broker_accepted_no_return', 'returned_unroutable', 'outcome_unknown']
if __name__ == '__main__':
    actual = [classify(*c) for c in cases]
    assert actual == expected
    print(actual)

The first trace contains a matching ACK without a return, so it records broker acceptance without return evidence. It does not establish consumer completion. The second returns before being ACKed and must remain unroutable; the final event's name cannot overwrite the earlier fact. The third disconnects before confirmation and remains unknown. Unknown is different from rejected: the broker might have accepted the message while its receipt was lost.

These expected values are supplied independently of the classifier. They follow the documented routable-acceptance and return-before-confirm branches, plus the inability of a disconnect to establish acceptance. The outbox worker can use those separate outcomes to repair topology, investigate or retry. Treating every unsuccessful attempt as the same network failure loses that choice.

The concurrency responsibilities omitted here

Real publishers often have multiple messages in flight. A confirm with multiple can cover all relevant sequence numbers through its tag on one channel. Confirms for different publications need not arrive in publication order. The official reference documents both conditions. “The third confirmation received” therefore cannot mean “the third message completed,” and one global integer table cannot safely associate attempts across channels.

The teaching classifier handles neither multiple confirms nor concurrent callbacks after reconnect. Extending it requires an outstanding-sequence set scoped to a channel, range updates for the appropriate attempts, and preservation of each correlated return. Advancing a single maximum-success number must not discard unexplained publications. Those are implementation responsibilities, not capabilities claimed for the example.

Keep business-event identity separate from sending-attempt identity. Resending an event on a new connection creates a new channel sequence without necessarily creating a new event. The October 21, 2026 article on CloudEvents identity and deduplication covers recognizing redelivery at the receiver. Routing evidence does not replace that protection, and an unknown publish is not a reason to generate a fresh business identity automatically.

Will mandatory return a message merely because no consumer is online?

No. A message can route to an existing queue without an online consumer. Consumer availability is a separate condition. A requirement to know that an order was processed needs a consumer-side or business-result protocol; mandatory is not an online-consumer probe.

The official separation between publisher confirms and consumer acknowledgements says these mechanisms are orthogonal and unaware of each other. A publisher ACK can help finish a sending attempt without carrying an inventory or order outcome. User-facing states such as accepted, sent and processed must come from their respective authorities.

A proposed integration check uses an isolated RabbitMQ 4.1 environment, an existing exchange, and two routing keys: one with a matching binding and one without. Register a return handler, enable confirms, publish each case and retain message identity, channel sequence, returned content and event order. Require the unroutable result to survive the later confirm. Then retain the queue but stop its consumers to observe the difference between publishing and processing. Publishing to a nonexistent exchange is a channel-error case and should not be substituted for the no-binding case.

Also disconnect before confirmation and check whether the application retains an unknown outcome and a recovery route. None of these tests was performed; there is no compatibility or delivery-rate claim. When applying this to the transactional outbox handoff, assign evidence to each sending outcome before updating the record. A single ACK boolean can conceal a routing failure that the protocol already made observable.
