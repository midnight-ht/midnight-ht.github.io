Why does another listener on the same button survive stopPropagation?

The current same-target listener sequence differs from later propagation. Three expected custom-event traces separate immediate stopping, cancellation and completed side effects.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-08 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • Distinguish the current listener sequence from later-target delivery.
  • Immediate stopping cannot undo earlier side effects.
  • Synthetic traces do not establish real-input or default-action behavior.

Two noncapture listeners can run on the same button even when the first stops propagation. Separate the current listener sequence from later targets before choosing what to suppress. This propagation control does not mean that every remaining piece of event-related code stops, and it cannot undo an action that already completed.

The DOM Living Standard’s event algorithms specify that stopPropagation sets a propagation flag; stopImmediatePropagation additionally sets an immediate flag. The checked standard was updated on November 4, 2026. This discussion concerns native DOM dispatch, not an assumed equivalence with a framework’s synthetic event layer.

The current sequence differs from the next target

Suppose a component installs a handler on a button, the page installs a second handler on that same button, and a parent container delegates events. The component can stop later propagation to the parent without immediately ending the current ordinary listener sequence. The second button listener can still run.

The inner invocation algorithm checks the immediate flag after invoking a listener and breaks the loop when it is set. That is the distinction between the two methods. Sharing an event object does not turn every callback into one reversible business action.

Registration order matters. The fixture deliberately uses two same-target noncapture listeners installed in a known order, without changing registrations during dispatch. An earlier handler can affect a later one; a later handler cannot travel backward. Capture listeners, shadow trees and registration changes require their actual invocation positions to be reconstructed separately.

The passive-listener article already separates propagation from cancellation. The added question here is which listeners on the current target still receive delivery, even when there is no default action.

Specify three independent traces

This complete HTML remains unexecuted. It dispatches a custom probe event, with no network, save operation or click default action. Each case creates a fresh event. The button is a convenient target, not evidence that script dispatch reproduces genuine user input.

<!doctype html>
<meta charset="utf-8"><title>Listener trace</title>
<div id="parent"><button id="probe" type="button">Probe</button></div>
<pre id="log"></pre>
<script>
const [container, button, output] = ['parent', 'probe', 'log'].map(
  id => document.getElementById(id));
let mode = 'none';
let trace = [];
const registrations = [
  [button, event => {
    trace.push('first');
    if (mode === 'stop') event.stopPropagation();
    if (mode === 'immediate') event.stopImmediatePropagation();
  }],
  [button, () => trace.push('second')],
  [container, () => trace.push('parent')]
];
for (const [owner, handler] of registrations) {
  owner.addEventListener('probe', handler);
}
const rows = [];
for (mode of ['none', 'stop', 'immediate']) {
  trace = [];
  const event = new Event('probe', {bubbles: true, cancelable: true});
  const returned = button.dispatchEvent(event);
  rows.push({mode, trace: [...trace], returned,
    canceled: event.defaultPrevented});
}
output.textContent = JSON.stringify(rows, null, 2);
</script>

The independent expected traces are first/second/parent for none, first/second for stop, and first for immediate. All three calls should return true and leave defaultPrevented false. These are specification-based expectations, not captured output.

The dispatchEvent return contract concerns cancellation rather than the number of listeners reached. A true return does not establish that the parent ran; an absent parent callback does not establish default-action cancellation. This fixture deliberately makes no cancellation call.

Distinguish duplicate observation from duplicate action ownership

Consider an unexecuted control: the first listener records analytics and the second saves. Both invocations can be necessary, and immediate stopping would suppress the intended save. If both listeners instead own the same save, duplicate action ownership is the problem. Two log entries can therefore call for opposite repairs; callback count alone cannot choose suppression strength.

The fixture makes ownership inspectable through a registration table containing each target and handler. Installation follows table order, making the two same-target entries and the parent entry explicit. The native addEventListener call remains complete and visible. Centralizing a save need not silence legitimate observation or routing; suppression still follows the intended interface protocol.

Establish action ownership before stronger suppression

A propagation boundary may fit a separate button inside a clickable card. Another option is for the parent to inspect the actual action element before routing, rather than depending on every descendant to suppress delivery. The appropriate choice depends on the component’s published event protocol and the owner of navigation.

Immediate stopping can also silence a third-party observer, accessibility interaction or cleanup handler. It does not know which callbacks matter. Duplicate API calls should prompt an investigation of registration and action ownership before stronger suppression: duplicate installation and two distinct action entry points are different problems.

A single explicit business-action entry point is often easier to reason about. An analytics observer should not accidentally save again. Stale registrations from repeated mounting need lifecycle cleanup; suppressing a later invocation does not remove the registration that should never have remained installed.

Can immediate stopping undo an ancestor capture listener that already ran?

No. It controls subsequent dispatch rather than rolling back completed calls or side effects. If an ancestor capture handler already sent a request, immediate stopping at the target does not automatically cancel that request or reverse a server commit.

This is why diagnostics should retain handler names, nodes and phases instead of only total counts. Three callbacks in a different order give suppression a different scope. Moving a handler to another phase may change the symptom while also blocking intended input handling; eligibility should be an explicit decision.

The related dispatch-lifetime discussion explains why currentTarget describes the current invocation. Record it synchronously alongside eventPhase rather than reconstructing an identity after dispatch has ended.

Proposed validation starts with the three custom traces, then checks actual registrations and real input in the target interface. Add an ancestor capture control and verify that completed work is never described as undone. No browser or device execution is reported here. Each allowed, suppressed and already completed handler should have an identifiable position and reason.
