Is a default-filled field in an old Avro event an original fact?

Compare identical old bytes under different defaults and separately encoded EUR data to distinguish reader interpretation from recorded values.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-08 · Estimated read 17 min
Translations
zh-CN en

Article

Key takeaways

  • Reader-filled values are not producer evidence.
  • Retain the original writer and pinned reader schema.
  • An existing EUR value is not replaced by a USD default.

An old event never wrote currency, yet the reader returns CNY. That value comes from a reading policy, not new historical evidence. Avro reader defaults can let a new schema read older data, but a supplied interpretation should remain distinguishable from what the producer actually recorded. Reproducible replay needs the original writer schema and a pinned reader schema and default policy.

Suppose an old payment file contains only an ID. After adding currency, a team chooses CNY as the reader default so old events can enter a report. Successful resolution does not establish that those transactions used that currency. The business needs evidence for that interpretation; a compatibility check cannot supply missing historical facts.

At which stage does the default appear?

The Schema Resolution section of the Avro 1.12.0 specification distinguishes writer and reader schemas. Record fields match by name. When the reader requires a field that the writer schema lacks, the reader uses its declared default. Without a default, resolution reports an error. This assumes matching records and compatible field types, not arbitrary schemas made compatible by defaults.

Resolution does not modify the old file. Its output depends on the old bytes, the original writer schema and the selected reader schema. Changing the reader policy can therefore change the result of reading the same historical file again. A replay receipt that names only the input file cannot fully explain the report; retain the reader schema and interpretation version too.

The October 18 article on database defaults and explicit nulls concerns values supplied during a write. This question concerns reading data that has already been encoded. The shared word default does not make the two mechanisms occur at the same stage or perform the same migration.

This complete teaching program is unexecuted. It targets the Python API in Avro 1.12.0 and needs the corresponding avro package in an isolated environment. Every schema and datum is included; it does not access an event platform, schema registry or payment record.

import io
import json
import avro.schema
from avro.io import BinaryEncoder, BinaryDecoder, DatumWriter, DatumReader


def schema(fields):
    return avro.schema.parse(json.dumps({
        "type": "record", "name": "Payment", "fields": fields
    }))


old = schema([{"name": "id", "type": "long"}])

def current(default_marker):
    field = {"name": "currency", "type": "string"}
    if default_marker is not None:
        field["default"] = default_marker
    return schema([{"name": "id", "type": "long"}, field])


def encode(writer, datum):
    output = io.BytesIO()
    DatumWriter(writer).write(datum, BinaryEncoder(output))
    return output.getvalue()


def decode(raw, writer, reader):
    return DatumReader(writer, reader).read(BinaryDecoder(io.BytesIO(raw)))


reader_cny = current("CNY")
reader_usd = current("USD")
raw_old = encode(old, {"id": 7})
assert decode(raw_old, old, reader_cny) == {"id": 7, "currency": "CNY"}
assert decode(raw_old, old, reader_usd) == {"id": 7, "currency": "USD"}

from avro.errors import SchemaResolutionException
try:
    decode(raw_old, old, current(None))
except SchemaResolutionException:
    pass
else:
    raise AssertionError("A missing reader field without default must fail")

raw_eur = encode(reader_cny, {"id": 7, "currency": "EUR"})
assert decode(raw_eur, reader_cny, reader_usd) == {"id": 7, "currency": "EUR"}
assert decode(raw_eur, reader_cny, old) == {"id": 7}

The independent oracle contains five outcomes. Old writer data resolves to CNY or USD according to the selected reader default; the same old bytes fail against a reader with no currency default. New data actually containing EUR retains EUR under the USD-default reader. The older reader ignores that new field and returns ID seven alone. These are specified expectations, not observed program output used to manufacture assertions.

Why is the current schema not a substitute for the original writer?

Binary decoding depends on the writer schema. Claiming that an old ID-only record also encoded a currency string gives the decoder the wrong layout. A reader default cannot repair a false account of what the writer encoded. Obtain the real writer schema from the container, a reliable schema identity or the actual protocol; the current application class is not the historical producer definition for every record.

Asynchronous consumption also needs a durable association between data and schemas. Upgrading the consumer today does not prove that a future replay can retrieve the writer definition. A registry can manage that association, but availability, retention and compatibility policies need separate checks. This example supplies no registry configuration and treats no compatibility label as approval of historical business meaning.

The specification permits a reader to ignore writer fields it does not contain. A new event being readable by an old consumer therefore does not mean that consumer understands currency. A legacy single-currency total can remain wrong while parsing succeeds. Check the actual output and downstream calculation, not just the absence of a consumer exception.

Does a default make an encoded field optional?

The record-field definition says a default supports reading missing fields during schema evolution. It does not make the field optional at encoding time; a field is encoded even when its value equals its default. A library may offer input-object convenience, but that does not authorize a binary record to omit arbitrary field bytes.

Keep three pieces of evidence separate: the object supplied to the writer, the writer schema, and the resulting bytes. A successful call can reflect library-side input filling rather than a universal Avro rule. Check missing inputs, explicit values and invalid types against the actual write library. The program above supplies complete write data and relies on no such convenience.

The business choice is how to interpret unknown history. It can approve a documented assumption, or represent an explicit unknown state with an appropriate schema and processing rule. Permanently rewriting old records with the true currency requires an independent fact source and a controlled migration. A reader default cannot discover the original currency or create that migration evidence.

A second negative case has an existing field with incompatible types: the writer declares currency as long while the reader requires string. Under the matching and promotion rules, a USD default cannot repair that mismatch. Expect a resolution error, neither USD nor an implicit string conversion. Encode this case separately with its real writer schema. Catching every decoding failure and substituting USD would conceal corrupted data or a wrong schema association as an ordinary historical default.

bad_writer = schema([
    {"name": "id", "type": "long"},
    {"name": "currency", "type": "long"}
])
raw_bad_type = encode(bad_writer, {"id": 7, "currency": 978})
try:
    decode(raw_bad_type, bad_writer, reader_usd)
except SchemaResolutionException:
    pass
else:
    raise AssertionError("A reader default must not repair a long/string mismatch")

Will a reader default of USD overwrite EUR already written by the writer?

No. With matching string fields of the same name and EUR actually encoded by the writer, resolution retains EUR. The specification resolves matching fields recursively and uses a reader default when the writer schema lacks the field. The separate raw_eur encoding above tests this condition. Reusing the ID-only old bytes would not test an existing writer value.

For replay acceptance, freeze input bytes, both schemas, library version and whether each expected field is original data or an approved derived value. Change the reader default and confirm that only the missing-writer-field path changes. Retain the defaultless failure and old-reader omission cases too. Readability, approval of the derived meaning and reproducible report policy should each have their own evidence.
