Why can a preview escape while its iframe still has sandbox?

An unexecuted two-file fixture compares same-origin iframe permissions, sandbox removal, navigation timing and dedicated hosting for untrusted HTML.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-08 · Estimated read 16 min
Translations
zh-CN en

Article

Key takeaways

  • allow-same-origin retains the real origin; it does not make an arbitrary site same-origin with its parent.
  • A same-origin child allowed scripts and its real origin can remove sandbox and reload.
  • Attribute changes do not establish immediate revocation or rollback of prior actions.

A same-origin child with allow-scripts and allow-same-origin can reach its iframe element, remove sandbox and reload. The attribute’s presence alone does not establish isolation from untrusted script. Assess parent and child origins, permissions and the next navigation together.

How two permissions combine into parent access

The HTML iframe specification explicitly warns that a same-origin embedded page with both keywords can remove sandbox and reload, effectively escaping it. The Living Standard checked here was last updated on 6 November 2026. That date is not a tested browser-version claim.

Without allow-same-origin, sandbox forces an opaque origin. With it, the content retains its real origin. This does not turn an arbitrary external website into the parent’s origin. A third-party page retaining its own origin generally remains cross-origin from the application; an application-hosted preview retains the same origin as its parent. Adding script execution then allows the child to use that DOM relationship to reach its container.

Counting tokens alone is insufficient, and not every iframe with allow-same-origin has this escape condition. The relevant premises are a genuinely same-origin parent and child plus executable script. Record actual schemes, hosts and ports. Moving a file under uploads or preview does not change those inputs. The Cookie Path discussion also explains why a directory is not a separate trust zone, but it does not replace this sandbox analysis.

Two local files demonstrate the proposed chain

The following fixture is unexecuted. It operates only on an iframe in self-created teaching pages, reads no user data and contacts no external website. Save both files in an isolated directory and serve them over same-origin HTTP. Do not substitute file URLs, whose origin treatment is not the experiment’s premise.

<!-- parent.html -->
<!doctype html>
<title>Sandbox parent</title>
<p id="parent-marker">parent-visible</p>
<iframe title="demo"
  sandbox="allow-scripts allow-same-origin"
  src="child.html"></iframe>

<!-- child.html -->
<!doctype html>
<title>Sandbox child</title>
<p id="result"></p>
<script>
const out = document.querySelector("#result");
let result = "";
try {
  const frame = window.frameElement;
  if (!frame) {
    result = "parent frame unavailable";
  } else if (frame.hasAttribute("sandbox")) {
    frame.removeAttribute("sandbox");
    result = "reload requested";
    location.reload();
  } else {
    result = "sandbox absent after reload";
  }
} catch (error) {
  result = "parent access blocked: " + error.name;
}
out.textContent = result;
</script>

A candidate command is python3 -m http.server 18181 --bind 127.0.0.1 in that directory. Open http://127.0.0.1:18181/parent.html in a test browser, assuming the port is available and Python’s standard library is installed. Stop this teaching server afterward. No server was started, and no screenshots or passing logs exist here. The markers are proposed observation points, not results.

For the two-token group, the independent expectation is that the child finds its container, removes the attribute and reloads, then displays the second-load marker. Inspect the actual iframe attribute from the parent document as well. A child’s claim that it escaped is insufficient. Retain navigation and console evidence to avoid confusing cached content or another process with this run.

For the second group, change only the parent attribute to allow-scripts, retain the files and HTTP origin, and reload the parent. The child has an opaque origin and cannot access the parent container as in the first group. It may receive no frameElement or encounter a blocked access. The acceptance condition is that the child does not remove the parent iframe’s sandbox, not one mandatory diagnostic string across browsers. The fixture distinguishes an unavailable container from a container with no attribute, avoiding a false escape report for a null reference.

The third control retains only allow-same-origin and reloads the parent. Script does not execute, the result paragraph stays empty and the parent container remains restricted. An empty paragraph alone does not establish why: a failed fetch or syntax error could also explain it. Check responses and browser diagnostics. Change one input per group so an observation can be attributed to permissions rather than simultaneous changes to hostnames, files and policies.

Revocation has a navigation boundary

The standard says the flags take effect when the iframe’s content navigates. Removing sandbox does not immediately change the already loaded document, which is why the fixture reloads. Deleting an attribute in developer tools without navigating cannot establish that the restriction is impossible to escape. Adding an attribute after script ran also does not undo its earlier actions.

This matters when an application reuses one iframe. If a broadly permitted document is loaded and the application then changes attributes without replacing or navigating that document, identify which navigation actually establishes the new restrictions. Determine minimal permissions before loading sensitive previews and establish a controlled document. Replacing the element, navigating again or changing the hosting origin should follow the real lifecycle, rather than accumulating tokens after a failure.

Does removing allow-scripts after load immediately stop existing scripts?

That is not guaranteed. These flags take effect when the iframe navigates; configure them before navigation and establish a controlled document again instead of treating an attribute change as proof of immediate runtime revocation.

Even replacing the old document does not undo its earlier external requests, committed writes or actions delegated to the parent. Verify those resources separately rather than treating the iframe’s disappearance as rollback. This follow-up concerns revocation timing and completed actions, adding a decision beyond the two-token escape condition.

Hosting layout establishes the trust boundary

The HTML standard recommends serving potentially hostile HTML from a separate dedicated domain. Direct access is one reason: a file opened at the top level no longer receives protection from its parent’s iframe attribute. A dedicated origin limits access to the application origin, but does not replace authorization, sanitization or cross-origin message validation. Check whether it receives inappropriate credentials or can navigate to application-origin content.

A trusted component that needs parent DOM access is already inside the parent’s trust boundary. The same configuration cannot promise isolation from malicious documents. For untrusted content, constrain origin and script capability first, then consider individual features. Enabling scripts and the real origin together to repair preview compatibility can remove the isolation premise.

Separate policies govern what the parent can load and who may embed the child. The frame-ancestors discussion addresses embedding permission, not script capability. Record actual origins, permissions before load, navigation timing, container attributes and sensitive-action outcomes. No browser run or security acceptance is claimed here. Decide whether the content is trusted code or an untrusted document, then choose origins and permissions consistent with that decision.
