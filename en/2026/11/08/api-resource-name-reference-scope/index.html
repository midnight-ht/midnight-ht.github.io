Separate resource identity from its access URL

Distinguish local IDs, relative and full resource names, and access URIs under Google AIP-122, using parent collisions, declared version mappings and caller-dependent aliases.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-08 · Estimated read 17 min
Translations
zh-CN en

Article

Key takeaways

  • A local ID needs an explicit parent and owning-API scope.
  • Resource identity and access versions or endpoints require separate contracts.
  • Resolve lookup aliases to canonical names before retaining references.

Define persistent resource references separately from the URL used to access them. A resource can be reachable through different versions or endpoints; treating each access URL as its identity can turn an endpoint migration into an apparent new object. The contract must also identify the parent and API to which a local ID belongs.

Suppose two publishers each have a book with local ID b7. A cross-project task storing only book_id=b7 needs someone to reconstruct its publisher scope. Reconstructing it incorrectly can produce a valid request for the wrong object. This discussion uses Google AIP-122 resource-naming conventions. They are a particular API design specification, not a requirement for every HTTP service. No real API was called.

Local IDs, resource names and access URIs serve different purposes

AIP-122's resource-name guidance requires resource names to be unique within an API and normally alternate collection identifiers and resource IDs. publishers/p1/books/b7 and publishers/p2/books/b7 have the same terminal segment but identify different resources. Retaining only b7 discards the scope that distinguishes them.

The field name here is not an editable display title. AIP distinguishes terms such as display_name and specifies resource-name references for existing resources. An API can separate a book's human-readable title from its machine reference, allowing a title edit without treating every reference as a different book. Moving a resource between parents needs the API's evolution contract; this simple example does not define it.

The guidance also distinguishes relative resource names from full resource names. Relative names work when the owning API is known. Where cross-API ambiguity exists, a full resource name includes the service name. An access URI additionally contains protocol, API version and a particular endpoint. Service identity and endpoint selection are related but different fields.

Do not therefore write a universal function that removes any URL's v1 segment to discover resource identity. Mapping is justified only when the service contract explicitly relates endpoints, versions and resource patterns. Unknown hosts and prefixes need an unknown or rejected outcome, rather than silently merging similar-looking strings.

Carry the scope a consumer actually needs

An AIP-style list request can use parent=publishers/p1 and return each book's name, rather than returning an unscoped book_id alone. A field referring to a shelf can hold its resource name instead of embedding an entire shelf as a permanent snapshot. Embedding also introduces lifecycle and permission relationships that saving a network call does not resolve.

Existing services need not rename every field. If a local ID already has an explicit, stable scope and consumers never pass it between parents, retaining it can be simpler. Specify which context the field carries and which context the endpoint guarantees. Do not require every consumer to remember an undocumented tuple. Explicit references become particularly useful in generic logs, task queues and cross-service fields.

This complete Python 3 file has not been executed. It declares two allowed version endpoints and recognizes only the two supplied teaching resources. It is neither a universal URL normalizer nor an authorization check. The independent expectation is that two explicitly mapped version URIs produce the same full resource name, while b7 under different parents remains distinct.

"""Unexecuted local mapping fixture, not a universal URL normalizer or auth check.
Service/endpoint/version bindings are explicitly declared and cannot be inferred.
"""
from urllib.parse import urlsplit
resource = 'publishers/p1/books/b7'
other_resource = 'publishers/p2/books/b7'
SERVICE = 'library.example'
allowed = {
 (SERVICE, '/v1/'): SERVICE,
 (SERVICE, '/v2/'): SERVICE,
}
def resolve_declared_uri(uri):
    parts = urlsplit(uri)
    if parts.scheme != 'https' or parts.query or parts.fragment or parts.username:
        raise ValueError('Not an allowed fixture URI')
    for (endpoint, prefix), service in allowed.items():
        if parts.netloc == endpoint and parts.path.startswith(prefix):
            relative = parts.path[len(prefix):]
            if relative not in {resource, other_resource}:
                raise ValueError('Unknown fixture resource')
            return '//' + service + '/' + relative
    raise ValueError('Unknown endpoint/version mapping')
uris = ['https://library.example/v1/' + resource,
        'https://library.example/v2/' + resource]
expected = '//library.example/publishers/p1/books/b7'
if __name__ == '__main__':
    assert resource != other_resource
    assert [resolve_declared_uri(u) for u in uris] == [expected, expected]
    aliases_by_caller = {'u42': {'users/me': 'users/u42'},
                         'u99': {'users/me': 'users/u99'}}
    saved = aliases_by_caller['u42']['users/me']
    assert saved == 'users/u42'
    assert saved != aliases_by_caller['u99']['users/me']
    print(expected, saved)

The allowlist supplies the semantic premise: those endpoints belong to one service and address the same resource data. The program does not discover that premise. Another API's v2 might address different data or follow another migration policy, so its URLs cannot inherit this mapping's result.

Keep both useful log fields. Access records can retain the endpoint and version actually used; business references can retain canonical resource names. Correlation then shows where a request went without turning an endpoint change into a new object. A publicly visible resource name does not grant access. The object-authorization article explains why identifier complexity and permission remain separate decisions.

Resolve a lookup alias before storing a reference

AIP-122 permits convenient aliases such as users/me but requires returned data to use canonical resource names. Me depends on the caller. In the example, u42 resolves it to users/u42, while u99 resolves it to users/u99. Persisting the alias unchanged in a shared task can consequently change its target on a later execution.

The example stores users/u42 after resolution. That is not authentication evidence: a real service still decides whether the caller may resolve and access the target. Alias resolution determines which resource, not who may perform an action.

The article on CloudEvents source and id discusses another scoped identity, an event. This article concerns persistent resource references and access URIs. A resource-naming convention is not automatically an event-deduplication algorithm, and a sending attempt does not define a resource's lifecycle.

Must a full resource name change when a service uses a regional or mTLS endpoint?

Under AIP-122, one service can expose regional, mTLS or private-access endpoints without changing the full resource name. The client still needs the endpoint mapping and its access conditions. An unfamiliar host does not establish shared identity or permission merely by resembling an existing endpoint.

For example, a business field can continue holding its canonical reference when connection configuration moves to an approved private endpoint. The actual request still needs the correct address, certificates and access rules. No private network or certificate was configured here. A naming convention cannot establish real connectivity or authorization acceptance.

Check document dates at the clause level too. The AIP header still says Updated in 2019, while its substantive changelog includes March 10, 2025, when guidance discouraging UUID user-specified IDs was removed. This article treats neither the header as the latest semantic revision nor UUIDs as forbidden. Read current full conditions before copying an older naming summary.

Proposed acceptance cases include equal local IDs under different parents, two declared version mappings producing one resource identity, canonical names returned after alias lookup and rejection of unknown endpoints. Then verify actual fields, permissions and errors with the real client and service. This is a teaching mapping with independent expected values, not an API compatibility, migration or authorization pass report.
