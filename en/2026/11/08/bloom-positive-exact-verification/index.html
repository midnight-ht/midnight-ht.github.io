Can a positive Bloom filter result reject a username?

Use expected-count tables and a deterministic collision model to decide when probabilistic positives need authoritative verification.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-08 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • False-positive rate differs from the error fraction among positives.
  • Verify positives exactly when false rejection is unacceptable.
  • A negative does not replace atomic uniqueness enforcement.

If rejecting an available name is unacceptable, a positive Bloom filter result needs an exact lookup. It means “possibly added,” not “the database proved this name is occupied.” Using a positive directly to reject registration or discard an event accepts the business cost of false positives. A small error_rate cannot make that decision on the business’s behalf.

Suppose a registration endpoint puts a filter ahead of the database to reduce reads. It immediately rejects a name after a positive response. That saves a lookup but can reject a name that has never been registered. Decide whether the rejection is acceptable before calculating resource savings. No Redis connection or latency measurement is claimed here.

Why is the error fraction among positives not the configured rate?

The BF.RESERVE command documentation defines error_rate as the desired false-positive probability and supplies a capacity argument. A false positive concerns a query for an actually absent item. The fraction of all positive responses that are wrong also depends on the prevalence of true members. The denominators differ.

Take 10,000 queries: 100 actually present and 9,900 absent. Assuming a one-percent false-positive rate among absent queries gives an expected 99 false positives. The 100 true members are positive too, so there are 199 positives. The wrong-positive fraction is 99/199, about 49.75%, rather than one percent.

Now use 9,000 present and 1,000 absent queries. The same rate gives an expected ten false positives and 9,010 positives overall. The wrong-positive fraction is 10/9,010, about 0.111%. Identical configuration can therefore produce very different confidence in a positive. These are expected-count thought experiments, not guarantees that finite samples produce those exact integers.

This complete arithmetic program has not run. Its expected values are independent literals; a sample experiment should not be mistaken for proof of the configured rate. The convenient counts are illustrative, not observed registration traffic.

from fractions import Fraction

def expected_table(present, absent, false_positive_rate):
    fp = absent * false_positive_rate
    tp = Fraction(present)
    return tp, fp, Fraction(absent) - fp, fp / (tp + fp)

assert expected_table(100, 9900, Fraction(1,100)) == (
    Fraction(100), Fraction(99), Fraction(9801), Fraction(99,199)
)
assert expected_table(9000, 1000, Fraction(1,100)) == (
    Fraction(9000), Fraction(10), Fraction(990), Fraction(1,901)
)

The official Bloom filter guide confirms that an item never added can still produce a positive. Its introductory shorthand about one wrong answer among a number of positives can obscure the denominator. Here the command’s probability definition and the explicit table govern the calculation; that shorthand is not treated as a guarantee of positive precision.

Can a deterministic collision test the rejection path?

A million random usernames are unnecessary for this counterexample. Fix two hash positions for each teaching item: stored a uses one and three; absent b uses the same positions; absent c uses two and three. This is not Redis’s hashing algorithm and predicts no collision for an actual Redis string. It supplies a deterministic false-positive input.

# Unexecuted collision illustration, not Redis internals.
hash_positions = {'a': (1,3), 'b': (1,3), 'c': (2,3)}
exact = {'a'}
bits = set()
for item in exact:
    bits.update(hash_positions[item])

def may_contain(item):
    return all(bit in bits for bit in hash_positions[item])

assert may_contain('a') is True
assert may_contain('b') is True
assert ('b' in exact) is False
assert may_contain('c') is False

The independent oracle is a positive true member, b positive but absent, and c negative and absent. A business test should make b reach the authoritative check rather than stop at the duplicate branch. Suppressing one disposable recommendation might be acceptable. Applying the same approximation to discard a new event needs a different, explicit decision.

The October 21 article on CloudEvents identity and deduplication covers deterministic identity and business commits. This question keeps the identity correct and asks whether probabilistic membership may replace an exact processing record. Losing a unique event to a false positive differs from failing to stop a duplicate.

Which path can actually avoid work?

For a filter that fully represents the authoritative set, negatives can exclude some lookups while positives receive exact verification. Savings depend on traffic composition, actual false positives and lookup cost. The count table supplies no fixed latency improvement. If most queries are true members, many still need exact checks.

An authoritative rejection should also have a clear meaning. A database can confirm that a name is occupied; an event ledger can return a prior processing result. A filter alone must not turn a positive into a business completion receipt. If the exact lookup fails, unknown is not proof of either presence or absence.

Separate the mathematical structure from synchronization. A standard intact Bloom filter does not create false negatives for inserted members through hash collisions. An application can nevertheless miss an update, query another instance or use an incomplete rebuilding filter. BF.EXISTS return information also includes a missing key among negative outcomes. A negative therefore does not unconditionally describe current database membership.

The November 8 article on Redis eviction and authoritative state examines lost keys. The false positives here exist even with intact keys and correct synchronization. Fixing durability and capacity cannot remove probabilistic membership errors; retain distinct checks for both.

Can a negative filter result replace a database uniqueness constraint?

No. A concurrent creation can occur after the check, and a missing or rebuilding filter may not cover current database members. The authoritative write still needs an atomic uniqueness constraint. A pre-check does not reserve the name.

Acceptance should separately cover present items, a forced collision, absent items, missing keys, rebuild epochs and concurrent creation, using an independent exact set as the oracle. Record false positives against absent-query count and positive precision separately. Establish the permitted consequence of each error before choosing capacity, error_rate and query optimizations. These programs and counts remain unexecuted illustrations rather than Redis runtime evidence.
