A removed set member returns: should a concurrent add win?

Trace two addition identities in a complete teaching model and distinguish shared-label convergence from revocation policy.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-08 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • Observed removal covers additions it has seen.
  • Replica convergence does not certify global revocation.
  • Distinguish the tagged teaching model from ORSWOT storage.

One offline replica removes the member it has seen while another adds it; an add-wins OR-set can retain the member after merge. Before choosing that set, decide whether a concurrent addition should defeat removal. Eventual agreement establishes convergence under the selected rule, not that a deletion globally revokes every addition.

Suppose two people manage shared labels offline. One removes team-red while the other adds it again, and synchronization brings the label back. That can be reasonable for shared organization. It can violate a different promise if membership represents permission and the interface says removal prevents future access. Start with the business meaning of the operation rather than assuming every conflict needs one latest timestamp.

Which addition did the removal observe?

The Basho riak_dt_orswot source explicitly states that a concurrent add wins against a remove. It records actor/counter dots for additions and uses version vectors to distinguish whether another replica has seen them. Absence can mean an addition has not arrived, or that it arrived and was removed. Visible membership alone cannot distinguish those causes.

Context-aware removal subtracts the dots observed by its context; merging also filters dots using the other replica’s clock. A removal is therefore not a permanent ban on a display string. It removes additions within a particular causal scope. This discussion concerns ORSWOT’s add-wins observed-remove semantics, not every CRDT set.

The Riak set documentation fetches context and sends it with removals. Real API context is opaque client data. Preserve it according to the API rather than constructing it from the a1 and b1 labels below. These historical project documents also do not establish a current production-support claim.

What do two addition identities reveal?

This unexecuted Python teaching model uses a tagged observed-remove set and explicitly retains removed tags to expose the causal relationship. It is not ORSWOT’s tombstone-less storage implementation, which represents that knowledge using dots and clocks. The model explains the relevant add-wins result and is not a production CRDT library.

# Unexecuted tagged OR-set semantics model, not ORSWOT storage.
from dataclasses import dataclass

@dataclass(frozen=True)
class State:
    adds: frozenset
    removed: frozenset

def merge(left, right):
    return State(left.adds | right.adds, left.removed | right.removed)

def visible(state):
    return {member for member, tag in state.adds - state.removed}

a1 = ('team-red', 'a1')
b1 = ('team-red', 'b1')
initial = State(frozenset({a1}), frozenset())
replica_a = State(initial.adds, frozenset({a1}))
replica_b = State(initial.adds | {b1}, frozenset())

assert visible(replica_a) == set()
assert visible(replica_b) == {'team-red'}
combined = merge(replica_a, replica_b)
assert combined.adds == frozenset({a1,b1})
assert combined.removed == frozenset({a1})
assert visible(combined) == {'team-red'}
assert merge(replica_b, replica_a) == combined
assert merge(combined, combined) == combined

removed_after_observing_both = State(combined.adds, combined.adds)
assert visible(removed_after_observing_both) == set()

The independent oracle follows the two identities. Replica A removes initial addition a1. Fresh addition b1 on B is outside A’s observations. The merged additions are a1 and b1, while only a1 is removed, so team-red remains visible. A later removal that observes both additions can make the visible set empty. One visible string does not imply only one addition occurred.

Reversing merge inputs gives the same state, and merging the result with itself leaves it unchanged. Those assertions check commutativity and idempotence for this fixture, not correctness of a complete implementation under every failure. Adoption still needs actual library tests, replica identity management, causal-context retention and persistence checks.

Why is final replica equality insufficient?

Both replicas can converge to team-red while violating a product promise of revocation. Conversely, making every deletion permanently dominate all future additions can prevent an intended label from being added again. The application must choose a concurrent outcome; the phrase “avoid conflicts” supplies no universal policy.

The October 9 discussion of conditional updates describes a different policy: reject stale writes and let the user compare again. An OR-set can accept offline operations and merge them later, but it deliberately retains concurrent additions under this rule. The availability and conflict-handling promises differ; replacing an ETag with a set name is not enough.

If revocation must immediately constrain other nodes, define authoritative revocation state, the point of enforcement, propagation delay and offline access policy. A disconnected node must have an explicit rule: refuse, defer or continue under older authority. This example designs no complete authorization system and does not recommend its teaching model for permission enforcement. It shows why convergence does not establish immediate global revocation.

The same day’s article on transaction isolation and business invariants also starts with the invariant. Here it might be “do not lose a concurrent new label” or “a banned member must not regain eligibility.” Distinguish those requirements before selecting add-wins semantics or moving some actions to a separate authority.

Give the last condition its own oracle: after observing and removing both additions, a fresh c1 should make team-red visible again, while a1 and b1 remain removed. This is acceptance of a third new operation, not restoration of an old deleted tag. Retain the creation point of c1 in the timeline. If the product must reject it, enforce the ban when accepting new operations rather than expecting the earlier removal to express every future restriction.

c1 = ('team-red', 'c1')
future = State(
    removed_after_observing_both.adds | {c1},
    removed_after_observing_both.removed
)
assert future.removed == frozenset({a1,b1})
assert visible(future) == {'team-red'}

Will deleting again after synchronization prevent every future return?

It removes the additions observed by that deletion. A later permitted add is a new operation; preventing rejoining requires a separate ban or revocation policy. The first code block’s empty-set assertion for removed_after_observing_both covers the observed a1 and b1 additions. The later block separately establishes that a fresh c1 becomes visible; neither treats one deletion as a permanent ban.

Acceptance should retain three timelines: concurrent addition, removal after observing all additions, and a new addition after deletion. Write the business oracle before checking a model or library. Real client tests also need fetched context, sent operations and merged results. No Riak cluster, Erlang test or Python program has run here. A reviewable result identifies the chosen set semantics, which additions each removal observed and which stronger revocation requirements have another enforcement mechanism.
