Why can SELECT still read old prices after a write CTE?

Use complete temporary-table SQL to compare old base values, new returned values and audit inputs, including overlapping-write limits.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-08 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • Base-table scans and returned relations differ within one statement.
  • Pass modified values through RETURNING.
  • Zero consumed rows do not prevent a write CTE.

Updating prices in a WITH clause and selecting the base table is not the same as two sequential SQL statements. PostgreSQL 18 data-modifying CTE substatements and the main query share a snapshot. To pass values produced by the modification into the rest of that statement, read its RETURNING relation. Text appearing later does not establish sequential visibility.

Suppose an admin operation adds ten to product one’s price of 100 and needs to audit the new price. The developer puts UPDATE in changed but makes the main query select the original table. It can read 100. Seeing the update succeed does not prove that the consumer selected its new value. The immediate issue is the source of data within one statement, not a rollback.

Which outputs are available within the snapshot?

Section 7.8.4 of the PostgreSQL 18 WITH documentation explains that data-modifying substatements and the main query share a snapshot and cannot see one another’s changes through their target tables. RETURNING supplies the communication path. The documentation contrasts reading the base table with reading the returned relation after a price update.

This does not mean a transaction can never read its own earlier writes. A subsequent ordinary SQL statement can see them. The scope here is one statement containing a data-modifying CTE. For consecutive statements, the October 20 article on Read Committed snapshots discusses consecutive statements; their order cannot be inferred from textual positions inside WITH.

The complete fixture below is unexecuted and intended for a disposable environment. It creates temporary state in a transaction and rolls back. There are no sequences, external functions or triggers. Two products provide affected and unaffected rows, while source labels distinguish the two values for product one.

BEGIN;
CREATE TEMP TABLE price_probe (
  id integer PRIMARY KEY,
  amount integer NOT NULL
);
INSERT INTO price_probe VALUES (1,100),(2,200);

WITH changed AS (
  UPDATE price_probe SET amount=amount+10
  WHERE id=1
  RETURNING id,amount
)
SELECT 'base' AS source,id,amount FROM price_probe WHERE id=1
UNION ALL
SELECT 'returned',id,amount FROM changed
ORDER BY source;

SELECT id,amount FROM price_probe ORDER BY id;
ROLLBACK;

The independent oracle is base, 1, 100 and returned, 1, 110 for the first result. The next SELECT should return product one at 110 and product two at 200. The first result contrasts two sources within a statement; the next checks visibility across statements. These are expected values, not observed client output.

Which data flow should feed the audit?

To save this update’s new price, an audit INSERT can consume the explicit id and amount columns from changed. Rereading price_probe is not a substitute for that result. This standalone variant is also unexecuted; run it separately in disposable state rather than appending it to the prior rolled-back setup.

BEGIN;
CREATE TEMP TABLE price_probe(id integer PRIMARY KEY, amount integer);
CREATE TEMP TABLE price_audit(id integer, new_amount integer);
INSERT INTO price_probe VALUES (1,100),(2,200);
WITH changed AS (
  UPDATE price_probe SET amount=amount+10 WHERE id=1
  RETURNING id,amount
)
INSERT INTO price_audit(id,new_amount)
SELECT id,amount FROM changed;
SELECT id,new_amount FROM price_audit ORDER BY id;
ROLLBACK;

The audit oracle contains one row: product one, new price 110. Product two must not produce an audit row. Changing the update predicate to id=99 makes changed empty, so the audit receives no input. Whether that means not found, conflict or an allowed no-op is a business decision. Do not manufacture a successful audit row from an old application object.

This establishes a value handoff within a database statement. The October 16 article on RETURNING and commit boundaries explains why returned rows do not by themselves establish that an explicit transaction committed. An audit insert also does not prove external delivery. The SQL provides no cross-system atomicity guarantee.

Can textual order sequence two changes to the same row?

The documentation says the actual update order is unpredictable, and attempting to modify the same row twice in one statement is unsupported. Avoid overlapping writes in sibling CTEs or between a CTE and the main statement. Naming them first and second makes the text easier to read without adding an execution guarantee.

If the business requires a second modification based on an earlier change, separately executed statements within an explicit transaction can make that sequence visible. Concurrency and constraints still need treatment, but the design no longer relies on unsupported same-statement duplicate modification. If one expression can calculate the final value, a single modification may be simpler.

Do not invent a fixed winner for an overlapping-write example and then treat a matching run as proof. The negative case should identify and reject the overlapping design, not search for a plan that happens to choose the desired outcome. Review each write’s target identity and predicate to find potentially intersecting row sets.

The October 21 discussion of CTE materialization covers optimization of ordinary side-effect-free SELECTs. MATERIALIZED and NOT MATERIALIZED do not turn write CTEs into an imperative script. Use the rules for data-modifying statements here.

Make the zero-consumer expectation a complete fixture. After the main query returns no rows, the next statement should still return product one at 110. Reinitialize and change only the update predicate to id=99; the next statement should retain 100. These controls distinguish no consumption from no matching target. A test driver must not skip the subsequent check merely because the first result is empty. The outcomes remain unexecuted expectations.

BEGIN;
CREATE TEMP TABLE zero_consumer(id integer PRIMARY KEY, amount integer);
INSERT INTO zero_consumer VALUES (1,100);
WITH changed AS (
  UPDATE zero_consumer SET amount=amount+10 WHERE id=1
  RETURNING id,amount
)
SELECT id,amount FROM changed WHERE false;
SELECT id,amount FROM zero_consumer ORDER BY id;
ROLLBACK;

Will the update run if the outer query never consumes changed?

Yes. A data-modifying CTE executes once to completion regardless of consumption of its returned rows. An outer LIMIT zero or zero-row result must not be treated as a guard against the internal write.

A proposed negative test initializes the price to 100, uses an UPDATE CTE and gives the main SELECT a WHERE false condition. Even with zero returned rows, the next statement should read 110. This has not been executed and belongs in an isolated database. Acceptance should retain separate oracles for the base-table source, returned relation, next statement, zero affected rows and zero consumed rows. Each check addresses a distinct misconception instead of attaching a single “transaction correct” label to the query.
