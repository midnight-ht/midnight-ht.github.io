Choose the out-of-memory outcome before mixing cache and authoritative state

Choose where Redis caches and authoritative records belong by their eviction or write-rejection consequences, with explicit allkeys, volatile and noeviction eligibility examples.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-08 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • TTL does not guarantee retention until its deadline under memory pressure.
  • Volatile policies can still select important expiring records.
  • Avoiding eviction requires handling rejected writes rather than reporting false acceptance.

Before mixing caches and sole business records in one Redis instance, decide what may disappear and which writes may fail when memory is exhausted. TTL is not a minimum-retention guarantee. Choosing noeviction does not add capacity; it changes some memory pressure into write errors.

Suppose an instance stores report caches, accepted-task records and duplicate-charge identifiers. A developer gives caches a one-minute TTL and deduplication records a one-day TTL, assuming the latter remain available for at least a day. An eviction policy that selects expiring keys invalidates that assumption. This analysis follows the current official Key eviction guide. No Redis connection, memory-pressure experiment or charge was performed.

Expiration and capacity eviction are different causes of absence

The Redis key-eviction guide explains that memory exceeding maxmemory triggers the selected eviction policy. Expiration governs what happens at a deadline; eviction selects data that can disappear earlier under capacity pressure. Correctly preserving a TTL during an update does not remove the second mechanism.

The November 5, 2026 article on SET and TTL replacement addresses commands that preserve or change a deadline. Here the TTL is assumed correct. Fixing KEEPTTL in a wrapper does not change the instance's eviction policy.

Allkeys-lru considers all keys, including a task record with no expiration. Volatile-lru selects keys with an expiration, so the one-day deduplication record remains eligible. Keeping a permanent task key outside that candidate set does not guarantee unlimited successful writes. Once that eligible set is empty, volatile policies behave like noeviction according to the guide.

Eligibility is not an exact prediction of the next victim. The documented LRU algorithm uses approximate sampling. Do not derive a fixed deletion order from three keys or claim repeated reads make an important key untouchable. First determine whether losing each class means recomputation, an authoritative lookup or loss of a unique business fact.

Check policy against three different data roles

This complete Python 3 candidate-set example has not been executed. It neither implements Redis memory accounting nor simulates LRU. TTL values indicate whether expiration exists; they do not represent time elapsed on this machine. Independent expected sets describe allkeys, volatile and noeviction eligibility.

"""Unexecuted policy eligibility illustration. No Redis connection.
It does not predict approximateLRU choice or emulate memory accounting.
"""
keys = {'cache:report': 60, 'task:accepted': None, 'dedup:charge': 86400}
def eligible(policy, key_ttls):
    if policy == 'allkeys-lru':
        return set(key_ttls)
    if policy == 'volatile-lru':
        return {k for k, ttl in key_ttls.items() if ttl is not None}
    if policy == 'noeviction':
        return set()
    raise ValueError('Unsupported teaching policy')
expected = {
 'allkeys-lru': {'cache:report', 'task:accepted', 'dedup:charge'},
 'volatile-lru': {'cache:report', 'dedup:charge'},
 'noeviction': set(),
}
if __name__ == '__main__':
    for policy, oracle in expected.items():
        assert eligible(policy, keys) == oracle
        print(policy, sorted(oracle))
    # No eligible victim does not imply successful new-data writes.

The consequences matter more than the sets. cache:report can be rebuilt from a durable source and its loss might cost another query. If task:accepted is the sole acceptance receipt, losing it can make an accepted task untraceable. If dedup:charge is the only duplicate guard, an old request arriving after its removal can be mistaken for a new intent. This charge scenario is a hypothetical risk, not an incident report about a payment system.

Volatile-lru appears to protect the permanent task key while still making the expiring deduplication record eligible. Making that record permanent creates another question: what happens when eligible candidates are exhausted and a new write fails? A name such as cache and the existence of a TTL cannot establish reconstructability. Identify the reliable source and what callers see while rebuilding.

Noeviction transfers responsibility to the write path

The guide says noeviction does not evict keys, but commands trying to cache new data return errors; commands that only read existing data continue. Applications choosing it must inspect write outcomes. Catching the error and still returning “task accepted” converts an observable capacity failure into a missing business record.

This is not a recommendation to place everything in one noeviction instance. Report caches can still compete with task acceptance for capacity. The guide suggests separate instances for caches and persistent keys where possible. That separates policy and budgets without automatically providing backups, recovery or business authority. Choose separation according to failure consequences and operational cost.

In this example, a more direct design keeps task acceptance and deduplication authority in storage meeting their commit requirements. Redis may accelerate lookups, but a miss must not independently prove that a task was never accepted or that a request is new. External operations still need their own identity and lookup contracts. The question here is specifically whether a capacity policy may remove the only record, rather than a general persistence tutorial.

Memory budgeting also needs more than the host's installed RAM. The guide explains that some replication and AOF buffers are excluded from the eviction comparison; INFO memory exposes mem_not_counted_for_evict. Maxmemory is therefore not a hard ceiling on every byte in the process. Buffer, client and environment headroom require actual observation. No unmeasured sizing percentage is supplied here.

Does an unchanged evicted_keys counter prove that a key expired?

No. Explicit deletion, replacement, a namespace mistake or querying a different instance can also explain absence. Investigate expired_keys, the actual write path and instance identity together. An aggregate cumulative counter is not a causal history for one missing key.

Start with read-only observations. These redis-cli commands were not executed and do not change a shared instance's global configuration. Supply connection settings through the authorized environment rather than putting credentials in the article or logs.

redis-cli CONFIG GET maxmemory
redis-cli CONFIG GET maxmemory-policy
redis-cli INFO memory
redis-cli INFO stats
redis-cli INFO commandstats

Record an observation window, compare eviction, expiration and command-rejection changes, and verify which instance the application actually uses. A pressure test belongs in a disposable instance with retained server version and configuration. Check reconstructable cache misses, propagation of rejected critical writes and the caller's lookup route. No such experiment was run here.

The UNLOGGED reconstructability article concerns another failure condition. This decision concerns capacity during operation: evictable keys need an acceptable absence path, and a non-evicting instance needs an understandable write-rejection path. Increasing a TTL alone cannot supply either business promise.
