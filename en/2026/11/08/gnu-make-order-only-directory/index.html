Use order-only prerequisites to create directories without invalidating files

Directory preparation and target invalidation are separate requirements. Compare complete rules while checking that real input updates still rebuild the report.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-08 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • Order-only prerequisites impose order without timestamp invalidation.
  • Keep content inputs normal so changed inputs invalidate old reports.
  • A normal declaration wins when a prerequisite appears in both classes.

An output directory must exist before a report is written, but adding an unrelated entry should not regenerate that report. GNU Make’s order-only prerequisites can express both requirements: prepare the directory first without treating its newer timestamp as a reason to rebuild. Real content inputs should remain normal prerequisites.

One dependency can make two promises

GNU Make’s prerequisite-types manual distinguishes normal prerequisites from order-only prerequisites. Normal prerequisites impose ordering and participate in freshness decisions; order-only prerequisites retain the ordering relationship. This article also checked the complete corresponding section in doc/make.texi from the official GNU Make 4.4.1 release archive. Direct retrieval of the HTML subsection returned 403, which is not source text. No installed make version is inferred here.

Suppose input.txt produces report.txt inside out. Listing both input.txt and out as normal prerequisites prepares the directory first, but a directory newer than the report can also invalidate it. Adding, removing or renaming directory entries can change that timestamp even when the report does not depend on those entries. The extra rebuild follows the dependency definition.

Timestamp freshness and equal content are different observations. A recipe can execute and reproduce identical bytes. A skipped recipe can leave bytes that happen to look correct despite an incomplete dependency list. Retain the execution marker, contents and actual timestamps rather than relying on a zero exit status alone.

Give preparation and content different contracts

This complete minimal Makefile is unexecuted. It requires GNU Make, a conventional shell, cp, mkdir and an independent writable directory. Recipe indentation must remain tabs. The report is a real file target; all is the default entry in this fixture, with no real file named all. Nothing removes an existing project directory.

all: out/report.txt

out/report.txt: input.txt | out
    @printf 'build-report\n'
    cp input.txt out/report.txt

out:
    mkdir -p out

Create input.txt containing alpha and a newline. Because input.txt is left of the pipe, its update can invalidate an existing report. Out is on the right: its rule must finish first, but its timestamp alone does not trigger the report recipe. A missing report still needs generation; the pipe does not make an absent target usable.

For a controlled comparison, use another fresh directory with identical input and change only input.txt | out to input.txt out. The groups must not share out. Alternating rule files over the same existing outputs would carry one group’s state into the next.

The proposed sequence has not been run. First run make separately in both groups and check that the report contains alpha. Add unrelated.txt inside each out directory, inspect the actual timestamps and run again. The comparison requires the directory to be newer than the report. Otherwise the normal-prerequisite group might also skip rebuilding, leaving the intended branch untested. Record filesystem precision and clock conditions instead of assuming creation order establishes the required timestamps.

Three inputs with independent expectations

Initially both the directory and report are absent. Each group should prepare the directory, generate the report and produce alpha. After the unrelated entry is added, a confirmed newer directory can produce another build-report marker in the normal group. The order-only group should not regenerate solely because that directory timestamp changed. “Solely” matters: an edited input or deleted target supplies a separate reason.

Finally change input.txt to beta plus a newline in both groups, confirm that the input is newer than the report and run again. Both rules should regenerate beta because the actual input remains normal. This checks that the fix preserves content updates. Preventing a directory-only rebuild is insufficient if the change also suppresses required rebuilding.

A concrete failure is moving input.txt to the right of the pipe as well. With an existing target, a newer input no longer supplies its normal freshness condition, so alpha can remain after the source changes. Moving a dependency is not simply a performance setting: it changes which facts establish that an output is stale.

Which rule wins when a directory is both normal and order-only?

The normal prerequisite takes precedence. The official section explains that declarations for the same target can accumulate, with normal prerequisites providing the stronger behavior. A pipe in one line therefore does not prove that directory timestamps have been excluded everywhere. Review included files, generated fragments and additional rules for the same target.

This follow-up changes the investigation scope. A correct local edit can leave the original normal edge elsewhere in the complete graph. Preserve the actual rule set read by make rather than applying one-line reasoning to a large project’s total rebuild count.

Does a phony preparation step force the report to rebuild?

Not solely when it is order-only. The preparation action is still considered according to its contract, and failure cannot be treated as successful report generation. If it changes a content-bearing configuration file that is absent from the normal input list, order-only dependencies can hide that change. Register the content input instead of relying on an action name to signal it.

The phony-target article addresses name collisions and action identity. The failure-deletion article addresses incomplete files left behind. Here the report is a valid real file; the decision is which changes should invalidate it. Making every output phony would replace that decision rather than resolve it.

The proposed verification retains both Makefiles, GNU Make version, immediate exit statuses, markers, contents and timestamps. Test a missing directory, a directory-only change and a real input update separately. Preserve contrary results instead of retrying until the expected branch appears. No builds were executed here, and the fixture proves nothing about concurrent generation, atomic publication or undeclared inputs. Give directory preparation and content updates their separate dependency relationships before judging the real report’s input coverage.
