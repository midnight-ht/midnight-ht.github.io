Why is a Ready Pod not yet counted as available?

Trace an interrupted readiness interval and compare it with a zero-second control to explain Deployment availability.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-12 · Estimated read 10 min
Translations
zh-CN en

Article

Key takeaways

  • Read the two replica counts separately.
  • Start the interval at the most recent Ready transition.
  • Match the observed Pod and Deployment generation.

The new Pod is Ready, but the Deployment’s available replica count has not increased. Check the minimum ready interval.

During a rollout the readiness probe can succeed before the Deployment counts the replica as available. To explain that gap, identify the ReplicaSet that owns the Pod and record the actual condition changes. Status lines captured at different moments can otherwise combine several effects, including a change of rollout generation or a delayed controller update.

A Deployment’s minReadySeconds sets how long a new Pod must remain ready without any container crashing before it qualifies as available. The default is zero. The readyReplicas count follows the Ready condition of managed Pods. The availableReplicas count also requires the configured interval to elapse. Deployment documentation

Record three condition changes

Use an isolated test namespace. This single-replica manifest uses a file to control a readiness probe. The container keeps running while the file appears and disappears. The manifest and timeline have not been executed against a cluster.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: readiness-window-demo
spec:
  replicas: 1
  minReadySeconds: 20
  selector:
    matchLabels:
      app: readiness-window-demo
  template:
    metadata:
      labels:
        app: readiness-window-demo
    spec:
      containers:
        - name: app
          image: busybox:1.36.1
          command: ["sleep", "3600"]
          readinessProbe:
            exec:
              command: ["test", "-f", "/tmp/ready"]
            periodSeconds: 1
            failureThreshold: 1

Apply the manifest and record the Pod’s name and UID. Run kubectl exec POD -- touch /tmp/ready. After the Ready condition becomes true, use kubectl exec POD -- rm /tmp/ready while the first twenty-second window is still open. Wait for Ready to turn false, then recreate the file. Record the actual condition changes and confirm that the UID and container restart count stay the same. If the first window already elapsed before the deletion, start a fresh run for this control. Probe and controller scheduling can shift the observed times.

Relative time Ready on the same Pod Availability qualification
10 s Turns true First window begins
15 s Turns false The first five seconds are lost
22 s Returns to true A fresh window begins
42 s Stays true with no container crash Earliest qualification

At 30 seconds, the latest uninterrupted interval is eight seconds. Counting from the first transition would predict availability twelve seconds too early. The 42-second point is the earliest qualification in this timeline. The controller can publish the updated replica count later.

In a rolling update, an old replica can already account for the available count of one while the new Pod first becomes Ready. That aggregate alone cannot tell you which revision contributes the available replica. The single-replica exercise starts from a clean environment to avoid that ambiguity. In production, record which ReplicaSet owns each Pod before interpreting an unchanged total.

Keep the file operations and Pod transitions in separate columns. Removing and recreating the file between probes can leave Ready true throughout. An observed false transition is the evidence that the experiment actually interrupted the interval.

Compare the same evidence with a zero interval

Capture kubectl get pod POD -o yaml after each change and look for the Ready condition’s status and lastTransitionTime. The object holds only the most recent transition for that condition. Save each snapshot while it is relevant. On the Deployment, save the two replica counts and status.observedGeneration from kubectl get deployment readiness-window-demo -o yaml. Match the observed generation to the manifest change. If more than one Pod appears, check owner references before interpreting the aggregate count.

Repeat the probe exercise in a fresh test environment with minReadySeconds: 0. A ready replica can qualify immediately, with any remaining reporting delay coming from observation and reconciliation. In an actual rollout where continuous readiness has already outlasted the configured interval, inspect the generation, owning ReplicaSet and controller events. If the Pod never turns Ready, check for a missing custom readiness condition. To establish when requests reached the application, collect endpoint or request evidence separately.

Can a thirty-second ready interval use a thirty-second progress deadline?

progressDeadlineSeconds must be greater than minReadySeconds. Give the rollout a longer progress deadline so there is room for scheduling, startup and readiness. When the deadline expires the Deployment can report ProgressDeadlineExceeded and the controller continues to retry. Use that condition alongside the relevant Pod events and readiness history to decide how to respond. Deployment progress deadline
