Where does a Redis task go if its worker crashes after claiming it?

Trace the ready and processing lists through a Redis claim, worker interruption, and acknowledgment.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-12 · Estimated read 10 min
Translations
zh-CN en

Article

Key takeaways

  • LMOVE moves an entry from ready to processing in one command.
  • Acknowledge the claim after its work completes.
  • Two interruptions with the same list state can require different recovery actions.

A Redis worker pops a job and crashes. The job has already left the ready list. If the worker claims it with LMOVE, Redis moves it into a processing list in the same command. Recovery now has a place to look, though it still needs to find out whether the work finished.

Consider a queue that generates export files. Job A is first and job B is second. A worker claims A and exits just before reading the source data. If it used LPOP, a look at the ready list only finds B. If it used LMOVE, A is still visible in the processing list. Another worker can claim B. Redis can show where the job is while the export service keeps the evidence of what happened to the file.

Check the two lists around claim and acknowledgment

LMOVE is available in Redis Open Source 6.2 and later. The following commands are unexecuted. Use a disposable instance or unused test keys with no competing writers. Both keys start out absent. Read list contents from left to right so the check covers the selected ends of both lists.

RPUSH {move-demo}:ready job-a job-b
LRANGE {move-demo}:ready 0 -1
LRANGE {move-demo}:processing 0 -1

LMOVE {move-demo}:ready {move-demo}:processing LEFT RIGHT
LRANGE {move-demo}:ready 0 -1
LRANGE {move-demo}:processing 0 -1

LREM {move-demo}:processing 1 job-a
LRANGE {move-demo}:processing 0 -1
LRANGE {move-demo}:ready 0 -1

After the initial push, ready should contain [job-a, job-b] and processing should be empty. LMOVE should return job-a. The next two range reads should show [job-b] and [job-a]. For the interruption test, stop there and omit LREM. Recovery should find A in processing before it consults the application's records. On a separate run starting from the same state, let the worker finish and acknowledge A. LREM should remove one element and leave processing empty. Ready should still contain only B. Redis LMOVE.

A pop followed by a separate write to the processing list leaves another place for the worker to fail. LMOVE puts both list changes in one Redis command. To test the interrupted worker, pause after the claim response and before acknowledgment, then read both lists from a second connection. That assertion is about the visible Redis state. If the client disconnects before seeing a reply, inspect the server state or a durable application claim record. A client exception alone cannot tell you that A stayed in ready.

Decide whether to run the job again

Suppose the export service accepted A and created a file before the worker died. The processing entry looks the same as it did when the worker died before calling the service. Sending A straight to another worker can generate the export twice. An application can look up the existing export by stable job ID or use a service that supports idempotent submissions under that ID. The recovery decision depends on what that service actually guarantees. Exercise two interruptions in the application, one before the external call and one after it is accepted. The list state can match while the correct recovery action differs.

Processing also needs a policy for when a claim has expired. A long-running worker can still be active when another process tries to recover its job. Start with a single-worker test and record how a stale claim is recognized and where the retried job is placed. If multiple recovery workers are added, test two concurrent attempts to recover the same job and verify that the application registers only the permitted claim. The serial commands above do not implement that control.

Test persistence and failover separately if the Redis instance itself can fail. A successful reply does not prove the entry will be visible after restart. In clustered Redis, check the deployment's multi-key rules for the two keys. The fixture uses a shared hash tag and does not exercise a cluster. These list observations also leave external exactly-once delivery unverified. The related Redis transaction example covers errors across command batches.

What if two jobs have identical payloads?

Give the two jobs distinguishable list values, such as job-a and job-b, even if their export requests contain the same data. Acknowledgment can then target the identity returned by the claim. If the list stores only the identical payloads, LREM matches the value and cannot establish which of the two jobs the worker completed.

There is a separate problem when the same job is reclaimed and its original worker later tries to acknowledge it. An acknowledgment by job ID alone can remove the newer claim. Give claims distinct receipts and accept an acknowledgment only for the current receipt. If receipts live in a separate record, also test the concurrency boundary between checking the receipt and applying the acknowledgment. A useful fixture gives the same job two receipts and delays the earlier acknowledgment until the second is active. Expect the active claim to survive. This follow-up is unexecuted. The original list commands do not implement a receipt protocol.
