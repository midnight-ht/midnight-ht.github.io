Why does CMake reuse output after an input the generator read changes?

Compare two Ninja builds that run the same generator and track different sets of input dependencies.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-12 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • Record the inputs the generator reads.
  • Include an edit after the first successful build.
  • Inspect command output and generated content together.

The first report build succeeds. Editing its nested configuration then leaves the generated report untouched. Inspect the build graph for that input. A custom command can open a file during execution, but a later build needs a declared or recorded dependency to know when that command should run again.

Put the entry point and the discovered input in the graph

Suppose a manifest names a fragment. The generator reads both files. The command line names the manifest, and the build rule lists the manifest and generator script in DEPENDS. An edit to the fragment changes neither listed input. The first build still works because the output is missing. The stale result appears only when the output already exists.

For a short fixed list, put the inputs directly in DEPENDS. When the generator discovers them while processing the manifest, it can write a depfile and declare it through DEPFILE on a supported generator. CMake documents a dependency-file format compatible with GCC's dependency output. This example uses regular Ninja with CMake 3.20 or later for the selected policy. Regular Ninja has supported the keyword since CMake 3.7. CMake custom command reference

Keeping discovery in the generator avoids maintaining another parser for its input format. Review what the generator reports, especially when the manifest changes which file it reads. An omitted input stays invisible to subsequent builds.

Run the same command in two build trees

This complete example is proposed and unexecuted. Use a new directory without spaces, hash signs or dollar signs in its path. Create manifest containing fragment and a newline, and fragment containing blue and a newline. The simple paths keep depfile escaping outside the example.

# CMakeLists.txt
cmake_minimum_required(VERSION 3.20)
project(ReportProbe NONE)
option(TRACK_READS "Attach the dependency file" OFF)

set(report "${CMAKE_CURRENT_BINARY_DIR}/report")
set(deps "${CMAKE_CURRENT_BINARY_DIR}/inputs")
set(extra)
if(TRACK_READS)
  list(APPEND extra DEPFILE "${deps}")
endif()

add_custom_command(
  OUTPUT "${report}"
  COMMAND "${CMAKE_COMMAND}"
    "-DSOURCE=${CMAKE_CURRENT_SOURCE_DIR}"
    "-DREPORT=${report}"
    "-DDEPS=${deps}"
    -P "${CMAKE_CURRENT_SOURCE_DIR}/generate.cmake"
  DEPENDS "${CMAKE_CURRENT_SOURCE_DIR}/manifest"
          "${CMAKE_CURRENT_SOURCE_DIR}/generate.cmake"
  ${extra}
  VERBATIM
)
add_custom_target(report_probe ALL DEPENDS "${report}")

# generate.cmake
file(READ "${SOURCE}/manifest" child)
string(STRIP "${child}" child)
set(input "${SOURCE}/${child}")
file(READ "${input}" value)
file(WRITE "${REPORT}" "${value}")
file(WRITE "${DEPS}" "${REPORT}: ${input}\n")
message(STATUS "generated report")

set -eu
cmake -S . -B without-edge -G Ninja -DTRACK_READS=OFF
cmake -S . -B with-edge -G Ninja -DTRACK_READS=ON
cmake --build without-edge
cmake --build with-edge
cat without-edge/report with-edge/report

cmake --build without-edge
cmake --build with-edge

printf 'green\n' > fragment
cmake --build without-edge --verbose
cmake --build with-edge --verbose
cat without-edge/report with-edge/report

Both first builds should write blue. An unchanged rebuild should reuse the reports. The last round changes only the fragment. The report without the attached depfile should remain blue, and the report with it should become green. Both commands write the file named inputs, so the existence of that file cannot distinguish the cases. Check the command output and report content together.

If both commands rerun, check for a cleaned build tree, a changed manifest or a repeated configuration step. If neither reruns, confirm that the filesystem recorded the edit and that the depfile names the report actually being built. Preserve the commands' status and output before deciding which condition failed.

Check each input change independently

The script and manifest remain explicit dependencies. Switching the manifest to a different fragment should rerun both builds and produce an updated report of discovered inputs. Test that separately from an edit to a fragment already named by the manifest. Add an unrelated file as another control. A rebuild caused by scanning a directory does not establish that the generator reported its own dependencies. CMake source membership checks

If a rebuild is missed, inspect what the generator actually wrote. A missing entry in the file calls for fixing the generator's record of its reads. When the entry is present, compare the recorded path, the configured depfile path and the output being built. This finds a disconnected or misdirected dependency without changing the input again.

The fragment in this fixture exists before the first build. A real project may have another rule create it. Arrange that producer to run before the report command reads the fragment. A dependency report that appears only after the reader runs cannot supply a missing first-run input. Verify that ordering from an empty build directory and then make a separate incremental edit.

Where does a relative DEPFILE point after moving the rule into a subdirectory?

For Ninja with CMP0116 set to NEW, the relative argument and the relative paths inside the file are based on the current binary directory. CMake writes a transformed internal file after the command runs and leaves the original intact. After a move, check the output and input paths against that subdirectory's binary directory. The main fixture uses absolute paths. Moving the rule and introducing relative paths adds a separate condition to verify. CMake policy CMP0116
