Why did ZADD GT add a new leaderboard member?

Use independent membership and score checks to explain Redis ZADD GT, XX, and the behavior of a missing leaderboard key.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-12 · Estimated read 11 min
Translations
zh-CN en

Article

Key takeaways

  • GT limits existing score updates and still permits insertion.
  • Use XX GT when only enrolled members may increase their scores.
  • A missing board needs an explicit admission or recovery step.

Redis ZADD GT can add a new member. It requires a higher score only when the member already exists. If a job may raise scores for enrolled members only, include XX so the write checks membership as well as score.

Imagine a leaderboard that requires manual enrollment. A score synchronizer receives an old result and must avoid lowering an existing score. GT handles that case. An unapproved participant can still appear on the board after their first report. The missing check concerns admission.

A score comparison needs an existing score

The Redis ZADD command reference defines GT and XX separately. GT updates an existing member only when the new score is strictly higher. It permits insertion when that member is absent. XX restricts the command to existing members. GT and LT were added in Redis 6.2.0. Record the server and client versions when validating the actual path.

A member is a sorted-set identity. Two members can have the same score. Two different strings can also create separate entries for the same person if the application fails to normalize the identity. Use a stable enrollment identifier consistently across writers. The score comparison cannot reconcile aliases.

An equal score does not change the existing score. Review comments, event versions, and timestamps still need separate rules if they accompany the score. A leaderboard projection alone may be unable to explain which event should change related data.

Write the state oracle before reading replies

The following commands are unexecuted. Use a disposable instance you own and a previously absent example key. The scores are integers. Each read checks the affected member at a specific step.

ZADD article:nov12:rank 10 A
ZADD article:nov12:rank GT 9 A
ZSCORE article:nov12:rank A
ZADD article:nov12:rank GT 4 B
ZSCORE article:nov12:rank B
ZADD article:nov12:rank XX GT 100 C
ZSCORE article:nov12:rank C
ZADD article:nov12:rank XX GT 12 A
ZSCORE article:nov12:rank A
ZADD article:nov12:rank XX GT 12 A
ZSCORE article:nov12:rank A

The expected reads are ten, four, absent, twelve, and twelve. The lower existing score is rejected. GT alone admits B. C stays absent under XX GT despite its proposed score of one hundred. A can increase to twelve, and the equal-score write leaves it there.

A final cardinality of two would miss an incorrect insertion of C followed by a deletion of B. A final score of twelve would not show whether nine temporarily replaced ten. Record each reply and its position if testing through a pipeline. These are expected state observations for the fixture. No Redis server or client was exercised here.

The default count tracks new members, so a successful update from ten to twelve can return zero. CH changes the count to include changed members. A zero change count can still describe several different outcomes. When membership and retained scores matter, check the affected member state. The site’s HSET reply article covers reply interpretation for a different command. The central question here is which writes GT and XX permit.

Decide which writer owns admission

An open board can use GT when a first report may establish a score and existing scores may only increase. A reviewed board can let the enrollment workflow create or remove members and use XX GT for score updates. If the product supports score deductions, GT would prevent a legitimate update. That policy needs its own version or event ordering rule.

Reading, deciding and then writing in separate commands leaves an interval in which another writer can remove a member. Adding XX to the write lets Redis check presence at that command’s execution. A separate approval service still needs a contract for updating the projection, revoking eligibility and handling late events.

Include a specifically identified unapproved participant in the test data. Fixtures with enrolled members only never exercise the admission failure. Preserve the actual member string and inspect the final lookup so an identity-encoding error can be distinguished from a score or membership decision.

Can XX GT establish the first entry when the entire key is missing?

It cannot add the first member. XX requires an existing member, and an absent key has none to update. Choose two disposable keys and confirm that each is absent with its own EXISTS call. Run ZADD board:missing:xx XX GT 10 A and expect EXISTS board:missing:xx to return 0. As a positive control, run ZADD board:missing:gt GT 10 A on the other key. Expect EXISTS board:missing:gt to return 1 and ZSCORE to report a score of 10 for A. This distinguishes the existence of the key from the state of a candidate member. The key-level control is unexecuted. Redis EXISTS.

If the full production board disappears, repeated XX GT calls cannot restore its membership history. The enrollment records and reconstruction process need their own checks before resuming synchronization. This fixture addresses command conditions. Rebuilding, persistence, and production recovery remain outside the execution evidence.
