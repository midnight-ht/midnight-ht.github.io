Why can a literal qualify for a partial index while a bound status cannot?

Compare generic and custom PostgreSQL plans to tell partial-index eligibility from the path the planner actually chooses.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-12 · Estimated read 10 min
Translations
zh-CN en

Article

Key takeaways

  • A generic plan cannot use the current status argument to establish the partial-index predicate.
  • The custom planner can use the argument; cost still determines the access path.
  • A dedicated pending-only query can continue binding its owner input.

Two executions of a pending-job query can return the same row and have different plans. A custom plan can use the value passed for this run to see whether a partial index covers the query. A generic plan has to work when a later call supplies a different status.

Imagine a jobs page with a switch between pending and completed work. The database has an index just for pending jobs so completed rows do not take up space in it. During diagnosis, someone copies the query from a log, substitutes the literal pending, and sees that the rewritten query can use the index. The prepared statement still shows a sequential scan. Before comparing those plans, account for what the planner could establish when each was built.

Fix the arguments and the expected result

The SQL below is an unexecuted teaching fixture. Build the table and prepare the statement once in a test session. Each transaction changes the plan mode locally while the records and arguments stay fixed. Use EXPLAIN to inspect the plan and a separate EXECUTE to verify the result.

CREATE TEMP TABLE plan_jobs (id int, status text, owner int);
INSERT INTO plan_jobs VALUES (1, 'pending', 8), (2, 'done', 8), (3, 'pending', 9);
CREATE INDEX plan_jobs_pending_owner ON plan_jobs (owner) WHERE status = 'pending';

PREPARE list_jobs (text, int) AS
SELECT id FROM plan_jobs WHERE status = $1 AND owner = $2;

BEGIN;
SET LOCAL plan_cache_mode = force_generic_plan;
EXPLAIN (COSTS OFF) EXECUTE list_jobs ('pending', 8);
EXECUTE list_jobs ('pending', 8);
COMMIT;

BEGIN;
SET LOCAL plan_cache_mode = force_custom_plan;
EXPLAIN (COSTS OFF) EXECUTE list_jobs ('pending', 8);
EXECUTE list_jobs ('pending', 8);
COMMIT;

Both executions should return only job 1. Job 2 has the same owner but is done. Job 3 is pending but belongs to another owner. Check both exclusions before interpreting a plan difference. Use one database session for the setup, prepared statement, and transaction-local setting.

Consider a future execution with done as the status. It should return job 2, which is absent from the pending-only index. A generic plan cannot use the status parameter to establish the pending predicate for every execution. A custom plan can substitute the current status, and pending satisfies the index predicate. On three rows a sequential scan can still be cheaper. Eligibility and the chosen path are separate decisions. PostgreSQL 18 partial indexes and PREPARE.

Read what each plan had to work with

EXPLAIN EXECUTE shows parameter symbols in a generic plan and substitutes supplied values in a custom plan. Look at the scan's filter or index condition, then look for the name of the index. Seeing the literal identifies the value available to the custom planner. Seeing the index name tells you whether the planner selected that index. Preserve both plans without changing cost settings just to make an index appear.

The small fixture checks the predicate and row values. On representative data, separately measure the effect of different statuses and owner distributions. A busy owner with many pending rows can make a different access path cheaper even when the partial predicate is recognized. Save the observed plan and the parameter frequencies instead of estimating production latency from three rows. A related index-only scan example covers heap access once an index path has been chosen.

When people need to choose any status, keep the prepared query and evaluate plans with the distribution that the interface sees. A complete index is another option to evaluate, including space and write costs. The forced settings here belong to a local diagnostic transaction. For an application-side investigation, record the actual SQL and find out whether the driver creates a reusable server-side prepared statement. Confirm which connection EXPLAIN ran on. Two endpoints that log the same parameter notation can still have different preparation behavior.

What if only the owner is bound?

Suppose a separate endpoint always lists pending jobs. Prepare SELECT id FROM plan_jobs WHERE status = 'pending' AND owner = $1 for that endpoint, with the owner still bound. The literal establishes the partial-index predicate even in a generic plan. The parameter selects an owner within that range. Expect job 1 for owner 8 and job 3 for owner 9. This follow-up is also unexecuted, and the cost-based choice can still be a sequential scan. Put the literal in predefined SQL and continue binding the user input. The original endpoint still needs to serve done jobs, so the fixed-state statement belongs to the narrower endpoint.
