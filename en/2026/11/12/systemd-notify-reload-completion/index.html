Why can systemctl reload return before new settings take effect?

Compare a signal-only reload with a notification-based reload and check the active configuration generation.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-12 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • Observe the command return and application state separately.
  • Send the completion notification after applying settings.
  • Use a synchronous command or the application notification protocol.

An ExecReload command that only sends a signal can exit while the application is still reading its new settings.

A release script writes new settings and runs systemctl reload. The prompt returns, yet the application reports the old configuration generation. Record three separate events to locate the gap. The signal command exits, the application switches generations, and the manager learns that reload has completed. The shell exit code alone leaves the application’s timeline unclear.

Let the application mark completion

With ExecReload=kill -HUP $MAINPID, the command completes once it sends the signal. The main process handles configuration loading afterward. A successful command exit says nothing about when that process will finish. A control command that requests reload and waits synchronously for the result is one option. The service manual recommends a synchronous reload command or the notification protocol so dependent reloads can be ordered correctly.

With Type=notify-reload, the manager sends the reload signal, which defaults to SIGHUP. The application begins by sending RELOADING=1 and a current monotonic timestamp in microseconds, MONOTONIC_USEC, in one message. After applying the configuration it sends READY=1. The manager uses that final message to finish the reload. The same service type uses a readiness notification at startup. This example follows the systemd 262 manual. Check the installed manager and the application before selecting the type.

Give each generation a visible handoff

Use an isolated Linux host for the lab. The systemd example was not run for this article. The service writes the active generation to an active file. During reload it waits for a separate release file before applying the new value. That gate makes the ordering observable without relying on a guessed sleep duration. Create /var/lib/reload-lab, save this program there as app.py, write old to wanted, and make sure there is no release file.

import os
import signal
import socket
import time
from pathlib import Path

wanted, active = Path("wanted"), Path("active")
pending = False

def notify(message):
    address = os.environ["NOTIFY_SOCKET"]
    if address.startswith("@"):
        address = "\0" + address[1:]
    with socket.socket(socket.AF_UNIX, socket.SOCK_DGRAM) as sock:
        sock.sendto(message.encode(), address)

def on_hup(signum, frame):
    global pending
    pending = True

def apply():
    generation = wanted.read_text().strip()
    temporary = active.with_suffix(".next")
    temporary.write_text(generation + "\n")
    temporary.replace(active)

signal.signal(signal.SIGHUP, on_hup)
apply()
notify("READY=1")

while True:
    if pending:
        pending = False
        now_usec = time.monotonic_ns() // 1000
        notify(f"RELOADING=1\nMONOTONIC_USEC={now_usec}")
        print("reload entered", flush=True)
        while not Path("release").exists():
            time.sleep(0.05)
        apply()
        print("generation applied", flush=True)
        notify("READY=1")
    time.sleep(0.05)

Install the following as the dedicated test unit reload-lab.service. Run systemctl daemon-reload and start the unit with the appropriate privileges. Confirm active contains old, then write new to wanted. Run systemctl reload reload-lab.service in one terminal. In another, use journalctl -u reload-lab.service -f to follow the application messages and check the active generation.

[Unit]
Description=Reload completion lab

[Service]
Type=notify-reload
NotifyAccess=main
WorkingDirectory=/var/lib/reload-lab
ExecStart=/usr/bin/python3 /var/lib/reload-lab/app.py

The expected result at reload entered is a pending management command and an active value of old. Create the release file. The process replaces the active generation and sends completion before the management command should return successfully. Capture both observations. The journal message shows the reload handler has entered its work. The file shows which generation the application has actually applied. Leaving the gate behind from a previous run removes the waiting state and makes the ordering harder to observe.

Read the generation once before opening the gate and once after the manager returns. If the command has already returned while the gate is closed, save that result alongside the old generation before opening it. If the command is still waiting, record that state first. The gate is for this lab. A real application decides when to switch based on its own validation and commit steps.

Repeat with a signal-only command

Stop the lab unit, change the type to notify and add ExecReload=/bin/kill -HUP $MAINPID under the service section. Reload the unit definition, restore the initial files, and start the same program. Startup still uses its readiness message. For reload, the command now waits only for the signal command. Write the new generation again and initiate reload with the release gate absent. The expected outcome is a successful command return while the active value is still old. Creating the gate lets the application complete the change. The application behavior is held constant across the two cases.

A real application might already expose a control interface that can wait for reload results. Where completion is implemented through notifications, verify which process can send them and confirm that the service announces readiness only after a successful switch. The lab handles a single successful generation replacement. A production service also needs behavior for invalid configuration and concurrent requests, and a way to query its actual state. Keep the manager result, active generation, and a request that exercises the changed setting when validating a rollout. For the initial service startup path, see how systemd uses startup readiness.

After the comparison, stop the test unit, remove the unit file and data directory created for it, and reload unit definitions. Label the two records with their service types. The service manual covers the signal command, notification protocol and reload deadline under the corresponding directive names. systemd.service manual

Does TimeoutStartSec also apply to reload?

The limit applies to reload too. The manual says that when reload times out, the operation reports failure and the existing service continues running. Check the application’s generation and logs before deciding whether to retry. A failed manager operation tells you it did not receive completion on time. The state of an application that continued its work requires separate evidence.
