What does Last-Event-ID tell an SSE server after reconnect?

Follow two notifications with an inherited ID in a loopback fixture, then separate the EventSource reconnect cursor from application acknowledgment.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-12 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • An SSE block can update the browser’s resume cursor.
  • A later message can inherit the previous event ID.
  • Replay and application acknowledgment require their own contract.

A browser reconnects to a notification stream with Last-Event-ID: 41. The server sees the resume position recorded by EventSource. The header does not establish that an application callback finished or that a write committed. Define the browser cursor and the application’s acknowledgment separately before using either to decide what to replay.

Two messages can carry the same cursor

HTML’s event-stream interpretation algorithm processes fields line by line and handles an event block at a blank line. An id field value without a NUL character updates the last event ID buffer. Processing the blank line updates the EventSource’s stored ID. A message created at that point carries that value. A later message with only data can inherit it.

Suppose a progress stream sends stage-a with ID 41, then stage-b without a new id field. The two messages contain different data and both report lastEventId 41. Deduplicating solely on that value drops stage-b. If the application needs distinct message identities, define them and decide whether they also represent positions in the stream.

A transport read does not define the event boundary. It can yield several lines or part of one line. The sample writes two blocks in a single response. Blank lines separate them. Remove the final blank line and the end of the response does not dispatch the unfinished block. A server log that shows a write does not establish a client notification.

Record the requests and the messages separately

This complete Node fixture has not been run with a browser. It binds only to loopback and serves the example page and stream from the same origin. Save it as server.mjs, run node server.mjs, and open the address printed in the terminal. Use one tab and restart the process between trials. The response ends to trigger a reconnect, then the server returns 204 to stop this example. The retry value is a teaching choice.

import { createServer } from 'node:http';

const page = `<!doctype html>
<meta charset="utf-8">
<title>Reconnect cursor example</title>
<pre id="events"></pre>
<script>
const log = document.getElementById('events');
const stream = new EventSource('/events');
stream.onmessage = ({ data, lastEventId }) => {
  log.append(JSON.stringify({ data, lastEventId }) + '\\n');
};
</script>`;

let opened = false;
const frameA = 'retry: 100\nid: 41\ndata: stage-a\n\n';
const frameB = 'data: stage-b\n\n';

createServer(({ url, headers }, res) => {
  if (url === '/') {
    res.writeHead(200, { 'Content-Type': 'text/html; charset=utf-8' });
    res.end(page);
    return;
  }
  if (url !== '/events') {
    res.statusCode = 404;
    res.end();
    return;
  }
  const { 'last-event-id': cursor } = headers;
  console.log('EventSource request cursor:', cursor ?? '(absent)');
  if (opened) {
    res.statusCode = 204;
    res.end();
    return;
  }
  opened = true;
  res.writeHead(200, { 'Content-Type': 'text/event-stream' });
  res.end(frameA + frameB);
}).listen(8765, '127.0.0.1', () => {
  console.log('Open http://127.0.0.1:8765/ in a browser');
});

Expect three independent observations. The initial event request has no last event ID header. The page receives stage-a and stage-b, both with lastEventId 41. The subsequent request carries 41 under HTML’s reconnect header rule. These are expected values, not captured browser logs.

Record the server request and the page messages separately. EventSource can update its stored ID and queue a message before the page processes it. Even if both messages eventually appear in this demo, the server still cannot infer from the header that the callback completed. This fixture also returns no replayed events, so it does not establish recovery of application state.

Give replay and acknowledgment their own rules

A server using the cursor for replay needs to define the stream identity, the cursor’s meaning, and its retention window. An ID might locate one persisted log entry or mark a recent synchronization point. In the latter case, recovery may start with a fresh snapshot. If the server can no longer recover an old position, provide an explicit recovery path under the application’s contract.

Suppose processing stage-b fails while updating storage. The interface can still lack the new progress state while the browser retains 41. Recovery depends on how the application tracks processed messages and what the server can supply again. CloudEvents event identity covers redelivery and business transactions. Here the browser’s HTTP reconnect marker needs a separate interpretation.

A proposed integration check can verify the reconnect header first, then force an application processing failure. Record the request cursor, whether the application saved the update, and what the recovery path obtains. Keep automatic reconnection of one EventSource separate from a page that intentionally creates a new one. This fixture covers the first case only.

Does an id-only block dispatch a message?

No. It updates the resume cursor. Add a literal id: 42 followed by a newline and a blank line at the end of the first response. The two original data blocks still produce their original messages with ID 41. Processing the extra block records 42 without creating a third message, since the data buffer is empty. The next reconnect should carry 42. This changes just the final block and gives separate expected message counts and cursor values. Keep the blank line in the new block so the browser processes it.
