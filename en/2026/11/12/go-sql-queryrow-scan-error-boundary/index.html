Why does Go QueryRowContext return a Row before Scan reports an error?

Use four test-driver inputs to trace the boundaries of a Go query Row, Row.Err, and Scan.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-12 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • A non-nil Row still needs a Scan check.
  • Handle absence, query failures, and conversion errors separately.
  • Reading the first row does not establish uniqueness.

Go’s QueryRowContext can return a *Row before Scan reports an error. Handle the return from Scan before handing a query result to the caller. The pointer gives you an object to read from.

Consider an order lookup that returns a total. Existing code logs a successful lookup as soon as it receives a Row, then reads the amount later. An unknown ID should become a missing-order result. A driver failure and a value that cannot be stored in the requested destination also prevent the service from returning an amount. Scan is where the caller can observe all three outcomes and decide what each means.

Fix four inputs and observe their outcomes

The following standard-library teaching program is unexecuted. The tiny driver accepts scenario names in place of SQL to isolate database/sql behavior. It uses no real database. The example checks the Row pointer, Row.Err, and Scan through the same entry point for each scenario.

package main

import (
    "context"
    "database/sql"
    "database/sql/driver"
    "errors"
    "fmt"
    "io"
)

var offline = errors.New("fixture query failure")

type fixtureDriver struct{}
type fixtureConn struct{}
type fixtureRows struct{ values []driver.Value }

func (fixtureDriver) Open(string) (driver.Conn, error) {
    return fixtureConn{}, nil
}

func (fixtureConn) Prepare(string) (driver.Stmt, error) {
    return nil, errors.New("unexpected Prepare")
}

func (fixtureConn) Close() error { return nil }

func (fixtureConn) Begin() (driver.Tx, error) {
    return nil, errors.New("unexpected Begin")
}

func (fixtureConn) QueryContext(_ context.Context, scenario string, _ []driver.NamedValue) (driver.Rows, error) {
    switch scenario {
    case "ok":
        return &fixtureRows{values: []driver.Value{int64(12)}}, nil
    case "missing":
        return &fixtureRows{}, nil
    case "bad-value":
        return &fixtureRows{values: []driver.Value{"not numeric"}}, nil
    case "driver-error":
        return nil, offline
    default:
        return nil, errors.New("unknown fixture case")
    }
}

func (*fixtureRows) Columns() []string { return []string{"total"} }
func (*fixtureRows) Close() error { return nil }

func (rows *fixtureRows) Next(dest []driver.Value) error {
    if len(rows.values) == 0 {
        return io.EOF
    }
    dest[0] = rows.values[0]
    rows.values = rows.values[1:]
    return nil
}

func main() {
    sql.Register("row-fixture", fixtureDriver{})
    db, err := sql.Open("row-fixture", "")
    if err != nil {
        panic(err)
    }
    defer db.Close()

    ctx := context.Background()
    for _, scenario := range []string{"ok", "missing", "driver-error", "bad-value"} {
        row := db.QueryRowContext(ctx, scenario)
        queryErr := row.Err()
        var amount int
        scanErr := row.Scan(&amount)
        fmt.Printf("%s row=%t query=%v scan=%v missing=%t driver=%t amount=%d\n",
            scenario, row != nil, queryErr, scanErr, errors.Is(scanErr, sql.ErrNoRows),
            errors.Is(scanErr, offline), amount)
    }
}

Expect a Row in all four cases. In ok, Row.Err and Scan should both return nil, and the amount should be twelve. In missing, Row.Err should return nil and Scan should satisfy errors.Is(err, sql.ErrNoRows). In driver-error, Row.Err should already contain the driver error and Scan should return that error too. In bad-value, Row.Err should be nil, and scanning the nonnumeric string into an int should return a conversion error. That error matches neither ErrNoRows nor the sentinel driver error. Classify the errors before using the amount. The program prints the value for illustration, including in branches where it carries no business meaning.

The standard library documents a non-nil return from QueryRowContext and defers errors to Row.Scan. Row.Err allows a wrapper to inspect a query error already encountered. Scan will also return that error if present. When Row.Err is nil, the first row and its conversion still need to be checked. The empty-result and bad-value cases exercise those different boundaries. Give absence and read failure their own outcomes

An order details endpoint can treat an unknown ID as a business-level absence. Call Scan, then use errors.Is to identify ErrNoRows. Preserve the operation and original error in the other failure path. A zero amount can be a legitimate result. The endpoint’s contract determines how to represent a missing order over HTTP.

Add an endpoint-level control in which order 8 exists with a zero total and order 9 is absent. Check that the first response still identifies an order, while the second represents absence. If the interface only checks a displayed amount, both can look like zero. Pair this with a dependency failure so a service outage cannot accidentally pass the same missing-order test. The toy driver supplies a string conversion failure. A real integration test should exercise the actual database’s types and the destinations the application scans into.

Use separate logging points for a query attempt and a completed read. Write the success event after Scan and any required field validation. With several fields, an error can leave some destinations populated, so build the application object only after the scan succeeds. A wrapper can log an already available Row.Err, while still preserving a path for Scan to fail. The related RETURNING and commit article checks a write boundary. The evidence here concerns reading the row.

Connection events and returned column names can help locate a failure, but the caller still needs to verify the outcome it receives. Keep absence, driver failure, and conversion failure separate in the logs, and verify how the service maps those outcomes. Cancellation and timeouts need separate tests with the production driver. The four fixed inputs here leave that timing unverified.

A column-list change is another useful regression test. If the endpoint adds a currency, update the scan destinations and check the amount and currency independently. Include a row with an invalid amount and verify that the service does not publish a partially read record. The single-column driver above does not exercise this extension.

What if the query matches two rows?

Scan uses the first row and discards the rest. If a test driver sends totals twelve and twenty in that order, a successful scan can yield twelve without demonstrating that the second row was absent. Check the uniqueness constraint and the shape of the query separately if a lookup must produce at most one result. A unique order ID in the base table can still appear in several output rows after a one-to-many join. A regression test can enumerate the result rows to verify cardinality. If the requirement is to pick a representative row, express the intended order in the query and use distinct totals to test the selection. This follow-up is unexecuted. The main fixture does not verify uniqueness in a real database.
