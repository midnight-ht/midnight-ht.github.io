Why can moving the same custom element run its setup again?

Compare lifecycle callbacks when reordering native custom elements with insertBefore and moveBefore, then check the rule for first insertion.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-12 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • The same node identity and final order can accompany different lifecycle calls.
  • A custom element can define connectedMoveCallback to handle eligible moves directly.
  • First insertion and moving an existing node use different operations.

The list moves B ahead of A and keeps the same object. B can still record a disconnect and another connect. For an already inserted custom element, insertBefore and moveBefore can yield the same order through different lifecycle paths. To explain repeated setup, check the operation and the callbacks the component defines.

The same object can connect again

DOM’s insertion algorithm handles an already parented node through removal and insertion. Suppose a queue row sets up a subscription on connection and tears it down on disconnection. A reorder can run both operations even though the application still holds the same object. Whether it resets draft data or rebuilds a subscription depends on the component’s code.

The DOM move method uses the move algorithm. In the connected tree used here, it can invoke connectedMoveCallback on a custom element that defines it. HTML’s custom-element move guidance also specifies a compatibility path. Without a move callback, the element retains the disconnect/connect behavior. Replacing the caller’s operation alone may leave the component’s setup unchanged.

A connection count is therefore a poor proxy for the number of objects created. It can include another connection of the same object. Conversely, keeping that count fixed leaves a decision for the component. A row that uses its current column to compute a label can update that label on a move while retaining its subscription and editor state.

Record order, identity, and callbacks

Save the complete fixture as an HTML file. It has not been executed in a browser. Both parents begin with A then B and share the same custom-element definition. After initial connections, clicking Compare clears the log and performs each reorder. Element IDs distinguish entries in the log. The sample uses plain DOM and has no external service.

<!doctype html>
<meta charset="utf-8">
<title>Custom-element reorder comparison</title>
<section id="insert"><x-order-row id="ia">A</x-order-row><x-order-row id="ib">B</x-order-row></section>
<section id="move"><x-order-row id="ma">A</x-order-row><x-order-row id="mb">B</x-order-row></section>
<button id="run" type="button">Compare once</button>
<pre id="out"></pre>
<script>
const events = [];
const record = (type, element) => events.push([type, element.getAttribute("id")]);
class OrderRow extends HTMLElement {
  connectedCallback() { record('connect', this); }
  disconnectedCallback() { record('disconnect', this); }
  connectedMoveCallback() { record('move', this); }
}
customElements.define('x-order-row', OrderRow);
const byId = id => document.getElementById(id);
const [insert, move, ia, ib, ma, mb, run, out] =
  ['insert','move','ia','ib','ma','mb','run','out'].map(byId);
const report = () => events.splice(0);
const order = parent => Array.from(parent.children, el => el.textContent);
run.onclick = () => {
  run.disabled = true;
  report();
  insert.insertBefore(ib, ia);
  const ordinary = { order: order(insert), same: insert.firstElementChild === ib, events: report() };
  const supported = typeof Reflect.get(move, 'moveBefore') === 'function';
  let atomic = { supported };
  if (supported) {
    move.moveBefore(mb, ma);
    atomic = { order: order(move), same: move.firstElementChild === mb, events: report() };
  }
  out.textContent = JSON.stringify({ ordinary, atomic }, null, 2);
};
</script>

For the ordinary insertion, expect B then A, with the first element still equal to the original B. Its events should be ib disconnect and ib connect. For the move on a supporting implementation, expect the same order and identity result, with only an mb move event. A test that checks only the order and the object identity would pass both paths and miss the behavior under investigation.

If the move method is absent, the second branch records that condition. A method check does not establish the callback output, so record the target engine and the observed events when running the fixture. An application can use ordinary insertion as a fallback, with the lifecycle behavior that entails. Treat the effect on actual subscriptions or edit state as a separate acceptance check.

This custom row records only events. It has no embedded document, timer, focus management, or live connection. The fixture isolates the callback contract and leaves those other states for the actual component. A production check should say exactly which state must survive a reorder before it declares that state has been preserved.

Check which setup depends on the parent

Reordering within a list and moving to a different column in the same tree create different component requirements. If the parent supplies a group name, a move can preserve editing while refreshing the group label. Split that read from subscription setup, so a move does only the part that depends on the parent. If moving between columns should end editing, define that behavior as a product choice and check it explicitly.

An acceptance test can start each path with the same draft and subscription state, then reorder in one case and change columns in another. Inspect the label, draft, and subscription counts independently. Those tests remain proposed. DOM event dispatch and node references covers references that outlive event dispatch. Here the reference survives either operation, so it cannot distinguish the lifecycle path.

Can moveBefore put a newly created node into a connected list?

In this case it throws HierarchyRequestError. A freshly created detached element has a different root from the connected parent. The DOM move algorithm checks that root relationship. B was already in the tree in the main example. To verify the new case, use a fresh element, catch the named exception, then use appendChild or insertBefore for its first insertion. Record those as two different operations.
