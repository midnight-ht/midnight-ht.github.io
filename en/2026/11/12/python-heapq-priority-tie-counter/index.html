Why does heapq compare dictionaries when priorities tie?

Compare two-field heap entries with entries carrying a counter, using an unexecuted standard-library fixture for tie order and re-addition policy.

Article

Key takeaways

  • Tied priorities can make a two-field tuple compare its payload.
  • A distinct insertion counter defines FIFO order among ties.
  • Re-addition needs an explicit position policy.

A Python heap containing (priority, payload) pairs can reach the payload comparison when two priorities tie. If the payloads are different dictionaries, the second push can raise TypeError. For FIFO order within a priority, add an increasing insertion counter so comparison settles the tie before reaching either task object.

Imagine a single-process export service with ordinary jobs at priority five and urgent jobs at priority one. The queue should claim equally urgent jobs in the order this process accepted them. That is a claim-order requirement. Worker concurrency and job duration can still produce a different completion order.

The second field becomes relevant when the first ties

The Python 3.14.10 heapq documentation discusses stable priority queues and incomparable tasks. Tuple comparison proceeds from left to right. If the priorities differ, the first field settles the comparison and a dictionary payload can go unnoticed. A test with distinct priorities only will miss this defect.

A comparable payload can hide a related problem. With string task IDs, the queue may run without exceptions while ordering ties by ID. Include an input in which the second task’s ID sorts before the first to expose the difference between payload order and arrival order.

Comparability and stability are separate requirements. Excluding the task object from comparison avoids ordering dictionaries, but equal priority alone does not specify which task is next. A unique entry count both breaks the tie and prevents comparison from reaching the payload.

Verify the exception and the order in separate heaps

This standard-library example is unexecuted. The deliberately failing heap is separate from the repaired heap. The task data exists only in memory and starts no export.

from heapq import heappop, heappush
from itertools import count

broken = []
heappush(broken, (5, {"id": "A"}))
try:
    heappush(broken, (5, {"id": "B"}))
except TypeError:
    print("tied priority compared two payloads")
else:
    raise AssertionError("expected incomparable payloads")

ready = []
sequence = count()
for priority, task_id in [(5, "A"), (5, "B"), (1, "C")]:
    heappush(ready, (priority, next(sequence), {"id": task_id}))
claimed = [heappop(ready)[2]["id"] for _ in range(3)]
assert claimed == ["C", "A", "B"], claimed
print(claimed)

The independent expectation is that the second push into the first heap reaches the exception handler. The repaired heap should pop C, A, B. C arrives last and takes precedence because one is smaller than five. A precedes B because their priorities tie and A received the smaller counter value. A pure arrival queue would fail the first position. A queue sorted by payload can fail the same-priority positions.

Use a separate comparable-payload control. Push (5, "Z") and then (5, "A") into an empty heap. Two pops should give A and then Z, although A arrived second. Add distinct counters zero and one and the order should reverse. Deliberately opposing payload order to arrival order catches a queue that never raises an exception but still applies the wrong business rule.

Check actual pops rather than inspecting the array representation. The heap invariant makes the smallest entry available at the root without requiring the underlying list to be fully sorted. If a display needs a fully sorted view, sort a copy by priority and counter rather than rearranging the working queue.

Allocate the counter at the point that defines arrival

When one thread owns the heap, allocate the counter when it enqueues a task. A producer’s preassigned request ID does not show when the queue owner accepted the work. If submissions can interleave, define which action counts as acceptance and coordinate counter allocation with insertion. A different requirement, such as ordering by an upstream acceptance record, needs evidence from that upstream boundary.

A process-local counter is sufficient here. Independent counters across processes can collide, and one machine’s monotonic clock does not establish a cross-machine arrival order. If ordering must survive restart, retain the relevant sequence data with the queued record. Assigning new counters during recovery makes the order depend on how records were loaded.

If a product genuinely does not care how equal priorities are ordered, a wrapper with compare=False on the payload makes that choice explicit. Add a comparable counter when the product promises FIFO ties. The site’s pagination order article considers a separate use of tie-breakers. This counter belongs to an individual enqueue and establishes neither a database snapshot nor the order of worker completion.

Does a removed job recover its old place when re-added?

Decide what re-addition means first. The documentation shows marking the old entry removed and pushing a new entry. With a fresh counter on every push, re-adding a job puts it behind existing jobs at its priority. If A and B entered at priority five in that order, removing A and then adding it again gives B the next live position. The pop operation still needs to skip the marked entry.

Keeping the original place is a different policy. Preserve the original ordering data and ensure the old and new entries cannot both represent live work. Avoid changing a comparison field in place without restoring the heap invariant. An acceptance test should track the identities before removal, after re-addition and at the next claim. This case is a planned check, and the three local pops do not establish restart, concurrency or delivery behavior.
