Why does navigation use aria-current while tabs use aria-selected?

Follow navigation and manual tabs in notification settings to check current page, tab selection, and keyboard focus separately.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-12 · Estimated read 16 min
Translations
zh-CN en

Article

Key takeaways

  • Current page and tab selection belong to different sets.
  • Focus can move before selection in a manual tablist.
  • Check semantics, panel visibility, and keyboard operation together.

Settings highlights Notifications in the navigation and Email in the tablist. The first highlight marks the page you are on. The second identifies the panel that is showing. Use aria-current for the navigation position and aria-selected for tab selection. In a manual tablist, keyboard focus also needs its own state.

WAI-ARIA defines aria-current for the current item in a related set. A navigation link can use page for the current page, generally with one such item in that set. A progress indicator may instead use step. The state needs to follow the actual view. A bold link or a URL change does not assign the attribute for you.

The same standard defines aria-selected for selection on a supported widget. Within a tablist, the selected tab represents the displayed tabpanel. Associate each tab with its panel and update the panel when selection changes. Setting a new tab to selected while leaving the previous panel visible leaves the component in two conflicting states.

Move focus, then activate a tab

Suppose notification settings has Email and Text Messages panels. The design lets users explore tabs with the arrow keys before they activate one. The APG tabs pattern describes arrow and activation keys for this manual model. An automatic model would select a tab as it receives focus. Name the model before testing.

The complete HTML can be saved as a single local file. It has not been run with a browser or assistive technology. The links reopen the file with different page parameters. The native buttons handle activation through their click handler. A separate handler moves focus when the user presses an arrow key. Both panels contain plain text, so the sample makes each visible panel a tab stop.

<!doctype html>
<html lang="en">
<meta charset="utf-8">
<title>Settings</title>
<style>
[aria-current="page"], [aria-selected="true"] { font-weight: bold; }
:focus-visible { outline: 2px solid currentColor; outline-offset: 3px; }
</style>
<nav aria-label="Settings">
  <a id="notifications-link" href="?page=notifications" aria-current="page">Notifications</a>
  <a id="profile-link" href="?page=profile">Profile</a>
</nav>
<main>
  <section id="notifications">
    <h1>Notifications</h1>
    <div id="channels" role="tablist" aria-label="Notification channel">
      <button id="email-tab" type="button" role="tab" aria-selected="true" aria-controls="email">Email</button>
      <button id="sms-tab" type="button" role="tab" aria-selected="false" aria-controls="sms" tabindex="-1">Text messages</button>
    </div>
    <div id="email" role="tabpanel" aria-labelledby="email-tab" tabindex="0">Email settings</div>
    <div id="sms" role="tabpanel" aria-labelledby="sms-tab" tabindex="0" hidden>Text message settings</div>
  </section>
  <section id="profile" hidden><h1>Profile</h1></section>
</main>
<script>
const byId = id => document.getElementById(id);
const [navA, navB, notifications, profile, list, mail, sms, mailPanel, smsPanel] =
  ['notifications-link','profile-link','notifications','profile','channels','email-tab',
   'sms-tab','email','sms'].map(byId);
const tabs = [mail, sms], panels = [mailPanel, smsPanel];
let selected = 0;
const moveTabStop = index => tabs.forEach((tab, i) => { tab.tabIndex = i === index ? 0 : -1; });
function choose(index) {
  selected = index;
  moveTabStop(index);
  for (const [i, tab] of tabs.entries()) tab.setAttribute('aria-selected', String(i === index));
  panels.forEach((panel, i) => { panel.hidden = i !== index; });
}
for (const [index, tab] of tabs.entries()) tab.onclick = () => choose(index);
list.onkeydown = event => {
  const { key, target } = event;
  const current = tabs.indexOf(target);
  if (current < 0) return;
  let next;
  if (key === 'ArrowLeft' || key === 'ArrowRight') next = 1 - current;
  else if (key === 'Home') next = 0;
  else if (key === 'End') next = 1;
  else return;
  event.preventDefault();
  moveTabStop(next);
  tabs[next].focus();
};
list.onfocusout = event => {
  if (!list.contains(event.relatedTarget)) moveTabStop(selected);
};
if (new URLSearchParams(location.search).get('page') === 'profile') {
  navA.removeAttribute('aria-current');
  navB.setAttribute('aria-current', 'page');
  notifications.hidden = true;
  profile.removeAttribute('hidden');
}
</script>
</html>

Open Notifications and Tab into the Email tab. Notifications is current, and Email is selected and focused. Press Right Arrow. Focus moves to Text Messages while Email stays selected. Press Enter. Text Messages becomes selected, its panel appears, and the Email panel is hidden. The Notifications link remains current through all three steps. Follow the Profile link to change the current page and leave the Notifications component.

For a negative check, preserve bold styling with a separate class, then remove aria-selected from the tabs. A test of the visuals or panel content can still pass while the selection state is missing. Also check leaving the tablist before activating the focused tab. Tab should enter the visible Email panel in that state. On reentering the list, its selected tab should be the starting point. These are proposed tests for the manual model; they do not establish speech output from any screen reader.

Give each state an owner

A review can ask three different questions. Which page is showing? Which panel is selected? What would the next activation act on? The page renderer can manage navigation, the tab widget can manage panel selection, and the keyboard handler can manage focus. Styles can distinguish the three, for example with bold navigation, an underline for selection, and a visible focus outline. A generic active class is a poor sole source of truth.

If client-side navigation changes the view, use the same position rule on direct entry and history traversal. Changing a tab need not change the navigation position unless the design treats that tab as a separate page. Page titles and view identity covers how to identify a page outside its content. Here the question is how a user identifies a current item within navigation and a selection within a widget.

When running the check, record visible content, focused element, and attribute state at each step. Then observe the supported browser and assistive technology combinations. A mouse click and a screenshot will not reveal a missing keyboard focus indicator or prove how selection is exposed.

Can the same navigation tree have a current item and a selected item?

Yes, if the two states have distinct meanings. Imagine a tree that currently displays Activity A, while the user selects Activity B in preparation for opening it. A is current and B is selected. The current item changes when B is opened. WAI-ARIA gives a navigation-tree case with this distinction under aria-current. This time the states are in one set. Define when selection and activation occur before deciding when each attribute changes.
