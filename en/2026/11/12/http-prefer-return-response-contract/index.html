Why can a request with Prefer: return=minimal still return JSON?

Check two valid 201 replies to the same create request and handle response content and preference disclosure under the endpoint contract.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-12 · Estimated read 11 min
Translations
zh-CN en

Article

Key takeaways

  • A server can ignore a preference sent in Prefer.
  • Creation status and response size are separate parts of the contract.
  • Parse the response actually received under the endpoint contract.

The mobile client adds Prefer: return=minimal to a bookmark creation request and still receives JSON in testing. The server can ignore the preference. The client needs to handle the reply allowed by the endpoint, then inspect any statement about which preference the server applied.

RFC 7240 defines Prefer as a request for optional behavior. Section 4.2 defines two mutually exclusive return preferences. The minimal option asks for a minimal success reply. The representation option asks for a representation of the current resource state. A minimal response can still include information such as the location of a new resource. The preference does not fix a status code.

Accept two successful replies from the same endpoint

Suppose POST /bookmarks returns 201 and the new resource’s Location. This hypothetical endpoint allows either empty content or an application/json bookmark. Both replies refer to /bookmarks/9. A server can honor return=minimal and send just the location with Preference-Applied. Another deployment can ignore the request preference and include the default bookmark representation with ID 9 and title Guide.

This complete local Node fixture uses normalized lowercase header names and an already available body string. It neither sends HTTP nor validates wire framing. Its expected results follow from the two fixed replies: both return the same location, and only the second carries a resource object.

import assert from 'node:assert/strict';

const location = '/bookmarks/9';
const applied = {
  status: 201, headers: { location, 'preference-applied': 'return=minimal' },
  body: '',
};
const ignored = {
  status: 201, headers: { location, 'content-type': 'application/json' },
  body: '{"id":"9","title":"Guide"}',
};

function readCreated({ status, headers, body }) {
  const { location, 'content-type': type } = headers;
  if (status !== 201 || typeof location !== 'string' || !location)
    throw new Error('unexpected creation reply');
  if (body === '') return { location, resource: null };
  if (type !== 'application/json') throw new Error('unexpected media type');
  const resource = JSON.parse(body);
  if (typeof resource?.id !== 'string' || typeof resource?.title !== 'string')
    throw new Error('invalid bookmark');
  return { location, resource };
}

const results = [applied, ignored].map(readCreated);
assert.deepEqual(results, [
  { location: '/bookmarks/9', resource: null },
  { location: '/bookmarks/9', resource: { id: '9', title: 'Guide' } },
]);
const broken = ({ headers }) => ({ location: headers.location, resource: null });
assert.notDeepEqual(broken(ignored), results[1]);
console.log(JSON.stringify(results));

Check the creation status and location. If there is content, check its media type and structure. This fixture uses an exact match for application/json because the hypothetical contract calls for that literal value. A more general client needs its own rules for media type parameters and other permitted formats. An empty body is represented as an absent resource rather than an invented object. The negative parser discards content based on the requested preference and loses Guide even though the reply is valid.

A nonempty 201 with an unexpected media type, or a JSON object without an ID, would violate this example’s response contract. If a caller cannot use the returned object, keep the creation status and location available for recovery. A representation error after a write is a poor reason to repeat the POST blindly.

Decide what the caller can do with less content

A caller that only needs a success notice and a link may choose the minimal preference. An editing screen that needs a normalized title or server defaults might need the resource body. If it cannot continue without that information, an extra read can offset the saved response bytes. Decide when to follow the returned location and how to show the state if that read fails.

If the UI has a temporary local bookmark, the representation branch can reconcile the local item with the returned fields. An empty-content branch can keep the returned location and defer the server fields until it reads the resource. The caller should make that difference visible in its data contract. Handling a 204 with no content addresses the parsing rule after that status arrives. This case has two content shapes with the same 201 status.

An endpoint integration check could hold the creation input constant and exercise both the applied and ignored paths, using distinct request identities when sending writes. Check the location, what the caller does with any returned object, and whether a follow-up read is needed. The local example exercises only response handling.

Does an empty 201 without Preference-Applied mean the preference was ignored?

No. This time the response still has empty content and a location, but no statement about application. RFC 7240’s Preference-Applied field can declare which preference the server used. Its absence leaves open whether empty content was the default or the result of the preference. Unless the endpoint specifies a reliable signal, process the actual empty reply while leaving application of the preference undetermined.
