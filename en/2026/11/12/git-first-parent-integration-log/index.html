Why does git log --first-parent omit commits that were merged?

Compare two logs from a pinned merge tip and check feature ancestry independently.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-12 · Estimated read 11 min
Translations
zh-CN en

Article

Key takeaways

  • A first-parent walk preserves the integration view.
  • A regular ancestry walk can expose the feature commits behind a merge.
  • Record the inspected object IDs and ordered parents so the report can be reconstructed.

The release log shows a merge but skips the two commits it brought in. Check whether the command used --first-parent. A regular log can follow the parents on both sides of the merge. With this option, it follows only the first parent. The side-branch commits remain reachable through the other parent.

Read the parent order of the merge

Consider a small history. The main branch goes from baseline B through a notes change N to merge M. The feature branch starts at B and adds F1 and F2. The merge is made while main is checked out, so M has N as its first parent and F2 as its second. For a real merge, inspect the recorded parent order. Today's branch names do not tell you the direction of an earlier merge.

Walking all parents from M can reach B through N and also reach it through F2 and F1. B is a single commit even though both paths lead to it. The first-parent walk from M follows N back to B. Its membership is M, N and B. Both queries start from the same object. This example leaves out path filters and excluded ranges so the parent traversal is the only difference. Git log commit selection

A release note can use M to describe the integration. An audit may need the objects F1 and F2 to trace specific changes. Those questions call for different views of the same graph.

Compare the logs from a pinned tip

This proposed example uses a new temporary repository and a Git version that supports git init -b. The branches write separate files, keeping conflict resolution out of the comparison. The commands were not run for this article. The expected members below come from the declared graph.

set -eu
repo=$(mktemp -d)
cd "$repo"
git init -q -b main
git config user.name "History Probe"
git config user.email "probe@example.test"

printf 'baseline\n' > baseline
git add baseline
git commit -qm B
git branch feature

printf 'release notes\n' > release-notes
git add release-notes
git commit -qm N

git switch -q feature
printf 'first change\n' > feature-changes
git add feature-changes
git commit -qm F1
printf 'second change\n' >> feature-changes
git add feature-changes
git commit -qm F2
feature_tip=$(git rev-parse HEAD)

git switch -q main
git merge --no-ff -qm M feature
tip=$(git rev-parse HEAD)
git show -s --format='%h %P %s' "$tip"
git log --format='%s' "$tip"
git log --first-parent --format='%s' "$tip"
git merge-base --is-ancestor "$feature_tip" "$tip"

Compare membership rather than output order. The first log should contain B, N, F1, F2 and M. The second should contain B, N and M. The ancestry check should exit zero. Save the inspected tip, feature tip, ordered parents and both lists together. If a command fails, retain its diagnostic before interpreting a missing entry.

N is deliberately independent of the feature. It makes the expected result distinguish two cases: feature commits are omitted from the first-parent walk, while a direct mainline change stays visible. Deleting the feature branch name after this merge would leave the recorded parent edge intact. Record the pinned tip when preparing a release note so the result can be reconstructed later.

Match the evidence to the release question

For a release summary, start with integration points and direct mainline changes. For a question about whether a particular object entered the history, test its ancestry from the same release tip and link that evidence to the relevant entry. Squash workflows may record the integration as a new ordinary commit while leaving the original feature objects outside the target ancestry. Trace the squash result using the project's actual change records.

Timing can introduce a different failure. If the release tip moves between the two commands, a count difference might simply reflect new commits. Pinning the tip avoids that ambiguity. Confirm that the required objects and parent chains are present locally before drawing conclusions about old history. Where a fix was later reverted, inspect the current tree and behavior separately. Checking commit ancestry and present content

For a release record that also supports audits, keep the merge object, the main tip before the merge and the feature tip. A test for the release-note generator can check that N and M appear in its integration view. A separate check can confirm that F2 is reachable from M. Recording the path filters matters too, since a file-limited query introduces history simplification that the example deliberately omits.

Why can adding -p also change the patch shown for a merge?

Under the ordinary defaults, git log -p omits merge diffs. With --first-parent, the default merge diff format is first-parent. In the example, that patch compares N with M. It still does not create individual log entries for F1 or F2. Compare the merge with its first parent using git diff M^1 M, substituting a real merge reference for the diagram label. Use --diff-merges=off when the release list should contain only the textual integration entries. Include the Git version and options with a patch-based report. Git log merge diff formats
