Who can settle a promise created with withResolvers?

A one-shot import receipt separates waiting from settlement and checks two readers, duplicate notifications, and rejection with deterministic assertions.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-12 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • Create a separate promise for each receipt and pass reader and owner interfaces by role.
  • The resolving functions of an ordinary promise share one decision state.
  • The surrounding module owns subscription, cleanup, and failure notification.

Two parts of a page wait for the same import receipt. The badge needs to await it. If it also receives resolve, it can publish a success to the history panel before the import owner has a result. When using withResolvers to wrap a one-shot callback, give readers the promise and keep the resolving functions inside the module responsible for that import.

Give the reader and the owner different interfaces

ECMAScript’s withResolvers creates a promise capability and puts its promise, resolve, and reject in the result object. The examples use the built-in Promise constructor. Compared with saving two functions from a constructor executor, this form makes the capability easier to retrieve. The surrounding code still decides who may use it.

Suppose an import page updates a badge and an operation history. Both can wait on the same receipt, then attach different rendering work. An error in one rendering chain belongs to that chain. The renderer has no need to reject the underlying import. Two readers can agree on one outcome without being given permission to decide it.

The import adapter owns the result of the factory. It keeps the second entry and passes only reader to the consumers. Freezing reader in this example fixes its public shape. It neither freezes the promise’s internal state nor retracts resolving functions that have already been shared. In a review, follow the actual objects passed to the badge and history. A neatly named property does little if both consumers still receive the full factory result.

Check the two waiters and the duplicate notification

The fixture uses fixed local values. Both waiters attach before the first notice. They should receive A17, even though a failure notice follows. A separate receipt attaches a rejection assertion before receiving an error and then attempts to overwrite it with B99. These expectations come from the specified call order and the resolving rules. No request timing is needed.

import assert from 'node:assert/strict';

function openReceipt() {
  const { promise, resolve, reject } = Promise.withResolvers();
  return [Object.freeze({ promise }), { succeed: resolve, fail: reject }];
}

const [reader, { succeed, fail }] = openReceipt();
const { promise: first } = reader;
const forBadge = first.then(value => value);
const forHistory = first.then(value => value);
succeed('A17');
fail(new Error('duplicate'));
const both = await Promise.all([forBadge, forHistory]);
assert.deepEqual([Object.keys(reader), both], [['promise'], ['A17', 'A17']]);

const [{ promise: second }, next] = openReceipt();
assert.notEqual(first, second);
const failure = new Error('input is incomplete');
const rejected = assert.rejects(second, err => err === failure);
next.fail(failure);
next.succeed('B99');
await rejected;

const [exposed, wrongOwner] = openReceipt();
const { succeed: anyoneCanSucceed } = wrongOwner;
anyoneCanSucceed('too early');
anyoneCanSucceed('A17');
assert.equal(await exposed.promise, 'too early');
console.log('A17 A17; second rejected; exposed resolved too early');

CreateResolvingFunctions gives the two resolving functions shared decision state. In the first run the ordinary string is accepted before the failure arrives. In the second run the failure is accepted first. Calling a function says little about whether it changed the result; observe the promise. The rejection assertion checks the identity of the Error so an unrelated exception cannot pass the check.

The last branch deliberately gives the consumer access to the success function. The early value wins even though the owner subsequently offers the actual receipt number. This is a local demonstration of an interface mistake. The Promise API enforces the decision order; the adapter needs its own rule for which code can issue a decision and which import a callback belongs to.

Keep ownership through the whole wait

Create a separate receipt for each import. If a callback from the previous import can arrive after the next starts, capture the previous owner in its closure. If the library reports every result through the same callback, check the task identity at the adapter before making a decision. A single global resolve variable is easy to overwrite, even if every individual promise was created correctly.

Some callback APIs can report a result while the handler is being registered. Create the receipt before subscribing. The adapter also needs a cleanup rule and a policy for a callback that never arrives. Rejecting a local promise can inform the waiters; it does not stop work in the callback provider. The fixture does not connect to an importer or modify any file.

A continuing notification stream needs a separate interface. One promise may represent its first useful notification, but subsequent events still need somewhere to go. Sending all of them to one resolve function will discard events after the first decision. Promise.any and usable candidates addresses the later choice among independent candidates; this example concerns the owner of one candidate.

Can reject win after resolve receives a pending promise?

No. This time the input is a pending inner promise instead of a string. The outer promise has adopted the inner outcome, but cannot fulfill or reject until that outcome is available. A subsequent call to the outer reject cannot take over the already made choice.

import assert from 'node:assert/strict';

const { promise: outer, resolve: adopt, reject: cancel } = Promise.withResolvers();
let deliver;
const inner = new Promise(resolve => { deliver = resolve; });
adopt(inner);
cancel(new Error('too late'));
deliver('receipt from inner');
assert.equal(await outer, 'receipt from inner');
console.log('outer adopted inner');

If the adapter is meant to decide the final outcome itself, check what a promise passed to resolve represents. Adopting pending work hands the outcome to that work. Apply any deadline or outcome selection required by the adapter before handing a result to its waiters.
