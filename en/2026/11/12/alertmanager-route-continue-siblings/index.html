Why does Alertmanager choose one receiver when two routes match?

Trace four label sets through ordered child routes and see when Alertmanager falls back to the root receiver.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-12 · Estimated read 10 min

Article

Key takeaways

  • Continuation is controlled by the child that matches.
  • Test both the overlap and the unmatched input.
  • Verify notification delivery separately from receiver selection.

The alert matches both team=payments and severity=critical. Route order determines whether Alertmanager evaluates the second sibling.

The payments team already receives its alerts. The on-call team adds a severity route so it can receive critical alerts too. Yet a critical payments alert still selects only the payments receiver. Testing the matchers individually confirms that both accept the same labels. To explain the result, trace which nodes Alertmanager actually visits.

Follow the route tree in order

A parent checks its children in configuration order. When a child matches, Alertmanager processes that branch. The matching child’s continue field controls whether the search then visits later siblings. The default is false, so the sibling search ends at that branch. With continue: true, the next sibling still has to match on its own terms. Alertmanager routing configuration

The parent handles the alert if none of its children match. In the two-level tree below, each child is a leaf, so you can read the receiver directly from each matched branch. With both children selected during traversal, the parent has no fallback work to do.

Compare four inputs against two configurations

Save this example as route.yml. The receivers are names only. That keeps the exercise focused on selection and avoids any connection to a real notification destination. Check the documentation for the installed version before taking the matcher syntax into an existing instance.

route:
  receiver: fallback
  routes:
    - receiver: payments
      matchers:
        - 'team="payments"'
    - receiver: critical
      matchers:
        - 'severity="critical"'
receivers:
  - name: fallback
  - name: payments
  - name: critical

Use the original file for the first column of expected results. For the second, add continue: true to the payments route at the same indentation as its receiver. Leave every other line alone. These are results derived from the documented routing rules. The example was not run against an Alertmanager instance or a route-testing command.

Input labels Original receiver selection Selection after the change
team=payments, severity=critical payments payments and critical
team=payments, severity=warning payments payments
team=search, severity=critical critical critical
team=search, severity=warning fallback fallback

The overlap in the first row exercises the changed path. The second row checks that traversal can continue without adding a receiver whose condition fails. The third reaches the severity route because the first child never matches. The last row protects fallback behavior. If you check only the first row, accidentally removing the severity matcher could still give you both names. The extra alert for a routine payments warning would surface later.

Now return to the original configuration and reverse the order of the two children. The overlap selects only critical. Turning on continuation for the payments route in that position has no effect on this input because the earlier severity route ends the search. This makes a useful regression case when separate people maintain team routes and cross-team escalation routes. The same labels expose a change in which branch wins after someone inserts a broader rule near the top.

Decide who should receive the overlap

If the severity route owns escalation exclusively, put it first and keep its default stopping behavior. Check a payments warning to verify the team still has its own path. If both teams should handle the critical alert, preserve the payments route first and let the search continue through its siblings. Before editing the production configuration, write down the expected receiver set for each label combination.

Then return to the evidence that started the investigation. When the selection already contains both names, follow the grouping and delivery evidence for the receiver that missed the notification. The names in this exercise have no external integrations. To verify delivery you need separate evidence from a configured destination. If you suspect the alert resolved while a notification group was waiting, see why a short alert can disappear during group wait.

What if the first matching route is in a mute interval?

A route with mute_time_intervals still behaves normally during matching and ends the sibling search unless it has continuation enabled. The interval suppresses notifications from that route. In the original configuration, the later severity branch still goes unvisited if the payments route matches during maintenance. If the on-call team is expected to handle the overlap during that window, test that particular input and check both the later route’s selection and its notification behavior.
