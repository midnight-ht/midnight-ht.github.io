Why does SQLite reject ORDER BY lower(name) after UNION ALL?

Trace SQLite compound sort terms to result columns using three executed queries and an alias-resolution follow-up.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-12 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • A compound sort term resolves to a result column.
  • An outer simple SELECT can sort by an expression while preserving the output shape.
  • SQLite searches branches from left to right for a matching alias.

A simple SQLite SELECT can sort by lower(name). Once UNION ALL combines multiple SELECT statements, the final ORDER BY follows the compound-query rules. A sort term can identify a result column by position or alias, or match an output expression. If the compound projects only name, wrap the union in a simple SELECT before sorting by lower(name).

Consider a local directory that merges cached and freshly imported names. Both branches can compute lower independently. After the merge, a sort term can fail even though every name is present. The relevant change is the query level that owns the sort.

Identify the sort’s query level

The SQLite SELECT reference permits arbitrary sort expressions in a simple SELECT. A compound query resolves sort terms as result columns. A positive integer can designate a column position. A matching output alias names a column. Another expression needs to match a constituent result expression. Projecting name alone does not turn every computation over name into an output term.

Switching lower to upper or normalizing stored values does not resolve an unmatched output expression. If the product merely wants to sort by the existing name column, use that column. If it needs transformed display order, choose where the transformation belongs.

A secondary ordering rule still matters when transformed values tie. This fixture uses the original name with BINARY collation and ASCII input. For a locale-specific directory, verify the comparison rules of the application’s actual connection.

Run the same inputs through three query shapes

The three teaching queries ran against an in-memory SQLite 3.53.1 database through Python 3.11.15’s sqlite3 module. Build the tables in a disposable in-memory database. Treat the first SELECT as a separate expected failure, then run the two positive cases against the same data. A client that stops at the first error will need separate submissions.

CREATE TABLE cached(name TEXT NOT NULL);
CREATE TABLE incoming(name TEXT NOT NULL);
INSERT INTO cached VALUES ('beta'), ('Alpha');
INSERT INTO incoming VALUES ('alpha');

SELECT name FROM cached
UNION ALL
SELECT name FROM incoming
ORDER BY lower(name);

SELECT name
FROM (
  SELECT name FROM cached
  UNION ALL
  SELECT name FROM incoming
) AS merged
ORDER BY lower(name), name COLLATE BINARY;

SELECT name, lower(name) AS sort_key FROM cached
UNION ALL
SELECT name, lower(name) AS sort_key FROM incoming
ORDER BY sort_key, name COLLATE BINARY;

The first query should reject the unmatched sort term. The outer-query version should return one column with Alpha, alpha, beta in order. The first two lowercase values tie, and the secondary BINARY comparison places uppercase A first. The projected version should return the same name order plus sort_key values alpha, alpha, beta. Compare the entire rows and column names rather than merely checking a visually sorted list.

Choose the wrapper when a consumer must receive the original column shape. Project the key when downstream code genuinely needs to inspect it. Keep the final ORDER BY on the output query so the consumer’s order does not depend on a branch scan.

With UNION rather than UNION ALL, changing the projected columns changes what the engine compares when removing duplicates. A deterministic sort key derived from an existing value need not split duplicate rows, while a new branch identity could. The site’s union and row identity article develops that separate contract. The fixture keeps UNION ALL to isolate compound sort resolution.

Verify columns alongside row order

A position-based client can be affected by an added field even when every visible name stays in the same order. Give the two positive cases separate column and row expectations. An outer projection can keep a single public name column while using the expression internally to sort it.

An adapter that catches a database error and retries without sorting needs a separate check. Preserve the original error, then independently confirm that the unsorted union still contains the same three rows. Compare that control as a multiset. A successful unsorted fallback leaves the display order unspecified. Check the positive cases against the ordered oracle and preserve the actual error for the negative case.

Record the SQLite version and execution entry point. A command-line client and an application may embed different builds. Capture the exact submitted SQL and its actual error before attributing a problem to the database or a wrapper. The archived assertions cover the first error type and the two successful results, including column names and ordered row values. The adapter fallback and the alias follow-up remain unexecuted.

Which column wins when branches use the same alias in different positions?

SQLite searches compound SELECT branches from left to right for a matching non-integer sort term. Consider a left branch SELECT 2 AS k, 1 AS b and a right branch SELECT 1 AS a, 2 AS k, combined with UNION ALL and a final ORDER BY k. The left branch’s k matches the first column, so the row with first value one should precede the row with first value two. The right branch’s k does not give its row a separate second-column sort.

Give result columns distinct and consistent aliases, or expose an explicit name at the outer query. When adding another branch, verify that the chosen sort term still resolves to the intended position. This checks a successful name match with an unexpected binding, distinct from the unmatched expression in the original failure.
