Why does an asyncio task read the old ContextVar value?

Use an executed event-gated fixture to separate asyncio task creation, context copying, and the later read.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-14 · Estimated read 9 min
Translations
zh-CN en

Article

Key takeaways

  • The default context is copied at task creation.
  • Rebinding a parent variable leaves the child’s copied binding alone.
  • Mutable values need a separate ownership decision.

By default, asyncio copies the current context when it creates a task. A later ContextVar rebinding in the parent does not change the child’s copied binding, even if the child has not read it yet. Create work after setting the intended binding, or pass a deliberate context.

Suppose a service keeps a request ID in a context variable. It creates a background task and then changes the ID in the current request. The background task waits before recording anything, yet it still reads the earlier ID. Look at the binding where create_task ran. The log time tells you when a read happened and cannot identify the context by itself.

Gate the read without a sleep

The asyncio reference says create_task copies the current context when no explicit context is supplied. Creating a coroutine object is separate from creating a task for it. The fixture’s binding is tied to task creation. Python 3.14 asyncio Tasks.

The following program ran on Python 3.11.15. The parent sets A and creates a task, then sets B before releasing an event. The child reads only after that event. A second task is created while the parent already has B, giving an independent control.

import asyncio
from contextvars import ContextVar

request_id = ContextVar("request_id")

async def read_when_ready(gate):
    await gate.wait()
    return request_id.get()

async def main():
    gate = asyncio.Event()
    first_token = request_id.set("A")
    try:
        first = asyncio.create_task(read_when_ready(gate))
        second_token = request_id.set("B")
        try:
            gate.set()
            first_value = await first
            parent_value = request_id.get()
            second = asyncio.create_task(read_when_ready(gate))
            observed = (first_value, parent_value, await second)
            assert observed == ("A", "B", "B"), observed
            print(observed)
        finally:
            request_id.reset(second_token)
    finally:
        request_id.reset(first_token)

asyncio.run(main())

Expect A from the first task, B in the parent, and B from the second task. The archive records all three observations and the exact code. The event makes the read order explicit without assuming how fast the machine schedules the coroutine. These observations concern one local event loop and do not verify worker threads, processes, HTTP middleware, or a logging service.

Choose what the task should inherit

When a task represents the current request, put task creation after setting the request identity. If background work needs information that will only be known later, pass the value to a later stage as an argument or delay creation of the task that needs it. Arguments make a cross-system handoff visible. A context variable is useful for helpers that share a binding within the execution.

Python 3.11 and later also let create_task accept a context argument. Choose the background task’s scope explicitly if it should carry a different set of values. The fixture does not exercise that option or reuse one custom context across tasks. The related TaskGroup failure article examines which tasks are awaited and canceled. The issue here is where a task’s binding comes from.

An application can add a control in which both records are emitted after the parent changes the value. Check that each record still belongs to the right request. Simply checking that both records contain an ID would miss attributing everything to the latest request. Observe the function that actually reads the value and the final log that uses it. That application check was not run.

To isolate coroutine construction from task creation, construct a coroutine under A, create its task under B, and let it read only after the parent has set C. It should read B. A separate worker-loop check can also fail one job deliberately and verify that the parent’s temporary binding is restored before the next job. These additional checks were not run.

What if the ContextVar holds a list and the parent appends to it?

A context copy is shallow. If both bindings refer to the same list, appending to that list before releasing the gate can be visible in the child. Rebinding the parent to a new list is a separate case. Compare object identity and contents in two independent tests. Use an immutable value or make an independent object at handoff when a stable snapshot is required. The main program uses immutable strings. This list probe was not run. Python contextvars.
