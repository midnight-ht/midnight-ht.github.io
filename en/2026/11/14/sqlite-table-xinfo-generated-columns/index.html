Why does a SQLite schema diff miss a generated column?

Use a tested SQLite fixture to distinguish generated values from two different schema inventories.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-14 · Estimated read 9 min
Translations
zh-CN en

Article

Key takeaways

  • The table_info inventory omits generated columns.
  • Use the complete inventory to inspect column names and hidden values.
  • Schema visibility and writable fields have separate contracts.

A SQLite SELECT can read a generated column that PRAGMA table_info leaves out. Use table_xinfo when the migration check needs a complete column inventory. Interpret its hidden field according to what the tool needs to verify.

Suppose an inventory migration adds a derived quantity. The application displays the new value, but a deployment script reports a missing column. The script built its supposedly complete inventory with table_info. Check the generated value and the table definition through separate observations before rerunning the migration.

Know what the inventory covers

SQLite documents that table_info omits generated columns and hidden columns of virtual tables. The broader table_xinfo includes them and adds the hidden field. Ordinary columns have value zero, generated columns use two or three, and a virtual-table hidden column has value one. The fixture is an ordinary temporary table with virtual and stored generated columns. A virtual generated column is a different feature from a hidden field of a virtual table. SQLite PRAGMA reference.

Generated columns are available from SQLite 3.31.0. Virtual and stored columns compute at different times. Both are omitted from table_info. Keep the inventory name and engine version with a schema report. Comparing counts alone misses a wrong name and may fail to detect any newly added generated column. SQLite Generated Columns.

Make three observations against one table

The following SQL ran in an in-memory SQLite 3.53.1 database through Python 3.11.15’s sqlite3 module. The archive checks the selected values, ordinary column names, and full inventory’s name/hidden pairs. It does not test an application driver or migration runner.

CREATE TEMP TABLE stock (
    id INTEGER PRIMARY KEY,
    qty INTEGER NOT NULL,
    doubled INTEGER AS (qty * 2) VIRTUAL,
    tripled INTEGER AS (qty * 3) STORED
);
INSERT INTO stock (id, qty) VALUES (9, 4);

SELECT id, qty, doubled, tripled FROM stock;
PRAGMA temp.table_info(stock);
PRAGMA temp.table_xinfo(stock);

The SELECT should return ID nine, input four, and generated values eight and twelve. The narrower inventory gives id and qty. The wider one adds doubled and tripled. In this run, their hidden values were zero, zero, two, and three respectively. Check each name with its marker. Finding two generated columns alone would not detect an unintended change in their roles.

If the real tool uses another connection, verify the database file, schema, and table. A console that can query the generated value may be using a different connection or database. The fixture qualifies its temporary schema and does not exercise multi-connection configuration.

Preserve column roles in the diff

A structure report can compare names, declared types, and generated roles separately. If doubled should be computed on read and tripled on write, the two columns need their own expectations. A later ordinary column should stay in a different category. The fixture checks two derived values for one input. A real migration also needs acceptance checks for the values and writes it changes.

Choose separate projections for a read model and an importer. The former can expose derived fields. The latter should use a deliberate writable list. An ordinary column can also have a default or a business restriction. A complete inventory gives the tool the data to make those decisions. The related PostgreSQL generated-column article concerns a different engine’s DDL policy.

For a deployment diagnostic, run the old and new inventories against the same schema. If only the old one misses the generated columns, the observation fits the documented omission. If both miss them, check the actual migration and database file. That application-level comparison is unexecuted.

Can the full list become the INSERT column list?

Generated columns obtain their values from an expression and cannot be written directly. In a fresh test table, try an insert that assigns doubled and expect rejection. Then insert through id and qty and expect the generated value to remain readable. Apply the business allowlist after excluding generated columns. This follow-up was unexecuted. The archived fixture only runs the base-column insert and three reads.
