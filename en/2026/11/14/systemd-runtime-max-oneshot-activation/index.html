Why doesn’t RuntimeMaxSec stop a stuck systemd oneshot?

Use three systemd service configurations to separate activation timeout from a limit on active runtime.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-14 · Estimated read 9 min
Translations
zh-CN en

Article

Key takeaways

  • A one-shot command runs as part of activation.
  • Use the startup timeout to bound that command.
  • Distinguish the start command’s exit from later unit failure.

The one-shot command runs during activation. Use TimeoutStartSec to bound that work. Systemd’s RuntimeMaxSec limits time spent active and has no effect on the execution of a Type=oneshot command.

A release task is supposed to finish within a fixed window. An operator sets a short runtime limit, but the process keeps waiting. Check the unit’s state before shortening the limit. The manager may still be waiting for startup. For a one-shot command, the process can exist throughout activation.

Change one decision for each test unit

The systemd manual applies the runtime limit after the service becomes active. Exceeding it terminates the service and puts it into a failure state. A one-shot command belongs to activation. Use the startup timeout for that phase, and note that the startup timeout defaults to disabled for oneshot services. The example follows the systemd 262 reference. systemd.service reference for RuntimeMaxSec

Save the complete definition below under three distinct test unit names on an isolated Linux machine. Its only work is an eight-second sleep. This lab was not executed. The selected values make the expected outcomes easy to distinguish.

[Unit]
Description=Activation and runtime limit lab

[Service]
Type=oneshot
ExecStart=/bin/sleep 8
TimeoutStartSec=12
RuntimeMaxSec=2
Restart=no

Keep the original for activation-control. For activation-timeout, change only the startup timeout to two seconds. For active-timeout, start from the original and change only the type to simple.

Unit After the command starts Expected outcome
activation-control The one-shot command is still activating Sleep finishes normally and the unit need not remain active
activation-timeout The one-shot command is still activating Startup times out and the unit fails
active-timeout The simple service becomes active Its runtime limit expires and the unit fails later

Install the definitions, reload the manager and start each unit separately. Observe its state in another terminal and review that unit’s journal for the end reason. If you start without waiting for the job, observe the final job state separately. The start command for the simple service can succeed before the unit fails on its active runtime limit.

Check that the executable and actual unit definition match the fixture. A missing executable can also fail the service. It cannot establish that either timer fired. The two timeout paths may have a similar terminal state, so retain the preceding stage and the manager’s reason.

For each test unit, capture ActiveState, SubState and Result with systemctl show and retain the unit journal. A brief state transition can pass between polls. If the control is still running when observation stops, leave that row incomplete until the command finishes.

Choose the limit from the operational promise

A one-shot migration, warm-up or export preparation can use a startup limit. Decide how to handle partial writes when time expires. A manager timeout does not establish what happened in the application. A long-running service might instead need a limit on one continuous active period. These are different contracts even if the durations match.

Record the loaded unit, relevant state transitions and the journal before comparing runs. This fixture disables automatic restarts to make one invocation visible. If a real service restarts, distinguish the failed process from the next activation. See why a reload command can return before settings apply for a separate completion boundary. After the exercise, stop the dedicated units, remove their test definitions and reload the manager.

Can several long-running services stagger their runtime limits?

On versions supporting RuntimeRandomizedExtraSec, it adds a uniformly distributed duration to an existing runtime limit. The option has no effect without a configured base limit. A separate experiment could observe the resulting range across starts, without requiring distinct times on every run. It does not turn the setting into a one-shot activation deadline. The lab above did not configure or exercise this variant. systemd.service reference for RuntimeRandomizedExtraSec
