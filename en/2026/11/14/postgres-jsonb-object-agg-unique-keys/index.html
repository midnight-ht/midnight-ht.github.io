Why did two PostgreSQL rows turn into one JSONB key?

Use two groups of settings to distinguish PostgreSQL JSONB aggregation order, duplicate rejection, and strict mode.

Key takeaways

  • Ordinary aggregation keeps the last processed value for a key.
  • Unique aggregation rejects repeated keys within a group.
  • Choose the collision policy from the output contract.

PostgreSQL’s jsonb_object_agg collapses repeated keys, keeping the last value it processes. If each object key must have exactly one source row within its group, use an aggregate that rejects duplicates and retain enough input identity to investigate the error.

Suppose a settings API builds one JSONB object per department. Department 1 has two color settings, red and blue. Department 2 has a green color setting. The intended rule permits one color per department. A successful query that returns two objects can still hide the first department’s conflict. The output key count cannot stand in for the source rows.

The aggregate input determines the last value

PostgreSQL 18 documents that object keys are coerced to text. The ordinary JSONB aggregate keeps only the last value for a repeated key. If the business explicitly wants the last change to win, order inside the aggregate and resolve any ties. An outer ORDER BY arranges department rows. It does not define the order of the values fed into the aggregate. When a collision is an error, make it fail rather than choosing an arbitrary winner. PostgreSQL 18 aggregate functions.

The same key can appear in two departments because the rows go into separate objects. Define the grouping and the key expression together. This fixture already uses text keys. A real key expression might convert several source identifiers into the same text.

Give three outcomes their own checks

The following PostgreSQL teaching statements are unexecuted. A temporary table holds two departments and three source rows, with distinct sequence numbers within each department. The first query deliberately uses the last value. The second provides a successful unique-mode control with the same key in two separate groups.

CREATE TEMP TABLE settings (
    department int,
    seq int,
    name text,
    value text
);
INSERT INTO settings VALUES
    (1, 1, 'color', 'red'),
    (1, 2, 'color', 'blue'),
    (2, 1, 'color', 'green');

SELECT department, jsonb_object_agg(name, value ORDER BY seq) AS payload
FROM settings
GROUP BY department
ORDER BY department;

SELECT department, jsonb_object_agg_unique(name, value) AS payload
FROM settings
WHERE department <> 1 OR seq = 1
GROUP BY department
ORDER BY department;

Expect blue and green by department in the first query. Expect red and green in the unique-mode control. For the independent rejection test, repeat the second query without its WHERE clause and keep its grouping intact. Department 1’s duplicate color should fail. Record the actual server version, error code, and source identifiers if you run it. Do not expect a successful set of objects from the failed statement.

Compare each department and its key-value pairs. Returning two objects alone cannot establish which inputs were aggregated. An unintended join can add a duplicate whose value happens to match the correct result. Count source rows by group and key before aggregation. A unique aggregate can expose the duplicate without proving that all joins are correct.

Choose an explicit collision policy

If the contract requires one source per key, use the unique aggregate and look up offending input groups after an error. If consumers need every source row, a list can preserve that information. If the business truly says the latest value wins, ordinary aggregation can implement it using a stable tie-breaker. A passing query only shows how the chosen policy behaved on its input.

Try two source rows with the same value as another negative control. Comparing the final JSON cannot detect a collapse when both values match. Retain source identities in diagnosis. The related JSON duplicate-member article handles objects before parsing. This case builds an object from relational rows.

A failed statement and a subsequent diagnosis are separate observations. Handle the application’s transaction outcome before inspecting its source groups. Also test what the interface should return for a department with no settings. That empty-input contract does not change the duplicate policy. No SQL or API integration was run here.

Can strict unique mode omit null values and still reject duplicates?

In PostgreSQL 18, jsonb_object_agg_unique_strict skips pairs with SQL NULL values while rejecting repeated keys, including pairs with null values. Start with color set to green and memo set to SQL NULL. Expect ordinary unique mode to retain memo as JSON null and strict unique mode to omit the key. Add a non-null memo row in a separate run. The strict unique aggregate should now fail for the duplicate. These unexecuted controls distinguish skipping a value from checking its key.
