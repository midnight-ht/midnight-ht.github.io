Does HTTP 416 plus the current length mean the download is complete?

Use two equal-length files to interpret the current representation length in HTTP 416 and test what evidence a download still needs.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-14 · Estimated read 10 min
Translations
zh-CN en

Article

Key takeaways

  • A bytes */N field in 416 gives the current selected representation length.
  • Equal local length still needs representation and content evidence.
  • Without Content-Range, keep the current length unknown.

The local file already has eight bytes. A resume request starts at offset eight and receives HTTP 416 with Content-Range: bytes */8. The field gives the current selected representation’s length. It explains why there is no ninth byte to read, but it cannot establish that the client has the right eight bytes.

Interpret the length after the asterisk

RFC 9110 defines 416 for rejected range requests, including unsatisfiable ranges. Consider one valid open-ended byte range. A representation eight bytes long has positions zero through seven. The request bytes=8- starts outside that extent. A server can ignore Range and return a full response, so the client still needs to read the actual reply.

The Content-Range field uses this unsatisfied-range form to convey the representation length. It does not identify an interval of representation bytes carried by the error response. Do not append an error body to the local file. The sample compares identity-coded byte lengths. A system with more than one coding or variant needs to bind its measurements to the selected representation.

An address can begin serving a different file of the same size. A damaged write can also leave a file at the expected length. The number in the response does not distinguish either case from a complete copy.

Compare two eight-byte files

This complete local Node example uses a fixed status and header object. It sends no HTTP. A trusted teaching value, ABCDEFGH, is available in advance. The first local file matches it, the second replaces one byte, and the third is longer. Only the first is both the expected length and the expected content. The regular expression accepts the limited example’s field shape rather than serving as a general HTTP parser.

import { deepEqual } from 'node:assert/strict';

const reply = { status: 416, contentRange: 'bytes */8' };
const trusted = Buffer.from('ABCDEFGH', 'ascii');
const correct = Buffer.from('ABCDEFGH', 'ascii');
const wrong = Buffer.from('ABCDEXGH', 'ascii');
const longer = Buffer.from('ABCDEFGHI', 'ascii');

function inspect(bytes, { status, contentRange }) {
  if (status !== 416) throw new Error('expected fixture status 416');
  const field = /^bytes \*\/(\d+)$/.exec(contentRange);
  const length = field ? Number(field[1]) : null;
  const sizeMatches = length === bytes.length;
  return [bytes.length, length, sizeMatches, sizeMatches && bytes.equals(trusted)];
}
const report = [correct, wrong, longer].map(file => inspect(file, reply));
deepEqual(report, [
  [8, 8, true, true],
  [8, 8, true, false],
  [9, 8, false, false],
]);
console.log(JSON.stringify(report));

Both eight-byte inputs pass the size check. The second fails the byte check. The longer file cannot be assumed correct after truncation either. A real downloader may not have an expected copy of the full file. It can use other evidence under its own contract, such as a confirmed representation validator together with verified local coverage, or a trusted integrity value. If that evidence is missing, preserve the distinction between a matching size and verified completion.

The fixture supplies expected bytes independently from the files being checked. If the implementation uses a digest, test the source of the expected value as well as the local computation. Exercise both equal-length inputs so a size-only pass cannot hide corruption.

Use the response actually received

A full response belongs in the replacement path. A partial response needs a matching starting position and representation identity. With 416, keep the reported current length and requested range, then check whether local evidence supports completion. Representation identity during download resume addresses appending versus replacing. The additional question here is what the current-length field establishes after a request reaches beyond the boundary.

A production check can cover verified full local coverage, equal size with uncertain identity, and a file larger than the current representation. Separately compare a persisted progress record with the bytes actually on disk. If progress says eight but only seven were written, a new request cannot use the old progress indicator as its only evidence.

Can a cached size stand in for a missing Content-Range on 416?

Keep the current length unknown. Remove the field from the earlier fixture and the client still knows the requested range was rejected, but it has no new length from that reply. The specification recommends the field for a byte-range 416. Obtain fresh representation metadata where the endpoint provides it, or use the full retrieval path. A historical size does not confirm this response’s representation.
