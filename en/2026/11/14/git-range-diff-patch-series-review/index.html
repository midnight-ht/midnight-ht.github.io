Every Git commit ID changed. Which patch actually changed?

Compare two fixed Git ranges to distinguish a new commit identity from a changed patch.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-14 · Estimated read 10 min
Translations
zh-CN en

Article

Key takeaways

  • Give each series its own baseline.
  • Patch pairing can identify equivalent work after object IDs change.
  • Inspect the final tree separately from patch correspondence.

After replay every commit has a new object ID. The review still needs to know which patch changed. Git’s range-diff compares two commit ranges and shows which patches correspond, changed, or remained unmatched.

A reviewer has already seen one version of a configuration change. The new version follows a different upstream base and changes a service mode. Comparing object IDs makes every commit look new. Comparing the two tips also shows a file added by upstream. First identify the base of each series so the comparison describes the topic work under review.

Compare the work added by each series

Git pairs commits based on the similarity of their patches, including author information, commit message and diff. It then shows the matched and unmatched commits. Similarity helps a human review the sequence. It does not establish commit identity or validate a signature. Git range-diff documentation

The complete script below creates a temporary repository. The old series adds notes and changes a service configuration. The new base adds a license. The script replays the topic commits and amends the mode in the second one. This ran with Apple Git 2.50.1. It uses no remote and leaves existing repositories alone.

set -eu
work=$(mktemp -d)
trap 'rm -r "$work"' EXIT
cd "$work"
git init -q -b trunk
git config user.name Fixture
git config user.email fixture@example.invalid
git config commit.gpgSign false

commit() { git commit --quiet "$@"; }
printf 'port=80\n' > service.conf

git add .
commit -m base
git tag old-base
git switch -qc old
printf 'readme\n' > notes.txt
git add .
commit -m 'Add notes'
printf 'port=80\nthreads=4\nqueue=16\nretry=3\nformat=json\nmode=read\n' > service.conf
commit -am 'Choose service mode'
git switch -q trunk
printf 'upstream only\n' > license.txt
git add .
commit -m 'Add license'
git tag new-base
git switch -qc new
git cherry-pick old~1 old >/dev/null
sed 's/mode=read/mode=write/' service.conf > changed
mv changed service.conf
commit -a --amend --no-edit

git diff --name-only old new
git range-diff --no-color old-base..old new-base..new

The tip comparison lists license.txt and service.conf. The license belongs to the updated base. In the range comparison, the notes commits have different IDs but pair with an equals sign. The service-mode commits pair with an exclamation mark, and the inner diff shows the added mode changing from read to write. The license never enters either topic range.

Keep three observations separate. The notes patch still matches. The service-mode patch corresponds but has changed. The final tree includes an upstream addition outside the topic. A review of the final tree can still be needed for release. A check that an original object remains reachable also needs separate ancestry evidence.

Inspect the full patches if pairing changes

The second patch in the fixture retains several configuration lines to make the changed pair observable. With very small or substantially rewritten patches, Git can instead show one removal and one addition. An early local version of this fixture did exactly that. Open the actual patches before reading those markers as proof that functionality was lost.

The reference describes the output as human-readable and subject to change across versions. Save the command, both ranges and the Git version so another reviewer can reproduce it. If automation must verify a configuration value in the final artifact, inspect that value independently. A punctuation marker identifies where to look. Acceptance still depends on what the change does.

Save full object IDs for both bases and tips. Reusing a branch name can make an identical-looking command resolve to a different range. If the new side starts at the old base, a comparison may report the upstream license commit as additional work. That wrong-range case was not run.

If you lost the original range boundary, recover it from a review record or another source before comparing. See finding the old fork point after an upstream rewrite for that separate question.

Does the default comparison include merge commits?

It ignores merge commits by default. If the review needs to see changes introduced while resolving a merge, choose an appropriate --diff-merges mode from the manual and inspect the merge itself. The main fixture uses linear histories. A separate test could create a merge with a manual resolution and check whether the selected mode exposes it. That test was not run.
