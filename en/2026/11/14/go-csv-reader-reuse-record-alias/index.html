Why do buffered Go CSV rows end up identical?

Use two Go CSV rows to distinguish immediate field reads from a retained slice that may be reused.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-14 · Estimated read 9 min
Translations
zh-CN en

Article

Key takeaways

  • Reuse can share backing storage across reads.
  • Copy a retained row before the next read, or disable reuse.
  • Check immediate values and delayed batch contents separately.

With ReuseRecord enabled, Go’s CSV Reader can reuse the backing array from a previous Read. Each row can look right when it arrives while a retained batch changes later. Turn reuse off or copy the row before the next read when the batch needs to keep it.

Suppose an importer logs each product ID and then buffers the whole row. The log shows a followed by b, but the later batch can show b twice. Check whether buffering saved the field values or retained a slice that a later read can overwrite.

Observe the immediate value and the retained row

The standard library documents that each Read owns newly allocated memory by default. With ReuseRecord enabled, a returned slice may share the previous slice’s backing array. That permission is the contract. A particular row shape or version need not reuse the same memory every time. Go encoding/csv reference.

The following complete program is unexecuted. It supplies two rows of two fields. Each run saves the first field immediately, then appends either the row slice or a copy. A fresh Reader is used for each configuration.

package main

import (
    "encoding/csv"
    "fmt"
    "io"
    "reflect"
    "strings"
)

func collect(reuse, snapshot bool) ([][]string, []string) {
    parser := csv.NewReader(strings.NewReader("a,1\nb,2\n"))
    parser.ReuseRecord = reuse
    var batch [][]string
    var ids []string

    for {
        row, err := parser.Read()
        if err == io.EOF {
            return batch, ids
        }
        if err != nil {
            panic(err)
        }
        ids = append(ids, row[0])
        if snapshot {
            row = append([]string(nil), row...)
        }
        batch = append(batch, row)
    }
}

func main() {
    expected := [][]string{{"a", "1"}, {"b", "2"}}
    for _, config := range [][2]bool{{false, false}, {true, true}, {true, false}} {
        batch, ids := collect(config[0], config[1])
        if !reflect.DeepEqual(ids, []string{"a", "b"}) {
            panic("immediate IDs changed")
        }
        if (!config[0] || config[1]) && !reflect.DeepEqual(batch, expected) {
            panic("retained rows changed on an owning path")
        }
        fmt.Printf("%v: %q\n", config, batch)
    }
}

The immediate IDs should be a and b in every run. With reuse disabled or with a copy, the retained batch should hold a with one and b with two. The last run leaves the slice unowned and prints what happened. If the second read reuses the first backing array, both retained entries can reflect the second row. The program does not assert that this particular bad result must occur. It asserts that the two owning paths preserve the data.

Record the toolchain, actual configuration, and observed batch when diagnosing a real instance. Keep an immediate observation and a delayed one under the same input ID. That lets you tell a parse error from a later overwrite. The related CSV record boundary article handles quoted multiline fields. This input uses two simple records.

Give retained rows a clear owner

An immediate consumer can finish before the next Read. Check whether it also stores the slice, sends it to a channel, or gives it to a later worker. Copy before the first operation that can overwrite the retained data, or disable reuse and keep the per-read allocation. Copying after a queue handoff can be too late.

For an importer with immediate counters and a later writer, give both paths their own acceptance test. Check the counters by ID and let the writer inspect the batch only after parsing has finished. This fixture has no queue, database, or concurrency test. It provides no throughput measurements.

A malformed record is another case. Read can return a partial record and an error. This program aborts on errors other than EOF. If the application accepts some recoverable rows, test its own error policy separately from row reuse.

Can I keep just the string from record[0]?

Assigning the string value to a variable or appending it to another slice keeps the value read at that point. Replacing a position in the record later does not alter the saved string. The example observes those IDs separately. A retained row slice still needs its own lifetime check. This reasoning assumes ordinary use of the public API.
