Why did Prometheus return a p75 and report repaired buckets?

Work through classic bucket repair and use a monotonic control to separate the returned quantile from input quality.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-14 · Estimated read 11 min
Translations
zh-CN en

Article

Key takeaways

  • Classic cumulative bucket counts should not fall as the bound increases.
  • A quantile can still be computed after repair.
  • Check the returned value and query info separately.

A wider cumulative bucket has fewer observations, yet Prometheus can still return a quantile. For classic histograms, histogram_quantile can raise a materially lower bucket for the calculation and attach an informational annotation. Check the returned value and the input quality separately.

An operator sees p75 still at 0.45 seconds while the query response reports repaired input. A panel showing only the number can conceal the difference. This example uses classic histogram series labeled with le. Native histograms have a different input representation and different interpolation rules in some cases.

Read the cumulative counts in upper-bound order

A classic bucket counts observations at or below its upper bound. A wider bucket includes everything counted by the narrower one, so the total can stay flat or rise. In the following input, the second count falls from 30 to 20. Prometheus raises material reversals to the preceding count after handling tiny discrepancies. The calculation uses the adjusted counts and reports an info annotation. That query operation does not rewrite the stored samples. Prometheus histogram_quantile reference

Upper bound in seconds Original count Count used in the calculation
0.1 30 30
0.3 20 30
0.5 50 50
+Inf 60 60

Seventy-five percent of 60 is 45. That rank falls in the finite bucket ending at 0.5, with a preceding bound of 0.3. Its cumulative count increases from 30 to 50, and rank 45 is three quarters of that interval. Linear interpolation gives 0.45 seconds. This is an estimate derived from the repaired counts.

Use the same numerical result as a control

Give a second series group counts of 30, 30, 50, and 60 from the start. Its output value is also 0.45. The complete proposed promtool test below checks both values, with one sample per series and no rate calculation. Save it as repair.yml and run promtool test rules repair.yml in a suitable Prometheus environment. It has not been executed here.

rule_files: []
evaluation_interval: 1m
tests:
  - interval: 1m
    input_series:
      - series: 'bad_bucket{le="0.1"}'
        values: '30'
      - series: 'bad_bucket{le="0.3"}'
        values: '20'
      - series: 'bad_bucket{le="0.5"}'
        values: '50'
      - series: 'bad_bucket{le="+Inf"}'
        values: '60'
      - series: 'ok_bucket{le="0.1"}'
        values: '30'
      - series: 'ok_bucket{le="0.3"}'
        values: '30'
      - series: 'ok_bucket{le="0.5"}'
        values: '50'
      - series: 'ok_bucket{le="+Inf"}'
        values: '60'
    promql_expr_test:
      - expr: 'histogram_quantile(0.75, bad_bucket)'
        eval_time: 0m
        exp_samples:
          - labels: '{}'
            value: 0.45
      - expr: 'histogram_quantile(0.75, ok_bucket)'
        eval_time: 0m
        exp_samples:
          - labels: '{}'
            value: 0.45

Even two passing value assertions would leave the input-quality question open. To check the annotation, submit both expressions to a Prometheus HTTP API with the same input samples available at the chosen instant. Preserve the whole response and inspect the top-level infos alongside the value. The damaged group should report the repair, while the control should omit that particular message. That API exercise was also not run. An API response can contain data and information together, so check whether the client displays the latter. Prometheus HTTP API response format

Find the counts before repair

Record the evaluation time and full labels. Work backward from the aggregated query to the neighboring buckets that fell out of order. Check whether they describe the same observations, units and dimensions. If aggregation combines several targets or ranges, examine each one separately. The annotation is evidence to investigate the inputs. It does not diagnose the cause.

Compare the complete labels and evaluation time before treating two displayed lines as adjacent buckets. A query that keeps an instance label on one bound and aggregates it away on another can put unrelated observations next to each other. Preserve the full response before diagnosing a missing annotation in a client.

A separate article on combining distributions rather than averaging reported quantiles addresses what belongs in the group. Here the group is fixed and the question is whether its cumulative counts are valid. Keep the value, annotation and original neighboring counts together in the investigation record.

Does a tiny decrease produce the same repair annotation?

The manual first ignores discrepancies small enough to attribute to floating-point precision. Its threshold is one trillionth of the sum of the neighboring counts. Near 30 and 30, a decrease far below six times ten to the minus eleven is well below the threshold. A reversal that remains after this adjustment is raised to the preceding count and produces the annotation discussed above. The decrease of ten in the main case is well outside that range. This smaller comparison was not run.
