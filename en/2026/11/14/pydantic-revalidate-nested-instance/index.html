Why can a valid outer Pydantic model contain an invalid nested field?

Trace three executed Pydantic inputs through default reuse, dictionary validation, and instance revalidation.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-14 · Estimated read 9 min
Translations
zh-CN en

Article

Key takeaways

  • Existing instances are not revalidated by default.
  • A dictionary and an existing instance can take different paths.
  • Configure revalidation on the model being reused.

Pydantic does not revalidate existing model instances by default. If an instance changes after its first validation, passing it to a parent model can preserve the invalid value. Check whether the parent receives a dictionary or an already-created object.

Suppose a notification contains a user profile. The profile originally has a list of strings, but another step replaces that field with a list containing an integer. The notification can still be constructed from the profile instance. Passing the same content as a dictionary produces a validation error. The two inputs take different validation paths.

Set the policy on the model being reused

Pydantic v2 offers never, always, and subclass-instances. The default never skips revalidation of existing models and dataclasses. The always policy revalidates them. The subclass option applies when the instance is a subclass of the expected model or dataclass. These settings affect the model on which they are declared and do not propagate to models referenced by fields. Pydantic configuration reference.

Field assignment is a separate entry point. The fixture leaves assignment behavior at its default so both instances can be changed. Otherwise an earlier error could remove the very input the reuse test needs.

Verify the three inputs independently

The following fixture ran on Python 3.11.15 with Pydantic 2.13.4. It creates valid lists and replaces each with a list containing one integer. It does not call an API or decode a request body.

from pydantic import BaseModel, ConfigDict, ValidationError

class User(BaseModel):
    hobbies: list[str]

class CheckedUser(BaseModel):
    model_config = ConfigDict(revalidate_instances="always")
    hobbies: list[str]

class Envelope(BaseModel):
    user: User

class CheckedEnvelope(BaseModel):
    user: CheckedUser

def rejected(factory, value):
    try:
        factory(user=value)
    except ValidationError as exc:
        assert exc.errors()[0]["loc"] == ("user", "hobbies", 0)
        return True
    return False

plain = User(hobbies=["reading"])
checked = CheckedUser(hobbies=["reading"])
plain.hobbies = [1]
checked.hobbies = [1]

observed = (
    Envelope(user=plain).user.hobbies,
    rejected(Envelope, {"hobbies": [1]}),
    rejected(CheckedEnvelope, checked),
)
assert observed == ([1], True, True), observed
print(observed)

The first wrapper accepts the existing instance and retains the integer. The second rejects the dictionary. The third rejects the existing instance whose own model enables revalidation. Both validation errors identify user, hobbies, and index zero. Checking that path keeps an unrelated constraint from satisfying the test. The run does not establish any network error response or copying policy.

Check the real entry point as well. A cache hit may hand off an existing instance, while a fresh request is parsed from a dictionary. An integration test can exercise both paths with the same invalid value. The related article on duplicate JSON members covers a different boundary before raw members become a mapping.

Choose the validation point from the write path

If an application assigns new values directly, validate_assignment can catch an invalid assignment at that location. Revalidation can protect a later boundary where existing objects are accepted. Give each check its own fixture so a refusal at one point does not hide missing validation at the other.

Test direct assignment separately from modifying a list in place. An append is not the same operation as assigning a new list to the field. If the caller needs a stable object at handoff, it can use an immutable structure or construct independent data under a deliberate schema. These alternative paths are unexecuted.

For the notification service, preserve the value before mutation, the changed value, the validation outcome, and the output as separate observations. Include a valid profile as a control. The fixture does not test serialization, caching, or delivery.

Does always on the parent also revalidate a child model?

The setting does not propagate into models referenced by fields. A wrapper with always still uses the default User policy for an existing User child. An independent check can give a new wrapper the same changed instance and verify that the list still contains the integer. Configure the model responsible for that field when the instance itself must be revalidated. This parent-only probe was not run.
