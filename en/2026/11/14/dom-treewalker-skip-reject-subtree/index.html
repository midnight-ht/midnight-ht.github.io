Why did TreeWalker lose the children of a wrapper?

Use one DOM tree to compare TreeWalker SKIP, REJECT, and their effect on descendant visits.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-14 · Estimated read 10 min
Translations
zh-CN en

Article

Key takeaways

  • SKIP can omit the wrapper while retaining descendant traversal.
  • REJECT prunes the branch in TreeWalker.
  • NodeIterator handles these filter values differently.

An outline omits a section wrapper and unexpectedly loses the heading inside it. With TreeWalker’s forward traversal, FILTER_SKIP can omit the wrapper and keep searching its descendants. FILTER_REJECT skips the branch. Decide whether the current node alone should be omitted or whether none of its descendants belong in the outline.

Give each filter decision a scope

DOM defines TreeWalker’s nextNode algorithm by searching from the current position. It does not descend into a rejected node. It can still visit descendants of a skipped node. A layout wrapper can be transparent to an outline, while an excluded reference region can keep all of its headings out.

Imagine an editor that shows the article and a reference copy of an older draft. The outline should include headings in the article. If every non-heading is skipped, old headings can still appear. If every non-heading is rejected, the article can lose headings within normal layout wrappers. Check for excluded regions before applying the ordinary heading rule.

The filter describes traversal, not visual visibility. This fixture uses node identity to make the decision. An application excluding visually hidden content needs to define that condition and test it. A heading omitted by the traversal can still exist in the DOM and be returned by another query.

Compare visits and results on a fixed tree

The complete local HTML has not been run in a browser. A is under an ordinary wrapper, B under the excluded branch, and C is a direct child. The two traversals share the same static tree. Only the wrapper’s decision changes. The filter records the nodes it visits, and the loop separately records returned headings.

<!doctype html>
<html lang="en">
<meta charset="utf-8">
<title>TreeWalker branch comparison</title>
<main id="source">
  <section id="wrapper"><h2 id="a">Heading A</h2></section>
  <section id="excluded"><h2 id="b">Heading B</h2></section>
  <h2 id="c">Heading C</h2>
</main>
<pre id="output"></pre>
<script>
const root = document.querySelector('#source');
const { SHOW_ELEMENT, FILTER_ACCEPT, FILTER_SKIP, FILTER_REJECT } = NodeFilter;

function outline(wrapperDecision) {
  const visited = [], headings = [];
  const walker = document.createTreeWalker(root, SHOW_ELEMENT, node => {
    const { id, tagName } = node;
    visited.push(id);
    if (id === 'excluded') return FILTER_REJECT;
    if (id === 'wrapper') return wrapperDecision;
    return tagName === 'H2' ? FILTER_ACCEPT : FILTER_SKIP;
  });
  for (let current = walker.nextNode(); current; current = walker.nextNode()) {
    headings.push(current.id);
  }
  return { visited, headings };
}
const results = { skip: outline(FILTER_SKIP), reject: outline(FILTER_REJECT) };
document.querySelector('#output').textContent = JSON.stringify(results, null, 2);
</script>
</html>

For the skip path, expect visits to wrapper, A, excluded, and C, with A and C returned. B is below a rejected node. For the reject path, expect visits to wrapper, excluded, and C, and only C in the result. A remains in the DOM. An assertion that finds A with a selector would therefore miss a broken outline.

The sample considers elements only. It does not return the root as the first result of this traversal. If the application needs text or comments, its node mask and filter should reflect that output requirement.

Make the outline’s scope testable

Use a specific editor marker for a reference region. Normal layout wrappers can allow the walk to reach their headings. Regression cases can add another wrapper to verify that layout changes do not silently shrink the outline. Record heading IDs rather than titles alone if two headings can have the same wording.

When the structure is editable, decide what version a single outline calculation uses. NodeList membership and updates covers lists after DOM changes. Here a static tree isolates filtering. Derive the expected headings from a marked-up test tree, then keep the filter’s visit trace when a heading goes missing. That trace can distinguish a rejected ancestor from a heading that was visited and skipped.

Does NodeIterator prune descendants on FILTER_REJECT?

No. Replace TreeWalker with NodeIterator’s forward traversal while keeping the tree and filter. It returns a node only for ACCEPT and otherwise continues in tree order. The excluded wrapper can be omitted while B is still visited and accepted, yielding A, B, C. If branch pruning is a requirement, choose a traversal that implements it or express it in the traversal logic.
