Why didn’t a shared Make rule pick prerequisites for each target?

Use GNU Make secondary expansion to give two targets different prerequisites and verify an incremental rebuild.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-14 · Estimated read 9 min
Translations
zh-CN en

Article

Key takeaways

  • The first expansion cannot read the automatic target variable.
  • Escape a reference to preserve it for secondary expansion.
  • Change one input to verify that the dependency reaches the right target.

The automatic target variable is unavailable on GNU Make’s first prerequisite expansion. Preserve the reference for secondary expansion when a shared rule needs to select prerequisites by target.

Two targets use the same recipe. Each copies an input file to its output, but the inputs differ. A maintainer combines the rules and tries to select the source with the target name. The target variable still works in the recipe, while the prerequisite list comes out empty. The difference is when Make evaluates each expression.

Keep a reference for the target context

Make expands ordinary prerequisites when it reads the rules. At that point there is no automatic variable for the target being updated. Put .SECONDEXPANSION before the affected rules and escape the references that should survive the first expansion. On the second expansion, Make has the target context. GNU Make manual on secondary expansion

The outer escaped dollar preserves the variable lookup. The inner one preserves the target reference. For main, the resulting lookup reads main_SRC. For lib, it reads lib_SRC. Once the right prerequisite exists, the recipe can use it as its first input.

Give the two targets different inputs

Save this complete Makefile in a disposable directory, keeping the Tab at the start of its recipe. Create main.txt with main-v1 and lib.txt with lib-v1. Run make all and compare the output contents with the two inputs. This fixture ran locally on GNU Make 3.81.

main_SRC := main.txt
lib_SRC := lib.txt

.SECONDEXPANSION:
all: main lib
main lib: $$($$@_SRC)
    cp "$<" "$@"

The first run executed both copies. After enough time for a distinct modification timestamp, change only lib.txt to lib-v2 and run the same target. The archived run executed only the lib copy. The lib output changed to lib-v2 and main still contained main-v1. Checking just the final contents of lib would miss a needless rebuild of both targets. Counting commands alone would miss a rebuild of the wrong target.

As a negative control, save the prerequisite line as main lib: $($@_SRC) in a separate broken.mk. Run make -f broken.mk all. Use the same inputs without either generated output. The early expansion resolves no source. In the run, the recipe attempted to copy an empty filename and Make exited two. Both input files existed. The rule failed to connect them to their targets. Running that negative with old outputs present could instead leave Make with nothing to do and conceal the missing edge.

Decide whether the rule benefits from the indirection

Two plainly named inputs may be easier to review as separate rules. A shared expression helps when a larger family follows a stable naming convention. Decide what should happen when a member has no defined input. This recipe fails if the first prerequisite is empty. A recipe that tolerates an empty list may instead emit an incomplete artifact.

Diagnose an incorrect prerequisite name separately from a correct prerequisite that did not trigger a rebuild. Check the expansion and variable definitions for the former. Check timestamps and prerequisite type for the latter. Order-only directory prerequisites explains a separate choice about the effect of an edge.

Write down the expected input for each target before running the test. Distinct marker contents expose a wrong source even if the build exits zero. The one-file update also catches a rule that needlessly connects both inputs to both targets. Those observations apply to this Makefile. They do not establish the dependency contract for other generated artifacts.

Can secondary expansion use the stem in an explicit rule?

In an explicit rule, $$* and $$? expand to empty during secondary expansion. This fixture only needs $$@. If the rule needs a piece of the target name, it can derive that piece explicitly and check a target that breaks the naming convention. The availability of automatic variables in a recipe does not establish their availability in this explicit-rule prerequisite list.
