Can an API still work after a Deprecation response header?

Read deprecation and expected retirement dates from an old endpoint that still returns 200, then separate response handling from migration planning.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-14 · Estimated read 10 min
Translations
zh-CN en

Article

Key takeaways

  • The two dates describe different events.
  • Handle the current reply according to its actual status and contract.
  • Keep an absent retirement date unknown.

The old endpoint still returns 200 and a usable body, alongside Deprecation and Sunset dates. Process the current result under its normal response contract. The first date tells clients when the resource is deprecated. The second conveys when the URI is expected to become unavailable.

Read the two dates for different decisions

RFC 9745 defines the Deprecation field as a Structured Fields Date. In the positive integer example, an @ precedes the Unix time in seconds. A past date marks a deprecation that has taken effect. A future date can announce a planned one. The field does not change the resource’s existing meaning or behavior.

The Sunset field uses an HTTP date for the point when the URI is expected to become unresponsive. That expectation does not guarantee a particular status code or an outage on the date. Plans can change. Record availability from the endpoint’s actual response and any separate operational confirmation.

Imagine a guide service that wants callers to migrate from an old address. The old address still returns the guide, and the two fields give maintainers time to schedule the change. The application can display the guide while recording the notice for the owning team. Treating the notice as a failure would hide usable data and count a migration signal as an error.

Check both times with fixed UTC inputs

This complete local Node example takes a fixed status, body, and header values. It accepts the teaching fixture’s positive ten-digit timestamp and uses the runtime’s date parser for the supplied HTTP date. It is a limited fixture rather than a general-purpose header parser. The independent expectations are midnight UTC on January 1 in 2025 and 2026, and the guide ID guide-9. It sends no HTTP requests.

import { deepEqual, equal } from 'node:assert/strict';

const sample = {
  status: 200,
  body: { id: 'guide-9' },
  deprecation: '@1735689600',
  sunset: 'Thu, 01 Jan 2026 00:00:00 GMT',
};

function inspect(reply) {
  // Deliberately accepts only this fixture's positive date shape.
  const match = /^@(\d{10})$/.exec(reply.deprecation);
  if (!match) throw new Error('unexpected fixture date');
  const sunsetTime = reply.sunset === undefined ? null : Date.parse(reply.sunset);
  if (sunsetTime !== null && !Number.isFinite(sunsetTime)) {
    throw new Error('invalid fixture sunset');
  }
  return {
    id: reply.status === 200 ? reply.body.id : null,
    deprecatedAt: new Date(Number(match[1]) * 1000).toISOString(),
    expectedUnavailableAt: sunsetTime === null ? null : new Date(sunsetTime).toISOString(),
  };
}
deepEqual(inspect(sample), {
  id: 'guide-9',
  deprecatedAt: '2025-01-01T00:00:00.000Z',
  expectedUnavailableAt: '2026-01-01T00:00:00.000Z',
});
const { sunset, ...withoutSunset } = sample;
equal(inspect(withoutSunset).expectedUnavailableAt, null);
console.log(JSON.stringify(inspect(sample)));

Keep the current guide ID, deprecation date, and expected unavailability as separate results. The negative omits Sunset and leaves the expected retirement unknown while still reading the guide. Copying the deprecation time into that field invents a commitment. Rejecting a usable response solely because it carries a notice loses the current result. Both errors can be tested without moving the system clock.

A production client can decide how to surface malformed lifecycle metadata independently of its normal response handling. A useful test matrix includes valid dates, missing Sunset, a date the client cannot parse, and a genuine request error. Record the resource associated with each field as well as the outcome. A host can serve multiple versions and resources with different plans.

Check which callers the migration affects

An old and new guide endpoint might accept different language parameters. A planned retirement date cannot establish that their representations or errors are interchangeable. Choose representative calls, compare outputs, and check the actual entry points before migrating a caller. Lifecycle differences between 404 and 410 covers the later decision when a resource is no longer served. This example works while the old endpoint still returns content.

Should a client swap the dates if Sunset is earlier?

No. Section 4 of the deprecation specification requires Sunset to be no earlier than Deprecation. Change the fixture’s retirement date to January 1, 2024 while keeping the 2025 deprecation date to exercise the new condition. Preserve the original fields and ask the provider to clarify the schedule. A client cannot infer the correct dates by reversing them. Continue to handle the current response under its own status and content contract.
