Why are the resources still open after ExitStack exits?

Trace partial acquisition failure and successful callback transfer in an executed ExitStack fixture.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-14 · Estimated read 9 min

Article

Key takeaways

  • pop_all transfers exit callbacks.
  • The original stack can clean up partial acquisitions.
  • After transfer, the new stack owns the exits.

ExitStack.pop_all transfers registered exit callbacks to a new stack. Leaving the original with block no longer runs those callbacks. If resources must stay open for the caller, hand over the new stack with them and give it a clear owner.

Suppose an exporter acquires two input handles. If the second acquisition fails, it must release the first. If both succeed, the caller needs them to stay open. A local with scope can handle failures during acquisition, then transfer cleanup after the last prerequisite succeeds.

Transfer the callbacks

An ExitStack can enter a context manager and register its exit method. It unwinds registered callbacks in reverse order. pop_all moves the callback stack into a fresh ExitStack without invoking anything. The new owner can call close or manage it with another with statement. The documentation also says garbage collection does not invoke the callbacks. Keep the transferred stack until there is a deliberate cleanup path. Python 3.14 contextlib.

The transfer keeps the same exit operations and their order. It does not acquire the resources again. Returning only the handles can make the transferred responsibility invisible to the caller.

Observe success and partial failure

The following program ran locally on Python 3.11.15. Its two in-memory context managers record attempted acquisition and cleanup. It does not open files or connect to a service.

from contextlib import ExitStack, contextmanager

events = []

@contextmanager
def acquire(name, fail=False):
    events.append("try " + name)
    if fail:
        raise ValueError(name)
    try:
        yield name
    finally:
        events.append("close " + name)

def open_pair(fail=False):
    with ExitStack() as stack:
        first = stack.enter_context(acquire("A"))
        second = stack.enter_context(acquire("B", fail))
        return (first, second), stack.pop_all()

try:
    open_pair(fail=True)
except ValueError:
    assert events == ["try A", "try B", "close A"]
else:
    raise AssertionError("expected acquisition failure")
print("partial:", events)

events.clear()
pair, owner = open_pair()
assert pair == ("A", "B")
assert events == ["try A", "try B"]
try:
    print("after transfer:", events)
finally:
    owner.close()
assert events == ["try A", "try B", "close B", "close A"]
print("after close:", events)

When B fails, expect attempts for A and B, followed by cleanup of A alone. B has not handed over a resource or registered an exit operation. On success, the function returns both values without closing either. Closing the new stack should then release B before A. The receipt records all three observations. Checking only the final closed resources would miss a premature cleanup at the original boundary.

If a real context manager acquires something internally before its own entry fails, it needs a cleanup path for that partial construction. An enclosing ExitStack cannot infer which internal resources were acquired. The related single-yield context manager article covers responsibility inside a manager. This fixture starts from the exit methods that were successfully registered.

Finish protected work before transferring

An exporter might validate both file headers or allocate another buffer after acquisition. Do that work before handing over responsibility, or put the new owner on an explicit failure path. A separate test can make both acquisitions succeed and fail the final preparation step. The caller should receive no usable handles, and both resources should close exactly once. That variation was not executed.

The caller also needs to stop using the resources after closing the new stack. Exercise its success and failure paths with observable handles. If cleanup itself can fail, test the propagation of that failure independently. The in-memory callbacks here cannot establish file persistence or how a real exporter reports multiple failures.

Does close pass the same exception information as with?

A direct close begins unwinding without an exception. If the body of a with block raises, an exit callback can receive that exception. Earlier callbacks may suppress or replace it before later callbacks run. An independent probe can register one exit method that records the three exception arguments, then compare a direct close with a failing body. Plain functions registered through callback do not receive those arguments. This follow-up was not run.
