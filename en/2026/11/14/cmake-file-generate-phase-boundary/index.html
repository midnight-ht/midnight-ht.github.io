Why can’t the next CMake command read a file just scheduled by file(GENERATE)?

Compare file reads during configuration and after generation, including a stale output from the previous run.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-14 · Estimated read 8 min
Translations
zh-CN en

Article

Key takeaways

  • Scheduling generation does not write the file immediately.
  • A pre-existing file does not prove a new write.
  • Configuration-specific outputs need compatible paths and content.

When file(GENERATE) returns, the new output is still pending. CMake writes it during generation, after it has processed the project’s configuration files.

A maintainer schedules a status file and tries to read it on the next line. A clean build directory has no file. A reused directory may have one, left by an earlier run. Before treating either observation as proof, decide whether the consumer needs this run’s value or a previously recorded state.

Read two different values in the same build directory

Save this complete project as CMakeLists.txt in its own source directory. It needs no compiler. During configuration it schedules status.txt, then checks the same path and reports the contents if the file exists. CMake file GENERATE reference

cmake_minimum_required(VERSION 3.18)
project(generation_boundary NONE)
set(VALUE A CACHE STRING "A short teaching value")
set(path "${CMAKE_CURRENT_BINARY_DIR}/status.txt")

file(GENERATE OUTPUT "${path}" CONTENT "value=${VALUE}\n")
if(EXISTS "${path}")
  file(READ "${path}" observed)
  string(STRIP "${observed}" observed)
  message(STATUS "during: ${observed}")
else()
  message(STATUS "during: missing")
endif()

Run cmake -S . -B out -DVALUE=A with a fresh output directory, then read status.txt after the command succeeds. Run it again against the same directory with -DVALUE=B. This was executed on CMake 4.2.3. Both configure-and-generate invocations succeeded. No build ran.

B, reused directory value=A value=B

The second run gives a useful false positive. An existence check passes in configuration, although it sees A from the previous invocation. Testing only in a clean directory would miss that path. Record the input, output directory and both reads. The table gives four separate observations to compare.

The manual also says that a subsequent run changes the generated file and its timestamp only if the contents change. An unchanged timestamp alone cannot establish a failed generation. Compare the actual contents with the input for that run. This fixture deliberately changes the input and tests the timing of the write.

A failed configure can leave the previous output in place. Preserve that failure before examining any old file. For a successful run, check the path as well as the value. The same source revision may have been configured with different inputs in another directory.

Choose the write point from the consumer’s needs

If configuration itself needs a plain text file, use a write operation that completes before its reader. On a supporting version, file(CONFIGURE) can substitute variables at configure time. Its output and content do not accept generator expressions. If the consumer needs a generator-dependent result, arrange to read it after generation. CMake file CONFIGURE reference

Sometimes the earlier consumer already has the value in memory. Use that value to make the configure decision and keep the generated file for downstream tools. Both can verify the same setting at their respective stages. Avoid turning the later artifact into an implicit input that only works in a reused directory.

Test the reader in a clean directory and in one with a deliberately stale marker. Preserve its actual path as well as its result, since an unrelated file with the same name can make an existence check pass. This extension was not run. For a separate timing mechanism, see when CMake deferred calls evaluate their arguments.

Can a multi-config generator write each configuration to the same path?

Only when the generated content is identical. If Debug and Release need different output, give them distinct paths, for example by including the configuration in the filename. The main fixture uses constant content within each invocation. In a multi-config test, verify both paths and both contents. That additional test was not run here.
