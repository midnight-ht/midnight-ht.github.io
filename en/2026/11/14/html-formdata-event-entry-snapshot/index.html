Why does new FormData fire formdata without submitting the form?

Use a form preview to distinguish entry construction, synchronous listeners, control values, and submission.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-14 · Estimated read 10 min
Translations
zh-CN en

Article

Key takeaways

  • Constructing FormData from a form builds its entry list.
  • A synchronous listener can change the current entries.
  • A preview event provides no submission receipt.

The user clicks Preview Entries and never submits the form, but the formdata listener still runs. Passing the form to new FormData builds an entry list and fires the event during that work. A synchronous listener can change the entries that the constructor returns. Observing the event does not establish that a request was sent or saved.

Identify which object should change

HTML’s entry-list algorithm gathers the applicable controls, associates a FormData object with the list, fires the event, and returns a copy of the entries. The XHR constructor invokes that algorithm when it receives a form. The example uses a text control and a source value, without serializing or sending a request.

An editor can preview what a future request might contain and add a source marker to that preview. The marker does not need a visible control. Updating an input after its value has been collected also does not rewrite the current entries. Decide whether the listener is meant to change a control, a snapshot, or later request data.

Counting this event as a successful save gives the preview an outcome it never reached. Keep any diagnostic event count separate from the application’s actual receipt.

Observe the preview in a complete local page

The fixture has not been run in a browser. A form begins with Guide as its title and has a regular preview button. The code records before, adds source in the listener, and records after once the constructor returns. It also reports the input’s current value.

<!doctype html>
<html lang="en">
<meta charset="utf-8">
<title>Form entry preview</title>
<form id="editor">
  <label>Title <input name="title" value="Guide" required></label>
  <button id="preview" type="button">Preview entries</button>
</form>
<pre id="log"></pre>
<script>
const byId = id => document.getElementById(id);
const [form, button, log] = ['editor', 'preview', 'log'].map(byId);
const input = form.elements.namedItem('title');
let record;
form.addEventListener('formdata', ({ formData }) => {
  record.push('listener');
  formData.set('source', 'preview');
});
button.onclick = () => {
  record = ['before'];
  const entries = Array.from(new FormData(form));
  record.push('after');
  log.append(JSON.stringify({ record, entries, title: input.value }) + '\n');
};
</script>
</html>

Expect before, listener, then after for each click. The snapshot should contain title Guide and source preview. The control remains Guide and no source control is created. These checks distinguish the listener’s call from its effect on the returned list. The fixture never sends a request.

For a negative, change only the input to Changed inside the listener. The current construction has already collected the title, so its first result should still contain Guide. A second construction can collect Changed. You can also inspect what an empty required field contributes. Creating the snapshot is not the same action as triggering validation or sending the form.

Keep preview and submission intent visible

An application with preview, draft, and submit actions can share a function that calculates extra fields. The caller still needs to apply the fields appropriate to that action. Otherwise every construction might add a preview label even when the application really submits. Scripted submission and submitter intent covers validation and submit events. Here the question is what can still change after the list has been built.

Test the control value, snapshot, transmitted request, and stored result at their own boundaries. A second preview should reflect the current controls rather than reuse an earlier snapshot. If the user edits after preview, decide whether submission uses the confirmed snapshot or builds a new one. The decision depends on which content the user actually approved.

Will construction wait if the listener awaits before adding a value?

No. Change the synchronous listener to wait behind a gate and release it only after construction returns. Event dispatch does not await the listener’s promise. The HTML algorithm copies the entries after synchronous dispatch. The listener’s old object can acquire the new value later while the returned object remains unchanged. Check both after releasing the gate. Acquire asynchronously produced fields before construction or add them explicitly to the final object at the sending boundary.
