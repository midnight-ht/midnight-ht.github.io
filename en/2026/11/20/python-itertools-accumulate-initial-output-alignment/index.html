Why does accumulate return three balances for two transactions?

Check opening and post-event states, then reproduce a shifted zip that silently drops the last balance.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-20 · Estimated read 11 min
Translations
zh-CN en

Article

Key takeaways

  • A non-None initial value is yielded before input transitions.
  • Pair post-event balances after retaining the opening separately.
  • initial=None selects the mode without an initial value.

Two movements passed to accumulate with initial=100 produce three balances. The first is the opening state. The other two follow the movements. Zipping the entire result with transaction identifiers attaches the opening balance to the first movement and leaves the final balance unattached.

Number events and states independently

A local inventory example starts at one hundred. A adds ten and B subtracts three. The sequence is an opening hundred, then 110 after A, then 107 after B. Two events have three states because the first state precedes both events. The example uses integers and connects to no warehouse or database.

accumulate defaults to addition and yields each running result. Without an initial value, the first input becomes the first running value. With one, it yields that value before applying the inputs, adding one output. A consumer can inspect the starting state as well as each transition. An extra result alone is no evidence of an extra addition.

An opening state also has provenance: a previous batch's confirmed ending or a window's starting condition. A row showing an event and a balance must say whether that balance precedes or follows the event. A “balance after processing” view requires the later state. Checking a final total alone can miss the row-level shift.

Assert the actual offset

The fixture retains all states and compares an intentionally shifted pairing with the desired pairing. Expected values come from one hundred plus ten minus three. Empty inputs have independent calls.

from itertools import accumulate

movements = [10, -3]
ids = ["A", "B"]
balances = list(accumulate(movements, initial=100))
assert balances == [100, 110, 107]
assert list(accumulate(movements)) == [10, 7]
assert list(accumulate([], initial=100)) == [100]
assert list(accumulate([])) == []
assert list(zip(ids, balances)) == [("A", 100), ("B", 110)]
assert list(zip(ids, balances[1:])) == [("A", 110), ("B", 107)]
assert list(accumulate(movements, initial=None)) == [10, 7]
print("opening=100; A=110; B=107; empty with opening retains 100")

The three states are 100, 110, 107. The wrong pairing gives A 100 and B 110, leaving 107 unused. zip stops at the shorter input, so no exception is needed for this failure. The correct pairing retains the opening separately and attaches the subsequent states to A and B. Both pairings have the same identifiers, so comparing identifiers alone misses the bug.

Deleting an arbitrary output is no repair. Removing the last state also gives two elements while leaving both rows at their pre-event state. Exact assertions on A=110 and B=107 define the actual contract. A zero movement could conceal the shift because adjacent balances match; the fixture uses two nonzero movements.

Without initial, the result is ten and seven. That answers a different question starting from the inputs themselves. It cannot replace an account state starting at one hundred. Charts can show similar directions on different baselines. Retain the initial value and input window with the result.

Decide whether the interface exposes events or states

A complete trajectory can include the opening with an explicit starting position on its axis. An event report can instead return identifiers with post-event states and a separate opening field. Both can use accumulate internally. Name the stage rather than allowing balance to mean before on one page and after on another.

A large input need not be materialized entirely. One caller can consume the opening and then pair later states incrementally. Keep ownership of those reads clear so a preview cannot advance the state iterator before another function starts pairing. This short fixture uses lists for complete observation and measures no streaming memory use or database running-total implementation.

Diagnostics can record the opening, event identifier, and phase. If the final row disagrees with a total, inspect whether it displays the pre-event state before rechecking arithmetic. Another sum will not expose a view selecting the wrong position from a correct array. The site's signed inventory difference article addresses which quantities survive an operation. Here the quantities are correct but attached to adjacent events.

Across batches, do not apply the opening twice. A batch that starts at the previous ending should not insert the old opening as another movement. A proposed regression can split one input into two batches and compare event/state pairs at the seam. That variation is outside the executed fixture.

Can initial=None represent a real None starting state?

None selects the default mode without an initial value. The explicit initial=None control still produces ten and seven. It does not yield None first. A state machine that genuinely starts at None needs explicit initialization or its own iterator. This new condition concerns a nullable state rather than the numeric opening. Empty input with initial=None supplies no opening output either; an application displaying “not established” must represent that condition itself.
