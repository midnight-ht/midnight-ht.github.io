How can CTest keep two tests off the same device during a parallel run?

Verify a named CTest resource lock using an atomic marker and execution intervals, with explicit scope boundaries.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-20 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • A shared lock name excludes overlapping tests.
  • Verify intervals and cleanup independently.
  • Cross-job coordination requires its own contract.

Give two CTest tests the same RESOURCE_LOCK name to prevent them from running concurrently within one parallel invocation. Unrelated tests can still run in parallel. Map the shared resource to a common name, then verify actual holding intervals.

Two tests might both reset one local simulated device. Each passes alone, but parallel runs interfere. A shared lock expresses their narrower constraint. The suite maintainers must agree on the resource name.

Observe the holding interval independently

Save this as worker.py. Each process atomically creates the same directory, holds it briefly, and releases it. A concurrent attempt would fail to create it. On normal completion, it records monotonic start and end times. The oracle checks ordering rather than a promised duration.

import json
from pathlib import Path
import sys
import time

root = Path(sys.argv[1])
name = sys.argv[2]
lock = root / "occupied"
lock.mkdir()
started = time.monotonic_ns()
try:
    time.sleep(0.2)
finally:
    ended = time.monotonic_ns()
    lock.rmdir()
(root / (name + ".json")).write_text(json.dumps([started, ended]))

Save this CMake project beside it. Both tests use the same resource directory and lock name, with distinct output identities.

cmake_minimum_required(VERSION 3.20)
project(ResourceFixture NONE)
enable_testing()
find_package(Python3 REQUIRED COMPONENTS Interpreter)

foreach(name IN ITEMS alpha beta)
  add_test(NAME ${name} COMMAND "${Python3_EXECUTABLE}"
    "${CMAKE_CURRENT_SOURCE_DIR}/worker.py" "${CMAKE_BINARY_DIR}" "${name}")
  set_tests_properties(${name} PROPERTIES RESOURCE_LOCK device)
endforeach()

Run this script from the source directory. A budget of two permits parallel scheduling. The outer check reads both records, sorts by start, and verifies the intervals do not overlap. It checks resource cleanup independently.

set -eu
work=$(mktemp -d)
trap 'rm -r "$work"' EXIT
ctest --version
cmake -S . -B "$work/build"
ctest --test-dir "$work/build" -j 2 --output-on-failure
python3 - "$work/build" <<'PY'
import json
from pathlib import Path
import sys

root = Path(sys.argv[1])
windows = [json.loads((root / name).read_text()) for name in ("alpha.json", "beta.json")]
windows.sort()
assert windows[0][1] <= windows[1][0]
assert not (root / "occupied").exists()
print("nonoverlapping", windows)
PY

On CTest 4.2.3 with Python 3.11.15, both tests passed, their intervals did not overlap, and the occupied directory was gone. The script exited zero. This verifies named exclusion in one CTest invocation without using a device or measuring a speedup. Either execution order satisfies the test. RESOURCE_LOCK reference

Make the names represent actual ownership

The scheduler sees a resource name, not the device address or database identity. Two names for one device leave the conflict unrepresented. One common name for two independent devices can serialize work unnecessarily. Review the actual resource, tests, and shared name together.

Scope matters too. Another terminal, CI job, or operator can still use the device. Cross-process or cross-machine exclusion needs its own resource-service contract and validation. The directory here is an observation tool, not a remote-device locking system.

Preparation and release need evidence beyond a scheduling opportunity. Verify the device's generation and initial state on entry, and its expected state on departure. Preserve release errors and test identity so the next test does not inherit an unexplained configuration. The fixture's finally block only removes a local marker.

Keep intermittent failures interpretable

Retain the locked run and confirm both tests were selected. A run containing only one test cannot verify exclusion. Missing time records also require investigation even if the suite reports success. Fresh build directories prevent old JSON records from satisfying the current checks.

Removing the lock does not guarantee a collision on every run. The scheduler may happen to start them sequentially. Report observed overlap or its absence without inferring the property is ineffective. A controlled extension can widen the holding interval and record both entry attempts. The unlocked branch was not run here.

Failure before acquisition and failure during holding are different cleanup situations. The former may produce no end record. Normal exception unwinding after acquisition attempts the finally cleanup. Forced termination needs the resource's actual recovery policy. Correlating scheduling, acquisition, use, and release helps a maintainer choose between fixing a lock name, a test, or a device.

An end record cannot establish that the device test passed. Work can hold the resource and finish timing without checking the returned device value. Assert the intended operation result and bind it to the same interval. A diagnostic end timestamp written in finally can identify departure from the protected scope while the original failure still propagates. Keep test outcome and cleanup evidence together so exclusion does not substitute for behavior acceptance.

What if one test must exclude every other test?

Consider RUN_SERIAL, which prevents that test from running in parallel with any other test. That broader scope can fit a test using global state that cannot be enumerated reliably. A named resource lock retains parallel opportunities when the shared device is clear. This adds whole-run exclusion beyond the main fixture. No RUN_SERIAL comparison was executed.
