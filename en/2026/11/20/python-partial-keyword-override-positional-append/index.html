Why can a caller override a timeout bound by partial?

Compare keyword overrides, positional collisions, and mutation of stored configuration at the underlying function.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-20 · Estimated read 11 min
Translations
zh-CN en

Article

Key takeaways

  • Call-time keywords override stored values with the same name.
  • New positional arguments follow the stored positions.
  • The read-only keywords attribute still refers to a mutable dictionary.

A factory binds a five-second timeout with partial. The caller supplies timeout=20, and the underlying function receives twenty. Keyword binding supplies an overridable default. If five seconds is a business limit, enforce it where the request is accepted.

How creation-time and call-time arguments combine

A task factory can create a callback with a job name and a usual timeout for later execution. The executor may know that one call needs a different wait. Keyword overrides serve that contract well. A factory promising an unchangeable restriction needs a different enforcement boundary. Decide what binding promises before choosing the mechanism.

partial stores a function, a tuple of positional arguments, and a keyword dictionary. When called, it prepends the stored positional arguments to the new ones. Keywords merge, with later values replacing earlier values under the same name. These are different combination rules. Supplying a new positional number does not replace an old bound position.

Ordinary argument binding still happens when the underlying function is invoked. If timeout is already positional, another positional argument can exceed the signature. If timeout is stored as a keyword and a new positional argument occupies its slot, the call can assign it twice. The fixture tests those two collisions. partial does not invent a signature where every parameter can be replaced arbitrarily.

Keep independent oracles for three call outcomes

request only returns the two values it receives. It performs no HTTP request. The first checks demonstrate overriding, the error calls test positional composition, and the final checks support the follow-up about stored configuration.

from functools import partial

def request(label, timeout=1):
    return label, timeout

configured = partial(request, "job", timeout=5)
assert configured() == ("job", 5)
assert configured(timeout=20) == ("job", 20)
fixed_position = partial(request, "job", 5)
for fn, values in [(fixed_position, (20,)), (configured, (20,))]:
    try:
        fn(*values)
    except TypeError:
        pass
    else:
        raise AssertionError("positional collision must fail")
configured.keywords["timeout"] = 7
assert configured() == ("job", 7)
assert configured(timeout=20) == ("job", 20)
print("keyword default overridden; positional collisions rejected; stored default updated")

A default call returns job and five. An explicit keyword returns job and twenty. A callback with two bound positional arguments receives an unwanted third value. The keyword-bound variant receives that parameter both positionally and by name. Both raise TypeError. The test relies on the exception type rather than version-specific message text.

Observe what the underlying function actually receives. A callback's name, representation, or creation log cannot establish which timeout a later executor used. A log saying five seconds can coexist with a twenty-second call. Where appropriate, record the effective configuration and its provenance at the real execution entry.

Give defaults and enforced limits distinct contracts

An overridable callback should document its configurable keywords and test both default and override calls. Moving a keyword to a stored positional argument can leave the default test green while breaking customization. Two separate expected results catch that migration.

A maximum wait can be checked in the final function against the value actually received. A wrapper can also expose only allowed fields and retain controlled configuration internally. Specify how it rejects extra arguments and exercise the actual object registered with the scheduler. Filtering timeout in one wrapper does not validate a second path that calls the original function.

For a wrapper enforcing five, twenty should produce a clear rejection while a default five should reach the function. These are proposed enforcement checks, outside the executed fixture.

Different fields may have different rules. A system-owned job identifier, a caller-shortenable timeout, and a capped retry count need separate contracts. Use allowed, out-of-range, and omitted inputs to verify what reaches the executor. This fixture implements no such business limits or scheduler.

Shared callbacks raise ownership questions too. Independent tasks can receive separate objects if configuration is fixed at creation. Runtime adjustments need a defined set of calls they affect. Execution here is sequential and verifies no concurrent mutation, queue, or thread behavior. The site's wrapper introspection article addresses signatures exposed to tools. Here the observation is the actual arguments delivered to the function.

Does a read-only keywords attribute make its dictionary immutable?

You cannot replace the attribute itself, but you can mutate the dictionary it refers to. The last control changes its stored timeout to seven. A call without an override now receives seven, while an explicit twenty still wins. This adds a post-construction change to the contract. Control ownership and exposure if callers must not alter stored configuration. A read-only attribute alone cannot establish immutable contents, and this single-object test supplies no cross-thread ordering guarantee.
