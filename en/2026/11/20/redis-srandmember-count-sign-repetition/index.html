Why can SRANDMEMBER return A three times from a set?

Use exact single-member replies and multi-member invariants to check signed counts, repetition, and source state.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-20 · Estimated read 11 min
Translations
zh-CN en

Article

Key takeaways

  • Positive count requests distinct members up to cardinality.
  • Negative count permits repeated draws from a nonempty set.
  • Random reads leave source membership intact.

A Redis set contains only A, yet SRANDMEMBER can return A three times. A negative count permits repeated draws. A positive count requests distinct members and is capped by cardinality. Repetition in the reply creates no duplicate members in the source set. Check the sampling result and source state independently.

The sign selects a sampling contract

With only candidate A, positive three can return one distinct item. Negative three can return A in three reply positions. The sole candidate removes uncertainty about which value appears, making it useful for checking count interpretation.

The documentation defines positive count as a distinct sample of at most the smaller of count and cardinality. A negative count permits repetition and returns its absolute size for a nonempty set. An empty or absent set returns an empty array. Ignoring the sign leads to wrong expectations about both length and repetition.

Choose the product policy first. Three distinct candidates require a positive count and a decision about insufficient candidates. Three draws with replacement can use a negative count. Converting those draws to a set afterward loses their occurrence count. Source membership and the record of draws have different contracts.

Use exact values for one member and invariants for several

This Redis fixture is unexecuted. Start with absent keys in a disposable database and exclude concurrent writers and expiry. One candidate establishes exact values. Three candidates establish size and membership constraints. A deliberately absent key controls empty input.

SADD review:srand:one A
SRANDMEMBER review:srand:one 3
SRANDMEMBER review:srand:one -3
SCARD review:srand:one
SADD review:srand:three A B C
SRANDMEMBER review:srand:three 5
SRANDMEMBER review:srand:three -5
SCARD review:srand:three
SRANDMEMBER review:srand:absent -3

Adding A should report one new member. Positive three returns one A, negative three returns three As, and cardinality stays one. The second set contains A, B, C. Positive five returns exactly those three distinct members in an unspecified application order. Negative five has five positions, each belonging to A, B, C. It need not include every candidate or follow a fixed sequence. Cardinality stays three.

Do not assert a particular ordering for the distinct sample. Compare length and membership separately. A consumer can sort afterward for display without treating its sorted result as evidence about sampling order. Nor should the repeated sample require A specifically to repeat; another candidate can supply the repetition.

The one-member negative control can require three As because the candidate space forces that value. It detects a client wrapper that stores reply entries in a set and collapses them to one. Testing only positive distinct samples would miss that representation bug. The multi-member control separately detects values outside the candidate set while preserving the number of draw positions.

Verify the draws and source under their own rules

SRANDMEMBER reads without removing the selected member. Using it to claim work therefore leaves the member available to another caller. A workflow requiring removal needs an interface with the corresponding mutation semantics and its own acceptance test. Logging “claimed” after a random read cannot establish exclusivity.

An application retaining each draw can identify reply slots one, two, and three independently from member identity. A single-member negative-three sample then has three records pointing to A. Replays preserve occurrence count without inventing duplicate source members. This proposed record shape is not persisted by the command fixture.

The site's sorted-set pop and key-lifecycle article covers a modifying operation. Unchanged cardinality here is a separate control showing that repeated reply positions do not insert duplicate source members. It supplies no guarantee that later calls repeat the same sequence.

Sampling quality also needs separate evidence. A five-item reply cannot establish fairness or a long-term distribution. Define any required probability property against the actual version and policy, then design appropriate observation and analysis. This fixture checks documented invariants and measures no statistical distribution.

A report can record source identity, the signed request, actual slot count, and membership checks. A short positive result may already equal cardinality. An empty negative result requires checking whether the key was nonempty at execution time. On a busy system, a later cardinality read is another observation rather than an atomic description of the earlier draw. The fixture assumes isolated sequential commands.

Are omitted count and count=1 the same reply shape?

Omitting count returns one member. An explicit one returns an array containing at most one member. Client libraries can wrap protocol results in their own types, so inspect the actual interface. Separate controls can ensure a parser does not iterate a member string as an array or use an array as one candidate identifier. This adds a protocol-shape condition. The main fixture always supplies count and leaves the omitted-count variation unexecuted.
