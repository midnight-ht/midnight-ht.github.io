Why can pytest run tests outside configured testpaths?

Compare pytest's default search roots with an explicit test path and retain the actual node identities.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-20 · Estimated read 11 min
Translations
zh-CN en

Article

Key takeaways

  • Testpaths supplies conditional default roots.
  • A supplied path can select another suite.
  • Verify the selected set using node identities.

Explicit test paths can select tests outside configured testpaths. The setting supplies default search roots when pytest is invoked from rootdir without explicit test paths. Check the actual arguments and node IDs to establish what a CI run selected.

A project may default to unit while an integration job appends integration to its command. A maintainer treating the configuration as an allowlist might think pytest ignored it. Both invocations can use the same configuration and still select different tests. Fix the environment and vary that argument to isolate the behavior.

One configuration, two nodes

Create these three files without extra conftests or third-party plugins. The test bodies are markers without product logic. Their passing outcome makes execution observable, while the oracle identifies their source nodes.

pytest.ini
unit/
  test_unit.py
integration/
  test_integration.py

Set the default in pytest.ini.

[pytest]
testpaths = unit

Place the first function in unit and the second in integration. Distinct names keep their reports distinguishable.

def test_unit_marker():
    assert "unit" == "unit"

def test_integration_marker():
    assert "integration" == "integration"

Use the same isolated pytest environment from the project root. Only the explicit path changes. Save each output and status.

export PYTEST_DISABLE_PLUGIN_AUTOLOAD=1
python -m pytest -v -p no:cacheprovider
python -m pytest -v -p no:cacheprovider integration

With Python 3.11.15 and pytest 9.0.2, the first run executed only test_unit_marker under unit. The second executed only test_integration_marker under integration. Both reported the same rootdir and pytest.ini, passed one test, and exited zero. Count and success alone cannot distinguish them; their path-qualified nodes can. Pytest testpaths reference

You can separately use --collect-only to examine collection without running tests. Preserve that invocation's own result. The receipts here came from executing both marker cases. Restore the actual plugin and collection environment before verifying a real job's final node set.

State which set the job selected

A basic job relying on defaults should record its invocation and effective configuration. An integration job can explicitly name its suite and preserve that set. Calling both “pytest passed” loses the obligation each fulfilled. Adding a directory to the configuration can also change a default invocation while leaving an explicitly selected job alone.

List important expected test identities, then compare the actual nodes. Ten passes do not show a particular integration case ran. If unit and integration both contain ten tests, a wrong argument can leave the same count. Paths and node IDs distinguish the sets before outcomes are examined. Investigate the entry point and collection rules when a required node is missing.

The rootdir and configfile lines identify the project root and configuration source. They do not establish which test-selection input took effect. Preserve the full command, working directory, configuration path, and environment when investigating a discrepancy. Align test paths before attributing the difference to missing configuration.

The setting also does not implement access control. Explicit collection does not grant file permissions or authorize running unknown code. The pipeline's permitted entry points and code trust boundary decide what it can execute. This example used two fixed local files.

Collection is only one part of acceptance. The two markers show which functions ran. They cannot establish database connectivity, device behavior, or provider acceptance. A job requiring those results needs the relevant preparation and actual test receipts. The collection experiment does not establish product-test adequacy.

Use the rule when adding a suite. A team might create an acceptance directory while keeping the basic job restricted to unit tests. A release job must explicitly select or otherwise include the new acceptance suite. Creating the directory alone cannot extend a fixed integration entry point. Verify the new node in the release receipt. Whether the default job should change depends on its own contract. This migration scenario was not executed.

Moving a test also changes its path identity even if its body stays the same. Save old and new collections and have review establish whether a node moved or a new obligation appeared. A passing old task cannot complete the migration if the intended new entry point lacks the corresponding node. Keeping the selection contract beside these changes makes later coverage history auditable.

What changes when pytest starts in a subdirectory?

The default-setting rule includes invocation from rootdir. In a third local run, pytest started inside integration with no explicit path. It still discovered the project's pytest.ini and reported the same rootdir, but ran the integration marker in the current directory. This adds a working-directory condition beyond the root-based main pair. Record the final working directory when a script changes it before invocation. Discovering a project root does not mean the process started there.
