Why can an entrypoint miss configuration created by PostStart?

Compare concurrent PostStart preparation with an ordered entrypoint and verify the application's first configuration read.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-20 · Estimated read 11 min
Translations
zh-CN en

Article

Key takeaways

  • PostStart has no guaranteed order relative to the entrypoint.
  • Chain required preparation through explicit completion.
  • Preserve the first read and container attempt identity.

PostStart is not guaranteed to complete before the container's main process. Kubernetes triggers the hook concurrently with the entrypoint. A main process can therefore read before a configuration-generating hook finishes. Put required preparation and application start into an explicitly ordered flow.

An application might open its configuration immediately while a PostStart handler creates the file. Being in one container does not establish write-before-read. A successful start can merely reflect a favorable schedule.

Record the first read

These unexecuted isolated-cluster fixtures compare two Pods. The first delays the hook for observation without promising a particular interleaving. The main process reads once, then waits and reads again.

apiVersion: v1
kind: Pod
metadata:
  name: hook-preparation
spec:
  restartPolicy: Never
  containers:
  - name: app
    image: busybox:1.36
    command:
    - sh
    - -c
    - |
      file=/tmp/prepared-config
      if test -f "$file"; then
        printf 'initial='
        cat "$file"
      else
        echo initial=missing
      fi
      while ! test -f "$file"; do sleep 1; done
      printf 'later='
      cat "$file"
      sleep 60
    lifecycle:
      postStart:
        exec:
          command:
          - sh
          - -ec
          - sleep 2; printf 'prepared\n' > /tmp/prepared-config.tmp; mv /tmp/prepared-config.tmp /tmp/prepared-config

The independent control writes and reads in one shell flow, with preparation failure stopping startup.

apiVersion: v1
kind: Pod
metadata:
  name: ordered-preparation
spec:
  restartPolicy: Never
  containers:
  - name: app
    image: busybox:1.36
    command:
    - sh
    - -ec
    - |
      file=/tmp/prepared-config
      printf 'prepared\n' > "$file"
      echo preparation-complete
      printf 'initial='
      cat "$file"
      sleep 60

Create them only in a disposable test context with image access and suitable policy. Capture each Pod's log, UID, current container state, and restartCount so observations belong to the same attempt. No API or container run was performed for this article.

The first Pod might report initial=missing then later=prepared, or it might read prepared immediately. Both fit the ordering guarantee. If the second command executes successfully, preparation-complete must precede initial=prepared. Its oracle follows explicit shell control flow. Missing logs from an unstarted Pod cannot establish absence of a race. Container lifecycle hook ordering

Give preparation a clear owner

For required local configuration, complete preparation before opening it. The application can manage this step, or an entry script can prepare successfully and exec the application. Verify the real completion condition. An accepted request that has not finished writing the file needs a readback or defined completion signal.

An independent preparation container needs init-container semantics and a shared-volume contract. Identical path strings in two containers do not establish shared files. Both fixtures here have one container and do not test that handoff. A probe can observe conditions; configuration production still needs an owner.

Some PostStart work may have no input dependency with the main process, such as an independent registration. Identify the required ordering before moving everything earlier. Concurrency can fit an independent action. A required dependency needs an explicit flow and corresponding acceptance check.

Preserve the initial failure

A later successful read cannot rewrite an earlier missing input. Label the initial and later observations separately. If a real application exits on the first miss, retain that attempt's error and identify any subsequent container. A later successful start is a separate event.

A useful unexecuted negative control makes preparation return an error and verifies that the entrypoint does not start the application. Restore preparation and check the current configuration value afterward. The acceptance condition is that incomplete preparation cannot proceed.

The two-second delay only opens an observation window. It cannot prescribe the scheduling of kubelet, runtime, and application. Use actual completion signals in production. Observing a missing initial read supplies evidence; failing to observe it once does not establish a valid dependency order.

The file publication step needs a clear success condition too. The hook writes a temporary path first, then moves it to the application read path after a successful write. Errors stop the flow. The comparison can focus on reading before or after publication. Validate real configuration before publishing it and provide its current content identity to the application. This does not verify durability across power failure; no such test was performed.

Does one successful PostStart establish exactly-once execution?

No. Hook delivery is intended to be at least once, and a handler can run repeatedly. Business side effects need their own idempotency identity and outcome verification. A successful call establishes that call's completion. This adds a repeated-delivery condition beyond the ordering experiment. No repeated-hook test was performed. Hook delivery guarantees
