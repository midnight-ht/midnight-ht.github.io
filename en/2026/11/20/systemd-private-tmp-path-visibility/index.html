Why can a service and the host see different files at the same tmp path?

Read distinct temporary markers from host and service views to explain PrivateTmp visibility and cleanup boundaries.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-20 · Estimated read 11 min
Translations
zh-CN en

Article

Key takeaways

  • One path string can identify different views.
  • Associate file evidence with its actual reader.
  • Verify cleanup in each relevant view.

A service and its host can use the same /tmp path and read different files. With PrivateTmp=yes, systemd gives the service a private temporary-directory view. Identify which view supplies a reading before investigating a missing file.

An operator may write a preparation marker on the host, then start a service that cannot open the same path. Matching path strings can lead to repeated permission changes while the views still differ.

Give each view a different marker

This unexecuted Linux system-service exercise requires PrivateTmp and a usable filesystem namespace environment. Use a disposable machine with unused fixture paths. Save the script as /run/zy20-private/worker.sh.

marker=/tmp/zy20-private-marker
if test -e "$marker"; then
  printf 'before='
  cat "$marker"
else
  printf 'before=absent\n'
fi
printf 'service-marker\n' > "$marker"
printf 'inside='
cat "$marker"
exec /bin/sleep 60

Save the unit at /etc/systemd/system/zy20-private.service. Confirm its shell and script path exist. Type=exec startup evidence does not replace the script's markers.

[Service]
Type=exec
PrivateTmp=yes
ExecStart=/bin/sh /run/zy20-private/worker.sh

After installing both files, run from a privileged host terminal. Inspect the logs for the current start while the service remains alive.

set -eu
marker=/tmp/zy20-private-marker
printf 'host-marker\n' > "$marker"
systemctl daemon-reload
systemctl start zy20-private.service
systemctl show zy20-private.service -p ActiveState -p PrivateTmp
invocation=$(systemctl show zy20-private.service -p InvocationID --value)
test -n "$invocation"
seen=no
for attempt in $(seq 1 30); do
  if journalctl "_SYSTEMD_INVOCATION_ID=$invocation" --no-pager -o cat |
    grep -F 'inside=service-marker'; then
    seen=yes
    break
  fi
  sleep 1
done
test "$seen" = yes
test "$(cat "$marker")" = host-marker

Expect before=absent and inside=service-marker in the service log, while the host still reads host-marker. Together they show different contents at one path string in different views. A successful start alone cannot establish that result. If markers are missing, retain the logs and state and investigate whether the script reached them. No Linux manager run was performed. PrivateTmp documentation

Associate the reading with its reader

A file handoff must identify where its writer and consumer run. If the service needs the file as input, choose an agreed shared or configuration path and verify its view and permissions. A host read cannot establish service input availability. Private storage may also be intentional, making host invisibility consistent with correct behavior.

A service readback cannot establish the host file's contents either. Tie each reading to its unit and start. Identical markers in both places would provide weak evidence of sharing; this fixture uses distinct values deliberately. A real handoff can add invocation identity and provenance, then read through the actual consumer.

PrivateTmp addresses temporary directories. Other mounts, credentials, and permissions have their own configuration. The fixture does not establish general isolation from host data or application compatibility.

Account for the stop boundary

The manual says the service's private temporary files are removed after stop. A script that exits immediately could cross that boundary before inspection. The sleep here leaves an observation window without guaranteeing an overloaded host will complete every command in time. Use state and log timestamps when interpreting readings.

The host marker belongs to another view. Cleanup of service-private files cannot establish cleanup of the host file. After the exercise, stop the unit, remove its definition and script, clear the fixture's host marker, and reload. Repeated runs need distinct content or an explicit start association so stale logs cannot satisfy a new check.

An unexecuted control can set PrivateTmp=no while keeping the rest fixed. Expect the service to read host-marker first, then replace it so the host reads service-marker. This changes sharing only. Choose the real service setting based on its intended file contract and validate it in the actual environment.

Wait for the service readback before asserting that the host still retains its own value. The script filters journal records by the current InvocationID so an earlier marker cannot satisfy the wait. If the marker does not appear within thirty attempts, fail and preserve that invocation’s log and state. This waiting logic was not executed; check field availability and journal permissions on the target host. The association establishes evidence identity without promising a log-delivery deadline.

Can two services share private temporary storage?

For ordinary PrivateTmp=true, the manual describes JoinsNamespaceOf= for joining a private temporary namespace, subject to the relevant unit configuration and lifecycle. PrivateTmp=disconnected uses an independent tmpfs and does not share with other units even through that relationship. This adds a second service and another mode to the host-versus-one-service example. Neither comparison was executed.
