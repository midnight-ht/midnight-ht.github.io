Why does changes return one when a trigger wrote two more rows?

Check one direct INSERT, two trigger audit rows, and their state after rollback in an isolated SQLite transaction.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-20 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • changes excludes auxiliary writes in lower-level triggers.
  • Check direct counts and audit identities separately.
  • A zero count on a view write does not establish no business effect.

An INSERT creates one task and an AFTER INSERT trigger writes two audit rows. SELECT changes() still returns one. It counts the direct statement and excludes auxiliary writes in lower-level triggers. Read the audit records separately to establish whether they were produced.

One statement and its wider effects

A local task table writes illustrative start and end audit markers for each new identifier. Expecting an affected-row count of three combines the direct INSERT and the trigger program. SQLite's changes result reports the former.

The SQL changes() function wraps changes64 and follows its counting rules. Trigger writes, foreign-key actions, and REPLACE conflict-resolution effects are excluded auxiliary changes. Both audit rows here belong to the trigger. A result of one says neither that the trigger wrote one row nor that it failed to run.

The result also belongs to a connection's most recently completed write statement. A later unrelated INSERT can change what a subsequent query observes. Associate the result with its statement promptly. A SELECT does not turn those separate effects into a business-wide aggregate.

Assert one direct row and two audit rows

The fixture creates real tables and a trigger in a fresh in-memory database. An explicit transaction allows before-and-after-rollback observations. The helper materializes query results as lists.

import sqlite3
from contextlib import closing

def rows(db, sql):
    return list(db.execute(sql))

with closing(sqlite3.connect(":memory:", isolation_level=None)) as db:
    db.executescript("""
        CREATE TABLE task(id INTEGER PRIMARY KEY);
        CREATE TABLE audit(task_id INTEGER, phase TEXT);
        CREATE TRIGGER task_added AFTER INSERT ON task BEGIN
            INSERT INTO audit VALUES(new.id, 'start');
            INSERT INTO audit VALUES(new.id, 'end');
        END;
    """)
    rows(db, "BEGIN")
    rows(db, "INSERT INTO task VALUES(7)")
    assert rows(db, "SELECT changes()") == [(1,)]
    assert rows(db, "SELECT id FROM task") == [(7,)]
    assert rows(db, "SELECT task_id,phase FROM audit ORDER BY phase") == [
        (7, "end"), (7, "start")
    ]
    rows(db, "ROLLBACK")
    assert rows(db, "SELECT id FROM task") == []
    assert rows(db, "SELECT task_id,phase FROM audit") == []
    print(sqlite3.sqlite_version, "direct=1; audit=2; rollback removed both tables' rows")

After insertion, changes is one, the task identifier is seven, and the audit table has both markers for seven. Ordering audit output by phase puts end before start alphabetically. That stabilizes comparison; it does not describe trigger execution time. Execution order needs its own evidence.

Each assertion matters. Without a trigger, the direct count can still be one. A count of two audit rows can also be misleading if they belong to another task or an old fixture. This fresh database checks the task identifier and both concrete phases. A service needs corresponding business identities to correlate audit with an operation.

Rollback then removes the new rows from both tables. It is a secondary failure control showing that a statement count is no commit receipt. The central question remains trigger exclusion. The example implements no transaction retries and supplies no guarantee about retracting external effects.

Read the audit contract directly

Define whether every task needs two audit rows or only certain transitions need an entry. Conditional triggers need inputs on both sides, with expected present and absent audit records. Treating the direct count as proof of trigger execution leaves those branches untested.

An application receipt can retain the direct count and a separate business check, such as having read both markers for task seven from the target database. Fill that check only after reading them. If an asynchronous worker continues the task, its completion belongs to a later event. This fixture has no worker or queue.

Batch writes need their own expected identities. Different tasks can invoke different rules, and a trigger can update existing rows. A one-to-two ratio in this example cannot define every production audit metric. Specify whether a metric counts direct rows, auxiliary rows, or business events before choosing its evidence source.

The site's REPLACE identity article covers another observation boundary around internal conflict-resolution deletion. Here an ordinary INSERT with two explicit trigger writes isolates the direct-count rule. It gives no reason to infer that a trigger failed from a displayed count.

An independently empty target database can serve as a negative control: it must not supply task seven or its audit. That rejects an accidental query sent to another database even if an unrelated direct count matches. This cross-database control is unexecuted.

Also record which connection invocation produced the result. A coincidentally matching number from another pooled connection proves nothing about this request. All fixture operations run sequentially on one connection; pool and concurrent-sharing behavior remain untested.

What if the INSERT targets a view with an INSTEAD OF trigger?

Changes made through that view yield a direct changes result of zero even when the trigger writes a real table. A consumer cannot interpret every zero as no business effect. Read the real target under the view's contract. This variation is unexecuted; the main fixture uses real tables. A supported view entry point needs a separate view and trigger control, expecting a zero direct count and the specified real-table identifier together.
