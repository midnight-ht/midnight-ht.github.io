Why can normalize detach a Text reference while leaving the text unchanged?

Trace three Text nodes becoming one while the content stays AB, and inspect what saved references represent afterward.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-20 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • Equal textContent does not establish equal node structure
  • A contiguous run combines its data in the first node
  • Check the current tree role of saved references

A container still displays AB, yet a saved reference to its right-hand Text no longer belongs to it. normalize can preserve content while changing text-node structure. For three adjacent nodes containing A, an empty string, and B, it combines the data in the first and removes the others. A saved object reference can outlive its role as the displayed text.

Equal text can have different tree structures

The DOM operation processes ordinary descendant Text nodes. It removes empty nodes and combines a contiguous run into its first node, removing the subsequent nodes from the tree. This article concerns ordinary HTML text and does not treat every node type as mergeable text.

The original three nodes already concatenate to AB. After normalization, a single Text contains AB. A textContent assertion passes in both states while missing the changed child count and reference ownership.

The operation does not allocate a replacement Text for this nonempty left node. That first node remains and its data becomes AB. The saved right object loses its parent. When changing right later fails to change the container, inspect tree membership instead of merely checking that the variable still holds an object.

Removal from the tree does not make a referenced object disappear. Code can still read and change right. Those changes affect the detached object. Whether the page changes depends on its connection to the current tree. No garbage-collection or memory-leak conclusion is offered here.

A complete three-to-one page

The script creates nodes explicitly so HTML indentation cannot add unexpected whitespace nodes. The container starts detached from the document, with its own parent-child relationships already established. It is attached after normalization alongside its recorded readings.

<!doctype html>
<meta charset="utf-8">
<title>Text node normalization</title>
<script>
addEventListener('DOMContentLoaded', () => {
  const parent = document.createElement('div');
  const [left, empty, right] = ['A', '', 'B'].map(text =>
    document.createTextNode(text)
  );
  parent.append(left, empty, right);
  const before = { text: parent.textContent, nodes: parent.childNodes.length };
  parent.normalize();
  const after = {
    text: parent.textContent,
    nodes: parent.childNodes.length,
    keepsLeft: parent.firstChild === left,
    leftText: left.data,
    emptyDetached: empty.parentNode === null,
    rightDetached: right.parentNode === null
  };
  const output = document.createElement('pre');
  output.append(JSON.stringify({ before, after }, null, 2));
  document.body.append(parent, output);
});
</script>

The standards-based expectation is AB and three nodes before, then AB and one node after. The first node remains left, whose data becomes AB. Both empty and right have null parents. These expectations were specified independently. No browser was run and the page's output is not presented as an observed local result.

Check that the initial count really is three before executing the operation. Starting with one node and finishing with one establishes no merge. Inserting a single string may create one Text from the outset, so it does not supply this fixture's three identities. Retain both input construction and final readings.

A separate negative control can change right.data afterward and reread the container. For this input the detached object should not change the container's text. Changing the current first node should. This distinguishes a populated variable from a reference to the currently displayed object. The main page does not execute those additional mutations.

Give editor references a lifecycle

An annotation system storing positions as Text objects needs to inspect what those objects represent after normalization. Saving an array of old childNodes fixes membership at that time; it does not prevent a tree operation from removing them. See live and static NodeList membership for that collection behavior.

A product can establish text structure before creating annotations and maintain it through a controlled entry point. Another design can relocate positions through its own model after structural changes. The choice depends on the editor's contract. This fixture establishes no safe migration for an arbitrary editor, and identical text alone cannot recover an unrecorded position reliably.

Node cleanup also differs from character normalization. This DOM method arranges Text structure. It does not generate an NFC comparison key or define character equivalence. Strings have a separate normalize method. Check the receiver and API when investigating a call with that name.

In a framework page, establish who owns the nodes. Internal references, editor selections, and later rendering may depend on the structure. This article gives the standard node results without validating manual tree modifications in a particular framework. Identify callers that continue using old references before designing their update path.

An evidence record can name every input node and inspect its parent, data, and relationship to the current first child before and after. Serialized HTML alone can conceal different text-node divisions. Without the original identities, a final AB cannot show which object was retained.

A second call on the same unchanged container should leave the one nonempty node intact. Retain its identity across both calls. Rebuilding a fresh container each time does not test repeated execution. Inserting another Text between calls changes the input structure and needs its own record before the next merge is assessed.

Will normalization merge text across an intervening element?

It will not skip that element to treat the two Text nodes as contiguous siblings. This adds an em element between the text runs. The outer children are Text, em, and Text. The merge stops at that element boundary.

Normalization still visits descendants, so adjacent Text nodes inside em can merge within it. Inspect the outer children and em's children separately. Preserving the outer boundary and tidying the inner run can happen together. Concatenated textContent does not establish that the nodes became one Text across an element.
