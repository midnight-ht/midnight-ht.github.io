Does an empty Scanner.Text mean EOF?

Compare blank lines, empty input, and an unterminated final line to detect early termination of a Scanner loop.

Updated 2026-11-19 · Estimated read 12 min
Translations

Article

Key takeaways

  • Use the Scan boolean to determine whether a token was obtained.
  • The default line splitter permits empty lines.
  • Check Err after scanning and define partial-result handling separately.

An empty Scanner.Text in Go does not establish EOF. The default line splitter can return a valid empty line. Scan reports whether a token was obtained. A loop that exits on an empty Text loses footer and every other line after that blank.

One string cannot represent both data and status

An operations import receives a simple line-based manifest: header, an empty separator line, then footer. The reader already has all the text, with no network or encoding issue. The business layer sees only header. Inspect the loop's termination condition before removing all blank lines to make the import proceed.

Scanner defaults to ScanLines. It produces lines with the ending marker removed, and a returned line may be empty. Two adjacent line endings therefore contain a real zero-length line. After Scan returns true, Text is a valid result. The application can preserve it, ignore it, or reject it under the grammar. A separator line should not terminate the entire read.

A false Scan means no next token, because input ended or an error occurred. Err reports a non-EOF error encountered during scanning; normal EOF gives nil. If the application breaks early, a nil Err does not prove it scanned the remaining input. The failing path loses footer because the application stops before EOF.

Five inputs distinguish a blank from the end

This Go teaching fixture is unexecuted. Every call starts with a fresh strings.Reader and compares all returned text. The switch deliberately enables the premature break so the same input has a successful and a failing path.

package main

import (
    "bufio"
    "reflect"
    "strings"
)

func lines(input string, breakOnBlank bool) []string {
    out := []string{}
    scan := bufio.NewScanner(strings.NewReader(input))
    for scan.Scan() {
        text := scan.Text()
        if breakOnBlank && text == "" {
            break
        }
        out = append(out, text)
    }
    if err := scan.Err(); err != nil {
        panic(err)
    }
    return out
}

func main() {
    cases := []struct {
        input string
        stop bool
        want []string
    }{
        {"header\n\nfooter", false, []string{"header", "", "footer"}},
        {"header\n\nfooter", true, []string{"header"}},
        {"", false, []string{}},
        {"\n", false, []string{""}},
        {"header\n\nfooter\n", false, []string{"header", "", "footer"}},
    }
    for _, c := range cases {
        if got := lines(c.input, c.stop); !reflect.DeepEqual(got, c.want) {
            panic(got)
        }
    }
}

The first case keeps three elements. The second deliberately keeps header alone. Identical source text isolates the mistake to the empty-Text branch. The lack of an exception cannot establish a complete import. A truly empty input yields no tokens, while an input consisting of one newline yields one empty token. Both look blank, but their structures differ.

Checking the whole list also preserves footer's position. Counting nonempty lines can conceal deletion of a meaningful separator. If the grammar permits dropping blank lines, skip a token after a successful Scan and continue, then require footer to remain. Skipping one result and ending the loop need distinct branches.

The fixture injects no read error. A controlled Reader should test that condition independently. Every short input returning nil Err says little about failures on other sources. Scanner also has a token buffer limit. Test a service's configured size and error policy separately; these short strings cover neither.

Report where the import stopped

A manifest with section identifiers can record the last processed section and the reason scanning stopped. A full read followed by a missing-footer validation error differs from a function returning at a separator. The former directs attention to generation or formatting; the latter points to the loop. Recording any nonempty output as success obscures that distinction.

A service acceptance test can place a required footer marker after a blank. The correct implementation must see it, and the faulty one must omit it. Add a case where blank filtering is intentional and expect just header and footer. That accepts filtering while rejecting a break disguised as a filter. Specify whether blank lines count toward reported totals so a physical line and a logical record do not receive an ambiguous shared number.

Line-based text has its own grammar. CSV can place a newline inside a quoted field, and ScanLines does not track that state. Use a CSV reader for a CSV source. The site's CSV newline and record-boundary article covers that separate format. This fixture assumes ordinary line records without a multiline field grammar.

Specify who owns the original reader, too. If a caller plans to resume reading it after this function returns, processed line count does not establish the underlying reader position: Scanner can read ahead. This fixture gives the reader to one scan and does not hand an early-stopped source to a second reader.

Decide whether callers may receive partial results after an error. The fixture panics on a read error to fail its assumptions. A service usually needs a structured error and an explicit partial-result policy. Whichever policy applies, tell the caller whether scanning reached a normal end. The example implements no database writes or external commit.

Does an unterminated final line lose footer?

ScanLines returns the last nonempty line even without an ending newline. The first and fifth cases differ only in that final marker and expect the same three strings. Appending a newline is unnecessary to rescue this case. A protocol may independently require a final terminator, which needs its own validation. Keep final-line presence, termination syntax, and read errors distinguishable so a missing final newline cannot be mistaken for a missing record.
