Why can Promise.resolve(load()) miss a synchronous throw?

Locate a synchronous throw before or inside an adapter. Use a fixed error and event list to test Promise.try invocation and reaction timing.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile

Translations
zh-CN en

Article

Key takeaways

  • Arguments are evaluated before resolve receives a value
  • try includes callback invocation in the promise boundary
  • Test invocation and reaction timing separately

A plugin sometimes returns a value and sometimes a promise. Its caller uses Promise.resolve(load()) to put failures into one chain. A synchronous throw escapes before that expression produces a promise. The boundary has to include invocation as well as the returned value.

Locate the call that can throw

JavaScript evaluates load() before passing its result to resolve. If that evaluation throws, resolve never receives a value. Adding catch afterward doesn't give the expression a returned promise on which to attach it.

Promise.try accepts the function. It calls that function inside its own operation, resolves an ordinary return value, and rejects on a thrown error. Passing load rather than the result of load() puts invocation inside the boundary. The same thrown object becomes the rejection reason.

The callback runs synchronously. Its initial side effects can occur before try returns. Promise reactions still follow their normal scheduling; synchronous callback execution doesn't imply a synchronous catch handler.

Calling load inside then on an already resolved promise can also represent the throw as rejection. Its invocation waits for the reaction job. The final result can be the same while the start time differs. Check whether a caller depends on starting immediately.

Preserve the error and the order

This local script uses a function that always throws the same error, a fixed value, and an event list. It makes no network requests or retries. The final wait joins the work created for the ordering comparison.

import {strictEqual as equal, deepEqual, rejects} from 'node:assert';

const failure = new Error('fixture load failed');
function load() { throw failure; }

let caught;
try {
  Promise.resolve(load());
} catch (error) {
  caught = error;
}
equal(caught, failure);

await rejects(Promise.try(load), error => error === failure);
equal(await Promise.try(() => 42), 42);
const events = [];
const immediate = Promise.try(() => events.push('try callback'));
events.push('returned');
const deferred = Promise.resolve().then(() => events.push('then callback'));
deepEqual(events, ['try callback', 'returned']);
await Promise.all([immediate, deferred]);
deepEqual(events, ['try callback', 'returned', 'then callback']);
console.log('Throw identity, return value, and invocation order passed.');

The assertions passed in local Node. The directly evaluated expression throws to the outer try/catch. Passing the function to Promise.try preserves that error as a rejection. The ordinary value is 42. The synchronous event list has try callback before returned. Waiting adds then callback.

The checks cover failure ownership, value preservation, and invocation time separately. Testing only an awaited value misses the escaped throw. Checking only the error class can miss code that replaced the original error. The event list detects a change from immediate to deferred invocation.

A returned promise is followed by the resolving process. Receiving the wrapper promise does not establish that plugin work has completed. Await success or handle rejection under the operation's own rules. The wrapper supplies no cancellation or rollback policy.

Retain the plugin's other contracts

An object method can depend on its receiver. Extracting it as a function loses that relationship. Call it as an object method inside the supplied function where needed. The wrapper cannot infer which instance originally owned load.

The successful shape remains another contract. One plugin might return rows while another returns rows plus paging metadata. Both can be awaited, but the consumer still needs to know what it receives.

Check the actual deployment runtimes. This local execution establishes support in the recorded Node version, without establishing old browser support. Compare existing tests for ordinary values, promises, and synchronous throws before replacing an adapter.

If the boundary should include preparation, put input reading, validation, and invocation inside the supplied callback. Keep the failing stage in diagnostics. One returned promise does not require using the same user message for missing input and a plugin rejection.

An application regression can add a plugin that returns a rejected promise. Verify that it reaches the intended failure path while retaining its origin. The published fixture checks synchronous throws, values, and ordering; it does not execute that additional application case.

Each try call actually invokes the callback. It is not a cache of earlier work. Repeating an adapter around a write starts another operation, so use the business retry contract and preserve each operation identity.

Can evaluation of an argument throw outside this boundary?

Yes. In Promise.try(load, makeInput()), makeInput() is evaluated before try is called. If it throws, that error never reaches the callback invocation inside the method.

To include input construction, supply a callback that calls load(makeInput()). Test the same failing input. The relevant distinction is which invocation contains the potentially throwing operation, even if both expressions mention try.

For adapting older callback methods, see receiver and custom conversion contracts in promisify.
