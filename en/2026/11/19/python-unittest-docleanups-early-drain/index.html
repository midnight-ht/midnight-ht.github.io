How can unittest release registered resources before the test ends?

Verify early cleanup, a repeated drain, and newly registered callbacks with a two-phase unittest event sequence.

Updated 2026-11-19 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • An early drain pops the current callbacks.
  • A drained batch does not execute again.
  • Later callbacks still participate in final cleanup.

A unittest test can call doCleanups() before it ends to release callbacks already registered on its cleanup stack. The method pops callbacks in reverse order, so the drained batch will not run again at normal test completion. New callbacks can still be registered afterward.

This addresses a specific phased test. The first phase acquires A and B and needs to release both before the next phase acquires C. Waiting for end-of-test cleanup could leave the earlier resources held during that second phase. Manually closing a resource while leaving its registered callback in the stack could instead close it twice. Make the timing and ownership explicit.

Assert the intermediate state and final cleanup

This program records acquisition and release in memory. It does not handle real files or remote systems. Each callback captures a fixed resource name as its argument. The test drains the stack, checks that B and A were released, and drains again to check for repetition. It then registers C and ends normally. A separate TestResult runs the case and the outer program verifies the full sequence.

import unittest

events = []
record = events.append

class PhasedCase(unittest.TestCase):
    def setUp(self):
        for name in ("A", "B"):
            record("acquire-" + name)
            self.addCleanup(record, "release-" + name)

    def test_phases(self):
        self.doCleanups()
        self.assertEqual(events, [
            "acquire-A", "acquire-B", "release-B", "release-A"
        ])
        self.doCleanups()
        self.assertEqual(len(events), 4)
        record("acquire-C")
        self.addCleanup(record, "release-C")
        record("test-end")

    def tearDown(self):
        record("tearDown")

result = unittest.TestResult()
PhasedCase("test_phases").run(result)
assert result.wasSuccessful(), (result.errors, result.failures)
assert result.testsRun == 1
assert events == [
    "acquire-A", "acquire-B", "release-B", "release-A",
    "acquire-C", "test-end", "tearDown", "release-C",
]
print(events)

Running this script with Python 3.11.15 returned zero. Its events were acquisition of A and B, release of B and A, acquisition of C, test end, tearDown, and release of C. The outer program also checked that one test ran without an error or assertion failure. The second early drain added no events. C remained registered until after tearDown. Checking only that all three names were eventually released would miss the phase boundary. Without the first early drain, the final sequence could still include all resources, but A and B would have been held while C was used. That modified branch was not run. The intermediate event assertion distinguishes eventual cleanup from timely cleanup.

LIFO can reflect resource dependencies. Acquire the underlying A, then B that depends on it, and cleanup releases B before A. The framework does not infer that relationship. Registering in the wrong order gives a different release sequence. Name each acquisition and corresponding release before treating order as evidence. Binding callbacks to the specific handle can also avoid a closure later reading a different resource.

Assign the entire drained batch to one phase

Decide which resources belong in the same stack. The early drain handles the callbacks registered at that point. If A must survive the second phase while B must end earlier, putting both in one drained batch cannot express the intended lifetime. Use a narrower resource scope or separate tests where the lifetimes are clearer. Let the actual dependency define the boundary.

Explicitly closing a resource without adjusting the cleanup plan introduces a separate risk. Rely on repeated close only if the resource's API supports it. The fixture's callbacks append a new event every time to expose repetition. For a real connection, check the resource's state too and verify later code does not use an invalid handle. An event marker cannot establish that a server removed an object.

Preserve the original test result when an outer program runs cases this way. This fixture uses TestResult to inspect the framework sequence and then checks whether it succeeded. A production verifier should retain errors, failures, and the cleanup trace. Its zero exit should mean the intended observations matched. A wrong sequence should fail the outer check and expose the complete trace so a reviewer can distinguish a behavior failure from a resource-boundary mistake.

A second-phase failure is another useful extension. With an isolated resource, make C's use raise an exception and verify that its cleanup receipt and original error both survive. That branch was not run. A crash or forced process termination also needs a separate resource expiry or recovery mechanism. Python callbacks do not perform cross-process recovery. Associate shared-environment resources with the current test so cleanup cannot claim another run's work.

Resource names can repeat between phases. Releasing a session in phase one and acquiring another session in phase two gives two different handles with one name. A final record of one session release cannot establish which was returned. Record the acquisition phase or handle identity beside the resource name and verify each release separately. A, B, and C are deliberately distinct names in the fixture. This extension was not run.

Does enterContext register an exit when entering fails?

The enterContext helper registers the context manager's exit method only after successful entry. If __enter__ raises, the context implementation owns any partial acquisition. There is no newly registered exit callback to perform that compensation. The method was added in Python 3.11. The main program registers three callbacks directly and did not exercise contexts or failed entry. Verify a real context's successful exit and its failed-entry residue independently.
