Why can a service exceed MemoryHigh without being killed immediately?

Distinguish systemd reclaim pressure from the hard memory limit and inspect effective values alongside cgroup events.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-19 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • MemoryHigh drives reclaim and throttling.
  • MemoryMax provides a separate hard boundary.
  • Read effective thresholds and event counters together.

A service can survive after exceeding MemoryHigh and still behave according to systemd's memory-control design. That threshold drives reclaim pressure and throttling. MemoryMax supplies a separate hard boundary. Read the effective controls before interpreting whether the process survived or exited.

A release check can misread this easily. A configuration says thirty-two megabytes and a later sample shows more. Calling the limit ineffective skips a step. Check which boundary was configured and whether reclaim pressure occurred. Usage staying below the threshold also cannot establish that throttling was exercised. A graph alone cannot replace effective settings and event counters.

Identify the two controls

In a unified cgroup v2 hierarchy, MemoryHigh maps to memory.high. Crossing it subjects processes to reclaim and throttling. The kernel documentation says exceeding high does not itself invoke the OOM killer, and the boundary can be breached under extreme conditions. MemoryMax maps to memory.max. Reaching that hard boundary without being able to reclaim enough can invoke OOM in the group. The kernel also documents temporary overshoot and allocation failures that do not invoke OOM. Exceeding a number does not promise a kill event. Kernel memory interfaces

Both settings can be used together, with high for normal control and max as a further defense. Pressure may slow the program and affect requests, but those effects need measurement. A threshold does not imply a fixed latency penalty. A surviving process may still have been constrained. Systemd memory-control settings

Collect evidence from an isolated workload

This is an unexecuted Linux test-machine exercise. It requires a unified hierarchy, the memory controller, a suitable systemd version, and sufficient spare capacity. Use a disposable machine. Save the Python program as /run/zy19-memory/allocate.py. It allocates forty-eight one-megabyte arrays and touches pages so the observation is not just virtual address reservation. The interpreter and allocator also consume memory.

import time

blocks = []
for index in range(48):
    block = bytearray(1024 * 1024)
    for offset in range(0, len(block), 4096):
        block[offset] = 1
    blocks.append(block)
print("allocation-ready", len(blocks), flush=True)
time.sleep(60)

Save the unit as /etc/systemd/system/zy19-memory.service. Use the interpreter path that exists on the test machine. The workload holds its allocations for a minute to allow inspection. That duration does not predict a reclaim count.

[Service]
Type=exec
ExecStart=/usr/bin/python3 /run/zy19-memory/allocate.py
MemoryAccounting=yes
MemoryHigh=32M
MemoryMax=96M

After starting it, inspect effective properties and this run's journal. Observe allocation-ready before treating the sample as post-allocation. Run the following in another terminal on the same host and in the same cgroup namespace.

unit=zy19-memory.service
systemctl show "$unit" -p ActiveState -p MemoryCurrent \
  -p EffectiveMemoryHigh -p EffectiveMemoryMax -p ControlGroup
group=$(systemctl show "$unit" -p ControlGroup --value)
test -n "$group"
base="/sys/fs/cgroup$group"
for file in memory.current memory.high memory.max memory.events.local; do
  printf '\n%s\n' "$file"
  cat "$base/$file"
done
journalctl -b -u "$unit" --no-pager

Reload the manager after installing the definition and explicitly start the fixture unit. Timestamp observations. A baseline can set high to infinity while retaining the same max, followed by a fresh run with high set to thirty-two megabytes. Compare effective values and the local high-event counter, with snapshots before and after allocation. If the process exits before its marker, inspect its original error and OOM-related events before interpreting the case.

The oracle is a semantic relationship. Increasing high events without oom_kill can be consistent with reclaim at the high threshold. No events with an effective threshold calls for checking whether usage actually crossed it. Do not require a fixed event count. Record unsupported fields if the kernel lacks an interface. No service was started or memory pressure applied for this article. Stop the fixture and remove its definition and script after a real exercise.

After installing the script and unit, run systemctl daemon-reload and systemctl start zy19-memory.service in the preparation terminal. Repeat the observation procedure for each run and reload after configuration changes. Select the current start interval so an older allocation marker cannot satisfy this run.

An event value is a count. A nonzero reading alone does not tie it to the current phase. Keep before-and-after values and control-group identity, then compare the same group. A quickly exiting process may leave no group to inspect afterward. Arrange collection in advance and retain the receipts outside the fixture group. If the group is recreated or the count resets, treat the snapshots separately. This collection was not run. It defines what evidence a later exercise should preserve.

Verify more than process survival

A process may retain its working set but slow down enough for application requests to time out. Survival and an effective setting do not establish the response contract. Use controlled requests to record behavior and align their timing with pressure events. An application that drops its own cache can reduce usage without exiting. Decide whether the operational goal is lower memory, acceptable response, or isolation, then collect evidence for that goal.

A low-load control is useful too. A workload far below high can finish normally without exercising reclaim. Let a normal control verify the program can start, then inspect resource events during pressure. This small program does not test application caching, swap strategy, or system-wide exhaustion, and cannot establish product capacity.

Can a larger child MemoryMax override a parent slice?

No. Systemd reports EffectiveMemoryMax using the tighter limits in the unit and its parent slices, capped by physical memory. A ninety-six-megabyte child setting is insufficient evidence if the parent is stricter. Inspect the effective hierarchy and relevant events before loading the service. This introduces the parent-limit condition. The main fixture assumes its effective boundaries match the proposed values and does not configure a parent-slice comparison.
