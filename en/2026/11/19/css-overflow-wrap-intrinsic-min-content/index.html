Why can break-word and anywhere yield different intrinsic widths?

Compare one token under two wrapping values and separate visible line breaks from intrinsic sizing.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-19 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • Anywhere opportunities contribute to min-content sizing
  • Break-word opportunities do not contribute to that size
  • Separate fixed-width wrapping from intrinsic-size tests

The long identifier wraps, yet its card remains surprisingly wide. Switching from break-word to anywhere changes the width. Both values can break a long token in a constrained line, but they contribute different opportunities to min-content sizing. Check how the box gets its width before examining how its text fills that width.

Similar visible breaks can produce different intrinsic sizes

CSS Text Level 3 explicitly distinguishes the values. Soft wrap opportunities introduced by anywhere count when calculating min-content intrinsic sizes. Those introduced by break-word do not. A screenshot of both values wrapping inside a narrow fixed box cannot establish that their intrinsic widths are equal.

For this fixture, think of min-content width as the width obtained by narrowing the content at the allowed opportunities. The input is an ordinary Latin token without spaces. There are no images, tables, or additional minimum-width constraints. With anywhere, opportunities inside the token enter the calculation, allowing a much narrower result than treating the entire token as indivisible. No particular pixel width is promised across fonts.

This does not remove break-word's ability to handle overflowing text. Give its box a narrow available width first and it can still wrap the token. The distinction concerns intrinsic sizing. A card whose size depends on that content contribution can therefore receive a different input before space is allocated.

Compare exactly the same token

This complete static page uses two inline-block elements with min-content widths. Their font, text, border, and other breaking controls are identical. The two classes change only the value under investigation. There is no flex minimum adjustment or script assigning another width.

<!doctype html>
<meta charset="utf-8">
<title>Intrinsic wrapping comparison</title>
<style>
.sample {
  display: inline-block;
  width: min-content;
  font: 16px monospace;
  white-space: normal;
  word-break: normal;
  border: 1px solid;
  vertical-align: top;
}
.anywhere { overflow-wrap: anywhere; }
.breakword { overflow-wrap: break-word; }
</style>
<span class="sample anywhere">abcdefghijklmnopqrstuvwx</span>
<span class="sample breakword">abcdefghijklmnopqrstuvwx</span>

The standards-based prediction is that the anywhere sample has a smaller content width than the break-word sample. Read their bounding widths and inspect the lines. Identical borders add the same amount on either side and do not change this ordering. A particular font's pixel result is not the general acceptance criterion.

As a negative control, give both classes break-word. The width difference should disappear. If it remains, inspect the input, overriding styles, and font selection. This control checks whether the comparison isolates the property. A complex production layout still needs its own analysis.

No browser was run and no pixel measurement or screenshot was collected for this article. The page supplies a standards-based prediction and a comparison that can be executed manually. A product test should record its browser version, font, and zoom before archiving actual dimensions. Those records would establish the observed relationship in that environment.

Use the same measurement layer on both samples. Comparing one content box with the other border box mixes definitions. This fixture has equal borders and no padding. A component library may add padding or a minimum width, so inspect those constraints when integrating it. An extra minimum can mask the difference by raising both widths to the same value. That result does not make the two sizing rules identical.

Identify the card's width source

In a card with a fixed width, both values may wrap successfully. That test observes layout after the available space has been established. Keep it to check the final presentation, and retain an intrinsic-size comparison to investigate the cause.

Real URLs and order identifiers may have different opportunities at punctuation or spaces. Fonts and language-specific rules also matter. The fixture deliberately repeats the same token without punctuation to keep those variables out of the comparison. Archive the actual input when substituting production data.

Changing word-break at the same time introduces another control over line breaking. Start with the fixture's normal setting and restore business styles one at a time. That separates newly introduced opportunities from those already available in the original input.

A flex item's automatic minimum brings another constraint into the layout. For a requirement to let an item shrink below that minimum, see flex automatic minimum sizes and shrinking. Here the question is how text opportunities enter min-content sizing. Check which constraints the containing layout actually uses when applying the result.

An acceptance record should identify the token, the width source, and the relationship being checked. For example, the intrinsic-size sample becomes narrower while the fixed-width business card still exposes the complete identifier. If multiline identifiers are allowed, also verify that copying preserves the characters. Visual breaks do not create new data characters.

Will anywhere force wrapping with white-space: nowrap?

That value alone will not force it. This adds a condition that forbids soft wrapping. The specification says overflow-wrap only has an effect when white-space allows wrapping. Replacing normal with nowrap in the shared fixture rule invalidates the earlier wrapping and narrowing prediction.

Keep the token and other styles unchanged for this test. Inspect the effective white-space value before examining width and overflow. A single-line requirement needs a suitable container and overflow presentation. A multiline requirement needs wrapping to be permitted. Repeatedly switching the breaking value cannot remove this new restriction.
