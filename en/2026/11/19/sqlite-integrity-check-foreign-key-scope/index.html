Why can SQLite integrity_check return ok with an orphan row?

Compare structural success with a foreign-key violation in an isolated database, then verify the repaired relationship and preserved child.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-19 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • integrity_check excludes foreign-key violations.
  • Use the four foreign_key_check columns to locate a failing relationship.
  • Parse structural and relationship checks using their distinct success results.

SQLite integrity_check can return ok while an order references a missing customer. That check excludes foreign-key errors. A restore acceptance procedure that needs relationship validation should also run foreign_key_check and interpret its child table, row identifier, parent table, and constraint number.

Structure and references can have different results

Suppose a migrated database has parent customers and child orders. Customer one exists, while order ten references customer 999. Pages, indexes, and storage can be structurally normal while the relationship is broken. Stopping at ok leaves the problem for business code trying to read the customer later.

The integrity check covers many internal problems and can find UNIQUE, CHECK, and NOT NULL errors. The official documentation explicitly excludes foreign keys and directs callers to foreign_key_check. Preserve the names of individual checks in a report so its recipient can identify which conditions were tested.

foreign_key_check returns one row for each violation. It reports the referencing child table, usually the child's rowid, the referenced parent table, and a foreign-key number. The last column is not the missing parent identifier. Match it to foreign_key_list when a child table has several constraints. Misreading the child rowid as the referenced value would send someone looking for customer ten in this fixture.

Produce ok and a relationship error on the same database

The local fixture explicitly disables foreign-key enforcement on its connection and reads the setting back. It uses a disposable in-memory database to construct an existing bad reference, with no project database involved. After setup, it checks both results, supplies the missing parent, and checks the relationship again.

import sqlite3
from contextlib import closing

def rows(db, sql):
    return list(db.execute(sql))

with closing(sqlite3.connect(":memory:")) as db:
    db.execute("PRAGMA foreign_keys=OFF")
    assert rows(db, "PRAGMA foreign_keys")[0] == (0,)
    db.executescript("""
        CREATE TABLE parent(id INTEGER PRIMARY KEY);
        CREATE TABLE child(
            id INTEGER PRIMARY KEY,
            parent_id INTEGER REFERENCES parent(id)
        );
        INSERT INTO parent VALUES(1);
        INSERT INTO child VALUES(10, 999);
    """)
    assert rows(db, "PRAGMA integrity_check") == [("ok",)]
    assert rows(db, "PRAGMA foreign_key_check") == [
        ("child", 10, "parent", 0)
    ]
    db.execute("INSERT INTO parent VALUES(999)")
    db.commit()
    assert rows(db, "PRAGMA integrity_check") == [("ok",)]
    assert rows(db, "PRAGMA foreign_key_check") == []
    assert rows(db, "SELECT id,parent_id FROM child") == [(10, 999)]
    print(sqlite3.sqlite_version, "structural ok; FK orphan found; parent repair verified")

The initial oracle requires one ok row from integrity_check and exactly child, ten, parent, zero from foreign_key_check. Inserting parent 999 empties the violation result while integrity_check still returns ok. Finally, order ten must remain and still reference 999. That guards against a repair that merely deletes the child. Two identical structural results and two different relationship results establish the checks' different scope.

Adding a customer is a controlled test repair, with no claim that it is the correct business action. A missing parent might indicate a bad migration mapping. The right action could change the reference, isolate the record, or supply a verified parent. This fixture changes only the relational condition and preserves the child. A business restore needs its own repair decision and data provenance.

Turning on foreign_keys at a connection cannot serve as a record of scanning existing data. The site's SQLite foreign-key connection article covers enforcement scope. This fixture adds a diagnostic comparison with a specific location for an existing orphan. Keep command names and their actual results in the restore report.

Leave enough information for the next operator

A violation report can retain child table, child location, parent table, and constraint definition alongside the database or connection identity checked. Checking a temporary copy and then querying the original says nothing about whether the copy was repaired. Complete the same checks on the restore target and retain before and after evidence with stable business identifiers.

An error count can show that problems remain but cannot tell retries apart. One remaining violation might be the old one or a different one. For this fixed fixture, compare all four columns. Larger reports should preserve sufficient controlled identifiers to locate failures. These are teaching integers, with no real customer data.

This in-memory setup has no concurrent writer, so the inserted parent explains the changed result. A live database can change after the check. Tie the report to an observation time and scope. A migration can place the check before opening writes; a continuously updated system needs to explain which changes occurred afterward. Passing both checks provides no guarantee about every future write.

If reports are written to files, retain the target database identity and backup batch. Before comparing a later diagnostic, check those identities so an empty result from an earlier restore cannot be counted as this run passing.

Parse the two success shapes independently in automation. integrity_check succeeds with an ok row; foreign_key_check succeeds with no rows. Treating success as no output would reject the structural success. Treating any returned row as success would accept an orphan report. The initial state above is a useful negative control for the latter mistake.

Does a WITHOUT ROWID child report its business key in the second column?

For that table kind, the second foreign_key_check column is NULL. SQLite does not substitute the business primary key for rowid. A diagnostic consumer needs another controlled lookup of stable fields using the relation definition. A null row identifier does not erase the violation described by the other columns. The executed fixture uses an ordinary rowid table and leaves this variation unexecuted. Add a violating WITHOUT ROWID sample when that schema is actually supported and verify that the report still locates the row for remediation.
