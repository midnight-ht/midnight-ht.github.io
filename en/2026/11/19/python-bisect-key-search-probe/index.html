Why does bisect with a key still reject a whole search record?

Check probe types, tied-score boundaries, and inserted record identity across bisect and insort.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-19 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • A bisect probe belongs directly to the comparison-key domain.
  • insort extracts the new record's key to search and inserts the record itself.
  • Exact lookup needs bounds and equality checks after locating an insertion point.

The records are sorted by score, and bisect_left has a key that extracts score. Why does searching with a new dictionary still compare a dictionary with an integer? The search applies key to the records in the list. Its probe must already belong to the comparison domain. To search for score twenty here, pass the integer twenty.

Records in the list and values at the search boundary

Imagine four rows ordered by score: A has ten, B and C have twenty, and D has forty. A user enters a score to find its position. They have no complete record to supply and need no invented identifier. The extractor converts list members to scores; the caller supplies the number to compare.

bisect_left returns a left insertion point that preserves order. It does not first establish equality. With two records at twenty, the left boundary precedes B and the right boundary follows C. Together the boundaries can describe the matching score range. The list must already be ordered by the same key and stay unchanged during the search. Passing key performs no preliminary sort.

A dictionary probe fails because the middle list element becomes an integer while the caller's dictionary remains a dictionary. There is no ordering defined between those values. Renaming the score field or supplying an equivalent extractor leaves the mismatch intact. Decide whether the public search parameter represents a score or an entire business record.

Three positions and one inserted record

The fixture keeps distinct identifiers for tied scores. Left and right boundaries and an absent score have independent expected positions. It checks the invalid probe separately, then inserts a full record into a shallow copy of the list.

from bisect import bisect_left, bisect_right, insort_right
from operator import itemgetter

rows = [
    {"id": "A", "score": 10},
    {"id": "B", "score": 20},
    {"id": "C", "score": 20},
    {"id": "D", "score": 40},
]
score = itemgetter("score")
assert bisect_left(rows, 20, key=score) == 1
assert bisect_right(rows, 20, key=score) == 3
assert bisect_left(rows, 30, key=score) == 3
try:
    bisect_left(rows, {"id": "X", "score": 20}, key=score)
except TypeError:
    pass
else:
    raise AssertionError("whole record must not be the score probe")
updated = rows.copy()
insort_right(updated, {"id": "X", "score": 20}, key=score)
assert [r["id"] for r in updated] == ["A", "B", "C", "X", "D"]
print("score probes: 1,3,3; record insertion: A,B,C,X,D")

Twenty produces boundaries one and three. Thirty produces three although no record has score thirty. A valid position therefore cannot prove presence. The dictionary probe must raise TypeError. The insertion control puts X after the existing twenty-score records and before D, with a full assertion on the identifiers.

insort_right accepts a new record. It applies key to that record for the search, then inserts the original object. Moving the fix from a search call mechanically into an insertion call would supply an integer where a record is needed. Depending on the extractor, that could fail during key extraction or put an invalid element in the collection. Exercise the actual API and check the resulting record shape.

Name the parameter for the value it represents

A search method can accept score and an addition method can accept record. If an upstream caller has a record but needs its score boundary, extract the score explicitly before searching. If ordering later includes a second field, its comparison domain becomes a compound key. An old single-score probe then needs a newly specified range contract.

Ties belong in the test. With only ten and forty, left and right boundaries can coincide, leaving the choice untested. B and C make the distinction visible. Check both boundaries and the identifier order after insertion. Which side a new tied record should enter is a service decision; the algorithm supplies both options.

Mutation can also invalidate order. Change A's score from ten to fifty in place and the list no longer meets the search premise. One plausible answer on that list proves little. A service might remove and reinsert changed records or rebuild order at an appropriate boundary. The site's article about merging sorted sources covers another caller-owned ordering premise. Here the issue is the search probe and its insertion boundary.

This local test covers comparisons, returned positions, and insertion identity on a short list. It measures no concurrency control, database index behavior, or performance. Inserting into a list moves later elements; a logarithmic search cannot establish a logarithmic cost for the entire insertion. A request-local copy isolates the fixture, while shared mutable lists need their own coordination.

Does a returned position mean an equal record exists?

Thirty returns position three, occupied by forty. For exact lookup, first check that the position is within the list, then compare that record's key with the probe. Fifty would return the list length, making the bounds check essential before indexing. This adds a requirement that the key already exist. Specify whether the API returns an insertion point, a matching interval, or an exact record, then test an absent interior value and a value beyond the end separately.
