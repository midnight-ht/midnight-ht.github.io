Why can CTest fail a process that returns zero?

Compare CTest's inverted and ordinary normal-exit rules, then verify the identity of a negative test's rejection.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-19 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • WILL_FAIL reverses normal zero and nonzero criteria.
  • Verify why the program rejected the input.
  • Record runner and process outcomes separately.

A test process can exit normally with zero and CTest can mark it failed. With WILL_FAIL, the runner reverses the normal zero-versus-nonzero criteria. If a negative test unexpectedly accepts input it was meant to reject, that success needs to become visible.

Give the test a precise obligation. A command-line validator receiving a configuration without a required field should reject it with a nonzero status. A later zero exit means the intended rejection did not happen. This is distinct from mapping a dedicated outcome to a skip. The test ran, and the question is whether it rejected the input as required.

Build an inversion matrix with one tool

Save this as CMakeLists.txt. The project needs no compiler. Its test commands use the configured CMake executable, whose true and false commands return zero and one normally. Both negative controls set WILL_FAIL. A third test stays an ordinary success to check the runner independently.

cmake_minimum_required(VERSION 3.20)
project(InvertedExit NONE)
enable_testing()
add_test(NAME expected_rejection COMMAND "${CMAKE_COMMAND}" -E false)
add_test(NAME unexpected_acceptance COMMAND "${CMAKE_COMMAND}" -E true)
set_tests_properties(expected_rejection unexpected_acceptance
                     PROPERTIES WILL_FAIL TRUE)
add_test(NAME ordinary_success COMMAND "${CMAKE_COMMAND}" -E true)

Run this script from the source directory. It selects one test per invocation, captures CTest's status, and checks the expected runner outcome. A process return in the configuration and the runner exit in the script describe separate layers.

set -eu
work=$(mktemp -d)
trap 'rm -r "$work"' EXIT
ctest --version
cmake -S . -B "$work/build"
check() {
  status=0
  ctest --test-dir "$work/build" -R "^$1$" --output-on-failure || status=$?
  printf 'test=%s runner_exit=%s\n' "$1" "$status"
  test "$status" -eq "$2"
}
check expected_rejection 0
check unexpected_acceptance 8
check ordinary_success 0

With CTest 4.2.3, expected_rejection returned one normally and was Passed, with runner exit zero. Unexpected_acceptance returned zero and was Failed, with observed runner exit eight. Ordinary_success also returned zero but had no inversion, so it was Passed with runner exit zero. All fixture assertions passed. Eight is an observed result for this invocation. A production collector should preserve its actual status and test classification. It is not the reason the test process failed. WILL_FAIL property reference

The ordinary success control helps catch a missing property. If the inverted zero-exit test has the wrong property or test name, it could pass like the ordinary test. Running only the rejection case would leave that side unexamined. Check both rejection and unexpected acceptance so the gate can distinguish them. These commands verify runner policy using fixed outcomes. They do not validate a product configuration.

Identify the nonzero outcome independently

The property reverses exit criteria without interpreting the cause. A validator that should reject a missing field might instead fail to open the input file. That can also produce a normal nonzero exit and pass under inversion. It has not verified the required rejection. Check a separate observation such as a dedicated error category and the field involved. Establish that the program read the intended input, verify the rule it rejected, and then inspect the runner's classification.

A controlled business example could use a valid configuration, one missing a required field, and a nonexistent file. The first two check both sides of validation. The third checks that an environment failure cannot satisfy the target rejection. A wrapper checking the process output should fail when the error identity is wrong, with CTest configured for the wrapper's own contract. A straightforward option is for the verifier to return zero only after all checks match, then run it as an ordinary CTest test. That verifier owns the success decision and does not need WILL_FAIL. The article ran only the fixed CMake returns, without a business verifier.

Choose the form that makes the contract understandable. A simple command with an unambiguous normal nonzero rejection can use inversion directly. A program with multiple nonzero outcomes often benefits from an explicit verifier that names the intended error. Retain the original output and the verifier's decision so a pass can be tied to the actual business rejection. Classifying every error as expected leaves space for missing dependencies or an unusable environment to appear successful.

A release handoff should identify which tests use inversion. Passed can reflect ordinary success or a normal nonzero result accepted under that test's definition. Save the test name, effective property, and input identity so a reviewer can reconstruct it. Before removing inversion, repeat the valid-input and rejected-input controls. Determine whether product behavior changed or the job now runs a verifier with its own success decision.

Tie the error identity to the same input and invocation. A collector could attach an earlier missing-field message to a current file-open failure. Both fragments are real but cannot jointly prove the current rejection. Give each invocation an identity and input record so the diagnostic, process status, and verifier decision belong together. On a mismatch, repeat the relevant inputs rather than widening text matching until the case passes. This collector scenario was not executed.

Does a timeout become a pass too?

No. A test exceeding TIMEOUT still fails. The manual also notes that system errors such as segmentation faults, signal aborts, or heap errors may fail even with WILL_FAIL enabled. Normal nonzero exits are the fixture's inputs. They do not establish a result for every abnormal outcome. Inspect the effective timeout and process when handling a timeout report. No timeout, crash, or signal was simulated here. Those boundaries come from the property documentation.
