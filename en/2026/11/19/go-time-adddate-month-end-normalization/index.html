Why does Go add one month to October 31 and land on December 1?

Compare UTC timestamp oracles for AddDate normalization, an explicit month-end clamp, and a reverse calendar change.

Updated 2026-11-19 · Estimated read 11 min
Translations
zh-CN en

Article

Key takeaways

  • AddDate normalizes missing dates using Date's rules.
  • Clamping to the target month's end requires an explicit application policy.
  • Reversing a month change does not generally restore a month-end input.

Add one month to October 31 at noon with Go's AddDate and the result is December 1 at noon. AddDate applies calendar changes and normalizes out-of-range values the same way Date does. November has no day 31, so that position normalizes into December. A service requiring the last day of November needs an explicit rule.

Who chooses what an absent day means?

Suppose a subscription has an October 31 renewal anchor. The product expects November 30 next. Calling AddDate with one month schedules a December notice. The parameter is correct for the API, while the product's end-of-month policy is different. Put both expected dates in the requirement.

The Go documentation explicitly gives this example: October 31 plus one month yields December 1, the normalized form of November 31. Date permits out-of-range components and normalizes them. That is useful calendar behavior. A rule that clamps a missing day to the end of the target month needs to determine the target month's length before constructing the date.

Date also requires a non-nil location. This fixture supplies time.UTC explicitly so a missing location cannot trigger a construction panic.

The fixture uses UTC and preserves noon throughout. There is no daylight-saving transition or changing offset. A different month therefore points directly to calendar policy. Named locations need additional tests; these UTC dates establish no universal elapsed duration between renewals.

Write down the native and product outcomes independently

This Go fixture is unexecuted. It checks native normalization, a neighboring valid day, and an explicitly clamped result. The fourth case checks the reverse change for the follow-up. Every oracle is a full timestamp.

package main

import "time"

func clampNextMonth(t time.Time) time.Time {
    year, month, day := t.Date()
    hour, minute, second := t.Clock()
    last := time.Date(year, month+2, 0, hour, minute, second, t.Nanosecond(), t.Location())
    if day > last.Day() {
        day = last.Day()
    }
    return time.Date(year, month+1, day, hour, minute, second, t.Nanosecond(), t.Location())
}

func main() {
    start := time.Date(2026, time.October, 31, 12, 0, 0, 0, time.UTC)
    rolled := start.AddDate(0, 1, 0)
    cases := []struct {
        got time.Time
        want string
    }{
        {rolled, "2026-12-01T12:00:00Z"},
        {start.AddDate(0, 0, -1).AddDate(0, 1, 0), "2026-11-30T12:00:00Z"},
        {clampNextMonth(start), "2026-11-30T12:00:00Z"},
        {rolled.AddDate(0, -1, 0), "2026-11-01T12:00:00Z"},
    }
    for _, c := range cases {
        if c.got.Format(time.RFC3339) != c.want {
            panic(c.got)
        }
    }
}

October 31 normalizes to December 1, while October 30 reaches November 30. The clamp helper also sends October 31 to November 30. Neighboring starting dates separate policies that would look identical on the fifteenth of a month.

The helper finds the target month's end by asking Date for day zero of the following month. It compares the original day with that end, shortens it if necessary, then reconstructs the target date with the original clock fields and location. This is an application policy. It does not establish a permanent month-end anchor or specify whether a February result should keep day 28 afterward.

The helper advances one month only. An interface accepting arbitrary month counts needs additional input bounds and a policy for negative changes. Date's normalization also cannot validate whether a nonexistent appointment date was valid business input. This example implements no renewal service and performs no payment.

Preserve the anchor the recurring schedule needs

“Same day each month, clamped when absent” needs the original day. If November's clamped day 30 becomes the only input for December, the schedule can remain on the thirtieth and lose its original intent. Store the anchor separately from each calculated execution date and compute for the target month. Test at least two consecutive months to see whether the schedule returns to the intended day after a short month.

A policy of “one month from the last actual execution date” can intentionally retain the recursive result. Specify which policy applies and align stored fields with notices. A single ambiguous next_date field can leave notification and billing code applying different rules.

A service test can stay entirely in calculation at first: list November and December outcomes for one anchor. If an anchor is editable, define which period uses the change and whether existing pending notices are recalculated. The fixture runs no storage, notifications, or settlement. A computed timestamp alone does not validate the complete renewal flow.

The site's location interpretation for timezone-free input addresses how an input becomes a particular instant. This problem starts with a definite UTC timestamp and chooses a date when the target month lacks the original day. A scheduling service can need both checks, with separately named expectations.

Does adding a month and subtracting it restore the original?

October 31 becomes December 1; subtracting one month then gives November 1. The fourth oracle records that result explicitly. Normalization loses information about the out-of-range date that produced it. An undo action needs the saved original value or business anchor. Reversing AddDate is not a general undo operation for month-end inputs. Keep that condition visible in change records, particularly when a UI previews and reverses a next-run date.
