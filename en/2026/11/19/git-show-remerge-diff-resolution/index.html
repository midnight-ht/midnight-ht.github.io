How can you isolate the resolution in a Git merge commit?

Compare a Git remerge view, first-parent diff, and committed file to inspect a two-parent conflict resolution.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-19 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • Remerge compares a temporary tree with the recorded result.
  • Inspect the final file from the merge commit independently.
  • Verify resolution and application behavior separately.

For a two-parent merge commit, git show --remerge-diff can expose how a conflict was resolved. Git recreates the merge of the parents in a temporary tree that may contain conflict markers, then compares that tree with the recorded merge result. Removed lines may belong to the temporary conflict. Added lines describe the recorded resolution.

This helps with a specific handoff. Both branches were reviewed, but integration left a configuration with a third value. A first-parent diff confirms that the value changed without showing the choice offered by the other branch. The reviewer wants to inspect the decision made during integration. Recreating the comparison can bring that choice into view.

Make both branches edit the same line

The following script creates a disposable repository. Two branches replace one line with main and side. Merging should produce a content conflict, after which the fixture explicitly writes chosen as its resolution. It also reads the file back from the merge commit independently. Use a Git version that supports remerge diff.

set -eu
lab=$(mktemp -d)
trap 'rm -r "$lab"' EXIT
cd "$lab"
git init -q -b main
git config user.name Fixture
git config user.email fixture@example.invalid
git config commit.gpgsign false
git version
file=policy.txt
recreated=resolution.patch
ordinary=first-parent.patch
printf 'policy=base\n' > "$file"
git add "$file"
git commit -qm base

git switch -qc side
printf 'policy=side\n' > "$file"
git commit -qam side
git switch -q main
printf 'policy=main\n' > "$file"
git commit -qam main
status=0
git merge --no-edit side || status=$?
test "$status" -eq 1
printf 'policy=chosen\n' > "$file"
git add "$file"
git commit -qm resolution
test "$(git show HEAD:policy.txt)" = policy=chosen
git show --format= --remerge-diff HEAD > "$recreated"
git diff HEAD^1 HEAD -- "$file" > "$ordinary"
cat "$recreated"
printf '\nFIRST PARENT\n'
cat "$ordinary"
grep -F '+policy=chosen' "$recreated"
grep -F -- '-policy=main' "$recreated"
grep -F -- '-policy=side' "$recreated"
grep -F -- '-<<<<<<<' "$recreated"

On Apple Git 2.50.1, the merge returned one and reported a content conflict. After resolution, the remerge patch removed the conflict markers and both candidates and added policy=chosen. The first-parent comparison showed only main changing to chosen. The script checked the committed file and those patch lines and exited zero. The intermediate merge failure is expected evidence that the fixture exercised the conflict path.

Each report has a purpose. The first-parent view shows what integration added to the main line. In this fixture the remerge view shows how the two conflicting candidates became the final content. The conflict markers in the temporary tree were never committed into the release file. Inspect the merge commit itself to verify what users receive. Git show's remerge definition

Identify the parents before judging the resolution

Retain the full merge object ID, both parent IDs, Git version, and commands with the review. Branch names can move afterward. Repeating the merge against current branch tips may examine a different integration. Locate paths as they existed in the merge if later revisions renamed files.

Give the chosen value an independent application check. Main might identify a local environment, side a remote environment, and chosen an approved isolated environment. A patch can show the string selection without showing whether the configuration reaches the intended dependency. Read the setting from a controlled configuration and exercise a suitable non-production behavior. This fixture only compared strings and made no connections. Record source selection separately from runtime validation so the next reviewer knows what evidence is missing.

A conflict-free merge is a useful counterexample. If each branch changes a different file, the recreated and recorded trees may agree. An empty remerge view then says nothing about whether the merge introduced behavior. The two changes may be combined for the first time through a call path, configuration, or shared resource. Inspect actual parent differences and the result tree, then test the integration contract.

Before collecting these reports automatically, decide whether they are human review attachments or a long-lived machine input. The manual says remerge output and its interaction with other options may change. Preserve the original output, version, and object IDs for reproducibility. A parser needs checks against the versions and samples it supports. The fixture's searches verify a few expected lines without implementing a general conflict classifier.

For a historical investigation, locate the merge that made the choice, inspect both sides and the recorded result, then recover the constraints that applied. Mechanically valid text can still embody an unsuitable business choice. Choosing a third value also need not be a mistake. The remerge view narrows the decision to explain. Requirements and behavior evidence determine whether that decision was appropriate.

Check object identity when collecting the attachment. A review system might display merge M while an on-call terminal is already at a later HEAD. Using the terminal default to explain M would import another decision into the record. Generate both reports with an explicit object ID and read the final file from that object too. If the three records refer to different merges, fix the association and preserve the mismatched attachment to explain the confusion. This handoff scenario was not run. All three reads in the script use the same newly created HEAD.

Does the same view cover an octopus merge?

The documented remerge mode applies to two-parent merge commits. Identify the structure of a merge with three or more parents before selecting its review method. Comparing the result with each parent can help, but it supplies different information from recreating a two-parent conflict tree. Unexpected or absent output is insufficient grounds to call a multi-parent merge free of resolution changes. The fixture created only two parents and did not run a multi-parent comparison.
