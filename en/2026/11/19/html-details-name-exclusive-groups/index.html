Why do same-name details in separate sections close each other?

Use four details elements to test local exclusion and independence across sections. Check the scope of a shared name in one tree.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-19 · Estimated read 11 min
Translations
zh-CN en

Article

Key takeaways

  • Matching nonempty names form an exclusive group in one tree
  • A section does not scope that name
  • Test within-group closing and across-group retention

Shipping and returns information live in separate sections. A reused component gives all four details elements the same name. Opening a return item closes the shipping item the user was reading. The visual sections are independent, but the shared name puts the elements in one exclusive group.

A section doesn't scope a details name

HTML groups details elements with the same nonempty name in one tree. They need not be adjacent. A section organizes content without limiting the name comparison to its descendants.

At most one group member can be open. An expansion changes the old member's open attribute. The cross-section effect may happen without an application listener that closes anything.

Give the two areas different names if each needs to retain an open item. Shipping can use shipping and returns can use returns. Keep a shared name within each group so the intended local exclusivity survives. A unique name on every item would remove that relationship.

The id and name also have different jobs. The example uses an ID to read one element's state and a name to define the group. Reusing a group name can be deliberate; duplicate IDs create a different lookup problem.

Check local exclusion and independence across groups

The standalone page starts with four closed items. The read button records open for each one so the test can tell which contents remain available.

<!doctype html>
<meta charset="utf-8">
<title>Two details groups</title>
<section>
  <h2>Shipping</h2>
  <details name="shipping" id="a"><summary>Standard</summary>Three days.</details>
  <details name="shipping" id="b"><summary>Express</summary>One day.</details>
</section>
<section>
  <h2>Returns</h2>
  <details name="returns" id="c"><summary>Unopened</summary>Return within 14 days.</details>
  <details name="returns" id="d"><summary>Damaged</summary>Contact support.</details>
</section>
<button id="read" type="button">Read open states</button>
<pre id="output"></pre>
<script>
const byId = document.getElementById.bind(document);
byId('read').onclick = () => {
  const state = ['a', 'b', 'c', 'd'].map(id => [id, byId(id).open]);
  byId('output').textContent = JSON.stringify(state);
};
</script>

Open Standard. Expect only a to be true. Open Express and expect a false and b true. Keep b open and expand Unopened. Expect b and c both true. Finally open Damaged. Expect c to close while b remains open. These steps test different relationships.

These are predictions from HTML. No browser or assistive technology was exercised for this article. In a product test, activate each summary with the keyboard and record focus, open, and content visibility separately.

Make a failure variant by changing only returns to shipping. Expanding the return item should then close the shipping one. That controlled change checks whether the regression actually observes the grouping rule.

Preserve the relationship when reusing a component

Two product components may need to keep an item open for comparison. Generate a stable group name for each instance and give it to all members of that group. A global name baked into a template joins instances the page may have intended to keep separate.

Determine the business grouping before rendering. If components move, their current visual positions should not silently decide which name they receive. Record the member label and group name so a reorder test can verify the same relationships.

The task can also require several descriptions to stay open. Exclusive behavior is available but isn't automatically the right design. A comparison task may benefit from independent items. Test the chosen behavior against the information people need at the same time.

HTML also forbids nesting one member inside another member of the same name group. For a second disclosure inside a panel, define its relationship separately instead of expecting the name to encode hierarchy.

Inspect the initial markup as well. An author should not mark several members of the same group open. A browser correcting that conflict does not make the template valid. Keep the generated attributes separate from the state after interaction.

If the page restores previous choices, restore at most one per group under the new contract. Independent Boolean values saved before grouping can conflict after the component adds a shared name. Make that migration explicit.

For final state, read open directly rather than inferring it from the number of toggle events. A separate event-driven feature can log notifications, but that count is another observation.

Does an empty name group all the items together?

No. This changes the name condition. Group membership requires matching nonempty names within one tree. Giving every item name="" does not create one exclusive group. Standard and Express can both remain open.

Each details element still has its own open state. An empty group name doesn't disable ordinary opening and closing. Check both that the selected item opens and that the other remains open.
