Why does a full deque accept append but reject insert?

Compare endpoint additions, indexed insertion, and a left-side batch on independent bounded deques.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-19 · Estimated read 12 min
Translations

Article

Key takeaways

  • A full deque evicts from the opposite end when appending.
  • Indexed insertion raises IndexError if it would exceed maxlen.
  • Successive left appends reverse the batch's displayed order.

A bounded deque holds three log records. Appending a fourth succeeds, but inserting it by position raises IndexError. maxlen sets capacity, and the write method determines the overflow behavior. Endpoint additions evict from the opposite end. Indexed insertion raises if it would exceed the bound.

What an unchanged length can hide

A local activity panel retains the latest three records. A, B, and C have arrived, filling the window. D should produce B, C, D and remove A. That view permits eviction. Its test needs to identify the retained records; a length of three could also mean D was silently ignored.

Another entry point might place D after A. With no room left, the intended eviction is less obvious. Python's indexed insertion does not infer which record the application regards as oldest. It raises when the operation would grow the deque beyond maxlen. An interface that allows manual placement must reject the action or arrange space under its own policy. Sharing a capacity does not make the two writes interchangeable.

Endpoints matter too. Appending on the right evicts on the left, and appending on the left evicts on the right. Adding D on the left gives D, A, B and removes C. That suits a view whose left end represents the newest activity. If the display still regards the right end as newest, inspect the direction contract. The deque knows its endpoints; the application assigns their meaning.

Give each operation the same independent starting state

Create a fresh deque for each trial. Keep a full deque for the failing operation and a two-record deque for a successful indexed insertion. The identifiers represent local test data, with no connection to a log service.

from collections import deque

def full():
    return deque("ABC", maxlen=3)

right = full()
right.append("D")
assert list(right) == ["B", "C", "D"]
left = full()
left.appendleft("D")
assert list(left) == ["D", "A", "B"]
middle = full()
try:
    middle.insert(1, "D")
except IndexError:
    assert list(middle) == ["A", "B", "C"]
else:
    raise AssertionError("full indexed insertion should fail")
space = deque("AC", maxlen=3)
space.insert(1, "D")
assert list(space) == ["A", "D", "C"]
batch = full()
batch.extendleft(["D", "E"])
assert list(batch) == ["E", "D", "A"]
print("right BCD; left DAB; insert rejected; room ADC; batch EDA")

Right append leaves B, C, D. Left append leaves D, A, B. The full indexed insertion raises while A, B, C remain intact. With room available, inserting into A, C produces A, D, C. Together these assertions isolate the combination of operation and capacity. Only showing the failure could suggest that middle insertion never works. Only testing an empty deque misses the full-capacity behavior entirely.

Limit the exception handler to the operation expected to fail. Catching IndexError around construction, reading, and later processing could misclassify an unrelated bad index as a full deque. The assertion on existing members also protects against a caller removing an old item before an eventual error.

Identity supplies evidence that length lacks. Silently discarding D would pass a capacity test. Evicting C would pass it too while violating the latest-activity contract. Assert the full identifier order. Repeated activity text should still have distinct identifiers so the test can detect the loss of one occurrence.

Choose the receiving policy for a full buffer

An activity window can accept opposite-end eviction if consumers understand that records outside the window disappear. A system that must retain every unprocessed job needs a policy for waiting, rejection, added capacity, or storage elsewhere. If A is still waiting for a consumer, the next append can evict it. The right policy comes from the service requirement, with an observable result for each accepted or refused job.

For manual placement, the application might tell a user to delete or replace an item first. If the feature inserts in the middle while evicting the oldest record, specify the evicted identity and implement that action explicitly. Check the entire resulting order. This fixture implements no replacement UI or coordination between concurrent writers.

If the panel must explain where an old record went, its application event can include both admitted and evicted identifiers. Appending D can record that A left the window; a refused insertion can record that D was not admitted and no old record was removed. Inspecting the deque verifies this fixture. Audit history is an additional application feature. Treating the window alone as such a history could make a user mistake disappearance for completion.

A service acceptance test can hold the consumer, seed three jobs, and submit a fourth. Observe whether the agreed outcome is rejection, waiting, or durable retention. Resume consumption and account for all four identifiers. The site's queue completion accounting article concerns acknowledgement. A bounded window first requires assurance about whether pending work can disappear before it is consumed. This fixture covers local deque operations alone.

Will extendleft preserve the order of its input batch?

Start independently with A, B, C. Extending the left with D, E first gives D, A, B and then E, D, A. E precedes D because each item is appended on the left in turn. Each append can also evict on the right. The fixture asserts the complete result. Merely confirming that two new records appeared would miss the reversal. If a new batch must display D before E at the left, choose the input iteration direction accordingly and verify which older record survives at the boundary.
