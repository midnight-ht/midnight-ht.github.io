How can Docker COPY preserve parent paths from several directories?

Compare ordinary and parent-preserving Docker COPY exports with content and absence checks at the consumer's expected paths.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-19 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • Parent preservation changes artifact hierarchy.
  • Read content at the consumer's expected locations.
  • Check paths again after final packaging.

Use COPY --parents to retain source parent paths when copying files from different directories into one Docker destination. Ordinary copying places the files in the destination. Parent-preserving copying brings their source directory relationships along. That difference belongs in the delivery contract when a consumer reads relative paths.

Imagine alpha contains a configuration and beta contains a template. Both files appear in an export and the build is called correct. The consumer expects their original hierarchy and cannot find them from its configured root. Finding a filename somewhere on disk has not established its parent path. Two known inputs and two fresh exports make the comparison observable.

Export one directory tree per stage

Save this Dockerfile in a new directory. Create alpha/one.txt containing the single line alpha-marker and beta/two.txt containing beta-marker. Different basenames keep a same-name collision out of this experiment. The frontend must support parents; the current reference gives a minimum Dockerfile syntax version of 1.20. The local builder used a supporting frontend.

FROM scratch AS ordinary
COPY ./alpha/one.txt ./beta/two.txt /payload/

FROM scratch AS retained
COPY --parents ./alpha/one.txt ./beta/two.txt /payload/

Run the script from the context root with a single-platform builder that supports local export. Each stage writes to a fresh destination. The assertions read the contents and check an incorrect location is absent. They do not run a container or push an image.

set -eu
work=$(mktemp -d)
trap 'rm -r "$work"' EXIT
first=one.txt
second=two.txt
docker buildx version
docker buildx build --progress=plain --target ordinary --output "type=local,dest=$work/plain" .
docker buildx build --progress=plain --target retained --output "type=local,dest=$work/parents" .

test "$(cat "$work/plain/payload/$first")" = alpha-marker
test "$(cat "$work/plain/payload/$second")" = beta-marker
test ! -e "$work/plain/payload/alpha"
test "$(cat "$work/parents/payload/alpha/$first")" = alpha-marker
test "$(cat "$work/parents/payload/beta/$second")" = beta-marker
test ! -e "$work/parents/payload/one.txt"
printf 'plain: payload/one.txt, payload/two.txt\n'
printf 'parents: payload/alpha/one.txt, payload/beta/two.txt\n'

Both builds and readbacks passed on Buildx v0.37.2. Ordinary copying put the two files directly in payload. The retained stage put them under alpha and beta. The first had no alpha directory and the second had no one file directly under payload. Positive content checks establish file identity. The absence checks establish the changed hierarchy. Dockerfile parent-preservation rules

This changes the copied artifact layout without changing source files or the runtime working directory. Before modifying an older script, identify the delivery root its consumer uses. Adding the option can move files away from the consumer's expected paths. Verify both sides before treating the new hierarchy as a repair.

Verify the consumer's own paths

Suppose the consumer expects payload/alpha/one.txt and payload/beta/two.txt. It should read the files at those relative locations from its received output or archive. Searching the whole disk for one cannot satisfy that contract. Show the consumer manifest alongside the new parents option in review. If the manifest intentionally expects a flat layout, the ordinary stage may be the appropriate choice.

Keep content identity separate from hierarchy. A correct directory can still contain an old file from a different worktree used to assemble the context. Fixed markers are suitable for this small example. A real job should verify the contents or artifact identity corresponding to its expected version and preserve context provenance. Path and content assertions cover distinct failure modes.

For a migration, choose representative inputs in different directories and write the intended output list. Export ordinary and retained layouts into empty destinations and test each against the consumer. If both layouts are allowed, support and verify them explicitly. An opportunistic recursive search can select stale output, especially when both layouts remain in an old directory. Separate fresh prefixes prevent that state from satisfying the fixture.

If packaging later strips or rewrites paths, repeat the readback in the final archive. A correct local export only establishes its own filesystem state. A compression step that removes a top-level directory changes the consumer's path contract again. Retain the export root, packaging input, and final archive list so a reviewer can locate the change. This fixture tested local exports without producing a release archive or validating a downstream service.

A source directory rename can expose another compatibility change. Move alpha under config/alpha and update the COPY sources. Parent preservation now carries the extra config directory into the artifact. The copy can succeed with identical contents while the old consumer manifest fails. Decide whether a source organization change should propagate into the delivery contract. If consumer paths must remain fixed, express that layout explicitly in the build rule and verify the old manifest. If the contract changes too, identify which consumer version accepts it. This refactoring branch was not executed.

Version the manifest with its consumer. After a build-rule update, run the old path checks against the new export and retain the failing location. Verify the agreed new rules separately. If both contracts remain supported, keep both successful receipts. Otherwise identify the consumer version that changed. This acceptance workflow still needs an actual consumer run.

Can only part of the source parent path be retained?

Insert a dot-slash pivot in the source path to retain parent directories after that point. A separate local stage used COPY --parents ./outer/./inside/three.txt /payload/ with pivot-marker as input. Its export contained the marker at payload/inside/three.txt and no payload/outer directory. This adds a retention-start condition to the full-parent main experiment. For absolute sources copied from another stage, verify the pivot against that source path too.
