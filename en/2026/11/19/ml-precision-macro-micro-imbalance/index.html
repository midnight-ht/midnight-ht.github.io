Why can micro precision be 80% while macro is below 45%?

Compute two precision averages from a fixed nine-to-one example and retain class denominators to expose the minority-class failure.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-19 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • Precision uses a class predicted count as its denominator
  • Micro precision aggregates counts before division
  • Macro precision averages the class precisions without weights

Ten classification results give micro precision of 80% and macro precision below 45%. The model and test set have not changed. The aggregation has. With nine true A cases and one true B case, one error in each class can leave the minority class's failure relatively unobtrusive in the totals.

Identify what each denominator counts

The scikit-learn precision_score reference defines precision as TP divided by TP plus FP. For a particular class, the denominator counts predictions of that class and the numerator counts the correct ones. This asks how reliable those predictions are. Finding the true members of the class is a different question.

Micro aggregation adds the class counts before calculating a ratio. Macro aggregation calculates precision for each class and takes the unweighted mean. The fixture fixes the labels to A and B, uses no sample weights, and has one label per output. These conditions are part of the explanation.

Eight of the nine true A cases are predicted as A. The remaining one is predicted as B. The sole true B case is predicted as A. There are therefore nine A predictions with eight correct and one B prediction with none correct. Both classes have nonzero prediction counts.

A precision is 8/9; B precision is 0/1. Micro divides eight hits by ten predictions, giving 80%. Macro averages 8/9 and zero, giving 4/9, approximately 44.44%. The class mean gives B an equal place in the average instead of a one-tenth contribution based on its true sample count.

Compute the fixed cases individually

This script uses Node's standard facilities. It loads no classifier and does not call scikit-learn. It counts hits and false positives from fixed arrays, then checks independently calculated counts and ratios. Entries correspond by position, with the errors in the final two positions.

import assert from 'node:assert/strict';
const actual = ['A', 'A', 'A', 'A', 'A', 'A', 'A', 'A', 'A', 'B'];
const predicted = ['A', 'A', 'A', 'A', 'A', 'A', 'A', 'A', 'B', 'A'];
const labels = ['A', 'B'];
const counts = labels.map(label => {
  let truePositive = 0;
  let falsePositive = 0;
  for (let i = 0; i < actual.length; i += 1) {
    if (predicted[i] !== label) continue;
    if (actual[i] === label) truePositive += 1;
    else falsePositive += 1;
  }
  return { label, truePositive, falsePositive };
});
assert.deepEqual(counts, [
  { label: 'A', truePositive: 8, falsePositive: 1 },
  { label: 'B', truePositive: 0, falsePositive: 1 }
]);
const perClass = counts.map(row =>
  row.truePositive / (row.truePositive + row.falsePositive)
);
const totalHits = counts.reduce((sum, row) => sum + row.truePositive, 0);
const totalPredictions = counts.reduce((sum, row) =>
  sum + row.truePositive + row.falsePositive, 0
);
const micro = totalHits / totalPredictions;
const macro = (perClass[0] + perClass[1]) / labels.length;
assert.equal(micro, 8 / 10);
assert(Math.abs(macro - 4 / 9) < 1e-12);
console.log(JSON.stringify({ counts, perClass, micro, macro }, null, 2));

The exact script ran locally in Node. Its count assertion and both aggregate checks passed. The output contains eight true positives and one false positive for A, zero and one for B, micro at 0.8, and macro at approximately 0.444. This receipt establishes the arithmetic fixture, not a classifier's real quality.

As a separate negative control, correct the final two predictions to A and B respectively. Both classes then have perfect predictions and both aggregates should be one. The current script's fixed expectations should fail on that changed input. Create new expectations for the new case instead of deleting the checks and treating a printout as verification.

Keep enough counts to trace the failure

A total score alone hides which predictions were unreliable. Retain each class's hits, false positives, and predicted count to trace the nine A predictions and one B prediction. Retain true class counts as well to expose the test set's nine-to-one distribution. Both quantities matter, but they are not interchangeable denominators for precision.

These ten artificial cases illustrate aggregation. They establish no confidence interval, representative sampling, or production coverage. B has only one true case, so replacing one item can change the report sharply. Acceptance decisions need a suitable sample design and error-cost rationale. The toy distribution is not a claim about a business population.

Macro averaging also does not decide whether a product should pass. Equal weight for each class's precision is an aggregation choice. A product may attach different costs to particular false positives. Declare class responsibilities and acceptable costs before choosing thresholds so that the choice can be reviewed.

With exactly one true and one predicted label per case, and all classes included, micro precision also equals accuracy here. That equality depends on these conditions. Do not carry it unchanged into a selected subset of labels or a multilabel task. Retain explicit metric names when reporting the same 80% in a different setting.

If a report also includes probabilities, examine their reliability separately. Label-count aggregation cannot establish whether predictions assigned 80% confidence are correct about 80% of the time. See confidence bins and calibration gaps for that question. The evidence can appear side by side while answering different quality questions.

For version comparisons, fix the labels, sample identities, and averaging parameter. Adding a class changes the objects in a macro average. A changed score alone cannot attribute the difference to a model update. Record an intentional contract change beside the result and retain a comparable result under the previous contract.

Before counting, check that cases correspond one to one. Sorting the two arrays separately can destroy the pairing even though they contain labels from the same batch. A report that joins predictions by sample identifier needs unique identifiers and no missing cases before counting.

What if a class is never predicted?

This adds a zero-prediction condition. If there are no B predictions, B has zero true positives and zero false positives. Its precision has a zero denominator. The main fixture's 0/1 result cannot be transferred to this undefined case.

The current reference lists zero_division choices of warn, zero, one, and np.nan. The default warn returns zero and raises a warning. With np.nan, those values are excluded from the average. The reference records that the np.nan option was added in version 1.3. No Python package was executed here; this is a reading of its documented parameter behavior.

Retain the library version, parameter, and unpredicted labels in the report. Exclusion changes which values participate in macro averaging and should be visible alongside the result. Do not silently count an unpredicted class as perfect or conflate a policy assigning zero with actual predictions that were all wrong.
