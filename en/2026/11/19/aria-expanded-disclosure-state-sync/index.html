Why can content stay hidden when aria-expanded becomes true?

Keep a button’s expanded state in sync with its panel. Test opening, closing, reopening, and restoring state.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-19 · Estimated read 10 min
Translations
zh-CN en

Article

Key takeaways

  • An expanded declaration does not show the panel by itself
  • Render semantics and visibility from one state
  • Inspect the button and panel after each action

The delivery-details button already has aria-expanded. After activation the attribute reads true, but the panel stays hidden. The code changed the declaration without changing visibility. A custom disclosure needs its button's state to agree with the content people can actually reach.

State and visibility have separate outputs

The W3C disclosure pattern has a button and a controlled region. aria-expanded on the button indicates whether that content is expanded. The optional aria-controls relation can identify the region. These are semantic declarations, not commands to change the target's display.

A closed component starts with false and a hidden panel. Expanding changes both to true and visible. Closing reverses them. An arrow or a color is a third observation and can't establish that the other two agree.

Keep a stable label such as Delivery details for the button. Use its state to describe the current expansion. A native button already provides keyboard activation; the fixture doesn't recreate a button on an ordinary container.

One Boolean state drives both outputs here. The render function writes the attribute and the panel's hiding condition. That avoids treating the current arrow as the source of truth.

Use the same entry point for two cycles

The local page already contains the delivery text and fetches no data. The button has an explicit type so moving the component into a form won't give it submit behavior. The initial attributes match the state variable.

<!doctype html>
<meta charset="utf-8">
<title>Delivery details</title>
<button id="toggle" type="button" aria-expanded="false" aria-controls="delivery">
  Delivery details
</button>
<div id="delivery" hidden>Standard delivery takes three days.</div>
<script>
const byId = document.getElementById.bind(document);
const button = byId('toggle');
const panel = byId('delivery');
let expanded = false;

function render() {
  button.setAttribute('aria-expanded', String(expanded));
  panel.hidden = !expanded;
}
button.onclick = () => {
  expanded = !expanded;
  render();
};
</script>

Expect false and a hidden panel initially. Activate once for true and a visible panel, then activate again for false and hidden. Run another cycle. An initialization-only implementation may open once and fail when reopening.

These are predictions from the code. No browser or assistive technology was exercised for this article. In product testing, reach the control with the keyboard, activate it, and record whether the state and content can be understood. Keep attribute evidence separate from actual presentation.

Find entry points that change only one side

A click handler might update hidden while a legacy CSS class still suppresses the panel. Inspect the rule that actually hides the content and retain one explainable visibility contract. A correct Boolean attribute cannot establish what the stylesheet displays.

The reverse failure leaves false on the button while the panel is visible. Introduce that failure deliberately to check that a regression detects it. Record the instance, button state, effective hiding condition, and action.

If loading is asynchronous, distinguish expansion from readiness. A product might expand a region containing a loading message or wait until content is ready. In either design, give people something consistent with what the control claims.

Restoring a saved choice needs to call render as well. Assigning true to a variable doesn't invoke a function. Check both outputs immediately after restoration without clicking first, since a later interaction could repair the stale state.

A framework can replace the panel while a handler still refers to an old node. Check that the current button controls the current instance and that the target ID remains unique. The static fixture doesn't test component replacement.

Resolve the button’s target identifier and check that it points to the delivery region in this instance. A similarly named panel can mislead a test. Changing the target to a missing ID can leave the button toggling normally, so inspecting that attribute alone misses a broken relation. Record target existence, the relation, and visibility for the same action.

What if two buttons control the same region?

Both must reflect the shared state. After the first opens the panel, leaving false on the second misdescribes the same content. Render both controls from the same expansion state instead of having each toggle its own stale attribute.

Open with one button and close with the other. Read both button values and the one panel after each action. Checking only after the final close could miss the stale second button during expansion.

For a different semantic relation, see structured descriptions with aria-details.
