Why do saved Python itertools.groupby groups become empty?

Use complete standard-library comparisons to explain groupby lifetime, immediate consumption, materialization, consecutive keys and later handoffs.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-01 · Estimated read 15 min
Translations

Article

Key takeaways

  • Saving a group iterator does not retain its rows independently.
  • Immediate materialization and aggregation retain different information.
  • Sorting keys does not extend an old group iterator's lifetime.

itertools.groupby returns group iterators sharing the outer iterator's input, not independently stored collections. Saving those objects and advancing the outer iterator can move beyond their data. Consume and retain required rows while each group is current. If only an immediate aggregate is needed, retaining every row is unnecessary.

Saving an object does not save its rows

The Python itertools groupby reference explains the shared source and loss of access to a previous group when the outer iterator advances. The page checked on November 1, 2026 was Python 3.14.10. No program or real import file was processed here.

The outer iterator identifies the current consecutive segment while the inner iterator consumes it. They do not own separate copies. Finding the next group advances through the current segment. A saved object can remain accessible without owning independently retained rows.

Suppose orders arrive sorted by customer. A processor collects group objects and plans to send customer reports later. Collecting the outer iterator has already advanced the input to its end. Retrieving those objects does not reopen the file or rewind to each customer's first order. This is a lifetime error, not deletion of source data.

A lazy object is not necessarily a replayable query. Its source may be a one-use queue or network stream. A grouping name does not promise independent database-like result sets. Identify who advances the source, when values are needed and whether the source can be obtained again.

Compare retention strategies with fresh inputs

This complete, unexecuted standard-library program constructs fresh supplied rows for each comparison. It does not test a repair against an input already exhausted by the failure case, and it performs no external reporting or database writes.

from itertools import groupby


def rows():
    return [('A', 10), ('A', 20), ('B', 30)]


def customer(row):
    return row[0]


def main():
    delayed = list(groupby(rows(), key=customer))
    lost = [(key, list(group)) for key, group in delayed]
    print('delayed group iterators:', lost)
    if any(values for _, values in lost):
        raise RuntimeError('Unexpected retained group data')

    retained = [
        (key, list(group))
        for key, group in groupby(rows(), key=customer)
    ]
    expected = [('A', [('A', 10), ('A', 20)]), ('B', [('B', 30)])]
    if retained != expected:
        raise RuntimeError('Retained groups differ from expected rows')
    print('materialized groups:', retained)

    totals = [
        (key, sum(amount for _, amount in group))
        for key, group in groupby(rows(), key=customer)
    ]
    if totals != [('A', 30), ('B', 30)]:
        raise RuntimeError('Immediate aggregation changed totals')
    print('immediate totals:', totals)


if __name__ == '__main__':
    main()

The first approach exhausts the outer iterator before reading old groups, so their earlier rows are expected to be unavailable. The second consumes each group into a list before advancing. The third aggregates immediately and retains only customer totals. These are reasoned expectations, not captured output.

The distinction is not list-comprehension syntax. One comprehension consumes group contents; the other only collects iterator objects. A conventional loop needs the same ordering. Changing syntax cannot undo a shared-source lifetime.

Aggregation also discards information deliberately. A saved total cannot later reconstruct line-level audit data. Conversely, retaining every order is unnecessary if only the total is required, and it adds memory and sensitive-data retention. Choose the retained shape from the downstream operation.

Consecutive equal keys define a group

Keys A, B, A produce three segments rather than one global A group. Materializing each segment changes its lifetime, not its membership rule.

If all orders for each customer must be combined, sorting by the same key can make equal keys adjacent. Sorting changes order and needs suitable access to the data. Completely sorting an unbounded, one-use stream is not a cost-free fix. If the intended groups are consecutive sessions, sorting may destroy the temporal structure the application wanted.

A dictionary-based accumulation strategy can form global groups but retains unfinished state too. Removing groupby does not eliminate the capacity problem. An unlimited history requires a window, external storage or a declared end condition; the language utility does not decide when a customer's data is complete.

Express this in interfaces. A consumer of adjacent segments and a consumer of complete customer collections have different completeness requirements. Naming both inputs groups can let a downstream component mistake one segment for an entire history.

Does sorting make old group iterators reusable later?

No. Sorting makes keys adjacent without giving group iterators independent sources. Even a sorted list retains the same outer/inner advancement rule. Before handing work to a later task, materialize the necessary fields or retain a controlled identity supporting independent retrieval. An iterator placed in a background queue does not thereby acquire a longer data lifetime.

If the next stage only needs a customer ID, do not automatically copy the full record into its payload. An identity can lead to later current state, while a snapshot needs version and retention semantics. This handoff decision is not consistency supplied by groupby.

The existing article on early closure of async generators addresses who closes resources when consumption ends. This problem occurs while the outer iterator is still advancing. Correct file closure would not repair old groups losing access to rows.

Does list(group) eliminate resource concerns?

A list makes retention explicit, not free. One customer may have a very large group; retaining every group can approach the entire input size. Consider maximum group size and the number held simultaneously rather than extrapolating from two teaching rows.

For bounded summaries, consume a group, create its summary and finish the handoff before advancing. If sending creates external effects, retain failures and retry identity independently. Successful grouping is not successful delivery, and retry after source advancement needs stored data or replay support.

Proposed tests include sorted input, separated equal keys, deferred group consumption, immediate materialization and partial group consumption. Inspect group counts, row identities and later accessibility, not just a total amount. Incorrect customer assignment can preserve an overall sum.

A source that records each retrieved identity can expose whether the outer iterator, inner group or another helper advanced it. State whether that source is replayable; a list-based success cannot certify one-use stream recovery. None of these checks was run. Decide when a segment expires and what the next stage needs before choosing immediate consumption, materialization or independent retrieval. Saving an iterator saves an object; saving data requires an explicit act.
