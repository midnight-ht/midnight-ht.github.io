Why does a Docker build reuse a step after its secret changes?

Compare three builds using a harmless secret and independent revision, separating cache reuse, credential validation, and dependency updates.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-01 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • Changing secret contents does not automatically invalidate cache.
  • An independent non-secret revision can express rerun intent.
  • A cache hit validates neither new access nor old-access revocation.

Changing only a Docker build secret can leave the consuming step cached. Secret contents do not participate in cache comparison, so a successful rebuild may never have used the new credential. If rotation requires an access check, explicitly rerun the relevant step and inspect its result rather than interpreting reuse as authentication success.

Which changes cause another execution?

Docker's Build cache invalidation guide separates secret contents from other inputs. Changing the value does not invalidate cache; secret identifiers and mount properties participate in cache checks. A separately changed build argument can express the need to rerun. The online guide was checked on November 1, 2026. No build, credential rotation, or private dependency request was performed.

The cache has not determined that the new credential works. It has reused an earlier result without running this attempt at authentication. Previous access does not establish the replacement credential's permissions, scope, or expiry. If testing rotation is the goal, a skipped command leaves that evidence missing.

Not every rotation requires rebuilding every approved dependency. Some deliveries intentionally reuse an accepted result; others must contact the remote service again. State that choice. Credential replacement, dependency updates, and image rebuilding are related operations with different completion conditions.

A harmless cache comparison

This example has not been executed. In one terminal, create the owned lab parent and context subdirectory below, then save the Dockerfile in that context. The fake value belongs only to this new parent, not an arbitrary existing project sibling. A BuildKit-capable builder is required; verify the selected busybox tag independently rather than treating it as a pinned production image.

lab_root="$(mktemp -d)"
mkdir "$lab_root/context"
secret_file="$lab_root/training-secret"

Save this as context/Dockerfile under the newly created directory:

# syntax=docker/dockerfile:1
FROM busybox:1.37
ARG SECRET_REV=first
RUN --mount=type=secret,id=training \
    test -s /run/secrets/training \
    && printf 'executed revision %s\n' "$SECRET_REV" > /run-proof
CMD ["cat", "/run-proof"]

In the same terminal, define the complete build function and run the three comparisons. Every call uses the newly owned paths. These values are invalid training material, not production credentials.

run_build() {
  docker buildx build --load --progress=plain \
    --secret "id=training,src=$secret_file" \
    --build-arg "SECRET_REV=$1" \
    -t secret-cache-demo "$lab_root/context"
}
printf 'training-only-a\n' > "$secret_file"
run_build first
printf 'training-only-b\n' > "$secret_file"
run_build first
run_build second

The first build supplies an existing result. The second changes only secret contents; the third changes an independently consumed revision argument. The value change alone does not require invalidation, while the changed argument can trigger execution. Inspect the actual target-step cache status rather than three occurrences of the same image name.

The run-proof file contains only a public revision marker. It does not copy the secret. It helps identify the result included in the image when read alongside build logs, but proves no authentication outcome: this fixture contacts no authenticated service. Its purpose is to isolate cache semantics.

Keep the refresh signal separate from the secret

A public configuration revision or another non-sensitive identifier can mean that this attempt requires execution. The rotation process must maintain it; a permanently unchanged value cannot support a claim of repeated authentication. It also should not imply a new dependency version. A credential revision expresses rerun intent, not a requirement to fetch the latest package.

Do not put a password into an ordinary build argument to invalidate cache. Arguments have different recording and artifact boundaries from secret mounts. A password digest is not automatically public either: guessability and cross-system correlation still need assessment. An independent revision expresses intent without propagating derived secret material.

Where supported, invalidate a named dependency stage rather than every step, or explicitly choose a broader cache bypass and its cost. Renaming secret IDs or paths can affect the cache, but endlessly renaming interfaces is a poor implicit rotation policy. Keep mount contracts understandable.

What establishes that the new credential was checked?

In an authorized environment, fix the target resource, request and required permissions, ensure the consuming step actually executes, and observe access with the new identity. Test old-access revocation separately. New success does not establish that the old credential stopped working, nor does access success establish the final dependency contents.

If new authentication fails but the pipeline falls back to an old cached artifact, that is a fallback decision. It is not successful validation of the replacement credential. An approved old artifact may remain usable under release policy, but record what was reused and which rotation check remains open. Do not swallow the access failure to obtain a green result.

Build secrets and final outputs explains why a protected input channel does not prevent a command from copying secrets. This article explains why providing a new input does not prove the command ran. Both controls are needed; a cache revision does not replace output or permission protection.

Should a secret digest become CACHEBUST?

Not by default. Assess whether it reveals guessable information, creates durable correlation, or enters build records. Prefer an independent revision where it adequately expresses the rerun. No universal safe digest construction or real-secret entropy assessment is provided here.

A proposed receipt records a non-sensitive secret-object identity, public revision, build inputs, step execution status, and authorized-access outcome without the value itself. Check the final image's dependencies and deployment adoption separately. This fixture has no execution, image digest, authentication receipt, or completed rotation claim. Cache reuse is evidence of reuse; rotation validation requires new access evidence.
