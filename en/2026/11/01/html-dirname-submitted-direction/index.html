HTML dirname: why does saved text lose its writing direction?

Trace dirname entries with a complete textarea example, separating text, base direction, language and manual JSON collection.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-01 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • The dirname value names the direction field.
  • Native direction entries and manual objects need an explicit agreement.
  • Direction, language and alignment are different properties.

Receiving a comment's characters does not establish that the form also sent its base direction. HTML dirname adds a named ltr or rtl entry. The receiver still needs validation, storage and rendering rules. Direction is neither a language name nor merely left or right alignment.

The attribute value names a field

The HTML dirname section defines submission of a control's directionality under the name supplied by the attribute. A specified value must not be empty. Dirname="comment.dir" names the additional field; it does not set direction to a value called comment.dir.

Native entry construction supplies ltr or rtl as the direction value. The original name carries the text, while direction is another entry. Replacing name with dirname, or merely setting dir, does not establish both relationships. Inspect entries instead of inferring a request from visual alignment.

Language and direction overlap without being equivalent. Latin text, numbers and Arabic text can share one comment. Rtl is not a complete language tag; lang does not automatically create a direction entry. Right alignment also does not establish the base direction of bidirectional content.

A complete local collection sample

This unexecuted HTML has no backend. Submission is intercepted to display FormData entries. It demonstrates collection rather than saved comments. Compare ordinary Latin content, appropriate right-to-left content, automatic behavior and explicit choices.

<!doctype html>
<html lang="en">
<head><meta charset="utf-8"><title>Comment direction demonstration</title></head>
<body>
<form id="comment-form">
  <label for="comment">Comment</label>
  <textarea id="comment" name="comment" dirname="comment.dir"
            dir="auto" rows="4"></textarea>
  <p>Choose this comment's base direction:</p>
  <button type="button" data-dir="ltr">Left to right</button>
  <button type="button" data-dir="rtl">Right to left</button>
  <button type="submit">Show pending entries</button>
</form>
<pre id="result"></pre>
<script>
const [form, comment, result] = ['comment-form', 'comment', 'result'].map(
  id => document.getElementById(id)
);
form.onclick = event => {
  if (!(event.target instanceof Element)) return;
  const button = event.target.closest('button[data-dir]');
  if (button && form.contains(button)) comment.dir = button.dataset.dir;
};
form.onsubmit = event => {
  event.preventDefault();
  result.textContent = JSON.stringify([...new FormData(form).entries()], null, 2);
};
</script>
</body>
</html>

Comment carries the characters and comment.dir their associated direction. Auto applies initially; the local buttons choose ltr or rtl explicitly. Compare the actual entries and ownership rather than the position of a scrollbar.

The code neither transmits data nor accepts arbitrary CSS. A real endpoint should restrict the direction values it accepts, store them under its contract and render text appropriately. A direction value is not permission to interpolate arbitrary markup or style.

Why can manual JSON lose it again?

A framework that reads only comment.value into an object may bypass native dirname collection. An attribute in the DOM does not control every custom serializer. Choose native entries or explicit paired state, and make the paths agree.

Draft restoration also needs both parts. Restoring text while retaining the previous editor's rtl state can attach one comment's direction to another. Replacing text while preserving an unsuitable direction creates a different mismatch. Decide how explicit user choice, automatic inference and defaults interact.

Not every source must be retained permanently. If only the final direction is stored, define whether editing respects it. Reverting to auto on every remount can erase a deliberate choice. Product requirements should determine that behavior rather than an incidental component default.

Why retain a choice if the text appears to identify its direction?

A comment may begin with a reference number or quotation before its main content. Its first strong character need not represent the user's intended base direction. Automatic inference helps common cases but does not prove permanent intent. The buttons make the choice observable without claiming one method suits everything.

Numbers and punctuation also need their context examined. Rendering the same characters under a different surrounding direction after storage can change their presentation. A field can preserve a chosen direction without solving every bidirectional-layout issue.

Language-of-parts and pronunciation addresses another responsibility. Storing rtl does not declare the language, while a correct language tag does not establish submitted direction. Review language, direction and text separately instead of grouping them under one multilingual-support verdict.

What about duplicate names or disabled controls?

The extra name belongs to the request contract. A hidden input also called comment.dir can introduce multiple entries, and the receiver needs a repeated-key policy. Missing appropriate names, disabled controls and other entry-list exclusions cannot be assumed to produce a complete direction record anyway.

Check the actual element and applicable state rather than extending the textarea example to every tag. Plain displayed text has no equivalent native form-control collection path; saving its direction needs an explicit flow.

Check three distinct variants. With name retained, rtl explicitly selected and no required constraint, an empty comment can yield an empty text entry plus its direction entry. Removing name makes entry construction skip the field before the direction step. Disabling it also triggers an earlier exclusion. These are not all one “no comment” state: the receiver must distinguish empty content from absent entries.

Proposed acceptance covers auto, both manual choices, empty and mixed content, restoring two drafts, duplicate names and disabled states. Record control direction, entries, actual requests and retrieved server records. The local sample covers collection only and was not run. Establish that text and direction return on the same object before claiming the writing choice is preserved.
