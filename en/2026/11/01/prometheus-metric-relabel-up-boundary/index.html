Why does Prometheus retain up after metric relabeling drops scraped samples?

Use complete self-scrape configurations to distinguish sample and target filtering, explain the up exception, and inspect history and downstream inputs.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-01 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • Metric relabeling excludes generated series such as up.
  • Target removal and scraped-sample removal act at different stages.
  • Existing history does not establish continued collection.

Prometheus can retain up even when metric_relabel_configs drops every scraped sample. Metric relabeling excludes automatically generated series such as up. Decide whether the requirement is to discard samples or to avoid scraping a target before selecting the stage. A queryable up does not by itself show that the sample filter failed.

Target filtering and sample filtering act at different stages

The Prometheus configuration reference places metric relabeling immediately before ingestion and excludes generated series such as up. Target relabeling operates before scraping. This article checked the current reference on November 1, 2026; match it to the deployed version. No Prometheus instance or real metrics were queried.

Follow the pipeline: discovery supplies candidates; target relabeling chooses targets; scraping obtains exposed samples; metric relabeling filters scraped samples before storage. Both stages can use drop actions, but the affected objects differ. Shared action syntax does not establish shared scope.

up is not simply an application counter emitted by the endpoint. Prometheus generates it as part of scraping. Its presence cannot establish retention of a particular business metric, and a missing business metric cannot establish that no request was made. Inspect target state and required stored series separately.

A complete self-scrape comparison

This unexecuted configuration is intended for an isolated local Prometheus listening on its default port without a conflict. It scrapes its own monitoring endpoint under a unique job name and uses no business credentials. Save it as sample-filter.yml and load it with a compatible version; configuration loading and resulting series remain separate checks.

global:
  scrape_interval: 15s
scrape_configs:
  - job_name: sample-filter-demo
    static_configs:
      - targets: ['127.0.0.1:9090']
        labels:
          demo_scope: sample-filter-demo
    metric_relabel_configs:
      - source_labels: [__name__]
        regex: '.*'
        action: drop

Install a matching prometheus executable and launch the first configuration from the exercise directory. It runs in the foreground; query it from another terminal or browser. Use only a new exercise-owned storage directory. These commands are unexecuted; the Prometheus command-line reference documents the configuration and storage flags.

sample_data="$(mktemp -d)"
prometheus --config.file=sample-filter.yml --storage.tsdb.path="$sample_data"

Inspect target status, up, and a metric actually exposed by the monitoring endpoint. Restrict queries to the demonstration job so another default self-scrape does not contaminate the comparison:

up{job="sample-filter-demo"}
prometheus_build_info{job="sample-filter-demo"}

The paper expectation is continued scraping with matching scraped samples discarded; the metric rule does not delete up. First establish that the chosen comparison metric exists at the endpoint, the configuration loaded, and a scrape occurred. Without that baseline, an empty result could reflect a name or version mismatch rather than filtering.

The rule is deliberately broad to isolate the mechanism. Dropping all scraped samples in a real system removes diagnostic evidence. Define cost goals and necessary retained metrics first. A lone up without explanatory measurements can make a later incident harder to diagnose.

Which stage avoids the target request?

Use target relabeling to select discovery candidates rather than expecting a sample rule to stop requests. This second complete configuration is intended for an independent test instance with separate storage, avoiding old-sample interference. Its job name also distinguishes it from the first experiment.

global:
  scrape_interval: 15s
scrape_configs:
  - job_name: target-filter-demo
    static_configs:
      - targets: ['127.0.0.1:9090']
    relabel_configs:
      - source_labels: [__address__]
        regex: '.+'
        action: drop

Save the second configuration as target-filter.yml. Stop the first foreground process with Ctrl-C and confirm that it exited and released the port. Do not start two instances on the same port. Then launch the second with a different new storage directory:

target_data="$(mktemp -d)"
prometheus --config.file=target-filter.yml --storage.tsdb.path="$target_data"

A bind conflict while the first process remains alive is not a target-filtering result. Record which process loaded each file and query the instance actually running.

The action addresses the discovered target before scraping. Inspect discovery and dropped-target state and whether a new scrape is created, not only an empty query. One configuration retains the target and filters samples; the other filters the target itself.

With dynamic discovery, preserve the metadata labels used by the rule and the resulting identities. One static address does not imply that a production rule matches only one object. Test both intended exclusions and neighboring targets that must remain.

Why can historical curves remain after filtering?

A filtering change controls subsequent processing; it does not delete stored history. Range queries can include pre-change samples, and instant queries have their own sample-selection semantics. Record the activation point, query window, and identity before interpreting an old curve as continued collection.

Independent storage reduces that interference in this fixture, but a real change must account for its existing history. Retain the baseline, loaded configuration, subsequent scrape records, and queries over an explicit new window. Leave uncovered intervals unknown rather than deleting data to manufacture a clean-looking test.

Missing metrics and real zero values describes another consequence: an absent result is not measured zero activity. Filtering is one possible cause alongside endpoint changes, scrape failure, and query conditions. The generated-series exception does not make ordinary scraped metrics immune to metric relabeling.

How do you protect dependent alerts?

Inventory alerts, recording rules, dashboards, and diagnostic queries that depend on the affected metrics and labels. Define the removed set and verify that required inputs remain. Parsing proves syntax, while an up value describes the corresponding scrape state; neither verifies every downstream contract.

A proposed comparison establishes the endpoint baseline without filtering, checks continued scraping with sample removal, then checks candidate exclusion with target filtering. Query explicit windows and retain the actual loaded configuration and version rather than an editor buffer. These tests were not run, and no storage savings or alerting success is claimed.

Before choosing the stage, finish the requirement: do not request which target, or do not retain which samples after requesting it? Once that distinction is explicit, a remaining up is an explainable boundary rather than a contradiction.
