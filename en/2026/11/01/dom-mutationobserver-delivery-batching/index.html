MutationObserver: why has the DOM changed before the callback runs?

Separate synchronous DOM changes, queued records and callback batches with a complete attribute sample, including oldValue, takeRecords and shutdown.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-01 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • Callback count is not mutation count.
  • A target reference has a current value separate from recorded oldValue.
  • TakeRecords and disconnect need an explicit shutdown policy.

A script can change an attribute twice before the MutationObserver callback runs. The DOM mutation and delivery of its observation records are different moments. Distinguish the current tree, queued records and callback notification before diagnosing a missing change.

One callback is not one mutation

The DOM mutation-observer algorithms queue records and notify pending observers through a microtask. When a notification microtask is already queued, another identical notification need not be queued for each synchronous change. A callback receives a batch, not a user-operation counter.

This does not mean all changes collapse into one final record. Type, target and options determine what is observed. Attributes, childList and characterData are not interchangeable. Enabling only childList cannot establish observation of attribute changes.

A record's target is the actual node, not a complete historical DOM copy. Reading it during delivery can reveal a later value. Check the relevant oldValue option if the previous value matters instead of expecting a current target read to reconstruct history.

A complete local sequence sample

This unexecuted file uses no framework or API. Its button changes one attribute twice. The log sits outside the observed target so logging does not become another observed input. Log order is a proposed observation, not captured output.

<!doctype html>
<html lang="en">
<head><meta charset="utf-8"><title>Mutation record demonstration</title></head>
<body>
<h1>Compare current DOM with queued records</h1>
<div id="target" data-state="idle">Demonstration target</div>
<button id="run" type="button">Make two changes</button>
<pre id="log"></pre>
<script>
const [target, run, log] = ['target', 'run', 'log'].map(
  id => document.getElementById(id)
);
function write(entry) {
  log.textContent += JSON.stringify(entry) + '\n';
}
const observer = new MutationObserver(records => {
  write({ phase: 'observer', records: records.map(record => ({
    type: record.type, old: record.oldValue,
    current: record.target.getAttribute('data-state')
  })) });
});
observer.observe(target, {
  attributes: true, attributeFilter: ['data-state'], attributeOldValue: true
});
run.onclick = () => {
  write({ phase: 'handler-start' });
  target.setAttribute('data-state', 'loading');
  target.setAttribute('data-state', 'ready');
  write({ phase: 'handler-end', current: target.getAttribute('data-state') });
};
window.addEventListener('pagehide', () => observer.disconnect(), { once: true });
</script>
</body>
</html>

On the first click, the algorithm predicts ready before the synchronous handler ends. Subsequent delivery can contain two attribute records whose old values are idle and loading. Reading the shared target during that callback can return ready for both. Different old values and identical current values do not establish duplicated records.

That reasoning is limited to the sample's two synchronous changes without other intervening code. Changes across tasks, microtasks or component lifecycles can produce different batches. Do not generalize one callback and two records to all scheduling, or use an arbitrary delay as proof that every intermediate state was captured.

Are the options enough for an audit?

Old values can help investigate a broken attribute. A business-edit audit also needs identity, cause and server confirmation. One user action can change many nodes; a render can recreate an entire region. Treating every record as a transaction mixes implementation details with business events.

Choose options from the evidence required. Filter data-state when that is the concern; add childList and an appropriate subtree scope for node changes. More observations create more processing and interpretation duties rather than automatically stronger conclusions.

If the requirement is a derived summary, reading the final state once a relevant batch arrives may be appropriate. It need not pretend to replay user history. Final-state maintenance and historical evidence are distinct contracts.

Live and static NodeList membership also distinguishes references from snapshots, but does not define observer delivery. A fixed member list does not freeze the later content of those nodes. Here, queued records and oldValue provide an additional relationship to inspect.

Does disconnect flush the last records?

The MutationObserver interface algorithms define takeRecords as returning and emptying the record queue. Disconnect removes observation relationships and clears the queue. Stopping is not a promise to deliver all pending records first. Explicitly obtain and process them if shutdown requires retention.

TakeRecords does not execute callback logic for its caller. Taking the records and discarding the returned array can explain a later absence of callbacks. Reusing a processing function for delivered and explicitly drained batches is a possible design, with care against double accounting.

Decide what shutdown promises. A temporary visual summary may tolerate dropping undisplayed updates; complete recording needs a lifecycle policy for leaving the page and destroying components. This observer example is not a durable business log or cross-page delivery implementation.

Why can an observer keep triggering itself?

Changing observed content from the callback can produce more records. That may be intended post-processing or an unintended continuing cycle. Keeping the sample log outside its target prevents diagnosis from modifying the input, without prescribing that DOM structure for every application.

Document who owns each modification, when a derived result need not be rewritten and how observation and references are cleaned up. A blanket boolean lock can hide legitimate later changes; repeatedly erasing logs can hide evidence. Trace the action producing each record back to the maintained state.

Proposed checks compare the initial pair of changes, separate batches, filter changes, takeRecords and disconnect. Retain synchronous values, record count, old values, callback time and final summaries separately. None was executed here. A useful handoff explains what a record describes and why its target's current value is not a historical snapshot.
