Why does Python sqlite3 executemany discard INSERT RETURNING rows?

Compare discarded executemany output with per-row execute results in a complete SQLite example, retaining source mappings and commit and recovery boundaries.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile

Translations
zh-CN en

Article

Key takeaways

  • Discarded RETURNING output does not establish that inserts did not occur.
  • Map stable source keys to actual returned identities rather than guessing ranges.
  • Returned IDs, commit and recovery require separate checks.

Python sqlite3 executemany discards result rows, including output from INSERT ... RETURNING. An empty subsequent fetch therefore does not establish that no insert occurred. If a batch needs each generated identity, choose an execution path that collects results and check source identity, returned ID and commit separately. Do not reconstruct the batch from one lastrowid.

SQL support and retained driver results differ

The Python sqlite3 executemany reference explicitly documents discarded result rows. The page checked on November 1, 2026 was Python 3.14.10. The example requires underlying SQLite support for RETURNING and records the actual versions. It was not run, and no successful write is claimed.

Distinguish whether SQLite accepts the SQL, which Python execution method is called, and whether that method retains output. Database support for RETURNING does not make executemany return every row. Discarded output does not reverse side effects either. Record statement, call form and commit state together.

Suppose an import needs a mapping from source catalog keys to generated IDs. An empty result may tempt the caller to rerun the file. If the first write committed, this can create duplicates or encounter a source-key uniqueness conflict. Neither outcome follows merely from the missing result list.

When a batch only needs writes, executemany may remain suitable. Changing to per-row execute should follow result and failure requirements plus actual performance evidence. This article measures no throughput and does not prescribe its identity-collection example for every large import.

Compare writes and returned rows in independent tables

This complete, unexecuted standard-library program uses an isolated in-memory database, two supplied rows and two teaching tables. Source keys have explicit scope. Generated IDs belong to their respective tables; the demonstration does not require them to match across tables.

import sqlite3
import sys


def main():
    print('Python:', sys.version)
    print('SQLite:', sqlite3.sqlite_version)
    if sqlite3.sqlite_version_info < (3, 35, 0):
        raise RuntimeError('This demonstration requires SQLite RETURNING support')
    source_rows = [('catalog-a:7', 'Alpha'), ('catalog-b:7', 'Beta')]
    con = sqlite3.connect(':memory:')
    execute = con.execute
    try:
        for table in ['batch_demo', 'mapped_demo']:
            execute(f'''CREATE TABLE {table} (
                id INTEGER PRIMARY KEY,
                source_key TEXT NOT NULL UNIQUE,
                label TEXT NOT NULL
            )''')
        con.commit()

        with con:
            cur = con.executemany(
                'INSERT INTO batch_demo(source_key, label) VALUES (?, ?) RETURNING id',
                source_rows,
            )
            returned = cur.fetchall()
        stored = execute(
            'SELECT source_key, label FROM batch_demo ORDER BY source_key'
        ).fetchall()
        if returned != [] or stored != source_rows:
            raise RuntimeError('Unexpected batch result or stored rows')

        mapping = {}
        with con:
            for source_key, label in source_rows:
                row = execute(
                    'INSERT INTO mapped_demo(source_key, label) VALUES (?, ?) RETURNING id',
                    (source_key, label),
                ).fetchone()
                if row is None:
                    raise RuntimeError('Missing generated identity')
                mapping[source_key] = row[0]
        restored = execute(
            'SELECT source_key, id FROM mapped_demo ORDER BY source_key'
        ).fetchall()
        if dict(restored) != mapping:
            raise RuntimeError('Identity mapping mismatch')
        print('discarded rows:', returned)
        print('committed mapping:', mapping)
    finally:
        con.close()


if __name__ == '__main__':
    main()

The table names come from two fixed program constants, not user input; data values remain parameterized. Do not turn the teaching string formatting into an arbitrary table-name API. Setup, writes, queries and closure are supplied without an undefined database client.

The first table exposes empty returned rows alongside stored data. The second uses execute within an explicit connection transaction scope and associates each actual returned identity with its source key. Checks compare contents rather than only affected counts. The program's expectations are not captured results.

This arrangement relies on the example connection's default transaction-control mode and its context manager's commit behavior on normal exit. A project selecting another autocommit mode must check its own boundaries. Merely writing with is not an atomicity proof. The article on executescript entry commits addresses another method; its behavior should not be assigned to executemany.

Why not count backwards from lastrowid?

The Python reference limits when lastrowid updates: qualifying execute inserts or replacements, not a batch identity list supplied by executemany. Apparently contiguous numbers in one sample do not establish correspondence for all inputs.

Real batches may involve rejection, conflict handling, triggers or concurrent writers. Inspect the actual statement. This example records each returned value and does not rely on a contiguous range. Source keys include catalog scope, so two local identifiers of seven do not overwrite each other in the mapping.

Similarly, do not universally pair batch-returned rows with inputs by position. SQL shape, driver behavior and ordering need a contract. Retained source identities are easier to audit than incidental order. A server can keep restricted source keys internally and return appropriately scoped results to clients.

May an empty fetch be retried immediately?

Establish write and commit state first. If the initial transaction committed, discarded output did not remove its rows. If it rolled back, collected IDs must not be handed off as created objects. Recovery from an uncertain result needs uniqueness, queries and a defined idempotency policy rather than repeated insertion by guesswork.

The example prints its mapping after normal commit. It does not create a cross-system transaction. Sending a message immediately after obtaining an ID inside the transaction would need separate handoff semantics; database rollback cannot withdraw an external call.

What happens to the mapping when one row fails?

For an all-or-nothing contract, prevent commit and discard uncommitted mappings. A duplicate source key is a useful failure case: specify no new batch rows as the expectation, then inspect persistent state independently. A Python dictionary left after an exception is not evidence of partial success.

Partial acceptance instead needs per-source accepted, rejected and unknown states, plus a precise retry scope. An execute loop does not supply that policy automatically. Large inputs also need a capacity decision for the mapping; a controlled result table may be appropriate where a large in-memory dictionary is not. Two teaching rows establish no capacity result.

Proposed validation covers discarded output with stored rows, collected identities, duplicate keys, mid-transaction failure, outcome queries and closure. Preserve actual Python and SQLite versions and final row sets. None was executed. A repair should identify the discarding interface, map each source object to its actual target, and establish the commit that made it effective rather than manufacturing a plausible ID range.
