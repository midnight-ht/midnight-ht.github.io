PostgreSQL UNLOGGED is not an ordinary table with only a speed switch

Separate current visibility, crash truncation and standby content for UNLOGGED, using a complete configuration example and explicit rebuild requirements.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-01 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • UNLOGGED changes recovery and replication guarantees, not merely speed.
  • Visible committed rows do not certify crash survival or standby content.
  • Rebuilding needs a trusted source, stable identity and explicit absence handling.

PostgreSQL UNLOGGED is not an ordinary table with only a speed setting changed. It changes logging, crash retention and standby-content guarantees. Rows visible after commit are not evidence that they survive an unclean shutdown or exist on a standby. Evaluate this storage choice only with a credible rebuild source and an accepted loss policy.

Commit and crash retention answer different questions

PostgreSQL 18's CREATE TABLE reference states that these data writes are not recorded in WAL, the table is truncated after a crash or unclean shutdown, and its contents are not replicated to standbys. This article checked version 18 documentation on November 1, 2026. No crash, replication or performance test was run.

A commit result does not erase the table's chosen recovery limitations. An import might put the only copy of human corrections in supposedly disposable staging. Ordinary queries can look fine, but if those corrections cannot be reconstructed, the table is not merely a rebuildable cache.

Distinguish derivable stage output from new facts created there. Keeping the original file does not necessarily retain review decisions, edits or external receipts. If their sole record is in staging, reevaluate the assumption that loss is harmless.

The reference describes performance characteristics but provides no measurements for this application. Measure representative workloads and include reconstruction, cleanup and recovery costs. Changing one keyword does not support an invented improvement percentage.

Inspect configuration without pretending to test a crash

This unexecuted SQL requires an isolated database and a fresh teaching schema. Matching structures and supplied rows compare declarations and current visibility only. Stop on an existing schema rather than adopting unknown objects.

BEGIN;
CREATE SCHEMA demo_unlogged_boundary;
SET LOCAL search_path = demo_unlogged_boundary, pg_catalog;
CREATE TABLE durable_stage (
  id integer PRIMARY KEY,
  value text NOT NULL
);
CREATE UNLOGGED TABLE rebuildable_stage (
  id integer PRIMARY KEY,
  value text NOT NULL
);

INSERT INTO durable_stage VALUES (1, 'source-A');
INSERT INTO rebuildable_stage VALUES (1, 'source-A');
COMMIT;

SELECT 'durable' AS kind, id, value
FROM demo_unlogged_boundary.durable_stage
UNION ALL
SELECT 'rebuildable' AS kind, id, value
FROM demo_unlogged_boundary.rebuildable_stage
ORDER BY kind, id;

SELECT c.relname, c.relpersistence
FROM pg_class AS c
JOIN pg_namespace AS n ON n.oid = c.relnamespace
WHERE n.nspname = 'demo_unlogged_boundary'
  AND c.relkind = 'r'
ORDER BY c.relname;

Creation and writes share one transaction. SET LOCAL selects the newly owned schema for unqualified setup names; post-commit queries remain qualified. Both tables can currently hold committed rows. The catalog query checks their declarations; it does not simulate failure or establish crash survival. Recovery testing needs a separate disposable instance and explicit fault conditions. An expected SELECT result is not that receipt.

Clean up with DROP SCHEMA demo_unlogged_boundary CASCADE; only after confirming this exercise owns every object and nobody continues using it. No forced-stop command is issued here. Destructive fault exercises need their own environment, authority and operational record rather than being hidden in a query tutorial.

Catalog configuration must also match the relation the application actually uses. Wrong databases, unqualified names and other schemas can make a correct observation irrelevant. Preserve instance, database and qualified relation identity rather than only a screenshot showing rows.

Is UNLOGGED interchangeable with TEMP?

Temporary tables address session scope and lifetime policies; UNLOGGED changes logging and recovery without automatically deleting the table at request or session end. The existing article on temporary tables and pool lifetime covers the former. Both can support some staging tasks without sharing a lifecycle contract.

A batch shared across sessions may not fit a session-private temporary table. Conversely, UNLOGGED does not provide automatic request-end cleanup. Specify visibility, retention, crash loss and cleanup ownership separately.

The reference also makes indexes on an unlogged table unlogged. An index is not an independent durable backup. Normal-operation uniqueness enforcement and crash retention remain separate properties.

Why are the rows absent from a standby?

Not replicating this content is a documented limitation, not necessarily replication lag. A read-router must know whether the selected standby can contain its dependencies. Additional waiting does not turn intentionally unreplicated content into eventual delivery.

One empty query still does not diagnose UNLOGGED by itself. Check relation identity, instance role, permissions and visibility. A documented limitation supports one hypothesis; actual deployment evidence identifies its cause. No standby was run here.

A workflow requiring stage data across instances can evaluate ordinary replicated storage or place rebuilding on an explicitly source-owning node. Identify who rebuilds, its accepted duration and what callers see meanwhile. An empty table during reconstruction must not silently become a claim that no business records exist.

Can converting back to LOGGED restore lost rows?

A declaration change cannot reconstruct missing content. Restore or recompute from a trusted source with a version and reconstruction identity. The conversion itself needs a target-environment plan for locks and rollout; no production-ready conversion script is supplied.

Check reconstruction completeness beyond counts. A source may still contain one hundred rows while one has changed version. Matching quantity does not restore the original batch. Compare stable identifiers, source digests and required versions instead of accepting a nonempty table.

Separate clean restart, unclean shutdown, primary recovery and standby reads in an exercise. Retention after an orderly restart does not establish crash retention; a primary query does not certify a standby. Report only the performed operation and observed environment.

If temporary loss is acceptable, provide an explicit caller exit: rebuilding status, refusal of dependent operations or another reliable source. Do not retain an old completed marker while data remains missing, letting downstream readers interpret absence as a verified zero result.

No SQL or fault exercise was executed. Before choosing UNLOGGED, establish reconstructability, accepted absence and standby requirements. An unresolved answer should not inherit ordinary durable-table promises in exchange for an unmeasured performance impression.
