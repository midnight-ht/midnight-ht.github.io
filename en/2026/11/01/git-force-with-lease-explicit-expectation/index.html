Why can Git --force-with-lease still overwrite unreviewed remote work?

Explain implicit leases and background fetch with a local bare-repository fixture, then inspect explicit expectations, rejection recovery, and final refs.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-01 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • Background fetch can move an implicit lease's comparison point.
  • An explicit expectation needs an acknowledged state, not automatic overwrite approval.
  • Ref acceptance does not establish ancestry, behavior, or deployment.

Git --force-with-lease without an explicit expected value generally uses local remote-tracking state as its comparison point. A background fetch can advance that state even when you have not reviewed or integrated the new remote work. Protect an acknowledged remote object identity rather than relying on the presence of lease in the command name.

Why can the comparison point move without a code edit?

The git-push manual's force-with-lease discussion warns about interaction with background fetches and describes a form naming the ref and expected value. This article checked the online manual on November 1, 2026. No push, rebase, or ref update was performed in the current workspace or against a remote. Check the installed Git version and repository policy before applying a workflow.

There are three objects: the server branch tip, the local remote-tracking ref recording it, and the new tip proposed for publication. An implicit lease relies on the second; it does not ask whether a person read the added commits. An editor can refresh that ref while the proposed tip remains based on older history.

Suppose B is the common base, a colleague advances the server to C, and you rewrite the old history into A. A background fetch updates origin/main to C without integrating C into A. A comparison against C can match the server even though A does not preserve the colleague's work. The assumed comparison point moved; Git did not randomly ignore a promise of review.

A complete local practice setup

This script has not been executed. It creates a bare repository and two clones in a new temporary directory, with no network remote and no operation on this site's repository. The name main keeps the example short; it is not a recommendation to rewrite a shared main branch.

demo_root="$(mktemp -d)"
git init --bare --initial-branch=main "$demo_root/remote.git"
git clone "$demo_root/remote.git" "$demo_root/a"
git -C "$demo_root/a" config user.name Training
git -C "$demo_root/a" config user.email training.invalid
printf 'base\n' > "$demo_root/a/demo-file"
git -C "$demo_root/a" add demo-file
git -C "$demo_root/a" commit -m base
git -C "$demo_root/a" push origin main
git clone "$demo_root/remote.git" "$demo_root/b"
git -C "$demo_root/b" config user.name Training
git -C "$demo_root/b" config user.email training.invalid
expected_oid="$(git -C "$demo_root/a" rev-parse refs/remotes/origin/main)"
printf 'peer\n' > "$demo_root/b/peer-file"
git -C "$demo_root/b" add peer-file
git -C "$demo_root/b" commit -m peer
git -C "$demo_root/b" push origin main
git -C "$demo_root/a" fetch origin
printf 'rewritten\n' > "$demo_root/a/demo-file"
git -C "$demo_root/a" add demo-file
git -C "$demo_root/a" commit --amend -m rewritten-base
git -C "$demo_root/a" push \
  "--force-with-lease=refs/heads/main:$expected_oid" \
  origin HEAD:refs/heads/main

The final explicit condition still expects the server to be at the originally recorded B. Because the other clone advanced it, rejection is the intended direction. It does not integrate the peer commit. A rejection is not a reason to replace the command with ordinary force. No output was captured here.

Compare the implicit form only in another independently recreated setup with the same starting state. Record the base, peer commit, fetched tracking ref, proposed tip, server result, and final ref. Reusing a scene altered by the first push would change the question being tested.

What should establish the expected value?

A full object identity fixes a comparison point, but it must correspond to an actual review. Taking the latest tracking ref and immediately calling it approved does not supply that review. Inspect the new work, decide whether the proposed replacement is authorized, then record the acknowledged state.

The server can change after that decision. An explicit lease can reject a newer head rather than overwrite it; it does not lock the remote for an exclusive interval. Recovery should stop and compare again, not repeatedly fetch and refresh the expected value until a push happens to pass.

Scope matters too. Identify both the server ref being updated and the local object supplying its new contents. Default push configuration, multiple branches, or additional tags can expand an operation. The example spells out the target ref so the condition and affected object can be reviewed together.

Which records prevent a timing mistake?

Retain the complete target ref, acknowledged expected object, proposed object, and final server object. They identify where to update, which previous state authorizes it, what is proposed, and what actually remains. One moving branch name cannot replace all four, and a pre-push observation is not a post-push result.

Consider checking the remote, then allowing a peer update before the push. Equality at query time does not prevent that later change. The explicit lease supplies a condition checked when the server accepts the update rather than an indefinitely safe interval after one query. This race was not executed here; it explains why object and timing records matter.

What remains after a lease passes?

Acceptance establishes the ref-update condition, not content correctness or preservation of required ancestry. Use an ancestry check when history reachability is required and behavior tests when the requirement concerns the current code. Tree equality and commit ancestry explains why those claims can differ.

For undoing one change on a shared branch, a new reverse commit may fit the traceable workflow better than rewriting history. Revert and shared history provides that alternative without making it mandatory for every situation. Personal scratch branches, collaboration branches, and protected release refs have different policies.

Record the final remote object rather than only a success message. If a push result is unknown, inspect the target ref and operation records before retrying with a stronger overwrite. A ref update also does not establish subsequent build or deployment adoption; no such outcome is claimed here.

Can you fetch and immediately retry a rejected lease?

Refreshing information is not renewed approval to overwrite it. Compare the new remote work with the candidate, decide whether to integrate, abandon the rewrite, or obtain collaboration approval, and establish a new condition. A wrong target, missing object, or permission policy needs a different repair from a changed remote head.

A proposed test covers an unchanged remote, a peer update, a background fetch, and another update after review, retaining full ref identities and exit results. These disposable local exercises have not been run. The useful result is a statement of which acknowledged server state authorizes the update and who decides again when it changes.
