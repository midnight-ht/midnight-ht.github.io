Why can res.end no longer send an error after Node.js pipeline fails?

Use a complete local file service to separate early rejection from pipeline-owned interruption, covering socket lifetime, handles and response-phase evidence.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-01 · Estimated read 16 min
Translations
zh-CN en

Article

Key takeaways

  • Catching a pipeline error does not restore its response channel.
  • Acquire the actual read handle rather than relying on an existence precheck.
  • Early rejection, interrupted transfer and receiver acceptance need different evidence.

A failed Node.js pipeline can clean up its streams and destroy the connection used by an HTTP response. Receiving the error in a callback or catch does not mean res.end can send replacement JSON. Design separate exits for failures before handing the response to the pipeline and interruptions after streaming begins. The latter cannot promise to replace an already started or destroyed response.

Why does catching an error not restore the channel?

The Node.js version 24 Stream reference documents destruction rules and an HTTP file example where the expected error message can no longer be sent. The page checked on November 1, 2026 was v24.22.2. Neither the service below nor any real network scenario was executed.

The pipeline propagates errors and manages stream termination as well as connecting data flow. If a source fails, leaving its destination waiting forever would be inappropriate. Automatic cleanup is useful; the conflict arises when application code simultaneously assumes it still owns a writable response after that cleanup.

Draw three phases: before handoff, while the pipeline owns delivery, and after completion or destruction. An early error can take an ordinary HTTP rejection path. A later failure must be interpreted at its actual delivery phase. Writing a message after destruction cannot reverse connection lifetime. The presence of an exception alone does not choose the exit.

Do not turn this into the claim that every error destroys every object without exception. The reference specifies exceptions for certain already-ended streams. The defensible conclusion is that observing an error does not guarantee recovery of the writing channel, rather than an invented universal sequence for custom streams.

Open the handle that will actually be read

This complete, unexecuted ESM teaching service targets Node version 24. Save it as download-demo.mjs. It creates a private temporary directory and fixed input, listens locally and accepts no arbitrary file path. Ctrl+C initiates cleanup of its directory. It demonstrates response phases, not production authorization or a business download service.

import http from 'node:http';
import { mkdtemp, writeFile, open, rm } from 'node:fs/promises';
import { tmpdir } from 'node:os';
import { join } from 'node:path';
import { pipeline } from 'node:stream/promises';

const directory = await mkdtemp(join(tmpdir(), 'pipeline-demo-'));
const report = join(directory, 'report.txt');
await writeFile(report, 'teaching report\n', 'utf8');

function reject(response, status, message) {
  response.writeHead(status, { 'Content-Type': 'text/plain; charset=utf-8' });
  response.end(message);
}

const server = http.createServer(async (request, response) => {
  if (!['/report', '/missing'].includes(request.url)) {
    reject(response, 404, 'unknown teaching route');
    return;
  }
  let handle;
  try {
    const target = request.url === '/report' ? report : join(directory, 'missing.txt');
    handle = await open(target, 'r');
  } catch (error) {
    reject(response, error.code === 'ENOENT' ? 404 : 500, 'cannot open report');
    return;
  }
  const source = handle.createReadStream({ autoClose: true });
  response.setHeader('Content-Type', 'text/plain; charset=utf-8');
  try {
    await pipeline(source, response);
  } catch (error) {
    console.error('transfer interrupted', error.code ?? error.message);
    // The response has been handed to pipeline. Do not promise another body.
  }
});

server.listen(8766, 'localhost');
process.once('SIGINT', () => {
  server.close(async () => {
    await rm(directory, { recursive: true, force: true });
  });
});

Run the service in one terminal and issue these requests from another:

node download-demo.mjs
# Keep the service in its own terminal; issue these from a second terminal.
curl -i http://localhost:8766/report
curl -i http://localhost:8766/missing

The foreground service does not return control for the following commands in its own terminal. The successful route streams from the handle already opened; the missing-file route rejects before pipeline handoff. The status and wording are teaching choices. A real service needs its own object authorization and error-disclosure contract.

Opening the handle does not guarantee later reads. Storage failure, a custom stream, client disconnection or process termination can still interrupt delivery. This arrangement moves an open failure to a phase where a response can be selected; it does not certify a completed transfer or receiver persistence.

The example leaves file-stream closure to its automatic-close setting and pipeline lifetime. It does not lend the handle to another concurrent reader. Sharing it would require another ownership review so that one failing branch cannot close another's resource. Temporary-directory cleanup covers controlled shutdown, not guaranteed cleanup after forced termination.

Why not precheck with access or stat?

Checking a path and subsequently reopening it are distinct operations. The file can change between them. The existing article on access/open races explains that boundary. Here the service acquires the actual handle rather than treating a precheck as permission to assume a later file state.

A readable handle is not business authorization either. Fixed paths constrain this example, but real downloads still need permission checks for the requested artifact. Do not turn request text into arbitrary filesystem paths. Complete authorization before delivery where possible: a later catch cannot retrieve sensitive bytes already sent.

Reading the whole file into memory merely to retain an error-body option introduces a separate capacity decision. Buffering can suit a bounded small object. Large or uncontrolled inputs require a deliberate comparison of size, cancellation and receiving protocol rather than a universal replacement of streaming.

Does headersSent being false guarantee replacement JSON?

No single flag provides that guarantee. It describes header sending, not continued peer connectivity or the validity of a destroyed response. Once pipeline owns the response, its error handling may end the channel even before headers were delivered. Observe actual lifetime rather than promising a replacement based on that flag alone.

Logging and recovery also differ. A transfer-error record explains what the server observed. Resumption requires an artifact identity, retention policy or protocol with suitable retry support. An error log does not create those capabilities or determine how many bytes the client received.

Validate the two error exits separately

First use a missing fixed file and inspect the agreed early rejection. Next, in an isolated sample, introduce a source error after delivery starts and check that clients observe interruption rather than a fictional complete JSON error. Finally disconnect a client partway through and observe the source and handle reaching their expected end state.

Record whether status was already determined, whether a complete body reached the client and whether resources finished cleanup. Server-side pipeline success is not business-level receiver confirmation. End-to-end file acceptance may need length, digest or application acknowledgement. None of these tests was run, and no fault-injection receipt is supplied.

A useful repair identifies the handoff point and who can still decide a response when an error occurs. Reject before handoff, recognize interruption during delivery and stop pretending to write after termination. Those boundaries make catch describe the actual state instead of constructing an answer for an invalid channel.
