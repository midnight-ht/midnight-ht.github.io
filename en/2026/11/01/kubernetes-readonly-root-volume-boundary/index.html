Why can a Kubernetes volume remain writable with a read-only root filesystem?

Compare root and emptyDir writes in a complete Pod fixture, separating root access, volume mounts, runtime identity, and other writers.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-01 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • A read-only root does not make separate mounts read-only.
  • Ownership, mount access, and content integrity are separate checks.
  • One read-only consumer does not eliminate other writers.

Kubernetes readOnlyRootFilesystem makes the container's root filesystem read-only. It does not automatically make separately mounted volumes read-only. A failed root-path write and a successful volume write can coexist. Identify the mount serving each path, then check mount access and process identity separately.

Root access and volume access are separate settings

The security context guide defines readOnlyRootFilesystem as mounting the container root filesystem read-only. The volume documentation describes separately mounted storage. These current pages were checked on November 1, 2026; navigation version links do not pin their contents to a release. No cluster or write test was used.

A process sees one directory tree, but different paths can be supplied by different filesystems. Program files in the image and a volume at /work do not share one write switch merely because both use absolute paths. Record the resolved path, volume, mount point, and access mode rather than only a true security field.

Identity permissions add another layer. A writable mount can reject a process because of ownership or permissions; an otherwise writable root path can be blocked by the read-only filesystem. Changing ownership does not make a read-only filesystem writable, and changing mount mode does not resolve every identity problem.

A complete root-versus-volume fixture

This unexecuted configuration defines a namespace and one Pod. Verify image availability in the test environment. The fixture deliberately uses UID zero so ordinary ownership is less likely to explain the root-path failure first. It is not a production security baseline or a request to bypass admission policy. If the environment prohibits that identity, preserve the rejection and choose an authorized method.

apiVersion: v1
kind: Namespace
metadata:
  name: readonly-root-demo
---
apiVersion: v1
kind: Pod
metadata:
  name: root-versus-volume
  namespace: readonly-root-demo
spec:
  restartPolicy: Never
  containers:
    - name: probe
      image: busybox:1.37
      securityContext:
        runAsUser: 0
        readOnlyRootFilesystem: true
      command: ["sh", "-c"]
      args:
        - |
          if touch /root-proof; then
            echo 'unexpected root write'
            exit 1
          else
            echo 'root write rejected; inspect the actual error'
          fi
          printf 'training marker\n' > /work/proof
          cat /work/proof
      volumeMounts:
        - name: scratch
          mountPath: /work
  volumes:
    - name: scratch
      emptyDir: {}

The conditional handles the first expected failure without skipping the volume comparison. Inspect the actual error for the read-only cause and check the /work write and read separately. A nonzero result alone cannot distinguish a missing command, wrong path, or another security control.

There is no creation receipt here. Admission or image-pull failure means file operations never ran; it is not evidence of a denied root write. One training marker also cannot certify the entire filesystem. At most, a real observation would cover that path and runtime condition.

How do you attribute the rejected write?

A disposable baseline can preserve image, command, identity, and volume while turning off only the root read-only setting. If the same training path still fails, investigate the command, identity, or another restriction. Do not attribute every initial failure to the root control. Arrange this wider-write baseline only under authorized test conditions.

Then restore the read-only root and change only volume access. Keep three separate records: both paths allowed, root denied with volume allowed, and both denied. Retain the final object, mount state, and raw error for each. An object that never ran supplies no write result, and another Pod's log is not evidence for the current object.

Which paths should an application write?

Inventory actual temporary files, caches, upload intermediates, locks, and generated state. Static programs and configuration may need no write access, while temporary state can have a dedicated location. A read-only root can expose accidental writes into program directories without deciding which data must survive.

An emptyDir can suit disposable scratch data. Unique results and original uploads need separate cross-Pod storage and confirmation rules. The emptyDir lifecycle explains why surviving a container restart does not establish survival after Pod replacement. Writability and recoverability require different checks.

Test real deployments under their intended nonprivileged identity instead of copying the teaching UID as a universal repair. Appropriate directory preparation, group settings, or storage capabilities can provide required access, subject to actual platform behavior. Broad recursive permissions enlarge the write surface without explaining the application's needs.

What does a read-only volumeMount comparison show?

A second test Pod can preserve the root setting and mark the scratch mount readOnly. Observe /work writes again. The purpose is to distinguish mount control from root control, not certify every volume type. Retain both actual configurations, mount states, and errors, and ensure the identity or storage content did not change at the same time.

Read-only does not mean immutable contents. Another consumer or a platform-managed source may change the volume. A process unable to write through its own mount has no proof that the bytes never change. Source identity, version, and integrity requirements need separate definitions.

Runtime users and copied ownership addresses the adjacent permission boundary. Here, the added distinction is that one process can face different access modes on different mounts. Record identity, ownership, and read-only state together before deciding where to repair the configuration.

Does one read-only mount restrict every other consumer?

Do not extend a consumer's mount setting into a global write prohibition for the volume. Inspect every container, mount point, and external writer. Another authorized writable consumer can still change the contents. Single-writer or all-read-only requirements belong in the complete storage and permission design.

A proposed validation compares root paths, writable-volume paths, read-only-volume paths, and the intended runtime identity. Exercise a task that genuinely needs scratch writes and ensure it does not fall back into the image directory. These checks have not been run; no cluster security or business-completion result is claimed. The root control, write inventory, volume permissions, and data lifecycle each need their own evidence.
