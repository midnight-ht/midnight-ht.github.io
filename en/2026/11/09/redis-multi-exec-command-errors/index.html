Why did other Redis writes survive an EXEC WRONGTYPE error?

Separate Redis queue-time errors, execution-time WRONGTYPE and WATCH aborts, using individual replies and final key state to assess retries.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-09 · Estimated read 10 min
Translations
zh-CN en

Article

Key takeaways

  • An execution-time command error does not stop the other queued commands.
  • Queue-time and execution-time failures need separate cases.
  • A WATCH conflict aborts the queue rather than returning an individual command error.

An execution-time error does not roll back successful commands or prevent the later commands from running. First locate the error phase. A command rejected while being queued can produce a different outcome from a WRONGTYPE discovered during EXEC.

Suppose an application wraps three operations in MULTI/EXEC. The client raises one exception, so the business layer retries everything. If the middle command failed at execution time, both surrounding writes may already have happened. Non-idempotent increments could happen twice. Catching an exception does not establish that every key returned to its original state.

QUEUED is not completed

The official Transactions documentation describes commands being queued after MULTI and executed by EXEC. EXEC returns individual replies in issuance order. Review how the actual client exposes that result, rather than relying on whether one wrapper call returned or threw.

Redis executes transaction commands sequentially without interleaving requests from another client. That isolation guarantee is not error rollback. The documentation explicitly states that transaction rollback is unsupported and other queued commands continue after an execution-time command error.

The Redis transaction documentation distinguishes these stages. It dates refusal after a detected queue-time error to Redis 2.6.5. Verify the project's actual server and client versions; a library method named transaction does not settle the failure behavior.

Put an error between two writes

These are unexecuted redis-cli inputs for a new disposable local instance with an exclusively owned test prefix. No local redis-server or redis-cli was found for this article, so the outcomes below are documented expectations, not execution receipts.

MULTI
SET article_demo_unique:a text
LPOP article_demo_unique:a
SET article_demo_unique:b done
EXEC
GET article_demo_unique:a
GET article_demo_unique:b

All three command forms can be queued. At execution, SET creates a string; LPOP attempts a list operation and fails with WRONGTYPE; the final SET still executes. The expected reply sequence is success/error/success, with a=text and b=done afterward.

SET makes final-state inspection simple. It does not establish that repeating an arbitrary business transaction is safe. Replace a successful write with a non-idempotent increment, retry the entire queue because of the middle error, and the completed effect may repeat. Recovery must consider individual effects.

Placing the failure in the middle tests both directions. A last-command failure cannot show whether later commands continue. The three-command input observes prior success, the failure and subsequent success together.

Run queue-time failure separately

A malformed INCR can be rejected without inspecting its target's runtime type. Use another test key:

MULTI
SET article_demo_unique:c pending
INCR article_demo_unique:c extra
EXEC
GET article_demo_unique:c

With the documented modern behavior, EXEC refuses this transaction and the earlier queued SET does not take effect. The final key is absent. Do not apply the previous “other commands continue” rule to this different phase.

Retain every queue reply, the EXEC outcome and final values. A client may raise before sending EXEC; then inspect whether the connection still has transaction state and how the wrapper cleans it up. These are client-specific checks, not consequences of the server documentation alone.

DISCARD drops commands that have not executed. It cannot undo an EXEC already run. Sending DISCARD after catching an execution error does not establish recovery. Query known effects and design any compensation with its own retry contract.

The site's SET and TTL article covers each write's expiration semantics. Grouping commands does not erase their individual type, expiration or conditional-result rules.

Is a WATCH conflict another partial command error?

No. This adds an optimistic precondition: watch a key, let another client modify it, then attempt EXEC. Redis aborts the entire transaction without running its queue and returns a null reply. That differs from an array containing an individual WRONGTYPE error.

A validation needs two connections. Client A watches and reads; client B modifies the same test key; client A submits its prepared queue. Verify that the queued writes did not occur, then reread the condition before deciding whether to retry. A retry is a new attempt based on current state, not unconditional replay of the old queue.

This two-connection case has not been run here. Check the exact client representation of null and keep its handling separate from execution errors. Collapsing both into “retry everything” discards the crucial question of whether any write already occurred.

Isolation, conditional abort, command errors, persistence and external delivery require separate evidence. Preserve replies and final values first; then decide which effects permit retries or need queries and compensation.
