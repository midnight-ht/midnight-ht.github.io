Why does a JSON replacer see different fields? Check toJSON first

Trace toJSON before the function replacer, root wrapping and holder identity, with complete unexecuted probes for original and replacement entry stages.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-09 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • A callable toJSON runs before the function replacer for that property.
  • The two callbacks have different this roles, and root processing uses an empty-key wrapper.
  • Returning an object from replacer does not restart the same property operation at toJSON.

If a replacer cannot find an object's original fields, toJSON may already have returned a different representation. A function replacer receives the value at that stage, not necessarily the original object. Trace callback order, the current key and the holder before deciding where a validation belongs.

The current ECMAScript SerializeJSONProperty algorithm reads holder[key], calls a callable toJSON when applicable, and then calls the function replacer. The reference is the ECMAScript 2027 draft snapshot obtained on November 9, 2026, §25.5.4.2. The draft year does not establish support for every draft feature in a local runtime.

The value can change shape before the replacer

Suppose an export object has publicName and internalNote, while its toJSON returns only label. A replacer identifying the type by publicName can fail because it is examining another representation. JSON has not randomly skipped a field; the classification happens after a conversion.

ToJSON receives the current property key with the converted object as this. A function replacer receives key and the converted value, with the containing holder as this. Those roles differ. Use an ordinary function to inspect the holder; an arrow function has no own this binding.

JSON.stringify also creates a wrapper holding the root under an empty-string key. The initial replacer key is therefore normally empty. A user object may itself contain an empty-string property, so key==='' is not a universal root detector. Track the first invocation or an explicit root location when that distinction matters.

This complete Node.js ESM teaching program has not been run. It uses hypothetical fields without a network, database or actual bill. The expected trace is written from the algorithm before comparison with any runtime output.

import assert from 'node:assert/strict';
const trace = [];
const item = {
  publicName: 'Demo',
  internalNote: 'teaching only',
  toJSON(key) {
    trace.push(['toJSON', key, this === item]);
    return { label: this.publicName };
  }
};
const root = { item };
const text = JSON.stringify(root, function (key, value) {
  trace.push(['replacer', key,
    key === 'item' ? value.label : typeof value,
    key === 'item' ? this === root : null]);
  return value;
});
assert.equal(text, '{"item":{"label":"Demo"}}');
assert.deepEqual(trace, [
  ['replacer', '', 'object', null],
  ['toJSON', 'item', true],
  ['replacer', 'item', 'Demo', true],
  ['replacer', 'label', 'string', null]
]);
console.log(text, trace);

Root has no callable toJSON, so its replacer invocation happens first. Processing item then calls item.toJSON before its replacer invocation, and subsequently visits label. InternalNote is absent from the returned object; traversal of that representation cannot expose it again.

For the first probe, the root callback and the item callback also have different holders: the former sees the wrapper, while the latter sees root. The identity assertion for item is therefore independent of whether the replacement happens to contain the same text. Changing the callback to an arrow function would change what this refers to without changing its key argument; check identity separately from field content.

Do not call JSON.stringify on the inspected object to create each log entry: the logging can invoke toJSON again and contaminate the trace. This probe records only keys, booleans and simple text. A console's expandable object is also not necessarily a frozen record of its earlier value.

Validate the representation you actually own

A requirement about original fields belongs in a separate pre-stringify check, or in an explicitly controlled conversion contract. Replacer can assess the representation it receives. Treating it as every object's first inspection stage ignores an earlier conversion opportunity.

Returning a primitive changes later traversal too. If toJSON returns a string, the replacer sees that string rather than the original object's properties. It can return another value deliberately, but that adds another transformation. Keep original input, both return values and final JSON distinct.

This is not a side-effect-free clone of arbitrary objects. Property access, obtaining toJSON and calling it can have observable behavior. A simple teaching method says nothing about proxies or accessors in actual input. No malicious-object test or general security filter is claimed here.

Does a new object returned by replacer get another toJSON call immediately?

The same property operation does not jump back to its completed toJSON stage. After replacer returns, it continues according to the new value's type. A returned object's child property values each get their own property operation, but that is not another toJSON call on the returned object itself at the same stage.

This second complete program is also unexecuted. The derived expectation is that keep remains and called stays zero. Supplying the replacement as the original root takes a different entry path and calls its method.

import assert from 'node:assert/strict';
let called = 0;
const replacement = {
  keep: 1,
  toJSON() { called++; return 'converted'; }
};
let first = true;
const text = JSON.stringify({ original: 1 }, function (key, value) {
  if (first) { first = false; return replacement; }
  return value;
});
assert.equal(text, '{"keep":1}');
assert.equal(called, 0);
assert.equal(JSON.stringify(replacement), '"converted"');
assert.equal(called, 1);
console.log('different entry stages checked');

The function property does not become a JSON member; that does not mean its body executed and was then discarded. A child value with its own toJSON can still invoke it during its separate operation. Limit the no-restart conclusion to the current property processing, not the entire tree.

Verification should record the Node version, both scripts, stdout, exit status and assertions, then repeat the trace with the project's actual classes and wrappers. Neither script was executed for this article. A basic object probe would still not validate an SDK's complete outgoing request.

Undefined and clearing semantics concerns what an exported representation means at an interface. This question is narrower: locate the stage that changes object identity or value, then validate what that stage can actually observe.
