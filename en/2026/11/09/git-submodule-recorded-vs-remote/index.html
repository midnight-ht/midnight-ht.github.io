Adding --remote changes the source of the submodule commit

Separate the parent index gitlink, committed tree, child HEAD and remote candidate with a complete A/B fixture and a staged-upgrade counterexample.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-09 · Estimated read 19 min
Translations
zh-CN en

Article

Key takeaways

  • Ordinary update uses the dependency record in the parent index.
  • Remote update changes the target source, not every procedure.
  • Checking out a new child commit does not record a new parent gitlink.

Adding --remote to git submodule update changes the source of the target commit. Ordinary update uses the dependency commit recorded in the parent index; remote update uses the submodule’s remote-tracking state. It does more than fetch. Decide whether the task is reproduction or a proposed dependency upgrade before choosing the command.

Separate the index target from the committed record

The git-submodule manual says the default checkout procedure checks out the parent’s recorded commit, normally on a detached HEAD. The page identifies its last manual update as Git 2.54.0 and lists no changes through 2.56.0. That is a documentation history, not a probe of the installed Git version.

A parent can record A while the dependency remote has advanced to B and the local submodule has yet another HEAD. The gitlink in the parent HEAD tree describes the committed dependency. The gitlink in the parent index is the target ordinary update currently uses, and it can differ from that committed record. The child HEAD describes the checked-out input; the remote-tracking reference identifies an upstream candidate. Calling these positions “the current version” makes a handoff ambiguous.

The A/B fixture below assumes the parent index and HEAD tree both record A, with no staged dependency upgrade. Under that condition, restoring A may be exactly the correct reproduction. Selecting B locally also does not update the parent’s record. Changing the child worktree and committing a reproducible parent input are separate actions.

A complete local A/B fixture

This unexecuted Python script creates three repositories in a new temporary directory. It contacts no hosted remote and does not alter the actual site theme. File transport is enabled only on individual commands; no global Git configuration is changed. It requires Git and Python with support for the shown commands. Teaching identity and disabled commit signing are local to the new repositories.

# submodule_demo.py
from pathlib import Path
import subprocess
import tempfile

root = Path(tempfile.mkdtemp(prefix="submodule-demo-"))

def git(where, *args):
    p = subprocess.run(["git", "-c", "protocol.file.allow=always", "-C", str(where), *args],
                       text=True, capture_output=True, check=True)
    output = p.stdout.strip()
    if output:
        print(output)
    return output

def identity(where):
    git(where, "config", "user.name", "Teaching Fixture")
    git(where, "config", "user.email", "fixture@example.invalid")
    git(where, "config", "commit.gpgsign", "false")

print("Fixture directory:", root)
print(subprocess.check_output(["git", "--version"], text=True).strip())
remote, work, parent = (root / n for n in ["remote.git", "work", "parent"])
git(root, "init", "--bare", str(remote))
git(root, "init", "-b", "main", str(work))
identity(work)
(work / "value.txt").write_text("A\n")
git(work, "add", "value.txt")
git(work, "commit", "-m", "A")
a = git(work, "rev-parse", "HEAD")
git(work, "remote", "add", "origin", str(remote))
git(work, "push", "-u", "origin", "main")
git(remote, "symbolic-ref", "HEAD", "refs/heads/main")
git(root, "init", "-b", "main", str(parent))
identity(parent)
git(parent, "submodule", "add", str(remote), "dep")
git(parent, "add", ".gitmodules", "dep")
git(parent, "commit", "-m", "Record A")
(work / "value.txt").write_text("B\n")
git(work, "commit", "-am", "B")
b = git(work, "rev-parse", "HEAD")
git(work, "push", "origin", "main")
git(parent, "submodule", "update", "--init", "--checkout")
assert git(parent / "dep", "rev-parse", "HEAD") == a
git(parent, "submodule", "update", "--remote", "--checkout")
assert git(parent / "dep", "rev-parse", "HEAD") == b
recorded = git(parent, "ls-tree", "HEAD", "dep")
assert a in recorded, recorded
git(parent, "diff", "--submodule=log", "--", "dep")
print("Expected identities matched; fixture retained:", root)

The oracle is fixed in advance: ordinary update leaves the child at A, remote update selects B, and the parent HEAD tree still records A. The script deliberately leaves B unstaged in the parent so the dependency diff remains reviewable. It retains its temporary directory; any later cleanup must target the exact directory it prints.

The candidate command is python3 submodule_demo.py. Save its real exit status and output. This article did not run it: the final success message is proposed code, not an observed receipt. Directory creation alone does not prove the later Git operations succeeded. A real project must separately test B’s code and interfaces.

A staged but uncommitted dependency changes this analysis. If parent HEAD still records A while the index records B, ordinary update can select the index’s B rather than A. This does not change what --remote means; it identifies the actual input location used by ordinary update.

These unexecuted read-only commands inspect the index, committed tree and checked-out child separately. Replace dep with the verified path. Do not erase a useful staged upgrade merely to make the identities equal.

git submodule status --cached -- dep
git ls-tree HEAD -- dep
git -C dep rev-parse HEAD

The teaching script never stages B in the parent, so all three original expected identities remain: ordinary update selects A, remote update selects B, and the HEAD tree records A. In a real handoff, record the index too when staged changes exist, distinguishing a prepared input from a committed one.

Target source and update procedure are independent

The manual permits --remote with checkout, merge or rebase. Source selection chooses the target commit; the procedure decides how to apply it to the child’s current state. “Pull latest” hides both decisions and their different consequences for local branches and conflicts.

The fixture explicitly uses checkout to make the identity comparison clear. That is not permission to overwrite work in an arbitrary dependency directory. Inspect the child’s own branch and uncommitted changes, preserve useful work and avoid forcing a checkout merely to erase a version difference. A clean parent does not prove the child is safe to modify.

Remote update normally fetches before calculating the target. With --no-fetch it uses existing local remote-tracking state, which can be old. Record the remote, branch, fetch outcome and final object. Successful object transfer does not establish dependency compatibility.

For an approved release reproduction, use the recorded pointer. For an upgrade, review B, perform the project’s checks, then stage the dependency path and commit the new parent gitlink. Otherwise another operator can correctly restore the old parent record and return to A despite the first operator’s local B checkout.

For a second operator, verify the parent commit first, read its gitlink, update the child in an independent checkout, and compare the resulting child identity with that record. If they obtain A, check whether the handoff actually included a parent commit recording B rather than asking them to follow your unrecorded local upgrade.

A test performed on B can be real while approval still names a parent that records A. That result does not validate the delivered input. Bind checks to both identities and confirm the final parent record after the upgrade commit exists. The fixture now centralizes command-scoped file transport in its local wrapper and binds stdout once; none of the three identity assertions is removed.

Does branch configuration make ordinary update follow it?

No. The submodule branch setting selects the target for --remote; ordinary update still uses the parent record. The remote target otherwise defaults to the remote HEAD, and local .git/config takes precedence over .gitmodules for this setting.

A project may specify main while one machine overrides it with release. The same remote-update command can then choose a different target. Inspect the effective configuration and selected remote-tracking object rather than treating the shared file as proof of local selection.

The existing restore source-and-target article covers file state within one repository. This task adds the version contract between a parent and nested repository. A useful handoff names the parent commit, recorded gitlink and actual child HEAD, and states whether the work reproduced an input or proposed an upgrade.
