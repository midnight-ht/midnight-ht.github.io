Three table rows, one Gherkin scenario: where did the other runs go?

Separate Examples expansion from a step Data Table using complete permission features, independent outcomes and multi-section counting; distinguish selection, matching and assertions.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-09 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • Examples creates an instance for each data row; neither header nor template adds a run.
  • A step Data Table is one argument whose row processing belongs to its implementation.
  • Count rows across Examples sections, then verify the separately selected execution set.

Three permission rows below a step do not necessarily produce three independent scenario results. Check who owns the table: Examples instantiates a Scenario Outline, while a step Data Table passes the whole dataset to one step invocation. Define the unit of expansion before comparing it with the executed test set.

A table can belong to two different contracts

The Cucumber Gherkin Reference defines a Scenario Outline as a template that is never run directly. Each data row in Examples produces a run; the header does not. The page checked for this article was updated on November 8, 2026. That does not establish the parser version installed in a project or compatibility between its editor plugin and runner.

A Data Table under a step is instead passed as the step definition's final argument. Three or thirty rows remain one table received by that invocation. The implementation may loop through rows, but that does not create independent scenario reports. Whether a failure prevents later rows from being checked depends on the code.

This affects attribution. If one denial rule is wrong, a loop inside one step may report a dataset failure. Separately instantiated scenarios can associate the failure with a particular input. Neither table form is inherently better: choose between data for one business operation and independent repetitions of a common workflow.

A permission matrix with three expected instances

The following feature is an unexecuted teaching example. Its hypothetical policy considers user state and order ownership, without connecting to an account, permission service or file store. Product owners must approve the allow/deny decisions; Gherkin does not establish their correctness.

Feature: Download permission
  Scenario Outline: Decide <state> access to <owner> order
    Given the user state is "<state>"
    And the order belongs to "<owner>"
    When the user requests a download
    Then the permission result is "<result>"

    Examples: permission rules
      | state     | owner | result |
      | active    | own   | allow  |
      | active    | other | deny   |
      | suspended | own   | deny   |

Write the oracle independently: an active user can access their own order; someone else's order is denied; a suspended user is denied even for their own order. With no selection filter, expect three candidate instances. Do not count the template as a fourth run or multiply the three columns into every possible combination. Each instance needs its own preconditions so that a previous row's account or order does not leak into the next one.

Angle-bracket parameters refer to column headers. Cucumber substitutes values before matching the text against a step definition. Inspect the expanded text when a header or placeholder changes. Similar words in the source template do not prove that the intended value reached the implementation.

Then must also test the promised outcome. A When step that receives HTTP success, followed by a Then that merely checks for no exception, could incorrectly pass the denied cases. A real application check should inspect the permission result and verify that denial did not deliver the file. This feature implements neither service check. Correct expansion and sufficient business assertions are separate gates.

Moving the rows below a step changes the test

This second, also unexecuted feature has one scenario. It can be appropriate for an operation that accepts a dataset in one call.

Feature: Check a permission dataset
  Scenario: Evaluate one dataset
    Given these permission cases
      | state     | owner | result |
      | active    | own   | allow  |
      | active    | other | deny   |
      | suspended | own   | deny   |
    When I evaluate the dataset
    Then every reported outcome matches its expected result

The definitions now own table interpretation, dataset execution and outcome comparison. Header conversion, error aggregation and early termination depend on that implementation. Vertical bars do not specify them. When the actual target is a batch validator, keeping the dataset intact can test duplicate identities, ordering or cross-row restrictions that isolated single-row calls would miss.

The two forms therefore cannot replace each other merely because both finish green. Independent outline instances may run in separate environments; a Data Table can deliberately represent a joint input. Decide whether failure belongs to an individual input or the collection as a whole.

A plain Scenario containing angle brackets and a step table does not activate outline expansion. Inspect the parsed structure and generated execution objects. Editor highlighting is not a receipt showing that the runner created three instances.

Do several Examples sections form a Cartesian product?

No. Each data row in each Examples section instantiates the outline. Two rows in one section and three in another give five candidate instances, not six combinations. If every pairing of two dimensions is required, list the intended pairings explicitly and explain exclusions.

Sections can still separate groups of cases or selection conditions. Candidate count and executed count remain different: tags, names or runner configuration may select only part of the set. Missing results call for inspection of that selection, not an immediate conclusion that expansion failed. An expected five instances is not evidence that five actually ran.

Keep the feature hash, runner version, command and filters, generated names and assertion results together. Confirm structure and selection before execution; successful step matching does not establish correct assertions. No runner was executed for this article, so the counts above are derived expectations.

Rules and unresolved requirements addresses deciding what correct means. This article starts after that decision: attach each expected outcome to the correct execution unit. For a table with three rows and one reported scenario, inspect table ownership and generated instances before changing either the feature or the step implementation.
