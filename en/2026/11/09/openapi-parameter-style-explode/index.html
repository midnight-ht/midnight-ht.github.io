Why does an OpenAPI array become repeated query keys instead of commas?

Compare form arrays as commas or repeated keys with a complete OpenAPI parameter contract, parser failure cases and limits for nested deepObject values.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-09 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • Value schemas and query serialization specify different parts of a contract.
  • For form arrays, explode distinguishes comma-separated values from repeated keys.
  • Verify raw URLs, parsed structures and results; nested deepObject behavior cannot be inferred.

An array in an API description may reach the URL as status=open&status=closed. If the server reads only the last value, the array declaration has not implemented parsing. To explain comma-separated values versus repeated keys, inspect the parameter location, style, explode setting and receiver's reconstruction of the value—not just the schema type.

The OpenAPI 3.1.1 Parameter Object separates the value schema from serialization fields. This article pins the October 24, 2024 version rather than calling it the latest release. The order endpoint below is an unexecuted teaching contract, not a working server or a tested generated client.

Equivalent intended values need an agreed wire format

In this version, query parameters default to form style. When style is form, explode defaults to true; other styles default to false. Omitting the fields therefore leaves defined defaults, rather than permitting arbitrary array encoding.

For the values open and closed, form with explode=false produces the illustrated shape ?status=open,closed. With explode=true it produces ?status=open&status=closed. The specification's Style Examples shows the same distinction for a color array. A collection separator and repeated keys are different strategies, not cosmetic formatting that a framework may interchange without agreement.

Here is a complete parameter context. It defines only a teaching operation and response status; it does not implement a server or a response data model. For the comma form, explicitly change explode to false and align both ends, rather than changing a documentation example alone.

openapi: 3.1.1
info:
  title: Order filter teaching contract
  version: '1.0'
paths:
  /orders:
    get:
      parameters:
        - name: status
          in: query
          style: form
          explode: true
          schema:
            type: array
            items:
              type: string
              enum: [open, closed]
      responses:
        '200':
          description: Teaching response only

The derived expectation is that repeated status keys reconstruct a two-element array whose values are checked separately. A single-value accessor may retain only one value. Conversely, a comma form without the corresponding decoding may reach validation as the single string open,closed, which is not one of the listed enum values. Save the original query and parsed result to distinguish transmission, parsing and legitimate validation failures.

Validation placement matters. A receiver that collapses repeated keys before schema validation has already lost information. Broadening the item enum cannot restore the second value. The parsing stage must first produce the agreed structure; the validator can then assess it.

Defaults depend on location and value type

Do not copy query defaults everywhere. This specification defaults path and header parameters to simple, and cookie parameters to form. Changing explode for a simple array does not produce query-style repeated keys. A wrapper that sets explode=true for every array needs review against each parameter's in and style fields.

Objects behave differently too. An exploded form object introduces property names as independent keys; the unexpanded representation keeps keys and values within the parameter value. Review collisions with other query parameters before choosing the expanded object form. Shared support for form does not demonstrate that the combined query namespace is unambiguous.

A required parameter and a nonempty array are separate constraints. required governs presence; the schema governs item count. A minimum selection needs an explicit rule such as minItems. Missing parameters, empty strings and an empty result set should have separate expectations rather than acquiring one meaning accidentally through the parser.

A join/split shortcut is not a complete encoder

Simple English enum values make comma joining look sufficient. Values containing commas, spaces or reserved characters expose the relationship between data encoding and separators. Follow the pinned specification's serialization and percent-encoding rules instead of asking the server to infer original boundaries from a convenient string.

URLSearchParams can construct and read key/value entries, but does not know the OpenAPI style assigned to a parameter or choose the application's duplicate-key aggregation. A local conversion probe proves only its own output. It does not establish agreement across a generator, gateway and backend. Keep the structure actually observed at each boundary.

For an existing interface, changing commas to repeated keys can alter old-client behavior. Inventory the current formats and accepted input set first. If both formats are temporarily accepted, define how a mixed query such as status=open,closed&status=open is handled: reject, deduplicate, preserve order or another documented policy. OpenAPI does not choose that compatibility policy for this service.

Does deepObject define nested objects and arrays portably?

Not in this pinned version. OAS 3.1.1 leaves representations of nested array or object properties in deepObject undefined. Combinations marked n/a in Style Examples likewise have undefined behavior. A readable filter[range][min]=10 string is not proof that every conforming tool must interpret it the same way.

A complex filter can use an explicitly agreed serialization contract or investigate the Parameter Object content approach with a defined media type. That choice affects generation, parsing and practical URL constraints. It still requires tests of the actual tools, and does not justify mixing the schema/style and content strategies or promising that JSON automatically removes every interoperability issue.

The proposed acceptance starts with the two basic URLs. Capture the SDK request, gateway forwarding, server parse and final filter result. Add one value, duplicate values, unknown states, absence, empty input and allowed separator-containing values. HTTP success alone cannot establish that both states affected the query; the result fixture must distinguish one-state filtering from two-state filtering.

Nullable migration addresses value types and presence. This question concerns how values cross the query string. No SDK, gateway or service verification was run here. Put the raw URL and parsed array beside the declaration before approving “array support.”
