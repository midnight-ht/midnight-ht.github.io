Why does adding two pixels per frame make your animation faster on another screen?

Use a one-second, 240px teaching animation to explain timestamp progress, first-frame baselines, cancellation, hidden time and shared animation clocks.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-09 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • Fixed movement per callback makes speed depend on callback frequency.
  • Calculate clamped progress from elapsed time and define the start and cancellation semantics.
  • Hidden-time policy and a common baseline for several animations are separate choices.

Moving two pixels on every callback makes callback frequency part of the speed calculation. For a fixed-duration animation, derive elapsed time from the requestAnimationFrame timestamp and then derive position from elapsed time. When a high-refresh-rate screen makes the movement faster, inspect frame counting before assuming every device must behave as a 60Hz display.

MDN's requestAnimationFrame reference, modified August 21, 2026, says callback frequency generally follows the display refresh rate and warns against fixed per-frame progress. Generally is not a guarantee of a constant interval, or evidence that an application has been tested on every screen.

A frame is an opportunity to update

At an assumed 60 callbacks per second, two pixels per callback yields 120 pixels per second. At an assumed 120 callbacks, it yields 240. Those are arithmetic examples, not measured browser frequencies or a claim that every refresh delivers a callback.

Dropped frames expose the opposite failure. With fewer callbacks during a busy interval, fixed increments can extend the overall duration rather than merely omit intermediate pictures. For a fixed-duration interface transition, position can be a function of elapsed time so missing a sample does not redefine the endpoint's time contract.

The HTML animation-frame callback algorithm, checked in the November 6, 2026 snapshot, removes a callback before invoking it and passes the round's time value. A request is not a permanent subscription. Continuation, cancellation and restart must manage request identity explicitly.

A complete one-second, 240px move

This complete page has not been executed in a browser. It moves a teaching block without a network request or any representation of a real task's completion. The first callback establishes the baseline, progress is clamped to the endpoint, and restarting cancels the old pending chain.

<!doctype html>
<meta charset="utf-8">
<title>Elapsed animation</title>
<style>
#track { width: 280px; padding-block: 10px; border: 1px solid; }
#box { width: 30px; height: 30px; background: #275dad; }
</style>
<button id="start" type="button">Start one-second move</button>
<button id="stop" type="button">Stop</button>
<div id="track"><div id="box"></div></div>
<pre id="out"></pre>
<script>
const byId = id => document.getElementById(id);
const box = byId('box');
const out = byId('out');
let request = null;
let start = null;
function stop() {
  if (request !== null) cancelAnimationFrame(request);
  request = null;
}
function frame(timestamp) {
  request = null;
  if (start === null) start = timestamp;
  const elapsed = timestamp - start;
  const progress = Math.min(Math.max(elapsed / 1000, 0), 1);
  box.style.transform = `translateX(${240 * progress}px)`;
  out.textContent = JSON.stringify({ timestamp, elapsed, progress });
  if (progress < 1) request = requestAnimationFrame(frame);
}
byId('start').onclick = () => {
  stop(); start = null;
  box.style.transform = 'translateX(0px)';
  request = requestAnimationFrame(frame);
};
byId('stop').onclick = stop;
window.addEventListener('pagehide', stop);
</script>

Independent expectations are 60, 120 and 240 pixels after 250, 500 and 1000ms. Sampling frequency changes which intermediate points are observed; the same elapsed value should give the same position. A callback beyond the duration still stops at 240px because progress is clamped.

The second starts at the first callback, not the click. Initial callback delivery can be delayed; using that timestamp avoids treating the initial wait as movement already shown. Synchronizing to media or another external timeline requires another deliberate baseline.

Stop cancels a pending request, not an already displayed state. Here it leaves the current position; Start resets it. Production components may need pause, completion or replay semantics, but absence of later callbacks must not automatically mean a business operation completed.

Stop here cancels future frames and retains the position, while Start returns to the beginning. The fixture does not implement Resume from that position or an automatic notice carousel. If a product needs readers to pause content and continue using the page, the related notice pause, stop and resume discussion checks the trigger, duration and concurrent-content conditions before choosing a resume position and behavior after focus leaves the control. This manually started one-second animation does not establish accessibility acceptance for a product’s pause mechanism.

Decide what hidden time means

MDN says most browsers pause callbacks in background tabs or hidden iframes. Timestamp-based progress does not promise continued background rendering. On return, elapsed time can exceed the duration and this fixture reaches its endpoint. That can suit an absolute-time transition but may not suit an introduction that users need time to watch.

If only active viewing time should count, explicitly record suspension and resumption and exclude hidden intervals. Arbitrarily clipping a large resumed delta while still claiming an absolute one-second duration changes the contract without naming it. Define whether elapsed time or active animation time owns progress.

Physics simulation is another problem. Integrating a large delta can require fixed timesteps, substeps or another stability policy. This absolute-position interpolation does not validate collision or integration behavior simply because the block reaches its endpoint.

Why can same-frame animations still be out of sync?

MDN says callbacks queued for the same frame receive the same timestamp even after an earlier callback has consumed computation time. A shared sample time does not establish a shared start. Independent first-callback baselines or different durations still produce different progress values.

For common progress, pass one baseline to the renderers and derive their positions from the same elapsed value. Separate performance.now calls sample separate execution moments; they do not create synchronization automatically. Do not extend the same-frame observation into an arbitrary cross-process or cross-origin clock protocol.

Proposed verification first tests a pure progress function with different timestamp sequences, the three known points and clamping. Then use a target browser for start, stop, repeated start and background return, preserving times and positions. Pure-function tests do not measure refresh rate; rendering logs do not establish business completion. Neither test category was executed for this article.

Separate position from callback count when an interface movement has a fixed distance and duration. That lets subsequent dropped frames, delayed starts and hidden periods be discussed as sampling conditions or explicit time-policy choices.
