Why did a null-valued Merge Patch delete the member?

Trace RFC 7396 member removal, recursive objects, whole-array replacement and root null, including the trade-off for explicit null data.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-09 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • A null member in an object patch requests removal.
  • Objects can merge recursively while arrays are replaced as values.
  • A root null patch replaces the entire target; the resource schema must allow that result.

Inside an RFC 7396 object patch, null requests removal. It does not set an existing member to an explicit JSON null. Before choosing Merge Patch, decide whether the product's “clear” action means removing a member or retaining that member with a null value.

A settings page may submit nickname:null and find that the field disappears. If the interface really uses application/merge-patch+json, that follows the format's removal rule. It is not ordinary object assignment. Conversely, a product requiring an explicit null cannot obtain that distinct instruction by silently redefining the same standard format.

Identify the patch format

HTTP PATCH alone does not specify the meaning of a JSON request body. RFC 7396 defines Merge Patch and its processing algorithm. Choosing PATCH over PUT does not also select this format; request media type, implementation and contract must agree.

Omitted object members remain unchanged. A supplied null member removes its target member. Other members are processed recursively: object values can be merged, while non-object values such as arrays are replaced as complete values. This is neither a generic shallow dict update nor a name for every sparse JSON update.

RFC7396 was published in October 2014; section 2 defines the algorithm and section 4 the media type. Today's inspection date is not its publication date. The resource and fields below are teaching assumptions.

One target and three changes

The target has a nickname, nested preferences, tags and a switch untouched by the patch. A complete expected result checks both changes and preservation:

{
  "target": {
    "nickname": "Ada",
    "prefs": {"theme": "light", "lang": "zh"},
    "tags": ["a", "b"],
    "keep": true
  },
  "patch": {
    "nickname": null,
    "prefs": {"theme": "dark"},
    "tags": ["c"]
  },
  "expected": {
    "prefs": {"theme": "dark", "lang": "zh"},
    "tags": ["c"],
    "keep": true
  }
}

Nickname is absent. Preferences retain lang while changing theme. Tags becomes only ["c"], rather than appending c. Keep remains true because it was omitted. Checking only the new theme would miss an incorrectly retained nickname, a deleted language or an incorrectly merged array.

Type changes introduce another condition: if the patch at a location is an object but the target there is not, the algorithm begins with an empty object for that location. It does not preserve the old scalar as a hidden child. The resource schema still needs to decide which type changes it permits.

Arrays are not edited by index

A supplied tags array replaces that entire value. Sending one item does not mean “change one position and retain the rest.” Object members and array elements do not share the same recursive update policy.

For fine-grained array operations, evaluate a different format or an identity-based business action. The site's JSON Patch coordinate article covers RFC 6902's sequential operation array. It is a different protocol; adding remove, replace or test fields to a Merge Patch does not automatically switch interpretation.

Omitting tags also differs from supplying an empty array. Omission preserves it; the empty array replaces it with an empty list. A form that fills every untouched list with [] can accurately execute the wrong user intention. Follow intent through the actual request, rather than checking only parsed object shapes.

This educational function implements data-item processing on a copy. It does not include HTTP handling, permissions, schema validation or concurrency checks:

from copy import deepcopy

def merge_patch(target, patch):
    if not isinstance(patch, dict):
        return deepcopy(patch)
    out = deepcopy(target) if isinstance(target, dict) else {}
    for key, value in patch.items():
        if value is None:
            out.pop(key, None)
        else:
            out[key] = merge_patch(out.get(key), value)
    return out

Retain target and patch, compare the result with the independent expected document, and verify the original target is unchanged. Also test removal of an absent member, empty-array replacement and an object patch applied to a scalar. A local function pass would establish only these cases, not a production server's compliance.

When explicit null is ordinary data

The RFC describes the format as principally suitable for object-oriented documents that do not use explicit null as ordinary data. An object member patch cannot separately express “retain this member with null” and “remove this member.” Choose a format or business action that makes the required distinction rather than changing null semantics per field without saying so.

Recursive merging does not solve concurrent edits. Two editors sending whole tags arrays can overwrite one another even if each changed only one item in the interface. Version conditions and atomic persistence need a separate contract. The in-memory function verifies neither.

Does a root null patch remove a member?

No. This changes the patch's own type and scope. Target {"a":1} with object patch {"a":null} produces{}. The same target with a root patch null becomes JSON null. One enters member removal inside an object patch; the other replaces the entire target with a non-object value.

Do not document only “null means delete” without locating that null. Whether the resource permits a null root is a separate schema decision. Keep the two complete inputs as distinct integration cases and inspect the actual rejection or persisted result, rather than relying on an empty-looking page.

The site's PUT/PATCH contract article asks for an explicit update intention. Here that intention is tied to concrete format branches. Verify media type, complete before/after documents and preservation first; the teaching function cannot replace evidence from the real update entry.

The function ran on Python 3.11.15. Its main result matched the independent expected document and left the original target unchanged. Local assertions also covered absent-member removal, an empty array, object-on-scalar processing and both null cases in the follow-up. No HTTP server, database persistence or concurrent update was tested.
