Why did a SQLite ANY column lose the leading zeroes?

Compare numeric text in ordinary and STRICT ANY columns, inspect storage class and spelling, and distinguish new-input preservation from historical identity recovery.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-09 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • STRICT ANY preserves the supplied storage class; ordinary ANY can convert numeric text.
  • A strict table cannot recover spelling lost before binding.
  • Historical reconstruction needs source evidence and collision checks.

If the application supplies 000742 as text but reads back 742, compare the table option before blaming the display layer. SQLite preserves the supplied value and storage class in a STRICT ANY column. An ANY column in an ordinary table can instead convert numeric-looking text to a number.

Imagine an external catalog using six-character identifiers. The importer checks only that inserts succeed. A later export reveals that leading zeroes disappeared. Padding the output might hide the mismatch while assigning the wrong spelling to an identifier. First locate the conversion; this is a hypothetical import, not a reported production incident.

Inspect the binding before the table

SQLite introduced per-table STRICT mode in version 3.37.0. The official STRICT Tables documentation explicitly contrasts the two meanings of ANY: the strict version preserves its input without affinity conversion, while the ordinary version attempts numeric conversion for suitable strings.

Preservation begins with the value SQLite receives. If application code has already converted the identifier to integer 742, the strict column receives an integer. It cannot recover six original characters. Keep the actual binding type, table definition and stored type in the diagnostic record. Logging only the final displayed number loses the location of the change.

The official STRICT Tables documentation establishes these rules. It does not recommend ANY for every identifier. Whether a business field must contain text is a separate contract, preferably established before an importer starts converting it.

Compare identical inputs

This Python example uses a new in-memory database, parameter binding and three input classes. It opens no business file. The query explicitly orders these teaching rows by rowid. The typeof result identifies the storage class; quote makes the difference between numeric and textual values visible.

import sqlite3
c = sqlite3.connect(':memory:')
c.execute('CREATE TABLE strict_values(v ANY) STRICT')
c.execute('CREATE TABLE ordinary_values(v ANY)')
values = [('000742',), (742,), ('part-742',)]
for table in ('strict_values', 'ordinary_values'):
    c.executemany(f'INSERT INTO {table}(v) VALUES (?)', values)
    print(table, c.execute(
        f'SELECT typeof(v), quote(v) FROM {table} ORDER BY rowid'
    ).fetchall())
print('SQLite', sqlite3.sqlite_version)

These are ordinary rowid teaching tables. Ordering makes each output position correspond to its input in this fresh example. Without ORDER BY, SQLite does not guarantee the order of a multirow result; the SELECT ordering documentation states that limit. A real importer should carry a stable input identity rather than treat this teaching rowid as a business identifier.

The documented expectation is text '000742' in the first row of the strict table, but integer 742 in the ordinary table. The original integer remains an integer in both. The non-numeric text remains text in both. These outputs describe different preservation contracts; they do not establish that either table validates the business identifier.

A display-only test can miss the difference. A driver might stringify every result, or a template might format both as numbers. Inspect the raw database output before checking the driver and interface. If the API promises a string, also check that the outgoing JSON contains a string.

For a negative case, bind int('000742'). Both tables now receive an integer, and the strict table must not be expected to recover its earlier spelling. Separately test ANY NOT NULL with a null value: accepting mixed storage classes does not cancel a non-null constraint.

Preservation is not identifier validation

Other typed columns in STRICT tables can still perform lossless conversions. STRICT is therefore not a universal reject-any-conversion switch. ANY intentionally permits mixed storage classes. That may suit a raw import area, while character rules, length, source identity and uniqueness require their own decisions.

For a text-only identifier, a TEXT column with an explicit input contract may communicate intent better. TEXT alone does not validate every format rule. If mixed types are intentional, the reader and exporter must preserve their distinctions rather than turning everything into strings.

Check the engine linked into the actual application. A system CLI, Python runtime and mobile application may embed different versions. A successful table creation in one proves nothing about another package. Read the engine version on the actual connection and verify the relevant path there.

The site's JSON integer-precision article covers another kind of information loss. Here the number can fit comfortably within the integer range and still lose its original spelling. Numeric precision and leading-zero preservation need separate checks.

Will moving to STRICT recover old zeroes?

No. Historical strings 000742 and 742 may both have become integer 742. A new table option cannot determine which spelling belonged to each old row. Padding every value to six characters may silently change a legitimate identity.

An engineering recovery plan needs an authoritative source-to-target mapping. A documented fixed-length rule can help only after confirming its scope across historical sources and periods. Check collisions, conflicting mappings and rows without enough evidence. Leave ambiguous rows unresolved rather than guessing their spelling.

Validate historical reconstruction separately from new writes. The former needs source evidence and mapping checks; the latter needs the identical-input matrix and storage-class results. A successful insert into the new table establishes its input behavior, not the correctness of reconstructed history.

The archived local run used Python 3.11.15 with SQLite 3.53.1 in memory. The three-input matrix, pre-converted integer and NOT NULL rejection matched expectations. This covers only those local inputs, not the application importer or another device.
