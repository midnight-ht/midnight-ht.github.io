Tab still reaches the background? Define the inert region around your overlay

Explain inert through flat-tree scope, the native modal-dialog exception and concurrent blocking ownership, using a complete unexecuted teaching page.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-09 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • Inert applies to the nonescaping flat-tree subtree and activates by attribute presence.
  • Native modal dialogs have an ancestor-inert exception that custom overlays do not inherit.
  • Release the region only when all valid application blocking reasons have ended.

A dim backdrop does not remove a background form from Tab navigation. Inert can express that a whole region is temporarily unavailable, but its subtree boundary, release owner and native modal exception must be explicit. Restoring the picture is insufficient while another blocking reason remains active.

The HTML Living Standard on inert subtrees is the reference checked here, marked updated November 6, 2026. The page below is an unexecuted teaching fixture, not browser or assistive-technology certification. Inert controls user interaction; it does not authorize server operations.

A subtree state, not a dimming effect

Inert is a boolean attribute: presence activates it. Therefore inert="false" still sets the attribute. Use element.inert=false or remove it to clear the state. Changing attribute text is not the same as changing boolean presence.

Its scope includes the element and flat-tree descendants that do not escape inertness. This is not simply a walk through ordinary DOM children. Slots and shadow trees can affect the relevant relationship. A component's visual placement does not by itself prove that a control lies outside the restricted region.

The standard makes hit testing behave as pointer-events:none, makes editable nodes noneditable, generally prevents focus, and excludes inert nodes from accessibility APIs. Selection and find-in-page have related rules and user-agent exceptions. Neither aria-hidden alone nor pointer suppression alone establishes the same contract.

Inert supplies no default persistent visual cue. Dimming, a loading message or an offscreen position should explain availability. Keep essential active instructions outside the restricted subtree; otherwise visible text may be unavailable to some users. Do not make the only recovery explanation inert too.

Native modal dialogs have an explicit exception

Calling showModal() puts a dialog in the top layer and makes connected document nodes outside the dialog and its flat-tree descendants inert. That modal dialog can escape inertness inherited from ancestors. Inert set directly on the dialog still applies.

This exception does not extend to every overlay. A div with a high z-index, fixed positioning or a modal role does not acquire native escape behavior. A custom overlay inside an inert ancestor may disable itself. Establish whether showModal actually opened a dialog before reasoning about its ancestors.

Native modal closure also does not finish application loading. It releases the dialog's modal blocking mechanism, while an application-set inert attribute may still need to remain. Those are separate sources of restriction.

Can closing one of two states simply remove inert?

No. Remove only the closing state’s reason, then derive inert from the remaining owners. If loading still owns the restriction, closing confirmation must not reopen the background.

This complete HTML has not been run. It models loading and confirmation without fetching data or performing a business action. The teaching completion button deliberately stays outside main, so the operator can end the loading reason. A real application must use actual completion, failure or explicitly defined cancellation.

<!doctype html>
<meta charset="utf-8">
<title>Inert reasons</title>
<style>
main[inert] { opacity: .45; }
dialog::backdrop { background: #0006; }
</style>
<p id="status" tabindex="-1" role="status">Ready</p>
<button id="finish" type="button">Finish teaching load</button>
<main id="page">
  <label>Note <input></label>
  <button id="load" type="button">Start teaching load</button>
  <button id="open" type="button">Open confirmation</button>
</main>
<dialog id="confirm" aria-labelledby="heading">
  <h2 id="heading">Teaching confirmation</h2>
  <p>No business action is performed.</p>
  <button id="overlap" type="button">Add loading reason</button>
  <form method="dialog"><button value="cancel">Close</button></form>
</dialog>
<script>
const $ = id => document.getElementById(id);
const reasons = new Set();
function setReason(name, active) {
  active ? reasons.add(name) : reasons.delete(name);
  $('page').inert = reasons.size > 0;
  $('status').textContent = reasons.size
    ? 'Blocked: ' + [...reasons].join(', ') : 'Ready';
}
$('load').onclick = () => setReason('loading', true);
$('finish').onclick = () => setReason('loading', false);
$('open').onclick = () => {
  $('confirm').showModal();
  setReason('confirmation', true);
};
$('overlap').onclick = () => setReason('loading', true);
$('confirm').addEventListener('close', () => {
  setReason('confirmation', false);
  ($('page').inert ? $('status') : $('open')).focus();
});
</script>

Derive expectations from the reason set. Closing confirmation alone empties it and restores the background. Add loading inside the dialog, then close: loading remains, main stays inert, and focus is directed to the external status location. The completion button removes the final reason. An unconditional page.inert=false in the close handler would incorrectly reopen a still-loading region.

The set is an implementation recommendation, not a standard-mandated reference counter. Names must represent real owners. Two concurrent loads sharing the same loading key can still interfere when the first completes. Use independent task tokens or derive availability from a unified state model rather than assuming Set automatically solves concurrency.

Navigation, failure and unmounting also need ownership rules. An error branch that changes only the message may leave a stale restriction forever. Clearing every reason may instead bypass another valid restriction. Inspect each source's lifetime, not just the opening and closing animation.

The teaching completion button is not a recommendation to let a user declare a network request complete. Actual request outcomes or an explicit cancellation policy must drive the state, including retries and whether the current data is editable.

The proposed verification walks through ready, confirmation, confirmation plus loading, confirmation closure and loading completion. Record the reason set and attribute, then inspect real Tab input, pointer input and the active element. Calling click() or dispatching an event does not reproduce user hit testing. Accessibility-tree exposure and available status feedback need their own target-environment checks.

For an individual unavailable form control, the standard says disabled is often more appropriate. This article concerns whole-region availability. The existing modal focus workflow covers entering and returning to the task; the added questions are which subtree is restricted and when the last owner actually releases it.
