An instant query need not return old samples for five minutes

Two paper timelines distinguish lookback selection from stale termination, with exporter timestamp, sample-age and query-step conditions.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-09 · Estimated read 12 min

Article

Key takeaways

  • An instant value can come from an older sample.
  • Staleness can stop selection before lookback expires.
  • More evaluation points do not create ingested samples.

A Prometheus instant result does not establish that the target just reported that value. An evaluator can select an older eligible sample within lookback. Once the series is marked stale, however, later instant evaluations can stop returning it. “A stopped series remains visible for exactly five minutes” is therefore not a reliable query rule. Inspect sample time, evaluation time and staleness together.

The query’s present is not the sample’s present

The Staleness section of Querying basics explains that evaluation timestamps are independent of actual sample timestamps. Different series do not have to be sampled at precisely the same instant. The evaluator chooses the newest eligible sample within lookback rather than requiring a simultaneous collection from every target.

This rolling latest page was read on 9 November 2026. It documents a five-minute default, configurable with query.lookback-delta or the per-query lookback_delta parameter. That is a selection condition, not a universal outage-display delay or a storage-retention duration.

A dashboard repeatedly showing seven could be selecting fresh samples that all equal seven, or repeatedly selecting the same old sample. A refresh animation and successful query request cannot distinguish those cases. Inspect the selected sample timestamp.

Two paper timelines

These are unexecuted teaching assumptions, not an incident record. A bare instant selector reads demo_value. Its last ordinary sample is seven at 12:00. In the first timeline there are no later samples and no stale marker; lookback remains at the default five minutes.

At 12:02, the 12:00 sample can still qualify. A result at 12:02 must not be described as a sample collected at 12:02. At 12:06, that sample lies outside the assumed window. The example avoids an exactly-five-minute timestamp so endpoint details do not distract from the selection rule.

The second timeline keeps the same ordinary sample but marks the series stale at 12:01. Later evaluation no longer returns the old series, so the 12:02 result can already be absent without waiting for the lookback window to expire. The value did not change; the eligibility condition did.

An inspection table should list the last sample time, evaluation time, stale event and effective lookback before writing expected results. Do not present the paper timeline as measured output. Newly ingested samples can make the identity return again; staleness is not a claim that all history was permanently deleted.

Both simple slogans fail: immediate disappearance overlooks an eligible old sample, while a guaranteed five-minute continuation overlooks a stale marker. Determine the actual input condition before assigning business meaning to the graph.

Target state, timestamp provenance and identity

The documentation describes staleness when a scrape or evaluation no longer returns a previously present series, and after target removal. It does not guarantee the same exact marker time for every stopping cause. Process exit, service-discovery removal, one metric disappearing and a changed selector are distinct conditions to investigate.

Exporters that attach their own sample timestamps can have different behavior; track_timestamps_staleness can change it. Record who supplied timestamps and the effective setting instead of applying a scrape-time model unconditionally. The online manual cannot establish the reader’s installed configuration.

up and an application metric are also different series. A current up result does not establish a fresh application sample. Label changes can create another identity, and aggregation may hide one member’s disappearance. Preserve the target and label detail needed for the actual decision.

The rule limit article discusses a specific evaluation error that does not write stale markers. That is one possible explanation, not the universal cause of old queryable values. Check whether that failure condition applies before using it as a diagnosis.

Check freshness at a fixed evaluation time

These proposed expressions are unexecuted. Replace the selector with a verified identity and evaluate all three at the same fixed time. Preserve server version, raw responses, lookback settings and collection state. No Prometheus server was contacted for this article.

demo_value{job="demo",instance="demo-a"}
timestamp(demo_value{job="demo",instance="demo-a"})
time() - timestamp(demo_value{job="demo",instance="demo-a"})

The official function reference defines timestamp as the input sample timestamp and time as expression evaluation time, both in epoch seconds. demo-a is a teaching label value; replace it with the verified target identity.

The first shows selection, the second the selected sample timestamp, and the third its age relative to evaluation time. If selection is absent, the later expressions cannot invent a selected sample. Missing age must not silently become zero age. Acceptable freshness depends on the business decision; a report estimate and an immediate operation can need different bounds.

A smaller lookback can disqualify older samples but cannot repair ingestion or prove recovery. A window shorter than normal collection spacing can also create more gaps. Establish collection cadence and the required freshness before tuning it.

Does a smaller query step create more real samples?

For the bare selector used here, no. The querying introduction describes range queries as equally spaced evaluations between start and end, equivalent to repeated instant evaluations. A denser grid does not ingest more samples; several points may select the same old one.

That statement concerns evaluation times and original collection. If an expression explicitly uses step() in its arithmetic, changing step can also change the calculation. Do not extend the bare-selector conclusion to arbitrary expressions. A denser graph, a successful request and a newly collected observation are three distinct facts.
