A second CSP header cannot override the first one

Two enforced policies constrain each request. A local three-endpoint fixture separates the rejecting policy, CORS, delivery ownership and meta timing.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-09 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • A request must satisfy every enforced policy.
  • Relaxing another policy cannot revoke a rejection.
  • Meta delivery adds a parsing-time boundary.

Two enforced CSP policies do not use a last-header-wins rule. A request must pass each policy. If the original policy rejects a connection, appending another header that allows the API origin cannot rescue it. Find the policy that rejects the request, then identify the delivery layer that owns it.

An additional allowlist has no override authority

The CSP Level 3 Working Draft dated 27 October 2026 explains that each policy applies according to its disposition. This article considers two enforced Content-Security-Policy response headers. A Report-Only header is a separate reporting policy, not an additional source of permission. The document remains a Working Draft; it does not establish uniform browser support.

Suppose the application permits same-origin connections and a proxy appends a policy allowing a new API. The proxy’s permission satisfies one check. It does not remove the application’s restriction. Origins listed within one connect-src are also different from origins split across two policies: the second arrangement does not create a union of permissions. Evaluate each applicable directive separately, including its own fallback and matching rules.

A complete local fixture

The following server is an unexecuted teaching fixture. Save it as demo.py in an independent directory, run python3 demo.py, and open its printed URL in a browser. It listens only on loopback and contains no business data. Ports 8000 through 8002 must be available. No browser result or security-test pass is claimed.

from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
from threading import Thread

HOST = "127.0.0.1"
PAGE_ORIGIN = f"http://{HOST}:8000"
API_ORIGIN = f"http://{HOST}:8001"

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        port = self.server.server_port
        page = port == 8000 and self.path == "/"
        script = port == 8000 and self.path == "/app.js"
        if page:
            body = b'<!doctype html><title>CSP demo</title><pre id="out"></pre><script src="/app.js"></script>'
            kind = "text/html; charset=utf-8"
        elif script:
            body = b"""(async () => {
 for (const p of [8000, 8001, 8002]) {
  try {
   const r = await fetch(new URL(`/data`, `${location.protocol}//${location.hostname}:${p}`));
   document.querySelector('#out').textContent += `${p}: ${await r.text()}\n`;
  } catch (e) {
   document.querySelector('#out').textContent += `${p}: rejected\n`;
  }
 }
})();"""
            kind = "text/javascript; charset=utf-8"
        else:
            body, kind = b"endpoint reached", "text/plain"
        self.send_response(200)
        headers = [("Content-Type", kind), ("Access-Control-Allow-Origin", PAGE_ORIGIN)]
        if page:
            headers.extend([
                ("Content-Security-Policy", "connect-src 'self'"),
                ("Content-Security-Policy", f"connect-src 'self' {API_ORIGIN}"),
            ])
        for name, value in headers:
            self.send_header(name, value)
        self.end_headers()
        self.wfile.write(body)

servers = [ThreadingHTTPServer((HOST, p), Handler) for p in (8000, 8001, 8002)]
try:
    for server in servers:
        Thread(target=server.serve_forever, daemon=True).start()
    print(f"Open {PAGE_ORIGIN}/ ; press Enter to stop")
    input()
finally:
    for server in servers:
        server.shutdown()
        server.server_close()

Call the policies P1 and P2. The request to port 8000 passes both. Port 8001 passes P2 but fails P1. Port 8002 fails both. Only the same-origin request should return a readable body. The page deliberately prints a generic rejected message for any exception; that message alone cannot identify the failure as CSP.

For a second condition, add the 8001 origin to P1 and leave everything else unchanged. That request should now pass both policies. Relaxing only P2 leaves the original P1 rejection intact. This comparison tests whether the changed configuration actually owns the restriction. It is not a security template for a production application.

The data responses provide explicit CORS permission to reduce an unrelated source of failure. CSP permission does not guarantee that a cross-origin response is readable. Match the page result to the console’s directive and policy diagnostics, endpoint logs, and any network or CORS errors. The external app.js also avoids making an inline-script rejection the accidental subject of the experiment.

Trace the delivered response to its owner

An application, reverse proxy and static host can each add headers. Finding the new configuration in a repository does not establish what the browser received. Preserve every enforced and report-only policy on the actual document response, then map each one back to its owner. Different public routes or cache states may deliver different combinations; a direct origin response is not evidence for the public entry point.

If a legitimate feature requires another connection origin, review and change the policy that rejects it while retaining unrelated restrictions. Removing all CSP may restore the feature at a broader cost. A reduction in violation reports is also not sufficient evidence of compatibility: collection itself can fail.

A useful acceptance record includes browser version, document URL, both policy texts, the three-request table, endpoint logs, and the single changed condition. curl can verify header delivery but does not enforce CSP. Report only that narrower check if no browser interaction has been observed.

After changing a delivery layer, check whether the public entry still serves a cached old header combination. Preserve the actual document response and repeat the same browser flow; clicking a cache-clear control is not evidence that clients received the new policy. Keep the prior policy combination available for a scoped rollback, and distinguish resource permission from server authentication and business completion.

The revised fixture names its origins and stores headers in an ordered list. Both same-name CSP headers are still sent separately. Replacing that list with a plain dictionary would overwrite one header and change the experiment into a single-policy input. The second condition must change the first list entry while retaining the second.

Can a meta CSP override the server header?

No. The meta delivery section says an active meta policy is enforced alongside other active policies. It introduces a timing boundary absent from the header fixture: resources before the element are not retroactively blocked by that policy. Changing its content after parsing is not a dynamic replacement mechanism either.

Moving a restriction into a late meta element can therefore change protection for early resources without creating last-policy-wins behavior. Review placement and parsing time along with policy text.

The existing Worker fallback article already mentions the no-override rule. Here the separate task is to locate the owner of a rejection across delivery layers. Before changing a rule, write down which policies each necessary request must satisfy and who controls the rejecting one.
