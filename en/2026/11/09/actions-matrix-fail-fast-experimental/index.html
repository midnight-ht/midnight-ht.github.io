Why a tolerated experimental matrix still has cancelled siblings

Identify the failed member before interpreting job tolerance and fail-fast. A complete two-input workflow retains queued-job and scheduling boundaries.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-09 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • Tolerating an experiment does not tolerate stable failures.
  • Fail-fast can cancel running and queued members.
  • Disabling cancellation does not waive quality requirements.

Tolerating an experimental GitHub Actions matrix member does not tolerate every member’s failure. When siblings are cancelled, identify the failed member and its effective job-level continue-on-error value first. A stable member can trigger fail-fast even when experimental tolerance is configured correctly.

Two controls with different scopes

The matrix failure-handling documentation explains job tolerance alongside matrix fail-fast. Failure of a non-tolerated member can cancel running or queued matrix jobs. Failure of a tolerated member does not affect siblings because of that failure. This is the rolling documentation read on 9 November 2026, not a claim about its publication date.

Consider two stable environments and one experiment. Tolerating the experiment allows stable results to remain useful when that experiment fails. It does not remove a simultaneous stable failure. Seeing the experiment cancelled therefore does not prove its tolerance failed; the stable job may have triggered the cancellation.

A cancelled member may never have tested anything or may have stopped partway through. Neither case is a pass, and missing results do not identify a code defect by themselves. Preserve the cancellation reason, failure identity and effective configuration before changing the policy.

A complete two-input workflow

This unexecuted workflow is intended for an independent test repository and an authorized manual run. No hosted job was created for this article. It does not check out source, upload artifacts or deploy. Exit codes and a short teaching delay isolate matrix behavior; the delay is not a performance measurement.

name: inspect-matrix-failure
on:
  workflow_dispatch:
    inputs:
      fail_case:
        type: choice
        required: true
        default: experimental
        options:
          - experimental
          - stable
permissions:
  contents: read
jobs:
  inspect:
    runs-on: ubuntu-latest
    continue-on-error: ${{ matrix.experimental }}
    strategy:
      fail-fast: true
      max-parallel: 2
      matrix:
        include:
          - name: stable-a
            experimental: false
          - name: stable-b
            experimental: false
          - name: experiment
            experimental: true
    steps:
      - name: Controlled result
        env:
          MEMBER: ${{ matrix.name }}
          FAILURE_CASE: ${{ inputs.fail_case }}
        shell: bash
        run: |
          printf 'start %s\n' "$MEMBER"
          if [[ "$FAILURE_CASE" == experimental && "$MEMBER" == experiment ]]; then
            exit 1
          fi
          if [[ "$FAILURE_CASE" == stable && "$MEMBER" == stable-a ]]; then
            exit 1
          fi
          sleep 20
          printf 'end %s\n' "$MEMBER"

Choose experimental for the first run. Only the experimental member deliberately fails. That failure should not trigger cancellation of the stable members. They can still be cancelled for independent reasons, such as a manual cancellation or runner failure, so the acceptance record must establish causation rather than just a final color.

Choose stable for the second run. stable-a deliberately fails without job-level tolerance. Fail-fast can cancel siblings that are running or queued. Already completed members do not retroactively become cancelled. The workflow does not guarantee scheduling order or which member completes first.

Retain workflow commit, input, expanded configuration, job start and end times, conclusions and original logs for both runs. A missing end marker only establishes that the script did not reach that line; the platform state is needed to distinguish cancellation from command or runner failure. A start marker is not evidence of completed business validation.

Step tolerance is not the experiment’s job policy

Step-level continue-on-error affects failure propagation inside one job. It is not the same policy as job-level tolerance selected by a matrix field. Inspect the effective job rather than assuming that finding the keyword somewhere proves the experiment has the intended status.

Do not prematurely blame the layer either. A correctly configured stable failure can legitimately cancel siblings, as in the second condition. Identify the relevant failure first, then interpret its policy. Otherwise a legitimate cancellation may be “repaired” by weakening required checks.

The outcome and conclusion article covers original step results versus tolerated conclusions. Here the separate question is what happens to sibling jobs. Keep command exit, step conclusion, job tolerance and matrix cancellation visible as distinct facts.

Choose diagnostic coverage deliberately

Keep fail-fast when further results are no longer useful after a stable failure. Disable it when an upgrade investigation needs results from every environment and the extra runner work is justified. Disabling cancellation does not convert a stable failure to success or redefine merge and deployment requirements.

This fixture only waits locally. A real job may already have submitted work to an external service; cancelling the GitHub job does not establish that remote work stopped. Preserve its task identity and query its terminal state before a retry creates another submission.

An experimental designation also needs an owner and a support meaning: which environment is provisional, who investigates failures and what would end that status. The configuration cannot supply those decisions automatically.

Does max-parallel: 1 prevent cancellations?

No. Fail-fast can cancel queued members as well as running ones. max-parallel limits simultaneous execution; it does not disable the cancellation policy. With one slot, a non-tolerated failure can prevent later members from starting at all.

Change fail-fast when the goal is complete diagnostic results. Change concurrency when the goal is resource control. Keep stable success as a separate delivery requirement so experimental failure, stable failure and unexecuted work remain distinguishable.
