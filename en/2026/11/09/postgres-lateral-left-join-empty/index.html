Why did the customer disappear from a latest-order query?

Use a complete latest-order fixture to separate LATERAL references from row preservation, including empty children, ties and aggregate cardinality.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-09 · Estimated read 11 min
Translations
zh-CN en

Article

Key takeaways

  • LATERAL permits correlation; the join determines empty-result preservation.
  • Latest requires an explicit order and correct parent-child ownership.
  • An ungrouped aggregate not eliminated by HAVING can return one row on empty input.

A correlated subquery can return no orders. LATERAL does not make a cross join keep that customer. For a report that must retain every customer, use LEFT JOIN LATERAL and define both the correlation and the order-selection rule inside the subquery.

Suppose customer 1 has two orders, customer 2 has none, and customer 3 has one old order. A support page needs all three customers, with an empty order field for customer 2. If the second customer disappears after introducing a correlated query, inspect the join before manufacturing a dummy order. Missing from a result is not deleted from storage.

References and preservation are different choices

PostgreSQL 18 documents LATERAL as permitting references to preceding FROM items. For each source row supplying a correlated value, the item is evaluated with that value and its output is joined in the usual way. This changes visibility, not join cardinality.

A cross join combines the current parent with every returned child row. If there are no child rows, there are no combinations. A left join supplies a null-extended right side when no qualifying match exists. The keyword LATERAL itself does neither.

The official LATERAL section explicitly describes preserving source rows with LEFT JOIN LATERAL. The SQL below is an unexecuted example derived from that rule; no PostgreSQL instance or query plan was run for this article.

A complete latest-order input

The input includes a timestamp tie for customer 1. A unique order id breaks that tie for this exercise. Whether a greater id should mean a later business event is a separate decision.

WITH customers(id) AS (VALUES (1),(2),(3)),
orders(id, customer_id, created_at) AS (
  VALUES (11,1,timestamp '2026-11-01 09:00'),
         (12,1,timestamp '2026-11-01 09:00'),
         (31,3,timestamp '2026-10-01 09:00')
)
SELECT c.id AS customer_id, latest.id AS order_id
FROM customers c
LEFT JOIN LATERAL (
  SELECT o.id
  FROM orders o
  WHERE o.customer_id = c.id
  ORDER BY o.created_at DESC, o.id DESC
  LIMIT 1
) latest ON true
ORDER BY c.id;

The expected pairs are (1,12), (2,NULL) and (3,31). Replace the left join with CROSS JOIN LATERAL and remove ON true: the expected result contains only (1,12) and (3,31). Run each version against identical input and compare parent membership plus child ownership, not just row counts.

ON true accepts the rows already selected by the correlated subquery. It does not establish correlation. Remove the internal customer condition and each customer may receive the same global latest order. The result can still contain one row per customer while assigning the wrong child, so a count-only test is inadequate.

LIMIT 1 supplies an upper bound, not a minimum. It does not turn an empty input into a row. Likewise, ordering only by timestamp does not resolve the tie. Maximum child count, empty-child preservation and representative selection each need their own explicit rule.

Later filters still matter

A subsequent WHERE latest.id IS NOT NULL removes customer 2 even after a left join. That may satisfy a different report, but it no longer preserves the original parent set.

A status requirement introduces another choice: should the latest order be paid, or should the report select the latest paid order? Selecting first and filtering afterward differs from filtering before selection. A newer unpaid order and an older paid one expose the difference. Do not silently add an undefined status requirement to the final WHERE.

The site's LEFT JOIN filter-location article explains matching versus post-join filtering. This article adds a per-parent computation whose own result may be empty. Diagnose the row count of that specific subquery before examining its join and subsequent filters.

Also establish the authorized parent set separately. Restricting tenants only inside the orders subquery does not restrict which customers can appear on the left. This is a review consideration, not evidence that the example implements tenant isolation.

Can an aggregate subquery return a row on empty input?

Yes, under a specific additional condition: a plain aggregate with no GROUP BY and no HAVING that removes the group returns one aggregate row. For an empty order input, count(*) is 0. The main example's SELECT id with LIMIT 1 returns no row instead.

A cross join retaining customer 2 with count 0 therefore does not demonstrate that a cross join retains customer 2 with a normal latest-order subquery. The aggregate produced a real result row; LATERAL did not supply one automatically. GROUP BY can leave no groups, and HAVING count(*) > 0 can remove the single aggregate group.

The aggregate-function documentation and table-expression grouping rules support the distinction. Compare LIMIT 1, ungrouped count, grouped count and a count filtered by HAVING, recording both row counts and values per customer.

No execution-time or performance claim is made here. Validate the parent set and selected child first, then compare equivalent query forms using the real data, indexes and plans.
