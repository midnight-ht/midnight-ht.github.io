Why did the next assertion inside a failing subTest not run?

Trace the skipped tail and continuation point of a failed subTest, retain the inner failure, and change the stopping condition in a separate fail-fast comparison.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile

Translations

Article

Key takeaways

  • Continuation is after the with block, not the failed assertion.
  • Continued execution does not erase a failed subtest.
  • Stopping configuration and shared state need separate checks.

A failed assertion inside subTest skips the remaining statements in that with block. With the standard runner’s default settings, the failure is recorded and execution can continue after the block, including later loop iterations. It does not resume on the line after the failed assertion. Inspect the context boundary and execution trace before concluding that every check ran.

The continuation point matters

The Python 3.14.10 unittest documentation uses subTest to distinguish similar parameterized checks inside one test method. The CPython 3.14 implementation implements it as a context manager that reports an exception and resumes at the end of the enclosed block. The online version does not identify the reader’s installed interpreter. The first example assumes the standard result collector supports subtests and uses default stopping behavior.

Suppose one subtest checks an amount, currency and tax rate. A failure in the amount assertion leaves the block. The other assertions may never run. One reported failure therefore does not establish that the remaining properties passed. Give independent checks separate contexts or methods when each needs a result. Keep genuine dependencies explicit: a later calculation that requires a valid amount may only produce a secondary error after that prerequisite fails.

Specify the trace before running it

This is a complete, unexecuted local teaching file. It deliberately fails an inner subtest. The outer harness checks that both the trace and the retained failure match the stated expectation. Success of that harness would not mean that the inner test passed. It uses no business service, database or network.

# trace_subtest.py
import io
import unittest

EVENTS = []

def record(n, position):
    EVENTS.append((n, position))

def require_inner_failure(result, report):
    assert len(result.failures) == 1, report
    assert not result.wasSuccessful(), report

class TraceCase(unittest.TestCase):
    def test_rows(self):
        for n in [0, 1, 2]:
            with self.subTest(n=n):
                record(n, "enter")
                self.assertNotEqual(n, 1)
                record(n, "inside-tail")
            record(n, "outside")
        record("method", "done")

def observe(failfast=False):
    EVENTS.clear()
    stream = io.StringIO()
    suite = unittest.defaultTestLoader.loadTestsFromTestCase(TraceCase)
    result = unittest.TextTestRunner(stream=stream, failfast=failfast).run(suite)
    return list(EVENTS), result, stream.getvalue()

if __name__ == "__main__":
    events, result, report = observe()
    expected = [
        (0, "enter"), (0, "inside-tail"), (0, "outside"),
        (1, "enter"), (1, "outside"),
        (2, "enter"), (2, "inside-tail"), (2, "outside"),
        ("method", "done"),
    ]
    assert events == expected, events
    require_inner_failure(result, report)
    print(report)
    print(events)
    print("Expected inner failure and trace matched")

The candidate command is python3 trace_subtest.py. Capture its actual exit status and output before running unrelated commands. The expected list is supplied in advance; copying an observed trace into the oracle afterwards would remove the independent check.

Input zero reaches both inside-tail and outside. Input one records enter, raises at the assertion and skips inside-tail. Under the default conditions, execution resumes at outside. Input two then runs, followed by done. The markers establish reachability; result.failures and wasSuccessful establish the failed requirement. Neither replaces the other.

The harness explicitly requires an unsuccessful inner result. Removing the failing assertion to make the example appear green should break that contract. This is a teaching wrapper for an expected failure, not a CI policy for ignoring actual product failures. A real business test must still propagate its failed requirements to the appropriate gate.

Independent reports do not create independent state

Two subTest contexts remain inside one method and can share mutable objects. A list changed in one context can affect the next. Create fresh inputs at the intended boundary when independence is required. Database isolation and cleanup need their own real mechanisms; parameter labels do not provide rollback or recreate the fixture for each subtest.

Cleanup placed after a potentially failing assertion can also be skipped. Use finally or an appropriate cleanup registration according to resource lifetime, then verify acquisition failure, repeated cleanup and cleanup-error reporting separately. Continued execution does not establish that external side effects were undone.

A method-level run count is not a substitute for the trace. Several inputs belong to one method here; running that method does not establish that every statement for every input was reached. Preserve the failing input identifier as well as the events.

A named recorder centralizes event formatting without moving any observation point. Both scripts share the same unsuccessful-result verifier so the default and stopping conditions retain one definition of the expected inner failure. The product assertion remains in its original position.

Why does -f prevent the next subtest from running?

Fail-fast changes the continuation condition. The standard runner can stop after the failed subtest, so the earlier default trace does not apply. Save this separate comparison file alongside the first file. Importing it loads definitions without executing the main-guarded default harness.

# trace_failfast.py
from trace_subtest import observe, require_inner_failure

events, result, report = observe(failfast=True)
expected = [
    (0, "enter"), (0, "inside-tail"), (0, "outside"),
    (1, "enter"),
]
assert events == expected, events
require_inner_failure(result, report)
print(report)
print(events)
print("Expected fail-fast boundary matched")

This comparison is also unexecuted. The candidate command python3 trace_failfast.py should show no outside marker for input one, no input two and no method-tail marker. Preserve the actual runner configuration; absence of a stopping flag in the test source does not establish how every execution environment runs it.

The existing patch lookup article concerns which dependency name is replaced. Here the separate question is which checks remain reachable after failure. Keep the input, trace and final failed result together so an unreported error is not mistaken for a verified requirement.
