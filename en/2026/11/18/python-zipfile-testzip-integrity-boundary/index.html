Why did testzip() return None for a ZIP missing its manifest?

Use intact, corrupted, and missing-manifest ZIPs to compare testzip(), required names, and format identification.

Updated 2026-11-18 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • Report a bad member separately from missing required files.
  • Follow successful format identification with member and delivery-contract checks.
  • Verify required fields even when the archive contains the manifest.

The archive passed testzip(), but the importer still cannot find manifest.json. An omitted manifest leaves every file actually packed in the archive free to pass its checks. Record member integrity and required-file presence separately so each failure reaches the person who can fix it.

What the check sees inside the archive

Python's ZipFile.testzip() reads the files in the archive and checks their headers and CRCs. When it finds a bad member it returns the first bad filename. If it reports no bad member, it returns None. Its inputs are the files in the archive. It has no way to learn that an importer expects a file called manifest.json. If the packager never inserted the manifest, the check has no corresponding member to read.

Reading the central directory does not establish that every member's data is readable. Opening the archive can give you a list of names. A CRC result here comes from reading and checking member data. Troubleshooting can yield at least three distinct observations: the archive will not open, the archive opens but a member is damaged, or the archive and its existing members look fine but a required file is absent. Record them separately so a packager can decide whether to try the transfer again, rebuild the archive, or verify which build the importer received.

The word first matters. A returned member name tells you the first failure this check reported. It does not imply the rest of the members were all checked. Use that name as a diagnostic. An inventory of every bad member needs its own member-by-member logic and exception policy. Keep failures opening the whole archive separate from a returned bad-member name. For example, calling testzip() on a closed ZipFile directly raises ValueError instead of returning a filename.

Three inputs make the two checks fail independently

Build the archive in memory and use uncompressed ZIP_STORED so the fixture can change a literal payload byte. Assert that the payload occurs only once, then replace its first byte without changing its length. The original directory and headers stay intact and the stored CRC still describes the old payload. Build the missing-manifest example as a valid ZIP in its own right so deleting bytes does not also corrupt that control.

from io import BytesIO
from zipfile import ZIP_STORED, ZipFile, is_zipfile

payload = b"UNIQUE-LOCAL-ZIP-PAYLOAD"
required = {"manifest.json", "payload.txt"}

def make_zip(with_manifest):
    out = BytesIO()
    with ZipFile(out, "w", compression=ZIP_STORED) as archive:
        archive.writestr("payload.txt", payload)
        if with_manifest:
            archive.writestr("manifest.json", "{}")
    return out.getvalue()

def inspect_archive(blob):
    with ZipFile(BytesIO(blob)) as archive:
        missing = required - set(archive.namelist())
        return archive.testzip(), missing

complete = make_zip(True)
assert complete.count(payload) == 1
bad = complete.replace(payload, b"X" + payload[1:], 1)
assert inspect_archive(complete) == (None, set())
assert inspect_archive(bad) == ("payload.txt", set())
assert inspect_archive(make_zip(False)) == (None, {"manifest.json"})
assert is_zipfile(BytesIO(bad))
print("intact, corrupted payload, and missing manifest distinguished")

Compare the three results. The intact archive returns None and an empty missing-name set. The altered archive still contains both names, but the check returns payload.txt. The third also returns None, while its missing set contains manifest.json. Two different inputs produce None, so that return value cannot distinguish a complete delivery from an omission. Different fields expose different failures, allowing the importer to classify each.

The fixture covers no digital signature, authenticated transfer, or deliberate tampering detection. It shows that a one-byte alteration breaks the CRC check on this constructed payload. A separate question is whether this file came from the approved build. An archive under the expected name that passes CRC can still come from a different build. The site's build artifact identity article shows how to leave verifiable records for that question.

Specify the delivery contract and route each failure

Suppose the importer accepts ZIPs with a manifest and a payload. Its entry point can record file-level integrity and the required member list separately. Keep the member name when reporting corruption and the required path when reporting an omission. One generic archive error gives the sender no way to tell whether to recover a transfer or change the build. Separate evidence avoids rerunning every possible failure on each upload path.

Suppose the importer shows the packager the first rejection and keeps more detail in an internal intake report. If the archive cannot open, mark the member checks as not started. Do not record them as clean. If names were read before a member failed, the report can retain the name-check result and say that content loading stopped. Marking any check that could not run makes it possible to verify the same stage on the next delivery.

The content contract is a third check. An archive can open, pass CRC, and supply every required filename while its JSON manifest still omits a necessary field. If the importer expects a format version, read and parse the manifest, then assert that field separately from filesystem presence. The fixture's empty JSON object keeps the first two checks independent. It does not stand in for a real manifest schema.

Decide what to do with extra files using the same approach. If the format permits attachments, checking for a required subset can be sufficient. If the intended shape is fixed, the check should report unexpected names too. Define how directory entries, duplicate members, and path casing affect the format before choosing a representation. This simple fixture uses a set to find missing names, so it checks no per-name multiplicity and implements no filesystem extraction policy.

Would is_zipfile catch the altered payload on its own?

The final assertion shows that is_zipfile still accepts this altered example. It identifies recognizable ZIP input using the format's magic, rather than reading each member and verifying its CRC. An upload entry point could use it to reject plainly non-ZIP input, then run a member check to catch this broken payload. Keep both observations in the acceptance test: format identification returned true and the member check reported payload.txt. The first result alone cannot describe whether the archive is ready to import.
