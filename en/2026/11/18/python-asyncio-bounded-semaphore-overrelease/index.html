How did a Semaphore initialized with one permit admit two acquires?

Compare plain and bounded asyncio semaphores to see how an extra release affects capacity and how to assign cleanup around cancellation.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-18 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • Use separate instances to check extra releases and subsequent capacity.
  • The bound checks a total; give each release its own accountable owner.
  • With manual cleanup, enter the release-protected region only after acquisition succeeds.

The semaphore starts with one permit. A worker finishes and returns its permit, then returns it again while exiting. A plain asyncio.Semaphore accepts the extra release. The next two acquires now succeed immediately. When investigating this kind of capacity change, start with releases and find the code that owned the permit.

How far can the count rise after a release?

A semaphore maintains an internal count. Acquiring a permit reduces the count. If it is zero and the call cannot acquire immediately, the acquire waits. Releasing increases available capacity and can wake a waiter. A plain Semaphore permits more releases than acquires. In this example there are no waiters. Taking the single permit reduces the count to zero, returning it brings it to one, and returning it again brings it to two. No task explicitly changed the configured limit, yet the semaphore can now accommodate two holders.

BoundedSemaphore serves the same purpose and checks the starting bound on release. A release() that would push the count above its initial value raises ValueError. The legitimate return from zero to one works. The next return, at one already, fails. The exception lands at the extra release, so the stack can point to the cleanup branch that ran an extra time.

This is a check on the total, without knowledge of task identity. Imagine a bound of two with both permits held and nobody waiting. One task returning its own permit twice can bring the count to two without crossing the starting bound. When the other real holder releases later, the failure can appear far from the original mistake. If you need to trace this kind of bug, record who acquired and who released rather than counting exceptions alone.

Use two controls without queued tasks

Create two independent semaphores, each starting at one. Acquire and return a permit, then attempt one extra release in each case. The fixture creates no background tasks and uses no timer. It uses locked() to inspect whether an immediate acquire is possible, so it does not have to issue a deliberately blocked acquire.

import asyncio

async def exercise(make_semaphore, bounded):
    sem = make_semaphore(1)
    take_permit = sem.acquire
    return_permit = sem.release
    await take_permit()
    return_permit()
    try:
        return_permit()
    except ValueError:
        assert bounded
    else:
        assert not bounded

    await take_permit()
    assert sem.locked() is bounded
    if not bounded:
        await take_permit()
        assert sem.locked()
        return_permit()
    return_permit()

async def main():
    await exercise(asyncio.Semaphore, bounded=False)
    await exercise(asyncio.BoundedSemaphore, bounded=True)
    print("ordinary admitted two; bounded rejected extra release")

asyncio.run(main())

The plain object accepts the first extra release. After the next acquire it can still admit a second, and the fixture actually takes both. Only after holding two does it show that a further acquire would not be immediate. The bounded object raises on the extra release. Once its one legitimate permit is held, it cannot admit another immediately. Fresh instances keep the altered state of one trial out of the other.

The test protects a legitimate return as well. The first release is outside the exception handler; a failure there fails the test outright. An assertion that merely observed some ValueError would not prove which release produced it. Cleanup at the end returns exactly the permits acquired in that trial, making the routine suitable for other independent trials in the same loop. This run tests starting capacity and extra releases within one event loop. It measures no fairness, thread behavior, throughput, or network load.

Give one layer ownership of the release

Two functions sometimes both take responsibility for cleanup. An outer worker acquires the permit before it enters a critical section. An inner operation releases it to be safe, and the outer worker then executes its own cleanup. By the time a busy service appears to admit too much work, the surplus release may be hard to locate. A clear contract gives release to the same layer that acquires. The inner operation is responsible for returning its work result.

If acquisition and cleanup can live together, using the semaphore as an async context manager reduces the number of manually managed branches. If ownership really travels between functions or objects, test successful return, a work exception, and a repeated cleanup call separately. Check the capacity left afterward as well as the calls that returned it. A bounded semaphore detects some mistakes early. An ownership check still needs to account for each acquired permit separately.

A service test can put the first admitted request behind an application-controlled gate and verify that a second request remains outside. Then trigger an error in the work branch and see which layer releases. Only exit by the original holder should admit the second request. That test checks an actual critical section in addition to primitive calls. The site's TaskGroup cancellation and cleanup article covers propagation of failure across a task group. Here the issue is which code owns the release when a holder exits or is cancelled.

Where should finally go if a task can be cancelled while waiting?

Put await sem.acquire() before the manual try/finally. Enter the protected work region only after acquisition returns successfully. Cancellation while waiting means the caller has acquired no permit and needs no release of its own. If cancellation instead interrupts work that already started, the work exits through the protected region and releases. Avoid an unconditional finally enclosing both the wait and the work.

Test the two cancellation times separately. Hold a permit, cancel a second task while it waits, and verify that the original holder remains exclusive. In another run, let the task acquire, hold it at a controlled wait inside the work, and cancel it there. A fresh task should then get the permit. Those are recommended service tests. The executed fixture above checks sequential acquires and releases; it covers neither cancellation scenario.
