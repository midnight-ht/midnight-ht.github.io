Can Git recognize the same patch when its files arrive in a different order?

Swap complete Git file diffs and introduce an actual edit to see when stable and unstable patch IDs differ.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-18 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • Stable IDs tolerate reordering complete file diffs.
  • Patch identity and commit identity support different checks.
  • Record the fingerprint mode and comparison endpoints.

Swap the order of two complete file diffs and their stable Git patch IDs can agree. The stable mode computes a patch fingerprint that tolerates this rearrangement. When checking a backport or regenerated patch, choose a mode explicitly and preserve the comparison range for each input. A mismatch alone does not tell you that code behavior changed.

An engineering handoff makes the problem visible. One tool regenerates a patch and prints the second file first, whereas the approved copy started with the first file. A direct text comparison shows whole blocks moving. If the release gate stores a fingerprint, the reorder may produce a needless rejection or reveal that the gate uses another hashing mode. A small repository can demonstrate the difference without any commit history.

Hold the edits fixed and swap complete file blocks

Save the following as check.sh and run it with Git that supports --stable and --unstable. The script creates a disposable repository, puts the original files in the index, then edits the working tree. Both diffs compare the same index and working tree while selecting one file each. The reorder moves complete file blocks, keeping their hunk headers, context, and edited lines intact. It does not shuffle additions or removals inside a file's patch.

set -eu
lab=$(mktemp -d)
trap 'rm -r "$lab"' EXIT
cd "$lab"
git init -q
git version
first=a.txt
second=b.txt
printf 'a before\n' > "$first"
printf 'b before\n' > "$second"
git add "$first" "$second"
printf 'a after\n' > "$first"
printf 'b after\n' > "$second"
git diff --no-ext-diff -- "$first" > a_diff
git diff --no-ext-diff -- "$second" > b_diff
cat a_diff b_diff > ab_diff
cat b_diff a_diff > ba_diff

patch_id() {
  git -c patchid.verbatim=false patch-id "$1" < "$2" |
    cut -d' ' -f1
}
stable_ab=$(patch_id --stable ab_diff)
stable_ba=$(patch_id --stable ba_diff)
unstable_ab=$(patch_id --unstable ab_diff)
unstable_ba=$(patch_id --unstable ba_diff)
printf 'stable ab=%s ba=%s\n' "$stable_ab" "$stable_ba"
printf 'unstable ab=%s ba=%s\n' "$unstable_ab" "$unstable_ba"
test -n "$stable_ab"
test "$stable_ab" = "$stable_ba"
test -n "$unstable_ab"
test -n "$unstable_ba"
test "$unstable_ab" != "$unstable_ba"
printf 'b distinct\n' > "$second"
git diff --no-ext-diff -- "$second" > changed_diff
cat a_diff changed_diff > changed-ab_diff
changed=$(patch_id --stable changed-ab_diff)
printf 'stable changed=%s\n' "$changed"
test -n "$changed"
test "$stable_ab" != "$changed"

On Apple Git 2.50.1, the stable IDs for ab and ba both began with d98bfeff. The script compared the full values. The two unstable results differed. Then the script changed b's new content to distinct, kept the original a block, and regenerated the b diff. The stable ID changed. That gives the fixture two independent checks. File order must not change the stable result, while the introduced content change does affect it. The prefix describes this run. Compare the complete outputs when reproducing it.

The unstable control suggests a useful migration check. If a team has saved IDs from an older tool and switches its pipeline to stable, it cannot assume those old identifiers form a baseline for the new mode even if the order has never changed. The Git manual documents the compatibility difference. Save a small reconstructable input set and its mode during the migration. Generate the old and new values against the same patch, then change the downstream checks. If the historic input is unavailable, record that gap and establish the new baseline with a controlled sample.

Use the fingerprint to narrow the review

Suppose the main branch already reviewed a fix and someone backported it to a maintenance branch. The commit objects can differ because the parents, commit timestamps, or messages differ. To flag likely duplicate edits, pin the parent and result on each side. Export the patches with the same rules and then compare stable IDs. Keep the commands and the base or parent objects with the result. Someone rerunning a default working-tree diff may be looking at different inputs altogether.

Matching fingerprints still leave the backport context to review. Imagine both patches change a line in a configuration validator, but one branch sets a different default before calling it. The source patch can match while application behavior differs. Check that the changed file and relevant call path exist in the release branch, then run a behavior check against that branch's inputs. The fingerprint narrows the changed code to inspect. Commit identity anchors its history. The behavior test supplies evidence for the scenario it actually runs.

Some teams also want the gate to flag formatting changes. That makes stable's whitespace policy part of the decision to adopt it. If a human needs to review indentation introduced by a formatter, an equal stable ID cannot record that review. If the goal is to recognize likely duplicate patches, a mere reorder need not count as a reject reason. Define the change the gate should block, then calibrate it with both a reordered patch it should accept and an edit it should reject.

A short prefix can be convenient in logs, but retain the full ID and source of the patch in the receipt. When values disagree, first check whether both were generated in the same mode, then look for an extra path outside the approved scope. With those inputs aligned, inspect the actual patch blocks that produced the discrepancy.

If the gate produces a review record, give the fixture two expected outcomes. A reordered patch can reference the existing content review when the fingerprint modes match. The changed-content control should request a fresh review and preserve its changed line. When a newly configured task returns a different ID, there is a third possibility: the comparison mode changed. Check both modes against one saved patch without touching the release branch. This is a gate design, outside the local fixture.

What if trailing whitespace needs to affect the ID?

Use git patch-id --verbatim. It preserves whitespace while retaining stable file-order handling, and it is incompatible with --unstable. A separate one-file run on the same Git version changed mode=old to mode=new, once without extra whitespace and once with a trailing space. The full stable IDs matched and the full verbatim IDs differed. This control changes whitespace in the content. The reorder in the main fixture changes no bytes inside the file blocks. Record the mode in the receipt so a whitespace-normalizing baseline is not reused by accident.
