Why can a Pending Pod avoid scheduling even when nodes are free?

Compare gated and ungated Kubernetes Pods, and verify gate release, node assignment, and application readiness independently.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-18 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • A scheduling gate holds the Pod before normal placement.
  • Check PodScheduled and identity after removal.
  • Verify container readiness separately.

A Pending Pod can have free nodes available and still be waiting to enter node selection. While spec.schedulingGates contains an outstanding gate, normal scheduling waits. Inspect the actual gate list and node assignment to distinguish a Pod that is not yet eligible from one the scheduler cannot place.

This can show up when a prerequisite takes longer than expected. A delivery process creates a Pod, then waits for preparation that has nothing to do with choosing a node. The Pod is visible and the creation step reports success, but scheduling has not started. Someone might see Pending and add capacity. More nodes cannot remove a gate owned by another process. A gated Pod and an otherwise equivalent control make the cause visible.

Add a gate to just one Pod

Use a disposable cluster. PodSchedulingReadiness has been stable since Kubernetes 1.30. The fixture needs permission to create a namespace and Pods, the default scheduler, and at least one node that meets the constraints of both Pods. It does not set nodeName and assumes admission does not set it or add further gates. Save this as pods.yaml.

apiVersion: v1
kind: Pod
metadata:
  name: ordinary
spec:
  containers:
  - name: pause
    image: registry.k8s.io/pause:3.10
---
apiVersion: v1
kind: Pod
metadata:
  name: gated
spec:
  schedulingGates:
  - name: example.com/prepared
  containers:
  - name: pause
    image: registry.k8s.io/pause:3.10

Set LAB_CTX to the confirmed disposable context. Save the following as a shell script. The ordinary Pod's PodScheduled condition is the positive assignment control. It is a better signal for this stage than container readiness, since the image may still be pulling. Inspect the gated Pod's reason and fields next. The final assertions follow gate removal. Expect that transition on the same Pod UID.

set -eu
: "${LAB_CTX:?set LAB_CTX to the disposable cluster context}"
ns=zy18-scheduling-gate
lab() { kubectl --context "$LAB_CTX" -n "$ns" "$@"; }
kubectl --context "$LAB_CTX" create namespace "$ns"
lab create -f pods.yaml
lab wait --for=condition=PodScheduled pod/ordinary --timeout=90s

status_path='{.status.conditions[?(@.type=="PodScheduled")].reason}'
lab wait --for="jsonpath=$status_path=SchedulingGated" pod/gated --timeout=90s
node_path='{.spec.nodeName}'
uid_path='{.metadata.uid}'
gate_path='{.spec.schedulingGates[0].name}'
observed_gate=$(lab get pod/gated -o "jsonpath=$gate_path")
test "$observed_gate" = example.com/prepared
test -z "$(lab get pod/gated -o "jsonpath=$node_path")"
before=$(lab get pod/gated -o "jsonpath=$uid_path")

lab patch pod/gated --type=merge -p '{"spec":{"schedulingGates":[]}}'
lab wait --for=condition=PodScheduled pod/gated --timeout=90s
after=$(lab get pod/gated -o "jsonpath=$uid_path")
test -n "$after"
test "$after" = "$before"
lab get pod/gated -o wide

Expect ordinary to get a node. Gated should still show the gate, no node assignment, and the SchedulingGated reason. The Pod becomes eligible for ordinary scheduling once the sole gate is gone. If a suitable node remains, expect PodScheduled to become true for the same UID. If the gate is gone and that condition has not been met, inspect resources, constraints, and scheduling events. Eligibility grants neither resources nor a reservation. Ninety seconds is a client timeout rather than a scheduling guarantee.

No cluster was contacted and these commands were not run. During your own acceptance check, save the initial observations and the same-UID result after release. If ordinary also fails to get a node, restore the positive control before attributing the two outcomes to the gate. Remove the fixture namespace afterward using the same disposable context.

Give release of the gate an owner

Use a gate for a condition that can be observed before placement. A controller responsible for data preparation can remove its named gate after receiving evidence that the current input was registered. Write down exactly which event authorizes removal. Deleting the gate based only on Pod age could let the Pod proceed before preparation finishes. An admission process that adds an unowned gate can leave an otherwise schedulable Pod waiting indefinitely. Preserving the prerequisite receipt and the gate owner's action gives each a source of evidence.

Acceptance should include a contrary input. If preparation explicitly fails, keep the gate in the list and provide a reason for the wait. An operational timeout can prompt investigation of the owner and preparation process, rather than waiting indefinitely for Running. After preparation succeeds, inspect scheduling and application availability separately. Image pulling, process failure, or readiness problems can arise after node assignment. Treating readiness as the gate-removal receipt hides the decision the operator needs to verify.

Tie the preparation receipt to the current object. Suppose release automation deletes a Pod that has waited too long and recreates it under the same name. A delayed success receipt then arrives for the first input. Releasing a gate by name alone could admit work whose current input is not prepared. Bind preparation to the relevant object identity or business batch and verify it again before release. If names match but the batch differs, leave the gate in place and get a current receipt from the owner. This is a failure example and was not executed.

For two prerequisites, give each a gate name and an owner. A storage process might confirm that the data exists, while an orchestration process confirms permission to start. On the first receipt, remove its corresponding gate and leave the other waiting. Read the resulting gate list alongside the prerequisite receipts. Do not reuse the sample patch that clears the entire list for a Pod with several owners. The fixture has only one known gate. A real controller should remove only its own entry.

An on-call record can track when the gate list changed, when placement succeeded, and when the application served traffic. If the window does not contain a successful application request, record that part of acceptance as outstanding even when placement is confirmed. This gives the preparation, scheduling, and application owners the evidence each needs.

Can the gate be added back to the same Pod after release?

No. The documented API allows gates to be set on creation and removed afterward. In the same isolated environment, try a patch that would add example.com/prepared back to gated. Expect the API to reject it, then read the gate list to confirm it was not added. This control was not executed. A new waiting cycle can use a newly created Pod with the right prerequisites, or an independent application state control. The removal is a one-way change for this Pod.
