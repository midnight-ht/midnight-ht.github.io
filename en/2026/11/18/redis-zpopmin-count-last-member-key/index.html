Why did ZPOPMIN return one member and remove the key?

Compare a read and two pops on a disposable sorted set. Check the return count, member order, and key state after the last pop.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-18 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • Treat count as a limit and assert the identities of returned members.
  • Check the key separately after the last member is popped.
  • Use a range read for previews that must leave pending work in place.

Both ZPOPMIN calls ask for two items. The first returns two. The second returns the last item and removes the key as part of the command. The requested count is an upper limit. To test the final batch, inspect the members returned and whether the key still exists separately.

Separate what came out from what remains

Take a disposable priority set with a, b, and c at scores ten, twenty, and thirty. Lower scores come out first. A preview only needs to read the two lowest ranks. A worker that intends to remove work uses a pop. Both calls can show a and b. The difference appears when you inspect the original set after the call.

ZPOPMIN removes and returns up to count of the lowest-scoring members from one sorted set. The default count is one. Asking for more than are currently present does not fail or undo the items removed. When the reply has multiple members, they are ordered from lower to higher scores. Using distinct scores here isolates priority ordering, short batches, and the subsequent state.

Redis deletes the sorted-set key when the pop takes its last member. After the first pop, the key still names a set containing c. After the second, the key is gone. Counting the one returned member misses that change. A cardinality check alone also leaves the key-level observation out of the report. Check the same key with EXISTS to connect the final pop and the disappearance.

Walk the commands on an isolated key

The Redis fixture below is unexecuted. The expected results are derived from the command documentation. Use an initially absent temporary key in a disposable database and exclude concurrent writers and expiry for the duration. Each observation can then be attributed to the preceding command. The text describes member and score pairs conceptually; RESP versions and client libraries can represent them differently.

ZADD review:zpop:nov18 10 a 20 b 30 c
ZRANGE review:zpop:nov18 0 1 WITHSCORES
ZCARD review:zpop:nov18
ZPOPMIN review:zpop:nov18 2
ZCARD review:zpop:nov18
EXISTS review:zpop:nov18
ZPOPMIN review:zpop:nov18 2
EXISTS review:zpop:nov18
ZPOPMIN review:zpop:nov18 2

Initialization should report three new members. The rank read returns a at ten and b at twenty. The following cardinality is still three, which supplies a read-only control. The first pop returns a and b in that order too, but the following cardinality is one and the existence check returns one. The same two members can come back with very different effects. Cardinality distinguishes the two paths.

The second pop returns only c at thirty. The next existence check should return zero. The third pop returns an empty result. There is no placeholder member in the second batch even though the request still says two. Iterate over the members actually returned, record the one that arrived, and verify that it is the c you inserted. A caller that treats a short batch as complete failure would lose track of work that Redis already removed. Checking identity and score also detects wrong-key or decoding mistakes a length assertion would miss.

Use the same adapter logic for full and short batches. Normalize each fixture reply to member-and-score pairs, then confirm the second batch contains one pair and the score can be represented as the application expects. A flat array can hold a member and its score in two entries. Raw array length is therefore an unreliable member count. Give the empty reply its own assertion so the adapter cannot confuse no member with a member whose name is the empty string.

Preview, claim, and completion have different owners

A dashboard usually needs to show the lowest few items. A range read lets it refresh without modifying work. A worker that chooses a pop should define what happens to a member once it leaves the pending set. If the workflow needs recovery after a crash, design an independently verifiable processing state. The site's article about Redis worker claims and recovery discusses a processing list. This sorted-set fixture covers removal and key deletion, with no verification of recovery or redelivery across processes.

When investigating a short batch, record the requested count, the actual members, and the time of the key check. Suppose a producer adds a member just after your pop. A later EXISTS can then find the key again. That observation does nothing to change the earlier one-member reply. The fixture assumes isolated sequential commands. A pop reply and a later existence check on a busy service are separate observations. If the application needs a durable status that correlates them, decide where in the workflow that status is created.

You can give the preview its own regression check. Seed a different temporary key with the same three members and simulate two refreshes. Both should display the same lowest pair and leave cardinality at three. Only the worker path should assert that the key becomes absent after the final pop. Even if client wrapper methods happen to return identical member arrays, the test exposes use of a write command in the preview. It observes server state directly.

Will a larger count wait for the producer to add another member?

ZPOPMIN returns what it can take when it runs. Raising the count introduces no wait. If a worker should wait when a queue is empty, BZPOPMIN offers a timeout and pops one member at a time. It does not wait to fill a requested batch. For an empty set with a two-second waiting budget, separate the timeout branch from the branch that obtains a member. Any batching policy still needs its own deadline or size commitment. This fixture starts no producer and measures no wait or timeout.
