Which stage does Buildx select by default in this Dockerfile?

Inspect the default Buildx stage and compare it with an explicit target using two fresh local exports.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-18 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • The targets call reports available targets and the default.
  • Release builds can select their intended target explicitly.
  • Read back the files from the actual export.

When a multi-stage Dockerfile runs without --target, use docker buildx build --call=targets to inspect which stage the frontend marks as default. That call lists the available targets. If the release expects another stage, select it explicitly and read back the export. The target list tells you which stage will be selected. The files tell you what you actually delivered.

A developer might append a stage for local inspection and make debugging easier. An existing release command has never set a target explicitly. It still completes and produces a nonempty export. Only when a downstream job cannot find the runtime entry does the team revisit stage selection. You can demonstrate the failure without running a container or pushing an image.

Give each independent stage a different file

Save this Dockerfile in an empty directory. Both stages use scratch and neither copies from the other. Create runtime.txt and inspection.txt next to it. Give them the single lines runtime-marker and inspection-marker, respectively. A file unique to each stage gives you independent evidence of which stage the export selected.

# runtime is the shipping file set
FROM scratch AS runtime
ARG MODE=delivery
LABEL demo.mode=$MODE
COPY runtime.txt /runtime.txt

# inspection is the local inspection file set
FROM scratch AS inspection
COPY inspection.txt /inspection.txt

Run the following from that directory. Use a Buildx builder that supports the targets call and local exporter, and build for a single platform. The first call reports the stage names and default. The next two build and export files. Each uses a fresh destination. Check both the expected contents and the absence of the other stage's file.

set -eu
work=$(mktemp -d)
trap 'rm -r "$work"' EXIT
docker buildx version
docker buildx build -q --call=targets .
docker buildx build --progress=plain --output "type=local,dest=$work/default" .
docker buildx build --progress=plain --target runtime --output "type=local,dest=$work/runtime" .
test "$(cat "$work/default/inspection.txt")" = inspection-marker
test ! -e "$work/default/runtime.txt"
test "$(cat "$work/runtime/runtime.txt")" = runtime-marker
test ! -e "$work/runtime/inspection.txt"
printf 'default=inspection explicit=runtime\n'

On Docker Desktop with Buildx v0.37.2, the report marked inspection as default and listed runtime. The first export, with no target specified, contained only the inspection marker. Selecting runtime produced only the runtime file. The script exited zero after checking both expected contents and absences. It did not push an image, run a container, or verify a production build.

The fixture also shows where stage descriptions come from. A comment immediately before a stage that begins with its name can appear in the report. Calling a stage the shipping file set describes the author's intent. It does not change the default. Treating that description as target selection picks the wrong export in this fixture. Read the default marker or the explicit command argument and verify the selected stage with its unique file.

Turn the release contract into two checks

A team may deliberately keep a development stage as default. The release job can record the intended stage, such as runtime, and select it explicitly. To calibrate a CI gate, temporarily remove the target argument and check that the gate rejects an export containing only inspection. Restore the selection and verify the expected runtime file. The two local exports exercise these inputs. The fixture does not run a real CI gate, packager, or release. A nonempty directory or successful command cannot distinguish the two outputs.

A project that promises a customer artifact from the default build can instead make release the default stage. Verify the default marker in its target list so reordering or inserting a stage cannot change selection silently. Correct selection still needs a file check. Someone can leave the stage name unchanged and remove or replace a required file. A listed target does not establish that an older file contract remains true. Save the build configuration, target choice, and a readback of expected files from the delivered output.

If your team works with several build frontends, use --call=subrequests.describe to see whether the selected frontend supports the targets call. Use the same Dockerfile and frontend input for inspection and release. A report from -f Dockerfile.dev cannot explain a build using Dockerfile.release. When they disagree, identify the file the actual build used and verify its default. That separates an invocation mismatch from a changed artifact. The inspection call does not build the example artifact. Some Dockerfiles may still require the frontend to resolve base-image information.

A downstream job publishing an image must also verify what it actually releases. A local file export can confirm an entry file, but check the chosen target in the image build and destination receipt separately. A filesystem export cannot replace inspection of the complete image configuration. Verify the runtime entrypoint in that image's configuration or exercise it in a controlled run. This fixture only ran the local exporter.

Test whether the invocation can also reject a name missing from the stage list. Keep the same Dockerfile and context, replace --target runtime with the nonexistent --target delivery, and choose a fresh export destination. The local build returned one. Its diagnostic said the target stage could not be found, and the output directory was never created. This is a separate failure. Omitting the target can successfully export inspection, while misspelling an explicit target gives no export. A handoff that says only “incorrect artifact” cannot distinguish the cases. Save whether the target was omitted or provided, along with the process status and output check.

How do I inspect build arguments for the chosen stage?

Run docker buildx build -q --call=outline --target runtime .. Outline lists the arguments the target consumes and their defaults. A separate local invocation on the sample printed runtime and MODE delivery. That identifies a parameter and the default value the stage sees. The main comparison identifies the stage and verifies its exported files. Check the resulting artifact to see how build arguments affect actual behavior.
