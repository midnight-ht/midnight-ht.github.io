Why didn't sync.Once.Do retry after a panic?

Use an attempt count, configuration state, and a fresh-instance control to separate Once behavior after a panic from retries owned by the application.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-18 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • A Once does not invoke a new function after its first invocation panics.
  • Check the initialization artifact and the recorded failure separately.
  • Use application retry state if initialization must recover after a temporary failure.

A Go service panics on its first attempt to load a local config. The caller recovers and calls Do on the same sync.Once again. The second call returns, but the config is still missing. “Do returned” and “initialization succeeded” are different observations. The first call used up that Once even though its function panicked.

Recovery changes the caller's control flow

Suppose the initializer reads local configuration and saves the parsed result in memory. It panics before the read completes, and its caller recovers so it can continue. The program has an error record but no valid config for a consumer. Give the same Once a second Do call, even with an innocuous replacement function, and the new function will still be skipped. Recovering does not undo the Once's record of the first call.

The Go contract applies to an instance. Do invokes the function only for the first call on that instance. If it panics, Do treats that invocation as having returned. Future calls return without invoking a function. A Once coordinates callers around one initialization attempt. It does not preserve a business success value or replay the first panic to later callers. If a consumer assumes there is config after Do, its next error could come from accessing missing state, with no second initializer run.

The return count can give a misleading picture. After the first panic, the caller that recovered can continue its own work. Three later calls might all return. Four log entries cannot establish that any config was loaded. Track the actual artifact, recorded failure, or readiness state if you need to know whether the service can accept work. The wait between attempts changes nothing: the file could become readable immediately, seconds later, or never, and the original Once would still skip the function.

Use a second function and a second instance as separate controls

This sequential Go fixture has not been run. Its first helper recovers the expected panic around a single Do call. The second call on the original Once passes a different function, which sets loaded if invoked. A fresh Once receives exactly the same writing function as an independent control.

package main

import "sync"

func firstAttempt(once *sync.Once, attempts *int) (failure any) {
    defer func() { failure = recover() }()
    once.Do(func() {
        *attempts += 1
        panic("temporary config failure")
    })
    return
}

func main() {
    var once, fresh sync.Once
    attempts := 0
    loaded := false
    if firstAttempt(&once, &attempts) != "temporary config failure" {
        panic("first call did not report the expected panic")
    }

    load := func() { loaded = true }
    once.Do(load)
    if attempts != 1 || loaded {
        panic("the original Once should not run load")
    }

    fresh.Do(load)
    if !loaded {
        panic("fresh Once should run load")
    }
}

First, check that the intended panic occurred. A missing invocation or unrelated panic should fail the fixture immediately. Then require both one attempt and a false loaded flag. This confirms the original function did run once, but the writer never ran on that instance. Finally, the fresh Once runs the same writer. The last check shows the writer is capable of changing the flag.

Simply recovering and calling Do again gives you a program that continues running. A test checking only for a lack of another panic would misclassify that as a successful retry. A service acceptance test can instead verify that an actual consumer reads the desired version before reporting readiness and that a failed initialization reports missing state. This fixture reasons about sequential calls and local variables. It does not test concurrent goroutines, production logs, or I/O recovery.

Decide what “once” means for your initializer

If a service permits one attempt, retain either the loaded value or the failure and expose that result after Do. A process that needs static configuration before accepting requests can stay unready and let the deployment controller decide whether to restart it. Do can manage the single function call while the application reads the actual readiness state. A request path should not announce that config is readable just because Do returned.

If you need to reload in the same process after a temporary failure, use a state model that supports retries. Decide who makes the next attempt, how concurrent callers wait, which version becomes visible after success, and when to report a persistent failure. An acceptance test should start with a failed read and a recorded error, then make the file available and verify that a consumer reads the new version and that the observable success count follows the retry contract. Creating a fresh Once for each request simply discards the shared boundary between them.

Logs can distinguish tried from ready. Record start and result in the actual loader. At the caller, record the recovered failure and any readable version separately. The distinction remains useful if a process has several unrelated initializers. If a log shows one function entry, one load failure, and many Do returns, inspect how the application interprets those events. The site's article about stopping a Go AfterFunc covers another distinction between an API result and completed work. Here the state is that of a single initialization.

What if the initializer calls Do on the same Once?

The call deadlocks. The original Do waits for its function to finish; the nested call also waits for that same execution. Imagine a loader that calls the outer initialization API to read a default, inadvertently reaching the same Once instance. Panic recovery cannot resolve that wait. Keep the routine that reads config beneath the boundary that coordinates initialization, so the loader cannot re-enter its own guard. The fixture does not execute this case. Inspect the call chain and the identity of each Once to diagnose it.
