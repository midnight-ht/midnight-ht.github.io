Why remove aria-sort from the old header after changing columns?

Sort a table by name and count, then check the row order, active direction, and previous header after switching columns.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-18 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • Put the current order on the active header
  • Clear the old header when changing columns
  • Verify row order and header state independently

A stock table starts sorted by product name. The user activates Count and the rows move. The old Product header still says it is sorted ascending. A new arrow or first row can hide that stale state in a visual review. In a table with one active sort column, the rows, visual indicator, and header state should follow the same decision.

Let the button act and the header describe the result

A column header names the column. A button inside it provides one trigger for keyboard or pointer users. Put aria-sort on the header associated with the current order. The sort direction describes the column's state, rather than a toggle value on the button.

WAI-ARIA 1.2 defines direction and other sort values and recommends applying the property to only one header at a time in a table or grid. The W3C sortable-table example removes it from the previous header when the active column changes. A column can offer a sorting button without currently controlling the order.

Clear the old triangle when Count becomes active. A triangle can serve as a visual hint. In this example it is decorative and hidden from the button's accessible name, which stays the same as the column name.

The attribute does not move any rows. Apply the ordering rule and show the resulting column and direction. Changing only the attribute or only the rows produces contradictory evidence.

Use rows that expose the column change

The fixture starts with A, B, and C, with counts of nine, two, and five. Product order is initially A, B, C. Count order interleaves those rows differently. If both columns happened to produce the same order, a row-only check could pass without the sorting code ever running.

<!doctype html>
<meta charset="utf-8">
<title>Sortable stock table</title>
<table id="stock">
  <caption>Stock. Select a column button to sort.</caption>
  <thead><tr>
    <th scope="col" aria-sort="ascending">
      <button type="button">Product <span aria-hidden="true">▲</span></button>
    </th>
    <th scope="col">
      <button type="button">Count <span aria-hidden="true"></span></button>
    </th>
  </tr></thead>
  <tbody>
    <tr><td>A</td><td>9</td></tr>
    <tr><td>B</td><td>2</td></tr>
    <tr><td>C</td><td>5</td></tr>
  </tbody>
</table>
<script>
const table = document.getElementById('stock');
const headers = Array.from(table.tHead.rows[0].cells);
const [body] = table.tBodies;

function sortRows(header, column) {
  const ascending = header.getAttribute('aria-sort') !== 'ascending';
  const read = row => row.cells[column].textContent;
  const rows = Array.from(body.rows);
  rows.sort((a, b) => {
    const order = column === 0
      ? read(a).localeCompare(read(b), 'en')
      : Number(read(a)) - Number(read(b));
    return ascending ? order : -order;
  });
  for (const row of rows) body.append(row);
  for (const cell of headers) {
    cell.removeAttribute('aria-sort');
    const indicator = cell.querySelector('span');
    const arrow = ascending ? '▲' : '▼';
    indicator.textContent = cell === header ? arrow : '';
  }
  header.setAttribute('aria-sort', ascending ? 'ascending' : 'descending');
}

headers.forEach((header, index) => {
  header.querySelector('button').onclick = () => sortRows(header, index);
});
</script>

Activate Count once. Expect B, C, A, with ascending on Count and no sort attribute or triangle on Product. Activate Count again and expect A, C, B with descending on the same header. Activating Product afterward should return to ascending order on the new column. These are fixed sample rows.

Those are expectations from the code. No browser or assistive technology was exercised for this article. In the real interface, reach and activate the button with the keyboard, then verify the order, header attribute, and visible indicator. Observe actual presentation separately using the product's supported combinations.

Check focus too. This example moves existing rows without rebuilding the header buttons. A real application may replace the whole table and lose the user's place. Even if its sort state is correct, verify that a keyboard user can still operate the header.

Update the rows and sort state together

In a table with a remote data source, activating a button only starts a request. Keep the existing sort state while showing that the new result is pending, then update rows, column, and direction together. Otherwise the interface can describe an order the reader can't see yet.

A user may pick another column before the first result arrives. Apply the result associated with the current choice. An older name-sort result that arrives last should not switch a table back from count order. This fixture uses synchronous updates, so test out-of-order results separately in a real client.

Record the row IDs, active header, direction, visible indicator, and focus before and after switching columns. A single “sorted” flag cannot show which of those changed. Confirm the new attribute appears and the previous one is gone.

Define the sort scope if the results are paginated. Sorting all inventory before selecting a page and sorting only the three loaded rows can produce different answers. Both can use header state, but a test for whole-inventory order needs rows whose positions change across a page boundary.

A restore-default action also needs an explicit outcome. If it restores product order, restore the corresponding header state and indicator. If the intended default has no active sort, leave no direction behind. The header buttons can remain available.

What about count followed by a name tiebreaker?

Two aria-sort attributes aren't a way to encode sort priority. Keep one indication on the primary header and explain the secondary rule in nearby text, for example “Count ascending, then product ascending when counts match.” A person can then determine the primary order and why tied rows appear in a particular sequence.

Add two products with the same count and different names to that test. The original three counts never invoke the tiebreaker. Verify their relative order, the explanation, and the same single active state.
