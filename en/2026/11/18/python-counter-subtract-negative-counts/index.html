Why did the shortage disappear from Counter subtraction?

Compare two inventory calculations to see which Counter operation preserves signed balances, explicit zeros, and the original snapshot.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-18 · Estimated read 13 min

Article

Key takeaways

  • Compute a signed balance on a snapshot copy to retain shortages.
  • Use binary subtraction when the view needs positive availability alone.
  • Use a membership assertion to verify an explicit zero row survives.

The warehouse has two apples and three reservations for them. You subtract two Counter objects and send the result to purchasing, but apples are missing. The arithmetic came out as expected. Binary subtraction filters zero and negative results out of the output. That gives you a positive availability view. Purchasing needs the signed balance.

Two teams need different answers from the same stocktake

Start with a single inventory and reservation snapshot. Apples have two in stock and three reserved. Pears have one in stock and one reserved. Lemons have four in stock and none reserved. Those three items cover the distinct outcomes. Apples are one short, pears are exactly used up, and four lemons remain. Purchasing needs to distinguish apples from pears. A storefront may only need to know it can still promise four lemons. The two views answer different questions about identical inputs.

Binary subtraction computes the difference for each key and keeps positive results, so both apples and pears disappear. The subtract() method mutates its receiver and allows zero and negative counts in the result. You can pass another counter to the method. Here the reservations themselves are all nonnegative integers. The negative value comes from insufficient stock. Copy the snapshot before updating it so the availability calculation can still use the original stocktake.

Explicit zero can carry meaning of its own. A warehouse operator auditing known but empty shelves still needs the pear row. If zero represents a valid condition, retain that row until the relevant view has applied its filter. A key never entered in the inventory can also read as zero. Reading the number alone does not distinguish the two cases.

Replay the same snapshot through two separate calculations

Each count is a number of pieces. Both calculations start from the same stock and reservation data. The signed calculation changes a copy, then the other calculation starts from the original snapshot.

from collections import Counter

stock = Counter(apple=2, pear=1, lemon=4)
reserved = Counter(apple=3, pear=1)
ledger = stock.copy()
ledger.subtract(reserved)
available = stock - reserved

assert dict(ledger) == {"apple": -1, "pear": 0, "lemon": 4}
assert dict(available) == {"lemon": 4}
assert dict(stock) == {"apple": 2, "pear": 1, "lemon": 4}
assert "pear" in ledger and "pear" not in available
print("ledger:", dict(ledger))
print("available:", dict(available))

Look first at what the assertions require of the keys. The ledger must contain apples and pears at negative one and zero. Only lemons remain in the availability result. The original stock still has two apples, one pear, and four lemons. If you call subtract() directly on stock and then subtract reservations again, the second operation starts from a snapshot that has already been debited. The lemons can still look right. The assertion on the input exposes the mutation.

Use a plain dictionary comparison or a membership assertion if the pear row must be explicit. Since Python 3.10, Counter equality treats missing counts as zero. An assertion comparing two Counter objects can pass even if an explicit zero row disappears. Looking up apples in the availability result also gives the default zero, which cannot tell you that purchasing was short one. Make this distinction before serialization if the consumer decides which rows to show from key presence.

Consider a handoff failure. The purchasing service reads the availability view and fills all missing keys with zero. It now reads both apples and pears as having no outstanding shortage. A signed interface can set an explicit acceptance rule: the purchasing file must show apples with a balance of negative one, while pears can remain visible only in the warehouse audit. Run the incorrect pipeline as a control. A purchase request derived from availability will contain no apples. That test catches a report wired to the wrong upstream view, even if both arithmetic operations are implemented correctly.

Choose what the view preserves before filtering it

Suppose you store a signed balance at the end of each day. Keep nonpositive values in that record and derive separate shortage and availability views as needed. Store which stocktake and reservation batch went into the calculation. A correct calculation that subtracts all of today's reservations from yesterday's inventory can still report the wrong shortage. The fixture checks keys and counts from one input. It covers no calendar cutoff, concurrent reservation, returned order, or database transaction.

Binary subtraction suffices for a storefront calculation that only needs positive stock. If the same computation also feeds reconciliation, call that result available stock and store a signed balance separately. Keep the reports from sharing a counter that a later step can still mutate. The computed values can travel with their input version instead. For testing, keep all three outcomes in one fixture. A fixture built entirely from positive balances cannot distinguish the two operations.

A reservation may also introduce a SKU absent from the stocktake. Decide whether that means zero stock, a bad catalogue mapping, or a receipt still waiting to be recorded. You can compute a number in all three cases, but sales and purchasing need to know which workflow should see the row. This example starts with three known SKUs and leaves the meaning of other missing keys to the application. The site's article about preserving multiplicity when order does not matter makes a similar point about choosing what a test must retain, in that case the number of times each record appears.

Can elements() expand a purchase order into individual units?

Pass it the signed balance and apples will be absent. The method repeats each element by its count, skips counts below one, and emits four lemons here. That represents the positive side of the ledger. To create individual shopping units, select deficit rows and invert their counts first, giving one apple in this case. This is a new choice about converting a quantity into individual records. If the purchasing system can accept a SKU and quantity together, keeping one quantity-bearing row makes the source batch easier to trace.
