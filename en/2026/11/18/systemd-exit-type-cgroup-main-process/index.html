Why can a systemd service still run after its main process exits?

Compare the main and cgroup lifetime rules in systemd using the same parent and child processes, then verify application delivery separately.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-18 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • Main mode observes the designated main process.
  • Cgroup mode tracks remaining group members.
  • Verify application output independently.

The main process can exit while systemd still considers the service running. With ExitType=cgroup, the manager watches for remaining processes in the service's control group. The default, ExitType=main, ties the end of the service to the main process. Check this setting when the main PID and the service state seem to tell different stories.

A delivery wrapper might start a child and return quickly. A monitor marks the job complete after seeing the wrapper exit. When the next task tries to move the output directory, the child may still be writing. Another deployment treats the wrapper's exit as the end of the service and cleans up the other processes. The same process tree can support different lifetime contracts. Use a fixture without application writes to identify what the manager observes first.

Give both services the same process tree

Use a disposable Linux machine with systemd 250 or later. Create worker.sh under /run/zy18-exit-lab/. The parent starts a child, waits three seconds, writes a return marker, and exits successfully. A child that can keep running eventually writes a completion marker. Use the first marker to locate the observation window and the second to check independent progress.

(
  sleep 18
  printf 'zy18-child-complete\n'
) &
printf 'zy18-child-start pid=%s\n' "$!"
sleep 3
printf 'zy18-main-returning\n'
exit 0

Save the following as /etc/systemd/system/zy18-exit-main.service. Copy the definition to zy18-exit-group.service and change only ExitType=main to ExitType=cgroup. Both use Type=exec and the same cleanup settings.

[Service]
Type=exec
ExitType=main
KillMode=control-group
ExecStart=/bin/sh /run/zy18-exit-lab/worker.sh

Start them from a privileged test shell and capture the properties and logs for both. The sleeps provide a sample window only. If machine load or marker times show the observations happened in a different phase, confirm the phase in the current run's logs and repeat. A still-running parent cannot serve as evidence for the post-exit interval.

systemctl daemon-reload
systemctl start zy18-exit-main.service zy18-exit-group.service
sleep 7
systemctl show zy18-exit-main.service zy18-exit-group.service \
  -p Id -p MainPID -p ActiveState -p ControlGroup
sleep 14
for unit in zy18-exit-main.service zy18-exit-group.service; do
  systemctl show "$unit" -p ActiveState
  journalctl -b -u "$unit" --no-pager
done

After the parent exits successfully and before the child would finish, expect the main unit to have stopped. Its remaining processes are cleaned up as configured. Expect the cgroup unit to stay active without a living main process. Correlate the logged child PID with the service's control group to identify the same attempt, then check the completion marker for the child's last action. After the remaining child exits, expect the cgroup unit to stop too. These outcomes follow from the documented rule and the unit definitions. No Linux service manager run was performed. Remove the fixture units and files from the disposable machine afterward.

Interpret an active service before handing it off

For a service with a stable supervisor, the supervisor's exit is often the event the operator needs to handle. The default can fit that model. If the application lacks a reliable main process and several processes together represent ongoing work, the cgroup model includes the lifetime of those processes. Give remaining processes a known role first. An accidentally retained debug process can also keep the group alive. The active state does not establish that the application is still producing expected output.

Put manager state and application milestones on one timeline. Preserve the current start identity, parent exit, child marker, and the relevant state. Limit logs to this run so an earlier completion cannot satisfy it. When a unit is active after its output stopped changing, identify the remaining group member. When the unit is inactive but the output is incomplete, investigate child cleanup and the application's recovery boundary.

There is another independent control. Suppose an export must write ten shards and the manager eventually sees every process in the group exit. The group lifetime has ended. A child could still have returned after five shards, and the manager's end state does not identify which files are missing. Provide an expected list and verify shard identities and contents before accepting the export. Inspect the application's exit reason where needed. This business example was not run. The service fixture has only the two process markers.

Define the operational handoff event when changing the exit model. A cleanup tool that only needs to know whether a process still holds the output directory can check service stop plus group membership. Moving a finished archive calls for its own completeness check. Both consumers observe the same service. The separate parent-return and child-completion markers help identify which event each consumer depends on.

On a machine using unified cgroup v2, read /proc/PID/cgroup for the child PID logged at the start. Record the time and compare the unified hierarchy path with the unit’s ControlGroup property. A process that already exited cannot supply that reading. A reused PID is not evidence that the original child survived. Leave enough time to observe the child and retain the log interval for the current attempt. This membership check was not executed.

Can a Type=oneshot service use ExitType=cgroup?

No. The manual excludes this combination. If a unit is oneshot today and the work after its main script returns needs an ongoing process-group lifetime, choose a type that models those continuing processes. Verify its start, completion, and stop separately. Both main examples use Type=exec and do not exercise oneshot. Launching untracked background work simply to let the next task start earlier would leave its lifetime undefined.
