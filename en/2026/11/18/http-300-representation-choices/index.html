Does HTTP 300 make a client jump to one URL?

Compare web and print alternatives to see how HTTP 300 offers representations, indicates a preference, and supports a client’s choice.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-18 · Estimated read 11 min
Translations
zh-CN en

Article

Key takeaways

  • 300 offers information about alternatives
  • Check a preferred target and the candidate list separately
  • Automatic selection requires an understood format

An installation guide has a web edition and a print edition. The client requests the general URL and receives HTTP 300 with two candidates. Its redirect code looks for a single destination and reports a failure when there isn't one. The response offers a choice. The user, or a client that understands the list, can select the appropriate representation.

Give each representation a specific identifier

RFC 9110 uses 300 where the target resource has multiple representations, each with a more specific identifier. The response supplies information about alternatives so the recipient can choose. Unlike proactive negotiation, in which the server selects based on request preferences, the recipient can make the choice after seeing the available representations.

A documentation team can offer a web page for on-screen reading and a paginated PDF for printing. Both versions help users install the same product. The general endpoint can present them together, and the action the user is trying to complete determines which one to read next.

If the server has a preferred choice, the RFC recommends giving its reference in Location. The client may use it for automatic redirection. An endpoint with no preferred choice can omit the field. Missing Location in this example doesn't invalidate a list with two available representations.

For the GET in this example, the standard recommends content containing representation metadata and references. It defines no universal machine format for that list. A client that recognizes 300 still needs to understand the media type and endpoint contract. A human-readable choice page isn't automatically input for a JSON-only parser.

Test each choice from a fixed list

The local fixture assumes an agreed response structure. Each candidate has a label, a media type, and a relative reference. The function looks for a known type in that fixture. It sends no HTTP request, verifies no headers, and makes no claim about automatic browser selection.

import {deepEqual} from 'node:assert/strict';

const choices = [
  {label: 'Read online', type: 'text/html', uri: '/guides/setup/web'},
  {label: 'Print', type: 'application/pdf', uri: '/guides/setup/print'},
];
const response = {status: 300, choices};

function choose(reply, type) {
  if (reply.status !== 300) return null;
  return reply.choices.find(choice => choice.type === type)?.uri ?? null;
}

const inputs = [
  ['application/pdf', '/guides/setup/print'],
  ['text/html', '/guides/setup/web'],
  ['text/plain', null],
];
for (const [type, expected] of inputs) deepEqual(choose(response, type), expected);
console.log('Both known choices and the missing choice passed.');

All three assertions passed locally. Selecting PDF returns the print path. Selecting HTML returns the web path. Asking for plain text returns null. These are results of looking up an item in the fixture. It does not retrieve a second representation.

If the client actually follows a choice, test that request separately. A print action should select the print reference, and the retrieved content should fit the endpoint's promised type and behavior. The initial 300 establishes which choices were offered, not whether the next request succeeded.

Keep the missing choice test. The interface can show available formats when the requested one is absent. Silently selecting the first entry might send a reading tool a format it cannot use. Assert what happens when the requested type is unavailable.

Keep the selection evidence

Expose information a person or client can use to choose, rather than a bare address. The user can read “Print.” A client can check the documented type and identifier. If the product uses a priority rule, record it rather than relying on the order the list happens to appear in.

If the server introduces a preferred choice, test both the presence and absence of that preference. Verify the preferred address refers to a current representation. Also verify a client can choose from the list without it. Fetching the default alone leaves the alternatives unchecked.

For a reported failure, capture the first response, the client's selection, and the result of the subsequent read. That lets you determine whether the list was missing, the client couldn't parse it, or the chosen version was unavailable.

Test a stale list as well. The print service may have moved to a new version while the general endpoint still advertises the old address. The client can select correctly while the publishing process is wrong. Record the catalog version used to generate the list and verify each advertised reference separately.

Should HEAD include the choices in its response body?

No. This changes the request method. A HEAD response has no content, and the list-content recommendation for 300 explicitly excludes HEAD. An empty body does not establish that only a single representation exists or that the print edition is absent.

For a client that needs the list, use a retrieval contract that supplies it, such as the endpoint's documented GET. Track the metadata that HEAD can verify separately. The fixture tests only a local list and does not implement either method.

For the effect of redirects on request methods, see the HTTP redirect method contract.
