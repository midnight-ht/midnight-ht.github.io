Why can a newly inserted notice appear without fading in?

Insert two notices with the same ordinary opacity. Compare entry starting styles and verify that the feedback stays visible with reduced motion.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-18 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • A newly inserted node may lack a before-change style
  • Starting rules participate in the normal cascade
  • Check the transition and the final feedback separately

A button inserts a new notice. The stylesheet defines an opacity transition, but the notice appears fully visible. The new node's first render has no previous style for the transition to use. An entry effect needs a starting value for this case.

What the first render lacks

A transition compares before-change and after-change styles. A notice that's already rendered at zero opacity can use that previous value when its style changes to one. A notice inserted in the current style change has no rendered state from the previous one.

CSS Transitions Level 2 supplies @starting-style for that case. When there is no before-change style, use the after-change style with the applicable starting rules to establish a comparison value. This example supplies zero opacity. The ordinary final opacity is still one. A later change can use the actual previous style when it exists.

Starting rules participate in the normal cascade. The grouping rule doesn't automatically outrank a declaration outside it. Selector weight and order can matter. Check whether the applicable style really gives the notice an initial opacity of zero.

Increasing the duration cannot create a missing previous value. Check that the property can transition and that the two values differ. If both end up at one, the notice has no visible opacity change to make.

Insert both notices and change only the starting rule

The local HTML page creates two paragraphs on each click and inserts them into the same container. Their ordinary opacity and duration are equal. Only the second can match the starting rule for zero opacity. Both listeners are attached before insertion.

<!doctype html>
<meta charset="utf-8">
<title>Notice entry comparison</title>
<style>
  .notice { opacity: 1; transition: opacity 600ms; }
  @starting-style {
    .entry { opacity: 0; }
  }
  @media (prefers-reduced-motion: reduce) {
    .notice { transition: none; }
  }
</style>
<button id="show" type="button">Insert notices</button>
<div id="notices"></div>
<pre id="output"></pre>
<script>
const byId = document.getElementById.bind(document);
const notices = byId('notices');
const output = byId('output');

function makeNotice(label, className) {
  const el = document.createElement('p');
  el.className = className;
  el.textContent = label;
  el.addEventListener('transitionend', event => {
    if (event.propertyName === 'opacity') output.append(label, ' ended\n');
  });
  return el;
}

byId('show').onclick = () => {
  output.replaceChildren();
  const plain = makeNotice('Ordinary notice', 'notice');
  const entry = makeNotice('Notice with starting style', 'notice entry');
  notices.replaceChildren(plain, entry);
};
</script>

In a supporting environment without reduced motion enabled, expect the first notice to appear directly in its final state. The second can fade in and log an opacity transition completion. Both should be visible at the end. Avoid assigning a particular screenshot moment to a fixed animation frame.

These are expectations from the standard and code. No browser trace was collected. If the log is missing, check whether the environment supports the rule, whether motion was disabled, and whether the node survived long enough to finish. Another click creates new paragraphs and can interrupt the previous effect. Wait for the first trial when checking completion.

A final-visibility assertion alone passes both branches. A transition event assertion alone could treat reduced motion as a failure. Keep access to the notice separate from the motion check.

Fit the rule into the actual feedback path

In the product, follow the action that creates the notice. Establish whether it inserts a new node or merely updates a node that was already rendered. Record whether the node was created, which styles matched, and whether it reached the visible state. That evidence tells you whether a starting style is relevant.

Keep a path that shows the final message without motion. Don't delay the notice text until the transition callback. A person who reduces motion still needs the save or failure feedback. The example disables transitions in that case but keeps the ordinary visible styles.

Check the cascade again when moving the rule into real component styles. If the standalone example works but the product doesn't, look at which component, utility, and theme rules apply. This comparison only describes an entry transition on opacity.

Track how often each notice is created in the real interface. Replacing the node during a list refresh can replay the entry effect even when its starting style is correct. Retain a stable notification identity and distinguish first appearance from a text update in the log. If two successive actions reuse the same notice, test that behavior separately from creating a new node for each action.

Does removing the notice automatically play the reverse effect?

No. Direct removal is a different operation. A starting style provides a value for an entry that has no prior style. It does not keep a deleted node rendered or generate a reverse endpoint. To fade out, keep the notice in the document while applying its exit style, then remove it according to the component's completion or cancellation policy.

A separate exit test can check that the notice exists, begin dismissal, and verify it is removed afterward. Check the motion-disabled path too. The node should not stay indefinitely because a completion event did not fire.

For how reduced motion can retain feedback, see preserving state information while reducing motion.
