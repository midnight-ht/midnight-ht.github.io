Why does EJECT return an int for an unknown flag bit?

Compare four FlagBoundary policies on the same integer. Check the retained bits and the type each constructor returns.

Article

Key takeaways

  • EJECT returns a plain integer for an out-of-range value
  • KEEP preserves both bits and flag membership
  • Choose a policy for the actual consumer and its round trip

An older reader knows two settings, preview and captions. A new version defines another bit, and the number received by the old reader is nine. The caller expects an enum with a value attribute but gets an int. This constructor uses EJECT. An unknown bit makes it return the original number as a plain integer.

The number can survive a change in type

Preview is one and captions is two. Nine contains the known preview bit and an unknown bit worth eight. The old definition identifies the preview setting but cannot interpret that other bit. The interface has to decide whether to refuse the value, drop the unknown part, or preserve it for a receiver that knows more.

Python 3.11 added FlagBoundary to control how Flag and its subclasses handle out-of-range values. STRICT raises ValueError. CONFORM removes the unknown bit and returns a flag with value one here. One branch explicitly refuses the input. The other continues with what it understands.

EJECT preserves the number nine and loses flag membership. KEEP preserves both. A number in a log can look the same for either policy. The difference matters to code that needs a flag attribute or needs to pass the result to another enum-aware function.

Check the same two inputs against all four policies

The local script creates four enum classes with identical members. It changes only the boundary policy. Each class gets the known value one and then nine. The output distinguishes rejection, a plain integer, and a flag. The reader and its data exchange are hypothetical.

from enum import Flag, STRICT, CONFORM, EJECT, KEEP

members = {"PREVIEW": 1, "CAPTIONS": 2}
policies = (STRICT, CONFORM, EJECT, KEEP)
classes = [Flag(policy.name, members, boundary=policy) for policy in policies]

def inspect(flag, number):
    try:
        result = flag(number)
    except ValueError:
        return ("rejected", None)
    if type(result) is int:
        return ("int", result)
    return ("flag", result.value)

assert [inspect(flag, 1) for flag in classes] == [("flag", 1)] * 4
expected = [("rejected", None), ("flag", 1), ("int", 9), ("flag", 9)]
actual = [inspect(flag, 9) for flag in classes]
assert actual == expected
for policy, result in zip(policies, actual):
    print(policy.name, *result)

The exact script passed in local CPython 3.14. All four policies accept one as a flag. For nine, STRICT rejects, CONFORM returns a flag of value one, EJECT returns the plain integer nine, and KEEP returns a flag of value nine. The script checks for exactly int before trying to read value.

Send the real numeric input to the constructor in a regression. If a test reduces nine to one up front, every policy can pass. Record what entered the constructor and inspect the type and number it returned.

Choose a policy for the boundary's job

A display-only path can deliberately discard an unfamiliar bit if it only needs to decide whether to show preview. Record the original and interpreted values. The pair explains why a value of nine took the same display path as one.

Writing the value back carries another responsibility. Suppose the user changes only preview and the new bit must survive. An edit based on an already-trimmed value can lose eight along with the preview setting. Document which bits the older client owns and check the returned value in the newer reader.

Keeping a bit does not assign it a local meaning. A path that needs to understand the whole setting can refuse it and ask for a compatible client. A forwarding path can preserve the integer for another component. Decide based on the consumer's job.

Keep the enum definition version, policy, original value, and return type in diagnostic evidence. Printing nine alone cannot reveal whether KEEP produced a flag or EJECT produced an integer. That missing distinction makes an attribute error harder to explain.

Once the newer definition names the bit worth eight, nine can be an ordinary known combination for it. Test both definitions rather than using the newer constructor to stand in for the older reader. They have different information.

The same value can pass through more than one boundary. A view can derive its own known options from the original value while a save path still needs the original bits. Give these values different fields in the application and test the save independently of the display.

When several modules share the definition, add a known combination to the application regression. A test for one alone would not detect a missing captions bit. The value three checks both known capabilities together, while nine checks the unknown bit. The published script uses only one as its positive control.

What happens if you omit boundary and switch from Flag to IntFlag?

The default changes with the base class. Flag defaults to STRICT and rejects nine with this older definition. IntFlag defaults to KEEP and preserves the unknown bit and enum membership. It also inherits from int, so a broad integer instance check can succeed on both an IntFlag and EJECT's plain return value. Check the exact type or membership in the intended enum, as appropriate.

Every class in the main example specifies its policy. Omitting it makes the choice of base class determine the behavior. During migration, verify both the retained bits and the type received downstream. Printing the value nine verifies neither distinction by itself.
