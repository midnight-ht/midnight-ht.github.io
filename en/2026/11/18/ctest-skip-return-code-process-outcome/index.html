Why did CTest show a skip after the test process exited nonzero?

Use three isolated process outcomes to distinguish passed, skipped, and failed CTest runs and verify required coverage.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-18 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • The test process and CTest have separate exit values.
  • A green summary may contain skipped tests.
  • Check the outcome of each required test by name.

A test process can exit nonzero and CTest can still record it as skipped. With SKIP_RETURN_CODE set on a test, a normal process exit with the designated value is classified as Not Run. Launching the command and completing the intended verification are separate outcomes. Read the classification for the specific test before deciding what the pipeline covered.

This comes up in matrices that include optional capabilities. A basic build might lack a simulator. Its test starts, looks for the prerequisite, and exits without a behavior check. A full job is supposed to verify the interaction in the simulator. Green statuses beside both jobs do not show that both ran the same assertion. Let the test process identify the branch it took, then have CTest preserve the result.

Record the process outcome and the runner's outcome

Create an empty directory and save this as CMakeLists.txt. The project needs no compiler, but the local Unix-like system needs sh. Its three test processes exit zero, one, and seventy-seven. Only optional declares the skip code. The value is a fixture convention. A real suite should reserve a value that cannot collide with its ordinary failures.

cmake_minimum_required(VERSION 3.20)
project(SkipFixture NONE)
enable_testing()
find_program(SHELL_PROGRAM NAMES sh REQUIRED)

add_test(NAME available COMMAND "${SHELL_PROGRAM}" -c "exit 0")
add_test(NAME broken COMMAND "${SHELL_PROGRAM}" -c "exit 1")
add_test(NAME optional COMMAND "${SHELL_PROGRAM}" -c "exit 77")
set_tests_properties(optional PROPERTIES SKIP_RETURN_CODE 77)

Run the following from that directory. It captures CTest's output and status for each test. The process statuses are fixed in the configuration. The second argument to the helper is the runner's expected exit value. Executing each test independently associates every outer status with a single test outcome.

set -eu
work=$(mktemp -d)
trap 'rm -r "$work"' EXIT
ctest --version
cmake -S . -B "$work/build"

probe() {
  status=0
  ctest --test-dir "$work/build" -R "^$1$" --output-on-failure || status=$?
  printf 'case=%s ctest_exit=%s\n' "$1" "$status"
  test "$status" -eq "$2"
}
probe available 0
probe optional 0
probe broken 8

On CTest 4.2.3, available was Passed and CTest exited zero. Optional was Skipped and appeared among tests that did not run, while CTest still exited zero. Broken was Failed and the runner exited eight. Eight is the observed status for this invocation, not the exit value of the test process or a promise about all versions. The configuration makes broken's process exit one. Each number describes a different layer.

Look closely at optional. Its summary also reported 100%, then printed The following tests did not run and named optional. This test did not verify the intended behavior. It demonstrated a process reporting an unavailable prerequisite. A collector that only reads the percentage and exit status can mistake it for a pass. Exercise the collector against both cases, then use broken to verify that a real failure still stops the workflow.

The manual also sets two boundaries. A test that exceeds TIMEOUT still fails. System-level errors such as a segmentation fault or signal abort may fail despite a corresponding exit value. Reserve a normal process code to report a known missing prerequisite. A wrapper that reduces arbitrary errors to the skip value could hide a different problem. The fixture exercised normal exits and did not try a timeout or signal.

Decide which skips invalidate release acceptance

Start with the environment's contract. A basic job that omits a simulator can record a skip, but its handoff still needs the test name and reason. The same skip in a full job that promises simulator coverage means the run did not produce the required evidence. Check that the tool can start during setup and confirm the intended test actually ran afterward. A usable environment and a passing behavior test need their own evidence. Installing the simulator and then filtering out its test could otherwise leave a misleading green result.

Test the collection rule with a controlled fault. In a full job you could deliberately remove a dedicated prerequisite marker so one test returns seventy-seven. A collector that reads only exit status could still let it through. A classification assertion keyed by test name should flag the missing result. Restore the marker and environment and confirm the actual assertion runs and passes. This is a suggested collector exercise. The local run used the three small processes without running a real product or simulator.

Reserve the skip code for a clear prerequisite branch. A test that runs an assertion and then rewrites its failure to “simulator unavailable” loses the original fault. Check capability before the behavior test and report different outcomes for different errors. A review record can list which tests may skip in a basic job and which must pass in the full environment. When a new architecture joins the matrix, change the affected requirements and rerun a missing-capability control to check that test selection still works as intended.

Retain the expected test names when comparing jobs. Consider one test that may skip in a basic job but must pass in a full job. A green report containing only a different set of tests cannot satisfy the full job. Compare explicit test identities. If the expected result is absent, inspect the selection arguments and discovered tests before labeling it a skip. Once the identity and outcome are known, you can distinguish an unavailable prerequisite, an omitted test, and a genuine failure. This is a proposed pipeline check.

What if the test can only print a diagnostic?

Consider SKIP_REGULAR_EXPRESSION. A match on stdout or stderr can mark a test skipped. A timeout still fails and system-level errors can still fail. In a separate local fixture, a process printed the fixed text UNAVAILABLE: simulator and exited one. CTest classified it as Skipped and returned zero. The acceptance condition here is the diagnostic, so the same exit one may also indicate a genuine failure without the match. Use a narrow, stable marker that unrelated failures will not accidentally produce.
