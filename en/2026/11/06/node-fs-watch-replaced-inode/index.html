Why can fs.watch miss later writes after a file is replaced?

On Linux/macOS a file watch follows its resolved inode, not a replacement at the same path. An owned temporary fixture separates callbacks from directory reconciliation and missing-filename recovery.

Key takeaways

  • The same path does not make the original watch follow a new inode.
  • A missing callback filename still needs scoped reconciliation or another fallback.
  • Reconciling current state differs from retaining every intermediate update.

An unchanged path does not mean fs.watch is following the replacement file now at that path. Node.js documents that on Linux and macOS a watch follows the inode resolved from the path. Deleting and recreating the file gives it another inode; the original watch does not automatically receive events for that new inode.

This explains a stalled configuration reload when an editor writes a temporary file and renames it over the target instead of updating the old file in place. The replacement can produce a signal, yet later writes to the new file no longer reach the original file watch. Comparing path strings does not expose the identity change.

The inode clause was checked in documentation titled Node.js v24.22.2 when retrieved. That version-line URL can change, so the title and body are preserved in the source snapshot. This is not a claim that the program below was tested in that runtime. Nor does the documented behavior establish an unconditional guarantee for every platform or filesystem.

Separate the path from the watched object

A path locates an object. When the watch is established, the system resolves it and watches the corresponding file. A different file subsequently occupying that name does not automatically inherit the subscription. The documentation says the original inode watch emits a deletion event but continues watching the original inode; events for the new inode are not emitted by that old file watch.

Receiving a rename or deletion hint therefore does not establish that the subscription follows the replacement. A callback might reread the new file successfully while leaving the old watch installed. Current content can look correct once, then the next update loses its signal. One successful reread does not establish future subscription recovery.

Observe an owned temporary directory

This unexecuted ESM program creates its own temporary directory. It logs callbacks from both the file and its parent directory, separating replacement from the subsequent write. Manual Enter prompts allow observation, but are not barriers proving that the operating system has delivered every event. There is no fabricated fixed event count or transcript.

import { watch } from 'node:fs';
import { mkdtemp, writeFile, rename, rm } from 'node:fs/promises';
import { tmpdir } from 'node:os';
import { join } from 'node:path';
import { createInterface } from 'node:readline/promises';
import { stdin, stdout } from 'node:process';

const dir = await mkdtemp(join(tmpdir(), 'watch-inode-'));
const file = join(dir, 'config.json');
const next = join(dir, 'next.json');
const rl = createInterface({ input: stdin, output: stdout });
const watchers = [];
const log = label => (eventType, filename) =>
  console.log(label, { eventType, filename });
try {
  await writeFile(file, '{"version":1}\n');
  const fileWatch = watch(file, log('file'));
  watchers.push(fileWatch);
  const directoryWatch = watch(dir, log('directory'));
  watchers.push(directoryWatch);
  for (const watcher of watchers)
    watcher.on('error', error => console.error('watch error', error));
  console.log({ dir, file });
  await rl.question('Press Enter to replace the file; observe callbacks afterwards. ');
  await writeFile(next, '{"version":2}\n');
  await rename(next, file);
  await rl.question('Press Enter after observing callbacks to write the replacement. ');
  await writeFile(file, '{"version":3}\n');
  await rl.question('Press Enter after observing callbacks to close and clean up. ');
} finally {
  for (const watcher of watchers) watcher.close();
  rl.close();
  await rm(dir, { recursive: true, force: true });
}

Save it as watch-inode.mjs and, in a prepared owned environment, run node watch-inode.mjs. The first Enter writes a temporary file and replaces the target. The second writes to the replacement, and the third closes the watches and removes only the newly created directory. Do not substitute an existing user directory for the printed path.

The question to investigate is whether the two watch scopes behave differently, not whether one run happens to produce a particular number of rename callbacks. Preserve raw callbacks and record the actual operating system, filesystem and Node version. Distinguish documented behavior from observations. Temporary-file activity can also trigger the parent watch; those messages do not establish that the target configuration is ready to adopt.

Reconcile current state after directory hints

For applications that need eventually to adopt the current configuration, a parent-directory event can mean “recheck state.” Schedule a coalesced rescan, reopen the current target path, read its complete content, validate its format and version, and only then decide whether to adopt it. Several hints can be coalesced. The goal is reconciling the current state, rather than interpreting each hint as a distinct business update.

That is an application design inference, not a promise that directory watches provide a reliable log. The program above only logs events; it is not a production reloader. A reread can encounter an absent file, incomplete content, changed permissions or parse failure. Keep the last known good configuration and record the retry or failure state explicitly.

For example, if version two is active and a later read contains invalid JSON, an arriving file event should not clear the running state. Adopt a candidate only after complete parsing and domain validation. Configuration versions belong to the configuration protocol; counting events cannot infer them, because repeated hints are not repeated business versions.

Reestablishing a file-level watch requires managing the old watch, creating the new one and reconciling changes during the interval. Calling watch again inside a callback does not, on its own, explain how that gap recovers. Review the complete reconciliation process rather than treating one subscription call as sufficient.

Can an event with a null filename be discarded?

Not for that reason. The official filename and watch caveats says the callback filename is not guaranteed, even on platforms supporting it. The application still knows the directory scope it watches and can fall back to rescanning instead of demanding a target name in every event.

The same caveats section describe platform and filesystem dependencies, including unreliable behavior on some network or virtualized filesystems.

A present filename is not content validation either. It can narrow the reconciliation scope, but proves neither existence nor completeness nor a new version. Returning immediately on a missing name can leave stale state; treating every name as a successful target update can misclassify temporary-file activity. Design both branches explicitly.

A controlled logic test can call the reconciliation function with a null filename and check that it schedules a scoped rescan. That proves the function branch, not that the operating system actually produced that callback. Preserve real callbacks unchanged and label deliberately injected logic-test inputs separately.

Require a different delivery contract for every update

If every intermediate update must be processed and traceable, hints followed by rereading the current file do not automatically meet that requirement. A newer version may already have replaced intermediate content.

Choose a versioned delivery channel, durable record or other coordination mechanism matching the requirement, then define recovery. Periodic state reconciliation can help eventual recovery but is not an archive of every intermediate version. Decide whether the goal is eventual current-state agreement or accounting for every change before assigning reliability guarantees to a convenient notification mechanism.

Rereading a path also has its own operation boundaries; see why access before open does not eliminate a file race. A prior existence check does not prove the next operation succeeds. Handle read failures, validate current content and review watch scope together with recovery to explain how the system continues after a same-path replacement.
