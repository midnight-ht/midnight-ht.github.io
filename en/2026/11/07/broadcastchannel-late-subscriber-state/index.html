Why does a newly opened tab miss an earlier BroadcastChannel message?

Explain late subscription and sender exclusion through the recipient-selection algorithm, then separate change notifications from the source of current state.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-07 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • Recipients are selected when a message is sent; later pages get no history replay.
  • The sending object is excluded, so its local update needs a direct path.
  • Define current-state reads separately from notifications, including the initialization window.

A tab opened after a BroadcastChannel message was sent does not need a reconnection option to recover that message. The channel selects eligible recipients at send time; it does not retain history for pages created later. A preferences feature needs a separate source of current state, with broadcasts prompting existing pages to check for changes.

Recipients are selected before delivery

The HTML Standard’s broadcasting algorithm checks whether the sender is eligible, serializes the value, and finds eligible channel objects with the matching name and storage key. It removes the sending object from that list before queuing delivery tasks. This account uses the specification snapshot last modified on 5 November 2026; it is not a browser compatibility result.

Suppose only tab A exists when it sends. There is no object belonging to tab B in the destination list. Creating B one second later does not add it to an already selected list. A subsequent send performs a new selection and can include B. Channel construction has no step that reads the last published message, so the name is not a retained-state topic.

Eligibility also means more than an open window. A window’s associated document must be fully active, and workers have their own closing and suspendability conditions. A destination closed after selection is skipped when its queued delivery task runs. A normal return from postMessage indicates that the call did not throw synchronously; it is not an acknowledgement that every other page has rendered a new value.

Separate late subscription from a delivery failure

The following unexecuted teaching page writes only to its visible log and broadcasts a synthetic version number. It performs no login, persistent write or remote request. Serve the same file from a trusted local HTTP origin and open it twice in the same browser. Do not use file-URL origin behavior as a substitute for ordinary site conditions.

<!doctype html>
<meta charset="utf-8">
<button id="send" type="button">Broadcast v2</button>
<pre id="log"></pre>
<script>
const out = document.querySelector('#log');
const channel = new BroadcastChannel('a-nov7-local-demo');
channel.onmessage = event => {
  out.textContent += JSON.stringify(event.data) + '\n';
};
document.querySelector('#send').onclick = () => {
  channel.postMessage({type: 'changed', version: 2});
  out.textContent += 'sent locally\n';
};
addEventListener('pagehide', () => channel.close());
</script>

Open A alone, press its button, and then open B. The independently specified expectation is that B’s log remains empty: joining a channel does not replay A’s earlier send. Once B has finished loading, press A’s button again. B can now receive the new object and display its type and version. The sending channel object in A does not receive its own message. A’s “sent locally” line comes from the click handler and is not evidence of a received message event.

This sequence distinguishes conditions that random clicking in two open tabs can obscure. If B receives nothing on the second send, check the actual origins, channel names, installation of listeners, object closure and supported environment separately. Record the order of loading, sending and receiving rather than retaining only a screenshot of the final logs. These are expectations derived from the algorithm; this article has not run the steps or collected browser output.

The page closes its channel on pagehide for the example. It does not rebuild a subscription when a document returns from a page cache. A product supporting navigation restoration must test object and listener recreation. The small fixture is not a complete lifecycle adapter, and initial operation does not establish correct behavior after returning to the page.

A change notification still needs a source of current state

Assume the preference starts as light. A changes it to dark, then B opens. If B initializes by creating a channel and waiting, it can remain on its default indefinitely. A more reviewable design reads the product’s defined current preference during initialization and reads again when notified. Version rules may be needed to stop an older read from replacing newer state.

That source could be existing controlled storage or a service, depending on whether the preference belongs to a tab, an account or a device. No real state endpoint is supplied here. Naming a read function would not demonstrate an implemented preference service. A design review still needs the access rules, failure behavior and version contract.

There is also a gap to handle around initialization. If a notification arrives during a read, the receiver can remember that another read is needed, or use a protocol that establishes whether the returned version covers the change. “Read, then subscribe” alone leaves a window between those actions. BroadcastChannel does not close that application-level race for the caller.

Treating the last received message as permanent state fails when all pages close and a new one opens. It also confuses delivery scope with business identity: another same-origin page can send a value of the same shape. The channel name neither authenticates the current account nor authorizes a preference change. Validate the message format and read from a state source whose access and lifetime are defined. Avoid distributing an entire personal record merely to announce that something changed.

A requirement to recover every event after reopening needs a durable event record, a consumer position and recovery behavior. None is provided by a broadcast channel. For more elaborate locking or resource coordination, the specification points toward arrangements such as shared workers; a “first broadcast wins” convention is not proof of exclusive write ownership. The existing article on per-tab session storage explains initial copying and later independence, which is a different mechanism from notification replay.

Should the sending tab wait for its own message event to update?

Do not depend on an echo to the same sending object: the algorithm excludes it. Apply the local state transition and UI update through the local path, then notify other channel objects. A separate eligible channel object created in the same page can still receive the message. The precise boundary is the sending object, rather than the entire sending page.

This distinction prevents opposite mistakes. Repeatedly rebroadcasting in order to update A adds traffic without creating a self-echo. Suppressing all messages in A using a page-wide flag can discard messages intended for its other legitimate objects. Record channel object identity in tests, not just tab names. Nor should an application infer a total order across all agents: the specification constrains only part of the creation ordering, leaving application version semantics necessary.

A useful acceptance record separates late joining, delivery to an installed subscriber, the sender’s local update, closure before delivery and navigation restoration. Browser and partition conditions that have not been exercised remain unverified. Establish that a new page can read the present state, then verify how a notification makes an existing page check again. Both results are needed to support a multi-tab preference promise.
