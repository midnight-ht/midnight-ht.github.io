Why can OpenSSL s_client complete a handshake despite certificate errors?

Separate OpenSSL handshake, trust, expected identity, and error handling with an explicitly unexecuted local fixture.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-07 · Estimated read 16 min
Translations
zh-CN en

Article

Key takeaways

  • Diagnostic continuation is not certificate acceptance.
  • SNI, trust material, and expected identity are distinct inputs.
  • A printed certificate list is not a verified chain.

OpenSSL s_client is a diagnostic client that can continue after certificate verification errors. An acceptance check needs explicit trust inputs, error handling, and the expected hostname; SNI and a printed certificate list do not replace them. Negotiation information alone is not a TLS identity acceptance result.

Continuing helps diagnosis, not acceptance

The OpenSSL 3.6 s_client manual explains that verification can continue after errors so chain problems remain visible. verify_return_error returns those errors and typically aborts the handshake with a fatal error. This is the versioned documentation namespace, not an observation of the reader's installed version. No server was contacted here.

A returned certificate and negotiated cipher show protocol activity. They do not establish that the chain reaches an accepted root or that the certificate represents the intended name. Define acceptance before selecting a successful-looking line from diagnostic output.

Separate connection address, SNI selection, trusted material, and expected identity. Connecting to a local IP while checking a DNS identity makes that distinction particularly visible. Similar values in ordinary commands do not merge their responsibilities.

A complete local teaching script

This script was not executed and generated no actual certificates or successful handshakes. It requires OpenSSL 3.6 commands, a conventional shell, and an unused local port. It creates one-day teaching material in a new directory without installing a system trust root. localhost avoids external DNS. Unencrypted keys are solely for this disposable example, not a production recommendation.

Save it as tls-demo.sh and invoke it with sh in an isolated practice environment. Preparation stops on failure. Probes permit expected failures and immediately capture each client result. Overall script termination does not mean all four probes passed.

set -e
tls_demo_dir=$(mktemp -d)
cd "$tls_demo_dir"
tls_endpoint=127.0.0.1:18443
tls_name=localhost
tls_root_cert=root.pem
tls_other_cert=other.pem
make_request() {
  tls_material=$1; tls_subject=$2
  shift 2
  openssl req -newkey rsa:2048 -noenc -keyout "$tls_material.key" \
    -subj "$tls_subject" "$@"
}
make_request root '/CN=Demo Root' -x509 -days 1 -out "$tls_root_cert" \
  -addext 'basicConstraints=critical,CA:TRUE' \
  -addext 'keyUsage=critical,keyCertSign,cRLSign'
make_request other '/CN=Other Root' -x509 -days 1 -out "$tls_other_cert" \
  -addext 'basicConstraints=critical,CA:TRUE'
make_request server '/CN=localhost' -new -out server.csr
printf '%s\n' 'subjectAltName=DNS:localhost' \
  'basicConstraints=CA:FALSE' 'extendedKeyUsage=serverAuth' > server.ext
openssl x509 -req -in server.csr -CA "$tls_root_cert" -CAkey root.key \
  -CAcreateserial -out server.pem -days 1 -extfile server.ext
openssl s_server -accept "$tls_endpoint" -cert server.pem \
  -key server.key -www > server.log 2>&1 &
tls_server_pid=$!
trap 'kill "$tls_server_pid" 2>/dev/null || true' EXIT
set +e
probe() {
  tls_case=$1; tls_trust=$2; tls_expected=$3
  shift 3
  printf 'GET / HTTP/1.0\r\nConnection: close\r\n\r\n' |
    openssl s_client -connect "$tls_endpoint" -servername "$tls_name" \
      -verifyCAfile "$tls_trust" -verify_hostname "$tls_expected" \
      -no-CAfile -no-CApath -no-CAstore -ign_eof "$@" \
      > "$tls_case.log" 2>&1
  tls_result=$?
  printf '%s status=%s\n' "$tls_case" "$tls_result"
}
probe diagnostic "$tls_other_cert" localhost
probe wrong_chain "$tls_other_cert" localhost -verify_return_error
probe wrong_name "$tls_root_cert" otherhost -verify_return_error
probe matched "$tls_root_cert" localhost -verify_return_error
printf 'inspect sandbox: %s\n' "$tls_demo_dir"

Preparation follows the official req, x509, and s_server interfaces. Creating a request, signing it, and listening do not replace client verification. The extension file explicitly puts localhost in the certificate SAN rather than assuming CSR extensions are automatically copied. Inspect the resulting certificate and confirm this server owns the chosen port before interpreting probes.

Background startup also creates a readiness race. If a probe first receives connection refusal, inspect server.log and process state, then retry after establishing this fixture's listener. That is not a chain-verification failure. The HTTP request and connection closure address noninteractive input handling; closing behavior must not be confused with identity acceptance.

Interpret four separate records

The diagnostic case uses material that does not trust the fixture's issuer but omits error-return enforcement. It demonstrates continued diagnostics, not acceptance. wrong_chain adds verification failure handling. wrong_name trusts the fixture root but changes the expected identity. Only matched supplies both the intended root and name.

These are predictions, not captured logs. Even a zero matched result needs the actual trust file, name, endpoint, and diagnostics associated with it. A nonzero result is not synonymous with certificate failure: expired inputs, a port conflict, or transport failure need their own classification.

The verification-options manual separately documents expected-hostname checking. Hold service, certificate, and trust constant while changing that name to isolate the identity comparison. Changing all inputs at once makes a failed result ambiguous.

Each record should name preparation completion, connection establishment, trust file, expected identity, verification diagnostics, and client status. Failed preparation means no probe; connection refusal means the transport prerequisite failed. Interpret a chain or name negative control only after establishing that the fixture certificate was received. Four nonzero statuses are not automatically four correct verification rejections.

Inspect issuer, validity, and SAN as actual inputs. Omitting the extension file can make the certificate differ from the written design; an expired one-day fixture can also invalidate the matched case despite the correct name. Preserve the material and errors rather than keeping only a convenient later attempt.

The GET request supplies a local connection-ending path. It does not establish a real website, browser policy, or every certificate-lifecycle requirement. Receiving teaching HTML is distinct from accepting identity under the recorded roots and expected name.

Can SNI and verify_hostname be different?

Yes, but explain the difference. SNI requests a virtual host; the expected name defines the identity being accepted. This fixture holds SNI at localhost while deliberately using another expected name in wrong_name, separating selection from acceptance.

Real proxies or dedicated access paths may have their own identity design. The example does not establish that every difference is correct. Record both inputs and their provenance rather than assuming that supplying SNI performed verification.

Does showcerts printing a list prove trust?

No. The manual says it displays the server-sent certificate list in its sent order, not a verified chain. That helps inspect supplied certificates without establishing which roots the client accepts. Preserve the list separately from the verification conclusion.

The November 5 SSH host-identity article concerns a different first-trust mechanism. This question is limited to a TLS diagnostic client's controls; known_hosts rules do not substitute for certificate-chain acceptance. Fix the trusted inputs, expected identity, and failure policy before incorporating the result into a release check.
