How should hidden until-found keep collapsed HTML discoverable?

Check until-found discovery, layout conditions and the beforematch recheck, with an explicit reveal fallback.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-07 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • Until-found and ordinary hidden have different discovery contracts.
  • Layout overrides can defeat native revelation.
  • State and connection are checked after beforematch.

Hidden until-found preserves find-in-page and fragment revelation while content is not presented. Ordinary hidden has a different contract, and display overrides can break revelation. Decide whether temporarily collapsed information should remain discoverable before treating every hidden state alike.

The HTML hidden definition distinguishes Hidden and Hidden Until Found. The latter lets find-in-page or fragment navigation run an ancestor-revealing algorithm before scrolling to the target. This conditional discovery mechanism does not make all hidden content searchable.

Skipped content is not a missing box

Ordinary hidden describes content not directly relevant to the current presentation. Until-found expresses a different intention: undisplayed now but reachable through discovery. Its rendering uses content-visibility rather than simply removing the whole box with display:none, so borders, padding and margins can remain.

Visibility inheritance and descendants covers a different mechanism. Here the browser also owns a discovery-to-revelation flow. A shared hidden CSS class can erase that flow while temporarily preserving the same appearance.

Suppose a policy contains supplemental expired-material instructions. They should not interrupt the main reading sequence but should be found when someone searches for expired. The text and identity must exist in the document. A browser cannot match text that has not been fetched; this attribute supplies no remote search or loading.

A complete document with a manual fallback

This HTML has not been executed and contains no real policy, endpoint or form. Supplementary text is present from the start. A fragment points to its actual id. The manual button is a separate fallback; using it successfully does not validate native discovery.

<!doctype html>
<html lang="en">
<meta charset="utf-8">
<title>Teaching discovery routes</title>
<h1>Teaching material instructions</h1>
<p><a href="#expired-rule">Go to expired-material instructions</a></p>
<button id="show" type="button">Show supplementary instructions</button>
<button id="hide" type="button">Restore discoverable collapsed state</button>
<p id="status" role="status">Use find-in-page to locate the complete supplemental heading.</p>
<section id="extra" hidden="until-found">
  <h2 id="expired-rule">Teaching expired materials</h2>
  <p>Fictional instructions: confirm the applicable version for expired materials.</p>
</section>
<script>
const [extra, show, hide, status] = ['extra', 'show', 'hide', 'status'].map(
  id => document.getElementById(id)
);
const on = (node, name, fn) => node.addEventListener(name, fn);
const say = text => { status.textContent = text; };
on(extra, 'beforematch', () => {
  say('Native discovery notification received; the browser checks what follows');
});
on(show, 'click', () => {
  extra.removeAttribute('hidden');
  say('Manually shown; native search has not been verified');
});
on(hide, 'click', () => {
  extra.setAttribute('hidden', 'until-found');
  say('Collapsed again; inspect search or fragment navigation separately');
});
</script>
</html>

The section has no overriding display or content-visibility styles. In this standalone HTML page, search for the complete hidden heading, “Teaching expired materials”, and verify that the match is expired-rule rather than the visible status. Then fold it again and follow the fragment, recording each path separately. Fragment success does not establish identical find-in-page behavior in every browser.

Restoring until-found differs from assigning hidden=true, which creates ordinary Hidden state. A framework using one boolean for every collapsed panel must inspect the final DOM value rather than relying on the name of a component variable.

Why can display:none defeat discovery?

The standard requires layout containment and explicitly identifies none, contents and inline display values as preventing this revelation. Removing borders or space through those overrides can remove discovery too. Decide whether content, decoration or the entire box should disappear.

Use otherwise identical samples for each display condition. Do not manually remove hidden in a broken variant and then report native revelation. That would test the fallback's responsibility. Retain the CSS condition that changed the premise.

A revealed target may still sit behind a fixed header. Fragment targets and scroll-margin addresses that subsequent geometry question. Expansion, readable positioning and keyboard continuation are distinct observations, not consequences certified by one event.

Why does changing to ordinary hidden in beforematch stop revelation?

After notification, the algorithm checks for Hidden Until Found again. If a listener changes the element to ordinary Hidden, it returns without removing the attribute. Connection is rechecked too. Removing the node can therefore change the remaining process; the browser does not promise to reveal an old target regardless of application changes.

A component can accidentally trigger this by rerendering from an old collapsed=true model during beforematch. Discovery occurs, then the application restores ordinary hidden. Assign ownership of the discovered expanded state instead of maintaining mutually overriding browser and component models.

The sample changes only external status text. A real component can synchronize its expanded model, but must avoid replacing the target with another ordinary-hidden node. Asynchronous loading introduces another contract about what text already exists and how waiting continues; it is not implemented here.

Does dispatching beforematch automatically reveal the content?

It does not invoke the browser's ancestor-revealing algorithm. Synthetic notification can exercise application listeners without reproducing search, matching, state rechecks or attribute removal. Test those mechanisms through real search or fragment navigation.

The fallback should remove the attribute directly instead of fabricating a discovery event. It supports browsers or users not taking the native path. Record manual display as manual display to preserve the compatibility boundary.

Hiding also supplies no access control: the document already contains the text. The specific task here is retaining intended discovery and coordinating state after revelation, not building another visual secrecy mechanism.

Proposed checks retain browser, query, fragment, computed display, event order and attribute transitions, including a listener that changes back to ordinary hidden. No browser pass is claimed. Preserve actual discoverable content, then make layout and component state respect revelation rather than merely checking that source contains until-found.
