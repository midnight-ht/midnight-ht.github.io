Why can contains pass while another array item is invalid?

contains counts matching elements, items validates every element, and separate bounds control total length. An exactly-one-primary schema exposes all three layers and the same-object scope rule.

Key takeaways

  • A passing matching subset does not establish validity of every element.
  • Match counts and total array length are independent constraints.
  • minContains/maxContains need contains in the same schema object.

Passing contains does not mean every array item is valid. It constrains how many elements match its subschema. Independent constraints such as items are needed to validate all elements. Treating “a qualifying item exists” as “the whole array is valid” can admit malformed nonmatching elements.

The Draft 2020-12 contains clause concerns matching elements. This example pins that dialect and separates item shape, match counts and total length. The outcomes are reasoned expectations, not validator execution results or assumptions borrowed from a browser selection control.

One primary record is not one total record

Suppose an interface accepts route records with a string id and a role of either primary or secondary. It requires exactly one primary record and between two and four records overall. Those are distinct concerns: the shape of every record, the number of primary records and the total record count.

The schema below assigns these responsibilities separately. items constrains every element, contains identifies primaries, both match-count bounds are one, and the total length has independent bounds. Names and identifiers are hypothetical and do not configure any real routes.

{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "array",
  "minItems": 2,
  "maxItems": 4,
  "items": {
    "type": "object",
    "required": ["id", "role"],
    "properties": {
      "id": { "type": "string" },
      "role": { "enum": ["primary", "secondary"] }
    },
    "additionalProperties": false
  },
  "contains": {
    "type": "object",
    "required": ["role"],
    "properties": { "role": { "const": "primary" } }
  },
  "minContains": 1,
  "maxContains": 1
}

The contains subschema does not repeat the id requirement because items already supplies the base shape. Its required: ["role"] makes the matching predicate explicit: an object needs an actual primary role to match. properties alone does not require a property to exist, so it cannot establish that an object missing the role fails the predicate.

Attribute failures to the right constraint

Start with [{"id":"p","role":"primary"},{"id":"s","role":"secondary"}]. Both objects satisfy the base shape, exactly one matches the primary predicate, and the total length is two. The complete schema is expected to pass. The secondary record's failure to match contains is not an invalid-record result; it simply lies outside the counted subset.

Replace the second item with nine: [{"id":"p","role":"primary"},9]. There is still exactly one primary match, so the matching-count requirement can hold. However, items rejects the number, so the schema should fail overall. This is the counterexample: remove items, leaving only array type, length and primary-count constraints, and the malformed number is no longer excluded by the base shape.

Make both records primary next. Each can be a valid object and the total length can be allowed, yet two matches exceed maxContains. Conversely, two secondary records can both have valid shapes while failing the minimum match count. A single overall validation result should not erase those different causes; an inaccurate error message can make callers change the wrong field.

Finally, combine four valid secondary records with one primary. There is still one primary match, but the total length is five and fails maxItems. maxContains: 1 never promised at most one total element. Without a total-length bound, many valid nonmatching records can remain acceptable. The interface must choose its own resource limit.

Read the boundary rules explicitly

The validation vocabulary's match-count definitions require nonnegative integers. Use that normative condition rather than interpreting a guide's broader “number” wording as permission to use fractions. Dialect support matters too: recognizing contains does not prove that a tool implements every related keyword.

Without an explicit minContains, the minimum match count is one. Setting it to zero can allow no matching items, but it does not disable every count restriction. A simultaneous maximum can still reject too many matches. With a minimum of zero and maximum of one, zero and one matches can satisfy the range; two cannot.

That alone does not establish whether an empty array passes. The complete schema still has minItems: 2. Even after changing the minimum match count to zero, an empty array fails total length. Diagnose the constraint that rejects the input rather than declaring the entire schema permissive because one parameter is zero.

Does minContains work without contains?

No. It needs contains in the same schema object. Placing the minimum outside a subschema and moving contains inside it does not automatically pair the two locations. Related keywords still have structural scope; appearing somewhere in the same file is insufficient.

To probe this failure, delete the same-level contains from a copy of the complete schema but retain the minimum and maximum match counts. Reconsider the input with no primary record. The match-count keywords no longer constrain it, while items and total-length constraints remain active. That does not mean the validator has ignored the entire schema.

A validator producing matching-index annotations also cannot assume that finding the first primary ends all evaluation. The core specification requires the relevant annotation to cover every matching index. Computing the matching set and merely asking whether a match exists are different tasks. This example makes no performance or early-exit claim.

Retain the outer array type constraint too. Match-count keywords do not convert arbitrary input into an array. If the interface receives an object or string, type: "array" should reject it directly; an array-element keyword should not be expected to provide the missing type check. Wrong input kinds and malformed records inside a legitimate array need separate test cases.

The example also does not require unique identifiers. Two objects can share an id without this schema declaring that a failure, provided their roles and other constraints hold. If the domain needs identity-based deduplication, define that separately. Exactly one primary does not imply that every record has a unique identity. Stating unexpressed requirements prevents callers from deriving too many guarantees from a passing result.

Keep tests that discriminate between the rules

Before adopting the schema, choose a validator supporting the declared dialect, record its actual tool and version, and run the normal, malformed-secondary, double-primary, no-primary and excessive-length instances. Until that happens, keep their results labeled as expectations. If a minimum or total-length limit changes, derive the new outcomes rather than copying the old report.

For a different interaction between prefix elements, remaining items and total length, see why prefixItems does not fix tuple length. Here the decision is concrete: use whole-array item constraints for every record's shape, match counts for the distinguished subset and total-length bounds for overall size. Passing one layer cannot guarantee the other two.
