Why does a unittest.mock patch at the definition site miss the consumer?

Trace Python consumer bindings with a complete pricing fixture, separating patch target, lifetime, and create=True.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-07 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • Patch the binding actually read by the consumer.
  • From-import and module-attribute lookups need separate analysis.
  • create=True does not establish a real API or a correct target.

Patch the name the system under test actually looks up. A consumer that already imported fee from fees has its own binding; replacing fees.fee later does not replace that local name. A longer patch lifetime cannot repair a target outside the lookup path.

One function can have several bindings

The unittest.mock documentation says to patch where an object is looked up, which need not be where it was defined. The page returned on November 6, 2026 identifies itself as Python 3.15.2 documentation; that does not identify the reader's interpreter. The example uses local pure functions. No fee service was contacted and no test was run.

Suppose fees defines a fee function and billing imports it to calculate a total. A from-import creates a name in the consumer. It does not require every later call to return to the defining module and retrieve that attribute again. Two names may initially point to the same function, while rebinding one leaves the other unchanged.

A patch context can therefore enter successfully and have a configured return value while the business function still uses the original fee. That is not necessarily a malfunctioning mock. Inspect the consuming expression before lengthening the patch scope or retrying the test.

Three files and an observable business result

This complete, unexecuted teaching project needs an isolated writable directory. Save each block under the indicated name and run unittest from that directory. It requires no third-party network or database. The numbers illustrate binding rather than a real pricing policy.

# fees.py
def fee():
    return 3

# billing.py
from fees import fee

def total(base):
    return base + fee()

# test_billing.py
import unittest
from unittest.mock import patch
import billing

class BillingLookupTest(unittest.TestCase):
    def test_definition_patch_misses_consumer(self):
        with patch("fees.fee", return_value=9) as substitute:
            self.assertEqual(billing.total(10), 13)
            substitute.assert_not_called()

    def test_consumer_patch_changes_business_result(self):
        base_price = 10
        with patch("billing.fee", return_value=2) as substitute:
            patched_total = billing.total(base_price)
            substitute.assert_called_once_with()
        restored_total = billing.total(base_price)
        self.assertSequenceEqual((patched_total, restored_total), (12, 13))

if __name__ == "__main__":
    unittest.main()

The proposed invocation is python -m unittest -v test_billing. Preserve its actual exit status immediately, along with output, before running other checks. A successful directory listing afterwards is not the test result. The expected totals of 13 and 12 are derived from these inputs, not captured passing output.

The first test intentionally demonstrates the missed binding. billing was imported before the patch and retained its original reference, so its total remains 10 plus 3. The unused substitute is supporting evidence; the returned business value identifies the effective path. Checking only that the substitute returns nine would mostly check the test's own configuration.

The second test changes billing.fee, which total actually reads, and expects 12. After the context exits, the expected 13 checks restoration of that name. No external effect needs undoing in this deliberately pure example. Production code that writes a file or sends a request needs separate isolation and result checks.

Consider a separate explicit product contract: this invocation must use a fee of nine on a base of ten. Its independent expected total is 19. A definition-site patch that leaves the consumer returning 13 must fail that acceptance test. The demonstration asserts 13 only to expose the retained binding; it is not the correct product expectation for the substituted-fee contract.

The same lookup matters when simulating provider failure. If a replacement at the definition site raises but the consumer still returns normally, the failure input never entered the business path. That does not establish error handling. Compare original, replacement-value, and replacement-error inputs against explicit caller outcomes instead of swallowing every exception to obtain green tests.

A different expression can require a different target

If billing instead uses import fees and calls fees.fee, it retrieves a module attribute. Patching fees.fee is then on that path. “Always patch the consumer module” would be another inaccurate shortcut. Choose from the actual expression; import syntax helps reveal the lookup but does not replace inspection.

A review can list definition location, consumer binding, and call expression. Both versions define the function at fees.fee. The from-import version reads billing.fee, while the module-import version reads fees.fee. Both are legitimate styles. Tests should match the current contract rather than casually changing production imports to accommodate an existing patch.

Default arguments, closures, and previously constructed objects may capture references elsewhere. Continue tracing the actual reader and capture time in those cases, or consider explicit dependency input. This example does not establish that either patch string changes every historical reference.

Does create=True prove that the patch target is correct?

No. It can create an attribute that was absent. Successful setup does not prove that production code reads it. The official reference warns that this can produce passing tests against APIs that do not exist. An absent-target error should first prompt a check of spelling, module identity, and consuming expression.

For example, a typo changing billing.fee into billing.fees would normally expose a missing attribute. Allowing creation can make setup succeed while total still reads fee. A test checking only the created substitute misses the business behavior. Runtime-created attributes can justify the option, but identify their creator, reading point, and observable result explicitly.

Change the import or the dependency interface?

Start with the narrowest patch consistent with the existing lookup. If testing repeatedly needs many replacements inside a complex module, an explicitly supplied fee provider may express the dependency more clearly. Whether to refactor depends on responsibility and cost; difficulty in one test does not condemn every from-import.

The October 14 patch-scope article addresses lifetime, restoration, and the limits of undoing side effects. This question comes earlier: which binding should change? The location and lifetime decisions can succeed or fail independently.

Proposed verification keeps an unpatched baseline, a definition-site miss, the consumer-site replacement, and restoration after exit. Use independently stated business expectations. Record interpreter version, file locations, invocation, and actual errors, and confirm that imports resolve to the intended files. Establish that the replacement enters the business lookup before expanding scope or adding more elaborate simulation.
