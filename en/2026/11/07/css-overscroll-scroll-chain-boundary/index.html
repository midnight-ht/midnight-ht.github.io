Why does the page keep scrolling after an inner CSS scroller reaches its edge?

Separate scroll chaining, local feedback and DOM propagation with nested scrollers and real-input comparisons.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-07 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • Boundary policy belongs to the actual scroller and axis.
  • Local feedback remains with contain; none additionally restricts it.
  • Programmatic scrolling is not a boundary-gesture test.

Scroll chaining can hand a boundary action to an ancestor scroller. Overscroll behavior controls that boundary policy on a scroll container, not DOM event propagation. When the pointer remains over a sidebar but the page moves after the sidebar reaches its end, inspect the chain before adding wheel listeners.

CSS Overscroll Behavior Level1 defines transfer between a scroll container and an ancestor, typically at a boundary. This article uses the Editor’s Draft dated June30,2026 and compares the relevant auto, contain and none behavior. It does not claim exhaustive value coverage or verified platform compatibility.

Identify the boundary and the container

A documentation panel and its outer page can each scroll vertically. Once the panel reaches its end, continued input may be handled by an ancestor in the chain. An event originating inside the panel does not establish that only its scrollTop may change. Record both containers.

The specification distinguishes local overscroll feedback from non-local boundary actions. A rubber-band indication can be local; chaining or navigation can affect other parts of the page. Contain blocks non-local actions while preserving local behavior. None additionally blocks local feedback. A platform with no such feedback need not manufacture it for the comparison.

Passive-listener cancellation concerns cancelable and listener conditions. Here the scroller declares a boundary policy. StopPropagation controls propagation, not proof of a stopped scroll chain. A missing outer callback does not establish a stationary outer scroller.

A static comparison on the actual scroller

This complete HTML has not been executed. Both outer and inner areas have constrained heights and scrolling. Start with auto, change only the panel to contain, then none. The content is instructional and connects to no service or analytics.

<!doctype html>
<html lang="en">
<head>
<meta charset="utf-8">
<title>Scroll-chain comparison</title>
<style>
#outer { height: 24rem; overflow: auto; border: 2px solid; padding: 1rem; }
#panel { max-height: 8rem; overflow: auto; overscroll-behavior-y: auto; border: 1px solid; }
#panel ol { margin: 1rem; }
.spacer { height: 20rem; }
</style>
</head>
<body>
<h1>Scroll the panel, then observe the outer area</h1>
<div id="outer">
  <p>The outer area can continue scrolling.</p>
  <section id="panel" aria-label="Teaching documentation">
    <ol>
      <li>Check material identity</li>
      <li>Read its current version</li>
      <li>Check scope</li>
      <li>Confirm complete instructions</li>
      <li>Record follow-up questions</li>
      <li>Return to the task</li>
    </ol>
  </section>
  <div class="spacer" aria-hidden="true"></div>
  <p>End of the outer area.</p>
</div>
</body>
</html>

First establish that the panel has scrolling space and that the outer area has not reached its end. Continue real input at the panel boundary and record both scrollTop values and visible positions. If the outer area was already at its end, every variant can appear still; the comparison cannot discriminate.

A declaration on a decorative wrapper may be ineffective. The standard requires a non-scroll-container to accept but ignore the property; it does not create scrolling. Inspect computed overflow, dimensions and the element that actually moves. Sticky scroll-ancestor diagnosis can help identify containers, but correct sticking establishes no boundary result.

Check the axis as well. A vertical problem may need only y-axis policy, leaving horizontal behavior untouched. Two-axis input requires separate consideration. Success with one trackpad gesture does not validate touch, wheel and keyboard paths.

Can setting scrollTop at the end test scroll chaining?

Not by itself. Programmatic scrolling is clamped and does not trigger boundary default actions. It can prepare a position, but real input must exercise the subsequent boundary behavior. Setting a maximum and seeing no outer movement is not evidence about continued user scrolling.

A constructed wheel event is likewise not a device test. DefaultPrevented describes a flag, whereas the user agent implements scrolling and boundary behavior. Retain device, direction, input location and both positions so an observation can be attributed to a real route.

Is the property always ineffective when content cannot scroll?

No blanket rule follows. A scroll container without scrolling potential in an axis is considered at its boundary. That differs from an element that is not a scroll container. Establish the relevant container and axis rather than treating a visible scrollbar as the definition.

An empty-result panel therefore deserves its own comparison after a long list. Its computed styles and actual input conditions matter. Input directly outside the panel need not pass through its chain. Contain is not a global modal background lock and supplies no focus or interaction restriction.

Switch the same panel between long and short content to expose a misleading comparison. With long content, begin midway down the inner range. A downward action should first consume its remaining space; continued input at the end reaches the boundary discussed here. If the outer container moves from the middle, inspect the input location and actual size constraint before attributing the whole input sequence to a boundary property.

For short content, rebuild the observation sheet. Record that the inner element has no consumable vertical distance and whether overflow still establishes a scroller. Then move the pointer into outer blank space for a separate comparison. Outer movement there does not contradict the inner policy: that action did not start through the inner container. This separates a short-list boundary constraint from a requirement to prevent scrolling everywhere. If the latter is the actual product requirement, redefine the interaction scope before strengthening this property.

Choose contain when local feedback should remain and none when deliberately suppressing that feedback too. Do not impose a stronger behavior merely because the keyword sounds more complete. No performance or latency measurements were made here.

Proposed checks retain the three policies and add a non-scrolling wrapper, short content and outside input. Record computed properties, actual boundaries and both movements. A useful conclusion identifies one container's policy in one axis, rather than claiming the entire page is locked.
