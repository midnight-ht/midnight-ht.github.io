CONFIGURE_DEPENDS adds rechecks without removing the source-list tradeoff

Compare explicit lists, plain GLOB and CONFIGURE_DEPENDS to inspect new-source membership, generator support and unintended matches.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-07 · Estimated read 16 min
Translations
zh-CN en

Article

Key takeaways

  • Observe glob rechecking and actual new-source compilation separately.
  • Generator reliability and repeated check cost remain documented tradeoffs.
  • Running a program that never calls the added function does not prove its source was compiled.

CONFIGURE_DEPENDS can make a build-system check rerun a flagged GLOB and regenerate the build system when its results change. It does not remove source-list maintenance tradeoffs. Whether a new file participates in this build depends on when membership was expanded, whether the generator supports the check and whether the generated graph actually changed.

A file can exist outside the generated graph

The CMake file(GLOB) documentation says CONFIGURE_DEPENDS, added in 3.12, adds glob-rechecking logic to the main build-system check target. Changed results cause regeneration. The page read on November 7, 2026 is titled CMake 4.5.0-rc3 documentation; that is not the reader’s installed stable version.

An ordinary GLOB forms its list during configuration. The generated graph then uses that result. A new file does not edit the already expanded list. Another change to CMakeLists.txt or a configuration dependency might happen to trigger configuration and reveal the new member, but that does not prove the plain glob independently detected directory changes.

The same official section discourages GLOB for source lists, warns that CONFIGURE_DEPENDS may not work reliably with all generators and notes a checking cost on every rebuild. No benchmark here establishes that it is slow, and the warning does not mean every existing generator fails. Decide within the project’s supported generators and maintenance constraints.

One program with three membership sources

This complete teaching project is unexecuted. Create three fresh source directories named probe-explicit, probe-glob and probe-tracked, each containing identical copies of main.cpp and the CMakeLists.txt configuration. The added extra.cpp source must be absent initially. The fixture requires CMake, an available C++ toolchain and Ninja. Version 3.20 is its illustrative minimum. Use independent build trees without an old cache.

cmake_minimum_required(VERSION 3.20)
project(MembershipProbe LANGUAGES CXX)
set(MEMBERSHIP_MODE "explicit" CACHE STRING "explicit, glob, tracked-glob")
if(MEMBERSHIP_MODE STREQUAL "explicit")
  set(inputs main.cpp)
elseif(MEMBERSHIP_MODE STREQUAL "glob")
  file(GLOB inputs LIST_DIRECTORIES false "${CMAKE_CURRENT_SOURCE_DIR}/*.cpp")
elseif(MEMBERSHIP_MODE STREQUAL "tracked-glob")
  file(GLOB inputs LIST_DIRECTORIES false CONFIGURE_DEPENDS
       "${CMAKE_CURRENT_SOURCE_DIR}/*.cpp")
else()
  message(FATAL_ERROR "unknown MEMBERSHIP_MODE")
endif()
message(STATUS "members=${inputs}")
add_executable(membership_probe ${inputs})

// main.cpp
int main() { return 0; }

From the common parent of the three source directories, the proposed commands are below. The cmake_step function captures a failed command’s status immediately and exits the current shell, preventing subsequent configuration or builds. Success proceeds to the next step. Each group keeps its own probe and build paths; an old artifact from another directory cannot substitute. These commands have not been run and produced no compilation evidence here.

cmake_step() {
    if cmake "$@"; then
        return 0
    else
        cmake_status=$?
        printf 'cmake failed: %s\n' "$cmake_status" >&2
        exit "$cmake_status"
    fi
}
for variant in explicit glob tracked; do
    case "$variant" in
        tracked) mode=tracked-glob ;;
        *) mode=$variant ;;
    esac
    cmake_step -S "probe-$variant" -B "build-$variant" \
        -G Ninja -DMEMBERSHIP_MODE="$mode"
    cmake_step --build "build-$variant" --verbose
done

The independent first-build expectation is that main.cpp is the sole source member in every group. Then add the following extra.cpp to each source directory without changing CMakeLists.txt and repeat only the build loop shown below. Do not repeat the configuration loop: doing so would explicitly refresh the plain GLOB and invalidate the comparison. The independent function has no required reference from main, deliberately making build success insufficient to expose omission.

// extra.cpp, added only after the first build
int extra() { return 7; }

for variant in explicit glob tracked; do
    cmake_step --build "build-$variant" --verbose
done

Continue in the same shell where cmake_step is defined. After adding files, invoke only builds. Removal and nonmatching-file controls likewise change one input in each independent source directory, followed by this build loop and retained membership and compilation records.

The explicit group still lists only main.cpp until someone updates its list. The plain glob has not independently registered a recheck for this directory mutation and updates membership when configuration runs again. Where the generator supports the flagged check, the tracked group should detect the changed list, regenerate and include extra.cpp in the compilation. These are expected branches, not evidence of results in the reader’s environment.

Does a successful program run prove the added file was compiled?

No. Main never calls extra, so omitting extra.cpp still allows the program to link and return zero. Preserve the current members output and regeneration record, then find the command that actually compiles extra.cpp in this build. Then identify the artifact from that same build tree. Running the executable alone cannot distinguish these membership sets.

This adds an acceptance decision: a membership signal must actually change when membership changes. If main instead required extra, omission might produce a link error. That tests another dependency relationship rather than replacing this contract that an unused source must still enter the release. Both tests can be useful once the project states what it requires.

Who owns automatic discovery’s costs?

An explicit list puts member additions into a build-file diff where reviewers can discuss their inclusion. It requires maintenance and can itself suffer missed updates. Its benefit is a reviewable decision, not automatic proof that every file belongs in a release.

Globbing reduces list maintenance but can include scratch.cpp, merge artifacts or experiments that match the pattern. Automatic rechecking treats a matching file as an ordinary new member without understanding its purpose. Limit directories and patterns, inspect the resulting set and test additions and removals on supported generators.

Generated files need a boundary too. A build that writes into its own source-matching directory can change the next membership set. The fixture separates source and build trees to avoid that extra input. Real paths must be inspected independently; a clean example does not validate production layout.

What changes when the generator changes?

Record the CMake version, generator and complete configuration commands. Check that the relevant build check participates in a normal build. Test adding a matching file, removing one and adding a nonmatching file, retaining regeneration and compilation evidence separately. If check cost matters, measure it in the actual project under comparable conditions rather than deriving a performance claim from this unexecuted fixture.

The generator-configuration article concerns when Debug or Release is selected. This question concerns which sources enter the graph. Both need generator identity but make different decisions. The reproducible-build article requires fixed comparison inputs; fixing build time cannot establish equal inputs when source membership is unknown.

The final record should identify the members found during configuration, whether the graph regenerated after a directory change and which files the current build compiled. No project was configured or compiled here and no generator version was validated. Associate those observations with the same source and build tree before trading explicit-list maintenance for constrained discovery.
