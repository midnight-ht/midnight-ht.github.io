Why is a saved DOM event’s currentTarget null after dispatch?

Explain currentTarget cleanup after DOM dispatch while separating event state, captured nodes and task identity.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-07 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • Dispatch cleanup clears currentTarget.
  • Capturing a reference does not freeze its node.
  • Check connection and task identity before applying a result.

CurrentTarget describes the listener target during dispatch and is cleared when dispatch ends. Capture needed references and identity synchronously for later work. Retaining an Event object does not freeze its invocation state.

The DOM dispatch algorithm sets currentTarget while invoking listeners and clears it to null during cleanup. That is separate from a button's connection to the document. A null value is not evidence of component removal.

Inspect timing rather than an async keyword

A handler can read the button synchronously and later read null from the saved event in another task while the button remains unchanged. The currentTarget reference explains this temporary availability.

Do not generalize to every continuation after await. Native dispatch and microtask checkpoints can interleave differently; the relevant condition is whether dispatch has ended. This example uses a later task instead of treating an async keyword as a universal scheduling rule.

Target and currentTarget are not interchangeable either. In ordinary light DOM, clicking a span inside a button can target the span while the button owns the listener. Delegating from a parent changes the listener target again. Shadow-tree retargeting is outside this example.

Capture the object identity too

This complete HTML has not been run and has no interface or persistence. A1200-millisecond teaching delay leaves time to switch records. It is not a network or performance limit. The handler captures a button and record, later reports both event state and the reference, and only treats a matching task as applicable.

<!doctype html>
<html lang="en">
<meta charset="utf-8">
<title>Dispatch state and node references</title>
<button id="inspect" type="button" data-record="lesson-a">
  <span>Inspect current record</span>
</button>
<button id="switch" type="button">Switch record</button>
<p id="status" role="status">Current record lesson-a</p>
<pre id="log"></pre>
<script>
const [inspect, change, status, log] = ['inspect', 'switch', 'status', 'log'].map(
  id => document.getElementById(id)
);
const on = (node, type, handler) => node.addEventListener(type, handler);
const write = (node, text) => { node.textContent = text; };
const recordOf = node => node.getAttribute('data-record');
let generation = 0;
const pending = new Set();
on(inspect, 'click', event => {
  const owner = event.currentTarget;
  if (!(owner instanceof HTMLButtonElement)) return;
  const record = recordOf(owner);
  const ticket = ++generation;
  const before = owner.id;
  const timer = setTimeout(() => {
    pending.delete(timer);
    const matches = owner.isConnected && recordOf(owner) === record
      && ticket === generation;
    write(log, JSON.stringify({ before, after: event.currentTarget,
      savedNode: owner.id, connected: owner.isConnected, record, matches }, null, 2));
    write(status, matches ? `Applicable to this operation: ${record}` : 'Old task no longer matches');
  }, 1200);
  pending.add(timer);
});
on(change, 'click', () => {
  generation++;
  const nextRecord = recordOf(inspect) === 'lesson-a' ? 'lesson-b' : 'lesson-a';
  inspect.setAttribute('data-record', nextRecord);
  write(status, `Current record ${nextRecord}`);
});
on(window, 'pagehide', () => {
  for (const timer of pending) clearTimeout(timer);
  pending.clear();
});
</script>
</html>

Moving the listener from a button to a common parent preserves the capture rule but changes what is captured. The parent's current listener target is the parent, so the original button-type guard no longer succeeds. Derive the matched button and registered listener container separately: the former may come from a range-checked closest result, the latter from the current target during the callback. Widening a type assertion does not make the old record lookup correct.

Specify these inputs at the task boundary. Work addressing lesson-a can receive an immutable record key instead of an event that a deeper function must inspect. Work updating the button needs its node and key together. A container may handle many records, and its own id cannot identify each of them. Connection, object identity and operation generation answer different questions; omitting any one can apply later work to the wrong destination.

Without a record change, the proposed observation is a null event property after dispatch, alongside a connected, matching captured node. Switching during the delay makes the old task inapplicable. Both routes retain the node and distinguish reference survival from current task ownership.

Repeated clicks create multiple tasks. Generation invalidates older application rights while retaining their diagnostic observation. A real product can cancel expensive work or ignore old results according to its own contract. This sample sends nothing to a server, so ignoring a result is not cancellation of a remote write.

Does shallow-copying the event preserve currentTarget?

Do not rely on that. Read required properties explicitly during the synchronous callback instead of treating a platform event as an ordinary enumerable record. Capturing currentTarget reads its then-current value; a later read from the event sees later dispatch state. Explicit inputs also reveal what subsequent work needs.

A captured node remains a live reference. Its text, attributes and record binding may change, and a removed node may remain referenced. Mutation records and current node values describes a related reference distinction; here the additional mechanism is the dispatch algorithm clearing currentTarget itself.

If later work needs only a record key, retain that identity rather than a node. If it updates a button, validate connection, identity and operation ownership. Passing an Event through service layers can conceal that its current-target state is temporary.

May a result be applied whenever the captured node still exists?

No. A list can reuse a connected button for a different record. The example compares both data-record and generation. A framework may use versions or cancellation, but must explain when a previous result loses authority.

Proposed checks cover unchanged identity, switching, repeated clicks and node removal. Record synchronous currentTarget, post-dispatch readings, captured-node connection and record identity. A constructed Event read after dispatchEvent returns can separately test cleanup; it does not demonstrate real user input.

Passive listeners and cancellation flags emphasizes the actual registration. Preserve the listening location and observation phase here too. No browser logs were captured; the JSON shape in code is not a runtime receipt. Establish the dispatch stage first, then choose what to retain and who may apply a later result.
