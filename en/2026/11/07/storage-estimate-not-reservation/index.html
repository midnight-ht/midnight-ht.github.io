Design an advisory capacity check for an offline package

Use a read-only classifier and four independent expected cases to separate estimated capacity, actual writes and persistence permission.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-07 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • An estimate reads values without reserving space for the next operation.
  • Quota policy may consider persistence permission, but a grant does not reserve this package’s bytes.
  • A may-fit hint still needs a real write outcome, while unknown does not mean insufficient capacity.

An offline-package download can use estimated storage headroom as a preflight hint. It cannot claim that space has been reserved. StorageManager.estimate reads usage and quota estimates without reserving bytes for the next write. Persistence permission concerns clearing policy and makes no promise to expand capacity for this package. The interface should report the outcome of the actual storage operation separately.

What the numbers describe

The Storage Standard’s usage and quota section defines usage as an implementation-defined rough estimate and quota as a conservative estimate of the total bytes a shelf can hold. Compression and deduplication affect accounting. This article uses the standard last updated on 19 October 2026. One device’s returned value is neither a universal browser allowance nor a direct measurement of free disk space.

Consider synthetic values of 1,000 bytes of quota, 500 bytes of usage and a 400-byte package. The arithmetic leaves 500 bytes. That supports a “may fit according to this estimate” hint. It does not prevent another page from writing afterward, deduct 400 bytes, or lock them for this operation. Even without competition, the application’s package-size calculation and the storage implementation’s accounting may differ.

Preflight can help avoid an obviously unsuitable download or let a user choose a smaller package. It is not an account entitlement or a prediction of download success. A dependable product promise also needs a plan for actual write failure: preserving recoverable work, resuming the task or offering an export. A green capacity icon cannot establish those capabilities.

A read-only check with independent expectations

The following unexecuted example classifies supplied values and shows how to inspect the browser APIs. It neither downloads nor writes data, and it does not call persist. All sample sizes are synthetic bytes chosen for easy arithmetic, not real browser quotas. Check the fixture independently before using the browser-facing function in a supported secure context.

function advise({usage, quota}, bytes) {
  const values = [usage, quota, bytes];
  if (!values.every(Number.isFinite) || values.some(v => v < 0)) {
    return 'unknown';
  }
  return quota - usage >= bytes ? 'may-fit' : 'too-large-for-estimate';
}

const samples = [
  [{usage: 700, quota: 1000}, 400],
  [{usage: 500, quota: 1000}, 400],
  [{usage: 600, quota: 1000}, 400],
  [{usage: null, quota: 1000}, 400]
];
console.log(samples.map(([estimate, bytes]) => advise(estimate, bytes)));

async function inspectStorage(bytes) {
  if (!navigator.storage?.estimate || !navigator.storage?.persisted) {
    return {advice: 'unknown', persistent: null};
  }
  try {
    const [estimate, persistent] = await Promise.all([
      navigator.storage.estimate(),
      navigator.storage.persisted()
    ]);
    return {estimate, persistent, advice: advise(estimate, bytes)};
  } catch (error) {
    return {advice: 'unknown', persistent: null, errorName: error.name};
  }
}

The independently specified results are too-large-for-estimate, may-fit, may-fit and unknown. The first three headroom values are 300, 500 and 400. The fourth usage value is not a finite number and must not silently become zero. Unknown means that a usable estimate is missing; it does not establish that the package is too large or authorize deleting user content. These are expected values, not captured console output.

A real UI must also account for stale readings. A user can leave a capacity confirmation page open and act much later. Reading again before the operation may improve the hint, but another read is still not a lock. Frequent polling should not imply a storage lease or be presented as precise disk monitoring.

What persistence changes

The standard’s persistence and storage-pressure provisions distinguish default best-effort local buckets from persistent ones. Under pressure, automatic clearing policy targets best-effort storage; persistent storage receives protection, while clearing involving the user or origin remains possible. Persistence is neither a backup nor a conversion of session storage into long-term retention.

Permission and quota policy are not categorically unrelated. The standard encourages user agents to consider factors including persistence permission when determining quotas. The accurate boundary is that persist does not promise extra capacity or reserve this write’s bytes. It would be wrong to claim that permission can never influence any implementation’s quota. If offline availability requires a persistence request, design that separately at an understandable moment and handle its real result. No request has been made for this article.

A product can need both capacity and retention, but these remain separate decisions. Denied persistence need not mean that the current save failed. Granted persistence does not establish that a package will fit. Distinguish estimate availability, advisory capacity, actual write progress and persistence status instead of collapsing them into “safely saved.”

Handle a write failure after a positive hint

Suppose another cache write consumes 200 bytes after the estimate. The package now faces different conditions. Handle actual request errors and transaction abortion, preserve recoverable task information, and provide workable retry, smaller-package or export choices. Do not label every storage failure a network problem to defend the preflight result. Nor should the first successful write request announce completion of the whole package.

Capture the estimate time, the package-size accounting basis, the final storage operation and the user-visible result. With IndexedDB, request success and transaction completion still need separate handling; see transaction activity and final outcomes. The present question concerns the absence of capacity reservation before a write, rather than the transaction’s lifetime.

Planned tests should include a may-fit hint followed by write failure, unavailable estimates with a controlled write path, user cancellation, and a cleanup suggestion with insufficient removable content. If deletion is offered, identify the objects and whether they can be recovered. Do not silently remove unsynchronized work to make a download fit. No write or cleanup test has been executed here.

If estimated headroom equals the package size, can the UI promise success?

No. Equality satisfies only the arithmetic condition for that snapshot. Indexes, encoding and other writes can consume space, and the API does not reserve it. The example’s 600-byte usage, 1,000-byte quota and 400-byte package deliberately produce may-fit. An additional safety margin would be an application policy, not a standards-backed success percentage.

A reviewable delivery separates three pieces of evidence: the snapshot behind the hint, the final write outcome and the persistence state. If only estimate has returned, the available result is advisory capacity. Make the button wording and failure recovery match that scope before integrating a real offline-save workflow.
