An extra rsync directory level: what does the source trailing slash change?

Compare existing rsync destination trees to trace source slashes, receiving levels, deletion scope, and shell expansion.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-07 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • A directory and its contents define different transfer roots.
  • Deletion considers extra items within synchronized directories.
  • A preview is separate from actual transfer evidence.

A source-directory trailing slash copies its contents without adding that directory-name level. Fix the existing destination and intended tree before choosing the form, then review deletion against the actual synchronized directory scope. The slash changes the transfer object, rather than merely its spelling.

Name the intended receiving path first

The official rsync manual describes a source trailing slash as copying contents while avoiding an extra directory level. Its VERSION clause identifies 3.5.2 and its footer says November 4, 2026. Those are observations about the manual, not the installed program or release status.

Suppose package contains one.txt. Should an existing destination receive one.txt directly, or package/one.txt? Either tree can be intended. State the full path before calling an additional level a defect.

A directory source without the slash normally retains its directory-name level under an existing receiver directory. With the slash, its contents go into that receiver. This example deliberately pre-creates destinations as directories, keeping missing-destination single-item naming rules out of the primary comparison. Record both sides rather than asking a source-path fragment to explain everything.

Preview two existing trees without deleting anything

This complete local teaching setup was not executed. It requires rsync, a conventional shell, and disposable writable storage. There is no remote endpoint or wildcard, and no real release directory belongs in these inputs.

rsync_demo_dir=$(mktemp -d)
cd "$rsync_demo_dir" || exit 1
mkdir -p src/package dest-named/package dest-content/package
printf 'new\n' > src/package/one.txt
printf 'keep?\n' > dest-named/root-marker
printf 'old\n' > dest-named/package/stale
printf 'keep?\n' > dest-content/root-marker
printf 'old\n' > dest-content/package/stale
preview() {
    rsync -ani "$@"
    rsync_result=$?
    printf 'preview-status=%s\n' "$rsync_result"
}
preview src/package dest-named/
preview src/package/ dest-content/
preview --delete src/package dest-named/
preview --delete src/package/ dest-content/

The n option makes all four calls previews; i itemizes changes. The function immediately records rsync's status before printing anything else. Even four successful previews do not copy or remove the destination files. Files created during preparation are not completed synchronization results.

Without deletion, the proposed receiving paths are dest-named/package/one.txt and dest-content/one.txt respectively. The prepared markers and stale files remain on disk because no transfer has run. These are predicted path relationships, not invented itemized output.

Adding deletion exposes the different roots. The first form synchronizes package, making its internal stale file a deletion candidate; the destination-root marker is not automatically part of that same synchronized directory. The second synchronizes package's contents into dest-content itself, bringing its root marker and source-absent package subdirectory into a different deletion scope. Inspect the actual preview item by item before accepting either set.

delete is not a universal destination cleanup switch

The manual limits deletion to extraneous receiving files inside synchronized directories. Filtering, recursion conditions, and other options affect the set too. Do not generalize the simple example into deleting everything absent from the source throughout an arbitrary destination.

A destination root may also hold runtime configuration, uploads, or another site. Establish whether those objects belong to the synchronization. The teaching root-marker makes the boundary visible; it is not a suggestion to experiment on real configuration. Stop on unexpected preview entries and inspect roots and filters instead of removing the object to make the preview tidy.

Before actual execution, verify readable source contents, unchanged destination identity, and intervening writes. An old preview describes the tree observed then, not every later state. This article does not remove n and perform deletion or establish delivery of a real directory.

Copying “contents” does not mean the receiving directory’s own attributes remain unchanged. The manual’s slash example also maps containing-directory attributes onto the corresponding receiver directory. With archive mode selected here, inspect that mapping alongside the location of one.txt; correct nesting does not promise unchanged permissions.

A separate owned sandbox can give source and destination distinguishable permitted attributes, record them, and inspect preview and actual changes. Preserving receiver attributes needs an option-level decision, not an assumption about the slash. Test this independently of deletion.

Is a wildcard equivalent to synchronizing the directory?

No. The shell expands it into individual items before rsync receives the request. The manual's deletion section explicitly distinguishes a directory argument from dir/*. Similar-looking file copies do not inherit the same parent-directory deletion assumptions.

Item count can also affect naming. Under the documented conditions—a single transfer item, no existing destination directory at the final element, and no destination trailing slash—the destination can become the item's new name. Pre-created destination directories avoid that branch here. Scripts should define destination type rather than depend on a wildcard matching several files today.

Does a successful dry run mean the destination was synchronized?

No. It previews proposed changes without supplying copied-content or persistence evidence. Permissions, source changes, disk errors, and concurrency can alter actual execution. Keep preview acceptance separate from the actual exit status, resulting tree, and content checks.

For understanding the slash, retaining n is sufficient for this comparison. An independently authorized sandbox copy should inspect one.txt's real contents and location after execution. A deletion experiment needs another explicit protection-set check. Those possible followups are not operations performed for this article.

Correct directory layout also does not establish atomic publication. Files can be replaced at different moments, and directory attributes have their own transfer behavior. An application's exposure to mixed versions needs a separate release design. A trailing slash is neither a rollback protocol nor a guarantee that permissions stay unchanged.

The November 5 Make target-collision article concerns action names and filesystem identity. Here the question is which directory object a synchronization actually requests. Identical-looking names do not establish identical sets. Draw the intended receiving tree, inspect transfer and deletion scope, then decide whether to execute.
