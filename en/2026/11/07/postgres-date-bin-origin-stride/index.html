Why do two fifteen-minute date_bin queries disagree?

Fifteen minutes defines a span, while origin defines alignment. Use boundary and pre-origin inputs to separate binning, filtering and calendar requirements.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-07 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • A binning contract needs a stride, an origin and the input timestamp type.
  • origin is an alignment anchor, not a filtering lower bound.
  • Months and larger units cannot be used in a date_bin stride.

Two services can both aggregate into fifteen-minute buckets and still disagree because date_bin uses both a stride and an origin. The stride specifies the span; the origin specifies alignment. Agreeing on “fifteen minutes” alone does not establish the complete binning rule.

Suppose a collector uses 09:02 as its anchor while a reporting service uses quarter-hour boundaries. The same record at 09:16 belongs to a bin starting at 09:02 in the first service and one starting at 09:15 in the second. Neither has miscalculated fifteen minutes. They disagree about the boundaries. Relabeling one result does not establish that both buckets contain the same records.

Start with four boundary inputs

This read-only PostgreSQL 18 example explicitly uses timestamp without time zone to isolate alignment. Its results are predictions derived from the official contract, not a database execution transcript. If a real system stores timestamptz, its type and conversion contract must also be made explicit.

WITH samples(t) AS (VALUES
  (timestamp '2026-11-06 09:01:59'),
  (timestamp '2026-11-06 09:02:00'),
  (timestamp '2026-11-06 09:16:59'),
  (timestamp '2026-11-06 09:17:00')
)
SELECT t,
       date_bin(interval '15 minutes', t,
                timestamp '2026-11-06 09:02:00') AS bucket
FROM samples
ORDER BY t;

The four predicted bin starts, on that date, are 08:47:00, 09:02:00, 09:02:00 and 09:17:00. Exactly 09:02 starts a new bin, as does exactly 09:17. Expressed as an interval, the 09:02 bin includes inputs from 09:02 up to, but not including, 09:17. The right boundary belongs to the next bin and should not be counted twice.

Keep the first row in the test. It precedes the origin by one second, but the result is neither 09:02 nor an input rejection. It is the preceding bin's start, 08:47. The anchor defines alignment in both directions; it is not the earliest acceptable record. If the product accepts only records from 09:02 onward, it needs a separate filter.

The documentation defines the return value as the beginning of the bin containing the source, aligned with the specified origin. Do not casually implement that as integer truncation of the timestamp difference divided by the stride. For negative differences, truncation toward zero and selecting the earlier bin are different operations. The one-second-before-origin row exposes that mistake.

Change only the origin

The next example shows both definitions in one row, rather than comparing reports that have already been aggregated independently. The source, stride and type remain identical; only the anchor changes.

SELECT timestamp '2026-11-06 09:16:00' AS t,
       date_bin(interval '15 minutes',
                timestamp '2026-11-06 09:16:00',
                timestamp '2026-11-06 09:00:00') AS aligned_at_zero,
       date_bin(interval '15 minutes',
                timestamp '2026-11-06 09:16:00',
                timestamp '2026-11-06 09:02:00') AS aligned_at_two;

The predicted results are 09:15:00 and 09:02:00. An interface parameter such as bucket=15m cannot tell a consumer which definition the producer used. Before comparing aggregates, assign a label to the same raw timestamp in both implementations. Establish that the partitions agree before investigating filtering windows and aggregate functions.

For a fixed stride, the origin need not be the timestamp of an actual event. A stable shared configuration value can serve as the anchor. Conversely, different origin values need not define different partitions: origins separated by an integer multiple of fifteen minutes generate the same boundaries. Check whether the origins align on the stride, rather than requiring their configuration strings to be identical. This is a deduction from periodic boundaries, not an additional runtime measurement.

Separate binning, filtering and empty-bin generation

Binning asks which interval contains a selected record. Filtering asks which records participate in the query. Empty-bin generation asks whether intervals containing no records should appear. A report can need all three, but calling date_bin does not perform all three automatically. It returns a time value; it does not generate every empty interval or select the business query window.

For example, if the report begins at 09:00 but retains the 09:02 alignment, records between 09:00 and 09:02 receive an 08:47 label. Filtering result labels to “09:00 onward” can then discard records that already passed the raw-timestamp filter. Decide whether the page displays complete bins or a clipped window before choosing the query structure. A label preceding the page's start does not, by itself, make the input invalid.

This matters when recomputing historical aggregates too. If the anchor changes while old cache keys and aggregate identifiers remain, one label can acquire two definitions of membership. Record a rule version, compare raw timestamps under the old and new definitions, and then decide whether aggregates need rebuilding. That is application-level rule management, not a claim that PostgreSQL detects or migrates caches automatically.

A larger stride does not create a calendar model

The stride must be positive and cannot contain months or larger units. A one-month stride will not implement a business monthly report. Months have different lengths; fixed-duration cells and a schedule beginning on a particular local calendar date are different requirements. Choose a calendar model for the latter rather than treating thirty days as every month.

The documentation notes agreement with analogous date_trunc calls for complete standard units. Preserve the alignment condition when using that comparison: the origin must align with the relevant standard-unit boundary. A fifteen-minute partition shifted by two minutes deliberately differs from quarter-hour alignment. A familiar unit name does not make every origin equivalent.

For requirements involving recurring local times, see timestamps and recurring schedules. This fixture resolves fixed strides and anchors. It does not establish that local calendar intervals across daylight-saving changes always have identical durations.

Is the same fifteen-minute stride enough for shared bucket keys?

No. Confirm that the origins align on that stride, and agree on the input timestamp type and conversion rules. A cache key can identify the complete rule and append the bin start. It should not hide the remaining configuration behind a seemingly complete “fifteen-minute” label.

For validation, retain a point just before a boundary, a point exactly on it, a later point inside the bin and a point before the origin. Shift the origin by two minutes and derive new expectations rather than copying the old answers. Finally, use zero, negative and month strides as rejection probes, leaving actual error wording to a real execution record. Comparing bucket counts across services becomes meaningful only after their boundary contracts agree.
