Why does jsonb_set leave a missing nested field unchanged?

jsonb_set creates only the final path item. Compare missing, empty and populated parents, then define an explicit construction or rejection policy before reporting a successful field update.

Updated 2026-11-07 · Estimated read 18 min
Translations
zh-CN en

Article

Key takeaways

  • create_if_missing does not recursively construct parent paths.
  • Object construction needs an explicit rejection or migration policy for incompatible existing types.
  • Neither row counts nor unchanged equality alone establishes the target-path postcondition.

Setting create_if_missing to true lets jsonb_set create the final path item. It does not recursively construct missing parents. To write profile.color, the profile step must already exist; otherwise PostgreSQL returns the original JSON, and the statement can still finish normally.

That explains an awkward profile-update failure: the database reports no error and the update finds the row, but a subsequent read still has no color. Repeatedly changing the Boolean argument, or suspecting a cache, will not resolve a missing intermediate step. Inspect each part of the path before interpreting the statement as a successful business operation.

Three inputs take different paths

This read-only example targets PostgreSQL 18. The profiles are hypothetical, and the results below are predictions from the documented function contract, not a database execution transcript. It changes no existing table and uses no array indexes.

WITH inputs(label, doc) AS (VALUES
  ('missing', '{}'::jsonb),
  ('empty', '{"profile":{}}'::jsonb),
  ('existing', '{"profile":{"color":"old","name":"Ada"}}'::jsonb)
)
SELECT label, doc,
       jsonb_set(doc, '{profile,color}', '"blue"'::jsonb, true) AS result
FROM inputs
ORDER BY label;

The result for missing remains {}. Before the function reaches the final color item, it encounters the absent profile step. The empty result is {"profile":{"color":"blue"}}: the parent exists, so the final key can be added. The existing result is {"profile":{"color":"blue","name":"Ada"}}, replacing the color while retaining its sibling name.

“Add the key if it is absent” is too broad a description of these results. An absent target key and an absent parent step have different consequences. The official jsonb_set contract explicitly requires every earlier path step to exist; otherwise the target is returned unchanged. The true argument is working, but its responsibility is narrower than the caller assumed.

Decide whether an absent parent is valid input

If profile initialization is supposed to create profile, an absent parent violates that precondition. The application can report an incomplete structure or send the data through an explicit repair process. Executing a write that returns the original value and then telling a client “color saved” mistakes a normal database return for a satisfied domain condition.

A different product contract may allow old profiles without profile to acquire a color immediately. That requires explicit parent construction. It is an application data-shape decision, not something the function can infer from its Boolean flag. In particular, distinguish an absent parent from an existing string, array or JSON null: replacing those values with an empty object can discard old information.

The next transformation deliberately accepts a narrow set of inputs. The root must be an object, and profile must either be absent or be an object. Other inputs receive a rejection status and no adoptable candidate. This is another self-contained read-only example; it does not hide a type migration inside an unrestricted merge.

WITH inputs(label, doc) AS (VALUES
  ('missing', '{}'::jsonb),
  ('object', '{"profile":{"name":"Ada"},"enabled":true}'::jsonb),
  ('scalar', '{"profile":"legacy"}'::jsonb),
  ('json-null', '{"profile":null}'::jsonb)
), checked AS (
  SELECT label, doc,
         jsonb_typeof(doc) = 'object'
         AND (NOT (doc ? 'profile')
              OR jsonb_typeof(doc -> 'profile') = 'object') AS allowed
  FROM inputs
)
SELECT label,
       CASE WHEN allowed THEN 'accepted' ELSE 'rejected' END AS status,
       CASE WHEN allowed THEN
         doc || jsonb_build_object(
           'profile',
           COALESCE(doc -> 'profile', '{}'::jsonb)
             || jsonb_build_object('color', 'blue')
         )
       ELSE NULL END AS candidate
FROM checked
ORDER BY label;

Under this policy, an absent parent is constructed. The object-valued parent's name and the root's enabled field are retained. The string and JSON-null rows are rejected. Their candidate is SQL NULL, meaning that this transformation supplies no candidate to adopt. It is not an instruction to update the stored profile to a database null. A real update flow must adopt only accepted candidates, rather than writing every returned row back indiscriminately.

Here COALESCE handles SQL NULL produced by reading an absent key. It does not turn JSON null into an empty object; the type guard is what rejects that input. If the distinction is unclear, compare JSON null with SQL NULL. The purpose of this transformation is to define the parent-object policy, rather than to redefine an API's clearing protocol.

What the two merge levels preserve

The two || operators do different work. The inner expression puts the existing profile object on the left and the new color object on the right. The new color therefore replaces the old one while other keys, such as the name, survive. The outer expression then puts the complete replacement parent back into the original root, retaining root siblings such as enabled. Each merge handles siblings at a different level.

If the inner merge is omitted and a new {"profile":{"color":"blue"}} is merged directly into the root, enabled may survive but profile.name disappears. That is not a failed recursive merge: object concatenation merges only the top level. A duplicate key takes the right-hand value, so the new parent replaces the entire old parent. The official JSON operator table states that rule explicitly. Preserving siblings at a particular level requires representing that level in the expression.

Removing the type check does not make concatenation a general object repair. Combinations involving arrays or scalars can follow array-concatenation rules instead of producing the profile shape the application needs. Narrowing the accepted inputs first makes the object-to-object behavior inspectable. More nesting requires a preservation and replacement policy at each level; adding another path item does not automatically extend this example's guarantees.

Check postconditions rather than guessing from row counts

A real update needs to establish at least two things: the input satisfies the permitted structure, and the resulting target path has the required value. UPDATE 1 says that the update processed one row. It does not prove that a deeply nested field changed from absent to present. A driver's success status cannot perform that domain check on the application's behalf.

Conversely, equality between the input and result does not, by itself, prove that the parent was absent. A profile whose color was already blue can remain equal after setting the same value again. Preserve the initial structure and inspect both jsonb_typeof(doc -> 'profile') and the result's #> '{profile,color}'. Compare the latter with the expected JSON string value, rather than checking only whether the entire object differs.

To validate the design in an owned test database, start with the two read-only examples and add an input whose color is already blue. Then replace the parent with an array, a number and JSON null, checking whether the application policy rejects each one or explicitly migrates it. Recalculate the expected result for each mutation and inspect sibling fields that should survive. These are proposed checks, not claims that the variants have already passed.

Should a string-valued parent be replaced with an empty object?

Only if an explicit data-migration contract permits it. An ordinary field update should not silently erase the old value. If "legacy" still represents an older profile format, establish its meaning, the intended conversion and failure handling before replacing it. Making the color write succeed does not establish that the existing information is disposable.

Such a migration also needs its own concurrency analysis. The read-only transformation above does not prove that reading a document into an application, editing it and writing the entire object back is safe. Nor does it implement a universal recursive patch. For this problem, keep the boundary concrete: parents must already exist or be created by an explicit object-construction policy; incompatible existing values belong to a separately defined migration.
