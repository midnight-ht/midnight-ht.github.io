Why does dependentRequired require an address when invoice is false?

dependentRequired tests presence, not truth. Compare it with guarded if/then schemas using five inputs that expose directionality, missing-property conditions and independent type checks.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-07 · Estimated read 15 min
Translations

Article

Key takeaways

  • false is still a present property value.
  • A true-only condition needs an explicit presence guard inside if.
  • Reciprocal dependencies and independent property types must be specified separately.

invoice: false still triggers dependentRequired because the keyword checks property presence, not truth. If an address is required only when invoicing is selected, use a value condition instead of treating a presence dependency as a Boolean switch.

The Draft 2020-12 dependentRequired clause defines its trigger in terms of an existing property. A field carrying false is present. The rule has not misread the Boolean; it is answering a different question. Establish whether the product wants fields to appear together or wants another field when a particular value is true.

Two complete schemas express different requirements

Suppose an interface accepts an invoice flag and an invoice address. One contract requires an address whenever the flag appears, regardless of its Boolean value. This schema expresses that presence dependency. It does not require every request to contain the flag.

{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "properties": {
    "invoice": { "type": "boolean" },
    "invoiceAddress": { "type": "string", "minLength": 1 }
  },
  "dependentRequired": { "invoice": ["invoiceAddress"] }
}

A second contract requires an address only when the flag is explicitly true. Use an if containing a presence guard, followed by a then that requires the address. This is another complete standalone schema. Combining both schemas would not make the first presence dependency disappear.

{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "properties": {
    "invoice": { "type": "boolean" },
    "invoiceAddress": { "type": "string", "minLength": 1 }
  },
  "if": {
    "required": ["invoice"],
    "properties": { "invoice": { "const": true } }
  },
  "then": { "required": ["invoiceAddress"] }
}

The conditional subschema rules use the validity of if to decide whether then applies. They do not perform a programming language's truthiness conversion. Here the input object must satisfy both the condition's presence requirement and its constant-value constraint. The outer Boolean type constraint remains independently active.

The inputs and outcomes below are manually derived expectations, not validator results. Adoption requires a tool supporting the declared dialect and a record of its actual version and observed behavior. Do not turn these predictions into a claimed passing test report.

Five inputs reveal the difference

{} is expected to pass both schemas. It contains no flag, so the first dependency is not triggered. It also fails the second schema's conditional required, so then does not demand an address. If every request must declare its invoice choice, an outer required would express that additional requirement. Neither current schema already says so.

Consider {"invoice":false}: it is expected to fail the presence-dependency schema and pass the value-condition schema. Presence triggers the former's address requirement. A value other than true prevents the latter from applying that requirement. This row distinguishes the policies directly; a true-only test cannot establish that the schemas are equivalent.

{"invoice":true} is expected to fail both because each requires an address. {"invoice":true,"invoiceAddress":"A"} is expected to pass both. The successful input does not prove that the correct policy was selected: different implementations can agree on one happy path. Discriminating cases matter more in a schema review.

The fifth input is {"invoiceAddress":"A"}, which both schemas allow. An address does not automatically require the flag. A form that prefills an address before the user submits an invoice choice may need precisely this behavior. If the business prohibits that combination, declare the reverse requirement explicitly rather than adding symmetry for its own sake.

Does an address require invoice in return?

Only if the reverse dependency is explicitly declared. The official conditional-validation guide also emphasizes that dependencies are not bidirectional. Adding invoiceAddress: ["invoice"] to dependentRequired rejects the address-only input. That changes the policy; it does not repair an implicit rule the validator forgot to enforce.

The reverse dependency does not require a true flag either. It requires presence, and false is still a present Boolean value. If an address must imply a true invoice choice, express a value condition as well. Conflating required presence, required value and reciprocal relationships makes the next form change harder to reason about.

Preserve the presence guard when switching to if

A common repair keeps only properties: {"invoice":{"const":true}} as the condition. But properties does not require the property to exist. An object without the flag can satisfy that condition, activating then and requiring an address. Switching to a value condition has then accidentally rejected the previously allowed empty object.

Placing required: ["invoice"] inside if limits when the branch applies. Placing it at the outer level requires the flag in every input. Those are different requirements. Decide whether an empty object is allowed before moving a presence constraint merely to satisfy the current test.

Also, invoice: null triggers the presence dependency while independently violating the outer Boolean type constraint. Supplying an address does not make the entire schema valid. This distinguishes which rules activate from whether the whole input passes. A final failure alone does not prove that the address was the sole problem, and Boolean type validation does not convert null into false.

Address shape has independent constraints too. A true flag plus an empty string has a present address but fails minLength. A false flag plus a numeric address still violates the outer property type, even though the true-only condition is inactive. A condition adds requirements; it does not disable other constraints already on the root object.

Validate the policy with discriminating cases

Keep the five baseline inputs, then add true plus an empty address, false plus a numeric address, and null plus an address. Record rule activation separately from overall validity. Error messages should distinguish missing fields, wrong types and empty addresses instead of reporting every failure as “invoice address required.” Recalculate empty-object and address-only outcomes whenever the rules change.

Validation decides validity; it does not populate a default flag, generate an address or modify the input. For the division of responsibility between client and server, see form validation and server authority. The immediate decision is explicit: use presence dependencies for fields that must appear together, a guarded value condition for a true-only branch, and reciprocity only when the domain requires it.
