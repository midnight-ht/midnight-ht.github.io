Why does History pushState change the URL without firing popstate?

Separate history mutation from traversal using a complete two-view page, including initial state and direct-load boundaries.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-07 · Estimated read 16 min
Translations
zh-CN en

Article

Key takeaways

  • History mutation does not render the application.
  • Button navigation and traversal share a defined view rule.
  • Same-document updates do not prove reload availability.

Calling pushState adds an entry but does not itself fire popstate. Render the forward action explicitly and use the same rendering entry for history traversal. If the address changes to a detail view while the body remains a summary, identify who renders the new view rather than waiting longer.

The popstate reference distinguishes mutation from traversal: pushState and replaceState alone do not fire the event; Back and Forward can. It is not a subscription that redraws the application after every history change.

Keep three related states aligned

A teaching directory has summary and document views. Its URL supports copying and reentry, history.state supports restoration of an entry, and visible content identifies the current view. They are related, but browsers do not maintain the application's correspondence automatically.

The shared HTML history-writing algorithm serializes state and checks document and URL-rewrite conditions. It does not render application headings, lists or errors. Page titles and view identity covers naming; this article connects explicit navigation and traversal to one rule.

Decide which actions deserve entries. Moving to a returnable view can use push; correcting the current entry or initializing it can use replace. One entry per keystroke can make Back traverse unwanted intermediate input, while replacing every action can erase expected return points. The task determines that choice.

A complete same-path query-view sample

This HTML has not been executed. Serve the file over same-origin HTTP before opening it; do not assume identical rewrite conditions for file URLs. The example changes only its current file's query and has no form, fetch or application endpoint. It is not a general router.

<!doctype html>
<html lang="en">
<meta charset="utf-8">
<title>Teaching directory</title>
<nav aria-label="Teaching views">
  <button type="button" data-view="summary">Summary</button>
  <button type="button" data-view="documents">Documents</button>
</nav>
<main><h1 id="heading"></h1><p id="note"></p></main>
<script>
const views = new Map([
  ['summary', ['Summary', 'This is a teaching directory summary.']],
  ['documents', ['Documents', 'Teaching materials only; no real application.']]
]);
const [menu, heading, note] = ['nav', '#heading', '#note'].map(
  selector => document.querySelector(selector)
);
function fromURL() {
  const key = new URL(location.href).searchParams.get('view');
  return views.has(key) ? key : 'summary';
}
function render(key) {
  const [title, text] = views.get(key);
  document.title = title + ' | Teaching directory';
  heading.textContent = title;
  note.textContent = text;
}
const initial = fromURL();
history.replaceState({ view: initial }, '', location.href);
render(initial);
menu.addEventListener('click', event => {
  if (!(event.target instanceof Element)) return;
  const button = event.target.closest('button[data-view]');
  if (!button || !menu.contains(button)) return;
  const key = button.dataset.view;
  if (!views.has(key)) return;
  const next = new URL(location.href);
  next.searchParams.set('view', key);
  history.pushState({ view: key }, '', next);
  render(key);
});
window.addEventListener('popstate', event => {
  const saved = event.state?.view;
  render(views.has(saved) ? saved : fromURL());
});
</script>
</html>

Initialization reads an allowed URL view, registers a small state on the current entry and renders it. Button navigation writes then renders directly. Traversal validates saved state and otherwise uses the URL fallback. It never blindly dereferences event.state.view, so absence alone does not cause a property-access failure.

The fallback accepts only two known views; it is not a rule to trust arbitrary route data. A real application must validate identity, authorization and loading results before showing a record. An identifier in history.state grants no server access. This sample supplies no such capability.

Remove the final render from the button path as a paper counterexample. The address and state change, but this push does not supply the missing popstate later. Conversely, updating a title only on button clicks leaves traversal capable of restoring a URL beside a stale title. Inspect both entry paths.

Label entries on paper to distinguish the summary button from browser Back. Call the initial summary A: initialization replaces its state without adding an entry. Clicking Documents creates B; clicking Summary creates C. Back from C should restore Documents at B, even though the latest button requested Summary. Another Back reaches the original summary at A. Two entries may show the same view while occupying distinct positions in history.

If Documents merely corrects a display option, replacing B updates that entry and Back still reaches A. Pushing the correction instead adds another return point. This does not require storing a whole page: a view key sufficient for the stated restoration rule is enough. Mark each acceptance step as adding, correcting or traversing an entry before comparing its URL and content. Similar screenshots alone cannot establish identical history behavior.

Can history state contain DOM nodes or functions?

It is not arbitrary object storage. The algorithm serializes for storage, and the method reference identifies DataCloneError for nonserializable state. Small explicit view data is easier to reason about than a component or event object. Do not expect preserved functions, DOM identity or external resources.

Serializable also does not mean suitable for secrets. Browsers can retain state, and URLs can enter history, sharing and logs. A real product must choose acceptable fields. These teaching keys are public view names, not a sensitive-storage design. Navigation state restores a basis for a view, not every business fact.

The original entry may have no application state. Initialization and legacy fallback therefore serve separate purposes. ReplaceState registers the current entry without adding a duplicate home entry. Retaining a URL fallback handles other entries; an unknown state should not silently become the last successful business object.

Why can reload fail after a successful URL update?

The pushState method reference says the new URL is not loaded immediately but may be loaded later. A working client transition does not establish a matching server or static-host route. The sample keeps its path and changes a query to limit that prerequisite.

A real new path needs direct-entry, reload, error-route and relative-resource checks. URL base resolution covers the independent path semantics. A generic200 fallback is not proof that the intended view restored; inspect identity and content as well.

Proposed verification starts with an entry lacking application state, then visits Documents and Summary and uses Back and Forward. Record URL, state, title and body at every step. Add unknown views and null state, then reload separately. These paths have not been run; no event counts are reported.

A handoff should identify who writes history, who renders each entry route and what appears on failure. Explicit mutation and traversal notification need one defined state rule to keep the address and visible view meaningfully recoverable.
