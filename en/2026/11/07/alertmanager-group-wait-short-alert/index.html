Why can Alertmanager receive a firing alert yet send no notification for it?

Use a local receiver and short-lived/persistent controls to explain Alertmanager group timing and initial completeness.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-07 · Estimated read 17 min
Translations
zh-CN en

Article

Key takeaways

  • Resolution before the new-group wait can mean no notification.
  • Initial group waiting differs from later group processing.
  • Zero waiting does not guarantee a complete first notification.

If an alert resolves before its new group's group_wait expires, Alertmanager sends no notification for that alert. Identify the group and resolution time before treating intentional waiting as delivery failure. Receiving a firing alert does not create a historical notification that must later be replayed.

The wait belongs to a new group

The Alertmanager configuration reference defines group_wait before a new group's first notification and explicitly excludes alerts resolved before that wait finishes. Waiting allows related or inhibiting alerts to arrive and reduces short-lived noise. The online reference was checked on November 6, 2026. No alerting system was contacted.

An alert arriving and resolving twenty seconds later under a thirty-second new-group wait can therefore produce no notification by design. Silence state, receiver failure, or upstream firing are not established by that absence. Preserve arrival evidence and group identity before choosing a cause.

The actual route and grouping labels matter. Here cluster and alertname define the group, allowing different instances to share a notification. A label or route change can create a different group or inherited timing configuration. Identical displayed alert names alone do not establish a shared waiting origin.

A complete local-only fixture

This configuration and its programs were not executed. They require an isolated Alertmanager, Python's standard library, unused local ports, and a practice-only data directory. There is no external receiver, real alert, or silence. The fixture exercises notification processing without creating a service incident.

# alertmanager.yml
route:
  receiver: local
  group_by: [cluster, alertname]
  group_wait: 30s
  group_interval: 2m
  repeat_interval: 10m
receivers:
  - name: local
    webhook_configs:
      - url: http://localhost:18555/
        send_resolved: true

Save this as receiver.py. It prints received teaching JSON and returns an HTTP success. Those records could become receipt evidence after execution; none were produced here.

import json
from datetime import datetime, timezone
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

class Receiver(BaseHTTPRequestHandler):
    def do_POST(self):
        size = int(self.headers.get("Content-Length", "0"))
        payload = json.loads(self.rfile.read(size))
        print(datetime.now(timezone.utc).isoformat(), payload, flush=True)
        self.send_response(200)
        self.end_headers()

ThreadingHTTPServer(("localhost", 18555), Receiver).serve_forever()

Run python receiver.py in one terminal, then start a separate Alertmanager from the practice directory in another. Check that the installed program supports these options and that both processes belong to the fixture. Do not submit these alerts to an existing production instance.

alertmanager --config.file=alertmanager.yml \
  --storage.path=./alert-data --web.listen-address=localhost:19093

Save the driver below as driver.py and run it in a third terminal only after setup is ready. The official API v2 specification defines labels, startsAt, and endsAt. Printed submission status is not notification receipt. A failed submission should stop the experiment with its actual error retained.

import json
import time
from datetime import datetime, timedelta, timezone
from urllib.request import Request, urlopen

endpoint = "http://localhost:19093/api/v2/alerts"

def current_utc():
    return datetime.now(timezone.utc)

def as_timestamp(value):
    return value.isoformat()

start = current_utc()

def alert(cluster, instance, begins, ends):
    return {"labels": {"alertname": "TimingProbe", "cluster": cluster,
                       "instance": instance},
            "startsAt": as_timestamp(begins), "endsAt": as_timestamp(ends)}

def post(items):
    request = Request(endpoint, data=json.dumps(items).encode(),
                      headers={"Content-Type": "application/json"}, method="POST")
    with urlopen(request, timeout=5) as response:
        print("submission-status", response.status, flush=True)

post([alert("A", "one", start, start + timedelta(minutes=5)),
      alert("B", "one", start, start + timedelta(minutes=5))])
time.sleep(20)
post([alert("A", "one", start, current_utc())])
time.sleep(25)
later = current_utc()
post([alert("B", "two", later, later + timedelta(minutes=5))])

A's same label identity resolves before the initial wait ends. B remains active beyond it, then receives a second instance in the existing group. Sleep durations are planned inputs, not precise observed event times. Correlate actual submissions, Alertmanager state, and receiver times. Stop the two owned foreground processes at the end and preserve inputs and logs; process termination does not replay past notifications.

Where do the two timers start?

The paper expectation is no notification for A, while B enters initial notification processing after the new-group wait. The later B instance follows the subsequent group_interval path rather than starting its own thirty-second group_wait. Processing and HTTP receipt remain separate, so adding configured durations does not prove an exact delivery second.

The reference describes group_interval as recurring checks after the first wait. Newly firing or resolved alerts affect subsequent notifications; otherwise the repetition timer is considered. The ten-minute repeat_interval here is not a replay switch for every short event that was never sent.

Retain complete A and B labels, group creation, resolution or join times, and identities in each received JSON document. One B notification does not explain A by itself. API success does not establish route or receiver operation either. Persistent B is a same-path control that helps distinguish a broken fixture from the intentional short-alert behavior.

Do not use startsAt alone as the new-group waiting origin. That field describes the alert; the current route must actually receive and process it. A twenty-second driver sleep does not establish twenty seconds of observed group state when submission is delayed. Preserve request/response times and group observations before classifying early resolution.

Use three diagnostic branches. A rejected submission leaves the fixture prerequisite unmet. An accepted A that resolves during its wait, with persistent B received normally, supports the short-alert explanation. If B also remains active without receipt, inspect effective routing, suppression, and HTTP delivery errors; A’s expected silence cannot validate the whole path.

One receiver URL does not prove identical routing. Check effective configuration, inherited timers, and complete group labels. Repeated practice should use distinct recorded identities rather than mistake an old group’s state for a newly created group.

Inspect identities and statuses inside received JSON, not just HTTP request count. One notification can include multiple instances, and delivery processing can produce repeated attempts. Request count is not alert count. Full synthetic samples make that relationship checkable without recommending indiscriminate logging of sensitive real-alert contents.

Does setting group_wait to zero guarantee a complete first notification?

No. Related or inhibiting alerts may arrive later. The reference warns that too-short waiting can produce an incomplete initial set or miss inhibition that would have applied had its source arrived. Removing waiting does not guarantee timely networking or receiver success.

Choose by response risk. An urgent actionable alert may justify early notification with later additions; a brief fluctuation may not justify interrupting responders. Compare policies under the actual labels and route rather than declaring zero or a documented default universally best. Silences, inhibition, grouping, and upstream rule duration govern different objects.

The October 31 silence and rule-state article addresses explicit notification suppression. This question concerns new-group timing. Establish group membership, wait completion, and resolution timing before choosing between a timer change and a delivery repair.
