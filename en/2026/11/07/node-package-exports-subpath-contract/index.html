Why does Node reject a package subpath when the file exists?

exports exposes package-specifier entries, not every physical file path. A no-install fixture separates public keys, targets, historical compatibility and filesystem access.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-07 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • A physical file does not automatically expose its package subpath.
  • main does not bypass an existing exports map to restore undeclared entries.
  • Export encapsulation maintains public interfaces, not file confidentiality.

A file can exist inside a package and still fail to import through a package subpath. exports defines the public package-specifier entry points. An undeclared subpath can produce ERR_PACKAGE_PATH_NOT_EXPORTED; that does not mean its target file is missing from disk.

The Node.js package-entry-point documentation separates this encapsulation from filesystem existence. The retrieved page was titled Node.js v24.22.2, and its snapshot is preserved. The version-line URL can change; it is not a permanently pinned “latest” claim. The local example below requires no dependency download or installation and is not presented as an executed test.

Build a small package without a registry

Create demo inside a new, owned empty directory and add the files shown below. Do not overwrite an existing project's node_modules. Placing this fixture package manually gives Node's package resolver a concrete input without publication or installation commands.

demo/
  package.json
  app.mjs
  node_modules/
    contract-demo/
      package.json
      public.js
      internal.js
      lib/
        feature.js

The complete outer demo/package.json is {"type":"module"}. The package's own package.json below defines the root and one logical feature entry. Its version identifies the hypothetical package; it is not a runtime-version requirement.

{
  "name": "contract-demo",
  "version": "1.0.0",
  "type": "module",
  "exports": {
    ".": "./public.js",
    "./feature": "./lib/feature.js"
  }
}

Each JavaScript file contains one complete line. Put export const name = "public"; in public.js, export const feature = "feature"; in lib/feature.js, and export const internal = "internal"; in internal.js. Create all three; omitting the internal file would manufacture a different, missing-file failure.

Finally, place this complete program in demo/app.mjs. Two static imports exercise public entries. The dynamic imports try an internal file and the physical target path of the public feature. Errors are printed as codes, rather than silently swallowed and reported as universal success.

import { name } from 'contract-demo';
import { feature } from 'contract-demo/feature';
console.log({ name, feature });

for (const specifier of [
  'contract-demo/internal.js',
  'contract-demo/lib/feature.js'
]) {
  try {
    await import(specifier);
  } catch (error) {
    console.log(specifier, error.code);
  }
}

After creating the files, run node demo/app.mjs if desired. The export map predicts that the root and logical feature load, while the two undeclared package subpaths report the export error. This is an expectation to verify, not a fabricated terminal transcript. A missing-file, syntax or other actual error requires checking the fixture rather than attributing every failure to exports.

Public keys do not expose every physical alias

The logical name contract-demo/feature maps to lib/feature.js. It does not automatically expose contract-demo/lib/feature.js. Consumers use the map's keys; the right-hand path identifies the package-internal target. A file can have a deliberately chosen public name without exposing its physical path as another entry.

That supports internal rearrangement while maintaining promised import names. Changing a public key or the interface provided by its target can still break consumers. Review internal file movement separately from public-contract changes instead of checking only whether a similarly named file remains in the directory tree.

Do not immediately respond to the error by adding a wildcard exposing every path. That may restore one caller while giving consumers many more internal paths to depend on. Withdrawing those later creates another compatibility burden. Establish which paths were supported before choosing explicit preservation or consumer migration.

Can main restore an unexported subpath?

No. Node versions supporting exports give the export map precedence over main. Keeping the old root-entry field does not automatically restore an undeclared deep path. A working root import establishes that the root key resolves, not that every file in the package remains public.

When introducing exports into an existing package, inventory genuinely supported historical entries, including package-metadata entries consumers may read. Adding only the dot key is not a behavior-neutral cleanup. Preserve previously documented deep entries explicitly or treat their removal as an interface change with migration guidance, rather than blaming consumer caches.

Compatibility checks can give each promised entry its own import probe and record expected versus actual error codes. A filesystem inventory is not a public-API inventory. Nor does one application avoiding deep imports prove that every consumer is unaffected. The compatibility promise needs a defined audience and entry set.

Export encapsulation does not protect secrets

The same official entry-point section explicitly says this is not strong encapsulation. Direct absolute file paths can bypass package-specifier encapsulation. An unexported file is not a safe place for secrets in a distributed package.

These are different goals. An export map helps maintain supported import interfaces. File-access permissions and secret distribution are separate boundaries. A rejected package subpath proves that this resolution route does not expose the name; it has not imposed access controls on reading the package's files. Giving the error a security meaning it does not possess undermines later architectural decisions.

The example is also limited to Node package-specifier resolution. It does not directly establish browser import-map or compiler type-resolution behavior. For another name-to-target mechanism, see how import-map scopes affect module resolution. Related mechanisms still need their own environments and guarantee boundaries checked.

Test the explanation with one export change

In a copy of the fixture, add only "./internal.js": "./internal.js", leaving physical files unchanged. Predict that the internal-file import becomes resolvable, while the physical feature-path import does not automatically become public. The experiment distinguishes API expansion from file creation; changing many files at once and merely checking for errors obscures that distinction.

Conversely, delete the public feature's target file in the fixture copy. Its public key can remain declared while loading fails because the target is unavailable. Permission through the export map guarantees neither file existence nor syntax nor interface contents. Check the public key, target file and load outcome separately to locate a particular error.

If executed, record the actual Node version and complete inputs, labeling only observed results as measured. Clean up only the newly created owned directory. The maintenance decision is to define public names and historical promises, then verify them with focused import probes, rather than letting physical file existence define the entire public package contract.
