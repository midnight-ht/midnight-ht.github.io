How does OpenAPI require two security schemes together?

Schemes in one requirement object are AND; objects in the security array are OR. A credential matrix distinguishes grouping, overrides and empty structures without claiming deployed authorization.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-07 · Estimated read 15 min
Translations

Article

Key takeaways

  • All schemes within one requirement object must hold; array objects are alternatives.
  • Operation security overrides the root, and an empty scheme value is not anonymous access.
  • Correct document semantics do not prove server authentication or authorization enforcement.

To require two security schemes together in OpenAPI, put them in the same Security Requirement Object. Splitting them into two objects in the security array declares alternatives. The grouping changes which credential combinations satisfy the interface contract.

The OpenAPI Security Requirement Object distinguishes those two levels explicitly: all schemes in one object must be satisfied, whereas only one of the objects in the array needs to be satisfied. This example is pinned to that version. Other versions in the documentation navigation do not change its dialect, and a security declaration is not evidence that a gateway enforces it.

Define the four combinations first

Suppose an endpoint needs both a user's Bearer credential and a client's API key. Requiring both means that only the combination in which both schemes are valid satisfies the declaration. One valid scheme alone is insufficient. An endpoint offering either access method needs a different Boolean grouping, rather than another name for the same structure.

The complete definition below describes hypothetical endpoints. It contains no real credentials, deploys no service and sends no requests. /both inherits the root conjunction; /either explicitly changes it to alternatives; /health removes the inherited security declaration. The response entries complete the definition, rather than proving that a server returned those responses.

openapi: 3.1.1
info:
  title: Credential contract example
  version: 1.0.0
security:
  - bearerAuth: []
    clientKey: []
paths:
  /both:
    get:
      responses:
        '200': { description: OK }
  /either:
    get:
      security:
        - bearerAuth: []
        - clientKey: []
      responses:
        '200': { description: OK }
  /health:
    get:
      security: []
      responses:
        '200': { description: OK }
components:
  securitySchemes:
    bearerAuth:
      type: http
      scheme: bearer
    clientKey:
      type: apiKey
      in: header
      name: X-Client-Key

The declared matrix is straightforward. With neither valid scheme, neither /both nor /either is satisfied. With only valid Bearer or only a valid API key, /either is satisfied and /both is not. With both valid, both declarations are satisfied. This checks the document's Boolean relationships. It is not a successful-request transcript and does not establish permission to access a particular business record.

When reading the YAML, first identify each object introduced by a dash, then count the schemes within it. The root requirement used by /both contains two schemes in one object: AND. /either places them in two separate objects: OR. Seeing both names somewhere in the definition is insufficient, and an array does not inherently mean “all of these.”

Empty structures at three different levels

An operation's security: [] removes the root security declaration for that operation. The health endpoint uses this form. Omitting operation-level security instead leaves the root declaration applicable. Interpreting the empty array as “no extra rule here, so keep inheriting” reverses its meaning.

security: [{}] contains an empty requirement object. The specification permits that object to support anonymous access. Because array entries are alternatives, an anonymously satisfiable object supplies an unauthenticated route through the declaration. Adding a Bearer requirement beside it does not make Bearer mandatory. Inspect the entire array for such alternatives.

The third form is bearerAuth: []. The empty list is the value attached to a named scheme; that scheme is still present in the requirement object and still required. Confusing it with an empty operation-level array would make the example's /both declaration appear to require no authentication. Identical punctuation at different structural levels does not carry an identical meaning.

This example uses HTTP Bearer and a header API key, with no OAuth scope list. It does not justify the version-independent claim that every non-OAuth scheme array must be empty. The specification version and scheme type remain relevant conditions. These two schemes and their grouping are enough to resolve this interface question.

Does operation-level security append to root requirements?

No. Operation-level security overrides the root declaration. If the root requires both Bearer and an API key, an operation declaring only Bearer has restated its own requirement. It has not retained the root conjunction and added Bearer again.

When reviewing an exception, inspect what inheritance it replaces as well as which name the change introduces. /either deliberately changes the policy. If the business does not permit API-key-only access, that override should be rejected in the specification. Writing the expected matrix first is more reliable than inferring product intent from indentation.

Does bearerAuth: [] allow anonymous access?

No. The object still requires bearerAuth; its list value is empty. {} is an anonymous alternative, while an empty operation security array removes inheritance at another structural level. Identify the level before interpreting an empty value.

The distinction also supports useful mutation checks. Split the root's combined requirement into two objects and recalculate the two single-valid-credential cases. Then add {} to /either and reconsider the no-valid-credential case. These are expectations derived from the specification, not executed tests or a gateway acceptance report.

Requirements should also distinguish allowing anonymous access from deciding what anonymous users may see. An empty requirement object answers whether a security scheme is required; it does not define public response fields. Removing inheritance for a liveness endpoint does not imply that diagnostic information elsewhere should be public. Endpoint responsibilities and authorization rules must define that resource scope.

When root requirements change, revisit operation exceptions too. An explicit override does not automatically acquire a scheme newly added at the root. Review whether it intentionally retains an earlier policy or has missed the new requirement. A root-only edit can otherwise leave exceptions outside the intended change.

A valid document does not establish deployed authorization

Security requirements describe named schemes and their combinations. They do not automatically prove signature verification, revocation checks, tenant isolation or data permissions. A version-compatible tool can check document structure. The four combinations can then become real request tests against an owned service. Invalid credentials need separate tests too: the presence of a string does not establish that a scheme is satisfied.

Even two valid credentials do not necessarily authorize the target resource. This Boolean matrix concerns the declared combination of schemes, not the complete business authorization model. A tool may read the definition without connecting it to the running middleware. The document can therefore be correct while the deployment is wrong. Record observed request outcomes and configuration versions rather than inferring runtime behavior from a definition file.

For a related boundary between API metadata and runtime enforcement, see why OpenAPI readOnly does not filter server input. The review should reach two explicit conclusions: whether the declared combination matches the requirement, and whether the deployed service has been independently verified. Passing the first check cannot substitute for the second.
