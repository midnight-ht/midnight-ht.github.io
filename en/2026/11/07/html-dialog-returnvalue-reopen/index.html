Why can a canceled reopened HTML dialog retain the previous result?

Use current dialog closing rules to separate retained values, per-open initialization and omitted versus explicit results.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-07 · Estimated read 16 min
Translations
zh-CN en

Article

Key takeaways

  • ReturnValue retains its assigned value across openings.
  • Omitted and explicitly empty close results differ.
  • Associate each decision with its current object.

ReturnValue retains its last assigned string. Reopening does not make it a fresh answer; establish a per-open initial value and distinguish decisions from dismissal. A previous accepted value must not turn a later cancellation into renewed consent.

The HTML dialog definition returns the last assigned value and initializes it to an empty string when the element is created. Creating a node and showing that node again are different operations. Closing assigns a new returnValue only when the supplied result is not null.

Trace two openings, not one close

A local teaching dialog closes with accepted or declined. After acceptance, the property contains accepted. If the next opening merely calls showModal and later closes without a supplied result, the earlier value can remain. A close event announces closure, not an explicit decision belonging to this opening.

A longer enum does not solve missing initialization. Distinguish node lifetime, opening, current object and decision. Keeping the node alive cannot make a previous result a new authorization. This article implements no real consent or agreement service.

Modal focus workflow covers entry, internal navigation and return. Result ownership is separate: returning users to the correct control does not prove the string belongs to their latest operation.

Establish an undecided state explicitly

This complete HTML has not been executed. It has no form or saving request. Every opening clears the result; buttons assign explicit decisions. Other accepted closure paths leave the current empty value. The opener stays disabled until the close notification is processed, avoiding a new reset before the previous notification finishes.

<!doctype html>
<html lang="en">
<meta charset="utf-8">
<title>Teaching dialog results</title>
<button id="open" type="button">Open teaching decision</button>
<dialog id="decision" aria-labelledby="question">
  <h2 id="question">Use this teaching preference?</h2>
  <p>This records a local choice, not a real setting.</p>
  <button type="button" data-result="accepted">Use it</button>
  <button type="button" data-result="declined">Do not use it</button>
</dialog>
<p id="status" role="status">No decision yet</p>
<script>
const [opener, dialog, status] = ['open', 'decision', 'status'].map(
  id => document.getElementById(id)
);
const say = text => { status.textContent = text; };
const on = (node, type, handler) => node.addEventListener(type, handler);
const setAvailable = available => { opener.disabled = !available; };
on(opener, 'click', () => {
  if (typeof dialog.showModal !== 'function') {
    say('The required dialog method is unavailable');
    return;
  }
  dialog.returnValue = '';
  setAvailable(false);
  try {
    dialog.showModal();
  } catch (error) {
    setAvailable(true);
    say(`Opening failed: ${error.name}`);
  }
});
on(dialog, 'click', event => {
  if (!(event.target instanceof Element)) return;
  const button = event.target.closest('button[data-result]');
  if (!button || !dialog.contains(button)) return;
  const result = button.dataset.result;
  if (result === 'accepted' || result === 'declined') dialog.close(result);
});
on(dialog, 'close', () => {
  const result = dialog.returnValue;
  say(result === '' ? 'No explicit decision this time' : `Local result: ${result}`);
  setAvailable(true);
  if (opener.isConnected && !opener.disabled) opener.focus({ preventScroll: true });
});
</script>
</html>

Disabling the opener changes the premise for focus restoration. Re-enabling it after closure alone does not establish that focus returned. The standard closing algorithm attempts focusing steps for the previously focused element before queuing the element task that fires close. This sample disables the button before opening, potentially affecting the saved focus identity, and it remains unavailable during the native restoration attempt. Enabling it in the later notification cannot replay that earlier step.

The close callback therefore restores availability, checks that the opener is connected and enabled, and explicitly calls focus. This is an application-owned handoff, not a guarantee derived from returnValue. A real product that removed the original button needs another meaningful destination; this sample skips an invalid node. Record activeElement separately from result text: a correct decision string can coexist with lost keyboard position. This focus path has not been run, so the added call is not an accessibility pass.

The proposed sequence accepts once, reopens and uses an actual supported close request, then checks the empty-result branch. Repeat after declining. No Escape interaction or logs were captured here. If a browser does not accept the close request, record that the dialog remains open rather than reporting successful cancellation.

The explicit reset agrees with the official returnValue example. Empty string is this sample's contract, not a required representation for every product. Another undecided value can work if it stays distinct from explicit decisions and is initialized consistently. “No choice” and “keep the previous choice” must not merge accidentally.

Only two explicit values are accepted here. Visible labels can be translated without letting arbitrary words determine internal actions. Adding “Decide later” needs a choice about whether it is a distinct result or dismissal; calling close without a result must not inherit an old acceptance.

Do close() and close("") produce the same result?

No. Omitting the result leaves the previous value unchanged; an explicit empty string assigns an empty result. The algorithm tests whether the result is null, not whether a string is truthy. An empty string is still a supplied result.

For an isolated comparison, assign accepted, then close without an argument. In another open dialog with the same prior value, call close with an empty string. Compare only when the dialog is open and the closing algorithm actually runs. A no-op on an already closed dialog is not a counterexample to the assignment rule.

Do not substitute visual hiding for closure. The standard identifies consequences of directly removing open, including no close event and potentially retained modal document blocking. Result processing and cleanup can both be bypassed. Popover dismissal policy concerns a different overlay contract, not dialog results.

Associate the decision with this opening's object

If the component later handles applications A and B, clearing the value alone does not establish write-back identity. A handler should not consult a mutable global current-application variable after closure. Capture an opening's identity and pass the decision with it; invalidated objects need rejection or reconfirmation.

That is application design, not a service supplied by returnValue. A string contains no version, permission or server receipt. This example only updates local text. Real asynchronous processing needs explicit rules for another opening, failure and retained decisions.

Proposed verification retains the complete two-opening sequence, values before opening and during close, object identity and actual closure method. Include supplied, omitted and empty results, rejection and unaccepted close requests. No browser or real-consent record is claimed. Define undecided state per opening and associate the resulting decision with that opening's object.
