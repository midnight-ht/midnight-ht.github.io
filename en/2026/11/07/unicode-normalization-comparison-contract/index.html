Preserve the name and define its Unicode comparison key separately

Preserve original names and derive NFC comparison keys, using five independent expectations to examine compatibility folding, collisions and concatenation.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-07 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • Canonical equivalence, compatibility equivalence and record identity are distinct decisions.
  • A derived key needs a field purpose while originals remain available for display and rebuilding.
  • Joining independently normalized fragments can require normalization of the complete result.

A multilingual name search can preserve the original input and derive a separate Unicode comparison key. Identical-looking text need not contain identical code sequences. Choosing a normalization form does not by itself define identity, case handling or security. Specify which differences the field may merge before deciding how its comparison key is generated and maintained.

Identical rendering is not strict equality

An é can be represented by one code point or by e followed by a combining acute accent. JavaScript strict string equality does not merge those sequences merely because they look alike. The decision is not simply whether to add a sorting comparator. Decide whether the application wants canonical equivalence, compatibility equivalence, case-insensitive matching or some other relation.

Unicode Standard Annex #15, Unicode Normalization Forms distinguishes canonical and compatibility equivalence. The inspected document is Unicode 18.0.0, revision 58, dated 12 August 2026. NFC and NFD preserve compatibility distinctions. NFKC and NFKD apply compatibility decomposition and can erase formatting distinctions. The annex explicitly cautions against applying those forms blindly to arbitrary text.

The String.prototype.normalize specification accepts NFC, NFD, NFKC and NFKD, defaults to NFC and throws RangeError for another form name. That link points to the current ECMAScript 2027 draft snapshot, not a promise about Unicode data in deployed browsers. The following fixture uses long-established characters rather than assuming that every device implements new Unicode 18 behavior.

Keep the original and derive a key

Assume name search should merge canonically equivalent spellings while preserving the input for display. This complete read-only example has not been executed. It writes no database, accesses no account and grants no permission from a comparison result. Escapes identify the exact input sequences rather than relying on their rendered appearance.

const a = '\u00E9';
const b = 'e\u0301';
const original = [a, b, '\uFF21', 'A'];
const byForm = new Map(
  ['NFC', 'NFKC'].map(form => [
    form, original.map(text => text.normalize(form))
  ])
);
const keys = byForm.get('NFC');
const compatibility = byForm.get('NFKC');
const fragments = ['e', '\u0301'].map(text => text.normalize('NFC'));
const joined = fragments.join('');

console.log([
  a === b,
  keys[0] === keys[1],
  keys[2] === keys[3],
  compatibility[2] === compatibility[3],
  joined === joined.normalize('NFC')
]);

The five independently specified results are false, true, false, true and false. The first two distinguish original sequences from NFC keys. The third and fourth compare fullwidth capital A with ordinary A: NFC preserves their difference, while NFKC merges this compatibility distinction. The last result concerns concatenation, discussed below. This is an expected array derived from the rules, not captured runtime output.

The original array retains all four strings. Keys serve only the declared search purpose. Matching keys need not delete or overwrite either original record: both can be candidates located through actual record identifiers. A uniqueness requirement needs an authoritative collision policy. Frontend search similarity cannot establish that two records describe one person.

Why NFKC is not universal cleaning

Merging fullwidth A into ordinary A can suit a restricted code field without being appropriate for every name, title or text with meaningful formatting. Retaining original input permits later reinterpretation. Destructive replacement can make an unwanted merge impossible to reverse. Compatibility folding belongs in the field contract rather than a global “make text uniform” helper.

A negative design applies NFKC to original names, search keys and account identifiers, then automatically merges records with colliding keys. Correct API output does not establish shared identity. Normalization selects a representation within an equivalence relation. It does not detect all lookalike attacks or supply every case, language-conversion or authorization rule.

The existing article on Collator ordering policy addresses language order and ties. Here the question is how to construct a representation with a defined comparison purpose. A zero Collator result, equal NFC keys and identical user records are three different judgments. The interface can show approximate candidates while final actions continue to carry stable record identity.

Inspect sequences rather than screenshots

Planned validation should retain the original value, code-point representation, selected form, key and matching records. Check the five expectations against frontend and backend contracts. A screenshot showing two identical é glyphs cannot establish the values. Record actual runtime and Unicode-data conditions across environments and test a shared controlled fixture; one browser does not establish every receiving system’s behavior.

An existing index migration also needs collision inspection. An old index may distinguish the two é sequences while the new key merges them. A search index can retain multiple candidates with useful context; a unique field needs a separate conflict decision. Do not silently discard a later record to make migration finish, or rewrite originals before investigating which distinctions need preservation.

Version information matters for recovery too. A client using a new comparison policy with an old server index can preview a match that submission cannot locate. Include key policy and index version in release, rollback and rebuilding plans, keeping originals available for regeneration. No index migration or cross-runtime compatibility test has been executed here.

Must I normalize again after joining two normalized fields?

Yes, if the contract requires the complete key to be in the selected normal form. The Unicode annex explains that normalization forms are not closed under arbitrary concatenation. An independently NFC e followed by an independently NFC combining acute accent can still compose to é. That explains the fixture’s fifth false result; it does not mean normalize is unstable.

Generate the comparison key from the final assembled input. An optimization that processes fragments needs real boundary rules and validation, rather than an assumption that processed parts guarantee a processed whole. Separators and their escaping are another independent concern: different field combinations can otherwise produce the same string. Normalization does not define a compound-identity encoding protocol.

A reviewable delivery preserves originals, states the key’s purpose and form, defines collision handling and identifies where post-assembly normalization happens. Check the result with independent character fixtures. If canonical equivalence is all the team needs, define that first. Review compatibility folding, case rules and security policies separately instead of allowing a text helper to make undefined identity decisions.
