Why can copying only the main SQLite file miss a committed row?

Compare a main-file-only control with a SQLite connection backup and verify a committed row in the destination.

Updated 2026-11-15 · Estimated read 10 min

Article

Key takeaways

  • A committed SQLite row can remain in the WAL.
  • Verify the target copy through an independent read.
  • Opening the file does not establish which records it contains.

A committed SQLite row can still live in the WAL. Copying only the main database can produce a file that opens but lacks that row. Use SQLite’s connection backup API for a live database and verify the resulting copy separately.

Suppose an application commits a second inventory record. The writer can read it, while a task that copies only the main database produces a file containing the table and just the first record. Check how each copy was made and compare the business IDs. A readable older database can still fail the backup contract.

Account for state in the WAL

SQLite documents the WAL as part of the database’s persistent state. Separating a database in use from its WAL can lose committed transactions. The engine’s live connection can read committed contents using its own coordination. This example deliberately leaves a second row in the WAL, with no competing writer. SQLite WAL file.

Python’s sqlite3.Connection.backup uses a distinct target connection. Give it a dedicated path and verify its contents through a new read afterward. Reading from the source does not establish what the copy contains. This fixture does not establish a production cutoff under concurrent writes. Python sqlite3 backup.

Compare two ways to obtain a copy

This complete standard-library program ran in a temporary directory on Python 3.11.15 with SQLite 3.53.1. It disables automatic checkpoints on the writer, checkpoints the baseline, and commits row two. Copying the main file is an isolated negative control.

from contextlib import closing
from pathlib import Path
from shutil import copyfile
from sqlite3 import connect, sqlite_version
from tempfile import TemporaryDirectory

def query(connection, sql):
    return list(connection.execute(sql))

def rows(connection):
    return query(connection, "SELECT id FROM sample ORDER BY id")

with TemporaryDirectory() as directory:
    root = Path(directory)
    live = root / "live"
    main_only = root / "main-only"
    backup = root / "backup"
    with closing(connect(live)) as writer:
        assert query(writer, "PRAGMA journal_mode=WAL") == [("wal",)]
        writer.executescript("""
            PRAGMA wal_autocheckpoint=0;
            CREATE TABLE sample (id INTEGER PRIMARY KEY);
            INSERT INTO sample VALUES (1);
        """)
        assert query(writer, "PRAGMA wal_checkpoint(TRUNCATE)") == [(0, 0, 0)]
        query(writer, "INSERT INTO sample VALUES (2)")
        writer.commit()
        assert rows(writer) == [(1,), (2,)]
        copyfile(live, main_only)
        with closing(connect(backup)) as target:
            writer.backup(target)

        with closing(connect(main_only)) as isolated:
            assert rows(isolated) == [(1,)]
        with closing(connect(backup)) as restored:
            assert rows(restored) == [(1,), (2,)]
            assert query(restored, "PRAGMA integrity_check") == [("ok",)]
        print(sqlite_version, "live=1,2 main-only=1 backup=1,2")

The writer returned both IDs. The main-file-only copy reopened with ID one. The connection backup reopened with both and reported ok for integrity_check. The run kept the writer open through verification. No application writes occurred during either copy. The receipt covers this timing and these rows.

Keep the observations independent. Use distinct files and record the actual paths opened by the check. A test that sends its verification query back to the live source can inadvertently prove the wrong result. A misplaced sidecar would also change the negative control.

Give recovery its own acceptance criteria

Choose stable committed IDs and inspect their related records in the destination. A structural integrity check has its own purpose. If the product promises a business cutoff, verify the relevant commit and what the restored copy contains. External services and separate databases have their own recovery conditions.

A useful negative check lets the main-file-only copy open and find the baseline, then requires ID two by name. That makes it impossible for a successful open to stand in for the expected data. The related SQLite checkpoint article covers long reads and checkpoint progress. Here the checkpoint timing is controlled to isolate the backup input.

A recovery test can also verify a related detail row for ID two, then confirm that a known absent ID stays absent. Query the restored target for both checks. This catches a partial restore or a test accidentally reading another copy. Those application checks were not run.

Does the default also back up an attached database?

The source name defaults to main. To back up a separately named ATTACH database, make a deliberately selected copy with the name argument and a distinct destination. Give each source a separate marker and verify it in the intended copy. Two individual backups do not establish a shared business snapshot across databases. This follow-up was not run.
