Why can CMake try_compile pass while program linking still fails?

Probe the same unresolved C symbol with an executable target, a static library and the real build target.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-15 · Estimated read 9 min
Translations
zh-CN en

Article

Key takeaways

  • The static-library probe does not link an executable.
  • Record the probe type and diagnostics with its boolean result.
  • Retain separate linker evidence for the deliverable.

Static-library mode can compile and archive the source without producing an executable. When CMake’s try_compile passes, check what it built. An executable link still needs its own evidence.

A cross-compilation setup may need a target-specific linker script. A maintainer switches the probe to a static library to check the compiler first. That can be an appropriate change, but the successful check now supports a different conclusion. Keep the target type and diagnostic with the result.

Hold the source fixed and change the probe target

The CMake target-type variable defaults to an executable in the source-file probe. Set it to STATIC_LIBRARY to build an archive without linking an executable. A reference to an external function can remain unresolved in that archive.

Save the following as CMakeLists.txt and main.c in a disposable directory. This ran locally with CMake 4.2.3 and Apple Clang. It tests native configure and linking behavior, without exercising a cross toolchain.

cmake_minimum_required(VERSION 3.25)
project(LinkBoundary C)
set(src "${CMAKE_CURRENT_SOURCE_DIR}/main.c")
set(CMAKE_TRY_COMPILE_TARGET_TYPE EXECUTABLE)
try_compile(linked SOURCES "${src}" NO_CACHE OUTPUT_VARIABLE link_log)
message(STATUS "executable probe: ${linked}")
message(STATUS "${link_log}")
set(CMAKE_TRY_COMPILE_TARGET_TYPE STATIC_LIBRARY)
try_compile(archived SOURCES "${src}" NO_CACHE OUTPUT_VARIABLE archive_log)
message(STATUS "static probe: ${archived}")
if(linked OR NOT archived)
  message(FATAL_ERROR "Unexpected probe results")
endif()
add_executable(real_program "${src}")

extern int optional_provider(void);

int main(void)
{
    return optional_provider();
}

Run cmake -S . -B out, then cmake --build out. The executable probe returned FALSE and reported the missing optional_provider symbol. The static probe returned TRUE. Those outcomes were the project’s assertions, so configuration exited successfully. Building the actual executable then failed at the linker with the same unresolved symbol and returned two.

Both probes used the same source. Its function declaration lets the compiler process the call, but it does not provide an implementation for the executable linker. Treat the static result as evidence that the compiler and archiver accepted the input. Changing only the target type does not provide the missing symbol.

Choose the probe that matches the required evidence

A static target can be appropriate for a syntax, header or compiler-option probe. Keep the final link as a separate check once a cross toolchain has the required startup files and linker settings. If the question is whether a library supplies a symbol, pass the actual link inputs to an executable probe or build the intended target.

A zero configure status does not turn every probe into a pass. This fixture deliberately expects FALSE once and TRUE once. Preserve their labels and relevant diagnostics alongside the overall exit. A production check should also capture the selected compiler, platform and link configuration. CMake’s file generation boundary covers another case where configure evidence must be interpreted by stage.

A feature flag may use a probe result to enable calls into an optional library. Record separately whether the headers are usable and whether the implementation links. The first result cannot activate a feature that also requires the second.

Running a program is another claim. Choose a compatible runtime separately when the delivery requires it. To test a repair to this fixture, add a provider implementation and explicitly include it in the relevant probe and real target. Check that the unresolved-symbol error disappears. That repair was not run here.

Does the target-type variable also change a whole-project try_compile?

It applies to the source-file signature. A whole-project probe uses the targets declared inside that project. Choose the target and type there, and verify its result separately. This article did not run the whole-project variation. CMake try_compile signatures
