Why can valid JSON still receive HTTP 422?

Compare 415, 400, and 422 on a booking endpoint to locate a failure in the media type, JSON syntax, or the relationship between the two times.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-15 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • A 422 response can follow successful parsing
  • A fixed start isolates the time rule in a regression test
  • Use the documented error reason to guide correction

The meeting-room form sends JSON that parses. The start is ten and the end is nine. After HTTP 422, the client rebuilds the same JSON to fix what looks like a missing quote, only to fail again. The server understood the content. The booking instruction needs to change. In this case, making the end later than the start reaches the creation branch.

Where the three failures occur

The endpoint has to accept the media type and parse the body before it can evaluate the requested action. An error message that identifies the failing step gives the user or developer somewhere concrete to start.

This example accepts only application/json. A request labeled text/plain gets 415 even when its bytes look exactly like JSON. Check the way the client sends the content before changing the booking fields.

Once the type is accepted, a truncated JSON document fails during parsing. The example returns 400 for that case. Until the app can read start and end, it can't establish that the end is earlier.

The last failing request uses the supported type and yields two readable fields. Nine is earlier than ten, so the booking fails the endpoint’s ordering rule. RFC 9110 describes 422 for content whose type the server understands and whose syntax is correct, but whose instructions it cannot process. This request fits that status. Other business failures need to be considered under their own contracts.

Keep the start fixed and correct one field

This standalone local fixture uses integers for the two hours and requires the end to be later than the start. The cases are an unsupported type, truncated JSON, reversed hours, and corrected hours. It does not start a server or send an HTTP request.

import assert from 'node:assert/strict';

function createBooking(type, body) {
  if (type !== 'application/json') return {status: 415};
  let value;
  try {
    value = JSON.parse(body);
  } catch {
    return {status: 400};
  }
  if (!value || !Number.isInteger(value.start) ||
      !Number.isInteger(value.end)) {
    return {status: 422, issue: 'invalid-hour-fields'};
  }
  if (value.start >= value.end) {
    return {status: 422, issue: 'end-must-follow-start'};
  }
  return {status: 201};
}

const cases = [
  ['text/plain', '{"start":10,"end":9}', 415],
  ['application/json', '{"start":10,', 400],
  ['application/json', '{"start":10,"end":9}', 422, 'end-must-follow-start'],
  ['application/json', '{"start":10,"end":11}', 201],
];

const {equal} = assert;
for (const [type, body, expected, issue] of cases) {
  const response = createBooking(type, body);
  equal(response.status, expected);
  equal(response.issue, issue);
}
console.log('Expected status branches passed: 415, 400, 422, 201.');

The local status assertions passed in this order: 415, 400, 422, 201. Only the end changes between the last two cases, which isolates the booking rule. Submitting the same invalid hours again takes the same failure branch. The fixture returns 201 for the passing case but doesn't store a reservation.

For an actual API, see whether the error response identifies a stable reason. A documented code for reversed hours can map to a message in the booking-time area: “The end must be after the start.” Keep the entered values so the user can correct one of them without re-entering the room, date, or attendees.

A 422 status cannot tell a client whether a date is unacceptable, a room is too small, or two fields conflict. Read the details under the API contract. Don't use the fixture's time message for every response with that status.

The fixture also distinguishes field shape from order. A missing hour or a non-integer value returns the same status with another reason. If the end is the string “nine,” first correct the type expected by the endpoint. Ordering applies after there are two integers to compare. A client should keep a separate format error intact when showing a reason about the order.

Use the reversed and corrected requests as a regression pair on the server. Keep the media type, parser, and start the same, then change the end from nine to eleven. If several request settings change at once, a passing request can't tell you which was responsible. Separate tests for malformed JSON and unsupported type can catch code that inadvertently labels an earlier failure as a booking rule.

For diagnostics, record whether parsing completed, the rule identifier that fired, and the status returned. You can often identify this boundary without storing the actual times or the person's identity. Seeing that the media type and JSON checks passed, followed by a specific range-rule identifier, directs the investigation to the form and endpoint contract.

Keep the server assertion even when the form checks the range before submitting. The form gives the user earlier feedback. The server still has to decide whether the instruction meets the current rule. The request-level test continues to check that contract when the form changes independently.

What if the response has a reason but no field path?

Place a cross-field error with the time group or explain the relationship in the error summary. Ten to nine violates the rule, but moving the start to eight or the end to eleven could both fix it. If the server gives no field path, the client has no reason to insist that the end field is the only one to correct. Keep both entries and let the user choose the time that matches the meeting.

With only a status and no reason, the client can't infer a range problem. Preserve the entries and present the failure, then use the API's documented details to route future instances to a specific part of the form.

If the request stops before instruction validation, see how to diagnose the request media type after HTTP 415.
