Does an omitted update_mask behave like an empty path list?

Send the same title with an omitted mask, an empty mask, and an explicit title path. Compare the scopes and return values under AIP-134.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-15 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • Omission infers a scope from non-empty fields
  • AIP-134 recommends a no-op for an empty path list
  • Preserve mask presence across decoding

Two book editors send a title of New. The first leaves the update mask out. The second sends a mask with no paths. After saving, the first has changed the title and the second still reads Old. Under the standard update contract described by Google AIP-134, those requests select different update scopes.

Where the scope comes from

The stored book has a title of Old and a note of Keep. The submitted resource contains a title of New and no note. The method needs to know which fields it may write. With an explicit title path, it writes the submitted title and leaves the note outside the update.

When the entire mask is omitted, AIP-134 infers the mask from populated fields with non-empty values in the resource. Here only title qualifies. The note is absent from the request, so the result becomes New with Keep still in place.

If a mask is present but lists no paths, AIP-134 recommends treating the request as a no-op and returning the unchanged resource. Although the request contains New, the selected scope does not contain title. The caller receives Old and Keep.

That distinction can be lost before the update code runs. If the decoder supplies an empty mask object for every omitted mask, it erases presence. The same input that was meant to infer the scope now reaches the point where the method chooses to do nothing. Compare the raw request against the decoded mask before diagnosing the update from path length alone.

Three scopes with one resource value

This Node fixture illustrates the rules using JavaScript objects with the two known string fields and their known paths. It leaves out general path resolution and persistence. The mask name in the object is a local choice. The object is not intended as a ready-to-send request for every protocol.

import assert from 'node:assert/strict';

const stored = {title: 'Old', note: 'Keep'};
const edits = {title: 'New'};
const hasMask = Object.hasOwn;

function updateBook(current, request) {
  const submitted = request.book;
  const paths = hasMask(request, 'updateMask')
    ? request.updateMask.paths
    : Object.keys(submitted).filter(key => submitted[key] !== '');
  const next = {...current};
  for (const key of paths) next[key] = submitted[key];
  return next;
}

const cases = [
  [{book: edits}, {title: 'New', note: 'Keep'}],
  [{book: edits, updateMask: {paths: []}}, stored],
  [{book: edits, updateMask: {paths: ['title']}}, {title: 'New', note: 'Keep'}],
];
const {deepEqual} = assert;
for (const [request, expected] of cases) {
  deepEqual(updateBook(stored, request), expected);
}
console.log('Omitted, empty, and title masks passed.');

All three assertions passed locally. Each call uses the same stored book and submitted title. The omitted mask gives New, the empty list gives Old, and the explicit title path gives New again. All three assert that the note still reads Keep so an unintended replacement cannot pass unnoticed.

Test the same cases through the real request decoder as well. Constructing two different objects beside the business function verifies only that the update code can tell them apart. It cannot catch a decoder that merges them before they reach that function. An endpoint test can record whether the mask was present on the wire and whether that information survives decoding.

Have the same request builder produce both endpoint test cases. Omit the mask field entirely in one, and keep it with the transport’s representation for an empty mask in the other. Check the actual messages before comparing the response and a subsequent read. If that transport or decoder collapses the two requests, record the limitation. The local objects do not prove that an endpoint can preserve the distinction.

Look at the request builder too. A shared form client may initialize a path list to an empty array and send it before deciding which fields changed. That default changes the intent if the client originally relied on inference. A no-op can still return a successful response, so success by itself doesn't prove the title was saved.

When the response includes the resource, compare its title with the value the user just submitted. If it still reads Old, verify the selected path before changing the displayed title to New. Otherwise the interface may report an update that disappears on refresh.

The asterisk is a separate mask value for full replacement. It differs from an empty list. This fixture does not implement it or nested paths. Check the specific endpoint contract if replacement must account for output-only fields or writable fields added in a later version.

Name test cases after the caller's intent: infer the title, select zero fields, and select the title explicitly. Numbered cases can make it easy to fold two different requests into the same serialized shape. A descriptive test name and a shared assertion for Keep give the next maintainer a starting point when that happens.

Can leaving out the mask clear the title?

Don't rely on omission for that operation. Add a condition: this resource permits a blank title. If the submitted title is an empty string, inference from non-empty fields does not select it. The old title stays. Send the title path explicitly along with an empty string so the method attempts to clear the field. A real resource that demands a title can still reject the value.

The two paths that looked equivalent with New now diverge. Only the explicit title path conveys the intended clear. An extra test using an allowed empty value can catch a client that can save replacement text but has no way to erase it.
