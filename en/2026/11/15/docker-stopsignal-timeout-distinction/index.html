Why did Docker kill the container after sending its stop signal?

Use three stops of the same image to verify Docker’s initial signal separately from its grace period.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-15 · Estimated read 10 min
Translations
zh-CN en

Article

Key takeaways

  • Identify Docker’s first signal.
  • Observe both handler entry and completion.
  • Change the grace period and signal override independently.

Which signal Docker sends first and how long it waits are separate settings. If the container remains running after the grace period, Docker can still end it with SIGKILL.

An operator changes an image’s stop signal and sees the application log its receipt. The cleanup completion record never appears. The signal may have arrived while the work was still unfinished. Verify handler entry, completion and container exit individually before changing the stop policy.

Read the initial signal and grace period separately

Dockerfile STOPSIGNAL chooses the initial signal for daemon stops. Without a setting, the default is SIGTERM. Container creation can override the image through --stop-signal. A particular stop command can also select its own signal and wait time. If the container has not exited when the wait expires, the daemon sends SIGKILL. Record the image setting, container configuration and actual command rather than assuming they agree. Dockerfile STOPSIGNAL and Docker stop reference

Compare two signal handlers in one program

This complete example is for an isolated Linux-container environment. It was not built or run. Python runs as the main process and registers both handlers before printing ready. The USR1 path waits six seconds. The TERM path finishes without that delay. The sleep represents unfinished work in this exercise.

FROM python:3.12-slim
COPY shutdown.py /shutdown.py
STOPSIGNAL SIGUSR1
ENTRYPOINT ["python", "/shutdown.py"]

Save this as shutdown.py next to the Dockerfile.

import signal
import time


def stop(signum, frame):
    print(f"received:{signal.Signals(signum).name}", flush=True)
    if signum == signal.SIGUSR1:
        time.sleep(6)
    print("finished", flush=True)
    raise SystemExit(0)


signal.signal(signal.SIGUSR1, stop)
signal.signal(signal.SIGTERM, stop)
print("ready", flush=True)
while True:
    signal.pause()

Build once with docker build -t stop-signal-lab .. Start three separate containers, using the image default for the first two and passing --stop-signal SIGTERM when creating the third. Wait for ready in each set of logs before running its stop command. Give the first and third containers twelve seconds with docker stop --timeout. Give the second one second.

docker run -d --name grace-long stop-signal-lab
docker run -d --name grace-short stop-signal-lab
docker run -d --name signal-term --stop-signal SIGTERM stop-signal-lab
# Inspect each container's logs for ready before stopping it.
docker stop --timeout 12 grace-long signal-term
docker stop --timeout 1 grace-short

Wait for all three ready markers before the stop lines. A container that exits before registering its handlers leaves the trial incomplete. A successful stop command by itself supplies no evidence about the handler’s completion.

Trial Handler entry marker Expected completion marker
Image default, longer grace received:SIGUSR1 Present
Image default, short grace received:SIGUSR1 Absent
Container override, longer grace received:SIGTERM Present

The short grace is a negative control. Retain the markers and the final container state from docker inspect. Check the effective signal and logging path if even the receipt marker is missing. Actual timestamps depend on scheduling. A particular exit status alone cannot reconstruct which signals and application actions preceded termination.

Check what changed before widening the rollout

The first two trials vary the wait. The first and third vary the initial signal. An orchestrated deployment also needs the stop operation’s actual configuration. Check application behavior separately, such as finishing a required write or releasing a connection. The fixture only records that its handler reached a marker.

This exercise fixes an exec-form entrypoint. If a wrapper still sits in the signal path, see how entrypoints hand signals to the application. Preserve the container ID, creation settings, stop command and markers for each independent trial. A completion message can also be emitted before a real process finishes all its work. Observe the actual exit rather than assuming the two events are equivalent. Remove only the test containers and image afterward.

Does pressing Ctrl+C use the image’s configured signal?

The Dockerfile reference distinguishes keyboard interrupts from daemon stops. Ctrl+C sends SIGINT, regardless of the image’s USR1 setting. Verify the actual interactive path if it passes through a terminal wrapper. A separate foreground fixture could register a visible SIGINT handler. The stop lab does not exercise that path, and the variation was not run.
