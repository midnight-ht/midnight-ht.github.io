Why can projected text change without a slotchange event?

Change text and replace an element in the same default slot. Compare assigned node identity, displayed content, and notification.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-15 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • Text edits can leave the same node assigned
  • A replacement can change assignment with identical text
  • Check identity and content separately from notification counts

A component projects text through its default slot. The visible text changes from A to B, yet the slotchange listener logs nothing. Replace the whole span with another one containing B and the listener gets an event, although the screen looks the same. Inspect the assigned node separately from the text a reader sees.

Start with the assigned node

The host in this example contains one span with the text A. Its shadow tree contains a default slot. The assigned node is the outer span. A reader sees A at the slot's position, while the assignment list holds an element reference. The text is a descendant of that element.

Change the span's existing text node to B and the same span remains assigned. Check the first entry in the assignment list against the original element reference. You can record that equality separately from the element's current text.

Now create a new span containing B and replace the original span with it. The visible string is still B. The first entry in the assignment list is a different element. The DOM assignment algorithm compares the lists by node, so this change signals the slot.

A screenshot can't distinguish those cases. If you suspect the listener is missing an update, log the assigned reference and the text you need to display. Different nodes can display the same text and one node can display different text over time.

Record the running event count after each operation

Save the following as an HTML file. It lets one task pass after setting up the slot before it registers the listener, so the initial assignment notification stays out of the measurement. Each subsequent operation gets its own observation interval. A row records the operation, the cumulative event count, whether the assigned element is the original, and its current text.

<!doctype html>
<meta charset="utf-8">
<title>Slot assignment check</title>
<div id="host"><span>A</span></div>
<pre id="result"></pre>
<script type="module">
const host = document.querySelector('#host');
const output = document.querySelector('#result');
const shadow = host.attachShadow({mode: 'open'});
const slot = document.createElement('slot');
shadow.append(slot);
const pause = () => new Promise(resolve => setTimeout(resolve, 0));
await pause();

let events = 0;
slot.addEventListener('slotchange', () => { events += 1; });
const first = host.firstElementChild;
const report = label => {
  const [assigned] = slot.assignedNodes();
  output.textContent += [
    label, String(events), String(assigned === first), assigned.textContent,
  ].join(' | ') + '\n';
};

first.firstChild.data = 'B';
await pause();
report('text edit');

const replacement = document.createElement('span');
replacement.textContent = 'B';
first.replaceWith(replacement);
await pause();
report('node replacement');
</script>

The specification leads to the following expectations: text edit, zero, true, B; then node replacement, one, false, B. Those are predictions for this standalone page. The page wasn't tested in a browser for this article. If you add whitespace inside the host markup, check that the first assigned node is still the example element.

Read the count after allowing time for notification. The standard adds signaled slots to a set and queues notification in a microtask. The two operations are separated for this demonstration. One callback per synchronous edit isn't guaranteed in a component that makes several changes at once.

Other code could also change the slot during a real application update. Isolate the listener in a page like this before debugging the timing of the framework. Once you can read identity and content separately, compare them against the actual app's updates.

Does your component depend on assignment or content?

A sidebar that initializes newly projected controls needs to know when the original element has been replaced. This makes the assignment signal useful. It still needs an initial read for controls that were already in the slot before it attached its listener.

For a label that follows projected text, decide how text edits reach it. With a shared data model, the upstream change can update both outputs. If the component accepts DOM it doesn't control, it can observe the relevant text or subtree of a currently assigned element. When assignment changes, move that observation to the new element.

Test those responsibilities separately. The first operation can verify that content observation reports A changing to B. The second can check that the component starts observing the replacement. An edit to the removed element can then check that the component has stopped reacting to it.

A useful assertion failure identifies the column that changed: count, reference, or text. A text-only log can miss an observer still attached to a removed element. A callback-only log can make an ordinary text edit look like a broken notification. Keeping the observations together ties them to the same operation.

Can adding fallback content signal an empty slot?

Yes. Suppose the host has no children to assign and the default slot starts empty. After initial notifications have settled, append a span directly to the slot inside the shadow tree. The DOM insertion algorithm signals this previously unassigned slot. A plain call to assignedNodes still gives an empty array. The new child provides fallback content and never entered the host's assignment list.

Read the assignment list when handling the event. The interface can show the new fallback text and still have no projected controls to initialize. The event alone does not establish that the assignment list contains something.

If you're investigating which element a click inside a shadow tree presents as its target outside, see shadow DOM event retargeting and paths.
