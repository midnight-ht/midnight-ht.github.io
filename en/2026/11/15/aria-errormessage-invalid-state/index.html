How should a corrected input stop exposing its old error?

Use a verification-code field to check how validation controls the invalid state, error reference, and message visibility.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-15 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • An invalid field can reference a visible error
  • Clear stale error state when the input passes
  • Test the transition without discarding the corrected value

The verification-code field last showed “Enter six digits.” The user changes 123 to 123456, checks the field again, and the error disappears. Check one more thing: does the field still say it is invalid or still identify the previous message as its current error? Removing the red text alone cannot establish that the field's other state has been cleared.

Let the message follow validation

There are three useful checkpoints. At first render, the product hasn't checked the code. Give the input a label that identifies it and leave it unmarked as invalid. The error paragraph can already exist in the DOM, but it begins hidden and the input does not reference it.

The user enters three digits and presses Check code. The app rejects this value under the six-digit rule. Reveal the error paragraph, mark the input invalid, and point aria-errormessage at the paragraph ID. A person reading the page can see how to correct the value. The relation also identifies which input the message belongs to.

Once the input has six digits and the user checks it again, the error no longer applies. The example removes the error reference, hides the paragraph, and clears the invalid marker. It keeps the user's entry. Resetting the field would discard the value they just corrected. The same error paragraph can be used again on the next failed check.

WAI-ARIA 1.2 ties the error message relation to aria-invalid. When the message is no longer pertinent, hide its target or remove the reference. If the reference remains with an explicit non-invalid state, the user agent must not expose that error relation. This example clears all three pieces of state so the recovery is easy to inspect.

Check all three states

The following local fixture has no verification service and sends no code. It only tests whether the string contains exactly six ASCII digits. Validation runs on the button rather than after each keystroke.

<!doctype html>
<meta charset="utf-8">
<title>Code validation</title>
<label for="code">Verification code</label>
<input id="code" inputmode="numeric">
<button id="check" type="button">Check code</button>
<p id="code-error" hidden>Enter six digits.</p>
<script>
const input = document.getElementById('code');
const button = document.getElementById('check');
const notice = document.getElementById('code-error');
button.onclick = function validate() {
  if (/^[0-9]{6}$/.test(input.value)) {
    input.removeAttribute('aria-errormessage');
    notice.hidden = true;
    input.removeAttribute('aria-invalid');
    return;
  }
  notice.hidden = false;
  input.setAttribute('aria-invalid', 'true');
  input.setAttribute('aria-errormessage', notice.id);
};
</script>

On first load, the input should have neither of the two ARIA attributes and the error paragraph should be hidden. Enter 123 and press Check code. The input should now be marked invalid and the error reference should resolve to the visible instruction. Change the value to 123456 and check again. The paragraph should be hidden, both attributes should be gone, and the field should still contain 123456.

For an automated assertion, examine the attributes, the target, and the field value separately. Checking only that the error is invisible misses a stale invalid marker. Checking only that the attributes are gone misses a visible old message. Sequence failure and recovery on the same page to catch state that survived the first check.

Keep both snapshots in a test failure report. On failure, require the reference to equal the actual paragraph ID instead of checking that some string is present. On recovery, require both attributes to be absent and confirm the paragraph is hidden. A later ID rename or a stale reference then produces evidence of which piece failed.

Try another failure after recovery. Remove one digit and run the check again. The paragraph should return and the reference should resolve to the same ID. This finds an implementation that accidentally removes the reusable paragraph and leaves a dangling reference on the next failure. For repeated form instances, check that each input points to its own target.

These are expectations based on the page and the specification. Neither a browser nor an assistive technology was exercised for this article. Test how your supported combinations announce the message with their actual user interactions. Rendering a paragraph and declaring an error relation are separate from measuring what a person hears.

An application might also validate at the server. If the failure for 123 arrives after 123456 has passed its check, that old response should not reopen the error for the current value. The example runs validation synchronously and doesn't handle request ordering.

Can a format hint coexist with an error message?

Yes. Put a persistent, visible hint such as “Use the six digits from your text message” in its own element and associate it with the input via aria-describedby. On failure, add a separate message that only applies to the invalid state, such as “There are only three digits. Enter the rest of the code.”

On recovery, retain the description and clear the error reference. Someone returning to the input can still find its purpose and format without getting the previous failure as the current error. Separate targets let the description remain available while the error expires. Test that the description reference resolves in both states.

If several fields fail and the user needs a route from the top of the page back to each input, see how an error summary guides people to the fields they can correct.
