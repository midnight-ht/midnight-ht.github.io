Why did an existing Python logger go quiet after dictConfig?

Compare two executed dictConfig cases to distinguish a disabled instance from a handler that receives no record.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-15 · Estimated read 9 min
Translations
zh-CN en

Article

Key takeaways

  • Nonincremental configuration can disable existing non-root loggers.
  • Check both the instance and actual delivery.
  • Keeping a logger enabled does not establish the route.

A nonincremental dictConfig can disable an existing, unlisted non-root logger by default. A root handler may still receive messages at the same level from another module. Check the quiet logger’s disabled flag before changing thresholds or handlers.

Imagine importing a reconciliation module before applying the main logging configuration. That module obtains its logger during import. Another module starts logging later and remains visible. Lowering the root level cannot help if the first logger has already been disabled.

Find what the configuration can change

The documentation gives disable_existing_loggers a default of True and links it to fileConfig semantics. Existing named loggers covered by configured names or named ancestors need separate consideration. This fixture uses unrelated non-root names that are absent from the configuration. The root handler is the observer. Python logging.config.

The policy applies to instances that already exist at configuration time. A module may obtain its logger on import or much later at its first request. Record the instance’s creation point and state around configuration, then inspect actual delivery.

Verify the receiving handler

This fixture ran in a separate Python 3.11.15 process. An in-memory stream receives the records. Each round creates an early logger, applies a configuration, and creates a different late logger. One round omits the setting and one sets it to False.

import io
import logging
import logging.config

def observe(keep):
    early = logging.getLogger(f"demo_early_{keep}")
    buffer = io.StringIO()
    config = {
        "version": 1,
        "handlers": {
            "probe": {"class": "logging.StreamHandler", "stream": buffer},
        },
        "root": {"handlers": ["probe"], "level": "INFO"},
    }
    if keep:
        config["disable_existing_loggers"] = False
    logging.config.dictConfig(config)
    late = logging.getLogger(f"demo_late_{keep}")
    early.info("early")
    late.info("late")
    return early.disabled, buffer.getvalue().splitlines()

for keep, expected in [
    (False, (True, ["late"])),
    (True, (False, ["early", "late"])),
]:
    actual = observe(keep)
    assert actual == expected, actual
    print(actual)

The default round leaves the early logger disabled and delivers only late to the handler. The explicit preservation round leaves it enabled and delivers early followed by late. Both the flag and the received records were asserted. A test that only checks that some message arrived could miss the quiet module.

For a startup regression, record the initial state before applying configuration. If the process reloads configuration, the same instance may have been affected before. Exercise the real startup sequence with distinct messages and record the names that reached the handler. This application check was not run.

Verify where messages go after enabling them

Preserving existing loggers may fit an application with plugins that initialize them early. The setting does not choose their final handler, effective level, or propagation route. Test a record with a unique ID and check that the intended receiver sees it once. The related pytest logging article examines level and propagation from another observation point.

Another policy is to enumerate the application’s required loggers in the configuration. Check the scope of each configured name and exercise nearby names separately. The fixture has one memory receiver. It does not verify routing to multiple handlers, concurrency, or production retention. Keep business success and diagnostic delivery as independent checks.

For a separate negative control, keep the logger enabled and give it a higher effective level. INFO should stay absent while WARNING reaches the receiver. The same symptom now has a different cause. This control was not run.

Does the setting act when incremental=True?

The documentation says the setting is ignored for incremental configuration. Start a separate test with an already enabled logger and handler, then apply an incremental configuration carrying the key and a supported level change. Check the logger’s enabled state and observe a message under the new threshold. Do not assume this operation re-enables an instance that was already disabled. That probe was not run. The main fixture covers nonincremental configuration only.
