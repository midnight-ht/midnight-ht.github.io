Which systemd timer starts the wait after a job finishes?

Compare two monotonic systemd timer anchors and verify the gap between a job finishing and the next start.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-15 · Estimated read 9 min
Translations
zh-CN en

Article

Key takeaways

  • Choose the reference event before choosing the delay.
  • Verify the initial trigger separately from subsequent runs.
  • Measure the finish-to-start interval from service observations.

Start the wait from the target unit’s last deactivation when the delay must follow completion. Systemd’s OnUnitInactiveSec uses that reference point. A delay measured from activation includes the time the job spends running.

A scheduled fetcher needs to leave a gap after each run. Its operator sets an interval of twenty seconds and expects a full twenty seconds of rest. An eight-second job can leave only about twelve seconds before the next nominal start if the timer counts from the previous activation. Record which event starts the clock and measure the gap the downstream task actually needs.

Choose the preceding event

The systemd.timer manual distinguishes three events. OnActiveSec uses activation of the timer itself. OnUnitActiveSec uses the target unit’s last activation. OnUnitInactiveSec uses the last deactivation of that unit.

Suppose a service starts at second ten and finishes at eighteen. A twenty-second activation-relative delay has its nominal deadline at thirty. A deactivation-relative delay has its deadline at thirty-eight. This assumes normal completion before the first timer would elapse. The accuracy window and dispatch can affect actual timestamps.

Compare two timers with the same task

Use an isolated Linux test system. The following complete unit definitions were not run. Save this service as anchor-finish.service and copy it to anchor-start.service. Both services stop normally after the task and do not remain active on exit.

[Unit]
Description=Timer anchor demonstration task

[Service]
Type=oneshot
ExecStartPre=/bin/echo task-start
ExecStart=/bin/sleep 8
ExecStartPost=/bin/echo task-finish

Save the timer below as anchor-finish.timer. Copy it to anchor-start.timer, change Unit to its corresponding service and replace the last directive with OnUnitActiveSec. Keep the remaining settings fixed. Activation of the timer provides the first run after two seconds. The selected target event supplies the subsequent delay.

[Unit]
Description=Timer anchor demonstration schedule

[Timer]
Unit=anchor-finish.service
AccuracySec=1s
OnActiveSec=2s
OnUnitInactiveSec=20s

Load the test units and start both timers. Observe at least two complete cycles. Use the service journal to record the start marker, finish marker and next start. The finish marker is near the end of the job. Manager state is needed if the exact deactivation point matters. Compare the planned next activation against the actual service record.

Relative rule Nominal start-to-start interval Nominal finish-to-start interval
Activation Twenty seconds About twelve seconds
Deactivation About twenty-eight seconds Twenty seconds

These are predictions. Finding that both services ran twice would not distinguish them. Check which interval matches the requirement and diagnose a failed service before using its output as timing evidence. Stop the dedicated timers before removing the lab definitions.

Verify the delay that the work requires

A periodic maintenance attempt may be scheduled from the previous start. A cooldown or a handoff after completed work needs a finish-relative gap. A real service can finish its business action before its unit deactivates, so record the application event when that is the contractual boundary. If the target is already active, the timer does not launch a second instance. The calendar catch-up article explains a separate problem involving missed events.

Record the observations by unit and run before subtracting times. If a manual start falls between scheduled runs, leave that record out of the timer-only comparison or use it as a separate test.

For another proposed control, change the task duration from eight to ten seconds with both timer settings fixed. The deactivation-relative gap stays at a nominal twenty seconds. The activation-relative start period stays fixed while the remaining gap shrinks. That variation was not run.

Does the clock keep advancing during system suspend?

The ordinary monotonic timer clock pauses during suspend. The manual says WakeSystem selects a clock that keeps advancing and can wake a supported system. The main exercise assumes the system stays awake. Test suspend, resume and actual triggering separately on the intended hardware.
