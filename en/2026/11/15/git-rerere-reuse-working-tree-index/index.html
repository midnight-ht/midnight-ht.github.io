Git reused the old conflict resolution. Why is the file still unmerged?

Replay one conflict and check whether Git reused its resolution in the working tree alone or in the index too.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-15 · Estimated read 10 min
Translations
zh-CN en

Article

Key takeaways

  • Inspect the working tree and index separately.
  • Disable index autoupdate to review before staging.
  • Validate the merge after inspecting what was staged.

The file contains the old resolution, but the index still has unmerged entries. Git’s rerere can reuse the saved result in the working tree. Whether it updates the index too depends on this merge’s autoupdate setting.

A maintainer merges two long-lived branches. The conflict looks familiar, and the file now contains the previous resolution. Git still reports it as unmerged. Read the file, then examine the index. The first observation can show a candidate resolution while the second still records the conflict.

Inspect the two places that can change

The Git rerere manual describes applying an earlier resolution to the working tree when it fits the current conflict. With --no-rerere-autoupdate, you can inspect the result and update the index yourself using git add. Autoupdate also stages the result. The same working-tree text can coexist with different index states. Git merge reference

Use git ls-files -u to check for remaining unmerged index entries. Once you stage the reviewed result, inspect the staged content too. The absence of conflict markers in the working tree does not establish either observation.

Repeat the same conflict

This complete script ran with Apple Git 2.50.1 in a disposable repository. It creates two branches that change the same line. The first merge records a hand-written resolution. The resets and repeated merges operate only in the repository created by the script.

set -eu
work=$(mktemp -d)
trap 'rm -r "$work"' EXIT
cd "$work"
git init -q -b ours
git config user.email fixture@example.invalid
git config user.name Fixture
git config rerere.enabled true
git config commit.gpgsign false
write() { printf '%s\n' "$1" > settings; }
save() { git add settings && git commit -qm "$1"; }
write base
save base
git branch theirs
write ours
save ours
git switch -q theirs
write theirs
save theirs
git switch -q ours
if git merge --no-rerere-autoupdate theirs; then exit 1; fi
write combined
git add settings
git commit -qm learned
git reset --hard -q HEAD^
if git merge --no-rerere-autoupdate theirs; then exit 1; fi
test "$(cat settings)" = combined
git ls-files -u
test "$(git ls-files -u | wc -l | tr -d ' ')" = 3
git add settings
test -z "$(git ls-files -u)"
printf 'manual stage: %s\n' "$(git show :settings)"
git merge --abort
if git merge --rerere-autoupdate theirs; then exit 1; fi
test -z "$(git ls-files -u)"
test "$(git show :settings)" = combined
printf 'automatic stage: %s\n' "$(git show :settings)"

The second merge disables autoupdate. The file already reads combined while the index still has all three unmerged stages. After staging, the entries disappear and the index reads combined. The third merge enables autoupdate. At inspection its index has no unmerged entries and already contains combined. The outer script exits zero because its assertions passed. The third merge command itself still returns nonzero and leaves the merge to be completed.

Reading only the file cannot distinguish those two paths. Checking only for an empty unmerged list would not tell you which resolution was staged. Keep both observations and, when several files conflict, check the decisions for each affected path.

Decide what deserves another review

Reusing a resolution is useful when a conflict and its intended outcome recur. A resolution can still apply after the meaning of nearby configuration changes. Review the resolved file against both branches’ intent and test the behavior it controls. If the team requires review before staging, disable autoupdate explicitly. If it uses autoupdate, review the staged change before committing.

Keep a before-and-after record when a human approves the candidate. Save the conflict entries and candidate before staging, then inspect the actual staged version. An edit between those readings can change what the index contains.

Record whether rerere actually reused a resolution. A different clone may lack the recorded outcome. Seeing unmerged entries in both clones does not establish that both working trees contain the same text. For a separate review task involving completed commits, see comparing two revisions of a patch series.

Can you forget the saved resolution for just the current conflict path?

Use git rerere forget with a pathspec matching that conflict. This addresses an incorrect saved resolution. The previous experiment deliberately reused an appropriate one. Preserve whatever evidence you need for review, then resolve the current conflict and inspect the newly chosen result. This forget-and-resolve variation was not executed.
