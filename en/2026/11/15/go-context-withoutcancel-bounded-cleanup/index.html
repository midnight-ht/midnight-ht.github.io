Why is Done nil after Go’s WithoutCancel?

Compare cancellation on a Go parent, the state returned by WithoutCancel, and a newly bounded child.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-15 · Estimated read 10 min
Translations

Article

Key takeaways

  • WithoutCancel detaches cancellation and deadline.
  • Parent values remain available.
  • Give detached cleanup its own bound.

Go’s WithoutCancel detaches a derived context from its parent’s cancellation and deadline. Its Done channel is nil, while value lookups still follow the parent. When cleanup needs to outlive a canceled request, give that work a separate deadline.

Suppose an export request acquires a temporary resource. The client leaves, but the service still needs to report a cleanup outcome. The request context may be canceled before the cleanup receiver starts. A detached context avoids that cancellation and also loses the earlier time limit. Define who owns that work and where waiting ends.

Inspect exactly what was detached

WithoutCancel was added in Go 1.21. The documentation says the derived context has no deadline, Err or Cause and that Done is nil. The pinned implementation delegates Value lookups to its parent chain. If diagnosis needs the original failure, retain the parent’s result separately. Go context reference and pinned implementation.

A nil channel cannot make a select case ready. Inspect a wait loop that previously depended on the cancellation case. A deadline provides a signal for code that observes it. An operation that ignores the signal needs its own integration check.

Give the three contexts distinct expectations

This complete Go teaching program was not run. It creates a parent with a trace value and a distant deadline, then creates a detached child. It cancels the parent and gives a descendant of the detached context a fixed deadline in the past. No sleep is needed to inspect the final states.

package main

import (
    "context"
    "fmt"
    "time"
)

type traceKey struct{}

var deadline = context.WithDeadline

func main() {
    root := context.WithValue(context.Background(), traceKey{}, "demo-17")
    parent, stop := deadline(root, time.Now().Add(time.Hour))
    defer stop()
    detached := context.WithoutCancel(parent)
    stop()

    _, hasDeadline := detached.Deadline()
    observedErrors := [3]error{parent.Err(), detached.Err(), context.Cause(detached)}
    if observedErrors != ([3]error{context.Canceled, nil, nil}) {
        panic("unexpected error state")
    }
    if detached.Done() != nil || hasDeadline || detached.Value(traceKey{}) != "demo-17" {
        panic("unexpected parent or detached state")
    }

    bounded, cancel := deadline(detached, time.Unix(1, 0))
    defer cancel()
    select {
    case <-bounded.Done():
        if bounded.Err() != context.DeadlineExceeded {
            panic("wrong bounded context error")
        }
    default:
        panic("expired deadline did not finish")
    }
    fmt.Println("parent canceled, detached alive, bounded deadline expired")
}

Expect Canceled on the parent. The detached context should still supply demo-17 while having no deadline, error, cause, or Done channel. The newly bounded child should immediately report DeadlineExceeded. Checking only the trace field would miss the disappearance of the parent’s bounds. Checking only the final error would not show that the detached context remained usable after the parent’s cancellation.

An application test can inject a receiver and verify that cleanup still reaches it after the request is canceled. A separate receiver can wait on the cleanup context and report its own deadline error. This checks that the caller passes the new context through the real path. That integration probe was not run.

Detach only the work that has another owner

The main upload should ordinarily still honor the caller’s cancellation. Temporary cleanup may instead belong to the service. Set an independent budget at that call boundary. Decisions about external side effects, ownership, and duplicate requests need their own rules.

Test completion and early cancellation separately. On cancellation, the original work should stop and the cleanup path should reach its own terminal outcome. Keep a cleanup failure distinct from the first request failure. The related cancellation and settlement article covers asynchronous cleanup timing. This fixture deals with the Go context bounds only.

Also test a receiver that returns early, then cancel its independent context to release associated resources. Compare that result with a receiver that actually waits for the deadline. These application cases are unexecuted.

Do identity values disappear with the original cancellation?

Normal values still resolve through the parent. If a background operation only needs a trace ID, construct a context with just that value and give it a new deadline. A separate test can put two markers on the original context and verify that only the intended marker reaches the job. Reading a value does not establish authorization for the background action. This value-selection probe was not run.
