How can focus move without scrolling the container?

Compare normal focus and preventScroll on the same offscreen button. Check which element received focus and whether the panel moved.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-15 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • Default focus includes a scroll step
  • The option skips that step for the current focus call
  • Assert the active element separately from the panel offset

A script moves focus to a button below the visible area of a scrollable panel. The button receives focus, but the panel jumps away from where the user was reading. A focus call can take preventScroll to preserve that position on an ordinary focusable button. Check focus and scroll offset separately.

One focus call, two outcomes

The HTML focus method runs the focusing steps. With the default options it then runs the step that scrolls the target into view. FocusOptions defaults preventScroll to false. Set it to true to omit the method's own scroll step while still attempting to focus the target.

This example assumes a connected, enabled button that can already receive focus. The option doesn't make a disabled button focusable. If nothing moves, the target might have received focus without scrolling or it might have failed to get focus. The offset alone cannot distinguish those cases.

A panel jump does not establish that the target received focus either. Another handler could move the container while the trigger still has focus. The focus reading tells you which element can receive the next keyboard action. The scroll offset tells you where the user is looking.

Focus the same target from the same position

Save this example as an HTML file. The panel is a hundred pixels high. The target sits below a taller gap. Both outer buttons first receive focus explicitly so the test begins with a different active element. The fixture then returns the panel to the top, leaving only the target's focus options different between the two actions.

<!doctype html>
<meta charset="utf-8">
<title>Focus and scroll check</title>
<style>
  #pane { height: 100px; overflow: auto; border: 1px solid; }
  .gap { height: 220px; }
</style>
<button id="normal">Focus normally</button>
<button id="steady">Focus without scrolling</button>
<div id="pane">
  <div class="gap"></div>
  <button id="target">Target</button>
  <div class="gap"></div>
</div>
<pre id="output"></pre>
<script>
const byId = document.getElementById.bind(document);
const pane = byId('pane');
const target = byId('target');
const output = byId('output');

function check(trigger, options) {
  trigger.focus({preventScroll: true});
  pane.scrollTop = 0;
  const before = pane.scrollTop;
  if (options) target.focus(options);
  else target.focus();
  const focused = document.activeElement === target;
  const after = pane.scrollTop;
  const result = focused + ' | ' + before + ' → ' + after;
  output.textContent = trigger.id + ' | ' + result;
}

const normal = byId('normal');
const steady = byId('steady');
normal.onclick = () => check(normal);
steady.onclick = () => check(steady, {preventScroll: true});
</script>

Click Focus normally from the top of the page. The expected result has true for focus, zero for the initial offset, and a positive final offset. Then click Focus without scrolling. Focus should again be true, with both offsets zero. The test doesn't require the default scroll to end at a particular pixel.

These are predictions from the HTML algorithm and the fixture layout. No browser or assistive technology was exercised for this article. The sample looks only at the panel's vertical offset. If your UI has an outer scrolling element, log its offset separately so a panel that stays still doesn't mask a page jump.

The output needs two assertions. Check whether the chosen target is the active element. Then compare the panel offsets before and after the call. Keep both offsets in a report, so you can see whether the wrong position came from the initial state or from the action under test.

Choose when the position should stay put

An interface may want the current reading position to survive a scripted focus operation, such as returning from a keyboard interaction while the user keeps their place. Confirm that the resulting focus target is clear in that workflow. Focus on a control the person cannot see can make the next keyboard action difficult to predict. The option controls a scroll step. The application still chooses where to put focus.

When you return to the actual component, identify what triggers focus. Isolate that call temporarily from focus handlers, automatic scrolling, and layout changes. A different part of the application can still alter the viewport after the method skips its own scroll step. The sample has no such application handlers on the target.

Check that each regression case really starts from zero and places the target below the panel. If the button is already visible, the default call might leave the offset alone too. Reset focus and position so an earlier run cannot make the next branch appear to pass.

If one result differs from the prediction, repeat each action through the keyboard and through the mouse. Log the trigger and the focus and offset after the fixture resets their starting state. The script sets the same initial state for either input method. A difference that appears earlier points back to activation or the outer controls.

A report can capture where the action came from, which element received focus, and which container moved. For example, a keyboard shortcut should first have an active element other than the target. After it runs, the target should become active while the panel stays at its previous row. Clicking the target directly would exercise a different entry point.

Does the option also block a later scrollIntoView call?

No. Focus the target with preventScroll and read the panel offset while it is still zero. A subsequent scrollIntoView call makes a new scrolling request. The earlier option only affected the steps of the earlier focus call and did not attach a persistent rule to the target or panel.

Read the offset between the two operations when debugging. A focus change with no initial offset change followed by a scroll during the explicit reveal attributes each effect to the right operation. If a focus listener triggers that second operation, its own conditions determine when the reveal occurs.

If the focus change happens as a dialog closes or is reopened, see how to handle a dialog's previous return value on reopening.
