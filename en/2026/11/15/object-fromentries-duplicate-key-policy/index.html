Why does Object.fromEntries keep only the last value for a key?

Entry order determines which value survives under a repeated key. Test both orders and decide whether your importer should keep the last value or report a collision.

Article

Key takeaways

  • The last write for a property key is the value in the result
  • Input rows remain available after conversion
  • Validate keys before conversion when duplicates should be rejected

The preferences import preview shows three rows. The theme is light on the first row, the time zone is UTC on the next, and the theme is dark on the last. After saving, there are two fields and the theme is dark. Swap the theme rows and the saved theme becomes light. The order that matters is the order of the entries you pass to Object.fromEntries.

How three rows become two properties

Each entry supplies a key and a value. The method iterates through the entries, writing the values to a new object. It writes light under theme, then UTC under timezone, then dark under theme. The final write replaces the value of the existing theme property.

The input still contains all three rows. What the result loses is the information you'd need to distinguish the earlier and later writes. Seeing dark in the object tells you nothing about whether light appeared earlier or which file row supplied the winning value. Keep the original rows if the application needs a record of the import.

The order in which a console displays the object's properties isn't a reliable way to diagnose an overwrite. You might still see theme above timezone after the second write to theme. To find the winning row, trace the input order and each value written under the conflicting key.

Test order and the duplicate policy separately

This script limits its inputs to string keys. It checks the original order, then swaps the duplicate rows. UTC survives both conversions and the theme changes. It also checks a reject-on-duplicate conversion, which validates its in-memory entries before constructing the object.

import assert from 'node:assert/strict';

const rows = [['theme', 'light'], ['timezone', 'UTC'], ['theme', 'dark']];
const opposite = [rows[2], rows[1], rows[0]];
const collapse = Object.fromEntries;

function unique(entries) {
  const keys = new Set();
  for (const [key] of entries) {
    if (keys.has(key)) throw new Error('Duplicate key: ' + key);
    keys.add(key);
  }
  return collapse(entries);
}

const examples = [
  [collapse(rows), {theme: 'dark', timezone: 'UTC'}],
  [collapse(opposite), {theme: 'light', timezone: 'UTC'}],
  [rows.length, 3],
  [unique(rows.slice(0, 2)), {theme: 'light', timezone: 'UTC'}],
];

const {deepEqual, throws} = assert;
for (const [actual, expected] of examples) deepEqual(actual, expected);
throws(() => unique(rows), /Duplicate key: theme/);
console.log('Both orders and the duplicate guard passed.');

The script passed in local Node. The original order yields dark, the opposite order yields light, and the original array still contains three entries. The rejecting converter accepts the two distinct rows and raises an error naming theme when the third row is present. Keep an assertion for that last path. Clean imports can't tell you whether the guard is working.

If your importer normalizes keys before conversion, use those normalized keys for the duplicate check as well. For example, a key with trailing whitespace and the same key without it are distinct strings. If you check the raw strings and trim them only when writing, the resulting properties can still collide.

Sometimes later entries winning is the intended contract. If you're applying shared defaults followed by personal preferences, document that sequence and build the list in that order. The swapped test pins down which source wins. If the two sources sometimes arrive in another order, decide which one has precedence before building the entries.

A file that allows each key only once needs a different policy. Find the collision before conversion and show both row numbers in the import preview. Counting the properties afterward can't distinguish a legal two-row file from a three-row file that overwrote one value.

A review workflow may need to preserve every value until a person chooses one. Keep the records as rows or group them by key. Write the property after confirmation, while the report can still tell the reviewer where each former candidate came from.

For a test fixture, three fixed entries are more useful here than many randomly generated distinct keys. UTC is a control: the collision leaves it alone. The theme assertion checks the actual winning value. If you check only that both outputs have the same number of properties, the wrong winning theme still passes.

Decide whether case matters at the import boundary too. Treating Theme as a separate field or folding it to lowercase leads to different collisions. The file contract determines the rule. Use one representation for checking and writing, while keeping the original spelling for a correction message.

If the production log only holds the saved object, capture conflict row numbers and the policy while constructing the entry list. Record that the theme appeared on rows one and three, with row three winning under the later-write rule. That gives someone a row to fix and a way to check ordering without putting the original values in the log.

What happens if an entry uses a Symbol key?

Object.entries leaves it out when converting back. Create const key = Symbol('source'), then convert [[key, 'upload']]. You can read upload from the new object's result[key]. Object.entries returns an empty array because it collects own enumerable string-keyed properties. Read by the original key, or inspect Object.getOwnPropertySymbols(result), to find the property.

The property still exists in this example. The export method is what omits it. If the application must export the entire object structure, decide which kinds of keys the format can preserve before choosing that method.

If the input is still raw JSON with repeated members, see how duplicate JSON members affect interoperability.
