Does Array.fromAsync pull the next item while a mapper is pending?

Use controlled gates to separate the next asynchronous pull, mapper scheduling, and output order.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-13 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • The next pull waits for the current mapper.
  • Output order alone does not show when work started.
  • Collecting work cannot retroactively control tasks already started.

The mapper for A has started and is waiting behind a gate. Has the producer already been asked for B? The method waits for the current mapper before pulling the next item. The finished array keeps A before B, but that order cannot tell you when either item started.

Observe the next pull

ECMAScript defines fromAsync for async iterables, sync iterables, and array-like inputs. Consider the async iterable branch first. It calls next and awaits the iterator result. If a mapper is supplied, it calls the mapper on the value and awaits the result before writing it and advancing. The next pull therefore depends on the current transformation finishing.

Imagine a small catalog adapter that produces one record per pull. If reads are lazy, the traversal cannot initiate its second read until it calls next again. The source can still prefetch on its own, and another caller can start work ahead of time. The collection method cannot put already started tasks back into a queue.

Two implementations can return the same ordered array through different schedules. One can wait before starting each item. Another can launch both tasks and assemble their results in input order. If scheduling matters, test the calls and completions themselves.

Use a gate to fix the observation point

The local Node fixture has two inputs, A and B. A’s mapper announces that it has started, then waits for the test to release it. Once the test receives that announcement, it can inspect the trace without waiting for an arbitrary number of milliseconds. The sample uses fixed strings and contacts no catalog.

import { deepEqual } from 'node:assert/strict';

const gate = () => Promise.withResolvers();
const { promise: waiting, resolve: release } = gate();
const { promise: began, resolve: markStarted } = gate();
const order = [];
const record = item => order.push(item);
const values = ['A', 'B'];
let index = 0;
const input = {
  [Symbol.asyncIterator]() { return this; },
  async next() {
    const value = values[index++];
    record(value ? 'pull ' + value : 'done');
    return { value, done: value === undefined };
  },
};
const result = Array.fromAsync(input, async value => {
  record('start ' + value);
  if (value === 'A') {
    markStarted();
    await waiting;
  }
  record('finish ' + value);
  return value.toLowerCase();
});
await began;
deepEqual(order.slice(), ['pull A', 'start A']);
release();
deepEqual(await result, ['a', 'b']);
deepEqual(order, [
  'pull A', 'start A', 'finish A', 'pull B', 'start B', 'finish B', 'done',
]);

const { promise: parallelGate, resolve: releaseParallel } = gate();
const launched = [];
const tasks = values.map(async value => {
  launched.push(value);
  if (value === 'A') await parallelGate;
  return value.toLowerCase();
});
deepEqual(launched, ['A', 'B']);
releaseParallel();
deepEqual(await Promise.all(tasks), ['a', 'b']);
console.log(JSON.stringify({ order, launched }));

Before release, only the pull and start of A should appear. After release, A finishes, then B is pulled and mapped. A final call reports completion. The expected trace follows from the fixed input and the controlled gate. The other branch uses map to create both tasks before awaiting the group. It starts B while A remains behind its gate. Both branches return a and b in that order.

The trace records the producer as well as the mapper. An implementation that pulls B early but delays its transformation could have the same mapper log as a serial implementation. If the producer itself can perform I/O, a producer trace is necessary to distinguish those cases. Internal prefetch needs its own observation point.

Decide which order is part of the contract

A transform that needs the previous item’s result has a reason to wait before the next pull. Independent work might justify bounded concurrency, with a separate rule for output order. The two-task example is small enough to demonstrate the difference without prescribing a production limit. An unbounded source also needs a stopping rule or incremental consumption before materializing an array.

Write separate acceptance conditions for the output order and the pull order. A proposed negative can make the first mapper reject, then inspect the collector’s rejection and whether this traversal ever requested B. Cleanup of the source and already started work needs separate evidence. Asynchronous forEach and completion covers the outer caller’s wait. Here the focus is what the producer and the mapper do before that wait ends.

Does a promise in an async iterator’s value field get unwrapped?

It depends on the path. For a direct async iterator without a mapper, the method awaits next’s result object and stores its value field. A promise in that field can remain in the array. A synchronous array uses the async-from-sync adapter, which adopts the value. Providing a mapper that returns the value also introduces the mapper-result await.

import { deepEqual, strictEqual } from 'node:assert/strict';

const inner = Promise.resolve('A');
const { fromAsync } = Array;
const collect = fromAsync.bind(Array);
function direct() {
  let used = false;
  return {
    [Symbol.asyncIterator]() { return this; },
    async next() {
      if (used) return { done: true };
      used = true;
      return { value: inner, done: false };
    },
  };
}

const [carried] = await collect(direct());
const [adopted] = await collect([inner]);
const [mapped] = await collect(direct(), value => value);
strictEqual(carried, inner);
deepEqual([adopted, mapped], ['A', 'A']);
console.log('direct value retained; sync wrapper and mapper awaited');

The first example used ordinary strings. This one changes the item shape and checks reference identity as well as the string result. Getting the completed array does not by itself tell the caller that every element is already a string.
