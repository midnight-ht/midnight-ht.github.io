Why does a deferred CMake call read a value set later?

Compare late evaluation and a captured value in a CMake configure run.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-13 · Estimated read 10 min
Translations
zh-CN en

Article

Key takeaways

  • Deferred arguments can read the value at execution.
  • Capture the scheduling-time value explicitly when needed.
  • Configure output and build output answer different questions.

The value is first when you schedule the call and second when it prints. CMake’s DEFER evaluates the variable reference when the command runs. Capture the value explicitly when the later command needs the earlier one.

Imagine a build maintainer handling two artifacts in the same directory. A callback should record the first artifact’s label after configuration reaches the end of the directory. The label is correct at registration. The next artifact changes it, and the log ends up attributing the second label to the first artifact. Quoting the variable reference in a deferred call does not capture the current string. CMake’s Deferring Calls reference

Give two callbacks the same assignments

Save this complete project as CMakeLists.txt and run cmake -S . -B out in its directory. It ran locally with CMake 4.2.3. The configure command exited zero and printed now=first, late=second, and frozen=first in that order. No subsequent build ran. DEFER was added in CMake 3.19.

cmake_minimum_required(VERSION 3.19)
project(deferred NONE)

set(label first)
message(STATUS "now=${label}")
cmake_language(DEFER CALL message STATUS "late=${label}")
cmake_language(EVAL CODE "
  cmake_language(DEFER CALL message STATUS [[frozen=${label}]])
")
set(label second)

The ordinary deferred call carries the reference forward. When it runs, the directory has already set the label to second. The other call uses EVAL to construct CMake code while the label is still first. By registration, the bracket argument contains the literal text frozen=first. The bracket form prevents it from being expanded again as an ordinary argument. The fixture uses a controlled short string. Inserting arbitrary input into generated CMake code would need a different approach. CMake’s Deferred Call Examples

The immediate message establishes the starting value. The late message proves that a later assignment can affect a deferred argument. The captured message checks the earlier value after that assignment. If both deferred messages print first, verify whether the final assignment actually ran. If both print second, check what was registered for the captured case. The configure exit status alone does not establish which value reached either callback.

Use a hard-coded value as a negative control

Replacing the capture with a literal first would produce the same output with this input. Change the initial label to alpha and leave the final assignment at second. The proposed check expects alpha immediately and in the captured callback, and second in the ordinary deferred callback. A hard-coded first would now fail. This extra input was not run in the local receipt described above.

Save the source path, output directory and source digest with the configure output. A reused console log can contain a correct value from another invocation. A project that also prints build-time messages can label the configure diagnostic so the two phases are easy to tell apart. This exercise establishes configuration behavior, not execution of a generated build command.

Decide which time belongs to the callback

A directory summary may need the final values accumulated throughout configuration. Late evaluation fits that task. An artifact record may need the value assigned at registration. Give each contract a distinct output and assertion. Looking only at the last log line can conceal earlier records that were all changed by the same later assignment.

For multiple registrations, compare each artifact ID and label as a pair. Finding both expected words somewhere in the log would miss a swap between artifacts. That check is proposed for an expanded fixture.

For complex inputs, consider storing data under a stable key at registration and letting the callback retrieve that record. This avoids generating executable code from arbitrary values. The bracket argument in the example is intentionally simple. If the question is which normal or cache binding CMake reads, see why an updated cache can still yield an older normal variable value. Here both callbacks use the same ordinary variable at different times.

Does an early return skip calls that are already deferred?

The manual says deferred calls still run at directory end after a return(). As a separate, unexecuted check, put an early return just before the last assignment and leave both registrations in place. The ordinary callback should now read first because the assignment to second never ran. Its message should still appear. If a branch must prevent an action entirely, avoid registering it or explicitly arrange to cancel it.
