Why can a Go recorder show a header that Result omits?

Use two handler paths to separate the mutable Go recorder headers from the snapshot in Result.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-13 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • The recorder’s Header gives the handler a mutable map.
  • Use Result after the handler finishes to inspect the response snapshot.
  • Test a real connection separately when the transport matters.

A Go handler can set an ordinary response header after writing the body. The recorder’s mutable header map can show that value, while Result’s response snapshot leaves it out. To test what the handler produced, wait for it to return and read the headers from Result.

Suppose a download handler adds a completion marker. A unit test calls the handler directly, finds X-After in the recorder’s header map, and assumes the client will get it. The browser does not. Put both observations in one test. One sees what the handler can still mutate. The other sees what had been set at the first write. This isolates a timing bug before investigating a proxy or deployment setting.

Look at the two observation times

ResponseRecorder’s Header method supplies a map the handler can mutate through ResponseWriter. The httptest reference says to call Result after the handler finishes. The response header snapshots the first write. If the handler never writes, it snapshots the headers when Result is called. The discussion here is about ordinary response fields, with no trailers or real HTTP connection. Go net/http/httptest.

The late write to the header map can show that the assignment occurred. Even a correct status, body, and early header cannot establish that the late header entered the response snapshot. Move an already available value before the first write. If the value is only known at the end of processing, decide whether to delay committing the response or give the client a different contract.

Change the assignment time in one fixture

This teaching test is unexecuted. Put it in an isolated Go test directory and use a toolchain with io.ReadAll support. The handler sets X-Before first. Both paths write ok. They differ in whether X-After is assigned before or after that write. The requests are constructed in memory, with no HTTP server.

package recorderdemo

import (
    "io"
    "net/http"
    "net/http/httptest"
    "testing"
)

func report(w http.ResponseWriter, r *http.Request) {
    h := w.Header()
    h.Set("X-Before", "ready")
    if r.URL.Path == "/fixed" {
        h.Set("X-After", "done")
    }
    _, _ = io.WriteString(w, "ok")
    if r.URL.Path != "/fixed" {
        h.Set("X-After", "done")
    }
}

type observation struct {
    status int
    body, mutableLate, responseEarly, responseLate string
}

func TestReportHeaders(t *testing.T) {
    for _, tc := range []struct {
        path, sent string
    }{{"/late", ""}, {"/fixed", "done"}} {
        t.Run(tc.path[1:], func(t *testing.T) {
            rec := httptest.NewRecorder()
            report(rec, httptest.NewRequest(http.MethodGet, tc.path, nil))
            res := rec.Result()
            defer res.Body.Close()
            body, err := io.ReadAll(res.Body)
            if err != nil {
                t.Fatal(err)
            }
            mutable, response := rec.Header(), res.Header
            got := observation{
                status: res.StatusCode, body: string(body),
                mutableLate: mutable.Get("X-After"),
                responseEarly: response.Get("X-Before"),
                responseLate: response.Get("X-After"),
            }
            want := observation{http.StatusOK, "ok", "done", "ready", tc.sent}
            if got != want {
                t.Fatalf("got %+v, want %+v", got, want)
            }
        })
    }
}

Both subtests should get status 200, body ok, and X-Before set to ready. The final mutable map contains X-After: done in both cases. Result.Header should yield an empty string for that header in the late path and done in the fixed path. Keeping only the mutable-map assertion would make both cases pass without detecting the bug. The positive control shows that the same response assertion can observe a header when it is set in time.

A lookup with Header.Get is sufficient for these nonempty markers. If the production contract distinguishes absence from an empty value, inspect key presence and the value list as well. Give multiple values their own expected shape.

Put the contract on the right observation

Recorder is useful for a direct handler test. Assert the response fields you need instead of comparing the entire Response with DeepEqual. The package documents that more fields may be populated in the future. Route the test through relevant middleware if it owns the header. A real HTTP connection or proxy test is a separate check for client-visible transport behavior. This fixture never observes one.

For an application control, run both the successful and failing requests. An error path may write the error status and then try to attach a request ID. Assert the error status, expected body shape, and request ID independently. If the middleware is responsible for the ID, include it in the test entry point. A deferred assignment at the end of a handler also needs to be checked against the first write.

Keep both observations when diagnosing a failure. The mutable map helps locate an assignment. Result shows whether it was present at the response boundary. Save the write point and the request path so the integration test can reproduce the same branch. The related Go test resource lifetime article describes another timing boundary involving the test tree.

What if the handler returns without writing?

Add an independent handler that sets X-Before and returns without calling Write, WriteHeader, or Flush. Result should snapshot the headers at that call, yielding ready with an empty body. Use a fresh recorder for this case. A recorder that has already seen a write would be testing a different condition. Call Result after the handler has finished. This follow-up is unexecuted and does not establish what a real HTTP server sends.
