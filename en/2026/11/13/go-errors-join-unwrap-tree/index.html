Why does errors.Unwrap return nil for a Go errors.Join value?

Use a joined error and an outer wrapper to distinguish Go’s one-step Unwrap from matching through an error tree.

Translations

Article

Key takeaways

  • The Unwrap helper only recognizes a method that returns one error.
  • Is and As can inspect an error tree.
  • A complete stage report needs each failure’s context.

Go’s errors.Join puts multiple errors into a tree. The errors.Unwrap helper only calls the method that returns one child, so it returns nil on a Join value. Use errors.Is or errors.As to test whether a target is still reachable in the tree.

Suppose an export fails and cleaning up the temporary resources fails too. The service joins both errors for the caller. An old logging utility repeatedly calls Unwrap until it gets nil. It suddenly stops finding the original errors and the counters based on them fall silent. Ask what the code is testing. A one-step unwrap asks for a single child. A match asks whether any node satisfies the target.

The two unwrap signatures serve different shapes

The Go errors package recognizes wrappers with two method signatures: one returns an error, the other returns a slice of errors. A non-nil Join result implements the slice-returning method. The Unwrap helper only calls the single-return method. It can therefore return nil for a value that wraps two non-nil errors. Is and As inspect the error and then visit each child’s tree in pre-order, depth-first order. Go errors package reference.

Wrap the joined value once more with a single fmt.Errorf %w and the first Unwrap can reach the join. A second call on that result returns nil. The nil comes from the helper’s method selection. An old loop that counts error categories through a chain needs another observation when it starts receiving trees.

Give the operation and cleanup separate identities

This teaching program is unexecuted and requires Go 1.20 or later. It constructs errors locally without running an export, closing a resource, or sending logs. Each wrapping layer has its own one-step expectation, while both should still match the two original sentinels.

package main

import (
    "errors"
    "fmt"
)

func main() {
    exportFailed := errors.New("export failed")
    cleanupFailed := errors.New("cleanup failed")
    joined := errors.Join(exportFailed, cleanupFailed)
    outer := fmt.Errorf("finish export: %w", joined)

    cases := []struct {
        label string
        candidate, expectedChild error
    }{
        {"joined", joined, nil},
        {"outer", outer, joined},
    }
    for _, c := range cases {
        child := errors.Unwrap(c.candidate)
        if child != c.expectedChild {
            panic(fmt.Sprintf("%s: unexpected child: %v", c.label, child))
        }
        for _, target := range []error{exportFailed, cleanupFailed} {
            if !errors.Is(c.candidate, target) {
                panic(fmt.Sprintf("%s: missing %v", c.label, target))
            }
        }
        fmt.Printf("%s: child as expected, both sentinels found\n", c.label)
    }
}

For joined, expect no single child and two successful matches. For outer, expect the original joined value as its single child and the same two matches. The program compares objects, so it does not need to parse error strings. If one branch were replaced with a new error constructed from the original text, the message might look the same while matching the original sentinel should fail. That negative control is unexecuted.

A real call-path test can inject an operation failure and a later cleanup failure, then inspect the caller-visible result. Add a case in which only one fails to make sure the service does not count a failure that never occurred. Verify that cleanup actually ran. This fixture checks the standard library’s error structure and matching only.

Choose the observation your caller needs

Use Is when the caller needs to know whether a particular failure occurred. Two targets can match at once, so mutually exclusive branches can drop one of the metrics. Use As when the caller needs a typed value. For a complete stage report, keep operation and cleanup context or deliberately traverse the wrapper shapes. One successful match says nothing about how many other failures a report should include.

Use the text for display and the wrapping contract for classification. An acceptance test can give different errors the same display text and verify that the caller still recognizes both. Adding context to an existing error should not change its classification when wrapping is preserved. The related QueryRowContext error article uses a sentinel to classify absence in a query. Here multiple original errors can be present together.

If a team needs every branch, verify both wrapper signatures and their combination explicitly. Keep each stage’s identity attached to its result. When only classification is required, the standard helpers avoid duplicating traversal. The example implements no custom walker or resource recovery.

A caller regression can exercise four outcomes: operation failure only, cleanup failure only, both failures, and neither. Compare the two counters independently and check the returned result. A user interface can choose one message to show while the reporting layer retains both failures. The fixture does not run that integration test.

Which value does As return if both branches match the same type?

Suppose the operation and cleanup produce the same pointer error type, with Step fields of export and cleanup. If the outer error itself does not match, joining export before cleanup should return the export value. Reverse the two inputs and expect cleanup. Use two independently constructed joins and a fresh target for each. This unexecuted check exercises first-match traversal, while a complete stage report still needs both results.
