Why does Intl.Segmenter still overcount words at word granularity?

Compare all word-granularity segments with the isWordLike count, then check positions against the original string.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-13 · Estimated read 10 min
Translations
zh-CN en

Article

Key takeaways

  • Word granularity produces iterable segments.
  • Use isWordLike to select word-like segments.
  • Document the locale and implementation behind the count.

Tea, cake! reads as two words, but the word-granularity iterator can return five segments. Intl.Segmenter also returns the comma, space, and exclamation mark. If your product counts the word-like results from this segmenter, filter on isWordLike before counting. Keep the source offsets if the same results also drive highlighting.

Word granularity still describes the text between words

ECMA-402 defines the segmentation method and the iterable result. A segment data record carries the input, segment, and start index. At word granularity it also carries isWordLike. The classification is implementation-dependent, with locale-sensitive tailoring recommended. Segments made entirely of whitespace or punctuation are generally not word-like, but the specification does not prescribe a single dictionary for every locale.

Imagine an editing tool that shows a word count and highlights a word for review. Counting all segments reports five, and the second segment is a comma. If the product measures word-like segments in the configured locale, use the same filtered records for counting and highlighting. Keep the full segment stream when you also need to inspect punctuation.

Check the count and offsets against the original string

The local Node example uses fixed English text. First write out Tea, the comma, the space, cake, and the exclamation mark. Joining them must reconstruct the input. Tea starts at zero and cake at five. These expectations follow from the written fixture before running the code.

import { deepEqual, equal } from 'node:assert/strict';

const text = 'Tea, cake!';
const { Segmenter } = Intl;
const segmenter = new Segmenter('en', { granularity: 'word' });
const pieces = Array.from(segmenter.segment(text));
const labels = pieces.map(({ segment }) => segment);
const words = pieces.filter(({ isWordLike }) => isWordLike);
const positions = words.map(({ segment, index }) => [segment, index]);

deepEqual(labels, ['Tea', ',', ' ', 'cake', '!']);
deepEqual(positions, [['Tea', 0], ['cake', 5]]);
equal(labels.join(''), text);
const { version, versions: { icu } } = process;
console.log(JSON.stringify({ version, icu, labels, positions }));

Counting every record yields five. Splitting on spaces happens to yield two chunks, but they still contain punctuation. The word-like filter keeps two source records with their positions. Use those offsets against the original string, before any later operation that collapses spaces or normalizes the text. If a transformation changes the string, calculate offsets on the string the reader will actually see or retain a mapping back to it.

State which word count the product uses

A reading-length indicator, a submission limit, and a search index can have different definitions of a word. A local estimate can use this classification with a documented locale. A count that rejects submissions should be reproducible at the receiving end, with agreed boundary fixtures. A search index might use additional language processing and should define that separately.

Record the runtime and ICU versions alongside the exact text, the selected locale, and the segment output when validating an upgrade. The fixed English example is designed to expose counting punctuation and spaces. It gives no fixed word counts for other languages or mixed scripts. Try a punctuation-only string and a mixed string with repeated spaces as separate checks. The complete segment stream should still reconstruct its source. The native textarea length limit concerns code units used by the browser’s control. This case concerns a word-like metric for editing.

Can index be read as a code point offset after an emoji?

No. Change the input to 😀 followed by a space and Tea. The emoji occupies two UTF-16 code units and the space occupies one. Tea starts at code unit offset three. The prefix contains only two code points. Using two in a string slice would start at the space. The earlier ASCII-only example could not distinguish the coordinates.

import { equal } from 'node:assert/strict';

const text = '😀 Tea';
const { Segmenter } = Intl;
const words = new Segmenter('en', { granularity: 'word' });
const [, , last] = words.segment(text);
const { index, segment } = last;
equal(segment, 'Tea');
equal(index, 3);
const prefix = text.slice(0, index);
equal(Array.from(prefix).length, 2);
equal(text.slice(index), 'Tea');
console.log('Tea starts at UTF-16 offset 3 and code point offset 2');

Name the coordinate in the interface and convert it only at a consumer that needs a different unit. Check offsets against the original input, especially when supplementary characters or combining sequences appear before the selected text.
