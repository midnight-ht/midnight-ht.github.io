Why do two blank CSV fields import as different PostgreSQL values?

Use three PostgreSQL CSV rows to distinguish a missing value, empty text, and a single space.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-13 · Estimated read 11 min
Translations
zh-CN en

Article

Key takeaways

  • Default CSV COPY distinguishes SQL NULL from empty text by quoting.
  • Verify the imported row ID, nullness, and text length.
  • Retest each input when the marker or FORCE options change.

With PostgreSQL’s default CSV settings, COPY FROM reads an unquoted empty field as SQL NULL and a quoted empty field as an empty string. A preview can make both look blank. Inspect the actual CSV bytes, then verify nullness and text length in the imported rows.

Imagine an issue import with an optional note. A missing note means the producer supplied no value. An empty string means the producer explicitly supplied empty text. A spreadsheet preview displays both cells as blank, and a row count makes both imports look successful. If the distinction belongs to the data contract, check how the producer represents each state and how the database reads it.

The quote marks carry information

PostgreSQL 18’s COPY reference defines the default CSV null marker as an unquoted empty field. A quoted empty field is non-null text. This applies to ordinary CSV mode with the default options. A custom NULL marker or the FORCE options can change the mapping. CSV does not have a universal null convention, so neither a filename nor a spreadsheet preview establishes the interpretation. PostgreSQL 18 COPY CSV format.

If a preprocessing tool turns both fields into the same value, saving a new CSV can lose the distinction. Retain a small input fixture and its generation method. Check whether the quotes are present before testing the imported values by row ID. An equal number of copied rows cannot reveal this kind of change.

Read the three rows separately

The following psql teaching input is unexecuted. Use a disposable database session and pass the whole block to psql. It creates a temporary table and uses COPY FROM STDIN. There is no header row. The third row has one ordinary space inside its quotes. A line consisting of backslash and dot terminates the inline input for psql. A database driver needs its own COPY input interface rather than sending this entire script as a query.

CREATE TEMP TABLE copy_notes (
    id int PRIMARY KEY,
    note text
);

COPY copy_notes (id, note) FROM STDIN WITH (FORMAT csv);
1,
2,""
3," "
\.

SELECT id, note IS NULL AS missing, length(note) AS chars
FROM copy_notes
ORDER BY id;

Expect missing true and chars SQL NULL for row 1. For row 2, expect missing false and chars zero. For row 3, expect missing false and chars one. The third row catches a different change: trimming a single space into an empty string. If the application intentionally trims the value, verify that separate path and specify what the trimmed field means.

Assert the boolean and length rather than relying on how a terminal formats blanks. If another stage applies defaults or normalizes values, inspect the first imported state before the transformation. An interface might label NULL as “not provided” and display empty text as blank. That is a downstream policy with its own acceptance test. This fixture does not exercise an actual database or interface.

Define the marker with the producer

If a producer cannot preserve the quote distinction, it can agree on a specific null marker. Define how a source can also send that marker literally. Test an unquoted marker and the same quoted text separately. With the usual CSV quoting behavior and a custom NULL marker, those rows can represent different results. Use an actual producer sample for integration testing so the consumer is not validated only against a handcrafted file.

For example, an unquoted MISSING marker can mean absence, while the quoted word MISSING can mean literal text. If the producer cannot control quoting at all, choose an unambiguous encoding or use a separate field for presence. The database cannot recover two intentions from identical bytes. Keep empty text as a third control under the new marker. This alternate contract was not exercised.

Also inspect files that have been resaved or processed in transit. A tool can drop quotes around empty content and still emit syntactically valid CSV. Pass the three-row fixture through the actual producer and exchange path, then verify all three imported states. The related COPY file ownership article covers which process reads a file. This example concerns the interpretation of the bytes after they are read.

For a failure report, record the row ID, expected nullness, actual length, import settings, and fixture digest. That gives you a way to separate a producer error, an option change, and a later normalization step. Keep the space-only control if whitespace is part of the contract. Real driver integration and application retention are outside this example.

What if the same column uses both FORCE options?

PostgreSQL 18 permits FORCE_NULL and FORCE_NOT_NULL on the same column in CSV COPY FROM. With the default null marker, the quoted empty field becomes SQL NULL and the unquoted empty field becomes an empty string. Repeat the first two input rows in a separate temporary table with FORCE_NULL (note) and FORCE_NOT_NULL (note) together in the WITH options. Expect false and zero for the first row, then true and SQL NULL for the second. This variation is unexecuted. Use a fresh table so duplicate IDs cannot mask the parsing behavior.
