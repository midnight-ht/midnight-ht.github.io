Why does HTTP 103 Early Hints not establish request success?

Record a loopback 103 and final 404 separately to distinguish advisory headers, final status, and content.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-13 · Estimated read 11 min
Translations

Article

Key takeaways

  • A 103 can provide hints for preparation.
  • The final response supplies the status and headers used to handle it.
  • A loopback event trace does not establish browser asset loading.

The server sends HTTP 103 and hints that the client may need style.css. The page request ultimately returns 404. Record two separate facts: a hint arrived, and the request ended with a 404. The 103 does not establish success, and its Link field does not become a final response header.

What the client can do with the hint

RFC 8297 defines Early Hints as an informational response. While preparing a final reply, a server can send header fields it is likely to include. The client can use them for speculative preparation, such as recognizing a preload link. The final response still supplies the headers used to handle it. The server might learn that its initial suggestion was incorrect or send only part of what the final response will contain.

HTTP’s informational status rules place 1xx responses before the final outcome. Here the application can record that it saw an early hint while leaving the request pending. It needs the final result before interpreting the body and recording success or failure. If the log merges fields into one generic header map, it can lose track of which response actually contained the value.

Keep two records for one loopback request

The complete Node example binds to loopback on an ephemeral port. It sends one hint containing a Link and a final 404 with no Link and the text missing. The client listens for information separately from the final response. The fixture specifies what must arrive before reading the observed output.

import { deepEqual } from 'node:assert/strict';
import { createServer, get } from 'node:http';
import { once } from 'node:events';

const link = '</style.css>; rel=preload; as=style';
const server = createServer((request, reply) => {
  reply.writeEarlyHints({ link });
  reply.writeHead(404, { 'Content-Type': 'text/plain; charset=utf-8' });
  reply.end('missing');
});
server.listen(0, '127.0.0.1');
await once(server, 'listening');

try {
  const { port } = server.address();
  const events = [];
  const final = await new Promise((resolve, reject) => {
    const request = get({ hostname: '127.0.0.1', port, path: '/' }, reply => {
      reply.setEncoding('utf8');
      let body = '';
      reply.on('data', chunk => { body += chunk; });
      reply.once('end', () => resolve({
        status: reply.statusCode, link: reply.headers.link ?? null, body,
      }));
      reply.once('error', reject);
    });
    request.on('information', ({ statusCode, headers }) => {
      events.push({ status: statusCode, link: headers.link });
    });
    request.once('error', reject);
  });
  deepEqual(events, [{ status: 103, link }]);
  deepEqual(final, { status: 404, link: null, body: 'missing' });
  console.log(JSON.stringify({ events, final }));
} finally {
  await new Promise((resolve, reject) => {
    server.close(error => error ? reject(error) : resolve());
  });
}

The first assertion verifies the hint and its resource relation. The second verifies the final status, headers, and body. Checking only whether an information event arrived would leave the final request outcome unverified. Merging the hint headers into the final headers would also fail the second assertion. This client records protocol events. It never opens a browser or fetches the hinted stylesheet.

Use one request identifier and keep the ordered informational events separate from the final result. If the connection fails before a final reply, leave the outcome unknown or mark it as a transport failure according to the application contract. Do not turn the latest visible interim status into a final code. If the application needs complete content, record final headers separately from body completion. Browser preparation, cache use, and rendering belong to separate observations.

Verify the real path in layers

Check a plain final response, a hint followed by success, and a hint followed by failure. Those tests exercise whether the application records each event in the right place. A browser test can then establish whether a hint reached the browser, whether it scheduled a fetch, and whether the final page used the resource. The loopback fixture has no proxy, gateway, or CDN and does not establish any of those outcomes.

A preload hint is more useful when the asset is likely to be used by the eventual view. A guessed resource can produce work the client never needs. Use measured evidence on the real path before making a performance claim. The 100 Continue upload exchange addresses when the client sends request content. This example is about advisory response headers and final processing.

If the second 103 omits the first Link, does the earlier hint still count?

It can still inform preparation. A first 103 can name style.css and a second can name script.js without repeating the earlier field. RFC 8297 permits more than one hint and does not require repetition. If the final reply omits Link, neither informational field is a final header. This changes the number of hints from the main fixture. Record both events and the independent final reply, then check separately what the client actually did with the hints.
