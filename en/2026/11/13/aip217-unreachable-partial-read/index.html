Can a successful cross-region list with unreachable entries be treated as complete?

Use two cross-region pages to separate pagination completion from source coverage under AIP-217.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-13 · Estimated read 10 min
Translations
zh-CN en

Article

Key takeaways

  • A successful cross-collection read can report unreachable scopes.
  • Retain each page’s gaps and any later recovery evidence.
  • Reaching the last page does not by itself prove full coverage.

A cross-region catalog call succeeds and returns two items from East, while West appears in unreachable. The client can use the returned items. It cannot conclude that West has no records. For a service following AIP-217, keep the results and reported coverage gaps visible through the end of pagination.

Interpret success within the scope that was read

Google’s AIP-217 guidance describes how a cross-collection read can report temporarily unreachable resource names. The field uses service-relative names without meaningful ordering. A West location name can indicate that the service could not read that scope on this call. It does not give a record count or a detailed cause. If the request names a specific parent collection and that parent is unreachable, the guidance requires failing the call.

A browse view may show the items it has with a clear indication of the missing scope. An export that promises complete coverage needs to keep the gap open or label its output as partial. The same response can serve both clients, provided they state different guarantees.

Keep a gap reported on an earlier page

Imagine a course catalog for East and West. The first reply contains east-A and east-B, reports West as unreachable, and supplies token p1. The second reply contains east-C, reports no gap, and ends the traversal. The absence of a new gap on the last page does not remove the first report.

This complete local Node fixture takes those two replies in order. It does not contact a catalog or test network pagination. The expected output follows from the response table: three East records, an end signal, and a gap report for West on page one.

import { deepEqual, equal } from 'node:assert/strict';

const west = 'projects/demo/locations/west';
const pages = [
  { items: ['east-A', 'east-B'], unreachable: [west], next_page_token: 'p1' },
  { items: ['east-C'], unreachable: [], next_page_token: '' },
];
function reviewPages(replies) {
  const items = [], pageGaps = [];
  let atEnd = false;
  for (const [page, reply] of replies.entries()) {
    const { items: found, unreachable, next_page_token: next } = reply;
    items.push(...found);
    if (unreachable.length) pageGaps.push({ page: page + 1, scopes: [...unreachable] });
    atEnd = next === '';
  }
  const coverage = pageGaps.length ? 'gap reported' : 'no gap reported';
  return { items, atEnd, pageGaps, coverage };
}
const report = reviewPages(pages);
deepEqual(report, {
  items: ['east-A', 'east-B', 'east-C'],
  atEnd: true,
  pageGaps: [{ page: 1, scopes: [west] }],
  coverage: 'gap reported',
});
const lastOnly = pages.at(-1);
equal(lastOnly.unreachable.length, 0);
console.log(JSON.stringify(report));

A client that keeps only the last page’s metadata would see zero unreachable entries and might report complete coverage. A count of three also cannot rule out missing West records. Store page identity with the coverage observation. An empty page with a continuation token explains when to advance. A client can reach the right stopping point and still have incomplete results.

The reported name can denote a wider scope than an individual record. AIP-217 also permits a documented cap after grouping scopes. Do not interpret the number of reported names as the number of missing rows, or generate record-level retries from a region-level report.

A follow-up read may supply new recovery evidence. Track which earlier scope it covers instead of treating the historical report as permanent or erasing it when a later page omits the name. The fixture reports a gap seen during a traversal, and does not claim that West remains down.

Preserve the default when adopting partial success

An existing API might fail whenever one location is unreachable. Its callers can reasonably depend on that default. The AIP’s migration guidance retains it and introduces return_partial_success together with unreachable. A caller that needs usable partial data can opt in where the query supports it.

A compatibility check can run the same simulated West outage with and without the new option. Verify that the old caller keeps its documented failure and the opted-in caller can identify the missing scope. Then check that the interface distinguishes a successful empty read from an unreadable region. These are proposed integration checks. The code above tests the local aggregation only.

What if West recovers but its items sort before the first page boundary?

Do not insert them on the next page if that breaks the ordering contract. AIP-217’s pagination rules admit recovered results only when the paging parameters permit them, including documented default ordering. The main fixture had no recovered records. Here availability changes after the cursor passes the relevant position. Use a separate compatible read if the caller needs those records, and record what that read actually recovered.
