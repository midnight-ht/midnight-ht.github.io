Can Docker reuse a copy layer after the base changes?

Keep an artifact constant and compare conventional Docker COPY with an independent COPY --link layer.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-13 · Estimated read 10 min
Translations
zh-CN en

Article

Key takeaways

  • Linked copy reduces dependency on preceding layers.
  • Check final image contents separately from cache hits.
  • Verify assumptions about the destination before migrating.

The artifact stays the same, but an updated runtime can invalidate a conventional copy step. With COPY --link, a compatible builder can make the artifact copy independent and combine it with the updated runtime state.

A maintainer changes one runtime setting and sees the build handle the same artifact again. There are two questions to answer. Did the builder reuse an existing copy layer? Does the final image have both the intended runtime and the intended artifact? Build logs and file checks provide different evidence.

Separate the copy from its preceding state

The Dockerfile reference for COPY --link describes copying source files into an empty destination and turning that result into a layer. The builder then combines it with the preceding image state. An ordinary copy can be invalidated when that state changes. A linked copy can reuse its result when suitable cached data are available, even if the preceding layers change.

This matters when the artifact is built in one stage and installed in another. Updating the runtime may leave the artifact unchanged. Updating the artifact is a separate input change. Test both cases before attributing all cache behavior to the earlier layers. The site’s Docker package-index cache article examines when an installation command reruns. Here the question is what the copy step depends on.

Change one preceding file and keep the artifact constant

This complete Dockerfile is an unexecuted example for a BuildKit builder and frontend that support linked copy. Save it in an otherwise empty context with a payload.txt file containing artifact-v1 and a newline. Both final stages share the earlier stage. The destination is an ordinary path that does not already exist. Use the same resolved base image across the comparison so a moving tag cannot introduce another change.

# syntax=docker/dockerfile:1
FROM alpine:3.22 AS earlier
ARG BASE_MARK
RUN printf '%s\n' "$BASE_MARK" > /runtime-mark

FROM earlier AS regular
COPY payload.txt /opt/demo/payload.txt

FROM earlier AS linked
COPY --link payload.txt /opt/demo/payload.txt

Build both targets with one builder, platform, and context. Start with an old runtime marker, then change it to new while retaining the previous build cache. The following commands are intended for an isolated teaching environment.

set -eu
for mark in old new; do
  for target in regular linked; do
    docker build --progress=plain --target "$target" \
      --build-arg "BASE_MARK=$mark" -t "copy-lab:$target-$mark" .
  done
done

The loop stops at the first failed build. Keep that result before interpreting subsequent cache behavior.

Both new images should contain new in /runtime-mark and the original contents at /opt/demo/payload.txt. Read them with cat in the example image or compare file digests using your normal image inspection method. Save all four build outputs with their image identities. The whole image identity can change even when the copy layer is reused, so it cannot settle the layer question by itself.

A conventional copy can lose its cached result when the earlier state changes. The independent result remains eligible for reuse if the builder has the relevant data. Check the actual step log before claiming a hit. A different builder instance, platform, or cache source may change the result. Identical payload contents alone cannot distinguish a reused layer from a fresh copy.

For a negative control, leave the runtime marker at new and replace the payload with artifact-v2. Build both targets again. Both images should now contain the new payload even if the earlier runtime step was cached. This checks that the artifact itself still participates in the input. Keep the artifact and marker observations separately so a correct marker cannot mask an old payload.

Move only copies that can stand on their own

An artifact installed at an explicit ordinary path is a good candidate for linked copy. Review any later instructions that read it or change its permissions, then verify the resulting image with the intended runtime user. Reusing an artifact layer cannot establish that the application starts or that a registry holds the intended image.

For a build split across nodes, check how each node obtains earlier cache data before predicting reuse. This example did not run, time a build, import remote cache, or exercise a registry-side rebase.

What if a previous layer made the destination a symlink?

A linked copy cannot follow a destination symlink from the preceding state because it does not read that state. The linked destination path is made of directories. If the base image uses /opt/current as a symlink to a versioned directory, decide where the artifact must land. Use ordinary copy if following that link is part of the contract, or use an explicit physical path and verify where the runtime reads from. The main fixture uses a regular destination and does not test symlinks.
