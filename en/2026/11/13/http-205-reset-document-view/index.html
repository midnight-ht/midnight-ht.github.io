Why can an empty HTTP 205 reset the data-entry view?

Compare 204, 205, and a failure with a nonempty default category to decide when a data-entry view should reset.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-13 · Estimated read 10 min
Translations
zh-CN en

Article

Key takeaways

  • A 205 expresses a request to restore the view that initiated the request.
  • Restoring original values can preserve nonempty defaults.
  • The application needs an explicit policy for failure or a newer draft.

The data-entry view starts with Books as its category. The user changes it to Stationery for this record. If the server returns HTTP 205 and the application restores the view, the category returns to Books. An empty response body does not mean all the restored fields should be empty.

RFC 9110 defines 205 Reset Content as a fulfilled request with an intent to restore the document view that caused it to be sent. It supports repeated entry through a form, notepad, or similar interface. The server must not generate response content. The original state therefore needs to be established by the interface, rather than read from a response payload.

A 204 response also has no content, but it carries no specific reset instruction. The 204 parsing contract covers why an empty success reply should not be parsed as JSON. Here the decision is which view state to retain after the response has arrived. The sample keeps the draft for 204 as a product choice.

Keep original values, current values, and the result distinct

Consider an inventory entry view with Books as its initial category and an empty note. This record changes the category to Stationery and adds pen as the note. Under the sample contract, 204 reports saved and retains both current values. A 205 reports saved and restores Books and the empty note. A 500 leaves the draft in place and reports an unconfirmed outcome. An error code alone need not establish what happened to external writes.

The complete local Node fixture passes statuses directly into a state transition. It does not send HTTP, run a browser, or persist a record. The expected states come from the input and the three specified outcomes.

import { deepEqual, notDeepEqual } from 'node:assert/strict';

const original = { category: 'Books', note: '' };
const draft = { category: 'Stationery', note: 'pen' };

function afterSave(status, values) {
  if (status === 205) return { outcome: 'saved', values: { ...original } };
  if (status === 204) return { outcome: 'saved', values };
  return { outcome: 'unconfirmed', values };
}
const outcomes = [204, 205, 500].map(status => afterSave(status, { ...draft }));
deepEqual(outcomes, [
  { outcome: 'saved', values: { category: 'Stationery', note: 'pen' } },
  { outcome: 'saved', values: { category: 'Books', note: '' } },
  { outcome: 'unconfirmed', values: { category: 'Stationery', note: 'pen' } },
]);
notDeepEqual(outcomes[1], {
  outcome: 'saved', values: { category: '', note: '' },
});
console.log(JSON.stringify(outcomes));

The negative clears both fields. A check that looks only at the note would miss the error, since the note is empty after both a correct reset and a blanket clear. Include a field with a default, a field without one, and the failure case. If a saved record reference belongs in a receipt area, verify it independently from the next-entry controls.

An implementation can use native form reset for the relevant controls. HTML’s reset algorithm also allows the reset event to be canceled. An application that manages its own model needs to keep that model, validation, and visible controls aligned. Reading an empty control does not establish that the next render or submission uses the intended values.

Give the reset a scope

A repeated-entry form can sit beside a warehouse filter. The form may reset to defaults for that warehouse while the surrounding filter stays in place. If the user moved to a new warehouse, check whether the response still belongs to the current view before applying defaults from the older one. The status carries reset intent. View identity is an application concern.

An acceptance check can record the response, view identity, before-and-after values, receipt, and the next submitted input. A success notice does not prove the entry view is ready, and a cleared field does not prove the saved result. An autosave action may need a different view policy from a deliberate submit.

What if a 205 arrives after the user has started the next draft?

Check which draft was submitted. Suppose the request carries draft version seven, and the user edits again while waiting, creating version eight. The response can confirm version seven. If editing remains available during the request, only apply the reset to the view that still belongs to the submitted version. Another design temporarily prevents editing until the request completes and the next entry starts. The main example had no concurrent editing, so a late reply needs its own test.
