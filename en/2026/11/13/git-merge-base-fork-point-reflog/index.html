Why does a rewritten upstream put one extra commit in my topic range?

Use a small Git graph and two local tracking refs to verify the replay range after an upstream rewrite.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-13 · Estimated read 11 min
Translations
zh-CN en

Article

Key takeaways

  • A former upstream tip can produce a different boundary from the merge base.
  • Inspect the full candidate commit list before replay.
  • Local reflog history determines whether the historical boundary is available.

The upstream dropped an old commit. The graph still gives a valid merge base, but using it as the replay boundary includes one extra commit. Git’s merge-base --fork-point can use the local tracking ref’s history to recover the former upstream tip.

You started a topic branch from the upstream tip and are preparing to replay it onto a rewritten upstream. The candidate list includes an old upstream change as well as your own work. The graph explains why it appears: that change is now reachable from the topic alone. Before replaying it, establish whether it was one of your changes or a change upstream deliberately discarded.

Two answers from one commit graph

Let R be the shared base. The old upstream adds U, and the topic adds T on top of U. The upstream then goes back to R and replaces U with V. That makes R the ordinary merge base, so the range from R to the topic includes U and T. If the local tracking ref once pointed at U, its reflog records that earlier tip. Fork-point considers those former tips and finds U in this graph. The remaining range contains only T. Git merge-base documentation on fork-point

R correctly answers the graph question about the two current tips. U answers where work on this topic began. This exercise checks the list you would feed to a later operation. It does not replay anything. A correct boundary still leaves the application of those patches and any conflicts to verify.

Give two tracking refs the same current tip

The following script creates an isolated repository with four empty commits. It ran with Apple Git 2.50.1. The graph-based range listed U and T, and the fork-point range listed T. The tracking ref without U in its reflog produced exit status one and no output. The whole script exited zero without accessing a remote or changing an existing repository.

set -eu
case_dir=$(mktemp -d)
trap 'rm -rf "$case_dir"' EXIT
cd "$case_dir"
git init -q -b base
git config user.email fixture@example.invalid
git config user.name Fixture
git config commit.gpgSign false
git commit -q --allow-empty -m R
r=$(git rev-parse HEAD)
git commit -q --allow-empty -m U
u=$(git rev-parse HEAD)
git update-ref --create-reflog refs/remotes/origin/main "$u"
git switch -q -c topic
git commit -q --allow-empty -m T
git switch -q -c rebuilt "$r"
git commit -q --allow-empty -m V
v=$(git rev-parse HEAD)
git update-ref refs/remotes/origin/main "$v"
git update-ref --create-reflog refs/remotes/other/main "$v"

graph_base=$(git merge-base origin/main topic)
fork=$(git merge-base --fork-point origin/main topic)
test "$graph_base" = "$r"
test "$fork" = "$u"
ordinary=$(git log --reverse --format=%s "$graph_base..topic")
selected=$(git log --reverse --format=%s "$fork..topic")
test "$ordinary" = "$(printf 'U\nT')"
test "$selected" = T
set +e
missing=$(git merge-base --fork-point other/main topic)
status=$?
set -e
test "$status" -eq 1
test -z "$missing"
printf 'ordinary:\n%s\nfork-point:\n%s\nmissing: exit=%s, bytes=%s\n' \
  "$ordinary" "$selected" "$status" "${#missing}"

The script checks the exact base objects before checking the commit lists. For a real topic, record full object IDs alongside the subjects. Two commits can have the same title. Save the resolved topic and upstream tips, then list the proposed replay range from oldest to newest. Find the extra commit and establish who introduced it before deciding whether it belongs in the new history.

The negative case points a second tracking ref at V. It uses the same repository objects and the same topic, but the second ref never pointed to U. This is how two local repositories can disagree even when they can draw the same graph. Inspect the actual tracking ref with git reflog show origin/main. A clone might never have observed the old tip, or its reflog may have expired. Preserve the failure when fork-point cannot determine a base. Passing an empty result onward or silently using the ordinary merge base can change the range.

Keep the evidence behind the replay boundary

A recorded original base can be more useful than reconstructing one after the fact. Look for the full object ID in a branch creation record, release note, or build input record. If you have only the current graph, review the full candidate list and establish where each questionable change came from. Before comparing notes across repositories, check that both observers used the same topic tip.

Save the topic tip, chosen boundary and intended commit list before replay. The example has no merge commits. On a topic with merges, decide whether the operation must preserve topology and verify that separately. Once the changes have been applied to the new base, run the relevant behavior checks. If the question is whether a particular original object is already reachable, see the distinction between matching trees and shared ancestry.

What if the topic started at the parent of the former upstream tip?

Suppose the tracking ref began at U, but the developer deliberately created the topic from R, its parent. Even a complete reflog of that ref has no old tip at R. The ordinary merge base can still be R. Fork-point cannot recover R as a former tip from that reflog. Use an independently recorded base or review the exact candidate range when the topic started behind the upstream tip.
