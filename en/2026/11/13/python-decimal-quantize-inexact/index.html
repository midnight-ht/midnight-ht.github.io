Why does Inexact reject 1.234 but accept 1.230?

Use three executed Python Decimal inputs to separate a quantization signal from a rule about how a reading is written.

Article

Key takeaways

  • Rounded can be set when only zeros are discarded.
  • An Inexact trap can reject a change in numeric value.
  • A lexical contract needs access to the original token.

Quantizing Decimal('1.230') and Decimal('1.234') to two places discards a digit from each input. Inexact traps only the second case, because discarding the zero preserves the first value. A rule about how many places the caller may write still needs a representation check.

Suppose a device sends measurement strings and a warehouse stores values in hundredths. The import team traps Inexact to stop silent changes to a reading. An input with three fractional digits still gets through when the final digit is zero. That fits a contract about exactly representable values. A format contract that allows at most two written fractional digits would reject the same input. Both contracts can produce the same output format for accepted readings.

Decide what kind of change matters

Python’s quantize adjusts the result to the exponent of its second operand. For the finite numbers here, a quantum of 0.01 produces exponent minus two on success. Rounded is set when digits are discarded, even if they are zeros. Inexact means discarded nonzero digits changed the value. The two-place input sets neither signal. The trailing-zero input sets Rounded only, and 1.234 sets both. Numeric equality cannot show that distinction because the first two inputs are equal in value. Python Decimal quantize and signals.

A local context lets a test observe the flags or trap Inexact before using a changed value. Clear flags before reading an individual operation’s result. A flag that was set during one operation does not clear itself when a later operation has nothing to signal. Explicit settings fix precision and rounding explicitly so its observations do not depend on the caller’s active defaults.

Verify the three inputs separately

The program uses decimal strings. It ran locally on Python 3.11.15, and the archive contains the actual output and hash of the exact shared code. It does not run the import service or exercise storage.

from decimal import Decimal, Inexact, Rounded, ROUND_HALF_EVEN, localcontext

cent = Decimal("0.01")
cases = [
    ("1.23", "1.23", False, False),
    ("1.230", "1.23", True, False),
    ("1.234", "1.23", True, True),
]
with localcontext() as ctx:
    ctx.prec = 12
    ctx.rounding = ROUND_HALF_EVEN
    ctx.traps[Inexact] = False
    ctx.traps[Rounded] = False
    for text, rendered, rounded, inexact in cases:
        ctx.clear_flags()
        actual = Decimal(text).quantize(cent)
        observed = (str(actual), ctx.flags[Rounded], ctx.flags[Inexact])
        assert observed == (rendered, rounded, inexact), (text, observed)
        assert actual.as_tuple().exponent == -2
        print(text, observed, actual.as_tuple().exponent)

    ctx.traps[Inexact] = True
    ctx.clear_flags()
    assert Decimal("1.230").quantize(cent) == Decimal("1.23")
    try:
        Decimal("1.234").quantize(cent)
    except Inexact:
        print("1.234 trapped")
    else:
        raise AssertionError("expected Inexact for 1.234")

All three results render as 1.23 and have exponent minus two. Each case checks Rounded, Inexact, and the exponent for each input, then turns on the Inexact trap. The trailing-zero case still succeeds and the nonzero case raises Inexact. The last discarded digit is four, so half-even produces 1.23. A halfway value is outside these checks. A change in rounding policy deserves its own boundary inputs.

The assertions are suitable for running the teaching program without optimization. An importer should explicitly handle the trap and any invalid input formats. Retain a record identifier and classify malformed text, an out-of-range coefficient, and discarded nonzero digits separately. Those outcomes may need different corrections upstream.

Test written form where you still have the token

Suppose a later rule allows at most two fractional digits and disallows exponent notation. Try 1.23, 1.230, and 123E-2 at the text boundary. The first fits the sample rule. The other two can represent the same number and still violate it. Keep the numeric and lexical expectations separate so a failure tells you which policy changed.

Check where the application first quantizes. If it takes a string that was already reformatted by another stage, it can only observe that new representation. An import test can record the incoming token and the error category. A consumer test can check the measurement, display format, and source identifier separately. When the caller needs only a normalized value, the application may allow extra zeros while refusing actual changes. A related Decimal input article covers a different issue involving construction from floats. This fixture uses decimal strings throughout.

A useful additional test would quantize 1.234 and then 1.23 in the same context without clearing flags. The second inspection could still see Inexact from the first input. Bind each observation to an operation so a previous row’s flag cannot be reported as the next row’s error. This repeated-call check remains unexecuted.

Why could an input with two places still raise InvalidOperation?

Try quantizing Decimal('1.23') to 0.01 with a context precision of two and the InvalidOperation trap enabled. The expected exception comes from the coefficient needing three digits. This limit is independent of whether rounding changes the number. Keep enough coefficient digits for the accepted range, or give coefficient overflow and Inexact separate error categories. The small-precision variation was unexecuted. The three main inputs fit comfortably in the configured precision of twelve.
