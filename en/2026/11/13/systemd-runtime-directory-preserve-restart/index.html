Why did a runtime file disappear after systemd restarted the service?

Compare systemd runtime-directory cleanup across a direct restart and an explicit stop.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-13 · Estimated read 10 min
Translations
zh-CN en

Article

Key takeaways

  • Check the original marker as well as the directory.
  • A direct restart and a separate stop and start have different boundaries.
  • Use storage with a suitable lifecycle for durable data.

The restarted service has its runtime directory again, but a marker from the previous run is gone. If systemd manages the directory through RuntimeDirectory, check RuntimeDirectoryPreserve. Cleanup can remove the old directory before startup creates it again.

A maintenance script leaves a marker so the next service process can pick up a piece of work. After restart, the directory exists and the marker is absent. The application could have deleted the file, or the manager could have removed the whole directory. Use an inert service and write the marker yourself to separate those paths.

What operation did the manager receive?

For a system service, RuntimeDirectory creates the named directory under /run. The default preserve setting is no, so the directories are removed when the service stops. With restart, they survive a manual restart and an automatic restart triggered by Restart=. With yes, the manager also leaves them in place on an explicit stop. This article uses the systemd 262 manual. The option was added in 235. systemd.exec reference for RuntimeDirectoryPreserve

The difference matters when an operator replaces one restart command with a stop and a later start. The service can return to the same running state while the two procedures leave different files behind. Record the actual management commands before blaming the next process for a missing marker.

Compare a restart and a stop with an inert service

The following lab is for an isolated Linux machine. It has not been executed here. Install this complete definition as zy-runtime-lab.service, using a directory that no other service owns. Its process only sleeps. The observer creates the marker.

[Unit]
Description=Runtime directory lifecycle lab

[Service]
RuntimeDirectory=zy-runtime-lab
RuntimeDirectoryPreserve=no
ExecStart=/bin/sleep infinity

Run systemctl daemon-reload and start the unit. Confirm that /run/zy-runtime-lab exists and write a marker with the value first-run. Run systemctl restart zy-runtime-lab.service. Once it returns, inspect the directory and read the marker if present. Write a fresh marker with the value explicit-stop and run systemctl stop zy-runtime-lab.service. Inspect both before starting the unit again.

Repeat both checks with the preserve setting changed to restart, then with it set to yes. Stop the dedicated unit and clear any leftover lab directory between trials, reload the definition and use fresh markers. These are documentation-based expectations.

Preserve setting After restart returns After explicit stop, before starting again
no Directory exists, original marker absent Directory removed
restart Directory and original marker retained Directory removed
yes Directory and original marker retained Directory and marker retained

Checking only that the directory exists after a restart would give the same result in all three cases. The original marker distinguishes preservation from recreation. Looking after a later start would also hide what happened at the explicit stop. Write down the operation, service state and observed marker value for each trial.

Record a failed service command before interpreting the marker. A failed startup or a permission error needs its own diagnosis. Neither is the expected missing-file result in the table.

Match preservation to what the file represents

Choose default cleanup if temporary state belongs only to the current process generation. A service that needs to hand a short-lived file across restarts while clearing it on explicit stops can use restart. With yes, later operators can encounter old state even after the unit was stopped on purpose. Decide who reads it, how to identify its generation and when it becomes stale before retaining it.

A leftover socket pathname cannot tell you whether a process is listening. This lab only reads a marker. Check actual connectivity and the serving process generation separately. If you are diagnosing when a manager acknowledges an application configuration change, see why reload can return before the new configuration applies.

After the lab, stop the dedicated unit, remove the definition and the files created for it, and reload the manager. Keep the trial directory separate from other services so both the cleanup and the resulting observations have a clear scope.

Does yes preserve the directory across a machine reboot?

For system services, the manual notes that reboot removes these runtime directories because /run is a tmpfs. The preserve setting governs cleanup around the unit’s lifecycle. If the application needs the last confirmed state after a machine reboot, choose durable storage and verify recovery separately. A surviving marker after a unit restart provides no evidence for that recovery case.
