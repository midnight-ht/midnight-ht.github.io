Why does array_agg return {NULL} for a parent with no children?

Use three PostgreSQL customers to distinguish a null-extended row, a real null note, and an empty response array.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-13 · Estimated read 10 min
Translations
zh-CN en

Article

Key takeaways

  • array_agg can include the null value supplied by an outer join.
  • Filter by a non-null child key to preserve real null-valued children.
  • Verify SQL NULL, an empty array, and a null element separately.

PostgreSQL can return an array containing NULL for a customer with no notes. A left join supplies one null-extended row, and array_agg includes that row’s value. Filter by a non-null child key if null values from real notes need to survive.

Suppose an export includes each customer ID and a list of notes. One customer has no note. A second has a note whose text is still unset. A third has two notes. The first two cases both have a blank text value in the joined data. A consumer that distinguishes “no notes” from “a note still needs text” needs a way to identify the actual child row.

A left join already supplied an input row

PostgreSQL preserves an unmatched left row and fills the right-side columns with NULL. The nonarray overload of array_agg includes null inputs. With no matching notes, it still sees one row and produces an array with a null element. With truly zero input rows, it returns SQL NULL. An array containing NULL, SQL NULL, and an empty array describe three different outcomes. PostgreSQL 18 aggregate functions.

An aggregate FILTER controls which rows enter that aggregate. The fixture tests the note ID because a real note has an ID even if its text is unset. A null-extended row has no ID. Filtering on non-null note text would also remove the real note for customer 2. Putting the ID condition in the query’s WHERE would drop customer 1 before grouping. PostgreSQL 18 aggregate expressions.

Write down each customer’s expected row

This PostgreSQL 18 teaching query is unexecuted. The values clauses define the whole fixture, including the assumption that real note IDs are non-null. Aggregate order follows note ID. The third customer gets beta before alpha so a consumer that sorts by text can be detected.

WITH customers(customer_id) AS (VALUES (1), (2), (3)),
     notes(note_id, owner_id, label) AS (
       VALUES (21, 2, NULL::text), (31, 3, 'beta'), (32, 3, 'alpha')
     ),
     rollup AS (
       SELECT customer_id,
              array_agg(label ORDER BY note_id) AS raw,
              array_agg(label ORDER BY note_id)
                FILTER (WHERE note_id IS NOT NULL) AS matched,
              count(note_id) AS actual_notes
       FROM customers LEFT JOIN notes ON customer_id = owner_id
       GROUP BY customer_id
     )
SELECT customer_id, raw, matched, actual_notes,
       coalesce(matched, ARRAY[]::text[]) AS response_array
FROM rollup
ORDER BY customer_id;

For customer 1, expect raw {NULL}, matched SQL NULL, actual_notes zero, and response_array {}. For customer 2, expect one note and {NULL} in each array column. For customer 3, expect two notes and {beta,alpha} in each array column. Verify the customer IDs, array lengths, element values, and order separately. Three output rows alone cannot detect an unwanted null element in the first customer’s response.

Give the client decoder a separate check for SQL NULL, an array with a null element, and an empty array. A client that discards null elements can hide an editable note. This fixture gives SQL expectations and does not exercise a driver or API response.

Choose the array shape from the consumer contract

If the interface lists only completed note text, filtering on text can be intentional. If it lets users edit unfinished notes by identity, a text array may be insufficient. The response can carry an object with an ID under a separate contract. The ID in this query is only the SQL existence marker. Apply an empty-array default when it expresses the policy, and preserve any distinct business meaning of a missing value.

Run two negative controls on the same fixture. Filter the aggregate by non-null text to see customer 2 lose its real null element. Move the child-ID condition to the query WHERE to see customer 1 disappear. These failures distinguish the scope of an aggregate filter from the scope of a query filter. The related LEFT JOIN condition article covers matching and post-join filtering.

In a multitenant application, also verify the join keys include the intended ownership scope. Two customers with the same local ID in different tenants give an independent association test. The example does not exercise that production condition.

What if joining tags duplicates a real note?

Suppose note 21 has two tags. Bringing both tag rows into the aggregate input can produce two copies of that note ID. Both pass the existence filter. Check input cardinality by note ID before aggregating. Aggregate tags separately or finish the note array before adding the tags. Add two different note IDs with the same text to verify the fix preserves both. This unexecuted follow-up concerns duplicate real rows, independently of null extension.
