Why did assertLogs pass when my normal handler saw nothing?

Use an executed unittest fixture to distinguish temporary capture from normal handler delivery in CPython.

Updated 2026-11-13 · Estimated read 10 min

Article

Key takeaways

  • assertLogs checks a temporary observation point.
  • Normal handler delivery needs an independent test.
  • Restored settings do not establish isolation during the capture.

In CPython, assertLogs can capture a message even though the logger’s usual handler receives nothing. The test context temporarily replaces the selected logger’s handlers. Test normal delivery in a separate window that lets the real handler receive the record.

Suppose an export module needs both an accepted event and a record delivered through its configured logging route. A passing assertLogs check can establish that the message reached the temporary capture. It cannot establish that the configured handler saw it. Inspect those results independently before marking both requirements as satisfied.

See what the capture context changes

The unittest reference says assertLogs matches qualifying records from the named logger or its children. At least one record must match. The returned helper exposes LogRecord objects in records and formatted strings in output. Use those records to identify which source, level, and fields satisfied the assertion. Python 3.14 unittest.

The CPython 3.14.10 implementation saves the selected logger’s handlers, level, and propagation setting on entry. It installs a capture handler, sets the level, and turns off propagation from that logger. It restores the saved settings when it exits. These are implementation details of that pinned version, separate from the public matching contract. CPython v3.14.10 logging assertion implementation.

Give the capture and the usual handler different records

The fixture creates a private logger instance and an in-memory handler. It changes no root logger and connects to no service. The exact standard-library program ran locally on CPython 3.11.15. That runtime receipt is separate from the pinned source citation.

import logging
import unittest

class MemoryHandler(logging.Handler):
    def __init__(self):
        super().__init__()
        self.events = []

    def emit(self, record):
        self.events.append(record.getMessage())

class TestLogDelivery(unittest.TestCase):
    def test_capture_and_normal_handler(self):
        audit = logging.Logger("fixture.audit", logging.WARNING)
        ordinary = MemoryHandler()
        audit.addHandler(ordinary)
        try:
            with self.assertLogs(audit, level="WARNING") as captured:
                audit.warning("export accepted")
                while_captured = tuple(ordinary.events)

            restored = audit.handlers == [ordinary]
            audit.warning("export complete")
            observed = {
                "during": while_captured,
                "capture": [event.getMessage() for event in captured.records],
                "restored": restored,
                "after": ordinary.events,
            }
            self.assertEqual(observed, {
                "during": (), "capture": ["export accepted"],
                "restored": True, "after": ["export complete"],
            })
            print(observed)
        finally:
            audit.removeHandler(ordinary)
            ordinary.close()

if __name__ == "__main__":
    unittest.main()

The capture should record export accepted, with no messages in the ordinary handler’s list. After the context exits, record whether the original handler is installed and send export complete. Expect the ordinary handler to hold only the second message, with the previous capture unchanged. The archived run passed those assertions. Distinct messages make it easier to detect a test reading the wrong observer.

The memory handler verifies the route to that handler. A production route can include filtering, formatting, buffering, or transport to an external collector. Give the stage you care about its own observation. A passing message check never reaches those later stages in this fixture.

Choose the test according to the contract

A test for “the module logs a warning when it refuses input” can assert the source, level, and record fields with assertLogs. Test a configured handler independently when the contract includes rewritten fields or delivery. Use a concrete result such as “the target handler receives one record with this batch ID.”

Also try an unrelated record with the same message. Text alone can make an assertion pass when the wrong component emitted it. Match stable fields and the logger name when origin matters. Keep the delivery check outside any context that replaces the target handlers. The related pytest logging capture article covers threshold and propagation checks in a different capture setup.

Consider shared logger state when tests run concurrently. Restoring the original settings afterward does not prevent another invocation from seeing the temporary configuration. The example avoids shared state with its own instance and verifies one serial case.

What happens to the handler if the tested code raises?

The pinned CPython implementation restores the saved settings before letting the exception propagate. An unexecuted follow-up can wrap assertLogs in assertRaises(RuntimeError), raise inside the capture, and then emit a new message on the same logger. Verify both the propagated exception and delivery to the restored handler. The archived run only covered normal exit.
