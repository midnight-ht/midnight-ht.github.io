How should a virtual list expose positions when it renders only three items?

Compare two three-row windows within a 60-item set to check true positions, set size, and the unknown-size case.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-13 · Estimated read 10 min
Translations
zh-CN en

Article

Key takeaways

  • Set positions start at one.
  • A partial DOM window can have fewer rows than the full set.
  • Keep a verified position when the total is unknown.

A course list has 60 items, but its window renders only items 21 through 23. The first visible row can still be the 21st item in the set. Use aria-posinset for the real position and aria-setsize for the size of that set, rather than treating the three rendered rows as a new list.

Identify the set before assigning its positions

WAI-ARIA defines aria-posinset as a position within the current set, starting at one. When every item is present, authors do not normally need to provide the position. A partial DOM cannot tell the user agent where its three items sit in a 60-item catalog. Put the known values on a role that supports them. This example uses native list items for a read-only catalog.

The aria-setsize property gives the size of the current set. All three rows in the window use the same total, taken from the data model. An item cannot be 21st in a three-item set. Calculate positions and total from the same collection.

Filtering can change that collection. If a filter leaves twelve active courses and the interface presents those results as a list, calculate positions within those twelve. A course may keep its business ID even as its position changes. The identifier answers which record it is. The position answers where the record sits in the current ordering.

Check two windows with independent expectations

The complete local HTML has not been run in a browser or with assistive technology. It creates sixty named courses and renders a window of three. Click the button to change the range. The button stays outside the list, so this fixture does not exercise scrolling or removal of a focused item.

<!doctype html>
<html lang="en">
<meta charset="utf-8">
<title>Course window positions</title>
<h1>Course catalog</h1>
<button type="button" id="next">Show items 24 to 26</button>
<ul id="courses" aria-label="Courses"></ul>
<pre id="log"></pre>
<script>
const byId = id => document.getElementById(id);
const [list, button, log] = ['courses', 'next', 'log'].map(byId);
const catalog = Array.from({ length: 60 }, (_, i) => 'Course ' + (i + 1));
const { length: total } = catalog;

function render(first) {
  const rows = [];
  for (let position = first; position < first + 3; position++) {
    const row = document.createElement('li');
    row.textContent = catalog[position - 1];
    row.setAttribute('aria-posinset', String(position));
    row.setAttribute('aria-setsize', String(total));
    rows.push(row);
  }
  list.replaceChildren(...rows);
  log.textContent = JSON.stringify(rows.map(row => [
    row.getAttribute('aria-posinset'), row.getAttribute('aria-setsize')
  ]));
}
button.onclick = () => render(24);
render(21);
</script>
</html>

Expect positions 21, 22, and 23, each with size 60. After the button, expect 24, 25, and 26, again with size 60. The DOM contains three rows both times. The page log records attribute values. It does not verify an announcement or the accessibility API’s exposed values.

For a negative, leave the names intact but assign positions one through three and size three. The rendered appearance can remain the same while the declared set is wrong. Derive expected attributes from the fixture data, rather than reading the DOM values and calling them the expectation. Locator enumeration and the current DOM describes how tests see the rendered subset. Here that subset is deliberate and provides no evidence for the full size.

Test a window update separately from a collection change

A window move retains the collection size. A filter or data refresh can change both order and total. Bind the visible rows and their attributes to the same collection version so a slow earlier response cannot restore old positions. The application owns that check.

Positions and size do not implement selection, keyboard movement, or data loading. A production component that removes a focused item needs a separate focus test. Try the complete task in the supported environments: enter the list, identify an item, move to another window, then find the intended course again. The local example only provides the markup and planned state transition.

What if item 21 is known but the total is not?

Keep position 21 and set aria-setsize to -1 when the collection size is unknown. The first example has a fixed total. This case has a known start position but no verified total. If the service does not know the position either, do not substitute the visible row index. When the total is confirmed, update it against the same version of the collection and verify how the intended assistive technology exposes it.
