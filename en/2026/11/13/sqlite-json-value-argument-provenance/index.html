Why did SQLite put quotes around an array inside JSON?

Trace six verified SQLite path types to see when an array is embedded and when it becomes a string.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-13 · Estimated read 11 min
Translations

Article

Key takeaways

  • Ordinary SQL strings become JSON strings.
  • Direct results from json() or the single-arrow operator can preserve structure.
  • Check nested path types separately from the client’s display.

Ordinary SQL text passed as a value to SQLite’s json_object becomes a JSON string, even when the text looks like an array. To embed the array itself, pass the result of json() directly to the outer function. The two arrow operators also hand different kinds of values to the outer call.

Imagine a report response whose items field is supposed to be an array of IDs. The source column holds serialized text. Both the database console and the browser can show brackets around two numbers, even though the client needs a second parse to reach the elements. Decide what the consumer should receive. A field it iterates should arrive as an array, while text entered for display can stay a string.

Where SQLite gets the value

SQLite calls these inputs VALUE arguments. An ordinary SQL string becomes a quoted JSON string, even if it contains valid JSON. A direct result from another JSON function or from the single-arrow operator is embedded as JSON. The double arrow produces a SQL representation. For the array in this example, it produces SQL text, which the outer VALUE argument treats as a string. SQLite JSON VALUE arguments.

Use the type at the nested path to see the difference. In one document, items is text containing brackets and digits. In the other, items is an array whose two elements can be queried individually. An extraction or display step can make both shapes look like the same string. Checking the type on the generated document preserves the evidence.

Give six paths the same type check

This fixture uses a temporary table and a labeled query. It requires a SQLite build with JSON support. The arrow operators are available from SQLite 3.38.0.

CREATE TEMP TABLE item_payload (raw TEXT NOT NULL);
INSERT INTO item_payload VALUES ('[1,2]');
WITH objects(label, doc) AS (
  SELECT 'literal', json_object('items', '[1,2]')
  UNION ALL
  SELECT 'parsed', json_object('items', json('[1,2]'))
  UNION ALL
  SELECT 'arrow', json_object('items', '{"v":[1,2]}' -> '$.v')
  UNION ALL
  SELECT 'double-arrow', json_object('items', '{"v":[1,2]}' ->> '$.v')
  UNION ALL
  SELECT 'stored', json_object('items', raw) FROM item_payload
  UNION ALL
  SELECT 'stored-parsed', json_object('items', json(raw)) FROM item_payload
)
SELECT label, json_type(doc, '$.items') AS nested_type
FROM objects ORDER BY label;

In label order the expected types are arrow array, double-arrow text, literal text, parsed array, stored text, and stored-parsed array. The storage comparison explicitly uses a TEXT column. It establishes nothing about arbitrary query boundaries or a client’s own serialization. The exact SQL ran through Python 3.11.15’s sqlite3 module using SQLite 3.53.1. The archived assertions check the six labels and their types. Application serialization and the extra checks below were unexecuted.

A separate acceptance test can look at the elements. For the parsed and stored-parsed cases, assert the array type before checking the integers at positions zero and one. Keep the string case as a negative control so a harness that helpfully parses strings does not report an accidental pass. That can identify three different changes: a wrong container, a changed element order, or numbers converted to strings. The archived main check only covers the container type.

Give each source column a contract

A service can decide that a controlled configuration column contains an array and interpret it accordingly, then check the business types of its elements. Free-text notes have a different contract. Treating every valid-looking string as JSON could make the same field return an array for one user and a string for another.

Check for consumers already parsing the field twice before changing an existing API. A client that knows the previous field as a string may keep trying to parse the new array. Retain one old response as a compatibility fixture and assert the array shape explicitly in the new response. Checking storage or looking only at the displayed numbers can hide the change at the API boundary.

Record the actual SQL, the target path, and the expected type for each input. If the object is later assembled in application code, keep the same assertion at the response boundary. A passing SQLite fixture only describes the database-side path. The related article on JSON field presence and type covers another boundary involving missing and null values.

Should a note containing true be passed through json() as well?

Suppose the export also has a free-text remark whose value happens to be the four letters true. Inserting that text directly should leave the path type as text. Parsing it with json() and directly embedding the result should change the type to true, so a consumer receives a boolean. Both outer documents are valid JSON. Only one preserves the note’s field contract. Include this input in a separate check to detect an array-column conversion applied to the note by mistake. That additional probe is unexecuted.
