Why does changing a Terraform for_each key plan to replace a cloud resource?

A for_each key becomes part of a Terraform resource address. Renaming it can look like one instance was removed and another added; use a moved block or state mv for a deliberate rename.

Updated 2026-11-27 · Estimated read 12 min
Translations

Article

Key takeaways

  • A map key or set element becomes instance identity in the resource address and must be stable and non-sensitive.
  • Changing only the key changes the address and can plan a destroy and create.
  • Declare an old-to-new address move and review the plan before applying it.

A Terraform for_each map key or string-set element becomes part of the resource address and identifies an instance in Terraform state. Changing a key from west to us-west can make Terraform interpret the change as an old address disappearing and a new one appearing, even when both configurations point to the same cloud object. If the change only renames the instance identity, declare an address migration with a moved block or a controlled terraform state mv, then review the plan instead of applying it blindly.

The key is part of the address, not just a loop variable

Suppose a resource block uses for_each = var.regions and the map contains west and east. Terraform creates an address such as aws_instance.worker["west"]. each.key is available in configuration, and each.value contains the map value. The key is therefore part of the state-location contract: it must be known during planning and cannot come from a sensitive value because addresses can appear in plans, logs, and UI output.

This is one operational difference between for_each and count. count uses numeric indexes, and reordering a list can change which resource corresponds to an index. for_each uses keys that can express instance identity more clearly. That does not mean keys can be changed later as if they were display labels. Addresses match configuration blocks to objects recorded in state, and a key change changes Terraform addressing.

The for_each input must also be known before remote resource actions begin. If a key depends on a cloud resource ID that will only be created during this apply, Terraform cannot know which instance addresses to create and reports an unknown-dependency error. Impure functions such as uuid and timestamp cannot generate stable keys. Sensitive maps or sets are also disallowed because their keys would be disclosed. Use a stable business identifier for the key and put dynamic IDs in value attributes.

Why can a rename become destroy and create?

The original configuration contains regions = { west = {...} }, and state records the object at aws_instance.worker["west"]. The team changes only the map key to us-west. The current configuration now contains aws_instance.worker["us-west"], while state still contains the old address. Terraform normally treats the new address as an object that does not yet exist and the old address as an object removed from configuration, so the plan may propose a create and a destroy. The provider and resource attributes determine whether the object itself must be replaced, but the address mapping has already changed.

Terraform v1.1 and later support a moved block:

moved {
  from = aws_instance.worker["west"]
  to   = aws_instance.worker["us-west"]
}

The next plan checks for the old address in state and continues managing the existing object under the new address. The move itself does not destroy the object. It declares a state-address migration; it does not rename the cloud resource or prove that unrelated configuration changes are non-replacing. Review the full plan for provider attributes that may independently require replacement. For versions earlier than Terraform 1.1, use the state mv workflow and back up and lock state appropriately.

Separate identity changes from resource-attribute changes

Two different changes can appear together: an instance key changes the state address, or an attribute change asks the provider to update or replace the resource. A moved block handles the first. It does not suppress the second. Separating a rename from a large attribute upgrade lets the plan first show the address move and object retention, then show whether a later attribute change would replace it.

A poor response to a plan showing destroy and create is to edit state manually or automatically apply the plan in CI. The destroy may be caused by a missing address migration, or by a real change to instance type, network, or disk that cannot be made in place; the risks differ. Check key consistency across workspaces, module instances, and environments too. Adding a move for one workspace does not tell another environment how to interpret its state.

Verify a rename without accidentally deleting the object

In a disposable workspace, create a resource using a fixed map key and save terraform state list and the full plan. Change the key without applying and observe the default address change. Add a moved block, plan again, and check whether Terraform shows the address move, whether it still proposes remote replacement, and whether the state retains the same object ID. In a separate test branch, deliberately change a provider attribute that cannot be updated in place and confirm that the move and replacement appear in different parts of the plan.

For production, bind the from and to addresses, workspace, module path, object ID, plan file, and approval commit in the change record. Keep migration declarations in a shared module until all users have migrated. HashiCorp warns that removing a moved block is a breaking change: users on older configurations may see a destroy again. No Terraform command or cloud resource was run for this article; these are proposed acceptance steps, not an observed plan.

If a key really represents reassignment of a resource rather than a display-name change, creating a new object and removing the old one may be correct—for example, when ownership, network isolation, or lifecycle truly changes. For a stable-name cleanup, preserve address continuity explicitly. Ask whether the same object in state should continue to be managed at the new address. If yes, declare the move; if no, review replacement impact before execution.
