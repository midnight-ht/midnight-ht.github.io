SQS heartbeats can reduce premature redelivery, but the 12-hour limit does not reset

An SQS visibility timeout is a lease-like way to hide a message temporarily, not a processing lock. Renewals remain subject to a 12-hour ceiling from the first ReceiveMessage, so consumers must plan for duplicate delivery and delayed retries.

Key takeaways

  • A processing timeout can make a message visible again without proving the first consumer has stopped.
  • ChangeMessageVisibility can extend the lease but cannot restart the 12-hour clock.
  • Persist recoverable business state before deleting the message, and retain an idempotent path for redelivery.

Amazon SQS's visibility timeout temporarily hides a message from other consumers after a consumer receives it. It does not lock the message or prove that the original consumer is still alive. When processing exceeds the timeout, the message can become visible again and another consumer can receive it. ChangeMessageVisibility can renew the lease as work progresses, but the 12-hour ceiling measured from the first ReceiveMessage does not restart with each renewal. Long-running jobs must therefore account for duplicate execution, delayed retries, and a hard maximum processing duration.

What do timeouts that are too short or too long cause?

Suppose a consumer receives a job that calls an external rendering service and writes an archive. It usually finishes in two minutes but sometimes takes ten. If the initial visibility timeout is only 30 seconds, the message may become visible again while the original consumer is still waiting for rendering. A second consumer can start the same work. Both jobs may contend for the same object, write twice, or trigger downstream billing twice. The message was not lost; the lease was shorter than the work, so duplicate concurrent delivery became possible.

At the other extreme, suppose every message gets a 12-hour visibility timeout, but a consumer crashes after one minute. Recovery may wait a long time before the message is visible again. A long timeout reduces the chance of mistaking a slow, live consumer for a failed one, but it delays recovery after a real failure. Standard queues can deliver duplicates; a visibility timeout is not an exactly-once lock. Choose it using the task-duration distribution, downstream idempotency, and retry objectives rather than the average alone.

How long can a heartbeat renew the timeout?

When processing duration is hard to predict, start with a shorter visibility timeout and have a consumer that is still making progress periodically call ChangeMessageVisibility. For example, checking work once a minute and extending the remaining visibility by two minutes can reduce premature redelivery of a long task that is still advancing. Those numbers are a hypothetical explanation, not universal AWS recommendations, and no real queue was used here.

The clock boundary is easy to misread. AWS documents a maximum visibility duration of 12 hours from the time the queue first receives the ReceiveMessage request; repeated changes do not reset that limit. Network queuing, worker startup, and latency in the renewal call also consume available time. If work may exceed the ceiling, split it into resumable steps or use an orchestration service designed to represent long workflows. Do not renew every minute while assuming the deadline can be extended forever.

The heartbeat itself can fail. A paused process, network outage, revoked permission, or timed-out AWS call can prevent a planned extension. Another consumer may then start processing before the first one realizes that its lease expired. The application should protect concurrent work for the same business key, record the most recent successful renewal, and stop starting new irreversible side effects after an internal safety margin is crossed. A local timer saying “still working” does not prove SQS accepted the renewal.

If a unit of work truly cannot finish within 12 hours, redesign it as stages with durable checkpoints. Commit resumable state after each stage, then start the next one; after a restart, resume from the last confirmed stage. AWS documentation suggests breaking up the task or considering Step Functions when work exceeds the limit. This changes the work model instead of trying to disguise a finite lease as an unlimited lock.

There is another edge case: setting a message's visibility to the full 12 hours immediately after receiving it can be rejected because time has already elapsed between ReceiveMessage and the renewal request. The 12 hours are measured from the receive request; they are not a fresh allowance for every ChangeMessageVisibility call. A renewer must inspect the service response and leave room for request latency. Supplying the maximum number as a parameter is not proof that the extension succeeded.

Should business state commit before or after deleting the message?

If the consumer deletes the message first and then its database write fails, the message is gone while the business result is missing. If it commits the business result first, then deletion fails or its response is lost, the message may be redelivered and the consumer must recognize that the result already exists. The latter is often easier to recover: store the event ID and business change in one transaction, commit, and then delete. On redelivery, the consumer can find the completed record, skip the duplicate side effect, and retry deletion. If an external API supports idempotency keys, propagate the same event identity downstream.

There is still a boundary: a database record and an external payment or email are not in one local transaction. If the external service supports neither idempotency keys nor a queryable receipt, SQS ordering alone cannot resolve uncertainty about whether the remote action happened when the client did not receive a response. Use an outbox, a downstream idempotent interface, or a reconciliation process. The visibility timeout controls when a message may become visible again; it does not provide distributed business atomicity.

How should renewal and recovery be accepted?

In a nonproduction queue, test a short job, a job exceeding its initial timeout, a failed renewal API call, consumer termination, a process exit after the side effect commits, the 12-hour boundary, and the dead-letter path. Observe when a message becomes visible again, whether business idempotency absorbs repeated work, and whether the DLQ retains enough diagnostic context. Compare AWS request results rather than a local heartbeat log when deciding whether renewal succeeded. Failure tests should distinguish “the first consumer exited” from “no progress was observed during this monitoring interval.”

No queue was created and no AWS request was run for this article, so these items are a verification checklist, not execution results. Before deployment, check queue-level defaults, message-level overrides, whether the SDK deletes messages automatically, the start time of the receive request, concurrency quotas, and visibility policy. Treating visibility timeout as a finite lease rather than an exclusive lock leaves a correct path for both slow normal work and abnormal redelivery.
