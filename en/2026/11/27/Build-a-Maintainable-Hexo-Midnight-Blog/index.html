Deploying a Hexo + Midnight Blog: Build from Source or Publish Static Files?

A maintainable Hexo + Midnight blog depends on separating source, the public build, hosting, and DNS. Compare Vercel source builds with a separate static-artifact repository, then verify the release boundary.

Article

Key takeaways

  • Choose whether Vercel builds the source repository or receives Hexo's generated public directory; the two paths have different commit and rollback boundaries.
  • Fix the Node major version, package lock, theme version, and build command so another machine can rebuild the site.
  • Cloudflare DNS-only and proxied records behave differently; obtain domain targets from the Vercel project instead of copying a generic IP.

A local homepage proves only that this machine generated a page. To verify a production update, match three things: the source commit, the generated public/ files, and the SHA associated with the production deployment. A reachable domain does not prove that all three belong to the same release. To maintain a Hexo + Midnight blog, separate four concerns: Markdown and configuration are source; Hexo turns them into files under public/; a host publishes a particular build; and DNS points a domain at the host. Source and generated files may live in one repository or in two. The difference is which commit you must verify before calling a release current.

This guide compares two paths: connect the source repository to Vercel so it installs dependencies and builds, or run Hexo locally or in CI and push public/ to a separate static repository. Both can work, but their commit, preview, and rollback evidence differs. The commands and examples below explain configuration boundaries; they are not a claim that a complete registration-to-production tutorial was run with a new GitHub and Vercel account. Any build run on this existing Hexo site is recorded separately and does not replace end-to-end acceptance for a new account.

Separate source, build output, and production

Hexo reads site configuration, the theme, plugins, and posts under source/, then generates static files in public/. A theme controls page structure and presentation. It does not version the post repository for you, recover an overwritten deploy, or configure a hosting provider automatically. The Midnight README's installation path adds hexo-theme-midnight to the Hexo project and sets theme: midnight in the site's _config.yml. The README also says not to put provider secrets in the theme configuration or browser code. Language switching uses a shared translation_key, while each translated post can keep its own route.

The pipeline looks like this:

posts and config --Hexo--> public/ static files --host deployment--> live domain
      source commit          build/artifact commit                    DNS and HTTPS

This separation prevents several common false conclusions. A successful hexo generate does not mean the host received the new public/. A successful Vercel deployment does not prove that article URLs, canonical links, or English routes are correct. A reachable domain does not prove that it points to the latest deployment. Each layer needs evidence: a source commit, a build log and output, the commit associated with deployment, and public requests that return the intended content.

Fix the rebuild inputs before adding services

Hexo's current documentation lists Node.js 20.19.0 as the minimum for Hexo 8. Node support changes over time, so “use the latest” is not a permanent instruction. When checked on 2026-11-27, the Node.js release table listed versions 24 and 26 as LTS. Choose a supported LTS major that works with the site's dependencies, then align local and hosted builds. Pin that major in a runtime file such as .nvmrc and select the same version in Vercel settings; test an upgrade separately.

A basic project and theme installation looks like this:

npm install -g hexo-cli
hexo init my-blog
cd my-blog
npm install
npm install hexo-theme-midnight

Set the theme name in _config.yml. The Midnight README lists sitemap and feed plugins as recommended site plugins; add only what the site needs. Commit package.json and package-lock.json, not node_modules/. npm documents npm ci for automated environments: it requires the lock file to match package.json, removes an existing node_modules/ before installing, and does not rewrite either manifest. It installs the dependency tree from the lock file, but it does not freeze the Node major version, operating system, CPU architecture, or native build toolchain. The runtime should therefore be recorded and the target build environment verified as well. Lock the theme too: when installed through npm, the lock file fixes the resolved package version; when installed from a Git URL, use a reviewed commit rather than a moving branch.

There are two useful local checks. hexo server lets you inspect the rendered pages. Running hexo clean followed by the project's build command checks whether the current source can regenerate the site. An old public/ directory that happens to render in a browser is not evidence of a clean build. A multilingual site also needs a route check: every translation_key should have its intended counterpart, and language-switch links should point to real translated pages.

Choose one deployment path as the production source

Path A: Vercel builds from the source repository

The source repository contains posts, configuration, theme dependencies, the lock file, and package.json. Connect it to Vercel, then check the project's Root Directory, Build Command, Output Directory, and Node.js Version. Vercel's documentation says that only files in the configured output directory are served. For Hexo, the build must produce public/, and the output-directory setting must match. If the project has a build script, first confirm the command Vercel detected. If it does not, configure one explicitly—for example, npx hexo generate—instead of assuming the platform knows how to build Hexo.

This path keeps the source commit close to the build record. Branches can produce preview deployments, and the configured production branch can produce production deployments. Vercel also supports targeting a specific Git commit SHA. For rollback, include the deployment and its source commit in the release record instead of relying on a “latest successful” label. This approach fits a blog whose dependencies can be installed by the host, whose build settings are explicit, and whose maintainers want previews.

A counterexample is a project that depends on an uninitialized Git submodule, a local file the host cannot access, or a build script that writes output to an unexpected directory. Vercel may fail because the Root Directory, install command, or output directory does not match. Even if the build reports success, an empty site or stale directory is not a correct release. Inspect a preview deployment's generated files and pages before attaching the production domain.

Path B: publish Hexo's generated files separately

The other path builds locally or in CI, then pushes public/ to a repository dedicated to static files. Hexo's hexo-deployer-git configuration includes a destination repository and branch. The official example uses gh-pages as the default branch for GitHub, while other hosts can use different defaults. If that static repository is connected to Vercel, configure the Vercel project for the files it receives; do not ask it to build the post source as if it were still a Hexo project. GitHub Pages also supports publishing from a branch/folder or building through Actions; follow the selected host's documented setup.

This approach makes the generated files a snapshot that can be inspected independently, and it can separate build approval from production deployment. But it adds a release boundary to record: the source commit and the static-repository commit are not the same SHA. To investigate a stale English page, record both “which source commit generated this” and “which static commit is being served.” Keeping only the static repository makes post edits and lockfile changes harder to trace. Keeping only the source repository does not prove that the live files were updated. Before pushing, a deploy script should verify the target branch's current commit, the generated tree, and the expected relationship between commits; it should not force-push over remote history.

Avoid letting two uncoordinated pipelines publish the same production domain. For example, Vercel could build from the source branch while hexo deploy pushes files to a second project. Without an agreed source of truth, there are two production routes. If you retain both stages, define the single production entry point, the commit that serves as release evidence, who may roll back, and how public URLs are checked after deployment.

A hypothetical example of why two commits may matter

Suppose a Chinese post and its English translation are merged into source commit S. Hexo builds public/, and Path B commits those files to a static repository as A. Vercel then creates deployment D from the static repository's production branch. If the English page is stale, do not start by clearing the CDN. Check whether S contains the translation, whether public/ contains the correct output, whether A includes that file, and whether D was created from A. A mismatch at any one of those boundaries explains why cache clearing cannot repair a missing build input.

With Path A, the chain is shorter: source commit S → Vercel build → deployment D. The generated output still needs verification. Neither path is proven by a green Git status alone. This example is a hypothetical diagnostic sequence derived from the source/build/deploy boundaries documented by the providers; it does not describe a real incident at the site.

Cloudflare is an optional DNS/proxy layer, not an automatic speed multiplier

When Cloudflare manages the domain and the site is hosted on Vercel, add the domain in the Vercel project and verify it first; then configure the returned records at Cloudflare. Vercel's documentation says to use the A/CNAME values reported by the project's domain settings or vercel domains verify. Its example values are placeholders, not shared targets for every project. With an external DNS provider, add the returned records in that provider's control panel, then verify DNS and SSL again. Cloudflare distinguishes DNS-only and Proxied: DNS-only returns the origin address without routing HTTP/S traffic through Cloudflare, while Proxied sends that traffic through Cloudflare's network and enables its proxy features. Choose based on caching, WAF, request routing, and certificate configuration.

If Cloudflare proxying is enabled, the two TLS legs must both be correct. Full (strict) mode encrypts the Cloudflare-to-origin connection and validates the origin certificate. A casually chosen Flexible mode can make the browser-to-Cloudflare leg look secure without proving that the backend connection is encrypted as expected. Do not copy another site's DNS IP or switch modes before the certificate is ready. Before changing DNS, save the old value; afterwards check DNS resolution, certificates, redirects, static assets, and canonical URLs.

A blog can deploy on a Vercel domain without Cloudflare if it does not need Cloudflare's proxy rules or DNS management. Each additional layer adds settings and failure boundaries. For rollback, see the site guide to verifying release artifacts and recovery. For teams pinning dependency inputs in CI, see the limits of npm ci and reproducible install inputs.

Prove that the release path is recoverable

Check four layers so that one green indicator is not mistaken for end-to-end success:

  1. Source: git status is clean; posts, theme settings, package.json, and the lock file are committed. Do not put credentials in the repository or theme's browser configuration.
  2. Build: in a clean state, run npm ci, npm run clean, and the project's build command. Check that public/ contains the home page, posts, CSS, images, language routes, and sitemap. With Path A, do not assume local and CI builds use the same Node version or environment variables.
  3. Deployment: confirm the source SHA for the production deployment. If there is a static repository, also identify the source SHA that generated it. On failure, preserve the logs and current production commit instead of force-pushing a replacement directory over history.
  4. Public access: request the home page and both language versions without relying on a cached local copy. Check canonical and hreflang links, structured data, and internal links. A 200 response proves only that the URL returned a response at that time; compare the full body with the reviewed version and confirm that categories or archives link to the article.

Hexo's documentation separates hexo clean, which clears the cache and generated files, from hexo deploy, which invokes the deployment adapter. They have different responsibilities. The exact scripts, Vercel Root Directory, output directory, and Cloudflare DNS mode must be set for the actual repository and account. This guide was not run end to end against a new account and domain, and copying its commands does not by itself prove a deployment succeeded.

The original post's personal-experience claims and screenshot placeholders had no traceable field record, so this rewrite removes them. The reusable decision is to separate source, static files, production deployment, and DNS; choose one primary path; then use the adjacent commits and public pages to prove what is serving. If you cannot answer “which inputs generated this live HTML?”, improve the build and deployment record before adding comments, analytics, or CDN settings.
