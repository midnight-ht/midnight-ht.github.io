A metric chart shows a spike but no request: what does an OpenTelemetry exemplar connect?

An exemplar attaches a selected measurement to a metric point and can carry trace and span IDs. It helps jump from an aggregate to a trace without storing a span for every request.

Updated 2026-11-27 · Estimated read 12 min
Translations

Article

Key takeaways

  • An exemplar associates one representative measurement with context; histogram statistics already include its value.
  • A trace exemplar needs usable trace context and support across export, storage, and query systems.
  • An exemplar is a sampled diagnostic link, not a guarantee that every metric sample has a retained trace.

When a latency chart shows a spike but no request explains it, an OpenTelemetry exemplar can connect a selected metric observation to the trace context that existed at that moment. An exemplar is a representative measurement attached to a metric data point. It can include a timestamp, value, filtered attributes, and optional trace_id and span_id. It does not create an additional span for every request, and it does not guarantee that every metric point has a trace.

Why jump from an aggregate to one request?

A histogram describes request-duration distribution over an interval. Its bucket counts, count, and sum help answer whether tail latency changed and how many observations occurred. Those aggregates do not identify which request encountered slow SQL, a large upload, or a downstream timeout. Keeping a full trace for every request would make investigation more direct, but it would also raise sampling, storage, indexing, and privacy costs.

Exemplars preserve sparse links between the signals. As a metric is recorded, an SDK may retain a measurement value and attach the trace ID and span ID active at that time. A backend can then link from a histogram bucket or time point to a trace. The OpenTelemetry specification defines an exemplar as a recorded value associated with a measurement in a Metric. For a histogram, its value is already included in bucket_counts, count, and sum; adding it again would double-count it.

This lets a team investigate an aggregate trend and then inspect an individual sample without placing every request attribute into a high-cardinality metric label. filtered_attributes can add context, but teams should review them for user IDs, request parameters, and credentials. The trace link is also subject to sampling and export: an ID in a metric does not guarantee that the trace backend still retains the referenced trace.

How does a slow request leave a clickable link?

Suppose a service records the http.server.request.duration histogram. A request is running within an active span. The SDK’s exemplar filter selects a measurement and attaches its duration and trace context to a corresponding metric point. The exporter must preserve exemplars, the receiver and storage backend must support them, and the chart must link to a tracing backend with the same environment, tenant boundary, and time range. If any stage drops fields or points at a different trace store, an operator will see the metric spike but cannot follow it.

The OpenTelemetry metrics data model specifies a recorded value, observation time, filtered attributes, and optional trace/span IDs. An exemplar may exist as a numeric observation without usable trace context; in that case it cannot navigate to a trace. A trace may also have been dropped by head sampling, leaving an ID that cannot be resolved. Distinguish “no exemplar selected,” “exemplar without context,” “ID present but trace not retained,” and “backend or UI not connected” instead of treating all four as metric collection failures.

Exemplar selection is not metric sampling

The exemplar filter chooses which measurements become exemplars; metric aggregation determines how measurements are summarized; and the trace sampler determines whether spans are retained. These are three different control points. Increasing the number of exemplars does not automatically increase trace retention. Retaining more traces does not mean every measurement will be marked as an exemplar. The specification defines the data model, while filter strategies and implementation support depend on the language SDK, its version, and the exporter.

For example, a team may choose a trace-based filter that stores exemplars only when valid trace context exists. This supports metric-to-trace navigation, but links can still be missing when there is no active span, asynchronous context was lost, or trace sampling rejected the span. Another policy might favor unusual or high-valued measurements, but do not assume every SDK uses the same selection algorithm. Check the language SDK documentation and test a request with a known trace ID end to end. No exporter, backend, or dashboard was deployed for this article; this is a design interpretation of the specification, not an observed screenshot or performance result.

Test the correlation path, not just the metric value

In a test environment, issue a request with a known trace ID. Verify that the metric point contains an exemplar, that its timestamp and value correspond to the histogram data, and that the tracing backend can find the same trace ID. Then record a measurement without an active span and confirm that metric aggregation still works while the trace link is absent for an understood reason. Exercise trace sampling, metric export failure, backend expiration, and incorrect environment labels as separate negative cases, recording where the association disappears.

When evaluating cost, compare exemplar storage, metric cardinality, and trace retention; do not market exemplars as “free full request tracing.” Putting trace and span IDs into ordinary labels would create high-cardinality series for individual requests. The point of an exemplar is to keep a small number of cross-signal links while aggregate metrics remain responsible for trends and alerts.

Finally, confirm that the query UI can open the linked trace for the same project, region, service, and time window, and verify that access controls are consistent. Seeing a trace ID does not mean every user should be allowed to read its contents. An exemplar is an investigation entry point, not an access-control mechanism, a retention policy, a guarantee of trace completeness, or an alert rule. Treat link success rate, missing-trace reasons, and backend lookup latency as separate acceptance checks.
