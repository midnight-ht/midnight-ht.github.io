Why is the old file still there after DELETE succeeded in a versioned S3 bucket?

In a versioned S3 bucket, DELETE without versionId usually creates a delete marker. Recovery removes that exact marker; permanently deleting old versions is a separate operation.

Key takeaways

  • A DELETE without a version ID usually adds a marker instead of erasing earlier object versions.
  • To restore an object, identify and remove the current delete marker by versionId.
  • Another unversioned DELETE can add another marker, while lifecycle rules may permanently remove noncurrent versions.

In an Amazon S3 bucket with versioning enabled, DeleteObject without a versionId usually does not permanently erase earlier object versions. It creates a delete marker that makes an ordinary GET behave as if the object were deleted. To recover the object, first find the current marker and remove that specific version. Sending another unversioned DELETE for the same key may only create a second marker. Deleting the currently visible object and permanently removing its history are different operations.

A delete marker changes the current view, not the object bytes

With versioning enabled, a key can have multiple versions. An unversioned delete inserts a marker in front of the current version, so normal reads stop returning the older content. That older version can remain stored and continue to incur storage charges. The marker has its own version ID and becomes the key’s current version. A successful S3 response means the delete request was accepted; it does not prove that the previous bytes were physically erased.

This explains a common mismatch between the console, API, and application logs. The key may disappear from the ordinary object listing, and HEAD or GET may return 404, while a lookup using an earlier version ID still finds the data. “Not visible to current reads” can be true while “permanently deleted” is false. A compliance requirement for irreversible destruction must account for old versions, replication destinations, backups, Object Lock retention, and lifecycle rules; one DeleteObject event is not sufficient evidence of destruction.

Recovery must target the marker’s version ID

List the versions for the key, confirm that the newest entry is a delete marker, and record its version ID. Then delete that marker by specifying its version ID in the request. Once the marker is removed, the newest non-marker version becomes current and an ordinary GET returns the object again. This does not copy an old version into a new object or disable versioning for the bucket.

The trap is issuing another DELETE without a version ID. AWS documents that if the current version is already a delete marker, the unversioned request does not remove it; it writes another marker. The key still returns 404 and the version listing can accumulate markers. A marker with a NULL version ID is a special case: the request must explicitly pass NULL to delete it. Omitting the version ID may instead create another marker with a unique ID. A recovery script that deletes only by key without inspecting versions can manufacture more deletion records.

Deleting data is different from undoing a hidden state

To permanently remove a specific historical object version, specify that object version’s versionId in DeleteObject. Removing a marker only makes an older version current; it does not delete that older version or bypass Object Lock. A version protected by retention or a legal hold may reject permanent deletion. An unversioned delete can still create a marker and hide the object from ordinary reads without destroying the protected data.

Lifecycle rules also represent two distinct actions. Expiring a current version in a versioned bucket can add a marker, while expiring a noncurrent version permanently removes historical data. A marker is not an “expired marker” while object versions remain behind it. Only when versions have been removed and a marker remains by itself can a particular lifecycle action remove that expired marker automatically. A lifecycle rule that is too broad can confuse temporary hiding with irreversible cleanup. Design it against recovery windows, storage cost, audit retention, and Object Lock instead of applying one age threshold to every version.

Example: an upload service treats DELETE as an undoable upload

Suppose an application deletes a user-uploaded image. The request succeeds in a versioned bucket, the application stores deleted=true, and the interface stops showing the image. Months later, a recovery exercise finds the image in the version listing. S3 did not ignore the request; the application’s meaning of “deleted” was only that a marker hid the current version. A better data contract distinguishes states such as hidden_from_current_reads, recoverable_version_retained, and permanently_deleted, and identifies who owns cleanup of noncurrent versions.

For recovery, a controlled process can list the object’s versions, verify that the current marker’s key and version ID match the incident record, and then remove that exact marker. Before acting, verify the account, bucket, region, and version ID. A key-only search is not enough because a concurrent upload or another delete can change which version is current. For permanent destruction, inspect every version, marker, replication destination, and retention policy; bind approval and outcome records to the specific version IDs.

No AWS account was accessed and no S3 API was called for this article. The procedure follows S3 documentation; validate it against the bucket’s versioning state, permissions, Object Lock configuration, and the SDK or API in use. Do not treat this example as a recovery script for an arbitrary bucket.

Test recovery while preserving failure cases

In a nonproduction bucket, enable versioning, upload two different payloads to one key, and record both version IDs. Issue an unversioned DELETE and observe the ordinary GET result and version list. Then delete the precise current marker version and confirm that the older payload becomes current. Also test a second unversioned DELETE against a marker, a NULL version ID, an Object-Locked object, lifecycle expiration of noncurrent versions, and a concurrent upload and delete. Record response version IDs, the delete-marker flag, and read results instead of retaining only the HTTP status.

Production acceptance should distinguish three promises: hidden from current reads, recoverably deleted, and permanently erased. Application state machines, event records, version cleanup, backup policy, and replication should use consistent terms. If the application maps one successful DELETE to permanent destruction, a recovery exercise exposes a semantic gap. If marker removal is mistaken for a new upload, the process can overwrite a current object. Naming visibility, retained history, and irreversibility separately keeps the application’s delete action aligned with S3’s version state.
