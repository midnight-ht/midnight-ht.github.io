Why has AbortSignal.timeout not expired after a page was suspended?

AbortSignal.timeout measures active time, not simply wall-clock time. Its clock pauses while a document is in the back-forward cache or a Worker is suspended, so it is not an absolute server-side deadline.

Key takeaways

  • The timeout is measured in active milliseconds; it does not guarantee firing after the same amount of wall-clock time has elapsed.
  • BFCache and suspended Workers pause the timer, so an operation may still be live when the page resumes.
  • Use a separate responsibility for cancellable timers or absolute server deadlines.

AbortSignal.timeout(ms) returns a signal that automatically aborts after a specified amount of active time. That is not simply wall-clock time measured from creation. The MDN documentation says the timer pauses while a document is in the back-forward cache (BFCache) or a Worker is suspended. A request may therefore still lack a TimeoutError when a page returns after ten minutes away. The API is useful for constraining asynchronous operations while the browser context is active; it should not replace a server deadline or business expiry time.

How does active time differ from wall-clock time?

Suppose a user opens an order-detail page. The page starts a cancellable data read in the background and sets AbortSignal.timeout(5000). If its JavaScript context stays active, the signal aborts the wait after roughly five seconds. But if the user navigates elsewhere and the browser places the original page in BFCache, the clock pauses. When the user returns ten minutes later, five active seconds may not yet have accumulated and the read can still be waiting. This is not the browser forgetting to count; it is the API's documented active-time behavior.

The difference affects both product language and incident diagnosis. If the requirement is “wait at most five seconds while the user is on this page,” active time may match the experience. If the contract says “background work must stop within five seconds after the server accepts the request,” creating a timeout signal only in the client does not satisfy it. Page freezing, device sleep, process scheduling, and network delay are not the same lifecycle as server execution. A frontend signal can ask a browser-side asynchronous operation to abort; it does not prove that a remote server stopped processing.

What can combining signals handle?

A request may be cancelled by the user or by an active-time timeout. AbortSignal.any([userSignal, timeoutSignal]) can combine the causes so operations such as fetch that support AbortSignal receive a cancellation request when either input aborts. The caller must still inspect signal.reason and distinguish the user leaving from a timeout. Treating both as a generic AbortError can show an incorrect retry message or record a user cancellation as a network failure.

Keep the combination scope aligned with the operation lifecycle. If a page loads an avatar and order details independently, sharing a very short timeout signal can make an avatar problem cancel the order read. Conversely, putting several steps that must succeed together under one signal expresses a shared wait budget. Before creating the signal, draw the cancellation path: who can cancel, which requests stop, and which background writes cannot be rolled back by interrupting the browser. Sharing a signal is then an inspectable operation contract, not merely a coding convenience.

A combined signal does not clean up every resource for you. The timer created by AbortSignal.timeout() cannot be directly cancelled. Even if the operation finishes early, the timeout may remain pending. MDN also warns that a signal with an abort listener stays alive while the timeout is pending; long timeouts and listeners that are not removed can delay garbage collection. If an application needs deterministic early cleanup, it can create its own AbortController and setTimeout(), call clearTimeout() when the operation finishes, and remove listeners it no longer needs. That solves a resource-lifecycle problem; it does not automatically turn browser time into a server clock.

If product policy requires checking a wall-clock deadline when a page resumes, the client can store a readable deadline when the request starts, then compare it on pageshow or when page visibility returns and cancel local work that is already expired. This is only a check when the browser gets an opportunity to run again. It is affected by device-clock changes and by how long the page did not run; it cannot execute code while the page is frozen, and it cannot replace the server rejecting an expired write. Do not describe “the client stored a deadline” as “the server is guaranteed to stop in time.”

How should an absolute server deadline be expressed?

For a request with server-side effects, define the deadline or cancellation contract on the server. The client can pass an absolute deadline as a business parameter or protocol agreement. The server can then check its own clock, queue time, and progress, and stop work at an appropriate boundary. For example, assume an export must return within 20 seconds of request creation. The frontend can show a countdown and let the user cancel waiting, but the server still needs to store the creation time, deadline, and job state. Closing a browser tab must not be the only control preventing an expired task from running indefinitely.

If the goal is only to stop waiting for the current fetch, a signal is enough to express local cancellation intent. If the requirement is to ensure a database write is not committed after a deadline, re-check the server-side deadline at the transaction boundary; aborting a network request cannot roll back a transaction that already committed. If a server job continues asynchronously after queueing, persist cancellation state and define whether cancellation means “stop returning results” or “make a best effort to stop side effects.” Those semantics belong in the API and business state machine, not in the timeout duration alone.

How can suspension and cleanup be verified?

In a browser that supports BFCache, construct a page-return scenario and compare a page that remains open with one that is left and restored, plus a suspended and resumed Worker. Record signal-fire time, page-resume time, active-operation time, and signal.reason. Test that listeners are cleaned up when a request completes naturally, that user cancellation retains different behavior from timeout, and that the resulting server-side state remains queryable after client cancellation. Compatibility should be measured on target browser versions; one developer-tools session does not establish identical behavior on every platform.

No browser automation or network request was run for this article. The timeline is a hypothetical example based on the MDN documentation and DOM Standard, not a measured result. Keep three clocks distinct: document active time, elapsed time observed by the client, and the server's execution deadline. Assign each to the runtime responsible for it. This explains why a request that appears to have waited more than five seconds may not yet have been aborted by AbortSignal.timeout().
