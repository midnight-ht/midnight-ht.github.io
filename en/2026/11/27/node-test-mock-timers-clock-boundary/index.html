The test clock moved forward, so why is the Promise still pending?

Node's test-runner MockTimers controls selected timer and Date APIs, but setTime, tick, and Promise microtasks are distinct. Decide which wait your test must drive.

Updated 2026-11-27 · Estimated read 12 min
Translations

Article

Key takeaways

  • MockTimers controls selected timer APIs and Date; it does not advance every asynchronous operation.
  • setTime changes the virtual clock without firing due timers; tick advances timer time.
  • The test runner restores its per-test mock tracker, but custom fixtures can still leak real timers.

Node.js node:test MockTimers can advance a virtual timer and Date clock without waiting real seconds for setTimeout. Changing the clock and firing timers are not the same operation. In the official API, setTime() changes the mock clock but does not execute timers that are due at or before the new time. tick() advances timer time and runs timers that expire. If a test treats these operations as interchangeable, a pending Promise does not prove that mocking failed.

List the time sources the test needs to control

An “expiry” path may depend on several clocks: Date.now() for a business deadline, setTimeout() for a retry, setInterval() for a heartbeat, and node:timers/promises for an awaitable delay. MockTimers can mock setInterval, setTimeout, setImmediate, and Date by default, or let you select APIs explicitly. When one timer API is selected, its corresponding clear function is mocked too. Do not assume that mocking Date freezes every time source in an external library or also controls performance.now().

Start a deterministic test by identifying each time dependency, its expected boundary, and its side effect. For a retry after 500 ms, assert that no second request has started at 499 ms and that one starts only after crossing 500 ms. For an expired TTL, check whether both the virtual wall clock and timer callback must move. These boundaries are more reviewable than “fast-forward time.”

The difference between setTime and tick

Suppose a test enables mock.timers.enable({apis:['setTimeout','Date'], now: 0}) and schedules a 1,000 ms timer. Calling setTime(1000) can make Date.now() report the new time, but it does not cause that timer to run simply because the clock has crossed its deadline. Calling tick(1000) advances timer time and runs the due callback. The distinction can model the difference between manually changing the system clock and allowing a waiting interval to elapse.

Calendar-boundary tests also need an explicit decision about crossing a local date, timezone offset, daylight-saving transition, or month end. Adding 24 hours in milliseconds is not always equivalent to “tomorrow” in a business calendar. MockTimers replaces only selected APIs; it does not define calendar semantics for the application. If code combines Date with real network responses, a database clock, or native extensions, the virtual clock may control only part of the test.

Observe timer callbacks, microtasks, and Promises separately

When an expired callback calls resolve(), a Promise continuation generally runs later in the microtask queue. The test should await the relevant Promise or use the mock timer APIs available in its Node version; it should not treat “callback ran” and “the whole asynchronous chain finished” as the same observation. The current documentation URL cited here shows Node.js v26.13.1. MockTimers was introduced in v20.4.0 and v18.19.0, and became stable in v23.1.0. A project on Node 20 or 22 should read its release-specific documentation rather than copy the newest syntax.

Also consider node:timers/promises delays, AbortSignal cancellation, ordering among timers with the same deadline, and intervals that span multiple ticks. A test that advances once and immediately asserts that a service finished may miss Promise settlement or another interval execution. Separate assertions for clock readings, callback count, request count, Promise state, and cleanup reveal whether the clock failed to move, the callback failed to run, or the asynchronous continuation remains incomplete.

A test design for a retry boundary

Suppose a request function rejects once and succeeds on its second call, while production code schedules retry with setTimeout(retry, 500). Create mock timers in a test context, make the first request, check at 499 ms that there was still only one call, advance another millisecond, await the retry Promise, and assert the second call and final result. Add a cancellation case: abort before expiry and verify that the timer is cleared and no later side effect runs. This is a proposed test design; no Node command was run and there is no observed test log.

Negative cases matter too. If a test does not restore timer behavior after assertions, a simulated state can contaminate shared fixtures. If it mocks only setTimeout while the code uses timers/promises, the test may still wait on real time. If a callback schedules another timer, one tick may not be enough to execute the second deadline. Node’s test runner binds a mock tracker to a test context and restores it when the test completes, but custom clocks, third-party fake timers, and objects shared across contexts still need explicit management.

Choose to test logical time, not to create a global illusion

Use built-in node:test MockTimers when the goal is to test Node timer APIs, Date boundaries, and a retry path within that test. Mock only the APIs needed so real asynchronous dependencies remain visible, and set an explicit epoch with now. If a component already accepts a clock abstraction, dependency injection may be better for cross-runtime or pure-function tests. Avoid layering multiple fake-timer systems unless it is clear which one replaces each global API.

For acceptance, record the Node version, runner, enabled APIs, initial time, each tick or setTime, callback count, and asynchronous completion point. No example was executed for this article; it explains behavior from current Node documentation and is not evidence that a project’s tests pass. State both “what time is virtual now?” and “which timers have actually run?” instead of letting a vague fast-forward hide the mechanism under test.
