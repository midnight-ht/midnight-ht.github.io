TypeScript `satisfies` checks a config without widening it to a broad interface

`satisfies` checks compatibility while preserving the expression's inferred result. It catches missing keys and bad value types, but is neither runtime validation nor an escape from inference rules.

Key takeaways

  • `satisfies` checks compatibility instead of declaring a variable as the broader target type.
  • Excess-property checks, contextual typing, and mutability still follow TypeScript inference rules.
  • Type checking happens at compile time; external JSON and environment variables still need runtime validation.

TypeScript’s satisfies operator checks that an expression is compatible with a target type while preserving the expression’s more specific inferred result. It fits configuration tables, maps, and enum-like objects: it can catch missing required keys, misspelled properties, and incompatible values without widening every property to a union from an interface. It runs only during type checking. It does not validate JSON, environment variables, or API responses at runtime.

An annotation and satisfies answer different questions

Consider a color palette where red is an RGB tuple, green is a string, and the required keys are red, green, and blue. If you write const palette: Record<Colors, string | RGB> = {...}, the variable has the target Record type. When reading palette.green, TypeScript may know only that the value is string | RGB, so calling toUpperCase() is rejected even though the initializer clearly contains a string.

With const palette = {...} satisfies Record<Colors, string | RGB>, the compiler still checks the object against the target constraint, but the inferred type of palette.green stays closer to the expression and retains its string-specific members. The TypeScript 4.9 release notes describe the design as ensuring an expression matches a type without changing the expression’s resulting type. This does not mean “no contextual typing at all”: the target still participates in checking. Inspect the inferred result instead of treating satisfies as a type assertion.

Which configuration errors can it catch?

Record<Colors, ...> can require the expected keys and report a misspelling in a direct object literal. If blue is written as bleu, the compiler can report a missing required property or an unexpected property before a runtime renderer encounters an undefined color. It can also preserve distinct value types for each key: booleans remain booleans, string lists remain arrays, and functions remain callable signatures. This is useful for named configuration, handler tables, and feature-flag maps.

However, the “no extra key” check depends on the shape being checked. Excess-property checks usually catch a typo on a direct object literal. Structural typing may allow a value stored in another variable to carry additional properties when it is assigned to a target type. Spreads can also change which properties are directly visible to the literal check. If runtime data must contain only allowed keys, satisfies cannot replace a schema parser.

A broad target type also provides a broad check. Record<string, unknown> accepts arbitrary string keys and does little to catch a misspelled dictionary key. If a value type is an unnecessarily large union, a wrong configuration may still be legal. Define a concrete key set and useful value types, then verify that the target represents the intended contract rather than assuming that adding the satisfies keyword automatically makes a config safe.

Keep exact configuration types and their limits

Suppose a navigation map requires fixed route names and values containing label, path, and optional external. Define the route-name union and the item shape, then apply satisfies Record<RouteName, NavigationItem> to the literal. Adding a required route without configuring it becomes a compile error; external: "yes" also fails. At the same time, reading an individual entry retains more specific properties instead of turning every value into one broad interface.

Arrays and tuples need extra attention. An array literal often infers as a mutable array rather than a fixed tuple, and a string literal may widen to string. If the business contract needs a literal union, readonly data, or a fixed length, combine satisfies with as const, an explicit tuple constraint, or an appropriate generic design. Do not assume that preserving a type means every literal is automatically locked to its narrowest type. satisfies and as const do different work: the former checks compatibility; the latter affects readonly and literal inference.

A bad pattern is parsing external JSON, asserting it to Config, and treating that as equivalent to a compile-time satisfies check. Type declarations are erased, so hostile or malformed data can still lack keys, contain wrong value types, or include an unexpected structure. Validate at the boundary with a runtime validator, then convert the result into a domain type. Use satisfies for static objects maintained by developers; the two mechanisms address inputs with different trust levels.

Verify that the inferred type is the one you intended

Create a small type test with a valid object, a missing key, a misspelled key, a wrong value type, assignment through an intermediate variable, and a spread merge. Confirm that the first cases produce the expected compile errors or success, then inspect the inferred property type in the editor and with tsc. For runtime boundaries, separately test missing fields, invalid JSON types, and extra keys against the parser’s error path.

No TypeScript compiler or repository configuration was run for this article. Behavior can also depend on TypeScript version, strictness options, generic target types, and contextual typing; TS 4.9 is the release note that introduced this operator. satisfies improves precision of a static contract. It does not prove business correctness and does not make user input trustworthy. Keep evidence for compile-time structural compatibility separate from runtime input validation so the covered boundary remains clear.
