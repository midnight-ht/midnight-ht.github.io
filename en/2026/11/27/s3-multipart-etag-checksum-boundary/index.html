Why is an S3 multipart ETag not the MD5 of the whole file?

An S3 multipart ETag identifies a completed object but is not guaranteed to be the whole-file MD5. Choose a checksum algorithm and full/composite type when initiating the upload, then validate the stored checksum on completion and retrieval.

Key takeaways

  • A multipart object's ETag is not the MD5 of the entire object and should not be compared directly with a local whole-file digest.
  • Multipart checksums can be full-object or composite, and algorithm support differs.
  • Declare the algorithm when initiating the upload and verify the resulting checksum through the upload and download paths.

An Amazon S3 ETag returned after a multipart upload can identify the completed object, but it cannot generally be interpreted as the MD5 of the complete object's bytes. AWS documentation explicitly says that an object created by multipart upload does not have a whole-object MD5 ETag, regardless of encryption. Only under specific conditions for single-part uploads might an ETag equal the object's MD5. To verify a large object's integrity, explicitly choose an S3-supported checksum algorithm and checksum type, then confirm that S3 validated and stored the checksum during upload and that it can be checked again on retrieval.

Why is a three-part file easy to verify incorrectly?

Suppose a local file is split into three parts, uploaded separately, and the client receives an ETag from CompleteMultipartUpload. The value may look like a string with quotes and a suffix. Running MD5 once over the original complete file and comparing that result with the ETag can fail; this alone does not prove that the upload was corrupted. For some upload paths, the ETag is formed from part digest information rather than one MD5 over the final concatenated object. AWS also says the ETag of a multipart-uploaded object is not a whole-object MD5, regardless of encryption. Experience with a particular SSE-S3, small, or single-part object should not be generalized to multipart uploads.

An ETag can also be part of an object's version representation and help identify whether content changed, but it is not a general integrity protocol. A metadata change and a byte-content change are not the same thing. Treating any ETag that looks like a hexadecimal string as a “trusted strong hash” can collapse cache identity, conditional requests, and transfer integrity into one contract. First define which property you need to verify: that each part arrived intact, that the final object equals expected bytes, or that the object changed. Those properties require fields and procedures that can actually verify them.

What is the difference between a full-object and composite checksum?

S3 multipart checksums support full-object and composite types, but not every algorithm supports both. The current documentation lists CRC-64/NVME as supporting full-object but not composite checksums; CRC32 and CRC32C support both; SHA-1, SHA-256, MD5, and several XXHash/SHA-512 algorithms support composite only. A full-object checksum represents the concatenated object. A composite checksum is built from part-checksum information and cannot automatically be treated as an ordinary whole-file digest. A verification system should retain the algorithm, checksum type, and object version context instead of storing an unexplained string.

With the multipart API, specify the checksum algorithm and type when initiating the upload, then provide the relevant checksum for each part. AWS specifically warns that for newer checksum algorithms, supplying a checksum header only in CompleteMultipartUpload without specifying the algorithm in CreateMultipartUpload causes the completion request to fail. For some existing algorithms, a checksum supplied at completion when no algorithm was declared at initiation may not be validated or stored. The safe approach is to establish the checksum contract when the upload starts, rather than assuming a value in the last request proves server-side validation occurred.

When the requirement is a full-object check, define the complete flow this way: calculate the chosen full-object checksum from the original file before upload; bind its algorithm, type, expected value, and object key to one task record; declare a supported algorithm and checksum type when creating the multipart upload; save each part number and response after upload; then read the stored checksum field after completion and compare it with the task's algorithm and expected value. If the value does not match, S3 rejects completion with a checksum error instead of letting the application mark a questionable object successful. The exact fields still need validation with the SDK in use.

How can an existing ETag comparison become a checksum contract?

Suppose a system currently treats equality between a local MD5 and the S3 ETag string as proof of successful upload. During migration, add the expected checksum algorithm, value, type, and object key to the upload job. Declare the algorithm when starting multipart upload, upload each part and retain its response state, then complete the upload. Next, read the object's metadata and compare the returned checksum field with the expected algorithm and type. For download verification, calculate the stored algorithm over the retrieved bytes. This flow must account for the SDK version, whether checksum fields are requested in responses, multipart checksum-combination rules, and object encryption; simply swapping field names is not enough.

A counterexample is choosing SHA-256 composite and comparing it directly with a one-shot SHA-256 over the local whole file. A composite checksum has a different meaning. If the requirement is a whole-file SHA-256 but that algorithm does not support full-object validation for the chosen upload type, design a separate whole-object verification path rather than relabeling a composite value. The current documentation provides a full-object path for CRC-64/NVME, though the client SDK and retrieval process still need support.

If a legacy object has no stored checksum metadata for the property you now need, do not backfill a “verified” state merely because its ETag looks similar or different. Mark the integrity evidence as insufficient in the inventory, then choose based on risk: download and calculate a checksum, compare with a trusted source digest, or upload again under a new checksum contract. This is a conservative migration decision, not a claim that the old object is corrupt; it prevents missing evidence from being reported as a successful integrity check.

Record why it remains unverified so a later migration can revisit it.

How should an upload be accepted?

In a test bucket, use fixed byte input and cover both a single PUT and a multipart upload. Record the algorithm and type declared at initiation, each part checksum, the completion response, and the later object checksum fields. Deliberately alter one part, swap part numbers, or omit a part from completion and confirm that the failure path does not mark the object as verified. Also check how encryption, SDK upgrades, and legacy objects without checksum metadata are classified instead of guessing from an ETag.

No S3 bucket was created and no CLI or SDK was run for this article. The inputs and steps are an acceptance design, not an execution log. The final policy should follow current AWS documentation, SDK behavior, and the actual upload protocol. Treat an ETag as an object-identification clue, a declared checksum as integrity evidence, and preserve the algorithm and checksum type. That prevents visually similar hexadecimal fields from being assigned the same meaning.
