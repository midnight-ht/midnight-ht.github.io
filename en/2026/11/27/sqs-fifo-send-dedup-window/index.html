SQS FIFO's five-minute deduplication protects send retries, not business side effects

Amazon SQS FIFO uses a message deduplication ID to prevent duplicate enqueueing within a five-minute window. It does not make a consumer's charge or database write happen once, and content hashing excludes message attributes.

Key takeaways

  • The five-minute window applies to FIFO send deduplication, not to one-time execution of business effects.
  • Content-based deduplication hashes the message body with SHA-256; message attributes are excluded.
  • Critical business side effects still need a consumer-side idempotency key or transactional record.

Amazon SQS FIFO's deduplication window addresses a sender that cannot tell whether SendMessage succeeded and therefore retries the same message. If the same deduplication ID is sent again within the five-minute window, SQS does not add a second copy to the queue. This does not guarantee that a consumer charges a card, sends an email, or writes to a database only once. Consumers can still see redelivery, timeouts, and crashes after a side effect but before deleting a message. Design “queue-send deduplication” separately from “business-operation idempotency.”

Where does the five-minute window apply?

Suppose an order service needs to send an “ready for fulfillment” event for order o-817 to a FIFO queue. The connection drops after sending, and no response arrives, so the service cannot tell whether the message reached SQS. It retries using order:o-817:ready:v1 as its MessageDeduplicationId. If the retry falls within the same five-minute deduplication interval, SQS recognizes it as a duplicate send and does not enqueue a second copy. The client can retry an uncertain send without assuming that every network timeout means the original request failed.

There is a precise boundary: the guarantee applies to FIFO's send-deduplication mechanism and its time window. After five minutes, the same ID no longer has the suppression guarantee provided during that window. The business system must handle delayed replay, manual resends, or recovery after a longer interval. Whether a consumer succeeds, processes halfway, commits a side effect and then crashes, or fails to delete a message is not proved by send deduplication. Although AWS uses “exactly-once processing” in the page title, the body describes avoiding duplicate enqueueing over a short interval. Do not expand that title into an end-to-end transaction guarantee.

Which fields does content-based deduplication consider?

With content-based deduplication enabled, SQS calculates a SHA-256 hash of the message body to generate the deduplication ID; message attributes are not part of that hash. Two messages can therefore have identical JSON bodies but different tenant, trace-id, or schema-version attributes and still produce the same deduplication ID. If those attributes change the business meaning, do not silently rely on body-only deduplication. Supply an explicit MessageDeduplicationId that includes the business version, or include the semantic fields in a canonicalized body. Document what defines stable event identity.

Conversely, two JSON strings with different field order can represent equivalent business data while having different bytes, so content-based deduplication can produce different IDs. It is not a JSON semantic comparator; it does not sort fields, normalize numbers, or remove metadata that does not matter to the application. For a business action, constructing a stable event ID explicitly is often easier to audit than expecting a hash to infer semantic equivalence. The ID format above is a design assumption and was not sent to an AWS queue.

Explicit IDs also need to avoid excessive reuse. If the system uses only order ID o-817, two distinct events for the same order—ready and a later valid cancelled event—could collide within five minutes, suppressing the second send. A more explanatory identity usually includes the aggregate, event type, and a stable version or sequence for the change. It must remain the same across a network retry while distinguishing separate business changes. The counterexample is generating a new random UUID on every retry: that disguises one business event as multiple new messages and defeats retry deduplication. Define the fields from the event model instead of copying the sample string mechanically.

How can a side-effect timeline get past send deduplication?

Suppose a consumer receives an order event, calls a payment service, and then deletes the message. The payment succeeds, but the consumer crashes before DeleteMessage. The message may later be delivered again. FIFO still preserves queue ordering, but the consumer may call the payment service a second time. The deduplication window describes repeated submissions by the sender; it does not check whether an external payment system has already charged the customer, nor does it make the payment call and message deletion one atomic transaction.

A safer consumer contract records a stable event_id in a business processing table in the same database transaction as the business change. If the side effect happens in an external service, pass that ID as the downstream idempotency key, or write an outbox first and let a downstream component with deduplication perform the effect. A database unique constraint can prevent registering the same event twice, but it cannot undo an external action that has already completed when the downstream service provides no idempotency support. The right design depends on the side-effect boundary; SQS FIFO does not provide a generic distributed transaction by itself.

The processing record also needs state transitions. For example, the first delivery creates a unique event_id; after the business transaction commits, the record becomes complete. A second delivery can then skip the external call when it finds the completed record. If the consumer crashes while the record only says “in progress,” lease expiry must allow recovery or operator reconciliation; it should not reserve the event forever. That database state machine belongs to the consumer. SQS's five-minute send deduplication does not maintain it.

How should the sender and consumer guarantees be tested separately?

Sender tests should cover a first send that succeeds while its response is lost, a retry with the same ID inside the window, a message with a different business ID, a send after the window, and content-based deduplication where attributes differ but the body does not. Consumer tests should cover a crash before processing, a crash after the business side effect but before deletion, redelivery of the same event, an existing idempotency record, and a temporary downstream failure. The goal is not to prove that a real queue executes anything exactly once; it is to prove that each layer handles retries within its own stated contract.

No SQS queue was created and no AWS client was run for this article. The timeline and checks are hypothetical examples organized from the official documentation, not measured logs. Before deployment, confirm whether content-based deduplication is enabled, how explicit IDs are generated, the FIFO message-group ordering, and the consumer's visibility and deletion policies. Use the five-minute send window as one layer that reduces duplicate enqueueing, then design business idempotency independently. That separation prevents a local mechanism from being mistaken for end-to-end “execute once” behavior.
