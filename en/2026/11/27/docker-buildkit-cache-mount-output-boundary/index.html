Why does CI still download dependencies after adding a Docker cache mount?

A BuildKit cache mount is reclaimable builder-local performance state, not an image layer or an exported --cache-to cache. A fresh CI builder may start empty.

Updated 2026-11-27 · Estimated read 15 min
Translations

Article

Key takeaways

  • A cache mount and a reusable instruction layer are different caching mechanisms.
  • Cache mounts normally live in one builder's local storage and are not included in --cache-to/from exports.
  • A build must remain correct with an empty or reclaimed cache; the mount should accelerate work, not become its sole input.

BuildKit RUN --mount=type=cache gives a build command a persistent directory for repeated downloads, such as package-manager or compiler data. It is builder-local, reclaimable performance state. It is not written into the final image layer and is not exported through ordinary --cache-to. A CI job that creates a new builder can therefore start with an empty mount. A correct build must still produce the right artifact when the cache is missing or cleared.

A cache mount and an instruction layer are different

Docker’s regular build layers are reused when the instruction and its inputs match. If an earlier COPY input changes, a later layer may be invalidated and executed again. A cache mount instead places a directory, such as /root/.npm or a compiler cache, inside the container while a particular RUN instruction executes. When the command reruns, the package manager may reuse downloaded files and reduce network traffic, but the mount contents are not part of that instruction’s output layer.

Think of two separate kinds of state: a layer cache reuses the result of an earlier instruction, while a cache mount provides accumulated data to an instruction that is running again. If an instruction has not been invalidated, Docker may reuse the layer and never run the command. If it has been invalidated, the mount may speed up the rerun. Their hit conditions, storage locations, and export behavior differ. “The image layer was cached” does not mean “the cache mount exists on a new machine.”

Why can CI start from an empty directory?

Docker documents that cache mounts live in the BuildKit builder’s local storage. They are not part of an exported external build cache and are not restored by --cache-from. If every CI job creates a new builder, its cache mount starts empty. Even on a reused builder, another build can overwrite shared contents or garbage collection can remove them. The Dockerfile reference says the build must remain correct with any contents of the cache mount; it cannot assume the directory always contains a previous download.

First determine whether CI reuses the same BuildKit daemon or builder, then distinguish external-cache configuration from local cache-mount persistence. Adding cache-from and cache-to alone does not restore a mount directory on a new builder. To share package downloads across fresh builders, use an appropriate CI cache import/export feature, an external package repository, or a persistent builder strategy. The exact behavior depends on Docker/BuildKit versions and the CI platform.

Make a cache miss affect speed, not correctness

A Dockerfile might mount /root/.npm as a cache and then run npm ci. The project’s lockfile must still determine dependency versions; the mount only helps reuse downloaded package data. If the mount is empty, the command may be slower, but it must not install different versions or fail solely because the cache disappeared. If /root/.npm is treated as the only place where node_modules is retained while later instructions depend on it, the mount’s lifecycle can leave the expected files outside the image layer.

Concurrent access also needs to match the cache client. sharing=shared allows concurrent writers to use one mount; private can provide separate caches to concurrent writers; locked makes a later build wait for the current user. Docker’s documentation uses apt caches as an example for sharing=locked because package data needs exclusive access. Do not select one sharing mode for every directory; consider the package manager’s locks, concurrent-write safety, and failure behavior.

A cache configuration can be valid and still not speed up CI

A developer adds a cache mount, sees consecutive local builds get faster, and then notices every CI job downloading packages again. If each runner creates a fresh builder, the documented local mount cache is not restored by --cache-from. The behavior matches the design; it does not necessarily mean the Dockerfile syntax is wrong. A useful diagnosis records builder identity and lifetime, cache mount ID and path, whether the mount was hit, download volume, and whether the RUN instruction actually executed. Then choose whether to reuse a builder or add an external package cache.

Another bad assumption is that /root/.npm contents provide supply-chain verification. Another build may write to the cache, and the content can be reclaimed or stale. Lockfile integrity, package source, dependency review, and final artifact identity need independent checks. A cache can make repeated work faster; it does not automatically make dependencies safer or prove that two builds are reproducible.

Verify empty, concurrent, and exported-cache paths

In a test runner, record the builder ID, run the same build twice, and observe whether the mount persists. Then run it with a new builder and confirm an empty mount still succeeds. Record whether each RUN instruction hit the layer cache so a reused layer is not mistaken for a cache-mount hit. Next export with --cache-to, import into a new builder with --cache-from, and inspect the mount’s starting state. Finally, run concurrent builds and determine whether a package-manager cache needs locked sharing.

No Docker build was run and no download time was measured for this article. Acceptance should record Docker/BuildKit version, Dockerfile syntax directive, builder driver, cache ID, sharing mode, external cache backend, and command results. A performance gain must come from an observed CI comparison; it cannot be inferred from documentation alone. Treating cache-mount contents as data that can be cleared, overwritten, or reclaimed while keeping the build deterministic separates performance optimization from build correctness.

Cache IDs also determine which builds share a directory

Different RUN --mount=type=cache instructions can use id to name a cache identity; without an explicit ID, the target path helps determine the default identity. Branches, projects, or concurrent jobs can unexpectedly reuse package data if they share a builder and cache ID. Give the cache a stable but appropriately isolated identity, and choose shared, private, or locked according to the tool's write-concurrency model. These options govern cache access, not dependency integrity. When setting uid, gid, or mode, make sure the build user can read and write the mount; otherwise cold and warm cache behavior may differ.

Do not use a cache mount as storage for credentials or tenant-specific data. Even though the directory lives in builder storage, the builder's reuse scope determines which builds can mount its contents again. Use BuildKit secret mounts or another dedicated mechanism for private-repository credentials instead of writing authentication material into a reusable cache. No runner isolation test was performed for this article; this is a design judgment based on Dockerfile mount options and CI trust boundaries.
