Why does an EventBridge target stop retrying after five minutes by default?

EventBridge stops delivery when either the retry-attempt or event-age limit is reached. A DLQ must be configured explicitly, and a successful retry does not guarantee exactly-once side effects.

Key takeaways

  • Retries stop at whichever limit is reached first: attempt count or maximum event age.
  • Current custom-event-bus target docs list defaults of 5 attempts or 300 seconds; migrations should compare semantics explicitly.
  • Without a DLQ, exhausted events can be dropped. Treat DLQ entries as replayable work and make the business operation idempotent.

When EventBridge cannot deliver to a target, it stops at whichever limit is reached first: the maximum retry-attempt count or the maximum event age. Current documentation for custom event-bus targets lists defaults of five attempts or 300 seconds. After the limit, only an explicitly configured dead-letter queue (DLQ) receives a failure record. Assuming EventBridge will retry for a full day can send an event to the DLQ after a short outage if a migrated design is still using the defaults.

The two limits compete

RetryPolicy includes MaximumRetryAttempts and MaximumEventAgeInSeconds. The first limits attempts to call a target; the second limits how long delivery continues. Retries stop when either is reached. The API reference lists ranges of 0 to 185 attempts and 60 to 86,400 seconds. Check the current service documentation for defaults for the target type; the custom event-bus target guide currently lists five attempts and 300 seconds.

Increasing one value does not necessarily extend the delivery window. A low attempt count can stop delivery long before a large age limit is used. If event age expires first, attempts may remain unused. An event can reach a DLQ even though an operator thinks the retry “budget” was not exhausted. Treat these limits as one delivery contract, not as two independent retry knobs.

When migrating an older rule or another event product, do not treat an observed day-long retry as the current default. AWS explicitly notes that a design relying on 24 hours of retries should set the maximum event age to 86,400 seconds; the default may be 300 seconds. Align product settings, rule and target types, and deployment templates. Changing a parameter in code does not update a target previously created through the console.

A DLQ is not a recovery process by itself

After target retries are exhausted, an SQS queue configured through OnFailureConfiguration.Arn can receive a dead-letter record. Without a DLQ, exhausted events are dropped; the remaining observable signal may be the EventsDropped metric. A DLQ item is an EventBridge failure-record JSON envelope, not necessarily the original event payload by itself. A consumer should parse the record, extract the event and failure metadata, and retain the original delivery identity.

Failure causes require different fixes. Insufficient permissions, a temporary target outage, a KMS denial, and an invalid message shape are not the same problem. Immediately redriving every item can repeat the same failure or trigger duplicate downstream effects. Classify the errors, fix target permissions or code, limit the redrive rate, and use an event ID or business idempotency key. A replay proves another attempt occurred; it does not prove the first attempt had no side effect.

How can a short outage send an event to the DLQ early?

Suppose a target is under maintenance for 12 minutes while its maximum event age remains at the 300-second default. EventBridge retries according to policy. When the event reaches five minutes old, delivery stops and it goes to the configured DLQ. The target’s recovery after 12 minutes does not automatically return an expired event to the original retry loop. Operators may see a healthy target while some events were not automatically delivered; the issue is a mismatch between the age limit and maintenance duration, not a retry service that never ran.

Increasing maximum age to 24 hours also has a cost: stale business events may execute much later, such as order-status notifications, price updates, or resource cleanup. Derive the age window from business validity instead of assuming larger is always safer. An event outside its useful life may need rejection, compensation, or manual review rather than blind redelivery.

Design an end-to-end acceptance test

In a test event bus, configure a controlled failing target. Verify the default attempt and age limits, which limit triggers first with explicit values, and whether the target receives the event again if it recovers within the age window. Test observability with no DLQ, then configure a DLQ and inspect its envelope, original event ID, error reason, and fields needed for redrive. For migrations, compare existing console settings with the infrastructure-as-code template.

No EventBridge rule, target, or SQS queue was created for this article, and no replay was run. Acceptance should also record target type, Region, event bus, RetryPolicy, EventsDropped, and DLQ enqueue time. Test consumer idempotency, expired-event handling, and replay rate so delivery reliability is not mistaken for exactly-once business effects. A target call’s success must also be observed separately from business processing, a database commit, or a downstream side effect.

A useful policy table includes assumed target recovery time, maximum acceptable delay, retry count per event, whether failure is retained, the DLQ owner, the post-fix replay method, and the idempotency key. Only after these are specified can the team choose a number of seconds and attempts. Otherwise, the values are service configuration rather than a verifiable delivery promise.
