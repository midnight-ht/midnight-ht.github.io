The CMake generator expression is valid, so why did it not expand?

Generator expressions are evaluated during generation and only in supported properties or command contexts. Command-argument parsing happens first, so quoting may matter.

Updated 2026-11-27 · Estimated read 13 min

Key takeaways

  • Generator expressions are not configure-time variable substitution; they are evaluated while generating the build system.
  • Not every property supports them; check the property's documentation.
  • Spaces, semicolons, and nested expressions interact with command parsing, so quote a whole expression when needed.

When a CMake generator expression has valid syntax but does not expand as expected, check three boundaries first: whether generation has happened, whether the target property or command supports generator expressions, and whether CMake split the expression during command-argument parsing because of spaces or semicolons. A generator expression is not configure-time variable interpolation. Writing $<...> does not guarantee that every CMake argument will be evaluated in the right context.

Generator expressions handle configuration-specific information later

Generator expressions can produce build rules based on the build configuration, target properties, platform, or other queryable data. A common example, $<$<CONFIG:Debug>:DEBUG_BUILD>, adds a compile definition for a Debug configuration. It is usually evaluated while CMake generates the build system, not immediately when a CMakeLists.txt configuration command reaches that line. Printing a variable during configuration therefore may not show its eventual value.

This explains a familiar puzzle: target_compile_definitions() contains $<CONFIG:Debug>, configuration succeeds, yet DEBUG_BUILD never appears in the configure log. The expression has not been evaluated at that point. The generator determines the result when it writes rules for a particular configuration. With a multi-config generator, one build tree may support both Debug and Release; inspect the generated rules for each configuration instead of relying on one string from configuration time.

Property support matters as much as expression syntax

CMake documents generator-expression support for many target properties and the commands that populate them, but not all properties support it. A valid expression placed where no evaluation context exists may remain literal or fail during generation. Check the documentation for the specific property instead of assuming that because a neighboring property supports expressions, every argument to the same command does too.

Target references inside expressions also depend on timing and target relationships. An expression can read a target property or resolve a target name while generating different configurations. A target that has not been created, an unsupported reference context, or an empty property can change the result. “CMake expands it automatically” omits the important conditions: which generator, property, target, and configuration perform the evaluation.

Command parsing happens before expression evaluation

Generator expressions are generally processed after command arguments are parsed. If an expression contains spaces, newlines, semicolons, or other characters that may be interpreted as argument separators, the CMake documentation says to pass the entire expression as one quoted argument. For example:

target_compile_definitions(app PRIVATE
  "$<$<AND:$<CONFIG:Debug>,$<BOOL:${ENABLE_TRACE}>>:TRACE_ON>"
)

The quotes keep the composite expression together as a command argument; the configuration condition is still evaluated during generation. If the parser splits it first, an error can look like a generator-expression syntax problem even though the argument boundary changed. Semicolons need particular care because CMake uses them as list separators; the documentation provides escapes such as $<SEMICOLON> for literal special characters.

Expressions can be nested, but deeply nested syntax is harder to inspect. CMake 4.5 documentation adds $<ARGS:...> for converting a CMake list into the argument format expected by expressions, and some expression forms impose constraints on commas in strings. These are not arbitrary shell substitutions. Check the supported expressions for the target CMake version and test the actual argument shape in a small configure-and-generate project. No CMake project was run for this article; the code is illustrative.

Split “not expanded” into three diagnosable failures

The first failure is a timing mismatch: expecting a generator expression to become a configuration value during the configure stage. Move the observation to generation or build output, for example by enabling verbose build output and inspecting the generated command. The second is an unsupported property or context: consult the property documentation and the location of the generation error. The third is argument parsing: inspect quotes, semicolons, newlines, and list expansion, and keep a complex expression as one argument.

A bad assumption is treating ${CMAKE_BUILD_TYPE}, a shell $VAR, and $<CONFIG:...> as variables evaluated at the same stage. The first is a CMake variable; the shell expands the second when a command runs; CMake evaluates the generator expression while generating build rules. They may all appear in one CMakeLists.txt, but their timing and evaluators differ. Changing a value from the wrong stage cannot repair another stage’s expression.

Keep the version, generator, and context fixed during verification

Create a small project in a clean directory and record the CMake version, generator, target property, configuration set, and actual build configuration. Add a conditional definition to a property explicitly documented to support expressions, then add a negative case in a context known not to support them. Inspect generated files or a verbose build log for the result. Follow with an expression containing spaces and a semicolon to test quoting. Preserve each full command and exit status; do not infer a new configuration from a cache in an old build tree.

If behavior changes after switching generators, inspect that generator’s configuration model and property support before changing the expression itself. If only one target fails, check target creation order, inherited properties, and whether referenced targets exist. If the expression remains literal in output, confirm that the output location actually performs generator evaluation. Checking phase, context, and input parsing in sequence is usually more effective than repeatedly rewriting the inside of $<...>.
