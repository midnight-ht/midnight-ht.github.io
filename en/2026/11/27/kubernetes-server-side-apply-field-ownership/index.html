A Server-Side Apply conflict says a field has an owner, not that it can never change

SSA records field managers. A conflicting value is rejected, while force transfers ownership; first clarify controller responsibilities before using force-conflicts.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-27 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • An SSA conflict protects a field declaration; it is different from a generic resource-version conflict.
  • Managers may share ownership while asserting the same value, but a later change can conflict.
  • force-conflicts overwrites the value and transfers field management, so treat it as an explicit handoff.

A Kubernetes Server-Side Apply (SSA) conflict usually protects a field that another manager has declared responsibility for. The new apply wants a different value while the existing manager still owns the field. Inspect managedFields, the current value, and each controller’s responsibility before changing the manifest, changing the manager, or using --force-conflicts to take over intentionally. Automatically forcing every conflict can make GitOps, operators, and human operators overwrite one another indefinitely.

SSA records field management

Client-side apply traditionally stores the last applied configuration in the kubectl.kubernetes.io/last-applied-configuration annotation and compares it with the new manifest. SSA instead asks the API server to record which manager declared which fields. That information is stored in metadata.managedFields. A manager is a client-supplied identity string, such as kubectl, a deployment controller, or a custom tool. It is not a Kubernetes authentication principal and does not grant API permissions by itself.

Suppose a platform controller sets spec.replicas and spec.template, an autoscaler changes replica count, and a release tool updates the image. If several clients use apply configurations that all declare the same field, SSA can report a conflict when one tries to change its value. This makes overlapping ownership visible. A conflict does not mean that the entire object is invalid or that its current value is wrong; it signals that this apply might undo another manager’s still-active declaration.

The official documentation says that changing a field owned by another manager causes a conflict. Managers can share ownership when they declare the same value. Shared ownership is not a permanent exemption: if either manager later changes the field to a different value, the apply can conflict again. A manager can give up its declaration by omitting a managed field from an apply request. When no other manager owns the field, the API server may clear it or restore default behavior. Removing an optional field from a manifest can therefore change behavior; it is not merely text cleanup.

Decide whether this is overlap or an intentional handoff

Imagine a Deployment whose image belongs to a release pipeline, replica count belongs to an HPA, and labels belong to a platform policy tool. A kubectl apply manifest that includes all three can conflict with the HPA if it retains a stale replica count. Renaming the field manager for the whole object does not automatically reorganize ownership according to team intent. A better fix is to narrow the release manifest so each controller writes only its own fields, then check that the desired application state is still produced.

In another case, an old controller has been retired and a new controller is explicitly taking ownership. Force may be appropriate, but first confirm that the old manager will not continue running, document the handoff in the change, and record the resulting ownership. kubectl apply --server-side --force-conflicts overwrites conflicting values and transfers their management to the current manager. It is not a harmless retry flag. If the old controller is still active, force only makes the back-and-forth harder to see and can lead to repeated reconcile conflicts.

There is also an important distinction between apply and ordinary updates. Kubernetes documents that a regular PUT or non-apply update does not fail merely because it modifies a field managed by another manager through SSA, but the update changes the field-management record. A successful ordinary update therefore does not guarantee that the next SSA request will succeed. Nor is managedFields a complete audit history: it describes current field management, not every historical change.

Reproduce the conflict with a small test object

In a disposable cluster, create a ConfigMap and let manager-a use server-side apply to set data.color: blue. Then have manager-b apply green to the same field. The expected result is a field-conflict response. If both managers apply blue, ownership can be shared, but a later attempt by either manager to switch the value to green can conflict. Finally, use force on a test object where the takeover is intentional, then inspect both the value and the manager in managedFields. This is a proposed experiment; no cluster was used here, so these expectations are not execution logs.

For a deployment review, inspect the object and its managedFields with kubectl get -o yaml, then use kubectl apply --server-side --field-manager=<name> --dry-run=server to preview the target manifest. Dry run can reveal some conflicts and validation problems, but it is not a full release test: admission webhooks, concurrent reconciliation, permissions, and later controller behavior still matter. Do not edit managedFields manually; Kubernetes documents it as API-server-managed state.

Choose between eliminating double-writes and audited takeover

If two systems need to manage the same field long term, ask whether their responsibilities can be separated, whether they can use different fields, or whether one can observe without writing. If the product really requires multiple managers to uphold the same field, have them declare the same value and test how future changes will be coordinated; shared ownership is not an approval workflow. If a controller is being replaced, treat force as a scoped transfer of responsibility and verify that every old manager stops declaring the field.

A bad response is to classify every apply conflict as a release failure and append force until the pipeline turns green. The deployment might then steal replica count from the autoscaler or another operator; its next reconcile still produces drift or another conflict. A useful change record names the manager, conflicting field, old and new owners, whether force was used, the commit SHA, and the rollback path. This helps distinguish an overbroad manifest, a changed manager identity, concurrent controllers, and a genuine handoff.

SSA makes disputes among declarative tools visible as conflicts. It cannot decide which tool ought to own a field, and it does not record business authorization. A stable field-responsibility map, server-side preview, and a test-cluster handoff exercise reveal problems during deployment review instead of after several reconcilers have fought over a live object.

During a hand-off, use the stable manager name that will own the field and run a server-side dry run first. Record the conflict list. Ask the current owner to narrow its apply set and preview again, confirming that the new manifest will not accidentally clear fields still owned by the old manager. Force only fields whose transfer has been approved, then read the live object and managedFields back against the expected change. If a controller writes the field back after the dry run, there is still an active writer; one force operation does not complete a responsibility transfer.
