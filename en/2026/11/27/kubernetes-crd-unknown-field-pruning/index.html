A CRD apply succeeds but a field disappears: check schema pruning first

A structural OpenAPI schema defines what a CRD persists. Unknown fields may be pruned before storage unless a specific subtree explicitly preserves them.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-27 · Estimated read 12 min

Article

Key takeaways

  • A successful kubectl command does not prove every input field was persisted.
  • CRD schemas normally prune fields they do not declare; apiextensions.k8s.io/v1 requires a structural schema.
  • Preserving arbitrary JSON is scoped to explicitly marked subtrees and affects validation and CEL visibility.

A successful Kubernetes CRD apply does not prove that every input field was stored in etcd. For a custom resource with a structural OpenAPI schema, the API server validates the object against that schema and may prune undeclared fields before persistence. When a field appears in the submitted YAML but disappears from the GET response, compare the object sent by the client, the CRD schema, and the object returned by the API server before blaming a controller.

The schema is a boundary between the client object and stored object

Suppose a CronTab custom resource needs spec.schedule and spec.image, and its CRD schema declares only those properties. A client also submits spec.retryPolicy. kubectl may reject that unknown property using the API schema published by the cluster. If the request uses --validate=false, the API server still validates and prunes the object according to the CRD schema. The official Kubernetes example shows an undeclared someRandomField disappearing from the creation result.

This makes “the command returned zero,” “the request passed schema validation,” and “the expected field was persisted” three different claims. Client version, validation settings, CRD version, and resource version can change where an error is observed, but disabling client-side validation does not disable API-server behavior. The most useful diagnosis compares the JSON or YAML sent over the wire with kubectl get -o yaml and inspects the active CRD’s openAPIV3Schema.

Why pruning is usually safer than preserving everything

A structural schema gives Kubernetes and controllers a defined shape for the resource: types, nested properties, list semantics, and validation constraints. If unknown fields are always retained, a typo can silently enter the cluster while the controller continues using a default. Later, it may also be unclear who owns arbitrary data left over from an earlier version. Default pruning brings the set of persistable fields closer to the declared API contract and surfaces disagreement between a manifest and the schema.

Pruning can still destroy an intentionally extensible field. For example, an operator might need to store cloud-provider-defined JSON under spec.providerConfig. Kubernetes lets a structural schema mark a specific subtree with x-kubernetes-preserve-unknown-fields: true; unknown structure below that point is retained. If the subtree later declares properties or additionalProperties, those declared portions re-enter normal schema processing. This is not a global switch that disables validation; types and other declarations still need to be read in context.

Preserved unknown data has another limit: Kubernetes documents that CEL expressions cannot access preserved unknown fields. If a team wants both arbitrary extensions and CEL-based field rules, it should reconsider the shape. One option is to keep opaque provider data in a narrow JSON field while declaring business fields structurally. “The API server can store it” does not mean that admission, policy, or controller code can understand it.

Why might a field disappear after apply?

Follow the request through the system. First inspect the object actually sent and its apiVersion. Then inspect spec.versions[].schema.openAPIV3Schema in the CRD: is the field declared at that nesting level, or is it inside a preserve-unknown subtree? Finally, read the stored resource with kubectl get <resource> -o yaml. An unknown-field error can come from client validation. If --validate=false makes the request succeed but the field is absent from the returned object, investigate server-side pruning and the active CRD version.

For a multi-version CRD, check the conversion webhook and storage version too. A field defined in one version is not necessarily present in another, and conversion code can discard data it cannot represent. Existing objects and newly created objects deserve separate tests: changing a schema affects later API behavior, while migration and conversion of stored data depend on the exact versions and storage path. These are verification steps to run in the target cluster; no kubectl experiment was executed for this article.

A poor fix is to put x-kubernetes-preserve-unknown-fields: true on the whole spec just because a field vanished. That makes typos and uncontrolled configuration harder to detect and can make the extension area invisible to CEL. First identify which fields truly come from an external system, then preserve only the smallest opaque subtree and keep types and validation for everything else. The more structural the CRD contract, the more deterministically clients, reviewers, and upgrade tooling can reason about it.

Test both preservation and error detection

In a test cluster, prepare an object containing a declared field and an intentionally misspelled field. Try ordinary client validation and record the schema error. Use --validate=false only to isolate server behavior, then read back the resource and record which fields were rejected or pruned. Next submit the same structure under a dedicated preserve-unknown subtree, verify that only the intended area is retained, and confirm that other fields remain type-checked. If CEL is in use, test the extension subtree to ensure rules do not rely on fields they cannot see.

When changing a CRD schema, compare old and new field paths, defaults, list merge behavior, conversion behavior, and CEL expressions. Exercise representative old resources with reads and writes. A valid CRD YAML file or one successful kubectl apply does not prove compatibility of the field contract. Distinguishing client rejection, API-server pruning, conversion loss, and controller overwrite is what identifies the responsible layer.
