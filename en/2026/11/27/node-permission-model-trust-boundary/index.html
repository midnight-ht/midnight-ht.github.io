Node.js permissions can limit a process, but they are not a sandbox for hostile code

Node.js 22's --permission can reduce accidental access to files, child processes, and Workers in trusted programs. The official documentation explicitly says it is not a security boundary against malicious code.

Key takeaways

  • The model is designed to constrain accidental actions by trusted code.
  • Dependencies are still code that runs with the process's granted capabilities.
  • Put hostile-code isolation at an operating-system or separate-container boundary.

Node.js 22's Permission Model can narrow which files, child processes, Workers, native add-ons, and other resources a process may access. It is useful for reducing accidental overreach by trusted software; it does not make untrusted JavaScript safe. The official documentation describes a “seat belt” approach and makes no promise that the model can resist malicious code. Decide whether the code is trusted before choosing the flags. Do not treat --permission as a universal sandbox switch.

What kind of mistake is it meant to prevent?

Imagine a local document-conversion service. It reads from an upload directory, writes converted files to a dedicated output directory, and loads several project dependencies. A trusted converter release contains a path-joining bug and accidentally overwrites a user's configuration elsewhere on the same host. The Permission Model can help narrow the readable and writable areas, making that mistake less able to cross the intended boundary. The idea is: “This program is trusted, but it should not touch arbitrary resources,” much like giving a trusted employee a key that opens only specific rooms.

Now change the premise. An attacker can control JavaScript executed by the converter, or one of its dependencies is malicious. The code can deliberately search for ways to act outside the intended scope. An application cannot rely on its own declared permissions alone to guarantee isolation. Node.js's security policy treats code that a user asks Node to run as trusted; the Permission Model documentation also warns that malicious code can bypass the model and perform operations that were not granted. Applying an accidental-misuse control to an adversarial threat puts the boundary in the wrong place.

This article checks the Node.js v22 documentation, which currently identifies version v22.23.5. The model was added in v20.0.0 and ceased to be experimental in v22.13.0. Flags and available permissions evolve across release lines. The v22 scope here should not be generalized to every Node version, nor should behavior across operating systems, filesystems, and native modules be assumed identical.

Express the minimum required permissions

Suppose the service entry point is /srv/converter/app.mjs, input comes from /srv/converter/inbox, and output is written only to /srv/converter/outbox. Before deployment, write a permission table. Reading the entry point and dependencies is needed at startup. The inbox is read-only. The outbox is writable. Access to other users' directories is unnecessary. If the converter does not invoke a shell, do not grant child-process creation. If it does not use Workers, do not grant Worker access. Then grant those paths and actions using the syntax for the exact Node v22.23.5 release you deploy.

This is a configuration-design example. It was not run against a real converter project in this environment, and it does not prove that every dependency starts under those restrictions. Tightening should begin in an isolated test environment with representative jobs. Observe denied accesses, then decide whether each one is a required feature or a hidden dependency. Do not grant read and write access to an entire host directory merely to make the process start; that would defeat least privilege. Each added grant should name the code path that needs it and explain how a narrower scope was ruled out.

Why do dependencies change the trust boundary?

Permissions apply to the running process, not only to the entry-point function you wrote. Once loaded, a dependency can try to use capabilities available to that process. Therefore, “our code reads one file” is not sufficient evidence that “this process can read only one file.” Dependency upgrades, optional plugins, and build-script changes can add resource needs, so permission scopes should be reviewed when the version or dependency tree changes.

A common counterexample is to run arbitrary Pull Request code in CI with permission to write to a deployment directory and read production credentials, then assume --permission will stop every possible way of exfiltrating them. The Permission Model is not a security boundary against malicious code. It cannot justify exposing credentials. Untrusted contributor code should be isolated from deployment secrets, host credentials, and production networks. If operating-system users, containers, or virtual machines provide that isolation, inspect their mounts, kernel capabilities, network rules, and host interfaces. Those external boundaries determine the strength of isolation.

How can you verify that a narrower policy still works?

Treat permissions as reviewable configuration rather than a one-off startup trick. Record the exact Node version, launch flags, allowed paths, and denied accesses. Use test inputs that cover reads, writes, conversion failures, temporary files, and optional features that need a child process. If a feature needs more access, first ask whether a controlled interface can replace it; otherwise grant only the corresponding path or action. A runtime permission-query API can tell code whether a scope is available, but “allowed” proves only the policy state, not that the business code is safe.

Test negative paths as well: an attempt to read outside the allowed area should be denied, as should a write outside the output directory. Then run the actual conversion path and confirm that required operations still work. The tests and commands are not executed in this article, so they are an acceptance plan, not a successful run log. Production adoption still needs validation against your operating system, Node build, dependency graph, and deployment model.

When should isolation live outside Node?

If you run your own service code with reviewed dependencies and mainly want to reduce path mistakes or accidental child-process use, the Permission Model can add a useful defense-in-depth layer. If the workload executes user scripts, marketplace plugins, unknown npm packages, or external submissions, design for the possibility that code is malicious. That usually means combining operating-system and deployment-platform controls over identity, filesystems, networks, resource limits, and process lifetime. Node's own restrictions are not a replacement for that layer.

A threat-model record should state which code is trusted, which inputs an attacker controls, which host resources the process can reach, and what an escape could affect. Answer those questions before deciding whether to enable --permission, which scopes to grant, and what an external sandbox must control. The feature is useful when placed at the right trust boundary; it should not create the impression that hostile code has already been contained.

The configuration and verification flow above is a design example. It does not claim that a converter or production environment was executed or validated.
