Why can a CMake installation break after its directory moves?

Compare copied and relative-symlink CMake installations, then check both after moving their install trees.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-16 · Estimated read 8 min
Translations
zh-CN en

Article

Key takeaways

  • Inspect file types and symlink targets.
  • Move the install tree to test whether it is self-contained.
  • Check existing entries when switching installation modes.

Relative-link installation leaves a path back to its source. Moving only the install tree can break it. After CMake reports success, check whether the installed file is a copy or a symbolic link.

A build produces a directory for the next job. The template reads correctly in place. After moving the directory, the same entry no longer opens. The path can still exist as a symbolic link whose target is no longer reachable from the new location.

Check what installation leaves behind

The CMake installation-mode reference describes copying as the default. Since CMake 3.22, the environment variable can change how files are installed. REL_SYMLINK creates a relative link and fails if it cannot. This example avoids a mode that falls back to copying, so the two file types remain distinct.

A development tree may benefit from an ongoing connection to source files. A package handed to another environment may need to stand alone. A readable template on the build host establishes neither portability nor which file supplies its bytes.

Move the same files one directory deeper

Save the complete CMakeLists.txt below and create payload.txt alongside it with payload-v1 followed by a newline. Use fresh output and install destinations. This example ran with CMake 4.2.3 on a macOS filesystem that supports symbolic links.

cmake_minimum_required(VERSION 3.22)
project(InstallMode NONE)
install(FILES payload.txt DESTINATION share/demo)

cmake -S . -B out
CMAKE_INSTALL_MODE=COPY cmake --install out --prefix "$PWD/copy"
CMAKE_INSTALL_MODE=REL_SYMLINK cmake --install out --prefix "$PWD/links"
mkdir package
mv copy package/copy
mv links package/links

The archived exercise used equivalent separate absolute prefixes. Both installed entries read payload-v1 before the move. It also recorded the symlink string. After moving each install tree one level deeper, the copy remained readable. The symbolic link was still present but its target could no longer be resolved. The outer check exited zero. The source stayed in place. Moving a tree that preserves both ends’ relative layout can produce a different result.

Check link identity and target availability independently. A conventional existence check can make a dangling link look like a completely missing entry. Reading the copied file’s content answers a different question from either file-type check.

Test the intended delivery boundary

For a standalone package, install copies and verify them in an environment without the original source. If a delivery intentionally keeps links, record their targets and the required relative layout. Validate path, type and contents separately. A test that opens just one file in the original directory can pass for both installation modes.

Check the archive and its extracted files separately from the install prefix. A packager that dereferences links can produce a readable archive even when the original install tree was not self-contained. This is a proposed check, not a result of the relocation exercise.

For another control, change the source after installation. The symlink can continue to expose the edited file while the copy contains the earlier bytes. That variant was proposed but not run. See when CMake writes a generated file for another distinction between configuration and what actually reaches a destination.

Does switching back to COPY replace an existing symlink?

The manual warns that switching away from a symlink mode does not replace the existing link with a regular file. Use a clean install prefix and inspect the resulting file type if the delivery now requires a copy. If the path must be reused, inspect and handle the old entry explicitly. The main exercise used separate fresh prefixes and did not run this mode-switch variation.
