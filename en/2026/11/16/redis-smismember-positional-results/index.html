Why doesn’t SMISMEMBER return the member names?

Use mixed and repeated requests to check positional Redis membership replies.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-16 · Estimated read 7 min
Translations
zh-CN en

Article

Key takeaways

  • Flags are returned in request order.
  • Repeated inputs keep their positions.
  • All-zero flags cannot explain whether the set exists.

Redis SMISMEMBER returns one membership flag per input position, in request order. The reply contains no member names. A repeated input still occupies a position, so keep the request order when attaching flags to the original work.

Imagine checking tags for several jobs before showing a status on each card. Two jobs can use the same tag. Deduplicating tags and then assigning the replies to the original jobs position by position can shift a result to the wrong card.

Preserve the question behind each flag

Redis introduced SMISMEMBER in version 6.2. It checks multiple candidates against one set and returns 1 for a member and 0 for a nonmember or missing key. The reply is ordered to match the request. Attach each flag to its input when the consumer needs attribution. Redis SMISMEMBER.

Summing the flags answers a different question. Two batches with the same hit count can have hits at different positions. A client can deduplicate its queries if it retains enough information to rebuild the original positions.

Mix a hit, a miss, and a repeated hit

The following teaching commands are unexecuted. Use an isolated Redis instance and an unused key. The set contains a and c. The first query requests c, b, c, and a. The second requests b and a against the same set.

SADD {members-example}:known a c
SMISMEMBER {members-example}:known c b c a
SMISMEMBER {members-example}:known b a

Expect 1, 0, 1, 1 from the first query and 0, 1 from the second. Verify both reply length and positions. A client that sorts requests but does not restore their original order can still have the correct hit count and length. Preserve the actual outgoing member sequence before diagnosing the reply.

A whole-request test can also exercise two inputs that normalize to the same value. Keep the original value, the submitted value, and the returned flag distinct. That application test was not run.

Match the result to the caller’s work

For a row-oriented UI, an output list can preserve each row ID with its result. A map can suit a caller that explicitly works with unique tag IDs. If the implementation uses a map internally, rebuild the original output list before handing it to a consumer that needs repeated entries.

Splitting a batch also requires preserving original positions. Test a value repeated across chunks and exercise one request failing while the other succeeds. A command failure should not be turned into a normal array of misses. These application probes were not run. A related Redis intersection article concerns counts rather than attribution.

Can an all-zero reply distinguish a missing key?

Check the same values against an absent key and an existing set containing neither value. Both should return zero at each position. The membership array does not distinguish those reasons. Use the configuration authority if the product needs to distinguish an unconfigured set from a normal miss. A separate existence check does not establish a shared snapshot under concurrent changes.
