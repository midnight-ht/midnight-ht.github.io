Why can’t Go Rows.Next returning false certify a complete result?

Use an identical row prefix to distinguish normal completion from a terminal Go database/sql error.

Updated 2026-11-16 · Estimated read 10 min
Translations
zh-CN en

Article

Key takeaways

  • Next can return false for distinct reasons.
  • Check Rows.Err after iteration.
  • Keep Scan errors and partial delivery separate.

Go’s Rows.Next returns false when there is no row left to scan or when preparing a row fails. Check Rows.Err after the loop before treating the collected result as complete.

Imagine exporting orders from a database. The first row scans successfully. Preparing the next one fails. Old code sees false, returns its list, and presents a one-row export as complete. Retain distinct evidence about starting the query, reading each row, and ending the iteration.

Separate completion from a failed read

The standard library says Next prepares the next row for Scan. A false result cannot distinguish exhaustion from an error. Rows.Err supplies that distinction. Each Scan requires a preceding successful Next. This is a multi-row contract rather than the one-row QueryRow path. Go database/sql Rows.

An endpoint that promises complete output needs to check the query, the current row’s conversion, and the terminal iteration result. A nonempty list cannot substitute for any of those checks.

Keep the two prefixes identical

The unexecuted teaching program uses a small standard-library test driver. Both scenarios return ID 12 first. The clean mode then reports EOF. The broken mode returns a sentinel error. The test does not connect to a real database.

package main

import (
    "context"
    "database/sql"
    "database/sql/driver"
    "errors"
    "fmt"
    "io"
)

var readFailure = errors.New("fixture read failure")

type demoDriver struct{}
type demoConn struct{}
type demoRows struct {
    first bool
    end error
}

func (demoDriver) Open(string) (driver.Conn, error) {
    return demoConn{}, nil
}
func (demoConn) Prepare(string) (driver.Stmt, error) {
    return nil, errors.New("unexpected Prepare")
}
func (demoConn) Close() error { return nil }
func (demoConn) Begin() (driver.Tx, error) {
    return nil, errors.New("unexpected Begin")
}
func (demoConn) QueryContext(_ context.Context, mode string, _ []driver.NamedValue) (driver.Rows, error) {
    var terminal error = io.EOF
    if mode == "broken" {
        terminal = readFailure
    }
    return &demoRows{first: true, end: terminal}, nil
}
func (*demoRows) Columns() []string { return []string{"id"} }
func (*demoRows) Close() error { return nil }
func (r *demoRows) Next(dest []driver.Value) error {
    if r.first {
        r.first = false
        dest[0] = int64(12)
        return nil
    }
    return r.end
}

func run(db *sql.DB, mode string) {
    result, queryErr := db.QueryContext(context.Background(), mode)
    if queryErr != nil {
        panic(queryErr)
    }
    defer result.Close()
    var ids []int
    for result.Next() {
        var id int
        if scanErr := result.Scan(&id); scanErr != nil {
            panic(scanErr)
        }
        ids = append(ids, id)
    }
    terminal := result.Err()
    want := map[string]error{"clean": nil, "broken": readFailure}
    if len(ids) != 1 || ids[0] != 12 || !errors.Is(terminal, want[mode]) {
        panic(fmt.Sprintf("%s: %v, %v", mode, ids, terminal))
    }
    fmt.Println(mode, ids, terminal)
}

func main() {
    sql.Register("rows-demo", demoDriver{})
    db, openErr := sql.Open("rows-demo", "")
    if openErr != nil {
        panic(openErr)
    }
    defer db.Close()
    run(db, "clean")
    run(db, "broken")
}

Both paths should scan ID 12. The clean path should finish with no Rows.Err, while the broken path should return the sentinel. A test that checks the first result, its count, or the initial query alone would accept both. This fixture gives every output its own expected result and makes no claim about production buffering or network timing.

Decide what a consumer can do with a prefix

An API can buffer the result and report failure before presenting it as complete. A streaming contract may present a prefix and later send a distinct terminal outcome. Data already sent does not disappear when the caller receives an error. A separate integration test can show ID 12 and then a failure and verify that the UI never marks the export complete.

An intentional early exit is another case. If the application chooses to keep only the first result, report that limit rather than inferring exhaustion. Give the complete and intentionally limited paths separate acceptance tests. Those application checks were not run. The related QueryRow error article covers the single-row boundary.

Can Rows.Err replace a failing Scan check?

Check the Scan result directly. For a separate case, present nonnumeric text and scan it into an integer. Expect a conversion error and verify that the application does not deliver the row. The documented Rows.Err contract concerns iteration and should not stand in for checking Scan. This variation was not run. The main example covers two endings after a successful scan.
