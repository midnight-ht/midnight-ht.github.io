Why is a blank required input invalid before it is user-invalid?

A blank required input can be invalid before a submit attempt. Read both selectors before submission, after failure, and after correction.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-16 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • A blank required field can match :invalid at first render
  • Read user invalidity after a native submit attempt
  • Compare the same empty value before and after submission

Open a project creation form and the name field is empty. The browser already knows it violates the required constraint, but the user has not attempted to submit. A red outline based on :invalid would make an unanswered field look like a rejected submission. Check ordinary validity and user validity separately before choosing when to show the error style.

An empty required field starts out invalid

An empty value does not meet the required constraint. For a text input that is a candidate for constraint validation, :invalid can already match when the page first renders. It doesn't depend on a script writing an error message or the user pressing a button.

The :user-invalid selector also depends on what HTML calls user validity. For this input, that flag starts false. The selector needs a candidate for validation that fails its constraints and has user validity set to true. The flag isn't a verdict that the answer satisfies its constraints. A field can have user validity true and still be invalid.

An attempted submission through a native button sets the user validity of the relevant fields before interactive constraint validation. The empty input fails in this fixture and blocks submission. Reading again should show a match for both selectors. The browser may also show its own validation feedback, which is a separate observation from either CSS rule.

Once the user types a valid project name, neither invalid selector matches. That result alone doesn't establish that the flag was cleared. The input now satisfies its constraint, so one of the necessary conditions is already missing. Reset behavior has its own test below.

Keep both selector readings

Save the following as a local page. The one required field has no default value. The read button inspects the two selectors without trying to submit. The script records the initial state and prevents navigation for a valid submission. No form data is sent.

<!doctype html>
<meta charset="utf-8">
<title>Required input states</title>
<style>
  input:invalid { border-color: #646d7b; }
  input:user-invalid { outline: 3px solid #ac3126; }
</style>
<form id="form">
  <label>Project name <input id="project" name="project" required></label>
  <button type="submit">Try submit</button>
  <button type="button" id="read">Read current matches</button>
</form>
<pre id="output"></pre>
<script>
const byId = document.getElementById.bind(document);
const field = byId('project');
const output = byId('output');

function record() {
  const ordinary = field.matches(':invalid');
  const interacted = field.matches(':user-invalid');
  output.append(String(ordinary) + ' | ' + String(interacted) + '\n');
}

byId('form').addEventListener('submit', event => event.preventDefault());
byId('read').onclick = record;
record();
</script>

Expect true and false on the first line. Start from a fresh form. With the field still empty, click Try submit and then Read current matches. The next line should be true and true. Type Atlas and use the read button again. The third line should be false and false. The columns correspond to ordinary invalidity and user invalidity.

Pair the readings with what you see. If the selector matches but the outline does not appear, check for an overriding rule. If the target browser does not support a selector, record that boundary before deciding how the product will deliver error feedback.

These are predictions from the standards. No browser or assistive technology was exercised for this article. In a real form, run the three states and separately check how a keyboard user finds and corrects an error. The example tests when a style can match. It does not implement a complete accessible error workflow.

Test the actual trigger

A check that only looks for :invalid on an empty value can pass whether the first render is quiet or shows the error too early. Use the same empty value at two separate moments, then add a valid value to check recovery. This catches timing changes without needing a complicated validation rule.

If the app submits using an external control or a script, follow that actual entry point. Reuse both selector readings. A visible click that never entered the native validation flow is a different issue from a selector failing to match after an attempted submission.

An outline can identify a field. Text can tell the user what's missing. If the larger form reports several failures, check both this field's styling and the route a user can take from the overall feedback to the input. Changing a CSS match doesn't supply a useful message by itself.

Start a regression from a fresh form before any entry. Observe the screen, attempt an invalid submission, then read again after correction. Treat input methods, autofill, and different control types as separate product conditions if they matter to the implementation.

Does a native reset make the empty required field red again?

The user-invalid style in this fixture should stop matching. Imagine adding a native reset button after the invalid submission attempt. The input reset algorithm clears user validity and restores an empty value when no default was supplied. Empty still violates the required constraint, so :invalid is true. Resetting the flag makes :user-invalid false. Another attempted submission can make it match again.

A custom Clear button that only changes the value has not performed the reset algorithm. If the product needs to restore the entire initial state, check both the value and the selector matches. A blank field alone reveals neither the action nor its effect on user validity.

For submissions initiated by script, see how to preserve validation and submitter intent.
