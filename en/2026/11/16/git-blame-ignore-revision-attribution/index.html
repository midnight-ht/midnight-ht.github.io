How do you read Git blame past a formatting commit?

Compare attribution on an unchanged file before and after explicitly ignoring a mechanical Git revision.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-16 · Estimated read 9 min

Article

Key takeaways

  • Inspect the scope of the revision before ignoring it.
  • Attribution can change while the current line stays fixed.
  • Read the actual historical patch to establish intent.

A formatter now owns the whole block in Git blame. Once you have checked that the revision only changes formatting, ignore it explicitly and look for the earlier attribution.

A service setting changed from initial to ready. Later, the team standardized spacing around equals signs. Blame now points to the formatting commit. Its author can explain the spaces, while the earlier patch may explain the setting. Keep the current file fixed while comparing those two views.

Look past one named revision

The Git blame manual describes --ignore-rev as ignoring that revision’s changes during attribution. Git tries to attribute affected lines to an earlier commit that changed those lines or nearby ones. The operation leaves the current file and history intact. Inspect the candidate revision before ignoring it, especially if it mixes mechanical changes with behavior.

Save ordinary blame and the result with the revision ignored. Compare full object IDs, then read the earlier patch to check whether it explains the decision. A name or attribution alone does not establish intent.

Use one file and three commits

This complete script ran with Apple Git 2.50.1 in a disposable repository. The commits record the original setting, the behavior change and the spacing change. The script compares its output with object IDs saved when each commit was created.

set -eu
work=$(mktemp -d)
trap 'rm -r "$work"' EXIT
cd "$work"
git init -q -b main
git config user.name Fixture
git config user.email fixture@example.invalid
git config commit.gpgsign false
printf 'mode=initial\n' > settings
git add settings
git commit -qm base
printf 'mode=ready\n' > settings
git commit -qam behavior
behavior=$(git rev-parse HEAD)
printf 'mode = ready\n' > settings
git commit -qam formatting
formatting=$(git rev-parse HEAD)
plain=$(git blame --porcelain -L 1,1 -- settings | head -1)
ignore=$(git blame --porcelain --ignore-rev "$formatting" -L 1,1 -- settings | head -1)
test "${plain%% *}" = "$formatting"
test "${ignore%% *}" = "$behavior"
test "$(cat settings)" = 'mode = ready'
printf 'formatting: %s\nbehavior: %s\nplain: %s\nignored: %s\n' \
  "$formatting" "$behavior" "$plain" "$ignore"

Ordinary blame returned the formatting commit. The ignored view returned the behavior commit. The current file still contained the spaced version. The script exited zero. Compare the IDs within one run since a new repository will have its own object identities.

As a proposed negative control, make the last commit change ready to stopped as well as the spacing. Its patch would now contain a behavior change worth investigating. That variant was not run. It illustrates why a formatting label alone is an insufficient reason to ignore an entire revision.

Preserve the review input

A single revision can be enough for a one-off lookup. For a reviewed list of formatting commits, use a file of complete object names. The manual explains that command-line lists follow configured lists. Preserve the command and relevant settings so a teammate can reproduce both views. This fixture uses no default ignore file.

Record the inspected commit, path and exact line contents. Another branch can have the same setting on a different line or in a different file. Confirm both viewers are inspecting the same subject before attributing differences to an ignore option. Comparing two patch series answers a complementary question about which patches changed between revisions.

Record what each reported commit actually changed. The formatting patch should explain the spaces, and the earlier patch should explain the value. If that does not match, check the branch and configured ignore list before investigating further.

Can Git always find earlier attribution for a newly added line?

No. For a line touched by an ignored commit that cannot be attributed to another revision, blame.markUnblamableLines can mark it with an asterisk. blame.markIgnoredLines marks lines that could be reassigned. Use a separate fixture with an unmatched added line to test this case. The executed fixture changed only the formatting of an existing line.
