Why does Map.groupBy split objects that share a name?

Group the same three tickets by object reference and by name. Verify membership and check what happens when a new object looks identical to an existing key.

Translations

Article

Key takeaways

  • An object key is distinguished by identity
  • Nonadjacent items can belong to one group
  • Choose the key using the application’s identity rule

Three tickets in a list all display Support as their department. After Map.groupBy runs, the page renders two groups with the same heading. The first contains the first and third tickets. The second contains only the middle ticket. Check what the grouping callback hands to the map. It may return two distinct department objects while the UI reads the same name from each.

Which rows actually share a key?

Suppose there are two objects, A and B. Each has the name Support. Tickets T1 and T3 refer to A, and T2 refers to B. In input order the references are A, B, A. Group by department object and the first A creates a group. The final A joins it. B creates its own group between them.

The key comparison uses object identity. Printing identical fields does not establish that the keys are the same. A label tells the reader what the group represents. To retrieve the group by object key, pass the same reference the grouping operation used. A third object with an identical name retrieves neither A nor B.

The values in the map are arrays. Within each group, they contain the assigned records in input order. Reading group A therefore yields T1 followed by T3. A gap in the input does not create another group for the same key.

Use the same three tickets for both tests

The following script holds the input constant. One callback returns the department object, while the other returns its name. The assertions check membership by both original keys and confirm that a newly created lookalike has no group.

import assert from 'node:assert/strict';

const a = {name: 'Support'};
const b = {name: 'Support'};
const rows = [
  {id: 'T1', team: a},
  {id: 'T2', team: b},
  {id: 'T3', team: a},
];

const group = Map.groupBy;
const byTeam = group(rows, row => row.team);
const byLabel = group(rows, ({team}) => team.name);
const identities = [
  [Array.from(byTeam.keys()), [a, b]],
  [byTeam.get(a), [rows[0], rows[2]]],
  [byTeam.get(b), [rows[1]]],
  [byTeam.get({name: 'Support'}), undefined],
  [Array.from(byLabel.entries()), [['Support', rows]]],
];

const {deepEqual, equal} = assert;
for (const [actual, expected] of identities) deepEqual(actual, expected);
equal(byTeam.size, 2);
console.log('Object identity and label grouping checks passed.');

The assertions passed in local Node. Grouping by object gave two keys: T1 and T3 under A, and T2 under B. Grouping by name gave one Support key with all three rows. Each result matches its callback. The script makes no network request and provides no evidence about whether your API responses share references.

Before bringing the test into an application, write down the expected member IDs as well as the group count. The count could be right even when T2 and T3 are assigned to the wrong places. Membership is the stronger check. A debug log can also record whether the departments that look alike actually hold the same reference.

Records decoded from separate responses can refer to different objects for the same department. If the application's identity is a stable department ID, group by that ID and get the display label separately. Check the ID's scope first. If two organizations can reuse it, a cross-organization list can't use that ID alone.

In another application, two organizations may each have a Support department that should remain separate. Grouping by name would merge them. Object keys are reasonable when the system holds shared reference objects and treats those as identities. Start with which records are meant to go together.

Look for callbacks that create a fresh object for every row. A callback might assemble two fields in an object in order to group by that combination. Every new object still has its own identity. Reuse one stable object per combination where that is the chosen model, or use an existing domain key that has the intended scope.

Retain the key, the visible label, and the member IDs in diagnostic output. If duplicate headings appear, those details let you determine whether two groups should coexist or whether an identity rule split one group. A log containing only strings identical to the headings can't answer that question.

A legitimate pair of same-name departments can produce the same screenshot as a single department split by mistake. Test both cases when changing the key. Use a stable known department identity for the rows that should merge, and Support departments in separate organizations for the rows that should stay apart. Check membership against each row’s organization and department.

If the groups also support actions such as collapsing a section or navigating to its department, keep a distinguishable identity for those actions. The headings can remain short. A user selecting one group should not act on the other just because their visible labels match.

Will a ticket move automatically if its department changes?

No. First create the two groups, then change T1's team to B. The object in group A still represents T1, and reading its team now reveals B. The group array retains T1 and group B does not gain it. The assignment finished before that property changed.

Regroup the updated rows or make the membership change explicit in application code. Test the new department, T1's removal from the old group, and its presence in the new one. Checking only the updated property leaves old membership undetected.
