Why can pytest pass with a misspelled configuration key?

Hold the test fixed while checking pytest’s warning, strict failure, and repaired result for an unknown configuration key.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-16 · Estimated read 7 min
Translations
zh-CN en

Article

Key takeaways

  • Passing assertions leave configuration validity unanswered.
  • Strict configuration promotes parsing warnings to errors.
  • Record the chosen config file and test outcome.

Passing tests do not prove pytest recognized the configuration key. An unknown key can produce a warning under the default behavior. Strict configuration can turn that warning into an error.

A maintainer asks for concise test output and still sees the full report. Every test passed. Before investigating assertions, establish which configuration the command read and whether its keys were registered by the active pytest environment.

Misspell one key while leaving the test unchanged

The pytest configuration reference says strict_config raises an error for warnings encountered while parsing the pytest configuration section. The command-line switch is --strict-config. This example concerns an unknown configuration key. It makes no claim about unrelated Python warnings.

Create a disposable directory. Save the test below as test_example.py and save the two configurations as bad.ini and good.ini. Disable external plugin autoload and extra pytest options from the environment. The exercise ran with pytest 9.0.2 and Python 3.11.15.

def test_sum():
    assert 2 + 3 == 5

[pytest]
addoptz = -q

[pytest]
addopts = -q

Run each command in that directory and record its own status. The middle command is expected to fail.

python -m pytest -p no:cacheprovider -c bad.ini
python -m pytest -p no:cacheprovider -c bad.ini --strict-config
python -m pytest -p no:cacheprovider -c good.ini --strict-config

The ordinary run passed and warned about the unknown option. It exited zero. The strict run reported that option as an error on standard error and exited four. The fixed file passed strict mode with one test and exit zero. The fixture kept the same test throughout. Preserve both output streams and the exit status so the error retains its explanation.

Check what the gate actually covers

Strict configuration can flag unrecognized keys. For accepted values, still verify the result that matters. The corrected option in the example requests quieter output. A job concerned with test coverage should also check the selected nodes rather than inferring their identities from configuration acceptance.

If a key only fails in CI, check whether it comes from a missing plugin. Removing the setting could leave the intended feature absent. Confirm the environment, plugin registration and config path first. Explicit -c keeps the fixture controlled. Actual entry points can select a different file, so retain the one the real job reports. See what strict markers catch and what selection still misses for a separate gate.

Point both entry points at the same absolute config file when comparing them. If the gate is required in CI, check a deliberately invalid fixture as well as the corrected one. That shows whether the wrapper actually preserves the configuration failure.

Can strict-config replace strict-markers?

They govern different inputs. Configuration warnings are separate from unknown test decorators. Try a valid configuration with a deliberately unregistered marker to verify the marker gate separately. The main fixture uses no markers, and this additional control was not run.
