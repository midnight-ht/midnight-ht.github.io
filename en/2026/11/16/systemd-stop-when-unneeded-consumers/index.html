Why did systemd stop the shared service after its last consumer stopped?

Use two systemd consumers to reason about when a shared service stays active and when it can stop automatically.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-16 · Estimated read 8 min
Translations
zh-CN en

Article

Key takeaways

  • Configure the policy on the shared unit.
  • Check the last consumer with a declared dependency.
  • Unit dependencies do not measure live application connections.

A shared unit can opt into stopping when nothing needs it. Systemd follows unit dependencies. If its last dependent stops, the shared service can stop too.

Two local workers use the same service. It stays active when the first worker stops and exits after the second. Before attributing this to an application failure, inspect the shared unit’s cleanup setting and the dependencies that still exist.

Inspect the policy on the shared unit

The systemd.unit manual gives StopWhenUnneeded a default of false. When enabled, it can stop a unit after no active unit needs it. Put the setting on the service you want the manager to clean up.

This fixture uses Wants from the consumers to the shared service. In systemd 262, the reverse WANTED_BY relationship participates in the cleanup check. The manager also considers jobs, unit transitions and impending restarts. Observe settled unit states instead of assuming a submitted stop has already taken effect. Systemd 262 cleanup check and dependency mapping

Stop one consumer, then the other

Use an isolated Linux test system. This proposed exercise has not been run. Save the first definition as shared-lab.service. Save the second under both client-lab-a.service and client-lab-b.service. The units only sleep.

[Unit]
Description=Shared dependency lab
StopWhenUnneeded=yes

[Service]
ExecStart=/bin/sleep infinity

[Unit]
Description=Consumer in shared dependency lab
Wants=shared-lab.service
After=shared-lab.service

[Service]
ExecStart=/bin/sleep infinity

Load all three units and start both consumers. Check that all three are active. Stop the first consumer. The shared service should stay active while the second remains active. Stop the second and check whether the manager stops the shared service. Allow outstanding jobs to finish before comparing final states.

shared=shared-lab.service
first=client-lab-a.service
second=client-lab-b.service
status() { systemctl show -p ActiveState "$shared"; }

systemctl start "$first" "$second"
status
systemctl stop "$first"
status
systemctl stop "$second"
status

The last read is a snapshot. Retain jobs and logs if the manager is still stopping the shared unit. Keep the middle observation separate and discard a run in which either consumer failed to become active.

Repeat with StopWhenUnneeded=no, starting from a clean test state. With no other dependency or process failure, expect the shared service to remain active after both consumers stop. A failure to stay active in that control warrants inspection of the loaded settings and the process exit reason.

Check which clients the unit graph describes

Automatic cleanup fits a service whose lifetime belongs to these short-lived consumers. External callers may not have corresponding unit dependencies. Their last successful requests and the manager’s unit state answer different questions. Define who controls the lifetime before enabling cleanup for a service with external callers.

Retain the loaded definitions, the consumer states, and the shared unit’s exit record. If a real application must remain available during a handoff, validate that request path separately. See runtime directory retention during unit restarts for the distinct question of what happens to files around a stop.

Can PartOf make a unit stop with a designated service?

PartOf propagates stop and restart actions from listed units to the unit carrying the declaration. That is a different contract from waiting until no consumers remain. It can follow one designated consumer even while another remains active. The main example does not configure it. Test the propagation and direction separately if that relationship is required.
