Why is a heapq.merge result still out of order?

Use a two-stream Python fixture to check the merge precondition and its failure boundary.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-16 · Estimated read 7 min
Translations
zh-CN en

Article

Key takeaways

  • Every input must already be sorted.
  • Check values and order independently.
  • A descending merge requires descending inputs.

Python’s heapq.merge expects every input stream to be sorted by the same rule. It can choose the next item across streams, but it does not reorder a particular stream. If the output has a backward step, inspect each source before blaming the merged ordering.

Imagine merging two operation logs by timestamp. One is produced by an ordered query and the other comes from a backfill. A smaller timestamp can be hidden behind a larger one in the backfill. A consumer that has already received the larger timestamp cannot be rewound automatically.

Keep the merge precondition visible

The standard library describes a lazy merge of already sorted inputs. It does not pull all values into memory at once. If a comparison key is supplied, each stream needs the same ordering by that key. Looking at the candidates currently available cannot reveal a smaller item that has not yet been reached. Python heapq reference.

Count and ordering have separate contracts. A consumer can receive all four events and still have a misleading cursor if it assumes each later event has a later timestamp. That downstream contract needs its own test.

Change only one input’s order

This complete program ran on Python 3.11.15. Both calls have four identical values. Only the second stream’s order changes.

from heapq import merge

good = list(merge([1, 4], [2, 3]))
bad = list(merge([1, 4], [3, 2]))
assert good == [1, 2, 3, 4]
assert sorted(bad) == good
assert bad != good
print("sorted inputs:", good)
print("one unsorted input:", bad)

The positive run produced 1, 2, 3, 4. The invalid input produced 1, 3, 2, 4 in this run. The assertion verifies the same values are present and that the order differs. The bad arrangement is an observation for this fixture, not a guaranteed result for invalid inputs.

Verify input ordering close to the source if that helps diagnose a failure. Record the stream name and the pair that violated ordering. If output must stay invisible after any validation error, a streaming check that discovers an error late does not satisfy that contract by itself. This program did not exercise application delivery.

Decide who owns ordering

An ordered query can supply a documented key to the merge. A small batch already held in memory may be simpler to sort as a whole. A large lazy source needs a clear producer precondition and an error policy. This sample compares no performance measurements.

Test a concrete combined key when stable tie-breaking is part of the result. Order each source by timestamp and event ID, then exercise equal timestamps across two streams. Check just the timestamp groups when the consumer legitimately does not care about order within them. The related heapq priority tie article handles ordering among queued objects, rather than pre-sorted input iterators. These application cases were not run.

Does reverse=True reverse ascending sources automatically?

The documentation requires each input to be descending for a descending merge. Give it streams containing 4, 1 and 3, 2 and expect 4, 3, 2, 1. Supply an ascending source separately to test an application’s precondition check. This reverse variant was not run.
