Why doesn’t singledispatch choose a handler from the second argument?

Trace first-argument selection and the default path in four executed Python calls.

Key takeaways

  • Selection uses the first argument’s type.
  • The implementation can handle later parameters itself.
  • Verify fallback and inheritance separately.

Python’s singledispatch chooses an implementation from the first argument’s type. Annotating another parameter or changing the value passed there does not make it part of the dispatch. Express a second decision explicitly when both inputs matter.

Imagine an inventory exporter that accepts a product ID and an output mode. It has implementations for integer and string IDs. Someone annotates the output argument and expects an integer mode to switch between them. The integer ID still selects the integer handler. Inspect the actual first argument at the dispatch boundary.

Separate registration from argument handling

The standard library uses the first argument for dispatch. When registration is inferred from annotations, the first parameter supplies that type too. A selected implementation can still examine other arguments itself. The example returns labels so formatting and conversion cannot be mistaken for dispatch. Python functools.

The decorated function is registered for object and serves as the fallback. Decide whether unknown records should reach a real default handler or a clear error. The sample reports a label so the fallback remains visible.

Change the two positions independently

The following program ran on Python 3.11.15. Its first two calls keep the integer record while changing the output argument. A third uses a string record and retains the integer option. The last supplies a value without a specific registration.

from functools import singledispatch

@singledispatch
def route(record, output):
    return "base"

@route.register
def number(record: int, output: str):
    return "integer"

@route.register
def text(record: str, output: int):
    return "text"

inputs = [(4, "json"), (4, 0), ("4", 0), (object(), "json")]
actual = [route(record, target) for record, target in inputs]
assert actual == ["integer", "integer", "text", "base"], actual
print(actual)

The observed labels are integer, integer, text, and base. The second call still selects the integer implementation. The annotations are not a runtime check for the remaining parameter. A real implementation could accept dispatch and then fail while handling an unsupported second value. Verify both stages when diagnosing that result.

An integer 4 and a string containing 4 can display the same way while selecting different handlers. Keep the input types in the expected results. If an application wrapper converts the record before the call, test that entry point independently. This program never runs an exporter.

Give a second decision its own place

An implementation can select a serializer after dispatching by record type. Another design can map an explicit pair of record kind and output format to behavior. Give unsupported pairs their own outcome. For example, an integer ID may support JSON and text while a string ID supports only text. Verify the three supported combinations and the rejected fourth. This integration matrix was not run. A related Pydantic validation article concerns a different question about how typed objects are validated.

Keep a fallback control when adding registrations. A new success does not prove existing unknown inputs still use their intended path. If a refactor changes the parameter order, exercise the real caller and check which position the generic function receives first.

Can an unregistered subclass use its parent’s implementation?

If there is no registration for the concrete type, the documented search follows method resolution order toward a more general implementation. A separate call with True should choose the int handler in this fixture because bool subclasses int and has no own registration. Add a bool registration only if the interface needs a distinct behavior, then check True and 4 independently. That inheritance probe was not run.
