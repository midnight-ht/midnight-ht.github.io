Does a false return from Go AfterFunc’s stop mean cleanup finished?

Separate Go AfterFunc cancellation, stopping, and callback completion with two channel-based controls.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-16 · Estimated read 7 min
Translations
zh-CN en

Article

Key takeaways

  • The stop function does not wait.
  • Two paths can yield false.
  • Use an independent completion signal.

The stop function returned by Go’s context.AfterFunc does not wait for the callback. A false result can mean the callback has started or that it was stopped earlier. Use a separate completion signal when cleanup needs to finish before another operation can proceed.

Suppose a download uses a callback to clear a temporary resource registration after cancellation. The download code sees false from stop and reuses the resource ID. The callback might still be waiting for a lock. Decide from the callback’s outcome rather than inferring completion from the attempt to stop it.

Read what stop actually reports

The registered function runs in its own goroutine after cancellation. Its stop function reports true when it prevents the callback from running. The same return value can also come from a callback that was previously stopped. The standard library explicitly says stop does not wait. Completion requires explicit coordination with the callback. Go context AfterFunc.

A successfully prevented callback cannot send its own completion signal. If multiple callers can stop it, save the decision in a shared lifecycle or give one caller ownership. Otherwise a late stop returning false does not tell a waiter which path happened.

Hold the callback in a known running state

The following complete teaching program is unexecuted. It registers a callback and cancels the context. Once running, it announces its entry and waits for release. A separate context gives a previously-stopped control.

package main

import (
    "context"
    "fmt"
)

func main() {
    ctx, cancel := context.WithCancel(context.Background())
    started := make(chan struct{}, 1)
    release := make(chan struct{})
    done := make(chan struct{})
    stop := context.AfterFunc(ctx, func() {
        started <- struct{}{}
        <-release
        close(done)
    })
    cancel()
    <-started
    if stop() {
        panic("callback already started")
    }
    select {
    case <-done:
        panic("callback still held by test")
    default:
    }
    close(release)
    <-done

    fresh, finish := context.WithCancel(context.TODO())
    suppressed := context.AfterFunc(fresh, func() {
        panic("stopped callback unexpectedly ran")
    })
    before, again := suppressed(), suppressed()
    finish()
    if !before || again {
        panic("unexpected stop states")
    }
    fmt.Println("running false; completed after release; stopped true then false")
}

For the running callback, stop should return false while done remains open. Release the callback and observe completion separately. On the separate context, stop should return true and then false before its context is canceled. That second false has the same value as the first case and implies a different lifecycle. The sample operates on channels and contexts, with no actual resource.

An application can signal closure after its cleanup and record any error separately. If normal completion also releases the resource, exercise both entry points and check that release happens only once. The related Go detached cleanup article deals with independent deadlines. This fixture concerns when a callback finishes. The application probes were not run.

What if the context was already canceled before registration?

The reference says the callback is invoked immediately in its own goroutine. Test entry and completion separately with the same kind of release gate. Do not rely on an unsynchronized ordering of log messages between the caller and the callback. That separate case was not executed.
