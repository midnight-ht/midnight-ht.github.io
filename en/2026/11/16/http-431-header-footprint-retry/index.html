What should you reduce after HTTP 431?

A smaller body can still get 431. Use a fictional header budget to distinguish a single oversized field from an oversized set and see what the client can change.

Article

Key takeaways

  • 431 concerns request header size
  • Check single fields and the total
  • Use the actual endpoint contract when reducing optional fields

A ticket client receives HTTP 431 and shortens the notes in its JSON body. The next submission has a smaller body and gets the same status. The server is rejecting the size of the request header fields. Check the field footprint and the receiving endpoint's limits before choosing which optional field to reduce.

One field or the set of fields can be too large

RFC 6585 allows a server to reject a request because its header fields are too large. The limit can concern the whole set or one field. When a single field is at fault, the response content should identify it. An aggregate failure may have no individual field to identify.

That puts the problem at a different part of the request from its business content. Changing a ticket from two pages of text to a line does not fix a header limit when the request still carries the same field values.

RFC 9110 does not set one HTTP size limit for all field lines or sections. Applications, proxies, and deployments can differ. Check your endpoint's contract and the diagnostics you control. The example uses deliberately small numbers for arithmetic, without treating them as protocol defaults.

Use a fixed budget to isolate the fields

The fixture counts only the lengths of its own ASCII values. A value can have at most twelve characters and the sum can be at most twenty. Real HTTP implementations may count names, delimiters, or other representation overhead. This code does not connect to a server or establish any endpoint's actual limit.

import {deepEqual} from 'node:assert/strict';

function assess({fields}) {
  const values = Object.entries(fields);
  const oversized = values.find(([, value]) => value.length > 12);
  if (oversized) return [431, oversized[0]];
  const total = values.reduce((sum, [, value]) => sum + value.length, 0);
  return total > 20 ? [431, 'total'] : [200, 'accepted'];
}

const wide = {label: 'x'.repeat(13)};
const combined = {label: 'x'.repeat(11), note: 'y'.repeat(10)};
const cases = [
  [{fields: wide, body: 'longer body'}, [431, 'label']],
  [{fields: wide, body: ''}, [431, 'label']],
  [{fields: combined, body: ''}, [431, 'total']],
  [{fields: {label: combined.label}, body: ''}, [200, 'accepted']],
];
for (const [request, expected] of cases) deepEqual(assess(request), expected);
console.log('Body, per-field, and total fixture cases passed.');

All four assertions passed locally. The first two cases send the same label of thirteen characters in the model, first with a body and then without one. Both receive the label-specific 431. The third case has lengths eleven and ten. Neither exceeds twelve, but their sum is twenty-one, so the total rule rejects them. Removing the optional note leaves eleven, which the example accepts.

The two controls serve different purposes. The shorter body with identical fields locates the constraint. Two individually acceptable values show why the largest field is not the only possible issue. Use the actual documented rules for an endpoint regression; don't carry the toy limits into that test.

If a client adds more optional metadata over time, keep a distinction between required and optional fields. A tag used only for a display feature may be removable. Check the application contract before changing it and preserve required authentication fields. A request-size correction doesn't have to change who is allowed to make the request.

Record enough to diagnose the result

A support ticket can name the layer that made the decision, the reason it reported, and the sizes of non-sensitive fields. It doesn't need their values to diagnose the fixture's two cases. Apply the system's logging policy before keeping details about real requests. A size only has meaning under the counting rule that produced it.

After changing the client, keep the same business body when testing the correction. If fields and body change together, a successful response does not tell you which change mattered. Save the failure and the result after the change. A request that fits can still fail another application rule. The example's 200 marks only the local budget decision.

RFC 6585 permits resubmission after reducing the request header size. The application still needs its own contract for resubmitting a ticket and recognizing prior or duplicate outcomes. A header size change doesn't establish those workflow rules.

If two layers you operate can reject the request, record their decisions separately. Acceptance at the first does not establish that the second applies the same limits. Identify which layer generated the response before choosing a regression. An absent application log can mean the request stopped at the gateway.

Record the sample’s non-sensitive fields, their expected sizes, and the rule intended to fire. If one optional field is no longer part of the contract, update the client against that contract rather than inferring its rules by varying requests.

After shrinking the fields, can a cache return the old 431?

A cache must not store a 431 response for subsequent reuse under RFC 6585. Suppose a request failed because it carried too much optional metadata and the client removes that metadata. The old rejection cannot serve as a cache hit for the current request. If 431 appears again, check the source of the current response and whether the fields now satisfy that layer’s rules.

That restriction concerns using an earlier response to answer later requests. An operational record can still document why an earlier request failed. The script models the size decision only. It does not implement a cache or measure a proxy’s storage behavior.
