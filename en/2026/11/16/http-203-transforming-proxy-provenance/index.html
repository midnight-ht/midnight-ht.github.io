Is HTTP 203 a failure? Check the response’s transforming proxy

Compare an origin catalog with a 200 response and a transformed view with a 203 response. Keep the request path when interpreting or validating the delivered content.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-16 · Estimated read 11 min
Translations
zh-CN en

Article

Key takeaways

  • 203 reports successful delivery of transformed content
  • The status does not enumerate the changes
  • Keep the request path for later validation

A catalog service returns two records at the origin. Through a proxy operated by the same team, the client receives one record and an HTTP 203 response. The request succeeded, but the content differs from what a direct read returns. Keep the route when diagnosing the discrepancy so you can find the layer that transformed the content.

A 203 reports a transformation of a successful response

RFC 9110 uses 203 for a successful response whose content a transforming proxy modified from the origin's 200 response. The proxy can use the status to tell the recipient about the transformation. A catalog with one record at the proxy and two at the origin does not by itself indicate failed delivery.

Suppose a test catalog contains A and B. An internal presentation route is configured to show selected entries only. Where that transformation is permitted, the proxy applies the rule, keeping A and dropping B. The origin receives no deletion and still has both entries. The difference is in what this response delivers.

The status indicates that a transformation happened. It doesn't identify every change. To explain the difference, read the proxy policy or compare the evidence on both sides. Absence of a 203 does not establish that there was no transformation. Using this status is an option for a transforming proxy.

This is about a meaningful content change. A forwarding intermediary can perform normal HTTP processing without changing the application catalog. Compare the actual origin and delivered records instead of treating a change to transfer framing as proof that the catalog itself changed.

Keep both receipts in a controlled example

This script models only the permitted transformation route. The input contains A and B, the view selects A, and the proxy uses 203 in this example. It doesn't start a server or forward an actual response. Its run verifies the local model.

import {deepEqual} from 'node:assert/strict';

const origin = {
  route: 'origin',
  status: 200,
  content: ['A', 'B'],
};

function projectCatalog(reply) {
  const content = reply.content.filter(id => id === 'A');
  return {route: 'catalog view proxy', status: 203, content};
}

const result = projectCatalog(origin);
deepEqual([origin, result], [
  {route: 'origin', status: 200, content: ['A', 'B']},
  {route: 'catalog view proxy', status: 203, content: ['A']},
]);
console.log('Catalog receipts match both expected routes.');

The local assertion passed. The direct receipt has 200 with A and B. The view receipt has 203 and A. The check covers both status and content, so an implementation that changes only one cannot pass. This comparison offers no evidence that a deployed proxy actually applies these rules.

If a client keeps only a response body, a later read on another route can make a stable origin look like a changed catalog. The user saw A through the proxy yesterday and sees A and B directly today. That's insufficient evidence that B was added today. Preserve the path from each read before drawing a conclusion.

The standard notes that later validation of the content may apply only on the same request path. Keep provenance and validation information for direct and transformed reads. Establish whether you are validating what the origin produced or what the application delivered to the user before reusing a validation result.

Handle the receipt in a client

If the client recognizes precisely 200 as success, find out whether its contract deliberately limits successful responses or simply omits other cases. A catalog client designed for the proxy view can process the delivered content and preserve the 203 in diagnostics. Follow the specific endpoint contract for payload handling.

Check the rendered catalog and diagnostics separately. The user should see A and support should be able to tell which path produced it. If the client reports a network failure, inspect its classification of 203. If it displays B, verify which route's content it actually consumed.

Use the same fixed data on both routes when testing. A test that updates the catalog in between requests adds another cause for a difference even when the proxy policy hasn't changed. Record the scenario, content version, and request path.

A debugging receipt can carry record IDs and the route without storing the full catalog. To reproduce this example, keep the applicable selection rule and the IDs seen on each path.

Can a proxy transform a response with no-transform and then use 203?

No. Add the no-transform response directive to the example and the proxy must not remove B under its catalog rule. RFC 9110 limits the transformation itself. A status reporting a transformation cannot override that directive. If the product needs a different presentation, build it from a source or representation where the change is permitted.

For that test, confirm the restriction is present and then inspect the delivered records. The negative case should keep both A and B. A changed status wouldn't repair a forbidden transformation. This is a specification prediction; the script exercised only the permitted case.

For the difference between checking a representation and checking content bytes from a specific response, see what Content-Digest and Repr-Digest each cover.
