Why did a BuildKit multi-platform export add another directory level?

Compare BuildKit local exporter layouts using a distinct marker for each target platform.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-16 · Estimated read 8 min
Translations
zh-CN en

Article

Key takeaways

  • Multi-platform exports default to separate directories.
  • Merged outputs need distinct file names.
  • Verify paths and contents after exporting.

BuildKit’s local exporter defaults to subdirectories for multiple platforms and a flat output for a single one. Adding a platform can change the path a downstream job needs to read.

A packaging job used to read an artifact directly from the export directory. The build still completes after another platform is added, but uploading fails because the file is no longer at that path. Inspect the resulting tree before changing the consumer. A recursive search can find the wrong platform’s artifact and still report success.

Make platform identity visible in file names

The Docker local and tar exporter reference describes the local exporter’s platform-split option. A multi-platform local export uses separate directories by default. With the option set to false, it merges output into one directory. Those rules concern the local file tree.

Save this complete Dockerfile in an isolated context. Its first stage performs its work on BUILDPLATFORM and writes names and contents using the target arguments. The final stage contains the marker. The example checks paths, not cross-compilation. It has not been run.

# syntax=docker/dockerfile:1
FROM --platform=$BUILDPLATFORM alpine:3.22 AS make_marker
ARG TARGETOS
ARG TARGETARCH
RUN mkdir /out && printf '%s/%s\n' "$TARGETOS" "$TARGETARCH" \
    > "/out/marker-$TARGETOS-$TARGETARCH"
FROM scratch
COPY --from=make_marker /out/ /

Use the same compatible BuildKit builder for both commands and give them separate, empty destinations.

platforms=linux/amd64,linux/arm64
docker buildx build --platform "$platforms" --output type=local,dest=./split .
docker buildx build --platform "$platforms" \
  --output type=local,dest=./flat,platform-split=false .
Layout Expected path Contents
Default split/linux_amd64/marker-linux-amd64 linux/amd64
Default split/linux_arm64/marker-linux-arm64 linux/arm64
Merged flat/marker-linux-amd64 linux/amd64
Merged flat/marker-linux-arm64 linux/arm64

The table gives predicted outcomes. Record the actual builder, paths and file contents when running the exercise. A file count would miss two incorrectly labeled outputs. Checking the full paths and their contents distinguishes a layout problem from a target-argument error.

Match the layout to what reads the files

Keep separate directories when readers select artifacts by platform. Use a merged layout only where each output has a distinct name and the consumer needs a single level. The example does not test collisions. Choose a naming convention or keep the directories separate before comparing artifacts with identical base names.

A negative control can apply a single-platform upload contract to the default multi-platform result. A marker expected at the root should be missing there, while it remains available inside the platform directory. This consumer check was not run. Use a fresh output directory so a stale file from a previous flat export cannot satisfy it.

When substituting real artifacts, verify their contents and platform requirements independently. A correctly named binary can still fail on the named system. Docker’s independent copy-layer example covers a separate property of image layers. This article checks the files exported to the host.

Keep each export’s exit status with its destination. A failed flat export must not hand a consumer the old flat directory. Build a platform-to-path checklist from the planned platform list and compare that checklist with this run’s artifacts. These release-side checks are proposed.

Can a single-platform export still include a platform directory?

Yes. Specify platform-split=true explicitly. The reference distinguishes this from the default flat single-platform export. Use it if the consumer needs a consistent platform directory whether it receives one platform or several. Check the exact resulting path. The single-platform variation was not run in the main multi-platform exercise.
