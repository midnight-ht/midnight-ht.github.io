Why can daily PostgreSQL series points be 25 hours apart?

Compare calendar-day and 24-hour series across a documented historical transition using separate local-date and UTC-time oracles.

Updated 2026-11-10 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • Consecutive local dates need not be 24 hours apart.
  • Record generation zone, display zone, step, and endpoints separately.
  • Derive an independent local-date vector for a 24-hour comparison.

A timestamptz series advancing by local calendar days need not have 24-hour gaps between instants. PostgreSQL 18 can generate the series using a named time zone’s clock and daylight-saving adjustments. Across a fall-back transition, consecutive local midnights can be 25 hours apart without a missing local date.

Suppose a regional report needs a row for every date, including dates without events. An engineer sees an extra hour between UTC values and proposes inserting another point. First decide whether the report requires consecutive local dates or fixed-duration samples. Adding a fixed-duration point to an already complete calendar series can duplicate a local bucket.

Record generation and display zones separately

PostgreSQL 18’s set-returning function table includes an optional timezone argument for the timestamptz overload. It controls time-of-day and DST calculations; without it, the session TimeZone is used. The example fixes UTC display and passes America/New_York explicitly so generation semantics are not hidden in a connection default.

Changing display does not remove an explicit generation zone. Conversely, omitting the fourth argument and changing the session setting can change more than formatting: it changes the rules the generator uses. Preserve input types, explicit endpoint offsets, step, generation zone, and display environment.

The site’s AT TIME ZONE type-direction article distinguishes instants from local clock values. Here projection into New York supplies a separate local-date check. The timestamp-without-time-zone overload is different; do not mechanically append a fourth argument to every call named generate_series.

Check dates and elapsed time independently

This complete query has not been executed. The historical 2001 New York boundary follows the period used in the official example. It is not a prediction of future time-zone policy or validation of deployed time-zone data.

SET TIME ZONE 'UTC';
WITH s AS (
  SELECT generate_series(
    timestamptz '2001-10-27 00:00-04',
    timestamptz '2001-10-30 00:00-05',
    interval '1 day',
    'America/New_York'
  ) AS t
)
SELECT t,
       t AT TIME ZONE 'America/New_York' AS local_clock,
       extract(epoch FROM t - lag(t) OVER (ORDER BY t)) AS elapsed_seconds
FROM s
ORDER BY t;

The independent local oracle contains October 27, 28, 29, and 30, all at midnight. The UTC oracle is October 27 at 04:00, October 28 at 04:00, October 29 at 05:00, and October 30 at 05:00. Expected successive differences are NULL, 86,400, 90,000, and 86,400 seconds. The first point has no predecessor; do not fill its difference with one day merely for convenience.

The date vector checks calendar coverage. The differences check elapsed duration. Requiring every gap to equal 86,400 would reject the intended calendar series. Checking only four rows is also inadequate: four rows could contain a duplicated date and omit another.

Derive a new oracle for a 24-hour step

The date/time arithmetic documentation distinguishes an interval’s day field, which advances the local date while preserving clock time, from its microseconds field, which adds literal elapsed time. Change only the step above to interval '24 hours'.

This comparison is unexecuted too. Its independent UTC oracle is October 27, 28, 29, and 30 at 04:00, exactly 24 hours apart. Projected into New York, those values are October 27 at 00:00, October 28 at 00:00, October 28 at 23:00, and October 29 at 23:00. October 28 appears twice; October 30 midnight is not a generated point. Reusing the first query’s local-date expectations would be wrong.

The endpoint remains October 30 at 00:00-05, or 05:00 UTC. The final fixed-duration point is at 04:00 UTC, still within the bound; the next point exceeds it. An endpoint bounds generation but need not lie on every step’s grid. Identical endpoints do not imply identical local dates after changing the step.

Choose the calendar contract before filling gaps

For a report settled by regional calendar dates, derive boundaries using that region’s rules before joining events. For fixed-duration sampling, specify the duration grid and anchor and accept changing local clock values. A generator does not decide business day ownership or prevent an event at a shared boundary from being counted twice by a later join.

The site’s timestamp and recurring-intent article covers the stored schedule model. This article checks one finite series, not a complete scheduler. Future rules, holidays, and nonexistent or ambiguous local times require additional policies. One historical midnight example cannot validate every region or appointment.

A real run should archive the PostgreSQL version, deployed time-zone data source, full query, both oracles, and row-level differences. Establish semantics before investigating join performance. No database was connected and no production throughput was measured here.

Should an empty series first be blamed on DST?

Check inputs and direction first. The function documentation specifies zero rows for positive steps with start greater than stop, negative steps with the opposite mismatch, and null inputs. A zero step is an error. These conditions add a no-candidate branch, unlike the four-row example with unequal durations.

Retain endpoint values and types and test direction mismatch, null parameters, and a zero step separately. Do not package all of them as a successful empty report: an empty result may be allowed or may reveal an omitted upstream endpoint. Establish that points should exist before applying the local-date and UTC-time oracles to calendar boundaries.
