Why did HSET return 0 after updating the value?

Keep HSET’s count of added fields separate from write errors, final values, and the meaning of a retry after a lost reply.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-10 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • HSET counts new fields rather than changed values or success.
  • Overwrites and same-value writes can both return zero.
  • A retry count cannot reconstruct an earlier command whose reply was lost.

HSET returning zero does not mean that an update failed. Its integer reply counts newly added fields. Overwriting an existing field can change its value without adding a field, so a valid update can return zero. Converting that count directly into a success boolean sends normal overwrites down a failure path.

Suppose a nickname changes from old to new. A cache wrapper gets zero and reports “save failed,” yet a subsequent read returns new. Those observations need not imply inconsistent storage. The wrapper interpreted a field-addition count as success, while the read inspected the value. This is a teaching scenario, not a recorded user-service incident.

What the reply measures

The official HSET documentation says that the command sets specified fields, overwrites existing fields, and creates a hash key if the key does not exist. Both RESP2 and RESP3 integer replies count fields added. Adding a field and overwriting one can therefore produce one and zero respectively without either command failing.

The count is not changed_values either. Writing new over old and writing new over new both leave the field set unchanged. Zero cannot distinguish them or establish the old value. A business requirement to record content changes needs its own design.

Key creation and field creation also differ. Adding city to a hash that already contains name adds a field without creating the key. Calling the result key_created introduces another misleading contract. Name the quantity added_fields rather than affected, changed, or success.

Four writes to one owned hash

These redis-cli commands have not been executed. Use your own disposable empty instance and replace the prefix with a unique name for this exercise. Do not overwrite a similarly named key in a shared instance.

HSET nov10_example_unique:user name old
HSET nov10_example_unique:user name new
HGET nov10_example_unique:user name
HSET nov10_example_unique:user name new
HSET nov10_example_unique:user name newer city Shanghai
HGETALL nov10_example_unique:user

The independent expected HSET replies are 1, 0, 0, and 1. The first adds name; the second changes its value; the third writes the same value without adding anything; the fourth adds city while overwriting name. The intermediate read should return new. The final mapping should contain name=newer and city=Shanghai. These are derived expectations, not manufactured command output.

Retain the field set before each write, its reply, and the reads. Final state alone could hide the wrapper rejecting the second update; replies alone do not establish the intended values. Do not assert HGETALL presentation order: compare the mapping.

The command history dates multiple field/value arguments to Redis 4.0.0. Record the actual server and client versions and verify the complete arguments sent by the wrapper. Current documentation does not establish old dependency support. Client single-field and multi-field methods may expose different language return types; the integer described here is the command reply, not a promise about every wrapper API.

Keep errors separate from a zero count

An expression such as if (!reply) rejects ordinary overwrites in languages where zero is false. That can trigger a retry or an incorrect failure message. Preserve transport and command errors through an explicit error channel, and preserve a normal reply as its actual count. This does not mean every returned value proves business success.

Add a failure probe using another owned key containing a string, then issue HSET against it. A wrong-type error must not be swallowed and converted into zero. That probe is unexecuted here. Actual exception classes, error objects, and connection state require evidence from the selected client.

The site’s Redis transaction error article covers per-command results within a batch. If HSET is placed in a transaction or pipeline, identify its own reply rather than letting an outer batch boolean replace its meaning.

Likewise, SET and TTL replacement covers expiration behavior. An added-field count is not expiration evidence. When values, existence, and expiry all matter, inspect them separately.

Specify an adapter contract before using a client result. If the selected method returns an integer, preserve zero as added_fields=0. If a single-field method exposes “field was new” as a boolean, false means an existing field was set, not necessarily that the call failed. This is a proposed adapter contract, not a claim that every library has that interface.

Send the four writes through the actual wrapper and inspect the underlying reply, wrapper result, and user-facing error separately. A multi-field method must not collapse a count of two to true and later reinterpret it as one. Preserve exceptions in the failure probe. Record the exact client method, version, and return type to locate where a quantity became a success flag.

Can retrying after a lost reply recover the first addition count?

Not reliably. The first command may have added the field before the connection failed. Reissuing it can then overwrite the existing field and return zero. That reply describes the second command; it does not reconstruct the first attempt’s history.

A “set the final value” contract can design a retry around desired state, while still considering whether overwriting another writer is allowed. A “reward the first creation” contract cannot reconstruct a unique business event from the retry count. Inspect current state and use the business operation’s identity; concurrency, durability, repeated delivery, and external effects need separate acceptance evidence. None of those paths has been tested here. The supported conclusion is narrower: field-addition counts must not masquerade as success booleans.
