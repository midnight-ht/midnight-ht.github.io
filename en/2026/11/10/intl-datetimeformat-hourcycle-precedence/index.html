Why does a formatter still use 12-hour time after requesting h23?

Trace merged options, locale hc preferences and hour12 precedence using a fixed UTC instant and local effective-option output.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-10 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • A defined hour12 option overrides hourCycle control.
  • Explicit hour cycles and locale preferences follow resolution precedence.
  • ResolvedOptions is not an unchanged constructor-input backup.

An options object containing hourCycle:"h23" does not guarantee that the formatter uses it. If merged defaults still contain hour12:true, resolution handles that boolean choice first. Capture the complete object passed to the constructor, then inspect resolvedOptions rather than inferring behavior from the caller’s small configuration fragment.

Imagine a report component requesting hours zero through twenty-three while shared defaults require twelve-hour display. Adding hourCycle leaves the existing hour12 intact. Changing timeZone to remove the surprising display can then change the displayed time without resolving the conflicting preference. This is a configuration example; no actual report or user setting was changed.

Precedence is not property order

The current ECMA-402 CreateDateTimeFormat algorithm handles hour12 separately. When it is not undefined, it nulls the hc resolution option and subsequently chooses a twelve- or twenty-four-hour variant from locale data. A precise-looking string does not automatically outrank the boolean option.

The retrieved document identifies itself as the 2027 internationalization draft, not a final future edition. Its resolution rules are the source contract; locale data and rendered wording still depend on the implementation. Keep the runtime alongside the normative reference in an engineering record.

Without hour12 overriding it, an explicit hourCycle option can override an hc preference in the locale tag. A locale requesting h12 combined with an explicit h23 option should therefore be examined after option resolution. Locale defaults apply when a more explicit preference is absent. Writing a property earlier or later within the same final object does not alter the algorithm’s precedence, although merging objects determines which values survive.

Distinguish a missing field, undefined and false. False is a definite twenty-four-hour preference, not “no preference.” A component exposing only one control can reject conflicting configuration or remove the other field under a documented policy. Keeping two controls that appear equivalent but express different intentions makes the contract harder to inspect.

Fix the instant and time zone before comparing

The sample uses one UTC instant, one locale and the same hour/minute fields. It changes only the cycle-related options and prints the request, effective options and semantic parts.

const instant = new Date('2026-11-10T00:30:00Z');
const common = {timeZone: 'UTC', hour: 'numeric', minute: '2-digit'};
const configure = extra => Object.assign({}, common, extra);
for (const [name, options] of [
  ['locale hc', common],
  ['explicit h23', configure({hourCycle: 'h23'})],
  ['boolean wins', configure({hourCycle: 'h23', hour12: true})]
]) {
  const formatter = new Intl.DateTimeFormat('en-US-u-hc-h12', options);
  console.log({name, options, resolved: formatter.resolvedOptions(),
    parts: formatter.formatToParts(instant)});
}
// Independent semantic expectations: locale hc h12; explicit h23; boolean case 12-hour cycle.
// The h23 case represents hour zero at UTC midnight; do not assert a cross-locale full string.

The independent expectations are h12 for the locale-only case, h23 for the explicit-cycle case, and a twelve-hour variant when hour12:true is added. Under Node v24.21.0, the observed resolved cycles were h12, h23 and h12, with hour parts 12, 00 and 12. The second case still formats the same UTC instant; no hours were added or subtracted from the event.

That output verifies these comparisons in this local environment. It does not promise identical punctuation, spacing or day-period labels across locales. The third case selecting h12 for the recorded en-US data does not make hour12:true universally equivalent to that exact subtype. Full-string snapshots need an explicit reason to freeze those localized details.

FormatToParts helps inspect hour, minute and dayPeriod semantically. It does not justify discarding localized separators or rebuilding every display indiscriminately. This example is diagnostic, not a custom date-layout engine.

Twenty-four-hour preference is not a complete midnight requirement

The h11, h12, h23 and h24 values describe specific hour ranges. A boolean twelve-versus-twenty-four-hour preference does not independently state every midnight detail. If acceptance requires a zero-based midnight hour, preserve that exact cycle intention in the final options rather than assuming every hour12:false mapping is h23.

The negative case retains both hour12:false and hourCycle:h23, then treats a zero-based result on one machine as a permanent guarantee. The output can happen to agree while the configuration still communicates conflicting controls. Remove the unwanted control, inspect the effective options, and report any unmet environment requirement rather than shifting the instant to improve the screenshot.

Time zone selects the clock context for an instant; it does not override the cycle-selection rules. Date parsing, instants and display zones covers the other semantic problem. A pure date’s default interpretation is not the explanation for an hour12 option surviving a merge.

A useful target-runtime check includes midnight and an afternoon time, with both request and effective options recorded. Expected semantic properties should come from the requirement and specification, not from calling the same formatter again to manufacture an expected value. Literal formatting assertions require their own justification because locale data may change.

Why is hourCycle absent when formatting only a date?

When the effective format contains no hour, do not assume every cycle field will appear. The resolvedOptions specification describes effective options, not an unmodified backup of the constructor input. Establish whether hour or timeStyle produces an hour component before investigating a missing cycle field.

All three main cases request hour explicitly. Removing it and formatting only a date changes the condition and therefore the expected result. A missing field in that different format is not evidence that a browser ignored a requested hour cycle. The original object answers what was requested; effective options answer what the format adopted.

Before delivering a time component, state which preference control is supported, how conflicts are resolved and which time zone is used. Then verify midnight and an ordinary time in the target environment. Only the local three-case script was run here; browser and device checks remain separate.
