Trace the initial accumulator in four reduce calls

Inspect accumulator initialization through omitted arguments, explicit undefined, singleton objects and an observed negative maximum case.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-10 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • Unseeded reduce needs a first present value.
  • Explicit undefined still supplies the initial argument.
  • Define seed type and empty-input policy for the aggregation.

Omitting reduce’s second argument differs from explicitly passing undefined. Without an initial accumulator, reduce must find the first present input value as its seed. Empty input provides none, so it throws TypeError. It does not automatically choose zero for a sum or decide what the product should display when there are no records.

Consider a charge-detail list whose total works until a filter removes every row. Catching all exceptions and returning zero can hide unrelated errors. First establish the required result type and the accumulator’s source. The example uses synthetic integer units, not real billing or accounting.

Argument presence comes before argument value

The ECMAScript reduce algorithm distinguishes whether initialValue was supplied. Zero length without that argument throws. With it, the accumulator is initialized to the supplied value. Undefined can be explicitly supplied, so an empty array with that seed returns undefined rather than taking the missing-seed branch.

For nonempty input, the unseeded form takes the first present value and starts invoking the reducer at the next present item. The seeded form also passes the first present item through the reducer. This can change the first accumulator’s type, callback start and eventual result.

A singleton object is particularly revealing. With no seed, that object can be returned unchanged without a single callback invocation. Tests containing only two or more rows may miss a total function that returns an entire record for one row. A numeric return annotation does not create a numeric accumulator at runtime.

Four calls and a typed aggregation contract

The script compares empty and singleton cases, then totals charge records from an explicit zero. Its receiver requires complete own positions and nonnegative safe-integer fees, checking the running total as well. Those are this example’s rules, not requirements imposed on every reducer.

const add = (sum, value) => sum + value;
const cases = [
  ['empty omitted', () => [].reduce(add)],
  ['empty zero', () => [].reduce(add, 0)],
  ['empty undefined', () => [].reduce(add, undefined)],
  ['single object omitted', () => [{fee: 7}].reduce(add)]
];
for (const [name, invoke] of cases) {
  try { console.log(name, invoke()); }
  catch (error) { console.log(name, error.name); }
}
function sumFees(rows) {
  if (!Array.isArray(rows)) throw new TypeError('rows must be an array');
  for (let i = 0; i < rows.length; i++) {
    if (!Object.hasOwn(rows, i) || !rows[i] ||
        !Number.isSafeInteger(rows[i].fee) || rows[i].fee < 0) {
      throw new TypeError('each row needs a nonnegative safe integer fee');
    }
  }
  return rows.reduce((sum, row) => {
    const next = sum + row.fee;
    if (!Number.isSafeInteger(next)) throw new RangeError('total too large');
    return next;
  }, 0);
}
console.log(sumFees([{fee: 7}, {fee: 3}]), sumFees([]));
// Independent expectations: TypeError / 0 / undefined / {fee:7}; totals 10 and 0.

The independent expectations are TypeError for empty unseeded input, zero for an empty zero-seeded call, undefined for an explicitly undefined seed, and the record itself for the singleton unseeded call. None of the empty seeded cases or singleton unseeded case requires a reducer invocation. Seven plus three should total ten; an empty charge collection returns zero by this example’s policy.

Under Node v24.21.0, the basic calls and fee totals matched those expectations. Raw stdout is retained with the editorial material. This verifies local integer examples, not financial precision or database behavior.

Zero belongs to the sum contract

The fee function uses zero because its defined empty sum is zero and its result is numeric. If an empty list means “not loaded yet,” displaying no charge would be a separate error. Represent loading separately from a successfully retrieved empty collection before invoking aggregation.

Object rows expose the initial-type problem. In an unseeded array of fee records, the first accumulator is a record, not its fee field. Reading fee from subsequent rows does not repair that initial mismatch. An explicit seed makes the first invocation follow the same numeric-accumulator contract as later ones.

Avoid silently normalizing every supplied seed with seed || 0. That creates an additional wrapper policy, can confuse permitted falsey values, and hides whether the caller supplied an argument. Zero values and configuration defaults develops that defaulting distinction. A wrapper may define its own optional-seed behavior, but should not attribute it to native reduce.

Positive length may still offer no first value

The unseeded algorithm looks for a present property, not simply a positive length. With an ordinary prototype containing no relevant indexed properties, an array consisting entirely of holes can still fail to provide a seed. flat and missing slots covers the property-existence foundation; this is only the boundary condition for accumulator initialization.

The fee receiver rejects missing positions before reduction so that a data problem appears through its input contract. If an import permits blank rows, model or exclude them explicitly under that policy and preserve their source. Silently skipping potentially missing charges cannot establish that the remaining total is complete.

Empty input, singleton input and missing positions deserve separate expected outcomes. A successful two-item sum covers only one common path. A filter that legitimately produces zero rows should have an empty-result contract before an exception becomes an operational surprise.

Can a maximum reducer also start at zero?

Not for every domain. With inputs minus nine and minus four, the correct maximum is minus four. A zero seed introduces a larger value that was never in the input, producing zero instead. The independent snippet below introduces that new condition. Its observed zero is a demonstrated wrong answer, not a passing maximum test.

console.log([-9, -4].reduce((maximum, value) => Math.max(maximum, value), 0));
// Wrong seeded result: 0. Independent correct maximum: -4.

Choose a seed together with the allowed value domain and empty-input policy. An interface might require nonempty input, use an appropriate mathematical boundary with separate empty handling, or return an explicit empty status. This article does not provide a universal default maximum for all types.

Make the empty state distinguishable for downstream consumers rather than passing a placeholder as an observation. Before delivery, check unseeded emptiness, explicit undefined, singleton objects and an all-negative maximum independently. Derive those answers first; do not invoke the same potentially wrong reducer to manufacture the expected result.
