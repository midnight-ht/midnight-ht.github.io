Why can every pass without checking a single input?

Separate empty collections, missing slots and invalid values with five inputs and observed local callback counts.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-10 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • A true every result does not prove any item was visited.
  • Nonemptiness, complete positions and item validity need explicit contracts.
  • Every does not await an async predicate’s Promise.

A filtered array can contain no records while every returns true without calling the predicate once. If that result releases a batch submission, the missing condition comes first: whether zero records are allowed and whether every required position exists are product decisions, not facts established by an item predicate.

Imagine an import screen that requires at least one valid selection. A handler enables Continue whenever every reports true. It looks reasonable with ordinary records, then remains enabled after the user clears all selections. This is a local validation scenario, not an operating import service, and it performs no submission or persistence.

True rules out a counterexample; it does not establish existence

The ECMAScript every algorithm obtains the length, checks whether each indexed property exists, and invokes the callback only for present properties. A callback result that converts to false stops the traversal immediately. If no such result appears, every returns true. An empty array has no item callback that could fail.

“All items satisfy the condition” does not include “at least one item exists.” JavaScript has not secretly approved an empty business operation. The caller has assigned a wider responsibility to a narrower operation. A true result may be exactly right when empty input is allowed; otherwise nonemptiness must be a separate condition.

Positive length is not sufficient either. With an ordinary unmodified prototype, Array(2) has length two without two present indexed properties. Its callback may also run zero times. flat and missing slots explains the underlying property distinction. Here the question is which input set can be released, rather than how a transformation preserves coordinates.

Five inputs with independent expected answers

This script uses synthetic numbers only. Its proposed contract is deliberately narrow: a nonempty array, an own property at every index, and finite positive numbers. Requiring own properties is the example’s receiving policy. Native every uses HasProperty, which also considers inherited properties.

const valid = value => Number.isFinite(value) && value > 0;
function canSubmit(values) {
  if (!Array.isArray(values) || values.length === 0) return false;
  for (let i = 0; i < values.length; i++) {
    if (!Object.hasOwn(values, i)) return false;
  }
  return values.every(valid);
}
const inputs = [[], Array(2), [undefined], [2, 3], [2, -1]];
for (const values of inputs) {
  let calls = 0;
  const result = values.every(value => { calls++; return valid(value); });
  console.log({length: values.length, result, calls, canSubmit: canSubmit(values)});
}
// Independent expectations: raw true/true/false/true/false;
// calls 0/0/1/2/2; release false/false/false/true/false.

The expected raw results are true, true, false, true and false. Expected callback counts are zero, zero, one, two and two. The proposed release results are false, false, false, true and false. The first three inputs separate an empty collection, missing slots and an explicitly present invalid value. The final negative number is second, so two callbacks occur before failure.

Running this exact sample under Node v24.21.0 produced those results; its raw stdout is retained with the editorial material. That verifies the local numeric functions in that environment, not browser controls, server validation, authorization or storage. Since the sample sends nothing, a true canSubmit result is not a successful submission.

Filtering first changes the question

Filtering invalid values before calling every can turn “the input contains an error” into “the erroneous input no longer belongs to the set.” A positive and a negative item become one positive item, and the remaining predicate passes without explaining whether the negative should be rejected, reported or legitimately ignored. Filtering can be correct, but its responsibility must be explicit.

Likewise, filling missing positions with valid defaults does not prove the original input was complete. It may merely convert missing data into accepted business values. An import preflight may need to preserve error locations; an intentional user filter may define a new processing set that needs its own nonempty check. Those are different reasons for having fewer items.

The example’s strict receiver also has costs: it rejects inherited indices, empty arrays and anything other than the specified numbers. It is not a universal form validator. Real records require field rules and errors tied to stable record identities, rather than a bare false with no indication of what failed.

Keep the validation set stable

The specification fixes the traversal range before the first callback. Later appended items are not visited, and a property deleted before its turn can be skipped. A callback is a poor place to negotiate a growing validation set. If input can change, take an explicit snapshot for this check and confirm its identity before adopting the result.

Short-circuiting also prevents every from collecting all errors: callbacks stop after the first false. A complete error list needs a process that actually visits and reports all relevant inputs. “Does any item fail?” and “Which items failed?” should not silently share a completeness claim.

Array.fill and independent editable state addresses a further condition: whether records share objects. Passing every cannot prove that editing one record leaves another unchanged. Collection completeness, item validity and object independence need their own checks where the actual workflow requires them.

Why does every(async ...) pass despite an eventual false?

Every converts the callback’s immediate result to a boolean; it does not wait for a Promise’s eventual value. An async callback returns a Promise object, which is truthy for this conversion. Resolving it to false later does not rerun an already completed every call. Rejection also requires explicit handling rather than being treated as this boolean failure.

When validation depends on remote work, design asynchronous result collection, concurrency and error meanings first. Then make the release decision from known results. Adding async to a synchronous predicate does not establish an asynchronous validation workflow. This sample performs no remote checks: retain its five independent input expectations, then collect separate evidence for the real asynchronous path.
