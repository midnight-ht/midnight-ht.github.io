Why does deleting an author try to null tenant_id too?

Use PostgreSQL18 ON DELETE SET NULL column subsets while preserving post and tenant identities, including a same-numbered author in another tenant.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-10 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • Without a subset list, SET NULL acts on the whole referencing key.
  • Optional authors require an explicit matching policy and independent tenant protection.
  • Verify complete cross-tenant identities and keep update and authorization checks separate.

A composite foreign key’s ON DELETE SET NULL action does not automatically choose nullable columns. Without a column list, it sets the entire referencing key. If tenant_id remains part of a post’s primary key, attempting to null it can fail its nonnull requirement. PostgreSQL 18 supports ON DELETE SET NULL (author_id) to limit this action to the optional author while preserving post and tenant identity.

Suppose user identifiers are unique only within a tenant. Posts reference authors through tenant_id and author_id. The product permits deleting an author but requires posts to remain with their original tenant. Switching to cascading post deletion changes the lifecycle; making tenant_id nullable sacrifices mandatory ownership. Specify the identities that must survive before choosing the action.

Two column lists with different jobs

PostgreSQL 18’s foreign-key guide explicitly permits a SET NULL column list and otherwise applies the action to all foreign-key columns. Its tenant/user/post example preserves tenant_id by nulling only author_id. The list limits the action’s writes, not the original matching relationship.

Keep (tenant_id, author_id) referencing (tenant_id, user_id). Reducing the foreign key to user_id alone would discard tenant scope, and user_id alone is not unique in this model. Referenced columns need a qualifying primary key or uniqueness condition; this example uses the composite primary key.

Referential actions do not bypass other constraints. Resulting values must still satisfy nonnull, primary-key, and other foreign-key requirements. author_id must genuinely be optional. A separate post-to-tenant foreign key preserves tenant existence when the author is absent rather than treating a null author as permission for an arbitrary tenant number.

Specify every final row before running the delete

This complete illustrative SQL has not been executed. Use a disposable empty database you own. tenant_id is a logical ownership key and a primary-key component. No physical partitioning, row-level security, or authorization behavior is modeled. Both tenants have user number seven as a deliberate scoping control.

CREATE TABLE editorial_tenants (tenant_id integer PRIMARY KEY);
CREATE TABLE editorial_users (
  tenant_id integer NOT NULL REFERENCES editorial_tenants(tenant_id),
  user_id integer NOT NULL,
  PRIMARY KEY (tenant_id, user_id)
);
CREATE TABLE editorial_posts (
  tenant_id integer NOT NULL REFERENCES editorial_tenants(tenant_id),
  post_id integer NOT NULL,
  author_id integer,
  PRIMARY KEY (tenant_id, post_id),
  FOREIGN KEY (tenant_id, author_id)
    REFERENCES editorial_users(tenant_id, user_id)
    MATCH SIMPLE ON DELETE SET NULL (author_id)
);
INSERT INTO editorial_tenants VALUES (1), (2);
INSERT INTO editorial_users VALUES (1,7), (1,8), (2,7);
INSERT INTO editorial_posts
VALUES (1,101,7), (1,102,8), (2,201,7), (1,103,NULL);
DELETE FROM editorial_users WHERE tenant_id=1 AND user_id=7;
SELECT tenant_id,post_id,author_id
FROM editorial_posts ORDER BY tenant_id,post_id;
SELECT tenant_id,user_id FROM editorial_users ORDER BY tenant_id,user_id;
SELECT tenant_id FROM editorial_tenants ORDER BY tenant_id;

The independent ordered post oracle is (1,101,NULL), (1,102,8), (1,103,NULL), (2,201,7). Only the first post’s author changes. All four post identities remain. Users should contain (1,8) and (2,7); tenants remain one and two. These are derived expectations, not database output.

Keep both controls. Post 103 was already authorless and stays unchanged. Post 201 still references its own tenant’s user seven. Checking only that the target user disappeared or that four posts remain would miss a wrongly scoped modification. Compare the complete tuples or equivalent identity mappings.

MATCH SIMPLE is an explicit part of this contract

The CREATE TABLE foreign-key reference describes default MATCH SIMPLE: any null referencing column exempts the row from matching that foreign key. Here (tenant_id, NULL) is deliberately valid: the post belongs to a tenant but has no author. Its independent tenant foreign key still requires that tenant to exist. A complete nonnull author key must match a user in the same tenant.

MATCH FULL is not a stricter drop-in replacement for this contract. Its null exemption requires all referencing columns to be null, so nonnull tenant plus null author fails. The site’s composite-key matching article already explains that insertion rule. The new decision here is which columns a delete action changes, not a repeated insertion matrix or a reason to weaken identity constraints.

Add two rejection inputs: tenant one with nonexistent author 99 must fail the complete author reference. Nonexistent tenant 99 with a null author must still fail the separate tenant foreign key. These check distinct relationships. Neither establishes that a caller is authorized to delete a user in a tenant; service permissions need separate evidence.

Preserve two independently failing variants

In the first independent schema, remove only (author_id) after SET NULL. Keep the same structure and input. Deleting the user then attempts to null tenant_id as well and should fail its nonnull requirement. Do not diagnose this as author_id being nonnullable. In a fresh autocommit test, the failed delete statement should leave the original three users and four posts unchanged.

In the second variant, retain the subset action but select MATCH FULL. Omit the already authorless post 103 during setup so initialization itself does not fail. Prepare only the three author-linked posts, then attempt deletion. It should fail when the action produces mixed null and nonnull referencing values. If using an explicit transaction, record the error and rollback before inspecting state rather than interpreting further commands in a failed transaction as new evidence.

Neither variant was run, and no exact error wording is promised. A real migration must inspect existing constraint definitions, historical references, other triggers, and the deletion entry point. A teaching DDL is not a migration receipt. The child-side index guide covers lookup cost separately; correct referential actions do not make deletion load-free.

Can ON UPDATE use the same subset list?

No. PostgreSQL 18’s CREATE TABLE reference permits SET NULL column subsets only for ON DELETE. Updating a referenced key cannot reuse that column-list syntax under ON UPDATE. The version also does not support SET NULL for temporal foreign keys. This example is an ordinary foreign key without PERIOD and does not establish temporal behavior.

If author identifiers may change, choose a separate update policy and independent oracle: propagate the new key, prohibit the change, or explicitly reassociate through the application. An optional-author deletion policy does not automatically define a key-update policy. The design here limits deletion’s write set; actual database execution, authorization, migration, and update paths remain separate acceptance tasks.
