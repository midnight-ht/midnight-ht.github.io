Why is the SQL ratio zero after casting it to numeric?

Move conversion before integer division, then verify negative values, zero denominators, units, and bound parameter types.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-10 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • A late cast cannot recover an integer division fraction.
  • Promote an operand before division, then define units and scale.
  • Test signed inputs, zero denominators, and actual bound types separately.

Casting an integer division result to numeric cannot recover a discarded fraction. PostgreSQL 18 truncates division between integral operands toward zero. If a fractional ratio is required, convert an operand before division. A numeric result column proves that the final value was converted, not that earlier arithmetic preserved the fraction.

Suppose a report records one success in four attempts. Its intended ratio is one quarter, but (successes / attempts)::numeric produces zero. Formatting that value as 0.00 or adding more decimal places does not fix the arithmetic. Locate the loss before changing the display.

Which expression receives the cast?

PostgreSQL 18’s mathematical operator table specifies truncation toward zero and includes signed examples. The type-cast section explains conversion of an already typed value expression. This is not a new interpretation of an original fractional string.

In (1 / 4)::numeric, the parenthesized integer expression yields zero and the outer cast converts that zero. In 1::numeric / 4, division receives a numeric operand. 1 / 4::numeric also promotes an operand in this simple case. Review the expression tree rather than searching for the word numeric somewhere on the line.

Assigning the late-cast result to a numeric column does not help. Zero is a perfectly acceptable numeric value; the destination column cannot infer that the author intended a quarter. Successful calculation and storage are weaker claims than business correctness.

Specify values before probing types

This complete illustrative query has not been run. It reads no business table. NULLIF allows the zero-denominator case to remain in the comparison, but does not decide how a product should display a rate when there were no attempts.

WITH sample(a, b) AS (
  VALUES (1, 4), (-5, 2), (0, 3), (3, 0)
)
SELECT a, b,
       (a / NULLIF(b, 0))::numeric AS late_cast,
       a::numeric / NULLIF(b, 0) AS early_cast,
       pg_typeof(a / NULLIF(b, 0)) AS division_type,
       pg_typeof(a::numeric / NULLIF(b, 0)) AS promoted_type
FROM sample;

The independent oracle is: 1/4 gives zero with the late cast and 0.25 with the early cast; -5/2 gives -2 and -2.5; 0/3 gives zero through both paths. For 3/0, both expressions return NULL because NULLIF deliberately replaced the denominator. The division_type should be integer and promoted_type numeric. These are derived expectations, not captured database output.

Keep the negative case. Truncating -2.5 toward zero yields -2; rounding down in the floor sense yields -3. Positive-only samples can hide a mistaken description of the rule until refunds or reversals introduce negative values.

Run an unprotected SELECT 3 / 0; separately as a rejection probe: it should fail with division by zero. Do not describe the NULLIF branch as PostgreSQL’s automatic behavior for zero division. The conditional-expression documentation defines NULLIF as returning null when its two values are equal. The query has chosen this policy. Replacing that null with zero later would merge “not applicable” with an actual zero success rate.

Arithmetic type does not define display precision

Early conversion determines the arithmetic for this expression; it does not select the final scale. The numeric type documentation distinguishes precision from scale and describes rounding when storing into a constrained-scale column. One quarter is convenient, but one third cannot be displayed exactly with finitely many decimal digits. This example does not establish unlimited exactness for every calculation.

Specify whether the result is a ratio or a percentage before multiplying or rounding. An interface returning 0.25 and a consumer interpreting it as 0.25 percent disagree despite both using numeric. Keep raw counts, units, output type, and display policy in the acceptance record so exports do not inherit assumptions hidden in a UI formatter.

Integer division can be the intended operation, such as counting complete batches. In that case document truncation and the remainder rather than ratifying an accidental implementation. The site’s UNION type-resolution article covers a different late-conversion problem: that expression may not parse. Here calculation succeeds but loses the fraction.

A second counterexample checks whether the repair stopped at types. Suppose two groups have one success in four attempts and nine in ten. If the metric combines all attempts, its independently derived numerator is ten and denominator fourteen: the ratio is five sevenths. Averaging the two group ratios instead gives 0.575. Both paths can use early decimal conversion and still calculate different metrics. This is hand-derived arithmetic, not an executed aggregation query.

Retain numerators, denominators, and the combination rule after fixing the cast. Equal weighting of groups and equal weighting of attempts answer different business questions. Have the metric owner choose that rule before verifying the corresponding arithmetic. A valid decimal value can otherwise conceal a second calculation error after truncation has been repaired.

Why can bound parameters change a working constant query?

Binding introduces actual parameter types. A literal probe cannot establish what a driver sends. Preserve the driver version, complete SQL, and bound types; inspect pg_typeof using the same connection and binding method before comparing the numbers.

If one caller binds integers and another binds numeric values, operator selection has different inputs. Make the contract explicit instead of relying on a caller happening to send a decimal-looking value. Verify the quarter, the negative case, and the zero-denominator policy separately, then check display formatting. That separates arithmetic errors from an undecided business rule or a harmless presentation difference.
