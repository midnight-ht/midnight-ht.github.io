Why does an Index Only Scan still fetch heap rows?

Separate index coverage from snapshot visibility before changing INCLUDE columns or interpreting heap-fetch counts.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-10 · Estimated read 13 min

zh-CN en

Article

Key takeaways

  • Coverage establishes eligibility, not snapshot visibility.
  • An unset visibility-map bit can require a heap visit.
  • Compare observed plans and result sets without promising zero heap fetches.

An Index Only Scan does not promise that every candidate row avoids the heap. An index may supply all the required values while PostgreSQL still needs to establish visibility to the current MVCC snapshot. The executor consults the visibility map for the corresponding heap page and visits the heap when that map cannot establish visibility. Nonzero Heap Fetches therefore do not, by themselves, show that a covering index is broken.

Suppose an order query reads a customer identifier and an amount, with the amount already included in a covering index. Its plan says Index Only Scan, but an engineer sees heap fetches and proposes another, wider index. Ask what the extra columns would change. Supplying another value does not supply the missing visibility evidence.

Two separate requirements

PostgreSQL 18’s index-only scan documentation first requires a supporting index type and a query whose referenced columns are available from the index. B-tree supports this access method. Other index types cannot simply be assumed to preserve returnable original values. Expression and partial indexes introduce further planning conditions; this example uses ordinary B-tree columns.

Meeting those requirements makes an index-only scan physically possible. It does not settle snapshot visibility, which is not stored in index entries. The visibility map records information per heap page. A set bit lets the scan establish visibility without visiting the heap tuple; an unset bit requires a heap visit to check it. This is not a separate visibility flag for every included column.

Keep eligibility separate from the work avoided during a particular execution. The plan node identifies an access method; Heap Fetches records heap checks made by that execution. Neither is a direct count of physical disk reads. Buffer residency and actual I/O require their own observations.

Plan three captures, without promising their plans

The following illustrative SQL has not been executed. Use an isolated database you own. It creates objects and EXPLAIN ANALYZE executes the query. The optimizer is not required to choose the desired node for this small dataset.

CREATE TABLE editorial_orders (
  id integer PRIMARY KEY,
  customer_id integer,
  total numeric
);
INSERT INTO editorial_orders
SELECT n, n % 2, n::numeric FROM generate_series(1, 10000) AS n;
CREATE INDEX editorial_orders_cover
  ON editorial_orders(customer_id) INCLUDE(total);
EXPLAIN (ANALYZE, BUFFERS)
SELECT total FROM editorial_orders WHERE customer_id = 1;

-- Run VACUUM separately, outside a transaction block.
VACUUM (ANALYZE) editorial_orders;
EXPLAIN (ANALYZE, BUFFERS)
SELECT total FROM editorial_orders WHERE customer_id = 1;

UPDATE editorial_orders SET total = total + 1 WHERE id = 1;
EXPLAIN (ANALYZE, BUFFERS)
SELECT total FROM editorial_orders WHERE customer_id = 1;

Specify the data oracle before inspecting the plan: the first two queries should return the 5,000 amounts belonging to odd identifiers. The third still returns 5,000 rows, with identifier one’s amount changed from one to two. Compare multisets because the query has no ordering. The desired node name cannot substitute for a result check.

For each capture retain the server version, complete SQL, chosen nodes, Heap Fetches, buffers, collection time, and intervening modifications. If the optimizer chooses another access method, preserve that result and investigate scale, selectivity, and cost. Disabling alternatives would not prove that the optimizer naturally prefers the index.

If an Index Only Scan is selected, interpret its actual counts against the visibility mechanism. Do not predeclare zero fetches after VACUUM or a particular count after UPDATE. Here VACUUM supplies a maintenance comparison point, not a universal command for eliminating heap visits. Active transactions, concurrent changes, and page state need evidence from the actual environment. A migration tool must also keep VACUUM outside its transaction wrapper.

Decide whether the missing ingredient is a value or visibility

Change the query to return the uncovered id column and the coverage requirement changes. That is a genuine missing-value problem. It differs from a query whose values are already available but whose candidate rows still need visibility checks. Record which gap exists before proposing another index.

INCLUDE columns are payload, not search keys. The documentation warns that wide payload duplicates table data, enlarges the index, and can exceed index-tuple size limits, causing insertion failure. Frequent changes can also undermine the opportunity to avoid heap access. Review write maintenance alongside representative reads rather than treating a complete copy of the table as the goal.

The site’s EXPLAIN evidence guide covers estimates and execution costs. This question adds a narrower distinction: an available access method does not establish that each execution avoids heap checks. Comparable parameters, modifications, and result sets provide more evidence than a cropped node name.

Keep a second, explicitly different parameter range: change customer_id = 1 to customer_id IN (0, 1) on this teaching table. Its independent result oracle is 10,000 rows instead of 5,000. The optimizer may reasonably choose a different access method; preserve each plan rather than requiring matching node names. Neither parameter version was executed here.

This also catches an invalid maintenance comparison. A capture for one customer before maintenance and all customers afterward changes both table state and the requested set. Put parameters and expected results beside each capture, reject that unequal comparison, and only then interpret the counters. Plan evidence needs a reproducible query contract, not a predetermined favorite scan.

Does a zero-row scan establish visibility for the whole table?

No. With no candidate index entries, the execution has not established visibility for unrelated heap pages. Zero Heap Fetches may merely accompany an empty candidate set. It cannot demonstrate that the whole table is ready for heap-free reads.

Add a representative matching query, specify its expected rows first, and then interpret its counts. Keep the empty case as a useful control. A reviewable result states which values came from the index, which candidates required further checking, and what the query returned. It does not claim a production speedup from an unexecuted script.
