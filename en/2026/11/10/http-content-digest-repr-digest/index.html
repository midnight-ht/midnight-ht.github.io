A range contains cde. Why does Repr-Digest still cover abcdef?

Compare a single identity-coded range with the full selected representation using fixed byte oracles, retaining coding and trust boundaries.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-10 · Estimated read 18 min
Translations
zh-CN en

Article

Key takeaways

  • Content-Digest and Repr-Digest can cover different bytes.
  • Representation data includes Content-Encoding, not automatically decoded text.
  • A fragment check does not establish the whole object, metadata or authentication.

The selected representation is the six bytes abcdef, but this single-range response carries only cde. Content-Digest covers the fragment; Repr-Digest covers the full selected representation. Different values alone do not establish an error. Identify the bytes before comparing digests: sharing SHA-256 does not make the two inputs identical.

Suppose a downloader receives a 206 response with Content-Range identifying bytes 2-4/6 and exactly the three ASCII bytes cde as content. It hashes those bytes against Repr-Digest and reports an integrity failure. Fix the conditions first: no content coding, no newline, and no multipart range wrapper. Those conditions already explain how two valid digest values can differ.

Give each field its own input

RFC 9530, Digest Fields defines Content-Digest over actual message content in Section 2, and Repr-Digest over the entire selected representation data in Section 3. Published in February 2024, it obsoletes the older Digest and Want-Digest fields. A library accepting an older field has not thereby demonstrated support for these newer contracts.

For this example, the inputs are cde and abcdef respectively. Appendix B.3 likewise shows different values in a partial response. The scope differs; the SHA-256 algorithm does not. In a full response whose content is exactly the selected representation, both inputs can coincide. That special case does not require equal values for every response.

The field encoding matters too. These fields are Structured Fields dictionaries: sha-256 identifies the algorithm, and the colon-delimited Byte Sequence carries the raw digest bytes. Do not substitute a Base64 encoding of arbitrary hexadecimal text. The example creates one fixed sha-256 entry, not a general dictionary parser, algorithm negotiator or receiver policy.

Keep fixed byte identities beside independent answers

This complete Python standard-library program works locally. It sends no HTTP and starts no range server. The representation is b'abcdef' without a line ending. Python’s slice starts at index two and stops before five, yielding b'cde'. The fixed digest values were obtained beforehand using the separate Perl shasum tool, then checked with hashlib rather than generated from the function currently under test.

"""Local bytes only; no HTTP messages are sent or parsed."""
import base64
import hashlib

def field_value(data):
    raw = hashlib.sha256(data).digest()
    return 'sha-256=:' + base64.b64encode(raw).decode('ascii') + ':'

# No newline and no content coding: exactly six ASCII bytes.
representation = b'abcdef'
content = representation[2:5]  # single range bytes 2-4 inclusive
assert content == b'cde'
assert representation.hex() == '616263646566'
assert content.hex() == '636465'

# Fixed oracle values obtained beforehand with Perl shasum, not this function.
expected_full = 'sha-256=:vvV+x/U6bUC+tkCngKY5yDvCmsipgW8fxsXG3Nk8RyE=:'
expected_part = 'sha-256=:CKAYqVSSINcH4RxcT+lNjdYIJfAQ5x76qR5eeE82TXs=:'
assert field_value(representation) == expected_full
assert field_value(content) == expected_part
assert expected_part != expected_full
assert field_value(content) != expected_full  # wrong byte scope
assert field_value(b'cdX') != expected_part   # same-length mutation
assert representation[1:4] != b'cde'         # wrong offset, still length three
print('Content-Digest:', field_value(content))
print('Repr-Digest:', field_value(representation))
print('byte identities, field scopes and negative controls checked')

The independent identity oracle is hexadecimal 616263646566 with length six for the representation, and 636465 with length three for content. The fragment field starts CKAY; the full-representation field starts vvV+. Negative controls reject the full digest applied to the fragment, a same-length cdX mutation, and bcd selected from the wrong offset. Length three does not establish the correct three bytes.

Under local Python 3.11.15, the program exited zero, matched both full field values and passed those negative assertions. The script and output are archived. This verifies the stated byte inputs, SHA-256 and Base64 construction. It does not establish whether a real client exposes bytes before decoding, whether an intermediary transforms them, or whether a server emits the correct fields. Printed header-like lines are not captured network messages.

A checked fragment is still not the complete object

With only cde, a receiver can check that content’s digest but cannot recompute the digest of all six representation bytes. The teaching program can calculate Repr-Digest because it also possesses the complete representation. A real downloader needs that full selected representation, acquired or reconstructed under matching conditions, before making the corresponding comparison.

Do not instead put the fragment’s value into Repr-Digest merely to make the fields agree. That changes the object the field promises to describe. Keep the requested range, received content identity, complete representation identity and each comparison result separately, rather than collapsing them into “hash correct.”

Combining fragments also needs a version and range contract. If-Range and resumed downloads addresses mixing versions; this article does not implement another downloader. Digest comparison does not choose file-replacement timing, authorize continued access or establish that a business operation was saved.

Representation data includes content coding

RFC 9110 §8.1 models representation data as Content-Encoding applied to Content-Type data. Repr-Digest is not automatically a hash of decompressed text. For a gzip-coded selected representation, the coding’s result participates in the input. Comparing decoded text can therefore change the object under examination.

The same underlying text can also produce different coded bytes through different parameters. The digest specification’s §6.5 calls out such variation. Equal decoded text, even with the same gzip label, does not imply equal digest inputs. No compression or transparent-decoding behavior was tested here. Content-Length and coding layers explains the related length distinction; this question concerns digest scope.

A plain hash is not authentication either. RFC 9530’s security discussion excludes full protection of HTTP header and trailer fields. An attacker able to change both data and digest can replace both consistently. A match can support integrity checking for the chosen input without establishing sender identity, authorization or trustworthy metadata. Select the required trust mechanism separately.

Can a HEAD response carry both digests without content?

Yes. This changes a condition absent from the main example: the selected representation is still abcdef, while the HEAD response carries no content. RFC 9530 Appendix B.2 explicitly demonstrates Content-Digest over empty content and Repr-Digest over the complete referenced representation. Do not replace both with an empty-input digest simply because no response body was transferred.

This separate local probe sends no HEAD request. It names the new empty content without also clearing the selected representation.

"""Separate HEAD-condition calculation; no HTTP request or server."""
import base64
import hashlib

def field_value(data):
    return 'sha-256=:' + base64.b64encode(hashlib.sha256(data).digest()).decode('ascii') + ':'

# Same selected identity-coded representation, but HEAD sends no content.
content = b''
representation = b'abcdef'
assert field_value(content) == 'sha-256=:47DEQpj8HBSa+/TImW+5JCeuQeRkm5NMpJWZG3hSuFU=:'
assert field_value(representation) == 'sha-256=:vvV+x/U6bUC+tkCngKY5yDvCmsipgW8fxsXG3Nk8RyE=:'
print('HEAD Content-Digest:', field_value(content))
print('HEAD Repr-Digest:', field_value(representation))

The independent expectation is the standard empty-byte digest starting 47DE for Content-Digest, while Repr-Digest remains the full vvV+ value. Both matched in the same local environment, with exact output retained. That is not acceptance of a HEAD endpoint or server implementation. Metadata about a representation does not establish that the receiver obtained or verified the GET content.

HEAD metadata versus GET content develops that access boundary. When delivering a digest check, keep field name, algorithm, actual input bytes and execution scope together. Establish which object was checked before deciding what a successful comparison permits downstream.
