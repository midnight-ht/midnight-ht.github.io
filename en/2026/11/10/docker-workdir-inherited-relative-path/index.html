Test a Dockerfile path contract with two controlled base directories

Use two controlled base stages and four expected paths to distinguish WORKDIR inheritance, absolute anchors, and runtime -w overrides.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-10 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • A relative WORKDIR uses the preceding working directory as input.
  • Check image configuration, process directory, and copied location separately.
  • Runtime -w does not relocate files already copied during the build.

Two controlled base stages that differ only in WorkingDir can expose Dockerfile directory inheritance. Compare relative and absolute child paths against those bases. WORKDIR app does not promise /app; the inherited current directory is an input. Inspect both image configuration and the actual copied file location.

Declare four expectations first

Docker’s WorkdirRelativePath explanation says that a relative directory uses the previous working directory. Changing a base from /srv/a to /srv/b therefore moves an unchanged downstream app path. Equal Dockerfile text does not establish equal inherited inputs.

Base working directory Child WORKDIR Expected child directory
/srv/a app /srv/a/app
/srv/b app /srv/b/app
/srv/a /app /app
/srv/b /app /app

The Dockerfile WORKDIR reference applies the selected directory to subsequent RUN, CMD, ENTRYPOINT, COPY, and ADD instructions, creating it when needed. Relative WORKDIR instructions accumulate from the preceding working directory. A cd executed inside RUN instead affects that command process; it is not a persistent directory declaration for later build instructions.

Control the base rather than guessing its defaults

This complete teaching project was not built or run. It requires a Linux-container builder and Docker CLI. Save Dockerfile and marker.txt in a new owned context. No image was pulled and no container started. The illustrative base is alpine:3.20; an actual run must retain its resolved digest rather than treating a tag as immutable.

# Dockerfile.base
FROM alpine:3.20
ARG ANCHOR
WORKDIR ${ANCHOR}
CMD ["pwd"]

# Dockerfile.child
ARG BASE
FROM ${BASE}
ARG CHILD_WORKDIR
WORKDIR ${CHILD_WORKDIR}
COPY marker.txt .

Prepare marker.txt containing workdir-probe and a newline. First build the bases with docker build -f Dockerfile.base --build-arg ANCHOR=/srv/a -t workdir-probe-base-a ., then change a to b. Build the four children using Dockerfile.child with BASE selecting either base tag and CHILD_WORKDIR selecting app or /app. The first cell is docker build -f Dockerfile.child --build-arg BASE=workdir-probe-base-a --build-arg CHILD_WORKDIR=app -t workdir-probe-relative-a .; vary both declared inputs and the independent output tag for the remaining cells. Check that those local tags are unused or select a unique experiment prefix. Do not overwrite release tags.

Preserve each build’s immediate status and output. A failed cell remains failed; an old image carrying its tag is not replacement evidence. For successful builds, record the new image ID, base digest, and input hashes. Use that image ID for subsequent checks so later tag changes cannot switch the object under inspection.

Read Config.WorkingDir using docker image inspect, run the image’s default pwd with docker run --rm, then read marker through the absolute path assigned by the table. For example, relative-a should contain /srv/a/app/marker.txt; absolute-a should contain /app/marker.txt.

These observations answer different questions. Image configuration identifies a default. Pwd identifies the current process directory. Reading the absolute marker identifies where COPY placed this input. None substitutes for all three.

A correct pwd can conceal a misplaced file

The independent oracle is the four paths and exact marker bytes. A file from an older image can also make an unbound path check misleading. An absolute cat can also succeed despite an incorrect default directory because it bypasses that default.

The COPY ownership article asks which user can write a path. It does not determine the path chosen here. An absolute WORKDIR grants no permissions, removes no mount, and proves no application configuration. Those deployment conditions need their own checks.

Relative paths remain useful after an explicit anchor

WORKDIR /srv followed by WORKDIR app has a visible starting point in the stage. Docker’s check warns about relative use without a preceding absolute anchor; it does not ban every relative directory. Whether that check actually ran depends on the builder and invocation. A documented rule name is not an execution receipt.

Use an absolute path when the release needs a fixed directory. Relative composition can suit an owned parent-directory contract. Review the cumulative path and reconsider its starting point when changing FROM or stages.

Can docker run -w move files COPY already misplaced?

No. The container working-directory reference says that -w overrides the command’s default directory and creates that directory if absent. It does not rerun COPY or move existing image files. A relative image can consequently print /app while its marker remains elsewhere.

A useful negative control adds -w /app when running a relative image. Pwd can then show /app, while marker remains at that image’s original build-time location. A pwd-only acceptance check would miss this distinction. This is an unexecuted expectation derived from build-versus-run semantics.

This adds a runtime-override condition beyond relative-path inheritance. Retain startup options alongside image defaults. If an entrypoint changes directory again, inspect the application’s final directory and resolved absolute filenames. Making one pwd check green does not repair missing application inputs.

The four near-identical children can be expressed with complete parameterized base and child files. Build two bases with only ANCHOR changed, then combine BASE and CHILD_WORKDIR for four real child builds. This is still four image artifacts, not merely four computed strings. Both files and all command-line arguments belong in the input record.

Cache-hit output is neither proof of an old wrong directory nor proof of correct paths. The builder may legitimately reuse equal inputs. Inspect final configuration and marker bytes. Disabling cache merely to obtain fresh-looking output is unnecessary; preserve the original observation before any controlled comparison.

Target filenames matter too. COPY marker.txt renamed.txt would need a different absolute-file expectation from COPY into the current directory. Directory resolution, naming, and read method each participate in the contract, so changing one requires checking the original assertions again.

Acceptance for this fixture requires all four new images to meet configuration, process-directory, and marker-location expectations. They remain expectations until run. Preserve Docker/buildx versions, commands, immediate statuses, image identities, and container output. The conclusion should cover directory inheritance, not broader deployment readiness.
