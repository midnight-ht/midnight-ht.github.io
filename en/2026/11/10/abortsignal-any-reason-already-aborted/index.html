AbortSignal.any reasons: DOM rules and a Node v24.21.0 comparison

Separate the DOM reason-selection rules, a synchronous recorder and local Node subscription/read-condition observations.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-10 · Estimated read 17 min
Translations
zh-CN en

Article

Key takeaways

  • Already-aborted and future inputs have different selection conditions.
  • Retain runtime version, subscription and read timing with observed discrepancies.
  • Pushing sources after the call does not extend an existing combination.

The DOM contract selects reasons differently for already-aborted inputs and future aborts. Local Node observations also need their subscription and read timing recorded. Separate that contract from actual output before turning one result into a promise about every runtime.

Suppose a local preview accepts manual cancellation and navigation cancellation. AbortSignal.any combines the inputs, but does not create a history of causes or give the first array entry permanent priority. This article sends no requests: controllers only produce local signals, and cancellation does not establish that a server operation was undone.

Start with two timing conditions

The DOM dependent-signal creation algorithm first examines inputs in order for an already-aborted signal. It takes the first such reason and returns. When both inputs were aborted before construction, input order determines this selection; their historical abort times are not compared.

If construction finds no aborted source, it establishes dependencies. The signal abort algorithm propagates a source reason to dependents that have not yet aborted and returns when an abort is already established. The independent normative expectation is that the first future abort fixes the reason and a later one does not overwrite it. That rule comes from the contract, not from one local output.

An empty input list does not automatically abort. The result is a Signal, not a Controller with an abort method. A consumer accepting an already-aborted signal must inspect its state at entry or use the appropriate check; adding a listener afterwards does not replay the past event. State and subscription timing therefore belong to the operation’s design.

A local comparison with a synchronous recorder

The complete sample centralizes control and observation in explicit helpers; state reads occur only at their calls. It installs a synchronous abort recorder on future before aborting either source. Reasons are objects compared by identity. Every group gets new controllers rather than treating an aborted signal as resettable.

// Complete local comparison. Helper reads occur only where explicitly called.
function source() {
  const controller = new AbortController();
  return [controller.signal, reason => controller.abort(reason)];
}
const isAborted = signal => signal.aborted;
const reasonOf = signal => signal.reason;
const onAbort = (signal, callback) => signal.addEventListener('abort', callback);
const combine = signals => AbortSignal.any(signals);

const [manual, stopManual] = source(), [navigation, leave] = source();
stopManual({kind: 'manual'}); leave({kind: 'navigation'});
const prior = combine([navigation, manual]);
console.log('prior', isAborted(prior), reasonOf(prior) === reasonOf(navigation));
const [later, stopLater] = source(), [earlier, stopEarlier] = source();
const future = combine([later, earlier]), records = [];
onAbort(future, () => records.push(reasonOf(future)));
stopEarlier({kind: 'earlier'}); stopLater({kind: 'later'});
console.log('recorder', reasonOf(future) === reasonOf(earlier), records.length);
console.log('empty', isAborted(combine([])));
let lateEvents = 0;
onAbort(prior, () => lateEvents++);
console.log('late', isAborted(prior), lateEvents);

for (const mode of ['no-listener', 'listener', 'read-after-first']) {
  const [first, stopFirst] = source(), [second, stopSecond] = source();
  const combined = combine([first, second]);
  const earlyReason = {kind: 'earlier'}, lateReason = {kind: 'later'};
  if (mode === 'listener') onAbort(combined, () => {});
  stopSecond(earlyReason);
  if (mode === 'read-after-first') {
    console.log('early', isAborted(combined), reasonOf(combined) === earlyReason);
  }
  stopFirst(lateReason);
  console.log(mode, isAborted(combined), reasonOf(combined) === earlyReason,
    reasonOf(combined) === lateReason);
}

const [originalSource, stopOriginal] = source(), [added, stopAdded] = source();
const inputs = [originalSource], original = combine(inputs);
inputs.push(added);
const rebuilt = combine(inputs);
stopAdded({kind: 'added-later'});
console.log('extension', isAborted(original), isAborted(rebuilt),
  reasonOf(rebuilt) === reasonOf(added));
stopOriginal({kind: 'original-source'});
console.log('after original', reasonOf(original) === reasonOf(originalSource),
  reasonOf(rebuilt) === reasonOf(added));

Independent expectations are two true values for prior; true and one record for the recorder branch; false for the empty list; and an aborted state with zero events for the late listener. The recorded Node v24.21.0 run matched those expectations. That positive comparison includes the synchronous recorder; it does not establish that every observation pattern passed.

The original sample had neither a future listener nor a read after the first abort, and produced a different result. Its failed expectation and original bytes were retained rather than replaced by this positive example. Exit code zero only says the program completed; the individual comparisons still need checking.

How should different observations on the same Node version be recorded?

The three-branch diagnostic in the complete program creates fresh matching sources for each branch and changes only subscription or read conditions. Each branch aborts the second listed source first, then the first listed source. The final comparisons identify the earlier and later reason objects.

On the same installation, the final two reason comparisons were false/true without a listener, true/false with a listener, and true/false after an early state read. The early-read branch also reported true/true immediately after the first abort. Thus, the branch first reading state only after both aborts, without a listener, observed the later reason; the other two conditions retained the earlier one.

The listener-free observation differs from the independent DOM expectation and remains recorded as a discrepancy. It has not been relabeled as an all-pass result. It does not establish behavior for every Node version or any browser, and it does not identify an internal cause. A product depending on reason classification should retain precise code, runtime version, synchronous subscription and read timing in each supported environment.

Application-level cause labels also deserve an explicit contract. Controlled reason values can distinguish navigation from manual cancellation, while wrappers may transform errors. A local identity comparison does not prove that background work stopped or a transaction did not commit. Cancellation and stale-result ownership covers that separate application question.

Does pushing a signal later extend the original combination?

No. Web IDL sequence conversion consumes the iterable and returns an IDL sequence; the DOM algorithm then registers dependencies from those sources. This statement concerns an ordinary array modified after any returns. It does not generalize every mutation during execution of a custom iterator.

The program’s final section compares the original array with a rebuilt combination. The independent expectation after added aborts is that original remains un-aborted, while rebuilt is aborted with added’s reason. After first aborts, original takes first’s reason and rebuilt retains added’s reason. The local run matched this comparison. Modifying the input container did not subscribe the old combination to the added source; another call created a different combination.

That is not an instruction to rebuild combinations indiscriminately on every render. Consumers must know which Signal they use, its sources and who owns cleanup. Replacing an array or variable after an operation begins does not migrate the operation to a new signal. Decide whether old work continues or a new task starts.

Keep three conclusions distinct when delivering cause classification: the DOM rule, the current code’s observed runtime behavior, and the application’s chosen user message. These local comparisons do not replace browser acceptance or establish resource cleanup. readFile cancellation and handle ownership develops another API-specific boundary; unsupported claims remain outside this evidence.
