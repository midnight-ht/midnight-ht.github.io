An existing job.lock does not mean Linux flock is still held

Trace Linux local-filesystem flock through duplicate references, independent opens, last close, and child inheritance without certifying network storage.

Article

Key takeaways

  • flock belongs to an open file description, not path existence.
  • dup shares a lock; an independent open supplies contention.
  • Last close, explicit unlock, and path cleanup are different operations.

An existing job.lock does not establish that Linux flock is still held. The lock belongs to an open file description, and releasing it does not require deleting the path. After the last related descriptor closes, the file can remain while a fresh open acquires the lock. Use an independent contender to inspect contention, not a directory listing.

Separate the name, open description, and descriptor number

The Linux flock manual associates the lock with an open file description. A process’s small integer fd refers to that description. dup returns another number referring to the same description and lock; related descriptors inherited through fork share it too.

If fd1 holds a lock and fd2 is its duplicate, closing fd1 is not the last close. An independently opened fd3 can still be rejected, even within the same process. Retesting through a duplicate does not create an independent competitor.

The file-watching article explains how a name can point to a replacement inode. flock adds another lifetime: the open description and its references. A path-existence check cannot distinguish never locked, currently held, and already released. It cannot decide whether another job may proceed.

A descriptor comparison in an owned Linux directory

This complete teaching program is unexecuted and targets Linux local-filesystem flock semantics. The current host is macOS; running it there would not certify Linux behavior. Save lock_probe.py and use the proposed python3 lock_probe.py in a prepared Linux environment. Do not substitute a production lock path.

import fcntl
import os
import sys
import tempfile
from pathlib import Path

if not sys.platform.startswith("linux"):
    raise SystemExit("this fixture requires Linux")

with tempfile.TemporaryDirectory(prefix="flock-probe-") as directory:
    path = Path(directory) / "job.lock"
    descriptors = []
    exclusive = fcntl.LOCK_EX | fcntl.LOCK_NB
    try:
        first = os.open(path, os.O_CREAT | os.O_RDWR, 0o600)
        descriptors.append(first)
        fcntl.flock(first, exclusive)
        duplicate = os.dup(first)
        descriptors.append(duplicate)
        contender = os.open(path, os.O_RDWR)
        descriptors.append(contender)

        def expect_blocked():
            try:
                fcntl.flock(contender, exclusive)
            except BlockingIOError:
                return
            raise AssertionError("independent open unexpectedly acquired lock")

        expect_blocked()
        os.close(first)
        descriptors.remove(first)
        expect_blocked()
        os.close(duplicate)
        descriptors.remove(duplicate)
        fcntl.flock(contender, exclusive)
        assert path.exists()
        print("acquired after last related close; path remains")
    finally:
        for descriptor in descriptors:
            os.close(descriptor)

The independent exclusion contract supplies the oracle: the contender must fail initially, still fail after first closes, then acquire after duplicate closes. The path must still exist. All observations belong to one run. The final message would establish these conditions, not concurrency safety for a real scheduled job.

Only BlockingIOError is accepted as expected contention. Permission failures, invalid descriptors, and unsupported filesystems must remain failures. Nonblocking acquisition avoids an indefinite demonstration wait; it does not choose whether a real job should skip, queue, or fail.

Deletion is not an unlock protocol

Release follows an explicit LOCK_UN on a related descriptor or closing every related reference. Unlinking the path is not one of those conditions. An object-identity inference follows: a holder can retain the old opened object while another participant recreates the same path and opens a different object. They then no longer contend on the same file. Equal path text does not transfer the old lock.

Use a stable shared object and keep the holding descriptor around the whole protected action. Removing this fixture’s owned temporary directory is cleanup, not a production algorithm of repeatedly deleting and recreating lock files. Reclaiming a shared path requires an explicit participant-lifecycle arrangement.

LOCK_UN also differs from closing one reference: any descriptor sharing the lock can release it even while another duplicate remains open. A library given such a descriptor can therefore affect the protection. Track authority to unlock as well as resource cleanup. The fixture deliberately tests last-close release instead.

Can a background child keep the lock after its parent exits?

Yes, if it retains a related open-description reference. Parent exit closes the parent’s descriptors, not every child reference inherited through fork. A disappeared parent PID does not establish last-close release. This is a new process-lifetime condition beyond the single-process dup example.

Across exec, FD_CLOEXEC or O_CLOEXEC matters. The open reference documents close-on-exec flags, and language runtimes may set descriptors non-inheritable. Neither “every background child retains it” nor “every exec releases it” is adequate. Record creation and inheritance settings, then use an independent contender.

The protected action has its own completion boundary. A parent can acquire the lock, launch a writer child, close its references, and exit without waiting. Another contender may legitimately acquire while the first writer still runs. The lock has not violated its lifetime rule; the application held it for too little of the action. Wait for completion or explicitly assign ownership and close responsibility to the actual executor.

The opposite failure is accidental inheritance after protection is no longer needed, delaying later work. Inspect the process and descriptor relationship rather than deleting the path. PID, object identity, open origin, and close time can explain the lifetime without exposing protected contents. Insufficient visibility remains unknown.

Test explicit LOCK_UN separately from last close. Keep a duplicate open, release through one shared descriptor, then try the independent contender. That adds the state “references remain but protection was explicitly removed.” Neither path can be inferred from file existence or certified by the other test.

Finally, local Linux flock is generally advisory: a writer not participating in the protocol can ignore it. The manual documents different NFS, SMB, and historical-kernel behavior, including SMB conditions that change advisory semantics. Preserve kernel, Python, mount type, script hash, stdout, and immediate exit status. A local result does not certify remote shared storage. Establish a common object before relying on the lock’s lifetime to cover the action.
