Fix a make cd by choosing the scope of shared shell state

Compare local cd && with file-wide .ONESHELL through isolated Makefiles, failure propagation, and interpreter-prefix conditions.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-10 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • A local cd && and file-wide .ONESHELL change different scopes.
  • A single shell requires a fresh intermediate-failure review.
  • Check the working directory, output location, and immediate status together.

A single recipe line containing cd out && command shares a working directory for those actions. .ONESHELL changes recipe execution across the Makefile. The local repair needs a local explanation; the broader change also requires a fresh review of intermediate failures. A report finally appearing under out does not finish that review.

Locate the output before choosing the scope

In an ordinary GNU Make recipe, each logical line runs in a new subshell. Changing directory affects that process, not the shell started for the next line. The official Recipe Execution section documents this boundary and shows cd && command on one logical line. The source checked here is the GNU Make 4.4.1 manual. A logical line is not necessarily one visual line in an editor.

Suppose the contract requires out/seen.txt and forbids seen.txt at the recipe’s starting directory. Two separate lines can both succeed while writing the file at that starting directory. Making cd’s argument absolute does not preserve its process-local state. The relationship between the actions needs changing.

For two actions, one logical line is usually easy to review. && expresses that generation requires successful entry. A semicolon merely sequences commands and can continue after cd fails. With output redirection, a file in the wrong directory may be truncated before the intended generator even runs. Include both location and stopping behavior in the contract.

Keep three complete Makefiles separate

The following teaching comparison is unexecuted. It requires GNU Make with support for the single-shell feature and a POSIX-style shell. The local command available here reports GNU Make 3.81; it cannot certify this feature. Create three independent new directories, each initially containing its own out directory and one Makefile. Recipe indentation must be tabs. Do not put these alternatives in one file and pretend the declaration is local to one target.

The deliberately incorrect ordinary version is:

.PHONY: bad-probe
bad-probe:
    cd out
    pwd > seen.txt

The local repair is:

.PHONY: local-probe
local-probe:
    cd out && pwd > seen.txt

The single-shell version also contains two failure controls:

.ONESHELL:
.PHONY: single-probe masked guarded
single-probe:
    cd out || exit 1
    pwd > seen.txt
masked:
    false
    printf 'continued\n'
guarded:
    false || exit $$?
    printf 'unreachable\n'

Run make bad-probe, make local-probe, or make single-probe independently, save its exit status immediately, then inspect both candidate file locations. The oracle comes from the path contract: the ordinary version exposes a file at the starting directory; the repairs should create only out/seen.txt, whose content should identify this run’s absolute out directory. A zero status alone cannot distinguish them.

Use fresh copies without out for the repaired variants. Neither location may acquire seen.txt, and make must return nonzero. Existing output from an earlier run would invalidate that observation. This checks directory-entry failure, not report correctness, parallel safety, or atomic publication. A semicolon version that creates a file in the starting directory violates the contract even if its final command succeeds.

Sharing a shell changes failure visibility

Using One Shell says that declaring the special target anywhere supplies each target’s recipe lines to one shell invocation, preserving newlines. Other targets and included rules therefore enter the review scope.

The same section warns that make may not notice a non-final command’s failure. The masked target deliberately follows false with a successful printf; guarded explicitly returns the failure. Invoke them separately and preserve their immediate statuses. Seeing false in echoed text is not evidence that make rejected the target. These are documented expectations, not captured local results.

Adding -e to shell options is another possible design, but it changes existing behavior and needs review of actual conditions, pipelines, and interpreters. Explicit failure propagation is easier to explain in this small fixture. Do not turn one simple example into a universal shell-error policy.

The failure-deletion article concerns partial targets; the order-only directory article concerns timestamp invalidation. Here the earlier question is execution context. Correct dependencies do not prevent writing in the wrong directory, and a correct directory does not establish correct failure reporting.

Why do internal @ prefixes depend on the interpreter?

This adds an interpreter condition rather than repeating the directory lesson. Under the single-shell mode, ordinary special-prefix processing applies to the first line. For a recognized POSIX-style shell, make also removes those prefix characters from internal lines. With another interpreter, internal characters can remain program text. Copying a shell recipe’s per-line @ into Perl can therefore change syntax rather than merely suppress echoing.

Fix another experimental input before running: action targets must not collide with same-named real files. Each Makefile declares its own phony target and is invoked by that name. Switching rule versions over one directory mixes old seen.txt state into the comparison. Retain each initial directory, rule, and command together.

A file-wide change also includes the actual include chain. One visible probe does not establish that no imported recipe depends on separate failure handling or another interpreter. List the files read and their shell settings before deciding that a global change is local in effect. This scope review needs no unmeasured performance claim.

Keep failing observations as well as repaired results. A file found in the missing-directory test might be an old artifact rather than a new write. Associate its current-run identity with the immediate exit result before diagnosing independent shells, stale setup, or a swallowed failure.

Retain the actual SHELL, options, file hash, exit results, and output locations. Share only the context the actions require. Choose a file-wide single-shell arrangement only after reviewing its failure and prefix behavior for the other recipes too.
