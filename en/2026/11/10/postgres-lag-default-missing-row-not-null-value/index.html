Why can lag(value, 1, 0) still return NULL?

Compare missing predecessors, existing null readings, and COALESCE placement while keeping predecessor identity and every original row.

Article

Key takeaways

  • lag uses its default only when the offset row is absent.
  • COALESCE placement determines which null states are collapsed.
  • Keep predecessor identity and original row counts alongside values.

lag(value, 1, 0) returns zero when the requested preceding row does not exist in the partition. If that row exists and its value is NULL, lag still returns NULL. The third argument handles an absent row; it does not replace every null result. Choose the intended null contract before adding a default.

A report may preserve every device reading and attach the preceding value. Its first reading has no predecessor, while another reading follows a recorded acquisition failure with a null value. Displaying both as zero can hide a useful distinction. Conversely, a developer who intended only an initial value may be surprised by later blank cells.

Establish identity before filling values

PostgreSQL 18’s window function table defines lag by an offset within the partition, using default only when no such row exists. Both offset and default are evaluated for the current row. It is not an instruction to search backward for a record satisfying another business condition.

Specify the partition and window ordering first. Devices must not borrow predecessors from one another. Tied timestamps need an explicit rule if predecessor identity must be stable. This example uses a unique id as its agreed teaching order, not as a universal claim that database identifiers represent acquisition time.

The site’s last_value and window-frame article already discusses null skipping and filtering risks. Here the selected row remains fixed. The question is where a value is replaced, not how to find the latest valid record.

Four rows and three contracts

This complete SQL example has not been executed. Device A has values ten, null, and thirty; device B has one null reading. Preserve all four input rows in the output.

WITH r(g, id, v) AS (
  VALUES ('A', 1, 10),
         ('A', 2, NULL::integer),
         ('A', 3, 30),
         ('B', 4, NULL::integer)
)
SELECT g, id, v,
       lag(id) OVER w AS prev_id,
       lag(v, 1, 0) OVER w AS boundary_default,
       lag(coalesce(v, 0)) OVER w AS input_fill,
       coalesce(lag(v) OVER w, 0) AS result_fill
FROM r
WINDOW w AS (PARTITION BY g ORDER BY id)
ORDER BY g, id;

In displayed order, the independent expected vectors are:

Column A1 A2 A3 B4
prev_id NULL 1 2 NULL
boundary_default 0 10 NULL 0
input_fill NULL 10 0 NULL
result_fill 0 10 0 0

Write these expectations before running the query. A3 has predecessor A2, so the boundary default is not triggered; the predecessor’s value is null. A1 and B4 have no predecessor and receive the explicit zero default. A2’s ordinary predecessor value of ten is a necessary positive control.

The COALESCE documentation defines the first nonnull argument as its result. Inside lag, it replaces null values in existing input rows before selection. Without a predecessor, lag’s own default remains null. Outside lag, it replaces the result after selection and therefore merges both kinds of null.

Equal numbers can conceal different decisions

Adding the boundary default to the inner expression, lag(coalesce(v, 0), 1, 0), yields the same numbers as outer COALESCE for this fixed-zero contract. That does not establish equivalence for arbitrary defaults or expressions. It shows that these particular choices collapse the same states in this example. Recheck the contract when the default becomes another column or provenance must be preserved.

Use a boundary default when the first row needs an initial zero but an existing failed reading should stay null. Use outer COALESCE when every null output is deliberately displayed as zero. Use inner COALESCE when existing null inputs mean zero but an absent predecessor remains unknown. These are semantic decisions, not three interchangeable optimizations.

The example also returns prev_id because a value alone cannot reveal its origin. With unique, nonnull input identifiers, a null prev_id indicates no predecessor; a nonnull prev_id can accompany a null predecessor value. If identifiers themselves may be null, that inference is invalid. Carry an explicit existence indicator instead.

Verify row counts as well as numbers. Filtering null readings before lag changes the predecessor relation; filling values afterward preserves identities. Even if a UI hides some rows, review window input selection separately from final display filtering. Reordering the VALUES text should not change an explicitly ordered predecessor relation. The outer ORDER BY controls presentation, not window selection.

Add an identity negative control in a separate variant: change only A2 from null to ten, so A1 and A2 share the value ten. A3’s correct predecessor is still id 2. An incorrect association selecting id 1 would return the same number. A value-only assertion would pass; checking prev_id would detect the wrong record. Retain the original null example as well rather than replacing it with this variant.

When an interface also returns a predecessor timestamp or status, verify that those fields belong to the same predecessor identity. A value from id 2 and a timestamp from id 1 do not form a correct record merely because the values match. This unexecuted check concerns row identity, not searching for a different valid reading.

Does a default expression read a column from the preceding row?

No. The documented evaluation context is the current row. Add a different seed column on each row and use lag(v, 1, seed). At a partition’s first row, the fallback is that current row’s seed, not the seed of a nonexistent predecessor. Rows with an existing predecessor still read its v, including null.

Give A’s first row seed 100 and B’s first row seed 400. The independent expectation is 100 and 400 at those partition starts; A3 remains null. This additional probe has not been run either. Keep absent, existing-null, and ordinary predecessors distinct in both the acceptance record and the interface meaning.
