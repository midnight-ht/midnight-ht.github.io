HTML showPicker: why can a previous click still lead to NotAllowedError?

Classify activation, mutability and origin errors with a form-free teaching page that separates preparation, invocation and a chosen date.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-05 · Estimated read 17 min
Translations
zh-CN en

Article

Key takeaways

  • Invocation needs transient activation, not merely a historical click.
  • A fresh selection action can follow preparation; await alone does not prove failure.
  • Normal return establishes neither a chosen date nor business acceptance.

showPicker needs transient activation when it is called. An earlier click does not guarantee that activation survives an asynchronous prerequisite. Classify the exception before inspecting expiration or consumption. An await alone does not prove failure, and historical interaction does not guarantee success.

The HTML showPicker method requires transient activation at invocation and throws NotAllowedError without it. Mutability and origin restrictions have separate checks. Reporting every exception as an unsupported date picker hides conditions an implementation can address.

Previous interaction is not current authorization

The user activation guide distinguishes sticky from transient activation. Transient activation expires and can be consumed by some protected APIs. hasBeenActive describes prior activation; isActive describes current transient activation. They are not interchangeable.

Suppose a Choose delivery date button first fetches available dates, then calls showPicker. A quick response may leave the condition satisfied; a slower one may not. Another protected operation can affect it too. Neither “await always breaks it” nor “it worked once, so network latency is irrelevant” follows. This article measures no timeout window and supplies no universal duration.

Observing isActive does not preserve or grant activation. More asynchronous work after that observation can change the condition before invocation. Keep diagnostic observations close to the call and record browser, input type and preceding protected operations. A screenshot proving an earlier click cannot reconstruct those conditions.

Give selection a fresh action after necessary preparation

If asynchronous preparation is a genuine prerequisite, complete it first and enable a separate selection action. Clicking Choose date then calls the method immediately. Waiting and choosing become separate activities, and preparation failure has a clear recovery point. This is a design option, not a requirement for two buttons on every date field.

This complete teaching file has not been executed. Preparation awaits only an already-resolved local Promise and fetches no remote rules. There is no form and therefore no form default-submission path. The native input remains available; the picker button enhances it without implementing reservation, saving or authorization.

<!doctype html>
<html lang="en">
<meta charset="utf-8">
<title>Teaching date selection</title>
<label for="date">Teaching date</label>
<input id="date" type="date">
<button id="prepare" type="button">Prepare selection</button>
<button id="choose" type="button" disabled>Choose date</button>
<p id="message" role="status">The native date input can be edited directly.</p>
<p id="value"></p>
<script>
const find = id => document.getElementById(id);
const say = (node, content) => { node.textContent = content; };
const on = (node, event, handler) => node.addEventListener(event, handler);
const enable = (node, yes) => { node.disabled = !yes; };
const date = find('date');
const prepare = find('prepare');
const choose = find('choose');
const message = find('message');
const value = find('value');
on(prepare, 'click', async () => {
  enable(choose, false);
  enable(prepare, false);
  try {
    await Promise.resolve(); // local teaching preparation only
    enable(choose, true);
    say(message, 'Local preparation complete, click Choose date again');
  } finally {
    enable(prepare, true);
  }
});
on(choose, 'click', () => {
  if (typeof date.showPicker !== 'function') {
    say(message, 'Method unavailable, edit the native input directly');
    return;
  }
  try {
    date.showPicker();
    say(message, 'Picker invocation returned, check the current date value');
  } catch (error) {
    say(message, `Invocation failed: ${error.name}, Direct editing remains available`);
  }
});
on(date, 'change', () => {
  const current = date.value;
  say(value, current ? `Current date: ${current}` : 'No current date');
});
</script>
</html>

This preparation has no real failure source and is not a remote-rule failure demonstration. A real service needs failure feedback and a selection action that stays unavailable until its prerequisite is met. Whether users may edit the native field beforehand, and whether an existing date needs checking against newly fetched rules, are product decisions.

An editable date is also not a confirmed available date. A delivery service may recheck capacity or permissions when submitting. This page only displays the value and sends it nowhere; opening a picker is not evidence of a reservation.

Separate the exception categories

NotAllowedError identifies missing transient activation. InvalidStateError identifies a nonmutable element. Inspect the actual target state rather than changing network waits. After component rerendering, a stored reference may not identify the visible input; confirm identity and attributes.

SecurityError concerns cross-origin iframe restrictions. Historical origin-check exceptions cover file and color inputs, not dates. Those exceptions do not remove activation or mutability requirements. Record the top-level origin and the input document's origin in embedded products.

Method existence also does not prove an applicable picker for every input on every platform. If no applicable picker is supported, the algorithm can finish without displaying one. Feature detection establishes interface availability, not actual UI or a chosen value. A caught exception must not be converted into a fabricated selection-success state.

Why does no exception not mean a date was chosen?

The method reference returns undefined, not a Promise waiting for a date. Normal return does not establish that users accepted a value. They may cancel or retain an existing date. The example observes field changes rather than reporting completion after awaiting the method.

Do not make two sequential picker invocations the default interpretation of one click. The standard's display algorithm consumes activation, so the second invocation may lack the required condition. An explicit action for each choice is easier to understand and verify than automatically chaining protected interfaces.

Suggestions and membership validation distinguishes visible options from accepted answers. Native pickers likewise establish no server acceptance. Button types separates auxiliary actions from submission; this example avoids forms entirely.

Proposed checks cover direct editing, selection after preparation, script invocation without activation, nonmutable controls, actual embedding origins, and values after choice or cancellation. Retain real exceptions and browser versions rather than prefilled pass results. Invocation eligibility, displayed UI, a user answer and business acceptance are separate questions; one exception-free return cannot resolve them all.

Does preparation validate the existing date?

Suppose a user entered Friday, then loaded rules allowing only next week. Preparation means rules arrived; it does not authorize silently replacing Friday with an arbitrary suggested date. Preserve the answer and explain the need to choose again, or ask for explicit confirmation.

Now suppose the delivery address changed during preparation. A late result for the previous address must not enable the current selection merely because the button node survived. Associate real results with their address or record version. This is business-state reasoning; the teaching sample fetches no remote results and implements no version comparison.

The second button offers a fresh activation opportunity, not frozen business conditions. Result ownership and date validity remain separate checks. Vary invocation timing and business identity independently so a visible picker cannot hide stale preparation data.
