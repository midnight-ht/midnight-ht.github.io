When a file named clean suppresses a GNU Make task: use .PHONY for the action

Separate GNU Make action targets from real outputs with a clean-name collision sandbox, dependency-direction checks, and literal declarations.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-05 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • Separate action identity from same-named filesystem objects.
  • Keep real generated files tied to their input-update rules.
  • Phoniness is not inherited, while ordinary prerequisite direction affects rebuilding.

GNU Make treats an ordinary target name as a file whose update status matters. If clean names an action but a same-named file or directory already exists, a rule with no prerequisites can be skipped as current. Declaring that action phony separates the task from the filesystem object. It does not complete cleanup for the command or justify making every generated file phony.

Skipped execution is different from command failure

The GNU Make Phony Targets manual uses clean to explain the collision. A recipe that does not produce a file with that name normally runs when requested, but an existing same-named object can make an ordinary no-prerequisite target appear current. The declaration removes that object's update status from the action's identity.

Suppose a team uses make clean for teaching-build outputs, then creates a directory named clean to hold reference material. The task reports no error, yet old outputs remain. The decision may have happened before rm was invoked: make considered the target satisfied. Rechecking removal arguments misses the earlier decision about whether to enter the recipe.

This differs from a real generated file left partially written after failure. That problem accepts the target's file identity and needs a failure policy for invalid contents. Here clean was never meant to represent a file's timestamp. Restore the action's identity rather than deleting an unrelated directory or forcing every report to rebuild.

A complete disposable collision example

These unexecuted inputs require GNU Make, a conventional shell, and a newly created disposable directory. Removal is limited to this sandbox's build/demo-output. The recipes are identical; only the action declaration differs. Preserve literal tabs in recipe indentation when copying.

phony_demo_dir=$(mktemp -d)
cd "$phony_demo_dir" || exit 1
mkdir clean build
printf 'old output\n' > build/demo-output
cat > Ordinary <<'MAKE'
clean:
    rm -f build/demo-output
    printf 'cleanup action entered\n'
MAKE
cat > Declared <<'MAKE'
.PHONY: clean
clean:
    rm -f build/demo-output
    printf 'cleanup action entered\n'
MAKE

Both invocations below explicitly request clean, avoiding ambiguity about default targets. The first starts with the directory and old output present. The second leaves the clean directory in place, recreates the teaching output, and selects the other rule file. These are proposed inputs and observations, not captured terminal results.

make -f Ordinary clean
phony_exit=$?
printf 'ordinary-status=%s\n' "$phony_exit"
ls -ld clean
ls -l build
printf 'old output\n' > build/demo-output
make -f Declared clean
phony_exit=$?
printf 'declared-status=%s\n' "$phony_exit"
ls -ld clean
ls -l build

The ordinary case is expected to emit no action marker and leave the old output. The declared case should enter the recipe, emit the marker, remove the designated output, and leave the clean directory intact. A successful make exit alone does not distinguish successful cleanup from skipped execution. Inspect the marker and resulting filesystem state together.

If the declared case enters the recipe but removal fails on permissions, that is a separate branch. The declaration does not bypass permissions or turn failure into success. Preserve exit status, original errors, and the designated file's existence. A printed marker cannot replace the removal result, and removing this single teaching file cannot establish complete project cleanup.

Extend the comparison with three initial conditions: no same-named object, a same-named regular file, and a same-named directory. Use a fresh sandbox for each variant while keeping the rule unchanged. That helps distinguish an actual collision from the wrong working directory, wrong rule file, or another target definition. None of these commands was executed for this article.

Keep real outputs as file targets

Choose by what the recipe delivers. clean and check usually express requested actions. A report target representing an actual generated file should state its real inputs and retain make's update decision. Skipping an existing file with no newer prerequisites is useful behavior for that contract.

Declaring the report itself phony changes that contract. If the requirement is to validate an existing report on demand, introduce a separate check action that reads it. Generating the report when needed and checking it now are different decisions; they need not share one target identity.

The October 25, 2026 reproducibility-scope article asks whether controlled inputs reproduce identical bytes. This question comes earlier: should a request enter an action or generation rule? Unchanged output bytes cannot establish that skipped execution was the intended behavior.

Does a phony all goal make every prerequisite rebuild?

No. The manual explicitly states that phoniness is not inherited. A phony all entry can depend on a real report file. Requesting all causes make to consider that report, while the report still uses its own inputs and filesystem state to decide whether it needs updating. Entering an aggregate goal and rebuilding every artifact are separate decisions.

Reverse the dependency and the effect changes. A phony action used as an ordinary prerequisite of a real file is processed when that file is considered. With that prerequisite succeeding and other conditions permitting, the real file needs rebuilding because the prerequisite is always treated as needing an update. That is an update relationship, not inherited phoniness. If the prerequisite fails, the dependent recipe has not completed normally.

Read the arrow carefully. An action depending on real files can preserve their incremental behavior. A real file ordinarily depending on an always-updated action changes when that file rebuilds. Convenient naming is not sufficient reason to attach a preparation action to every output and then call repeated work unpredictable.

Does a percent sign in the declaration match a pattern?

No. The manual says the special target's prerequisites are literal names, even when they contain a percent sign. A wildcard-looking entry does not establish that all corresponding object-file rules became phony. Declare the intended action names. If a pattern rule truly needs forced rebuilding, consult that separate mechanism rather than treating this declaration as a wildcard.

For verification, record GNU Make version, working directory, selected rule file, and requested goal, followed by action marker, exit status, and output changes. For the all relationship, run twice with unchanged real inputs, then change one real prerequisite and inspect which generation rule enters. Collision handling, dependency direction, and command outcomes each need their own evidence. That distinguishes an identity repair from a task that merely happened to run after a directory was emptied.
