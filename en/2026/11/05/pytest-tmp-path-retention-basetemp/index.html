pytest reruns erased the evidence: check --basetemp first

Separate pytest scratch-directory lifetime from retained failure artifacts, including basetemp clearing and concurrent-run identities.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-05 · Estimated read 14 min
Translations

Article

Key takeaways

  • Default retention and explicit-base clearing are different branches.
  • Transfer evidence to independent artifact storage before rerunning.
  • Concurrent runs and sensitive diagnostics need explicit ownership.

A pytest temporary directory is not a durable artifact store. An explicit --basetemp is cleared before each run, so failure evidence needs a separate destination before the next invocation. The default three-run retention is configurable debugging convenience, rather than a CI artifact-retention promise.

Test isolation and evidence retention have different owners

The pytest temporary-directory guide describes tmp_path as a directory unique to each test function, represented by pathlib.Path. tmp_path_factory is a session-scoped directory factory. Those facilities determine where tests write; they do not promise that an investigator can download the files next week. The online guide was checked on November 5, 2026. No test or CI job below was executed.

Consider a hypothetical JSON-to-report converter. A failed test needs its input, actual output, and a difference note for diagnosis. The next invocation needs clean scratch space, while the investigator needs the previous invocation's contents. Calling both locations “the output directory” leaves cleanup and preservation competing over the same files. Assign separate owners before choosing an upload mechanism.

By default, pytest numbers invocation directories and retains the last three. Retention count and policy are configurable, so three is a documented default rather than an observation about every project. Executor lifetime is another constraint: files on an ephemeral CI machine may disappear with that machine regardless of pytest's retention settings.

Hand off a small diagnostic package

This complete, unexecuted teaching test writes all three files inside its own tmp_path. The deliberately wrong expected result creates a diagnostic failure; this is not a converter implementation or an observed product defect.

import json

def test_export(tmp_path):
    source = {"title": "campus", "rows": 2}
    (tmp_path / "input.json").write_text(
        json.dumps(source), encoding="utf-8"
    )
    actual = "campus:2\n"
    (tmp_path / "actual.txt").write_text(actual, encoding="utf-8")
    expected = "campus:3\n"  # teaching failure
    (tmp_path / "difference.txt").write_text(
        f"expected={expected!r}; actual={actual!r}", encoding="utf-8"
    )
    assert actual == expected

The test leaves inspectable files before its assertion fails, but it does not upload them. A candidate CI arrangement gives each invocation a distinct run identity and dedicated scratch base. A collection step that also runs after test failure copies selected diagnostics into an independently owned artifacts directory for that run. The upload then targets that destination. Preserve the test's nonzero result; arranging collection must not silently turn failure into success.

Preserve test identity within the package. One test's actual.txt must not overwrite another's identically named file. Retain relative test directories or another unambiguous mapping. Check the collected manifest and digests, then associate them with the source revision, command, and run identity. An upload response alone is weaker than an authorized download that confirms the intended contents can actually be retrieved.

If the process crashes before writing every file, collection should tolerate missing files and label them as missing. Do not manufacture an empty difference note to make packaging pass and present it as evidence produced by the failed run. For sensitive inputs, decide which fields can enter the package before copying; a prepared minimal reproduction may be more appropriate than the original input.

An explicit base directory has no invocation history

The guide warns that an explicit basetemp is cleared before each run and has no multi-run retention feature. Use a dedicated disposable directory. A project root, shared export destination, or sole copy of failure evidence is an unsuitable base. A directory name containing “temp” establishes nothing about the value of its contents.

This changes the order of recovery actions. Immediately rerunning the same command can delete the previous evidence before any new test begins. Collect first, or have the job system transfer evidence to independent storage. Increasing default retention does not override the explicit basetemp clearing contract.

Default directories suit short local investigations. A dedicated explicit base can simplify CI collection, provided another owner handles preservation across steps and runs. Reusable caches need their own lifecycle; tests should not depend on scratch files surviving by accident.

Can two independent invocations share a base?

Use unique bases for concurrent invocations. Otherwise one invocation may clear files another is still using. The official guide explicitly discusses configuring a unique base for concurrent runs. That is different from pytest-xdist coordinating subprocess directories inside one invocation: organizing one run does not authorize unrelated jobs to share its scratch area.

Carry run identity into collection and upload names as well. Different local paths do not prove that the remote service assigns distinct artifact identities. Check its naming and access rules rather than having concurrent jobs publish over the same “latest” package.

Does saving only failures make their contents safe?

No. Failure-only collection is a selection policy, not a sensitivity classification. Define the files and fields required for diagnosis, authorized readers, download permissions, and expiry. Exceptions can contain credentials even when input JSON has been filtered. Review the diagnostic writer as well as the source fixture.

Retention must also fit investigation timing. If failures are normally reviewed several days later, a one-day artifact lifetime may fail the actual purpose despite a successful upload. Conversely, that does not justify keeping every input indefinitely. Establish expiry, exceptional extensions, and cleanup ownership, then verify expiry behavior.

A proposed sandbox check first confirms the base is disposable, places a sentinel there, and compares two invocations with the independent artifact copy. Cover ordinary failure, early exit, and concurrent runs. Record source and pytest versions, directory identities, and retrievable contents. No such checks were executed here.

The October 11 fixture-isolation article deals with shared mutable state. This question concerns who owns evidence after a run ends. Give clean test space and retrievable diagnostic artifacts separate locations before a rerun becomes an evidence-deletion operation.
