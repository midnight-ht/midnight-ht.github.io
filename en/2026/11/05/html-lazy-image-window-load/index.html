Why can lazy images remain unloaded after window load?

Separate window load from lazy-image success and track thumbnail and preview lifecycles explicitly.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-05 · Estimated read 16 min
Translations
zh-CN en

Article

Key takeaways

  • Lazy images do not delay window load.
  • A broken image can have complete true.
  • Verify per-image state together with resource identity.

Lazy images do not delay window load, even when initially in view. An operation that needs one image should check that image rather than the document-wide event. Enabling every gallery editor after load mistakes a page event for proof that each image succeeded.

The MDN img reference distinguishes eager and lazy loading. Browsers defer lazy images according to distance from the viewport, and those images do not participate in window load completion. The documentation does not establish one prefetch distance for every browser or a measured performance improvement for a project.

Different scopes of readiness

Imagine a teaching gallery with twenty covers and a user interested in the fifteenth. The document, header and form can be usable before that distant cover is requested. The page need not block on every distant image, but an action using one image must know its result.

Identify the resource required by the next operation. Reading text does not require a distant cover. Showing an image needs that resource; pixel editing, cross-origin reading or exporting introduces further decoding, access and canvas conditions. The teaching example below only displays a preview. It implements no pixel editor or export.

Network idle and business readiness discusses the general scope mismatch. Here the specific mechanism is lazy images being excluded from load. Replacing load with another global event does not automatically create an all-images-ready condition.

Track each image independently

This complete teaching page has not been executed. The runner must supply the image files; they are not included or asserted to exist. A button becomes available after its own thumbnail receives load, then copies its selected URL into an ordinary preview region. It connects to no gallery service or saving system.

<!doctype html>
<html lang="en">
<meta charset="utf-8">
<title>Independent lazy-image states</title>
<div id="gallery"></div>
<p id="message" role="status"></p>
<div id="preview"></div>
<script>
const find = selector => document.querySelector(selector);
const text = (node, value) => { node.textContent = value; };
const gallery = find('#gallery');
const message = find('#message');
const preview = find('#preview');
const make = tag => document.createElement(tag);
const available = (button, yes) => { button.disabled = !yes; };
const on = (element, event, handler) => element.addEventListener(event, handler);
for (const [id, url] of [['a', '/teaching/a.jpg'], ['b', '/teaching/b.jpg']]) {
  const card = make('section');
  const image = make('img');
  const button = make('button');
  image.loading = 'lazy';
  image.width = 320;
  image.height = 240;
  image.alt = `Teaching cover ${id}`;
  button.type = 'button';
  text(button, `Preview ${id}`);
  available(button, false);
  on(image, 'load', () => { available(button, true); });
  on(image, 'error', () => {
    available(button, false);
    text(message, `Cover ${id} failed to load; preview unavailable.`);
  });
  on(button, 'click', () => {
    const copy = make('img');
    copy.alt = image.alt;
    copy.src = image.currentSrc || image.src;
    preview.replaceChildren(copy);
  });
  card.append(image, button);
  gallery.append(card);
  image.src = url;
}
</script>
</html>

Listeners are installed before src so an event cannot finish before registration. Each button closes over its own image. A successful first thumbnail does not enable the entire list. Real lists that replace sources or reuse nodes must reset success state and associate it with the new resource identity.

The new preview image still has its own loading lifecycle. A successful thumbnail establishes a past result for that resource, not permanent success for another use or a different original-image URL. If complete preview display is required, observe the preview's own load and error events. Button availability is not proof that original-image editing has completed.

Why complete alone is not success

The HTMLImageElement.complete reference includes absent sources, empty sources and broken images among its true conditions. A broken image with complete true is not contradictory. Enabling an operation solely from that flag confuses completion with successful availability.

The example owns image creation and listens before requesting the source. Existing DOM images may already have completed before binding; initialization needs a deliberate strategy rather than copying only the listener code. Pixel-consuming applications need additional checks appropriate to their resource and operation.

A real failure path also needs more than a permanently disabled button. Provide discoverable failure information and a way to continue or retry. This teaching page reports failure but implements no retry workflow. Adding retries requires clearing old success state so a new failed resource cannot inherit availability.

Why give lazy images width and height?

The current img reference warns that unloaded images without dimensions can lack visible area, affecting the conditions that trigger loading. The loading property reference describes loading as a browser hint. Dimensions establish space; they do not prove successful fetching.

Keep layout, source selection and loading state separate. Responsive image selection through srcset and sizes explains why currentSrc matters. Do not inspect only the authored src when a browser may select another candidate. This example has no srcset and validates no responsive-image policy.

Should a test scroll or force eager loading?

To examine the actual deferred path, retain lazy, scroll as a user would and inspect the target image and button. Forcing eager tests a different condition and removes the mechanism under investigation. Avoid asserting a universal exact scroll distance because scheduling belongs to the browser.

Proposed comparisons include valid and missing files, distant targets, repeated entry and source replacement. Retain target identity, load/error observations, button state and preview outcome. Window load timing is background evidence, not a per-image success condition. No browser or image requests have been run for this article. Identify the required image first, then collect evidence for that image.

Can a reused card inherit an old image's success?

Suppose cover A loaded and a filter reuses its card for cover B. Keeping A's enabled button lets users preview B before B succeeds. The apparent fast-click bug is actually stale success state. Success belongs to a resource use, not permanently to a button node.

Disable dependent actions before replacing the source, update record identity and establish success/failure handling for the new resource. Concurrent original-image reads also need ownership rules so an old completion cannot enable a new record. The fixed-loop sample implements no virtualized-list or concurrent-read solution.

Retry moves failure back to waiting. Setting src again is not immediate success and does not prove a new network request: caching and browser scheduling still matter. Keep failure feedback attached to the current cover and observe the actual result.

Record both URL and business identity. A new resource version for the same record, or a new record on the same node, needs its own comparison. That explains which successful load enabled an action rather than borrowing success from the previous image.
