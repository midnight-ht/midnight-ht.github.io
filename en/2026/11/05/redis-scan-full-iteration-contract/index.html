Why an empty Redis SCAN batch does not finish an iteration

End Redis SCAN by cursor, handle empty batches and repeated keys, and qualify COUNT, changing membership, and single-database coverage.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-05 · Estimated read 10 min
Translations
zh-CN en

Article

Key takeaways

  • An empty nonzero-cursor batch continues; the zero-cursor batch still needs processing.
  • COUNT is a work hint, and the application must handle duplicate effects.
  • Full iteration covers continuously present elements, not a point-in-time or cross-cluster snapshot.

A SCAN iteration ends when the returned cursor is zero, not when a batch is empty. Keys may also appear more than once, so a maintenance action must tolerate repeated processing. SCAN is not a fixed-size page API that delivers every key exactly once.

A task can receive no matches for an owned prefix and still have work remaining. “Processed zero items” describes that call; it does not establish completion. This article covers a selected database, without connecting to Redis or performing cleanup.

Finish by cursor, not batch length

The official SCAN reference defines a full iteration as starting at cursor zero and feeding back each returned cursor until zero returns again. An empty batch with a nonzero cursor requires another call.

Do not increment the cursor as a page number or treat it as a completion percentage. The following unexecuted pseudocode retains the client’s decimal-string representation to avoid accidental numeric conversion; use the actual library’s prescribed cursor type.

cursor = "0"
repeat:
    reply = scan(cursor, match=owned_prefix + "*", count=100)
    next_cursor = reply.cursor
    keys = reply.keys
    for key in keys:
        process_repeatably(key)
    cursor = next_cursor
until cursor == "0"

process_repeatably is a required application behavior, not an implemented helper. Processing precedes the termination check, so the final batch is retained. A failed network call must not become an empty array followed by a success report. Preserve an incomplete or unknown task state instead.

A client protocol test can supply three explicit fixtures: a nonzero cursor with no keys; another nonzero cursor with two keys; then zero with a duplicate key. Expect three calls, processing of the final batch, and safe duplicate handling. These are designed fixtures, not observed Redis replies.

COUNT is a work hint

The reference describes COUNT as the requested amount of work, not a fixed output size. MATCH results do not turn that hint into a database total. Fewer than 100 results, no results, or an entire small collection in one response need not indicate a paging failure.

Choose COUNT from measurements on the target workload. Larger calls can change both call count and per-call resource use; no universal optimum follows from a documentation example. Progress can report calls made and keys observed, but the numeric cursor does not supply a reliable percentage. A total or deadline needs its own contract.

Repeated keys require repeated-safe effects

SCAN may return an element several times. An unprotected increment can therefore overcount. A process-local seen set also loses its protection on restart. Choose a repeatable action or durable identity handling according to the actual effect, not just the loop’s shape.

Even deletion needs a concurrency decision. A key observed earlier can be replaced with new content before deletion runs. Repeating a delete may be harmless in one sense while deleting a newly created value is still wrong. If cleanup targets a specific generation, define that generation through naming or an appropriate conditional operation. “DEL can be repeated” does not prove ownership of the current value.

Operate only in an isolated instance or under explicitly owned unique prefixes. No shared-database deletion script or database-clearing command is provided here.

A full iteration is not a snapshot

Coverage applies to elements continuously present from the beginning through the end of the iteration. An element present for only part of that period may or may not appear. Creation, expiration, deletion, and recreation can prevent the observed list from representing any single instant.

The October 10, 2026 article on pagination and stable reads separates ordering from cross-request snapshots. SCAN has its own weak iteration guarantees; adding SQL-style unique ordering does not change them. Exact inventory requires a separately justified data source or coordination design.

An indefinitely growing collection also does not justify an unconditional completion deadline. A time budget can stop a task as incomplete, with its processed scope recorded. One selected database’s iteration does not establish coverage across every Redis Cluster node.

Does a zero-cursor reply still need processing?

Yes. Zero means no further call is needed, not that the current batch should be discarded. Test this alongside an empty batch with a nonzero cursor; the two cases expose different early-exit mistakes. Record request and response cursors, processed identities, and final task state, then inspect actual behavior in an isolated version-specific test.

The pseudocode and fixture sequence were not executed. Completion requires a zero cursor, a processed final batch, controlled repeated effects, and a claim about changing membership that stays within the documented guarantee. An empty batch alone establishes none of those outcomes.
