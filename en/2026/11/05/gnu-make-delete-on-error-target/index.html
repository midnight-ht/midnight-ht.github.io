GNU Make failed once—why does the next run accept the partial target?

Explain partial GNU Make targets, timestamp-based reuse, and the tradeoff between failure deletion and staged publication.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-05 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • A partial target can appear current on the next invocation.
  • Failure deletion requires failure to reach make.
  • Staged publication can preserve a previous valid version.

A failed GNU Make recipe does not necessarily remove a target it has already changed. If that partial file looks newer than its prerequisites, the next invocation can skip rebuilding it. Review .DELETE_ON_ERROR and the exit status actually delivered to make before deciding whether to delete failed targets or generate elsewhere first.

How one failed run affects the next

The GNU Make section on recipe errors describes a changed target surviving a failed recipe. Its timestamp can then make it appear up to date. The manual recommends explicitly requesting deletion through its failure-deletion special target. The online manual was checked on November 5, 2026; the Makefile below was not executed.

Suppose report.txt depends on input.txt. A generator opens the report, writes its heading, then fails while reading a later record. The first invocation correctly returns nonzero and CI turns red. Nevertheless, report.txt is now newer than input.txt. If the input remains unchanged, the next ordinary timestamp comparison can accept the incomplete report as current.

There is no contradiction between those observations. One invocation reports execution failure; the next examines files and dependency timestamps. Retrying without changing the invalid target leaves the same evidence available to that comparison. Generated archives, reports, and source files need a deliberate policy for this state.

A small two-invocation example

This unexecuted example assumes GNU Make, a conventional command-line shell, and an isolated writable directory containing the input file. Recipe indentation must be a tab. report.txt is a real file target, not a phony task name.

.DELETE_ON_ERROR:

report.txt: input.txt
    printf 'partial report\n' > report.txt
    false

Without the special-target declaration, the first invocation writes partial content and false returns nonzero. Ordinary error reporting does not guarantee removal of the file. If the timestamp relationship makes it current, a second invocation can skip the recipe. With the control, the changed target is deleted after failure, so a later invocation sees a missing target and must attempt the rule again. These are documented-behavior predictions, not captured execution logs.

Record both the make exit status and the target's existence and contents. A terminal error excerpt misses the residual file; existence alone mistakes a partial artifact for a finished report. Control the input timestamps too. An editor that happens to rewrite input.txt between attempts can force rebuilding and conceal the behavior under investigation.

The control does not make the broken generator succeed. Repeating this recipe still reaches false. Its purpose is to prevent a partial target from qualifying as valid input to a later incremental run. A successful generator separately needs content checks. “The failed target was removed” and “the report is correct” are different results.

Save the displayed fragment as Makefile inside a new sandbox. The unexecuted sequence below creates that directory and input, then creates a comparison rule by removing only the first-line control. Save the Makefile at the indicated point before continuing. Inspect each exit result immediately and list the directory. Do not use an existing release directory.

make_demo_dir=$(mktemp -d)
cd "$make_demo_dir" || exit 1
printf 'input\n' > input.txt
# Save the displayed Makefile here before continuing.
sed '1d' Makefile > WithoutControl
run_demo() {
    make -f "$1"
    make_result=$?
    printf 'status=%s\n' "$make_result"
    ls -l
}
run_demo WithoutControl
run_demo WithoutControl
rm -f report.txt
run_demo Makefile
run_demo Makefile

Without the control, a second invocation accepting the leftover file can skip false and return success. That is the invalid reuse being exposed, not a repaired report. With the control, both invocations should retry and fail. If filesystem timestamp precision or ordering produces another branch, retain the observations and inspect those conditions rather than rerunning until a preferred result appears.

Failure must reach make

GNU Make examines the exit status of each recipe-shell invocation. A leading minus, global ignore-errors option, or .IGNORE can turn an error into an ignored result. A shell expression that swallows a generator's failure may likewise return zero. In those cases, the control has no reported recipe failure on which to act.

Review the chain rather than searching only for the special target: generator status, shell status, then make's decision. A final command printing “complete” can obscure an earlier failure if the surrounding shell expression does not preserve it. Visible error text does not establish a nonzero final shell result.

Ordinary recipe lines run in separate shells. In this example the write and false each return through their own invocation. Combining them, using .ONESHELL, or changing the configured shell requires a fresh review of failure propagation. This article does not promise identical semantics for every shell configuration.

Does -k turn the build into a success?

No. The manual distinguishes keep-going from ignoring errors. With -k, make continues considering independent work, then returns nonzero. Targets depending on the failed prerequisite still lack what they need. This is useful for finding several independent compilation problems in one attempt; it does not repair partial files.

For two independent reports, the second may be checked after the first fails. An archive depending on both is still not deliverable. Collecting additional diagnostics and refusing an incomplete deliverable are compatible goals.

When is a temporary output preferable?

If the previous complete report must remain usable, overwriting the target and deleting it on failure also loses that old version. A candidate design generates into a separate temporary path, validates the result, and only then publishes it as the target. That preserves the old file until publication, but still needs temporary-file cleanup, concurrency rules, and understood rename conditions. Do not extend a local rename claim to a multi-file, cross-filesystem, or remote transaction.

Choose by the desired failure state. Deletion suits targets that must not exist when invalid. Generate-then-publish better expresses a requirement to retain the last valid version. Neither local policy undoes database writes, notifications, or uploads performed by the generator; those side effects need their own idempotency or reconciliation arrangements.

Proposed validation uses isolated directories with and without the control. Fix the input, record the first exit result and target content and timestamps, then rerun unchanged. Add ignored-error and successful-generation cases. Confirm that failure leaves no misleading target and that success meets the report's content requirements. Keep the experiment out of the real release directory.

The October 25 reproducible-time article asks whether controlled inputs reproduce identical bytes. This question comes earlier: should a file left by a failed attempt qualify for the next incremental build at all?
