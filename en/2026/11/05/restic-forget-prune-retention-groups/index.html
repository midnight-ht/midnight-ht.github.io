restic forget removed a snapshot—why has repository size not fallen?

Distinguish restic snapshot removal, shared data references, per-group retention, and repository maintenance acceptance.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-05 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • forget removes recovery points; prune handles unreferenced data.
  • Default retention applies separately to host-and-path groups.
  • Structural checks and selected restores need separate evidence.

restic forget removes snapshot records; prune removes stored data that retained snapshots no longer reference. Shared data remains live when another snapshot still needs it. A repository that has not immediately shrunk is not a reason to delete more recovery points. Review retention first, then schedule storage maintenance.

Removing a snapshot does not remove every referenced byte

The restic snapshot-removal guide separates forget from prune. The former removes snapshots; the latter handles data referenced only by removed snapshots. A prune option can combine the sequence when forget actually removes snapshots, but combining commands does not eliminate their different purposes. The current stable guide was fetched on November 5, 2026. No repository was changed.

Consider a hypothetical reference map. Host A's early snapshot references shared block A and old-file block B. Its later snapshot references A and replacement block C. Host B has another snapshot referencing A and its own block D. Forgetting the early snapshot can leave B unreferenced, while A remains necessary for two retained snapshots. Removing A would damage those recovery points.

These letters are teaching labels, not real restic object IDs or measured storage figures. They show why adding snapshot logical sizes does not predict reclaimable bytes. Actual storage also involves packing and repacking. Logical contents, unreferenced data, and repository occupancy are different quantities. A large removed snapshot may therefore yield little uniquely reclaimable data.

If the snapshot list shrinks but storage does not, first establish whether only forget ran. Then examine shared references and the maintenance plan. Do not infer that snapshot deletion failed and remove additional recovery points as an experiment. A later prune can make a mistaken retention decision much harder to recover from.

Why can --keep-last 1 leave several snapshots?

By default, the documented policy groups snapshots by hostname and paths and applies retention separately to each group. Suppose two hosts each back up /srv/app and each has an early and late snapshot. Keeping the last one normally retains one per group, rather than one for the entire repository. That protects unrelated backup sets from competing for a single recovery point.

These unexecuted commands show a candidate inspection against an isolated teaching repository. Repository identity, access, and retention policy must be established separately; /sandbox/repo is not a production target.

restic -r /sandbox/repo snapshots
restic -r /sandbox/repo forget --keep-last 1 --dry-run

The first command inventories snapshots. The second prints proposed keep/remove actions without removing anything. Review hostname, paths, timestamps, and snapshot identity in each group, rather than counting the final rows. Renaming a host or changing backup paths may create a new group. Decide whether that reflects the intended recovery boundary before changing grouping.

The group-by option can choose different grouping fields, and an empty value disables grouping. Disabling it merely to obtain a tidy total of one makes unrelated hosts compete under one policy. Changing that boundary requires a deliberate recovery decision, not a desire for a smaller displayed count.

Filtering and grouping are separate controls. Restricting candidate snapshots by host or tags determines which snapshots the policy considers; grouping determines how those candidates are partitioned. A maintenance request saying only “keep one” is incomplete until it specifies which backup sets that statement covers.

Pruning needs a maintenance window

The guide states that prune locks the repository and backups cannot complete during the operation. Partly used packs may need downloading and repacking before upload. This is repository maintenance with resource costs, rather than a free deletion step. Repository scale, remote throughput, available space, and the next backup window matter; none was measured here.

A reviewable sequence saves the dry-run list and policy version, confirms retained recovery points, and schedules authorized deletion and pruning in a separate maintenance window. Preserve complete exit results. Afterwards, inspect repository structure and restore a specifically identified retained snapshot. This article supplies no automated destructive script because the hypothetical repository has no established protection set or operating budget.

If maintenance fails, preserve the state and tool details and follow the relevant troubleshooting procedure. Repeating broader deletion is not diagnosis. A remote storage provider may also retain object versions or calculate billing differently. restic-visible object changes do not establish an immediate billing reduction.

Does successful prune prove recoverability?

No. Maintenance completion, structural checking, and application recovery answer separate questions. The guide advises running check after pruning to detect internal-structure damage. That does not supply application roles, configuration, or external dependencies. Recovery acceptance requires selecting a retained snapshot, restoring into an isolated destination, and checking needed contents and operating conditions.

For the reference example, create distinguishable teaching files for A, B, C, and D. Save both hosts' snapshot inventories and verify that the dry run retains the intended later snapshot in each group. An actual sandbox exercise should then confirm that both retained restores remain complete after authorized forgetting and pruning. Record storage changes separately rather than adjusting acceptance to obtain a larger reclaimed-byte count.

New snapshots arriving between preview and execution can change the evaluated set. Record observation times, repository identity, and intervening changes, and review again when necessary. A dry run describes a policy against the set observed then; it is not approval for every future repository state.

The October 9 restore-rehearsal article addresses the endpoint of usable business recovery. This article is narrower: selecting restic recovery points and maintaining deduplicated storage. Establish which usable recovery points remain before asking how much space can be reclaimed.
