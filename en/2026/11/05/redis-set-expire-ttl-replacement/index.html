Why a Redis cache update can remove its expiration

Compare plain Redis SET, KEEPTTL, and expiration options, separating fixed deadlines, sliding refreshes, and failure between two calls.

Updated 2026-11-05 · Estimated read 13 min

Article

Key takeaways

  • Replacement and in-place modification handle an existing TTL differently.
  • Retaining a deadline, renewing a lifetime, and creating expiration are separate intentions.
  • Inspect conditional results and verify TTL with ranges that allow elapsed time.

A successful plain SET discards the key’s prior TTL, while an in-place hash update preserves it. Decide whether an update keeps the original deadline or starts a new lifetime. Updating the value and deciding its remaining lifetime are separate parts of the write contract.

Suppose a result cache should expire after two minutes. Refreshing it with a plain SET changes the value successfully, but it remains past the original deadline. Inspect the actual command before blaming expiration cleanup. This explanation follows the current official documentation; no Redis connection or command execution was performed.

Replacing a value differs from changing part of it

The Redis SET reference says that a successful SET discards the previous time to live. Expiration options can provide a new lifetime, while KEEPTTL preserves the current one. The EXPIRE reference distinguishes replacement from in-place modification: operations such as INCR, LPUSH, and HSET leave an existing timeout intact.

“Update” is too broad to determine this behavior. Replacing an entire JSON string and changing a hash field may serve a similar product action but issue different commands. Preserve the command, options, and starting state. A wrapper named updateCache does not reveal whether it preserves, renews, or removes expiration.

For an existing expiring string, three intentions differ. Plain SET replaces its content without keeping the old TTL. SET with KEEPTTL retains the existing deadline. SET with EX assigns a lifetime to the new value. Fixed deadlines and sliding refreshes are different requirements; neither is universally preferable.

Compare only keys you own

These unexecuted redis-cli examples belong in an isolated local instance or under a prefix you explicitly own. Replace the example prefix with one unique to this experiment. Do not overwrite business keys in a shared instance. Each key tests a separate policy, and no database-clearing command is included.

SET editorial_demo_unique:plain v1 EX 120
TTL editorial_demo_unique:plain
SET editorial_demo_unique:plain v2
TTL editorial_demo_unique:plain

SET editorial_demo_unique:keep v1 EX 120
SET editorial_demo_unique:keep v2 KEEPTTL
TTL editorial_demo_unique:keep

SET editorial_demo_unique:refresh v1 EX 120
SET editorial_demo_unique:refresh v2 EX 120
TTL editorial_demo_unique:refresh

The derived expectations are state-based. The first key ends without an expiration. The second retains its previous deadline, with time passing during the experiment. The third receives the stated lifetime from its latest write. Do not assert that every TTL observation equals exactly 120; commands take time. Check command results and existence too, so a missing key is not mistaken for a persistent one.

An additional owned hash can compare HSET behavior: create it, assign an expiry, then change a field and observe the remaining lifetime. This tests the in-place rule. It does not establish that every string cache should become a hash. Choose representation from the required read and write granularity, not from expiration alone.

Review SET followed by EXPIRE as two operations

An application can stop after writing a value but before sending EXPIRE. The intended new content then exists without its intended lifetime. This is a gap between application calls, not a claim that Redis partially executes one received SET command. If a new value and new lifetime belong to one write decision, the corresponding SET expiration option expresses that decision directly.

Retries also change the timeline. Repeating SET with EX starts the lifetime from another write time. That may suit a sliding cache but violate a rule that data must not outlive a fixed business deadline. For an absolute deadline, choose an option that expresses it and check the relevant clock assumptions. For an existing deadline, consider the retention semantics of KEEPTTL. Cache expiration is not a substitute for business authorization checks.

A wrapper can name the policy explicitly and require creation paths to choose a lifetime as well. Quietly renewing every update may keep hot keys indefinitely. Quietly dropping expiration may make short-lived data persistent. Both mistakes can pass a test that merely reads the new value.

Does KEEPTTL give a persistent key an expiration?

No. Retaining an existing TTL does not create one. Test three starting states separately: an expiring key, a persistent key, and an absent key. A successful result with the first state does not establish the creation policy for the others.

Check server and client support too. The current SET command history identifies KEEPTTL as introduced in Redis 6.0. Whether the project’s client library exposes it and the wrapper actually sends it requires evidence from those versions. A modern documentation page does not upgrade an older dependency.

Why can EXPIRE GT leave a persistent key unchanged?

For GT and LT comparisons, the EXPIRE documentation treats a nonvolatile key as having an infinite TTL. A finite lifetime is not greater than infinity, so GT does not satisfy its condition. Inspect the conditional result rather than recording only that the call returned. Policies for creating, modifying, extending, and shortening expiration need matching command conditions.

Expiration belongs to the storage path being investigated. The site’s October 30, 2026 article on Node.js DNS lookup boundaries concerns resolver responsibility. An application’s Redis expiration is a separate state; changing one place’s caching does not establish the other’s lifetime.

For acceptance, record expected values and expiration states across the three starting conditions and chosen write forms. Compare remaining time using sensible ranges rather than exact seconds. Interrupt the application between separate SET and EXPIRE calls to inspect the failure path. None of these tests was run here. A useful delivery explains whether each write keeps, replaces, or removes expiration and why that behavior fits the cache’s purpose.
