Why PostgreSQL last_value does not automatically mean the last row in a partition

Distinguish partitions, ordering, and window frames in PostgreSQL 18, with a complete reading report and checks for peers, nulls, and output granularity.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-05 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • The default frame ends at the current row’s last peer, not necessarily the partition’s end.
  • Keep meaningful ordering and state a complete frame when selecting a partition-final value.
  • Check nulls, tied ordering, and retained row identities separately.

last_value reads the final row of its window frame. PostgreSQL 18’s default frame stops at the current row’s last peer, so a partition-wide final value needs an explicit frame. Interpret “last” together with the set of rows visible to the function.

Suppose a device report must retain every reading for a day and attach that device’s final reading to each row. A time-ordered last_value changes as the report proceeds. The ordering may be correct: the mistake can be treating a partition and the current row’s frame as the same range. The following input and results are teaching examples, not an executed database test.

Each row has a frame inside its partition

The PostgreSQL 18 window-function reference says that first_value, last_value, and nth_value consider the window frame. With ORDER BY, the default frame extends from the partition’s start through the current row’s last peer. Peers are rows indistinguishable using the window’s ordering columns; that boundary need not be just the current physical row.

PARTITION BY separates devices. ORDER BY defines the order within each device. The frame determines which slice is visible from a particular output row. Ordering a partition does not automatically extend that slice to the partition’s end. List the visible row identities first, then find the last member of that set.

This example adds a unique reading ID to resolve tied timestamps. That is an explicit tie rule for this example, not a claim that IDs universally carry more business meaning than timestamps.

WITH readings(device, id, measured_at, value) AS (
  VALUES ('A', 11, timestamp '2026-11-05 09:00', 10),
         ('A', 12, timestamp '2026-11-05 09:00', 20),
         ('A', 13, timestamp '2026-11-05 10:00', 30),
         ('B', 21, timestamp '2026-11-05 09:00', 70)
)
SELECT device, id, value,
       last_value(value) OVER (
         PARTITION BY device ORDER BY measured_at, id
       ) AS default_last,
       last_value(value) OVER (
         PARTITION BY device ORDER BY measured_at, id
         ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
       ) AS partition_last
FROM readings
ORDER BY device, measured_at, id;

From the stated input, A’s default values should be 10, 20, and 30; its full-partition value should be 30 on all three rows. B’s single row should show 70 in both columns. Both expressions retain all four rows. Window calculations do not reduce A to one representative record. These are derived expectations; the SQL has not been run.

Remove id from the window ORDER BY and A’s first two rows become peers. Their default frames include both 09:00 readings. They do not necessarily stop at the current physical row. Without a further order between those different values, do not require last_value to select one particular reading consistently. An outer ORDER BY containing id cannot complete the ordering inside the window.

Why not remove ORDER BY?

For window aggregates, the reference describes omitting ORDER BY or writing a whole-partition frame to aggregate the entire partition. For last_value, there is another question: without an order, which member deserves to be called last? This report needs the final reading in time, so retain the ordering and extend the frame explicitly.

Reversing the order is not a mechanical substitute either. It changes which end represents the latest reading while leaving the default-frame rules intact. first_value with a descending order can serve a different formulation, but still needs tie rules, null semantics, and the correct output shape. Explain why a replacement selects the same record identity; matching one sample value is insufficient.

If the page only needs one latest record per device, change the output contract first. The October 14, 2026 article on DISTINCT ON representative selection addresses that task. Representative selection changes the number of rows. A window result attaches information to rows that remain in the report.

Will a null final reading be skipped?

No. PostgreSQL 18 does not implement the SQL standard’s IGNORE NULLS option for these window functions; it uses RESPECT NULLS behavior. Change A’s final value to NULL and last_value over the complete frame selects that null rather than automatically falling back to 20.

“The latest record” and “the latest valid measurement” are separate questions. The former may need to expose that the most recent collection failed. The latter needs a definition of validity and selection from qualifying rows. Filtering nulls before the window can also remove original rows that the report was meant to retain. Computing the latest valid reading separately and joining it back is a possible design, but the association, duplicate handling, and all-null case require their own checks.

Related fields must retain their provenance. If a value, collection time, and status must come from one record, independently taking their maxima can manufacture a combination absent from the input. last_value computes one expression; the application must still ensure that accompanying fields describe the same chosen record.

Verify identities and values on every row

Write the expected final record identity for each device before running the query. Then check that every retained row carries its value. Include tied times with distinct IDs, a final NULL, a single-row device, and several devices. Shuffle the input declaration order and verify that the explicit ordering still determines the result.

If the real partition includes a date, define the timezone used to establish that date. The example’s timestamps do not define a global device-day boundary. A late-arriving record can also change a partition’s final value; one query does not promise that a later request will return the same answer.

Preserve the PostgreSQL version, complete SQL, input, and row-by-row differences. Evaluate sorting cost and partition size after verifying semantics; four teaching rows cannot establish production performance. No query was executed here. The first acceptance task is to identify the frame visible from each row and show that its final member matches the intended business record.
