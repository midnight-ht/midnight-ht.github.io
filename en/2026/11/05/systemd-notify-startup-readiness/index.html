systemd start succeeded—why did dependent work still start too early?

Model systemd startup through Type, READY sender identity, timeout, and dependency ordering under four explicit inputs.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-05 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • simple, exec, and notify use different completion boundaries.
  • Requirement dependencies and startup ordering are separate.
  • Verify both the READY send point and the main-process identity.

Startup completion in systemd depends on Type. simple proceeds after fork and exec waits for executable invocation; neither inherently waits for application initialization. A notify service must report READY=1 at the right point. Changing the type also does not create an ordering relationship for a dependent unit that has none configured.

Choose the completion boundary before the dependency

The systemd.service manual defines Type as the mechanism used to report startup completion. simple has a boundary before program execution. exec exposes invocation failures such as a missing executable, but does not inspect application progress. notify requires an explicit protocol message. The latest online manual was checked on November 5, 2026; it does not establish any particular host's installed version.

Suppose a report service loads templates, builds a read-only index, and binds its listening port. A warmup task must access it only after all three steps. With simple, the task may be released before executable invocation. With exec, invocation has succeeded but template loading may still be underway. Neither boundary identifies the end of initialization.

notify lets the application make that report, but the application still needs a truthful send point. For this scenario, templates, index, and listener must be ready first. Sending READY immediately on entering main merely moves the premature completion claim into application code. The manager can wait for the report; it cannot prove the report's meaning.

Units and explicit implementation assumptions

This unexecuted protocol design assumes an owned report-service whose main process implements sd_notify and provides a controlled initialization-delay mode. The /opt executable is not supplied as a runnable implementation. These fragments express interface conditions and state predictions, rather than a complete installation tutorial. The proposed service file is report-demo.service.

[Unit]
Description=Report initialization contract demo

[Service]
Type=notify
NotifyAccess=main
TimeoutStartSec=30s
ExecStart=/opt/report-service/bin/report-service

The proposed warmup-demo.service assumes another owned program making one read-only request and returning an explicit result. Its dependencies express separate requirements.

[Unit]
Requires=report-demo.service
After=report-demo.service

[Service]
Type=oneshot
ExecStart=/opt/report-service/bin/warmup

The systemd.unit manual explains that requirement dependencies do not impose startup ordering. After or Before must configure that separately. Here Requires pulls report into the startup transaction, while After orders warmup after report's startup completes. After alone does not start the other unit; Requires alone does not establish the intended ordering.

Thirty seconds is a teaching budget, not a universal recommendation. Choose an actual budget using acceptable initialization time, machine conditions, and data size. TimeoutStartSec bounds startup waiting. Failure to complete within it is treated as startup failure under the configured timeout policy. Notification-based extension is possible, but is outside this scenario and is not an excuse for indefinite waiting.

Four input conditions and their state transitions

In the normal case, the manager invokes the main process and report remains activating. The application finishes templates and indexing, establishes the listener, and sends READY=1 from that same main process. report's startup completes and ordered warmup can start. The warmup request still needs its own outcome; report's startup does not prove that later task succeeded.

In the delayed case, template loading takes longer but finishes within budget. report remains activating and warmup waits until the real completion notification. Explain the wait through event records rather than a fixed sleep. If initialization exceeds the budget, this scenario fails startup; a port appearing later does not retroactively make the failed transaction successful.

In the early-exit case, a template error terminates the main process before READY. The startup contract was never fulfilled. With this example's Requires and After combination, the failed activation does not provide the prerequisite for ordinary warmup. Preserve the exit reason and dependent-job result rather than reporting that a process once existed.

In the no-notification case, the process keeps running and may even listen, but never sends READY. The manager does not infer a missing protocol message from a listening port. It continues waiting subject to the startup timeout. Changing Type does not add protocol support to an old executable; implement support or explicitly choose a different completion boundary.

Why is the notification sender part of the readiness protocol?

The manager accepts readiness updates only from senders allowed by NotifyAccess; with main, that means the service’s main process. An arbitrary helper is not necessarily that process. The manual also describes attribution races when an auxiliary sender exits immediately; widening access to all does not justify ignoring those races. Prefer an owned, long-running main process reporting at the defined completion point.

The sd_notify manual does not define READY=0 as a reversal. Startup notification is not a continuous routing-health switch. A database outage after READY needs separate application responses, recovery, and monitoring; sending zero does not undo dependent work.

Proposed verification uses an isolated Linux machine, records the manager version and effective units, and exercises normal, delayed, early-exit, and no-notification inputs in the owned implementation. Correlate initialization start, listening, READY transmission, dependent start, and request result with startup-job state. Include run identity, main-process PID, input mode, initialization step, monotonic time, and dependent exit status. These fields help distinguish no message, an unaccepted sender, and a successful notification followed by a failed request. Syntax validation alone cannot establish sender attribution or successful requests. No unit was installed and none of these cases was executed here.

The October 24 Compose startup-dependency article also separates startup from ongoing recovery. Here the specific mechanism is an identity-constrained application notification plus a separately configured ordering relationship. Verify protocol support, the actual send point, and the complete dependency before recording startup success.
