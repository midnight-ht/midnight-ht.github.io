Why an index does not answer PostgreSQL partition pruning questions

Separate PostgreSQL 18 partition pruning from indexed access and inspect parameters, subplans, and observations at planning, initialization, and execution.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-05 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • Partition bounds eliminate partitions; indexes govern access within those retained.
  • Parameters can allow pruning during planning, initialization, or execution.
  • Listed plans, actual scans, and lock footprints need different evidence.

Pruning excludes partitions that cannot match; indexes govern access within the remaining partitions. PostgreSQL 18 can also prune during execution, so several listed subplans do not by themselves prove failure. Ask which partitions must participate before asking how their rows are read.

For a monthly log table, a query covering early November may exclude October regardless of whether a date index exists. Excluding October also does not force an index scan in November. These are separate decisions.

Bounds and indexes answer different questions

The PostgreSQL 18 partition-pruning reference explains exclusion by proving a partition cannot contain qualifying rows. Declarative partitioning supplies partition bounds. An index instead helps locate rows inside a retained partition.

Pruning can therefore occur without a partition-key index. A sequential scan can be reasonable when most remaining rows qualify; an index may help for a selective query. Adding indexes to fix a missing bound proof can increase maintenance without addressing the cause.

Inspect actual SQL too. A date filter may wrap the key in a function or introduce a conversion. Whether the planner can derive usable bounds from that expression needs evidence. Neither “all wrapped keys prevent pruning” nor “mathematical equivalence guarantees optimization” is a reliable blanket rule.

Establish the expected rows first

This unexecuted example belongs only in a separate isolated test database. It must not overwrite existing objects. The transaction rolls back its table and data; no plan output is fabricated.

BEGIN;
CREATE TABLE demo_measurements (
  id bigint NOT NULL,
  logdate date NOT NULL,
  value integer
) PARTITION BY RANGE (logdate);
CREATE TABLE demo_measurements_oct PARTITION OF demo_measurements
  FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
CREATE TABLE demo_measurements_nov PARTITION OF demo_measurements
  FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');
INSERT INTO demo_measurements VALUES
  (1, DATE '2026-10-31', 10),
  (2, DATE '2026-11-01', 20),
  (3, DATE '2026-11-03', 30);
PREPARE demo_lookup(date, date) AS
  SELECT id, logdate, value
  FROM demo_measurements
  WHERE logdate >= $1 AND logdate < $2;
EXPLAIN (COSTS OFF) EXECUTE demo_lookup(
  DATE '2026-11-01', DATE '2026-11-03'
);
EXECUTE demo_lookup(DATE '2026-11-01', DATE '2026-11-03');
DEALLOCATE demo_lookup;
ROLLBACK;

The derived result contains only ID two: November 1 is included and November 3 excluded. Verify that set before optimizing. A faster query that accidentally excludes a boundary row answers a different question. Cross-month parameters need separate expectations because both partitions may legitimately participate.

No index is created, deliberately separating bounds from indexed access. If adding one later, keep SQL and parameters constant and record partition elimination and within-partition access independently.

When does the parameter become known?

The documentation distinguishes planning-time pruning from execution-time pruning. Values available during planning can exclude partitions early. Other prepared parameters, subquery results, or parameterized join values may become available at initialization or during execution.

PREPARE does not promise one plan shape or a Subplans Removed field on every execution. Planning decisions and actual parameter values matter. Preserve observed plans rather than inventing fields expected by a tutorial, and identify which stage the evidence can establish.

Subplans Removed can help identify initialization-time removal. Runtime pruning also needs careful examination of subplan loops in EXPLAIN ANALYZE. A never executed label can have other control-flow causes; it is not sufficient by itself to prove pruning.

Does a listed partition necessarily get scanned?

No. Ordinary EXPLAIN describes a plan, not every actual execution count. Use ANALYZE only in a controlled isolated setting when actual behavior is required: it really executes the statement. The October 9, 2026 article on EXPLAIN evidence boundaries separates estimates from runtime observations.

Preserve parameters, enable_partition_pruning, complete parent and child nodes, and execution counts. Cropping out a never executed node or counting partition names cannot explain why a partition was avoided. Test several months rather than allowing one planning-time-resolvable case to represent every request.

Avoid equating “not scanned” with “untouched.” The reference notes that partitions removed at initialization are still locked at execution’s start. Lower read volume does not establish a narrower locking footprint for online maintenance. Inspect reads and locks separately.

A pruning-off comparison must keep business filters and expected results unchanged. Confine experimental settings to an isolated transaction and preserve the original values; a reused pooled connection can otherwise carry a test setting into another request.

Reconsider the partitioning contract when necessary

Queries that do not constrain the partition key may gain little from pruning. Revisit access patterns and lifecycle requirements instead of assuming more partitions always help. Planning, object maintenance, and changes also have costs; small tables or all-history summaries need their own justification.

Acceptance should compare single-month, cross-month, empty-range, and boundary-date result sets before inspecting pruning stages. Measure buffers, latency, and workload only after semantics agree. No SQL or performance experiment was run here. Separate evidence for eliminated partitions from evidence for reading the rows that remain.
