Why deleting a Protobuf field still needs reserved numbers and names

Separate binary field numbers from text-format names, preserve retired identities, and review compiler failures, historical bytes, and mixed deployment independently.

Updated 2026-11-05 · Estimated read 14 min

Article

Key takeaways

  • Removing a declaration does not free an existing binary field number.
  • Reserved numbers and names have distinct roles and do not supply a universal runtime rejection policy.
  • Compiler checks, historical decoding, and client retirement require separate evidence.

When you delete a Protobuf field, reserve its old number and consider its name for text-format compatibility. Removing the declaration does not retire bytes or clients already using that identity. Decide separately whether you are retiring a field from new code or retiring the data still held in files, queues, and older applications.

Why a deleted number is still occupied

The Protocol Buffers proto3 language guide explains that field numbers identify fields in the binary wire format. Once a message type is in use, its numbers must not be changed or reused. A field name helps a developer read the declaration; the number is part of the serialized identity.

Suppose an older order message declares string legacy_note = 4 for a support note. A later version removes it and introduces string routing_region = 4. An old note can now be interpreted as a routing region. Both fields have a string representation, so an absence of decoding errors would not establish business correctness. Matching types can make the mistake less visible. This is a hypothetical consequence of the format rules, not an executed serialization experiment.

The scope is the message type. This does not require every message in an entire project to share one global number ledger. Using number four in a separate message is different from assigning a second meaning to number four in the same order message. A review needs the complete message identity as well as the number.

Preserve the retirement decision in the declaration

These are uncompiled teaching examples. Keep the versions in separate test directories rather than compiling both declarations of the same message together. Version two reserves the retired identity and gives the new business field a fresh number.

// v1/order.proto
syntax = "proto3";
package example;
message Order {
  string id = 1;
  string legacy_note = 4;
}

// v2/order.proto
syntax = "proto3";
package example;
message Order {
  reserved 4;
  reserved "legacy_note";
  string id = 1;
  string routing_region = 5;
}

The guide’s deleting-fields section recommends reserving deleted numbers and discusses reserving names. reserved 4 gives a compiler a rule it can check: a future declaration cannot allocate number four in this message. A comment asking developers not to reuse it does not supply that compiler check. Numbers and names belong in separate reserved statements; they cannot be mixed in one statement.

The new declaration does not convert old notes into regions. Nor does it promise to preserve old notes forever. It prevents two meanings from receiving the same field identity. What happens to undeclared fields in old messages depends on encoding, runtime behavior, and any transformations performed by the application. A reserved declaration is not a data-retention or erasure procedure.

Moving a field from number four to number five is also not a transparent binary rename. It removes one identity and adds another. Older readers do not automatically understand the new number. If the migration needs both old and new meanings for a while, specify the readers’ and writers’ behavior explicitly rather than relying on similar names or adjacent numbers.

Is reserving the number enough?

The number protects binary identity. Names require a separate decision when the system uses JSON or TextProto. The official guide notes that reusing a name is generally safe for binary encoding but can create problems in encodings that serialize names. Check exported JSON, text fixtures, debugging formats, and cross-system text messages, not just binary RPC traffic.

Reserving a name primarily constrains later schema compilation. It is not a universal runtime rule telling a JSON parser to reject that property. The guide explicitly says reserved names do not affect runtime JSON parsing. It also describes a special TextProto behavior in some language implementations that can discard unknown fields with reserved names. That is not a promise that every runtime rejects an old name.

If an API still receives legacy_note in JSON, decide whether the application rejects it, ignores it, or reads it for compatibility. Test that policy at the actual parsing boundary. Preventing a future binary-number allocation and deciding what to do with an incoming text property are separate checks. A single statement that “compatibility passed” can hide which behavior was actually inspected.

Will reserved stop older clients from sending the field?

No. It checks future declarations. It does not update deployed clients or empty a queue of historical messages. A retirement record should identify producers that have stopped writing the field, consumers that still depend on it, and the period during which stored messages may be replayed. No recent traffic only supports an observation about that period; it does not prove an offline client can never return.

Use those dependencies to determine deployment order. If a consumer stops applying the old field while an older producer still relies on that behavior, messages may remain parseable while the business operation changes. A binary-compatibility check alone will not catch that decision. Obtain agreement that the old meaning can be discarded before removing the read behavior. Reserving the number prevents future reassignment; it does not authorize today’s feature retirement.

The site’s October 23, 2026 article on gRPC terminal status and business results examines whether a call actually completed. This check asks whether its fields were interpreted correctly. A normally completed call can still carry data interpreted under an incorrectly reused field number.

Test declarations and historical bytes separately

Start with compiler checks. In a disposable copy of version two, deliberately add a field using number four and verify that the actual protoc version rejects it. Then try the reserved name. Preserve the version and errors, and restore the correct declaration afterward. These checks establish compiler behavior, not compatibility across a deployed fleet.

Next, produce bytes with version one and decode them with both an intentionally incorrect reuse version and the correct version two. Inspect the specific business fields rather than merely checking for exceptions. For text paths, exercise the old name, an unknown name, the new name, and omission through the actual JSON or TextProto library and application entry point.

Finally, test mixed deployment and historical replay against the agreed retirement policy. None of these procedures was executed for this article, and the snippets are not successful test records. A reviewable retirement identifies where the old number remains reserved, which readers and writers still exist, and how compilation plus compatibility tests constrain the next change.
