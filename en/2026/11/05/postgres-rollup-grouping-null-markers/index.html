Which PostgreSQL ROLLUP rows are totals when source keys are null?

Use PostgreSQL GROUPING masks to distinguish source null categories from ROLLUP totals, retain row levels, and avoid summing mixed aggregation grains.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-05 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • Source nulls and omitted-dimension nulls can look identical; GROUPING distinguishes their levels.
  • The rightmost argument owns the lowest bit: included is zero, omitted is one.
  • Keep raw keys and mask identity, then select the intended level before using amounts.

A null key in ROLLUP output is not necessarily a total; it may come from an unclassified source value. PostgreSQL GROUPING identifies dimensions omitted from the current grouping set. Identify the grouping level before labeling subtotals and unknown categories.

Suppose one sales result contains region/product details, regional subtotals, and a grand total. Source rows can have unknown regions or products. Labeling every null region “all regions” misidentifies actual unclassified data. Using only the category keys as row identities can also overwrite a row from another level. First establish which grouping produced the row.

Several grouping levels share one result

The PostgreSQL 18 grouping-sets reference explains that ROLLUP includes the supplied expression list and each prefix through the empty grouping set. ROLLUP(region, product) groups by both keys, by region alone, and by neither key for the overall aggregate.

A grouping expression omitted from the current set is represented by null in that result row. A null product in a regional subtotal therefore means that this level does not divide by product, rather than that product data is missing. Source nulls can have the same visible value. Inspecting the value alone cannot distinguish these causes.

The Grouping Operations table defines GROUPING’s mask: an included expression has bit zero and an omitted expression bit one. The rightmost argument occupies the least-significant bit. GROUPING(region, product) is therefore zero for details, one for regional subtotals omitting product, and three for the grand total omitting both.

Preserve three different rows with the same null keys

This complete teaching SQL is unexecuted. Amounts are hypothetical and share one unit, not actual sales or financial results. The final input has two null keys specifically to test that it is not mistaken for a total.

WITH sales(region, product, amount) AS (
  VALUES ('north'::text, 'book'::text, 10),
         (NULL::text, 'book'::text, 20),
         ('north'::text, NULL::text, 5),
         (NULL::text, NULL::text, 7)
)
SELECT region, product,
       GROUPING(region, product) AS level_mask,
       SUM(amount) AS amount
FROM sales
GROUP BY ROLLUP(region, product)
ORDER BY level_mask, region NULLS FIRST, product NULLS FIRST;

The derived expectation is seven rows. Four detail rows have mask zero and amounts 10, 20, 5, and 7. Two regional subtotals have mask one: north is 15 and the unknown region 27. The grand total has mask three and amount 42. These are acceptance expectations from the stated input and documented rules, not database output.

Check the three rows whose keys are both NULL. They represent an unclassified detail worth 7, the unknown-region subtotal worth 27, and the grand total worth 42. Keep level_mask alongside raw keys in API and export data. A display label alone cannot preserve those identities.

Generate labels afterward: inspect whether a dimension is omitted, then name a source null “unclassified” only when that dimension still participates. COALESCE(region, 'total') renames both kinds of null. A real category could also be named “total,” so the label should not be the sole machine identity.

Does a source NULL make its GROUPING bit one?

No. The corresponding bit remains zero while the expression participates in the current grouping set. The detail worth 7 has two null keys and mask zero. The unknown-region subtotal omits product only, so its mask is one, without an additional bit for an unknown region.

GROUPING is not another null-value test. Its arguments are not evaluated as ordinary data values; the documentation requires them to match GROUP BY expressions exactly at the associated query level. If grouping uses an expression, refer to that expression rather than wrapping it in an unrelated display conversion.

The October 19, 2026 article on SUM with empty inputs and unknown amounts concerns whether aggregate inputs supply calculable values. Its default-value choices cannot identify which grouping level produced a row here.

Why should I not sum every returned amount?

The same input contributes at several levels. Details total 42, regional subtotals total 42, and the grand-total row is 42. Adding all seven amounts yields 126, not another sales total. A common column name does not give all its rows one additive grain.

Select mask zero for details or the appropriate mask-three row for the overall total. A SQL filter using GROUPING selects aggregate levels; removing source rows with WHERE region IS NOT NULL instead changes the amount being aggregated. It is not an equivalent way to remove total rows.

ROLLUP suits a declared prefix hierarchy. Explicit GROUPING SETS can select combinations that do not form that hierarchy. Avoid generating every combination and asking a client to guess its purpose. SELECT DISTINCT is not a substitute for level identity either: without the mask, distinct levels can have coincident keys and amounts and be collapsed incorrectly.

Can I reuse mask meanings after reordering GROUPING arguments?

No. The rightmost argument supplies the lowest bit, so reordering changes which dimension that bit identifies. Keeping the same region/product ROLLUP but switching to GROUPING(product, region) changes the bit representing omitted product. Fix the expression order and mapping in the interface, or version the change explicitly. A mask is not a universal identifier independent of its query.

Proposed verification compares raw keys, mask, and amount per row, including seven rows distributed four/two/one across levels. Shuffle inputs, replace an unknown region with a real category, and make values at different levels coincide. Check that pages and exports preserve their row identities. Verify 42 within each selected level rather than adding across levels. No database or interface test was executed, and no performance benefit is claimed. Give every row an explainable level before deciding where it belongs in the report.
