Why an OpenAPI discriminator does not validate your payment variant

Validate payment variants with explicit branch constraints in the pinned OpenAPI specification, separating discriminator mapping, oneOf exclusivity, and object closure.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-05 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • A discriminator must not change schema validation outcomes.
  • Branches must express tags, required fields, and extra-property policies.
  • Parent validation does not discover children; verify tooling and instances separately.

In OpenAPI 3.1.1, a discriminator cannot change a schema’s validation outcome. If a payment request must match one variant, the oneOf branches must constrain their own tags and fields. Mapping kind to a type and proving that an instance satisfies that type are separate checks.

Suppose a request supports a card token or a bank-account reference. An object says kind is card but supplies bank-transfer fields. Inspect the schema actually used for validation rather than treating the presence of discriminator as enforcement. This is a teaching contract, with no payment service or transaction executed.

Mapping does not add branch constraints

The pinned OpenAPI specification’s Discriminator Object section says a discriminator must not change validation results. oneOf, anyOf, and allOf provide the composition rules. A mapping cannot rescue an invalid instance or add a rejection absent from those rules.

Declaring cardToken or accountRef under properties does not make it required. If both permissive branches accept an object, oneOf should fail because exactly one branch must pass. That is a branch-design problem, not a failure to look up a mapping name.

Give each branch its own tag constraint and required fields. Mapping card to Card does not implicitly insert const: card into Card or require the tag.

A complete checkable document

This unexecuted OpenAPI document defines a Payment component and no callable endpoint. Both objects deliberately reject extra fields. A product that permits extensions needs a different closure policy.

openapi: 3.1.1
info:
  title: Payment variant example
  version: '1.0'
paths: {}
components:
  schemas:
    Card:
      type: object
      properties:
        kind:
          const: card
        cardToken:
          type: string
          minLength: 1
      required: [kind, cardToken]
      additionalProperties: false
    Bank:
      type: object
      properties:
        kind:
          const: bank
        accountRef:
          type: string
          minLength: 1
      required: [kind, accountRef]
      additionalProperties: false
    Payment:
      oneOf:
        - $ref: '#/components/schemas/Card'
        - $ref: '#/components/schemas/Bank'
      discriminator:
        propertyName: kind
        mapping:
          card: '#/components/schemas/Card'
          bank: '#/components/schemas/Bank'

Derived expectations are: a card tag with a nonempty cardToken passes; a bank tag with a nonempty accountRef passes. Missing tags, mismatched fields, missing required data, and empty strings fail. A card object carrying accountRef also fails, but that extra-field rejection relies on additionalProperties: false. Do not attribute it solely to oneOf or discriminator.

Record which branches pass and which constraints fail. A oneOf failure can mean no branch matched or several matched. The former might need required data; the latter might expose missing tag exclusivity. Constraint locations explain more than a selected type name.

Does a correct kind reject extra fields?

No. The object schema determines whether unknown properties are allowed. Remove closure from this example and an object with valid card data can carry extra fields while still satisfying exactly one branch. Fields do not become forbidden merely because their names resemble another variant’s properties.

If allOf reuses a base, review where closure applies. The October 21, 2026 article on closed objects and JSON Schema composition explains additionalProperties’ local scope. Do not solve rejected legitimate fields by silently permitting every unknown field, or assume inheritance-like names merge property declarations.

Choose composition from the contract. Mutually exclusive payment modes fit exactly-one semantics; composable capabilities may need at-least-one semantics. Changing oneOf to anyOf changes accepted inputs and needs compatibility checks with real callers, not merely fewer validation errors.

Will validating a parent discover its children?

Not through an allOf parent’s discriminator. The pinned specification explicitly says this form is useful for nonvalidation purposes: validating the parent does not search child schemas or include them automatically. List the alternatives that belong to the actual validation contract.

The specification also recommends requiring the property named by propertyName because behavior when it is absent is undefined. Both branches here require kind. A prose instruction to send it is insufficient if the schema still accepts omission, and one generator’s fallback is not a standard-mandated choice.

Separate instance validation from tool selection

First test Payment and its resolved references with the actual validator, dialect, and reference handling. Run the valid and invalid matrix. Then test the project’s OpenAPI tooling or generator for mapping, serialization, and errors. Preserve versions and inputs for both tracks. Schema success does not prove SDK selection, and SDK generation does not prove runtime rejection.

Locate validation relative to transformations. A framework may first construct a selected type and discard unrecognized fields. The resulting object is no longer the original mixed request. Preserve redacted input and the structure reaching the validator, and state which conversions the contract permits. Passing after silently removing fields does not prove the original request was valid.

Keep negative cases as branches evolve. Adding a bank property or removing a tag constant can change which branches accept an old request. Expected sets of matching branches reveal changes that a final boolean alone may conceal.

Application acceptance still needs the real service entry point, authorization, and persistent outcome. This schema cannot establish account existence, token validity, or permission to pay. No validator, client generator, or service was executed here. Make each invalid request correspond to a specific constraint, then verify that tooling honors rather than changes that contract.
