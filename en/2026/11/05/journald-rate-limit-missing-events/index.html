Missing journald events: inspect the service rate-limit window first

Investigate journald event loss through per-service windows, disk multipliers, unit overrides, and bounded numbered inputs.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-05 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • Window limits can leave gaps in failure diagnostics.
  • Burst alone does not predict an exact cutoff.
  • Suppression counts cannot reconstruct individual business events.

journald can drop a service's messages after its window limit is exceeded. Inspect effective limits, suppression counts, and the message path before concluding that the application never emitted a missing event. Rate limiting is a diagnostic branch requiring evidence, rather than an explanation for every gap.

Bursts can make failure evidence incomplete

The journald.conf manual states that a service exceeding RateLimitBurst within RateLimitIntervalSec has further messages dropped until the interval ends, with a message reporting the dropped count. Limits apply per service, so unrelated services do not simply share one combined allowance. The latest online manual was checked on November 5, 2026. No host settings were changed and no log burst was generated.

Imagine a report service repeatedly logging connection errors while an important task emits its own failure note. A missing note has several possible explanations: the branch never ran, application-level filtering, an unexpected output path, journal suppression, downstream forwarding loss, or an incorrect query. One page of journalctl results cannot select among them.

Start with event identity and the message path. Is there a checkable count at the sender? Does output go to standard output or another destination? Does it belong to the expected service and invocation? Does the query cover the relevant interval? Comparing counts with different units—such as lines versus events—can create an apparent loss that never happened.

Burst is not an exact cutoff by itself

The manual says the effective limit includes a factor derived from available disk space. A service's LogRateLimitIntervalSec or LogRateLimitBurst can also override global journal settings. A global Burst value of 1000 therefore does not establish that event 1001 must disappear. Window boundaries, service attribution, overrides, and disk conditions matter.

Sending 1001 messages and finding all of them does not prove limiting is broken; the actual allowance may not have been reached. Finding one missing message does not prove suppression either. Sender termination and query boundaries remain possible. Record conditions before choosing bounded inputs instead of increasing production traffic until something disappears.

Storage capacity and rate limiting also act at different points. Retention can remove older files, while window suppression can prevent new messages from entering the queryable record. Both produce missing results but require different observations. Raising a storage-size setting does not by itself repair window-based loss.

A bounded experiment in a dedicated service

A candidate sandbox experiment uses one dedicated service with fixed output path, level, and identity. Messages contain only a teaching run_id, sequence number, and event type. A separate sender counter records attempts and final exit status. That counter establishes attempted emission, not journal acceptance of every event.

Use two inputs. A low-rate case below the established effective allowance checks sequence completeness. A bounded burst checks visible sequence numbers, suppression reports, and recovery after the interval. Counts are planned inputs, not observations from a real host; actual limits must be chosen with the recorded overrides and disk conditions.

For example, a teaching plan might prepare fifty slow events and five hundred burst events, each tagged with the run identity. Whether that triggers limiting depends on sandbox configuration. Establish those conditions first rather than presenting these counts as production recommendations. Bound total volume and define a stop condition so the verification itself has an explainable resource cost.

Make the paper inputs explicit: global RateLimitIntervalSec=30s and RateLimitBurst=100, no unit LogRateLimit override, no other writers from the service, and a fresh independent window for the second case. Assume 64 MiB available for the journal. In the latest manual's table checked here, that falls in the up-to-256-MB multiplier-three bracket, giving a nominal budget of 100 times 3, or 300.

Fifty events fit below that paper budget even within one window; five hundred events in one burst exceed it, so inspect suppression and post-window recovery. The simplified 300-within-budget/200-excess split is an input calculation, not an observed cutoff. Real window attribution, emission errors, and additional messages still need checking. Do not reduce production free space to reproduce the assumed multiplier.

Save query parameters, service invocation identity, and time boundaries. Correlate visible sequence numbers and suppression counts. If no suppression is observed, report that result for the tested input; do not conclude that limiting is disabled. A suppression report likewise cannot assign an exact business identity to every missing message.

Can the dropped count restore a missing order event?

No. A count indicates suppressed input; it does not recreate message contents or necessarily identify the task concerned. It helps establish an evidence gap. Critical business state needs suitable durable records, rather than depending solely on a diagnostic message that can be suppressed.

This distinction belongs in incident language. “The service reported suppression, so logging coverage was incomplete” is defensible when observed. “Order A's failure note was dropped by journald” needs additional emission and identity evidence, plus exclusion of other explanations. Keep the hypothesis separate from the observation.

Should limiting simply be disabled?

First determine whether repeated noise consumed the allowance or necessary events exceed it. Consider summarizing repeated errors with counts and first/last times, keeping details within controlled bounds, then evaluating a per-service adjustment. Disabling a protection does not fix application filtering, output routing, or downstream storage, and may increase capacity pressure.

The manual allows either relevant setting to be zero to disable this limiting. That is a configuration capability, not a recommendation for this service. Balance diagnostic needs against storage and forwarding capacity, and verify the effective unit conditions after a change. A global edit can leave behavior unchanged when a unit override remains in force. No production limit is prescribed here.

The October 16 Docker logging-driver article asks which configuration a running instance actually uses. This article identifies a specific journal ingestion loss mechanism. Align emission, reception, retention, and query evidence before deciding to adjust the allowance.
