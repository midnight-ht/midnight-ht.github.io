Why does opening a second HTML popover close the first?

Compare auto dismissal, manual coexistence and nested exceptions with a complete HTML example.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-05 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • Independent auto popovers generally dismiss one another.
  • Manual coexistence needs explicit closure and useful layout.
  • A top-layer popover remains non-modal.

When two independent popovers use auto, opening the second generally closes the first. Choose the dismissal policy before debugging stacking. If the first element has been closed by native popover behavior, increasing its z-index cannot keep it open.

The HTML popover attribute reference distinguishes auto, manual and hint. Auto supports light dismissal, including clicking outside and Escape. Showing another independent auto popover generally closes an existing one, with exceptions for nested relationships. Manual permits multiple independent panels and requires explicit controls or scripts to manage visibility. These documented rules still need checking in the browsers a product supports.

Distinguish closure from coverage

Imagine a documentation page with “Field details” and “Export details” panels. Opening the second makes the first disappear. Check whether the first still matches :popover-open before assuming that the second is covering it. A closed element points to dismissal policy; a still-open but invisible element calls for a rendering and layout investigation.

This differs from inherited visibility and visible descendants. Open native popovers enter the top layer and escape the usual influence of ancestor position and overflow. That does not mean they stay open forever. Display order and open state are separate properties.

Auto can suit a task requiring one temporary explanation at a time. A new explanation replacing an old one may reduce clutter. But comparing two definitions requires a different contract: both independent panels must remain available. “Fix the disappearing panel” does not identify that choice clearly enough.

Compare auto and manual with two panels

This complete HTML teaching file has not been executed. It makes no requests and connects to no documentation service. Both panels initially use auto. Predict their mutual dismissal, then change both attributes to manual and compare coexistence and closing.

<!doctype html>
<html lang="en">
<meta charset="utf-8">
<title>Tool-panel dismissal policy</title>
<h1>Teaching documentation</h1>
<button type="button" popovertarget="fields">Field details</button>
<button type="button" popovertarget="exports">Export details</button>
<section id="fields" popover="auto">
  <h2>Field details</h2>
  <p>A record identifier distinguishes teaching records, not display positions.</p>
  <button type="button" popovertarget="fields"
          popovertargetaction="hide">Close field details</button>
</section>
<section id="exports" popover="auto">
  <h2>Export details</h2>
  <p>Export scope needs confirmation. This page does not export data.</p>
  <button type="button" popovertarget="exports"
          popovertargetaction="hide">Close export details</button>
</section>
</html>

Explicit close buttons become particularly important with manual. The implementation cannot rely on auto light-dismiss behavior. Changing only the attribute to prevent disappearance can leave users with accumulating panels and no obvious way to dismiss them.

Manual also does not position the panels for comparison. They may overlap at their default locations. Layout must make both useful, especially with long text, narrow windows, zoom and keyboard interaction. Two open DOM elements do not prove that users can compare their contents.

A large z-index is a failed remedy when auto has already closed the first element. Another poor repair immediately reopens every closed panel with showPopover: a user deliberately clicking outside may then find it impossible to dismiss. Choose a state that matches the task rather than fighting native behavior with a compensation loop.

Why can nested auto popovers coexist?

Independent and nested panels have different relationships. The reference explicitly permits nested auto cases, such as an explanatory panel opened from its parent menu. One nested example does not establish that arbitrary independent auto panels coexist. Nor should unrelated panels acquire an artificial parent-child relationship merely to evade dismissal.

Current documentation also describes hint. Showing a hint does not itself close auto popovers, but it manages other hints outside its ancestor relationships. Triggering through hover, focus or a click introduces conditions that still need inspection. Hint is not a universal switch for independent coexistence. The complete example here uses only auto and manual and makes no compatibility claim for hint.

Does a backdrop make a popover modal?

No. The Popover API overview says API-created popovers are always non-modal. Dimming the background does not prove that background interaction has been blocked. A task requiring a decision before users return to the page needs an actual modal-dialog design.

Modal focus entry and return covers that separate contract. Here the decisions are whether panels exclude one another, whether outside interaction dismisses them and whether users need simultaneous comparison. Similar visual presentation does not make those contracts interchangeable.

Proposed verification records opening order, each panel's :popover-open state and explicit closure. Add outside clicks, Escape and a nested comparison. Repeat after switching to manual and check whether both contents and close controls remain usable. Retain the browser version and observed results. This example has not been run; it is not a cross-browser pass report. A written dismissal policy gives a team a basis for deciding whether disappearance is expected or defective.

What stays open after comparison ends?

Imagine comparing two definitions and their units. Auto dismissal makes users remember the first definition while opening the second. Manual coexistence removes that particular cost, but it does not decide whether old panels should survive navigation to another record.

Bind contents to an explicit record identity. On a record change, either close stale panels or update their titles, contents and actions together. Replacing text while leaving an old action target is unsafe. If comparison intentionally spans two records, label both identities instead of letting one global current-record variable control everything. This is a proposed interaction contract, not user-research evidence.

Closing scope also matters. “Close field details” closes one panel; “Close all tools” closes both. If open preferences are remembered, distinguish remembering a tool type from retaining an old record's contents.

The attribute choice therefore includes task duration. Temporary explanation may disappear with other interaction; sustained comparison needs an explicit ending and object boundary. Simultaneous DOM visibility alone does not establish a useful comparison workflow.
