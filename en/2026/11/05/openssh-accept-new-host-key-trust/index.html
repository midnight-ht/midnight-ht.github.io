OpenSSH accept-new removes the prompt—who verifies the first host key?

Separate OpenSSH first-use trust from changed-key detection and plan independently verified known_hosts material for deployment.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-05 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • accept-new records new keys and refuses changed known keys.
  • keyscan collects material without authenticating it.
  • Controlled deployment needs trusted inputs and a rotation process.

OpenSSH accept-new saves a new host key automatically and rejects changed keys for known hosts. That comparison does not independently authenticate the key received on first contact. Unattended deployment needs a trusted source for host identity as well as a way to avoid interactive prompts.

First contact and a changed known key are different branches

The OpenSSH ssh_config manual says that StrictHostKeyChecking=accept-new automatically adds new keys but refuses changed host keys. With yes, new keys are not added automatically and changed keys are refused. The current OpenBSD manual was checked on November 5, 2026. No SSH connection was made and no remote key was changed.

Suppose a CI job first connects to a deployment host with an empty user known-host file and no matching baseline supplied by a global database, host-certificate trust, or another effective source. accept-new can save the key received without asking an operator. A later connection using that saved record has a comparison baseline and can reject a different key. The first record, however, still came from that initial network interaction. Automatically saving it does not correct a mistaken identity at first contact.

First-use trust can be a deliberate choice in an environment that accepts that boundary. It supplies continuity and helps detect later changes. It should not be described as independent identity verification. Ask separately where the original authentic key came from and whether subsequent jobs read the same controlled baseline.

Why ssh-keyscan does not authenticate the first answer

The ssh-keyscan manual explicitly states that it cannot verify the authenticity of collected keys. A network attacker able to intercept traffic may substitute a key. Collection supplies material to check; it is not itself the check. Writing the output directly to known_hosts saves the answer received over that path.

A problematic deployment pattern scans on every run, overwrites the known-host file, and then declares verification enabled. The client may compare against the file, but its baseline has just been replaced through the same unauthenticated path. That erases the previous evidence that could have exposed a changed key.

An independent source might be a controlled server console, an authorized administrator, or an established secure distribution process. Choose according to the actual environment. This article supplies no invented working fingerprint and does not assume that forwarding an unverified message creates an independent source. Check the target identity, relevant port, algorithm, and key or fingerprint; an authentic fingerprint for another machine is not evidence for this one.

Inputs for a controlled deployment job

This unexecuted example uses the reserved teaching domain example.invalid. trust/known_hosts must contain independently verified material; no real entry is supplied. The command is assumed to run from the directory containing trust so that the relative path has an explicit interpretation.

Host deploy-demo
    HostName deploy.example.invalid
    User deploy
    StrictHostKeyChecking yes
    UserKnownHostsFile ./trust/known_hosts

A proposed invocation saves the configuration as ssh-demo.conf and uses ssh -F ./ssh-demo.conf deploy-demo. User-authentication credentials and server-side permissions are separate prerequisites. The fragment does not promise a successful login. yes requires host checking against established trust material; it does not grant deployment authorization.

Record versions, provenance, and ownership for the configuration and known-host material. Ensure the job can read them and that untrusted changes cannot redefine them. Inspect effective client configuration to verify alias matching, destination, and file path. Check additional sources such as GlobalKnownHostsFile and KnownHostsCommand too; an empty user file alone does not establish an empty client trust baseline. A file existing in the repository does not prove the invoked client reads it; other configuration or arguments may change the inputs.

Use an owned isolated SSH endpoint to test matching, unknown, and changed-key cases. A matching host key should pass host checking, while later user authentication may still fail independently. With yes, an unknown key should not be silently added. A changed known key should not be “fixed” by deleting the record during the test. Preserve target and trust-material identities, and do not attribute every nonzero exit to host verification.

What if CI starts with an empty file every time?

Then accept-new sees first contact on every run only if no other effective trust source supplies a matching baseline. The previous baseline is absent. Destroying a container or cleaning a workspace can have the same effect. The option name stays unchanged while the conditions supporting continuity disappear. Cross-run comparison requires a baseline that is actually retained or distributed and read by the later job.

Assign ownership to that material. A controlled repository or configuration system can distribute verified records, with restricted modification and changes tied to authorization. Indefinite caching is not the complete answer either: legitimate host rebuilding or rotation needs a reviewable update process.

Can a rebuilt server's old record simply be deleted?

Verify the new key and the rebuild through an authentic source first. Deletion reopens first-use trust; it does not establish that the change was legitimate. Identify the host, affected names or ports, authorized change, and source of the new fingerprint before distributing a replacement baseline. No public target needs to be scanned or changed for this teaching exercise.

If impersonation is suspected, investigate the actual exposure rather than just removing the warning. A server public key and a user's private credential are different objects. Updating known_hosts does not revoke a leaked login credential. The October 9 credential-revocation article addresses that neighboring responsibility, rather than replacing host-identity verification.

Choose according to the stated risk. A temporary environment accepting first-use trust must preserve its later baseline and acknowledge first-contact uncertainty. A controlled deployment job can provision verified records and use yes to reject unknown or changed hosts. In either case, record real verification results instead of treating an absent prompt as completed security acceptance.
