Why does the later CSS layer lose after adding important?

Use three buttons to distinguish normal, important and unlayered declarations and plan a bounded layer migration.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-05 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • Normal and important declarations use opposite layer order.
  • Layered important beats unlayered important in the same origin.
  • Reopening a named layer does not reorder it.

Within one origin, normal declarations favor later layers while important declarations reverse layer precedence. Check layer membership before increasing specificity. If app originally overrides vendor but loses after both declarations become important, the cascade may be behaving exactly as specified.

The MDN @layer reference establishes layer order at initial declaration. Later layers have precedence for normal declarations; important declarations reverse that order. Unlayered normal declarations outrank layered normal ones, whereas layered important declarations outrank unlayered important ones. This article compares author declarations, not the entire ordering of user styles, animations and transitions.

List the competing declarations

Suppose a page establishes vendor and app layers, then adds rules to them from separate files. Reopening vendor does not move it after app. The end of a file and the position of a layer in the cascade are different things.

For a disputed color, collect declarations matching the same element, their origin, importance and layer membership. Compare specificity and subsequent tie-breakers only at the appropriate point. A longer selector does not necessarily overcome a layer boundary.

That differs from a hidden ancestor with a visible child. An ancestor's stronger declaration is not a direct declaration on its child. Here both declarations can match the same button while occupying different layers. Both failures may look like ineffective specificity, but their mechanisms differ.

Compare three buttons

This unexecuted teaching file separates normal layered declarations, important layered declarations and important declarations inside and outside layers. The colors identify their source; they are not a product status design or a contrast assessment.

<!doctype html>
<html lang="en">
<meta charset="utf-8">
<title>Cascade layer comparison</title>
<style>
@layer vendor, app;
@layer vendor {
  [data-case="normal"] { color: maroon; }
  [data-case="flagged"] { color: maroon !important; }
  [data-case="outside"] { color: maroon !important; }
}
@layer app {
  [data-case="normal"] { color: navy; }
  [data-case="flagged"] { color: navy !important; }
  [data-case="outside"] { color: navy !important; }
}
[data-case="outside"] { color: green !important; }
</style>
<button data-case="normal" type="button">Normal declarations</button>
<button data-case="flagged" type="button">Layered important</button>
<button data-case="outside" type="button">Layered versus unlayered important</button>
</html>

The documented rules predict navy from app for the first button and maroon from vendor for the second. The third also favors vendor's layered important declaration over unlayered green. These are predictions, not computed styles captured in a browser. Verification should record computed color together with matched and overridden declarations.

If only app becomes important while vendor stays normal, app wins on importance. “The first layer always wins” is therefore also wrong. Preserve the importance condition on both sides instead of applying a mnemonic to unrelated cases.

Identical selectors isolate the relevant conditions. A later experiment can give vendor's normal declaration higher specificity and observe why app's later layer can still prevail. Such a comparison explains ordering; it does not recommend continually lengthening selectors in an application.

Where should important declarations live during migration?

Putting ordinary third-party styles in vendor and ordinary application overrides in a later layer can reduce selector competition. But the actual import must put those rules in that layer. Existing unlayered normal rules can still override layered normal rules. Merely naming a layer in documentation does not classify the project's CSS.

Inventory existing important declarations separately. Moving an entire library into the first layer can make its important rules harder to override. Record which exceptions are necessary, who owns them and whether unnecessary importance can be removed. A migration intended to simplify normal overrides should not accidentally strengthen another group of declarations.

Choose a structure around maintenance responsibilities. A new project can begin with a few stable layers. An existing project can migrate one component, compare its matched declarations and computed results, then expand. A limited, verifiable change is easier to assess than an unsupported claim that all styles are now organized.

Does reopening an old layer move it to the end?

No. The reference permits adding rules to an existing named layer without changing its order. Investigate initial establishment when the overall order is wrong. Rules added inside that layer still participate in its internal cascade; fixed layer order does not make later declarations irrelevant.

Unlayered important is not a universal last override either. Within the same origin, it follows layered important declarations. Teams relying on a final unlayered important rule should test the third comparison rather than assuming that physical placement gives it precedence.

Proposed verification starts with the three buttons, changes importance on one side, reopens an existing layer and finally introduces a real library import. Change one condition at a time and retain origin, importance, layer, matched declarations and computed values. None of these checks has been executed here. A correct color also does not validate the component's reading, state and interaction behavior. The related box-model sizing contract shows why one correct CSS property cannot establish an entire task's correctness.

Explain a color change during a partial migration

Suppose both a legacy library and its higher-specificity application override are unlayered. Moving only the override into app can make it lose: the remaining unlayered normal library declaration outranks layered normal declarations. Making app later does not solve that boundary. Record partial migration as its own condition.

Moving the library into vendor changes ordinary competition again, but important declarations need their own inventory. One ordinary button screenshot cannot validate disabled, error or loading rules from different files and importance levels. Identify actual competitors per property and state.

Assign ownership of initial layer order too. Independently loaded style blocks that first establish layers in varying sequences can make ordering difficult to explain. A stable entry point can declare the intended names before later files append rules, subject to the actual build and delivery system.

No build or browser test was run here. A reviewable migration should identify the old winning declaration, the new winner and whether the change came from layered versus unlayered placement, importance or another condition.
