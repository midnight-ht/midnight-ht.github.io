WCAG custom switches: why does green still sound like off?

Use a notification switch to separate accessible state, stable naming, keyboard activation and unsaved preferences.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-05 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • A name identifies the setting; state exposes its current value.
  • Native activation and custom state synchronization have separate responsibilities.
  • Local rejection demonstrates an unsaved draft, not a backend test.

Changing a custom switch to its on color does not expose its new state to assistive technology. Check the name, role and current state on the same control. If notification settings look enabled but a screen reader still reports off, another color adjustment will not resolve the disagreement.

WCAG 2.2 Understanding Name, Role, Value requires programmatically determinable names and roles, support for programmatically setting user-settable states, properties and values, and notification of changes to user agents, including assistive technology. This is not a prescription to attach identical ARIA attributes to every element. Using a native control according to its specification and inventing a custom control involve different responsibilities.

Decide what the control represents

“Receive teaching notifications” can be a switch with on and off values. It changes a preference rather than selecting a record for a batch operation. The APG Switch Pattern restricts switches to binary input. A partially enabled or inherited setting needs an interaction that expresses its actual alternatives.

The name identifies the setting; the state expresses its current value. Renaming “Receive notifications” to “Stop notifications” while reporting on can make it unclear what is enabled. APG requires a switch label to remain unchanged across state changes. “Receive teaching notifications, on” gives a stable object and a changing value.

This extends the issue in including visible labels in accessible names. A correct name can identify a setting without exposing whether it is enabled. Conversely, an accurately exposed state without a name leaves users guessing which preference they changed.

A complete teaching example without a backend

This file has not been executed. It connects to no notification provider. A native button supplies button activation behavior, while the switch role and checked state express the setting. Saving invokes a local function deliberately written to reject. That is an instructional branch, not an observed API failure.

<!doctype html>
<html lang="en">
<meta charset="utf-8">
<title>Teaching notification preference</title>
<button id="notice" type="button" role="switch"
        aria-checked="false">Receive teaching notifications</button>
<p id="state">Current draft: off; not saved</p>
<button id="save" type="button">Save teaching draft</button>
<p id="result" role="status"></p>
<script>
const find = selector => document.querySelector(selector);
const text = (node, value) => { node.textContent = value; };
const toggle = find('#notice');
const state = find('#state');
const result = find('#result');
let enabled = false;
function render() {
  toggle.setAttribute('aria-checked', String(enabled));
  text(state, `Current draft: ${enabled ? 'on' : 'off'}; not saved`);
}
toggle.addEventListener('click', () => {
  enabled = !enabled;
  render();
  text(result, '');
});
async function rejectLocallyForTeaching() {
  throw new Error('Local teaching rejection; no request was sent');
}
find('#save').addEventListener('click', async () => {
  try {
    await rejectLocallyForTeaching();
  } catch {
    text(result, 'Teaching save incomplete; the selection is still an unsaved draft.');
  }
});
render();
</script>
</html>

The example preserves the unsaved draft after rejection. The switch still reports the editable value users see; separate text explains that it has not taken effect. A real product may instead restore the server-confirmed value. If it does, it must restore visible and exposed state together and explain the rollback.

Activation is another responsibility. Native buttons have keyboard activation behavior, so this example handles click without also implementing a second Space-key toggle. Toggling on both a key event and the resulting click can reverse the value twice. A div does not acquire keyboard behavior merely by receiving a role.

Why one attribute is insufficient

A common failure changes only a green CSS class, leaving aria-checked false. Another exposes true but provides no stable name to distinguish four similar controls. Inspect identity, state and behavior on the same element rather than reviewing disconnected CSS and ARIA screenshots.

A checkbox implementation is also reasonable. APG includes a checkbox-based switch; that variant uses native checked state rather than maintaining a competing aria-checked value. Choose a role that matches the meaning and visual design. A slider-shaped illustration alone is not a reason to replace native form behavior.

Proposed checks begin with off, then activate using a keyboard and verify the unchanged name, the new on state and the visible draft text. Toggle off again, then enable it and trigger the local rejection. Check the failure explanation alongside the retained draft. An accessibility-tree inspection provides evidence about name, role and value; actual announcement timing needs the supported browser and screen-reader combinations. None of these runtime checks has been performed for this article.

Does a reported switch state replace a save-failure message?

No. The switch reports an editable value; the message reports the result of saving it. On does not mean the server confirmed on. Preserve the draft or roll it back according to an explicit contract, and communicate that decision. A real pending request also needs rules for further editing and for older responses arriving after newer choices.

After a real successful save, read the confirmed preference and compare it with the visible and exposed values. That requires an actual interface and persistence check, which the teaching file does not implement. Establish the relationship between draft and effective values, then verify what the control is called, what kind of control it is and what value it currently holds.

Should a late initial read replace an edited preference?

Suppose the confirmed preference has not arrived and the page temporarily shows off. If off is only a placeholder, it must not masquerade as the user's actual setting. A product can wait for the read before enabling editing, or permit editing while defining whether a late read may overwrite the draft.

If users enable notifications while waiting and an older read then reports off, blindly applying it loses their choice. Updating only color creates a second disagreement with exposed state. Editing during loading needs a dirty-draft condition or record-version rule for accepting results. This is design reasoning, not an executed race test.

Waiting before editing is simpler but needs a comprehensible loading state and recovery if reading fails. Saving an unknown value as off can overwrite a genuinely enabled preference. Separate unknown, loaded, edited and confirmed states so tests know which value the switch represents.

Account or record changes add identity: a previous preference must not remain authoritative simply because the button node was reused. A stable name identifies the setting; record identity identifies whose setting is being changed.
