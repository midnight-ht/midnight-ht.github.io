Why does a Go Context keep only one cause when several cancellations race?

WithCancelCause lets Go callers attach a reason to cancellation, but it is not a list: the first effective cancellation determines a Context's Cause. Separate control-flow cancellation from multi-cause diagnosis.

Key takeaways

  • Context.Err reports a general cancellation state, while context.Cause returns the first effective specific cause.
  • When parent and child cancellations race, a Context does not automatically accumulate every reason.
  • Record structured events separately if you need multiple candidate causes; do not treat Cause as an audit history.

Go's WithCancelCause lets a caller attach a reason to cancellation, but context.Cause(ctx) is not a collection of reasons. One Context retains the first cancellation outcome that affects it. If a parent deadline, client disconnect, and local policy cancellation happen around the same time, the Cause depends on which cancellation reaches that Context first. ctx.Err() and context.Cause(ctx) answer different questions: the former says the Context is cancelled; the latter provides a specific cause. Treating Cause as a complete failure record turns a concurrent race into a misleading single-cause diagnosis.

Why can the two cancellation queries return different values?

The older Context API uses Err for general states such as context.Canceled or context.DeadlineExceeded. WithCancelCause adds a path for the caller to provide a specific error. After cancellation, Err() remains useful for control-flow decisions, while context.Cause() returns the attached reason. Code can therefore use errors.Is(ctx.Err(), context.Canceled) to decide whether to stop and log a more specific “client disconnected” or “quota reached” cause. The cause does not change the fact of cancellation, nor does it automatically carry every failure from the upstream call chain.

Go's implementation has an important first-cancellation rule. For a derived Context, whichever parent or child cancellation takes effect first determines the relevant Cause; a later cancellation does not append itself to a list. If the parent cancels first, a child generally inherits the parent's cause. If the child has already been cancelled with its own cause, a later parent cancellation does not replace it. This semantics suits a one-time control-flow stop, not a complete diagnostic model for several failing dependencies.

A hypothetical race: a disconnect arrives near a deadline

Imagine an HTTP handler creates a cause-aware Context for a downstream RPC and also watches for a client disconnect and an internal deadline. One request disconnects near the deadline. If the disconnect callback calls cancel first, the Context's Cause may be “client left.” If the timer wins, it may be the deadline error. Only the winning first cause appears on that Context in that run. Logging Cause is useful, but it does not prove that the other condition never happened; it only means that condition did not become this Context's termination cause.

A clearer design separates the “control-flow winner” from “events observed.” A Context cause can select one reason for stopping work. A separate structured log or span event can record that the deadline fired, that a disconnect was observed, and which downstream dependency returned. Each event can include a timestamp, request ID, and source, allowing later diagnosis to distinguish the reason that first stopped the task from other signals that occurred around it. This is a design illustration, not a production trace.

How can parent and child causes be made predictable?

Define the cancellation policy first. Must a cancelled parent request override a local failure? Should a local quota stop only one child task? Should a timeout map to a retryable state? These are business contracts; the API does not choose them. With parallel children, let each child's Context express its own stop reason and collect multiple errors in the aggregate result. Do not expect one parent Context Cause to record every child failure. Go's cancellation-cause API and error-aggregation tools such as errors.Join have distinct responsibilities.

Cancellation causes also affect error classification. Calling a client disconnect an internal service failure creates noisy alerts. Collapsing a server deadline into user cancellation can hide a rising timeout rate. Stable cause types or sentinel errors can define semantics; log details can remain variable. Avoid putting raw request parameters, credentials, or personal data in cause text. A cause can be propagated through a Context whose lifetime extends beyond one call stack, so diagnostic text must follow privacy and retention rules.

How do you verify first-wins without testing scheduler luck?

Write deterministic unit tests that cancel parent and child in a controlled order. In one test, cancel the parent first and assert the derived Context's Err and Cause. In another, invoke the child's cause-aware cancel first and then cancel the parent, confirming that the child cause is not replaced. For a concurrent race, do not assert that the scheduler always chooses one particular cause. Assert that the Context is eventually cancelled, that its Cause belongs to the expected candidate set, and that the separate event records preserve both observations. Also test the semantics of passing nil to the WithCancelCause cancellation function and the classification of deadline versus cancellation errors.

Finally, inspect how callers consume the result. If code checks only Cause != nil and retries based on its text, it has made a string into an unstable protocol. If the system does not record request IDs and child errors, Cause cannot reconstruct the full event chain. Use Context to propagate a stop signal, and use return values and observation events to aggregate outcomes. This article checked API semantics against Go's official source; no concurrency test or live service was run. Confirm behavior against the Go version used by the project.

Also avoid placing a mutable, cross-request error object in the cancellation cause. If multiple goroutines hold the same wrapper and mutate its fields after cancellation, a later log read may differ from the state at the cancellation instant. First-wins constrains which cancellation stores the Cause; it does not freeze mutable fields inside the error object. Prefer an immutable sentinel or independently constructed error, and record changing details as timestamped events. Classification then remains stable while logs can still preserve later observations of a deadline, disconnect, or dependency failure without implying that each became the termination cause.

One more boundary is easy to miss: cancellation is cooperative. Calling cancel closes Done, but it does not forcibly interrupt a function already running. A dependency stops only if it checks the Context, uses Context-aware I/O, or listens to Done itself. Cause therefore describes which stop signal won in the Context tree; it does not prove that a remote request was withdrawn, a database transaction rolled back, or a goroutine exited. Record cancellation requests, dependency responses, and work completion separately when cleanup timing matters. A test can make a fake dependency report that it exited after observing Done, then verify that the caller waits for cleanup; merely asserting that Cause is set does not establish resource release.
