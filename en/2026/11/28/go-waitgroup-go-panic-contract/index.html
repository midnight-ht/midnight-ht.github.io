Why must a Go 1.25 WaitGroup.Go function still not panic?

Go 1.25 WaitGroup.Go couples goroutine startup with task accounting and marks the task done when the function returns. It does not provide error collection or panic recovery.

Translations
zh-CN en

Article

Key takeaways

  • WaitGroup.Go calls f in a new goroutine and removes the task from the group when f returns.
  • The documentation requires f not to panic; the Go 1.25 method is not panic containment.
  • Starting work on an empty WaitGroup must happen before Wait; callers still own error and panic policy.

Go 1.25 sync.WaitGroup.Go(f) couples launching a goroutine with task accounting: when f returns, the task is removed from the group. It saves the manual Add(1) and defer Done() pairing, but it does not collect errors, recover panics, or isolate tasks. The official documentation explicitly requires that the function not panic. If the work may panic, define who recovers it and how failure is reported before choosing Go directly.

It handles counter lifetime, not full task supervision

The older pattern makes the caller increase the counter before starting a goroutine and call Done() on every return path. Forgetting a defer or returning early can make Wait() block forever. Calling Done() more than once can drive the counter negative and panic. WaitGroup.Go puts “task starts” and “task ends when its function returns” in one method, reducing these pairing errors. The standard-library documentation recommends preferring the method and marks it as added in Go 1.25.

But a WaitGroup answers only whether tracked tasks have ended. It does not hold task return values because f has no return type, and it does not define how multiple errors should be combined. It does not cancel other goroutines, limit concurrency, recover a panic, or guarantee successful side effects. Interpreting Wait() returning as “every child task succeeded” confuses a counting barrier with a task-result protocol.

Why does the panic requirement matter?

The documentation says that f must not panic. An unrecovered panic in a goroutine generally takes the process down a panic path; the WaitGroup counter lifecycle does not turn it into an observable error. WaitGroup.Go does not automatically provide isolation semantics such as “one worker panics, the others continue, and the caller receives an error slice.” If the team expects local failure, leaving panic behavior undefined is not a complete failure policy.

Imagine a batch job uses wg.Go(func() { process(record) }) and calls wg.Wait() afterward. Parsing one record encounters a nil pointer and panics. A developer might expect the WaitGroup to decrement and return a structured failure to the caller. The method documentation only describes removing the task when f returns and explicitly excludes panic. If the panic is not recovered, it can terminate the process; the caller gets no structured error to inspect. This illustrates a risk, not a run of a real batch job.

Define panic and error boundaries explicitly

If a function can return a normal business error, have each task store it in a synchronized result slot or send a result through a bounded channel. After waiting, aggregate errors according to the business rules. If a panic must become a local task failure, recover it at the boundary inside the same goroutine and pass the stack, task ID, and recovered error to the caller. recover works only in a deferred function, and it should not conceal a broken runtime invariant or pretend that process state is safe.

A worker pool also needs a separate concurrency limit, cancellation policy, and queue backpressure. A WaitGroup does not limit the number of goroutines. Acquire a semaphore before starting work; on cancellation, stop submitting and wait for already-started tasks. Whether one task failure should stop the others is a business decision unrelated to counting. If you need cancellation and error aggregation, compare a higher-level abstraction such as errgroup, but read its own error and cancellation contract rather than assuming it swallows panics.

Go and Wait ordering still have rules

When the WaitGroup counter is zero, Go must be called before Wait. If the group is already non-empty, the documentation allows a task to call Go from another goroutine. When reusing one WaitGroup for several independent task sets, the previous Wait must return before the next set of calls to Go. Starting work only after an empty group has begun Wait can make a caller think the wait includes the task when the synchronization contract does not say that.

Compared with Add/Done, the method ties startup to counting but does not remove lifecycle constraints for a shared WaitGroup. A WaitGroup must not be copied after first use, and task-start locations still need to be visible to the surrounding concurrency policy. Test zero tasks, startup before waiting, nested task startup, group reuse, normal errors, and the panic boundary—not just that Wait eventually returns.

When should you use Go, and when keep Add/Done?

When a work function will not panic, the caller only needs to wait for a set of launched tasks, and an outer layer controls concurrency, WaitGroup.Go can reduce boilerplate and counter-pairing mistakes. Add/Done may still fit when a goroutine is created elsewhere and must be registered independently from its execution function. If the system needs returned errors, sibling cancellation, or a concurrency limit, use a coordinator with an explicit contract instead of expecting a WaitGroup to perform work it does not provide.

This article checked the method's introduction, panic requirement, and lifecycle rules against the Go 1.25 release notes and standard-library documentation. No concurrency experiment was run. Confirm the project's minimum Go version, error and panic policy at each call site, and whether a WaitGroup is reused across phases. A shorter method does not make the task boundary safe automatically.

The method also does not provide a timed wait. Wait() blocks until the counter reaches zero; it takes no Context and does not cancel work when a deadline expires. If tasks may hang on network calls, pass a Context into the work, configure client timeouts, and manage cancellation and cleanup separately. Wrapping Wait() in another goroutine and selecting on a timer only stops the caller from waiting; it does not stop the underlying tasks. Track goroutine completion, external side-effect state, and the WaitGroup count separately.

The result should not be reduced to one aggregate error without a storage contract. If several tasks write into one slice, establish synchronization explicitly. One simple design preallocates result slots by input index, lets each goroutine write only its own slot, and has the caller read them in order after Wait returns. For a very large task set, retaining every full error may exhaust memory; define a first-error rule, an error cap, or a back-pressured result channel, including who closes it. A WaitGroup does not choose data ownership or capacity policy. If input contains duplicate records, indexed results preserve both occurrences, while a map keyed only by record ID may overwrite one. That choice belongs to the result contract, not the counter.
