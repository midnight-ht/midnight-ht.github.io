Why does the same iframe service see different cookies on two sites?

A CHIPS Partitioned cookie is isolated by top-level site, so one embedded service can have separate state on two sites. It supports per-site continuity, not a shared cross-site login cookie.

Key takeaways

  • A partitioned cookie's state is distinguished by both its setting origin and the top-level page origin.
  • An embedded service gets a separate cookie jar under different top-level sites.
  • Cross-site account linking still needs an explicit top-level authentication or user-authorized flow; a shared third-party cookie cannot provide it.

CHIPS Partitioned cookies are stored separately by top-level site. The same third-party iframe service embedded on shop.example and news.example may therefore read different cookie state in each context. The browser distinguishes the cookie using both the origin that set it and the top-level page origin. This can preserve per-site continuity for an embedded chat, map, or configuration service without creating one third-party identity cookie shared across every website. If users need cross-site identity, design a separate account-linking or top-level authentication flow.

Partitioning changes what “the same cookie” means

An unpartitioned third-party cookie could let one embedded service read the same state across unrelated top-level websites. CHIPS double-keys the state: the setting origin and top-level page origin together identify the isolated context. MDN describes the behavior as a separate cookie jar per top-level site. The embed's domain being identical does not mean that the same cookie value is shared across sites.

For example, widget.vendor.test may write a partitioned theme=dark state while embedded on store.example. That does not mean it can read the value on forum.example; the second top-level site has its own partition and may have no state on first visit. If the service interprets “no cookie” as “anonymous user,” it may create a second state. If it treats the partitioned cookie as a cross-site login credential, it crosses a security and product boundary. Partitioning solves state isolation, not account identity.

Hypothetical case: an embedded chat keeps unread state per site

Suppose the same chat provider is embedded on three customer websites. A user dismisses a hint on site A but may still see it on site B because each top-level site has a separate cookie jar. That isolation may be appropriate for per-site unread counts, interface preferences, or temporary session state. The provider does not need a cookie readable across unrelated sites to correlate activity.

If the product needs a user to sign in to the provider and synchronize conversation history across all three sites, CHIPS will not create that account link automatically. The user can choose to open the provider's top-level site, sign in, and then use an explicitly authorized callback or server-side association to connect the account to the customer site. Do not infer “the same browser means the same user” from a partitioned cookie, and do not quietly send partition identifiers to a central server to stitch a cross-site profile. This is a product-flow illustration, not a tested federated-login implementation.

Cookie attributes and compatibility still matter

MDN's CHIPS guide explains the Partitioned attribute and the double-keying goal. Actual cookie creation must still follow security attributes and browser rules. For cross-site use, check Secure and the relevant SameSite setting against current browser documentation and test the target browsers. Adding the string Partitioned alone does not prove identical behavior everywhere. Privacy settings, third-party-cookie policies, and the embedding context can affect whether a cookie is accepted or sent.

The server should treat a partitioned cookie as state for its current context, not as a trusted authorization fact. Authorization still comes from a verified login session, signed token, or server-side account relationship. If a partitioned value is copied to another site or submitted by a client, the server must not trust it as cross-site identity. CSRF, session fixation, and cookie-scope protections still need to follow the application's protocol.

How can you verify that two top-level sites are isolated?

In the target browser, create two distinct top-level sites that both embed the same third-party origin. Have the iframe write different random values in each context, then switch sites and read them back. Inspect cookie attributes, request headers, iframe origin, and top-level origin in developer tools. Also test a fresh profile, pre-existing unpartitioned cookies, a user setting that disables the capability, and cross-device sign-in. Record browser version and privacy settings because support can change.

Failure patterns include assuming a value written under site A is automatically readable under B; silently falling back to an unpartitioned cookie; treating missing state as account logout; or sharing a user-specific response across top-level sites in a cache. Design application cache keys and server-side session associations with the top-level partition in mind so two partitions are not collapsed into one identity.

When is CHIPS suitable, and when is top-level identity needed?

CHIPS fits an embedded component that needs settings, temporary session continuity, or abuse-prevention state within each customer site without sharing state across unrelated sites. If the product truly needs account continuity across top-level sites, use explicit top-level login, user consent, and controlled account association. Do not treat partitioned cookies as a general replacement for third-party cookies or as authentication that works in every browser.

This article follows MDN's CHIPS guide for top-level partition semantics; no browser compatibility test was run. Before rollout, validate writing, isolation, and transmission with the target browsers and privacy settings and audit the cookie's data use. A readable attribute does not authorize cross-site identity linking, and partitioning does not replace authorization, consent, or retention policy.

Align the product's domain assumptions with the browser's definition of a top-level site. shop.example and admin.shop.example are not necessarily treated like two completely unrelated partitions; do not design identity state solely from whether hostname strings differ. Cross-site behavior follows browser site semantics, including schemeful-site rules, so test the target browsers. Cache keys, server logs, and analytics should not attribute one partition's preference to another organization or user.

Related reading: the site’s exact OAuth redirect URI matching. An explicit authentication flow provides an identity-linking checkpoint, but does not make CHIPS share cookies across top-level sites.

The product should define what happens when a user clears site data or moves to a new browser profile. A partitioned preference can disappear without the provider account being deleted; recreating it should not silently create a new identity link. Conversely, a user may authenticate at the provider's top-level site but still have no partitioned state for a customer embed until that context is visited and the browser accepts the cookie. Document those as separate states in the sign-in and support flow, and avoid using a missing partition key as a signal to merge records across sites.
