Why can an S3 key get a new version while Object Lock is enabled?

S3 Object Lock protects a specified object version, not a frozen key name. New versions and delete markers can still change the current view; audit version IDs, retention modes, and permissions.

Key takeaways

  • Object Lock applies retention or a legal hold only to the object version specified in the request.
  • It requires S3 Versioning but does not prevent new versions or delete markers from being created.
  • A key being invisible and a protected old version being destroyed are different states.

S3 Object Lock protects a specified object version; it does not permanently freeze an object key. AWS documentation says Object Lock works only in a bucket with versioning enabled, and a retention period or legal hold protects only the version specified in the request. It does not prevent another version from being written to the same key, nor does it prevent a delete marker from being added above an object. Therefore “the current key no longer shows the object” does not prove that an older version was destroyed. “One version is protected” also does not prove that the current content seen by a caller is that version.

A key is a name; a version is the retention unit

In a versioned bucket, repeated writes to one key create different version IDs. Object Lock retention metadata attaches to a specific version. A bucket's default retention can give newly written versions a default period, but individual versions may have their own retain-until dates, governance or compliance modes, and legal holds. If an audit records only reports/monthly.csv without a version ID, it can conflate several objects with different dates and retention states.

AWS also documents that a PUT to a key with an existing protected version creates a new version while the old version remains locked according to its existing configuration. The new version does not automatically inherit the old version's protection unless a new setting or bucket default applies one to it. As a result, the same key may point to a protected historical version and a newer unprotected version at once. A console view or an unversioned GET that shows the current version cannot replace a per-version review.

Hypothetical timeline: a delete marker appears above a protected object

Suppose version A of archive/receipt.json has a 30-day retention period. An operator issues a simple DELETE without a version ID. AWS documents that this request can return 200 and insert a new delete marker, which becomes the current version while protected A remains in the version history. The ordinary object listing may no longer show the content, and an application GET may behave as if the object is absent. Neither observation means that A was permanently destroyed.

A new PUT to the same key can similarly create version B; the key may then point to B while A remains protected. A key-level inventory can lead a recovery operator to think the lock failed or to apply B's retention state incorrectly to A. This is a hypothetical sequence based on the manual, not an operation performed against a real bucket. Both recovery and deletion require distinguishing version IDs, the current marker, and each version's status.

Choose governance, compliance, and legal hold by threat model

AWS describes governance mode as allowing principals with the required bypass permission to alter or delete protected versions. Compliance mode imposes stricter deletion limits during retention. A legal hold has no automatic expiry; a principal with permission must explicitly remove it. Check exact permissions and exceptions against the current account policy. Treating “Object Lock enabled” as one security property hides who may change retention, create a new version, remove a hold, or add a marker.

For immutable retention, place the writer identity, retention settings, version inventory, replication destination, and lifecycle rules in one audit model. A protected version does not prevent someone from uploading an incorrect new version and making it current. The application may need to verify a version ID, object digest, or signature before trusting the new version. For regulatory retention, a recovery window, or ransomware protection, define separately whether the requirement is “do not delete old evidence,” “do not replace the current business object,” or “ordinary users cannot access it.” These require different policy combinations.

How can you verify which object is protected?

In a non-production bucket, enable Versioning and Object Lock, write a test object, and save the returned version ID. Apply a short test retention or legal hold to that version. Then try four operations: permanently delete by version ID; issue a simple DELETE without a version ID; PUT another object to the same key; and inspect the current key and version history. Record every response, current marker, version list, and retention state. Test governance bypass, compliance mode, and legal hold only in a dedicated account with minimal permissions; do not probe against production data.

Keep the bucket versioning state, Object Lock configuration, version ID, retain-until time, mode, legal-hold state, caller identity, and API timestamp in the acceptance record. Inventory and backup systems should store key and version ID together, and recovery procedures should identify which version to restore. Review lifecycle rules for current and noncurrent versions separately; a key being hidden is not a reason to delete every historical version automatically.

Choices and limits

Object Lock provides WORM retention for versioned objects. It is not a key lock, application permission system, replicated backup, or immutable audit log by itself. To prevent deletion, select version-level retention and legal hold. To limit changes by ordinary operators, evaluate compliance mode or governance permissions. To preserve the current business pointer, also control who can create new versions and delete markers. A separate article covers recovery from versioned delete markers; this article focuses on the unit Object Lock protects.

This article checked version-level protection, new-version behavior, and delete-marker behavior in the official Amazon S3 User Guide. No AWS account was accessed and no API was run. Before implementation, inspect the actual bucket configuration, IAM permissions, replication, and lifecycle rules and retain per-version evidence. Object Lock can restrict changes to a specified version; it cannot alone prove that the business key points to the right data or that a cross-region backup exists.

Review replication per version as well. Object Lock on a version in the source bucket does not prove that every replica, cross-account archive, or backup lifecycle has the same retention. Check target-bucket versioning, whether replication preserves lock settings, whether target version IDs are recorded, whether failed replication alerts, and who may change target retention. A regulatory evidence chain must describe the lock state of each copy; the current source key alone cannot prove that every replica is immutable.

Related reading: the site’s recovery of versioned S3 delete markers. Both require operation records to identify the target version ID; a key and successful API status alone cannot prove retention or deletion is complete.

A recovery plan should treat the desired data version and the current key pointer as separate outputs. Restoring an old protected version may require copying it into a new current version, which creates a new version ID and its own retention decision; it does not move the historical version back into place. Record the source and destination version IDs, retention mode, and actor for that operation. This prevents a “restore succeeded” message from obscuring whether users now read the intended content and whether the archived evidence remains protected.
