Why doesn't switching npm trusted publishing to OIDC prove the release is safe?

npm trusted publishing associates a trusted CI identity with short-lived OIDC publishing credentials and reduces long-lived tokens. It does not prove that the workflow, dependencies, or artifact are benign.

Key takeaways

  • The npm trusted-publisher configuration binds a CI provider, repository, and workflow filename, with an optional environment.
  • GitHub Actions needs id-token: write to request an OIDC identity token.
  • Identity exchange reduces long-lived tokens, but code review, workflow permissions, and artifact validation remain separate security gates.

npm trusted publishing can let a supported CI identity exchange an OIDC token for a short-lived publishing credential, reducing the need to store a long-lived npm token in a repository. It does not prove that the release workflow, dependency tree, or package is safe. npm's trusted-publisher configuration binds identity to a provider, repository, and workflow filename; GitHub Actions also needs id-token: write. If an untrusted change controls the workflow, OIDC can make it easier to hand real publishing authority to the wrong code.

OIDC proves who is requesting a token, not that the code is trustworthy

Traditional publishing often puts a long-lived token into a CI secret. Trusted publishing instead lets a supported CI provider issue an identity token. npm checks whether its claims match the package's trusted-publisher configuration and exchanges the token for a short-lived publishing credential. npm currently documents GitHub-hosted Actions, GitLab.com shared runners, and CircleCI cloud as supported providers; self-hosted runners are not currently supported. GitHub Actions needs id-token: write, but that is not a reason to grant the entire workflow broader contents, packages, or other write permissions.

This makes “which workflow identities may publish?” an explicit configuration, but it does not review shell commands inside the workflow. If a publishing job downloads an unpinned third-party action, executes a pull-request script, loads publishing configuration from a writable branch, or combines build and publish authority in an unprotected job, the OIDC identity can still be abused. An identity assertion can establish that a request matches a repository/workflow claim; it cannot prove that the workflow inputs, dependencies, source, and package were reviewed safely.

Hypothetical release chain: a trusted identity can run untrusted steps

Suppose a GitHub Actions workflow publishes on a release tag from main, but ordinary write users can still create that tag. npm trusts the repository and publish.yml, so the eligible workflow can request an OIDC token. If the release step first fetches an action that is not pinned to a commit SHA, or dependency installation runs a substituted script, successful publisher authentication does not stop those supply-chain risks. The attacker used a legitimate identity to execute the wrong content; they did not need to forge its identity claim.

Mitigation spans several boundaries: protect release tags and environments, limit who can edit the publishing workflow, pin actions to full commit SHAs, use controlled lockfiles and build inputs, connect the tested artifact to the publishing step, and audit the npm package version, source commit, and provenance relationship. Confirm that environment protection actually applies to the job; npm makes the environment name an optional publisher field, and it constrains identity only when the configured name matches the CI environment. This threat-model example was not a release run or security audit.

Check identity matching field by field during migration

npm trusted-publisher configuration includes the CI provider, GitHub user or organization, repository name, workflow filename, optional environment, and permissions for direct npm publish, npm stage publish, or dist-tag management. The workflow filename is entered as a filename and must exist in .github/workflows/; organization or repository renames also require identity configuration changes. For a reusable workflow_call publisher or parent/child workflows, npm warns that caller names and OIDC permissions affect validation. Do not assume that adding permissions only to the final file that runs npm publish is enough.

Do not delete the old token at the beginning of migration. First validate the actual CI event, audience claim, workflow and environment names, and publishing scope against an isolated package or staging package. Observe whether npm recognizes the identity and completes the short-lived exchange. Then test the recovery path for a failed publish and confirm that no long-lived token remains in logs, caches, or backups. Revoke the old token only after the new path is verified, and audit whether other workflows still use it.

Keep provenance and security conclusions separate

Build provenance can associate a package with a repository, build environment, or workflow and help consumers trace its origin. It is not an independent code audit, and it does not prove that dependencies are vulnerability-free or the build was uncompromised. Trusted publishing describes how a publishing credential is obtained and authorized. Provenance describes an origin claim. A signature or checksum addresses data integrity. Human review and tests describe process checks. Calling all of these “supply-chain security” hides their different guarantees.

Release acceptance should compare the package name, version, tarball contents, source commit, CI run, identity claim, and permissions; do not rely only on a zero exit code. For packages with a build step, verify that the published artifact is the immutable artifact that was tested, rather than fresh content generated after dependency downloads in the publish stage. No npm publish or provenance artifact was produced for this article; the checklist is recommended practice, not execution evidence.

When is migration useful?

If a project currently relies on a long-lived npm token and uses a CI provider supported by npm, trusted publishing can reduce static credential storage and rotation. It still requires a stable, protected workflow identity, correct permissions, and an auditable release event. If the current self-hosted runner is unsupported, do not claim that OIDC publishing is ready; first assess a supported execution environment or retain a tightly scoped, least-privilege credential process.

This article follows the npm trusted-publisher documentation for supported providers and GitHub permission requirements. Validate the configuration with the target package and workflow before rollout. Successful identity matching does not mean that the package is benign, its dependencies are safe, the build is reproducible, or a human approved the release. Short-lived credentials reduce exposure; the publishing code still needs a trusted build, review, and origin validation.

Publishing scope is another easily missed boundary. npm lets a trusted publisher define allowed operations; direct publish, stage publish, and dist-tag management are distinct permissions. Enable only what the job needs, ensure test jobs do not inherit the publishing identity, and prevent the release workflow from running on arbitrary branches or unapproved tags. In validation, try an unauthorized branch and confirm it cannot obtain an OIDC token. A failed request alone does not prove the whole policy is correct; also inspect repository environment rules and GitHub token permissions.

Related reading: the site’s the input boundary of npm ci. Trusted publishing changes release identity credentials; it does not make varying lockfiles, lifecycle scripts, or build inputs trustworthy.

One useful release invariant is that the bytes reviewed before publication are the bytes consumers receive. Build once in the protected job, retain an immutable artifact, compute its digest, and make publication consume that artifact rather than rerunning install or build after credentials become available. Then compare the package tarball and provenance to the source commit and run identity. OIDC narrows who can ask npm to publish; artifact identity and reproducible build checks answer what was published. Both are needed to investigate a release whose identity was valid but whose contents were unexpected.
