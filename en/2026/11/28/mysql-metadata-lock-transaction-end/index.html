Why can a failed MySQL statement still block DDL?

In MySQL 8.4, a syntactically valid statement that fails during execution can retain a metadata lock until its transaction ends; autocommit releases it with the statement. Trace the transaction and lock holder when DDL waits.

Key takeaways

  • Metadata locks coordinate object definitions and can block incompatible DDL.
  • A statement that is syntactically valid but fails during execution does not necessarily release its metadata lock early.
  • The transaction boundary matters; with autocommit, each statement is its own transaction.

In MySQL 8.4, an error from a statement does not prove that a metadata lock it already acquired has disappeared. The manual says that a syntactically valid statement that fails during execution does not release its metadata locks early; their release is deferred until the transaction ends. Under autocommit, each statement is effectively a complete transaction, so its lock is normally released when the statement ends. When DDL waits, the last SQL line in an application log may not identify the blocker. Connect the waiting DDL to the lock-holding session and its transaction boundary.

What does a metadata lock protect?

A metadata lock (MDL) coordinates concurrent access to definitions of tables, views, and other objects. When a query or update uses a table, the server must prevent an incompatible definition change from interfering with that work. DDL needs a lock that allows it to change the definition. If a transaction still holds a conflicting lock, an ALTER TABLE, DROP, or similar operation may have to wait. That delay does not necessarily mean the DDL itself is slow or that a storage engine is processing a large table. The conflict may come from another connection that accessed the table earlier and never ended its transaction.

InnoDB row locks and MDL are different mechanisms. Row locks coordinate record-level concurrency; MDL coordinates object definitions. Looking only at a row-lock view may therefore miss a metadata-lock wait that blocks DDL. An application SELECT can return quickly, yet if it ran inside an explicit transaction, that connection may retain transaction-scoped MDL until commit or rollback.

Why can execution failure leave a waiting chain behind?

The MySQL 8.4 manual describes a counterintuitive boundary: if a syntactically valid statement fails during execution, the server does not release metadata locks it acquired early. The manual explains that this protects binary-log consistency because the failed statement is still written to the binary log; lock release remains deferred until transaction end. A statement rejected during parsing and one that entered execution are not the same path. Do not treat an “error returned” event as proof that the transaction ended.

Imagine session A opens an explicit transaction and runs a valid statement that accesses orders. The statement then fails because of a constraint or data error. The application catches the exception and logs it, but never rolls back; the connection remains in the pool. Session B then tries DDL that needs a conflicting metadata lock on orders and waits behind A. The application log makes A's business operation look finished, while its database transaction remains open. This is a hypothetical timeline based on the documented mechanism, not a report of a real incident.

Diagnose both the waiter and the lock holder

First identify the DDL that is waiting, its object, and how long it has waited. Next identify the session holding the conflicting lock. Then inspect whether that connection is in an uncommitted transaction, its transaction start and last activity, and the application instance that owns it. MySQL Performance Schema provides metadata-lock observations; check the exact tables and privileges for the deployed 8.4 point release and its instrumentation configuration. Map the connection ID to a pool, service instance, and request log. Otherwise, you may know that “a transaction holds a lock” without knowing who must end it.

Do not default to killing every slow query. Terminating the lock holder rolls back its transaction and may disrupt active business work; cancelling the waiting DDL may leave a release operation incomplete. Choose based on the change window, retry safety, rollback cost, and service impact. A migration task can use a bounded wait and stop with an alert when it expires. For long-lived application transactions, fix transaction cleanup and pool-return behavior instead of repeatedly restarting DDL.

How can a small test expose this boundary?

On an isolated instance, create a test table. In session A, begin a transaction and access the table. In session B, attempt DDL that needs an incompatible metadata lock. Exercise two endings: A commits after the access; or A runs a valid statement that fails but leaves the transaction open. Observe whether DDL remains blocked until A commits or rolls back. Repeat with autocommit to compare the lock lifetime at statement completion. Use Performance Schema lock-wait records and connection state before and after; do not rely only on client-side elapsed time.

Use isolated objects, set a cleanup deadline, and explicitly roll back in failure paths. Do not manufacture a long transaction against a production table merely to “confirm” the documentation. Do not generalize one test output from one point release to every deployment. On the application side, also verify whether the ORM or driver automatically rolls back after a statement error. Without transaction cleanup, returning a connection to the pool can turn one local error into a queue of later DDL.

Which design choices reduce repeat failures?

Keep explicit transactions for online requests short. Do not wait for an external API, user input, or a queue message while a transaction is open. Make the error path decide clearly whether to commit or roll back, and check transaction state before returning a connection to the pool. Migration tooling should detect long transactions and metadata-lock waits, use an explicit wait policy, and stop outside the release window rather than wait forever. Application monitoring can correlate transaction age, connection ID, request ID, and DDL release record, but logs do not replace database lock evidence.

This article describes behavior in the MySQL 8.4 manual. Different statement types, transaction modes, storage engines, and point releases can affect the observed wait, so validate against the actual connection pool and migration tool. The key distinction is that a statement's error status and a transaction's lifetime are separate states. Only transaction end reaches the MDL lifecycle boundary discussed here; the last error line in a log is not enough to prove that it did.

When handling a wait, separate a statement error from a transaction error. Some database errors cause an application to roll back, but do not infer from the exception type alone that the driver already ended the transaction; the pool may still hold the session while rollback is pending. Record transaction age, current state, the locked object, and owning service instance, then determine whether a request is still active. Before killing a connection, decide whether it is processing an important write, idle with an uncommitted transaction, or left in an exceptional state. The rollback cost and recovery differ; a generic “kill old connections” script can turn an MDL issue into a business outage.
