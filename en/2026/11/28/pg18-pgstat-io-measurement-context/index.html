Why don't pg_stat_io read and write counts prove that storage is slow?

PostgreSQL 18 pg_stat_io splits cluster-wide statistics by backend, I/O context, and target object, with documented blind spots. Define the window, counter semantics, and exclusions before using it for diagnosis.

Article

Key takeaways

  • Each pg_stat_io row represents a backend type, I/O context, and target object combination, not one database-wide disk speed.
  • Some relation I/O that bypasses shared buffers is not tracked by this view.
  • Cumulative values need a fixed interval and consistent dimensions; the view alone does not prove a storage bottleneck.

Read and write counts in pg_stat_io do not directly answer “Is the disk slow?” PostgreSQL 18 presents cluster-wide I/O statistics in separate rows for backend type, I/O context, and target object. The numbers first tell you how many events a particular kind of PostgreSQL work accumulated during an interval. They are not device latency, a throughput limit, or causal proof about one query. Before troubleshooting, record the dimensions, time window, and paths the view does not cover so a counter is not mistaken for a root cause.

Each row represents a combination of work roles

The manual defines each row as a combination of backend type, target I/O object, and I/O context. Only meaningful combinations appear; pg_stat_io primarily covers relation and temporary-relation objects, so WAL statistics should not be folded into it. PostgreSQL exposes WAL activity separately through pg_stat_wal and a separate track_wal_io_timing setting. That separation matters. Relation reads performed by user backends and work associated with a background process or checkpoint should not be combined into one unexplained “database read count.” If checkpointer writes rise while application shared-buffer behavior stays stable, a single total makes two different questions look like one.

pg_stat_io is not a block-device monitor. The manual explicitly says that relation I/O bypassing shared buffers—for example, I/O while moving a table to another tablespace—is not currently tracked. An event absent from the view is not a zero, and it does not prove that the database performed no I/O. Likewise, the counters do not directly report device queues, cloud-volume throttling, operating-system page-cache hits, or storage latency. Those require observations outside PostgreSQL statistics.

Set the observation window before reading counter changes

Statistics are generally cumulative state. Suppose one backend/context/object row contains 10,000 reads at the start of a sample and 10,600 five minutes later. The increase of 600 says that the combination's counter increased by 600 during that window. To estimate a rate, divide by the actual elapsed time and confirm that no statistics reset, instance switch, or dimension change occurred between samples. Comparing absolute values from two instances with different uptime turns “has been running longer” into a false “is busier” conclusion.

The workload must also match. Suppose morning request volume is three times afternoon volume. Even if afternoon reads per minute are lower, absolute counts alone cannot prove that an optimization worked. You can normalize the change by request, transaction, or row count, but the denominator needs to come from the same service instance and time boundary. If one sample is a cluster aggregate and the other is a single node, or one includes accumulated values from before a restart, the calculation may look precise while remaining incomparable.

Hypothetical example: a write increase is not yet a disk diagnosis

Imagine that after a release, one write-related combination increases by 40% compared with the prior window. That is a signal to investigate, not a conclusion that “storage became slow.” Possible causes include more page writes per request, a change in checkpoint work, overlap between batch work and online traffic, or a different request mix. Preserve the backend, context, and target-object dimensions, then align them with transaction volume, request rate, checkpoint observations, wait events, and host or cloud-storage measurements to find the layer that changed.

A counterexample is to add all reads and writes together and call the result disk IOPS. That mixes backends and ignores whether an operation passed through shared buffers, its actual latency, and device coalescing behavior. If cloud-volume latency later rises, investigate whether the working set or request volume also grew. If host I/O rises while the PostgreSQL view remains unchanged, check paths the view does not cover, logs, temporary files, or other processes. This is an analysis example, not a measurement from production.

Keep a sample table that preserves diagnostic clues

For each sample, record a timestamp, instance identifier, PostgreSQL major version, backend type, context, target object, counter values before and after, and elapsed interval. Save request and transaction volume, wait categories, checkpoint-related observations, and host I/O for the same window. If a counter moves backward, do not interpret the negative delta as negative I/O. Check for an instance restart, statistics reset, exporter-label mapping change, or a different sampled object. Keeping the original groups before aggregation lets you recompute and audit the result later.

Start validation in a non-production environment with known operations: run controlled table reads, writes, or checkpoint work and confirm the expected direction of the relevant row changes. Then compare with an independent host observation. To test a documented blind spot, perform an operation that bypasses shared buffers without demanding that pg_stat_io report that relation I/O. The point is to verify the collection pipeline, labels, and interpretation—not to prove that one view explains every live I/O event.

What evidence supports the claim that storage is the bottleneck?

You need several observations that agree: PostgreSQL counter changes for the same interval, query or background-work waits, host or storage latency and queue data, a workload denominator, and continuous samples that rule out restart or reset. A rising count with stable latency may mean more throughput rather than degradation. If the application slows while I/O counters remain stable, the bottleneck may be locks, CPU, network, a connection pool, or activity outside the view's coverage. A cumulative counter cannot establish user-visible p95 latency, and a statistic column should not be renamed as a device metric.

This article uses PostgreSQL 18 documentation to explain the view's dimensions and scope. No database was connected to, pg_stat_io was not queried, and no disk was benchmarked. For a real system, verify its running version, view fields, collection interval, and instance topology, then validate the mapping with controlled work. The view is useful for asking “Which kinds of PostgreSQL work are accumulating I/O statistics?” It cannot by itself answer “Which device is slow?” or “How much did this release regress performance?”

The collector should also record statistics-reset boundaries. An upgrade, manual reset, or instance switch can make adjacent snapshots belong to different cumulative sequences. A direct subtraction may then produce a negative value or a jump that reflects counter lifetime rather than PostgreSQL performing reverse I/O. Include database identity, start time, and reset events in the sample dimensions, and start a new series when the exporter labels change. During a rolling upgrade, compare nodes separately before aggregating rates over the same interval. This prevents pre-restart history from one node being mixed with another node's current state and preserves the raw deltas for later review.
