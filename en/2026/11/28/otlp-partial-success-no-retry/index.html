Why shouldn't an OTLP client resend an entire batch after partial success?

A populated OTLP partial_success means that part of a request may already have been accepted; the protocol says not to retry the whole request. Handle rejection counts and causes separately from retryable responses.

Key takeaways

  • partial_success reports rejected signal items; it is not an ordinary all-or-nothing transient failure.
  • The OTLP specification says not to retry the entire request when a populated partial_success response is received.
  • Expose rejection counts and investigate data quality instead of using full replay to hide rejection.

When an OTLP response contains a populated partial_success, the client must not retry the entire request. The OpenTelemetry Protocol specification says the client MUST NOT retry such a request: the server may have accepted part of it and rejected only the remaining signal items. Treating the response like a normal 503 or network disconnect and resending the whole batch can duplicate spans, metrics, or logs already accepted. Dropping the whole batch, however, loses valid data along with rejected items. Processing needs to distinguish partial acceptance, retryable transport states, and permanently invalid data.

partial_success describes a partial result, not a transaction rollback

An OTLP partial-success structure can include counts such as rejected_spans, rejected_data_points, rejected_log_records, or rejected_profiles, together with a server-provided explanation. It describes how many items were rejected. It does not provide a transaction ID that makes an entire request safe to replay, and it does not imply that the server rolled back the data it accepted. A request can contain valid and invalid records of one or more signal types. The client must not infer that it can resend the other items together with rejected ones.

The specification also allows a server to use partial_success for warnings or suggestions even when it accepted the request fully. In that case, the rejected count must be zero and the error message nonempty. Therefore, the presence of a partial-success object alone does not prove data loss. Read the rejection count, explanation, and response status according to their field semantics. Verify the OTLP version and whether the exporter supports the response fields correctly.

Hypothetical batch: three of one hundred spans are rejected

Imagine an exporter sends an OTLP request containing 100 spans and a collector reports that three were rejected. The remaining records may already have been accepted. If the exporter resends all 100 because it saw an “error message,” downstream storage may contain duplicates for the accepted spans. If it marks the whole batch successful, the three rejected spans may be lost without anyone tracking them. A safer response is to stop whole-batch automatic retry, increment a rejected-item metric, preserve the error category, and investigate shared properties of the rejected data, such as field types, resource attributes, or capacity limits. The numbers are hypothetical; no collector was run for this example.

Another failure is mapping partial success to a nil error. Higher layers then assume everything arrived while the rejection count disappears. Or an exporter may map it to a generic retryable error and replay everything. Integration tests should verify how the exact response fields pass through the exporter, queue, and alerting system rather than checking only the HTTP status code. Preserve enough information from upstream responses and collector logs to avoid reducing the event to the vague text “partial failure.”

Why not automatically retry only the rejected records?

The protocol count says how many items were rejected but may not provide a stable index or replay ID for each record. rejected_spans=3 does not necessarily let a client reconstruct which three spans they were. An exporter that retains the original batch and has an exact rejection mapping could build a more granular recovery path, but it cannot assume the server supplied that mapping. Any custom retry must avoid resending accepted records and must not retain sensitive telemetry payloads indefinitely.

For permanently invalid data, the OTLP specification requires handling the error rather than repeatedly sending the same invalid payload. An exporter can monitor dropped-item counts, causes, and resource or scope labels. If the cause is a fixable configuration or schema issue, correct it and process only data known not to have been accepted. If the acceptance boundary is unknown, record that the result is partially known and use collector observations, downstream deduplication, or data audit to close the gap; do not pretend to have exactly-once delivery.

How should tests and alerts be designed?

Construct at least four responses: full success without partial success; a zero rejection count with a warning; partial rejection with a nonempty explanation; and a permanent non-retryable error. Verify the exporter's return value, queue acknowledgment, drop policy, and retry count for each case. Specifically confirm that populated partial success does not replay the whole request, rejected counts increase, and the response remains associated with its export batch. Include process restart with a persistent queue so “no retry” does not accidentally become silent data loss.

Alerts should not watch only the HTTP failure rate. Track rejected-item counts and ratios by signal type, error class, and consecutive time window. Compare receiver and collector counts over the same window. A rising ratio may come from a schema change, throttling, resource-attribute change, or exporter bug; rejection alone does not prove that the collector needs more capacity. This article did not run SDK, exporter, or collector tests; its evidence is the protocol specification. Check the version and implementation used by the project.

When is a retry appropriate?

Separate protocol-defined retryable transport states from partial success and permanently bad data. For partial success, do not resend the full request. For a temporary response that the protocol permits retrying, use bounded backoff and queue limits. For malformed or permanently rejected data, record and drop it or send it through a controlled quarantine path. A recovery boundary needs stable evidence: the client can identify exact unaccepted items, or the business layer has a verifiable deduplication key. Without that, splitting and resending can still create duplicates.

OTLP is not a transactional database interface. It does not promise atomic commit across all telemetry records in an Export request and does not offer a business-level uniqueness guarantee. The exporter's job is to follow the protocol, expose rejection information, and prevent incorrect replay. The operator's job is to investigate rejection causes and data-completeness boundaries. Designing those responsibilities separately avoids hiding partial acceptance behind a simplistic “failure means retry” rule.

Pair rejection counts with exporter queue metrics. If rejected_spans rises while the queue stays stable, the issue may be data shape or collector policy. If the queue also grows, send rate, receiver capacity, and retry behavior may all be out of balance. Break rejection rates down by instrumentation scope, resource attributes, and exporter version to locate recent changes, while controlling label cardinality. Avoid logging raw user data in error details; redaction should still preserve the field type and error category needed for a fix.
