Why can a Prometheus native histogram have fewer buckets after merging without losing samples?

A native histogram schema sets exponential bucket resolution. Downscaling merges buckets and removes detail; understand schema, interpolation assumptions, and storage budgets before explaining query differences.

Article

Key takeaways

  • For standard schemas, a higher number means denser exponential buckets; increasing it by one doubles resolution.
  • Compatible downscaling can merge adjacent buckets, reducing detail while preserving the overall range.
  • Quantile estimates depend on bucket layout and interpolation assumptions, so a schema change is not a raw sample change.

Fewer buckets in a Prometheus native-histogram query do not necessarily mean samples were lost. A native histogram's schema determines exponential bucket resolution. In standard schemas, increasing the schema number by one doubles resolution and makes boundaries denser. To merge data with different resolutions or control storage and transfer costs, buckets can be downscaled and combined, reducing detail. Before diagnosing missing observations, compare schema, downscaling, and the query path.

A schema describes bucket-space resolution

An exponential histogram divides positive and negative ranges into adjacent buckets on a logarithmic scale. A standard schema number defines the factor between adjacent boundaries; a higher schema divides the range more finely. The Prometheus Native Histograms specification explains that increasing the schema number by one splits buckets in two and doubles resolution. This is not sample precision or samples per unit of time. It controls the density of aggregated bucket boundaries; it does not mean each observation was measured more precisely.

Downscaling to a lower schema can combine adjacent fine buckets so different resolutions can be represented together or data volume can be controlled. Merging does not invent a new total count, but it discards detail about where observations fell inside the finer buckets. If an SLO threshold lies inside a merged interval, a quantile estimate can become coarser. Querying also uses assumptions about the distribution within a bucket. Prometheus documents exponential interpolation for standard schemas, assuming that newly split buckets contain similar populations on average. A strongly skewed real distribution can make that assumption matter.

Hypothetical example: a threshold sits near a merged interval

Imagine a service tracks request latency with a p99 target of 500 ms. A higher-resolution schema has several buckets around 450 ms and 510 ms. A receiver downscales the data to match a lower resolution, merging nearby buckets into a wider interval. The query can still estimate the quantile, but it cannot recover whether each observation landed at 470 ms or 505 ms. A chart can shift slightly even if the raw request distribution did not change at the same time.

The wrong response is to call every new/old quantile difference a “latency regression,” or to assume that an unchanged total bucket count proves nothing happened. Align the schema, sum/count, positive and negative buckets, zero bucket, and query function for the same interval. Check whether scrape, remote write, storage, or query paths apply different downscaling. These values are hypothetical; no Prometheus server or latency workload was measured.

How should resolution be balanced against cost?

Higher resolution can locate a threshold more accurately but may create more non-empty buckets for each sample group. Data volume, remote transfer, and aggregation costs can grow with the workload. A lower schema reduces bucket count and can improve merge compatibility, but quantile estimates near boundaries become less precise. Choose based on the decision the metric supports: a coarse resolution may be enough if an alert only distinguishes “well above 500 ms.” If a product decision must distinguish 490 ms from 505 ms, verify that the resolution can support that separation.

Do not estimate cost from average bucket count and apply one schema to every metric. Low-volume endpoints, high-cardinality labels, and bimodal or long-tailed distributions can produce very different patterns of non-empty buckets. Measure real samples across the target instrumentation, compression, remote-write, storage, and query versions, together with retention, label count, and query frequency. Native Histogram support and configuration have version and component boundaries; one successful experiment does not prove that the entire production chain preserves the same resolution.

How can you locate the source of a bucket change?

Record schema and histogram fields at each stage: application generation, scrape, remote write, receiver storage, read API, and PromQL result. Compare count, sum, schema, zero bucket, and positive/negative bucket boundaries. If count remains stable while schema is lower and buckets are merged, the change is more likely resolution downscaling than sample-count loss. If count also falls, investigate scrape failure, filtering, throttling, queue overflow, and misaligned time windows.

Build a controlled dataset with observations on both sides of a target threshold. Write and merge it under several schemas, then compare buckets and quantiles. Cover a concentrated distribution near a boundary, a long tail, sparse values, and zero values. Record query interpolation and component versions. Do not use a dashboard's pixel movement as a substitute for numeric validation; plot resolution, query step, and interpolation affect the visual curve.

When is lower resolution acceptable?

If storage, network, or aggregation compatibility matters more than precise boundary estimates and the business threshold is broad, lowering the schema may be reasonable. For SLO decisions that require precise thresholds, use matching resolution and monitor whether downstream components downscale it. If the chain cannot guarantee that resolution, design alerts to tolerate the estimate's uncertainty. Do not conflate a native histogram schema with explicit bucket boundaries in a classic histogram; their representation and merge behavior differ.

This article follows the Prometheus Native Histograms specification for standard schemas, merging, and interpolation. It includes no benchmark or observation from a live cluster. Validate bucket growth, query precision, and storage costs with the deployed Prometheus and remote-write versions, scrape configuration, and workload. Fewer buckets may be an intentional consequence of downscaling; whether that is acceptable depends on the decision threshold, not bucket count alone.

Recording rules need a traceable resolution history. When a rule merges histograms from multiple sources, the resulting schema can depend on the coarsest input and conversion support; checking only the raw scrape schema at dashboard time is insufficient. Keep pre- and post-aggregation schema and count in regression samples to catch unexpected downscaling after Prometheus, remote-write, or rule upgrades. If an alert is sensitive near a threshold, test conservatively with coarser inputs instead of only the ideal maximum resolution.

Related reading: the site’s Prometheus recording-rule label contracts. Check label identity separately from histogram schema before and after aggregation, so merging instances is not mistaken for a resolution change.

Comparisons need aligned populations as well as aligned schemas. If a recording rule changes labels, the old and new histograms may represent different endpoint groups even when their counts look similar. Fix the time window, label set, reset boundary, and schema before comparing quantiles. Then inspect whether the threshold falls inside one coarse bucket or across several fine buckets. This makes the review answer two separate questions: did the represented request population change, and did the bucket layout lose decision-relevant detail?
