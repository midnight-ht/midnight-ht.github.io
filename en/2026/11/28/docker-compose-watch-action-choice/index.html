Why does a container still use old dependencies after Compose Watch syncs a manifest?

Compose Watch's sync, rebuild, and sync+restart actions serve different changes. Copying a file does not rebuild an image or install dependencies; the wrong action can keep the development loop on an old process.

Key takeaways

  • Compose Watch requires Docker Compose 2.22.0 or later.
  • sync copies files; dependency or compiled-output changes usually need rebuild or sync followed by restart.
  • Path rules, ignore patterns, and container-user write permissions determine what actually happens.

If Compose Watch syncs package.json, the container has not necessarily installed the new dependencies. The action determines how a change reaches the running service: sync copies files, rebuild rebuilds the service image, and sync+restart synchronizes files and restarts the process. Syncing only a dependency manifest may leave the container with a new file but old node_modules and an old process. Docker's Compose Watch documentation requires Compose 2.22.0 or later. Before configuring rules, decide whether a change affects source files, image-build inputs, or process configuration.

The three actions serve different feedback loops

sync fits source or static files that the application can hot-reload directly. It does not rerun the Dockerfile or automatically install dependencies. Copying a manifest into a container cannot update packages already installed in an image layer. rebuild rebuilds the service image and fits changes to dependency manifests, compiler toolchains, or files baked into the image. sync+restart fits files that need to be copied into the container while a process must restart to reread configuration or content.

Not every file should be watched. Docker's documentation defines paths relative to the Compose project directory; watch behavior follows .dockerignore rules, and directory paths are handled recursively. The service user inside the container needs write access to the target path, or synchronization may fail or appear incomplete. A host path that ignores the image work directory, ignore rules, and USER permissions can produce the misleading impression that “saving did nothing.”

Hypothetical example: source and dependency changes need different rules

Suppose a Node service uses a hot-reload directory for src/ and a separate sync-and-restart rule for package.json and the lockfile. Changing src/handler.js may let the development server reload the code. But syncing the two manifests and restarting can still launch the old node_modules already present in the image. If the change requires npm ci, the correct action should trigger a rebuild or an explicit, auditable development startup process that installs dependencies. Check the image and installation state, not just the manifest inside the container.

The opposite mistake is rebuilding for every change under src/. That slows the feedback loop and treats source edits as image-structure changes. If compiled output is not generated inside the container, even rebuilding may not fix the file mapping. Configure actions according to the consumer of each file: a running interpreter, build stage, startup configuration reader, or static server. This example illustrates a decision; no Compose project was run and no build time was measured.

A simplified rule grouping

You might configure hot-reloadable source as sync, dependency manifests, Dockerfiles, and compiler versions as rebuild, and configuration files that must be reread as sync+restart. Validate the actual YAML patterns, targets, and actions against the installed Compose version instead of copying a sketch. If the service uses only a prebuilt image: with no local build context, a local file change does not magically rebuild the upstream image; the service must be tied deliberately to a local source build.

Exclude secrets, caches, generated output, and large directories from synchronization where appropriate, while ensuring ignore rules do not hide required source files. When the service runs as a non-root user, target-directory write access is part of the development environment contract. Do not switch the entire container back to root merely to fix a sync error. Review the documentation's pruning behavior for the current configuration so image cleanup does not create a false expectation about build-cache preservation.

How can you verify that the loop does not silently run old content?

With the actual Compose version, change one source file, one dependency version, one image-build file, and one runtime configuration. For each, observe whether Watch matched the path, which action started, whether the container target changed, whether dependencies or image ID changed, whether the process reloaded, and whether a test request shows the new behavior. A log line that says a file watcher fired is not enough to prove success; the relevant rebuild or restart should be visible.

Also test failures and boundaries: a file excluded by .dockerignore, a read-only target, multiple matching rules, no build context, a path with the wrong case or relative root, and a health check failing during restart. After changing dependencies, inspect the installed package version in the container; after changing a compiler, inspect the image digest and binary version. Without these checks, a common split state is new host source with an old container binary.

When should you choose sync, and when rebuild?

If the running process can consume a synchronized file and the change does not affect image layers or dependency installation, sync is usually the lightest action. If a change alters image-build or installation state, rebuild covers that boundary. If the process only needs to reread a copied file, sync+restart is more appropriate. Match each action to the change semantics rather than making every save trigger the heaviest build.

This article follows the current Docker Compose Watch documentation, including its Compose 2.22.0 minimum. No Compose stack was started, no project YAML was validated, and no benchmark was run. Test paths, permissions, ignore rules, dependency state, and health recovery with the actual Compose version and container user. “The file was copied” does not mean “the application is using it.”

Make overlapping rule behavior explicit with configuration tests. If a file matches both rebuild and sync, the result may be duplicate builds or order-sensitive behavior; do not rely on YAML order to choose an action. Test changes to important paths and include the image digest, process start time, and source revision in local diagnostics. For a shared Compose file, ensure watch rules do not require privileges beyond ordinary developer file access or sync host credentials into the container.

Related reading: the site’s Docker COPY, chown, and runtime users. Watch sync updates a container path, but does not automatically change ownership, install dependencies, or fix the service process’s read permissions.

Keep the check observable at the same layer as the change. For a dependency update, compare the lockfile in the build context, the installed package version inside the running container, the image digest, and the process start time. If the lockfile changed but the image digest and installed dependency did not, the watch rule did not refresh the dependency layer. For a source-only sync, the image digest may stay constant; verify the served response or hot-reload event instead. A single “container is running” health check cannot validate both paths.
