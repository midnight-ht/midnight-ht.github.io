Why can a browser reuse an old CORS preflight after policy changes?

Access-Control-Max-Age caches method and header permissions from a preflight, and browsers may impose a lower cap. A policy change does not instantly clear every client cache; server authorization remains separate.

Key takeaways

  • Fetch defines Access-Control-Max-Age as the seconds for which preflight method and header information may be cached; the default is five seconds.
  • A user agent may impose a shorter maximum, so servers cannot assume every browser caches for the same duration.
  • Preflight permission is not authentication or server-side authorization; the actual request still needs an access check.

A browser does not necessarily send a new preflight immediately after a CORS policy changes. Access-Control-Max-Age specifies how many seconds a preflight's method and header permissions may be cached. The Fetch Standard sets a five-second default, and user agents may impose a lower maximum. As a result, clients that passed preflight shortly before a policy change may continue to use a valid cached result during its remaining lifetime. This does not mean that the browser ignores the server, or that a cross-origin request has gained a user identity or business authorization.

What does the preflight cache contain?

When a browser wants to send a CORS request that needs preflight, it first sends OPTIONS and asks whether the server allows the origin, method, and header combination. The server can use Access-Control-Allow-Methods and Access-Control-Allow-Headers to describe the allowed set. Access-Control-Max-Age gives those preflight results a cache lifetime. The Fetch preflight cache is not an ordinary HTTP response cache and does not cache the business API response. It lets the browser omit repeated OPTIONS requests when a cache entry matches; the actual request still goes to the server.

The standard uses five seconds if max-age is absent. If its value exceeds a browser-imposed limit, the user agent applies its lower limit. The server cannot predict the effective window from its own header alone because clients can differ. A preflight cache match also depends on request conditions such as origin, URL, credentials mode, method, and headers. Changing one condition may create a different entry; this is not simply “the domain has cached CORS.”

Hypothetical revocation: the new server rule is deployed, but the browser sends the actual request

Suppose an API previously allowed https://admin.example to use PATCH with X-Change-Reason, and the preflight max-age was 600 seconds. The deployment removes that method permission. A browser passed preflight 30 seconds earlier. While its cached entry remains valid, it may skip another OPTIONS request and send the actual PATCH. If the new policy exists only in the OPTIONS handler and the PATCH handler does not check account and operation permissions, the business write may still happen.

Conversely, if the actual PATCH response lacks the right CORS headers, the browser may refuse to expose that response to page script even though the server already performed the write. CORS primarily controls whether a browser shares a cross-origin response with a page. It is not an identity check that prevents every cross-site request. A JavaScript CORS error does not prove that the server never received or processed the request. This illustrates a protocol boundary; no request was sent to a real service for this article.

Credentialed requests require stricter combinations

For a credentialed request, Access-Control-Allow-Origin cannot simply be * while credentials are allowed. The server must return a matching explicit origin and correctly handle Access-Control-Allow-Credentials. Allowed methods and headers also need to be explicit; wildcards are restricted for credentialed requests. If the allowed origin is dynamic, response caching must account for the origin and Vary: Origin, so a shared cache does not reuse an allow response for a different source.

Reducing max-age can propagate policy changes sooner, but increases OPTIONS traffic. Extending it can reduce preflight requests while widening the window in which a client continues using an old permission. To revoke a dangerous write quickly, changing the max-age on new responses does not erase existing entries. Revoke authorization at the business handler, use a versioned API or path, or deploy an immediate deny condition. Do not use CORS cache expiry as a security revocation mechanism.

How can you test revocation and actual server behavior?

In the target browser, create tests with preflight caching: pass an allowed preflight and repeat the same request to see whether OPTIONS is omitted; change the method, headers, origin, or credentials mode and observe whether a new preflight occurs; then change the server policy and test before and after cache expiry. Record request times, whether OPTIONS and the actual request reached the server, server status, and response headers. A clean browser profile tests a cold cache but does not replace the warm-cache path used by existing users.

More importantly, send a request without valid identity or permission directly to the actual API and confirm that the server rejects it, even if a test harness bypasses browser CORS enforcement. Verify that authorization middleware runs before a write and that audit logs distinguish “preflight rejected” from “business operation rejected.” Observing only a browser-console error can confuse response-sharing failure with a rejected server write.

How should you choose max-age?

A frequently changing, higher-risk API may use a shorter cache to narrow the policy propagation window. A stable, mostly read-only request with significant OPTIONS overhead may justify a longer value after checking client caps and emergency revocation plans. The actual choice depends on browser distribution, preflight load, policy change frequency, and server-side authorization. Max-age must not hide inconsistent CORS configuration and is not a substitute for rotating access tokens or revoking permissions.

This article follows the Fetch Standard's preflight-cache semantics; no browser or server experiment was run. Measure effective caching in the target browsers, and verify CORS, authentication, authorization, and write execution as distinct layers. Even when a browser reuses cached permission, the server must check identity and authorization on every actual business request.

Separate preflight caching from authorization-header and business-token rotation. Cached methods and headers are browser protocol state; access-token expiry, revocation, and account permission changes are separate state. Even if the browser skips OPTIONS, the server can reject an expired token or revoked permission on the actual request. If a server treats an OPTIONS allow result as authorization for a later PATCH, the cache window becomes a security flaw rather than a performance parameter.

Related reading: the site’s private and shared caches for personalized responses. A preflight-permission cache and a proxy response cache hold different objects; a hit at one layer does not mean another layer authorized the request.

A policy rollback therefore needs two timelines. The browser preflight cache determines when a new cross-origin request may skip OPTIONS; the application authorization check determines whether the operation is allowed now. If a newly cached rule is removed, an already cached client may still send the request, but the server can reject its action immediately. Record both the preflight response and the business authorization decision during rollout. This lets operators distinguish a stale browser permission hint from a genuine access-control failure without waiting for every client cache to expire.
