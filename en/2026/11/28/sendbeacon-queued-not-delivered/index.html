Why doesn't a true sendBeacon result prove that the server stored the data?

A true navigator.sendBeacon result means the user agent queued data for transfer; queued data is limited to 65,536 bytes. It provides no server acknowledgment and does not prove persistence.

Key takeaways

  • The promise of sendBeacon's true return value ends at browser queueing; it does not confirm server receipt or storage.
  • The total queued data limit is 65,536 bytes, and the API can return false when it cannot queue more.
  • Events that require durable confirmation need a transport contract with responses, retries, and deduplication.

navigator.sendBeacon() returning true means only that the browser user agent successfully queued the data for transfer. It does not mean the server received the request, the application parsed it, or a database committed it. MDN also documents a total queued-data limit of 65,536 bytes; the method returns false when the queue cannot accept the data. Beacon is therefore useful for best-effort, small telemetry near page exit, not as confirmation that a critical business operation has been saved.

Which stage does the return value describe?

sendBeacon(url, data) sends an asynchronous POST request without blocking the page from navigating. Its Boolean return value reports whether the user agent accepted the data into its transfer queue. After queueing, the network can still disconnect, a device can go offline, the browser process can terminate, or the server can return an error or crash while processing. The API does not give the page a response object, so the caller cannot read an HTTP status, response body, or business-persistence receipt.

Naming the return value sent=true can mislead later monitoring. A more accurate state is queued. The server can record received only when it observes the request and stored only after persistence. Those states belong to different participants; the page cannot merge them into “success” from one Boolean.

Hypothetical example: a critical event is sent as the page closes

Imagine that a user submits a paid order, the page is about to close, and the frontend calls sendBeacon with a purchase-confirmed analytics event. After the function returns true, the frontend can record “queued.” It cannot update the order interface to say “the analytics database saved this” or stop querying the order service based on that return value. If the analytics system never receives the request, the page may already be gone and unable to retry. If the browser retries while the response is unknown, a duplicate event may result. The server-side payment/order status remains the source of truth; beacon is only a best-effort observation.

Estimate payload size in UTF-8 bytes, not characters. A Chinese character usually takes more than one byte, and JSON serialization adds keys, escaping, and structure. Multiple concurrent beacons share the 65,536-byte total queue limit; it is not enough to check that each payload individually fits. When the limit is reached, remove low-value fields, combine events, or choose another transport rather than splitting requests without bound during page teardown.

Design both loss and duplication paths

A network failure may mean the server never saw an event. If the server processed it but the client does not know, retrying may write it twice. Beacon provides neither idempotency nor exactly-once delivery. If telemetry can tolerate some loss, accept best-effort semantics and use aggregate sampling and gap monitoring. If an individual event is needed for audit or settlement, use a transport with server acknowledgment, a reliable queue, or a business-state query. Even fetch with keepalive requires checking its behavior and payload constraints; do not assume it is an unlimited reliable channel.

An event ID in the payload lets a server deduplicate and record raw receipt separately from database insertion. But the client cannot know that deduplication occurred. This can make duplicate delivery safer for the server; it does not give the UI a real-time save confirmation. Use a response-bearing request for a business receipt and treat beacon as supplemental delivery before leaving the page.

How can you verify queueing, receipt, and persistence separately?

On a test page, record the sendBeacon Boolean and payload byte size. On the server, record request IDs, parse results, and commit status. Exercise offline transitions, background suspension, process termination, queue-limit exhaustion, server errors, and persistence failures. Compare the three kinds of evidence. Do not rely only on browser network tools because their state may be incomplete after a page closes; correlate with server logs and queryable event IDs.

If the call returns true but there is no server record, queue acceptance did not prove delivery. If there is a server record without a commit, receipt did not prove persistence. If a commit exists but the client has no acknowledgment, the result is unknown to the page. If the method returns false, check whether the application should reduce the data rather than retry forever. No browser or server experiment was run for this article; these are suggested test paths, not observed results.

When should you use a beacon, and when an acknowledgment protocol?

Small performance telemetry, diagnostic signals, or analytics that may be lost can fit sendBeacon's non-blocking queue semantics near page unload. Orders, payments, permission changes, legal consent, and individually auditable data need an API or reliable message channel with a response, authentication, persistence confirmation, and retry/deduplication design. Choose based on the business cost of loss and duplication, not merely on how convenient the call is.

This article follows the MDN API documentation for the return value and data limit. It does not claim that an event was delivered or stored. Application metrics should distinguish queued, received, stored, and dropped states so operators can locate failure in the browser queue, network, server processing, or persistence stage.

Include privacy and capacity in page-exit telemetry. Sending several objects during teardown can serialize full URLs, user input, or identifiers, increasing both payload size and sensitive-data retention. Apply a field allowlist and sampling before serialization, then pack against a UTF-8 byte budget. Data that should not be sent should be removed before payload creation, not merely discarded by the server. Batching, compression, and retries still need to respect the 64 KiB total queue limit and browser page lifecycle.

Related reading: the site’s why tail sampling cannot restore an already-lost trace. Page-exit events need their own ID and separate client queueing, server receipt, and persistence stages; sampling gaps are another observability cause.

An event identifier should survive the part of the lifecycle that can be retried. Generate it before page teardown and reuse it if another authorized path later reconciles the same event; otherwise client-side retry can create a second logical event even if the server deduplicates identical payloads. On the server, set a retention period for deduplication keys that covers the expected delayed-delivery window, and record whether the key was new, duplicate, or malformed. This improves duplicate handling, but still does not turn a queued beacon into a client-visible durable acknowledgment.
