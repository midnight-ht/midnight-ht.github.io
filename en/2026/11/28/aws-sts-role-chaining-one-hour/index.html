Why are chained AWS role credentials limited to one hour when the target allows 12?

AWS role chaining depends on the credential source: assuming another role with temporary credentials from one role caps the session at one hour. That limit does not apply to an initial assumption from user credentials.

Key takeaways

  • Role chaining occurs when temporary credentials for one role are used to call AssumeRole again.
  • A chained role session is limited to one hour even if the target role permits longer sessions.
  • Do not apply the same limit to an initial assumption from user credentials or to an EC2 instance-profile path.

When an application uses temporary credentials for one role to call AssumeRole and obtain another role, AWS calls it role chaining and caps the chained session at one hour. Setting the target role's maximum session duration to a longer value does not remove that limit. Conversely, if user credentials are assuming a role for the first time, or an EC2 instance obtains role credentials through an instance profile, do not assume that every session must end within one hour simply because you saw that limit. Trace the credential source first, then inspect the target role configuration.

Draw the role chain before changing a duration

A common chain looks like this: a user or federated identity obtains credentials for role A; an application uses A's temporary credentials to call STS AssumeRole; STS returns another set of temporary credentials for role B; the application uses B to access a resource. The second call is “assume another role using existing role credentials,” so it is role chaining. MaxSessionDuration on the target role is a configuration boundary, not a pass that bypasses the chained-session cap.

Another path is a user credential directly assuming role A. It does not contain the “role A temporary credentials then call AssumeRole” hop. The AWS IAM guide explicitly says the one-hour limit does not apply to the initial assumption from user credentials or to an application running on an EC2 instance profile. Check the actual STS API and credential provider for federation, workload identity, and role-chain boundaries. The final access-key prefix or target role name alone does not reveal the full path.

A hypothetical long job: an expiration error after 70 minutes

Imagine a CI job that obtains role A through OIDC federation and then assumes deployment role B. The deployment takes 90 minutes. If B is configured for a 12-hour maximum session, an engineer may expect its credentials to last for the entire job. The chained-session cap can still limit the session to one hour. The first 55 minutes work; a later upload fails because the temporary credentials have expired. Increasing the target role's configured maximum will not extend this chain's effective limit.

Refreshing credentials at minute 55 requires checking that the provider can still reacquire A's credentials, that authorization remains valid at every hop, and that refresh cannot switch accounts or roles. If the source credentials have expired or the workflow identity token is no longer available, refresh can fail as well. This is a hypothetical timeline derived from AWS's documented limit, not a report of a CI incident.

Three design directions for longer tasks

First, remove unnecessary role hops. A trusted workload may be able to assume a minimally privileged target role directly, avoiding an intermediate role. But this changes trust policies and account boundaries; do not broaden permissions solely to make sessions last longer. Second, design short-lived credential renewal: request new credentials before expiry from a source that can still be authenticated, and ensure each AssumeRole step still satisfies its trust relationship and session policy. Third, split the job into recoverable phases so state is persisted between phases instead of depending on one fixed set of credentials for the entire run.

Renewal is not the same as a long-lived key. Temporary credentials should have a short lifetime and only the actions and resources needed. Logs must never include a secret access key or session token. Also account for session tags, external IDs, source identity, MFA, and permission boundaries so a renewed session does not accidentally gain broader access. If renewal is impossible or requires human approval, stop at an auditable, retryable stage instead of silently continuing with expired credentials.

How can logs and configuration prove that this is role chaining?

For each credential issuance, record non-secret identity metadata: caller ARN, target role ARN, AssumeRole API, requested duration, session name, source identity, and CloudTrail event time. Never log the credentials themselves. Compare the call sequence to determine whether the caller for the second hop is itself a role session. The target role's maximum duration alone is insufficient. Check whether AWS errors point to the chained-session limit, and verify that client clock skew is not a separate expiration cause.

In an isolated account, compare two paths: user credentials directly assuming a role and role A credentials assuming role B. Request durations longer than an hour in each and inspect the expiration time actually returned by the service. Also test renewal during a job, source identity revocation, temporary STS unavailability, and target trust-policy changes. Do not generalize one simulated provider result to every organizational SSO or OIDC flow, especially when the actual chain may contain a hidden intermediate role.

When should you remove a hop, and when should you refresh?

For short jobs or work that can resume by phase, accepting the one-hour cap and handling failure clearly may be simplest. A long cross-account task should use explicit renewal or phases and document its principal chain for operators. Direct role assumption can reduce complexity but may change the security boundary. An intermediate role can isolate trust but adds credential-renewal and audit work. Choose based on least privilege, identity-source reliability, recoverability, and audit needs, not only a duration value on one role.

This article follows the AWS IAM documentation on the role-chaining limit. No AWS account was accessed and no AssumeRole call was run. Before rollout, inspect the actual OIDC, SSO, or EC2 credential path and CloudTrail to identify which calls are second-hop assumptions. Credential renewal, long-lived user identity, and job idempotency are separate design questions.

Audit renewal from the source identity through to the final resource. A successful refresh means STS returned new credentials; it does not prove that the new session has the expected session policy, tags, or resource scope. Compare caller/role ARNs, expiration, permission simulation, and CloudTrail events before and after renewal to ensure a fallback provider did not switch to a developer's personal identity. On failure, stop, alert, or use a documented manual recovery path; do not use a long-lived static key as an automatic fallback.
