Python 3.14 buffersize bounds submissions without changing result order

In Python 3.14, Executor.map buffersize limits submitted tasks whose results have not been yielded; map still returns results in input order. It provides bounded backpressure, not a completion-order stream.

Key takeaways

  • Without buffersize, Executor.map collects its input iterable eagerly.
  • Once the buffer is full, input iteration pauses, bounding submitted tasks whose results have not been delivered.
  • Results are still yielded in input order, so an early slow task can cause head-of-line waiting.

Python 3.14's Executor.map(..., buffersize=n) can limit the window of tasks that have been submitted but whose results have not yet been delivered. When the window reaches its limit, map pauses reading the input iterable, preventing an unbounded source from turning into a large set of Futures. Results are still yielded in input order. In other words, this adds bounded submission and backpressure; it does not turn map into “return whichever task finishes first.” Before choosing it, decide whether the caller needs ordered output or completion-order consumption.

What does buffersize actually bound?

Without a buffer limit, the traditional Executor.map collects its iterables and submits the work. That is convenient for a small finite list. With a database cursor, file stream, or infinite generator, it can read many items early and create a large amount of pending work. Python 3.14 added buffersize: once the number of submitted tasks whose results have not been yielded reaches the limit, input iteration pauses until a result is consumed and a slot becomes available. The parameter changes the amount of work in flight between the input source and result iterator, not the number of threads or processes.

max_workers and buffersize act at different layers. The first controls how many workers may run concurrently. The second controls how much submitted work can remain queued or complete but not yet consumed by the map iterator. For example, eight workers and a buffer of sixteen may allow roughly two worker waves of work in the pipeline, but real memory also depends on each input, result size, task-local caches, and executor implementation. A buffer number is not a direct process-memory cap.

Why can a slow result still block the iterator?

The API preserves input order. Suppose task 0 needs 20 seconds while tasks 1 through 15 each take 100 milliseconds. Later Futures can finish early, yet the iterator waits for task 0 before delivering the next result. Tasks that have not been yielded continue to occupy buffer slots. Once the window fills, the producer stops reading new input. That head-of-line blocking is not a buffersize bug; it follows from ordered delivery combined with bounded buffering.

If the application must process any completed result immediately, Executor.map may be the wrong abstraction. You can manage Futures with submit and as_completed, or maintain your own bounded pending set. But completion-order consumption loses the natural input-position alignment. Associate each Future with an input ID and decide explicitly whether later processing needs to restore order. First determine whether order is a correctness requirement, a convenience, or an accidental dependency.

Hypothetical example: a slow first item and large results

Imagine a generator that reads compressed logs one record at a time. Each task parses a large object, and the consumer writes a report in source-file order. max_workers=8 and buffersize=8 allow initial tasks to run in parallel while keeping the window of submitted, unconsumed results near one worker wave. If task 0 is unusually slow, later results occupy the window and the generator pauses. That bounds input and result accumulation, but it also limits the opportunity to prefetch more work for idle workers. A larger buffer may use workers more effectively during variable workloads, but it retains more unconsumed results. A smaller buffer saves pending space but can leave workers waiting for input. These values illustrate a tradeoff; they are not performance recommendations.

Another failure mode occurs when the consumer reads a result and then blocks on a network write. The map iterator cannot deliver results promptly, so the window fills and the producer experiences backpressure. If the system mislabels this pause as “the thread pool is stuck,” an operator may add workers without fixing the slow consumer or output backlog. Measure input production, task execution, result delivery, and downstream writing separately to locate the actual bottleneck.

How should you choose a window and verify backpressure?

Estimate peak task rate, typical and worst-case input/result size, consumer speed, and how many submitted but unconsumed results are acceptable. Do not choose a buffer by copying the worker count alone; it also needs to tolerate occasional slow tasks and brief consumer pauses. Start with one worker wave in an isolated environment, then increase gradually while observing executor utilization, peak memory, source read rate, and result waiting time. If result objects are large, a smaller window may be worth more than a few extra concurrent tasks. With stable, lightweight work, a somewhat larger window may reduce worker starvation.

Test at least these cases: a lazy generator stops reading when the buffer is full; a slow early task still yields in input order; an exception appears when the iterator reaches the corresponding result; a slow consumer propagates pressure back to the source; and remaining Futures are handled after cancellation or executor shutdown. Testing only list(executor.map(...)) hides consumer pacing and the memory window because it immediately collects all output. The example values and timings here are hypothetical; no benchmark or Python task test was run for this article.

Where does it fit, and where does it not?

buffersize fits ordered transformations where both the input source and undelivered results need explicit bounds: ordered stream conversion, batch file processing, or cursor consumption. For a small bounded input, the default may be simpler. If work must consume any completion immediately, explicit Future management is clearer. A strict end-to-end memory budget also requires limits on input objects, task-local caches, and downstream queues. The parameter only bounds the map submission window; it does not close a database cursor, cancel a remote task, or recover a failed side effect.

At the version boundary, buffersize is new in Python 3.14; older interpreters reject the keyword. Check the deployed interpreter rather than assuming that documentation on a development machine matches production. This article follows the Python 3.14 library reference and reports no execution in a project environment. The choice depends on ordering semantics, object size, and consumer pacing, not on treating one integer as a universal concurrency knob.

If the input iterable has side effects—for example, advancing a database cursor—pausing consumption affects more than memory: it can extend the lifetime of upstream resources. When a full window stalls the generator, a database transaction or file handle may remain open. Ensure the producer can pause, close, and resume safely so backpressure does not become lock occupancy. Check whether the input source is cleaned up when result iteration exits after an exception. An end-to-end buffer budget must include the task queue, source connection, and result buffers, not only the number of Futures.

Test exceptional exit as well. If the consumer raises while handling result k, leaving the loop does not necessarily mean that all submitted work has stopped; tasks may still be running and Futures may still hold results. Validate executor shutdown policy, cancellation of pending tasks, and generator cleanup separately. buffersize bounds the map window; it is not automatic cancellation, timeout, or resource reclamation. For tasks that modify external systems, define idempotent recovery for calls whose outcome is unknown when the executor closes.
