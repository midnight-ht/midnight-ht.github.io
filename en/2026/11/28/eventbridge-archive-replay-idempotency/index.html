Why can replaying an EventBridge archive repeat side effects?

EventBridge archive replay resends events from a selected time range to the original event bus. It does not undo consumer side effects or preserve original arrival order; scope targets and protect downstream writes first.

Article

Key takeaways

  • An EventBridge archive replays only to the event bus that originally received the events.
  • Replay processes event-time intervals and does not guarantee the archive's original arrival order.
  • The replay-name field identifies replayed events, but consumers still need idempotency or isolation for side effects.

An EventBridge archive replay resends events from a selected time range to the event bus that originally received them. It does not undo side effects that consumers already completed, and it does not guarantee that events arrive again in the order they originally entered the archive. If a consumer sends email, charges a payment, creates a ticket, or updates state, decide how to prevent duplicate side effects before replaying. “This is a recovery operation” does not automatically tell the consumer that it processed the business event before.

Archive retention and replay scope are separate choices

When creating an archive, you can use an event pattern to filter what is retained and choose a retention period. AWS documentation says an archive can retain events indefinitely by default, but confirm the actual account configuration. To start a replay, specify a time range and optionally choose rules on the original event bus. An archive replay can return only to the source bus; it is not an export mechanism for an arbitrary destination bus. Events remain in the archive after replay and can be replayed multiple times until they exceed retention or the archive is deleted.

This makes replay a redelivery, not a move or an “undo then restore.” AWS adds replay-name metadata to replayed events and uses it to prevent them from returning to the archive. Consumers can distinguish replay traffic from live events, isolate it, or record the name in an audit field. But this marker is not a business idempotency key and does not prevent the same event from triggering a second payment or email.

Hypothetical case: recovering order events sends duplicate notices

Suppose a consumer handles OrderPaid by sending a receipt and changing the order state to notified. A deployment interruption means some events were not delivered successfully, so an operator plans to replay the last 30 minutes. Some events may actually have been processed; only the acknowledgment or downstream metric was lost. When replayed, the same order may run through the consumer again. If email sending is not idempotent, the customer receives a second receipt. A database update from paid to paid may look harmless, but it does not prove that the external email was not duplicated.

Separate transport event IDs from idempotency keys for business side effects. Before sending, the consumer can record a deduplication key associated with the order and notice type, and make external-send state recoverable with an outbox or a reconciliation boundary. If the mail provider offers no idempotency, define a manual review path. replay-name can annotate the recovery batch, but the business event ID still needs to be compared with the side-effect record. This is an architecture example; no replay was run against a real order system.

The replay window is not original arrival order

AWS says there may be a delay before an event reaches the archive and recommends waiting 10 minutes before replay so events have arrived. Replay processes events using the time in the event in one-minute intervals; for a 20-minute range, it processes the first minute and then the next. Even though the ranges advance in time, do not assume that events within an interval follow their original archive-arrival order. Business event time and delivery time may also differ.

If a system depends on strict order—for example, an account must be opened before a balance change—selecting a time range does not automatically reconstruct that sequence. A consumer may need aggregate-version checks, rejection of stale updates, or a dedicated validation flow before applying side effects. Inspect DescribeReplay progress and EventLastReplayedTime, but do not interpret the last replay timestamp as proof that every target completed its business operation.

How can you reduce impact before replay?

Verify the archive pattern and retention settings, then confirm the selected interval and event origin. Enumerate rules and targets on the original bus: which consumers will run, which create external side effects, and which only build analytics or indexes. You can scope replay with rules, but rule changes also need review and rollback. A high-risk consumer can first parse events in an isolated target or dry-run path and count candidate events, duplicate business IDs, time ranges, and records that cannot be correlated.

Prepare an idempotency strategy, rate limits, a pause switch, and stop conditions. AWS notes that replay may be separate from the account's PutEvents transaction-per-second quota, but regional replay concurrency limits still apply. Plan throughput against current quotas and target capacity. If duplicate rates rise, ordering conflicts appear, or state regresses, pause replay and preserve progress evidence instead of widening the window. Because replay advances by minute intervals, align pause/resume decisions with replay status, time range, and business acknowledgment.

How do you accept recovery without confusing delivery with business completion?

On a test event bus, create an event, consume it once normally, and replay a range that includes it. Confirm that the target sees replay-name, that the idempotency key keeps the side effect unique, and that delivery count and business-write count are recorded separately. Also cover delayed archive arrival, repeated replay of the same interval, consumer failure, an excluded rule, and a mismatch between event time and creation order. Before testing, confirm that the archive retained the event under its actual filter.

Production recovery acceptance should combine EventBridge replay state, target-delivery metrics, consumer outcomes, and a business side-effect ledger. “Replay completed” proves the AWS replay process state; it does not prove that every Lambda, queue, HTTP endpoint, or external system finished its business work. No AWS account was accessed and no replay was run for this article. Verify current regional quotas, target latency, and recovery behavior for the actual consumer.

Limits of the mechanism

Archive replay is useful for reprocessing retained events after a consumer fix or for applying new logic to historical input. It is not a transaction rollback, global ordering service, cross-bus replication feature, or deduplication service. If historical events can trigger real-world side effects, make targets recognize replay, implement idempotency, and provide a stop control before selecting the window. The final evidence of correct recovery is agreement between business state and the side-effect ledger—not merely a replay status of COMPLETED.

Rules can also change while a replay is running. Temporarily disabling one rule to narrow scope may leave another default rule delivering events to a side-effecting target. Enumerate all matching rules before starting and record rule changes during the replay. Regional concurrent-replay limits affect queueing and staged recovery. A pause can stop later processing, but it cannot retract events already delivered to Lambda, a queue, or an external HTTP service.
