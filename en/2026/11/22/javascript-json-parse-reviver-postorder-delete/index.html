Why does a JSON reviver visit children before their parent?

Trace child deletion and the parent snapshot, then inspect a new array-index case without confusing deletion with compaction.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-22 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • Child callbacks run before their containing value
  • Returning undefined requests deletion
  • Parent rules see the processed structure

A JSON.parse reviver processes child properties before receiving their containing object. Returning undefined from a child callback deletes that property, so the nested callback can already see an empty object after nested.b is removed. Arrange nested cleanup rules around this postorder traversal and explicitly return values that should remain.

The parent does not receive an original-structure snapshot

The parser first creates a value, then recursively processes its properties. For an ordinary object, the algorithm obtains enumerable own keys and enters their values. It applies each child callback’s result by deleting or updating the property before calling the reviver for the containing value. The parent therefore receives a structure whose children have already been processed.

The ECMAScript InternalizeJSONProperty algorithm lists recursion, deletion or creation, and the current callback in that order. This explanation uses the current ECMAScript 2027 specification and fixed JSON data. It does not introduce callbacks that add keys or otherwise mutate traversal unexpectedly.

The return value is part of the contract: return the current value to retain it, another value to replace it, or undefined to delete it. Adding a log without a return statement is not a neutral observation. If every callback does that, the effect can reach the final result. A logging-only reviver must return the value it intends to preserve.

This has a different purpose from JSON number precision and long identifiers. That article explains information lost before a callback receives a numeric value. Here, the question is how an already-created structure is visited and modified. Traversal order cannot restore information lost during earlier numeric conversion.

Check order, parent input, and final shape separately

The fixed input contains a and a nested object containing b. Only b is removed; every other callback returns its current value. The nested callback records Object.keys immediately, preserving a key list from that moment rather than retaining a mutable object reference for later inspection.

import assert from 'node:assert/strict';
const order = [];
let parentKeys;
const result = JSON.parse('{"a":1,"nested":{"b":2}}', (key, value) => {
  order.push(key);
  if (key === 'b') return undefined;
  if (key === 'nested') parentKeys = Object.keys(value);
  return value;
});
assert.deepEqual(order, ['a', 'b', 'nested', '']);
assert.deepEqual(parentKeys, []);
assert.deepEqual(result, {a: 1, nested: {}});
console.log(JSON.stringify({order, parentKeys, result}));

The exact module ran locally in Node. The key trace was a, b, nested, and the empty string. The nested callback recorded no keys. After traversal, the result retained a with value 1 and an empty nested object. That final empty-string callback is arranged by the parsing entry point for the overall value; it is not an extra business field inserted into the original JSON.

Each assertion has a separate purpose. The trace rules out parent-before-child assumptions. The parent key snapshot shows that deletion has already occurred. The final shape confirms that the containing object was returned and retained. Checking only that b is absent would not expose every mistaken assumption about timing; checking only callback count would not identify which field was removed.

The key order also has a scope. This fixture uses ordinary textual keys a and nested rather than integer-like keys whose enumeration rules introduce another consideration. It contains no duplicate names. More complex key sets require their own property-enumeration expectations; this four-call sequence is not a promise about arbitrary source-text order.

A callback’s key is not a full path. The same name can occur in several nested objects. The b rule is deliberately narrow for this fixed input, not a general business cleaner that should erase every field with that name. A position-sensitive policy needs a representation of its path or structural role rather than depending on a fixture with one occurrence.

Place each rule where its required evidence exists

Suppose a product wants to retain a parent only if required children remain after conversion. A postorder callback can inspect those processed children and decide. That is an application rule, however, not automatic JSON validation. Returning an empty object keeps it; deleting a child does not automatically delete its empty container.

If a parent rule instead needs the original child set, reading the current value at the parent stage cannot reconstruct it. Child callbacks may already have removed fields. Preserve the required original structure separately, or parse first and perform an explicit transformation against a defined input snapshot. Choose the location from the rule’s evidence requirements rather than squeezing every operation into one callback.

Diagnostic records need the same attention to time. Keeping an object reference and inspecting it after later mutation does not establish what its contents were when the reference was saved. The fixture copies the required key list immediately. Other snapshot strategies should state which values were copied and which remain shared before calling them historical state.

Local execution covers this fixed module, not an API, import file, or server framework. Before changing a real cleanup rule, combine fields that must remain with fields that must disappear, retain callback positions, and verify the final structure. A logging-only branch particularly needs a preservation assertion so a debugging change cannot silently become data deletion.

Does returning undefined for an array item shift later elements left?

No. This introduces array indices. The array branch recursively visits each index and deletes the corresponding property when the callback returns undefined. It does not perform splice, shift later values left, or shorten the original length as a consequence of that deletion.

import assert from 'node:assert/strict';
const result = JSON.parse('[1,2,3]', (key, value) => value === 2 ? undefined : value);
assert.equal(result.length, 3);
assert.equal(Object.hasOwn(result, 1), false);
assert.equal(Object.hasOwn(result, 2), true);
assert.equal(result[2], 3);
console.log(JSON.stringify({length: result.length, keys: Object.keys(result), last: result[2]}));

This separate script also passed locally. Length remains 3, the own keys are 0 and 2, and index 2 still contains 3. Object.hasOwn distinguishes an absent index from an existing property whose value is undefined. Merely reading result[1] can produce undefined for either shape.

Avoid introducing another representation ambiguity when displaying the entire array. A later serializer may represent a missing item with a placeholder; that does not mean the reviver inserted that value. The fixture prints the key list and last item while retaining explicit existence assertions. If the product needs a compact array, implement that as a separate, specified transformation rather than reading automatic compaction into the deletion contract.
