Why does an updated image not start a rollout while a Deployment is paused?

Correlate paused template edits with the resumed rollout identity; the cluster fixture is unrun.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-22 · Estimated read 19 min
Translations
zh-CN en

Article

Key takeaways

  • Paused template edits do not trigger a new rollout.
  • Inspect the final template after resuming, not just command echoes.
  • A paused Deployment must be resumed before rollback.

Pod-template edits do not trigger a new rollout while a Deployment is paused. Resuming lets the accumulated template progress. An accepted image update establishes desired configuration, not replacement Pods. Check paused state, template identity, ReplicaSets, and current generation separately.

A maintainer might update an image and then CPU requests before releasing both together. Pausing creates that editing window; it does not freeze existing Pods or stop the application. Neither absence of a new rollout nor a command echo establishes that the new version is running.

Begin with a completed baseline

These are complete inputs for an isolated cluster. No cluster was contacted, kubectl was not run, and the object oracle below was not evaluated. Only YAML parsing, shell syntax, and Python syntax were checked. None certifies pause, resume, or application execution. Use a context with namespace permissions, working controllers, and accessible images.

Save deployment.yaml. Two replicas and HTTP readiness are teaching choices, not capacity or business-health requirements. Confirm both initial and later alpine-tag images are obtainable. Tags do not supply an immutable byte-identity guarantee.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: zy22-pause
spec:
  replicas: 2
  selector:
    matchLabels:
      app: zy22-pause
  template:
    metadata:
      labels:
        app: zy22-pause
    spec:
      containers:
        - name: web
          image: nginx:1.28.0
          resources:
            requests:
              cpu: 50m
          readinessProbe:
            httpGet:
              path: /
              port: 80

Save check.sh, replace the context placeholder, and use an absent dedicated namespace where only this exercise changes the objects. Stop on creation failure. The snapshot function records Deployment and ReplicaSet state under each stage; the oracle filters owned objects by one Deployment UID.

set -eu
context=REPLACE_WITH_ISOLATED_CONTEXT
namespace=zy22-pause-lab
deploy=deployment/zy22-pause
k() { kubectl --context "$context" --namespace "$namespace" "$@"; }
snapshot() {
  k get "$deploy" -o json > "$1-deployment.json"
  k get replicasets -o json > "$1-replicasets.json"
}
k create namespace "$namespace"
k apply -f deployment.yaml
k rollout status "$deploy" --timeout=120s
snapshot initial
k rollout pause "$deploy"
k set image "$deploy" web=nginx:1.28.0-alpine
snapshot image
k set resources "$deploy" -c=web --requests=cpu=100m
snapshot resources
k rollout resume "$deploy"
k rollout status "$deploy" --timeout=120s
snapshot resumed
python3 inspect.py

Wait for the baseline to complete before attributing later non-rollout to pausing. Image retrieval, readiness, and an unobserved generation can block the initial rollout independently. Repair those prerequisites and preserve their diagnostics rather than allowing a final successful recovery to overwrite them.

Compare desired templates with rollout objects

Save inspect.py. It reads four real command snapshots, verifies both paused edits in spec, checks that no additional owned ReplicaSet appeared during the pause, and verifies completed counts and combined template after resume. Do not hand-fill JSON to make it pass. No synthetic snapshots were substituted for cluster receipts here.

import json
from pathlib import Path


def read_stage(name):
    deployment = json.loads(Path(name + "-deployment.json").read_text())
    items = json.loads(Path(name + "-replicasets.json").read_text())["items"]
    uid = deployment["metadata"]["uid"]
    owned = [item for item in items if any(
        owner.get("uid") == uid and owner.get("controller") is True
        for owner in item["metadata"].get("ownerReferences", []))]
    return deployment, owned


def web(template):
    return next(item for item in template["spec"]["containers"] if item["name"] == "web")


expected_image = "nginx:1.28.0-alpine"

initial, initial_sets = read_stage("initial")
uid = initial["metadata"]["uid"]
baseline_ids = {item["metadata"]["uid"] for item in initial_sets}
assert baseline_ids
for stage in ("image", "resources"):
    deployment, sets = read_stage(stage)
    assert deployment["metadata"]["uid"] == uid
    assert deployment["spec"]["paused"] is True
    assert web(deployment["spec"]["template"])["image"] == expected_image
    assert {item["metadata"]["uid"] for item in sets} == baseline_ids
    if stage == "resources":
        assert web(deployment["spec"]["template"])["resources"]["requests"]["cpu"] == "100m"
resumed, resumed_sets = read_stage("resumed")
assert resumed["metadata"]["uid"] == uid
assert not resumed["spec"].get("paused", False)
assert resumed["status"]["observedGeneration"] >= resumed["metadata"]["generation"]
assert resumed["status"]["replicas"] == resumed["spec"]["replicas"]
assert resumed["status"]["updatedReplicas"] == resumed["spec"]["replicas"]
assert resumed["status"]["availableReplicas"] == resumed["spec"]["replicas"]
assert any(web(item["spec"]["template"])["image"] == expected_image
           and web(item["spec"]["template"])["resources"]["requests"]["cpu"] == "100m"
           for item in resumed_sets)
print("PAUSED_EDITS_AND_RESUMED_TEMPLATE_OK", uid)

In the image stage, expect the desired image to change while owned ReplicaSet identities remain the baseline set. Resources then adds the new CPU request. After resuming, expect the current generation to be observed, the rollout complete, and a ReplicaSet template containing both final settings. The comparison does not prescribe a global ReplicaSet count or include unrelated objects.

This fixture assumes one controller of intentional edits during its window. Another operator, GitOps controller, or automation changing the template changes the inputs. Preserve that evidence and reinterpret the result rather than calling a failed set comparison a Kubernetes contract violation.

The official pause/resume section explicitly demonstrates image and resource edits while paused followed by their combined rollout. This bounds template-triggered rollout, not every controller action. Existing replicas remain under normal management.

No new object has more than one explanation

A screenshot of unchanged counts does not establish that API edits succeeded or that the controller could progress. Check spec.paused, accepted template contents, ownership, and events. Permission or connectivity failures can prevent the intended input and cannot serve as evidence that pause worked.

Desired and running images may differ during the pause. Report “template updated, rollout still paused” rather than “image upgraded.” After resume, obtain fresh template and status receipts instead of relabeling the earlier desired-state receipt as execution evidence.

Pods may still be replaced through normal health management or other causes. The contract is not that all Pod UIDs remain frozen forever. It is that paused template edits do not trigger a new rollout. Uninterrupted-request goals require separate traffic and availability evidence; this example defines no Service and ran no request probe.

Resuming does not sign off a release

Resume removes the pause condition. An inaccessible image, insufficient resources, or failed readiness can still block the release. Retain the resume request, wait result, current generation, and template snapshots to distinguish unpausing from completed rollout. No business version was accepted by this example.

The JSON reads are not an atomic cross-object snapshot. Controller work can continue between them. Preserve boundary-state readings with timestamps and resample the same UID if needed. Do not delete contrary observations and keep only a convenient success. A handoff should permit unknown or missing evidence.

Before cleanup, retain four-stage inputs, command outcomes, actual controller version, and relevant events. Confirm the namespace belongs only to this run, then delete it using the same explicit context if required. A changed context, recreated same-name Deployment, or different template needs fresh UID association rather than a spliced timeline.

Can a paused Deployment be rolled back directly?

The reference says to resume it before rollback. This introduces a different operation: the main example continues accumulated edits, while rollback selects an earlier revision. Resume may start progressing the current template, so confirm the target revision, image, and configuration under the recovery plan before acting. Resume itself does not mean the old version is restored. No rollback was executed here.
