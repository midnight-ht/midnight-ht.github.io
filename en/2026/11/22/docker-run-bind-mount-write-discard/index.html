Why do files written to a writable RUN bind mount vanish in the next step?

Verify RUN bind-write lifetime with separate output paths, a read-only failure, and a stage-source control.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-22 · Estimated read 20 min
Translations
zh-CN en

Article

Key takeaways

  • rw permits current-step writes without persisting them.
  • Write retained outputs outside the mount.
  • from changes the mount source identity.

A writable RUN bind mount retains its writes only until that instruction ends; rw does not commit them to an image layer. Write retained artifacts outside the mount. Seeing a file during generation and reading it in a later step or export are different facts.

A generator may process input under /input and report success, yet a later instruction finds no result. Inspect whether the output landed inside the mount instead of repeatedly rebuilding. Writable does not mean persistent build output.

Compare temporary writes with retained output

This exercise builds locally and exports a file without running nginx, starting a service, or pushing an image. Its existing base supplies the shell tools. Record the resolved image identity rather than treating a tag as permanent byte identity. The context contains harmless teaching inputs only.

Save Dockerfile. The build stage required by the default artifact target changes mounted input.txt, creates temporary.txt, and copies the processed bytes outside the mount to /out. The next RUN checks that the temporary file is gone while the external result remains generated. A scratch stage exports only that result. Cross-step assertions are essential; successful current-step writes cannot replace them.

ARG BASE
FROM ${BASE} AS readonly
RUN --mount=type=bind,source=.,target=/input \
    printf 'unexpected\n' > /input/temporary.txt
FROM ${BASE} AS build
RUN --mount=type=bind,source=.,target=/input,rw \
    printf 'generated\n' > /input/input.txt \
    && printf 'temporary\n' > /input/temporary.txt \
    && mkdir -p /out \
    && cp /input/input.txt /out/result.txt
RUN test ! -e /input/temporary.txt && \
    test "$(cat /out/result.txt)" = generated
FROM scratch AS artifact
COPY --from=build /out/result.txt /result.txt

The same file provides readonly as a negative target. Without rw, the default read-only mount should reject creation. The default artifact depends only on build; the script explicitly selects readonly for its rejection control. BASE is a fixed build argument shared by the relevant FROM instructions, not a Dockerfile generator.

Run the script from the Dockerfile directory. It creates a fresh context containing source in input.txt, then compares source and exported result independently and checks that temporary.txt was not written back. The expected source remains source while the artifact is generated. These are deliberately different byte expectations, not guesses from an old output directory.

set -eu
work=$(mktemp -d)
base=docker.m.daocloud.io/library/nginx:1.28.0-alpine
context="$work/context"
source_file="$context/input.txt"
result_file="$work/out/result.txt"
source_expected="$work/expected-source.txt"
result_expected="$work/expected-result.txt"
mkdir "$context"
printf 'source\n' > "$source_file"
cp Dockerfile "$context/Dockerfile"
docker version --format '{{.Client.Version}} / {{.Server.Version}}'
docker buildx version
docker image inspect "$base" --format '{{.Id}}'
docker buildx build --pull=false --build-arg "BASE=$base" --progress=plain --output "type=local,dest=$work/out" "$context"
printf 'source\n' > "$source_expected"
printf 'generated\n' > "$result_expected"
cmp "$source_expected" "$source_file"
cmp "$result_expected" "$result_file"
test ! -e "$context/temporary.txt"
status=0
docker buildx build --pull=false --build-arg "BASE=$base" --target readonly --progress=plain --output "type=local,dest=$work/rejected" "$context" > "$work/readonly.stdout" 2> "$work/readonly.stderr" || status=$?
test "$status" -ne 0
rg -i 'read-only file system' "$work/readonly.stderr"
printf 'fixture=%s\nreadonly-exit=%s\n' "$work" "$status"

Docker client and server were both 29.8.2, with Buildx 0.37.2. The actual matching build passed its cross-step assertions and external byte comparison, leaving source unchanged. The read-only branch exited one with Read-only file system. Image retrieval, syntax, or network errors were not substituted for that rejection.

The build-cache bind documentation distinguishes default read-only access, discarded rw writes, and retained external output. The Dockerfile option table likewise says mount writes are not committed. This is a build-time RUN mount, not a runtime host-bind editing workflow.

Why can the source remain unchanged while the result changes?

The instruction gets a temporary writable view. It reads modified bytes there and copies them to an ordinary layer path that later steps can read. The retained object is the explicitly written artifact, not the entire mounted input tree. Configure the generator's output location and verify that it actually uses it.

If output location cannot be configured, generate and copy the required result outside the mount within the same RUN, then inspect contents. The copy must happen while the mount exists. A later instruction cannot recover its vanished temporary file. The example's cp follows that order without claiming every generator supports separate output directly.

A filename called result has no special persistence property. Actual paths and mount boundaries determine ownership. Inventory inputs, temporary workspace, and retained artifacts, then check expanded command paths. A generic generation-success line cannot explain a missing final file.

Keep failure and cache evidence distinct

Without the expected read-only diagnostic, preserve the actual error. An unavailable base, unsupported frontend, or absent command never exercised write permission. Restore prerequisites and rerun the same negative branch instead of relabeling any nonzero result as a passed read-only check.

Report cache use from logs. Reuse may provide an existing result without running generation again. This exercise retains build output and an independent exported-file cmp. On a cached repeat, do not describe it as fresh network retrieval or full tool execution. Positive output, negative rejection, and readback have different evidentiary roles.

The final main and stage-source reruns both logged cached steps, so neither is described as executing every generation command afresh. The external source and exported-byte comparisons still ran in this invocation, and the read-only target produced its specific rejection again.

Output must belong to the current invocation too. Fresh temporary directories avoid mistaking old result.txt for a failed build's new artifact. Define output ownership and cleanup when integrating with an existing pipeline rather than recycling a public directory without identity.

This does not verify application execution

The scratch stage contains a file and no service process. Matching bytes do not establish startup or downstream parsing. An executable artifact still needs its intended architecture and runtime dependencies plus behavior checks. No product execution, speedup, or release availability was established here.

Temporary writes do not decide source trust either. Public text, generated code, and dependencies need their own provenance and content review. A mount does not automatically constrain the generator's entire input access. This minimal harmless context is not an audit of a real project's inputs.

Before cleanup, retain Dockerfiles, input, resolved image identity, versions, outputs, and exported-byte checks. Remove only the printed fixture directory rather than other caches or outputs by a broad prefix. A reviewer should reconstruct unchanged source, discarded temporary writes, and explicitly retained output separately.

What if the source must come from another build stage?

This new condition selects the source with from. The independent Dockerfile below creates stage-source in seed and mounts /seeds from that stage instead of the context root. It was built and exported too: the result was stage-source while a same-named context file contained context-source and remained unchanged. Equal names are not equal source identities.

ARG BASE
FROM ${BASE} AS seed
RUN mkdir -p /seeds && printf 'stage-source\n' > /seeds/input.txt && \
    test "$(cat /seeds/input.txt)" = stage-source
FROM ${BASE} AS build
RUN --mount=type=bind,from=seed,source=/seeds,target=/input \
    mkdir -p /out && cp /input/input.txt /out/result.txt
FROM scratch
COPY --from=build /out/result.txt /result.txt

Save it as stage.Dockerfile. These complete commands use a fresh context and local export and compare exact stage-source bytes.

set -eu
work=$(mktemp -d)
base=docker.m.daocloud.io/library/nginx:1.28.0-alpine
context="$work/context"
source_file="$context/input.txt"
result_file="$work/out/result.txt"
expected="$work/expected.txt"
mkdir "$context"
cp stage.Dockerfile "$context/Dockerfile"
printf 'context-source\n' > "$source_file"
docker buildx build --pull=false --build-arg "BASE=$base" --progress=plain --output "type=local,dest=$work/out" "$context"
printf 'stage-source\n' > "$expected"
cmp "$expected" "$result_file"
test "$(cat "$source_file")" = context-source
printf 'STAGE_SOURCE_OK\nfixture=%s\n' "$work"

The current reference allows stages, contexts, or images as from sources. Retain the chosen source's identity; the main context readback cannot certify this new stage-source case.
