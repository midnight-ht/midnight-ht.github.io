Why can a stored string still fail isWellFormed?

Inspect lone and paired UTF-16 surrogates by exact units, distinguish replacement from recovery, and test a new URI-encoding consumer.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-22 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • A string value can contain lone surrogates
  • Replacement does not recover a missing character
  • Preserve originals and apply an explicit receiver policy

A JavaScript string can exist without containing correctly paired UTF-16 surrogates. isWellFormed detects lone surrogates; toWellFormed replaces them with U+FFFD. The transformation produces a well-formed result but does not recover a missing original character. Preserve the input, inspect its code units, and explicitly choose acceptance, rejection, or replacement.

A string value and valid pairing are different checks

A JavaScript string can contain a high or low surrogate on its own. A supplementary code point normally needs a surrogate pair, but a string containing only one half can still be passed around. It has length, supports concatenation, and may display as a replacement-like glyph. None of those observations establishes complete original encoding.

The ECMAScript isWellFormed and toWellFormed definitions cover checking and transformation respectively. The latter walks code points and replaces high or low surrogates that are not part of a pair. The source is the current ECMAScript 2027 specification, not a claim that every deployed client supports these methods.

Detection does not select a business policy. A restricted field may reject incomplete input; a display field may allow explicitly documented replacement. Either choice needs a policy for retaining originals and communicating changes. Providing a repair method does not require applications to overwrite every original silently.

Three fixed inputs, before and after

The main fixture uses a lone high surrogate, a lone low surrogate, and a correctly paired simple smiling face. Escapes specify the actual input units rather than relying on editor appearance. charCodeAt reads UTF-16 units by index; code-point iteration is not substituted for that measurement.

import assert from 'node:assert/strict';
const units = text => Array.from({length: text.length}, (_, i) => text.charCodeAt(i));
const samples = ['\uD800', '\uDC00', '\uD83D\uDE00'];
const observations = samples.map(original => ({
  wellFormed: original.isWellFormed(),
  before: units(original),
  after: units(original.toWellFormed())
}));
assert.deepEqual(observations, [
  {wellFormed: false, before: [55296], after: [65533]},
  {wellFormed: false, before: [56320], after: [65533]},
  {wellFormed: true, before: [55357, 56832], after: [55357, 56832]}
]);
console.log(JSON.stringify(observations));

The exact module ran locally in Node. Both lone inputs returned false and became the single unit 65533 after repair. The paired input returned true and retained units 55357 and 56832. Independent expectations constrain both the boolean and the transformed units, rather than merely checking whether a method throws.

Both lone inputs produce the same replacement character, demonstrating that this is not reversible recovery. The repaired unit does not identify which original half was present, or even whether a source already contained a legitimate U+FFFD. If diagnosis needs that history, preserve the input and transformation record instead of overwriting them with the result.

The valid pair is an important negative control. An implementation that replaces every surrogate indiscriminately could pass both invalid-input assertions while destroying valid text. Requiring the paired sample to remain unchanged detects that excessive transformation. Testing only failures does not establish that already-valid text survives.

Appearance does not identify the original units

A replacement glyph is a presentation choice. The input may contain an actual U+FFFD, or a renderer may display a lone unit in a similar way. Matching screenshots do not establish matching units. Recording original and repaired arrays locates the transformation layer instead of mistaking display tolerance for intact input.

The article on textarea length and UTF-16 units explains how truncation can split a pair. This article does not choose a text quota; it checks a string already received. If a source repeatedly produces lone units, replacing them at display time does not identify the stage that damaged them. Trace controlled samples through reading, joining, truncation, and transfer.

Well-formedness is also separate from Unicode normalization. Correctly paired text can have distinct canonically equivalent representations. The article on original names and normalization keys addresses that equivalence relation. A true isWellFormed result does not mean that every business comparison considers the text identical, and normalization is not a substitute for checking surrogate pairing.

The method does not count user-perceived characters, validate language, or decide record identity. Its boolean concerns the specified lone-surrogate condition. Keeping that scope precise helps diagnosis: if this check passes but a receiver still rejects text, inspect the receiver’s separate contract rather than attributing every text error to pairing.

Local results cover the current Node version and fixed samples, not browsers, input methods, file decoding, or storage. Integrating an application still requires checking support and input sources. A compatibility implementation should face the same independent valid and invalid cases; returning a string alone does not establish equivalent behavior.

What happens in encodeURIComponent, and can repaired input be encoded?

This adds a specific downstream consumer. ECMAScript’s Encode algorithm, used by encodeURIComponent, throws URIError for an unpaired surrogate. The original input therefore fails that encoding, while the replacement U+FFFD has its own UTF-8 percent encoding.

import assert from 'node:assert/strict';
const original = '\uD800';
assert.throws(() => encodeURIComponent(original), URIError);
const repaired = original.toWellFormed();
const encoded = encodeURIComponent(repaired);
assert.deepEqual([repaired, encoded], ['\uFFFD', '%EF%BF%BD']);
const observedUnits = [original, repaired].map(value => value.charCodeAt(0));
console.log(JSON.stringify({observedUnits, encoded}));

This separate script also ran locally. The original threw the specified error, and repaired input encoded as %EF%BF%BD. That shows this consumer accepts the replacement character after the input has changed. It does not show recovery of the missing original, and no URL or HTTP request was sent.

For an identity field that requires exact preservation, silently repairing and continuing may violate the contract. Require an explicit policy rather than treating encodability as the only correctness criterion. Retaining original input, transformed value, and receiver rules makes it possible to distinguish valid original text from an intentionally accepted replacement.
