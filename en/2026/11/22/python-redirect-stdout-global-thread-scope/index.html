Why does redirect_stdout capture another thread too?

Separate global capture, restoration and explicit streams with a controlled joined worker and an independent stderr check.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-22 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • redirect_stdout replaces the global sys.stdout binding.
  • Restoration does not isolate who writes during the context.
  • Explicit stream targets and stderr need separate checks.

You redirect a function's output into StringIO and another thread's print appears there too. redirect_stdout temporarily replaces the global sys.stdout; it does not allocate an output channel owned by the current function. Leaving with restores the binding, but restoration does not establish who used that binding in the meantime.

A context limits time, not every caller

A small tool captures a report that normally prints directly. The main thread generates it while a worker in the same process prints progress. If the caller assumes the capture follows only its own call stack, the saved report can unexpectedly contain worker output. A downstream parser may report a broken format even though the underlying issue is a shared output destination.

The official redirect_stdout documentation, checked in Python 3.14.10, explicitly calls out the global side effect and its unsuitability for library code and most threaded applications. A normal with block does not supply thread isolation. The tool can still be useful in a controlled utility script; that is a different operating condition.

Separate restoration time from observation scope. A manager can restore the original target on exit while letting other users of the current global binding observe the temporary target throughout the context. Correct cleanup and unsuitable concurrent scope can coexist. Restoration after an exception would not remove unrelated text already written to the capture.

Construct a controlled ordering without sleeps

The complete fixture saves the original object, prints main, starts a worker that prints one line and joins it before leaving. The order follows explicit actions rather than a timing delay. Its archived receipt records actual execution with Python 3.11.15, code hash, output and exit status. That runtime is distinguished from the documentation version.

import sys
from contextlib import redirect_stderr, redirect_stdout
from io import StringIO
from threading import Thread

read_capture = StringIO.getvalue
original = sys.stdout
captured = StringIO()
with redirect_stdout(captured):
    print("main")
    worker = Thread(target=lambda: print("worker"))
    worker.start()
    worker.join()
assert read_capture(captured) == "main\nworker\n"
assert sys.stdout is original

def emit(stream, message):
    stream.write(message + "\n")

explicit = StringIO()
emit(explicit, "owned")
assert read_capture(explicit) == "owned\n"
out, err = StringIO(), StringIO()
with redirect_stdout(out), redirect_stderr(err):
    print("out")
    print("err", file=sys.stderr)
assert read_capture(out) == "out\n"
assert read_capture(err) == "err\n"
print("global capture, restoration, explicit stream and stderr separation checked")

The complete capture expectation is main followed by worker. This is not a prediction of arbitrary service output ordering. It demonstrates that another thread using the current global entry during this controlled context writes to the same capture. An independent identity check confirms restoration, separating mixed-origin content from a failure to restore.

This is no concurrent stream stress test. The worker has one action and finishes before exit. There are no background tasks retaining the stream, logging frameworks, custom thread-local output proxies or other capture layers. An application with such an existing replacement needs that layer's contract checked separately.

Code retaining a reference to an earlier stream might bypass the current binding. The claim concerns prints using current sys.stdout, not every possible write path. File-descriptor writes, child-process output and configured logging handlers cannot be inferred from this one experiment. The official documentation separately says subprocess output is unaffected; no subprocess was launched by the fixture, so that remains a documented claim rather than a local measurement.

Make the receiver explicit when you own the function

The emit helper accepts a stream and writes owned to that target. It need not replace a process-wide entry or assume ownership of every print in the process. A report function you maintain can accept an in-memory destination in tests and a real output destination at its command-line entry.

That interface is not an isolation wrapper for an arbitrary legacy library. Changing an outer signature does not change a third-party function that internally hardcodes print. The library needs to support a stream, return text or expose another controlled interface. Otherwise decide whether the tool actually owns its execution environment. This article integrates no third-party library or production reporting system.

Stream lifetime also remains a separate contract. The fixture creates its own memory destination and does not close the caller's object inside emit. A real file or network stream can have additional error and ownership rules. Passing a stream does not automatically authorize the callee to close it. This example demonstrates destination ownership without implementing a full resource protocol.

The site's ContextVar task-snapshot article describes how a different kind of context state propagates into tasks. Similar terminology does not turn sys.stdout into a task-local variable. Inspect storage, lookup and propagation rules rather than inferring isolation from with syntax or a function name.

A containment check for main would also be too weak: it passes even with an unexpected extra line. Validate complete text, structure or explicitly allowed additions according to the product. The two-line expectation here exposes the shared binding instead of silently filtering the evidence away.

Is stderr automatically redirected as well?

The new condition is the separate standard-error stream. The fixture redirects stdout and stderr to different memory objects, then prints explicitly to the relevant destinations. The expected out capture contains only out, while the error capture contains only err. Replacing stdout does not automatically choose the same object for stderr.

A tool may intentionally merge those channels, but merging should be an explicit decision. Structured report data can use a return value or designated stream while diagnostics use another target. Validate each according to its own contract. Successful restoration proves the binding was restored, not that the captured content belonged to one caller; first establish who shared the entry during that interval.
