Why does Base64 Strict still accept a newline?

Check valid bits, invalid bits, CRLF and unpadded forms against the precise Strict contract in an unexecuted Go fixture.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-22 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • Strict requires unused trailing padding bits to be zero.
  • Strict decoding still ignores CR and LF.
  • Unpadded encoding and single-line policy are separate choices.

Go's Base64 decoder can still accept embedded line breaks after Strict is enabled. Strict requires unused trailing padding bits to be zero; it continues to ignore carriage returns and line feeds. A protocol requiring one line needs a separate character-format check. A method name is not the complete input policy.

Which layer is strict?

Consider Zg== and Zh==. Ordinary decoding can produce the byte f from both, while the latter violates the strict trailing-bit rule. Insert a newline into the first encoding and its valid trailing bits are unchanged, so strict decoding can still succeed. These results concern meaningful data bits, unused trailing bits and ignored characters respectively.

The encoding/base64 Strict documentation explicitly specifies zero trailing padding bits and immediately notes that CR and LF remain ignored. The snapshot is go1.27.4, published November 10, 2026; Strict was added in Go 1.8. The cited bit rule does not silently supply every text-format restriction an application might want.

Write the receiving contract in separate parts. The decoder checks its encoding rules. The application decides whether line folding is allowed, which alphabet applies and whether padding characters may be omitted. A strict switch without those conditions leaves future callers unsure what successful decoding established.

A complete table with independent expectations

The table uses literal input and expected status rather than treating the ordinary decoder as the oracle for the strict one. It includes standard text, nonzero trailing bits, both line-ending forms and the unpadded follow-up. No Go toolchain is installed here, so this program is unexecuted. Its assertions are a prospective acceptance plan grounded in the documentation.

package main

import (
    "encoding/base64"
    "fmt"
    "strings"
)

func main() {
    standard := base64.StdEncoding
    raw := base64.RawStdEncoding
    strict := standard.Strict()
    strictRaw := raw.Strict()
    cases := []struct {
        encoding *base64.Encoding
        text, want string
        wantError bool
    }{
        {standard, "Zg==", "f", false},
        {standard, "Zh==", "f", false},
        {strict, "Zg==", "f", false},
        {strict, "Zh==", "", true},
        {strict, "Z\ng==", "f", false},
        {strict, "Z\r\ng==", "f", false},
        {raw, "Zg", "f", false},
        {standard, "Zg", "", true},
        {strictRaw, "Zh", "", true},
    }
    for _, item := range cases {
        decoded, err := item.encoding.DecodeString(item.text)
        failed := err != nil
        if failed != item.wantError { panic("wrong error status") }
        if !failed && string(decoded) != item.want { panic("wrong decoded bytes") }
    }
    containsLineEnd := strings.ContainsAny("Z\ng==", "\r\n")
    if !containsLineEnd { panic("outer grammar control") }
    fmt.Println("zero pad bits, ignored CRLF, unpadded input and outer grammar checked")
}

The two ordinary successes establish that equal output bytes do not prove equally valid input encodings. Strict accepts Zg== and rejects Zh==, isolating the trailing-bit condition. The line-broken samples retain valid bits and still succeed. Testing only those line breaks could misleadingly suggest that Strict does nothing.

A separate check detects the newline for an outer single-line rule. It does not clean the input and then claim that the original contained none. If the protocol permits folded text, that acceptance may be correct; if it forbids folding, reject at the relevant boundary. The example implements no network endpoint or authentication, signature or authorization policy.

Malformed input can return partially decoded data together with an error. For expected failures, the fixture checks the failure status and does not use those bytes as a valid message. A whole message needs to satisfy the full contract; a produced prefix is not permission to start business processing. No real sensitive payload is collected by this teaching program.

Validate original text and decoded bytes separately

An internal binary-content tool may intentionally accept multiple textual forms for the same bytes. Document that tolerance so another maintainer does not mistake intended behavior for an unexplained exception. An interface requiring a fixed textual form must validate that form rather than substituting byte equality for its contract. The protocol determines the choice.

An application may also choose one encoder for a uniform output form, but output selection and input acceptance remain separate decisions. This article defines no cross-system canonicalization algorithm across all alphabets, padding options and whitespace. Ignoring CRLF does not imply ignoring spaces, tabs or arbitrary other characters.

A wrapper can introduce another failure if it returns produced bytes while dropping the decoder's error. Such a layer needs its own rejection samples showing that partial data never becomes an accepted message. That is a proposed application test, beyond this unexecuted table; it cannot be reported as an already completed service check.

The site's HMAC representation article explains why byte and text representations cannot be mixed casually. This problem concerns the decoder's specific acceptance rules. Equal bytes, valid trailing bits and conformance to an outer text format need their own evidence.

Should standard encoding accept Zg without equals signs?

The new condition is omitted padding. RawStdEncoding uses the standard alphabet without padding characters. Sharing the alphabet does not give it the same terminal-equals requirement as standard padded encoding. The table therefore expects raw Zg to succeed and standard Zg to fail. Sender and receiver should explicitly agree on the chosen form.

Omitting equals signs does not remove the trailing-bit rule. Strict raw decoding still rejects Zh because the unused bits are nonzero. Padding characters and unused bits are different conditions. When running this program in a Go environment, retain its version, source hash, output and exit status, and ensure that no preprocessing silently changes the independent inputs.
