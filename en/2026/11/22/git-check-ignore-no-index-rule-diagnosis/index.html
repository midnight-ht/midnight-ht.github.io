How can check-ignore explain a rule match for an already-tracked file?

Diagnose ignore patterns separately from index state, including verbose negated-pattern output.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-22 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • Rule diagnostics do not change index identity.
  • Retain source, line, and pattern before judging.
  • A verbose negated match does not mean exclusion.

Use git check-ignore --no-index -v to inspect a path's matching ignore rule without consulting the index. It reports the source, line, and pattern; it does not remove a tracked path. An ordinary call omits tracked files, so silence alone cannot establish that a wildcard is wrong.

Suppose configuration is already in the index when an ignore pattern is added. A maintainer runs check-ignore and sees nothing. Separate two questions: is the path tracked, and what rule would match when checking patterns independently? Mixing them encourages editing a correct pattern or mistaking a diagnostic flag for a cleanup action.

Observe two facts in a disposable index

This script only modifies a fresh temporary repository. It creates no commit and contacts no remote. The harmless fixture first creates a rule and then force-adds the matching file. Existing tracking and a matching pattern can therefore coexist without experimenting on project configuration.

set -eu
work=$(mktemp -d)
git init -q "$work"
cd "$work"
printf '*.log\n' > .gitignore
printf 'tracked\n' > settings.log
git add -f settings.log
before=$(git ls-files --stage -- settings.log)
git --version
status=0
git check-ignore -v settings.log > default.txt || status=$?
test "$status" -eq 1
test ! -s default.txt
git check-ignore --no-index -v settings.log > diagnostic.txt
printf '.gitignore:1:*.log\tsettings.log\n' > expected.txt
cmp expected.txt diagnostic.txt
test "$(git ls-files --stage -- settings.log)" = "$before"
test "$(cat settings.log)" = tracked
cat diagnostic.txt
git ls-files -- settings.log
printf 'DEFAULT_SILENT_AND_INDEX_UNCHANGED\nfixture=%s\n' "$work"

On local Git 2.50.1, the ordinary verbose call produced no output and returned one. Adding no-index printed .gitignore:1:*.log with settings.log and returned zero. An independent index listing still contained settings.log, its stage record matched the earlier record, and the file still contained tracked. The final marker confirms these assertions passed rather than merely recording one successful command.

No commit is needed for this distinction: presence in the index is enough. Whether a later commit includes the file is a separate delivery step, not executed here. The minimal state makes the changed diagnostic attributable to the index check rather than history or remote references.

The official check-ignore manual says tracked files are omitted by default and no-index avoids consulting the index during the check. It supports diagnosing how a path was added or developing patterns for a force-added path. It neither repairs tracking nor establishes security isolation.

Retain the source and line

Verbose records contain source, line, pattern, and queried path. One root-level rule lets the fixture compare the entire output with an independent expected line. Real repositories may have directory rules, local exclusions, and user configuration. Follow the actual reported source and inspect its context rather than searching only one root file.

Line numbers identify a particular file layout. Later edits can move them. Retain the effective rules or content identity, working directory, full arguments, and result. A screenshot containing only a path may not reconstruct the original rule set.

Associate relative paths with the invocation directory too. A name in a subdirectory need not identify the root's same-named file. Establish the queried object before interpreting the result, and do not splice another checkout's diagnostic into this index record. The printed temporary directory correlates this exercise's inputs and receipts.

Decide which state should change next

If the task is pattern diagnosis, leave the index intact. A decision to stop tracking needs a separate review of index contents, subsequent commits, and collaborators' updates. It also cannot revoke historical content. The linked earlier article covers those responsibilities; this query should not become an opaque deletion sequence.

No output does not establish that a file is absent. Check-ignore is a rule diagnostic, not a filesystem inventory. Read working-file, index, and rule facts through their respective tools. An empty result in one scope cannot certify another.

The deliberate counterexample is a matching rule alongside an unchanged index entry. It refutes the assumption that matching automatically stops tracking; it does not show Git malfunctioning. Unchanged state is consistent with this read-only query. Any later index mutation needs its own input and receipt.

Make the diagnosis reproducible

State the path and expected rule, then preserve tool version, effective inputs, ordinary invocation, and no-index invocation. If results differ, first verify equal inputs. Without the complete rule source, report an unresolved diagnosis rather than choosing a similar-looking pattern to manufacture certainty.

The fixture uses simple filenames and a fixed textual record. It does not cover names containing newlines, tabs, or arbitrary bytes. A collector accepting those inputs needs a separately tested machine-parsing contract; this comparison is not a universal parser.

Nor does it inspect build contexts or publication artifacts. Default exclusion from Git addition cannot prove that another copy process omits a file. Verify each delivery channel independently. For this task, the evidence establishes the rule source and unchanged index identity, and stops there.

Does a printed negated pattern mean exclusion?

No. A separate disposable control added !keep.log on the second rule line and created untracked keep.log. Verbose output printed that negated pattern; the same local Git version also returned zero. The manual explicitly says a leading exclamation mark here means the path is not excluded. This new condition requires reading pattern meaning rather than equating output, or this observed zero status, with exclusion. The main fixture used only the ordinary wildcard; introducing negation does not change settings.log's tracking result.
