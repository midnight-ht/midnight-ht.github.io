Why can casefold match Straße when lower cannot?

Separate caseless matching from original-text highlighting using expansion, offset and canonical-composition controls.

Updated 2026-11-22 · Estimated read 14 min
Translations

Article

Key takeaways

  • Case folding removes distinctions that lower can leave intact.
  • Expansion can invalidate offsets into the original text.
  • Canonical equivalence and case folding need separate decisions.

Lowercasing Straße and the query STRASSE still leaves different strings; casefold can make them equal. Lowercasing leaves the already lowercase ß alone, while case folding expands it to ss. For textual filtering, retain the original display text: a successful folded comparison does not make folded offsets valid indexes into the original.

Decide which difference the filter should ignore

Imagine a local list of road descriptions. A user enters an uppercase search term, and the product should ignore case while displaying the entered text unchanged. Converting both sides to lowercase is an easy first implementation. Examples using only English letters pass, but that does not establish the intended contract for every input character.

The official case-folding documentation, captured from Python 3.14.10, describes caseless matching and uses the German lowercase letter to explain the difference from lower. The method was added in Python 3.3. Its default folding behavior is not a promise to implement every language's preferred natural-language search policy.

Start with a visible acceptance question: should these particular words compare equal? If so, choose a conversion that meets the sample and keep the original for presentation. Pronunciation, accents and locale preferences need additional examples and a separate policy. A successful caseless comparison is not permission to treat all visually similar words as equivalent. Account identity, unique keys and mapping-container policies are outside this article.

Matching succeeds, but highlighting moves

The complete fixture has separate expectations for comparison, length and position. Its archived local receipt records execution with Python 3.11.15, including the exact code, output and exit status. That is neither execution of the documentation's Python 3.14 version nor acceptance evidence for a production search service.

from unicodedata import normalize

lowercase, fold, locate = str.lower, str.casefold, str.index
source = "Straße"
query = "STRASSE"
assert lowercase(source) != lowercase(query)
folded = fold(source)
assert folded == fold(query) == "strasse"
assert (len(source), len(folded)) == (6, 7)
assert (locate(source, "e"), locate(folded, "e")) == (5, 6)
assert source[6:7] == ""
assert source == "Straße"
composed, decomposed = "é", "e\u0301"
assert fold(composed) != fold(decomposed)
left = normalize("NFC", composed)
right = normalize("NFC", decomposed)
assert fold(left) == fold(right)
print("caseless match, expansion, offset failure and normalization control checked")

The original has six characters and the folded representation has seven. The final e is at index five in the original and six in the folded text: one earlier character became two. Using the folded range six to seven on the original produces an empty string instead of highlighting that letter. The match result and the displayed range therefore need independent assertions.

A query does not have to include the expanding character to expose the problem. Any match after it can acquire a different offset. Saying that a keyword contains only ordinary Latin letters does not establish that transforming the searched source preserved positions.

Retaining the original is also distinct from protecting it against mutation. The methods return new strings; the fixture explicitly checks that the source remains unchanged. The application can still overwrite a variable with its folded representation and accidentally display that representation. Separate names for display text and comparison text make those responsibilities visible during review.

Choose whether precise highlighting is required

A whole-row filter can test the comparison representation and still display the complete original. It then needs no reverse position mapping. The tradeoff is the absence of a precise highlight, which may be an acceptable choice for short labels. It is preferable to an improvised offset conversion whose assumptions nobody has checked.

If highlighting is required, use an implementation that maintains correspondence between original and comparison representations. Test matches before an expansion, inside it and after it. Subtracting one fixed offset is insufficient: different positions can have different numbers of preceding expansions, and the match itself may cover an expanded character. This article implements no general mapping algorithm and makes no claim that concatenating per-character transformations handles every normalization or grapheme boundary.

For interface acceptance, retain the original input, comparison representation, match range and final displayed fragment. Those observations distinguish the wrong comparison policy from missing coordinate conversion or a rendering interface with different index units. Saving only the transformed word removes an important diagnostic reference. The fixture uses fixed teaching strings and collects no real user text.

Whole-word equality and substring search also need separate tests. The executed fixture establishes the specific equality and offset controls shown here; it is not a tested search library. An application doing containment filtering should independently test acceptance in the transformed representation and how it returns to the original. Do not label the whole search feature accepted merely because an equality example passed.

What if casefold still leaves canonically equivalent text different?

The additional condition is a precomposed accented character on one side and a base letter followed by a combining accent on the other. Case folding does not automatically perform every canonical-equivalence transformation. The fixture first checks that folding alone leaves these two sequences unequal, then applies canonical composition before folding for this particular sample.

The unicodedata.normalize documentation defines the composition and decomposition forms. This example chooses canonical composition rather than an arbitrary compatibility transformation. The business policy must decide whether further distinctions may be removed. One accented-character control does not establish an ordering of operations suitable for every language algorithm or Unicode version. A deployed service should retain its actual runtime's character-database version in its own evidence.

The site's Unicode normalization and comparison contract article develops canonical-equivalence choices. The additional concern here is responsibility after a folding expansion: make the intended comparison succeed, preserve the original display, and validate any returned location. Natural-language ordering needs a separate sorting contract; it cannot be inferred from this equality check.
