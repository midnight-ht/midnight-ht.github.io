How can a selected CTest test bring its setup and cleanup along?

Verify fixture setup and cleanup added for selected consumers, including failed preparation and independent logs.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-22 · Estimated read 19 min
Translations
zh-CN en

Article

Key takeaways

  • A fixture can expand the executed test set.
  • Failed setup blocks consumers but cleanup still runs.
  • Shared preparation and resource exclusion differ.

Associate a consumer with FIXTURES_REQUIRED and CTest automatically adds its fixture setup and cleanup tests. Selecting one name with -R does not necessarily mean only that test executes. Failed setup prevents its consumers from running while cleanup remains scheduled. Preserve those outcomes separately.

A test may need temporary state before use and removal afterward. Rather than hiding all preparation inside the consumer, declare the lifecycle. Setup, consumer, and cleanup must use the intended case-sensitive fixture identity.

Three tests around one selected consumer

Save worker.py in a dedicated directory. It records entry events, creates a known marker during preparation, checks its exact contents during use, and removes it during cleanup. Failing preparation leaves the marker behind deliberately. Cleanup tolerates absence because setup need not finish completely.

from pathlib import Path
import sys

root = Path(sys.argv[1])
action = sys.argv[2]
marker = root / "state"
log = root / "events.txt"
with log.open("a") as stream:
    stream.write(action + "\n")
if action == "PREPARE":
    marker.write_text("ready\n")
    if sys.argv[3] == "fail":
        raise SystemExit(1)
elif action.startswith("USE"):
    assert marker.read_text() == "ready\n"
elif action == "CLEANUP":
    marker.unlink(missing_ok=True)
else:
    raise AssertionError(action)

Save verify.py as an independent outer oracle. It reads events and residue, not CTest properties or internal outcomes.

from pathlib import Path
import sys

root = Path(sys.argv[1])
mode = sys.argv[2]
lines = (root / "events.txt").read_text().splitlines()
assert mode in ("pass", "fail")
expected = ["PREPARE", "USE", "CLEANUP"] if mode == "pass" else ["PREPARE", "CLEANUP"]
assert lines == expected
assert not (root / "state").exists()
print("EVENTS_AND_CLEANUP_OK", mode, lines)

Save CMakeLists.txt beside it. State is a fixture name, not a required test-name convention. Setup and cleanup do not require their own fixture, which would create a self-dependency. FAIL_SETUP changes only preparation's process outcome.

cmake_minimum_required(VERSION 3.20)
project(FixtureSelection NONE)
enable_testing()
find_package(Python3 REQUIRED COMPONENTS Interpreter)
option(FAIL_SETUP "Make preparation fail after creating state" OFF)
if(FAIL_SETUP)
  set(mode fail)
else()
  set(mode pass)
endif()
set(worker_command "${Python3_EXECUTABLE}" "${CMAKE_CURRENT_SOURCE_DIR}/worker.py" "${CMAKE_BINARY_DIR}")
add_test(NAME prepare COMMAND ${worker_command} PREPARE "${mode}")
add_test(NAME use COMMAND ${worker_command} USE)
add_test(NAME cleanup COMMAND ${worker_command} CLEANUP)
set_tests_properties(prepare PROPERTIES FIXTURES_SETUP State)
set_tests_properties(use PROPERTIES FIXTURES_REQUIRED State)
set_tests_properties(cleanup PROPERTIES FIXTURES_CLEANUP State)

The script uses two fresh build directories so a successful run cannot seed the failure control. Replace the local absolute interpreter path with a real persistent path on your machine. No compilation is needed.

set -eu
work=$(mktemp -d)
python_path=/opt/homebrew/bin/python3.11
test -x "$python_path"
ctest --version
for mode in pass fail; do
  flag=OFF
  if test "$mode" = fail; then flag=ON; fi
  cmake -S . -B "$work/$mode" -DPython3_EXECUTABLE="$python_path" -DFAIL_SETUP="$flag"
  status=0
  ctest --test-dir "$work/$mode" -V -R '^use$' || status=$?
  printf 'case=%s ctest_exit=%s\n' "$mode" "$status"
  if test "$mode" = pass; then test "$status" -eq 0; else test "$status" -ne 0; fi
  "$python_path" verify.py "$work/$mode" "$mode"
done
printf 'fixture=%s\n' "$work"

With local CMake/CTest 4.2.3 and Python 3.11.15, the successful selection added prepare and cleanup even though the regex named only use. All three passed. An independent log contained exactly PREPARE, USE, CLEANUP, and state was absent afterward. This checks lifecycle and residue beyond the summary pass rate.

In the failure control, preparation created the marker and exited one. CTest reported prepare Failed, use Not Run, cleanup Passed, and exited eight. The log contained only PREPARE and CLEANUP and the marker was gone. The outer script accepted the expected failure protocol; it did not establish passed consumer behavior. Original outputs and statuses remain preserved.

The FIXTURES_REQUIRED reference documents selection expansion and setup-failure handling. Basic fixtures date from version 3.7. The current page also describes newer repeat behavior; this example does not use repeat, and the page version is not a local runtime receipt.

A blocked consumer did not fail its assertion

A missing USE event is expected after failed preparation, but a missing line alone cannot identify the cause. Correlate CTest's failed-dependency record, named outcome, and actual log location. A wrongly placed log or undiscovered node cannot demonstrate fixture blocking.

First establish that the successful control discovers and runs the consumer, then compare the same selection with failed setup. Only preparation mode changes, and each directory is recorded independently. This makes absence attributable rather than concealing an omitted selection or stale report.

Do not count Not Run as behavior coverage. After repairing preparation, actually rerun the consumer and its assertions. Successful cleanup here establishes marker removal, not device reset, database recovery, or business readiness. Real resources need their own readback.

Fixtures do not imply exclusion

Fixtures define setup and cleanup; resource locks define exclusion. The reference allows combining them but gives their names no automatic relationship. State does not serialize every device user. Declare and verify a shared resource independently when exclusion is necessary.

A resource lock likewise does not automatically add preparation. Identify resource ownership, setup, consumer nodes, and release actions, then assign each requirement to its declaration. Reducing the entire suite to one worker and attributing the improvement to fixtures would not isolate the cause.

Cleanup must accept partial setup

The marker is intentionally written before failure. Real setup can create some resources and fail before others exist. Cleanup needs current-run ownership and tolerance for absent pieces. A dedicated directory and identity are easier to audit than deleting a shared path indiscriminately. Without ownership evidence, preserve the scene instead of deleting someone else's resources.

Scheduling cleanup in a normally running CTest process is not universal recovery. Forced runner termination, machine restart, and lost remote connectivity need separate treatment. None was tested here. Removing a local marker cannot certify remote reclamation; residual resources need an additional investigation path.

Keep the original layers: preparation exited one, consumer did not run, cleanup passed, and CTest exited eight. Reducing all four to “test failed” loses the next action; rewriting them as success after cleanup invents coverage. The receipt should tell the next operator to repair preparation and then run the consumer.

Do two consumers prepare the same fixture twice?

This introduces a second consumer. Append these lines, then run the fresh-directory check below. Setup executes once for the selected consumer set, and cleanup follows completion of that set. This is neither per-consumer preparation nor persistent reuse across CTest invocations.


add_test(NAME use2 COMMAND ${worker_command} USE2)
set_tests_properties(use2 PROPERTIES FIXTURES_REQUIRED State)

The outer shell check independently verifies first/last events, total count, one event per consumer, and no state residue.

set -eu
work=$(mktemp -d)
cmake -S . -B "$work/build" -DPython3_EXECUTABLE=/opt/homebrew/bin/python3.11
ctest --test-dir "$work/build" -j 2 -V -R '^use'
log="$work/build/events.txt"
test "$(head -n 1 "$log")" = PREPARE
test "$(tail -n 1 "$log")" = CLEANUP
test "$(wc -l < "$log" | tr -d ' ')" -eq 4
test "$(grep -cx USE "$log")" -eq 1
test "$(grep -cx USE2 "$log")" -eq 1
test ! -e "$work/build/state"
cat "$log"
printf 'ONE_SETUP_TWO_CONSUMERS_ONE_CLEANUP\nfixture=%s\n' "$work"

The local four-test run passed with PREPARE, USE2, USE, CLEANUP. Consumer order is not promised, so the external oracle checks each middle event once while checking the first/last events and counts strictly. The main fixture had one consumer, making this an additional condition.
