Why does O_CREATE leave the old suffix after a shorter write?

Distinguish creation, overwriting, truncation and append with independent full-content oracles in an unexecuted Go fixture.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-22 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • O_CREATE creates a file when it is absent.
  • os.Create truncates an existing file; O_CREATE alone does not.
  • Validate complete final content separately from the write count.

Opening an existing abcdef file with O_CREATE and writing XY from the beginning can leave XYcdef. The flag creates a missing file; it does not clear an existing one. To rewrite an entire ordinary file, choose truncation explicitly. The truncation promised by os.Create cannot be inferred from the similarly named flag alone.

Why do four old bytes survive a successful write?

A teaching tool previously produced six bytes and now has only two to write. It observes a successful two-byte write and assumes it replaced the file. But writing from the initial offset overwrites two positions. Without truncation or a later explicit length adjustment, the suffix survives. Writing all new bytes and leaving only those bytes in the file are separate acceptance conditions.

The os flag documentation, checked at go1.27.4 published November 10, 2026, separates creation from truncation. One creates when absent; the other truncates a writable regular file when opened. The documentation also warns that not every flag is implemented on every system. This example concerns ordinary temporary files, not devices, network filesystems or platform-specific guarantees.

The function and flag are especially easy to confuse. Create explicitly creates or truncates. OpenFile is the general interface governed by its supplied flags. Sharing the word create does not give them identical defaults. Review the actual function, access mode and complete flag combination.

Compare independent files, not a mutated shared setup

The complete program creates a dedicated temporary directory. Every case has a different filename initialized with the same six-byte seed. The expected contents cover preserved suffixes, explicit truncation, the convenience function and the append follow-up. A separate missing path provides a negative control without the creation flag. No Go toolchain is installed in the current environment, so this program is unexecuted; its literal expectations come from the documented contract.

package main

import (
    "errors"
    "fmt"
    "os"
    "path/filepath"
)

func must(err error) { if err != nil { panic(err) } }
func main() {
    directory, err := os.MkdirTemp("", "create-contract-")
    must(err)
    defer os.RemoveAll(directory)
    ordinary := os.O_WRONLY | os.O_CREATE
    samples := []struct { name string; flags int; want string; useCreate bool }{
        {"keep", ordinary, "XYcdef", false},
        {"clear", ordinary | os.O_TRUNC, "XY", false},
        {"helper", 0, "XY", true},
        {"append", ordinary | os.O_APPEND, "abcdefXY", false},
    }
    for _, sample := range samples {
        path := filepath.Join(directory, sample.name)
        must(os.WriteFile(path, []byte("abcdef"), 0600))
        var file *os.File
        if sample.useCreate { file, err = os.Create(path) } else {
            file, err = os.OpenFile(path, sample.flags, 0600)
        }
        must(err)
        n, writeErr := file.WriteString("XY")
        closeErr := file.Close()
        must(writeErr); must(closeErr)
        if n != 2 { panic("short write") }
        content, readErr := os.ReadFile(path)
        must(readErr)
        if string(content) != sample.want { panic(sample.name + ": wrong content") }
    }
    missing := filepath.Join(directory, "missing")
    file, openErr := os.OpenFile(missing, os.O_WRONLY, 0600)
    if file != nil { file.Close(); panic("unexpected file") }
    if !errors.Is(openErr, os.ErrNotExist) { panic("missing-file control failed") }
    fmt.Println("creation, truncation, append and missing-file expectations checked")
}

The first two cases differ in explicit truncation. The third is an independent control using the convenience function. Every write checks its count, write error, close error and complete final content. Checking just a prefix would miss the precise suffix defect under investigation. The program opens no repository or real service configuration files.

The missing-path control expects a not-exist error from write-only opening without creation. Preparing to write does not itself create a file. The program uses standard error matching rather than a platform-specific error message. Short ASCII input keeps byte length and displayed character count aligned so encoding differences do not hide the length problem.

Independent preparation matters. Running a truncating case first on one shared path could shorten the seed before the supposedly preserving case begins and allow a broken implementation to pass accidentally. Initial state is part of the oracle. Cleanup must likewise remain restricted to the directory created by this program, rather than an externally supplied shared directory.

Specify final content and the failure tradeoff

For a temporary product that may be cleared and rewritten directly, explicit truncation or Create can express the intended policy. Truncation happens when opening: a later failed write does not restore the old bytes. A successful two-byte final-content assertion therefore supplies no old-version preservation guarantee.

A requirement to retain the previous version after failure needs a separate replacement protocol and platform checks. Temporary-file replacement can involve paths, permissions, synchronization and concurrent observation. This example implements no deployment configuration replacement and tests neither crashes nor simultaneous writers.

Before applying a fix, list the existing-file and missing-file inputs separately. Use new content shorter than the seed to expose omitted truncation, and ensure a missing-path error is not swallowed as success. A logged byte count can aid diagnosis; the complete final content is the acceptance object for this problem.

Creation permissions also have their own conditions. The supplied mode concerns a newly created file and is subject to the process umask; it is not a promise to reset an existing file's permissions. The fixture asserts no permission bits and has no inaccessible-directory test. Those need their own environment and expectations.

The site's temporary-file handoff and cleanup article asks whether a file remains alive for its reader. This problem assumes the file exists and asks which bytes survive writing. Correct lifetime can coexist with incorrect length.

Does O_APPEND replace the old content instead?

The additional condition is append mode. It writes at the end rather than clearing or overwriting the beginning. Its independent file starts with six bytes and expects the eight-byte result abcdefXY. That differs from the first case's XYcdef: both preserve old content, but in different positions and for different purposes.

Append can fit an accumulating-record contract, not an export that should retain only the newest text. This single teaching write establishes no cross-process record atomicity or durability. When a Go environment is available, retain its version, program hash, output and exit status, then verify all four contents and the missing-path error. A lack of reported errors alone would not validate all those policies.
