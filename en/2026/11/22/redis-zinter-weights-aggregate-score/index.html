Why is a ZINTER score eight when the inputs were one and two?

Use independent integer oracles and a reversed-order control to explain weighting before aggregation; Redis commands unexecuted.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-22 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • Intersection membership and result scores are separate contracts.
  • SUM, MIN and MAX aggregate weighted contributions.
  • Zero weight does not remove a source membership requirement.

A has scores one and two in the input sorted sets, yet ZINTER returns eight. Membership is not wrong: weights first turn those contributions into two and six, and the default aggregation sums them. Diagnose who survives separately from what score the survivor receives.

A sorted-set intersection also defines a score

Imagine a teaching ranker keeping candidates present in two indicators. A caller thinks intersection merely filters members and expects one original score to survive unchanged. The command also has a score contract. Identical correct members can receive different valid scores under different weights and aggregation choices.

The official ZINTER documentation says the result is returned to the client instead of being stored like the storage variant. It points to the related command for option semantics. The ZUNIONSTORE options explicitly multiply each source score by its weight before SUM, MIN or MAX aggregation. These are current official snapshots obtained November 22. ZINTER is available since Redis 6.2; other newer options appearing on a current page are not promised for every older server.

The examples use ordinary sorted sets with finite integer scores and finite weights, on one standalone server. Clustered multi-key operations have additional conditions, and no cross-slot behavior is tested. Fix the input and deployment scope before attributing a result to score arithmetic.

Two sources, three independent numeric expectations

The left input has a at one and b at three; the right has a at two and c at four. Only a intersects. Weights two and three produce contributions two and six, so the default sum is eight, the minimum is two and the maximum is six. High scores cannot admit b or c: each lacks membership in one source.

This complete teaching sequence includes the later counterexample and follow-up. Use a dedicated test database where these keys initially do not exist; example key names authorize no writes to shared data. Neither a Redis service nor CLI is installed here, so the commands are unexecuted. Every response described below is an independently calculated expectation, not an observation.

ZADD lesson:left 1 a 3 b
ZADD lesson:right 2 a 4 c
ZINTER 2 lesson:left lesson:right WEIGHTS 2 3 WITHSCORES
ZINTER 2 lesson:left lesson:right WEIGHTS 2 3 AGGREGATE MIN WITHSCORES
ZINTER 2 lesson:left lesson:right WEIGHTS 2 3 AGGREGATE MAX WITHSCORES
ZRANGE lesson:left 0 -1 WITHSCORES
ZRANGE lesson:right 0 -1 WITHSCORES
ZADD lesson:control-left 3 a
ZADD lesson:control-right 2 a
ZINTER 2 lesson:control-left lesson:control-right WEIGHTS 1 10 AGGREGATE MIN WITHSCORES
ZINTER 2 lesson:left lesson:right WEIGHTS 0 0 WITHSCORES

Check the first three intersection results as member-score pairs: a/eight, a/two and a/six. Clients and protocol versions may represent scored responses with different nesting or string formatting. The acceptance object is membership and mathematical value, not one screenshot's layout.

The range queries check that both sources retain their original members and scores. A returning intersection does not write the weighted result back into them. If an application later sees changed source scores, inspect other writes rather than assuming that eight was stored there. ZADD prepares the fixture explicitly; preparation writes must not be attributed to the intersection operation.

A control that exposes weighting after the wrong selection

Use separate control sets with a at three on the left and two on the right, then weights one and ten. The right raw score is smaller, but the weighted contributions are three and twenty. The correct minimum is three. Selecting the smaller raw source first and then multiplying would incorrectly produce twenty.

The original inputs happen to preserve the ordering between raw scores and weighted contributions. They cannot by themselves distinguish those algorithms. A useful counterexample changes the condition that separates the competing interpretations. Independent keys prevent the control from silently mutating the first example before the later follow-up.

Choose aggregation from the business contract. SUM accumulates contributions; MIN and MAX express different combination policies. The command documentation does not establish which policy is fair or effective, nor that weights are statistically calibrated. Specify representative desired ranking outcomes before checking the implementation against them.

Weights also correspond to source positions. Swapping sources without their weights changes contributions even if the command succeeds. This fixture includes no extra swapped-order run or performance measurement. A real project should retain the mapping from business indicators to input keys instead of logging an unexplained sequence of numbers.

The site's intersection-cardinality threshold article asks whether a count reaches a threshold. Here a score contract remains after membership is known: one survivor does not tell you whether its value should be eight, two or six. Membership, score and response parsing deserve separate acceptance checks.

Does a zero weight remove that source's membership requirement?

The additional condition is a zero weight. It changes a numeric contribution, not which sources must contain a member. The last command gives both sources zero weights. It still expects only a, now with score zero; b and c remain absent. A client must not confuse a zero score with no member, so check existence and value separately.

Actually ignoring an indicator requires reconsidering which sources participate in the intersection rather than merely setting its weight to zero. That changes membership policy and needs separate review. When Redis execution is available, retain the server version, initial key state, complete commands, raw replies and exit status, then compare those observations against each expectation. An unexecuted teaching sequence establishes neither performance nor production acceptance.
