Why does ^ still use the original string origin in a fullmatch window?

Check original spans, sliced spans and real-newline controls to distinguish bounded matching from a new string origin.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-22 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • pos does not create a new string origin.
  • endpos supplies an effective end for the operation.
  • Slicing changes the coordinate system of returned spans.

A digit window passes fullmatch until you add ^. The starting position limits where matching begins; it does not turn that position into the beginning of the original string. If diagnostics need original coordinates, validate the window without an unnecessary start anchor, then decide separately whether that anchor expresses a real requirement.

Why do the same three digits produce different results?

Take xx123yy and select indexes two through five, excluding the right endpoint. A field extractor has already identified those bounds. The caller wants every character in that region to be a digit and wants any returned position to refer to the original text. A digit-only fullmatch satisfies that requirement. Adding ^ introduces a second requirement about the matching position itself.

The official re documentation, captured from the Python 3.14.10 documentation, says fullmatch uses the same pos and endpos meanings as search. The adjacent search documentation explicitly distinguishes pos from slicing: ^ refers to the real beginning, or an appropriate position following a newline, rather than necessarily to the supplied starting index.

Keep two questions separate: where may the operation match, and which assertions must hold there? The method requires the bounded region to match completely. It does not remove assertions from the pattern. The digits satisfy the character rule while their position fails the start assertion. A None result therefore does not imply that the method ignored the supplied bounds.

Four expectations before examining any output

This complete fixture writes literal expected spans and None values. One observed call is never used as the oracle for another. The archived local receipt records Python 3.11.15, rather than pretending that the machine ran the documentation's Python 3.14 version. Its assertions cover these calls only.

import re

text = "xx123yy"
line = "xx\n123yy"
line_mode = re.MULTILINE
cases = [
    (r"\d+", text, 2, 5, 0, (2, 5)),
    (r"^\d+$", text, 2, 5, 0, None),
    (r"^\d+$", text[2:5], 0, 3, 0, (0, 3)),
    (r"\d+$", text, 2, 5, 0, (2, 5)),
    (r"^\d+$", line, 3, 6, line_mode, (3, 6)),
    (r"^\d+$", text, 2, 5, line_mode, None),
    (r"\A\d+", line, 3, 6, line_mode, None),
]
for pattern, value, start, stop, flags, expected in cases:
    compiled = re.compile(pattern, flags)
    found = compiled.fullmatch(value, start, stop)
    actual = None if found is None else found.span()
    assert actual == expected, (pattern, value, expected, actual)
print("window origin, virtual end, slice spans and multiline controls checked")

The unanchored window match returns the original span, two to five. The start-anchored window fails. Slicing first creates a different string whose digits begin at index zero, so the anchored pattern succeeds with span zero to three. The end-anchored window succeeds as well: the two endpoints are deliberately asymmetric.

endpos makes the string effectively end at that bound for this operation. The trailing letters still exist in the original object but are outside the matching range. pos does not create a corresponding virtual beginning. Treating both parameters as if they constructed a sliced string would lose that distinction.

These are Python string indexes, not encoded file-byte offsets. Keeping original spans avoids an additional slice-relative coordinate system; it does not make every editor or storage interface use the same units. No byte-to-character conversion is implemented by this fixture.

Choose the coordinate contract as well as the matching API

A bounded call is useful when later diagnostics need positions in the original text. Check both matched content and span: correct digits at an incorrect reported location are still a broken diagnostic. This small example measures no allocation or performance effect, so it supports no general claim that avoiding a slice is faster.

An independent substring is reasonable when the downstream interface already accepts an independent field. Its local coordinates then fit that contract. If a later consumer needs original positions, retain the field's starting index and translate deliberately. A change from bounded matching to sliced matching must update the position assertions along with the content assertions.

Existing patterns may have several callers. Removing an anchor could fix fullmatch on a window while changing what another caller's search accepts. Inspect those entry points before sharing or rewriting the pattern. The recommendation is to decide which layer enforces whole-region matching, rather than to delete anchors throughout a project.

Useful project controls include changing characters outside the window without changing acceptance, and replacing a digit inside it with a letter and requiring rejection. Those are proposed additional checks, not assertions executed in the archived fixture. They would help validate a real field extractor, whose behavior this demonstration does not establish.

The site's HTML pattern whole-value matching article concerns browser constraint validation. A browser validating an entire value supplies no evidence that Python pos creates a new origin. When moving a pattern between interfaces, compare input units, bounds and result coordinates before comparing the pattern text alone.

Does MULTILINE make any window start a line start?

No. The additional condition is an actual newline immediately before the position in the original text. The fixture inserts one after xx and starts the digits at index three. With MULTILINE, ^ can hold there. Applying the same pattern to the original input, with no newline before its window, still fails.

The absolute-start assertion supplies another control: MULTILINE does not let it accept index three merely because a newline precedes that index. Line start and string start are separate promises. If a real field may contain multiple lines, decide which region is being validated instead of using a flag as a general repair for failed window matching. Preserve the original prefix, both bounds and the resulting span so that the next maintainer can verify that decision.
