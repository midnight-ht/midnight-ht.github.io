Why can a long loop still block inside requestIdleCallback?

Use a four-item queue to explain cooperative idle budgets, separating an unexecuted page from an executed timeout-policy fixture.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-22 · Estimated read 16 min
Translations
zh-CN en

Article

Key takeaways

  • An idle estimate does not preempt JavaScript
  • Each individual work unit needs a bound
  • Scheduling does not establish completion

requestIdleCallback supplies an estimated idle budget; it does not interrupt a long loop when that budget expires. Moving a large synchronous operation into the callback can still block input and rendering. Split work into bounded units, check timeRemaining between units, and schedule the remainder separately. A positive reading does not make an arbitrarily long next operation safe.

A budget estimate is not preemption

IdleDeadline.timeRemaining returns the estimated deadline minus the current time, clamped to zero. It is a reading taken when called, not a switch that stops JavaScript at expiration. Starting an expensive synchronous operation after that reading does not make the browser divide the operation for the application.

The IdleDeadline definition specifies this calculation. The examined original is the Working Draft of November 12, 2026, not evidence of tested scheduling across devices. The user agent determines idle periods; a reading cannot establish a fixed batch count or completion delay.

Control both the number of items per callback and the cost of an individual item. A two-item cap does not establish a time bound if each item is a huge synchronous parse. Design the unit first, dividing it further when necessary. The teaching units here merely square small integers; they do not provide performance evidence for a real indexing workload.

Leave room for follow-on work too. The specification’s idle-period discussion notes that layout or Promise-related operations can lead to later work. Returning from the callback does not mean every consequence has finished. A safety margin is an application policy, not proof that a fixed millisecond threshold suits every page. Real workloads need measurements of their own units and responsiveness.

A complete page with four small items

This HTML page has not run in a browser. It squares 1, 2, 3, and 4 in order, processing at most two items per callback while the estimated budget exceeds a teaching threshold. It performs no requests, persistence, or real indexing. Starting temporarily disables the start button so another click cannot reset the queue while the first request chain is active.

<!doctype html>
<meta charset="utf-8">
<title>Cooperative idle chunks</title>
<button id="start" type="button">Start four teaching items</button>
<pre id="out"></pre>
<script>
const get = document.getElementById.bind(document);
const output = get('out');
const button = get('start');
let pending = [];
const completed = [];
function runChunk(deadline) {
  let count = 0;
  while (pending.length && count < 2 && deadline.timeRemaining() > 1) {
    const item = pending.shift();
    completed.push(item * item);
    count += 1;
  }
  output.textContent = JSON.stringify({count, pending: pending.length, completed});
  if (pending.length) requestIdleCallback(runChunk);
  else button.disabled = false;
}
button.onclick = () => {
  if (!('requestIdleCallback' in window)) {
    output.textContent = 'This environment does not provide requestIdleCallback.';
    return;
  }
  button.disabled = true;
  pending = [1, 2, 3, 4];
  completed.length = 0;
  requestIdleCallback(runChunk);
};
</script>

The independent final expectation is 1, 4, 9, 16, without duplicates or omissions. Batch sizes are not fixed: insufficient budget can mean doing nothing before scheduling again. The example does not promise completion in two frames, and successful scheduling does not establish completed work. The button becomes available again only when pending is empty.

This path has no waiting deadline. A busy or hidden page is not guaranteed prompt progress. The specification permits a user agent to have no available idle period, potentially postponing these callbacks for a long time. This illustrates deferrable background work, not a submission that must finish within a stated interval. A time-critical task needs its own execution and feedback design.

When the method is unavailable, the page reports that fact rather than silently substituting a timer and claiming equivalent idle behavior. A product can define a fallback, but it must describe the different scheduling contract. Making a demonstration complete with an ordinary timer would change the very mechanism under examination.

Retain pending work and per-callback progress

The output records count for the current chunk, pending for remaining items, and completed for accumulated results. They distinguish different defects: repeated results can indicate overlapping request chains, an unchanged queue can indicate inadequate budget, and prematurely enabling the button can indicate a faulty completion check. Callback count alone cannot separate these cases.

The article on elapsed-time animation progress addresses refresh rate and displacement. Here, count does not determine animation speed, and an idle callback is not a per-frame notification. Both APIs require lifecycle management, but work should follow rendering opportunities or wait for idle time according to its actual purpose.

A useful regression first checks the bounded work function, then records budgets, chunk inputs, and final results in a target browser. Supplying a fabricated deadline to a pure function checks parameter handling; it does not measure when the browser supplies a budget. Syntax checking likewise cannot prove responsive input. Keep these evidence types separate rather than letting a passing array fixture stand in for scheduling and responsiveness tests.

If a timeout callback has zero budget, should it do nothing?

This introduces the timeout path. The timeout invocation algorithm sets the new deadline’s getter to the captured current time and didTimeout to true. A subsequent remaining-time reading reaches zero. The flag indicates execution after the wait condition, not a newly granted idle period.

An application can choose to advance at most one known bounded item on that path and schedule the remainder later. The following fixture tests that application policy with manually constructed deadline objects. It does not call a browser API. Normal zero budget makes no progress; timeout zero budget advances one item. Each queue starts independently. One item is a policy choice, not a specification mandate or permission to drain the entire queue without a bound.

import assert from 'node:assert/strict';
function takeChunk(queue, deadline) {
  const results = [];
  const cap = deadline.didTimeout ? 1 : 2;
  while (queue.length && results.length < cap
    && (deadline.didTimeout || deadline.timeRemaining() > 1)) {
    const item = queue.shift();
    results.push(item * item);
  }
  return results;
}
const timedOutQueue = [1, 2, 3];
const normalQueue = [1, 2, 3];
const timeoutResult = takeChunk(timedOutQueue, {didTimeout: true, timeRemaining: () => 0});
const normalResult = takeChunk(normalQueue, {didTimeout: false, timeRemaining: () => 0});
assert.deepEqual([timeoutResult, timedOutQueue, normalResult, normalQueue], [
  [1], [2, 3], [], [1, 2, 3]
]);
console.log(JSON.stringify({timeoutResult, timedOutQueue, normalResult, normalQueue}));

This pure-function script ran locally in Node. The independent expectations are timeout result 1 with 2 and 3 remaining, versus an empty normal result with all three original items remaining. It establishes the bounded branch, not browser invocation at an exact configured instant. Timeout processing still queues work and can include user-agent delay. A task with a real completion deadline cannot claim punctuality from a timeout option alone.
