Does RestartPreventExitStatus turn a failed exit into success?

Separate restart prevention from successful-exit classification with two same-exit fixtures; Linux execution remains unrun.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-22 · Estimated read 16 min
Translations
zh-CN en

Article

Key takeaways

  • No restart does not establish a successful exit.
  • Read result classification and retry evidence separately.
  • Helpers do not inherit the main-process prevention contract.

Preventing a restart does not by itself turn failure into success. RestartPreventExitStatus suppresses automatic retries for specified main-process outcomes; SuccessExitStatus declares additional successful outcomes. Read result classification and retry evidence separately instead of treating absence of a new process as normal completion.

Suppose a program rejects unrecoverable input with exit forty-two. A maintainer wants to retain failure visibility without repeatedly launching it. Declaring success may also stop on-failure retries, but changes the result contract for monitoring and operators. Decide which meaning is intended first.

One exit value, two policies

These are teaching inputs for an isolated Linux host. No systemd unit was installed or started here. Only inline Python and shell syntax were checked on macOS; manager state, journal output, and retry behavior remain unobserved. The following results are expectations from the reference, not passed runtime receipts.

Save the first file as prevent.service: The program prints a marker and exits forty-two. On-failure remains the base policy while the additional directive suppresses that outcome's retry. The finite start budget prevents an accidental unlimited loop; it is not evidence of classification.

[Unit]
Description=Prevent restart without reclassifying exit
StartLimitIntervalSec=60s
StartLimitBurst=3

[Service]
Type=exec
ExecStart=/usr/bin/python3 -c "print('EXIT42', flush=True); raise SystemExit(42)"
Restart=on-failure
RestartSec=1s
RestartPreventExitStatus=42

Save the second file as success.service: Apart from description and the final policy, the program and observation conditions match. Forty-two is classified as successful, so on-failure should not retry it. Both programs terminate immediately; absence alone cannot distinguish success from prevented retries.

[Unit]
Description=Classify an additional successful exit
StartLimitIntervalSec=60s
StartLimitBurst=3

[Service]
Type=exec
ExecStart=/usr/bin/python3 -c "print('EXIT42', flush=True); raise SystemExit(42)"
Restart=on-failure
RestartSec=1s
SuccessExitStatus=42

On an isolated Linux host authorized for these dedicated names, run as root from the input directory. It needs the system manager, supported directives, and /usr/bin/python3. Check that paths are absent and names are not loaded. Stop if a prerequisite fails rather than overriding an existing service.

set -eu
test "$(id -u)" -eq 0
test -x /usr/bin/python3
unitdir=/etc/systemd/system
unit_name() { printf 'zy22-%s.service' "$1"; }
for name in prevent success; do
  unit=$(unit_name "$name")
  test ! -e "$unitdir/$unit"
  test "$(systemctl show "$unit" -p LoadState --value)" = not-found
done
systemd --version
for name in prevent success; do
  unit=$(unit_name "$name")
  install -m 0644 "$name.service" "$unitdir/$unit"
done
systemctl daemon-reload
for name in prevent success; do
  unit=$(unit_name "$name")
  started=$(date -u '+%Y-%m-%d %H:%M:%S UTC')
  status=0
  systemctl start "$unit" || status=$?
  printf 'unit=%s start_exit=%s\n' "$name" "$status"
  sleep 3
  systemctl show "$unit" -p Result -p ActiveState -p SubState -p ExecMainStatus -p NRestarts
  journalctl -u "$unit" --since "$started" --no-pager
done

Both main exit values are expected to remain forty-two. Prevent retains an unsuccessful result while suppressing automatic restart; success classifies the result as successful and therefore does not trigger on-failure. Preserve actual version-specific displays. Main status, whole-service Result, and retry evidence matter together; no host output is prefilled here.

The systemd.service reference defines these mechanisms separately. Its current page identifies systemd 262, not the test host's version. Success classification also leaves numeric-to-name mapping intact: the application returns its original value while the manager changes its effect on service results.

Several paths can leave no replacement process

Suppression, successful exit, exhausted start budget, explicit stop, and missing triggers can all leave no new process. Fix the main-process input and retain effective configuration before attributing that shared symptom to one setting.

Inspect drop-ins and effective values. A repository file describes intended input; a host may add successful statuses, prevention values, or another restart policy. Both lists can coexist. Reinterpret the actual configuration instead of imposing the fixture's table on different inputs. No production override was inspected here.

The three-second sleep is an observation window, not proof of no future restart. Effective policy and original exit facts explain behavior; the journal correlates this invocation. If several starts appear unexpectedly, preserve their identities and investigate rather than waiting until one attempt looks right.

Separate requests from process outcomes

Record systemctl start's status too. It describes handling a start request, not necessarily the short-lived program's forty-two. Type=exec distinguishes successful executable startup from what happens immediately afterward. A final terminal status cannot substitute for ExecMainStatus or certify business completion.

A journal time window is not a unique invocation identity. Repeated starts may put several markers in that interval. Associate the current request, process exit, and corresponding entries. Separate unit names prevent one case's failed state from being silently reused for the other.

An unsuppressed on-failure control would need another dedicated unit, a bounded start budget, and explicit stop steps. That third case was not run and no precise count is promised. Do not change a working business service merely to obtain a restart screenshot.

Preserve the intended failure signal

An expected normal program outcome may justify additional success classification. An error requiring intervention, where retry is pointless, may justify retaining failure while suppressing retries. Align the choice with callers, monitoring, and recovery ownership rather than selecting the setting that makes the display green.

Define who responds afterward. Configuration neither repairs input nor notifies the responsible operator automatically. Connect the failure to a real handling path and verify a repaired run through business behavior. No alert system or recovery was exercised here; this is an exit-semantics verification design.

Before cleanup, retain versions, effective units, original results, and journal evidence. Stop these fixture units, remove only files established as created by the exercise, and reload the manager. Do not clear another service's failure records. If retaining the scene, hand off its names explicitly to avoid later overwrite.

Does the same prevention work for exit forty-two from ExecStartPre?

This changes the failing process. RestartPreventExitStatus applies to the main service process, not ExecStartPre and other helpers. For a separate dedicated unit, copy prevent with its same start budget and restart settings, add ExecStartPre=/usr/bin/python3 -c "raise SystemExit(42)", and replace ExecStart with /usr/bin/python3 -c "import time; time.sleep(30)". This moves forty-two into preparation and leaves a waiting placeholder main command. Determine retries from helper failure and the remaining effective policy, not the main-process prevention conclusion. This variant was not run either.
