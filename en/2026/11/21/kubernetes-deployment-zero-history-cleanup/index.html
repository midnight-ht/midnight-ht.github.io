Why can old ReplicaSets remain with revisionHistoryLimit zero?

Check current Deployment completion before interpreting zero history and remaining ReplicaSets; cluster execution is unrun.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-21 · Estimated read 18 min
Translations
zh-CN en

Article

Key takeaways

  • Zero does not mean immediate object deletion.
  • Use UID and current generation to assess the rollout.
  • Distinguish template changes from scaling.

revisionHistoryLimit: 0 does not mean old ReplicaSets disappear immediately. Old-history cleanup starts after a Deployment completes. During an incomplete rollout, especially when replacement Pods cannot become ready, zero alone does not establish that old objects should already be gone. The official cleanup policy specifies this timing.

A team may set zero history, deploy an image, and see the previous ReplicaSet remain. Before assuming the controller ignored configuration, check the current rollout. Old replicas may still serve while the new template has no available replacements. Their presence is compatible with retaining no history after completion.

Observe an incomplete rollout

These are inputs for an isolated cluster, not a Kubernetes execution report. No cluster was contacted and kubectl was not run. Object lists, pull failures, completion, and cleanup below are expected observations still awaiting verification. Use an isolated context with namespace permissions, functioning controllers, and image access, rather than production.

Save deployment.yaml. It requests two replicas, no retained history, and an HTTP readiness probe for the teaching container. Confirm the image is accessible in the target environment first. The tag is a fixture input, not proof of a business image's availability or immutable identity.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: zy21-history
spec:
  replicas: 2
  revisionHistoryLimit: 0
  selector:
    matchLabels:
      app: zy21-history
  template:
    metadata:
      labels:
        app: zy21-history
    spec:
      containers:
        - name: web
          image: nginx:1.28.0
          readinessProbe:
            httpGet:
              path: /
              port: 80

Save the script below and replace the context placeholder. Use a dedicated namespace that does not already exist. Stop if creation fails. The script waits for the initial rollout, changes to an address intended to prevent image retrieval, and saves objects and events. Recovery atomically changes the image and a template annotation, giving that template an explicit identity.

set -eu
context=REPLACE_WITH_ISOLATED_CONTEXT
namespace=zy21-history-lab
k() { kubectl --context "$context" --namespace "$namespace" "$@"; }
k create namespace "$namespace"
k apply -f deployment.yaml
k rollout status deployment/zy21-history --timeout=120s
k get deployment zy21-history -o json > initial-deployment.json
k get replicasets -o json > initial-replicasets.json
k set image deployment/zy21-history web=example.invalid/zy21-history:unavailable
status=0
k rollout status deployment/zy21-history --timeout=30s || status=$?
printf 'bad-rollout-status=%s\n' "$status"
k get deployment zy21-history -o json > blocked-deployment.json
k get replicasets -o json > blocked-replicasets.json
k describe deployment zy21-history
k get pods -o wide
k get events --sort-by=.metadata.creationTimestamp
k patch deployment zy21-history --type=merge -p '{"spec":{"template":{"metadata":{"annotations":{"zy21-recovery":"v2"}},"spec":{"containers":[{"name":"web","image":"nginx:1.28.0"}]}}}}'
k rollout status deployment/zy21-history --timeout=120s
k get deployment zy21-history -o json > recovered-deployment.json
k get replicasets -o json > recovered-replicasets.json

Read Pods and events to establish the actual blocking cause. A nonzero rollout command can also result from connectivity, permissions, or unrelated faults; it cannot prove an image-pull failure alone. If the initial image cannot be obtained either, the completed-baseline precondition is absent. Fix the environment and record again instead of combining two failures into the intended control.

Identify owned objects

Save inspect.py and run python3 inspect.py initial, python3 inspect.py blocked, and python3 inspect.py recovered. It filters ReplicaSets by the Deployment UID and controller ownerReference, then prints generation, status, annotations, and replica information. Unrelated workloads in the namespace must not become part of the history count.

import json
import sys

prefix = sys.argv[1]
with open(prefix + "-deployment.json") as stream:
    deployment = json.load(stream)
with open(prefix + "-replicasets.json") as stream:
    replicasets = json.load(stream)
uid = deployment["metadata"]["uid"]
print("deployment", uid, deployment["metadata"]["generation"],
      deployment.get("status", {}))
for item in replicasets["items"]:
    if any(owner.get("uid") == uid and owner.get("controller") is True
           for owner in item["metadata"].get("ownerReferences", [])):
        print(item["metadata"]["name"],
              item["metadata"].get("annotations", {}),
              item["spec"].get("replicas"), item.get("status", {}))

During the blocked rollout, expect the new template to lack a complete set of available replacements while an old ReplicaSet remains and may still hold replicas. Establish that from snapshots rather than assuming an exact object count. Controller progress, additional attempts, and environment history can affect counts. Ownership, template identity, and completion are the relevant evidence.

After recovery, verify that the controller observed the current generation, all replicas are updated to the target template and available, and no old-template replicas remain running. Rollout status is a useful entry point; Deployment and ReplicaSet snapshots let another reader reconstruct it. A previous generation's completion or one Running Pod cannot establish the current Deployment is complete.

Then observe old-object cleanup. It is asynchronous controller work; this article promises no precise number of seconds or immediate final object count. If old objects remain in the recovered snapshot, reread with timestamps while checking the same UID and current generation. Without cluster receipts the result remains unverified. YAML syntax cannot establish controller cleanup.

Consider the delivery cost of zero history

The documentation says zero removes history and prevents rollback using those historical records. It does not mean no new ReplicaSet is created: a new template still needs one to progress, with cleanup following completion. Zero history cannot replace checking rollout state or repair a blocked template.

Choose this policy only with a defined recovery approach. If recovery requires an old template, retain its inputs, image identity, and configuration source rather than assuming the controller will preserve the old object. No real business recovery was run here. The fixture merely restores an accessible teaching image with a new annotation.

Preserve all three stages' objects, events, and command results before cleanup. Confirm that the namespace contains only this exercise, then delete it using the same explicit context. Original failure events explain why history remained more usefully than a final green rollout alone. A different namespace, context, or recreated same-named Deployment requires a fresh UID association; do not splice them into one timeline.

A screenshot containing only a total is weak handoff evidence. The next operator needs the context, namespace, UID, template, and state at the observation time. Keep configuration input alongside the three snapshots, distinguishing direct command readings from conclusions. Leave missing observations unfilled with an interruption reason; never substitute objects from another exercise to complete a timeline.

Manual intervention is a separate decision. Read current replica duties and controller state before deleting an object because of the retention number. This fixture reads state and changes its dedicated teaching template; it does not authorize production history cleanup. Any later intervention needs current dependency and recovery checks plus before-and-after evidence, so waiting for controller completion remains distinguishable from human object changes.

Does changing only replica count create a revision?

Scaling alone does not create a new revision. The official reference ties revisions to Pod-template changes. This is a new condition: the main example changes image and annotation, whereas scaling changes only desired count. A separate control can hold the template fixed, change replicas, and compare revision annotations and object identity. It was not run here. A generation change is not automatically a new revision.
