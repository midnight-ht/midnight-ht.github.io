Why can validate_only succeed while the resource remains unchanged?

Compare equal success responses with different stored states and retain permission checks, request mode, and later reads.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-21 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • A successful preview does not establish an applied change
  • Validation retains the live request checks
  • Retain the request mode alongside read-back evidence

A request with validate_only succeeds and previews rating four, while a fresh read still shows rating one. That can follow the preview contract. An endpoint adopting AIP-163 can validate a request without applying its change. Retain that choice instead of turning every successful response into a saved-state message.

Keep validation and execution distinct

Google's Change validation guidance allows an option to validate without executing and provide the response that execution would produce. It uses a Boolean validate_only request field. Check the actual endpoint contract rather than inferring this guarantee from a parameter name.

The option does not skip live-request checks. The guidance requires permission checks and other validation that the live request would perform. If the real request would fail, validation must fail too. An unauthorized caller does not receive success merely by asking for a preview.

Whether inputs and current conditions validate differs from whether this call applied a change. A successful preview can support confirmation of intended content. It does not establish that the resource was updated.

The main fixture changes the rating of a known resource from one to four. Its preview names the same resource and intended rating. It creates no new resource and performs no external side effect.

Equal responses and different local state

This complete script uses an in-memory teaching store. CanWrite is a local test condition; validateOnly represents the documented choice. The function authenticates nobody, sends no HTTP, and connects to no database. The one-to-five rating range is the hypothetical endpoint's business rule.

import { deepEqual } from 'node:assert/strict';
function review(store, canWrite, validateOnly, rating) {
  if (!canWrite) return { status: 'PERMISSION_DENIED' };
  if (!Number.isInteger(rating) || rating < 1 || rating > 5) {
    return { status: 'INVALID_ARGUMENT' };
  }
  const result = { name: 'books/B1', rating };
  if (!validateOnly) store.rating = rating;
  return { status: 'OK', result };
}
const cases = [
  [true, true], [true, false], [false, true], [false, false]
];
const actual = cases.map(([canWrite, validateOnly]) => {
  const store = { rating: 1 };
  const response = review(store, canWrite, validateOnly, 4);
  return { response, storedRating: store.rating };
});
deepEqual(actual, [
  { response: { status: 'OK', result: { name: 'books/B1', rating: 4 } }, storedRating: 1 },
  { response: { status: 'OK', result: { name: 'books/B1', rating: 4 } }, storedRating: 4 },
  { response: { status: 'PERMISSION_DENIED' }, storedRating: 1 },
  { response: { status: 'PERMISSION_DENIED' }, storedRating: 1 }
]);
console.log(JSON.stringify(actual));

Exact local Node execution passed. Authorized preview and execution produced the same successful response with rating four. Preview retained stored rating one; execution changed it to four. Both unauthorized paths rejected and retained one. Every case starts with an independent store.

The receipt establishes this local contract's branches and states. Actual endpoint evidence needs the request field, response, and subsequently read resource version. A response screenshot alone cannot explain unchanged state without the request's preview choice.

A negative control is mapping every OK result to saved. The first case returns OK without writing. A UI using that rule can send someone away believing a change was applied. Check prepared-preview and applied-change states separately.

Bind confirmation to the previewed content

A preview can show intended fields before a live request. Preserve which input it represents. If the user changes four to five after previewing four, confirmation should not silently stand for two different sets of content.

Retain the resource and authorization timing too. Another actor can update the resource or permission can change after preview. A preview is not a permanent guarantee of future execution. The live call still checks its current conditions. See If-Match and edit conflicts for version preconditions.

Do not automatically insert a previewed object into a list representing persisted resources. Keep its display scope and origin explicit until the application has actual execution evidence. The cache design is application-specific, but its state meaning should remain understandable.

A failed permission check also needs accurate feedback. Correcting input requires a new preview tied to its resource, contents, and caller conditions. An old result cannot establish the outcome for a changed request.

This differs from a schema's readOnly annotation. See readOnly declarations and server behavior. Validate_only is an endpoint contract that still needs actual service testing; sending the field alone establishes no implementation result.

A controlled service test can read a baseline, preview, reread, execute, and reread again. Rejected permissions and invalid input should also leave the resource unchanged. No HTTP or persistence test was performed here.

Why might a successful create preview omit an automatically generated ID?

This adds creation rather than updating a known resource. AIP-163 notes that some live output is infeasible to provide during validation, including automatically generated resource IDs. Such fields should be omitted in that situation.

Display the available preview information under the endpoint contract and use the actual creation result for the formal identity. Do not invent a temporary ID and treat it as an accepted resource name. No creation or ID allocation was executed here. An absent generated ID alone cannot establish either creation failure or completion without the request mode.
