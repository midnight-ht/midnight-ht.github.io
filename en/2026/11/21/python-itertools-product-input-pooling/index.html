Why has product consumed its input before the first output?

Observe a finite source at construction and first-read boundaries, then distinguish zero axes from one empty axis.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile

Translations

Article

Key takeaways

  • product consumes input pools before generating combinations.
  • Incremental output does not establish bounded source consumption.
  • Zero axes yield an empty combination; one empty axis yields none.

Before the first product result is requested, its input generator can already be exhausted. product consumes its inputs into in-memory pools and then yields combinations incrementally. Lazy output still requires finite input preparation.

Laziness belongs to the output side

A configuration tool combines versions A and B with identifiers one and two. Constructing the iterator may look like a step that reads nothing yet. But product needs to revisit each axis's values, so it prepares pools first.

The documentation explicitly requires finite inputs and describes complete consumption into memory. It does not say every output tuple is built upfront. Pool size grows with the sum of axis sizes, while combination count grows with their product. Incremental output does not remove input storage.

Input generation can also have effects such as logging, loading a page, or converting data. The fixture logs two strings only and establishes no behavior of a real database or network driver.

Observe construction separately from next

A finite generator marks A and B in seen as it yields them. Independent expected values cover all four outputs. The program deliberately runs no infinite source.

from itertools import product

seen = []
def source():
    for item in ["A", "B"]:
        seen.append(item)
        yield item

assert seen == []
pairs = product(source(), [1, 2])
assert seen == ["A", "B"]
assert next(pairs) == ("A", 1)
assert list(pairs) == [("A", 2), ("B", 1), ("B", 2)]
assert list(product()) == [()]
assert list(product([])) == []
print("source pooled before first output; four pairs restored; zero/empty axis controls passed")

seen is empty before construction and contains A and B immediately afterward, before any next call on pairs. The first result is A, one; the rest are A, two, B, one, B, two. The output assertions confirm pooling did not lose values, while the timing assertion explains when source consumption occurs.

Two values per axis yield four combinations. Bound input sizes and permitted output count separately. Reading ten displayed combinations cannot establish that construction read only ten source values.

If source reads must be limited, apply a justified input limit before product. That changes the candidate space. With A, B, C and one, two, taking two outputs covers A alone; limiting the first axis to A, B and producing everything gives four combinations. A resource fix must preserve the intended selection contract.

Choose finite snapshots or a streaming policy

Small finite option lists fit pooling. Specify axis bounds and validate them before combination. A continuously growing event stream instead needs a window, stopping condition, or different algorithm. Passing it directly to a finite-pool interface cannot establish termination.

Materializing lists first moves source consumption into an explicit application stage rather than eliminating it. That can separate loading errors from combination errors, but still costs storage. This article supplies no tested disk-backed alternative or measured memory threshold.

The site's tee lag-buffer article covers storage for consumers moving at different speeds. Here storage precedes the first combination. Test the actual entry point instead of transferring timing assumptions between iterator APIs.

A proposed failure control can raise from the source after A. Preparation may fail before first-result code runs, so the error belongs to source loading. That variation is not executed here.

Configuration changes also need a version policy. A product built from values read during construction does not automatically reload a later source update. New requests can build a new controlled snapshot; repeatable tasks can record the original version. This fixed-string fixture tests no live configuration change.

Are zero axes and one empty axis equivalent?

product() yields one empty tuple: the sole combination of zero choices. product([]) yields nothing because an axis has no candidates. The final assertions preserve that difference. A dynamically assembled option list needs a rule for a missing axis versus an explicitly empty one, or it can produce one unintended task or omit an intended one.
