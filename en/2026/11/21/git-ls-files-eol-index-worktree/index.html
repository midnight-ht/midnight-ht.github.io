Why can Git report LF while the working file contains CRLF?

Read index and disk bytes independently to interpret Git EOL content fields and conversion attributes.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-21 · Estimated read 11 min
Translations
zh-CN en

Article

Key takeaways

  • Index, working tree, and attributes have separate fields.
  • Policy cannot replace inspection of actual bytes.
  • Verify the input used by the intended consumer.

Git can report LF while the working file still contains CRLF. In git ls-files --eol, distinguish i/, w/, and attr/. They describe index content, working-tree content, and conversion attributes. One column cannot establish the bytes seen by every consumer.

A file may be staged before an editor saves its working copy with another line ending. A terminal report says LF, but a packager reading disk gets different bytes. Expose both versions of the same path before deciding what to repair.

Read both byte sequences independently

The script creates a disposable repository with automatic conversion disabled. It stages LF, then changes only the working file to CRLF. Python reads the index through Git and the file through the filesystem. Finally, the script adds an attribute and checks the report again.

set -eu
work=$(mktemp -d)
trap 'rm -r "$work"' EXIT
cd "$work"
git init -q
git config core.autocrlf false
git version
printf 'alpha\nbeta\n' > sample.txt
git add sample.txt
printf 'alpha\r\nbeta\r\n' > sample.txt
git ls-files --eol -- sample.txt
python3 - <<'PY'
from pathlib import Path
import subprocess

index = subprocess.check_output(["git", "show", ":sample.txt"])
working = Path("sample.txt").read_bytes()
assert index == b"alpha\nbeta\n"
assert working == b"alpha\r\nbeta\r\n"
print("index", repr(index), "working", repr(working))
PY
printf 'sample.txt text eol=lf\n' > .gitattributes
git ls-files --eol -- sample.txt

On Apple Git 2.50.1, the initial report showed i/lf and w/crlf with an empty attribute value. The independent byte assertions confirmed LF in the index and CRLF on disk. After adding text eol=lf, those content columns stayed unchanged and the attribute column displayed the policy. The script exited zero. Editing the policy alone did not convert both existing contents in this fixture. Git ls-files EOL fields

The index describes staged content. The working-tree column describes that path now. Attributes express conversion policy for commit or checkout. Treating policy as a completed conversion receipt would misread this example. Disk CRLF also does not establish CRLF in the index.

Repair the input the consumer uses

A job packaging the working tree needs its disk content and current input identity. A job exporting a fixed commit needs that commit's bytes. The index is not the input to every delivery path.

For normalization, establish the policy and choose an operation suitable for the current task. Preserve existing edits and scope. Verify staging, checkout, or explicit conversion in a controlled case before applying it. This fixture did not run bulk renormalization or overwrite a shared working tree.

For instance, a future LF commit can include a reviewed attribute change and an explicitly selected normalization set. Read back the resulting index and diff so unrelated business edits are not staged accidentally. Other working-tree changes can still leave the local and staged versions different.

Some projects intentionally store LF while checking out CRLF in particular environments. That difference can satisfy the policy. Define which consumers require which bytes before deciding that unequal columns should fail a gate.

Associate the report with the current file

Retain the relevant commit or index state, path, and working-file digest. An editor can save the same filename again after observation. Attaching that new report to an earlier build would misidentify its input. Inspect the actual delivery snapshot and use the fields to explain its source.

An application may accept multiple separators or require one. The byte checks do not exercise its parser or establish that a script runs on another operating system. Bind a separate parser or execution check to the same file version where the delivery contract requires it.

Git also has classifications for nontext, no line endings, and unavailable content. An empty field needs investigation of the index entry and working path before it is labeled LF. The fixture uses an accessible regular text file without symlinks, sparse-index behavior, or binary classification.

For reports differing across machines, align commits and actual content before examining local conversion settings. Equal policy does not make different working bytes equal. The three columns and their contents let an investigation separate input, conversion conditions, and observation time.

What if one file mixes LF and CRLF?

Git's content identifiers include mixed. A separate fixture can put LF on one line and CRLF on another, then inspect which of the index and disk versions is mixed. This adds variation within one content object; each object in the main fixture is internally consistent. The mixed branch was not run. Locate the bytes and verify the actual consumer rather than assuming every application rejects the classification.
