How can Docker ADD verify the expected content after a remote download?

Pin an approved digest, exercise matching and one-character-wrong builds, and verify exported bytes beyond download success.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-21 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • Fix the expected digest before building.
  • Identify a genuine mismatch in the negative control.
  • Matching exported bytes does not verify the application.

For an HTTP source, ADD --checksum=sha256:… checks the downloaded content against the supplied digest. A successful download establishes receipt, while expected byte identity requires a digest fixed in advance. That expected value also needs provenance; an arbitrary fresh download must not silently become the new baseline.

Suppose a build consumes a public text. Pin its reviewed digest, then deliberately alter one character as a negative control. Both builds target the same source. Verify the successful exported bytes and the specific mismatch rejection, rather than counting nonzero command results.

Pin the source, digest, and output

This Dockerfile retrieves the Open Container Initiative image-spec README through a URL containing a full commit identity. It is public teaching material, not product configuration. The scratch build exports a local file without running a container, pushing an image, or publishing a service.

FROM scratch
ADD --checksum=sha256:3e104c2dc2032ca367461f50f213adca7ef77530ed53785519065a7a674ac4d5 https://raw.githubusercontent.com/opencontainers/image-spec/147f9c13cedb47a0c4d9a11a222961073d585877/README.md /payload/input.txt

Save it as Dockerfile. The SHA-256 identifies the frozen input and must not be replaced automatically if a later build fails. The Dockerfile frontend must support HTTP checksum. The current reference lists the HTTP option from version 1.6. Actual acceptance still needs this build's diagnostics and negative control.

Save wrong.Dockerfile with only the initial digest character changed from three to zero. Source and destination remain unchanged. This is intentionally invalid input, not another approved identity.

FROM scratch
ADD --checksum=sha256:0e104c2dc2032ca367461f50f213adca7ef77530ed53785519065a7a674ac4d5 https://raw.githubusercontent.com/opencontainers/image-spec/147f9c13cedb47a0c4d9a11a222961073d585877/README.md /payload/input.txt

Keep the frozen public text as input.md beside these files. It provides an extra comparison, not a dynamically generated expected digest. This script requires a Docker builder, shasum, cmp, and rg. It uses separate fresh contexts and outputs, reads back the correct file, and checks the specific wrong-build diagnostic.

set -eu
work=$(mktemp -d)
mkdir "$work/good" "$work/wrong"
cp Dockerfile "$work/good/Dockerfile"
cp wrong.Dockerfile "$work/wrong/Dockerfile"
docker version --format '{{.Client.Version}} / {{.Server.Version}}'
docker buildx version
docker buildx build --progress=plain --output "type=local,dest=$work/out" "$work/good"
file="$work/out/payload/input.txt"
printf '%s  %s\n' 3e104c2dc2032ca367461f50f213adca7ef77530ed53785519065a7a674ac4d5 "$file" | shasum -a 256 -c -
cmp input.md "$file"
status=0
docker buildx build --progress=plain --output "type=local,dest=$work/rejected" "$work/wrong" > "$work/wrong.stdout" 2> "$work/wrong.stderr" || status=$?
test "$status" -ne 0
rg 'digest mismatch' "$work/wrong.stderr"
test ! -e "$work/rejected/payload/input.txt"
printf 'fixture=%s\nwrong-exit=%s\n' "$work" "$status"

The actual local matching build exported payload/input.txt, which passed the independent SHA-256 check and matched the saved text. The wrong digest returned exit one with digest mismatch, showing actual and expected digests, without an acceptable target file. This negative control establishes that the supplied digest was checked rather than the URL merely downloaded.

Not every nonzero result means a checksum mismatch. Connectivity, authentication, or unsupported frontend options can stop a build too. Preserve the full error and identify the digest rejection. Without that diagnostic, record that the intended verification was not completed. Both original outputs were retained; no network error was substituted for a mismatch.

Hand off the digest's prerequisites

Downloading a file and automatically writing its new digest into the Dockerfile on every run lets any new content become correct. That describes current receipt without checking an earlier approved input. Freeze candidate bytes, provenance, and digest first; let the builder check independently. Here input.md is retained evidence, not a newly accepted download before every build.

A digest also does not establish source trust. An unapproved file can have a stable digest. Decide which input may enter the build, then use the checksum to preserve its identity. This example does not assess licensing, business meaning, production suitability, or all supply-chain risks.

A commit-pinned URL expresses the selected version without replacing receiver-side content verification. Retain URL, approved digest, snapshot, and exported-file checks. They identify intended source, expected bytes, and actual retained bytes respectively. State missing evidence rather than keeping only the final success line.

Read the current output, too. Reusing a directory can leave an old file after failure and mislead a check. Fresh temporary output and a separate rejected branch avoid that ambiguity here. Docker does not manage every consumer's directory lifecycle. Define it explicitly when integrating this assertion into an existing pipeline.

What this small build does not verify

The scratch fixture has no program entry point and does not test application startup. Matching text cannot establish downstream parsing, execution permissions, container networking, or business behavior. A consuming program needs its own environment and content assertions. None was run here.

The wrong-digest control does not simulate every remote change. It holds the source fixed and changes the receiver's expectation to verify rejection. Testing content changes between requests needs a controlled service and request timeline. The receipts cover one fixed text with matching and one-character-wrong digests only.

After preserving inputs, builder versions, logs, and content checks, remove only the temporary directory printed by this exercise. Do not delete other outputs by a vague prefix. Hand off runnable files alongside execution receipts and indicate any cache use. A cache hit is not failure, but its log alone cannot replace readback and the mismatching-digest control.

Does a Git source use a file SHA-256 too?

It has a different contract. The current Dockerfile reference uses a commit SHA for Git sources and a content SHA-256 for HTTP sources. A README file digest cannot substitute for the former's commit identity. Only HTTP text was tested here; Git ADD was not run. Rebuild the example for its source-type contract before claiming that branch passes.
