Why can setRangeText produce the same text with different selections?

Compare three selection modes for one replacement and retain the text plus both endpoints before the next editing action.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-21 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • The replacement interval can differ from the original selection
  • Equal resulting text can have different endpoints
  • Retain both value and position in the test

Replacing cd with XYZ can produce the same abXYZef while leaving different selections. setRangeText uses selectionMode to select the replacement, collapse to its end, or adjust the original range. A text-only test can pass while the next keystroke replaces an unintended selection.

Replacement and selection have separate coordinates

HTML text-control selection APIs use code-unit offsets in the relevant value. This fixture uses an ordinary text input and ASCII. The replacement starts at start and ends before end.

In abcdef, the range two to four identifies cd. XYZ has three units instead of two, increasing the value's length by one. The original selection is separately set to one through five, covering bcde. It is deliberately different from the replacement range.

Select chooses the new text at offsets two and five. End collapses both endpoints to five. Preserve adjusts the original range relative to the edit: the original start at one precedes it, while the original end at five follows it and moves to six with the length increase.

All three outcomes can accompany abXYZef. Retain the value and both endpoints. Selecting the suggestion for review and continuing to type after it are different tasks. The method does not infer that product choice.

Mark zero before a, two before c, and four before e. The interval two to four removes cd while retaining e. Treating the end as the index of the final deleted character would remove an extra unit. Establish that interval before comparing selection modes.

Three controls begin from one specified state

The complete page creates a fresh input for each mode, writes the same text, sets the same original selection, and performs the replacement. It never reuses another mode's modified control. Readings retain the mode, value, and both endpoints.

<!doctype html>
<meta charset="utf-8">
<title>Replacement selection modes</title>
<script>
addEventListener('DOMContentLoaded', () => {
  const create = document.createElement.bind(document);
  const panel = create('div');
  const results = [];
  for (const mode of ['select', 'end', 'preserve']) {
    const input = create('input');
    input.type = 'text';
    input.value = 'abcdef';
    input.setSelectionRange(1, 5);
    input.setRangeText('XYZ', 2, 4, mode);
    results.push({ mode, value: input.value,
      start: input.selectionStart, end: input.selectionEnd });
    const label = create('label');
    label.append(mode + ' ', input);
    panel.append(label, create('br'));
  }
  const output = create('pre');
  output.append(JSON.stringify(results, null, 2));
  panel.append(output);
  document.body.append(panel);
});
</script>

The standards-based expectations are abXYZef in every case, with endpoints 2/5 for select, 5/5 for end, and 1/6 for preserve. No browser was run, so these are not observed local outputs. Product evidence still needs actual readings in its target environment.

Logical selection properties do not establish a currently visible highlight. The fixture sets ranges on newly created inputs without making focus a prerequisite for reading them. Actual interaction should inspect the editing control, focus, and visible selection separately.

As a negative control, passing end for every mode would preserve all text expectations while failing the first and third selection expectations. This catches a lost mode more effectively than checking that XYZ appears somewhere. Retain independent initial values and ranges.

Choose the policy from the editing task

A proofreading tool may let someone overwrite a suggested word immediately or continue after it. Follow the replacement with the intended next action and inspect where input lands before choosing a mode.

Asynchronous preparation can make stored offsets stale. If the user keeps typing, two through four may no longer identify the original text. Check the current value or document version before replacement and relocate or request confirmation under the product's policy. This synchronous fixture implements no collaborative position system.

A later whole-value assignment or framework render can also replace the state established here. Identify the owner of input state and connect the API to its supported update path. Local replacement, replacing the full value, and setting a selection are separate operations.

See programmatic values and input events for notification responsibilities. This page checks replacement content and positions; it treats no event count as a document version and validates no framework synchronization.

Non-ASCII text needs a consistent offset unit. A user-perceived symbol can occupy multiple code units. Preserve the original text, unit, and actual range instead of generalizing from six Latin letters to every writing system.

Observation timing matters too. A later handler may move focus or selection. Read immediately after the call to test its direct result, and separately record the state before the user's next action when investigating the editing experience.

Will start greater than end swap the endpoints automatically?

It will not repair this input that way. This adds a reversed range to the valid forward ranges above. The HTML algorithm throws IndexSizeError before modifying text. Do not transfer endpoint-adjustment behavior from a different selection interface to this method.

<!doctype html>
<meta charset="utf-8">
<title>Reversed replacement range</title>
<script>
addEventListener('DOMContentLoaded', () => {
  const create = document.createElement.bind(document);
  const input = create('input');
  input.type = 'text';
  input.value = 'abcdef';
  let errorName = 'none';
  try {
    input.setRangeText('XYZ', 4, 2, 'select');
  } catch (error) {
    errorName = error.name;
  }
  const output = create('pre');
  output.append(JSON.stringify({ errorName, value: input.value }));
  document.body.append(input, output);
});
</script>

The independent page's expected error is IndexSizeError with value still abcdef. It was not run in a browser. If a product accepts a directional drag selection, its input handling should establish the intended valid interval before requesting replacement.
