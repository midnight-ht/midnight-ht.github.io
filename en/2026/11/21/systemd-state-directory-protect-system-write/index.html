Where can a systemd service write state with ProtectSystem=strict?

Keep necessary state writes in a managed directory and check an EROFS control with the same identity; Linux execution remains unrun.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-21 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • Managed state directories are excluded from read-only protection.
  • Identify the precise error in the rejected control.
  • Verify recovery separately from access.

Declare service state with StateDirectory; its managed location is excluded from the read-only effect of ProtectSystem=strict. This allows necessary state writes without opening an entire system tree. This example concerns a Linux systemd system service with one state directory.

Suppose a service needs a progress marker. Rather than disabling protection after arbitrary system-path writes fail, identify service-owned state and bind the program to the directory supplied by the manager. Writability establishes access, while the contents still require an application assertion.

Test an allowed write and a rejected control

This is a reproducible fixture for an isolated Linux host, not a Linux execution report. On macOS, only the inputs and Python/Shell syntax were checked. No service start, mount view, or read-only error was observed here. All following runtime results are expectations.

Save check.py. It writes through STATE_DIRECTORY and reads back the exact value. The same process then tries an ordinary dedicated control directory and accepts only EROFS. Other errors, including missing paths and permission denial, propagate; an unexpected successful control write also fails.

import errno
import os
from pathlib import Path

state = Path(os.environ["STATE_DIRECTORY"])
marker = state / "marker"
marker.write_text("state-ok\n")
assert marker.read_text() == "state-ok\n"
print("STATE_READBACK_OK", state, flush=True)
try:
    Path("/var/lib/zy21-control/marker").write_text("unexpected\n")
except OSError as exc:
    if exc.errno != errno.EROFS:
        raise
    print("CONTROL_EROFS", flush=True)
else:
    raise AssertionError("control directory unexpectedly writable")

Save check.service. This teaching unit explicitly uses root, so the host-created root-owned control directory is writable at the ordinary permission layer. That is not a production identity recommendation. The common identity helps distinguish read-only mount protection from directory ownership.

[Unit]
Description=Isolated managed-state write check

[Service]
Type=oneshot
User=root
Group=root
StateDirectory=zy21-state
StateDirectoryMode=0700
ProtectSystem=strict
ExecStart=/usr/bin/python3 /run/zy21-state-check.py

On an isolated Linux host where these dedicated paths may be created, run as root from the input directory. The absence checks prevent overwriting an existing unit or state. The host needs the systemd system manager, support for these protections, and /usr/bin/python3. Investigate missing prerequisites rather than ignoring errors.

set -eu
test "$(id -u)" -eq 0
test ! -e /var/lib/zy21-state
test ! -e /var/lib/zy21-control
test ! -e /run/zy21-state-check.py
test ! -e /etc/systemd/system/zy21-state-check.service
install -d -m 0700 /var/lib/zy21-control
install -m 0600 check.py /run/zy21-state-check.py
install -m 0644 check.service /etc/systemd/system/zy21-state-check.service
systemctl daemon-reload
systemctl start zy21-state-check.service
journalctl -u zy21-state-check.service --since '5 minutes ago' --no-pager
cat /var/lib/zy21-state/marker

Expected logs contain both STATE_READBACK_OK and CONTROL_EROFS, and the host reads state-ok from marker. One verifies a particular state write and readback; the other verifies rejection at the ordinary control directory. A successful systemctl result alone does not identify the asserted contents, and an arbitrary OSError does not identify its cause.

Why use a managed state location?

The systemd.exec directory and protection reference excludes managed directories such as StateDirectory from ProtectSystem's read-only effect. For system services, state directories are under /var/lib. The manager creates them and handles ownership according to configuration. Consuming the supplied location avoids a separately hard-coded state root drifting from the unit.

The ordinary control is created on the host before startup at a different path. It exists and root has directory permissions, yet the service is expected to see it read-only. This checks the fixture's protection, not comprehensive service isolation. Other mounts, explicit exceptions, identities, and host capabilities can change an application's actual writable scope.

Decide whether contents really belong to one service before choosing this facility. Shared database files and directories maintained by several accounts have different ownership requirements. Do not move an existing shared path under a dedicated state name merely to make the fixture pass. Identify ownership, choose storage, then verify readback and the rejected control.

A green receipt also cannot establish recovery semantics. Partial files after a failed update and format compatibility on the next start belong to the application. This fixture writes a fixed string without power-loss, concurrency, or migration tests. Real state formats need appropriate atomic-update, recovery, or migration checks. Writability is not a durability guarantee.

Check retention and clean up owned paths

StateDirectory has a different lifecycle from temporary runtime storage: stopping the service does not automatically remove the state directory. A stop followed by reading marker could check retention, but that was not run here. If contents must be cleared on every start, reconsider whether they are persistent state rather than treating retention as a cleanup defect.

After preserving logs and contents, stop the fixture, remove its unit and /run script, and reload the manager. Once no other references exist, remove only the two dedicated /var/lib directories that the preflight established did not exist. Never delete the entire parent tree or apply this cleanup to existing production state. Keep the inputs and pre-cleanup evidence.

For a failed write, identify the current start's logs, actual STATE_DIRECTORY value, effective unit configuration, and error class. If Python never started, fix its invocation first. EACCES calls for permission inspection. EROFS on the managed path calls for host-support and configuration checks. This is a diagnostic sequence, not a list of locally reproduced errors.

A journal time window is only a convenient search filter. Repeated starts can share that window. Associate the current invocation result with its corresponding entries and establish that both markers belong to the same execution before accepting the receipt. Old entries cannot replace a missing current result.

Can the variable still be treated as one path with two entries?

The single-path assumption no longer holds. The reference specifies a colon-separated STATE_DIRECTORY value for multiple entries. Parse it according to the application's directory contract and identify each purpose; passing the whole string to Path can mistake several locations for one pathname. This introduces a new directory-count condition. No multi-directory service was run. Verify each destination with its own write and readback rather than extending the one-directory result.
