Why does unpack reject a complete frame larger than its two-byte header?

Compare exact and offset header decoding, a short header, payload boundaries, and incomplete fixed records.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-21 · Estimated read 10 min
Translations

Article

Key takeaways

  • unpack requires an exact format-sized buffer.
  • unpack_from requires sufficient bytes after its offset.
  • Whole-frame and fixed-record tail validation remain separate checks.

A frame contains its two-byte header, yet struct.unpack rejects it because payload follows. unpack requires the whole supplied buffer to match the format size exactly. unpack_from can read a field at an offset in a larger buffer. Validate payload boundaries separately.

Enough header bytes and an exact format buffer

The teaching frame holds marker X, a two-byte length, and payload abc. !H specifies a network-order unsigned short with a standard two-byte size. The length starts at offset one and the payload at three, avoiding native alignment assumptions.

unpack treats its buffer as the complete format input. The full frame is too large, although the length value itself is valid. A two-byte header slice satisfies that contract. unpack_from instead requires sufficient bytes after the requested offset and permits payload afterward.

That condition establishes field readability. It does not validate the marker, allowed length, or complete payload. Preserve those checks separately before accepting an application message.

Compare the full buffer, slice, and offset

The fixture creates fixed bytes in memory. It runs no socket or external-message receiver. Fixed-record iteration supports the follow-up.

from struct import Struct, error, iter_unpack

header = Struct("!H")
pack = header.pack
decode = header.unpack
decode_from = header.unpack_from
assert header.size == 2
frame = b"X" + pack(3) + b"abc"
try:
    decode(frame)
except error:
    pass
else:
    raise AssertionError("unpack must reject an oversized buffer")
assert decode(frame[1:3]) == (3,)
assert decode_from(frame, 1) == (3,)
assert frame[3:] == b"abc"
try:
    decode_from(b"X\x00", 1)
except error:
    pass
else:
    raise AssertionError("only one header byte remains")
assert list(iter_unpack("!H", pack(3) + pack(4))) == [(3,), (4,)]
try:
    list(iter_unpack("!H", pack(3) + b"X"))
except error:
    pass
else:
    raise AssertionError("fixed records require a size multiple")
print("exact buffer and offset controls passed; incomplete headers/records rejected")

The full frame must raise struct.error. The exact slice and offset decode both return the one-item tuple containing three, and the payload slice must equal abc. Even a single field returns a tuple, which the expected values preserve.

After offset one, the short control has just one header byte and must fail. It catches a mistaken check on total buffer size instead of remaining size. The success control retains abc afterward, showing that the offset interface accepts a larger buffer.

These assertions implement no network framing. A receiver may have only part of a header or several messages at once. Decide when to wait for more data and when an ended input is truncated. Here the short buffer is a complete fixed argument to the library call.

Separate fields from message completeness

For this layout, the header ends at three and declares three payload bytes, so the message should end at six. A five-byte buffer still permits decoding the length but lacks payload. Additional bytes need a protocol decision: another frame, an allowed trailer, or an error. unpack_from cannot choose that policy.

An application test can specify a full frame, short header, short payload, and adjacent frames, checking the decoded value, consumed bytes, remainder, and failure recipient. Returning a length alone cannot establish full-message acceptance. These framing variations are proposals outside the fixture.

Keep format strings in the interface contract. One side using !H and another using native defaults can disagree about representation. Cross-check fixed samples from any supported external implementation. This example verifies no device compatibility or universal native size.

The site's concatenated gzip member article addresses another boundary between decoded bytes and business records. Here a correctly extracted header is likewise only input to further validation.

All fixture offsets are explicit nonnegative constants. A public API allowing callers to choose them needs its own contract for negative, out-of-range, and boundary offsets and the resulting errors. Those cases are outside this run.

Retain the actual offset in diagnostics. Accidentally reading at zero can still produce a plausible integer. Use visibly different marker, header, and payload bytes and exact expected values. An all-zero sample is weak evidence for offset correctness.

Does iter_unpack ignore an incomplete final record?

Its buffer length must be a multiple of the record size. Two !H records yield three and four; an extra X after one complete record must raise. The interface does not silently discard it. This is a whole-record iteration condition, separate from reading one field from a larger payload. If a protocol permits a trailer, validate and separate that region explicitly before iterating complete records.
