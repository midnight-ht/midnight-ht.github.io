Why can a new defineProperty value resist writes and disappear from key lists?

Compare new descriptor and literal properties through values, flags, keys, and writes, with creation and update treated under their own conditions.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-21 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • Omitted flags default to false for new data properties
  • Reading a value does not establish editability or enumeration
  • Check each attribute against the field contract

A new property created with defineProperty and only value can read as A, reject an edit, and disappear from Object.keys. The creation contract can explain all three observations. For a new data property, omitted writable, enumerable, and configurable flags default to false. That differs from an ordinary object-literal field.

A value does not establish a property's behavior

ECMAScript's Object.defineProperty applies the supplied descriptor to property definition. When an ordinary extensible object has no such property, omitted attributes take their defaults. The current property table gives false defaults for writability, enumerability, and configurability. This example concerns new ordinary data properties, without accessors or proxies.

Directly reading code therefore does not establish that it will appear in an enumerable key list. Ownership, writability, and enumeration are separate conditions. A successful value read alone misses the contract needed for later editing.

Replacing an object literal with a descriptor can retain the initial value while changing later operations. Compare what callers previously could do, rather than only the initial display. An intentional restriction also deserves explicit configuration so maintainers can identify it.

Retain configurability in the diagnosis even when the immediate symptom concerns a write. It addresses later changes to the property definition. Avoid collapsing several attributes into a generic locked state; inspect each against the operation the caller needs.

Two objects start with the same value

This complete script creates independent descriptor and literal inputs. For each it records the initial value, descriptor, and enumerable keys, attempts the same Reflect.set, then reads the value again. Literal expectations are specified before execution.

import { deepEqual } from 'node:assert/strict';
const defined = {};
Object.defineProperty(defined, 'code', { value: 'A' });
const literal = { code: 'A' };
function inspect(object) {
  const before = object.code;
  const descriptor = Object.getOwnPropertyDescriptor(object, 'code');
  const keys = Object.keys(object);
  const writeAccepted = Reflect.set(object, 'code', 'B');
  return { before, descriptor, keys, writeAccepted, after: object.code };
}
const actual = [inspect(defined), inspect(literal)];
deepEqual(actual, [
  {
    before: 'A',
    descriptor: { value: 'A', writable: false, enumerable: false, configurable: false },
    keys: [], writeAccepted: false, after: 'A'
  },
  {
    before: 'A',
    descriptor: { value: 'A', writable: true, enumerable: true, configurable: true },
    keys: ['code'], writeAccepted: true, after: 'B'
  }
]);
console.log(JSON.stringify(actual));

Exact local Node execution passed. Both objects began at A. The first had three false flags, no enumerable key, a false write result, and a final A. The second had three true flags, the code key, a true write result, and a final B. This receipt establishes the local language fixture; no component, API, or persistence path was exercised.

Reading the property directly might restore a missing display while leaving it nonwritable. Listing more own keys also would not change its write result. Each repair must address the attribute required by the actual field contract.

The script retains both the Reflect.set result and the subsequent value. An absence of exceptions is an incomplete write check. A Boolean result alone also cannot establish the contents of a later business submission. Keep the observations attached to the same object and attempt.

The descriptor was read before the attempted write. The second record therefore retains A in its descriptor while its final value is B. Record observation timing. A previously returned descriptor is not a live reading of later property changes; reread it after the write when that is the required check.

Reconnect creation with the field's role

An editable record can explicitly allow the required operations when creating its properties. That does not call for enabling every flag on every field. A generated identity, read-only display metadata, and user input may have different owners and update rules.

A wrapper may also supply flags for its caller. Inspect the returned object's actual descriptor instead of relying only on the business arguments passed into that wrapper. Another entry point may create a literal object with a different contract under the same field name.

Export and editing need separate checks. A list built from enumerable keys can omit this field consistently with its descriptor. Whether to export it belongs to the data representation contract. See object enumeration and key order for that related output question. Here the mechanism is the attribute set chosen during creation.

Nonenumerability supplies no confidentiality boundary. The code already reads the known property name directly. Exclusion from one key list does not establish access permission, and this fixture supplies no sensitive-data hiding scheme.

Retain the creation entry point, whether the property existed, the complete descriptor, required operations, and their results. That distinguishes a changed property contract from a caller using a different operation. A final screenshot of A erases the differences between creation, enumeration, and writing.

Do omitted flags become false when updating an existing property too?

The new-property rule cannot be transferred unchanged. This adds an ordinary writable field already created by a literal, then updates it with a value-only descriptor. Omitted flags are not reset wholesale to false on an existing property.

import { deepEqual } from 'node:assert/strict';
const row = { code: 'A' };
Object.defineProperty(row, 'code', { value: 'B' });
const descriptor = Object.getOwnPropertyDescriptor(row, 'code');
deepEqual(descriptor, {
  value: 'B', writable: true, enumerable: true, configurable: true
});
console.log(JSON.stringify(descriptor));

Local execution produced value B with all three flags still true. The difference from the main fixture is whether the property already existed. Keep separate creation and update cases when reviewing a wrapper so its defaults are not generalized beyond the applicable branch.
