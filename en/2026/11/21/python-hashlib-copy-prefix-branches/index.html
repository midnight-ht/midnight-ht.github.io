Why did the second hash include the first suffix?

Check copied prefix branches against complete byte inputs, an alias contamination control, and a later update after digest observation.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-21 · Estimated read 11 min
Translations

Article

Key takeaways

  • Another variable can reference the same accumulating state.
  • copy creates independent branches from the current prefix.
  • Reading a digest still permits later updates.

Two payloads share a prefix. Code appends A and then B to one hash object, so the second result includes A. update continues the existing state. To calculate two independent suffix branches, copy the prefix state and update each copy separately.

A renamed variable does not restart the input

The intended inputs are prefix:A and prefix:B. Assigning the hash object to another variable leaves both names pointing at one state. After A and B, that object represents prefix:AB. The hash calculation can be correct for the wrong input.

The documentation defines successive update calls as equivalent to updating with their concatenated arguments. Another call does not create another task. Alongside the actual bytes, check which object each processing step owns and whether earlier work has already appended data.

copy clones the current state. Copies of a fixed prefix can receive A and B independently. Keep ownership of the baseline clear: if another caller updates it, future copies inherit the extra data.

Compare against independently assembled full inputs

Fresh SHA256 objects are created from the complete expected byte strings. No branch supplies the other branch's expected answer. It checks the prefix, independent results, and an alias failure control. It reads no file and runs no authentication protocol.

from hashlib import sha256

def hex_of(state):
    return state.hexdigest()

base = sha256(b"prefix:")
left, right = [base.copy() for _ in range(2)]
for state, suffix in [(left, b"A"), (right, b"B")]:
    state.update(suffix)
for state, complete in [
    (base, b"prefix:"), (left, b"prefix:A"), (right, b"prefix:B")
]:
    assert hex_of(state) == hex_of(sha256(complete))
bad = sha256(b"prefix:")
alias = bad
alias.update(b"A")
bad.update(b"B")
assert hex_of(bad) == hex_of(sha256(b"prefix:AB"))
assert hex_of(bad) != hex_of(right)
before = hex_of(left)
left.update(b"C")
assert before == hex_of(sha256(b"prefix:A"))
assert hex_of(left) == hex_of(sha256(b"prefix:AC"))
assert hex_of(base) == hex_of(sha256(b"prefix:"))
print("A/B branches independent; alias accumulated AB; digest observation did not freeze AC update")

The branches equal fresh hashes of prefix:A and prefix:B, while the baseline still represents prefix:. The alias path equals prefix:AB and differs from the correct B branch. Every path yields valid hexadecimal text, so output format alone cannot catch the contamination.

Check the baseline too. Two distinct branches copied from a baseline already containing A would still start from the wrong bytes. Object independence and correct initial state are separate conditions.

Full-input recomputation gives the fixture an easily inspected reference construction. It tests no cryptographic property across implementations. A file workflow also needs evidence about the actual file and read range; rehashing sender-side bytes cannot verify receiver-side storage.

A proposed empty-suffix control can check the branch origin. A fresh copy with no new bytes should match the prefix digest, without being the same object. Updating one copy afterward should leave the other at the prefix. This extra test targets copy timing and is outside the executed fixture.

Distinguish continuing one stream from branching another payload

For one file, successive chunk updates intentionally preserve state. Resetting before every chunk would be wrong. For separate files, continuing the previous state erases the file boundary. Name those two operations and their input identities explicitly.

Create suffix branches after the prefix is fixed. If a prefix can change, version it and record which version each task used. This run has one fixed prefix and tests no thread coordination, process transfer, or external scheduling.

The site's digest representation article concerns byte and hexadecimal formats. This bug occurs earlier: both sides can use hexdigest and still disagree because one accumulated an extra A. Check input composition and ownership before changing representation.

A digest supplies no sender authentication by itself. Identical bytes can produce matching results without establishing who generated them. Approved version, trusted sender, and freshness need their own protocol evidence. The fixture implements no signing, authentication, replay decision, or performance comparison.

Can update continue after reading a digest?

Yes. Reading a digest observes current input without finalizing the object. The last control saves the A branch's hexadecimal string, then appends C. The saved string still describes prefix:A; the current object describes prefix:AC.

A saved string can retain a checkpoint. A saved reference to a hash object that keeps changing can expose a later state. Record when the digest was produced so a mid-task observation does not become a claimed final-file result. The example checks this standard-library continuation only.
