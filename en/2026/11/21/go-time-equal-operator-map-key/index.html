Why does a map keep two Time keys for the same instant?

Compare Equal, structural equality, and normalized map keys for two location representations of one instant.

Updated 2026-11-21 · Estimated read 10 min

Article

Key takeaways

  • == includes location and monotonic representation.
  • Instant-based keys need consistent location and stripped monotonic state.
  • Equal instants do not establish business event identity.

Two time.Time values represent one instant. Equal returns true, but a map retains two keys. Go's == also compares Location and any monotonic reading, and maps use that structural comparison. An instant-based key policy should normalize location and remove monotonic state.

Same instant, different representation

One event is represented as noon UTC and again as one o'clock at a fixed plus-one offset. Both describe the same instant. Equal recognizes that fact, while the Time representations can occupy separate map entries.

The map follows Go key comparison; it does not invoke Time.Equal automatically. Decide whether location belongs to identity. Separate location views may be intentional, while instant-based caching needs another representation policy.

The Time documentation explicitly includes location and monotonic readings in == and recommends consistent location plus removal of monotonic state before key use. The fixture uses UTC and Round(0) in one key function. UTC avoids dependence on a machine's local zone.

Check clocks, equality, and both maps

This Go fixture is unexecuted. It uses a fixed date and a fixed plus-one teaching zone, with no current-clock or city-rule dependency.

package main

import "time"

func key(t time.Time) time.Time {
    return t.Round(0).UTC()
}

func main() {
    utc := time.Date(2026, 1, 1, 12, 0, 0, 0, time.UTC)
    offset := utc.In(time.FixedZone("plus-one", 3600))
    if !utc.Equal(offset) || utc == offset {
        panic("instant and structural equality must differ")
    }
    if utc.Format(time.RFC3339) != "2026-01-01T12:00:00Z" {
        panic(utc)
    }
    if offset.Format(time.RFC3339) != "2026-01-01T13:00:00+01:00" {
        panic(offset)
    }
    raw := map[time.Time]string{utc: "UTC", offset: "offset"}
    canonical := map[time.Time]string{key(utc): "UTC", key(offset): "offset"}
    if len(raw) != 2 || len(canonical) != 1 {
        panic("map key policy mismatch")
    }
    later := utc.Add(time.Second)
    if key(utc) == key(later) {
        panic("normalization must not erase a second")
    }
}

The displays are noon UTC and one o'clock plus one. Equal is true and == is false. The raw map has two entries; normalized keys produce one. The second assignment overwrites the value under that shared key, so a business cache still needs a policy for competing contents.

Adding one second must remain distinguishable after normalization. That rejects a repair that merely rounds keys to minutes or dates. Merging the original pair cannot justify merging genuinely distinct instants.

No request parsing or database participates. A misinterpreted timezone-free input would remain the wrong instant after normalization. The site's timezone-free input article covers that earlier boundary.

Apply one key policy to writes and lookups

Normalizing insertion alone can leave queries using a different representation. An integration test can write through UTC and look up through an equivalent offset value, then reverse the direction. The fixture checks key equality and entry count; that access-path variation is unexecuted.

A cache containing only the UTC key supplies three proposed lookup controls: the unnormalized offset lookup misses, the normalized equivalent hits, and a normalized query one second later still misses. These checks exercise the caller more directly than final entry count and remain unexecuted.

Preserve the original location as a record field when display needs it. A local-calendar appointment identity, on the other hand, can need location and calendar fields in its key. Define identity before discarding representation details.

Equal time also supplies no event identity. Two messages might repeat one event or describe different simultaneous events. Deduplication needs the business identifiers and sources required by the contract. A composite-key control can retain two identifiers sharing an exact instant, or an aggregation can keep both in its value list. Neither application index is implemented here.

Persisted keys need a precision contract too. Saving a nanosecond value as seconds can erase distinctions before reading it back. Verify the actual storage round trip. This fixture uses Time values and claims no database compatibility.

Does monotonic state from time.Now affect ==?

It participates in structural comparison. Round(0) strips it without changing the represented instant. The documentation also describes Equal's handling when only some inputs contain monotonic readings. Consistent UTC alone does not strip that extra state, which is why the key function includes both steps. This fixture uses Date, never Now, and measures no system clock or cross-process timing behavior.
