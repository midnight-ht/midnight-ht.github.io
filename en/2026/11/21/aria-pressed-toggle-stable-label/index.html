Why does a mute toggle keep the Mute label when aria-pressed changes?

Compare a stable Mute label with pressed and teaching mute states, and distinguish that design from changing action labels.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-21 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • A stable-label toggle retains its function name
  • The pressed declaration must match the function state
  • Test names and states under one chosen design

A mute toggle can remain labeled Mute after muting is enabled. Under the APG's stable-label design, the function name stays fixed and aria-pressed reports whether it is enabled. Changing that name to Unmute while retaining the same toggle-state interpretation can make the combination convey a different meaning.

The stable name and current state have separate roles

The W3C Button Pattern uses mute to explain that a toggle label remains unchanged when its pressed state changes. Mute names the function. True means muted and false means not muted. A description of the next action should not silently replace that state meaning.

The same control therefore keeps naming the same function. Someone can find Mute again, inspect its state, and decide whether to toggle it. A visual indicator can supplement that state. No exact screen-reader announcement is promised here.

The APG also describes a different design: changing action labels between Mute and Unmute without needing aria-pressed for that toggle interpretation. Choose a consistent name, role, and behavior contract. The main example fixes the stable-label design instead of assigning this attribute to every button that changes something.

The attribute itself does not mute the application. Writing true while the media remains unchanged leaves an inaccurate declaration. Changing the function while leaving false on the button creates the reverse mismatch.

One Boolean drives two teaching outputs

This complete page retains the Mute label. Activation changes a local muted value and renders both pressed and a teaching status text. It loads and plays no audio. The Boolean is not evidence of a real media device being controlled.

<!doctype html>
<meta charset="utf-8">
<title>Stable toggle label</title>
<button id="mute" type="button" aria-pressed="false">Mute</button>
<p id="state">Teaching muted state: false</p>
<script>
const button = document.getElementById('mute');
const output = document.getElementById('state');
let muted = false;
function render() {
  button.setAttribute('aria-pressed', String(muted));
  output.textContent = 'Teaching muted state: ' + muted;
}
button.onclick = () => {
  muted = !muted;
  render();
};
</script>

The independent expectations are Mute/false/false initially, Mute/true/true after one activation, and Mute/false/false after another. Repeat the cycle to check reopening and closing through the same rendering entry point.

These are source-and-code predictions. No browser or assistive technology was exercised. A product test should reach and activate the control through supported input methods and record its name, state, and actual functional result. Real audio needs its own media or business-state evidence.

A negative control can update pressed without updating muted. The readings should disagree. A component rerender could also retain the function while replacing the toggle with a button lacking pressed. A click-handler invocation alone misses both user-facing outcomes.

Test the real keyboard entry point too. The APG lists Space and Enter activation for a focused button. Start each case from off and check that one activation changes state once. A custom key handler combined with native activation can toggle twice and return to the initial state. This page adds no custom keyboard handling. A wrapper that does so needs observations of each transition, not just the final Boolean.

Identify the chosen naming contract first

A stable-label test should not demand Unmute after activation. It should retain the same function name and inspect the pressed state. Mixing expectations from different designs can reject a consistent control or accept an incoherent combination.

Inspect the actual accessible name too. Visible Mute text can coexist with a stale aria-label naming another action. A screenshot cannot establish the computed name. Minimize competing naming sources and inspect the resulting name in the target environment when needed.

An asynchronous media operation also needs a decision about when the state becomes true. Flipping the declaration when sending a request and retaining it after failure can misdescribe the function. Define waiting, success, failure, and restoration under the product's state flow. The local Boolean fixture implements none of that device workflow.

After switching media sources, a retained muted value may belong to the previous object. A stable DOM identifier does not bind the control to the current media automatically. Stable labeling establishes function recognition, while object association and asynchronous results still need their own handling.

For extra effects caused by settings changes, see input changes and context. That article addresses navigation and focus consequences. This one checks naming and pressed state; neither check alone establishes the whole interaction's conformance.

Can mixed describe a collection with some items on and others off?

This adds multiple controlled objects. A Bold button may control selected text passages, some already bold and others not. WAI-ARIA defines mixed for inconsistent states among controlled items. That differs from the main fixture's one mute Boolean.

Identify the controlled collection and inspect its current states before choosing mixed. Do not use the value as a synonym for loading, an outstanding request, or unknown state. Whether activating the control turns all items on or off belongs to the component's task policy; the mixed declaration does not choose that action.
