Which of the two Buildx metadata digests identifies the image output?

Trace the Buildx output descriptor and its OCI manifest configuration reference, then verify both digests against the local archive.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-17 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • Output and config digests identify separate objects.
  • Follow the manifest to verify its config reference.
  • Retain the output media type alongside the digest.

A Buildx receipt can contain two different SHA-256 values. For the exported image object, look at containerimage.digest and its output descriptor. Use containerimage.config.digest to verify the configuration referenced by the image manifest. They identify separate byte sequences, even when both values appear in one receipt.

This can surface when a release script switches to Buildx metadata. The old release record had one image digest. Someone sees the new configuration field and copies its value over. The build succeeds, but the next stage cannot match the artifact it received. You can trace the references in the archive to see exactly which object each value names.

Fix the shape of the export first

In an empty directory, save this Dockerfile. Create its input with printf 'receipt demo\n' > marker.txt. The build starts from scratch and copies one known file, so it needs no base image pull or program execution. Choose a local Buildx builder that supports the OCI exporter. Write both outputs outside the build context. Request one target platform and turn off extra attestations for the archive so the example can focus on an image manifest and its configuration. The verifier expects a manifest descriptor. A different descriptor needs a different structural check.

FROM scratch
COPY marker.txt /marker.txt

Run the build from the same directory. The Python readback does not load the image into an engine or push it to a registry.

work=$(mktemp -d)
docker buildx build --platform linux/amd64 --provenance=false --sbom=false \
  --output "type=oci,dest=$work/output.tar" \
  --metadata-file "$work/receipt.json" .

Inspect three fields in the receipt. containerimage.descriptor gives the output media type and digest. containerimage.digest records that output digest. Both identify an image manifest in this single-platform archive. The manifest has a separate config descriptor pointing to configuration content. The archive's root index.json locates the manifest in this fixture. Its own bytes are separate from those of the object it points at. Follow the descriptors before deciding which file to hash.

Save this as verify.py and run python3 verify.py "$work/receipt.json" "$work/output.tar". It checks that the output type matches the fixture, retrieves the manifest and configuration from their content addresses, then hashes the two sets of original bytes. It also verifies that the validated manifest references the configuration digest recorded in the receipt. A string with the right digest syntax cannot satisfy the checks by itself.

from hashlib import sha256
import json
from pathlib import Path
import sys
import tarfile

receipt = json.loads(Path(sys.argv[1]).read_text())
descriptor = receipt["containerimage.descriptor"]
output = receipt["containerimage.digest"]
config = receipt["containerimage.config.digest"]
assert descriptor["mediaType"] == "application/vnd.oci.image.manifest.v1+json"
assert descriptor["digest"] == output

with tarfile.open(sys.argv[2]) as archive:
    def read(name):
        member = archive.extractfile(name)
        assert member is not None
        return member.read()

    def verified_blob(digest):
        algorithm, expected = digest.split(":", 1)
        assert algorithm == "sha256"
        data = read(f"blobs/sha256/{expected}")
        assert sha256(data).hexdigest() == expected
        return data

    entries = json.loads(read("index.json"))["manifests"]
    assert any(item["digest"] == output for item in entries)
    manifest = json.loads(verified_blob(output))
    assert manifest["config"]["digest"] == config
    verified_blob(config)

print("output", output)
print("config", config)

The build and readback succeeded locally with Docker Desktop engine 29.8.2 and Buildx v0.37.2. The Linux amd64 manifest digest began with d490f6f4. The configuration digest began with ef05c138. The program checked both full hashes. Those prefixes describe this run. Recompute the values for a different build and check the descriptor type it actually produces. This verifier does not verify image layers, execute the image, or check registry acceptance. The attestation options keep this example focused. Build information in the metadata is a separate observation from attestations in the exported artifact.

Record what the next stage actually consumes

If the next stage takes the exported image object, record the output digest, media type, and artifact location in the handoff. If unpacking or image analysis also verifies the configuration, record its digest with its relationship to the manifest. When the configuration changes, the manifest must reference the new configuration content. Matching configuration bytes do not establish that a whole manifest matches because the manifest also covers layer descriptors and other fields.

Try a negative control by keeping the archive and editing a copy of the receipt. Substitute the configuration digest for the output digest. The verifier should reject it because the descriptor still points to the manifest. If the descriptor digest is also edited, the archive still does not list the configuration as the output manifest. A local follow-up put each mutation in its own copy and kept the archive fixed. The first run stopped at descriptor equality. The second stopped at the archive entry assertion. Both returned one. The controls check that the consumer rejects a valid digest put in the wrong role, which a format check alone would miss.

A real release needs a receipt from the artifact destination too. A successful archive check before upload establishes that the local export can be read. Verify the object reference accepted by the registry during the actual release. Preserve local structural verification separately from the destination's record so a rollback or mismatch can be traced to the right operation.

If the destination reports a different digest, first check which build produced each record and which type of object the destination identifies. Compare their referenced bytes once both sides identify the same kind of object. Preserve the relationship between the build receipt, archive, and handoff log so a reviewer can distinguish a mix-up between build outputs from reading the wrong field. Actual destination acceptance still needs an actual release receipt. The local fixture did not run that step.

Which platform does the output digest identify after a multi-platform build?

If the output descriptor is an OCI image index, the output digest identifies that index. It cannot serve as the digest of one platform's manifest. The index lists descriptors with their own digests. Choose the intended entry from its platform metadata, then verify its manifest and configuration. Check operating system and architecture, along with variant when relevant. If the required identifying information is absent, determine the intended descriptor before using one. The local run was single-platform. No index-output case was run, and the verifier rejects an index at the media-type check.
