Why did a full CMake install omit this component?

Use three fresh CMake installation prefixes to check what a full install and two component installs actually deliver.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-17 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • A component name groups install rules.
  • A full install skips excluded rules.
  • Read back the files in the prefix you actually ship.

CMake finishes installing and the runtime files land in the delivery directory, but the development file is missing. Look for EXCLUDE_FROM_ALL on that file's install rule. A full install skips such a rule. Installing the component that owns it explicitly selects the rule.

Build logs make the distinction easy to miss. Configuration succeeded, installation ran, and some new files appeared. A gate that checks only the installer exit status leaves the missing-file problem for the consumer. To review an installation, find out which rules that invocation selected and whether its actual destination matches the delivery contract.

Run one definition through three installs

Create a directory and save this as CMakeLists.txt. The project needs no compiler. Both source markers have distinct contents. The runtime rule belongs to Runtime and the development rule belongs to Development. Vary only the component selection on the install command. COMPONENT assigns a rule to a group. EXCLUDE_FROM_ALL controls its participation when a full install runs without a component filter. A single rule can have both properties.

cmake_minimum_required(VERSION 3.20)
project(ComponentFixture NONE)

install(FILES runtime.txt DESTINATION share/demo COMPONENT Runtime)
install(FILES developer.txt DESTINATION share/demo COMPONENT Development EXCLUDE_FROM_ALL)

Create the inputs in the source directory, then use a new build directory and fresh prefixes. Check each expected file by reading its content. Also verify that the other file is absent. Keeping all three prefixes separate makes the exclusion observable, and an older file cannot satisfy a readback.

set -eu
printf 'runtime\n' > runtime.txt
printf 'developer\n' > developer.txt
work=$(mktemp -d)
cmake --version
cmake -S . -B "$work/build"
cmake --install "$work/build" --prefix "$work/full"
cmake --install "$work/build" --prefix "$work/runtime" --component Runtime
cmake --install "$work/build" --prefix "$work/dev" --component Development

verify() {
  directory=$1/share/demo
  present=$2
  absent=$3
  test "$(cat "$directory/$present.txt")" = "$present"
  test ! -e "$directory/$absent.txt"
}
verify "$work/full" runtime developer
verify "$work/runtime" runtime developer
verify "$work/dev" developer runtime

A local run on CMake 4.2.3 installed and read back all three prefixes. The full install included only runtime, Runtime included only runtime, and Development included only developer. The first two file lists happen to match. If another component adds a rule without the exclusion, the full installation can include its files too. The run did not add that extra rule.

Use the Development install as the positive control. Finding the file absent after a full install has at least two explanations. The rule may have been excluded as intended, or the project may never have assigned the correct file to Development. Then select the component and read its file to distinguish those cases. For a real component with many files, choose one that the component alone can provide. A generic file available from several components offers weak evidence about whether Development ran.

Choose the install that the release actually promises

A runtime archive may deliberately omit internal development files from the normal install. Its acceptance test then checks that runtime material is present and the development file is absent. A development archive has its own file list. If the product promises users can compile a plugin after following the standard install instructions, run the unfiltered install and check that the development material is there. A CI job that keeps the exclusion but installs Development separately would prove the component works without testing the user-facing default. The release contents determine which behavior matters.

Keep the command and destination together in a handoff. A log might contain one install into the full prefix and another into the Development prefix. A downstream packager that reads the full prefix will produce an archive missing the development file, even though a search of the whole build directory can find that file. List the contents of the path the packager receives. When needed, read the component-specific file out of the archive too. The receipt should connect the relative filenames, component argument, and packaging input, instead of reporting a single success flag.

Reusing a prefix can conceal the behavior in another way. Install Development there first, then run a full install into the same place. The previously installed file can still be in the directory. The listing only shows what is on disk now. Use an empty prefix to check which files the latest invocation produced. The same build directory can serve all three installs. The variables under comparison are the destination and component argument.

Calibrate the archive gate by deliberately giving it the wrong prefix. Tell the packager to produce the development release but point its input at the full install. A check for the development file and its content should fail. Point it back to the Development prefix and the check should pass. This exercise changes where the packager reads, while the install rules remain fixed. The first step catches a superficial nonempty-directory gate. The second verifies the gate accepts the intended development artifact. The local run checked install prefixes without creating an archive. If the real packaging step rewrites paths, read the component-specific file at its final advertised path too.

Which group gets a rule without COMPONENT?

CMake assigns it to the default component, named Unspecified unless the project changes CMAKE_INSTALL_DEFAULT_COMPONENT_NAME. If a team wants rules without component names to belong to Common, check the default effective when those rules are declared, then explicitly install Common into a fresh prefix and read back its files. Both rules in the main fixture name their components, so this branch was not run. When a component archive misses a file from an unnamed rule, trace which group owns the rule before changing the file list.
