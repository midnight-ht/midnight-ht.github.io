Why can a focused button fail to match :focus-visible?

Use Tab and a pointer click on the same button. Compare its active element, selector matches, and visible focus indicator.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-17 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • Check focus and its indication separately
  • Pointer focus on a button can depend on the platform
  • Preserve a visible keyboard focus indicator

The same button has a visible outline after Tab and may have none after a mouse click. A screenshot could make it look as if the click never focused the button. Check the active element, then compare :focus and :focus-visible. One describes where focus is. The other describes whether that focus should be indicated.

The selectors share a subject and use different conditions

Selectors Level 4 uses :focus for an element that has focus. For the ordinary button in this standalone page, compare the document's active element with the target. Gaining focus does not itself activate the button. After reaching it with Tab, the user can choose whether to press it.

The :focus-visible selector is narrower. The element has focus and the user agent determines that focus should be made evident. The specification offers guidance about input modality, user preference, and whether the control supports keyboard input. The selector lets authors add styling under that decision instead of treating every pointer event as a reason to hide focus.

Keyboard navigation commonly produces an indicator on a button. Some pointer operations focus the same button without requiring the same indicator. Check focus first. Some platforms don't focus a button when a user clicks it. A click event or a successful application action cannot establish why the selector didn't match.

That distinction matters when a team changes the style. One failure leaves keyboard users without a visible focus target. Another treats a missing custom outline after a click as a focus failure and moves the user somewhere else. Reading a state helps diagnose it; keeping the user able to continue is the interface test.

Read the same button after Tab and after a click

The local page has two native buttons. The target uses one rule for :focus and another for :focus-visible. It never removes the browser's default indicator. Each observation records the action, whether the target is active, and the two selector matches.

<!doctype html>
<meta charset="utf-8">
<title>Focus comparison</title>
<style>
  #target:focus { border-color: #20506d; }
  #target:focus-visible { outline: 3px solid #20506d; outline-offset: 3px; }
</style>
<button id="start" type="button">Start</button>
<button id="target" type="button">Target</button>
<pre id="result"></pre>
<script>
const byId = document.getElementById.bind(document);
const target = byId('target');
const output = byId('result');
const hasSelector = CSS.supports('selector(:focus-visible)');

function record(action) {
  const active = document.activeElement === target;
  const focused = target.matches(':focus');
  const indicated = hasSelector ? target.matches(':focus-visible') : 'unsupported';
  output.append([action, active, focused, indicated].join(' | ') + '\n');
}

document.addEventListener('keyup', event => {
  if (event.key === 'Tab') record('tab');
});
target.addEventListener('click', () => record('click'));
</script>

Begin the keyboard case on a fresh page. Tab to Start, then to Target, and read the last Tab row. Expect the target to be active and to match :focus. Keyboard navigation is a case for which the specification recommends a visible indication. Look at the outline too. A selector match alone doesn't establish adequate contrast or a distinguishable shape.

Reload for the pointer case and click Target directly. A true focus match together with a false focus-visible match is consistent with the modality decision. Both can also be true, for example if user preferences request a visible indicator. If the active element is elsewhere, record that the click did not focus the target. That is a separate case.

These are observation steps based on the specification and the code. No browser, keyboard run, or assistive technology was exercised for this article. Record the action, active element, selector matches, and actual visibility so an unexpected screenshot has a diagnosable cause.

Test whether a person can keep operating the interface

Keep a usable focus indicator before adding a selector-specific refinement. Border color, outline, and background all affect whether somebody can distinguish the selected target. This fixture separates the selector states. Its palette is not an accessibility result in the application.

Record platform keyboard preferences too. If the target isn't reachable in the expected Tab sequence, establish where the key went and whether another component handled it. A style change can't fix a button that never becomes the active element.

Repeat the visible check in the themes the product supports, including forced colors if applicable. A color that stands out in one theme can blend into another. Confirm which control is active and which indication a person can actually identify.

Repeat the same check on the product button after establishing a baseline in the standalone page. If the fixture shows an outline and the product does not, inspect stylesheet precedence and whether an update moved focus. For example, replacing a button during a render can leave a different element active. Report which element remained before concluding the style failed.

Could a pointer-focused text input match too?

Yes. Replace the button with an editable text input. The keyboard will be used for text entry even when a click gives the field focus. The specification recommends that an already focused control that supports keyboard input match :focus-visible. A pointer action isn't enough to conclude there should be no indicator.

For this case, verify that the input received focus and accepts text, then read the match and the visible result. If the browser treats the button and the text field differently, record the control type. The main example covers a button only.

If focus already exists but author content covers it, see how to check the minimum requirement for unobscured focus.
