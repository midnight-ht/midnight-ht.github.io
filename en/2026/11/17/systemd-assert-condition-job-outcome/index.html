Why does a missing file skip one systemd unit but fail another start?

Check the same path in two systemd units and distinguish a condition skip, an assertion failure, and actual execution.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-17 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • One path can produce two start outcomes.
  • An assertion failure does not itself change the unit state.
  • Record the start result separately from execution evidence.

The same missing readiness file can make systemd skip one service and report a failed start job for another. The unit definition determines whether it checks ConditionPathExists= or AssertPathExists=. They can read the same path and give the caller different start outcomes.

Imagine one machine has no local reporting feature. Its optional reporting service has no work to do there. Another unit explicitly consumes report configuration and should tell its caller when that input is missing. Using the same directive for both hides the distinction between an optional role and an assigned task without a required input. Two definitions with one changed directive make the behavior visible.

Give both units the same input

Use the system manager on a disposable Linux test machine. Save the definitions in /etc/systemd/system/ as zy17-condition.service and zy17-assert.service. The examples assume echo is available at /bin/echo. The probe path is reserved for this fixture. Start with it absent and confirm nothing else uses it.

[Unit]
ConditionPathExists=/run/zy17-lab/ready

[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/bin/echo zy17-ready

[Unit]
AssertPathExists=/run/zy17-lab/ready

[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/bin/echo zy17-ready

The following function records the start command's status independently of the unit's properties. Reload after installing the definitions. Leave the probe absent for the first round and create it for the second. Run these commands with the necessary privileges on the test machine. Start from new, inactive units to avoid probing an already active service.

probe() {
  status=0
  systemctl start "$1" || status=$?
  printf '%s start=%s\n' "$1" "$status"
  systemctl show "$1" -p ActiveState -p ConditionResult -p AssertResult
  journalctl -b -u "$1" --no-pager
}

systemctl daemon-reload
probe zy17-condition.service
probe zy17-assert.service

mkdir -p /run/zy17-lab
touch /run/zy17-lab/ready
for unit in zy17-condition.service zy17-assert.service; do
  probe "$unit"
done

With the file absent, the condition skips the start and the direct start command should return successfully for that skip. The assertion fails the start job, so expect the other command to return nonzero. Neither unit should emit its execution marker. An assertion failure does not itself put the unit into failed state. A clean unit that never started should therefore still be inactive. The second command's nonzero status does not show that echo ran and failed. The job record and service output answer different questions.

With the file present, both paths should pass. The example sets RemainAfterExit=yes, so expect both units to be active after the oneshot commands finish and look for zy17-ready in each unit's log for this round. Restrict the observation by run time or start with a clean machine. A marker from an earlier start cannot confirm the current one. These outcomes are expectations derived from the manual and the fixture. No Linux manager run was performed. Stop the units after the exercise, remove both fixture definitions and the probe, and reload the manager.

Did the start job fail, or is the service failed now?

A single systemctl is-active after both rounds cannot explain the earlier assertion result. Both units may report inactive while the file is absent. Once the file is present, both starts may succeed. The latest state is a new observation rather than a record of the earlier job. Save the time, command result, unit state, and execution marker for each start request. The assertion outcome and whether the service binary ran require separate evidence.

Choose the directive based on the machine's responsibility. If the missing input is expected for an optional role, a condition expresses where to run the service. If this machine must handle an assigned task and a missing input needs investigation, an assertion tells the caller the start job failed. The caller still decides what to do next. Suppose a setup script will write the probe five seconds later. Verify that setup separately and issue another start request. The file's appearance alone does not show that a start occurred. The fixture explicitly starts both units again after creating the probe.

Write the expected matrix before trying this on the actual target system. For a condition, insist on observing a fresh marker when the file exists. Otherwise an executable problem might be mistaken for the path check. For an assertion, preserve the failed job when the file is absent so you can verify that automation and alerting receive it. A copied terminal error without the corresponding input or unit state leaves the next reviewer guessing whether to fix the environment, the unit's role, or a process that actually ran.

Include an instance that is supposed to be skipped when testing monitoring. Polling only for active after each start would put that instance and an assigned task with missing input into the same failure group. Classify the start request from its own receipt, then check for execution. Record the reason for an expected skip and retain an assertion failure for whoever prepares the input. Another independent control could keep the probe present and make the fixture run a command that deliberately fails. Verify the execution result and service state for that case. This additional control was not run. It would check whether the alert distinguishes a start rejected by the unit definition from a process that ran and failed.

How can either of two candidate paths satisfy the check?

Prefix the values with | to make those checks triggering. The systemd manual requires at least one triggering condition to hold, along with every regular condition. For an optional service that can use either a local or a mounted configuration, write the two paths as triggering conditions and keep a regular condition for their common directory. The service should still be skipped if that directory is absent, even when the alternate configuration is found. This adds grouping beyond the single check in the main fixture. Assertions have an analogous form and still affect the start job on failure. These combinations were not run.
