Why can a bound method keep a weakref.finalize target alive?

Compare two executed CPython registrations to see how a callback can retain its own target.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-17 · Estimated read 7 min
Translations
zh-CN en

Article

Key takeaways

  • A bound method can retain its target.
  • Observe target and registration liveness separately.
  • Give deterministic shutdown an explicit owner.

Passing an object’s bound method to weakref.finalize can let the callback keep its own target alive. Deleting the original variable leaves that reference in place. A collection-triggered fallback needs a callback that holds only the resources or values it will actually use.

Imagine a component that registers its own cleanup method. A test deletes the last obvious variable and sees no cleanup event. Before collecting again, follow the reference from the registration to the callback and from the bound method to the component.

Inspect what the callback retains

The standard-library documentation says that the callback and its arguments must not directly or indirectly reference the target. It specifically warns against a bound method of that target. A standalone function would still retain the object if it received the object as an argument. A closure can have the same problem. Python weakref.finalize.

Observe object liveness with a separate weak reference and check the registration’s alive property separately. A live registration does not prove that a resource is open or that its owner is healthy.

Compare two registrations

This complete program ran locally on CPython 3.11.15. One object registers its own bound method. The other registers append on a separate list with a constant. Neither opens a real resource.

import gc
from weakref import finalize, ref

events = []

class Payload:
    def mark(self):
        events.append("held")

held = Payload()
free = Payload()
watch = (ref(held), ref(free))
bad = finalize(held, held.mark)
good = finalize(free, events.append, "free")

del held, free
gc.collect()
assert tuple(ref() is not None for ref in watch) == (True, False)
assert tuple(entry.alive for entry in (bad, good)) == (True, False)
assert events == ["free"]
bad()
bad()
gc.collect()
assert watch[0]() is None
assert not bad.alive and events == ["free", "held"]
print(events)

After deleting the outer variables, the first target and its finalizer were still alive. The second target was gone and its registration had recorded free. Calling the first finalizer twice added held once. The first target was then no longer visible through the weak reference. This is a runtime observation for the fixture, not a scheduling promise across interpreters.

Explicitly invoking a live registration runs its callback and marks it dead. It is a separate operation from waiting for collection. Verify real resource release through its own observable boundary.

Give deterministic cleanup its own owner

A normal close path can call a cleanup function that only receives the file path or other independent data. Verify that those values do not refer back to the object. Test normal close, failed close, and repeated calls separately. The related ExitStack article covers deliberate transfer of existing exit callbacks. This local test does not exercise resources, concurrent closes, or interpreter shutdown.

Does detach cancel the registration without running it?

On a live finalizer, detach marks it dead and returns the object, callback, arguments, and keyword arguments. Keeping that tuple retains the object. A separate test can verify that the callback did not run, then discard the returned tuple before checking liveness. That cancellation probe was not run.
