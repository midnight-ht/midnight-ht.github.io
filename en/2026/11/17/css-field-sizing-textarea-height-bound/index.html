How can a fixed-width textarea grow with its content?

Compare fixed and content on equally wide textareas. Measure how a longer value changes height and inspect any layout constraints.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-17 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • The initial and content-based sizing rules differ
  • Fixed width can still allow growth in height
  • Compare height changes rather than fixed pixels

A note grows from one line to three. The product wants the field to grow downward but stay as wide as the title above it. The old field keeps a fixed number of rows, so the user scrolls inside it to read the rest. Let the content contribute to height while the form column still determines width.

The layout sets width and the content contributes height

The CSS Form Control Styling Level 1 draft defines fixed and content for field-sizing. The initial value, fixed, retains the host language's default preferred size. Typing more lines in a textarea doesn't normally turn that default size into the height of the new text.

The content value instead derives intrinsic size from the contents and ignores the default preferred size. With a fixed width, extra text lines can increase height without widening the field. Other layout constraints still apply. An explicit height can mask the benefit of the intrinsic sizing change.

Trace width and height separately in an existing component. Width may come from the form column, a grid, or a rule on the field. If a shared style sets a fixed height, decide whether that dimension should remain fixed. A requirement to keep the form in one column need not lock the height too.

Text can also wrap at the available width. The example uses distinct, short lines separated by explicit line breaks so word wrapping and fonts are less likely to confound the sizing comparison. Real note content may include soft wraps as well.

Compare the same change in two equally wide fields

The local page has two textareas with the same attributes, font, and width. One uses fixed and the other content. Both start with One. The button replaces both values with three explicit lines. The script reads height after the change without choosing a height for either box.

<!doctype html>
<meta charset="utf-8">
<title>Textarea height comparison</title>
<style>
  textarea {
    display: block;
    inline-size: 16rem;
    min-block-size: 2rem;
    box-sizing: border-box;
    font: 16px/20px monospace;
    resize: none;
  }
  #ordinary { field-sizing: fixed; }
  #growing { field-sizing: content; }
</style>
<label for="ordinary">Ordinary field</label>
<textarea id="ordinary" rows="2">One</textarea>
<label for="growing">Growing field</label>
<textarea id="growing" rows="2">One</textarea>
<button id="more" type="button">Use three lines</button>
<pre id="result"></pre>
<script>
const byId = document.getElementById.bind(document);
const fields = ['ordinary', 'growing'].map(byId);
const output = byId('result');

function record() {
  const heights = fields.map(field => field.getBoundingClientRect().height);
  output.append(heights.join(' | ') + '\n');
}
output.append('supported: ' + CSS.supports('field-sizing', 'content') + '\n');
record();
byId('more').onclick = () => {
  for (const field of fields) field.value = 'One\nTwo\nThree';
  record();
};
</script>

Read the support line first. If it is false, equal measurements might indicate the new declaration was ignored. In a supporting environment, compare each field with itself: the ordinary field is expected to keep its outer height, and the growing field should be taller than before. Their initial heights don't need to match. The two sizing paths can begin at different heights.

These are predictions from the draft and the fixture, not browser measurements or a cross-engine support claim. Padding, borders, and fonts can differ by environment, so the example uses changes rather than a fixed pixel count. When testing the actual UI, also verify that both widths remain the same and all three lines can be read.

Find what actually constrains the height

If support is present but the adaptive field remains the same height, inspect applied styles. A shared form style can set a fixed block size even when the new declaration is valid. Remove that competing constraint in an isolated example and compare the same two values again.

Check content growth separately from box growth. Three lines might be present and increase the scrollable height while the layout box stays put. A test that reads only the field value would pass and never establish whether the surrounding layout moved.

Record the initial text, the edited text, both heights, and the containing width. Test the initial render with a longer saved note if that is a product entry point. A screenshot of a single value cannot identify which sizing constraint caused the result.

Give unsupported environments a usable ordinary field. The user still needs access to the latter part of a long note even if the box doesn't grow. A support check alone doesn't establish that the resulting interaction is usable.

Run the growth check in reverse too. Remove two of the three lines and see whether the field returns to its initial height while keeping the insertion point. A legacy resize routine may increase height without ever decreasing it. The same one-line text before and after the edit gives the test a useful endpoint. The minimum height can still keep the field from shrinking further.

Does a maximum block size stop the form from growing indefinitely?

Yes. Add max-block-size to the growing field and allow scrolling for overflow. Enter enough lines for the box to reach the bound, then add more. Expect the box to stop growing at the constraint while the remaining lines can still be read by scrolling the field. The main fixture has no maximum.

Check the box and access to the remaining content separately. A test that only expects the panel to stop moving can miss text that is clipped and unreachable. If the product also permits dragging a resize handle, test that interaction separately. The fixture disables manual resizing to hold the other conditions fixed.

For a separate property of script-assigned values, see why programmatic changes don't fire the input event.
