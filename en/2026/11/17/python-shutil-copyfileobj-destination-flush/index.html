Why can a reader still see an empty file after copyfileobj returns?

Compare two executed reads around a buffered Python file-copy handoff.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-17 · Estimated read 7 min
Translations
zh-CN en

Article

Key takeaways

  • Copy completion does not guarantee flushing.
  • Flush or close before handing the output to the reader.
  • Check visibility separately from durability.

A second reader can still see an empty file after Python’s copyfileobj returns. The helper writes into the destination object without guaranteeing that its buffer has been flushed. Flush or close the writer before the handoff, then verify what the reader actually sees.

Suppose a service copies a small export into a temporary file and passes its path to a preview component. The copy reports no error, but the preview finds no content. Before rerunning the copy, identify the writer, the reader, and the event that was supposed to make the handoff safe.

Separate copying from reader visibility

The standard library documents that copyfileobj does not guarantee a destination flush. To read the destination afterward, ensure that its owner flushes or closes it first. Python shutil.copyfileobj.

When the caller supplies a writable object, it may still need to write a footer. The owner can flush without closing in that case. A completed file can be closed before the owner hands its path to a consumer. Test the actual handoff rather than merely observing a successful copy call.

Use a new reader at each observation

The following program ran locally on Python 3.11.15. It copies three bytes to a buffered binary destination. It opens a separate reader before and after flushing, while keeping the writer open throughout.

from io import BytesIO
from pathlib import Path
from shutil import copyfileobj
from tempfile import TemporaryDirectory

with TemporaryDirectory() as directory:
    target = Path(directory) / "demo.bin"
    with target.open("wb", buffering=8192) as writer:
        copyfileobj(BytesIO(b"abc"), writer)
        before = target.read_bytes()
        writer.flush()
        after = target.read_bytes()
        assert (before, after) == (b"", b"abc")
        print(before, after)

The first read returned empty bytes and the second returned abc. Both conditions were asserted. The empty result depends on the fixture’s buffering and input size. The documented contract does not require all destinations to remain empty before a flush. Verify the bytes under the buffering policy your application actually uses.

A writer’s position can move without proving that another object can read those bytes. Record the intended path, the bytes observed, and the order of the observations. The local test does not check access permissions or a separate process.

Verify the intended delivery boundary

If readers can only see complete outputs, make visibility a separate policy. A successful flush of an early chunk cannot provide that guarantee. Test one failed export and one complete export at the real consumer boundary. A deliberately empty source can provide another control: after a flush it should still produce empty output. Those application probes were not run. The related spooled temporary file article covers a different transition triggered by a descriptor.

Reading the bytes on the same system is a visibility check. It does not exercise recovery after a crash, durable storage, or a remote reader’s view.

What if some of the source has already been consumed?

The helper copies from the current source position. An independent probe can read the first byte of abc before copying, flush the new destination, and expect bc there. If the caller requires the entire stream, agree on who can rewind a seekable source or supply an untouched one. This follow-up was not run.
