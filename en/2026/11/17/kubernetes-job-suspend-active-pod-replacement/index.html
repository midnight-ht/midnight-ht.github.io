Do running Pods wait in place when a Kubernetes Job is suspended?

Compare Job and Pod UIDs across Kubernetes suspension and resumption, and verify application progress separately.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-17 · Estimated read 16 min
Translations
zh-CN en

Article

Key takeaways

  • Suspension terminates active Pods.
  • Compare Job and Pod identities across the transition.
  • Read persisted application progress independently.

Suspending a running Kubernetes Job causes its controller to terminate active Pods. On resume, the same Job can create Pods again, but an old Pod will not pick up at its previous execution point. Record the identities of the Job and its Pod, then see which identities survive resumption.

That affects a real maintenance decision. A team may want a shard processor to give up resources temporarily and finish writing the same batch later. If the process keeps its progress only in memory, resuming the Job cannot recover that position. The Job manages execution attempts and outstanding work. The application knows which business data it has already processed. Start by checking the first part with a Job that writes no business data.

Identify the running Pod

Use a disposable test cluster with the necessary permissions and access to BusyBox. Set LAB_CTX to that cluster's explicit context and put the two shell blocks in one script in order. This Job starts one long-running wait, with no external storage or other work consumers. Five minutes gives the operator time to verify that the first Pod is running before requesting suspension.

apiVersion: batch/v1
kind: Job
metadata:
  name: pause-demo
spec:
  parallelism: 1
  completions: 1
  template:
    spec:
      restartPolicy: Never
      terminationGracePeriodSeconds: 5
      containers:
        - name: timer
          image: busybox:1.36
          command: ["sleep", "300"]

Save this as pause-demo.yaml. This is the first half of the script. After the first Pod exists and is ready, save both UIDs. Keep the old Pod's name for observing deletion, so a listing after resume cannot be mistaken for the state of the old Pod. The single-item lookup assumes a fresh namespace and the one Job in this fixture.

set -eu
: "${LAB_CTX:?set LAB_CTX to the disposable cluster context}"
ns=zy17-job-suspend
lab() { kubectl --context "$LAB_CTX" -n "$ns" "$@"; }
kubectl --context "$LAB_CTX" create namespace "$ns"
lab apply -f pause-demo.yaml

selector=batch.kubernetes.io/job-name=pause-demo
lab wait --for=create pod -l "$selector" --timeout=90s
old=$(lab get pod -l "$selector" -o jsonpath='{.items[0].metadata.name}')
lab wait --for=condition=Ready "pod/$old" --timeout=90s
job_uid=$(lab get job pause-demo -o jsonpath='{.metadata.uid}')
old_uid=$(lab get "pod/$old" -o jsonpath='{.metadata.uid}')
printf 'before job=%s pod=%s\n' "$job_uid" "$old_uid"

Request suspension. Wait for the Job's Suspended condition, verify removal of the old Pod, and list the Job's Pods again. The object might have disappeared before the deletion wait starts, so look for it first. Save the empty listing while suspended before resuming.

lab patch job pause-demo --type=merge -p '{"spec":{"suspend":true}}'
lab wait --for=condition=Suspended job/pause-demo --timeout=90s
remaining=$(lab get "pod/$old" --ignore-not-found -o name)
if test -n "$remaining"; then
  lab wait --for=delete "pod/$old" --timeout=90s
fi
suspended=$(lab get pod -l "$selector" -o name)
test -z "$suspended"
printf 'Pods during suspension: [%s]\n' "$suspended"

lab patch job pause-demo --type=merge -p '{"spec":{"suspend":false}}'
lab wait --for=create pod -l "$selector" --timeout=90s
current_job=$(lab get job pause-demo -o jsonpath='{.metadata.uid}')
new_uid=$(lab get pod -l "$selector" -o jsonpath='{.items[0].metadata.uid}')
printf 'after job=%s pod=%s\n' "$current_job" "$new_uid"
test -n "$new_uid"
test "$current_job" = "$job_uid" && test "$new_uid" != "$old_uid"

Expect the same Job UID before and after, a different Pod UID, and no replacement Pod during suspension. If image pulling fails or the old Pod completes before the suspension request, record what happened and restart the fixture. Successful patch submission confirms the API accepted the write. Controller reconciliation and Pod termination take their own time. The timeout expresses how long the client will wait. Check the condition and object lifecycle before comparing the resumed identity. No cluster was contacted and these commands were not run. The results are expectations derived from the official documentation. Delete the fixture namespace afterward, using the same disposable context.

Preserve separate evidence for application progress

A long-running wait demonstrates replacement. Consider a task that writes documents. The old Pod writes the first document and gets suspended while working on the second. A new Pod demonstrates another opportunity to run. It cannot show whether the first write committed or whether a consumer read the second document. Even if the old process gets a chance to handle a termination signal, claiming that it safely saved its progress requires separate evidence. No signal-handling or write workflow was exercised.

If the goal is to release background capacity and retry work in replacement Pods, include the suspended interval and the UID comparison in an operations exercise. To resume a particular shard, design progress the application can reload and a way to verify retries. Record the shard key and read its durable progress directly from application storage. For instance, give two inputs distinct IDs. Before pausing, leave one finished result and one uncommitted result. After resumption, check whether the application finished the second input or published the first a second time. That is a separate test of resumed business behavior. The timer-only control cannot answer that release question.

Keep three observation points in an on-call handoff. Before requesting suspension, capture the original Pod readiness and ownership. After waiting, record the Job reporting suspension and the absence of a replacement at that moment. After resuming, save the first observation and identity of the new Pod. A final Pod listing cannot prove there was an empty interval, and an old Pod stopping cannot alone prove suspension took effect. A second operator could resume the Job before the first operator confirms that interval. Using one operator and a fresh namespace helps to avoid that race.

If multiple people maintain the workload, check whether another process recreated its Job. One operator may report a resume by name while the next finds a different Job UID with the same name. Record a recreation in that case. Establish continuity of the Job first, then interpret the Pod UIDs as attempts. If that assertion fails, save the controller ownership and UIDs from both observations before recording the outcome. If the application only needs to relinquish resources, confirming that active attempts have stopped may complete the handoff. Data recovery or resumed writes need an owner and separate evidence of completion.

Do active Pods terminated by suspension count toward completions?

No. The Job controller does not count Pods stopped for suspension toward required completions. The official Job documentation distinguishes them explicitly. With one completion required here, suspending the only still-running Pod does not meet that count. A replacement still has to produce an actual execution outcome. Resuming the Job is not evidence of completion. This question adds the completion-accounting condition to a fixture that observes identity and replacement.
