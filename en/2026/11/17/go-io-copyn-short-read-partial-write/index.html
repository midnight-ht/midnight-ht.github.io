Why did Go CopyN write bytes even though it failed?

Compare a complete Go transfer with a short source and verify what would remain in the destination.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-17 · Estimated read 7 min
Translations
zh-CN en

Article

Key takeaways

  • A failed fixed-length copy can leave a prefix.
  • Check count, error, and destination independently.
  • Define when complete output becomes visible.

Go’s io.CopyN can fail after writing a prefix. If a transfer requests three bytes from a source that provides two, the error does not retract the two bytes already written. Check the count, error, and destination before handing anything to a consumer.

Imagine an exporter that writes a header and copies a fixed-length body after it. The source ends early. The caller sees an error and retries into the same destination, assuming the header is still the only content. A previous prefix can remain and mix with the retry.

Separate the requested length from progress

The Go reference says CopyN copies the requested number of bytes or stops at an error. It returns exactly that number if and only if the error is nil. An arbitrary Writer has no built-in rollback contract. Go io.CopyN.

Keep the requested length independent of what the source happened to supply. Recalculating the expectation from the observed short input would let the failure pass.

Give a complete and short source independent targets

This complete teaching program was not executed. Each branch creates an in-memory destination with head: and requests three bytes. The first source is abc and the second is ab.

package main

import (
    "bytes"
    "fmt"
    "io"
    "strings"
)

func main() {
    cases := []struct {
        input string
        count int64
        failed bool
    }{{"abc", 3, false}, {"ab", 2, true}}

    for _, example := range cases {
        target := bytes.NewBufferString("head:")
        n, err := io.CopyN(target, strings.NewReader(example.input), 3)
        if n != example.count || (err != nil) != example.failed ||
            target.String() != "head:"+example.input {
            panic(fmt.Sprintf("unexpected transfer: %d %v %q", n, err, target))
        }
        fmt.Printf("%q: written=%d failed=%t target=%q\n",
            example.input, n, err != nil, target)
    }
}

Expect three written bytes, no error, and head:abc for the first source. Expect two written bytes, an error, and head:ab for the second. The fixture does not require a particular error identity from arbitrary readers. An error-only test would overlook the prefix. A contents-only test might mistake the prefix for the whole output.

Decide when to expose the result

If readers need only complete bodies, stage the bytes until the count and result pass. A streaming API can instead make partial output visible with its own terminal state. The related Go row iteration article covers a different terminal condition. Here the destination can already have changed.

Test retry behavior separately. Fail with two bytes, then succeed into a fresh stage and verify that exactly one complete body is exposed. A separate writer failure can reveal a different partial-write path. These application checks were not run. Neither the fixture nor the proposed checks verify durability.

What if the source contains more than three bytes?

Try a fresh strings.Reader containing abcdef. After requesting three bytes, expect abc in the destination and def when reading the remainder from that reader. This unexecuted follow-up checks the particular reader and record boundary separately from the short-source failure.
