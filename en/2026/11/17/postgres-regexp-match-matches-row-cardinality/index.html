Why can switching PostgreSQL regex functions remove unmatched rows?

Compare scalar captures with per-match rows and check source identity in PostgreSQL.

Updated 2026-11-17 · Estimated read 7 min

Article

Key takeaways

  • A scalar miss returns SQL NULL.
  • A set-returning miss yields zero rows.
  • Check detail rows against the original source IDs.

PostgreSQL’s regexp_match returns SQL NULL when there is no match. Its set-returning regexp_matches can return zero rows. A replacement can therefore remove an unmatched source from a report. Decide whether the output should preserve source rows or produce one detail per match.

Imagine extracting numeric references from notes. The old report shows each note and leaves the reference blank on a miss. The new version needs every reference, but it drops notes without any. A test that checks only successful matches would miss that change.

Distinguish a null field from zero detail rows

The PostgreSQL 18 reference describes a scalar array for the first match and a set of arrays from regexp_matches. The g flag requests all matches. These expressions use one numeric capture, so each matching array has one string. The number of capture fields is separate from the number of result rows. PostgreSQL matching functions.

A nullable scalar keeps its source row. Cross joining each source to its matches yields no detail rows for an empty result. The underlying note has not disappeared from the relation.

Compare the two result shapes

This teaching SQL is unexecuted. It creates two notes in a disposable session. The first has 12 and 34. The second has no digits.

CREATE TEMP TABLE extract_demo (id int, note text);
INSERT INTO extract_demo VALUES (1, 'A12 B34'), (2, 'none');

SELECT id, regexp_match(note, '([0-9]+)') AS captures
FROM extract_demo ORDER BY id;

SELECT id, captures
FROM extract_demo
CROSS JOIN LATERAL regexp_matches(note, '([0-9]+)', 'g') AS m(captures)
ORDER BY id, captures;

The scalar query should return ID 1 with an array containing 12 and ID 2 with SQL NULL. The detail query should return two rows for ID 1, with 12 and 34. Both queries should return two rows in total. Check source identity and counts per ID to detect the lost source. A query that accidentally applies shared text to both notes can also produce correct-looking totals and wrong attribution.

Choose what a row means to the consumer

A source-oriented report can keep the first match in a nullable field. A detail report can expand all matches and retain the source ID. If two notes match the same value, keep their separate identities when the consumer needs attribution. A report that derives source counts from detail output would otherwise double-count sources with multiple matches and omit nonmatching sources. The related LATERAL article explores a different per-source query. These consumer checks were not run.

Also verify existing workflows that depend on an empty field. The unmatched note might need to enter a manual queue. Dropping its row can bypass that step.

Can we keep every match and still keep an unmatched source?

Change the detail query to LEFT JOIN LATERAL with ON true. Expect two matched rows for ID 1 and an additional null-extended row for ID 2. Verify any later filter separately so it does not remove the preserved row again. This variant was not run.
