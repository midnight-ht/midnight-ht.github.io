Why can two A votes choose different answers?

Map A and B votes back to candidate IDs after swapping presentation order. Distinguish stable preferences, explicit ties, and inconsistent results.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-17 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • Presentation labels are not candidate IDs
  • A stable win requires agreement on the same candidate
  • Distinguish explicit ties from conflicting valid votes

A model compares two support replies. It selects A in the first run. You swap the answers and it selects A again. The report counts two votes for the same reply, even though A was draft X first and draft Y second. Map the display labels back to candidate identities before treating the votes as agreement.

Give the draft an identity independent of its position

Keep drafts X and Y unchanged, along with the question they answer. In the first order, X is A and Y is B. In the second, Y is A and X is B. These are labels for the current comparison, not durable identities for the drafts.

Two A votes then select two different drafts. The swap didn't produce a consistent preference. An A followed by a B, by contrast, can select X both times. Read each label through the mapping for its own run.

Zheng and colleagues report an example in Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena where switching answer order changed the judge's preference. Their position-bias experiment has specific models, prompts, and questions. It motivates checking order, without giving results for every current model or for this article's inputs.

The authors describe a conservative policy: ask twice with swapped order and declare a winner only when both prefer the same response. Their treatment can count inconsistent results as ties. This article keeps the original records more granular. Two explicit tie votes and two inconsistent preferences both leave no stable winner, but they are different reasons to review a case.

Decode the votes before making a decision

This local Node example contains three invented sets of votes. Every case uses the same X, Y order and its reverse. The decision function expects previously validated values of A, B, or Tie. The script calls no model and contains no actual reviewer annotations.

import {deepEqual} from 'node:assert/strict';

const first = ['draft-X', 'draft-Y'];
const swapped = ['draft-Y', 'draft-X'];

function candidate(order, vote) {
  if (vote === 'Tie') return null;
  if (vote === 'A') return order[0];
  return order[1];
}

function decide(earlier, later) {
  const a = candidate(first, earlier);
  const b = candidate(swapped, later);
  if (a !== b) return ['unresolved', a, b];
  if (a === null) return ['tie'];
  return ['winner', a];
}

const cases = [
  [['A', 'A'], ['unresolved', 'draft-X', 'draft-Y']],
  [['A', 'B'], ['winner', 'draft-X']],
  [['Tie', 'Tie'], ['tie']],
];
for (const [[earlier, later], expected] of cases) {
  deepEqual(decide(earlier, later), expected);
}
console.log('Position labels mapped to the expected case outcomes.');

All three assertions passed locally. A followed by A stays unresolved and retains the selected X and Y. A followed by B maps to X twice and can declare X the winner under this rule. Two explicit Tie votes give a tie. Set the rule and its possible states before looking at actual evaluation data.

Keep the context for both raw outputs. A record can include the question ID, candidate IDs and positions, judge model and prompt version, raw responses, parsed labels, and mapped identities. A summary that keeps only A and B cannot show which response was selected or help investigate a changed prompt later.

Test whether the preference survives the swap

Hold the evaluation rubric and both answers fixed. Don't fix a typo in Y during the second run and attribute a changed vote to order. Record sampling variation too. One conflicting pair shows that the choices differ under the tested conditions. It does not isolate the cause or estimate bias across the evaluation set.

Track a stable winner, an explicit tie in both runs, and conflicting valid votes separately. Keep the set of attempted questions as a denominator and document which cases didn't finish both directions. A comparison after changing the model or prompt should use matching task conditions rather than combining unrelated categories into one number.

Even when both directions favor X, the result only says that exchanging positions didn't change the choice in this test. It does not show that X meets the support policy or what a real user would prefer. For a formal quality decision, use separate reference checks or review by a person. This fixture did not perform either.

In one experiment, the paper generated similar answers to the same questions and compared orders under fixed prompts. Its report distinguishes consistency from favoring the first or second position. Preserve that paired evidence by task category in your own test. Results on open writing questions need not describe questions with a reference answer, and the paper’s sample count does not set your acceptance threshold.

Consider retaining two report views. One groups records by display position so the team can inspect where votes are concentrated. The other groups them by candidate identity so it can identify stable wins. Keeping only the second view can hide a positional pattern. Keeping only the first repeats the label-mapping mistake. Derive both from the same underlying receipts.

What if one output cannot be parsed?

Under the two-direction rule, the valid vote alone cannot declare a winner. Suppose the first run clearly selected X. After swapping, the model returned “Maybe the second one, but I'd need to check,” without a valid label under the output contract. Only one run can contribute to the comparison. Calling the other a tie hides missing information. Calling X a stable winner treats one run as two.

Keep the case incomplete and store the raw output and parsing reason. A predeclared policy might repeat the same direction or route the case for manual review. In the summary, keep incomplete comparisons separate from explicit ties. The example accepts valid labels only and neither retries nor parses model prose.

For how a project can act when its evidence is incomplete, see the criteria for continuing or stopping discovery.
