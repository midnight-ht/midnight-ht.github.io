After HTTP 413, should the client shrink the file or wait?

The same file can exceed a standing or a temporary size limit. Use a local comparison to decide when to change the content or check the wait condition.

Article

Key takeaways

  • 413 concerns the size of request content
  • Change the input when a documented limit remains in effect
  • A wait hint does not guarantee recovery

An upload of ten units receives HTTP 413. Someone suggests removing a few pages, and someone else suggests waiting ninety seconds. Both can be useful under different conditions. Waiting won't change the size of a file that exceeds a documented limit. If a route temporarily reduced the size it can accept, editing the file may be unnecessary.

Find out which limit rejected the content

RFC 9110 uses 413 when a server is unwilling or unable to process request content of that size. The status identifies this request's outcome. It doesn't give a numeric limit or establish whether the limit will change. Check the endpoint contract, response fields, and the component that made the decision.

Suppose a document route has a documented limit of eight units. An upload of ten fails. Selecting or generating a version of eight can satisfy this limit. Waiting doesn't fix the original ten while the limit stays at eight. The interface can tell the user how to correct the file instead of offering an unexplained retry.

Another route normally accepts twelve and temporarily accepts only six. The same file receives 413. When the condition is temporary, RFC 9110 says the server should provide Retry-After to indicate when a client may try again. The ninety seconds in this example are invented. A wait is not a guarantee that the file will be accepted afterward.

The absence of Retry-After doesn't establish that the limit is permanent. If the response has no wait information, explain that the current content exceeded the receiving conditions and use the documented limit if you have it. Avoid inventing a global limit from a single failure.

Control the size and policy in separate comparisons

This local fixture has four inputs and three configurations. It uses integer units and does not read a file, start a server, wait ninety seconds, or upload anything. Its 200 is an acceptance decision in the local model, without a save operation.

import {deepEqual} from 'node:assert/strict';

const fixed = {limit: 8};
const temporary = {limit: 6, retryAfter: 90};
const normal = {limit: 12};

function checkUpload(size, {limit, retryAfter}) {
  if (size <= limit) return {status: 200};
  const status = 413;
  return retryAfter === undefined ? {status} : {status, retryAfter};
}

const cases = [
  [10, fixed, {status: 413}],
  [8, fixed, {status: 200}],
  [10, temporary, {status: 413, retryAfter: 90}],
  [10, normal, {status: 200}],
];
for (const [size, policy, expected] of cases) {
  deepEqual(checkUpload(size, policy), expected);
}
console.log('Fixed, reduced, temporary, and restored cases passed.');

All four assertions passed in Node. Ten exceeds eight, while eight passes the same size check. Ten exceeds the temporary six and returns a wait of ninety seconds. The final case changes the policy to twelve and accepts ten. That outcome depends on the restored configuration being present. It does not follow automatically from the previous response.

Keep the policy fixed while reducing the file in the first comparison. Keep the file fixed while changing policy in the second. If both change at once, a passing retry cannot tell you whether the file was smaller or the receiving capacity recovered.

Give the uploader a next step that fits the evidence

For a known standing limit, tell the user how to choose or export a smaller file. Preserve unrelated form values so they can correct the item that failed. A 413 alone doesn't justify clearing the entire form.

For a known temporary condition, show that the upload hasn't completed and that another check may be appropriate later. Follow the product's request lifecycle and access to the original file. The wait field does not establish that a stream remains replayable or that resubmission is safe. Any automated retry still needs the application's own contract for repeated operations.

Record which layer emitted the status and the restriction it applied. A gateway could reject content while the application has a different documented limit. Don't tell users the file reached the save service unless you have evidence that it did.

Also check what the real endpoint measures. Its contract might set a limit at a specific stage rather than equating incoming and decoded size. The fixture's numbers only demonstrate recovery choices. Verify that the actual comparison uses equivalent input at the same measurement boundary.

Tie the wait hint to the file that was rejected. If the user chooses a smaller file, evaluate that new content instead of carrying over the previous decision. If they leave and return, check whether the original file and permission are still available. The receipt explains the earlier failure and does not establish the new input’s outcome.

Can the server stop the request before the body finishes?

Yes. This changes the timing: the client may not have received a complete response. RFC 9110 permits terminating the request if the protocol version allows it and otherwise permits closing the connection. The upload may stop during transmission. The disconnect alone doesn't identify a 413 because other failures can also end a connection.

If no status or response fields arrived, record the observed transfer failure. Don't infer a size limit or assume another upload is harmless. If the client did receive a 413, apply the actual response and endpoint contract to decide what it can do next.

For using an interim response before sending a body, see the timing of HTTP 100 Continue for uploads.
