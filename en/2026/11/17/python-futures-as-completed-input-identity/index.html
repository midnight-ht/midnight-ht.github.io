Why can’t you zip as_completed results back to the original inputs?

Use a gated thread-pool run to distinguish completion order from input identity.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-17 · Estimated read 7 min
Translations

Article

Key takeaways

  • Completion order need not match input position.
  • Keep identity at submission time.
  • Verify attribution and presentation order independently.

Python’s as_completed yields futures as they reach completion. Its results cannot be paired position by position with the original input. Save the input identity with each future when submitting the work.

Suppose an inventory report queries stores A and B. B responds first. Zipping the two results against the original store list can put B’s inventory under A. Both requests can succeed and the report can still assign both values incorrectly.

Keep identity out of the ordering rule

The standard library yields completed or cancelled futures. Futures already finished before the call are yielded first, and repeated instances are yielded once. The input sequence does not assign positions to these outputs. Python concurrent.futures.

A progress display can update as work finishes, while a final report uses input order. Both can associate results with the same stable task IDs. Use a composite identity if one store can have several distinct jobs.

Gate the first job without sleeping

This program ran locally on Python 3.11.15. It uses two workers. The first submitted task waits on an event and the second can complete immediately. The main thread observes the first completion before releasing the event. The finally block releases it even if the first observation fails.

from concurrent.futures import ThreadPoolExecutor, as_completed
from threading import Event

release = Event()

def slow():
    release.wait()
    return "slow-value"

with ThreadPoolExecutor(max_workers=2) as pool:
    source = {pool.submit(slow): "A", pool.submit(lambda: "fast-value"): "B"}
    observed = {}
    try:
        finished = as_completed(source)
        first = next(finished)
        assert source[first] == "B"
        observed[source[first]] = first.result()
    finally:
        release.set()
    for future in finished:
        observed[source[future]] = future.result()

assert list(observed) == ["B", "A"]
assert [observed[key] for key in ("A", "B")] == ["slow-value", "fast-value"]
print(list(observed.items()))

The run observed B with fast-value, then A with slow-value. Reading the saved results in input order gives slow-value and fast-value. The fixture checks the IDs as well as order and values. This ordering comes from the explicit gate, not from a promise about real task timings.

Checking that both values are present would accept a swapped result. An application regression can check the pair of store and value before display. The tested worker-pool size matters, since one worker would leave the second task unable to begin while the first waits.

Give each task a distinct outcome

A completed future can still represent a failure or cancellation. Keep its task ID and apply the interface’s policy before marking it successful. A partial report can preserve the failed store’s slot while showing the other result. This application path was not run. The related Promise.all cancellation article covers a separate question about what other work continues after failure.

Use stable IDs for both a progress display and a final ordering step. A visible label can appear in more than one batch and cannot stand in for identity.

What if the same Future appears twice?

The iterator yields a repeated future once. If two report slots share one real job, retain a mapping from that future to both slots. Check one iterator output and two correctly attributed application slots in separate assertions. That variation was not executed.
