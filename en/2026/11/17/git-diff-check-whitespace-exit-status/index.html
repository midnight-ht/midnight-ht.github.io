Why can Git diff --check pass with uncommitted changes?

Compare three states in a small Git repository to distinguish patch policy from the presence of differences in a release check.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-17 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • A valid edit can pass the check.
  • Record distinct outcomes for one comparison range.
  • Check staged and unstaged edits with the intended endpoints.

A changed setting can pass git diff --check. That check looks for newly introduced whitespace errors and conflict markers in the comparison. To find out whether there are any differences at all, ask Git separately and use the same comparison range both times.

A release script can lose one of those questions. It runs a command with “diff” in the name and records a green exit as a clean working tree. Change a setting while keeping its formatting valid and the check still passes. The input has changed, but the record says otherwise. Three states of one tracked file show exactly what that record missed.

Fix both sides of the comparison

Start with a disposable repository that has a commit containing a single-line settings file. Modify only that tracked working-tree file and leave the two edits unstaged. Both commands below compare the working tree with the index by default. The first applies the whitespace rules and checks for conflict markers. The second quietly returns one when differences exist and zero when they do not. The Git manual says --check and --exit-code are incompatible, so the fixture saves both outcomes from separate invocations. It also fixes the whitespace settings locally so that the person running it gets a known policy.

set -eu
work=$(mktemp -d)
trap 'rm -r "$work"' EXIT
cd "$work"
git init -q
git config user.name Fixture
git config user.email fixture@example.invalid
git config commit.gpgsign false
git config core.whitespace blank-at-eol,space-before-tab,blank-at-eof
printf 'value=base\n' > settings
git add settings
git commit -qm base

probe() {
  check=0
  changed=0
  git diff --check || check=$?
  git diff --quiet --exit-code || changed=$?
  printf 'check=%s diff=%s\n' "$check" "$changed"
  test "$check" -eq "$1"
  test "$changed" -eq "$2"
}
git --version
probe 0 0
printf 'value=next\n' > settings
probe 0 1
printf 'value=next \n' > settings
probe 2 1

On Apple Git 2.50.1 this fixture returned 0/0, 0/1, and 2/1. The third check also named the file and line. The value two is an observed result the fixture asserts. A gate used across versions should rely on the documented nonzero status when the check finds a problem. Capturing the statuses first keeps an expected nonzero result available as evidence. The fixture's independent tests then decide whether the results agreed with the prediction.

Use the second step to check an existing gate. The content has changed from base to next, which anyone reading the file can confirm. The line has no extra whitespace, so the policy check passes. The third step adds one trailing space. Differences still exist, while the policy result changes. A record that says only “changes found” collapses the last two cases. A record that says only “check passed” collapses the first two. Save both outcomes so the person responding can tell whether to inspect the content or remove an error introduced by the patch.

Name the comparison your gate performs

The fixture observes unstaged changes to a tracked file. For the pending commit, use git diff --cached ... in both invocations. This compares the index with a specified commit, HEAD by default. A tree with staged and unstaged edits can warrant checks of both comparisons. Label them independently in a report. If the edit in the second step is staged, the default comparison becomes quiet while the index comparison still shows base changing to next. This is a consequence of changing the comparison range, and the three-state run did not perform that staging step.

Fix the endpoints when comparing releases too. A task that has the commit used for the last build and the current input commit can use that pair for both checks. Preserve the endpoints alongside exit values and commands. Someone using the default working-tree command may get a correct answer to a different question. Untracked files also fall outside the two default diff commands above. If your delivery contract covers newly generated local files, decide which paths count and check their status separately. A statement about the difference between two build inputs and a statement about untracked files on the current machine need their own evidence.

Some pipelines allow ordinary product changes and block a patch only for whitespace errors or leftover conflict markers. Use the policy check for that gate and report the presence of differences separately. A build that requires a clean working tree can gate on the relevant comparison. Preserve diagnostics from command errors as well. A failed object lookup should not be classified as an ordinary difference. For an ambiguous red build, start with both statuses and the diagnostic output for the same input, then decide whether to repair the patch, verify the endpoints, or fix the Git invocation.

A common mismatch occurs when the build packages staged content. One task checks unstaged differences and another builds from the index. Attaching the first task’s green result to the second task’s artifact says nothing about the patch that went into that artifact. Have the build record its base commit and input source, then retain the arguments and outcomes of both checks beside them. If the comparison ranges disagree, repeat the checks for the same input. To test whether the report can show the mismatch, stage the second change and save both pairs. A zero in the default comparison and a one for the index difference expose the reporting error. Read the actual artifact separately to see which line was packaged. This is a suggested follow-up check.

Can different whitespace settings change the check outcome?

Yes. If the patch introduces only the trailing space from the third step, git -c core.whitespace=-blank-at-eol diff --check turns off that whitespace rule for the invocation. It leaves the file unchanged and still checks for conflict markers. This explains how a setting affects the comparison and was outside the three observed runs. If two machines disagree about the same patch, compare their effective rules before deciding whether to state the team's policy in the gate invocation. Save both the policy and the endpoints to make the check reproducible.
