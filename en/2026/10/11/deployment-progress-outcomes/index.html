A completed Deployment rollout still needs user-path acceptance

A completed Deployment rollout proves controller-observed conditions, not user success. Separate revision identity, Pod readiness, business-path acceptance, and rollback signals.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-26 · Estimated read 19 min
Translations
zh-CN en

Article

Key takeaways

  • Deployment completion describes the controller-observed rollout, not business acceptance of user requests.
  • Readiness controls whether a Pod can receive Service traffic; a probe is not a complete business acceptance test.
  • kubectl rollout status follows the latest revision by default; bind observations to a revision during concurrent releases.
  • progressDeadlineSeconds reports stalled progress but does not roll back automatically; rollback depends on retained history, data compatibility, and side effects.

A completed Deployment rollout shows that the controller observed the requested revision meet its update conditions. It does not, by itself, prove that user requests work, and it does not decide whether a team should roll back. To accept a release, record the target version, controller progress, Pod eligibility for traffic, and a key business-path result separately, and make sure every piece of evidence refers to the same revision.

Who defines “complete”?

The Deployment controller advances a ReplicaSet toward the desired replica count. During a rolling update, new Pods join while old Pods leave. Conditions and replica counts describe that orchestration process. The Kubernetes Deployment documentation lists common reasons progress can stall: insufficient quota, image pull errors, inadequate permissions, runtime misconfiguration, and failing readiness probes. These causes can all prevent the desired state, but they call for different fixes.

“Available” also has a specific meaning. The current Deployment API reference defines minReadySeconds as the minimum time a new Pod must remain Ready without a container crash before it counts as available. Rollout status, available replicas, and user requests answer different questions. Seeing availableReplicas reach the desired value does not show that the new version has passed business checks for payments, sign-in, search, or data access.

progressDeadlineSeconds is the time limit after which the controller reports that a Deployment has stalled. The current upstream guide gives a default of 600 seconds; when the deadline is exceeded, the Deployment status gains Progressing=False with reason ProgressDeadlineExceeded. The documentation says the controller reports that condition but takes no rollback action on its own. A higher-level orchestrator can react to the signal. Progress is not estimated against the deadline while a Deployment is paused. A deadline that is too short can label a slow but healthy startup as stalled; one that is too long delays detection. Neither value supplies a response policy.

Why does Pod readiness not equal business acceptance?

A readiness probe controls whether a Pod is eligible to receive traffic through a Kubernetes Service. When the probe fails, the Pod becomes unready and Services do not send it ordinary traffic. That is a routing-eligibility check, not a complete acceptance report. The probe documentation also distinguishes readiness from liveness: readiness affects traffic, while a failing liveness probe may restart a container. Putting every dependency into readiness can remove all Pods from service during a transient external outage. Checking only a TCP port or shallow /healthz endpoint can miss a real business failure. A probe should answer a narrow runtime question; acceptance should cover the most important user outcome.

Imagine a new version of an order API is deployed. The process starts, /healthz returns 200, Pods remain Ready, and the Service routes requests. But the new version reads orders with a database permission that has not been granted. The rollout may be complete at the controller layer and the basic probe may stay green, while users receive errors when they query an order. This is a hypothetical mechanism example, not an incident or test record from this site’s cluster. It shows why “can run,” “can receive traffic,” and “can complete the intended work” must be checked separately rather than turning /healthz into a substitute for every feature.

Business paths with side effects need extra care. Creating an order, charging a card, or sending a notification to prove a release can turn a test into a real operation. Prefer a controlled, repeatable read against a known test record or verify writes in an isolated environment. If a production check must write, give it dedicated data, an idempotency key, a cleanup plan, and explicit authorization. What is safe depends on the system; no single probe or acceptance command fits every service.

A concurrent rollout can make you watch the wrong revision

Version identity is another commonly missed layer. When CI runs kubectl rollout status deployment/<name>, kubectl watches the latest rollout by default. If a second change starts while the command is waiting, it continues to follow the latest revision. Pipeline A may therefore wait for the version it launched but observe the status of revision B, launched by pipeline B. The rollout status reference provides --revision=N to pin observation to one revision; if that revision is superseded, the command aborts rather than silently attesting to another version.

The release system should record the expected version. If an image tag can move, writing v2 alone does not prove which image is running. Record an immutable image digest, Deployment generation or revision, and make sure the acceptance request reaches instances of that release. Kubernetes rollout history can show retained revisions and configurations, but it does not automatically prove which replica currently receives user traffic. Controller state and real traffic still require separate evidence. During a rolling update, a stable Service may have both old and new Pods as endpoints; one random request does not prove it reached the target revision. If acceptance must be tied to the new version, use the existing canary router or a controlled dedicated entry to direct traffic there, and retain a build identifier that can be checked in the response, trace, or gateway record. If the system cannot identify the serving version, record that as unverified instead of treating a successful response as acceptance of the new release.

A reviewable example can be organized as a timeline: the release system records the target image digest and expected revision; the controller reports the new ReplicaSet, desired replicas, and old-replica termination; probes show which Pods are eligible for service traffic; then a controlled read against known test data records the response, observation window, and version that handled it. If the business read fails, this chain helps an operator distinguish “the deployment did not progress,” “traffic did not reach the new Pod,” and “the new code received the request but its dependency failed.” A green rollout is not a diagnosis.

A stalled rollout or failed acceptance does not make rollback automatic

When a Deployment reports ProgressDeadlineExceeded, inspect the condition’s reason and message, Events, and ReplicaSets. Determine whether the cause is quota, image availability, scheduling, probes, or application configuration. A progress condition is a troubleshooting clue; it does not say the data layer or user outcome has failed, nor does it tell the operator whether to roll back or wait. Pausing an update can help inspect a partial change, but the progress deadline is not evaluated during the pause. After resuming, recheck the target revision and observation window.

Kubernetes supports explicit history inspection and rollback. The upstream guide states that Deployment revisions are stored in controlled ReplicaSets and that 10 old ReplicaSets are retained by default; setting revisionHistoryLimit: 0 disables rollback through that history. kubectl rollout undo can also target a selected revision. Retaining history is one rollback prerequisite, not a guarantee that the old application remains compatible with the current database schema, message formats, or external side effects. If a release includes an irreversible data change, reverting the image may be riskier than repairing the new version.

A practical acceptance record can include five items: the expected image digest and revision; Deployment conditions and replica state; Pod readiness and service routing; repeatable results for critical user paths; and an owner, stop-the-rollout action, and assessed recovery choice for failures. Record the observation time and actual version for each item. If the controller fails, the evidence chain stops at the deployment layer. If a business path fails, a passed rollout is not acceptance. If all checks pass, the evidence only shows that the specified paths met the agreed standard for that version and time window; it does not prove every user behavior is correct.

What was actually verified here?

This article uses current upstream Kubernetes documentation and generated kubectl/API references for status semantics, and checks that those source pages are reachable. It did not connect to a cluster, run kubectl, wait for a rollout, execute a business acceptance check, or perform a rollback. The order read, concurrent pipeline, and evidence record are hypothetical examples. Verify exact fields, commands, permissions, and rollback compatibility against the target cluster version, application state, and change type. A controller’s green status can be one link in the evidence chain. Calling it business acceptance requires additional user-path evidence tied to the same release and capable of failing.
