A complete Deployment rollout still needs business acceptance

Separate version identity, controller completion and business acceptance; progress deadlines only signal stalled rollout.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-11 · Estimated read 6 min
Translations
zh-CN en

Article

A completed Deployment rollout establishes controller-observed update conditions, not business acceptance. Record target version, controller state and real user-path outcomes separately. A progress deadline is also a status signal, not an automatic promise to restore an earlier version.

What the controller completes

The Kubernetes Deployment documentation defines completion through updated and available replicas and removal of old ones. A progress deadline reports stalled progress. The controller reports that condition; higher-level orchestration may take additional action. Automatic rollback is not the parameter’s own guarantee. No cluster commands were executed here.

Imagine all new replicas becoming available while database permissions break user queries. The update may be complete within the controller’s responsibility, while business reads fail. This hypothetical example demonstrates a separate evidence layer, not a real incident.

Read reasons alongside state

A true progress condition can persist after completion rather than indicate ongoing work. Examine type, status, reason and version together. Replica availability and rollout progress have different meanings; a dashboard should distinguish advancement, minimum availability and failure causes.

Evidence must identify the current change. Old-request results, previous ReplicaSet logs or an earlier success receipt cannot prove this rollout. Associate acceptance with the intended version and observation window. Consult the actual Kubernetes version for commands and fields; online examples are not execution records from this cluster.

Acceptance must be able to fail

Select a few critical user paths, including essential reads and carefully controlled consequential operations, with explicit failure criteria. A static page cannot represent every subsystem. Production checks need appropriate data and permissions without unnecessary real transactions; safe coverage depends on the system.

Prepare an assessed response path: stopping, correcting configuration or reverting may each fit. Database changes and external effects can limit reversal. Record decision conditions and recovery capability rather than merely promising rollback. Progress deadlines cannot replace this business judgment.

Proposed scenarios include completed rollouts with failing user paths, stalled progress and evidence from the wrong version. None were executed here. See artifacts and rollback boundaries. Split one release green light into version identity, controller completion and business acceptance, with an owner and action for each failure.
