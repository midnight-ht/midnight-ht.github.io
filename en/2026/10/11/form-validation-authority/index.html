What must the server verify after browser validation passes?

Browser feedback cannot authorize a target object or reserve changing business state; the API must independently check the request, caller, and write-time conditions.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-26 · Estimated read 28 min
Translations
zh-CN en

Article

Key takeaways

  • Browser validation proves only that the current page passed its local rules; it is not server authorization or a write receipt.
  • Bound and parse requests, validate field meaning, then authorize the target from trusted identity context.
  • Mutable conditions such as availability and uniqueness must be checked at the write boundary and protected against races with an appropriate transaction or constraint.
  • Shared field rules can reduce drift, but each side still executes them; permission and current state cannot be inferred from the UI.
  • A rejection should help the user correct an error without disclosing sensitive details about an inaccessible object.

After browser validation passes, the server must independently confirm three things: whether it can accept the request data, whether the caller may act on the target object, and whether business state still permits the action when the write occurs. The browser can help a user catch a format error sooner, but it runs in an environment the user controls and cannot freeze server state. A green form is not permission to write.

What does browser “valid” actually prove?

Constraints such as required, type="email", min, and maxlength help the browser identify some problems in the current input. checkValidity() likewise reports whether the current control meets its local constraints. It does not mean the API validated the data or that an operation was committed. The MDN Constraint Validation guide notes that users can modify the page, construct an HTTP request by hand, or set field values with a script; browser constraints do not replace server-side validation. It also documents a precise difference: calling HTMLFormElement.submit() directly does not trigger native constraint validation, while requestSubmit() follows the submit-button process. Unless validation is disabled on the form or submitter, it validates according to the form before submitting. The MDN submit() reference distinguishes the two methods.

That does not make client checks useless. If a date is malformed, telling the user how to fix it immediately is usually better than a server round trip. The point is not to turn “fewer obviously bad requests” into “the server can trust page state.” What reaches the server is a new HTTP request, whether it comes from browser code, a mobile client, an automated caller, or a handcrafted request. That request carries no proof of which prompt the user saw or whether a hidden field was changed.

First check: can the request be parsed and meet the field contract?

Start at the request boundary. Limit oversized bodies before fully buffering or deeply parsing them. Handle parse failures, unknown fields, missing values, null, type mismatches, and nested structures according to the API contract. Successful parsing only means the data could be read; it does not establish business meaning. OWASP recommends checking both syntax and semantics, such as whether a date range is coherent, and distinguishes input validation from parameterized database access and output encoding. Rejecting a few “suspicious characters” can reject legitimate names without replacing SQL parameterization or context-aware encoding. The OWASP Input Validation Cheat Sheet explains these separate boundaries.

A booking API might accept a slot_id and a note for staff. Its handler can check whether the identifier has an allowed shape, whether the note fits its length limit, whether the JSON contains supported fields, and whether the note meets product rules. It must not assume that because the front end showed ten options, a request cannot name an eleventh. Nor should it trust client-supplied user_id, tenant_id, or is_admin as identity. If the API needs one of these values, derive it from a validated request identity and server data, or explicitly validate whether the user is permitted to choose it.

Normalization also needs a defined order and meaning. If the server validates one encoded representation and a downstream component decodes or transforms it again, the check may have applied to a different value than the one used in the operation. For names, free text, and internationalized fields, allowing only ASCII letters and digits is neither complete nor harmless. OWASP recommends defining the application’s actual allowlist and preserving reasonable character sets for free text while applying size limits. Rules should follow each field’s meaning instead of applying a single “safe regex” to everything.

Second check: may this caller perform this action on this object?

A well-formed slot_id does not prove the submitter may book it. Authorization begins by obtaining the subject from a session, token, or otherwise validated service-call context, then checking the subject’s relationship to the target and whether this particular action is allowed. “Logged-in user” does not mean “may write every object.” A hidden button or an option absent from the page is not a security boundary either. The OWASP Authorization Cheat Sheet says permissions should be validated on every request, whether it originated from AJAX, server-side code, or another source. Client-side access control may improve the experience, but it must not decide authorization.

Use a hypothetical “edit someone else’s booking” path to examine the responsibility boundary: user A opens their booking; a developer-tools change replaces the hidden reservation_id with a record belonging to user B; the caller then sends an update directly to the API. Checking that the ID exists, the fields have valid lengths, or user A is authenticated is not enough. The request handler has to establish that A has the authorization needed for this operation on B’s booking. Whether the response should say “exists but unauthorized” or use a uniform “unavailable” result depends on the information-disclosure risk. Do not disguise an authorization failure as “invalid date”; that invites changes to a correct field and makes logs and client behavior misclassify the failure.

This check depends on the actual authorization model. Roles, tenant relationships, resource ownership, or sharing relationships may jointly determine the result; do not compare only a role supplied in the request. If a gateway enforces a common policy, the application still needs a clear assignment of object-level business checks so that a gateway that proves “logged in” does not leave resource scope unchecked in application code. The discussion concerns design responsibility, not a particular framework or authentication scheme.

Third check: is the business state still valid when the write happens?

Some rules change over time. A time slot is available when the user opens the booking page; someone else submits first while the form is being filled out. The browser still holds the earlier selection, and its format checks pass, but the second request must not treat the slot as vacant. This is a state race, not a problem a regular expression can detect.

Suppose a meeting-room service stores bookings as discrete slots. A and B both see Friday at 10:00 as available, then submit at nearly the same time. If the server checks availability and inserts outside an atomic boundary, both reads may see the slot as free and both inserts may succeed. If the data model represents each slot as a unique resource, a database uniqueness constraint can be the final concurrency guard; request handling must still map the conflict to a useful rejection so the user can choose again. If the business uses arbitrary time intervals, capacity decrements, or a multi-part eligibility rule, the protection will differ. Choose a constraint, conditional update, lock, or transaction isolation that matches the data model, and test the concurrent path instead of copying one generic recipe.

For PostgreSQL 18, the official documentation explains how isolation levels affect what concurrent transactions observe and that Serializable transactions can end in serialization failure; an application must be prepared to rerun the complete transaction logic where appropriate. Its constraint reference describes what UNIQUE, EXCLUDE, and FOREIGN KEY constraints can express and warns that CHECK constraints are not suitable for maintaining cross-row invariants. PostgreSQL 18 Transaction Isolation and Constraints describe PostgreSQL-specific behavior and should not be generalized to every database. Choose based on the actual invariant: a simple discrete slot may be represented by a unique key; overlapping intervals or multi-table rules require checking the constraints and isolation behavior of the selected database.

When a conflict occurs, the API should explain that state changed and offer a refresh or new selection path, rather than blaming the original input format. RFC 9110 defines HTTP 409 as a request that cannot be completed because it conflicts with the target resource’s current state, and recommends enough response information for the user to recognize the conflict. That is one possible semantic fit; it does not require every application to return 409 for every form error. RFC 9110, Section 15.5.10 defines other failure semantics too, so the choice belongs in the API contract.

What can shared client and server rules solve?

A shared field schema can reduce drift in length, enum, or type rules. For example, generating both a “maximum note length” hint and a server rejection condition from one contract avoids maintaining two definitions. But that rule must still run separately in the browser and on the server. It cannot prove caller identity, object permission, or that another person has not just taken the booking slot. Putting a database lookup inside a shared schema can even give the browser a stale cached result that incorrectly says “available.”

A clearer division is: the client performs low-cost, immediate checks that help the user; the server always performs trusted request-structure and semantic validation, authorization, and the business check at the write boundary. The front end may ask for an expensive or state-dependent preview, but that preview is only an estimate of state at that time; the submission endpoint must still check again. For how a form question should connect to a service rule, see the field protocol for service decisions. The focus here is the acceptance boundary of each submission.

After rejection, how can the user correct the form without leaking data?

A rejection should not be only a vague “failed,” nor should it expose a validation-library stack trace or database constraint name. When an input fails its contract, the response can identify the field and the acceptable range. When the caller lacks access to an object, the prompt must not reveal a record the caller should not know exists. When business state conflicts, explain the next action: refresh or choose another slot. Error type, HTTP status, readable explanation, and internal diagnostic data each have a purpose; the client should not guess whether to retry or edit a field by matching localized sentences.

W3C WCAG 2.2 Success Criterion 3.3.1 requires that an automatically detected input error identify the affected item and describe the error in text. It does not mandate one layout, but a user should be able to tell what went wrong. The W3C WAI explanation of SC 3.3.1 also distinguishes identifying an error from suggesting how to fix it. An implementation could link a form summary to the relevant field, associate an explanation with that field, and preserve non-sensitive values that remain valid after the response. An authorization rejection or sensitive state conflict must not reveal another user’s name, booking time, or whether a resource exists just to make correction more convenient.

Test the keyboard and assistive-technology path too: where does focus go after the summary appears? Does the link reach the correct field? Does the old error clear after correction? A red style is not a text description, and a single message at the top may be noticed by a mouse user with sight while leaving a screen-reader user unaware of which field it concerns. The related error-summary correction route discusses the path to the right field; stable problem-detail types discusses machine-readable error categories. Their implementation details belong to those articles; the category here must retain the difference between invalid input, failed authorization, and business conflict.

How can you verify that each check runs in the right layer?

At review time, list at least three requests: one that bypasses the page and submits invalid syntax or an unknown field; one with valid syntax but another user’s object ID; and one where another concurrent request takes a resource after the page read but before this form is submitted. Observe the response, authorization decision, transaction or constraint result, and final persisted state. A safe negative case should show that an unauthorized object did not change, invalid data was not written, and a state race allowed only the outcome the business rule defines. A proposed test case is not evidence that it has been run.

Also cover oversized or malformed bodies, failed cross-field rules, the message after a state change, and whether an authorization refusal reveals resource existence. If the design uses a database constraint or isolation level, record its version, transaction scope, concurrency method, and retry behavior. A single-threaded happy path does not establish a concurrent invariant. Avoid logging the entire form body for convenience; redact or exclude sensitive fields and use a request identifier to correlate internal records.

The stated boundaries are drawn from the currently checked MDN, OWASP, W3C, RFC 9110, and PostgreSQL 18 documentation. No browser automation, direct API calls, concurrent database tests, or assistive-technology acceptance checks were run. The booking, object substitution, and competing slot are hypothetical examples, not results from this site or a customer system. If a team can name which layer owns request structure, object permission, and state-at-submit—and can keep each rejection safe and correctable—browser validation helps users without being mistaken for an authorization credential.
