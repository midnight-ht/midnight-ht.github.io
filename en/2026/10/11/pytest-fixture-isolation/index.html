A broader fixture scope also broadens shared state

Broader fixture reuse needs explicit initial state, failure cleanup and external-resource isolation.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-11 · Estimated read 5 min
Translations
zh-CN en

Article

Increasing a pytest fixture’s scope extends reuse and may extend mutable-state lifetime. When tests influence one another, identify who changes the shared object and how each test obtains its initial state. Reordering tests does not repair isolation.

Objects outlive setup costs

The pytest fixture guide defines teardown boundaries from the default per-test scope through class, module, package and session scopes. It also notes that parametrization can invoke a fixture more than once within a scope. Scope is therefore not an unconditional promise of exactly one instance throughout a run.

Imagine a shared client where one test switches authentication to administrator and another assumes a regular user. State residue, not assertion order, creates the problem. This example was not executed. Passing alone and failing in a group is a clue, not proof: external data and timing dependencies also deserve investigation.

Separate reusable infrastructure from mutable context

Expensive connection creation does not make session state safe to share. Separate reusable infrastructure from per-test identity, data and transaction boundaries. Read-only configuration may be shared; modified collections, credentials and temporary records need explicit reconstruction or cleanup. Scope decisions need contracts and measured cost, not a desire for a shorter-looking run.

Final teardown cannot prevent one test’s data contaminating the next. Reset at the relevant isolation boundary, including failure paths. Expose cleanup failures and residue risks rather than silently treating them as an incidental success detail.

Parallel runs change assumptions

Process-local scope does not establish isolation for external databases, accounts or directories. Different worker objects can still share the same external resource. Use appropriate identities or concurrency strategies and correlate resource creation, usage and cleanup.

Proposed checks compare individual and grouped runs, changed order, state after a failed test and concurrent access. No pytest run was performed here; no speedup or passed-isolation result is claimed. Also ensure cleanup has not erased data conditions that the test was supposed to exercise.

The transaction recovery discussion distinguishes boundaries with different meanings. List every mutable property of one broadly scoped fixture, then choose resetting, reconstruction or a narrower scope. Reuse should rest on known initial conditions rather than accidental order.
