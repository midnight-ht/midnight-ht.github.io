Why Do Tests Start Affecting One Another After a Fixture Scope Change?

pytest fixture scope extends reuse and state lifetime, not isolation. Decide from mutability, cleanup boundaries, dependency scope, and external resource identity.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-26 · Estimated read 23 min
Translations
zh-CN en

Article

A pytest fixture’s scope determines how long its result can be reused; when that result or the service behind it is mutable, widening the scope also lengthens the life of shared state. Scope does not guarantee isolation. Before changing it, identify who owns the object, which properties can change, and where the state is recreated or cleaned up.

Scope governs lifetime, not a clean starting point

The pytest fixture guide describes scope in terms of fixture creation and teardown. The default function scope gives each requesting test a fresh result. Class, module, package, and session scopes widen the reuse window. When a test requests a fixture, pytest resolves its dependencies, creates what is needed, and passes the resulting object to the test. The test receives a concrete object—or a handle to external state—not an abstract setup instruction.

A common reason to change function scope to module scope is expensive initialization: starting a service, loading a large read-only index, or opening a test database connection. Reuse can reduce repeated setup, but it changes the lifetime of the result. If that result is immutable configuration, a wider scope may change only the cost. If it contains a list, authentication identity, cache, transaction state, or external records, two tests may now observe the same state. The issue is not that a broader scope is always wrong; it is that the reuse contract may not define how state returns to its starting point.

The fixture guide also explains that parametrization can lead to multiple fixture instances within a declared scope. “Session scope means exactly one instance for the whole run” is therefore not a universal guarantee. Include parameters, dependencies, and actual caching behavior in the reasoning instead of reading a single word on the decorator as the whole contract.

A state-leak example you can reason through

The following is an illustrative hypothetical, not a pytest result from this article’s project:

import pytest

@pytest.fixture(scope="module")
def catalog():
    return {"items": []}

def test_adds_item(catalog):
    catalog["items"].append("alpha")
    assert catalog["items"] == ["alpha"]

def test_starts_empty(catalog):
    assert catalog["items"] == []

Both tests request the same module-scoped fixture. One test appends alpha; if the next test reuses that result in the same module, its expectation of an empty list no longer holds. Reversing the order may change which assertion first exposes the issue, but it does not change the fact that the tests share an object. Reducing the fixture to function scope recreates the dictionary for each request. Another option is to share an expensive read-only foundation while giving each test its own mutable catalog or transaction.

The second approach often makes the boundary easier to explain. For example, a session-scoped fixture might own an already-started test service, while a function-scoped fixture creates a unique tenant, record set, or transaction for the current test and cleans it up at that test boundary. First establish whether the service supports concurrent sessions, whether rollback covers the writes in question, and whether background work can escape the transaction. Calling rollback() does not prove that every external side effect was undone.

Separate the stable foundation from test state

A useful scope decision starts by splitting a fixture into two layers. A stable foundation may contain expensive resources that should remain unchanged during tests: a local service process, a read-only schema, or a connection pool. The second contains context whose value a test changes or whose initial state it relies on: a login identity, order, queue message, random-port mapping, or temporary directory. That stable layer may be a candidate for reuse; mutable test context needs an explicit per-test creation, naming, reset, or teardown strategy.

This is not an absolute rule that every mutable Python object must be function-scoped. A module-level object can be safe if it is genuinely read-only or if each test obtains an independent session through a factory. Conversely, a function-scoped fixture can still pollute later tests if it writes to a database table shared by the suite. The unit of analysis is observable state, not only Python object identity. A client that appears read-only may still retain cookies, a current user, or a cache. Two separate connections can still update the same row.

For each broad-scope fixture, write a short contract: which resource does it own; which operations mutate state; what may remain shared across tests; who resets it; how cleanup works after normal completion and an exception; and how parallel workers distinguish their resources. If those answers are unclear, defer widening the scope.

Cleanup must align with the state boundary

A pytest yield fixture can place resource-release code after yield. That expresses “release after use,” but the teardown time still follows the fixture’s scope. A module-scoped fixture’s final cleanup occurs after its module-related work; it cannot replace resetting state between two tests. If one test’s record can be read by the next, cleanup belongs at a test-level transaction, unique namespace, or explicit deletion boundary.

If a fixture raises before reaching yield, its post-yield cleanup does not run, although pytest still attempts teardown for dependencies that completed successfully. Avoid placing several state-changing operations that can partially succeed inside one large fixture. A safer structure separates actions such as “create one user” and “start one browser” into fixtures that each own their cleanup. After a state change succeeds, its release path is registered immediately. The pytest safe-teardown guidance recommends pairing a state-changing action with its own cleanup to reduce the window in which a later setup failure can leave residue.

Also inspect autouse fixtures. They cause tests in their visibility scope to request a fixture automatically, even if it does not appear in the test function signature. This can remove repetitive declarations but can also hide a setup dependency. Search not only test parameters but also conftest.py, directory-level fixtures, and autouse=True; then check whether the fixture scope expands its effects to a wider set of tests.

If teardown itself fails for an external database, cloud resource, or account, preserve that as a diagnostic result and record a locatable resource identifier for cleanup. A test process exit ends local execution; it does not prove remote state has disappeared.

Dependency lifetimes must also match. A broad-scope fixture cannot rely on a narrower-scope dependency for its entire lifetime; pytest reports a scope mismatch because the narrower fixture cannot remain valid for the broader object. The fixture reference ties instantiation order to scope, dependencies, and autouse behavior. Do not use fixture names, file order, or accidental test ordering as an initialization contract. Declare the real dependency in the fixture parameters, or split the resource boundary.

Parallel runs need external resource identities

Scope manages pytest-managed fixture instances and their lifetimes. It does not automatically isolate databases, object storage, test accounts, ports, or queues outside the process. Two workers can each hold a distinct client object and still write to the same table or account. If conflicts appear only in parallel runs, inspect the identity of external resources instead of focusing only on Python fixture scope.

One strategy is to combine a run identifier and worker identifier into a separate schema, directory prefix, or tenant name, then have tests touch only their own namespace. Cleanup uses the same identifier. This adds creation, migration, and garbage-collection cost; it also requires protection against identifier collisions and accidental deletion of shared data. If the system cannot isolate by namespace, serializing the affected tests may be more honest than pretending they are parallel-safe, at the cost of runtime. Neither strategy is universal; choose based on resource capabilities and execution constraints.

Diagnose “passes alone, fails in the suite”

First hold conditions steady: the same code revision, environment variables, and external services. Then record which fixtures, globals, and external resources the failing test and its neighbors write. Run comparisons that separate hypotheses: does the failure differ between an isolated and grouped run; when order changes, does the failure move with a preceding writer or remain attached to the same test; can a read-only check see residue after a failure; does disabling parallelism change the outcome? Each observation narrows the search; none alone proves causality.

For example, if an isolated test passes but a changed order repeatedly exposes failure after a shared catalog is appended to, in-memory state leakage becomes a stronger hypothesis. If a dedicated temporary directory does not change the failure, continue investigating database records or time dependence. If only parallel execution fails, distinct Python objects have not ruled out a shared database-key conflict. Conversely, a failure that stays with one test and also occurs when run alone is not likely to be fixed by reordering. These are proposed diagnostic steps, not results from an executed investigation.

pytest 9.2.0 was released on 2026-10-27. The current stable documentation was checked on 2026-11-26. Its release notes include updates to parametrization APIs and fixture declarations, but the central point here remains lifetime, dependencies, and state boundaries; the release is not evidence of a changed scope-isolation rule. For older pytest versions, check the documentation and behavior matching the version installed in the project.

Choose scope from evidence

For an existing broad-scope fixture, list the mutable fields in its returned object, the external resources it points to, who writes them, and whether writes may remain visible between tests. Then ask, in order: Is initialization cost large enough to justify reuse? Can the reusable part become a read-only foundation? Can each test have its own transaction, identity, or namespace? Does cleanup work on failure? Will parallel workers contend for an external key? If the initial state and cleanup owner cannot be described, narrow the scope first and optimize against measured cost later.

No pytest command was run for this article, and no timing or pass-rate measurement was collected. The list-mutation scenario is a hypothetical explanation; the diagnostic sequence is a proposal, not a test report. Evidence for retaining a broader scope should include both the actual cost change and a check that the initial state still holds across tests. Otherwise, avoiding a few object creations may buy an order dependency that is difficult to reproduce.

The related discussion of savepoints and partial transaction recovery also stresses that a recovery boundary must match data ownership. For fixtures, identify who owns the state and who restores it before deciding to let the result live longer. Scope is a lifetime tool, not an isolation strategy.
