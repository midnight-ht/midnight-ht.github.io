How can an uncommitted local file enter a Docker build context?

Local directories, remote Git sources, and named contexts have different input boundaries. Inspect the build arguments, effective ignore rules, and image separately.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-26 · Estimated read 19 min
Translations
zh-CN en

Article

Key takeaways

  • A local-directory context reads the developer's working tree; a remote Git context reads a repository reference. Git ignore rules do not make them equivalent.
  • The final positional argument selects the context, while -f selects the Dockerfile; moving the Dockerfile does not narrow the input.
  • .dockerignore and Dockerfile-specific ignore files apply according to context and precedence; ! exceptions and later matches affect the result.
  • Context visibility, builder transfer, and final-image contents are separate boundaries. Verify inputs, build instructions, and artifacts independently.
  • Provide build credentials through secret or SSH mounts, then check that commands do not print or copy them.

If the final argument to docker build is a local directory, a file that Git has never committed may still be visible to the builder. The command selects the build context; .dockerignore filters files from that context; a Dockerfile instruction determines whether a visible file is copied into an image. Keeping these three steps separate is the only reliable way to answer whether a local file will be included.

Which argument selects the build context?

Docker defines a build context as the set of files a build instruction can access. In docker build [OPTIONS] PATH | URL | -, the positional argument can be a local directory, a remote Git or archive source, or standard input. It is not the Dockerfile path. -f or --file selects the Dockerfile. So in docker build -f docker/app.Dockerfile ., the Dockerfile is under docker/, while . still makes the current directory the default context. Moving the Dockerfile does not automatically narrow that context. Build-context documentation describes local, remote, and standard-input contexts separately; the image build CLI reference likewise treats the positional path and --file as different inputs.

This explains a common false conclusion: if .gitignore keeps an untracked file out of git status, that changes Git’s version-control handling. It does not remove the file from the developer’s directory or turn it into a Docker exclusion rule. For a local-directory context, the build client applies .dockerignore. With a remote Git repository as the context, Docker obtains source from the selected repository reference instead of reading the uncommitted working tree on your laptop. The remote branch, tag, or commit then determines that source. Calling both cases “building from Git files” hides the boundary that matters most.

Compare two entry points in one repository

The following monorepo is hypothetical. It is not a real project or an executed result:

repo/
├── .env.local                 # ignored by Git, still present on disk
├── .dockerignore
├── shared/schema/
└── apps/catalog/
    ├── Dockerfile
    ├── package.json
    └── src/

If the command runs at the repository root as docker build -f apps/catalog/Dockerfile ., -f selects the application Dockerfile, but . still sets repo/ as the default context. .env.local is inside that scope. Whether it is sent to the builder depends on the ignore file and patterns actually in effect. Even if it is not excluded, that alone does not put it in the image. If the Dockerfile copies only apps/catalog/package.json and apps/catalog/src/, other visible files do not automatically become image contents. The result differs if the Dockerfile uses COPY . /app.

If you instead enter apps/catalog/ and run docker build ., the default context shrinks to the application directory. The root .env.local and shared/schema/ are outside that default scope. Git did not cause this change; the command did. If the application needs shared code, design the input deliberately: build from the monorepo root and narrowly control that context, or add a named context for BuildKit and reference it by source. A named context makes the second source explicit in the command, which helps reviewers see what comes from outside the main project. It does not decide whether that source contains unnecessary files. Named-context documentation documents --build-context and COPY --from.

Why is .dockerignore not a mirror of Git rules?

For a local filesystem context, .dockerignore belongs at the context root. Matching files are removed before the context is sent to the builder. When a project has multiple Dockerfiles, a Dockerfile-specific ignore file can live beside each Dockerfile, such as docker/app.Dockerfile.dockerignore; when both it and the context-root file exist, the Dockerfile-specific file takes precedence. Reading only the shared root file may therefore miss the rules used by the build that actually ran. The official syntax reference also explains that leading and trailing slashes are disregarded, ** is supported, and a rule beginning with ! can re-include a previously excluded path.

Rule order changes the answer. Suppose the file first excludes all Markdown, then re-includes the root README.md. If README-private.md is excluded by a later rule, it stays out. But if !README*.md is moved to the end, it may bring the private README back. Seeing *.md in the file is not enough to conclude that every Markdown file is excluded; evaluate the matching rules from top to bottom for the exact path. Docker also says that a standalone . pattern is ignored for historical reasons, so treating it as shorthand for “exclude the whole context” is a mistake.

Both build-definition files remain available to the builder even if an ignore pattern excludes them, because the build needs them. The documentation also says they cannot be placed into the image with ADD, COPY, or a bind mount. This exception is easy to misread: ordinary context files are subject to filtering, while the files defining the build still have to be processed; that does not make them application files to package.

Does sending a file to the builder put it in the image?

By default, docker build uses Buildx/BuildKit except in Windows container mode or when DOCKER_BUILDKIT=0 is set. The official CLI documentation distinguishes transfer behavior: the legacy builder sends the entire context to the daemon, while BuildKit transmits the files used by the build. That affects transfer size and exposure, but it is not proof that a file is safe. An ignore rule is an input-layer conclusion; a visible file that the current Dockerfile never copies is an instruction-layer conclusion; a file in an image layer requires checking build steps, stages, and the artifact itself. Each layer needs a different check. The CLI reference’s legacy-builder discussion is limited to the cases described on that page.

Likewise, COPY ../shared/schema /app/schema is not a way to climb out of a small context. Dockerfile COPY source paths are interpreted relative to the context root. The current reference says that a path prefix navigating outside the context is removed; it does not enlarge the default context. If the file is missing, inspect the context argument or add a named context explicitly. Do not treat ../ as a permission escape hatch. See the Dockerfile COPY path rules.

How can you verify the path a file actually takes?

A reviewable investigation starts with the actual entry point, not Git status. Record the command run by CI or the developer, its working directory, final context argument, Dockerfile selection, and whether the input is a local directory, Git URL, or archive. CI’s working directory and context can differ from a local terminal. Inspecting the Dockerfile alone cannot tell you which path the command supplied. Then identify the ignore file that applies at that context root; if a Dockerfile-specific file exists, read it according to its precedence. Finally, evaluate the patterns for each sensitive relative path, paying special attention to ! exceptions and later matches.

Split verification into two passes. First, use harmless canary files such as local-marker.txt containing sample-only, placing one inside the context, one under an ignored path, and one outside it. With a minimal Dockerfile, try referencing each and observe whether the build can resolve it. This tests the input boundary, not production-image security. Second, in an isolated environment, inspect the resulting image file list or layers and confirm that prohibited files were not copied by the build. With a remote builder, also determine which context files need to be uploaded; a transfer-size line in a build log does not replace content review.

Real credentials should not be managed by “adding them to .dockerignore.” Ignore rules are one defense against ordinary files in a context, but a team may switch Dockerfiles, add another named context, or build from a CI archive that the old rule set never covered. When a build must download private dependencies, Docker recommends BuildKit secret or SSH mounts instead of putting tokens in ARG or ENV. A mount changes how a build step receives the credential, but the command must still be checked for printing it or copying it into output. The build-secrets guide distinguishes secret mounts from build arguments and environment variables that may persist in the image. Inspect the artifact; no input mechanism is an absolute guarantee.

This article follows the currently available Docker documentation. No Docker build was run locally or in CI, no image was scanned, and no customer or production environment was observed. In a real investigation, record separately what input the command selected, which files passed filtering, which paths the Dockerfile consumed, and what remained in the artifact. Instead of asking only whether a file entered Git, give a verifiable answer for each of those four boundaries. For the separate path by which a build command can carry a secret into output, see the secret-mount output boundary; that article concerns secret consumption and output, while this one concerns context inputs.
