Git ignore rules do not define the Docker build context

Inspect actual context sources, ignore precedence and exceptions, then verify build artifacts separately.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-11 · Estimated read 5 min
Translations
zh-CN en

Article

A file absent from Git can still enter a Docker build context. Inspect the directory or other source actually supplied to the builder and its exclusions. Version-control ignore rules do not define build inputs.

Identify the input boundary

The Docker build-context documentation explains .dockerignore filtering, Dockerfile-specific ignore precedence and pattern rules. This article uses the current online documentation and reports no Docker build or proof that an image excludes every sensitive file.

Imagine local environment files and debugging exports ignored by Git. If the context is a local directory, build-specific rules still need to handle them. This hypothetical example contains no real secrets. The problem is a mistaken boundary assumption, not Git malfunction.

Directory choices change scope

Using the parent directory instead of the current project can include neighboring projects, archives or tooling data. Review the command, context and Dockerfile together instead of inspecting copy instructions alone. Remote and named contexts have their own boundaries; local-directory experience is not a guarantee for every mode.

Review ordering and exceptions. A later inclusion can bring an object back after a broad exclusion. Dockerfile-specific rules may take precedence over a shared file. Maintainers should be able to explain which inputs are permitted, rather than indefinitely appending exclusions.

Smaller inputs do not prove safe outputs

A constrained context clarifies dependencies but does not establish image safety. Builds may download material, generate debugging output or copy credentials. Inspect input boundaries and final artifacts separately. Steps needing secrets also require suitable delivery and output checks.

Proposed tests use a controlled directory with representative files, checking shared rules, exceptions and Dockerfile-specific rules before inspecting artifacts for prohibited content. No such checks were run; no size reduction or security result is claimed. Use harmless substitutes rather than real secrets to verify path behavior.

Reassess after changing working directories, Dockerfiles or additional contexts. The build-secret output discussion explains why safe input does not imply safe output. Inspect the actual context argument, list necessary and prohibited inputs, then verify exclusions and artifacts. “Not committed” is insufficient evidence.
