How can PostgreSQL imports report results after per-row savepoints?

A SAVEPOINT rolls back part of a transaction; it does not commit each row. A trustworthy partial-import receipt needs stable input identities and a queryable outcome tied to the outer commit boundary.

Updated 2026-11-26 · Estimated read 27 min

Article

SAVEPOINT lets an importer undo one failed input and continue with later inputs. It does not make each row an independent commit. A trustworthy partial-import receipt must put accepted data, rejection details, and the job's terminal state behind a clear outer commit boundary. It also needs stable job and input identities so a client can query the outcome when the commit acknowledgement is lost. Without those pieces, an API can report a batch of “successful” records even though the database later rolls the entire transaction back.

A savepoint solves transaction recovery, not product semantics

The PostgreSQL 19 SAVEPOINT documentation describes a savepoint as a marker inside the current transaction. ROLLBACK TO SAVEPOINT discards commands after that marker and restores the transaction to a usable state; the savepoint itself remains valid. RELEASE SAVEPOINT removes the marker and merges changes that were not rolled back into the enclosing transaction. It is not a COMMIT. The official transaction tutorial says that intermediate transaction states are not visible to other sessions before the outer commit, and a failed multi-step transaction is rolled back as a unit.

So “a savepoint per row” describes a local recovery strategy, not “a row is durable as soon as it succeeds.” Imagine importing a contact list into a contacts table and writing one result per input. If the third email violates a unique constraint, the application can roll back that input's database work, record it as rejected, and continue with the fourth. But if the result table becomes unavailable after the ninetieth input, a later statement is aborted by a deadlock, or the final commit fails, the accepted contacts and all accepted and rejected details belong to the same outer transaction. They disappear together.

That outcome does not mean savepoints malfunctioned. A savepoint provides a way to discard local changes while retaining earlier work in the transaction. The product still has to decide whether inputs may be accepted independently, how long failure details remain available, when a final receipt becomes readable, and how to recover an unknown outcome. If the business contract says that a file is either wholly valid or causes no changes, skipping individual errors violates that contract. This capability alone is not a reason to make savepoints the default.

Persist a queryable job identity first

Map the user's submission to a stable import_id and record an input digest or version. A job might have states such as running, committed, failed, or needs_reconciliation; each input also needs a stable source_key. The original file's row number is useful for display, but it may change after reordering, adding a header, or exporting the file again. It cannot be the only identity for a retry.

A reviewable simplified flow is to create or obtain a unique job record in a short transaction and commit it as running. A second transaction processes business data, per-input results, and the job's terminal state. Only after that second transaction commits should external queries see committed and the full receipt. If a worker crashes or its commit response is lost, the client can query the same import_id instead of creating a fresh job that writes the whole file again. If an existing identity arrives with a different input digest, reject the reuse or require a new job identity; do not silently return a receipt for a different file.

The following is pseudocode to illustrate transaction boundaries. It is not a complete implementation to copy, and it was not executed against PostgreSQL. Table fields, constraints, isolation level, and concurrent job-claiming rules must fit the actual data model:

BEGIN
  for each input with a stable source_key:
    SAVEPOINT one_input
    try to write the business record
    if this is an input constraint error the product allows to reject:
      ROLLBACK TO one_input
      write a rejected result for this source_key
      RELEASE one_input
    else if the write succeeded:
      write an accepted result for this source_key
      RELEASE one_input
    otherwise: abort the outer transaction
  compute totals from the result rows, not process-local counters
  update the job to committed and persist its totals in this transaction
COMMIT

The order matters. On success, the accepted result and business row must be written within the same savepoint/outer-transaction scope; otherwise a contact could exist with no corresponding accepted result. On the rejection path, roll back the failed input's local work before inserting its rejection detail. If that diagnostic cannot be persisted, stop the batch and roll back the outer transaction. Do not swallow “failed to record why this row failed” and still claim the receipt is complete.

Error classification matters too. Not every SQL exception is a bad row that can be skipped. An application may put confirmed input constraint failures on a rejection allowlist, keyed by an identified constraint or SQLSTATE. Even when PostgreSQL could technically recover from another statement error by rolling back to its savepoint, a deadlock, serialization failure, permission misconfiguration, or result-table failure should normally be treated as a system-level failure rather than mislabeled as invalid user input. Let the outer transaction fail and use the appropriate retry or investigation path. The transaction tutorial explains that an error in a transaction block leaves it aborted until it is rolled back or rolled back to a savepoint.

Update the job's terminal state in the same transaction as accepted data and row-level results. When a client sees committed, its related accepted rows, rejected rows, and totals should already have committed together. Before that commit, another session should still see the durable job as running. If a process increments “90 accepted, 10 rejected” in memory, returns success, and only then attempts the database commit, those numbers describe an unconfirmed calculation, not a receipt.

Apply the rule to a hypothetical three-row file. row-A passes validation, is inserted, and gets an accepted result. row-B conflicts with an existing email, so the importer rolls back its savepoint and stores a rejected result with the named constraint. row-C also passes. Before the outer commit, another session cannot see the new row-A, row-C, or the three result records; the durable job header still says running. After a successful commit, the client can read two accepted records, one rejection, and the reason linked to its source key. If the summary update fails after row-C, the business changes and all row results roll back; the job header created earlier remains running, ready for retry or reconciliation. These counts only illustrate data relationships; they are not measured results.

Do not replay a file blindly when commit confirmation is lost

A common boundary is not an explicit database error but a dropped connection after the client sends COMMIT. The application has no confirmation and cannot infer from a network error alone whether the server committed or rolled back. Query by the original import_id. If its state is committed, return the report stored in the database. If it remains running, a worker or coordinator can decide whether to take over using a lease, heartbeat, and input digest. If the answer is temporarily unknown, return “processing” or “reconciliation pending”; do not disguise uncertainty as success or failure.

Queries and retries also need concurrency rules. Two workers must not both insert results under the same identity and independently mark the job complete. A unique constraint on (import_id, source_key) can prevent duplicate result rows; a row lock, lease, or equivalent ownership mechanism can arbitrate job claiming. These are design choices to verify for the deployed database version, isolation level, and worker model. Local rollback markers do not provide them automatically. A unique key or explicit upsert conflict target may define the behavior of a replayable business write. The documented ON CONFLICT clause handles unique or exclusion-constraint conflicts; it does not convert type errors, missing foreign keys, trigger failures, or arbitrary business validation into ignorable errors.

For a large job, one outer transaction can hold locks for a long time and enlarge the rollback window. Committing smaller chunks may reduce the scope of each transaction, but it changes visibility and cancellation semantics: previously committed chunks remain even if a later chunk fails. The receipt must then expose chunk boundaries, a cursor, and retry rules. Chunking is not merely an implementation optimization; it is a different product promise. Choose based on data volume, lock waits, recovery time, and user acceptance of partially visible output, rather than assuming smaller transactions are always faster.

Separate invalid inputs from transaction failures

Per-input reports are useful for expected data problems, such as a field failing a product-defined validation rule. A deadlock or serialization failure caused by concurrent database activity is different. Recording the current transaction as “this row was invalid” misleads the user. The locking guidance recommends retrying a transaction that was aborted by a deadlock. Repeatable Read and Serializable guidance likewise says serialization failures require retrying from the beginning. Such retries must rerun the whole transaction logic and rely on stable job identity and idempotent data constraints; they must not resume only at the statement that failed.

Do not treat gaps in a sequence-generated primary key as proof that imported rows were lost. Sequence allocation does not reclaim a nextval value when the transaction rolls back; conflicts and failures can also leave gaps. The job result table and stable source keys, not consecutive IDs, are the reliable basis for the report.

When the main problem is input conversion, PostgreSQL 19's COPY FROM ... ON_ERROR offers ignore and set_null behavior. The documentation limits these options to errors converting input values to target data types, and describes aggregate counts plus optional verbose notices with input line and column details. This is not general business validation, foreign-key repair, or a per-record results API. Loading into a staging table and validating with set-based queries can preserve source identity and error categories more clearly. Whether staging or per-row savepoints fit better depends on constraint complexity, batch size, maintainability, and measured evidence. No performance comparison was run here, so this article makes no claim that either approach is faster.

Keep the receipt and side effects on the right boundary

A database transaction can roll back database changes; it cannot retract an email, HTTP request, or message already sent to another system. If the importer calls an external service after accepting each contact, a later outer rollback does not undo those external actions. A common design is to write an outbox row in the same database transaction, then let a post-commit dispatcher send it with a stable event key that handles duplicate delivery. Another option is an explicitly compensating business workflow. Either way, record delivery failures, replay, and compensation. Adding savepoints does not make a cross-system import atomic.

Verify state transitions, not just exception handling

For an actual implementation, verify at least these paths: an allowed rejected input followed by a valid input; an unavailable results table causing the outer transaction to fail rather than leaving unexplained data; final commit failure leaving no false success; a lost commit response followed by a query using the same job identity; a retry of the same (import_id, source_key) without a duplicate write or count; accidental reuse of a job key with a different file; deadlock or serialization failure retried from the transaction beginning; sequence gaps while the report still uses result details; and logs that do not expose entire rows of personal data.

Tests should not merely assert that an exception was raised. Read the committed business table, job table, and result details, then check that they agree. Use a separate connection to confirm that uncommitted running progress is not mistaken for committed. If the design commits chunks, add a case where chunk N succeeds and the next chunk fails, then verify that the product accepts the earlier chunk's visibility and that the recovery cursor is correct. These are proposed verification cases. No PostgreSQL server, SQL snippet, or load test was run for this article, and it contains no measured performance result.

The practical boundary is simple: when the receipt depends on the outer commit, the system can claim success only after that commit; when job and result identities are stable, a client can determine what happened after a timeout. Decide first whether the promise is an atomic batch, visible chunks, or independently committed rows; then choose savepoints, staging, or asynchronous job states. For an asynchronous endpoint, pair this design with the terminal-state contract for HTTP 202 requests. For retry identity, see API retries and idempotency keys. A savepoint is a local recovery tool. A trustworthy receipt comes from a consistent state model and a verifiable commit boundary.
