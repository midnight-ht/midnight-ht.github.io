How can a resumed download avoid joining two file versions?

A byte offset does not identify a file version. Use If-Range to condition resumption, validate Content-Range on 206, and route a full 200 response through replacement.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile

Article

Key takeaways

  • An offset records how many bytes are local; it does not prove they belong to the currently selected representation.
  • A 206 response still needs range and representation checks; a full 200 response belongs in a replacement path.
  • An ETag is a representation validator, not automatically a tamper-proof checksum.

A resumable downloader should not append bytes based on a local offset alone. It must establish that the saved bytes still belong to the same selected representation, then verify that the response starts exactly where the local file ends. A complete 200 OK response belongs in a replacement path: the client must replace the temporary object or write a new one. Adding that full response after the old file creates an object assembled from two versions.

Why does an offset fail to identify a version?

Suppose a URL serves a 10 MiB export called version A on Monday. The client receives and saves the first 5 MiB before the connection drops. On Tuesday the export is regenerated at the same URL and remains 10 MiB, but its bytes are now version B. A recovery routine that reads only the local file length asks for Range: bytes=5242880-. When the rest of B arrives, the assembled file is still 10 MiB and passes a length check, yet its prefix came from A. These numbers describe a hypothetical example, not an observed transfer.

An offset answers “where does my local copy currently end?” It does not answer “which representation produced those bytes?” Recovery state needs to associate the resource address, selected variant, validator, persisted ranges and temporary object. If language negotiation, content coding or caches can select different bytes, the downloader also needs to preserve enough of the original selection context. Treating a URL as one immutable byte sequence is a common source of silent corruption.

An HTTP Range request asks for a portion of the selected representation. A server can ignore the range. Accept-Ranges: bytes advertises support, but it is not a promise that every later request will receive 206; RFC 9110 §14.2 explicitly allows a server to ignore Range. The absence of Accept-Ranges by itself is not proof that range requests can never work. Let the actual response determine the write decision; an earlier capability probe is not enough.

How does If-Range connect saved bytes to the current representation?

When it first receives data, a downloader can save the server's strong entity tag, for example the hypothetical value ETag: "release-41". On resumption it sends both Range: bytes=5242880- and If-Range: "release-41". Under RFC 9110 §13.1.5, when the validator still matches, the server processes the range. On a mismatch, the server ignores Range and sends the current complete representation instead of a partial response that the client might mistakenly append. The client must route that full body to a fresh-download path.

If-Range cannot use a weak entity tag. A date form is allowed only when the client has no entity tag for the corresponding representation and the date is a strong validator; the date must exactly match the selected representation's Last-Modified value. Many systems do not have enough timestamp precision or a reliable update process to distinguish multiple generated objects within one second. An arbitrary timestamp is not a strong version identifier. Use a validator whose behavior is understood by the server. If no dependable validator is available, starting over is usually safer than guessing; an application can also expose versioned, immutable download URLs.

Representation validation and tamper detection are different jobs. Entity tags support HTTP conditional requests and cache validation. An ETag alone is not a cryptographic integrity guarantee. If the application must detect corruption or verify that the delivered file is an approved release, it needs a trusted digest or signature and a defined binding to the expected artifact: who issued it, which version it describes and how the client checks it. A range response is not, by itself, a security proof for the assembled file.

After a 206 response, what must be checked before appending?

Continuing the hypothetical example, if the server confirms version A, the resumed range begins at byte 5,242,880. The expected response is 206 Partial Content, with a Content-Range such as bytes 5242880-10485759/10485760. Its first position must equal the next byte durably recorded by the client. The last position cannot precede the first, and when the total length is known it must be greater than the last position. RFC 9110 §14.4 says recipients must not recombine content when Content-Range is invalid. Do not treat the status code alone as permission to append.

For a single-part 206, Content-Length normally describes the response body's range, not the size of the entire file. Content-Range describes where the body belongs and, when known, the representation's complete length. Compare the actual received byte count with last - first + 1, then advance the stored offset to last + 1. An overlapping range, a gap, or a different start means appending silently will duplicate or omit bytes. Stop combining and rebuild the recovery state instead.

Compare any response ETag with the validator in the saved state. A conflicting validator, final response URL or content coding means the response does not belong in the old object. Intermediaries and negotiation can change the selected representation too. If an application chooses to resume without an ETag, it should document which endpoint evaluated If-Range and under what validator assumptions. Where those assumptions cannot be established, a full download is more defensible than accepting a range that merely looks plausible.

Why should a full 200 response replace rather than append?

Return to the A/B example. After a representation change, the If-Range condition fails and the server may ignore Range, returning the complete 10 MiB version B with 200 OK. Concatenating those 10 MiB with the old 5 MiB prefix produces a 15 MiB object. Truncating the old data and writing B produces the new complete object. The apparent difference is one file-write operation; the semantic difference is whether the result represents one version.

Parse and branch before writing: a valid 206 enters the range-append path; a complete 200 enters a full-replacement path; authorization failures, redirects to a login page, server errors and unexpected content types go to error handling. They are not file bytes. This is especially relevant when an expired signed URL redirects, or when an application follows redirects automatically and then mistakes an HTML sign-in page for a successful download.

To avoid losing the only usable copy halfway through replacement, write each attempt to a separate temporary object. For a full replacement, write the entire new object, validate its length and any trusted digest or signature, and then switch the official filename where the filesystem supports the required operation. A resumed chunk can likewise be staged separately, checked against the expected range and byte count, and only then committed to the progress record. Rename behavior depends on the filesystem, cross-volume moves and crash timing. The protocol does not provide a local file transaction, so the write sequence still needs testing in the target environment.

Parallel ranges add another set of state combinations. Every worker must use the same validator, representation selection and byte coordinate system. If one chunk receives a different ETag, total length, invalid Content-Range or a complete 200 response, the whole batch should be discarded or restarted. Keeping the other chunks can still create a file made from multiple versions. Whether parallelism is worthwhile depends on the network benefit versus coordination, retry, storage locking and whole-batch restart costs. For a small file, extra range state may not be worth maintaining.

Does 416 with bytes */N mean the local file is complete?

No. RFC 9110 §14.4 defines Content-Range: bytes */N on a 416 response as the current length of the selected representation. It reports a length; it does not prove that the local temporary file contains the first N bytes of that representation. If the local offset is greater than N, the server's representation may have shrunk, the local state may be stale, or the request may have selected another variant. Silently changing the offset hides which condition occurred. Even when the local length equals N, matching lengths do not prove matching content or version.

The related article Does HTTP 416 plus the current length mean the file is done? demonstrates why equal lengths are weak evidence. For the separate question of which bytes a digest covers, see What do Content-Digest and Repr-Digest each cover?. A digest's scope does not automatically tie an old partial file to the version currently selected at a URL. Recovery still has to connect validator, ranges and whole-object verification.

Keeping the progress record in step with disk writes

Even when the remote response is handled correctly, a process crash can separate local metadata from file contents. If the client records “received through 8 MiB” before those bytes reach disk, a crash between the two writes causes the next attempt to skip bytes that do not exist. If the data is flushed first and progress is updated second, a crash can cause the same range to be replayed. Replaying is easier to make safe when writes are positioned at the exact byte offset and duplicate ranges can be detected, but it still needs an explicit policy.

One option is to stage each range, verify its length and location, then commit a recoverable progress record. Another is a small journal with operation-started, data-persisted and metadata-committed markers, so startup can replay or roll back incomplete work. The right choice depends on the storage medium and its crash-consistency guarantees. A progress record can include a stable task ID, URL or selection context, validator, byte coding strategy, confirmed ranges, temporary object path and last committed file position.

Do not write signed URLs, cookies or authorization tokens to general logs in clear text. A persistent task that can survive sign-out also needs a reauthorization path when credentials expire. The protocol does not persist these states for the application, and it cannot guarantee that a mobile device's file flush and metadata transaction commit together after power loss.

Invest in resumable state when files are large, networks are unreliable or users need pause and resume. If an object is small, cheap to fetch again, or served without a stable validator, discarding partial bytes and restarting may cost less than maintaining range and version state. Decide from redownload cost, failure consequences, validator quality, concurrency and local-storage reliability—not from a rule that every download must resume.

A test matrix for the state machine

A controlled test matrix can use fixed objects and synthetic versions, but without execution evidence it must remain a plan. First serve fixed bytes with a strong ETag such as "release-41". Let the client save one range, then resume with the same validator. Check that the server returns 206, the range begins at the expected offset, and the assembled bytes match a separately downloaded reference object. Next change the representation and ETag, then retry with the old validator. The correct branch receives a complete 200 and replaces the temporary object with the new reference. Assert the final bytes as well as the length; a status code is not a content comparison.

Have a test server ignore Range, return a misplaced Content-Range, change the total length, return 416 with bytes */N, and disconnect mid-body. Assert that incomplete or identity-mismatched data never becomes the official file. Then terminate the process between writing data and committing progress. On restart, verify that recovery can only replay a confirmed range or start again; it must not skip a missing range. Finally cover 401/403, redirects, expired download credentials, content-coding changes and exhausted disk space so that an error page or another variant cannot be saved as part of the file.

Completion has three distinct checks: whether the response matches the request, whether temporary storage covers the entire byte range, and whether the final object passes the application's content-integrity requirement. If a trusted signature or digest is required, verify how it is bound to the task and version. With only an ETag, report HTTP representation validation—do not upgrade that into a security-integrity claim. The numbers above are hypothetical and the matrix is a proposed test plan. No downloader, test server, fault injection or transfer benchmark was run for this article, so it makes no claim about compatibility, performance, integrity or production results.

When reviewing a resumable-download implementation, inspect its two write branches before its progress bar: does a valid range for the same representation append at the exact offset, and does a complete response isolate old fragments before replacement? Then inspect the order in which disk bytes and progress metadata are committed. Those boundaries determine whether a failure should resume, restart or report a version conflict.
