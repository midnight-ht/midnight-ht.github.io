Intl.PluralRules Selects Categories, Not Sentences

Plural categories are neither translations nor product empty states. Separate complete messages, zero semantics, number formatting, and runtime tests.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-26 · Estimated read 25 min
Translations
zh-CN en

Article

Intl.PluralRules returns a grammatical category such as one, few, or other for a locale, number, and set of options. It does not write the sentence, nor does it know what “no results” means in a product. Reliable count copy keeps data state, product meaning, plural selection, complete translation, and number display separate, then verifies how they work together.

The boundary is easy to miss when the mental model is “add an s for English plural.” 1 file and 2 files look like the rule itself, but they are one language’s presentation. Reusing the same string-concatenation logic elsewhere turns English grammar into a data model. Even after adopting the browser API, an application can still be wrong if it stores only noun fragments or converts an unknown loading value into zero.

What does the API return?

Intl.PluralRules(locale).select(count) returns a category identifier. See MDN’s Intl.PluralRules API documentation and ECMA-402 2027’s specification for select(). An application can use that identifier to choose the complete message for the target language. The one category does not promise that the value is exactly 1 in every language, and locales do not all have the same set of categories. Unicode CLDR’s “UTS #35 Part 3: Numbers” explains that each language defines only the categories it needs: Arabic can use zero, one, two, few, many, and other, while English defines one and other. These labels help implementers discuss grammar; they are not arithmetic constants for business logic.

A grammatical difference may not appear in the noun. CLDR’s plural-rules guide uses English “sheep”: the noun does not change, but the verb does in “1 sheep is here” and “2 sheep are here.” In some languages a later pronoun changes instead. Complete messages let translators adjust word order, verbs, and references. Concatenating {count} + noun fragments locks those choices into code. Map a category to a whole message instead of mapping it to an English suffix.

Count copy is a stateful pipeline

Imagine a “files needing attention” label above a file list. At least four inputs have different meanings: data has not arrived, the request failed, the service confirmed a count of zero, or the service returned a known count. They should not all enter a plural selector. Loading should show progress; failure should explain or offer a retry; only confirmed zero should enter the product’s empty-state design; positive values can use a count message. Otherwise, an initial 0 can briefly tell a user that no files exist before the request has completed, presenting uncertainty as fact.

Inside a count message, distinguish cardinal from ordinal. A cardinal answers “how many files?” An ordinal answers “which file?” or “which step?” English ordinal 1st, 2nd, and 3rd do not use the same selection as cardinal 1 file and 2 files. ECMA-402, the “ECMAScript 2027 Internationalization API Specification,” defines cardinal and ordinal types for Intl.PluralRules; select() returns a category. A page that shows both “3 unread items” and “step 3” needs separate message models rather than one shared suffix.

A practical implementation validates that a count is a finite business value, checks that the message table has the selected category, and inserts a formatted number into the translation. A missing translation category should trigger an explicit fallback and a development or content-validation warning. Do not silently borrow singular copy, and never let undefined reach the interface. other is a required CLDR catch-all category, but a technically available fallback is not evidence that the wording is natural, accurate, or reviewed.

const messages = {
  en: {
    zero: "No files need attention.",
    one: "{count} file needs attention.",
    other: "{count} files need attention.",
  },
};

function pendingFilesMessage(locale, count) {
  if (!Number.isFinite(count) || count < 0) {
    throw new TypeError("count must be a known, non-negative number");
  }

  if (count === 0) return messages[locale].zero;

  const numberOptions = { maximumFractionDigits: 0 };
  const rules = new Intl.PluralRules(locale, {
    type: "cardinal",
    ...numberOptions,
  });
  const category = rules.select(count);
  const template = messages[locale][category] ?? messages[locale].other;
  const formattedCount = new Intl.NumberFormat(locale, numberOptions).format(count);
  return template.replace("{count}", formattedCount);
}

In this run, the code block was executed on Node.js v24.21.0 with ICU 78.3 for English counts 0, 1, and 2; it returned “No files need attention,” “1 file needs attention,” and “2 files need attention.” This verifies the minimal example on that machine only. It is not a browser-compatibility test and does not verify translations for other locales.

This is a minimal rendering example, not a complete localization library. It contains English messages only, assumes files cannot be negative, and deliberately displays integers. Other locales need their own reviewed full messages and the same state semantics. The integer options are inappropriate for measured fractions, currency, or values whose precision carries meaning. A real UI should also distinguish invalid input and service failure rather than representing every problem as an exception.

Is the zero category the same as an empty state?

No. zero is a grammatical category that a language’s rules may return. “There are no files needing attention” is a product message the application may choose. CLDR notes that a special zero message can be useful even when a language has no separate zero category. Conversely, a locale having a zero category does not require every zero to be shown as “nothing.” The right message depends on whether the product is inviting a user to begin, reporting a statistic, or emphasizing a filter. Product semantics should determine the message; a category name cannot make that decision.

That is why the example checks for a known zero before invoking the selector. A product can choose to handle zero as an ordinary count sentence and omit that branch. If it wants a dedicated empty state, the branch should be explicit rather than depending on whether one locale happens to classify 0 as zero or one. An empty state may include a button or next step; that is already more than a noun form can express.

Number formatting and category selection need a joint check

Number selection and number formatting are separate responsibilities, but related options can affect both. MDN’s Intl.NumberFormat constructor documentation lists digit and rounding options. Intl.NumberFormat controls grouping, digit system, fraction digits, and rounding; Intl.PluralRules chooses a category for a locale. With fractional or rounded values, a message can become inconsistent if the selector interprets one precision while the display formats another. Align compatible options such as minimumFractionDigits, maximumFractionDigits, and roundingMode, then verify the target environments. That does not mean every value should be rounded first. Balances, measurements, and “about” copy have their own precision contracts; do not change the meaning of a quantity just to simplify plural selection.

CLDR’s guide specifically warns that some languages distinguish fractions by their decimal digits or visible trailing zeros. It gives examples such as 1, 1.0, and 1.00. A JavaScript Number cannot retain how many decimal places were present in the user’s original text. If the product genuinely needs that lexical precision, preserve a decimal string or fixed-point/decimal representation at parsing time and use a suitable message-formatting tool. Do not expect conversion to an ordinary Number to preserve the input scale. If scale does not affect meaning, define a numeric formatting rule so that input spelling does not accidentally become semantics.

Can pluralCategories be the translation-key checklist?

It can help test one concrete runtime configuration, but it does not certify that translations are complete. MDN’s resolvedOptions() documentation describes pluralCategories as the array of categories used by the locale; it reports the categories that may be returned for the current locale and cardinal or ordinal type. It can drive a missing-key warning or help build tests that choose values for each category. Iterating the category names and passing them to select() is meaningless: those names are outputs, not test numbers.

A local probe for this article used Node.js v24.21.0 with ICU 78.3: en exposed one, other, ru exposed one, few, many, other, and ar exposed six categories; in that environment French returned one for both 0 and 1.5. This is an observation on this machine, not a browser coverage guarantee. The rules come from internationalization data shipped with a runtime. Unicode CLDR 49 release note is dated October 22, 2026; it updates plural or ordinal rules for several languages and fixes Norwegian Nynorsk (nn) inheritance from Norwegian (no). Language rules therefore change with CLDR data. Actual behavior depends on the ICU/CLDR data in a browser or Node release. A list from a developer’s machine is not proof that every client behaves identically. Catalogue validation can use the project’s supported runtime baseline, while real-client coverage should still include target browsers and devices and record version differences.

Start verification with a product-state matrix, then a locale matrix: loading, failure, confirmed zero, ordinary integers, locale-specific boundaries, fractions if allowed, and cardinal and ordinal cases separately. For each input, inspect the selected category, the rendered full sentence, and the displayed number. For Russian, CLDR’s guide shows that 1, 2, 5, and 1.5 can select one, few, many, and other respectively. This article does not provide a complete Russian translation; the example shows why testing only 1 and 2 misses categories. Arabic’s six-category set likewise needs representative values. Determine test numbers from select() in the target runtime and repeat when fraction or rounding options change.

Test ordinals separately. In English, cardinal 2 is other, while ordinal 2 is two; this is a quick check that type: "ordinal" has not been mixed into a cardinal message. If the product supports a range such as “showing items 2–4,” do not assume the ending value’s category describes the range. MDN’s selectRange() documentation describes locale-sensitive range categories; ECMA-402 defines selectRange(); verify it with the complete range message. If the target environment lacks it, use a documented compatibility strategy rather than pretending that one endpoint determines the result.

Automated checks can cover category keys, missing templates, state branches, invalid inputs, and number-format consistency. They cannot decide whether a translation sounds natural, whether its tone is right, or whether “no results” helps more than “0 results.” Those judgments require a reviewer who knows the language and product context to inspect the complete page. This article records standards and one local runtime observation; it does not claim testing across every language, browser, or interface.

For count messages, first define numeric states and the meaning of zero; then choose a cardinal, ordinal, or range model. Ask translators for complete sentences, and add the runtime matrix, formatting options, and translation checks to the test suite. This order avoids baking a fragile rule into a shared helper such as count + (count === 1 ? "" : "s"). A constrained internal prototype for one supported language may not need more. Once copy reaches multilingual users, category selection and sentence generation should be separate responsibilities that can be verified independently.

The same design lesson applies to form-validation feedback: a technical rule can answer only the question it owns; it cannot decide what the user should see. For count copy, the API answers “which category does this locale select?” The application and translation process still have to answer “which sentence accurately describes this state?”
