A valid JWT signature does not establish the intended recipient

Signature verification answers a cryptographic question, not who should accept a token. RFC 7519, RFC 8725, and the OAuth JWT access-token profile explain audience validation and its limits.

Key takeaways

  • A valid signature does not establish that the current API is an intended recipient.
  • When one issuer serves multiple applications, audience must be checked under the recipient's policy; the OAuth JWT access-token profile has a specific resource-server check.
  • Treat the signed recipient claim as one boundary; keep token type, scope, tenant, and object authorization separate.

A JWT can have a valid signature and still be the wrong token for a service. Signature verification establishes a cryptographic relationship between the protected token contents and the verification key; it does not automatically establish that the current API is an intended recipient. A recipient must apply its own issuer, audience, and token-purpose rules. The requested resource and operation then go through authorization. Treating “the signature verifies” as “this token is usable here” collapses several distinct boundaries.

One trusted key does not make every service a recipient

Imagine a service that offers both a reporting API and a payments API. Its authorization server uses one issuer identifier and signing key to issue separate JWTs for those resources. A reporting token really was signed by the trusted authorization server, so the payments API may be able to verify it too. That check alone does not show that the token was intended for payments. If the payments endpoint checks only the signature, it can accept a credential in a context for which it was not issued. This is a hypothetical example to explain the boundary, not a report of a real attack or a claim about a particular product.

The missing decision is independent of the signature check. A key may be trusted by multiple recipients, and a token may contain plausible permission claims, while each resource still needs to ask: “Was this credential issued for me?” RFC 7519 defines aud as the JWT's intended recipients. When the claim is present, a principal that does not identify itself in the audience values must reject the token. The same specification says that aud is optional in a generic JWT and that its interpretation is generally application-specific. Therefore, merely observing an aud field does not prove that a system has a correct recipient policy.

Separate generic JWT rules from a token profile

RFC 8725's Best Current Practices addresses substitution risks created by a shared issuer: when the same issuer can issue JWTs for multiple applications, the token must contain an audience that can help determine whether it is being used by an intended party, and the receiving application must validate it. It must reject a missing audience or one not associated with that recipient. RFC 9068 defines a specific profile for OAuth 2.0 JWT access tokens. Under that profile, a resource server must check that aud contains a resource identifier it expects for itself and reject an access token that does not. The profile also requires the typ value to be at+jwt or application/at+jwt, and specifies checks for issuer, signature, and other fields.

These documents are not interchangeable “JWT magic.” RFC 7519 describes generic claim semantics; RFC 8725 explains security requirements for cross-application and cross-token use; RFC 9068 applies to OAuth JWT access tokens that follow its profile. A deployment must establish whether its service declares that profile, how its issuer assigns resource identifiers, and whether old tokens remain in circulation from the actual protocol and configuration. A token does not follow an OAuth profile just because it is a JWT.

The aud value may be a case-sensitive string or an array of strings. A recipient should match its own stable identifier according to the agreed protocol. A check such as “contains this substring” can blur the boundary through similar names, case differences, or unexpected values. The allow-list should come from trusted service configuration or registration data, not from unverified token contents that are allowed to define policy for themselves. Multiple audiences also do not mean every resource may exercise every permission in the token. The issuer expresses the authorization scope, and each recipient validates the portion relevant to itself.

Audience does not replace token type or authorization

A recipient match settles only the intended-recipient question. It does not automatically distinguish an ID token from an access token, nor does it establish that a subject may view a particular order. For cross-JWT confusion, RFC 8725 recommends mutually exclusive validation rules for different token kinds; strategies can include explicit typing, distinct required claims, different keys, or distinct audience values. RFC 9068 uses at+jwt to identify its access-token profile. A resource server still needs to apply the requirements of that profile instead of accepting any JWT with a matching audience.

Even when signature, issuer, time, type, and audience all satisfy policy, authorization remains. A scope may be meaningful only for certain audiences. Whether a user belongs to the current tenant, owns the target object, or may initiate a payment in the current business state is usually a separate decision. For example, a token for the payments API with a scope that permits initiating payments does not automatically authorize changing any account or paying another tenant's invoice. Authentication, token applicability, object authorization, and business-state validation are consecutive but different gates.

The site's article on refresh-token reuse and grant families discusses authorization relationships and the lifecycle of refresh credentials; it does not replace each resource server's access-token recipient check. The article on GitHub Actions OIDC trust for AWS shows how issuer, audience, and subject conditions can jointly constrain cloud-role trust. Both concern what one system may trust, but their protocol claims and acceptance policies cannot be copied across contexts without review.

Put rejection paths in the validation matrix

Design checks by first fixing the receiving service's expected issuer, audience, token profile, algorithm, key source, and time rules. Then list inputs that must fail. At a minimum, distinguish a correctly signed token whose audience points to another resource; a missing audience where policy requires it; an array that includes this resource versus an array naming only another; an identifier with only a case difference; invalid signature, issuer, or time; a token type that does not match the adopted profile; and a correct audience paired with insufficient scope or object permission. The first group should fail at token applicability. The last group should be rejected by authorization. The API contract determines whether an authentication failure returns 401 or 403; one status code does not substitute for evidence about which validation ran.

Changes to an audience identifier also need a careful migration plan. If a service accepts old and new identifiers at once, the broader the window, the harder it is to explain which services can still use old tokens. A transition can be scoped by issuer, resource, and expiration, with telemetry recording the rejection category, policy version, and request context. Do not log complete tokens, signing keys, or material that enables replay. Logs can help identify which rule rejected a request; they must not turn unverified claims into trusted input.

This article follows the original texts of RFC 7519 (2015), RFC 8725 (2020), and RFC 9068 (2021); the service scenario is hypothetical. No token-library configuration, resource server, or penetration test was run, so this article does not establish that an implementation is secure. For a real deployment, identify the token profile first, then test with controlled tokens that the intended resource is accepted, the wrong resource is rejected, and object permissions and business-state rejection paths are independently enforced. If the specification and a library behave differently in a particular setup, use the deployed configuration and reproducible checks as evidence.
