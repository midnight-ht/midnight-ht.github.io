A valid JWT signature does not establish the intended recipient

Validate intended issuer, audience and purpose, then authorize the requested resource separately.

Updated 2026-10-11 · Estimated read 6 min

Article

A valid JWT signature still requires checking the intended recipient, trusted issuer and permitted purpose. Signature verification relates protected content to a key; it does not alone establish whether the token belongs here. Decoding establishes even less.

One issuer can serve multiple systems

RFC 8725, published in 2020, addresses substitution and cross-purpose confusion, including audience validation where applicable and algorithm verification. These requirements do not establish that a library's defaults satisfy an application's policy. No security tests were executed here.

Imagine one identity service issuing tokens for analytics and payments. Payments accepting an analytics token merely because its signature verifies could widen its intended scope. This hypothetical scenario reports no real attack. Shared issuers and keys do not make all credentials interchangeable.

Acceptance policy belongs to the application

Define trusted issuers, expected audiences, permitted algorithms and token purposes before validating input. An unverified claim cannot become trusted policy merely by being read. Where different token kinds could meet the same endpoint, distinguish their validation rules to prevent substitution.

Audience checking is not arbitrary substring matching. Use the protocol and library's supported claim forms and reject missing or unsuitable claims as required. Implementation needs the actual library and protocol documentation rather than universal copyable code. Include applicable time conditions, key rotation and subject checks instead of trusting every field after a valid signature.

Authentication still leaves authorization

An accepted credential does not authorize every resource operation. Check permissions and object relationships; an ordinary user's valid token should not expose someone else's data. Role mapping, revocation and extra conditions for sensitive actions require their own contract.

Test rejection while limiting disclosure. Appropriate failure categories can aid diagnosis, but complete tokens and secrets do not belong in logs. User feedback need not reveal internal key selection. Observability should not become another credential exposure path.

A proposed matrix includes correct signatures with wrong audiences or purposes, disallowed algorithms, expired tokens and valid tokens accessing forbidden objects. These checks have not been executed. As with server-side form acceptance, define permission before examining requests. Inspect one real endpoint's checks beyond the signature.
