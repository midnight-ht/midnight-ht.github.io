Password-hash upgrades need a migration path, not just a new name

Plan legacy verification, authenticated upgrades, dormant-account recovery and rollback compatibility together.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-11 · Estimated read 6 min
Translations
zh-CN en

Article

Upgrading password hashes requires legacy verification, new-parameter writes and a policy for dormant accounts. Changing an algorithm name alone can lock out existing users or leave weak records indefinitely. The migration needs inspectable rules grounded in security and actual capacity.

This is not re-encrypting a file

The OWASP password-storage guide recommends password-specific hashing and discusses upgrading work factors after authentication, with reset policies for accounts that never return. Costs require evaluation on the actual servers. Current guidance does not make any parameter set universally suitable for all machines.

An existing hash is not a recoverable plaintext password store. Retain the metadata needed to identify legacy algorithms and parameters, verify the submitted password appropriately, and only after successful authentication generate and persist a record under the current policy. No account migration was executed here; no completion or latency result is claimed.

Bound both verification paths

Supporting only the new format rejects correct legacy passwords; indefinitely keeping the legacy path defeats upgrading. Identify formats clearly and guard new writes against concurrent password changes. Confirm migration through persistence, not merely through computing a new hash.

Failed authentication must not rewrite a record. Resource shortages must not silently weaken parameters. Assess rate limiting and capacity protection against expensive verification floods. Threats and measured load determine policy; this article supplies no untested universal or optimal parameter set.

Dormant accounts remain a decision

Login-time migration leaves accounts that never authenticate. Decide whether to retain, restrict or require recovery, providing a safe user path. Observe remaining legacy formats without exposing passwords or hashes. Account value and recovery cost matter; “next login” is not a complete plan.

Backups and rollback can restore old records or remove support for new ones. Verify mixed deployment and restoration paths rather than a new-version-only case. Record adequate workflow state without sensitive authentication material.

Proposed acceptance cases cover successful legacy upgrades, no rewrite for wrong passwords, concurrent changes, rollback compatibility and dormant-account recovery. None were executed here. The JWT acceptance article concerns another credential boundary. Inventory formats and recovery paths first, then deploy new parameters as one part of a verifiable migration.
