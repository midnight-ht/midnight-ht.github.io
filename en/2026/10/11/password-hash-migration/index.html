Password-hash upgrades are constrained by what the old hash cannot reveal

Compare login-time rehashing, dormant-account recovery, weak legacy hashes, concurrent password changes, and rollback as one verifiable migration plan.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-26 · Estimated read 28 min
Translations
zh-CN en

Article

Key takeaways

  • A one-way legacy verifier does not contain the plaintext needed for direct bulk conversion; formats must remain identifiable and verifiable.
  • Work-factor increases, weak MD5/SHA-1 exposure, and dormant-account recovery are different decisions; login-time rehash is not a universal answer.
  • Guard migration writes against concurrent changes, and verify capacity, rollback, and recovery in the target environment; no migration or benchmark was run here.

A server that stores only a one-way password verifier does not have enough information to convert the entire old table directly to a new password-hashing scheme. Ordinary gradual migration must wait until a user presents the correct password again. Dormant accounts need a separate recovery decision. If the old verifier is already considered dangerously weak, waiting for another login may be insufficient. A password-hash migration is therefore a compatibility change across verification, persistence, concurrency, recovery, and rollback—not a database field rename.

Why the old verifier cannot be converted in bulk

A password verifier normally consists of a scheme, salt, work parameters, and output. The salt and parameters let the verifier recompute a candidate password under the old rules and compare the result. The salt is not a secret, and the stored record should not reveal the plaintext password. NIST SP 800-63B-4 requires salted password hashing with a suitable scheme and recommends storing a reference to the scheme and cost factor so verifiers can migrate algorithms and work factors. “Support migration” does not mean recovering a password from its hash.

Suppose a database contains H_old(password, salt, cost). From that output alone, the application does not know the original input, so it cannot compute H_new(password, new_salt, new_cost). Feeding the old output to the new algorithm produces H_new(H_old(password)); it is not a new verifier derived directly from the user's password. This determines the ordinary migration window: after the legacy verifier accepts a submitted password, the server briefly has the correct input and can create a direct verifier under the new policy.

The record format must be self-describing. Store an explicit format version or use a standard encoding that carries the scheme and parameters. Do not infer the algorithm from output length alone. Formats can share lengths, and historical implementation or default-parameter changes can make a verifier choose the wrong path. Storing the salt, scheme identifier, and cost parameters answers “how do I verify this record later?” It is not a way to hide the algorithm name. Passwords, full verifier strings, peppers, and reusable credentials do not belong in ordinary logs.

Login-time rehashing is a conditional state transition

A successful login is often the lowest-friction chance to upgrade a record, but the operation should not be implemented as “login succeeded, so overwrite unconditionally.” At least three conditions matter: the legacy format actually verified; the credential version is still the one used for that verification; and the new verifier has been persisted and can be read by subsequent authentication. Computing a new hash, enqueueing a background job, or returning success from the login endpoint does not prove that migration completed.

Consider a hypothetical record with credential_version=12. A login request verifies the submitted password against version 12. At the same time, the user changes the password from another device and the record becomes version 13. If the first request does not check the version, it could overwrite the new password with a rehash of the old one. A conditional update can write the new verifier and version only if the database is still at version 12. If that condition fails, the migration must not overwrite the current credential; the normal password-change flow determines the request outcome. This is a design example, not a migration run by this site.

Failure paths matter too. A wrong password must never trigger a rehash write. If new-format computation or the database update fails, the system must not report the record as migrated. Depending on an explicit policy, the current authentication might succeed while the old verifier remains, or the user might be asked to retry. Either choice must account for the fact that the next login could still use the legacy path. If a background job runs after the login response, it needs observable failure state, idempotent conditions, and a compatibility window. Otherwise the dashboard may show successful logins while old records never decline.

Separate a work-factor increase from a weak-scheme response

Raising the cost of a still-usable scheme is not the same incident as moving away from a fast general-purpose digest such as MD5 or SHA-1. OWASP's Password Storage Cheat Sheet recommends rehashing with new parameters after successful authentication. It also discusses older MD5 or SHA-1 verifiers as a different case: defenders should expire the current password and require a reset so the weaker verifier is no longer retained. Choose a path based on the old implementation, exposure evidence, password rules, and recovery capability. “It will migrate at next login” is not a general remedy for credentials known to be exposed.

For an account whose scheme remains usable but whose cost parameters are low, gradual rehashing can avoid an immediate forced password change for everyone. Dormant accounts need a stated cutoff policy: preserve the legacy verifier until the next login, require a reset after a deadline, or handle groups according to risk. Forced resets create support costs, user friction, and opportunities for phishing messages that imitate the reset flow. Delivery channels, reset-token lifetime, and session handling are part of the migration. Silently deleting a verifier is not a complete migration unless the user has a viable recovery path.

OWASP also describes a transitional option: use the legacy verifier as input to a new password-hashing algorithm, for example wrapping MD5(password) with a modern slow hash. This changes the online verification path without knowing the plaintext, but it does not turn the old verifier into a strong record derived directly from the original password. If the old verifier leaked, an attacker can still guess against that old value. If used, the wrapped form should be clearly marked as temporary and limited in scope, then replaced by a direct verifier the next time the user genuinely authenticates. It is not a risk-free bulk upgrade and cannot repair an exposure that has already occurred.

Budget capacity before increasing the cost

A slow password hash makes offline guessing more expensive, but it also consumes more resources during legitimate authentication. NIST SP 800-63B-4 says the cost factor should be as high as practical without harming verifier performance and should increase as computing capability improves. OWASP's current guide lists recommendations and minimum configurations for Argon2id, scrypt, bcrypt, and PBKDF2, while emphasizing measurement on target servers. RFC 9106 includes Argon2id recommendations, including an option for memory-constrained environments; those values are reference profiles, not evidence that a particular production fleet can sustain the associated concurrency.

Before rollout, put per-verification CPU time and memory, peak authentication volume, concurrent logins, container memory limits, and autoscaling behavior on the same capacity worksheet. For example, if each verification requests tens of MiB, one request may look harmless while concurrent requests accumulate. A low per-request latency alone does not establish acceptable memory peaks or queueing delay. Measure successful and failed verification paths on hardware and limits close to deployment. Include login bursts, rate limiting, resource exhaustion, autoscaling delay, and node restarts. No parameter was benchmarked for this article, so it does not claim to provide an optimal setting for this site or any reader's system.

The policy should also allow a safe rollback. That does not mean reverting to a weaker scheme and making newer records unreadable. A more useful compatibility window is to let the new application read both old and new formats while only writing the new one. Once all instances and recovery tools can read the new format, the old format can be rejected gradually. If a parameter choice is wrong, pause or slow new upgrades and adjust the verifier instead of rewriting already-created new records into the old scheme. The rollback plan must account for restored database backups, application compatibility, and monitoring the remaining legacy-format population.

Divide the migration into reviewable steps

Inventory record formats before changing an algorithm constant. For each format, record its source version, scheme, readable parameters, salt encoding, password-character handling, any pepper dependency, and whether current code can still verify it. Do not guess at an unknown format's defaults; recover its semantics from known historical code, backups, or test vectors. If older services normalized Unicode, truncated, or encoded passwords differently, compatibility verification must preserve those rules or users may be rejected despite entering the password they originally chose.

Next, deploy a verifier that can read the compatible formats while making all new or changed credentials use the new format. During a rolling upgrade, confirm that old and new application instances can handle every format that might appear. If older instances cannot read the new format, first upgrade all nodes or stage writes so the new format is not introduced too early. Then apply conditional updates after successful legacy verification and track format counts, upgrade failures, and concurrency conflicts. Metrics should record format categories and outcomes, not passwords or full verifier strings. Finally, define the dormant-account policy and the conditions for disabling old formats. Observe real data rather than declaring success from one deployment log.

Acceptance is more than “new users can log in.” Cover a correct legacy password becoming verifiable under the new format; a wrong password leaving the record unchanged; a failed write not being reported as complete; concurrent password change resisting overwrite; an unknown format entering controlled recovery; a restored old backup remaining verifiable; pepper revocation following the reset path; and the legacy-format retirement condition being independently auditable. These are proposed checks, not tests executed for this article. A real rollout should bind results to the code version and data-migration state.

Which accounts should not wait for another login?

If monitoring indicates a password-database leak, the old scheme is cheap to guess, or a pepper has been exposed, gradual login-time rehashing may leave risk in storage. First assess the incident evidence: affected records and time window, whether an attacker could obtain verifiers and salts, suspicious logins, and whether sessions or reset credentials need revocation. Then determine the reset scope using evidence and the account recovery mechanisms available. Do not force every account through one path by default, but do not silently keep known-vulnerable verifiers merely to avoid support work.

When the only issue is a work factor that should increase, with no evidence of exposure or scheme retirement, an immediate password change for every user may not be the only reasonable choice. Risk, user experience, support capacity, and dormant-account share should be explicit inputs. Format counts can answer “how many legacy records remain?” and login or recovery completion rates can show migration friction. Those numbers do not by themselves prove account security and are not substitutes for password strength or attacker success rates.

A common reader question is whether a dormant user's record can be migrated in the background. Without the original password or an independently usable recovery credential, a system that stores only a one-way verifier cannot directly create a new verifier derived from the original password. The choices are to require a reset or to wrap the old verifier as temporary input while accepting its residual risk. Keep “the new record uses a stronger outer scheme” distinct from “the old secret was never exposed.” If an account is already considered affected, follow the incident-response policy rather than waiting for a natural login.

Before implementation, verify three things: current production and recovery code can identify every historical record; conditional writes protect new credentials during concurrent password changes; and the target environment can handle the new cost at expected concurrency. Without evidence for those, the migration is still a design proposal. See session boundaries after a password reset and enumeration and timing in password reset flows for the separate problems of existing sessions and information leakage in recovery flows. Neither replaces migration of the stored verifier format.

Sources and limits

NIST SP 800-63B-4 §3.1.1.2 requires centrally verified passwords to be stored as salted hashes using a suitable scheme and recommends retaining scheme and cost-factor references for migration. It does not say to mechanically copy one parameter set from this article. The OWASP Password Storage Cheat Sheet sections on work factors, upgrading, and legacy hashes discuss rehashing after successful authentication, dormant accounts, old MD5/SHA-1 verifiers, and the tradeoffs of transitional wrapping; this living guide was checked on 2026-11-26. RFC 9106 §4 gives an Argon2 parameter-selection procedure and reference settings. It is an IRTF Informational RFC and instructs implementers to select memory and time they can afford, then measure. It is neither a configuration tutorial for a specific language library nor a record of this site's runtime behavior.
