Why Readable HTTP Errors Still Leave Clients Unable to Act

Readable error text is not a stable client contract. RFC 9457 separates problem identity, occurrence detail, and HTTP status; learn when a client can correct, wait, stop, or fall back safely.

Article

A readable sentence does not give a client a stable basis for deciding what to do. RFC 9457 uses type to identify a problem class and detail to explain one occurrence; clients should make decisions from the type and defined extensions, not parse text that can be localized or edited. Serializing an error in a standard JSON shape solves how to express it. The API contract still has to say whether the client should correct input, wait, stop, or show a generic failure.

Separate the HTTP status, problem class, and occurrence

Published in July 2023, RFC 9457 is an IETF Standards Track document that obsoletes RFC 7807. It defines JSON application/problem+json and an equivalent XML representation so an API can provide more detail than a general HTTP status code. It can be used with any status code, though it fits most naturally with 4xx and 5xx responses. If the response is already a representation of a resource and the application has a suitable domain format, that format may be preferable. The RFC does not require every error to be wrapped in Problem Details.

The members of a Problem Details object carry different kinds of information. type is the primary identifier of the problem type; when absent, it defaults to about:blank. A stable absolute URI under the API owner's control can help clients and developers identify its semantics over time. The RFC encourages a type URI to resolve to human-readable documentation where practical, but a consumer should not automatically fetch every address found in a response; a developer-oriented diagnostic tool may offer controlled lookup. A per-occurrence random identifier should not be put in type, or every occurrence would look like a new problem type.

title is a short human-readable summary of the type and should not vary from one occurrence to another except for localization. detail explains this occurrence and ought to help the client correct the problem rather than expose debugging information. The specification says consumers should not parse detail: human prose is not a dependable data contract. instance identifies one occurrence. It may be opaque to the client; it is not automatically a public diagnostics page or an authorization credential.

The body status member is also easy to misuse. It records the HTTP status generated by the origin server for this occurrence, primarily as a reference when the problem object is stored without HTTP metadata. If a generator includes it, the value must match the actual HTTP response. A proxy, cache, or gateway may change the status the client ultimately receives, so generic HTTP semantics still come from the received response; the body member may help explain a change during transport. A well-formed JSON object cannot fix a contradiction between the status line and its body.

Follow one form error through a client decision

The following is a fictional API design using the reserved .test domain. No request or product was executed. Suppose an organization-registration form contains an invalid code and the service returns HTTP 422 with application/problem+json:

{
  "type": "https://api.example.test/problems/invalid-organization-code",
  "title": "Invalid organization code",
  "status": 422,
  "detail": "The organization code must contain 8 uppercase letters or digits.",
  "instance": "https://api.example.test/problem-occurrences/req-7f31",
  "errors": [
    { "pointer": "/organizationCode", "code": "invalid_format" }
  ]
}

Here type identifies a stable problem class; detail explains this submission; instance associates the occurrence; and errors is an application-defined extension, not a member required by RFC 9457. The application must define the extension's shape, compatibility rules, and permission boundary. A client could branch on the stable type, use errors.pointer to mark a form field, and display detail to the user. If the interface instead matches the sentence “The organization code must contain…”, changing the language, wording, or screen-reader copy may break its machine logic.

Choosing 422 in this sample is part of the hypothetical API contract, not a requirement of Problem Details. Section 15.5.21 of RFC 9110 defines it for content whose type and syntax the server understands but whose instructions it cannot process. Mapping an invalid organization-code format to that status is a possible application design, not the only status code for every field error.

Condition actually observed by the client A possible next action What must not be assumed
Known field-validation type with a field pointer Mark the field and allow correction before resubmission This is not permission to replay the same request blindly
Actual status is 429 and the server sends Retry-After Wait according to the contract, then retry Do not extract a delay from detail prose
Unknown type or extension Show a generic failure and preserve a diagnostic identifier Do not treat it as success or retry forever
403 means a general lack of write permission Explain the denial or offer a controlled request path Do not reveal whether a protected object exists or its attributes

This table is editorial API-review guidance, not a set of business actions mandated by the RFC. The HTTP status provides general semantics; the type and extensions may add domain distinctions; the interface maps known conditions to actions a user can understand. For about:blank, the RFC recommends that title use the corresponding HTTP status phrase. The type adds no semantics beyond the status, so a team need not invent a category merely to standardize the format.

Consider a hypothetical intermediary failure: the origin generates HTTP 422 with status: 422 for a field error, but a gateway changes the status received by the client to 502 and leaves the body untouched. If the interface reads only the body, it may tell the user to correct input; monitoring that reads only the received status may classify a gateway failure. The body member is advisory, and generic HTTP software continues to use the actual status. In this hypothetical case, investigation should preserve the status received by the client, the problem type, instance, and a controlled correlation identifier rather than silently overwriting the conflict with one “correct” value. Which layer normalizes the response, and whether the client presents a generic gateway error, depend on the real deployment contract; the RFC does not prescribe one rule for every proxy.

Stable identity does not mean every field is stable

A problem-type URI is part of the contract. If a team publishes an unresolvable temporary identifier and later wants developer tools to retrieve documentation, replacing the URI changes the type's identity; older clients may treat it as unknown. At design time, choose a type URI the team can maintain, and document a short title, applicable HTTP status, meaning, and resolution guidance. The documentation may evolve, but if the meaning changes enough to affect client action, design explicit compatibility or a new type instead of silently reusing the old identity.

The response's title can be localized through Accept-Language; the client may still receive a default language. Type identity remains language-independent, while detail can explain the particular occurrence in the request's language. Machine fields such as an extension's code or pointer should keep stable types and constraints. Consumers conforming to the RFC must ignore extensions they do not recognize, allowing a service to add context without breaking older clients.

Extensibility is not permission to put internals in a public response. The security section says to vet both problem-type definitions and generated details carefully to avoid exposing information useful for attacks or privacy violations. It specifically warns against exposing implementation details such as stack dumps through occurrence links. An instance or controlled correlation identifier can support investigation, with access to restricted logs reserved for authorized tools. Do not send SQL, filesystem paths, secret fragments, other users' data, or a full exception object to an untrusted caller. The same principle applies to sensitive logging boundaries: correlation information should be useful without making all evidence public.

Format migration also means old and new clients may coexist. If an older client reads a legacy error body while a newer one understands type and extensions, the service needs a clear content-negotiation policy, a period for preserving the old format, and consistent behavior across versions. Merely changing a serializer may leave new fields ignored or confuse proxy monitoring. Observe business errors separately from Problem Details parsing failures and unknown client types: the first means the request was rejected or invalid; the others indicate a protocol-consumption problem. If error responses are replayed across services or retained in logs, the same data-retention and permission rules apply.

Verify the action with tests that could falsify the design

No API or test environment was run for this article. A proposed check set is: for a known field-error type, confirm the client uses pointer rather than detail wording to locate the field; change title and detail to another locale and verify the machine action stays the same; add an unknown extension for an old client and verify it ignores the member; return an unknown type and verify the interface shows a comprehensible fallback without success messaging or an automatic retry loop. Then pass a response through a proxy or cache and check whether the client preserves the actual HTTP status and records a mismatch with the Problem Details status member.

The security path needs counterexamples too. Request details and occurrence correlation for a resource the caller cannot access and check that the response does not reveal its existence or personal data. Trigger a failure containing internal exception details and verify the public detail does not expose a stack, host path, or secret. Check the stability of the type URI documentation so its explanation is not removed by temporary publishing or deployment cleanup. These are proposed acceptance checks, not executed results.

During review, ask API, frontend, and operations owners three separate questions: which stable field drives the client's branch; which readable explanation helps the user correct the problem; and how can support trace one occurrence through a controlled identifier? If all three point to the same natural-language sentence, the format may look friendly while the interface still cannot act safely. If a status code already states a general denial, keep the response simple; define a type and extension only where a stable domain distinction is needed. Problem Details is a shared representation convention, not a substitute for retry budgets, idempotency, or object authorization; see business idempotency and object-level authorization for those separate boundaries.

Source: RFC 9457: Problem Details for HTTP APIs, especially Sections 1, 3, 4, 5 and the publication metadata. Normative claims, editorial API-review guidance, hypothetical examples, and unexecuted tests are kept distinct. This article does not claim that any server framework or client library implements these behaviors automatically.
