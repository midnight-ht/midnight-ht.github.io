OIDC removes stored cloud keys, not the need for narrow trust

Narrow workflow trust and cloud roles, accounting for repository subject-format changes and approval paths.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-11 · Estimated read 6 min
Translations
zh-CN en

Article

GitHub Actions OIDC still needs limits on which workflow identities can obtain which cloud permissions. Short-lived credentials reduce stored long-lived keys, but broad trust or role permissions can grant unintended deployment capability.

Exchange and authorization are separate

The GitHub OIDC documentation describes a cloud provider validating claims before issuing short-lived access. Trust permits specific workflows to request access for a role; cloud policy determines permitted operations. No role or workflow was configured here, and this article does not claim the site uses this authentication path.

The documentation also states that repositories created after July 15, 2026 use an immutable default subject format containing owner and repository IDs, excluding GitHub Enterprise Server. Old example string conditions may therefore fail to match. Inspect the actual repository’s format and relevant reference rather than broadening acceptance to arbitrary subjects.

Follow control over workflow inputs

Imagine a production role trusting a broad organization condition. Multiple repositories or execution paths could fall within its exchange scope. This hypothetical example has no real cloud-account data. Examine how repository, environment and workflow governance enter trust. Providers support different condition keys and matching behavior; one provider’s configuration is not universal.

Include who can modify release workflows, which environments need approval and which triggers can reach sensitive steps. A short-lived token does not assess whether code changes were accepted by the team. Evaluate third-party actions and execution environments participating after access is granted.

Limit role capabilities too

Permission to exchange identity does not justify all cloud operations. Restrict actions and resources to the actual deployment, possibly separating build, preview and production roles. Additional roles cost maintenance but clarify misuse impact. Removing long-lived secrets does not remove least-privilege review.

Proposed checks cover the intended workflow, rejection of other repositories or environments, mismatched claim formats and denial of operations outside role scope. Preserve adequate execution identity and outcomes without storing raw tokens. None of these checks were executed here.

Authentication success also does not identify the deployed artifact. See artifact identity. For one production role, list allowed identities and actions, then compare actual claims, approval paths and deployment receipts. That establishes which risks short-lived credentials actually reduce.
