With GitHub Actions OIDC, whom should an AWS production role trust?

After GitHub Actions exchanges OIDC for temporary AWS credentials, teams still need to constrain token requests, role trust claims, and role permissions. This guide explains subject-format changes, Environment branch conditions, and denial paths.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-26 · Estimated read 23 min
Translations

Article

Key takeaways

  • OIDC replaces stored long-lived access keys with short-lived credentials requested by a workflow, but it does not decide whether that workflow is trusted or narrow the AWS role's permitted operations.
  • An AWS trust policy should constrain the expected audience and subject. A GitHub Environment changes the subject context; a branch restriction may need to check `ref` separately.
  • New GitHub repositories created after July 15, 2026 default to immutable subjects containing owner and repository IDs. Older repositories keep the prior format unless they opt in; renames and transfers also need review.
  • A sound verification plan covers the intended job assuming the role, other repositories or environments being denied, excess role operations being denied, and logs avoiding raw tokens.

OIDC answers “how can a workflow obtain short-lived credentials?” It does not answer “which workflows should be trusted?” When GitHub Actions connects to AWS, review three separate boundaries: whether a job may request a GitHub ID token, which identity an AWS IAM trust policy allows to assume a role, and which resources that role can operate on after receiving credentials. Removing a long-lived key changes how credentials are obtained and how long they last. If either of the other two boundaries remains broad, production access can still reach an unintended execution path.

Three permission layers are not one setting

Start with the requesting job. A workflow needs to declare id-token: write so GitHub will let that job request a JWT from its OIDC provider. This permission concerns requesting a token. It does not grant permission to write to an AWS S3 bucket, change IAM, or deploy production resources. Under GitHub’s AWS setup guide, an authentication action obtains the JWT and presents it to AWS STS through AssumeRoleWithWebIdentity. AWS validates the issuer, audience, and role trust conditions before returning temporary role credentials. Do not conflate these steps just because the YAML contains the word write.

The second layer is the role trust policy. It answers which external identity may assume the role. AWS’s official role-trust example checks at least token.actions.githubusercontent.com:aud and token.actions.githubusercontent.com:sub. The default audience is usually sts.amazonaws.com, although the actual value also depends on the AWS partition and authentication action configuration. The subject identifies a repository and execution context. AWS IAM Access Analyzer explicitly warns that an unconstrained wildcard in sub can bring GitHub Actions from organizations or repositories outside your control into the role-assumption scope. Replacing a stored key with a broad identity entrance trades away some of the security benefit.

The third layer is the AWS permission attached to the role. Passing the trust check only means the identity can obtain temporary credentials for that role; it does not make the role read-only or restrict it to one bucket. The role’s identity policies, resource policies, and any session restrictions determine what those credentials can actually do. Imagine a production publishing role that can be assumed only by one fixed repository’s production job but still has administrator permissions across the account. The identity entrance is narrower, yet the impact of misuse or a compromised workflow remains large. Conversely, a role limited to uploading specific static assets may bound mistakes to a smaller resource area, even if more than one controlled job can assume it. Review trust and permissions separately.

The subject must match the real workflow context

Many older examples use a subject like repo:ORG/REPO:ref:refs/heads/main. It is not a fixed string for every GitHub Actions workflow. GitHub’s OIDC reference says that if a job runs through a GitHub Environment, the default sub contains environment:NAME rather than ending with branch context. AWS guidance says that when the subject does not contain the branch—for example, when it names an Environment—add a separate condition on token.actions.githubusercontent.com:ref if the branch must also be constrained. Copying an old branch-form subject into an Environment-based job commonly makes the condition fail and STS deny role assumption. Changing sub to repo:ORG/REPO:* just to “fix login” may then give all branches, tags, or environments the same entrance.

Instead of guessing strings, start with an identity matrix. Suppose a preview job may assume a preview role only from the preview branch, while a production job must use a protected Environment named production and may be assumed only from the protected default branch. This is a hypothetical design for explanation, not an actual account or AWS configuration. Record the repository, ref, Environment, audience, role ARN, and role resource permissions separately. Then compare the actual execution context with the default subject formats in GitHub’s documentation and check each AWS policy key and value. GitHub documents that colons within context values are encoded. Colons in Environment names can also be a source of mismatches. The policy should express the intended path precisely; do not add * incrementally until a failed login succeeds.

Check the repository-specific subject change in 2026

GitHub’s current OpenID Connect reference says that repositories created after July 15, 2026 default to an immutable subject format containing owner and repository IDs, such as repo:octo-org@123456/octo-repo@456789:ref:refs/heads/main. Repositories created earlier retain the old format by default unless the organization or repository opts in to immutable subjects. Repository renames or transfers after that date also move to the immutable format. GitHub Enterprise Server is outside this default-format rollout. GitHub announced the change on April 23, 2026 and updated the ID separator example on June 10. Review the current reference and the actual repository token rather than copying the hyphen format from an earlier article.

This change affects name stability, but it does not choose an authorization boundary for the team. Immutable IDs reduce the risk that an old name-based condition might match a different repository after a rename or after a released name is claimed again. But a policy that restricts only the organization ID while allowing every repository in that organization to assume a production role may still be too broad. Conversely, after a repository rename, continuing to use the old subject can block a legitimate job. A safer repair sequence is to check repository creation date, whether a custom format is enabled, whether the repository was renamed or transferred, and the actual token claims; then update trust conditions and denial tests. Do not widen the pattern first and hope an audit will find the excess access later.

There is another boundary to record in the design: GitHub's AWS setup guide says custom OIDC claims are not supported in AWS, but that does not mean IAM can check only aud and sub. AWS's condition-context documentation lists mapped standard GitHub Actions claims, including repository_id, ref, environment, and job_workflow_ref, which can be used to constrain a role. Distinguish using a standard claim issued by GitHub as an IAM condition from changing the composition of the token's sub or depending on an arbitrary custom claim; these are not the same operation. Check the current AWS mapping and values, and confirm the subject format GitHub actually issues before selecting a provider-supported restriction. If the goal is a protected Environment, verify that environment protection rules are actually configured. Neither a generic GitHub reference template nor a single sentence about custom claims replaces checking both sides.

Design denied paths alongside the allowed path

A reviewable change records more than the job that deployed successfully. List the intended identity and its neighboring identities that should be denied. For example, the target production workflow may assume a role with the correct repository, default branch, Production Environment, and audience. The same repository on a feature branch, another repository with a similarly named workflow, a preview Environment, the wrong audience, and a legacy subject that no longer matches should all be denied. If production relies on human approval, confirm that the target Environment actually has the required reviewers configured and that the job does not run until its protection rules pass; the presence of environment: in YAML alone does not prove that an approval gate exists. Anyone who can edit release workflows, Environment protection rules, or cloud trust policies can alter this authorization chain; include those control paths in code review.

After successful assumption, verify the role’s boundary too. Separate preview and production roles add IAM objects and maintenance, but they can prevent preview jobs from overwriting production. Whether to split roles depends on resource boundaries, release frequency, and potential impact. You can run AWS IAM Access Analyzer checks and controlled allow/deny cases in a non-production account. A static JSON review alone does not prove that GitHub issues the claim you assumed. One successful role assumption does not prove that excess operations are denied. Preserve separate evidence for run identity, evaluated policy, STS result, and least-privilege operation checks. The AWS credentials action documentation also presents trust conditions and role permissions as separate configuration steps.

Logs are part of the verification boundary. Do not write an unredacted JWT, OIDC response, or short-lived secret to build logs. Record correlation data such as run ID, repository and ref, target role identifier, and a summarized denial reason, while following the cloud account’s sensitive-data rules. A raw token may be valid for a short period, but it can still be replayed or misused during that window. Short-lived credentials can reduce long-term credential storage and rotation work and shorten an exposure window. They do not guarantee that workflow scripts, third-party actions, runners, or cloud policies are safe. Pinning actions to full commit hashes and assessing hosted versus self-hosted runners are supply-chain and execution-environment decisions that OIDC does not replace.

Finish with a repeatable verification table

Before migration, write one verification table per role with four columns: expected token context, trust condition, operations allowed to the role, and neighboring contexts that must be denied. Include at least the intended branch and Environment path, the wrong audience, a non-target repository, the wrong branch, missing Environment approval, and a resource operation that the role policy must reject. Test first in a low-risk account and then migrate production identities gradually. If an old key remains as a fallback, give it its own expiry, disablement, and revocation checks rather than keeping two equivalent entrances indefinitely. Exact keys and formats depend on GitHub repository state, the AWS partition, workflow context, and role design; a table template cannot replace inspecting the real claims.

This article did not configure AWS IAM, invoke GitHub Actions, call STS, or run a real cloud allow/deny test. The production and preview paths above are explicitly hypothetical. Verifiable facts come from current GitHub and AWS documentation: inspect the repository’s sub format, check the Environment and ref conditions, and validate the policy in the target account with analysis and controlled tests. If identity exchange succeeds but an artifact could still be replaced, the release path also needs to identify the deployed object and its digest; pair this review with build artifact identity verification. OIDC’s value is not changing a key into a switch that needs no review. It is making trust around a specific workflow run expressible, restrictable, and verifiable.
