HTTP 202 Acknowledges Processing, Not a Completed Business Result

HTTP 202 acknowledges acceptance for processing. An async API must also define durable acceptance, terminal-state retrieval, result authorization, and recovery from uncertainty.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-26 · Estimated read 22 min

Article

HTTP 202 says the server accepted a request for processing; it does not say processing is complete or guarantee the request will eventually be acted upon. A page can say “accepted” or “processing.” It should report a business result only after receiving evidence of an application-defined terminal state. The distinction sounds like status-code trivia, but it affects when a server may respond, when a client may retry, whether a user can retrieve a result, and who can still see a job after permissions change.

What HTTP confirms—and where that guarantee ends

Section 15.3.3 of RFC 9110 defines 202 Accepted as a request accepted for processing while processing remains incomplete. The request might eventually be acted upon, or it might be disallowed when processing actually takes place. The standard also says HTTP has no facility for resending the original request's status code after an asynchronous operation completes. It recommends that a 202 response describe the current status and point to or embed a status monitor where a user can see progress or an estimate. RFC 9110 was published in June 2022 as an HTTP Semantics standard; it is not an implementation promise from a particular queue product.

“Success” should therefore be split into facts that can be proved separately. First, the network endpoint returned 202. Second, did the application persist the job intent? Third, did background processing start? Fourth, did the business operation succeed, fail, or get cancelled? Fifth, can the current user still access the result? Sixth, was a notification delivered or seen? At the protocol layer, this response states only acceptance for processing. The remaining facts require application state, storage, and result interfaces.

Writing these boundaries into interface copy prevents the server and product text from promising different things:

Server-side fact observed What the interface may say What it cannot claim yet
Synchronous validation completed and the endpoint returned 202 The request was accepted for processing The business outcome succeeded
Job intent is durable and a status resource is queryable Submitted, with a status link The output file is ready
The application recorded terminal success, the result is retrievable, and current authorization passes The result is ready or available Unconditional, permanent availability

The last row still depends on retention, revocation, and deletion rules; “success” is not a reason to skip authorization. This table is an API-design judgment. RFC 9110 defines only the protocol-level acceptance semantics.

A job identifier is a locator, not proof that a job was durably stored and not an authorization credential. If a service creates an in-memory object and returns 202 before writing the job to a durable queue, a process crash can leave the client with a receipt for work that no longer exists. If acceptance promises “the job is persisted and can be recovered,” the server must first create a recoverable record or use a design that handles partial failure between recording and queue delivery. That usually brings up the database/message-system dual-write problem. Whether to use a transactional outbox, a polled work table, or another design depends on the actual stack; this article does not implement one.

A document-generation job makes the boundary visible

The following is a hypothetical scenario, not a real project or an executed queue. A user submits a request to generate a document. The service validates input and permissions, creates a job record, and a background worker later reads it. The acceptance response could mean: “synchronous validation passed, the job intent is durably recorded, and a queryable job identifier exists.” That promise is stronger than “the request reached a web process,” but it still does not mean the file has been generated.

The record needs to explain a lifecycle, not just display a percentage. For example, queued may mean waiting for execution, running may mean a worker claimed the job, succeeded may mean the result resource has been created and associated with the job, failed may mean a terminal error has been recorded, and cancelled may mean cancellation was confirmed. These are one possible application model, not RFC-defined values. Each transition needs a real trigger. Can a worker claim a message twice? If it crashes after writing a file but before recording success, will a retry create a second result? Does retry after failure resume the same job or create a new one? Without answers, a status field exists but cannot serve as business evidence.

Walk one interruption through: a worker claims the job, writes a file, then crashes before updating the job state. The client still sees running. A retrying worker that writes a different file may create a duplicate result; changing the old record to succeeded without finding a complete file publishes a broken outcome. One design to consider is a stable output key derived from the job and a check that the object exists and is complete before publishing succeeded; a retry can reuse or verify the same object. This is a design illustration, not a guarantee from a particular storage system, and it was not executed. It shows why a terminal state should bind to a retrievable result, not merely record that a worker once started.

Separating status from result is also essential. Succeeded might mean the application registered a result identifier, but the download endpoint must still check the caller's current identity and object permissions. If the user was authorized when submitting but lost permission while the job was running, access to the result should follow the product's security policy and be checked again. An identifier that is difficult to guess can reduce accidental enumeration, but it does not replace authorization on every status read or result download. The longer an asynchronous job waits, the more likely its original request context and current permissions differ.

Status retrieval, notifications, and retention own different responsibilities

A status monitor can be the job resource itself or a separate progress endpoint. Its representation should describe the current state and, where useful, provide an estimated completion time or next retrieval location. A rough estimate should not be phrased as a guarantee. Clients also need to know which states are nonterminal, which are terminal, and when status records expire. Whether an expired record, a nonexistent job, and a job the caller may not view produce the same response is a design choice balancing useful errors against resource enumeration.

Polling is not free. If thousands of clients query at a short fixed interval, the status endpoint can become a new load source; if the interval is too long, users see stale state. An increasing interval, server-suggested retry time, or notifications may help, but each must fit the workload. That status code implies no universal polling interval. Notifications do not constitute the terminal state either: they can arrive late, repeat, or disappear, and a user may never open one. If users need a recovery path, the service should retain status retrieval; notification records may need lifecycle management separate from job state.

Retention belongs in the contract. If records expire too soon, a user may return to find the result gone; indefinite retention increases storage, privacy, and deletion responsibilities. After expiry, the interface should say whether the result was deleted, whether it can be regenerated, and how it avoids revealing that a private job once existed. Deleting the job and deleting the result may also differ: audit records might need retention while the downloadable file should be revoked immediately. Product and data policies determine these boundaries, not the status code.

A client timeout does not establish job identity

If a client sends a creation request and the network drops before the 202 response arrives, it cannot tell whether the server accepted the work. Blindly retrying can create two expensive jobs; refusing to retry can make the user believe the request vanished. A stable idempotency key can associate repeated submissions of the same business intent with an existing result, but its scope, retention, and behavior when parameters conflict must be part of the API contract. The same key with a different request body should be rejected or return the original job explicitly; the server should not silently choose one.

There are two different timeouts here. A creation timeout leaves acceptance uncertain; a status-query timeout means only that this query did not receive an answer. It should not change the job to failed. The interface can retain a “checking” state and let the client query again with the same job identifier. If the identifier never arrived, the client can retry or look up the original intent only if the server's idempotency contract permits it. Recovery depends on whether the server stores an idempotency record, how long it lasts, and whether replaying the request is safe.

Verify that “submitted” is not a false terminal state

One proposed acceptance plan is to test boundaries instead of merely asserting that the creation endpoint returns 202: restart after the acceptance record is written; duplicate message delivery; worker failure after file creation but before status update; permission revocation during processing; duplicate or missing notification; a lost creation response followed by client retry; status-endpoint timeout; and expiry of the job or result. For each case, inspect job state, result resources, duplicate-submission behavior, authorization, and user feedback.

Before running such tests, state what each can prove. A local test that simulates a worker exception does not establish how a production queue behaves under duplicate delivery. An end-to-end check of one failed job does not validate cleanup after a long retention period. A tutorial or test report should name the actual environment, inputs, and result. No queue, polling loop, notification, or test listed here was executed; these are proposed checks, not a passing test report.

When reviewing an API, ask: what is persisted before returning 202; which state and result resource constitute a business terminal outcome; how does a client avoid duplicate work if the response is lost; when are permissions checked again; how long do status and result records live; and how does a user recover after notification failure? Only when the answers match real interface behavior can “accepted” remain distinct from “completed.” Related articles on business idempotency and object-level authorization address retry identity and resource access; 202 does not replace either.
