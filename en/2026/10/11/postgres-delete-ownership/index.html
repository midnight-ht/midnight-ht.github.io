Use a lifecycle map to choose PostgreSQL ON DELETE

Use order lines, a shared catalog and historical snapshots to choose CASCADE, RESTRICT, NO ACTION or SET NULL, then verify the deletion scope.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-26 · Estimated read 22 min
Translations
zh-CN en

Article

Choose a foreign key's delete action by asking whether the two objects share a lifecycle. A component that cannot exist without its parent may be deleted with it; a shared object or a row that carries historical meaning should instead block deletion, preserve a snapshot, or lose only an optional reference. PostgreSQL will execute the referential action you declare, but it cannot decide whether a product-level “delete” means hide, archive, or physically destroy.

This distinction is easy to lose in a code review when someone says, “the database will clean it up for us.” A foreign key answers whether a reference remains valid. A product operation answers what the user has authorized the system to remove. Those questions are related, but they are not interchangeable.

A reference does not prove ownership

Consider an order system. An order line belongs to one order, while the product comes from a shared catalog. Once an order is closed, its lines may have no independent life. The product, however, may be referenced by many orders, quotes, and reports. If every foreign key uses ON DELETE CASCADE, deleting one product could also remove historical lines when the caller only meant to stop selling that product.

This is a hypothetical model used to explain a design choice, not an incident reported by this site. Each edge in the foreign-key graph needs its own meaning: is it a true component relationship, optional metadata, a shared reference, or a historical association that must remain? A parent table can connect to children with different lifecycles; one action should not be applied to every outgoing relationship by habit.

The PostgreSQL 19 constraints documentation illustrates the distinction with orders, order items, and products. An item may be a component of an order, while orders and products are independent objects; the delete action depends on what the two tables represent. The documentation establishes database behavior. The lifecycle categories and review steps below are an editorial modeling method.

Draw the lifecycle one edge at a time

Before choosing the most convenient action, follow the requested deletion through each relationship and ask:

  1. Does the child still have an interpretable meaning after the parent is gone? An order line may need its order context and be an exclusively owned component.
  2. Could several entities share the referenced object? Catalog products, user accounts, and tags often have multiple consumers.
  3. Does the child preserve a historical fact that cannot be recovered from the current parent row? A product name, SKU, and price at checkout may belong in a purchase snapshot rather than being looked up from today's catalog.
  4. Did the caller request irreversible physical deletion, or only hiding, deactivation, or deferred cleanup? If the intent is to delist an item, deleting its catalog row may be unnecessary.

The answers can change over time. A product may initially be referenced by one order, then become reusable through bulk import or a shared catalog. A cascade that looked safe can then acquire a much larger impact. A constraint is a long-lived data contract, so a review should consider future sharing paths as well as today's UI action.

As a minimal lifecycle map, write two edges first: orders → order_items (owned component, CASCADE); products → order_items (shared reference, RESTRICT). Mark purchase snapshots and the requested kind of deletion beside them. The map is not decoration: it is a deletion-scope table that reviewers can compare edge by edge with the foreign-key declarations.

Separate order-owned lines from shared catalog rows

The sketch below treats order lines as components of orders and catalog products as shared objects. It stores the facts of a purchase as a snapshot and prevents physical deletion of a product while an order line still references it.

CREATE TABLE products (
    product_id bigint PRIMARY KEY,
    sku text NOT NULL,
    discontinued_at timestamptz
);

CREATE TABLE orders (
    order_id bigint PRIMARY KEY,
    created_at timestamptz NOT NULL
);

CREATE TABLE order_items (
    order_item_id bigint PRIMARY KEY,
    order_id bigint NOT NULL
        REFERENCES orders(order_id) ON DELETE CASCADE,
    product_id bigint NOT NULL
        REFERENCES products(product_id) ON DELETE RESTRICT,
    sku_at_purchase text NOT NULL,
    item_name_at_purchase text NOT NULL,
    unit_price_at_purchase numeric(12, 2) NOT NULL
);

CREATE INDEX order_items_order_id_idx ON order_items(order_id);
CREATE INDEX order_items_product_id_idx ON order_items(product_id);

This SQL is a design sketch and was not run for this task. Deleting an order can remove its exclusively owned lines through the foreign key. Deleting a product that is still referenced by a line fails; the caller can explain that the product is tied to historical orders and offer a discontinued state. The snapshot fields answer “what was purchased then,” while the current products row answers “what is in the catalog now.” They should not be treated as the same source of truth.

If the product allows catalog rows to be physically removed while historical lines remain, order_items.product_id could be nullable with ON DELETE SET NULL. The snapshot would remain the basis for historical display, while the link to the current catalog row would become optional. If audit or operational needs require that link to remain forever, do not make it nullable just to make a delete button succeed. SET NULL remains subject to NOT NULL, composite-key, and other constraints; every remaining constraint must still be satisfied after the action.

If “delete product” really means discontinue sales, an update to discontinued_at or a separate active state is usually a more direct model. The order-to-catalog reference remains intact and storefront queries filter by sales state. Modeling delisting as physical deletion introduces extra questions about snapshots, detached references, and recovery from mistakes. Soft deletion is not free either: queries must handle the state consistently, and someone must define when final cleanup happens.

NO ACTION and RESTRICT differ when a transaction needs it

For delete actions, the default is NO ACTION. If an operation would leave a dangling reference when the constraint is checked, it raises an error. When a foreign key is deferrable, one transaction can temporarily delete a referenced row and then remove or repair its referencing rows before the deferred check decides whether the final state still violates the constraint.

RESTRICT rejects deletion as soon as the referenced row has a match; that check cannot be deferred. The PostgreSQL 19 CREATE TABLE reference makes this distinction explicit. Both actions can prevent an invalid final reference, but they are not equivalent when a transaction deliberately passes through an invalid intermediate state. If the business workflow does not need to repair references within one transaction, the default NO ACTION is often enough. Choose RESTRICT when the rule is that this deletion must not enter that intermediate state at all.

CASCADE, SET NULL, and SET DEFAULT are referential actions performed by the database. SET DEFAULT can still fail if the default does not identify a valid referenced row. Composite foreign keys add another boundary: in PostgreSQL 19, ON DELETE SET NULL (author_id) can clear only the selected column while retaining a tenant_id that is part of the key. This column-list syntax is a PostgreSQL extension, so check the target database before treating it as portable SQL.

Check the impact graph and failure path before deletion

An API request can be one line while its cascade path crosses several tables. Start at the row being deleted, enumerate downstream tables, classify owned components, shared references, historical snapshots, and audit data, and identify which constraint is expected to block removal. A local foreign key cannot coordinate lifecycle across services; if references cross service boundaries, define how deletion state propagates, how failures are retried, and what evidence each side retains.

In a recoverable test database, inspect the target and its related rows, exercise the delete inside a transaction, inspect the resulting state, and roll the exercise back. The sketch below must be adapted to real keys, permissions, and tenant predicates. It was not executed for this article and is not a production command or a success log:

BEGIN;

SELECT order_id
FROM orders
WHERE order_id = 4201;

SELECT order_item_id, product_id, sku_at_purchase, unit_price_at_purchase
FROM order_items
WHERE order_id = 4201;

DELETE FROM orders
WHERE order_id = 4201
RETURNING order_id;

-- Query order_items and products again to inspect the cascade and retained catalog row.
ROLLBACK;

DELETE ... RETURNING returns the order row deleted directly by that statement; it is not a complete list of every order line removed through the foreign key. Query the related tables separately to confirm that the cascade scope matches the intended policy. An error from RESTRICT or NO ACTION is not necessarily a bad constraint: it may be the guard that stops a historically referenced object from being physically destroyed. A live workflow also needs checks for caller-visible messaging, authorization, retries, concurrent requests, and backup recovery. This article did not measure any of those system behaviors.

Indexes belong in the same review. The referenced primary or unique key is indexed, but creating a foreign key does not automatically index the referencing columns. The official documentation notes that deletes or updates to a referenced key must find matching referencing rows, and that an index on those columns is often useful. Whether it is worth adding depends on data volume and the read/write workload; validate it with representative data and real queries. No performance test was run here.

What is the real question behind “should this cascade?”

The useful follow-up is whether the child retains historical or shared meaning apart from the parent. If it does, do not cascade it away. If the current relationship is optional, keep the historical snapshot and consider detaching only that reference. If the child is an inseparable component of its parent, cascade matches the lifecycle. After choosing the action, verify every affected table, expected constraint failure, and rollback in a recoverable environment.

A database review should ask not only whether the foreign key is valid, but which business actor's authority the delete action represents. Mark the lifecycle of each edge first, then use the constraint to enforce that edge. Do not let a convenient CASCADE stand in for a deletion policy.

References: PostgreSQL 19 constraints and foreign-key delete actions, PostgreSQL 19 CREATE TABLE reference, and PostgreSQL 19 transactions tutorial. Related reading: Savepoints and isolating a local failure.
