Object.entries key order: why numeric-looking keys move ahead

Trace index-key ordering through field entry, deletion and undo, then store user order as explicit data.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-26 · Estimated read 10 min
Translations
zh-CN en

Article

Key takeaways

  • Ordinary objects enumerate array indices before other string keys.
  • Store user order explicitly rather than infer property history.
  • Test value updates, recreation and omitted properties separately.

Insert key "10" and then key "2" into an ordinary object, and Object.entries can list two before ten. Array-index string keys come first in numeric order; other string keys follow creation order. If a screen must preserve entry or drag order, store that order explicitly.

Numeric-looking strings are not one category

Object.entries in ECMAScript gathers enumerable own string-keyed entries. For ordinary objects, OrdinaryOwnPropertyKeys orders array indices before other string keys and then symbols. The entries operation excludes symbols from its result.

The retrieved living draft is labelled ECMAScript 2027. This article concerns ordinary objects, not a uniform guarantee for proxies or every exotic object. Being convertible to a number is broader than being an array index. "02", "-1" and "2" do not belong to one ordering category, and the index range has a defined upper boundary.

The following teaching example is unexecuted. Under the ordinary-object rules, its expected keys are two, ten, leading-zero two and label.

const fields = {};
fields['10'] = 'ten';
fields['2'] = 'two';
fields['02'] = 'leading zero';
fields.label = 'label';
const rows = Object.entries(fields);
// Expected keys by specification: ['2', '10', '02', 'label']

No value has disappeared. The enumeration order differs from entry history. Sorting rows by key is a repair only if the business requirement is identifier order. It does not restore user-defined positions.

Make position part of the data model

For a workflow form with draggable fields, use records containing stable identifiers and explicit positions, or an ordered identifier list with an object used only for lookup. Content changes then need not move rows, and position changes do not depend on whether an identifier resembles an integer.

A Map can be appropriate for insertion-order needs, but its transport representation, updates to existing keys and consumer expectations still require design. Converting it back to a plain object with numeric-looking keys at an API boundary reintroduces the original enumeration rules.

For an existing payload, locate the actual source of order. Perhaps the server already returns a rank the UI ignores. Perhaps the database never stored user order. In the latter case, current object keys cannot recover missing history. A migration needs a deliberate initial order, rather than a claim to restore an unrecorded past.

The site's own-property discussion asks whether fields belong to the input. This question adds another axis: ownership does not establish business position. Existence, enumerability and order deserve separate expectations.

Does deleting and re-adding a key restore its position?

For an ordinary non-index string key, recreating it establishes a new creation order and can move it after other string keys. Updating its value is a different action. Index keys remain governed by index ordering, so rebuilding "2" does not reliably place it after "10".

This matters for undo. Restoring a deleted value may restore content without restoring its former position. If undo must restore both, include position in the history snapshot. A test asserting only that the key exists misses the visible behavior.

Likewise, a value update should not accidentally become a sorting event. Rebuilding objects on refresh and relying on construction order allows upstream merge order to leak into the UI. An explicit position field lets tests demonstrate that content and location remain independent.

Missing entries require another diagnosis

Symbol keys, non-enumerable own properties and inherited properties do not appear as normal entries. If data is absent rather than reordered, inspect descriptors and origin before changing sort logic. Reflect.ownKeys can support inspecting all own keys, but later value reads and serialization have separate contracts.

Add the string boundary pair "4294967294" and "4294967295" to the expected table: the first can be an array index, the second is outside that category. Large database identifiers can therefore cross ordering categories. Preserve original strings in boundary tests rather than normalizing away leading zeros.

A proposed matrix includes index strings, leading zeros, negatives, ordinary names, symbols, non-enumerable properties and inherited fields. Add value updates, deletion and recreation, and serialization round trips. At the UI level, verify saving, refreshing and undoing a dragged order. No code or form repair is reported here. Persistent order needs explicit data rather than an inference from enumeration output.
