Why Is the Second Template Insertion Empty?

Explain fragment-child movement, create a fresh copy per instance, and verify actions, identifiers, and removal independently.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-26 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • Inserting a fragment moves its children.
  • Start each instance from a fresh content copy.
  • Manage interaction and identifier relationships explicitly after cloning.

If the first template insertion works and the second is empty, check whether both operations append the same template.content. Inserting a DocumentFragment moves its children into the destination, leaving the fragment empty. Repeated cards need a fresh content copy for each instance, followed by data population, interaction setup, and insertion. Reusing one fragment repeatedly consumes the same material.

What belongs to the template and to the fragment?

The HTML Living Standard's template definition places template contents in the DocumentFragment returned by content, rather than among the template element's ordinary children. This article addresses ordinary script-based instantiation, not the complete rules for declarative shadow roots. The inspected HTML page identifies an October 22, 2026 update.

The DOM Standard insertion algorithm takes a fragment's children and inserts them into the destination. An empty fragment has no such children to insert. The template is therefore not an automatic factory, and accessing content does not return a new copy each time. A saved reference still points to the same possibly emptied container.

Separate reusable structure, a copy being prepared, and the connected instance. The template retains structure; a copy belongs to one creation operation; inserted nodes occupy their destination in the document tree. Similarly, appending the same connected card elsewhere moves it instead of creating two independent cards.

Make a loop produce two independent cards

Consider an unexecuted order-summary example. Each of two orders needs a title and a “View order” action. The faulty loop fills the template's original content and appends that content. On its second iteration, querying the original fragment may find no title because the first insertion moved it away.

Instead, begin every iteration with template.content.cloneNode(true). Find fields inside that new fragment, set the order title as text, associate the action with the current order identity, then append the copy. After the first insertion, the reusable template should retain its structure. Create the second card from that structure, rather than borrowing a modified node from the first card.

Scope queries to the current copy. A global query that always finds the first button can attach the second order to the first card even when cloning is correct. Obtain the current root, locate its fields, and preserve its data identity. Identical display titles cannot replace order identifiers.

The complete proposed result is two cards showing their respective data, with each action opening its own order. Remove the first card and confirm that the second still works. These are unexecuted acceptance goals, not observed outcomes. Counting two similar containers would miss actions that both point to the same order.

Does deep cloning also copy event listeners?

Do not assume that it does. Node cloning copies structure through the applicable cloning steps; listeners registered on an object using addEventListener are not a runtime state that every copy automatically inherits. Bind during instance initialization or use suitable delegation from a stable list container. Verify either choice against instance identities.

Per-instance binding makes action ownership visible at initialization but needs an appropriate reference lifecycle on removal. Delegation centralizes routing but must locate the actual card and data. Adding an icon inside a button can break code that assumes the raw event target is the button. Component lifecycle and action structure should determine the choice; the fragment does not manage those responsibilities.

Avoid replacing binding work with untrusted HTML interpolation. A template supplies reusable structure, not input trust. An order title normally belongs in a text node. A genuine rich-text requirement needs an appropriate trust and sanitization policy. This boundary is a design recommendation, not evidence of a security review.

Can cloned cards create duplicate identifiers?

Yes. Identical id values do not become unique merely because more instances exist. Label and description references can then identify the wrong control. Use classes or data attributes for local queries, and assign unique instance identifiers when a document-level relationship requires them. Update every corresponding reference.

If each card has a note input, copying its identifier unchanged can make the second label address an unintended input. Repair the input identifier, label association, and help-text references together. Avoid arbitrarily changing identities on every redraw, which can undermine existing references and focus restoration.

Cross-document use adds another condition. DOM importNode imports with a target document context; custom-element behavior needs evaluation against the actual document and registration environment. This two-card, same-document example does not establish compatibility for every cross-document component. Retain document and construction-lifecycle evidence when that requirement exists.

Proposed verification records the template's child count, creates two cards consecutively, and checks that template contents remain, nodes differ, fields and actions are independent, and removing one card preserves the other. Include label relationships and duplicate identifiers. Button types and default actions adds a useful check when template buttons appear inside forms. No DOM example or browser test was run here. Establish that two creations preserve reuse before expanding the list.
