Why can fetch --prune remove tags you created locally?

Follow refspec destinations to distinguish branch cleanup from local tag deletion, including configuration, dry runs and recovery evidence.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-26 · Estimated read 11 min
Translations

Article

Key takeaways

  • Pruning follows mappings, and explicit tag mappings can include locally created tags.
  • --tags differs from --prune-tags, while --no-tags does not cancel explicit tag mappings.
  • Establish tag authority across remotes before dry-running and comparing full references.

Your local experiment tag scratch-a was never pushed to origin, yet a fetch cleanup can remove it. If the effective refspec maps remote tags into local refs/tags/*, pruning can include local tags absent from that remote. Creating a tag yourself does not isolate its namespace. Inspect mapping destinations and configuration before deciding which references cleanup may remove.

Pruning follows the destination mapping

The PRUNING section of the fetch manual explains that pruning follows the remote's refspec rather than the category “branch.” Ordinary branch mappings target refs/remotes/origin/*, making routine pruning appear branch-specific. A mapping of refs/tags/*:refs/tags/* instead targets the local tag namespace. A local tag name does not tell Git which remote originally supplied it.

This matters with multiple remotes. Remote-tracking branches generally have separate namespaces, while local tags do not automatically have origin and upstream compartments. If several sources write the same tag namespace, pruning against one source can affect tags unique to another. Review the destination side of every mapping, not just the number of remotes.

How a personal tag becomes eligible

Consider an unexecuted teaching repository. Local tags include release-a and scratch-a; the remote contains only release-a. The developer created scratch-a as an experiment. A normal branch-only mapping does not itself establish that branch pruning deletes this tag. Adding an explicit tag mapping and enabling pruning changes the scope: scratch-a can now be removed because it is absent remotely.

The deciding fact is the mapped namespace, not who created the tag. The manual explicitly warns that many locally removed tags might never have come from the remote being pruned.

Preserve tag names and object IDs, inspect the remote tag set, and review a dry run first. If a personal tag appears in the deletion set, narrow the mapping or omit tag pruning while establishing which remote is authoritative. An object potentially remaining locally is not a substitute for a saved reference identity, annotation and recovery basis.

Tag following, --tags and explicit mappings differ

Tags fetched by default auto-following, or only because of --tags, are not subject to pruning on those grounds alone. Tags fetched through an explicit refspec are. Consequently, --tags and --prune-tags are not interchangeable script conveniences.

--prune-tags is shorthand for supplying the tag refspec; with pruning enabled, tags absent remotely can be removed locally. Inspect fetch.pruneTags, remote-specific pruneTags and pruning configuration as well. A script containing only fetch --prune can have a broader effective scope because of configuration outside the script.

A poor policy is globally enabling tag pruning without establishing whether every repository treats the same remote as the sole authority. Some repositories retain multiple upstreams' markers or unpublished experiments. If a mirror is intended, make that purpose explicit in an isolated mirror rather than treating a personal checkout as disposable.

Does --no-tags cancel an explicit tag mapping?

No. It controls default tag following, not explicit tag refspecs. The manual illustrates --no-tags together with explicit tag mapping still fetching tags. Avoiding tag operations therefore requires checking explicit mappings and equivalent configuration, not merely adding an option whose name sounds prohibitive.

Read dry-run output by full destination reference. If refs/tags/ is still targeted, explain why those references remain in scope. Disabling an automatic behavior does not withdraw a separate explicit instruction.

Verify reference differences

A proposed isolated validation uses a temporary local remote and disposable clones. Compare default branch mapping, additional tag mapping and tag-pruning configuration. Run git fetch --dry-run --prune origin first, then perform the corresponding fetch only in the disposable repository and compare complete reference inventories. These are proposed commands; no pruning was performed in the current repository for this article.

Cover auto-following alone, --tags alone, an explicit tag refspec, and --no-tags combined with that refspec. Include a local-only tag, a tag unique to another remote and a tag deleted from the authoritative remote. Explain each outcome using its mapping. Unchanged working files cannot prove unchanged references.

Prepare recovery before mutation. Preserve reference-to-object mappings and, where needed, use an approved backup that retains objects and annotated-tag information. Restore accidental removals from that evidence rather than attaching a remembered name to the current commit. This article does not report a recovery test or guarantee eventual object availability.

Pushing branches and release tags examines selection in the other direction. Fetch pruning likewise requires a decision about full reference names, mapping and authority. Convenient cleanup of obsolete remote branches should not accidentally become deletion policy for a shared local tag namespace.
