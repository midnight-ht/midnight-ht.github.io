TaskGroup child failure: cancellation scope and cleanup ownership

Use a two-list import to examine peer cancellation, handled item errors, detached tasks and the separate commit boundary.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-26 · Estimated read 10 min
Translations
zh-CN en

Article

Key takeaways

  • A non-cancellation failure cancels remaining group members and waits for exit.
  • Cancellation does not roll back external effects.
  • Handled item outcomes and detached tasks need separate contracts.

When a TaskGroup child fails with a non-cancellation exception, remaining children in that group are cancelled, and context exit waits for them to finish. This establishes a failure scope. It does not undo files already written or requests already accepted by another service.

Make decisions after the group has finished

The Python task-group reference defines waiting, cancellation and exception grouping. The retrieved 3.14 page is labelled 3.14.9. The API was introduced in 3.11; version-specific additions should not be assumed for every runtime. This article focuses on ordinary non-cancellation failures.

Imagine an import requiring both a product list and a price list. Neither is useful as a complete published version alone. Placing their reads in one group expresses that one failed dependency should end continued production of the other result. Commit only after normal group exit and completeness checks.

This teaching code is unexecuted. The read functions are hypothetical asynchronous dependencies, not validated clients.

import asyncio

async def prepare_import():
    async with asyncio.TaskGroup() as group:
        products = group.create_task(read_products())
        prices = group.create_task(read_prices())
    return build_import(products.result(), prices.result())

If the price read fails while the product read is waiting, the group requests cancellation of unfinished members and waits for their cleanup. Normal execution does not continue to build_import. No exact completion order or maximum cancellation time follows: responsiveness depends on suspension points and task behavior.

Cancellation does not roll back external effects

Suppose the product reader has already written part of a cache. A later price failure does not delete that cache or retract a remote request. Stage task-owned temporary outputs, validate both results after normal exit, and define a separate commit boundary if they must become visible together. That is application design, not a filesystem transaction supplied by TaskGroup.

Resource owners should arrange cleanup, commonly in finally. A task that creates a temporary file can close or remove its own file; it should not arbitrarily close a shared connection or external handle. Failure containment requires ownership as well as cancellation.

The Python documentation warns that structured-concurrency mechanisms use cancellation internally and can misbehave when CancelledError is swallowed. Cleanup and cancellation propagation are separate decisions. Catching cancellation to release a resource should not silently turn that task into a successful business result.

What if a child catches an expected error?

A child that catches an expected exception and returns a result object completes normally from the group's perspective. That handled error does not automatically trigger cancellation of peers. This can support partial-success batches, but normal context exit then proves only task completion, not business success for every item.

For ten URL checks, a missing page might be data worth collecting, while an unavailable shared connection pool might justify failing the group. Classify expected item outcomes separately from failures that invalidate the operation. Catching every Exception merely to keep the context successful removes that distinction.

For the two-list import, returning an empty list after a price failure can instead produce a plausible but incomplete import. Use an explicit status and check it before commit. Tolerance should preserve explainable outcomes rather than force every path through a success-shaped return.

Work created outside the group stays outside its scope

A task launched elsewhere with create_task is not a group member merely because it shares a function or request identifier. Group exit cannot certify its completion. Detached background work needs its own lifecycle, error route and shutdown responsibility.

The site's asynchronous listener article separates dispatch from completion. Here, group membership gives the concrete Python boundary: identify what was created through group.create_task and therefore waited for by this context.

After members finish, ordinary non-cancellation failures are raised in an ExceptionGroup or BaseExceptionGroup as appropriate. KeyboardInterrupt and SystemExit receive special treatment. Preserve child-error identity at the group boundary rather than collapsing all failures into one source-free message; matching syntax should be checked for the target Python version.

Proposed verification uses controlled suspension points, fails one child, and records peer cancellation, cleanup and context exit. Add voluntary cancellation, expected errors converted to data, cleanup failure, detached work and near-simultaneous failures. Avoid relying on real network timing. No tasks or fault injections were executed for this article. Verify membership, terminal outcomes and the commit boundary before treating a cancellation message as completion evidence.
