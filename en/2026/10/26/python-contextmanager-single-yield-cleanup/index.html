Why contextmanager must yield exactly once

Trace entry, borrowing and exit through one yield, including swallowed errors, cleanup failure and single-use instances.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-26 · Estimated read 10 min
Translations
zh-CN en

Article

Key takeaways

  • One yield separates entry and exit rather than repeated resource iteration.
  • Logging a body error should preserve the intended propagation contract.
  • Create a fresh generator-based manager instance for a new borrowing interval.

A generator decorated with @contextmanager must yield exactly once. Code before yield enters the context, the yielded value is borrowed by the with body, and execution resumes afterward to exit. This is not an iterator for the caller to consume repeatedly. Catching a body exception without re-raising can also make a failed operation appear successful.

One suspension defines one borrowing interval

The Python contextlib reference requires a single yielded value and explains that a body exception is thrown back into the generator at the yield point. The retrieved page is labelled 3.14.9. This article covers synchronous generator-based managers rather than assuming identical behavior for async, reusable or reentrant managers.

Imagine an exporter borrowing a text-file handle. This teaching code has not been executed. The path and content are hypothetical, and closing is not a claim of transactional or durable publication.

from contextlib import contextmanager

@contextmanager
def report_file(path):
    handle = open(path, 'w', encoding='utf-8')
    try:
        yield handle
    finally:
        handle.close()

with report_file('example-report.txt') as output:
    output.write('draft\n')

Acquisition occurs before the protected borrowing interval. If open fails, there is no acquired handle and the body does not begin. If writing fails, the exception returns at yield and finally still arranges closing. Resource release and body success are distinct facts.

A real exporter also needs a policy for partial files. Closing does not delete them. If only complete outputs may become visible, stage a temporary artifact and define a separate publication step, with failure cleanup tied to ownership. Filesystem replacement, concurrency and durability require their own investigation.

Zero or two yields violate the protocol

Returning before the first yield does not naturally mean “skip this with body.” It fails to provide the value and entry required by the manager protocol. Put a conditional skip at the caller or choose an explicitly suitable abstraction.

Yielding a second time after the body also fails to finish the exit handshake. To manage two resources, yield one structure containing both and arrange cleanup, or use nested contexts or ExitStack. A single borrowing interval may contain multiple resources; its protocol still has one entry and one exit.

Logs should distinguish acquisition, body completion and cleanup completion. An “opened” log does not prove the body ran, and a body-finished log does not prove cleanup succeeded. A single completed state can hide where failure actually occurred.

Why can logging an exception turn failure into success?

If the generator catches an exception around yield and then finishes normally, contextmanager interprets that as handling the exception. A failed write can therefore be logged while the caller proceeds down a publication-success path.

When the purpose is observation only, re-raise after recording. If suppression is intentional, name the policy and communicate the non-success outcome. Broadly catching and continuing should not silently decide that permission errors, exhausted storage and validation errors all permit the same next action.

Cleanup can itself fail. Test how the original body failure and cleanup failure remain diagnosable, rather than checking close only on the successful path. This is not a recommendation to swallow closing errors. The actual exception chain and logging behavior depend on the resource and should be verified.

The site's promisify protocol article makes a related point: wrapping an interface does not replace its contract. contextmanager reduces boilerplate; it does not decide ownership, acceptable suppression or business completion.

Must each with statement call the factory again?

An ordinary manager instance produced by contextmanager is single-use. Call the factory again for another with statement rather than storing one returned instance and re-entering it. A generator advances through execution and does not reset after exit.

This also makes a shared global instance unsuitable as a casual connection-pool substitute. Concurrent requests need the pool's documented acquisition and return behavior. Reusability, reentrancy and single-use generation are different capabilities even when all appear behind with syntax.

Proposed verification covers acquisition failure, successful body, body failure, cleanup failure and logger failure. Check whether the body ran, release count, received exceptions and accidental success branches. Add zero-yield and double-yield managers, reuse of one instance and fresh-factory calls. No code execution is claimed. Closing becomes useful evidence only when considered alongside body outcome and exception propagation.
