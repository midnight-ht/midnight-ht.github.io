Unequal arrays in unnest: NULL padding is not input rejection

Check positional pairing, interior gaps, independent sorting and lower bounds before accepting a bulk payload.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-26 · Estimated read 9 min
Translations

Article

Key takeaways

  • Padding a shorter array does not validate the payload.
  • Equal lengths cannot detect independently reordered values.
  • Verify pairing, line identity and failure policy before commit.

Passing product identifiers and quantities to the same unnest does not make unequal lengths an error. PostgreSQL expands by position and pads the shorter array with NULL. Before a bulk write, the application must establish that both arrays describe the same complete set of pairs.

Padding describes output, not repaired input

The PostgreSQL 18 array reference defines multi-array unnest, including NULL padding and its FROM-clause form. It does not infer what a missing business value should be.

Imagine a purchase import containing identifiers 101, 102 and 103, with only quantities two and five. The paper expectation is three rows: the first two have quantities, while the third has NULL. Defaulting that NULL to one would invent a purchase quantity. This teaching query has not been executed.

SELECT *
FROM unnest(ARRAY[101,102,103], ARRAY[2,5])
  AS line(product_id, quantity);

If the protocol requires every item to have a quantity, reject the incomplete payload before writing. A successful query return is not evidence that the payload met that protocol.

Length checks also need deliberate handling for empty arrays and unknown arrays. An empty pair might be a legitimate empty batch or a missing submission. cardinality can establish element counts, but equal counts do not establish valid shapes, values or associations. The site's array cardinality article addresses the counting distinction; this question additionally requires a pairing contract.

Can equal lengths establish the correct pairs?

No. Suppose identifiers remain in the order A, B while quantities are independently sorted. Original pairs A-nine and B-one become A-one and B-nine. Every value is positive and both lengths match. The database cannot infer the intended association.

Prefer a structured record per line when fields must move together throughout editing and transport. Parallel arrays can work when ownership of order is explicit: who creates it, who may reorder it, and whether any transformation can filter only one column. Removing internal NULL values before expansion is especially dangerous because later values shift left, converting visible incompleteness into apparently valid mispairing.

Repeated product identifiers need a separate rule. They might represent distinct uses, require summing, or be invalid. Deduplicating drops information; summing may combine deliberately separate deliveries. Define line identity before deciding either policy.

Two independent expansions are a different query

Separate FROM items with no pairing condition can form a Cartesian product. Two products and two quantities can yield four combinations rather than two positional pairs. A surprising row count should prompt inspection of the join shape, not a DISTINCT patch.

When combining independent row sources, join on an explicit key. An ordinal position can support diagnosis, but it is not durable business identity. Deleting the first displayed line changes later positions; updates to existing order lines should use stable line identifiers and treat display position separately.

Validation and execution should consume the same payload snapshot. Checking one mutable array and later rereading another version can invalidate the earlier length result. This is an application ownership responsibility, not a lock supplied by unnest.

Do different array lower bounds align by subscript number?

The expansion advances through each array's stored element order. A first element from a zero-based array is paired with the first element from a one-based array; no cross-column identity check is inferred. If actual subscripts carry meaning, use a design that retains them and explicitly joins the intended indices.

External producers may disagree about whether arrays are sequences or maps from indices to domain identifiers. Choose and document one interpretation, and validate shape at the boundary. Accepting the values is not enough if their identity meaning changes.

A proposed verification matrix covers equal and unequal lengths, interior NULL, empty and wholly NULL arrays, repeated identifiers, independently reordered quantities and different lower bounds. Assert acceptance or rejection, row count, exact pairings and written identities. A rejected batch should not leave partial records unless a separate partial-success protocol provides per-line receipts and retry rules. No import or SQL execution is claimed here. Padding is a language behavior to recognize, not proof of business completeness.
