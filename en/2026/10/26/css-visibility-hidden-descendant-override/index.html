Why Is a Child Button Visible Inside a Hidden Parent?

Explain descendant visibility overrides, distinguish group opacity from subtree box suppression, and separate stable space from interaction state.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-26 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • A descendant can override inherited hidden with its own visible value.
  • Group opacity and subtree box suppression are different mechanisms.
  • Define space, painting, interaction, and focus separately.

A review card becomes visibility:hidden, its border and explanation disappear, but “Continue review” remains visible. Inspect the button's own visibility declaration. The property is inherited, yet a descendant can explicitly use visible. Hiding the parent does not irrevocably suppress painting throughout the subtree. Define whether the component should retain space and interaction before choosing its state implementation.

How can a child become visible under a hidden parent?

CSS Display Level 3's visibility definition marks the property as inherited and explicitly allows descendants of a hidden element to appear when their own visibility is visible. Hidden boxes still affect layout. This differs from suppressing box generation. The inspected page is the June 5, 2026 Editor's Draft, not evidence of acceptance in a target browser.

Inheritance supplies a value when the descendant does not have its own applicable declaration; it is not an irreversible ancestor command. A parent computed value of hidden and a button computed value of visible can coexist. Looking only at the parent's computed style misses the element that actually appears. Increasing the parent's selector specificity does not become a direct declaration on the child.

This can intentionally hide a container's appearance while retaining selected descendants. It does not automatically meet a requirement to hide an entire review area. A reusable button may introduce visible in its own stylesheet, creating an exception the caller did not expect. Document why such local declarations are necessary rather than letting them silently redefine the parent's state contract.

Follow a card through hiding and restoration

Consider an unexecuted design. A page shows an application summary and “Continue review.” Switching applications should temporarily remove the old content, then show the new record. A waiting state adds a parent hiding class, while the button still explicitly requests visibility.

<section class="review-card is-hidden">
  <h2>Application summary</h2>
  <button class="review-action" type="button">Continue review</button>
</section>

.review-card.is-hidden { visibility: hidden; }
.review-action { visibility: visible; }

Under these rules, descendants without an override inherit hiding while the button keeps its own visible value. The expected result is an action separated from its explanation. This is a teaching prediction, not a browser observation. First decide whether retaining the button is intentional. If not, remove the unnecessary local declaration or choose a state representing withdrawal of the whole content region. Covering it with a higher layer does not explain the ownership problem.

Complete the proposed task: the user switches applications, the old action becomes unavailable, and successful loading updates record identity, summary, and action target before restoration. On failure, keep an accessible failure message and retry route outside unavailable content. A reappearing button does not establish that it now acts on the new record.

One counterexample adds increasingly strong hidden rules to every descendant. That can also suppress an intended local message and make restoration depend on reversing many declarations. Define which component layer owns state and remove unexplained local visibility exceptions first. If exceptions are deliberate, include them in the interface and acceptance criteria.

Are opacity and display equivalent replacements?

No. CSS Color Level 4's opacity definition describes group rendering followed by compositing: the element and its descendants form a rendered result that is blended using opacity. A child opacity of one cannot independently recover its appearance from a parent group composited at zero. This is a different mechanism from overriding inherited visibility. The inspected color document is the October 20, 2026 Editor's Draft.

If the requirement includes collapsing occupied space, display:none expresses another contract: the element and its descendants generate no boxes. A child's visibility:visible cannot restore box generation suppressed by that ancestor. The change affects layout and can affect the task's focus position. It does not delete business data or stop application scripts; visual removal is not a background-work cancellation protocol.

The site's transparency and interaction discussion explains why transparent controls may remain operable. The additional issue here is scope: inherited visibility permits local restoration, opacity applies group compositing, and display suppresses subtree boxes. Similar screenshots do not make those contracts interchangeable.

How can space remain without letting child controls restore interaction?

Separate the stable outer space from the actual content region. The shell owns layout; an inner region owns whether the complete content is presented. Put loading information somewhere accessible. If the inner region uses display:none, the shell needs an appropriate responsive space policy rather than a desktop height assumed to fit every text and viewport. This is a design option, not a required structure.

If content is temporarily unavailable for interaction, HTML's inert subtree rules offer another contract. Under the applicable conditions, the element and its flat-tree descendants become inert. This does not provide default visual hiding and cannot replace a display or visibility choice. Explain the unavailable state visually, and keep essential recovery controls outside the inert region. This discussion concerns an ordinary card, not every exception involving modal dialogs and other contexts.

On restoration, remove the intended interaction restriction and establish a useful focus position for the current record. If focus was in the button being hidden, design its destination instead of relying on an incidental browser fallback. Space, visibility, interaction, and focus need separate responsibilities so the transition remains explainable.

Semantic relationships add a boundary. The CSS Display draft warns about browser and assistive-technology handling of visible descendants related to invisible semantic ancestors, such as visible cells in hidden rows. A visually plausible result does not prove that those relationships work. Avoid using an isolated visible descendant as a repair for a critical task and then declaring screen-reader acceptance.

Proposed verification covers normal, waiting, failure, and restored states. Record parent and child computed values, occupied space, the next keyboard target, and the record actually affected by the action. Remove the child's visible declaration as a comparison, then inspect narrow layouts, long text, and assistive-technology relationships. No browser checks were executed here. Establish which nodes and states the hiding contract covers before selecting the style switch.
