Why Zero Is Not Unknown Progress in HTML

Use value-attribute presence to distinguish unknown progress from zero, and separate measured stages from final results.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-26 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • Remove value when the completion fraction is unknown.
  • Counts need a defined stage and work unit.
  • A completed stage does not establish final business success.

When task completion is unknown, omit the native progress element's value attribute. Zero means determinate progress with no work completed; it does not mean the completion fraction is unavailable. Showing zero percent while an import is still discovering its total turns an unknown denominator into an apparently stalled start. Connect the element to a measurable stage instead of using a default number as a task state.

What distinguishes unknown progress from zero?

The HTML Living Standard's progress definition makes attribute presence decisive: without value, progress is indeterminate; with it, progress is determinate. Value describes completed work and max describes the total. If max is absent or is not a valid positive value, the maximum defaults to one. The page inspected for this article identifies its last update as October 22, 2026. That does not establish identical presentation or announcements across browsers.

Assigning zero therefore cannot switch the element to indeterminate. When moving back to a stage with unknown completion, remove the attribute rather than supplying a negative number or invalid text and expecting the browser to infer intent. Invalid values can still produce zero in a determinate state. An empty-looking bar is not enough to establish semantics.

There is also a diagnostic trap: the value IDL getter can return zero when the attribute is missing. Do not classify progress using that number alone. The standard specifies position as minus one for indeterminate progress; attribute presence is another useful observation. Application state should determine the intended semantics, with DOM observations verifying the output.

Give each number a defined import stage

Consider an unexecuted import design. A person selects a file; the service checks its structure and discovers its row count, writes records, and then verifies the result. Suppose scanning finds five hundred records. That number is hypothetical, not a benchmark or test observation. While the total is unknown, show “Reading file structure” and omit value.

After the total is known, enter “Writing records,” with max representing five hundred and value representing confirmed writes. Zero is now meaningful. After one hundred confirmed writes, report that stage's count. Bytes sent over a network are not automatically records durably written. Define where confirmation originates and what rollback does to the count.

Writing all records may still leave duplicate checking or report generation. Enter an explicit verification stage; if its workload is unknown, remove value again. One hundred percent of writing is not task success. A download action should appear only when the result is actually ready, based on the business terminal state.

A counterexample increments progress on a timer and stops near completion until the server responds. It resembles measurement but has no work unit. If a product uses an estimate, label it as such and retain uncertainty. This example is better served by stage text and genuine counts than by insisting on a percentage at all times.

Failures belong in the same state model. A rejected write should leave the running state and provide an appropriate action, rather than keeping an animation moving indefinitely. If cancellation only dismisses the display while server work continues, explain that scope instead of implying that all work was withdrawn.

Can the percentage decrease when the total grows?

A changing denominator can mathematically reduce the fraction, but readers need to understand the change. When scanning and writing overlap, early discoveries may cover only part of the file. Until the scope closes, use indeterminate progress and perhaps report completed records, rather than presenting an unexplained fluctuating percentage.

This is an engineering choice, not an HTML prohibition on changing max. Define whether the scope is a batch, the whole file, or the complete process including verification. Change the stage label when its meaning changes. Several independent zero-to-one-hundred cycles should not sit under an unexplained “Overall progress” heading.

Why might a completed bar still have no download?

A fraction describes its specified work, not the availability of a result file. Verification may fail after writing completes, or report generation may fail separately. Enabling a download after the write count reaches its maximum creates a false result promise. Styling cannot repair that contract.

Keep the current stage, measured work, and final result reference distinct. Say “Records written; verifying” when appropriate, and give an explicit failure and recovery route if verification fails. An isolated one hundred percent provides insufficient context. HTTP 202 and terminal states discusses another boundary between intermediate acceptance and completion.

Proposed verification covers slow scanning, measurable writing, failed verification, and cancellation. Record business state, attribute presence, max, position, and stage text. Inject a late message from an earlier stage to ensure an obsolete count cannot replace the current stage. That ordering policy belongs to the application, not the native element.

Accessibility checks should also establish a useful name and appropriate announcement frequency in supported browser and assistive-technology combinations. No import service, page, or screen-reader test was run here. Start the next review with the scanning-stage DOM: while completion is unknown, a default zero should not answer on the application's behalf.
