Why can the same hostPath contain different files after a Pod moves?

Separate hostPath data ownership from host capabilities, then validate node changes, read-only limits and independent disk monitoring.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-26 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • A hostPath belongs to the current node; identical specifications can see different content elsewhere.
  • Directory checks and read-only flags do not replace content identity or privileged-interface review.
  • Cross-node recovery and host disk growth require separate design and validation.

An import worker moves to node B. Its /input path still exists, but the batch file on node A has not followed it. A hostPath identifies storage on the current host, so the same pathname does not establish cross-node recovery. Access to that directory also needs a separate review of host trust and interface capabilities. Establish which machine owns the file before deciding who may access it.

The same path can identify different data

The Kubernetes hostPath documentation describes mounting files or directories from the host node and warns that identically configured Pods can behave differently because node files differ. /srv/import on node A and the same pathname on node B are separate locations unless another system provides synchronization.

The container path is another part of the mapping. /input inside the container may represent /srv/import on the node. Record the Pod UID, node, host path and mount path when investigating missing data. Confirm that the application actually writes to the mount rather than an adjacent directory in the image filesystem.

Path type checks do not establish content identity. Directory requires an existing directory; DirectoryOrCreate creates an empty one when absent. Creating a directory can change an obvious mount failure into an application that successfully opens an empty location. If startup requires a specific ruleset, verify its version and checksum rather than treating a successful start as acceptance.

Follow an import across a node change

Consider an unexecuted hypothetical import. Its only input, batch-a.csv, lives in /srv/import on node A. A worker reads it through /input and stores a checkpoint beside it. Replacing the Pod on A can leave both files accessible. That observation establishes retention on A; it does not exercise recovery on another node.

Suppose the replacement lands on B. With Directory, a missing host directory prevents the mount from meeting its requirement. With DirectoryOrCreate, the worker may start with no input or checkpoint. If B happens to contain another file with the same name, it might process the wrong batch instead. Validate work identity and content, not merely the filename.

A design for portable recovery can keep original inputs and confirmed outputs in a system accessible across nodes, treating the node directory as a rebuildable cache. The worker obtains the source and checksum from a durable work record, downloads and checks the input, computes and uploads the result, then confirms completion. A replacement consults that record to decide whether to continue or skip completed work. This is a design example, not a cluster recovery result or a guarantee about any storage provider.

A node log collector has a different purpose. Reading the local node's logs is intentional, so node identity should accompany exported events. Moving to another node changes the observation target. It should not be expected to recover the old node's files just because the pathname is unchanged.

Host access grants more than a convenient directory

Kubernetes warns that host filesystem access can expose privileged credentials or container runtime sockets. I would first establish why the workload needs a node-level object. Storing uploaded attachments ordinarily calls for a storage interface with the required recovery scope, not access to the host.

A poor response to a permissions error is mounting the entire host root writable and increasing container privileges. That expands accessible objects without identifying the file the application actually needs. Review the narrowest directory, process identity, host permissions and necessary operations separately.

The documentation also says admission-time restrictions to specific host directories are only effective when those hostPath mounts must additionally be read-only. A path allowlist alone is insufficient. Evaluate all relevant mounts and the actual cluster policy; no universal security policy is validated here.

Does readOnly make a runtime socket safe?

That conclusion does not follow. Restricting filesystem writes does not turn an interface exposed through a file into a read-only protocol. For a privileged API socket, evaluate the requests available through the interface. Kubernetes explicitly names runtime sockets as a host access risk. Remove a mount whose authority cannot be justified rather than relying on its directory name or mount flag.

Ordinary read-only logs also need a data access review: they can contain credentials or user information. Protecting files against modification does not establish that this container should see their contents. Record storage scope and the identity receiving access as separate decisions.

Validate both placement and authority

A proposed isolated test uses two nodes containing different markers and checksums. Exercise replacement on the same node, then placement on another node. Include absent directories, incorrect content versions, denied permissions and partially processed inputs. Preserve node identity, Pod UID, mounts and work records so file retention cannot be confused with application recovery. None of these tests was executed for this article.

Monitor disk use independently. Kubernetes states that hostPath usage is not counted as ephemeral storage usage and needs separate monitoring. Container resource settings therefore do not establish a bound on growth in the host directory. Define cleanup ownership and which outputs must be confirmed before deletion.

emptyDir lifetime explains a different removal boundary. For hostPath, decide whether node-specific data and host capabilities are intentional. When recovery must cross nodes, verify that recovery path instead of accepting a familiar pathname as evidence.
