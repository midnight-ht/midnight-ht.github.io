Ordering inside string_agg: why the outer ORDER BY cannot fix a list

Use a signature export to separate aggregate input order, tie-breakers, join multiplication and missing names.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-26 · Estimated read 10 min
Translations
zh-CN en

Article

Key takeaways

  • Order fragments inside the aggregate and result rows outside it.
  • Establish signature identity before fixing join multiplication or duplicate names.
  • A display string is not a completeness or interchange contract.

Sorting customer rows does not sort the names inside each customer's exported signature list. If the list must follow signing time, put the order inside string_agg, and add a stable tie-breaker for signatures with the same timestamp. The outer order and the aggregate's input order have separate jobs.

A result row contains another ordering decision

The PostgreSQL 18 aggregate reference identifies string_agg as order-sensitive and allows ordering within the aggregate call. An outer ORDER BY acts on result rows after aggregation. With one summary row, there is no second row to move, and no instruction to rearrange fragments already joined into a string.

Consider a hypothetical customer with three signatures: Lin at nine, Zhou at nine, and Chen at ten. Their record identifiers are twelve, eleven, and thirteen. The export contract says earliest time first, then identifier. The independently derived expectation is Zhou, Lin, Chen. The following teaching query has not been executed.

WITH signatures(customer_id, id, signed_at, name) AS (
  VALUES (7, 12, timestamp '2026-10-26 09:00', 'Lin'),
         (7, 11, timestamp '2026-10-26 09:00', 'Zhou'),
         (7, 13, timestamp '2026-10-26 10:00', 'Chen')
)
SELECT customer_id,
       string_agg(name, ', ' ORDER BY signed_at, id) AS names
FROM signatures
GROUP BY customer_id
ORDER BY customer_id;

Time and identifier control the list; customer identifier controls the order of customer rows. Time alone leaves the two nine o'clock records tied. A stable unique identifier completes the requested relation. It is a correctness decision, not a promise about which index or scan the planner will use.

Establish record identity before joining text

Correct order does not establish correct membership. Suppose signatures are joined to attachments, and one signature has two attachments. The aggregate may receive the signer twice. Recover one input row per signature before aggregating if that is the intended unit. DISTINCT name can hide this mistake while also merging different people with the same name, or legitimate repeat signatures.

If the requirement is one appearance per participant, define which signature determines that participant's position. For example, derive the first valid signature and then order those representative records. Arbitrarily selecting one record cannot support a claim that the list follows first signing time.

Keep structured identifiers and timestamps alongside the display field. A comma-separated string is not automatically a reversible interchange format: a name can itself contain a comma. Choose a structured representation or an explicit escaping protocol when consumers must parse the output. Joining fragments and designing an exchange contract are different responsibilities.

Is ordering a subquery sufficient after a join?

The official reference warns that additional outer processing, including joins, can reorder a sorted subquery before aggregation. Place an order that directly affects aggregate meaning in the aggregate call, so maintenance does not depend on tracing several query layers.

A subquery order can still serve a separate purpose. Selecting a limited set of recent records is a membership decision; ordering that selected set for display is another. Removing an apparently repeated order can alter either the selected records or the final text. Preserve an expectation for each stage. The site's DISTINCT ON discussion addresses representative-row choice; this article addresses the later order in which selected fragments are combined.

How do missing names differ from empty strings?

string_agg combines non-null inputs. A missing name does not automatically leave an unknown-name slot. An empty string is different and can produce adjacent delimiters. If the export requires a visible placeholder, define the mapping deliberately and retain a missing-value count when completeness matters.

Zero signatures and signatures whose names are all missing may need different business states even when their aggregate text provides no useful distinction. Carry total records and known names rather than making a display string prove participation or completeness.

A proposed verification set includes tied timestamps, duplicate names, missing names, one signer and zero signers. Write expected record identities before running the query. Add two attachments to one signature to expose accidental multiplication, then permute input rows and check that explicit ordering still yields the same contracted list. No database execution or cost measurement is reported here. The claim is about expressed membership and ordering, not a fixed plan or runtime.
