Why a file URL pathname is not a reliable native path

Separate URL encoding, module-relative bases, platform paths and access permission at the file conversion boundary.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-26 · Estimated read 10 min
Translations
zh-CN en

Article

Key takeaways

  • Convert deliberately between file URLs and native paths.
  • Module location and working directory are different resource bases.
  • Conversion establishes neither permission nor packaged-resource identity.

A URL's pathname is a URL component, not an already converted native file path. Spaces and Unicode can remain percent-encoded, and Windows drives or network shares require platform-specific interpretation. In Node, use fileURLToPath when a file URL must become a native path.

A filename and its URL representation are different values

The official Node URL reference contrasts pathname with fileURLToPath using encoded characters, drive letters and network shares. The current page opened for this article identifies itself as v26.12.1. This discussion does not assume that every older version supports every newer option.

Imagine a build script installed under a directory containing spaces and Chinese characters. It resolves a template relative to import.meta.url. Passing pathname directly to a path-only consumer can supply literal %20 text where the filesystem name contains a space. The URL can identify the intended resource while the string handed to the consumer uses the wrong representation.

This teaching code has not been executed. It demonstrates module-relative resolution, not the existence or readability of a template.

import { fileURLToPath } from 'node:url';
import { readFile } from 'node:fs/promises';
const templateURL = new URL('./templates/report.txt', import.meta.url);
const templatePath = fileURLToPath(templateURL);
const text = await readFile(templatePath, 'utf8');

The base is the module location, not the process working directory. If the requirement is to read a caller-owned file relative to where the command was launched, this design changes the contract. Establish whether a resource belongs to the module, installation or caller before choosing a base.

Why is decodeURIComponent insufficient?

Percent decoding is only part of the conversion. A file URL has a scheme, host and platform representation. A network-share host and Windows drive syntax have native-path meaning that generic string decoding cannot supply.

Also control how many times conversion occurs. A real filename containing the literal characters %20 needs its percent sign represented in the URL. Manually decoding one layer and then passing the intermediate string through another decoder can change a literal sequence into a space. Keeping a URL object until the conversion boundary is easier to audit than moving partially decoded strings through several helpers.

Diagnostic logs should distinguish a redacted URL representation from the resulting native path. A display layer may itself decode text; two readable strings are not evidence of identical resource identity. Compare the actual converted target with the expected resource contract.

Why not construct a file URL by concatenation?

Use pathToFileURL for the reverse boundary. A local filename containing # or ? must not accidentally turn part of its name into a URL fragment or query. Adding a file:// prefix does not supply a complete encoding and platform conversion policy.

Relative input also needs a base. Appending ./report.txt to a prefix is not a complete absolute-location strategy. Resolve according to the agreed working-directory or module-relative contract, and do not silently switch bases on failure: a fallback can find a different same-named configuration.

Some Node filesystem APIs formally accept file URL objects. Where that contract applies, passing the URL directly can avoid an unnecessary string conversion. Convert explicitly for a library that requires a native path or for native-path operations. The receiving API determines the boundary.

Does successful conversion authorize reading?

No. Conversion does not prove existence, business permission or confinement to an allowed directory. Untrusted inputs still require a file-access design that checks the permitted scheme, scope and target identity. This article is not a complete directory-sandbox or symbolic-link policy.

A successful read also does not establish that the correct template version was packaged. Validate the expected file in the actual output layout. The site's readFile cancellation article concerns what happens after reading starts; this question establishes which resource is addressed beforehand.

A proposed packaging check moves the output to another installation directory containing spaces and launches it from an unrelated working directory. Give the installed template and a same-named caller file different markers. A module-owned resource should resolve to the installed marker. This relocation was not performed; bundler rewrites require verification against their actual output.

A proposed matrix includes spaces, Unicode, literal percent signs, hash characters, different module and working directories, and platform-appropriate drive and share paths. Check converted values, actual targets and failure types separately. Cross-platform claims require execution on those platforms. No files were created and no code or platform matrix was executed for this article.
