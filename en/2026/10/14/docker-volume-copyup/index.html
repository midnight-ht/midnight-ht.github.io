Why does a mounted volume still show old files after an image update?

Docker copies destination files into an empty volume on its initial mount by default; an existing volume then obscures newer image files. Learn how to inspect mounts, plan migrations, and preserve safe rollback.

Article

Key takeaways

  • An empty volume copies destination contents by default; a non-empty volume masks image files, while volume-nocopy disables that empty-volume copy.
  • Inspect the actual mount source and destination before concluding the image update failed.
  • Docker does not migrate persistent business state when an image changes; test ownership, recovery, and rollback separately.

Changing a file in an image does not keep it synchronized with a volume that is already mounted. Docker's official documentation says that when an empty volume is mounted over a directory that already has files, Docker copies the destination contents into the volume by default. Once the volume has its own contents, later mounts expose the volume over the same image path. Container recreation, image upgrade, and data migration are separate operations. When a container still shows an old file after an image update, inspect the actual mount type, volume identity, and destination before deciding whether state should be migrated. Do not begin by deleting a volume or overwriting user data.

Separate the image directory, writable layer, and volume

A container path may look like one set of files while being backed by different sources. The image layer contains defaults written during the build; a container's writable layer contains changes made by that container; a Docker-managed volume can outlive its container; and a bind mount maps a path from the host where the Docker daemon runs. Their lifecycles and ownership differ. After a mount is attached, the visible path comes from the mount source, not necessarily from the image file that used to exist there.

This can lead to opposite misunderstandings. A newly created empty volume mounted over a directory containing default templates may appear as though Docker “wrote image files into the data volume.” That is the default volume-initialization behavior. Later, after the image template is upgraded, the same volume may still contain its original copy. Recreating the container does not necessarily create a new volume. In another case, a non-empty volume obscures the image's underlying files, so the new version is not visible inside the container. Neither situation proves that the image pull failed or that the file is corrupt.

The Docker volumes guide documents the two behaviors under mounting over existing data and mount options: a non-empty volume obscures the destination's existing files; an empty volume receives the destination contents by default; and volume-nocopy disables that copy. The option changes empty-volume initialization only. It does not merge or upgrade an existing volume. If copying is disabled, the application needs its own initialization path, and behavior with an empty directory must be verified separately.

Walk through a template upgrade

Imagine an application that ships default notification templates in the image at /app/templates. The first deployment mounts an empty named volume called notice-data at the same path. At initial mount, Docker copies the templates that are present at that time into the empty volume. A later image changes the wording and is built again, but deployment mounts notice-data back at /app/templates. The new image contains the new template while the volume retains the old one; the container sees the volume's files, so the interface still displays the old wording. This is a hypothetical walkthrough of the documented mechanism; it was not run on this site or in a production environment.

First establish what the running container actually mounts. You can inspect its mount type, name or source, and destination, then check whether the application's read path is exactly the mount destination. If it is a volume, verify the volume name and its inspection output. If it is a bind mount, inspect the host source path. For Docker Desktop or a remote daemon, the path belongs to the daemon's view of the host; it may not be a same-named path on the terminal client. The Docker bind-mount guide documents this distinction. A filename inside the container and an image tag alone cannot identify whether the visible bytes came from the image, a volume, or a host directory.

Collect evidence separately for the image defaults and volume contents: record the image digest or build identity, volume identity, mount destination, file hash or internal version marker, and the path the application actually reads. If the volume contains the first-release template while the corresponding new image path has changed, the missing behavior is an undefined default-file upgrade responsibility—not a Docker guarantee to continuously synchronize. If the files did not come from the expected volume, inspect the deployment definition and running container instead of changing copy behavior. Reproduce the mechanism in a test environment with a new volume and sample files, not with a user's persistent volume.

Defaults can be copied; business state needs a migration contract

Some directories are suitable for default copying, such as a read-only dictionary, static template, or configuration that can safely be regenerated on first use. Other directories contain user edits, database files, uploads, or state created at runtime. Keeping both in one persistent directory makes image defaults and real volume state compete for ownership. Copying new defaults may overwrite user changes; copying nothing may leave a required setting absent. Before choosing, classify each file by owner, regenerability, upgrade order, rollback compatibility, and whether overwriting is permitted.

A design that is easier to evolve keeps versioned defaults in a read-only image path and persistent data in a separate volume path. The application can then read each source deliberately and migrate user state according to an explicit version, rather than assuming Docker continually updates a volume. If initialization into a volume is necessary, retain an initialization version or migration marker, check for existing user changes, and make the migration idempotent: a restart does not append or overwrite twice; partial failure is detectable; and the next start can resume from a known point. Write the completion marker only after data has been migrated and checked, not before a write that might be interrupted.

Know the recovery plan before migrating. Docker's guide includes volume backup, restore, and migration examples; a production process still needs to choose a safe write boundary, snapshot consistency, and restore acceptance criteria. Creating an archive does not itself prove that restore works. If the data can be written concurrently, a backup must account for those changes. If a migration is irreversible, record whether the old image can read the new data, or arrange a data snapshot and a tested rollback transformation. Restarting an old image only changes the code. It does not revert the volume. If the old program cannot read migrated data, an image rollback may fail or misinterpret state.

What volume-nocopy, an empty volume, and deletion actually change

volume-nocopy fits a case where the application needs a genuinely empty volume and has its own initialization logic.

Also distinguish an empty-volume state from a volume that has ever been mounted. Default copying depends on whether the volume is empty at the current mount and whether volume-nocopy is enabled for that mount; Docker does not document a permanent one-time migration marker on the volume. If a prior volume-nocopy mount left the volume empty because the application wrote nothing, a later mount without that option over a populated destination should be reviewed against the new mount conditions. Do not use the historical option setting as a substitute for checking the volume's current contents. It does not mean “use the image directory on every mount,” and it does not replace an existing volume with image contents. If the application assumes Docker already supplied templates, disabling copy-up can cause missing files; startup checks should report that clearly instead of silently creating an incomplete configuration.

Deleting and recreating a volume is not a generic repair button. A volume may contain user changes or business records, and Docker documents container removal and volume removal as distinct lifecycle operations. Deleting the volume changes the data path. Consider a new volume only after confirming ownership, making a restorable backup, and explicitly deciding what happens to the old state. During diagnosis, use read-only inspection, an isolated environment, or a new test volume. Do not use a cleanup operation such as docker volume prune as a way to inspect a file version.

File type Decision to make What to verify during an update
Image default template Is it read-only and regenerable? The new image contains the intended version; an empty volume is initialized as expected.
User state or database file Who owns writes, and can it migrate? Backup and restore, migration idempotency, and old/new image read-write compatibility.
Temporary cache Can it be reconstructed after loss? Startup reconstruction and whether the cache was accidentally placed in a persistent volume.

Test first mount, reuse, and rollback boundaries

In an isolated test environment, create an empty volume and mount it over an image directory containing a template-v1 marker. Check the destination after the first mount. Then build an image with a template-v2 marker and reuse the same volume to see which contents are visible. Finally mount a separate, clearly new empty volume to check initial copying; if volume-nocopy is configured, verify that the destination is empty and the application initializes it safely. This separates first-copy behavior, an existing volume obscuring image files, and disabled initialization without making deletion of a production volume a test prerequisite. This article did not run that test; it is a verification proposal, not a passed result.

Persistent business data needs additional tests for an interrupted migration, repeated startup, backup restoration, and an old image reading the migrated state. Record the image digest, volume name or ID, mount source, migration version, input/output checkpoint, and result-file hash. A “started successfully” log does not prove that the new template was used. A path inside the container does not reveal its source. Only when path, source, version, and application behavior line up can a team locate whether the change took effect in the image, volume initialization, or data migration layer.

A successful image update, changed volume contents, completed migration, and application adoption are separate states and should be recorded separately.
