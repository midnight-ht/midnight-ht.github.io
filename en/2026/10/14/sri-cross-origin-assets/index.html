Keep integrity hashes, bytes and cross-origin permissions aligned

Align expected bytes and cross-origin permissions without treating integrity as code trust.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-14 · Estimated read 5 min
Translations
zh-CN en

Article

Cross-origin scripts using SRI need both matching content hashes and appropriate cross-origin access. An integrity attribute does not authorize arbitrary CDN loading. Resource updates, different response bytes, or CORS changes can independently prevent execution.

Integrity concerns actual content

The MDN Subresource Integrity guide requires CORS for cross-origin integrity checks and the corresponding crossorigin setup. A hash identifies expected content; it neither authorizes reading nor certifies business logic. No CDN deployment or compatibility test was performed here.

Imagine a fixed hash paired with a URL whose content changes. The address stays the same while bytes differ, causing rejection. Alternatively, matching bytes can lack the necessary cross-origin permission. A filename existing cannot distinguish these failures. Removing integrity changes the validation goal rather than proving it satisfied.

Collect resource identity, expected hash, response conditions, and browser diagnostics. Successful transfer does not establish permitted reading or execution; a working page does not show that integrity protection remained intact.

Align updates with pinned bytes

Use explicit versions where content must remain fixed and check hashes against the final deployed asset. Automatically following latest content requires a maintenance decision; an old hash cannot predict new bytes. A development file’s hash is not necessarily the deployed file’s identity.

Matching content also does not establish trustworthiness. If the pinned code is flawed, integrity can confirm that same flawed file. Source review, dependency assessment, and business testing remain separate.

Preserve intent during fallback

Define degraded functionality and reviewed alternatives. An arbitrary mirror can break provenance and review relationships. No universal fallback list or external change is performed here.

A fallback policy should state which operations remain available and which must stop. A visible page shell must not conceal a critical operation whose required script is unavailable.

Proposed checks cover updates, wrong hashes, missing cross-origin headers, and replacements; none were run. See response-scoped CSP nonces. CSP and SRI impose distinct conditions, so one attribute cannot establish the other boundary.
