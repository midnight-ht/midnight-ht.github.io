Why does a CDN script with integrity still fail to load? Separate hash and CORS failures

A cross-origin script with integrity can still be rejected. Check request mode, CORS headers, final response bytes, and the digest separately, then define a bounded fallback.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-25 · Estimated read 20 min
Translations
zh-CN en

Article

Key takeaways

  • Cross-origin SRI depends on both matching expected bytes and valid CORS conditions; HTTP 200 does not prove that a browser will execute the resource.
  • Check the browser's request mode and Access-Control-Allow-Origin before comparing integrity against the final release artifact, not a guessed version or development file.
  • A digest identifies pinned bytes, not trustworthy code; do not remove integrity or switch to an unreviewed mirror as an unconditional fallback.

If a cross-origin CDN script still fails with an integrity attribute, separate two questions first: do the bytes the browser received match the declared digest, and did the cross-origin response satisfy CORS? An HTTP 200 response only means the server returned something. It does not prove that the browser may use the response for this cross-origin request, that its content matches the digest, or that the script executed. Start with the browser's actual request, then verify CORS and the final bytes independently. Do not remove the integrity attribute just to make the page appear to recover.

SRI means Subresource Integrity. The HTML integrity attribute declares one or more digests; the browser hashes the fetched resource and compares it before proceeding. The current Subresource Integrity Level 2 Working Draft was published on 20 March 2026. The document labels itself a Working Draft, not a finalized Recommendation. This article uses it to verify the mechanism and does not assume that every browser already supports newly added policy interfaces from the draft.

Two gates check content identity and cross-origin permission

integrity answers a narrow question: does the resource content match the digest declared by the page? It does not authorize a cross-origin request, decide whether code is trustworthy, or grant permission to execute a script. Further handling can also be affected by Content Security Policy, resource type, JavaScript syntax, and runtime errors. Calling every failure a “bad hash” merges separate stages into one guess.

For a cross-origin resource protected by SRI, the specification requires a CORS or same-origin request mode. One reason is to prevent a page from inferring cross-origin content by observing whether a digest matches. An ordinary classic <script> without a crossorigin attribute generally makes a cross-origin request in no-cors mode. MDN's SRI and CORS explanation explains why that combination cannot be used for cross-origin SRI. Setting crossorigin="anonymous" makes the element use a CORS request, but the resource server must still return an Access-Control-Allow-Origin value that permits the page's origin. For a public static library meant to be shared by any site, the server can usually return Access-Control-Allow-Origin: *; a restricted resource should return the allowed origin.

These gates produce different failures. A response whose body does not match integrity is rejected even when CORS succeeds. A matching body can still be unusable if the request is no-cors or the response does not grant CORS access. So a command-line download, an unchanged CDN filename, or a working development page cannot by itself prove that the production browser can use the resource.

Two distinct failures in a hypothetical release

Assume a page loads a pinned public library from https://cdn.example.invalid/lib/4.2.1/app.min.js. The .invalid address is hypothetical; it is not a real CDN. The release pipeline calculates SHA-384 from the final app.min.js artifact, places the result in integrity="sha384-…", and marks the element crossorigin="anonymous". The CDN response must allow anonymous cross-origin access. For a public resource that needs no credentials, a wildcard origin is usually an appropriate setting. The user's cookies do not need to be sent to the CDN.

Now suppose the browser's Network panel shows a successful GET with status 200, while the Console reports a CORS error. Check whether the final response includes Access-Control-Allow-Origin and whether the page actually uses crossorigin="anonymous". curl can download the file, but it does not apply the browser's CORS restrictions. An accurately computed digest cannot make up for a missing cross-origin permission.

The reverse case is different: if CORS is allowed but the Console reports an integrity mismatch, compare the browser's final URL and redirect result with the artifact version used by the release pipeline. The same path may have been overwritten with new bytes; an edge proxy may also transform a resource. The proxy section of the W3C SRI draft warns that an intermediary which modifies response content must keep the digest synchronized or serve the canonical version associated with the integrity metadata. If changed bytes retain an old digest, rejection is the correct result; silently accepting new code would defeat the assertion.

Diagnose in request-to-execution order

First inspect the browser, not only the release pipeline's download log. Record the page URL, final resource URL, whether the request is cross-origin, any redirect, the element's integrity and crossorigin attributes, and the exact Console error. A 200 shown in developer tools and permission for a script to execute are different observations. For module scripts, remember that module loading itself uses CORS; do not apply the default no-cors behavior of classic scripts to modules. MDN's crossorigin reference describes anonymous and credentialed modes.

Next inspect response headers and the request's credentials mode. Public CDN assets generally do not need cross-origin credentials. crossorigin="anonymous" uses a CORS request without sending the target site's cookies cross-origin, so a server can use Access-Control-Allow-Origin: * for public content. Use crossorigin="use-credentials" only when credentials are actually required: the server must then return an explicit allowed origin and Access-Control-Allow-Credentials: true; a wildcard origin cannot be used with a credentialed request. If the server varies the allowed origin dynamically, check for Vary: Origin so that a shared cache does not reuse one origin's response for another. MDN's CORS guide and configuration guidance describe these conditions.

Then bind the digest to the file that will actually be deployed. Repository source, a build-directory file, and the final file served by a CDN may not contain the same bytes. Version upgrades, minifier differences, release rewrites, and edge-proxy changes can invalidate an old digest. Keep the resource URL, pinned version, final artifact digest, build identifier, and whether response transformation is allowed together in the release record. The following command only illustrates a possible form; it was not run in this article, and no CDN was measured here:

curl -fsSL 'https://cdn.example.invalid/lib/4.2.1/app.min.js' \
  | openssl dgst -sha384 -binary \
  | openssl base64 -A

Prefix the output with sha384- before comparing it with an HTML integrity value using the same algorithm. A download tool may see different redirects, cache behavior, request headers, or edge configuration from a browser, so this command can help inspect an artifact but cannot replace browser acceptance. A test environment could inject a wrong digest, missing CORS header, and valid configuration separately to locate each rejection stage. These are proposed tests, not results performed for this article.

Updates and fallbacks should preserve the same security intent

A fixed digest fits a resource with an explicit version: review the upgrade, generate a new digest from the final build artifact, then change the URL, lockfile, or version record together. If a URL always points to a mutable alias such as latest while the page keeps a fixed digest, the release combines two conflicting goals: automatically follow new content and accept only known bytes. A mutable URL is not automatically forbidden, but it needs an explicit process to generate and review the next digest.

If loading fails, do not remove integrity and call that a neutral recovery. If CORS is the problem, removing the digest may bypass one check without fixing the server configuration. If the digest is wrong, switching to an unreviewed mirror transfers supply-chain trust to a new source. Safer options include a locally hosted, reviewed copy with its own fixed digest for critical functionality, or stopping the critical operation and explaining that the resource is unavailable. Non-critical enhancements may degrade gracefully. The right choice depends on what the missing script does, not on whether the page shell still renders.

A matching digest also does not replace dependency review. If the originally selected code has a flaw, SRI confirms that the browser received those bytes; it does not make them safe. Source provenance, version updates, business testing, CSP, and SRI each have distinct responsibilities. For a separate execution-permission boundary, see response-scoped CSP nonces; a nonce does not replace SRI's content digest.

Does a same-origin script also need crossorigin?

Not necessarily. The additional CORS condition discussed here concerns cross-origin SRI requests; a same-origin resource uses same-origin request mode, which is accepted by the specification's integrity-checking algorithm. For a third-party cross-origin script, check integrity, an appropriate crossorigin value, and the server's CORS response together. Do not add one attribute mechanically to every resource; choose the request mode based on the resource origin and credential requirements.

When a resource has integrity but does not load, preserve the browser's actual request and response evidence. Then check separately whether CORS allowed the request, whether response bytes match the final artifact, and whether a later policy allowed execution. Fix the condition that failed and preserve the reviewed content identity in the fallback; do not hide an unlocated problem by deleting the attribute or changing the URL.
