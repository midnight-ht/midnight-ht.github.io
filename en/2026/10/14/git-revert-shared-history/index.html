Git revert records an inverse commit; how do you verify recovery?

A revert preserves the original and records an inverse change. Verify the tree, merge parent, built artifact, and runtime separately to state what actually recovered.

Key takeaways

  • The original commit remains; revert records an inverse change as a new commit.
  • The selected mainline parent and merge ancestry affect what a later merge brings in.
  • Verify source tree, built artifact, runtime, and external state independently.

git revert keeps the target commit and records a new commit that applies inverse changes to the current branch. It is neither a history-deletion button nor proof of a production rollback. To establish the recovery you need, inspect the commit graph, the resulting tree, the build artifact, and the running version separately; database rows, delivered messages, and exposed credentials may require independent compensation.

The inverse applies to the current state; it does not rewind the branch

The Git git-revert manual describes reverting changes introduced by one or more existing commits and recording new commits. Its current version selector says the manual was last updated in 2.54.0, with 2.54.1 through 2.56.1 listed as having no changes. That is documentation version information, not the Git version installed on a reader’s machine. The original commit remains in ancestor history, so seeing it in git log is expected.

An inverse patch is also not a command to copy every file back to the target commit’s parent. Consider a graph where A is the shared baseline, B adds validation to a login screen, C refactors the error message in the same file, and the team creates R on top of C to undo B. R applies the inverse of B’s change to the current tree at C. The validation may be removed while C’s message refactor remains; if the changes overlap, Git may require conflict resolution. The result can retain other changes from C. It need not equal A, and it does not automatically prove that the intended behavior has returned.

This graph is a hypothetical explanation; no git revert was run in this repository. In a real review, compare B’s original diff, the C-to-R result, and the desired behavior. A clean command exit only shows that Git could produce a commit or working-tree change. It does not establish that the inverse patch covers every business effect.

Revert, reset, and restore change different state

When a shared branch needs an auditable reversal, revert creates a new commit and preserves the identities and order of earlier commits. The Git git-reset manual says reset with a commit changes where HEAD points; its modes also update the index or working tree. In particular, reset --hard overwrites files with the target commit and may overwrite untracked files. If the commits have already been shared, rewriting the branch can leave collaborators’ commits based on a different history and requires coordination. It is not an interchangeable form of revert.

If the goal is to restore selected paths, git restore has a different scope from moving the branch. Choose by asking which state must change: shared history, the branch pointer, the index, or named file contents. Similar command names do not mean they operate on the same layer.

There is also an index boundary for multi-commit work. git revert -n applies inverse changes to the index and working tree without automatically creating commits; the manual says it applies against the index state at the beginning of the operation. If other content is already staged, inspect the resulting staged snapshot before committing a range of reversals. Otherwise a request to undo several commits can accidentally include unrelated staged changes.

A merge’s mainline parent affects later merges

An ordinary commit has one parent as its comparison base; a merge commit has multiple parents. git revert -m <parent-number> identifies which parent is the mainline, so the inverse is computed relative to that parent. Parent numbers follow the merge commit’s parent order. Do not assume that “the main branch is usually parent 1” applies to this graph. Inspect the graph and each parent’s tree difference to determine which side introduced the changes you intend to reverse.

The Git manual also says reverting a merge declares that the tree changes brought in by that merge are no longer wanted. On later merges, Git brings in tree changes introduced by commits that are not ancestors of the reverted merge. Therefore merging the same topic branch again will not generally reapply its old commits, which are already ancestors. If the team wants those changes back, make the choice explicit: review a revert of the original revert, or implement the desired behavior in new commits, and inspect the resulting diff. A merge command on the branch name alone does not prove that the old feature returned. The actual graph, conflicts, and resulting tree still decide.

How to prove the source change reached users

A reviewable verification sequence establishes the commit identity, then the artifact identity, then runtime behavior. First record the reverted commit, R’s full SHA and parent, and inspect the R^..R diff. Confirm that it reverses only the intended changes and keeps necessary later edits. Next run the build and tests related to the affected behavior on R. If the command never ran, dependencies were unavailable, or the test is unstable, record an environment problem or an unknown result instead of calling it a pass.

Third, bind the artifact digest to the source SHA. Seeing R on dev does not prove that deployed files were built from R. After deployment, inspect the provider’s commit or artifact identity, the version actually serving the route, and user-visible behavior. If a different commit was selected, a cache still points to the old artifact, or a later commit supersedes the inverse, the source branch alone cannot establish recovery.

Fourth, list state outside Git. Reversing a migration file does not necessarily remove rows already written or restore an earlier data format. A message already delivered to a queue does not disappear when its producer commit is reverted. External payments, notifications, and permission changes require their own compensation mechanisms. If a secret was committed to shared history, revert does not erase historical copies or revoke an exposed credential; rotate it and assess repository mirrors and access separately.

For a hypothetical release with an overly broad authorization check, R may restore the source condition. To claim that user permissions are corrected, also verify that an artifact built from R is deployed, the public route returns the expected authorization result, and caches or background jobs are not still using the old rule. If sensitive rows were exposed during the incident, assess that exposure and remediation too. This is a proposed verification plan, not a result from this site or a real service.

What should be checked before merging a reverted branch again?

Identify the old merge and its mainline parent, then list commits added to that branch after the old merge. The documented ancestry behavior means old commits do not become new changes simply because the branch is merged again. New commits, the revert-of-revert, and conflict resolutions together determine the resulting tree. Use diff, tests, and deployment identity to confirm the behavior that should return instead of inferring it from a branch name.

Shared history can answer which commit changed source. Deployment records answer which build is running. Data and external side effects need their own recovery evidence. git revert addresses the first layer: commit history and source changes. For artifact provenance and rollback acceptance, see artifact and rollback acceptance. No revert, deploy, or production recovery was performed in this repository; no service recovery is claimed.
