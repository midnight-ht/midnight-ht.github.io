Keep remote waits outside the local transaction lifetime

Respect IndexedDB task boundaries and distinguish request success from transaction completion.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-14 · Estimated read 5 min
Translations
zh-CN en

Article

An IndexedDB transaction is active according to event-loop tasks, not for the lifetime of an arbitrary async business function. A remote await can outlive its activity or automatic commitment. Prepare input before establishing the local atomic write scope.

The function can outlive the transaction

The MDN IDBTransaction reference describes activity in the creation task and request event-handler tasks, inactivity elsewhere, and automatic commitment when no pending work remains. Retaining a transaction variable does not keep that activity alive.

Imagine opening a transaction, awaiting product data from the network, and then attempting to write through the original transaction. The resumed work may no longer be in its active scope. Actual behavior needs browser-specific checks; this page was not executed.

Generating meaningless requests to prolong activity obscures the lifecycle and does not make network and local storage atomic. Remote success, local commitment, and user-task completion need separate states.

Prepare and validate before writing

After fetching, confirm that the result still belongs to the current task before starting a suitable local transaction. Cancellation or object switching can invalidate an old response. This is a proposed design requiring identity and failure validation.

A single request’s success is also not the transaction’s final completion. Later operations can fail. Observe transaction-level completion or abort before announcing that all data was saved; otherwise an early message overstates the evidence.

Specify failure recovery

Storage still faces permissions, capacity, and application changes. Decide whether unsaved input is retained, how retry works, and how duplicate business records are avoided. No cross-browser measurements or guarantee of asynchronous saving during page closure is offered.

Proposed checks cover remote waits, cancellation, intermediate write failure, and final transaction events. For response identity, see cancellation and stale-result submission. The goal is a clear local atomic boundary, not an indefinitely extended transaction.
