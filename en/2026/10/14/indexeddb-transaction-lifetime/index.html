Can an old IndexedDB transaction still write after `await fetch()`? Check its state

After IndexedDB requests are handled and control returns to the event loop, an old transaction may auto-commit; keep network waits before the short local write transaction.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-25 · Estimated read 21 min
Translations

Article

Key takeaways

  • Retaining a transaction reference does not mean it is still active.
  • Finish the network request first, then check the local revision and write in a short transaction.
  • Request success, transaction complete, and server-side effects are separate states.

If an IndexedDB request has been handled, no database request remains pending, and the code then waits for fetch(), it may be too late to write through the old transaction when the promise resumes. The cause is not that the await keyword always closes a transaction. IndexedDB manages its own active state and request queue: after control returns to the event loop, the transaction may enter automatic commit. A JavaScript variable can still reference the IDBTransaction object without making it active again. A safer order is to finish the network wait first, then open a short transaction, check the local version, and write.

The transaction object can exist after requests are no longer allowed

IndexedDB describes transaction states as active, inactive, committing, and finished. The W3C Indexed Database API 3.0 draft says a transaction is active when created and while success or error events for its requests are being dispatched; script can enqueue another request during such an event handler. After control returns to the event loop and no request event is being dispatched, the transaction becomes inactive. Inactive transactions do not accept new requests. Once pending requests have completed, their results have been handled, and no new requests have been placed, the user agent must attempt to commit. This lifecycle is not the same as the interval between entry to and return from an async function. The specification page currently identifies itself as a W3C Working Draft dated 2026-10-30, not a published Recommendation; it is cited here as the current draft text, not as a final standard. Indexed Database API 3.0, §2.7.1

The MDN IDBTransaction reference likewise describes activity in the creation task and in request success or error event-handler tasks, inactivity in other tasks, and automatic commitment when there are no new or outstanding requests. The deciding factors are state transitions and requests, not whether a variable remains in scope. The transaction remains a referenceable object, but it may already have committed or may be in a state that rejects more requests. A later transaction.objectStore("drafts").put(...) can then raise a state error; that does not mean the fetch itself failed.

How an external wait crosses the local transaction boundary

Break the sequence into events. The page creates a readwrite transaction and reads a row from drafts. The browser dispatches the request's success event. If the handler queues no further IndexedDB request, the read is complete and the transaction has no pending work. After control leaves the event task, the browser can attempt to commit. Meanwhile, the business function is waiting for a network preview; hundreds of milliseconds later its promise resumes with a reference to the old transaction. To write the new result it needs a transaction that still accepts requests, and the old reference cannot do that.

This is a hypothetical state sequence, not a reproduction run for this article. The specification allows requests to be queued while a request event is being dispatched, so “never use await” is too broad. If a promise wraps an IndexedDB request and continuation scheduling happens in relation to that request's event, the exact behavior depends on the actual code and wrapper. A more useful question than whether the source contains await is: did the event loop run between creating this transaction and placing the next .get() or .put()? Have all earlier IndexedDB requests been handled? Was the next request queued while the transaction was still active? MDN's Using IndexedDB guide also emphasizes the relationship to the event loop and that returning to it without placing more requests makes the transaction inactive.

Do not use timers, empty requests, or write loops to “keep it alive.” That turns a small local atomic operation into prolonged transaction occupancy and makes concurrent read/write scope harder to reason about. It also cannot make a remote HTTP operation part of an IndexedDB atomic commit: if the server has already received a request and the local write later fails, the browser cannot roll back the server-side effect. Short transactions make it clearer which changes commit together and which require compensation.

Fetch first, then check the version inside a short local transaction

Suppose an editor requests a preview from a server and stores it alongside a local draft. Fetch the result first, then open a readwrite transaction; inside that transaction, read the current draft version and decide in the request success handler whether to write. The following ordering is a design example and was not run in a browser:

const response = await fetch(previewUrl);
if (!response.ok) throw new Error("preview request failed");
const preview = await response.json();
if (taskId !== currentTaskId) return; // the user switched or cancelled

const tx = db.transaction("drafts", "readwrite");
const store = tx.objectStore("drafts");
const read = store.get(draftId);
let stale = false;
read.onsuccess = () => {
  const draft = read.result;
  if (!draft || draft.revision !== requestedRevision) {
    stale = true;
    tx.abort();
    return;
  }
  store.put({ ...draft, preview, revision: draft.revision + 1 });
};
tx.oncomplete = () => showSaved();
tx.onabort = () => stale ? showConflict() : reportStorageFailure(tx.error);

There are two distinct guards. The taskId check stops an old promise from updating a new view after the user changes or cancels the task. The revision comparison in the request success handler prevents a local draft changed during the network wait from being overwritten. The read and put are in one transaction, and the comparison queues the write only after the read result arrives; this avoids the race window between checking a version outside the transaction and opening another transaction to write. If the row is missing or the version differs, the example aborts deliberately and presents a stale-result conflict instead of silently overwriting local content. On failure, retain unsaved editor text and offer the user a choice to refresh, merge, or discard.

Keep the transaction scope limited to the object stores actually needed. IndexedDB does not coordinate consistency across a network request and local storage. If the application must also send an action to the server, it could store the local draft and an outbox intent with a stable business key in the same transaction, then send after complete. The server would need to deduplicate by that key. This is still not a distributed transaction: if sending succeeds but the acknowledgement is lost, retry deduplication and state reconciliation remain application and server responsibilities. A preview cache may only need a simple retry; a payment, external message, or irreversible action needs server idempotency, reconciliation records, and a defined compensation path.

Request success, transaction completion, and durability are different claims

An IDBRequest success event says that one request returned a result or was processed. A later request in the same transaction can still fail. Showing “everything saved” in the first put success handler is premature. Register complete and abort handlers when creating the transaction, then treat complete as the boundary for successful commitment of that group of local requests. MDN defines the complete event as firing after successful commit; the W3C draft describes attempting an atomic commit after pending requests complete, their results are handled, and no more requests are placed. A failed request that is not handled under IndexedDB's error-event rules can abort the whole transaction, so the application must treat abort as failure of the unit.

Even complete should not be inflated into “the data is permanently on disk under all conditions” or “the server has synchronized it.” IndexedDB durability options are hints that a user agent considers during commit; default behavior depends on the implementation. This article describes a page-observable successful transaction, not a universal guarantee about persistent media or completion of a server action. Page closure, quota exhaustion, device failure, and browser cleanup are separate concerns. Products needing stronger save guarantees should check durability support and behavior in their target browsers and define any server copy policy, instead of keeping a transaction open while waiting on a network. MDN's IDBDatabase.transaction() reference describes transaction scope, modes, durability options, and the advice to limit scope to the stores actually needed.

How to verify the boundary

Run a controlled test in each target browser. Issue an IndexedDB get; after its success event, do not immediately queue another request; delay fetch with a test server, then attempt to write through the old transaction. Record the order of get success, transaction complete or abort, network response, and write-request event. In a second case, queue put synchronously from the get success handler and confirm that the transaction can be extended while that request event is being dispatched. In a third case, make a write violate a unique index constraint and verify that the application sees transaction abort rather than treating an earlier request success as success for the group. Finally test cancellation, a version conflict, network timeout, and retry deduplication. These are proposed checks, not browser test results from this batch; record actual versions and outcomes for the deployment matrix.

In an implementation, keep network waiting, JSON parsing, cancellation, and task-identity checks before the local transaction. Put related local reads and writes in a narrow, short transaction. Keep “local transaction completed,” “server received the action,” and “server state reconciled” as separate states. Only the last local database operations are protected by IDBTransaction. For the identity of asynchronous frontend results, see cancelling requests and avoiding stale-result submission.
