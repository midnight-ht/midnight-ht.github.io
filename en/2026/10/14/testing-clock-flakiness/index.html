Fixed dates, fast-forward, and ticking clocks test different behavior

Playwright's fixed-date, fast-forward, ticking, and system-time controls produce different callback behavior. Define the time semantics first, then choose an API and assert the product outcome.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-25 · Estimated read 18 min
Translations
zh-CN en

Article

Key takeaways

  • setFixedTime fixes Date readings while timers keep running; it does not simulate elapsed time.
  • fastForward fires due timers at most once, while runFor advances through the interval and fires relevant callbacks.
  • A browser clock does not advance server time; check the Playwright version and the time boundary under test.

Fixing Date does not necessarily stop timers, and fast-forwarding is not the same as running every callback in the interval. Before choosing a clock control, say whether the test is about a displayed date, elapsed time, or a sudden system-time change. Otherwise, “make time go faster” bundles different product promises into one test setup. When it fails, it becomes difficult to tell whether the page is wrong or the test chose the wrong clock operation.

A fixed date value does not stop timer callbacks

Playwright’s current Clock guide uses setFixedTime to fix the values returned by Date.now() and new Date() while timers continue running normally. It fits cases such as a date label, billing-cycle date, or event start time where the test only cares which date is displayed. It does not pause setTimeout or setInterval, and it does not make elapsed time pass automatically.

Consider an illustrative page that calls render() every second. The function reads Date.now() and calculates how many seconds remain before an event ends. If the test only fixes Date, the callback still runs, but each calculation uses the same fixed reading. The displayed countdown may remain unchanged. Increasing an assertion timeout from one second to ten seconds has not advanced the application clock; it has only made the test wait nine seconds longer. By contrast, if the page periodically formats a fixed date and writes it back to the screen, the timer continues to run while the displayed value stays constant. That may be exactly the contract of “fixed date, periodic refresh.”

Separate two questions: what should the current time value be, and when should callbacks run? Checking a single fixed string does not prove that a countdown advances. Seeing a callback run does not prove that the deadline state is correct. State the product rule first. For example, “show an expiry notice after five minutes without activity.” Then decide whether the test should advance five minutes, whether each interval callback should run along the way, or whether it only needs to jump to the deadline.

Installation timing is part of page initialization

To control both date values and timers, Playwright’s page.clock.install() installs controllable browser time functions. Included in the current list are Date, setTimeout, setInterval, animation-frame callbacks, performance, event timestamps, and related APIs. This control belongs to the entire BrowserContext, so pages and iframes in that context share it; its scope is not one assertion or one tab.

Installation order changes the page’s startup conditions. The Clock API reference recommends installing the clock before navigating and initializing it slightly before the time the test wants to inspect; after the page has loaded, the test can pause at the target time. This matters because application startup may register intervals, wait on delayed callbacks, or initialize state based on elapsed time. If the page first registers that work using native clock functions and the test later replaces those functions, part of the application started under a different clock. There is also an order requirement: install() must precede other Clock-related calls in the test, or the order is undefined.

The following is illustrative only. It was not run in a real project or browser:

await page.clock.install({ time: new Date('2026-01-01T11:55:00Z') });
await page.goto('/session');
await page.clock.pauseAt(new Date('2026-01-01T12:00:00Z'));
await expect(page.getByText('Session expired')).toBeVisible();

The intent is to let the page load naturally from a time before the deadline, then jump to the deadline and pause. A real test still needs to handle the product’s time-zone, authentication, and page-initialization requirements. The URL and message are hypothetical; this script was not executed here. If the server owns session expiration, browser-clock control alone cannot establish whether the server will reject a request.

Fast-forward, ticking, and setting system time are different

Similar method names do not promise the same callback path. fastForward() is like putting a device to sleep and waking it later: it jumps into the future and fires each due timer at most once. It is useful for checking the final state after a deadline, but it cannot prove that an animation or poll ran once per second during a five-second interval.

runFor() advances the clock for the specified duration and fires the relevant time-related callbacks along the way. It fits checks for periodic tasks, repeated updates, or interactions between timers. If a page updates every second, running for five seconds may produce a different observation from fast-forwarding five seconds: the former processes callbacks through the interval; the latter fires due timers at most once. Choose based on the page’s actual semantics, not on which operation completes faster.

setSystemTime() is different again. The documentation says it changes the current system time but does not trigger timers. It can be used to inspect how a page responds to a clock jump, such as a daylight-saving or time-zone change. It is not equivalent to making the application experience that duration. To test a timeout callback, choose an operation that advances the relevant clock and triggers the scheduled work. To test a sudden calendar or system-clock shift, use a system-time change.

Playwright’s API reference dates these Clock methods from v1.45. For an older project, check the locked Playwright version and its matching documentation before relying on them. Their reach ends at the documented browser-context APIs; they do not change the clocks of a server, database, message queue, or separate process.

Use a deadline to choose the assertion

Suppose the product rule is to show “Session expired” after five minutes with no activity. This is a hypothetical test-design example, not a customer story. The test could confirm that a countdown appears after page load, perform an interaction that resets activity time, advance four minutes and fifty-nine seconds and assert that the session is still active, then advance the final second and assert that the notice appears. The point is not to copy this schedule; each assertion should correspond to a defined product boundary.

If the implementation combines Date.now() with setTimeout(), choose a Clock operation that makes the two mechanisms progress consistently. Fixing Date alone may stall the calculated difference; changing system time alone does not fire the timeout. If the test models “the laptop was asleep and has just woken up,” a fast-forward can check the final state after due work, but it cannot establish that every poll in the gap ran. To observe each tick, use the callback-by-callback progression path and assert an actual state or count, rather than merely asserting that a clock method was called.

A misleading counterexample is a browser clock reaching expiry while the page shows a logged-out state, but the server still accepts a request. Or the browser clock may move backward while the server deadline remains unchanged. Either behavior may be an architectural choice or a security defect; the product contract and server-side tests decide which. Playwright Clock can isolate front-end time logic. It cannot prove that the backend clock changed, and it cannot replace an assertion about the request result.

Specify the time semantics before increasing a timeout

Classify the assertion before writing the test: date formatting reads a fixed value; a recurring countdown needs elapsed time and periodic callbacks; waking after sleep checks the state after a jump; a system-clock adjustment checks a sudden shift; a server deadline needs a controllable server clock or an explicit API contract. Then check the Playwright version, installation order, BrowserContext sharing, and whether startup code creates timers.

The test need not wait for a long real duration. Assert the visible business state before the boundary, at the boundary, after it, and after cancellation or reset. If a callback has not run after time control, inspect the selected operation’s semantics, installation timing, and call order. If the interface changes but the business request still succeeds, inspect the server’s time source instead of continuing to adjust the browser timeout. For asynchronous condition selection, see Playwright auto-waiting and outcome conditions. A Clock API arranges test conditions; the assertion must say what the user sees and what the system does at the relevant time boundary.
