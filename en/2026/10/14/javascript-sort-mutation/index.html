Why does `sort()` change the original array?

`sort()` mutates its array and returns the same reference; copying the container does not isolate its record objects.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-25 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • sort() mutates the array container; different variable names do not imply different references.
  • toSorted() or a shallow copy creates a new container, while record objects may remain shared.
  • Choose based on container ownership, comparator contract, target runtime, and field ownership; validate in the real environment.

Array.prototype.sort() rewrites the array it is called on and returns the same array reference. Any timeline, cache, or component that still holds that array can observe its new order. If a view needs a sorted result of its own, first decide who owns the original container. toSorted() or sorting a copy preserves the container order, but a shallow copy does not isolate the record objects inside it.

Who still holds the same array?

Imagine an order service gives a page one orders array. A timeline displays it by creation time; a ranking displays it by amount. If both modules receive the same array object, the ranking's call to orders.sort(compareByAmount) changes that object in place. Different variable names and different components do not create different underlying arrays. The timeline's next read sees the amount order. If it also retained a separate index or pagination cursor, the visible sequence can then disagree with that cursor.

The reference graph is simple: “timeline ─┐” and “ranking ─┴→ the same array.” The value returned by sort() still points to that one object; it is not a second sorted view. This is a semantic example, not a result observed in a framework or browser, and it does not claim a real production incident. It shows why a useful diagnostic question is “Who holds this container?” rather than only “Who called sort?”

A one-line assignment can hide the ownership change:

const ranking = orders.sort(compareByAmount);

ranking looks like a new result, but it is the same array as orders. Sorting ranking again also changes the order seen through orders. MDN explicitly describes sort() as returning a reference to the original array. An implementation that promises to return a view but calls sort() on its input can therefore violate an ownership boundary that callers rely on.

A copied container does not copy the orders

Changing the call to orders.toSorted(compareByAmount) creates a new array container and preserves the original array's arrangement. In older runtimes without toSorted(), use [...orders].sort(compareByAmount) or Array.from(orders).sort(compareByAmount). MDN marks toSorted() as Baseline Widely available since July 2023. That still does not replace a compatibility check for the project's runtime, embedded WebViews, and test environment.

This is only a shallow copy. The new array can still share references to the original order objects; after sorting, the same object may occupy a different index. If the ranking writes a temporary display field such as sorted[0].displayAmount, the matching object in the original array now has that field too. The timeline's order remains unchanged, but the record is still shared and mutable. Whether to copy each record, use immutable data, or calculate the display label during rendering depends on who owns that field. toSorted() alone does not establish data isolation.

The distinction also changes the debugging path. If a second list changes order, trace array references and sort calls. If the order is stable but a field changes, trace object references and field writes. Calling both symptoms a “deep-copy problem” can send the fix to the wrong layer. For a different ownership mechanism, see structured cloning and transfer boundaries; it is not the default replacement for every list sort.

The comparator also has a contract

Without a comparator, sort() converts elements to strings and compares those strings. MDN's numeric example produces [1, 100000, 21, 30, 4], not numeric ascending order. For numeric amounts, state the direction explicitly, for example (a, b) => a.amount - b.amount. If an amount may be missing, NaN, or arrive in mixed types, define whether those values sort first, last, or are rejected.

ECMAScript requires a consistent comparator. The same pair should produce the same result, comparison must not mutate the objects being compared, and reflexivity, antisymmetry, and transitivity must hold. The implementation determines the order and number of comparator calls, so do not increment business counters, send requests, edit records, or depend on which pair is compared first. A common error is (a, b) => a > b ? 1 : 0: when a is greater it returns a positive value, but the swapped pair may still return zero, violating antisymmetry. MDN demonstrates this malformed comparator producing different results in V8, JavaScriptCore, and SpiderMonkey. When results diverge, correcting the comparator is closer to the cause than changing engines.

Sorting has been stable since ECMAScript 2019: elements that compare equal keep their relative order from before the sort. Stability is useful, but it does not make a business order reproducible by itself. If equal-amount orders came from an uncertain merge of pages, stable sorting merely preserves that uncertain input order. For repeatable output, add explicit keys such as amount, creation time, and finally an immutable order ID. Stability preserves an existing order; a secondary comparator key defines the product rule for equal amounts.

When to copy and when to mutate

If an array came from a cache, state container, function argument, or is read by several views, treat a sorted result as derived data: use toSorted() or copy before sorting. In-place sort() can be simpler when the code exclusively owns a temporary array, no longer needs its previous order, and its caller contract permits mutation. The decision follows ownership and lifetime, not unmeasured claims such as “immutability is always faster” or “in-place sorting always uses less memory.” Copying retains another array container; temporary space and actual cost also depend on the runtime and data size, so measure in the target environment.

Keep the sorted container's role separate from the order records' role. If a ranking only changes presentation order, it should not write back into business records as a side effect. If the user is permanently changing priority, that is not a display sort: it needs an explicit save operation, authorization, and conflict handling. The UI action should match the data action; preview sorting and persisted ordering should not share ambiguous logic.

How to verify order ownership

A minimal proposed test matrix starts with orders that have stable IDs and records the input ID sequence. After calling the view-sorting function, check whether the input sequence stayed the same. Then check whether the result is a new container and whether its order objects are still the same objects as the inputs. Finally test equal amounts, missing amounts, a default-comparator counterexample, and what a second consumer reads after sorting. Comparator samples can separately check sign reversal for swapped inputs and transitivity across triples; one engine output is not proof of comparator correctness.

These are proposed checks. No browser, Node.js, or business test was executed for this historical rewrite, and no memory or performance measurements were made. Even passing checks would establish only those assertions in the tested data and runtime; they would not prove that every consumer was found or that another write path cannot mutate shared fields. Recording order, object identity, and lifetime separately helps identify an array mutation instead of misdiagnosing it as a random sorting algorithm or a failed copy method.
