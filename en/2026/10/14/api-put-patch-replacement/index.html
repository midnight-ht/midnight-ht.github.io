A contract table for PUT and PATCH updates

PUT uses a request representation to define target state; PATCH applies instructions in a specified format. The contract table covers omissions, nulls, arrays, and stale versions, while concurrency and domain commands need separate rules.

Article

Key takeaways

  • PUT expresses a replacement representation; PATCH expresses instructions, so sparse input needs an explicit contract.
  • Merge Patch treats null as removal and replaces arrays as a whole; explicit null values or element-level list edits may need another format.
  • Concurrency conditions, replay safety, authorization, and domain validation do not come from the PATCH method name.

The boundary between PUT and PATCH belongs in an update-contract table: PUT uses the request representation to define the target state, while PATCH applies instructions in a specified patch format. PATCH does not define null, arrays, concurrency conflicts, or replay behavior for a particular API. Choose based on whether the client sends a complete representation or a modification document with explicit rules—not merely because one form field changed.

Define the resource representation first

An HTTP resource is not synonymous with a database table. An API may expose a representation assembled from several tables, derived fields, and state, or only part of what is stored. RFC 9110 defines PUT as requesting that the target resource's state be created or replaced by the state defined by the request representation. RFC 5789 defines PATCH as applying a set of modification instructions carried by the request. Those standards establish operation intent; they do not decide how a particular business API maps an omitted JSON property to a database column. Define the resource representation and its persistence mapping first.

Suppose a profile currently has this representation:

{
  "displayName": "Lin",
  "biography": "Enjoys hiking",
  "locale": "zh-CN",
  "notifications": ["security", "product"]
}

The user changes only the biography. If the client sends { "biography": "Enjoys road cycling" } with PUT, the server cannot infer “partial update” from an undocumented convention. If the endpoint treats the request as the complete representation, the client has not supplied displayName, locale, or notifications; the server might reject an incomplete representation or apply the replacement behavior defined by its resource contract. The contract must say which behavior applies. Do not treat a server's current habit of retaining some fields as a guarantee from HTTP, and do not silently interpret a sparse object as a complete replacement.

PATCH still needs a specific patch format

PATCH says that the request carries modification instructions. It does not make every PATCH body share one structure. A server interprets a patch according to its media type and should document supported formats, potentially advertising them with Accept-Patch. A client cannot infer a universal meaning for omitted fields, null, or arrays just from the method name.

JSON Merge Patch (RFC 7396) represents changes with an object resembling the target JSON document. Members absent from the patch remain as they are; ordinary values add or replace members; a member whose value is null means removal. The format is intended for documents primarily structured as objects and that do not need explicit null values as ordinary data. Arrays are not merged element by element: an array value replaces the target array as a whole. If a resource must distinguish an existing field whose value is explicitly null, Merge Patch's null-as-removal rule cannot by itself express “set this field to null.”

JSON Patch (RFC 6902) is a sequence of operations such as add, remove, replace, move, copy, and test, applied in array order to JSON Pointer paths. A test operation can state an expected old value—for example, assert that locale is still zh-CN before changing the biography. This adds complexity around operation order, path escaping, and failure handling. If an operation cannot be applied, the whole PATCH must still obey RFC 5789's atomicity requirement: the server must not leave only some changes applied. Confirm that the server implementation and resource model support the selected operations before adopting this format.

Use a hypothetical profile to separate omission, clearing, and replacement

For the profile resource, imagine three distinct intentions: change only the biography, clear the biography, and replace the entire notification preference list. With Merge Patch, the first can send just biography. The second can send "biography": null, but the API must document that this means removing or clearing the property rather than storing an ordinary null value. The third can send a complete notifications array; that replaces the whole array, so a client should not expect one element to be merged. If the domain needs explicit null values or single-element array operations, consider JSON Patch or a purpose-built domain operation, and document the allowed paths and operation scope.

Request case Contract question Typical acceptance outcome
PUT omits a public field Is the representation invalid, or is that omission part of the resource definition? Reject it or apply a defined complete-representation rule; never assume retention
Merge Patch omits a member Does omission mean no change? An absent object member remains unchanged
Merge Patch supplies null Does it mean removal or a storable empty value? RFC 7396 removes that member
Merge Patch supplies an array Modify one item or replace the list? The array value replaces the target array
Conditional update is stale Must a write based on an old version stop? A failed If-Match condition prevents the method; 412 is available

This is a hypothetical API design exercise. No live API, database, or browser was used. It explains how a request could express intent; it is not evidence that a service implements these semantics. { "biography": "" } is yet another value. Unless the contract defines otherwise, an empty string, null, an omitted property, and a delete request are not interchangeable. Server validation must check more than JSON syntax: it must check whether a field is writable, whether its value satisfies domain constraints, and whether the final resource remains valid.

Concurrency and repeated delivery are separate contracts

Even when PATCH precisely means “change the biography,” two clients can still edit from the same old version. Client A reads ETag "v7"; client B changes the locale and advances the resource to "v8"; if A later submits an unconditional full representation based on the old read, B's change can be lost. For a change computed from a known version, the client can send If-Match: "v7". RFC 9110 requires strong comparison for If-Match. If the current representation does not match, the server must not perform the method and can return 412. The client should reread, merge the user's intent, and let the user resolve a real conflict instead of automatically resending stale content.

PATCH itself is not guaranteed to be idempotent, although a specific patch can be designed to be. Setting a field to a fixed value and issuing an “increment by one” instruction have different replay consequences. A network timeout also does not prove the server skipped the change: if the response was lost on its way back, blindly resending might cause another side effect. Decide whether retry is safe from the endpoint contract, using If-Match, an idempotency key, or an operation-status lookup when appropriate. Confusing the HTTP method, patch format, concurrency condition, and business replay policy makes recovery a guess.

PUT can also be combined with If-Match to prevent a full replacement based on a stale read from overwriting another user's change. Its complete representation can make comparison and repeated submission easier; it does not eliminate concurrency conflicts or guarantee that side effects outside a database transaction are absent. If a client has only a partial representation, choosing PUT may force it to fetch, edit, and submit the whole resource—or force the server to define a non-standard sparse-PUT convention. The latter can work, but callers need to know that its semantics do not follow from the method name alone.

When a generic PATCH endpoint is the wrong abstraction

A generic patch format is not ideal for every domain operation. Increasing a cart quantity, approving a payment, or claiming a one-time reward is closer to a command with permissions and business preconditions than arbitrary representation editing. If clients can send replace /status to mark an order paid, the API may expose a path around payment validation. A safer interface often gives the action a named command and lets the server validate authorization, current state, business rules, and duplicate-request handling.

Fields can also be interdependent. A start time must precede an end time, or notification preferences may allow only certain combinations. Applying fields one at a time could create an invalid intermediate state. RFC 5789 requires all direct modifications within a PATCH to be atomic, but atomicity does not make domain validation correct by itself. The server still needs to validate the final state in a controlled transaction and consider whether related resources and side effects share that transaction boundary. A database rollback alone cannot guarantee consistency with an external system; define compensation or status-query behavior where needed.

Turn the contract into an acceptance matrix

Before implementation, list the meaning and error behavior for each public field: Should an incomplete PUT be rejected or treated as a complete replacement? Does an omitted PATCH member remain unchanged? Does explicit null mean removal, a valid value, or a validation error? Does a list replace the whole array or use element-level operations? What happens when a client modifies a read-only field? Do concurrent versions produce 412? If an intermediate patch operation fails, is partial persistence prevented? Accepted patch formats should be documented by media type; a client-library default is not a contract.

Build tests from a known initial resource and an expected final state, not from “got 200” alone. Cover complete PUT replacement, incomplete PUT representation, omitted PATCH properties, null, empty string, array changes, read-only properties, malformed syntax, a failed JSON Patch test, a stale If-Match validator, and the status-query path after a lost response. Record the initial state, request and Content-Type, expected status, complete result representation, whether any side effect occurred, and whether replay is safe. These are proposed acceptance tests; no API or performance tests were run for this article.

Use PUT when the request fully represents the resource state it replaces and its constraints are documented. Use PATCH after the patch format, field semantics, and concurrency behavior are defined. A form changing one input is not, by itself, a protocol definition for partial updates.
