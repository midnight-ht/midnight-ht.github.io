Define replacement and patch instructions before choosing an update method

Distinguish replacement from patch instructions, including omissions, nulls and concurrency.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-14 · Estimated read 5 min
Translations
zh-CN en

Article

A single-field change should not automatically be represented as a sparse PUT object. PUT requests creation or replacement of the target resource’s state using the supplied representation; PATCH carries modification instructions. Define omitted fields, nulls, and the patch format explicitly.

Representations and instructions differ

RFC 9110’s PUT definition describes creation or replacement intent. RFC 5789 contrasts the modified representation sent with PUT and the instructions sent with PATCH. Neither requires a resource to correspond directly to one database row; define the representation’s fields.

Suppose a profile editor sends only a biography. If treated as replacement, omitted fields need specified behavior: retaining, clearing, or rejecting them must not emerge accidentally from database code. This example was not executed and alleges no actual data loss.

Omission and explicit null may represent different intentions, but their meaning depends on the interface and patch format. Missing a JSON key does not universally mean retaining the previous value. Clients need a contract before making the change.

PATCH does not supply every update guarantee

RFC 5789 says PATCH is not inherently idempotent, although a request can be designed that way. Setting a fixed field and incrementing a counter can behave differently when repeated. Renaming the method does not prevent duplicate effects.

Concurrent editing also needs version conditions or a conflict policy. Clear single-request semantics do not prevent stale updates overwriting another user’s work. No universal implementation or patch-format suitability is claimed here.

Verify the intended operation

Proposed checks cover replacement, omission, clearing, repetition, and stale versions. Verify server-side restrictions on non-editable fields rather than relying on a hidden control. A successful status must match the accepted scope.

A returned representation describes a processing-time state; another client may subsequently change it. For concurrency, see conditional updates and version conflicts. Establish the operation’s meaning before designing conflict and retry handling.
