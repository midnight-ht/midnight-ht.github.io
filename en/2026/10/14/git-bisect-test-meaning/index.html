Git bisect can narrow the range and still leave the culprit uncertain

A bisect result depends on a consistent property predicate. Separate setup errors, behavior regressions, and skipped revisions before interpreting a boundary or making a causal claim.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-25 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • Define the property, endpoints, and measurement conditions so an unrelated build failure is not called a behavior regression.
  • `git bisect run` distinguishes 0, 125, and other statuses; 126/127 do not automatically mean untestable.
  • Skipping near the transition preserves an uncertain range; localization still needs diff and mechanism validation.

git bisect narrows a trustworthy range only when both endpoints and each tested revision are classified against the same property; a build failure, a failing assertion, and an untestable revision are different evidence. Even when it reports a commit, it has located a transition in an observable property. You still need to inspect the diff and validate a mechanism before calling the commit—or its author—the complete root cause.

Define the property you are searching for

As checked on 2026-11-25, the Git git-bisect manual page lists version 2.56.0 (and says 2.56.1 has no changes); that is the document version, not the Git version installed by a reader. The manual describes searching from known good to bad revisions and also supports old/new terms for other property changes. The property should be concrete enough to test, such as “the same input produces p95 latency above a threshold,” not the vague statement “the system is slower.” Each revision must be evaluated against the same property, inputs, measurement rule, and comparable environment. If the good endpoint never exercised the target path, or the bad endpoint does not meet the predicate, binary search only narrows a set of incorrect assumptions.

For an automated search, the classifier is part of the measurement instrument. A failing assertion can support a bad classification. A missing compiler, unavailable dependency source, stopped database, or test process that never ran says nothing about the target behavior. Collapsing those cases into one nonzero result turns “could not test” into “behavior is broken.”

Exit codes classify; they do not summarize logs

The Git manual defines the git bisect run contract: exit 0 means good/old; a status from 1 through 127 except 125 means bad/new; 125 means the revision cannot be tested and should be skipped; other statuses abort the search. Git does not inspect the log or infer whether a failure was an assertion or test setup. In particular, POSIX shells use 126 and 127 for a command that cannot execute or cannot be found, but those values are still in the bad/new range for bisect run unless an outer script maps them to 125 or aborts.

The wrapper therefore has to understand the test tool. A short build && test command may be insufficient: if the build fails with status 1, Git classifies that revision as bad; a missing test command returning 127 may also be treated as bad. A safer wrapper validates prerequisites first and returns 125 or aborts when the environment cannot test the revision. Only after the target probe actually runs and meets a defined failure condition should it return a bad status. If the probe itself reports timeouts, assertion failures, and external-service outages as the same 1, the wrapper cannot recover the distinction; the probe needs a better classification contract.

Walk through a hypothetical search

Suppose a team is locating a change in API latency. An older revision is known to meet a threshold under reproducible inputs, while the current revision exceeds it. The team defines the predicate as “the same request sample exceeds the threshold,” rather than relying on one monitoring screenshot. For every candidate it fixes the request sample, measurement steps, and dependency-service version, and records the actual values and environment.

One revision uses an older build tool that cannot start in the present environment. The wrapper confirms that the failure occurred before the API probe began, classifies that revision as untestable, and uses 125 to skip it. On other revisions, the probe runs; only a stable reproduction above the threshold is bad, while a result within the threshold is good. This is an illustrative scenario. No git bisect session or service test was run, and no actual regression commit was found.

If the skipped revision is adjacent to the good/bad boundary, Git explicitly warns that the first bad revision may not be uniquely identifiable. Record the last confirmed good revision, earliest confirmed bad revision, skipped revisions, and remaining candidate boundary. Do not present a nearby commit from the output as a unique answer. If you repair the environment, confirm that the workaround only makes the old revision buildable and does not change the latency property. Otherwise the measurement applies to a revision with a compatibility patch and has a narrower scope.

A located revision still needs causal validation

A commit may change a query, cache, and logging at once; a regression can also result from an older change interacting with new configuration. Bisect locates history under the supplied predicate; it does not understand the application mechanism. Editorial judgment: if the property changes several times across history—slow, then fast, then slow again—the question “first bad” must be narrowed to the specific transition or time interval of interest. Treating commit identity as cause skips this step.

After localization, inspect the candidate diff and identify a path that explains why the target input crossed the threshold. Then design a check that distinguishes competing mechanisms: disable one change, pin a dependency, compare query plans under the same input, or replay a smaller set of changes. These are follow-up causal-analysis methods, not evidence that bisect supplies automatically. A symptom disappearing after a revert is a clue, but if the revert removes several changes, it does not prove which one was necessary.

Keep a correctable search record

Retain the endpoints and how they were verified, the predicate, Git version, environment image or dependency lock, each candidate’s classification, skip reasons, script version, output logs, and final diff. For timeouts or flaky tests, also retain the repetition count and classification rule; otherwise someone may see only a final bad marker without knowing its evidence strength. Git provides git bisect log for the session. If a classification was wrong, the log can be edited and the session corrected with git bisect reset and git bisect replay. A replayable log does not make the experiment automatically reproducible; the environment and measurement inputs still need to be recorded.

Write the conclusion with its boundary: “Under this environment, these endpoints, and this predicate, the change falls within the interval between the confirmed good and bad revisions; later validation supports this candidate as an explanation for the observed difference.” If there are skipped revisions, preserve the candidate interval. For how to make follow-up actions verifiable, see postmortem actions and verifiable risk reduction. No search was run against this repository; the example and classification sequence are review methods, not a completed incident investigation.
