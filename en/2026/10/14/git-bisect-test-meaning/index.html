Define a reliable predicate before interpreting a bisect result

Use a reliable bisect predicate and preserve uncertainty before making causal claims.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-14 · Estimated read 5 min
Translations
zh-CN en

Article

git bisect depends on reliable good/bad classification. It narrows where an observable property changed; environmental failures and flaky tests can misclassify revisions. A selected commit still needs diff and mechanism investigation before a root-cause claim.

Use trustworthy endpoints and a predicate

The Git bisect reference describes searching between known endpoints and supports properties beyond bugs. Automated execution uses defined exit codes, with 125 for an untestable revision. Do not classify installation, compilation, and target assertion failures identically.

Imagine an old build tool incompatible with today’s environment. Compilation fails before the test runs, so treating it as bad contaminates the search. No repository search was executed here. Confirm that the classifier distinguishes preparation failure from the target behavior first.

Likewise, a historical successful build is not a good endpoint if the relevant feature was never checked. Validate both endpoints under reproducible conditions and record inputs, environment, and classification criteria.

Keep untestable boundaries uncertain

Skipping revisions permits progress, but untestable versions near the boundary can prevent unique identification. Preserve candidate ranges and skip reasons rather than overstating the final output. Any temporary compatibility adjustment needs a statement about whether it changes the tested property.

An intermittently passing test also undermines classification. Repeating until a preferred result appears creates false certainty. Repetition and agreement rules should follow the failure mode, not a promise that binary search always identifies one responsible commit.

Identity is not the end of causality

Inspect how the change affects input, state, or dependencies and validate the proposed mechanism. One commit can contain several actions or expose an older latent condition. Blaming its author cannot substitute for explanation; reverting and observing silence is not a complete repair argument.

A proposed record retains the predicate, endpoints, skipped revisions, search log, and final diff. None were executed. See postmortem actions and verifiable risk reduction. Localization evidence still needs failure-condition validation.
