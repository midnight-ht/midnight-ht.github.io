Define the base and reference before composing an API URL

The URL constructor resolves references by path rules; a trailing slash, root-relative input, and an absolute input produce different destinations.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-25 · Estimated read 20 min
Translations
zh-CN en

Article

Key takeaways

  • `/v2` treats `v2` as a replaceable final segment; `/v2/` expresses a directory boundary.
  • `users`, `/users`, and an absolute URL are different reference forms; the latter two can leave a service prefix or change the origin.
  • Successful construction proves parsing only; destination authorization, redirects, and network boundaries need separate controls.

For example, new URL("users", "https://api.example.test/v2") replaces v2; ending the base in /v2/ preserves it as a directory. Changing the reference to /users starts again at the origin root. A correct endpoint therefore depends on three separate decisions: the base's directory boundary, whether the reference is relative or root-relative, and whether the resulting destination is allowed. The example domain is illustrative and does not identify a real service.

The last path segment is not automatically a directory

The URL constructor takes a URL reference and an optional base, then resolves them according to URL path rules. It does not join two strings. The MDN URL constructor reference contrasts a base without a trailing slash with one that ends in a slash. In the first case, the final path segment is a leaf that an ordinary relative reference replaces. In the second, the slash marks the current directory, so the next path segment is added beneath it. This is structural meaning, not cosmetic formatting.

With https://api.example.test/v2 as the base, users resolves to https://api.example.test/users. The parser treats v2 as the segment to replace. With https://api.example.test/v2/, the same reference resolves to https://api.example.test/v2/users. If configuration stores a versioned API prefix, omitting one trailing slash can move every relative endpoint outside that prefix. The reverse also matters: if the base represents a single resource rather than a directory, a trailing slash changes its meaning. A formatter should not blindly add one everywhere.

This explains one way an endpoint can work locally and return 404 behind a production gateway mounted below a path prefix. The local configuration may point at the origin root, while production includes /service/v2. If some call sites use root-relative references, that prefix is discarded even when the configured base includes it. Increasing retries, changing timeouts, or adding a proxy rewrite may make one case appear to work while other input forms remain inconsistent. First identify where the base comes from, who constructs the reference, and which layer owns the expected prefix.

Three reference forms lead to different paths

users and ./users are path-relative references resolved from the current directory. With the directory-form base https://api.example.test/v2/, the result retains /v2/. With https://api.example.test/v2, the final v2 is treated as a leaf and the result is /users. If every endpoint should be relative to one API directory, make that directory contract explicit in configuration validation and accept only relative endpoint names at that boundary.

/users is root-relative. It resolves from the origin's root path, regardless of whether the base path is /v2/ or /service/v2/. That is suitable when the caller deliberately needs an origin-root resource. It is unsuitable when a gateway prefix must be preserved. Do not collapse it and a path-relative reference into the vague category “an endpoint with a slash.”

An absolute URL such as https://other.example.test/users does not use the base to construct the result. A reference beginning with // keeps the base scheme but replaces the host. This matters for a client that is supposed to use a fixed API origin: even if a caller meant only to supply a path, another reference form can change the origin. Supplying a base does not constrain all results to that base's origin.

A parent reference such as ../health moves up from the current directory and then appends health; repeated ../ segments continue toward the site root. Query components follow reference rules too. If a new reference carries its own query, that query appears in the result; a nonempty reference normally removes the base query, while an empty reference retains it. If query parameters are part of the contract, pass them deliberately instead of expecting string concatenation to merge them. The MDN relative-reference guide and constructor reference show these forms; an application still has to decide which forms it accepts.

Turn URL composition into a checkable contract

The following pure parsing snippet was executed locally under Node.js v24.21.0. It constructs URL objects but sends no HTTP request and does not establish that the example domain exists. Its outputs confirm the results for a missing trailing slash, a directory-form base, root-relative and parent-relative references, and an absolute reference. The constructor throws TypeError when the relative input has no base. The Node.js v26.13.1 URL API documentation says its URL class follows the WHATWG URL Standard used by browsers. The recorded runtime result establishes only the behavior of these inputs in local v24.21.0.

const cases = [
  ["leaf base", "users", "https://api.example.test/v2"],
  ["directory base", "users", "https://api.example.test/v2/"],
  ["root relative", "/users", "https://api.example.test/v2/"],
  ["parent relative", "../health", "https://api.example.test/v2/users"],
  ["absolute", "https://other.example.test/users", "https://api.example.test/v2/"],
  ["new query", "users?limit=10", "https://api.example.test/v2/?tenant=staging"],
  ["empty reference", "", "https://api.example.test/v2/?tenant=staging"],
];

for (const [name, reference, base] of cases) {
  console.log(name, new URL(reference, base).href);
}

try {
  new URL("users");
} catch (error) {
  console.log("missing base", error.name);
}

The observed paths, in order, were /users, /v2/users, /users, /health, and /users on a different origin. The query case produced /v2/users?limit=10, replacing the base query; the empty-reference case retained /v2/?tenant=staging. The final missing-base case produced TypeError. This check covers constructor output only. It does not prove that an API route exists, that a browser, reverse proxy, and backend use the same prefix, or that redirects, DNS, and access permissions have been tested.

At the application boundary, a configuration contract could say: “The service base must be an absolute URL ending in a slash; endpoint inputs must be relative paths without a leading slash; after construction, check the expected origin and business path range.” If root-relative or absolute references are needed, expose them as a distinct, explicit interface rather than accepting them silently. Checking only endsWith("/") is weak: it says nothing about protocol, host, encoded path content, or whether the value names an allowed service. Parse the configuration first, validate that it uses the expected HTTP(S) origin and directory, and then resolve constrained endpoint input.

Does a parsed URL mean the application may access it?

No. The parser answers, “What address does this reference produce under URL rules?” Application policy answers, “May this operation go there?” For a fixed API client, compare the result with the expected origin and check that the path lies within the intended API prefix. A path-prefix check must respect segment boundaries so that /api-evil is not mistaken for a child of /api. For user-supplied complete URLs, policy also needs to define allowed schemes, ports, credentials, redirects, and the resolved host addresses.

A browser client and a server-side proxy are different security contexts. Browser same-origin rules, CORS, or page CSP do not authorize destinations for a backend that makes requests on a user's behalf. A server accepting a URL can be exposed to redirects, private-network addresses, DNS changes, or unusual address forms that bypass a one-time string check. This article does not present a wrapper around new URL as SSRF protection. See validating user URLs and outbound requests for the broader server-side boundary.

Which boundaries should tests cover?

The following values are resolution expectations using https://api.example.test/v2/ as the base. They demonstrate path structure; they do not replace integration checks against real service routes.

Reference Resolved path or address Contract to check
users /v2/users Ordinary endpoint retains the service prefix.
/users /users Root-relative input intentionally skips /v2/, or should be rejected.
../health /health Parent reference leaves the version prefix; accept only deliberately.
https://other.example.test/users Different origin A fixed-origin client should reject an absolute destination.
users?limit=10 /v2/users?limit=10 New query replaces the base query; it does not merge tenant.
Empty string /v2/?tenant=staging Empty reference retains the base query and identifies the directory itself.

Put these values into pure unit tests and assert the resulting origin, pathname, and query fields. Then use service-route contract tests to verify actual endpoint paths. If the system supports deployment beneath /service/v2/, repeat the checks with that configuration rather than testing only at /. Allow-list and redirect checks belong at the request-making layer, where rejection paths can be exercised; a unit test that builds the expected string does not prove that a proxy or service enforces access control.

The URL constructor outputs shown here were run locally under Node.js v24.21.0. No real HTTP request, browser integration, or backend security test was performed. Treat the base as an “origin plus directory” setting, specify the endpoint reference form as part of the interface, and inspect the final destination separately. That turns a trailing-slash issue into a testable input boundary instead of a production-only surprise.
