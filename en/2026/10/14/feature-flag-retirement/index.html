A stale flag is not an off switch: separate three layers before retirement

A lifecycle label is a cleanup signal, not proof that runtime behavior or source branches have changed. Follow a hypothetical rollout to retire a flag in dependency order, including consumer and rollback checks.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-25 · Estimated read 19 min
Translations

Article

Key takeaways

  • “Stale” and “completed” are management signals; they do not prove that deployed applications stopped evaluating the flag.
  • Confirm the business end condition, consumers, and supported versions; remove code references before archiving configuration.
  • No usage metric means no use was observed under a particular telemetry window, not that dormant consumers have migrated.

Marking a feature flag as stale is usually a cleanup signal. It does not necessarily change how an application evaluates the flag, and it does not remove the conditional branch from source code. Safe retirement treats three things separately: the lifecycle status in a flag-management system, configuration used by running applications, and conditionals in source code. Treating them as one “off” action can lead to deleting configuration before discovering that an older consumer still reads it.

One name can describe several different jobs

Feature flags do not all have the same purpose. Pete Hodgson’s methodological article distinguishes release, experiment, operations, and permissioning toggles, then discusses how longevity and dynamism affect their design. A release toggle is often transitional; an experiment toggle has to remain long enough to support a decision; an operations toggle can support incident control; and a permissioning toggle may remain part of the domain. Their exit conditions therefore differ. The article dates to 2017. It is a useful classification, not a rule that every flag must expire automatically after a week or two.

Another source of confusion is a management platform’s “stale” or “completed” status. In Unleash’s current documentation, a flag can move through Define, Develop, Production, Cleanup, and Archived stages based on usage metrics and interactions. Marking a production flag complete does not itself change its configuration. Cleanup indicates that production usage metrics are still arriving and that code references should be removed before archiving. Passing a flag type’s expected lifetime can make it potentially stale; a team can also mark it stale manually as a deprecation signal. The documentation describes stale state as a way to manage debt, not as a direct change to application behavior. Unleash documents feature-stale-on and feature-stale-off events with null data and preData; these record a platform status change, not a snapshot of every application's evaluation. An event integration may notify people, open work, or trigger code checks, but an event cannot determine by itself whether every user has migrated.

Ask three separate questions: What state does the management system show? Do deployed application versions still evaluate this key? Do source code and configuration consumers still refer to it? A dashboard can help answer the first. Runtime behavior and code review must answer the other two.

Follow a hypothetical discount rollout through retirement

Suppose a team creates checkout-discount-v2, first enabling it for internal users and then for a small cohort before deciding whether to expand the rollout. This is a hypothetical example; no real flag service was connected and no release was run. Early in the rollout, keeping both old and new paths can have value: the team can compare results, catch incorrect totals, and switch back during the release window. But enabling the new path for everyone only says that current configuration routes new requests there. It does not delete old code or prove that every instance loaded the same configuration.

When the product decision is that the new path is the only supported behavior, record the decision and the boundary of support first. Must a region, historical order, or older client still use the old logic? If so, the flag is still carrying a business difference; it is not ready for retirement. If not, the team can keep the new path enabled while scheduling code cleanup: remove the old branch and tests and documentation specific to that path, while retaining tests for the supported behavior. After deploying the code to a test environment, verify that the target version routes through the new path at every relevant call site.

Next, check older production instances and other consumers. Several services may read the same key. A management system’s “completed” label does not update those services’ code. If an older instance remains, removing the configuration entry may cause it to use a default or raise an error; the result depends on the SDK, application defaults, and error handling. That behavior must be tested in the specific system. “All users have switched” does not imply “no consumer reads the key.” Evidence should cover service versions, references to the key, defaults, behavior when configuration is missing or unavailable, and the actual scope of telemetry.

Only after supported versions no longer depend on the decision should the team archive or delete the management record, keeping an audit trail. At that point a rollback may mean redeploying the previous version rather than switching the flag back. Also check whether that version can read data already written by the new path. If the new path changed a persisted format, a simple rollback might not restore the old behavior; recovery may require a forward fix or an explicit data-compatibility step. Confirm that the release process and data boundary support the chosen rollback. Do not describe a deleted old branch as an instant fallback that still exists.

The failure path: archive first, remove code later

A plausible failure begins when a team sees falling usage metrics, marks a flag stale, and archives it immediately. An older service that still reads it may then see no value and use false, use true, or fail. Any of those can differ from the expected behavior. A low-frequency background job, long-offline client, or instance without telemetry may still reference the flag, so a short period with no observed use is not enough to prove safe deletion.

Unleash documents “at least two days without detected production usage metrics” as one input to its archival lifecycle stage. That is a product-specific lifecycle meaning when the relevant metrics are enabled; it is not a universal safety threshold. Editorial inference: missing telemetry, event sampling, dormant clients, and long-period jobs weaken the meaning of “not observed,” so an observation window should match consumer call cycles. The exact behavior of archiving or deleting configuration also has to be checked against the chosen platform version and SDK. Do not assume another vendor has the same semantics.

An experiment flag should not be deleted merely because a new version appears better. Wait for the preselected observation window and decision criteria; otherwise later changes from code cleanup may become mixed with the experiment, making the result hard to interpret. Conversely, a long-lived permission flag may represent an authorization decision. Removing it changes the permission model; it is not ordinary debt cleanup.

A retirement evidence matrix

What to inspect Useful evidence What that evidence does not prove
Product decision A record of the one supported path, exceptions, and end condition That every deployed version has applied the decision
Source code Search for key names and wrappers; inspect dynamic key construction and cross-repository consumers Text search can miss indirect access, and one repository may not contain every consumer
Running versions Deployment inventory, version distribution, supported client range, and execution records for key jobs No recent traffic does not prove a call will never happen again
Behavior regression Tests for the new path, important outcomes, missing-configuration defaults, and rollback Passing tests do not prove complete production telemetry or every combination
Management system Verify flag type lifetime and the exact meaning of stale/completed, archive, and revival A management state does not remove application branches or necessarily turn the feature off

A practical sequence is: confirm the flag category and exit condition; assess whether evidence covers production and every consumer; remove unsupported branches in code; deploy and observe supported versions; then archive or delete the control-plane record. If the risk requires an immediate switch, explicitly maintain it as an operations flag, define on-call ownership and failure behavior, and stop treating it as a temporary release flag with an endlessly postponed expiry.

When retirement is the wrong action

If a flag represents lasting permissions, regional rules, a compliance boundary, or an ongoing degradation control, the right action may be to rename and maintain it rather than delete it. Long-lived flags should also avoid scattered conditionals: centralize the decision behind a testable domain interface so each call site does not interpret the same key differently. For how an interactive prototype acquires production responsibilities, see the boundary between a usable prototype and production responsibility.

The final question is not “How long has this flag gone unchanged?” It is “What behavior does the business still promise, which versions still depend on this decision, and how far does the evidence reach?” Retirement is a behavior migration. Lifecycle state, configuration value, code branch, and rollback mechanism belong in one change plan. This article did not inspect a real flag inventory or perform cleanup; the matrix is a review plan, not a report of executed verification.
