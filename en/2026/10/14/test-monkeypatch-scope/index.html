A monkeypatch restores a function reference, not everything the test already did

pytest restores managed replacements at the end of a test or fixture. Threads, started subprocesses, cached configuration, and external side effects need their own boundaries and cleanup.

Key takeaways

  • Patch the name the consumer looks up; fixture scope determines teardown timing.
  • Threads, child processes, and import-time configuration have distinct lifetimes.
  • Restoring a reference does not undo completed filesystem, network, or database effects.

When a test has ended but a background callback still holds a substitute function, or a request has already been sent, monkeypatch does not rewind either event. pytest manages temporary names, mapping entries, and environment changes it recorded. Test tasks, threads, subprocesses, and filesystem or network effects each have their own lifetime. When designing a patch, ask first, “Who reads this name, and when?” Then ask, “What exactly must be restored on exit?”

What gets restored is a reference, not the whole process

monkeypatch.setattr(module, "read_config", fake) makes module.read_config refer to fake for a period of time. The fixture saves the original attribute and undoes its recorded changes when the requesting test or fixture ends. Object attributes, dictionary entries, environment variables, the current directory, and import paths are among the changes that pytest can track and undo. The pytest monkeypatch guide also makes clear that the patch affects code that actually reads the replaced name; it cannot know which reads are “part of the test target.”

The patch location must therefore match the lookup location used by the code under test. If worker.py runs from gateway import fetch at import time, later calls use the name worker.fetch; replacing only gateway.fetch may not change the already-bound reference in worker. An attribute replacement must target the name used by the system under test. This is a common counterexample: the patch succeeds, but the call under test never goes through the substitute. Read how the dependency is bound before choosing the attribute to replace. That is usually clearer than adding another global patch.

To confine a replacement to a few lines inside a test, use monkeypatch.context():

def test_uses_fallback(monkeypatch):
    original = service.use_cache
    with monkeypatch.context() as patch:
        patch.setattr(service, "use_cache", False)
        assert service.use_cache is False
    assert service.use_cache is original

This is illustrative code; it was not run against a project here. Exiting the context undoes changes recorded by that context object, whereas pytest's fixture ordinarily cleans up at the end of the test. The official guide specifically recommends context() to remove standard-library patches early when they could affect pytest itself. Avoid casually calling monkeypatch.undo() on a shared fixture in a fixture stack: the API notes that the same fixture instance may be used by both a test function and its fixtures, and undo() reverses all changes recorded on that instance. A separate context makes the local cleanup boundary easier to see.

A fixture’s end is not a task’s end

Fixture scope determines when pytest destroys a fixture: the default function scope ends with one test, while class, module, package, and session scopes last for their corresponding containers. The fixture guide also says that code after yield runs when a fixture successfully yielded and the test has finished; if setup fails before yield, that fixture’s post-yield cleanup does not run. “The framework manages cleanup” therefore has exact boundaries: what was created successfully, where cleanup was registered, and which scope owns it all need to be explicit.

Consider a hypothetical case: a test replaces mailer.send with a function that only records arguments, then starts a thread to process a queue message. When the test function exits, the patch is restored. The thread may still be running. If it captured the substitute function, it can still call that object; if it looks up mailer.send only when it executes, it may instead see the restored implementation. Which path occurs depends on how the code stores and reads the dependency. Leaving a context alone cannot tell you. No thread was started to test these cases here. A safer approach is to wait for the task to finish before leaving the patch scope. If the test needs to prove concurrency isolation, pass a dependency explicitly to each worker or use separate processes instead of contending over one module-global object.

This also explains why side effects do not roll back. A patch can restore the mailer.send function reference, but it cannot unsend an email, erase a written file, or roll back an already committed database transaction. External effects need separate cleanup contracts: a resource fixture removes a temporary directory, a database test rolls back or uses a dedicated test database, and a fixture that creates a remote resource arranges its deletion. pytest’s safe-teardown guide recommends limiting each fixture to one state-changing action and keeping that action with its cleanup. This gives successfully created resources their own cleanup path if a later setup step fails. Restoring a patch and cleaning up a resource are different responsibilities; one assertion cannot stand in for both.

Environment variables also have a read time

Calling monkeypatch.setenv("APP_MODE", "test") changes the current Python process’s os.environ mapping; fixture cleanup restores the prior value. The Python os documentation explains that Python captures that mapping when os is imported; later direct changes to it are reflected in the underlying environment. An application can still copy a value into a constant while importing its own settings module:

# settings.py
MODE = os.getenv("APP_MODE", "prod")

Importing settings before setenv runs means settings.MODE is not automatically assigned again when the environment mapping changes. The test then observes “configuration captured at import time”; it does not prove that setenv failed. Depending on the application’s real configuration contract, set the variable before importing the module, defer the read until a function call, or pass a settings object as an argument. Do not clear module caches unconditionally just to make the test pass.

Child-process configuration is a separate boundary. The Python subprocess documentation says that a child normally inherits the current environment when it starts, or can be given an explicit mapping through env. Starting a subprocess while a patch is active means that process receives the environment supplied at startup; restoring the parent’s variable later does not rewrite an already-running child. For subprocess configuration tests, construct env explicitly and check process completion and cleanup instead of asserting only that the parent environment was restored.

Choose a scope, then verify the exit

When a dependency is already a component input, injecting a substitute is often easier to reason about than changing a module-level name. Use pytest’s fixture for a temporary replacement in one test. For a standard-library function or another replacement that could affect the test framework, put the local patch context around the smallest call block. When a resource is shared at module scope, first determine whether it is immutable data, a controlled connection, or a global dependency that changes between tests. Do not extend patch scope to a whole module or session merely to avoid initialization cost.

Validation has at least two layers. First, confirm that the target call uses the substitute inside the context, then assert by identity or behavior that the original name is restored afterward; the context must also exit through exception paths. Second, check whether work started inside the patch scope has finished, and whether files, database rows, or remote objects have separate cleanup owners. If calls cross thread or process boundaries, test dependency transfer and completion at those boundaries. These are proposed validation steps, not tests run against pytest applications or external services for this article.

Keep one rule in view: the patch tool restores the state it recorded; you define when work started by the test is finished and who cleans up what it leaves behind. If a global dependency is hard to pass in, gradual dependency injection may be worth considering, but the cost and risk of changing a legacy system still need separate evaluation. For the related resource-lifetime question, see pytest fixture isolation and cleanup.

Does a patch automatically affect another thread or subprocess?

Threads share module objects inside one process, so another thread that reads the same patched attribute during the active scope may see the substitute. A local variable that captured the old function earlier may continue holding that object. The child has a separate address space and normally gets the environment and arguments passed to it when it starts; restoring the parent’s attribute later does not rewrite the child’s memory. Do not infer either result from fixture teardown. Check when the dependency is read, where it is copied, and whether the task has actually finished.
