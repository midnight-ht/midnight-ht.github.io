Why did PostgreSQL ignore the offset in my timestamp string?

PostgreSQL interprets an offset-bearing string according to its type: timestamp without time zone keeps calendar fields and ignores the offset, while timestamptz represents an instant. This guide distinguishes typed literals, session TimeZone, both AT TIME ZONE directions, DST ambiguity, and legacy migration assumptions.

Key takeaways

  • A typed TIMESTAMP literal is resolved before its text is read; the no-zone type ignores offsets, while timestamptz represents an instant.
  • AT TIME ZONE interprets zone-free fields in a region, but renders timestamptz in that region; the result types are opposite.
  • Migrations and recurring schedules must account for session zones, DST gaps/folds, and zone intent; the SQL and checks here were not executed.

PostgreSQL did not convert the +02:00 in the input string because the value's type matters: timestamp without time zone stores calendar and clock fields, not a globally unique instant. timestamp with time zone interprets input as an instant. A particularly misleading case is TIMESTAMP '2026-04-01 09:00:00+02': the type keyword has already specified a timestamp without time zone, so the text offset does not change the type. To represent an instant, use a type that represents one in both the column and input contract, and define the timezone assumption for inputs without an offset.

When an offset is ignored, first check the value's type

The PostgreSQL 19 date/time type reference describes timestamp without time zone as date and time without timezone conversion, and timestamp with time zone as date and time with conversion. The phrase “with time zone” can suggest that the user's America/New_York or Asia/Shanghai label is stored verbatim. That label is not part of the resulting value: input is converted to an instant, then rendered as local date and clock fields in the current session TimeZone.

Type resolution matters during parsing. SQL permits typed literals such as TIMESTAMP '...'. The PostgreSQL parser does not inspect the quoted text before determining the type; it resolves the TIMESTAMP keyword as a timestamp without time zone. The SQL standard has a different type-inference convention for an offset-bearing literal, but that convention should not be applied to PostgreSQL. Thus, the following is not interpreted as a zoned instant merely because its text contains an offset:

TIMESTAMP '2026-04-01 09:00:00+02'

By contrast, explicitly writing TIMESTAMP WITH TIME ZONE '2026-04-01 09:00:00+02' asks PostgreSQL to use the offset to interpret the input. These examples explain the documented parsing rule; they were not executed against a PostgreSQL server.

For application parameters, inspect the driver's bound type, ORM field type, and server column type as well. A JSON string's appearance alone does not establish which PostgreSQL type the parameter uses in an expression. Check the API contract and schema, then verify parameter binding and connection settings to locate the conversion boundary.

There are at least three distinct concepts. First, an instant: for example, an already completed payment event that must be ordered against events in other regions. Second, local calendar time: a shop opening at 09:00 each day is initially a clock reading at a place, not inherently one UTC instant. Third, timezone intent: a user may choose America/New_York so future weekly appointments continue to follow the rules in force there. A single timestamp field cannot guarantee that all three are preserved.

The direction of AT TIME ZONE depends on the left-hand type

Section 9.9.4 of the PostgreSQL 19 AT TIME ZONE reference documents two directions. Applying timestamp AT TIME ZONE zone to local fields interprets them as local time in that region and returns a timestamp with time zone instant. Applying timestamptz AT TIME ZONE zone to an already determined instant renders it under that region's rules and returns local date and time fields without a zone.

-- Interpret local clock fields as an instant in a specified region
local_meeting_time AT TIME ZONE 'America/New_York'

-- Render an existing instant as local clock fields in a specified region
occurred_at AT TIME ZONE 'America/New_York'

These expressions represent opposite data directions. Do not describe every AT TIME ZONE operation as “converting to UTC.” The first treats its input as local fields; the second requires an already determined instant. If only the zone-free fields returned by the second expression are saved, a later reader cannot tell whether they came from New York, Tokyo, or elsewhere. If the first expression's timestamptz result is saved, it preserves the instant but not the region name the user originally selected. In code review, write the actual type of each side next to the expression; this is more reliable than looking for utc in a column name.

Session settings enter at several implicit boundaries. When text without an offset is input as timestamptz, PostgreSQL assumes the connection's TimeZone; it also displays timestamptz values using that setting. Converting timestamp without time zone to timestamptz, or comparing the two types, requires a timezone interpretation for the zone-free fields. If none is explicit in the expression, the documentation specifies the session timezone. The same migration script can therefore interpret identical calendar fields as different instants under different connection settings, while the same internal instant can display as different clock times in different sessions.

A row that says 2026-04-01 09:00:00 may come from a historical API that never supplied a region or offset. A migration connection configured for one region can convert those fields into an instant under that region; another region would produce a different instant. Successful SQL, unchanged row counts, and a completed type conversion do not prove that the old field originally meant nine in that region. This is a hypothetical example, not an executed migration. A real migration needs evidence such as the source interface, legacy system settings, user region, or import batch.

Daylight saving time can make local clock values non-unique

A named timezone is not a fixed UTC offset. A full name such as America/New_York carries regional rules; those rules may change between standard and daylight time and may change in the future through political decisions. By contrast, -05:00 is one explicit fixed offset; it does not encode how a region changes throughout the year. Use a suitable named zone when regional behavior matters. For an event that has already occurred and arrives with a numeric offset, that offset can directly identify the corresponding instant.

When clocks jump forward, some local readings never occur; when clocks move back, a reading occurs twice. Appendix B.2 of the PostgreSQL 19 manual says these inputs are not always rejected as errors. For a nonexistent spring-forward local time, the database uses the offset that prevailed before the transition. For a repeated fall-back time, it defaults to the offset after the transition. An explicit offset or abbreviation can choose a different interpretation. This default is an input rule; it is not automatically the right policy for an appointment product.

Imagine a user scheduling “02:30 on the spring-forward day” in New York. The local clock never showed that reading. PostgreSQL may interpret it under the documented rule, but the product may instead need to prompt the user to choose another time.

Now consider 01:30 on the fall-back day: the local clock will show it twice. If users must select the first or second occurrence, that choice must be part of the input; timestamptz cannot preserve a named region that was never stored. A numeric offset resolves the instant for a past event; future recurring local schedules often need the region name and recurrence rule as well.

Choose fields from the business meaning

For an event that has happened, a message receipt, or an audit event, the central question is usually “when did it happen?” A timestamp representing an instant, such as timestamptz, is appropriate. The API should require Z or an explicit offset, or define who supplies a region when it is missing. A column named created_at_utc does not by itself ensure correct input conversion. Whether to retain the original request text for compliance or reconciliation is a separate data-retention decision.

For “09:00 on a region's calendar,” such as weekly business hours or a monthly local billing deadline, store the local date/time rule and, where needed, the IANA zone name separately. A one-time appointment may preserve both the user's local choice and the region, then calculate one instant. A recurring appointment must preserve its recurrence rule: future timezone policy changes may lead the product either to reinterpret the local time under new rules or keep a precomputed UTC instant. That choice follows the product promise. If timestamptz is stored while the zone name is discarded, the user's intended future regional rule cannot be recovered from the instant.

Make the decision jointly in the API and domain model: Is the field an instant, a local clock reading, or a region-specific calendar rule? Is a missing offset acceptable? Does the region name affect future calculations? What should users do with a daylight-saving gap or repeated time? When new timezone rules appear, should an appointment move with the local clock or remain at the same instant? Encode these answers in constraints, API validation, and product state rather than making each caller guess.

Validate migration assumptions before applying a blanket cast

Migration planning can first inventory each legacy value's provenance: which client wrote it, whether that client sent an offset, what database session TimeZone was configured, and whether jobs from multiple regions wrote the same column. If evidence establishes that all old values are local fields in one region, convert with that region explicitly and compare samples against source records. If the old values were intended as UTC but were not declared that way, use a confirmed UTC interpretation. If provenance is mixed or unconfirmable, mark those rows for review instead of creating false precision through a blanket conversion. The database's current timezone is not historical evidence.

Before release, a validation matrix should include: an input with Z, positive and negative explicit offsets, an offset string explicitly typed without a zone, timestamptz input without an offset, two different session TimeZone settings, both directions of AT TIME ZONE, a nonexistent spring-forward time, a repeated fall-back time, and legacy rows with known and unknown sources. Compare not just rendered text but the type, whether the value represents the same instant, what information a round trip loses, and the session setting. For application parameters, test the actual driver or ORM binding path, not only handwritten SQL literals.

This is a proposed verification plan, not an executed SQL tutorial. No PostgreSQL query, migration, or output comparison was run for this article. A real migration should compare an isolated copy with source records, confirm how business owners want ambiguous history handled, then change or add fields in stages, verify dual writes, and monitor differences. For the separate modeling question of future recurring schedules, see instants and recurring time intent. The point is not “use UTC for everything”; it is to make each field preserve the meaning it promises and to state the regional rule explicitly whenever local time is resolved to an instant.
