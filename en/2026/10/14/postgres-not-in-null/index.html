Why did NOT IN omit the rows I expected to be unmatched?

A right-side NULL, an empty subquery, and a NULL left value produce different three-valued outcomes for NOT IN. Define what unknown identity means before rewriting to NOT EXISTS or relying on constraints.

Key takeaways

  • NOT IN needs every comparison to be known unequal; a right-side NULL can make an unmatched comparison UNKNOWN.
  • An empty right side makes NOT IN TRUE even for a NULL left value; WHERE discards UNKNOWN.
  • Validate NOT EXISTS rewrites, composite keys, and null constraints against business states; the SQL here was not executed.

A NULL on the right side of NOT IN, with no equal value found, can make the whole predicate UNKNOWN rather than TRUE. Because WHERE keeps only TRUE, the result can look as if unmatched rows disappeared. Before changing the query, define what an unknown identifier means, then choose among NOT IN, NOT EXISTS, or an explicit null policy. These forms are equivalent only when their null rules and data assumptions are the same.

NOT IN needs every comparison to be known unequal

The PostgreSQL 19 subquery-expression reference describes x NOT IN (subquery) as comparing x with every returned row. The result is false if any row is equal; it is true only when every comparison is unequal. If there is no equal value but at least one comparison is UNKNOWN, the result is UNKNOWN. The expression is equivalent to x <> ALL (subquery). This is a logical result of the comparisons, not an intermittent execution-plan failure.

Consider a deliberately small hypothetical example. Pending task identifiers are 10, 20, and 30; the exclusion table contains 20 and NULL. For 10, 10 <> 20 is true while 10 <> NULL is UNKNOWN, so true AND UNKNOWN remains UNKNOWN. For 20, one comparison is false and the whole predicate is false. For 30, the result is again UNKNOWN. The PostgreSQL 19 logical-operator truth table also shows that TRUE AND UNKNOWN remains UNKNOWN. Only 20 is known to match, while 10 and 30 do not pass a WHERE filter that requires TRUE. This table is derived from the documented rules; it was not run against a database.

A common mental model is two-valued set difference: “the identifier is not in the table, therefore return it.” SQL comparisons also represent what cannot be determined. NULL is not a special identifier, does not equal another NULL, and is not a shared sentinel for all unknown values. A right-side NULL might mean an association has not arrived, data is missing, a mapping is awaiting repair, or an invariant was violated. Each meaning changes whether the product may label a task “unmatched.”

Separate logical values from business outcomes

A SQL predicate can evaluate to TRUE, FALSE, or UNKNOWN. The PostgreSQL 19 WHERE reference keeps rows only when the condition is TRUE; FALSE and NULL are discarded. Therefore, a row missing from a query result is not evidence that it matched, completed, or does not exist. It might instead be impossible to determine whether it is unmatched. If downstream logic treats the result as a retry queue, accounting candidate set, or manual-review list, these states should not be collapsed into “present” and “absent.”

Before repairing the query, answer two independent questions. Should a task with a null left-side identifier be eligible? If an exclusion row has a null identifier, should it be ignored, block processing, or mark related tasks for investigation? If the schema guarantees a non-null exclusion identifier, a constraint can enforce that invariant. If non-nullness is only an import target, the query must still account for cases where the invariant is false. Filtering bad data can make NOT IN return more rows, but it can also hide bad data; it is not merely a syntax patch.

What changes when the query uses NOT EXISTS?

If the intended meaning is “there is no equal, valid association,” a correlated subquery can localize the comparison:

SELECT t.task_id
FROM task AS t
WHERE NOT EXISTS (
  SELECT 1
  FROM exclusion AS e
  WHERE e.task_id = t.task_id
);

EXISTS asks whether the subquery returns a row. Here, the equality join counts only when it evaluates to TRUE. A row with e.task_id IS NULL does not match a non-null task identifier, and it does not turn the other candidates into UNKNOWN as a NOT IN member can. The reference also says that EXISTS cares only whether at least one row is returned; the select list normally does not affect the result.

However, when t.task_id itself is NULL, e.task_id = t.task_id is not TRUE, so the subquery finds no matching row and NOT EXISTS is true. A null-identified task can therefore enter the result. NULL NOT IN (...) can instead be UNKNOWN. If the product must exclude unknown left-side identity, add t.task_id IS NOT NULL; if it must retain and label it for review, make that state explicit in the query or output. Switching to NOT EXISTS is not a universally equivalent rewrite. It chooses the semantics “only a definite equality counts as excluded.”

If the policy is to ignore unassociated rows on the right and the left identifier is guaranteed non-null, one option is to filter e.task_id IS NOT NULL and keep NOT IN. That condition should reflect a data rule enforced by a constraint or monitored validation. If an unassociated exclusion row must block a batch and trigger repair, filtering it out is wrong. Query or count null identifiers separately instead of mixing them into the exclusion set and expecting the main query to report the data problem.

Test an empty subquery and multi-column comparisons separately

When the right side is an empty set, NOT IN is true even when the left value is NULL, because there are no rows to compare. The official reference documents an empty subquery as a true NOT IN result. That SQL TRUE still does not mean the product knows that a null identity is unmatched: if policy excludes unknown identity, handle the left value explicitly rather than relying on the empty set to contain no comparisons. This edge is easy to miss when tests only use a populated exclusion table, especially if filters can make the subquery empty.

If exclusion uses two fields, such as tenant and external identifier, row comparison combines NULLs using SQL Boolean rules. The PostgreSQL 19 comparison reference says two rows are equal when all corresponding members are non-null and equal; they are unequal when a member is definitely unequal; otherwise the comparison is unknown. Thus (tenant_id, external_id) NOT IN (...) does not mean “ignore any null column” or “nulls match each other.” Decide which fields form identity and which missing values need quarantine. Explicit join predicates, IS NOT DISTINCT FROM, and constraints may express different policies; they are not interchangeable choices.

PostgreSQL 19’s optimization note does not change the predicate

For version context, PostgreSQL 19 was released on November 19, 2026. Its release notes say the optimizer can convert NOT IN clauses to an anti join when NULLs are absent. This is an implementation optimization with a stated condition. It does not relax NOT IN null semantics, promise that every statement will be rewritten, or guarantee a faster plan. When comparing older and newer plans, verify the server version, constraints, data distribution, and actual EXPLAIN; do not use the release note as a reason to rewrite a query containing nulls. The examples here were not run on a PostgreSQL instance, and no plan or performance comparison is claimed.

Validate with cases that can change the result

A small decision table should include: a non-null left value that matches; one that does not; a right side containing NULL with no match; a null left value; an empty exclusion subquery; a right side containing both NULL and a matching value; and a composite key with one null member. For each case, write the three-valued SQL result and the intended business state, then compare the original and candidate expressions. The key question is not which syntax is “safer,” but whether every data state reaches the outcome the product specified.

A realistic validation should also trace null origins: which import batch introduced them, when, whether there is a stable source identifier, and whether they can recur after repair. On test data, compare result identifier sets and their differences instead of only comparing row counts. Equal totals can still hide one missing row and one extra row. If NOT EXISTS and NOT IN are claimed equivalent, record the assumptions—such as non-null keys on both sides, equivalent operators, and identical correlation predicates—and deliberately violate those assumptions to confirm the tests catch the difference.

Finally, encode the decision in constraints, import validation, and business-state definitions. If NULL is legitimate, make “identity unknown” visible in the interface or report. If it is invalid, reject new rows early and alert on legacy data. A query should compute an outcome from an explicit policy; it should not guess whether “unknown” means “unmatched.” For a separate question about constraints and UNKNOWN, see CHECK constraints and unknown values. That article explains when a constraint accepts UNKNOWN; it does not imply that WHERE or an exclusion predicate will keep the row.
