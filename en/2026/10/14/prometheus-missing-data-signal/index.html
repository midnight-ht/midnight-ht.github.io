How to tell zero values, missing targets, and failed scrapes apart in Prometheus

An empty PromQL vector is not a measured zero. Use query time, up, target inventory, and absent functions to separate inactivity, scrape failure, and a missing target.

Updated 2026-11-25 · Estimated read 22 min

Article

Key takeaways

  • An empty vector is not zero; instant selectors also depend on evaluation time, lookback, and stale samples.
  • up == 0 indicates a failed scrape; no up series requires comparison with an independent expected-target set.
  • absent checks whether a selector is empty; it cannot enumerate arbitrary missing members. The scenario matrix and commands were not run.

An empty PromQL vector has not measured zero; it returned no matching samples. Genuine inactivity, a failed scrape, a target leaving service discovery, a renamed label, and a query-window mismatch can all leave a blank graph. To interpret the gap, check application samples, collection health, and the independent answer to “which targets should exist?” separately.

Emptiness and zero are different states

If requests_total{job="checkout"} returns a sample with value 0, it says that a matching series exists and the selected sample is zero at that evaluation. The sample need not have been scraped at that exact wall-clock second; whether it remains within the valid lookback also matters. No matching series means no sample was returned at that evaluation. Rendering both states as zero merges “zero was observed” with “there is no observation on which to decide.”

That distinction changes the on-call action. Zero requests with healthy collection may be an ordinary quiet period. A blank result could mean that a metric or job label changed, a scrape failed, or Prometheus stopped discovering the target. Those cases call for different responses: interpret business activity, correct a query or confirm a rollout, investigate collection, or compare target sources. A default value cannot make those decisions for you.

For a deliberately global activity panel, or vector(0) can be appropriate when the business contract explicitly defines no events as zero and the page also preserves collection health. Using the same default for per-instance, tenant, or partition coverage can create a label-free global zero or hide a missing member. Before filling, state which business fact the default represents. Do not reuse it as evidence that monitoring is healthy.

Query time and staleness affect an empty result

A Prometheus instant vector selector takes the newest sample for each series at the evaluation time. By default, it accepts samples no older than five minutes; configuration or a per-query parameter can change that lookback delta. When a target or rule stops producing a previously present series, Prometheus marks it stale. Later evaluations no longer treat the stale sample as a current value. Exporters that attach their own sample timestamps have additional behavior after they stop exposing a series, so the default explanation does not apply mechanically to every input.

Read a blank graph together with its query type and time window. Instant queries, range-query resolution selected by a dashboard, offsets, and label filters all affect what appears. absent_over_time(metric[10m]) means that the selector found no samples in the interval. It does not prove there was no business activity during those ten minutes, nor identify which system caused the gap. The range defines the evidence being tested; it does not set the business's acceptable outage or quiet-period threshold.

During an investigation, split the final expression into pieces. In tabular results, inspect original series, labels, latest sample timestamps, and counts per group before adding aggregations, matching, or time functions. A fleet-wide sum(requests_total) can still return a value after one replica disappears because the other replicas continue to contribute. Conversely, a range function that finds an older sample does not prove collection is still healthy now. Record the evaluation time, query window, and actual scrape interval instead of comparing screenshots of a line chart alone.

Check up for scrape health, then check whether the target is expected

Prometheus automatically creates up{job,instance} for each scraped target: 1 means the scrape succeeded and 0 means it failed. This answers a limited question: could Prometheus scrape this configured or discovered target on that scrape? It is not a business-traffic metric and does not replace an application's metrics.

Suppose a target has up == 1 but its request counter query is empty. Check whether the exporter exposes the metric, whether it is created only after the first event, whether metric relabeling filters it, and whether the application renamed the metric or labels. If up == 0, inspect target health, lastError, the latest scrape time, and the endpoint itself. If up for the instance is absent too, the target may have been removed, discovery or relabeling may have changed, or the query labels may not match. Do not call “no up series” a scrape failure: a failed scrape generally has an up series with value zero, while a missing series needs another source of expected membership.

That expected target set should come from trusted control-plane evidence, such as static configuration, a service registry, desired deployment replicas, or file service-discovery input. The Prometheus targets API can tell you what it currently discovered; it cannot by itself tell you what the application team expected it to discover. If expected membership and scraping depend on the same failing system, both views may disappear together and leave a blind spot. For short-lived jobs, on-demand environments, and rolling deployments, define when a target becomes expected and when it may be removed. Otherwise a target that just finished can look like a missing-target incident.

Absence functions detect a selector, not every missing member

absent(v) returns an empty vector if its input contains any elements and a one-element vector with value 1 if it contains none. absent_over_time(v[10m]) produces the same kind of signal when it finds no sample in the selected range. These are useful for asking whether a fixed metric and label combination exists now or during a period. Prometheus attempts to derive output labels from a simple input selector. If you first aggregate with sum() and remove those labels, then call absent(), the original member identity is already gone; the function cannot infer which instance is missing.

That is why “the whole metric group disappeared” and “one replica is missing from the list” are different query problems. absent_over_time for a fixed job can detect that the selected group has vanished. It is not a per-replica set difference. To identify a missing member, compare observed samples with an expected-member set using stable identity. Keep that expected set bounded and give it a lifecycle; permanently registering every dynamic label value is not a reasonable shortcut.

If an application does not expose a business metric while idle, it may make sense to initialize a finite, semantically defined zero-valued series when the application starts. Do not pre-create series for arbitrary user inputs, request paths, or high-cardinality labels. That expands time-series volume, and a pre-existing zero still does not prove that collection is complete. The metric contract and label cardinality should determine initialization; it should not be used to conceal an observability gap.

Clearing an alert is not proof of business recovery

Prometheus alerting rules maintain active state for vector elements and their label sets. An optional for clause requires an element to remain active for a duration before it moves from pending to firing. If the expression later stops returning that element, the alert can deactivate according to rule state behavior. That only says the element is no longer present in the current expression result; it cannot distinguish service recovery from missing samples, changed labels, or a broken query.

keep_firing_for can keep an alert firing for a period after its condition was last met, which can reduce false resolution notifications during short fluctuations. It is a state-transition policy. It does not restore samples, create a target inventory, or verify that collection recovered. If the absence itself matters, define a separate expression and route it to someone who can investigate collection. Do not lengthen a business alert's firing state and treat that as missing-data monitoring.

Validate the distinctions with counterexamples

The following is a hypothetical three-replica service, not a real system at this site, and it has not been run in Prometheus. Before rollout, an isolated test can vary one condition at a time and save expression results, target state, sample timestamps, and alert state:

Changed input Possible business-metric view Evidence to inspect
Requests are collected, but none occur in the window Existing series at zero, or empty if not initialized Metric contract, up, and raw /metrics output
One replica endpoint fails to scrape That target's up is zero; business samples may become stale and disappear Target health, error, and latest scrape time
One replica leaves service discovery Its up and business series may both disappear on removal Independent desired replicas, deployment event, discovery input
Metric label changes but query retains the old condition Scrape still succeeds, old selector is empty Full scraped label set and change diff
Prometheus or remote storage is unavailable Many unrelated queries may have no data Monitoring-system health, read/write errors, external probe

Include a case where the fleet total remains positive while a member is missing, as well as one where there are truly no requests but a zero was collected. Acceptance does not mean every graph has a number. It means the business dashboard, collection-health panel, and alert routing do not tell contradictory stories for the same scenario. If you must choose an alert delay, use the scrape interval, scrape timeout, evaluation interval, transient-target lifecycle, and business detection objective, then confirm the actual telemetry. A generic ten-minute window is not a fault threshold supplied by Prometheus.

These queries and checks are unexecuted design suggestions; no promtool output, alert result, or reduction in missed events is claimed. A useful diagnostic order is to determine whether the expression returned a zero-valued sample or an empty vector; check up, latest scrape, and labels for the same identity; compare them with an independent expected-target set; and finally inspect the alert element's lifecycle. When any evidence layer is unavailable, keep the status unknown rather than rewriting an empty result as zero. For a related failure mode, see how changing alert labels interrupts pending state and Prometheus scrape and evaluation clocks.
