What makes this the representative row in each group?

PostgreSQL DISTINCT ON keeps the first ordered row in each group. Separate eligibility, business precedence, tie-breaking, and presentation order to explain why that row represents the group.

Updated 2026-11-25 · Estimated read 17 min
Translations
zh-CN en

Article

Key takeaways

  • DISTINCT ON keeps the first ordered row in a group; the product must still define eligibility, precedence, and tie handling.
  • A WHERE filter changes the candidate set, while the inner selection order and outer display order are separate contracts.
  • Validate ties, null times, late arrivals, empty candidate sets, and pagination; the proposed SQL and EXPLAIN were not run.

When a query keeps one row per group, first define what that row represents. PostgreSQL DISTINCT ON retains the first row according to ordering; it does not decide what “latest” means, which statuses qualify, or how ties are resolved. Make candidate eligibility, business precedence, tie-breaking, and final presentation order separate contracts so the result can be explained.

The first row comes from ordering and candidate eligibility

The current PostgreSQL major is 19, released on November 19, 2026. Its SELECT reference I checked says DISTINCT ON (device_id) keeps the first row among rows with an equal device ID. Without an ORDER BY that ensures the intended row comes first, the choice is unpredictable. DISTINCT ON expressions must match the leftmost ORDER BY expressions; later sort keys express precedence within each group. DISTINCT ON is a PostgreSQL extension, not standard SQL that can be copied to every database.

Suppose a report table stores a device, report time, receipt sequence, publication status, and unique report_id. When a product asks for the “latest report,” report time might be when the source says an event happened, while the receipt sequence represents when the system received it. A late message can describe an earlier event and arrive later. If the page reconstructs event time, sort by the report time; if it explains what the system most recently observed, receipt time may better match the question. Columns that are both called time are not interchangeable.

Two reports can also have the same time, so the business needs a precedence rule. If an approved version should win, sort by approval priority first and use a unique report_id only to break any remaining tie. A unique key makes the output stable for the same input; it does not prove that the tie rule is meaningful. If every tied first row must remain visible, a unique key must not break that tie.

Candidate filtering changes the meaning of “latest.” WHERE visibility = 'published' means the latest report among published reports; it does not mean the latest report across all statuses. If the newest report is pending review, filtering first can make an older published version appear current. Decide whether the product wants “latest visible version” or “latest status,” then decide whether to filter before selection or show the selected row’s status afterward. Predicate placement is part of the candidate-set definition.

NULL timestamps are not a harmless default

The ordering reference says descending order defaults to NULLS FIRST. If unknown report times should come after known times, write NULLS LAST; alternatively, exclude null times from the candidate set, but then some devices may have no representative row. When every time in a group is null, receipt sequence or ID can still choose a stable row, but it cannot turn an unknown time into a known one. The product must decide whether to show an “unknown time” candidate or no selectable report.

Every displayed field should also come from the same selected row. GROUP BY device_id, MAX(reported_at) can calculate each group’s maximum time, but the maximum does not carry that row’s status and payload. Joining the maximum back to the source may return two rows when both share the maximum timestamp. If a later arbitrary LIMIT 1 cuts them down, the undefined choice has only moved. Use aggregation when the output is an aggregate; select one row when the output is a complete report.

Express a complete choice in the sort order

Suppose the product contract is: “the latest published report per device; when event times tie, prefer the one received later; if rows still tie, use the unique ID for a stable result.” This is a proposed query; it was not executed against a database for this article:

SELECT DISTINCT ON (device_id)
       device_id, report_id, reported_at, received_seq, status, payload
FROM device_report
WHERE visibility = 'published'
ORDER BY device_id ASC,
         reported_at DESC NULLS LAST,
         received_seq DESC,
         report_id DESC;

The sort starts with the device group key, satisfying the leftmost-prefix requirement. It then sorts event time descending, explicitly places nulls last, sorts receipt sequence descending, and finally uses the assumed-unique report_id for any remaining tie. Every field corresponds to a rule the team can explain. If “latest” means when the system received a report, replace the business-time field. If a pending report must be the latest result, do not remove it in WHERE. If approval state should take precedence over time, put that rule first and accept that this changes the product’s meaning of “latest.”

After selecting a row per group, how can results be sorted globally without changing the choice?

The ORDER BY device_id, ... above lets the database select one representative per group. It does not automatically arrange the final page by every device’s report time from newest to oldest. The sorting reference says output order is reliable only when the outer query explicitly specifies ORDER BY. Put the within-group selection in a CTE, then sort the representatives outside it:

WITH chosen AS (
  SELECT DISTINCT ON (device_id)
         device_id, report_id, reported_at, received_seq, status, payload
  FROM device_report
  WHERE visibility = 'published'
  ORDER BY device_id ASC,
           reported_at DESC NULLS LAST,
           received_seq DESC,
           report_id DESC
)
SELECT *
FROM chosen
ORDER BY reported_at DESC NULLS LAST, device_id ASC;

The inner sort determines which row each group keeps; the outer sort determines how those representatives appear. They are compatible responsibilities, but neither replaces the other. Acceptance should ask separately: does the selected report_id satisfy the within-group business precedence, and does the page order the representatives globally by time? The final display order alone cannot prove that the correct row won within each group.

When a window function fits better

For the top N rows per group, row_number() OVER (PARTITION BY device_id ORDER BY ...) can number rows within each group and an outer query can filter row_number <= N. If all tied first rows must remain, rank() retains equal ranks for equal sort keys; adding a unique ID to the ranking order would split the tie. Choose the function based on whether the contract says “exactly one,” “top N rows,” or “all rows tied at the top.” Window functions and DISTINCT ON both require decisions about eligibility, null placement, and precedence.

For a query that must run across database engines, a window-function form is often easier to adapt than PostgreSQL-specific DISTINCT ON, although the target database’s syntax and plan still need checking. If the result requires averages, totals, or every anomalous member, neither function should be mistaken for a representative-row query. Aggregation or retaining all members matches that output better. Choose syntax from the result contract, not from which SQL is shorter.

Build tests that can change the winner

For one device, include different report times, equal times with different statuses, receipt order opposite event-time order, a null time, and a group where all times are null. Also include a device with no published candidate, a newly pending version, and multiple tied candidates. Write the expected report_id and its reason for every case before checking query output against eligibility, precedence, tie handling, and page ordering. A test group with only one candidate cannot reveal a missing sort key; vary fields that can change the winner.

The query plan is a separate question. The PostgreSQL 19 index-ordering reference says B-tree can provide ordered output, while the planner weighs an index scan against an explicit sort; an explicit sort may be preferable when a large fraction of the table is read. Inspect EXPLAIN on the actual data and parameters before choosing index column order or an index for null ordering. No EXPLAIN or benchmark was run for this article, and no performance improvement is claimed. If results are paginated, stability across pages is another ordering contract; see the site’s pagination and ordering boundary. Check it separately from choosing a representative row within each group.
