Import maps: why can the same name resolve to different modules?

Trace a complete static module graph through importer scopes, fallback and the effects of moving build output.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-31 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • Scopes match referring module URLs rather than page routes.
  • Specific scopes and broader mappings determine resolution.
  • Version mappings do not define state or security isolation.

An old editor and a new workspace can import the same name while needing different implementations. Native import map scopes provide localized mappings according to the referring module URL. Look at the importer, not the address-bar route or the directory containing the dependency.

Draw the import edges before splitting versions

The HTML import maps section defines global imports and localized scopes. The consulted page was marked updated on 30 October 2026. This article concerns native browser module resolution; neither target-browser support nor a particular bundler was tested.

Scopes are not a version environment dynamically inherited from a call stack. An import inside a shared module is resolved with that module's own URL. Being initially imported by the old editor does not make its dependencies automatically use the editor's scope.

A useful migration table lists importer URL, specifier, applicable mapping and final dependency URL. “Page A uses v1” is insufficient when both pages also import common modules.

Prepare an independent static example

This complete teaching example is unexecuted and has no framework or remote package dependency. Create a fresh directory and save the files at the paths shown. With Python 3 available, run python3 -m http.server 8000 in that directory and open the local HTTP page. The command and browser steps have not been run; choose another free port if necessary.

Create index.html:

<!doctype html>
<html lang="en">
<meta charset="utf-8">
<title>Scoped module mapping example</title>
<h1>Check the dependency versions of two entry modules</h1>
<p>Inspect the demonstration labels in the developer console.</p>
<script type="importmap">
{
  "imports": {
    "formatter": "/deps/formatter-v2.mjs",
    "label": "/deps/label.mjs"
  },
  "scopes": {
    "/legacy/": { "formatter": "/deps/formatter-v1.mjs" }
  }
}
</script>
<script type="module" src="/legacy/entry.mjs"></script>
<script type="module" src="/work/entry.mjs"></script>
</html>

Create legacy/entry.mjs:

import { version } from 'formatter';
import { label } from 'label';
console.log('legacy', version, label);

Create work/entry.mjs:

import { version } from 'formatter';
import { label } from 'label';
console.log('work', version, label);

Create the three dependency files:

// deps/formatter-v1.mjs
export const version = 'v1-demo';

// deps/formatter-v2.mjs
export const version = 'v2-demo';

// deps/label.mjs
export const label = 'shared-demo';

The expected resolution is v1 for the legacy importer and global v2 for the work importer. Both use the global label mapping. Omitting label from the local scope does not itself make that import fail: broader applicable mappings can supply it. These are predictions, not collected console output.

The sample uses root-relative URLs, so serve the new directory as the HTTP root. Copying it under a subdirectory of an existing site without adapting the addresses changes that relationship. Establish the serving root before blaming scopes for missing files.

Specific scopes and fallback

The standard explains that more specific applicable scopes are consulted before broader ones and the global map. A /legacy/editor/ scope can override one specifier while allowing others to resolve through /legacy/ or global imports. It is not a closed dependency object that must repeat every mapping.

Extend the sample with a deeper entry only after writing its expected resolution table. Check the overridden formatter, the shared label and a deliberately unmapped bare name separately. One fully rendered page is a weak diagnostic when several paths change together.

Scope keys follow normalization and matching rules, rather than interpreting a directory's business name. Choose prefix boundaries deliberately, including the appropriate slash for a directory scope. Preserve actual normalized importer and target addresses in release evidence.

Why does moving output matter if the route stays unchanged?

A client route might remain /legacy/edit while its module moves to /assets/editor-abc.mjs. The old /legacy/ scope may no longer cover the importer. The address bar does not establish the module's applicable mapping.

Inspect final output. A bundler may rewrite bare names or inline a dependency, so native import maps may no longer control the edge under discussion. Decide between build-time aliases, separate output or native mappings based on what the browser actually resolves.

URL and base resolution covers the related address construction problem. This article adds specifier mappings and importer scopes; record absolute importer and target addresses to avoid conflating the two.

Does splitting versions isolate shared state?

Scopes are resolution rules, not a sandbox or a policy for application state. Distinct final module URLs can yield distinct instances, with consequences for singleton state, class identity and caches. Review those consequences in the actual module design instead of equating a split version with compatibility.

A common module located outside the legacy directory resolves its own formatter import using its own URL. Keeping an entire old feature on v1 therefore requires examining dependency edges, while duplicating every dependency indiscriminately may break intended sharing.

Coordinate the map with asset availability. Publishing a new mapping before its file exists yields a correctly resolved but unavailable URL. Rolling back HTML while deleting old resources can affect clients still holding an earlier page. Document availability windows and rollback targets for both versions. This is deployment analysis from the static dependency graph, not evidence of live availability or cache behavior.

Proposed acceptance checks the sample's labels and network URLs, then changes an importer directory, adds a nested scope and introduces an unmapped name. Preserve expected and actual outcomes before repeating the relationships in production output. None was run here. Hand over an explainable import-resolution table before claiming the old feature is isolated.
