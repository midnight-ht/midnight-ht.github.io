Why does Decimal(0.1) still contain a long fraction?

Distinguish decimal text, existing floats, arithmetic precision and FloatOperation exceptions without claiming that conversion restores lost input.

Updated 2026-10-31 · Estimated read 15 min

Article

Key takeaways

  • Decimal constructed from float preserves that existing binary value.
  • Context precision does not simply truncate every constructor input.
  • FloatOperation has specific exceptions; validate the input contract separately.

Decimal(0.1) receives an already-created binary floating-point value and preserves that value accurately. It cannot recover the decimal text the caller originally intended. If an interface requires decimal input semantics, preserve text at the boundary or use parsing that does not first produce a float. Lowering Decimal context precision does not turn construction into a repair step for float input.

Why does an accurate conversion produce a long fraction?

The Python 3.14 decimal reference specifies accurate conversion from float. The page checked on October 31, 2026 identified itself as Python 3.14.10. The program below was not run and does not define financial, tax or settlement rules.

Python creates the literal 0.1 as a float before passing it to Decimal. That binary floating-point format cannot represent this decimal fraction exactly. Decimal expands the value it actually received, which explains the long representation. The earlier conversion has already happened; the later type cannot infer the lost intention.

The text form Decimal('0.1') instead constructs a value from decimal text. The two results do not mean Decimal is accurate in one case and broken in another. Their inputs differ. A float originating in a measurement may be exactly the value that should be preserved; a float inserted into a decimal-text interface may violate its contract. Source meaning, rather than short output, determines the appropriate conversion.

An explicit Decimal.from_float call makes intentional preservation of a float explicit. Converting every float through str first instead chooses the decimal value corresponding to that float's current string representation. It cannot recover the original text, trailing zeros or input format. It is not a universal precision-recovery formula for historical data.

When does context precision apply?

The documentation distinguishes construction from arithmetic. The supplied input determines the digits of a new Decimal; context precision and rounding apply to arithmetic and other operations that consult the context. Setting precision to three does not mean every constructed value has three significant digits, much less three decimal places.

This complete, unexecuted program uses only supplied constants and the standard library. Capture actual output when running it; the assertions express expected relationships rather than presenting fabricated terminal logs.

from decimal import Decimal, FloatOperation, localcontext


def main():
    from_text = Decimal('0.1')
    from_binary = Decimal(0.1)
    explicit_binary = Decimal.from_float(0.1)
    print('text:', from_text)
    print('float:', from_binary)
    assert from_binary == explicit_binary
    assert from_text != from_binary

    with localcontext() as ctx:
        ctx.prec = 3
        exact_input = Decimal('1.23456')
        rounded_sum = exact_input + Decimal('0')
        print('construction:', exact_input)
        print('arithmetic:', rounded_sum)
        assert exact_input == Decimal('1.23456')
        assert rounded_sum == Decimal('1.23')

    with localcontext() as ctx:
        ctx.traps[FloatOperation] = True
        try:
            Decimal(0.1)
        except FloatOperation:
            print('implicit float input rejected')
        else:
            raise RuntimeError('expected FloatOperation')
        intentional = Decimal.from_float(0.1)
        print('explicit conversion:', intentional)


if __name__ == '__main__':
    main()

The first comparison separates text and binary provenance. The second preserves the input, then performs addition by zero to expose the arithmetic boundary. Adding zero does not change the ideal mathematical value, but it still executes a context-sensitive operation. The precision of three demonstrates that mechanism; it is not a recommended business setting.

The third section enables the FloatOperation trap to catch accidental float construction. localcontext confines these settings rather than changing the context expected by unrelated subsequent code. Assertions here document teaching relationships. Production input rejection should use explicit checks rather than assert, which an optimized interpreter can disable.

Does FloatOperation prevent every float from entering the system?

It is not general-purpose taint tracking. The reference specifies particular mixed operations: with the trap enabled, certain constructions and ordering comparisons raise, while equality comparisons and explicit conversions have exceptions. The example deliberately uses from_float as an explicit permitted conversion. A configuration setting cannot replace tracing values through decoding, arithmetic, serialization and persistence.

An interface accepting only decimal strings can check the input type, parse its defined syntax, then validate finite values and business bounds. Decimal can represent non-finite values; that does not authorize NaN or Infinity in a business field. Excessively long input also needs a resource policy. Actual field requirements must determine those limits, not arbitrary numbers in a tutorial.

If an upstream system must send JSON numbers, check whether the selected decoder first creates floats and whether it supports the required decimal semantics directly. Wrapping a downstream float in Decimal does not establish lossless preservation of the original decimal. The output contract also needs a deliberate representation, such as a string or integer unit, so serialization does not silently reverse the choice.

Can Decimal(str(value)) restore the user's input?

It creates a value from the current string representation, not from historical provenance. The user may have supplied more digits, exponent notation or trailing zeros that an earlier conversion discarded. Where audit requirements justify it, preserve an appropriately protected original representation or recover it from a trusted original record. Do not reconstruct a shorter value and report it as the text originally received.

The existing article on PostgreSQL numeric and input rounding explains why a storage scale is not an input-rejection rule. This question occurs earlier: the Python application can change numerical meaning before the database sees it. A correct final column type is not evidence that the preceding path preserved the input.

Input tests should distinguish numerical equality from identical representation. A contract may accept both a tenth and a tenth written with a trailing zero while preserving that scale for display or measurement. Whether to merge them is a field decision. Numerical equality cannot prove unchanged text, but a trailing-zero difference is not automatically an error either.

Start another comparison from request bytes: send the field as text and as a JSON number, then record decoded type, pre-arithmetic representation, result and database parameter. A unit test constructing Decimal from text bypasses the parser where float may enter. A passing path covers that serialization route, not every client encoding.

A proposed validation should cover text and float construction, explicit conversion, low-precision arithmetic, trap exceptions, non-finite values and actual types passed from the request decoder to database parameters. Derive expectations from the contract independently of the implementation. None was run here. After choosing Decimal, the remaining question is which value it actually receives; the type name cannot answer its provenance.
