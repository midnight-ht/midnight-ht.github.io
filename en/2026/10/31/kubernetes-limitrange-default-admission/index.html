Why does the admitted Pod contain an unrequested CPU request?

Compare submitted and admitted Pods with a complete namespace example, covering default injection, conflicting values, and unchanged existing Pods.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-31 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • A missing template field does not prove an absent Pod request.
  • Explicit requests and default limits must remain consistent.
  • Policy changes do not rewrite existing Pods.

A Pod can acquire CPU requests absent from the submitted manifest because a namespace LimitRange can inject default requests and limits during admission. Compare the submitted definition, namespace policy, and actual Pod before inferring what the scheduler received. A resource problem is not automatically a reason to raise quota.

Follow the field through admission

The Kubernetes Limit Ranges documentation describes default injection and per-object constraints. This article checked the current page on October 31, 2026. Its navigation displays v1.37, but the URL is not pinned to that release. Verify the actual cluster version and enabled admission behavior.

The developer's template, the object after control-plane processing, and the resource declarations used for scheduling are related materials, not necessarily identical text. A controller-created Pod still passes through admission. A missing template field therefore does not prove the final object lacks a value. Preserve the source of defaults alongside the workload definition.

ResourceQuota request accounting concerns aggregate namespace allowances. This question concerns the origin of one Pod's resource fields. Injection can affect later accounting, but calling both policies quota obscures the configuration that needs correction.

A complete illustrative configuration

The following unexecuted teaching example defines a namespace, one container-level LimitRange, and a Pod without explicit resources. It assumes the relevant admission behavior is enabled and no other policy changes the values. The image demonstrates object structure; image availability has not been tested.

apiVersion: v1
kind: Namespace
metadata:
  name: limitrange-demo
---
apiVersion: v1
kind: LimitRange
metadata:
  name: cpu-defaults
  namespace: limitrange-demo
spec:
  limits:
    - type: Container
      defaultRequest:
        cpu: 100m
      default:
        cpu: 500m
---
apiVersion: v1
kind: Pod
metadata:
  name: defaulted
  namespace: limitrange-demo
spec:
  containers:
    - name: demo
      image: registry.k8s.io/pause:3.10

In an isolated validation, establish the namespace and policy before submitting the Pod, then inspect the resource fields saved by the control plane. The paper expectation is a default CPU request and limit. The YAML is not a creation receipt. Additional admission mutations need their own explanation rather than being forced into this simplified model.

One hundred millicores is not a capacity recommendation. The numbers distinguish the fields and their origin. Actual sizing needs workload evidence; a small default does not automatically reduce real consumption.

Explicit requests can conflict with default limits

Modify the example conceptually so the Pod explicitly requests 700m CPU but supplies no limit. Admission can supply the 500m default limit, leaving a request greater than its limit. Inspect the actual API response, controller events, and object existence to locate validation or admission failure. Do not assume this necessarily creates a Pending Pod.

The official page illustrates an inconsistent request/default-limit combination. This article uses it to explain effective values, not to promise an identical error string or response code across versions. No API request was run. If the object was never accepted, waiting for scheduling cannot fix it. If it exists but is unplaced, investigate the recorded scheduling reason separately.

Possible corrections include explicit, justified workload requests and limits or a review of namespace defaults. The choice depends on policy ownership, the application's resource commitment, and other affected consumers. Lowering a request solely to pass admission is not capacity validation. Raising a shared default can also affect unrelated applications.

Compare replacements with explicit records

A controlled comparison can create an old Pod, change the default request, and create a new Pod from an unchanged template. Record the template identity, policy contents, creation times, and saved resource fields. Different values are consistent with defaults applying at creation; they do not show that a running process changed its own allocation.

If observations differ, exclude a different template, an absent policy, or another mutating actor. Similar Pod names do not identify one delivery. Check controller ownership and object identity rather than list order.

These records inform migration choices. If existing resource commitments must be preserved, assess replacement under the new defaults first. If replicas must converge, assign ownership for the workload update and verify its results. Defaults alone complete neither migration nor preservation. Treat the policy version as a release input.

Does changing a LimitRange rewrite existing Pods?

No. The documentation limits these checks to Pod admission; existing Pods retain their configuration. Compare actual objects by creation time instead of treating an updated policy as a completed migration.

An unchanged controller template can produce replacement Pods under a newer default policy. During replacement, replicas may therefore carry different effective settings. Check the actual objects and creation records, not only a Deployment template. If consistency is required, coordinate the default change with an owned workload-update process.

The documentation also warns that defaults are nondeterministic when multiple LimitRange objects exist in the namespace. Do not infer a winner from object names or modification time. Consolidate competing defaults and verify the intended result with a new object.

A proposed validation covers absent fields, explicit fields, conflicting combinations, and old versus new Pods after a policy change. Record submissions, policy versions, responses, saved objects, and subsequent events. No cluster was connected and no creation, scheduling, or readiness result is reported here. Establish where the fields came from before changing the layer that accounts for or schedules them.
