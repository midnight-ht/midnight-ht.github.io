Does an indeterminate HTML checkbox submit a third value?

Separate indeterminateness, checkedness and native entries with a complete local example, then examine activation, scope and business enums.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-31 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • Indeterminateness does not create a third submitted value.
  • A Select all controller needs an explicit child set.
  • Filtering, restoration and data changes require recalculation.

A dash in Select all does not make native form submission send a mixed value. Indeterminateness is independent of checkedness. An application representing partial selection must manage both states and the child set they summarize. Inspect the selected children and actual entries rather than inferring a business value from the dash.

Mixed presentation is not a third submitted value

The current HTML input definition distinguishes indeterminateness from checkedness. It affects checkbox rendering and accessibility semantics, so describing it as purely decorative is too narrow. It does not create a third checked value. The source consulted was marked updated on 30 October 2026.

Native entry-list construction uses checkedness when deciding whether to include a checkbox, then applies its value rules. A controller can therefore expose a mixed state while the payload contains only selected children. A summary and its business details have different responsibilities.

For this example, no children selected means both controller states are false; partial selection means checked is false and indeterminate is true; complete selection means checked is true and indeterminate is false. This is an application convention. The browser does not discover the children and calculate it automatically.

A complete local preference example

Save this unexecuted example as HTML. It has no backend and sends no notifications. Submission is intercepted to display the native FormData values.

<!doctype html>
<html lang="en">
<meta charset="utf-8">
<title>Notification selection example</title>
<form id="prefs">
  <fieldset>
    <legend>Choose demonstration notifications</legend>
    <label><input id="all" type="checkbox">Select all three</label>
    <label><input class="item" name="channel" value="mail" type="checkbox">Email</label>
    <label><input class="item" name="channel" value="sms" type="checkbox">SMS</label>
    <label><input class="item" name="channel" value="inbox" type="checkbox">Inbox</label>
  </fieldset>
  <button type="submit">Show pending values</button>
</form>
<pre id="result"></pre>
<script>
const form = document.querySelector('#prefs');
const [master, ...items] = form.querySelectorAll('input');
const total = items.length;
function sync() {
  const selected = items.filter(item => item.checked).length;
  master.checked = total > 0 && selected === total;
  master.indeterminate = selected > 0 && selected < total;
}
master.onchange = () => {
  for (const item of items) item.checked = master.checked;
  sync();
};
for (const item of items) item.onchange = sync;
form.onsubmit = event => {
  event.preventDefault();
  document.querySelector('#result').textContent =
    JSON.stringify(new FormData(form).getAll('channel'));
};
sync();
</script>
</html>

The controller intentionally has no name: it operates the children rather than representing a fourth notification channel. Selecting Email should produce a mixed controller and an array containing mail. Activating Select all should select all three; clearing one child should restore mixed presentation. These are code-derived expectations, not recorded browser results.

Native user activation changes checkedness and clears indeterminateness; the application then recalculates the summary. In this example partial selection sets checked false, so activation takes the select-all route. A framework that intercepts activation or recreates elements needs verification against its final DOM.

Setting only indeterminate while leaving a named controller checked can add an unwanted controller entry. Updating the controller without its children creates the opposite mismatch: an apparently selected group with an unchanged payload. Compare states and entries to distinguish them.

What does Select all mean after filtering?

The example fixes the scope at three items. Real lists may paginate, filter or contain unavailable records. Selecting the visible page and selecting all search results are different promises; indeterminate chooses neither. Labels, counts and the request must identify the same scope.

If a search returns one hundred records but displays ten, a partial controller might summarize the page or the entire result. Maintain selected identities, the currently eligible set and the action scope explicitly. Counting only current DOM checkboxes cannot establish a selection across pages.

Unavailable children also need a policy: exclude them from the action, or preserve historical selections while preventing edits. Update the denominator and accepted set accordingly. Checkbox required and group constraints handles a different question: whether at least one selection is required.

Recalculate after restoring a draft, removing a channel or remounting the component. A one-time initialization of the dash cannot maintain a changing relationship.

What if the business field really has three states?

Allow, deny and inherit are an explicit business enum, not a summary of selected children. Define an input and request contract for those meanings rather than treating indeterminate as inherit. Similar presentation does not make the entities equivalent.

Proposed acceptance covers empty, partial and complete selection; mouse and keyboard activation; removing a child; pagination; and data reload. Record checked, indeterminate, FormData and retained identities. A real service must validate permitted values and permissions; this local array proves neither delivery nor persistence.

An empty eligible set needs special handling: selected count equals total count at zero, but nothing has been selected. The sample explicitly requires a positive total for checked. A real page should explain why no items are available and decide whether the controller is actionable.

After a failed save, distinguish the editable selection from the last server-confirmed selection. The controller should still summarize the current choices while the interface explains that they are unsaved. If a service rejects one item, identify it and offer correction before recalculating; silently clearing the group hides the failure. The local sample implements no persistence.

Assistive-technology checks should examine the controller's scope label, mixed-state interpretation and child operation in the supported environment. None was run here. A useful handoff lets a tester answer which set the dash summarizes and which identities the request contains.
