Can repeated clicks inside Playwright toPass create multiple records?

Use a complete local test to separate creation from observation and review toPass, poll, timeouts and uncertain command outcomes.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-31 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • ToPass can execute the whole callback again.
  • Repeating writes needs an actual business contract.
  • A local observation timeout does not extend the test budget.

Putting creation and its immediate check in a toPass callback can repeat the creation when the check fails. A test intended to wait for one result can become a test that issues another command. Separate the side effect from repeated observation before choosing a retry mechanism.

The retry unit is the code block

The Playwright assertions guide describes expect.toPass as retrying a block until it passes. It also provides expect.poll for repeatedly producing an observed value. Neither implies that the supplied callback executes only once or that only its last assertion is repeated.

If a callback clicks Create and immediately reads the record count, an early failure can lead the next attempt to click again. A failed assertion does not roll back a command already accepted by the application. This is an inference about callback repetition and side effects, not a claim that every application necessarily creates duplicates.

A display toggle, an irreversible submission and an explicitly idempotent command have different repeatability. Inspect the operations, not the callback's reassuring name.

Prepare a complete local observation sample

This unexecuted Playwright Test example simulates delayed display in a local DOM. It uses no backend and proves nothing about real ticket persistence. In a new directory, install the tool, save the test as observe.spec.mjs and run the named file. None of the commands or dependency downloads was executed here; existing projects should follow their lockfile and version policy.

npm init -y
npm install --save-dev @playwright/test
npx playwright install chromium
npx playwright test observe.spec.mjs --workers=1

import { test, expect } from '@playwright/test';

test('create once, then observe one local record', async ({ page }) => {
  await page.setContent(`
    <button id="create">Create demo record</button>
    <output id="attempts">0</output>
    <ul id="records"></ul>
    <script>
      let attempts = 0;
      const [button, counter, list] = ['create', 'attempts', 'records'].map(
        id => document.getElementById(id)
      );
      button.onclick = () => {
        attempts += 1;
        counter.value = String(attempts);
        const record = document.createElement('li');
        record.dataset.recordId = 'demo-' + attempts;
        record.textContent = 'Pending';
        list.append(record);
        setTimeout(() => { record.textContent = 'Ready'; }, 100);
      };
    </script>
  `);
  await page.getByRole('button', { name: 'Create demo record' }).click();
  const [record, records, counter] = [
    '[data-record-id="demo-1"]', '#records li', '#attempts'
  ].map(selector => page.locator(selector));
  await expect(record).toHaveText('Ready');
  await expect(async () => {
    expect(await records.count()).toBe(1);
    expect(await counter.innerText()).toBe('1');
  }).toPass({ timeout: 2_000, intervals: [100, 250] });
});

Creation sits outside the retried callback. A locator assertion waits for Ready, while toPass contains reads and comparisons. The two-second local budget is illustrative, not a product performance target. The page fixture comes from the declared test, and record identity is explicitly generated by the sample.

The sample checks local creation count and delayed text. A production test needs an identity provided by its actual business contract and evidence of the relevant state. Do not reuse demo-1 as a production assumption or describe local DOM changes as database persistence.

Choose by the observation contract

For one visible text condition, investigate the corresponding auto-retrying locator assertion. Use poll when repeatedly obtaining a value is appropriate. Consider toPass when a group of observations and assertions must succeed together. Wrapping everything in another retry layer does not inherently make a test stronger.

Several reads are not automatically an atomic snapshot. The application can change between reading a list count and reading a status. One successful callback establishes the conditions it actually checked, not consistency across systems. A same-version joint observation needs support from the real interface or controlled test data.

Whole-test retries are another layer. Retried tests and first-failure evidence discusses worker rebuilding and test attempts. A toPass callback can repeat inside one test attempt. Label test attempts and observation attempts separately in diagnostics.

Does it inherit the expect timeout?

The current guide specifically notes that toPass defaults to timeout zero and does not respect a custom expect timeout. Configure the local bound deliberately and check the installed version. It cannot extend an already exhausted outer test budget.

There is no universal CI timeout recommendation here. The sample's two seconds makes the local boundary visible. A real choice should explain the expected state, its acceptable wait and retained failure evidence. More time cannot repair an observation aimed at the wrong object.

Can creation be repeated after a request timeout?

An uncertain result is not proof that the service accepted nothing. Use the service's real query, identity or idempotency contract to determine recovery. The test framework does not supply that business guarantee, and this article does not invent an endpoint or idempotency-key feature.

If duplicate-click prevention is the requirement, deliberately issue multiple actions in a separate test with an explicit expected record count and feedback. Accidental repetition inside an observation loop is not equivalent coverage.

Inspect the cost of a nominal read too. A query may refresh state, consume a quota or invoke an external service. A repeated callback needs an interface that is actually appropriate for repeated observation and a reasonable sampling interval. This sample reads only local DOM.

Cleanup is not automatic rollback after a failed callback. Real temporary records need identifiable ownership and explicit cleanup, with failures retained. Later attempts must not mistake old records for new success, and backend tasks may outlive the test. The local page sample provides no server-lifecycle guarantee.

Proposed validation lengthens the sample delay, logs action and observation times, then deliberately moves the click into the callback to compare action counts. Preserve the file, actual version, command and raw output before reporting execution. None of those variants was run here. First identify every write inside the callback and explain why it may repeat; unexplained writes belong outside that boundary.
