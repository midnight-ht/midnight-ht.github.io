WITH HOLD ends one transaction, not the export resource bill

Separate transaction, session and retained-result lifetimes for WITH HOLD, then compare pool affinity, pagination and stored export artifacts.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-31 · Estimated read 15 min

Article

Key takeaways

  • WITH HOLD survives successful commit within the original session.
  • Small FETCH batches do not establish negligible server-side retention.
  • Cross-process recovery warrants an explicit export identity and artifact.

WITH HOLD lets a PostgreSQL cursor survive the successful commit of its creating transaction. It does not remove an export's resource obligations. The cursor still belongs to its original session, and the current implementation retains its rows in temporary storage or memory. It changes a transaction boundary without promising arbitrary-connection resumption, unlimited results or zero server-side storage.

What survives the commit?

PostgreSQL 18's DECLARE reference distinguishes ordinary cursors from held cursors. WITHOUT HOLD is the default and restricts use to the creating transaction. WITH HOLD permits use by later transactions in the same session after a successful commit. This article checked the documentation on October 31, 2026. It discusses SQL-level cursors, not PL/pgSQL cursor rules or every driver object also called a cursor.

Separate three lifetimes: the transaction, the database session and the retained result. Ending the first need not end the second. Surviving a commit does not make the cursor a persistent application object. A held cursor closes on explicit CLOSE or session termination; aborting its creating transaction removes it.

Consider an administrative report downloaded in small batches by a slow client. An ordinary cursor can fetch incrementally inside its transaction, but the client's pace can prolong that transaction. WITH HOLD changes this arrangement while leaving the database responsible for retaining the result. A small FETCH does not establish that the server retains only that batch.

The reference states that the current implementation copies a held cursor's rows into a temporary file or memory area for later transactions. This is a mechanism, not a measured storage or latency result for a particular dataset. No materialization time, temporary-file size or unlimited-export configuration is reported here.

Check the boundary in a single session

This complete, unexecuted teaching sequence uses one psql session in an isolated database. Generated data avoids dependencies on business tables:

BEGIN;
DECLARE demo_report NO SCROLL CURSOR WITH HOLD FOR
  SELECT n, 'item-' || n::text AS label
  FROM generate_series(1, 5) AS t(n)
  ORDER BY n;
FETCH FORWARD 2 FROM demo_report;
COMMIT;
FETCH FORWARD 2 FROM demo_report;
FETCH FORWARD 2 FROM demo_report;
CLOSE demo_report;

The documented expectation is that the first batch contains one and two, the next contains three and four after commit, and the final batch contains only five. ORDER BY defines that sequence. These are inferred expectations, not captured output. Check batch contents, successful commit, the partial final batch and closure rather than validating only the first fetch.

For a contrast, create a differently named cursor WITHOUT HOLD and try fetching after commit. Test rollback separately by declaring WITH HOLD and then rolling back its creating transaction. Keep expected errors in separate test stages so that an aborted transaction does not contaminate later observations. Check that no experimental cursors remain.

Another useful case closes the original connection and attempts a same-named FETCH through a new connection. A new session cannot resume the result merely by reusing the name. If a driver reuses database backends, inspect actual session identity rather than assuming a new application connection object implies a new database session. No pool was run here, so this procedure does not establish compatibility with any pool mode.

Why does pooling change the export decision?

The export must return to the same database session while using the cursor. A request pool can assign successive calls to different connections; a transaction pool can reassign the backend after commit. Storing a cursor name in a download token does not make that session's result available to arbitrary backends. Check the actual pool mode and driver support for session affinity before selecting WITH HOLD.

Dedicating a connection to the export introduces explicit decisions: concurrent-export limits, idle cancellation, closure failures and cleanup after the user leaves. Suitable limits depend on the connection budget and workload, so no universal numbers are supplied. An HTTP timeout does not by itself tell the database resource owner to close its cursor. Terminating the session ends the cursor but also prevents later continuation.

A bounded query completed within one controlled session can reasonably accept these costs. Work that must pause for hours, survive another process or provide a download the following day should evaluate a separately stored artifact and queryable job identity. That adds artifact storage and cleanup, but makes retention an observable application responsibility instead of an implicit database session lifetime.

Is this the same as API cursor pagination?

The state is different. A keyset pagination token usually carries a sorting boundary and leads to a new query. SQL DECLARE creates a session-owned cursor object. The existing article on pagination order and cross-page consistency discusses sorting values, mutations and snapshot promises. An encoded page boundary is not a handle to a database session's result.

Keyset pagination avoids retaining this SQL cursor, but mutable sort fields can still affect cross-page consistency. A held cursor retains a result while incurring storage and session obligations. Choose first between browsing changing data and exporting a fixed collection; then compare recovery, snapshot and retention requirements. A shared word in their names does not make the mechanisms interchangeable.

Can WITH HOLD keep records locked for later editing?

It cannot be combined with FOR UPDATE or FOR SHARE in the query. An editing interface needs its own authorization, version checks and transaction arrangement. A long-lived report result should not become an editing lock. Likewise, seeing an old exported row is not sufficient authorization or concurrency evidence for modifying the current record.

Freshness belongs in the delivery contract too. If another connection changes a product name after an export starts, the retained result must not be presented as the latest state at the moment a user opens it. Identify the query scope and generation task; editing should read a current version separately. Retaining an older result then becomes an explicit choice rather than an apparent failed update.

Validate more than successful CLOSE. Let a client leave halfway through and observe cancellation receipt, closure attempts, recorded failures and connection return. Without evidence of completed cleanup, retain a pending-cleanup state. Writing an application completion timestamp does not release a database session result.

Proposed validation includes reading after commit, rollback of the creating transaction, explicit closure, session disconnection, pool reassignment and resource observation with representative result sizes. None was executed. A review should identify who owns the session, where the result is retained, what closes it and whether disconnection causes a restart or a recoverable export. Avoiding the original long transaction answers only one of those questions.
