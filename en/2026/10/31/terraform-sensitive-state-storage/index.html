Why does Terraform sensitive hide output but retain state?

Use a fake-value local configuration to separate redaction from persistence, then review ephemeral capabilities, plans, state, and exports.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-31 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • Sensitive marking does not exclude values from state or plans.
  • Omission capabilities depend on version, context, and provider support.
  • Remote state does not protect every plan or exported copy.

Terraform's sensitive marker hides values in ordinary output; it does not remove those values from state and saved plans. A redacted terminal is insufficient reason to share a state file, plan artifact, or backup as ordinary data. Decide whether the requirement is hiding, controlled storage, or preventing persistence before choosing a mechanism.

Redaction and persistence answer different questions

Terraform's sensitive data management guide distinguishes these goals. Local state can retain sensitive values in plaintext. The sensitive marker does not exclude them from state or plans, while ephemeral values and write-only arguments have additional version and usage requirements. This article checked the online guide on October 31, 2026. No Terraform command was run and no infrastructure state was accessed.

Redaction reduces accidental exposure through routine interfaces. Storage controls address location, readers, backups, transfers, and retention. Those controls can complement one another but are not interchangeable. Generated materials may need credential-level protection even when the source variable is marked sensitive.

A saved plan is a separate handoff. A team might protect remote state carefully but upload plans as ordinary CI attachments or share an entire working directory for diagnosis. Follow the files actually generated and retained rather than looking only for secrets written literally in source code.

A complete local exercise with a fake value

This unexecuted exercise uses a separate empty directory containing main.tf. It requires Terraform 1.4 or later for the built-in terraform_data resource. The string is explicitly invalid training material. The configuration connects to no cloud service and creates no genuine credential.

terraform {
  required_version = ">= 1.4.0"
}

variable "demo_secret" {
  type      = string
  sensitive = true
  default   = "training-only-not-a-credential"
}

resource "terraform_data" "demo" {
  input = var.demo_secret
}

output "demo_secret" {
  value     = terraform_data.demo.output
  sensitive = true
}

The proposed sequence in that exercise directory is:

terraform init
terraform plan -out=demo.tfplan
terraform apply demo.tfplan

There is no execution receipt here. The observation is whether ordinary redaction coexists with values in saved local materials. Applying creates local state; saving the plan also leaves an artifact. Do not substitute a production password and then upload the directory for help.

A controlled local checker can report only whether the harmless training marker was found, without dumping the file to shared logs. Record which artifact and generation stage were examined, along with the tool version. Failure to find one literal string does not establish the absence of other sensitive fields, representations, or backups.

Why is another marker not a universal replacement?

The guide places sensitive variable and output arguments at Terraform 0.15 or later, ephemeral capabilities at 1.10 or later, and resource write-only arguments at 1.11 or later. Providers define the available ephemeral resources and write-only arguments. A qualifying Terraform version does not make every resource support them or every reference context accept an ephemeral value.

Start with the actual data path. If a resource interface persists a field, do not promise that a display marker removes it. If a provider offers a suitable write-only argument, inspect its update and version-management contract. For temporary data, check whether the chosen context accepts an ephemeral value. Similar argument names do not prove compatible behavior.

When the installed version or provider lacks a capability, improve access and storage controls while documenting remaining persistence. Removing a sensitive marker merely to make a plan succeed is not a solution. If persistence is prohibited, an unsupported capability is a design constraint requiring a different handoff or tool arrangement.

Does remote state eliminate local plan protection?

No. Encryption and access behavior depend on the backend, while saved plans, downloaded copies, and logs still need separate treatment. A remote location can provide centralized controls without proving that every consuming path is safe. Document who can read state, generate plans, export data, and retain attachments.

The article on state-lock coordination concerns concurrent writers. This article concerns disclosure. A lock is not confidentiality control, and encryption does not prevent an authorized reader from exporting data. Verify write coordination, encryption, and read permissions independently.

A saved plan is not a plain-text search target

A plan has its own format. Failure to find the training string with an ordinary search does not establish absence. The terraform show reference provides machine-readable inspection and warns that JSON output exposes sensitive values. Inspection can create another readable copy, so keep it in a controlled location rather than shared CI logs.

For this fake-value exercise, a local reviewer can inspect the structure with the appropriate version and schemas and retain only whether the intended field contains the training marker. Evidence should not unnecessarily reproduce the entire secret. Any authorized inspection of raw values still needs access and temporary-file ownership.

The Terraform 1.4 terraform_data reference supports the built-in input/state/output exercise without a configured provider. Real resources can additionally send values to an external system. Do not generalize this local example into uniform provider behavior; review those additional data paths separately.

Can ephemeral values go into any resource field?

No universal substitution is implied. Check the Terraform version, permitted reference contexts, and provider argument documentation. Unsupported positions need an explicit decision rather than a silent fallback to persistence. The exercise intentionally avoids those capabilities because it demonstrates the storage boundary of sensitive, not a provider-specific replacement.

A proposed verification covers ordinary display, saved plans, post-apply state, backups, and authorized exports using invalid test markers. If genuine credentials were exposed, address revocation, rotation, and retained copies; deleting today's state file does not invalidate an old credential. No real exposure was handled here. The useful outcome is an explanation of why each sensitive value is stored, where it is retained, and who may retrieve it.
