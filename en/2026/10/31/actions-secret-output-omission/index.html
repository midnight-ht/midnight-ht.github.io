Why is a GitHub Actions job output missing downstream?

Trace step outputs, job mappings, and runner finalization; validate a harmless handoff and choose an authorized path for secrets.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-31 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • Writing a step output does not establish job-output delivery.
  • Reject invalid references before dependent actions.
  • Encoding does not provide secret-transfer authorization.

Writing to GITHUB_OUTPUT does not prove that a dependent job received the value. Check whether the producing step ran, whether its output was mapped to a job output, and whether the runner omitted that output during end-of-job processing because it might contain a secret. A missing deployment parameter should stop the dependent action before it selects a target.

The handoff continues after the step finishes

The job outputs section of GitHub Actions workflow syntax describes evaluation at the end of the job. Outputs containing secrets are redacted on the runner and are not sent to GitHub Actions; a suspected secret produces an omission warning. This article checked the online reference on October 31, 2026. The workflow below has not been executed, and no repository-specific detection result is claimed.

There are four separate handoffs: a script writes a step output; a step ID makes that output addressable; the job maps it to a job output; a dependent job reads it through needs. A missing link can look like an empty value. A message printed by the producing script cannot establish what happened during later job finalization.

Investigate without turning diagnostics into another secret store. Record step results, output key names, mapping expressions, and relevant omission warnings. Reproduce structural mistakes with harmless values before inspecting a privileged workflow. Printing a production credential is unnecessary evidence for whether a mapping exists.

A complete handoff using a non-secret reference

This manually triggered workflow can be saved as a workflow file in a test repository. It passes only a reference derived from the run ID. It contains no deployment, secret store, or credential. It is an unexecuted illustration of mapping and consumer validation, not a reproduction of secret detection.

name: output-reference-demo
on: workflow_dispatch
permissions:
  contents: read
jobs:
  prepare:
    runs-on: ubuntu-latest
    outputs:
      ref: ${{ steps.make.outputs.ref }}
    steps:
      - id: make
        shell: bash
        run: printf 'ref=run-%s\n' "$GITHUB_RUN_ID" >> "$GITHUB_OUTPUT"
  inspect:
    runs-on: ubuntu-latest
    needs: prepare
    steps:
      - name: Check the non-secret handoff
        shell: bash
        env:
          REF: ${{ needs.prepare.outputs.ref }}
        run: |
          if [[ ! "$REF" =~ ^run-[0-9]+$ ]]; then
            printf 'Missing or invalid reference\n' >&2
            exit 1
          fi
          printf 'Received non-secret reference: %s\n' "$REF"

The prepare job maps ref from the make step. The inspect job declares its dependency and rejects both an empty value and an unexpected format. The example prefix is merely a demonstration contract; it is not a production authorization boundary.

A run ID does not automatically identify a stored secret. A real reference design must define the object, its version, and the identity permitted to retrieve it. Knowing a reference should not grant access by itself. Missing objects, revoked versions, and denied reads need explicit failures rather than a search for a convenient older credential.

Does encoding the value solve the problem?

Encoding changes representation, not authorization, confidentiality, or revocation. Avoiding a detector does not turn a secret into approved public metadata. Explain who can read the channel and where the value is retained before deciding that it is suitable for the handoff.

If the consumer needs a secret, use an authorized identity to retrieve a controlled object, potentially through a non-secret reference to a specific version. If it needs only a build identifier, artifact digest, or plan identifier, pass that metadata instead of an entire authentication response. Narrower outputs also make missing-data failures easier to diagnose.

This relates to reviewing workflow token permissions. Splitting work into two jobs does not decide who may create or retrieve secrets, or which third-party steps share the resulting identity. A valid reference format is not evidence of appropriate privilege.

Four records that lead to different repairs

Separate four states instead of recording only an empty output. If the producing step never ran, retain its skipped or failed result and inspect control flow. If it ran but the mapping key is wrong, retain the step ID, key, and mapping expression and repair that link using harmless data.

If the step and mapping are supported but finalization reports omission, preserve the key and warning and reconsider the transport. Do not widen a consumer default. If the value arrives but fails the consumer's format check, compare producer and consumer contract versions rather than disabling validation.

Attach the run ID and producer version to those records. Mixing yesterday's successful step log with today's failed consumer creates false evidence. A rerun can produce a new reference; recovery must identify which production attempt the consumer uses. For deployment parameters, confirm that the reference still identifies the authorized object rather than copying an apparently valid value from old logs.

How do you distinguish omission from a step that never ran?

Inspect the producing job and step results first. Then check the step ID, output key, and job mapping. If the producer succeeded but the consumer has an empty value, inspect end-of-job warnings. If the producer failed or was skipped, explain that control flow first. Neither every empty output nor every missing warning identifies a secret-detection outcome.

A proposed test starts with the harmless workflow above, then deliberately misspells the mapped key in a disposable branch. The consumer should reject the missing reference and perform no dependent action. Investigate an actual secret-omission case separately, retaining the trigger, runner environment, output key, and warning under the repository's authorized diagnostic process. These checks have not been run here.

Finally, inspect the consumer's failure behavior. A warning followed by deployment to a default environment defeats the guard. Dumping all contexts during recovery can introduce new secret copies. Reject an invalid handoff before side effects and give the operator a defined recovery path.
