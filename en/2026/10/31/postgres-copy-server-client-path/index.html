The CSV is on my laptop. Why can COPY not find it?

Choose server or client file access before debugging COPY; inspect a complete CSV import's fields, permissions and commit boundary.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-31 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • A COPY filename belongs to the database server's file environment.
  • psql's backslash copy is a client meta-command, not driver SQL.
  • File access, copied counts and committed business acceptance differ.

A CSV on your laptop is not automatically readable by a remote PostgreSQL COPY FROM 'filename'. With a filename, COPY opens the file on the database server, using that environment's paths and operating-system permissions. To read a local file, use psql's \copy or a driver's COPY STDIN interface. Decide which process should open the file before changing permissions.

Which machine owns the absolute path?

PostgreSQL 18's COPY reference distinguishes filenames from STDIN: a filename instructs the server to access a file directly, whereas STDIN transmits data over the client connection. This article checked the version 18 documentation on October 31, 2026. No import was executed and no real host's permissions were inspected.

Suppose an operator saves /tmp/customers.csv on a laptop and connects psql to a cloud database. Sending a COPY statement with that path sends SQL across the network, not the file's contents. The server looks in its own environment. Even identical paths on both machines do not establish identical contents. Granting a database role more privileges cannot make the laptop's file appear on the server.

Containers add another boundary. A host directory need not be mounted into the database container, and a directory with the same name inside the container may contain different data. Record the client process, server process, file location and mount relationship. Then decide which side needs file access. Making a directory world-readable is not a substitute for that diagnosis.

Server-side file COPY can be appropriate for controlled batch processing where the data is deliberately available to the database host. It needs suitable deployment permissions and data-management rules. Client-side access also requires permissions: the caller still needs the necessary database privileges on the target and remains responsible for allowed columns and business scope.

A small local-file import procedure

This unexecuted example requires psql on the local machine and an independently configured connection to an isolated test database. Keep passwords and tokens out of the example. Save the following UTF-8 text as a local file named customers.csv:

external_id,display_name
101,"Lin, Mei"
102,"He said ""hello"""

Connect psql to the test database and create the teaching table. These columns demonstrate the data path, not a production customer model:

CREATE TABLE demo_customer_import (
  external_id integer PRIMARY KEY,
  display_name text NOT NULL
);

Run the next line inside psql, replacing the absolute path with your actual local file. Keep the meta-command on one line rather than applying ordinary multiline SQL assumptions to psql's command parser:

\copy demo_customer_import(external_id, display_name) FROM '/absolute/path/customers.csv' WITH (FORMAT csv, HEADER true, ENCODING 'UTF8')

Inspect the values, not just a reported row count:

SELECT external_id, display_name
FROM demo_customer_import
ORDER BY external_id;

From the CSV text and quoting rules, the first name should retain its comma and the second should retain the quotation marks. These are expectations, not captured output. Record the psql version, target database, input file digest and actual query result when running the procedure. A count of two cannot rule out incorrect field content or mapping.

The psql reference for \copy places file access on the client. It does not copy the file into a permanent directory on the database host. Data travels through the connection, while the server still performs table writes and constraint checks. A readable local file does not make every input row acceptable.

Can an application driver send the backslash command?

Do not send psql's \copy as server SQL. psql interprets that meta-command itself. An application should use its driver's supported COPY input API to feed a COPY FROM STDIN operation, or parameterized INSERT when appropriate for the workload. Method names, cancellation and transaction integration depend on the chosen driver version; no universal driver API is assumed here.

A streaming upload also occupies a database connection. On cancellation or failure, finish the COPY operation and transaction according to the driver's contract before returning the connection. Closing an upload page does not prove that database work ended. Staging data for validation or accepting only some records may be useful, but those are import semantics, not automatic consequences of fixing a path.

Separate path, permission and format failures

A missing client file calls for checking its local path, working directory and retention period. A server-side file error should first prompt checking whether server file COPY was selected by mistake. Permission diagnosis must distinguish client operating-system access, server operating-system access and table privileges. A format error calls for checking encoding, delimiters, quoting, column order and types. Presenting all of these as “increase permissions” encourages unrelated configuration changes.

HEADER true should not be treated as an assumed column-mapping guarantee. The example fixes input order with an explicit column list. Review that list when the table or CSV changes. Where omitted columns rely on defaults, check the actual table's defaults and constraints rather than borrowing assumptions from another table.

Whether a failed import can preserve part of its data depends on the transaction boundary and product contract. The existing article on savepoints and partial-import reporting explains accepted and rejected outcomes. Repairing a file path does not authorize changing an all-or-nothing import into partial success.

Does successful COPY mean the business import is complete?

Check commit, the expected set of records and subsequent reads. If COPY runs inside an explicit transaction that later rolls back, its success was not durable import completion. Additional relationship checks may also determine whether the backend can accept the import. Row counts establish quantity, not correct names, external identifiers or ownership.

Before importing, record a small file manifest: digest, encoding, column order, expected identifiers and source. Matching digests help establish that both sides are discussing the same bytes, not that those bytes are trustworthy. Authorization and business validation remain separate. If an operator resaves the CSV, create a new manifest rather than retaining expectations for an older file.

For an all-or-nothing exercise, copy and inspect within an explicit test transaction, then choose commit or rollback and verify visibility from another read-only connection. Resolve an error transaction before starting another case. Two observed rows would cover that file and path, not large-file transport, driver reconnection or production mapping.

A proposed validation matrix should include a client-readable file absent from the server, denied client reads, duplicate primary keys, quoted delimiters and newlines, incorrect encoding and cancellation. Inspect both final table state and connection state. These checks were not run. A useful repair receipt identifies which process read which file and which columns entered the table through which commit, rather than merely recording that the command stopped failing.
