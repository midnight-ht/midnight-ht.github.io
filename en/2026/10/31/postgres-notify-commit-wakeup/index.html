NOTIFY can wake a worker without storing its unfinished work

Separate NOTIFY transaction boundaries, duplicate folding and listener setup from the durable state needed for worker recovery.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-31 · Estimated read 15 min
Translations

Article

Key takeaways

  • Sender commit and the listener transaction both affect notification delivery.
  • Repeated discovery does not authorize repeated side effects.
  • Recovery reads persistent work state; a signal only wakes the worker.

NOTIFY is useful for telling a worker that something changed and should be queried. It is not, on its own, a recoverable list of unfinished jobs. Notifications wait for the sending transaction to commit, and a listening session's own transaction can delay delivery to its client. Store unfinished work durably when it must survive a disconnect, and use notifications to wake the worker.

Why can the statement succeed before the notification arrives?

PostgreSQL 18's NOTIFY reference describes transaction boundaries on both sides. A sender's notification takes effect after a successful commit. A listening session that is inside a transaction does not deliver the notification to its connected client until that transaction ends. This article checked the version 18 documentation on October 31, 2026; no database or notification driver was run.

Draw two timelines. A sender can execute INSERT and NOTIFY without committing, in which case the receiver's wait is expected. If that transaction rolls back, its notification should not appear. Alternatively, the sender may already have committed while the listening session is holding a transaction open. Looking only at sender logs can misdiagnose the second case as a network problem.

Putting the data change and the notification in one transaction prevents this particular signal from surviving a rollback. It does not establish consumer acknowledgement. A notification reaching a connection does not show that the worker processed the row, let alone sent an email or completed a third-party request. Receipt, work claiming and business completion need separate evidence.

Use two sessions to separate the boundaries

The following is an unexecuted teaching procedure for two psql sessions connected to the same isolated database. Keep each terminal's session open. The table and values are illustrative; do not create them in a business database without an appropriate test setup. In session A, create the table and commit the listener registration:

CREATE TABLE demo_work (
  id integer PRIMARY KEY,
  state text NOT NULL DEFAULT 'pending'
);
BEGIN;
LISTEN demo_work_changed;
COMMIT;

In session B, run the transaction but pause before its final line:

BEGIN;
INSERT INTO demo_work(id) VALUES (1);
NOTIFY demo_work_changed, '1';
-- Inspect session A before running this line separately.
COMMIT;

In session A, issue a query, giving psql an opportunity to read and display asynchronous notifications while checking the committed state:

SELECT id, state FROM demo_work ORDER BY id;

The documented expectation is about ordering: the notification cannot be treated as delivered before commit; after commit, A can query the committed row. The moment a terminal prints a notification also depends on when its client reads the connection. A line appearing at a particular second is not a measured database latency. Repeat with a new identifier and ROLLBACK instead of COMMIT to check that neither the row nor its notification becomes part of that committed change.

Next, begin a transaction in A and leave it open. Commit a fresh row from B, then inspect delivery before and after A ends its transaction. This tests the receiving boundary. Repeatedly issuing NOTIFY from B would obscure that distinction. After the experiment, UNLISTEN in A and remove the teaching table only after checking its ownership.

Notification counts are not work counts

Repeated notifications with the same channel and payload within one transaction can be folded together. If a transaction changes three rows and sends changed each time, receiving fewer than three notifications is not evidence of missing rows. Distinct payloads avoid that particular folding rule but do not provide offline recovery or consumer completion acknowledgements.

Keep job identities and unfinished state in the work table. A wake-up should trigger a query of that state rather than incrementing a counter derived from signal delivery. Multiple workers still need a claiming policy, retries and idempotency. NOTIFY does not choose their locking protocol or include external side effects in the database transaction. The existing discussion of transactional outbox handoffs covers persistent intent and external delivery; the additional question here is when the database's wake-up signal becomes visible.

An online interface refresh can reasonably use notifications alone if missing one is acceptable and a later refresh can retrieve current state. A disposable hint need not justify a complex queue. Conversely, low latency does not make a hint suitable for work whose individual completion must be tracked.

Should the worker register first or query first?

Commit LISTEN first, read the initial state next, then use notifications to trigger subsequent reads. The LISTEN reference's notes explain the initial registration race. The point at which registration takes effect does not coincide exactly with the state observable by a query. Querying before registration leaves a gap in which a change can be missed.

The recommended order can still produce an initial notification for a change already covered by the initial read. Work identity and state checks must tolerate rediscovery. Seeing a row twice is not permission to perform its side effect twice: claiming or idempotency belongs at the processing boundary. Reconnect by registering and rereading persistent state, rather than recovering from memory associated with the lost connection.

Can the payload carry the entire user record?

Treating the signal as a private payload is a poor default. NOTIFY documents visibility to database users and a byte limit for the payload in its default configuration. A more reviewable design sends a controlled identifier and lets the worker fetch necessary data under its own permissions. The identifier itself may reveal information; removing a person's name does not by itself establish anonymization.

A recovery test can avoid timing assumptions: pause the worker, commit work, disconnect its listener, and reconnect. Have the worker rediscover pending rows from the table and inspect final state and external effect counts. This tests the recovery design without requiring a notification to arrive within an invented latency limit. A client that has not received its signal must still be able to recover from persistent state.

Also stop a worker after processing but before recording completion. Its successor may rediscover the same item. Preserve the business identity and distinguish rediscovery from repeated execution rather than assigning a new identifier to hide the gap. A single external effect requires appropriate receiver idempotency, outcome queries or compensation; one notification is not evidence of that guarantee.

A proposed validation should distinguish sender commit, receiver transaction end, client receipt, work claiming and final outcome. Include reconnection, repeated signals and recovery when no signal is received. These tests were not run, and no delivery rate is reported. A useful review question is: if the worker receives no notification at all, how will it discover after restart which item remains unfinished? An in-memory notification list cannot answer that recovery requirement.
