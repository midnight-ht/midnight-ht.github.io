RUN has no network. Why can remote ADD still fetch?

Separate RUN networking from input acquisition with a complete Dockerfile, explain cache effects, and choose the scope of offline validation.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-31 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • RUN settings do not cover every builder acquisition path.
  • A warm cache does not remove remote dependencies.
  • Offline validation must declare prepared inputs and control scope.

RUN with network none constrains that instruction's execution environment. It does not establish that the entire image build performs no external fetches. Base-image resolution, remote ADD sources, and other build inputs can be acquired outside that RUN instruction. Locate the fetching stage before deciding that the network setting failed.

Executing a command and acquiring its inputs are separate

The Dockerfile reference sections for RUN networking and ADD describe different responsibilities. The none mode removes network access for the RUN command while retaining an isolated loopback interface. ADD can acquire a remote URL. This article checked the online reference on October 31, 2026 and concerns BuildKit builds supporting the illustrated syntax, not a host-wide network switch.

A Dockerfile describes more than shell commands. A builder needs the definition, base image, context, and any remote material before commands can consume those files. The actor making a request determines the relevant control. Attributing every request to RUN can make a working local restriction look broken while obscuring a separate acquisition path.

Restricting a command remains useful. An installation step with prepared dependencies can avoid opportunistic network downloads. However, downloading those dependencies in an earlier instruction still makes the download part of the build. Define whether the requirement is an offline installation step or a builder with no outbound network access.

A complete definition that exposes the distinction

This example has not been executed. Create a Dockerfile containing the following in a disposable directory. It requires a Docker installation with BuildKit support and a builder able to obtain the selected image and public document. It is not a production supply-chain design: the image uses a tag and the remote content is not pinned by digest.

# syntax=docker/dockerfile:1
FROM busybox:1.37
ADD https://www.rfc-editor.org/rfc/rfc9110.txt /material/rfc9110.txt
RUN --network=none test -s /material/rfc9110.txt

A proposed build from that directory is:

docker buildx build --no-cache --progress=plain --load -t network-scope-demo .

ADD fetches a public text. RUN checks only that the resulting file is nonempty. Even without networking in the last instruction, the builder needs the remote material first; obtaining or resolving the base image may also require access. The nonempty check does not validate publisher identity, content version, or business correctness. Its narrow purpose is to separate file availability from command networking.

A successful run on one machine would still need build logs and knowledge of existing cache state to explain what was fetched. A failure while acquiring the base image does not prove that the subsequent RUN executed. Preserve the failing stage rather than translating every build error into evidence that networking was successfully blocked.

Why does caching obscure the dependency?

No new download during a cache hit does not mean that the build definition lacks remote inputs. A prepared builder today and a clean builder tomorrow can behave differently. A successful warm-cache run supports a result for that environment, not automatic portability to an offline recovery environment.

Disabling build-step cache does not justify assuming that every base image, frontend, or piece of builder state is absent. An offline test must state what is allowed to be preinstalled. A build with prepared images and a build that must obtain every input from scratch are different experiments.

The article on allowing files into a build context addresses local input scope. Remote acquisition adds another responsibility: even a context containing only a clean Dockerfile can declare external dependencies. The absence of local dependency files does not prove the absence of external inputs.

Which offline boundary do you need?

To prevent an installation script from downloading undeclared dependencies, prepare the required packages through a controlled process and restrict the consuming RUN. Check that required materials are complete, missing inputs fail explicitly, and alternative download paths are understood. The preparation process still needs provenance checks.

To prevent external access throughout a build, inventory base images, syntax frontends, remote contexts, ADD sources, and other inputs. Verify a policy that actually covers the builder. A restriction within one command environment cannot certify the behavior of a remote build service.

A proposed validation starts with an allowed baseline that proves the inputs and definition are usable. Then inspect the restricted path under stated input conditions, recording the request actor, destination, and failing stage. An unavailable URL, certificate error, or nonexistent image can otherwise imitate a network-control failure. No build or network capture was performed for this article.

Fix input identities before comparing runs

A useful comparison records the same Dockerfile, source, and intended content identity on a prepared builder and a separately controlled builder with missing inputs. List executed stages, reused results, and the actor performing each acquisition. A faster second run does not distinguish caching from network or remote-load effects.

A mutable remote source can change between runs, introducing a second variable. When fixed inputs are required, establish content identity through supported digests or a controlled archive before comparing network policy. The public-text illustration does not establish that identity and therefore proves no reproducibility result.

Observation scope matters too. No outbound requests from the local client do not establish the same result for a remote builder. A RUN log may omit the builder's acquisitions. State which process or service the observation covers and leave unobserved paths unknown.

Does a cache hit with no requests prove isolation?

No. Identify the preinstalled inputs and the stages that actually ran before interpreting request absence. Test the installation step if that is the requirement. Include the builder's acquisition paths if the requirement covers the whole build. Match the conclusion to the scope of the control.
