Keep async generator cleanup inside the consuming task

Check aclosing with early break and consumer failure, keeping ownership, asynchronous cleanup and cancellation deadlines distinct.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-31 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • Ending async iteration does not establish completed generator closure.
  • aclosing awaits aclose as the owning scope exits.
  • Borrowing rights and cleanup duration require separate contracts.

An owner that stops consuming an async generator early should explicitly await its closure. A break is not evidence that cleanup has completed. contextlib.aclosing awaits the object's aclose when its async with block exits, keeping asynchronous generator cleanup in the context used for iteration. It assigns closure responsibility without promising remote rollback or a hard cleanup deadline.

Ending consumption does not close the producer

The contextlib documentation for aclosing specifically addresses deterministic async-generator cleanup after break or exceptions. It also explains that exit code executes in the iteration context. aclosing was added in Python 3.10; the page checked on October 31, 2026 was Python 3.14.10. No asynchronous program was run.

An async generator can yield repeatedly and suspend between items. Its finally block may need to await resource release. A consumer that leaves after one item has stopped requesting values; that alone does not establish that the suspended producer finished its exit logic. A resource-owning scope must express that lifetime.

This does not mean every break leaks forever. Reference retention, garbage collection and event-loop shutdown influence eventual cleanup. The relevant contract is whether cleanup completes before the current scope ends. A finalizer that depends on request context or task-owned resources should not be left until those dependencies have expired.

Conversely, fully consumed generators can reach their own normal exit, and a borrower must not close a shared source managed elsewhere. Use aclosing where the current scope actually owns closure, not mechanically wherever async for appears.

Await closure within the owning scope

This complete, unexecuted standard-library example records control flow in lists. It uses no real database or network. The sleep in finally makes cleanup asynchronous; it is not a measurement of resource-return time.

import asyncio
from contextlib import aclosing


async def values(events):
    try:
        yield 1
        yield 2
    finally:
        await asyncio.sleep(0)
        events.append('closed')


async def consume_one():
    events = []
    async with aclosing(values(events)) as source:
        async for item in source:
            events.append(f'read:{item}')
            break
        events.append('loop ended')
    if events != ['read:1', 'loop ended', 'closed']:
        raise RuntimeError(f'unexpected cleanup order: {events!r}')
    print(events)


async def consume_with_error():
    events = []
    try:
        async with aclosing(values(events)) as source:
            async for item in source:
                events.append(f'read:{item}')
                raise ValueError('consumer rejected item')
    except ValueError:
        if events != ['read:1', 'closed']:
            raise RuntimeError(f'cleanup missing: {events!r}')
        print('consumer error preserved', events)
    else:
        raise RuntimeError('consumer error disappeared')


async def main():
    await consume_one()
    await consume_with_error()


if __name__ == '__main__':
    asyncio.run(main())

The first case records loop ended before leaving async with; closure is awaited on scope exit. The check outside the scope verifies closure before returning, rather than merely noticing that finally printed something eventually. The second case expects cleanup while preserving the consumer's ValueError instead of turning it into success.

These are expectations derived from code and documentation, not captured logs. Replacing the teaching generator with a real resource requires checking that resource's aclose contract. It may release a local handle without proving that a remote operation was reversed. The list marker tests control flow, not real connection return.

What should a comparison without aclosing observe?

Remove the owning context, retain the generator reference, break early, inspect events immediately, then explicitly await source.aclose and inspect again. Retaining the reference keeps the comparison focused on closure rather than incidental garbage collection. Do not claim that every platform must produce an identical delayed output sequence.

Resource acquisition, completed closure and consumer error propagation are separate assertions. A finally reached on normal completion does not prove failure cleanup. Catching ValueError does not establish resource release either. The example checks both on one path; a real test should also inject a failing closer and inspect the resulting exception chain and diagnostics.

The existing article on the single-yield contextmanager protocol concerns synchronous entry and exit for one resource loan. This async data generator can produce several values. aclosing ends it when its owner leaves; the contextmanager's single-yield requirement does not apply to the data producer.

Should a borrowed async iterator always be closed?

Check that it provides aclose and establish who owns it. Async iteration does not guarantee a uniform closing API. An internal helper must not terminate a shared subscription or a generator the caller intends to reuse. An interface should state whether it takes ownership and closes, or only borrows.

Suppose a parser examines two items and passes the iterator to the next stage. Wrapping that helper in aclosing could hand the next stage an already closed source. Closing is suitable if the remainder is deliberately discarded; continued consumption requires moving ownership to the scope spanning both stages. Earlier cleanup is not automatically more correct.

For request-owned resources, an entry point can create the source, consume it, await closure and pass ordinary extracted data to helpers. Long-running background consumption instead needs an explicit task identity and lifecycle. Returning a generator does not create its future owner. That is an application design choice, not task management supplied by aclosing.

Does aclosing make cleanup immediate?

It awaits closure without bounding the closer's duration. A blocked, failing or interrupted cleanup still needs an observable outcome. The article on wait_for and cancellation settlement distinguishes a waiting budget from completed cleanup. Adding another timeout around aclose does not prove that the resource was released.

A borrowing test can let a helper consume one item and have its outer owner continue with the next. Continued use should remain possible under a borrowing contract; a take-and-discard contract should not promise it. This tests the interface rather than merely counting aclose calls. Correct call counts at the wrong ownership boundary can still break the next stage.

Separate cleanup start from completion as well. Hold finally on a test event, check that the owning scope has not exited, then release the event and observe completion. This establishes waiting without a fragile millisecond expectation. If closure raises, verify that the caller sees failure rather than taking a started-cleanup marker as success.

Proposed tests include full consumption, early break, consumer failure, closer failure, cancellation and shared borrowing. Inspect completion markers, errors, resource counts and intended subsequent use. None was executed. Find the actual owner first, then have it await closure within its valid scope. If ownership must outlive that scope, explicitly hand off the remaining responsibility rather than relying on event-loop shutdown.
