Why Does Array.flat Remove Slots but Keep undefined?

Distinguish missing properties from undefined values, then preserve row coordinates before flattening an import.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-24 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • A hole and a present undefined property are different states.
  • Depth zero still skips missing root indexes.
  • Carry source coordinates instead of reusing result indexes as identity.

Array.prototype.flat does not preserve a hole as an explicit undefined element. It checks whether an indexed property exists before reading it and skips a missing property, potentially shifting later positions. The default depth descends one array level; deeper arrays not visited retain their internal structure. If input indexes identify spreadsheet rows or business records, retain their source coordinates before flattening instead of treating new indexes as old identities.

Similar reads can conceal different properties

For an ordinary array without relevant inherited indexed properties, a hole means no property exists at that position. An explicit undefined element has a property whose value is undefined. Reading either can return undefined, hiding the distinction. The ECMAScript flat and FlattenIntoArray algorithms perform HasProperty before reading and copying. Skipping a missing slot happens before its value is obtained.

Imagine an importer whose array positions correspond to worksheet rows. One source row is blank; another is an explicit record awaiting more information. Representing the former as a hole and the latter as an undefined-valued property does not preserve both as equivalent placeholders through flat. The language behavior does not decide whether a blank business row should be removed. That choice belongs to the import contract.

This unexecuted teaching example includes a root hole, a nested hole, and explicit undefined. The comments describe expectations derived from the specification, not captured terminal output.

const rows = ['A', , undefined, ['B', , 'C'], [['D', , 'E']]];
const one = rows.flat();
const zero = rows.flat(0);
// Proposed: one starts A, undefined, B, C, then retains ['D', <hole>, 'E'].
// Proposed: zero skips the root hole but does not flatten nested arrays.

Default depth one visits the root and one descended array level, skipping missing properties encountered there. The deeper array is copied as an array value without another descent, so its internal hole is not scanned away. Describing flat as removing every empty item overstates the mechanism. Explicit undefined remains, and holes inside unvisited arrays can remain too. Cleaning business-level empty values requires a different policy.

Depth zero is still not a hole-preserving copy

Flat(0) prevents recursive flattening but still performs the root-level property-existence check. Root holes can disappear. A requirement to preserve exact positions therefore cannot use depth zero as a generic unchanged-content copy. First specify whether the copy must preserve readable values, property existence, length, or nested object identity. Those requirements are not interchangeable.

Consider an importer that adds one to a result index and reports it as the original worksheet row number. Once an earlier hole disappears, a later validation error can be attached to the wrong row. A changed length is evidence worth investigating, but even matching lengths would not establish correct ownership: another transformation could filter, reorder, or insert records elsewhere.

A clearer design constructs records with source coordinates while reading the input: file identity, worksheet name, original row number, and parsing outcome. If blank rows need a diagnostic state, create an explicit record instead of using a hole to mean pending work. After flattening, write errors back through stable coordinates. The precise fields depend on the importer's input scope; this is a design recommendation rather than an API requirement.

For multiple batches, retain the batch identity as well as the within-batch row. Two worksheets can both contain row five. Losing the outer grouping while preserving only a local row number leaves an ambiguous reference. Flattening is often chosen specifically to remove grouping, so source ownership should be designed before that information disappears from the structure.

Test existence separately from values

A proposed test checks length, indexed property existence, and element values independently. Merely asserting that a read returns undefined cannot distinguish a hole from a present undefined value. Use an appropriate own-property check for that distinction and independently assert the resulting order. Do not generate expectations by invoking flat again, because that would duplicate the operation under test rather than validate the requirement.

Treat depth as a separate input: prepare expectations for zero, one, and a specifically deeper level. Infinite depth may suit a known, safely traversable structure, but it is not a universal cleanup switch. Cycles, extremely deep nesting, throwing accessors, and custom behavior require additional limits. The ordinary-array example supplies neither performance results nor a termination guarantee for arbitrary inputs.

The specification uses HasProperty rather than an own-property-only check. An indexed property on the prototype can therefore affect what the operation reads. The simple explanation of holes above explicitly excludes those inherited indexes. If data arrives through modified prototypes or proxies, establish its actual shape before applying the ordinary-array reasoning. A boundary should not silently depend on global prototypes never being changed.

Are object elements independently editable afterward?

A new outer result does not recursively clone business objects. If two original positions refer to the same record, the flattened result can retain that shared record. Mutating it through one position can be visible through another. An unflattened nested array also retains identity considerations. The article on fill and repeated object references explains how such sharing begins. Flattening levels and removing holes do not eliminate it.

A focused acceptance exercise can mutate an object after flattening, examine the intended source/result relationship, and check that an error carrying source coordinates returns to the right input position. If independent editable copies are required, choose copying depth according to the fields that may actually change. Flat depth controls array descent; it is not object-copy depth.

Prepare two worksheets, A and B, each containing a validation record on row five, with an earlier hole in A. The converted records may become adjacent, but their errors must retain A-row-five and B-row-five identities. Make only B fail and verify that A is not marked. This checks duplicate local row numbers and an earlier missing slot together rather than merely checking that output lost an element.

If blank rows must remain, have parsing create explicit blank-row records containing coordinates and a blank status. Check that conversion preserves them and distinguishes them from valid records containing undefined fields. Total input row count is a useful coverage check but cannot replace coordinate uniqueness and per-row status: equal totals can conceal one duplicated record and one missing record.

This article inspected the living ECMAScript specification on October 24, 2026, without executing JavaScript or importing a real worksheet. Define holes, explicit empty values, and business row identity separately before adopting flat. Otherwise a compact conversion leaves later validation with a list whose source positions can no longer be recovered reliably.
