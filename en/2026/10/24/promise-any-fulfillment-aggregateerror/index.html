Does Promise.any Select a Fulfilled Value or a Valid Result?

Validate each candidate before fulfillment and define aggregate failure, input identity, deadlines, and remaining work.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-24 · Estimated read 16 min
Translations
zh-CN en

Article

Key takeaways

  • First fulfillment does not establish business validity.
  • Aggregate rejection reasons follow input positions.
  • Deadlines, cancellation, and late results need separate ownership.

Promise.any chooses the first candidate to fulfill. It neither chooses the first candidate to settle nor understands business-level validity. If ordinary candidate promises all reject, it rejects with an AggregateError containing their reasons. When a candidate can fulfill with unusable data, validate inside that candidate's promise and reject invalid data before handing the candidates to any. Otherwise the fastest error-shaped value can become the winner.

One rejection leaves other candidates in contention

The ECMAScript Promise.any specification distinguishes first fulfillment from universal rejection. Imagine retrieving the same read-only catalog from three mirrors. A rejects first, B is still reading, and C later fulfills. C can supply the result if it is the first fulfillment. A finishing earlier does not independently fail the aggregate. Choosing the first settled outcome through race answers a different requirement.

However, fulfillment is not evidence that a catalog is acceptable. Suppose a reading client returns an expired catalog as a normal value. Any does not inspect its version, fields, or signature. It faithfully selects the value while the application mistakenly equates early arrival with current, usable data. Define whether each candidate promises a raw response or an already validated business object before choosing the aggregation method.

This unexecuted structural example leaves readCatalog and validateCatalog for the project to implement. It implies no particular HTTP client's treatment of response status. The validator must throw for unacceptable data so only qualified candidates fulfill.

const mirrors = ['mirror-a', 'mirror-b', 'mirror-c'];
const candidates = mirrors.map(async (mirror) => {
  const raw = await readCatalog(mirror);
  validateCatalog(raw);
  return { mirror, catalog: raw };
});
try {
  const selected = await Promise.any(candidates);
  consumeCatalog(selected);
} catch (error) {
  handleCatalogFailure(error);
}

Returning mirror identity with the catalog makes the chosen source explainable. The consumer and failure handler also need their own exception contracts; this sketch is not a complete client. A validator that merely returns false, with the caller ignoring that return, does not reject the candidate. The code acquires the appearance of validation while its selection condition remains unchanged.

A useful implementation review also distinguishes decoding from validation. Successfully parsing data into an object does not establish the required catalog version or required fields. Put every condition necessary for eligibility before fulfillment. Keep later optional enrichment separate if its failure should not invalidate an otherwise usable catalog.

Aggregate reasons follow input identity, not arrival order

PerformPromiseAny retains an index for each input and stores a rejection reason at that position. Suppose B fails first, C second, and A last. The errors collection still associates reasons in A-B-C input order rather than failure arrival order. A diagnostic routine that separately attaches source names in arrival order can attribute a timeout to the wrong mirror.

A reviewable failure record retains stable source identities before starting the candidates and explicitly relates input positions to reasons. Internal diagnostics and user messages should be separate. Errors can contain addresses, parameters, or stack details inappropriate for public output. Recording which sources were unavailable and explaining that no acceptable catalog is available are different communication tasks.

Empty input deserves an explicit policy. For ordinary use, any with no candidates returns a rejected promise with an AggregateError containing no candidate reasons. It does not succeed merely because no request failed. An empty mirror configuration should produce a configuration-oriented explanation rather than a claim that every network request timed out. No requests and several failed requests are different faults.

The ordinary-input qualification matters. This article does not promise that every error from every arbitrary iterable or customized Promise constructor is an AggregateError. Failures while obtaining or processing an input iterator can follow other rejection paths. A boundary that accepts only a validated array of ordinary promises can keep its own assumptions much clearer than accepting arbitrary producer behavior.

Selecting a result does not stop other work

Any defines no protocol for canceling the underlying tasks. After one mirror fulfills, other reads can keep using connections and parsing budget. Cancellation requires a separate client or task contract, and stopping local waiting does not prove remote work was undone. The discussion of Promise.all and cancellation separates aggregate outcomes from task lifetimes. First-success selection has the same lifecycle boundary.

This is also why substituting redundant writes for redundant reads is dangerous. If three candidates each create an order, the first fulfillment ends the caller's selection without making the other writes disappear. Side-effecting operations need idempotency, terminal-state queries, and recovery policies before an aggregate can represent their business result. Choosing one success cannot erase the other outcomes.

What if two candidates reject and one remains pending forever?

Any alone cannot conclude that all rejected, because the remaining candidate has not rejected and no fulfillment has occurred. Define a deadline for each candidate or the overall selection. Then decide whether expiration makes that candidate ineligible or ends the entire attempt. A timeout should not be translated into proof that a remote service never executed; it means no qualifying result was obtained within the selected contract.

Proposed verification can control promises rather than rely on network speed. Reject A, fulfill C, and confirm C can be selected while B remains unfinished. In another run reject all in reverse arrival order and inspect reason-to-source mapping. Add empty input, invalid fulfilled data, and permanent waiting as separate cases. Catching one aggregate error does not prove every underlying task has stopped.

The AggregateError statement covers normal settlement of candidate promises, not every failure of arbitrary iterables or customized constructors. An iterator that throws introduces a different input failure path. An API limited to a validated ordinary array can state that assumption explicitly, while a generic catch should still preserve unclassified exceptions instead of assuming an errors list always exists.

Keep stable source identities on validation failures too. A can return an expired catalog, B a structurally invalid one, and C nothing before the deadline. None is eligible, but their repair paths differ. Preserve version, shape, and timeout distinctions internally without exposing all diagnostics. The component ending overall waiting must also control late results so an old attempt cannot overwrite a newer selection. Checking the attempt identity before publishing to the interface or cache is business lifecycle control, not an implicit service of any.

This article inspected the living ECMAScript specification on October 24, 2026, without requesting mirrors, executing code, or measuring latency. Before adopting any, explain when each candidate is eligible to fulfill, when waiting ends, and who owns the remaining candidates' final states. Correctly selecting the first result is only part of a redundant-read contract.
