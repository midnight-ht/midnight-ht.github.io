Does a visible outline rescue a button hidden by a sticky footer?

Assess the focused component and its indicator separately, including dynamic footers, user-opened panels, and keyboard tasks.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-24 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • Assess the component separately from its external focus outline.
  • Dynamic footers and nested scrolling can invalidate a repair.
  • Minimum obstruction checks do not replace focus or contrast checks.

When a sticky footer covers keyboard focus, inspect the focused component itself before inspecting its focus indicator. A fragment of an outline outside the footer does not make a completely hidden button visible. WCAG 2.2 Focus Not Obscured (Minimum) sets a minimum visibility condition for the component. A useful product acceptance decision should also let people recognize what they are about to operate.

Why can a button remain hidden after the browser scrolls?

W3C's explanation of SC 2.4.11 says a component receiving keyboard focus must not be entirely hidden by author-created content. This AA criterion permits partial obstruction and assesses the component rather than an external focus outline. Record component visibility and focus-indicator visibility separately instead of merging them into one “focus works” result.

Fixed navigation, sticky checkout controls, and non-modal notifications can cover content. Scrolling a target into the viewport does not establish that it has cleared the page's own overlay. Treat the viewport as an area with occupied regions: a target can be inside the window and behind a toolbar at the same time. A coordinate check against viewport bounds misses that relationship.

A stronger outline alone does not repair obstruction. It might reveal that a control exists while leaving its name unreadable. Raising the button above a notification may create a different layering error. First establish which element occupies space, which container scrolls, and which task the user should perform next. Then choose spacing, layout changes, or a different interaction.

Follow one order through the last field

Imagine an order editor with a fixed “Save order” bar and an “Add delivery note” button near the end of its content. This is a hypothetical design, not an executed test. A keyboard user tabs from address fields to the note button, which receives focus entirely behind the bar. The page still accepts input, but the user cannot establish what Enter will activate. The failure concerns finding the current action target.

One candidate repair reserves space in the actual scrolling container and provides suitable scroll padding so the target can enter the unobstructed region. The reserved height should follow the real footer, rather than a desktop mockup's measurement. Enlarged text, error messages, and wrapping buttons can increase its height and invalidate a previously sufficient gap.

Continue the hypothetical task: focus the note button, expand the editor, enter a note, and move to Save. The repair must survive expansion, error-driven field focus, and reverse navigation. If an inner panel scrolls, padding on the document root may do nothing. Locate the container that actually moves before deciding where the spacing belongs.

Another option gives the footer space in normal layout. That changes presentation and available area, so the small-viewport task needs another review. A notification requiring an immediate decision may warrant a properly implemented modal interaction. Turning an optional promotional banner into a mandatory modal simply to escape an obstruction check is a poor task decision.

Is a visible corner a good acceptance target?

Minimum conformance and a recognizable target are different judgments. Partial visibility and total obstruction have different outcomes under this criterion. A tiny, unrecognizable fragment may still present a product problem. Prefer showing the whole component and a clear focused state where practical; that recommendation is not an additional verbatim requirement of the AA criterion.

A translucent overlay is a useful counterexample. It may leave a component partially discernible while making its focused state difficult to distinguish. Passing an obstruction check does not settle focus visibility or non-text contrast. Conversely, covering an external outline alone does not automatically establish failure of this particular criterion. Identify the object being assessed.

What if the user opened the obstructing panel?

Establish whether the user can reveal the focused component without advancing keyboard focus. The Understanding document discusses this situation; “the user opened it” alone is insufficient. Blindly tabbing onward to escape the covered region does not demonstrate the specified recovery condition. For user-movable interface content, assess the initial positions as required, rather than substituting an arbitrary arrangement the user created later.

Suppose a user opens a help panel while focus remains in a field behind it. Document how the panel can be dismissed, whether the original focus is retained, and whether typing can resume once the field is visible. If dismissal changes focus, do not automatically apply the explanation about revealing a component without advancing focus. Judge the actual interaction before assigning an exception.

Keep evidence that explains the outcome

Record observation timing too. Focus may trigger scrolling before asynchronous validation inserts another message and shifts the target behind the overlay again. A screenshot after the first scroll can miss the second layout change. Recheck once the state settles and retain the sequence of layout-changing events. If messages keep moving the page, address the unstable interface rather than repeatedly forcing scroll position.

A proposed check traverses the complete task forward and backward, recording the focused element, overlay, scrolling container, and viewport. Pair screenshots with the focused element's identity so hover is not mistaken for focus. Repeat the relevant steps with an expanded footer, added errors, a narrow viewport, and enlarged text. Distinguish hidden, partially visible, and fully visible outcomes.

These checks have not been run against a target application. Automated geometry checks can help locate candidates, while actual browser and assistive-technology combinations still need task validation. The site's modal focus lifecycle discussion addresses another part of navigation. Here, start with the button most likely to disappear behind the footer and preserve evidence of entering it, expanding its content, and returning.
