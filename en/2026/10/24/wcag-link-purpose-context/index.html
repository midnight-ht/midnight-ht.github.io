Which context actually explains repeated View details links?

Distinguish programmatic context from visual proximity through names, destinations, and selecting an application.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-24 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • Link text may work with qualifying programmatic context.
  • A visual card border does not establish the relationship.
  • Names and destinations should fulfill the same action promise.

Repeated “View details” links are not automatically failures, but each link must let users understand where it will take them. WCAG 2.2 permits link text to work with programmatically determined context. A nearby picture or heading does not automatically establish that relationship. Review actual names and structure instead of counting occurrences of “details”.

A visible card does not always explain its link

W3C's explanation of SC 2.4.4 permits purpose to be determined from a link alone or with programmatically determined context. Its sentence, paragraph, list item, table cell, or associated table headers can provide relevant context. Users should be able to decide whether to follow a link before opening every destination to discover its meaning.

People may read sequentially, move between links, or use an assistive technology's link list. Meaningful link text often reduces dependence on surrounding material. That useful preference must not be misreported as this criterion requiring every link to stand alone. Different conformance criteria have different scopes.

Visual cards can imply relationships their structure does not preserve. A heading and link might be close on screen but live in separate containers, or become separated after mobile reflow. If color, a photograph, or “the card above” provides the only clue, improve the wording and structure. Finding the link element does not prove that software can recover the intended relationship.

Make three applications distinguishable

Imagine an application center listing a repair request, an equipment loan, and a room booking, each ending in “View details”. This is an unexecuted hypothetical case. A user checking whether the room booking was approved encounters three identical entries during link navigation. Working destinations do not solve the choice before activation.

One option names the object directly: “View room booking”. If several bookings exist, add useful identifying information such as a room, date, or part of a reference. The accessible name need not contain the entire database object. Internal identifiers meaningful only to engineers do not necessarily help readers choose.

Another option retains a short link while providing the object in suitable contextual structure. Inspect the rendered relationship rather than a border drawn in a mockup. If additional accessible naming is used, keep it compatible with visible text. Someone using voice input should not have to guess an unrelated name for the visible “View details” control.

Continue the task: the user opens the room application, sees matching status and date information, then returns and can identify the same record. If one otherwise similar link downloads a PDF, its behavior may need clearer wording. Indicate file type or behavior when it affects the choice; that is a design recommendation, not a claim that this criterion requires one fixed file label everywhere.

More surrounding text can still leave the purpose ambiguous

Context should support a decision, rather than require reconstruction. A paragraph might mention two agreements and end with one “Download” link. Sharing a paragraph does not establish which agreement it downloads. Linking each document's actual name can make the purpose clearer than adding more general explanatory prose.

A different counterexample gives three links labels promising cancellation, editing, and viewing, while all lead to an application homepage. The common URL is not automatically wrong, but the promised action may still be misleading if users must search again. Review the destination as well as the name so wording improvements do not conceal incorrect routing.

Must every link work without context?

This criterion permits qualifying context. A list containing only unique standalone names is therefore not the sole acceptance test. Independent names remain a strong candidate for notifications, search results, and record lists. Within a sentence, mechanically turning the entire sentence into a link may create unnecessarily long announcements.

For example, a sentence referring to “October's deployment report” may use “deployment report” as the link while the month remains in the same sentence. Assess the actual structure and assistive-technology workflow. This example explains a choice; it certifies no component and promises no universal repair from a single attribute.

The exception for purpose ambiguous to users in general should not absorb wording a service could readily clarify. A puzzle intentionally withholding information is different from an ordinary application list. If maintainers know the destination but make users guess at “More”, the problem usually lies in content design. Explain why ambiguity is intrinsic to the task before considering an exception.

Validate choosing the target, not just opening it

Data binding can break the promise too. A second card may display a South-region application while retaining the previous card's record identifier. Renaming it “View South application” would still promise the wrong destination. Choose adjacent records with different states and compare the opened object and visible information. Text extraction alone cannot find this defect; repeat the check after filtering and pagination.

A proposed review inventories the actual link name, associated text, URL, and destination title. Check whether these express the same promise. Then use keyboard navigation and the target screen reader's link navigation to find a specified application, noting where surrounding content must be consulted. A developer remembering that the third link is the booking is not evidence of discoverability.

These checks have not been performed. Recheck relationships after layout, language, and record data change. Like the site's discussion of form-field purpose, link design should explain the decision an entrance supports. Begin with the link users cannot distinguish in a real task, then decide whether its context is sufficient or its name needs the object directly.
