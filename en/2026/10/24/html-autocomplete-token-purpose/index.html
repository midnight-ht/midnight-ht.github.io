Why declare autocomplete purpose when the browser already fills a name?

Use two shipping addresses to distinguish input category, purpose, grouping, person roles, and verification.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-24 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • Input category and data purpose are separate declarations.
  • Section tokens separate data groups without identifying people.
  • Autofilled data still needs confirmation and server checks.

A browser successfully filling a name does not establish that the page declared its purpose accurately. type describes an input category; autocomplete can identify a name, billing address, or current password and distinguish multiple sets of data. Determine whom the field represents and what it is for before writing tokens. Marking every text field as name creates opportunities for incorrect filling.

Input category is not the complete purpose

W3C's explanation of Identify Input Purpose concerns supported fields collecting information about the user for listed purposes, rather than every free-text input. type="email" identifies an email input without, by itself, identifying whose email it is. Visible labels explain the question to people, while programmatically determined purpose supplies another cue to user agents and assistive approaches.

HTML's autofill rules define ordered tokens: an optional section- grouping, an optional shipping or billing qualifier, and an appropriate field name. They are not an unordered keyword collection. Correct attributes also do not guarantee filling on every visit in every browser; available suggestions depend on the environment and user data.

A submitted parameter name serves another role. A server parameter called recipientFullName might have the purpose shipping name. Renaming a database column should not redefine what a user agent understands. Labels, submitted parameters, and purposes need corresponding meanings, not necessarily identical strings.

Keep two gifts' addresses separate

Imagine checkout sending a blue gift and a red gift to different recipients, each with a name, street address, and postal code. This is an unexecuted design example. Repeating the same purposes without clear grouping makes it harder to establish the intended data relationship. A browser guessing correctly once is not evidence that the relationship is declared.

One candidate uses section-blue shipping name for the blue recipient and the same section with street-address and postal-code. The red gift uses section-red. Keep fields for one recipient in one group and separate the other recipient. Blue and red are opaque group identifiers, not instructions for the browser to understand gift colors.

Continue the task by selecting the blue address, independently entering the red address, then removing and re-adding the red gift. Check that identifiers still correspond to their objects. If component state relies on array positions, reordering can attach an old address to another gift. Token grouping and stable business-object relationships need to be designed together; attributes cannot repair state-management errors.

A payer's billing address requires the relevant billing purpose and an explicit choice if it should match a shipping address. Autofill is not confirmation. Changing a shipping address should not silently overwrite billing information. Provide visible feedback and an editable choice instead of a hidden synchronization state users cannot understand.

Avoid familiar tokens with the wrong meaning

Using name for a project name presents an object as a person's name. Using current-password for new account credentials confuses existing and newly created secrets. When no listed purpose fits, preserve an accurate visible question and input constraints instead of selecting a nearby-looking token merely to fill a checklist. An incorrect declaration can be harder to diagnose than an absent one.

Autofill is not identity verification. Stored addresses may be stale, a person may be filling for someone else, and values can be edited. The server still checks format and business validity. Email or phone ownership requires the corresponding verification process when the service needs it. Convenient entry and verified truth require different evidence.

Setting everything to off is not a reliable privacy policy either. First reduce unnecessary collection and explain use and retention. Separately verify the user agent's actual suggestion and storage behavior. One token does not establish identical behavior across browsers, password managers, and user configurations.

Does section-child identify a child's profile?

No such meaning comes from the suffix. HTML defines section-* values as opaque groups: user agents should not infer a child or spouse's address from those names. Grouping separates objects; it does not select people for the user. Explain the role in visible questions, group headings, and interaction, then let the user confirm the data.

This matters in booking services where applicant and attendee may differ. Assigning both groups as if they concern one person can hide role confusion behind apparently successful filling. Identify the account holder, service recipient, and contact before deciding which purposes apply. A field component's default should not define the business relationship.

Check the declaration against the completed task

Error recovery must preserve deliberate edits. Suppose autofill suggests an old postal code, the user corrects it, and another field fails server validation. Reapplying account data after rerender can overwrite the correction. Distinguish current user input, historical suggestions, and server-confirmed values, and verify that each address retains its object association on return. A nonempty form after an error does not prove correct preservation.

A proposed review inventories rendered labels, types, tokens, and submitted parameters, checking order, applicable controls, and grouping. Use fictitious test profiles in target browsers for two addresses, reordering, removal and recreation, manual overrides, and return visits. Inspect the resulting payload and confirmation page as well as the initial field values.

These tests have not been executed, and no completion-speed or conformance result is claimed. The site's question protocol first determines whether data should be collected. Purpose declaration then helps people and software understand retained fields. Begin with a page containing two similar data groups and verify the represented people before applying attributes broadly.
