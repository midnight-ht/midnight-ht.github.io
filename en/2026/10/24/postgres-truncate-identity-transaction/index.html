What Happens to Identity and Rollback After TRUNCATE?

Check table rows, transactional identity restarts, session currval, and concurrency separately when planning PostgreSQL cleanup.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-24 · Estimated read 16 min
Translations

Article

Key takeaways

  • TRUNCATE preserves sequence progress by default.
  • Restart rollback and session-local currval are different observations.
  • Validate table scope, locking, and snapshot behavior separately.

TRUNCATE keeps sequence progress by default. RESTART IDENTITY explicitly restarts sequences owned by columns of the tables being truncated. In PostgreSQL 18, both the table truncation and that implicit restart can roll back with the surrounding transaction. A session's currval() can nevertheless remember a value obtained inside the failed transaction. Check table data, sequence state, and session observations separately before deciding whether recovery worked.

Emptying a table does not select a numbering policy

The PostgreSQL 18 TRUNCATE reference names CONTINUE IDENTITY as the default. The restart alternative covers sequences owned by columns of the affected tables. It does not mean every sequence with a related-looking name in the database. A maintenance script that empties a table and assumes the next identifier starts at one has silently added a promise the statement did not make.

Consider a disposable exercise database containing a batch table. Its identity column uses the default starting value, and it currently has rows numbered one and two. After an ordinary truncation, another insert should follow the existing sequence progress. Rebuild the same starting state and use RESTART IDENTITY to investigate restarting instead. These numbers are hypothetical conveniences, not a requirement that business identifiers be consecutive. Sequence configuration, caching, and other callers need separate inspection in a real environment.

The following SQL is an unexecuted teaching example for an isolated database. It deliberately puts a truncation and an insert inside a transaction that rolls back. No application database was touched, and this is not a production cleanup procedure.

CREATE TABLE scratch_batches (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  label text NOT NULL
);
INSERT INTO scratch_batches(label) VALUES ('A'), ('B');
BEGIN;
TRUNCATE scratch_batches RESTART IDENTITY;
INSERT INTO scratch_batches(label) VALUES ('C') RETURNING id;
SELECT currval(pg_get_serial_sequence('scratch_batches', 'id'));
ROLLBACK;
SELECT id, label FROM scratch_batches ORDER BY id;

Under the documented contract, rollback undoes both truncation and the implicit sequence restart, restoring the original rows. The identifier returned for C establishes only that a value was allocated inside that transaction. It does not establish that C remains in the table. A subsequent currval query in the same session may still reflect that failed transaction's allocation. This session memory does not by itself demonstrate a broken sequence rollback, and it cannot identify a committed row.

The ordinary sequence-gap rule answers a different question

The earlier article on sequence allocation and rollback explains why ordinary nextval allocations are not reclaimed after failure. This article adds a specific contract for the restart performed by TRUNCATE RESTART IDENTITY. That restart is transactional. The two statements concern different operations; treating all sequence-related changes as one rule loses the distinction.

A proposed verification should record the initial rows and sequence configuration, capture the insert's returned value inside the failing transaction, and inspect the restored rows after rollback. If another insert is used to examine subsequent allocation, remember that the diagnostic insert itself consumes an identifier. Repeatedly calling a sequence function in a shared database changes the state being investigated. An untouched second session may also have no currval defined yet, so it is not a universal read-only inspection mechanism.

There is another failure path beyond the database. Suppose a process truncates the table, tells an external service that identifier one can be reused, and then rolls back. Restoring local database state does not withdraw the external message. Links, audit records, and caches may still treat an old identifier as a durable identity. A table becoming empty is not sufficient evidence that reusing identifiers is acceptable across the whole system.

Concurrency and related tables change the decision

TRUNCATE takes ACCESS EXCLUSIVE locks on affected tables, blocking other concurrent operations. Sequences being restarted are also locked exclusively. The reference recommends DELETE when concurrent access must continue. Choosing between them therefore requires more than comparing statement length or expecting a faster cleanup. If the requirement is to remove only expired rows, the lack of a row predicate already makes whole-table truncation the wrong operation.

Foreign keys also affect scope. The default RESTRICT behavior refuses a truncation when referencing tables are omitted. CASCADE can add referencing tables to the group. Appending CASCADE simply to remove an error changes which data may disappear. A reviewable maintenance plan names the intended tables, examines their relationships, records expected contents, and decides whether the entire group may be emptied. Cascading is a scope choice rather than a repair button.

Triggers require their own review. The reference distinguishes ON TRUNCATE triggers from ON DELETE triggers. A system that depends on row-deletion auditing cannot assume the same path runs for truncation. Inventory the effects the business actually needs, then verify them in a recoverable environment. Rollback capability alone says nothing about whether the chosen command implements the business workflow, especially if trigger logic reaches a service outside the database.

Does transaction protection preserve what an older snapshot sees?

No such conclusion follows from rollback support. The reference explicitly describes TRUNCATE as not MVCC-safe: concurrent transactions using a snapshot from before truncation can see an empty table. Restoration and concurrent snapshot visibility are separate contracts. If readers must retain a consistent view through maintenance, define a maintenance window or choose an operation that meets that requirement, then investigate it with two controlled sessions.

That experiment should control when the reader establishes its snapshot, when the writer acquires its lock, and which statement actually obtains table access. Otherwise an apparently successful demonstration may simply have exercised a different lock order. Record the transaction isolation level and observed timing rather than generalizing from a single terminal transcript.

Use four independent starting states: keep identity and commit, restart identity and commit, keep identity and roll back, restart identity and roll back. Rebuild the same two rows and sequence configuration each time so an earlier diagnostic insert cannot contaminate the next case. Commit cases check disappearance of old rows and presence of the new row; rollback cases check the reverse. Only then examine allocation under the chosen identity policy.

Define acceptable lock-wait and execution deadlines for maintenance. Another session may hold a required lock, leaving the operation waiting rather than partly completed. Record the failed statement and whether its transaction still needs ending before issuing a reset-complete notification. Exact timeout and transaction handling require the actual session configuration. The PostgreSQL 18 sequence-function reference supports the distinction between allocation and session-local observation; it is not a reason to adjust a sequence merely to remove a visible gap.

This article inspected PostgreSQL 18 documentation without executing SQL, lock-wait, or snapshot experiments. Acceptance should explain five things: the original rows, the affected table set, the identity option, the transaction outcome, and the observing session. Before selecting a whole-table reset, establish that the business allows those states to change together.
