Compose depends_on: a healthy startup gate is not runtime recovery

Separate startup health, successful migration, explicit restart coupling, and application recovery after a connection breaks.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-24 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • service_healthy waits for a healthcheck rather than only a running container.
  • Use successful completion for one-shot tasks and lifecycle-appropriate gates for services.
  • Dependency restart:true concerns explicit Compose operations, not health-change cascades.

Compose depends_on expresses startup dependencies. With service_healthy, an application can wait for its dependency’s healthcheck before startup. That startup condition does not replace runtime reconnection, failure responses, or data recovery. A database that starts successfully in the morning can disconnect later; the application still needs a recovery policy.

Running, healthy, and completed establish different facts

Docker’s Compose startup-order guide says startup normally waits for a container to run, not for the service to be ready. In the long dependency syntax, service_healthy uses the dependency’s healthcheck, while service_completed_successfully requires successful task completion. The live guide was checked on October 24, 2026. No Compose command or fault-injection test was executed, and the fragment below is not a complete deployment configuration.

A container existing, its process running, and a database being able to handle a target request are progressively stronger claims. A passing database check may still say nothing about required tables, permissions, or migration versions. A healthcheck should ask an inexpensive question relevant to startup admission. Business initialization needs a separate completion definition.

Declaring a dependency does not mean an application connection failure will automatically reinitialize that dependency. The startup graph retains no transaction context and cannot know whether a request committed. Runtime outcomes need application behavior and persistent-state evidence.

A hypothetical database, migration, and application graph

Suppose a local test stack contains a database, a one-shot migration, and an application. The intended sequence is a database accepting connections, a successful migration, then application startup. This fragment shows those relationships only. Images, credentials, networking, and mounts require additional configuration; the migration command and check must exist and be verified in the project.

services:
  db:
    image: postgres:18
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U example -d example"]
      interval: 10s
      timeout: 5s
      retries: 5
  migrate:
    build: .
    command: ["./migrate"]
    depends_on:
      db:
        condition: service_healthy
  app:
    build: .
    depends_on:
      db:
        condition: service_healthy
        restart: true
      migrate:
        condition: service_completed_successfully

Assume initialization takes 25 seconds, health first succeeds around the third check, and migration then exits successfully. The application can now satisfy the declared creation conditions. This is a paper walkthrough, not observed timing. Probe scheduling, retries, and project operations affect the result; the fragment cannot promise an exact availability time.

If migration exits nonzero, having run its container does not establish completion. Retain the migration error and prevent the dependent application from proceeding. Similarly, a database accepting connections does not prove that the application account can write. Verify reachability, migration version, and a minimal application operation separately instead of compressing them into a generic startup timeout.

Why restart: true does not repair every runtime failure

The guide associates dependency-level restart: true with dependency updates or restarts caused by explicit Compose operations, such as restarting the database through Compose. It is not continuous automatic restarting of dependents whenever database health changes. It also differs from a container’s own restart policy. A configuration review should name both the field’s nesting level and the triggering operation.

Suppose the application has run for an hour when its database connection is interrupted, without either container exiting. The application needs bounded reconnection, explicit results for requests it cannot complete, and controls against retry storms. Retrying a write depends on whether the first attempt’s outcome can be established and on the business idempotency contract. Restarting the application cannot turn an unknown transaction outcome into a known non-execution.

Another failure path is an overbroad healthcheck that depends on a remote service. Temporary remote latency can fail local checks. An external script that restarts everything without identifying the cause may repeatedly interrupt applications that could recover. Each startup condition needs a reason to block creation; runtime failures need an assigned recovery owner. A field named restart does not settle those decisions.

Should a migration be healthy or successfully completed?

For a task designed to run once and exit, successful completion expresses the intended dependency. Waiting for it to remain healthy does not describe the desired outcome: the application needs the migrated database state, not a resident migration process. The script must also explain partial commits and safe reruns after failure. One successful exit is insufficient if the underlying state is wrong.

A resident service has a different lifecycle. Waiting for a database to complete successfully waits for a process that is not supposed to finish. Select the condition by the result the dependent needs: a service provides capability while running, whereas a task leaves a result after completion. That determines whether started, healthy, or completed-successfully is appropriate.

Proposed verification should cover slow database startup, a failed migration, and a database interruption after application startup. Observe container creation, health status, migration exit codes, and application request results. Test explicit Compose restarts separately from health-only changes: one examines configured restart coupling, the other application recovery. They cannot share one undifferentiated restart-passed receipt. None of these checks has been executed here.

For example, an insert may commit just before the connection breaks, leaving the application without confirmation. After reconnecting, inspect the outcome using a permitted business identity or the established idempotency mechanism rather than inserting again blindly. A healthcheck can observe service capability, not decide that transaction outcome. Checks should also avoid performing migrations, sample writes, or data deletion: repeated probes would then alter business state. Verify that the probe is read-only and leaves useful failure diagnostics.

Retain the local Compose version and resolved configuration, then use isolated data to check read/write consistency after recovery. Health establishes a startup gate; completed requests establish business outcomes. The article on probe responsibilities provides a related way to reason about recovery actions, but Kubernetes controller behavior should not be attributed to Compose dependency configuration.
