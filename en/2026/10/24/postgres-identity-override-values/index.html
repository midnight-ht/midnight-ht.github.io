Whose Identity Does PostgreSQL OVERRIDING Preserve?

Choose preserved or regenerated identity, then verify later allocation, parent-child mappings, and repeated imports.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-24 · Estimated read 17 min
Translations
zh-CN en

Article

Key takeaways

  • SYSTEM accepts supplied identities; USER generates destination identities.
  • Verify ordinary allocation after importing explicit values.
  • Preserve scoped source identities for mappings and retries.

Before importing an identity column in PostgreSQL, decide whether an old identifier must continue to name the same object. OVERRIDING SYSTEM VALUE accepts supplied identity values instead of sequence-generated defaults. OVERRIDING USER VALUE ignores the supplied identity values and generates new ones in the destination. The former can suit an identity-preserving migration; the latter can suit creating new copies. Neither option repairs foreign-key mappings or proves that subsequent automatic allocation will avoid imported values.

ALWAYS describes ordinary insertion, not an absolute migration prohibition

The PostgreSQL 18 INSERT reference distinguishes GENERATED ALWAYS from GENERATED BY DEFAULT. For an ALWAYS identity column, inserting an explicit value other than DEFAULT is an error unless an appropriate overriding clause is specified. BY DEFAULT already accepts explicit values as normal behavior. To avoid reversing the two clauses mentally, ask what is overridden: the system's generated value or the user's supplied value.

Imagine an old catalog containing product A with identifier forty-two. A migration preserving historical links may need to keep that identifier. A separate task that copies A into a new template creates another object, even if its name is identical. Copying the old primary key could collide with an existing row or incorrectly suggest that both templates have the same identity. These operations both look like copying data but require opposite identity policies.

This unexecuted SQL illustrates the distinction in a disposable exercise database. The first insertion preserves the supplied identity; the second generates a destination identity. Inspect RETURNING for the actual generated value rather than assuming a particular number.

CREATE TABLE scratch_catalog (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name text NOT NULL
);
INSERT INTO scratch_catalog(id, name)
  OVERRIDING SYSTEM VALUE VALUES (42, 'example') RETURNING id;
INSERT INTO scratch_catalog(id, name)
  OVERRIDING USER VALUE VALUES (42, 'copy') RETURNING id;

Removing the first overriding clause supplies a negative control for the ALWAYS restriction. Using the second clause during a migration that must preserve identity is a different failure: SQL may succeed while the business relationship changes. Database acceptance and compliance with the migration's identity contract are separate checks.

A successful import does not validate the next ordinary creation

Supplying explicit identity values should not be treated as advancing the associated sequence beyond every imported identifier. Imported rows and subsequent allocation are distinct state. If an import occupies a value that the sequence will later generate, a normal creation can encounter a primary-key collision long after the import appeared successful. Inspecting only the import receipt misses that later entry point.

A maintenance plan should inspect the destination sequence, the identifiers already present, whether concurrent writers are paused, and the outcome of a later ordinary insert in an isolated copy. If sequence adjustment is necessary, first identify the actual associated sequence and its configuration. Starting values, increments, direction, and allocation by concurrent transactions complicate a simplistic instruction to set it to the maximum row identifier. No sequence adjustment was performed here, and this explanation is not a complete migration utility.

Identity generation also does not replace an explicit uniqueness requirement. The example includes a PRIMARY KEY so the rule rejecting collisions is visible. If a real table has generation behavior without the uniqueness constraint its operators expect, imported duplicate identities may not fail as assumed. Review generation, non-null behavior, and uniqueness separately instead of searching the schema for the identity keyword and stopping there.

Child rows must follow the chosen identity policy

Suppose source product forty-two has two price records. When preserving its identity, verify that their references still designate the migrated product. When generating a new identity, retain a reliable mapping from the source identifier to the returned destination identifier. Child inserts must use that mapping. Regenerating the parent identity but copying child foreign keys unchanged can cause rejection or, more dangerously, associate them with a different product already present in the destination.

A reviewable process retains a stable source identifier for each imported object, records source-to-destination mappings during parent insertion, and processes children from those mappings. Define whether the batch may be retried, within what scope source identifiers are unique, and when mappings become durable. These are business and transaction decisions, not hidden services of an overriding clause.

Do not pair two bulk results by incidental array position. Filtering, conflict handling, or ordering can change which rows appear and in what sequence. If a result cannot be related to its source through a stable key, the migration needs a clearer mapping design before child rows are written. A count of returned rows is weaker evidence than a checked association for each relevant object.

For copying only non-identity fields, explicit column lists usually make review easier than SELECT *. A schema change can add identity-related or sensitive fields or change expected positional correspondence. The overriding clause handles destination identity columns; it does not decide the authorization or business meaning of newly copied fields. The related article on omission, DEFAULT, and explicit NULL examines another input distinction. Here the question is identity ownership and relationship preservation.

Does generating fresh identifiers make a repeated batch safe?

No. It can make duplicate business objects harder to notice. Suppose a timeout prompts the same source product to be imported twice. Two USER-overriding insertions may generate different primary keys, so primary-key uniqueness does not establish that the same source object was processed once. Define duplicate handling through an appropriate source identity or business key, retain batch outcomes, and decide whether retries fill gaps, skip completed work, or perform explicit updates.

That retry policy also needs an unknown-result path. If the caller loses its connection after submission, generating another identifier is not evidence that the first insertion failed. Query the stable import identity or retained batch record before creating another copy. This is a proposed design criterion, not an assertion about a particular driver's reconnect behavior.

Test mappings with two source catalogs whose local product identifiers are both forty-two. If source identity includes catalog scope, the mapping key must include that scope rather than letting one local identifier overwrite the other. Repeat one source object and verify the chosen duplicate policy: rejection, reuse of an existing mapping, or an explicit update. Decide that policy before child insertion.

A price record lacking a parent mapping should produce a locatable failure naming its source catalog, parent, and child. Verify rollback if whole-batch atomicity is required, or list committed and pending parts if partial success is allowed. Reducing an affected-row count silently loses the information needed for repair. The identity-column chapter separates generation from uniqueness, while sequence functions document allocation state and its manipulation. Review both alongside the actual schema when deciding how later allocation is handled.

Proposed acceptance should cover identity-preserving import, identity-regenerating copy, and an ordinary creation after import, together with parent-child mapping and repeated-batch negative cases. Compare returned identifiers, stored rows, relationship ownership, and later writes rather than just affected-row counts. This article uses PostgreSQL 18 documentation and executed no schema creation, import, or SQL. The decisive question remains whether an old identity must continue to denote the same business object.
