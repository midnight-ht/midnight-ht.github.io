PromQL group_left: keep left-hand detail, prove right-hand uniqueness

Work through matching keys, unique denominators, retained labels, missing series, and window alignment in a PromQL ratio.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-24 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • group_left allows many left series to match one right series without deduplicating the right.
  • Define the request population and matching key before checking uniqueness.
  • Missing denominators, zero values, and mismatched windows need distinct treatment.

group_left lets multiple left-hand series participate in a binary operation with one matching right-hand series while retaining left-hand detail. It does not automatically combine duplicate right-hand matching keys. Define the key and establish right-hand uniqueness first. Error rates split by method and status code divided by request rates split only by method are a suitable use case when the actual data satisfies those conditions.

Decide what matches before deciding which labels survive

The Prometheus operators documentation describes on as selecting matching labels and ignoring as excluding labels from matching. group_left identifies the left as the many side; its optional label list can bring additional labels from the one side into the result. This article uses the latest reference checked on October 24, 2026 and discusses ordinary float instant-vector division. It does not enable the separately documented experimental fill features, and no queries were run.

Matching and aggregation are different operations. Matching selects two series for an operation; aggregation reduces multiple inputs to a result. Treating group_left as an error-suppression switch skips the substantive question: should instances, clusters, or environments have separate denominators, or does the business question call for their sum? Syntax cannot establish that two series describe the same request population.

Include labels necessary to define that population. If both sides retain cluster identity, matching only by method may combine unrelated clusters in the same matching group. Conversely, putting status code in the key when the total-request denominator has no such label can prevent matching. Start with inputs that can be listed by hand before modifying a complex dashboard expression.

Divide three error rates by two denominators

Assume the inputs already contain rates over the same five-minute window, measured in requests per second, for one explicit cluster and environment. The error side has three series: read/500 is 2, read/404 is 3, and write/500 is 1. Total request rates are 100 for read and 20 for write. These are hypothetical inputs, not site traffic.

Under those assumptions, the output retains method and status code from the left. The two read results are 2% and 3%; the write result is 5%. The read categories use the same denominator without adding it twice. Each result means this error category's share of all requests for its method. A total error ratio requires an appropriately aggregated numerator; each individual ratio is not the overall error rate.

Three versus two describes only this dataset. Many-to-one is determined within each matching key, not by comparing total row counts. Equal overall counts can still hide two left-hand status categories and two right-hand instance denominators for one method. Similar global sizes do not establish local uniqueness.

Why an extra denominator is not an invitation to use max

Suppose the read denominator now has two instance series, 60 and 40. It is no longer unique by method, and group_left does not choose one. If the numerator already combines both instances, summing the denominator to 100 may be the intended question. If the numerator retains instance detail, adding instance to the matching key may be appropriate. These choices define different ratios.

An unexplained max by(method) creates a single denominator of 60. Dividing the error rate of 2 by it gives approximately 3.33%, rather than the intended 2%. Taking a maximum may have a rationale for redundant observations of the same fact under a defined deduplication contract. It should not conceal unidentified populations.

To bring a stable ownership label from the right, name it in group_left(...). That does not relax right-hand uniqueness or permit ambiguous output identities. With on, a label cannot appear both in the matching list and the group label list. Establish each label's origin and confirm that every output series remains uniquely identifiable.

Can a missing denominator simply become zero?

Ordinary binary vector operations omit elements without a match, so a missing denominator can remove left-hand detail from the output. A missing series and an existing zero-valued denominator are different states. Filling missing data with zero assigns a numeric meaning to uncertainty and may produce infinity when dividing. An absent graph line does not establish zero errors.

Query numerator and denominator separately to inspect scraping, labels, and recording-rule changes. If missing data needs a visible state, define that state and its alerting policy rather than letting the ratio silently imply success. No experimental fill modifiers are used here; check deployed-version support before adopting additional syntax.

Proposed verification begins with count by(method) on the right, expanded with the real scope labels, to inspect uniqueness for each key. Then compare original inputs, aggregated numerator and denominator, and output labels, hand-calculating one example. Add duplicate right-hand keys, a missing method, and a zero denominator to check whether errors and output match the contract. Merely returning a query result is insufficient. These checks remain unexecuted.

Uniqueness does not establish the meaning of the ratio. A numerator over one minute and a denominator over one hour can each be unique and measured per second while describing different observation periods. Equal windows do not turn rates into exact event accounting, but they align the scope of comparison. Also check that both sides describe the same entry point; dividing local application errors by all gateway requests does not establish that endpoint's error ratio.

For counter inputs, the calculation order is discussed in rate before sum. Inputs produced by recording rules also need their output label contract. Before publishing the dashboard, record the matching key, evidence of one-side uniqueness, denominator population, and missing-data policy so the next maintainer can identify the ratio being calculated.
