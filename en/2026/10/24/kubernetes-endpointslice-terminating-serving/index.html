Reading ready, serving, and terminating on departing EndpointSlice targets

Interpret EndpointSlice conditions together, including the publishNotReadyAddresses exception and proxy behavior limits.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-24 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • A deletion timestamp and process exit are different events.
  • The usual ready relationship has a publishNotReadyAddresses exception.
  • Possible routing to serving terminating targets is not proof of actual draining.

In an EndpointSlice, terminating=true means an endpoint is terminating, not that its process has exited. serving can still describe its ability to serve responses. Normally, ready is shorthand for serving and not terminating, so a departing endpoint can have ready=false and serving=true at the same time. Read all three conditions before investigating the behavior of the proxy and application.

Three fields answer different questions

The Kubernetes EndpointSlices documentation marks serving and terminating as stable since version 1.26. For Pod-backed endpoints, serving maps to the Pod Ready condition. Terminating is set when the Pod receives a deletion timestamp, usually before its containers exit. This article follows the live documentation checked on October 24, 2026. No cluster or rolling-update experiment was run.

Collapsing the fields into one health flag loses distinctions during shutdown. An endpoint can still serve while deletion is underway. Another can be unavailable without being deleted. The former calls for traffic migration and draining decisions; the latter calls for investigation of unavailability. One boolean can encourage the same recovery action for different situations.

There is an exception to the ordinary relationship: the documentation says ready is always true for a Service with spec.publishNotReadyAddresses=true. A ready value therefore cannot be interpreted independently of Service configuration. Retain that configuration alongside endpoint conditions rather than asking downstream consumers to infer application state from one compatibility-oriented field.

Follow a hypothetical two-replica shutdown

Suppose a report service has replicas A and B, both initially ready. After A receives a deletion timestamp, its terminating condition is set while it can still complete a report. A may be serving while terminating, with B available for new traffic. The usual ready interpretation excludes A from the ordinary ready set; it does not mean A’s process disappeared at that instant.

These observations illustrate possible states, not collected cluster logs. Propagation depends on the control plane, proxy, and application; it is not an atomic update across components.

For normally operating B, assume ready=true, serving=true, and terminating=false: it is an ordinary available target under the stated configuration. After A receives a deletion timestamp, assume ready=false, serving=true, and terminating=true: it is departing while still reporting serving capability. When A stops serving, ready=false, serving=false, and terminating=true describe another possible state. These observations do not establish the process-exit event.

If B also starts terminating, another decision arises. The official documentation says service proxies normally ignore terminating endpoints, but may route to endpoints that are both serving and terminating when all available endpoints are terminating. Preserve that qualification. It is not a guarantee for every proxy and traffic policy, nor permission for the application to accept unlimited new work.

The behavior can avoid a period without targets during an update, but capacity and completion within the shutdown budget remain separate conditions. A long request may still fail when the process exits. Serving is state supplied to a routing decision; a complete user outcome needs request-level evidence.

Serving is not a draining counter

serving=true does not count active requests or prove accepted work is durable. A false condition likewise cannot establish that every client connection has ended. Existing connections, ingress caches, proxy updates, and application admission control need separate observation. An EndpointSlice snapshot cannot replace their timeline.

For example, observing ready become false and sleeping a fixed interval does not establish successful draining. It shows a state observation and elapsed time, without establishing whether A still owns work, a request was retried, or B received all new traffic. Verification must associate accepted task identities with completion or handoff outcomes.

Application shutdown must also be compatible with routing behavior. Closing the listener immediately can reject connection attempts from proxies that have not seen the update. Accepting indefinitely can leave too little time to finish work. Define admission, rejection, completion, and handoff for the actual request type. No universal sleep interval can be derived from these three fields.

What does publishNotReadyAddresses change?

It changes how ready is interpreted; it does not replace an availability check. A consumer using this option for a special discovery requirement should state which conditions it reads and whether it validates the application protocol. Publishing an address and guaranteeing that it can process a particular business request are different promises. Enabling the option just to make an address appear does not establish a successful release.

A custom proxy or direct EndpointSlice consumer also needs to establish who manages the objects, which conditions it understands, and how versions interoperate. A field’s presence in the API does not prove that a deployed networking component uses it as expected. Verify the actual proxy documentation and configuration; this article does not validate any particular network implementation.

A proposed experiment would retain B while deleting A and collect the deletion timestamp, three condition changes, proxy target selection, and A’s last accepted request. An isolated second case could terminate all available endpoints. Compare short and long requests, tracking new traffic, in-flight work, and retries separately. Retain component versions and Service traffic policies to make differences interpretable. These experiments remain unexecuted.

The article on graceful termination budgets addresses available shutdown time. This one explains how service discovery describes departing targets. Associate a real request with the endpoint timeline before choosing changes to admission policy, proxy configuration, or shutdown budget. A changed condition begins the investigation.
