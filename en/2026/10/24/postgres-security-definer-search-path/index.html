Why Fix search_path in a SECURITY DEFINER Function?

Review trusted schemas, temporary-name precedence, and execution grants before exposing a privileged PostgreSQL function.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-24 · Estimated read 16 min
Translations
zh-CN en

Article

Key takeaways

  • Owner privileges do not bind every object name.
  • Trusted-schema permissions and pg_temp order require explicit review.
  • Deploy the function and restricted execution grants transactionally.

A SECURITY DEFINER function executes with its owner's privileges, but unqualified object names still require resolution. PostgreSQL 18 advises excluding schemas writable by untrusted users from its search_path and explicitly putting pg_temp last. Otherwise the caller can influence which objects privileged code finds. Fixing name resolution is one defense; function execution grants and business authorization remain separate decisions.

Higher privilege does not bind every object name

The security guidance in CREATE FUNCTION identifies tables, functions, and operators created by untrusted users as objects that can mask the intended ones. Adding SECURITY DEFINER does not automatically bind every name in the body to the schema the author had in mind. A caller lacking direct access to a protected table may still influence a decision made through a privileged function.

Consider a hypothetical administrator-maintained membership list. A function accepts a member identifier and returns whether that member is allowed. Its intended source is a table in a trusted schema. If it uses an unqualified table name and the caller can create a same-named temporary table, resolution can diverge from that intention. This is a threat model derived from the official mechanism. No object was injected into an online database, and no vulnerability in this site is claimed.

Reviewers should distinguish the function's own schema from the lookup path used inside its body. Naming a function admin.member_allowed does not establish that an internal allowed_members reference resolves within admin. Review attached settings, object references, and the roles actually permitted to create objects in the schemas involved. A reassuring schema name is not permission evidence.

Why listing only a trusted schema is insufficient

Temporary-table lookup is the easily missed condition. The documentation explains that listing admin without explicitly placing pg_temp can still allow a temporary table to mask the intended table. Naming pg_temp last establishes the intended precedence. The requirement is not a blanket prohibition on temporary tables; it is an explicit lookup order at a privileged boundary.

This unexecuted structural example assumes a private exercise database already contains controlled roles, schemas, and a membership table. It is not a complete authorization system ready for deployment. Creating those dependencies, selecting the function owner, and managing their privileges require a separate reviewed migration.

BEGIN;
CREATE FUNCTION admin.member_allowed(member_id bigint)
RETURNS boolean
LANGUAGE sql
SECURITY DEFINER
SET search_path = admin, pg_temp
AS $$
  SELECT EXISTS (
    SELECT 1 FROM admin.allowed_members AS m WHERE m.id = $1
  );
$$;
REVOKE ALL ON FUNCTION admin.member_allowed(bigint) FROM PUBLIC;
GRANT EXECUTE ON FUNCTION admin.member_allowed(bigint) TO app_reader;
COMMIT;

The example both qualifies its table and declares a path so the intentions are visible. Admin must actually be trusted and unavailable for low-privilege callers to populate. If the application role can create objects there, putting that schema first simply encodes an unsafe assumption. Verify privileges using the real roles rather than inferring trust from a label.

The owner also needs enough access for the stated query, while the caller needs appropriate access to the schema containing the function. Those deployment prerequisites should be explicit. A denied call can otherwise reflect a missing schema grant rather than successful enforcement of the intended function-level rule, leaving a test that passes for the wrong reason.

Deployment can create a temporary authorization opening

The documentation notes that newly created functions receive PUBLIC execution privilege by default. A restricted entry point should revoke that grant and selectively grant execution to intended roles. Creating the function and adjusting its privileges in one transaction avoids a period in which the function exists publicly before being restricted. Finding a REVOKE statement near the end of a migration is not enough if earlier commits expose the function first.

Consider a failure after creation: the privilege statement contains an error and the script has no surrounding transaction. The deployment process may exit unsuccessfully even though the function was created. Inspect actual database state instead of interpreting a failed process as proof that nothing changed. A proposed migration test should make a privilege statement fail and check whether an unintended callable function remains.

Choose ownership according to the limited operation required. A function that reads one protected table does not automatically need a superuser owner. Reducing owner capabilities does not replace a trusted lookup path, but it limits the impact of mistakes. The related discussion of RLS runtime roles also depends on actual identity. Here the relevant identity is the function's effective execution privilege, so a normal connection query cannot substitute for calling the function.

What remains after every table name is schema-qualified?

Inspect function calls, operator resolution, dynamic SQL, and authorization of parameters. Qualifying one table resolves that reference; it does not establish that every expression in the function is safe. A fixed path does not turn dynamically concatenated input into a trusted identifier or expression. Nor does it decide whether a caller may inspect any member or only their own membership. Those questions belong to input handling and business authorization.

A proposed verification creates a low-privilege calling role and checks the function under its intended read-only contract. Introduce a same-named temporary object as a negative control. The protected function should still read the trusted table, an unauthorized role should not call it, and an authorized role should not exceed its allowed member scope through a different identifier. Define that scope first; the membership sketch above does not implement per-caller business identity.

Keep the function definition, owner, schema creation privileges, execution grants, and returned values together in the evidence. A successful administrator query proves very little about the low-privilege caller's boundary. Repeat the checks after a migration changes function signatures or ownership, because a different callable object may have different grants.

Before the exercise, write an actual privilege matrix: the owner can read the membership table; the caller can use the containing schema and execute the exact signature; the caller cannot create objects in the trusted schema or directly read the protected list. Establish one permitted successful call before testing denied calls. Otherwise missing schema usage can make every call fail without exercising the intended function boundary.

Prepare a trusted list allowing member A and denying member B, then put the opposite data in the caller's same-named temporary table. Under the intended configuration, results must still follow the trusted list. Absence of an exception is insufficient. Restore the same starting state between cases and associate definitions and grants with the actual test role. Administrator access used to prepare expectations does not become data the application caller is entitled to receive.

This article inspected PostgreSQL 18 documentation without creating a database, changing grants, or executing an attack test. A delivery should establish whose privileges execute, which trusted objects resolve, and which results the caller is authorized to request. Configuring only one of those choices is insufficient evidence that the privileged entry point is ready.
