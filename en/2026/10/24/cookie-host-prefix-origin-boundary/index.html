Can __Host- cookies isolate different ports on one host?

Inspect host and port trust, subdomain login migration, legacy credentials, and logout before changing cookie prefixes.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-24 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • Host-bound __Host- cookies still ignore ports.
  • Shared-domain login and local host sessions require different designs.
  • Migration must address browser legacy values and server acceptance.

A __Host- cookie does not isolate different ports on the same host. Supporting browsers constrain secure transport, root path, and the absence of Domain so the cookie is host-bound. Ports remain outside that isolation. If an administrative service and an untrusted experimental service share a host, changing a cookie name cannot create the missing credential boundary.

A host boundary is not the full origin model

HTTPWG's cookie working draft explicitly notes that __Host- still ignores ports. The source checked here is the working draft published on 23 October 2026, not a final standard that has already replaced the older RFC. MDN's Set-Cookie reference also describes the Secure, Path, and Domain requirements. Confirm support in the actual target browsers.

A web origin includes scheme, host, and port, while the historical cookie scope model does not provide all those boundaries. Two HTTPS services on different ports of one host can be different origins without receiving independently isolated cookie credentials. Restrictions on cross-origin script access and conditions for sending cookies are separate questions.

The prefix does not imply HttpOnly either. Add that attribute when scripts should not read a session cookie. The server still decides session validity and operation permission. Browser checks on cookie configuration do not establish application authorization.

Follow two services sharing a host

Imagine production administration at https://admin.example.test and an experimental HTTPS service on another port of that host. Different teams maintain them with different trust levels. This is an unexecuted threat-model example. Administration returns __Host-session with Secure, Path=/, and no Domain, and the team assumes the experiment cannot encounter that cookie.

Now the user directly visits a qualifying path on the experimental port. Changing the port has not added a cookie-isolation dimension. Other sending conditions still matter, but the architectural conclusion is clear: separate ports are not evidence of separate host cookies. One request that happens not to carry a cookie cannot establish the opposite model.

A candidate repair moves mutually untrusted services to different hosts and uses appropriately host-only sensitive sessions, checking that proxies and services do not broaden their scope. Alternatively, services sharing a host may be deliberately managed within one trust boundary, with responsibility for the shared credential risk. Port labels, URL directories, and proxy route names do not make that decision disappear.

Continue the scenario after moving the experiment: log into administration, visit the experimental host, and inspect whether the administrative session appears; then check whether experimental cookie setting can affect what administration accepts. Use valueless test tokens and conceal values in records. This is a proposed acceptance method, not an executed visit or attack against a real service.

Why can the prefix break shared subdomain login?

An existing parent-domain cookie may deliberately share a session across subdomains. The no-Domain condition changes that ability. A cookie cannot simultaneously be confined to one host and be expected to arrive directly at every sibling subdomain. Migration is a login architecture decision before it is a response-header edit.

One option establishes a local session per application through a designed identity redirect or token exchange. That introduces callback validation, one-time state, revocation, and recovery responsibilities. No untested complete single-sign-on implementation is supplied here. If a shared domain scope is required, explicitly accept its wider trust boundary instead of expecting the prefix to satisfy conflicting requirements.

A counterexample changes the response header but continues accepting the old cookie name indefinitely. The new prefix appears successful while the broad legacy credential remains usable. Send and parse the complete prefixed name rather than stripping it in an intermediate layer and confusing it with legacy names. The server must be able to explain which credential path it accepts.

Avoid apparent logout during migration

Plan browser cleanup and server-side invalidation together. Setting a new host-local name does not delete old names, Domains, or Paths. Removing the current value from one interface does not prove that old sessions are unusable elsewhere. Inventory old and new scopes, acceptance windows, revocation, and the conditions ending fallback.

Suppose a user signs out of administration while another subdomain retains the shared credential. If the server still accepts it, returning may recreate access. Decide whether that is intended federated sign-in recovery or a logout defect, then implement the product promise. Inspect the server's final acceptance decision, not just disappearance of the new cookie from storage.

Keep three kinds of observation separate

A port experiment can produce a false success: the experimental service receives the test cookie but returns unauthenticated because it does not recognize the value. That establishes nonacceptance, not nondelivery. Conversely, administration accepting a value does not establish where it was originally set. Record request arrival separately from acceptance, using a valueless marker to correlate observations. Disable or redact raw Cookie logging before testing so the verification does not itself broaden credential exposure.

A proposed matrix covers valid configuration, missing Secure, incorrect Path, explicit Domain, sibling hosts, and different ports on the same host. Observe whether a response is accepted, whether a target request carries the cookie, and whether the server accepts the session. Browser rejection and server rejection are different outcomes. Include failed callbacks, coexisting legacy values, revisits after logout, and fallback removal.

None of these checks has been executed or establishes an overall security certification. The site's Secure and HttpOnly discussion addresses transport and script access. Here, first map hosts, ports, and trust. If mutually untrusted services are separated only by a port, address the deployment boundary before treating prefix migration as the fix.
