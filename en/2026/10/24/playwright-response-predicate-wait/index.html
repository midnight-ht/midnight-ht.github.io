Playwright response waits: register first, then identify the submission

Register before clicking, match the operation, then check response status, payload, and the page outcome separately.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-24 · Estimated read 14 min
Translations

Article

Key takeaways

  • Create the response Promise before triggering the request.
  • Match the operation before asserting status so conflicts remain visible.
  • Concurrency, asynchronous terminal state, and page presentation need separate evidence.

To wait for a submission response in Playwright, establish waitForResponse before triggering submission and match conditions that identify the intended operation. A URL alone may match a background read; registering after clicking may miss a response that has already arrived. Once matched, check status, data, and the page outcome separately. A network event does not by itself establish business completion.

Registration order and response identity solve different problems

The Page.waitForResponse reference demonstrates creating a response Promise before clicking, without awaiting it yet, then triggering the action and awaiting the response. The API accepts a string, regular expression, or predicate; a predicate can inspect the response and its request. The API is marked as introduced before version 1.9. The live reference was checked on October 24, 2026; that is not validation of every historical version or browser.

Registration order addresses fast events. If waiting begins only after the click finishes, the server may already have responded. A timeout can therefore mean late observation rather than a slow service. Conversely, awaiting the response Promise before triggering the click stops execution before the request-generating action. Moving one await changes the causal sequence.

Identity conditions address competing events. A hypothetical editor reads /api/orders/example-42 in the background and submits updates to the same path. Matching only that path can finish on a read. The request method distinguishes reads from updates. If concurrent updates to the same object are allowed, however, the test also needs an existing request identifier or input version that distinguishes attempts. Equal methods do not automatically identify this click.

Match the save result, then decide whether it succeeded

This unexecuted example assumes there is only one update for the selected order in the test window. The hypothetical contract uses PATCH and returns JSON containing an order ID and version. Replace these assumptions and locators with the actual application contract.

const pending = page.waitForResponse(response => {
  const url = new URL(response.url());
  return url.origin === 'https://app.example.test'
    && url.pathname === '/api/orders/example-42'
    && response.request().method() === 'PATCH';
});
await page.getByRole('button', { name: 'Save' }).click();
const response = await pending;
expect(response.status()).toBe(200);
const saved = await response.json();
expect(saved.id).toBe('example-42');
expect(saved.version).toBe(8);
await expect(page.getByTestId('saved-version')).toHaveText('8');

Origin, complete path, and method exclude reads and similarly named paths on another origin. Ignoring query parameters is not universally appropriate: if a parameter identifies a tenant or operation, include it. Regular expressions, globs, and parsed paths are expression tools. Define which differences change request identity before selecting the easiest tool to review.

Assume the prior version was 7 and a successful save returns version 8, which the page should then display. Response assertions examine the server result; the page assertion examines whether the frontend presents that result. A 202 response may merely accept asynchronous processing. Under that contract, the test must observe the defined terminal state rather than stop at a satisfactory status.

Should the predicate match error responses too?

For a single-attempt save, it is usually useful to match both successful and failed responses belonging to that operation, then assert status separately. Requiring status() === 200 in the predicate can exclude an actual 409 conflict. The eventual timeout says no matching response arrived while hiding the more useful evidence that the operation returned an error status.

Status is not forbidden in predicates. If a page explicitly retries and the test targets an eventual successful response, status may be part of the match. In that case, observe intermediate failures separately and explain why waiting for another request is permitted. Otherwise, the script can blur a failed first attempt into a successful second attempt. Side-effecting operations also need a defined duplicate-request contract and an observable attempt count.

A satisfactory status still does not validate the payload. Before parsing JSON, establish that this status has a body under the protocol; a no-content response is not automatically malformed JSON. On failure, retain method, a suitably redacted object identity, status, and necessary response diagnostics. Copying complete request bodies into reports can disclose unrelated sensitive data.

Locate the broken link before extending the timeout

Proposed tests should return the background read first and the target update second, confirming that the read cannot satisfy the predicate. Then return a conflict for the update and confirm failure at the status assertion rather than a wait timeout. Finally, make the response fast enough to check that observation is registered before clicking. These are unexecuted verification designs, not observed logs.

Also cover a failing click. If the button is obstructed or navigation has left the page, a pending waiter does not establish that the server failed to respond. A helper must handle action errors and the pending Promise lifecycle without letting a later timeout obscure the original failure. The appropriate wrapper and cancellation behavior depend on the project; this article does not provide a universal exception-handling helper.

Confirm the complete request sequence as well. A browser may request one address and redirect elsewhere. Origin changes, method differences, or duplicate submissions can change the object being matched. Inspect a controlled sequence, then encode the smallest sufficient identity condition. That is easier to audit than repeatedly extending a timeout around an overly broad URL glob.

If the real interface has no correlation identity and concurrent updates cannot be excluded, this predicate cannot establish ownership. Restrict concurrency in an isolated fixture or verify input and output using an existing product version field. Do not invent a request ID in the report. If concurrent operation tracing is required, define that protocol explicitly and verify that real requests carry it.

The article on network idle and business readiness explains why quiet networking does not establish completion. For one real save path, now write down when observation begins, which attempt is matched, which response counts as failure, and what the page must eventually display. Validate those four decisions with success and conflict cases.
