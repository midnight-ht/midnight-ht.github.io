OpenTelemetry metric overflow: retaining totals while losing identity

Distinguish metric cardinality limits, overflow aggregation, identity loss, and the implementation checks behind SDK guarantees.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-24 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • Overflow can retain contribution without retaining each original attribute identity.
  • The recommended default of 2000 is not proof of an enabled limit in every SDK.
  • Synchronous cumulative, delta, and asynchronous instruments have distinct rules.

When an OpenTelemetry metric reaches a cardinality limit, some attribute combinations may stop appearing independently and contribute to a synthetic aggregation with otel.metric.overflow=true. For synchronous instruments, the specification requires each measurement to enter exactly one aggregator during overflow, without duplication or dropping. That guarantee does not preserve every original attribute identity. A missing standalone series for a new tenant does not establish that the tenant made no requests.

Identify the stream being limited

The Cardinality limits section of the Metrics SDK specification was part of specification 1.62.0 when checked on October 24, 2026, and that section is Stable. Cardinality counts distinct attribute combinations. The limit concerns metric points collected in a collection cycle, and enforcement is recommended after attribute filtering. No language SDK was executed for this article.

Configuration precedence covers a matching View's stream limit, a relevant Reader default, and a recommended fallback of 2000 when neither is set. The specification uses SHOULD: this is not proof that every SDK enables a limit of 2000. Check the actual language, version, Reader, and exporter. Other sections on the page have their own maturity levels; a stable section is not a claim that the entire page describes a deployed stable implementation.

This is also not one global series limit for the monitoring system. A process can have several instruments and Readers; multiple instances collect independently, and an exporter can represent a metric point as multiple backend series. SDK aggregation scope and backend size require separate budgets. Reducing one limit does not establish the same bound for every stage's resource use.

A synchronous cumulative Counter example

Consider an isolated experiment with one synchronous Counter, cumulative temporality, one Reader, and no attribute filtering or transformations. Assume the implementation supports and correctly applies a cardinality limit of 4. Record 5 events for tenant A and 7 for tenant B, then collect. Next, record one event for each of 10 distinct new tenants and collect again. The first two attribute combinations are below the limit, so the specified no-overflow guarantee applies. The later 12 combinations require limiting.

These are proposed inputs, not SDK output. With synchronous cumulative aggregation, combinations observed before overflow must continue to be exported, so A and B should retain independent cumulative records. Combinations that cannot be aggregated independently contribute to a point containing only the overflow attribute. Do not preselect which later ordinary combinations survive without implementation evidence.

The hypothetical total is 22. Check that contributions across ordinary and overflow aggregations correspond to 22 while A and B remain identifiable. The goal is not a separate line for every new tenant. This concerns SDK aggregation, not an end-to-end delivery guarantee through networking, Collectors, and storage. Additional filtering or export failures need separate evidence.

The small limit makes overflow easier to observe in isolation; it does not justify preselecting the number or identity of ordinary combinations. Check the configured limit, the below-limit no-overflow guarantee, and actual output together rather than inferring a retention order from the special attribute.

A normal total can coexist with lost detail

An overflow aggregation can preserve contribution while discarding the full tenant, route, or error-category identity. An alert filtered to a new tenant may miss its overflowed activity, while a total that includes overflow appears normal. The queries ask different questions: volume and attribution. Make overflow visible rather than silently filtering out its special attribute.

Increasing the limit by orders of magnitude may preserve more combinations temporarily while increasing resource pressure. It does not fix an unbounded identity dimension. If operational decisions depend on a finite plan category, consider filtering tenant IDs and retaining that category, with event correlation handled by access-controlled logs or traces. Choose dimensions by the action they enable.

Filtering has a cost too. Removing tenant identity intentionally combines requests that share the remaining attributes; it does not recover detail. Document what those attributes can still answer and where individual event evidence lives. Limits, privacy, and diagnostic granularity belong in the same design.

Can an overflow value recover the original tenants?

The synthetic value alone cannot reconstruct identities already combined. Knowing that ten new tenants exist does not reveal how requests were distributed among them; different distributions can produce the same total. Recovery needs independent event evidence rather than another query over the overflow value. In particular, it should not be relabeled as zero requests for other tenants.

Temporality and instrument type also matter. The retention guarantee for earlier synchronous cumulative combinations cannot simply be applied to synchronous delta aggregation; the specification permits an arbitrary attribute subset there. Asynchronous instruments have a separate recommendation to prefer first-observed attributes in callbacks. An Observable current-value measurement should not be interpreted using this Counter's 22-event arithmetic.

Proposed verification should retain the exact SDK version, View, Reader, temporality, input attributes, and raw SDK export, then check whether the Collector and backend preserve the overflow point. Compare inputs before and after filtering and confirm that the limit applies to the intended stream. Include a below-limit boundary case so ordinary missing data is not mislabeled as overflow. No implementation outcome is claimed before those checks run.

For why dimensions become unbounded, see metric label budgets. For aggregation intervals, see temporality boundaries. First choose the dimensions needed for a real operational action, then treat overflow as an observable loss of detail. A surviving total does not establish trustworthy attribution.
