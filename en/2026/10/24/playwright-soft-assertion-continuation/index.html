Playwright soft assertions: set a boundary before execution continues

Separate independent observations, write prerequisites, timeout budgets, and cleanup when using Playwright soft assertions.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-24 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • A failed soft assertion fails the test while later statements can still have side effects.
  • Establish hard prerequisites and place a checkpoint before a dependent write.
  • Cleanup needs retained fixture identity; soft assertions do not soften action exceptions.

When expect.soft fails, Playwright Test records the error and continues with subsequent statements. The test is still marked as failed. Soft assertions are useful for collecting independent observations in one run. If a later action relies on a failed prerequisite, particularly before a write, payment, or deletion, insert a hard assertion before proceeding. Choosing soft assertions also means choosing what may still happen after failure.

Execution continues; the prerequisite does not become trustworthy

Playwright's Assertions guide distinguishes ordinary and soft assertions and limits soft assertions to the Playwright Test runner. This is error collection within that runner, not a recovery mechanism for arbitrary JavaScript exceptions. The live guide was checked on October 24, 2026. None of the examples here was executed, and there are no measured pass rates or timings.

Consider a hypothetical order review showing the recipient, address, and delivery estimate. All three fields display the same already-loaded order, and inspecting one does not alter the others. If the recipient is wrong, inspecting the other fields can help distinguish a component defect from incorrect order data. Soft assertions can preserve those observations instead of ending the run at the first mismatch.

Clicking Pay is a different decision. An incorrect recipient or address invalidates the premise for proceeding. The button may remain actionable, and the script may finish its steps, without making payment appropriate. A red final report cannot retract a request sent earlier in the run. Permission to perform the action must be expressed before the side effect.

Put a checkpoint after independent observations

This unexecuted TypeScript illustration assumes an isolated fixture, a sandbox payment, and example locators and text. Both ordinary and soft web assertions need to be awaited; otherwise the intended ordering is lost.

import { test, expect } from '@playwright/test';

test('review before sandbox payment', async ({ page }) => {
  await page.goto('/orders/example-42/review');
  await expect(page.getByTestId('order-id')).toHaveText('example-42');
  const fields = [
    ['recipient', 'Example recipient'],
    ['address', 'Test address'],
    ['delivery', 'Next day'],
  ] as const;
  for (const [id, expected] of fields) {
    await expect.soft(page.getByTestId(id)).toHaveText(expected);
  }
  expect(test.info().errors).toHaveLength(0);
  await page.getByRole('button', { name: 'Sandbox payment' }).click();
  await expect(page.getByText('Accepted', { exact: true })).toBeVisible();
});

Order identity is a hard prerequisite: the remaining checks assume this is the intended order. Collecting address errors from a different order would mislead the investigation. The three soft assertions then retain separate observations. The checkpoint requires the current error collection to be empty before sending payment. The final message establishes only what the page displays; persistent payment state needs whatever additional checks the sandbox contract requires.

The guide demonstrates checking soft failures through test.info().errors. This is the test's recorded error collection, not a counter automatically scoped to this group of fields. Earlier soft failures also prevent the zero-length check from passing. Decide whether that is the desired policy: should any earlier failure prohibit submission, or should unrelated goals be separate tests?

Saving the previous error count and checking only for new errors can accidentally exclude a failed prerequisite from the gate. A local policy is defensible only if the earlier errors are demonstrably unrelated to this write and data ownership and isolation are clear. Otherwise, splitting the test is easier to review. An error count helps implement a checkpoint; the author still chooses the business prerequisites.

A soft failure can still spend its waiting budget

A soft web assertion is not necessarily one immediate check followed by a skip. Auto-retrying matchers still observe their condition within the configured budget before failing and continuing. Several missing fields checked sequentially can spend several budgets. Making every element soft can produce a long report full of errors with one shared cause.

Identify shared prerequisites first. A page that never loaded, an expired login, or the wrong order identity usually makes dozens of field checks less informative. Keep a small set of hard prerequisites, then use soft assertions within the established context. Check timeout settings in the actual environment; this example makes no total-duration promise, and an unlimited wait would hide an incorrect entry point.

Should the failure checkpoint also block cleanup?

Required resource cleanup should usually be handled by fixtures or cleanup hooks, with independently limited permissions and object identities. A hard assertion may stop the test body while fixture data still exists. If deleting that data is merely the last line after payment, an earlier failure may leave that line unreachable. Removing the business gate would not solve the cleanup design.

Cleanup should not blindly trust whichever order identifier happens to be on the page: the identity assertion may be the failure being investigated. Use the exact identity retained when creating the fixture and clean up only within the authorized scope. Real payments and destructive paths need explicit test environments and data isolation; a test being destined to fail is no justification for continuing side effects.

A proposed verification needs at least two inputs. Deliberately mismatch one field and confirm that other independent observations are recorded while no payment request is sent. Then make all fields correct and confirm that the request occurs only after the checkpoint. Also fail page loading to check that the hard prerequisite prevents a cascade of unhelpful field errors. Retain both assertion reports and side-effect request records, rather than relying on a final success message. These checks have not been run.

Soft assertions do not soften ordinary action failures. A later click can still throw and stop execution. Keep independent observation groups read-only where possible. If observing the next field requires changing the page, establish whether that change alters the object being inspected; otherwise the additional failures may be produced by the test itself.

The existing article on asynchronous assertion waiting concerns when to read a result. This article adds the decision about what execution may do after the result fails. Mark the first write in a test and work backward to its required checkpoint; that is a more useful starting point than classifying fields as important or minor.
