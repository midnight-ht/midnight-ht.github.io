After Setting SameSite, Which CSRF Paths Still Need Verification?

SameSite restricts some cross-site cookie delivery. Review write routes, request methods, origins, tokens and resulting state instead of treating one attribute as CSRF acceptance.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-26 · Estimated read 24 min
Translations
zh-CN en

Article

After setting SameSite, review CSRF protection on every route that changes server state. SameSite=Lax still permits a class of cross-site top-level safe-method navigations to carry cookies. If an account-update endpoint performs a state change on GET, the cookie attribute does not make that endpoint safe. Start with the write routes and their actual request contexts, then assign separate responsibilities to tokens, origin checks, Fetch Metadata and cookie attributes.

The account service below is hypothetical. It does not describe this site's authentication architecture, and no browser attack test was run. The matrix is a proposed acceptance plan, not a test result.

SameSite changes when a cookie is sent, not what an endpoint does

The core CSRF condition is that a browser automatically carries an identity credential while the server interprets the request as intent from the logged-in user. If an external page can induce a browser request and the endpoint changes state merely because a session cookie is present, the browser may supply identity without proving that the user confirmed the action on the current page. Object authorization remains a separate question: even an intentionally initiated request must be checked against the caller's permission on the target object.

The attribute controls cookie delivery; it does not prove request intent. MDN's description of Lax contains an easy-to-miss condition: a cross-site request may still carry the cookie when it is a top-level navigation using a safe method. GET is generally a safe method. So the idea that “Lax blocks cross-site writes” holds only when the endpoint also respects method semantics. If a GET unsubscribes, deletes a draft or changes account settings, the defect is that the route uses a read method for a write—not that the browser failed to perform the application's security review. OWASP's CSRF guidance specifically calls for reviewing safe-method routes for state changes.

Strict suppresses cross-site cookies more aggressively, but that can affect the sign-in experience when users arrive through external links. A request from an email or document may initially lack the session context, which may require another load or reauthentication flow. Evaluate the cookie choice together with legitimate sign-in, payment-return and identity-provider callback paths, rather than looking only at attack requests. Browsers may apply different defaults when SameSite is omitted, so state the policy explicitly instead of treating a client default as acceptance evidence. If a product must send cookies in a cross-site context, None also requires Secure; review which origins can attach credentials.

Also distinguish same-site from same-origin. A browser's site relationship does not mean that every subdomain under a registrable domain has the same security owner. Suppose app.example.test stores a session cookie while uploads.example.test hosts user-controlled content. Some requests initiated by the latter may still be treated as same-site. Even if the cookie has no broad Domain attribute, the request's destination host and its same-site classification are separate checks. A SameSite boundary cannot establish subdomain ownership, hosting responsibility or compromise risk for the organization.

The acceptance unit is a write route, not the cookie settings page

Turn the review into a route matrix. Imagine an account service with three actions: change an email address, export account data and close the account. Record the HTTP method and handler for each route; the credential used for authentication, such as a session cookie, authorization header or both; where a request may originate; and the expected business change on success. Also specify which data, audit entries and side effects must remain unchanged on rejection.

This table exposes method-semantics problems quickly. Exporting data may be read-only, although access to the downloaded file still needs its own authorization check. Changing an email address or closing an account must use a non-safe method; GET should display a confirmation page or read state only. If an unsubscribe link in an email submits the change immediately, prefetching, link scanners or an accidental click can trigger it even without a malicious site. Make the link display a confirmation step and submit the mutation separately. That respects GET semantics and gives token and identity checks a defined place.

Record authentication state too. An anonymous visit may redirect to sign-in; after the callback, does the application still execute the same action? Does an administration route use a different middleware chain? Does a mobile client rely on cookies at all? Can a reverse proxy remove Origin or Sec-Fetch-Site? The same URL may have different request contexts across sessions, cache nodes and proxy paths. Checking the cookie on the homepage cannot answer whether each write route is actually protected.

Record Lax in the matrix as one layer, not as the conclusion for the whole row. If a session cookie only needs to be used on the host that set it, explicitly choose a policy that fits the flow and consider the __Host- prefix. In supporting user agents, that prefix requires Secure, Path=/ and no Domain attribute, narrowing which hosts can set or override the cookie. It does not validate request intent and cannot fix a state-changing GET, cross-site scripting or object-level authorization. Cookie attributes limit credential exposure; the server must still decide whether the request may execute.

Forms, JavaScript APIs and subdomains need different evidence

Traditional HTML forms can send simple cross-site requests. CORS does not guarantee that the server-side effect never happened. A synchronizer token is useful because the server validates it: a page or session associated with the request supplies an unpredictable token, and the server compares it before performing any partial mutation. Missing or invalid tokens should be rejected, and the review should confirm that neither data nor side effects changed. Keep tokens out of URLs and ordinary logs. When using a framework's built-in protection, verify which forms, administration routes, APIs and exception paths it covers.

If the frontend uses fetch for a JSON API, a custom request header or another non-simple request can cause a cross-origin preflight. A restrictive CORS allowlist can also limit which origins receive credentialed access. But “the attacking page cannot read the response” does not mean “the server did not process the request.” Simple form requests may still arrive. If the server accepts uncontrolled credentialed origins, or a write route does not require the expected custom header, there is a gap in the chain. A cross-origin API should state which origins are allowed, whether credentials are included, which methods and headers are accepted, and which request context the server validates on protected routes. CORS is a configuration constraint, not a way to outsource the entire CSRF problem to the browser.

If an API accepts only JSON, can CORS replace a CSRF token?

Do not close the CSRF review just because the request body is JSON. Check that every state-changing route rejects simple requests, requires the expected custom header, restricts credentialed CORS to reviewed concrete origins, and has no compatibility form or URL-encoded entry point. If a route still accepts a simple request or allows credentialed requests from arbitrary origins, the API's design intention does not constrain the handler. For a tightly constrained API, a custom header, preflight and origin validation can contribute to the defense. Whether a token is also required depends on the architecture and threat model, not on the content-type field alone.

Fetch Metadata can add another origin signal. Sec-Fetch-Site distinguishes contexts such as same-origin, same-site, cross-site and user-initiated navigation, but proxies may remove the header and some clients may omit it. Define the missing-header behavior: a sensitive write may reject an unknown context, or it may fall back to Origin/Referer and token validation. “No cross-site marker was observed” must not silently become “trusted.” If the server varies responses based on these request headers, caches must distinguish the variants; otherwise an edge cache or proxy may reuse a response generated for another context.

Several green checks can still miss a path

A state-changing GET is the first failure to look for alongside Lax. The cookie panel can show the expected attribute while an attacker induces a top-level safe-method navigation. Fix the route semantics and confirm that GET, HEAD and other safe methods only read data. Second, a registrable domain may contain subdomains with different levels of control. The parent-domain policy can look consistent while an old service, user-content host or abandoned DNS record lets an attacker influence a same-site request. Third, a token may be checked only by the primary form handler while an administration endpoint, mobile compatibility route or old API bypasses the middleware.

Fourth, a team may treat the status code as its only evidence. An invalid request can receive 403 after the backend has already written some data, sent an email or queued a job. Conversely, a valid request may redirect without meaning the write failed. Acceptance should compare business state before and after the request and inspect transactions, logs, queues and notifications. The test matrix should include missing and invalid tokens, trusted and cross-site origins, same-site but cross-origin requests, missing Fetch Metadata, and sign-in or callback paths. These tests were not run for this article, so it reports no browser logs or success rate.

Finally, CSRF protection does not replace XSS protection. A script already running in the trusted origin may call the application's own API, read a page token or issue a request through legitimate JavaScript. That cookie rule cannot tell whether the action came from a genuine user click. The same cookie policy also does not replace object authorization: a token or origin header does not prove that the caller may modify the target record.

When can SameSite be the main defense on its own?

The OWASP guide describes only a narrow conjunction of conditions under which relying on SameSite alone may be reasonable: no host or service under the application's registrable domain is outside the team's control; no state change uses GET or another safe method; the session cookie uses Strict, or Lax together with the __Host- prefix and a strict GET audit; write endpoints also verify Origin or Referer; and the team accepts the residual risk for clients that do not enforce SameSite. If any condition is absent, the guide should not be read as general permission to rely on the attribute. OWASP recommends combining additional controls such as tokens or a double-submit pattern in that case.

Before choosing controls, ask three questions: does the browser automatically attach authentication? Can an untrusted context trigger the request? Will the server change state based on the cookie alone? If the answers indicate risk, select tokens, origin validation, Fetch Metadata and cookie attributes according to the form, JavaScript API, subdomain and client-compatibility paths. The acceptance record should preserve the route, method, credential source, site relationship, defense, resulting business state on rejection and fallback for missing headers. That is a more meaningful security conclusion than “the cookie has Lax.”

Review this alongside object-level authorization boundaries: show separately that the request came from an expected context and that the user may modify the object. A token or origin header cannot prove the latter.
