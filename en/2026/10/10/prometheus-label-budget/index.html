Can one metric label per order make monitoring behave like an event database?

In Prometheus, label-value combinations identify time series. Before adding unbounded order dimensions, estimate the combination ceiling, inspect histogram behavior, and validate observed series growth.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-26 · Estimated read 17 min
Translations

Article

Key takeaways

  • Metric name plus label values define a series identity; unbounded order, user, and request values should not become default metric dimensions.
  • A combination ceiling is not the observed active-series count. Prometheus’s below-10 / above-100 guidance prompts investigation; it is not a hard capacity threshold.
  • Classic histograms add configured bucket, sum, and count series; individual lookup usually belongs in controlled event evidence, with its own access and retention limits.

Adding an order label can make one investigation easier, but in Prometheus a label-value combination is part of a time series identity. As order IDs keep changing, the set of series changes too. Event-level evidence such as logs or traces is usually a better place for order identity. That is a separation of responsibilities, not a claim that those systems are free or that Prometheus becomes a full event database.

Why a label value can create another series

The Prometheus data model identifies a time series by a metric name and its label key-value set. Labels such as method, route, and result combine; each value combination that actually appears has its own series identity. Changing a label value creates a different series. Scraped samples attach to those series. An old value disappearing does not mean its historical samples are immediately deleted; retention, compaction, and block storage depend on the configured deployment. It is therefore useful to distinguish two questions: how many series are active now, and how many new series keep turning over during a time window.

According to the Prometheus data model documentation, changing any label value creates a new time series. The metric and label naming guide adds that each distinct key-value combination is a series and warns about unbounded dimensions such as user IDs and email addresses. Labels are not universally harmful. Labels make bounded aggregation possible; risk comes from the number and rate of possible combinations and from the memory, processing, disk, and network work required to scrape those series.

Estimate the combination ceiling, then inspect the real distribution

The following is a hypothetical example to explain a budgeting method, not a measurement from this site or a production system. Suppose a request-duration metric distinguishes eight normalized route templates, five HTTP methods, three outcome classes, and up to 10,000 order IDs. If every combination appeared, the upper bound would be eight times five times three times 10,000, or 1.2 million combinations. Business constraints usually make the observed combinations fewer than this Cartesian product; the upper bound is a warning, not a claim about the actual active series count.

An order ID can correspond to only a few routes or results and still be an unbounded dimension. As orders keep arriving, label sets keep changing; an old order’s series identity is not reused by a new order. If the duration metric is also a classic histogram, each base label combination expands into bucket, sum, and count time series; the bucket count depends on configuration. Prometheus documentation explains that each configured classic-histogram bucket produces a series, while native histograms use composite samples. It does not support a universal “bytes per order” estimate: histogram type, bucket configuration, scrape path, retention, and deployment implementation all affect actual cost.

As a rule of thumb, Prometheus instrumentation guidance recommends: keep most metric cardinalities very low, typically aiming below ten; investigate reducing dimensions or moving analysis to a general-purpose processing system when a metric exceeds or could grow beyond one hundred. This is not a fixed capacity line. It does not imply that fewer than ten is always safe or that more than one hundred always fails. Concrete limits depend on the Prometheus version, scrape targets, scrape interval, other metrics, storage resources, and query patterns. Treat the numbers as a review prompt, not an alert threshold.

Metrics identify a class; event records identify an occurrence

A bounded label set can preserve operationally useful categories, such as aggregating request totals and latency by route template, method, and outcome class. Normalize routes before instrumentation to a template such as /orders/{id} rather than exposing each full order URL. Map exceptional paths to an explicit unknown class and monitor growth in that bucket, so a broken parser is not silently hidden. Raw error text, user IDs, order IDs, and random request IDs usually should not be metric labels: they may grow continuously and may contain personal or business-sensitive data.

For “why did this particular order fail?”, begin with aggregate metrics to identify the affected operation class and approximate onset, then use access-controlled log or trace context to locate the request. Order IDs in those records still need data-minimization, access, retention, and redaction policies. If teams need frequent, durable queries by arbitrary order, evaluate an event store or business query capability explicitly instead of making metrics serve as an event-search interface they were not designed to be.

This also explains why “never use labels” is not a general solution. If different result classes require different responses, merging them can make an alert useless. If route groups are too coarse, an anomalous latency becomes difficult to assign. Keep labels that are bounded, stable, and change an operational decision; remove dimensions that do not alter aggregation or response. The Prometheus cardinality guidance both recommends labels for aggregatable categories and notes the resource costs of each label set, advising investigation of alternatives for very high cardinality.

Histograms amplify the cost of a high-cardinality dimension

Latency distributions can be more useful than request totals, but a classic histogram is not one series per metric name. Each base label set produces bucket series plus sum and count series; configuring more boundaries adds bucket series. Adding order IDs to a latency histogram therefore expands the entire group of bucket series across orders and other dimensions. Native histograms have a different representation, so classic per-bucket counting cannot be copied directly. The choice also depends on the client library, Prometheus version, transport path, and query needs.

Differences in series count, bucket configuration, and queries for classic and native histograms are described in the official histogram guide. More classic buckets provide more query options and precision but also more individual series, while native histograms use composite samples. A deployment decision should include metric type and the data path, rather than looking only at a label-count chart.

Validate the label budget before rollout

Start code review by listing the source and upper bound of each label value. Then inspect combinations in test traffic or a local /metrics exposition. The following PromQL is an unexecuted inspection example and must be adapted to the metric names under review:

count by (__name__) ({__name__=~"http_.*"})

It counts matching series by metric name at an instant; it does not count every unique combination that ever existed historically. Detecting series turnover requires time-window analysis alongside active-series and newly-created-series signals, scrape volume, and query load. Verify which internal metrics the chosen Prometheus version exposes instead of treating internal metric names from different versions as a stable interface.

Test inputs should cover route templates, outcome categories, exceptional paths, and several batches of random order IDs. Check that raw IDs or dynamic URLs do not leak into labels; also cover the unknown bucket, a deployment change, and histogram configuration. Verify that queries aggregate as intended and that event identity has not slipped into the label set. Separately check that order IDs in logs and traces follow access, redaction, and retention policies. Prometheus was not run for this article, and no query or resource measurement was performed; these are proposed checks, not execution results.

After rollout, compare active series, new-series turnover, scrape samples, and query load with the pre-release baseline, tying each added dimension to a bounded need. If only individual lookup requires an order ID and aggregation does not, preserve the label budget and keep that identity in controlled event evidence. Read alongside service reliability indicators and incident learning to see how metrics help establish impact scope, and metric temporality to check how counters are interpreted across collection intervals. Each label should answer an operational question; when its upper bound is simply “as many as there are orders,” leave it out of metric labels by default.
