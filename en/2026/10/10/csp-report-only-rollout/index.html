Zero CSP Reports Are Not a Green Light to Block: Verify Three Things First

Zero CSP reports do not prove enforcement is ready. Verify response headers, report collection and critical workflows, then block in a bounded, reversible scope.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-26 · Estimated read 31 min
Translations
zh-CN en

Article

Zero CSP reports are not, by themselves, a reason to enable blocking. They may mean that the requests observed so far did not violate the candidate policy; they may also mean that critical workflows were never exercised, or that reports were not delivered or were discarded by the receiver. Before enforcing a policy, independently verify that the intended response carries it, a controlled report signal reaches the collection pipeline, and representative user tasks have been tested. Then begin enforcement in a bounded scope with an observable rollback path.

The administration portal below is a hypothetical example. This article does not configure CSP on this site and does not claim that browser tests or a production rollout were performed.

What does an empty report stream actually tell you?

Content-Security-Policy-Report-Only asks the browser to parse and monitor a policy without blocking requests because of that policy. The W3C Content Security Policy Level 3 document, published as a Working Draft on 27 October 2026, distinguishes the enforcing response header from the report-only header. It describes observing violations and moving to enforcement after gaining confidence. The draft also specifies that the report-only policy is a response-header mechanism; it is not supported through a <meta> element. This is a work-in-progress draft, not a finalized W3C Recommendation. (W3C CSP Level 3, Working Draft of 27 October 2026)

An empty dashboard therefore says only that the collection interface currently displays no events. It does not answer three separate questions: did the candidate header reach the real page, did the browser generate and deliver reports successfully, and did anyone exercise requests that would violate the candidate? Combining these questions turns “the monitor is quiet” into an unsupported claim that “the policy has no problems.”

A further limit is easy to overlook: the W3C Reporting API describes delivery as best-effort and explicitly says it is not guaranteed. Network conditions may prevent reports from reaching their endpoint, and user agents may decline to deliver them. Receiving one controlled report can show that a particular path worked during that test; it cannot prove that every later production report will arrive. (W3C Reporting API, Working Draft of 11 June 2025, §1.1)

The browser’s reporting directive and endpoint configuration must also match. MDN’s CSP implementation guide recommends testing with Report-Only first. The guide was last modified on 4 September 2026. It describes configuring the newer report-to path with Reporting-Endpoints while retaining the older report-uri for browser compatibility. MDN marks report-uri as deprecated, but also notes that report-to does not yet have full cross-browser support. “Preferred” should not be read as “every browser you support uses the same reporting path.” (MDN: CSP practical implementation guide, updated 4 September 2026)

If a site already has an enforcing policy and adds a new Report-Only candidate, the two policies have different jobs: the existing enforcing policy can still block requests that it disallows, while the candidate reports requests that it would disallow. Multiple enforcing CSP policies are not “last header wins”; a request must satisfy every enforcing policy. The rollout record should say which headers the browser actually received, not just quote the final text in a configuration repository. See the site’s explanation of how multiple enforcing CSP policies intersect.

Does the candidate reach the responses that matter?

Do not start with the report counter. Treat the candidate policy as a versioned release artifact: save its complete header value, change ID or content hash, intended routes, owner and rollback version. Then inspect actual page responses rather than only the CDN rule file or application repository. A response header can be assembled by the application, reverse proxy, edge rules and cache. The same route may return different headers before and after login, in different locales, or on a cache hit versus a miss.

Suppose an administration portal has a login page, a report page and a rich-text editor. A test matrix should list the URL, identity state, important action, expected policy version and browser version for each case. An anonymous request to /admin/editor may redirect to a login page, so the policy under inspection is the one on the login response. After authentication, the editor may be served through a different cache path. Seeing the candidate header on the homepage does not establish that those later documents carry it too.

The question is not whether the pages share an origin; it is whether each response class actually carries the expected policy. Record the status, final URL, enforcing CSP headers, Report-Only headers, Reporting-Endpoints header and policy version for each response. Check both cache hits and misses. If routes intentionally use different policies, write those differences into the matrix. A Report-Only policy placed in a meta tag does not pass this gate because the specification does not support that delivery method.

This step may explain the empty dashboard immediately: an edge rule omitted the header on one route, a proxy forwarded the enforcing header but not the reporting endpoint, or a page version is out of sync. Until the header reaches the intended response, the absence of reports is not evidence about the policy. Fix the delivery path before observing further; there is no need to loosen every policy or add every observed source to an allowlist first.

Can one controlled violation reach queryable data?

Use an isolated test page and a team-controlled test resource to create a predictable, harmless violation of the candidate policy. For example, the page can request a static image from a team test domain that is absent from the Report-Only candidate’s img-src. Because the policy is report-only, it should not block the request due to that candidate. This does not require injecting a script or harmful content. First confirm that another enforcing policy will not already block the same request, or the test will be observing the existing policy instead.

Then verify each link from configuration through storage: the response carries the candidate and the correct reporting endpoint name; the name referenced by the policy matches the name defined in Reporting-Endpoints; the browser-generated event reaches the receiver; and the receiver accepts, parses and queues or stores it so that the test event can be found in a queryable view. Record the policy version, test browser, page, event time, endpoint response and final query location. This article has not run the test for readers, so it does not invent a “successful” log line or prescribe one universal HTTP status code.

Reporting API delivery may happen asynchronously after the page action. “I clicked and did not see a record immediately” is not a sufficient test. More useful end-to-end evidence is that the browser generated the expected signal, the receiver recorded the raw event, and the aggregation layer did not discard it because of a schema change, rate limit or filter. The person investigating later should be able to locate the event by policy version and route. If a vendor dashboard shows only counts aggregated by domain, check whether the original event preserves enough context—such as effective directive, disposition and page context—to diagnose it. Handle URLs, user-agent strings and other potentially sensitive report fields according to privacy requirements.

Some collection failures hide in mismatched configuration rather than a fully unavailable endpoint: a response refers to csp-endpoint, but the endpoint list defines another name; the request reaches the API but disappears during JSON validation or queue writes; only one browser’s legacy or newer reporting path is connected; or a cache node still serves an older header. Searching application code for report-to cannot rule these out. A test event should reveal the actual response and pipeline behavior rather than invite conclusions from configuration text.

If the controlled signal does not reach the final query location, the result is “reporting is not yet verified,” not “there are no violations.” Fix the chain, send another controlled signal and record each target browser separately. Also state the test’s limits: one successful event demonstrates connectivity for one browser, response and endpoint at that time. It does not prove that all real devices, networks and sessions will deliver reports. The Reporting API’s best-effort contract is why reports cannot be the sole security acceptance channel.

Which critical tasks are missing from the dashboard?

No policy violation and no business failure are different things. An editor that nobody visited produces no report. Loading only the homepage will not cover login redirects, uploads, exports, payment confirmation, administrative actions or reauthentication after a session expires. Start from user tasks, not the number of URLs. List important identities, states and interactions, then note the script, style, image, connection, worker or navigation sources each task exercises.

In the hypothetical portal, exporting a report first calls a same-origin API, which returns a file; the editor loads a partner-hosted script and starts a worker. Opening the page may cover the initial HTML and some scripts without triggering the export request or initializing the worker. If the candidate tightens connect-src or worker-src, those actions expose the difference. The evidence should say which request was observed during which user action and what the page ultimately completed—not simply “page visited.”

Prioritize by both failure impact and likelihood, but low frequency does not automatically mean dispensable. A failed admin login and a missing decorative image have different costs; a rarely used financial export may still be critical. Define completion evidence for each task, such as reaching the correct page, loading complete data, downloading a valid file or saving successfully. The candidate’s CSP reports show policy differences; task outcomes show whether those differences harm the work.

Reports may also include browser extensions, proxy rewrites and sources outside the site. They do not necessarily indicate an attack, but they should not automatically become allowed sources either. Use the document URI, effective directive, blocked target, browser and business context to distinguish an application dependency, an approved third-party service, extension injection or an unknown source. An unexplained first-party request in a critical workflow should remain a blocker. When the source is unclear, adding its domain to a general policy preserves uncertainty instead of resolving it.

Make the limits of the coverage matrix explicit. Group by supported browser families and versions, identity state, region or network, cache state and application version; record tasks performed and routes not covered. Chrome for Developers’ Reporting API support table shows that CSP reporting through the newer report-to/Reporting-Endpoints path is not equivalent to the legacy report-uri path, and support differs among browsers. That table concerns the interface described on that page; it does not replace checking the browsers and versions your own project supports. (Chrome for Developers: Reporting API support and configuration)

After observation, verify blocking in a bounded scope

Passing the three observation gates gives you a reason to try enforcement; it does not prove safety for every route, customer network and device. Choose a page or stable user cohort with controlled risk. Record which candidate version it will receive, who will observe task outcomes, how failures correlated with the candidate will be detected, and what condition pauses or rolls back the change. The rollout scope depends on deployment capabilities and business impact; no traffic percentage or number of observation days fits every site.

Suppose the administration portal has an editor entry point separate from reporting. The team could let controlled accounts receive the new enforcing header while other users keep the known policy. If the deployment system cannot split by account, a lower-risk route might serve as a stage, but check whether dependencies are shared across routes: shared scripts or APIs may not be isolated just because pages have different paths. In either case, use a stable policy version and inspect the actual response header. “The configuration was deployed” does not prove that the test account received it.

Continue watching user tasks and browser CSP events during enforcement; do not expect the report counter simply to reach zero. A request that is actually blocked, a business error, task completion and security telemetry each provide different evidence. If login or save fails and the effective directive matches the candidate policy, pause expansion and restore the previously saved policy. If the failure has another cause, investigate it before attributing it to CSP. Rollback must resend the exact known header and verify cache propagation; having a rollback configuration does not prove that users have received the restored policy.

Distinguish two kinds of policy failure. An unhandled first-party resource reported during observation means there is still work to do; a critical task broken under enforcement means the trial scope or policy needs rollback. Neither should be “fixed” by adding broad allowances such as *, https: or unsafe-inline. If a candidate uses nonces, the header and permitted script tags also need to match for each response. The site’s article on CSP nonce and response-cache scope covers that separate boundary.

What evidence belongs in the change review?

Replace “we waited a few days and saw no reports” with a record another engineer can verify: the exact candidate policy and hash; the responses and cache variants where it was observed; the controlled resource used to produce an expected signal; where the receiver and aggregation view confirmed the event; the browser versions, identity states and critical tasks covered; user paths or third-party dependencies still unknown; and the first enforcement scope and rollback condition. Mark each empty field as unknown, not run or blocked rather than filling it in as passed.

A zero report stream can coexist with a decision to move to the next stage, but only after reporting and workflow coverage have been independently verified. The zero itself is not a release gate. Before a staged rollout, use the site’s guidance on risk-based quality gates to check whether validation covers the consequences that matter, and how to prove a deployment worked and rollback is available to retain the policy version, actual response and rollback evidence. Put the specific evidence and remaining blind spots in the change record before deciding who will enforce the policy and where.
