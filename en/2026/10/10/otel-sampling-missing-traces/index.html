Tail sampling cannot recover traces already discarded upstream

Tail sampling can judge only spans a Collector receives. Follow SDK drops, routing, late arrivals and buffer eviction to locate where an error trace became incomplete.

Article

No. Tail sampling can wait for some spans and then decide whether to keep a trace based on status, duration or attributes. It cannot reconstruct a span that was never created, recorded, exported or delivered to that sampler. To explain why an error trace is incomplete, inspect the collection path before the sampling decision as well as the decision itself. This article draws on OpenTelemetry specifications, concept documentation and the Collector Contrib tail sampling processor guide. No Collector was configured, and no load test or resource-cost measurement was performed. Processor documentation changes by version; check the distribution and version actually deployed before relying on a parameter or metric name.

Tail sampling judges the evidence it receives

A trace is not necessarily exported as one complete object. The OpenTelemetry data model describes spans as individual operations. A consumer groups received spans by Trace ID and uses parent-child relationships and links to assemble a trace. The trace shown in a backend is therefore a view of the data that arrived. The specification calls a trace incomplete when only some of its spans are available and lists common causes: sampling, filtering, failed or delayed export, span, queue or backend limits, and operations that have not finished yet. Facts F1 and F2

That defines the limits of a tail policy. The Collector tail sampling processor evaluates trace data it has received. The sampling concepts give examples such as traces containing errors, overall duration and selected attributes. Compared with a head decision at request start, it can use information that appears later. “Later,” however, does not mean it has every span from the system. Fact F3

Imagine a request passing through an entry service, an order service and a database. The entry span is exported; the order service's SDK makes a DROP decision and does not record its child span. If the database SDK inherits the unsampled context and drops its span too, the Collector may receive only the entry span; the child service's sampler determines the exact behavior. Adding a tail rule to retain traces with ERROR changes nothing when no error span is in the input set: the processor can only decide from the evidence it has. The SDK specification says that when IsRecording=false, span data is discarded and span processors do not receive it. Once a stage drops that data, a later processor cannot recover its attributes, events or status. Fact F4

A span recorded by the entry service can still disappear later. It may remain in an export queue, be dropped by queue limits, meet a Collector filter before the tail sampler, or fail to reach the receiver after a network problem. The data model also lists failed or delayed export and configured span, queue or backend limits as common causes of incomplete traces. Follow the path—span creation and recording, SDK export, receiver, earlier processors, tail sampler, backend—and check each boundary. The policy file alone cannot show where the evidence went missing. Facts F2 and F4

Routing can split one trace across instances

The tail sampling processor groups spans by Trace ID and holds state while it waits for a decision. Collector Contrib's processor documentation requires all spans for one trace to arrive at the same Collector instance. Otherwise each replica judges only its own fragment. A gateway guide shows a two-tier pattern: a first-tier Collector uses a load-balancing exporter keyed by trace ID; a second-tier Collector performs tail sampling. Facts F5 and F6

Consider three spans. If entry, order and database spans all reach Collector A, it may see the ERROR status and keep the group of spans that arrived. If an ordinary load balancer sends entry to A, order to B and database back to A, A and B do not automatically merge their in-memory buffers. A may see an entry and database fragment with no error; B may see an isolated error fragment. Neither result is the complete trace. This is a mechanism example, not a report of a tested environment.

Scaling makes routing an ongoing concern. Trace ID routing avoids arbitrary distribution while the routing topology is stable, but service-discovery membership changes can remap traffic. Spans already in flight and newly arriving spans can then reach different replicas. The agent-to-gateway guide describes multi-instance tail sampling as an advanced deployment with caveats around routing changes and decision consistency. It recommends considering a single, well-resourced tail-sampling gateway unless a robust sticky-routing strategy exists. Fact F7

A wait window waits; it does not recall

A sampler commonly buffers a trace for a period before deciding. The current Collector Contrib main-branch guide defines decision_wait as the wait used by the timer path. Under the trace-complete strategy, accumulated data is evaluated when the timer is handled; a longer wait generally means retaining state for longer. The guide currently lists 30 seconds as the default, but that is version-specific processor documentation, not a universal guarantee across distributions or strategies. Check which processor version and feature gates are present in the actual binary before configuring it. Fact F8

With a short window, a child span may arrive after the decision. A longer window gives more late data a chance to arrive first, but it cannot make discarded data appear. The processor guide says that a late span arriving while the original decision remains in the buffer inherits that decision; it does not change the policy evaluation already made. A decision cache can remember the outcome for a trace ID after span data is released, but it stores the decision, not the original trace contents. It is not a recovery mechanism. Without a cache entry, or after eviction, a late span may be buffered again and produce a new decision, so different parts of one trace can be treated inconsistently. Fact F9

Choosing a wait duration is a measured trade-off, not a rule that a larger number is always safer. Observe real span arrival delays, trace duration, buffer use and decision-processing latency. The processor guide documents metrics including otelcol_processor_tail_sampling_sampling_trace_dropped_too_early, otelcol_processor_tail_sampling_sampling_trace_removal_age, otelcol_processor_tail_sampling_sampling_decision_timer_latency and otelcol_processor_tail_sampling_sampling_late_span_age. These can help locate pressure within the sampler and quantify late arrivals; by themselves they do not prove that upstream spans were delivered. Fact F10

Buffer eviction and per-trace limits create different gaps

Adding replicas does not necessarily increase the buffer available to each trace. When traces are routed by ID to one replica, that instance's num_traces, memory, CPU and decision latency together affect whether it can retain enough state during the window. The Contrib guide describes a circular buffer that removes the oldest trace when num_traces is reached; a trace can be dropped before decision_wait expires. It also documents maximum_trace_size_bytes, a per-trace limit that immediately drops a trace from the tail sampler if it grows too large. The first case is many traces competing for a finite buffer; the second is one oversized trace. One setting may not solve both. Facts F11 and F12

So do not respond to a missing error trace by immediately doubling the wait. If early-eviction metrics rise, a shorter wait may reduce buffer pressure, but it also makes decisions sooner and may exclude slow spans. Increasing capacity uses more memory. If the per-trace size limit is being hit, increasing the number of buffered traces may not help; determine whether the trace has many spans, oversized events or attributes, or needs a specific protection policy. The documentation recommends fast downstream consumption so later pipeline work does not add decision latency. Actual capacity, fallback policies and safety margins need measurements at representative peak load, not copied example values. [Facts F10 and F11]

Fix data-path completeness before focusing on policy hit rate. A diagnostic test request can carry a low-sensitivity, stable release or experiment marker so operators can compare span presence across stages. Do not attach an email address, token or full request body merely to make a sampling policy match. Privacy constraints depend on the system; see OpenTelemetry baggage propagation boundaries for related context-propagation limits. If a policy relies on an attribute, verify which service writes it, on which spans it appears, and whether processors rename or filter it. A missing attribute and a missing span are different faults, even though both may look like a policy that failed to retain a trace.

Use a staged check to locate the loss

The following is a proposed validation plan, not an experiment that has been run. Create a controlled request with a stable trace ID. Produce distinguishable spans at entry, order and database stages, then make the second child call report ERROR. Record span IDs, parent span IDs and a test attribute or status at each stage. First disable sampling drops at the SDK and Collector and check whether all three spans reach the sampler. Then introduce one failure at a time—for example, SDK DROP, an earlier filter, an export-queue failure or ordinary load balancing. If the backend shows a gap, this distinguishes a loss before the tail sampler from one after it.

Next check timing and routing. Delay one service's span so it arrives before and after the decision window; observe whether it influences the decision or inherits an existing outcome. Send spans for the same trace through two first-tier Collector entry points and confirm whether trace-ID routing still directs them to the same tail-sampling instance. If production scales replicas, repeat during membership changes; a static topology test does not cover that condition. Finally, use controlled load near the expected peak and observe early eviction, processor delay, per-trace size limits and memory. Without such load evidence, do not claim that capacity covers production spikes.

Keep results in three groups: how many test spans the producer created and recorded; how many the tail sampler actually received and what decision it made; and how many the backend stored. They describe different boundaries. If the numbers differ, inspect the transitions before attributing every gap to a sampling percentage. Nor can total business errors be inferred directly from retained traces: a policy deliberately favors error, latency or attribute-defined groups. Use suitable metrics or another aggregate source for overall error rates.

When tail sampling helps—and when it does not

Tail policies are useful when the SDK and earlier pipeline deliver candidate spans to the sampler, the system can afford buffering and operational complexity, and the diagnostic question depends on error, duration or attributes known only after request start. The concepts documentation also describes combining sampling at multiple collection stages: under high volume, head sampling can limit data entering the pipeline, followed by tail sampling for more sophisticated decisions on the remaining evidence. That combination may protect the telemetry pipeline, but if the head stage stops recording or exporting a candidate trace, the tail policy acts only on the surviving subset. The related trust boundary for the sampled traceparent flag helps frame what a receiving service can infer from propagated context. Facts F3 and F13

If the real issue is that services do not create spans correctly, SDK decisions discard data, export or reception is unreliable, or routing fails to bring the trace together, fixing those stages is more direct than adding another tail policy. If the goal is high-cardinality reduction, storage cost control or a fixed statistical ratio, probabilistic sampling, metric aggregation or a backend-provided approach may fit better. The choice depends on which diagnostic evidence can be missed, where decisions are made and whether the team can operate stateful buffering.

A verifiable promise might read: “For candidate spans not dropped by the specified SDK, with a healthy export path, all fragments routed to the same tail-sampling instance, and wait and capacity limits met, retain received traces matching the error attribute.” It is longer than “keep every error trace,” but it gives an investigator places to look when evidence is missing. Check the path and deployed version before tuning the policy.
