Why Should a Log Field Allowlist Come Before Collector Redaction?

Define log events around the action, authorization decision and write outcome an investigation needs, then inspect fields in collectors, indexes and backups. Downstream redaction cannot prove upstream copies never existed.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-26 · Estimated read 21 min
Translations
zh-CN en

Article

Define what an event must answer in the application first, then use a collector as a second filter. A collector can only process data that reaches it. Replacing an attribute with asterisks later does not recall a copy already written by the application, proxy or debugger. When investigating an account change, responders usually need the action, authorization decision, write outcome, response status and a correlation identifier for one interaction. They do not need the request body, before-and-after values and authentication credential together. The example below is a design exercise: no live logging platform was inspected and no redaction test was run.

Turn the diagnostic question into an event contract

Suppose support receives a report that a contact update did not take effect. The investigator must distinguish four facts: whether the request arrived, whether authorization passed, whether the write committed and what status the service returned. A bounded event could contain a fixed event name, timestamp, service version, interaction identifier, operation type, object scope, authorization result, write result, error code and HTTP status. That record preserves a useful sequence: the interaction passes through a permission decision, reaches a write step and ends in success, denial or failure.

“Object scope” does not mean that the event must contain a person’s name or full account identifier. If the investigation only needs to know whether events refer to the same record, use a correlation value with restricted access and a defined lifetime. If long-term cross-request tracking is necessary, state why, who can correlate it and when that ability expires. An identifier that is not a name may still point to a person when combined with time, IP address or organization. Calling a value user_ref does not make it anonymous.

OWASP’s logging guidance recommends recording the action, object and result status, and using an interaction identifier to connect related events. It also says that access tokens, passwords, connection strings, encryption keys and sensitive personal data generally should not be recorded directly. That combination is more useful than “more log detail is always better”: write down the question first, then make each field justify which step it explains. Do not add the raw request as a substitute for a question the event contract has not answered.

OpenTelemetry’s Body, Attributes and Resource are different surfaces

Structured does not mean safe. OpenTelemetry’s log data model allows Body to be a string or a structured value made from arrays and maps. Attributes hold additional information that can vary by event, while Resource describes the application or infrastructure producing the log. Exception details can also appear as structured fields on an event. Sensitive data can occupy any of these locations, so checking one attribute name cannot prove that the record is clean.

Consider a failure path: the application writes fixed business fields to Attributes but places the entire HTTP request object in Body. On a connection error, a formatted exception may copy request configuration, headers or response text into another field. If a collector rule only walks record Attributes, it may filter the attributes it sees; that does not establish that arbitrary nested Body values, separate Resource metadata, proxy access logs or SDK-generated exception records were inspected. The specification defines Resource separately from event Attributes, and the processor documentation reviewed here describes record attributes as its scope. Confirm the exact fields covered by the deployed version rather than treating “structured” as automatic redaction.

In the OpenTelemetry Collector Contrib Redaction Processor README checked on 26 November 2026, the documented behavior is to remove span, log or metric attributes outside an allowed list and to mask configured attribute values. The repository snapshot labels log and metric support alpha, trace support beta, and lists contrib and k8s distributions. That is the status in the checked repository documentation, not a promise that a particular packaged distribution includes the processor and not a production security certification. Verify the actual Collector distribution and version before deployment.

The configuration itself can create blind spots. The README says an empty allowed_keys list removes all attributes; allowlist filtering occurs before sensitive-value matching; ignored keys pass without redaction; and an allowed value can take precedence over a blocked value. A summary: debug setting can also record names of attributes involved in processing. So “redaction is configured” is only a starting point. Review the allowlist, ignore rules, diagnostic summaries and destinations for their results. A broad ignored_key_patterns rule can bypass checks; an overly narrow allowlist can remove the error category responders needed.

Why downstream redaction cannot replace an application allowlist

A data-flow sketch exposes more than checking whether one formatter calls mask(): application and framework logs, proxy logs, local files or standard output, then a Collector, followed by possible copies to search indexes, alert attachments, temporary exports and backup archives. At every arrow ask which fields travel there, whether the record is copied before filtering and what happens if filtering fails.

In the hypothetical contact-update flow, the safest first step is not to make the Collector guess whether every field named “email” is sensitive. The application creates only the event contract above and never serializes the contact value or Authorization header. The Collector can then apply an allowlist and patterns to those defined attributes as a second control against later accidental additions. If a proxy still logs full requests and the Collector runs only on the application-log branch, cleaning that branch says nothing about the proxy copy. Those logging systems may use different field names, permissions and retention, so review them separately.

A second counterexample occurs during an HTTP 401 or network error. The primary event may contain no sensitive key, but application code that logs a formatted exception with the full request can still emit a token or response body. Another failure starts with an input value containing CR/LF: unstructured string concatenation can make that value look like a separate log event. OWASP recommends validating untrusted fields, sanitizing CR/LF and delimiters, and encoding for the output format, while retaining the necessary security event. When a field is rejected, record bounded safe context about the validation failure rather than discarding the fact that validation failed.

Choose between deletion, short-lived correlation and pseudonymization

First decide what kind of correlation the investigation requires. If events within one interaction are enough, a random interaction identifier usually exposes less than a persistent user identifier. If several events must identify the same entity over time, the system owner should define who holds the key, its scope, allowed users, rotation and retention. A plain hash does not automatically anonymize a low-entropy account number, IP address or short identifier: the value space may be enumerable and the result may be joined with outside data. The same processor documentation recommends HMAC over ordinary hashing for low-entropy values, but that statement describes a processor-specific option. It is not a substitute for key governance, legal review or a re-identification assessment.

Retention is not a number to copy from another team. OWASP says logs, debug files and their backup or extracted copies should not be kept beyond the period actually needed; access should be restricted and reviewed. Start by stating whether each event supports recovery, audit or security alerting, then identify owners, readers and deletion mechanisms for every copy. A file does not become low risk merely because its name says “temporary export.”

Verify every output path with a synthetic canary

A test plan could use fake email and token values plus a unique canary string, with no production permissions. Place them in request bodies, nested fields, headers and exception text in a controlled environment, then exercise success, authorization denial, validation failure, timeout and logging-processor failure paths. This plan has not been executed. Check the application’s raw output, proxy, logs before and after the Collector, search backend, alerts and exports, and any archive copies used for recovery. Searching for the exact canary proves only whether that known literal appeared; it cannot prove that every encoded or transformed variant is absent.

The same test should confirm that useful positive evidence remains: the interaction identifier connects the authorization decision and write result; time and service version remain available; and exceptions become safe error categories. Otherwise, “redaction succeeded” may just mean the event was reduced to nothing useful. Simulate network loss, exhausted disk, missing write permission and a logging-library error as well. Check whether the application continues or fails according to its risk policy, and whether the error path dumps more detailed data to a fallback destination. OWASP specifically recommends including such logging failures in code review, application testing and security verification.

No canary was run for this article, and no deployed Collector, index or retention policy was examined. For a real implementation, first reduce unnecessary input through the event contract, then treat collector filtering as a second control with a known version and field scope, and finally verify each export branch and historical copy. If nobody can say which question a field answers, where it travels, who can read it or when it is deleted, remove it from the event contract instead of relying on a query screen to hide it.

Continue with correlation identifiers and distributed-trace boundaries and secret rotation and revocation.
