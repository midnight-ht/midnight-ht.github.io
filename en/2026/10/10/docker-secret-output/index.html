A Docker secret mount cannot prevent a command from leaking its input

Secret mounts protect a build input channel; inspect commands, output files and caches for copied credentials.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-10 · Estimated read 5 min
Translations
zh-CN en

Article

A Docker secret mount does not remove the need to inspect where build commands write credentials. It provides an input channel, not automatic review of process output, generated files or copied artifacts. No image was built or scanned for this private-dependency example.

Input delivery and output content differ

Docker’s build-secret documentation discourages build arguments and ENV for secrets, recommending secret or SSH mounts. A step can consume a secret as a file or mounted environment value. Check actual builder and syntax support; this does not make all environment usage safe.

A package manager might read temporary credentials correctly yet copy authentication configuration into a directory later included in the image. Ending the mount does not erase program-created copies. Debug output or printed request headers can expose the same input in build logs.

Trace entry, reading command, generated files, copied directories and log destinations. Absence of a credential literal in the Dockerfile is not proof about build context, tool configuration, scripts or final content.

Limit access and copies

Give credentials only to the steps needing them, with suitable rights and lifetime. A mount does not sandbox untrusted download scripts; executable dependencies require source and permission review.

Multistage builds reduce copied scope only when that scope is inspected. Compiled output may contain authentication files, debug material or source configuration. Cache copies remain a concern even if the final image is clean; check actual platform sharing and access.

On exposure, assess where credentials traveled and revoke or rotate appropriately. Removing today’s file leaves possible historical logs, images and caches. Follow rotation and revocation responsibilities, recording inspected and unknown scope rather than merely the new mount configuration.

Inspect artifacts and handoff evidence

Proposed checks use controlled test credentials and inspect logs, image history/files, build output and cache rights, including failures. Do not publish credentials through the test itself. Pattern scans assist but cannot prove absence of transformed or fragmented secrets.

These checks were not executed. A review must explain both the protected input and its possible outputs.
