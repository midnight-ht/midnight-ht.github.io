A Docker Secret Mount Protects Delivery, Not Every Build Output

A Docker secret mount limits how a credential is delivered, not what the consuming command can write. Inspect outputs and remember that rotating the value alone does not invalidate a RUN cache.

Updated 2026-11-26 · Estimated read 21 min
Translations
zh-CN en

Article

A Docker secret mount protects how a build step receives a credential, not what the command can do after reading it. The command can still copy the value into an ordinary file, print it to a log, or produce an artifact that contains it. BuildKit also does not automatically invalidate the relevant RUN cache just because the secret value changed. A useful review therefore follows two paths: where the credential enters and which outputs can carry it away; and which steps actually rerun after rotation. The private-dependency example below is hypothetical. No Docker image was built, cache scanned or container test executed for this article.

A mount controls input delivery, not the process

Docker's Build secrets documentation recommends secret or SSH mounts for build credentials instead of putting secrets in ARG or ENV. The Dockerfile reference says a secret is available as a file by default, normally under /run/secrets/<id> inside the build step, and its target can be changed. The secret is made available to the build container for that RUN instruction. This is a useful boundary: merely declaring a mount does not automatically write the value into the final image configuration. But it does not turn the command into a restricted program that can read but never write.

Review the build command as a data processor. If it can read the credential, that process and its child processes can also write it somewhere else. Imagine a hypothetical Node project that needs a private registry to download locked dependencies. The step can read authentication data from a mounted configuration and run the package installation. If an install script copies the full authentication file into the working directory for convenience, and a later instruction copies that directory into the runtime stage, the credential travels into the image through an ordinary file path. The mount disappearing at the end of the step does not retract a copy that the command already created.

A second counterexample needs no file copy. Shell tracing, printing the full configuration while debugging, or including an authorization header in a failure message can send the credential to the build log. Logs are usually retained, searched and exported by CI systems with access boundaries different from those of an image registry. A clean final-image inspection therefore cannot prove that historical logs, build summaries or external caches never received the same value. The reverse is also true: not seeing the raw string in a log does not prove that a program did not encode, split or embed it.

The Build secrets documentation answers how to deliver input to a build step; it does not promise to inspect the command's outputs. Docker also warns against managing secrets with COPY or ARG. The resulting engineering distinction is that input delivery, process authority and persisted output are separate controls. A secret mount is a useful input boundary, not an end-to-end proof that nothing leaked.

Trace one dependency installation through its outputs

Start with the shortest data-flow map: CI secret storage provides the build credential; BuildKit mounts it into a specific RUN instruction; a package manager accesses a private dependency; the step produces an install directory; a later stage selects files; logs and caches may be exported remotely. At each arrow ask two questions: who can read this data, and what can remain afterward? Searching the Dockerfile for a literal token will not find a file created by a tool at runtime or configuration inherited from the build context.

Suppose the step only needs to read a temporary npm configuration. Review each instruction for a COPY . . that could bring a developer's local .npmrc into the context, an install script that could write authentication data into the project directory, an output directory that a later stage copies wholesale, or a failure path that prints environment values. A .dockerignore file can exclude local files that should not enter the build context. It cannot stop a script that is authorized to read the mounted secret from creating a copy. Excluding an unintended input and constraining outputs are useful together; neither replaces the other.

A multi-stage build can narrow the set of files copied into the final image. Docker's multi-stage documentation describes selectively copying artifacts from a prior stage. That means the runtime image need not contain the compiler or the entire build directory. It does not mean every intermediate file has vanished from builder caches, logs or artifact storage. If a build step writes authentication configuration into dist and the final stage copies all of dist, multi-stage syntax will not identify which file is sensitive. If the file is not copied to the runtime image, the cache and logs still need their own access review.

Identify the asset before choosing where to inspect it: check the final image filesystem, history and metadata; check build logs for command echo and error text; check exported cache destinations, sharing scopes and read permissions; and check the context for local configuration accepted by COPY. Docker treats external cache backends as separate destinations that must be configured for export or import. Their access controls and retention depend on the backend, so "only the final image can become public" is too narrow an assumption. Also distinguish a RUN cache mount from a secret mount: Docker's cache optimization documentation says cache-mount contents persist and are reused across builds. If one is mounted at a package manager's state directory, inspect what that tool actually stores there. This does not mean a package manager always writes a token; it means a persistent cache should not be treated as a temporary secret mount.

Rotating a credential does not prove it was tested

Secret mounts have a separate cache boundary. Docker's build cache invalidation documentation explicitly says secret contents are not part of the build cache checksum. Changing the secret value alone does not invalidate the cache; the secret ID and mount path do participate. In other words, updating the token under the same mount ID may still let a later build reuse the previous RUN result. The command does not execute again, so it has not verified that the replacement token can read the dependency.

This does not mean that a cache necessarily contains the old token. It means the cache key is not derived from the secret value, and whether the step runs depends on its other inputs. For a step that only authenticates, avoiding a rebuild on every secret rotation can be desirable. But if the acceptance question is whether the new permission scope works, whether a token has been revoked, or whether remote dependency state changed, cache reuse may create a green result that was never demonstrated. Credential exposure response and cache freshness are related but distinct concerns.

Define the acceptance question before choosing a cache strategy. If the question is "can this token read the repository now?", make that verification step execute, using a documented targeted --no-cache-filter, a non-secret cache marker, or an explicit forced-verification path. Do not put the real credential in ARG as a cache-busting trick: Docker warns that ARG and ENV are inappropriate secret channels because they may persist in the final image. A random marker with no sensitive meaning can trigger a required step, but it proves only that the step reran; it does not prove that its outputs are clean.

If the question is whether dependencies match declared versions, rely on lock files, checksums and the package manager's integrity checks rather than blindly clearing all caches. Disabling every cache can hide the actual dependency relationship and significantly increase build time. Separate "the authorization check must run again" from "every compile and download layer must start from zero" to get the necessary evidence with a narrower invalidation scope.

Make the review falsifiable

A useful review plan begins with a disposable canary credential that has no production permissions and a unique marker used only for the inspection. It must not be a copy of a real token or able to access a production repository. With a controlled build configuration, inspect build logs, the output directory, final image files, image history, exported caches and CI artifacts separately. If rotation is the subject, confirm that the relevant RUN instruction did not reuse the old cache and that the new credential actually participated in the check. Record which output and access boundary each step covered; "Docker build passed" is not enough evidence.

Cover negative paths too: does a missing mount fail clearly? When a package manager receives a 401, does the error reveal authentication configuration? After a script fails, can partial download files still flow into the next layer? Is a remote cache export readable by people who should not access this project? Search for the canary's exact value and common encodings, but treat that as a way to find known forms, not proof that every transformation has been found. Never print a real credential to a log to test redaction.

For a constrained step that reads the credential in memory, uses it only for authentication and produces a validated dependency artifact, a dedicated mount, narrow step permissions and selective copying into the final stage may be sufficient. If the script is untrusted, install hooks can run arbitrary code, or the build publishes remote caches, the mount alone is plainly insufficient; code provenance and cache-read scope matter too. The choice depends on who reads the secret and where the data can be written, not on whether one keyword appears in the Dockerfile.

This article provides a verification plan, not a Docker execution result. No image, cache or build log was inspected. If a real credential has appeared in a log, image or shared cache, revoke or rotate it promptly while checking who could have read it from logs and platform permissions, then handle affected artifacts. Deleting a file from the current working directory cannot erase copies already retained elsewhere. See the related guidance on secret rotation and revocation and release artifact and rollback verification.
