Promise.all rejection does not cancel the remaining work

Promise.all aggregates outcomes; cancellation, compensation and complete result collection need separate policies.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-10 · Estimated read 5 min
Translations
zh-CN en

Article

When Promise.all rejects, work already started by other inputs may continue. Aggregation does not define cancellation, transaction rollback or compensation. Decide whether to collect results, request cancellation or follow a business recovery policy. This batch-save example contains no executed requests.

Outcomes and task lifetimes differ

MDN’s Promise.all reference says the aggregate rejects with the first rejection reason and does not cancel remaining operations. allSettled can wait for every outcome. This does not imply automatic cancellation support in an HTTP client or server.

Suppose three configuration saves run together and one fails validation. The others may already be stored or still awaiting responses. “Everything failed” can prompt duplicate writes. An array of promises is not a database transaction; whole-batch atomicity requires a separate server-side boundary.

Creating requests may start work before aggregation. Passing promises does not turn them into lazily scheduled task factories. Concurrency control is another responsibility governed by deadlines and downstream capacity; no optimal count is measured here.

Cancellation cannot undo history

For read-only search, request cancellation and prevent stale results from reaching the interface, as discussed in request cancellation and stale state. Whether a server stops is implementation-dependent; ceasing to wait is not restoration.

Writes and notifications need actual business outcomes even after cancellation. Stable operation identities can support status queries and idempotent retry. Compensation is not an arbitrary inverse call: restoring old configuration could overwrite a later legitimate change. It needs conditions and authorization.

allSettled preserves individual results for partial-success workflows but neither retries failures nor reverses successes. One indefinitely pending input can delay collection. Define per-task deadlines, unknown status and later reconciliation; timeout does not prove nonexecution.

Make feedback reflect business state

For partial success, identify saved, failed and unconfirmed objects, and offer appropriate retries. For all-or-nothing behavior, design a server boundary that guarantees it rather than guessing from independent requests.

Proposed tests vary success, rejection and delay order and inspect feedback, repeated clicks and retry effects. They remain unexecuted. Review side effects before choosing the aggregation API.
