Promise.all rejection does not cancel the remaining work

Promise.all rejects its aggregate on the first input failure but does not stop the inputs. Use AbortController for signal-aware reads and business-state rules for writes.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile

Key takeaways

  • Aggregate rejection does not stop input tasks; work may already have started and side effects may already have occurred.
  • AbortController requests cancellation only from APIs that honor its signal; allSettled collects outcomes, while Promise.race only selects the first result.
  • Close writes through operation identity, idempotent replay, status queries, transactions, or guarded compensation; a lost connection does not prove nonexecution.

Promise.all rejects its aggregate result; it does not send a cancellation signal to its inputs. Work that has already started may continue unless the underlying API supports cancellation and the caller requests it. This distinction matters beyond UI behavior: when parallel saves fail early, the error path can run before other operations finish, and a retry may repeat a write that already succeeded. This hypothetical batch-save example explains the boundaries among task lifetime, cooperative cancellation, and business recovery. The code has not been run in a browser, Node.js, or a database.

Aggregate rejection is not task termination

Promise.all(iterable) returns a new aggregate promise. If an input rejects, the aggregate rejects with the first rejection reason. The other inputs keep their handlers, and their underlying operations continue according to their own implementations. MDN explicitly says that rejecting the aggregate does not cancel the other operations or unsubscribe their handlers. The ECMAScript specification describes how the result promise fulfills or rejects; it does not define a general cancellation protocol for arbitrary work.

Keep three layers separate: when the promise returned by Promise.all settles; when each input operation actually ends; and whether any external side effect has happened. The state of the first layer cannot establish the latter two. Rejection says that the caller will not receive a complete array of fulfillment values. It does not mean that a request, timer, file read, or remote write has returned to its starting state. The inputs have handlers attached when Promise.all is called, so a later rejection does not simply imply an unhandledrejection event.

The MDN Promise.all reference distinguishes fail-fast result behavior from underlying operations and says that allSettled waits for all inputs. The ECMAScript 2025 Promise.all section defines fulfillment values and the first rejection reason. These sources define aggregate settlement, not database transactions or cancellation for arbitrary APIs.

Work often starts before it reaches the aggregator. For example, items.map(item => save(item)) calls every save immediately. Passing the resulting promises to Promise.all waits for work that has already been created; it does not create a queue that can stop tasks one by one. If startup needs a limit, pass task factories to a separate scheduler and let it start work within a concurrency budget. The budget depends on downstream limits, deadlines, and resource constraints; Promise.all does not imply one universally best number.

Trace a three-save failure

The following is a hypothetical state example, not an executed test. A page starts three configuration saves with stable operation keys save-a, save-b, and save-c. The server permits each item to succeed independently and offers no batch transaction. One possible timeline is: request A commits on the server but its response is lost; request B fails validation; request C is still being processed. B's rejection quickly rejects the aggregate. At that point, A's actual state is unknown, and C may still be running.

If the interface marks the whole batch “failed,” a user retry may write A again. Without an idempotency identity or uniqueness constraint, this can create a duplicate. If the operation replaces configuration, a repeated request may overwrite a legitimate change made after the first save. Even an immediate cancellation request may arrive after A has committed. Stopping the browser from waiting is not a server rollback; a broken connection is especially poor evidence that the remote side did nothing.

The interface should show each object's confirmed state instead of reducing the batch to one boolean. A can be “awaiting confirmation,” with its status queried using the same operation key. B can show a validation failure and wait for corrected input. C can show “cancellation requested” only if the operation is actually cancellable; otherwise it remains in progress. Retry is appropriate only after the server confirms no commit, or when the operation protocol guarantees that replaying the same idempotency key is safe. If the business promise is all-or-nothing, implement atomicity at a server transaction or explicit batch-state boundary. Do not expect several parallel HTTP requests plus a client aggregator to provide it.

AbortController is cooperative, not a Promise cancel button

For disposable reads such as search suggestions or previews, a caller can create an AbortController and pass its signal to each fetch that supports the option. If one input fails, calling abort() in the error path requests that pending fetches stop. The official MDN example uses this approach to clean up other reads after Promise.all fails. It depends on the underlying operation accepting and honoring the signal. An ordinary promise, CPU-bound loop, or custom task that never checks a signal will not stop merely because abort() was called.

MDN's resource-management guide shows one shared AbortController signal. The Fetch guide documents that aborting causes the corresponding fetch to reject with AbortError. This covers signal-aware reads; it does not promise rollback of a remote write.

The following is an unexecuted teaching example. Adjust URL checks, error policy, and controller scope for the application:

async function fetchEveryPage(urls) {
  const controller = new AbortController();
  try {
    return await Promise.all(urls.map(async (url) => {
      const response = await fetch(url, { signal: controller.signal });
      if (!response.ok) {
        throw new Error(`HTTP ${response.status}`);
      }
      return response.json();
    }));
  } catch (error) {
    controller.abort();
    throw error;
  }
}

The catch requests cancellation of sibling fetches. It cannot guarantee that a server stops computation already underway, and it cannot undo a committed write. MDN also notes that fetch can fulfill once response headers arrive. If cancellation happens after that but before the body is consumed, reading the body can still reject with AbortError. Another boundary: HTTP 404 normally fulfills a Response; check ok or status and decide explicitly whether that response should reject the input.

Cancellation may also be composed with page lifecycle or batch deadlines. The current Node.js documentation describes AbortController as a signal mechanism for selected promise-based APIs and records it as added in Node 15.0.0 and 14.17.0. Its version history for AbortSignal.any is Node 20.3.0 and 18.17.0. Check the actual browser and Node runtime before relying on those static helpers. Combining signals does not stop a task that ignores them.

These release details come from the Node.js Global objects reference. They are included to flag runtime compatibility, not to claim that every asynchronous API hosted by Node supports cancellation.

allSettled, timeouts, and queues solve different problems

If a batch permits partial success and callers need every final outcome, Promise.allSettled waits for all inputs to fulfill or reject and returns status snapshots in input order. It collects results; it does not cancel running work, retry failures, or undo successful work. If one input never settles, allSettled waits indefinitely. Define per-task deadlines, cancellable operations, and an “unknown” outcome instead of waiting without a bound.

Using Promise.race([work, timeout]) to show a timeout sooner also only decides which promise settles the race first. It does not cancel work. If the goal is to stop a cancellable underlying operation, the timeout handler must signal that operation. If the goal is only to stop waiting, the caller still has to handle a late fulfillment or rejection so that it cannot update stale UI state. See request cancellation and stale results for preventing an old search response from overwriting a newer one, and API retries and idempotency for avoiding repeated side effects.

With many inputs, mapping directly to promises may start all work at once. A bounded queue should accept functions such as task(signal), not already-running promises. The scheduler starts another task only when capacity is available, stops starting queued tasks after cancellation, and signals running tasks that support cancellation. It must define the states of queued, running, and completed tasks at the moment cancellation is requested. Concurrency limits do not replace idempotency or server-side capacity controls. Synchronous exceptions during task creation also need handling so every started task can be tracked and brought to a known state.

Close write operations through business state

Write recovery should not rely only on the promise rejection object. A reviewable protocol usually needs a stable operation identity, a queryable terminal state, replay rules, and bounded waiting. If the client loses its connection, query the same operation key. If the outcome remains unknown, keep it pending rather than creating a new identity for another write. Retry only after confirming that the operation did not happen or when the server guarantees that replay with the same key is safe. Batch atomicity requires a transaction or server-side coordination. Compensation must check current version or ownership so it does not replace a newer value with an old one.

A verification plan should cover: the first input rejects while another completes late; multiple inputs reject in sequence; cancellation after response headers but before the body is read; an HTTP error response whose fetch itself fulfilled; parent-page cancellation overlapping a batch deadline; and a write that committed before its response was lost, followed by a retry with the same idempotency key. Also check that stale responses cannot update a replaced page and that abort errors are not mislabeled as ordinary business failures. These tests were not executed for this article; no network request or successful test log is claimed.

Before selecting an API, answer two questions: do callers need all results, early failure, or to stop a disposable read? Can an input leave an external side effect? Promise.all aggregates fulfillment values and the first rejection; allSettled waits for outcome snapshots; AbortController requests cancellation from operations that support its signal; a queue controls work that has not started; transactions, idempotency, and status queries handle write recovery. Making those responsibilities explicit keeps “failed” from hiding continued work or falsely claiming that an uncertain side effect was rolled back.
