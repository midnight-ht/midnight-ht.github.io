Should You Edit or Supersede an Old ADR? Check Whether It Reached Implementation

Choose how to revise an ADR based on its status, implementation history, and whether a replacement has been accepted. Preserve traceable history without implying that supersession completes migration.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-26 · Estimated read 23 min
Translations
zh-CN en

Article

Before deleting or rewriting an old ADR, check whether it is still a proposal under review or an accepted decision that has already shaped code. A proposal that was never implemented may be revised with the agreement of its reviewers and stakeholders. Once any part of the old decision has been implemented, the Government Digital Service (GDS) recommends writing a new ADR to explain the new decision, then marking the old record as superseded and linking to its replacement. Guidance differs on the treatment of accepted but wholly unimplemented decisions. Preserve a readable history rather than treating one ADR convention as a universal standard.

An Architecture Decision Record (ADR) answers a bounded question: what constraints existed, what the team chose, and what consequences it accepted. It is neither a runbook nor a complete architecture diagram. Michael Nygard's 2011 proposal emphasizes small records, a single decision, status, and consequences. Martin Fowler's page displays the date 24 March 2026 and advises against changing an accepted ADR, recommending a linked successor instead. The UK Government Digital Service's GDS Way page distinguishes a decision that was never implemented from one with partial implementation. It is marked last reviewed on 5 March 2026, with a six-month review interval. By the date this article's sources were checked, that interval had elapsed. The page is therefore used as a traceable governance reference, not represented as freshly reviewed current policy. Confirm your organization's current process before adopting it. The sections below separate source recommendations from editorial judgment.

“Proposed,” “accepted,” and “implemented” are different states

An ADR appearing in review does not mean the team has adopted it. GDS suggests using the pull request's state to reflect an unaccepted proposal; after the proposal is approved and merged to the main branch, it can be treated as accepted, subject to the repository's own convention. Acceptance is a governance state. Implementation is an engineering state. They can occur together, but one does not prove the other: a decision may be accepted but unscheduled, or implemented for only some callers while other paths still use the old design.

That distinction changes the right editing operation. First, the record may still be under review and never served as current guidance. Revising the proposal while retaining version history, and telling the original reviewers that a key assumption changed, is often clearer than adding a formal replacement. Second, the decision may be accepted but not implemented at all. Fowler's practice is to retain it and create a successor; GDS allows an update to a wholly unimplemented decision when reviewers and stakeholders agree. A team should record which convention it follows. Otherwise different maintainers can leave contradictory histories based on personal preference. Third, the decision may already have influenced code, interfaces, data, or deployment. In that case, write a new record explaining the new choice. Rewriting the old one would make readers mistake “what should we do now?” for “what have we always done?”

So “should an old ADR be edited?” is not just a formatting question. Check whether it was accepted, whether any implementation exists, which users depend on it, and whether the replacement has been approved. Missing status or implementation evidence should be marked unknown or checked with an owner. Do not hide uncertainty by making the documents look tidy.

A hypothetical example: synchronous reports become background jobs

The following is a hypothetical illustration of a recording method. It is not a zyweb project story and includes no actual migration result. Suppose ADR-0014 chose to generate reports synchronously inside an HTTP request because the data range was bounded and callers needed an immediate result. Later, the product supports larger report ranges. A browser disconnect leaves users unsure whether a report finished, so the team reviews and accepts ADR-0021: generate files in a background job and expose a job-status query.

If ADR-0014 was only proposed, never merged, and never implemented, the team can revise the proposal after agreement from its stakeholders. If it was accepted but never implemented, the team needs to choose and document its historical convention: Fowler's approach preserves it and creates a successor, while GDS permits an agreed update when the decision was wholly unimplemented. Do not edit the original and then pretend the repository has always contained only the new conclusion.

Once the synchronous path has served some callers, add ADR-0021. It should explain the trigger for change, the options considered, the reason for the selected option, its negative consequences, and which callers are in scope. A queue adds responsibility for retries, duplicate-task handling, status storage, file expiration, and alerts. Those are architecture costs; “better user experience” is not an adequate summary of them. Mark the old ADR as superseded and make the new record link back to it.

Suppose only the administration portal moves to asynchronous processing while an overnight batch still runs synchronously. Then “ADR-0014 is superseded” must not imply that migration is complete for every path. The status line can state the replacement's scope, or a project index can explain where the old decision still applies. That is a local governance choice: the GDS page does not prescribe a specific syntax for partial scope. Keep the records' jobs distinct: the ADR explains why the design changed, a tracked issue says which callers remain to be migrated, and the runbook describes how the system actually operates today.

Supersession does not mean the old system has been migrated

“Superseded” describes a relationship between decisions; it is not a deployment status. GDS explicitly says that incomplete implementation across relevant teams should be reviewed regularly and can be followed in an issue tracker. Even when a new ADR is accepted, old code, historical data, or operational procedures may remain. Treating a new decision as proof of completed migration makes both troubleshooting and audit records inaccurate.

Make the replacement chain readable in both directions. Put “Superseded by ADR-0021” immediately under the old ADR's heading; in the new record, explain why the old approach no longer governs and link back to it. The repository index can state the current scope and outstanding migration work. GDS specifically recommends a superseded status under the old heading and adding the link after the new decision is accepted. This helps someone arriving from a search result avoid mistaking historical guidance for the current instruction.

Conversely, do not mark the old decision superseded while its proposed replacement is still under discussion. Keep the new ADR proposed until it is accepted, then update the status and links. Otherwise a proposal that fails review can make the team believe a new architectural direction exists. This sequence is editorial advice; the names and transitions for statuses should follow the team's review process.

What if an old ADR contains a factual error?

Preserving history does not require repeating an error as fact. First identify the kind of error. If the old decision and its rationale were accurately recorded but the conclusion later became invalid, retain the original and link to the successor. If a factual detail was wrong at the time it was written, use a visible correction or addendum to reduce the risk of misleading readers while preserving the change history, and make the current index point to the corrected explanation. If sensitive information must no longer be public, follow the repository's data-handling and audit rules; historical completeness is not a reason to expose secrets.

None of the cited pages specifies whether every factual correction must be a footnote or a new file. Fowler's guidance is about not overwriting an accepted decision with a later one. GDS discusses clarification, non-implementation, and partial implementation. A practical editorial rule is that readers must be able to tell when the old decision applied, what was later learned, and which record governs today. Git can show when text changed, but it does not automatically tell a reader which version is current guidance.

How should you check the chain before publishing a successor?

The following are suggested checks. They were not run against a particular real repository in this article, and no result is claimed. Search the project for the old ADR's number, title, and key terms. Look for references in other ADRs, code comments, deployment notes, and runbooks. Confirm the successor's review status; only after acceptance mark the old record superseded and add its link. Then list the services, callers, data, and environments covered by the change, and separately check paths that still use the old implementation. Finally, ask the relevant teams to confirm the owner, migration-tracking location, and any required runbook changes.

A small review table can capture the evidence: record ID, status, implementation evidence, affected scope, successor, and migration tracker. It is a checklist for this change, not another global catalogue that must be maintained forever. Where implementation evidence is unavailable, write “unknown” and ask an owner to verify it. Inferring deployment from the presence of an accepted ADR is less reliable.

Do not judge the review by how neat the replacement chain looks. Ask two questions: can a new engineer find the decision that applies now, and can an on-call engineer explain why an old path still exists? An unanswered first question means current guidance is hard to discover; an unanswered second question means history and migration status have been conflated. The article on turning requirements evidence into design decisions can help connect needs to architecture choices; when a rollout is interrupted, release artifacts and rollback helps check whether operational instructions match actual deployment state.

When is it reasonable to edit the old ADR directly?

When it remains an unaccepted proposal, the review process allows edits, and the change and its reason remain visible in version history, revising it is usually appropriate. When it was accepted but never implemented, first choose and record the team's governance convention: GDS allows an agreed update, while Fowler recommends leaving an accepted ADR unchanged. If any part has entered code or operations, a successor usually preserves the history better; the old record should point clearly to it. If scope is unclear, implementation is unknown, or the replacement is not approved, gather evidence before publishing a superseded status.

Nygard's original proposal, Fowler's current overview, and GDS's lifecycle guidance support a cautious practice: retain why the old decision made sense, identify the currently applicable record, and track implementation still outstanding between them. Before the next ADR review, write down the old decision's acceptance state, implementation evidence, and scope. Those three facts are more useful than naming conventions when deciding whether to edit, supersede, or defer a change.
