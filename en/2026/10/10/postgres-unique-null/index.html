Why can a unique column still contain multiple NULLs?

PostgreSQL 19 treats NULLs as distinct in unique constraints by default. Choose NULLS NOT DISTINCT, NOT NULL, or a partial unique index from the business meaning of absence.

Article

Key takeaways

  • Default UNIQUE permits multiple NULLs; NULLS NOT DISTINCT makes missing values participate as equal.
  • Composite uniqueness compares the full key tuple, so any nullable component can change duplicate behavior.
  • Prechecks improve messaging, while the unique index protects concurrent writes; inventory data before changing the rule.

Ask what “missing” means before deciding how a unique constraint should compare it. PostgreSQL 19 uses NULLS DISTINCT by default: two NULLs in the constrained key do not conflict merely because both are absent. With NULLS NOT DISTINCT, multiple NULLs are treated as equal for uniqueness. The default can fit separate records awaiting identifiers; the latter can fit a rule such as “one default slot per tenant.” The tenant configuration and external identifier below are hypothetical. No SQL, migration, or concurrency test was run.

NULL is absence, not a shared placeholder string

A unique constraint answers which rows may not coexist; it does not define product identity for you. If an external system has not assigned a customer number yet, the value is usually unknown. Two different customers may both lack a number without being the same customer. Treating those NULLs as equal can prevent legitimate records from being created before their identifiers arrive.

A different rule appears in a configuration table: each tenant may have at most one default region configuration. Here a missing region might mean “the tenant’s default configuration,” rather than an unknown concrete region. A second row for the same tenant with no region could be a duplicate identity. If every absent value represents an independent unknown, the default behavior is appropriate; if absence names a single business slot, it may need to participate in equality.

That distinction is why duplicate NULLs do not automatically mean the database is broken. Write the business rule first: which fields identify a record, and can two records still be different when one field is absent? “We do not know yet” and “there can be only one default” need different models.

Section 5.5.3 of the PostgreSQL 19 constraints manual says that NULL values are distinct by default in unique constraints; NULLS NOT DISTINCT changes that comparison. The SQL standard leaves the default NULL treatment implementation-defined, so behavior differs among database systems. The PostgreSQL project announcement states that version 19 was released on November 19, 2026. This older article originally targeted version 18; the corresponding rule can also be checked in the PostgreSQL 18 constraints manual. Check the major version actually running in your environment rather than inferring it from this update.

A composite unique key compares the whole set of columns

Suppose a configuration is identified by tenant, region, and configuration type. A constraint can cover all three. “Tenant A, East, invoice” repeated is the same complete non-null key and should be rejected. Under the default behavior, “Tenant A, NULL, invoice” contains a NULL component that is not equal to another NULL component, so a second such row may be accepted. A composite unique constraint does not mean “unique among rows where the other fields match”; it compares the complete key, and NULL affects that comparison.

Section 11.6 of the PostgreSQL 19 unique-index manual says a multicolumn unique index rejects a duplicate only when all indexed columns are equal; NULLs are distinct by default. A test that repeats only fully populated keys will miss this case. Also, a PRIMARY KEY disallows NULL: it requires both uniqueness and non-null values, so it cannot directly replace a nullable external identifier that may be assigned later.

Choose the constraint from a rule matrix

List the important states before selecting the database mechanism. “One default per tenant” below is a hypothetical business rule, not a claim about this site’s data:

Business state Can two missing values coexist? Likely constraint direction
Customer waiting for an external identifier Yes; different customers remain distinct Nullable ordinary UNIQUE; reject duplicate non-null values when assigned
One unspecified-region default per tenant No; one default slot per tenant Tenant-scoped composite uniqueness, possibly NULLS NOT DISTINCT
A field must exist on every valid record No; absence is invalid NOT NULL plus UNIQUE, or a primary key when it is truly the row identity
Only active records must be unique Historical inactive rows may repeat Partial unique index for the active subset

The PostgreSQL 19 CREATE TABLE syntax allows UNIQUE NULLS [NOT] DISTINCT at column or table level. An ordinary UNIQUE constraint automatically creates the B-tree unique index that enforces it; creating a second manual unique index on the same columns duplicates that work. If a rule applies only to rows meeting a predicate, the official constraints manual says to use a unique partial index rather than an ordinary table-level UNIQUE constraint. Confirm whether the filter and row lifecycle are part of identity before choosing.

Do not replace NULL with an empty string just to make a missing value unique. An empty string is a concrete text value, so equal empty strings are compared as ordinary equal values. But user input, old clients, and imports may also send an empty string. Unless the domain forbids it and every input path normalizes consistently, it becomes a sentinel that can collide with a real value. A clearer model usually preserves NULL’s meaning, adds an explicit state, or models the default slot separately.

An application precheck cannot settle concurrent races

An application may first query whether the tenant already has an unspecified-region configuration and use the result for a friendly message. That is not a complete constraint. Two requests can both observe “none” and then both try to insert. At the index level, PostgreSQL 19’s uniqueness-check documentation explains the mechanism: if a conflicting row belongs to an uncommitted transaction, another insertion waits for that transaction to end. If the first transaction commits and the row remains, the second gets a uniqueness violation; if the first rolls back, the second can recheck and proceed. PostgreSQL integrates the final check with index insertion to avoid a race from an independent precheck.

The application and database therefore have different jobs. A precheck can improve feedback or avoid an obvious failed write; the unique index protects the committed state under concurrency. The application should translate a conflict from the relevant constraint into a useful product response and should not retry every failure blindly. If two customers are competing for the same external number, retrying that same number will not make it unique. If the conflict came from a transient wait or unresolved transaction, decide from the actual error and transaction state.

Inventory existing data before changing the rule

Switching from the default behavior to NULLS NOT DISTINCT is not merely a DDL edit. Rows that were previously allowed to share NULL may now conflict. Before adding the rule, separately inventory NULL, empty strings, whitespace-only input, and values that collide after the intended normalization. Whether case, surrounding spaces, or Unicode normalization affect identity is a product and data-owner decision; the unique constraint should not guess.

An inventory is not permission to clean data automatically. Two rows with NULL may be different pending objects or duplicate defaults. Only after the responsible owner determines their relationship can they be merged, assigned values, or retained. If old clients still write empty strings while new code writes NULL, define the compatibility-period normalization before enforcing the constraint. Otherwise the same business state is split across two database representations and becomes harder to query and explain.

For a large table, validate index locks and recovery behavior against the PostgreSQL major version, table size, write load, and migration tooling. This article does not provide an unverified online migration command, and no migration was executed. A safer review can split the work into read-only inventory, owner decision, compatible write paths, conflict resolution, constraint creation, and read-back verification. Record the rule and evidence at each step, and stop if conflicts remain instead of deleting data during a deployment window.

Validate more than duplicate non-null values

Tests should express the product contract, not merely prove that the syntax parses. For external identifiers, confirm that a repeated non-null value is rejected, that reuse across tenants matches the intended scope, that multiple unassigned identifiers are allowed, and that assigning a value later produces a clear conflict. For one default configuration per tenant, check that the first NULL can be inserted, a second NULL for the same tenant is rejected, and another tenant can have its own default. If region and type together identify the row, cover equal and different values plus partially missing combinations.

Also test the normalization of empty string versus NULL, clearing a previously assigned identifier, the treatment of historical duplicates during migration, and two concurrent requests creating the same default. A concurrency test should inspect the final row count and the application’s error mapping, not only assert that one request returned an error. These are proposed acceptance conditions; no successful SQL log or production migration is claimed.

A common follow-up is: “If one component of a composite unique key is NULL, can later rows always repeat?” Examine the columns. With default NULLS DISTINCT, if at least one corresponding component is NULL, the two key tuples are not equal in every column, so multiple rows can exist; a repeated complete non-null tuple still conflicts. With NULLS NOT DISTINCT, the NULL positions participate as equal values and the conflict scope changes. If only a subset of rows should be covered, a predicate matters too; changing NULL treatment alone will not express that rule.

Use this order: define the identity scope, define the business meaning of absence, list concrete row combinations that must pass or fail, then choose ordinary UNIQUE, NULLS NOT DISTINCT, NOT NULL/primary key, or a partial unique index. A table that permits many customers with unknown external IDs usually needs NULL to remain independent. A table with one default slot per tenant may need NULL treated as the same state. Concurrency, migration, and old-client compatibility require separate verification. For real concurrent write conflicts, see the article on transaction conflicts and retry boundaries; it cannot decide which missing values represent the same business identity.
