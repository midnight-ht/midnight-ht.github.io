Why can a unique column still contain multiple NULLs?

PostgreSQL 18 treats NULLs as distinct in unique constraints by default; choose semantics before enforcing identity.

Updated 2026-10-10 · Estimated read 5 min
Translations

Article

Multiple NULLs in a unique column can be expected PostgreSQL behavior. Decide whether missing values mean unknown identity, unassigned identity or one exclusive business state before choosing a constraint. An application precheck cannot replace concurrent database enforcement. The external-customer identifier example was not executed.

Define what missing means

PostgreSQL 18’s constraints documentation says unique constraints treat NULLs as distinct by default. NULLS NOT DISTINCT changes that comparison. Other databases may differ; do not assume equivalent syntax in older deployments or other engines.

Several customers awaiting external registration can legitimately lack identifiers. Treating all NULLs as equal would block the second customer. In contrast, one default configuration per tenant for an unspecified region may require missing regions to represent the same state. Identity rules distinguish these examples.

An empty string is a string, whereas NULL represents absence. Omitting a field, clearing a form and explicitly removing an identifier can mean different updates. Establish input normalization and intent before choosing storage.

Enforce the complete identity scope

If identifiers are unique only within a tenant, include that scope in the constraint. Examine every nullable component, including source system and identifier, rather than testing only fully populated rows.

A precheck can improve feedback, but simultaneous requests may both observe absence. The constraint protects the final state; the application translates conflicts into business errors. Blind retry cannot resolve a genuinely duplicate identifier.

Before migration, inventory NULLs, empty strings and duplicates after intended normalization. Case equivalence is another explicit decision. Data owners must approve reconciliation; do not delete historical customers merely to pass a migration. Coordinate data cleanup, client compatibility and error handling.

Test absence and concurrency

Proposed tests include equal non-null identifiers within and across tenants, two unassigned identifiers and partially missing composite keys. Concurrent tests should inspect surviving records and partial business changes. No successful test log is claimed here.

For multirow rules, consider whether uniqueness expresses the whole requirement; transaction isolation and retry address additional responsibilities. Start review by defining which records mean the same identity, then choose database syntax.
