Does readOnly in OpenAPI actually prevent a write?

In OpenAPI 3.1.1, readOnly is an annotation; define and verify the actual server-side write policy.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-10 · Estimated read 5 min
Translations
zh-CN en

Article

Putting readOnly in an OpenAPI schema does not by itself prove that a server rejects modifications. Review the contract, validator and business write path separately. For balances, approval states or generated identifiers, define who assigns them and how submitted values are handled.

Pin the specification before interpreting the keyword

OpenAPI 3.1.1’s Schema Object section treats readOnly and writeOnly as annotations. Validation may consider the annotation, direction and current value; a resource owner may ignore a readOnly field or treat it as an error. The specification notes a difference from 3.0. This discussion pins that specification version explicitly rather than generalizing across versions or generators.

An annotation is not authorization. Consider a client editing an order note and returning the entire response, including approval state. Passing that object directly into a database update would disregard the intended ownership of fields. This is a hypothetical design example, not an executed test or a claim about a particular framework.

Make ignore or reject an explicit contract

Ignoring protected fields can accommodate whole-object clients but may imply a requested change succeeded. Rejecting exposes misuse earlier but may break older clients. Choose deliberately, document the behavior and return an actionable error.

Map allowed properties into a defined update object, with approval changes handled through their own transition endpoint. Writable fields can still have role constraints. Schemas do not replace object-level authorization.

Compatibility also depends on consumers. An extra response field may trouble strict deserializers; a new required request field changes submission conditions. Verify actual clients and generator versions rather than relying on schema syntax checks.

Observe the stored result

A proposed acceptance test sends a valid note edit with a forged approval state. Under rejection, assert clear failure without partial modification. Under ignoring, assert the note changes as agreed while approval remains unchanged and the response is not misleading. Include nulls, nested objects and batch paths.

These tests have not been executed here. Generated client types reduce accidental misuse but cannot be the server’s only protection. Review the pinned specification, validator configuration, field policy and stored outcome together to locate where the promise is enforced.
