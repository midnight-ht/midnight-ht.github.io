Does readOnly automatically reject writes? OpenAPI 3.2.1 allows two choices

readOnly is a directional annotation, not a general write barrier. A server may ignore the submitted value or reject the request; the application still needs explicit mappings, permissions and observable outcomes.

Article

No. readOnly: true is not, by itself, a security rule that prevents a database update. The current OpenAPI version named in the headline treats readOnly and writeOnly as annotations. An implementation may perform extended validation using the annotation, request or response direction, and the field’s current value; the owning authority may ignore a read-only field or treat it as an error. The server must choose its behavior, and application code must still ensure that only intended fields are persisted. The specification text does not promise that every validator rejects the value by default.

Separate the contract, request validation and write behavior

An OpenAPI description is a contract between API authors and callers. Tools can use it to generate reference documentation, client types and validation helpers. It does not decide which fields a particular user may modify, nor does it rewrite an ORM update statement. These are three different layers: the contract marks status read-only; the request validator may or may not check a submitted status; and the business handler determines which properties reach the database. A label at the first two layers cannot protect a field if the third layer copies the request object wholesale into a persistent entity.

Specification versions also matter. The OpenAPI 3.0 line says a read-only property may be sent in a response and should not be sent in a request; if it is also required, that requirement applies to the response only. The 3.1 line adopted JSON Schema 2020-12 and explained how annotations can be checked with read/write direction. The current version keeps that framing and explicitly allows the owning authority to ignore the field or return an error. It also notes that ignoring an unchanged read-only value can help when PUT uses the same resource representation and the field is required in the response. Do not turn the older “SHOULD NOT be sent” into “every version and server MUST return 400.” See the OpenAPI 3.0 text and JSON Schema’s annotation guide in their versioned context.

A GET representation sent back through PUT makes the issue concrete

Suppose a read endpoint returns an order’s id, status, memo and updatedAt. A client wants to change the memo from “Ship Monday” to “Ship Tuesday” but sends the full representation in a PUT request. The id, status and updatedAt fields are maintained by the server. This order is a hypothetical design example, not a system we tested.

The mere presence of a read-only property does not answer what should happen. Does its value match the current state? Is the endpoint replacing the full representation or applying a partial change? Is the caller allowed to perform the state transition? Does the application update only memo, or map the complete object into storage? If the same request changes status from approved to cancelled, the server could reject it or ignore that property and apply the allowed memo change. Unless the response makes the choice clear, the caller may receive success without knowing whether the state change was accepted.

Request case Possible policy Misunderstanding to prevent
PUT returns the current value of a response-required field Ignore it or accept the unchanged value, then update writable fields Do not imply that the field itself was updated
PUT submits a different server-owned state Reject the request, or ignore the field and update only permitted data A general field mapper must not trigger an approval transition
PATCH omits the server-owned field Leave server state unchanged The meaning of omission and explicit null belongs to the selected PATCH contract
POST includes a server-generated ID Reject or ignore it and generate the ID on the server A caller-supplied ID does not prove ownership of a resource

This is a policy comparison, not a single answer selected by the specification. PUT and PATCH should not be collapsed into one rule: HTTP semantics define PUT in terms of creating or replacing the target resource state with the enclosed representation, while PATCH applies changes described by a patch document whose media type identifies its format. The PUT definition in RFC 9110 and PATCH definition in RFC 5789 therefore imply different handling for omitted fields. readOnly does not supply those request semantics.

Ignore, reject or preserve the old value depends on the operation

If existing clients routinely return the GET representation unchanged, rejecting every request that contains a read-only property can break requests that only intended to edit a memo. In that case, the server may ignore the value or accept it when unchanged, but it must document the rule and return the actual stored state. If a field is a critical state and callers are expected to understand that it cannot be changed, rejection can be clearer, provided clients can read the error and adjust. The specification permits both directions; API owners must weigh compatibility against clear failures.

The implementation can map the request into an explicit update object that contains only memo. The path parameter orderId identifies the target; after authorization, business logic checks whether that order is in a state where memo edits are permitted. A status transition goes through a separate command or transition function. “Writable” and “this caller may write it now” are different questions: a property open to a support agent is not thereby writable by an anonymous visitor. Field-level policy does not replace object ownership checks; see the site’s guide to object-level authorization.

A counterexample is binding the request JSON directly to a database entity and saving the entire row. Even if generated documentation hides status from an input form, an older client, a hand-crafted HTTP request, a batch import or an administrative job can submit the property. Successful schema validation only means the validator accepted the payload under its configuration; it does not establish authorization or safe persistence mapping. Another failure path is updating memo first, then discovering an invalid status and returning an error. Without a transaction or atomic update, the request appears to fail while the memo has changed. Evaluate the whole field policy before writing and keep the failure path within a transaction boundary.

Put the rule in observable outcomes, not only in the schema

Write a decision table for each endpoint and turn it into tests. Start with a known order state. Send separate requests for “valid memo, unchanged system value,” “valid memo, modified system value,” “invalid memo and modified system value,” and “a user without access to this order.” Do not check only the HTTP status; read the persisted values. On an accepted update, only memo should change. On rejection, every value should remain unchanged. On an ignored field, the response should show the real stored state rather than echoing the caller’s ignored value.

Cover write paths beyond the primary HTTP route. Batch endpoints, asynchronous tasks, administration tools and message consumers may reuse the same entity update function without passing through the same OpenAPI request schema. The service layer can map an explicit writable-field allowlist and check object ownership and state transitions before committing. Regression tests can assert database snapshots before and after the request and, where relevant, verify that an audit event records a rejected attempt. No requests were sent, database was connected, or API tests were run for this article; these are proposed checks, not a pass report.

If a schema is shared for reads and writes, define how the validator learns the operation direction, which annotations it interprets, and whether the current value affects the decision. If read/write properties, role permissions or state machines differ substantially, separate response and request schemas may express the boundary more clearly, but they add field synchronization and compatibility work. Where both models share stable structure, a shared base schema plus controlled composition or generated request models can reduce duplication. Do not assume that maintaining two copies is free simply because separation looks safer.

Assign the responsibility to the right layer

A concise review rule is: OpenAPI explains how a field should be understood; server-side mapping, authorization and state-transition logic determine whether it can actually change. For each write operation, document whether presence means ignore or reject, whether the unchanged value may be returned, which roles can update it, and whether failure is atomic. Then assert the stored result. Generated clients can help callers avoid mistakes, but they are not substitutes for a server-side field allowlist and permission check.

This rewrite checked the current OpenAPI specification, its 3.0.4 text and JSON Schema 2020-12 annotation guidance available on 26 November 2026. The version in the headline is dated 10 September 2026; 3.0.4 is dated 24 October 2024. The order, endpoint behavior and test matrix are hypothetical. No framework configuration, server, database, client generation or security test was executed. For the authorization boundary beyond read-only metadata, continue with object-level authorization and why a JSON Schema format annotation is not an assertion.
