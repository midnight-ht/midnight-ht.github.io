Image uploads need more than extension and MIME checks

Extensions, MIME and signatures are limited signals. A safer upload flow constrains parsing, quarantines unverified objects, binds review to a content version, and reauthorizes retrieval.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-26 · Estimated read 19 min
Translations
zh-CN en

Article

Key takeaways

  • Client filenames, extensions and multipart MIME values are submitter claims; the server cannot treat them as proof of content.
  • Signature recognition is not a complete safety proof; parsers, decoding resources, storage and public retrieval are part of the upload boundary.
  • Pending, rejected and deliverable should be distinct states; a review result must be bound to an immutable object version and cannot be reused after replacement.
  • Upload authentication and download authorization are separate checks; a failed asynchronous review should remain pending or fail closed rather than turn timeout into approval.

No. An extension, the MIME declaration in a multipart part, and a file signature are each limited signals. A safer upload boundary also constrains the server-side parser, quarantines unverified objects, binds a review result to the exact content version, and checks permissions again when the file is retrieved. A successful upload response can mean that reception finished; it does not prove that the file was approved, is public, or belongs to the person requesting it. The avatar flow below is hypothetical. No malicious sample, image parser, or scanning service was executed.

A filename and MIME value do not prove what the bytes are

Browser uploads commonly use multipart/form-data. RFC 7578 (2015), Section 4.2, defines the Content-Disposition header for a part and the optional filename parameter. A filename may be omitted in some cases. If supplied, the receiver must not use it blindly or trust directory path information it may contain. In other words, filename="avatar.jpg" is submitter-supplied metadata, not a server-verified type or safety conclusion. The RFC defines a form-data transport format; it does not specify how an application should review an image.

An extension is a cheap first business filter. If avatars only support JPEG and PNG, the service can reject formats it does not need. But filenames can be encoded, change case, or contain double extensions; the client also sets the MIME value. OWASP’s File Upload Cheat Sheet warns that the supplied Content-Type can be spoofed and says extension checks should occur after filename decoding. A string that “looks like an image” is not the same as bytes that parse as the intended image.

Server-side signature checks can reject some content that does not match the expected format, but they are not the same as fully parsing and validating a file. OWASP explicitly advises against relying on signatures alone. A file may start with a plausible header and still exercise a parser bug deeper in its structure. Even a file that decodes may consume substantial CPU, memory or temporary disk. A small compressed size alone does not establish a small processing cost. A useful model separates four questions: what the submitter claimed, what the bytes appear to be, whether the chosen parser can process them within limits, and who may see the result afterward.

Model quarantine as state, not as an obscure URL

Consider a hypothetical avatar pipeline. A user authenticates and receives an upload quota. The server creates a random object ID and stores the original bytes in quarantine with state pending. The object is not placed in an executable code directory, and an unguessable URL is not treated as authorization. The record captures the owner, object version or content digest, receipt time, and an application-generated storage name. If the original filename is displayed in the interface, encode it for its output context; never concatenate it into a server path.

An asynchronous worker reads one specific object version. It checks the allowed byte count, then uses a constrained image library to parse dimensions and pixel data, re-encode to an approved format when the product needs it, and remove metadata that need not be preserved. OWASP recommends decoding and re-encoding images, but also states that rewriting does not guarantee removal of all malicious content and that the image processor itself handles untrusted input. Limit which files it can read, its memory, runtime and network access. Concrete limits must be validated against the actual library, runtime, product image range and capacity budget; this article does not invent a universal safe threshold.

Even after processing succeeds, do not equate “the task returned zero” with approval. The worker should report the object ID and version it processed. The application can atomically move the state from pending to ready only if the current object is still that version, the owner remains valid, the derived output exists, and the relevant policy checks passed. Failures move the object to rejected or leave it pending with a recoverable reason. Temporary objects beyond their retention window move to expired and are removed. Whether to add antivirus or sandbox checks depends on the threat model, cost and supply-chain constraints. OWASP presents these as protections to use when available, not guarantees that every image flow already has them.

How a replacement race invalidates a review result

Suppose a user uploads image A and a queue worker begins parsing it. The user then replaces the bytes at the same storage key with image B. If the worker reads only by key, it may scan A and mark the record ready even though a later download returns B. One way to prevent this mismatch is to assign an immutable object version to each upload and have the review job carry the object ID, version and content digest. On completion, a database transaction compares the current version. If it differs, the stale result is discarded and the new version is processed; the old approval is not reused. This is an engineering response to replacement risk, not a database schema prescribed by OWASP.

Timeouts and retries also change the outcome. A worker may finish scanning but disconnect before writing its state, so the queue retries the task. A non-idempotent job could create duplicate renditions, charge twice, or overwrite a newer version. A work key such as “object version + processing-policy version” can let repeated consumers reuse a completed result. A retry must not make the object downloadable early. When a scanning service is unavailable, a public avatar might remain pending instead of becoming public; an internal low-risk draft might follow a documented delay policy. The choice is a business risk decision, but fail-open behavior should not be hidden in a generic timeout handler.

Storage success and permission to download are different

Upload authorization answers whether a principal may submit a file. Download authorization answers whether that principal may read that particular object. A private support attachment needs per-request checks for tenant, owner, sharing relation and state. A public avatar may use a public CDN, but only a derived image in ready state should be published; pending and rejected objects must not be exposed through a static directory. Predictable names, directory listing, a wrong cache key, or permissive object-storage ACLs can bypass an application permission layer. See object-level authorization for the related access-control boundary.

Choose storage for the business use. OWASP prefers a separate host; if that is not possible, it recommends storage outside the webroot and controlled mapping through an application handler or object store. A write-only directory can reduce direct web reads, but check whether the deployed server still has executable mappings, configuration overrides or alias behavior. If the product must publish original files directly, define who may publish, how to retract, CDN cache duration and how deletions propagate. Upload limits should not exist only in the form: the ingress proxy, application stream, storage quota and parser need aligned limits. Otherwise a request may exhaust resources before reaching business validation.

How to verify the complete lifecycle

A reviewable test plan follows state and object version instead of asserting only an HTTP status. Upload a normal avatar and confirm the quarantined object is not publicly readable. After approval, confirm the derived object corresponds to the reviewed version. Replace A with B and delay A’s old job; confirm it cannot approve B. Simulate parser timeout, worker retry, storage failure and user cancellation. Confirm that no path turns unverified content into ready, and check that temporary objects, renditions and queue state can be cleaned up or retried.

Input cases should include forged MIME, invalid signatures, signatures inconsistent with the actual format, double extensions, path characters, extreme dimensions, truncated files and parser failures. Access cases should include cross-user and cross-tenant reads, direct access to pending objects, cache hits for rejected objects, and old CDN URLs after a replacement. For each case, inspect database state, object-store version, response headers and actual visibility. Derive thresholds from allowed product formats, expected image range, actual parser resource limits and capacity budgets; record the parser version and runtime with test results.

This proposal has not been implemented or run here. The review questions are not only “did we check the extension and MIME?” Ask which parser handles the bytes, with what permissions and resource limits; which content version the review result refers to; what state follows a failure; and how the download path confirms the caller may read the object. Putting those decisions into the API contract, queue message and test matrix makes “images only” a verifiable business restriction instead of a security promise that the implementation may not meet.
