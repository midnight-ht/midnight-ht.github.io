Pagination needs a unique order and a cross-page consistency policy

Use a unique order for PostgreSQL pagination, and define what concurrent changes may do between pages.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-26 · Estimated read 17 min
Translations
zh-CN en

Article

Key takeaways

  • Before relying on LIMIT, make sure the complete sort key is unique; tied rows otherwise have no stable boundary.
  • A cursor records an ordering boundary, not a fixed set of rows across concurrent writes.
  • Choose separate policies for interactive lists, bounded reports, and long-running exports.

When pagination repeats or omits rows, first make the order unique, then decide which concurrent changes may appear between pages. LIMIT caps the number of rows; it does not assign permanent positions. Keyset pagination replaces “skip N rows” with “continue after this ordering boundary,” but it does not freeze the dataset across requests. The order-list example below is hypothetical. Its SQL is illustrative and has not been executed or benchmarked.

Tied sort values leave the boundary ambiguous

The PostgreSQL 18 LIMIT and OFFSET manual section recommends an ORDER BY that constrains rows into a unique order. Without it, different limits and offsets can produce different plans and subsets. Imagine an order list sorted by created_at DESC. Imported orders may share the same timestamp. If a page boundary falls inside that group, the database has no obligation to preserve the rows’ relative order across queries.

A stable unique tie-breaker, such as the order primary key, can define the order: ORDER BY created_at DESC, id DESC. The identifier separates tied rows; it does not prove that a larger ID is later in business time. If priority, name, or amount also affects ordering, every ordering component must be part of the boundary definition. The complete key combination must be unique. Adding a field at the end does not help if that field can still tie.

NULL values need an explicit policy too. An ORDER BY item can specify NULLS FIRST or NULLS LAST, but ordinary comparisons involving NULL do not behave like comparisons between ordinary values: SQL’s three-valued logic yields unknown. An API can partition null and non-null rows into separate cursor regions, or encode an explicit null marker and define the continuation rule for each region. Do not encode a cursor under one null ordering while the database uses another default.

OFFSET stores a position that inserts can push

Suppose each page contains 20 rows. After the first page is read, a new order is inserted at the front of the sort order. A second request with OFFSET 20 starts at row 21 of the new result set. A row near the end of the original first page may be returned again. If an earlier order is deleted, later rows move forward, and a row that belonged on page two can be skipped. The ORDER BY may be perfectly unique; the two requests still address different sets.

When investigating an intermittent duplicate, retain the filters, sort items, page size, offset or cursor, and writes between requests. One SQL statement and its row count are not enough to reproduce a moving boundary. The manual also notes that rows skipped by a large OFFSET still have to be computed by the server. Treat that as a cost signal to investigate with real data and plans, not as a fixed latency claim at any particular scale.

Cursor pagination fixes a boundary, not the dataset

For non-null, immutable created_at plus a unique id, a descending keyset query can carry the final row’s two values into the next request:

WHERE created_at < $cursor_time
   OR (created_at = $cursor_time AND id < $cursor_id)
ORDER BY created_at DESC, id DESC
LIMIT $page_size;

This SQL is a sketch of the boundary relationship, not an executed query. It assumes both columns are non-null, the filters remain unchanged, the sort direction stays fixed, and creation time is not later backfilled or edited. Comparison operators must match the sort direction. If the id direction changes to ascending, the comparison in the equal-timestamp branch must change too.

Keyset pagination prevents a new row at the front from shifting every later “skip N” position. But changes can still cross the cursor boundary. A newly inserted row whose sort value falls after the cursor may appear on a later page; one inserted into an already visited region will not be revisited. If a returned row’s mutable sort field moves it after the cursor, it may appear again. If another row moves before the cursor, the reader may never reach it. Deletion removes a row from the remaining result. Its token records sort values, not a database snapshot or an authorization decision. The server must still enforce the caller’s filter scope and consider signing, expiry, and cursor-version rules.

When the sort field can change, choose the guarantee the reader actually needs. A live operations console may care more about continuing through the current queue and accept that inserts or status changes alter the set. An audit export needs a repeatable membership set; a cursor alone is insufficient. Ordering by updated_at lets a status update move an order. Switching to immutable creation time may keep its browsing position stable, but does not freeze the order’s status or other contents.

A transaction snapshot does not span arbitrary browsing sessions

The PostgreSQL 18 transaction-isolation manual section says that under the default Read Committed level, each command gets a snapshot as the command starts. Two successive SELECT statements can therefore see commits made between them. Repeatable Read gives statements in the same transaction a consistent transaction snapshot. That can support multiple page reads inside a short transaction, but the boundary is the database transaction, not an HTTP request that returns minutes later.

Keeping a transaction and connection open for a browser session means managing connection occupancy, disconnect recovery, transaction timeouts, and users who abandon the page. Database cursors have their own lifetime: an ordinary cursor is transaction-scoped. A WITH HOLD cursor can survive commit in the same database session, but the official DECLARE documentation says that the current implementation copies the rows represented by a held cursor to temporary files or memory. This is not a stateless cursor string that any application instance can resume.

For a bounded report that must use one view, a server-side Repeatable Read transaction can finish the export promptly, with limits on row count, duration, and retry behavior. For a large export that a user may leave open for a long time, an asynchronous export job often makes the product boundary clearer: record the criteria, materialize the target IDs or generate the file at a defined time, then return job status and a download link. Freezing IDs fixes membership, not the values later read from those rows. If field values must also reflect one time, materialize the required fields or use an explicit snapshot strategy. Label the export with its generation time, filters, and expiry; do not present it as live pagination.

Acceptance tests must cover both ordering and change policy

For the hypothetical order list, the following are proposed test cases, not tests run here. Decide each expected result from product semantics rather than treating every change as a defect:

Scenario Contract to choose What to verify
Many rows share created_at id is a unique tie-breaker Tied rows retain order across reads
Insert before the next page Offset or keyset semantics Whether OFFSET repeats; whether keyset accepts new rows after its boundary
Delete between pages Whether membership must stay fixed Remaining rows respect the chosen boundary contract
Sort field changes Field is immutable, or movement is allowed Duplicates and omissions match the API promise
Filter changes Cursor is bound to filters Reject or reset a cursor used with a different status filter
NULL sort values Explicit null region and direction Continuation works from the null region
Retrying an export Frozen IDs or materialized file Retry returns the same members and version

Validate query plans and deep-page cost with actual data; see the EXPLAIN evidence guide. The PostgreSQL isolation and retry guide discusses isolation levels and transaction-failure boundaries. None of these tests was run for this article. Before release, translate the product guarantee into integration tests and confirm the selected index covers the full sort key.

The decision order is straightforward: define a total order, choose a page boundary, then state which changes between requests are allowed. For ordinary browsing where updates are acceptable, a unique order with keyset pagination is a clear interface design. When a reader needs a reproducible export, use a bounded transaction or an asynchronous materialization strategy. The token answers “where should reading continue?” It does not promise that every page represents the same dataset forever.
