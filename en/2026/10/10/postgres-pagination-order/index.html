Pagination needs a unique order and a cross-page consistency policy

Use a unique order for PostgreSQL pagination, and define what concurrent changes may do between pages.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-10 · Estimated read 5 min
Translations

Article

When pagination repeats or omits rows, first check whether the order is unique, then define what may change between reads. LIMIT caps quantity, not stable position. Cursors avoid skipped-row offsets but do not automatically create a shared snapshot. This order-list design was not executed or benchmarked.

Equal sort values leave positions unspecified

PostgreSQL 18’s LIMIT/OFFSET documentation requires an ordering that uniquely orders rows for predictable subsets. Skipped OFFSET rows still require computation; this supplies no fixed latency claim.

Imported orders may share a creation timestamp. Add a suitable unique identifier as a tie-breaker where permitted, checking direction, nulls and comparison rules. The identifier resolves ties rather than proving business chronology.

Even a unique order does not freeze the dataset. Inserts or deletions before a later offset can move its starting position. Investigation should retain the ordering and intervening writes, not merely one apparently correct query.

A cursor preserves a boundary, not the world

A cursor can carry the final row’s sort values and tie-breaker. Subsequent filtering and direction must match; changed filters require a new cursor. This is design guidance rather than a production query verified here.

Mutable update times can move rows across the boundary. Creation times and stable identifiers reduce some movement only if backfills and edits obey the assumed rules. Protect exposed cursor information according to risk, and enforce authorization independently of whether the cursor is readable.

Interactive browsing may reasonably show recent changes. An auditable financial export may require a common snapshot or frozen target identifiers. Long transactions introduce database responsibilities, so do not turn all browsing sessions into them.

Specify allowed changes in acceptance criteria

Proposed tests cover tied values, intervening inserts and deletes, mutable sort fields, changed filters and expired cursors. State whether repetition or omission is permitted rather than checking only page size.

Investigate deep-page cost with query-plan evidence; no improvement percentage has been measured. Choose read semantics before implementation: unique ordering and cross-page consistency are separate promises.
