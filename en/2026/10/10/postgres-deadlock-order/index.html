Row locks can still deadlock: why competing writers need one lock order

PostgreSQL 19 detects and breaks deadlock cycles, but cannot make the business operation succeed. Learn to order multi-resource locks, identify 40P01 and retry safely at the transaction boundary.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-26 · Estimated read 27 min
Translations
zh-CN en

Article

PostgreSQL 19 can detect a deadlock and abort one of the transactions involved, but that only breaks the wait cycle; it does not mean the business operation completed. Even when every statement uses row locks correctly, two transactions can wait on each other if they acquire several rows or lock types in opposite orders. A durable fix brings every writer under one inspectable resource-ordering rule. After 40P01, retry the complete transaction from fresh business state, rather than replaying the statement that happened to fail. The inventory-transfer example below is hypothetical; no database or concurrency test was run.

This article uses the PostgreSQL 19 documentation as its version baseline. The official release notes date PostgreSQL 19 to November 19, 2026. The locking, deadlock and SQLSTATE claims below follow PostgreSQL 19 documentation; deployments on another major release should check that release's documentation and verify how their database driver exposes error codes. This article does not claim to have run the example on PostgreSQL 19.

A row lock protects a row, not an acquisition order

The scope of a row lock is specific. SELECT ... FOR UPDATE locks the rows returned by the query. Other transactions that try to update or acquire a conflicting lock on those rows must wait. The lock is released when the transaction ends or rolls back. That coordinates competing changes to the same row, but it does not choose a global order for acquiring a set of rows.

Suppose an inventory table has two warehouses: warehouse 17 holds eight units and warehouse 42 holds three. Request A transfers two units from 17 to 42. Request B transfers one unit in the other direction. A locks 17, then asks for 42. B locks 42, then asks for 17. A owns a lock B needs; B owns a lock A needs. The wait graph contains a cycle. Adding FOR UPDATE to both paths does not remove the cycle. The locks are doing their job; the problem is the order in which they were requested.

The PostgreSQL 19 manual gives the same shape of example with two account rows: two transactions first lock different rows, then each asks for the row held by the other. The server detects the deadlock and aborts one transaction; applications must not depend on a particular transaction always being chosen as the victim. Its deadlock section recommends acquiring locks on multiple objects in a consistent order; when an object needs more than one lock mode, acquire the strongest mode that will be needed first. The useful invariant is not “add more locks.” It is “all participants follow the same partial order.”

Separate business order from lock order

For the hypothetical transfer, the business operation remains “subtract two units from the source warehouse, then add two to the destination.” The lock order can instead be ascending warehouse ID. A conceptual flow is: begin a transaction; normalize and validate source, destination and quantity; sort the resource identifiers; lock each row in that sorted order; reread the locked inventory and check the business conditions; apply both updates; commit. Whether the transfer goes from 17 to 42 or from 42 to 17, both transactions request 17 before 42.

This is a design sketch, not a complete implementation. The actual SQL, isolation level, constraints and update strategy depend on the schema and should be tested. Do not assume that one UPDATE ... WHERE id IN (...) acquires row locks in the business order you imagine. If correctness depends on order, use an acquisition path whose behavior you can establish in your system, and confirm it with execution and concurrency tests. The rule must also define duplicates, empty sets, parent-child resources and cross-table locks. Define it over resource keys rather than inventing a local comparison rule at each call site.

The writer inventory is often more useful than a list of SQL statements. The user-facing API, batch processor, compensation worker, admin console, scheduled job and repair script all belong to the same contention domain if they can lock the same resources. Imagine the online endpoint sorts by warehouse ID, while a compensation job updates rows in message order and a background recalculation locks an order before its inventory. These participants do not know that another path uses a different order. Fixing the main API may reduce the frequency of deadlocks, but it does not create a shared invariant.

The order may span lock types. A transaction can acquire table locks as well as row locks. Triggers, foreign-key checks or extension logic may touch objects that are not visible in the caller's immediate SQL. The manual describes table locks, row locks and advisory locks as distinct mechanisms. Application-defined advisory locks are cooperative: the server does not force every writer to acquire them. When drawing a resource-order graph, record the lock class, resource key, acquisition point and release boundary. If two orders cannot be unified, explain why they cannot participate in the same wait cycle.

Waiting longer does not repair a deadlock

A deadlock differs from an ordinary lock wait. A wait chain can have a transaction that proceeds and eventually releases the lock. In a deadlock, the dependency graph closes into a cycle. Without a detected deadlock, conflicting lock requests can wait until locks are released; the documentation therefore advises against holding transactions open for long periods. Keeping a transaction open across a network call, user confirmation, slow file read or uncontrolled external operation enlarges the time window in which locks remain held. Shortening that window can reduce exposure, but it does not replace an ordering rule. Increasing a client timeout changes how long the caller waits; it does not remove the database's circular dependency.

Another mistaken shortcut is to treat SERIALIZABLE as a universal deadlock switch. An isolation level controls the consistency guarantees transactions receive; it does not promise that locks never wait, deadlocks never happen, or retries are unnecessary. In v19, SQLSTATE 40001 means serialization failure and 40P01 means deadlock detection. Section 13.5 says serialization failures require retrying the complete transaction and deadlock failures may also be suitable for retry. A retry must include all logic that determines which SQL to issue and which values to use; the server does not perform it on the application's behalf because it cannot guarantee that a replay is correct.

Application code and logs should use SQLSTATE rather than parse a localized error message. The v19 error-code appendix lists the five-character codes. An application can count 40P01 and 40001 separately, record the transaction type and a redacted request correlation ID, and then inspect the transaction's statement path and wait objects. Production investigation can use official views such as pg_locks, but a snapshot shows one point in time. It cannot, by itself, prove that every service follows the same lock order.

Why replaying only the final statement can corrupt the operation

When the server aborts a transaction because of a deadlock, its database changes are rolled back. If the application catches the error and resends only the last SQL statement, it may skip checks performed at the start of the transaction or reuse a value read from a stale snapshot. The correct retry unit begins a new transaction, rereads the necessary state, revalidates the conditions, obtains locks under the same ordering rule and applies the operation again. Use a finite retry count, controlled backoff and clear final failure feedback. Those are application policies, not a universal PostgreSQL retry count or a documented best delay.

Retrying the full transaction still cannot roll back side effects that happened outside the database. Suppose an application publishes “inventory moved” to a message system before the transaction commits, and then PostgreSQL aborts the database transaction as a deadlock victim. A consumer now sees a fact that the database rejected. If the side effect must track the commit, use an appropriate handoff design, such as a transactional outbox, and make downstream consumption idempotent. See the related transaction and message handoff article; this discussion assumes no particular queue or outbox implementation.

Even if message publication happens after commit, a process can fail after the database commits but before the client receives confirmation. Retrying the whole operation can then apply it twice. A business operation needs a stable idempotency key or queryable operation state, with behavior that distinguishes “the previous attempt did not commit,” “it committed but the response was lost” and “it ultimately failed.” Some external operations cannot be included in a database transaction or fully deduplicated by an idempotency key. In that case, the compensation and manual-recovery boundary needs to be explicit; “automatic retry” must not conceal an uncertain outcome.

How can you verify the ordering rule reaches every writer?

Start by listing workflows and write paths, rather than repeatedly retrying in production. For each path, record the resources involved, which lock is requested first, whether a trigger or external service is involved, and where recovery begins after failure. Then check whether paths touching the same resource set use the same order and whether that set can be added to or replaced concurrently. If the set cannot be determined safely under concurrent changes, sorting the IDs that were read does not guarantee that the complete set remains unchanged. The design may need a higher-level business constraint, explicit coordination or a serializable strategy. The right choice depends on the permitted concurrency and write scope.

In an isolated test database, construct two transfers in opposite directions. Arrange for each transaction to acquire its first lock before asking for the second; record the actual SQLSTATE, waiting objects, entry point and final inventory-conservation result. Add the batch, compensation and cross-table paths, and check whether they follow the same rule. After a fix, verify two separate outcomes: whether the covered paths stop producing that wait cycle, and whether an aborted, retried or finally failed business operation is recorded exactly as the product requires. A lower deadlock count alone is insufficient because test traffic may not have exercised the original race. A conserved total alone is insufficient because duplicated transfers can preserve the total while assigning inventory to the wrong warehouse.

If deadlocks remain, do not immediately conclude that ordering is useless. Inspect which lock types appear in the wait graph. Look for table or row locks omitted from the map, triggers, foreign keys, advisory locks, or a writer using a different resource key. A consistent order can remove one class of cycle among the resources it covers; it cannot prove that arbitrary SQL, migration jobs and third-party extensions will never deadlock. The proposed tests have not been run here, and no production error rate or performance result is claimed.

When is consistent ordering not enough?

An operation that changes only one row may have lower exposure to reverse acquisition across multiple locks, but a foreign-key check, trigger or another transaction can still introduce additional locks. “Single-row write” does not prove that a system has no deadlocks. If requests touch dynamic resource sets, cross-tenant relationships or a hierarchy, a complete ordering rule may be difficult to define. First determine whether the business invariant can be represented by a constraint, one coordination row, partition-level serialization or another mechanism. Then compare the loss of concurrency from a wider lock scope with the queueing introduced by a coordination point.

An explicit advisory lock can fit mutual exclusion keys that do not map neatly to database rows, but it is a cooperation protocol. One path that forgets the lock bypasses the protection. The design must also handle key collisions, lock lifetime and the difference between transaction-level and session-level semantics. The documentation notes that session-level advisory locks do not follow rollback semantics like transaction-level locks, while transaction-level locks are released at transaction end. Check the documentation for the deployed major version and the exact function used before relying on either behavior.

The decision can be reduced to a short set of questions: Which objects make up one business operation? Can every writer use the same ordering key? Does the resource set remain stable after sorting? Can the complete business transaction be retried safely? Can external side effects be aligned with the commit result? If any answer is no, adding a row lock to one statement is not a complete design. Define a shared resource order; where that cannot be done, name the coordination mechanism; then verify both deadlock recovery and the business result. That is how a team can state what its row locks actually protect.
