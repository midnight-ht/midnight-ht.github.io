Row locks can still deadlock: order resources across every entry point

Prevent PostgreSQL deadlocks with consistent resource ordering across writers, and retry at the transaction boundary.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-10 · Estimated read 5 min
Translations

Article

Row locks coordinate writes but do not guarantee that acquiring several resources avoids a wait cycle. Examine resource ordering across every writer, not merely whether the failing statement uses a lock. Retry from the business transaction boundary. This inventory-transfer example was not executed.

Individually reasonable paths can conflict

PostgreSQL 18’s locking documentation describes deadlock detection and aborting one participant; applications cannot depend on a particular victim. It recommends consistent ordering and avoiding long-held transactions.

Imagine opposite transfers: one locks warehouse A then B, while another locks B then A. Both lock before changing stock yet can wait on each other. Lock acquisition can follow stable resource identifiers before business updates follow their own sequence. This recommendation is not a complete inventory implementation.

All entry points must share the rule. An API using identifier order can still conflict with compensation using message order or imports using file order. Review background jobs, administration and repairs alongside the main endpoint. Fixing one path does not prove elimination.

Shorten ownership rather than hiding waits

Prepare inputs before a short transaction where feasible, then recheck current state and write. Avoid unconditional external calls, user confirmation or slow file reads while holding locks. Longer timeouts do not remove a cycle and may extend queues.

On failure, roll back, reread necessary state and retry the complete operation under a defined policy. Database rollback does not undo external effects. Notifications or charges need their own idempotency, as discussed in transaction/message handoff.

Bound attempts and define final feedback. Unlimited retry can sustain load; swallowing errors falsely implies movement occurred. Asynchronous recovery needs queryable state, and enqueueing is not completed transfer. No universal retry interval is measured here.

Verify the relationship and the result

Proposed tests combine opposite transfers, bulk writes and compensation, retaining actual wait objects and entry points. Inspect business outcomes, retry limits and user feedback, not just error counts. Failure to reproduce cannot cover all production schedules.

These tests remain unexecuted. Retain correlatable request and transaction evidence without logging sensitive payloads. Every writer should explain its ordering and recovery boundary.
