How Can You Prove a Downloaded Build Is the One Approved?

A successful download and matching digest prove only part of an artifact handoff. Track source, workflow run, digest, provenance and approval separately so deployment cannot select a different build by name.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-26 · Estimated read 23 min
Translations
zh-CN en

Article

A successful download does not prove that the object is the build approved for release. A dependable handoff must answer three different questions: are the downloaded bytes the same as those uploaded, what source and workflow produced them, and which exact object does the release approval authorize? A digest mainly answers the first. Provenance evidence helps answer the second. An approval policy answers the third. This article uses a hypothetical GitHub Actions release flow; no workflow was run, no attestation was generated, and no real approval record was verified.

Write identity as a relationship you can trace backward

release.zip is a convenient label, not a complete identity. A repository can have several branches, workflows, reruns, and artifacts with the same name. If a deployment job selects “the latest successful release.zip,” it can pick up a newer rerun or a build from another branch. An approval record naming a source commit does not automatically constrain which file the download step eventually selects.

A release handoff can record these fields together: repository and source commit SHA; workflow file or workflow identity; run ID and attempt; artifact ID and display name; the digest returned by upload; the reviewer’s decision; and the target environment. GitHub’s artifact REST API example response includes an artifact id, name, digest, and a linked workflow run with id, head_branch, and head_sha. The upload action repository also says a successful upload exposes an artifact-id for REST API use and a SHA-256 artifact-digest. Those fields do not create an approval decision or prove that a team policy binds them. The deployment job should select the named artifact from the approved run, verify its digest again after downloading, and record the digest actually used. Including the attempt, target environment, and approval decision in the same relationship is an editorial recommendation, not an approval binding GitHub creates automatically. Artifact REST API; upload-artifact outputs If the archive is unpacked, repacked, configured, or compressed again after download, its bytes have changed. The final deployment object needs its own digest; the upstream archive digest must not be presented as proof of different bytes.

Consider a purely hypothetical flow: commit S1 triggers run R1, which produces an artifact called site-bundle and an upload digest D1. If approval says only “approve site-bundle,” the release job remains ambiguous. If the record identifies S1 / R1 / attempt 1 / artifact ID A1 / D1 / production, the deployment step can check whether it selected the same object. These symbols are illustrative; they are not actual run IDs or a real deployment system.

In the current workflow-artifacts guide, an artifact is a file or collection of files produced during a workflow run that can be retained after a job or passed to another job. For downloads from a different workflow or run, the guide says to supply a token and run identifier. The guide’s upload example uses upload-artifact@v4, while its download example uses download-artifact@v5. Those are the examples I checked, not a claim that they are the latest versions or behave identically in every environment. Workflow artifacts; Store and share workflow data

A digest checks bytes, not the producer

For digest validation, the official guide says each use of the upload-artifact action returns a SHA-256 digest. The download action recalculates the digest and compares it with the upload step’s output. If they differ, the workflow UI and job logs display a warning. The documentation does not promise that the warning automatically stops the next deployment step, so a release team must define the gate itself: a missing or mismatched digest stops deployment or enters an explicit human-resolution path. A warning that is ignored cannot be recorded as a successful verification. Validating artifacts

Suppose a deployment job processes the downloaded file. If it only unpacks the archive into a temporary directory and deployment still refers to the original archive, verify the archive digest and establish that the deployment input is the expected extracted tree. If a script changes files inside the package or repacks them, the new package is no longer the same bytes as D1; calculate a new digest and apply approval policy to that object. A digest match shows that the compared bytes match. By itself, it does not show that D1 came from a trusted workflow, belonged to the expected branch, or was reviewed by an authorized person. If an attacker or a misconfigured process can control both the file and the “expected digest,” recomputing the hash does not establish a trusted source.

The official guide describes upload-artifact v4 artifacts as immutable: files cannot be appended to an existing artifact as if it were an intermediate directory. The action repository also explains that overwrite: true fully replaces a same-named artifact with a new ID, and the previous object no longer exists. “Immutable” therefore describes an existing object that cannot be mutated in place; it does not mean a same-name reference always resolves to the original object. When a job transforms files, upload the result under another name. If an intentional overwrite is used, the approval record must check the new ID and digest rather than reusing the name. Either way, the control still needs to prevent selecting an artifact from the wrong run or detaching approval from selection. The name helps locate an item; a run/artifact identity says which item; a digest says which content. upload-artifact overwrite behavior

Provenance evidence is still not release approval

An artifact attestation can cryptographically link an artifact to build information such as its workflow, repository, organization, environment, source commit, triggering event, and OIDC-derived information. A consumer can use GitHub CLI’s gh attestation verify to check an attestation, then apply a policy to decide whether the source matches expectations. For example, a policy might require the repository, workflow, commit SHA, and deployment environment to match the approval record. The command does not decide which workflows are trustworthy or whether the software is safe.

The command below follows the documented form and is illustrative only; it was not run in this project or against any repository:

gh attestation verify path/to/release-binary -R OWNER/REPOSITORY

The attestation guide also warns that an attestation is not a guarantee that an artifact is secure. It links a consumer to the source and build instructions; the consumer still defines policy and evaluates the content. Creating an attestation that nobody verifies does not create an effective gate. Feature availability is also conditional: the documentation I opened says current GitHub plans support attestations except legacy Bronze, Silver, and Gold plans; Free, Pro, and Team support is limited to public repositories, while private or internal repositories require GitHub Enterprise Cloud. Verify the current plan, repository visibility, and account before adopting the feature; do not copy another project’s permissions as a universal template. Artifact attestations; Establish build provenance with artifact attestations

A release gate can therefore be layered. First, confirm the downloaded item came from the specified run and artifact. Then compare its digest with the upload output. If provenance matters for this release, verify the attestation and check policy conditions such as repository, commit, workflow, and environment. Finally, ensure the approval covers that digest or that verified provenance. A matching digest does not replace an attestation; a valid attestation does not replace business or security approval. A temporary test artifact may need only a run identity and retention record. A binary released for users has a stronger case for provenance verification. Controls should match the risk, consumer, and cost of recovery.

How to handle reruns, missing artifacts, and changes

The most easily missed failure is not a broken hash algorithm; it is selecting the wrong object from a set with similar names. Suppose R1, built from S1, is approved. Someone then reruns the workflow, or S2 uploads an artifact under the same name. If the deploy script queries for “the latest successful artifact” again, it may leave the approval boundary. Recording the run attempt, artifact identifier, and digest is a recommended way to avoid guessing based on chronology. Approval should identify an object, not only a branch or filename.

If an artifact is missing, expired, or its workflow run has been deleted, do not quietly rebuild another one and reuse the old approval. The workflow-artifacts guide says deleting a workflow run also deletes its artifacts; retention can also be limited by repository, organization, or enterprise policy. Mark the release as missing its approved object and return to build and approval. Even a new build from the same commit can be affected by changes in dependencies, runners, environment variables, or build process. Reusing a content-only approval is a possible team policy only if the policy explicitly approves by digest and provenance and other conditions still match. GitHub does not make that decision automatically.

How to prove deployment used the approved object

A release gate can use checks that do not depend on “latest”: before approval, store the source commit, run identity, attempt, artifact ID, and digest; at deployment, fetch by those identifiers; verify the downloaded digest; for releases that require provenance, check the attestation’s repository, workflow, commit, and environment conditions; if any transformation changes the bytes, calculate a new digest and apply the approval policy to the final object; and keep the final object identity in the deployment receipt. Missing fields, mismatches, policy failures, expired artifacts, or changed final content should have an explicit stop or re-approval path.

These are proposed checks, not tests performed for this article. Useful cases include: a download from the specified run; a same-name artifact from another commit cannot replace the approved object; a digest mismatch prevents deployment; a missing artifact does not trigger a silent rebuild; a rerun with a new attempt or new content needs a new approval binding; and repacking after download changes the final digest. Then check whether the deployment receipt can trace back to source and review records. Assert the actual stop state in tests, not merely that a warning appeared in a log.

Artifact identity is only one part of release and rollback. Configuration, database migrations, and rollback conditions also need verification; see release artifact and rollback checks. Token permissions affect who can upload, delete, or release an object; see workflow token permissions. Those links do not imply that the hypothetical workflow in this article was tested.

During a release review, ask the reviewer to start with the approval record and point back to the source commit, workflow run, exact artifact, digest, and deployment target. If the answer relies on “whichever one was latest” or a filename alone, the identity chain is incomplete. If the identifiers line up but there is no source trust policy or authorization binding, the digest has not supplied the missing approval. These are two separate gaps and should be fixed separately.
