A JSONB GIN index does not support every query shape

In PostgreSQL 18, JSONB GIN support depends on the operator class, indexed expression and data distribution. Compare key-existence, containment and path queries before diagnosing the plan.

Updated 2026-11-26 · Estimated read 22 min
Translations
zh-CN en

Article

Key takeaways

  • Check the operator class, indexed expression and JSON shape before diagnosing GIN usage.
  • jsonb_ops and jsonb_path_ops cover different operators; key existence, containment and path queries are distinct.
  • A sequential scan may be cost-effective; validate estimates, executed plans and production observations separately.

GIN is an inverted-index access method, not a universal index for every query against a JSON document. To determine whether PostgreSQL 18 can use one for a query, check at least four things: whether the operator belongs to the selected GIN operator class, whether the operator's left-hand expression matches the indexed column or expression, whether the relevant JSON shape produces searchable index entries, and whether the planner considers an index path worthwhile for the current data and estimated cost. The product-attribute examples below are hypothetical; no benchmark was run.

This article uses the PostgreSQL 18 JSON types and indexing documentation. That manual lists the version's JSONB GIN operator support and expression-index examples. For another major release, check that release's documentation and a plan from the target server. No index was created and no SQL was executed for this article; it makes no claim that a particular configuration is faster.

First distinguish an unsupported operator from a plan that does not choose an index

Suppose products.attributes stores supplier-specific fields such as {"region":"west","tags":["premium"]}. The product may need to answer three different questions: does the top-level document contain a region key; is its value west; and does the tags array contain premium? They all sound like “search the JSON,” but they are different SQL expressions:

attributes ? 'region'
attributes @> '{"region":"west"}'::jsonb
attributes -> 'tags' ? 'premium'

The default jsonb_ops GIN operator class supports ?, ?|, ?&, @>, @? and @@. The non-default jsonb_path_ops supports @>, @? and @@, but not the key-existence operator ?; the official operator list makes that difference explicit. If a team chose jsonb_path_ops for containment queries and later issues attributes ? 'region', the index's existence cannot compensate for an operator the class does not support. Inspect the operator class in the index definition and compare it with the emitted SQL. The column type and index name are not enough.

An indexable operator also does not guarantee that the indexed expression matches. The manual shows a whole-column index, GIN (jdoc), followed by the query jdoc -> 'tags' ? 'qui'. Although ? is supported by the default operator class, it is applied to jdoc -> 'tags', not directly to the indexed jdoc expression. The documented options include an expression GIN index on (jdoc -> 'tags') or a whole-document containment query such as jdoc @> '{"tags":["qui"]}'. The JSONB indexing examples explain this relationship. Choose based on whether the query is stable, what other fields are queried and whether the actual expression matches the index.

The semantics of the existence operator are another boundary. ? checks for an object key or array element at the top level of a JSONB value; it does not recursively look for a same-named key at any nesting level. For example, '{"profile":{"region":"west"}}'::jsonb ? 'region' does not mean “region appears somewhere in the document.” For a nested field, first decide whether the requirement is structural containment, a path predicate or a comparison against an extracted scalar. Then choose the corresponding operator and index form. Otherwise a plan may use an index while the query still fails to express the product's intended semantics.

Why operator classes trade coverage for index behavior

GIN indexes elements inside composite values. Its implementation guide describes an inverted structure organized around keys and the row identifiers associated with them. For JSONB, the operator class determines how keys are extracted from documents and query conditions and how candidate rows are checked. The default jsonb_ops stores key and value information separately; jsonb_path_ops combines a value with the path of keys that leads to it into a more specific index item. This helps explain why the path operator class is usually more compact and selective for the containment queries it supports, while giving up key-existence coverage.

That does not mean “path operator class is always better.” Imagine an administrative interface that runs attributes ? 'region', attributes @> '{"region":"west"}' and filters on several arbitrary fields. A jsonb_path_ops index does not support the first request. The default jsonb_ops covers more operators, but the number of index items, storage footprint and maintenance work depend on document shape. Conversely, if a stable hot path queries only tags, an expression index on (attributes -> 'tags') may index a narrower part of the document. It does not thereby become a general index for every other field.

Faster reads do not make write cost irrelevant. A JSON document can contain many indexable keys and values, so inserting or updating one row can cause multiple GIN index insertions. PostgreSQL's GIN fast-update documentation describes a pending list: with fast update enabled, some work is deferred and later merged in bulk. Searches must also inspect pending entries, and cleaning an oversized list can make one update slower than usual. Evaluate operator classes and expression indexes against query selectivity, document size and shape, write frequency and maintenance behavior, rather than the plan for one query alone.

One data shape can disappear from a tidy benchmark: a JSON structure containing no values. The PostgreSQL 18 JSONB index documentation notes that jsonb_path_ops creates no index entries for some such structures, including {"a":{}}; a search for one may require a full index scan. A test set containing only ordinary strings and numbers cannot represent production behavior for missing keys, empty objects, empty arrays, JSON null and SQL NULL. These states can carry different business meanings, so an evaluation should not remove rare structures merely to make the data look tidy.

A supported index path is not necessarily the planner's choice

The cases above concern capability and expression matching. A different case occurs when the query is supported but the plan shows a sequential scan. PostgreSQL chooses a plan based on query structure, data properties and estimated cost. A small table, a predicate returning most rows, heap-page reads associated with an index path, or statistics that do not reflect the current distribution can make a sequential scan a reasonable candidate. That is not automatically an “index failure.”

Start diagnosis by preserving the full SQL, parameter types, index definition, data volume and EXPLAIN output. Check whether the condition appears as an Index Cond, Recheck Cond or an ordinary Filter. The EXPLAIN guide for PostgreSQL 18 says plain EXPLAIN reports estimated costs and row counts, not actual elapsed time; EXPLAIN ANALYZE executes the query and reports actual rows and timing. Do not casually add ANALYZE to a write or side-effecting query in production: it executes the statement. Use a representative, controlled environment and compare estimated rows with the observed distribution.

If you already have a plan and need to interpret the gap between estimated rows, filter placement and execution evidence, see the related guide on reading PostgreSQL EXPLAIN evidence. That article explains plan nodes; this one defines the diagnostic sequence and does not replace validating a real query.

Disabling enable_seqscan is not a fix either. The planner configuration reference describes these settings as discouraging certain plan types; a plan may still include a discouraged node when necessary. In a controlled investigation, this can help compare alternatives, but it cannot prove an index is faster on production data. Nor is one forced-plan runtime evidence of a durable improvement: cache state, data distribution, concurrent writes and result size all affect the cost.

Use a query contract to choose a whole-column index, expression index or column

Write an index decision as a query contract instead of starting from “JSONB needs GIN.” Suppose attributes contains flexible supplier fields, while region is stable and frequently filtered. List the real questions: does the query only test whether region exists or compare a fixed value; are tags a top-level array or a nested object; is arbitrary attribute exploration needed; are missing and empty values distinct; and does the request require exact ordering or range comparisons? For each query, record its actual operator, indexed expression, operator class and expected results.

If requests mainly use several containment predicates against the whole document, evaluate whole-column jsonb_ops or jsonb_path_ops against the operators required. If a hot path consistently targets one stable subdocument, evaluate a targeted expression index. If an attribute has become stable and participates in constraints or ordering that need relational semantics, promoting it to a column may express the contract more directly. There is no universal winner. A narrower index covers fewer queries and may reduce the work per update; adding more indexes increases write maintenance, build time, disk use and operational responsibility. The CREATE INDEX reference permits indexes on expressions and warns that inappropriate indexes can reduce performance.

Verify the choice in layers. First compare DDL with SQL to confirm operator-class coverage and expression matching. Next prepare positive and negative cases for existence, containment, paths and empty structures to check semantics. Then preserve estimated EXPLAIN plans and assess whether estimated rows fit the data distribution. Finally, in a safe environment, measure actual rows, time, buffers and index-maintenance effects under representative read and write load with EXPLAIN ANALYZE. Estimates, executed plans and production observations are different kinds of evidence; one cannot replace another. None of these steps was run for this article, and no performance number is presented.

When a GIN index appears unused, the efficient order is: ask whether the operator class supports the operator; whether the indexed expression matches the WHERE expression; whether the JSON shape produces searchable entries; and only then why the optimizer chose its current plan. After the first three checks pass, a sequential scan may simply be cost-effective. Conversely, treating an unsupported operator as a statistics problem will not make it enter the index contract through tuning. This sequence keeps index capability, SQL semantics and cost selection separate.
