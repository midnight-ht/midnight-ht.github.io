Why are files still present after git stash?

Compare default, -u and -a in independent identical fixtures, inspecting entry identity, partial staging, recovery conflicts, and backup scope.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-01 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • Default, -u and -a have different save and cleanup scopes.
  • Restored text does not establish restored staging.
  • Conflicting pop retains the entry; local stash is not a remote backup.

Default git stash is not a complete directory snapshot. Tracked modifications, untracked files, and ignored files have different scopes: -u includes untracked files, while -a also includes ignored files. Before switching tasks, establish what entered which entry and what remains in the working tree rather than treating disappearing edits as a complete backup.

Establish the file class from actual state

The Git stash manual describes working-tree and index preservation and the default, include-untracked, and all options. The broader options also clean the corresponding working files. This article reread the online manual on November 1, 2026. No stash, cleanup, restoration, or private-file inspection was performed in this site's workspace.

A new file is not a sufficient classification. It may be untracked, already staged, or ignored. A tracked path does not leave the default scope merely because a later gitignore rule matches it. Gitignore and tracking state explains that neighboring boundary. Use current state rather than assumptions about filenames.

The index and working tree also differ. One tracked file can contain a staged change plus another unstaged change. Restoring its text does not establish that the original staging division was restored. An editor view alone cannot show what the next commit would contain.

Compare three independent practice repositories

This unexecuted script creates the same starting state in three disposable repositories under a new temporary directory. Every repository has tracked edits, avoiding the case where only untracked files exist and no ordinary entry is created. All strings are harmless training material. No remote or existing project is involved.

demo_root="$(mktemp -d)"
for mode in default untracked all; do
  repo="$demo_root/$mode"
  git init "$repo"
  git -C "$repo" config user.name Training
  git -C "$repo" config user.email training.invalid
  printf 'scratch.tmp\n' > "$repo/.gitignore"
  printf 'base\nmiddle\nbase\n' > "$repo/tracked.txt"
  git -C "$repo" add .gitignore tracked.txt
  git -C "$repo" commit -m initial
  printf 'staged\nmiddle\nbase\n' > "$repo/tracked.txt"
  git -C "$repo" add tracked.txt
  printf 'staged\nmiddle\nunstaged\n' > "$repo/tracked.txt"
  printf 'new training file\n' > "$repo/new.txt"
  printf 'ignored training file\n' > "$repo/scratch.tmp"
  git -C "$repo" status --short --ignored
  case "$mode" in
    default) git -C "$repo" stash push -m scope-default ;;
    untracked) git -C "$repo" stash push -u -m scope-untracked ;;
    all) git -C "$repo" stash push -a -m scope-all ;;
  esac
  stash_oid="$(git -C "$repo" rev-parse 'stash@{0}')"
  printf 'entry %s\n' "$stash_oid"
  git -C "$repo" stash show --include-untracked --stat "$stash_oid"
  git -C "$repo" status --short --ignored
  git -C "$repo" stash apply --index "$stash_oid"
  git -C "$repo" diff --cached -- tracked.txt
  git -C "$repo" diff -- tracked.txt
  git -C "$repo" status --short --ignored
done

The paper expectation is that the default handles tracked work while new.txt and scratch.tmp remain separate considerations. The -u case includes untracked material without thereby including ignored material. The -a case broadens the scope to ignored files and cleans the corresponding working paths. Record before-state, entry contents, and after-state rather than only how empty the directory looks.

Independent initial states prevent one case's cleanup from changing the next. Resolve and retain the entry object identity before inspection and application. Inserting another stash can move relative positions, so stash@{0} should not remain an unquestioned identity. No execution transcript accompanies these expectations.

When should you avoid including everything?

Ignored files can be caches, dependencies, large intermediates, or local credentials. Treating -a as the safest default can preserve material unsuitable for repository object storage. Inventory allowed contents and use explicit paths or separate data handling where appropriate rather than indiscriminately seeking a clean working tree.

Conversely, default exclusion does not make untracked files unimportant. A new API sample, design note, or unstaged source file may be essential. Establish its destination before cleanup instead of treating a command's success as permission to delete what remains.

Recovery context matters too. An entry depends on its original base, layout, and application assumptions. A textual application to another branch can still produce semantic conflicts. Long-lived handoffs may be clearer as an identified branch, commit, or another controlled record than an unexplained local entry, subject to secret and access requirements.

What should follow apply --index?

The fixture uses apply to retain the entry while checking text and staged differences. The --index option requests index restoration; it does not guarantee success in every conflicting scene. Identify existing work before recovery rather than mixing two changes and investigating ownership afterward.

For tracked.txt, compare cached and ordinary differences to verify the staged split. For new.txt and scratch.tmp, explain whether each was restored from the entry or never left the working tree. A filename reappearing is not proof of prior preservation. This comparison detects false reassurance that a final text view would miss.

Run normal build and behavior checks after recovery as needed. Successful patch application establishes its text/index result, not compatibility with the new branch's interfaces, dependencies, or runtime configuration. Temporary storage preserves work without granting an exemption from review.

Does a conflicting git stash pop delete the entry?

The manual states that a pop failing with conflicts leaves the entry in the list. Resolve the conflicts and explicitly decide on removal afterward. Do not blindly repeat pop or reset current work to make progress. Record the object identity and working state before selecting the next recovery operation.

A successful pop removes an entry in a way apply does not. Decide whether immediate list removal is intended rather than exchanging the commands merely because both can restore text. Verify required material and staging before deletion, particularly when untracked contents are involved.

A stash remains part of a local workflow, not an automatically uploaded cross-machine backup. Machine loss, repository deletion, and access changes need separate recovery arrangements. A clean working tree also cannot revoke an exposed credential. No restoration or deletion was executed here. Scope, object identity, recovery conditions, and excluded material are more useful safeguards than a command that merely reported no error.
