Should undefined become null when JSON.stringify drops a field?

Compare objects, JSON text and a complete pure patch policy to separate omission, array nulls, top-level undefined and retain-versus-clear semantics.

Key takeaways

  • Default object omission differs from null array positions.
  • Replacing undefined with null cannot authorize an endpoint's clearing policy.
  • Check objects, wire text, parsed structure and persistent outcome separately.

By default, JSON.stringify omits undefined object properties but writes null in corresponding array positions. Replacing every undefined with null is not a general repair: an update endpoint may interpret omission as retain and null as clear. Define the action, then inspect JSON text and parsed field presence rather than treating the original object as request evidence.

Position changes representation

The ECMAScript JSON serialization algorithms distinguish object and array processing. The MDN JSON.stringify reference illustrates undefined, functions and Symbols. This article checked the current ECMAScript 2027 draft and reference on November 1, 2026. No program below was executed.

An unsupported ordinary object-property value produces no member text. Arrays retain positions by producing null for these entries. At the top level, serializing undefined returns undefined rather than a JSON string. A sending path assuming text therefore needs a check before using that result.

These rules do not define update intent. Assigning undefined to an existing note may omit it, after which an endpoint's retain-on-omission policy leaves the note unchanged. Serialization followed its rule; the business action and representation did not align.

The reverse replacement can be harmful too. Turning unspecified values into null may clear fields the user never edited. A more complete-looking payload does not establish more accurate intent. Define absence, null and empty text for each relevant field.

A complete serialization and patch matrix

This unexecuted ESM program can be saved as note-patch-demo.mjs and run with Node without external dependencies. It defines a hypothetical pure-function policy: missing retains, null clears to a null value, and text updates. It is not a deployed endpoint or database and does not prescribe this policy universally.

const { stringify, parse } = JSON;
const owns = Object.hasOwn;
const original = { id: 'demo-1', note: 'keep this' };

function applyNote(before, patch) {
  if (patch === null || typeof patch !== 'object' || Array.isArray(patch)) {
    throw new TypeError('patch must be an object');
  }
  if (!owns(patch, 'note')) return Object.assign({}, before);
  const value = patch.note;
  if (value !== null && typeof value !== 'string') {
    throw new TypeError('note must be null or text');
  }
  return Object.assign({}, before, { note: value });
}

const cases = [
  ['missing', {}, 'keep this'],
  ['undefined', { note: undefined }, 'keep this'],
  ['null', { note: null }, null],
  ['empty', { note: '' }, ''],
  ['text', { note: 'new' }, 'new'],
];
for (const [name, input, expected] of cases) {
  const wire = stringify(input);
  if (typeof wire !== 'string') throw new TypeError('JSON text required');
  const received = parse(wire);
  const result = applyNote(original, received);
  if (result.note !== expected) throw new Error('unexpected patch outcome');
  console.log(name, wire, owns(received, 'note'), result.note);
}

const positional = stringify([undefined, () => 1, Symbol('demo')]);
if (positional !== '[null,null,null]') throw new Error('position mismatch');
if (stringify(undefined) !== undefined) throw new Error('top-level mismatch');
try {
  applyNote(original, { note: 42 });
  throw new Error('invalid type was accepted');
} catch (error) {
  if (!(error instanceof TypeError)) throw error;
}

The matrix compares input, generated text, parsed ownership and final value. The undefined case reaches the same retain branch as missing. Null remains present and takes the clearing branch. Here clearing means assigning null, not deleting the key; another product must define its chosen action separately.

Generating and printing wire is not network transmission. Returning a new object is not a commit. The matrix tests the connection between serialization and the stated pure policy. Real acceptance still needs parsing, authorization, persistence and a subsequent read through the actual interface.

A direct numeric note is rejected, but undefined has disappeared before the pure function receives parsed data. Validation location determines what remains observable. If explicit undefined must be rejected, check before information loss; a receiver cannot distinguish two identical JSON texts.

Why is property presence not sending evidence?

An own property containing undefined differs in memory from an absent property. Default serialization can erase that distinction. Label evidence as an original object, serialized text or parsed structure rather than comparing different stages unknowingly.

Logs may use another serializer or observation time. An expandable debugger object need not be the actual sent byte snapshot. Capture necessary redacted text or structure in controlled conditions and correlate stages by task identity, without copying private profiles into public logs.

Validate required information before sending and validate received requests independently. A client unable to represent intent should reject or use an agreed action, not silently omit. A server should not infer missing input from an old log. Shared type declarations do not merge those responsibilities.

Does a replacer converting undefined to null solve clearing?

It changes representation without establishing backend acceptance or meaning. Custom toJSON and replacer behavior also changes the default path; inspect the real object and wrapper. An object's conversion can produce a different value before later processing.

A common replacer can affect requests, caches, logs and signing material. They need not all accept missing-to-null normalization. A form fix may change another caller's identity or validation rules. Review actual call sites and migration behavior rather than treating one helper replacement as completion.

An explicit clearing operation can name that action; a partial-update document can define missing/null semantics. No serializer default universally decides retain, delete, inherit or reset. Those belong to the entity's contract.

Can null array entries simply be filtered out?

Check positional meaning. If another ID list is aligned by position, removing one entry shifts later associations. Retaining length also does not establish valid content. Where stable identity matters, retain identity and data together rather than treating serialized null positions as disposable noise.

A collection that deliberately ignores absent items still needs a chosen filtering boundary and checks for count, identity and order. Do not infer user intent merely because filtering made a request pass. Distinguish an empty array, null-only array and omitted array where the product requires it.

JSON parsing and long identifiers covers a separate numerical boundary. A field crossing the wire does not establish that its internal number stayed unchanged.

Proposed validation covers missing, undefined, null, empty text, array positions, top-level unsupported values and real custom conversions. Record sent text, parsed shape, patch action and final read, including failures and older clients. None was executed. Clearing is complete when the contracted update takes effect, not when a property name once appeared in memory.
