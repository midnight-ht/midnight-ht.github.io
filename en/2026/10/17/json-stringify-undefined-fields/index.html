Define missing fields before JSON serialization

Define missing and null fields before relying on default JSON serialization behavior.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-17 · Estimated read 6 min
Translations
zh-CN en

Article

By default, JSON.stringify omits object properties whose value is undefined but converts corresponding array entries to null. Define missing versus cleared fields explicitly. The JavaScript object visible before sending is not necessarily the JSON the server receives; inspect actual serialization.

Position changes the treatment

The MDN JSON.stringify reference documents these behaviors for undefined, functions and Symbols, which are not valid JSON values. Serializing certain such values directly can produce undefined rather than JSON text. Custom replacers and toJSON methods can change behavior, so default rules do not describe every project wrapper.

Imagine clearing an optional note by assigning undefined. If serialization omits it and the endpoint interprets omission as “leave unchanged,” the old note can remain. This scenario was not tested. Its outcome depends on the update protocol; JSON itself does not define business modification semantics.

Define missing, null and empty text

An absent property, explicit null and an empty string might mean retain, clear and empty input—or something else. Agree on their meanings across client and server. Replacing every undefined with null can introduce clearing or validation behavior that did not previously occur.

Array positions can also carry meaning. A null entry is not a removed entry. Unchanged array length does not establish complete data, while automatically filtering nulls can destroy positional correspondence. Serialization and collection policy need separate decisions.

Review custom conversion across requests, logs and caches. A debugger’s object display may not use the request serializer. Label observations as pre-conversion objects, JSON text or received structures; otherwise reviewers may compare different stages unknowingly.

Verify the network boundary

Proposed cases include ordinary values, omitted properties, null, empty text and nonrepresentable array values. State expected server behavior and check custom conversions for hidden fields or type changes. These tests were not executed and no project serialization logs are claimed.

Validate necessary information before sending, with independent server validation afterward. A property existing in client memory does not establish its presence in the request. Do not reconstruct user intent from an older logged object. Stable task identity and explicit errors are safer than silent defaults for state-changing requests.

Migration needs review of older clients’ missing/null assumptions. A new clearing meaning can affect stored data, so changing one helper is insufficient. Verify field contracts, callers and persistence together.

JSON parsing and long identifiers covers another boundary. This article addresses which fields cross the request boundary and how they are interpreted, rather than delegating business policy to serialization.
