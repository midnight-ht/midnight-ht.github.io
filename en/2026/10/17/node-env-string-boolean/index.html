Parse environment flags before startup: false, missing and invalid are different states

Use a strict boolean parser, valid and invalid input cases, and a fake service factory to verify pre-resource startup failure; distinguish that from effective configuration across instances and Workers.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-09 · Estimated read 15 min
Translations

Article

Key takeaways

  • Separate absence, accepted true/false tokens and invalid text; choose defaults for the specific flag.
  • Parse before creating resources and test types, exceptions and the off branch.
  • Workers normally have separate environment copies; updates require explicit propagation and adoption checks.

For a reliable off switch, parse configuration before opening the service: accept only documented tokens, choose a default for absence, and reject other spellings. A boolean-looking word in an environment file does not give business code a boolean value. Testing the resulting nonempty string still enters the enabled branch.

A false-looking value is not a parsed boolean

The Node.js environment-variable rules say that Node's own environment-file parser reads values as text rather than inferring boolean, numeric or object types. The reference checked for this revision is v26.13.0. An additional configuration library can implement conversions of its own; its rules must be checked separately.

The ECMAScript ToBoolean operation distinguishes the empty string from other strings. It does not recognize the English word false as a special instruction. Both Boolean('false') and Boolean('0') therefore produce true. Language coercion and the tokens accepted by an application are different contracts. Wrapping an environment value in Boolean repeats the original coercion rather than repairing it.

Suppose ENABLE_EXPORT controls an export feature. A maintainer intends false to disable it, but a business module tests the raw string and still registers the export entry point. Replacing that with “enable unless the value is false” leaves other states unresolved: a misspelled treu, an empty string and an uninjected value can take unintended paths. Enumerate the input states before deciding which ones permit startup.

A complete fixture includes the failure path

This example uses a strict policy: only the two lowercase words are accepted; absence defaults to disabled; empty input, uppercase words, numeric forms and surrounding spaces are rejected. The default is a choice for this hypothetical export flag, not a universal safe default for permissions, payment or migration controls. If a project accepts other casing or whitespace, make that normalization an explicit tested rule.

Save the following as config-fixture.mjs and run node config-fixture.mjs. The complete fixture was executed locally in this revision with Node.js v24.21.0. Its assertions cover a pure parser, a fake service factory's call order and the off branch. They do not verify a real export endpoint, container configuration or production deployment.

import assert from 'node:assert/strict';

function readFlag(raw, name, fallback) {
  if (raw === undefined) return fallback;
  if (raw === 'true') return true;
  if (raw === 'false') return false;
  throw new Error(`${name}: expected true or false`);
}

function loadConfig(env) {
  return Object.freeze({
    exportEnabled: readFlag(env.ENABLE_EXPORT, 'ENABLE_EXPORT', false)
  });
}

function boot(env, createService) {
  const config = loadConfig(env);
  return createService(config);
}

for (const [raw, expected] of [
  [undefined, false], ['true', true], ['false', false]
]) {
  const config = loadConfig({ ENABLE_EXPORT: raw });
  assert.equal(config.exportEnabled, expected);
  assert.equal(typeof config.exportEnabled, 'boolean');
  assert(Object.isFrozen(config));
}

for (const raw of ['', 'FALSE', ' false ', '0', 'treu']) {
  let created = 0;
  assert.throws(() => boot({ ENABLE_EXPORT: raw }, () => ++created),
    /ENABLE_EXPORT: expected true or false/);
  assert.equal(created, 0);
}

assert.equal(Boolean('false'), true);
let mode;
boot({ ENABLE_EXPORT: 'false' }, config => {
  mode = config.exportEnabled ? 'enabled' : 'disabled';
});
assert.equal(mode, 'disabled');
console.log('config fixture: parser, boot order and off branch passed');

The input matrix and factory count form the oracle together. All three valid states must produce actual booleans. All five invalid strings must throw while the factory count remains zero. Moving service creation ahead of parsing, or creating it after catching a configuration error, should break that second assertion. In a real application, place the seam around listeners, consumers or scheduled work. Testing a helper alone does not prove that every startup path uses it.

The exception omits the raw value. That avoids turning a diagnostic template into a secret leak if someone later reuses it for credentials. The option name and allowed forms identify the configuration problem. Operational reporting can expose validated nonsensitive flags and a configuration version without dumping the whole environment. Even option names may be sensitive in some systems; this is a bounded diagnostic policy, not a blanket disclosure rule.

Give the effective configuration an owner

A production entry point should load the agreed configuration sources, parse them and pass the result to the business factory. Creating a scheduled task while a separate module is still validating input means startup can fail after resources have become active. Define resource creation against the actual architecture rather than treating an HTTP listen call as the only possible side effect.

The frozen value here is a flat ordinary object containing one boolean. It discourages business code from modifying the validated flag; it does not freeze process.env or establish deep immutability for a complex configuration tree. Accepting an input object also lets tests supply individual cases without changing process-wide environment state. That makes the dependency visible and avoids another shared test variable.

Parsing once requires an explicit activation lifetime. Reading during module import, taking a startup snapshot and rereading on every request are different designs. A platform setting can change without existing instances restarting or reloading it. A screenshot of the setting is therefore insufficient evidence that business code adopted the new value. Dynamic configuration needs its own version, application acknowledgement and failure policy; assigning an environment property is not a distributed update protocol.

Does changing the main thread's value update an existing Worker?

Not by default. The process.env Worker documentation explains that each Worker normally has its own environment copy obtained at creation. The constructor's env option can explicitly choose a different source; default behavior is not a live shared feature flag. This adds a propagation condition between execution units, separate from the earlier text-parsing question.

For a hypothetical worker-based export task, the main thread may display disabled while an existing Worker still has the old configuration. Recreating the Worker is one option. Another is a versioned message whose receiver validates the update and reports the applied version. Until that acknowledgement arrives, retain a propagating state rather than announcing that every worker is disabled. Retry rules, in-flight work and partial receiver failures remain business decisions. No Worker hot-update or online shutdown experiment was executed for this article.

Release acceptance needs separate evidence for accepted parser inputs, use of validated types by the real startup entry point, and the actual feature's enabled and disabled behavior. The last check must also consider old instances when invalid configuration prevents a replacement from starting. A failed new instance does not prove that the old export service stopped. Feature-flag retirement covers ownership once a feature is fully rolled out.
