Which label wins when Prometheus creates exported_job?

Trace Prometheus job/instance conflicts with a local exporter and two scrape policies, preserving provenance and query identity.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-06 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • False and true choose different label owners.
  • Queries must match the resulting series identity.
  • External labels do not replace scrape-conflict policy.

honor_labels chooses precedence when scraped and server-added labels conflict. With false, conflicting scraped labels gain an exported_ prefix and server values are attached; true keeps the scraped values. Trace both sources before changing identity policy merely to remove a prefix.

One label can have two owners

The Prometheus configuration reference scopes this option to conflicts involving scraped labels and server-added labels, including job, instance, target labels, and service-discovery labels. The current reference was checked on November 6, 2026. No server or query was run, and the rolling page does not identify a deployed version.

Suppose an endpoint emits job=exporter-job while its scrape job has another name. The default policy renames the conflicting scraped label before attaching the server-managed value. exported_job can therefore be a scrape-stage result, rather than a second label originally exposed by the application.

True changes precedence, not formatting. It does not verify that a target's value is meaningful or trustworthy. Controlled federation or Pushgateway scenarios may need to preserve target identity. Ordinary application scraping still needs an explicit decision about who owns that identity.

A distinguishable local input

This complete, unexecuted exporter requires Python's standard library and an unused local port. Save it as exporter.py. It reads no business data and emits a teaching value of seven, two deliberately conflicting labels, and a nonconflicting scope label.

from http.server import BaseHTTPRequestHandler, HTTPServer

BODY = b'demo_value{job="exporter-job",instance="exporter-instance",scope="raw"} 7\n'

class Exporter(BaseHTTPRequestHandler):
    def do_GET(self):
        if self.path != "/metrics":
            self.send_error(404)
            return
        self.send_response(200)
        self.send_header("Content-Type", "text/plain; version=0.0.4")
        self.send_header("Content-Length", str(len(BODY)))
        self.end_headers()
        self.wfile.write(BODY)

HTTPServer(("localhost", 18080), Exporter).serve_forever()

Run python exporter.py in an owned terminal and first confirm the actual response. If the port belongs to another program, stop and choose another owned port; do not attribute that program's response to this fixture. Exposition is the first piece of comparison evidence, not an optional step before inspecting a graph legend.

Save this complete configuration as honor-demo.yml. Both jobs scrape the same endpoint. The nonconflicting demo_case label provides a stable selector while the conflict policy changes.

global:
  scrape_interval: 15s
scrape_configs:
  - job_name: server-false
    honor_labels: false
    static_configs:
      - targets: ['localhost:18080']
        labels:
          demo_case: 'false'
  - job_name: server-true
    honor_labels: true
    static_configs:
      - targets: ['localhost:18080']
        labels:
          demo_case: 'true'

In another terminal, use a matching local Prometheus with new storage and a separate listening port. The process runs in the foreground; inspect it from another terminal or browser. Stop only this owned process and exporter afterwards, without touching existing monitoring data.

honor_data=$(mktemp -d)
prometheus --config.file=honor-demo.yml --storage.tsdb.path="$honor_data" \
  --web.listen-address=localhost:19090

This command was not executed. Parsing configuration establishes syntax, not actual loading or a completed scrape. Confirm the running process, loaded file, endpoint, and scrape first. A port conflict or wrong file path fails earlier than label selection and must not be interpreted as an expected empty query.

The expected labels differ in specific places

For false, the paper expectation is job=server-false and instance=localhost:18080, with exported_job=exporter-job and exported_instance=exporter-instance preserving scraped values. For true, job and instance retain the endpoint's values while conflicting server values are ignored. demo_case still distinguishes the two results, and scope=raw does not change through this conflict rule.

These are derived expectations, not database output. The fixture does not already expose exported_ names, so it makes no claim about more complex repeated-name handling. New conflicts or simultaneous changes to exposition and configuration require a new derivation.

Use the stable nonconflicting selector to inspect both results:

demo_value{demo_case="false"}
demo_value{demo_case="true"}

A query insisting on job=server-true can miss the second result precisely because true preserves the endpoint's job. An empty query does not establish a failed scrape. Inspect full labels before changing selectors, and do not discard dimensions merely to make an old query return data; that can merge distinct sources.

Add a nonconflicting control: a teaching sample containing demo_plain and scope but no job or instance still permits server target labels to be attached. Changing this option should not invent exported_job without a conflict. Check the actual exposition before interpreting an absent metric as a successful filter.

Then independently change the endpoint’s job value while preserving the server job and demo_case. Under false, the server-job selector remains useful, while selectors using exported_job face the changed raw value. Under true, job itself follows the endpoint. Inspect complete labels rather than assuming one stable server field preserves every consumer’s condition.

Change exposition and policy separately and retain each input. Simultaneously changing job name, target address, and metric labels removes the controlled comparison needed to attribute the final legend.

Decide who should define identity

Ownership is the selection criterion. Federation may already carry source identity that must survive. Uncontrolled target labels should not silently become authorization or trusted business assertions. Preserving a value and establishing its accuracy are separate tasks.

Before changing policy, inventory dashboards, recording rules, alerts, and routes depending on job or instance. Subsequent samples can acquire a different label identity; existing history is not automatically rewritten. Validate new samples and their consumers rather than relying only on a successful target status. Compatibility and rollback need to follow actual dependencies, not a universal switching recipe.

Can changing external_labels repair a locally stored exported_job?

No. The reference says external_labels are unaffected by honor_labels. In communication with external systems, they fill labels a series does not already have and leave existing values alone. That is not another spelling of local scrape-conflict handling.

Adding cluster for external communication does not turn this fixture's stored exported_job back into job. Inspect scrape policy, exposition, and downstream selectors instead. Confusing communication-stage additions with ingestion-stage conflicts can change the remote payload without explaining the local legend.

The October 15 recording-rule label article addresses later changes through expressions and rules. This article covers the earlier scrape conflict. Preserve exposition, effective configuration, final labels, and query conditions to explain the prefix and identify who must adapt when precedence changes.
