Verify Kubernetes Service target port resolution

Trace Service entry ports, named targets and actual application listeners during rollout.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-17 · Estimated read 6 min
Translations
zh-CN en

Article

A Service's port is its entrance, while targetPort identifies the backend port and can reference a named Pod port. Changing the entrance number does not reconfigure an application's listener. Trace the entry point, backend selection and actual listening process separately.

Names separate a contract from a number

The Kubernetes Service guide explains targetPort mapping and its default to port when omitted. Pod port declarations can have names referenced by the Service. Backends using different numbers can remain behind one named contract. Inspect deployed objects rather than inferring runtime behavior from templates.

Imagine a stable service entrance while a new application version changes its listener. Updating only Service port may leave the backend mapping wrong. This scenario was not executed in a cluster. Selectors, endpoints, readiness and network policies can also cause failures and need independent evidence.

A declaration does not start a listener

Pod port declarations describe and support references; they do not configure the application process to listen. Startup arguments, environment and application settings still need agreement. Correct-looking YAML cannot establish connectivity to a process listening elsewhere.

With names, maintain spelling, protocol and ownership. A numeric change can preserve a named contract, while an arbitrary rename can break it. For multiple ports, distinguish Service port names from Pod target names; a shared field called name does not automatically connect them.

Selectors establish candidate Pods, while port settings establish how to address them. Correct selection does not prove a correct target, and a correct target does not prove business readiness. Preserve each layer's state and observation time.

Observe old and new instances

During rollout, inspect name resolution and actual listeners for both versions, together with endpoint state. One request reaching an older Pod does not validate the new version. No cluster commands or requests were executed here.

Proposed cases include no matching Pods, mismatched names, absent listeners and valid business responses. Distinguish connection failures from application errors. Save necessary object versions and request identities without dumping tokens or configuration secrets, and plan suitable recovery for traffic changes.

Keep interface documentation aligned with the stable Service entrance. Clients should not need arbitrary changes because an internal port changed. If the external entrance changes, treat it as a consumer-visible change with compatibility and communication planning, not merely a manifest edit.

Probe responsibilities discusses readiness separately. Verify entrance, target resolution and process listening to locate where traffic stops.
