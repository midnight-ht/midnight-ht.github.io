Keep a Kubernetes Service port stable while backend ports change

Trace a stable Kubernetes Service entry through named target ports, separate backend cohorts, and all related EndpointSlices.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-05 · Estimated read 13 min
Translations

Article

Key takeaways

  • A stable entry can map one target name to different backend numbers.
  • Service port names and Pod port references have different roles.
  • Inspect all slices, actual listeners, and requests to both cohorts.

A Kubernetes Service can map a stable port to a named targetPort. Old and new Pods can use different numbers under the same port name, provided selection, name resolution, and the actual listener agree. A port declaration does not start the application listener, and changing the Service entry port does not reconfigure the process.

Separate the client entry from backend implementation

The Kubernetes Service documentation describes mapping port to targetPort. If targetPort is omitted, it defaults to port. Pod ports can have names, and a Service can reference that name. Backends sharing a name and protocol may use different numbers, allowing a gradual listener-port change.

The migration example follows official pages checked on November 5, 2026. Navigation version labels do not establish the version of any deployed cluster. No cluster, manifests, or requests were executed; names and numbers below are teaching inputs.

Suppose clients always use report-service on port 80. The old application listens on 8080 and its replacement listens on 9090. Clients need not change addresses for that internal implementation change. Keep the Service entry stable and use the target name web. Each Pod resolves that name through its own declaration, which must agree with its actual application listener.

One Service and two Pod cohorts

This Service selects Pods labeled app=report and uses TCP. It expresses the relationship, but supplies neither a complete workload nor an image and process configuration. It is not a runnable deployment tutorial.

apiVersion: v1
kind: Service
metadata:
  name: report-service
spec:
  selector:
    app: report
  ports:
    - name: public-http
      protocol: TCP
      port: 80
      targetPort: web

The old and new workloads respectively contain these fields. They are separate Pod-container fragments, not two same-named ports to combine into one container. The application startup configuration must also select the corresponding listener; containerPort does not launch it.

# old Pod container fragment
ports:
  - name: web
    containerPort: 8080
    protocol: TCP

# new Pod container fragment
ports:
  - name: web
    containerPort: 9090
    protocol: TCP

The expected relationship is explicit: Service port 80 maps to old-cohort port 8080 and new-cohort port 9090. Changing Service port to 9090 instead changes the client entry and fails to express the cohort-specific targets. Omitting targetPort also changes the contract, because the default then follows port rather than resolving a stable name.

Inspect real selector inputs too. Both cohorts need the expected label to enter this candidate set. Correct naming does not compensate for an unmatched selector, and matching labels do not prove the named port exists. These are independent relationships.

Why one EndpointSlice is not the whole answer

The EndpointSlices documentation states that the same named port can resolve to different numbers across Pods, requiring different EndpointSlices. A slice showing only 8080 does not establish that the 9090 cohort is absent or broken. Enumerate all slices associated with the Service, then associate endpoint identity with each cohort.

A proposed read-only inspection starts with the actual Service selector, port, and targetPort. List matching Pods and their labels, named ports, and readiness conditions. Then inspect every EndpointSlice labeled kubernetes.io/service-name=report-service. This is a field-level inspection plan, not fabricated kubectl output or addresses from a real cluster.

Resolved ports show the control plane's backend representation, not proven network reachability. In an authorized environment, inspect actual process listeners and request each cohort, identifying response version and contents. One successful request through the Service may happen to reach only an old Pod. More anonymous requests still leave uncertainty about which backends were covered.

Must the two name fields match?

No. The name of the Service port entry and the Pod port name referenced by targetPort have different roles. public-http identifies this Service port; web is the backend name being resolved. They need not be cosmetically identical. The required agreement is between the targetPort reference, each relevant Pod port name and protocol, and the actual listening number.

If the new cohort renames web to http while the Service still references web, its correct numeric declaration does not preserve the named contract. Fix that relationship rather than broadening the selector. A broader selector may introduce an unrelated application and turn a naming problem into misrouting.

What if the declaration says 9090 but the process uses 8080?

Correct the disagreement between process configuration and declaration, then inspect the real listener. Editing containerPort does not create a new socket. Also verify the binding address and actual access path; matching numbers do not exclude other network failures.

Make the diagnostic branches explicit. If the new cohort has no resolved target, inspect naming and selection. If a 9090 target exists but connections fail, inspect its listener and network path. If connection succeeds but content identifies the wrong version, inspect response identity and application behavior. Changing the Service entry port in all three cases changes the client contract without necessarily addressing the cause.

A teaching acceptance exercise can introduce a name mismatch, no listener, no selector match, and a normal response as separate inputs. Save Service, cohort, and all associated slice observations with times, then inspect connection results. Components do not update atomically, so snapshots from different moments cannot be combined into a single instantaneous conclusion. Run fault changes only in an owned isolated environment with the original configuration available for restoration.

Readiness and termination also affect endpoint use. The October 24 EndpointSlice termination-state article explains ready, serving, and terminating, including configuration exceptions. An address appearing in a slice does not establish reachability. Correct named-port resolution is one step in request-path verification, rather than the end of release acceptance.

For an internal number change, keeping the entry port and name stable can avoid client migration. An intentional external-entry change needs its own compatibility and communication plan. Identify the layer being changed, then verify entry, target resolution, and listener separately.
