What does an HTTPS report page send in Referer?

Three receiving endpoints show which address fields the referrer can contain and how to tell whether the browser sent the request.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-13 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • Same-origin navigation can retain the path and query.
  • A trustworthy cross-origin destination normally receives only the origin.
  • Confirm that an HTTP request actually arrived before evaluating the downgrade case.

Under strict-origin-when-cross-origin, a navigation from an HTTPS report to the same origin can still send the report path and query in Referer. A navigation from that page to another HTTPS origin normally sends only the origin. Keep the report URL fixed across the same-origin, trustworthy cross-origin and downgrade checks.

Imagine a reporting product that lets customers return from help to the original view and gives a partner enough information to identify the referring product. Both links use HTTPS, so the team writes one acceptance condition for what their recipients can see. That condition lacks an input: the relationship of each destination to the report’s origin. If a help page needs only to return users to the report landing page, receiving the particular report number may already exceed its purpose.

Hold the report URL fixed and change the recipient

The W3C Referrer Policy editor’s draft identifies this policy as the default. With a short address, no extra browser privacy restriction and no element or redirect overriding the policy, the same-origin request uses the stripped referrer URL. A cross-origin request to a trustworthy destination uses the referrer’s origin. A request from a trustworthy referrer to an untrustworthy destination omits the header. Browser settings can reduce the information further, so compare these expectations with observations in the target browser.

Use a hypothetical report at https://reports.example.test/monthly?case=DEMO-42#chart and explicitly set the policy in that page’s response. Open each controlled receiver by following an ordinary link. Return to the original report before following the next one. These reserved addresses and synthetic identifiers describe a test design. Configure your own controlled receivers and certificates to run it. No browser was run for this article, and no requests were sent to these addresses.

Call the report’s origin R, the support origin S and the legacy origin L. The support origin uses a different host under the same parent domain. The legacy origin uses ordinary HTTP and is untrustworthy. Give the three receivers the same collection path.

Receiving endpoint Expected referrer on the receiving request
Collector on R R plus the report path and synthetic query, without the fragment
Collector on S The serialized R with its root slash
Collector on L Absent, provided an HTTP request to the untrustworthy address actually occurred

In the first row the report number remains and the fragment disappears. The referrer stripping algorithm removes the fragment and user information. The origin-only form also discards the path and query. The second row deliberately uses another host under the same parent domain. An origin is identified by its scheme, host and port. A shared parent domain does not make the two hosts same-origin. Check the observed value again if the help endpoint moves to another host.

The third row is easy to misread. A browser can upgrade the old endpoint to HTTPS or block the navigation. If the receiver gets nothing, record that observation first. Then use the browser’s network view to distinguish a request that never went out, a scheme upgrade and other failures. Only an HTTP request that actually reaches the receiver can show whether that request carried the header. A broken configuration, a certificate failure or a timeout could also leave no referrer value in the logs.

Rule out a gap in observation

Use the same small record at each receiving endpoint. Capture the test case, receiving scheme, receiving host and whether the header was present, along with its value. A test identifier in the controlled receiving path can align the network view with the server record. Read the agreed synthetic fields and avoid copying full requests, session state or user addresses into a shared issue. If a proxy might change the header, inspect the edge and application observations separately to see where the value disappeared.

Run the same-origin positive control first. If all three rows omit the referrer, the observations do not establish that each policy path worked. Browser preferences, log filtering and proxy changes can look identical in the final records. Confirm that the same-origin request arrived and check the browser network view to see whether it was absent before sending or removed later. Once that observation chain works, match the cross-origin result to the attribution requirement.

For a separate control, place a synthetic number in the destination URL query while suppressing the referrer. The receiving application can still read the number from the destination URL. That control distinguishes two data paths and explains why an acceptance test needs to examine both. If an identifier need not appear in a browser URL, keep it on the server or redesign how it is passed. Authorization should still verify that the current principal may read the report. The presence or absence of the referrer does not grant access. See retaining evidence without spreading secrets for the related question of what diagnostic records to keep.

Match disclosure to the recipient’s purpose

If a partner needs only product attribution, check whether origin-level information is sufficient. If internal help needs only to return to the reports landing page, provide an explicit return link so the help page need not interpret the current report from the referrer. If both same-origin and trustworthy cross-origin destinations need only the origin, evaluate strict-origin. If the report must omit the referrer on every navigation, evaluate no-referrer and use the same cases to check whether existing behavior depends on the field. The policy governs this browser-generated header. Check destination URLs and log records separately.

During rollout, record the layer that sets the effective policy. A proxy can add a response header, a document can set a policy and an individual link can carry an attribute. When the receiver-visible output is part of the acceptance criteria, a change to any one of those layers can be checked against the original data contract.

Can one same-origin link omit the referrer?

Yes. To preserve other same-origin navigations on the report page, add referrerpolicy="no-referrer" to that ordinary hyperlink. The HTML hyperlink referrer policy algorithm uses the attribute when following the link. Keep an ordinary link from the same page to the same receiver as a control, so the requests differ only in the link attribute. If the application intercepts the click and issues another kind of request, check the request it actually issues. This follow-up was also unexecuted.
