Why PostgreSQL COUNT(*) and COUNT(column) disagree

Align PostgreSQL row, non-null-contact, and applicant counts in a department report, checking outer-join placeholders, empty text, and attachment fan-out.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-05 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • COUNT sees the input reaching aggregation, not an automatically restored business-object set.
  • Count non-null matched identities for empty outer-join groups; empty text remains non-null.
  • Applications, applicants, and contacts use different units, especially after attachment fan-out.

COUNT(*) counts input rows, while COUNT(column) counts non-null inputs. Establish what each row represents first: after a left join, a star can count a department’s placeholder row even when no application exists. Replacing a nullable field with a star can fix one metric and inflate another.

A department report might need application records, applications providing contact information, and distinct applicants. One person can submit twice; contact information can be absent; an empty department may still need a row. Name the metrics before adding DISTINCT to reconcile the numbers.

Aggregation receives an already-shaped input

The PostgreSQL 18 aggregate reference defines star counting as input rows and expression counting as rows whose expression is not null. Filters may already have removed rows, and joins may have multiplied them. COUNT does not restore the original business-object count.

The aggregate-expression section explains that COUNT(DISTINCT expression) counts distinct non-null values. Applicant counts need actual applicant identity. Names can merge different people, while application IDs still identify applications rather than people.

Define the department, status, observation time, authorization scope, and counting unit. No function can decide whether drafts, withdrawn records, or inaccessible objects belong in the denominator.

Keep empty departments explicitly

This complete SQL is unexecuted teaching material. Real application IDs are non-null in the example. Department one has two applications from one person, one without contact information. Department two has an empty string, and department three has no application.

WITH departments(id) AS (VALUES (1), (2), (3)),
applications(id, dept_id, applicant_id, contact) AS (
  VALUES (11, 1, 101, 'ada@example.test'::text),
         (12, 1, 101, NULL::text),
         (21, 2, 201, ''::text)
)
SELECT d.id AS department,
       count(*) AS joined_rows,
       count(a.id) AS applications,
       count(a.contact) AS nonnull_contacts,
       count(DISTINCT a.applicant_id) AS applicants
FROM departments AS d
LEFT JOIN applications AS a ON a.dept_id = d.id
GROUP BY d.id
ORDER BY d.id;

Derived counts are 2,2,1,1 for department one; 1,1,1,1 for department two; and 1,0,0,0 for department three. The final star count includes the outer join’s placeholder row, not an invented application. Counting a.id represents actual matches only because that identity is non-null for real applications.

Check departments individually, including their presence. Losing an empty department while multiplying another can produce a plausible total over an incorrect result set. Verify department identities and the application and applicant sets behind each metric.

Does an empty string count as missing?

Not to COUNT. It is a non-null input. If the business excludes empty text, state that extra condition, for example with FILTER requiring contact IS NOT NULL and contact different from the empty string. That changes the metric rather than correcting the function.

Whitespace-only strings need another policy. Trimming affects stored or compared values and belongs to an input-normalization contract. Non-null contact data also does not establish correct formatting, reachability, or verification; those stronger labels require their own evidence.

COALESCE is not a general fix. Replacing null with empty text makes the expression non-null and can even cause a placeholder to count. It has not discovered another application. COUNT already returns zero for no qualifying input, so display requirements should not silently change the counted expression.

Why can attachments inflate the result again?

If application eleven has two attachments and application twelve one, joining attachments can produce three department-one detail rows. Both the star and the application-ID count then count application eleven twice. Its contact field can also repeat without anyone providing another contact value. The null rule has not changed; the input grain has.

Form one row per application before application-level metrics. If attachments only qualify an application, consider an existence condition; if their quantity matters, aggregate it at its own grain. COUNT(DISTINCT a.id) can express a unique application count, but it should not conceal an incorrect join while other metrics remain multiplied.

Filtering can also remove empty departments. If the report retains every department while counting submitted applications, define qualifying matches deliberately. A right-side status predicate in WHERE can remove unmatched rows. The October 18, 2026 article on LEFT JOIN predicate placement explains that separate boundary.

Write acceptance as identity sets

List expected application IDs, qualifying-contact application IDs, and applicant IDs per department, then count each set. Include nulls, empty strings, repeated applicants, empty departments, and multiple attachments. Check both values and whether each department remains present. No SQL was executed here; the numbers are expectations derived from the stated input.

Preserve query versions and effective dates when changing definitions. A higher historical curve may reflect a switch from non-null contacts to applications, not business growth. Explain the difference and consider recalculation before comparing periods. Measure plans and workload after fixing semantics rather than declaring one count form universally faster.

Exports and pages need the same definitions. A page showing applications and an export still counting contacts can give downstream consumers two incompatible fields both named “count.” Preserve the metric name, scope, and version in an appropriate interface or report description without exposing unnecessary internal data. A reliable number traces to that definition rather than merely agreeing with another column.
