Choose a PostgreSQL count that matches the metric

Match PostgreSQL row and non-null counts to an explicit metric definition.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-17 · Estimated read 6 min
Translations
zh-CN en

Article

COUNT(*) counts input rows; COUNT(expression) counts rows where that expression is not null. Match metric names to their query semantics. Different results need not indicate a database error: establish what each row represents and whether the counted expression can be null.

The same input supports different counts

The PostgreSQL 18 aggregate reference defines these two forms separately. Their input is the row set reaching aggregation. Filters and joins may already have changed it, so a final count is not automatically the number of original table records.

Imagine a metric called “submitted applications” counting an optional contact field. Applications without that field are excluded. This unexecuted example would be a mismatch if the requirement concerns submissions, but could be correct for “applications providing contact information.”

Write the complete metric definition

Specify the object, filters, observation time and counting unit. Application records, distinct applicants and applications with certain information are different measures. Replacing a field with a star cannot solve every distinction. One applicant may submit several applications.

Joins require cardinality review. A single application joined to several details produces several input rows, which COUNT(*) counts. Business-object counting requires the appropriate relationship and aggregation. Adding deduplication merely because a number looks large can conceal an incorrect join or model.

Replacing missing values with zero is not a universal correction. Making an expression non-null can change which rows count. That must be deliberate business policy. Unknown, unprovided and actual zero may need to remain distinct.

Use interpretable acceptance data

Proposed samples include complete fields, null fields, several details for one object and no matching input. List expected input rows and metrics before checking the query. No SQL or performance tests were executed here; these are acceptance-design suggestions.

Preserve query versions and field definitions in reports. Changing the count can alter a historical curve without establishing growth or loss. Explain the definition change and recalculate where appropriate rather than presenting a technical correction as a product outcome.

Optimize after semantics are fixed. Plans, indexes and data scale affect cost; a function name does not establish which form is always faster. A faster answer to a different metric is not a valid optimization.

Array count definitions examines a related distinction. A useful count is explained by its input set and business meaning, not by two columns happening to agree.
