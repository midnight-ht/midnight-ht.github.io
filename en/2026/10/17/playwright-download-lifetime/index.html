Why is a Playwright download lost after its event fires?

Join download events, explicit saving, content validation and CI retention, including remote path limitations.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-05 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • The download event marks a start, not completed persistence.
  • Await saveAs and inspect this task’s content.
  • Remote path limits and CI upload need separate handling.

The download event fires when a download starts. Await saveAs in the main test and finish persistence and checks before closing the context. A successful click, a download object, a saved file and correct business content are four separately fallible stages.

The Playwright downloads guide starts waiting before the click, awaits the object and then saves. It warns that context closure deletes its downloads and that asynchronous event-handler work may outlive the main scenario. This rewrite preserves the original publication date and URL. It adds a complete teaching test and failure distinctions without claiming a real export run.

Give temporary downloads and test artifacts different ownership

The Download API emits the event at download start; the path becomes available after completion. SaveAs copies to a caller-specified destination and can be called while downloading, waiting as necessary. Keep that promise in the main test's accountable control flow.

The browser context owns its temporary downloads. A test-output directory belongs to the test runner and subsequent CI retention process. Explicit copying establishes a destination, but cleanup, upload and retention still need owners. SaveAs returning does not prove upload to a remote artifact store or correctness of a real export service.

SuggestedFilename is browser-computed information derived from sources such as Content-Disposition or the download attribute. Browsers may compute it differently. It can be an experience assertion without controlling the local destination. A test-owned path also makes parallel isolation easier to explain. Download filename trust boundaries examines that responsibility.

A complete test with an explicit content expectation

This Playwright test has not been executed and calls no real export endpoint. It creates fixed CSV data in the page and checks event waiting, saveAs and saved content. Literal text comparison is intentional for this two-column fixture. Real CSV with quoting, embedded newlines or different encoding needs an appropriate parser and business assertions.

import { test, expect } from '@playwright/test';
import { readFile } from 'node:fs/promises';

test('preserve a teaching download', async ({ page }, testInfo) => {
  const csv = 'record_id,status\nteaching-42,ready\n';
  await page.setContent(`<!doctype html><html lang="en">
    <meta charset="utf-8"><button type="button" id="export">Export fixture</button>
    <script>
    document.querySelector('#export').onclick = () => {
      const text = ${JSON.stringify(csv)};
      const link = document.createElement('a');
      link.href = 'data:text/csv;charset=utf-8,' + encodeURIComponent(text);
      link.download = 'teaching.csv';
      document.body.append(link);
      link.click();
      link.remove();
    };
    </script></html>`);
  const pending = page.waitForEvent('download');
  await page.getByRole('button', { name: 'Export fixture' }).click();
  const download = await pending;
  const destination = testInfo.outputPath('teaching-export.csv');
  await download.saveAs(destination);
  const failure = await download.failure();
  expect(failure).toBeNull();
  const saved = await readFile(destination, 'utf8');
  expect(saved).toBe('record_id,status\nteaching-42,ready\n');
});

Waiting begins before clicking so a fast event is not missed. The destination belongs to this test rather than a browser-suggested directory. The final expected literal comes from a predefined teaching contract, including record identity and status, rather than being calculated from the downloaded result itself.

This illustrates a complete control flow, not correctness of a production report. Real checks need request scope, permissions, identity, required columns and data version. A saved login page can have a plausible CSV filename. Persistence alone cannot classify it as the requested export.

If saveAs fails, this test stops there. A project may collect additional failure information while preserving the original error, but should not let later diagnostics obscure the first failed stage. No file or stdout was generated for this article.

Why an asynchronous listener can still lose the file

Registering an async page.on callback does not make the test body await the callback's save. The body may return, fixture cleanup may close the context and temporary files may disappear. Give the main flow a completion promise or await the event object and save directly.

A fixed sleep does not define completion. Small files may finish early; a slow download may still be active when it ends. Timeouts should come from actual export requirements, with event waiting, downloading, saving and content checks classified separately.

Parallel tests also need separate output locations. A shared report.csv can be overwritten by another test and accidentally satisfy the wrong assertion. Associate the test, requested object and destination. Retried attempts need identifiable artifacts rather than overwriting all evidence with the last attempt.

Why not rely on path for a remote browser?

The API explicitly states that path throws for remote connections. A locally accessible temporary path is not a stable address for every execution mode. SaveAs expresses explicit copying to a chosen destination; verify it and artifact collection in the actual connection mode rather than treating local success as remote-CI evidence.

Failure waits as necessary and returns an error or null. Cancel cancels the browser download, and successful cancellation yields canceled through failure. Those object states do not cancel a server-side export job automatically. Query and retry behavior need the real endpoint's task and duplicate-operation contract, which this example does not implement.

When is the export test complete?

Proposed acceptance covers missing events, canceled or failed downloads, destination failures, incorrect content and parallel isolation. A normal path should retain the current file and its content judgment. A failed path should retain its first failed stage, identity and original error. CI artifact upload needs its own verified result after local saving.

Assertions after clicking explains observable-state waiting; downloads add file ownership and lifetime. Keep saving in the main flow, inspect this task's content and verify subsequent retention before treating a button action as evidence of file delivery.
