Check batch tracing with an in-memory exporter before trusting the graph

Verify a three-source batch and B-only retry with an actual Python in-memory exporter, separating parentage, links, business outcomes and target visibility.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-10 · Estimated read 17 min
Translations
zh-CN en

Article

Key takeaways

  • Define the operation boundary before selecting parents and source links.
  • Creation-time links can inform sampling; limits and export need actual configuration checks.
  • Local relationship assertions establish neither business success nor target visibility or exactly-once delivery.

Three sources do not give a batch Span three parents. Define the operation first, then record the source SpanContexts as links. A background batch can start a new root; work inside an existing execution context needs a separate parent decision. Inspect actual exported parents, link identities and retry scope before trusting a connected tracing graph.

Execution ownership is different from source relationships

Suppose a background worker aggregates messages A, B and C, each carrying a different producer context. A parent places the operation in one execution tree. Links preserve additional relationships. Selecting A simply to connect the picture does not establish that B and C are A’s child operations. Explain the relationship before optimizing the graph’s appearance.

The Tracing API Link section permits links to SpanContexts in the same or different traces. The specification site inspected on November 10, 2026 identifies version 1.62.0. That is not a Python package version or proof of identical behavior across SDKs and backends. Parent identity, recorded links and target visibility require separate checks.

Define what one Span covers: fetching messages, processing the batch, or persisting an aggregate. If B fails before persistence starts, a generic success marker can misdescribe the operation. A link records a relationship; it neither acknowledges a message nor establishes processing success, committed offsets or deduplication.

This fixture covers background tracing structure. Write its oracle first: the batch operation has no parent and exactly three links, to A, B and C. Under the hypothetical decision to retry B alone, another root operation links only B. The code creates telemetry objects; it does not execute that message-processing or retry policy.

A complete, locally executed in-memory fixture

The local run used Python 3.11.15 with opentelemetry-api and opentelemetry-sdk 1.45.2 in an isolated temporary virtual environment. It changed no site dependencies. The installed package version was recorded separately from the general specification version.

All identifiers below are synthetic, nonzero teaching values. An explicit empty Context makes each operation a root. ALWAYS_ON and a limit of eight links are fixture settings, not production sampling or capacity recommendations. The exporter stores records only in this process: there is no Collector, broker or query backend.

import json
from opentelemetry.context import Context
from opentelemetry.trace import Link, SpanContext, TraceFlags
from opentelemetry.sdk.trace import TracerProvider, SpanLimits, sampling, export
from opentelemetry.sdk.trace.export.in_memory_span_exporter import InMemorySpanExporter

# Synthetic identifiers; no producer or broker is contacted.
origins = {
    name: SpanContext(trace_id=number, span_id=number + 16,
                      is_remote=True, trace_flags=TraceFlags(1))
    for name, number in zip(('A', 'B', 'C'), (1, 2, 3))
}
exporter = InMemorySpanExporter()
provider = TracerProvider(sampler=sampling.ALWAYS_ON, span_limits=SpanLimits(max_links=8))
provider.add_span_processor(export.SimpleSpanProcessor(exporter))
tracer = provider.get_tracer('example.batch.links')
scenarios = (
    ('batch-process', [origins[key] for key in ('A', 'B', 'C')]),
    ('retry-B-only', [origins['B']]),
)
for name, contexts in scenarios:
    span = tracer.start_span(name, context=Context(),
                             links=[Link(context) for context in contexts])
    span.end()

def identity(context):
    return context.trace_id, context.span_id

finished = exporter.get_finished_spans()
observed = [
    (span.name, span.parent is None,
     [identity(link.context) for link in span.links])
    for span in finished
]
expected = [
    ('batch-process', True, [(1, 17), (2, 18), (3, 19)]),
    ('retry-B-only', True, [(2, 18)]),
]
assert observed == expected, observed
operation_ids = [identity(span.context) for span in finished]
assert operation_ids[0][1] != operation_ids[1][1]
print(json.dumps(observed))
provider.shutdown()

The actual process exited zero. The predefined identity checks found three source pairs on batch-process and only B’s pair on retry-B-only. Both operations had no parent and had distinct operation Span IDs. Expectations were not inferred from newly generated random IDs. The printed result does not establish a successful business retry.

The program deliberately creates no producer Spans for A, B or C. Only the two new operations appear in its exported collection. A source relationship can therefore exist without a locally queryable target record. Even a sampled flag in a supplied context cannot prove that its target was collected, delivered and retained within the current query scope.

A retry needs its own actual input boundary

Copying all three links onto a B-only retry implies a wider input set than intended. Inventing an unrelated B context instead can break the investigation trail. Retain the context dictated by the actual message lifecycle, rather than padding relationships to keep link counts equal.

The same business task need not always have one creation context. Redelivery of an original message and publication of a replacement message can carry different propagation material. Keep explainable task and attempt identities, and associate them according to the real protocol. A link is not a universal business primary key that merges every attempt.

For partial failure, inspect actual processing, durable effects and acknowledgement as well as telemetry. Whether A and C run again is a retry-contract question that two exported Spans cannot answer. A test asserting only Span count could pass even when the application incorrectly labels all three inputs successful.

Creation-time information and later loss are separate

The API prefers supplying already-known links when a Span is created because head sampling can consider only information available then. The SDK’s ShouldSample and Span Limits sections describe initial link inputs and configurable limits. A later addition cannot be promised to rerun the original sampling decision or recover unrecorded targets.

This sampler setting does not test a real selective sampling policy. Three links also do not exercise the fixture’s limit of eight. At an actual integration boundary, compare input membership, extracted contexts, submitted creation-time links and exported links. Missing propagation, limit overflow, export failure and a backend’s display behavior occur at different boundaries.

Do not wait indefinitely for a batch to acquire every possible source. Define when membership becomes fixed and whether late input belongs to another batch, a correction or a different operation. Quietly adding later knowledge to an earlier success story changes its meaning. Truncation, retained diagnostic fields and drop reporting require the actual SDK and collection configuration; a specification default is not a capacity guarantee.

Must a batch create another root inside an HTTP server Span?

No. This adds a condition absent from the background fixture: processing occurs inside a valid HTTP execution context. If the operation belongs to that request, it can retain the ambient parent and link the message creation contexts instead of clearing Context. The fixture’s explicit empty context is not a universal batch recommendation.

The inspected messaging Span conventions identify version 1.45.0 and Development status. They use links as the default producer–consumer correlation mechanism and discuss single-message parent alternatives and ambient contexts. That does not certify every auto-instrumentation library as implementing the same policy.

At integration time, identify who established the current context and read the instrumentation’s parent/link configuration. Give no-ambient and HTTP-ambient cases independent expected exports. The HTTP case was not executed by the program above. If upstream records remain unavailable, sampling and missing traces offers the next diagnostic boundary. A local relationship check proves neither cross-service visibility nor business success or exactly-once delivery.
