Why can a working error-summary link still reach the wrong answer?

Follow a household date correction through summary, targeting, editing, and resubmission; apply GOV.UK composite-answer guidance and handle removal, reordering, and late responses.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-30 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • Summary links need to reach the current answer belonging to an error and match inline guidance.
  • Known date errors target the first erroneous field; unknown parts target the first field.
  • Stable object identity is an implementation recommendation maintained with applicability and submission state.

Two household members have date-of-birth fields. An error-summary link correctly targets the second member’s missing year; after the first member is removed, the old link lands in the wrong group. A link that moves focus does not necessarily preserve ownership of the error. Correction routes must follow the current form objects rather than retain an old position.

Imagine a household application. Member A’s contact details are correct, while member B’s birth date lacks a year. After submission, the summary says “Enter member B’s year of birth,” links to B’s year input, and matches the inline message. The person enters the year and submits again. The corrected error disappears and other answers that may be retained remain available. That is one complete correction round trip.

Checking only for a red summary, an href, and visible movement misses whether the user reached the answer belonging to this error. In repeatable forms that support deletion or reordering, a position change can leave an apparently working link pointing at somebody else’s details.

Establish the ordinary correction route

The GOV.UK Design System error-summary guidance recommends a summary even for a single validation error, moving focus to it, using matching summary and inline error wording, and linking errors to the relevant answers. These are that design system’s component guidelines, not a claim that every product must use one exclusive layout.

GOV.UK Frontend can handle the focus behavior through its associated script. Copying similar HTML and styles does not establish that the behavior exists. With another component or a custom implementation, inspect focus destination, visible guidance after arrival, and the operation sequence. No page or assistive-technology tests were executed for this article.

In the household application, the summary needs to distinguish member B instead of repeating only “Invalid date.” The inline message should offer the same correction information. Identification should be sufficient to locate the answer without copying unrelated sensitive details to the page top. The product task and privacy requirements determine what is appropriate.

Composite dates and choice groups need specific targets

A composite date has day, month, and year inputs. The guidance says to link to the first field containing an error when the erroneous fields are known, and to the first field when the specific erroneous part is unknown. B’s missing year should therefore target the year, rather than always targeting the day because this is a date group.

If the server only knows that the overall date is invalid and cannot identify a particular part, the first field provides the entry point. This distinction connects the error model to the target rule. “All date errors target the first input” is too broad to cover both cases.

For radio or checkbox groups, the guidance targets the first option. That differs from a date with a known invalid subfield. Preserve rules for each answer type instead of making a generic summary component guess from whichever clickable element it happens to find first.

Position changes must not change ownership

Continue the unexecuted example. A initially occupies row zero and B row one. A link named member-1-year can become stale after removing A and renumbering B to row zero. It may point nowhere or later point to a newly added member’s year.

This article recommends associating error records with stable object identity and generating targets from the current rendering, rather than permanently retaining an array index. An internal member key B can map to the currently rendered year control even when order changes. This is an implementation recommendation, not a GOV.UK-mandated ID format, and it does not require exposing database identifiers publicly.

After reordering, rebuild summary order, wording, and targets from current state. A late validation response also needs to be matched to its submission, objects, and answers. Otherwise an old response can restore B’s error after the user already corrected it. An error result belongs to a particular version of the application, not simply whichever response arrives last.

A server-rendered full-page response and an in-place error update can both work. Each needs its own check of how the result is discovered and how the field is reached. In-place updates do not justify pulling focus back to the summary on every keystroke; a full-page response does not automatically guarantee correct focus. Define and verify behavior at the submission-result step.

Finish the correction, including retained answers

After correcting B’s year, check that resubmission uses the new answer for the same member, removes the corrected error, and preserves A’s previously valid details where retention is allowed. A network failure is not validation success. Repeated submissions also need observations showing that the displayed result belongs to the current request.

Retention has boundaries. Sensitive fields, file selections, session expiry, and storage policies may require different treatment. Do not promise that all information remains in a browser indefinitely. Explain what can remain, what requires re-entry, and why. A summary provides a correction route without overriding authorization or server-side business decisions.

Acceptance cases can include members A and B, a missing year, an invalid overall date, an unanswered choice group, removing A, reordering B, and a late response. Use the keyboard to move from submission to summary and then to the intended target, inspect the member identity and correction guidance, and complete resubmission. Cover both one error and several, retaining the form state associated with each result.

Should an error remain after its row is removed?

Distinguish actual deletion, temporary hiding, and an answer still required by the business rules. If the object was legitimately removed, recalculate errors against the current application rather than leaving a dead link. If the answer is merely collapsed or hidden but remains applicable, provide a route to reach and understand it. Removing the error solely to tidy the page would conceal the requirement.

If the client considers a member deleted while the server still requires their information, resolve that object-state or rule conflict before deciding what the summary should show. A permanently unreachable target cannot resolve it. This turns the summary from a colored list into a correction route whose relationships remain consistent with the current answers.
