Interpret HTTP 405 through the target resource contract

Diagnose unsupported methods against the target resource and keep authorization separate.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-17 · Estimated read 6 min
Translations
zh-CN en

Article

HTTP 405 identifies a method unsupported by the target resource. Diagnose it using Allow and the actual route rather than blindly changing the request to GET. The question is whether this resource accepts this method, not merely whether the server is online. Changing the method can also change business intent.

Method and target form a contract

RFC 9110, section 15.5.6, defines 405 as a method known by the origin but unsupported by the target resource. The origin must generate Allow listing that resource's currently supported methods. This differs from a server not recognizing or implementing a method. Establish which layer produced an observed response; the status alone does not prove application execution.

Imagine modifying an order collection when modification belongs on an individual order resource. The method can be valid while the target is wrong. A gateway route could also reject the intended method. These are unexecuted hypotheses, not universal vendor behaviors. Evidence needs the address, method, entry point and configuration.

Allow is not a user's permission list

A resource supporting DELETE does not authorize every identity to use it. Resource capabilities and user permissions are separate decisions. The header can guide diagnosis without replacing server authorization or being reduced to button visibility.

A missing expected Allow may indicate a nonconforming or intermediary-generated response. It does not select a safe replacement method. Retrying every failure as GET can replace a write with a read or expose parameters in an address. Explain why the chosen method is correct rather than seeking any successful status.

Record method, a safely identifiable target, necessary response headers and business-task identity without publishing tokens or personal data. With redirects, verify the final method and target instead of repeatedly changing the wrong stage.

Check the real entry point

Proposed cases include supported and unsupported methods, incorrect resource addresses and unauthorized identities. Compare gateway and application behavior, including documentation and generated clients from different versions. These requests were not executed here.

After changing configuration, check older clients and useful error diagnostics. Converting mismatches into success objects can let callers proceed without performing the intended operation. An explanation must not fabricate a completed state.

Redirect-induced method changes are a separate cause: see redirect method contracts. Establish the resource-method pairing, then independently verify authorization and business outcomes.
