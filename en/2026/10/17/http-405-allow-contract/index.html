Interpret HTTP 405 through the target resource contract

Diagnose 405 with a complete local route example while checking authorization, ingress, redirects and cached errors separately.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-31 · Estimated read 16 min
Translations
zh-CN en

Article

Key takeaways

  • 405 concerns a known method unsupported by the target, with Allow required.
  • Resource capability does not establish the caller's authorization.
  • Successful GET, handler reachability and the intended write are different outcomes.

When an API returns HTTP 405, check the target-method pair before changing the client. The status means that the origin knows the method but the target resource does not support it. Replacing a write with a successful GET can leave the original task undone. Resource capability and the current caller's authorization also need separate checks.

The contract belongs to the target resource

RFC 9110's definition of 405 requires the origin to generate Allow listing methods currently supported by the target. This article checked RFC 9110, published in June 2022, on October 31, 2026. The service and requests below are unexecuted teaching examples.

An order collection might support listing and creation while /orders/7 supports modification. A method can be appropriate for the business operation but paired with the wrong resource. A gateway can also route that method differently, preventing the application from seeing the request. A 405 does not prove that business code ran and does not justify repeating creation to investigate.

An origin not recognizing or implementing a method differs from a particular resource not supporting a known method. Authentication and authorization have their own semantics as well. Some systems deliberately conceal whether a resource exists; interpret actual responses under that policy rather than requiring every unauthorized request to reveal the same information.

A complete local resource-and-method example

This standard-library Python service listens only on the local machine and returns fixed teaching data. It has no real order persistence, account authorization or production service capability. PATCH merely reports reaching its demonstration route; it does not claim a saved modification. Save it as method_demo.py to run it. It was not executed here.

import json
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer


class Handler(BaseHTTPRequestHandler):
    def respond(self):
        status, payload, allow = 200, {'id': 7, 'state': 'teaching fixture'}, None
        if self.path != '/orders/7':
            status, payload = 404, {'error': 'unknown teaching resource'}
        elif self.command == 'PUT':
            status, payload, allow = 405, {'error': 'method unsupported here'}, 'GET, PATCH'
        elif self.command == 'PATCH':
            payload = {'demo': 'PATCH route reached; no order was changed'}
        data = json.dumps(payload).encode('utf-8')
        headers = {
            'Content-Type': 'application/json; charset=utf-8',
            'Content-Length': str(len(data)),
            'Cache-Control': 'no-store',
        }
        if allow is not None:
            headers['Allow'] = allow
        self.send_response(status)
        for name, value in headers.items():
            self.send_header(name, value)
        self.end_headers()
        self.wfile.write(data)

    do_GET = respond
    do_PATCH = respond
    do_PUT = respond


if __name__ == '__main__':
    with ThreadingHTTPServer(('localhost', 8765), Handler) as server:
        server.serve_forever()

From another terminal, issue requests without bodies:

base=http://localhost:8765
curl -i "$base/orders/7"
curl -i -X PATCH "$base/orders/7"
curl -i -X PUT "$base/orders/7"
curl -i -X PUT "$base/orders/8"

The code expects the first two requests to reach supported branches, the third to return 405 with GET and PATCH in Allow, and the fourth to reach the missing-resource branch. This separates resource differences from method differences. It does not implement every HTTP method; undefined handlers remain the standard library's responsibility, so the example is not a complete production route contract. Stop the process when finished and verify that this teaching process no longer holds the port.

The example deliberately avoids accepting arbitrary order JSON and pretending it was saved. Testing an actual modification requires a test persistence layer, validation, authorization and a subsequent state read. Reaching a PATCH handler is different from updating an order. Preserve that distinction in a repair report.

Does DELETE in Allow authorize the user to delete?

No. Allow describes capability, not the current identity's permissions. Clients may use it for diagnosis but cannot bypass server authorization because a method appears in the list. Hiding a button also does not establish authorization. If capabilities change with resource state, account for the response's time rather than treating it as permanent permission.

The Allow field definition also prohibits proxies from modifying it. Deployment diagnosis still needs actual ingress and direct-application responses to identify the generating layer. A normative rule is not evidence that a deployment follows it. Missing Allow calls for investigating conformity or intermediary behavior; it does not safely mean that no methods are available.

Authorization tests need separate identities: permitted, forbidden and expired credentials, with missing-resource behavior checked independently. The teaching server has no identity system and cannot validate these paths. Use controlled accounts and records in the real test environment. Keep method, safely identifiable target, task identity and necessary headers in diagnostics without publishing tokens.

If GET works, is the original problem fixed?

It establishes a reading path, not the original write. Confirm the resource and method against the current interface version and check that the actual ingress forwards that method. A successful object returned for every request would conceal the difference rather than repair it.

Redirects can change the final method or target, so inspect the chain rather than only its last status. The existing article on redirect method contracts explains that separate question. Preserve the original request, redirected request and application-observed request to decide which configuration or client behavior needs correction.

Why can an old 405 remain after the route changes?

A 405 is heuristically cacheable, subject to the method's definition and explicit cache controls. Repeated responses do not prove caching, but error status alone does not rule it out. Inspect cache information, target URL and ingress, then compare cache and origin paths in a controlled investigation.

The teaching service supplies no-store to avoid using its errors as retained cache entries. That is not a universal production policy. A temporary cache bypass can locate a cause without establishing a lasting fix. Review deployment behavior and older clients, including path normalization and case differences, before treating similar-looking URLs as the same resource.

Also inspect the business meaning of the returned value. If ingress turns method errors into HTTP 200 and an empty object, a client may continue to payment or refresh as though an update occurred. Error mapping must retain the fact that the operation did not complete. Preserve user input so the corrected request can be retried rather than forcing the user to refill a form.

A regression table can separate request intent, expected route response and expected stored state. A refused write method should explain rejection without the corresponding modification. A permitted correct request needs its own commit verification. This lets client, gateway and backend owners compare responsibilities for the same task instead of accepting one layer turning green.

Proposed regression cases cover supported and unsupported methods, wrong targets, unauthorized identities, forwarding, redirects and retained errors, with actual business state checked separately. None was run. A completion receipt should establish that the authorized caller performed the original action on the correct resource while unsupported methods still produce meaningful errors. Merely eliminating the 405 cannot establish that result.
