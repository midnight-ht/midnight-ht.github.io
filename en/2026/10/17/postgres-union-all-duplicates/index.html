Why can UNION undercount different events with equal values?

UNION compares complete projected rows rather than inferring event identity. Four independent events expose two rows totaling thirty versus four totaling fifty, source-key effects and separate ordering/LIMIT decisions.

Key takeaways

  • Equal complete projected rows do not establish equal business events.
  • Preserving source and event identity changes deduplication outcomes.
  • Business deduplication, ordering and LIMIT scope need separate definitions.

Two events can have equal projected values without being the same event. UNION removes duplicate complete projected rows, while UNION ALL preserves multiplicity. If a merged event total is too small, inspect which columns survived the projection before deciding that business deduplication was intended.

The PostgreSQL 18 set-operation documentation explicitly says that UNION removes duplicate rows unless ALL is used. “Row” means the values output by the query, not an event identity inferred by the database. Project away the event ID and keep only date and amount, and equality can use only those remaining values.

Four valid events become two distinct projections

Suppose two sources contain four independent events. Source A has A1 and A2, both on November 6 with amount ten. Source B has B1 on the same date with amount ten, plus B2 on November 7 with amount twenty. All four are independent in this example; they are not four replays of one event.

This complete read-only query uses hypothetical inputs, explicitly typed dates and integer amounts. Its outcomes below are deductions from set-operation semantics, not a claimed database execution, and it modifies no existing business table.

WITH a(event_id, day, amount) AS (VALUES
  ('A1', date '2026-11-06', 10),
  ('A2', date '2026-11-06', 10)
), b(event_id, day, amount) AS (VALUES
  ('B1', date '2026-11-06', 10),
  ('B2', date '2026-11-07', 20)
), u AS (
  SELECT day, amount FROM a
  UNION
  SELECT day, amount FROM b
), ua AS (
  SELECT day, amount FROM a
  UNION ALL
  SELECT day, amount FROM b
)
SELECT 'UNION' AS method, count(*) AS row_count, sum(amount) AS total
FROM u
UNION ALL
SELECT 'UNION ALL', count(*), sum(amount)
FROM ua
ORDER BY method;

The first predicted result has two rows totaling thirty; the second has four totaling fifty. The three November 6 tens become identical after projection to date and amount, so the first operation retains only one. The November 7 twenty supplies the other distinct row. The missing twenty comes from losing two legitimate observations, not from SUM adding ten incorrectly.

count(*) exposes the row count after the merge. Multiplicity has already changed before aggregation. Investigating an aggregate's null handling cannot restore events removed earlier. For the separate input-counting question, see how COUNT handles null inputs. Keep those diagnostic layers distinct.

Adding a column changes the equality being tested

Adding only a source column still merges A's two tens. B's ten is now distinct from A's ten, and B's twenty remains, producing three rows totaling forty. Source information helps, but does not preserve both independent events within A. This follows by comparing complete projected rows; it is not an additional measurement.

Retaining both source and each source's event ID makes all four events distinct in this fixture. Extra columns do not give the database an abstract instruction to avoid deduplication. They change the values being compared. Expand each branch's actual output when diagnosing the query rather than checking only whether the underlying tables have primary keys.

An event table's unique ID therefore does not guarantee that an upper UNION preserves events. An ID omitted from the projection does not participate in equality at that level. Once identity is discarded, an outer aggregate lacks the information to recover independent records. Repair the point where information is lost rather than multiplying the final total by a guessed factor.

Nor should random values be added merely to make every row unequal. That prevents equality without defining which rows represent independent business facts, and can make repeated computation over the same input unstable. Preserving meaningful source and identity differs from manufacturing a never-equal field.

Does UNION ALL automatically deduplicate one event across sources?

No. It preserves rows; business identity and conflict rules need separate definitions. In a different dataset where two sources genuinely report one event, UNION ALL retains both reports. It cannot decide which should be adopted.

Establish the shared business key before treating a source-local identifier as cross-source identity. Different identifiers can describe one event, and equal identifiers from separate sources can describe different events. Also decide how conflicting amounts are handled, which audit records survive and which conflicts must be rejected. A set-operation keyword does not answer those product and data-quality questions.

Keeping source and event information makes differences traceable until the policy is known. Collapsing date/amount pairs too early can lose independent events or compress conflicting reports into apparently clean output. A deduplication key needs a business justification; fields that currently look equal do not automatically identify one fact.

Ordering and LIMIT have separate scopes

The documentation does not guarantee that a combined query returns the first branch's rows first. Preserving multiplicity does not turn source precedence into output order. Logic needing earliest, latest or source priority requires explicit ordering and selection rules, rather than assuming that the first returned row came from the first written branch.

LIMIT also needs a defined scope: one branch or the combined result. These complete read-only integer examples isolate that question from event identity. The first selects one row per branch; the second selects one row after combining all input. Their outputs remain paper expectations.

(SELECT n FROM (VALUES (1), (2)) AS a(n) ORDER BY n LIMIT 1)
UNION ALL
(SELECT n FROM (VALUES (3), (4)) AS b(n) ORDER BY n LIMIT 1)
ORDER BY n;

SELECT n FROM (VALUES (1), (2)) AS a(n)
UNION ALL
SELECT n FROM (VALUES (3), (4)) AS b(n)
ORDER BY n
LIMIT 1;

The first is expected to return one and three, the second only one. The official parenthesis explanation distinguishes clauses applied to a branch from clauses applied to the entire set result. Parentheses set scope; final ordering sets display order. Neither defines business event identity.

Enumerate the events before checking merged rows

For actual validation, run the hypothetical-input query and record the real database version and output. Add another legitimate equal-valued event and recalculate both operations' counts and sums. Do not reuse the baseline two-row/four-row expectations after changing the input. Then add source and event IDs separately to determine which column changes equality.

Branches also need the same column count and compatible types at corresponding positions. That establishes composability, not equivalent business meaning. Names, convertible types and matching business dimensions need separate checks, otherwise syntactically valid positions can still represent the wrong concepts.

Choose from the requirement: use UNION for set semantics over complete projected rows; use UNION ALL to preserve legitimate observation multiplicity; define business identity and conflict policy before designing business deduplication. A projection without identity should not decide what the entire event system means by duplicate.
