Why can an outer page block framing after the partner portal is allowed?

Work through an unexecuted three-origin framing fixture, distinguishing full-ancestor permission, parent loading, actual response delivery, self, and user access.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-30 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • frame-ancestors checks every ancestor, not just the immediate parent.
  • Parent loading and leaf embedding policies face different directions.
  • Inspect headers, browser display, and business authorization separately.

Allowing a partner portal in an admin page's frame-ancestors does not automatically allow the page above that portal. The directive checks the full ancestor chain. Map who embeds whom, then inspect both the parent's child-frame loading policy and the leaf document's ancestor permission.

Two directions and more than one ancestor

The MDN frame-ancestors reference, checked on October 30, 2026 and marked modified August 27, distinguishes it from frame-src. It checks every ancestor, and a mismatch can cancel loading. No browser framing tests were run.

Suppose outer workspace A embeds partner portal B, which embeds admin document C. B is C's immediate parent, but A is also its ancestor. A's permission to load B does not authorize C to be embedded under A. Each response protects its own document and direction.

The CSP Level 2 Recommendation, dated December 15, 2016, describes ancestor traversal. The separately inspected CSP3 document is a Working Draft dated October 27, 2026, not a completed Recommendation or browser deployment receipt. No new capability is inferred from draft status.

Work through three origins

This complete local fixture has not been executed. It uses Python's standard library for three HTTP servers listening only on loopback. Different ports make three origins: 8101 is outer A, 8102 is partner B, and 8103 is admin C. The ports must be available. This is not production hosting or authentication code.

A single mapping keeps each document's response policy beside its HTML. A can load B; B permits A and can load C; C permits both ancestors. The proposed browser check opens the outer entry and observes the leaf marker. Enter stops the servers. No server or browser result is claimed.

import threading
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

outer = "http://localhost:8101"
partner = "http://localhost:8102"
admin = "http://localhost:8103"
leaf_ancestors = f"{partner} {outer}"
pages = {
    8101: (f"frame-src {partner};",
           f'<iframe src="{partner}/" title="Partner"></iframe>'),
    8102: (f"frame-ancestors {outer}; frame-src {admin};",
           f'<iframe src="{admin}/" title="Admin"></iframe>'),
    8103: (f"default-src 'none'; frame-ancestors {leaf_ancestors};",
           '<p id="fixture-result">Controlled framing fixture</p>'),
}

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        policy, fragment = pages[self.server.server_port]
        body = ("<!doctype html><title>Framing fixture</title>" + fragment).encode()
        self.send_response(200)
        self.send_header("Content-Type", "text/html; charset=utf-8")
        self.send_header("Content-Length", str(len(body)))
        self.send_header("Content-Security-Policy", policy)
        self.end_headers()
        self.wfile.write(body)

servers = [ThreadingHTTPServer(("127.0.0.1", port), Handler) for port in pages]
for server in servers:
    threading.Thread(target=server.serve_forever, daemon=True).start()
try:
    input("Open http://localhost:8101/ in a test browser; Enter stops servers. ")
finally:
    for server in servers:
        server.shutdown()
        server.server_close()

The normal configuration satisfies the relationship's relevant ancestor conditions, not every application requirement. Connectivity, other policies, and browser behavior need actual checks. Prepared header values are not evidence of responses received.

For the first negative control, set leaf_ancestors to partner alone. For the second, restore both ancestors but make B's frame-src reject admin. Restart the controlled fixture for each change and retain actual responses. These isolate the outer-ancestor decision from the parent's loading decision instead of changing two conditions together.

Why not rely on default-src or meta?

MDN states that frame-ancestors has no default-src fallback. default-src 'none' does not independently establish an ancestor deny-list. The leaf example declares both because they control different relationships. Finding no iframe inside C says nothing about another page framing C.

The directive is also unsupported in meta. Inspect actual document response headers and identify the application, proxy, or hosting layer that delivers them. Multiple policies require review too; adding a permissive policy does not necessarily replace earlier restrictions.

When legitimate embedding breaks, locate the document, directive, and mismatched origin before changing policy. Do not disable all CSP or permit every origin simply to restore the picture. Environment migrations and ended partnerships need an updated allow set.

Whose origin does self mean?

It is relative to the protected document. For C, self means the admin document's origin, not whichever partner happens to be its parent. B's own policy evaluates its own self separately. Identical text does not imply identical origin relationships.

Cross-origin embedding therefore needs a reviewed source list rather than assuming self on every page permits the chain. Scheme, host, and port matter; development and production origins are not interchangeable merely because their names resemble one another. No universal wildcard policy is proposed.

Does HTTP 200 prove successful embedding?

No. Obtaining a response and permitting its display under this ancestor chain are different outcomes. Retain real headers, chain origins, browser diagnostics, and visible content. A successful response or an iframe event alone does not establish the intended page was shown, much less that an admin operation completed.

Proposed checks cover direct partner embedding, a fully allowed three-level chain, a missing outer ancestor, a parent's rejected child, meta-only text, and an allowed origin with an unauthorized user. The last case verifies that embedding permission does not grant business access. The site's report-only and enforcement article covers another independent enforcement boundary.

Opening the admin document directly is a separate control, not proof of framing permission. Reuse the same leaf response for direct, partner-only, and three-level cases rather than accidentally testing different environments. Every allowed source needs a business reason. The local ports isolate test origins; they are not a production partner allow-list. An unexpected outer origin requires a policy decision before broadening access.

No security pass or observed clickjacking incident is claimed. List every ancestor and each document's policy direction, then verify that contract in actual headers and browser results. One approved immediate parent cannot approve the entire chain.
