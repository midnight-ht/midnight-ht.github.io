Where did an INFO record disappear in pytest?

Use a runnable import test to distinguish logger thresholds, propagation and caplog stages. Verify attribution with a return value, batch identifier and negative controls.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-12 · Estimated read 16 min
Translations
zh-CN en

Article

Key takeaways

  • Assert the import result and attributable record separately.
  • Effective levels and upward propagation affect root capture independently.
  • Read preparation records from the stage that captured them.

When an INFO record is missing in pytest, independently assert that the operation completed. Then check whether its logger accepts INFO and whether the record can reach caplog through the logging hierarchy. Lowering the capture threshold solves a threshold problem. A record routed elsewhere remains absent when you lower that threshold again.

Trace the path from an import result

Suppose a catalog importer receives three rows, two of them nonblank, and returns the number accepted. Its test also requires the import module to record the batch identifier and accepted count for later investigation. The return value and record serve separate commitments. The value two establishes the outcome of the call for the chosen input. A batch record shows that the promised diagnostic reached the observation point. A single substring assertion can overlook a missing record and pass on a coincidentally identical message from another module.

The pytest logging guide describes default log capture and caplog. Projects can change thresholds in configuration, command-line options, and fixtures. Diagnose the effective level of the originating logger, then establish whether the handler receives the record. A named logger with no explicit level can inherit its effective level from a parent. Once a child logger accepts a record and propagates it, ancestor handlers receive the record directly. Ancestor logger levels do not filter it again. The handlers still apply their own thresholds and filters. Python 3.11 logging documentation

These mechanics determine where to make a change. If a module explicitly accepts only warnings and above, setting the root logger to INFO can still leave the module's INFO record absent. If the module accepts INFO but disables propagation and writes through its own handler, relaxing the root capture handler does not change the route. Before the experiment, record the source logger, effective level, propagation setting, and intended destination. That gives you a basis for explaining which change affected the observation.

Compare three conditions in one test

Save the complete example as test_import_logging.py and run it with pytest 9.0.2 in an isolated environment. Each parameter case calls the same function. It first emits a preview record with identical text, then checks the return value and the number of records meeting the importer contract. Batch identifiers are synthetic.

import logging

import pytest

logger = logging.getLogger("catalog.importer")
neighbor = logging.getLogger("catalog.preview")


def import_rows(rows):
    accepted = sum(bool(row.strip()) for row in rows)
    logger.info("rows accepted", extra={"batch": "A17", "accepted": accepted})
    return accepted


def is_import_record(record):
    return (
        record.name == logger.name
        and record.levelno == logging.INFO
        and record.getMessage() == "rows accepted"
        and getattr(record, "batch", None) == "A17"
        and getattr(record, "accepted", None) == 2
    )


@pytest.mark.parametrize(
    "level,propagate,count",
    [(logging.WARNING, True, 0), (logging.INFO, False, 0), (logging.INFO, True, 1)],
    ids=["threshold", "route", "captured"],
)
def test_import_capture(caplog, monkeypatch, level, propagate, count):
    monkeypatch.setattr(logger, "propagate", propagate)
    caplog.set_level(logging.INFO, logger=neighbor.name)
    neighbor.info("rows accepted", extra={"batch": "P03", "accepted": 2})
    with caplog.at_level(level, logger=logger.name):
        assert import_rows(["a", "", "b"]) == 2
    assert "rows accepted" in caplog.text
    assert sum(map(is_import_record, caplog.records)) == count

The WARNING case returns two, but the INFO message does not pass the originating threshold. The second case admits INFO and turns off upward propagation on the importer logger. The same value returns, and the capture handler at the root still cannot see the target. The third case allows both the level and the route. It expects exactly one matching importer record. All three branches invoke the operation and assert its result independently.

This file ran in an isolated local environment and pytest reported four passing tests. The first three passes establish the expected zero, zero, and one matches. The fourth exercises stage-specific retrieval. These observations describe this file. Application configuration, asynchronous consumption, and an external log platform each need their own verification.

The preview record appears in all three cases. A substring check on caplog.text would pass even in the two cases missing the importer record. The example uses the logger name, level, formatted message, batch identifier, and accepted count to distinguish them. A real requirement limited to a diagnostic code and task identifier can use fewer fields. If retry count belongs to the contract, make the expected number explicit and provide input that causes the retry. Timestamps, terminal colors, and source line numbers often change with the environment or a refactor. Use those values as stable assertions only when the requirement gives them that role.

Decide how long the level change should last

The versioned pytest implementation temporarily changes the selected logger and capture handler levels in at_level and restores them on exit. Use set_level when the changed level should remain in force until the test ends. For a test with multiple operations, scope the context to the one emitting the target record. Verify its outcome together with the record attribution. If setup and execution require different levels, give them separate contexts so the first operation does not expand the second operation's observation range.

An application that replaces the root logger's handlers during a test may remove the capture handler. Check its presence before and after the relevant call, then decide how to preserve it within the application's logging initialization design. Switching all modules to DEBUG can add unrelated records and still leave the broken route untouched. Terminal live logging uses another output configuration. Visible text establishes that a record reached the display path. The test still needs to inspect its own capture. For code that writes directly to standard output, see the stdout and file descriptor capture boundary.

Why is an INFO message from a fixture absent in the test body?

First establish that the message was emitted during setup. In the test body, caplog.records reflects the call stage. Use caplog.get_records("setup") to inspect already captured preparation records from the body. The staging_marker fixture emits staging ready during setup. Its two assertions distinguish the current stage from preparation. Append this block to the previous file and repeat the same command.

@pytest.fixture
def staging_marker(caplog):
    with caplog.at_level(logging.INFO, logger=logger.name):
        logger.info("staging ready")


def test_setup_record(caplog, staging_marker):
    assert not any(r.msg == "staging ready" for r in caplog.records)
    assert any(r.msg == "staging ready" for r in caplog.get_records("setup"))

If a later change moves preparation into the test body, update the phase assertion to match the intended contract.

Looking back at setup retrieves records actually captured at that time. A lower threshold applied later in the test body cannot recover records already filtered during preparation. Configure the level inside the emitting fixture before the event, as the example does. Keep the emission stage, expected source, observed match count, and operation result together in the test evidence. An empty result can then direct the next investigation toward timing, the propagation route, or the assertion.
