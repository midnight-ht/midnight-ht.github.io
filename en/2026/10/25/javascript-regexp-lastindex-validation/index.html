Identical inputs alternate: inspect the regex lastIndex

Trace repeated tests and g/y cursor behavior, then define ownership, empty-match progress, and independent validation checks.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-25 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • Global and sticky matches carry cursor state between calls.
  • Removing flags does not create a whole-field grammar.
  • Empty matches need an explicit scanning progress policy.

Repeated calls to test on the same regular expression and the same string can return true, false, then true. Check for g or y: these modes read and update the object's lastIndex. A field validator that only needs to classify the current input can accidentally incorporate the previous call by reusing a scanning cursor.

The string is not the only input

The ECMAScript RegExpBuiltinExec algorithm specifies lastIndex handling. An ordinary expression without global or sticky mode starts from zero. With either mode, a successful match writes its end position to the cursor, while the relevant failure paths reset it to zero. This discussion assumes built-in RegExp behavior rather than an object with an overridden exec method.

This teaching example was not executed. Its comments are expectations derived from the algorithm, not captured browser or application output.

const check = /x/g;
const first = check.test('x');
const afterFirst = check.lastIndex;
const second = check.test('x');
const afterSecond = check.lastIndex;
const third = check.test('x');
// Expected: true / 1, false / 0, true.

The first call finds x at zero and ends at one. The second begins at one in the same one-character string, finds nothing, fails, and resets the cursor. The third begins at zero and succeeds again. The string is unchanged; the expression's state changed. Logging only input and outcome can make a deterministic state transition look intermittent.

A shared global expression inside map or filter can similarly make fields affect one another. If three fields all contain x, each successive check inherits the previous cursor. This needs neither threads nor asynchronous concurrency: sequential calls in one event loop are sufficient. A failed field passing on retry does not establish that its input was previously invalid.

Separate validation from scanning

For an independent whole-field decision, prefer a pattern matching the agreed grammar without g or y, alongside type, length, and business-range checks. Removing g eliminates this cursor dependency but does not turn substring search into complete validation. /x/ still finds x inside a larger string. Whole-field rules require their own definition.

For sequential scanning, such as recognizing tokens at a particular location, lastIndex is useful state. Global matching can seek a later match from the supplied position; sticky matching requires a match at the cursor and does not search for a later starting point. Sticky mode is not a stateless validation switch merely because it sounds stricter. It updates the cursor too, under different scanning rules.

Resetting lastIndex to zero before each test is one possible repair, but every call path must follow the convention. If a form and scanner share the expression, resetting during validation can destroy the scanner's progress. A clearer ownership arrangement gives independent validation a stateless rule and each scanner its own instance and cursor lifetime. Whether constructing expressions affects meaningful costs requires measurement; no benchmark is provided here.

Consider a page checking a field once during editing and again before submission. Acceptance cannot stop at the first successful call. Repeat the same valid input, interleave other fields, and retry after failure. Write expectations from the product rule rather than deriving them by calling the current expression once, which can copy the state bug into the test.

Capture the transition that explains failure

A proposed diagnostic record includes source, flags, lastIndex before and after the call, and privacy-appropriate input categories and lengths. Do not log sensitive field contents simply to investigate a cursor. A post-call zero alone is insufficient because failure resets it. The preceding one explains why the second identical string failed. Logs should reconstruct the transition rather than record only a red or green outcome.

Inspect ownership too. A module-level expression with global mode can be shared by every caller; a new instance inside each function invocation has another lifetime. const prevents variable rebinding but does not make lastIndex immutable. Naming the variable VALIDATOR cannot change the object's mutability. Review its creation point, flags, and actual invocation relationships.

The earlier article on complete integer validation explains why successful parsing is not whole-input acceptance. This article adds a separate concern: even a correct grammar can yield unstable repeated decisions through call history. Test allowed inputs independently from whether the same input receives the same decision after different preceding calls.

Why can an exec loop stop advancing when empty matches are allowed?

A successful built-in exec sets lastIndex to the match end. For a zero-length match, the end can equal the start. Success therefore does not guarantee cursor advancement. A handwritten loop repeatedly executing a global pattern that accepts empty strings needs an explicit progress policy or can remain at one position. This is a scanning-loop problem distinct from the earlier alternating-validation example.

Unicode affects the policy. Adding one advances a UTF-16 code unit and may differ from advancing a complete character as intended by the scanner. Options include restricting patterns to nonempty matches, using an appropriate built-in iteration interface, or implementing advancement according to the chosen Unicode mode. A bare lastIndex++ is not evidence that every text scanner is safe. Validate the selected policy against allowed patterns and the target runtime.

A useful scanning counterexample places a separator before the desired character. For target x and input consisting of a hyphen followed by x, start the cursor at zero. Global search can seek x later; sticky search fails because position zero is not x. A tokenizer requiring every position to start a valid token could hide an illegal character by skipping it. A simple occurrence search might instead find sticky matching unnecessarily strict.

Specify expected start and end positions independently, not only the final boolean. Identical successful booleans can originate at different locations. Document which text may be skipped, whether failure retries, and who advances the cursor. That makes a flag change reviewable as a protocol change. These are proposed cases, not evidence of browser coverage for every Unicode combination.

No expression script or form was executed for this article. Proposed cases include repeated identical inputs, interleaved fields, recovery after failure, the positional difference between g and y, and termination with empty matches. A change should state whether the expression is an independent validator or a stateful scanner and give it a lifetime consistent with that responsibility.
