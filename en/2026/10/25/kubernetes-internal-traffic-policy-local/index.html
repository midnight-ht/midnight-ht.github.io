Healthy Service endpoints can still fail locally: internalTrafficPolicy Local

Local restricts candidates to the source node; verify client placement, endpoint coverage, and update windows.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-25 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • Local does not promise cross-node fallback.
  • Global endpoint health does not establish per-node availability.
  • Verify eligible endpoints throughout updates, not just desired replicas.

internalTrafficPolicy: Local does not mean “prefer local, then fall back across nodes.” It restricts cluster-internal traffic to endpoints on the originating node. Without a local endpoint, the Service behaves as though it has no endpoints for a Pod on that node, even when healthy backends exist elsewhere. Investigate partial connectivity by relating endpoint coverage to client placement.

How a globally healthy Service develops a local gap

The Kubernetes Service Internal Traffic Policy documentation marks the feature stable since version 1.26. Internal traffic here originates from Pods in the current cluster. Default Cluster policy considers cluster endpoints, whereas Local restricts candidates to the source node. It is a routing constraint rather than an automatic fallback promise.

A global endpoint list answers which backends exist. Local policy answers which of them a particular source node can use. Healthy global endpoints and failed local access can therefore coexist. A screenshot showing addresses but omitting the client node removes the input needed to interpret the policy.

Local means the same node, not merely the same zone or a nearby location. If the requirement is to reduce cross-zone traffic while permitting other nodes, assess routing features suitable for that goal. Validate the actual proxy or networking implementation in the target cluster.

Work through three nodes

In this unexecuted example, nodes A and B each host a ready backend. Node C hosts only a client. A client runs on each node and requests the same Service. With Cluster policy, candidates can include the A and B backends. With Local, A uses only A, B uses only B, and C has no local candidate.

Neither an incorrect selector nor a crashed backend is necessary for this outcome. A probe only from A may overstate availability; one only from C may wrongly suggest that every backend is broken. Record source nodes, their local candidates, and request results rather than treating one request as representative of the cluster.

This undeployed fragment shows the field location. Ports and selectors must match the real application.

apiVersion: v1
kind: Service
metadata:
  name: inventory-local
spec:
  selector:
    app: inventory
  internalTrafficPolicy: Local
  ports:
    - port: 80
      targetPort: 8080

For a failed request from C, confirm the client’s node, absence of an eligible C endpoint, and that the policy governs the actual request path. Successful direct access to a backend can help separate application health from the Service path, but changes the routing conditions and does not prove that the original path recovered. DNS resolution also says nothing about local endpoint availability.

When is the restriction appropriate?

Same-node routing may suit latency, cost, or local-processing requirements, but benefits require the actual topology and measurements. If clients must work on arbitrary nodes while backends cover only some nodes, Cluster may better match the failure-tolerance goal. A field named Local does not establish a performance gain.

Choosing Local ties the set of possible client nodes to backend coverage. Replica count, updates, maintenance, and scheduling restrictions can all change that relationship. Two replicas on distinct nodes do not cover an entire cluster. Adding workers can expand client placement and create new gaps.

The session-affinity article concerns source-based backend selection. Local policy neither maintains application sessions nor replaces authentication, object authorization, or a separately defined network-access policy.

Does a DaemonSet guarantee a local endpoint at all times?

The workload type alone provides no such guarantee. Per-node deployment can help coverage, but startup failures, readiness, node selection, tolerations, and update windows can still leave a node without an eligible backend. Check actual ready endpoints rather than expected replicas or Pod existence.

Suppose an update replaces A’s backend while its client remains. The replacement Pod exists but is not ready. A can lose its local candidate during that window, and a healthy B does not automatically provide cross-node fallback. Decide whether that window is acceptable in update strategy and service objectives. Marking an unready application ready simply to fill the gap can send traffic to a process unable to handle it.

Possible responses include coordinating backend updates and client migration, or selecting another policy when cross-node service is acceptable. Define the intended failure behavior explicitly: fail, wait for local recovery, or permit remote service. Configuration should implement that choice.

Verify the node dimension

A proposed validation record includes Service specification, EndpointSlice node ownership and readiness, client node placement, and networking implementation and version. Request the same path from representative source nodes while local backends are healthy, unready, deleted, and restored. Record connection and application outcomes without assuming every implementation returns an identical error code.

Coverage acceptance should distinguish desired placement, a scheduled object, and an eligible endpoint. During maintenance, desired replica counts may look correct while local requests already face a gap. Observe the update window separately; a healthy global count after recovery does not erase local failures. A snapshot taken only after the update misses this risk.

Include new-node and maintenance scenarios. If a successful request unexpectedly reaches a remote backend, investigate whether the policy governs the traffic, whether the Service was bypassed, or whether another proxy intervened. Success alone does not establish Local enforcement. No cluster or requests were exercised here. Establish the desired fallback behavior first, then make coverage and verification reflect it.
