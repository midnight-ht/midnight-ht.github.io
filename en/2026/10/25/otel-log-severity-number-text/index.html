OpenTelemetry log severity: preserve SeverityText and compare SeverityNumber

Map source levels deliberately, include 17 in error filters, and distinguish unspecified severity from INFO display defaults.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-25 · Estimated read 12 min
Translations

Article

Key takeaways

  • Source labels and normalized numbers have different jobs.
  • Zero can mean unspecified and is not automatically INFO.
  • Error-and-above selection must include severity 17.

In OpenTelemetry logs, SeverityText preserves the source system’s level name, while SeverityNumber provides a normalized comparison scale. If an ERROR-looking record misses an “error and above” filter, inspect numeric mapping, missing values, and the predicate. Uppercasing a label does not establish cross-system severity normalization.

The two fields have different jobs

The OpenTelemetry Logs Data Model, currently under specification 1.62.0, defines six numeric ranges: 1–4 TRACE, 5–8 DEBUG, 9–12 INFO, 13–16 WARN, 17–20 ERROR, and 21–24 FATAL. Larger numbers mean greater severity. Zero may represent unspecified severity; it is not an alias for INFO 9.

Both fields can be absent. Text retains a source framework’s vocabulary; the number supports comparison. Warning and WARN may map to the same range under an explicit mapping while preserving their original spellings. When a source has only one level within a range, the specification recommends using that range’s smallest value.

This is not dictionary classification. A level called Critical must be interpreted using the source format’s semantics and documented mapping, not its spelling alone. A message saying “error count is zero” also does not become an erroneous event because its body contains the word error.

Test the filtering contract with three records

Consider an unexecuted pipeline whose fictional source has three levels: notification, caution, and failure. After confirming their semantics, the team maps them to information, warning, and error. These are illustrative records, not collected output.

[
  {"SeverityText":"Notice","SeverityNumber":9,"Body":"Job accepted"},
  {"SeverityText":"Caution","SeverityNumber":13,"Body":"Retry budget low"},
  {"SeverityText":"Failure","SeverityNumber":17,"Body":"Job rejected"}
]

Within the valid normalized numeric space, an error-and-above predicate of greater than or equal to 17 selects only the third record. Strictly greater than 17 misses the lowest error level. Alphabetical comparison of text has no reliable severity meaning. This example establishes inputs, an explicit mapping, and a predicted result; it does not claim an executed query.

Add another record whose text is Failure but whose number remains zero. It may reveal an unsupported input or mapping gap and should enter an explicit unspecified path. Conversely, a record with number 17 but no source text need not be discarded. A UI can use the standard short name while preserving the distinction between a missing original label and missing severity.

Map known sources and retain unknowns

For a known format and version, an auditable mapping near ingestion lets downstream filters share one comparison contract. Record source meaning, target value, and conversion ownership. Recheck the mapping when the logging framework changes. Applying competing transformations in both a collector and backend can reinterpret already normalized data.

For uncertain third-party text, do not invent a number to make a dashboard tidy. Retain source text and provenance, mark uncertainty, and define how queries handle it. A product may deliberately display unspecified records as information, but that display policy is not a fact supplied by the source.

Technical severity also does not establish business incident priority. A single error may be handled by a successful retry, while sustained warnings may signal widespread user impact. Normalization supports comparison; teams still define aggregation windows, alert thresholds, and impact criteria.

Should every record without severity become INFO?

Do not collapse all missing cases. The specification allows sources without a level concept to omit both fields. A backend or UI may display them separately or interpret them as information. Mapping a known erroneous event has separate guidance. A source with no level, a conversion that lost a field, and an unrecognized source value are different conditions.

Suppose an old collector reads the wrong input key and emits zero for every record. An unconditional INFO display can hide the mapping regression and remove error-filter coverage. Compare raw input with transformed output before choosing a display default. An explicit unspecified group and count can help expose such regressions; no missed-alert rate was measured here.

A three-level source need not acquire three invented extra levels. Map existing semantics faithfully. Unsupported subdivisions add apparent precision without source evidence.

Verify the full path

Plan fixed inputs for every source level and inspect application output, collector transformation, exported records, and backend queries. Cover numeric boundaries, absent text, absent number, unrecognized values, and malformed input. Check that error-and-above includes 17. Color alone is weak evidence because a UI may apply defaults.

For alerting, separate record selection from notification delivery. Mapping and queries govern selection; aggregation, suppression, routing, and delivery govern the later path. If an error sample appears in query results but no notification arrives, increasing its severity arbitrarily changes semantics without repairing the failed stage. Locate the last stage supported by evidence first.

The log correlation article separates an identifier from a retained trace. Likewise, correct model fields, correct conversion, and an alert actually being delivered are separate outcomes. No collector or query was run here. Start with one real framework’s level table, compare each mapped export, and build filters on the confirmed numeric contract.
