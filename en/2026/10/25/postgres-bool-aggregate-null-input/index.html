Why true from bool_and does not approve the whole batch

Separate passing known inputs from complete review coverage, empty batches, and reviewed document versions.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-25 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • Passing known checks does not establish complete coverage.
  • Aggregate a complete collection tied to reviewed versions.
  • Define empty batches separately from unknown results.

A true result from bool_and(ok) establishes that all non-null inputs participating in the aggregate are true. It does not establish that every original item has been checked. If a batch contains true values and NULL, the unknown result does not turn the aggregate false. Mapping that result directly to “ready to publish” confuses successful checks with complete coverage.

Failure, unknown, and no items require different decisions

The PostgreSQL 18 aggregate documentation defines the input rules for bool_and, bool_or, and count. Boolean aggregates use non-null inputs; without any non-null boolean inputs, the result is NULL rather than an automatic business approval. The SQL and batch below are unexecuted teaching examples based on that version's documentation.

Suppose a release requires three documents to pass review. A is true, B is NULL, and C is true. If NULL means the reviewer has not returned a result, bool_and answers whether all available results passed. It says nothing about when B will finish or whether B may be omitted. A false input produces false; an entirely unknown batch has no known aggregate conclusion. An API should expose those states separately.

An empty batch needs its own definition. No required documents and several documents awaiting review can both yield NULL, yet require different actions. The former might prohibit creating the release task; the latter might require waiting or investigating the reviewer. Labelling both “in review” could conceal a configuration error. My recommendation is to return item count, known-result count, failure count, and the aggregate, then calculate eligibility from an explicit policy.

Include coverage in the eligibility expression

This example assumes checks is already a complete collection with exactly one row per required item. It shows one batch; a multi-batch report also needs a deliberate relationship between batch records and detail rows.

WITH checks(item_id, ok) AS (
  VALUES (1, true), (2, NULL::boolean), (3, true)
)
SELECT count(*) AS total,
       count(ok) AS known,
       count(*) FILTER (WHERE ok IS FALSE) AS failed,
       bool_and(ok) AS known_all_passed,
       count(*) > 0 AND count(ok) = count(*)
         AND bool_and(ok) IS TRUE AS releasable
FROM checks;

The proposed result has three items, two known results, zero failures, and all known results passing. Release eligibility is nevertheless false. This chooses a specific contract: a nonempty batch, a known result for every item, and every result true. If empty batches are allowed, change that requirement deliberately and name the exception rather than allowing an aggregate default to decide it.

Completeness of the aggregate input is essential. An upstream WHERE ok IS NOT NULL removes pending rows, making both counts equal again. No aggregate can recover the discarded items. Starting only from a results table can also omit documents for which no check was ever created. To establish coverage, begin with the required-item collection, associate results, and distinguish a missing result record from an existing record with an unknown result.

One-to-many joins can distort the denominator too. Several review attempts per document may count the same document repeatedly or retain both an old failure and a new success. First define the applicable attempt, such as the result for a particular current version, then construct one row per item. Equal counts alone do not prove coverage. Adding deduplication without defining attempt ownership hides the problem.

Treating NULL as false is a policy

bool_and(COALESCE(ok, false)) makes existing unknown rows prevent approval. That can express “anything short of explicit approval blocks release.” It also collapses pending and failed results into one aggregate outcome. A caller that must offer retry, document correction, or continued waiting still needs separate counts. COALESCE inside an aggregate changes its inputs; COALESCE outside it replaces the final unknown outcome. Those interventions happen at different points.

Replacing the final NULL with true deserves particular scrutiny. It can express vacuous truth for an empty collection, but it can also authorize an unexpected release. A database function cannot choose the legitimate interpretation for the product. If the goal is simply a display field that never contains NULL, a separate presentation status can meet that need without rewriting unknown values in authorization logic.

The earlier article on COUNT input definitions explains why counts differ. Here those counts become decision inputs. An “all passed” field should identify which items it covers, which review version it uses, and how many results remain unknown. Retaining only the boolean makes later diagnosis difficult: true might reflect complete approval or merely the available subset.

Does replacing NULL inside the aggregate also reject an empty batch?

That substitution alone is insufficient. An empty input has no row on which COALESCE can operate, so bool_and can still return NULL. For a strict boolean that rejects empty batches, explicitly combine the nonempty requirement with IS TRUE, or deliberately select false as the final default. First decide whether an empty collection is an error, an exemption, or an allowed release. Client handling of NULL should not accidentally make that decision.

This also matters for batch lists. A scalar aggregate without GROUP BY returns a summary row; a grouped query can have no group at all for a batch with no input rows. Handling only the aggregate value cannot restore that missing batch. Start with the batch collection when such rows must appear, and check both membership and values. “No row” and “a row containing NULL” are different results.

A summary also has a time boundary. Suppose a document is edited after all checks are summarized. Three earlier approvals may no longer apply to the new contents. Bind completeness to reviewed document versions rather than identifiers alone; a changed version should return to the appropriate pending state. This is a proposed release protocol, not an implemented concurrency mechanism.

An interface can carry reviewed versions and the observation time so authorization can establish whether the summary still applies. A cached green indicator assists presentation but does not automatically authorize another release. Add a case that edits one document after aggregation and confirm that the old result is not reused. Coverage then describes both the intended collection and the version actually observed.

Write independent expectations for five cases before running SQL: all true, true plus NULL, false plus NULL, all NULL, and no rows. Add missing check records, duplicate review attempts, and upstream filtering as failure paths. Compare the complete expected item collection, not just the green indicator. These queries were not executed and no performance comparison is offered. The first acceptance evidence should show that every unknown or missing condition produces its agreed state.
