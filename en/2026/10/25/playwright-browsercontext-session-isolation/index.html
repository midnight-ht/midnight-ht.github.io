Two Playwright pages can share a login: isolate roles with BrowserContext

Model buyer and reviewer with separate contexts, then verify account identity, server data, and authorization independently.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-25 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • Another page in one context does not create another identity.
  • Separate contexts using one snapshot still use the same account.
  • Browser isolation does not isolate server-side carts or permissions.

Opening another page inside one BrowserContext does not create an independent login identity. Use two contexts to act simultaneously as a buyer and a reviewer, then open a page in each. A page represents a document surface; the context is Playwright's browser-session isolation boundary. Assigning roles by page alone can let one login replace the credentials used by the other.

Why pages can share an identity

Playwright's isolation guide describes contexts as separate browser profiles. Playwright Test creates a context for each test and provides a default page inside it. This does not mean that every newPage call creates an isolated identity: pages created through an existing context remain in that context.

Sharing still follows Web storage rules. Cookies apply according to domain, path, and other restrictions; localStorage is separated by origin. Different origins do not gain access to each other's data merely by sharing a context. sessionStorage has page-session rules, so it is also inaccurate to claim that every storage category is unconditionally shared between all pages. Separate contexts express cross-test browser isolation more clearly than manually enumerating storage to erase.

The authentication snapshot article addresses what gets saved and restored. Here the question is which browser identity concurrently active pages belong to. The problem can occur without saving any state file.

Model a buyer and reviewer explicitly

Consider an unexecuted order workflow: the buyer submits an order, the reviewer approves it, and the buyer checks its status. If both pages share a context, the reviewer's login can replace a same-domain session cookie used by later buyer requests. The buyer page may still display a cached buyer avatar. That display does not establish the identity of its next protected request.

Create two contexts, perform the application's authorized login independently in each, and verify identity through protected responses. This unexecuted skeleton contains no real site or login implementation.

const buyerContext = await browser.newContext();
const reviewerContext = await browser.newContext();
try {
  const buyer = await buyerContext.newPage();
  const reviewer = await reviewerContext.newPage();
  // Perform the application's authorized login separately in each page.
  // Verify each identity before creating and approving a dedicated order.
} finally {
  await Promise.all([
    buyerContext.close(),
    reviewerContext.close()
  ]);
}

A complete validation plan also connects the business objects. The buyer creates an order identified by this test run; the reviewer approves that exact order; the buyer reads the same ID and checks the transition. Add a negative case in which the buyer attempts approval and the authoritative endpoint rejects it. Two pages opening proves only browser object creation, not role permissions or completion of the approval workflow.

When using saved authentication, select a distinct, valid state file for each role. Two contexts loading the same identity snapshot still access the server as the same user. Context separation does not create new accounts, and a file named buyer is not evidence of the identity returned by the server.

Why clearing cookies is a different design

Clearing cookies before switching roles in a shared context may miss other state and can log out another page that is still active. Interleaved role actions introduce races between clearing and login. Separate contexts directly express the requirement for simultaneous identities and give each role a distinct lifecycle.

A test of logout synchronization between tabs for one user should instead retain a shared context. Sharing is then part of the test condition. Check the second page's cached presentation, next request, and reauthentication behavior according to the product contract. Choose the model by the behavior being verified.

Context isolation is not a claim of operating-system sandboxing or remote tenant separation. Backend data, network proxies, and third-party accounts retain their own state boundaries. Correct browser separation cannot establish correct object authorization on the server.

Can contexts using the same account still interfere?

Yes. Contexts do not isolate a server-side account profile, cart, or session-revocation policy. Suppose two tests create separate contexts for the same buyer. One empties the cart while the other prepares checkout. Browser storage is separate, but both operations may modify the same server-side cart.

Choose an account strategy by identifying mutable state. Read-only checks may reuse an account after assessment; tests changing orders, roles, or carts generally need dedicated accounts, dedicated data identifiers, or controlled serialization. If a product revokes an old session on a new login, logging into the same account from another context can correctly invalidate the first session. More waiting cannot repair that contract mismatch.

Copying a snapshot also copies credentials, not a business user. Two contexts using those copies may be affected by one logout depending on server revocation and client checking. They are not automatically independent accounts.

What evidence supports an isolation conclusion?

Record roles, context identifiers, page ownership, and business data identifiers without recording tokens. Check each identity after login and again after the other role logs in and acts. Verify both authorization and rejection branches, then close contexts and clean up owned business objects.

A useful diagnostic is to close and recreate the buyer context, then log in again without changing server data. If the wrong identity disappears with local state, investigate context reuse. If an independent login still reads another account's order, inspect server query conditions and authorization. This narrows the search rather than proving a cause: logging in again can itself change server-side sessions.

When failures occur, compare authoritative identity responses with the page's display before inspecting context creation and shared fixtures. Page names and variable names do not establish identity. No browser or approval flow was executed for this article. Before extending a two-role test, establish which context owns each page and whether the account and server data also support concurrent isolation.
