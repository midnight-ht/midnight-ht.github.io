readFile was cancelled: why does that not prove disk reads stopped?

Limit AbortSignal claims to documented readFile buffering and verify result ownership and FileHandle cleanup separately.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-25 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • Cancelling internal buffering does not withdraw every OS request.
  • A timeout does not automatically cancel the original operation.
  • Caller-owned handles need explicit cleanup ownership.

When readFile responds to cancellation by rejecting with AbortError, that does not mean the operating system has withdrawn every file-read request. Node documents a specific boundary: cancellation affects readFile's internal buffering rather than aborting individual operating-system requests. “The user stopped waiting,” “the read Promise rejected,” and “resource cleanup completed” need separately explainable states.

Identify the layer being cancelled

The fsPromises.readFile documentation describes AbortSignal support and explicitly states that operating-system boundary. The page checked here is labelled v24.22.1 and records signal support in v15.2.0 and v14.17.0. This article discusses path-based reading and caller-owned FileHandle objects, not a universal cancellation guarantee for streams, devices, or third-party libraries.

Suppose a background importer reads a file and the user cancels before reading finishes. Pass the signal to that read and prevent its result from reaching parsing when cancellation applies. If cancellation takes effect before completion, the Promise rejects with AbortError. This does not establish that disk activity immediately reaches zero or reveal how many requests remain, how long they take, or when memory must be reclaimed. Without measurements, the button should not promise those resource outcomes.

This unexecuted example connects the signal to the actual operation instead of equating a closed waiting screen with cancellation. The file and application behavior are hypothetical.

import { readFile } from 'node:fs/promises';
async function loadDraft(path, signal) {
  try {
    return await readFile(path, { encoding: 'utf8', signal });
  } catch (error) {
    if (error.name === 'AbortError') return null;
    throw error;
  }
}
const controller = new AbortController();
const pending = loadDraft('./draft.txt', controller.signal);
controller.abort();
const text = await pending;

The example uses null for cancellation. A real API can return a tagged result to avoid confusing cancellation with ordinary empty content. It neither invokes a parser nor proves any file was closed. Immediate abort demonstrates wiring, not a promise that cancellation wins every real race. A signal sent after successful completion cannot make that success never have happened.

A timeout does not automatically notify the worker

Promise.race can select between reading and a timeout so the caller stops waiting sooner. It does not automatically send cancellation to readFile; the original operation may continue. If cancellation is required, retain a controller, supply its signal, and handle the original operation's eventual completion or rejection. A timeout branch should not abandon responsibility for background work. This compares completion relationships, not measured performance.

Cancelling a read also does not undo subsequent parsing or database writes. Suppose reading completes, parsing begins, and the user then cancels. Whether parsing responds depends on its own support and the application's wiring. A requirement to undo the whole batch needs a commit boundary and recovery protocol. A file-level AbortSignal is not a transaction rollback.

The UI can show “cancellation requested” before reporting cancellation or completion according to actual task state. If work finishes before the request takes effect, an explicit policy should describe that outcome instead of reporting cancellation while a save succeeded. Give each attempt an identity so an old result cannot overwrite a newer task. Cancellation and result ownership are related responsibilities, but neither substitutes for the other.

Set buffering budgets before cancellation

Ordinary readFile usage produces the file contents as a result and suits files within an acceptable size budget. Cancellation does not turn it into chunk-by-chunk consumption with fixed memory. Large imports may justify streaming and incremental parsing, but budget downstream buffers, parsed objects, and concurrent tasks too. The word “stream” alone does not establish constant memory use.

The article on Node stream backpressure explains when a producer should pause. Here the concern is the layer affected by cancellation. Backpressure, cancellation, and concurrency limits address different resource problems. One request stopping internal buffering does not establish that other simultaneous reads stopped. Unbounded immediate retries after cancellation can still exceed the resource budget.

For a known small configuration file, a path-based readFile call can express the requirement clearly. If position, chunking, and ownership need closer control, choose the corresponding interface and inspect its documentation. No universal size threshold is recommended here: acceptable limits depend on environment, decoding, concurrency, and parsed data, none of which was measured.

Does cancellation close a FileHandle supplied by the caller?

Do not treat cancellation as an explicit close operation. A caller holding a handle obtained through open needs its own cleanup responsibility and must await the relevant cleanup. The filehandle.close documentation says close waits for pending operations on that handle before closing it. Reading and closing are separate actions; AbortError is not a close receipt.

A function that opens its own file can await close in its cleanup path. If a handle comes from outside, document whether that function has authority to close it. Silently closing an externally shared handle can disrupt another user; each party assuming the other will close it leaves an ownership gap. Define how cleanup failure is reported without obscuring the original cancellation or read error. The example does not implement a complete handle manager and cannot prove those responsibilities fulfilled.

Consider two imports. The first read is slow; the user cancels and selects a second file. Even if the first later emits a completion notification, it should not overwrite the second file's name, preview, or button state. Check task identity when accepting results, not only when the button is clicked. Timely cancellation and rejection of obsolete results require separate controls.

If the second attempt fails, the first attempt's late success is not an automatic fallback unless the product explicitly permits that behavior and identifies its source. Verify which file supplies the preview and which attempt owns the save. Seeing one cancellation indicator disappear does not cover this interleaving. No real disk timing was simulated and no maximum wait between attempts is asserted.

Proposed verification separates an already-aborted signal, cancellation during reading, cancellation after success, ordinary read failure, and cleanup failure. Record Promise outcome, whether parsing began, whether handle cleanup completed, and whether an old result was accepted. Resource observations need their own environment and time window. No file reading, cancellation, or resource measurement was performed here. Limit an acceptance conclusion to the layer actually observed rather than expanding one rejection into a claim that disk, memory, and business processing all stopped.
