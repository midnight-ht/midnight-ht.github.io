After promisify loses this, which function should be bound?

Review receiver ownership, error-first callbacks, success result shape, and custom overrides before migrating a legacy API.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-25 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • Promisifying a method does not retain its instance automatically.
  • Nonstandard callbacks and multiple results need explicit contracts.
  • A custom override selects the function actually returned.

util.promisify(client.load) creates a Promise-returning function from a callback interface. It does not make that function remember client. If the original method reads instance state through this, calling the extracted wrapper directly may still fail. Preserve the receiver first, then check callback position, error-first semantics, and the intended success result.

A function reference does not carry its owning object

The Node.js v24 util.promisify documentation demonstrates a class method losing its receiver and shows call and bind as remedies. The page checked for this article identifies itself as v24.22.1. The following hypothetical client was not executed and is not evidence of a completed SDK migration.

import { promisify } from 'node:util';
class Client {
  constructor(prefix) { this.prefix = prefix; }
  load(key, callback) {
    callback(null, `${this.prefix}:${key}`);
  }
}
const client = new Client('draft');
const load = promisify(client.load);
const value = await load.call(client, 'A');
// Expected value by inspection: 'draft:A'.

Reading client.load obtains the method function. Calling client.load supplies client as the receiver through the call expression. Storing that function independently and calling it directly does not preserve the relationship automatically. The example uses call to supply it explicitly. If a downstream caller cannot specify a receiver, bind the result of promisify to client before exposing it.

This does not mean Promises remove this. Extracting a function loses the original invocation relationship, and synchronous code can have the same problem. The migration merely exposes it. Test two instances with different prefixes so each load uses its own state. A single instance returning a constant can conceal an accidental binding to another instance or a global object.

Error-first callbacks are a prerequisite

The default adapter expects the final argument to be an (err, value) callback. Its first argument communicates rejection; the agreed success position supplies the result. An API with separate success and failure callbacks, or a callback shaped like (value), does not become compatible merely because promisify accepts the function. A successful string passed in the error position can become a rejection.

Check whether multiple success values matter. A legacy callback might provide an error, a body, and response headers. Retaining only the body can discard pagination or validation information. Design an explicit Promise result such as { body, headers }. Do not assume every callback argument automatically becomes an array. APIs with library-specific custom behavior require inspection of that library's contract rather than extrapolation from a generic adapter example.

When the default convention does not fit, write a small Promise adapter that specifies argument order, receiver, and result fields. For error-first callbacks, inspect the error and combine the required success values into one object. For split callbacks, connect the success and failure positions to resolve and reject separately. The additional code exposes a previously hidden protocol for review. The adapter still needs to respect the API's synchronous throws and completion rules; wrapping does not eliminate every legacy-interface concern.

custom selects an implementation

The documentation says promisify returns the function stored under util.promisify.custom when that override exists. An override that is not a function causes an error. The property therefore does more than annotate the default conversion: it selects another implementation. Inspect that actual function's receiver requirements, returned value, and rejection behavior.

If bind creates a new function before promisify is called, do not assume the original function's custom property becomes a property of the new function. A clearer inspection sequence is to look for the override on the original method, establish which function promisify actually returns, then decide how to supply its receiver. The documentation's ordinary binding example cannot establish this semantics for every third-party override.

Suppose a default callback returns a body but the custom version returns an object containing the body and validation details. A test checking only that the result is truthy will miss the changed return type. Specify the caller's required fields, types, and failure behavior independently, then check the actual branch. Merely observing that the custom property exists does not prove it was invoked or fulfilled its contract.

Should a function that already returns a Promise be promisified?

Repeated wrapping should not be the default migration step. The checked documentation records that promisifying a function returning a Promise has been deprecated since Node v20.8.0. A function that only returns a Promise and never invokes the appended callback does not automatically satisfy the callback convention. Establish the API's supported asynchronous interface first. If an appropriate Promise API already exists, using it directly is usually clearer.

For a hybrid API supporting both callbacks and Promises, follow the library's documented invocation mode rather than guessing from its name. Error monitoring and resource cleanup must follow the actual completion relationship. The article on finally and final outcomes addresses later cleanup; this article first establishes that the awaited Promise represents the intended invocation and result protocol.

Cross receiver correctness with callback correctness rather than testing each only on one success. Suppose two tenant clients return their respective prefixes, but one failure path puts its error in the second callback argument. Binding repairs the prefix without repairing that protocol. Conversely, a perfectly error-first function bound to the wrong tenant can return structurally correct data belonging to the wrong instance.

Specify expectations by instance, input, and completion: A returns A's data, B returns B's data, and both failure paths preserve identifiable errors. Required error fields follow the actual API contract; the example's strings are not a universal format. Even a correctly shaped asynchronous result needs ownership checks by its caller. An adapter does not grant cross-instance or cross-tenant access.

Proposed acceptance cases include receiver isolation across two instances, success, an error callback, explicit adaptation of a nonstandard callback, a custom override, and preservation of required multiple success values. Write expected result objects independently rather than deriving them from the result under test. No client, SDK, or end-to-end migration was executed here. Being awaitable is an entry point; receiver ownership, result shape, and error responsibility define a reviewable migration.
