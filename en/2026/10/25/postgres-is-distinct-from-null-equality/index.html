Why changing NULL to text can escape change detection

Compare nullable before-and-after states without sentinel collisions, while preserving omitted versus cleared request fields.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-25 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • Ordinary inequality with NULL yields unknown.
  • IS DISTINCT FROM distinguishes one NULL from two NULLs.
  • Preserve omitted-field intent before comparing values.

Using old_value <> new_value to detect changes in a nullable field can miss both the first value replacing NULL and an existing value explicitly cleared to NULL. Ordinary inequality produces unknown when NULL participates. If the business treats two NULLs as unchanged and exactly one NULL as changed, consider IS DISTINCT FROM and separately define omission versus explicit clearing.

Compare complete field states

The PostgreSQL 18 comparison documentation specifies that IS DISTINCT FROM behaves like inequality for non-null inputs, returns false for two NULLs, and true when exactly one input is NULL. Conversely, IS NOT DISTINCT FROM returns true for two NULLs. This is a defined comparison including empty state, not a universal change to SQL’s treatment of unknown values.

Suppose a profile audit compares a contact note before and after an update. User one previously had no note and enters “evening.” User two removes that note explicitly. User three has no note before or after. The business expects changes for the first two and none for the third. Ordinary inequality does not return true for the first two, so the audit misses real transitions.

This complete hypothetical input exposes the difference. The SQL was not executed; the explanation is derived from documentation rather than database logs.

WITH changes(id, old_value, new_value) AS (
  VALUES (1, NULL::text, 'evening'),
         (2, 'evening', NULL::text),
         (3, NULL::text, NULL::text),
         (4, '', NULL::text),
         (5, 'same', 'same')
)
SELECT id,
       old_value <> new_value AS ordinary_different,
       old_value IS DISTINCT FROM new_value AS changed
FROM changes
ORDER BY id;

The expected changed values are true for one, two, and four, and false for three and five. Row four deliberately distinguishes an empty string from NULL. If an empty string is a legitimate supplied value, clearing it to NULL is a change. Ordinary comparison encounters NULL in all four initial rows and cannot provide the desired two-valued change flag. Row five retains a non-null equality baseline instead of testing only NULL cases.

A COALESCE sentinel can hide a legitimate transition

A common patch replaces NULL on both sides with an empty string before comparing. Row four then becomes empty string versus empty string, turning a real transition into “unchanged.” A special-looking string merely postpones the collision until that value enters the data. Unless a constraint makes the sentinel impossible, the comparison silently merges distinct states.

If the business intentionally treats empty strings, whitespace-only strings, and NULL as “not supplied,” define normalization first. Apply it at a clear boundary and decide whether audit needs the original input. Equating those storage states is then a product policy rather than a temporary trick to obtain a boolean. IS DISTINCT FROM does not trim whitespace, normalize case, or standardize phone formats for the team.

For example, whether removing surrounding spaces creates an audit event depends on comparing raw input or normalized state. If the product needs both a record of user actions and suppression of identical normalized updates, record request events and actual state changes separately. One changed field serving both purposes makes it unclear whether it represents clicking Save or a stored difference.

Conditional updates do not implement an entire audit

A hypothetical endpoint that updates only genuinely different notes can include the comparison in UPDATE’s WHERE clause while locating the target by stable identity. This means “update if the target exists and its current field differs.” No updated row can mean identical content, an absent target, or another unsatisfied predicate. Zero rows cannot automatically be translated as “the profile already matched.”

An audit still needs old value, new value, actor, and transaction ownership bound to the actual change. A correct SELECT comparison does not establish that a later UPDATE uses the same state version or that audit and update commit together. This article does not implement complete transaction or concurrency control; it addresses field-comparison semantics. Verify actual authorization, update protocol, and transaction behavior independently. One predicate is not an audit system.

Write independent expectations for the five rows, then add two different non-null texts, equal ordinary texts, and two empty strings. Check updated identities and audit counts as well as values. A single test changing one non-null text to another misses first-entry and clearing paths. No SQL was executed and no reduction in write cost was measured.

Can an omitted request field and explicit NULL use the same comparison?

Do not turn both into NULL first and expect the database to recover intent. A partial-update contract may define omission as preserving the existing note and explicit NULL as clearing it. That contract must be stated. Preserve field presence before deciding whether a new value enters the comparison. The predicate sees two supplied values, not the original request’s shape.

Suppose the stored note is evening. Request A omits the note field; request B explicitly provides it as NULL. Under this contract, A skips the note update, while B compares evening with NULL and produces a clearing event. Defaulting A’s missing field to NULL makes both requests perform the same action unintentionally. Tests must therefore cover raw request shape rather than only direct database parameters.

The response contract should retain this distinction. If a client submits the same note twice, the service can report no content change, but it should establish target and access conditions rather than infer or disclose record state from zero updated rows. Deliberately presenting absent, inaccessible, and unchanged targets alike may be a product and security choice; an incidental shared count should not make that choice.

For audit acceptance, send two identical requests in a proposed case. Check that an actual state-change event is not recorded twice while retaining whatever operation evidence is needed to establish that two requests arrived. Request counts and state-change counts need not match. This does not automatically provide idempotency: request identity, transactions, and repeated side effects still require implementation. Precise event names are easier to investigate than calling every record update success.

The earlier article on NOT IN and NULL examines unknown propagation in set filtering. Here the question is comparison of before-and-after update states. Sharing a NULL theme does not make one rewrite suitable for every query. A profile-change repair should deliver field-presence rules, empty-state equivalence, and expected transitions, then verify that update and audit follow the same agreement.
