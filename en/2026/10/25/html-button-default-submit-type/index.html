Preview submits the form? Inspect the button type first

Current HTML Auto conditions, form ownership, rendered types, and keyboard activation determine preview, submit, and reset behavior.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-25 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • Missing type means Auto; submission depends on current standard conditions.
  • Declare types for local actions and intended submission controls.
  • Check rendered DOM, form association, requests, and persistent state together.

If “Preview” submits a form, inspect the rendered button type and form association first. A typical form button without an explicit local-action type can become a submit button. A click handler that opens a dialog does not automatically cancel the browser's submission behavior. Declare submission, resetting, and local actions separately, then verify the actual activation paths.

What is the current default type state?

The current HTML Living Standard button definition gives missing and invalid type values the Auto state. An Auto button is a submit button when neither command nor commandfor is present and its parent is not a select element; an explicit submit state also makes it a submit button. The familiar warning that omitted types can submit ordinary forms is useful, but an unconditional claim that every omitted type means submit misses these current conditions.

An explicit button type has no built-in form submission or reset action and suits local interactions such as preview, help, or display toggles. The submit and reset states have their corresponding form behaviors. Text reading “Cancel”, or an eye-shaped icon, does not select a browser behavior. Element state, attributes, and associations determine it, rather than the product wording.

Visual placement is insufficient to determine form ownership. A component can use the form attribute to associate a button with a particular form. Inspect the actual DOM. A toolbar outside the apparent form boundary can still belong to it; conversely, a missing type alone does not establish that a network submission will occur without the relevant form association and conditions.

How would you repair an application preview that submits?

Imagine an application form with a contact field, “Preview application”, and “Confirm submission”. Preview opens a read-only dialog; confirmation submits the application. This is an unexecuted example. If both buttons omit their types, preview might open its dialog and then initiate form validation or submission before the user intends to confirm.

Set the preview button to type="button" and the confirmation button to type="submit". Keep submission handling in a defined form submission path. Fill in a valid application and activate preview: the expected result is a dialog without a submission request or persisted state transition. Close it and confirm that input remains. Then activate confirmation, expecting validation, the request, and result feedback, and reopen the application to inspect the same persisted state. A dialog appearing alone would not establish that preview stayed local.

Next leave the required contact blank and activate preview. If the product allows previews of incomplete drafts, accidental form submission should not let native required-field validation block that preview. Confirmation should reject the missing information according to its contract. Allowing incomplete previews is an assumed product choice here, not a universal HTML requirement.

One failure is treating the end of a business callback as the end of the click: default behavior remains a separate concern. Another is repairing the page's native button while a design-system wrapper discards its type prop. Review the emitted element, not just attributes passed at the call site.

Can cancelling click replace declaring the type?

Cancelling an event's default action can affect that activation, but an accurate type usually makes the component's role easier to maintain. A protection embedded in one handler can disappear after a branch, handler, or event route changes. The type states the role at the control itself. Stopping propagation and cancelling default behavior are different operations and should not be confused.

A team can require callers to choose a role explicitly, or choose a documented component default. Defaulting to button reduces accidental submission from local actions but requires every intended submission control to declare submit. Preserving browser behavior requires careful review of each auxiliary action inside forms. No default replaces page verification: the rendered behavior must match caller intent and expose exceptions.

Include keyboard paths in form-level checks. Users can activate buttons from the keyboard, and input may lead to implicit form submission under its applicable rules. Mouse-only handlers do not establish a consistent submission route. Observe actual submission events, requests, and persistent state instead of treating click counts as application counts. No browser event test was executed for this article.

Can a button outside the form submit it?

Such an association is possible; inspect the form attribute and target identifier. A fixed bottom toolbar might sit outside the form element while its confirmation button uses form="application". That button still has a submission role. If preview inherits the same association and omits a local-action type, visual separation provides no protection. Record ownership, type, disabled state, and submission overrides for each control.

Review reset separately too. Resetting form controls is not closing a dialog, navigating back, or deleting a saved server draft. A “Cancel” action intended to close while preserving input would violate that intent if implemented as a reset. Decide the preservation boundary before selecting native behavior.

The site's button-promise article examines the business state promised by an action. This article adds the browser path into submission. For preview, cancel, save, and confirmation, record mouse and keyboard activation, events, requests, persisted changes, and input retention after failure. Evaluate the type repair alongside those outcomes to establish that preview stays preview and submission starts from its intended route.
