Artifacts still differ after SOURCE_DATE_EPOCH: define reproducibility scope first

A deterministic time input does not fix paths, ordering, dependencies, or toolchains; inspect the artifact boundary and differences.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-25 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • Only supporting tools consume the deterministic time input.
  • Other build inputs still need identities and control.
  • Keep source time separate from actual release audit events.

Fixing SOURCE_DATE_EPOCH supplies a common time input to build steps that support it. It does not automatically fix toolchains, directory paths, file ordering, or dependency contents. When artifacts still differ, locate the changed bytes and identify their inputs before checking whether the responsible step consumes the variable. A matching environment value is not proof of reproducibility for the complete artifact.

What the variable constrains

The SOURCE_DATE_EPOCH specification is revision 1.1, dated November 27, 2017. It defines an integer-second timestamp passed through the environment so participating build processes can replace current build time with deterministic source-related time. It neither freezes the operating-system clock nor changes programs that have not implemented support.

Choose a traceable value, including packaging changes where applicable, rather than taking the current time on every run. A stable variable name with a changing value solves nothing. A commit-time policy must explain uncommitted changes and packaging patches; the latest upstream commit alone may omit changes in the delivered source. Keep the policy with the input record.

The value is seconds since the epoch, not a localized date string. Rendering belongs to the consuming tool. Converting one integer into different local-time strings can reintroduce variation. Expose malformed input rather than silently falling back to current time and producing an intermittently reproducible build.

Equal timestamps can still produce different archives

Consider an unexecuted documentation build in two isolated directories with identical source, dependencies, and environment values. It creates a version page and an archive containing that page and images. Assume the page generator supports the variable: embedded generation dates match. Archive ordering or embedded absolute paths can still differ.

Comparing final hashes establishes only whether the files match. If they differ, unpack or use a format-aware comparison tool to inspect entry names, contents, timestamps, permissions, and ordering. A difference confined to order calls for deterministic input ordering or archive policy. Directory names embedded in generated content call for path mapping or generator changes, not another timestamp adjustment.

No archive was built here, and no particular tool is claimed to always embed absolute paths. The example demonstrates narrowing the investigation by difference location. Signatures, compression metadata, and debugging information may need specialized inspection; unreadable binary output is not evidence of equality.

Maintain an input record covering source identity and local changes, lockfiles and actual dependency resolution, compiler and plugin versions, arguments, environment, paths, locale, and time policy. A command alone cannot identify packages downloaded behind it.

Cache policy answers another question

The package-index cache article concerns whether dependencies are fetched again. Reproducibility asks whether reexecution from defined inputs produces identical contents. Disabling cache can fetch changed dependencies; reusing cache can conceal missing input records. Neither establishes reproducibility by itself.

Choose by release objective. Reproducing an approved version calls for fixed sources, tools, and immutable dependency identities. Obtaining current fixes deliberately changes inputs and creates a new artifact identity. An unconditional promise of both “always latest” and “always identical” leaves no coherent acceptance criterion.

Formats may have limited timestamp precision or ranges, and tools may clamp values. The specification discusses timestamp clamping; it does not require blindly overwriting every file with one timestamp. Read the relevant tool's versioned behavior and inspect output. No compiler, archiver, or plugin version was tested here.

Does deterministic time erase release audit time?

It need not. Internal timestamps used to produce deterministic bytes and external records of actual build, signing, upload, and deployment events have separate jobs. Name them distinctly. Do not display source time as the time this deployment occurred, or remove genuine receipts to force equality.

A version rebuilt two days later can retain the same internal source timestamp while its pipeline start and end times differ. Associate each record with source and artifact identities. If signing introduces time or randomness, define whether comparison covers the unsigned payload, signed package, or final published object. Changing that boundary after seeing differences does not prove the original promise.

For unsupported tools, consider removing unnecessary build dates, using native deterministic options, or changing generation logic within the authorized scope. Post-processing can invalidate signatures or hide meaningful differences, so document exactly what it changes. Variation after setting a variable does not automatically establish a specification failure.

Design a useful comparison

Define the artifact boundary first. Rebuild from identical inputs in two clean independent directories and record environments, tool versions, actual variable values, and hashes. Introduce a controlled directory change to detect path leakage, and a time change to detect current-time embedding. Change conditions deliberately so differences remain interpretable.

Equality supports only the tested boundary and environments, not all platforms or future versions. Preserve differing artifacts and their comparison instead of rerunning until they happen to match. This article executed no archive build or hash comparison and verified no tool support. A reproducibility task should identify both the steps consuming deterministic time and the complete object whose equality it promises.
