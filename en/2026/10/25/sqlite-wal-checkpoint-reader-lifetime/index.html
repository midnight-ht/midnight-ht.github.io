SQLite WAL checkpointing is not file shrinkage: inspect readers and choose a mode

Trace two connections to separate checkpoint progress, WAL reuse, and truncation, with PASSIVE results and reader-lifetime tradeoffs.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-25 · Estimated read 17 min
Translations
zh-CN en

Article

Key takeaways

  • A zero PASSIVE busy column does not prove complete copying.
  • Logical progress, reuse, and truncation need separate evidence.
  • Shorter read transactions must preserve export consistency and patched-runtime scope.

A SQLite checkpoint does not establish that the WAL file has shrunk. Separate three questions: how much log content has been copied back, whether old read transactions still need the log, and whether the selected mode requires physical truncation. Long readers can restrict progress and reuse. Even after complete copying, retaining the file for later overwriting can be normal. Neither one return value nor file length alone establishes failure.

What does a long read transaction retain?

SQLite's WAL documentation explains that a read transaction fixes its commit boundary when reading starts, preserving one snapshot. Later writes can append to the log, but checkpoint progress cannot destroy content needed by an older reader. Concurrent reading and writing therefore does not imply unrestricted log reclamation.

The relevant lifetime belongs to the transaction, not the loading indicator. An exporter may finish fetching a batch and wait for an upload while its transaction remains open. Check the binding's relationship between returning pooled connections, closing cursors, and ending transactions. A query function returning does not by itself establish transaction completion.

The two-connection workflow below is unexecuted. Proposed concurrency checks should use a runtime containing the official WAL-reset fix. The official page identifies version 3.51.3 and later, with backports in 3.44.6 and 3.50.7. Verify vendor backports separately, and identify the library embedded in the application rather than assuming the system command uses the same build. Write volume, maintenance settings, lock contention, or version defects can also contribute to growth; a long reader is not an established root cause without observations.

Build a complete two-connection timeline

In a disposable database, connection B enables WAL and checks the returned mode, temporarily disables its own automatic checkpointing, creates a table, and commits an initial row. Disabling the automatic work makes the manual timeline easier to interpret; it is not a production recommendation. Connection A then starts an explicit read transaction, actually executes a query to establish its snapshot, and keeps the transaction open.

-- Connection B: isolated setup, not executed.
PRAGMA journal_mode=WAL;
PRAGMA wal_autocheckpoint=0;
CREATE TABLE sample(id INTEGER PRIMARY KEY, value INTEGER);
INSERT INTO sample VALUES(1, 0);
-- Connection A: establish and keep the read transaction.
BEGIN;
SELECT value FROM sample WHERE id=1;
-- Connection B: commit a later version, then inspect progress.
UPDATE sample SET value=value+1 WHERE id=1;
UPDATE sample SET value=value+1 WHERE id=1;
PRAGMA main.wal_checkpoint(PASSIVE);

Send each section to its labelled connection rather than pasting everything into one session. Suppose A still depends on the old WAL snapshot and B has committed a newer version beyond that boundary. PASSIVE can copy eligible content but cannot cross the boundary protecting the old reader. A repeating the query inside the same transaction should retain its original snapshot rather than see B's new value. Actual frame counts depend on pages and prior state; no fixed result row is fabricated here.

A then explicitly commits or rolls back its read transaction and releases the relevant statements. B tries checkpointing again. With no other readers, writers, or errors, the original reader obstacle is gone. Still inspect the result: a UI completion action is not reclamation evidence. To test physical truncation, B can request PRAGMA main.wal_checkpoint(TRUNCATE) in this isolated window and record both its returned values and file length.

-- Connection A: explicitly release the read transaction.
COMMIT;
-- Connection B: compare progress after release, then request truncation.
PRAGMA main.wal_checkpoint(PASSIVE);
PRAGMA main.wal_checkpoint(TRUNCATE);

What does PASSIVE returning zero in its first column establish?

The wal_checkpoint PRAGMA definition returns three integers. The first indicates a busy condition preventing the requested operation from completing; the other two describe log pages and checkpointed pages. PASSIVE does not wait for readers or writers and does not invoke the busy handler. Its first column can be zero despite partial progress, so inspect the remaining columns too.

Those counts describe the log and checkpoint progress at completion. The third is not simply the amount newly copied by this invocation; adding it across calls double-counts earlier work. Equal counts support logical completion over that log range at that moment, not a zero-length file or a promise that the next write adds nothing. A non-WAL case can yield negative-one counts; inspect mode and errors rather than computing negative backlog.

A large directory entry can also represent a log available for reuse. Treating byte length as uncheckpointed work can misclassify retained allocation, while looking only at the page-count difference can miss disk pressure. Record logical progress, physical length, and observation time separately.

Choose a mode by its waiting target

The checkpoint interface documentation distinguishes FULL, RESTART, and TRUNCATE. FULL waits for the writer and for readers to reach the latest snapshot before copying the log. RESTART additionally waits until readers no longer use the WAL, enabling the next writer to restart from its beginning. TRUNCATE also requires truncating the log to zero bytes before successful completion. Stronger modes can wait and affect writes; a large file alone does not justify putting them unconditionally on a request path.

Background maintenance may choose best-effort PASSIVE with progress and transaction-lifetime monitoring. A maintenance window explicitly requiring returned space can assess truncation with a waiting budget. When the busy handler declines further waiting, a stronger mode can perform only partial work and report busy. Issuing TRUNCATE is not evidence of truncation. Another checkpoint holding the checkpoint lock can also cause immediate failure; increasing a busy timeout does not make every lock conflict wait.

Do not manually delete an active database's -wal file. It may contain committed data not yet copied back, and deletion bypasses SQLite's consistency management. A capacity alert should lead to identifying owners, controlling new work, and deliberate maintenance, rather than treating the log as disposable cache.

Does ending an export transaction early sacrifice one-snapshot consistency?

It can change the contract. If the whole export must reflect one instant, ending and reopening transactions between batches can expose later commits and produce an internally inconsistent output. Consider consuming the same snapshot faster, producing a controlled intermediate result, or batching by a business-approved version boundary. Explain consistency, additional storage, and recovery costs for each choice.

The per-connection foreign-key article concerns initialization settings. Here ownership follows the actual read transaction. Do not silently sacrifice export consistency to solve disk growth, or leave a transaction open indefinitely while waiting on a user without an owner.

Is the automatic threshold a hard WAL size limit?

No. A page threshold triggers maintenance; automatic checkpoints are PASSIVE. Persistent readers can prevent completion, and the trigger does not promise physical truncation. Define observations and responses separately for capacity, longest read transaction, and maintenance delay. Multiplying the threshold by page size does not establish a disk limit the file can never exceed.

Proposed verification records runtime identity, journal mode, both transaction timelines, every three-column result, file length, waits, and errors. Cover an old snapshot held open, its release, competing maintenance, and successful truncation, while checking business query results. No database or command was executed here. Identify which transaction restricts which stage, then choose maintenance that matches the required copying, reuse, or physical-reclamation outcome.
