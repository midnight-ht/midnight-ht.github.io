JOIN USING changed a column: why did the interface change too?

Track column merging, order, explicit projection, and provenance when a join refactor feeds an interface.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-25 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • USING changes the columns expanded by a star projection.
  • Explicit projection makes interface changes visible.
  • A merged key alone does not establish source provenance.

Changing JOIN ON a.id = b.id to JOIN USING (id) can preserve matched rows while changing the columns produced by SELECT *. USING merges the named join columns into one output column. The left and right keys no longer occupy separate positions. For exports, serializers, or consumers depending on column count and order, that is an output-contract change.

A shorter condition also changes projection

The PostgreSQL 18 table-expression documentation specifies that ON produces all left columns followed by all right columns. USING produces the merged columns in the order listed, then the remaining left columns, then the remaining right columns. This article discusses that version's result shape and makes no claim that one form is universally faster. All SQL here is unexecuted.

Suppose customers has columns id and name, while credits has id and points. Customers contains keys one and two; credits contains one and three. An equality inner join using ON produces id, name, id, points under a star projection. USING produces id, name, points. Customer one remains the same matched entity, but column four becomes column three and a duplicate name disappears. Comparing row counts cannot detect this.

WITH customers(id, name) AS (
  VALUES (1, 'A'), (2, 'B')
), credits(id, points) AS (
  VALUES (1, 20), (3, 30)
)
SELECT * FROM customers c JOIN credits r USING (id);

Reasoning from this input, the result contains customer one with three values: one, A, and twenty. An old exporter reading points from position four now addresses a nonexistent position. If a driver converts rows into objects by field name, its handling of duplicate id fields is a separate driver concern. No particular overwrite rule should be presented as PostgreSQL's universal contract. Verify the database result and object conversion separately.

Multiple join keys create another ordering trap. USING (tenant_id, id) places the tenant key before the entity key even if their original table positions differ. Reordering that list for appearance can change how a positional consumer interprets values. When a shared query feeds a CSV export, report, or record-returning function, review its output list as an interface.

Explicit projection makes refactoring accountable

For an interface returning customer identity, name, and points, explicitly select c.id AS customer_id, c.name, r.points. The join condition can then change without using star expansion to redefine the interface. If both source keys matter, select c.id AS customer_id and r.id AS credit_customer_id separately. Identical source names should not conceal different responsibilities.

Explicit projection has a maintenance cost: new business fields require a query and consumer-contract update. That cost makes change visible. Whether star projection is appropriate depends on whether this is temporary exploration, whether consumers depend on a stable structure, and whether a version boundary exists. A blanket prohibition is less useful than explaining the difference between inspecting data and exposing a long-lived interface.

Another failure case involves two status columns describing different things: customer status and credit-account status. Matching names do not establish matching meaning, so adding status to USING can be incorrect. NATURAL JOIN automatically includes all common names in its matching condition. A future same-named field can therefore change which rows match. USING lists its names explicitly, so unrelated added columns do not automatically become predicates; a star projection may still gain fields.

Separate predicate drift from projection drift. The former changes which rows match; the latter changes which columns consumers receive. USING constrains automatic predicate expansion but does not freeze star output. Review both “did the matching rule change?” and “did the visible fields change?” instead of attaching a single safety label to a keyword.

Test the column contract as well as values

A proposed test should record field names, order, count, and business meaning, then independently check row membership and values. For positional access, run the old consumer against the new result and look for silent misalignment. For object access, inspect driver column metadata and duplicate-name handling. Comparing only unordered objects can discard the very duplicates or ordering being examined.

Prepare left-only, right-only, and matching keys, plus non-key fields sharing a name. Explain which differences are intended and which must block the change. An interface can deliberately evolve when a new field is required. An internal readability refactor should preserve the agreed external projection. No driver, CSV export, or database was run here; these are acceptance proposals.

After FULL JOIN merges the key, how can a consumer identify each source?

The merged id alone is insufficient. A full outer join retains unmatched rows from both sides, and its merged key may be populated without identifying which side supplied a record. Explicitly select each side's non-null primary key under a separate name, or introduce source markers in the inputs and expose them deliberately. A provenance field must distinguish a real NULL value from an absent matched row. An arbitrary nullable business field cannot reliably do that.

With customers one and two and credits one and three, the full join represents one as matched, two as customer-only, and three as credit-only. All three merged ids have values, so their presence does not reveal the missing side. Retain separate source keys, write independent expectations for each case, and verify that serialization does not merge them again. Provenance is an additional requirement; column-name guesses are inadequate.

Nullable join keys need a separate decision. Two NULL keys do not become the same entity merely because USING merges output columns. Output merging does not change equality matching for NULL. If each side contains a record with a missing customer identifier, their empty-looking keys should not be interpreted as a successful association. Input constraints might prohibit missing identities altogether.

If the business truly requires a relationship between empty states, write its matching condition explicitly and review possible many-to-many expansion. Column merging cannot supply missing identity semantics. Add NULL-key inputs on both sides and inspect matching rows and provenance markers. This checks column compatibility without mistaking an empty output cell for evidence that both sources identify the same entity.

The earlier LEFT JOIN condition-placement article examines why rows disappear. This article examines why fields can differ even while the rows remain. Include before-and-after column contracts with a join refactor and identify the consumer's actual dependency. Equal row counts are useful evidence for one property, not a conclusion about result compatibility.
