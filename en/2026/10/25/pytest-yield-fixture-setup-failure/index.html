pytest setup fails before yield: give acquired resources a cleanup owner

Separate pre-yield setup failure, completed-fixture teardown, and unknown remote creation outcomes.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-25 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • A pre-yield failure skips that fixture’s post-yield teardown.
  • Assign cleanup promptly after successful acquisition.
  • Unknown remote creation needs reconciliation rather than assumptions.

When a pytest fixture raises before reaching yield, pytest does not execute that fixture's teardown code placed after the yield. Resource creation, configuration, and delivery may look like one setup operation, but failure can occur before delivery. Close that gap by assigning cleanup as soon as a resource has been acquired successfully.

Why teardown does not cover every setup operation

The pytest fixture guide distinguishes the failing fixture from fixtures that have already completed setup for the same test. The former does not get its post-yield teardown; pytest still attempts normal teardown for the latter. One missing deletion does not establish that every fixture lost its cleanup opportunity.

Replacing yield with return does not address the underlying ownership problem. The framework must first receive the yielded value before it can drive the generator's remaining code as teardown. A setup sequence with several side effects does not automatically roll back earlier successful operations when a later one raises. External state can exist before the test function starts.

The earlier fixture isolation article concerns the lifetime of shared mutable state. This article concerns a different interval: the resource exists, but its cleanup path has not been established. Reducing fixture scope alone does not close it.

Split a failed invitation workflow by ownership

Consider an unexecuted example that creates a temporary team, invites a member, and finally yields the team. Creation succeeds, but the invitation raises a permissions error. Deletion placed after yield is never reached. A later test using the same team name may then encounter a conflict that appears unrelated to the original setup failure.

Have one fixture own team creation and deletion, and a dependent fixture perform the invitation. Once the team fixture has yielded successfully, a failure in invitation setup still leaves the team eligible for normal teardown. The following illustration has not been run. api represents a project-provided test client, not a built-in pytest feature.

import pytest

@pytest.fixture
def team(api):
    created = api.create_team()
    yield created
    api.delete_team(created.id)

@pytest.fixture
def invited_team(api, team):
    api.invite_member(team.id)
    return team

def test_member_list(invited_team, api):
    assert api.member_count(invited_team.id) == 1

On success, the test receives the invited team and teardown deletes it. If invitation setup fails, the test body does not run, but the team fixture has completed setup and pytest still attempts its cleanup. If creation itself fails, no value has been delivered. Whether a remote object nevertheless exists depends on the creation endpoint's transaction and timeout contract.

Deletion of the team must also have a defined relationship to invitations. If an invitation is a separate object that requires explicit withdrawal, assign separate ownership. Do not assume cascading deletion because the objects appear in the same test. Split fixtures around meaningful acquisition and reversal boundaries, rather than wrapping every line.

When direct finalizer registration helps

The same guide describes request.addfinalizer: once a finalizer is registered, pytest calls it even if later setup raises. Register immediately after the operation that creates something requiring cleanup, rather than before acquisition with a closure referring to an unassigned handle.

A fixture acquiring several handles can register each closer after its corresponding acquisition. Waiting until every configuration step succeeds reintroduces the gap. A straightforward acquire-and-release resource can keep the simpler generator fixture. The deciding question is which resources exist at each possible failure point.

Local synchronous acquisition may also use try/finally after successful acquisition, protecting later configuration and yield with ordinary Python unwinding. This cannot promise cleanup after a forcibly terminated process. Remote resources may need run identifiers, expiration policies, or controlled reconciliation for that case. Those are system design measures, not automatic pytest features.

What if creation times out after the server commits?

Moving yield cannot resolve an unknown remote outcome. A client that receives no object ID cannot conclude that creation never happened. Consider an authorized lookup using a run identifier or an idempotency key, then clean up resources whose ownership is established. Broad deletion by name prefix is unsafe when workers or developers share an environment.

Suppose the server commits team creation and the response is lost. Retrying without an idempotency contract may create another team. Deleting only the second leaves the first behind. Validation must distinguish no creation, unknown outcome, and confirmed creation. Unknown outcomes need reconciliation or manual handling rather than a report saying that failed creation required no cleanup.

What should happen if deletion fails?

Keep resource identity and error details when cleanup itself fails. Show both the original setup error and the cleanup error; neither should erase the other. Whether repeated deletion is safe, and whether not-found means already cleaned, belongs to the endpoint contract.

How to verify that the gap is closed

Plan isolated cases for creation failure, configuration failure after creation, assertion failure, success, and deletion failure. Query resource existence by run identifier and check whether the test body should have executed. An exit code alone cannot reveal a leak: an expected setup error should still fail the test while owned resources are reclaimed.

Check teardown order for dependent resources and give concurrent tests distinct ownership. Otherwise one test's cleanup can hide another's leak. This article has not run pytest, called a remote service, or verified an empty environment. Start with one real multistep setup path, mark every acquisition and cleanup registration, and use those intervals to choose fixture decomposition or finalizers.
