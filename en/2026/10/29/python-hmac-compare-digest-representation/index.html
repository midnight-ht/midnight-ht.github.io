Why can compare_digest still reject an HMAC signature?

Distinguish raw HMAC bytes from encoded text, implement a narrow illustrative parser, and separate comparison properties from replay and endpoint security.

Updated 2026-10-29 · Estimated read 11 min
Translations
zh-CN en

Article

Key takeaways

  • Matching types does not establish matching digest representations.
  • Cryptographic comparison does not prove endpoint-wide constant timing.
  • A matching message authenticator does not establish freshness.

hmac.compare_digest() does not decode hexadecimal text into digest bytes. When verification keeps failing, first establish the representation, type, and format on each side. A comparison function suitable for cryptographic use cannot interpret a signature protocol for you.

Thirty-two bytes are not sixty-four characters

The Python hmac reference, checked on October 29, 2026 in Python 3.14.10 documentation, distinguishes digest bytes from hexadecimal text. compare_digest requires compatible inputs of the same documented type: ASCII strings or bytes-like objects.

Suppose a protocol encodes an HMAC-SHA256 digest as 64 hexadecimal characters. hmac.digest(key, body, 'sha256') produces 32 bytes, while the header is a string. Encoding that string into bytes only produces bytes representing hexadecimal characters; it does not recover the original digest. Matching types is necessary but does not settle representation.

Alternatively, compute hexdigest and compare the required textual representation. The protocol must determine case rules, prefixes, separators, and algorithm identifiers. Arbitrary trimming or lowercasing expands accepted inputs unless the protocol authorizes that normalization.

Separate parsing from authentication comparison

This complete function assumes a deliberately narrow protocol: exactly 64 lowercase hexadecimal characters, without a prefix. Key retrieval, rotation, and transport limits belong outside it. It has not been executed or security-tested.

import hmac
import re

HEX_SHA256 = re.compile(r"[0-9a-f]{64}")

def verify_message(key: bytes, body: bytes, signature: str) -> bool:
    if not isinstance(signature, str):
        return False
    if HEX_SHA256.fullmatch(signature) is None:
        return False
    received = bytes.fromhex(signature)
    expected = hmac.digest(key, body, "sha256")
    return hmac.compare_digest(expected, received)

The parser validates the entire text, then decodes it into digest bytes. The final operation compares the same representation. A real provider that accepts uppercase or supplies an algorithm prefix needs its documented parser and tests; this example is not a universal Webhook verifier.

A well-formed signature computed with the wrong key should fail during comparison. Malformed text fails earlier. Internal diagnostics can distinguish those stages without recording secrets or full sensitive bodies. Whether public responses distinguish them is a separate interface decision.

What timing property does the function provide?

The documentation describes avoiding content-based short-circuiting. It also warns that differing lengths or errors may theoretically reveal type and length information. Therefore, using compare_digest does not establish constant-time behavior for the entire endpoint or eliminate all side channels. Parsing, message acquisition, and key selection have their own behavior.

A threat model requiring additional uniformity needs review of the complete implementation. Padding every malformed input with a fake digest is not automatically the right repair. Nor should an implementation try ordinary equality first and then fall back to another representation merely to make tests pass. Use a defined conversion for each supported protocol version, with explicit version and key selection.

Does a match make a repeated Webhook acceptable?

Not by itself. An authentic message sent earlier can still carry a valid digest. compare_digest does not check time, event identity, or whether the operation already happened. A signed timestamp, an allowed time window, and durable deduplication need their own protocol and business rules. None is implemented by the example.

The site's raw-body verification article explains why parsing and reserializing a message can change the signed bytes. This article addresses the opposite end: correct message bytes still do not make raw digest bytes and encoded digest text interchangeable. Keep message acquisition, signature parsing, key selection, and comparison separately diagnosable.

A proposed test uses a fixed non-production key and message to generate a valid signature. Change one message byte, the key, a digest character, and the length. Add uppercase, spaces, non-ASCII input, well-formed wrong content, and a raw-versus-hex representation mistake. Define acceptance from the protocol before observing what the implementation accepts.

A fixed-size signature does not make processing the message fixed-cost. Apply the endpoint’s body-size policy before verification, and do not let an untrusted algorithm name choose arbitrary server computation. Supporting several algorithms requires controlled version and key selection followed by the corresponding parser. Passing signature-format validation must not bypass the message resource limit.

Those tests establish behavior for their inputs, not production security. Provider acceptance additionally requires the correct algorithm, covered message fields, key source, rotation, and replay policy. No code, provider callback, or timing experiment was run here. Write down both sides' type, encoding, and length before blaming the comparison operation.
