Why can SQLite writes fail with a five-second busy_timeout?

Follow an unexecuted two-connection example to distinguish SQLite waiting policy, deadlock exceptions, handler replacement, and transaction retry boundaries.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-29 · Estimated read 11 min
Translations
zh-CN en

Article

Key takeaways

  • A timeout installs a bounded waiting policy rather than a success promise.
  • A connection has one busy handler and later settings replace it.
  • Inspect transaction state before deciding what to retry.

Setting SQLite busy_timeout=5000 does not promise that every write waits five seconds and succeeds. It installs a bounded busy handler on a connection. The operation can still return SQLITE_BUSY, and SQLite may bypass the handler to avoid a potential deadlock. First identify the lock owner and the connection's actual policy.

A waiting policy is not a success reservation

The sqlite3_busy_timeout reference, checked on October 29, 2026, describes repeated sleeping until the accumulated sleep budget is reached, after which the handler stops retrying and the operation returns SQLITE_BUSY. A non-positive value disables the handler. This living reference does not pin a library release; record the project's actual SQLite version.

Accumulated sleeping is not identical to total request latency. SQL execution, scheduling, and other work take time too. The configured number is neither a universal minimum wait nor an exact wall-clock maximum. A quick failure alone does not establish that configuration was ignored.

The busy-handler reference explicitly permits returning SQLITE_BUSY without invoking the handler when waiting could cause deadlock. Two connections can each hold a lock the other needs. Waiting longer cannot resolve that arrangement; a participant must release resources.

Separate the owner from the waiter

These complete two-session teaching steps have not been executed. Assume one local database file with no other writers. Initialize it and close the initialization connection without an open transaction:

CREATE TABLE counters(id INTEGER PRIMARY KEY, value INTEGER NOT NULL);
INSERT INTO counters VALUES (1, 0);

Connection A starts a write transaction and deliberately remains open:

BEGIN IMMEDIATE;
UPDATE counters SET value = value + 1 WHERE id = 1;

Connection B installs its policy and attempts its own transaction:

PRAGMA busy_timeout = 5000;
BEGIN IMMEDIATE;
-- Continue only if BEGIN succeeded:
UPDATE counters SET value = value + 1 WHERE id = 1;
COMMIT;

The execution environment must inspect BEGIN's result. Do not continue after failure while assuming the intended transaction exists. If A keeps its lock, B may exhaust its permitted waiting and fail. If A commits in time, B may proceed. No measured durations or fixed output are claimed.

After observing B, explicitly commit or roll back A and retry B from a fresh transaction entry. This distinguishes a short waiting policy from an owner that never exits. The simple case does not construct a lock-upgrade deadlock, so it cannot prove that every busy error sleeps through the full budget. Reproduce the application's actual read-then-write sequence separately.

Do two libraries' handlers accumulate?

No. SQLite permits only one busy handler per connection. Installing another clears the old one; busy_timeout and its PRAGMA also change it. A custom handler installed during initialization may be replaced by a later adapter setting.

Trace who creates each connection and who configures it afterward. Inspecting one pooled connection does not establish the policy on all others. Configuration checks belong at the real creation or handoff boundary.

The callback is also non-reentrant. The official reference forbids modifying the invoking connection or closing it or its statement from the handler. Complex business recovery should occur after control returns to an application error path, not through SQL issued recursively inside the callback.

What should be retried after a busy error?

That depends on transaction state and prior decisions. Retrying only the final UPDATE may preserve a stale decision made from earlier reads. Establish the current transaction state, end or recover it according to the contract, and restart at the appropriate decision boundary. A database retry does not undo or deduplicate an external request already sent.

Do not use the same retry policy for lock contention, constraint failures, permission errors, and disk faults. Bound the operations that are safe to retry with a total budget and an observable terminal result. Avoid waiting indefinitely after the original request has lost its owner.

The site's WAL checkpoint article covers readers affecting checkpoint progress. That is a different object from configuring a write contender's busy handler or replaying a business transaction.

Proposed validation records connection versions, transaction ordering, settings, timestamps, and error codes. Test early owner commit, continued lock ownership, rollback, and later handler replacement. Add the real application's lock-upgrade sequence. Coordinate release with barriers rather than random sleeps.

Disable an experiment driver’s continue-on-error behavior. If B’s BEGIN fails, record that result and stop the round; a later UPDATE might otherwise become an unlabelled autocommit attempt, followed by a misleading COMMIT error. Start each round from a confirmed clean transaction state and preserve its identity and statement results. This isolates the waiting policy from accidental writes introduced by the test harness.

No two-connection experiment or throughput comparison was run. A useful waiting policy names its owner, waiter, and stopping condition. A timeout number without transaction exit and failure handling is not a complete write contract.
