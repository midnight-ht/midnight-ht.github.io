Why can Python wait_for return after its one-second timeout?

Separate timeout initiation, completed cancellation, and cleanup ownership using an unexecuted asyncio example, including cleanup failures and shield.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-29 · Estimated read 11 min
Translations

Article

Key takeaways

  • Cancellation settlement can extend waiting beyond the timeout.
  • Cleanup failure can change the exception observed by the caller.
  • Shielded work still needs an owner after the waiter times out.

asyncio.wait_for(..., timeout=1) does not guarantee that the whole call returns within one second. On timeout it cancels the awaited task and waits for cancellation to finish. Cleanup can extend that wait. A request budget needs separate decisions about when cancellation starts and when resource ownership ends.

Timeout is not process termination

The Python wait_for reference, checked on October 29, 2026 in documentation headed Python 3.14.10, explicitly permits total waiting beyond the timeout. Exceptions raised during cancellation propagate. Waiting for cancellation has applied since Python 3.7; the built-in TimeoutError replaced asyncio.TimeoutError in this interface in 3.11.

Imagine an export that must close a connection and remove temporary output after cancellation. “Start exiting after one second” and “all cleanup has finished after one second” are different promises. Specify when new results stop being accepted, who owns cleanup, how long the service will wait, and where cleanup failure is reported.

Cancellation is cooperative. Long synchronous work inside a coroutine can prevent the event loop from running timeout logic promptly. Wrapping it in wait_for does not create a preemptive execution boundary. Work requiring separate termination controls needs a design appropriate to its execution model.

Make the cleanup phase visible

This complete teaching program has not been executed. Its delays construct stages; they are not measured performance results, and scheduling does not guarantee an exact sum of durations.

import asyncio

async def export_report():
    try:
        await asyncio.sleep(60)
        return "report"
    finally:
        print("cleanup started")
        await asyncio.sleep(0.2)
        print("cleanup finished")

async def main():
    try:
        await asyncio.wait_for(export_report(), timeout=1)
    except TimeoutError:
        print("caller observed timeout")

asyncio.run(main())

Reasoning from the documented behavior, timeout moves the export into its finally block. The waiter settles cancellation before the caller handles the timeout. The useful observation is the relationship among cleanup start, cleanup finish, and the caller's terminal state, rather than a claim that a line appears at exactly one second.

If cleanup instead raises RuntimeError, a test expecting only TimeoutError has the wrong contract. Preserve the cleanup error and resource identity rather than flattening every failure into “timed out; retry.” A user-visible failure does not itself delete temporary output.

Likewise, catching CancelledError and returning normally changes how the task responds to cancellation. Normally cleanup should be followed by propagation. If the application intentionally allows completion after a cancellation request, its caller must explicitly accept that behavior; it cannot simultaneously advertise a hard deadline.

Who owns work protected by shield?

The shield documentation explains protection from cancellation originating in the outer waiter. Applying wait_for to shield(task) can change which task receives cancellation, but does not provide a manager for the internal work. Retain its reference and decide who later awaits its outcome or cancels it.

If the export becomes a background job, give it an identity, observable status, retry rules, and result retention. If it remains request-scoped, decide whether it is allowed to outlive that request. Adding shield merely to return sooner can otherwise leave unowned work consuming resources.

The site's TaskGroup article concerns group membership and joint failure. This question exists even with one task: a wait budget, a cancellation request, and completed cancellation are distinct events.

Test settlement, then measure time

A proposed test can use event barriers: confirm work has started, trigger timeout, hold cleanup at a controlled event, check that the waiter has not settled, then release cleanup and inspect the terminal state. Additional cases should cover cleanup failure, suppressed cancellation, shielded work, and cancellation of the outer waiter.

If durations matter, record an appropriate monotonic clock, Python version, and environment. Event ordering and latency distributions answer different questions. A local delay test does not establish a production maximum, or prove that a remote write was rolled back. Query the remote protocol's result before retrying work whose side effects may already exist.

A second cleanup budget needs an explicit exhausted state. If synchronous cleanup can no longer be promised, register the remaining resource with an owned recovery process. Another timeout wrapper does not establish that a file was deleted or a connection closed. Whether cleanup may itself be cancelled and safely retried depends on the resource interface. Include a cleanup-that-does-not-finish case and verify both bounded user waiting and an honest unresolved-cleanup state.

No asynchronous program or timing measurement was run here. Before accepting “one-second timeout,” specify the user's waiting budget, the cancellation point, the cleanup owner, and confirmation of external outcomes. Then assign wait_for the particular part it actually implements.
