Why can Node.js open fail after access succeeds?

Use direct opening and exclusive creation to explain Node.js file races, meaningful error states, handle closure, and target-filesystem boundaries.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-29 · Estimated read 10 min

Article

Key takeaways

  • A successful accessibility check does not reserve a path.
  • Express create-without-overwrite through the open flags.
  • Read, write, close, and delivery failures need separate handling.

A successful fs.access() call does not reserve a path for a later open(). Another process can change the filesystem between those operations. Read by opening the file and handling that operation's error. When creation must not overwrite an existing file, express that condition in the open flags.

An accessibility result describes an observation

The Node.js filesystem reference, checked on October 29, 2026 with a v24.22.2 header, explicitly discourages checking accessibility before opening a file. This discussion assumes an ordinary file in a trusted directory; selecting authorized paths is a separate requirement.

Suppose configuration rotation removes an old file after an accessibility check succeeds but before the read starts. The read can encounter ENOENT. Conversely, a file missing during the check can exist when the read would run. Adding another check merely moves the gap. Synchronous JavaScript calls do not freeze other processes or the operating system's namespace.

Handle errors at the operation that matters

This complete illustrative example has not been executed. Its interface permits a missing optional configuration but propagates other errors:

import { open } from 'node:fs/promises';

export async function readOptionalConfig(path) {
  let file;
  try {
    file = await open(path, 'r');
  } catch (error) {
    if (error.code === 'ENOENT') return { status: 'missing' };
    throw error;
  }
  try {
    const text = await file.readFile({ encoding: 'utf8' });
    return { status: 'loaded', text };
  } finally {
    await file.close();
  }
}

Only a missing file at open time becomes missing. A read failure after opening is not silently reclassified as absent configuration. The acquired handle is closed in finally. A loaded result establishes that text was obtained, not that JSON is valid, its version is correct, or the application adopted it.

A handle also does not establish an agreement with every writer to leave the contents unchanged. A consistent configuration snapshot may require a separate write-and-replace protocol. The site's rename and file-delivery discussion covers additional delivery and durability boundaries.

Put exclusive creation into open

Checking that a path is absent and then opening it with an ordinary write mode lets two creators both observe absence. Use wx when the intended condition is “create only if it does not already exist,” and handle EEXIST:

export async function createNewText(path, text) {
  let file;
  try {
    file = await open(path, 'wx');
  } catch (error) {
    if (error.code === 'EEXIST') return { status: 'exists' };
    throw error;
  }
  try {
    await file.writeFile(text, { encoding: 'utf8' });
    return { status: 'written' };
  } finally {
    await file.close();
  }
}

This unexecuted function illustrates conditional creation and cleanup. It does not provide crash-safe delivery. A write failure may leave an incomplete file created by this operation; cleanup or diagnostic retention needs an ownership decision. Exclusive creation also does not prevent later modification. Node warns that the exclusive flag may not work on network filesystems, so a local test cannot validate a shared-drive contract.

Nor is wx a path-authorization mechanism. A user-controlled directory, symbolic links, or an unauthorized target still needs its own design. The example is not a secure service for arbitrary untrusted paths.

Should every use of access be removed?

No. Accessibility can itself be the information being requested, such as a status display or a signal supplied by another process. The display must not eliminate error handling from a later read. Node also documents a Windows limitation: access does not check directory ACL restrictions in the same way that the eventual operation encounters them. It is not the authority for application permissions.

A useful test uses controlled coordination: pause after the check, remove the file from another participant, then allow opening to proceed. Also cover permission denial, failure after acquiring a handle, and two competing exclusive creators. Verify the returned state, propagated errors, closure, and EEXIST handling. Use target-environment checks for Windows and network filesystems.

The small function lets a close failure propagate. If reading also fails, an exception from finally can obscure the original read error. A service needing both diagnostics should collect and associate them explicitly rather than suppressing close failures to preserve success. Inject read failure, close failure, and both together to verify the intended reporting policy; an accessibility precheck cannot resolve this handle-lifetime decision.

No filesystem or concurrency tests were run for this article. Find the assumption that a successful check guarantees the next operation, move the required condition into that operation or an explicit coordination protocol, and retain a meaningful failure result.
