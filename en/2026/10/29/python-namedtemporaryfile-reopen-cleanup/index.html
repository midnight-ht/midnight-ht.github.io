Why can a named Python temporary file fail to reopen?

Use Python 3.12+ delete_on_close to define a path-based consumer lifetime, Windows handle constraints, and cleanup or durable-artifact handoff.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile

Translations

Article

Key takeaways

  • Default closure deletes the named temporary file.
  • Deferred deletion still requires readers to finish before cleanup.
  • Returning a path string does not extend the file lifetime.

A NamedTemporaryFile has a visible path, but its default configuration deletes it when it closes. Passing that path to another reader requires an explicit lifetime extending through the reader's work. Python 3.12 added delete_on_close=False to defer automatic deletion until context cleanup, while still requiring readers to finish and close their handles.

Separate the name, handle, and deletion point

The tempfile reference, checked on October 29, 2026 in Python 3.14.10 documentation, describes these controls. Both delete and delete_on_close default to true. With delete true and delete_on_close false, closing does not immediately delete the file; context exit provides the later cleanup point. Older interpreters do not accept this parameter.

Imagine creating CSV input for a converter that accepts only paths. Closing before starting the converter can remove the input. Keeping it open introduces platform-specific reopening rules. Random filenames address collisions, not this lifetime problem. A path does not tell the creator when a consumer has finished; a synchronous return, awaited task, or another completion protocol must express that handoff.

Finish the second read inside the owning context

This complete illustrative function requires Python 3.12 or newer and has not been executed. A standard open call stands in for a path-based consumer. It returns content rather than an expiring path.

from tempfile import NamedTemporaryFile

def read_through_path(text: str) -> str:
    with NamedTemporaryFile(
        mode="w", encoding="utf-8", suffix=".txt",
        delete=True, delete_on_close=False,
    ) as temporary:
        temporary.write(text)
        temporary.flush()
        path = temporary.name
        temporary.close()
        with open(path, encoding="utf-8") as reader:
            result = reader.read()
    return result

Flushing and closing hand the buffered output to the filesystem before reopening. The inner reader closes before the outer context attempts deletion. This is not a crash-durability guarantee or proof that an external tool interprets the content correctly.

For a subprocess consumer, wait for completion and check its exit status inside the same owning scope. Starting background work and immediately returning can let cleanup win the race. A genuinely long-running background consumer needs transferred ownership and a separate cleanup protocol, not a guessed delay.

Why does Windows need its own check?

The official reference distinguishes POSIX and Windows reopening. POSIX permits reopening a still-open named temporary file. Windows requires an appropriate condition, such as disabling deletion, sharing delete access on the additional open, or using delete true with delete_on_close false. In the last case, ordinary additional opens must close before context exit or deletion can raise PermissionError.

Reading successfully and cleaning up successfully are separate acceptance points. Deferred deletion can also expose insufficient directory deletion permission at context exit. A passing test on a POSIX development machine does not establish Windows acceptance.

That difference does not make delete=False a universal Windows fix. It transfers cleanup responsibility to the application. An exception path that omits unlink can retain private content; a temporary directory is neither a confidentiality policy nor an expiry service.

Does delete=False solve the handoff?

It prevents automatic deletion at close, but does not establish when the reader finishes or who eventually removes the file. Diagnostic retention can be legitimate if a controlled failure branch records the artifact's identity, permitted access, and expiry. Without that policy, retained files become ambiguous leftovers.

A finally block also cannot guarantee cleanup after forced termination. The documentation specifically notes that POSIX SIGKILL cannot automatically remove the named temporary files created by the killed process. A later cleanup job needs ownership and age criteria; it should not indiscriminately delete files in a shared directory.

The site's contextmanager article addresses control flow. Even correct context-manager control flow cannot establish when an external consumer is done. The cleanup point must match that consumer's actual completion.

Proposed validation should compare written and reread content, then check that the path is absent after normal return. Inject write failure, read failure, an unclosed reader, and an unfinished consumer. Run POSIX and Windows checks separately, recording interpreter version and permissions. Treat forced-termination recovery as a separate operational test.

If the caller needs a downloadable artifact, returning this function’s path is the wrong interface. Storing its string in a queue or database does not extend the file’s lifetime. Copy the content into a separately owned artifact location and verify that handoff, or explicitly transfer ownership to a durable manager. A successful temporary read and an export available later require different completion evidence.

No file, subprocess, or cross-platform test was run here. Define the period during which the path must exist, place the complete read inside it, and change ownership when that cannot be done.
