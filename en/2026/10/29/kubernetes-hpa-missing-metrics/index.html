Why missing Pod metrics can make HPA downscale less than expected

Separate the displayed utilization from conservative decision inputs, calculate a four-Pod example, and check multi-metric failures and observation times.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-29 · Estimated read 11 min
Translations
zh-CN en

Article

Key takeaways

  • Displayed utilization can omit the assumptions used for missing Pods.
  • The isolated four-Pod example yields three replicas rather than the intuitive two.
  • Check metric-fetch errors, readiness and timestamps as separate inputs.

The average utilization shown in HPA status is not necessarily the final ratio used for a downscale decision. When some Pods lack metrics, the controller recomputes conservatively. The reduction can therefore be smaller than a direct calculation from the displayed average suggests. Identify the valid samples before changing the utilization target.

Displayed observations and decision assumptions

The Kubernetes HPA algorithm description describes direction-dependent assumptions: missing Pods consume 100 percent of the target during downscaling and zero percent during upscaling. Both assumptions dampen the proposed change. Status continues to report the original average without those adjustments. The documentation was checked on October 29, 2026; no cluster was accessed.

An assumption is not a measurement. Missing data remains missing even when the controller inserts a conservative decision value. Preserve observed values, missing objects and substituted assumptions separately. Otherwise a dashboard can accidentally report an algorithmic assumption as real CPU usage.

CPU utilization relative to resource requests also differs from absolute CPU consumption. Requests, readiness, sample timing and metric type affect the eligible inputs. A workload overview is not automatically the same input set that HPA evaluated.

A four-Pod example

Assume four eligible Pods with equal CPU requests and a 50 percent utilization target. Two valid observations are 20 percent each; two Pods have no samples. Temporarily exclude bounds, tolerance and stabilization to isolate the missing-data calculation. This is an unexecuted example, not measured cluster capacity.

Treating the observed 20 percent as a complete average yields four times twenty divided by fifty, rounded upward to two replicas. Conservative downscale recomputation instead uses twenty, twenty, fifty and fifty. Their average is 35 percent. Four times thirty-five divided by fifty rounds upward to three replicas. The example explains a smaller reduction, from the intuitive two to three; it does not demonstrate that downscaling must stop entirely.

A real controller also applies tolerance, direction checks and other constraints. Listing both averages and their denominators is more useful than immediately lowering the target. If status shows twenty while the recommendation retains three, investigate the missing Pods and remaining controls.

A no-action example requires adjusted inputs that enter the actual tolerance range. Record the controller version and configuration rather than treating a default boundary as a universal promise. Hand calculation checks the example's consistency; it is not evidence of a controller action.

Why zero during scale-up?

Zero assumptions reduce an average derived from a few high observations. They limit expansion under incomplete information; they do not establish that missing Pods are idle. Not-yet-ready Pods also receive separate CPU treatment and should not all be classified as identical missing measurements.

The documentation says that a recomputed ratio reversing the original direction, or entering tolerance, produces no scaling action. Follow the candidate direction through the final ratio. Lowering a target while the metric pipeline is broken can conceal the evidence problem.

The remedy depends on the cause. Startup behavior calls for readiness and initialization checks. Metric API failures require pipeline diagnosis. Missing resource requests require workload-specification review. Shortening every window because the controller appears conservative can amplify instability elsewhere.

Can one failed metric prevent every action?

For multiple metrics, HPA calculates recommendations separately and selects the largest. If a metric cannot be converted into a desired replica count while the available metrics suggest downscaling, it skips that reduction. An available metric recommending more replicas can still permit expansion. A whole metric-fetch error differs from missing Pod samples within one metric.

For example, CPU might recommend three replicas while the queue metric API fails. Low CPU alone does not establish that an unknown queue permits releasing capacity. If CPU instead requires expansion, the failed queue metric need not block it. Preserve each recommendation and error rather than recording only “metrics unhealthy.”

Proposed validation fixes requests, target, metric type and windows, then varies complete observations, partial missing data, readiness changes and total retrieval failure. Save raw sample timestamps, HPA status, events and actual replica changes. These checks were not executed, and no resource savings are claimed. As with missing metrics versus zero traffic, preserve unknown information before judging the controller's protective response.

Correlate observation times. A manual query may return samples newer than the controller decision being investigated. Record sample timestamps, metric API response time and controller events; otherwise two different moments can create a false discrepancy. If the original inputs are unavailable, mark the explanation as unconfirmed rather than using later complete samples to declare the earlier decision wrong.
