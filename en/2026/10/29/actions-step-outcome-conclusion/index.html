GitHub Actions: read outcome before trusting a tolerated step conclusion

Preserve the original test result while collecting diagnostics, with an explicit final gate and separate policies for skipped checks, cancellation and missing reports.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-29 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • Outcome precedes continue-on-error; conclusion follows it.
  • A diagnostic report can complete while an explicit gate still blocks release.
  • A success outcome cannot expose an error swallowed by the underlying script.

After a GitHub Actions step uses continue-on-error, its original execution result can differ from its final conclusion. Read the pre-tolerance outcome to determine whether the check actually succeeded. Read conclusion to explain why execution continued. Collecting a report can remain possible without turning a failed test into permission to deploy.

Two results for one step

The GitHub Actions steps context reference defines outcome before continue-on-error is applied and conclusion after it is applied. Its explicit example is a failure outcome with a success conclusion. This discussion uses the online documentation checked on October 29, 2026. No hosted workflow was executed, and the step-level behavior is not presented as a description of every job-level policy.

A nonzero test exit describes how the command ended. Permission to continue describes what the workflow should do next. The latter is useful for diagnostics and cleanup, but cannot re-evaluate the assertions. A deployment condition that reads only the adjusted conclusion can therefore allow release while the test report still records a failure.

Decide whether failure is legitimately optional before choosing the syntax. An experimental compatibility check might be advisory under an explicit policy. A required test should not become permanently advisory merely because its report needs collecting. Identical YAML can implement either policy; the project owns that distinction.

Continue reporting while preserving the gate

This unexecuted workflow illustrates a single job without repository code or third-party Actions. Replace the deliberate failing command and reporting method before using the pattern in a real project.

name: inspect-step-result
on: workflow_dispatch
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - name: Deliberate failure
        id: tests
        continue-on-error: true
        run: exit 1
      - name: Record result
        if: ${{ always() }}
        env:
          STEP_RESULT: ${{ toJSON(steps.tests) }}
        run: printf '%s\n' "$STEP_RESULT"
      - name: Enforce successful test
        if: ${{ !cancelled() && steps.tests.outcome != 'success' }}
        run: exit 1

Assuming the first step starts and executes exit 1, its original outcome is failure while tolerance can make its conclusion success. The reporting step preserves both. The final step requires an actual success outcome, so the original failure becomes blocking again. Successfully writing a report does not overwrite the test result.

The last condition checks for anything other than success, rather than checking only failure. A skipped check has not demonstrated success. Cancellation also needs an explicit policy: this example does not deliberately start another enforcement step after cancellation, and a cancelled run is not release evidence.

Do not add always mechanically to every operation. Continuing expensive network work after cancellation may obstruct stopping, and a report operation with missing prerequisites may produce only a secondary error. Review reporting conditions separately from deployment conditions.

Choose the smallest tolerance mechanism

Ordinary failure propagation is simplest when nothing needs continuing. If only diagnostics must survive, an appropriate reporting condition may be enough without changing the test step. Step-level tolerance followed by an explicit final gate is useful when several diagnostics must continue, but every newly added required check must enter that final gate.

There is a different failure that outcome cannot detect: a wrapper catches an error, writes a report and exits zero. The original outcome is then success because the command itself claimed success. Repair the exit contract. Shell pipelines, wrappers and test-runner exit behavior need project-specific checks.

Job-level tolerance, matrix summaries, dependent jobs and required checks introduce other contracts. A single-job example does not establish correct branch protection. When results cross job boundaries, define where the output comes from, how cancellation is represented and which job performs the final enforcement.

How can the original numeric exit code reach the report?

Outcome provides four states, not the command's complete exit code. To distinguish an assertion failure from a runner error, a controlled wrapper can save the numeric result to a file or step output and then return or forward it under an explicit policy. Capture must happen after the original command and before an early shell exit prevents the recording line from running.

Keep both a machine-readable final exit status and a diagnostic report. A file's existence is insufficient: bind it to the run, commit and check so an old file cannot explain a new failure. This article supplies no execution receipt for such a wrapper.

Proposed validation covers success, deliberate failure, a skipped prerequisite and manual cancellation. Inspect outcome, conclusion, report production and deployment eligibility separately. Include a wrapper that intentionally returns zero after an error to expose the limit of context inspection. See artifact identity checks for report and release handoffs. Preserve the original failure evidence before deciding which subsequent work may continue.

Define whether report generation failure is blocking too. If the gate requires that evidence, successful tests alone are insufficient. Save test and report results separately. A deliberately unwritable report directory is a useful proposed control: evidence must be marked missing rather than replaced by an old file, and a secondary reporting error must not erase the original failure.
