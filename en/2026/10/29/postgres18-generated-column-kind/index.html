What does omitting STORED mean in new PostgreSQL 18 DDL?

Check PostgreSQL 18 virtual defaults for new declarations against version 17, then distinguish row-derived amounts, ordinary defaults, and historical snapshots.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-29 · Estimated read 11 min
Translations

Article

Key takeaways

  • An omitted kind in a new PostgreSQL 18 declaration selects virtual.
  • An upgrade alone does not convert existing stored definitions.
  • Stored computation does not replace rules protecting historical inputs.

In PostgreSQL 18 DDL that creates or recreates a table, omitting VIRTUAL and STORED from a generated-column declaration selects VIRTUAL. Write STORED explicitly when the result should be computed and stored on writes. This declaration rule does not mean an upgrade automatically converts existing stored columns.

Check the version before interpreting an omission

The PostgreSQL 18 generated-column reference, checked on October 29, 2026, describes stored computation on writes and virtual computation on reads, with virtual as the default. The version 17 reference implements only stored generated columns and requires STORED. New syntax rules cannot be projected backward.

Imagine removing STORED while simplifying a migration. An older server may reject the declaration; an 18 server can create a virtual column. Successful execution alone would not establish preservation of the previous computation choice. Review the deployed version, actual DDL, and resulting column definition. This is a hypothetical migration risk, not an upgrade performed for this article.

Generated values also differ from ordinary defaults. A default supplies an initial value when no value is provided. A generated column derives its value under a database rule and cannot be arbitrarily overridden by a writer.

Start with a deterministic expression within one row

This complete teaching example has not been executed. STORED makes the choice explicit. Quantity and the agreed unit price belong to the same row; taxes, discounts, and cross-table prices are outside the example.

CREATE TABLE order_lines (
  id bigint PRIMARY KEY,
  quantity integer NOT NULL CHECK (quantity > 0),
  unit_price numeric(12,2) NOT NULL CHECK (unit_price >= 0),
  line_total numeric GENERATED ALWAYS AS
    (quantity * unit_price) STORED
);
INSERT INTO order_lines(id, quantity, unit_price)
VALUES (1, 2, 12.50);
UPDATE order_lines SET quantity = 3 WHERE id = 1;
SELECT quantity, unit_price, line_total FROM order_lines WHERE id = 1;

The documented semantics imply that changing quantity changes the derived total even though the UPDATE does not name it. Choosing VIRTUAL still produces a derived value, but computes it on reading. This does not establish which choice is faster for a real workload or quantify storage savings.

A negative case should attempt to write an arbitrary line_total directly. The reference forbids that while allowing the DEFAULT keyword to request generated handling. This keyword is not a second ordinary default attached to the column. An API accepting a client-supplied total must separately decide whether to reject, verify, or ignore it.

Immutable is a dependency promise

PostgreSQL 18 requires immutable functions, forbids subqueries and references outside the current row, and disallows reference to another generated column. Virtual columns additionally cannot use user-defined functions or types, including indirect use through operators or casts. The choice therefore affects legal expressions as well as computation time.

A value based on current exchange rates, another table's latest product price, or the clock does not fit this simple row-derived expression. Labeling a function immutable does not remove its real external dependencies. Dynamic query results may belong in a query or view; a historical business snapshot needs explicitly preserved inputs and update rights.

Choose first by meaning: an ordinary column records an independently controlled fact, a generated column expresses a current-row dependency, and a view can express a query. Indexing, replication, privileges, and performance need their own version-specific review and workload evidence.

Should every order amount be generated?

No. A captured transaction unit price multiplied by quantity may represent a line amount. A live product price is a different requirement if changing it would rewrite the meaning of historical orders. Tax, discount allocation, rounding, and manual adjustments can have independent confirmation rules.

STORED does not freeze history: updating a base input can still change the stored derived value. If confirmed orders must be immutable, enforce that through the relevant state and permission rules. Column storage kind does not replace business authorization.

The site's DEFAULT and explicit NULL article covers ordinary omitted values. Generated columns require a separate agreement about their base inputs, allowed changes, computation kind, and readers.

Proposed validation should run explicit and omitted-kind declarations separately against isolated target 17 and 18 servers, recording acceptance or rejection. On 18, cover insert, input update, direct generated-column assignment, user-defined functions, and cross-row dependencies; inspect the resulting column definitions. Measure workload performance separately.

When computation timing is the remaining choice, compare identical inputs, expressions, and query sets. Observe writes, reads, storage, and update frequency separately. Different selected columns or indexes can confound the comparison. Establish equivalent results before evaluating costs; the workload determines whether shifting computation is worthwhile.

No migration or performance experiment was run. Make the kind explicit in production-bound DDL, verify that the value should really change with its inputs, and inspect existing definitions instead of inferring them from the upgrade version.
