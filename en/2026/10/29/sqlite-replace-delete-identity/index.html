Why can SQLite REPLACE delete the customer whose name you changed?

Compare SQLite REPLACE with an explicit UPSERT for customer imports, checking identifiers, omitted notes, delete triggers, and related rows.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile

Key takeaways

  • REPLACE can delete a conflicting row before inserting.
  • List only the fields an import is allowed to update.
  • Inspect final identity and deletion audit separately.

SQLite INSERT OR REPLACE can delete an existing row that causes a uniqueness conflict and then insert the incoming row. Treating it as a partial UPDATE can lose information the import never intended to change. A customer import should first decide which record identity and fields must survive.

A repeated email does not establish an update

The SQLite conflict-resolution reference, checked on October 29, 2026 and marked updated November 22, 2025, describes deletion for UNIQUE or PRIMARY KEY conflicts under REPLACE. Other constraint failures have separate rules; this is not a claim that every failed constraint causes deletion.

Imagine an import that refreshes customer names using email as a unique key. Existing rows also carry a stable identifier and an operator's note. Keeping the email string does not establish that the original row or its other values survived. The following complete example is illustrative and has not been executed.

CREATE TABLE customers (
  id INTEGER PRIMARY KEY,
  email TEXT NOT NULL UNIQUE,
  name TEXT NOT NULL,
  note TEXT NOT NULL DEFAULT 'unreviewed'
);
INSERT INTO customers VALUES
  (7, 'a@example.test', 'Alice', 'verified manually');
INSERT OR REPLACE INTO customers(email, name)
VALUES ('a@example.test', 'Alicia');
SELECT id, email, name, note FROM customers;

Reasoning from the definition, the email conflict deletes the existing row. The inserted row receives the default note, and its omitted integer primary key follows insertion rules. The statement does not promise to preserve identifier 7. Do not replace that qualified claim with “the number always changes”: identifier allocation depends on the remaining table state. A coincidentally equal number would not prove that an UPDATE occurred.

Express the fields that may change

If the requirement is to preserve the customer and refresh only the name, compare this statement against a freshly restored copy of the original data:

INSERT INTO customers(email, name)
VALUES ('a@example.test', 'Alicia')
ON CONFLICT(email) DO UPDATE SET name = excluded.name;

The UPSERT documentation describes update or no-op actions selected by a uniqueness conflict. Here excluded.name is the name attempted by the incoming insert. Only name appears in the update set, making preservation of the other columns reviewable. A new email still takes the ordinary insert path and its default note.

UPSERT does not turn every error into success. If another unique customer number points to a different person, the import has an identity conflict that needs an explicit business decision. A missing non-null value or foreign-key violation is also outside the promise of this email conflict action. List the meaning of each unique key before designing automatic merging.

Does a missing delete-trigger entry prove no deletion?

No. SQLite documents special REPLACE behavior: delete triggers for these deletions run only when recursive triggers are enabled, and the update hook has an exception for the deleted rows. The reference warns that these exceptional behaviors may change. Audit code therefore needs the actual SQLite version and connection configuration; silence in its log is insufficient evidence that the original row survived.

An isolated test can compare the recursive-trigger settings, inspect an audit table, and separately inspect final data. A client-reported affected-row count does not replace those checks. No trigger experiment was run for this article.

Foreign-key relationships require another check of the real schema, connection enforcement, and deletion actions. The site's connection-level SQLite foreign-key article covers enforcement configuration. Do not assume that every child row is deleted, or disable constraints merely to make an import succeed.

Verify identity and omitted information

Restore identical initial data for each alternative. Record SQLite version, schema, triggers, and relevant PRAGMAs. Cover a new email, an existing email, a second unique-key conflict, a missing required value, and a referenced parent. Inspect identifiers, names, notes, and related rows after each operation. Then repeat a batch to test the intended idempotency contract.

The application should report creation, update, no change, and rejection separately when those distinctions matter. Also review mapping code: an ORM that turns every omitted field into null and updates them all can still erase information after UPSERT is selected. Keep failure records traceable without logging an entire private customer file.

If two unique keys may identify a customer, preflight should distinguish keys pointing to the same row, different rows, or no row. Different owners require an identity-conflict result rather than automatic merging. Also inspect duplicate identities within the incoming batch: later rows must not silently decide the accepted value unless that ordering policy is intentional. Verify each row’s ownership, not just the batch count.

Use REPLACE when deletion and recreation match the object's contract. For an import authorized to change only names, choose the narrower update action and accept it using evidence about identifiers, notes, and relationships.
