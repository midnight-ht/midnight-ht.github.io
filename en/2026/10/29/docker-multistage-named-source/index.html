A new Docker build stage can change what COPY --from=0 means

Trace a successful copy to the wrong producer, replace positional coupling with named stages, and verify the final runtime artifact set.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-29 · Estimated read 11 min
Translations
zh-CN en

Article

Key takeaways

  • Zero identifies the first FROM stage, not its previous business role.
  • Named references remove ordering coupling without proving content correctness.
  • Check the final required file set and selected target, not merely an intermediate build.

After a stage is inserted at the start of a Dockerfile, COPY --from=0 still refers to the first FROM stage. It does not remember that stage's former business role. Name cross-stage dependencies, then inspect the final image's contents. A successful build establishes that instructions completed, not that the intended release artifact was selected.

Zero denotes a position

The Docker guide to naming build stages documents zero-based numbering for unnamed stages and names assigned with AS. Named references avoid dependency changes caused solely by rearranging stages. This article uses documentation checked on October 29, 2026. No image was built; example versions are illustrative rather than claims about the latest or an approved project version.

Each FROM begins a stage. A numeric reference implicitly requires maintainers to preserve the source stage's position. Adding an audit stage can break that agreement even when a review focuses only on the new instructions.

A missing file causes an obvious build failure. A less obvious case occurs when both stages contain a file at the same path: the copy succeeds with unintended contents. Changing zero to one without tracing the intended producer merely repairs a position, not the dependency contract.

Make the source visible with distinct contents

This unexecuted example writes text markers so dependency installation and compiler behavior do not obscure the stage-selection question.

FROM alpine:3.22 AS audit
RUN mkdir -p /out && printf 'audit-only\n' > /out/result.txt

FROM alpine:3.22 AS release_build
RUN mkdir -p /out && printf 'release-content\n' > /out/result.txt

FROM alpine:3.22 AS runtime
COPY --from=0 /out/result.txt /result.txt
CMD ["cat", "/result.txt"]

Suppose the original file contained only release_build and runtime. Zero selected the release content. Inserting audit changes zero's meaning. Since audit also supplies /out/result.txt, the copy can succeed and the final file would contain audit-only. This is a deduction from the example, not captured build output.

Changing the instruction to COPY --from=release_build /out/result.txt /result.txt expresses the intended producer. Adding an unrelated earlier stage no longer changes the source merely by renumbering it. The name also gives reviewers a useful question: does this stage actually produce the approved artifact?

Renaming a stage still requires updating references. Keeping a name while redefining its contents can also change the contract. Review names, output paths and consumers together. A successful debug target does not establish what the runtime target contains.

When a name helps

Numeric references are adequate in a short disposable demonstration. Named roles are easier to maintain in a file that regularly gains testing or audit stages. Names such as stage1 offer little additional information; choose names that communicate responsibility.

A stage called test is not evidence that the runtime artifact was tested. The runtime stage might copy an earlier file while tests inspect a modified one. Trace the actual file dependency. Docker's --target option can stop at an intermediate stage, which is useful for diagnosis but does not produce or validate the final image. BuildKit processes stages required by the selected target, so the mere presence of a test stage is not an execution receipt.

How should the final runtime artifact set be verified?

A proposed isolated test compares numeric and named references, then inserts a stage that supplies different contents at the same path. Only the stage ordering changes. Deliberately break the source path afterward to confirm that an error is exposed rather than accidentally satisfied elsewhere.

Real projects can compare files extracted from the final image with an approved artifact's digest, version or reviewable manifest. A later instruction may modify files after COPY, so inspecting only the producer is insufficient. Runtime mounts can also change the visible files; see bind mounts obscuring image contents.

Record the Dockerfile revision, selected target, builder version, base-image identity and final-file evidence. These checks were not executed here, and no size reduction is claimed. A smaller image and a correct image are separate results.

Finally, COPY --from can reference an external image. A value that resembles a name is not automatically a local stage. Identify how every source resolves and whether remote acquisition or mutable tags are involved. Names remove positional coupling; final artifact inspection remains responsible for verifying the contents.

For an artifact containing a binary, templates and configuration, inspecting only the binary leaves a gap. A proposed allowlist can map each required file to its producer and final path, then check missing, extra and mismatched contents. Mixed old and new files may start successfully and fail only on a particular feature. Verify the required set rather than substituting one successful launch for consistency.
