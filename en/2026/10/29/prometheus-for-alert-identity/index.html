Prometheus for keeps restarting when each value creates a new alert identity

Trace changing value labels through pending, move display measurements into annotations, and separate rule timers from Alertmanager grouping.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-29 · Estimated read 11 min
Translations
zh-CN en

Article

Key takeaways

  • The for interval belongs to one complete alert label set.
  • Display measurements need not create new alert identities.
  • Notification grouping and incident linking do not join rule timers.

Prometheus for waits for the same alert label set to remain active. A chart that always contains a value above the threshold does not establish that continuity. If the current measurement is templated into alert labels, each changed value can create a new instance and restart pending. Check identity before shortening the delay.

A continuous curve can hide changing identities

The Prometheus alerting rules documentation defines active alerts for expression elements' label sets and requires continued activity through the for interval before firing. Rule labels can add or overwrite identity fields; annotations hold descriptive information and support templates. Documentation was checked on October 29, 2026. No server or rule test was run.

The complete label set matters, not merely alertname. A changing latency label distinguishes instances even when their alert name, service and threshold match. Charts often hide dimensions or aggregate them. Inspect the expression output, additional rule labels and actual alert instances together.

“Something is still above the threshold” differs from “the previous identity remains above it.” Lowering for without making this distinction can turn brief fluctuations into notifications while preserving the underlying identity error.

An instance replaced every minute

Assume an existing api_latency_seconds gauge separated by service. This unexecuted example uses hypothetical input rather than production measurements.

groups:
  - name: api-alerts
    interval: 1m
    rules:
      - alert: ApiLatencyHigh
        expr: api_latency_seconds > 1
        for: 5m
        labels:
          severity: warning
          observed_latency: '{{ $value }}'
        annotations:
          summary: 'High latency for {{ $labels.service }}'

Suppose three consecutive evaluations return 1.2, 1.3 and 1.4 seconds for one service. Every value breaches the threshold, but observed_latency changes the final label set every time. The first instance is absent from the next result and a new one starts. Three different one-minute lifetimes cannot be added into three minutes of continuity.

Move observed_latency into annotations and retain stable identity or routing dimensions in labels. The displayed measurement can update without creating another object. Check every remaining output label: removing one dynamic field cannot compensate for a request ID, timestamp or random value added upstream.

A changing version label can be intentional if each version genuinely needs a separate lifecycle. The cost is a new instance and fresh pending interval during rollout. Decide whether the field defines a distinct investigation object, rather than placing it in labels merely because it is convenient to display.

Stable identity can still lose continuity

A separate cause is an evaluation that does not return the element. The measurement may fall below the threshold, or missing input may remove the output. Chart interpolation and a previously visible value do not establish what the rule returned at its actual evaluation time.

Use two independent proposed tests. First, keep every value high and vary one label. Second, keep labels fixed and remove one expression result. Both failures can coexist, but separate tests make the repair explainable. See missing metrics versus zero traffic for why absent data does not establish recovery.

Keep_firing_for preserves an already firing state; it does not repair a constantly replaced pending identity. See the firing hold window for the other end of the timeline. Increasing both durations is not a general solution.

Can Alertmanager grouping join the pending periods?

Notification grouping does not merge Prometheus instance timers. Prometheus evaluates alert state; Alertmanager subsequently handles grouping, silencing and delivery. Several alerts appearing in one message do not become one complete label identity in the rule engine.

First determine whether an instance is firing in Prometheus. Then inspect transmission to Alertmanager, and finally grouping delays, silences and receivers. Repeated pending points to a rule problem. An already firing instance with no notification calls for a downstream investigation. Preserve timestamps at each layer.

Proposed validation covers stable labels with continuous high values, changing labels, a below-threshold evaluation, missing data and recovery after firing. Save rule loading separately from behavioral tests: valid YAML does not prove the expected timeline. Promtool was not executed here.

A label migration can affect routing, inhibition and dashboard filters. Review consumers before moving a field. Stable fault categories can remain labels while current measurements become annotations. Verify instance count, duration and message content, rather than treating the first arriving notification as complete success.

Observe the label migration itself. Old and new instances have different identities; do not assume pending time transfers automatically. Record when the new rule becomes active and inspect the new label set. An incident system keyed by the old fingerprint may need a deliberate record-linking policy. Joining investigation records does not join rule timers, and an expected new identity should not be misreported as another monitoring defect.
