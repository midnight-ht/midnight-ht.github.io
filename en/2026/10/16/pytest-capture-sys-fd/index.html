pytest Captured No Output: Should You Use capsys or capfd?

Choose by the write boundary and snapshot time: capsys observes Python streams, capfd observes file descriptors, and redirected subprocess pipes need their own reader.

Updated 2026-11-24 · Estimated read 16 min
Translations

Article

Key takeaways

  • The capsys/capfd boundary follows the write path, not terminal visibility.
  • readouterr() snapshots ongoing capture; it does not wait for work to finish.
  • Validate redirected subprocesses, bytes, and log handlers through their actual destinations.

Choose by the write boundary: use capsys for Python sys.stdout and sys.stderr; use capfd when a library or inherited subprocess writes directly to operating-system file descriptors 1 or 2. An empty readouterr() snapshot also requires a timing check: it does not wait for an asynchronous task or child process.

The fixtures observe different layers

The pytest stdout/stderr capture guide and fixture reference distinguish sys capture from fd capture. capsys replaces Python stream objects; capfd observes operating-system descriptors 1 and 2 and can catch direct writes to them; when a child is explicitly redirected to a separate pipe, read that pipe instead. The guide also says global capture defaults to fd level, but a test's requested fixture still defines its local observation boundary.

Imagine a wrapper that prints a Python message and calls a native library that writes a diagnostic directly to stderr. A capsys assertion may see the Python message but miss the native write. In this assumed inherited-descriptor scenario, capfd covers both paths. This is an explanatory scenario, not an executed test. For ordinary Python output, capsys is narrower and often expresses the intended contract more clearly.

Do not diagnose from terminal visibility alone. Ask whether the producer used print, sys.stderr.write, os.write(2, ...), or a logging handler. Does a subprocess inherit pytest's captured descriptors, or did launch code redirect stdout to a separate pipe or file? Network logs and file-backed handlers are not automatically covered by either fixture. If output is explicitly redirected, read the corresponding pipe and wait for the process; neither fixture crosses that redirection boundary for you.

readouterr() is a snapshot, not a waiter

readouterr() returns stdout and stderr captured so far, then capture continues. It does not wait for a coroutine, background thread, or subprocess. If a test reads immediately after starting a child and gets an empty string, the fixture may be correct: the child may not have written yet, output may still be buffered, or the task may not have finished. The right ordering follows the task API—for example, wait for communicate() or an explicit completion signal before asserting. A fixed sleep turns a scheduling race into a slower scheduling race; it does not establish completion.

Name repeated snapshots by stage. One can check initialization output; a later one can check the final result. They are distinct observation points, not a magically combined transcript. If the test requires A, B, then C, confirm that the interface guarantees this order and synchronize concurrent events deliberately. A single local run is not an ordering contract.

Text, bytes, and temporarily disabling capture

Text fixtures return strings. capsysbinary and capfdbinary return bytes. If the interface is byte-oriented, decoding with a default encoding before asserting can hide encoding or truncation defects. If the contract is human-readable text, state its encoding and error policy. A binary fixture preserves observed bytes; it does not define which bytes the application should accept.

The capture guide documents a fixture disabled() context that can temporarily let output pass through for debugging. It is an observation aid, not a fix for a failing capture assertion, and it can expose diagnostics to CI logs. Redact passwords, access tokens, and personal data before captured output enters a failure artifact. Test reports may be retained or shared, so broader capture calls for stronger log handling.

Reconstruct “missing output” as a reproducible path

Consider a command-line adapter that prints a job identifier and then calls a C extension that writes an error code. If a capsys assertion sees the identifier but not the code, that outcome points to different writing layers. If neither appears, check whether the fixture was read too early, whether the call ran, and whether the application replaced a stream. An expected string containing both values does not replace those checks: the producers and destinations differ. A test name can also state whether it proves a Python-stream contract or a lower-level diagnostic contract, so a failure points reviewers toward the relevant code.

Now consider a child process. If it inherits descriptors pytest has captured, capfd can observe its stdout and stderr. If the parent passes subprocess.PIPE, the bytes travel through CompletedProcess.stdout or communicate() instead; the capture fixture does not own that route. Another common failure is taking a snapshot immediately after starting the child. Wait for process completion or a protocol completion marker instead of changing fixtures. A counterexample is a child that never started, or exited nonzero before writing: empty capture is then the actual result, not a missed write. Assert the exit status alongside output so startup failures are not misdiagnosed as text capture defects.

Ordering has its own boundary. Python streams can buffer, while a direct os.write bypasses that layer; concurrent threads and child processes can interleave writes. Seeing both strings in capfd does not guarantee a stable order on every run. If order is part of the output protocol, synchronize the producer or emit stages explicitly and test that contract. Otherwise, assert required elements without overconstraining incidental order. Output sent to a log file or socket is not collected from “elsewhere on the system” by these fixtures; observe it through the logging interface or a file/network test double.

A small matrix for locating empty output

Consider four independent producers: Python print and sys.stderr.write; direct os.write(1, bytes); a child inheriting stdout/stderr; and a child whose output is explicitly redirected to PIPE. Test the first cases with the matching fixture. For the final case, read the pipe and wait for the child to exit; do not expect capfd to infer the redirected stream. For Python logging, inspect the handler destination; pytest’s caplog is a separate observation interface. A logger event is not synonymous with stderr output.

State the expected destination and completion condition in each test. Asserting a stable diagnostic code often says more than freezing a transcript containing a temporary path, timestamp, and thread ID. But if output format is itself public, validate it intentionally rather than deleting important assertions in the name of stability. A useful diagnosis identifies producer and destination, checks fixture coverage, establishes completion, then distinguishes a stable contract from incidental formatting. Each step suggests a reproducible counterexample; adding sleeps or switching to -s without explaining the cause only makes the test look different.

Global --capture=sys, --capture=fd, --capture=tee-sys, and -s affect session behavior. Tests requesting capsys or capfd have fixture-level observation, and the guide says a fixture takes precedence over a global option disabling capture. Do not infer from a CI command which object a specific fixture sees. This article follows the official stable docs opened on 2026-11-24; stable docs change over time, and the reader's installed pytest version is unknown.

These examples and the matrix are proposed checks, not tests executed in a specific project. For real acceptance, record Python/pytest versions, launch command, output API, subprocess redirection, the wait condition before each snapshot, and the asserted text/bytes. Check failure paths too: nonzero child exit, buffered output, timeout, early exception, redirection, and sensitive data entering reports. Then choose capsys, capfd, a binary variant, or direct pipe reading. pytest fixture isolation covers a related lifecycle boundary.
