Select Git tags deliberately when pushing a release

Select release tag scope deliberately and verify remote targets against build artifacts.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-16 · Estimated read 6 min
Translations
zh-CN en

Article

A successful branch push does not establish that the intended release tag exists remotely. Select release references explicitly and verify their remote targets. Uploading a commit object is different from creating the expected tag reference.

Include the intended references

The Git push manual says --tags pushes all references under refs/tags. By contrast, --follow-tags additionally pushes missing annotated tags pointing to commit-ish objects reachable from the references being pushed. It does not upload every local tag. Check actual Git configuration too, because it can affect defaults.

Imagine creating a local version tag, pushing only a development branch and treating success as readiness for a release tool. That tool may not find the expected tag or may resolve another version. This scenario was not executed and is not a reported incident. Inspect reference selection rather than merely checking whether a commit object exists.

Match scope to intent

Explicitly selecting one version tag can make a single-release operation easier to review. Automatic following requires understanding annotated tags, reachability and missing remote references. Do not assume it handles every lightweight tag, unrelated-branch tag or conflicting existing reference. No tags were created, pushed or rewritten for this article.

Before using broad selection, inspect local experimental and internal tags. A convenient option can publish unrelated references. Successful execution does not establish that the scope was appropriate.

Distinguish a tag name from its target content as well. A plausible version name does not prove it points to an accepted commit. Annotated tags have tag objects, so verification should state whether it compares the tag object or the resolved commit instead of confusing identifiers at different layers.

Keep remote release evidence

A release record should identify repository, tag, expected commit and actual remote resolution, linked to the build artifact. Websites, packages and images may have separate artifact identifiers. The source-to-artifact relationship explains what users received; tag existence alone does not establish build or deployment success.

Proposed checks cover a selected tag, qualifying annotated tags, nonqualifying tags and local experimental references that must remain unpublished. Define scope before execution and verify remote references and artifacts afterward. No push commands were executed here.

If an already published tag is wrong, first assess existing consumers, repository policy and how correction should be versioned. Moving a reference can make one name mean different content over time, affecting audit and reproduction. Force pushing is not a default repair.

Gitignore and tracked files examines another Git state boundary. Select references, verify destinations and retain artifact evidence before claiming that a version was delivered.
