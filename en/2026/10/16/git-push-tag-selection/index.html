Why is the release tag missing after a successful branch push?

Compare three pushes to a temporary receiver to choose release tags and verify the resulting refs.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-17 · Estimated read 16 min
Translations
zh-CN en

Article

Key takeaways

  • Branch and tag refs are selected separately.
  • Automatic following checks tag type and commit reachability.
  • Match the resolved remote commit against the release record.

Check the remote branch and release tag separately. A branch push updates the refs selected for that push. The remote can already have the release commit while a job looking it up by tag name still finds nothing. When the pipeline takes a named version as input, select that tag explicitly and check which commit the remote tag resolves to.

One commit can have two independent names

Imagine that the release candidate is at the tip of the main branch. An engineer creates an annotated tag locally and pushes main. The commit reaches the remote through the branch, but the branch ref and the tag ref have separate names. The remote commit history shows whether the branch contains the commit. It does not establish whether a downstream job can locate the same commit through the version tag. You can test both properties independently on the receiving repository.

The Git push manual describes a push as a mapping from a source to a destination ref. A branch push selects a branch ref. Enabling automatic tag following can extend that scope, so inspect the effective command and configuration while diagnosing what happened. Explicit source and destination tag names record precisely which version name the release was authorized to publish. Full ref names also avoid ambiguity when a branch and a tag share a short name.

Compare three pushes to the same receiver

The following fixture uses a temporary bare repository as the receiver. A bare repository has no checked out working tree. Only its refs matter here. The working repository creates an empty commit and places two tags on it. The annotated tag is release-a and the lightweight tag is local-marker. Each push goes to the same directory, and the next check reads that receiver’s tags. Four assertions check the branch target and tag scope. The final assertion checks which commit the annotated tag resolves to.

set -eu
tmp=$(mktemp -d)
trap 'rm -rf "$tmp"' EXIT
export GIT_CONFIG_NOSYSTEM=1 GIT_CONFIG_GLOBAL=/dev/null
git init -q --bare "$tmp/receiver.git"
git init -q -b main "$tmp/work"
cd "$tmp/work"
git -c user.name=Fixture -c user.email=fixture@example.invalid \
  -c commit.gpgsign=false commit -q --allow-empty -m base
git -c user.name=Fixture -c user.email=fixture@example.invalid \
  -c tag.gpgSign=false tag -a release-a -m 'release candidate'
git -c tag.gpgSign=false tag local-marker
git -c push.followTags=false push -q "$tmp/receiver.git" main
test "$(git ls-remote "$tmp/receiver.git" refs/heads/main | cut -f1)" \
  = "$(git rev-parse HEAD)"
test -z "$(git ls-remote --tags --refs "$tmp/receiver.git")"
git push -q --follow-tags "$tmp/receiver.git" main
actual=$(git ls-remote --tags --refs "$tmp/receiver.git" | cut -f2)
test "$actual" = refs/tags/release-a
git push -q "$tmp/receiver.git" refs/tags/local-marker:refs/tags/local-marker
actual=$(git ls-remote --tags --refs "$tmp/receiver.git" | cut -f2)
test "$(printf '%s\n' "$actual" | wc -l | tr -d ' ')" -eq 2
test "$(git ls-remote "$tmp/receiver.git" 'refs/tags/release-a^{}' | cut -f1)" \
  = "$(git rev-parse 'release-a^{commit}')"
printf '%s\n' 'All five assertions passed.'

All five assertions passed locally with Git 2.50.1 (Apple Git-155). With automatic following disabled for the first push, the receiver gets main while its tag list stays empty. Enabling following on the second push adds the annotated tag. Although the lightweight tag points to the same commit, it appears only after an explicit push, when the receiver finally lists two names. Both tags point at the tip of main in this example. It does not exercise tag protection or release triggers on a hosting service.

The manual also sets a reachability condition for automatic following. It adds annotated tags missing from the remote whose commits are reachable from the refs being pushed. Suppose a team tags an unmerged maintenance branch. Pushing main without that history cannot rely on automatic following to bring along the maintenance tag. Trying this scenario requires an extra branch. To verify that counterexample, rerun it against a fresh receiver. Confirm the main branch arrived and check for the maintenance tag separately, so a failed push cannot masquerade as an excluded tag.

Decide which version names the pipeline owns

If approval covers a particular version, make the target tag an input and check that it resolves to the already accepted commit. Limit the tag selection in the push to that name. The release owner can then compare the request with the approval. Housing both kinds of jobs in the same repository does not change the decision. The branch job can build main by default, while the job producing a downloadable package should take the approved version tag as input.

The follow-tags option can be convenient for annotated tags managed across maintenance branches. Work out which refs this push includes and which candidates sit outside their history. If one push is supposed to carry several tags, list the expected names and commits, then check whether they are all authorized for publication. The all-tags option selects all local tag refs and is appropriate when the entire collection is meant to be synchronized. It can publish experimental names too. Discovering a single missing tag does not justify expanding the scope to every local tag.

An existing name changes the response. The manual limits automatic following to eligible annotated tags that are missing remotely. When the same name points to a different commit, retain both observed targets for the release owner and stop before triggering artifact generation. The old name might already appear in download links, build caches or other repositories. Use the project’s version policy to decide how to correct it. For a version already in use, one option is a new corrected version that documents its relationship to the old one. An automatic retry should not make the decision.

Keep the remote evidence with the release record

Turn “the remote has the tag” into two assertions. Establish that the expected name exists, then compare the remote’s resolved commit with the one approved for release. Keep the target repository and time so downstream readers know where the evidence came from. After the commit matches, record the relationship between build input and artifact identity. For example, the build job can record the checked out commit and the artifact manifest can hold the resulting archive’s checksum. Someone with a copy of the archive can then tie it back to that build.

In a system test, deliberately point the tag at a different existing commit. The existence check still passes while the second assertion catches the mismatch. Also verify that a truly absent tag produces a diagnostic naming the missing version. Silently falling back to a branch build would hide the failed release precondition. See how to verify deployment and rollback artifacts for the checks that follow artifact selection.

Why does an annotated tag appear on two lines?

The Git ls-remote manual distinguishes the annotated tag object from the object reached by peeling the tag. Without the refs-only option, the output can show the tag ref itself and an additional line with the peeled marker. For an annotated tag pointing at a commit, the latter line can be compared with the approved commit ID. The first line serves a different check, such as identifying the tag object that bears a signature. If your repository permits tags pointing outside the commit graph, confirm that the target object type satisfies the release pipeline’s input contract.
