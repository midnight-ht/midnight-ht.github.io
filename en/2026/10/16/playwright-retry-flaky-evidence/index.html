Keep first-failure evidence when Playwright retries pass

A green retry does not prove the first failure was fixed. Use worker identity, trace-retention modes, and per-attempt results to decide what evidence to keep.

Key takeaways

  • A passing retry is a later attempt result; it does not erase the first failure or prove the defect was fixed.
  • Playwright replaces the worker and browser, but it does not automatically roll back external databases, messages, or shared accounts.
  • Choose trace retention for the question, and verify recording, cleanup, upload, and report display separately; the proposed setup was not executed.

Yes. When a Playwright test turns green on retry, the later attempt passed; the first failure remains a real test result. Collapsing both attempts into one “passed” outcome loses where the failure occurred, what changed during the retry, and whether the test is still unstable. A release report should distinguish a first-run pass, a pass after retry, and a failure after retries are exhausted, while keeping each outcome tied to its attempt and artifacts.

A retry is not another run in the same process

The Playwright retries guide says that after a test fails, Test Runner discards the entire worker process and its browser, then starts a new worker. If retries are enabled, that worker retries the failed test first. beforeAll runs again with the new worker. An initially failed test that passes on retry is classified as flaky in Playwright, not as an ordinary passed test.

That changes what “passed on retry” means. A new browser and worker may remove browser-process state, but they do not automatically roll back database records, messages, third-party calls, or a shared test account. Suppose an order test times out while waiting for a state change on its first attempt, then succeeds on retry. The second attempt may simply have waited long enough for a slow service. It may also have rerun setup in a new worker, or read an order created by the first attempt. The final green check alone cannot distinguish these mechanisms.

So the first failure should not be dismissed as an “environment flake,” and a passing retry should not be treated as proof that a product defect was fixed. The cause may lie in an assertion's waiting condition, shared state, concurrent resources, product behavior, test-data cleanup, or an external dependency. A retry lets the test flow continue and gives an intermittent failure another chance to appear or disappear. It does not identify the cause by itself.

Give each attempt a stable identity

An investigation needs to separate test identity from attempt identity. Test identity should include the commit, project or browser combination, file, and test name. Attempt identity should add the retry number, worker number, start time, and artifacts produced by that run. The testInfo.retry property is available in a test and its hooks; TestResult.retry is a sequential retry number in the report. TestResult also exposes fields such as workerIndex, startTime, status, and attachments. These fields do not explain root cause, but they prevent the first attempt and later runs from being blended together.

For example, a report might preserve: “same commit, Chromium project, first attempt (retry=0) timed out waiting for order.status=paid, worker 2; second attempt (retry=1) passed on new worker 5.” The exact fields depend on the configured reporter and reporting pipeline. A timeline is more useful than “intermittent failure”: maintainers can see whether the worker changed, whether both attempts used the same input, and whether setup ran under different preconditions.

Worker replacement does not mean environment isolation. If a test creates an account under a fixed email, a record left behind by the first attempt can make the second beforeAll hit a uniqueness constraint. If the test catches and ignores that error, it may even follow a different state path. Conversely, deleting a record or clearing a cache only on retry changes the conditions of the run. Cleanup can be an intentional recovery strategy, but it must be reported as part of the retry behavior. The second pass can no longer be described as a repeat under unchanged conditions.

Trace mode determines which runs you can compare

When retaining screenshots, video, or traces, choose a mode based on the question. Do not assume that enabling retries automatically saves evidence from the first failure. The Playwright TestOptions trace reference distinguishes several settings that are easy to confuse. on-first-retry records a trace only on the first retry; it usually gives you the retry's state, not a trace of the initial failure. retain-on-failure records every run but keeps only traces from failed runs; when the first attempt fails and the next passes, the first trace remains while the passing retry's trace is normally removed. retain-on-failure-and-retries records every run and retains failed runs and retry runs, which allows a failed attempt to be compared with a later pass at the cost of more artifacts.

The tradeoff is concrete. If you only need to inspect the page during a retry, on-first-retry may be enough. If you need to keep failures and minimize retained artifacts, retain-on-failure is a smaller choice. If the investigation depends on comparing an initial failure with a successful retry, consider retaining both failed and retry runs. The v1.59 release notes list retain-on-failure-and-retries as a new trace mode, and the current TestOptions API reference also documents these options. For an older installed version, use the documentation matching the dependency in your lockfile; do not paste a configuration from current docs into an older release without checking support.

The following configuration illustrates the syntax and evidence choice. It has not been executed as part of this article and may need adjustment for a particular Playwright version:

import { defineConfig } from '@playwright/test';

export default defineConfig({
  retries: process.env.CI ? 1 : 0,
  use: {
    trace: 'retain-on-failure-and-retries',
  },
});

Recording and retaining are separate stages. Some modes create traces during each attempt and remove files later according to the outcome. Even with the right test configuration, the attachment may not reach a usable report if the CI upload step only collects files still present in test-results, or if the job stops before upload. Configuration, artifact generation, cleanup, upload, and report display form one evidence chain; each needs verification.

A final status can fold different failures into one

With retries enabled, Playwright categorizes tests as passed on the first run, flaky when they pass after a retry, and failed when all retries fail. If a CI page paints every final pass green, a trend dashboard can hide instability. The opposite mistake is to count every failed attempt as a separate test case, inflating the denominator with multiple attempts from one test. A team should define its statistical unit first: for example, count the final classification once per test in a CI run, while storing every attempt separately. Retry count and failure count then remain distinct.

Also check whether aggregation preserves Playwright's flaky classification. The official reporter documentation says reports can include flaky tests that pass on retry, and the JSON reporter can write test-run results. A custom script that reads only the last result, or a mismatch between failure filtering and artifact upload, can produce a split view: the test runner knows a test was flaky while the dashboard says everything passed. This is not an argument for a universal release threshold. An authorization or payment flow has different consequences from a minor presentation check; the project should set policy according to risk.

How should you investigate a failed first run followed by a pass?

First confirm that the report contains two attempts rather than one record overwritten with the final result. Check test identity, commit, project, retry number, worker, start time, and each error. Then compare the traces: which action failed on the first run, what the page, network, and assertion observed, and whether the later attempt passed at the same logical point or followed a different path because of beforeAll, retry-only cleanup, or residual data. A trace explains browser-side timing and actions; it does not prove the state of a server database or external service. When necessary, compare controlled server logs using the same correlation or test identifier, without placing sensitive data in long-lived build artifacts.

Turn the failure into a testable hypothesis rather than closing it with the flaky label. If the failure comes from “wait a fixed duration, then read a state,” check whether the application exposes a meaningful observable condition, then decide whether a condition-based web-first assertion fits. The related Playwright assertion-waiting article discusses that choice. If the trace shows both attempts used the same business identifier, inspect data isolation and idempotent cleanup. If several tests fail together, examine shared services, worker concurrency, and resource limits. Each explanation should identify the observation that supports it and the alternatives that remain open.

Finally, run a bounded verification after the repair: repeat the test with the same project and controlled input, compare whether the failure recurs, confirm that reports still preserve attempt identity, and check that artifacts can be downloaded from the CI result. This plan has to be executed before it supports a conclusion. No Playwright test was run for this article, and no team CI was observed. If the first-run trace was not retained, the browser state of that attempt cannot be reconstructed from the retry. State the evidence gap rather than filling it with a plausible-sounding cause.

How many runs to retain depends on the investigation and artifact cost. Keeping only failed and retry attempts is usually cheaper than retaining video for every run. For a hard-to-reproduce failure on a critical path, temporarily collecting fuller traces or correlated server-side evidence may be justified. Artifacts can contain page snapshots, request data, and personal information, so check retention time, access controls, and redaction alongside the actual CI artifact settings. Too little evidence prevents comparison; keeping everything indefinitely expands privacy and storage risks.

What should a release do when a retry passes?

Treat “eventually passed” and “stable on the first run” as different facts in the release decision. A low-risk test may let the pipeline continue while still creating a flaky record, owner, and investigation deadline. Whether a critical authorization, charge, or data-integrity path blocks release should be decided by a risk policy, not implicitly by the number of retries. Exceptions should be traceable and have exit criteria. More retries change the chance of another run and the time spent in CI; they do not improve the explanation of the first failure.

If the only evidence you can see is the last attempt, do not start by increasing the retry count. First verify, in a controlled test, the trace-retention mode, the retry and worker identity for every attempt, and the artifact upload. Once those records can answer “where did the first attempt fail, and what changed in the next one?”, choose whether a flaky result should be recorded, reviewed, or block release according to business risk. Where the observation was not retained, leave the cause unknown. That is more reliable than turning a green retry into a claim that the problem was fixed.

Reader question: Does on-first-retry save the first failure? It is not a substitute for a trace of the initial run; that mode records the first retry. To keep a failed first attempt, check retain-on-failure. To compare the failure with the retry's trajectory, evaluate retain-on-failure-and-retries against artifact cost and privacy requirements.
