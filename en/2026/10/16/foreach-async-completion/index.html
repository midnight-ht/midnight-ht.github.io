Why does forEach finish before its async callbacks?

Run a local example that isolates the forEach return value, then choose sequential waits, parallel aggregation, or per-item outcomes.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-16 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • The callback promise does not determine when forEach returns.
  • Scheduling determines starts; aggregation determines what to await.
  • Confirm writes using verifiable outcomes.

Array forEach calls a callback for each element that exists, but it does not wait for promises returned by those callbacks. An await inside the callback only pauses that callback. If the outer operation needs to wait for a batch, await each item in turn or retain the individual promises and await an aggregate. The choice depends on which items may start early and what the interface needs to report to the user.

Iteration can finish while a callback is at its first await

The ECMAScript algorithm for Array.prototype.forEach checks whether the element exists, calls the callback, advances to the next index, and returns undefined on normal completion. It neither collects the callbacks’ return values nor waits for them. A direct throw from an ordinary callback interrupts iteration. A throw inside an async function body rejects the promise that function returns. If the outer operation never obtains that promise, it has lost a route for receiving the task’s failure.

Two tasks are enough to show the difference. A pending promise acts as a gate, making starts and completions separately observable. The letters are test labels. There are no network requests, and the demonstration does not depend on timer speed. The harness keeps work so it can finish the experiment; the bug in application code often leaves no such collection.

import assert from 'node:assert/strict';

let release;
const gate = new Promise(resolve => { release = resolve; });
const events = [];
const work = [];
const outer = ['A', 'B'].forEach(id => {
  work.push((async () => {
    events.push(`start:${id}`);
    await gate;
    events.push(`done:${id}`);
  })());
  return work.at(-1);
});
assert.equal(outer, undefined);
await outer;
assert.deepEqual(events, ['start:A', 'start:B']);

release();
await Promise.all(work);
assert.deepEqual(events, ['start:A', 'start:B', 'done:A', 'done:B']);

The first array assertion runs before the gate is released. Both tasks have entered their function bodies and are waiting for the same promise. The outer code has even executed await outer, but the value there is undefined. The second array assertion requires the harness to open the gate and await both saved operations. All three assertions passed locally on Node v24.21.0. The experiment verifies these controlled events and does not measure endpoint latency.

Decide whether the next item can start

Imagine a spreadsheet import that saves each row on the server. An address row needs an identifier returned by the preceding account row. Putting both into a direct map calls the address task before the account result is available. Build an explicit chain: await the account save, extract its identifier, and hand that identifier to the address save. If the account save fails and the exception propagates out of the chain, the address operation has not started. A for…of loop with await in its body can express per-item dependencies, provided the function returns the promise that actually represents the step.

If the rows update independent labels and calls may overlap, await Promise.all(rows.map(saveRow)) can await their collective success. On an ordinary array, the calls to saveRow happen in map; the aggregate receives promises that already exist. The specification for Promise.all attaches fulfillment and rejection handlers to the inputs and returns results in input order when all fulfill. That order tells you nothing about which write happened first on the server. To cap the number of simultaneous operations, dispatch new items only when there is capacity. Scheduling every operation in map has already bypassed that decision.

The approaches can coexist. An import file may contain independent accounts, each with addresses that depend on creating that account. Group the rows by account, await the required steps inside each group, and limit the number of active groups. If an account has multiple addresses, check whether those writes depend on each other before imposing or removing an order. Keep original row numbers and account membership in the interface. An address that was never attempted because its account failed needs a different message from an address that was submitted and actually returned an error.

When the batch reports an error, what is still unconfirmed?

Suppose two independent rows are already in flight: the first gets an immediate rejection from the server, and the second is still waiting. With Promise.all, the second operation need not stop when the aggregate rejects. The article on rejection and cancellation explains the distinction. The interface can report that the batch encountered an error without declaring the second row a failure and immediately resending it. If the server wrote the second row but the browser never received confirmation, resending could repeat the update. Use any available business-level lookup or deduplication mechanism to check the outcome first. Cancelling a request alone does not establish that a write was rolled back.

If the product must report a result for every row before closing the view, preserve the task outcomes and wait for all of them to settle, for example with Promise.allSettled. Each promise may fulfill or reject; the caller can inspect the individual outcomes. If one settles with “job queued,” it does not also wait for the background write. Decide which response or state actually confirms success and keep a row pending verification when that signal is missing. A view with a deadline can stop waiting and tell users where to check later. The deadline itself is not evidence of the business outcome.

Test more than a successful batch: make one row fail and keep another pending until the test releases it, then observe whether the latter can still be confirmed. Make the fake endpoint distinguish failure, success, and unknown outcomes. Assert that the interface reports status by original row number and that the retry list neither drops unattempted rows nor includes confirmed successes. Test empty input too: the product can describe it as having no work to do. The absence of failures does not mean an import occurred. Define passing conditions in terms of observable events and results, not a guessed sleep interval.

Why did the outer try/catch miss a failure?

A try/catch around forEach can catch an exception thrown directly during traversal. It does not catch a rejection from a promise returned by an async callback. To reach that catch, await the promise inside its try block. If the task handles its own rejection, have it report the outcome to the batch explicitly. A wrapper that invokes an operation without returning its promise can lose the same failure path. Work backward from the line that declares the import complete: what value was awaited, which items did it represent, and which layer dropped the promise from the save? Finding the first break in that chain explains an early success message better than adding async at each layer.
