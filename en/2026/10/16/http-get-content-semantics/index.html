Why may a GET filter body fail across a service chain?

Observe local Request construction, then check query identity, caching and compatibility-period input rules.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-19 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • Define filter locations in the public contract.
  • Verify the real entry point after construction works.
  • Specify whether repeated query keys represent one value or many.

Content in a GET request has no generally defined semantics. An origin accepting it does not establish that clients and intermediaries apply the same filters. A search endpoint used by several clients needs a public contract for where filters belong and what identifies a result. Check that the real request path can express those conditions, then choose query parameters or an operation with a defined content contract.

The client API has its own construction rules

RFC 9110’s definition of GET says content cannot alter the meaning or target of the request. It sets a condition for direct requests where the origin has previously indicated support. It also warns origins against depending on private agreements because participants may not know about the intermediaries in the chain. That does not predict that a particular proxy drops the body. Acceptance, parsing and result identity need verification on the actual implementation.

An application is also constrained by its client API. The Fetch Request constructor requires a TypeError when a GET or HEAD request has a non-null body. A direct backend script capable of sending a request does not establish that browser Fetch can send the same request. First determine whether it left the client. When construction fails, there will be no matching origin request log. Changing the server’s JSON middleware does not fix that construction path.

Observe construction before introducing a network

This fixture compares hypothetical searches for two departments. It uses a reserved invalid domain, creates request objects and makes no network calls. The first assertion preserves the failing construction. The next ones show a query-based request for an endpoint whose contract permits query parameters. Two final checks expose repeated-key parsing as a migration boundary.

import assert from 'node:assert/strict';

const base = new URL('https://example.invalid/search');
assert.throws(() => new Request(base, {
  method: 'GET',
  body: JSON.stringify({ department: 'support' })
}), TypeError);

const makeQuery = department => {
  const url = new URL(base);
  const params = url.searchParams;
  params.set('department', department);
  params.set('state', 'open');
  return url;
};
const first = new Request(makeQuery('support'));
const second = new Request(makeQuery('sales'));
assert.equal(first.body, null);
assert.notEqual(first.url, second.url);
assert.equal(new URL(first.url).searchParams.get('department'), 'support');

const repeated = new URL('?tag=a&tag=b', base);
const query = repeated.searchParams;
assert.equal(query.get('tag'), 'a');
assert.deepEqual(query.getAll('tag'), ['a', 'b']);
console.log('Six assertions passed');

All six assertions passed with the Fetch implementation in Node v24.21.0. Adding a body to GET throws during construction. The two requests without bodies have different URLs. Reading a repeated query key as one value or as all values produces different results. These observations cover that runtime and those values. They do not exercise a browser, proxy, CDN or production endpoint. Browser integration still needs checks of where an error occurs and which URL actually leaves the client.

Give caches and authorization an unambiguous query

The cache overview in RFC 9111 requires a cache key to include at least the method and target URI, and permits additional material. Imagine that the origin privately uses a department in GET content while a cache uses only method and URI. The cache could classify two different department searches under the same key. This identifies a property to check. It neither demonstrates a vendor defect nor establishes that a deployed cache actually reuses the wrong result.

An acceptance test can search through the real entry point using two departments with disjoint fixture data. Record the parsed filter reaching the server, then inspect which department owns each result. If there is a cache, use its observations of keys and hits instead of guessing from response time. Test the same search under different users too, checking that results belong to the access scope the server grants that identity. A department query parameter describes the requested filter. The server still determines which departments the user may access.

Short public filters that are suitable for sharing can fit a bookmarkable URL. For private values, complex structures or query lengths unsuitable for the actual entry point, define a search operation with an explicit content contract. Specify response shape, pagination, errors and caching. Choosing POST does not independently decide whether results are stored or whether retrying meets the application’s requirements. Those decisions belong to the endpoint contract. A team can also submit a query, receive a result-resource identifier and use a defined read operation afterward. Account for the extra resource lifecycle and expiry management before choosing that approach.

How does a compatibility period end?

Suppose the old client sends content and the new version sends query parameters. A compatibility layer can identify the client version and choose one parser. If both locations are permitted, decide whether conflicting values are rejected or one has precedence. A support query parameter paired with sales in the body could otherwise make logs and query execution disagree. Treat the conflict as input validation and report a diagnostic before executing the query. Identify the field and its conflicting locations so the rejection can be traced. Apply the application’s logging rules to decide whether sensitive values may be recorded.

Keep old, new and conflicting examples in migration tests. Send them through the real entry point and record the final query structure. Checking only that the new request returns 200 can miss traffic still using the old path. Before retiring compatibility, use known client inventory and entry-point logs to establish whether the old path is used, then have the endpoint owner decide when to remove it. This article collected no project traffic and specifies no universal retirement period. See the metadata contract for HEAD for another boundary between protocol metadata and representation data.

Does a repeated query key mean overwrite or multiple filters?

The endpoint decides. In the fixture, tag occurs twice. A single-value read returns the first value and an all-values read keeps both. A client cannot infer multi-value server filtering merely from the repeated key. Some server bindings retain one value while others produce a list. For a multi-tag feature, define whether all tags or any tag must match and verify with records that distinguish the two. For a single-value feature, rejecting repeated input can prevent clients and log tooling from silently reading different values.
