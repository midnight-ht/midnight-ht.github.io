Avoid assuming shared semantics for GET request content

Define interoperable query semantics rather than relying on private GET-body assumptions.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-16 · Estimated read 7 min
Translations
zh-CN en

Article

A GET message can carry content at the message-framing layer without giving body-based filters semantics shared across the HTTP chain. An origin server accepting such input is insufficient justification for a public interface. Choose an expression that clients, intermediaries and the origin can consistently understand.

Transmission is not shared meaning

The GET definition in RFC 9110, section 9.3.1, says GET content has no generally defined semantics and cannot alter the request's meaning or target. Some implementations may reject it and close the connection because of request-smuggling concerns. The standard constrains when clients should generate content and warns origins against relying on private agreements when intermediaries may be unknown. This does not mean every GET body is syntactically forbidden; local support is not a general interoperability contract.

Imagine filters for department, access scope and dates working against a development origin but behaving differently through a gateway. This is an untested design scenario. Direct success establishes only that particular path's behavior, not what proxies, caches, monitoring or other clients understand.

Express query identity clearly

Query parameters may suit filters whose exposure, size and sensitivity permit them. Complex search can instead have an explicitly defined operation, including caching, retry and authorization behavior. There is no universal choice independent of interface constraints.

Moving inputs into a URL is not permission to expose secrets. Addresses may appear in browsing history, access logs and other observation systems. Changing the method does not independently provide confidentiality or authorization either. The server must derive permitted scope from actual identity rather than trusting a submitted department identifier.

Document which inputs determine query identity and how defaults affect results. If different filters appear as the same target to an intermediary, investigate whether it has enough information to distinguish responses. One test without a cache hit cannot establish that all future paths are unambiguous.

Verify the real migration path

Inventory clients, gateways and callers before changing an existing interface. During compatibility periods, old clients may send content while new clients use parameters. If both are accepted, define conflict precedence and an exit condition instead of silently merging them into another meaning.

Proposed checks cover actual entry points, differing filters on the same target, empty criteria and unauthorized scopes, with evidence of the request identity each layer sees. They were not executed here, and this article does not claim a particular vendor always discards GET content.

The design question is whether all participants can interpret the same request through a public contract. HEAD metadata contracts examines a related representation boundary. Establish shared semantics before settling on a transport convenience.
