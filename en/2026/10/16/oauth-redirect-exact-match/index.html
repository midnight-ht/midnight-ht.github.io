Why must OAuth callbacks match exactly, even on the same domain?

A shared hostname does not prove a shared receiver. RFC 9700 requires exact OAuth redirect matching, with a narrow native-app loopback-port exception.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-24 · Estimated read 19 min
Translations

Article

Key takeaways

  • The authorization server should compare redirect_uri with the client's registered value exactly; matching a host or path prefix is not a substitute.
  • RFC 9700 preserves a narrow variable-port case for native-app loopback redirects and a conditional trust path for integrity-protected requests.
  • Exact callback matching still needs open-redirect defenses, token-endpoint value consistency, and applicable code protections.

An OAuth callback is not safe merely because it shares a domain with the client. OAuth 2.0 Security Best Current Practice requires an authorization server to compare a requested redirect URI with the client’s registered value using exact string matching (RFC 9700). A variable port for a native application's local loopback redirect is a narrow exception. If the server accepts only a matching host or path prefix, another route on the same site may become a second receiver—or forward the response elsewhere.

A host is not a callback endpoint

Treating redirect_uri as “the application's domain” collapses the security check at the wrong level. A URI has a scheme, host, port, path and possibly a query, and an application can route each combination differently. To an authorization server, https://login.example.test/oauth/callback and https://login.example.test/redirect?next=... share an origin but are not the same receiver. If the second route reads next and returns an external Location, it is also an open redirector.

Published in January 2025, RFC 9700, Best Current Practice for OAuth 2.0 Security, makes the rule explicit: under §2.1, client redirect URIs are compared exactly with pre-registered values. Its §4.1.3 discusses this as a countermeasure to redirect URI validation attacks and says servers hosting redirect URIs must not expose open redirectors that forward browsers to arbitrary destinations. RFC 9700 That comparison is against the registration for that client, not a domain that merely looks like the client’s brand and not the page a user hopes to visit after signing in.

How a wildcard can defeat a same-domain check

The RFC 9700 redirect-validation example describes a concrete leakage path involving a loose pattern and an open redirector. Suppose a client is registered with a pattern such as https://client.somesite.example/cb?*, and its /cb handler accepts a redirect_to parameter and issues an HTTP 303 redirect. An attacker constructs a request that first matches the registered host and path, then points redirect_to at a page they control. The authorization server accepts the pattern and returns the authorization response. The site's redirect handler then sends the browser to the external address. If the response carries an access token in the URL fragment and the next Location does not include its own fragment, the browser may carry the original fragment forward, allowing the attacker's page to read it.

This is not a claim that every same-domain callback is dangerous, nor an attack executed during this rewrite. That standard describes a specific configuration: a permissive registration, a callback path that can redirect again, and a response mode that places a token in a browser URL combine to create the leakage route. It shows why a shared host is not proof of a safe receiver and why exact matching does not remove the need to inspect the behavior of the registered endpoint itself. Even an exactly registered /redirect is a poor OAuth callback if it accepts arbitrary destinations.

The rule's place beside RFC 6749

RFC 6749, published in 2012, already required an absolute redirection URI and prohibited fragments. When a complete URI was registered, the authorization server was to compare it using the simple string comparison defined by RFC 3986. It also allowed a less specific registration of scheme, authority and path—with a variable query—if complete URI registration was not possible. RFC 6749, Section 3.1.2 provides that earlier compatibility context.

The BCP also updates and extends earlier OAuth security advice. It describes pattern matching as more complex and error-prone to implement and manage, and requires exact matching. RFC 3986 §6.2.1 defines simple string comparison as character-by-character comparison. It is not an invitation for each service to invent a permissive regular expression for URIs that “look equivalent.” Registration and authorization requests should use a consistent, reviewable serialized value. Do not omit a default port in one environment and append it in another, then rely on undocumented normalization. If multiple callbacks are genuinely required, registering each complete URI separately is easier to review than widening permission to a host wildcard or path prefix.

The callback value also needs to remain consistent beyond the authorization endpoint. Under RFC 6749 §4.1.3, the token request must include the same redirect_uri when it was present in the initial authorization request, and the server must verify that the values are identical. RFC 6749, Section 4.1.3 The server therefore needs to bind the redirect URI used in the authorization transaction to the authorization code or its transaction state. It should not accept another same-domain URI during code exchange.

The port exception is for a native app's local listener

A desktop native app may open a temporary local port to receive a callback. RFC 8252 §7.3 describes loopback interface redirects using 127.0.0.1 or [::1], with a port assigned at runtime; the authorization server must allow the appropriate port for these loopback IP URI requests. RFC 8252, Section 7.3 RFC 9700 phrases the exception as a native app using a localhost URI and refers back to RFC 8252. It does not mean a web client may use any port, or that the host, path or scheme can change freely.

That distinction affects registration design. A web client can register separate exact callbacks for production and testing. A desktop native client can implement a temporary listener using its loopback form and handle port variation only within the protocol's stated scope. RFC 8252 also says the client should listen only on the loopback interface and close the port after receiving the response. It notes that another application may still attempt interception on some operating systems, so the port exception does not replace authorization-code protections. Applying the native-app exception to a browser website is a client-type mismatch.

How to test the rejection path

Register one complete callback for a test client, such as https://login.example.test/oauth/callback, then define inputs and expected results at the authorization endpoint. The exact registered value should continue to work. A different same-host path, /oauth/callback/extra, a lookalike prefix, /oauth/callback-evil, another scheme, an unregistered port, or a route that acts as an open redirector should be rejected according to policy. If the product genuinely needs several callbacks, register each full URI as its own entry instead of replacing the allowlist with startsWith() or *.example.test.

Pseudocode can express that choice, but the following was not connected to a real authorization server and is not a production SDK:

registered = registrations[client_id]
if request.redirect_uri is not an exact registered value:
    reject authorization request
else:
    continue the authorization flow

Acceptance should go beyond observing an error page. Confirm that rejection does not redirect the browser to a URI supplied by the request; verify the same redirect_uri again at code exchange; and inspect whether the callback endpoint itself permits arbitrary next destinations. Also preserve the qualification in RFC 9700: when the authorization server can verify the origin and integrity of the authorization request—for example, through a request object or PAR with client authentication—it may trust the URI without further checks under that section's conditions. This is not a blanket exemption for unauthenticated client requests.

Record the client ID, registration configuration version, authorization request, rejection reason and whether an external redirect occurred. Do not put authorization codes, access tokens or sensitive query strings into logs. One rejected request proves only that the input was rejected in that environment; it does not establish that other identity providers, client types or configuration branches behave the same way. No authorization requests were executed for this article.

Can returnTo replace redirect_uri?

No. redirect_uri is the protocol receiver for the OAuth authorization response; an application's returnTo usually selects where the browser goes after sign-in. They belong to different navigation steps and need separate validation. Adding user-controlled returnTo to a callback does not make it a registered OAuth URI. Registering the protocol callback exactly does not secure the application's later navigation. See Trust decisions for return destinations for that adjacent boundary.

Exact matching limits the registered endpoints to which an authorization server may send a response. Open redirects, code protections, client type and in-app navigation each retain their own verification responsibility. If a callback must vary, first establish that the protocol requires it; then choose multiple explicit registrations, the native-app loopback-port rule, or the integrity-protected request condition RFC 9700 actually describes—not a hostname treated as a wildcard grant.
