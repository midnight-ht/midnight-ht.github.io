Why can a Fetch body reject a read while bodyUsed is false?

Compare locked, disturbed and cloned local responses, then assign ownership for parsing and diagnostics.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-15 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • An unused response body can be locked.
  • Release an unused reader to restore access.
  • Decide whether to clone before consuming.

A reader can lock a Fetch body before reading any bytes. At that point bodyUsed can be false while json still rejects the read. Trace which code holds a reader and check whether reading or cancellation has already started before handing the response to a parser.

Imagine a request wrapper that displays download progress and also passes the response to a shared parser. A diagnostics module acquires a reader, planning to wait for the interface to subscribe before reading. The business layer receives a successful status, sees bodyUsed is false, and starts parsing. Neither module has taken any content yet, but the business operation can already fail. Find which code acquired the right to read. Looking only for another read beside the parser can miss an earlier lock.

Follow the two states

The Fetch Standard’s Body definition treats a non-null body as unusable when its stream is locked or disturbed. The bodyUsed property reflects disturbance. It does not treat a lock taken before a read as prior use. The stream’s locked property gives another clue during diagnosis. The code that hands out the body still has to manage readers and their lifetime.

The Streams Standard’s locking section says a readable stream has only one active reader at a time. Acquiring a reader locks it. Releasing an unused reader lets later code acquire access to the same stream. Releasing the lock after reading does not restore bytes already taken. Other operations may happen between checking both properties and calling the parser. Give one module responsibility for reading and pass the necessary results to the other.

Observe three paths with local responses

The following program creates Node Response objects locally. It makes no network requests. The first rejection can recover by releasing the reader. The second has already consumed input. Take a lock without reading, check that bodyUsed is false and expect business parsing to reject with a type error. After releasing that reader, parse the same response and expect a count of two. Read once before releasing the reader on a different response. Although the lock clears, a second parse should still fail. Finally, clone before consuming so each branch can read once, then verify that a clone attempt after consumption throws.

import assert from 'node:assert/strict';

const payload = '{"count":2}';
const fresh = () => new Response(payload);
const parse = response => response.json();
const stream = response => response.body;
const locked = fresh();
const reader = stream(locked).getReader();
assert.equal(locked.bodyUsed, false);
assert.equal(stream(locked).locked, true);
await assert.rejects(parse(locked), TypeError);
reader.releaseLock();
assert.deepEqual(await parse(locked), {count: 2});

const disturbed = fresh();
const consumer = stream(disturbed).getReader();
await consumer.read();
consumer.releaseLock();
assert.equal(stream(disturbed).locked, false);
assert.equal(disturbed.bodyUsed, true);
await assert.rejects(parse(disturbed), TypeError);

const original = fresh();
const copy = original.clone();
assert.equal(await copy.text(), payload);
assert.deepEqual(await parse(original), {count: 2});
assert.throws(() => original.clone(), TypeError);
console.log('locked, disturbed and clone assertions passed');

All assertions passed locally on Node v24.21.0. The first failure uses the same valid JSON as the other paths. No middleware processed the freshly constructed response. The separate fixtures remove a server-side difference from the comparison. The second path asserts both that the lock cleared and that bodyUsed is set, so a remaining lock cannot explain the failure. The fixture did not test browsers or cancellation of a network stream.

For a request-wrapper test, give business output, diagnostic collection and parse errors separate assertions. Start with a fixed result of two. Enable diagnostics and require the same business result, then verify that diagnostics has only the task identifier and approved summary. Use malformed JSON to exercise a format error. Give diagnostics an unused reader to exercise lock contention and record both the stage and reader owner. Neither negative gives a business value, but each has a different repair. The format and wrapper checks are proposals and were not executed here.

In the wrapper, observe three points for the same request: delivery to diagnostics, release of its reader, and the start of business parsing. If diagnostics exits after acquiring a lock, the release observation is missing. If it has read the body and releases normally, release is recorded but parsing begins with a used body. These failure paths tell you who acquired access and who took the content. Make the duty visible in function arguments: give the progress module a dedicated reader object or pass it progress events. Exercise those cases on separate responses and compare the business value with and without a progress subscriber. This wrapper test is a design and has not been run.

Give diagnostics the result it needs

When business code needs structured fields, the request boundary can parse once and send diagnostics a filtered summary. Define what each consumer receives and how failures are reported. Downstream readers can rely on the business object and a diagnostic identifier tied to the request. Finding the body owner does not require keeping credentials, full user objects or the entire import record. If a separate consumer needs to store download contents, decide who owns each branch, how long data lasts and how cancellation works before choosing to clone.

Recovery also depends on the operation. Consuming a local response again cannot replay the network exchange. Automatically resending the request may start a separate business operation. A closed progress callback may also leave a reader holding a lock. Manage release and cancellation under the reader owner’s contract. Observe request success, body parsing and business validation separately to decide whether to restore access to the stream, retry the request or report invalid data. When the operation permits an empty body, handle that protocol state before consumption. The contract for an empty HTTP 204 response

Can the diagnostic branch wait while the business branch reads?

The branches have separate consumption interfaces. A slow branch can still incur a resource cost. When the underlying data is distributed across both branches and one lags behind, unread chunks may queue in the slower one. The short local response only confirms that both consumers receive the expected values. With a large download, measure what happens when one branch pauses, resumes or cancels. Then decide whether diagnostics can use metadata alone or needs another read path with a resource budget. This example did not measure buffer size, network backpressure or process memory. The queueing behavior follows the Streams Standard’s teeing and backpressure rules.
