Verify logging configuration on existing Docker containers

Verify per-container logging settings and plan recreation with data and recovery evidence.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-16 · Estimated read 6 min
Translations
zh-CN en

Article

Changing a Docker daemon’s default logging configuration does not update existing containers. Inspect the driver and options actually assigned when each container was created, then plan any required recreation. An updated default is not evidence that running instances changed their log destination or rotation policy.

Defaults affect new containers

The Docker Engine logging guide states that default driver or option changes affect newly created containers. Existing containers retain their original settings and must be recreated to use new ones. It also requires log-option values in daemon.json to be strings. Operational steps remain environment-specific; one platform’s restart procedure is not a universal runbook.

Imagine changing a daemon configuration to limit log growth and assuming every service is updated because the default looks right. Older containers can still retain previous settings. This scenario was not executed and is not a diagnosis of a particular machine. Configuration files, defaults and actual instance settings are different evidence.

Trace the complete logging path

Associate container identity, service version, creation time, actual driver, options and downstream destinations. A correct driver name does not establish collector receipt, query availability or retention. Validate the path used during real diagnosis.

Explicit service configuration may override the daemon default. Preserve precedence and ownership so that a later recreation does not silently restore another setting. A review should explain why each instance has its configuration, rather than merely attach a desired template.

Content matters too: confirm that applications write to the collected destination, sensitive data is handled appropriately and events identify the instance. Reduced volume should not remove necessary diagnostics, while diagnosis does not justify unlimited request-body retention.

Recreation needs a release plan

A requirement to recreate containers is not permission to delete them immediately. Confirm persistent data, dependencies, startup settings and recovery, including preservation or handoff of old logs. This article executed no deletion, restart or recreation and claims no interruption-free transition.

Proposed validation creates a new instance in an appropriate environment, checks actual settings and follows a recognizable nonsensitive event through collection and query. Production replacement also needs traffic and business-state checks. A searchable event verifies one logging path, not application health or task completion.

Separate configuration failure, missing event production, forwarding interruption and incorrect queries. Otherwise teams can repeatedly edit defaults without reaching the actual obstacle. Record the changed instances and settings, not just a command invocation.

Docker exit and restart boundaries discusses a related operational concern. Deliver the configuration to running instances, then verify the real log path.
