Why does an existing Docker container keep its old logging driver?

Check the daemon default, actual container settings and a distinct diagnostic event to verify a logging migration.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-14 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • Existing containers keep the logging configuration assigned at creation.
  • Check identity and effective settings after replacement.
  • Use a distinct event to verify collection and query.

Changing the Docker daemon default leaves the logging configuration of existing containers in place. Restarting the same container also leaves its chosen driver in place. Check the actual instance’s driver and options, then verify that an event it writes reaches the query interface operators use.

Imagine an import service with two replicas. An operator changes the default to local on a test host to limit the growth of locally stored container logs. The daemon reports the expected default after the change, but the old replicas still use the original driver. Replacing one replica leaves both configurations in service. A checklist filled from the host default misses the unchanged replica. Checking only an old replica can also lead to a false diagnosis that the default did not take effect.

Use container identity to locate the decision

The Docker Engine logging configuration guide says that a default driver or option change affects containers created after the daemon applies it. Existing containers retain the options from creation. An explicit driver on the creation request can also determine the result. Put the host default, creation declaration and effective container configuration in separate columns to see which decided the outcome. Docker also requires option values in the daemon configuration to be strings. Apply the change using the procedure for that host. An application container restart alone does not prove the daemon loaded its configuration.

For example, a deployment declaration that explicitly selects the old driver can keep using it even when it creates a replacement. A new replica with no override can use the new default. Both can have fresh container identifiers, so replacement is an intermediate result. Read the effective logging configuration and verify that the intended declaration reached the creation step. When separate people maintain the deployment file and the command line, record which one supplied the explicit setting. A temporary command can pass while the next regular deployment restores an earlier setting.

Keep three observations from an isolated host

Use a test environment without service traffic. This is a verification design. No daemon restart, container creation or traffic migration was executed for the article. Start with json-file as the default and create a test instance A without an explicit driver. Record its complete identifier and logging configuration. Then change the default to local and have the daemon apply it through the operating procedure for that environment. Use read-only commands to compare the host default and container configuration. Substitute your actual test name in the example.

docker info --format '{{.LoggingDriver}}'
docker inspect --format '{{.Id}} {{.HostConfig.LogConfig.Type}} {{json .HostConfig.LogConfig.Config}}' demo-log-a

The host should report local while A still reports json-file. Restart A in the test environment and inspect its identifier and driver again. Both should match the values from before the restart. Create B from the same image without an override. Expect a different identifier and the local driver. Create C separately with an explicit json-file driver. It should keep that driver despite being newer than A. C checks whether you can detect an explicit override. It does not recommend a driver for production.

For each row, save the identifier, expected driver, observed driver and relevant options for each row. If the host default has not changed, check the daemon connection and whether the host applied the update. If the default changed and a new container still differs, inspect the creation declaration and actual arguments. Use the same identifier for the restart control. An orchestrator may have replaced a replica during the operation, which would give you a different object to inspect.

Validate logging and traffic separately

After checking the new driver, have the test application write a synthetic marker to standard output or standard error. Look for it at the container’s readable entry point, the collector and the query interface used for diagnosis. Assign distinct markers to the old and new instances. Otherwise an event from the old replica can appear to verify the new one. If the marker is readable at the container but missing at the collector, check the collection methods the collector supports. If it has arrived and a query still returns nothing, inspect the time range, instance labels and index conditions. A query hit verifies the path of that event.

Suppose the change is L17 and the replacement writes event B9. Accept a result only if it can be linked to the change, instance B and event B9 in the time window after cutover. A service-name query can otherwise find a delayed event from an old replica. Verify that the same query can distinguish the old event, then generate B9 and trace its arrival at each point. If the collector is buffering, record that the container wrote the event and that the collector has not observed it yet. Those observations show where to wait or investigate and which step to repeat after recovery.

Before replacing a production replica, identify the mounts, startup arguments, dependencies and recovery steps that need to survive. Begin with a replica whose traffic can be isolated. Compare the configuration, diagnostic event and business probe against their respective expectations before expanding the change. If the new instance is healthy but its logs cannot be queried, pause expansion and use the release plan to decide whether to restore the original settings. Confirm the container identity and data state for recovery too. Preserve any old diagnostic material needed for an investigation according to its retention rules. Container exit and restart boundaries addresses a related distinction between a process failure and another startup.

What if the driver stays the same and only the rotation options change?

Applying new creation options to an old instance still requires recreating it with the intended settings. Compare two isolated instances that both use local, one with the old file limit and one with the new limit explicitly configured. Inspect the effective options and observe rotation with nonsensitive test output. The local logging driver options describe file size, file count and compression. Record the settings separately from any observation of rotation. This follow-up was also unexecuted.
