Why does npm test still run with ignore-scripts enabled?

A local npm CLI 11.9.0 fixture shows that ignore-scripts skips install scripts and pre/post hooks, while an explicit npm test still runs its target.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-24 · Estimated read 17 min
Translations
zh-CN en

Article

Key takeaways

  • ignore-scripts controls automatic lifecycle triggers; it is not a code sandbox.
  • An explicit npm test still runs test while its pre/post hooks are omitted.
  • Use a clean fixture to inspect dependency presence, side effects, and the command target separately.

ignore-scripts does not mean “this project cannot execute code.” The npm CLI 11 documentation defines it as a way to skip scripts in package.json, but it also preserves the target of an explicit command: npm test still runs test, and npm run build still runs build. With the option enabled, the matching pretest, posttest, prebuild, and postbuild scripts do not run alongside those targets. The setting controls a class of automatic triggers; it is neither a sandbox nor an authorization check for later commands.

I reproduced that boundary in a temporary directory with the locally installed npm 11.9.0. With --ignore-scripts, installing a local file dependency still placed it in node_modules, while its install and postinstall marker files were absent. Running npm test with the same option then created the test marker, but not pretest or posttest. This demonstrates only the behavior of that npm version in this small, network-free fixture. It is not a dependency security audit, and it does not show that a project or CI environment is isolated.

Which part does the setting control?

The npm CLI v11 configuration reference lists false as the default value of ignore-scripts. When set to true, npm does not run scripts in package.json. The same entry names an exception: commands explicitly intended to run a particular script, including npm start, npm stop, npm restart, npm test, and npm run, still run their target, but omit associated pre- and post-scripts. Read this as CLI v11 behavior; it should not be assumed to describe every historical npm release or another package manager.

The distinction is easy to miss because “turn off scripts during installation” sounds close to “the pipeline will not execute repository code.” They are not equivalent. After automatic dependency lifecycle scripts have been suppressed during installation, the next pipeline command can still explicitly run the project’s tests or build script. If that command loads repository files, dependency modules, or build plugins, their code runs with the current user and container permissions. The option does not inspect the target script or revoke credentials already present in the environment.

Which hooks disappear with the target?

npm’s scripts documentation spells out the ordinary command hooks. Under normal behavior, npm test runs pretest, test, and posttest in that order. User-defined commands have corresponding pre<name> and post<name> hooks. With ignore-scripts enabled, the exception for explicit npm test preserves the test target but not those surrounding hooks.

Imagine a team that puts test-data preparation in pretest and cleanup in posttest, then adds npm --ignore-scripts test to CI. The test body runs, but setup and cleanup no longer happen as expected. If the test happens to consume files left by an earlier build, it may still pass. That is a hypothetical failure path, not an outcome guaranteed by npm’s documentation; it is a reason to verify in a clean directory. Conversely, if a security scan exists only in pretest, explicitly running npm test does not substitute for that scan. The important question is not simply whether to use the setting, but which event actually owns each check and preparation step.

Package installation can create a similar false inference. npm install --ignore-scripts can install a package while skipping its automatic scripts. A package may rely on an install script to compile a native binding, download a platform artifact, or generate a runtime file. Its directory being present does not prove those operations took place, or that the program remains usable without them. A successful npm exit status answers whether the install process ended successfully; it does not certify every package’s later runtime requirements.

Verify the boundary with a clean fixture

The following experiment uses no external registry. Give a temporary root project three scripts, then give it a local file dependency with install and postinstall scripts:

npm install --ignore-scripts --offline --no-audit --no-fund
npm --ignore-scripts test

In the fixture I ran, the first command exited with code 0 and the dependency directory existed, but neither dependency-script marker appeared. The second command also exited with code 0; only the test marker was written, with no pretest or posttest marker. The root project’s scripts used echo to write markers, and the dependency came from a local file: path. No third-party package was downloaded. This separates installation behavior from deliberate script execution. It does not prove that malicious code cannot run through another entry point, and it does not cover every combination of workspaces, Git dependencies, npm versions, or platforms.

Start by removing previous output and old dependencies, then check three distinct things: whether the target dependency exists, whether automatic lifecycle side effects occurred, and whether the explicit target plus its surrounding hooks ran. Looking only at the command’s exit status or only at node_modules can lead to opposite mistakes: concluding that all scripts were disabled, or concluding that dependency preparation finished. Record the npm version, exact commands, and each marker so the documented rule becomes reproducible engineering evidence.

Separate installation policy from execution policy

If the goal is to reduce automatic dependency-script execution during installation, ignore-scripts can be one bounded control. If the goal is to keep untrusted code away from a publishing token, the setting alone is insufficient. Explicit tests, builds, packagers, code generators, and the plugins they load still need their own review. A more cautious pipeline design separates dependency installation from validation and publishing jobs: the install job receives no publishing credential; jobs that must execute repository scripts use minimum permissions, short-lived credentials, and controlled network access; generated artifacts come from a clean workspace and remain inspectable. These are design recommendations to compare against the actual threat model, not a production CI setup tested here.

An audit record should say more than “ignore-scripts is enabled.” At minimum, list the npm version and configuration source, installation command, explicitly executed script names, which pre/post hooks actually run, artifact differences caused by skipped scripts, and whether a failed build can leave stale files behind. When configuration can come from the command line, environment, or project settings, record the effective value together with the command. A developer’s .npmrc alone does not establish behavior in the release environment.

“Remove the setting and the build passes” is not a complete verification either. The change may have regenerated a missing artifact, or it may have re-enabled dependency scripts that have not been reviewed. First identify which input is absent and which lifecycle step creates it. Then test an approved replacement in an isolated fixture and verify that build output came from the current revision. If a script looks suspicious, inspect logs, files, and credential exposure for the actual execution window. Changing the configuration later cannot undo an action that already happened.

Where does this conclusion stop?

The code and logs here record a temporary local fixture run with npm 11.9.0. The official sources describe CLI v11 configuration and script conventions. Whether a particular project lacks generated files, exposes secrets, or requires a given hook still depends on its package.json, dependency contents, and task environment. Other package managers have their own configuration and lifecycle models; do not infer their behavior from the same option name.

For a related question about whether installation inputs are fixed, see npm ci and installation inputs. Lockfiles, reproducible installation, lifecycle suppression, review of explicit code execution, and artifact validation answer different questions. Recording each action, permission, and artifact is what lets a team tell which automatic path the setting reduced—and which execution path it still owns.
