Why does Map miss a new object with the same fields?

Ten locally checked outcomes separate object identity, business IDs and undefined membership, with scoped refresh and invalidation rules.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-22 · Estimated read 17 min
Translations
zh-CN en

Article

Key takeaways

  • Reconstruction does not retain object identity.
  • Scope business keys by tenant and identifier type.
  • Use has to distinguish absence from stored undefined.

Map recognizes an object key by identity; recreating its fields does not recreate the stored key. Start a lookup investigation by checking membership with the original reference, then decide whether the mapping represents a particular page instance or a business record across refreshes. These are different identity requirements, and changing one get call does not finish the cache design.

Equal fields do not recreate a stored key

MDN’s explanation of Map key equality describes object-key equality in terms of object identity. Two values may both mean user seven to the application while being different objects to the language. A new response, an object spread, or a list mapping can create a new instance. Matching fields do not make separate construction steps share a reference.

The following fictional page-selection example stores a choice against the first object, copies that object, and changes the original name. The code records ten outcomes and compares them with one expected record. The first three show that the original reference is present, the copy is absent, and mutating the original’s fields leaves its entry accessible. The scoped and membership results are explained below. There is no server call or frontend framework in this fixture.

const assert = require('node:assert/strict');
const original = { tenant: 'north', id: '7', name: 'Lin' };
const copied = Object.assign({}, original);
const byObject = new Map([[original, 'selected']]);
const originalPresent = byObject.has(original);
original.name = 'Chen';
const byTenant = new Map([
  ['north', new Map([['7', 'selected']])],
  ['south', new Map([['7', 'idle']])],
]);
const { tenant, id } = copied;
const pending = new Map([[original, undefined]]);
const observations = {
  originalPresent,
  copiedInstance: byObject.has(copied),
  renamedInstance: byObject.get(original),
  refreshedRecord: byTenant.get(tenant).get(id),
  otherTenant: byTenant.get('south').get('7'),
  numericId: byTenant.get('north').has(7),
  registeredValue: pending.get(original),
  registeredPresent: pending.has(original),
  absentValue: pending.get(copied),
  absentPresent: pending.has(copied),
};
assert.deepEqual(observations, {
  originalPresent: true, copiedInstance: false, renamedInstance: 'selected',
  refreshedRecord: 'selected', otherTenant: 'idle', numericId: false,
  registeredValue: undefined, registeredPresent: true,
  absentValue: undefined, absentPresent: false,
});

The successful lookup after renaming separates two failure types. An entry can remain present while its calculated value becomes outdated. If the stored value were a display label derived from the name, changing the key object would not recalculate that label. Updating values and diagnosing missing entries require separate rules.

Object keys may also be the right choice. An editor might need independent transient selections for two separately opened nodes that refer to the same database identifier. Replacing both keys with that identifier would merge state that the panels need to keep separate. Define which instances should share state and which should remain isolated before selecting a key. The collection cannot supply that product rule.

Across refreshes, define the identifier’s scope

Preserving a selection after a list refresh requires an identity that survives instance reconstruction. The next design uses nested tenant and user-ID maps rather than serializing an arbitrary object. Assume the interface contract defines both tenant and ID as strings. North and south each have a user seven, and their selections must remain separate.

The copy still carries the same tenant and string identifier, so it retrieves the north selection. The same local identifier in south retrieves different state. The false numericId outcome shows that numeric seven is different from string seven. If a server changes identifier types, old state may become inaccessible. That is an inconsistent interface boundary, rather than Map randomly converting query keys.

The two levels make the scope explicit; they are not a universal storage recommendation. A globally unique identifier might make the outer map unnecessary. State intended for one session also needs a session-specific storage lifetime or cleanup rule. This fixture calls the inner get directly because both tenants already exist. With unknown tenant input, decide whether to return absence or create a container as appropriate. An exception from this example must not become an authorization decision.

Serializing an entire object is no general identity substitute. A mutable display name should affect identity only if the business contract says so, regardless of property-writing order. Objects that represent the same record but expose different field subsets can also encode differently. Choosing identity fields belongs in an explicit, testable protocol. A serializer cannot discover their business meaning.

Fixing the lookup leaves refresh and invalidation decisions

Consider a list update that reconstructs every object after an old object was selected. Looking up a new reference in the old reference-keyed map fails consistently with its rules. A scoped business key can preserve the selection across reconstruction. But should state disappear when the user leaves the tenant? Should a deleted record’s selection transfer to a newly created record if its identifier is reused? Map does not decide these policies. For example, a rule against inheriting a deleted record’s selection could clear entries on deletion. If deletion and recreation events can be missed, consider including a record generation supplied by the data contract in its key, or rebuilding the state after a refresh. An arbitrary current timestamp cannot replace that generation. This is design advice; the fixture implements no event receiver.

Turn these transitions into inputs with expected outcomes: changing only the display name preserves selection; changing tenant isolates it; deleting a record removes its entries; entering another session initializes state according to product rules. A permissions computation needs its own policy-version and revalidation decisions. A business-key hit establishes only that a saved value was found, not that authorization remains valid.

Diagnostic logs should include the identity information needed to explain a transition—tenant, identifier type, construction stage, and session identifier—rather than dump a complete user object. Reproduce the step that creates a new instance before judging the repaired code against the intended identity. One successful lookup does not verify tenant isolation or deletion behavior. See structured cloning and ownership transfer for related object-copy boundaries.

Does undefined from get mean the object key is absent?

No. undefined is itself a valid stored Map value. The ECMAScript get algorithm returns undefined when it finds no key, while the has algorithm reports membership. In the final four observations above, registeredValue and absentValue are both undefined, but registeredPresent is true and absentPresent is false: equal lookup values with different membership results.

If a business model uses undefined for “requested but no result written yet,” checking get alone could treat a registered operation as completely absent and start work again. Express membership separately from result availability. An explicit state object can also make the distinction easier to explain. That is a state-model choice; this fixture makes no network requests and establishes no request deduplication or concurrency control.

The single assertion compares ten outcomes, all passed locally on Node.js v24.21.0. They verify language behavior on fictional data, not framework update policies, real permission caches, or memory consumption. During integration, encode the lifecycle expectations above in project tests and verify whether the mapping should retain one instance, one record, or freshly initialized state.
