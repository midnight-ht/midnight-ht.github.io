Handle successful HTTP 204 responses without parsing a body

Handle no-content success explicitly and keep parsing failures separate from operation outcomes.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-16 · Estimated read 6 min
Translations

Article

HTTP 204 means the server successfully fulfilled the request and has no response content to send. Clients should follow an explicit no-body path rather than treating a JSON parsing failure as an operation failure. After a write, that misleading error can encourage duplicate submission.

No content is part of the contract

RFC 9110, section 15.3.5, says a 204 response ends after its header section and cannot contain content or trailers. Response metadata describes the target resource and selected representation after the action. Its PUT example includes an ETag identifying the new representation. An absent body therefore does not make all headers irrelevant.

Imagine a settings page receiving 204 after saving. A shared wrapper then attempts JSON parsing and displays a save failure even though the server may already have updated the resource. This is a hypothetical explanation, not an executed endpoint test. The repair is to recognize the status and content contract, rather than manufacture a success object from an empty body.

Do not guess missing business data

A request abstraction can distinguish no-content results from results containing data. The precise type depends on the project, but every successful response need not contain identical JSON fields. If the caller requires the updated object, change the interface or fetch it separately. The response cannot supply values it did not send.

Nor should every empty response be accepted. An endpoint that promises an object may have broken its contract. Consider status, media type, content and business expectations together. Swallowing all parsing errors would also conceal malformed responses; skip reading only where the contract allows it.

The interface may clear a pending-save marker while retaining the current view. Refreshing values and resolving concurrent edits require their own decisions. Preserve any updated version identifier for later edits. Stale visible values alone are not a reason to repeat a write.

Locate failure before recovery

Proposed checks include valid 204 responses, valid JSON successes, server errors, malformed required content and successful writes followed by display failures. Verify that messages distinguish these states. These checks have not been executed for this article.

A client exception does not prove that a write never occurred. For consequential side effects, use the operation's identity, idempotency design and status evidence before retrying. A 204 indicates success for the requested action; it does not independently establish completion of downstream notifications or settlement.

Review callers and logs after fixing the wrapper: they may still expect a nonexistent object or classify no content as an error. HTTP 202 terminal-state confirmation discusses the related distinction between acceptance and an eventual business outcome.
