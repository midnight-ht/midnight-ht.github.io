Why should a successful HTTP 204 skip JSON parsing?

Compare a 204 and two forms of 200 on a local HTTP server, then distinguish save success, response metadata and decoding errors.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-18 · Estimated read 16 min
Translations
zh-CN en

Article

Key takeaways

  • Give a successful 204 an explicit no-content result.
  • Keep headers the next operation needs.
  • Handle unexpected responses according to the endpoint contract.

HTTP 204 already confirms the operation succeeded. There is no response content to parse as JSON. When a wrapper receives 204, it should return an explicit no-content result and keep the response headers the application needs. If the endpoint promises JSON on other successful statuses, keep decoding those responses according to that contract. The shared wrapper can then report a successful save without prompting the user to retry.

Check the status before reading the response

In RFC 9110’s section on 204, the response ends after the header section and carries neither content nor trailers. Information can still arrive in the headers. The specification uses the example of a successful PUT where a 204 with an ETag identifies the new representation after the operation. An editor can keep the document view in place, indicate success and apply the returned metadata to its active representation.

Suppose a settings page saves a color theme. The browser receives the success status, and a shared function then calls the JSON parser. The parse throws because there is no data to read. The interface reports a failed save even though the server may already have applied the update. Retrying creates a second write request. Whether that repeats notifications or audit entries, or affects the setting itself, depends on the application contract. The decoding error cannot answer those questions.

Give the wrapper three distinct response cases

This fixture starts a temporary loopback server. It counts PUT writes and returns 204 with an example version tag. The read paths return either valid JSON or a truncated object. Parsing a clone of the save response exposes the old behavior before the revised decoder handles the original. The decoder checks for an HTTP success status, then handles the no-content result this particular contract permits. Its other success branch still expects JSON.

import assert from 'node:assert/strict';
import { createServer } from 'node:http';
import { once } from 'node:events';

const host = '127.0.0.1';
let writes = 0;
const jsonHeaders = { 'Content-Type': 'application/json' };
const server = createServer((req, res) => {
  const saving = req.method === 'PUT' && req.url === '/settings';
  if (saving) writes++;
  const status = saving ? 204 : 200;
  const headers = saving ? { ETag: '"v2"' } : jsonHeaders;
  const content = saving ? undefined : req.url === '/broken' ? '{' : '{"theme":"dark"}';
  res.writeHead(status, headers);
  res.end(content);
});

server.listen(0, host);
await once(server, 'listening');
const base = 'http://' + host + ':' + server.address().port;

async function decode(response) {
  if (!response.ok) throw new Error('HTTP status: ' + response.status);
  if (response.status === 204) {
    return { kind: 'no-content', etag: response.headers.get('etag') };
  }
  return { kind: 'json', value: await response.json() };
}

try {
  const saved = await fetch(base + '/settings', { method: 'PUT' });
  await assert.rejects(saved.clone().json(), SyntaxError);
  assert.deepEqual(await decode(saved), { kind: 'no-content', etag: '"v2"' });
  assert.deepEqual(await decode(await fetch(base + '/settings')),
    { kind: 'json', value: { theme: 'dark' } });
  await assert.rejects(async () => decode(await fetch(base + '/broken')), SyntaxError);
  assert.equal(writes, 1);
  console.log('Five assertions passed');
} finally {
  server.close();
}

All five assertions passed locally on Node v24.21.0. Parsing the 204 as JSON throws a syntax error. The status-specific branch still reads the version tag. The valid read produces a settings object and the truncated read still throws. The counter stays at one, which means this test did not send another save. The fixture did not exercise a browser interface, a gateway, real settings storage or server-side conditional writes.

The Fetch definition of a null body status includes 204. This wrapper deliberately branches only for the update endpoint’s 204 contract. A shared wrapper can serve other kinds of endpoints. If it maps every unreadable response to an empty value, a failed lookup might be displayed as an empty record list, hiding the actual status. An API that also uses HEAD should decide whether content is expected from the request method and endpoint contract. The status check in this example alone cannot express that decision.

What state should the editor keep after saving?

The no-content success result lets the page clear its pending-save indicator. The reported success comes from the HTTP status. If the server normalizes the submitted values and the page must show those values, another read or an endpoint that returns the representation is more reliable than guessing from an empty response. If the service has only accepted the work and has not finished, follow the endpoint’s state contract. See how to confirm the final state after HTTP 202 for the distinction between accepting and finishing work.

A local edit can occur between saving and reading back the result. Suppose the user submits the dark theme, then switches the unsent draft to light while the request is in flight. When the first save succeeds, clear the pending status for the dark submission only. Preserve the light draft. A subsequent read returning dark must also leave that draft in place. To test this, control when the first save and the read complete, change the input between those responses, then check the confirmed server value and the unsent draft separately. The save button should still let the user submit the new draft. These are proposed UI checks and the local server fixture did not run them.

With concurrent editing, a returned ETag can help with the next write, provided the server defines which representation the user edits, what precondition the next write applies and how users resolve a conflict. If the API specifies a strong tag for If-Match, the client can retain the returned tag as the validator for its next request. The tag does not provide document content or resolve a clash between concurrent editors. When the API does not send a tag, expose that fact and let the caller decide whether it needs to read the representation again.

Keep the failure stage visible. Receiving an HTTP error, losing the connection before a reliable response and receiving a success status with an invalid payload call for different recovery decisions. In the first case, show the rejection according to the endpoint contract. In the second, consider that the write may have occurred and check its state if needed. In the third, log the received status and decoding stage so a maintainer can locate the mismatch. A confirmed 204 does not require another save merely to get an object. An acceptance test can use the same type of counter to detect duplicate requests, and then check the actual UI button state separately. This fixture did not run those UI checks.

May I treat an empty 200 like a 204?

Follow that endpoint’s documented response format. A read endpoint that promises a JSON settings object on every 200 has violated its contract when it sends an empty body. Keep the resulting error visible so someone can fix the endpoint. If another endpoint specifically permits an empty 200, define that branch for it and test both an empty body and a valid object under the same status. A parser exception cannot make the decision by itself because truncated JSON also raises one. Specify the operation, expected status and return type in the same contract test to protect callers from silent decoder changes.
