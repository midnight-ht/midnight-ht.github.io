Why do failed Pod counts miss Kubernetes Job retries?

Compare fictional failed-Pod and active-restart snapshots, then organize diagnostic and recovery evidence by execution identity.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-21 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • Keep Pod outcomes and active-restart evidence together.
  • Associate each execution with its business input.
  • Check confirmed external outcomes before recovery.

Diagnosing Kubernetes Job retries requires both failed Pods and container restarts in active Pods. With OnFailure, a Pod can still appear Running while its task has executed several times. A failed-Pod count alone cannot describe the retry evidence or establish that a business action happened only once.

Keep both counts in the diagnostic record

The Job documentation’s backoff section describes two calculations. One counts Failed Pods. With OnFailure, another considers container retries in Pending or Running Pods. Reaching the limit through either calculation causes the Job to be considered failed. A view showing only terminal Pod counts omits repeated execution inside one Pod.

This article uses the ordinary backoff mechanism described in the current Job documentation. Indexed execution, per-index limits and custom failure policies can change the diagnostic path. Preserve the actual Job configuration and cluster version first, establish which rules apply and then interpret observations under those rules. A field called retry count is not a shared budget for every application and controller involved.

Two fictional snapshots expose the missing signal

This local observation function uses invented states. One case has a failed Pod and a running Pod with no container restarts. The other has one running Pod whose container has restarted four times. The script reports failed terminal states and active restarts separately. It does not connect to a cluster or use production or customer data.

import json

snapshots = [
    {"name": "new-pods", "policy": "Never",
     "pods": [{"phase": "Failed", "restarts": [0]},
              {"phase": "Running", "restarts": [0]}]},
    {"name": "same-pod", "policy": "OnFailure",
     "pods": [{"phase": "Running", "restarts": [4]}]},
]

def observe(case):
    failed = sum(p["phase"] == "Failed" for p in case["pods"])
    active = sum(sum(p["restarts"]) for p in case["pods"]
                 if p["phase"] in ("Pending", "Running"))
    return {"case": case["name"], "failed_pods": failed,
            "active_restarts": active}

result = [observe(case) for case in snapshots]
assert result[0]["failed_pods"] == 1
assert result[0]["active_restarts"] == 0
assert result[1]["failed_pods"] == 0
assert result[1]["active_restarts"] == 4
print(json.dumps(result, indent=2))

All four assertions passed locally on Python 3.11.15. The second case reports zero failed Pods and four active restarts. This verifies the function against its fictional input. It does not simulate controller reconciliation or establish that a Job has reached a terminal condition at a particular time. Use it to review a dashboard’s missing signal, then use real object conditions and events for the actual diagnosis.

After an alert, preserve the Job UID, configuration, start time and conditions. Collect Pods by owner UID. A reused name does not identify the same historical Job, and mixing old Pods with a new Job would corrupt the record. Keep each Pod UID, phase, container name, restart count and last termination information, together with the observation time. Before collecting previous container logs, establish that the relevant run remains available. This article did not execute those cluster reads.

The collection window can itself span a change. If the Job is read before another restart and the Pod afterward, the condition and counter belong to different moments. Keep the collection start and end times and raw objects. Compare a later observation by the same UID. When an old Pod has disappeared, record its absence and last-seen time instead of substituting zero. The function’s extracted counts do not independently decide whether a Job should fail. Use the actual Job condition and applicable policy for that decision.

Which layer is rerunning the application?

Application request retries, container restarts, replacement Pods and newly scheduled Jobs can all revisit the same input. If a user receives two results while operations sees only one active Pod, trace the input identity and execution confirmations. Pod inventory describes scheduling objects. Application evidence is needed to reconstruct business executions.

Consider an unexecuted report task. It uploads a report to external storage, then exits before recording completion locally. On restart, checking only the incomplete local status can cause a second upload. A larger retry limit permits another run without resolving the gap between external completion and local acknowledgement. Recovery should use the stable work-item identity to check existing artifacts before recording acknowledgement, skipping confirmed work or processing what remains. Validate the external API’s deduplication behavior separately.

Acceptance cases for side-effecting work should cover failure before processing, failure after external confirmation but before the local record, and failure partway through a collection. Identify items that may be retried, those that need a lookup and those that never started. Link both successes and failures to the work item and attempt identity. A terminal failure of the Job does not describe every business action it attempted.

Choose a debugging policy for the evidence you need

When comparing each new process’s input and exit, Never can organize observations around separate Pods. You still need owner and input identity. If production uses OnFailure, test repeated executions inside the same Pod, including temporary files, locks and unfinished output. A policy change alters where evidence appears. Validate it against the application in a controlled environment instead of assuming that the setting makes the program reentrant.

Assign evidence-retention responsibilities too. Keeping a Job object, retaining its Pods and exporting logs are separate actions. Expiry of any one can leave a retrospective with only the final attempt. Record the retention window, collection entry point and identity attached to a failure notification before deciding when to clean up objects. See CronJob duplicate scheduling for the boundary where an external scheduler creates another Job.

Will a Failed Job resume after a dependency recovers?

The failure condition ends this Job execution. A later dependency recovery does not imply it starts again. A new Job or another external schedule needs its own input and recovery decision. Keep the old Job identity and failure reason, then associate the new execution with the remaining work that has actually been checked. A fresh object starts with fresh status, while earlier external artifacts and business records may still exist.
