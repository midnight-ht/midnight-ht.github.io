A Span Ended. Should You Flush Before the Process Exits?

For orderly exit, usually wait for provider teardown. Understand its relation to ForceFlush, and why export success is not proof of backend persistence.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-24 · Estimated read 19 min
Translations
zh-CN en

Article

Key takeaways

  • Span.End finishes a Span; it does not prove export.
  • For orderly teardown, check the language SDK's provider contract; the specification requires processor shutdown to include ForceFlush effects.
  • The evidence behind a successful flush or shutdown depends on the exporter and receiver; it does not by itself prove backend indexing or durable retention.

Usually, you do not need to call ForceFlush immediately after every Span ends. Span.End() ends the Span record; a batch processor may still hold it in an in-process queue. For an orderly exit, check the TracerProvider.Shutdown contract of the language SDK you use and wait for its success, failure, or timeout result. The OpenTelemetry Trace SDK specification released on September 14, 2026 requires SpanProcessor.Shutdown to include the effects of ForceFlush. An explicit flush is more appropriate at an exceptional lifecycle boundary where a platform may suspend the process before scheduled export. Even a successful call does not prove that the backend indexed the data or will retain it permanently.

There are several stages after “end”

It helps to separate at least five states: application code calls End(); a processor receives the end event; a batch processor queues an exportable record; an exporter attempts to send it; and after a receiver accepts it, the backend processes and indexes it until a query can see it. The stages are not one atomic operation. Completing the first does not prove that later stages completed. An exporter success result must also be interpreted according to that exporter's and transport protocol's contract.

The same specification says OnEnd(Span) runs synchronously inside the Span.End() call. That synchronous callback does not mean that network export is complete before End() returns. A batch processor groups ended Spans and typically exports after a scheduled condition, when a batch threshold is reached, or when it receives ForceFlush. A short-lived job that exits just after its last Span ends may therefore leave before scheduled export. But a Trace missing from a backend query could also reflect sampling, broken context propagation, a full queue, export failure, receiver delay, or a query-scope mistake. Absence from the result does not locate the failing stage.

The specification lists reference defaults for the standard batch processor: a maximum queue of 2,048, a scheduled delay of 5,000 milliseconds, a maximum export batch of 512, and an export timeout of 30,000 milliseconds. Treat these only as configurable specification defaults, not measured settings for every language SDK, version, or deployment. The processor drops Spans when the queue limit is reached. If a language implementation or environment changes these values, inspect the effective configuration instead of explaining a production observation with defaults.

For orderly exit, start with the teardown contract

Under that release's provider contract, each provider's shutdown method should be called only once. The provider must invoke shutdown on its internal processors and should give callers a way to learn whether it succeeded, failed, or timed out. A processor's shutdown must include the effects of ForceFlush and should complete or abort within a timeout. Under this general contract, the usual first choice for orderly teardown is to call provider shutdown and inspect its result, rather than flushing each request and then issuing another flush at exit.

“Usually” has a boundary. Language SDKs map the specification to different APIs, asynchronous models, and configuration points; a processor may also be custom. This article cannot guarantee a method name, return type, concurrency behavior, or timeout unit for an unspecified SDK version. Read the official API for the version actually in use, then confirm which processors provider shutdown reaches. Shutdown is a lifecycle boundary: the specification does not allow processors to keep receiving new OnEnd or ForceFlush calls after shutdown. Stop accepting new work, finish in-flight operations under their business policy, and then shut down telemetry so teardown does not race with continued Span production.

When is a separate ForceFlush warranted?

Provider ForceFlush has a clear use as well: some FaaS platforms may suspend a process after an invocation but before scheduled export. The function may need to advance Spans that have not yet been exported before crossing that suspension boundary. The specification describes flushing as a hint and, when a timeout is supplied, prioritizes the time limit; some export work may be skipped or aborted. It is not a command to “write data permanently to disk.” Calling flush after a batch processor has already shut down is not a reliable fallback; accepting a flush after shutdown may violate the lifecycle contract.

A shutdown timeline with explicit assumptions

The numbers below explain state transitions; they are not execution results. Assume a task uses the specification's reference defaults of a 5,000-millisecond scheduled delay and a batch threshold of 512. At a hypothetical point in time, only three ended Spans are in the queue and the application begins exiting. Since the batch threshold is nowhere near reached, do not assume a scheduled export has already happened. The application calls provider Shutdown, and the processor attempts to drain its queue and exporter work within its shutdown budget. If the exporter reports success within that budget, the application can record “SDK shutdown call succeeded.” Whether it can say “the server received it” depends on the exporter's definition of success; whether it can say “the backend indexed it” requires evidence from the backend or query path.

Now assume the host gives the process a two-second termination grace period while the exporter is configured with a 30-second timeout. The 30 seconds set an upper bound on the SDK's wait; they do not turn the host's two seconds into 30. Forced termination may arrive before the SDK reports a timeout. The right budget is not a universal copied number: place business intake and cleanup, provider shutdown, transport waiting, and the host's termination deadline on the same timeline, and preserve an observable outcome for work that cannot finish. This example was not run and does not prove that three Spans would be lost. It only illustrates how time budgets can conflict.

Why ForceFlush success may not make a Trace visible

Consider a flush that returns success while a target query cannot yet find a Span. That is not necessarily contradictory. For protocol exporters, the specification says success typically means the data was sent over the network and delivered to the destination server; subsequent persistence, indexing, and query visibility are separate confirmations. Another counterexample is a Span excluded by sampling: orderly shutdown cannot export a Span that was never recorded. Queue overflow, export failure, and timeout occur at other stages. When data is missing, inspect Span.End, the sampling decision, queue and drop evidence, export result, receiver acknowledgement, and backend query conditions separately.

Repeated calls also have a cost. If provider shutdown already closes its processors and processor shutdown includes flush effects under the specification, then “ForceFlush succeeds, immediately followed by Shutdown” is usually a redundant request; it does not upgrade receiver acknowledgement into proof of long-term retention. By contrast, an explicit flush can help at a FaaS invocation boundary where the provider remains alive but the runtime may suspend execution. Before choosing, ask: is this an ordinary process exit or an imminent suspension? Does the provider method in this SDK guarantee that it reaches every processor? Does the processor or exporter have its own buffer? Which hop does the return status represent? Those answers are more useful than “flush after every End.”

How to verify your SDK without inventing a result

Pin the exact language, SDK, and exporter versions. Read the official documentation for those versions and confirm whether provider Shutdown closes all registered processors, whether it blocks, how timeout is configured and expressed, and how the result is represented. Then use a controlled exporter in an isolated test: create and end a Span, and observe orderly shutdown, exporter failure, a wait timeout, and queue pressure separately. Record whether the processor received the end event, whether the exporter was invoked, what result it returned, and whether the process exited before the host's deadline. Do not rely only on a backend UI, and do not put tokens, personal attributes, or sensitive business fields in test logs.

That test matrix is a proposal, not a run recorded for this article; no specific language SDK was tested. The OpenTelemetry Go main-branch implementation can help explain how one implementation handles queues, shutdown, and flush, but main can change and is not a substitute for checking the version pinned in production. If the business requirement is audit-grade or accounting-grade retention, use a record mechanism with explicit acknowledgement, retry, persistence, and retention contracts. Trace export should provide diagnostic evidence, not silently replace a business ledger it was never designed to be.

If you are also deciding whether an exception belongs as an event or a Span status, see Exception events and Span status. For shutdown, gather evidence from the lifecycle, exporter contract, and host deadline; state only the delivery boundary those sources actually confirm.
