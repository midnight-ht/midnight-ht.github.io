Why should a multilingual list choose its Collator locale?

Compare German and Swedish locally to define locale selection, ties and the limits of repeatable list order.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-20 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • Choose a locale for the readers’ purpose.
  • Keep distinct record identities when names compare equal.
  • Record effective settings and define a tie rule.

A multilingual list needs a sorting locale chosen for its readers’ purpose, with the effective locale and options recorded. Intl.Collator compares text under a language policy. Equality only says that those strings have no ordering distinction under that policy. Business fields still identify records, and paging needs a consistent source order plus a stable rule for ties.

Choose the locale before judging the displayed order

The MDN documentation for Intl.Collator illustrates the difference between German and Swedish. A character with an umlaut can occupy a different position depending on the language. The product has to decide whether a list follows the UI language, the list’s main language or a user-selected policy. Without that decision, a developer can only describe the order on their own machine, rather than determine whether a reported order is correct.

The ECMA-402 string comparison definition connects the comparison result with the configured collation. Consume the result by its sign or equality to zero. Code that only recognizes exactly negative one adds an unnecessary numeric assumption. Passing the comparator to sorting, or checking its sign, matches the ordering contract.

Two positions for one character, plus a tie

This fixture uses fictional records. Both German and Swedish comparisons use base sensitivity so the same character’s relative position is observable. The numeric IDs are unique finite integers in this fixture and break ties in ascending order. Copying before sorting preserves the caller’s input order. Four assertions check the two locale-dependent comparisons, the German tie, and the final ordering of tied records.

import assert from 'node:assert/strict';
const collators = ['de', 'sv'].map(locale =>
  new Intl.Collator(locale, { sensitivity: 'base' })
);
const [german, swedish] = collators;
const [de, sv] = collators.map(value => value.compare);
assert(de('ä', 'z') < 0);
assert(sv('ä', 'z') > 0);
assert.equal(de('a', 'ä'), 0);
const rows = [
  { id: 20, name: 'ä' },
  { id: 10, name: 'a' }
];
const ordered = [...rows].sort((a, b) =>
  de(a.name, b.name) || a.id - b.id
);
assert.deepEqual(ordered.map(row => row.id), [10, 20]);
console.log(JSON.stringify({
  locales: collators.map(value => value.resolvedOptions()),
  icu: process.versions.icu, ids: ordered.map(row => row.id)
}, null, 2));

All four assertions passed locally on Node v24.21.0. German places ä before z here, while Swedish places it after z. German compares a and ä as equal, yet the resulting list retains both IDs. The output also records the ICU version and effective options. This is an observation of those local samples. It does not cover a browser, a database or the user’s own names.

The definition of resolvedOptions gives you a way to inspect effective settings. Requested locales can go through matching or fallback, so record both the request and the resolved value. When output differs, compare the language and options first, then inspect the runtime’s localization data. General Intl support alone does not establish that all language orders agree.

What still needs a decision after equality?

Ignoring some spelling distinctions can be appropriate for a readable list. Account merging, authorization and database uniqueness need their own identity rules. The fixture retains the separate records even when the names compare equal. Treating that comparison as proof of one person can introduce record loss through a display feature. A product review can distinguish textually similar candidates from the final selected record, then check that submission carries the original identity.

The tie rule also depends on the task. Numeric IDs make this fixture deterministic, but production records may use another field. A list might prioritize creation order or organizational hierarchy. Additional fields can themselves tie, so repeatable output ultimately needs a field that is stable and unique within the result set. When that policy is used for export or a sorting link, later reproduction should identify its direction.

Data can change between pages. A renamed or newly added record may move even when the comparator and ID policy stay the same. A display-order test only covers its fixed collection. Stable paging requires a cursor, snapshot or other read policy executed by the data source that owns pagination. A cursor needs to correspond to the policy that produced it. After changing locale or tie fields, an endpoint can reject an old cursor and ask the user to start a new list. Specify that choice and test old cursor examples before changing the client comparator. Reordering one page in the client changes that page’s display without deciding which records belong on the other pages.

How do you accept a sorting policy change?

Choose a small set that distinguishes old and new behavior. Many ordinary ASCII names can appear identical under both policies. The character positions and tie in this fixture cover two distinct decisions. Product tests should also include blank names, uncommon valid characters and several identical display names, with a defined rule for missing names. Fictional records avoid bringing unnecessary personal data into the test. Handle production samples according to the team’s data rules.

When the server owns page order, the client should display the returned order and exports should use the same agreed ordering source. A database collation need not coincide with a particular JavaScript option set. If agreement is required, compare diagnostic samples across both environments and record the database, localization library and client versions. This article did not run that cross-environment test. A change can affect comparisons with historical exports, so explain the visible differences and affected records. See sorting and in-place mutation for the separate array-ownership check.

Can the digits in a filename sort numerically?

Collator’s numeric option supports numeric-style comparisons, but the list’s purpose determines whether to enable it. It can arrange some numbered display labels as readers expect. It does not replace a business parser. If a numeric segment belongs to a fixed-width identifier, the product might require character ordering. Test labels representing the ninth and tenth items, alongside leading zeros and nonnumeric segments. Numeric comparison can still produce ties, so preserve the agreed record-identity and secondary-order rules.
