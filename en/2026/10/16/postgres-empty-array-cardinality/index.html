Why Does array_length Return NULL for an Empty Array?

array_length measures one dimension; cardinality counts all elements. Distinguish an empty dimension, an absent dimension, and SQL NULL before filtering or changing business state.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-24 · Estimated read 22 min

Article

Key takeaways

  • array_length returns NULL for an empty or missing dimension; cardinality returns 0 for an empty array.
  • For multidimensional arrays, array_length measures one dimension while cardinality counts elements across all dimensions.
  • Use COALESCE to map NULL to zero only when the business contract intentionally merges those states.

The length of a requested dimension on an empty array is NULL, while its total cardinality is zero. The former describes a dimension; the latter answers how many elements the array contains in total. PostgreSQL 19 documents array_length as returning NULL for an empty array or a dimension that does not exist. The cardinality function counts elements across every dimension and returns zero for an empty array. Use cardinality when the question is whether the collection has any elements; use array_length when you need the size of a particular row or column, and name the dimension explicitly.

Similar names, different measurements

It is tempting to read array_length(arr, 1) as “how many things are in the array,” especially for a one-dimensional value where it often matches the total count. But the second argument is part of the question, not decoration: the function reports the length of a specified dimension. The total-count function has no dimension argument because it combines element counts across the array. For a non-empty one-dimensional value the two measurements commonly coincide. That coincidence comes from the shape of the data; it does not make the functions interchangeable.

For empty input, the PostgreSQL documentation specifies NULL, rather than zero, when array_length is asked for the first dimension. The total-count function asks a different question: how many elements exist in total? Its answer is zero. If a non-empty one-dimensional array is queried for a second dimension, array_length also returns NULL; that means there is no reportable length for that dimension, not that the whole array is empty. Remembering only “COALESCE empty arrays” can merge an empty collection and a dimensionality mistake into one state.

Examples in the PostgreSQL 19 documentation show the distinction: array_length(ARRAY[10,20,30], 1) returns 3, and cardinality(ARRAY[10,20,30]) also returns 3. But array_length(ARRAY[]::integer[], 1) returns NULL, while cardinality(ARRAY[]::integer[]) returns 0. These behaviors are based on the PostgreSQL 19 documentation. No SQL was run in this article’s environment. A project on another database version should consult the function reference for its pinned version.

NULL changes a WHERE result

This distinction can change query results, not merely display text. Suppose an array named flags uses an empty array to mean “we confirmed that no switches are enabled,” while SQL NULL means “the selection has not been computed.” A developer writes array_length(flags, 1) = 0 to find records with no switches and finds that empty arrays are missing. The left side is NULL for an empty array; an ordinary comparison involving NULL also yields NULL, or unknown, rather than true. WHERE keeps rows only when the predicate is true, so the row is filtered out.

If the actual question is “does this array contain no elements?”, cardinality(flags) = 0 evaluates true for an empty array. A SQL NULL input still needs its own definition: it does not mean “confirmed empty,” so the predicate remains unknown and does not select that row. If the business deliberately wants uncomputed values to count as empty, it can merge them explicitly. If they represent different lifecycle states, keep them separate. For a related discussion of NULL in constraints and data domains, see CHECK constraints and null domains.

COALESCE does not make this decision automatically. COALESCE(array_length(flags, 1), 0) = 0 maps the NULL returned by array_length for an empty dimension or a dimension that does not exist to zero. If flags itself can be SQL NULL, handle that explicitly with flags IS NULL in the state logic; do not let a default value define whether “not computed” means “confirmed to contain no elements.” In validation or state reporting, mapping an uncountable result to zero without a contract can disguise an unknown value as a confirmed empty collection. A clearer approach is to handle state first, then use cardinality(flags) = 0 for a known empty array.

A two-dimensional array shows why total is not a dimension

Consider a matrix with two rows and three columns. Its first dimension has length 2, its second dimension has length 3, and its total cardinality is 6. array_length(matrix, 1) and array_length(matrix, 2) answer row and column lengths; the function cardinality(matrix) answers how many elements the matrix contains. These numbers do not conflict; they use different units. To display “2 rows × 3 columns,” use the two dimension lengths. To count cells or determine whether the entire matrix is empty, the total-count function is more direct.

SELECT
  array_length(ARRAY[[11,12,13],[21,22,23]], 1) AS rows,
  array_length(ARRAY[[11,12,13],[21,22,23]], 2) AS columns,
  cardinality(ARRAY[[11,12,13],[21,22,23]]) AS total;

This SQL fragment illustrates the documented semantics and was not executed during this task. Another counterexample is asking a one-dimensional array for its second dimension: array_length(ARRAY[10,20,30], 2) is NULL, but cardinality remains 3. Treating “dimension 2 is absent” as “the array has no values” confuses shape validation with counting. To check whether a value has the expected dimensionality, inspect array_ndims or array_dims and then validate each required length. Do not turn a NULL dimension length into zero and call the shape valid.

Array subscripts also need not start at 1. The PostgreSQL documentation shows an array whose lower bound is 0, such as [0:2]={1,2,3}. It has three elements but its first subscript is 0. When array_length returns 3, it is reporting the size of that dimension, not saying the largest subscript is 3. If code needs index boundaries, inspect array_lower and array_upper. If it needs a count, use a dimension length or cardinality. Treating the upper bound as the number of elements creates an off-by-one error for a non-default lower bound.

A declared dimension is not a runtime shape constraint

There is another easy-to-miss failure path: declaring a column as integer[3][3] does not ensure that every stored value will always have three rows and three columns. The PostgreSQL 19 array chapter says the current implementation ignores declared array size and does not enforce the declared number of dimensions. Arrays of the same element type do not become different runtime data types just because a declaration lists a size or dimension count. The declaration can document intent for people, but it is not a complete runtime shape check.

Imagine an API contract requiring a 3×3 matrix, while historical records contain a one-dimensional value, a 2×3 value, and an empty array. A query using only array_length(matrix, 1) = 3 proves at most that the first dimension has length 3. It does not prove that the second dimension is also 3, and a NULL result alone cannot tell whether a matrix is known to be empty or has not been generated. Validation should reflect the actual contract: Is SQL NULL allowed? Is an empty matrix allowed? How many dimensions are required? Are all lengths fixed? Once those states are separate, choose a constraint, write-time validation, or rejection policy. This article does not provide an unverified production CHECK expression because NULL handling in constraints must be assessed together with the application’s empty-value semantics.

A worked example with an explicit business meaning

Suppose a task table stores confirmed rule selections in an integer array. The product contract says: SQL NULL means selection computation has not finished; an empty array means computation completed but the user selected no rules; a non-empty array contains selected rule identifiers. A report needs to count “tasks confirmed to have no selections.” The predicate array_length(rules, 1) = 0 misses empty arrays because the result is NULL. Another incorrect predicate is rules IS NULL OR cardinality(rules) = 0 for “confirmed to have no selections”; it deliberately includes tasks whose computation has not finished. If the array contract guarantees one dimension and the question concerns total elements, express the known-empty state as rules IS NOT NULL AND cardinality(rules) = 0. This puts the state decision in the predicate rather than relying on a default to merge states.

That conclusion depends on the business contract and predicate semantics; it does not mean PostgreSQL can infer what “not computed” means. If upstream writers convert NULL to an empty array, the database cannot later recover which rows were originally unknown. If the same column permits multiple dimensions, cardinality can count all elements but does not tell the caller the row and column boundaries. In those cases, change the data contract or preserve computation state separately from the array. One integer-valued expression cannot replace a state model.

A small validation matrix for your own contract

Before release, design isolated samples for SQL NULL, an empty array, a one-element one-dimensional array, a multi-element one-dimensional array, a 2×3 array, an array with a lower bound other than 1, and a request for dimension 2 on a one-dimensional value. For each sample, record every array_length result, cardinality, array_ndims, whether the business predicate matches, and the state returned by the API. This checks not only the function values but also whether PostgreSQL WHERE, the ORM mapping, and the UI all preserve unknown versus empty.

This is a proposed validation plan, not an executed result. During implementation, confirm the PostgreSQL version, how the driver represents SQL NULL, whether serialization converts NULL to an omitted field, and whether the ORM supplies a default empty array. Creating a JavaScript empty array in application memory does not test PostgreSQL’s dimension functions. Querying the database without checking the API response cannot reveal whether the mapping layer collapsed distinct states.

When should each function be used?

For “how long is this dimension?”, use array_length(array, dimension) and account for NULL when the array is empty or that dimension is absent. For “how many elements are there in total?”, use cardinality(array), which returns zero for an empty array. For “is the database value NULL?”, express IS NULL separately. To inspect dimensionality and bounds, use array_ndims, array_dims, array_lower, and array_upper, then validate against the contract. Use COALESCE only at a boundary where the product explicitly says that unknown should count as zero.

Reader question: Can I always write COALESCE(array_length(a, 1), 0)? You can, but it no longer means “the length of dimension 1.” It means “use zero when the length of dimension 1 cannot be reported.” If downstream logic interprets zero as a confirmed absence of selections, the expression erases the distinction between an empty array and a missing dimension. If a itself may be SQL NULL, define that input state and handle it explicitly. Decide which states must remain distinct before merging them.
