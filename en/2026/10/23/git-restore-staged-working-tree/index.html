Git Restore: Choose the Source and Destination Separately

Use three file versions to distinguish unstaging from discarding edits, then verify index and working-tree differences.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-23 · Estimated read 11 min
Translations
zh-CN en

Article

Key takeaways

  • Source and destination independently determine the result.
  • Unstaging preserves the working tree while changing the diff baseline.
  • Verify exact paths with file contents and both diffs.

To unstage edits while keeping file contents, target the index with git restore --staged. Plain git restore instead restores working-tree contents by default. Those operations are not interchangeable forms of “undo.” Choose the source and destination separately, especially when a file contains both staged and unstaged edits.

Compare three states of one file

The official git-restore manual says the default source is HEAD when --staged is given, otherwise the index. The default destination is the working tree. Combining --staged and --worktree restores both locations, and --source selects another source explicitly. Restore is not a search through every piece of text ever edited.

Consider an unexecuted exercise with a tracked config.txt. HEAD contains mode=old, the index contains mode=review, and the working tree contains mode=experiment. Unstaging restores the index to old while leaving the working-tree experiment content intact. The review version is no longer selected for the next commit.

Starting from those same initial states, restoring only the working tree copies review from the index and overwrites experiment. Restoring both locations defaults to HEAD, bringing both to old. Important work needs a recoverable copy or reviewed commit before an operation that may overwrite it.

# Illustrative only; no command was run against this repository.
# Unstage the confirmed path while preserving working-tree contents.
git restore --staged -- path/to/file
# This overwrites unstaged working-tree edits at the confirmed path.
git restore --worktree -- path/to/file

The path separator distinguishes paths from options; it does not decide scope. Replacing an exact file with a directory-wide path may affect unrelated work. A shared checkout can contain changes owned by several tasks, so repository membership is not ownership of every edit.

Partial staging separates selection from content

Different hunks of one file can live in the index and working tree. Unstaging the whole file changes the selection for the next commit while preserving current disk contents. It does not reconstruct the file before the last editing session. Patch mode can select hunks, but still compares a particular source with a particular destination.

Ask whether the intent is to remove a change from the next commit or remove it from the disk file. The first is index work. The second affects working-tree content and needs a review of what must be kept. Combining commit organization and experimental-code disposal in one vaguely described action makes review harder.

An explicit older source can restore a path's content without moving the branch. That does not reset the entire repository or reverse later external effects. An older file inserted into newer code may be incompatible and needs ordinary testing. Undoing an already shared commit is a separate history-management decision.

Verify two differences and the file itself

In a disposable repository, prepare the three versions. Before and after each operation, record git diff, git diff --cached, and actual file contents. These compare working tree to index and index to HEAD respectively. Confirm both the intended change and the content that should survive. Status letters cannot explain which text was retained.

Add an unrelated tracked file to check path scope. New files, deleted files, and unmerged paths need separate exercises; do not extend the ordinary tracked-file example to those states without checking their documented options. Preserve conflict evidence instead of forcing a routine restoration over it.

Unstaging is not a backup. The guide to stash scope addresses saving tracked, untracked, and ignored work. It does not guarantee automatic recovery of content already overwritten by restore.

Why can diff become larger after unstaging?

The comparison baseline changed. When the index returns to HEAD, changes previously staged can reappear in the working-tree difference alongside the latest edits. More diff output does not necessarily mean the disk file changed. Inspect the actual content and cached difference before inferring an extra modification.

Order matters too. Unstage first and then restore the working tree, and the second command's default index source is now HEAD. Restore the working tree directly from the initial state, and its source is still review. Recreate the same initial state for each comparison rather than building one experiment on the previous result.

If unstaging is part of splitting two commits, select hunks again according to the next commit's intent and inspect the complete staged difference. A configuration repair might belong in the first commit while an experimental flag stays in the working tree. Verify both choices; a successful build does not establish which changes were selected.

Retain the intended path list and deferred edits. Automatic formatting can alter hunk boundaries, so review them again after formatting. The final commit preview must correspond to the current index rather than a screenshot captured before unstaging.

No restore command was executed here. Useful evidence identifies source, destination, exact path, retained disk content, and final staged difference. A command returning without an error cannot establish those outcomes on its own.
