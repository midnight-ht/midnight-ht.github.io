Use AsyncLocalStorage.run to Bound Request Context

Trace run and enterWith across synchronous listeners, async creation points, context loss, and overlapping requests.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-23 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • Create inheriting work inside the run callback.
  • enterWith affects the remaining synchronous execution.
  • Test interleaving, nested restoration, and exceptional bridges.

When request logs need an identifier, prefer AsyncLocalStorage.run around the callback that starts the request's work. enterWith changes the remainder of the current synchronous execution, so later listeners in the same event can see the new context. Treating it like an ordinary local assignment misses that scope. First identify where work is created and who should inherit the identifier.

Context follows execution paths

This article checked the Node.js v26.12.1 asynchronous-context reference. It covers run, enterWith, and getStore; it does not assume newer APIs exist on older runtimes. run synchronously invokes its callback with a store available to asynchronous work created inside that callback. The surrounding synchronous execution has its own context after the call leaves that scope.

Consider two unexecuted requests, req-a and req-b. Each entry creates its own store and starts configuration reads, database work, and response logging inside run. A's database work is slower, so B finishes first. Each chain should retain its identifier despite interleaving. A process-global “latest request ID” cannot represent that relationship.

import { AsyncLocalStorage } from 'node:async_hooks';
const context = new AsyncLocalStorage();
function handle(requestId) {
  return context.run({ requestId }, async () => {
    await performWork(); // Unimplemented illustrative business operation.
    return context.getStore()?.requestId;
  });
}

handle returns the callback's return value. Its caller must still await or handle the promise. Context propagation neither succeeds nor cancels the business operation. Dropping that promise can leave errors unhandled even when every log has the correct identifier. A correlated log is not a completed request receipt.

The enterWith counterexample needs only one dispatch

The reference warns that enterWith inside an event handler also affects subsequent handlers unless they are specifically bound to another context. That is why it prefers run unless there is a strong reason for enterWith. Two concurrent network requests are not required to expose the scope difference.

Suppose a notification bus's first listener enters an order context. Its second listener only counts notifications, but getStore now returns that order. If the counter starts asynchronous work, the unintended label can propagate. The issue is who may establish the context, rather than whether the logger prints it correctly. Wrapping the first listener's work in run gives that work a boundary and preserves the surrounding synchronous context.

A distinct context is not automatically immutable. Reusing the same store object across requests, or permitting downstream code to overwrite requestId, can undermine attribution. Create a small store per entry and separate stable identifiers from mutable business data. Correlation is also not authorization: a client-supplied label and an authenticated identity have different origins.

For libraries that save callbacks and invoke them later, inspect the context at invocation as well as registration. Custom thenables and callback bridges may require the documented context-loss investigation and possibly AsyncResource integration. Adding enterWith at every missing label can repair one log while widening another synchronous scope.

Test ownership rather than log order

A proposed test holds both work chains, completes B first, then releases A. Compare expected IDs with getStore at each stage rather than requiring sequential logs. Add nested run calls and inspect restoration of the outer store after the inner callback. Outside all initialized scopes, check the documented baseline state.

A separate event test uses two synchronous listeners. Compare the second listener's observed value when the first uses enterWith and when its work is bounded by run. For a suspected bridge, read getStore immediately before and after each boundary and locate the first loss. Execute with the actual runtime and dependency versions; comments in a sample do not establish compatibility.

Keep initialization inputs in the reproduction record. The article on environment-variable string parsing helps confirm that a textual flag actually enables the intended entry behavior. It does not solve propagation, but it can explain a mismatch between test configuration and execution.

Does the store cross a service boundary automatically?

A process-local asynchronous store is not a network protocol. Cross-service correlation requires explicitly transmitting approved fields and having the receiving service validate them and establish its own context. Decide which identifiers may cross the trust boundary and which should be regenerated. Local context continuity and distributed correlation are separate acceptance goals; the example implements no network propagation.

A creation-point control is useful: start one operation before entering the request boundary and another inside run. Awaiting preexisting work inside the callback should not be treated as changing that work's origin retroactively. Read context in the actual callbacks and compare the intended ownership. If an external result must be associated with a request, establish that association at a controlled receiving boundary.

Test restoration on failure too. Throw synchronously in a nested callback, inspect the outer store at the catch site, then reject asynchronous work and inspect both error-log attribution and the caller's failure. Correct correlation and delivered errors are two assertions; either can pass while the other fails.

No Node.js request, event-dispatch, or library-bridge test was run. A useful delivery record covers entry, asynchronous creation, nested restoration, and failure paths. Those boundaries make a log's request label meaningful before anyone uses it to infer progress.
