PostgreSQL Lock and Statement Timeouts Need Different Budgets

Use a two-session migration scenario to separate lock waits, statement budgets, transaction cleanup, and connection reuse.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-23 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • Lock timeouts apply separately to acquisition attempts.
  • Statement and client deadlines cover different intervals.
  • Recover transaction state and verify reused connection settings.

A migration may tolerate half a second waiting for a lock while allowing several seconds after acquisition. Give those stages different budgets. In PostgreSQL 18, lock_timeout applies while waiting for locks and separately to each acquisition attempt. statement_timeout constrains statement processing. Giving both the same value usually lets the statement limit act first, obscuring the distinction.

The clocks cover different intervals

The PostgreSQL 18 client-defaults reference covers explicit and implicit lock acquisition. A lock timeout is neither a cumulative transaction wait budget nor an execution-time limit. A statement acquiring several locks has separate acquisition attempts; the value cannot be read as the maximum duration of an entire migration.

The statement limit runs from receipt of the command at the server until completion, with documented details for simple and extended query protocols. End-to-end application latency also includes pool queues, network time, and retries outside that interval. A product deadline needs a budget for those stages too.

In an unexecuted scenario, inventory already contains data. Session A opens a transaction and holds a lock that conflicts with a schema change. Session B wants to add a column. The change can be retried later, so waiting briefly is preferable to a long lock queue, while execution after acquisition gets a longer allowance. These values illustrate a relationship; they are not production recommendations or measurements.

-- Session B: illustrative, not executed.
BEGIN;
SET LOCAL lock_timeout = '500ms';
SET LOCAL statement_timeout = '5s';
ALTER TABLE inventory ADD COLUMN review_note text;
COMMIT;

If A retains its lock, B is expected to hit the lock-wait limit first. If A releases promptly, B can proceed while the statement limit remains relevant. A counterexample sets lock_timeout to ten seconds but leaves statement_timeout at five: the statement deadline arrives before the lock budget expires. Absence of a lock-timeout error does not prove there was no lock wait.

An error leaves transaction work to do

A timeout exception does not mean that application rollback and connection cleanup are complete. After an error in an explicit transaction, end or recover that transaction according to its actual state before returning the connection to a pool. Partial recovery requires a savepoint established before the failing statement and a business contract that permits that scope. Sending another business statement blindly is not recovery.

The SET reference says SET LOCAL lasts until the current transaction ends, whether by commit or rollback. This makes it useful for a migration transaction. Session-level settings can persist after commit and affect a reused connection. Rolling back to a savepoint earlier than a SET LOCAL also cancels that setting.

For example, a batch sets a short wait after a savepoint, fails, and returns to an earlier point. Its next change may no longer have the intended budget. Either set budgets at a stable outer entry point or reestablish them before each local retry. Recovery paths, rather than shorter SQL, should determine the placement.

Retain which deadline fired, the statement identity, the transaction action, and the retry decision. A timed-out migration is not a successful column addition. When connection loss leaves the outcome unknown, inspect final schema state and migration records before retrying. No lock contention or driver recovery was executed for this article.

Make the failure modes distinguishable

A proposed test uses independent sessions: A holds a conflicting lock; B applies local limits and runs the change. Record the database error, elapsed time, and transaction state, end B's transaction, and then release A. Separately test the statement deadline without competing locks using a suitable disposable workload. If both cases are reported as a lost connection, error classification needs attention.

Include short-wait/long-execution and multiple-lock paths. One blocked statement cannot prove a cumulative cap. Review client cancellation as well: if the client gives up first without cancelling server work, the database may continue after the application reports failure.

After transaction cleanup, inspect current parameter values and run an ordinary request on the reused connection. Record the actual database identity alongside the settings. The related article on savepoints and partial-import reports addresses the result contract; this article addresses the clocks.

Can the application retry immediately?

Only after defining retry semantics, transaction recovery, and the total deadline. Repeatedly joining a queue behind a long maintenance task may accomplish little, while synchronized retries add competition. Deferral, backoff, or an assigned maintenance window may fit different workloads. Keep the total elapsed budget rather than restarting the user's deadline for each new statement.

Recovery also consumes the remaining deadline. Suppose a hypothetical client allows six seconds and the statement limit consumes five. Error handling, rollback, and a useful response still need time. Returning a connection to the pool without confirmed cleanup does not finish recovery. Determine actual margins with the driver and environment rather than treating these numbers as recommendations.

A test can start an independent operation immediately after cancellation and inspect whether it receives a clean connection. Preserve the original operation's terminal state and cleanup result separately; a later successful request must not erase evidence of a failed cleanup. Let connection management handle a connection whose reuse cannot be established.

This is a PostgreSQL 18 documentation review and a test design. No two-session experiment, pool test, or driver cancellation was run. Assign responsibility for waiting, execution, transaction recovery, and client deadlines separately; one timeout cannot promise when the whole operation will finish safely.
