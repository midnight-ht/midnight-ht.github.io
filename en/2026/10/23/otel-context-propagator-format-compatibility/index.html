OpenTelemetry Propagation: Injection and Extraction Must Agree

Check injection, transport, extraction, and parent use while preserving concurrency and trust boundaries.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-23 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • Propagation and export are different paths.
  • Matching formats still require correct parent use.
  • Check concurrency ownership and trust separately.

Two services can both install OpenTelemetry SDKs and still create separate traces. Check whether the sender’s propagation format is the format the receiver extracts, then verify that the receiver uses that extracted context to establish the intended relationship. SDK installation alone proves none of those boundaries is connected.

Propagation is an agreement on the wire

The OpenTelemetry context propagation guide calls writing context into a carrier injection and reading it extraction. It uses W3C Trace Context headers to illustrate cross-service correlation. The carrier might instead be agreed message metadata. Choose propagators for the actual protocol and SDK rather than expecting a telemetry backend to infer parents from timestamps.

Propagation and export happen at different points. Propagation delivers an upstream identity to another operation boundary; export sends already-produced telemetry to a receiver. Independent exports to one backend establish that each service has a functioning output path. They may still produce separate traces when inbound context is absent. Conversely, correct parent propagation does not guarantee every span was sampled, delivered, retained, or included in the current query.

Suppose an order service calls inventory. The sender creates an outbound operation and injects its current context in W3C format, while inventory extracts only another format. The business request can succeed and inventory can emit a span, yet the expected upstream identity is unavailable. Data from both services is not proof of a connected relationship. This is an unexecuted hypothetical example, not a real order-system test.

Make the mismatch concrete: the sender writes traceparent using W3C Trace Context, while the receiver enables only B3 multi-header propagation, expecting X-B3-TraceId and X-B3-SpanId. This fictitious W3C-only input contains none of the expected B3 headers. It is an illustrative wire value, not a packet capture or SDK execution.

traceparent: 00-11111111111111111111111111111111-2222222222222222-01

Check the whole path: the current operation at injection, expected outbound fields, arrival without gateway removal, the receiving extractor and format, and the parent context used when inventory creates its operation. Each step needs its own observation. A final line drawn in a trace viewer does not explain which boundary established it.

Matching formats can still lose context

Now suppose both sides use W3C format and the fields arrive, but inventory creates a root span before extracting the upstream context. Transport is fixed while operation creation remains wrong. Follow the SDK contract for using the correct context when the operation starts. Another failure occurs when an asynchronous branch loses its current context and a later outbound request injects empty context or another task’s identity. A single-request demonstration does not cover concurrent ownership.

Interleave at least two different orders in validation. Correlate safe request identifiers with exported trace, span, and parent relationships, checking that order A never supplies order B’s context. Repeatedly testing one request may establish field presence without establishing ownership. Diagnostic identifiers must not contain customer records or authentication tokens, and trace identities themselves need appropriate access controls.

Gateways, proxies, and message brokers introduce another boundary. Business data surviving transport does not prove propagation metadata survives. A protocol without dedicated metadata requires an explicit encoding, size budget, and extraction point, so propagation information does not unexpectedly reach business parsing as payload. Do not change a consumer protocol merely to draw a connected trace. Protocol compatibility and tracing relationships require separate acceptance evidence.

Must every service switch formats together?

Not necessarily. A coordinated cutover reduces transitional combinations but requires synchronized releases. A staged migration must identify which boundaries accept the old format, which send the new one, and how simultaneous inputs are resolved. Check the actual SDK’s composite-propagator capabilities and conflict rules. Supporting several formats does not imply that conflicting parents are automatically merged correctly.

Review three request forms: old format only, new format only, and both formats carrying different identities. The first two test migration coverage; the third forces an explicit precedence or rejection policy. Without that agreement, dual writing can produce inconsistent relationships. This is a proposed migration test, not completed compatibility certification across SDKs.

Parent-child relationships also differ from multiple-source relationships. A synchronous call can continue a clear upstream context. A batch combining several messages cannot treat all extracted identities as one parent. The October 17 article on Span Links and parents discusses that modeling decision. Available context still needs operation boundaries to determine its causal meaning.

Should incoming baggage be forwarded unchanged?

Do not treat valid syntax as trusted content. Decide what to accept, filter, and forward at each trust boundary. The propagation guide warns about forged inbound context and information disclosed by outbound context. Authorization must remain with authentication and permission mechanisms, not a baggage field claiming an administrator role or tenant identity.

Define allowed fields and size policies separately for internal calls and public entry points. Diagnostics should record presence, format, handling, and configuration version without copying arbitrary inbound content into unprotected logs. Filtering unnecessary propagation may reduce correlation, but that is an explicit trust decision. Do not manufacture a parent to make the viewer appear complete.

Do not reconstruct a trace merely by substituting a business request identifier for propagation fields. That identifier helps investigate one business operation, which may span retries or asynchronous batches rather than a single parent tree. Preserve it as a separate search key and explain why several traces belong to one investigation. This retains a diagnostic entry point during propagation failure without rewriting historical causality. Any supplementary correlation should state its source and limitations.

No SDK or telemetry backend was run for this article. An acceptance record should name both versions, propagator settings, carrier delivery, extraction, operation relationships, and exported query results, identifying the failed step when something breaks. Distinguish an installed SDK, a present header, an exported span, and a correct relationship so the next change repairs the actual boundary.
