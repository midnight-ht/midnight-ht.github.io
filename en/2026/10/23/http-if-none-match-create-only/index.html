Use If-None-Match for Create-Only Intent

Explain concurrent creation, recovery after 412, and name reuse with an enforced create-only precondition.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-23 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • A separate absence check does not prevent a write race.
  • The asterisk condition and idempotency answer different questions.
  • Reusing a deleted name requires an identity policy.

A GET that finds no resource followed by an ordinary PUT does not guarantee creation without replacement. Another client can create the same target between those requests. If the intention is “create only while the target has no current representation,” use If-None-Match with an asterisk to express that precondition, and ensure the server enforces it at the write boundary.

Absence is different from an old version

RFC 9110 section 13.1.2 defines the asterisk condition around the existence of a current target representation. When the condition is false, the method must not execute. For PUT, failure is 412 rather than the 304 used for GET or HEAD validation. An asterisk cannot be mixed with entity tags in a valid field value.

The target is the requested resource, not every related database row. If an address identifies a configuration within a tenant, define how tenant and name establish identity. Inconsistent case normalization, ignored tenant scope, or aliases for one object can make that identity ambiguous. A conditional header cannot repair the routing model; establish a stable target first.

Consider an unexecuted concurrent-creation example. Two deployment clients want to create the nightly schedule in the same tenant. A proposes one o'clock; B proposes two. Both query absence and then send their writes almost together. If ordinary PUT permits replacement, the final state may be whichever write arrives last. An earlier success tells neither client why its configuration disappeared.

With a create-only precondition on both requests, existence and creation need a single arbitration boundary. Once A wins creation, B must not overwrite it using an earlier absence observation. B receives precondition failure, keeps its draft, and can show the existing schedule for comparison. Real execution order decides the winner; the design does not promise that A always wins.

A possible implementation combines a unique constraint on resource identity with atomic insertion and an appropriate conditional-response mapping. Another uses storage with conditional writes. The relevant property is that a second creator cannot acquire the same absence-based permission between the check and commit. A lock inside one process may not cover multiple instances; verify the actual protected scope.

Does conditional creation make retry return the original success?

Not necessarily. Suppose A commits but loses the response. On retry, the resource exists, so the condition can fail. That does not prove the first attempt failed, nor prove that the existing object belongs to A's request. Query and compare business correlation before deciding whether it is the earlier result or someone else's object. Automatically choosing a new name after 412 may create an unintended duplicate.

If replaying the same intention should retrieve its original result, define a separate request identifier, content digest, and retention period. Create-only conditions protect an existing target from replacement; business idempotency correlates repeated intentions. They can cooperate, but neither one header nor one database insertion guarantees exactly one effect across notifications and external systems. A creation email needs its own handling for conflict and lost receipts.

A dangerous recovery is to remove the condition and repeat ordinary PUT just to obtain success. That changes “do not replace” into permission to replace. If the person chooses replacement, show the existing object, confirm the difference, and use an explicit update flow. The related article on PUT and PATCH contracts explains why full replacement and partial modification also need separate meanings.

Is recreating a deleted name the same object?

The header cannot settle this lifecycle question. After deletion, the target may again have no current representation and satisfy the condition. Old links and tasks may nevertheless interpret the reused name as the old schedule. Decide whether identity includes an unrepeatable identifier, whether deletion reserves the name, and how restoration differs from new creation.

For example, an old schedule might already have launched jobs before being deleted and recreated. If those jobs look up configuration by name alone, they can read the new schedule. A distinct creation identity, or a policy that prohibits name reuse, can avoid that ambiguity. This is an engineering choice, not a requirement to use one primary-key format for every API.

Proposed verification submits different conditional creations concurrently and checks that one creates the target while the other neither overwrites nor sends a creation notification. Then exercise a lost response, deletion and recreation, aliases, and tenant separation. Inspect the stored representation and side effects rather than counting one successful and one failed HTTP response.

Decide what happens to writers that omit the condition. A protected new client cannot preserve a resource if an older script may still overwrite it unconditionally. A create-only endpoint can require its contract, or creation and update can have distinct routes with a migration plan. Include older writers in verification instead of demonstrating only two clicks in the new interface.

No server or database concurrency test was run here. Check that the framework reads the condition, intermediaries preserve it, evaluation precedes the write, and errors retain useful recovery information. The contract is effective only when “existing means no replacement” survives from request intent through storage arbitration.
