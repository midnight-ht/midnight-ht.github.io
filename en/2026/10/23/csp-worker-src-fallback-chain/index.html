CSP Worker Sources: Follow the Fallback Chain Before Changing Policy

Distinguish directive fallback, Blob entry points, and later requests when diagnosing Worker failures.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-23 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • Fallback applies when a directive is absent.
  • Validate Blob entry points for the actual API.
  • Entry permission does not grant later requests.

A page script loading from an allowed host does not establish that a Worker entry point is allowed by the same rule. Find worker-src first. Only when it is absent does CSP fall back through child-src, script-src, and default-src, in that order. Rejection by the applicable directive does not send the browser onward to a more permissive fallback.

Missing directives trigger fallback

The MDN worker-src reference documents that order and covers Worker, SharedWorker, and ServiceWorker script sources. The CSP Level 3 Working Draft provides the corresponding directive and source-matching mechanisms. The cited draft is dated September 16, 2026; verify implementation in supported browsers. No browser security-policy experiment was executed for this article.

Suppose a page on app.example.test permits itself by default, additionally allows an asset host for page scripts, and prohibits child sources. Without worker-src, Worker evaluation reaches child-src 'none' first. The more permissive script list does not rescue it. A working page script and a blocked Worker entry can therefore coexist. This is a hypothetical policy analysis, not a production incident log.

Content-Security-Policy: default-src 'self'; script-src 'self' https://assets.example.test; child-src 'none'

This header illustrates the conflict, not a complete deployable security template. If the application genuinely needs a same-origin dedicated Worker, evaluate an explicit worker-src that separates that requirement from frame policy. Change the Worker boundary rather than opening every child resource to fix one task. Additional sources require actual build-output and trust analysis.

Explicit policy also makes upgrades easier to review. A team might previously rely on script-src because it has no worker-src. Adding child-src for frame management can change which rule controls Workers. A change appearing to affect one resource type can therefore alter another entry point. List resources relying on fallback before the change and inspect the actual response afterward, rather than leaving an implicit dependency unexplained.

Evaluate Blob entry points by their actual scheme

Suppose a bundler turns generated code into a Blob and creates a dedicated Worker from a blob: URL. The page’s main script appearing under an HTTPS asset host does not establish the Worker’s entry URL. Inspect the value used for Worker creation. If generated Blob entry points are required, evaluate an explicit policy such as worker-src 'self' blob:. This example does not assume that every browser treats Blob URLs identically under 'self'.

Allowing blob: expands the source-expression scope permitted to start Workers; it does not validate the business purpose of the generated code. If the toolchain can instead produce a maintainable same-origin Worker file, compare auditability and deployment cost. The decision should explain where executable code comes from, not merely which line removes a console error.

CSP permission cannot override the Worker API’s own restrictions. A permitted scheme is not necessarily valid for every Worker type and registration mechanism. In particular, do not generalize a dedicated Blob Worker example into a ServiceWorker registration guarantee. Record the exact API, entry URL, build strategy, and supported browsers, then validate that combination.

Does an allowed entry point permit internal fetches?

Entry permission does not grant unrestricted network access. Worker script entry and subsequent requests are different checks. Examine the applicable execution-context CSP, destinations, cross-origin rules, and server authorization separately. Ordinary network-loaded Workers and special entry points such as Blob URLs can differ in policy inheritance; identify the protected environment instead of treating one page source list as permission for every later request.

For example, a report Worker may start successfully and then fail while retrieving report data. Determine whether failure occurs at creation, dependency loading, or the data request, then inspect the rule controlling that step. Adding the data API host to worker-src may leave the actual failing restriction untouched. Relaxing a connection rule likewise cannot repair a prohibited Worker entry.

The CSP header reference details Worker policy ownership and multiple-policy behavior. Multiple delivered CSP policies also matter: adding a permissive policy does not override an existing restrictive one. Applications, proxies, and static hosting layers may all set headers. Preserve the actual header combination and identify each policy’s owner. Report-only behavior is not proof of enforced permission or blocking. The October 10 discussion of report-only rollout checks separates observation from actual enforcement.

A proposed validation set includes a same-origin static dedicated Worker, a build-generated Blob dedicated Worker, an entry from a disallowed source, and a successful entry whose data request is denied. Record delivered policies, actual URL schemes, creation results, and subsequent task outcomes. Fetch headers through the real deployment entry point so a correct local configuration is not mistaken for the version delivered by a proxy.

Policy ownership matters during rollback. An application change can add explicit Worker permission while an edge proxy still delivers an older restriction. Reverting application code may neither explain nor remove that block. Record which layer creates the final response, which adds restrictions, and when configuration caches refresh. Compare origin and public-entry headers while stating which entry users actually follow; collecting both is not authorization to bypass the intended entry.

Treat creation failure as a product state as well. If a report Worker is blocked, offer an implemented retry, smaller task, or server-generation path where available; otherwise state that the task is unavailable. Avoid indefinite preparation indicators or repeated attempts to start the same prohibited entry. A policy rejection needs user-facing handling, not only a console message. Alternative paths still require authorization and data-integrity checks.

None of those samples was executed here. Acceptance should explain which directive, through which fallback chain, governs each request, then establish whether the Worker completes its intended task. An explicit directive is a configuration change, successful startup is a runtime observation, and task completion requires its own business evidence.
