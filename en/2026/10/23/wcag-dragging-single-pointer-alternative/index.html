A Non-Dragging Pointer Route for Card Reordering

Design source-and-destination ordering that works without dragging and survives conflicts and failed saves.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-23 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • Keyboard ordering alone does not establish a pointer alternative.
  • Use the same authorization and persistence rules for both routes.
  • Verify order after reloading, including failed moves.

Keep drag-and-drop if it helps, but do not make holding and moving the only way to reorder cards. A person may be able to tap individual controls yet struggle to maintain contact while moving a pointer. Keyboard shortcuts may not solve that task on a touchscreen. For ordering, a useful alternative is to choose an object and then choose its destination, with the same business outcome as dragging.

Why is keyboard reordering not sufficient?

WCAG 2.2 Understanding Dragging Movements requires a single-pointer method without dragging for functionality that uses dragging, subject to essentiality and unmodified user-agent exceptions. It explicitly distinguishes this requirement from keyboard accessibility. A touchscreen user may not use a physical keyboard, so working arrow keys do not establish an alternative pointer route.

Dragging combines establishing a start, maintaining contact, moving to a destination, and releasing. An alternative should remove that combined dexterity requirement. Replacing dragging with a fast movement along a prescribed path may still require a precise gesture. Design around the intended function rather than reproducing every visual frame of the drag operation.

Consider an unexecuted scheduling example with twenty task cards. The user needs to move card eighteen before card three. Each card offers Move; activating it opens a destination choice. The user chooses the third card, selects Before, and confirms. Individual taps complete the task without sustained contact. The numbers illustrate a long move, not observed user behaviour.

Before confirmation, show the full intent: “Move equipment check before venue confirmation.” After server acceptance, reorder the list and report the result. If ordering saves immediately, report persistence in that flow. If there is a separate Save order action, both interfaces should initially change a pending version. Dragging must not persist immediately while the menu changes only local state under the same success message.

Up and down buttons may provide an alternative, but moving from eighteenth to third takes many activations, especially if each waits for the network. A destination selector or Move to top action can reduce that cost. The choice depends on list length, positional meaning, and required precision; the criterion does not mandate a particular menu. A three-card demonstration cannot establish that the same controls suit two hundred cards.

Does a visible destination remain a valid destination?

Suppose another editor deletes the third card while the menu is open. A cached index no longer expresses a stable target. “Move to position three” and “move before this card” are different intentions. The former can place the object beside something unexpected after concurrent edits; the latter should detect that its target disappeared. This is an engineering analysis of the example, not an interface format prescribed by WCAG.

One option is to send stable source and destination identifiers with a list version and handle conflicts on the server. Preserve the choice and request renewed confirmation after a conflict rather than silently changing its meaning. Both dragging and the menu should use the same authorization and ordering rules. A menu must not bypass a restriction such as moving only tasks owned by the current editor.

An apparently helpful Move button can still fail if it appears only on mouse hover, leaving touch users unable to discover it. A menu that itself requires a precise hold has preserved the original obstacle. Make the entry discoverable for supported inputs, distinguish similarly named destinations, and offer cancellation. Removing dragging does not remove the need to communicate the intended result.

Does freehand drawing need a destination menu too?

Do not apply a sorting pattern mechanically to every canvas function. Whether dragging is essential depends on the function: producing a particular freehand stroke is different from moving an existing object. Calling an application a drawing tool does not automatically exempt its layer ordering. List zooming, object movement, ordering, and drawing separately, then assess equivalent alternatives for each.

For acceptance, prohibit dragging and complete an end-to-start move, a move across groups, and cancellation. Reload to verify the stored order. Then test the same tasks using only the keyboard; that is a separate input dimension. When an operation fails, people need to find the affected object and the corrective action. The related article on error summaries and correction routes addresses that discovery problem.

The destination interface needs a scale strategy too. Two hundred similar titles can replace dragging difficulty with a search problem. Existing groups and searchable destinations may help, with enough context to distinguish items. Keep no search match separate from no permission, and never silently substitute a new first result when the list changes. Evaluate controllable task steps rather than the mere presence of a menu.

Also exercise lost permission, a deleted destination, a changed list version, and a save timeout. Check whether the interface distinguishes unsaved changes from a saved result awaiting refresh, preserves the previous selection, and produces equivalent results through both entry points. None of these checks was run here, and no component conformance or completion-rate improvement is claimed. A reviewable delivery runs from Move to the correct order after reload and explains each failure; a drag animation and a keyboard listener establish only part of that path.
