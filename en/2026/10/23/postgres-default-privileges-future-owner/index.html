PostgreSQL Default Privileges Follow the Creating Role

Separate existing grants from future defaults, identify the creating role, and test new tables with the intended reader.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-23 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • Defaults apply to future objects; existing grants need a separate review.
  • The current creating role determines which defaults apply.
  • Test different creators with the actual reader role.

A migration login belongs to the table-owner role, yet a newly created table still rejects the reporting account. Check the current role at object creation. In PostgreSQL 18, default privileges follow that role; membership does not combine the defaults of other roles. A repair has two separate jobs: grant what existing objects require, and establish which role will create future objects.

Defaults apply at creation

The PostgreSQL 18 ALTER DEFAULT PRIVILEGES reference limits these rules to future objects. Rules can apply throughout the current database or within named schemas. Changing a rule does not recalculate privileges on existing tables. A successful command therefore does not establish that yesterday’s table is readable.

Only the current creating role’s defaults apply. Distinguish the login, the role currently executing SQL, and the resulting object owner. A deployment configuration naming a login is insufficient: determine whether the migration changes roles before creating tables. A role change on one connection is not evidence about a fresh connection opened by the migration tool.

Consider an unexecuted example. The app schema and three roles already exist: owner_role owns tables, migrator may switch to it, and reporter needs read access. Migrator creates app.before without switching. An administrator then grants reporter default SELECT for tables created by owner_role. This does not repair app.before. If migrator subsequently creates app.after while still acting as migrator, membership alone does not make owner_role’s defaults apply.

One design standardizes creation: switch to owner_role before creating app.future and configure defaults explicitly for owner_role. Another permits several creating roles and maintains each role’s defaults. The tradeoff is how many creation identities the team must maintain. Granting everything to PUBLIC to clear the error broadens a reporting requirement into access for unrelated users.

-- Illustrative SQL, not executed; requires authority over these defaults.
ALTER DEFAULT PRIVILEGES FOR ROLE owner_role IN SCHEMA app
  GRANT SELECT ON TABLES TO reporter;
-- Existing objects need a separately reviewed grant.
GRANT SELECT ON app.before TO reporter;

The example assumes reporter already has the required USAGE on app. Table SELECT does not supply schema access. Use schema-qualified names so a search path cannot direct the check toward another table. An administrator’s successful query is not a substitute for reporter’s result.

A schema-level revoke cannot cancel a global grant

The reference also explains that schema defaults are added to global defaults. If a privilege is granted globally, a schema-level REVOKE cannot subtract it. Review where the effective privilege originates before changing either level.

Suppose reporter should read most schemas but never payroll. A global default SELECT followed by a payroll-specific revoke does not express that exception. A reviewable alternative removes the overly broad global default and grants defaults in the intended schemas, then examines existing objects separately. This is a design example, not an instruction to change an existing database without an inventory.

Object classes require their own decisions. Defaults for tables do not establish grants for sequences, functions, or every other object type. A read-only reporting contract should start with table reads. If a writing service needs sequence permissions, derive them from its actual statements and object model. A broad permission template is harder to justify than a specific business requirement.

Test the creation path that deployments use

In a disposable database, prepare an old table, a new table created by the intended role, and a control table created by another role. Record current_user during creation, the owner, the configured defaults, and reporter’s actual queries. State expectations beforehand: the old table needs an explicit grant; the intended creator’s new table should be readable; the control creator should not inherit another role’s defaults merely through membership.

Repeat creation through a fresh migration connection. This catches role switching that exists only in a manual session. Pools, migration runners, and scheduled jobs may use different entry points. Distinguish failures of schema access, object privileges, and row security. The related guide to runtime roles and RLS covers a boundary that remains after table access is granted.

Should every old table receive the new grant?

No automatic conclusion follows from changing defaults. Inventory reporter’s business scope first: historical tables may contain data excluded from reporting. Future and existing objects can share an intended policy while requiring separate actions and evidence. For a bulk repair, review the exact schema and table set and its rollback plan.

During a handover, retain the creation record rather than relying only on today’s owner field. If ownership is transferred after deployment, the final inventory establishes current ownership but cannot alone reconstruct which defaults applied at creation. Record role switching, creation statements, the migration identity, and a snapshot of relevant defaults.

Assign an owner to the creation entry point too. A second migration runner or background partition task requires a new identity check. A previous successful reader query does not validate a new creator. Review both creators and readers whenever the permission policy changes.

No roles, migrations, or queries were executed for this article. It describes PostgreSQL 18’s documented behavior and a validation design. Useful evidence connects creation identity, future defaults, existing grants, and reader results. A receipt for changing defaults alone cannot establish how the next migration will act.
