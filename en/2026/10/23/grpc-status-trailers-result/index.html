HTTP 200 Does Not Establish gRPC Call Success

Use final status, partial-result rules, and proxy observations to distinguish response start from RPC completion.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-23 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • Headers and messages do not replace final call status.
  • Using partial results needs an explicit business contract.
  • Classify completed calls once by their final outcome.

Neither HTTP 200 nor the first message establishes that a gRPC call succeeded. The application must observe the final call status and distinguish normal completion, rejection, and interrupted transport. Monitoring needs that same result layer. A proxy that counts success when response headers arrive can hide failed calls inside a healthy HTTP success rate.

Why does status come after messages?

The responses section of gRPC over HTTP2 describes headers, zero or more messages, and trailers, with a trailers-only response available for immediate errors. Status belongs in trailers even when the call completes normally. This article concerns native gRPC over HTTP/2; other browser-facing encodings do not necessarily use the same wire representation.

When a streaming response begins, the server may still have work left. A later read, authorization condition, or calculation can fail after headers have been sent. Headers show that a protocol response started; completion describes how the call ended. Treating its first message as completion removes the possibility of later failure. Renaming an HTTP metric does not add the missing observation.

Consider a hypothetical inventory service streaming availability from three warehouses. This is an unexecuted sequence, not a packet capture. HTTP 200 arrives first, followed by records for warehouses A and B. Reading warehouse C fails, and the call ends with a non-success status. The consumer has two valid messages but cannot declare the three-warehouse query complete.

An unexecuted wire sketch makes the inspection target concrete: :status: 200, then two warehouse messages, then grpc-status: 13. Here 13 means INTERNAL; normal completion can instead end with grpc-status: 0, meaning OK. Check the definitions in the gRPC status-code table. This is not a capture, and not every third-warehouse read error should map to INTERNAL; that code only illustrates failure after successful response headers. Zero establishes normal RPC completion. The application must still interpret whether stock exists; it does not establish that a transfer or stock deduction occurred.

It could buffer records until normal completion, or display them incrementally while marking an incomplete result on failure. Choose according to whether partial results are useful. If allocation must compare every warehouse, the consumer cannot silently stop after finding stock in A. A per-warehouse dashboard may retain confirmed records while explaining what remains unknown.

A complete product design includes that failure state. Suppose the page preserves two records, says “Two warehouses received; one incomplete,” and blocks allocation that requires the complete set. A retry should specify whether it reloads everything or fills the missing part. Match warehouse identifiers and query versions when merging. One fresh record combined with two older ones is not automatically a single coherent snapshot.

Is a missing trailer an implicit success?

No. A disconnect, incompatible intermediary, or server exit can prevent usable final status from arriving. Read the completion result exposed by the selected client library rather than inventing a successful default. Diagnostic tools should also distinguish a status actually received from one synthesized by the library after a transport failure. A derived result is not an original server receipt.

The monitoring path often makes this boundary visible. A gateway counts HTTP 200 at header time; the business client later observes a failed RPC. Both can accurately describe their observation, but only one measures final RPC success. Name the denominators: requests entering the gateway, calls that ended, and completed calls grouped by RPC status. A call still streaming should not be counted as successfully completed early.

An opposite failure is a server that catches every exception, reports normal completion, and puts an error string in an ordinary message. A status-based client then records protocol success. Applications can define result types, but their contract must explain which outcomes are successful calls and which require failed call status. Protocol status does not replace business meaning, and a message string does not restore an unobserved protocol result.

Can a failed stream simply be retried?

First examine what earlier messages caused. If every inventory record creates a transfer, replaying the stream may create the first two transfers twice. Even a read-only stream can influence a user’s decision before failure; specify whether new results replace or append to old ones. Define query correlation, deduplication, and retry scope rather than mapping every error to “connect again.” The protocol does not guarantee one business effect for the consumer.

A deadline introduces a separate question. The article on deadlines and downstream cancellation asks when waiting ends and whether work stops. Here the question is whether received data establishes complete success. A client timeout does not prove rollback, and normal protocol completion still requires interpretation of business results. Name both checks separately.

Proposed tests include normal completion with no messages, one message, several messages followed by failure, immediate failure, and a disconnect after headers. Record completion callbacks, message counts, final status, proxy logs, and metric classification. Route the tests through the intended intermediary: a direct connection does not establish trailer handling across the deployed path. No service, proxy, or capture test was run here, and no language-library compatibility is claimed.

Define one transition from in-progress to a measured final outcome. Counting success at headers and later adding failure can count the same call twice. Correlate each call, classify it once at completion, and observe active calls and duration separately. A long-lived stream is not a completed success sample; otherwise failures appear only when connections close and distort the time meaning of the chart.

Choose one scenario that fails after HTTP 200 and make the interface, call log, and alert agree about its outcome. If only a packet inspector knows it failed while the user sees completion, status exists on the wire but has not reached the product’s decision. Bring final status to the layer that decides success before setting success-rate targets.
