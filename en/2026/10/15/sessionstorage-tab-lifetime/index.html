Understand per-tab storage without assuming a blank initial state

sessionStorage is usually isolated by origin and page session, but a new auxiliary context with an opener can start from a copy. Use task identity to distinguish fresh work from recovery.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-25 · Estimated read 19 min
Translations
zh-CN en

Article

Key takeaways

  • Opener copying, independent later changes, and reload persistence are separate lifecycle events.
  • Bind drafts to a task ID and recovery intent; do not restore a new task merely because a key exists.
  • Storage can be denied or writes can fail, so recovery needs visible fallback behavior and scoped claims.

A new tab showing an old value does not necessarily mean sessionStorage is continuously synchronized across tabs. A new auxiliary browsing context with an opener can begin with a copy of the opener's storage; after that, each side changes independently. A reload can also retain the current page session. Neither the WHATWG HTML Standard nor the MDN sessionStorage reference says “tabs are always unrelated”; initialization depends on the page session and how the page was opened. Bind drafts to a task identity and distinguish “new” from “resume.” Do not populate a new task just because a key exists.

Partitioned by origin and top-level context does not mean blank on creation

MDN describes sessionStorage as partitioned by origin and browser tab session. Same-origin documents in a top-level page session can use that session's storage; a cross-origin embedded document uses the storage area for its own origin. This differs from localStorage, which is partitioned by origin rather than by top-level tab. “Tab-scoped” describes the boundary for ordinary parallel pages; it does not promise that every newly created page starts with all state erased.

Section 12.2.2 of the HTML Standard says session storage is copied after a new auxiliary browsing context and document are created. MDN explains the case directly: if a new page has an opener, its initial sessionStorage is a copy of the opener's; the two remain separate, and later changes in one do not change the other. There are three distinct moments: existing data is copied, the child page initializes, and both pages continue writing independently. Seeing an old value on the child's first read can be mistaken for ongoing sharing when it is only the initial copy.

Whether an opener exists depends on how the application opens the page. A scripted new window, a link with target="_blank", and a URL entered directly should not be treated as the same test condition without checking the actual relationship. If the product does not need opener capabilities, a technique that removes the opener can avoid the copy path; verify the link and browser behavior that the product actually uses. More importantly, the browser's initial copy explains where a value came from; it does not decide whether the application should use it.

A page session also survives reload and restoration, ending only when the associated tab or window session ends. Therefore, a value remaining after reload and an initial copy into a new auxiliary context are different explanations. Record the page creation method, opener state, origin, storage read/write times, and whether a reload occurred instead of writing down only “new tab.”

Two parallel orders show why task identity matters

The HTML Standard's Web Storage introduction uses concurrent purchase windows to explain session-scoped state: if every window shared one value for the current ticket, switching between windows could overwrite one purchase with another. The following extends that idea into a hypothetical workflow; it is not a real product or an executed test.

Imagine a user entering travel dates and passenger details in window A, then opening window B from an “another booking” action. If B is an auxiliary context created by A with an opener, B may initially receive a copy of A's sessionStorage. If B initializes with if (sessionStorage.getItem("draft")) restore(), it can treat A's draft as the booking B was meant to start. When the user changes the date in B, A does not automatically change, because the stores diverged after the copy. The user saw a one-time state import, not continuous tab synchronization.

The fix is not necessarily to rename draft to bookingDraftV2: if the child copies the opener's entire storage area, the new key can be copied too. A maintainable contract describes task identity, whether the user intends to create or resume, draft version, and applicability. A new-task action generates a new identity and reads only records for that identity. A resume flow requires the user to select the draft and rechecks current identity and server authorization. An unconfirmed local form should not be auto-submitted as a saved booking.

One simple design wraps each draft in a record with taskId and schemaVersion. “Create new” generates a new ID rather than reusing one copied from the opener; “continue editing” takes an explicitly selected draft ID into the recovery path. The application can keep the active task ID in route or business state and compare it with the record. If the schema version is incompatible, show a recovery choice instead of silently merging stale fields into the new model. Which fields need confirmation depends on business risk: payment method, delivery address, or a price-changing option are examples.

This does not mean every form needs a complex version system. A short form that only needs reload recovery within one tab may need only a scoped draft key and a clear cleanup point. Multiple concurrent transactions call for separate task identities and a selection flow. The decision depends on whether parallel tasks are real, whether drafts must survive reload, the cost of losing or mixing them, and whether they can be safely fetched again—not on the word “session” sounding temporary.

When to clear, and when to keep the draft

Calling sessionStorage.clear() at every page start may produce a blank new flow, but can also discard input the user expected to recover after a reload, Back navigation, or interruption. It may remove unrelated state for another feature in the same tab, such as a multi-step flow marker. On the other hand, automatically restoring every non-empty key can put an old task into a new workflow. Both policies compress distinct user intent into one “has value/does not have value” check.

A more controlled lifecycle clears a specific namespace or task after a product action: on explicit “new,” allocate a new task identity and stop reading the old draft; on “resume,” read only the selected task; after submission, abandonment, or a business-defined timeout, remove the associated draft. Before deleting a prior task, decide whether the user needs undo or a return path. If the same session carries other flow state, avoid using clear() as a substitute for scoped cleanup.

sessionStorage is not a durable persistence service. MDN and the HTML Standard say access may throw SecurityError for an opaque origin or a user-agent policy. A write may also fail when storage is disabled or quota is exceeded. If an application treats “called setItem” as proof that a draft was safely saved, it can mislead users on an exception path. The UI can state that local recovery is unavailable and allow work to continue without promising retention; important drafts may need a server-side or other persistence contract with explicit authorization, conflict, and retention rules.

Switching to localStorage is not an automatic repair. It is shared across windows and lasts longer, which can make a key collision a cross-window shared-state problem. Larger or longer-lived data may call for IndexedDB or server-side drafts, but each adds its own transaction, expiration, conflict, and identity boundaries. See IndexedDB transaction lifetime for a different persistence lifecycle. A storage API does not define when the business considers work new or recoverable.

How to verify where an old value came from—and what was not tested

Build a matrix for the product's supported browsers. Write a uniquely identified test task in window A, open window B using the actual product entry point, then record B's first read, opener state, and whether later writes are visible in both directions. Repeat with an opening method that has no opener and compare the initial value. Use non-sensitive test data; one browser's result does not establish behavior in every supported environment.

Then test reload, browser restoration, closing and reopening a tab, account switching, new-task creation, resume, and storage-policy denial. Give each case an expectation: should reload preserve the draft, does resume require confirmation, does a new task get a fresh ID, does closure end the intended session, and what does the UI say when a write fails? Also verify that child-page cleanup does not alter the opener, task A and task B do not mix, and a draft from an old schema is not silently treated as current.

These are proposed acceptance checks, not executed results. No real browser, private-browsing mode, or application code was run here, and no retention-rate measurement is claimed. If a supported environment differs from the expected behavior, record browser version, opening method, opener state, policy settings, and event order before changing the product or compatibility policy. Reading a value is not a complete recovery pass: verify whose task it belongs to, whether the current user may resume it, and whether the next write succeeds.

The implementation review can end with three questions: does this opening mean resume or create, what proves that stored data belongs to that task, and what does the user see when the browser cannot read or write storage? Answering those questions turns an old value from a browser mystery into task state that can be chosen, recovered, and tested.
