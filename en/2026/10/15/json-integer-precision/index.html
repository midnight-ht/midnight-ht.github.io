Preserve long identifiers before numeric parsing loses precision

JSON number syntax can be valid while a long identifier loses distinguishable digits. Preserve identity before conversion and verify every boundary.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-24 · Estimated read 21 min
Translations

Article

Key takeaways

  • JSON number grammar can express integers beyond the range that JavaScript Number represents exactly; successful parsing does not preserve every digit.
  • For stable identity, a string contract is usually the simplest default; modern JSON.parse reviver context.source can recover selected numeric source text, subject to runtime support and field semantics.
  • Strings, BigInt, and Number have different serialization, sorting, and client-compatibility boundaries that must be checked across the real data path.

A successful call to JSON.parse proves only that the input matched JSON syntax accepted by the parser; it does not prove that every number remains exact in the runtime. JavaScript Number has a defined safe-integer boundary, and above it adjacent integers can map to the same Number. For fields that identify an order, user, or external resource, the safest default is usually to define the field as a JSON string at the sender, instead of trying to repair it after a browser has parsed it.

JSON number syntax is not a runtime number guarantee

RFC 8259 §6 defines JSON numbers as decimal text and allows implementations to limit the range and precision they accept. It notes that integer values in [-(2^53)+1, (2^53)-1] can be interoperable among implementations that widely use binary64. The point is not that JSON cannot contain larger numeric text; different implementations may not preserve the same value for it.

In ECMAScript 2026, Number.MAX_SAFE_INTEGER is 9007199254740991. The specification defines a safe integer so that no other integer has the same Number value. It gives the example that 9007199254740992 and 9007199254740993 both evaluate to the former Number value. A syntactically valid JSON integer can therefore lose its ability to distinguish neighboring identities when converted to JavaScript Number.

This does not necessarily raise a SyntaxError. The parser can produce a Number, so structural validation continues; the mismatch is that the business needs the original decimal identity while the runtime object contains a rounded value. Calling String(value) then formats the rounded Number. It does not recover the original last digit. Number.isSafeInteger is useful for a value that has already been parsed, but it cannot reconstruct the source text that mapped to it, and it is not a substitute for an API contract.

A minimal example actually run

The following ran under Node.js v24.21.0:

const raw = '{"id":9007199254740993,"small":9007199254740991}';
const parsed = JSON.parse(raw);
console.log(parsed.id, parsed.small, Number.isSafeInteger(parsed.id));

It printed 9007199254740992 9007199254740991 false. This is a local runtime result, not a browser matrix or production API test. The source JSON's id ends in 3, while the Number prints as ending in 2; parsed.id can no longer uniquely identify which neighboring integer was present. By contrast, the maximum safe integer, 9007199254740991, remains safe according to Number.isSafeInteger.

If identity is sent as a JSON string, such as {"id":"9007199254740993"}, ordinary JSON parsing preserves every character. The cost is that consumers must honor an identity contract: define length, allowed characters, normalization, and null semantics. Otherwise one service may sort numerically, one client may preserve leading zeroes, and one validator may convert the value back to Number. For an identifier such as 000123, numeric semantics discard the leading zeroes; RFC 8259 JSON number syntax itself does not allow that integer form with leading zeroes. If an upstream first turns the identity into 123 and then serializes it, the loss happened before sending. A string can keep the zeroes, but only the business contract can say whether they are significant.

Why a traditional reviver is usually too late

The callback in the traditional JSON.parse(text, reviver) API sees values that have already been parsed. MDN warns that JSON numbers have already been converted to JavaScript Numbers before the reviver receives them and may have lost precision. If the callback sees only 9007199254740992, it cannot tell whether the source was 9007199254740992 or 9007199254740993.

The ECMAScript 2026 specification provides context.source for reviver calls on primitive source values. When a runtime implements this capability, a known field can be converted from its original decimal text to BigInt:

const value = JSON.parse(raw, (key, parsedValue, context) => {
  if (key === "id" && typeof parsedValue === "number" && context?.source) {
    return BigInt(context.source);
  }
  return parsedValue;
});

This logic was run under Node.js v24.21.0: context.source returned 9007199254740993, and BigInt preserved that value. This proves support only in the local runtime, not across browser or server-version matrices. Use the approach only when the contract confirms integer identity. Feature-test other target runtimes and keep a compatibility path. Restrict conversion to known keys and allowed numeric forms. Do not turn every number into BigInt: decimal amounts, measurements, counts, and version fields may have different type contracts.

Even when context.source is available, it supplies the source text for a value; it does not establish what that field means. Converting it to BigInt changes later arithmetic behavior. Number and BigInt cannot be mixed directly, and native JSON.stringify does not serialize BigInt by default. If output must remain JSON, define whether the value is serialized as a string, use a contractually specified custom serializer, or declare the identity as a string in the schema. Recovering a value at parse time does not mean every downstream system can represent it losslessly.

Different representations solve different problems

Representation Suitable when Boundaries to own
JSON string Identity, postal codes, account references, or codes with leading zeroes; exact character preservation matters Define character set, maximum length, validation, and ordering
JSON number kept as Number The value is used for arithmetic in JavaScript and the API restricts it to a safe range for every party The service and every intermediary must enforce the same range
context.source converted to BigInt The field is known to be an integer, the target runtime supports source context, and integer arithmetic is needed Runtime compatibility, field selection, BigInt operations, and JSON output format
Raw-token or arbitrary-precision parser The application must preserve broader number syntax or control numeric types itself Extra library, audit, version, error-handling, and schema costs

The JSON Schema Validation 2019-09 interoperability clause permits arbitrary-precision JSON numbers, and its integer type is based on a zero fractional part. That mathematical model does not force a validator or application implemented with JavaScript Number to preserve arbitrary precision. Declaring integer in a schema is not proof that a runtime stores every digit. RFC 8785's JSON Canonicalization Scheme is more explicit: its canonical number data must be representable as IEEE 754 binary64, and it recommends JSON strings for higher precision or longer integers. If data is signed, hashed, or compared after canonicalization, runtimes cannot parse a large integer independently and still be expected to produce the same canonical bytes.

A common misconception is that a database BIGINT can simply be projected into a JSON number. Exact database storage does not imply that the driver, service language, JSON serializer, gateway, browser, and client model all use the same integer type. Once one layer converts the value to Number, a later exact PostgreSQL or BigInt field cannot recover the digits. Trace the path from persistent column through the final consumer, recording input and output types and decimal strings at each type boundary.

Validate each boundary in the real identity path

An API test should not stop at asserting that JSON.parse succeeds. Identify which fields are identities and which are quantities. For identity fields, use neighboring values beyond the safe boundary, such as 9007199254740992 and 9007199254740993, and check that they remain distinguishable in serialized text, the HTTP response, server model, gateway, client parse result, logs, and a subsequent request. If the contract uses strings, test "000123" for leading zeroes, length, and invalid-character behavior. If the field is numeric, enforce the range before the first lossy conversion rather than parsing first and checking formatting afterward.

Test failure paths too. Middleware may coerce a string schema to a number; analytics storage may infer a floating type; a client may call parseInt before sorting; a CSV export or spreadsheet application may auto-convert identifiers. A screenshot of the final page will not reveal all of those changes. Send distinct neighboring IDs through write, read, serialization, pagination cursors, and resubmission, then compare every digit. One test ID that happens not to change does not prove the full range safe.

Identity ordering differs from quantity ordering. Lexicographic comparison of strings such as "100" and "20" does not match numeric order. If the product needs numeric ordering, perform it in a service with an explicitly adequate numeric type, or use a separately defined sort key. Do not force identities through Number just to sort. The API contract should say whether leading zeroes are normalized, whether case is folded, and whether Unicode digits are allowed; language defaults should not make those decisions for the business.

If historical values have already been rounded, recovery depends on another trustworthy source, such as raw request logs, the upstream system, or an audit record. The current value 9007199254740992 may have originated from multiple source strings; appending a digit or guessing from a format is not recovery. This article did not run a migration or verify a real data source. Before repair, keep evidence for the affected range, the basis for each backfill, and rows that cannot be recovered. Exact identity and identity uniqueness are separate guarantees; see PostgreSQL unique constraints and NULL behavior.

Should a long identifier be a JSON string? Usually yes when it represents identity, must remain digit-for-digit exact, and does not need arithmetic in JavaScript. For a quantity, define range, precision, and rounding explicitly. context.source is a parsing option when the target runtime supports it; it does not replace the contract, compatibility tests, or cross-service validation.
