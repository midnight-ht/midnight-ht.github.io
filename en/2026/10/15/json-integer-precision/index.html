Preserve long identifiers before numeric parsing loses precision

Preserve exact identifiers before numeric conversion and inspect every transport boundary.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-15 · Estimated read 5 min
Translations
zh-CN en

Article

Successful JSON parsing does not guarantee exact long identifiers in JavaScript numbers. Conversion can lose information before later formatting checks. For digit-for-digit business identities, preserve a string from the transport contract and distinguish identity from quantities used in arithmetic.

Syntax and precision differ

The MDN JSON.parse reference warns that numbers are parsed before reviver processing and may already have lost precision. It also describes source-aware handling for particular values. Check runtime support rather than assuming every older client exposes current examples.

Imagine reading a long order identifier as a number and then converting it to text for display and another request. The string preserves the changed value if loss already occurred. No order interface was executed and no real corruption is alleged.

Digits alone do not imply arithmetic meaning. Leading zeros, fixed width, and inter-system identity rules may require original text. Define whether the value supports calculation, ordering, or identity lookup. A string contract still needs permitted characters and length.

Reviver cannot always reconstruct lost information

A callback receiving only an already-converted number cannot infer every original digit. Source-aware handling offers another path where supported, with explicit field typing. Converting every number into a large integer can break measurement and floating-point contracts.

Inspect middleware, drivers, and logging too. A string-preserving frontend cannot repair an intermediary that first converts to a number. Trace conversions rather than checking that the final text merely looks long enough.

Verify identity digit for digit

Proposed tests cover long values, leading zeros, similar distinct identities, and repeated transport, comparing each boundary. Exact storage does not automatically supply the required ordering. No tests were run.

The interface schema and generated client should agree on identity type. Fixing display code while generated models still require numbers can reintroduce conversion in the next update.

Historical precision loss requires a trustworthy source; padding or guessing digits fabricates recovery. No migration or universal restorability is claimed. See uniqueness constraints and null values. Exact identity transfer and uniqueness need separate evidence.
