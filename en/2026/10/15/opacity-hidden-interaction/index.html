The Button Is Transparent, but Tab Still Finds It: Hiding Must Change Three Paths

opacity: 0 changes visual compositing, not pointer targeting or keyboard focus. Choose the actual state mechanism for a control, subtree, or transition, and check assistive-technology exposure separately.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-24 · Estimated read 25 min
Translations

Article

Key takeaways

  • An opacity-zero element remains in the DOM and may still receive pointer events and sequential keyboard focus; opacity alone does not communicate a hidden state to screen readers.
  • pointer-events: none handles pointer targeting only; use disabled for supported individual controls and consider inert for an unavailable subtree.
  • Choose a focus destination before hiding focused content, then check behavior during animation, after hiding, and after restoration.

Fading a submit button to opacity: 0 makes it disappear from a screenshot. If the node is still in the DOM, however, it may continue to sit above another target for pointer input and may still receive focus when someone presses Tab. The animation did not fail; the visual state changed while the interaction state did not. To decide whether an operation is actually hidden, check pointer targeting, keyboard focus, and assistive-technology exposure separately. If the action involves authorization or submission, check the business rule on the server as well; CSS and HTML attributes are not access controls.

A screenshot settles only the visual question

opacity controls the transparency of an element and its content as a whole. MDN's opacity reference is explicit about opacity: 0: the element is invisible but remains in the DOM, can still receive pointer events, and can still receive focus if it is in the tab order. It also notes that opacity does not remove the node from layout and that values other than 1 create a stacking context. MDN cautions that opacity alone should not be used to convey information to screen readers; if content also needs to be hidden from them, choose a separate, appropriate mechanism. The CSS Color Module Level 4 Candidate Recommendation Draft describes opacity as post-processing after rendering and says its value does not affect hit testing. W3C identifies this version as work in progress. “Cannot see it,” “takes up no space,” “cannot activate it,” and “is unavailable to a screen reader” are different claims; a screenshot proves none of the latter three.

Consider a side panel that fades out when closed. At the end of the animation it is transparent, but the implementation has not changed its interaction state with display: none, hidden, or another mechanism. If the panel still covers part of the page, a pointer click there may target one of its buttons; keyboard focus may continue through the panel's controls in DOM order. What the screenshot, mouse, and keyboard reveal can therefore differ. This is a hypothetical scenario derived from browser behavior, not a test of a real page or a claim that every transparent element causes duplicate submissions.

A transparent control still has three routes to it

Separate the paths that are easy to conflate. Pointer behavior asks which element receives an event at a coordinate. Keyboard behavior asks where Tab, Shift+Tab, arrow-key navigation, or scripted focus can go. The accessibility path asks whether the node remains in the accessibility tree and whether its name and state can be understood. There is also a business path: even when the client prevents interaction, the server must enforce its own authorization and request validation.

Mechanism Pointer targeting Sequential keyboard focus Accessibility and business meaning
opacity: 0 The element may still receive events It may still receive focus Does not communicate hidden semantics to screen readers or check business permission
pointer-events: none Generally removes the element as a pointer-event target The element may still be reached by Tab Changes pointer targeting only; allowed descendants and event propagation still matter
Native-control disabled The control is not interactive The control cannot receive focus Fits supported form controls; disabled values are not submitted with the form
Container inert Descendants cannot be clicked Descendants leave the tab order The subtree also leaves the accessibility tree; the attribute supplies no visual cue by itself
hidden or display: none The content is not presented as an interactive control Normally not in the focus order Not presented to assistive technologies; hidden descendants may still run scripts and form controls may still be submitted
aria-hidden="true" Does not change pointer behavior by itself Does not block keyboard focus by itself Removes content from the accessibility tree; must not wrap focusable content

This is not a recipe to combine attributes indiscriminately. The MDN pointer-events reference states that pointer-events: none does not automatically remove an element from sequential keyboard navigation. If a still-focusable subtree is then marked aria-hidden="true", a keyboard user may still reach controls that a screen reader no longer reports. MDN's aria-hidden reference explicitly warns against applying it to a focusable element or an ancestor of one. Fixing one route does not establish that the other two changed.

Choose a real state for the intended scope

If one Save button is temporarily unavailable while a request is in progress, and it is a native button, consider using the native disabled attribute along with visible waiting or disabled feedback. It prevents the normal user interaction with that supported control and exposes the state through native semantics. But a disabled form control does not participate in form submission. If the request depends on that button's name or value, do not assume that setting the attribute leaves the submitted data unchanged. The MDN disabled reference lists supported controls and describes the focus and submission boundaries. A native attribute also does not stop a forged request at the server.

If an entire background region must be unavailable while a modal dialog is open, consider making the corresponding subtree inert and moving focus into the dialog. The MDN inert reference says that an inert element and its flat-tree descendants cannot be clicked or focused and are removed from the tab order and accessibility tree. inert itself has no reliable visual cue. The WAI-ARIA modal dialog pattern calls for focus to move into the dialog, for Tab navigation to remain within it, and usually for focus to return to the invoking control when it closes. Setting aria-modal="true" alone does not implement that behavior; MDN describes aria-modal as semantic communication for assistive technologies, not a script that blocks background interaction.

If content is simply irrelevant for the moment, hidden or a layout mechanism may better match the intended state. MDN says hidden content is not presented to users, including screen-reader users, but a CSS display: block rule can override the rendering of the HTML hidden attribute. Collapsible content intended to be revealed by Find in Page can use the distinct hidden="until-found" behavior. Hiding also does not freeze scripts or form logic: MDN notes that scripts in hidden descendants can still run and form controls may still submit, so business behavior needs its own rule. By contrast, aria-hidden is often appropriate for redundant or purely decorative content, not as a way to switch off a button that remains visible or keyboard-reachable. Before choosing, write down whether the requirement is “ignore pointer input,” “operation unavailable,” “not currently presented,” or “everything outside the modal is unavailable,” then verify the actual effect.

Closing a drawer is a state transition, not one style declaration

Breaking a side drawer's close behavior into states can expose gaps that a single CSS rule misses. The following is an implementation approach, not browser-tested component code:

  1. When the user starts closing the drawer, decide whether its operations become unavailable immediately. If they do, change the relevant interaction state at that point. Waiting until transitionend to make the controls inert leaves an interval during which the animation is running and the controls still work.
  2. If focus is inside the drawer, move it to the opener or to the next logical location before the drawer becomes unavailable. Otherwise the drawer may visually leave while the user's next keyboard action has no clear, visible destination. If the opener no longer exists, choose a real workflow destination rather than restoring focus to a stale reference.
  3. Make the visual feedback explain the transition. If interaction is already locked while the panel continues fading, ensure the fading state communicates that it is closing or unavailable. The HTML Standard also cautions that an inert subtree should be visually obscured and should not contain content critical to understanding or using active content.
  4. Once the animation is done, perform any layout cleanup, such as setting hidden. When reopening, restore the lifecycle in the opposite direction: present the content, remove inert or disabled if it is now available, and then place focus where the task expects it. Restoring the old focus target depends on why the drawer closed and what the reopened task is; it should not be a blind replay of a stored DOM reference.

A revealing counterexample is setting aria-hidden="true" on the drawer root as soon as closing starts, without moving focus or blocking interaction. The panel remains visible as it fades; keyboard focus may still move through its controls, while a screen reader no longer reports them. The three routes now describe conflicting states. Another counterexample is applying pointer-events: none to a container while a descendant explicitly restores pointer targeting; MDN notes that events targeted at such a child may still travel through parent listeners. These cases are diagnosed from the DOM and actual event path, not by guessing from a CSS property name.

Verify the transition as well as the final frame

The following is a proposed test matrix, not testing performed for this article. For a control changing from available to unavailable, record the starting focus, the action that starts the transition, behavior mid-animation, final state, and focus after restoration:

Check Evidence to observe Common omission
Mouse or touch Actual target and action when pressing where the panel used to cover Checking only after transparency reaches zero and missing the transition window
Keyboard Tab/Shift+Tab order and visible focus indicator Relying on pointer-events and forgetting that it does not alter Tab order
Assistive technology Name, role, state, and whether the control remains discoverable after hiding Checking only DOM attributes without listening to screen-reader output
Focus relocation Focus before closing and whether it lands on a logical next step afterward The panel disappears while focus remains on a descendant or jumps to the page start
Restoration Whether reopening restores the right interaction and focus The visual panel returns while disabled/inert remains, or focus lands in the wrong place
Modal background Whether background controls can be clicked or focused while the dialog is open, and where focus returns Setting only aria-modal without actually limiting background interaction

During debugging, browser developer tools can help inspect document.activeElement, DOM attributes, and computed styles, but each proves only one part. The accessibility tree and actual keyboard behavior still need checking in the target browser, input mode, and assistive-technology combination. Automated assertions should name whether they test the DOM, focus, or the user's visible state. No browser, screen reader, or application component was tested for this article, so it does not establish conformance to a complete accessibility audit.

A useful selection order is: use native disabled for one supported form control that is temporarily unavailable, with a clear state cue; use inert for a whole unavailable region, with visible indication; use hidden or a layout state when content truly should not be presented; reserve aria-hidden for removing redundant or decorative material from the accessibility tree, and never wrap focusable controls with it. For modal interaction, verify focus entry, confinement, exit, and restoration as a complete behavior. For animation, state explicitly which interaction changes at the beginning and which layout cleanup occurs at the end. For reduced motion, see reduced motion and state feedback; changing animation does not substitute for interaction state. Transparency changes the pixels; the chosen behavior still has to determine whether a person can act.
