Validate redirect destinations as a navigation trust boundary

Prefer server-side destination mappings; when URLs are necessary, validate parsed components and keep navigation policy separate from authorization.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-25 · Estimated read 23 min
Translations
zh-CN en

Article

Key takeaways

  • Use server-side destination IDs instead of complete URLs when the destination set is finite.
  • Parsing supplies structure; policy must still approve scheme, origin, port, and any required path.
  • Navigation approval does not grant resource access; invalid targets need a fixed safe landing page.

A login page on your site does not make the next destination trustworthy. A returnTo, next, or redirect parameter influences where the browser goes, so the application must decide whether that destination is allowed before writing it to Location. Prefer a server-maintained mapping from destination IDs. If the product truly needs URLs, parse them with semantics compatible with browser navigation, approve the protocol, normalized origin, effective port, and any required path, then redirect using the same validated result. Authentication proves identity; destination policy constrains navigation; the destination page must still check access.

Name the boundary: navigation is not password verification

OWASP describes an unvalidated redirect as an application accepting untrusted input and redirecting to the URL in that input. One risk is phishing: a link begins at a familiar site, but after sign-in sends the user to an attacker-controlled page. The trust attached to the entry point is lent to the next hop. This article concerns browser navigation. If the server itself fetches a user-supplied address, that is a separate network boundary and requires separate controls.

A login flow contains at least three decisions. First, did the credential or identity provider authenticate the user? Second, may the application navigate to the requested destination? Third, may this user access the feature and object at that destination? They can happen in one request chain, but should not share one boolean decision. For example, /admin/reports may be same-origin and still be forbidden to an ordinary user. Conversely, a user may be allowed to use a feature while an unapproved external domain remains an invalid destination.

This separation also affects error handling. Failed authentication must not execute the successful-login redirect. A rejected destination can use the product's safe default. An authorization failure at the destination belongs to that page or API. If all three cases become “bad URL,” logs cannot distinguish credentials, navigation policy, and object access.

When destinations are few, a mapping is simpler than a full URL

Imagine a hypothetical product with three legitimate post-login destinations: the personal workspace, a task list, and organization selection. The client submits destination=tasks; the server maps that identifier to a fixed local route and creates the response. The caller can submit only a short identifier, not an arbitrary https://… URL. OWASP likewise recommends, where possible, accepting a short name, ID, or token and mapping it server-side to the full destination. It also warns that such identifiers should not become an enumerable directory of redirect targets.

A mapping is not just a dangerous string with a new name. It needs a clear product contract: which destination each ID represents, who maintains it, and which entry points may use it. In a multi-tenant application, “organization selection” may be a valid destination, but a submitted tenant ID should not be appended to a route without verification. The mapping answers “which kind of page?”; the session and target API still answer “may this person access this organization?” Guessability is not the only concern. If an attacker learns a valid ID, whether it reveals sensitive information, changes authorization, or leaves the site determines whether the identifier must also be bound to a session, purpose, or one-time state.

A full URL can be necessary: perhaps a product supports several reviewed identity-provider callbacks, or a controlled workflow carries a return address. Then the required artifact is not a string that “looks like ours,” but a finite destination policy. If that policy cannot be described as a small, auditable table, revisit whether arbitrary URLs are actually required.

Parsing exposes structure; policy decides what is allowed

The current Node.js URL documentation describes the WHATWG URL class as exposing components such as protocol, hostname, port, pathname, search, and origin. Relative input requires a base; absolute input ignores it. The documentation also advises checking the resulting origin when the input might be absolute, even if a base was supplied. A parser helps the application and browser interpret the string consistently; it does not choose the application's allowed schemes, hosts, or paths.

Suppose the site is app.example.test and the code checks only whether the raw text begins with that string. https://app.example.test.attacker.invalid/ has that textual prefix while its actual host is different. A URL containing userinfo, such as https://app.example.test@attacker.invalid/, can also make the host and username easy to confuse. OWASP explicitly rejects raw prefix or suffix matching. It recommends a maintained URL parser, checks for scheme, canonical host, and effective port, and path constraints when needed; it also recommends rejecting userinfo and ambiguous inputs. These are hypothetical explanatory strings; no links were sent or tested against this site or another system.

If the product allows only local relative paths, require the parsed result to have the fixed site origin and constrain it to the intended page set. Passing an input to new URL(input, siteBase) does not automatically make it local: absolute URLs ignore the base, and network-path references can resolve to another origin. Read and validate the parsed result rather than serializing it and applying a second interpretation before creating Location. Otherwise the value approved during validation may differ from the value in the final response. For approved external destinations, enumerate the scheme, origin, port, and permitted path instead of merely checking HTTPS or whether the hostname contains a company name.

Walk through a hypothetical login flow

Assume a user opens /login?returnTo=..., and the server copies the parameter directly into a 302 response after successful authentication. If the value names an external address, the browser leaves the product. There are two design choices. If only three fixed pages are valid, change the input to destination=tasks, look it up server-side, and produce a constrained local response. If an external integration callback is needed, parse the candidate with a URL API compatible with the final response, check https:, the exact normalized origin, effective port, and the integration's allowed path, then use the parsed target to construct the redirect. An unknown ID, parse failure, or policy mismatch goes to a fixed local default; do not try to “repair” the original string.

The two options have different operational costs. A mapping is easy to review and roll back, but adding a destination needs a code or controlled-configuration change. An external allowlist supports more destinations but requires an owner for domain migrations, subdomains, ports, paths, and exit notices. If users can save an address in their profile, distinguish “saved” from “approved for every future login.” A destination change may need renewed confirmation. If a mapping token carries temporary authorization data, logging the complete parameter could expose it. A log may need a policy ID, decision, and rejection category without the raw query string.

An external-destination confirmation page can clearly state that the user is leaving the site and require an explicit click. OWASP lists this as one option, but it is not suitable for every workflow and does not repair an incorrect authentication callback configuration. OAuth or OIDC callbacks need the protocol's registered redirect URI matching rules. A normal post-login returnTo allowlist neither replaces nor is replaced by identity-provider configuration.

Define a safe failure destination

A rejected destination should not be sent through unchanged or inserted into another unvalidated link on an error page. A fixed local landing page can explain that the return location is unavailable and let the user navigate to a familiar page. If a flow must preserve a transaction or form, design a recoverable state ID or draft recovery at the business layer. Do not preserve every input by storing an arbitrary URL and sensitive query data unchanged in the client.

Keep the policy result explicit: approved target, rejection category, and fixed fallback. Logs can then distinguish an unmapped ID, origin mismatch, or lack of permission for the requested feature without recording the full URL. Overly vague logs prevent investigation, but logs should not capture password-reset tokens, one-time codes, addresses, or other sensitive values that may appear in a query string. Actual fields depend on the application's data classification; this article did not audit a real logging implementation.

How to verify the policy rather than one startsWith assertion

Build a test matrix around request input, parsed result, policy decision, and final response Location, with an expected result for every case. Include a mapped destination; an unknown ID; a local relative path; an absolute external URL; the same hostname on a different port; a URL with userinfo; invalid or empty input; an approved integration path and a neighboring unapproved path; and middleware that might rewrite the destination after validation. Check the final destination, not only whether a helper returned true.

Add a same-site but unauthorized destination: navigation policy may approve it, while the next page must still deny access. Also check that failed authentication does not trigger the success redirect, that a rejected destination uses the expected fixed fallback, and that logs omit raw sensitive parameters. These are proposed acceptance checks. No tests were run here, and the article does not claim the implementation has blocked attacks.

When compatibility problems appear, identify which business path truly needs a full URL and allow only that path under a documented policy. Do not globally permit every origin because one old client sends an absolute URL. A known legacy format could be converted within an explicit version window, while unknown forms use a safe default. Monitoring rejection categories and client versions can help operations, but a falling rejection count is not direct proof of better security; it could also mean detection was bypassed or usage changed.

A practical decision order is: Is the destination set finite? If so, use a mapping. Who owns external allowlist changes, and can they be reviewed? If nobody does, do not support arbitrary destinations. Could a valid destination still read another user's or tenant's data? If so, enforce object-level authorization at the target API. For URL base and path semantics, see URL directory boundaries and base parameters; for permissions after authentication, see Does replacing order numbers with UUIDs prevent unauthorized access?.

The review question can be reduced to four points: who supplied the return destination, what evidence lets the server approve it, how does the same validated value reach the response, and who checks resource authorization after arrival? When all four are explicit, the redirect is an auditable navigation feature. If one is missing, record an unresolved boundary instead of treating “the request began on our site” or “it uses HTTPS” as the decision.
