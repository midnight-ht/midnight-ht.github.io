Make pre-submission review editable without restarting the journey

Preserve task identity and dependent answers during pre-submission correction.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-15 · Estimated read 5 min
Translations
zh-CN en

Article

A pre-submission review should help users find an error, edit it directly, and return to review. Displaying answers again while requiring an entire journey restart is not effective correction. Distinguish review, editing, and final submission.

Editing needs a return path

The GOV.UK Design System Check answers pattern recommends retaining the original question and answers, then returning to review without repeating unrelated steps. Ask newly relevant questions before returning when an edit changes dependencies. Display unanswered optional questions explicitly rather than implying lost data.

Imagine correcting a booking date. Lost previous selections or repeated unrelated pages can make the user unsure whether they are editing the same application or creating another. This example was not executed and alleges no actual duplication. Preserve task identity, not just a back link.

Label edits so users know which answer they change. Repeated context-free controls leave meaning dependent on position. Page semantics and accessible names should identify the actual object.

Reassess dependent answers

Switching from an individual to an organizational application can invalidate old answers and require new questions. Hidden fields are not necessarily current confirmed intent. Decide what becomes invalid, what remains, and how the change is explained.

Conversely, clearing everything turns a small edit into unnecessary repetition. Model dependencies rather than describing all correction behavior as going back one page. No universal component is claimed to make those product decisions automatically.

Bind consequences to the intended action

Review and final submission need distinct commitments. Editing, refreshing, or returning must be interpreted against the real server-side task state rather than automatically repeating submission. Control text and result messages should describe the actual consequence.

Proposed checks include individual edits, newly relevant questions, optional omissions, return, and refresh, checking answers, identity, and final state. They were not run, and no completion-rate results are offered. See handoff responsibility beyond a successful page. Correction succeeds when the right intent reaches the submission boundary.
