An editable review page is a transaction-state problem, not a navigation problem

An editable review must preserve the same task, recalculate invalidated answers and separate final submission from browser history, refreshes and retries.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-24 · Estimated read 30 min
Translations
zh-CN en

Article

Key takeaways

  • Editing should resume the same task and preserve unaffected answers; browser history is not business state.
  • When an edit changes later questions, recalculate dependencies and explicitly invalidate answers instead of keeping or clearing everything.
  • Review, save and submit are different states; server-side version checks and idempotency handle concurrency and retries.

Clicking “Change” on a review page looks like navigation. The system actually has to answer three questions: which task is being edited, which existing answers are still valid, and when submission really occurs. Here, “transaction state” means the application's business lifecycle from entry to confirmation, not specifically a database ACID transaction. Preserve the task and unaffected answers, explicitly recalculate any later questions that depend on the edited field, and make final submission a separate server-confirmed state transition. Browser back, refresh and network retry cannot substitute for that business rule.

A review page is more than a read-only summary

The GOV.UK Design System Check answers pattern recommends a review page before final confirmation, a clearly identified Change link beside each answer, pre-populated answers on the original question page, and a return to review after editing. If a change makes new questions relevant, ask them before returning. Show skipped optional questions as “Not provided” so an empty value does not look like lost data. For very large transactions, section-level review may be worth considering, but its usefulness should be tested with the people completing the service.

A route change alone does not solve the problem. Imagine an applicant who first selects “individual,” enters a name, contact details and address, then changes the applicant type to “organization” on the review page. The system now needs an organization name and registration number. A sound outcome is neither to make the person refill everything nor to combine personal-application answers with organization fields and send them as-is. Preserve contact details that still apply, mark type-dependent answers for review, ask the new questions, then render a review of the current version. The case is illustrative, not a flow implemented or measured on this site; it makes no claim about a measured change in error rate.

At the engineering level, distinguish task identity, answer data and workflow state. Task identity says which application is being edited. Answer data stores each field value, its origin and version. Workflow state says whether the application is being completed, ready for review, waiting for more answers or already submitted. If these concepts exist only in browser history, clearing storage, switching devices or opening a second tab changes what “back” means. Pages can be reconstructed; the server-side task record determines whether the task is editable and whether it has been submitted.

One possible state model is draft, review_ready, needs_more_answers and submitted. These are not a standard or a description of a deployed system; they are prompts for defining valid transitions and actions. For example, review_ready could mean that required fields passed the current rules and may be reviewed. It does not mean the user authorized submission. A review request reads that version; an edit request carries a task ID and version observed by the user; final submission is a distinct explicit action. This keeps browsing, saving and confirming from collapsing into one generic “Continue.”

Which answers should remain, and which need review?

Do not equate “keep saved data” with “every old value remains valid.” A dependency graph makes the relationships clearer: applicant type controls which questions appear; country can affect address format; a delivery option can reveal a time slot. After an upstream answer changes, recalculate which questions apply and which answers still address the current task. A name or phone number might remain usable. Personal identity evidence might no longer apply to an organizational application and should be removed, isolated or explicitly reconfirmed according to the domain rules. A hidden field still present in JSON is not proof that the user confirmed it for the current application.

It is safer to define invalidation policy explicitly than to clear fields from scattered page components. Each answer can be associated with applicability conditions, its last edited version and a validation state. In a hypothetical rule, changing applicant_type from individual to organization keeps contact_email, marks personal evidence as no longer applicable, adds organization-registration questions and invalidates the current review version. After the new questions are answered, generate a new review page. If the domain cannot determine whether a value still applies, show “check this answer” and ask for confirmation instead of silently presenting an old state as a new choice.

Invalidating and retaining data have consequences. When an upstream choice makes downstream answers obsolete, tell users what needs to be completed again; if you keep a value to reduce work, label it “needs confirmation” on both the page and the server. Conversely, clearing the entire form after every edit turns a small correction into re-entry and may discard information the user meant to keep. For each field, decide: does it depend on the changed answer, can it be reused safely, does it need confirmation, and how will the user see that decision?

Review, save and submit are separate actions

A review page should display the version that would be submitted, but merely displaying it should not change business state. Saving an edit is not submission: it updates a draft and returns the task to a reviewable state. Final submission must recheck on the server that the task is still eligible, the current version remains valid, dependent questions are complete and the caller is authorized. The GOV.UK example separates confirmation text from an explicit “Accept and send” button. In an implementation, that visible commitment should map to a clear server action; page rendering should not trigger it.

A common counterexample is a double-click, or a request that reaches the server while its response is lost and then gets retried by the browser. Disabling a button prevents some repeated clicks, but it cannot prove the server executed only once. If submission creates a record, takes payment, sends a notification or starts an external job, the server needs to recognize duplicate requests. One common design associates an idempotency key for a deliberate submission with the task, request content and result; a retry using the same key returns the existing result instead of repeating the side effect. Scope, retention and conflict handling depend on business constraints. Adding a UUID alone does not prove every system is safe.

Concurrent edits are another easy failure to miss. A person opens task version 12 in two tabs. Tab A edits the address and saves version 13. Tab B still has version 12 and edits the phone number. If the server accepts B’s whole stale form unconditionally, it may overwrite the newer address. A write can include expected_version=12 and be accepted only if the current version is still 12. If the current version is 13, return a conflict so the user can refresh and choose how to merge. Field-level saving is another option, but adds comparison and merge complexity. Choose based on whether fields depend on one another and the cost of a lost update. This transaction is illustrative and has not been run; it is not claimed as the only approach for a database or framework.

For consequential actions such as payment or application submission, also handle “the page says success but nothing was submitted” and “the task was submitted but the success response was lost.” The server should rely on task state: after first success, change the state to submitted and record the outcome; a repeat request follows a defined policy instead of creating a second application. If the database write is followed by a message, account for the failure window between the two: the application may be saved without the message, or a message could go out while the transaction rolls back. A transactional outbox and retryable consumer are possible choices, not mandatory components for every simple form. Use them when cross-resource side effects and recovery requirements justify their complexity.

Validation cannot live only in the browser

Browsers can give prompt format feedback, but the server still needs to validate submitted data. The W3C WAI forms-validation tutorial explicitly says client-side validation alone does not ensure security and server-side validation is also needed; custom controls also need accessible notifications. For a review page, “the user saw the right answer” is not a trust signal. The server should validate required fields, branch conditions, permissions and answer versions against the task’s current state. After switching from an individual to an organization, the organization fields must apply to this task and be confirmed; checking only whether an organization_name field exists in the request is insufficient.

A task ID is not an authorization credential. If replacing /applications/123 with /applications/124 allows one user to read or edit another application, hiding the address in the interface has not fixed the risk. OWASP API1:2023 identifies manipulating an object ID to access or modify another person’s object as a broken object-level authorization issue, and recommends checking the current user’s permission for every operation that receives an object ID. Reading a review, saving a change and submitting all require object-level authorization for the current user and role. Hidden form values, stale session state or a client-supplied answers_checked=true must not be treated as authorization. Request state communicates intent; the server reads and validates the authoritative state.

Interaction text is part of correctness too. Repeated “Change” links should identify the answer they affect. GOV.UK’s example uses visually hidden supplemental text to distinguish links. W3C guidance on labels and instructions distinguishes information visible to everyone from programmatic relationships. A name available to assistive technology does not automatically replace instructions visible to all users. For a complex form, visible link text such as “Change organization name” may be clearer; if visual design requires a shorter label, provide an accurate programmatic name and verify the keyboard, screen-reader and magnified paths. Mark unanswered optional items explicitly so an empty value is not mistaken for an unsaved answer or a deliberate confirmation that it is blank.

Test failure paths, not just the happy path

A useful acceptance matrix should include at least the following state changes. The matrix below is a proposed test plan, not a report of tests run against an application:

Scenario Expected check
Edit a field with no dependencies Task ID remains the same; other answers persist; saving returns to the current review version.
Change a branching answer Dependencies are recalculated; obsolete values are not silently submitted; new questions are completed before review.
Save an old version from two tabs The later write sees a version conflict or follows an explicit merge rule; no silent overwrite.
Retry after a submission timeout The user sees a recoverable state; the same submission does not repeat side effects.
Expired session, account switch or replaced task ID Reauthentication or rejection; no unauthorized read or submission.
Optional omission, invalid format or server rejection The page identifies the field and next action; safely saved answers are not unnecessarily lost.

Test server state and visible feedback, not only that “the page returned 200.” Compare task versions, answer applicability and submission records before and after edits. In fault-injection tests, distinguish a request that never arrived from one processed whose response was lost, duplicate messages and a stale-version write. For highly dependent answers, generate cases from a rules table. Test data should distinguish “not applicable,” “not answered,” “needs more information” and “intentionally left blank”; representing all four as an empty string hides product errors.

At the page level, verify that each Change link names the right item, the returned question is prefilled, new questions appear before review when needed, and a successful submission shows confirmation rather than an editable draft. When keyboard or screen-reader checks are required, record the actual browser, assistive technology and steps. None of these checks were run for this article. It therefore makes no conformance claim and reports no measured change in error rate, completion rate or duplicate-submission rate. W3C guidance informs the checks; it does not certify this page.

When should all answers not be placed on one final page?

For a short transaction completed by one person, a single final review may be straightforward. A large application with many sections may benefit from a review at the end of each section, so users do not discover an early mistake only at the end. A task completed by multiple people needs clear rules about who can view, edit and confirm another person’s answers. GOV.UK suggests testing section-level review when different people complete parts of a large transaction; it does not claim one layout works for every service. Highly sensitive data or an edit with an irreversible effect may require confirmation or undo at the point of action, rather than relying only on a final overview.

Before choosing a layout, map the states and permissions: which roles edit which fields, which answers depend on earlier choices, which edits need someone else’s confirmation, and when an external side effect occurs. If answers are independent, the task is short and submission can be undone, a simple summary may be enough. If dependencies or participants make the state complex, partition the review and define transitions before choosing a component. Whatever the layout, each current answer should be traceable to the task, version, applicability and person who confirmed it.

How does editing fit into the rest of a service journey?

An edit path answers how this interaction continues; it does not define ownership, state or confirmation across team handoffs. A multi-person process also needs a named next owner, a way to expose missing information and a timeout policy. Handoff responsibility beyond a successful page covers the broader boundary; this article focuses on one task between review and submission.

Use one concrete question to check the design: when a user sees the review page a second time, can the system prove it is the same task at its current version and that it has not been submitted? If not, define server-side identity, version and state first. Do not ask the browser’s back button to repair missing business state.
