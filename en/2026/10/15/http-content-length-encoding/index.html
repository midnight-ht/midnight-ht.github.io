Why can a decompressed body differ from Content-Length?

Response headers report octets at a representation layer; content coding, HTTP/1.1 framing, and JavaScript string length are different quantities.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-25 · Estimated read 19 min
Translations
zh-CN en

Article

Key takeaways

  • Label the representation layer, processing stage, and unit before comparing lengths.
  • HTTP/1.1 Transfer-Encoding frames a message; Content-Encoding describes a representation.
  • Transfer completion, decoding, parsing, and saving are separate outcomes.

A Content-Length value may differ from the length of a decompressed body without indicating a transfer failure. The field measures the selected representation in octets; when Content-Encoding is present, related metadata normally describes the encoded form. An application that decodes the response observes a different byte sequence or string unit. Message framing adds another layer: HTTP/1.1 Transfer-Encoding must not be confused with content coding. Before comparing two numbers, identify the object, processing stage, and unit each one measures.

Label the layer before comparing lengths

“Body size” is often used for several different things: representation bytes before content coding, representation bytes after applying gzip or Brotli, an HTTP/1.1 message body with chunk markers, decoded bytes at the client, or a parsed string, record set, or object count. These values may be related by transformations, but they are not the same measurement.

RFC 9110’s Content-Length definition defines a non-negative decimal count of octets for the associated representation data. When the representation is transferred as content, that value can also delimit the content. When no content is transferred, the field can indicate the selected representation’s current length. It is therefore imprecise to describe the field as “the total number of bytes that crossed the network”: TLS records, TCP/IP headers, and link-layer overhead are outside what this field counts.

Content-Encoding is representation metadata. The MDN Content-Encoding reference explains that, unless stated otherwise, metadata such as Content-Length refers to the encoded form when a content coding is present. The receiver uses the coding information to recover the content format. By contrast, HTTP/1.1 Transfer-Encoding describes how the message is transferred and framed on that hop. RFC 9112’s framing rules explicitly distinguish it from representation coding. The names are similar; the layers are not.

Follow five values through one compressed download

Imagine a downloadable text report. Let A be its representation bytes before content coding, B the representation bytes after the server applies gzip, C the chunk-size lines and delimiters in an alternative HTTP/1.1 chunked framing branch, D the bytes the client has after removing the content coding, and E the JavaScript string’s length after text decoding. These are variables for reasoning, not measurements from a particular file or compression ratio.

If a response uses Content-Encoding: gzip with Content-Length framing, the field normally corresponds to B, not A, D, or E. A server may instead choose HTTP/1.1 chunked transfer coding: its chunk-size lines and CRLF delimit the message body. RFC 9112 says the terminating chunk identifies completion and prohibits sending Content-Length alongside Transfer-Encoding. Treat this as a separate framing branch, not a companion header on the first response. A captured byte stream may include framing that a client library has removed before exposing text through response.text(). Do not compare a packet tool’s byte count with a header value until you know whether the tool decoded the representation or removed chunk framing.

E has another unit. JavaScript String.length counts UTF-16 code units. It does not count UTF-8 bytes, and it does not always equal the number of Unicode characters a person perceives. A single 😄, for example, has a JavaScript length of 2 but is one Unicode code point. Passing it to TextEncoder produces a byte array containing its UTF-8 encoding. Thus D and E, though derived from the same decoded content, are not expected to have equal numeric lengths.

A common false alarm occurs when a downloader stores Content-Length as “expected bytes,” a page uses response.text().length as “received bytes,” and a monitor calls any mismatch corruption. That compares B with E. For a content-integrity check, compare at the same representation and byte boundary. If the business requirement is a text length, first define whether it means Unicode code points, grapheme clusters, UTF-16 code units, or encoded bytes. Different goals require different checks.

No Content-Length is not the same as a truncated response

A server generating or streaming content may not know its final size when it sends the headers. Chunked framing lets an HTTP/1.1 sender send pieces; the receiver recognizes the final chunk to know that this framing completed. The absence of Content-Length alone does not mean there is no body or that the message has no completion boundary. The same RFC also says a response is incomplete when a valid Content-Length declares more octets than arrived, and a chunked message is incomplete if its zero-size terminating chunk never arrives.

Unlike its HTTP/1.1 predecessor, HTTP/2 does not use chunked syntax. MDN’s version notes say that HTTP/2 can infer content length from DATA frames, so the field may be redundant while still appearing for compatibility. If tools, proxies, and application logs observe different protocol layers, their “received bytes” may not share a definition. When lengths disagree, record the protocol version, content coding, transfer coding, status, request method, and read API before deciding where the stream ended.

HEAD is an easy counterexample to misread. MDN’s HEAD reference says a successful response has no body. RFC 9110 nevertheless permits a Content-Length field, provided its value equals the number of octets that would have been sent as content for the corresponding request using GET. The header therefore does not mean that the HEAD message carried those bytes, nor does it guarantee that a later GET will select the identical negotiated representation or cache state. It is metadata, not a downloaded and verified file.

Choose separately for progress, integrity, and resource budgets

If a UI is meant to show transfer progress, the numerator and denominator need a defined, matching transfer measure. A percentage with a denominator is justified only when a trustworthy expected length is available. If the total is unknown, show indeterminate progress instead of quietly switching to decoded size. Even a completed transfer says nothing by itself about decompression, character decoding, JSON parsing, or local persistence. Separate those states so a failure points to the stage that needs a retry or correction.

For a decompression or parsing resource budget, B is not enough. Also constrain decoded bytes D, parsed object counts, or application-specific nesting depth. It is an engineering recommendation, not a universal safe limit. Content coding can expand a small transfer representation into a larger resource, but the amount depends on input and algorithm; no ratio was measured here. Implementations should accumulate limits at the actual decode and parse boundaries and stop when configured business limits are exceeded. With streaming APIs, also verify that backpressure, cancellation, and exceptions release temporary buffers.

For file identity or integrity, Content-Length answers only a length question, not whether the bytes belong to the expected file. Different files can have the same size, and an incorrect header can disagree with the content. An application protocol may use a digest, signature, version identifier, or business validation and should state whether it covers the pre-encoded resource, encoded representation, or downloaded file. The checksum must be computed at the agreed boundary: a digest of the original resource cannot be directly compared with a digest of gzip bytes.

Verify units without presenting a plan as a result

Build a small repeatable fixture for the target client: serve the same text as identity and gzip representations; include ASCII, multibyte CJK text, and a supplementary-plane emoji; then test a known length, HTTP/1.1 chunked framing, HEAD, an early connection close, a missing terminator, and a decoding failure. Record headers, protocol version, raw or decoded data exposed by the library, TextEncoder byte count, string length, parse result, and save state in separate columns. The aim is not to make all columns equal; it is to confirm that each follows its own definition.

The failure checks matter. If a response declares length L but fewer octets arrive, does the client mark it incomplete and discard or quarantine the partial file? If chunked framing is used, does a missing terminator cause rejection? If a complete response contains invalid JSON, is the failure attributed to parsing? If HEAD and a later GET report different lengths, are content negotiation, caching, and resource version checked before concluding that a request violated the protocol? Browsers, proxies, and HTTP client libraries expose different observation points, so bind acceptance results to the real version and call path. No download or cross-client test was run for this article; the checks above remain a proposed plan.

In implementation and logs, give metrics names that include both unit and stage, such as “encoded representation octets,” “decoded UTF-8 bytes,” and “JavaScript UTF-16 code units.” Then decide which one supports progress, resource protection, or business integrity. If all of them are still called body size, a team will keep treating different quantities as one total. For the related boundary where metadata describes a request with no response body, see the site’s HEAD metadata and GET-body verification.
