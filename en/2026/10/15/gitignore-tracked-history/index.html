A Path Is Still Tracked After .gitignore: Separate Rules, Index, and Worktree

A .gitignore rule applies to untracked paths. Check the index and worktree separately before choosing whether to untrack a file, keep local configuration, or respond to an exposed secret.

Updated 2026-11-24 · Estimated read 19 min

Article

Key takeaways

  • Ignore rules describe untracked paths that should stay out of the index; adding .gitignore does not change an existing index entry.
  • Use git ls-files, git status, and git check-ignore --no-index -v to inspect tracking, changes, and the matching rule separately.
  • git rm --cached removes an index entry while leaving the current worktree file; collaborator checkouts, key rotation, and history cleanup remain separate concerns.

When git status still shows a path after an ignore rule is added, do not start by adding a second wildcard. Ask whether the path is already in the index. An ignore file primarily excludes untracked paths; it does not automatically remove an existing index entry. Whether the file should stay on your machine, leave future commits, or trigger a response to credentials in history are three different decisions.

Separate three states before changing anything

The key distinction is between a file existing on disk, a file being present in the index for the next commit, and a file having appeared in an earlier commit. The worktree is the local file state. The index is the snapshot Git will use for the next commit. Commit history records earlier snapshots. Ignore files participate in deciding whether untracked paths should be excluded; they do not make an existing index entry disappear. Git's FAQ on files that remain tracked after an ignore rule is added makes the same distinction and points to removing the path from the index when the goal is to stop tracking it.

If git status reports a modified file, that tells you the worktree differs from the content represented by the current commit. It does not tell you why an ignore rule had no effect. For one exact path, git ls-files --error-unmatch -- path/to/config asks whether that path is in the index. A successful result usually means there is an index entry. A failure means the exact path was not found there, although case, spelling, submodules, and the repository root can still matter. This check says nothing about whether the file is appropriate to share, and it does not prove that no historical version exists.

Then inspect git status --short -- path/to/config to see the current difference. A modified tracked file may enter the next commit. An untracked path that is not excluded is normally reported as untracked. Status output is not a secret scanner: it cannot tell you whether a file contains a password. A local configuration file may be absent from the output because an ignore rule, a global exclusion, or the current working-tree scope hides it. That absence does not prove the file was never committed.

Locate the rule instead of endlessly changing a wildcard

Ignore patterns can come from command options, .gitignore files near the path, the repository's .git/info/exclude, and a user-configured global excludes file. Git's documentation says that rules intended for all contributors generally belong in a version-controlled ignore file. Rules for one repository's local workflow can live in .git/info/exclude; personal editor backups can use a global exclude file. The source matters when one developer sees a path disappear but teammates still see it.

For an untracked path whose match is unclear, git check-ignore -v -- path/to/file reports the matching source, line, and pattern. By default, tracked files are not presented as ordinary ignore candidates. To ask whether a pattern would match a tracked path, use git check-ignore -v --no-index -- path/to/file. --no-index changes whether this diagnostic consults the index; it does not remove the index entry or change the repository. The reported source is useful evidence: a match from one developer's global configuration is not a shared team convention.

Pattern scope can also differ from intuition. A name with no slash can match below the ignore file's directory level; a pattern with a slash is anchored relative to that file's directory level. If an entire parent directory is excluded, a later negated rule for a child may not re-include it because Git does not enumerate paths inside excluded directories. These details matter when an untracked file is not matching as expected. They are a distraction when the path is already tracked: inspect the index first, then analyze the rule.

Remove an index entry without deleting the local file

Suppose a team once tracked config/local.json and later decides that each developer should keep an individual configuration file. If the current worktree copy should remain, git rm --cached -- config/local.json removes the path from the index while leaving the working file on disk. Add a shared ignore rule for that path, then inspect git status to confirm that the staged change removes the path from the repository while the local file still exists. The boundary of --cached is the index; it is not a shorthand for deleting the worktree file.

Splitting the migration into inspection and change is safer than running commands blindly. The following is an illustrative hypothetical, not an operation performed in this site's repository: use git ls-files --error-unmatch -- config/local.json to ask whether the index contains the path, then git check-ignore -v --no-index -- config/local.json to see which rule would match it. Only after confirming that the path should no longer be shared would you consider git rm --cached -- config/local.json and add the actual path to a project ignore file. Then check status and whether the worktree file remains. Each command answers a different question; one successful exit status does not prove the whole migration is complete.

Before running the command, verify the path and the content you intend to preserve. Git cannot infer whether the file contains a secret. If the repository needs shared defaults, a better design may be to keep a non-secret config/example.json, ignore the private copy, and document how initialization creates a local file. The example must omit secret values, and its fields and required conditions must match the program. Otherwise a clean checkout will lose an input without gaining a clear way to start.

After the index removal is committed, collaborators will receive a repository change that removes the path. Git may stop to protect local uncommitted changes during their next update. Plan the transition across team communication, templates, deployment configuration, and local setup. Also inspect whether Docker, an archive, a copy script, or CI artifacts could reintroduce the same local file into a build. Ignore rules govern parts of Git's path discovery; they do not filter every packaging pipeline.

Treat a file containing a secret as an exposure

Adding .env to an ignore rule and removing it from the index affects future snapshots, but earlier commits can still contain its bytes. Branches, tags, forks, caches, build artifacts, and other clones may retain copies. More importantly, a credential that someone could have read does not become invalid when the latest commit changes. Revoke or rotate it at the issuing service first, and confirm that the replacement reaches the runtime environments that need it. Which credentials to rotate depends on their permissions and reachable resources; a filename alone is not enough to establish scope.

Removing a path from the current index and cleaning commit history are different operations. Rewriting shared history changes commit identifiers and requires coordination for collaborators to resynchronize. It also cannot prove that external caches or clones were erased. Follow the repository maintainers' process to decide whether history cleanup is needed, who owns it, how to preserve a recoverable copy, and how dependent branches will be handled. No history rewrite or repository scan was performed for this article, and no command can guarantee that every copy has disappeared.

Close with checks that answer different questions

A bounded verification can ask four separate questions: Is the path in the index? Which ignore file supplies the rule? Does the worktree file still exist? Can a clean checkout create valid configuration from the documented setup? Use git ls-files, git check-ignore -v --no-index, filesystem inspection, and git status to cross-check the first three. If local configuration is required, clone into a controlled temporary directory, follow the project instructions to copy a sample, and run the existing configuration validation. That checks setup documentation; it is not proof of production secret handling. These project-specific checks were not run here; the command meanings follow Git's documentation.

An unexpected global rule reported by git check-ignore will not be fixed for the team by changing only one developer's global file. Put public expectations in the repository and have the team adopt them. When git ls-files still finds the path, a more elaborate wildcard will not change its index state. A path absent from the current index but restorable from an older commit shows that current state and history differ. Each result has a different next step; do not collapse “not displayed,” “no longer tracked,” and “secret is safe” into one conclusion.

Developer-only settings may need only index removal, a usable sample, and validation. Shared runtime behavior calls for safe defaults and a migration path. A valid credential calls for revocation or rotation, followed by an assessment of history and external copies. The decision depends on whether the team needs the information under version control, whether it can be safely recreated, and whether historical values still carry access. Pattern complexity does not answer those questions. For packaging scope, also compare the build context input boundary; Git exclusions do not replace a release-input check.
