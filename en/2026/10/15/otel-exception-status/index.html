Why Is a Span Still Unset After Recording an Exception? Judge the Operation First

`recordException` adds an exception event; it does not set Span status to Error. Use the Span’s operation boundary, final outcome, and applicable semantic conventions to decide which signals to record.

Key takeaways

  • RecordException adds an event; Span status is set separately, and default Unset is not explicit Ok.
  • Define the operation represented by a Span and classify its final outcome under the applicable convention; a recovered attempt is not automatically a failed request.
  • Recording errors is marked Development; the Span exception convention is marked Deprecated and points to logs, so check SDK version and migration settings.

In manual OpenTelemetry JavaScript instrumentation, span.recordException(ex) records an exception event. It does not call span.setStatus({ code: SpanStatusCode.ERROR }) for you. A Span that still appears as Unset may reflect a missing status update, or it may represent an operation that recovered successfully. Start by asking what operation the Span represents and how that operation ended; then choose the signals to write.

The two APIs write different evidence

RecordException is a specialized form of AddEvent. It adds an event named exception and exception attributes to a Span. SetStatus changes the Span’s status field. The OpenTelemetry API defines them as separate operations, so the first call does not implicitly perform the second. The official JavaScript instrumentation guide demonstrates the two actions separately as well: in a catch block it calls recordException and then sets SpanStatusCode.ERROR. That is the API division. The Trace Exceptions page says an exception should be recorded as an event on a Span only when it remains unhandled at the end and causes Error status; the current semantic-convention page for exceptions on spans is marked Deprecated and points toward logs. Whether a particular automatic instrumentation library does additional work depends on its version and migration configuration.

Unset is the default Span status. It should not be translated directly as “explicitly successful.” The Trace API’s Set Status section says status generally remains Unset; set Error for an error according to the applicable semantic conventions, while application developers may explicitly set Ok when success has been validated. When inspecting a tracing UI, check separately whether the event exists, whether status was set, what operation the Span represents, and whether the Span was sampled and exported. Finding a recordException call in source does not prove the other conditions.

Define the operation boundary before setting status

An exception object answers “what happened”; status classifies “how did this operation end?” The tricky part is often not the API but an ambiguous Span boundary. A Span may describe one downstream attempt or an entire request that includes retries. Their outcomes do not have to be the same.

Imagine an order service first calls the primary inventory source, times out once, then reads consistent data from an allowed fallback and completes the order. If the outer Span means “complete one inventory read,” marking it Error merely because the first attempt threw would count a successful fallback as a failed outer operation. If each attempt has its own Span, the team must define whether that attempt failed and follow the conventions for that operation; it should not simply copy a child Span’s classification to its parent. This is a hypothetical example. No code or telemetry was run.

Conversely, suppose the fallback also fails and the inventory read returns no usable result. The outer operation has failed even if the code catches the exception and returns an error object. Throwing is not the only criterion: OpenTelemetry’s current Recording errors page also treats other error returns, such as error codes, as possible operation failures. The Recording errors page is marked Development. Teams should document the convention and version they use instead of presenting the recommendation as automatic behavior mandated by every library.

Result when the represented operation ends Event and status decision Misreading to avoid
An unhandled exception causes this operation to fail Under the applicable convention, record the exception and set this Span to Error Recording an event does not imply status changed
An exception is handled by retry or fallback and the whole operation completes Do not classify the Span describing the completed operation as failed solely because of a transient exception; handle diagnostics under the applicable signal and convention Do not inflate the completed operation’s error rate just to preserve an exception
An expected business refusal, such as an existing resource Classify it under the operation contract; it may be a business result rather than an error Not every language-level Exception means an operational failure
No exception occurs, but the operation returns an error code or result The domain convention may classify it as Error and add applicable error-type information The absence of a catch block does not prove success

This table is not a universal rule to treat every exception alike. OpenTelemetry’s Recording errors example distinguishes a handled ResourceAlreadyExistsException from an IOException propagated to a caller: the first example does not set the operation Span to Error, while the second sets Error and error.type. Context and the Span’s scope change the decision. “Not found” may be a normal answer when checking whether a resource exists, but a failure when a request is required to read that resource.

Where should manual JavaScript instrumentation set status?

When an application owns the Span, centralize the final outcome decision at the operation boundary instead of marking every low-level catch as an error. The following pseudocode illustrates lifecycle only. It was not run with a particular SDK, runtime, or backend; imports and exception types must be checked against the version pinned by the application. It awaits the operation before calling end(), but omits Context activation and child-Span propagation, which a real implementation must handle through the language API’s context mechanism.

const readInventory = async () => {
  const span = tracer.startSpan('inventory.read');
  try {
    try {
      return await readPrimary();
    } catch (primaryError) {
      // Attempt-level diagnostics depend on the attempt Span/log convention.
      return await readReplica();
    }
  } catch (finalError) {
    if (finalError instanceof Error) span.recordException(finalError);
    span.setStatus({ code: SpanStatusCode.ERROR });
    throw finalError;
  } finally {
    span.end();
  }
};

The example leaves the outer status decision to the final-failure branch. A real implementation must also answer: does the primary call have its own child Span; do both attempts belong to inventory.read; is an empty fallback result a business refusal or a failure; does the caller receive an exception, an error object, or a response code; and does status get set before end()? Without these answers, a generic exception handler tends to classify different operations with one rule.

A counterexample is a catch block that records an exception and continues normally, followed by unconditional Error status on the outer Span. The exception may be an attempt that resilience logic absorbed, so the telemetry describes an internal event as the final outcome. The reverse can happen too: a catch returns { ok: false }, but only recordException is called, leaving the Span Unset even though the call chain failed. Fix the boundary first: document each Span’s operation, inputs and outputs, completion conditions, and failure definition. Then map those conditions to code paths instead of starting with the red icon in a UI.

An event can exist without appearing in a query

Several gates sit between the API call and queryable telemetry. The Span must be recording; the event must be attached to the intended Span and its lifecycle; sampling may exclude the data; and processors, exporters, transport, or backend storage may drop or delay it. The Trace API also says that calls to Span methods after End are generally expected to be ignored, though implementations may have streaming exceptions. Thus “the source called the method” is not equivalent to “the backend displays the event.”

A useful investigation sequence is: is the caught value an Error in this language; does the active context yield the Span for the expected operation; were event and status both written before ending; is the Span recording; how are sampling and processors configured; and what time range and filters does the export response or backend query use? When automatic and manual instrumentation coexist, check whether the same exception is recorded more than once. The Trace API still defines RecordException as a Span event operation, but the current semantic-convention page for exceptions on spans is marked Deprecated and points to log signals. Migration guidance allows existing instrumentation to retain older behavior temporarily and even supports phased dual emission. Check the library version and configuration; the existence of an API method does not mean every current or older library should emit exceptions as Span events.

Exception messages may contain user input or business data; OpenTelemetry’s exception attribute conventions explicitly warn that exception.message may contain sensitive information. Handle stack traces and other context under the system’s data-classification rules as well. The exception-on-Span conventions describe attributes such as type, message, and stack trace and warn that messages may contain sensitive information; that does not mean the SDK automatically sanitizes every collection path. Review attribute allowlists, collection settings, exporters, and storage access. If useful, retain an error type and correlation identifier without copying sensitive raw text. Better debugging context is not permission to upload an entire exception object by default.

How can you tell which layer left status unset?

Begin with unit-level tests for distinct outcomes: an unhandled exception that ultimately fails; a transient exception followed by successful fallback; an expected business refusal; and a failure represented only by an error code. Assert both the event and status on the same Span ID, and record which operation boundary the test covers. Do not merely assert that some exported record contains the string exception.

Then test the SDK and export pipeline separately. Use a controlled in-memory or test exporter to inspect event, status, attributes, end time, and duplicate recording; confirm the Span is recording at call time; then use an integration environment to inspect sampling, batching, network delivery, backend indexing, and query filters. Each layer answers a different question: a unit test proves a code path wrote expected fields, an export test proves the SDK output includes them, and a backend check proves the data is queryable there. These tests were not run for this article, and no claim is made about a real production trace.

Should the exception event go on the parent Span or a child Span? Start with the question the Span should answer. To explain a specific attempt, give that attempt a clear boundary and record it under the applicable convention. To classify whether a user request succeeded, classify the parent according to the request’s completion contract. A failed child operation may be diagnostic evidence inside a recovered parent operation; that does not make it the parent’s final error. If the applicable convention says handled exceptions should not be recorded on a Span or metric describing the completed operation, follow it. If the team needs retry-attempt evidence, label it as attempt-level diagnostics and check it against the current exception-log migration guidance.

A useful error status comes from a clear boundary, not from painting every catch block red. Write one sentence for each Span defining what counts as failure, then test recovery, business refusal, error-code failure, and final propagation. Log identity and trace correlation also affect investigations; see log correlation and trace retention. That relationship still needs validation against the actual SDK, sampling, and backend configuration.
