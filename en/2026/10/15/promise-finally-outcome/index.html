Give cleanup failures an explicit outcome policy

Separate main-operation outcomes from cleanup failures and retry decisions.

finally is not a notification guaranteed to leave outcomes untouched. If cleanup throws or supplies a rejected Promise, the resulting chain rejects with that failure. Define how the main outcome and cleanup failure relate before reporting business results.

Usually transparent is not unconditional

The MDN Promise.finally reference explains that ordinary callback values usually preserve the original outcome, while thrown errors and rejected promises replace it with rejection. The callback itself receives neither the fulfillment value nor rejection reason.

Imagine data saved successfully before temporary-state cleanup fails. A caller observing only final rejection might announce save failure and invite another submission. This scenario was not executed; no real duplicate save is claimed. The issue is combining the main operation with all later work without defining the meaning.

When both stages fail, cleanup can also conceal the original diagnostic evidence. Decide what to preserve and what action the caller should take. Neither suppressing every cleanup error nor assuming the latest cleanup error identifies the original business failure is a general solution.

Define cleanup responsibility separately

Some cleanup failures threaten resources or later availability; others are secondary bookkeeping. Classify by consequence rather than making every finally silently succeed. This is a design discussion, not an executed exception wrapper.

For asynchronous cleanup, inspect the completion relationship. Starting work without including it in the returned dependency can leave its later failure outside the chain. Invocation is not completion; specify what is awaited and who owns errors.

User feedback should reflect the distinction. Confirmed saving and unconfirmed resource release may need separate states. Retry selection and duplicate prevention still require business identity and recovery rules, which finally does not supply.

Proposed tests combine main success/failure with cleanup success/failure and inspect final outcomes and retained evidence. They were not run. See Promise aggregation and cancellation for the separate question of continuing concurrent work.
