The Save Succeeded, but finally Rejected: What Should the Caller Retry?

A rejected finally cleanup changes the returned chain, but says nothing by itself about whether an external write committed. Separate operation, cleanup, and retry state.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-25 · Estimated read 23 min
Translations
zh-CN en

Article

Key takeaways

  • When finally completes normally, it preserves the original state and value; a cleanup rejection rejects the returned chain.
  • A rejected chain does not prove an external side effect rolled back or never committed.
  • Retry decisions need an operation identity, status lookup, or idempotency contract, not a guess based on cleanup failure.

A write may have succeeded while cleanup inside finally throws, leaving the caller with a rejected chain. That rejection does not prove the write failed. A Promise describes how an asynchronous chain settles; it does not report whether a remote database, file system, or payment service committed a side effect. To avoid turning a cleanup error into a duplicate operation, represent the primary result, cleanup result, and retry authorization separately.

finally preserves the outcome under one condition

Promise.prototype.finally() runs its callback after the original Promise is fulfilled or rejected, then immediately returns a new Promise. The MDN reference and the ECMAScript algorithm specify that if the callback completes normally, the new chain preserves the original state: a fulfillment keeps its value and a rejection keeps its reason. An ordinary value returned by the callback is ignored. Unlike a then() fulfillment handler, finally() does not replace the business value with the cleanup callback's return value. It also does not pass the original value or reason to the callback. The MDN finally() reference and the ECMAScript algorithm describe these propagation rules.

“Completes normally” does not mean merely that the callback was invoked. If the callback returns a Promise, the returned chain waits for it to settle. If it fulfills, the original state and value or rejection reason are restored. If it rejects, the returned chain rejects with the cleanup reason. A synchronous throw also rejects the new chain. There are therefore two paths: cleanup fulfillment is transparent to the original outcome, while cleanup failure becomes the rejection observed by the caller. The final chain state is not an audit record of every stage.

This differs from then(). A then(onFulfilled) handler uses its returned value as the fulfillment value of the next Promise; a throw rejects that next Promise. finally() is intended for outcome-independent cleanup, so it neither receives the main value nor makes an ordinary cleanup return value the business result. See MDN's description of then() for the contrast. If cleanup must choose different actions based on whether the main task succeeded, write the success and failure handling explicitly instead of expecting finally() to receive the original result.

A final rejection is not a rollback receipt

Imagine a report-saving workflow. A caller submits operationId = R-42; the server saves the report, and then the client's finally releases a temporary reservation. The release request times out and rejects. The caller sees a rejected Promise. That tells the caller that the observed chain did not fulfill. It does not establish that the server rolled the write back, or that the write definitely committed. A timeout, connection loss, or client cancellation can happen after the server has processed a request. This is a hypothetical example: no real service was called and no duplicate save is claimed.

Representing the stages in separate columns helps prevent one state from standing in for another:

Main task Cleanup Possible chain outcome Possible next step
fulfilled fulfilled fulfilled; original value remains Show completion; verify whether any further cleanup check is needed
fulfilled rejected rejected with cleanup reason Check commit status by operation identity; do not replay the write automatically
rejected fulfilled rejected with main reason Recover according to the primary failure classification
rejected rejected rejected, often exposing only cleanup failure Record both stages with a correlation ID and define the caller's next action

The final column is application design, not a policy supplied by the Promise specification. In particular, when both stages fail, the finally() chain can retain only the cleanup rejection. If the primary failure matters, capture it at the business boundary; one final rejection reason cannot reconstruct two failures after the fact. Stage logs can carry the same operationId and record whether the main operation received explicit confirmation, whether cleanup completed, which stage failed, and in what order. Logs are not transaction proof, but they keep known facts available to a recovery workflow.

Cleanup importance determines how failure should be presented

Cleanup has no single severity. Hiding a loading indicator usually does not change whether a write committed. Releasing a distributed lock or returning a lease may affect whether later requests can execute safely. Failure to remove a temporary file may consume storage without meaning that file generation failed. Design review should ask: can cleanup failure violate resource ownership? Can it prevent later work? Is cleanup retried independently? Does the user need to know that the primary task failed, that it completed while the environment degraded, or that both outcomes remain unknown?

For the hypothetical report save, the interface might say “save status needs confirmation; cleanup failed” and offer a status lookup rather than an immediate resubmit button. When the server supports idempotent replay for operationId, the client may retry under that documented contract instead of inventing a new identity. Without a status endpoint or idempotency guarantee, the safe choice may be to stop automatic writes and route the case through a recovery process. The remote service contract determines the policy. Promise does not create idempotency.

For secondary cleanup that cannot affect resource safety or later correctness, a team may decide to record an operational event without telling users that the main action is unfinished. If the team suppresses a cleanup rejection, it should define the suppression boundary, monitoring, and compensation path. Adding .catch(() => {}) to every cleanup hides important failures such as an unreleased lock. Reporting every cleanup rejection as a main-task failure can prompt an unsafe retry. The useful policy is neither “always suppress” nor “always throw”; it makes phase state and user action agree.

The dual-failure case deserves particular care. One maintainable boundary can capture the primary error, attempt cleanup, and return or throw a structured result containing both primaryError and cleanupError. The concrete error type depends on the project's runtime and compatibility target. Another policy may keep the primary failure as the control-flow reason and emit cleanup failure through a separate event. Either way, correlate the evidence, filter sensitive fields, and preserve causal order. Do not keep only whichever error was caught last without context about the first.

Asynchronous cleanup must be part of the wait relationship

A common mistake is to start cleanup without returning its Promise:

work().finally(() => {
  releaseReservation(); // The Promise is not returned.
});

The callback can return normally before releaseReservation() finishes. A later cleanup rejection is then outside this chain's propagation path. If the caller must wait for release and observe failure, return the Promise:

work().finally(() => releaseReservation());

Now the chain waits for cleanup, with the propagation consequence already described: if release rejects, the caller receives the cleanup rejection rather than the original fulfillment value. return establishes a completion and error-observation relationship. It does not decide retry policy, preserve the original result in a separate field, or make multiple remote steps atomic. If the business interface needs to report both phases, organize those outcomes explicitly outside a single final Promise state.

The same distinction applies to async functions. finally(async () => { await release(); }) returns a Promise, so the chain waits. If release() rejects, the async callback Promise rejects too. Conversely, calling an async function without returning it, or swallowing its error internally, can make the observer miss the failure it expected to see. Review the returned value through each call boundary; a function's async label alone does not show that a caller waits for it.

Use operation identity to resolve commit uncertainty

When an external side effect has an uncertain commit result, retry needs evidence independent of the cleanup state. A common design gives one logical action a stable operation identity and lets the server record that identity with its final state. A status endpoint can look it up, or the server can explicitly promise that resubmitting the same identity will not repeat the side effect. Only when that contract exists, its scope is clear, and its backing state is reliable should the capability be called idempotency. Putting an arbitrary request ID into a log does not make an operation idempotent.

This approach has limits. Operation records can expire. A server must define a conflict rule when the same identity can arrive with different payloads. A side effect spanning services may not be covered by one service's record. The lookup endpoint may itself be temporarily unavailable. A recovery workflow should distinguish “confirmed committed,” “confirmed not committed,” and “currently unknown”; it should not collapse unknown into failure. When recovery cannot determine the result, automatic writes may need to pause while reconciliation, operator handling, or compensation proceeds. Compensation is not necessarily a rollback of the original operation.

Cleanup failure therefore needs its own recovery policy: retry cleanup itself, report a completed primary task with degraded resources, or block related work until lock or lease state is clear. Do not assume cleanup and the primary write share one transaction just because finally() is convenient. Their storage, failure windows, and ownership may differ.

How to verify the boundary

Design tests for four combinations. With both the main task and cleanup fulfilled, the returned chain should fulfill with the original value. A fulfilled main task followed by rejected cleanup should reject the chain, while the business record is checked separately. When the main task rejects but cleanup fulfills, the original primary reason should remain. For two rejections, check whether the caller can access both error contexts required by the chosen interface. Add cases for a cleanup ordinary value, a fulfilled Promise, a synchronous throw, and a rejected Promise. Also verify the actual wait behavior when asynchronous cleanup is not returned.

If the main task is a remote write, the test layer also needs a controllable fake service or contract environment for “server committed, response lost.” A lookup by the same operation identity should distinguish committed and uncommitted results; replay should comply with the server's documented idempotency contract. A Promise unit test cannot substitute for this verification. This article proposes a test matrix; no tests, remote services, or production writes were run, and no success log is claimed.

If the main task is a concurrent composition, whether one rejection cancels the remaining work is a separate semantic question. See Promise aggregation failure and cancellation boundaries. Observe concurrent task completion separately from cleanup completion so a single chain state is not mistaken for a complete audit of the entire operation.
