Separate numeric storage rounding from input validation

Separate numeric rounding, input acceptance and calculation policy.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-15 · Estimated read 5 min
Translations
zh-CN en

Article

A numeric column with a declared scale may round extra fractional digits rather than reject the input. Storage precision and input acceptance are different policies. If excess input precision must be rejected, check it before conversion discards information.

A type can transform the value

The PostgreSQL 18 numeric-type reference describes rounding to scale before checking the permitted integer precision. Unconstrained numeric also differs from a declared precision/scale column. This is storage behavior, not a prescribed financial or measurement rule.

Imagine a two-decimal measurement accepting a value with more places. Saving can succeed after rounding, even if the product required rejection. The displayed value is then no longer the original input. No insertion or rounding experiment was performed.

Define precision and fractional places consistently. Interface text, parsing, columns, and tests must not each interpret “allowed digits” differently.

Preserve evidence before conversion

Where necessary, distinguish the submitted representation from the adopted value under appropriate access and retention rules. Not every application needs indefinite raw retention, but a rounded result cannot reveal how many places the original contained.

Decide how trailing zeros, exponent notation, and formatting variations relate to the policy. Display format alone cannot establish numerical meaning, and variation is not automatically invalid. No universal cross-language validation regex is offered.

Keep rounding coherent through the pipeline

Specify where rounding happens, which rule applies, and whether later calculations use original or processed values. Uniform two-place display does not establish consistent intermediate algorithms. Adopt rules from confirmed business requirements and applicable standards.

Proposed checks include exact scale, excess places, range boundaries, and repeated processing, comparing input, storage, and display. They were not run. See CHECK constraints and null values. Valid input, successful storage, and correct business calculation require separate evidence.
