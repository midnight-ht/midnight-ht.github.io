Why Does numeric(4,2) Round Extra Places but Reject 99.995?

PostgreSQL numeric(p,s) rounds to its declared scale before checking integer capacity. Storage rounding is not input validation; distinguish two rejection policies before conversion.

Article

Key takeaways

  • numeric(p,s) rounds to s fractional digits, then checks whether the result fits p-s integer digits.
  • Rejecting nonzero excess precision and rejecting extra digits in the original text are different rules.
  • Validate an original representation before type conversion discards the evidence.

PostgreSQL numeric(4,2) first rounds to two fractional places and then checks whether the result can fit in two integer places: 99.994 becomes 99.99, while 99.995 rounds to 100.00 and overflows. A declared scale is a storage-conversion rule, not an input validator that rejects every value with one extra typed digit.

What does numeric(p,s) limit?

In the PostgreSQL 19 Numeric Types chapter, precision is the total number of significant digits and scale is the number of digits to the right of the decimal point. For the common declaration with a nonnegative scale and s <= p, integer capacity is p - s. So numeric(4,2) can hold at most two integer digits and two fractional digits; its largest positive value is 99.99. An unconstrained numeric column does not coerce values to a fixed scale.

There are two distinct operations. During assignment to a column with a declared scale, the server rounds an over-precise value to the column's declared number of places. It then checks whether the integer portion of the rounded result exceeds p - s; an excess produces an error. The server does not begin by comparing the original input string's fractional digit count with 2.

Why does 99.994 fit while 99.995 overflows?

Break the example into the documented steps. Assume the destination is numeric(4,2):

Input Rounded to two places Integer digits Result
99.994 99.99 2 Fits numeric(4,2)
99.995 100.00 3 Overflows the two-digit integer capacity

The first row shows that having three fractional places does not by itself cause an error; the rounded value still fits. The second value carries into a new integer digit while scale is being reduced, so the result exceeds the range. The same boundary applies to negative values: PostgreSQL numeric rounds an exact tie away from zero, so -99.995 becomes -100.00 and likewise cannot fit in numeric(4,2). These results are derived from the official rules; no real INSERT was run for this article.

The phrase “more than two decimal places” can also mean two different things. A value-preserving rule treats 1.234 as a problem but 1.2300 as equal to 1.23. A literal rule that limits submitted text to two digits after the decimal point must reject 1.2300 too, even though rounding does not change its value. Those policies have different acceptance sets despite being described with similar language.

This distinction changes the API contract. A client that sends an amount as a JSON number usually gives the server a numeric value rather than the original character sequence. Whether the trailing zeroes in 1.2300 remain observable depends on the parser and the next representation. To reject text that spells three fractional digits, inspecting only the database value is insufficient. Preserve the raw field text before parsing, or define the amount as a decimal string and parse it under an explicit grammar. A string is not automatically safe: decide whether to accept a leading plus sign, whitespace, exponent notation, grouping separators, and negative zero, and reject forms that are not part of the contract. Otherwise the API, import job, and administrative write path may accept different input sets.

Why can a table CHECK be too late?

When the target column itself is numeric(4,2), PostgreSQL has already applied its scale conversion as part of storing the value. A row constraint then sees the value after target-type handling; it cannot reliably tell whether the submitted form was 1.23, 1.2300, or 1.234. For example, comparing amount = round(amount, 2) on that constrained column may look like a way to reject extra places, but amount has already been converted by the time the constraint evaluates it.

To reject values whose numeric value would change, check at an unconstrained numeric ingress before inserting into the fixed-scale table. This unexecuted sketch illustrates the separation:

-- Illustrative only; not executed against PostgreSQL.
CREATE TABLE amount_stage (
  raw_amount numeric NOT NULL,
  CHECK (raw_amount = round(raw_amount, 2))
);

CREATE TABLE invoice_amount (
  amount numeric(4, 2) NOT NULL
);

On unconstrained numeric, comparing raw_amount with its two-place rounded result means “do not change the numeric value”; 1.234 fails, while 1.2300 is numerically equal and can pass. A policy that rejects even trailing fractional zeroes can use PostgreSQL's scale(numeric) to check the represented fractional scale; for example, the documented scale(8.4100) returns 4. But confirm that the application and driver have not changed the original representation before sending it. If a request is first converted through JavaScript Number or another parser, trailing zeroes in the submitted text may already be gone, and the database cannot reconstruct them.

Whether a staging table should retain the raw value long term is a separate product decision. Raw text may help with rejection messages, audit, or replay, but it can also be unnecessary retained data. Limit access and retention. If long-term retention is not needed, validate at the request boundary, write only the normalized value to the business table, and keep only the minimum rule version and rejection reason needed for diagnosis.

Also decide whether validation and the final write share one transaction. If the application validates raw_amount, then a different path can alter the value before it reaches numeric(4,2), the validation result no longer describes what was stored. An auditable boundary is to parse into unconstrained numeric, apply the precision policy, and insert into the destination within one transaction, or to put validation and insertion behind a database function. When the request is text and its scale matters, record syntax validation separately from numeric range validation: the first evaluates the representation, the second the value. A rejection record can then say whether excess written places, a value-changing round, or the 99.99 range caused the rejection instead of storing only an ambiguous “invalid amount.”

Keep rounding policy consistent with later calculations

The PostgreSQL 19 Mathematical Functions documentation says round(numeric, s) breaks exact ties away from zero. It also notes that double precision commonly breaks ties to the nearest even number and that floating-point types are approximate. Do not assume that floating-point arithmetic in an application, PostgreSQL numeric rounding, and a display format all use the same rule.

If the business chooses to round, specify when rounding occurs, which rule applies, whether the rounded value feeds later tax or ratio calculations, and whether reprocessing could change it. The implicit rounding of numeric(4,2) is PostgreSQL's type behavior; it does not choose a banking, truncation, or other settlement policy for the business. If a requirement calls for a different rule, implement and test it at an explicit calculation boundary, and still ensure the destination column can hold the result.

How can you verify the rejection rule?

Divide boundary inputs into two sets: values that change numerically and values that change only in textual scale. At minimum, cover 99.994, 99.995, -99.995, 1.234, and 1.2300; record the original request, the value immediately before PostgreSQL, the ingress decision, the destination result or SQLSTATE, and what the UI displays. Also test exactly 99.99, values beyond the maximum, nulls, exponent notation, and whether every write path enforces the same rule.

Do not assert only that a request failed or that SQL succeeded. For each input, assert three observation points: the text retained after parsing, if the policy depends on the original representation; the precision-policy result on unconstrained numeric; and whether the fixed-scale column accepts or rejects the value. For a no-numeric-change rule, 1.234 should fail at the policy boundary while 1.2300 may pass that policy and still needs a range check. A lexical two-place rule should reject 1.2300 at the syntax boundary. 99.995 exposes the ordering: an unconstrained numeric can first become 100.00 under a two-place policy, after which the numeric(4,2) destination rejects it for integer capacity. Put those assertions in API, import, and database-path contract tests so one route cannot quietly use a different rounding policy.

If rejection belongs in the API, background jobs or manual SQL might bypass it. If every write passes through a staging table or stored procedure, verify that no alternate route can write directly to the final column. Acceptance evidence should separately prove which inputs the rule rejects, what the target column stores, and whether the application changed the number; a successful insert is not proof that the original input was valid. The SQL and test matrix here are proposals, not executed results. Validate the actual PostgreSQL major version, driver, and write paths. If a separate constraint needs to define what CHECK does with NULL, see PostgreSQL CHECK constraints and null values; that is another constraint boundary and does not replace an input-scale policy.
