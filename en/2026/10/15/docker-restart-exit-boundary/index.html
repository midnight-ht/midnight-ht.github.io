Why doesn't Docker restart an unhealthy container?

Docker HEALTHCHECK records a health state, while restart policies act on container lifecycle events. Learn the boundary, Compose startup dependencies, and a verifiable recovery design.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-24 · Estimated read 26 min
Translations
zh-CN en

Article

Key takeaways

  • HEALTHCHECK records probe results; it does not terminate the main process or constitute a restart command.
  • Restart policies act on container exits and daemon lifecycle; inspect exit codes, policy, and manual-stop state.
  • Compose service_healthy mainly gates startup ordering; ongoing recovery needs an explicit executor, limits, and business verification.

When a container is unhealthy but its process is still running, the restart policy usually has no exit event to act on. Docker's health check updates an additional state; a standalone container's restart policy decides whether to start it based on lifecycle conditions such as a container exit or a Docker daemon restart. They observe different events, so unhealthy alone does not mean that a restart action has fired.

That distinction determines who must perform recovery. Detection belongs to the probe, the action decision to a controller, while the business system must still establish that requests and jobs are correct after recovery. Docker does not describe HEALTHCHECK as a mechanism that kills the main process or restarts a container. Collapsing all three responsibilities into one red health label creates the impression that an observed problem will repair itself.

What HEALTHCHECK changes

The Dockerfile reference says a container with a health check has a health state in addition to its normal state. It begins as starting, becomes healthy when a probe succeeds, and becomes unhealthy after the configured number of consecutive failures (retries). A check that exceeds its timeout is considered failed, and the process running that check is terminated. The process being limited is the probe command, not the container's main process.

Health is therefore an additional diagnostic record. It answers whether a particular command succeeded in the container environment. It does not directly answer whether the main process exited, whether a user request can complete, or which recovery action should be taken. For example, the main process can keep its PID and event loop while its database connection pool is exhausted. The probe fails repeatedly and Docker changes the health state to unhealthy, while the normal container state remains running. Those two observations are compatible.

Probe design changes the meaning of the signal. Requesting only a static landing page may still succeed when the critical write path is broken. By contrast, traversing every downstream dependency can make all instances fail together during a short dependency interruption. Its executable, certificates, network route, and permissions must also exist in the final image. If curl is absent, a failed health check may mean that the probe command cannot run; it does not by itself prove that the application is unavailable. Inspect recent health-check results and exit codes alongside application and dependency logs rather than relying on the label alone.

Restart policies wait for container lifecycle events

Docker Engine's automatic-start documentation describes restart policies as controlling whether containers start automatically when they exit or when Docker restarts. The policies have distinct behaviors. no does not restart automatically. on-failure responds to a non-zero exit code and can have a maximum retry count; the documentation says it does not restart a container merely because the daemon restarted. always and unless-stopped cover broader cases and differ in what happens to a manually stopped container after a daemon restart. Read the documentation for the Engine version in use instead of inferring semantics from a policy name.

Two details are easy to miss. A policy takes effect only after the container has started successfully, which Docker defines here as running for at least 10 seconds while Docker monitors it. If someone manually stops the container, the restart policy is ignored until the daemon restarts or the container is started manually. unless-stopped preserves that manual-stop intent even across a later daemon restart. During an incident, distinguish an abnormal process exit, a health failure while the process remains alive, and an operator stopping the container.

Consider this explicitly hypothetical example. A service process remains alive, but after a database primary failover its connection pool is stuck on old connections. The health probe fails repeatedly and the health state becomes unhealthy; State.Status is still running, and no exit code exists yet. Neither on-failure nor always can be assumed to terminate the process solely because the probe failed. If the process later exits on its own, on-failure still depends on its exit code. If the container repeatedly exits before it has run for 10 seconds, the policy activation condition also matters. This is a walkthrough of trigger boundaries, not a reported fault-injection result.

A Compose health dependency is not an ongoing repair loop

In a Compose service definition, depends_on with condition: service_healthy can require a dependency to become healthy during startup before Compose continues starting the dependent service. This helps with a race such as an application starting before its database is ready. Compose also provides restart: true for a dependency: if that dependency is updated or restarted by an explicit Compose operation, such as docker compose restart, Compose restarts its dependent service. This is not an ongoing repair loop for a dependency that later fails its health check. A startup gate, a restart following an explicit operation, and a runtime health failure are three different conditions.

Even if startup succeeds, a dependency can fail later. The application still needs to handle connection errors, bounded backoff, request timeouts, idempotency, and eventual recovery. Otherwise, a control plane may amplify the same incident: a new container starts, connects to the same failed dependency, fails its probe, and prompts another restart. Operators see “restarted” repeatedly without business recovery. Judge the action by the business path, not by whether a container was recreated.

If a health signal should cause action, name the executor separately. It might be an on-call operator acting on an alert or an external monitor or platform controller with the required authority. A script or control plane needs thresholds, cooldowns, concurrency limits, retry bounds, circuit-breaker conditions, and a human escalation path. Docker Engine's restart policy and an external health-monitoring system are not the same control plane. Do not make a probe script kill PID 1 merely to trigger the policy: that turns observation into a destructive action and may hide a downstream failure. If the application exits deliberately on an unrecoverable state, ensure that the exit means a process-level failure that can be reconstructed, then verify the non-zero exit, retry limit, and job semantics.

How to design a bounded recovery acceptance test

In a test environment, record observation and action separately instead of stopping a production container to see what happens. Enumerate at least four states: probe passes while the process runs; probe fails while the process remains alive; process exits with code zero; and process exits with a non-zero code. Add manual stop and daemon-restart cases to distinguish always, unless-stopped, and on-failure. For each case, record the Docker Engine version, probe command in the image, policy, container uptime, source of the stop, State.Status, health log, exit code, restart count, and event timeline. This article did not execute those experiments; this is a proposed acceptance plan, not a test result.

Thresholds should match the target failure. The probe interval, timeout, and number of consecutive failures determine when health changes. start_period can give a container time to initialize; failures during it do not count toward the maximum retries. The current reference also says that once a health check succeeds during the start period, subsequent consecutive failures count. The documented default for start_interval is 5 seconds, and Docker specifies that this option requires Engine 25.0 or later. These values are documentation defaults and version conditions, not recommended settings. Choose parameters against the Engine version and startup time actually in use so that a dependency recovering during initialization is not prematurely classified as a sustained failure. A threshold that is too sensitive can cause flapping alerts or synchronized restarts; one that is too tolerant delays detection. With multiple replicas, consider whether restarting every instance while they share one failed dependency would create a connection storm. Retry and cooldown limits should constrain the blast radius of automated action, not conceal the underlying failure.

Acceptance should not stop when the container returns to healthy. Consider a hypothetical job write: submit a job with a unique business key, then simulate a container exit or temporary dependency failure. After recovery, inspect whether the job remains queued, whether it can run twice, whether external side effects are deduplicated, and whether backlog drains. A restart counter proves a lifecycle change. A successful probe proves that its selected condition passed. Business records and side-effect reconciliation are evidence for whether the user's job completed. If work can be interrupted by restart, the system needs acknowledgements, leases, idempotency keys, or recoverable checkpoints. Choose among them based on repeatability, external side effects, and acceptable delay rather than applying one universal answer.

Manual stop is another counterexample to include. An operator may intentionally stop a container to isolate a fault; ignoring automatic restart may be the desired behavior, and a controller should not immediately override that intent. Avoid repeatedly stopping critical production containers just to observe policy behavior. Reproduce it in an isolated environment and confirm that the test image, daemon version, and configuration resemble the target. Evidence should answer which event occurred and which executor took which action.

When a health check is still useful

The absence of automatic restart does not make health checks useless. They can help operational systems distinguish a live process from a failed probe and support load removal, alert levels, startup ordering, or manual diagnosis. Whether those actions happen depends on the component that reads the signal and its defined behavior. A successful health check establishes only that its selected command passed at a particular time; it does not replace an end-to-end transaction check.

Choose an action according to risk. During a brief dependency failure, the application may use bounded backoff while allowing existing requests to finish. If the process is unrecoverable internally and can be reconstructed after restart, a controlled process exit and a suitable policy may be appropriate. If a shared dependency remains down, alerting, rate limiting, or pausing new jobs may be safer than restarting the entire fleet. For a manual stop, preserve operator intent and document how to re-enable the service. These are engineering judgments that must be validated against the service's job semantics, redundancy, and rollback plan.

Keep traceable evidence for health probes, container lifecycle, and business recovery separately. State records what was observed; a restart policy constrains which lifecycle events can automatically start a container; a recovery controller and the application decide whether to act. Once those layers are separated, unhealthy is no longer mistaken for an unfulfilled promise to restart. To check how the main process receives a stop signal, see container entrypoint processes and shutdown signals and treat signal delivery, exit conditions, and business-job cleanup as a separate acceptance path.

Does a dependency's later health failure restart its dependent service?

depends_on: condition: service_healthy is a startup constraint. restart: true covers a dependent-service restart when an explicit Compose operation updates or restarts the dependency. Neither behavior by itself means that a later unhealthy state starts an ongoing repair loop. If runtime health failure requires action, name a separate controller and test how it handles transient failure, persistent failure, manual stops, and business consistency after recovery.
