Accept Is a Preference, Not a Guarantee: How to Check the Actual HTTP Response

Accept states a client's preferred representations; status, Content-Type, body syntax, and business structure still need separate checks, and 406 is not mandatory.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-24 · Estimated read 20 min
Translations
zh-CN en

Article

Key takeaways

  • Accept expresses a media preference, not a guarantee; a server may disregard the negotiation field or return 406 when it is unwilling to provide a default representation.
  • Use the status to decide whether a body should be read, then check Content-Type, syntax, schema, and business state separately; 204 carries no additional response content.
  • Use Vary for cache variants only when the representation actually changes with Accept; the test matrix here is proposed, not executed.

A request includes Accept: application/json, yet parsing the response as JSON fails. That does not by itself prove that the server returned “bad JSON.” The client declared a media-type preference. It still needs to check the HTTP status, the actual Content-Type, the body's syntax, and its business structure. If all of those boundaries are collapsed into one call to response.json(), distinct failures become one vague parsing exception.

Record preference and selection separately

In a request, Accept expresses the sender's preferences for response media types, such as application/json. A server can use that information for content negotiation. Once it selects a representation, the response's Content-Type describes the media type actually sent. RFC 9110 Accept definition defines Accept, while Content-Type definition defines Content-Type. Their directions differ: the former says “this is what I prefer”; the latter says “this is what this response contains.” Neither describes the business fields inside a JSON object. The MDN Accept reference also notes that browsers set different defaults according to request context, so success in one browser does not prove that another client sent the same preference or received the same representation.

Preferences can include quality values. For example, Accept: application/json, text/html;q=0.2 gives JSON a higher relative preference than HTML. If q is omitted, its default weight is 1; q=0 marks the corresponding range as unacceptable. An absent Accept does not mean that the client understands no type; it means there is no preference on that negotiation dimension. A wildcard such as / broadens the range of media types the client is willing to receive, but it does not give its parser new capabilities for images, HTML, or binary data.

406 Not Acceptable is another frequent source of confusion. It is not the only outcome a server must return when it cannot meet a preference. RFC 9110 negotiation-field rule allows an origin server either to return 406 when no available representation is acceptable or to disregard that negotiation field and treat the request as if it were not subject to negotiation on that dimension. 406 definition describes 406 in the case where the server is unwilling to supply a default representation. A caller must therefore be prepared to receive a different representation even after asking for JSON. Conversely, a server can return 406 with a JSON error body: the status and the error body's format are separate parts of the contract.

A reliable client should not assume that “a response arrived” means it should parse a success object. First determine whether the request completed normally, then distinguish statuses according to the API contract. For a 2xx response, check whether that particular status is expected to carry a body. For example, 204 definition defines 204 as successful fulfillment with no additional response content, so a caller should not unconditionally read JSON. For 4xx and 5xx responses, enter an error-handling branch, but do not infer that the body must be JSON. An API may describe validation errors in JSON, while a reverse proxy or CDN may supply an HTML error page. These are hypothetical failure paths; this article did not send requests to a real service.

This separation improves diagnosis. A timeout or connection failure belongs to the transport layer. A received 401 should invoke the authorization-failure policy rather than be logged as a JSON syntax error. A 200 with text/html has a successful status but a representation-contract mismatch. If the declared type is JSON but the bytes are not valid JSON, that is a syntax parsing failure. Each class may need different retry rules, user feedback, log fields, and alert categories. A single catch can provide a final fallback, but it should not erase the status and headers already observed.

A matching media type still does not validate the body

Content-Type: application/json is the sender's declaration about a representation. It does not prove every byte, object field, or business meaning. A parameter such as charset=utf-8 in application/json; charset=utf-8 should not make a client think the media type itself changed; checks normally need to parse the media-type essence instead of relying on brittle full-string equality. But media-type checking is only a gate for choosing a parser. Successfully parsing {} as JSON does not prove that it matches an interface requiring {id, state}; matching that structure does not prove that state is allowed for the current operation.

The Fetch Standard defines Response.json() as consuming the response body and parsing JSON from its bytes; it can reject with a SyntaxError when the body is not valid JSON. The method does not itself enforce a contract that the declared Content-Type must be JSON, and it does not validate an application schema. A response body is a one-shot stream: after calling json(), calling text() generally cannot retrieve a second copy of the same body. If diagnostics really require preserving text, design a one-read strategy first, with a size limit, sensitive-data redaction, and retention policy. Do not log unbounded response bodies just to aid troubleshooting.

With Fetch, make the handling order explicit. This is an implementation design, not an execution result: check response.status, distinguish expected success, bodyless statuses, and error statuses; then check whether Content-Type is among the representations allowed for that status, choose a parser, and finally validate the schema and business constraints. Handle 204 before reading the body. If error responses support multiple formats, define a separate error-parsing branch. Unknown or erroneous types should produce a diagnosable “unsupported representation” result rather than trying parsers until one happens not to throw. The example was not run locally or online.

Define the allowed media-type set from the interface rather than guessing without bounds. Some services allow only application/json; others explicitly use another JSON media type. If structured syntax suffixes are supported, record that as an interface rule and test it; do not assume that a type name that looks like JSON has the same object schema as the existing model. HTTP headers do not replace security validation: a JSON media type is not a reason to trust input, skip size limits or schema checks, or omit authorization checks. Cross-origin responses are also subject to CORS header exposure: even when a server sends a custom header, browser script may not be able to read it. MDN’s CORS response-header guide explains that Access-Control-Expose-Headers adds response headers to the list JavaScript may access. Record “header not exposed” separately from “header absent.”

Validate response combinations

Instead of asserting vaguely that “the endpoint returns JSON,” list the status and representation combinations for each operation. The following is a proposed test matrix and has not been run against this project or a target API: a successful 200 JSON response should pass syntax, schema, and business-state checks; 204 should yield a no-body result; a 401 JSON error should enter the identity-handling branch; a 502 HTML proxy page should preserve its status and type and enter a diagnosable upstream-failure path; a 200 HTML login page must not be treated as successful JSON; and syntactically valid JSON missing a required field should fail schema validation rather than media-type validation.

These cases expose branches that are often missed. If a client follows redirects, the final response may come from a login page or another resource, so the final URL and headers belong in the diagnosis. If Content-Type is missing or incorrect, RFC 9110 §8.3 allows a recipient to assume a generic type or inspect the data, but MIME sniffing can produce a wrong conclusion and introduce security risks. If duplicate fields are actually received, the caller also needs an explicit tolerance or rejection policy; it should not silently treat sniffing as the API contract. On the server side, test requests with no Accept, a specific media type, a wildcard, a type excluded by q=0, and an unsupported type. Document the actual fallback and 406 policy.

Assertions should cover status, Content-Type, required headers, parse-result classification, and user-visible behavior. Checking only that a Promise resolved can miss a 404 page parsed incorrectly; checking only for a parse exception can misclassify an expected 204 as a failure. Also distinguish “the client is not allowed to read the body” from “the representation type is unsupported,” so that an HTML error page is not copied wholesale into logs. An unexecuted contract test remains a test proposal, not a passing result.

If the same URL can return JSON or HTML according to Accept, a shared cache needs to know that the selected representation depends on a request field. RFC 9110 Vary rule defines those selection conditions. When a service actually varies its response by Accept, check whether the cache configuration includes it in the variant key. Not every request containing Accept requires Vary: Accept: if the representation does not change with that field, adding it mechanically can create unnecessary cache fragmentation. Cache keys, response declarations, and the origin's actual negotiation behavior must agree. For a related treatment of representation selection and cache keys, see Vary representation keys for one URL.

During diagnosis, preserve evidence in this order: request method and final URL, Accept preference, HTTP status, response Content-Type and Vary, body parsing result, schema result, and then business state. This sequence does not define the service contract, but it helps the team locate the layer where the failure occurred. Accept helps the parties negotiate a representation; response-handling code verifies what actually arrived. Both matter, and neither substitutes for the other.
