A Prometheus Recording Rule Returned a Value—Why Did the Instance Label Disappear?

A recording rule writes a new series. Aggregation, vector matching and label overrides can change its identity. Trace the expression, rule group and downstream queries.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-25 · Estimated read 25 min
Translations

Article

Key takeaways

  • Recording rules write new series; a value does not prove that the original instance identity survived.
  • Aggregation, vector matching, label overrides, and missed rule evaluations are distinct failure paths.
  • Treat the metric name, output labels, and downstream queries as one contract; assert labels and values in rule tests. The proposed tests were not run.

A recording rule can produce a sample without retaining the source series’ instance label. The expression determines which dimensions survive, and rule labels can later add or overwrite output labels. If a recorded metric has a value but a selector using the original instance returns nothing, do not immediately call it a scrape failure. Inspect the raw series, the PromQL expression result, the recorded series, and the rule group’s evaluation state separately. They answer different questions: what was scraped, what the calculation preserved, and whether the rule wrote on time.

A recorded result is a new series, not a copy

Prometheus identifies a time series by its metric name and complete set of labels. Adding, removing, or changing a label value creates a different series, as the data model documentation explains. Seeing the same numeric sample in a graph does not mean that two series still represent the same objects.

Under a recording rule, an expression result is stored under the specified record name. The recording-rule reference describes periodic evaluation and a new output series whose metric name comes from record. Its labels depend on the expression and rule configuration. Recording rules are useful for precomputing frequently used or expensive expressions, reducing repeated query work. They do not alias the original series or promise to copy every input label.

Consider a hypothetical input such as api_http_requests_total{job="checkout",instance="api-1",path="/pay",method="POST"}. If an expression aggregates across instances by path and method, its result no longer distinguishes instance, although it may still retain job, path, and method. The rule stores that output with a new metric name. Queries that require the old instance label will not identify the aggregate. A present value and instance-level traceability are separate contracts.

The project recommends recording-rule names in the form level:metric:operations, where the level describes the output aggregation and retained labels. Its naming and aggregation guidance also recommends stating the labels being removed with without, preserving other labels such as job. For example, sum without (instance) aggregates away the instance dimension while retaining the other labels that still define groups. It does not mean “sum while retaining instance.” Review the name and expression together: a name that says path-level while the output unexpectedly carries one instance sends conflicting identity signals.

Trace each transformation in order

First inspect the raw metric at the time and with the selectors in question. Confirm that the expected label value exists. Then evaluate the rule expression on its own and inspect the returned label set. Finally inspect the recorded metric to see whether labels changed after the expression. Keep the time range and matching conditions fixed at each step; otherwise a different query window can make “no sample” look like “the label disappeared.”

The first path is aggregation. sum by (job, path) explicitly groups output by the listed dimensions. sum without (instance) expresses the intent to remove instance while preserving other dimensions. The choices behave differently as input labels change: by keeps the output dimension set closed, so a newly added input label does not automatically join the grouping; without is useful when only a few known dimensions should be removed and other meaningful labels should remain. The choice is more than a style preference. It defines whether future instrumentation changes can silently change output identity.

The second path is vector matching. Arithmetic expressions match left- and right-hand instant vectors by labels. on(...) names labels used for matching; ignoring(...) excludes labels from the match key. The official operator and vector-matching documentation says that elements with no matching counterpart do not appear in an arithmetic result. Its example matches error rates with request totals by method; only methods present on both sides produce a result. An absent label value can therefore mean that a numerator or denominator lacked a counterpart, not that rule configuration removed the label. If group_left or group_right is involved, confirm the one-to-many relationship represents the data. These modifiers are not general-purpose switches for repairing unmatched input.

The third path is rule labels. A rule group can add or overwrite labels before storing results. Labels on an individual rule can also add or overwrite them, and rule-level values win when they collide with group labels. If an expression returns environment="prod" and a rule assigns environment="test", the recorded sample may still have a value while its identity has changed. Setting instance="all" at the end does not restore source-instance information; it creates a different dimension with a different meaning. If the original identity must survive, design it in the expression and aggregation level rather than fabricating a same-named label at the final step.

A missing sample can also mean the rule did not finish on time

“Label absent” and “no recorded sample at this time” require different investigations. Rules in a group run sequentially. If a group evaluation has not finished before the next interval, Prometheus skips subsequent iterations until the previous evaluation completes or times out, and increments rule_group_iterations_missed_total. The rule evaluation documentation says this can create a gap in the produced recording metric.

Filtering by the old instance label can therefore return no sample for several different reasons: aggregation removed the instance dimension; vector matching found no pair; a rule label overwrote the original value; the input had no sample during that interval; or the group missed an iteration. Check them separately: source-series freshness, expression output labels, recorded output, evaluation errors, and missed-iteration metrics. If an instant expression query returns a result but recorded samples are absent at certain evaluation times, inspect scheduling and evaluation duration. If the recorded values persist but consistently have a different label set, the rule contract or an override is more likely. That sequence is a proposed diagnostic method, not a report about a real incident.

Do not confuse an absent label with an empty string. An empty label value is equivalent to the label not existing in Prometheus. A query that appears to ask for zone="" may not be querying a distinct empty-valued identity. Before interpreting a missing label, confirm whether instrumentation omitted it, output configuration added an empty value, and how the selector actually matches.

Downstream queries depend on the label contract

Dashboards and alerts often reuse recorded metrics. If a dashboard depends on instance, changing a rule to aggregate across instances can leave the new calculation correct while removing the dashboard’s ability to answer “which instance is failing?” If an alert routes by service and a rule overwrites that value with a constant, a notification may still be sent, but with false service attribution. YAML parsing alone does not prove that consumers retain their meaning.

Before changing a rule, work backward from its consumers. List queries that require per-instance diagnosis, panels that only need path totals, and alerts that depend on environment, cluster, or service labels. Then choose the recording rule’s level. Removing instance may make sense for an overall service trend; incident diagnosis may need a separate series that retains the instance dimension or a query against the raw metric. Not every recorded metric should carry every label: high-cardinality dimensions also increase the number of series and storage cost. For each retained label, ask both who groups or routes on it and whether its value remains true after aggregation.

Pair the rule name with its output labels. Its naming guidance uses the level to indicate aggregation, rather than naming rules only after internal implementation details. A change review can state the old and new contracts explicitly: the former output grouped by instance and path; the new output groups by job and path. Then identify which consumers lose instance-level diagnosis and which remain unaffected. That is more useful than saying “metrics were optimized,” and it makes the exact semantics to restore during rollback clearer.

Test exact labels, not only values

The Prometheus project provides promtool test rules for rule tests. The format accepts input series and expected samples from PromQL expressions, as described in the unit-testing documentation. For a label contract, assertions should cover the recorded metric name, retained labels, removed labels, and values. Asserting only that a number equals a target misses a schema change in the series identity.

An unexecuted test design could use hypothetical inputs from two instances and two paths. First assert that an instance-level intermediate rule retains each instance; next assert that a sum without(instance) path-level output has no instance but retains job and path; then add a rule-level environment label and construct a group-label collision to assert the documented precedence. Another case can omit a method value from one side of a vector operation and confirm that unmatched elements disappear rather than being interpreted as zero. The matrix is proposed and was not run as a promtool test for this article.

Static validation and sample-level tests answer different questions. promtool check rules can validate rule-file syntax without starting a Prometheus server. A passing syntax check proves the file is valid, not that its labels meet dashboard requirements. Unit tests validate outcomes for specified inputs and evaluation times, but cannot prove that production scrape configuration, query load, rule duration, or all historical label values match the fixtures. Before rollout, inspect the rule group in the target environment and the actual consumer queries; where appropriate, observe output changes during a controlled window.

Record group evaluation failures, duration, missed iterations, source freshness, and output labels as distinct observations. If an output seems missing, determine whether the numeric value is zero, the vector has no element, or a sample exists under a different label identity. All three can look blank in a chart but call for different actions: arithmetic, matching or input availability, and identity-contract review. Keeping the original queries and before/after samples makes the diagnosis reviewable.

State who the recorded output represents

Successful rule evaluation does not guarantee that its output still supports instance-level diagnosis. The expression decides which input dimensions participate in grouping; vector matching determines which elements can be paired; group and rule labels can change stored key-value pairs; and missed evaluations leave gaps in time. Before interpreting the value, draw this transformation chain and verify series identity, label provenance, matching behavior, and runtime state separately.

Keep only labels that remain meaningful for the output, explain why each removed or overwritten dimension is intentional, and review the metric name, label set, and downstream dashboards or alerts together.
