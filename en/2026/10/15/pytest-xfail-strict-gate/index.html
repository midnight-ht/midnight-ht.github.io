An xfail Test Started Passing—Why Can CI Still Stay Green?

By default, XPASS is reported but need not fail the suite. Strictness changes the gate, not assertion validity; check configuration against the pytest version and retain removal evidence.

Article

Key takeaways

  • By default, XPASS is reported without failing the suite; strict=True or strict_xfail makes it a suite failure.
  • An XPASS may mean the implementation was fixed, or that the assertion or test conditions stopped exercising the defect.
  • Before removing a marker, verify the original requirement, current configuration, pytest version, and target commit.

By default, pytest reports an unexpected pass without failing the test suite; strict xfail can turn it into a gate failure, but it cannot prove that the assertion still covers the original defect. A green pipeline and a failed gate are each only part of the evidence. To decide whether an exception can be removed, return to the protected requirement, the path the test actually exercised, the current pytest configuration, and the commit that is about to be merged.

XPASS can be visible without failing CI

An xfail marker means that a test is expected to fail. When the test passes, pytest reports XPASS; when it fails as expected, it reports XFAIL. The current stable documentation says that neither XFAIL nor XPASS fails the test suite by default. So XPASS is not an ordinary PASS, but CI can still exit successfully if strictness has not been changed. In the pytest skip and xfail guide, XPASS is a separate report outcome for an expected-to-fail test that passes; the page also identifies the strict parameter that controls its effect.

That explains the apparent contradiction: the report can expose an outcome worth investigating while the process status still satisfies the pipeline's configured gate. The default is useful when a team wants to see unexpected passes without immediately breaking a legacy suite. But if a green gate is treated as proof that every old exception has been resolved, XPASS can turn into permanent noise. Conversely, making every XPASS fail can surface a large cleanup queue all at once. Strictness works best with an owner and an order for investigating the exceptions it reveals.

Strictness changes the gate, not the assertion's meaning

The local option is @pytest.mark.xfail(strict=True) on a particular test. If that test unexpectedly passes, the suite fails. Its scope is narrow and can fit a known issue for which the team wants a blocking signal when the expected failure disappears. A strict failure does not mean pytest has evaluated business correctness; it means the test passed despite a marker that said failure was expected.

A project can also define a suite-wide default. Current stable documentation uses strict_xfail = true to make XPASS fail for xfail markers that do not override the setting. The API reference lists both the marker's strict parameter and the strict_xfail option, with a default of false. Check how an explicit marker setting relates to the project default in the version and configuration actually used; a decorator alone does not reveal the behavior of every test in the suite.

There is a configuration migration detail. pytest 9.0 renamed the option from xfail_strict to strict_xfail while retaining the old name as an alias. The stable changelog currently lists pytest 9.2.0, released on 2026-10-27. This is the documentation context checked for this article, not the origin date of strict xfail behavior. The pytest changelog and API reference supply this version detail. A project pinned to an older pytest release should consult the documentation and runtime for that release instead of copying a current option name and assuming it took effect.

Avoid using --strict as shorthand for “fail on XPASS only.” Since pytest 9, the broader strict option enables several strictness settings. The API reference notes that future strictness options may also become part of that setting, so use it only when the version is pinned and the wider scope is intended. If the goal is specifically to maintain xfail behavior, an explicit option makes the gate easier to explain.

One unexpected pass can have two opposite causes

Imagine a cross-tenant read test marked xfail because of a known authorization defect. Later it reports XPASS. At least two explanations fit. The implementation may have been fixed and now correctly denies access to another tenant's data. Or the test may no longer traverse the original authorization path: the fixture could have changed to use one tenant, the route might bypass the protected reader, or the assertion may check response shape without checking data access. Either change can prevent the expected exception, but they mean very different things for a release. This is a hypothetical example; no real test was run and no project defect is claimed.

Start by recovering why the xfail exists: the inputs, expected business behavior, reason for expecting failure, and linked issue or support condition. Compare those conditions with the current test. First check whether identity, tenant, and target resource still form the intended cross-boundary combination. Then trace the call to the code responsible for authorization. Finally, inspect whether the assertion directly tests “data cannot be read,” rather than only checking that an error object or status field exists.

If the current test no longer checks the requirement, repair the test and then observe whether it passes, fails, or remains XPASS on the target commit. An XPASS from a repaired test is one piece of evidence that the implementation may have changed; it still needs confirmation against production code, the interface contract, and the relevant permission path. If the valid test still fails as expected, the xfail may remain necessary, but its reason and scope should be reviewed. Removing the marker is not itself a fix, and retaining it is not automatic risk acceptance.

Treat xfail as a maintained exception

pytest provides marker parameters such as reason, raises, run, and strict, but it has no built-in expiration date, owner field, or issue-completion state for an xfail marker. A team can keep a defect identifier, expected behavior, applicability, owner, and exit condition in the reason text or nearby review record. Those are team conventions; pytest does not verify them. The exit condition should be checkable, such as “after the target fix, verify this test on the supported Python and dependency versions.” Adding a future date alone does not make pytest execute or remove the marker when that date arrives.

The raises parameter narrows the expected failure to selected exception types; without it, an unrelated exception may be mistaken for the known failure. If a test cannot be run safely because it causes a known segmentation fault, run=False makes pytest skip execution and always mark it xfailed. These are different from running a test and observing an unexpected pass. A run=False test has not validated the current implementation, so it must not be presented as evidence that the test just passed.

Also distinguish xfail from skip. Skip means the test should not run when a condition is unavailable, such as a required database. Xfail means the test runs but is expected to fail. Marking a test xfail because its environment is unavailable can produce misleading XFAIL or XPASS reports. Conversely, changing an executed failure into a skip hides what the code did. A test plan should make both “was it executed?” and “what happened when it ran?” visible.

For a project with many old markers, enabling suite-wide strictness can reveal many XPASS results at once. Triage them in groups: first check whether each test still represents the requirement, then choose a marker-local setting, a global default, or the existing relaxed mode. Do not relabel every anomaly as acceptable just to restore green. At the same time, do not treat the count of strict failures as a count of defects; it may include fixed behavior, weakened tests, changed conditions, and configuration errors.

Verify the marker and the configuration CI actually uses

A proposed, unexecuted check is to prepare one deliberately failing case and one passing case, then apply marker-level strictness and the project default separately. Observe the XFAIL/XPASS report and final exit status. Current documentation shows that -r can add detail to reports, for example pytest -rxXs, but a more detailed summary does not replace reviewing the assertion. Collection, actual execution, marker application, working directory, environment, and configuration file all need checking; CI may be using a different context from a local run.

To temporarily check a configuration value, a controlled command can override the ini option, but the option name must match the installed pytest version. For example, pytest 9 documentation shows -o strict_xfail=true. Before and after an upgrade, record python -m pytest --version, the configuration file, command, test selector, and commit SHA, then run the relevant tests against the exact merge candidate. This article proposes a procedure; those commands were not executed and no XPASS output is invented.

When removing a marker, keep evidence tied to the code and environment actually being merged. A pass on another branch or with a newer dependency does not automatically qualify the current commit; closing an issue does not prove the assertion remains effective. Strict xfail makes a changed expectation visible. People still need to explain why it changed and what to do next.

For a related question about whether tests detect real regressions, see mutation testing and assertion gaps. XPASS tells the team that expected and actual outcomes diverged; it does not tell them whether the business defect is fixed. The gate, the assertion, and evidence for the requirement together determine whether the exception can be removed.
