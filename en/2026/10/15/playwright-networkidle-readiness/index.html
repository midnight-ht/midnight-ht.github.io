In Playwright, Wait for the User Task, Not Network Silence

networkidle reports a brief lack of connections, not rendered results or task success. Choose between URL, control, business-outcome, and network assertions based on the test contract.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-24 · Estimated read 21 min
Translations
zh-CN en

Article

Key takeaways

  • Five hundred milliseconds without connections establishes only that network condition, not task success.
  • Use actionability, destination URL, business outcome, and matched responses for their distinct contracts.
  • Sub-500 ms request gaps, stale responses, and empty/error results need explicit assertions.

Playwright marks networkidle as discouraged for tests: it observes 500 milliseconds without network connections, not whether the user's task has completed. For a search test, wait for results tied to the current query or an explicit empty state. For navigation, wait for the destination URL. Wait for a particular request or response only when network behavior is part of the contract being tested. One signal cannot stand in for another.

What does a quiet 500 milliseconds prove?

The Page API's waitForLoadState defines networkidle as no network connections for at least 500 milliseconds and labels it “DISCOURAGED”: do not use it to determine readiness in tests; rely on Web assertions instead. That definition does not promise that requests succeeded, data was accepted by the application, a component committed its render, or the visible result belongs to the current action.

Those are separate stages. A navigation response can arrive before JavaScript fetches data. A request can succeed while client-side validation produces an error. Data can arrive before the next state update replaces old content. Conversely, the page may keep sending analytics beacons or polling requests even though the search field accepts input and the save button is usable. Quiet connections do not establish whether the user can continue.

Playwright's navigation guide also notes that modern pages continue to fetch lazy data, populate UI, and load scripts or styles after the load event. There is no universal moment when every page is “fully loaded.” The precise point is not that network signals are never useful; it is that a network signal cannot answer a question it does not define. If the test contract is whether an endpoint returned a particular status, network observation is the contract. If the contract is whether the user sees the correct result, inspect the page state too.

Why can the same wait report success and still time out?

First, consider a false positive. Suppose a search page still displays the previous list of “black notebooks.” The user submits “teal notebook,” and the application briefly empties its request queue. After 500 quiet milliseconds, networkidle resolves. The server response then arrives, and the frontend still needs to parse, validate, and render it. Execution may continue while the old result remains visible or before any new result appears. The network wait passed, but it did not prove that the new query completed.

Now consider a false negative. A long-poll request keeps a connection open, or a sequence of short requests leaves gaps of less than 500 milliseconds. The list may already show “3 results for this search,” and the next user action may work, but the connection condition is still unmet. The test eventually times out with a message that sounds like “the page was not ready,” when the only unmet condition was unrelated network activity. This describes a hypothetical request cadence that satisfies the timing condition; it is not a measurement of a particular framework or live page.

The 500 ms value comes from Playwright's current API definition for this load state. It is not a measurement of application render time or a recommendation to copy a fixed delay into a test. Changing it to two seconds changes the wait condition; it does not turn an old list into a new one. A longer hard-coded delay can hide a race temporarily while making a real failure appear later.

Choose the wait from the test contract

An end-to-end test often combines three different questions: can the action run, where did the browser go, and did the product produce the right outcome? Each should use evidence that can actually establish it.

Test contract Useful evidence What it does not establish alone
The target can be clicked A unique target is visible, stable, receives events, and is enabled That the server saved something or the next page finished
Navigation completed The destination URL, route parameters, or page identity match That asynchronous data on the destination is ready
The user task completed New results, a success receipt, an explicit empty state, or a recoverable error is visible That no other request is active
A network contract was met A particular request matches method, target, and response status That the page consumed the response and rendered its result

Playwright's auto-waiting guide says locator.click() waits for the locator to resolve uniquely and for the element to be visible, stable, able to receive events, and enabled. Its assertions guide says Web-first assertions retry until the expected condition is met or times out. If a click causes navigation, waitForURL can separately check the destination. Actions, navigation, network behavior, and business outcomes can all be tested, but each assertion needs a clear boundary.

Sometimes the network itself is the subject. A test may verify that a request carries filter parameters, or that a 403 response produces a refusal message. In that case, declare the response wait before performing the action so the request cannot occur before the listener is installed. Then assert the method, URL, response status, and how the page handles the response. A 200 response proves a transport or endpoint condition; it does not prove that the list displays the corresponding data. Add a page assertion when rendering is also part of the product contract.

A search example: do not let the previous list satisfy this query

Consider a hypothetical single-page search screen. The user enters “teal notebook” and clicks Search. At first, the list may still contain the previous “black notebook” results. Once the server responds, the page updates the query and product rows; if there are no matches, it shows an empty state; if the request fails, it offers a retry message. This is a design example only; it was not run for this article.

The test's goal is not “the browser became quiet.” It is “the UI no longer presents the old query as the current one.” Locators depend on the actual application, but the pseudocode could look like this:

// Illustrative only; not executed against an application.
const responsePromise = page.waitForResponse(response =>
  response.request().method() === 'GET' &&
  new URL(response.url()).pathname === '/api/search'
);

await page.getByRole('searchbox').fill('teal notebook');
await page.getByRole('button', { name: 'Search' }).click();
const response = await responsePromise;
expect(response.status()).toBe(200);
await expect(page.getByTestId('active-query')).toHaveText('teal notebook');
await expect(page.getByTestId('search-results')).toContainText('teal notebook');

If the application allows overlapping searches, the response predicate should also distinguish the current query parameters; otherwise an older request could satisfy the wait. The page assertion still matters after the response because the response finishing does not mean React, Vue, or another UI layer has committed the state. Empty and error responses need their own assertions for an empty state, error message, or retry action. Otherwise a disappeared spinner can be mistaken for success.

The reason for separating these checks is attribution. With separate assertions, a test can locate “the search response returned 200” and “the displayed results belong to this query” in different layers. If the first check fails, inspect the response predicate. If it passes but the second times out, inspect response consumption, conditional rendering, the policy for retaining old results, or whether the page assertion targets the wrong object. A generic networkidle timeout often compresses these different failures into one unhelpful message.

Preserve evidence when a wait times out

Do not start by doubling the timeout. Record the stage where the test stopped, along with the current URL, query, request and response, actual objects in the result list, empty/error state, and a Playwright trace or screenshot. Then route the failure by its condition: a non-unique locator is a target-selection problem; no request may indicate an interaction or listener-order problem; a correct response with stale content suggests UI consumption, rendering, or state-association trouble; an error response treated as “ready” means the test never defined the error outcome.

A reviewable minimal search test can cover successful results, zero results, a service error, and a late response from an older query after a newer one was submitted. That final case matters: if “blue” is sent first and “green” second, a late “blue” response might overwrite the newer result. A useful assertion verifies the active query and result ownership, not merely that a list exists. Locators and test hooks should refer to real interface state; do not invent a separate “finished” marker that has no connection to what the user sees.

These are proposed tests and diagnostic steps, not results from running this site or an external application. No cross-browser stability, pass-rate, or time-saving data is claimed. Before writing a real test, check the Playwright version installed in that project as well as the current documentation. The links here lead to the current public docs, and API details can change across versions.

When should a test still wait for network activity?

When the network event is the target: a test really does need to establish that a request was sent, a response arrived, or a service-level flow finished. Match the specific request where possible instead of waiting for every connection on the page to stop. If the question is which control to click, resolve locator ambiguity first. If it is when the corresponding result appears, use an assertion tied to the object and state. For the first question, see locator ambiguity and positional choice; it answers “which element,” while this article addresses “which condition is sufficient to continue.”

If the only reason for waiting is that “the page still seems to be loading,” networkidle has not defined what the test must prove. Replace it with an observable condition for the user task, so a timeout can tell you which layer of evidence is missing instead of leaving you to guess when the network will stop.
