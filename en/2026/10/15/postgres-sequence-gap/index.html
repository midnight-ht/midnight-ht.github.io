A PostgreSQL Sequence Gap Does Not Prove a Lost Record

Rollback, ON CONFLICT, and sequence caching can leave gaps. Diagnose them against committed rows and business state; do not treat a primary key as a completion counter.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-25 · Estimated read 18 min
Translations

Article

Key takeaways

  • A sequence is a concurrency-safe value allocator, not a count of committed rows or completed work.
  • Rollback, conflict handling, and caching can leave gaps; a gap alone does not prove committed data was lost.
  • A genuine gapless business-number requirement needs separate serialization, void, and recovery rules, with a concurrency cost.

A PostgreSQL sequence consumes a value when nextval runs; rolling back the calling transaction does not return it. A gap therefore shows that a value was allocated, but it does not by itself prove that a committed row was lost. A sequence provides distinct values safely under concurrency, not a transactional count with no gaps. If a business really requires consecutive numbers, allocation, voiding, and recovery become a separate design problem.

nextval advances allocation state, not the number of committed rows

The PostgreSQL 19 sequence-functions documentation says that nextval atomically advances a sequence so concurrent sessions receive distinct values. The transaction-isolation documentation also lists sequence changes as special transactional behavior: they become visible immediately and are not rolled back when the changing transaction aborts. nextval does not wait for the caller's transaction to commit before deciding whether the number remains consumed. This lets concurrent inserts obtain values without blocking one another to reclaim a number after a failure. The tradeoff is that sequence state does not roll back with an ordinary row update.

Consider a hypothetical table. Session A inserts a task, receives 41, then fails validation and rolls back. Session B inserts a valid task and may receive 42. There is no row 41, but that observation is entirely consistent with A having allocated the number before failing. Looking only at max(id) - count(*), or at the distance between neighboring identifiers, cannot tell whether A rolled back, a conflict path ran, or an import used another numbering path. Those values do not replace checking committed rows and transaction outcomes.

A conflicting insert can consume a value too. The sequence-functions documentation for PostgreSQL 19 notes that an INSERT ... ON CONFLICT may evaluate its candidate row, including the required nextval, before it discovers the conflict and takes the conflict branch. Therefore, “the statement inserted no new row” and “the sequence did not change” are different claims. Retries, unique-constraint conflicts, and bulk writes can all produce allocated values that do not appear on a newly inserted row.

The values 41 and 42 here are hypothetical examples, not logs captured from a database or incident. To determine a real gap's cause, inspect committed rows in the target table, relevant request or job outcomes, conflict handling, and database errors. Without that evidence, the strongest justified conclusion is only that a value does not appear in the current row set.

Caching makes “the last number” harder to interpret

Sequence caching changes how sessions reserve values. With CACHE greater than 1, a session can preallocate a range, as the PostgreSQL 19 CREATE SEQUENCE documentation explains. Values reserved but not used when a session ends become gaps. Even though different sessions receive distinct values, the global order of values they return need not be strictly consecutive. For example, A may reserve 1 through 10 and return 1; B may reserve 11 through 20 and return 11; A can still return 2 later.

The same documentation says that with a cache greater than 1, last_value can reflect a value reserved by a session but not yet handed out. Treating it as “the last committed row ID” or “how far the business has completed” confuses four different states: reserved, returned, inserted, and committed. The sequence-functions documentation also notes that last_value from pg_get_sequence_data can be greater than the last value actually delivered to a caller when caching is enabled. It is sequence state, not a business completion report.

If the question is “which number did this session most recently obtain?”, currval answers with that session's latest nextval result. It does not tell you what another session allocated, and it does not establish that a row with that value committed. Choosing the right function still requires limiting the claim: session-local state is not global allocation state, and global allocation state is not committed business state.

Investigate a gap without creating another problem

Start by stating which question needs an answer. For “does record 41 exist now?”, query the business table while accounting for soft deletion and archival. To learn “why did 41 never become a row?”, inspect the corresponding request's transaction outcome, conflict branch, and error record. Whether an external system processed 41 requires evidence from the handoff and that system's result. The current nextval, last_value, or maximum primary key cannot reconstruct every historical call and commit order.

After finding a gap, do not move the sequence backward or reuse the value by default. setval changes sequence state immediately, and a rollback of the caller does not undo that change. Concurrent sessions may already hold cached values; the documentation also warns that other sessions may not immediately observe a setval change while cached values remain. Moving backward can conflict with existing rows or with values already reserved by other sessions. Unless there is a maintenance window, concurrency control, and a verified data-reconciliation plan, filling the visible gap only makes the numbers look tidy; it does not repair record state.

There is another boundary when a sequence value will be used persistently outside the database. For persistent use outside the database, PostgreSQL 19 advises confirming that the transaction containing nextval has committed first. After a crash before commit, it may be uncertain whether the sequence state was persisted. Even confirmed commit proves only that the database transaction completed; it does not prove that an external message, queue, or third party completed its work. The two systems need their own handoff record, idempotency key, or recoverable state. See transactional outbox and notification handoff for a related design.

A genuinely gapless business number uses a different mechanism

An ordinary primary key usually needs to be unique and stable. Allowing gaps supports concurrent allocation; the key should not be repurposed as a count of completed invoices or tasks. If a business process really requires consecutive numbers, first define its rules: at what state is a number formally issued, how are voids recorded, can a failed number be reused, who can correct it, and does a report count issued, voided, or completed items? This article does not assume that a particular industry regulation requires gapless numbers, and it does not treat a database implementation as a compliance conclusion.

An exclusive lock on a table containing a counter can be used to construct gapless allocation, the CREATE SEQUENCE documentation explains, at substantially higher cost than a sequence. The reason is straightforward: a sequence lets concurrent callers obtain distinct numbers; a transactional counter must serialize the update so only one allocation advances the counter at a time, and it must make rollback behavior match the business rule. A hot counter row can increase wait time, and throughput becomes sensitive to the slowest transaction. Evaluate lock waits and failure recovery under the intended workload rather than assuming this design is automatically more correct.

The counter also needs an explicit rule for “reuse after rollback.” If a number has already been shown to a user or written to an external system, silently assigning it to a different business record may be unsafe. One option is to retain the failed number as a void with an audit trail; another is to withhold it from external visibility until issuance is confirmed. The choice depends on business rules and when the number becomes visible, not on whether the database column uses serial or identity syntax.

Verify which numbering contract the team actually uses

For the target PostgreSQL major version, real cache setting, and every write path, design a verification matrix: obtain a number and roll back; run an ON CONFLICT insert that creates no new row; allocate concurrently in multiple sessions with CACHE 1 and a larger cache; end a session with reserved values; and hand a number to an external system before and after commit. For each case, record sequence observations, committed rows, transaction outcome, and external handoff state. This separates “a value was allocated without a new row,” “a cached reservation went unused,” and “expected business data is actually missing.”

This article did not run those tests against PostgreSQL and did not measure lock contention, crash recovery, or an actual system's missing values. The plan is meant to make a later experiment distinguish each state, not to claim that a cause has already been proven. A gap can be an expected consequence of allocation or a reason to investigate. The conclusion comes from row, transaction, and handoff evidence—not from whether identifiers form an unbroken sequence.
