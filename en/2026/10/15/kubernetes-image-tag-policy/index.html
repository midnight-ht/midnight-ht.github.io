Always Still Downloads Very Little: Which Image Is the Node Running?

imagePullPolicy: Always resolves a reference again while reusing cached layers. Check the Pod template, runtime imageID, and rollout to verify a release.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-24 · Estimated read 21 min
Translations
zh-CN en

Article

Key takeaways

  • Always requests reference resolution when a container starts; it does not require every image layer to be transferred again.
  • Moving a tag in a registry does not change a Deployment Pod template or independently trigger a rollout.
  • Verify the desired image, Pod template, runtime imageID, and rollout separately; network traffic is not a release receipt.

Low image-layer traffic under imagePullPolicy: Always does not, by itself, prove that a node reused stale code. Whenever kubelet starts a container with this policy, it asks the container runtime to contact the registry and resolve the image reference. If the layers for the resolved image are already cached on the node, the runtime can avoid downloading them again. To determine whether the workload adopted the intended version, inspect the Pod template, runtime-reported image identity, and rollout state; network bytes are not a release receipt.

Always requests resolution; it does not retransmit every layer

The Kubernetes images guide distinguishes three policies. IfNotPresent pulls only when the image is not local; Never does not try to fetch it; and Always asks the runtime to resolve the reference when a container starts. The runtime contacts the registry, resolves a tag or name to a digest, and fetches layers not already cached on the node. If all required layers exist, the cached image can be reused. The guide also says kubelet does not itself check the local cache; it delegates to the runtime.

These actions answer different questions. Always means a container start still asks the registry to resolve the reference. It does not mean the full image is transferred every time, and reuse of some layers does not show that the reference points to old content. Conversely, seeing a download does not prove that the business has switched to the approved version. The transfer might be for a missing layer, an architecture-specific image, or another Pod, and a single pull log lacks the object and time context.

Image layers are content addressed. In the OCI Image Specification, a descriptor uses a digest to identify referenced content and recommends verifying content retrieved from an untrusted source against that digest. A tag is a readable reference name; a digest is a content identity. The registry may move a mutable tag to different content over time, while a fixed digest requests a particular content identity. They serve different operational goals: tags are convenient for selecting versions, while digests help reproduce and compare them. Kubernetes also warns that if a registry changes the code represented by a tag, Pods can end up running different content; for production, consider meaningful version tags and/or digests.

A registry tag change does not publish a Deployment by itself

Separate “the tag moved in the registry” from “the Deployment’s .spec.template changed.” The registry-side change is not visible to the cluster controller. A Pod-template change is what triggers a Deployment rollout, such as changing the image field in the template. The Kubernetes Deployments guide explicitly says only Pod-template changes trigger a rollout; scaling replicas, for example, does not trigger this update flow.

If a Pod template contains service:stable, and the registry changes stable from digest A to digest B while the Deployment object retains the same template text, that tag movement does not automatically create a new ReplicaSet. Existing Pods are not restarted simply because the tag now points to B. A newly created Pod may resolve the tag to its newer digest when it starts. This can produce a subtle transition: old Pods continue serving while new Pods may use a newly resolved image. Without binding a release to an immutable identity, the same service can temporarily run different content.

The default pull policy is not guessed again from the current tag every time. The images guide says the API object receives a default imagePullPolicy when it is first created under the then-current image-reference conditions; later changes to the tag or digest do not automatically recompute the policy. For example, an object initially created with a non-latest tag may receive IfNotPresent; changing its image to latest later does not automatically change the existing policy to Always. Inspect the stored Pod template and actual Pod spec rather than only current Helm values, Kustomize overlays, or submitted YAML. Template rendering, admission mutation, and object history can make the final object differ from the source file.

Follow four kinds of evidence to locate the release

A useful diagnosis starts with the release intent, not “why was there no download?” First record the expected registry, tag, digest, build source, and change time in the release record. Second, read the Deployment’s .spec.template.spec.containers[].image and imagePullPolicy to confirm the image reference and policy held by the cluster. If a registry tag moved while the template did not, the missing event is in the release trigger, not necessarily the node cache.

Third, inspect the rollout and ReplicaSets: Deployment revision, updated ReplicaSet, desired and available replica counts, and creation times for the Pods involved. A rolling update can have old and new Pods at the same time. One inspected Pod does not establish that all instances have switched. The official guide recommends using kubectl rollout status to observe an update and then inspecting the Deployment, ReplicaSet, and Pods. A completed rollout status means the controller reached its state conditions; it does not by itself prove business metrics, every external traffic path, or image supply-chain approval.

Fourth, inspect each serving container’s status. The Kubernetes v1.35 API describes ContainerStatus.image and imageID as the image and image ID reported for a running container, but specifically notes that runtime resolution can make them differ from the PodSpec text. Do not compare the imageID string to YAML as a simple equality test, and do not assume every runtime exposes an OCI manifest digest in the same textual format. Record the Pod UID, node, container name, creation time, imageID, and expected release digest together, then map them according to that cluster’s runtime. If an admission controller rewrites images, retain both the declared and final Pod objects.

The following is a proposed check sequence to run against the target cluster; it was not run for this article:

kubectl get deploy app -o yaml
kubectl rollout status deploy/app
kubectl get pods -l app=app -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.containers[*].image}{"\t"}{.status.containerStatuses[*].imageID}{"\n"}{end}'
kubectl describe pod <pod-name>

The first command reads the current declaration; the second watches controller progress; the third puts each Pod’s requested image and reported image ID together; the last shows events and status for one Pod. In a real incident, include the namespace, time window, and workload selector, and inspect desired, updated, and available replicas with kubectl get deploy. If a Pod is in ImagePullBackOff, examine events for registry authentication, image-name, network, or digest problems. With Always, a new start can depend on registry access; cached layers should not be treated as a guarantee of offline startup.

Choose tags, digests, and policy for the actual goal

For a reproducible release, pin the digest in the release record and make the approved version, Pod template, and runtime instances traceable to one another. If a team still uses movable tags to roll out releases, it needs an explicit template-update mechanism: change to a new version tag, alter another release identifier in the template, or update the image reference through a controlled process. Overwriting the same tag in the registry is not a cluster-side release event. An immutable digest reduces ambiguity about whether the same declaration can yield different content, but it needs an update, vulnerability-response, and rollback process. Pinning is not a reason to leave a risky image unchanged indefinitely.

Policy choice also depends on registry availability and node management. Always requires the runtime to reach the registry and resolve the reference whenever a container starts. Missing credentials, DNS, connectivity, or registry rate limits can block a new container even when some layers are local. IfNotPresent can prefer a local image, but when a node has old content for a mutable tag, the started instance can differ from current team intent. Never depends on a preloaded image and fails to start when that image is absent; it fits controlled environments where node image provisioning is explicit. None is universally “safest” outside the release and node-management context.

Consider a hypothetical diagnosis: two of three Pods report an imageID corresponding to digest A, while the third Pod is starting in a new ReplicaSet. The registry’s stable tag now points to digest B; the Deployment still says stable and uses Always. Low traffic can coexist with runtime reuse of matching layers, but it does not tell us that all three Pods are now B. Compare the Deployment template first, then inspect the new Pod’s resolved imageID, ReplicaSet progress, and which Pods actually receive business traffic. If the third Pod is waiting because registry authentication failed, the fetch path has not completed. If both old and new Pods are available, this is a mixed-version rollout window whose handling depends on rollout policy and application compatibility. The three replicas and digest letters here are hypothetical; no real cluster was accessed.

A release record should retain at least the registry and immutable digest, build source or artifact attestation, target workload and changed template, rollout observation, relevant Pod UIDs and runtime imageIDs, observation time, and the scope of business validation. To prove that traffic has moved, use request attribution, instance labels, or observability data showing actual routing; Pod status alone is not a traffic-share measurement. For the earlier artifact identity chain, see verifying build-artifact identity.

Why did changing the tag in the registry not update the Pods? A registry tag change does not rewrite a Deployment’s Pod template, so it does not necessarily trigger a rollout. If the cluster later creates a new Pod, that Pod may resolve the tag again under Always; this still does not replace an explicit template release and verification of old and new instances.
