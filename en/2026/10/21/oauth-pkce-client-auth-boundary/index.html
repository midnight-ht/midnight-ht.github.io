PKCE passed. Why must the API still reject the token?

PKCE protects code exchange. Client authentication and the resource API’s audience, action, and object checks answer separate questions.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-21 · Estimated read 16 min
Translations
zh-CN en

Article

Key takeaways

  • PKCE ties a verifier to one authorization-code exchange; it is not a durable client credential.
  • Confidential-client authentication and token audience and action restrictions need separate tests.
  • An API should reject a token for the wrong resource or action and leave business state unchanged.

An access token issued after a PKCE-protected authorization flow may still have to be rejected by the orders API. PKCE checks whether the party redeeming an authorization code can supply the verifier associated with that particular authorization request. It does not decide which API may accept the resulting token, or whether a user may cancel a particular order. A test report that collapses those questions into one “OAuth passed” checkbox misses the request most likely to expose an integration error.

What PKCE binds at the token endpoint

Imagine a mobile client preparing to call a profile API. Before starting the authorization request, it creates a fresh code_verifier, derives an S256 challenge from it, sends the challenge to the authorization server, and retains the verifier locally. After the user authorizes, the client receives an authorization code and submits that code with the original verifier to the token endpoint. The server compares the verifier with the challenge associated with the code. An attacker who obtained only the code should fail at this exchange because they cannot supply its verifier. This is protection against misuse or injection of an authorization code, not proof of the software publisher’s identity. RFC 9700 §2.1.1 requires PKCE for public clients, recommends it for confidential clients, and identifies S256 as the current challenge method that avoids exposing the verifier in the authorization request.

“The server verified a secret” is an imprecise description here. A public client generates a verifier for one flow; that value is not a durable credential issued to identify an installation. Someone who controls their own copy of a public client can start their own legitimate PKCE flow. A matching challenge does not certify that the binary is an untampered official build. A confidential client that can protect credentials, on the other hand, may also have to authenticate to the token endpoint by its registered method. RFC 9700 recommends client authentication where credentials can be issued and kept confidential, with asymmetric methods recommended. Client authentication and PKCE can therefore coexist. Record whether the per-flow challenge matched separately from whether the applicable client-authentication requirement was met.

The callback is not the resource authorization decision either. A client must associate an authorization response with the session that initiated it. If it relies on PKCE for cross-site request forgery protection, it must know the authorization server supports and enforces PKCE; accepting a code flow that silently omits the challenge creates a downgrade path. Registered callback matching is another constraint to test in its own right; see this site’s discussion of exact OAuth callback matching. These measures make the authorization flow harder to hijack. None of them establishes that a token belongs at the orders API.

The API has a separate decision to make

Work through a hypothetical system. In this example, an authorization server issues a token intended for the profile service at https://api.example.test/profile, with permission to read the user’s own profile. The mobile client mistakenly sends that token to https://api.example.test/orders/42/cancel. The Authorization header is syntactically correct, the token has not expired, and its signature or introspection response is authentic. The orders API must still reject it: its audience is the profile service, and permission to read a profile does not grant permission to cancel an order. A useful integration test would show profile reading succeeding, order cancellation being rejected, and order 42 remaining unchanged. This is a design example, not an executed request against a real service. RFC 9700 §2.3 says resource servers should verify for every request whether the token was meant for them and whether it covers the requested resource and action.

Audience and action restrictions answer different questions. Audience limits a token to a resource server; it prevents a token accepted by one service from being treated as valid at another. A scope or more detailed authorization information narrows what can happen within that service. Even a token correctly addressed to the orders API does not permit cancellation of every customer’s order. The service still needs to evaluate the current subject, order ownership, business state, and requested action. With an opaque access token, the API might obtain these attributes through trusted introspection. With a JWT, it must validate the signature, issuer, audience, and token purpose under the chosen token profile. Neither representation makes PKCE a shortcut for resource authorization.

Consider the opposite counterexample. A backend authenticates as a confidential client and receives a read-only token. The backend may be trusted to identify itself, yet the token is still read-only. If the resource server interprets “authenticated client” as “write permitted,” it has imported a token-endpoint identity decision into an unrelated business decision. Conversely, the absence of a long-term client secret in a public app does not exempt its tokens from audience, lifetime, or action restrictions. The client type determines how it can authenticate; the resource’s needs determine which token and permissions it should accept.

Put the three checks into the test contract

Use three columns rather than one security checkbox. The authorization-flow column lists the challenge method, verifier, and one-time relationship to the code. A second column lists registration type and its authentication requirement. The resource column lists intended audience, allowed actions, and object ownership. In the flow column, the correct verifier should redeem the code while a verifier altered by one character should fail. An omitted challenge should fail where PKCE is required; exact error responses depend on the server. In the client column, remove or replace a confidential client’s credential and check that a correct PKCE verifier does not override that failure. Do not treat a public client’s client identifier as a confidential credential. The resource column then asks the tester to use an authentically issued token but change the target API, action, or object. The resource service should reject each unauthorized variation. There is no need to forge a bad signature to test audience enforcement.

Run those negative cases with isolated identities and resources, and check that a rejection left the business state untouched. Asserting only a 401 or 403 response can miss a defective implementation that writes first and reports an error afterward. The precise status code should follow the service’s authentication and authorization contract. Capture the audience and permissions the authorization server actually issued, then compare them with each API’s allowlist. That comparison reveals a mismatch far more reliably than a successful interactive login alone.

Decide whether sender-constrained tokens are needed from the token-leakage threat model, not from a wish to rename PKCE. RFC 9700 discusses mTLS and DPoP as ways to bind access-token use to a holder. They address replay of a leaked access token and bring their own client support and deployment costs. If a system uses bearer tokens, prioritize TLS, limited token lifetime, narrow audiences and permissions, revocation paths, and anomaly monitoring according to its risk. None of these single controls removes every replay risk.

The division of responsibility is concrete. At issuance, the server checks the code and verifier, authenticates clients as appropriate, and limits issued tokens. On the client side, the ongoing flow and tokens need protection. Each API checks, on each request, that the token is meant for it and that the requested action on this object is allowed. “PKCE enabled” records only part of that contract; it cannot predict the outcome of the order-cancellation request.
