What strict-markers Catches—and What Selection Still Misses

An integration-test typo shows how marker registration, strict collection, and a nonempty -m selection check cover different failure modes.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-21 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • Register custom markers and enable strict_markers to reject unknown decorator names during collection.
  • Strict markers do not prove a -m expression selected the intended tests; check cardinality and critical node IDs.
  • Selected, skipped, xfailed, and passed tests provide different evidence.

A CI job runs pytest -m integration to cover database integration tests. A developer marks a new test @pytest.mark.intergration, misspelling the marker name. Running the whole suite locally still executes the test, but the CI expression does not select that marker, so the test may quietly disappear from the job. strict_markers turns an unknown decorator marker into a collection error. It does not, by itself, prove that a -m expression selected the intended tests. Preventing this kind of omission takes two gates: a registered marker vocabulary and a check of the selected test set. The pytest guide to custom markers recommends registration and says strict mode treats typos in function markers as errors.

Give marker names a controlled vocabulary

Suppose a repository has fast unit tests and integration tests requiring a local database. Its configuration registers integration: requires local database and slow: may exceed normal unit budget; a database test uses @pytest.mark.integration. pytest --markers can list the approved names and their meanings. With strict_markers enabled, @pytest.mark.intergration is an unknown marker at collection time. The job fails rather than merely warning and then running a selection that excludes the test. Registration also tells reviewers what “integration” means in this repository instead of leaving the decorator as an unexplained word.

Work through three tests. test_total is unmarked, test_db_insert has the correct integration marker, and test_db_update has the mistaken intergration marker. The CI job intends to run both database tests with pytest -m integration. Without strict marker enforcement, collection may warn about the unknown name and the selector may run only test_db_insert; one passing test can produce a reassuring green result while test_db_update was never exercised. Register only the correct integration marker and enable strict markers: the misspelled decorator now causes collection to fail, so the job cannot mistake “one passed” for complete integration coverage. This is a worked inference from pytest's documented behavior, not actual output from this repository's CI.

Make the policy visible in configuration. In pytest.ini, add a [pytest] section with a markers = list defining integration: requires local database and slow: long-running scenario, and set strict_markers = true. The command-line --strict-markers option is also available, but repository configuration keeps local runs and different CI entry points on the same rule. Marker descriptions should define selection intent without exposing environment secrets. When retiring a marker, migrate its uses before removing registration, so a predictable collection failure does not become a surprise in an unrelated change.

Strict registration does not validate the selector

Now reverse the typo. Every function correctly uses @pytest.mark.integration, but the CI command is pytest -m intergration. There is no unknown marker in the source decorators for strict_markers to reject. The selector can collect tests and deselect them all. Exit handling can vary with wrappers or plugins, so the job should have its own assertion about how many tests it meant to select. Retain the original collected, selected, and deselected output. A green-looking terminal line without the selected set is not enough evidence.

A dedicated integration job can first run pytest --collect-only -q -m integration, capture the selected node IDs, and stop with a clear message if there are none. Then run the same expression for real. If two critical tests are mandatory, check that their node IDs are present, not merely that the selection size is above zero. A nonempty gate catches an empty selection but does not prove the correct tests were chosen. A critical-ID list needs maintenance as the suite evolves. The two checks serve different purposes; do not freeze a count and call it test coverage forever.

Marker expressions can change the set in less obvious ways. -m 'not slow' includes unmarked tests; it does not mean “unit tests only.” -m 'integration and not slow' intentionally excludes integration tests also marked slow. Module-level pytestmark, class decorators, and marks on individual parametrized cases can change the effective selection. Review the actual collected node IDs rather than inferring coverage from the command text. A selected integration test that skips because the database is missing has not completed its assertion. Report selected and passed counts separately.

Similar names are not a hierarchy. If the repository uses both integration and integration_api, -m integration does not automatically include the latter. Give every test needed by the integration job the shared integration marker, with an optional second marker for the subtype, or maintain and review two explicit selection expressions. A path argument can filter a moved test out before -m has any chance to select it, even if its marker is correct. Inspect the intersection of collection path and marker expression as concrete node IDs.

Our related article on strict xfail handling covers a different false green: a test that was expected to fail starts passing. Here the test may not run at all. Keep collection failure, zero selection, runtime skip, xfail, and genuine pass as separate statuses. Before changing CI selection, preserve pytest --markers, the collection summary, pytest version, and configuration source. Registration plus a nonempty selection still cannot prove sufficient behavioral coverage, but it makes one silent omission observable.

Verify the gates with a small isolated fixture

Create the three tests above in a minimal project with the correct marker registration. Leave the intergration decorator in place and predict a collection error under strict markers. Fix the decorator and confirm that -m integration selects exactly the two database tests. Then deliberately mistype the CLI expression as -m intergration and confirm that the job's nonempty-selection check reports a failure. Save the complete config, commands, pytest version, and raw stdout before calling these predictions measured results. No pytest probe was run for this article, so it supplies no invented exit code or selected count. In the real repository, also inspect plugin-provided markers, discovery paths, and wrappers that might swallow failures.

A concise team rule follows. Register and explain each new marker, reject unknown decorators during collection, verify that each dedicated -m job finds its intended node IDs, and report pass, skip, xfail, and failure after execution. A misspelled test_db_update decorator then fails at collection. A misspelled CI selection fails its selection gate. A missing database shows up in runtime status. Three distinct defects need three distinct pieces of evidence; a single green CI badge cannot stand in for all of them.
