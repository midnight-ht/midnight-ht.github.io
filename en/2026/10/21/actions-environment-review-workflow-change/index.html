Three checks for a release: environment, workflow, and artifact

GitHub environment approval releases a deployment job; review workflow changes and artifact origin separately to know what will ship.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-21 · Estimated read 16 min
Translations
zh-CN en

Article

Key takeaways

  • One named required reviewer can approve an environment job; verify actual settings.
  • Code-owner review of workflow changes serves a different purpose from environment approval.
  • Bind commit SHA, run ID, artifact digest, and target before approving.

A GitHub Actions job is waiting for approval to enter production, so the deployment appears to have a gate. The same commit, however, also changed .github/workflows/deploy.yml: instead of downloading the artifact from the expected build, it now downloads one from another run ID. An approver who checks only the environment name and green status checks may release something other than the deployment they understood. Approval of the environment, review of the workflow file, and verification of release inputs answer different questions.

Environment approval gates a job

The GitHub environment documentation says that a job referencing an environment must follow that environment's protection rules; environment secrets are not made available to the job until the rules pass. Required reviewers and branch or tag restrictions are examples, but feature availability depends on repository visibility and plan, so inspect the actual target repository. Several people can be named as required reviewers, yet GitHub requires only one of them to approve the job. A team requiring two independent approvals must not read “two people listed” as “two votes required.” Preventing self-review is also a distinct setting that must be enabled.

This gate answers whether this job may proceed into the named environment. It does not automatically answer who changed the workflow file, which artifact the script will deploy, or whether the target account still matches policy. The approver sees a pending run; approving it does not imply that someone reviewed every .github/workflows change in the commit. Those protection rules cannot retroactively secure high-privilege steps that already ran in another job. If build, signing, or artifact selection occurs elsewhere, those jobs need their own input and permission review.

At approval time, record the run's commit SHA, trigger event, target ref, environment name, and workflow revision. A “production deploy” display name may conceal different YAML content. An artifact name may also refer to files from different runs. If workflow_dispatch inputs can select an artifact or destination, the resolved input values are part of the release definition too. These fields let a later reviewer establish what was approved instead of finding only an “Approve” click on a particular day.

Workflow files and artifacts have separate boundaries

GitHub's secure-use guidance recommends putting .github/workflows under CODEOWNERS. To turn that ownership into a barrier, combine it with branch protection or a ruleset that requires code-owner review: a workflow change should not merge without the designated maintainers. Protect the CODEOWNERS file itself so a contributor cannot remove the ownership rule in the same change. Review more than YAML validity. Compare triggers, permissions, third-party action sources, artifact download location, deployment commands, environment names, and writable targets.

The artifact is another boundary. Even if deploy.yml is untouched, a release job that accepts a mutable artifact name, arbitrary run ID, or manual input may deploy bytes unrelated to the expected commit. A design can require a verifiable relationship among the target commit SHA, build run ID, storage location, and artifact digest or signature. Whether signatures are practical depends on the existing supply-chain setup, but a file named release.zip is not proof of origin. Show the approver the resolved identifiers, not merely the literal template expressions. If artifacts cross repositories or workflows, verify that source's permissions and retention as well.

These controls have distinct jobs. The environment rule determines when the deployment job can continue. Code review constrains changes to the execution definition. Artifact checks constrain where deployed bytes came from. Calling all three “approval” hides the gap between them. Concurrency control addresses how deployments queue or exclude each other; the site's deployment concurrency article covers that scheduling question, which does not replace change and input review here.

Test the three checks against one hypothetical release

This is a review exercise, not a workflow run or production deployment. Suppose main-branch commit abc123 changes service code and its build job produces an artifact with digest sha256:AAA. It is destined for production through deploy.yml. The intended path is: the protected branch requires code-owner review for workflow files; the build record binds abc123, run ID 417, and the artifact digest; the release job downloads that digest from run 417; a required environment reviewer sees these values and approves; only then can the job receive environment secrets and deploy. The expected outcome is that production receives the bytes built for abc123, and the audit trail identifies file review, artifact identity, and job release. This remains an expected outcome, not an observed deployment receipt.

Now change the download source in the same commit to run ID 402, which has digest sha256:BBB, while the job and environment still say “production deploy.” The environment rule may still pause correctly and accept approval from one reviewer. It will not decide whether 402 belongs to the approved commit. Without protected ownership review, the YAML change may pass unnoticed. Even if file review catches this change, an arbitrary manual run-ID input can leave the same gap elsewhere. The right decision is to stop, trace 402 to its producer and commit, and reject or correct the run as necessary. A clickable environment approval screen is not evidence that the artifact is the intended one.

Another failure is procedural. A team lists several candidate reviewers and assumes two people must approve every release. GitHub's documented rule is that one approval suffices. If a policy truly calls for two-person review, establish and verify a separate process that enforces it. Self-review prevention, administrator bypass, and branch restrictions are separate settings too. Availability may differ by plan and repository visibility; a control in an architecture diagram is not proof that it is active in the target repository.

Review the run, not the button

Start in a test repository or a non-production environment. Inspect which protection rules the current plan supports, and preserve the actual environment settings, branch rules, and CODEOWNERS match. Use a test PR changing only the workflow's artifact source to confirm whether it is blocked without owner review. Run a restricted test environment to check that secrets remain unavailable before approval and that approval releases only the intended job. Finally compare the run ID, commit SHA, artifact digest, and deployment target seen at approval with those in the execution record. Use artifacts without production credentials; validation should not become an accidental live deployment.

The subject here is the trust scope of one deployment approval, not an assumption that an environment replaces all supply-chain controls. If the workflow cannot select artifacts from outside its own build, protect workflow changes and permissions first. If a package crosses several pipelines, artifact identity may be the primary gap. In either case an approver should be able to answer: Which commit defined the steps? Which run produced these bytes? Which environment job am I releasing? If those answers are missing, pause approval and establish them rather than inferring release integrity from a green approval screenshot afterward.
