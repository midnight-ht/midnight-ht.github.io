JSON Schema allOf: Where to Close an Extended Object

See why additionalProperties rejects an outer field under allOf, then compare unevaluatedProperties and explicit final field lists.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-21 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • allOf requires each subschema to pass and does not merge them as inherited classes.
  • additionalProperties sees declarations in its own subschema.
  • With a supported dialect, unevaluatedProperties can close an object after successful composition.

An address schema originally accepts street. A team adds kind through allOf, but {"street":"Main","kind":"business"} now fails with “kind is an additional property.” The field appears in the outer schema, so why does an inner schema reject it? allOf is not an instruction to merge declarations into one global list. The instance must independently satisfy every subschema, and additionalProperties: false recognizes properties declared in the same subschema as itself. The JSON Schema object reference states this scope explicitly, while the combining reference warns against reading allOf as object-oriented inheritance.

A field visible outside can still fail inside

Imagine a base schema that declares street and sets additionalProperties: false. The application includes that base under allOf, then declares kind at the outer level. The full object is first evaluated against the base. It recognizes street but not kind, so the base fails. Passing the outer kind constraint cannot reverse that failure. Putting another additionalProperties: false on the outer level can cause a second rejection, because the outer level does not necessarily see street as one of its own declarations. The error path and the keyword responsible for it are more useful than the observation that the field name appears somewhere in the document.

This small schema illustrates the conflict. It is an example, not the contract of a live API:

{
  "allOf": [{
    "type": "object",
    "properties": {"street": {"type": "string"}},
    "required": ["street"],
    "additionalProperties": false
  }],
  "properties": {"kind": {"enum": ["business", "residential"]}},
  "required": ["kind"]
}

For {"street":"Main","kind":"business"}, the inner schema treats kind as undeclared. It is not making a business claim that kind must never exist. The current composition has treated a closed subschema as an extendable base class. Reading allOf as logical AND makes the problem plain: the same object must satisfy both “only street is allowed here” and “kind is required.” In this arrangement those constraints conflict.

Choose where to close the object

If the base schema can change, remove its closing rule and let it validate the fields it owns. After the composition, a schema using a draft that supports unevaluatedProperties can set unevaluatedProperties: false outside allOf and beside properties.kind. That keyword takes properties successfully evaluated by applicable subschemas into account. It can therefore recognize both the inherited street constraint and the outer kind, while rejecting an unrelated extra. This is not a magic fix for a base that still contains additionalProperties: false: if that base fails on kind, an outer keyword cannot turn the failed subschema into a pass. Move the closure before rerunning the test matrix.

A second route is useful when the deployed validator does not support unevaluatedProperties. At the final closing level, explicitly list all allowed property names and apply additionalProperties: false at that same level, while allOf reuses their actual constraints. This duplicates some names and may drift as the model changes. An inner schema that remains closed will still fail; outer redeclaration does not override it. Check the declared JSON Schema draft and the actual validator before choosing a route. The official material identifies unevaluatedProperties as a feature introduced in draft 2019-09. Adding it to an older dialect and assuming the tool will enforce it is not a migration strategy.

An isolated editorial check used Python jsonschema 4.26.0 and Draft202012Validator; the script and raw output are preserved in the editorial evidence. With the inner closure, {"street":"Main","kind":"business"} is invalid because kind is unexpected. After moving closure to an outer unevaluatedProperties: false, that same input is valid. Adding "extra":1 makes it invalid, and omitting required kind also makes it invalid. Those observations apply to that validator, dialect, and exact fixture. They do not prove that a project’s $ref, aliases, conditional subschemas, or runtime tooling use the same configuration.

Conditional branches change which fields are evaluated

Add a more demanding rule: only an address with kind="business" may—and must—have department; a residential address does not know that field. Use if to test kind, declare and require department in then, and close the composed object with outer unevaluatedProperties: false. An isolated probe with the same jsonschema 4.26.0 and Draft 2020-12 environment produced five outcomes. {"street":"Main","kind":"business","department":"Sales"} passes. The business address without department fails its required constraint. {"street":"Main","kind":"residential"} passes. A residential address with department fails because the successful branch did not evaluate that field. A business address with an unrelated extra:1 fails as an unevaluated property.

This is not a rule that any property mentioned in any branch becomes globally allowed. then participates when its condition matches, so its declaration does not license department on a residential address. If department were declared at the outer properties level, the residential instance might count it as evaluated, undermining the intended branch-specific closure. The business rule and extra-field rule need separate tests. A numeric department, an unknown kind, and an omitted kind should also be covered; five local fixtures are not proof for every conditional combination.

Test both erroneous acceptance and erroneous rejection

Once the legitimate new field passes, test that unintended fields do not silently pass. A useful matrix includes: base fields only; base plus valid new field; those fields plus an undeclared key; missing required new field; and a new field with the wrong type. Record the pass or failure and the subschema responsible. Conditional schemas need more care: a field allowed only when kind="business" should not automatically pass for a residential address just because some branch mentions its name. Which branch successfully evaluates the instance affects what unevaluatedProperties can collect. Test that exact draft and validator, rather than reading only the property names.

For an existing schema library, also ask whether current consumers deliberately rely on rejection of the new field. Changing the closure point is a compatibility change. Capture the failing instance, schema version, validator version, and precise error path before editing. If the old contract cannot change, publish a new schema version or avoid this inheritance-like extension. The related article on OpenAPI readOnly enforcement addresses another gap between a written constraint and what a tool actually executes. Here, each subschema must first accept the intended instance on its own terms; only then should the final level decide which additional fields to reject.
