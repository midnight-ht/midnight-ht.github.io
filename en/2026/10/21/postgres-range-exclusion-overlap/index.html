Prevent Overlapping Room Bookings With an Exclusion Constraint

A complete tstzrange and GiST example tests adjacent slots, overlapping bookings, other rooms, empty ranges, and concurrency.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-21 · Estimated read 17 min
Translations
zh-CN en

Article

Key takeaways

  • The conflict rule is equal room IDs plus overlapping ranges; a unique start time cannot express it.
  • Half-open [) ranges allow adjacent reservations; empty ranges and NULLs need separate policy.
  • btree_gist supplies GiST equality for integer room IDs, while the exclusion constraint arbitrates conflicting writes.

Two people book the same meeting room. One reservation runs from 10:00 to 11:00; the other runs from 10:30 to 11:30. Their start times differ, so UNIQUE (room_id, starts_at) would admit both rows. The room cannot serve both groups. The actual invariant concerns pairs of rows: equal room IDs and time intervals with at least one instant in common. PostgreSQL’s range and exclusion constraint documentation shows how to place that rule at the database boundary shared by every writer.

Encode the room rule, including its edge

This is an independent teaching table, not a migration script for an existing booking system. tstzrange stores a range of timestamp-with-time-zone values. The input below states +08 explicitly so that the example does not silently depend on a session time zone. The boundary string [) includes the start instant and excludes the end instant. A booking ending at 11:00 therefore does not overlap one beginning at 11:00. A venue might need a cleaning or handover buffer; if so, that time must be part of the business interval. A database constraint cannot infer it from a calendar label.

CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE room_booking (
  booking_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  room_id integer NOT NULL,
  during tstzrange NOT NULL,
  CONSTRAINT room_booking_nonempty CHECK (NOT isempty(during)),
  CONSTRAINT room_booking_no_overlap
    EXCLUDE USING gist (room_id WITH =, during WITH &&)
);

The first exclusion comparison asks whether two rows name the same room. The second asks whether their ranges overlap. The constraint rules out a pair for which both answers are true. If the rooms differ, or the intervals do not overlap, that pair is allowed. btree_gist provides a GiST equality operator class for the integer room ID; the range operator class handles &&. PostgreSQL’s extension reference explains why a simple scalar column can participate in a multicolumn GiST constraint. This is more than a unique index on the starting instant: overlapping reservations can have completely different starts and ends.

Four inserts reveal what the constraint accepts

Run the statements separately, or use savepoints around expected failures. In one unhandled transaction, the third statement’s error would leave that transaction failed, obscuring the result of the fourth statement. The first insert occupies room 7 from 10:00 until 11:00. The second begins exactly at 11:00 in the same room and should succeed under the half-open boundary. The third reaches back into the first booking and forward into the second; it should be rejected by room_booking_no_overlap. The fourth uses room 8 and should succeed despite its matching time interval.

INSERT INTO room_booking (room_id, during) VALUES
  (7, tstzrange('2026-11-02 10:00+08', '2026-11-02 11:00+08', '[)'));

INSERT INTO room_booking (room_id, during) VALUES
  (7, tstzrange('2026-11-02 11:00+08', '2026-11-02 12:00+08', '[)'));

INSERT INTO room_booking (room_id, during) VALUES
  (7, tstzrange('2026-11-02 10:30+08', '2026-11-02 11:30+08', '[)'));
-- Expected: room_booking_no_overlap violation; row not inserted.

INSERT INTO room_booking (room_id, during) VALUES
  (8, tstzrange('2026-11-02 10:30+08', '2026-11-02 11:30+08', '[)'));
-- Expected: succeeds because the room differs.

These outcomes are deductions from the PostgreSQL 18 documentation, not output captured from a database in this editorial run. In an isolated test database, query SELECT booking_id, room_id, during FROM room_booking ORDER BY booking_id after handling the expected error. You should find three rows corresponding to the first, second, and fourth inserts. Do not require consecutive generated IDs: an attempted insert may consume an identity value before a constraint rejects the row. Test the boundary separately with && over two constructed ranges. The official range-operator table defines && by whether the ranges share any elements. Adjacency alone is not overlap for these half-open intervals.

An availability lookup cannot be the last arbiter

A booking interface still needs an availability query to show useful options. That query is a view for the user, not the final integrity rule. Imagine two transactions asking for room 7 at 14:00–15:00. Each may check before the other’s uncommitted reservation is visible. Both application processes then believe the slot is free. If the system relies only on SELECT followed by INSERT, the check and the write leave a race window. The table constraint is the final arbiter for conflicting writes. The application should turn a resulting constraint error into a clear “that slot was just taken” response and coordinate payment or confirmation messages with the actual commit outcome.

Avoid claiming that the second transaction necessarily fails immediately. Waiting and the eventual result depend on what the concurrent transaction commits or rolls back. To verify the user-facing path, exercise two connections in an isolated environment: start competing inserts, observe any wait, commit or roll back one side, then inspect the other response and downstream actions. Sequential inserts on one connection prove that the constraint rejects a conflict with an established row; they do not test concurrency handling. The exclusion constraint creates its supporting index automatically. Adding an ordinary index for faster availability lookups does not itself enforce the no-overlap invariant.

Nulls, empty ranges, and unbounded ranges need policy

Both room_id and during are NOT NULL for a reason. An exclusion constraint prohibits a pair when all specified comparisons are true; false or null in at least one comparison means it is not a conflicting pair. If a booking can have an unknown room or interval, the constraint alone cannot promise that every such row conflicts with others. This table chooses to reject incomplete bookings at insertion. Its CHECK (NOT isempty(during)) makes a different decision: an empty range occupies no instant and therefore does not overlap a real booking. A zero-duration request should not slip through the occupancy rule as if it reserved time. The official isempty function reports that condition.

A range can also omit either bound, extending indefinitely toward the past or future. That may accidentally block future reservations. If every booking must have concrete start and end instants, add checks against lower_inf(during) and upper_inf(during). Maximum duration, overnight events, and cancellation are separate domain choices. For example, retaining cancelled bookings in this table would keep them in the exclusion comparison. A partial exclusion constraint restricted to active rows is possible, but then status changes and rebooking must be designed and tested together. Do not paste this DDL into a system whose meaning of “occupied” differs from the example.

Validate old rows and every write path before rollout

A new empty table can accept this definition directly. For an existing reservation table, first find historical conflicts and decide which records represent duplicate writes, failed reschedules, or intentionally shared capacity. A self-join on a.booking_id < b.booking_id, equal room IDs, and a.during && b.during lists each conflicting pair once. Review the pairs before changing valid customer bookings. Then try the constraint on an isolated copy, measure index-build time and lock waits, and plan the production change window. Interface tests should cover adjacent slots and different rooms succeeding, same-room overlap failing with a useful response, and updates that change room or extend an interval. Cancellation and rebooking deserve their own case if the product supports them.

This constraint gives a single database-level answer to a particular question: can two rows reserve the same room at overlapping instants? It does not implement capacity limits, shared seating, payment compensation, or a humane error message. If the venue allows multiple simultaneous reservations in one room, model that capacity explicitly rather than weakening the example with exceptions. Write down the accepted and rejected pairs before choosing the index and constraint. The SQL and expected results here were not executed against a live PostgreSQL instance; concurrency, migration locks, and extension privileges still require checks in the target environment.
