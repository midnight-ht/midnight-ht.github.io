Why an External Store Needs a Stable Snapshot

A cart counter traces subscription, cached immutable snapshots, and a matching server hydration value.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-21 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • getSnapshot must return the same value while the store is unchanged; cache immutable snapshots for mutable data.
  • Stable subscription identity and stable snapshot identity are separate contracts.
  • getServerSnapshot must agree between server rendering and hydration before client updates take over.

A shopping-cart count in the header comes from a store outside React. A customer clicks “Add” on a product card; the store's count changes from 2 to 3, and the header should update. The server-rendered first view must also match what the browser sees while it hydrates. useSyncExternalStore bridges those boundaries, but its three functions have distinct jobs: subscribe reports changes, getSnapshot gives React a stable comparable value, and getServerSnapshot supplies an initial value shared by server rendering and hydration. The React reference defines these contracts. The important question is whether each read represents the same version of state, not merely whether a listener fired.

Snapshot identity says whether state changed

Suppose the store holds {count:2, items:[...]}. If the component only needs the count, getSnapshot can return the primitive 2. While the count is unchanged, repeated calls return the same value. After an item is added, the store changes to 3, notifies subscribers, and React reads 3 to update the header. For an object snapshot, returning a fresh {count: store.count} on every call is wrong: even when the count remains 2, each object has a new identity and Object.is considers it different. React says getSnapshot must return the same value while the store has not changed. If the underlying data is mutable, create a new immutable snapshot only when it changes; otherwise return the cached snapshot.

A version number can help implement this contract, but the number alone is not the solution. Increment version on each meaningful store change and cache an immutable copy of {count, items}. An unchanged version returns the exact cached object; a changed version creates a new one. Notify listeners after writing the state so a callback's next read sees the new version. The subscribe function must return a cleanup function that actually removes the listener. Do not mutate items inside an old cached object: React may see the same outer identity while its contents silently change. If the source already uses immutable updates, returning that immutable value may be simpler.

Walk through a complete small case. The store starts at version 5 with cart count 2 and cached snapshot S5={count:2}. The header subscribes, reads S5, and displays “2.” A product-card action increments the count to 3 and the version to 6, then notifies listeners. The next getSnapshot creates S6={count:3}, and the header displays “3.” An unrelated search-field render calls getSnapshot again, but receives the same S6 object; the cart has not changed merely because another part of the page rendered. This is a worked sequence inferred from the API contract, not a browser measurement of a real shop.

Two counterexamples isolate two different identity problems. Defining subscribe inside the component creates a new function on every render, prompting React to unsubscribe and resubscribe; the documentation advises a stable function outside the component. A stable subscribe cannot fix a getSnapshot that manufactures a new object on every read: React can repeatedly render and report that the snapshot should be cached. Conversely, mutating a cached object in place can hide a real change. Subscription identity and snapshot identity are separate contracts.

Hydration must read the server's initial value

The server does not have the browser's live store. Suppose it renders a session cart count of 2, while a newly created browser store defaults to 0. If getServerSnapshot returns 2 on the server but 0 during hydration, the first views disagree. React says that omitting the third function while rendering this component on the server will throw. Transfer the same per-request initial data safely to the browser, make the client's hydration call to getServerSnapshot return 2, and let normal client getSnapshot follow later store changes. Serialization needs correct escaping and user isolation; a shared cached page must not leak another customer's cart.

Consider the interval after server HTML was generated but before hydration finishes. The server's initial value 2 still needs to match the HTML at the hydration boundary. If the browser store has already received an update to 3, let the normal subscription or subsequent snapshot read bring the UI to 3 after takeover; do not quietly change the hydration initial value to 3 while the HTML still displays “2.” A constant server snapshot works only for an initial value genuinely independent of the user. Session-specific state requires a per-request transfer path.

For a browser-only online-status badge, the server has no real navigator.onLine. The product may choose a consistent display default or render that part only on the client. It should decide what the first frame means instead of letting server and browser make unrelated guesses. Matching the initial value also does not keep remote state synchronized forever. Network responses, cross-tab messages, and stock updates still have to enter the store through its normal change notifications. This Hook connects React reads and subscriptions to an external source; it does not solve conflict resolution or cross-user permissions.

First decide whether an external store is needed. If the count already exists in React props or context, deriving it through the ordinary React data flow may be simpler. Our related article on derived state and Effects explains why a computable value often should not become a second synchronized copy. Use this bridge when a browser API, third-party subscription, or genuinely framework-external object owns the state. Creating another authority merely to avoid passing props introduces ordering questions that are harder than the Hook's API.

Verify a repeatable sequence of states

Build a controllable store in tests. Call getSnapshot repeatedly without a change and assert that Object.is sees the same value. Change the count, notify listeners, and assert a new immutable object or primitive value; unmount the component and verify the listener was removed. If snapshots contain arrays, confirm the old snapshot still has the old contents. For SSR, render HTML and hydrate it using the same transferred initial data, then simulate a client update. Also deliberately mismatch the two initial values to ensure the test detects the failure rather than only covering the happy path.

React's reference notes another boundary: if an external store changes during a non-blocking Transition, React may reread the snapshot and restart as a blocking update so the displayed components reflect one store version. That is a UI consistency mechanism, not a business transaction or database snapshot. No React rendering probe was run for this article. Its evidence is the official API contract, the cart-state walkthrough, and a proposed test sequence. A useful acceptance review can name the version, notification, snapshot identity, and hydration value at each step, instead of stopping at “the callback ran.”
