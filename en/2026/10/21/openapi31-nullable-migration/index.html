OpenAPI 3.1 Nullable Migration: Test Missing, Null, and String

Replace nullable with a JSON Schema type array, then verify three-state behavior in the schema, generated client, and server.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-21 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • OpenAPI 3.1 expresses nullable values with a type array that includes null.
  • Allowing null and allowing an omitted property are separate constraints.
  • Migration needs wire-level, generator, and server-behavior checks.

An OpenAPI 3.0 description gives nickname a type: string plus nullable: true, and a test sends {"nickname":null}. After the file is updated to 3.1, keeping the old spelling can leave JSON Schema-aware tooling with a string constraint that rejects null. The OpenAPI Initiative migration guide recommends replacing nullable: true with a type array, and OAS 3.1.1 aligns its Schema Object with JSON Schema Draft 2020-12, where null is an explicit type. The migration goal is not similar-looking YAML. It is agreement among the description, generated clients, server validation, and actual update behavior.

Keep three input states separate

For a profile update, start with an omitted property, an explicit null, and a string. {} contains no nickname; {"nickname":null} supplies a null value; {"nickname":"Ada"} supplies text. Whether they mean “leave unchanged,” “clear,” and “set” depends on the PUT or PATCH contract. The schema tells you which supplied values are valid, not the product meaning of an update. An empty string is still a string, not null; it needs a separate length or business rule if it should be rejected. The related guide to PUT and PATCH replacement boundaries covers update semantics; here the concern is preserving distinct states during a description upgrade.

The minimal syntax comparison is:

# OpenAPI 3.0 property
nickname:
  type: string
  nullable: true

# OpenAPI 3.1 property
nickname:
  type: [string, 'null']

If the containing object lists required: [nickname], absence still fails even though null can be a valid value. If it does not list the property as required, omission may pass, while explicit null still depends on the property’s type. Nullable and optional are separate questions. Simply deleting nullable without adding null can turn a previously accepted clear operation into a validation error. Adding null to every optional property does the reverse: it lets clients explicitly clear fields that formerly could only be omitted. Review the intent per field, not by one global search-and-replace.

Type constraints matter elsewhere too. Keywords such as format or pattern apply to instances of the relevant type; they do not themselves make every other type invalid. A migration that retains format: date-time but loses type: string may accept more values than intended. A minLength attached to a string-or-null property constrains strings; it is not proof that null is rejected. Check the final combination of type, required, enum, and other constraints instead of counting occurrences of the word nullable.

The same component can carry different meanings

A response may use null to mean “no nickname has been set,” while an update request uses null as an instruction to clear the nickname. A server-computed field may be returned in a response yet should never be accepted in a request. List the state matrix for each request and response context, even where both reference a shared component. Follow $ref and allOf to the effective schema. A generator may depend on an old extension or cached template. Even if a type array is valid according to the standard, the deployed generator version must be tested for nullable types, null serialization, and preservation of omitted fields.

Defaults are another trap. A schema with default: "guest" does not guarantee that a server fills in guest when a field is absent, and does not mean a client-sent null will be replaced. Treat default as a descriptive annotation or a specific tool behavior, not a substitute for request-processing rules. Capture the raw request, validation result, persisted value, and response. Seeing string | null in generated TypeScript is not enough to show that the server’s clear operation works. If a JSON serializer omits undefined, confirm that omission is not accidentally sent as null.

Non-JSON locations need their own contract. Query and path parameters, and form-encoded fields, travel as strings or encoded form data. Even if their schema allows null, the wire representation may not distinguish it from an empty string in the way a JSON body does. OAS leaves aspects of null parameter serialization implementation-defined. For a JSON body, { "nickname": null } is a concrete test. For ?nickname=, define how an absent parameter, an empty value, and the literal string null differ before claiming the same three-state behavior.

A migration difference table is more useful than testing the new schema in isolation. If the old contract accepted omission and null but rejected a number, the new one should preserve those outcomes unless the product deliberately changes them. Map every operation that references the component and its containing object’s required list. A script that only traverses direct properties may miss array items and composed schemas. Start with a small component and compare accepted inputs before expanding to all references. Record each pass-to-fail or fail-to-pass change and make the API owner decide whether it is intended.

Generated SDKs also need a wire-level check in both directions. Some languages represent omission with an optional field and null with a nullable value; some generators collapse both into one pointer-like construct. Feed the generated client three cases—keep the original value, explicitly clear it, and omit the field—and inspect the actual HTTP body. Then return a response containing explicit null and see whether the SDK preserves it rather than treating it as absent. Pin the generator version and template settings in the evidence, because a future upgrade may change the mapping even when the OpenAPI file does not.

Turn the comparison into acceptance evidence

Save the old description and a compatibility set: missing property, null, valid string, empty string, and wrong-type number. Run description and instance validation on the pre- and post-migration versions; record each outcome. For generated clients or server stubs, inspect language types, request bytes, and response parsing. If a generator treats type: [string, 'null'] as string-only, the specification being right does not make that deployed tool usable. Upgrade it, replace it, or defer the migration with the incompatibility explicit. A wrong-type number that begins to pass because type was lost is also a release blocker.

For a PATCH clear operation, an application-level test must inspect the database state and the subsequent read: null should clear the value, omission should preserve the previous value, and unauthorized updates should be rejected. Repeated submissions and audit events may matter to the product contract as well. The YAML above is an illustrative comparison; this article did not run an OpenAPI toolchain or call a live API. Separate the evidence for schema validity, generator behavior, and server behavior. The nullable migration is complete only when all three layers agree on the same input states.
