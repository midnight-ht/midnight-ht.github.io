CTE Materialization: Reuse or a Filter Barrier?

A two-reference reporting query shows when folding pushes filters down and when materialization saves repeated work.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-21 · Estimated read 16 min
Translations
zh-CN en

Article

Key takeaways

  • A side-effect-free, nonrecursive SELECT CTE can fold by default with one reference but normally materializes with multiple references.
  • NOT MATERIALIZED may permit filtering per reference while duplicating expensive work.
  • Compare real plans, row counts, buffers, function costs, and result equivalence before choosing.

A reporting query names a cleaned orders set w in a WITH clause, then refers to w twice: twice to count pairs of the same customer's orders. When it slows down, someone says, “CTEs always materialize; remove WITH.” That diagnosis misses the actual choice. The PostgreSQL 18 documentation on WITH queries says a nonrecursive, side-effect-free SELECT CTE can normally fold into its parent query when referenced once, while multiple references normally prevent that default folding. MATERIALIZED and NOT MATERIALIZED can influence the choice. The decision is whether pushing restrictions into each reference saves more work than computing the shared result once.

Two references can change where filtering happens

Suppose orders(id, customer_id, amount) contains a million rows, only eight of which belong to customer 17, and a usable index exists on customer_id. A report counts pairs among that customer's orders, including self-pairs. If WITH w AS (SELECT * FROM orders) is referenced twice, default materialization can produce an intermediate result over a broad part of orders before the parent's customer_id = 17 restriction applies. Conceptually, eight relevant rows are found after building a much larger candidate set. This is a path to investigate, not an execution plan measured on anyone's database.

To make both references reproducible, assume exactly eight rows for customer 17, each with a distinct id, and count pairs using two aliases:

WITH w AS (SELECT id, customer_id, amount FROM orders)
SELECT count(*)
FROM w AS left_order
JOIN w AS right_order ON left_order.customer_id = right_order.customer_id
WHERE left_order.customer_id = 17
  AND right_order.customer_id = 17;

Each alias has eight eligible rows, including self-pairs and reverse pairs, so the logical result is 8×8=64. For unordered pairs of distinct orders, add left_order.id < right_order.id; that result is 28. The 64 follows from the stated input and join, not from a measured access count. The execution plan is still an open question.

Compare the simpler WITH w AS (SELECT * FROM orders) SELECT * FROM w WHERE customer_id = 17;. There is one reference and no recursion or volatile function. Under the documented default, the CTE can be optimized together with its parent. When the index and table statistics make it attractive, the planner may fetch just customer 17's rows. The presence of the word WITH does not prove a temporary table is built. Nor does the syntax guarantee an index scan: estimates, selectivity, index structure, and cost settings influence the chosen plan.

Folding permits pushdown; materialization reuses work

Compare two explicit variants. A query beginning WITH w AS NOT MATERIALIZED (SELECT * FROM orders) asks PostgreSQL to merge an eligible CTE into the parent, allowing each reference to be optimized with its own restrictions. If both references need only a few rows, that may avoid a large intermediate result. A query beginning WITH w AS MATERIALIZED (SELECT * FROM orders) forces separate computation and can save work when both references need much of an expensive result. These are not speed rankings. They change which work can be shared and which conditions can be pushed into the underlying scan. PostgreSQL explicitly warns that NOT MATERIALIZED may duplicate computation, even when the net cost is lower.

Put numbers into the decision without pretending they are benchmark results. If each reference needs eight rows and suitable indexes support those restrictions, folding suggests two small targeted accesses; computing a million-row intermediate result once may be wasteful. If the CTE applies a costly pure transformation to each row and two references both need roughly the same 100,000 rows, merging might run the transformation twice, while materializing once could win. The eight and 100,000 figures are illustrative assumptions, not guaranteed physical reads. CPU time, memory, temporary storage, join predicates, and parallel plans all require actual workload evidence.

The documentation gives an especially useful counterexample: put very_expensive_function(val) in the CTE and self-join two references to it. Materialization ensures the expensive function is evaluated once per table row, rather than twice. A blanket policy of adding NOT MATERIALIZED to “make indexes work” can regress such a query. Before performance tuning, also check whether the CTE is eligible for the folding rule at all. Recursive CTEs, volatile functions, and data-modifying WITH statements have different semantics from the ordinary side-effect-free SELECT considered here.

Test a cost prediction against the real plan

Preserve the original query and its parameters. In a controlled environment with representative data, compare default, explicit MATERIALIZED, and explicit NOT MATERIALIZED using EXPLAIN (ANALYZE, BUFFERS). Inspect actual versus estimated rows, whether a CTE Scan appears, how the base table is accessed, how often expensive functions run, buffer activity, and elapsed time. ANALYZE executes the query, so a statement with data modification or side effects belongs in a safe isolated setting or needs a nonexecuting plan inspection instead. Our related article on row estimates and EXPLAIN covers the prerequisite of reading a plan rather than prescribing an index by reflex.

State a prediction that can fail. For the eight-row customer case, expect the folded variant to access the base table through two restricted paths and the materialized variant to handle a larger intermediate result. When the plan already applies restrictions near the base scan, or a sequential scan is genuinely cheaper, the prediction is wrong. Do not keep the hint because it matched a slogan. For the expensive-function case, expect materialization to reduce repeated evaluation. If each reference needs a tiny, disjoint subset, however, paying for one full materialized result may still cost more. Test a common customer as well as a rare one; one customer ID cannot represent a skewed distribution.

Result equivalence is a separate acceptance condition. Folding can change the number of times expressions are evaluated, which is why a performance-only argument is unsafe around side effects and volatile functions. Even for ordinary deterministic queries, compare row counts, duplicates, NULL behavior, and joins. Moving a predicate manually inside a CTE is not the same operation as adding NOT MATERIALIZED: two parent references may need different ranges, and a single early WHERE clause could change the result.

Choose for the ranges each reference needs

If the CTE is referenced once, first check whether the default folding already provides a good plan. If it is referenced several times and each reference needs a small slice, test NOT MATERIALIZED. If the references reuse a costly result over similar ranges, test MATERIALIZED or retain the default. Make the final decision from real parameters, plans, result equivalence, and measured costs. Revisit it when statistics, indexes, or data distribution change. A win on one report run is not a law about every CTE.

This is a choice about work within one query. CTE materialization is not a persistent cache for later requests, and it does not automatically give the parent query an ordinary index over an intermediate table. For reuse across requests, a materialized view, cache, or pre-aggregation may be appropriate, with separate freshness and maintenance costs. No database probe was run for this article. It explains the documented PostgreSQL 18 rules, derives possible plan paths, and gives a validation procedure; the actual performance answer belongs to the reader's workload.
