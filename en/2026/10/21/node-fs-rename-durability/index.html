After rename Succeeds, Is the File Delivered?

A configuration replacement separates visible path changes, file and directory sync, cross-device errors, and crash recovery evidence.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-21 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • A fulfilled rename establishes the path operation, not durable file data and directory entries after power loss.
  • Same-directory staging, validation, file sync, rename, and directory sync form a platform-specific sequence to verify.
  • Handle EXDEV and sync failures with recoverable states and precise receipts.

A build program writes config.json.tmp, calls fsPromises.rename(tmp, 'config.json'), and logs “delivered” when the Promise fulfills. A reader can now open the new path. An operator asks a different question: will that name and its contents survive an immediate power loss? Those claims require different evidence. The Node.js file-system documentation describes a successful rename as a successful path operation; a fulfilled Promise by itself does not certify durable file contents and directory metadata. A delivery design should separate the visible name switch, synchronization requests, and recovery after failure.

Replace one configuration file, step by step

Suppose the existing config.json contains {"version":1} and the desired file contains {"version":2}. Create a unique staging file such as config.json.tmp-42 in the target directory, write the complete bytes, verify them, and rename the temporary path over config.json. Under the applicable same-mounted-filesystem semantics, the Linux rename(2) manual says an existing target path is atomically replaced: a reader opening the target should not find a gap in which the name is missing. If the program renames before finishing the write, however, a reader may get a truncated version 2. Rename changes names; it does not validate the bytes. Parse the JSON, check the version and checksum, and only then publish.

From the process's perspective, await rename(tmp, target) returning means this rename operation succeeded. It is an important path-visibility milestone, but it is not the same as every storage layer confirming the new directory entry. Node documents filehandle.sync() as a request to flush data for an open descriptor to the storage device, with OS- and device-specific implementation. The Linux fsync(2) manual adds that syncing a file does not necessarily put its containing directory entry on disk; an explicit directory sync is needed there. These sources define operating-system boundaries. They cannot replace an unperformed power-failure experiment or be generalized unchanged to macOS, Windows, and network filesystems.

If the product needs a stronger durability target, design a supported-platform sequence: create the temporary file in the destination directory; write and validate it; call sync() on its file handle; close it; rename the temporary name to the target; open and sync the containing directory; then record a delivery receipt. Await each step and do not claim a later step succeeded when an earlier one failed. Newer writeFile APIs offer a flush option, but it is not a universal default and addresses the file-data step, not directory persistence. Directory opening and syncing, errors, device behavior, and the precise promise must be tested on the deployed platform.

A failure path shows what a receipt should say. Suppose space runs out and the temporary file contains only {"version":. Parsing fails: remove the staging file and leave version 1 at the target. If the process exits before rename, version 1 remains the published path and a leftover temporary file can be cleaned up later. If rename succeeds but directory sync fails, the running process may already see version 2 at the target, yet the requested durability level remains unconfirmed. Blindly retrying the same rename may find that the temporary path no longer exists. Recovery should read the target and the receipt, distinguish “visible” from “confirmed durable,” and decide whether to retry synchronization, rebuild, or restore. Those are design deductions, not results from a power-cut test.

Path layout changes the guarantee

Putting the temporary file in system /tmp while the target is on another mount can make Linux rename(2) return EXDEV. Copying the file to the destination and deleting the old one is not the same atomic replacement operation. If cross-device staging is unavoidable, stage a new temporary file within the destination filesystem before the final rename, or adopt an explicit multi-step copy and recovery protocol. Even same-directory staging does not make every platform identical: network mounts, container volumes, Windows file-handle and permission rules, and device caches can change the behavior available to the application. Identify the actual deployment filesystem before writing a platform-specific acceptance claim.

There is a reader-side boundary too. A process that already opened the old config.json may continue using its old handle; a later open by path may read version 2. If every worker must switch configuration at the same logical moment, a file rename is only the storage-level publication point. The application still needs version signaling, refresh behavior, and rollback policy. Our related article on Node stream backpressure explains why accepted writes are not a disk-commit receipt. Here, even a completed byte write leaves path publication and durability as separate questions.

Distinguish crash consistency from business acceptance. A version 2 file that survives restart might still contain an unapproved configuration. Before rename, validate its schema, critical ranges, version progression, and any dependencies. If two files must change together, one rename makes only one path switch atomically; it is not a transaction over both files. A versioned directory with a manifest pointer, or transactional metadata in a database, can address a broader publication contract, but its own sync and recovery behavior needs review.

Test the exact failure points

An isolated test directory can exercise process-level failures before write completion, after file sync, before rename, after rename, and before directory sync. At each point, check whether the target is version 1, version 2, or accompanied by a temporary file requiring cleanup. Exercise a cross-mount path to verify EXDEV handling, and confirm that a failed receipt does not masquerade as success. Killing a process tests recovery from a process exit; it does not demonstrate what a physical power cut does to the storage stack. A power-loss promise needs a separate controlled test with named OS, filesystem, mount settings, device, exact commands, versions, and raw results. No such probe was run for this article.

A precise receipt can record separate facts: bytes written and validated, file sync requested and returned, rename returned successfully, directory sync requested and returned, and a post-restart read validated the target. If the product only needs a visible path switch while the process runs, it may choose fewer durability steps and state the loss window. Irreplaceable credentials or accounting records require a stronger contract and may not fit a one-file protocol. Do not inflate one resolved Promise into “nothing can be lost after any failure.” Equally, do not dismiss the useful same-filesystem visibility boundary simply because hardware-level guarantees require more evidence.
