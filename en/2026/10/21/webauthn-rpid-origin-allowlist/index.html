Why check origin when WebAuthn rpIdHash already matches?

A parent RP ID can cover sibling subdomains; rpIdHash does not identify the calling webpage, so the server must verify clientDataJSON.origin.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-21 · Estimated read 16 min
Translations
zh-CN en

Article

Key takeaways

  • A parent RP ID broadens browser-eligible credential use, not login authorization for every sibling.
  • A valid signature and RP ID hash still require exact origin and challenge checks.
  • Test a legitimate origin, an unapproved sibling, and an unrelated domain as distinct cases.

The login page lives at https://auth.example.test. To reuse passkeys across subdomains, the product sets its WebAuthn RP ID to example.test. An engineer sees that the server already checks rpIdHash, challenge, and signature, then removes the clientDataJSON.origin check: surely a credential scoped to the parent domain makes its calling page trustworthy? That confuses credential scope with authorization of a web origin. An independently controlled sibling, evil.example.test, can satisfy the browser’s RP ID domain relationship while still being an unacceptable login page.

A parent RP ID broadens credential scope

The W3C WebAuthn Level 2 Recommendation says an RP ID defaults to the calling origin’s effective domain. A caller may instead choose a registrable-domain suffix of that domain or the same domain. The origin must use HTTPS; its port is unrestricted by this RP ID rule. For the authentication subdomain, the chosen parent is a valid suffix. Assuming another party controls the malicious sibling, the same parent is also a valid suffix for that page. A browser can let a navigator.credentials.get() call proceed under that relationship. This browser check has not authorized the page to sign a user into the server.

The RP ID selects the credential scope. The returned authenticatorData contains rpIdHash, which the server must compare with SHA-256 of the RP ID it expects. A hash of the parent is the same for both sibling pages; it cannot say which one called the API. If the product does not need cross-subdomain credentials, using the narrower authentication subdomain as RP ID reduces the browser-eligible scope. Moving an existing parent-scoped deployment to a narrower ID, however, can require credential re-registration and user migration. Changing only a server setting does not make previously registered credentials usable under the new scope.

Two different kinds of “origin” matter here. RP ID is a domain scope without scheme or port. clientDataJSON.origin is the calling webpage’s origin, including scheme, host, and applicable port. Comparing only rpIdHash leaves every eligible sibling to later server validation. A wildcard or loose suffix rule for origins can then admit a sibling the service does not control. Maintain an explicit allowlist of complete origins, perhaps only the authentication page at first. Add a second login origin only after separately reviewing who controls it. Shared parent-domain ancestry alone is not an authorization rule.

A valid signature preserves an origin; it does not approve it

Verifying an assertion takes more than one hash. The server checks webauthn.get, a challenge belonging to this authentication ceremony, and that the credential belongs to the identified user. It then checks the origin in clientDataJSON against the RP’s expected origin, the expected rpIdHash, user-presence and required user-verification flags, and the signature with the registered public key. WebAuthn Level 2 lists origin and RP ID hash as separate authentication-verification steps. Registration has corresponding checks; adding an origin rule only to login leaves another ceremony unreviewed.

The signature covers authenticatorData together with a hash of clientDataJSON. An attacker cannot simply edit the origin string of an otherwise valid assertion and keep its signature valid. That is exactly why the server should inspect the intact value: a browser can faithfully report the malicious sibling as the origin and produce a valid signature, while the business must still reject that source. The challenge makes the assertion fresh for a particular ceremony and blocks simple replay of an older assertion. If the server issued a fresh challenge for a login session the attacker controls, challenge validation does not reveal which webpage asked the user’s authenticator to sign. Signature, challenge, RP ID, and origin answer integrity, freshness, credential scope, and calling-page authorization respectively.

Consider a hypothetical flow; no browser, authenticator, or production login was exercised here. The attacker controls the malicious sibling page but neither the legitimate authentication page nor the victim’s private key. Knowing the victim’s account identifier, the attacker obtains a fresh server challenge for a login session under the attacker’s control and brings that challenge and the parent RP ID to the sibling page. If the victim visits it and deliberately completes a passkey prompt, the browser may produce an assertion for the parent RP ID. Its clientDataJSON.origin honestly records the sibling’s HTTPS origin, while rpIdHash remains the hash of the parent. The attacker relays the assertion to the session that owns the challenge. A server that checks challenge, hash, and signature but ignores origin could accept this login incorrectly. An allowlist containing only the legitimate authentication-page origin should reject it at the origin step. Victim interaction, challenge issuance, and correct session correlation are essential assumptions; a sibling cannot silently steal a private key or log in without them.

Change the hostile page to https://evil.other.test, outside the parent domain. Under the Level 2 RP ID suffix rule, the browser should reject its attempt to use the target parent’s RP ID. This browser-side rejection and the server-side sibling rejection occur at different boundaries. The fact that a completely unrelated domain is blocked does not establish that every sibling domain is blocked. Conversely, even with a narrower RP ID, the server should still inspect the origin as the specification requires, catching configuration mistakes or unacceptable client data.

Choose the scope, then test the allowlist

List the pages that actually conduct login. If only the authentication subdomain does so, a narrow RP ID simplifies the scope. If a second application subdomain must share credentials with it, a parent RP ID may be appropriate, but inventory who can create or control other subdomains and which complete origins may run ceremonies. Review staging and production settings separately. Do not substitute SameSite cookie behavior for WebAuthn origin checks; the site’s SameSite and CSRF boundary concerns a different browser mechanism.

Implement the allowlist as exact parsed origin values, not a endsWith or substring test. A loose suffix can admit an unintended sibling; a substring may confuse a host with text in a path. Behind a reverse proxy, do not derive the expected origin from an untrusted Host or X-Forwarded-Host header. Use controlled server configuration and keep the selected RP ID and origin policy consistent with the challenge’s ceremony. In a multitenant service, scope those settings by tenant rather than sharing one global parent-domain allowlist.

The test matrix needs independent outcomes. A legitimate page with the right challenge, RP ID hash, and signature should pass. An unapproved sibling with the other fields correct should fail on origin. The unrelated domain should fail the browser’s RP ID check. Wrong challenge, wrong rpIdHash, and wrong signature should each be rejected for their own reason. Record the complete parsed origin, expected RP ID, challenge-session association, and rejection reason without exposing reusable material in public logs. These are proposed tests, not observed results from an implementation.

This explanation uses the WebAuthn Level 2 Recommendation dated April 2021. It does not import related-origin behavior from other specification levels without a version distinction, or treat OAuth redirect and CORS response policies as replacements for WebAuthn assertion verification. The two independent decisions are whether the browser permits a credential under an RP ID and whether the server permits this exact webpage origin to use the assertion for account login.
