Why a 15-Second Expect Fails at the Test’s 30-Second Limit

A 12+8+15 second timeline separates Playwright test, assertion, and action timeouts so the right wait is diagnosed.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-21 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • The test timeout includes the test, test-level fixture setup, and beforeEach; expect has its own local ceiling.
  • After 12 seconds of setup and 8 seconds of action, a 30-second test has roughly 10 seconds left despite a 15-second assertion limit.
  • Identify whether test, expect, or action expires first before changing waits or budgets.

A Playwright test enters expect(locator).toBeVisible({ timeout: 15_000 }), then fails with “test timeout 30000ms exceeded.” The team raises the assertion limit from 15 to 30 seconds, but the test still stops at 30. Several timers have been mistaken for one pool of time. The Playwright timeout guide separates the test budget from retrying assertions, actions, navigation, hooks, and fixtures. A local assertion’s willingness to wait does not grant the whole test extra time.

Put the test on a timeline

Use an explicit hypothetical path. The total test timeout is 30 seconds. beforeEach takes 12 seconds to prepare a user and page. The test body spends 8 seconds clicking and waiting for that action to complete. Twenty seconds have elapsed, leaving roughly 10 seconds for the rest of the test. The next assertion permits up to 15 seconds, but the expected message never appears. Barring another earlier limit, the test timer reaches 30 seconds first; the assertion’s own deadline would have been about second 35. These 12, 8, and 15-second figures are teaching values, not a trace from a CI run. Raising the assertion ceiling to 30 seconds cannot create more total test time.

The documentation sets the default test timeout to 30 seconds and includes the test function, test-scoped fixture setup, and beforeEach hooks. Auto-retrying expect assertions default to 5 seconds and have a separate setting. After the test body completes, afterEach and fixture teardown have a separate allowance of the same configured value; they should not be indiscriminately added to the 12+8+wait window above. beforeAll and afterAll also have their own timeout behavior. A fixture with an explicitly configured timeout can add another boundary. Read the error and configuration to identify which timer actually expired.

Actions and navigation have their own low-level limits. The guide lists no separate default action or navigation timeout, but both can be set in the use configuration or on an individual call, such as locator.click({ timeout: 10_000 }). “No separate action limit” does not mean a click can ignore the test deadline; waiting for an actionable target can consume the remaining test time. Conversely, with a three-second action limit and twenty seconds left in the test, a button blocked by an overlay can fail at the action layer first. Those failures point to different repairs.

Compare three outcomes on the same page. First, a message never appears, twenty seconds remain in the test, and the assertion limit is five seconds: the expect timer should expire first, so inspect UI state, locator, and trigger. Second, setup consumes 12 seconds and clicking consumes 8, leaving only 10 seconds even though the assertion allows 15: the test timer should expire first, so inspect earlier setup and action costs. Third, click has an explicit three-second limit and an overlay prevents actionability while the test budget is ample: the action timer should expire first, so investigate the overlay rather than increasing expect. “Raise every timeout” is not a diagnosis.

Locate the wait before editing a number

Keep the error type, start time, duration of each hook and action, Playwright trace, and a page screenshot. If 12 seconds go to a login fixture, inspect its external dependency and reuse policy. If 8 seconds go to click, use the trace to see whether it waited for visibility, stability, event reception, or navigation. If an assertion begins but text never arrives, inspect the network response and final UI state. Auto-retrying expect is already designed to await an observable condition; adding a fixed sleep after the click usually obscures that condition. Our related article on assertion waiting after a click covers the local behavior; the extra concern here is how its wait spends the test budget.

Change a setting only after locating the bottleneck. A product-approved slow asynchronous operation may justify a longer assertion limit, provided the test’s overall allowance can contain reasonable setup, action, and assertion time with room for useful diagnostics. If a fixture stalls on an external service, raising a suite-wide timeout delays failure without addressing that dependency. A genuinely slow individual test can have its own timeout, or use test.slow() under the documented behavior, with the service expectation recorded. Avoid copying one large number across every test.

A loop can hide another budget mistake. Repeating the same assertion over several candidate rows with a 15-second limit gives each invocation its own local ceiling, not free time outside the overall test. The first failed wait has already consumed time; the second may have very little test budget left. Decide whether the product expects one known row or any matching row, then express a single observable condition. The trace will show the business event being awaited rather than several layers of redundant polling.

Timeout configuration is not a performance promise. A CI run that passes in 29 seconds has only proved that it stayed under 30 seconds that time. Repeated near-limit runs might mean environmental variance, a genuinely slow path, or the wrong wait condition. Record segmented durations across several runs and examine the failure distribution. If a background task is supposed to produce a message, wait for the eventual observable UI state, but also establish that the task actually runs in the test environment. A one-minute assertion cannot make an impossible event happen.

Verify the configured layers with a falsifiable case

In an isolated test project, configure a 30-second test limit and a 15-second assertion limit. Arrange controlled 12-second setup, an 8-second action, and an assertion that never passes; predict that the test timer expires first. Shorten setup to two seconds and predict that the local assertion times out. Finally, give a blocked action a three-second limit and predict an action error first. Only after preserving the actual Playwright version, configuration, command, stdout, and trace could a team claim those predictions were tested. No such probe was run for this article; its numbers are an explanatory timeline based on the official timeout contracts.

Check the entire run’s global timeout as well. It has no default value in the guide, but a team can configure it, adding another upper bound. A run can then stop before any individual test limit is reached. A useful failure report names the configured test, expect, action, navigation, fixture, hook, and global limits, and identifies the error that actually occurred. A good timeout change answers four questions: what state is being awaited, why that wait is legitimate, where earlier time went, and what evidence remains if it fails. Timers are diagnostic contracts, not knobs that remove flakiness by themselves.
