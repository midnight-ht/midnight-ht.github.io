After a CQRS Write: Confirm When the Read Projection Catches Up

Separate write acceptance from read visibility, then design version, watermark, operation-status, and failure feedback.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-21 · Estimated read 16 min
Translations
zh-CN en

Article

Key takeaways

  • A successful write response does not prove a separate read projection shows the change.
  • A watermark must certify relevant changes were applied, not just that a maximum version was seen.
  • User feedback should distinguish pending sync, confirmed, rejected, and timed-out states.

A user submits a delivery-address change, receives a success response from the write endpoint, then refreshes the profile page and sees the old address. In a CQRS design with separate write and read models, that observation does not necessarily mean the write failed: the read projection may not have consumed the change yet. The Microsoft CQRS pattern explicitly notes that a separate read database might not show recent changes immediately. The product must answer two questions: what was accepted or committed on the write side, and when can the user trust the read page to reflect it?

Give “success” two observable meanings

Suppose a person changes an address from A to B. The write model validates authorization and the address, commits revision v18, and returns operationId=op-73 with writeVersion=18. An event is sent to a projection worker, but the read database is still at v17, so the page returns A. A durable write and a caught-up projection are different facts. The first can be established by the write transaction. The second needs evidence from the relevant read model, such as an applied revision or a marker for this operation. If the client treats A as proof of write failure, it may prompt another submission and create a duplicate action. If it displays B optimistically forever without checking the projection, it can hide a broken worker.

A useful API contract returns an operation identity and revision from the write path and a projectionVersion from the read path. The profile page compares target writeVersion=18 with current projectionVersion=17. While the projection lags, it says “Address submitted; profile is updating,” and can show B as a local preview clearly marked as such. When the relevant projection reaches at least 18 and returns B, it can say the profile view has been confirmed. If the wait times out, offer a queryable operation status and a support route rather than an endless spinner. The versions must describe the same comparable aggregate or event stream. A site-wide count of unrelated events cannot safely be compared with one user's address revision.

{"operationId":"op-73","writeVersion":18,"status":"accepted"}
{"address":"A","projectionVersion":17}
{"address":"B","projectionVersion":18}

These are illustrative responses, not standard fields from a CQRS framework. If the first line is returned with HTTP 202, RFC 9110's definition of 202 Accepted means processing has been accepted but not completed. Whether the write database has already committed must be specified by this API. A synchronously completed write can use a different suitable response. HTTP 202 is not a mandatory CQRS signal. What matters is that the UI distinguishes “command received,” “write committed,” “read synchronized,” and “business rule rejected,” instead of calling them all “Saved.”

A watermark is meaningful only if it follows the data

A projection worker should advance its watermark after applying the event and committing the associated read-model change. If it updates the watermark first, the page could see projectionVersion=18 while still reading address A. Separate projections for the profile page and search index need separate status; the profile watermark does not prove search has caught up. On retries, duplicates, or out-of-order deliveries, the worker also needs event identity and aggregate-version guards to prevent an old value from overwriting a new one. A monotonic watermark should refer to changes actually applied by the particular projection, not merely received by the worker.

Consider a sharper counterexample. Revision 18 contains address B, but the projection mistakenly skips that event. It later processes unrelated revision 19 and writes a watermark of 19. If the client only compares numbers, it falsely concludes that B is visible. The watermark must mean that all required changes through that revision were successfully applied in order, or the system must record application of the target operation separately. “Highest version ever seen” is not the same as “contiguous version completed.” The design also needs an alert and replay path for a permanently failed event. In a partitioned system without one comparable global sequence, use aggregate revisions or an operationId-based confirmation service rather than pretending a global number exists.

Another counterexample is a command that asynchronous business validation eventually rejects. If the API only reports “received,” the client cannot immediately claim B was persisted. Operation status should distinguish pending, committed, and rejected, with an actionable rejection reason. If the write side synchronously completes authorization and validation, it can return the committed revision directly. The related guide on conditional writes and conflicts addresses write-side overwrites. The concern here begins once the write side has decided what happened and the read side must give a trustworthy account of it.

Select confirmation by user consequence

Not every page needs to wait. News browsing and trend reports may tolerate a few seconds of lag if they show when data was updated. A profile page after an edit, a transfer receipt, or a permission screen raises a stronger read-your-writes expectation. A local preview from the write response can bridge the gap while the app checks the projection. For consequential actions, expose an auditable operation status instead of relying only on optimistic UI. Where fresh read data is essential, briefly poll the target projection or operation status with a timeout and backoff. A timeout is not automatically a failed write, so the message must preserve that distinction.

Document the poll's completion condition as an actual predicate. GET /operations/op-73 might report writeStatus=committed, profileProjection=applied, and applied revision 18. The page should announce “Profile updated” only when the relevant operation is applied and the returned read model actually contains B. On rejected, it explains why and removes the local preview. On a long pending, it retains an operation number the user and support team can query. Refreshing the profile every two seconds proves only that the client tried; an operation status can expose where processing stopped.

The operation-status service can also lag or fail. For money movement and permission changes, identify the authoritative record and the reconciliation path; a projection status alone may not be sufficient evidence of the ultimate business outcome. A local optimistic preview on one device will not automatically appear on another. A server-side operation number and queryable state can carry the same explanation across devices. The UX requirement is therefore more than adding a “Syncing” badge. Each stage needs a traceable source of truth.

Test this contract by deliberately pausing the projection worker. Submit B, verify the write revision is 18, confirm the read side still reports 17, and check that the page says “pending sync,” not “failed.” Resume the worker and require the read page to return B with evidence that this operation was applied. Inject a duplicate event, out-of-order delivery, a failed projection write, and a rejected command; check for false confirmation or endless waiting. Restart the worker and test whether its watermark and operation lookup remain stable. This article did not connect to real read and write databases or run fault injection. Actual delay, revision granularity, and status APIs depend on the architecture. CQRS becomes understandable to a user when each visible state corresponds to a distinct internal fact, rather than an instruction to “try refreshing.”
