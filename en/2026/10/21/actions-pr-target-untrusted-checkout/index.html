A default-branch workflow does not make PR checkout trusted

pull_request_target can handle PR metadata, but executing a contributor-controlled head in that privileged job crosses a trust boundary.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-21 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • A trusted workflow definition does not make a contributor-controlled checkout trusted.
  • Keep PR metadata actions and PR code tests in separate authority contexts.
  • Review event fields, checked-out files, caches, and downstream artifacts as distinct trust inputs.

The workflow file for pull_request_target comes from the base repository's default branch. That does not make an external pull request's files trusted code. A job that only labels a PR can cross its intended trust boundary if it checks out the contributor's head and then runs the project's tests. The issue is not the word “checkout” in isolation; it is what a privileged job reads, interprets, or executes after bringing those files into its workspace.

Two sources of authority enter one job

Suppose a repository wants to add a needs-review label to pull requests from outside contributors. A workflow on the base repository's default branch subscribes to pull_request_target, receives the PR number and target branch in the event, and calls the GitHub API to update the label. No patch needs to be built, and no PR script needs to run. GitHub's event documentation says this event runs in the context of the base repository's default branch rather than the merge commit used by pull_request. It presents labeling or commenting on PRs from forks as uses for the event and advises against using it when the task is to build or run the PR's code.

Now imagine a maintainer adds a checkout “to save another workflow.” They point actions/checkout at the PR head SHA and execute npm test. The YAML still came from the default branch, but the PR author controls package.json, test scripts, installation hooks, and dependency configuration. If the job retains a write-capable GITHUB_TOKEN or access to referenced secrets, executing those files crosses the boundary intended for metadata work. GitHub warns that running untrusted code under pull_request_target can lead to cache poisoning and unintended access to write privileges or secrets. “Trusted workflow definition” is not equivalent to “all inputs used by this job are trusted.”

A review should list origins, not just steps. The trigger and workflow YAML belong to the base branch. GitHub supplies the event payload, but a contributor can influence fields such as PR title, branch name, and filenames. The PR head's files are directly controlled by the contributor. Tokens and environment secrets belong to the base repository. A trusted API does not sanitize every value passed to it: interpolating a PR title into a shell command can be dangerous even without checkout. A metadata workflow should pass contributor-controlled text as data to fixed API parameters, never build code, queries, or shell fragments from it. Identity and data flow need separate inspection.

A metadata-only design example

Assume PR #42 comes from a fork and targets the main branch. The requirement has two operations: read the PR's current labels using its event-supplied number; if needs-review is absent, add that fixed label. The proposed job gives permissions only the repository read access and PR label-writing ability needed for those API calls. It uses a fixed, reviewed action or API request, never checks out the PR head, does not run project scripts, and does not load configuration from PR files. The expected result is that PR #42 gains the label while repository files, release artifacts, and deployments remain unchanged. This is a design exercise; no GitHub workflow was run and no real PR was labeled for this article.

No-checkout does not make that job automatically safe. A mutable third-party action, unsafe expression interpolation, or code that turns contributor text into a command can still be vulnerable. Third-party actions run with the job's authority, so permissions should reflect the actual API work and action provenance should be reviewed. A labeler does not need contents: write, actions: write, or deployment credentials merely for convenience. This site's article on GitHub Actions token permissions explains why an action may reach the token context even when the workflow did not pass it explicitly as an input.

Use the same PR #42 for a counterexample. Its author changes a test script. A privileged job checks out that head and calls npm test, which executes author-controlled code; dependency installation can be another execution point. The safe design review rejects this combination before running it, rather than waiting for suspicious log output. If the job also writes dependency caches, contaminated material may influence later builds. Cache poisoning and secret exposure are distinct outcomes, but both follow from giving low-trust input a privileged execution path. The common response “fork PRs do not receive secrets by default” describes restrictions on ordinary fork-triggered PR workflows. It cannot be transplanted unchanged to a workflow deliberately running in the base repository's context.

Test the patch in a different authority context

The need to test PR code does not disappear. Put build, dependency installation, and tests in a pull_request workflow with explicitly limited permissions, no deployment secrets, and no automatic promotion of its caches or artifacts into privileged release inputs. Keep the pull_request_target job for labels and comments. Separation requires more than two YAML jobs: inspect whether workflow_run, artifact downloads, or shared caches later carry low-trust output back into a high-privilege step. If a privileged step must consume a PR-produced result, define a constrained result format, verify its identity and contents, use fixed trusted execution code, and review that trigger's permissions separately. GitHub gives a separate warning about executing untrusted code in privileged workflow_run paths.

Who may change the PR head matters more than whether the contributor looks friendly. A same-repository PR can modify test scripts too. An organization may choose to trust certain contributors at certain permission levels, but that is an explicit policy decision, not a guarantee supplied by the event name. Ordinary fork tests can report failures and logs with restricted authority. Write operations needing maintainer authority belong on a path that does not interpret the PR's code. Repository settings such as first-time contributor approval should be checked in the actual repository; they are not a universal substitute for sound job design.

For a proposed workflow change, ask four questions. Which commit supplies each executable file? What can this job's token and secrets do? Does contributor-controlled text or an artifact enter as data or as a command? Will another privileged workflow trust its output? A non-secret-bearing hypothetical PR that merely changes a test script to write a visible marker can support static review: the privileged metadata job should have no path that invokes it. In an authorized isolated test repository, the low-privilege test job may run it but should not gain write authority. No such test was run here; actual observations belong in that repository's execution record.

Choose the trigger from the operation. For PR metadata, stay in the base-repository context without interpreting the head. For tests, use a lower-privilege execution path. For publication based on test results, create a separate artifact-identity and authorization check. Moving all three operations back into pull_request_target reduces the number of YAML files, not the PR author's control over the executed content.
