Why an explicit NULL does not use a PostgreSQL column default

Keep omission, explicit clearing and supplied values distinct so database defaults receive the intended input.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-18 · Estimated read 8 min
Translations
zh-CN en

Article

A table can have a configured default while records created through an API still contain null. Inspect the generated INSERT first: omitting a column, requesting DEFAULT and supplying NULL express different inputs. A database default is not a blanket replacement policy for every empty value.

A default needs an entry point

The PostgreSQL 18 default-value guide describes defaults for columns without supplied values and explicit requests for default values. The INSERT reference specifies omitted-column and DEFAULT behavior. These mechanisms do not turn an explicit NULL into the declared default. The discussion here assumes an ordinary nullable column without additional triggers or write transformations.

Suppose a draft table uses a pending status by default. The following statements illustrate three inputs. The first omits status, the second requests its default, and the third supplies null. Under this hypothetical schema, the third does not become pending merely because a default exists. None of this SQL was executed.

CREATE TABLE drafts (id integer, status text DEFAULT 'pending');
INSERT INTO drafts (id) VALUES (1);
INSERT INTO drafts (id, status) VALUES (2, DEFAULT);
INSERT INTO drafts (id, status) VALUES (3, NULL);

For a real investigation, obtain the application’s final column list and parameters rather than stopping at the schema file. Imagine a request without status being normalized into a complete object containing null for every missing field. If that null is then written, the application has changed the input before the database can apply omission behavior. This is a proposed investigation path, not a claim about every ORM.

Preserve the caller’s three meanings

An interface should distinguish an unprovided field, an explicit request to clear it and a supplied status. For creation, omission may select the system default. Whether clearing is allowed is a business decision. If it is forbidden, explain the validation failure and align storage constraints with the contract. Quietly replacing a requested clearing with pending misrepresents what was saved.

Updates need a separate agreement. An omitted update field often means keeping its existing value; applying creation defaults may reset it instead. That is a design recommendation, not a universal statement about update protocols. Review bulk uploads, older clients and administration tools against the same agreement, including their treatment of missing fields, empty strings and nulls.

If the application fills defaults itself, identify who maintains the rule. Separate application and database defaults can diverge during version changes. When the database owns the default, verify that the write actually omits the column. When the application owns it, describe it as application policy and plan checks across old and new versions during migration.

Follow the value from request to storage

Proposed cases include omission, explicit null, an allowed status and a prohibited status. Inspect final parameters and stored values, then add update cases for retaining and clearing existing values. No such cases were executed here. Triggers, generated columns or specialized transformations require inspecting the actual schema before drawing conclusions.

Do not backfill historical nulls solely because a default is declared. Determine whether they mean unknown data, historical omission or permitted clearing. New-write policy and historical repair are separate decisions. The October 17 article on row and non-null input counts explains a related consequence. A useful review follows one traceable path: what the caller expressed, what the application supplied and what the database saved.
