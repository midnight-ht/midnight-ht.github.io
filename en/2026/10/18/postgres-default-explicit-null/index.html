Why Explicit NULL Does Not Use a PostgreSQL Column Default

Trace omission, DEFAULT, and NULL through SQL, non-null rejection, updates, mixed-version defaults, and historical repair.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-27 · Estimated read 12 min
Translations

Article

Key takeaways

  • Omission, DEFAULT, and NULL express different write intents.
  • NOT NULL rejects null rather than choosing a fallback.
  • Changing a default does not backfill historical nulls.

Suppose a draft status defaults to pending, but an API converts an omitted status into NULL before issuing INSERT. The default still exists; the database did not receive an omitted-column input. For an ordinary column, DEFAULT does not automatically replace an explicit NULL. Trace the request, mapped object, and final SQL to find where the intent changed.

Three input paths

The PostgreSQL 18 default rules distinguish an unspecified value from an explicit request for the default. The INSERT reference specifies omitted-column handling. This discussion assumes an ordinary nullable status column without triggers or extra transformations; identity and generated columns have additional rules.

The following SQL is an unexecuted teaching fixture, not a deployed draft service.

CREATE TABLE drafts (
  id integer PRIMARY KEY,
  status text DEFAULT 'pending'
);
INSERT INTO drafts (id) VALUES (1);
INSERT INTO drafts (id, status) VALUES (2, DEFAULT);
INSERT INTO drafts (id, status) VALUES (3, NULL);
SELECT id, status FROM drafts ORDER BY id;

The documented semantics imply pending for the first two records and NULL for the third. Omission, a request for the database default, and an explicitly supplied null are different instructions. An empty string is another concrete value whose acceptance needs its own policy.

Imagine a JSON request containing only id. A DTO initializes every optional property to null, then persistence writes all keys. The database receives the third path and cannot reconstruct the original omission. Investigate field presence, final column lists, and parameter types with appropriate redaction. This is an investigation hypothesis, not a claim that every ORM maps fields that way.

NOT NULL rejects; it does not fall back

If status cannot be null, align API validation and a NOT NULL constraint. An explicit NULL is rejected, not automatically retried using pending. A default chooses a value when requested or omitted; a non-null constraint restricts stored values.

Catching every insertion error and retrying with pending is a dangerous counterexample. The error could concern a primary-key conflict, another constraint, or a connection. The retry both hides the cause and may override a caller's intentional clearing. If the API deliberately treats null as “use default” during creation, document and map that specific contract before persistence.

COALESCE can implement an explicit null-replacement policy in a query, but that policy belongs to the query. It is not evidence that the column's DEFAULT handled the null. If the application hardcodes pending while the database default later changes to queued, the two paths can diverge. Name the owner of the default and verify mixed-version writes.

Creation and update need different mappings

Suppose an existing record is approved and an update changes only its title. Applying creation defaults to omitted status can reset it. The UPDATE column-assignment rule states that columns absent from SET keep their previous values. Decide how request omission becomes “do not modify” rather than reusing a creation DTO without review.

An explicit reset can use SET status = DEFAULT where appropriate. Explicit clearing uses NULL subject to constraints. Imports, administration tools, and older clients need the same intent review; a correct primary API does not establish consistency across every writer.

A parameter containing the string DEFAULT is data, not the SQL keyword. Do not splice arbitrary client strings into SQL to create a reset action. Define a controlled business operation and let the server choose an allowed statement structure. Values and instructions must remain distinguishable.

Does changing the default backfill old NULLs?

No. The ALTER TABLE reference says setting or removing a default affects subsequent relevant writes, not existing rows. Three historical NULLs might represent an old import omission, legitimate clearing, and a pending manual decision. A new default supplies no evidence that they should all be replaced.

For a repair, identify the erroneous population using reviewable conditions, record its expected scope and recovery plan, and perform a controlled update. WHERE status IS NULL does not establish that every selected row is erroneous. Stop new incorrect writes as well, or the repaired population will immediately grow again. No backfill was performed for this article.

Deployment order matters. If the database changes first while an old application still explicitly writes the old status and a new application starts omitting it, both statuses can appear during coexistence. Validate downstream compatibility or arrange the write-policy migration before changing the default. A new application passing alone does not verify every old entry point.

Diagnostic records can associate application version, entry point, field presence, controlled SQL path, and task identity without retaining complete private requests. Apply the project's access and retention rules. No logging service was implemented here.

Proposed creation cases include omission, explicit null, an allowed value, and an illegal value. Compare original presence, generated SQL, parameters, and stored results under nullable and non-null schemas. For updates, begin at approved and test omission, clearing, a supplied value, and resetting to default. Then change the default and confirm old rows remain while new defaulted writes change. These checks were not run; inspect real triggers and mappings before fixing expectations.

The related row versus non-null input count article explains a consequence of null data. Repairing this problem requires the earlier trace: caller intent, actual SQL input, default ownership, and evidence for the historical repair population.
