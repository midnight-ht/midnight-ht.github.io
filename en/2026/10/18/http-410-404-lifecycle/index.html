Does an empty lookup justify HTTP 410?

Distinguish missing and retired resources with lifecycle evidence, failure paths, cache recovery, and marker retention.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-25 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • An empty lookup does not establish retirement, and 404 promises no recovery.
  • Verify public retirement, cached responses, and internal cleanup separately.
  • Correcting retirement requires authoritative state and public-entry checks.

An empty lookup does not establish permanent retirement. A 404 describes an unavailable current representation or unwillingness to disclose existence; a 410 requires grounds for believing that access is unavailable and likely to remain so. Choose from lifecycle knowledge, while separately addressing disclosure, caching, and correction of mistaken retirement. Do not translate every empty result into “gone permanently”.

What knowledge distinguishes 404 from 410?

RFC 9110's 404 definition does not classify absence as temporary or permanent. Its 410 definition describes access that is no longer available and likely permanently so. When the origin cannot determine permanence, it ought to use 404. The mnemonic “404 temporary, 410 permanent” invents a recovery promise for 404.

An empty lookup might mean a mistyped identifier, unsynchronized data, retired material, or an object whose existence should not be disclosed. These require different evidence. A failed dependency query is also not an ordinary empty result. Keep internal failures distinguishable from lifecycle knowledge, or a temporary data-source failure can become a public retirement statement.

410 is not an absolute prediction either. Its qualified permanence allows correction of a mistaken decision or a policy change. Establish who can revise retirement and which routes, caches, and explanations must then change. A status code communicates external semantics but cannot perform that governance.

How would a document move from availability to retirement?

Suppose a service publishes an event document and its owner deliberately retires it after the event. This complete example has not been deployed. During normal service, requests return the current document. At retirement, record the old identifier, decision basis, effective scope, and responsible party, then return 410 with an appropriate explanation. Keeping a separate retirement record is an implementation suggestion, not an RFC-mandated table.

A subsequent visit to the old link should receive a real 410, rather than 200 with “Deleted” in the body. If a public replacement exists, provide a verified route without claiming that it fully continues the original resource. If the resource merely moved, design migration behavior instead of classifying every move as retirement to simplify logs.

Next request an identifier that never existed, and handle that as unknown absence. Request a confidential document as an unauthorized caller and apply the disclosure policy. A test's privileged knowledge of an existing database row does not justify naming that object in a public error. A retirement explanation must also avoid disclosing private ownership, reasons, or history.

Finally simulate failure to read retirement evidence. Returning 410 for every unknown address would turn dependency failure into a lifecycle decision. Exposing a retired object as normal could violate policy too. Define an observable failure path under the service contract instead of treating all error responses as interchangeable.

Why might users still see 410 after restoration?

404 and 410 are among the statuses identified as heuristically cacheable, subject to method, explicit controls, and other applicable conditions. Restoring the origin's representation does not instantly remove prior cached responses. Browsers, intermediaries, and CDNs can have different storage and invalidation behavior. One successful origin request does not establish recovery through the public entry point.

In the example, the owner discovers a mistaken retirement and restores the material. A proposed recovery first checks authoritative state and routing, then examines entry points that cached the error. Invalidate or wait according to the actual cache's defined behavior. Compare origin and public responses for the same resource, identifying any location still returning 410. This is an unexecuted plan; no CDN was exercised and no universal lifetime is recommended.

A refresh button that leaves reusable cached responses untouched is a counterexample. Clearing only an application cache while overlooking an edge's negative response is another. Without a record of retired addresses, an operator may not even know which entries need inspection. Resources with meaningful correction needs should acquire cache and recovery decisions during retirement design.

Must retirement markers be retained forever?

No. The RFC leaves both marking all permanently unavailable resources as gone and retaining those marks for any length of time to the server owner. A permanent-unavailability judgment does not require indefinite marker retention. Choose scope using old-link value, storage, privacy, and accountability needs. Returning 404 after deleting a marker does not establish that the resource returned.

Retaining the marker preserves known retirement; removing it can leave only unknown absence. Ask whether clients rely on the explicit signal, maintainers need recovery evidence, or identifiers can be reassigned. If addresses can be reused, define how a new object differs from the old one so stale caches or clients do not misinterpret the relationship.

Public retirement also does not prove internal destruction. Files, backups, search copies, and audit records have separate lifecycles. A 410 describes access to the target at the origin. A data-deletion obligation needs its own task and verifiable outcome. The site's 202 and terminal-state article separates acceptance from completion; a public response likewise cannot sign off an internal cleanup process.

Client recovery should follow evidence too. A 404 does not promise that repeated retries will succeed, and 410 does not require erasing every associated local record. Keeping bookmarks, offering alternatives, or contacting support are application-contract decisions. Do not expand protocol semantics into an irreversible business action without such a contract.

The proposed acceptance matrix covers normal resources, unknown identifiers, traceable retirement, nondisclosure, unavailable retirement evidence, and mistaken-retirement recovery. Record the decision basis, status, body, cache conditions, and client action; compare origin and real entry points during restoration. No HTTP regression or cache experiment was run here. The supported conclusion concerns the evidence needed for status selection; actual implementation conformity requires those checks.
