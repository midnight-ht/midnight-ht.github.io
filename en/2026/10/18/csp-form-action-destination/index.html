CSP Form Destinations Need form-action, Not a default-src Assumption

Review native forms, submit-button targets, delivered policies, script requests, and redirect checks as separate paths.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-23 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • form-action has no default-src fallback.
  • Inspect button overrides, URL resolution, and script-based senders.
  • Record delivered policy, receiver observations, and business receipts.

Even default-src 'none' provides no fallback for form-action. A native form's destination needs its own directive and an inspection of the resolved target. Start a checkout review with “this document submits to this origin,” then inspect the delivered policy. Strict resource-loading defaults cannot establish a form-destination restriction.

Separate form navigation from resource loading

The W3C CSP Level 3 form-action section constrains form-submission targets through a source-list pre-navigation check. The inspected document was a September 16, 2026 Working Draft, not a promise of identical browser implementations. MDN's form-action reference explicitly documents the absence of a default-src fallback and warns about implementation differences for redirects.

Imagine a merchant document at shop.example.test with a native form submitting test registration data to pay.example.test. Its only directive is default-src 'none'. Concluding that the cross-origin form must be blocked overlooks the relevant directive. A document needing no form submission can be assessed for form-action 'none'; legitimate same-origin and partner submissions need a list reflecting those actual destinations. The following policy is illustrative and unexecuted, and the names identify no real payment service.

Content-Security-Policy: default-src 'none'; form-action 'self' https://pay.example.test

This demonstrates destinations, not a complete checkout policy: script, style, and other resource needs remain unspecified. The proposed expectations permit the same origin and named partner while rejecting another controlled origin. Use non-sensitive test data and controlled receivers rather than sending real orders or identity material to an unfamiliar endpoint.

Record the environment and owner of every destination. Test and production partners may differ. When a partner changes, the business must decide whether the old origin remains necessary. Adding every newly reported domain defeats the purpose of the review. An allowlist should reflect a justified recipient and data transfer, not merely a matching URL.

Inspect submit buttons and actual sending mechanisms

The HTML Living Standard's submission attributes define formaction on submit controls, allowing a different target for that submission. Review each actual submit button as well as the form's action. A default button and a partner-transfer button can take different paths.

Relative actions also depend on the document's base. The related article on base-uri and relative URL resolution explains how to retain raw and resolved addresses. A string such as save containing no external hostname does not itself establish a same-origin destination.

Another counterexample intercepts submission and sends data through a script interface. CSP3 assigns script connections to connect-src; a form-action allowlist does not establish an identical policy for those requests. Identify the mechanism first. The browser's request type, initiator, and destination help establish whether a test exercised native submission.

Conversely, blocking a script connection does not establish that the native form path is restricted. A page may use both mechanisms. If a refactor changes the sender, repeat the relevant acceptance checks rather than relying on the same button having been tested previously.

Verify delivered policy and controlled receivers

A proposed test records browser version, entry document, all delivered CSP headers, and any report-only policy. Reporting is not enforcement. If a proxy and application both send policies, inspect all effective policies; adding a more permissive one does not necessarily relax an existing restriction.

Prepare same-origin, approved-partner, and disallowed controlled receivers. Submit non-sensitive fields through each relevant button. Retain resolved targets, network observations, console violations, and receiver records. Separate browser blocking from server business rejection. A successful terminal request does not test submission under a document's browser policy.

Test redirects separately: whether the receiver redirects, its destination, and the behavior of each supported browser version. Historical browser examples in MDN establish a reason to investigate, not a current compatibility matrix. A payment flow dependent on a partner redirect needs current observed evidence, rather than a promise that one match controls every later navigation.

Does form-action 'self' prevent cross-site request forgery?

An outbound restriction is not server-side request-authenticity validation. It describes where this document's forms may submit; it does not prove that every request received by the server came from that document. Authentication, action authorization, and appropriate request protections remain separate. A permitted destination can reject input, and a submitted form is not necessarily a completed order. Feedback should distinguish retryable failure, input correction, and an unknown final state.

Give the denied path a known-good control. First prove the controlled receiver can observe an allowed submission, then test the disallowed destination and correlate browser and receiver records. A broken receiver makes “nothing arrived” ambiguous between blocking and network failure. An unverified reporting chain also makes silence inconclusive. Define expectations before execution and retain one test identifier across observations.

Inspect feedback after blocking. The page must not display registration success for a blocked submission or automatically repeat an attempt with an unknown outcome. Before retrying after a policy repair, establish whether an earlier attempt reached the receiver. This tests user outcomes without expanding the directive's responsibility.

This substantial rewrite preserves the original publication date and URL. It adds submit-button overrides, sending mechanisms, and grouped acceptance checks. No browser submission, receiver test, or payment was executed. Useful evidence connects the document, final target, effective directive, observed blocking, and business receipt; a screenshot of one header cannot establish the complete path.
