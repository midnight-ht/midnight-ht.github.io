Ready containers, waiting Pod: readiness gates need update and withdrawal owners

Separate missing, False, and Unknown gates, then trace registration confirmation, status updates, stale True, and recovery.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-25 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • Container readiness and every declared gate must hold together.
  • Missing, False, and Unknown lead to different investigations.
  • Business evidence expiry and withdrawal need explicit ownership.

Containers can be Ready while their Pod waits for custom readinessGates. In addition to container readiness, every declared gate must be True. A missing condition is treated as False, and an explicit Unknown also does not satisfy the gate. Follow the ownership of condition production and updates rather than repeatedly restarting containers whose probes already pass.

A name in the specification is not a business result

The Kubernetes Pod lifecycle documentation describes gates as additional readiness signals, stable since version 1.14. The specification declares condition types; status supplies results. Adding a name does not create a controller that can evaluate the underlying business state.

There are two contracts: the application declares what must hold before the Pod is ready, and a status writer supplies current evidence. The kubelet evaluates the recorded conditions. It does not contact an external business system or infer successful registration. If no writer exists, continued waiting matches the declared requirement.

Missing, False, and Unknown lead to different diagnostic questions. For missing, identify the writer and target object. For False, inspect the unmet business condition. For Unknown, determine why the writer cannot decide. All fail the readiness requirement, but calling all three “probe failure” loses actionable information.

Build a complete external-registration chain

Consider an unexecuted example: the container can answer internal requests, but external router registration is required before the Pod becomes ready. This undeployed specification fragment declares an illustrative condition name.

spec:
  readinessGates:
    - conditionType: delivery.example.test/RouteRegistered

The container probe passes before the custom condition exists, so the gate remains unsatisfied. A registration controller sends a request, receives confirmation corresponding to the current Pod, then writes the matching condition True through an authorized status-update path. Sending the request alone does not establish successful registration. Treating submission as completion removes the gate's business meaning.

If registration is rejected, the controller should retain a useful reason and produce an appropriate non-True state rather than remain silent indefinitely. A timeout with an unknown outcome can justify Unknown and reconciliation. A misspelled status type does not satisfy the required name even if that unrelated condition is True. Align specification type, status type, Pod identity, and controller records.

Object identity also requires more than a name. A replacement may represent the same logical instance while being a different Pod. Old registration evidence should not silently establish readiness for the replacement. Relate external objects to the current workload identity and prevent delayed responses from assigning old results to new objects. These are design recommendations requiring validation against the actual client, API, and business model.

Verify the status-update path separately

The documentation permits applications or operators to set custom conditions through API PATCH and distinguishes this from ordinary object edits. Use an appropriate status interface and permissions. Constructing a True object in code does not establish that the API server accepted it or that the kubelet observed it.

Separate business-confirmation failure, authorization failure, update conflict, type mismatch, and observation delay. Each points to a different repair. Broadening permissions can conceal a flawed identity design, while restarting a container cannot give an independent controller permission to update status. Inspect update responses and actual Pod state before selecting the investigation path.

Use gates for conditions that genuinely determine whether work can be served. Attaching nonessential retrospective statistics to readiness can make telemetry failure block service. Conversely, omitting a necessary registration condition can announce availability too early. The criterion is the condition's causal relationship to the service promise.

Does an old True expire when the controller disappears?

Do not assume custom conditions carry automatic business leases or failure timeouts. True is a recorded state. If confirmation must expire, implement reevaluation and withdrawal ownership. The readiness mechanism does not define the lifetime of external registration evidence.

Suppose registration is later deleted while the controller is unavailable. Pod status can retain an old True while container probes continue passing. Neither proves registration still exists. Periodic checks, external events, or independent controller-health detection may support a withdrawal policy, but identify who writes non-True and who detects an unavailable writer. Expecting a failed controller to reliably announce its own failure leaves a responsibility gap.

Withdrawal must also account for transient faults. Removing service on every query timeout can amplify dependency disruption; retaining True for a long interval accepts stale evidence. Choose grace and alerting by business tolerance rather than inventing a universal timeout. Define fresh confirmation, expiration, and recovery as testable rules.

Cover the failure lifecycle

A proposed validation first makes containers ready, then supplies missing, False, Unknown, and True gate states and observes Pod Ready. Add the inverse case: all gates True while a container is unready. Custom True must not be mistaken for an override of container checks. With multiple gates, any unmet condition should remain explainable.

Also test registration success followed by failed status update, incorrect type, controller restart, delayed old responses, evidence withdrawal, and recovery. Preserve external confirmation, API response, actual Pod conditions, and business-path observations separately. Manually setting True during an emergency needs an explicit business decision and operation record; it does not prove the registration failure repaired.

No cluster, status mutation, or traffic verification was performed here. As with release artifacts and rollback, readiness covers one layer of a delivery promise. Assign each gate a producer, supporting evidence, withdrawal owner, and recovery rule, then verify those responsibilities under real failure conditions.
