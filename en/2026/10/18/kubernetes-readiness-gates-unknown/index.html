Why ready containers can leave a Pod waiting for a readiness gate

Custom readiness gates need every listed condition True; missing conditions count as False. Assign status ownership beyond container probes.

Updated 2026-10-18 · Estimated read 8 min
Translations
zh-CN en

Article

A container can be Ready while its Pod is not. With readinessGates, all containers must be ready and every listed custom condition must be True. An unwritten condition is not temporarily ignored: Kubernetes treats a missing condition as False.

A passing probe answers only part of the question

The Kubernetes Pod lifecycle documentation describes custom readiness gates as additional signals for Pod readiness. The application declares condition names in the Pod specification; the kubelet checks the corresponding status conditions. This feature has been stable since Kubernetes 1.14. That scope does not extend unrelated new features from the current online documentation to older clusters.

Suppose a hypothetical service can answer requests inside its container, but the team also requires successful registration with an external router before the Pod is considered ready. A passing container probe establishes only the first condition. If the registration controller never writes the agreed condition, continued waiting does not automatically mean the probe is broken. No cluster was accessed for this article; the scenario illustrates a division of responsibility.

Show container status alongside Pod conditions during diagnosis rather than capturing only a green indicator. Compare the declared condition name with the type recorded in status. A small naming mismatch can leave the kubelet unable to find the condition it was told to evaluate, even when someone believes a status update was made.

Missing differs from explicitly Unknown

The documented default for a missing condition is False. That is a different record from a present condition whose status is Unknown. Neither meets the requirement that every gate be True, but the diagnostic questions differ. For a missing record, first identify its writer. For Unknown, investigate why that writer could not determine the state.

Do not mark a condition True simply to unblock a release without assessing its business meaning. That changes the service-readiness promise. A registration gate needs registration evidence; an obsolete gate needs an intentional configuration and release-standard change, with a recorded reason.

Restarting the container may not repair the condition either. Its writer may be a separate controller with a permissions problem or failed external dependency. Find the owner of the status update and follow that path. This article establishes no actual incident cause and performs no status mutation.

A gate needs a writer and a withdrawal rule

The documentation explains that an application or operator can set custom Pod conditions using the API’s PATCH action. Implement the update through an appropriate status interface and check the capabilities of the target client and cluster. Adding a condition name to the specification does not implement its controller.

A design review should establish who writes True, which evidence justifies it, who changes it to a non-True state when that evidence expires, how controller failure is detected, and how recovery triggers a new assessment. Withdrawal and recovery rules are engineering recommendations here. The readiness mechanism does not decide what external registration means for the business.

Proposed tests should include ready containers with a missing gate, an explicit False, an Unknown condition, and all conditions satisfied. Inspect actual Pod state and the intended business path, then record what happened. None of these branches was run here; Service routing and user requests have no verified result in this article.

This distinction connects with release artifacts, availability, and rollback, published on October 8, 2026. A delivery record should name the evidence still awaited and its provider. After a container turns green, the remaining conditions behind the Pod’s readiness promise still need an explanation.
