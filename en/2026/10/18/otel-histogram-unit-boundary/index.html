How should histogram buckets and history move from milliseconds to seconds?

Convert values, boundaries and thresholds together, preserve comparability across releases, and distinguish unit scaling from lost historical resolution.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-26 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • Declaring a unit does not convert values; assign conversion ownership without duplication.
  • Measurements, buckets, thresholds and consumers need a common duration contract.
  • Existing buckets can be scaled, but their counts cannot recover unrecorded finer distributions.

A 300-millisecond observation is now recorded as 0.3 seconds, but a bucket upper bound still contains the number 500. Data can export while its distribution meaning changes. Histogram migration must align values, bucket boundaries, thresholds and historical consumers, rather than merely replace a unit string. Assign conversion ownership, then define where old and new streams remain comparable.

Units and values are separate inputs

The OpenTelemetry 1.62.0 Metrics API defines unit as an optional author-supplied string that the API should treat as opaque. Histogram Record accepts the caller's measurement value separately. Neither input proves the other correct. The semantic conventions 1.44.0 metric guidance recommends seconds for durations; that recommendation does not divide existing millisecond values automatically.

If a timer produces 300 milliseconds and the recording contract uses seconds, the input should be 0.3. Retaining 300 while declaring seconds changes interpretation. If the application already supplies 0.3 and a Collector divides again, the error goes in the other direction. Inventory transformations from timer and helper through SDK, Collector and query, with explicit ownership for each conversion.

Display formatting is another concern. A dashboard displaying seconds as milliseconds does not establish correct SDK data. Start with known caller inputs and raw export before interpreting presentation. Conversely, a large value might represent a genuinely slow operation; do not scale it simply because the chart looks implausible.

Move buckets and thresholds with the values

Consider unexecuted teaching inputs of 50, 300 and 1,200 milliseconds. Old finite bucket upper bounds are 100, 500 and 1,000 milliseconds, followed by the positive-infinity bucket. Under inclusive upper bounds, the observations belong to the first, second and final buckets respectively.

In seconds, values become 0.05, 0.3 and 1.2, and finite bounds become 0.1, 0.5 and 1. Their bucket assignments retain the same duration meaning. If values change but bounds remain numerically 100, 500 and 1,000, all three observations can enter the first finite bucket. The count is still three and export still works, but the original resolution is lost. Correct totals do not prove a useful distribution.

A threshold needs the same treatment. A condition representing more than 500 milliseconds corresponds to 0.5 seconds in the new stream. Leaving 500 changes the condition. Inventory alerts, variables, dashboard descriptions and business targets, identifying which stream generation each consumer reads. These numbers are hand-checkable examples, not SDK output or measured service latency.

The SDK's explicit histogram definition expresses buckets by upper bounds, exclusive below and inclusive above. An input exactly equal to a boundary tests the inclusive-upper-bound rule that ordinary interior samples cannot distinguish. Record actual aggregation and export representation rather than assuming this explicit-bucket procedure covers every histogram type.

Preserve meaning during mixed deployment

When versions coexist, consumers need to identify their contracts. Depending on the real system, this may use distinct stream names, explicit version scope or a validated transformation path. Do not assume that different unit strings force every backend to isolate streams safely. Identity conflicts and export behavior require implementation evidence.

A failure pattern is renaming an old dashboard “seconds” halfway through deployment while still aggregating both generations. A sharp decrease is not performance evidence. Before-and-after comparisons need common semantics, defined time windows and known instance sets, including unmigrated versions. Where comparability is unavailable, separate charts or show a discontinuity instead of hiding it for visual continuity.

I would prefer validating a new stream in a separate scope, migrating consumers, then retiring the old stream. This adds temporary maintenance work while keeping recording, conversion and query failures distinguishable. Central conversion can also be appropriate, but it needs proof that some callers have not already converted their inputs.

Can old bucket counts recover finer new buckets?

No. Aggregated counts do not preserve individual observations inside a bucket. Scaling units can change the numerical representation of existing boundaries without creating new distribution information. Two observations somewhere between 100 and 500 milliseconds might both be near 120 or both near 490. Their old counts match, but their assignments to a new 200-millisecond boundary differ.

Separate exact scaling of old buckets from the inability to reconstruct finer boundaries. More detailed historical analysis requires independently retained raw events or sufficiently detailed data. If none exists, mark that history as unable to answer the question. A query producing precise-looking numbers does not recreate the original distribution.

Validate known inputs through the pipeline

Proposed checks preserve timing provenance, recording entry point, exact SDK and semantic-convention versions, View and exporter configuration. Verify conversion happens exactly once, then inspect count, sum and bucket membership. Include zero, exact boundaries, large values and mixed process versions. If raw SDK output is already wrong, repair the entry point rather than compensating in a dashboard.

Continue through the Collector and backend query, comparing units and boundaries at each stage, then check alerts and display text. Include old callers that bypass the shared helper: one correct helper cannot prove universal adoption. These checks were not executed, and no performance improvement or error measurements are reported.

Delta and Cumulative boundaries concern temporal aggregation, not unit correctness. Completion evidence is a known input retaining the same duration meaning through every layer, with a clear historical comparison boundary. Changing the legend alone does not complete migration.
