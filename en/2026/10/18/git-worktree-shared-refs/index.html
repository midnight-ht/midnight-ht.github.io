Do Separate Git Worktrees Have Separate References and Stashes?

Trace two parallel saves to separate private HEADs and indexes from shared stash positions, object identity, and cleanup ownership.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-24 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • HEADs and indexes are separate; ordinary references are generally shared.
  • Stash positions move, so verify object identity and patch content.
  • Confirm restoration separately from deleting shared recovery entries.

Two worktrees have separate working directories, indexes, and HEADs, but generally share ordinary branch, tag, and stash references. A different directory does not establish that stash@{0} belongs to the current task. Before restoring parallel work, verify the saved object's stable identity, its actual changes, and the destination's current state. “Most recent” names a position that can change.

A separate HEAD is not a private branch copy

The Git worktree reference rules distinguish per-worktree pseudo-references from generally shared references under refs/. Each worktree has its own HEAD. References inside refs/bisect, refs/worktree, and refs/rewritten are exceptions and remain per-worktree. Neither “everything is shared” nor “HEAD is separate, therefore branches are private” accurately describes the boundary.

Suppose task A repairs a release script while task B edits documentation in another directory on another branch. Their uncommitted files and staging selections do not automatically synchronize. Creating an ordinary tag or changing an ordinary shared branch reference has a different scope. File isolation is not reference isolation. Git's default refusal to check out a branch already checked out elsewhere is a protection worth respecting, rather than routinely overriding to remove a warning.

Index independence has a practical meaning too: staging a file in A does not add it to B's index. Conversely, A's clean index says nothing about B's unfinished work. A handoff that reports “the repository is clean” should identify which worktree was checked. The discussion of restore sources and destinations examines directory-local state. This article adds the shared state between directories.

How two saves change who owns the zero entry

The Git stash description places the latest stash in refs/stash and older entries in that reference's reflog. Combined with worktree reference sharing, this means ordinary stash lists do not split into independent lists for the two directories. The following sequence is an unexecuted exercise. No stash was created, applied, or deleted in the current repository.

A edits release.txt, saves a stash with a task description, and immediately records its object identifier, source branch, and patch. At that moment it is entry zero. B then saves its docs.txt changes from another worktree. The new zero entry belongs to B, and A's record moves back in the list. If A restores the position remembered earlier, A selects a different object from the one originally saved.

Before restoration, A should list entries again, identify the saved object, and inspect that its patch really contains the intended release.txt change. Check the destination branch baseline and current differences as well. Descriptive messages help recognition but are not unique; two operators can use the same message. Object identity fixes which content is being discussed, while the task description explains ownership. Neither guarantees conflict-free application onto every later baseline.

These are unexecuted, read-only inspection examples. Replace the placeholder only with a confirmed object identifier. They inspect state without restoring work or deleting records.

git worktree list --porcelain
git status --short
git diff
git diff --cached
git stash list
git stash show -p <verified-stash-object-id>
git rev-parse --git-path HEAD
git rev-parse --git-path refs/stash

If the destination already contains unfinished changes, preserve a recoverable version before considering application over an exact scope. Do not clean both tasks' differences merely to make a command succeed. A restore method that retains the saved record can make it easier to verify content, staging intent, and business checks before separately deciding whether to remove the entry. This is a collaboration recommendation, not a guarantee that arbitrary conflicts can be resolved automatically.

Verify the restored task without sacrificing its neighbor

A proposed exercise builds two branches and directories in a disposable repository, then lets A and B save changes to different files. Verify that both directories see the same newer and older stash entries, and compare object identities across the two saves. After restoring A's content, check A's intended file, B's directory and index state, and the continued availability of B's required saved object. Seeing A's file reappear does not establish that B's recovery point survived.

Staging needs its own check. A stash records working-directory and index state, but restoring staging selections depends on the chosen options and whether they can be applied. If a handoff must preserve partial staging, retain both before-and-after differences rather than only checking file contents. Keeping a stash entry and restoring an index selection are different outcomes.

Ask Git to resolve administrative paths. A linked worktree commonly has a top-level .git file pointing to its management directory. Constructing a .git/refs/stash path by hand can both choose the wrong directory and assume an inappropriate reference-storage layout. The manual recommends commands such as rev-parse to account for private and common paths. Path discovery establishes scope; it is not a reason to edit internal storage directly.

Does knowing the object hash make deleting the list entry safe?

Identifying content does not establish that every user has finished with it. A stable identifier answers which object; cleanup changes shared recovery entry points and reachability conditions. Another task may still depend on that entry. Copying a hash into a conversation is not itself durable protection. Agree on retention method, retention period, and cleanup ownership instead of treating occasional recoverability as a backup contract.

Runtime isolation also needs independent evidence. Two worktrees can still use the same ports, database, or external credentials. Git separates editing state without provisioning two services. Record directory ownership, shared references, and runtime resources separately when starting parallel work, especially when a test command can modify data shared with another task.

Add an independent conflict exercise: after A saves, the destination branch changes the same part of the same file incompatibly. A conflict during application does not establish that the saved object is corrupt, nor justify deleting its entry or resetting the entire directory. Retain the conflict state and original object, inspect changed paths and unmerged index state, and choose resolution according to ownership.

Finish only after required content remains identifiable, no destination overwrite lacks explanation, and the neighboring task's saved records and directory state remain intact. Suspend shared cleanup until those conditions are checked. No conflict resolution was executed here; proposed steps are not a restoration receipt.

This article uses official Git manuals read on October 24, 2026, and executes no Git mutation commands. Evidence of restoration should identify the saved object, destination worktree, actual differences, and the neighboring task's retained recovery points.
