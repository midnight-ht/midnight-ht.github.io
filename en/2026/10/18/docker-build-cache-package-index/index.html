Docker package indexes: combining update and install still needs a refresh policy

Separate combined installation, cache invalidation, base-image pulling, and final package-version evidence in Docker builds.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-24 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • Combining update and install orders execution without forcing execution on every build.
  • no-cache and pull address layer reuse and base-image selection separately.
  • Trace a security update to final package versions, image identity, and the running service.

Combining apt-get update and installation in one RUN prevents a rerun of installation from using an index preserved in a separate layer. If the combined instruction is cached, it still does not contact the repository again. Package freshness depends on whether the installation layer executed, whether the base image changed, and which versions were installed. A successful build does not establish all three.

Combining operations fixes a specific separation

Docker's Building best practices recommend combining index updates and installation for Debian-based images. With separate layers, changing the installation list may reuse an earlier index update. The official sources were reread on October 24, 2026 for this substantive revision. No commands or scenarios below were executed; no image build or security update is claimed.

Suppose an image first updates its index and then installs a download utility. Days later, a maintainer adds an archive utility only to the installation line. The builder may reuse the unchanged index layer while executing the changed installation layer. Installation output proves that step ran; it does not establish that the index was fetched again. Availability of versions referenced by that index also affects the outcome.

This fragment combines related actions. It assumes a Debian-based image supporting the commands and is not a complete Dockerfile.

RUN apt-get update \
    && apt-get install -y --no-install-recommends curl unzip \
    && rm -rf /var/lib/apt/lists/*

The conjunction makes installation conditional on a successful update, while cleanup avoids retaining unnecessary index files in the resulting layer. Those actions happen only when the step executes. A command containing update is not proof that this build ran it.

Distinguish a changed list from an unchanged rebuild

Imagine a first build using the combined instruction, followed by a second build with no relevant input changes. The second can reuse the entire layer, including previously installed files; it has no newly downloaded index. A third build adds another utility to the combined instruction. When that changed step executes, it updates before installing. This paper matrix separates ordered execution from guaranteed execution on every build.

Docker's Build cache invalidation documentation explains that ordinary RUN cache does not invalidate merely with elapsed time. Repeating an unchanged installation command does not guarantee newer packages. If a release must query repositories again, select the invalidation scope explicitly.

The delivery goal determines the choice. Reusing an approved dependency layer can be appropriate for an application-only change. A release intended to incorporate a security fix should rerun the relevant installation stage and verify that the required version is available from the selected repository. Refresh intervals are a team policy, not a universal period supplied by this article.

A named dependency stage in a multistage build can make targeted invalidation possible with a supported --no-cache-filter option. Full --no-cache discards a broader set of build cache. Check the builder's version, option support, and actual stage structure rather than treating either switch as a guarantee for every environment.

Does disabling cache also fetch a new base image?

--no-cache alone does not guarantee the newest remote base image. Docker's best-practices guide separately describes --pull for attempting to obtain a newer base image. Base-image selection and subsequent layer reuse need independent decisions. If both must change, state both requirements and retain the identity actually resolved, rather than recording only the command string.

Pinning a base-image digest controls an input; it does not automatically obtain newer security content. Changing the digest needs review. Package version pinning likewise selects a desired version without guaranteeing that repositories retain it forever. Reproducing an older artifact and fetching new dependencies are different objectives. Deploying an approved artifact by identity can express reuse more accurately than rebuilding it.

For example, a build with both pulling and cache disabled may succeed while the repository still lacks the required fixed package. The package might not be present in the final runtime stage, or the service might still use the old image. Switches trigger actions. Verify the final package version, resulting image identity, and deployed version before claiming the fix reached users.

A failed refresh should remain a failed refresh

If updating the index fails, the example does not continue to installation. Retain the failure and follow the release policy: defer, repair repository access, or deliberately use an approved older artifact. Ignoring the update error to produce a green build cannot establish fresh dependencies. An explicit decision to use an old artifact is valid evidence of that decision, not of a new update.

A retry also needs proof that the intended step reran. Moving to another builder can change cache sources and base-image resolution. An unchanged Dockerfile name does not prove identical inputs. Retain input identities, repository policy, and installed versions where reproducibility matters, including the limitations imposed by external repositories.

Proposed isolated checks are to build the combined installation once, rebuild unchanged to inspect cache reuse, then change the package list and confirm execution of that step. Next, apply the chosen dependency-stage refresh, inspect installed versions in the final image, and confirm that the target package exists in the runtime stage. These remain test designs; no image digest or successful refresh log has been fabricated.

For another input boundary, see Git ignores and Docker build context. Deployment identity is covered by artifact and rollback checks. A package-update receipt should connect installation execution to the actual package version and then to the image serving requests. A cache hit describes reuse of one step in that chain.
