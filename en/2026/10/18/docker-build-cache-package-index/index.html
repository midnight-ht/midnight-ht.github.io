Why a cached Docker build can use an old package index

Package freshness needs an explicit cache decision and installed-version evidence. Combining update and installation fixes a narrower mismatch.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-18 · Estimated read 8 min
Translations
zh-CN en

Article

A Docker build cache hit does not prove that the package index was refreshed. Elapsed time alone does not force an ordinary RUN instruction to execute again. A release requiring fresh dependencies needs an explicit invalidation decision; reproducing an older artifact requires version records. “Rebuild it” does not adequately describe either goal.

A changed installation list can reuse an old index

Docker’s build best practices discuss apt-get in Debian-based images and recommend updating the index and installing packages in the same RUN instruction. Their separate-step example shows how adding an installation package can reuse a cached index update.

Suppose a hypothetical image updates the index in one step and installs a tool in the next. Days later, a maintainer adds another tool only to the installation list. Output from the later step does not establish that the package index was downloaded again. No image was built for this article; this is not a reproduced failure log.

The mistaken question is whether “the build ran.” The useful question is which steps executed. A build combines several operations, and partial execution differs from a complete refresh. An old index may cause installation trouble or versions that miss the intended update, depending on the repository and cached state.

Combining operations fixes a specific mismatch

Putting update and installation together ensures that when a changed package list invalidates that instruction and it executes, the index update precedes installation. It avoids rerunning installation against an index preserved in a separate layer. If the combined instruction itself remains cached, however, this build has not thereby contacted the repository or refreshed anything.

Docker’s cache invalidation documentation explains that RUN cache does not invalidate automatically. Repeating an unchanged package installation instruction does not guarantee newer packages. Documented options include changing a preceding layer, clearing cache, using --no-cache, or invalidating a particular stage with --no-cache-filter. Choose according to the update goal and build cost; none of these commands was executed here.

I would define the refresh policy before selecting a switch. Must a security-update build rerun the installation stage? May ordinary commits reuse it? Who checks the installed version? Those are team decisions, with no universal interval. Disabling all cache adds build work and still does not replace inspecting versions.

Freshness and reproducibility need separate records

Version pinning can reduce unexpected changes, but a chosen package version and the newest available package are different targets. If a repository removes the required version, an old Dockerfile does not guarantee rebuilding forever. Retain installed versions, base-image identifiers, build inputs, and the resulting image identifier. These are proposed delivery records, not artifact evidence collected for this article.

Avoid one “updated” flag for the base image, package index, and application dependencies. Even proof that installation executed needs to be followed by package-version checks and business validation. Conversely, when reusing an already reviewed image is the intended release method, record its identifier accurately. Another build should not be used simply to manufacture a more recent-looking receipt.

A related input boundary appears in Git ignores and Docker build context, published on October 11, 2026. At release time, use the checks in artifacts and rollback to identify the version actually serving users. A cache hit is evidence of build reuse. Actual version records must establish whether dependencies meet this release’s update requirement.
