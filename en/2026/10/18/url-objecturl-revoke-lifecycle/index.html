Who should revoke a Blob URL while its preview is still in use?

Use a single-owner preview controller to explain creation, replacement, release, shared addresses, persistent artifacts, and separate download acceptance.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-29 · Estimated read 11 min
Translations
zh-CN en

Article

Key takeaways

  • Image loading is not the end of every user interaction.
  • Every created address needs a clear owner and release point.
  • Preview display, persistent saving, and memory evidence are separate.

Do not revoke a preview's Blob URL merely because its image fired load while users may still save it, open it in a new tab, or inspect it. Give the preview component ownership of creation, replacement, and final release. A usable preview and a saved file remain separate outcomes.

Loading finished does not mean every use finished

MDN's Blob URL guidance, checked on October 29, 2026 and marked modified September 17, warns that revoking after image load can break interactions such as saving or opening the image. This article concerns a long-lived image preview, not a universal download timing recipe.

A document-upload screen may display the image successfully while the user still wants to enlarge or save it. The developer's convenient load event and the user's last use are different endpoints. A fixed delay replaces that ownership question with a guess about elapsed seconds.

MDN also explains that each createObjectURL call produces a new address even for the same Blob. Active addresses retain the backing object. Document unload releases them, but repeated replacements in a long-lived page need appropriate earlier cleanup.

Keep the address with its owner

This complete example has not been run. It assumes one dedicated image and no address sharing with independent windows or download queues. The caller must invoke dispose when removing the component; no framework lifecycle is automatically observed.

export function ownImagePreview(img) {
  let current = null;
  let disposed = false;
  return {
    set(blob) {
      if (disposed) throw new Error('preview disposed');
      const next = URL.createObjectURL(blob);
      const previous = current;
      try {
        img.src = next;
      } catch (error) {
        URL.revokeObjectURL(next);
        throw error;
      }
      current = next;
      if (previous !== null) URL.revokeObjectURL(previous);
    },
    dispose() {
      if (disposed) return;
      disposed = true;
      img.removeAttribute('src');
      if (current !== null) URL.revokeObjectURL(current);
      current = null;
    },
  };
}

A replacement creates the next address before handing it to the image. If assignment throws synchronously, that new address is released. After handoff, the previous address is no longer offered by this component. Disposal removes the source, releases the current address, and prevents later writes. Copying the address elsewhere would violate the single-owner assumption.

The implementation does not wait for the new image to decode before releasing the old one. An invalid replacement therefore does not retain the previous image as an automatic fallback. A requirement to replace only after successful decoding needs load confirmation, replacement identity, and failure recovery. Asynchronous image errors are not caught by the try/catch around assignment.

An upload preview and a gallery may legitimately choose different replacement behavior. The UI state and address ownership must agree. This example proves neither browser behavior in a target environment nor adoption by a real product.

Do two addresses for the same Blob expire together?

Treat each created address as a separate registration to release. If two components create separate URLs for the same Blob, revoking one does not discharge the other's cleanup responsibility. If they share one URL instead, one component can revoke something another still needs.

A shared design needs an explicit owner or a lease protocol handling abnormal consumer exits. For a simple preview, local creation and local release are easier to inspect, but that is not a performance conclusion for every resource-sharing design.

The revokeObjectURL reference states that invalid or already revoked addresses cause no action. Idempotent cleanup does not establish that its first invocation occurred at the correct time. The interface is unavailable in Service Workers, despite availability in other worker contexts.

Obtain separate evidence for saving

Creating an address is not a disk write. Preview display, download initiation, completion, and reopening the correct saved artifact may each need acceptance evidence. A fixed delay after click is not a general proof that every consumer has finished with the URL.

The site's Playwright download lifecycle article explains waiting for and preserving test downloads. It helps verify an artifact, but does not define every page-level URL consumer. Open the saved file and check scope, encoding, and version; separately inspect replacement and departure cleanup.

Proposed browser checks cover repeated replacements, saving after load, invalid images, rapid changes, repeated dispose, and rejected set after disposal. Memory claims require observations in the target browser; counting addresses cannot establish a number of bytes saved.

Do not store a Blob URL string as a permanent download link. It refers to a temporary object in the browser environment, not durable storage that a later session can rely on. Persistent access needs an artifact with its own authorization, retention, and deletion policy. Revocation releases a reference; it does not promise an immediate, fixed drop in a browser memory display.

No browser or memory test was run. Identify the consumers of each address and tie release to their actual end of use; a working preview verifies only one stage.
