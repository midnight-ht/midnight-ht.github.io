Why does OR IS NULL fail to restore a LEFT JOIN customer?

Use four customer groups to distinguish matching, filtering, null extension, detail counts, and absence queries.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-27 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • No qualifying match differs from no rows after filtering.
  • OR IS NULL does not create a replacement null row.
  • Check identities, detail counts, and a guaranteed non-null absence marker.

Customer A has a paid order, B only an unpaid order, and C no orders. After moving the payment condition into WHERE and adding “or order ID is null,” C returns but B still disappears. B already matched an unpaid detail and never received an extra empty order row. To retain all customers alongside qualifying orders, define qualification in the match.

Specify four customer groups first

PostgreSQL 18 Table Expressions separates outer-join matching from later filtering. A left join supplies null right-side values when no right row satisfies its join condition. WHERE subsequently retains only true conditions. The keyword does not permanently protect customers from every later filter.

Add customer D with two paid orders and one unpaid order. An all-customer report listing paid details should retain all four customer identities, but can have five detail rows: one for A, empty detail rows for B and C, and two for D. Customer population and detail-row count are different units.

This complete illustrative fixture was not executed. Order IDs are non-null in these invented inputs:

WITH customers(id) AS (VALUES (1),(2),(3),(4)),
orders(id, customer_id, status) AS (
  VALUES (11,1,'paid'),(21,2,'unpaid'),
         (41,4,'paid'),(42,4,'paid'),(43,4,'unpaid')
)
SELECT c.id, o.id AS order_id
FROM customers c
LEFT JOIN orders o
  ON o.customer_id = c.id AND o.status = 'paid'
ORDER BY c.id, o.id;

Specification-based reasoning gives customer1 order11, customers2 and3 null order columns, and customer4 orders41 and42. Status participates in ON because it defines a qualifying match. This is not a rule that every right-side condition must always appear in ON. A report deliberately requiring only customers with paid orders may correctly exclude B and C.

Why does OR IS NULL restore only some customers?

If ON matches customer identity alone, B first matches order21 and then fails the paid-status WHERE condition. C receives a null-extended row but its payment comparison is not true either. Adding a null-order-ID alternative retains C; B's ID is21, so B still fails.

Null extension happens during matching, not after WHERE has removed every detail for a customer. A left join does not return later to manufacture an empty row for B. Drawing those stages is more reliable than inferring preservation from the join's name.

Do not test an arbitrarily nullable business column for absence. An existing order can have a null note or status. Use a right-side identifier guaranteed non-null by the actual contract, or a direct existence formulation. The non-null property of this fixture's IDs must not silently become an assumption about every production column.

One row per customer is a separate requirement

D's two qualifying orders can legitimately produce two rows. A detail report may need both. A customer-level listing needs an explicit aggregation, separate detail retrieval, or existence approach. DISTINCT can discard required information—or fail to deduplicate when selected order columns differ.

Pagination must identify its object too. Paging joined details lets D consume several positions. Define whether page size counts customers or orders before implementing totals. The related COUNT input article distinguishes rows and non-null inputs; establish the correct population before asking an aggregate to count it.

Totals alone can hide an error. Losing B while duplicating D can leave the same row count. Compare customer identity sets, counts per customer, and actual order identifiers. Include both “only nonqualifying details” and “no details”; the erroneous query treats them differently.

How do you find customers with no paid orders?

This asks a different question from retaining everyone. Match paid orders in ON, then require a guaranteed non-null right-side order identifier to be null in the result. The hypothetical output is B and C. D has an unpaid order too, but also has paid matches and must be excluded. Filtering unpaid status directly can include D and miss C.

NOT EXISTS can express the absence of qualifying orders as well. Choose using clarity, constraints, and measured execution plans, not an unsupported claim that one formulation is universally faster. With a left-join absence check, review the qualification and non-null identifier guarantee together.

Tenant and authorization predicates need their own scope analysis. Restricting matching orders to a tenant does not automatically restrict the preserved customer population. Establish the authorized left-side set first. Retaining more customers is not inherently correct when the requirement or visibility boundary excludes them.

Even correct customer sets and per-customer counts can conceal a wrong attachment: an incorrect join can assign A’s order to B while each still has one detail. Compare customer–order key pairs, not just two independent identity sets. Record missing, extra, and misattached relationships; ordering the output makes comparison easier but cannot repair the relation.

A proposed check runs the fixture for both reports, then adds nullable business fields, multiple qualifying details, and mixed statuses. Preserve SQL, version, actual results, and differences from expectations; measure performance after semantics are established. No query was executed here. In a condition-moving review, require an explanation of B's fate: having details but no qualifying details is the case that exposes the matching-versus-filtering distinction.
