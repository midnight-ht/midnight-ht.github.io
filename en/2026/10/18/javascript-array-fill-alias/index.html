Why Array.fill makes several rows share one editable object

Repeated object references are shared state; construct independent editable rows and verify nested data and saved identities.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-18 · Estimated read 8 min
Translations

Article

Three editing rows can occupy separate positions while sharing the same state. If changing the first row seems to change all three, check whether Array.fill received one object. Three array positions do not establish three independently editable objects.

Repeating a value is different from constructing it repeatedly

The MDN fill reference states that an object supplied as the fill value is referenced by every filled slot. The method also mutates its receiving array. The following unexecuted illustration contrasts creating an object once before filling with creating an object on each mapping callback invocation.

const sharedRows = Array(3).fill({ checked: false });
const separateRows = Array.from({ length: 3 }, () => ({ checked: false }));
sharedRows[0].checked = true;

The first statement evaluates one object before passing it to fill. The last statement changes a property on that object, which other positions also reference. There need not be three mysterious writes or a duplicated event handler. Drawing the reference relationships can narrow the investigation. Whether framework or event problems coexist still requires actual runtime evidence.

Replacing an array slot with a new object is another operation. It differs from mutating the object already referenced by that slot. During diagnosis, inspect whether the assignment targets the array position or an internal property. A report saying only “the first item changed” hides that distinction.

Independent outer objects can still share their contents

The Array.from parameter reference describes invoking a mapping callback for each element. Creating an outer object there expresses per-row ownership. But putting one previously created tag list into every new object still shares that list. Cover the levels that editing actually mutates; comparing only the outer objects is insufficient. Conversely, a draft containing only a boolean field does not need an elaborate cloning system that obscures its state.

Sharing can be intentional. Several rows might reference one read-only configuration, in which case document that relationship and who may modify it. The absence of automatic copying does not make object values universally inappropriate for fill. The mismatch is expecting independent editable state while distributing one mutable object.

Check the rows that should remain unchanged

A proposed test should edit the first row, verify its intended change and confirm that corresponding fields in other rows retain their original values. Add nested-list changes where applicable. Checking only that the first row changed misses collateral edits; checking array length says nothing about ownership. No JavaScript or browser tests were executed for this article.

Expected values need independence too. If an expectation references the same object being edited, actual and expected values can change together and weaken the test. The October 13 article on parametrized input aliases examines the related ownership problem in another language.

A repair should explain what initialization creates, which members remain intentionally shared and which mutations were checked. Change the draft-row construction when that is the affected scope rather than indiscriminately copying every value. For saved edits, also compare submitted values by stable business identity. A correct change at position zero does not prove it belongs to the correct record after sorting or deletion. These remain proposed checks. Row numbers and variable names cannot substitute for an explainable object boundary.
