Array.fill shares references: initialize editable rows and matrices

Construct editable rows and matrix cells deliberately, then verify nested ownership, sparse mapping, undo, and saved identities.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-25 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • Separate positions do not establish independent mutable objects.
  • Factories must cover the nested state actually edited.
  • Check row isolation, undo versions, and save identity separately.

Array(3).fill({ checked: false }) creates three array positions but puts the same object into all of them. Changing checked through the first position is visible through the other two. Independently editable rows need their mutable state constructed per row, followed by a check that nested lists or matrix rows do not remain shared.

fill reuses an already evaluated value

The ECMAScript fill algorithm writes the same value into the selected indices and returns the receiving array. It does not repeatedly construct object copies. The object literal is evaluated once before fill is called; extra positions do not repeat that evaluation. This article assumes ordinary writable arrays. Its examples were not executed and are not observations from a broken page.

const shared = Array(3).fill({ checked: false });
const separate = Array.from({ length: 3 }, (_, index) => ({
  id: `draft-${index}`, checked: false, tags: []
}));
shared[0].checked = true;
separate[0].tags.push('urgent');

Reasoning from the code, all shared positions read checked as true. Each separate callback creates a fresh outer object and tags list, so adding a tag to the first row should leave the other rows unchanged. The draft identifiers are illustrative. Persistent identity needs its own policy; an array index is not automatically a stored record's identity.

Distinguish changing a property from replacing a position. shared[0].checked = true mutates an object reached through multiple positions. shared[0] = { checked: true } redirects only position zero to another object; the remaining positions still reference the original. Both can be reported as “changing the first item,” but their effects follow different reference relationships. Record the assignment target before blaming duplicate event handling.

An outer factory does not eliminate nested sharing

The Array.from algorithm invokes a mapper to produce each result. Creating outer objects inside it separates outer identities. Putting one previously created tags array into every object still shares the tags. Follow actual editing operations when deciding the repair boundary instead of stopping when two outer objects compare unequal.

Suppose three import-preview drafts support independent checkboxes and issue tags. Separate checked properties can make checkbox tests pass while a template-owned tags array still causes edits to spread. A test checking only selection says nothing about tag ownership. List the supported mutations first—boolean assignment, nested-field changes, list insertion—and assign ownership for each.

A matrix amplifies the issue. Array(2).fill(Array(3).fill(0)) constructs the inner array once and shares it between two rows. Changing the second cell in row one is visible in row two. Although the innermost values are numbers, the outer fill receives an array object. Construct each row inside an outer callback. If cells are themselves editable objects, construct each cell independently too.

const matrix = Array.from({ length: 2 }, () =>
  Array.from({ length: 3 }, () => ({ value: 0 }))
);
matrix[0][1].value = 9;

This expresses a hypothetical need for independent mutable state at both levels, not an optimal representation for every matrix. Numeric cells can be initialized with numeric fill values without wrapping every number in an object. If cells intentionally share immutable rules, separate those rules from editable values and document the sharing instead of indiscriminately cloning everything.

Match copying to the editing boundary

Spreading shared into a new array copies outer positions without severing their references to one object. Shallow-spreading a template into fresh row objects separates the outer objects but can retain shared nested lists. Deeper copying should follow which members need independent mutation, which identities must remain shared, and which data types exist—not a belief that more copying is always safer.

Serialization round trips used as a generic deep-copy technique can alter data unsupported by that representation. For a known draft model, an explicit factory can be easier to review than a hard-to-explain cloning operation. Complex data may justify another copy mechanism, but specify its treatment of types, cycles, and identity. No general copying library or performance improvement was verified here.

Proposed acceptance edits only the first row, then checks its new state and the unchanged state of the others. For a matrix, inspect other cells in the same row and corresponding cells in other rows. For nested lists, check insertion and deletion isolation. Expected data must not reference the object being mutated, or expected and actual can change together. Array length and unequal outer references establish only limited properties; they do not replace behavioral checks.

Why does an Array(n).map factory create no drafts?

Array(n) establishes length without creating an own indexed property at each position. map skips absent positions, so Array(n).map(() => ({...})) is not a reliable per-item constructor. Array.from with an array-like length and mapper expresses the intent directly; explicitly filling before mapping is another possible arrangement. Ensure the callback covers each position that needs construction instead of inspecting length alone.

This differs from shared references: one case may construct no elements, while the other populates several positions with one object. Check each expected index's existence first, then outer and nested independence. That separates missing drafts from shared drafts. The related article on flat and sparse positions explains how transformations treat absent positions. Reading undefined is not evidence that an element was constructed.

Undo exposes another sharing boundary. Suppose a page shallow-copies the draft array as its initial snapshot, then changes a row object. If the snapshot references that object too, undo retrieves mutated data rather than the initial state. Independent rows do not establish independence between current and historical versions. Row isolation and temporal-version isolation are separate decisions.

If undo is required, its snapshot strategy must cover mutable members, or updates must use a representation that explicitly preserves historical values. Check that the current value and undo target do not change together. Expected state should come from independently recorded literal data rather than the shared snapshot. Without undo requirements, do not introduce a version system for a hypothetical feature; the counterexample explains why independence must be defined around actual operations.

If edits are saved, sort or delete a row and then compare submitted values by stable record identity. Separate objects do not automatically establish correct save ownership. Object identity, display position, and business identity have separate roles. No JavaScript, UI edit, or save flow was executed here. A repair should describe the levels it constructs, any deliberate sharing, and the acceptance expectation that target edits leave other rows unchanged.
