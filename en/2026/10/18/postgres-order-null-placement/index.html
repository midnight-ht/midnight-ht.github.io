Why Descending Time Order Puts Missing Timestamps First

Specify PostgreSQL descending null placement, per-column direction, and ties with four rows separating order, eligibility, and cross-page guarantees.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-28 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • DESC defaults to nulls first unless placement is explicit.
  • Each column has independent direction; final DESC does not apply backward.
  • Null placement establishes neither eligibility nor cross-page stability.

Ordering recently completed jobs by completed_at DESC can put rows with no completion time first. PostgreSQL defaults to NULLS FIRST for descending order. NULLS LAST changes placement; a completed-only list still needs an independent eligibility filter. Direction, null placement, and business state need separate decisions.

Descending order also chooses a null default

The PostgreSQL 18 sorting reference treats nulls as larger than non-null values for default ordering. DESC defaults to nulls first; the other default direction puts them last. NULLS FIRST and NULLS LAST specify placement. No SQL or performance measurement was executed here.

Imagine four jobs: two with different completion times, one with no time, and another tied with the latest job. This input distinguishes direction, null placement, and ties. The rows and fields below are hypothetical.

WITH jobs(id, completed_at) AS (
  VALUES
    (1, TIMESTAMP '2026-10-01 09:00:00'),
    (2, TIMESTAMP '2026-10-02 09:00:00'),
    (3, NULL::timestamp),
    (4, TIMESTAMP '2026-10-02 09:00:00')
)
SELECT id, completed_at
FROM jobs
ORDER BY completed_at DESC NULLS LAST, id DESC;

The unexecuted expectation is identifiers four, two, one, three. Latest times come first, tied times use descending identifiers, and the missing time comes last. Removing NULLS LAST moves three before the dated rows. Removing the identifier rule leaves four versus two unspecified by this query. Assert exact identifiers rather than judging a screenshot for approximately descending dates.

The identifier is unique in this example. A real join can duplicate it, and a business sequence number may be nonunique. Choose a key distinguishing actual result rows. Its numerical order is a tie-breaker here, not evidence of completion chronology.

Placement does not remove a row

A strictly completed-only list can still be wrong with the null row last. NULLS LAST filters nothing. If completion time defines eligibility under the business contract, apply the appropriate filter. If a separate state model exists, use that actual model rather than silently equating missing time with unfinished work.

A complete task overview may retain nulls with accurate explanations. A work queue may intentionally prioritize unfinished jobs. A completion history may exclude them. Different headings should not conceal one shared query with an undefined population.

A missing time can also mean absent historical data or a task without that stage. Calling every such row “Waiting” infers state from missing storage. Establish its source and preserve unknown information where appropriate. Sorting cannot reconstruct missing domain meaning.

How do multiple directions apply?

Each expression has independent direction and null options. ORDER BY completed_at, id DESC means ascending completion time and descending identifier; the final DESC does not apply backward across the comma. Expand this explicitly during review.

NULLS LAST on one expression is not a universal policy for later expressions. A nullable second column needs its own placement decision when the first ties. The example uses a non-null unique identifier to reduce branches. Verify actual constraints rather than inferring them from the name id.

A list sorted first by priority and then descending completion time is latest only within a priority group. It is not a globally latest list. Compare an old high-priority record with a newer low-priority record to check that the heading and ordering priority agree.

What if every time is identical or missing?

The first expression then distinguishes nothing, so later keys decide. A suitable unique key can provide an explainable display order. It cannot recover missing business chronology. Repeatedly seeing the same arrangement is not evidence that historical sequence has been restored.

Pagination adds another contract. Inserts, deletions, and changed completion times can affect later pages even when each current result has a unique order. The site's pagination and cross-page consistency article addresses that boundary. This article provides no production cursor predicate and does not present NULLS LAST as a complete pagination repair.

Index suitability and performance also require actual evidence. An explicit order states the result requirement, not whether a particular dataset uses an adequate plan. Preserve conditions, row counts, and plans when comparing alternatives. Adding a keyword establishes no speedup or slowdown, and an existing index is not a reason to silently alter business null placement.

Proposed cases include differing times, ties, all-null times, mixed nulls, and opposing column directions. Check the eligible identifier set, full order, explanation of missing values, and tie-key uniqueness separately. Sorting an incorrect population consistently is not acceptance.

The same four rows yield two explicit expectations. An overview accepts one through four in order four, two, one, three. A history using non-null completion time as this example’s eligibility rule accepts one, two, four in order four, two, one. Checking only the first row permits both queries to pass and misses eligibility; checking only a count of three can miss retaining three while dropping one. Assert both population and full sequence, including reasons for exclusion. If actual state and timestamp disagree, add that counterexample and obtain the real business rule rather than extending this simplified assumption to production.

This historical rewrite adds complete inputs and counterexamples without claiming database execution. A list change should explain which rows enter, which columns take precedence, each direction and null policy, and how remaining ties are resolved. Align those decisions with the query and labels so “recent,” “waiting,” and “unknown” do not become interchangeable meanings of NULL.
