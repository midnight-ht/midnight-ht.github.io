Why does descending time order put missing timestamps first?

Specify null placement, individual column directions and tie handling in PostgreSQL lists, after defining what missing values mean.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-18 · Estimated read 8 min
Translations
zh-CN en

Article

Changing a list to descending completion time can put records with no completion time first. PostgreSQL may be following its default ordering correctly. If the interface means “most recently completed”, specify the direction for known values and the placement of nulls. Changing one keyword leaves part of that decision implicit.

Descending order has a null-placement default

The PostgreSQL 18 sorting documentation treats nulls as larger than non-null values for default ordering. They come last in ascending order and first in descending order. NULLS FIRST and NULLS LAST make the placement explicit. These are version 18 query semantics, not performance findings from an actual database.

Imagine an administration list with two completed jobs and one waiting job whose completed_at is null. Descending completion time places that waiting row before the dated rows by default. This hypothetical input is not a reported production incident. It may suit a queue that prioritizes unfinished work. A section called “Recently completed” needs a different discussion of eligibility as well as order.

This candidate query uses illustrative table and column names and was not executed:

SELECT id, completed_at
FROM jobs
ORDER BY completed_at DESC NULLS LAST, id DESC;

It orders known completion times from latest to earliest, places null times afterwards, and uses the identifier for tied timestamps. It does not remove null rows. If the section should contain completed jobs only, the input set needs an appropriate business filter. Moving missing times to the bottom does not establish that every listed job has finished.

Each ordering expression has its own options

The documentation also explains that direction is determined independently for each expression. In ORDER BY completed_at, id DESC, completion time still defaults to ascending. The final DESC does not apply backwards to all earlier expressions. Read null placement beside its own expression as well. Explicit directions and null rules make a shared query easier to review without reconstructing defaults.

An identifier is not a universal tie-breaker either. To help establish a deterministic order, it must distinguish rows still tied in the current result set. A join might repeat an identifier, and a business sequence number might not be unique. Choose a suitable key for the actual rows. This recommendation makes ordering explainable; it does not guarantee that every pagination scheme will avoid omissions or duplicates.

Establish what a null means

A missing completion time could mean unfinished work, missing historical data, or a task type without that stage. Putting all three first and labelling them “Waiting” would infer business state from missing storage data. Determine which conditions produce nulls. A separate state field may be appropriate; sorting should not carry the entire state model.

The site’s discussion of COUNT and non-null inputs raises a related question about which rows an operation includes. Correct counts do not validate the entire list rule. A query can count the wrong population accurately and place it in a consistent order.

Proposed validation inputs include different timestamps, tied timestamps, all-null rows, and mixed rows. Pagination also needs observations of changes between page requests. None of those tests was performed here. Index suitability and query plans require actual data; a semantically correct statement does not establish adequate performance.

Before editing the query, write the requirement as a sentence: which records belong, which field orders them, where missing values go, and how remaining ties are distinguished. Each decision should be visible in the query before the interface’s “latest” label has a definite meaning.
