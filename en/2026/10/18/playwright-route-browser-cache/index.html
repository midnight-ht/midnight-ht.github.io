Passing requests through route.continue does not preserve the cache environment

Playwright routing disables HTTP caching, so browser-cache acceptance needs its own controlled environment and evidence.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-18 · Estimated read 8 min
Translations
zh-CN en

Article

Letting a request reach the server through route.continue does not establish that browser caching remains unchanged. A pass-through route installed by a shared fixture can alter the conditions of an HTTP-cache test. Inspect the test environment before explaining network activity on a second visit.

Observing requests can change the conditions

The Playwright page.route reference states that enabling routing disables HTTP caching. That statement is not conditioned on whether a handler changes the response. “We do not mock anything; we only continue requests” is therefore insufficient evidence that the original cache environment remains intact. This article uses the online reference checked for this run; projects should record their own Playwright and browser versions.

Imagine a common fixture registering a route to record URLs and continue every request. A test visits the same resource twice and interprets its request count as evidence of cache failure. That inference omits a premise changed by the test itself: routing was enabled. This hypothetical scenario was not executed. It establishes neither incorrect server cache headers nor a guarantee that removing the route will make the resource reusable.

I would name the test for what it checks. A test relying on injected responses should accept page behavior under those conditions. A browser-cache test should have a dedicated path without network routing. Both can cover the same business page, but their evidence answers different questions. Maintaining separate paths costs effort while preventing one green result from carrying an untested promise.

Identify the cache layer being accepted

Checking server cache fields differs from checking browser response reuse. The former focuses on protocol output; the latter also needs first and subsequent visits, context state and resource identity. Do not reduce every observation to a request count. State which behavior satisfies the requirement and how the supporting evidence was collected. This article does not supply a universal cache-hit criterion for every browser.

Record Service Worker conditions separately. The same official reference says page.route does not intercept requests already intercepted by a Service Worker and recommends blocking Service Workers when request interception is needed. However, copying that configuration into acceptance of an application’s offline behavior changes the target. First decide whether the test concerns browser HTTP caching, site offline behavior or another cache layer, then choose the setup.

Failure evidence should reconstruct the premises

Proposed records include dependency and browser versions, shared fixture contents, page or context routing, Service Worker policy and observations for each visit. Inspecting common configuration before a run can address this question more directly than repeatedly extending timeouts afterward. A fresh controlled context helps explain the starting state, but a warm-cache scenario still needs explicit steps establishing its intended history.

No Playwright process, network capture or cache configuration was tested here. Removing routing is not promised to solve all repeated requests. Client-side application data is also distinct from HTTP caching; investigate its own layer when relevant rather than extending one routing note into a diagnosis of everything.

The October 17 article on download events and saved files raises a related acceptance issue: observing an event does not establish the desired state. A cache review should map its environment to its evidence and identify when common routing is installed. That is more reviewable than a bare claim that caching was tested.
