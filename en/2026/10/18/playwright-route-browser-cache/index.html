Pass-Through Playwright Routes Still Change HTTP Cache Tests

Pass-through routing still disables HTTP cache. Design unrouted cold and warm image visits, distinguish Service Workers and status evidence, and bound unroute claims.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-27 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • Enabling routing disables HTTP cache even when handlers continue requests.
  • Warm visits require deliberate history within an explicitly unrouted session.
  • Worker policy, status codes, and unroute alone do not prove reuse.

Suppose a shared fixture installs page.route("**/*", route => route.continue()) on every page, and a cache test then visits the same product image twice. Even though the handler does not alter the response, enabling routing has disabled HTTP caching. Network activity on the second visit cannot immediately be blamed on the server. Inspect shared test conditions before changing cache headers or waiting longer.

Pass-through preserves destination, not every condition

The Playwright page.route reference states that enabling routing disables HTTP cache. This is not limited to handlers using fulfill or abort. Calling continue allows a request to proceed; it does not cancel the environment change introduced by routing.

The online reference was checked on October 27, 2026. No Playwright process or cache capture was run. Record the project's pinned Playwright and browser versions, then inspect page routes, context routes, and shared fixtures. The absence of route calls in one test file does not establish their absence from common setup. Include HAR replay and response replacement in the inventory.

Two tests can both be useful. Routed timeouts or error responses can exercise a product page's messages and retry behavior. Browser response reuse on a second visit requires conditions appropriate to caching. Both may cover the same page, but passing the former does not validate the latter. The problem is a test promise exceeding its evidence.

Establish cold and warm visits to one image

Imagine a product page referencing /assets/item-42.webp, with a server policy permitting reuse for an interval. The requirement concerns an initial visit followed by ordinary navigation back to the same resource in one controlled session. The resource, policy, and steps are hypothetical; no browser result is claimed.

Create a dedicated context that has never installed page or context network routes. Exclude offline replay, response replacement, and shared interception fixtures from this path. A fresh context explains the starting point but is not already warm. First visit the page and complete the resource observation, then perform the agreed action to use it again. Creating another context before every visit changes the session instead of testing warm reuse within one session.

For the initial visit, record the complete resource URL, request conditions, response cache fields, and corresponding server observations. On the second visit, retain resource identity and record the actual user operation. If the application changes a query parameter or generates another URL, it has changed resource identity before the assertion. Similarly, specify the kind of reload if reloading is the chosen action; operations with different cache behavior cannot be merged into one unexplained count.

This is an unexecuted experimental outline, not a universal browser cache-hit assertion.

create dedicated context with no network routes
record browser version and Service Worker policy
visit product page; identify exact image response
perform the chosen normal navigation
visit again in the same context
compare resource identity, response information, and server observations
close context after collecting evidence

Assertions must follow the actual requirement. A reuse requirement within a freshness interval needs observations distinguishing full transfers, conditional validation, and client-side reuse. Server request counts provide clues but can be affected by proxies, preloading, and other traffic. A page request event or identical response status codes alone do not establish transferred content. Explain which reliable measurements the actual browser and tools provide.

Keep HTTP cache, Service Workers, and application data distinct

The same reference says page.route does not intercept requests already intercepted by a Service Worker and recommends blocking Service Workers when interception is needed. That recommendation serves interception tests, not every cache requirement. Blocking a worker for an offline feature removes part of the intended product behavior.

Define separate targets if necessary. One path can test browser HTTP caching without a Service Worker; another can test offline or update behavior with the application's actual worker. Keep the blocking condition visible in the former. The latter needs appropriate evidence of installation, activation, control, and resource version. Neither automatically validates a CDN cache or client-side business-data cache.

A counterexample fulfills a routed response with cache headers, sees the image render, and declares production browser caching correct. It demonstrates acceptance of constructed content without restoring the caching premise routing changed. Another checks headers with a Node HTTP client. That establishes fields received by that request, not browser storage and later reuse.

Does unroute prove that caching conditions were restored?

Not by itself. The checked reference documents disabling HTTP cache when routing is enabled. It does not promise that removing a handler makes all state identical to a context that was never routed. Do not build core acceptance on that unsupported inverse. Starting a fresh, never-routed context and deliberately establishing first and later visits is easier to explain.

The extra path costs maintenance but improves attribution. If a complex existing fixture must be reused, verify its caching conditions separately and preserve version-specific comparisons. Renaming a routed behavior test does not make it cache acceptance. Removing routing also does not guarantee a hit: server policy, resource identity, and browser decisions still require investigation.

Retain why reuse should be permitted. If the initial response forbids storage, test that restriction rather than labeling non-reuse a browser defect. If an updated image must become visible promptly, define resource versioning and invalidation separately. Indefinite reuse of one identity and unconditional immediate updates are not one coherent requirement. Keep freshness, update actions, and the user-visible version together in acceptance conditions to distinguish HTTP behavior from application state.

A failure record should retain exact resource identity, both actions, routing and worker conditions, effective response policy, and correlated client/server observations. The site's BrowserContext session-isolation article explains context scope. The additional requirement here is to establish history after choosing the isolated starting point. First and second observations belong on one explicit path if the test is to distinguish observing caching from changing its environment.
