Nested configuration after Object.freeze: establish snapshot ownership first

Separate copying, freezing, aliases and accessors through live configuration and historical snapshot ownership.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-26 · Estimated read 11 min
Translations
zh-CN en

Article

Key takeaways

  • Shallow freezing neither copies references nor recursively freezes their targets.
  • Separate snapshot ownership before restricting owned data.
  • Include aliases and accessor dependencies in verification.

An outer freeze restricts that object's own properties; it does not recursively freeze every referenced value. Ownership is the easily missed part. If an audit snapshot shares a child object with live configuration, freezing the wrapper neither copies that child nor prevents another owner from changing it.

Fixing a reference does not fix its target

The ECMAScript Object.freeze algorithm calls SetIntegrityLevel, which restricts the passed object's own properties and prevents extension. It does not recursively freeze property values. This article uses the retrieved ECMAScript 2027 living draft and limits examples to ordinary objects and arrays.

Suppose an audit record must retain an upload limit as submitted, while operations may update the current limit. This unexecuted teaching example does not create that snapshot:

const live = { upload: { maxFiles: 3 } };
const audit = Object.freeze({ ...live });
live.upload.maxFiles = 8;

The wrappers differ, but upload still points to one shared target. Replacing audit.upload and changing the target's maxFiles use different property descriptors. The frozen audit wrapper protects the former, not the latter. A test asserting only that the wrapper is frozen would certify the wrong requirement.

Object spread is fulfilling its shallow-copy contract. Substituting another shallow copy preserves the same aliasing problem. Define what the snapshot owns before selecting a copying or freezing operation.

Copy the ownership boundary, then freeze owned data

For a known configuration shape containing this numeric limit, construct an independent child and freeze the relevant objects. This remains an unexecuted, shape-specific example rather than a general deep-freeze utility.

Construct a new child containing the observed primitive limit, freeze that child, place it in a new audit wrapper and freeze the wrapper. Both objects belong to this construction; live configuration retains its separate mutable state.

The primitive value is read into a separate child, so later updates do not reach the snapshot through that alias. If the schema later adds a mutable list, construction and verification must change. Today's numeric field cannot justify a promise covering arbitrary future object graphs.

Recursively freezing live.upload instead could break the owner's legitimate hot updates. Copying separates identity; freezing restricts mutation. Combine them according to the contract. Deliberately shared read-only rules can remain shared when every owner agrees to the restriction.

Recursion needs a defined domain

Cycles and repeated references require visitation handling and ownership decisions. Functions, host objects and containers with internal state should not be accepted as plain configuration merely because their type is object. No universal traversal algorithm is supplied here.

Traversal choices matter too. Object.keys omits symbols and non-enumerable properties, while reading every value can invoke getters. A pure-data snapshot boundary can restrict shape, reject accessors and construct controlled records. That makes the accepted domain reviewable rather than declaring every runtime object safe.

A frozen array restricts its own indices and length but does not automatically freeze objects stored in it. The site's Array.fill discussion shows how several positions can share one object; snapshot tests should similarly look for aliases into other positions and historical versions.

Why can a frozen accessor still return changing values?

A frozen accessor retains its descriptor, not every external dependency used by its getter. If the getter reads a mutable variable, later reads can change. A setter also does not become uncallable merely because the wrapper is frozen. “Frozen” therefore cannot generally mean that every read forever returns the same value.

An audit observation should capture an ordinary data value at its boundary rather than retain a getter that continues computing later. Dynamic configuration and fixed evidence are both legitimate, but callers need to know which contract they receive.

Some prohibited assignments throw in strict mode, while other failure behavior depends on language context. Verify the resulting value as well as any exception. No exception does not prove mutation succeeded, and an exception at one path does not prove another alias could not change a child.

Inspect the graph, not only one boolean

A proposed matrix covers outer replacement, nested mutation, external aliases, array elements, cycles and changing accessor dependencies. Object.isFrozen can check one object's integrity level; it cannot establish ownership or stable reads across the graph. For an audit snapshot, update live configuration and then compare the old snapshot with an independently written submitted value.

No examples, audit writes or production configuration were executed. A useful review identifies which objects were frozen, which references remain shared and which reads depend on external state. Those answers determine whether the value can serve as a fixed snapshot.
