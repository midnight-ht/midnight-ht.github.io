Delta is not more fragile than Cumulative: decide where conversion state lives

Delta covers adjacent intervals; Cumulative covers a shared start through now. Choose by where state, gaps, and restart handling belong.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-25 · Estimated read 22 min
Translations
zh-CN en

Article

Key takeaways

  • Delta covers adjacent time windows; Cumulative covers a shared start through now, so overlapping cumulative points must not be added.
  • Delta shifts aggregation state downstream while Cumulative retains prior sender measurements; choose based on state ownership and recovery.
  • Starts, gaps, duplicate windows, and logical writer identity affect meaning and belong in acceptance tests.

Neither representation is inherently more fragile: Delta and Cumulative describe different time windows and place the cost of retaining state in different parts of a pipeline. Preserve metric identity, timestamps, and restart semantics before choosing whether the SDK, Collector, or backend performs a conversion. Once those details are discarded, adding values can double-count work even when the resulting graph looks smooth.

A sequence that double-counts

Imagine a service handles 8 requests during one 10-second interval and 11 during the next. Delta points describe two non-overlapping windows, so the values are 8 and 11 and the two-window total is 19. If Cumulative points share a start time, they describe “from the start through second 10” as 8 and “from the same start through second 20” as 19. Adding those cumulative points gives 27 because the first 8 requests appear in both windows.

The sequence is hypothetical arithmetic, not production data collected by this site. The problem is not which English label was attached to a number; it is whether the time windows overlap. A receiver that gets only a metric name, value, and unit cannot tell whether 19 means 11 new requests or the total since startup. A chart with only values and timestamps may not make the mistake obvious.

Check the point kind too. OTLP Sums and Histograms support Delta or Cumulative temporality; a Sum also has a monotonicity property. A Gauge represents a value sampled at a point in time. For temporal alignment, the model uses the last sample in the window, and Gauge does not have default additive aggregation semantics. Adding a Gauge such as temperature or current queue length as though it were an interval increment is wrong regardless of the temporality choice. A Histogram is a compressed representation of a population of observations. Before merging it across time or instances, check that the attributes and aggregation structure are compatible; two quantile values cannot simply be added. Temporality answers which time range an additive quantity covers. It does not prove that two metric streams are otherwise compatible.

The OpenTelemetry Metrics Data Model defines TimeUnixNano as the time a measurement took effect and the optional StartTimeUnixNano as information about the start and continuity of a series. A Delta point advances its start time from one interval to the next. A continuous Cumulative sequence repeats a shared start time while extending its covered range. Those timestamps are part of what the value means; a Collector or backend should not treat them as disposable metadata during conversion or aggregation. The current documentation navigation labels the specification version 1.63.0. The Temporality section is Stable, while Resets and Gaps is still marked Development, so this article keeps that distinction explicit.

The choice is where state lives

A Cumulative sender must remember earlier measurements and continue reporting a value from a shared start. The OpenTelemetry model notes that, for monotonic cumulative sums, intermittent collection failures can be naturally averaged across the gap by comparing cumulative measurements before and after it. The cost is state at the sender, proportional to series cardinality. For a service with many instances and high-cardinality attributes, that retained state can matter.

A Delta sender reports only the change in a new time window and does not need to maintain a cumulative value from the beginning. State can move downstream. A converter may also avoid reconstructing a cumulative series and calculate interval rates directly. That moves state and reaggregation cost to a receiver, or requires the query side to interpret each interval correctly. One documented OpenTelemetry use case is a stateless client exporting Delta while a stateful server-side Collector reaggregates longer intervals or converts to Cumulative. That pattern is a design option, not a claim that every SDK or backend uses it automatically.

So start by asking who should own the state, rather than which temporality is “better.” Client churn, process memory limits, Collector persistence, acceptable export loss, backend support for intervals, and the possibility of replayed data all affect the answer. Wherever state lives, document when it is established, how it is recovered after restart, what signal is emitted if it is lost, and how duplicate data is recognized.

For example, if short-lived jobs are created continuously and carry high-cardinality attributes, keeping full cumulative state in every client may distribute memory cost across many processes. Emitting Delta can move aggregation state to a central Collector. But if that Collector restarts and loses which windows it has already seen, a replayed point may be accumulated twice. A long-running service with stable series may find Cumulative state easier to maintain, while still needing to record resets and prevent replicas from competing for one identity. This comparison only describes where costs land. It does not establish which option uses less memory or is more reliable in a particular deployment; those claims need validation with the actual SDK, Collector, attribute volume, and delivery path.

Restarts, gaps, and multiple writers are different failures

A cumulative value falling from 500 to 12 is not automatically negative 488 requests. It may be a process that restarted and began a new sequence, or two writers alternating on the same series identity. Start and point timestamps can help a consumer identify a new sequence or some gaps, but OpenTelemetry marks the Resets and Gaps section as Development. Do not assume that every backend interprets unknown starts, a lost first point, out-of-order samples, or overlapping writers the same way merely because the data uses OTLP.

The first cumulative point after a restart has another boundary. When StartTimeUnixNano equals TimeUnixNano, the model uses that point to represent a new sequence with an unknown start. It has zero duration, so it should not be treated as an ordinary interval increment. If this first point is lost, a later point may look like a true reset from a known start, which can overcount the rate contribution. This start-time behavior is still in the Development section of the specification; test the specific “first point of a new sequence is lost” case against the backend you use.

Short windows do not make Delta immune to missing points. Suppose the 10-to-20-second point arrives, export of the 20-to-30-second point fails, and the 30-to-40-second point then arrives. A receiver that adds adjacent values without checking window boundaries can hide the missing ten seconds inside a plausible-looking total. It should not silently fill the gap with zero. Whether a system fills, interpolates, or marks the interval unknown is a storage and query policy that must be explicit.

Multiple writers create another class of ambiguity. If two instances accidentally use the same Resource and attribute identity, they can write to one series at the same time. Interleaved cumulative points may look like resets; Delta windows may overlap or be duplicated. OpenTelemetry's Single-Writer section requires one logical writer and treats multiple writers as an error state. A converter should therefore preserve Resource, Scope, and attributes rather than merge by metric name alone. Spatial aggregation that removes a dimension such as service.instance.id must also ensure that only one logical destination writes the aggregate.

Put the time semantics in the ingestion contract

An ingestion ticket needs more than the phrase “this is a counter.” Record the following:

Field What to specify
Data type and unit Sum, Histogram, or another type; whether units match. Streams with different units cannot be added directly.
Temporality Delta or Cumulative, and whether points cover adjacent intervals or a shared start through the current time.
Series identity Resource, Scope, metric name, and attributes; which dimensions may be removed and how removal avoids writer collisions.
Timestamps and start Who sets the start and end, how a restart or new sequence is represented, and how the receiver detects a gap.
Conversion state Whether the SDK, Collector, or backend converts; the state key; and what state loss on processor restart means.
Delivery semantics How retries, repeated exports, out-of-order points, and partial loss are detected or marked; what happens when the receiver cannot decide.

Treat these fields as an engineering checklist derived from the data model and its state tradeoffs, not as a prescribed OpenTelemetry form. Conversion is not just arithmetic: Delta-to-Cumulative must accumulate non-overlapping windows for the same series; Cumulative-to-Delta needs a prior comparable point and must handle resets and gaps. OpenTelemetry permits temporality conversion under applicable conditions, but it does not choose each team's state store, delivery recovery, or alert policy.

For Delta, a receiver can use “series identity plus start and end time” as one defensive way to detect a repeated window or an interval gap. Treat that as a design suggestion, not a mandated deduplication key. If a retry delivers the same window twice, blindly adding it counts the work twice. If a later window arrives first, the receiver should at least distinguish out-of-order delivery from a real empty interval, or mark the state as unresolved. For Cumulative, the receiver needs to track whether the shared start has changed, whether one logical writer is advancing the values, and whether the first point after a restart conveys a known change. Both models depend on reliable series identity. Deduplicating only by metric name can collapse different instances into one stream or split a single instance's history.

Acceptance tests can use controlled input for consecutive windows, a missing point, duplicate delivery, a cumulative restart, a converter restart, and two overlapping writers. Record the input windows, expected output, and expected warning or missing-data marker for each case. These are proposed tests; no Collector or SDK experiment was run for this article, and no reliability, latency, or memory result was measured. The acceptance question is whether the value can still be interpreted after a failure, not merely whether an export API returned success.

Transport temporality does not decide how the query layer should aggregate. For cumulative counters, interpreting change on each source series before aggregating across series usually preserves meaning better than summing overlapping cumulative values directly. See why to calculate counter rates before aggregation. Choose Delta or Cumulative based on state placement, delivery paths, and failure recovery, then write that decision into the ingestion contract.
