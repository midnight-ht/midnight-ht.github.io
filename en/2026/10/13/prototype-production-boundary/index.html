Should prototype code be rewritten? Start with its real side effects

Use a hypothetical refund flow to separate prototype evidence from production proof: verify identity, durable state, duplicate requests, recovery, and ownership before deciding what to reuse.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-25 · Estimated read 22 min
Translations
zh-CN en

Article

Key takeaways

  • A clickable path can validate a research question; real data, authority, side effects, and recovery each need separate evidence.
  • Reuse should be decided by component and responsibility, not by approving or discarding an entire prototype as one unit.
  • A timed-out refund request can have an unknown result; HTTP semantics do not deduplicate business operations for you.

A prototype that can be clicked through is not yet evidence that it can handle real business. That does not mean every line of prototype code must be discarded. For example, a refund page displaying a confirmation only proves that the message appeared; before reusing the code, check whether it touches real identity, durable state, or a hard-to-reverse side effect. A page may have passed an interaction study while still lacking evidence for permissions, state, failures, or operations.

State exactly what the prototype proved

The GOV.UK prototype guide uses code prototypes to test realistic interactions, while explicitly saying their code need not meet production security and performance standards and should not be copied directly into production. It also says publicly shared GOV.UK prototypes should be password protected so the public does not mistake them for a live service; the GOV.UK Prototype Kit itself is not for live services. These statements concern the guide's prototypes and tool. They do not imply that every prototype component is unsafe. The practical lesson is to review research purpose separately from production responsibility.

Imagine a refund prototype that lists orders, collects a reason, and ends with “refund submitted.” Whether a participant can find the action, understand the amount, and distinguish a refund from a cancellation are questions an interaction study can address. If the order list and result are fixed data and the page never calls a real refund service, however, the flow has not proved that identity was verified, the order is eligible, financial state was written, or repeated clicks cannot create two refunds. This refund flow is a hypothetical example to explain the boundary, not user research or a system test performed by this site.

A research note can state a finding precisely: “After seeing the order, participants understood the expected arrival time” supports keeping the explanation. It does not become “the live service completes refunds within that time.” Record which buttons are demonstrations, which data is synthetic, and which pages make no real service call. If a prototype is published to the internet, review access protection, data type, and on-screen notices so participants or bystanders do not mistake it for an account-operation entry point.

Follow one hypothetical refund across the boundary

Breaking a click into server-verifiable states is safer than calling a page transition “success.” A real order flow must answer who initiated the request, whether that person owns the order, whether a refund is allowed, when the operation is recorded, what the result is if a downstream service does not reply, and who will resolve an unknown state. These are design questions, not a complete checklist prescribed by any single source.

The case prototypes hide most easily is “the request may have taken effect, but the response never reached the browser.” Suppose the client sends a refund POST; the downstream system accepts it, then the connection breaks. The page sees a timeout. If it immediately shows failure and re-enables the button, the user may submit a second refund. If it shows success, it has mistaken “no error received” for “operation completed.” RFC 9110 lists POST as non-idempotent by default and says a client should not automatically retry a non-idempotent request unless it knows the request is safe to repeat or can establish that the original was not applied. HTTP does not decide whether a business refund has been recorded.

A production design could assign a stable operation identifier to one logical action and store a digest of the request and its state on the server. A retry with the same identifier and same content would return the existing operation state; reuse of that identifier with different content would be rejected. Whether the external service supports equivalent deduplication must be checked in its own contract. If the result cannot be confirmed immediately after a lost response, keep the operation “pending verification” or “unknown” and resolve it through a query or reconciliation path instead of guessing success or failure. This is a proposed application design, not a feature guaranteed by RFC 9110 and not a claim that any particular payment service supports it.

For this hypothetical flow, expected behavior can be written as a reviewable test table:

Input or failure Expected observation Evidence boundary
User does not own the selected order Reject the request without a refund side effect Identity and object authorization
Same operation identifier and same content are submitted again Return the existing operation state without creating another operation Application-level duplicate handling
The same identifier is sent with a different refund amount Reject the conflict and preserve the original operation Binding between request identity and content
Downstream may have accepted the request, but its response is lost Show a pending verification state; provide a query or reconciliation path Do not misreport transport timeout as business failure
The operation reaches a terminal state Visible state agrees with the durable record Server state is the result authority

This is a proposed acceptance design, not a test run in a real refund environment. The team should also define visible text for every state, repeated-request behavior, record retention, and ownership. If the provider offers neither a query nor deduplication capability, specify manual reconciliation, a pause on automatic retries, or another business compensation plan. A “retry” button in the prototype does not make an uncertain outcome recover automatically.

Reuse is not approval of the whole package

Decide reuse by the responsibility a piece of code carries. Color, layout, and presentation components may survive, subject to checks for keyboard operation, mobile layout, dependencies, and real content length. Logic that reads identity, decides order eligibility, calls an external service, writes a ledger, or retries a request must be reimplemented or reviewed against production data and failure semantics. A reusable dialog does not qualify the API it calls; copying a directory does not add authorization, audit history, or recovery behavior.

A handoff ledger can have four columns: prototype assumption, research evidence, production constraint, and reuse decision. For “show success after the click,” the research evidence may show that participants understand the confirmation wording. The production constraint may require showing success only after the server confirms a terminal state. The decision could be to keep the wording and layout while replacing the local-state logic. This preserves the part that was actually validated and gives implementation and testing an explicit owner for the rest.

Choose security checks to fit the system and the data. NIST SP 800-218 Version 1.1 describes SSDF as high-level secure-development practices that can be integrated into a lifecycle, not as a project certification. Version status also matters: as of 25 November 2026, NIST's publications listing marks 1.1 as Final and Revision 1 / Version 1.2 as a Draft released on 17 December 2025. This article refers to the published 1.1 final and does not present draft content as a settled requirement. OWASP ASVS 5.0.0 provides a basis for verifying web-application technical security controls; cite the version because requirement identifiers can change. These references help define checks. Citing SSDF or running through an ASVS list alone does not prove security, regulatory compliance, or release approval.

Turn the release decision into verifiable evidence

Google SRE's description of production readiness reviews is connected to SRE taking responsibility for a service. It includes system architecture and dependencies, instrumentation and monitoring, emergency response, capacity, change management, and availability, latency, and efficiency. The review is tailored to the service; it is not a universal certification that every team must copy. A team can borrow the questions and adjust their depth to impact, data sensitivity, and its operating model. A small internal display page calls for different evidence than a service that can refund money or change identity data.

A useful release record traces each user promise to a service result: negative tests demonstrate authorization rules; duplicate, timeout, and partial-failure tests observe state transitions; key business state has a durable record and lookup; alerts distinguish accepted requests from failed processing and unknown outcomes; on-call staff know when to stop automation and where to check; deployment has a limited exposure and a tested rollback or compensation path. Google SRE's review includes performance, capacity, dependencies, and emergency response. NIST and OWASP provide references for secure development and web control verification. The owning team still defines its actual acceptance conditions.

The matrix here is a proposed work plan, not something executed against a real service, load, account, or downstream refund system. A project could first cover the table above with isolated test data, then use automated tests and a separate human exercise to show that an unauthorized user cannot act; one logical request cannot cause duplicate effects; state remains traceable after a disconnect; a downstream outage does not display false completion; and on-call staff can find the next action. For a limited release, also define how to observe user-facing outcomes, the stop threshold, decision owner, and rollback action before exposure. A page loading successfully is not enough.

Must all prototype code be discarded?

No. Keeping a presentation layer that has no real side effects, has clear boundaries, and passes dependency, accessibility, and code-quality checks may be more appropriate than rewriting it. Remove or rewrite mock identities, fixed business results, authorization bypasses, and logic that triggers real effects without production safeguards. Check module boundaries too: a safe view can still depend on prototype data or an unverified service call.

For unresolved questions, label each conclusion “research-supported,” “awaiting production evidence,” or “defer release,” and attach evidence and an owner. For when discovery evidence justifies the next step, see discovery stopping criteria. To set test and release gates by business risk, see risk-based quality gates. Going live is not changing a demo page to a production domain; it is making sure every promise to users maps to a real state, a failure path, and a team responsible for it.
