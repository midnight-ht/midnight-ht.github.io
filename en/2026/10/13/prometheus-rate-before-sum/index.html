Rate each Prometheus counter before aggregation: why reset identity matters

Calculate counter rates per original series before aggregation so an instance restart is not hidden by other replicas. The guide also covers rate extrapolation, label changes, gauges and histogram ratios.

Updated 2026-11-25 · Estimated read 23 min

Article

Key takeaways

  • Rate-before-sum preserves the chance to detect resets in each original series; an early sum can erase one instance's drop.
  • Rate is a windowed estimate with boundary extrapolation, not an exact count from request logs; a hand-worked fixture is not a Prometheus result.
  • The final by/without labels, counter-versus-gauge contract and ratio denominator still depend on the question being asked.

One instance's request counter falls from 10 to 1 while another keeps rising from 1,010 to 1,020. If you sum the raw counters first, the total may still rise and reveal none of the reset. That is why the official guidance emphasizes calculating rate() for each series before aggregating by the business dimension. The order preserves information about which series reset. It is neither a formatting preference nor a rule to apply to every metric without checking its type and meaning.

A restart hidden by a sum

Assume Prometheus observes two instances at four evenly spaced times. Instance A has values 8, 10, 1, and 3; after the second sample, its process restarts and begins counting near zero. Instance B has values 1,000, 1,010, 1,020, and 1,030 and continues increasing. Summing the values at each time gives 1,008, 1,020, 1,021, and 1,033. The aggregate series never falls. From those totals alone, the query cannot tell that one member went from 10 back to 1.

If A and B remain separate counter series, A's decrease can be recognized as a reset. In a deliberately simplified boundary calculation, A contributes increments of 2, 1, and 2 over the three intervals, for 5 in total. B adds 30. The idealized corrected total is 35. Summing the raw values first leaves an endpoint difference of only 25. The gap comes from folding series identity away before interpreting the reset.

This table is a hypothetical hand calculation to make information loss visible; it is not the output of a Prometheus query. Actual rate() uses timestamps, sample spacing, window boundaries, and missing-sample information to extrapolate. Dividing 35 by the sample interval would therefore not establish an exact per-second rate for a real range. The point is narrower: whether the aggregate retains the original decrease depends on when the series identities are merged. For a related but separate question about fractional window estimates, see the worked example of rate/increase extrapolation; it covers range boundaries rather than cross-instance reset masking.

The version 3.13 function reference and the 2.55 reference both describe rate() as calculating a per-second average increase for each input time series. It adjusts for counter resets and extrapolates toward the range boundaries to account for missed scrapes or imperfect alignment. Both documents also say to apply rate() before an aggregation; after aggregation, a target restart may no longer appear as a reset that the function can detect. Check the documentation for the version actually deployed. This comparison verifies the stated behavior in the two named references; it does not promise that every future release will remain identical.

Aggregating before and after rate changes what rate can see

A common goal is “requests per second for all API instances, grouped by job.” One expression is:

sum by (job) (
  rate(http_requests_total{job="api"}[5m])
)

rate() first sees the original series with labels such as instance and pod, handles their resets separately, and then sum by (job) combines the rates into a job-level result. The aggregation reference says that by keeps only the listed labels and drops the rest. If the business question needs region or method, include those dimensions. If the intent is to remove only instance and pod while retaining every other label, sum without (instance, pod) may be clearer. Choosing by or without determines which questions the output can still answer; it is not merely a style choice.

A comparison for “sum first, rate afterward” must use a subquery when turning an aggregation expression into a range vector. A range selector cannot simply be attached to an arbitrary expression as if it were a bare metric selector. For example:

rate(
  sum by (job) (http_requests_total{job="api"})[5m:]
)

A subquery evaluates the inner instant query repeatedly over a time range and resolution, then returns those results as a range vector. The official basics reference says that when the resolution in [5m:] is omitted, Prometheus uses the global evaluation interval. This comparison therefore adds a subquery evaluation grid; it is not a pure algebraic swap over identical scrape timestamps. Fix that resolution when comparing actual expressions. Here the outer rate() sees the job aggregate, not each instance's counter. If one instance restarts while another grows enough to keep the total monotonic, the reset is no longer visible. If the aggregate itself falls, the outer function may instead correct the whole job series as if it had one shared reset. Neither case reconstructs what each instance did.

This also explains an apparent counterexample: some windows may make “sum then rate” look harmless because no instance restarted or because the combined series still exposes a drop. That does not make the orders equivalent. They may happen to be close on a smooth history. Only per-series processing retains the evidence needed to correct each series' decrease independently. The function reference explicitly ties the ordering to reset detection.

Rate handles observed resets, not unobserved increments

A counter represents a cumulative number of events or bytes and may reset on process restart. A gauge represents state that can move up or down, such as queued work or in-flight requests. The instrumentation guidance distinguishes these contracts: use rate() for cumulative counters, and do not treat a naturally decreasing gauge as a counter. Applying rate() to a queued-work gauge can interpret a real drain as a reset; it does not turn queue depth into completed jobs per second.

rate() works with samples that were observed. It cannot recover increments that occurred after the last scrape but before the process restarted. A short window can preserve less smoothing and become sensitive to sample availability; a long window smooths brief changes but blends the new post-deployment state with earlier history. The official guidance does not prescribe one universally optimal window. Choose it against the scrape interval, desired alert response, missing-sample behavior, and rule-evaluation interval, and document those conditions alongside a dashboard or alert.

An instance label is not a permanent process identity. During a rollout, a new Pod may receive a new instance or pod value. The old series can become stale and the new label set begins a separate series. Per-series rate() retains each lifecycle's samples before the surviving rates are aggregated, but it does not fill periods with no samples or prove that a new series has enough observations. During diagnosis, inspect raw values by instance or Pod, resets(), up, and deployment events before relying on the total. A smooth aggregate line can otherwise combine “old instance disappeared,” “new instance just started,” and “counter reset” into one ambiguous change.

irate() is not just a faster substitute for rate(). The function reference says it uses the last two data points and is intended for graphing volatile, fast-moving counters. Brief changes can repeatedly reset an alert's for condition, so the documentation favors rate() for alerting and slower-moving counters. A query review should therefore account for whether the output is meant for a transient graph, an alert, or a recording rule—not just swap function names.

Histogram sums and counts should not be averaged too early

A classic histogram or summary has separate cumulative _sum and _count series. To calculate the mean observation duration across instances, Prometheus's histogram guide uses the same general order: rate each _sum and _count series, aggregate as required, and divide the totals. Conceptually:

sum by (job) (rate(http_request_duration_seconds_sum[5m]))
/
sum by (job) (rate(http_request_duration_seconds_count[5m]))

Do not calculate each instance's mean and then take an unweighted mean of those means; instance request counts can differ. Nor can you add averages together and call the result an average. Keep cumulative duration in the numerator and observation count in the denominator until each is aggregated, so the ratio answers “mean duration for all requests.” This is still a mean, not p95. A quantile requires histogram buckets and a different expression. The related article on why per-instance quantiles cannot simply be averaged covers that distinction; this article focuses on reset information and the ratio denominator.

One less common condition matters: if a classic histogram or summary accepts negative observations, its _sum can legitimately decrease. The histogram documentation warns that this drop may be treated as a counter reset and distort rate(_sum). The documented issue does not apply in the same way to native histograms, which are handled as a whole. Rate-before-sum cannot repair an incorrect metric contract. Redesign the metric or expression instead of treating aggregation order as a universal fix.

Validate the query and recording rule with the same input

Before editing a production rule, inspect raw counters, resets(counter[window]), per-instance rate(counter[window]), and the final aggregate in Prometheus's table view. Keep deployment time, sample timestamps, and series labels in the same diagnostic record. The goal is not merely to see a nonempty total: verify the intended dimensions, that the restart series was handled separately, and whether missing samples near a window edge affect the reading.

For a repeatable regression, Prometheus documents promtool test rules fixtures with input series and expected expression samples. A proposed fixture can make one counter fall inside the window while another keeps rising, then assert per-series rates, the job aggregate, and the output labels. Add a negative case that changes the metric to a falling gauge or changes the instance label, so the test does not mistake missing observations for a stable total. This article did not create or execute that fixture and did not query a live Prometheus server; these are proposed validation steps, not test results.

Recording rules also need stable output labels and an interpretable name. The recording-rule guidance recommends names that express aggregation level, metric, and applied operations, and recommends stating which labels are removed when aggregating. If a result is named job:http_requests:rate5m, check that its actual label set preserves the promised job-level dimensions. Once instance is removed, that derived series cannot tell you which instance reset. Treat that information loss as a design decision rather than patching it after a confusing dashboard appears.

Before approving a query, answer three questions: does the metric obey the counter contract; do its labels still distinguish the relevant series across restarts; and do the final by/without labels and any histogram denominator represent the same business scope? If those checks are missing, an expression that parses and draws a continuous line does not prove that it represents the intended total rate. Rate-before-sum preserves evidence for reset detection; it does not choose the measured quantity, series identity, or statistical denominator for you.
