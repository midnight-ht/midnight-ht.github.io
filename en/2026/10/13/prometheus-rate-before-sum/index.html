Calculate each counter rate before aggregating replicas

Preserve counter-reset context by calculating per-series rates before aggregation.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-13 · Estimated read 5 min
Translations
zh-CN en

Article

Calculate rate for each counter series before aggregating replicas. Summing raw counters first can conceal one instance’s reset and remove information needed for per-series reset handling. Aggregation order changes meaning, not merely query style.

Each series has its own resets

The Prometheus query-functions reference instructs users to apply rate before aggregation so counter resets on target restart remain detectable. It also limits rate to counters. A gauge that naturally rises and falls has a different meaning.

Imagine two cumulative request counters. One restarts and begins again at a smaller value while the other keeps increasing. Their combined series can obscure the first instance’s decrease. Per-series rate calculation retains the reset context before combining the resulting rates. This explanatory scenario was not queried or measured.

Confirm metric type and series identity before simplifying the query. A request-related name does not guarantee counter behavior. A question about currently active requests may require a current-value metric rather than the rate of a cumulative count.

The window belongs in the interpretation

Rate estimates activity over an observation window; its displayed value is not a precise instantaneous count derived from individual request logs. Window length, collection intervals, and missing data affect the evidence. Preserve original series and collection status when diagnosing unexpected results, not just a dashboard screenshot.

Short windows can expose changes but depend more visibly on available samples. Longer windows provide different smoothing and can hide brief changes. No universal optimal window is prescribed here. Select it for the business decision and collection conditions, then disclose it in reports and alerts before comparing numbers across views.

A total does not diagnose an instance

Fleet rate describes overall activity. It does not explain a particular restart or disappearance; inspect instance series, deployment events, and collection errors. Aggregation labels must describe the intended scope, and incompatible units or operations must not be combined under a plausible-looking title.

A proposed controlled test compares query order when one counter resets and another grows. This test was not run, so no result is claimed. Verify actual metric types before publishing queries. See label-cardinality budgets for the separate cost of maintaining the series being aggregated.
