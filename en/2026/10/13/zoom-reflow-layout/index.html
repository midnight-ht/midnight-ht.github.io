Why can 400% zoom still hide content after mobile passes?

A mobile screenshot does not verify zoom reflow. Check content and tasks at a 320 CSS pixel viewport, and keep two-dimensional exceptions local.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-25 · Estimated read 22 min
Translations
zh-CN en

Article

A page that fits a phone screen has not necessarily preserved the same information and controls after desktop browser zoom. To review reflow, present vertically scrolling content in a viewport equivalent to 320 CSS pixels wide, then follow a real task and check what remains readable and operable. Two-dimensional scrolling is an exception only for the specific content whose use or meaning needs a two-dimensional layout. The disappearance of a horizontal scrollbar by itself can hide the more serious problem: content may have been clipped or removed.

A phone viewport and browser zoom create different states

Phone testing usually changes the device or browser viewport and may cross a responsive breakpoint. Desktop browser zoom reduces the visible CSS viewport while changing the space occupied by text, components, and fixed regions. Both states can become narrow, but they do not necessarily use the same layout rules. A page may switch to one column on a phone while retaining a minimum width at desktop zoom. A phone breakpoint may hide a sidebar, while the zoomed state removes the only search entry point inside it.

WCAG 2.2 Success Criterion 1.4.10, Reflow (Level AA), requires vertically scrolling content to be presentable at a width equivalent to 320 CSS pixels without loss of information or functionality and without requiring two-dimensional scrolling to read it. W3C explains that 400% zoom from a 1280 CSS pixel wide starting viewport is one way to reach that equivalent width. This is a sizing equivalence, not a promise that 400% on every browser, operating system, toolbar, or physical display yields exactly the same usable area. Review the actual CSS viewport and page behavior. This article focuses on horizontally written content; the corresponding height criterion for horizontally scrolling content is 256 CSS pixels.

For example, imagine an order console that changes a three-column layout into cards at a phone breakpoint. The mobile screenshot has no overflow, but at desktop zoom the header, fixed action bar, and table minimum width consume the available horizontal space. The order number is visible while the submit button is covered by the fixed bar. There are at least two separate questions: can the content be read in the narrow viewport, and can the user still perform the final action? A responsive screenshot answers only part of that.

The test record should therefore state the viewport width or zoom path, page state, scroll direction, and operations completed. The order console here is a hypothetical example. No browser zoom test was run on a real product for this article, and it makes no conformance claim about any site.

Follow the task before judging overflow

Choose a path that crosses several regions of the page. For order processing, it might be: find an order, confirm its amount and delivery details, read an error message, submit, confirm the result, and return to the list. Repeat the same path at a default desktop size, a narrow phone viewport, and the target equivalent width. A screenshot is not necessary at every step, but the reviewer should be able to answer: where is the information, is the control visible and reachable, and is there a next step after the state changes?

Inspect failure mechanisms individually. A fixed-height container can crop its final instructions. overflow: hidden can remove the scrollbar while cutting off a button or validation message. A fixed footer can cover the control that currently has focus. A sidebar can disappear at a narrow width without a disclosure control. A fixed-width input can push its label outside the visible area. No horizontal scrollbar is an observation; it does not prove that the content is still usable.

A useful record for each step is “expected information or operation — actual location — how to reach it — observed blocker.” For example: “Read the reason for a failed submission — message below the form — reachable by vertical scrolling — fixed footer covers the retry button.” This directs the repair toward the mechanism: clipping, stacking order, or fixed-region space, rather than the vague label “mobile incompatibility.” Retest the same path after the change. Switching to a different test object can make an unresolved defect look closed.

The two-dimensional exception belongs to a local region

WCAG 2.2 Reflow permits two-dimensional scrolling for content whose use or meaning requires a two-dimensional layout. W3C examples include maps, images needed to understand the content, video, games, presentations, data tables (but not each individual cell), and interfaces where a toolbar must remain visible while the user manipulates content. The deciding question is whether removing that two-dimensional relationship would damage understanding or functionality, not whether a different implementation is inconvenient.

Imagine a reconciliation page with a table containing many columns. Amounts across several periods have a horizontal relationship within each row; turning the table into cards could make comparisons harder. A local horizontal scroll area may therefore be appropriate for the table. The page title, filters, explanatory text, and Export button do not inherit the exception automatically. They should still be accessible at the narrow viewport. Cell text also needs inspection: W3C’s explanation says the exception covers the table relationship, not the disappearance of content inside cells.

A map works similarly. The map itself may need panning in two directions, while place names, filters, and results can use a single-column layout. If the map is the only way to understand locations, reviewers should also ask whether a text list or another equivalent interaction provides the essential information. That alternative is a product and validation question; “maps are excepted” is not a reason to end the review.

There is a useful counterexample. If ordinary article text sits inside a fixed-width inner panel and readers must drag horizontally to follow each line, labeling the panel “two-dimensional” does not show that the text itself needs a two-dimensional relationship. By contrast, code indentation or nested lists may rely on some two-dimensional structure. Keep the container adaptable and decide whether the local content truly needs the relationship. The exception should be tied to a specific region and reason, not used as a page-wide pass.

Make the viewport, zoom, and content reproducible

W3C defines the target in CSS pixels, not physical device pixels. Device pixel ratio, operating-system scaling, browser chrome, and scrollbars all affect the visible area. Setting a display resolution to 1280 pixels does not guarantee a 1280 CSS pixel web viewport. During a review, use developer tools to set a viewport near 320 CSS pixels, or zoom from an appropriate starting width and confirm the final viewport. Record the tool, starting width, and final viewport so another reviewer can reproduce the condition.

Representative content matters too. Short labels and empty forms will not expose wrapping problems caused by a long address, a large amount, an error reason, or multi-line instructions. Test data can contain representative long text without pretending it came from a real customer; identify it as test data. Cover the relevant states: default, validation error, loaded, success, insufficient permission, empty list, and confirmation dialog. Check that hidden or collapsed content has an operable entry point and that keyboard focus does not land on a control the user cannot see.

A compact acceptance record can include: page and state, target CSS viewport, task start and end steps, information lost or operation blocked, any claimed two-dimensional exception and its reason, the repair version, and the retest result. If the test setup or browser cannot provide the required size, record the uncovered scope. That limitation does not become a pass by itself. A Reflow review covers one WCAG success criterion; it cannot establish conformance with the entire WCAG set.

Repair the failure mechanism, then check what was traded away

Common repairs include switching to a single-column layout, allowing text and controls to wrap, removing unnecessary fixed heights, putting a fixed footer back into document flow, or preserving an independent scroll region for content that genuinely needs two dimensions. The right choice depends on the region’s function and the sequence of operations. Applying overflow-x: hidden to the whole page may remove a scrollbar while clipping content. Shrinking all text may make a narrow screenshot look tighter while undermining the readability zoom is meant to provide. Locate the failing mechanism and change the smallest relevant area.

Retest at the viewport and along the path that originally failed, then return to the phone layout to check for new occlusion or ordering changes. Keep the same long text, error state, and task steps for before-and-after comparison. If information is moved into a disclosure, dialog, or alternate view, verify that its entry point is clear, the information is complete, and the user can return to the task. W3C failure technique F102 describes a failure case where content available at a wider viewport disappears after reflow to 320 CSS pixels and cannot be reached another way. A hidden component needs an equivalent information or functionality path.

These checks can reveal layout and task-continuity defects, but they do not replace keyboard, screen-reader, text-resize, or other accessibility testing. For another related failure mode, see content loss after text-spacing overrides; for form feedback and business-state boundaries, see form validation and server authority.

What is a reproducible reflow acceptance sequence?

Choose a task and representative state, set the page to the target equivalent viewport, and follow the task while recording whether content, controls, feedback, and the next step remain accessible. For every removed or horizontally scrolling region, state whether it truly depends on a two-dimensional relationship and how equivalent information remains available. Retest the original failure and the phone layout after repair. Preserve the viewport, state, steps, and outcome. This creates a reviewable Reflow record; it is not a site-wide accessibility certification.
