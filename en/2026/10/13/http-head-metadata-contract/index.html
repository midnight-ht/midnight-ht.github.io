A successful HEAD response does not verify the GET body

HEAD success proves only that the method request succeeded; verify the GET representation under matching identity and negotiation conditions to check its body and locale.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-25 · Estimated read 17 min

Article

Key takeaways

  • HEAD shares GET's target-resource semantics but transfers no representation data, so it cannot by itself prove that readers receive the right body.
  • RFC 9110 says a server SHOULD send the same response fields as for GET, while allowing fields determined during body generation to be omitted.
  • Name reachability, authorization, body consistency, and business completion separately; verify each under the identity and language conditions readers use.

A 200 from HEAD establishes that this HEAD request succeeded according to the server's response. It transfers no representation data, so it cannot establish by itself that the GET body is complete, in the right language, or consistent with a release expectation. To verify what readers will receive, issue GET under the same identity, route, and negotiation conditions and assert on its body at a level that matches the release promise. HEAD remains useful for metadata and conditional requests, but it is not body evidence.

Where HEAD and GET are the same

RFC 9110 Section 9.3.2 defines HEAD as having the same semantics as GET, except that the server must not send content in the response. HEAD obtains metadata about the selected representation without transferring its representation data, for example to test a link or learn about recent modifications. “The same” does not mean both requests must traverse identical application code or produce byte-for-byte identical messages. It describes the method's semantics for the target resource and then explicitly excludes response content for HEAD.

The response-header rule has an important boundary. The specification says the server SHOULD send the fields it would have sent for GET, but it MAY omit fields whose values are determined only while generating content. A dynamically generated Content-Length or Vary can be in that category. SHOULD is a strong recommendation that permits justified deviation; MAY expressly identifies an option. A monitor that treats every missing field as a defect can turn permitted behavior into a false alarm. Conversely, seeing Content-Type in HEAD says nothing by itself about whether the body actually matches that type.

A status code does not enlarge the evidence either. Section 15.3.1 says 200 means the request succeeded, while the meaning of response content depends on the method: GET represents the target resource, and HEAD does not transfer representation data. “HEAD 200” therefore is not shorthand for “the GET body has been reviewed.” It does not show that an anonymous visitor and a signed-in user see the same representation, that the Chinese route did not return English, or that the HTML is not a generic error page carrying status 200.

A probe can succeed while the content is wrong

Suppose a release process monitors a public report. A probe sends HEAD to the default URL, gets 200 and plausible headers, and the dashboard marks “report body is readable” as successful. A real reader's GET might still hit an older edge-cache version, negotiate a different language, or receive a generic error page that the application incorrectly returns with status 200. This is a hypothetical design scenario, not a test performed against this site or a claim about a specific production service.

Even without an implementation bug, HEAD cannot find a missing paragraph introduced during body generation, a wrong visible title, an injected login page, or structured data that disagrees with the visible title. It gives resource-metadata evidence, not an answer to the reader's content question. Release verification can keep separate evidence for public-route response, authorization, selected language and representation, and whether the GET body contains markers from the reviewed version. The status page then does not need one green “healthy” light to conceal unchecked dimensions.

Here is a proposed validation plan that has not been run in this article's environment: issue anonymous GET requests for the Chinese and English public pages; record the final URL, status, Content-Type, language-related fields, HTML title, body fingerprint, and release revision marker. Then issue HEAD to each route and compare only metadata that the protocol says should generally correspond. For protected content, repeat under an ordinary reader's permission; an administrator session is not a substitute. Because request conditions can select different representations, hold Accept-Language, authorization state, query parameters, and cache directives constant. Otherwise, different responses may reflect different experiments rather than a method implementation bug. Compute the body fingerprint from the received body and compare it with the reviewed release artifact; checking only that a homepage link exists is insufficient.

304 validates a cache condition; it does not download the body again

Conditional requests are an easy boundary to confuse. A client can send If-None-Match or another condition and receive 304 Not Modified. Section 15.4.5 says that, without the condition, the request would have resulted in 200; the server does not transfer the representation because the client indicates it already has a valid one. A 304 therefore depends on the representation already held by the client and on the cache-validation flow. A monitoring probe with no saved response body cannot treat 304 as proof that it received the body. A client that really does hold a cached representation can continue using that saved content after validation.

HEAD can also participate in conditional validation, but that result still does not prove that a new response body reached the checker. If the objective is to reduce bandwidth, a client or monitor can retain an ETag and transfer only what is needed after a conditional request. If the objective is release acceptance, inspect the new version's GET body, or establish precisely which representation version the validator refers to and which stored body is available. These are different problems: one controls transfer; the other establishes content. Combining both into a single “URL returned 200” check makes the meaning of success ambiguous.

Diagnose a method difference without guessing

When HEAD and GET differ, first record the method, time, complete target URI, final redirect, identity scope, Accept-Language, cache conditions, status, and relevant response fields. Then compare whether both requests selected the same resource and representation. If GET returns 401, 403, or a redirect to a login page, investigate identity and access scope. If the GET body carries an old release marker although the reviewed artifact is new, inspect cache keys, invalidation propagation, and origin revision. If differences track language requests, check negotiation fields and route mapping. “HEAD succeeded but GET differed” does not prove the cache is broken; authorization, content negotiation, and request parameters can explain the result too.

A small result matrix keeps the difference from being misdiagnosed. If HEAD is 200 and GET is 404, inspect method routing, redirects, and gateway rules; HEAD reachability cannot stand in for the body request. If both are 200 but the GET body carries an older release marker than the current artifact, inspect cache keys, invalidation propagation, and origin revision. If HEAD omits Content-Length or Vary while GET includes it, first ask whether the field can be determined only while generating the body. RFC 9110 permits that omission, so it is not automatically a fault. This matrix separates protocol-permitted differences from an actual body error.

Write the smallest verification that adequately supports the promise. An external-link checker may only need to know whether a URL responds to a specified method; HEAD can be a low-cost signal. A web release needs the visible title, key paragraphs, and locale from an anonymous GET. A file download needs GET status and content identity. A protected resource needs the target reader's permission scope. Conditional caching needs a retained representation to verify cache-update semantics. For a very large download, HEAD can screen before a range request or sample, but partial bytes do not verify the whole file, and a sample does not prove every part is correct.

HEAD is neither useless nor a shortcut for content acceptance. It answers a narrower question: what metadata did the server report for HEAD on this resource? The GET body, access visibility, selected language, and business state each need their own evidence. Giving a monitor an accurate name and recording its method and request conditions prevents “response probe passed” from being relayed as “the reader's content was verified.” For the distinction between conditional validation and freshness, see cache validation and freshness.
