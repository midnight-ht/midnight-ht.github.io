Avoid mutable aliases between parametrized test cases

Inspect mutable aliases and independent expectations instead of relying on test ordering.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-13 · Estimated read 5 min
Translations

Article

pytest passes parametrized values without automatically copying them. If cases reference the same mutable object, a mutation in one can affect another. Inspect object ownership before changing execution order: ordering often exposes shared state rather than causing it.

Several parameter labels can reference one object

The pytest parametrization documentation states that values are passed as-is and warns that changes to lists or dictionaries can appear in subsequent cases. This applies when objects are shared; it does not mean every parametrization shares mutable state.

Suppose two scenarios reference the same order dictionary. One changes its state to simulate cancellation, and the next assumes it receives an uncancelled order. That case may inherit the mutation. This example was not executed and is not a reproduced project failure. The boundary concerns input aliases, not a broken promise of automatic pytest isolation.

Inspect object creation, module-level lifetime, and repeated references. Equal contents need not mean identical objects, while separate row descriptions do not guarantee independent inputs.

Explain the depth of isolation

Copying an outer dictionary can still share mutable nested lists. Choose construction or copying that matches the mutation scope. Building the required input per case is often clearer than duplicating a large template whose contents are poorly understood.

Keep expected results independent as well. If mutation affects both the input and the object used for assertions, they can change together and create a misleading pass. Do not solve sharing by deriving the expected answer from the very implementation being tested.

Verify independence rather than one ordering

A proposed investigation runs a suspicious case alone and changes ordering or adds a mutating neighbor. Order sensitivity remains a clue: external resources and caches may also be responsible. No such tests were performed here, so neither passing nor failing results are claimed.

When shared evolution is the intended business scenario, design an explicit sequence instead of using independent parameter cases as hidden steps. Isolation and continuity are different goals. Preserve checks that establish the object boundary rather than merely making today’s order green. For the separate resource-lifetime question, see fixture scope and isolation.
