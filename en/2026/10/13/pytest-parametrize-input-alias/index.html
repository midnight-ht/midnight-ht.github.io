Why pytest parameter cases contaminate each other: trace shared objects before copying

pytest passes parameter values as-is. Trace list identity, nested references, and expectations before choosing fresh construction, a fixture, or copying.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-25 · Estimated read 18 min
Translations
zh-CN en

Article

pytest passes parametrized values to a test without automatically copying them. If two parameter rows refer to the same list, an in-place mutation in one case changes the starting value seen by the other. Before fixing the test, trace object identity and decide where sharing occurs. Then choose among fresh construction, a fixture factory, a shallow copy, or a deep copy. Reordering cases can expose leakage; it does not define an isolation boundary.

Two parameter rows do not mean two objects

The pytest parametrization guide says parameter values are passed as-is, with no copy. It warns that mutations to passed lists or dictionaries may be reflected in later test-case calls. Python’s assignment and copy documentation explains the language-level reason: assigning an object to another name creates a binding, not a new object.

Consider this hypothetical example. The snippet is a mechanism walkthrough; it was not run and is not a reproduced project failure:

import pytest

shared_items = []

@pytest.mark.parametrize(
    "items, item, expected",
    [
        (shared_items, "A-7", ["A-7"]),
        (shared_items, "B-2", ["B-2"]),
    ],
)
def test_append_one_item(items, item, expected):
    items.append(item)
    assert items == expected

The two tuples are distinct, but their first element points to shared_items. The first call appends A-7 to that list. When the second call begins, the list already contains A-7; appending B-2 produces two values, while that row expects only B-2. The cause is not the repeated parameter name items, nor a pytest promise that inputs will be reset. Both rows supplied the same mutable object to separate calls.

Conversely, equal-looking lists need not have the same identity. If the rows are ([], "A-7", ["A-7"]) and ([], "B-2", ["B-2"]), each list literal creates a separate list, so this particular top-level alias is absent. Ask whether two positions refer to the same object, not whether their printed contents match. In Python, a temporary identity check with is answers whether two references point to the same object; == compares values.

Do not inspect only the outer dictionary

Sharing can hide one level down. Suppose template = {"cart": {"items": []}, "currency": "CNY"}. copy.copy(template) creates a new outer dictionary, but cart and items remain references to the objects in the original. If one case runs payload["cart"]["items"].append("A-7"), a shallow copy sees that addition too. An is not assertion on the outer dictionary alone can create false confidence about isolation.

The Python copy documentation draws the distinction precisely: a shallow copy creates a new compound outer object and inserts references to its contents; a deep copy recursively copies contained objects. This does not mean shallow copy is unsafe and deep copy is always correct. For object graphs with cycles, custom copy behavior, file handles, connections, or intentionally shared read-only objects, generic deep copying may fail, copy too much, or violate the object’s semantics. It may also turn each case into an unnecessarily expensive resource construction.

Start by listing the fields a test may mutate and who owns each object. If an input contains scalars and a short list, separately constructing each row is often clearest. If only the outer container must differ and its members are immutable, a shallow copy may suffice. If nested mutable data must be independent per case, deep copy or explicit field-by-field construction may be appropriate, with copying cost and custom type semantics considered. Avoid copying a large template tree without documenting which parts should remain shared.

Separate parameter descriptions from runtime objects

A parameter can be an immutable description rather than a mutable object that several cases might reuse. For example, a row can carry initial values and an operation name; the test can construct its list when it starts. If construction needs validation or more expensive setup, a pytest fixture can receive the parameter and build the object. The official indirect parametrization example shows that indirect=True sends the supplied value to a fixture, where it is available through request.param.

Isolation still depends on what the fixture constructs. A function-scoped fixture is destroyed at the end of each test by default, which suits objects that need to be rebuilt per test. But returning an externally shared container, using a broader scope, or placing the same nested member into every result does not remove aliases merely because a fixture is involved. Fixture scope describes a resource instance’s creation and destruction lifetime; it does not promise to deep-copy arbitrary parameter objects.

One practical pattern is to keep immutable specifications in the parameter table and let each fixture call create the mutable input:

@pytest.fixture
def payload(request):
    return {"items": list(request.param)}

@pytest.mark.parametrize(
    "payload, item, expected",
    [
        (["seed-a"], "A-7", ["seed-a", "A-7"]),
        (["seed-b"], "B-2", ["seed-b", "B-2"]),
    ],
    indirect=["payload"],
)
def test_append(payload, item, expected):
    payload["items"].append(item)
    assert payload["items"] == expected

This still deserves an object-depth check. list(request.param) creates a new outer list; the example elements are strings, so no nested mutable member needs separate copying. If the specification contains nested dictionaries or lists, the fixture should explicitly construct the fields that must be independent rather than assuming a shallow copy is enough.

Give expected results an independent source

If input and expectation share a mutable object, a test can mutate its answer along with its input. For example, if expected is derived from the same list passed to the implementation and the implementation changes that list in place, both sides of the assertion may change together. Even a passing assertion would then say little about correctness. An independent immutable expectation or a clearly specified expected value reduces this self-approval problem. But do not reproduce the implementation’s algorithm to generate the expected result; the same logic error could contaminate both sides.

Sometimes sharing is intentional because the behavior under test is a stateful sequence. In that case, several operations acting on one object may be the point. Do not disguise the sequence as independent parameter cases. One test can explicitly perform the transitions and assert each intermediate state. The goal is not to eliminate all sharing; it is to make shared state and its evolution part of the test contract rather than an accidental consequence of parameter order.

Verify object boundaries, not only a green result

A focused verification plan should answer several separate questions. First, inspect the identities of top-level parameters and nested members to confirm which values should be the same and which must differ. Next, let one case mutate a suspicious field and observe whether another case still starts from its independent initial condition. Then compare an individual run with a grouped run, including a mutating neighbor, to see whether results depend on state left behind. Finally, confirm that expected values are not aliases of the mutable input. These are proposed checks, not pytest results: no command was run for this article, and no pass or failure log is claimed.

If a case passes alone and fails in a group, order sensitivity is a clue, but fixtures, module variables, caches, databases, and other external state remain possible causes. For adjacent but distinct boundaries, see pytest fixture lifetime and test isolation and mutable references in mock call arguments. The former concerns resource scope; the latter concerns a reference retained after one mock call. Neither is identical to aliases in parametrized input.

The choice can be concrete: when the parameter is just input data, construct independent values per row; when it describes an expensive runtime resource, let a fixture construct it under an explicit scope; use a shallow copy only when the outer container is the sole boundary that must differ; use deep copy or explicit construction only when nested mutable values need independence. Whichever method you choose, keep a check that proves each case has an independent starting state and an independent expectation.
