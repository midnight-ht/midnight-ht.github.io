A SQLite foreign key in the schema does not protect every connection

SQLite stores foreign-key declarations in the schema, but enforcement is a connection setting. Initialize and read back each connection, then verify writes and inspect existing data.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-25 · Estimated read 22 min
Translations
zh-CN en

Article

A foreign-key declaration belongs to the database schema, but whether a write enforces it depends on the connection executing that write. An application should enable foreign keys on every newly created connection, read the setting back before starting a transaction, and verify the real write paths with controlled invalid references. Checking one connection at startup does not prove that other pool connections, background jobs, or migration scripts are protected.

Why is the table definition not enough?

A foreign key describes a relationship: for example, an order’s customer_id should refer to an existing customer id. SQLite’s official documentation treats the declaration and runtime activation as separate steps. The application must issue PRAGMA foreign_keys on a library build that supports foreign keys. The documentation also says enforcement is enabled separately for each database connection. The SQLite FAQ describes the historical default as off, while the current foreign-key documentation warns that defaults may change and the SQLITE_DEFAULT_FOREIGN_KEYS compile option can affect a build. The reliable practice is therefore to set and read back the state the application requires instead of relying on a remembered default.

This creates an important scope difference. Several connections can open the same database file, while each connection has its own current enforcement setting. Reading 1 from connection A proves only that A is enabled at that moment. It says nothing about connection B, a connection created later, or a separate handle used by a maintenance command. When a pool discards and replaces a connection, the replacement must go through the same initialization path. The schema says what relationship should exist; the connection state says whether this write enforces it. Those are distinct pieces of evidence.

How can one startup probe mislead a connection pool?

Suppose a service opens a dedicated health-check connection A at startup and reads PRAGMA foreign_keys as 1. Requests are handled by pool connections B and C; a background worker opens connection D independently. Unless the startup probe covers the creation path for B, C, and D, its log establishes only that A is configured correctly.

Consider orders and customers as a hypothetical example. The customer table contains id 12, while a new order sets customer_id to 700. If the write lands on a connection with enforcement disabled, the REFERENCES declaration does not automatically turn the connection setting on; the invalid reference may be stored. On an enabled connection, the same relationship should be rejected. This describes SQLite’s mechanism. It is not an insertion test performed for this blog, nor evidence of a production incident.

This is also why a successful migration is not proof of runtime protection. A migration can show that a CREATE TABLE statement was accepted and stored in the schema. It does not decide whether every connection opened later will enforce the relationship. Conversely, checking one connection’s setting cannot show that every existing row in the database already satisfies its declared relationships.

To make the scope difference observable, I ran an isolated shared in-memory test through Python sqlite3: Python 3.11.15 linked to SQLite 3.53.1. After enabling foreign keys on connection A, A read back 1 while untouched connection B read back 0. B accepted an insert that referenced a missing parent. PRAGMA foreign_key_check on A returned child, row 1, parent, foreign-key index 0. An attempt to enable enforcement inside B’s transaction still read back 0. After the transaction ended, setting it again produced 1, and the same invalid insert raised IntegrityError with FOREIGN KEY constraint failed. These are the observed results of a one-off local test. They establish connection isolation and transaction timing for that runtime, not the driver, pool, or build options used by this site or another application. The full script and captured result are archived with this review batch.

Why must the setting be applied outside a transaction?

SQLite’s documentation states that changing foreign_keys after a multi-statement transaction has begun has no effect, and this attempt does not return an error for that reason. A check that runs BEGIN, then PRAGMA foreign_keys = ON, and treats the absence of an error as success can therefore produce a false positive.

Give connection initialization an explicit order: create the connection, set foreign keys, query PRAGMA foreign_keys, confirm that the result is 1, and only then hand the connection to business code or begin a transaction. If the result is not 1, do not convert it into a routine warning and continue writing; reject the connection from the write path when referential integrity is required. If the query returns no row instead of 0 or 1, SQLite’s documentation says the library may not support foreign keys, for example because it is too old or compiled without the relevant features. Inspect the runtime library and driver build rather than assuming the SQL file proves enforcement exists.

The correct hook depends on the database driver and pool; this article does not assume a framework-specific option. During review, identify where each new connection is created, configured, read back, and prevented from being borrowed if initialization fails. Also cover replacement connections. If application or test code can change the pragma while a connection is checked out, define a reset or recheck policy before it returns to the pool. A single-connection program needs to initialize that connection, but a separate migration or maintenance tool is still a separate entry point.

Does a PRAGMA value of 1 prove writes and existing data are safe?

Split verification into three layers. First, query PRAGMA foreign_keys on every actual connection creation path. This establishes the setting on that handle; it does not prove the table declaration is correct or that old rows are clean. Second, use a disposable database or recyclable test database to create parent and child tables, then attempt to make a child row reference a nonexistent parent key. The shared-memory test above already exercised two connections: unconfigured B accepted the invalid reference, while enabled B rejected it. Product acceptance should also exercise the request handler, background job, and migration or maintenance entry point separately, rather than trying only one command-line connection. This article did not connect to the site application or a production database, so those integration checks remain proposals. Record the SQLite version, driver, connection path, and confirm that rejection came from the foreign-key constraint rather than another constraint.

Third, inspect existing relationships. PRAGMA foreign_key_check returns rows that violate declared foreign keys. Its output identifies the child table containing the REFERENCES clause, the child rowid (NULL for a WITHOUT ROWID table), the referenced parent table, and the foreign-key index. It can reveal relationship problems left while enforcement was disabled, but it does not enable future connections and cannot evaluate business relationships that were never declared. Decide whether to repair, isolate, or retain each finding based on the domain. Do not delete records merely to make the output empty. If the database lacks enough information to reconstruct the relationship, report that data gap instead of inventing a parent row.

The layers help distinguish failures. A connection probe returning 0 points to initialization. An invalid write succeeding on one path points to enforcement coverage or declaration behavior on that path. Rows returned by foreign_key_check point to historical data that needs assessment. Collapsing all three into “foreign keys passed” hides whether the evidence covers the setting, write-time behavior, or existing data.

How should the check follow the connection lifecycle?

List every database-opening path, not just the service process: request pools, queue workers, scheduled jobs, administration commands, migrations, tests, and recovery scripts. Confirm the library version and driver build used by each. Inspect each connection factory to ensure it sets and reads back the setting before a business transaction. For a pool, verify that replacement connections also run initialization. Then, against a temporary copy, test both a valid relationship and an invalid one through each entry point. Finally, run foreign_key_check on existing data and preserve both its result and the decision for each finding.

The parent and child records were test data for an isolated experiment that did run in a shared in-memory database on Python 3.11.15 and SQLite 3.53.1. It did not run against this site’s application or a production database. If test hooks cannot create every pooled connection individually, cover each creation configuration and reconnect behavior, and inspect the actual initializer. That remains bounded coverage evidence; it does not guarantee that every future version will be correct. Repeat the checks after upgrading SQLite, switching drivers, or changing how the pool is constructed.

Do indexes and business semantics still matter?

Yes, but they answer different questions. A parent key must meet SQLite’s primary-key or unique-key requirements. Without an index on the child key, SQLite may need to search the child table when a parent row is deleted or updated, which can make operations more expensive on large tables. A child-key index may improve that search; it does not enable enforcement and cannot repair a missing relationship. See the boundary between SQLite integrity checks and foreign-key checks. For parent-side operations and child-index costs, PostgreSQL foreign keys and child indexes discusses a related issue in another database; do not copy its implementation behavior directly to SQLite.

Foreign keys also have business boundaries. When a child key is NULL, SQLite’s documentation says the row does not need a parent row. If the product requires every row to belong to a customer, an additional constraint such as NOT NULL must express that rule. Enabling foreign keys does not repair old data, replace authorization checks, or decide who should restore a missing customer. A release review should keep separate records for the schema declaration, each-connection activation, rejected-write evidence, and historical-data handling. One startup probe cannot stand in for all four.
