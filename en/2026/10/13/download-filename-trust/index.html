Treat a download filename as a suggestion, not a local path

Treat Content-Disposition as a display hint: choose the write directory, storage identity, and permitted content type independently, then validate decoding and path containment.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-25 · Estimated read 19 min
Translations
zh-CN en

Article

Key takeaways

  • RFC 6266 defines a response filename as advisory; parsing filename* or stripping path components does not authorize a client write location.
  • Choose a fixed, controlled directory and an independent storage identifier first; process the decoded name as display metadata.
  • Display name, object identity, content type, and open policy are separate decisions; a safe-looking extension does not prove safe content.

The filename in a download response is a display suggestion. It should not decide which directory the client writes to, which object gets overwritten, or which program opens the bytes. Separate four responsibilities: parse the name under HTTP rules; derive a display-safe label; choose the real storage location and identity under local policy; and decide which content types may be previewed or opened. RFC 6266 explicitly calls filename and filename* advisory and requires that they not enable writes outside authorized locations. Decoding a name successfully establishes how its characters are represented, not whether its path, suffix, or contents are trustworthy.

A response header is not filesystem authority

Content-Disposition: attachment can carry filename or filename* for a recipient to use when constructing a suggested name during a save interaction. The filename subsection says recipients that understand the extended parameter should prefer filename* when both are present; older user agents may only use filename. RFC 8187 defines the extended parameter form charset'language'value. It requires senders to encode extended values as UTF-8 and percent-encode bytes outside its allowed character set. That is an encoding interoperability rule for HTTP parameters. It is separate from deciding whether the resulting text is safe as a complete local path.

The security boundary in RFC 6266 is more than a vague request to sanitize a string: the recipient must not be able to write to a location it is not entitled to use. The RFC names / and \\ as path separators when discussing untrusted path components, and calls out control characters, leading or trailing whitespace, dot-directory components, tildes, pipe characters, and device names as values with special meaning. Removing only the separator used by the developer's current operating system is insufficient when a server-supplied name can cross systems and be processed elsewhere. More fundamentally, even a name with no separator should not be concatenated into an arbitrary directory or used as the unique identity of a stored object.

Choose the storage location before handling the suggested name

Imagine a desktop sync tool downloading a partner's monthly report. The response proposes two parent-directory components followed by a shared folder and an executable suffix, while the product wants to display a recognizable label. The fragile design is “download directory + response filename”: remote input now controls the destination, object name, and extension. Removing one parent-directory component is not reliable. Nested encodings, backslashes, absolute paths, platform-special names, or fragments left after replacement can be interpreted differently by later layers.

A more controlled flow chooses a fixed download root from application configuration, then assigns this job a random ID or another identifier the response cannot control, for example job-8f31.bin. After parsing and display-specific checks, the suggested name is saved as metadata only. When the download is complete, the UI can show “October 2026 report” without using that text to reconstruct the destination path. Where the product permits a user-selected relative name, decode it completely once, resolve it to an absolute normalized path using the target platform's rules, confirm the result remains inside the download root, and use only the checked result for writing. OWASP's path traversal guidance primarily addresses application input used in server filesystem paths; applying its containment invariant to a downloader is an engineering analogy, not a claim that the cheat sheet defines desktop-client behavior. It warns that filtering only parent-directory components misses backslashes, later decoding, and absolute paths; a client still has to verify resolution under its supported operating systems. Where the business allows, prefer mapping an ID to the real path.

This is a design illustration, not a test of a local downloader. It does not require the user to see a random ID: storage identity can remain hidden while the display label preserves Chinese text. Keeping them separate addresses two different problems. The ID prevents two remote files with the same suggested name from overwriting each other; the label can still convey the source and date. If the product asks users to resolve collisions, define whether that includes names that become identical after Unicode normalization and collisions across directories. If the product renames automatically, specify whether it uses a sequence, timestamp, or collision ID and make the resulting object findable. Silent overwrite should not be the default compatibility fallback.

A readable filename* does not make content safe to open

The same standard also warns recipients not to trust the server-provided extension on platforms that use suffixes to determine file type. An unsafe extension can create a privilege-escalation risk when the saved file is later opened. A response might provide filename*=UTF-8''report and a plausible media type, but both values arrive in the same response; neither independently proves the bytes belong to a PDF or that this client should open them automatically. Show the name as a proposal. Decide preview, handler, quarantine, or scanning behavior from the product's content policy and its validation steps.

For example, a report workflow that accepts only PDFs could quarantine an unexpected download or reject it with a useful explanation. Before labeling a file with a PDF extension, it first needs an appropriate check supporting the claim that the content belongs to an allowed category. Changing an executable extension to a PDF extension changes the label, not the bytes; even a matching Content-Type and suffix remain response metadata rather than independent payload validation. Conversely, passing a format check does not make an untrusted macro-enabled document automatically safe. Whether to preview, quarantine, or open it remains a product content-policy decision. Without client-side content inspection, do not label “download complete” as “file safe.”

Name parsing also needs explicit failure behavior. Missing filename parameters, duplicate parameters, malformed percent escapes, invalid UTF-8, leading or trailing whitespace, control characters, dot-directory names, and excessive length should resolve to a product decision: use a fixed fallback label plus a controlled ID, display only safely rendered text, or reject the save. The standard classifies repeated parameter names as invalid; the particular client behavior—ignore, fall back, or reject—should be documented. Do not fall back to the unchecked raw header when parsing fails, and do not decode the same string repeatedly between parsing, path checks, and the final write. Filesystem rules for special names and browser behavior vary by target platform and need testing on platforms the product supports. The RFC identifies risk classes; it does not promise that all implementations sanitize names identically.

Validate the result, not just the save prompt

Start with a responsibility table: the response parser chooses a candidate under RFC 6266 and RFC 8187; the display layer handles control characters and legibility; the storage layer decides the root directory, object ID, collisions, and overwrites; and the content handler decides media category, preview, opening, and quarantine. A proposed test matrix can include both filename parameters at once, Chinese text and spaces, missing or conflicting parameters, parent-directory components, backslashes, absolute paths, percent encoding, dot-directory names, device names, surrounding whitespace, control characters, very long values, name collisions, and misleading extensions. For each case record the parsed label, absolute target path, containment decision, whether an object was overwritten, what the content check decided about the actual response bytes, and what error the user saw.

Do not test path containment only by asserting that the name lacks parent-directory components. Check the path after the target platform resolves it, including decoding order and symbolic-link conditions. OWASP recommends normalizing the full target, verifying that it stays within the fixed base directory, and then using the already-checked path; where symbolic links are possible, consider the race between checking and opening. For a normal browser download, the application may not control the operating system's final save location, so scope the security claim to “the response provides a suggested name” rather than saying a web page controls a user's directory permissions.

The RFCs and security guidance describe protocol boundaries and implementation advice, not universal compatibility guarantees for every browser, desktop application, or filesystem. No attack test, cross-system save test, or content-identification test was run for this article. Before release, verify destination behavior, same-name collision prompts, Unicode display, and automatic-open behavior on the actual supported platforms and retain those test records. For the server-side boundary on inbound files, see upload isolation and validation.
