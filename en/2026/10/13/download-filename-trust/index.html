Treat a download filename as a suggestion, not a local path

Separate suggested download names from authorized destinations and permitted content handling.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-13 · Estimated read 6 min
Translations
zh-CN en

Article

Treat a download filename as a server suggestion, not permission to select a local path or a safe file type. The client must control its destination directory, storage identity, and permitted handling. A friendly name should not grant remote input local write authority.

A name does not authorize a destination

RFC 6266 treats Content-Disposition filenames as advisory and discusses path components, dangerous extensions, control characters, and special names. When filename and filename* are both present, recipients supporting the mechanism should prefer filename*. That concerns representation and compatibility; successful internationalized decoding is not a safety check.

Imagine an internal tool downloading a supplier report. Concatenating the suggested name into a destination path lets a display hint influence storage location. A safer design chooses an authorized directory and independent storage identifier first, then derives a checked display name. This is a hypothetical design, not an attack or execution test performed here.

Account for more than the developer machine’s usual separator conventions. Display also raises normalization and recognizability concerns: a familiar-looking name is not necessarily the same identity the program uses. Keep destination control and display rules distinct instead of assigning every responsibility to an undefined string-cleaning operation.

An extension is not content validation

The RFC warns about unsafe extensions on platforms that depend on them. Decide what content the application permits rather than automatically invoking a risky handler because the server suggested a suffix. Declared media type, actual content, and business expectations offer different evidence; none is a universal safety certification.

A report-only workflow might isolate an unacceptable download, block automatic opening, and explain the failure. Retention follows the application’s data policy. Silently renaming a file and opening it does not change its contents.

State compatibility limits

A proposed test plan includes spaces, non-Latin names, missing fields, collisions, and malformed values. Actual behavior depends on client implementations; this article has not tested browsers or operating systems and makes no universal compatibility claim. A parse failure should use a product-defined safe default rather than an arbitrary path fallback.

Keep the visible name separate from the internal identifier to diagnose overwrites and duplication. Successful saving does not establish acceptable content or actual reading. For the corresponding inbound boundary, see upload isolation and validation.
