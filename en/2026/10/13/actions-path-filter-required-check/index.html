Why Is a Required Check Still Waiting After Path Filtering?

A GitHub Actions paths filter can prevent a workflow run from being created, leaving a required check pending. Keep the gate observable while selecting affected tests inside the workflow.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-25 · Estimated read 16 min
Translations
zh-CN en

Article

Key takeaways

  • Workflow-level path filtering can leave an associated required check Pending and block a pull request.
  • A job skipped by a condition reports Success, so a conditionally skipped test job should not alone define the gate.
  • Separate workflow triggering, affected-test selection, and the final required result; validate failure, cancellation, and merge-queue cases.

If a pull request changes only documentation, a paths filter may prevent GitHub Actions from creating a workflow run. If branch protection still requires the workflow’s build check, the pull request can show “Waiting for status to be reported.” This is not a slow build, and rerunning cannot repair a run that was never scheduled. The path filter acted before the workflow existed, so the required check has no conclusion for branch rules to evaluate. To keep the gate usable, each applicable commit needs an observable final result. Put test-cost optimization inside that gate rather than making the entire required workflow disappear.

The layer where skipping happens changes the meaning

GitHub Actions supports paths and paths-ignore filters for push and pull_request events. These filters determine whether the workflow starts. When a workflow is skipped by path, branch, or commit-message filtering, associated checks remain Pending; a pull request that requires one of those checks is blocked. GitHub also documents that an event cannot use both paths and paths-ignore. To include some paths and exclude others, use positive and !-prefixed negative patterns within paths, paying attention to their order.

A job-level condition is a different layer. GitHub documents that a job skipped by a condition reports Success. If a job fails or is skipped, jobs that depend on it are skipped by default unless their conditions allow them to continue. “The test did not run” can therefore mean at least three things: the workflow never started; a test job was intentionally skipped because the change was judged unrelated; or an upstream failure caused a downstream gate to be skipped too. Treating all three as “tests passed,” or all three as “still waiting,” misreads the gate.

Suppose a repository marks build as required, but its workflow runs only when a change matches services/api/**. A pull request that edits only the root README does not match, so the workflow is not created. Branch protection still expects build; it does not automatically infer that the change is unrelated. Waiting longer will not create the missing run. By contrast, if the workflow starts and the build job’s if condition says the change does not affect it, GitHub may report that job as Success. That is a completed result, but it proves that the skip rule ran—not that a build actually ran.

Separate the amount of work from the gate’s conclusion

A more dependable structure is to keep workflow triggering stable for pull requests and commits that need checks, identify which tests the change affects after the run begins, run expensive tasks only for affected areas, and then have a consistently named aggregate gate inspect the detection job and the real results of relevant tests. That aggregate check is what branch protection requires. A changed-path map may reduce irrelevant work, but “not affected” needs a clear, reviewable path through the workflow. It should not be expressed by making the whole required workflow vanish.

The aggregator must not simply mean “the last job succeeded.” For example, a required job that depends on a failed unit job may itself be skipped under the default dependency rule. If branch protection expects a different check name, the pull request may wait for a result that will never be reported. GitHub exposes direct dependency results through needs; it also permits always() in a job condition so summary logic can run after a dependency fails or is skipped. But always() is true even when a workflow is canceled, and GitHub advises using it carefully. It must not convert “someone canceled validation” into permission to merge. Decide explicitly how the gate handles success, failure, skipped, and cancelled: the final gate should succeed only when affected tests pass, or when a supported “not affected” decision passes; a failure must fail, and cancellation must never become success.

This is a design direction, not a workflow file ready to paste into every repository. The change-detection job itself can fail; matrix tests may run only partially; manual and concurrency cancellations change the result. Marking a test job as required while also allowing its condition to skip can leave a green status whose meaning is unclear. A clearer contract is for the required check to mean “the validations required for this commit completed and met policy,” rather than “a job named build once started.”

Walk through a small change example

Assume a repository has docs/** and app/** changes. Its policy says documentation-only changes may omit application unit tests, but required-ci must report a conclusion for every pull request. The workflow does not use a top-level paths filter to suppress documentation-only pull requests. Instead, after starting, a change-detection step outputs app_changed. Tests run when that output is true; otherwise, the test job is recorded as an expected skip. required-ci depends on change detection and the test result and runs under a condition designed for summary logic. It checks each result: detection failure fails the gate; if app_changed=true, a failed or canceled test cannot pass; if app_changed=false and detection succeeded, the gate may accept “application tests not required” according to the stated policy. Its externally visible check name stays stable.

The boundary matters as much as the example. If shared workflow files, lockfiles, or test tooling change but the impact map only watches app/**, detection may incorrectly conclude that no tests are needed. Test selection is not synonymous with directory matching: include configuration changes that alter test behavior in the impact map, and review that map with regression examples. For negative path patterns, verify positive and negative cases in declaration order. When branch and path filters are both configured, GitHub requires both kinds of filter to match; passing just one does not establish that a workflow will start.

How can you check that it neither blocks unnecessarily nor waves failures through?

Before enabling the rule, define hypothetical inputs for: only docs/**; only app/**; both areas; a change to the impact map or workflow; a test job failure; a change-detection failure; a canceled run; and a new commit that should refresh the result. For each input, write down which jobs should run, which may be skipped, and whether the final required check should be success, failure, cancellation, or unreported. Then observe the workflow and branch-protection result in a test repository or controlled pull request, including the check name and conclusion seen by GitHub. These cases were not executed for this article; no claim is made that the proposed design passes in a particular repository, nor are time savings or success rates reported.

If you use a GitHub merge queue, separately verify that the required workflow responds to the merge_group event. GitHub says a merge queue requires that separate trigger; a normal pull_request check does not automatically establish that the generated merge-group revision was validated. A pull request may have green checks and still lack the result the queue requires.

The selection rule can be stated simply: allow internal tests to skip according to impact, but keep the external required check observable and report success only for real passes or a reviewed “not applicable” result. Whenever you change a trigger, path pattern, check name, dependency, or merge-queue configuration, revalidate that contract on the newest commit. For the separate question of deployment cancellation and mutual exclusion, see deployment concurrency and cancellation. Whether a deployment task completed and whether a required pull-request check reported a trustworthy conclusion are separate facts.
