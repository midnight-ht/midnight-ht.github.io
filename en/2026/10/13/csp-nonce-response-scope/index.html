Should a CSP nonce follow the build or the response?

Generate a CSP nonce with each policy response and keep headers and approved tags aligned; evaluate content hashes for static scripts.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-25 · Estimated read 17 min
Translations
zh-CN en

Article

Key takeaways

  • Refresh the nonce with each policy response and match it to approved elements.
  • Evaluate content hashes for fixed scripts; use per-response nonces for dynamic inline content.
  • At an edge cache, check freshness, header/body matching, unauthorized blocking and cross-response reuse separately.

A CSP nonce should change with the policy and HTTP response that carry it; it should not be generated once during a build and then live indefinitely in a cache. For fixed page content whose script bytes can be known in advance, a static site should first consider hash-based authorization. If the server must allow inline content that varies with a response, it needs to create a nonce while producing that response and keep the policy header and authorized elements together. The issue is not that “dynamic is always safe” or “caching is always wrong.” It is the lifetime of each authorization value, response consistency, and whether the allowed script sources are explainable.

The nonce contract is per transmitted policy, not per release

CSP Level 3's security considerations require a server to generate a unique value each time it transmits a policy containing a nonce source. The value should contain at least 128 bits of random data and should come from a cryptographically secure random number generator. MDN's response-header reference likewise describes a nonce as a random value generated by the server for every HTTP response. The browser compares the nonce-... value in the policy with the nonce attribute on the target script or style element. These documents define the mechanism and recommendation; they do not prove that a particular application implements it correctly.

One nonce may appear in the policy header and in several explicitly approved elements within the same response. It should not be a build artifact reused across responses. Changing it once per deployment confuses two different lifetimes. If every visitor refreshes and receives the same HTML and policy, the authorization value is still reused. Randomness alone is not enough either: a value created at build time, assembled from a timestamp, or accidentally exposed through a template or logs can still miss the intended lifecycle or unpredictability requirement.

Inspect the header, HTML, and generation point together

Trace three operations: generation, insertion, and delivery. Generation should use a secure random source. Insertion should touch only scripts or styles the application deliberately permits. Delivery should keep the Content-Security-Policy header and those elements in the same page response. Finding nonce= in a template does not prove these steps are connected, and a clean browser console only says that certain problems did not surface in that particular page load.

Imagine a template that always emits an old nonce while an edge function updates the CSP header per request. The header and element do not match, so a legitimate inline script can be blocked. If the edge changes the element but not the header, they still disagree. Now imagine a shared cache serving request A’s HTML and header to request B. The pair might still match and work, yet the value is being reused for later visitors, contrary to the unique-value requirement for each transmitted policy. These are protocol-based cache-risk scenarios, not a CDN failure or attack reproduced for this article.

This does not mean that every shared cache is incompatible with nonces. The question is whether cache delivery can still generate a fresh value for the policy being sent and update the final header and trusted HTML together. If a cache merely replays an upstream header/body pair, it repeats the authorization value; if an edge layer changes only one part, legitimate scripts can be blocked. Teams also need to inspect compression, streamed responses, cached template fragments, error pages, and retry paths for places that might bypass the same processing. If the architecture cannot keep those pieces coordinated, do not freeze a nonce to increase cache hits. Choose a verifiable dynamic-rendering boundary or reconsider hash-based authorization.

Static hashes and dynamic nonces solve different problems

MDN’s CSP implementation guide suggests nonces when content can be generated dynamically and hashes when static content must be served. A hash authorizes the actual script or style content, so a content change requires updating the hash in the policy. For an external resource using src, the relevant integrity attribute also matters. A hash is not a universal replacement for allowing dynamic scripts, and it does not need to be regenerated randomly for each page request. A nonce, by contrast, places maintenance responsibility on the server or edge response path: generate it for each policy and insert the same value accurately into the header and approved elements.

Suppose a prerendered site has one small, stable inline bootstrap script. Its build can calculate a hash from the exact script bytes and publish the policy with the artifact; a build check can detect when the hash drifts after a script edit. If a page includes request-specific inline configuration, a static hash becomes harder to maintain as the content varies, so a dynamic nonce may fit better—but the page then needs request-time rendering or reliable edge rewriting. The Next.js 13 Pages Router documentation is an example for that specific version and router: it recommends generating a fresh nonce for each page view and says dynamic rendering is required. Do not generalize that framework example into a universal rule for every framework and route.

How one cache scenario helps locate a mismatch

Imagine an origin server rendering HTML, a reverse proxy caching some pages, and an edge layer setting CSP. During diagnosis, record four separate facts at each layer: the generated value, the value on the HTML elements, the value in the final response header, and whether a cache hit reused a page across users. If all three values match but repeat between requests, the page may work while uniqueness is still wrong. If the header and element disagree, legitimate scripts can be blocked. If a template indiscriminately adds the nonce to unknown elements, injected content may inherit permission. CSP Level 3 discusses nonce hijacking and leakage, so “add a nonce to every script tag” is not a substitute for a trusted-template boundary.

This is a hypothetical architecture walkthrough. It was not executed against this repository or a particular CDN, so it does not show that any cache configuration is safe. A real system needs to define which responses are cacheable, which must be dynamic, and whether the edge treats the header and body as one representation when updating them. If error pages, prefetches, or non-HTML paths bypass the same logic, the validation scope needs those branches too.

Validate with checks that can reveal a failure

Start with Content-Security-Policy-Report-Only, as MDN recommends, to observe violations before enforcing a policy. Reporting can expose compatibility issues, but it does not itself block an attack. Then define test cases for at least two consecutive page responses; header-to-element agreement within a response; cache miss and cache hit; template-fragment reuse; a page containing untrusted content; a static hash after a script edit; and error, cancellation, or retry paths. The results should answer four different questions: did the value change, did the values match, was unauthorized content still blocked, and did a cache reuse authorization across responses? “The page had no visible error” is not complete acceptance evidence.

Also account for how MDN documents the nonce attribute: browsers hide the nonce content attribute from the ordinary getAttribute() return value; code that genuinely needs it can use the element’s nonce property. Hiding reduces some avenues for stealing a nonce through attribute selectors, but it does not prevent every injection or disclosure. A nonce does not replace output encoding, safe templates, dependency governance, or least privilege.

The choice is ultimately a maintenance-responsibility question. For static content with fixed scripts and a build that can keep the content hash accurate, evaluate hashes first. Use a nonce when the response contains inline content that must be allowed and the server can generate, insert, and send it consistently per response. If caches or templates cannot preserve that contract, adjust the delivery boundary instead of turning the nonce into a permanent allowlist. For a staged rollout that observes violations before enforcement, see a gradual transition to CSP Report-Only.
