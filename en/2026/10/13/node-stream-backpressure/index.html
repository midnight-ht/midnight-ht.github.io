Respect writable backpressure before sending more chunks

When write() returns false, stop initiating writes and resume on drain; it signals buffer pressure, not rejection or business completion.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-25 · Estimated read 15 min

Article

Key takeaways

  • Stop writing after false and resume on drain; do not resend the chunk already submitted.
  • highWaterMark is a type-specific backpressure threshold, not a hard process memory cap.
  • Local drain, remote receipt, and business acknowledgment are separate states; bound stalled work with deadlines or cancellation.

With Node.js 26.13.1, when a writable stream's write(chunk) returns false, stop initiating further writes and wait for that stream's drain event before resuming. The chunk just passed to write() has entered the writable's handling path; false signals buffer pressure, not rejection and not a request to resend. Ignoring the signal turns a speed mismatch between producer and consumer into a growing queue. This article covers Node.js Writable streams; third-party implementations may have different contracts, so check their documentation.

False describes the queue after this write

highWaterMark is the threshold at which a stream starts applying backpressure. The API contract says write() returns true while the internal write buffer is below the threshold and false once the buffer reaches or exceeds it. The check therefore occurs after the current chunk enters the queue. Imagine a file reader producing 40 MB per second while a network destination can process only 5 MB per second. At first, the writer may get several true results before one false. That write has already been admitted; retrying the same chunk can duplicate it, while requesting the next chunk immediately makes the backlog grow faster.

After buffered data has progressed enough for writes to resume, the stream emits drain. “Handled” here has a local Writable meaning. For sockets, the documentation says the event follows the operating system accepting buffered data for delivery. That does not prove that the remote application read, validated, or persisted it, and it is not a business transaction acknowledgment. An upload interface that promises “saved” must wait for an application-level confirmation rather than treating drain as a receipt.

A callback passed to an individual write() is not a substitute for drain. It reports when that chunk has been flushed by the underlying implementation and can receive an error; the boolean lets the producer stop adding work as soon as the queue reaches its threshold. Serializing behind every callback can be a more conservative policy, but it changes concurrency and throughput. That is not the same signal as backpressure, and callback completion is not remote confirmation either.

The threshold is not a maximum chunk size. Since the check happens after the current write is admitted, a single chunk larger than highWaterMark is still accepted into the queue and then produces false. Nor does a later drain prevent that one input from causing a memory spike. A producer that can generate arbitrarily large Buffers or objects also needs a maximum chunk size and a bound on concurrent unfinished work.

Make the producer actually pause

With manual writes, continue requesting chunks only while write() returns true. When it returns false, register one resume wait and continue after the event. The following illustrates the control relationship; it is proposed code and was not executed for this article:

for await (const chunk of source) {
  if (!writable.write(chunk)) {
    await once(writable, 'drain', { signal });
  }
}
writable.end();
await finished(writable);

While waiting, Node.js events.once() rejects its promise if the emitter produces an error, and an AbortSignal can cancel the wait. The short example still needs lifecycle handling appropriate to the stream: early close, destroying resources after cancellation, a deadline, and cleanup. If the source is still being read after the destination has ended, the task must not wait forever for an event that can no longer happen. Do not poll writableLength in a tight loop after false; busy waiting neither speeds up the destination nor yields the event loop.

Most source-transform-destination chains do not need a handwritten loop. The stream/promises pipeline() coordinates flow between stages and represents completion or failure as a Promise. The same versioned docs also show passing an AbortSignal as an option; cancellation destroys the underlying streams in the pipeline. Prefer this orchestration API when it fits, then focus on whether cancellation reaches the right work, what happens to partial output, and who reports the error. A manual producer is justified when the application must control each fetch, implement a queue policy, or maintain business state, but it also takes on more lifecycle rules.

A threshold is not a memory limit

highWaterMark does not generally impose a hard limit on total process memory. Normal byte streams count bytes; object-mode streams count objects; undecoded string streams count UTF-16 code units. Ten objects might be ten short records or ten references to large buffers, so object count is not a byte estimate. Duplex and Transform streams have independent readable and writable buffers. Application batches, retry queues, and closure references can retain still more data.

Consider a hypothetical export pipeline with a file reader, a compression Transform, and a socket destination. Every stage may hold data, while the application separately keeps records awaiting server acknowledgment. Adding the highWaterMark values gives only a rough queue estimate; it cannot prove an RSS ceiling. Nor does “the system uses streams” establish constant memory. First identify the maximum chunk size, the buffer units allowed at each stage, concurrent work, and whether acknowledgment queues are bounded. If the receiver stops reading, a TCP socket may not emit drain for a long time. That wait prevents more writes but can still hold the request and upstream resources indefinitely. Backpressure therefore belongs with deadlines, cancellation, and resource cleanup.

What would verify the behavior?

Test by changing consumer speed rather than checking only that a file was produced. A proposed test could use a custom Writable with controllable delay and record each write, the point at which false appears, drain events, and writableLength. Slow the consumer and verify that the producer stops requesting chunks, then continues after drain. Also make the consumer reject data, close the destination early, and trigger an AbortSignal; verify that the task ends with an error or cancellation, stops pulling input, and leaves no promise waiting for drain. This is a test plan, not an experiment performed here; no memory or throughput results are claimed.

Keep local stream state separate from business confirmation. Let a test drain normally while a mock server withholds its acknowledgment: the interface must not report a completed save. Conversely, if an acknowledgment is lost and the client retries, an idempotency key or business protocol must prevent duplicate submission. Use writableLength, writableNeedDrain, paused duration, and cancellation reasons to diagnose local queues, but do not rely on buffer fields the documentation labels as internal implementation details. The right threshold depends on object size, stage count, destination speed, and acceptable latency. Raising it may reduce pause frequency while allowing more data to wait. Start by ensuring the pause signal travels from the destination back to the producer.

If the separate problem is decoding a UTF-8 character split between network chunks, see preserving decoder state across chunks. Character decoding and writable backpressure are different stages of a data path.
