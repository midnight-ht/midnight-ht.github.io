Make the container entrypoint hand off signals deliberately

Trace the container's main process and signal recipient before evaluating wrapper behavior, application shutdown, and orchestrator grace periods.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-25 · Estimated read 22 min
Translations
zh-CN en

Article

Key takeaways

  • docker stop targets the container's main process; the entrypoint process tree determines whether the application receives the signal directly.
  • exec replaces a wrapper with the application but does not implement graceful shutdown on the application's behalf.
  • Docker's stop timeout and Kubernetes' termination grace period are waiting budgets; neither repairs a broken process tree.

A container receives SIGTERM, but the service has no shutdown log. Inspect the process tree before increasing the grace period. Three separate questions need answers: which process the runtime signals, whether the application stops admission and finishes its work, and how long the platform waits. Mixing them often produces a larger timeout while requests or jobs still fail to drain.

First identify the signal recipient

Dockerfiles support exec and shell forms for ENTRYPOINT. The Docker ENTRYPOINT reference documents exec form as a JSON array, such as ENTRYPOINT ["node", "server.js"]; shell form is a command string. Docker's reference says a shell-form ENTRYPOINT starts the command as a subcommand of /bin/sh -c, and that shell does not pass signals to the target executable. Therefore a SIGTERM sent by docker stop to the container's main process does not establish that the application received it. Inspect the actual launch structure instead of inferring delivery from the fact that a stop request began.

Read ENTRYPOINT and CMD together. An exec-form ENTRYPOINT can receive arguments appended by CMD or docker run; a shell-form ENTRYPOINT ignores those command-line arguments. If an exec-form entrypoint is paired with a shell-form CMD, Docker wraps CMD in a shell invocation, so the entrypoint may receive different arguments from the bare command and parameters you expected. Exec form also does not invoke a shell automatically: variable expansion such as $HOME does not happen by itself. If shell syntax is required, call a shell explicitly and include that process in the design and diagnostic record.

Runtime configuration can override the image defaults. A local run may use the image's default command while a cluster supplies command or args; inspecting only the Dockerfile then does not reveal the final process tree. Record at least the image ENTRYPOINT/CMD, runtime overrides, container PID/PPID relationships, and the service's children. The claims here concern Linux container behavior in the cited documentation; verify other runtimes, operating systems, and platform configurations against their own specifications.

exec transfers process ownership, not cleanup behavior

A wrapper is not inherently wrong. It may check a mount, render configuration, set permissions, or validate a key before starting the service. The important decision is how it hands the long-running process responsibility over. If a script simply runs node server.js and waits, a shell or script may remain in front of the application; whether signals are forwarded depends on the actual process relationship and wrapper behavior. Changing the final step to exec node server.js replaces the wrapper process with the application. If the wrapper was the container main process and no init sits in front, the application becomes the recipient at that PID. With --init, the signal reaches init first and is then forwarded. Docker's exec-form ENTRYPOINT specifies the container entry executable directly.

That handoff has a concrete tradeoff: after exec, the original script no longer runs as the parent. If it was expected to remove temporary files, collect an exit code, or perform compensation after the application exits, that code will not continue after replacement. When post-exit supervision is necessary, use a supervisor that correctly forwards signals, waits for children, and reaps them, or move safe cleanup to an external lifecycle mechanism. Do not assume both that the wrapper has been replaced and that it will later resume parent-process work.

Consider a hypothetical image that reads a template from a read-only mount, renders a runtime configuration, and then launches a Node API. If rendering fails, the entrypoint should exit nonzero rather than start a service with stale configuration. If rendering succeeds and the API is the only long-running process, the script may hand off with exec. If the application also starts workers, determine whether it forwards termination, waits for each worker, and handles unacknowledged work on exit. This is a design example, not an image built or run for this article.

PID 1 and child processes are separate concerns

Putting the application in the PID 1 position addresses which process runs as the container's main process. It does not prove that the application handles signals, exit status, or children correctly. Linux gives PID 1 special signal and orphan-adoption semantics; relying on a default signal action may behave differently from relying on an ordinary process. A process can handle SIGTERM and begin closing without forwarding it to every worker or waiting for them. Verify those behaviors against the application's process model.

When a container genuinely needs to manage multiple processes, Docker's --init option can provide a lightweight init process. The Docker run reference says it runs an init process in the container and performs responsibilities such as forwarding signals and reaping processes. That can address some PID 1 and zombie-reaping concerns, but it does not define how the application closes database transactions, acknowledges queue messages, or stops HTTP admission. A dedicated supervisor is another option, but it adds a lifecycle component that must be configured, observed, and tested. Choose based on explicit parent/child relationships, signal propagation, and exit-waiting responsibilities—not a blanket rule that multiple processes are always wrong.

A counterexample is changing a single service command to exec, seeing the main process receive SIGTERM, and declaring shutdown fixed. The service might exit immediately during a request, a queue consumer might acknowledge a message too early, or workers might still be killed forcibly. Signal delivery passed; business draining did not. Design separate process-level checks (signal, state, exit status) and business-level checks (stop admission, finish in-flight work, acknowledge or make messages retryable).

A longer timeout cannot repair a missing signal path

The Docker container stop reference says docker stop sends a stop signal to the container's main process, waits for its configured grace period, and then sends SIGKILL if the deadline expires. The stop signal and timeout can be changed through STOPSIGNAL or runtime options. A longer timeout gives more time only to a process that received the signal and is shutting down. If the application never received it, it may continue working until it is forcibly ended. Establish the recipient and process path first, then estimate the budget from actual shutdown work.

Kubernetes adds an orchestration layer. The Pod termination flow says a configured preStop hook must finish before TERM is sent, while the grace-period countdown starts before the hook; the documented default is 30 seconds. In the default path, the kubelet asks the runtime to send TERM to each container's PID 1, and force termination follows when the grace period expires. An image STOPSIGNAL, runtime behavior, or a version- and feature-gate-dependent lifecycle stopSignal can change the signal actually used; verify the cluster conditions. For multiple ordinary containers, stop requests are processed asynchronously and their order is not fixed. Kubernetes gives declared sidecar containers special termination handling: they receive their stop signal only after main containers have terminated, in reverse definition order. A component merely called a sidecar in team terminology does not prove that this lifecycle semantic is in use. Hooks and total budgets can help drain traffic, but cannot bypass an entrypoint shell or make an application with no graceful-shutdown behavior correct.

Choose between a hook and in-process shutdown logic based on side effects and coordination boundaries. A preStop hook can trigger externally visible preparation, such as making an instance unready, but it is not an unlimited cleanup window. After receiving the signal, the application still needs to close listeners, drain requests, and stop workers. If the hook and application each wait for the same action, both periods consume one grace budget. Write a timeline: hook execution, readiness propagation, application draining, and process exit each have a possible duration. Leave room for variation instead of allocating the full budget repeatedly to each step.

Verify each responsibility separately

The Kubernetes container lifecycle hook reference also makes clear that preStop and normal shutdown share one grace period: a long hook leaves less time after TERM. The following is a proposed test plan, not a test performed on this machine or in production. In a controlled environment, start the same command as the target image and record the process tree and entrypoint arguments. Trigger termination once while idle and once with work in flight. Record signal arrival, whether new requests stop, how current work completes, the exit code, and total duration. Also simulate configuration-render failure and cancellation after startup; verify failure is not reported as a successful launch and that no worker is orphaned. Observe signal logs or process state rather than relying only on an orchestrator's “terminating” status.

If only an idle container stops cleanly, the business-work path remains unknown. If Docker works but Kubernetes does not, inspect command/args overrides, preStop duration, readiness changes, and the grace period before rewriting the entrypoint again. If the process received SIGTERM but timed out, examine application shutdown and the resources it is waiting on. If the parent exits while workers remain, revisit process management or the init/supervisor choice. Each observation supports only its own layer; one passing test cannot certify the entire container lifecycle.

Only after those observations should you decide whether to increase Docker's stop timeout or Kubernetes' terminationGracePeriodSeconds. Tie any added budget to the measured work item and upper bound, and verify that the deployed platform actually applies the setting. Rolling-update draining also depends on platform state transitions; see Kubernetes termination budgets. No Docker or Kubernetes experiment was executed for this article, and no logs, exit times, or production incident are claimed. The deliverable can be a process diagram and shutdown acceptance table: who receives the signal, who owns each child, who waits for which work, and who enforces the final deadline.
