Network Chunks Split Chinese Characters: Where Should You Handle It?

Preserve split UTF-8 characters with a stateful decoder, then frame messages by protocol; correct decoding still does not complete a record.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-25 · Estimated read 17 min
Translations
zh-CN en

Article

Key takeaways

  • A byte chunk is not a character boundary; StringDecoder or Readable.setEncoding preserves UTF-8 state across chunks.
  • Decoding and framing are separate steps: parse delimiters or length fields and bound unfinished records.
  • At EOF, handle decoder residue and an unterminated final message separately; a replacement character does not recover the original text.

Network reads give an application arbitrary byte chunks, not complete characters or business messages. For UTF-8, Node.js StringDecoder or a Readable configured with setEncoding('utf8') can preserve character-decoding state across chunks. Delimiters, length prefixes, JSON documents, and other record boundaries still belong to the protocol parser. Decoding answers how bytes form text; it does not answer where a message ends.

Why one Buffer.toString() call can split a character

UTF-8 characters use one to four bytes, while read boundaries depend on buffers, the network, and scheduling. They do not align with character boundaries. Suppose the three bytes of one character arrive in three separate Buffers. Calling toString('utf8') on each Buffer independently gives the first call no state in which to wait for the missing bytes. The result can contain a replacement character, and the later chunks do not automatically repair it. Code must not assume that one data event represents a complete piece of text.

The Node.js v26.13.1 node:string_decoder documentation says StringDecoder.write() retains bytes at the end of a Buffer that do not yet make a complete multibyte character, then waits for another write() or end(). Its example writes the three UTF-8 bytes of the euro sign in three operations and emits the character on the final end() call. stringDecoder.end() also handles residue: if the remaining bytes still cannot form a valid character, the encoding rules produce a replacement character. This preserves a temporarily split character in continuous input; it cannot recover bytes that were lost, reordered, or declared invalid by the protocol.

This is not specific to Chinese. Other non-ASCII UTF-8 characters and UTF-16 code units can cross chunk boundaries too; check the Node documentation for the encodings a particular decoder supports. The snippet below illustrates state handoff only. It was not run in a deployment environment or on a real socket:

const { StringDecoder } = require('node:string_decoder');
const decoder = new StringDecoder('utf8');

const pieces = [Buffer.from([0xE4]), Buffer.from([0xBD]), Buffer.from([0xA0])];
let text = '';
for (const piece of pieces) text += decoder.write(piece);
text += decoder.end();
// Under UTF-8 these bytes together encode “你”. This is an explanatory snippet, not executed.

The important property is not how the three chunks were split. One logical input must keep using the same decoder state. Creating a new StringDecoder in every callback does not let residue meet the next chunk. Sharing one decoder across unrelated connections can let connection A’s residue enter connection B. Usually the decoder lifetime should match one continuous byte stream, with an explicit policy to finish or discard state on end, cancellation, or error.

Choosing setEncoding or StringDecoder

If you consume a Node.js Readable and want later listeners to receive strings rather than Buffers, call readable.setEncoding('utf8') before reading data. The Node.js v26.13.1 Stream documentation states that a Readable properly handles multibyte characters delivered across chunks. After setting an encoding, data events carry strings; without it they generally carry Buffers. This keeps character decoding inside the stream, which suits consumers whose next processing step is text.

If the application needs raw Buffers, wants to place decoding explicitly among Transform streams, or maintains its own message parser, StringDecoder lets the application decide when to call write() and end(). Neither option replaces message framing or validates that the peer used the protocol’s required encoding. If the protocol requires UTF-8, use UTF-8 and define how invalid input is handled. Cycling through encodings until text “looks right” cannot prove that the bytes were interpreted losslessly.

Another choice is whether to keep bytes or convert to text early. A length field measured in bytes must be parsed and sliced before decoding. If the protocol measures length in characters, decode according to its rule first and verify what “character” means there: a Unicode code point, a UTF-16 code unit, or another unit. Otherwise a multibyte string can shift the boundary. A decoder maps bytes to text; it cannot define the protocol’s length unit.

Decoding needs a separate framing state machine

For newline-delimited text, append decoded output to a pending buffer, repeatedly extract every complete \n line, and retain the unterminated tail for the next decoder output. A Buffer can contain part of a line or several lines. Decoder output is not equivalent to a record. Passing each output directly to a JSON parser can split a record that spans reads or merge records that happen to share a chunk.

The framing layer must also define how it handles \r\n versus \n, whether the delimiter belongs to the record, and what happens if pending remains at end of input. The protocol determines whether a final line without a newline is valid. Stream end alone does not authorize adding a delimiter and sending a partial business message downstream.

Bound the buffer too. A peer that never sends a delimiter can make the unfinished tail consume more memory over time. Set a protocol-level maximum message byte size or text length, then reject, close, or enter an explicit error path when it is exceeded. For user-supplied data, parsing, authorization, and validation still follow. Document the unit used for the bound; pending.length is not an exact count of input bytes.

Handle EOF, errors, and cleanup as separate decisions

At a normal stream end, pass the final bytes to decoder.end(), send any returned text through the framing layer, and then ask whether the framing tail is a valid record. The first decision concerns character validity; the second concerns message completeness. If the decoder emits a replacement character, the text input may have ended in an incomplete character or contained invalid bytes. If the decoder ends normally but pending still contains text, the protocol may define that as an unterminated record. These are different failures with different remedies.

For example, a client consuming sensor text lines can keep one decoder and one line buffer per connection. It validates fields only after a complete line is found. If a connection resets, it records decoder residue and unfinished line length separately, then applies the protocol’s retry, discard, or error policy. A retry on a new connection must not reuse the old connection’s partial character or line; otherwise valid new bytes could be joined with stale residue to create a false record. This is a design example, not a report from a real device or customer system.

How to validate without treating “no exception” as success

Construct the same valid UTF-8 text with different chunk boundaries: split a multibyte character at each byte; split a newline record across reads; place multiple records in one chunk; end after a complete character but before the record delimiter; and end halfway through a character. Compare the decoded text and final record sequence across chunkings, and assert separately the chosen policies for an incomplete character and incomplete message. Add an overlong input with no delimiter to ensure the buffer limit triggers its intended handling instead of growing without bound.

Logs should distinguish input byte count, decoded text length, committed record count, and rejection reason. Seeing a replacement character does not reveal by itself whether bytes were truncated in transit, the encoding declaration was wrong, or the sender supplied invalid bytes. Absence of an exception does not prove that record boundaries were correct. This article proposes checks but did not run a network experiment or the code snippet, so it cannot claim a Node version or protocol has passed acceptance. After input decoding and framing, the output side still needs to respect write backpressure; see the conditions for continuing a writable stream.
