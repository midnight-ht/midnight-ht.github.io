Does changing a password sign out other devices? Verify server-side revocation

Password updates do not prove other sessions are revoked. Distinguish routine reset from suspected compromise and verify server-side rejection.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-25 · Estimated read 19 min
Translations

Article

Key takeaways

  • A new password does not automatically revoke other devices; clearing a browser cookie cannot revoke a server token copied elsewhere.
  • For suspected compromise, review recovery methods, MFA, active sessions, and unused recovery credentials.
  • Identity-provider sessions, application sessions, access tokens, and refresh tokens may have separate lifetimes; acceptance must verify server-side rejection.

Not necessarily. Changing a password means future password verification uses the new credential. Whether another device’s existing session stops working depends on whether the server revokes that session or token. Updating a password, rotating the current session ID, and revoking every active session under an account are three different operations. Ordinary forgotten-password recovery and suspected account compromise also need different policies.

“Password changed” is a result in the credential store; “other devices are signed out” is a result in server-side session state. A recovery flow may trigger both, but one does not automatically follow from the other. If the interface combines them into one success message, a user cannot tell whether an attacker may still be using a copied credential. If developers test only whether the new password works, they may miss continued access from another device.

Separate three state changes that look alike

The first change is replacing the password credential. The server stores new verification material, and later password authentication uses it. Unless the application separately checks and revokes sessions, changing a password record does not rewrite an existing browser cookie, a mobile client’s refresh token, or session state already cached by an application server.

The second change is rotating the current session ID. OWASP’s Session Management Cheat Sheet recommends renewing the current session ID after privilege changes such as password changes and destroying the old ID. This reduces the risk of reusing an old identifier after a privilege transition and addresses session fixation. It only means that the current authentication context received a new identifier. It does not prove that sessions on other devices, access tokens at another service, or a single sign-on session were revoked.

The third change is cross-device revocation. The server makes other sessions invalid based on the account, session identifier, or token version, so later requests are rejected. Clearing a browser cookie removes the browser’s copy; a copied value may still exist elsewhere. If an API continues to accept an old token server-side even when the browser shows a logged-out screen, access has not actually ended. OWASP likewise states that session expiration and logout need an active server-side invalidation action.

Ordinary resets differ from suspected compromise

For an ordinary forgotten-password reset, OWASP’s guide allows the product to ask whether existing sessions should be invalidated or to invalidate them automatically. After a new password is set, it recommends that the user sign in through the normal mechanism instead of being logged in automatically. This leaves a product choice that should be explained: preserving other devices may be convenient after an ordinary reset, while the product may choose a documented policy that signs all devices out. In either case, the server must carry it out.

Suspected compromise is a different flow. An attacker may retain an active session or have changed the email, phone number, or MFA methods. Accepting a new password does not prove that control has been restored. OWASP advises against relying only on recently added or changed recovery details. Review recovery methods with the verified account owner, remove unauthorized changes, invalidate existing sessions and unused password-reset or recovery links and codes, and notify channels that remain trustworthy. NIST SP 800-63B-4 distinguishes replacing a forgotten password while another authenticator remains available from account recovery after losing required authenticators; in its applicable credential service provider (CSP) context, an account recovery event triggers notification.

A hypothetical sequence makes the policy split concrete. The user receives a legitimate recovery message and resets the password on device A while device B still has the account open. For ordinary recovery, continued access on B may match the product’s policy; the interface should say so and let the user inspect or end other sessions. If the reset follows suspicious activity on B, the flow should become suspected-compromise recovery: verify recovery evidence that was not replaced by the attacker, review MFA and contact methods, revoke other sessions and outstanding recovery links, and notify a trusted address. This is an illustrative reading of the guidance, not an account incident observed by this site or a test of any product.

Token types and architecture define revocation boundaries

An application with server-side sessions can store an account identifier, session state, and revocation state for each session. “Sign out other devices” can mark every session except the current one as invalid. Another engineering pattern is an account authentication version or epoch: each request compares the version in a credential with the current account version. A per-session registry supports individual review and revocation but depends on session storage availability and consistency across nodes. An account-wide version makes broad invalidation simpler, but it can make ordinary password changes and suspected compromise produce the same wide logout. These keys, persistence choices, and transaction boundaries are design options; OWASP and NIST do not mandate one particular table schema.

Self-contained access tokens create another boundary. If a resource service checks only a signature and local expiration time, an access token may continue to be accepted until it expires even after the password changes. Early revocation needs a mechanism on the request path, such as a token-version lookup or a revocation record; that adds a state dependency and requires a defined cache-update delay. Refresh tokens may have their own records and rotation rules, and revoking the ability to refresh may not immediately stop an access token already issued. NIST specifically notes that access tokens and associated refresh tokens can remain valid after the authentication session has ended, so each credential type needs a separate check.

Single sign-on divides the boundary further. NIST says an identity provider (IdP) and a relying party (RP) manage separate sessions; the protocol does not automatically connect their session lifetimes. Revoking an application’s local session does not necessarily end the IdP session. Ending the IdP session may not immediately remove an RP session already established. If the interface claims “sign out all devices” or “revoke everything,” it should state which systems are included and verify revocation at every server that accepts the credential.

Distributed deployments also have a failure path. Imagine a revocation request is written to a primary store and then propagated to application nodes through an event. A node that still reads an old cached version might accept the credential for a while. The user sees “all devices signed out,” while one API continues accepting the old value until its cache refreshes. This is a design-review scenario, not an observed failure. It means the system needs a completion condition: is a successful write enough, or must critical validation nodes confirm? If some nodes cannot be reached, should the interface say “processing” or disclose that revocation is not yet confirmed? Logs can record session creation, change, revocation result, and time for investigation, but should exclude raw session IDs, passwords, one-time codes, and recovery links. Use a controlled correlation identifier instead.

Turn the policy into an acceptance contract

The recovery contract should distinguish at least these objects: the current password credential; the current device’s session; sessions on other devices; unused recovery links or codes; MFA and recovery addresses; access and refresh tokens; and IdP and RP sessions. It should also state whether an ordinary reset asks the user, which objects are forcibly revoked after suspected compromise, where notifications go, when the server considers revocation complete, and who handles partial failure. One vague “password reset succeeded” message should not stand in for every state transition.

A proposed acceptance plan keeps devices A and B signed in, performs an ordinary reset on A, and checks whether B remains or is rejected according to the documented choice. Then simulate suspected compromise and verify that B’s server requests, old reset links, MFA recovery data, and refresh-token path follow the stronger policy. With federation, check the IdP and application separately. Inspect real rejection from protected APIs, behavior during cache propagation, notification records, and an explainable failure state when a service is unavailable. These tests were not run, and no identity service is claimed to have been validated; a team should execute them against its actual framework, token types, and deployment topology before release.

So there is no universal answer to whether old sessions expire after a password change. Start by classifying routine credential replacement versus suspected compromise; then identify who validates each session and token, how revocation works, and when it takes effect. For the broader credential lifecycle, see rotation and revocation of old credentials; account recovery must also cover identity recovery and session lifetimes.
