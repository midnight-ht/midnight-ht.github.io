When should a Playwright test use first() after matching two buttons?

A strictness error means a single-target action has no unique identity. Anchor the button to its record; use an ordered choice only when the requirement names that order.

Updated 2026-11-25 · Estimated read 18 min
Translations

Article

Key takeaways

  • Single-target actions fail on multiple matches, while collection operations such as count() allow them; the error asks the test to identify its target.
  • Choose a control inside its identified business record; first() or nth() belongs only when the requirement specifies a defined order.
  • Auto-waiting checks when an element is actionable, not which record the test means to change; assert the resulting object as well.

When a Playwright single-target action matches two buttons, do not add first() automatically. The strictness error means the test has not identified the business object it intends to change. Identify a record such as an order, user, or conversation before narrowing to its control. A positional choice is justified only when the first item in the current ordering is itself the behavior under test. Even after a click succeeds, assert that the expected record changed.

Strictness refuses to guess

Playwright's locator guide describes a locator as a way to find elements on a page. An operation such as click() that requires one DOM target throws when several elements match. Collection operations such as count() can accept multiple matches. first(), last(), and nth() explicitly select a position, and the documentation warns that a page change can make that position refer to an unintended element. Strictness does not require every button on a page to be globally unique, nor does it reject every multi-element query. It stops code from silently guessing an identity before a write action.

Imagine an order list with six rows, each containing a Cancel button. If getByRole('button', { name: 'Cancel' }).click() matches several controls, the useful question is not “How do I make it pass?” but “Which order is the test cancelling?” If the target is order A-204, identify that row first, then find its Cancel button. Readers can review the test's intent, and a change in order does not quietly change the target. This order scenario is hypothetical: no business page was exercised for this article, and it does not allege that a real order was cancelled.

Adding first() to the global locator records DOM order, not business identity. Today the first button may belong to A-204. Tomorrow a pinned pending order, a shortcut in an alert, or a filtered result can appear before it. The locator then points to another record. The risk is not merely a brittle test. The test may remain green while operating on the wrong object. Strictness turns that possible false pass into a diagnostic failure earlier in the flow.

Identify the business region before the control

Reliable targeting has two levels: identify the record outside, then identify the action inside. If each row has meaningful record text or accessible semantics, use getByRole() to select the row, narrow it with filter({ hasText: 'Order A-204' }) or filter({ has: ... }) around a unique child, and find the button inside that region. Playwright documents locator.filter() as added in v1.22 and shows filtering by text or descendant. Its API also requires the outer and inner locators to belong to the same frame. If a project runs an older version, check the installed API before copying this syntax and use a scoping method supported there. Verify the filter actually distinguishes a record: an order summary might appear in both a desktop table and mobile card, or a row could contain the same identifier for an original order and a refund.

This can reveal a page semantics problem. Several Cancel buttons may each have an appropriate name; what is missing is a recognizable order region around them. If a user cannot tell which row owns a button, the product may need a row heading, relationship text, or accessible name that conveys the association. A data-testid can provide a deliberate engineering contract when role or text is insufficient, but it should not conceal ambiguity that users also face. Playwright recommends locators close to how a user perceives the page; test IDs are an explicit supplement when that user-facing contract is not the right one for the test.

The outer filter can still be ambiguous. filter({ hasText: 'Pending' }) may return three rows, leaving three inner buttons. Do not keep adding selector fragments until the count happens to be one. Find a field that genuinely identifies the business object and confirm the page exposes it. Stable targeting encodes identity; it does not hide a mistake in a longer CSS or XPath chain.

When is first() itself the right test expression?

If the product requirement really is “process the first task after this ordering,” first() or nth(0) can express it, provided the ordering and set are verifiable product contracts rather than incidental DOM order. Define the sort field, direction, filtering scope, and tie-breaking behavior, then establish that the list contains only eligible tasks. “The first result” is a business meaning only when the ordering contract is explicit; it otherwise describes an implementation detail.

A reviewable test might load pending tasks in descending creation time, confirm the unique identifier of the first row, click the action in that row, and assert that the task bearing that identifier changed state. Applying first() to a global button collection does not validate the filtering or ordering, and it gives no reason the target remains correct if the page changes. nth(2) similarly means the third matching element because the index is zero-based. Unless “third” is part of the requirement, it hard-codes today's layout.

An ordinal can also fit an ordered, controlled finite set, such as a test for fixed navigation order. It is a poor fit when data ordering is unspecified, asynchronous insertion is possible, pagination appends items, or virtual scrolling recycles nodes. Before selecting by position, answer: what is the set, who guarantees its order, and how should the test behave if the list changes? If those questions have no concrete answer, return to identity-based scoping.

Identity and auto-waiting are different failures

Playwright's auto-waiting checks that a locator resolves to one element before click(), then checks visibility, stability, event reception, enabled state, and that the element is not inert. It waits until those conditions pass or the timeout expires. Those checks answer whether an already identified element can be clicked now. They do not answer which order the test intends to select. Doubling timeout can wait for one button to load; it cannot turn six Cancel buttons into one target.

Classify the failure by signal. A strictness error calls for inspecting the match count and which record each result represents. A timeout calls for examining visibility, animation, overlays, or enabled state. A click without a business outcome calls for checking the request, response, and target record state. Attributing all three to a “slow page” misses identity errors; using force can skip some actionability checks, including whether the target receives events. The related guide to automatic waiting and assertion conditions explains when to wait for an outcome, but it does not choose the object for the test.

Verify who changed after the action

A useful acceptance sequence has four observable steps: establish the initial collection and ordering; find the target region by a stable business identity; perform its local action; then confirm through the page or a trusted test interface that the expected object changed and neighboring objects did not. For “cancel order,” an exception-free click proves only that the action call completed. A-204 changing to cancelled proves which result object changed; A-205 remaining pending can expose a bad locator's side effect.

Coverage can include an empty list, duplicate-looking records, insertion after filtering, tied sort values, a slow response, and a mobile layout. These probe no target, repeated identity, asynchronous insertion, ordering assumptions, actionability, and region stability. This is a proposed verification plan, not a Playwright test result that has been run. When implementing it, record the browser version, data fixture, filter, and ordering conditions so a failure can be reproduced. Revisit the locator when the page or API contract changes.

For dynamic collections, wait for a business-meaningful state and then use a locator or a retrying assertion to check the intended target. Do not use a one-time all() snapshot or fixed sleep as a substitute for readiness. The official Locator API notes that all() does not wait for matches and can be unpredictable for a changing list. A count assertion can check collection size but cannot establish each item's identity. A sound acceptance combines a justified scope, an identifiable object, satisfied actionability, and a result attributed to that object.

The conclusion is not “never use first().” If ordering is a product contract, it is an honest positional expression. If it merely makes a strictness error disappear, it hands unknown intent to DOM order. First answer which record the test should affect, then choose its scope, and verify that business object after the click. Failures can then distinguish identity, waiting, and outcome instead of allowing a green test to conceal the wrong target.
