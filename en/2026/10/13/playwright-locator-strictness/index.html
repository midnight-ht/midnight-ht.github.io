Resolve locator ambiguity before choosing the first match

Resolve locator identity and scope before relying on positional selection or longer waits.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-13 · Estimated read 5 min
Translations
zh-CN en

Article

When a Playwright operation matches several elements, clarify the target’s meaning and scope before adding first. Positional selection bypasses ambiguity without establishing that the selected control is the intended one. A test needs a stable expression of the user’s target.

Strictness concerns operations requiring one target

The Playwright locator documentation explains that single-target operations fail on multiple matches, while operations such as counting permit multiple elements. It provides first, last, and nth as explicit opt-outs but warns that page changes can make them target an unintended element. Not every multiple-element query fails.

Imagine an order page with several Delete buttons. Finding the button by name alone omits the order identity. Adding first may pass with today’s layout, but sorting or inserting another card can change which order occupies that position. This hypothetical scenario was not clicked through, and no actual deletion is alleged.

A more precise locator can identify the business card or region before finding the named button within it. That region must itself be unambiguous. Moving ambiguity to a repeated container is not a repair. Stable targeting depends on page semantics and an agreed record-identity contract.

Position can be a legitimate requirement

If the requirement is to select the first result under a defined ordering, position belongs in the test. Confirm the sort and result set as well. A business-defined first result differs from whichever element happens to appear first.

Labels, headings, and roles can narrow repeated areas, but do not distort user-facing meaning for test convenience. Missing identity may require a product and interface decision. Test identifiers can supplement a contract without concealing ambiguity that users also face.

Separate identity from waiting

Automatic waiting addresses when a target becomes actionable, not which business object is intended. More time will not make two identically named buttons become one. Inspect the match set and records before blaming loading or animation.

A proposed review covers sorting, repeated regions, empty results, and insertion, checking which object actually changed. These are not executed stability results, and one successful run would not guarantee every future layout. See automatic waiting and assertion conditions once the intended target is clear.
