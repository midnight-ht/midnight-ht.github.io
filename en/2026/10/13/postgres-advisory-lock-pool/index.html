When does a PostgreSQL advisory lock release through a connection pool?

A session advisory lock ends on explicit release or backend-session termination, not on rollback or pool release. Choose transaction scope or pinned-session ownership and test the actual pool mode.

Key takeaways

  • A session-level advisory lock ends on explicit release or backend-session termination; rollback and returning an application connection do not prove release.
  • A transaction lock fits short work inside one transaction; a session lock spanning transactions needs one pinned, observable backend session.
  • Test rollback, repeated acquisition, matching release counts, wrong-session cleanup, cancellation, reconnect, and the actual proxy mode; label proposed tests as unexecuted.

The release point depends on whether you take a transaction-level or session-level advisory lock, and on what your pool actually reuses. A session-level lock ends only after an explicit release or when the backend session ends. Rolling back a transaction does not clean it up. Returning an application connection to a pool does not necessarily close the backend session. If a lock outlives the code that borrowed the connection, the next borrower may inherit a session that still owns it.

Does a rollback immediately hand the advisory lock to another task?

No, if the lock is session-level. The PostgreSQL 19 explicit-locking documentation distinguishes session and transaction scopes: a session lock remains until explicitly released or the session ends, while a transaction lock is released automatically when the current transaction ends. Session-lock acquisition and release do not follow rollback semantics, so “the rollback succeeded” is not evidence that “the lock was released.” PostgreSQL 18 documents the same boundary. This article checks the current PostgreSQL 19 documentation; deployments on other versions should still consult the matching version.

The following three-task sequence is hypothetical, not an executed reproduction. Task A borrows backend session S from an application pool and calls pg_advisory_lock for resource key K. A database write then fails. A rolls back and returns its client connection, but the pool keeps S alive. The session lock is still owned by S. Task B later borrows that same backend session and requests K again. If the backend session already owns K, PostgreSQL allows it to acquire the lock again; the call can succeed even when another session is waiting. Task C, requesting K from a different session, still waits. If B interprets “the call returned successfully” as “I have exclusive ownership now,” it can mistakenly assume mutual exclusion between application tasks even though PostgreSQL sees one reentrant backend session.

A repeated acquisition is not an idempotent no-op. Successful session-level requests stack on one session; every acquisition needs a corresponding pg_advisory_unlock before the lock is fully released. If A acquired once and B acquired again, one release call by B leaves one acquisition outstanding. The release function returns a boolean that can confirm whether this call released a held lock layer. It cannot tell the application which business task owns that layer. Logs therefore need to connect the resource key, backend session, and acquisition/release count—not just request start and finish times.

Why is returning an application connection not the same as ending a session?

Connection pools are designed in part to reuse established connections. The application connection object may represent a temporary checkout lease; returning it can simply put its underlying connection back on a borrowable list. Pool implementation, reset queries, driver behavior, and proxy mode determine whether a PostgreSQL backend session persists and whether session state is cleared. “release ran” or “the finally block returned the connection” does not establish that the server disconnected.

Also distinguish a driver pool inside the application from a proxy in front of the database. For PgBouncer, the official features page says session pooling keeps one server connection assigned throughout a client connection, while transaction pooling assigns a server connection only during a transaction and returns it to the pool when the transaction ends. Its feature table marks session-level advisory locks as supported in session pooling and unsupported (“Never”) in transaction pooling. That is PgBouncer’s compatibility statement for its modes; it should not be generalized into a universal promise about every pool product. In transaction pooling, two client statements outside a transaction may even land on different backends, while a session lock remains attached to the backend that owns it. Whether the result is a retained lock, misuse, or session-mapping problem depends on the actual pool mode and reset configuration.

If code obtains a session lock in one pool query and releases it in a second independent query, the two leases may use different physical backend sessions. The first session can remain in the pool holding the lock; the second can attempt a release on a session that does not own it and receive a false result, leaving the original lock in place. In PgBouncer transaction pooling, clients cannot rely on session state outside the assigned transaction. A checkout token alone is not sufficient proof of lock ownership. Acquisition, protected work, and release must stay on the same deliberately owned backend session, and the application must verify that the pool does not remap it in between.

Should you choose a transaction lock or pin a database session?

Start by drawing the real boundary of the protected work. If all critical reads and writes fit into one short transaction, pg_advisory_xact_lock or pg_try_advisory_xact_lock is usually easier to maintain: acquisition, writes, commit, or rollback share a transaction, and the lock ends with it. The try variant returns immediately with success or failure, which lets a job choose to skip, queue, or retry later. Whether “could not acquire, so skip” is correct remains a business policy; the database does not decide that for you.

For a long task spanning multiple transactions, or one that waits on an external system, simply extending a database transaction is not a sound substitute. A long transaction prolongs lock ownership and resource use; a stalled network call can hold it open as well. If a single owner really must span transactions, one option is to pin a physical backend session for the entire operation, use a session-level lock, and guarantee that acquisition and release execute through that same session. After acquisition, the code needs a cleanup path. Exceptions, cancellation, timeouts, and process exit need release or connection-discard behavior that has actually been validated. Closing the database session releases the session lock, but whether an application pool or proxy closes that session must be proven from configuration and failure tests.

You can also evaluate a lease row in a business table or another coordination mechanism with an expiry. That design must separately handle an expired owner that is still running, a lost renewal, clock assumptions, and fencing tokens; it is not automatically safer than an advisory lock. Choose based on whether the protected interval can be reliably tied to one transaction or backend session, and whether you can prove an old worker cannot keep writing after failure. An advisory lock is an application convention: PostgreSQL does not force every path that changes a resource to acquire the same key first.

The lock key is part of that convention. PostgreSQL exposes advisory-lock functions with either one bigint key or two integer keys. Define a stable mapping and namespace so two modules do not interpret the same key as different resources, or produce different keys after a service version change. Do not assume an unanalysed string hash is a unique identity. If a hash mapping is used, record its algorithm, input normalization, and collision handling. Holding a lock only coordinates participants that follow the same key convention; it does not prove that a business permission check is correct.

How can you verify lock ownership through the pool?

A useful validation plan needs two distinct backend sessions and an observer. Have session A take a session-level lock for a test key. Cause a rollback inside A’s transaction, then inspect the lock state and ask another session to use a try-lock for the same key; verify that it still cannot acquire it. Call the release function on A one acquisition at a time, recording the boolean result and when the other session can proceed. Then have A acquire the key twice and release only once; verify that another session remains blocked. Run these steps in an isolated test database. This article has not executed those SQL statements and does not claim any observed output.

Next, run the same scenario through the application’s actual pool and proxy mode. Record the pool configuration, PgBouncer pool_mode, transaction boundary, and backend PID used by each operation. You can inspect advisory entries in pg_locks and correlate session identity with diagnostics such as pg_stat_activity; remember that the lock view does not automatically supply your application’s task name. Where appropriate, temporarily setting application_name or adding the business key to logs can help, but those labels must also be reset correctly when sessions are reused. Cover rollback, exceptions, request cancellation, pool return, backend reconnect, repeated acquisition, release on the wrong connection, and a change in proxy mode.

Keep three states separate in diagnosis: whether the business task is still running, whether its database transaction has ended, and whether a backend session still owns the key. A log saying “task finished” cannot prove the database lock ended. A successful SQL release cannot prove a remote side effect was undone. If a job sent a request to a message system or third party before releasing and the database later rolls back, PostgreSQL cannot roll back that external system. Retries still need an idempotency key, a way to query the remote result, or a compensation process. A retained pooled lock is primarily an ownership/lifetime mismatch; a wait cycle from inconsistent multi-resource lock order is a different problem. See deadlocks and lock acquisition order for that distinction.

The decision can be reduced to one check: does the database owner remain the same as the owner the business task assumes for the full protected interval? If the work fits in one transaction, use a transaction-level lock and keep the transaction short. If a session lock must span transactions, pin and observe the physical session, pair every acquisition with a release, and test pool and proxy failure paths. Until you can answer that ownership question, a longer timeout or a release statement at request end is not proof that mutual exclusion holds.
