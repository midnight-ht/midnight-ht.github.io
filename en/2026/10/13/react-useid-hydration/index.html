useId Is Not a Universal Key: Separate DOM Links, Data Identity, and Hydration Trees

Use React useId for accessibility relationships. List keys come from data, hydration requires matching trees, and multiple roots need coordinated identifierPrefix values.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-25 · Estimated read 19 min
Translations
zh-CN en

Article

React useId does not provide a universal identifier for every kind of identity problem. For example, a password input can point through aria-describedby to its help text; that value should not become an address-row key or a database primary key. It is useful for connecting related DOM elements inside a component. A list item still needs an identity from its data, and a business record needs its own key. With server rendering, the server and the browser must also produce the same initial React tree. Keeping these concerns separate makes it possible to diagnose the right failure.

Know which relationship receives the ID

The React useId reference describes IDs for accessibility attributes. For example, an input can use aria-describedby to point to the paragraph that explains what to enter. That is a page relationship: which help text belongs to this control? A component may appear more than once on the page, so a hard-coded string can make separate instances point at the same element. Calling useId at the top level of the component and using its value for both the input attribute and the paragraph gives each instance its own relationship.

import { useId } from 'react';

function PasswordField() {
  const hintId = useId();
  return (
    <>
      <label>
        Password
        <input type="password" aria-describedby={hintId} />
      </label>
      <p id={hintId}>Use a long phrase that you can remember.</p>
    </>
  );
}

This example shows one Hook call feeding two related elements. It does not write to a database or map a collection. The snippet is an explanation of the API, not code run in an application or with assistive technology. If the form also needs an error message, generate and connect the relevant IDs explicitly through the appropriate ARIA attributes. The string supplies the endpoints of a relationship; clear wording and the timing of an error announcement still need their own review.

The call site is part of the contract too. Like other Hooks, useId belongs at the top level of a component; it cannot be called conditionally or once per item from a loop. If a table needs a help ID on each address row, each row component can call the Hook once and pass the result to that row's input and help text. Putting the Hook in a map callback both violates the Hook call rules and conflates “which component owns this list item?” with “which DOM elements are related?” A row component is not needed merely to make strings look different. It gives each row a stable Hook call site while the record's data key continues to come from the address.

“Keep this row attached to the same record when items are inserted or reordered” is a different identity requirement. React's documentation says list keys should come from data rather than useId. If an address record has a stable address.id, that data identity should determine the list item's key. If the array index is used instead, an edit draft can follow a position and appear under another address after a reorder. useId cannot fill in a missing data contract and should not become an API or database primary key. The related article on React keys and draft reset boundaries discusses component state identity, rather than linking help text to a control.

How one tree lets server and browser agree

A server can send HTML first, after which the browser calls hydrateRoot to attach React to that markup. When the component tree has the same shape on both sides, React can generate corresponding useId values from the parent path of the component making each call. As the React documentation explains, this avoids relying on one global incrementing counter whose result could depend on client hydration order. Several client components may hydrate in a different order from the order in which the server emitted HTML; matching component paths can still identify the same calls.

There is a clear prerequisite: both sides must render the same tree initially. Suppose the server renders “heading, email field, help text, submit button,” while the browser, before calling hydrateRoot, checks window.matchMedia or local storage and inserts a notice panel before the email field. That extra sibling changes the path of later components. The fact that the email field still calls useId does not prove its generated value will match the one in the server HTML. The hydrateRoot reference requires the rendered content to match the server HTML and says React does not guarantee that every attribute difference will be patched.

When investigating a mismatch, first identify the input that changed the initial tree: browser-only state, a clock value, random output, user data that was not synchronized, or a capability check available only in the browser. A repair should make the server and browser use consistent initial data and structure, then update browser-specific state after hydration when the product requires it. Swapping to useId, suppressing a warning, or deleting an accessibility relationship does not repair the cause. A warning disappearing only tells you that the diagnostic output changed; it does not show that the relationship is correct or that users can still find the required content. This branch is a troubleshooting scenario, not a report of an executed React application or hydration log.

Multiple React roots need a prefix boundary

A page may mount separate React applications into separate DOM containers—for example, a billing panel and a support widget. Each tree can be internally consistent while the generated IDs still collide in the shared document. The useId reference explains that createRoot or hydrateRoot can receive an identifierPrefix so IDs from different applications use different prefixes. If a root was rendered on the server, the prefix used for that server render must match the one passed to the corresponding client hydrateRoot. With only one React root, this option is usually unnecessary.

The boundary is easier to reason about as a configuration table than as “add a prefix everywhere”:

Independent root  Server prefix  Client hydrateRoot prefix
Billing app       billing-       billing-
Support widget    support-       support-

Each row is a server/client pair. The prefixes differ between independent roots to distinguish their generated IDs; within a row they match so that root can hydrate with the same configuration. If only the server-side billing prefix changes while the browser keeps the default, the trees can be identical and the IDs can still diverge. This is a hypothetical configuration example, not a deployed or production-tested setup.

Review list keys, business IDs, and DOM IDs separately

A useful review can be carried out in four steps. First, render two password fields and verify that every aria-describedby target exists and points to that field's own help text, rather than checking only that the ID string is nonempty. Second, insert and reorder address records and verify that drafts follow stable data keys instead of array positions or generated DOM IDs. Third, compare the server HTML and the browser's initial render structure and data for an SSR route; test later updates after hydration separately. Fourth, if the page has several React roots, make sure their identifierPrefix values are distinct and that each server render uses the same value as its own hydrateRoot call.

The first check has two observable conditions: the attribute value resolves to an element in the current document, and that element's text is the help for this input rather than another field's explanation. With duplicate IDs, a query returning some matching element is not enough; the browser may return the first match and make an incorrect relationship look present. For an error message, also inspect when it is added and cleared and whether a user can locate the invalid field after submission. These checks do not require an ID to be a durable business value, but they do require the control, attribute, and target node to form a clear relationship in the current render.

This plan separates four failures: duplicate id attributes, a reference that targets the wrong element, data state attached to the wrong row, and a mismatch between the server and browser trees. Treating “the console has no warning” as the whole acceptance test can miss silent attribute differences and shifted business data. Conversely, a hydration warning does not by itself prove useId caused the problem; text, attributes, conditional branches, and initial data also deserve inspection. The React documentation navigation displayed v19.3 when it was checked. That records the label shown by the docs at that time; it does not establish which React version this site's project installs, nor does it promise that generated IDs are durable business identifiers across component lifetimes, list changes, or versions.

There is another boundary between a component and its data: derived state and Effects discusses who should own a value. Here, useId addresses which DOM elements refer to each other within a React tree. Generating a page ID does not establish record identity, guarantee matching tree structure, or prove hydration has passed.
