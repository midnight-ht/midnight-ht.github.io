Use React useId for accessibility relationships, not data identity

Use useId for accessibility relationships while preserving data identity and matching render trees.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-13 · Estimated read 6 min
Translations
zh-CN en

Article

React useId generates identifiers for accessibility relationships within components, such as connecting help text to an input. It is not a substitute for list keys or database identifiers. Server rendering also requires matching component trees on the server and client. These are distinct identity problems.

Page relationships and data identity differ

The React useId documentation warns against using it for list keys, which should come from data, and requires identical component trees for server rendering. Adding the API does not repair every hydration problem or make arbitrary conditional branches agree.

Imagine two address forms, each with help text. Distinct page identifiers let each input reference its own explanation. If an address list changes order, deciding which record remains the same address instead requires stable data identity. Correct accessibility references do not establish correct identity through reordering.

This helps clarify requirements. “The inputs must not conflict” concerns page identifiers, while “edits must stay with the original address” concerns record identity. Calling both a unique number can conceal the difference.

Matching trees are a prerequisite

Different data, times, or environment checks can make the server and client render different structures. Investigate those inputs instead of merely changing identifier generation. Establish which inputs are shared at initial rendering and when browser-specific information can be read. These are diagnostic suggestions; no application hydration repair was executed here.

Removing help text or relationship attributes just to silence a warning can discard the original accessibility requirement. A quieter console does not prove the field remains understandable or its association remains available to assistive technology.

Verify distinct responsibilities

A proposed review checks identifier collisions, input-description references, and preservation of the correct data’s state during insertion, deletion, or reordering. Server-rendered applications also need initial-render and takeover consistency checks. Absence of console warnings does not cover all these responsibilities.

Do not export generated page identifiers as long-lived business credentials. Backend interfaces, exports, and test selectors need their own identity contracts rather than depending on a component’s current tree position. No cross-version numbering guarantee is claimed. See derived-state boundaries for the connection between component state and its data source.
