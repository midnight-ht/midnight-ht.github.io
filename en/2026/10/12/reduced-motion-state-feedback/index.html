If Motion Stops, Is the Upload Still Running? Separate State from Animation

Use an upload flow to separate business state, visible feedback, and assistive-technology announcements when reducing motion.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-26 · Estimated read 19 min
Translations
zh-CN en

Article

Key takeaways

  • Model idle, uploading, complete, failed, and cancelled as business states; a rotating icon is only an optional presentation.
  • Show a determinate percentage only when the upload API provides real completed and total amounts; otherwise describe indeterminate work.
  • WCAG 2.2 SC 2.3.3 is a Level AAA criterion for interaction-triggered motion, while SC 4.1.3 is a Level AA criterion for status messages; a media query is not a complete audit.
  • Do not make request completion or cleanup depend only on transitionend; changing motion preference should change presentation without silently cancelling or resetting the operation.

Imagine an upload button: someone activates it, its rotating icon stops, and the file continues to transfer. In this hypothetical scenario, a stopped icon does not mean the upload stopped; the request and business state determine whether work is still in progress. The problem is not that one animation frame went missing; business state has been packed into a decorative effect. Reducing motion should change how an operation is presented, not quietly change what stage the operation has reached.

Start by separating three layers

An asynchronous operation has at least three layers: business state, feedback visible to the user, and status information that assistive technology can learn. They can work together, but none substitutes for the others. The business layer records whether work is idle, pending, in progress, successful, failed, or cancelled. The presentation layer chooses text, progress indication, and optional motion. The status-message layer considers how a screen reader can receive success, waiting, progress, or error information when focus does not move.

For an upload, business state might be idle, uploading, complete, failed, and cancelled. Activating the button moves the operation into the upload state; the response determines success or failure; cancellation follows its own completion path. A rotating icon should not decide when the request begins or ends, and it should not be the only evidence that work is in progress. This is a hypothetical design scenario used to reason about the interface. It is not based on interviews, product records, or a user study, and it does not establish how often this problem occurs.

The common implementation mistake is to express state only through a CSS class on an icon. A component enters isLoading, the icon starts spinning, and the interface has no text or semantic progress. Once reduced-motion styling stops the spin, the icon looks like static decoration. If the component also ties isLoading to the duration of the animation, a preference change can interfere with business cleanup. Giving business state an explicit owner and transition conditions before selecting a presentation makes that coupling easier to spot.

Do not invent a percentage when the real progress is unknown

Feedback should answer the user's practical question, not merely make the interface look busy. If the API says only that an upload was accepted and background processing continues, the page can say “Uploading; not complete yet,” but it has no basis for displaying “73%.” A determinate progress value needs real completed and total amounts from the upload interface. The HTML <progress> element's value represents completed work; when value is omitted, progress is indeterminate. A <progress> element also generally needs an accessible name, such as an associated <label>; text placed between its tags is fallback content, not its label.

Completion and failure should not be expressed through color alone. “Four files uploaded” or “Connection lost; three files were not uploaded and can be retried” is clearer than green or red. If a message updates in place without focus moving, check whether it is programmatically exposed as a status message. WCAG 2.2 SC 4.1.3 is a Level AA criterion for status messages that do not change context. It concerns making such messages determinable through roles or properties so assistive technology can present them; it does not require a notification for every interface change. Continuous progress announcements also need a sensible rate. Announcing every byte can make an interface noisy.

A media query only matches the presentation it can reach

CSS can suppress or replace a non-essential animation for prefers-reduced-motion: reduce. W3C's C39 lists this as one sufficient technique for SC 2.3.3, while also explaining that documented techniques are examples, not the only implementation or a compliance certificate on their own. MDN defines no-preference as no relevant preference reported by the device; it does not mean the person explicitly agreed to every animation. A safer design makes content and essential feedback understandable in a static state, then lets motion enhance that presentation when appropriate.

That CSS query does not automatically control JavaScript timers, Canvas drawing, the Web Animations API, third-party widgets, or automatic scrolling. For script-controlled motion, code can read window.matchMedia("(prefers-reduced-motion: reduce)").matches and observe the MediaQueryList change event. When the preference changes during a session, adjust the animation object's play, pause, or replacement behavior. Do not put upload cancellation or progress clearing in the media-query callback. Remove the listener when the component is disposed so that it does not remain subscribed. If animation is central to the tool itself, such as previewing a sequence in an animation editor, decide whether removing it fundamentally changes the information or functionality and whether that can be achieved another way. “The team considers it important” is not enough by itself.

Business completion should not wait for an animation event

There is another failure path that is easy to miss: a component waits for transitionend to hide a busy overlay, re-enable a button, or clear a request marker. MDN explains that transitionend does not fire when no transition runs, when duration is zero or absent, when the transition is removed, or when transitioncancel fires. Reduced-motion styling may remove the transition. Even where a particular style only changes the duration and does not override every possible implementation, business code should not assume that an animation event is guaranteed. Otherwise, the real request may have failed while the button remains locked, or the user may have cancelled while a busy indicator remains.

A more reliable sequence lets the request handler or state manager own the result: success moves to complete, an error to failed, and cancellation to cancelled. Animation may follow those states, but it is presentation. If the end of an effect needs visual cleanup, use a fallback that does not carry business meaning, and make sure cleanup still works on unmount, cancellation, and preference changes. With these responsibilities separated, a missing animation event means only that a transition did not occur; it does not leave the upload state stuck.

WCAG 2.2 SC 2.3.3, “Animation from Interactions,” is a Level AAA criterion. It says motion animation triggered by interaction can be disabled unless it is essential to functionality or information. That focus differs from Level AA SC 4.1.3: the former is about disabling non-essential interaction-triggered motion; the latter is about making status messages that do not move focus programmatically determinable. Citing one does not establish that a site meets the other, and neither criterion makes a single media query proof of WCAG conformance.

Use a scenario table to find the coupling

Do not rely on a single static screenshot showing motion turned off. Record the expected behavior for the same upload flow, then verify it in both normal and reduced-motion modes:

Scenario Business state Feedback that must remain Can motion change the operation?
Upload begins and transfers uploading “Uploading”; show completed amount only if total size is real Rotation may stop; the request should not be cancelled
Total is unknown and background work continues uploading Explain that work continues; do not invent a percentage It can be motionless without estimated values
Upload completes complete Success result and file count The response determines success, not transitionend
Request fails failed An understandable reason and retry path An error should not rely only on red flashing
User cancels cancelled Explain cancellation or partial-file results Visual cleanup should not delay cancellation
Preference changes mid-session Existing state remains Text and real progress continue Change presentation only; check listener cleanup

The actual review should also cover keyboard behavior, focus, and assistive technology. If status text changes without focus moving, observe whether a screen reader receives appropriate information. Do not mark every tiny update as an alert that interrupts current speech just to “make sure it is heard.” W3C warns that excessive live-region use can make an application too chatty. Choose announcement semantics based on task impact, frequency, and observed behavior. No browser or assistive-technology scenarios were run for this article; the table is a test plan, not a passing test record.

You can pair this review with the interaction states of transparent elements: motion disappearing, an element becoming hidden, and a control becoming unavailable are separate questions. Write down the operation state before deciding whether an icon needs to spin. If one preference can make the user think an upload stopped responding, the feedback was already too dependent on animation.
