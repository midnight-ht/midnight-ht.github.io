Transferring a buffer changes ownership rather than making a second copy

A transfer does not create another usable copy: it gives an ArrayBuffer to the result or receiver. Understand reachability, synchronous detachment and asynchronous retries before treating the original buffer as a backup.

Key takeaways

  • Without a transfer list, structured cloning copies ArrayBuffer bytes so the source and result can be used independently; with transfer, the result receives the resource and the original ArrayBuffer is detached.
  • The transfer list selects resources to move; each resource must also be reachable from the message graph, or the sender can lose access without the receiver getting it.
  • Worker.postMessage returning does not mean the worker finished processing. Decide where retry data comes from before transfer, and use request IDs and explicit acknowledgments to distinguish handoff from completion.

With transfer, a successful structuredClone hands the listed ArrayBuffer resource to the returned value and detaches the original ArrayBuffer. The variable binding still exists, but it no longer owns the original bytes. This is not the same as saying that the data was erased, and it does not give the caller another copy that remains readable. Before choosing transfer, answer an interface question: will the sender still need these bytes after handoff, and where will retry data come from if processing fails?

Copy and transfer produce similar-looking results with different ownership promises

Without transfer, structured cloning creates an independently usable object graph. If that graph contains an ArrayBuffer, its bytes are copied; the source and result can then access their own buffers. With transfer, the result is still a new object graph, but the specified transferable resource is moved into it instead of being copied again. The HTML Standard's StructuredSerializeWithTransfer validates the transfer list and serializes the value before running transfer steps and detaching the source; MDN's structuredClone reference likewise describes the original as unusable after transfer. Both calls appear to return new objects, but they leave the caller with different responsibilities.

A small Node check makes the difference observable. It verifies behavior in the local Node 24.x runtime only; it is not a browser matrix or an end-to-end Worker test:

const buffer = new ArrayBuffer(4);
const view = new Uint8Array(buffer);
view.set([1, 2, 3, 4]);
const result = structuredClone({ view }, { transfer: [buffer] });
console.log(buffer.byteLength);        // 0
console.log(result.view.byteLength);   // 4
console.log([...result.view]);         // [1, 2, 3, 4]

The observed source byteLength is 0, while the view in the result still reads four bytes. The old view variable does not somehow recover just because it was passed as a property; its backing ArrayBuffer has been detached from the sender. Calling this “the bytes were cleared” misleads incident responders, because the resource is now on the result side. The contract to maintain is who owns and can access the resource, not whether a variable can still be printed.

The transfer list is not shorthand for message contents

The transfer list means “transfer these resources”; it does not automatically insert them into the returned object. For the recipient to read the data, the ArrayBuffer or a view that refers to it must also be reachable from the object graph being cloned. A second Node 24.x check put a buffer in the transfer list but cloned only { ok: true }. The result had only the ok property, while the source buffer still had byteLength 0. The list and the message graph are separate inputs: one describes how a resource is handed off, and the other determines what structure the receiver gets.

This boundary can become a real fault during a refactor. The earlier payload may have nested payload.buffer, then a change sends only metadata while leaving the transfer list intact. The call succeeds, the sender's resource is detached, and the receiver has no buffer. The fix should follow the interface contract: make the resource reachable from the message if it must be sent; remove it from the transfer list if it is no longer sent; or choose cloning/an explicit copy if multiple consumers need it. “It is in transfer” is not a substitute for tracing the data path.

Also consider the view and backing-buffer range. Uint8Array and DataView are views over a buffer; the transferable resource is the ArrayBuffer they depend on. A view can cover only part of a larger buffer. When the backing buffer is transferred, the entire underlying resource is handed over, not only the bytes visible through the view. If other regions are present, the receiver can create another view into them. When only a specific range should be sent, first construct a precisely sized Uint8Array for that range and transfer its buffer. That adds a copy, but it makes the data boundary explicit and avoids handing over adjacent sensitive bytes.

Separate serialization failures from failures after handoff

Structured cloning does not support every JavaScript value. For example, an object containing a function causes structuredClone to throw DataCloneError. The HTML Standard runs serialization before the ArrayBuffer transfer and detach steps, so an exception caused by an unserializable object graph does not first complete this buffer transfer. A local Node 24.x check used an object with a callback: the exception was DataCloneError and the source buffer still had byteLength 4. This describes that serialization-failure path; it is not a blanket claim that every error for every transferable implementation rolls back the entire operation. Different transferable types have their own transfer steps.

The easier failure to overlook is asynchronous processing. structuredClone itself returns synchronously, so its result is immediately available. Worker.postMessage queues a message task for the receiving event loop. The sending call has already handed off the resource, but that does not mean the worker has run, validated or persisted it. MDN describes transferred objects as no longer usable on the sending side and the worker message as a queued task. If the main thread releases its file record or treats a byteLength-zero buffer as its retry copy, a timeout leaves no material to resend.

Represent at least the states “ready,” “handed off,” “receipt acknowledged,” “processing complete,” and “outcome unknown/recovery needed.” A request ID associates a reply with the original task; receipt acknowledgment and business completion should be different states. Retry data can come from a source that can still be read, such as the original File or Blob, a storage layer holding the original object, or a deliberate copy retained before handoff. A retained copy uses additional memory. A single handoff cannot honestly provide both “no copy” and “the sender always retains retry bytes.” If the input cannot be reread and loss is unacceptable, decide on backup cost and retention before transferring.

A minimal preparation step could look like this:

const sendBuffer = await file.arrayBuffer();
const retryBuffer = sendBuffer.slice(0); // keep an independent byte copy if retry is required
worker.postMessage({ requestId, buffer: sendBuffer }, [sendBuffer]);
// sendBuffer is no longer a usable sender-side copy; await a reply for requestId

This snippet expresses a responsibility contract; it is not a recorded local Worker run. If retryBuffer is removed, a timeout should trigger a reread from file or mark the task as not automatically retryable; it must not try to recover bytes from detached sendBuffer. The site's existing explanation of API retry and idempotency covers the related condition for safely issuing work again.

When should you copy, and when should you transfer?

If sender and receiver both need to read or modify the resource, or a request may need to be replayed, cloning or keeping an explicit recovery source usually matches the interface semantics better. Ordinary structured cloning creates independent data; measure its actual cost in the target environment. Choose transfer when the sender no longer needs the resource, the target object actually contains it, and failures can recover from somewhere else. Do not claim that transfer is always faster simply because the input is large. MDN's ArrayBuffer.transfer reference says implementations may use a zero-copy move or realloc; the actual path and performance depend on runtime and scenario. No benchmark was run for this article.

How can you verify the interface without treating one success as a guarantee?

In a non-production environment, construct four cases: after an ordinary clone, both sides have independent bytes; after transfer, the source byteLength is 0 and the result bytes are intact; when a transfer-list resource is absent from the payload, the test detects that the sender lost access but the recipient has no field; and when the graph contains an uncloneable value, check the error and source state before transfer. For a Worker, also test a queued message with no business acknowledgment, worker failure or termination, duplicate request IDs, cancellation and timeout. Confirm that any retry reads a valid source rather than reusing the old buffer binding.

The Node observations above were run in Node 24.x; no browser or Worker was launched, and no memory or time benchmark was measured. Run these tests in the target browsers and Worker lifecycle before project acceptance, then compare results with the request state machine. The right choice depends on whether an ownership handoff fits the task, not merely on whether the old variable name still exists.
