A CHECK constraint is not a required-value declaration

Separate CHECK ranges, required values and business stages without converting unknown data into false zeroes.

Updated 2026-10-12 · Estimated read 6 min
Translations
zh-CN en

Article

A CHECK expression requiring a positive quantity can still accept NULL. A value-range condition and a required-value declaration answer different questions. Decide whether “not yet known” is valid before judging the schema from its comparison operator.

Unknown is different from zero

The PostgreSQL 18 constraint documentation states that CHECK is satisfied when its expression is true or null. A positive-value comparison on a nullable column therefore does not require a value. NOT NULL addresses that requirement. These are PostgreSQL semantics, not a claim about every database implementation.

In a hypothetical procurement system, a positive quantity may mean an established requirement, zero may mean no requirement and NULL may mean awaiting confirmation. Mixing them changes storage, reporting and approval decisions. No actual procurement data supports this illustration; the permitted state depends on the business stage.

Define when completeness is required

Distinguish draft requirements from submission requirements. Allowing unknown draft values does not imply allowing them after submission. Review combinations of state and fields rather than adding required flags mechanically. Otherwise users may invent numbers simply to save work.

An update API should also distinguish an omitted field, an explicit null and a supplied number. Omission might retain the previous value while null might clear it, but the contract must define those meanings. Database constraints protect permitted states; they cannot infer editing intent. Frontend guidance and server validation should agree about incomplete drafts.

Inspect existing missing values

Before adding a non-null requirement, classify existing nulls: valid drafts, incomplete imports, historical defects or genuinely unknown values. Replacing every null with zero can transform uncertainty into false business information.

Proposed checks should cover positive, zero, negative and null inputs across save and submit paths. Document each expected result, including whether failed updates preserve the original record and whether the error explains what is missing. No SQL was run and no database was changed for this article.

Give each constraint a clear responsibility

A record condition, a required value and duplicate prevention are distinct schema concerns. Ask which states allow absence, which numbers are legal and which fields establish identity. Separating those questions reveals missing rules more clearly than counting constraints.

Start with one nullable field. Define unknown, zero and positive values, then compare the application and database against that state table. Being able to explain every accepted state is a more useful acceptance criterion than the number of constraints.
