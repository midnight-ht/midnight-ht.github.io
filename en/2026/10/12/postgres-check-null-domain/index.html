Why can PostgreSQL save NULL when a CHECK says greater than zero?

PostgreSQL treats TRUE and NULL as satisfying CHECK. Define value ranges, required states and historical-data migrations separately; do not turn unknown into zero.

Article

Key takeaways

  • `CHECK (quantity > 0)` evaluates to NULL for a null quantity; PostgreSQL considers both TRUE and NULL to satisfy a CHECK, so a range rule does not require a value.
  • If requiredness depends on row state, constrain the state, numeric range and state condition separately; an OR expression can still pass through NULL.
  • NOT VALID can constrain later writes before old rows are repaired and validated. The SQL here is a proposal; no database operation was run.

In PostgreSQL, CHECK (quantity > 0) does not evaluate to FALSE when quantity is NULL; it evaluates to NULL. A CHECK is satisfied when its expression is TRUE or NULL, so a range check is not automatically a required-value declaration. If a value is required only at a particular business stage, that state rule must also be part of the contract rather than being inferred from the comparison operator.

A CHECK rejects FALSE

The decision has three outcomes: a true expression passes; a false expression fails; an unknown result, represented as SQL NULL, also passes. The official constraints documentation explicitly says that a CHECK expression satisfies the constraint when it evaluates to true or null. Comparisons with a null operand usually propagate unknown, so NULL > 0 is not false; it is unknown.

The same column definition behaves differently for four values:

quantity result of quantity > 0 CHECK (quantity > 0)
8 TRUE passes
0 FALSE rejected
-2 FALSE rejected
NULL NULL passes

This is the constraint’s defined behavior, not a missed database check. It answers whether the expression has established that a row violates the rule; it does not answer whether the column must have a value. If the contract requires every row to have a quantity, use quantity integer NOT NULL CHECK (quantity > 0). The documentation also notes that an explicit NOT NULL constraint is preferable to treating CHECK (quantity IS NOT NULL) as its equivalent.

A default is a separate rule. DEFAULT 0 supplies a value when an insert omits the column; an explicit NULL does not turn into the default. On the other hand, an omitted field from a caller may mean “leave the draft incomplete” or it may be an API error. Do not merge NOT NULL, CHECK and DEFAULT into one meaning. The site’s explicit NULL versus default article separates an omitted field from an intentional null during writes.

Requiredness can depend on the row’s state

Consider a hypothetical request record. An unknown quantity is legitimate while a request is a draft; after submission, a review process requires a positive quantity. The legal value depends on the row’s state: draft can hold null or a positive value, submitted requires a positive value, and zero or negative values are invalid in either state.

Declaring the column NOT NULL would prevent a draft from representing an unconfirmed value. Writing only CHECK (quantity > 0) still allows a submitted row with a null quantity. One design is to express the numeric range and the state-dependent presence rule separately:

CREATE TABLE requests (
  state text NOT NULL,
  quantity integer,
  CONSTRAINT quantity_positive_when_known
    CHECK (quantity IS NULL OR quantity > 0),
  CONSTRAINT submitted_quantity_present
    CHECK ((state <> 'submitted' OR quantity IS NOT NULL) IS TRUE)
);

The NOT NULL on state rejects an unknown state. The first CHECK permits an unknown quantity but requires any supplied value to be positive. The second permits a draft without a quantity and requires one for a submitted row. Parenthesized IS TRUE is deliberate: for a submitted row with quantity = NULL, state <> 'submitted' is false and quantity IS NOT NULL is false, so the overall expression is false and the row is rejected. If the condition were written as CHECK (state <> 'submitted' OR quantity > 0), a null submitted quantity would make the right comparison null; FALSE OR NULL is still NULL, and CHECK would accept it. Copying a common OR pattern without tracing three-valued logic is a frequent way to miss the required-state boundary.

This pattern depends on the business definition. If a submitted state can later be reversed, the constraint only checks the stored state; it does not prove that review has completed. If state strings can be rewritten or have case variants, protect the state domain with an enum, controlled reference or another appropriate rule. A normal CHECK cannot query another table to keep a cross-row condition true. The constraints documentation says CHECK is evaluated against the row being inserted or updated, and recommends constraints such as UNIQUE, FOREIGN KEY or EXCLUDE for applicable cross-row restrictions. Other rules may need a trigger or transaction design.

NOT VALID changes migration timing, not NULL semantics

For a table with many historical rows, adding a new CHECK may require scanning existing data. PostgreSQL 18’s ALTER TABLE supports NOT VALID for CHECK constraints: the add step skips the historical scan, but subsequent inserted or updated rows must still meet the constraint. After legacy violations are repaired, VALIDATE CONSTRAINT scans existing rows. The documentation states that validation uses a SHARE UPDATE EXCLUSIVE lock and need not block concurrent updates because new writes are already constrained.

This does not transform “unknown” into “not permitted,” and it does not repair existing values. Suppose every submitted request must have a quantity. Before migration, count nulls by state and distinguish drafts, submitted records, incomplete imports and values whose source is genuinely unknown. Backfill a real quantity only when there is an authoritative source. Records that cannot be resolved should go through a correction, return or manual-verification path rather than being filled with zero.

A proposed rollout can follow this order: confirm the rule and distribution of existing nulls; add a NOT VALID check that matches the contract so new violations are rejected; repair historical values with evidence and route unresolved records for review; then run VALIDATE CONSTRAINT. If validation fails, retain the failing-row set and determine whether each row is a legitimate draft or a historical exception before changing data or changing the rule. The SQL and migration steps here are a design example; they were not executed against a database.

Also account for edits to old violating rows while the constraint is active. An update creates a new row version that must satisfy the constraint even when the previous row was not validated. The rollout should identify old records likely to be edited and choose how to repair, defer or phase their changes. If a business rule depends on other rows staying consistent after they change, CHECK is not the right mechanism: PostgreSQL does not reevaluate every related row whenever another row changes.

Test the promised boundary

A constraint review should not stop at finding a CHECK in the DDL. List combinations such as draft plus null, draft plus positive, draft plus zero, submitted plus null, submitted plus positive, submitted plus negative, null state, and an ordinary update to an old row with null. For every case, record whether it should be accepted or rejected and whether that decision comes from the business contract or the migration plan. A SQL verification plan should also check that a rejected write leaves the original row unchanged and that the application error explains what an operator must supply.

A counterexample is to update every null to zero and then observe that CHECK (quantity > 0) no longer accepts null. The database may satisfy the constraint while the data meaning is broken: unknown quantity has become “confirmed zero,” reports may say there is no demand, and the review process may treat the request as complete. Another counterexample is adding a state CHECK without testing the actual three-valued result for a submitted null. A positive-value test passes, so a developer may believe requiredness is protected. Writing a small truth table before the normal path is a stronger test of completeness.

The acceptance questions are: which states permit an absent value? What do zero, unknown and omitted each mean? Does every input rejected by the database correspond to a clear contract? How will old violations be corrected without inventing facts? Once those answers are explicit, CHECK, NOT NULL, DEFAULT and migration steps can each have a distinct responsibility. If a value is always required, explicit NOT NULL plus a range CHECK is clearer. If requiredness changes with state, express that rule separately and test the combinations. For a different NULL behavior in duplicate identity, see NULL in unique constraints.

Sources and factual boundaries

The PostgreSQL 18 constraints documentation explains that CHECK is satisfied by TRUE or NULL, describes NOT NULL, and sets the boundary for cross-row checks. The ALTER TABLE documentation describes NOT VALID, enforcement on subsequent writes and VALIDATE CONSTRAINT. The draft/submitted example, constraint combination and migration order are editorial recommendations. No SQL was run, no database was changed and no execution plan was checked.
