Test row security with the actual application role

Verify RLS with the runtime role, separating privileged bypass, ownership and read-write paths.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-12 · Estimated read 6 min
Translations
zh-CN en

Article

An RLS policy does not constrain every database connection automatically. When investigating tenant isolation, identify the role actually used by the application before changing policy expressions. An administrator seeing all rows is not evidence that an ordinary application role sees them too.

The role boundary comes first

The PostgreSQL 18 row-security documentation distinguishes bypass-capable roles and table ownership. Superusers and BYPASSRLS roles always bypass row security. Owners normally do too, although FORCE ROW LEVEL SECURITY can subject owners to policies. That does not constrain superusers. For a constrained role, enabling RLS without an applicable policy produces default denial.

Consider a hypothetical order service that uses the privileged connection configured for migrations. Its tenant policy may exist while the service bypasses it. Follow configuration, pool creation and database-session identity to establish the executed role. This is a diagnostic scenario, not a vulnerability found on this site.

Review runtime and migration identities separately

Maintain separate permission inventories for schema changes and routine business traffic. Record role attributes, table ownership, applicable policy roles and connection origins. Include background workers and administrative endpoints rather than reviewing only interactive requests.

Tenant context needs its own lifecycle. If the application carries tenant identity in session state, specify how pooled connections receive and clear it, including failed requests. A constrained role with the wrong context can enforce the wrong business identity faithfully. This is a condition to investigate, not evidence that a pool has leaked data.

A read query does not test every write path

Plan checks for reading one’s own rows, reading another tenant’s rows, creating records, changing ownership and accessing data without valid context. Derive expected outcomes from authorization requirements rather than current query results. Use the runtime role for acceptance and retain a privileged-role comparison with its purpose clearly labeled.

List-page checks do not cover exports, background tasks or bulk updates. Rejected writes also require truthful transaction feedback; partial failure must not appear as complete success. No database session or migration was executed for this article. These are proposed checks, not a passed security test.

Keep application authorization explicit

RLS does not replace authentication, business-action permissions or control over privileged maintenance. Document who can bypass the boundary, why and how those operations are traced. Deliver role identity and applicable policy as one reviewable contract.

The useful next step is a permission record gathered with the actual runtime role, not an unverified increase in policy count.

See object-level authorization. Review application actions alongside database row permissions.
