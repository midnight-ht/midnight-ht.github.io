Why Can the Application Still Read Every Tenant with RLS Policies in Place?

RLS behavior depends on more than policy text: runtime roles, table ownership, policy composition, and tenant context all affect access.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-25 · Estimated read 22 min
Translations
zh-CN en

Article

Key takeaways

  • Enabling RLS, granting table privileges, and identifying the actual current_user are separate checks; owners, superusers, and BYPASSRLS roles behave differently.
  • USING filters existing rows, WITH CHECK validates proposed rows, permissive policies combine with OR, and restrictive policies combine with AND.
  • Validate pooled tenant context, SET versus SET LOCAL lifetimes, and whole-table operations such as TRUNCATE separately.

The existence of an RLS policy does not mean every application connection is subject to it. When investigating a multi-tenant query, first check current_user, table ownership, and role bypass attributes on the connection the application actually uses. Then inspect the policies that apply to that command. Editing the tenant predicate may fix the wrong layer. This article describes the mechanisms documented for PostgreSQL 19. The SQL snippets are review examples; they were not run against a database.

Separate the application user from the database role

The “tenant A user” in an HTTP request is not automatically the identity of a PostgreSQL session. An application may connect through one shared service account and pass request identity as a parameter. It may instead switch database roles inside a transaction. Looking only at a connection string or deployment setting cannot prove which role executed a query.

The database distinguishes session_user, the login identity that established the session, from current_user, the effective identity used for permission checks. SET ROLE changes the latter. A SECURITY DEFINER function also runs with an effective identity different from the caller's. Diagnostics should therefore use a real application connection, not a migration script, operations terminal, or local administrator session.

A controlled diagnostic path could run this read-only query and associate the result with the deployment under review. This is a proposed check, not a result reported by this article:

SELECT session_user, current_user,
       current_setting('role', true) AS role_setting;

If the result shows a migration account or table owner, trace how the pool obtains credentials, whether background workers use another connection setup, and whether the request passes through a SECURITY DEFINER function. Do not keep sensitive connection details in ordinary application logs. Keep diagnostic output access-controlled and remove temporary instrumentation afterward.

Ownership and bypass attributes sit outside policy text

The PostgreSQL 19 row-security documentation says that, after row security is enabled, a normal role with no applicable policy is denied by default. Superusers and roles with the BYPASSRLS attribute always bypass row policies. Table owners normally bypass them as well. FORCE ROW LEVEL SECURITY can subject the owner to policies, but it does not constrain a superuser or a BYPASSRLS role. “A policy exists” and “this executor must obey it” are separate conditions.

Keep SQL object privileges separate from row policies too. GRANT SELECT determines whether a role may query a table; RLS then limits which rows it may see under that privilege. RLS does not replace GRANT. If row security is disabled on the table, defined policies are ignored and ordinary object privileges govern access. Check the table's relrowsecurity and relforcerowsecurity settings alongside the role grants; a policy visible in the catalog is not proof that a query applied it. For object grants, consult the PostgreSQL 19 privileges documentation.

There is another boundary worth keeping visible: TRUNCATE affects a whole table rather than filtering rows through RLS. Restrict it through object privileges. A runtime role with TRUNCATE does not become tenant-limited for that operation just because its row policies are careful. Include whole-table privileges separately in the maintenance and application role inventories. Further details appear in the row-security documentation.

That distinction explains a useful counterexample. An administrator may see rows from every tenant as expected; that alone does not show that tenant isolation failed. A production service using the migration role that owns the table is different: the business path itself may bypass the policy. Both cases can produce an all-tenant result, so distinguish them with evidence about current_user, table ownership, and role attributes instead of treating similar output as the same diagnosis.

Two PostgreSQL 19 catalog views help with the role and policy inventory: pg_roles exposes rolsuper and rolbypassrls; pg_policies exposes policy roles, commands, USING, WITH CHECK, and whether a policy is permissive or restrictive. Determine policy applicability using ordinary role membership and inheritance rules as well as the single current_user name. The table's relrowsecurity and relforcerowsecurity flags are available from pg_class. These are example checks to adapt and run under an authorized account:

SELECT rolname, rolsuper, rolbypassrls
FROM pg_roles
WHERE rolname IN ('app_runtime', 'app_migrator');

SELECT schemaname, tablename, policyname, permissive,
       roles, cmd, qual, with_check
FROM pg_policies
WHERE schemaname = 'public' AND tablename = 'orders';

SELECT c.relowner::regrole AS table_owner,
       c.relrowsecurity, c.relforcerowsecurity
FROM pg_class AS c
WHERE c.oid = 'public.orders'::regclass;

Confirm that the caller can read the relevant catalog information and that the results come from the same database and deployment version as the service. A copied role list from development is not acceptance evidence for a production connection.

USING and WITH CHECK govern different stages

USING determines whether existing rows are visible or eligible for the current command. A false or null result filters a row out. WITH CHECK validates a proposed row after an insert or update; false or null makes the write fail. A read policy alone does not establish that a new order belongs to the request's tenant, nor that an update cannot move an existing order to another tenant.

Suppose orders.tenant_id holds the tenant owner and a policy conceptually says that the row's tenant must equal the current request tenant. For a SELECT, the question is whether the row can appear. For an INSERT, the new row must be checked. For an UPDATE, consider both whether the old row can be targeted and whether the resulting row still satisfies the tenant boundary. The CREATE POLICY documentation specifies how expressions apply by command and policy type. It also describes cases where an omitted WITH CHECK is derived from USING, so reviewers should read the complete policy definition instead of inspecting one predicate in isolation.

Policy composition matters too. Permissive policies are combined with OR by default. If a tenant predicate and a broad policy such as USING (true) both apply, the latter may widen visibility. A restrictive policy combines with AND, but cannot grant access without at least one applicable permissive policy. Inspect each policy's roles, command, and composition; counting the number of policies tells you little about the effective rule.

Tenant context on a shared connection is a trust boundary

Some services use a shared database role and pass the current tenant to a policy through a transaction parameter or function. That design is meaningful only when the system defines who may set the context, where the value comes from, and when it expires as a connection is reused. RLS can filter according to the tenant value PostgreSQL receives. It cannot, by itself, prove that the value came from an authenticated HTTP user. If a client can choose any tenant parameter, the database is faithfully enforcing an untrusted input.

Connection pools reuse sessions, so an ordinary SET can leave state on a connection that later serves another request. SET LOCAL lasts only until the current transaction ends. The correct choice depends on the driver, transaction boundaries, and pool behavior. Verify commit, rollback, exception, queries outside a transaction, and connection return paths. With transaction-local state, business queries must actually run in that same transaction. If a connection was borrowed before the transaction began, confirm that rollback and pool cleanup leave it in the intended state. Transaction lifetime is covered in the PostgreSQL SET documentation.

One threat-model question is: under the shared account, can application code change the tenant context to an arbitrary value? If so, RLS can still protect against a forgotten WHERE clause, but it cannot alone prevent a compromised application from acting as another tenant. If the database must distinguish request principals, consider a controlled identity-transfer design, such as separate roles or constrained functions, and review the grant path along with it. This is an architectural judgment, not a finding about a pool or proof that a particular design is secure.

Accept reads, writes, and failure paths with the runtime role

An acceptance matrix should record who executes each case, which command runs, and the expected outcome. Cover at least: tenant A reading its own rows; A reading tenant B's rows; A inserting a row owned by A; A trying to insert a row owned by B; A updating a business field on its own row; A trying to change the tenant owner; reads and writes with no valid context; plus exports, background jobs, and bulk operations. If a tenant predicate evaluates to null because context is absent, USING hides the row while WITH CHECK rejects a proposed row; the test should distinguish those outcomes. Run each case using the role the application really uses. Record the database version, connection origin, and expected denial behavior.

Keep a separate control case for a table owner or operations role that may see every row. Label it as a diagnostic result, not ordinary-user security acceptance. Distinguish a query returning zero rows from a write rejected by policy, and verify the application does not report a partial failure as success. Asynchronous jobs, bulk updates, and SECURITY DEFINER functions may execute under different identities; a single web list-page check cannot stand in for them.

No application deployment configuration was inspected and no SQL was executed for this article. The matrix is a proposed acceptance plan, not a passed security test. RLS is one database row-level control; it does not replace authentication, business-action authorization, input validation, or governance of privileged maintenance. The evidence that answers “why did the application see every tenant?” is the effective role on the actual service connection, the table owner, bypass attributes, and applicable policies—not how complete a policy looks in an administrator's session.

If the concern also includes whether a user is authorized to act on a particular object, compare the object-level authorization review. Application action permissions and database row policies require separate acceptance.
