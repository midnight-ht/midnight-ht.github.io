Why can two builds differ even when npm ci locks the dependencies?

npm ci constrains dependency installation, not every build input. Inventory runtime, platform, configuration and time, then define how artifacts are compared.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-25 · Estimated read 22 min
Translations
zh-CN en

Article

Key takeaways

  • The frozen-install contract of npm ci concerns dependency installation and lockfile consistency; it does not promise byte-identical output from the whole build.
  • Runtime, npm configuration precedence, platform, lifecycle scripts, external inputs and clocks can enter the build path; a lockfile alone is not a complete audit trail.
  • Define byte identity versus behavioral equivalence first, then compare clean builds with an input manifest, hashes and explained differences. No two-build experiment was run for this article.

npm ci can start dependency installation again from the lockfile, but it cannot fix the Node version, platform, environment variables or generated time for the build that follows. To determine whether two machines produced the same artifact, inspect two separate contracts: whether the dependency tree was reinstalled as intended, and whether the build observed the same inputs. A lockfile is a necessary traceable input, not complete proof of build reproducibility.

What npm ci constrains

The npm CLI 11 documentation describes npm ci as a clean-install command intended for automated environments. A project must already have a package-lock.json or npm-shrinkwrap.json. If the locked dependencies disagree with package.json, the command fails instead of rewriting the lockfile. It removes an existing node_modules before installation and does not write back to the package manifest or lockfiles. Compared with npm install, those behaviors make it easier to check whether a dependency resolution can be reinstalled from the repository’s declared state.

The documentation also names a condition that CI pipelines can miss: if the lockfile was created with an option that changes dependency-tree shape, such as --legacy-peer-deps or --install-links, later npm ci calls need the same setting or may fail. Putting that option in a committed project .npmrc makes it reviewable with the repository. It does not mean that no other configuration source can override it. The npm CLI v11 docs list a precedence order: command-line flags over environment variables, then project, user and global configuration. An unrecorded npm_config_* value or extra CI flag can override repository settings and make the effective invocation differ from a developer’s local command.

So “both places run npm ci” does not yet establish that the inputs match. A more precise statement is that each place attempted a clean install under its effective configuration, with the manifest and lockfile consistent. To turn that observation into reproducibility evidence, also record the actual npm and Node versions, platform, architecture, configuration sources and install options. Do not treat identical command names as identical command contexts.

What can change after the same lockfile

The following is hypothetical and does not describe a recorded run on this site. A developer commits a lockfile from macOS, and CI installs on a Linux runner. Both call npm ci, but use different Node versions. Installation may succeed in each environment while a later npm run build follows a runtime-dependent code path, uses a native module, or emits different content. First locate the stage where the difference appears: the dependency directory, compiler output or packaged files. “Same lockfile” is not a substitute for that staged diagnosis.

Platform differences should be made specific. Some packages declare os, cpu or libc constraints, so an installer may select optional dependencies only on matching platforms; a native extension can also call the local compiler toolchain. This does not mean every project produces different output across platforms. If a project has these dependencies, however, architecture, system libraries, compiler and installation settings are inputs to check. A pure JavaScript project may still observe path separators, file ordering, newline handling or build-script behavior through the platform. Whether any of these actually matter must be checked rather than assumed.

Install lifecycle scripts and project build scripts bring the environment beyond the lockfile into the process. A script may read environment variables, download additional resources, include the current time, inspect local Git state or use a tool’s default configuration. That does not make every such script unsafe or nondeterministic. The question is whether the team knows what it reads and whether those inputs are versioned or explicitly allowed to vary. Frozen installation does not pin external data that a build script fetches, nor does it define which environment variables may affect compilation.

Also distinguish “the package was not downloaded again” from “every input was frozen.” The npm cache is a reuse path for package retrieval; the lockfile describes dependency resolution. A later build may read a schema, dictionary, generator or external data source through another path. Include those values in a reproducibility manifest only if the build depends on them. Inspect the scripts and tool calls first; the mere presence of networking does not prove that every build is affected by it.

Turn the build inputs into a reviewable manifest

A useful manifest answers: which source commit was used? What was the lockfile digest? Which Node and npm versions ran? What were the runner operating system, architecture and relevant system libraries? Which install and build commands ran? Which configuration came from project files, and which came from the caller’s environment? Did the build read Git state, a clock or external files? These questions do not require dumping the entire environment into logs. They help identify which values might change output and where to investigate a mismatch.

Configuration needs particular care because of precedence. The npm CLI v11 configuration documentation lists command-line flags, npm_config_* environment variables and several .npmrc files as configuration sources. A project .npmrc can record a shared non-secret option, such as a dependency-tree setting, but user configuration or CI invocation parameters still need inspection. The execution record can include effective npm ci arguments, the source of non-sensitive configuration and version information. Do not print registry tokens, private-registry passwords or signing keys to make a build “reproducible.” Record a secret variable’s name, source type and presence, while keeping the credential in secure storage.

The manifest should distinguish inputs from observations. Commit digest, lockfile digest, runtime version, target platform and explicit configuration can describe the conditions of a build. Duration, downloaded bytes or machine name may help with diagnosis but may not change the artifact. Whether a value is truly an input depends on whether the build reads it. Marking every environmental difference as forbidden makes the target impossible to execute; omitting a value that affects output makes “same command” hide an incomparable build.

Define “same” before using hashes

Byte-identical artifacts are one strict definition. Equivalent page behavior, API contracts or image execution are different levels of equivalence. First state what is being accepted: a deployment directory, archive, container image or observable behavior. Which files enter the hash? If the output contains source commit time, archive timestamps or image labels, must those fields match too? Without this agreement, two teams can both say “the build is reproducible” while one compares file digests and the other compares application tests.

A proposed validation flow can start from a fixed source commit: record the lockfile, Node/npm versions, platform, install options and controlled environment; run installation and build in two clean environments in the same order; save the output manifest and per-file hashes; inspect and trace any unequal files; then record explicitly allowed differences. Starting in a clean environment avoids old node_modules, generated leftovers or local caches making a run look fresh when it is not. This is a validation plan, not an experiment performed for this article; no runner outputs or artifact hashes are claimed.

If a difference comes from a timestamp, first decide whether that time has meaning for the product. Docker’s documentation describes SOURCE_DATE_EPOCH as a standardized time input and shows how to pass it into BuildKit integrations to affect image index, configuration and file metadata. That is specific support in a Docker build path; it does not rewrite output from an arbitrary JavaScript bundler. The value helps only when the actual tool consumes it. Setting the variable without a consumer does not prove reproducibility. If timestamps are accepted differences, document and exclude those fields deliberately; do not silently ignore every hash mismatch.

Narrow a mismatch by stage

Start by checking whether both installs observed the same lockfile state and effective options. If npm ci fails on one side because the manifest differs or a tree-shaping option was omitted, the issue is in the installation contract; no artifact comparison has happened yet. If both installs finish, compare runtime, platform-dependent packages, environment variables and lifecycle scripts. If those inputs are controlled but file digests still differ, inspect files individually for time, path, ordering or unpinned external data. Record observations separately from hypotheses. A changed artifact hash alone does not show that npm ci failed to lock dependencies.

The opposite mistake is to rerun npm ci in CI until the final digest happens to match once and treat that coincidence as a guarantee. Another is to ignore a timestamp file outright, potentially excluding a field that affects client caching or license information. The right verification layer depends on the release: a deployable archive may require byte-level comparison, while a platform-specific build may only promise repeatability on the same target platform and explicitly different outputs across platforms. Those are engineering choices for the team, not promises made by the package-manager command.

A practical reproducibility statement can be split into three parts: which installation inputs were locked; which build inputs were fixed or explicitly permitted to vary; and which target platform and artifact were compared more than once. If any part is missing, call the result partially traceable or unverified rather than fully reproducible. The site’s dependency-cache trust boundary covers whether cache contents can be trusted and reused. This article addresses the separate question of whether output can be regenerated after a locked install. The checks are related, but neither answers the other.

Sources and factual boundaries

The npm CLI v11 npm ci documentation supports the description of lockfiles, clean installation, tree-shaping options and frozen writes. Its Config documentation describes configuration sources and npmrc files. Docker’s reproducible-build documentation supports only the bounded description of SOURCE_DATE_EPOCH and relevant Docker build metadata. The manifest, difference classification and two-build comparison are editorial recommendations. The cross-machine scenario is explicitly hypothetical. No npm ci, build or artifact comparison was executed for this article.
