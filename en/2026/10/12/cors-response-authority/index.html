Can you retry after a CORS error? First find out whether the operation ran

A browser CORS error alone cannot prove that the server did nothing. Separate a rejected preflight from an unreadable response or transport failure, then use the server's operation record to decide whether retry is safe.

Updated 2026-11-25 · Estimated read 23 min

Article

Key takeaways

  • A rejected preflight can stop that actual request; a CORS check failure on the actual response happens after a network response was obtained.
  • A CORS error is not a business outcome and should not trigger a blind retry.
  • Correlate browser, server, and business records with an operation identifier, and define lookup and idempotent recovery for side effects.

A browser CORS error does not, by itself, prove that the server did not perform an operation. It means page script did not receive a usable cross-origin response. A preflight may have stopped this attempt; or the actual request may have been sent and the response may have failed the browser's CORS check. DNS, TLS, and connection failures can also look like a fetch failure. For an operation with side effects, identify the failure stage and inspect the server-side operation state before deciding whether to retry.

The browser reports readability, not a transaction receipt

CORS is a browser-enforced mechanism for sharing responses across origins. The server supplies response headers describing which origins may read a response; the browser decides whether to expose that response to page script. The WHATWG Fetch Standard places network or cache response retrieval, the CORS check, and conversion of a failed check into a network error in the same fetch flow. A page-visible TypeError: Failed to fetch or a console CORS message therefore does not carry a business conclusion such as “the server definitely did not receive this request.” The Fetch Standard's actual-fetch and CORS-check steps define what the browser exposes, not a database commit protocol.

That distinction matters differently for reads and writes. If a read-only query fails to produce a usable response, the page may simply be unable to render the result. Creating an order, payment intent, invitation, or configuration change is different: when the page loses its receipt, the operator may not know whether the server rejected the operation before processing, committed it and then lost the response, or never received it. The interface can say that the result is temporarily unknown. It should not call the operation failed unless the business system has evidence for that conclusion.

A rejected preflight and an unreadable response are different paths

Only some cross-origin requests require preflight. In a CORS-preflight, the browser sends OPTIONS to ask whether the target permits the requested method and headers. A successful permission can also be cached. So if a fresh OPTIONS request is absent from the network panel, that does not prove no actual request was sent: an earlier successful preflight may still be reusable, and some simple requests do not preflight at all. The Fetch Standard's preflight and cache algorithms describe these distinctions.

If this request requires preflight, no valid cached permission exists, and OPTIONS is rejected or fails the relevant permission checks, the browser does not send this attempt's actual request. That conclusion is limited to this attempt. It does not tell you whether the user clicked earlier, a client already retried, or another non-preflighted request took a different path. JavaScript still receives a generic failure; the sequence, method, and response headers shown in the browser's Console and Network panels are the useful starting evidence. MDN's CORS error guide also directs diagnosis to browser developer tools because page script does not receive the detailed reason.

Another path is that OPTIONS permits the request, the browser sends the POST, and the server returns a response, but that actual response lacks a matching Access-Control-Allow-Origin. A credentialed request also has to satisfy the credentials conditions. At this point, a failed CORS check becomes a network error and page script gets neither the response status nor its body. The server may have completed a transaction, returned a business error, or failed before commit; a browser CORS message alone cannot distinguish these outcomes. The Fetch Standard's CORS check decides whether a response may be shared, not whether a business action succeeded.

Keep a third possibility open: DNS resolution, TLS negotiation, a proxy disconnect, or a browser extension may cause a network or protocol failure. The interface may describe a fetch/network error that resembles a CORS issue, but server-side records are still needed to establish whether a request arrived. Seeing an Origin header is not proof that a request passed CORS; the Fetch Standard notes that non-GET and non-HEAD requests also include Origin in some contexts.

A hypothetical POST can leave the user seeing failure after a record exists

Suppose a page creates a payment intent with POST application/json and an application-defined operation identifier. The browser first sends OPTIONS; the server permits the origin, method, and requested headers, so the browser sends the actual POST. The application creates an intent and returns 201, but an egress proxy omits Access-Control-Allow-Origin on that response path. The server's record may now exist, while the browser refuses to expose the status and body to the page. The user sees a failed request and clicks again, potentially creating another intent.

This is a hypothetical example of the mechanism, not a payment request, production incident, or browser test performed for this article. If OPTIONS is rejected, that request does not proceed to the POST described above. If the network breaks before the actual request is sent, there may be no server-side record. If the application commits and a proxy then drops the CORS response header, the business state may already have changed. The same UI error spans different execution stages; that is why it cannot decide whether to retry.

If an API persists an operation_id, the client may be able to query the outcome of a request for which it never received a receipt. The key's deduplication scope, expiry, behavior when the payload differs, and handling of concurrent replays must be defined by that API. Adding a header named Idempotency-Key does not prove that a server implements idempotency. If the server provides neither a status lookup nor a documented deduplication contract, keep the outcome unknown and use the application's manual verification or recovery process instead of submitting a new operation identifier repeatedly.

CORS is neither identity authorization nor a general CSRF defense

CORS governs whether a browser exposes a response to cross-origin script. It does not authenticate a user, authorize that user to modify a particular object, or evaluate the business conditions for an action. Non-browser clients are not constrained by the browser's same-origin policy. OWASP says every request must be authenticated and authorized as if CORS did not exist. It also notes that some cross-origin form POST requests do not preflight: a server may process one even though the calling page cannot read its response. See the OWASP CORS Security Cheat Sheet, which treats CORS, access control, and CSRF defenses as separate concerns.

Changing Access-Control-Allow-Origin to * therefore does not fix authorization or give users a reliable receipt. In credentialed scenarios, a wildcard also fails the browser's CORS requirements. The correct fix is to verify which trusted origins need to read the response, the actual response path, and the credentials policy, while protecting side-effect endpoints independently with authentication, object authorization, CSRF defenses, and operation-state management. Do not open every origin just to remove a red console message, and do not treat preflight as a business permission check.

Correlate browser and server evidence

For the browser side, record the page origin, target URL, method, requested headers, whether preflight is required, whether an OPTIONS request occurred, whether the actual request appeared, the response status, and relevant CORS headers. Use the console's specific reason when reproducing the issue. Cookies, authorization headers, and request bodies in Network captures may be sensitive; redact them before sharing. A curl request can help inspect server response headers, but curl does not enforce browser CORS and cannot prove that a browser will accept the response.

On the server side, use the same non-secret operation identifier to correlate the ingress gateway, application receipt, authentication and authorization decision, transaction commit, and response proxy. A log saying “request accepted” is not equivalent to “transaction committed”; a 201 generated upstream may never reach page script. A state machine such as received, committed, and rejected is an application design recommendation; name states according to the real transaction boundary and persist the committed result. Use a browser request ID to correlate one network attempt and a business operation ID to identify one intended action. If the API supports idempotent retries, document whether replaying the same identifier returns the existing result or an in-progress status.

A bounded recovery flow can be defined for side-effecting actions: first look up the result by operation ID. If it is committed, show that result; if it is still processing, continue polling or ask the user to wait; only when the server explicitly confirms rejection without a side effect should the client create a new operation. For a timeout or proxy interruption, keep the state unknown and do not blindly send a new identifier. This is application-level guidance, not behavior supplied automatically by CORS or Fetch. If there is no query endpoint, specify a manual review path and the correlation data it needs; do not convert a network error into a duplicate business action.

Verify the recovery policy with four controlled cases

In an isolated test environment, arrange four cases with different expected evidence. First, use a new operation identifier and a test condition with no valid preflight cache, issue a request that needs preflight, and make OPTIONS reject it; confirm Network shows no actual-method request for that attempt and the server handler has no corresponding operation. Second, allow preflight but remove Access-Control-Allow-Origin from a successful business response; confirm page script cannot read it, then use the server operation record to determine whether the transaction committed. Third, interrupt DNS or the connection before the actual request is sent; check ingress evidence rather than treating the generic browser message as proof. Fourth, replay one operation identifier only against an endpoint whose idempotency contract is documented; confirm the system returns the agreed existing outcome instead of applying a second side effect.

No browser experiment, curl request, server-log query, or business API test was run for this article, so it reports no measured network success, request count, or duplicate transaction rate. When implementing the checks, reproduce the actual call: if production uses cookies, Authorization, custom headers, or a preflight cache, include those conditions. Otherwise the order of OPTIONS and the response exposure can differ. The goal is not merely to “get CORS green”; it is to identify the failed stage, find the server outcome for the operation identifier, and establish whether a repeat submission reuses or creates a side effect.

After a CORS error, locate whether the failure was at preflight, response sharing, or transport before retrying. For a side-effecting endpoint, follow its documented idempotent retry contract. If no such contract exists, keep the result unknown until it can be queried or reviewed; the page error cannot stand in for a server-side conclusion.
