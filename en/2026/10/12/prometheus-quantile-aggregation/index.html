Aggregate distributions before estimating a fleet quantile

The arithmetic mean of instance P95s is not the request population's P95. Define the population, aggregate histogram distributions, and check summaries, bucket boundaries, and estimation error.

Updated 2026-11-25 · Estimated read 23 min

Article

Key takeaways

  • Estimate request-population P95 from the aggregated available distribution; the equal-weight mean of local P95s is a different statistic.
  • Classic histogram aggregation must retain le, while native histograms aggregate composite samples; metric type determines query shape.
  • Histogram quantiles are estimates based on within-bucket interpolation and should be checked against the target window, known samples, and SLO boundaries.

Do not average the P95 values from several instances and call the result the service's P95. If the question concerns tail latency across all requests in a time window, combine an aggregatable representation of the instances' distributions first, then estimate a quantile from that combined distribution. If the metrics contain only each instance's already calculated P95, they do not contain enough information to reconstruct the request population's P95. This is why Prometheus summaries and histograms are not interchangeable display formats.

“Fleet P95” can mean two different things

A quantile belongs to a set of observations. After sorting observations from smallest to largest, P95 describes the value at a position below which roughly 95% of observations fall. The endpoint and interpolation convention for a sample quantile can vary by algorithm. The official guide defines a φ-quantile as the observation ranked at φ×N among N observations, and calls 0.95 the 95th percentile. The key question is which observations the quantile describes, not whether the graph label says P95.

“Calculate P95 on each instance, then average those P95s” answers: what is the average local P95 if every instance has equal weight? “Put all requests into one population, then calculate P95” answers: where does the latency distribution fall for a randomly selected request served by the service? Those answers may happen to be close under special conditions, such as equal request counts and similar distribution shapes, but there is no general reason they must be equal.

Consider a hypothetical sample used only to explain the statistical difference. It is not production data or the output of a Prometheus query. Instance A handles 100 requests in the window, each taking 100 milliseconds. Instance B handles one request taking 1,000 milliseconds. Under the nearest-rank convention stated here, A's P95 is 100 milliseconds and B's one-sample P95 is 1,000 milliseconds. Giving the two instances equal weight produces an average of 550 milliseconds. When all 101 requests are pooled, position ceil(0.95×101)=96 still gives 100 milliseconds. The 550 millisecond value does not describe the 95th percentile of these 101 requests; it is just the mean of two local summary values.

The same problem appears when one instance handles very few requests, all of which are slow: its P95 gets the same weight in an instance average as the P95 of a busy instance. If the service objective is defined over user requests, equal instance weights overstate the influence of the low-volume instance. If the operational question really is “what is the equal-weight mean of instance-level P95s?”, then equal weighting is intentional. It simply should not be named the request population's P95. Define the target population before deciding whether weighting is appropriate.

The metric type determines whether aggregation is possible

The “Histograms and summaries” practice guide explains that a summary calculates selected φ-quantiles in the instrumented program and exposes them directly. It cannot later recalculate another window or quantile, and quantiles from multiple instances cannot be aggregated into a service-wide quantile. If every instance exports only a summary time series such as quantile="0.95", the query engine sees the per-instance results, not the request samples that produced them. Applying avg to those results yields an average of local P95s.

A histogram retains counts of observations in buckets, so the server can still choose a window and quantile. Classic histograms represent buckets as cumulative-count time series labeled with le. For a monotonically increasing counter, calculate the rate of each bucket series over the window first, sum matching bucket boundaries over the intended population, and then call histogram_quantile. The following is the shape of a PromQL query for all instances in one request population:

histogram_quantile(
  0.95,
  sum by (le) (rate(http_request_duration_seconds_bucket{service="checkout"}[5m]))
)

Here service="checkout" is an example selector that makes the population boundary explicit. Replace it with the actual label and value used by the metric, whether that is job, app, or another field. sum by (le) drops every label it does not retain, so first scope the query to the intended service; an identical metric name is not a reason to merge requests from different business services. If you intentionally want to compare services, keep the service label in the by grouping instead of dropping it.

To retain a job breakdown, preserve job as well as le: sum by (job, le) (...). A classic histogram requires the le label; if aggregation removes it, the bucket boundaries disappear and histogram_quantile cannot reconstruct the distribution from classic buckets. Keeping rate inside sum handles counter resets per instance before combining rates. Summing counters first and then taking a rate can make a restart on one instance look like a reset of the combined counter.

A native histogram keeps the count, sum, and buckets in a composite sample, so a fleet query does not need an le label: histogram_quantile(0.95, sum(rate(http_request_duration_seconds{service="checkout"}[5m]))). Replace the selector with the actual population boundary as well; for a job breakdown, add by (job) to sum. These query shapes are not interchangeable without checking the metric type. The “Query functions” reference distinguishes classic aggregation, which must retain le, from native histogram aggregation over composite samples.

Histogram P95 is an estimate, and bucket design matters

A sum of bucket counts does not mean the original latency of every request is still available. Inside the bucket containing the quantile, classic histograms and native histograms with custom boundaries assume a uniform distribution and use linear interpolation; non-zero buckets in native histograms with the standard exponential schema use exponential interpolation. If P95 falls inside a very wide bucket, the metric does not reveal how observations are skewed within that bucket. The displayed value is a reasonable estimate, not necessarily the exact result of sorting every request.

This matters for an SLO. Suppose the team asks whether 95% of requests finish within 300 milliseconds. It can inspect the fraction of requests at or below 0.3 seconds; when a classic histogram has an le="0.3" boundary, that cumulative count directly represents the threshold and allows an exact fraction at that boundary. If there is no such boundary, histogram_quantile can estimate a quantile between neighboring buckets, but the interpolated value must not be described as an exact measurement. The official guide warns that direct classic-bucket calculations of a threshold fraction require every participating histogram to have the corresponding boundary; otherwise the result can be missing or incomplete.

Bucket selection is not simply “more is always better.” Every classic boundary creates a time series. More buckets can improve local estimation, while increasing storage, scrape, and query costs; changing a layout later also makes bucket boundaries from different instances harder to match. Native histograms manage buckets through a configurable resolution. Exponential layouts are reconciled to a compatible resolution, so resource use and precision remain a trade-off. If classic histograms are ingested as native histograms with custom bucket boundaries, reconciliation between different layouts can also reduce the effective resolution substantially. Choose boundaries or native resolution after identifying the latency range, SLO thresholds, and target population, and retain enough evidence to inspect estimation error.

Why keep an instance view next to the fleet P95

A request-population P95 answers a service-level question, but it is weighted by traffic. A low-volume instance that is persistently slow may barely change the fleet quantile. A small number of requests from one region or route may also be diluted by a high-volume path. Replacing the fleet P95 with the mean of instance P95s does not solve that problem: it changes the population being described and introduces the separate risk of mislabeling a statistic.

A more useful design keeps two explicitly named views side by side: a request-population aggregate for service-level objectives, and breakdowns such as instance, region, or route when they help locate an anomaly. Do not add labels without limit. More label combinations create more time series and smaller samples per group, making each local quantile less stable. A breakdown should support an action, such as investigating an instance and removing it from a load-balancing pool, rather than merely adding another curve to a dashboard.

Alerts should use the same population definition. If the SLO denominator is user requests, service-wide latency and error signals align more closely with the objective. If the goal is to detect one stuck instance or resource exhaustion, use a separate instance-level signal. Copying an instance P95 threshold into a fleet rule, or using a fleet P95 to assign health to an individual instance, changes what the rule means. The site's article on alert-label stability can help evaluate which fields identify an alert, but label design cannot make an incorrect aggregation correct.

How to verify that a query represents the intended population

Before rollout, give the query review a few known distributions: instances with very different request volumes, each instance's latency values, and the target window. Calculate the combined sample result independently under a declared quantile convention, then compare it with the query's intended population. For classic histograms, check that instances expose the same bucket boundaries, aggregation preserves le, and rates are calculated before summation. For native histograms, check that evaluation still uses compatible native samples, inspect annotations about layout reconciliation, and consider lost resolution. Then use a low-traffic instance or high-latency route to confirm that the local view has not been hidden by the aggregate.

No query was run and no metrics were generated for this article. The code snippets are query-shape examples based on current official documentation, not successful execution logs. Before adapting them to a specific site, verify the metric name, exposition format, labels, histogram layout, and Prometheus version; test the result with promtool rules or a controlled sample query. A verification report should state the target population, window, unit, metric type, bucket compatibility conditions, and estimation boundary. Without those details, a graph labeled “P95” does not tell the reader what it represents.

When implementing the query, start with one sentence: “Which requests does this P95 cover, over what window, and do requests have equal weight?” If the answer is a service's request population, aggregate the distributions before estimating. If only summary quantiles are available, do not invent a fleet P95 by averaging them; change the instrumentation or name the metric honestly as a mean of local summaries. Then choose the breakdowns and histogram resolution needed for diagnosis.
