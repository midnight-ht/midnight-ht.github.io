What does the server receive after a POST redirect? Inspect each hop

After a POST receives a 3xx response, the destination's request depends on the status and client. Inspect method, body, credentials, and side effects at every hop.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-25 · Estimated read 20 min
Translations
zh-CN en

Article

Key takeaways

  • 301/302 allow legacy POST-to-GET behavior; 303 retrieves an indirect result; 307/308 preserve the method when automatically followed.
  • Preserving a method does not prove the body is replayable or that cross-origin credentials will be sent.
  • A 3xx response does not say whether the first endpoint committed a side effect; correlate each hop with business state.

A redirect does not move the original request from one server process to another. After a POST receives a 3xx response, what the destination receives depends on the status code, whether the client follows automatically, and whether the body and credentials can safely be replayed. Diagnose each hop: method, body, headers, and side effects. The final URL alone is not a business receipt.

A 3xx response creates another client request

A redirect has at least two independent HTTP requests. First, the client sends a POST to the old URL. That server may process the request and returns a 3xx response with Location. If the client chooses to follow it, the client creates another request to the URI resolved from Location. The first server saw the original POST; the destination sees a request reconstructed by the client. Even if one button triggered both, the servers are not internally handing the same request object to each other.

This is why debugging needs two records. A browser Network panel or client trace can show statuses, Location, and the follow chain. Ingress logs at the old and new endpoints answer whether each server received a request. Seeing the page end at /orders/123 does not establish which method reached /orders, nor which endpoint created an order. At the protocol level, redirection is further action by the user agent; a server returning the redirect has not thereby proved business completion, as RFC 9110 makes clear.

Five status codes, not one POST rule

301 indicates a permanent move and 302 a temporary one. HTTP clients historically disagreed about whether a POST should remain a POST on the next request. Given that history, RFC 9110 permits a user agent to change POST to GET after either response for compatibility. “May” matters: it is not a guarantee that every client follows in the same way. Permanent versus temporary describes the move, not a guarantee that the method or body is preserved. A 301 can also be heuristically cached, while 308 is cacheable by default unless explicit cache controls or the method definition say otherwise. A later request may therefore not reproduce the first visible chain, which matters when testing migration and rollback.

303 See Other has a clearer purpose: the original request has an indirect result that can be retrieved separately. The client can use GET or HEAD for the Location resource. A common Post/Redirect/Get flow stores a submitted form after POST, returns 303, and lets the browser GET a confirmation page. Reading that page should not submit the original form again, and refreshing it should not create another order.

When the new address should process the original method, 307 (temporary) and 308 (permanent) require that an automatically following user agent not change the method. They tell the client to preserve the method, but do not prove that every byte was replayed, that credentials cross origins, or that the old endpoint had no side effects. The requirement for 307 is in RFC 9110 §15.4.8; the permanent 308 variant is defined in RFC 7538 §3. The specification treats unsafe-method redirects cautiously; user agents may decline to follow them. Redirect mode, client options, and security policy still matter.

Fetch and curl produce different evidence

In the browser Fetch algorithm, 301/302 change the method to GET only when the current method is POST; 303 changes methods other than GET/HEAD to GET. When the method changes, the body is cleared and request-body headers such as Content-Type and Content-Length are removed. The 307/308 path does not use that method-rewrite branch. If the body is a one-shot stream that cannot be read again, the standard algorithm can fail with a network error: preserving a method does not give the client a second copy of the body.

The origin boundary is separate. When Fetch encounters a cross-origin redirect, it removes Authorization to avoid automatically leaking the initial site's authorization header to another origin. It also tells clients to consider removing fields such as Authorization and Cookie when there are security implications. Whether cookies are sent is further constrained by browser credentials mode, SameSite, domain, and path. “307 preserves POST” answers only the method question, not which headers reach the target.

curl is not a browser. It does not follow 3xx responses by default; -L/--location opts in. With a custom method set through --request POST, --location uses that explicit method on later requests, while the newer --follow option applies status-based method handling (the official curl book says it was added in curl 8.16.0). Thus the same 302 can produce different observations in browser Fetch and curl -X POST -L. A copied command tests its own client options, not automatically the production client.

An order migration shows where a side effect happens

Consider a hypothetical migration. The old endpoint receives POST /orders, checks inventory, creates an order, and then returns 302 Location: /orders/123. A browser following under Fetch sends GET to the result URL. The old endpoint has already created the order; the destination only reads it. POST-to-GET is appropriate for result navigation, but treating the GET page as the first processing point would misattribute the work. This is a hypothetical example, not an observation from this site or a production trace.

A different migration has the old address perform no order operation and return 307 Location: https://api.example.test/v2/orders. The browser preserves POST, and the v2 endpoint receives a replayable JSON body before creating the order. That design fits a contract where the old endpoint is only a routing compatibility layer. If the old endpoint had already written a record before returning 307, v2 could create a second side effect. The status code does not deduplicate.

Now add two failure paths. If the POST body comes from a non-replayable upload stream, Fetch may be unable to follow even though 307 preserves the method; the target receives no second request, and the client reports failure. If Location points to another origin, the method can remain POST while Authorization is removed; the destination may receive an unauthenticated request. Do not mistake that for the same identity having completed the operation. Old and new ingress logs need a shared non-secret request or operation identifier, and should distinguish “received,” “started,” and “transaction committed.”

Choose the status from the business intent

If the current endpoint has completed the write and the next page should only display a separately addressable result, 303 usually states the intent most clearly: POST performs the write, then GET reads the result. If the old URL is a temporary routing layer that guarantees it performs no side effect, the body can be replayed, and the destination has the right authentication and idempotency contract, 307 may send the same method to a new address. For a permanent URI change, 308 may fit after checking client compatibility, caching, and existing bookmarks. RFC 7538 notes that 308 is newer than 301/302 and some older clients may not recognize it; confirm the client population if fallback behavior is unacceptable.

301/302 can suit navigation and compatibility, but a write contract should not depend on “one client has always behaved this way.” Identify the actual client, redirect mode, and version, then document the expected request chain. If users can control the Location target, validate the destination too: an HTTP redirect can become an open redirect. The related redirect destination trust boundary covers destination validation, a separate concern from method and body semantics.

Even a well-chosen chain needs business recovery for unknown outcomes. If the first endpoint committed and the second hop failed, retrying the whole POST can still duplicate work. Use a server-side result lookup or an idempotency contract tied to the same operation ID; a 302, 307, or final 200 does not prove exactly-once processing. See the request retry and business idempotency boundary for the repeated-intent question.

Verify every hop, not only the final page

In an isolated environment with non-sensitive test data, arrange four cases. After POST followed by 303, confirm the first endpoint received POST and the target received GET, with body-related headers removed. After POST followed by 307, confirm the target received POST and whether the replayed body digest matches. Change Location to another origin and inspect the actual Authorization and Cookie policy. Then use a one-shot body and establish whether the client can replay it. Record the client and version, initial URL, status, Location, next-hop method, body presence and digest, origin, response code, and operation state. Do not log live cookies, tokens, or payment data.

For curl, record the exact version and options, and limit the conclusion to curl. For a browser, inspect its real follow chain in Network tools. Server logs can show what method arrived and which stage a business operation reached, but “no log found” supports a non-arrival conclusion only when log coverage, clock alignment, and correlation keys are reliable. Proxies, load balancers, and asynchronous queues can add more boundaries. No browser, curl, server, or business API test was run for this article; it reports no success log, performance result, or order outcome.

What a server receives after a POST redirect is determined by status semantics, the particular client, body replayability, and origin/credential policy together. Draw the requests and side effects at every hop before choosing 303, 307/308, or a navigation-oriented status. Do not let the final URL stand in for evidence about the whole request chain.
