Property tests still need an independent behavioral claim

Generated inputs widen exploration, but they do not define correctness. Review the contract, oracle, boundaries and mutations that challenge each assertion.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-26 · Estimated read 27 min
Translations
zh-CN en

Article

Key takeaways

  • Generators explore inputs; correctness still comes from a reviewable behavior contract.
  • Fixed boundary examples, structurally different reference models and differential checks complement one another but retain common-mode risks.
  • Challenge assertions with boundary mutations and review the input domain, shrunk failures and rejection paths separately.

Property-based testing can generate many inputs, but “it ran many times” only means the tool repeatedly checked the condition you wrote. It does not show that the condition is correct. To review an assertion, first state the behavior contract in a way that can be independently challenged. Then use boundary examples, a reference model, or a distinct implementation to test that claim. The generator explores inputs and a shrinker can simplify failures; neither decides what correct behavior means. This division is not specific to one framework: Claessen and Hughes make it explicit in their original QuickCheck paper, published at ICFP in 2000. The tool generates random inputs and checks properties; the tester supplies the automatically checkable pass/fail criterion.

Translate the assertion into a behavior contract

Consider a function that filters integers into an interval. The product contract says: given lo <= hi, retain every input value satisfying lo <= x < hi, preserve order and duplicates, and return an empty sequence for an empty interval. That is four separate claims: which endpoints are included, whether order is preserved, whether duplicates remain, and what an empty interval means. Review them separately. “Every output is in range” is not enough.

The following sample is hypothetical and illustrates the contract; it is not an execution result. Given [0, 3, 5, 5, 8] and [3, 8), the expected output is [3, 5, 5]. An implementation that mistakenly uses x <= hi returns an extra 8. An assertion that checks only “every output is in range and the output is no longer than the input” would also accept an empty array. Even a million generated examples cannot reject an implementation if the property still permits that wrong output.

So the first review step is not to count inputs. Ask whether a counterexample could refute each part of the contract. A right-boundary error needs an x == hi case; a left-boundary exclusion needs x == lo; accidental deduplication needs duplicates; reordering needs an input with distinct values in an order that matters. Empty input and lo == hi also need explicit behavior. A few ordinary examples do not diminish property testing. They pin down the business boundaries that generation should not leave to chance.

The expected result can share the implementation's mistake

A straightforward oracle computes the expected result directly from the contract, for example with a clear list comprehension. It is easier to review than a copied version of a complex production algorithm, but common-mode mistakes remain possible: if both expected-value code and production code use <= hi, the implementation and assertion agree while both violate the contract. A second code path is not independent merely because it appears in the test file. Compare its requirements source, structure, and likely failure modes with the implementation.

Several complementary checks can reduce this risk. First, keep fixed boundary examples whose expected outputs a reviewer can calculate from the contract. Second, use a structurally different reference model. For example, production code might use indexed storage or a database query, while a test model simulates the behavior with a simple in-memory collection. Hypothesis’s official stateful-testing documentation shows this pattern for its example database: operations run against both the real implementation and a simplified Python dictionary model, and the test looks for behavioral discrepancies. This demonstrates how a model can serve as a comparison target; it does not establish that the model is correct. The model still needs calibration against requirements and known cases.

Third, differential testing can compare a second implementation, if you first establish that the two implementations do not share the same algorithm, configuration, or source of error. Fourth, relational properties can constrain several inputs: sorting an already sorted result should not change it, or decoding an encoded value should restore an allowed original value. These properties catch some defects, but they guarantee only a relation. Two mutually compatible encoder and decoder bugs may still pass a round-trip test while both violate an external format. A correct relation is not proof of correct absolute behavior.

The generator defines the world you are checking

The current official Hypothesis tutorial describes strategies as generated input types and shapes. It combines integer and list strategies, and demonstrates that allowing NaN in floating-point inputs creates a sorting case whose order is undefined. The lesson is not to exclude NaN automatically. First establish the interface contract: if the product accepts it, define sorting or rejection behavior; if the contract explicitly prohibits it, exclude it from that strategy and test the rejection path separately.

Likewise, .filter() or assume() narrows which inputs actually reach the assertion. A condition added for generator convenience can quietly remove the most revealing counterexample. First distinguish in-contract inputs, inputs the interface promises to reject, and values outside the interface entirely. They do not belong in one “normal result” property.

When should assume discard an input, and when should rejection be tested?

Discard an input only when it violates an explicit precondition for the property at hand. A promised rejection is itself part of the contract and needs a separate test. For the interval example, the normal-result property may generate only endpoints satisfying lo <= hi. For an API contract that says lo > hi must raise an error, add a distinct check that it rejects [8, 3) instead of returning an empty array or silently swapping endpoints. This separation keeps assume from erasing requests the interface is required to reject. It is an illustrative review example; no code was executed.

Then check whether the strategy omits None, empty collections, maximum lengths, encoding boundaries, or invalid states. Establish what the production entry point can accept and what it must reject before the strategy can describe the input domain instead of merely making the test pass.

Random generation is useful for exploring a wide input space; fixed examples make critical boundaries permanently visible. The current Quickstart page, whose heading identifies documentation version 6.170.17, says its default setting generates 100 random inputs and can be adjusted. That is a statement about the tool’s documented default, not a universal count for property-testing frameworks or evidence that 100 cases are sufficient. Whether finite sampling reaches a defect depends on the strategy, input space, distribution, budget, and trigger condition. Preserve important boundaries explicitly instead of hoping a random run happens to draw them.

Shrinking explains a failure, not the property

Property-testing tools often try to shrink a failing input so the trigger is easier to understand. A long sequence might shrink to the single value hi, making a right-boundary error obvious. But a shrinker optimizes for a simpler input that still triggers the current failure. It does not compare your assertion with the business specification. A weak property that accepts an empty result, shrinking will not supply the missing contract. If a strategy never produces hi, shrinking cannot discover that boundary either.

When a failure appears, retain the input, framework version, settings, random or example-database state, and full error. Then distinguish three cases: the implementation broke the contract; the property is too weak or incorrect; or the input is outside the contract and the strategy lacks a legitimate precondition. Do not respond to a failure by casually adding filters, and do not treat a green run as a proof. For a failure that represents a required rejection case, express that rejection in a separate test rather than silently removing the input from the normal strategy.

Challenge the test with an intentional mistake

Mutation testing can temporarily replace < with <=, remove stable-order handling, or make a deduplication branch run, then check whether existing assertions fail. A surviving incorrect mutation, the tests do not distinguish the corresponding behavior. This is not a proof of correctness: a mutation set may miss realistic faults, and a test can fail for accidental reasons. Still, it turns “the assertion looks reasonable” into a checkable question: can these meaningful wrong behaviors be rejected?

A compact property review table can record the requirement source, input domain, smallest counterexample, source of the expected answer, plausible missed faults, mutation challenges, and how a failure should be interpreted. Have someone familiar with the requirement review expected behavior first, then use generated inputs to widen the exploration. Consider a state machine for APIs with interacting sequences of operations; for independent inputs, ordinary @given tests may be simpler. The official stateful guide likewise presents state machines as useful when rules can be chained and interact, while noting that simpler cases may need only a regular generated test.

Stateful APIs require checking state, not only return values

For an API made of operation sequences, checking each function's return value can miss side effects. Consider a hypothetical key-value store: put(k,v) overwrites an existing value, get(k) returns an empty value for a missing key, and delete(k) removes the requested key; assume deleting a missing key is idempotent. A simple dictionary model can track expected state, but the property should not check only the return from delete. Run put(a,1), put(b,2), then delete(a), and read both keys: a should be absent while b should still contain 2. An implementation that mistakenly removes the most recently inserted key, a success return from deletion alone may not expose the wrong deletion.

This is another explicitly hypothetical example; no system was run. It shows why a state machine needs more than independent inputs: operation order changes later observable results. Hypothesis stateful tests generate chained rules, and its documentation's example applies operations to both a real implementation and an in-memory model to find sequence discrepancies. The team must still define overwrite, missing-key reads, and repeated deletion before adopting that model. A model with the wrong semantics, more generated sequences only compare two equally wrong answers. Checking state after each operation can localize a mismatch; checking only final state may reduce noise but can hide a temporary invariant violation. Choose the observation points from the interface contract.

Make each property reviewable later

A review record can capture five things for a contract instead of only a green build: the requirement source and semantic owner; the domain and preconditions; how the expected result is derived independently; the smallest input that should make a violating implementation fail; and the mutations that may still escape. For interval filtering, [8] in [3,8) must produce an empty sequence; [8,3] should expose ordering; and [5,5] must preserve both copies of 5. Each example checks a different promise. One assertion that every output is in range cannot stand in for all of them.

Pair deliberate faults with the property expected to reject them: changing < hi to <= hi should fail the upper-bound case; always returning an empty list should fail a completeness check; sorting the result by value should fail the order-preservation case. If a mutation survives, check whether the assertion is missing, the example actually reaches the strategy, a filter removed it, or the expected result is not independent. If it is killed, confirm that the intended assertion caused the failure; any red test is not automatically evidence of coverage.

This record makes “the property test passed” a bounded statement: no violation was found under the written input domain, observation points, settings and assertions. It says nothing about behavior outside the contract and does not imply a complete mutation set. Increasing the random-example count is less informative than adding contract-required boundaries and observations that distinguish wrong implementations.

These are review methods, not an executed testing tutorial. No Hypothesis, mutation tool, or project code was run for this article. A team can start with its weakest property: write down the requirement it comes from, construct one concrete input that a wrong implementation might pass, add an independent example or model, and inject the corresponding mutation deliberately. After each change, revisit whether the strategy and assertion are independent. The number of generated cases is a budget; the correctness basis must still be a reviewable behavior contract.

The related article on surviving mutation-testing errors connects “does the test reject a known wrong implementation?” with the question here: “does the property have an independent basis?”
