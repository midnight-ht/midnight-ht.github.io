Property tests still need an independent behavioral claim

Review independent properties, meaningful domains and explicit boundaries rather than treating generated input volume as proof.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-12 · Estimated read 6 min
Translations
zh-CN en

Article

Generating many inputs does not automatically make a property-test assertion correct. Review whether the property expresses an independent requirement, whether its domain covers relevant risks and whether failures can be explained against a contract.

Strategies do not supply the oracle

The Hypothesis quickstart, labeled version 6.169.0 when consulted, demonstrates strategies describing inputs and tests checking properties. Broader input generation does not decide the intended business behavior.

Consider a hypothetical encoder and decoder tested only for round-trip identity. Coordinated mistakes in both can preserve that property while violating an external format. This illustrates an assertion boundary; Hypothesis was not executed and no defect count is reported.

Give each property an independent reason

Record whether a property comes from an interface specification, a domain rule or an implementation convenience. External formats may need independently defined known examples. Financial calculations may need separate rounding and range requirements. Avoid using the implementation under test to produce its own expected results.

Several properties can complement one another, but similar assertions do not automatically add confidence. Assertions sharing an incorrect premise may pass together. Ask what incorrect implementation could still satisfy every current property. That question exposes behavioral requirements that input counts cannot describe.

Include the difficult parts of the domain

Strategies should reflect permitted product data: boundaries, empty collections, special characters and state combinations. Distinguish inputs that must be rejected from inputs outside the contract entirely. Filtering away difficult cases may leave only the easiest region under examination.

Retain explicit examples for mandatory boundaries and use generation to explore more broadly. Such cases should not depend on whether a particular generation run reaches them. No iteration count is promised to discover a defect, and a passing run is not proof over every possible input.

Interpret failures through the contract

Review one property’s business source, input restrictions, known examples and remaining blind spots. For a failure, preserve reproducible input and environment, then determine whether implementation, property or domain assumptions need correction. Do not expand filtering merely to restore a passing result.

No tests or failure examples were generated here. Start with an assertion supported only by implementation details and obtain independent requirement evidence. Generation assists exploration; the team still needs a reviewable answer to what counts as correct.

See surviving mutants. Inspect incorrect implementations that still satisfy existing assertions.
