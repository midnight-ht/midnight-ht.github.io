Why can tests with high coverage miss a wrong comparison operator?

Use a surviving >= to > mutant to inspect input boundaries, test oracles and mutant validity; treat the score as a review signal, not proof of test adequacy.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-25 · Estimated read 23 min
Translations
zh-CN en

Article

Key takeaways

  • Coverage describes execution; mutation testing asks whether current tests distinguish a selected incorrect change.
  • For a surviving comparison mutant, check boundary inputs, an independent expected-result oracle and whether the mutant changes observable behavior.
  • Record the requirement, input, test, expected result and disposition per mutant before interpreting the aggregate score; no test or Stryker run was performed here.

Coverage can show that execution passed through a line; it cannot tell you whether a test distinguishes a correct comparison from an incorrect one. When a comparison-operator mutant survives, first ask whether any test input lands exactly on the boundary. Also ask whether the expected result comes from an independent business rule or calls the implementation under test again. Mutation testing makes a controlled counterfactual: it inserts a particular code change and runs selected tests. If they do not fail, that establishes only that this change was not caught by this test set. It does not automatically prove that production behavior is wrong or that every test is ineffective.

Execution coverage is not behavioral discrimination

Code coverage is usually summarized by lines, branches or other execution points reached by tests. A run can execute both sides of a condition without asserting that the result meets a user rule. It can also assert a case far from a boundary while missing the boundary itself. Coverage therefore answers “what code ran in this test set?” A test oracle answers “what independent basis tells us that the result is correct?” The questions are related but not interchangeable.

Mutation testing adds a controlled counterfactual: if the current implementation were replaced by one particular local mistake, would the selected tests fail? The official introduction uses changing >= to > as an example. It calls a mutation killed when at least one test fails and survived when the tests continue to pass. Survival is not a verdict about the requirement. It is an observation about one generated change, one test set and the assertions they contain. Generated mutations cover a limited range of edits; an attractive score does not make ungenerated defect classes disappear.

Trace a surviving comparison mutant to its boundary

The following is hypothetical. It is not a description of this site’s code, a real discount rule, or an executed test. Suppose a business rule says an order qualifies for a discount at 100 currency units or more. Amounts are compared in minor units, and exactly 100.00 qualifies. The correct condition is amountInCents >= 10000. Existing tests use only 80.00 and 120.00: the first does not qualify and the second does. Change >= to > and both results remain the same. If those are the only relevant tests, the comparison mutant may survive.

Turn the clue into a precise question: do the tested inputs cover a region where the comparison changes the result? Here the minimum distinguishing input is exactly 100.00. If the product contract includes equality at the threshold, the independent expected result is “eligible.” The expectation after mutation should still come from a written rule or reviewed example, not from calling the same isEligible() implementation and using its result as expected. That would couple implementation and oracle so the same error could flow into both.

Before expanding the tests, verify the units and normalization rules. If the amount is rounded, reduced by tax or converted between currencies first, the boundary may not be the displayed 100.00. Tests should use the integer amount or value domain that the business process actually compares. If the system uses floating-point decimals or multiple currencies, precision and conversion contracts need their own definition; a mutation tool cannot infer the product rule from generated examples. A comparison mutant tells you whether this test set is sensitive to this program change. Requirements and data transformations determine how inputs map to a business boundary.

Classify the survivor before changing a test

The documentation lists several distinct states. Survived means the mutant ran and tests still passed. No coverage means the original code was not executed by the tests, so the corresponding mutant was not killed either. Both can expose a detection gap, but the remedies differ: the first calls for inspection of inputs and assertions; the second first needs a scenario that reaches the logic. Timeout may mean the mutation made a test exceed its limit. Error or a compile error does not mean an assertion found a requirement violation. An ignored mutant should not be mixed with a mutation that was actually run. State names visible in a report can depend on tool version and configuration, so check the documentation and output for the version in use.

A surviving mutant can also be equivalent: the code changes, but the externally observable result does not change within a defined input domain. Stryker’s equivalent-mutant page demonstrates a comparison change that preserves output and says it cannot reliably identify every equivalent mutant automatically. Reviewers must ask whether the change violates the service contract. For example, if equality is excluded by the business definition, or two branches differ internally but produce the same permitted output, adding an assertion merely to “kill” the mutation may encode an implementation detail that is not required.

Be careful in the opposite direction too. Calling a mutant equivalent because it “looks harmless” can hide a missing input constraint or side effect. State the assumptions behind the equivalence judgment: what inputs are allowed? Could an observable state, log, external call or permission differ? Who confirmed the contract behind the judgment? If those points are unknown, leave the mutant awaiting review rather than labelling it noise.

What a mutation score says, and what it does not

A mutation score is a proportion of selected mutations detected by the tests. A score formula in the FAQ separately lists no coverage, survived, timeout and error, and says its formula excludes errors. Its mutant-states-and-metrics documentation distinguishes valid mutants, undetected mutants and a score based on covered code. When reading a report, inspect the current version’s numerator, denominator, selected files, exclusions and no-coverage mutations. A percentage separated from its run configuration is not a universal measure of quality.

The aggregate is also affected by selection. If a team enables mutations for one small boundary function, the score describes that set of generated mutants, not the rest of the system. Conversely, including many low-risk, easy-to-kill mutations can make the total look steady while a critical permission branch contains survivors. Adding input tests may kill meaningful survivors, or it may simply cover easy mutations without touching high-risk rules. Choose scope using business risk, path complexity, relevance of mutation operators, test runtime and the team’s ability to review results—not a generic target. This article provides no universal threshold.

Keep one review record per consequential mutant

For each high-risk survivor, retain a checkable record: which business requirement it represents; what differs between original and mutated code; which inputs the test ran; what independent expected result applies; what state the tool reported; and whether the team added an assertion, fixed missing coverage, confirmed equivalence, excluded an invalid mutant or left the requirement awaiting clarification. On the next run, the team can see whether the survivor was explained instead of rereading the aggregate report from scratch.

For the hypothetical 100-unit threshold, the record might say: requirement source is “amount is at least 100.00”; mutation is >= to >; the old cases are below and above the threshold; the distinguishing input is exactly 100.00; and the independent expected result comes from the confirmed business rule. If the test still passes on the mutation, check whether the assertion only verifies a successful API response, whether it reused the implementation function, or whether another condition masks the result. Decide whether to add a test, fix implementation or clarify the rule only after the requirement and expected behavior are confirmed. This is a record format, not a test receipt from an executed run.

Choose a mutation scope without turning tests into a score chase

Mutation testing may rerun tests repeatedly. A larger scope, slower test suite and larger result set all add review cost. Start with a small piece of important business logic such as an amount boundary, a permission decision or a state transition. Confirm the baseline tests are stable, then mutate only the relevant production code and retain the report and configuration. If each mutant takes a long time, first improve the startup cost of relevant tests and exclude unrelated files, then decide whether to run in stages or by risk. For test runtime, the FAQ suggests reducing unnecessary mutation files and improving test speed; this does not make one configuration right for every project.

Avoid making tests serve the mutator. Assertions that focus only on private variables, call order or a particular implementation statement may fail during a valid refactor. At the other extreme, testing only a broad final page may miss the source of a user-visible error. A stronger oracle begins with the contract: what result should a caller observe, what state must not occur, and which side effects are required? When an internal constraint matters, state which module boundary it protects instead of adding a brittle assertion just because a tool changed a line.

Review a survivor in this order: is the requirement clear; would this mutation change the required result; did the test execute the mutated logic; is the expected result independent; is there an input that distinguishes the change; and is the mutation valid? An unclear requirement needs clarification. An equivalent mutant needs its assumptions recorded and may be ignored or the code may be expressed differently. An uncovered branch needs a scenario. A covered but undetected comparison may need a boundary input and an independent oracle. A compile failure or test-runner error needs a tool or environment fix, or an invalid-state classification. Each conclusion has a different owner and next action.

A mutation score cannot define correctness for a team. It is evidence about how tests respond to selected code changes. When a comparison mutant survives despite high coverage, the useful next step is not to add tests blindly; find the missing input partition, state the expected result independently, then decide whether the mutation violates the user contract. If you are designing an oracle for property-based tests, the site’s property-test oracle boundary addresses a related but different question: how to know whether generated results are correct.

Sources and factual boundaries

The Stryker mutation-testing introduction explains mutation execution and illustrates the >= versus > boundary. Stryker’s FAQ defines score calculation and execution states. Separate pages cover mutant states and metrics and equivalent mutants, including the limits of automatic equivalence detection. These are Stryker documentation claims, not a universal standard for every mutation-testing tool. The discount example and review procedure are explicitly hypothetical and editorial advice. No Stryker run, test suite or production experiment was performed.
