Why does React show the old filtered list before updating again?

When a list and its filter already determine the screen, do not store another result with an Effect. Separate stale renders, independent drafts, performance caches, and external synchronization.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-26 · Estimated read 24 min
Translations
zh-CN en

Article

Key takeaways

  • Calculate display values from current props and state during rendering instead of synchronizing a redundant state copy.
  • Drafts, independent selections, and workflow phases may carry irreducible information and need explicit lifecycles.
  • Use useMemo to address measured pure-computation cost; reserve Effects for external synchronization rather than click events.
  • Validate filter changes, record switches, removed selections, and stale asynchronous responses; this article proposes but does not execute those tests.

The task list, its filter, and the visible list do not all need to be stored separately. If the first two fully determine the last, calculate the visible list during rendering. A user’s unsaved draft, an independent selection, or a target that must be synchronized with an external system can justify separate state. Copying a derived result into state and using an Effect to chase its inputs can make the interface render old data, commit it, and then render the new result. It also leaves the team responsible for keeping two values that should agree.

The current React v19.3 Learn docs describe Effects as an escape hatch for synchronizing with systems outside React’s rendering flow. Filtering a list or combining first and last names is usually a render-time transformation. The useful question is not “Are Effects bad?” Ask whether the code runs because the screen is displayed, because a specific user action happened, or merely because existing inputs need to be presented in another form.

Why can a redundant copy show stale data first?

Consider a page that stores tasks and filter, then stores the filtered result in visibleTasks. An Effect calls setVisibleTasks whenever tasks or filter changes. When the user changes the filter, React renders with the new filter while visibleTasks still contains the previous result. After the screen is committed, the Effect runs, updates the list state, and causes another render. The official guide describes this render, commit, Effect, and state-update sequence as an unnecessary extra render pass; if the intermediate commit is visible, users can see the old rows briefly.

The result can instead be calculated at the top of the component:

function TaskList({ tasks, filter }) {
  const visibleTasks = tasks.filter(task => matches(task, filter));
  return <TaskRows tasks={visibleTasks} />;
}

This is an illustrative example and was not run in this repository. The important point is not merely “one fewer Hook.” There is one relationship: visibleTasks = f(tasks, filter). When either input changes, the next render computes the result from those inputs. No separate agreement is needed about who updates the copy.

The copy turns a simple data relationship into a synchronization protocol. Omit an input from the dependency list and the result can go stale. An Effect runs after a commit, so there is an interval in which the page can show the previous result. A chain of Effects that updates derived state can create cascades. If it also starts asynchronous work, a result for old inputs may arrive late and must not overwrite the current result. These problems do not arise from the Effect API alone; they arise because a derivable value was stored as if it were an independent fact, creating extra transitions.

Decide whether the value contains independent information

Ask a concrete question before storing a value: if it were removed, could the current props and other state reconstruct it? If yes, it is probably derived data. If it cannot be reconstructed because it contains user input, prior intent, a manual choice, or the phase of an asynchronous operation, it may be independent state. Similar names do not imply similar semantics.

For example, an edit form may have the server’s profile.name and the user’s draftName. While the edit is unsaved, the values are expected to differ. Replacing draftName with a value recalculated from profile.name on every render would erase what the user typed. By contrast, if a page stores firstName, lastName, and a fullName that is always their concatenation and cannot be edited separately, the third value is a redundant copy.

Server data that changes during an edit is harder. A new prop should not automatically overwrite the draft, and the draft should not automatically win either. The product needs a rule: discard the draft when switching to another record; preserve local edits when the same record refreshes in the background; or detect a version conflict and ask the user. State design should distinguish these events instead of copying objects in an Effect and hoping the dependency list expresses the product policy.

If an edit session belongs to one object as a whole—for example, switching from user A’s profile to user B’s must clear the comment field and all nested draft state—give the inner editing component a key based on userId. React treats different keys as different component identities and recreates the child state. This fits a clear boundary where changing the object starts a new editing session. If only part of the same object changes, resetting the whole subtree may destroy user input. Let object identity determine the key; do not use keys as a generic state-clearing button.

Store the source entity or only the selected identifier?

List selection is another place where copies accumulate. Storing the whole selectedItem object and clearing it in an Effect when items changes can leave a stale object, reset selection whenever an array reference changes, or duplicate entity fields. If the meaning of selection is “which ID in the current list is selected,” store selectedId and resolve the object during rendering:

const [selectedId, setSelectedId] = useState(null);
const selectedItem = items.find(item => item.id === selectedId) ?? null;

This makes a product boundary visible. When the list refreshes, an ID that still exists keeps its selection; an ID that disappeared no longer resolves to a visible object. If the product requires clearing selection whenever the dataset changes, include dataset identity or an explicit refresh event in that policy. A new array reference alone does not mean that the user must choose again. The state-structure guide recommends avoiding redundant, duplicate, and contradictory state; separating a stable ID from the entity that may be refreshed is one application of that advice.

It can help to draw the data flow as nodes: server entity, selected ID, edit draft, derived display value, and external side-effect target. A one-way calculation often does not need another node for the display value. If the user can write a value, identify which source is being edited. If a node belongs to an external system, identify synchronization, failure, and cleanup responsibilities. The diagram is not a proof, but it can expose copy debt hidden in questions such as “Who updates B after A changes?”

useMemo is a cache, not a second source of truth

After replacing the Effect with direct calculation, a team may worry about an expensive transformation on every render. React’s guide recommends calculating first, then checking for a performance problem; useMemo can cache a pure result when needed. It addresses computation cost, not correctness or ownership. Its function still runs during rendering, and React may reuse the previous value while dependencies remain unchanged. It is not persistent business state.

Decide whether caching helps by measuring the target interaction. For example, time the filtering work during text entry and compare updates with and without useMemo, using a production build and conditions near users’ devices. The performance section warns that development Strict Mode can call some logic more than once, so development measurements do not directly represent production. useMemo also does not make the initial render faster. The milliseconds shown in the docs are measurement guidance, not a performance guarantee for your application. No benchmark was run for this article, so it makes no speedup claim.

A reasonable order is: first make the calculation pure and ensure it has all inputs; then observe whether it consumes meaningful time; add useMemo only if caching improves the interaction being measured. Synchronizing the derived result into state to avoid recomputation creates a more complicated update, recovery, and concurrency policy. Saving one calculation at the cost of another consistency constraint is usually a poor trade.

Effects should target an external system or display lifecycle

Effects still have a clear role. Connecting to a chat server, subscribing to a browser event, or keeping a third-party chart widget aligned with React state are synchronization tasks between React and an external system. Establishing a connection when a component appears, switching it when its target changes, and cleaning up the old connection on removal or dependency changes describe a lifecycle. They are not copies of one value into another.

Network requests need more careful classification. When a search input changes, remote results must be synchronized with a data source; an Effect or a framework’s data-loading mechanism may be appropriate. A POST that should happen only when the user presses “Submit,” however, is caused by a specific click and belongs in the event handler. Wrapping that submission in an Effect can turn one event into state-based inference that may run again when the page is displayed. Ask why this code is running now: because the UI appeared, because an external target changed, or because the user clicked?

Even a necessary Effect needs failure and cleanup paths. If an older request returns after a newer query, stale results must not become current. A subscription must be canceled when its target changes. Connection failures need an observable state. In development, repeated setup and cleanup should not leave duplicate subscriptions behind. The synchronization guide defines Effects around external systems and discusses cleanup and development re-execution separately. Network origin alone is not a reason to add an Effect; compare the caching, race handling, and error behavior offered by the React framework in use.

Validate change paths, not just the static code

Review or test four paths. First, change a filter and check that the visible rows match it without showing the prior result. Second, edit a draft, switch records, and refresh the same record; verify the product’s defined keep-or-discard rule. Third, remove the selected item and check how its ID resolves and what empty state appears. Fourth, change remote query parameters quickly and arrange for the earlier request to return last; confirm that it cannot overwrite the newest result. Write the expected behavior first. A screenshot of the current interface is not a substitute for a product rule.

You can also challenge the test with a deliberate defect: temporarily remove one filter condition and confirm a test fails; repeatedly switch the same filter and observe whether redundant list state exists; simulate Effect cleanup before setting a new target and check that no subscription remains. These are proposed validation steps, not tests executed for this article. Deterministic transformations can be unit-tested, component interactions can be integration-tested, and real network races, browser subscriptions, or third-party widgets must be checked at their actual boundaries.

If list filtering is slow, should the result be stored in state?

Keep a performance cache separate from business state. First calculate the derived value during rendering from complete inputs, then measure the interaction. If the calculation meaningfully affects experience, test a cache such as useMemo and measure again instead of writing the result into another state variable with an Effect. If users can independently edit or confirm the result, it is no longer just a cache; give that draft or confirmation state its own lifecycle rule.

The related article on form state and server-side rules discusses how local editing and external decisions divide responsibility. When an Effect synchronizes state, identify the input nodes, user-writable nodes, and external-system nodes first. Keep values derivable from existing inputs in render calculations, model edits that must survive as explicit state, and reserve Effects for the external synchronization work that remains.
