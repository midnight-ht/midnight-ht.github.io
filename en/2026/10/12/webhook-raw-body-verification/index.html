Verify webhook signatures before changing the request body

Stripe verification depends on the original request body, signature header, and endpoint secret. Trace middleware, retries, and deduplication when equal-looking JSON fails, while keeping other providers' protocol boundaries clear.

Key takeaways

  • Stripe verification uses the original request body, Stripe-Signature, and the secret for the current endpoint; parsing and reserializing cannot prove that the input bytes stayed unchanged.
  • Scope raw-body handling to the webhook route before ordinary JSON middleware in Express; check each other framework and provider against its current protocol.
  • A valid signature does not mean one delivery or completed business work; design durable acceptance, event deduplication, and business-action idempotency separately.

If you use Stripe, a webhook can fail signature verification even when the parsed JSON fields look identical. The verifier needs the original UTF-8 request body Stripe sent, the Stripe-Signature header, and the secret for the current webhook endpoint—not an object that happens to parse to the same values. If any input is wrong, the official library cannot validate the signature. Preserve and inspect those three inputs before parsing the event, deduplicating it, or applying business actions. These details come from Stripe’s current documentation; another provider’s signature protocol may differ.

Why are equal field values not the same signature input?

JSON permits different textual representations of the same data. Matching fields and values do not prove that the original bytes match. For example, suppose the body contains an indented {"amount": 100}. Parsing it and calling JSON.stringify removes the whitespace and newline. The object’s meaning is unchanged, but its UTF-8 byte sequence is different. Property order, Unicode escaping, number formatting, or duplicate-key handling can also make a parse-and-reserialize result differ from the original text.

Verification asks whether the supplied input matches what the provider signed, not whether two parsed objects are equivalent. A serializer cannot be expected to reproduce the exact whitespace and character choices made by the sender. Logs often discard those distinctions too, so seeing the same fields in two log entries is not proof that the verifier received the original bytes.

A small local probe archived with this rewrite used Node’s crypto module to compute the same demonstration HMAC over a hypothetical JSON string and its parsed-then-reserialized form. The original input was 38 UTF-8 bytes; the reserialized input was 31, and the demo digests differed. The secret is explicitly a demo value. This was not a Stripe SDK test, a real endpoint secret, or a live event verification. It demonstrates only that changing bytes changes a digest computed over those bytes; it is not production acceptance evidence.

Which three inputs should you check first?

The endpoint troubleshooting guide lists the raw request body, the Stripe-Signature header, and the endpoint secret as verification inputs. It says a signature failure means at least one of them is incorrect. Checking them in this order is more useful than repeatedly changing verifier code because it separates body transformation, header extraction, and configuration selection.

First, confirm that the verifier receives the actual request stream, rather than a parsed object, log copy, or business DTO. In a diagnostic test, you can compare the length of the Buffer entering the route with the Buffer passed to the verifier, and record a hash instead of retaining a sensitive payload. Matching hashes show that the observed bytes match at those two points; they do not prove the event is authentic. Only the official verification library accepting the signature under the complete protocol completes source authentication.

Second, use the framework’s supported raw-body path and extract the correct header. Stripe’s Express example places express.raw({type: 'application/json'}) on the webhook route, then passes request.body, the header, and the secret to the library. If global express.json() has already consumed and parsed the stream, the later handler may receive only an object or may be unable to read the original stream again. Scoping raw-body handling to that route is usually easier to reason about than disabling JSON parsing for the whole application. For other frameworks, use their current request-body lifecycle and Stripe’s applicable example; do not paste Express middleware into an unrelated stack.

Third, confirm that the secret belongs to the endpoint currently receiving the event. Stripe explicitly says the secret printed by CLI stripe listen differs from the secret for a Dashboard or Workbench-managed endpoint. A mismatch will fail consistently. Trying a production secret “to see whether it works” can hide an environment-routing bug and increase exposure. Read secrets from controlled configuration. Diagnostic records should keep environment, endpoint identity, configuration version, and error category—not the secret itself.

Why is a non-empty signature header not enough to assemble your own check?

Stripe-Signature is a protocol input and should be parsed by the official verification function. The header can contain multiple versioned signatures and optional diagnostic data; Stripe says not to assume a fixed field order or count. More importantly, Stripe documents that debug metadata such as secret, destination, or payload is unsigned and must not be treated as authentication evidence. It may help diagnose a route or body mutation, but an attacker can forge it.

Do not “fix” the issue by accepting any parseable JSON, removing verification, or reconstructing a body from logs. Those changes turn a transport or middleware bug into an authentication gap. For Stripe snapshot events, use the SDK’s constructEvent; for thin events, follow its current parseEventNotification flow. Event formats and SDK entry points differ, but both still require the right signed input and endpoint secret. When changing SDK versions or event formats, check the current setup guide rather than guessing from old code.

What remains after verification: retries and business state?

Authenticating a request does not mean it will arrive only once, arrive in creation order, or finish the business action. Stripe’s event documentation says failed live-mode deliveries are retried with exponential backoff for up to three days; sandbox retry behavior differs, and event order is not guaranteed. A handler should distinguish “signature valid,” “durably accepted,” “processing,” and “business terminal state.” A 2xx response or successful verification log alone does not prove an order is complete.

Consider a hypothetical order flow. After verification, write a receipt keyed by the provider event ID with a uniqueness constraint. Persist the work item in the same database transaction, and return 2xx only after that chosen acceptance boundary commits. A worker claims the item and marks it processing; success records completion, while a transient error leaves a recoverable state. If the process fails before the work item is committed, it must not already have acknowledged success. If it fails after persistence but before fulfillment, the item should be claimable again. If fulfillment succeeds but the terminal-state write fails, the external business action needs its own idempotency key or reconciliation method; uniqueness on the event ID cannot roll back an external side effect. This is a design example, not a Stripe integration or payment test performed for this article.

Duplicate deliveries are also part of the documented behavior: the same event can arrive more than once, and in some cases separate Event objects can describe the same underlying object action. Event ID can identify duplicate deliveries; distinguishing separate events may require the object ID together with the event type. This affects the deduplication key: deduplicating only by order ID can suppress a legitimate later state event, while deduplicating only by event ID may not prevent two separate events from repeating one business action. Define the identity of the business action before choosing the uniqueness constraint and state transition. The site’s article on API retries and idempotency covers client-request idempotency keys; webhook event IDs and business-action keys are related but different concepts.

How can you check byte preservation without over-reading one successful sample?

Build a set of distinguishable checks in a test environment: the original body with its matching test signature should pass; changing only whitespace, property order, or escaping should be rejected by the provider’s verifier; using a CLI secret for a Dashboard endpoint should fail; placing ordinary JSON middleware before the verification route should make the missing or altered raw input observable; receiving the same event again should not trigger a second business action; and failures at different persistence boundaries should recover according to the state machine.

Each check proves only its own boundary. A body hash covers byte equality, not signature validity. An official SDK test covers that SDK and event format, not every proxy, API Gateway, or framework adapter. A local synthetic probe does not validate your production secret or endpoint. For this article, only the Node synthetic HMAC probe was actually run; no Stripe CLI, framework server, real webhook endpoint, or production payment flow was started. Production acceptance should trace raw input, header extraction, secret source, verification result, durable acceptance, and business terminal state in the target stack without logging secrets or complete personal data.

If you also need to decide when a successful response may be returned, see the article on HTTP 202 and terminal states. It distinguishes accepting asynchronous work from completing the business operation; it does not replace a webhook protocol. Finally, express.raw is one Stripe-documented input-preservation pattern for Express, not a universal template for every provider and framework. Start with byte source, request header, and endpoint secret; then verify durable enqueueing, event deduplication, and business idempotency separately. A semantic JSON comparison cannot substitute for those checks.
