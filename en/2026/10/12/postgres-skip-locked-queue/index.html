An empty SKIP LOCKED result is not an empty queue

An empty SKIP LOCKED claim means this statement acquired no eligible row; track pending, claimed, completed, and recoverable work separately.

Key takeaways

  • An empty SKIP LOCKED result means this statement did not acquire an immediately lockable matching row; it does not prove there is no backlog.
  • Transaction row locks end with the transaction; work that continues afterward needs durable claim state, a lease, and an explicit recovery owner.
  • Idempotency, ordering, fairness, and completion are different promises and need separate failure-path and concurrency checks.

No. A FOR UPDATE SKIP LOCKED query returning zero rows proves only that this statement did not acquire a qualifying row that it could lock immediately. Another transaction may hold a pending row, or work may already be claimed, unfinished, or awaiting recovery. To decide whether the business queue is empty, inspect durable task state and the recovery rules; do not treat one claim attempt as proof that all work is complete.

The statement does not see the whole queue

In the version 19 SELECT manual, SKIP LOCKED is defined to skip selected rows that cannot be locked immediately. The resulting view is inconsistent, so it is unsuitable for general-purpose queries, but it can reduce row-lock contention when multiple consumers access a queue-like table. The option changes row-level lock waiting; the statement still takes the ordinary table-level ROW SHARE lock. “Inconsistent” here does not mean corrupted data. It means the query deliberately omits rows currently locked by other transactions.

Imagine a jobs table with one due row in pending state. Consumer A begins a transaction and locks that row, but has not committed. Consumer B selects one due pending job with FOR UPDATE SKIP LOCKED. If no other matching row exists, B can return nothing. That result says B did not claim a job. It cannot tell whether there is no pending job at all or whether the only pending job is currently locked by A. This concurrent timeline is a hypothetical explanation; no database query was run and no lock wait was measured.

Lock lifetime is another reason not to treat a row lock as business execution state. PostgreSQL's explicit-locking documentation says that a normal lock is ordinarily held until the transaction ends. Once A commits or rolls back, the lock no longer indicates that a worker is still processing the job. If the application commits a claim and only then calls an external service, the earlier lock cannot prove that the call succeeded. Keeping a slow external call inside the transaction creates a different problem: it extends the transaction and lock duration, increasing the impact of waits and failures.

Separate “claimable now” from “work still outstanding”

A queue needs to distinguish at least pending, claimed, completed, retryable, and terminally failed work. Names vary, but each transition needs an explicit condition and an owner. For example, a claim can atomically change one pending row to claimed, record a worker identity, lease deadline, and attempt count, then use RETURNING to pass the row actually updated to the caller. The UPDATE manual says RETURNING computes values for rows actually updated.

The following is a proposed production-shaped example for discussing the boundary. It has not been executed. Columns, isolation, indexes, clock source, and error handling must be designed against the actual schema:

WITH candidate AS (
  SELECT id
  FROM jobs
  WHERE state = 'pending' AND available_at <= now()
  ORDER BY available_at, id
  FOR UPDATE SKIP LOCKED
  LIMIT 1
)
UPDATE jobs AS j
SET state = 'claimed',
    worker_id = $1,
    lease_until = now() + interval '2 minutes',
    attempts = attempts + 1
FROM candidate
WHERE j.id = candidate.id
RETURNING j.id, j.payload, j.lease_until;

Do not copy the two-minute lease as a universal value. Instead, make selection, locking, and the state transition one reviewable atomic boundary. After the database commit, the worker can perform slower work outside the transaction. If the process exits before commit, rollback leaves the job available to be claimed again. If it exits after commit, the row lock is gone, but the durable claimed state and lease show that the job is waiting or needs recovery. Reclaiming an expired lease should also increment an attempt counter and preserve the previous failure reason; resetting a row to pending without history makes diagnosis harder.

Isolation affects what “current” means. In version 19, READ COMMITTED is documented as the default isolation level: an ordinary SELECT sees data committed before that statement began, and later statements in the same transaction receive a new statement snapshot. A monitoring COUNT(*) is therefore a snapshot of committed states visible to that counting statement, and it can become stale immediately. The count may be useful for backlog observation, but it does not share exactly the locking predicate or instant of a claim query.

External side effects create an unknown-outcome window

Suppose a worker claims a task and calls a payment, email, or third-party API. The external service performs the action, but the worker disconnects before writing completed. The database lease eventually expires, and another worker may retry. This is not a row-lock bug; it is the result of two systems lacking one shared atomic commit. If repeating the business side effect is unsafe, pass a stable idempotency key so the receiver or a local effect record can recognize duplicate attempts. Also prevent an old worker's late completion update from overwriting a new owner after a reclaim. A lease timestamp alone cannot revoke a network request already sent. When needed, use a monotonically increasing fencing token and require the side-effect boundary to validate it.

That is why “claimed once, therefore executed exactly once” is not a guarantee provided by SKIP LOCKED. Row locks close a race in concurrent row modification; they do not replace cross-service transactions, idempotency, outcome reconciliation, or a dead-letter policy. After a timeout, the application may not know whether the remote side acted. Immediately marking the task failed and retrying can duplicate the effect; marking it complete can lose work. A more honest intermediate state is “outcome pending confirmation,” followed by an idempotency lookup, callback, reconciliation task, or manual review. Choose based on whether the effect is repeatable, whether the receiver supports idempotency, and whether the business tolerates delay or duplication.

Skipping locks improves throughput, not fairness

When a consumer skips a locked row at the head of the queue, it may process later jobs first. This improves progress on currently available work; it does not promise strict first-in, first-out order, nor a deadline by which every row will be processed. A long-held lock, repeated failures and requeues, or a steady stream of another class of work can keep an older job behind. A stable sort order for LIMIT cannot eliminate those cases, but it makes available choices easier to explain. The SELECT manual recommends pairing LIMIT with an ORDER BY that constrains a unique order. Sorting by available_at, id, for example, uses a unique ID to break timestamp ties. Without a unique order, plan changes can alter which subset is selected.

For per-account strict ordering, first ask whether a later task is allowed to pass an earlier one. Work for separate accounts may run in parallel while each account still needs its own partition, sequence number, or single-consumer lane. A global jobs table with SKIP LOCKED alone cannot establish strict FIFO. If tasks have deadlines, priority rules may also need aging; otherwise frequent new high-priority jobs can continually pass older low-priority work. By contrast, independent notifications that tolerate brief reordering may accept the trade-off. The right mechanism follows from the allowed reordering, latency, duplicate, and recovery semantics.

Prove the promise with monitoring and concurrent tests

Keep “pending count,” “age of oldest pending item,” “active leases,” “expired leases,” “retry attempts,” “outcome pending confirmation,” and “completed count” separate. A worker returning no row can signal “no matching job is immediately claimable now.” Show the queue as empty only when the business predicates, durable states, and recovery paths agree there is no outstanding work. If expired leases or unknown outcomes remain, a dashboard showing only pending = 0 hides backlog.

In a test environment, two real database connections can reproduce the lock race: connection A locks the oldest job but does not commit; connection B runs the claim. Verify that B neither reports A's job as complete nor updates another job incorrectly. Then test A committing, rolling back, and disconnecting. Simulate a worker exiting before a claim, after the claim commit, after a successful external call but before its completion write, and after a lease expires while the old worker returns late. Record state transitions, attempts, leases, and idempotency keys. Check whether the old worker can overwrite new ownership and whether an old task can remain skipped indefinitely. This article did not execute SQL or concurrency tests; these are checks an implementation should run in its own environment.

Finally, decide whether a database table remains the right queue. For complex delayed scheduling, broad cross-region consumers, message retention, visibility timeouts, or many independent subscribers, compare a dedicated messaging system's semantics and operating cost. A database design may be easier to review when task volume and consistency boundaries are clear. Either way, an empty claim, no pending rows, no active work, and business completion are four different facts.
