Why is the database file still large after VACUUM?

Ordinary VACUUM mainly makes space reusable; shrinking a file is a different rewrite outcome with lock, temporary-disk, and workload costs.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-25 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • Ordinary VACUUM removes old versions that are no longer visible and makes their space reusable in the table; it usually does not return that space to the operating system.
  • VACUUM FULL and similar rewrite operations can compact a relation, but require ACCESS EXCLUSIVE locking and extra temporary disk space.
  • Name whether a measurement covers a relation, database, or filesystem before accepting a capacity result; deleted row count is not released disk bytes.

An ordinary VACUUM finishing while database files remain large does not, by itself, mean cleanup failed. Its main job is to remove old row versions that no transaction still needs and make the corresponding space available for later writes to reuse within the table. Returning file space to the operating system is the outcome of a different compaction or rewrite operation. First name the goal: reuse inside a table, a smaller relation file, or more free capacity on the storage device. Only then can “the file did not shrink” be judged as a failure.

DELETE creates old versions before it changes file size

PostgreSQL uses MVCC. Updating a row creates a new version; deleting one does not immediately erase its physical version, because a transaction that is still running may need to see it according to its visibility rules. The PostgreSQL 19 routine-maintenance manual explains that VACUUM can reclaim those old versions only after they are no longer needed by any transaction. “Reclaim” first means reuse within the database, not truncating the end of a file.

Imagine an append-heavy event table from which the application deletes many expired records. A standard cleanup scan may leave pages available for new tuples, but those free regions can be scattered among pages that still hold live rows. Later inserts into the same table can reuse those holes while the relation file keeps its existing page layout. A filesystem or volume graph may therefore show no decrease corresponding to the deleted-row count. This is a mechanism example, not a measured ratio or capacity result from a real database.

There is a narrow exception: if one or more pages at the end of the table are entirely free and the required exclusive table lock can be obtained easily, ordinary VACUUM may truncate those tail pages and return that space to the operating system. The careful statement is “usually does not return space,” not “never shrinks.” Even an occasional reduction does not make standard cleanup equivalent to compacting the whole relation.

Old versions also have to become invisible before they can be reclaimed. Long-running transactions, old prepared transactions, or replication slots retaining an old snapshot can delay some cleanup. If repeated VACUUM runs do not remove the versions you expect, first check whether any of those visibility horizons remain and whether autovacuum is keeping up with the workload. Repeating the command can add I/O without making a still-visible tuple eligible for removal.

File size, reusable space, and free disk are different measurements

The number of deleted rows is a business-change count; it is not a count of bytes that can be released. A table relation file can contain live rows, free pages, page overhead, and other structures. Indexes and TOAST data also consume storage. Outside the database directory, WAL, logs, backups, and other databases can affect a filesystem or cloud-volume measurement. A change in a volume graph cannot be assigned directly to one table's VACUUM. Each comparison should name the object, collection method, and time: a relation, a table plus its indexes, a database, a data directory, or a mounted volume. “Disk usage” by itself is not a sufficient measurement definition.

Keep two kinds of observation: relation-level space and cleanup progress, plus operating-system or managed-platform capacity. During a standard vacuum, pg_stat_progress_vacuum can report its phase and block progress. The PostgreSQL 19 progress manual says rewrite progress for VACUUM FULL is reported through pg_stat_progress_repack and is also visible in the compatibility view pg_stat_progress_cluster. These views are snapshots. Collection settings and permissions in a managed service can also limit what is visible. No such query was run here, and there is no cleanup log from a real environment.

VACUUM FULL is a rewrite purchased for shrinkage

VACUUM FULL writes a new, compact table file; CLUSTER and REPACK also use rewrite paths. The VACUUM reference and routine-maintenance manual explain that a rewrite can take a long time and needs additional disk space for the new copy while the old copy remains. VACUUM FULL normally holds an ACCESS EXCLUSIVE lock on the table, blocking concurrent operations that access it. When storage is already close to its limit, temporary capacity may itself prevent the rewrite from starting or finishing.

Standard VACUUM makes a different trade-off. It can run alongside normal SELECT, INSERT, UPDATE, and DELETE operations on the table, but produces substantial I/O that can affect other sessions. It also takes a maintenance lock; “not ACCESS EXCLUSIVE” does not mean “no contention.” The explicit-locking manual lists the SHARE UPDATE EXCLUSIVE lock used by ordinary VACUUM. VACUUM ANALYZE combines cleanup with planner-statistics refresh. Better statistics may improve query planning, but are not a substitute for compacting a file.

Choose from the goal. If the aim is to let an active table reuse space in subsequent writes, standard VACUUM may be producing the intended result. If the requirement is to reduce a particular table's filesystem footprint, assess a rewrite, temporary capacity, maintenance window, and interruption budget. If future writes will refill the freed space, compressing the file to its minimum once may quickly reverse; routine standard cleanup and tuned autovacuum may better match steady-state capacity management. The manual says autovacuum reacts to activity and will never issue VACUUM FULL. This article did not inspect any instance's settings or runtime state.

Remove a cleanup blocker before choosing a rewrite

Two different situations are often described as “VACUUM did not release space.” In one, old versions remain visible because a transaction or replication horizon prevents cleanup. In the other, those versions are eligible and cleaned, but the space is retained for reuse inside the table. The first calls for examining long transactions, prepared transactions, and replication slots that hold back the visibility horizon. The second calls for comparing future reuse with relation-file shrinkage. Watching only the operating-system metric can make correct reuse behavior look like a database failure.

An acceptance record can compare the target relation and its associated indexes before and after maintenance, database and filesystem capacity, dead-tuple and autovacuum statistics, active transactions, and progress views. Then observe a period with real writes to see whether free pages are reused. If considering a rewrite, also record lock waits, affected reads and writes, temporary capacity, command phase, and failure recovery. Verify command and metric availability against the deployed PostgreSQL major version and the managed service; do not assume a cloud console exposes every server view.

For tables whose contents are periodically discarded in full, compare TRUNCATE, partition retirement, and row-by-row DELETE rather than defaulting to “DELETE, then FULL.” These choices differ in transaction-snapshot, foreign-key, trigger, and user-visible semantics, so validate them against the actual dependencies.
