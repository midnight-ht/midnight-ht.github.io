Why can one URL return the wrong language from cache? Treat Vary as a contract

One URL can select different representations from request headers. Use Vary to state reuse conditions, then verify defaults, private responses, and proxy cache policy separately.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-25 · Estimated read 18 min
Translations
zh-CN en

Article

Key takeaways

  • Vary expands a cache match condition by naming request fields that may have selected the representation.
  • Absence is a value too: a request without Accept-Language matches only another request without that field.
  • Vary does not authorize access or decide whether a shared cache may store private content; cache directives and authentication rules do that.

When one URL returns different bodies, a cache needs more than the address: it needs to know which request fields took part in selecting that representation. Vary is the response header through which a server declares that relationship. It can prevent an English response cached first from being reused for a Chinese request, but it does not control freshness, allow private data into a shared cache, or replace authorization checks.

Separate the resource from its representation

A resource is the object addressed by a request; a representation is the form selected for that request. The same /guide can return Chinese or English according to Accept-Language, or different compressed forms according to Accept-Encoding. The address is unchanged while the bytes differ. RFC 9111 §2 defines a cache key as including, at minimum, the request method and target URI. Many common caches store only GET responses, so in practice their key may be only the URI. If a server also selects a body from request fields, those selection conditions need to participate in matching.

That does not mean Vary makes every intermediary use exactly the same internal key. It supplies protocol-level reuse conditions. After seeing Vary: Accept-Language on a stored response, a cache cannot reuse that response directly unless the nominated field on the new request matches the request that produced the stored response, or the cache revalidates it with the origin. A cache vendor may also support additional key configuration. That is deployment behavior, not a substitute for the HTTP contract.

Trace two language requests through the cache

Suppose /guide is public documentation and the origin chooses its body from Accept-Language. The first visitor sends Accept-Language: en; the origin selects English and returns Vary: Accept-Language with a freshness directive that permits caching. That stored entry contains more than “the response for /guide”: it retains the request condition that produced the representation. A second visitor requests the same URL with zh-CN. The field differs, so the old English response does not match. Because the field differs, reuse should miss; the cache must forward the request or validate under its rules before storing a Chinese variant. One URI can therefore have separately reusable representations.

The default branch is easy to miss. A third request has no Accept-Language, and the application may fall back to Chinese. If that response omits Vary while other variants include it, response metadata becomes inconsistent across the same resource. The cache specification calls out a default response that omits Vary as a source of interference with later preference-bearing requests (RFC 9111 §4.1). When multiple responses are stored and some omit Vary, the specification says a cache SHOULD choose the most recent response with a valid Vary value. Actual behavior still depends on cache products and response order; this is not a promise that every configuration can never return the wrong representation. A safer origin contract makes every cacheable branch express the same selection dimension: English, Chinese, no-preference fallback, and conditional responses for the same resource all need inspection.

An absent request field is not meaningless noise. Under the matching rule in RFC 9111 §4.1, when the original request omitted a nominated field, a new request can match only if it omits that field too. Therefore “no preference” is not the same variant as Accept-Language: en; even if the application eventually returns English for both, treating them as equivalent needs to follow the actual application selection rule. Normalization of field values also follows that field's own semantics. Application code should not guess that case or ordering differences are irrelevant.

What Vary: * and a field list actually mean

Vary: Accept-Language, Accept-Encoding says those request fields may have influenced selection, so a cache uses them in later matching. A field list does not mean all headers matter, and it is not a security policy. It should reflect inputs the origin actually uses to choose content. RFC 9110 §12.5.5 allows an origin to omit Vary when the benefit of cache reuse outweighs the significance of the variation, but that decision weighs the risk of wrong reuse against shared-cache reuse. A server should not return different language bodies while assuming the URI alone is enough.

Vary: * means other request aspects may have influenced the representation, potentially including a client network address outside the message fields. A recipient cannot determine locally whether the stored response fits and must forward the request; such a response always fails ordinary Vary matching. A proxy MUST NOT generate the wildcard itself. Treating * as a universal cache-safety switch misunderstands it: it prevents local reuse based on ordinary matching, but does not define a model for isolating user identities.

Variant matching is not private-data protection

If a page returns each user's balance, inbox, or admin panel based on cookies or login state, adding Vary: Cookie does not by itself make shared caching safe. Vary answers whether a representation can satisfy a later request. Cache controls answer which kind of cache may store it, for how long, and when it must be validated. Authorization answers whether the current user may read the resource. These are different questions.

The private directive in RFC 9111 §5.2.2.7 means a shared cache MUST NOT store the response, while a private cache may store it under the applicable constraints; no-store is another storage restriction. Requests containing Authorization also have dedicated shared-cache rules. RFC 9110 §12.5.5 explains that it is generally unnecessary to list Authorization in Vary because the authentication field already restricts reuse across users. Whether a specific response may be shared still depends on its authentication method, response directives, and actual cache layers. For a private page, define private or a stricter storage policy before discussing content-negotiation fields.

Variation also has a cost. If a server varies on User-Agent, cookies, language, compression, experiment groups, and every possible preference whether or not it uses them, many combinations become distinct variants. Reuse falls and storage or origin traffic can rise. The reverse failure is possible too: if the server chooses different pages by experiment group but emits only Vary: Accept-Language, a cache can reuse group A's page for group B. Choose fields by asking which inputs actually change reusable content, not by listing everything in a request. If the selector is a cookie, client location, or server-side rollout state, first decide whether the response should enter shared caching at all; hit rate should not override isolation.

Use a request matrix to locate the missing condition

For a public /guide, design tests with no Accept-Language, en, and zh-CN; for each language, add only the Accept-Encoding values the service really supports. Record whether each request field is absent or present, the origin's selected-representation marker, response Vary, Cache-Control, Age or provider cache status, headers before and after proxies, and a body digest. Send requests in the order English, Chinese, no preference, then English again; repeat with the order changed. If the result changes with access order, inspect whether the default branch omitted Vary and whether the edge caches the origin field or overrides its key.

This is a verification plan, not an experiment performed for this article. Correlate browser developer tools, origin logs, and CDN logs with a request identifier; an Age value or one HIT field alone cannot prove the selected content is correct. If the origin sends Vary but a proxy removes or rewrites it before the browser receives the response, capture every hop and find which layer changed it. Sample more than one cache point as well: one edge having stored English says nothing about another edge that saw requests in a different order.

A final review can follow three steps: list the real inputs that choose the body; make cacheable response branches, including the default branch, return Vary consistent with that selection; then review private-data storage policy separately from Vary matching. If the problem is staleness or revalidation instead, representation matching does not replace entity tags or conditional requests. See the site article on HTTP cache validation semantics for that separate contract.
