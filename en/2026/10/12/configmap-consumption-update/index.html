Why does a process keep old settings after a ConfigMap update?

After a ConfigMap update, a process may still use old settings. Trace environment variables, projected volumes, subPath mounts, application reload, and each replica’s effective revision.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-25 · Estimated read 26 min
Translations
zh-CN en

Article

Key takeaways

  • The ConfigMap object, Pod input, and process adoption are separate states.
  • Projected volumes eventually update; environment variables need new Pods, and subPath does not update.
  • Verify fleet consistency using the effective configuration revision reported by each process.

The ConfigMap shows the new value, but the service still behaves according to the old rule. Those states are not necessarily contradictory: you may be looking at different stages. The object was saved; a Pod input may have changed; there is still no evidence that the application reloaded it. First identify how the process consumes the configuration. Environment variables usually require new Pods. A regular ConfigMap volume eventually exposes updated content, but the application must read and accept it. A subPath mount does not receive the update. Treating all of these cases as “the ConfigMap did not refresh” sends the investigation toward the wrong operation.

Break “the new configuration” into separate states

A useful investigation follows at least five stages: data in the API object, the object and key referenced by the Pod template, input visible inside the container, configuration currently adopted by the process, and behavior exposed by all replicas. Each stage has its own update point and can remain stale independently. A successful object update proves only that the API accepted a write. It does not prove that referencing Pods were recreated, that a mounted path contains a new file, or that the application parsed the value successfully.

Kubernetes documents four ways to consume a ConfigMap: command or arguments, environment variables, files in a read-only volume, and application code that reads the Kubernetes API. For the first three, the kubelet supplies the data when it launches containers. The fourth requires application code and can subscribe to object changes. This distinction determines who observes updates, who initiates reload, and whether the relevant evidence lives in the container, filesystem, or application telemetry. The official ConfigMap documentation describes these boundaries.

Record a revision marker at the process-adoption stage instead of relying only on an object resourceVersion. For example, a configuration could contain an operator-managed revision such as policy-42, while logs, a diagnostic endpoint, or a health view reports the revision the process has actually enabled. This marker is an application-design recommendation, not a business-consistency protocol provided by ConfigMaps. It helps connect a request, an instance, and a configuration. If the application merely echoes an object annotation without updating its process state after successful validation, the marker is misleading.

Four consumption methods, four update contracts

Environment variables and command arguments are taken from the Pod configuration when a container starts. Changing the source ConfigMap does not rewrite the environment of an existing process. A replacement Pod starts with the updated input. Use that replacement to make the new value available through this path. The Kubernetes tutorial demonstrates this distinction: after editing a ConfigMap, the old Pod continues to print the old environment variable; after a rollout replaces it, the new Pod prints the new value. If no new Pod identity appears, waiting for an existing process’s environment variable to change is pointless.

A regular ConfigMap volume follows a different path. The kubelet checks mounted content during periodic synchronization and can learn of changes through watch, a TTL-based cache, or direct API-server requests. Projected files are eventually updated, but the total delay includes the kubelet sync period and the propagation delay of the selected cache strategy. This is not a transaction that switches every Pod on every node at the moment apply returns, so avoid promising one fixed number of seconds across clusters. The cache strategy and node configuration affect the delay; verify the target cluster’s settings and acceptable window.

Two other boundaries are often confused. First, a ConfigMap key mounted through subPath does not receive ConfigMap updates; the eventual-update statement for a normal volume does not apply to it. Second, even after a regular mounted file contains new data, the application may read only at startup or may still use a previously parsed in-memory object. A new filesystem input does not parse, validate, switch, or roll back application state on its own.

Reading the API directly is a fourth option. It avoids the node-to-volume projection path but moves more work into the application: authorize access to the correct namespace and object, maintain or recreate a watch, handle disconnection and reconnection, and define what a partial update means for requests already in progress. The documentation says applications can subscribe to changes. Retry behavior, RBAC scope, concurrent switching, and error handling remain implementation responsibilities. Removing file projection does not remove application-level failure modes.

The file changed, but the program may not have reread it

Updating a projected ConfigMap volume is not simply an in-place overwrite of one file. In the pinned Kubernetes AtomicWriter implementation, user-visible paths lead to a timestamped directory, and switching the ..data symlink publishes a new set of content. The source says consumers can monitor changes to ..data. That explains why observing only one already-open file or an assumed-stable underlying path may not be equivalent to observing a projected revision change. The container environment and application’s file-watching library still need separate verification. See the pinned AtomicWriter implementation.

Even a reliable event needs a safe adoption rule. Separate “candidate discovered” from “candidate enabled”: read the candidate, parse and validate all dependent fields, then replace the process’s configuration reference through a controlled operation. If validation fails, retain the last usable revision and report the instance, candidate revision, failure reason, and revision still in use. This is application design advice, not a kubelet guarantee. If the configuration spans multiple files, make sure they belong to the same projected and business revision; do not activate half of one version and half of another.

How a hypothetical change can create mixed revisions

Suppose a service has three replicas, and policy-41 limits concurrent work per request to 8. An operator changes the ConfigMap to policy-42 and raises the limit to 12. After the object update, the three Pods may see the new file at different times. Seeing the file also does not mean parsing completed. If two instances validate and enable policy-42 while the third rejects the candidate because a new field is missing and retains policy-41, a load balancer may send similar requests to instances following different rules.

The replica count, revisions, and values are hypothetical examples; no Kubernetes cluster was started, no kubectl command was run, and no propagation latency was measured for this article. The example shows why an observable adoption state must bridge “ConfigMap changed” and “service changed.” A Deployment’s desired template, the object’s update time, or container file content alone cannot answer whether the third process adopted the new value.

A bad failure policy can be more dangerous than a delay. If a missing field silently defaults to zero, the process might accept a configuration incompatible with the previous rule. If it activates fields as they are read, requests can observe an internally inconsistent state. If the only log says “reload complete,” the next investigator still cannot tell which revision completed. Decide whether a parse failure keeps the old version, blocks a new instance from starting, or rejects a specific class of work. Make logs or diagnostics report the revision actually in use. For high-risk rules, consider validating in shadow mode or switching a limited set of instances first. Whether those approaches are safe depends on application architecture and business tolerance; not every setting is suitable for hot reload.

Choosing among restart, hot reload, and versioned objects

When values enter through environment variables or startup arguments, and a configuration change is meant to be a release event, a rolling Pod replacement is often easier to audit: the Pod template and new replica set can be associated with a workload revision. The cost is dealing with scheduling, startup, termination, capacity, and service continuity. The Kubernetes update tutorial also notes that without an explicit rollout, Pods created for another reason, such as scaling, may read the new value while older Pods keep the old environment. Two configuration revisions can therefore coexist temporarily.

If the service needs faster updates and the application can validate and switch safely, a regular projected volume with application reload avoids restarting on every change. It requires evidence for three separate conditions: the projected input eventually changed, the application reopened or watched the correct path, and every relevant replica reports the same effective revision after acceptance. Proving only the first condition can make automated file projection look healthy while business behavior remains unchanged.

If auditability and rollback boundaries take priority, create a differently named immutable ConfigMap for each revision and update the Pod template to reference the new name. The official tutorial explains that immutable objects cannot have their data changed; creating a new object and changing the Deployment reference triggers a rollout. That makes version relationships easier to retain, but requires an object-retention and cleanup policy, reference changes, and careful treatment of sensitive data. ConfigMaps are for non-confidential data; they are not a replacement for Secrets. Versioned objects still do not prove that the application has adopted the new rule safely.

How can you verify the revision each process adopted?

Start with a low-risk change that is easy to reverse, and label each piece of evidence with the object, Pod, and time. Confirm the changed ConfigMap content. Check that the workload references the intended object and key, and classify its consumption method as a variable or mount. Inspect the value or projected file in each Pod. Finally, ask the application for its active revision and connect that evidence to a diagnostic or safe request path bound to that instance. Do not treat a changed file as proof of a read, and do not infer fleet-wide consistency from one response through a load balancer.

Three bounded comparisons are useful to design. First, for an environment-variable reference, observe that an existing process retains its old value after the object changes, then use a controlled rollout to confirm the new process input. This task did not execute that test. Second, for a regular volume, wait for the projected revision and determine whether the application polls, watches, or keeps its startup value; test subPath separately and expect it not to follow object changes. Third, provide a recognizable but invalid candidate revision and confirm that the process does not claim adoption while its previous revision remains active. Each exercise should use isolated test resources and retain the original object snapshots and instance logs; do not overwrite unexplained failures with a later successful attempt.

A common question is, “Do I need to restart Pods every time?” It depends on the input and application contract: environment variables need new processes; a regular volume eventually changes files, but the process must support safe reload; subPath does not update; direct API reads leave change handling to the application. Another question is, “Can the ConfigMap’s update time count as release completion?” No. That time shows a change at the object boundary. Acceptance still needs to align each instance’s effective revision with the target and show that requests are not reaching replicas that still use the old one.

When investigating an old value, do not begin by restarting repeatedly. Identify how the configuration enters the process, find the first boundary where object, container input, and effective state diverge, and then record which instance adopted which revision and when. Keep that evidence separate from Deployment progress and business acceptance. If changing the Pod template is the right way to trigger a rollout, see template changes while a Deployment is paused.
