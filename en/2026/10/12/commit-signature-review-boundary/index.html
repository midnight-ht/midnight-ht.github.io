A verified signature can still leave the review approval on the wrong revision

Verified means the platform validated a commit signature. It does not show that a reviewer approved the current diff. Bind review, checks, artifacts and deployment to exact revisions.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-25 · Estimated read 26 min
Translations

Article

A Verified badge means GitHub validated a commit signature under its rules. It does not, by itself, show that anyone reviewed the code, that tests passed, or that this revision is live. A release record should bind signature status, approval, automated checks and the deployed artifact to exact commit IDs or digests, then confirm which of those records are actual merge gates in the repository.

A signature badge and a review approval prove different things

GitHub's documentation on commit verification statuses explains that the platform displays verification statuses for signed commits and tags. By default, a commit signed with a GPG, SSH or S/MIME key and successfully verified is marked Verified. With vigilant mode, status also depends on the relationship between the author and committer. For example, when the author is someone other than the committer and has enabled vigilant mode, the status can be Partially verified. GitHub says that in this case the signature does not guarantee the author's consent. The badge is therefore a specific signature-verification result, not a verdict on code quality, author authorization or the review process.

Git's signature-format manual describes a commit signature as a signature on the commit object. That object includes the tree ID, parent commit, author and committer information, and message. Verification helps a recipient determine whether the signature can be checked with the relevant key and whether the signed object remains intact. Signature verification alone does not determine who should control that key, whether that person has authority to approve a change, or which files a review covered. The badge does not inspect review comments or fill in those decisions.

Review approval answers a different question: whether an authorized reviewer approved a set of changes in a pull request, and whether repository policy requires that approval before merge. An automated check reports whether a particular workflow passed for a particular commit. The release record should identify the artifact's source revision, whether the deployment system accepted it, and whether the public page or service now serves that artifact. Collapsing these into “verified” loses the objects and conditions behind each claim.

Follow two revisions to see where the evidence splits

Consider a clearly hypothetical example. A pull request initially points to commit R1. R1 has a verifiable signature, a reviewer inspects the diff and approves it, and CI reports success for R1. The developer then pushes R2, which changes an authorization check without updating the review notes. R2 is also signed by a valid key, so its page still shows Verified. If the team saves only a screenshot of the badge and the old approval, the record looks complete. In reality, R1's signature says nothing about whether R2's new diff was reviewed, and R1's CI result says nothing about whether R2 passed.

Two states changed independently. First, R1's signature remains a fact about R1; adding R2 to the branch does not turn it into a signature on R2. Second, whether the R1 approval can still satisfy merge policy depends on branch protection or ruleset settings and the current pull-request state. GitHub offers an optional setting to dismiss stale approvals when the diff changes. A separate option requires the most recent reviewable push to be approved by someone other than the person who pushed it. Repositories do not all enable the same options. If policy does not require stale approvals to be dismissed, the interface state may differ from the team's expectation. Maintainers should inspect the actual rules before merging instead of assuming every later commit automatically forces another review.

The same applies to a green CI result. Tie the result to the commit SHA and workflow run. Even if the workflow succeeded, a result for R1 does not automatically cover R2 if the merge candidate now contains R2. With a merge queue or merge commit, the final SHA can differ from the pull-request head. Confirm which merge candidate the required check evaluated and retain the actual build input in the release record. This is a hypothetical workflow used to explain state relationships. No incident at this site or at a customer is being described, and no repository rules were configured for this article.

Do not substitute signature, review and status-check rules

GitHub's ruleset documentation lists “require signed commits,” “require a pull request before merging,” and “require status checks to pass” as separate rules. The signed-commit rule checks whether commits in a target-branch update have verified signatures. The review rule requires approvals with specified counts or sources. The status-check rule waits for named checks to report. They can block the same release path, but their failure conditions differ.

Control Question it answers What still needs checking
Commit signature verification Was this commit object's signature verified under platform rules? Key ownership, authority and fit with the team's identity policy
Pull-request approval Did an authorized reviewer approve the diff defined by current policy? The approved diff, later pushes and whether stale approvals remain usable
Required status check Did a named check report success for the merge candidate? The SHA tested, workflow trust and whether the check covers the risk
Deployment gate and receipt Did an environment accept a deployment, and what input did it use? Artifact digest, target environment and actual live service or page

This table is an editorial review framework, not a universal GitHub default. Availability and behavior depend on the rule type, target branch, merge method, permissions and product plan. Bypass permissions matter too: some rules allow specified roles or apps to bypass them. Reviewers should inspect who can bypass a rule, under what circumstances, and whether the bypass is recorded, rather than stopping at “the rule is enabled.”

Do not infer unanimous author consent from “approved.” GitHub's vigilant-mode documentation distinguishes Verified from Partially verified for multi-author commits. Signature verification expresses a relationship the platform can verify; it does not replace governance for contributors, delegated commits, key rotation or release permissions. A reviewer is not necessarily the signer, and a signer is not necessarily authorized to approve a merge. Define the responsibilities separately.

Keep an evidence ledger that can be reviewed later

To answer “Who approved the code that reached production?”, a release record should preserve at least: pull-request number; head SHA or diff state at review time; approver and approval time; signature status and when it was observed; required check names, workflow run IDs, results and SHAs; merge SHA; build artifact digest; deployment environment, task ID and actual deployment input; and the URL, time and observed result of post-release verification. The exact fields can vary, but each claim needs a durable identifier. A mutable branch name or screenshot alone is not enough.

Link the records one by one. A review record points to a pull-request diff state. A CI record points to a workflow run and commit SHA. A build record points to a source SHA and artifact digest. A deployment record points to that digest and an environment. If the build system cannot record an artifact digest, at least preserve its source commit and an immutable artifact identifier, and document how the mapping is guaranteed. If a page is updated through a CDN or asynchronous release, check the actual URL or version marker after deployment. A successful deployment API response proves only that the deployment system reported success; it does not prove that every visitor sees the new page.

The ledger does not mean all records were signed by the same actor or that every upstream system is trustworthy. It lets an auditor point to a break: missing approval, changed diff after approval, a check from the wrong SHA, an artifact that cannot be traced to source, or a public page still serving old content. Acting on the break is more reviewable than writing “GitHub Verified, therefore safe.”

Failure path: CI passed, but deployment used different code

Continue with a hypothetical example. R1 has been reviewed and passes CI; R2 later enters the main branch. The build job checks out a mutable branch label, or the deployment job reuses an earlier artifact. The release panel may say “deployment succeeded,” but that does not establish that the artifact came from R2. Confirm the checked-out SHA in build logs, compare the artifact digest with the release manifest, and verify that the deployment task references the same digest. If any mapping is missing, label the input revision “unconfirmed” instead of combining platform statuses into one green light.

Conversely, if approval and CI clearly point to R2, the build manifest records R2 and an artifact digest, and the environment receipt references that same digest, the evidence chain is stronger. “Stronger” still does not mean every risk has been tested. Business rules outside test coverage, incorrect dependency versions, post-deployment configuration differences and production data conditions require their own checks. Stating those limits prevents a commit-identity check from being overstated as a complete security guarantee.

For a real review, use this sequence and keep the observed results rather than merely checking boxes: fix the candidate SHA; inspect its signature status and verification reason; confirm the approval's diff and the repository's stale-approval policy; verify that required checks completed for the same merge candidate; record the final merge SHA; confirm that the build input SHA, artifact digest and deployment input match; then request the target page or service and inspect a version marker. If the repository uses a merge queue, include the queue's candidate and final merge state.

Three questions reviewers often ask

Does Verified prove who approved the code? It shows that the signature was verified under the platform's rules. It does not by itself show that the real-world key holder has repository approval authority or that every other author consented to the commit. GitHub's vigilant-mode guidance distinguishes multi-author cases. Ask separately about identity verification, content approval and release authorization.

Does a later push always invalidate an approval? No. GitHub offers an optional stale-approval dismissal rule and a separate requirement for approval of the most recent reviewable push by someone other than the pusher. Inspect the repository's actual protection rules, rulesets and bypass permissions. Without that configuration evidence, do not claim that every later push must revoke an approval or that approvals always remain valid.

Can a screenshot serve as the audit record? It can help illustrate what a page showed at one time, but it is usually inadequate as the only evidence: it may omit the full SHA, policy version, workflow run ID, artifact digest or environment. Prefer queryable platform object IDs and timestamps, with screenshots as supplements. For long-lived audits, record when the query was made and under which permissions, since interfaces, rules and visibility can change.

Sources and execution limits

GitHub's documentation separately describes commit signature statuses, required signatures and status checks in rulesets, and required reviews and stale-approval options for protected branches. Git's signature-format manual describes signatures bound to Git objects. These primary sources support the distinction between controls. The ledger and review sequence are editorial recommendations based on those mechanisms. Actual behavior must be checked in the target repository.

No signing operation, pull-request review, ruleset inspection, build or deployment was performed for this article. R1 and R2 are hypothetical names, not real commits, and this text is not a tested tutorial. For a specific repository, use its current rules, the pull request's diff state, CI runs and deployment records as evidence, and leave any unverifiable link marked unconfirmed.

Those articles cover acceptance records and patch differences; they do not replace this distinction between signatures and approvals.
