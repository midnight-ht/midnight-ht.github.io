A successful deployment is not a verified release

Verify the artifact, serving version, user path, and business outcome separately; canary evaluation and rollback rehearsal must also cover data written by the new version and external effects.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-27 · Estimated read 18 min
Translations
zh-CN en

Article

Key takeaways

  • Deployment-step success does not prove users received the intended version; connect the commit, build inputs, artifact, serving version, and real request.
  • A canary needs version attribution, representative samples, and absolute SLOs; a quiet low-traffic window does not prove critical paths are safe.
  • Application rollback does not reverse data writes; compatibility with new state and reconciliation of queues and external effects determine whether rollback is viable.

A deployment platform reporting success proves only that its deployment steps completed. To verify a release, connect the source commit, build artifact, serving version, real user path, and business result as separate pieces of evidence. To verify rollback readiness, ask another question: can the previous version read data already written by the new one, and can queued work and external side effects still be processed or reconciled? Switching traffic back to old code does not automatically reverse state.

Turn “deployment succeeded” into evidence

A release involves at least five identities: the source commit, build inputs, artifact digest, version recorded by the deployment controller, and version actually returned to a user request. A build manifest and deployment record can connect them, but one cannot stand in for another. A green CI job means its steps passed. It does not prove the CDN has refreshed, that a browser received current assets, that an API route points to a matching version, or that a critical business action succeeded.

A more reviewable approach is to build one immutable artifact with a unique digest and promote that same artifact through test, canary, and production environments. Record the lockfile, compiler version, build arguments, and generated asset manifest with it. Inject environment-specific configuration separately from artifact identity. If every environment reinstalls dependencies and rebuilds, the same source commit does not guarantee the same bytes. During an investigation, records should let an operator trace a request or deployed version back to an artifact digest and source commit rather than only a timestamp.

For a static site, the host’s success state and a real page response are separate checkpoints. Request the homepage, article pages, language-switch routes, and critical CSS, JavaScript, and image assets through the production domain. Check status codes, cache headers, asset versions, and links on the page. If the HTML points to an old asset version or a CDN still serves a previous page, uploading the new build does not mean users receive a consistent release. Verify the real entry point and the dependencies it references, not just that files exist in a build directory.

A stateful service should also record which application version handled each request. An aggregate cluster error rate can dilute a defect affecting only canary traffic. Google SRE’s canary chapter compares a release candidate with a control: per-version user-relevant signals such as error rate and latency can reveal degradation introduced by the new version, while absolute SLOs remain necessary. SRE also warns that the two populations may share a database, network, or other failure domains, so common changes can contaminate a comparison. Traffic percentages and observation windows should not be copied from a generic template. They must cover representative requests; for asynchronous work, the window should span at least one representative work unit.

If the canary has no errors, can you expand it?

Not on the basis of “no alert so far” alone. Imagine a new task-service version receiving only a small share of jobs, but the observation window happens to contain no paused tasks, retries, or high-load input. Stability then means only that the sample did not exercise those paths. Before release, choose a small set of signals tied to user outcomes and attributable to the serving version—for example, per-version success rate and latency, or completion rate for a particular task state—and define absolute SLOs that must not be crossed. A CPU increase can matter, but it can also be noise if other processes share the machine. More metrics do not automatically make a gate more reliable; stale metrics can erode trust in the release process.

A useful decision has three outcomes. If a signal crosses a stop threshold, pause further exposure and ask the designated owner to decide. If the sample is too small or a critical path has not appeared, extend observation or run a controlled synthetic check. Continue according to the planned stages only when the sample is representative, candidate-versus-control differences are acceptable, and absolute objectives hold. Calibrate thresholds, sample size, and duration to business risk and prior failures. The Google workbook explicitly says that low request volume, request diversity, time of day, queue depth, and attribution affect representativeness; it does not prescribe one traffic split or duration for every system.

Which data states must be checked before rollback?

List what the new version may write and the old version may read; do not look only for database column changes. Suppose an old task service understands waiting, done, and failed, while the new version adds paused. The schema may be unchanged, yet the old version’s enum parser, state transition, or background worker may fail when it encounters paused. This is a hypothetical example, not a migration that occurred on this site. One possible release order is to expand read compatibility first, deploy a version that can read both old and new values, and only then allow the new version to write the new state. After every old consumer has been retired, decide separately whether to narrow accepted values. Each step needs an actual consumer inventory and compatibility evidence.

The rollback boundary belongs to the controller. A Kubernetes Deployment records revisions for Pod-template changes; rollout undo restores the Pod template, not the database, queue, external service, or side effect already triggered by a user. It should not be described as returning the whole system to an earlier state. An ECS blue/green deployment can retain the old service revision during its bake time, making traffic reversal easier, but that is not a mechanism for undoing writes made by the new version. Blue/green also runs two revisions temporarily, and resource cost and traffic-shift behavior depend on how the ECS service is connected to load-balancing or service-routing components.

Database recovery is not a cost-free code rollback either. Restoring a backup can remove legitimate writes made after the backup point, while an already-confirmed payment, email, or third-party callback may not be reversible. For Amazon RDS blue/green, AWS specifically documents that after switchover the new production database’s point-in-time recovery history starts when the green environment was created; it cannot restore to a point before that creation. Keeping the old blue resource can preserve earlier recovery history, but it incurs compute and storage costs. That is RDS-specific behavior, not a rule for every database. Choose a path only after agreeing on acceptable data loss, recovery-point objectives, reconciliation of external state, and how long old resources must remain.

On failure, should you roll back or roll forward?

Before release, record who can stop expansion, what conditions trigger that stop, and what must be checked after traffic moves back. If the new version only changed static assets and wrote no state, returning to a known artifact and checking the production response may be enough. If it wrote values the old version cannot read, stop further writes, preserve evidence about consumers, and choose among a compatibility patch, temporary feature disablement, data conversion, or a business-approved recovery point. If an external side effect has already been sent, the decision must also cover idempotent replay or reconciliation; changing containers cannot be assumed to retract it.

A rehearsal record should include the trigger and decision owner; the target artifact and version; which version actually received requests after traffic shifted; the result of having old code read new state and process pending work; what a data restore would lose and how external actions would be reconciled; and the time required to reach the target version. These are proposed acceptance checks; no rehearsal was performed in this project or in production. A backup file, a retained image, or a cloud-console “rollback” button proves that a tool exists, not that recovery has been demonstrated.

Use service indicators and incident learning to choose user-outcome signals, and risk-based quality gates to catch failures before release. They serve different stages: post-release observation cannot replace pre-release validation, and pre-release tests cannot prove that production caches, actual routing, and data compatibility have no divergence.
