A successful deployment is not a verified release

Separate source, artifacts, deployment, and user outcomes; rehearse rollback with data compatibility in mind.

A successful deployment log does not establish that users received the intended version. Caches may be stale, interfaces may disagree, or a database change may already have altered the recovery options.

For a static site, republishing an old artifact replaces page files, but caches and actual responses still need verification. A service that writes data adds another question: can the old code handle data already written by the new release? The task service below is hypothetical.

Identify what is actually running

Record the source commit, build inputs, artifact identity, and version serving requests. They should be connected, but one cannot stand in for all four.

My recommendation is to promote the same artifact between environments where feasible. Track environment configuration separately. For a static site, verify article pages, language switching, and assets after publication rather than relying solely on the hosting status.

Compare the canary with something meaningful

Google SRE’s canary release chapter describes evaluating a limited exposure of a new release. It does not establish a universal traffic percentage or observation period.

For a hypothetical order service, compare user success, errors, and latency while checking sample representativeness. At low traffic, no observed errors may simply mean the failing path was not exercised. Add synthetic checks or more observation rather than declaring success from absence of evidence.

Rehearse compatibility, not just redeployment

Before rolling code back, ask whether the old version can read data written by the new one. Suppose an old task service recognizes waiting, done, and failed, while a new version adds paused. Old code may fail on that value even if the database columns never changed. Check value ranges, default behavior, and actual readers and writers. An expansion-first schema change is one possible approach, not proof of compatibility. Later removal of the old structure deserves a separate decision.

A rehearsal should include starting the previous version, reading new data, and handling queued work. A backup file does not prove restoration works. Recovery time and acceptable data loss require explicit business decisions.

Define stop conditions and decision ownership before release. Pause further exposure when they trigger, then choose rollback, a feature disablement, or data repair based on the failure. The release record should retain the artifact identity, observation window, results, and decision.
