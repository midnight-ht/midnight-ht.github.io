Green tests are not enough: design quality gates around failure paths

Prioritize logic, integration, end-to-end, security, and accessibility checks by the failures they detect.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-08 · Estimated read 10 min
Translations
zh-CN en

Article

A quality gate should block a defined failure. For order exports, prioritize unauthorized access, result integrity, and diagnosable failures, then choose unit, integration, or end-to-end checks for those risks. Coverage can reveal gaps but cannot replace acceptance criteria. The checks below are proposed test designs.

A green pipeline can coexist with an incomplete export or a download link accessible to the wrong user. Test counts do not automatically represent business risk.

For the hypothetical export feature below, prioritize unauthorized downloads: a normal-looking interaction could expose another department’s data. Design the check around that failure rather than starting with a coverage target. The scenario and steps are illustrative and have not been executed against a service.

Put checks near the relevant boundary

Test filtering logic close to the code. Check queue redelivery, storage failures, and state transitions across components. Keep browser checks for the user journey: create a job, observe its status, and obtain a usable result.

If authorization lives in a gateway, application unit tests alone cannot establish that it works. Exercise the boundary with identities holding different permissions. Hiding a button does not demonstrate that a result is protected.

An empty export should have a defined format and user message. A successful status code cannot verify either. Inspect generated fields and record scope with synthetic data rather than production personal information.

Specify a check that catches unauthorized downloads

In an isolated test environment, create two departments and identities using synthetic orders. User A creates an export and downloads it successfully. User B then requests A’s job status and download endpoint through the actual authorization boundary. Both requests should be denied according to the API contract, without returning a signed storage URL. If delegated access is a supported feature, define that exception first.

The failure condition is unauthorized disclosure of status or results, rather than a response differing from one particular status code. Retain the requesting identity, job owner, and sanitized response to locate a missing gateway check, application check, or storage-link bypass.

Include security and accessibility in acceptance

NIST SSDF 1.1 describes security practices integrated into software development. It does not certify this hypothetical workflow. Decide access revocation, file retention, and sensitive logging behavior during design, then verify those decisions.

W3C WAI tutorials provide guidance on form labels, validation, and notifications. For an export interface, check keyboard operation, understandable input errors, and perceivable task updates. A clean automated scan is not a complete accessibility evaluation.

Preserve useful failure evidence

Capture the build version, permission scope, task identity, and sanitized responses when a check fails. Screenshots explain interface state; they do not prove file integrity.

Do not hide intermittent failures behind unlimited retries. Separate environment instability, test defects, and product races. A temporary exception needs an owner, a stated residual risk, and a condition for restoring the check.

Start with a test that demonstrably fails for the most costly error. Confirm that the fix changes its result. That provides stronger evidence than another set of checks asserting that the page exists.

What a green result cannot tell you

Why inspect the file after meeting a coverage target?

Coverage describes which code the tests exercised, not whether they asserted the correct business result. A test may execute an entire export without checking fields, record scope, or encoding. Use a known dataset and compare its expected output with the file. Define comparison rules for unstable fields such as generated timestamps instead of skipping output verification entirely.

Can an intermittent failure be rerun until it passes?

A rerun may help diagnosis, but it does not erase the first failure. Preserve the original build, environment, task identity, and response. Determine whether the cause is infrastructure instability, a test defect, or a product race. If the check is temporarily isolated, record the remaining risk and restoration condition; otherwise, the green result simply represents less checking.

Gate conditions should come from the agreed requirements and permission rules. Passing them also does not replace production verification. After deployment, use the artifact and rollback discussion to check the serving version and critical user journey.
