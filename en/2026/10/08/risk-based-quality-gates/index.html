Green tests are not enough: design quality gates around failure paths

Work backward from high-impact failure paths to assertions, test boundaries, and ownership; coverage and pipeline status are limited evidence.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-27 · Estimated read 22 min
Translations
zh-CN en

Article

Key takeaways

  • Green means the current checks and assertions passed; it does not replace selecting and testing high-impact user risks.
  • Place tests at the boundary where failure can occur: local rules, component interactions, and the complete user journey answer different questions.
  • Define block conditions, diagnostic evidence, owners, and exception restoration criteria together; coverage does not predict release safety.

A quality gate should block a defined failure whose impact warrants stopping the change, not merely pursue a green result. A green CI run shows that this run’s checks passed their current assertions; it does not prove the team selected the riskiest failure to test. For a hypothetical order-export feature, first ask whether a user in department B can read department A’s job and file. Then decide which authorization boundary to exercise, what evidence to observe, and who responds to failure. The scenarios below are design examples; no tests were run.

Before release, teams often hesitate in front of a green pipeline: the test report looks good, but nobody confirmed the department scope of the file; an end-to-end test clicks through the button but never inspects the result; a security scan reports no alerts, yet nobody knows whether a revoked user can still use an old link. The problem is not necessarily a shortage of tests or an unattractive test pyramid. The green signal is not connected to a business risk.

What does “pass” actually establish?

Each gate needs at least a risk, an observable result, a test boundary, an owner for failure, and a response. “A user from department B must not read a task from department A” states the risk and expected result. Two synthetic accounts making cross-department requests through the actual status and download paths define a test boundary. Blocking the merge and routing the requesting identity, task owner, and sanitized response to the authorization owner define a response. A test that only checks whether the download button is visible can pass every time without exercising that authorization rule.

Coverage answers whether tests executed code; it does not answer whether assertions checked the right business outcome. A test may run the file-generation function without checking either row count or department ownership. Coverage can help locate unexercised code and suggest where to inspect next. If a team sets a uniform threshold, it should also ask which user risks the increase addresses. The number alone cannot turn “the function ran” into “the file is correct.”

Why start with the loss instead of the test type?

An export that includes another department’s records creates an unauthorized-disclosure path. Evidence should show that the file contains no unauthorized records, and the check must cross the real authorization boundary rather than call only a filtering function. Queue redelivery creates a different risk: inspect task identity, state, and side effects before and after retry instead of testing only the first execution. An empty result may be valid for the user, so inspect its file format, status, and message rather than treating zero rows as a program failure.

These scenarios determine where the tests belong. A pure field conversion can use a fast unit test. If authorization is enforced by an API gateway, an integration test should traverse the gateway’s real policy. Browser end-to-end tests are suited to checking whether a user can create a task, observe state changes, and download a result. These tests answer different questions; fixed proportions should not make them substitutes for one another. End-to-end tests tend to run more slowly and cover a broader diagnostic area. Integration checks cover component interactions, while unit tests validate local rules frequently. Choose the combination from where the failure can actually occur.

How do you build a gate that catches unauthorized access?

In an isolated environment, create departments A and B with synthetic orders. A user from A creates a job and retrieves its file. A user from B then requests that job’s status and download through the same authentication, gateway, and application path the product uses. Acceptance should first ask whether status or file contents were disclosed, not require every framework to return an identical status code. If delegated access is a supported feature, define how delegation is granted, revoked, and audited before adding it as an allowed case.

Keep enough information to diagnose the test: build version, requesting identity and permission scope, task owner, relevant request identifier, sanitized response, and the stage that failed. If B received task status, the test should identify a status-endpoint authorization failure. If the file is denied but a signed storage URL is leaked, the check still fails. A screenshot can show what appeared on the page; it cannot prove file contents or server-side access control.

There is a primary reference for integrating security into the development process. NIST SP 800-218, SSDF 1.1, describes high-level secure-development practices that can be integrated into an SDLC. NIST describes its intended benefit as helping reduce vulnerabilities and their impact; it is not a certification for a particular project. NIST SP 800-218 For quality gates, that means security requirements belong in design, implementation, and verification. Citing the framework does not justify a “security passed” label without evidence.

Do form and background-job failures reach the user?

For a form that accepts a date range and department, the W3C WAI Forms Tutorial recommends identifying controls with labels or other mechanisms, validating input, and notifying users when tasks complete or fail with instructions for correction. The page was updated in March 2026 and notes that it combines criteria and techniques from different WCAG conformance levels. W3C WAI Forms Tutorial Tests should therefore ask more than whether a screen reader can find a control: they should check which field owns an error, whether keyboard focus can reach the correction point, and whether a background-job failure is perceivable. The tutorial helps with implementation, but one automated scan cannot establish complete accessibility conformance.

The meaning of “complete” for an asynchronous job also needs a user-visible test. If the job fails, page status, notification, and retry path should agree. If some data fails, requirements should say which result can be downloaded, how the error manifest is represented, and whether retry could repeat the already successful portion. Tests may separately inspect API transitions, queue redelivery, and user notifications. A single click-through test may not identify whether a state error came from the queue, database, or page; unit tests alone cannot prove those components work together.

What should block, and what should warn?

Gate level should reflect impact and reversibility. A confirmed data leak, duplicate processing of financial data, or incomplete file contents may warrant blocking the change until expected behavior and evidence are clear. A low-impact wording difference or a non-critical browser issue might be a warning with an owner and repair deadline. This is not a universal severity table: teams still need to weigh users affected, data sensitivity, reversibility, and business deadlines.

Before making “all checks green” a blocking condition, decide who publishes the status, which commit it describes, and whether skipped or neutral outcomes are allowed. GitHub protected branches can require status checks before merge and distinguish strict from loose checks. Strict checks require the branch to be current with its base; loose checks allow it to lag, though GitHub notes that incompatibilities may appear after merge. GitHub protected branches This describes GitHub behavior. It does not select the right tests or define which product risks should block a release.

Intermittent failures should not be turned green through unlimited reruns. The first failure may reveal an environment problem, or it may be the product race or rate-limit boundary the suite was meant to catch. Preserve the initial build, environment, fixture, task identity, and response. Then distinguish test defects, infrastructure instability, and product behavior. If a check must be isolated temporarily, record who accepts the residual risk, the restoration deadline or trigger, and the fact that the check was skipped. Otherwise the dashboard converts “not tested” into “no issue.”

How can you tell a gate is not just a green light generator?

For each high-risk rule, keep positive and negative controls. Account A should retrieve its own task; account B should be denied A’s task. Then confirm that removing the authorization assertion makes the test fail. This checks whether the test is sensitive to the target behavior, but there is no need to mix deletion of production code into every routine pipeline run. For file integrity, prepare a known synthetic dataset and compare fields, ordering, row count, and encoding. Define comparison rules for unstable values such as generated timestamps rather than skipping the entire output.

A maintainable gate record should include risk ID, expected result, test boundary, failure category, severity, owner, block-or-warn decision, evidence link, and temporary-exception condition. CI status should point to a commit and a reviewable report. Passing does not prove production is safe; failure should not leave only “pipeline red.” If a team can locate the user risk behind a failure and name who may lift the block based on which evidence, the gate is beginning to support delivery accountability.

A coverage target can still miss the most dangerous error because execution is not a business assertion. An intermittent end-to-end failure should not be rerun until green without keeping and classifying the first result. A useful first move is to choose one costly failure for which evidence is missing, define the expected result, and select a test that crosses the real boundary. Add more gates only when each explains what it can stop.

The risks should come from the requirements and permission rules. Verification of the served version and rollback belongs to the separate release-artifact discussion. Each check answers a different question; one green line should not be expanded into a claim that the whole delivery path was verified.
