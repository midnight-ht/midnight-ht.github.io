Low CPU, failed users: connect service indicators to incident learning

Use a hypothetical asynchronous report service to define outcome SLIs, actionable SLO alerts, and verifiable incident follow-ups.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-27 · Estimated read 25 min
Translations
zh-CN en

Article

Key takeaways

  • An SLO should measure the user outcome; request acceptance, low CPU, and a usable report are different events.
  • The numerator, denominator, deadline, cancellation, and retry rules determine comparability; observe user symptoms separately from internal causes.
  • Alerts should map budget consumption to an action, while incident follow-ups need an owner, restoration condition, and reviewable acceptance evidence.

Low CPU does not mean users are succeeding. An asynchronous service-level objective should measure whether users receive a correct, usable result within the promised time, rather than whether an endpoint merely accepted a request. Define valid requests, success conditions, deadlines, and observation windows before calculating an SLI and its target. Black-box signals establish user symptoms; white-box signals explain possible causes; resource metrics help investigate capacity. The report-generation scenario and all numbers below are hypothetical. No real incident or monitoring configuration is being reported.

Imagine a report service whose creation endpoint quickly returns “accepted.” A queue consumer then reads data, generates a file, and makes a download link available. If the consumer stops, the endpoint may continue returning 202 while host CPU usage falls because no work reaches the compute stage. Both dashboard readings—“request succeeded” and “CPU is normal”—can be true, yet neither answers the product promise: did the user receive a usable report on time? Resolve that gap by defining a verifiable user journey as the objective, then placing internal metrics in their proper roles as explanation and response context.

Define the SLI from the user promise

For terminology, Google SRE defines an SLI as a carefully defined quantitative measure of some aspect of service, while an SLO sets a target or range for that measurement. Latency, error rate, throughput, and availability are common candidates. A server-side proxy can be used when an ideal client-side measurement is difficult, but it should be recognized as a proxy rather than the user’s direct experienceGoogle SRE: Service Level Objectives. In this example, the product promise is not “the job-creation endpoint returned 202.” It is “a valid report request receives a complete, accessible file within the agreed deadline.”

That sentence still needs a statistical definition. The numerator might be the number of files generated before the deadline, passing integrity checks, and accessible to an authorized user. The denominator is the valid report requests in scope. Link the creation request and completion event through the same job identifier; otherwise the service can mistake accepted work for completed work. Document how to classify user cancellation, duplicate submission, quota rejection, system rejection, and missing source data. For client cancellations, a defensible policy might depend on whether the system accepted the job and when the cancellation occurred, but there is no universal answer. Avoid silently removing abandonments caused by service failures from the denominator.

Suppose, purely for arithmetic illustration, that one month contains 10,000 valid requests and the target is 99.5% completed on time. That permits 50 events that fail the condition. These are hypothetical values, not site traffic or a recommended target. If the last jobs in a window have not reached their individual deadlines, do not prematurely label them late. If a job remains incomplete at its agreed deadline, count it as a bad event according to the predefined policy; a later recovery must not rewrite “late” into “on time.” Otherwise window totals keep changing after results arrive, making trends incomparable. When volume is low, one failure can sharply change the ratio, so also report raw event counts and window length. A percentage should not conceal a tiny sample.

Separate user symptoms from internal causes

Monitoring is not a single health number. At the monitoring-layer level, Google SRE describes black-box monitoring as testing externally visible behavior as a user would see it, and white-box monitoring as inspecting metrics, logs, or interfaces exposed by the system’s internals. Its monitoring chapter identifies latency, traffic, errors, and saturation as useful signals for user-facing services. It also notes that errors include more than HTTP failures: a 200 response with incorrect content can be an error, as can missing a promised latency boundGoogle SRE: Monitoring Distributed Systems. A report service therefore needs an external probe or user-path completion SLI, alongside internal diagnostic signals such as consumer age, queue depth, source-data failures, file-validation failures, CPU, memory, and disk use.

These measurements become more useful when linked along one event path. For example, falling completion and increasing queue age with low CPU may suggest consumers are not claiming jobs or have been throttled. Falling completion with rising database waits but low CPU may instead point to I/O waits or exhausted connections. Normal completion with steadily rising CPU and queue depth may indicate shrinking capacity headroom without yet showing user harm. These combinations are investigation clues, not automatic proof of causation. Retries, caches, dependencies, and tenant isolation can make the same pattern mean different things. An alert should establish that the user outcome is deteriorating, then attach white-box context that narrows the investigation.

Alerts should imply an action

For an SLO-based alert, the question is not merely whether CPU passed a threshold. It is whether the current rate of bad events threatens the objective’s error budget. For paging decisions, the Google SRE Workbook discusses budget consumption together with alert precision, recall, detection time, and reset time; it compares increasingly effective strategies. Its examples show why comparing a very short window directly with an entire SLO target can generate low-precision alerts, and why a fixed delay can miss periodic spikesGoogle SRE Workbook: Alerting on SLOs. This is not a threshold table to copy unchanged into any monitoring system: service windows, traffic, impact, and recovery actions differ.

For the hypothetical report service, alerts can be layered. A clear user-outcome deterioration with rapid budget consumption might page the on-call responder. Increasing queue age before the user target is affected might create a ticket or notify the responsible team. CPU or connection-pool saturation might support capacity investigation or preventive action. A page should include the affected journey, measurement window, bad-event definition, recent numerator and denominator, representative job identifiers, an actionable mitigation, and the relevant dashboard. It should also state what recovery looks like; otherwise an alert may continue after the issue is mitigated, leaving the responder unsure whether action is still required.

A low-traffic service is an important counterexample. A ratio with a small denominator can swing dramatically: one failure may produce a 100% error rate in a short window while affecting only one job. Conversely, a long-window average can dilute a brief total outage. Consider the actual number of bad events, customer impact, budget burn rate, and a synthetic probe together. A black-box probe can detect a complete outage when there is no real traffic, but it covers only the chosen sample journey. It cannot replace the distribution of real user behavior or checks for data correctness.

Turn incident observations into verifiable changes

A postmortem should start from an auditable timeline, impact, information available at the time, mitigations, and evidence of recovery—not from “the root cause was that someone ignored the alert.” On response coordination, Google SRE’s incident-response chapter emphasizes a clear command line, defined roles, a working record of debugging and mitigation, and declaring incidents early. Its postmortem chapter treats impact, actions, causes, and preventive follow-up as learning material rather than punishmentGoogle SRE Workbook: Incident Response. Google SRE: Postmortem Culture In a small team one person may temporarily hold several roles, but during a high-impact incident it is useful to separate coordination from hands-on production changes so someone remains responsible for overall state and communication.

The edition boundary matters here: these links point to chapters currently readable on the Google SRE site, while its books page also lists Site Reliability Engineering, 2nd Edition and describes that edition as rewritten. This article summarizes the visible chapter pages; it does not assume they are identical to the full new edition or copy the book’s example targets into a particular service. Google SRE Books

Suppose a training exercise stops a queue consumer after a credential rotation fails. Record when rotation began, when consumption stopped, when the first task passed its deadline, which black-box check detected it first, who declared the incident, when new exports were paused, when consumption resumed, and how queued jobs completed. If logs cannot identify an exact start time, record an interval or an unknown value rather than inventing precision. This lets the team check whether its service indicator represents user impact and whether monitoring fires only after an internal task-count change.

A follow-up should turn a contributing condition into an acceptance test. For example: “Add a consumer liveness check after credential rotation; in an isolated environment rotate the test credential and stop the consumer, confirm the alert and response guide work, and verify that backlog recovery produces each result once.” Record an owner, due date, risk, and verification evidence. “Improve observability” or “raise on-call awareness” does not let the next reviewer determine whether the system changed. Also examine side effects: more aggressive retries may drain a queue sooner but create duplicate messages if jobs are not idempotent. A shorter alert window may find spikes sooner while creating noise for low-traffic services.

Does low CPU mean resource monitoring is useless?

No. CPU, memory, disk, network, thread pools, and connection pools can explain system state and reveal capacity risk. The user-outcome SLI answers whether the service met its promise; neither category replaces the other. Low CPU can mean idle capacity, but it can also mean that consumers are not receiving work, threads are waiting on a network, an upstream layer is blocking requests, or a quota is rejecting jobs. First inspect queue growth, consumer polling, external dependency latency, and the layer where rejection counts increase before concluding that there is no capacity issue.

The telemetry itself also needs validation. Client clock skew can corrupt deadline measurements. Splitting one batch job into child jobs can double-count the denominator if parent and child events are both included. Retries with a new identifier each time can dilute bad-event counts. Delayed data may leave a window temporarily incomplete. Synthetic work can validate a path, but its permissions, scale, and data route should exercise the same critical boundaries as the real service. Mark metric-definition changes with their effective time, and make incomparable periods visible in charts and postmortems.

A practical implementation can begin with one important user journey. Record its event model from request acceptance to usable output, then connect one real user-side probe to internal diagnostic metrics. Calculate good events and window outcomes from historical events; manually check classifications for cancellation, timeout, retry, and partial completion. In a test environment, simulate a stopped consumer, a slow dependency, an invalid file, and recovery with redelivery, then check whether indicators and alerts provide the expected evidence. These validations were not executed for this article. Product promises, risk tolerance, traffic patterns, and recovery capacity should determine the SLI, target, and alert thresholds; do not copy them from a resource dashboard or another company’s target.

A service objective asks what users received; monitoring separates what happened from possible reasons; a postmortem turns evidence into a change that can be tested again. Connect alerts and recovery actions to the release and rollback plan and requirements and acceptance design: new objectives belong in acceptance criteria, and a release should still be checked against the artifact actually running online. CPU is then evidence in an investigation, not a substitute for user experience.
