“Support export” is not an acceptance criterion

This is a hypothetical administration workflow, not a reported deployment.

The ticket says “support order export,” and the demo shows a download button. It leaves several questions unanswered: what happens after a retry, whether revoked access invalidates an old download, and who owns failed jobs.

This is a hypothetical administration workflow, not a reported deployment. My recommendation is to settle observable outcomes and failure ownership before polishing the screen.

Resolve the disagreements first

Who may export? Does the file represent data at request time or execution time? When does it expire? These decisions affect queries, storage, and authorization.

Cucumber’s Example Mapping groups acceptance discussions around rules, examples, and unanswered questions. The technique does not require adopting Cucumber itself.

For this example, propose three acceptance scenarios: a department user receives only authorized records; a retry with the same request identity returns the existing task unless the business defines a new operation; a storage failure produces an understandable status without leaking credentials. These are proposed requirements for the example, subject to business and security review. Financial reporting may require stronger snapshot semantics.

Make the task traceable

I would separate task creation, status lookup, and result download. The task identity should travel through logs and support reports. Download authorization needs an explicit decision when access changes after creation. A small export may still be simpler as a synchronous response; asynchronous execution introduces queues and cleanup work.

Tests should inspect file contents and scope, not merely assert a successful HTTP response.

Record the decision that may change

An Architectural Decision Record captures a decision and its rationale. For this workflow, record data-volume assumptions, retry semantics, revocation behavior, and cleanup ownership. Add a condition for revisiting the choice.

Before release, ask a previously authorized user to download after access is revoked. If the team cannot state the expected outcome, the requirement is still unresolved.
