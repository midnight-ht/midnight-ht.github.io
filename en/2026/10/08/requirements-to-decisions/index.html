“Support export” is not an acceptance criterion

This is a hypothetical administration workflow, not a reported deployment.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-08 · Estimated read 8 min
Translations
zh-CN en

Article

An export acceptance criterion should define data scope, duplicate submissions, access revocation, and failure ownership. Synchronous versus asynchronous execution is a subsequent architecture decision. The rules below are design examples for a requirements review, not a deployed service specification.

The ticket says “support order export,” and the demo shows a download button. It leaves several questions unanswered: what happens after a retry, whether revoked access invalidates an old download, and who owns failed jobs.

This is a hypothetical administration workflow, not a reported deployment. My recommendation is to settle observable outcomes and failure ownership before polishing the screen.

Resolve the disagreements first

Who may export? Does the file represent data at request time or execution time? When does it expire? These decisions affect queries, storage, and authorization.

Cucumber’s Example Mapping groups acceptance discussions around rules, examples, and unanswered questions. The technique does not require adopting Cucumber itself.

For this example, propose three acceptance scenarios: a department user receives only authorized records; a retry with the same request identity returns the existing task unless the business defines a new operation; a storage failure produces an understandable status without leaking credentials. These are proposed requirements for the example, subject to business and security review. Financial reporting may require stronger snapshot semantics.

Make the task traceable

I would separate task creation, status lookup, and result download. The task identity should travel through logs and support reports. Download authorization needs an explicit decision when access changes after creation. For a synchronous export, decide what happens when the client disconnects. An asynchronous job survives the connection but adds state management, queue redelivery, and file cleanup. When a small export fits within the request timeout, those costs may not be justified.

Tests should inspect file contents and scope, not merely assert a successful HTTP response.

Record the decision that may change

An Architectural Decision Record captures a decision and its rationale. One proposed rule is to select records using the task creator’s scope at generation time, then check current permissions again at download. Revoked access means a denied download even if creation was authorized. Retention obligations or delegated access may need a different design. Record this choice alongside data-volume assumptions, retry semantics, cleanup ownership, and a condition for revisiting it.

Before release, ask a previously authorized user to download after access is revoked. If the team cannot state the expected outcome, the requirement is still unresolved.

Questions to settle in the review

Does every export require an asynchronous queue?

No. Consider the request timeout, expected data volume, recovery behavior, and maintenance cost. A synchronous design still needs a decision about server-side work after the client times out. An asynchronous design needs named ownership for backlog alerts, job cleanup, and result expiry. Those responsibilities should be part of the decision rather than an unspecified later optimization.

Is authorization at task creation enough?

Not necessarily. Permissions may change before download. The candidate rule here checks authorization again at download time. Delegated access or retention obligations require explicit exceptions and evidence of authorization. A long-lived storage URL should not silently become the authorization policy.

Leave unresolved questions in the requirement with a decision owner. In this example, whether revoked users can obtain results affects interfaces, storage, and testing, so it should be answered before implementation. Once the rule is agreed, turn it into a check using the failure-path quality gate discussion.
