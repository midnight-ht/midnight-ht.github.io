“Support export” is not an acceptance criterion

Turn “export” into testable decisions about data scope, time semantics, format, access, completion state, and ownership of failures.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-27 · Estimated read 23 min
Translations
zh-CN en

Article

Key takeaways

  • “Support export” is not a complete behavior contract; scope, snapshot time, format, authorization, status, and failure ownership need observable decisions.
  • RFC 4180 documents common CSV conventions, not uniform behavior across every consumer; valid CSV syntax also does not replace a spreadsheet-oriented formula-injection assessment.
  • Choose synchronous work, asynchronous jobs, authorization rechecks, and retention from task limits, risks, and operational ownership; the examples are not test results.

An export requirement is testable only when it states at least six things: who may export, which data is included, what time the data represents, which file format is promised, how completion is observed, and who owns failures. With only “support export” in the ticket, engineering, QA, security, and operations may fill in the blanks differently. Decide the user-visible outcome first, then choose a synchronous request, background job, or storage design. The order-report examples below are hypothetical; no export service or acceptance test was implemented.

A familiar review conversation goes like this: product asks for an export button, engineering returns a CSV, QA asks what an empty result means, security asks whether a revoked user can still use an old download link, and operations asks who retries a stuck job. The disagreement is rarely about the word “export.” That word compresses several independent decisions into one verb.

What data scope and time should the requirement define?

Start with the requester, filters, fields, sort order, and time zone. “Export orders” could mean all orders the current user may view or orders created by a department during a selected date range. The value of a refund-status column might be the value at purchase, at task creation, or when the file is generated. Those choices change the output.

A candidate requirement could say: “For the selected department and date interval, export orders that match at submission time, sorted by creation time ascending; express amounts in each order’s original currency and include a refund-status column.” This is a proposed contract for the example, not a universal rule. The business owner still has to confirm it.

The team also needs a snapshot rule. Suppose a user submits the request on Monday and a queue runs it on Tuesday, after an order has changed. Should the file represent data at submission time or the data visible at execution time? The first option requires a way to preserve or reconstruct the request-time view. The second is simpler, but two runs of the same filters may produce different files. Financial reconciliation, back-office operations, and one-off exploration may have different needs. “Latest data” is not a testable boundary unless the relevant time is defined.

What does CSV, Excel, or a download link actually promise?

RFC 4180, published in 2005, is an Informational RFC and explicitly says it does not specify an Internet Standard. It documents common CSV conventions such as an optional header, record delimiters, and quoting fields that contain commas, quotation marks, or line breaks. It registers the media type text/csv. RFC 4180 So “provide CSV” still leaves encoding, delimiter, header, date and number representations, null values, and supported consumers to decide. The RFC describes a common format; it does not guarantee identical behavior across every spreadsheet and downstream parser.

Valid CSV syntax does not automatically make a file safe to open in spreadsheet software. OWASP’s CSV Injection guidance explains that spreadsheet applications may interpret untrusted cell values beginning with formula-trigger characters as formulas. Separators and quotes also matter because they can create a new cell in which a dangerous value begins. OWASP warns that there is no universal sanitization strategy that works for all spreadsheet applications and downstream consumers; some Excel-oriented handling can alter the data later imported by a program. OWASP CSV Injection The requirement should therefore say whether the file is intended for people to open in a spreadsheet or for another program to ingest. If both use cases matter, separate formats or an explicit security transformation and compatibility boundary may be needed. A vague “export” does not promise both safely.

The HTTP response has its own contract. RFC 6266 says Content-Disposition: attachment indicates that the recipient is expected to be prompted to save the file. The filename and filename* parameters can suggest a save name, with filename* supporting internationalized names. RFC 6266 This expresses download intent and a suggested filename; it does not define file contents, authorization, retention, or link security. A useful check inspects the response header, a non-ASCII filename, and actual browser save behavior rather than merely asserting that the download endpoint returned 200.

When should an export be synchronous, and when should it become a job?

A synchronous response fits work that completes reliably within the request limit, produces a small result, and can be retried directly. It avoids a task table, status endpoint, and cleanup process. It still needs a rule for what the server does after the client times out and whether another click creates duplicate work.

When work takes significant time or needs visible progress, Google AIP-151 recommends that a long-running API method return a queryable operation rather than make the caller wait. Its metadata can carry progress and partial failures; execution errors can be represented in the operation’s error field. AIP-151 is a Google API design guide, not a requirement for every HTTP interface. Its roughly ten-second guidance is a rule of thumb, not a universal threshold. AIP-151: Long-running operations

For the hypothetical order report, if the selected range reliably fits within the request limit, the service could return the file synchronously and record the request result. If work may outlive the page connection, it could return a task identity and expose states such as queued, running, succeeded, and failed. If only some rows cannot be exported, the team must decide whether the whole file fails, the rows are skipped with a report, or a downloadable file is delivered with an error manifest. A partial failure should not be hidden inside a plain “success” state.

The task interface must also define duplicate submissions. Does the same idempotency key reuse the existing job, or is a new export allowed? Is an empty result a successful empty file or a business error? These are design choices, not evidence that any queue or service has already been built.

A background job adds ownership for queueing, progress, retries, timeouts, result retention, and cleanup. If nobody monitors backlog or acts on persistent failures, asynchronous execution does not make the feature reliable; it moves the wait from the user to operations. The requirement should name the operational boundary: who receives backlog alerts, whether retry can repeat reads or writes, how long failures remain available, and who intervenes after a defined delay. Thresholds need to reflect actual load and business deadlines; example values should not be copied into production promises.

Who verifies revoked permissions and expired files?

Authorization may need to be checked both when the task is created and when the result is retrieved. A single check at creation does not answer what happens if access is revoked hours later. One candidate policy is to generate data within the creator’s scope at job creation and recheck current authorization at download. Another is to permit a delegated recipient, with an explicit record of that delegation. The requirement owner should choose and state the audit evidence. If a long-lived object-storage URL bypasses the download authorization check, link lifetime may silently become the authorization policy.

The file also needs a retention rule: how long it can be downloaded, what the user sees after expiry, who monitors cleanup failure, and whether a ticket or audit needs to retain metadata. File deletion and task-history visibility are separate decisions. Even after the file is removed, a user may need the completion time, row count, or error summary. Separate checks can verify that an expired file cannot be fetched, the task record reports expiry, and cleanup failure is observable. “Periodic cleanup” does not specify all three.

How should empty results, partial failures, and format changes enter acceptance?

For a hypothetical “export March orders” request, define observable evidence for each case. With matching data, headers, column types, ordering, and row count should follow the contract. For no data, the business must choose between an empty file and a message. A user must not receive another department’s records. While a job is waiting, its status must be queryable. When some rows fail, the delivered result and error manifest must agree. After expiry, download must be denied. CSV fixtures should include commas, line breaks, quotation marks, non-ASCII characters, and untrusted text that starts with formula-trigger characters. A programmatic consumer should be tested by parsing the file and comparing fields with the defined source records, not merely by checking that a spreadsheet opens it.

Counterexamples make weak tests visible. A test that checks only for HTTP 200 can pass with an empty file. Clean sample data will not exercise formula injection or quoting boundaries. A download test run only under the same account before permissions change leaves revocation behavior unknown. Each test should point to a decided rule, so a failure can be classified as scope, encoding, authorization, task state, or delivery metadata. Cucumber’s Example Mapping is one way to organize discussion around rules, examples, and unanswered questions; using it does not require adopting Cucumber.

What decisions should survive the review meeting?

A small decision record can use five columns: question, choice, acceptance evidence, owner, and unresolved item. Scope and snapshot define query behavior. Format and consumer compatibility define serialization. Synchronous versus asynchronous execution defines task states and on-call responsibilities. Authorization defines checks at creation and retrieval. Retention defines storage cleanup. Partial-failure policy defines the result and error report. Each choice should explain why it fits the current reader, data volume, time limit, and compliance boundary. If an answer is still unknown, name who will decide it and by when; do not quietly hand the unresolved rule to the implementer.

For example, a team might propose that reports exceeding the request limit become queryable jobs, results remain available for 24 hours, downloads recheck authorization, and partial failures produce an error manifest. The 24-hour duration is an illustrative number, not advice; it needs to be set against data sensitivity, rerun cost, and support operations. The corresponding test plan should cover at least timeout, permission revocation, expired access, and partial failure. These are proposed tests, not tests executed for this article.

When the requirement states what the user receives, why they may receive it, when it expires, what they see on failure, and who handles that failure, engineering has an implementable boundary, QA knows what to observe, and operations knows where an alert goes. If the meeting still ends with “just build an export,” the next step is not to pick a CSV library. Write down the unanswered question and assign its decision owner. After the rule is agreed, it can be linked to the failure-path quality gate discussion; that is an entry point for checking design commitments, not a substitute for business acceptance of the export itself.
