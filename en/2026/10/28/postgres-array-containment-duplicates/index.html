Why Array Containment Can Match Two Demands With One Value

Explain why PostgreSQL array containment ignores multiplicity, distinguish tags from quantities and equality, and define validation boundaries.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-28 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • Containment checks value occurrence rather than allocating duplicate units.
  • Equal size and mutual containment do not prove sufficient quantities.
  • Array equality, tag sets, and allocation need separate contracts.

PostgreSQL array containment can consider ARRAY[1] and ARRAY[1,1] to contain each other. It checks whether element values occur, not whether enough individual units exist. One unit of a product does not become sufficient for a two-unit request because a containment predicate returns true.

Containment does not count duplicate requirements

The PostgreSQL 18 array reference defines @> by whether every element on the right has an equal element on the left. Duplicates receive no special treatment. This discussion uses ordinary integer arrays under version 18; no SQL was executed. Unknown elements, multidimensional structure, and other element types need their own contracts.

Imagine a prototype storing available units as product identifiers. Inventory contains one seven; demand contains two sevens. Both requested positions can be satisfied by the existence of the same value for the containment test.

SELECT ARRAY[7] @> ARRAY[7,7];
SELECT ARRAY[7,7] @> ARRAY[7];
SELECT ARRAY[7] = ARRAY[7,7];

These statements are unexecuted. Their documented expectations are true for the first two containment checks and false for array equality. Keeping those separate expectations prevents an acceptance check from merely observing that a query returned. The identifiers describe no real warehouse or order.

Containment remains useful for an appropriate contract. A product with a deduplicated tag collection may need both “recyclable” and “promotion.” Repeating either tag need not add meaning. The mistake is reusing that existence contract for quantities.

A field called items does not settle the issue. Elements might represent product kinds, order lines, individual units, or repeated historical events. Decide what one element means and whether repetition carries information before selecting an operator.

Equal total counts do not establish sufficient inventory

Comparing array lengths is insufficient too. Inventory containing seven and eight has the same total count as demand containing seven and seven, but not the same per-product availability. Equal total size plus any overlap can still accept a shortage. Compare required and available counts for each product.

Possible models include an explicit quantity per product or a distinct identity per traceable unit. The former fits aggregation; the latter may fit serial numbers or unit-specific requirements. This article supplies no concurrent stock-allocation SQL. A correct count check does not establish that another order cannot claim the same inventory before a later write.

If repeated arrays remain the quantity representation, grouping by value and comparing counts is a possible semantic design. Define empty, unknown, and invalid inputs first. Deduplicating before counting discards precisely the information being checked. Silently skipping an unknown product changes “everything is available” into a claim about only the retained subset.

Separate validation from allocation. A preview saying “currently available” can permit changes before submission. A promise that stock has been reserved needs persistent allocation state and recovery behavior. A Boolean containment expression supplies neither.

Does containment in both directions establish array equality?

No. It does not automatically compare repetition counts or original order. Array comparison preserves element and structural information; the documentation also includes dimensional information in comparison. A tag-set equivalence rule is not a rule for all arrays.

Seven-eight and eight-seven can contain each other while preserving different order. Seven and seven-seven can contain each other while having different lengths. If the business normalizes ordinary non-null integer tags by deduplicating and applying a fixed order, it can define a set contract around that representation. It must acknowledge the discarded order and multiplicity. Records needing that information cannot share the contract.

Lower bounds and multidimensional shape may also carry domain meaning. Similar-looking displayed numbers do not prove identical input protocols. List which differences the business explicitly permits before choosing an operation.

The site's array length and cardinality article addresses counting scope. Total size does not establish per-product counts or whether units are saleable. Counting, containment, and allocation need separate names and assertions.

Proposed tests start with one unit versus two repeated requirements, equal size with different products, reversed order, and different duplication counts. Write distinct expectations for tag filtering, quantity satisfaction, and original array equality. Add empty inputs, unknown sources, and invalid identifiers so failures do not become ordinary mismatches.

A discriminating count ledger has one available unit of seven and three of eight, against demand for two sevens and one eight. Four available units exceed three requested units, yet seven is short by one. Surplus eight cannot satisfy it. Report the shortage against seven rather than total inventory. Real grouping may also require warehouse, batch, availability, or delivery date; a product-only key is a simplification, not permission to ignore those constraints. Test a sufficient total with a deficient group, then a fully sufficient grouped case. This distinguishes genuine per-group validation from both total-count checking and rejection merely because an input contains duplicates.

If the implementation groups quantities, its rejection should identify the product and shortage rather than merely saying “array not contained.” The caller can then reduce demand, replenish inventory, or correct the payload. No such checks were run here. Before adopting @>, answer whether a repeated element represents additional demand.
