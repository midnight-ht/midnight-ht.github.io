Why an Unrequested Fixture Can Run Through autouse

Trace ordinary dependencies through autouse, compare class-local and outside tests, and separate visibility, lifetime, and actual business state.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-28 · Estimated read 12 min

zh-CN en

Article

Key takeaways

  • An autouse fixture requests ordinary dependencies for applicable tests.
  • That does not make the dependency globally automatic in every context.
  • Validate the request plan, business state, and resource isolation separately.

An autouse login fixture that requests a database fixture brings that dependency into tests where the automatic fixture applies. A database fixture without autouse can therefore run even when the test does not name it. Trace applicable automatic fixtures and their dependencies before searching only test parameters.

Ordinary dependencies can arrive through automatic requests

The pytest fixture reference explains that dependencies requested by an autouse fixture effectively become automatic for its applicable tests. The official 9.0.2 source checked here also limits that propagation to those contexts. No pytest run or database connection occurred for this article.

The following unexecuted example uses trace markers and an object as a database substitute. The name db does not claim a real client. Its purpose is to expose the request graph.

import pytest

@pytest.fixture
def trace():
    return []

@pytest.fixture
def db(trace):
    trace.append('db')
    return object()

class TestSignedIn:
    @pytest.fixture(autouse=True)
    def login(self, db, trace):
        trace.append('login')

    def test_page(self, trace):
        assert trace == ['db', 'login']

class TestPublic:
    def test_page(self, trace):
        assert trace == []

Inside TestSignedIn, the test names neither db nor login, but login requests db automatically. TestPublic can request module-level db, yet cannot see the other class's login fixture. It therefore does not acquire db through that chain. The dependency has not been globally redecorated as autouse.

Trace markers establish neither real authentication nor correct database state. Real product-entry tests must assert identity, data, and resource handling. Conversely, an external connection failure does not by itself prove the request graph was unintended; integration tests can legitimately require it.

Visibility and lifetime answer different questions

Fixture visibility determines which definitions a test can request. Scope controls caching and teardown boundaries. A class-local autouse login and a broadly scoped module connection are different decisions. Expanding lifetime does not explain why a public-page test requests authentication; first inspect the request edges.

Moving login from a class into a shared conftest can expand the applicable test population. That is behavior change, not merely file organization. Identify affected directories and preserve anonymous entry cases where required. Universal login preparation can conceal failures that only unauthenticated users encounter.

Renaming db or moving its definition to the bottom does not remove login's dependency. Ordering depends on scope, dependencies, and autouse relationships rather than definition order or names. If two state-changing fixtures require an order, express the required relationship instead of rearranging source until one local run happens to pass.

Do explicit requests still work after removing autouse?

Yes, subject to visibility. Removing autouse changes automatic inclusion, not the fixture's ability to be requested. A small integration subset can explicitly request login or use an appropriate explicit preparation mechanism. Review every entry that genuinely needs identity rather than fixing only the currently failing test.

An explicit login request still brings its ordinary dependencies. If login needs db, removing autouse does not create a database-free login. Tests requiring no external system need a suitable independent entry or a clearly bounded substitute. Returning an empty object merely to suppress a connection error can invalidate the behavior login needs.

A separate problem occurs when session-level resources retain mutable identity across tests. That is state isolation, not merely request propagation. The site's fixture scope and isolation article addresses lifetime responsibilities. First establish why the request occurs, then inspect initial state independently.

Check the request plan and actual behavior

The official source recommends pytest --setup-plan for the fixture plan of selected tests. Compare class-local and outside tests individually and together, preserving the pytest version, plugins, and selected node identifiers. This command was not run here and no output is invented.

A plan does not establish successful authentication. A login entry can appear while failing to switch identity correctly. In an isolated environment, observe actual acquisition, use, and cleanup, then assert that anonymous tests remain anonymous. Printing names alone cannot validate the product entry.

Cover dependency setup failure too. A login test depending on a failed db preparation must not appear to continue successfully. If an unrelated outside test still requests the database, inspect other outer autouse fixtures and plugins. More than one request edge can exist; deleting one does not prove all external dependencies disappeared.

For example, an outside public test may not see login but may have a module-level autouse health_check that also requests db. Removing the class-local login leaves that second chain intact; visibility rules have not changed. List request sources for each target and preserve required edges before removing unintended ones. Disabling db everywhere can also remove legitimate integration coverage. If a group promises no external access, verify observable access records rather than merely the absence of one fixture name. Imports and plugins can initiate calls outside that named chain, so inspect effective configuration and the product entry too.

Proposed cases include the class-local automatic chain, an outside test without it, an outside explicit dependency request, relocation of the automatic definition, and setup failure. Assert the request set, business state, and cleanup separately. A shorter run is not a correctness result. Find the automatic request edge before deciding whether it supplies a legitimate prerequisite or hides an independent scenario.
