Why does a three-digit pattern reject letters around the digits?

Explain whole-value matching, empty input, invalid expressions, and empty pattern attributes for identifiers.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-28 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • Pattern matching concerns the complete nonempty value.
  • A missing compiled pattern differs from a rejected value.
  • An empty pattern differs from an absent attribute.

An identifier field uses pattern="[0-9]{3}" and rejects AB123. The browser did not simply fail to find three digits: HTML pattern validation checks the complete value. A regular-expression search finding a substring answers a different question. Define the allowed identifier set, then handle empty values, leading zeroes, and receiver validation separately.

How does HTML compile pattern?

The HTML Living Standard's pattern section compiles the attribute using JavaScript v mode and constructs an expression anchored to the entire value. The inspected page reports an October 26, 2026 update; that is a document date, not a browser-feature release date. The rule applies to the relevant input types rather than every control.

Under this rule, [0-9]{3} describes three digits forming the complete value. A specification-based calculation accepts 123 and rejects AB123 and 1234. A separate JavaScript substring test can find 123 inside AB123. Before mechanically adding more anchors, establish whether the operation is search or whole-value validation.

Pattern does not supply every constraint. Its mismatch rule concerns nonempty values and a compiled expression that does not match. Empty-value acceptance depends on independent conditions such as required. An optional three-digit identifier and a mandatory one can share a pattern while treating empty input differently. An error's color cannot identify the actual validity flag.

What is a complete three-digit identifier contract?

Consider a hypothetical identifier requiring exactly three ASCII digits, preserving leading zeroes and forbidding empty input. This example was not executed.

<label>
  Material identifier (three digits; leading zeroes allowed)
  <input name="part" type="text" pattern="[0-9]{3}" required>
</label>

The object is an identifier rather than an incrementable quantity. Converting 007 to numeric seven can destroy its identity. Submission, storage, and display should preserve the same string. Native validation cannot restore zeroes removed by a later conversion.

Define whitespace and digit forms explicitly. [0-9] does not promise every script's numeric characters. If the page trims whitespace while the server validates the untrimmed input, they may accept different sets. Retain both the control value and payload instead of inferring alignment from matching help text.

The receiver must independently validate the agreed string contract. Client attributes are not a trusted acceptance boundary. Copying the HTML expression into an arbitrary backend engine does not establish equivalent syntax, options, or whole-value matching. Share explicit accepted and rejected examples, then implement and verify the rule in each environment.

Why might an invalid expression produce no patternMismatch?

If compilation fails, the element has no compiled pattern. That is different from a compiled pattern rejecting a value. A malformed expression can therefore remove the intended constraint rather than safely reject everything. Console diagnostics can help, but an absence of visible errors does not prove successful compilation.

When pasting expressions, check the syntax required by v mode rather than assuming that another engine's expression remains valid. The three-digit expression here is deliberately simple. More complex character-set operations need their own compilation and input checks in the actual environment; no untested migration recipe is implied.

A proposed matrix includes empty input, 007, two digits, four digits, letter prefixes and suffixes, and whitespace. Separate required-value failure from pattern mismatch. Record the actual attribute, type, required state, value, and individual validity flags. Send the same examples directly to the receiver and compare its accepted set.

Include a deliberately invalid expression so the checks can detect a constraint that never compiled. A suite containing only accepted values may pass even with no pattern enforcement. Rejecting examples need independent expectations. Also inspect understandable format help: HTML recommends a title description, but visible assistance should not depend solely on a tooltip.

Is an empty pattern equivalent to no pattern?

No. An absent attribute provides no compiled pattern. An empty expression can compile, and its whole-value form does not match nonempty values. Empty input itself does not trigger pattern mismatch solely through this rule; required remains separate. A template producing pattern="" can therefore reject ordinary nonempty input rather than mean “unrestricted.”

A dynamic component should deliberately remove the attribute or supply a real expression. Do not assume an empty string is a universal default for HTML bindings. Inspect rendered DOM, including restored drafts and type changes, because that is the contract the browser receives.

The related lastIndex article concerns a shared scanning cursor changing repeated decisions. Here the mechanisms are whole-value matching and compilation. Separate them before carrying the same identifier through input, request, receiver, and display. No example or browser test was executed for this article.

A concrete scope counterexample is changing the identifier to type number while retaining pattern as a supposed three-digit constraint. Pattern does not apply in the Number state. An attribute visible in DOM is not evidence that it constrains that input type. Preserve a text contract when leading zeroes identify the object.
