Why EXISTS Projection Is Not an Audit Hook

Separate existence results from projection evaluation, retain the INTERSECT exception, and define explicit audit lifecycle and retry responsibilities.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-28 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • EXISTS normally tests row existence without promising projection effects.
  • INTERSECT can make projected values relevant to existence.
  • Audit recording needs explicit attempt, completion, failure, and retry semantics.

Putting an audit-writing function in an EXISTS subquery's SELECT list does not guarantee an audit entry for every check. EXISTS needs to establish whether a row exists; evaluating the projected expression is usually outside that result contract. Reliable recording needs an explicit operation with defined failure behavior.

Finding a row is different from evaluating its output

The PostgreSQL 18 EXISTS reference defines true for at least one returned row and false for none. The output list normally does not matter, hence the SELECT 1 convention. It also warns against side effects because evaluation generally proceeds only far enough to establish existence. This article discusses version 18 semantics; no database probe was executed.

Imagine checking whether an order has an active voucher. A developer projects an audit function to record the check incidentally. The function name below is hypothetical, not an existing site function. The statement combines two requirements: finding an eligible voucher and creating a record of the check.

SELECT EXISTS (
  SELECT write_audit_note(v.id)
  FROM vouchers AS v
  WHERE v.order_id = 42 AND v.active
);

This unexecuted example has a contract problem rather than merely a slow logging function. Observing a function call in one run would not establish the same behavior for every plan, input, or branch. An assertion that every query must create exactly one entry would rely on execution behavior that EXISTS does not promise.

A constant projection makes the intention clearer while leaving the correlation and eligibility conditions in the filter. It is a readability convention, not a performance result. Replacing SELECT id with SELECT 1 does not establish fewer reads or lower latency, and cannot repair a missing relationship condition.

SELECT EXISTS (
  SELECT 1
  FROM vouchers AS v
  WHERE v.order_id = 42 AND v.active
);

If the order condition disappears, an active voucher for another order can satisfy the query. A constant output does not rescue the wrong question. Review the outer entity, relationship key, and eligibility conditions before relying on a familiar SQL shape.

Can every output list be replaced with one?

No. The reference explicitly identifies INTERSECT subqueries as a possible exception. Set operations can use output values to decide whether a row survives. “Normally unimportant” must retain its qualification.

These unexecuted statements show the distinction without business tables. The first pair of outputs has no common row; the second pair does. EXISTS therefore has different truth values.

SELECT EXISTS (SELECT 1 INTERSECT SELECT 2);
SELECT EXISTS (SELECT 1 INTERSECT SELECT 1);

Before changing a projection, inspect whether the subquery merely filters rows or also compares projected values through a set operation. For the latter, reason about the whole expression. This is not a claim that every other complex subquery permits a mechanical replacement.

Nor does an unimportant output list imply that filter expressions are unimportant. Correlation and filtering establish which rows exist. Their role differs from the projected output. The lesson is to reject an unsupported side-effect dependency, not to move it to another SQL position and continue guessing about execution order. Functions and the surrounding query still need their own documented contracts.

Where should a record of every check be written?

Make recording an explicit application step and define “every check.” Recording a successfully completed decision might mean writing the request identifier, entity identifier, and result after obtaining it. Requiring both the decision and record to succeed together needs a suitable transaction and failure design. These are design choices, not an audit implementation validated here.

If the decision is true but recording fails, should the interface fail or return with a separately managed recording obligation? If a caller retries after a timeout, can one logical request create two entries? Those choices determine idempotency and recovery requirements. Incidental projection-call counts cannot decide them. Recording to an external service also introduces a boundary beyond a local database transaction.

A requirement to record attempts, including failed queries, needs an outer lifecycle: started, result obtained, query failed, or recording failed. A start record does not prove completion. Preserve the input and request identity so a retry does not obscure the earlier failure.

Proposed checks cover no match, one match, multiple matches, another order's voucher, recording failure, and retries. Assert existence and entity ownership separately from the promised recording count and state. An increasing log count is not the sole proof that the query answered the correct question.

Consider a retry receipt too. Request A can observe true, lose its response, and observe true again on retry. Two attempt records may be correct under an attempt contract; one final decision per logical request is a different contract. Distinguish logical-request identity from attempt identity. A log count of two cannot establish whether an intended unique decision was duplicated. Proposed assertions can retain two attempts and at most one accepted final result, including the unknown first response. If availability changes before retry, choose reevaluation or replay of a durably saved decision. Saving only the request identifier does not implement the latter. This is hypothetical, not an observed disconnect.

The site's query-plan evidence article distinguishes observing a plan from establishing execution outcomes. None of these queries or audit transactions was run here. Preserve inputs, expected semantics, and eventual execution evidence for the existence decision and the recording operation separately.
