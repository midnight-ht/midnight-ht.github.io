Can an existing Span attribute update after the count limit is reached?

Use a two-slot example to distinguish replacement from addition, preserve SHOULD versus MUST, and inspect actual SDK limits and exported fields.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-28 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • Attribute limits count collection entries rather than SetAttribute calls.
  • Existing-key replacement is SHOULD; discarding a new attribute beyond the count limit is MUST.
  • Span, event, link, and value-length budgets differ; verify effective SDK settings and later stages.

Suppose a recording Span has reached its attribute-count limit and code then updates an existing key named status. Replacing an existing value differs from adding another key. Do not treat every later SetAttribute call as consuming a new slot. Identify whether the missing information was an update or a new key, then inspect the SDK's effective budget.

Count limits constrain collections, not calls

The OpenTelemetry common specification's Attribute Limits requires the SDK to discard an added attribute that would exceed the collection's count limit; otherwise it must not discard it under that count rule. Separately, setting an existing key SHOULD overwrite its value. Preserve that distinction in normative strength: replacement is SHOULD, while the count-discard rule is MUST. Do not turn a recommendation into an unconditional implementation guarantee.

The checked specification identifies version 1.62.0. This concerns API and SDK contracts, not proof of a particular language implementation or project setting. The common count parameter defaults to 128, but effective behavior still needs the language SDK, version, and configuration. The example deliberately uses a limit of 2 for observation, not as a production recommendation. No SDK was run.

A unique-key collection is not a call counter. Setting one key twice intends to update one identity, rather than export two slots with the same name. The specification requires unique keys by default in exported collections. If the application needs a sequence of states, use an appropriate time-aware record rather than relying on repeated keys to preserve history.

Distinguish replacement from addition with two slots

Assume a still-recording Span with a count limit of 2. Set job.kind=import and job.phase=queued, update job.phase to running, then add job.ticket. Following the replacement recommendation, the phase update does not increase the number of unique keys. Adding ticket would increase the collection from 2 to 3 and encounters the required count-discard rule.

# Language-neutral pseudocode, not executed; configure limit=2 in the actual SDK
set("job.kind", "import")
set("job.phase", "queued")
set("job.phase", "running")  # existing key
set("job.ticket", "T-7")     # new key beyond the limit

Check keys and values, rather than asserting that the fourth call disappears: did the implementation update the phase, discard the additional ticket, and retain the earlier keys? Counting calls would incorrectly classify the third call as another attribute. Also add ticket below the limit as a control, establishing that an unrelated filter does not always remove it.

Ordering has a practical cost. Optional diagnostic keys can consume the budget before a necessary classification key is added. Supply stable, necessary information already known at Span creation and budget later diagnostics deliberately. The Trace API additionally explains that samplers can consider only creation-time information; later attributes cannot retroactively change that decision. This is not a reason to invent an unknown final state early.

A visible Span does not prove complete attributes

Attributes can disappear during SDK recording, later transformation, export, or backend presentation. Seeing a Span establishes that some record reached the viewing point. Network retries cannot recover a key already excluded from the local collection. Compare controlled output close to the SDK with subsequent stages before selecting a remedy.

Do not collapse all limits into one number. The Tracing SDK Span Limits separately describes event counts, link counts, and attributes per event and link. A full Span-attribute collection does not mean an event uses those same slots. Conversely, an existing event does not prove that every event attribute survived. Identify the specific collection and its configuration.

Immediately increasing every limit by orders of magnitude is a counterexample: it identifies neither the loss location nor the value of the missing field. A highly unique ticket identifier might be sensitive or unusable for the intended diagnostic action. More budget can retain more unnecessary data. Choose necessary keys and stable names, then assess actual cost and access boundaries. No memory or backend cost was measured here.

Does encoding a large JSON object into one attribute avoid every limit?

No. Attribute count and value length are separate budgets, and the common specification also defines configurable length and truncation behavior. Encoding many fields into one string reduces visible key count without establishing unlimited value length. It also changes field-level querying. Define length, interpretation after truncation, and sensitive-content handling rather than treating encoding as a universal escape hatch.

Lifecycle is another independent condition: this example requires a Span that is still recording. It does not cover modifying ended records. The site's Span ending and Context scope article explains that separate boundary. An update's count behavior does not make it valid at any arbitrary time.

Isolate recording prerequisites too. A sampling setup that does not record the Span can make all attributes absent; writing after End also cannot establish a count-limit failure. First use below-limit stable attributes to confirm the recording and export path, then vary only added-key count. Changing sampler, processor, and backend filters together would obscure the cause. This is a proposed experiment, not predicted output for a particular sampler.

Reverse the final two operations as another control: attempt ticket first, then update the existing phase. A rejected new key is not a blanket signal that the Span can never change again; the later update still has its own same-key contract. Preserve identical earlier keys and budget across both orders. If inspecting dropped counts, check what the actual export representation provides instead of inferring a count from a blank backend field.

Proposed verification retains exact SDK version, effective limits, write order, and raw export across below-limit, exactly-full, existing-key-update, and new-key-overflow cases. Compare Collector and backend output afterward. If an implementation differs from the SHOULD replacement recommendation, record its actual behavior and conditions rather than inventing results from normative language. No such checks were executed. The deliverable is a method for identifying the collection budget and loss location, not certification that every SDK preserves these attributes.
