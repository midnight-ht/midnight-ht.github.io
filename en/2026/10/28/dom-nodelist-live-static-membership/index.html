Skipping nodes during deletion? Check whether membership changes.

Distinguish live childNodes, static query results, and retained object references before choosing a traversal.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-28 · Estimated read 11 min
Translations
zh-CN en

Article

Key takeaways

  • The returning API determines membership behavior.
  • An initial batch differs from continuously clearing current contents.
  • Fixed membership does not freeze node contents.

Forward index-based deletion from childNodes can skip every other node. After the current node is removed, the next moves into its index while the loop advances. The name NodeList does not establish fixed membership. Examine the API that returned it, then decide whether the task processes an initial batch or the tree's current contents.

Why can two NodeLists update differently?

The DOM collection definition distinguishes live and static collections. Collections are live unless otherwise specified: their operations use current underlying data rather than a creation-time snapshot. The same collection object can therefore return a different length or node at an index after tree changes.

In the same document, querySelectorAll explicitly returns a static result. childNodes returns a NodeList rooted at the node and matching its children; the default live rule applies. Neither forEach availability nor being a non-array determines this behavior.

Child nodes include text and other non-element nodes. Formatting whitespace can make indexes differ from the visible card count. Define whether the task removes matching elements or every child. Those are different target sets and need different expectations.

How can three nodes leave the middle one behind?

Consider precisely three children A, B, and C, without intervening whitespace nodes. This is an unexecuted specification-based trace. Delete index zero, A, and the live list becomes B, C. Increment to one and that index now refers to C. Delete C and terminate against the shortened length, leaving B.

No concurrency or asynchronous request is required. Deletion and index advancement are sufficient. Changing loop syntax may still read the changing collection at problematic times. Trace node identities, indexes, and membership rather than diagnosing interruption from a final count alone.

One strategy copies the target membership with Array.from before processing stored references. That fits “process the batch present when this began.” Later arrivals do not automatically enter the array. It is not equivalent to continuously emptying whatever enters the container.

Another strategy repeatedly removes the current first child until none remains. That better expresses clearing current contents, but ongoing insertion requires a defined ownership and termination policy. No loop is claimed to terminate under every competing application behavior.

When should membership be fixed or queried again?

Suppose a bulk action promises to remove three cards selected when clicked, while remote data inserts a fourth. Fixed membership can preserve the original three-item promise; repeated current queries may include the newcomer. The task determines correctness. “Delete the selected three” should not silently consume later arrivals.

For rebuilding a temporary container exclusively owned by the operation, repeatedly taking its first child can be simpler. Still handle listeners, application references, and other resources under their own lifecycles. Tree removal alone does not establish complete resource cleanup. No memory analysis or leak-prevention result is claimed here.

A static query can retain elements that no longer match its selector. Query selected cards, remove selected from one, and the old membership remains; a new query evaluates the current tree. If execution requires current selection or authorization, recheck those conditions rather than treating an earlier result as permanent permission.

Proposed tests record membership and identity at query time, after insertion, after removal, and after changing a matching attribute. Compare an old static result with a new query; read the same live collection after changes. Then verify the business batch's intended identities, not just its final count. Deleting the wrong objects can produce the right count.

Does Array.from retain a node after DOM removal?

Yes, unless code changes the array. Copying membership does not create an independent DOM tree. The referenced node's text, attributes, and location can change. Static membership is neither immutable objects nor a content snapshot; saved query results can therefore expose updated text.

After fixing A, B, C into an array, remove B and change its text. The array can still reference that detached object. Document connection, membership in the original container, and current business identity are separate questions. This is a reference-semantics example rather than captured execution. Immutable records require an explicit data-copy and version strategy instead of retained DOM references.

The related template-fragment article explains movement consuming a fragment's children. Here the question is how collection membership responds to modification. State which objects this operation owns, then compare the returning API, mutation during traversal, and retained references. No DOM scripts or browser tests were executed for this article.

A proposed identity check saves a static result, removes one member, then compares retention in the old result with absence from a new query. Change its text and inspect the old reference. These observations separate membership, tree location, and object contents rather than reducing them to one length.
