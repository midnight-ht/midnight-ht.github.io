Why Recursive mkdir Returns the First Created Directory

Separate the requested mkdir target from its first created path, explain successful undefined results, and distinguish preparation from unique workspaces.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-28 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • Recursive mkdir reports the first created path, not the requested target.
  • An undefined path can accompany successful reuse.
  • Preparing a shared path differs from allocating a unique workspace.

A recursive mkdir request for /tmp/demo/a/b may return /tmp/demo, the first directory it created. Using that return value as the final output directory can write files at the wrong level. Keep the intended target separate from information about this invocation's creation work.

Creation information is not an echo of the target

The Node.js v24.22.1 filesystem reference describes undefined for successful nonrecursive mkdir and the first created path for recursive creation. When no directory is created, such as an already existing target, the path can be undefined; the callback reference states that case explicitly. This article uses version 24 semantics and unexecuted examples.

Assume /tmp exists but demo, a, and b do not. The first required creation is demo, while the requested final directory remains b. If demo already exists, the first newly created level can instead be a. That result depends on prior filesystem state and cannot be a stable alias for the destination.

This unexecuted success-path example keeps target responsible for location and firstCreated responsible for reporting. A second preparation should not change where the report belongs.

import path from 'node:path';
import { mkdir, writeFile } from 'node:fs/promises';

const target = path.resolve('demo-output', 'daily', 'reports');
const firstCreated = await mkdir(target, { recursive: true });
await writeFile(path.join(target, 'report.txt'), 'example\n');
console.log({ target, firstCreated });

The example does not provide a file-publication protocol. Repeated calls write the same filename; it establishes neither preservation of old content, exclusive writing, nor crash durability. It demonstrates which path belongs in the next operation, not that an export has been delivered.

A counterexample assigns mkdir's result to outputDir and passes it to path.join. A new hierarchy can write too high; an existing target can produce undefined and fail later. “First run works, second fails” can therefore conceal an incorrect destination even on the first run. Inspect variable identity before adding retries.

Should undefined be treated as failure?

Not by itself. For the promise form, fulfillment versus rejection distinguishes the basic operation outcome. The returned path describes where creation began. Recursive mode accepts an existing target directory, so no creation can be normal. A truthiness-based success check breaks legitimate repeated preparation.

That does not justify swallowing errors. An ordinary file at the target, an unusable parent, insufficient permissions, or exhausted resources still require their actual failure handling. Returning target from a broad catch can falsely communicate readiness and lose the original cause before a later write fails.

A preliminary existence check is not a guarantee either. It observes one instant, and another actor can change state before mkdir. For a directory-preparation requirement, invoke the suitable operation and handle its result. Later writes still have their own permissions, resource conditions, and possible intervening changes.

Logs should distinguish target, first newly created path, no creation needed, and failure. “created undefined” obscures both target identity and normal reuse. Preserve the original error category and stage rather than collapsing preparation, content generation, and writing into one generic failure.

Does successful mkdir establish an exclusive workspace?

No. Two tasks can both successfully call recursive mkdir on the same directory. That prepares a shared path; it does not allocate a unique name. Subsequent writes to report.txt can still collide.

The same-version mkdtemp reference provides a unique temporary-directory operation. Where that matches the requirement, follow its prefix rules and retain its actual returned directory as the task's resource identity. Its result differs from mkdir's first-created-ancestor information.

Unique workspaces still need ownership and cleanup. Decide what to remove after failure and what diagnostics to retain from the allocation record. A firstCreated value that points at a shared ancestor is a dangerous basis for recursive cleanup. No deletion script or production cleanup implementation is supplied here.

A fixed shared publication destination may instead require serialized publication or a deliberate merge protocol. Do not change the required destination merely to avoid a collision, or assume mkdir provides a lock because the destination must remain fixed.

Proposed tests cover an entirely new hierarchy, existing ancestors, an existing target, a regular file at the target, and creation failure. Assert destination identity, actual output location, and returned information separately; repeat preparation. Test task isolation with two operations and their output ownership, not simply two fulfilled promises.

A receipt matrix can distinguish three initial states: every child missing, only the leaf missing, and the target already present. The requested target remains identical while firstCreated changes level or disappears. It describes a change during one operation, not long-term resource identity. Preserve the absolute target and verify the file’s actual location rather than accepting any returned directory. A relative target can also change with the launch directory, so choose and record the base beforehand. Recovery receipts need stable target identity and the failing stage: preparation, content generation, or writing. A sometimes-empty creation field cannot supply either.

The site's rename and file delivery article covers later publication. No directories or files were created for this article. Keep the target stable and give creation information its own name before building the rest of the delivery process.
