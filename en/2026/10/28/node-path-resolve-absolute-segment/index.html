Why path.resolve Can Discard Your Base Directory

Trace Node.js v24 right-to-left resolution and working-directory fallback, separating path form, lexical ancestry, and filesystem authorization.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-28 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • resolve processes arguments right to left until an absolute path is formed.
  • isAbsolute and raw prefixes do not establish allowed ancestry.
  • Lexical checks do not freeze links or filesystem state.

Passing /srv/uploads and /tmp/report.csv as the two arguments in the POSIX example below uses the absolute path on the right. Supplying a base directory does not confine later arguments to it. The method constructs an absolute path; the caller must separately define where access is permitted.

Arguments are processed from right to left

The Node.js v24.22.1 path resolution reference processes arguments from right to left until an absolute path is formed. The current working directory is used only if the supplied segments do not establish one. This article uses the checked version 24 documentation and explicit POSIX examples rather than leaving platform style implicit.

This teaching code was not executed. In the first call, the rightmost argument is already absolute. In the second, a relative filename needs the base. Calling a variable base does not alter the algorithm.

import path from 'node:path';
path.posix.resolve('/srv/uploads', '/tmp/report.csv');
path.posix.resolve('/srv/uploads', 'report.csv');

The documented expectations are /tmp/report.csv and /srv/uploads/report.csv respectively. No files were created or written. If an interface permits writes only under uploads, the first target violates that interface while resolve has still done its own job correctly.

Relative input can escape too. A segment such as ../private/report.csv can normalize outside uploads. Rejecting leading slashes handles one form; it does not establish safe relative input. Conversely, an interface intentionally accepting arbitrary absolute output paths may require the observed behavior. The product contract determines whether it is wrong.

Do not transfer this description mechanically to join. These methods have different contracts despite accepting multiple strings. Replacing a method name without checking its input and output can merely replace one misunderstanding with another.

Does the interface accept a filename or a path?

If an upload product needs only a display filename, the server can generate the actual storage identity and destination. Separating display names, stored identifiers, and disk targets removes unnecessary path authority from the caller. Allowed characters, extensions, and collisions still need deliberate rules; removing slashes alone is not a complete policy.

An interface that genuinely accepts subpaths under an allowed root can consider lexical containment. After obtaining a candidate, use relative under the same platform style to examine whether the relative representation escapes through a complete parent segment or remains absolute. This is a string-level design consideration, not a deployment-ready access-control function.

A raw startsWith(base) check ignores path boundaries. uploads-backup can share the uploads prefix without being its child. Separators, case behavior, Windows drives, and shares add platform conditions. POSIX reasoning is not evidence of Windows validation.

The isAbsolute documentation explicitly limits the operation to literal absolute-path form and warns against using it to mitigate path traversal. True does not establish allowed ancestry; false does not prevent parent segments from escaping. The application needs authorization while the method answers a representation question.

May the candidate equal the base itself?

That depends on the operation. For “write one file,” an empty relative representation can mean the storage root itself, which generally needs separate rejection. For “list the allowed root directory,” the same location can be legitimate. A universal accept-or-reject rule confuses file and directory contracts.

Empty input needs similar attention. The resolver ignores zero-length segments and may fall back to the working directory when no absolute base is established. A missing filename should not silently become a different writable directory. Validate required fields and distinguish missing names, invalid forms, and forbidden targets.

The site's file URL conversion article addresses representation. Obtaining a valid native path does not finish ancestry checking, and ancestry checking does not choose the correct URL decoding boundary.

Lexical checks do not freeze the filesystem

Suppose uploads contains a symbolic link pointing outside the root. A string may remain under the allowed prefix while the actual filesystem operation follows the link elsewhere. Resolving existing objects can help identify targets, but new files, parent permissions, and directory mutation need a fuller access design. String calculations do not lock filesystem state.

If another actor can replace a directory between checking and opening, a race remains. Choose deployment-specific permissions, trusted directory ownership, and suitable opening operations, then verify the actual accessed object. This article identifies the boundary; it does not offer an unverified symbolic-link defense or turn relative into a complete sandbox.

Use two relocation cases. A fixed absolute base plus a relative filename should retain this example’s destination after changing the launch directory. Relative segments alone bring the working directory into resolution and can change the destination. This separates an omitted base from a right-hand absolute argument replacing it. Do not silently change working directory and retry on failure; that can find another same-named file. Put distinct markers in isolated locations and inspect which is actually read. Matching basenames prove no identity. Passing paths to another process also requires either an agreed absolute representation or an explicit working-directory contract.

Proposed acceptance records input, platform style, working directory, resolved target, and actual accessed object. Cover ordinary names, absolute right arguments, parent segments, similar prefixes, the root itself, empty input, and symbolic links. Valid requests should reach a known marker; invalid requests should fail before writing. Cross-platform claims require those systems. No code or access tests were run here.
