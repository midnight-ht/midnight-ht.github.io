Why an idle CPU node can still have a Pod rejected by namespace quota

Separate measured node usage from namespace request accounting, then trace Deployment acceptance, Pod admission, scheduling, and readiness.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-28 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • Idle measured CPU does not reduce accounted namespace requests.
  • A successful Deployment create does not establish all its managed Pods.
  • Quota changes do not reclaim existing resources or guarantee scheduling and readiness.

Suppose a node's measured CPU usage is low, yet a new Pod receives an exceeded-quota error. ResourceQuota checks the namespace's accounted declarations against its hard limits. Idle CPU does not establish available quota. Identify the resource named by the rejection before changing requests, releasing allocations, or applying for more budget.

Node usage and quota accounting answer different questions

The Kubernetes Resource Quotas documentation defines namespace constraints covering aggregate resource consumption and object counts. A create or update that violates a quota receives HTTP 403 Forbidden, with an explanation of the constraint. This article uses the current online mechanism; a documentation update is not a cluster release date. No cluster was accessed.

Read the resource name. A requests.cpu quota concerns accounted CPU requests, not instantaneous CPU use. An object-count quota counts the relevant objects rather than busy processes. Retain the quota name, resource, hard limit, used value, and proposed addition. “The machine is full” loses the distinction needed to select a repair.

The example below uses a namespace quota without scopes and explicit CPU requests. It does not calculate default injection, Pod-level budgets, or mixed init-container configurations. Where actual objects differ, inspect their final configuration and version-specific documentation. A source template need not be the final submitted or admitted object, so one repository setting cannot establish every allocation.

Two idle replicas can exhaust a request budget

Assume a requests.cpu hard limit of 2 CPUs and two accounted Pods, each explicitly requesting 1 CPU. The accounted total is 2. A third identical Pod proposes another CPU and would exceed the hard limit. Both existing replicas can have very low measured use without changing that accounting. This is an unexecuted configuration example, not captured cluster output.

It does not claim that any used value below hard necessarily leads to rejection. With a limit of 3 and no other allocation or constraint, this particular addition no longer exceeds this particular limit. Other quota resources and admission policies can still matter. Likewise, a limit of 2 with 1.5 already used leaves only 0.5: the next 1-CPU request still does not fit. Compare the addition, rather than treating any remaining balance as sufficient.

Choose a remedy based on the declaration's purpose. A justified request may require more namespace budget or removal of genuinely unnecessary allocations. An oversized request needs application and load evidence before reduction. Arbitrarily lowering it changes the resource commitment without necessarily reducing real demand, and can affect subsequent placement. No application demand was measured here and no replacement value is prescribed.

A successful Deployment request does not establish all its Pods

The documentation specifically notes that creating a workload object such as a Deployment can succeed while some managed Pods cannot be created. The controller's subsequent Pod requests still encounter constraints. A pipeline that checks only the Deployment create response can therefore report completion before the desired replica count exists. Inspect controller status and events to identify the rejected object request.

Imagine scaling from two replicas to three. The workload declaration is updated, but quota blocks the third Pod. Waiting only for that nonexistent Pod to become Ready can conceal the actual failure location. Start with the controller's failed-creation evidence, then inspect the corresponding quota accounting. Existing Pod logs can look entirely normal because those processes were not the rejected new object.

Rebuilding the same image or restarting healthy old replicas does not add namespace budget. Reducing the desired replica count has capacity and availability consequences that need an explicit decision. Raising the budget requires capacity and administrative consideration in a shared cluster. The configuration change itself is not evidence that the service recovered.

Does lowering quota terminate already created Pods?

Quota changes do not themselves act on already created resources. The documentation states that contention and quota changes do not affect those resources. Accounting above a newly lowered limit does not imply automatic deletion of old Pods or reduction of their requests. Reclaiming existing allocations needs a deliberate workload operation with understood business consequences.

Similarly, an application becoming quiet does not establish returned budget. Check the actual objects and refreshed accounting. Before removing an apparently unused workload, identify its owner, purpose, and recovery material. Nothing was deleted for this article. The proposed distinction is between deciding that an allocation is unnecessary and observing that quota accounting reflects its removal; a stale screenshot cannot establish the latter.

Why can scheduling still fail after raising quota?

Namespace admission and node placement are separate stages. More quota can remove this example's budget rejection without creating a suitable node. Allocatable capacity, existing requests, and other scheduling constraints still need examination. The site's regular init-container request calculation describes another source of larger effective requests; that calculation is deliberately outside this simplified quota example.

Fix the observation time as well. Two release jobs can read the same earlier balance before each requests another replica. That screenshot does not guarantee both later requests fit. This example predicts no control-plane processing order; retain relevant objects and current status around the rejection. A pipeline precheck is useful information, not a guarantee of later creation. Before resubmission, determine whether another release consumed the earlier balance.

Proposed verification retains hard and used values, explicit requests, desired replicas, controller events, and resulting Pod states. First arrange the example's budget rejection in isolation, then change one budget and confirm that specific rejection disappears. Continue through scheduling and readiness; preserve any new failure reason. These checks were not run and no deployment success is claimed. State whether evidence ends at admission, placement, or service readiness, rather than attaching only an idle-CPU chart.
