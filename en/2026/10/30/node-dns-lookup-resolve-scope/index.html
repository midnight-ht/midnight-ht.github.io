Why can Node.js resolve miss a name available through hosts?

Compare system name resolution and DNS A queries with IPv4 controlled, then inspect Node.js result shapes, errors, implementation paths, and connection boundaries.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-30 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • lookup uses system resolution; the resolve family queries DNS.
  • Control address family when comparing answer sources.
  • Resolution results do not establish connection identity or authorization.

dns.lookup() and dns.resolve() do not ask identical questions. lookup uses operating-system name resolution, which can include host-file and other system configuration. The resolve family performs DNS queries. A name available to another local application need not produce the same direct DNS answer.

System resolution is not just a DNS request

The Node.js DNS reference, checked on October 30, 2026 with a v24.22.2 header, says lookup need not use the DNS protocol or network communication. It is the interface for resolution through the operating system. No DNS, container, or network experiment was executed here.

Imagine a development environment with a local mapping for a test service but no corresponding DNS record. A system-resolving application can find it while a resolve4 diagnostic fails. Those results can both satisfy their contracts. Record the answer source instead of assuming a successful browser visit proves API equivalence.

System resolution can consult more than one configuration source. Platform configuration determines actual behavior; lookup should not be described as “only reads hosts.” One container's ordering is not a universal macOS or Windows rule.

Preserve both questions in one comparison

This complete script has not been run. Supply a controlled test name and arrange its system mapping and DNS data separately. A name that happens to fail on the public internet is not a stable negative control.

import { lookup, resolve4 } from 'node:dns/promises';

const hostname = process.argv[2];
if (!hostname) throw new Error('provide a controlled test hostname');

const results = await Promise.allSettled([
  lookup(hostname, { all: true, family: 4 }),
  resolve4(hostname),
]);

for (const [index, result] of results.entries()) {
  const operation = index === 0 ? 'system lookup' : 'DNS A query';
  if (result.status === 'fulfilled') {
    console.log(JSON.stringify({ operation, value: result.value }));
  } else {
    console.log(JSON.stringify({ operation, error: result.reason.code }));
  }
}

One proposed fixture maps the name to a loopback address through system configuration while the controlled DNS server has no A record. Another gives the two sources different addresses. Retain configuration, DNS responses, and actual outputs when executing; no invented result is supplied here.

The result shapes also differ. lookup with all returns address-and-family objects; resolve4 returns A-record addresses. Equal text does not make those structures interchangeable. Review downstream expectations, address-family requirements, error handling, and whether a single address or a collection is required. Selecting the first result is itself a policy.

An asynchronous API does not establish the same implementation

Node documents lookup as using getaddrinfo through libuv's thread pool. The resolve functions use a different implementation and perform DNS queries without that same getaddrinfo path. That can matter under particular workloads, but does not mean resolve is always faster.

A performance comparison that changes the answer source has changed the task. Investigate actual contention, concurrency, latency distributions, and errors before changing thread-pool settings or resolvers. A short script cannot establish a production improvement. This article reports implementation boundaries, not measurements.

For specific record questions such as A, AAAA, or MX, choose the corresponding query and interpret that record type. For application connections, first establish which resolution path the library actually uses. Some networking APIs permit a replacement lookup function; that permission does not establish behavioral compatibility after replacement.

Does lookup ENOTFOUND prove a DNS record is absent?

No. Node documents other possible causes, including unavailable file descriptors. Internal diagnostics should retain the operation, original error code, and environmental state rather than turn a local resource failure into an authoritative DNS fact. Error mappings across these APIs require review too.

This distinction changes recovery. Repeated DNS queries may not fix an exhausted local resource; absent records may require configuration work. Select retries from the actual failure path, not merely the module name.

Does an IP settle the HTTPS destination?

Resolution does not supply HTTP host identity, TLS server-name policy, or permission to contact the destination. If a connection uses the address directly, inspect how the library preserves the original server identity and certificate checks. Do not disable verification to obtain a successful connection. The site's ExternalName and certificate discussion addresses another naming boundary.

Likewise, either resolver succeeding is insufficient for safe server-side fetching. The checked destination and eventual connection must follow the same policy, including address changes and redirects. See outbound destination boundaries.

The source comparison explicitly fixes lookup to IPv4 to match resolve4’s A query. Otherwise address family and answer source change together, so a difference cannot be attributed to hosts versus DNS. Add dual-stack and ordering cases separately afterward. Do not discard unwanted answers merely to force agreement; derive expectations from the controlled configuration before observing outputs.

Proposed validation covers system-only mappings, DNS-only records, conflicting answers, A/AAAA differences, and controlled failures, then inspects which answer the actual connection uses. Record system configuration and runtime versions rather than treating workstation caches as server facts. Explain where an answer came from before replacing the API that produced it.
