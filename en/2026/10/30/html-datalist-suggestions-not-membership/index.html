Why can an HTML datalist accept a value outside its suggestions?

Separate open text from directory identity, trace datalist value and label behavior, and handle duplicate or withdrawn suggestions without treating them as authorization.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-30 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • A datalist suggests values without imposing directory membership on text input.
  • Selecting a suggestion inserts its value; its label is not an identity check.
  • Open names and controlled identities need different acceptance and recovery rules.

A department field offers three suggestions, but typing a fourth name can still leave the input valid. A datalist supplies suggestions; it does not turn a text input into a closed selection. Decide whether free text is allowed or an approved organization must be selected, then align the control, acceptance rules, and feedback.

Suggestions and constraints have separate sources

The HTML datalist definition describes predefined options for other controls. Eligible nonempty, enabled options provide suggestions with values and labels; an input uses list to associate with that source. This does not introduce a requirement that the value equal a suggestion. The input’s own type and applicable constraints still matter.

This article concerns an ordinary single-value text input, not multiple email values or other specialized controls. Required and membership in a current directory are different conditions. A nonempty field does not establish that an organization exists, remains eligible, or belongs to the applicant.

A suggestion popup can resemble a select visually. Inspect the actual element and request contract rather than inferring closed-set validation from a screenshot. Reducing typing effort is not input authorization.

Follow one organization answer through the task

Imagine an event application that accepts organization names freely and suggests familiar ones. This unexecuted example uses fictional names:

<form>
  <label for="organisation">Organization</label>
  <input id="organisation" name="organisation" type="text"
         list="organisations" required>
  <datalist id="organisations">
    <option value="North Reading Club"></option>
    <option value="South Photography Club"></option>
    <option value="Student Volunteer Team"></option>
  </datalist>
  <button type="submit">Continue</button>
</form>

Because the hypothetical product allows new names, East Chess Club should not be rejected solely for being absent from the list. The server still checks the agreed text and business conditions. Save and redisplay the answer actually supplied rather than silently selecting the nearest known organization. Fuzzy matching can change the applicant’s stated affiliation.

Proposed paths choose a known name, inspect the input value, review it, submit, and reopen the record. Repeat with an unknown name. Separately leave the field empty and compare native feedback with server rejection. These paths were not executed in a browser or API.

If the requirement becomes “Select a registered host organization,” the example no longer expresses the whole task. Use a closed choice or an interaction that explicitly selects a directory object. The receiving service checks its stable identifier, status, and relationship to the applicant. Matching display text does not itself confer object identity or permission.

Validate selection, text, and identity separately

A saved organization can become ineligible before a draft is resumed. Preserve enough context to explain the earlier answer, but do not treat it as proof of current eligibility. Reconfirmation or a defined review path may be appropriate; silently switching to another organization is not a repair for required validation.

Names can also be ambiguous. Two campuses may have volunteer teams with identical names. If an actual directory relationship is needed, show distinguishing information and submit the selected business identity. Do not infer authority from a few words. This is an application-design recommendation, not a datalist feature.

Alternatively, explicitly save free text and provide guidance for organizations outside the suggestions. Downstream reporting must then accept that answers are not automatically standardized or authenticated. Do not label every free-text affiliation a verified organization.

A select still needs a genuine unselected state and validation of current options. See required-select placeholder rules. Changing controls does not make a client field the sole acceptance authority.

If label is a name and value is an identifier, what enters the input?

The input list rules say that selecting a suggestion for this single-value input sets its value to the suggestion’s value as if typed. Presentation of labels and values can vary with the user agent; identical popup formatting is not promised.

For value org-42 and a readable organization label, inspect the resulting input value. Do not assume that the control keeps readable text while secretly submitting a separately trusted identity. A user can also type org-42. Whether the same string came from clicking a suggestion or typing is not an authorization proof. A product needing both readable names and controlled identity should represent the selection explicitly.

If a suggestion is withdrawn during editing, let the field contract determine recovery. An open name field can retain the typed text while explaining that suggestions changed. A directory-object field needs confirmation of a currently eligible object. Avoid silently clearing the answer or carrying an obsolete suggested identifier into an authorization decision.

Proposed verification covers suggestion selection, typing the same value, unknown names, missing input, duplicate names, and invalidated directory entries. Preserve input, request, and stored-record evidence. Check keyboard and target assistive-technology use without claiming compatibility or faster completion from an unexecuted example.

First decide whether the record contains text or a directory relationship. Suggestions are one part of entering the answer; acceptance, association, and recoverable failure complete the field contract.
