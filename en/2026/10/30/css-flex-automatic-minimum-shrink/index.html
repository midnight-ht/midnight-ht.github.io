Why can a long filename overflow a flex item with flex-shrink:1?

Use a filename-and-download card to separate shrink distribution, the current automatic-minimum condition, the actual flex item, and access to complete content.

Key takeaways

  • Shrink participation does not remove an item’s minimum size.
  • Inspect the actual flex item, main axis, and computed overflow condition.
  • After allowing shrinkage, decide wrapping, truncation, and full-name access separately.

The filename area is allowed to shrink, yet it pushes Download out of the card. Shrink distribution can still encounter an automatic minimum size. Identify the actual main-axis flex item before deciding whether to lower that bound; readable content remains a separate decision after the box can shrink.

Shrink permission does not remove a lower bound

The Flexbox automatic-minimum definition uses a content-based minimum for the relevant main-axis automatic minimum of a flex item whose computed overflow is non-scrollable. This analysis follows the 8 May 2026 Editor’s Draft, not a browser acceptance result.

Do not reduce that to “every flex item always has a content-width minimum.” Inspect the axis, automatic minimum, computed overflow, and applicable element rules. Visible scrollbars alone do not establish the computed condition.

Flex-shrink and minimum size therefore answer different questions. Increasing a shrink factor may still encounter the same lower bound. Explicitly allowing a smaller box also does not decide how a long string, table, or image should be displayed inside it.

Trace one download row

Assume a content width of 320 pixels, an 80-pixel action, and a 16-pixel gap, leaving 224 for the filename. These are paper inputs, not component measurements. A long unbroken filename can require more minimum-content space. This simplified example was not run:

<div class="download">
  <span class="filename">a-very-long-unbroken-export-filename.csv</span>
  <button type="button">Download</button>
</div>

.download { display: flex; gap: 16px; width: 320px; }
.filename { flex: 1 1 auto; white-space: nowrap; }
.download button { flex: 0 0 80px; }

Here the span is the direct flex item. A candidate sets min-inline-size:0 on it, allowing a smaller inline dimension in this horizontal-row example. Then choose wrapping, a usable way to inspect the full name, or product-approved truncation. A reachable button does not establish that the filename remains understandable.

If two files differ only near the end, truncation can hide the distinction. Provide a usable full-name route or another presentation that supports reading and copying. A hover-only tooltip introduces its own keyboard and touch questions rather than completing that responsibility automatically.

Find the layer that owns the minimum

A real component may wrap the span in a file-information div. The div is then the direct flex item; changing the inner span does not remove the outer item’s automatic minimum. Inspect the allocation boundary and any nested flex containers instead of applying the same rule to every descendant.

The earlier box-sizing article defines whether declared width includes borders and padding. It does not remove a main-axis automatic minimum. Nor does a minimum-size rule reserve margins or other fixed space. Record parent content width, item bounds, descendant content, and action position separately.

Direction matters too. This example uses a normal horizontal row. A column’s main axis or another writing mode needs a fresh mapping to the relevant dimension. A universal physical min-width rule might never touch the actual constraint.

Another counterexample has a shrinkable item containing a fixed 400-pixel table. The table can still overflow after the item becomes smaller. Establish which box changed, then decide whether the table needs scrolling, another layout, or different content presentation. Item size and content extent are different observations.

Is clipping the easier repair?

Clipping can be deliberate, but it can also hide the action, focus outline, or filename. Removing a horizontal scrollbar is not proof of a usable task. A truncation policy must identify what disappears, where the full content remains available, and what gets copied.

Overflow also participates in the automatic-minimum condition. If it changes together with sizing, do not attribute the entire result to the shrink factor. A proposed isolated comparison holds overflow constant while changing the explicit minimum, then compares content policies separately. No browser output or screenshot is claimed.

Proposed verification uses short names, long names, two names differing at the end, and error text while completing identification, copying, and downloading. Repeat with narrow layouts, enlargement, reverse-direction text, and nested wrappers. Record the actual flex-item bounds and reachable action. Changes to fonts, container width, or button wording require recalculating available space; 224 is not a production constant.

Why might zero on the span still have no effect?

Use two names sharing a prefix but ending in draft.csv and final.csv. Without hovering, check whether keyboard interaction distinguishes the intended version. Then copy its name and compare the complete original with any ellipsized display text. If the action selects final but copying yields draft, the boxes may fit while the task still fails. This is a proposed check, not a passed component result.

First establish whether the span owns the main-axis allocation. Then inspect an ancestor minimum, definite dimensions, and fixed-size descendants. If the item already shrank while text still escapes, the remaining problem is presentation; repeatedly lowering an already-zero minimum will not choose that policy.

Document shrink participation, the limiting minimum, retained content, and the completed action. No browser tests were performed here. Identifying the item and axis explains more than treating min-width:0 as a universal overflow instruction.
