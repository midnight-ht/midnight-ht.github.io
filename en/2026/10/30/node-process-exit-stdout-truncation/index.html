Why can a Node.js CLI truncate JSON after printing and calling exit?

Separate forced Node.js exit from exit status using a controlled CLI, destination-dependent stdout behavior, resource liveness, and exit-listener limits.

Updated 2026-10-30 · Estimated read 11 min
Translations
zh-CN en

Article

Key takeaways

  • Forced exit can truncate pending standard output.
  • Setting an exit code does not close every owned resource.
  • Verify process status, output bytes, and business delivery separately.

A Node.js CLI can hand JSON to stdout and still deliver incomplete output if it immediately calls process.exit(). Writes are asynchronous for some platforms and destinations, while exit forces termination. Selecting an exit status and terminating immediately are different operations; verify status and output separately.

A terminal display does not establish pipe delivery

The Node.js Process reference, checked on October 30, 2026 with a v24.22.2 header, explicitly warns that exit can truncate stdout. Some writes complete over several event-loop turns, which forced termination prevents. No CLI, pipe, or cross-platform experiment was run here.

A large JSON result can appear complete during a terminal check while a pipeline receiver encounters invalid JSON. Terminal, file, and pipe behavior can differ across operating systems. Do not say stdout is always asynchronous, or treat one terminal success as disproving the conditional risk.

Explicit exit is also different from natural liveness. It does not ask whether required writes have finished. A return code does not encode the number of received bytes, much less downstream business processing.

Arrange output and status independently

This complete unexecuted program generates hypothetical diagnostic data. Its fixed nonzero status is an illustrative choice, not evidence of a real failed check. It reaches module end without explicitly exiting; real tools must also close their owned resources.

import process from 'node:process';

const result = {
  status: 'example_failure',
  items: Array.from({ length: 10000 }, (_, id) => ({ id, note: 'example' })),
};

process.stdout.on('error', () => {
  process.exitCode = 1;
  process.stderr.write('stdout write failed\n');
});

process.stdout.write(JSON.stringify(result) + '\n');
process.exitCode = 1;

A negative control replaces the last line with process.exit(1) in an otherwise identical isolated script. A parent can capture bytes, status, and stderr, then compare JSON validity, expected item count, and content identity. Neither script has been executed here, and no particular size is claimed to reproduce truncation reliably.

This one-write example is not a general unbounded export design. Large output may need chunking, bounded memory, and stream backpressure. The site's writable backpressure article addresses production versus consumption speed; this question concerns forced termination cutting delivery short.

An error listener is not proof of correct output. It retains a failure status and diagnostic in this small example; the receiver still verifies actual bytes. A JSON protocol should also keep debugging text out of stdout and place diagnostics on its designated channel, with each channel's failures handled deliberately.

Why might exitCode leave the program running?

exitCode selects the status used at natural termination. It does not close a server, connection, or referenced timer, or stop business code from scheduling more work. End the entry-point flow and close resources through their owners rather than using exit to conceal missing cleanup.

For example, changing exit to exitCode can expose a diagnostic CLI's forgotten listening server. The newly visible liveness problem is not a reason to force termination again. Arrange observable closure and a bounded policy for unresolved cleanup. There is no universal shutdown controller supplied here.

Unref on every timer is not cleanup either. It changes liveness responsibility rather than awaiting delivery. See timer liveness for that distinction. Optional statistics and required output can have different loss policies.

Can an exit listener perform the asynchronous flush?

Do not rely on it. Node documents exit listeners as synchronous-only work; asynchronous tasks queued there are abandoned when the process terminates. A Promise, timer, or network flush inside the listener does not turn forced exit into awaited cleanup.

Start cleanup while the normal lifecycle can still perform it and observe completion or failure. beforeExit has different triggering conditions; its ability to schedule work does not imply explicit exit follows the same path. Validate any lifecycle dependency in the real script.

Proposed checks use an independent parent process, not a test framework's unrelated open handles. Feed identical data through pipes, redirected files, and a controlled terminal; retain runtime, platform, byte count, JSON parsing, content identity, and exit status. Add an early-closing receiver and write failure to ensure partial JSON is not accepted.

The parent should explicitly accept the example’s combination of complete diagnostic JSON and a nonzero status. Requiring zero would misclassify a correctly reported failure as transport loss. Use a fixed fixture and an independent protocol check rather than copying the producer’s serializer. Report parse failure, content mismatch, and status mismatch separately to identify whether truncation was actually observed.

A parent receiving all expected bytes proves that particular handoff, not downstream persistence or business correctness. Uploads, storage, and notifications require their own outcomes. No truncation threshold or shutdown result is claimed. Find explicit termination points, identify required outstanding work, and accept exit status, byte delivery, and resource closure as distinct results.
