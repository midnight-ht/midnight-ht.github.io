Why does an earlier Python SQLite write survive a failed script and rollback?

Trace executescript pre-commit under Python sqlite3 legacy transaction control, separating earlier writes, script-owned work, rollback, and connection handoff.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-30 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • Legacy script entry can commit an existing pending transaction.
  • A later BEGIN cannot absorb work already committed.
  • Verify mode, pending state, and the actual execution connection.

With Python sqlite3 LEGACY_TRANSACTION_CONTROL, executescript() commits a pending transaction before executing its script. Rolling back after a later script failure cannot undo that earlier commit. Investigate the connection mode and commit timeline rather than assuming an outer context covers every operation.

Script entry can be a commit boundary

The Python sqlite3 executescript reference, checked on October 30, 2026 in documentation headed Python 3.14.10, states the condition explicitly: legacy transaction control plus a pending transaction causes an initial COMMIT. Other transaction control required by the script must be written into it. This article does not generalize that rule to every autocommit setting.

A migration may write an operation record first, then invoke a script for further changes. The caller expects any later failure to remove the record. But a BEGIN inside the script starts a subsequent transaction; it cannot absorb an earlier write already committed at script entry.

Python introduced the autocommit control in 3.12. When it appears alongside older isolation_level settings, identify which mode governs the connection. SQLite's general transaction support and a string-valued option do not prove the whole Python function is atomic.

Observe pre-script and in-script writes separately

This complete teaching program has not been run. It requires a Python version supporting the autocommit argument and uses an isolated temporary database. A nonexistent table deliberately causes failure; no measured output is supplied.

import sqlite3
from pathlib import Path
from tempfile import TemporaryDirectory

with TemporaryDirectory() as directory:
    path = Path(directory) / "example.db"
    con = sqlite3.connect(
        path, autocommit=sqlite3.LEGACY_TRANSACTION_CONTROL
    )
    try:
        con.execute("CREATE TABLE events(id INTEGER PRIMARY KEY)")
        con.commit()
        con.executemany("INSERT INTO events VALUES (?)", [(1,)])
        print("before script", con.in_transaction)
        try:
            con.executescript("""
                BEGIN;
                INSERT INTO events VALUES (2);
                INSERT INTO missing_table VALUES (3);
                COMMIT;
            """)
        except sqlite3.Error:
            con.rollback()
        print("after rollback", con.in_transaction)
        print(list(con.execute("SELECT id FROM events ORDER BY id")))
    finally:
        con.close()

The documented expectation places row 1 in the initial committed transaction and row 2 in the explicitly started script transaction that rollback discards. The distinction is transaction membership, not a general slogan that the first row always survives every failure. Changing initialization, mode, or script control requires a new expectation.

in_transaction helps observe current pending state. It does not reconstruct which business actions were committed earlier. Associate phase markers with row identities. A second connection can test visibility at a defined point, while its own read-transaction lifetime must also be controlled.

Choose one owner for atomicity

If all writes must succeed together, select one transaction-management approach and place the related statements inside it. Fixed SQL with parameterized values can use execute or executemany; several lines of Python do not require a script interface. Untrusted values should not become arbitrary SQL script text.

A migration script can explicitly own BEGIN, COMMIT, and failure handling, but any prior write that must share its outcome must belong to that contract too. A precondition rejecting an unexpected pending transaction can be clearer than silently committing the caller's work.

Putting BEGIN in a script does not guarantee a clean connection after every error. Handle the exception, establish current state, roll back unfinished work, and decide whether the connection can be reused. Closing in finally is resource cleanup, not evidence that the migration committed successfully.

Why does an outer connection context not undo the earlier write?

Context exit handles relevant pending work; it cannot reverse a completed COMMIT. If script entry committed earlier operations, a later context rollback has a narrower scope. That does not make connection contexts useless. It means an intervening commit changed the boundary.

Adding nested BEGIN statements without inspecting current state is not a general repair. Mode, pending state, and script-owned control can conflict. Draw the timeline and remove competing ownership rather than catching transaction-control errors and continuing.

The legacy-control explanation also says the script's initial commit is independent of isolation_level. Setting that attribute to None does not erase a transaction explicitly begun elsewhere. Keep this conclusion within legacy control; design and test other autocommit modes from their own documentation.

Proposed checks cover no pending work, pending writes, successful scripts, mid-script failures, and scripts without transaction statements. Start from equivalent databases and retain Python/SQLite versions, mode, stage states, observer reads, and final rows. Stop a failed round before unrelated writes obscure its boundary.

With reused connections, inspect the mode on the actual execution connection, not merely an initialization default. An adapter may change attributes later. Record mode and transaction phases without private row data, and reject an unexpected unfinished transaction at handoff. Tests that always create fresh connections do not validate pooled reuse. Also check that failure does not pass pending work to the next borrower.

The site's SQLite lock-wait and retry article covers another failure responsibility. No migration, rollback, or driver experiment was executed here. Acceptance should locate every jointly required write in its actual commit, not merely report that the function was “wrapped in a transaction.”
