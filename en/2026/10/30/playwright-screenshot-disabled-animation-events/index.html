Why can a Playwright screenshot still trigger transitionend with animations disabled?

Use a complete unexecuted Playwright spec to examine finite-transition completion, infinite-animation restoration, active-transition preconditions, accepted baselines, and task-completion evidence.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-30 · Estimated read 18 min
Translations
zh-CN en

Article

Key takeaways

  • Fast-forwarding finite animations can trigger end events and associated page logic.
  • Infinite animations return to their initial state and resume after the screenshot.
  • A stable image adds no evidence that a backend task finished.

Setting animations to disabled in a screenshot assertion does not preserve the page at the instant of the call. Playwright fast-forwards finite animations to completion, which can fire transitionend; infinite animations follow a different path. Those actions belong in an explanation of state before and after capture.

Imagine a report panel with an opening transition. A transitionend handler replaces “Opening” with “Expanded” and reveals the next action. A test starts opening the panel and requests a screenshot, expecting an intermediate state. The author assumes disabling animation only removes visual movement, then attributes the already-visible action to a fast request.

The Playwright toHaveScreenshot animation option supplies another explanation. With disabled, finite animations are fast-forwarded to completion so events such as transitionend can fire. Infinite animations are canceled to their initial state and played again after the screenshot. The option covers CSS animations, CSS transitions, and Web Animations, rather than changing one CSS property.

Expose the state dependency

This complete but unexecuted report-panel.spec.js uses the @playwright/test page fixture. It defines the button, panel, CSS, and handler inside the page, then operates them from the test. The button sits outside the transitioning panel. There is no request whose completion a screenshot could establish.

import { test, expect } from '@playwright/test';

test('capture the expanded report panel', async ({ page }) => {
  await page.setContent(`
    <!doctype html>
    <html lang="en">
      <head>
        <meta charset="utf-8">
        <style>
          body { margin: 24px; font-family: sans-serif; }
          #open { margin-bottom: 16px; }
          #panel {
            box-sizing: border-box;
            width: 320px;
            padding: 16px;
            border: 1px solid #333;
            opacity: 0.2;
            transition: opacity 30s linear;
          }
          #panel.is-open { opacity: 1; }
        </style>
      </head>
      <body>
        <button id="open" type="button">Open report</button>
        <section id="panel" data-testid="panel" data-phase="closed">
          <h1>Report preview</h1>
          <p>No remote request is part of this example.</p>
        </section>
        <script>
          const panel = document.querySelector('#panel');
          const button = document.querySelector('#open');
          panel.addEventListener('transitionend', (event) => {
            if (event.target === panel && event.propertyName === 'opacity') {
              panel.dataset.phase = 'expanded';
            }
          });
          button.addEventListener('click', () => {
            void panel.offsetWidth;
            panel.dataset.phase = 'opening';
            panel.classList.add('is-open');
          });
        </script>
      </body>
    </html>
  `);

  const panel = page.getByTestId('panel');
  await page.getByRole('button', { name: 'Open report' }).click();
  await expect(panel).toHaveAttribute('data-phase', 'opening');

  const hasActiveFiniteTransition = await panel.evaluate((element) =>
    element.getAnimations().some((animation) =>
      animation.playState === 'running' &&
      animation.effect !== null &&
      Number.isFinite(animation.effect.getComputedTiming().endTime)
    )
  );
  expect(hasActiveFiniteTransition, 'active finite transition before capture')
    .toBe(true);

  await expect(panel).toHaveScreenshot('report-panel-expanded.png', {
    animations: 'disabled'
  });
  await expect(panel).toHaveAttribute('data-phase', 'expanded');
});

The page handler marks expanded only when the event target is the panel and the property is opacity, excluding a child’s unrelated end event. The test separately checks opening and an active animation with a finite end time, performs a named screenshot assertion, and checks expanded afterward. If a precondition fails, investigate whether the transition started or already finished rather than skipping the check and attributing the result to capture.

Thirty seconds is an illustrative finite duration intended to make the transition observable, not a production recommendation or a timing guarantee. Time still passes between the precondition check and capture. This is a path to verify, not a claim that the final state alone isolates causation.

The screenshot assertion also needs a reviewed, accepted baseline for the relevant environment. No test was run, PNG generated, or baseline approval recorded here. Automatically producing a new baseline would not establish that somebody independently accepted it as correct. A complete spec is not a test-pass receipt.

If the relevant finite transition is fast-forwarded during screenshot preparation, its end handler may run. The expanded state could reflect a change influenced by the capture policy, not a backend result. If the callback does not run, check whether the transition was still active; the option’s name does not establish that every handler must fire.

Finite and infinite animations differ

A finite animation has an ending position. Fast-forwarding can bring it to that visual endpoint and trigger logic dependent on completion. An indefinitely spinning loading indicator has no equivalent natural finish. The documented behavior instead cancels it to its initial state and resumes it after capture. A still spinner does not establish that its associated work finished.

That distinction changes interpretation. A report-download spinner may look stationary because of screenshot handling while its request, file generation, or authorization decision remains pending. Treating “not spinning” as “report generated” turns a visual policy into a business-completion condition.

Panel opening and report generation can also happen concurrently. Completing the opening transition can legitimately establish an expanded panel. It cannot announce the result of a different asynchronous request. Application state should follow the relevant task result. A screenshot can inspect how a known state looks without becoming the sole proof that the backend finished.

Specify the state the image should prove

First state the screenshot’s purpose. For a panel after report loading, wait for an explicit application completion state and retain an assertion about the actual result. For an expanded layout, establish expansion before capture and let the screenshot policy handle remaining movement. Testing an animation’s intermediate frames needs an observation method suited to that goal; the default disabling policy should not be expected to preserve them.

A longer fixed delay does not replace this decision. It might happen to place a test after completion while leaving the screenshot preparation’s event effects unexplained. Nor should an end handler be deleted merely to stabilize an image. Determine whether it owns presentation lifecycle or mistakenly owns business state, then verify behavior and appearance separately.

Record the project’s Playwright version, state before the assertion, whether relevant animations are finite, what handlers do, and the state afterward. The current documentation entry does not assign one fixed version to every project, and this article did not inspect the reader’s dependency files. An actual project version is needed to explain environment-specific observations.

Preserve distinct failure paths

A child’s transitionend event could bubble to the panel while a handler fails to filter its target, marking expansion too early. That handler-scope problem can coexist with screenshot animation handling. Inspect event target and property information first, then determine how capture affects that condition instead of attributing every change to the tool.

A second failure concerns later test steps. Infinite animations resume after the screenshot, so subsequent observations can encounter movement again. A still image from one assertion does not establish a permanently frozen page for a shared test flow. Record the assertion’s scope separately from later behavior.

No tests were executed here, and no stability improvement or pixel-difference statistics were measured. These checks describe how to establish verifiable conditions; a project still needs to run its actual page with relevant browsers and recorded versions.

Can a stable screenshot replace a completion assertion?

Stable appearance alone does not justify removing it. Completing a finite animation or temporarily returning an infinite one to its initial state can simplify image comparison without adding evidence of a backend result. Keep the behavioral assertion about completion, then use a screenshot to inspect its presentation.

When animation changes, review whether capture preparation triggers lifecycle behavior. When requests or business results change, review completion state. The checks can cooperate while retaining evidence for what each actually establishes.
