Why can frontend connections still pass after a NetworkPolicy deny-all?

Combine a frontend allowance with an empty ingress policy for one ledger Pod, then separate additive permissions, source egress, enforcement support and new-connection checks.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-30 · Estimated read 14 min
Translations

Article

Key takeaways

  • Applicable policies combine allowed entries by direction; empty ingress does not override another permission.
  • Source egress and destination ingress are independent, and policy resources need an enforcing plugin.
  • Test new ordinary-Pod connections with a healthy positive control; inspect established connections separately.

Adding a NetworkPolicy with no ingress rules does not override another policy's existing permissions for the same Pod. Standard NetworkPolicy combines the allowed sets of applicable policies for each direction. Tightening access requires changing the rule that grants it, rather than creating a deny-all last. This discussion concerns new connections; the effect of policy changes on established connections is implementation-defined.

Confirm that the policy has an enforcing implementation

The Kubernetes Network Policies reference requires a supporting network plugin. Creating a resource without an implementation enforcing it does not provide the expected filtering. The original was checked again on October 30, 2026. No cluster was accessed and no security effectiveness was measured.

API acceptance establishes that a declaration exists. Plugin support, controller health and observation of the configuration are separate evidence. Record Kubernetes and plugin versions, and distinguish the standard API from vendor extensions with their own precedence or deny semantics.

The target selector identifies Pods, and policyTypes identifies directions. Ingress isolation does not automatically establish egress isolation. Nor is isolation a promise to block every network path: node and host-network traffic have additional boundaries. The example therefore fixes ordinary Pod-to-Pod connections and starts fresh TCP connections.

Two policies select one ledger service

Assume a normal Pod labeled app=ledger in namespace test, with an application actually listening on port 8080. The same namespace contains a role=frontend caller and another caller with different labels. Neither source is initially egress-isolated. These complete policy declarations are unexecuted; the corresponding workloads were not created.

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: ledger-from-frontend
  namespace: test
spec:
  podSelector:
    matchLabels:
      app: ledger
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector:
            matchLabels:
              role: frontend
      ports:
        - protocol: TCP
          port: 8080
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: ledger-empty-ingress
  namespace: test
spec:
  podSelector:
    matchLabels:
      app: ledger
  policyTypes: [Ingress]
  ingress: []

The first policy permits matching source Pods in the same namespace to connect to destination TCP port 8080. The second selects the same destination but contributes no allowed entries. Their ingress union retains the frontend permission. An empty list is not a higher-priority rejection action, and creating it later does not subtract an earlier permission.

The other caller does not obtain the same permission from these two policies. That prediction assumes these are the complete applicable policies, source egress remains unrestricted, and the test uses ordinary Pods and new connections. Another broad allow policy enlarges the union. A source-side egress restriction can prevent the frontend from connecting. Reading two YAML files alone cannot establish the complete state of a cluster.

Leaving only the empty ingress policy, with no other applicable permissions, expresses the example's default denial. Deleting both policies can instead return the Pod to non-isolated ingress if no other policy selects it. Deleting a policy is not inherently more restrictive; calculate the isolation condition and allowed set remaining afterward.

Tighten the permission or expand the isolation baseline?

To remove frontend access, change or remove the granting rule while preserving the required isolation baseline. To reduce permitted ports, narrow that rule's ports. A stricter-sounding object name does not change how selection, direction and rule contents are evaluated.

A separate namespace-wide baseline can use an empty target selector and add necessary permissions deliberately. It affects more workloads and needs a dependency inventory and recovery plan. It still does not override permissions from other applicable policies. A wider scope does not create higher priority.

Review the complete policy set for one destination and direction. List what each selects and which source-and-port combinations it permits, then compute the union. Inspect actual labels: a label change can make an older broad policy newly applicable. Diagnosis should name the permission explaining the result rather than merely asserting that the newest object failed.

Why can a new connection fail when ingress permits it?

The official documentation requires both source egress and destination ingress to allow a connection. If an empty egress policy later selects the frontend, destination permission alone cannot permit initiation. Inspect the source's policy set independently instead of broadening ledger ingress and increasing exposure without repairing the actual blocking side.

Permission also does not start an application listener. Separate policy allowance, network reachability and process listening. Service access introduces target resolution; see Service ports and targetPort. A direct Pod-address control can reduce discovery and forwarding variables, but is not automatically a production access design or a substitute for response and identity validation.

Proposed isolated checks fix Pod identities, labels, protocol and port. Compare the frontend permission alone, addition of the empty ingress policy, and removal of the old permission. Start new connections from both callers in every stage and retain the complete applicable policies, source-egress state and results. Reverse policy creation order as another control. Observe actual implementation readiness and propagation instead of treating an early attempt as a stable outcome.

First confirm that the test tool really creates a new connection and receives the expected application response under known permitted conditions. If the process is not listening, every caller can fail without proving any policy effect. Restoring the same necessary permission afterward can help distinguish policy changes from application or path failure. Keep the application version and destination fixed throughout.

Test established connections separately. The specification leaves their reaction to policy changes to the implementation. An old connection continuing to work does not establish that new connections remain permitted. None of these checks were executed. Identify the rule contributing permission, then verify new connections and application outcomes rather than accumulating deny-all names around the same old allowance.
