Why does a Pod keep sending an old token after the projected file rotates?

Follow a projected credential from file refresh to request adoption, including stale handles, subPath, client headers and separate receiver authorization.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-30 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • Platform rotation needs an application consumer that adopts the new value.
  • Old handles, copied files and fixed headers can preserve stale credentials.
  • Separate lifetime, audience and object authorization without storing replayable secrets.

A projected ServiceAccount token file can rotate while an application keeps sending the credential cached at startup. Kubelet refreshes the file; the application must reload it and make subsequent requests use the new value. A restart temporarily helping is a diagnostic clue, not evidence that credentials should become permanent.

Where does automatic rotation stop?

The Kubernetes service-account configuration guide describes kubelet requesting, storing and refreshing projected tokens, including proactive rotation after 80 percent of TTL or twenty-four hours. It separately assigns reloading to the application. Sources were checked on October 30, 2026. No real token was read, printed or saved, and no cluster was accessed.

There is a handoff between file and consumer. A startup-only string does not change when the mounted path changes. A request-header closure may keep the original value even after another task loads the replacement.

Separate file refresh, application reload, client adoption and receiver validation. File modification time does not prove which credential a request used; one authentication failure does not establish expiry. Preserve safe timing and state evidence without copying bearer tokens into logs.

Review the projection and consumer together

This unexecuted fragment describes source and path, not a complete application deployment. The account, image and receiver need separate preparation. Receiver.example is a hypothetical audience contract, not an integrated provider.

spec:
  serviceAccountName: build-robot
  containers:
    - name: worker
      image: example.invalid/worker:demo
      volumeMounts:
        - name: receiver-token
          mountPath: /var/run/receiver
          readOnly: true
  volumes:
    - name: receiver-token
      projected:
        sources:
          - serviceAccountToken:
              path: token
              expirationSeconds: 7200
              audience: receiver.example

Assuming the receiver trusts the issuer and audience, the consumer obtains credentials from /var/run/receiver/token. A faulty consumer reads once forever. A candidate reloader reopens the path at controlled times, updates future requests and handles read failure explicitly. Two hours is an illustrative requested lifetime, not a recommendation or evidence of the actual issued lifetime.

Follow the handoff to the real request generator. A refresh task can update a variable while an existing client retains a copied header. “Reload successful” then does not establish request adoption. Rebuilding clients repeatedly without checking ownership, concurrency and connections can conceal the same defect.

The projected-volume reference adds a specific boundary: projected sources mounted through subPath do not receive updates. Copying the token to an ordinary file and forever reading that copy also changes the source contract. Identify the consumed path and mount before tuning reload frequency.

Read every request or maintain a bounded cache?

Per-request reads make adoption simple to express, but introduce file-access cost and failure handling. Caching needs a refresh trigger, maximum staleness and safe replacement. The guide discusses periodic reload, but a particular interval is not a universal availability or security promise.

Do not permanently fall back to the old value after a refresh error while reporting success. A bounded policy might retain a known-valid credential briefly, or fail new requests clearly, according to explicit requirements. Concurrent replacement must provide a complete consistent value to each request.

A long-lived Secret is not a direct repair for a consumer that never adopts changes. It changes lifetime and revocation risk without fixing client behavior. Review exceptional needs explicitly rather than extending lifetime to avoid reload work. Rotation and revocation cover general incident handling; no actual leak is claimed here.

Should rejection after reload trigger more token rotation?

Locate the rejection first. Issuer, audience and lifetime checks differ from RBAC authorization for an operation. A fresh authenticated token can lack access to the target object. Rotation does not create the missing grant. Interpret actual receiver errors and server evidence rather than assigning every status code one cause.

The earlier receiver.example audience belongs to a hypothetical external receiver, whose authorization follows its own contract. For a separate Kubernetes API example, first use an audience that the API accepts and authenticate successfully, then inspect the account’s permission to read the target ConfigMap. An external-audience token is not assumed usable for that API. An audience mismatch instead calls for the projection and receiver contract. Preserve safe subject identifiers, operation scope and rejection stage without the bearer value.

Proposed isolated controls compare startup-cached and reloading consumers through a rotation. Add read failure, a stale header closure, subPath versus ordinary projection, audience mismatch and insufficient permissions. Use controlled audit and nonsensitive timelines. None were executed. The application's responsibility ends only when refreshed file content is actually adopted by requests, not when a refresh task logs success.

Distinguish reopening the current path from rereading an old file handle. A method named reload does not itself establish adoption of the updated projection. Compare those consumers explicitly under the selected mount and client behavior.

Adoption evidence can use reload times, client configuration revisions and controlled receiver identity results. It does not require storing reusable credentials. Use safe run identifiers and retention rules rather than preserving token contents or replayable authentication headers.
