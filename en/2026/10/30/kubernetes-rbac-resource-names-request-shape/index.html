Why can a named RBAC get succeed while a list is forbidden?

Separate named reads, selector-constrained collection requests and top-level creation, then verify the subject and other additive grants.

Updated 2026-10-30 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • Named reads and collection requests provide different authorization information.
  • A resource name does not express a named-only top-level create contract.
  • Other grants, stale client views and missing objects need separate controls.

A service account that can get one ConfigMap but cannot list ConfigMaps is not necessarily waiting for its authorization to take effect. ResourceNames must be interpreted with the request verb and shape. A named get, a collection list and a top-level create are different authorization questions. Inspect the actual client request before granting broader access.

A name restriction is not automatic result filtering

The Kubernetes RBAC reference allows resourceNames restrictions for certain requests. A name-restricted list or watch needs a matching metadata.name field selector for authorization. RBAC does not first grant access to the whole collection and then filter unauthorized objects for the client. The documentation was checked on October 30, 2026; no cluster or authorization test was accessed.

A get normally identifies its object in the resource path. A list addresses a collection. A UI operation described as viewing one configuration might nevertheless list everything before selecting it. Equivalent business intent does not imply equivalent information presented to the authorizer.

Record identity, namespace, resource, subresource, verb and name conditions. Discovery calls can fail before the resource request; do not treat every final error as justification for unrestricted resource access.

Authorize one configuration deliberately

Assume ConfigMap my-config and service account config-reader already exist in namespace test. This unexecuted Role and its binding command require separately prepared objects and isolated credentials.

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: named-config-reader
  namespace: test
rules:
  - apiGroups: [""]
    resources: ["configmaps"]
    resourceNames: ["my-config"]
    verbs: ["get", "list", "watch"]

Bind the same role and subject with this unexecuted command:

kubectl create rolebinding named-config-reader --namespace=test \
  --role=named-config-reader --serviceaccount=test:config-reader

With only this relevant authorization, getting my-config and getting a different name should differ. For collection reads, distinguish a matching selector from no selector. For example, kubectl get configmaps -n test --field-selector=metadata.name=my-config expresses the name condition, but must also use the intended account. No credentials or command receipt are supplied here.

An administrator running that command cannot establish the service account's permission. Other bindings may hide the narrow rule. Fix identity and request shape together, and preserve status codes and reasons so absence is not confused with refusal.

Does adding create restrict creation to this name?

The official reference says resource-name restrictions cannot constrain top-level create or deletecollection. The name may not be available for authorization during top-level creation. It explicitly distinguishes subresources, such as using resourceNames with pods/exec.

This does not mean adding create to a name-restricted rule automatically permits arbitrary names. It means the rule cannot express the desired named-create contract. Content and naming restrictions may require applicable admission mechanisms, with their own version and authorization review. Removing the name restriction to make a client work is an access expansion that needs an explicit decision.

A fixed-object reader can use get. A list/watch client needs to support the selector, including subsequent reconnect requests. A client that only lists everything may need modification, a different isolation design or consciously broader authorization. Do not silently turn the minimum scope into unrestricted reading.

Why can access survive after this Role is narrowed?

RBAC permissions can come from several roles and bindings. Narrowing one Role does not revoke another grant. Inspect the actual subject and relevant RoleBindings and ClusterRoleBindings. Missing permission in one rule is not a global denial.

If another binding grants config-reader access to every ConfigMap in the namespace, the named rule does not override it. Identify the binding supplying the additional permission. Before removing it, check its purpose and dependents; no permission changes were made here.

Proposed checks use an isolated account for named get, another-name get, matching-selector list, unfiltered list and watch reconnection. Add and remove a separate grant as an independent control. Test top-level create separately without interpreting its failure as universal permission for other names. Retain identity and request conditions without exposing tokens.

Permission to get also does not prove configuration correctness or permission to update. As with object access checks, names do not replace authorization. Here the additional requirement is that the request communicates the name condition that the rule actually evaluates.

A watch client must retain the selector when reconnecting, not merely on its first request. A controlled disconnect can expose a later unfiltered request without granting unrestricted watch to hide the error.

Prepare distinct object-state controls: permitted and existing, forbidden but existing, and permitted but absent. Failure to read a nonexistent comparison object alone does not demonstrate authorization refusal. Use nonsensitive fixtures and preserve the server result without exposing denied configuration contents.

Also separate cached UI content from a new authorized request. Record actual network requests, binding revisions and observation times rather than assuming an old displayed value proves continuing access.
