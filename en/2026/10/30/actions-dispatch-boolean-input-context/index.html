Why can an unchecked manual Boolean still select an Actions branch?

Trace manual input types through expression evaluation, shell text and step-output handoffs using a diagnostic-only workflow.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-30 · Estimated read 11 min
Translations
zh-CN en

Article

Key takeaways

  • A declaration and consuming context jointly determine the input contract.
  • Text handoffs require explicit format and type handling.
  • Correct branch selection does not establish production release authority.

If an unchecked manual-workflow Boolean still enters a condition, inspect which context the expression reads. Workflow_dispatch inputs can preserve Boolean false; the corresponding event-context value is a string. A nonempty “false” string is not a Boolean false. Trace the declaration, consumer and output handoff separately.

Identical-looking content can have different types

The GitHub Actions syntax reference distinguishes Boolean-preserving inputs from string-converting github.event.inputs. Choice inputs are strings too, even when an option is spelled true or false. The online documentation was checked on October 30, 2026; no workflow was triggered.

The expression reference identifies false, zero, empty strings and null as falsy; other non-falsy values become true in conditions. The string “false” is not empty. A direct condition consuming it can therefore disagree with the user's unchecked-box intention without the UI having changed the choice.

Capture the trigger, declaration and final expression. A screenshot displaying false does not establish its type. Reusable workflows, other triggers and step outputs have separate contracts.

A complete diagnostic-only workflow

This unexecuted example uses a manual trigger and a Boolean declaration. It prints diagnostics without deployment, external writes or production credentials.

name: inspect-boolean-input
on:
  workflow_dispatch:
    inputs:
      show_details:
        description: Show optional diagnostic details
        type: boolean
        required: true
        default: false
jobs:
  inspect:
    runs-on: ubuntu-latest
    steps:
      - name: Explain selected branch
        env:
          TYPED_VALUE: ${{ toJSON(inputs) }}
          EVENT_VALUE: ${{ toJSON(github.event.inputs) }}
        run: printf 'typed=%s event=%s\n' "$TYPED_VALUE" "$EVENT_VALUE"
      - name: Optional details
        if: ${{ inputs.show_details }}
        run: printf 'Optional details selected\n'

With false, the final step should skip; true selects it. JSON representations help distinguish the context values, but environment variables delivered to the shell are text. Their representation does not turn the shell environment into the original typed context. No actual stdout is supplied.

A negative control replaces the condition with direct consumption of the event-context switch without comparison. That nonempty string can select a different branch from Boolean false. If the event context is required, compare according to an explicit string contract rather than trusting Boolean-looking text. Prefer one reviewable input route instead of unrelated conversions in each job.

Explicit comparison or JSON conversion?

For the declared Boolean, typed inputs are clearest. For an external handoff restricted to true/false text, either compare strings explicitly or validate and parse them. Define missing, empty and malformed cases. Unknown values should not silently choose a more privileged action.

FromJSON parses valid JSON; it does not reliably infer arbitrary text as the intended Boolean. Invalid text can fail the expression, while a valid number or object is still not the promised type. A conversion function cannot replace the format and type contract.

Step outputs can reintroduce the string boundary. A value originally Boolean does not automatically retain that type after being serialized as a job output. Review the output contract and consuming expression, then test true, false, empty and invalid inputs separately.

Keep diagnostics narrow. This switch is nonsensitive, but real events may contain secrets or customer data. Record relevant fields and safe type indicators rather than logging the entire context to explain one Boolean.

Does a correct switch replace production approval?

No. Correct typing establishes branch selection, not the caller's release authority, environment protection or artifact provenance. Selecting true still needs independent permissions. Selecting false cannot undo a side effect that already ran.

Renaming show_details to deploy does not create environment rules. Inspect the trigger identity, workflow permissions, target and release object. The site's environment, workflow and artifact checks address that separate boundary. This diagnostic example neither deploys nor claims approval.

Proposed validation compares typed branches for two manual inputs, then tests the event-string condition and records the declaration, workflow revision and skip status. Pass the value through one step output and inspect restoration at the consumer. Use diagnostics without side effects rather than a real production deployment to establish branching behavior. Preserve separate evidence for type, branch and authority.

Expression evaluation and shell evaluation are separate. A Boolean serialized into an environment variable becomes text; a shell test for nonempty text does not preserve the original Boolean decision. Choose an explicit evaluation boundary and treat subsequent text as a handoff format.

Adding a push trigger later also does not guarantee the manual input exists. Define eligible events and missing-input behavior without silently expanding authority. During migration, compare old and new conditions in diagnostics for true, false and absence. Agreement for true alone does not validate the remaining branches.
