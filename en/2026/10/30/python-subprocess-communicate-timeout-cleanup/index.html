Why is a Python child still running after communicate times out?

Compare Python run and Popen timeout cleanup with a direct-child example covering termination, pipes, return codes, output bounds, and descendant limits.

Article

Key takeaways

  • A communication timeout does not prove the direct child exited.
  • Complete pipe handling after termination and retain final status.
  • Descendants, output budgets, and external effects need separate contracts.

Popen.communicate raising TimeoutExpired does not establish that the child stopped. It does not automatically kill the child; the caller still owns termination and pipe completion. subprocess.run has a different contract: it kills and waits for the direct child before raising the timeout.

The same parameter name does not imply identical cleanup

The Python subprocess reference, checked on October 30, 2026 in Python 3.14.10 documentation, describes both behaviors. This article concerns a direct child with controlled small output. No process, signal, or cross-platform tests were run.

A conversion tool may keep using CPU or writing files after its parent stops waiting. Returning “conversion timed out” ends user waiting, not process ownership. Conversely, do not apply communicate's rule to run and claim that every TimeoutExpired leaves a child alive. Choose the simpler high-level interface when it covers the requirement; use Popen when its additional control is actually needed.

Complete the direct-child failure path

This complete teaching program has not been executed. Its child prints fixed text, sleeps, and creates no descendants, files, or network requests. The durations construct a case; they are not measured total latency.

import subprocess
import sys

def stop_and_collect(child):
    child.kill()
    return child.communicate()

child = subprocess.Popen(
    [sys.executable, "-u", "-c",
     "import time; print('started', flush=True); time.sleep(60)"],
    stdout=subprocess.PIPE,
    stderr=subprocess.PIPE,
    text=True,
)
timed_out = False
try:
    try:
        output, errors = child.communicate(timeout=1)
    except subprocess.TimeoutExpired:
        timed_out = True
        output, errors = stop_and_collect(child)
    print({"timed_out": timed_out, "returncode": child.returncode,
           "stdout": output, "stderr": errors})
finally:
    if child.poll() is None:
        stop_and_collect(child)

On timeout the code kills the retained direct child, then completes communication and obtains returncode. finally attempts cleanup if the normal path is interrupted with that child still running. It is neither a process-tree terminator nor a strict one-second total-time guarantee. Resources that cannot settle promptly need their own observable recovery policy.

Python documents that retrying communication after a timeout does not lose already read output. Use the later complete result rather than blindly concatenating exception fragments and duplicating data. The reference also warns against supplying input again to a post-timeout communicate call; this example has no interactive input at all.

The timed_out flag and returncode answer different questions. Successfully collecting output afterward does not turn a timed-out conversion into business success. Keep diagnostic text, partial output, and accepted artifacts distinct.

Why not just wait after the timeout?

The current reference directs callers to finish communicate rather than call wait after its timeout. Process termination and stdout/stderr handling are separate responsibilities. More generally, waiting without consuming a child's full pipes can create mutual waiting.

communicate buffers output in memory, so it is unsuitable for large or unlimited data. Such a tool needs an appropriate file or streaming consumer, cancellation, and storage/output budgets. A wrapper thread alone does not establish bounded memory. The example's small fixed text deliberately isolates the lifecycle question.

If output is unnecessary, choose its destination deliberately rather than always creating PIPE. Every pipe adds a communication object to consume and close. Discarding output, retaining a controlled log file, and streaming it provide different diagnostic and retention contracts.

Does killing the child stop all descendants?

This example cannot establish that. Popen describes the started process; descendants, inherited pipe endpoints, and platform-specific process groups require further design. A direct child's exit may leave inherited endpoints open and affect communication completion. No universal process-group command is supplied.

Termination also does not undo prior files or remote requests. Before retrying, inspect stable task and artifact identity and decide whether to resume, rebuild, or reject replay. Accepted file delivery belongs in a separate integrity and handoff step.

Even run's timeout does not guarantee interruptible process creation. The reference notes that some platform creation APIs cannot be interrupted, so the exception may only appear after creation completes. A total budget must consider startup, execution, termination, and output settlement separately.

Proposed checks retain process identity, timeout branching, final status, complete streams, and resource state. Cover normal exit, nonzero exit, controlled timeout, and output pressure; test any required descendant scenario independently. A “timed out” log is not an exit receipt.

Creating the Popen object does not guarantee the child has already printed its started marker. If testing timeout after entry into work, add controlled readiness coordination rather than assume that line always precedes expiry. Missing text alone also does not prove the process never started. Retain launch identity, readiness, and final exit to distinguish slow startup from execution timeout.

The site's asyncio cancellation-settlement article concerns a different cooperative contract. No example here has been executed. Identify when waiting ends, when the direct child exits, when pipes finish, and who accepts external artifacts before declaring timeout handling complete.
