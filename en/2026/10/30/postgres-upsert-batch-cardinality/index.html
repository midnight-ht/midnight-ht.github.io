Why do two valid upserts fail when combined into one PostgreSQL INSERT?

Explain PostgreSQL batch-upsert cardinality, then define duplicate input, version selection, rejection reports, and the transactional cost of splitting statements.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-30 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • One DO UPDATE statement cannot repeatedly affect the same target.
  • Batch reduction needs identity, version, and content-conflict policies.
  • Splitting statements can change atomicity and intermediate visibility.

Two inputs that each work as separate upserts need not work in one INSERT … ON CONFLICT DO UPDATE. PostgreSQL does not allow that statement to affect the same target row repeatedly. Duplicate conflict keys within the proposed batch can cause a cardinality violation. Define the batch's identity policy before retrying its write.

A statement has its own cardinality contract

The PostgreSQL 18 INSERT reference, checked on October 30, 2026, calls this form deterministic: one existing row cannot be affected more than once by the command. It explicitly says proposed rows should not duplicate one another on the arbiter key. No SQL or production import was executed here.

The target can correctly contain only one row for an identifier while two proposed inputs both try to update it. A unique constraint establishes the target identity, not a rule that the last input wins, the highest version wins, or amounts should be added. Unstated file-order rules can make a change of batching alter business results.

Distinguish identical replay, different versions for one identity, and conflicting content at the same version. Those may require ignoring, selecting, and rejecting respectively, but the project must approve that classification. The database exception does not supply it.

Two proposals for one existing order

This complete unexecuted input belongs in an isolated database. The target already contains version one of order 42; the following statement proposes versions two and three together.

CREATE TABLE example_order_state (
  order_id bigint PRIMARY KEY,
  version integer NOT NULL,
  state text NOT NULL
);
INSERT INTO example_order_state VALUES (42, 1, 'created');

BEGIN;
INSERT INTO example_order_state(order_id, version, state)
VALUES (42, 2, 'packed'), (42, 3, 'shipped')
ON CONFLICT(order_id) DO UPDATE
SET version = EXCLUDED.version, state = EXCLUDED.state;
-- Inspect failure, then end this test transaction:
ROLLBACK;

The documented expectation is a cardinality error, not an invented client log. Verify how the actual driver exposes it and how the transaction is recovered. A test driver must not continue with unrelated writes after failure and attribute their outputs to the original statement.

Suppose the business has approved choosing the highest version, that maximum is unique, and its state transition is valid. A preceding stage can produce one approved candidate:

INSERT INTO example_order_state(order_id, version, state)
VALUES (42, 3, 'shipped')
ON CONFLICT(order_id) DO UPDATE
SET version = EXCLUDED.version, state = EXCLUDED.state
RETURNING order_id, version, state;

This statement shows the write after selection, not an algorithm that automatically authorizes that selection. A separate version condition can reject stale events if required. The site's conditional upsert and empty RETURNING article concerns a single proposed row. Here the earlier question is how many modifications one command proposes for the same target.

Produce candidates whose meaning can be explained

Staging should retain source-row identity, business key, version, and relevant provenance. Group by the actual conflict identity, including tenant dimensions where necessary. If an expression unique index arbitrates conflicts, check that application grouping represents the same identity.

“Last input” needs an ordering contract: arrival order, file position, and business version are different. Highest-version selection still needs a tie policy. Do not take a maximum status string or combine unrelated columns merely to manufacture one candidate.

Approved identical duplicates can collapse into one candidate, while the import report records which original rows map to it. A reduced row count is not sufficient evidence of loss or correctness. Conversely, distinct events with coincidentally equal fields should not be merged through unexamined whole-row DISTINCT.

Is splitting the statement a repair?

Splitting may avoid the one-statement restriction while changing transaction behavior. Autocommitted statements expose intermediate versions and leave earlier writes after a later failure. Even within one transaction, sequential overwriting chooses an order that requires business approval. “No exception after splitting” does not validate that choice.

Do not project the DO UPDATE rule onto all DO NOTHING behavior either. Selecting another conflict action changes the interface contract. Verify what is ignored, what is returned, and whether conflicting content is concealed.

Proposed checks cover one candidate, identical duplicates, different versions, same-version conflicts, and batches mixing new with existing keys. Define creation, update, merge, and rejection expectations first. Reverse input order, split batches, and replay them to detect dependence on unapproved ordering.

A cardinality exception is not a per-row import report. Associate duplicate groups with original rows before mutation, then decide whether the batch is rejected or an explicitly approved subset proceeds. Partial processing introduces commit and retry responsibilities; do not resubmit arbitrary remaining rows after catching the exception. Duplicate checking also does not replace field and state-transition validation.

Retain database effects, business import decisions, and final commit evidence separately. No throughput or idempotency improvement is claimed. Give each written identity one explicit candidate before asking the database to apply that approved modification.
