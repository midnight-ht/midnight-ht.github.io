Why can a 320-pixel HTML image still fetch a larger source?

Separate image layout from sizes hints, calculate candidate densities for a 320-pixel slot, and retain browser-choice, caching, and asset-dimension checks.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-30 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • The sizes attribute informs selection without setting CSS width.
  • A width descriptor must match the candidate resource’s natural width.
  • Density calculations explain inputs without guaranteeing one selected filename.

Writing sizes="320px" does not make an image 320 CSS pixels wide. It supplies an expected size for resource selection; HTML and CSS sizing rules still determine layout. Mixing those responsibilities makes it easy to mistake a download hint for a limit on a full-width card.

Imagine an article cover that fills a narrow-screen card and joins a three-column layout on wider screens. The same picture is available at widths of 400, 800, and 1200 pixels. An author adds a fixed sizes value to reduce downloads but never checks the card’s actual width. The image does not become narrower, and the requested filename does not remain constant. Each observation belongs to a different part of the mechanism.

The HTML Living Standard’s image selection guidance relates width-descriptor candidates to a source size. A w descriptor states the candidate resource’s natural width and must match that resource. The sizes attribute supplies intended layout-size information. The browser can convert candidates into densities and apply its selection rules. This is neither a CSS layout declaration nor an instruction to download one particular file.

Separate the two responsibilities

This unexecuted example assumes that the three files really have the natural widths declared below. No browser or image-file inspection was performed.

<img
  src="cover-800.jpg"
  srcset="cover-400.jpg 400w,
          cover-800.jpg 800w,
          cover-1200.jpg 1200w"
  sizes="(max-width: 600px) calc(100vw - 32px), 320px"
  alt="A workshop whiteboard covered with suggestion notes">

The hint estimates a source size of viewport width minus 32 pixels at viewport widths up to 600 pixels, and 320 pixels otherwise. Separate CSS must actually produce the matching gutters, grid, and image-width contract. If a redesign makes the wide-screen card 440 pixels wide while the hint remains 320, HTML will not shrink the card back. The two descriptions have diverged.

For a source size of 320 pixels, the 400w, 800w, and 1200w candidates correspond to densities of approximately 1.25, 2.5, and 3.75. That calculation explains an input to selection. It does not guarantee that a device pixel ratio of two always requests the 800-pixel file. Browsers can consider caching, network conditions, and the user environment. A previously downloaded large image need not be replaced by a smaller download when a window shrinks.

Record the viewport, rendered image width, device pixel ratio, currentSrc, and request conditions together. A network-panel screenshot showing one filename cannot distinguish reasonable cache reuse from an inaccurate size estimate.

Keep the hint connected to real layout

CSS can remain responsible for the card width: for example, a narrow container with 16-pixel gutters on each side and a full-width image, followed by a genuinely 320-pixel wide card on larger screens. Only then does this sizes expression have a clear layout basis. Sidebars, maximum widths, and different padding can invalidate that estimate even when the viewport looks roughly similar.

Do not read 400w as “display this at 400 pixels.” If a file is naturally 360 pixels wide but is labeled 400w, the selection calculation already has incorrect input. Check the files and descriptors before investigating the selected resource. This example also assumes width variants of the same composition; choosing a different crop or a different picture is a separate design question.

A reviewable division of work is for design to specify the image slot, CSS to implement it while the size hint tracks it, and the asset pipeline to provide files matching their descriptors. Making sizes smaller in isolation can tell the browser to select for a smaller slot while the visible image remains large.

For a blurry result, compare the actual slot with the hint and then examine candidate quality. For an unexpectedly large transfer, check caching and the recorded environment before changing the resource set. This article measured neither quality, bytes, nor loading time and makes no percentage performance claim.

Keep a counterexample in the verification

List the expected narrow and wide source sizes, then compare those estimates with measurements from the page. Check every file’s natural width, declared descriptor, and the selected currentSrc. Temporarily widening the large-screen card without updating sizes provides a useful counterexample: layout changes, while the hint does not automatically follow it. That demonstrates why both need maintenance.

The presence of src is not evidence that it is the only file a browser will request. Observe the actual selected resource. Record different viewport sizes, pixel ratios, and cache conditions separately instead of promoting the first observed filename into a permanent contract.

Those checks were not executed here. The calculations apply to the stated 320-pixel source size. Other descriptor schemes, automatic source sizes, or particular loading conditions need their own requirements checked rather than inheriting this example’s assumptions.

Can a breakpoint guarantee one downloaded filename?

Return to the candidate inventory when assets change. Compression or replacement can preserve a URL while changing the resource’s natural width; an old 400w descriptor will not correct itself. Recheck actual dimensions and then the template’s candidate list so an asset-pipeline change is not misdiagnosed as unusual browser selection.

This combination of w descriptors and sizes does not provide that promise. It supplies selection information while leaving a role for browser decisions. If the requirement concerns cropping or a different mobile composition, state that visual requirement explicitly and choose an appropriate delivery method instead of substituting “must request this filename.”

For ordinary clarity requirements, a stronger acceptance statement is that each layout has the intended slot, the hint matches it, candidate information is correct, and clarity and requests were checked in recorded environments. After a layout change, that statement also explains what must be checked again and why the selected file may change.
