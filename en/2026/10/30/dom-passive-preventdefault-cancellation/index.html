Why can defaultPrevented remain false after preventDefault?

Trace cancelable and passive-listener conditions with an unexecuted EventTarget example, keeping callback execution, cancellation flags, and actual scrolling separate.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-30 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • Cancellation requires a cancelable event outside a passive listener.
  • Observe callback receipt, the canceled flag, and the default action separately.
  • A synthetic-event flag check does not replace real-input device verification.

The handler ran and called preventDefault, yet defaultPrevented stayed false. Check whether the event is cancelable and whether this listener is passive before interpreting the default action. A callback running, a canceled flag being set, and a page remaining still are three separate observations.

Imagine a horizontally browsable card region. Its wheel callback logs every invocation and calls the cancellation method, but the page continues moving down. Adding logs confirms execution. Replacing the call with stopPropagation changes propagation. Neither explains whether this listener was allowed to set the canceled flag.

The DOM Living Standard’s preventDefault algorithm requires both a true cancelable value and an unset in-passive-listener flag to set the canceled flag. Being cancelable is necessary, but it does not guarantee that a particular listener can cancel the event. A passive listener cannot establish cancellation through this call even when the event itself is cancelable.

Separate the conditions first

This is an unexecuted reasoning example. It compares DOM event flags; it does not simulate browser scrolling or establish behavior on a phone.

const observer = new EventTarget();
const controller = new EventTarget();
function inspect(event) {
  event.preventDefault();
  console.log(event.cancelable, event.defaultPrevented);
}
observer.addEventListener('probe', inspect, { passive: true });
controller.addEventListener('probe', inspect, { passive: false });
observer.dispatchEvent(new Event('probe', { cancelable: true }));
controller.dispatchEvent(new Event('probe', { cancelable: true }));

Under the standard’s conditions, the first fresh event is cancelable, but its passive listener cannot set the canceled flag. The second fresh event meets both conditions. Changing cancelable to false would prevent even the second listener from establishing cancellation.

Two targets and two new events keep one comparison from inheriting an already canceled state. During a real dispatch, another listener might have canceled the event before yours ran. A true defaultPrevented value therefore does not prove that the current listener caused it. Record the value on entry and after the call, together with the registration options.

Find the actual registration

For the card region, first connect the callback to the user action that failed. An outer container, an inner component, and the document may all have listeners. Seeing one observer run does not establish that the listener responsible for the interaction is attached correctly. Event type, target, current target, and component identity help connect a log to a particular action.

Then inspect the registration actually used. A function definition is insufficient: a wrapper may install it, and a remount may take another branch. Another instance using passive:false does not establish the options of this instance. Defaults for particular event types and targets must be checked in the relevant environment; an omitted option should not be treated as one universal promise.

An observation-only handler does not need to cancel the default behavior. A deliberately controlled interaction may need cancellation, in which case express that requirement on the relevant listener and still check cancelability. Changing every listener to non-passive turns a local decision into an application-wide policy. No performance benefit or cost was measured here.

Finally observe the default action. The cancelable property describes an event capability, defaultPrevented reports a flag, and the movement of a region is a user-visible outcome. A different scrolling container, an uncovered input direction, or another input type can leave that outcome different from the intended one. Record whether the operation used a mouse wheel, trackpad, or touch input and identify the container.

Propagation is another control

stopPropagation affects propagation; it does not bypass the conditions imposed on a passive listener. It may change which other handlers run and complicate the symptom without making this cancellation call effective. The earlier button default-submission discussion separates propagation from default actions; this question adds the listener’s passive state to that distinction.

Do not make a test pass by replacing real input with a constructed event and then reporting the two as equivalent. A listener installed again after remount may indicate a lifecycle problem. A different handler canceling first may indicate incorrect attribution. Preserve event identity and before-and-after state so those failures remain distinguishable.

A useful inspection sequence is to connect the event to the user action, find the actual registration, record cancelable, compare defaultPrevented before and after the call, and observe the relevant default action. Each step answers a narrower question and identifies what the next investigation needs.

Does a canceled dispatchEvent prove a phone will not scroll?

If a third-party wrapper owns registration, application code may not directly control the options. Inspect the wrapper’s supported interface, the current instance, and cleanup before choosing a local replacement or interaction change. Adding a second listener speculatively makes cancellation harder to attribute and can leave an old handler behind when the component exits.

It does not. The constructed event can exercise the handler’s canceled-flag logic, but it does not generate the user’s touch input or reproduce the browser’s associated default action. Even a canceled result needs a separate check of the target device, actual input route, scrolling region, listener options, and visible behavior.

The reverse inference also fails: a page might stay still because it has no scrollable space or because the input landed elsewhere. Acceptance needs flag evidence alongside an operation that actually has a default scrolling action available. This article provides a mechanism and unexecuted examples, not a completed browser or device test.
