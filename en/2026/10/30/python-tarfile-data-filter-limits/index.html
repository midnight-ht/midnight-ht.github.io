Keep tar extraction in staging until the artifact is accepted

Use a controlled tar fixture to explain Python 3.14 data filtering, partial extraction, errorlevel, duplicates, and the separate policy for untrusted uploads.

Article

Key takeaways

  • The data default is not a complete untrusted-archive policy.
  • Aborted extraction can leave files; normal return still needs member checks.
  • Resource budgets, duplicate-name rules, and artifact handoff remain separate.

Python 3.14's default tar data filter does not make an untrusted archive suitable for direct extraction into a published directory. The filter restricts selected features. The application still owns source and member inspection, resource limits, partial-output cleanup, and the final artifact handoff.

What changed with the default?

The tarfile extraction-filter reference, checked on October 30, 2026 in Python 3.14.10 documentation, describes filters introduced in 3.12 and the default change to data in 3.14. Patch releases can also change path handling, so retain the deployed patch version.

The data filter inherits tar-filter behavior, rejects links to absolute or outside destinations and special files, and adjusts selected metadata. This is not accurately summarized as one universal rule rejecting every leading slash: stripping and normalization have their own documented behavior. Test the actual acceptance set instead of replacing it with an invented prefix check.

The documentation explicitly warns that no available filter blocks all dangerous archive features. Even data does not make extraction from untrusted sources appropriate without prior inspection. A better default does not approve an upload, define expected members, or impose CPU and disk budgets.

Verify a small owned fixture first

This complete teaching program has not been run. Its archive contains fixed, program-owned bytes; it accepts no user upload and is not a general safe-extraction service. A fresh staging directory, explicit filter, and content comparison illustrate a normal path. Temporary cleanup means it does not produce a persistent download.

import io
import tarfile
from pathlib import Path
from tempfile import TemporaryDirectory

expected = {"note.txt": b"example\n"}
with TemporaryDirectory() as directory:
    root = Path(directory)
    archive = root / "sample.tar"
    stage = root / "stage"
    stage.mkdir()
    with tarfile.open(archive, "w") as output:
        for name, content in expected.items():
            member = tarfile.TarInfo(name)
            member.size = len(content)
            output.addfile(member, io.BytesIO(content))
    with tarfile.open(archive, "r") as source:
        source.errorlevel = 1
        source.extractall(stage, filter="data")
    observed = {p.name: p.read_bytes() for p in stage.iterdir() if p.is_file()}
    assert observed == expected
    print(sorted(observed))

The assertion checks ordinary-file content in this known fixture. It does not implement a complete directory/link allow-list, duplicate-name policy, extraction limit, or protection against concurrent changes to a hostile directory. An upload service needs those decisions before extraction; renaming this function safe_extract would not supply them.

An explicit argument makes the intended policy visible without relying on whether another component changed extraction_filter. Method arguments and default attributes also accept different forms according to the reference; the example passes a named string only to extractall.

Does a rejected later member roll back earlier files?

No automatic transactional rollback is provided. Aborted extraction can leave partial output, and tarfile does not clean it up. Refusal behavior also depends on errorlevel. An exception does not prove the directory is empty, and an existing directory does not prove the artifact passed validation.

Give staging an identity and lifecycle state. On failure, remove the owned staging scope or retain diagnostics under a controlled access and expiry policy. Only a verified complete artifact proceeds to the final location. A fresh directory reduces pre-existing-link risks but is not proof of complete operating-system isolation.

Receiving an archive, checking it, extracting, rejecting, validating, and handing it off are distinct user-visible states. A partially available download after failure can otherwise look like the accepted version. Obscure path names do not replace access rules.

Who selects the correct repeated filename?

The reference notes that tar archives can contain several versions of one file, with later members overwriting earlier ones. The data filter does not choose the business-approved version. If each expected path must occur once, inspect and reject duplicate members rather than count only the files left afterward.

Case-insensitive filesystems add possible name collisions. Define allowed characters, lengths, member counts, and types from the use case. A service needing one report has little reason to accept every tar feature, but the expected set still requires a product decision.

Resource limits are independent. Python says predefined filters do not prevent denial-of-service attacks and recommends external CPU, memory, and disk limits alongside member-count and size checks. Compressed upload size does not establish expansion cost; metadata size alone is not observed execution cost. No universal safe threshold is offered.

Proposed isolated checks include the owned normal fixture, refused links, special members, duplicates, unexpected members, and failure after partial extraction. Inspect retained output and blocked handoff. Resource enforcement and concurrent directory changes need separate controlled checks with patch version, platform, and configuration retained.

Check errorlevel explicitly. At zero, a filter refusal can be logged and the member skipped while extraction continues, so normal return does not establish that every member was accepted. The fixture makes refusal-aborting behavior explicit only to expose its expectation. A real policy permitting skipped members needs an accepted skip list rather than silently losing evidence from the final directory.

The site's upload isolation article covers the broader intake lifecycle. No archive or security tests were executed here. Explain filter behavior, resource policy, partial failure, and artifact acceptance separately to show what the data default actually protects.
