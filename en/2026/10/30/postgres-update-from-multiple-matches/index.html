Which source row does PostgreSQL UPDATE FROM choose when two match?

Separate target identity from source-match uniqueness in PostgreSQL UPDATE FROM, with price-update controls, missing-source behavior, and preflight limits.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-30 · Estimated read 11 min
Translations

Article

Key takeaways

  • A target primary key does not establish one source match.
  • Reject or explicitly resolve competing sources before updating.
  • Scalar assignments and FROM joins differ when no source matches.

If PostgreSQL UPDATE … FROM joins one target row to several source rows, only one joined row supplies the update, and its selection is not readily predictable. A primary key on the target does not remove that ambiguity. Before changing prices, establish one source match per target and separately establish that the selected price is approved.

Success does not mean “the latest price won”

The PostgreSQL 18 UPDATE reference, checked on October 30, 2026, explicitly requires at most one join output per target when using FROM. Multiple matches do not create an approved latest, lowest, or reviewed-price rule. No database queries were executed for this article.

Suppose a product priced at ten has two incoming proposals, twelve and fifteen. Its unique identifier proves there is one target product, not one proposal. Adding an apparent ordering is not a substitute for defining review time, version priority, ties, and rejection rules. If competing proposals are an input error, rejecting them preserves more information than silently choosing one.

Make a unique source part of the design

This complete unexecuted example belongs in an isolated database. The source represents an already approved single batch; creating its table does not perform approval. A multi-batch or multi-tenant system needs its actual identity dimensions in both structure and join.

CREATE TABLE example_products (
  product_id bigint PRIMARY KEY,
  unit_price numeric NOT NULL
);
CREATE TABLE example_approved_prices (
  product_id bigint PRIMARY KEY,
  unit_price numeric NOT NULL
);
INSERT INTO example_products VALUES (1, 10), (2, 20);
INSERT INTO example_approved_prices VALUES (1, 12);

BEGIN;
UPDATE example_products AS p
SET unit_price = s.unit_price
FROM example_approved_prices AS s
WHERE p.product_id = s.product_id
RETURNING p.product_id, p.unit_price;
SELECT product_id, unit_price FROM example_products ORDER BY product_id;
ROLLBACK;

The first product has one source; the second has none and is not changed by this join. ROLLBACK discards the illustrative update. RETURNING therefore must not be described as evidence of a committed price change. The source primary key prevents a second proposal for the same product, but does not validate approval age, amount policy, or operator permission.

For a negative control, restore the initial database, remove source uniqueness, and add two prices for the same product. Inspect the candidate SELECT join before mutation. A particular update choosing twelve would not establish a rule, even if repeated locally. The useful acceptance condition is detecting and rejecting ambiguous input.

A preflight query does not reserve the future

Count candidate rows by the actual target identity and retain conflicting source identifiers. Use the same join keys and filters as the mutation. Grouping an import by product while later joining across tenant boundaries does not establish uniqueness of the real join. Equal total table sizes are also irrelevant to individual matching.

Another session can change the source after a preflight SELECT. Preserve an approved batch as immutable during the handoff, or use constraints and a transaction design that maintain the needed relationship. This is not a universal locking recipe; a prior observation alone is not a continuing concurrency guarantee.

If several versions are legitimate, reduce them in staging under an explicit selection rule and constrain the resulting source. Do not combine a maximum amount with an approver from another row or use DISTINCT to hide conflicting proposals. The site's representative-row article explains selection priorities; this article makes that choice a prerequisite for a write.

Is a scalar subquery equivalent?

No. PostgreSQL requires an assignment subquery to yield no more than one row. When it yields none, the assigned columns receive NULL. A FROM join with no match instead does not update that target. A nullable price could be cleared by the substitution; the example's NOT NULL column can make such an assignment fail.

Define zero-, one-, and multiple-source outcomes before choosing the form. “No proposal means keep the old value” needs a condition and a preservation check. “No proposal is an error” needs an explicit missing-input result. Rejecting multiple rows supplies only one part of that contract.

Proposed validation covers zero, one, and two candidates per target, cross-tenant identifiers, approval ties, changing source batches, and a target modified before the update. Inspect join input, actual mutation, and final commit separately. An expected-old-version condition may also be needed to prevent overwriting an obsolete target; unique source matching does not provide it.

Keep missing-source and multiple-source checks distinct. An inner candidate join can identify multiple matches; finding missing proposals starts from the target set. If a LEFT JOIN preserves unmatched targets, its placeholder row must not be counted as a real source through count(*). Count a defined non-null source identity, and retain target and proposal identifiers so the batch can actually be corrected.

No SQL execution, performance improvement, or production incident is claimed. First explain why each target has one source, then verify the choice, missing-source behavior, and committed result. A target primary key answers only the target's identity question.
