How can a single-pointer user select a store on a pinch-only map?

Provide a single-pointer route through zoom and store selection while distinguishing path gestures, dragging, and keyboard checks.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-27 · Estimated read 10 min
Translations
zh-CN en

Article

Key takeaways

  • Preserve the function through a single-pointer route.
  • Keyboard support alone does not establish this requirement.
  • Assess dragging separately from prescribed-path gestures.

A store map shows twelve markers, and two neighboring stores must be separated by zooming before either can be selected. If pinch zoom is the only route, provide a single-pointer alternative without a path gesture, such as clickable zoom controls. A desktop keyboard shortcut does not by itself serve someone operating with one contact point.

Replace the function rather than the animation

WCAG 2.2 Understanding Pointer Gestures requires functionality using multipoint or path-based gestures to work with a single pointer without a path-based gesture, unless essential. This concerns pointer actions interpreted by web content, rather than actions needed to operate the browser or assistive technology itself. Keyboard operability is a separate requirement.

List the functions: pinch changes scale, rotation changes orientation, and a directional flick may change pages. A Reset map button restores one view but may not replace the ability to select a useful scale. Individual zoom activations or a scale selector can provide the needed result without reproducing every frame of a gesture. Two extreme preset levels may be insufficient if neighboring stores become distinguishable only at an intermediate scale.

Follow the selection through to the correct store

Consider an unexecuted pickup-reservation example. Twelve markers are illustrative data, not a usage measurement. The reader seeks a store at the shopping street's east entrance. They activate zoom, separate the markers, select one, inspect its name, address, and opening hours, and confirm. The alternative must reach the same store details, not merely increment a scale label.

Choose a comprehensible zoom center. Recentring on the user's location after every activation could repeatedly push the shopping street out of view. A current-view-center policy is one option; its feedback should match its behavior. Edge-of-screen targets also require usable navigation. A store list can help, but compare its actual capabilities: names without addresses are not a universal replacement for spatial information.

Assess rotation separately. Zoom buttons do not cover a two-finger orientation function. Discrete rotation, an orientation selector, or north restoration may be appropriate, depending on the result and precision required. Record which outcomes remain reachable instead of claiming that one added control replaces every gesture.

Where can apparently useful buttons fail?

Controls visible only on mouse hover may be undiscoverable on touch. A zoom control that works only while held, with no ordinary tap action, can preserve the original difficulty. Define each activation and behavior at the scale boundaries.

Loading can also change the target. An older wide-view response might arrive after a newer zoom response and replace the markers. The apparent selected store can then change. Request or view identifiers can help reject stale responses; that is an engineering proposal for this example, not a network format prescribed by WCAG. Record the store finally confirmed rather than evaluating only a smooth animation.

Include maximum and minimum scale, offline state, no results, and dense markers. Explain a reached limit while preserving the route back into range. Distinguish unavailable data from a genuine absence of stores. No map or API test was performed here, and no completion-rate improvement is claimed.

Is single-finger panning already sufficient?

Counting fingers is insufficient. A single-pointer alternative must also avoid a path-based gesture. Ask whether recognition depends on a prescribed trajectory, direction, or speed pattern. A drag concerned primarily with endpoints is not automatically path-based merely because movement occurs. Dragging has a separate WCAG 2.2 requirement, SC2.5.7, so that distinction does not end the review.

The site's non-dragging card-ordering article discusses choosing an object and destination. A map need not copy that menu, but it still needs assessment of tasks otherwise requiring sustained contact. Gesture, dragging, and keyboard checks cover different difficulties and should retain separate evidence.

Essentiality must concern the actual function. Producing a particular freehand stroke differs from finding a store. Calling an application a map does not automatically exempt zoom, selection, and orientation. Explain why a conforming alternative would fundamentally change the particular function, rather than using limited space as a blanket exception.

A proposed acceptance route prohibits multipoint and path gestures while completing zoom, location, review, confirmation, and cancellation. Repeat keyboard checks separately. Save view bounds, activations, response versions, confirmed store identity, and recovery outcomes. Establish that the correct store is reachable; a working plus button proves only one step.
