Why pytest.warns Can Match and Still Report Other Warnings

Explain unmatched-warning re-emission since pytest 8.0, distinguishing existence assertions, exact warning sets, and outer policy through category and message cases.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-27 · Estimated read 13 min

Article

Key takeaways

  • pytest.warns requires at least one warning matching its category and message conditions.
  • Since pytest 8.0, unmatched warnings are re-emitted when the context closes.
  • A same-category wrong message can both fail the assertion and be re-emitted.

Suppose an import emits an expected DeprecationWarning and an unexpected RuntimeWarning. pytest.warns(DeprecationWarning) can satisfy its assertion while the report still contains the second warning. Since pytest 8.0, unmatched warnings are re-emitted when the context closes. “The expected warning occurred” and “no other warnings occurred” are different requirements.

What is recorded, and what is consumed?

The pytest warns API requires at least one warning of an expected category, optionally constrained by a message match. Its returned record includes warnings emitted during the block, not only the matching warning. Being present in that record does not make every entry expected or silently consumed.

The official pytest 9.0.2 recwarn implementation documents re-emission of unmatched warnings since 8.0. It matches category subclasses and, when match is supplied, performs a regular-expression search on the message. A different category or a matching category with a nonmatching message can therefore reach the outer warning policy. Check the installed version before interpreting an upgrade's changed output as newly introduced application behavior.

The outer policy determines what happens next: collection in a summary, filtering, or conversion to an error. A successful matching portion does not guarantee a successful test overall. An extra warning treated as an error can still fail it. Distinguish absence of the expected warning from an additional warning triggering project policy.

A complete compatibility-layer example

Imagine a legacy configuration reader that must retain a deprecation notice while a numerical problem also produces a runtime warning. This teaching substitute does not invoke a real product parser and was not run. It makes the warning set explicit.

import warnings
import pytest

def read_legacy_config():
    warnings.warn("legacy option", DeprecationWarning)
    warnings.warn("invalid numeric input", RuntimeWarning)


def test_legacy_notice():
    with pytest.warns(DeprecationWarning, match="^legacy option$") as caught:
        read_legacy_config()
    assert any(w.category is DeprecationWarning for w in caught)

One warning satisfies both expected category and message. The RuntimeWarning does not, so it is re-emitted on exit. Whether it appears in a summary or fails the test depends on outer rules. Finding both entries in caught is consistent with that behavior: recording precedes the decision about which entries belong to the outer policy.

If the contract is “exactly this one deprecation notice,” state the whole set. One approach is a controlled warnings recording scope with suitable filters, followed by checks of category, message, and count. Validate the arrangement with the project's warning plugin and configuration; another capture wrapper is not automatically strict. Keep a real product-entry test as well, because the teaching substitute cannot establish the parser's actual failure path.

The appropriate change might instead be fixing the numerical problem. If the extra warning is legitimate, define its own conditions and expectations. If it is forbidden, keep it visible as a failure. Quieter output alone says nothing about correct parsing.

Why not broaden the expected category to Warning?

It enlarges the accepted set. A RuntimeWarning can then meet a requirement originally intended for a deprecation notice, allowing the compatibility notice itself to disappear unnoticed. Removing the message condition broadens it further. That changes the test contract instead of explaining the warning.

Globally ignoring all warnings is another counterexample. It may hide the re-emitted warning without explaining its origin or correctness. Filters can be appropriate for a confirmed third-party issue, but should identify the relevant category, message, and source, with a removal condition. One newly failing upgrade test is not a reason to suppress future warnings across the project.

Under warnings-as-errors policy, verify in an isolated case that the expected warning is handled and an extra warning can still fail the test. Read effective configuration, command-line flags, and local marks before changing several layers at once. Deliberately injecting a forbidden extra warning checks that the gate still exists.

Is a same-category warning with the wrong message re-emitted?

It is unmatched, and if no other warning matches, the warns assertion also fails. Suppose the expectation is DeprecationWarning with ^legacy option$, but only legacy format is emitted. The category fits while the regex does not. It cannot satisfy the notice contract, and exit handling re-emits that unmatched warning. Seeing assertion failure alongside warning output does not establish that the application ran twice.

A separate branch emits the correct message and then a wrong message of the same category. The existence assertion can succeed while the second entry remains unmatched. Test this separately from the case with no matching message at all. Counting categories alone misses the additional boundary introduced by message matching.

Matching uses regex search rather than full equality. Choose metacharacters and anchors deliberately. The site's discussion of exception-message matching examines accepted strings; for warns, that accepted set also controls re-emission. If only a stable notice code is promised, define the allowed variable part. Do not add wildcards merely to remove a failure.

Preserve warning provenance. Recorded filenames and line numbers help distinguish the target function, import side effects, and test setup. A broad warns block can accept a notice from unrelated preparation while the actual entry emits none. Narrow the operation under assertion and compare an input that should not warn, checking that the fixture did not create the expected notice itself. Warning-set checks need real input coverage; a substitute printing two messages does not validate compatibility behavior.

Proposed checks cover only the correct warning, correct plus another category, only a same-category wrong message, correct plus same-category wrong message, and no warning. Preserve the pytest version and effective filters, then inspect assertion and reporting outcomes separately. None of these tests were executed here. Their eventual evidence should show whether the product requires at least one matching notice or exactly one permitted notice.
