Why can a two-position prefixItems schema accept one item?

Separate existing-position types, minimum length, and tail policy, including same-object scope under allOf.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-27 · Estimated read 11 min
Translations
zh-CN en

Article

Key takeaways

  • Prefix constraints do not require missing positions.
  • A fixed pair needs both a lower bound and a tail policy.
  • Items uses its sibling prefix; composition needs scope checks.

A coordinate schema lists two numeric schemas in prefixItems, yet an array containing one number is accepted. Prefix constraints apply to positions that exist; they do not require those positions to exist. A fixed pair needs a minimum length and a tail policy as well as positional types.

Position does not establish length

Draft 2020-12 Core's array rules apply prefixItems schemas to existing corresponding elements without constraining array length. Missing positions supply nothing to validate; additional positions lie beyond the prefix. Two numeric schemas alone therefore do not reject empty arrays, one-element arrays, or an unconstrained third label.

Declare type:array too when the interface requires an array. The keyword does not convert other JSON values. Length constraints such as minItems and maxItems belong to Validation section6.4. Instance type, position type, and length are separate responsibilities.

This unexecuted example defines two numeric positions, not complete geographic validation:

{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "array",
  "prefixItems": [{"type":"number"},{"type":"number"}],
  "minItems": 2,
  "items": false
}

In the same schema object, items handles positions beyond prefixItems; false rejects those extras. minItems supplies the lower bound. Together these form the fixed pair. A maximum length can also be an explicit contract choice, but items:false does not require the prefix positions to appear.

Use cases that reveal both edges

A paper matrix includes an empty array, one number, two numbers, a string in a prefix position, and three elements. Prefix rules alone do not fail the first two for missing positions. They check the existing first two types and leave the tail alone. The complete fixed schema adds lower-bound and tail failures. Run and preserve these outcomes in the selected validator; no validator was executed here.

Geographic ranges remain separate. Two numbers need not identify a valid place, and swapped longitude and latitude can sometimes fall within both permitted ranges. State order and units and choose values that distinguish the positions. Length success is not complete business validation.

Preprocessing can hide errors. If a receiver slices every input to two elements before schema evaluation, it can silently discard a third label. That does not prove the original input was rejected. Validate the original instance when rejection is required, or explicitly document preprocessing as part of the protocol.

Choose a fixed tuple or an extensible prefix

A fixed coordinate protocol can reject a misplaced label or altitude early. A deliberately extensible sequence needs a tail schema instead of mechanically using false. Define how consumers handle extensions; ignoring them is not the same as understanding them.

Named object fields may be easier to evolve when optional meanings keep accumulating, but that is a contract decision rather than a universal prohibition on tuples. Compact, stable positions can remain useful when required positions, tail behavior, and version changes are explicit.

The site's allOf object-closure article shows that composition does not merge local rules. This article applies a related scope distinction to array elements. Do not import older drafts' array-valued items syntax into 2020-12 and assume identical semantics. Fix the dialect and implementation when migrating.

Can outer items:false use an inner allOf prefix?

Do not assume it can. items determines its tail from prefixItems in the same schema object. If the prefix is inside allOf while outer items is false, the outer rule lacks that sibling prefix and can reject every element, including a legitimate pair. Inspect a minimal composition and the error location rather than searching for two schemas anywhere in the file.

A supporting 2020-12 implementation can use unevaluatedItems after successful evaluation to handle remaining positions, but it cannot reverse an already failed inner rule. Keeping positional schemas and tail closure together is often easier when composition is unnecessary. Choose reuse for an actual need, not merely to split a simple pair across several layers.

Distinguish an absent position from an explicit null. The one-element array [120] needs a minimum-length failure; [120,null] has sufficient length but fails the second numeric position. Allowing null changes that position’s accepted types without manufacturing a missing element or supplying a default latitude. Validation and data completion are separate operations.

Preserve the distinction in errors: missing coordinate, invalid second value, and unexpected tail need different corrections. After validation, check the mapping into the runtime tuple and its units. A tuple type in source code does not establish that the original network array passed runtime validation.

Preserve original instances, dialect, validator version, complete schema, results, and error positions. Cover short, long, mistyped, reordered, and composed cases. One- and three-element negatives reveal different defects; the valid pair guards against erroneous rejection. Those observations, once executed, can support a fixed-tuple acceptance result. The examples here remain specification-based reasoning.
