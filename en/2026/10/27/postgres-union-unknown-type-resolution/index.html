Why a Later Integer Cannot Rescue Two Earlier NULLs in UNION

Trace pairwise UNION resolution and distinguish typed placeholders, duplicate handling, and an outer cast.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile

Article

Key takeaways

  • An all-unknown pair can resolve to text before the integer arrives.
  • Empty branches need the declared report-column type.
  • ALL and an outer cast do not replace a typed branch.

Suppose a report generator produces SELECT NULL UNION SELECT NULL UNION SELECT 1. PostgreSQL can resolve the first two branches before considering the integer. Multiple UNION operations are treated as nested pairs, and a pair containing only unknown inputs resolves to text. The later integer does not restart the earlier inference.

Resolution happens at an intermediate boundary

The PostgreSQL 18 type-resolution reference applies resolution separately to each output column. It documents both the all-unknown-to-text rule and the failing two-NULL-then-integer example. An untyped NULL here is not already an integer null simply because an integer appears later.

Parentheses expose the relevant boundary. This teaching query was not executed; the explanation follows the documented algorithm.

(SELECT NULL AS amount UNION SELECT NULL)
UNION SELECT 1;

The inner operation resolves amount to text. The outer operation receives a text column and an integer column, not three still-undecided expressions. Their mismatch can fail before any report rows are produced. Preserve the actual SQL and original error rather than reporting the failure as “no sales found.”

Imagine a generator combining monthly amount branches. January and February are placeholders, while March supplies an integer. The failure concerns missing type information in those placeholders, not the value being too large or the earlier months having zero rows. Individually executable branches do not prove their combination satisfies every intermediate resolution step.

Declare the empty branch's output type

When the contract requires integer, the earliest placeholder can carry it explicitly. A generator is easier to maintain when every branch follows the same column contract rather than relying on one populated month happening to appear first.

SELECT NULL::integer AS amount
UNION SELECT NULL::integer
UNION SELECT 1;

These NULLs are integer nulls from the start. The example remains unexecuted. It does not recommend integer for every monetary amount: units, fractional precision, and range must be chosen separately. A numeric output contract should be applied consistently to placeholders and populated branches.

Moving a populated branch to the left can sometimes change resolution, but it makes correctness depend on generation order. A later refactor can put two empty branches first again. Explicit types also keep the all-empty report's metadata stable for drivers, exporters, and views.

Output names deserve the same attention. If the leftmost branch changes from a populated month to a placeholder and loses the intended alias, an exporter may read the wrong field despite a valid type. Maintain a declaration of names, units, and types and project every source against it.

Can UNION ALL or an outer CAST fix this type mismatch?

No. UNION ALL changes duplicate handling without removing type compatibility requirements, and an outer CAST cannot repair an inner query that fails to resolve. Choose ALL when the row contract requires duplicates, and verify types separately. A row-count change is not evidence that the original type problem was fixed.

An outer CAST cannot rescue an inner query that fails to resolve. The outer expression needs a valid inner result before it can convert it. Place the type declaration at the branch where resolution needs it rather than after a result that cannot yet exist. This is why “cast everything at the end” is not a sufficient repair.

Casting all amounts to text may make some branches compatible, but changes the report's interface. Character sorting is not numeric sorting, and downstream arithmetic would need parsing again. Select the meaning first; absence of an error is not the sole criterion for a type.

A new source returning currency symbols inside text should have a deliberate parsing and invalid-input policy at its boundary. Broadening every branch to strings merely postpones the failure and makes bad source rows harder to explain. A type contract should expose incompatible data rather than force every downstream consumer to guess.

Verify columns and empty cases independently

Because resolution is per column, declaring amount as integer does not settle an unknown source-name column. In an isolated database, inspect the first pair with pg_typeof(), then add the third branch. Compare no declaration, a typed leftmost NULL, typed placeholders throughout, and an outer-only conversion. Write expected column types and acceptance or rejection before running them.

Cover all-empty inputs, populated leftmost and rightmost branches, an incorrectly textual amount, and a value beyond the intended range. The range case tests whether the contract itself is too narrow. Do not hide it by converting everything to text. Bound parameters also need real-driver checks because their inference can differ from literal SQL. None of these checks were executed.

The related UNION duplicate-semantics article explains missing rows after combination. This article explains failure before a result exists. Preserve nesting, per-column types, and the earliest fixed type before adjusting duplicate handling or report presentation.
