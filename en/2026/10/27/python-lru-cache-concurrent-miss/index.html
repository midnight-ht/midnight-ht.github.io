Why Thread-Safe lru_cache Can Compute the Same Miss Twice

Separate coherent cache storage, per-key in-flight coordination, and persistent idempotency; inspect where a lock actually applies.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-27 · Estimated read 11 min
Translations
zh-CN en

Article

Key takeaways

  • Cache coherence does not guarantee one execution per concurrent miss.
  • An internal lock does not automatically repeat the wrapper lookup.
  • Cross-process side effects need more than a memory cache.

Suppose two threads request the price of product 42 while its cache entry is absent and the first remote read is still running. The cache can remain structurally coherent while both underlying calls overlap. Python's lru_cache thread-safety guarantee is not a per-key promise to execute concurrent misses only once.

Two callers can pass the same missing entry

The functools reference, retrieved as Python 3.15.2, explicitly allows repeated underlying calls before the first result finishes and is cached. This discussion concerns ordinary thread calls, not coroutine-object caching or another cache implementation.

Thread A looks up 42, misses, enters the function, and waits for a remote dependency. Thread B looks up 42 before A returns and can enter too. Both eventually return while the cache's own structures remain valid. Structural integrity and the number of business-function invocations are different acceptance conditions.

This unexecuted sketch identifies the boundary. fetch_price is an unspecified dependency, not a validated price service.

from functools import lru_cache

@lru_cache(maxsize=128)
def price(product_id):
    return fetch_price(product_id)

Repeated pure computation may cost only resources. A metered remote call has an additional billing consequence. A debit operation introduces a much more serious side-effect requirement. Decide whether duplication is acceptable from the function's actual contract rather than the decorator's thread-safe label.

Verify the key first. The reference requires hashable arguments and notes that distinct argument patterns, including keyword ordering, may produce separate entries. An application log showing the same product identifier does not establish identical function call shapes. Separate distinct-key misses from same-key overlapping misses.

Accept repetition, serialize, or merge in-flight work

When repetition is harmless and affordable, lru_cache may be sufficient for avoiding later completed-result work. Document that it does not eliminate every overlap and budget for bursts at cold start or invalidation. A high average hit rate does not settle the hottest missing-entry window.

If same-key callers must share one ongoing computation, maintain additional in-flight state. A leader creates the work record; followers wait for its result; completed results enter the cache. This singleflight design needs policies for shared failure, follower cancellation, producer cancellation, record removal, and a new leader after invalidation. This article does not provide a complete implementation.

A global lock outside the cache wrapper can be simpler. A later caller enters after the first finishes and may then hit the populated cache, but unrelated keys also wait. Choose that serialization only if its blocking cost fits the workload. Per-key coordination narrows contention while adding lock-record and exception-cleanup responsibilities.

Does a lock inside the cached function cause a fresh lookup?

Not automatically. Both A and B may already have passed the wrapper's miss check before reaching that internal lock. When B eventually acquires it, B is inside the original function, not back at the outer cache lookup. It can perform the second fetch sequentially. Serialization has replaced concurrent duplication without necessarily removing duplication.

The coordination protocol must hand the leader's result to followers, or place the cache check inside the appropriate locking boundary. Review recursion and exceptions so a caller does not wait on its own unfinished result. Creating a lock is not evidence of per-key call-once behavior.

Multiple processes add another boundary. Each process's memory cache and in-flight registry are separate, and a restart can discard them. Irreversible side effects need durable business identity and retry rules at the relevant service boundary. A computation cache is not a persistent debit-deduplication mechanism.

Use controlled overlap instead of lucky timing

A proposed test uses two worker threads and a controlled gate. Hold the first underlying invocation, then let a second same-key call reach that entry and record the invocation count. Release only after the intended overlap is established. Give the test an independent timeout and cleanup; an incorrectly designed barrier can otherwise hang indefinitely.

Then verify sequential repeated reads hit a completed result. Test different keys to discover accidental global blocking. Fail the leader and inspect what followers receive and whether a later call can start again. Mutable returned objects require a separate sharing review: memoization does not make results immutable. No thread tests, paid calls, or benchmarks were run here.

The TaskGroup article discusses cancellation among coroutine-group members. This question concerns same-key work among threads. Both require explicit waiting relationships, but the mechanisms are not interchangeable. State what may repeat, under which key and process scope, then measure the actual underlying invocations.
