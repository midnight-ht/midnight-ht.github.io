Temporary Tables Survive Commit: What the Next Pool Borrower Sees

Check backend identity, pool resets, and ON COMMIT policies for retained rows, table structure, and name shadowing.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-27 · Estimated read 11 min
Translations
zh-CN en

Article

Key takeaways

  • Request completion does not establish backend-session termination.
  • PRESERVE, DELETE ROWS, and DROP retain different state.
  • ON COMMIT DROP needs a transaction window containing table use.

Suppose batch A creates a temporary stage_ids table on a pooled connection, commits, and returns the connection. Batch B receives the same database session and creates the same name. TEMP does not mean “until this request ends.” PostgreSQL normally preserves the temporary table and its rows until session end unless an ON COMMIT policy changes that lifetime.

Requests, transactions, and backend sessions

The PostgreSQL 18 CREATE TABLE reference defines session-end removal and optional transaction-end behavior. The relevant session is the actual database backend session. Returning an application connection wrapper to a pool does not establish that the backend ended.

Two different sessions have separate temporary tables even when the names match. A pool may also reset a session effectively on return. Transaction pooling can assign different backends to adjacent transactions. Check the actual pool, reset commands, and mode. “Pooling causes leakage” is too broad: backend reuse, retained state, and subsequent access must coincide.

Imagine one physical backend. A leaves order 101 in its table after committing. B's unconditional CREATE can fail because the relation exists. Switching to IF NOT EXISTS and appending order 202 can then make B process A's old row. Suppressing the creation failure is not successful isolation. This scenario was not executed.

What survives each commit policy?

The ON COMMIT section distinguishes PRESERVE ROWS, the default; DELETE ROWS, which removes rows while retaining the table; and DROP, which removes the table at the current transaction's commit. Choose separately whether data and structure should survive.

For staging used only within one transaction, the intended boundary can be explicit. This unexecuted example demonstrates lifetime only, not a complete import.

BEGIN;
CREATE TEMP TABLE stage_ids (id integer) ON COMMIT DROP;
INSERT INTO stage_ids VALUES (101), (102);
SELECT id FROM stage_ids ORDER BY id;
COMMIT;
-- A subsequent same-session lookup should no longer find stage_ids.

The SELECT occurs inside the useful window. If an operation genuinely needs staging across two transactions, DROP is unsuitable. Review session ownership and exceptional cleanup instead of replacing every temporary table mechanically.

DELETE ROWS retains a structure that the next borrower must understand. IF NOT EXISTS does not verify that an existing table has the newly requested columns. During an application upgrade, an older session's shape may differ from the new code's expectation. Session initialization versions or explicit shape checks may be necessary; absence of a creation error is not a migration receipt.

Why can ON COMMIT DROP disappear immediately under autocommit?

With a separate implicit transaction per statement, CREATE commits before the following INSERT starts. DROP then removes the table as soon as creation's transaction completes. Use an explicit BEGIN, as above, to contain creation, use, and commit in one window. This is a transaction-boundary issue rather than an argument for abandoning cleanup.

Rollback needs separate expectations. A temporary table created within a rolled-back transaction has its creation rolled back. A preexisting session table is different: one failed transaction does not establish that its structure disappeared. A finally block issuing ROLLBACK is not a general certificate that session state is clean.

Names and borrower identity still matter

The reference places the temporary schema early in the default search path. A temporary stage_ids can hide a permanent public.stage_ids from an unqualified query. Qualify the permanent relation when that is the intended target. Clearing rows does not remove name shadowing.

Test with disjoint business identities as well as different batch numbers. A's allowed identifiers and B's should not overlap. Asserting only the final row count can miss substitution of an A row for a missing B row. Session-local storage is not itself user authorization; the final join or update must preserve the intended business scope.

A cleanup failure also needs a connection-management decision. If commit succeeds but cleanup fails, the uncertain session should not automatically be lent out as clean. Isolation or disposal may be appropriate depending on the pool. That is a design to verify against the implementation, not a feature claimed for every pool.

Proposed checks record pg_backend_pid(), run A and B sequentially on the same backend, inspect rows and object existence, and repeat on a second session. Then test the actual reset and transaction-pooling configurations. A driver wrapper identity cannot substitute for backend identity. These tests were not run.

For complex staging queries, assess manual ANALYZE after loading: the reference notes that autovacuum cannot access temporary tables. No performance improvement is claimed. The related advisory-lock and pool article concerns another session resource, but lock acquisition counts and temporary-table data, structure, and search-path behavior require different checks.
