Why must HTTP handling hand off after a 101 response?

Inspect HTTP/1.1 protocol selection, header boundaries, and buffered-byte ownership, with separate proxy-leg evidence.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-27 · Estimated read 10 min
Translations
zh-CN en

Article

Key takeaways

  • Process subsequent bytes using the selected protocol.
  • Preserve buffered bytes across the handoff.
  • Backend 101 does not establish the frontend transition.

An HTTP/1.1 client requests an upgrade, receives 101, and sends the next bytes to its JSON-response parser. The defect is at the protocol handoff. After the 101 header section ends, subsequent data belongs to the selected protocol rather than an ordinary HTTP response body.

What did 101 agree to?

RFC 9110's Upgrade definition describes an application-protocol change on an existing HTTP/1.1 connection. The server's 101 must identify its selection in Upgrade and must not select a protocol the client did not offer. A sender of Upgrade also lists upgrade in Connection. This changes neither the underlying transport nor the connection itself.

RFC 9112 section6.3 terminates a 1xx response at the first empty line after its fields, with no HTTP message body or trailers. New-protocol bytes following 101 are therefore not an ordinary body to read until closure. This article concerns HTTP/1.1 Upgrade, not HTTP/2 handshakes.

Verify the selected protocol against the request. A status line alone does not justify dispatching arbitrary bytes to an arbitrary decoder. The selected protocol can impose additional handshake checks; generic 101 semantics do not establish complete WebSocket security or readiness.

Who owns the bytes after the boundary?

Consider an unexecuted receiver design. A bodyless GET offers an upgrade. The server sends 101 and the required fields, followed by new-protocol traffic. The HTTP parser reads through the terminating empty line, validates negotiation, then transfers any buffered remainder to the selected parser.

One network read can contain both the complete header section and the new protocol's initial bytes. Signalling an upgrade while discarding that remainder can leave the new decoder waiting for an opening it will never receive. Leaving both parsers reading can make them compete. Specify buffer ownership, the unconsumed offset, subsequent read routing, and responsibility for closing after errors. These are proposed engineering checks, not a diagnosis of a particular library.

Sending has its own boundary. The client cannot begin using the upgraded protocol before completely sending its request message. The bodyless example avoids that complication; requests with content or a continue expectation require the specification's ordering rules. Do not reduce the bidirectional state machine to one received-101 flag.

Why not reuse the 100-response loop?

A loop that discards every 1xx and waits for 200 confuses continuation with protocol switching. The site's 100-continue article concerns permission to continue the current request and reach its final result. After a valid 101 handoff, ordinary HTTP processing must give way to the new protocol.

The reverse mistake is marking the business connection fully usable immediately. New-protocol authentication, application messages, or closure can still fail. A subscription being established or the first message being accepted needs its own evidence. The status code cannot report that work complete.

Proposed tests split headers and new data across reads, combine them in one read, fragment the boundary, and provide an unacceptable protocol selection. Record which parser consumes each portion and how errors terminate. No client, packet capture, or fixture was executed here. A server access-log entry cannot establish that the receiver preserved the initial bytes.

Does backend 101 establish a frontend proxy handoff?

No. Upgrade is connection-related negotiation. Inspect client-to-proxy and proxy-to-origin legs independently. A backend agreement does not establish that the frontend stopped ordinary HTTP handling and began the corresponding transfer.

Check the actual proxy product and version, both negotiations, byte boundaries, and closure reasons. Forwarding, buffering, and timeout behavior need implementation evidence. If the proxy terminates and reinitiates the new protocol, its two identities and lifecycles need explicit treatment. No proxy configuration was verified here.

What if the server sends 200 instead?

The server may ignore the upgrade invitation and continue HTTP. Handle that ordinary response, or report that the application's upgrade requirement was not met. Do not decode its HTML or JSON as new-protocol frames. Whether fallback is useful is a product decision; the invitation does not compel acceptance.

Distinguish refusal, invalid selection, post-handoff decoding failure, and application-message failure. They point toward different repairs: support and routing, negotiation, framing, or business rules. Preserve the phase in the error record instead of collapsing them into connection failure.

A reviewable result identifies the offer, selected protocol, header boundary, buffered remainder, and first valid new-protocol interaction. Without those, only the status code is established. For the initial JSON error, first ask whether those bytes belonged to HTTP at all.
