Why can an invalid email pass a format:email schema?

Inspect 2020-12 annotations, optional format checks, and required vocabulary support without confusing syntax with ownership.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-27 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • A format annotation does not automatically reject input.
  • Fix the dialect, validator version, and format configuration.
  • Syntax validation establishes neither existence nor ownership.

A registration schema declares a string with format:email, yet not-an-email passes. With JSON Schema Draft 2020-12, first establish whether the validator performs format assertions. The keyword can provide an annotation without rejecting malformed strings; repeating it does not enable a check that never ran.

Why can format be an annotation?

Draft 2020-12 Validation section7 distinguishes Format-Annotation from Format-Assertion. An annotation describes the intended format. Under that vocabulary, implementations may additionally validate formats, but must provide a switch and disable such evaluation by default. Enabling optional checks is not equivalent to complete Format-Assertion support; implementations should document their coverage.

A tool collecting interface hints need not implement every format's syntax. Dates, addresses, and network identifiers have different complexity and standards. If rejection is required, record the dialect, vocabularies, implementation, and configuration instead of merely locating email in the document.

This illustrative schema was not run against a live interface:

{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "string",
  "format": "email"
}

Type constrains the JSON instance type. Whether format rejects a string depends on the selected behavior. A number and a malformed string test different things: the former can fail type, while the latter needs an active format check. Acceptance of one ordinary address establishes neither negative case.

Make rejection an inspectable contract

Suppose an interface must reject an address string clearly lacking @. Fix the schema, validator name and version, selected draft, supported formats, and startup configuration. Submit an ordinary valid candidate and an obviously malformed string, recording the error path and responsible keyword. This is a proposed check, not an observed library default.

Application-level syntax validation can also be a deliberate choice. In that case, schema success covers only the schema's responsibilities; a subsequent business rule can still reject input. Document where that rule runs. Do not promise schema enforcement while relying on a helper called by only one route.

Test each format actually used. One email rejection does not establish equal support for date-time, uri, or a custom format. Constrain the evidence to the field and implementation examined rather than publishing a blanket claim of format support.

Does an assertion establish that an email address exists?

No. Format-Assertion concerns syntax; it does not require sending mail, connecting to a destination, or proving an entity exists. A syntactically accepted nobody@example.com does not establish delivery or ownership. Verified-address privileges need a separate business verification process.

Nor does an intuitively stricter regular expression necessarily improve the contract. Complex address syntax has compatibility conditions. State the accepted set and intended scope before imposing additional restrictions. First make the promised check match execution; then decide whether the business deliberately accepts a narrower set.

Cross-tool disagreement should be traced, not guessed away. An editor may reject a missing @ while the API accepts it because their configurations differ—or because the editor uses an unrelated rule. Record which tool rejects which value under which schema. Direct API callers cannot depend on client-side feedback.

Can $vocabulary inside an ordinary schema force assertion?

Do not treat it as a switch that works anywhere. Vocabulary declarations define a dialect in its meta-schema. An application schema uses its selected meta-schema to identify its semantics. Requiring Format-Assertion needs the appropriate dialect and an implementation that actually supports it. When that vocabulary is declared true, an implementation unable to provide the required support must refuse the schema rather than silently passing everything.

Changing the dialect can affect consumers that previously treated format only as a hint. Choose between supported implementation options, application validation, and a custom dialect according to the interoperability contract. A vocabulary change is not necessarily a harmless textual tightening.

The site's allOf object-closure article examines keyword scope; this article examines annotation versus assertion. Both require understanding the actual interpreter. A proposed acceptance set includes valid syntax, clearly malformed strings, wrong JSON types, omitted fields, and unsupported required vocabularies. Required presence belongs to surrounding rules such as required, not format itself.

Bind that configuration to the tested entry: preserve a schema digest, the active deployment format option, the called route, and the keyword in the error. A development script can enable checks while a deployed route uses another default-configured validator instance. Establish the actual schema and configuration before attributing disagreement to address syntax; these remain proposed evidence steps.

Preserve inputs, schema versions, configuration, and rejection reasons, with unexecuted checks identified. No registration endpoint was tested here. Demonstrate the intended rejection at the authoritative entry before reporting that email checking is enabled.
