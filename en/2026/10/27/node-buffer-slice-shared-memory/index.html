Why Buffer.slice Changes When the Original Bytes Change

Compare shared views and copies with four initialized bytes, including asynchronous handoff and ArrayBuffer offsets.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-27 · Estimated read 11 min
Translations
zh-CN en

Article

Key takeaways

  • Buffer.slice and subarray share underlying bytes.
  • Choose a copying overload before the producer reuses storage.
  • An ArrayBuffer view needs the correct offset and length.

Suppose a packet is Buffer.from([10,20,30,40]). A recorder saves slice(1,3), then the producer rewrites the second byte. The recorder owns a different object but still observes the same storage. Buffer.slice creates a shared view. An independent byte snapshot requires an explicit copy at the intended handoff.

Different objects can alias the same bytes

The Node.js Buffer reference distinguishes Buffer.slice from TypedArray.slice. The former retains legacy view behavior; the latter copies the selected portion. For deliberately shared views, subarray communicates consistent behavior across Buffer and other TypedArrays.

This four-byte teaching example was not executed. Every byte is initialized; the question is aliasing rather than unsafe allocation.

import { Buffer } from 'node:buffer';
const packet = Buffer.from([10, 20, 30, 40]);
const view = packet.slice(1, 3);
const snapshot = Buffer.from(view);
packet[1] = 99;
// Document-based expectation: view [99,30], snapshot [20,30].
view[1] = 88;
// The third packet byte should now also be 88.

Sharing works in both directions. A consumer writing the view changes the producer's corresponding bytes too. Different lengths and index origins do not imply independent ownership. Test both directions instead of comparing only the initial contents.

Const prevents rebinding; it does not prevent byte writes. A readonly parameter annotation also does not revoke another holder's runtime write access. Review every holder capable of mutating the underlying storage, not merely assignments in the recording function.

Decide ownership at the asynchronous handoff

Imagine enqueueing a view for later logging and immediately reusing packet for the next message. A later consumer can read the replacement bytes. An enqueue function returning does not establish that consumption finished. Copy before enqueueing, transfer ownership, or prevent reuse until consumption completes.

An independent snapshot increases retained bytes, especially under backlog. Sharing introduces lifetime coordination. Neither cost should be declared decisive without measurement. Small packets with unpredictable consumer timing often favor an explicit snapshot; large buffers with enforceable ownership transfer may justify sharing.

Timing is part of snapshot correctness. Copying when the consumer finally runs may faithfully copy already-reused storage. Define whether the record represents handoff-time content or consumer-time storage, and place copying accordingly. A request identifier cannot reconstruct overwritten bytes.

There is also an earlier boundary. If a checksum is filled just before send, copying before that step records an incomplete packet. The intended handoff lies after encoding and validation but before reuse. A fixture can pause before header completion, after completion, and after reuse and ensure only the intended version is admitted.

Copying isolates later writes; it does not validate content or redact sensitive fields. Check protocol correctness, permission to expose bytes, and storage independence separately. “Copied” is not a universal payload approval.

Does Buffer.from(view.buffer) make a copy?

Not by virtue of its name. The constructor reference distinguishes overloads: a Buffer argument is copied, whereas an ArrayBuffer argument can share its storage. view.buffer selects the underlying ArrayBuffer, not the Buffer view itself.

It can also expand the range. A view may occupy only part of an allocation; the underlying ArrayBuffer can include bytes outside that view. Sharing the exact region requires its byteOffset and byteLength. For an independent copy of a Buffer's visible bytes, Buffer.from(view) expresses the purpose directly. Range correctness and copy semantics are separate decisions.

Suppose packet is already a subview and its byteOffset is nonzero. Passing only its buffer loses the visible starting point and can introduce prefixes or extra bytes. Use known markers around the intended region in a test. There is no need to print arbitrary old memory to discover a range error.

Generic Uint8Array utilities need both instance cases

A function typed to accept Uint8Array can receive a Buffer at runtime. Calling the instance's slice can therefore select different behavior. Choose a deliberate copy operation when independence is required, or subarray when sharing is intended, and document lifetime. Test ordinary Uint8Array and Buffer inputs.

Proposed verification starts with the fixed four bytes, constructs a view and copy, mutates the source, and checks each outcome. Then mutate the view and check the original range. Hold an asynchronous consumer before reading and attempt producer reuse: the contract must either prevent reuse or give the consumer a prior copy. Add nonzero offsets, empty intervals, and full intervals. These examples and queue checks were not run.

Long-lived small views can retain a larger underlying allocation. Do not infer retained memory solely from view.length; inspect actual lifetimes before choosing a copy for long-term storage. No memory or performance benefit was measured here.

The allocUnsafe article asks which bytes are initialized and eligible to leave the encoder. This article asks who keeps those bytes stable until consumption. A reliable snapshot needs both boundaries.
