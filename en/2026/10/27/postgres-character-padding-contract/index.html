Why char Padding Changes Equality, LIKE, and Input Checks

Separate character padding, equality, LIKE, and explicit casts before choosing code storage and export rules.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-27 · Estimated read 11 min
Translations
zh-CN en

Article

Key takeaways

  • Check character equality, patterns, and text conversion separately.
  • File width is not the original business-code length.
  • Reject excess input before an explicit cast discards it.

Suppose a product code is stored as char(4). An equality lookup for AB finds it, while a LIKE predicate behaves differently. Inspect the operand types and operators rather than the two letters visible in a client. PostgreSQL's blank-padding and trailing-space rules do not apply uniformly to every string operation.

One stored code, different observations

The PostgreSQL 18 character-type reference describes fixed-width character padding. Comparisons between character values disregard trailing spaces, conversions to other string types remove them, and pattern matching treats them as significant. Keep the operand qualification: this is not a rule that every text comparison ignores spaces.

These teaching queries were not executed. Explicit types make the intended comparison visible instead of depending on a driver's parameter inference.

SELECT 'AB'::char(4) = 'AB  '::char(4) AS same_code;
SELECT 'AB'::char(4) LIKE 'AB' AS exact_pattern;
SELECT ('AB'::char(4))::text LIKE 'AB' AS after_text_cast;

The documented rules imply true for the first expression. The second pattern does not consume the padding, so equality does not justify expecting the same outcome. The third observes text after the character conversion has removed trailing spaces. A verification should record each Boolean result and expression type. A client hiding trailing spaces does not explain what the database evaluated.

A requirement saying “four-character code” also needs interpretation. It might mean four meaningful input characters or four positions in an exchange file. Padding establishes a representation; it cannot establish that a caller originally supplied four valid characters. Define the permitted alphabet and space policy before conversion when exact input length matters. Once padding has occurred, the original input length cannot be reconstructed reliably from the padded value alone.

Keep file layout separate from identity

Imagine an external format reserving four positions for codes that internally may contain two or four characters. Storing a canonical code as text or varchar and padding at export is one reasonable design. It separates identity from file layout, at the cost of an explicit export responsibility for width, encoding, and separators.

An existing system may deliberately depend on char comparison semantics. Retaining it can be justified, but identify queries comparing character operands, queries casting to text, and interfaces preserving spaces. Changing the column type is not proof that existing identity comparisons remain equivalent. Review actual operators and bound parameter types.

Blindly applying rtrim is a counterexample. If a source treats a trailing space as part of an identifier, trimming merges distinct inputs. If spaces are prohibited, postponing cleanup until query time can instead preserve invalid records indefinitely. Normalization is a business decision with a location and an information-loss policy.

Appending % to make LIKE match is equally dangerous. With codes AB and ABCD, AB% expands the lookup to both. A later update may affect more than the intended product. Repairing a type mismatch must not silently replace exact identity with a prefix search.

Does an explicit char(n) cast reject an overlong code?

No. The reference specifies truncation for explicit casts to char(n) or varchar(n). Under a hypothetical four-character contract, casting ABCDE first discards its fifth character. A length check afterward cannot detect the original violation. That differs from ordinary column assignment rejecting an overlong value containing non-space excess characters.

Validate before the cast when the requirement is rejection. Keep an import row identity in the failure record, and decide explicitly whether extra trailing spaces are tolerated. Do not let a database exception for all-space excess input silently choose the product policy.

Migration requires another check. Changing from character to text can change whether trailing-space variants are distinct; changing in the other direction can collapse distinctions. Examine candidate data for identity conflicts before the migration and decide whether to reject or merge them. Successful execution of the schema change is not evidence that business identity was preserved.

Round-trip export is a separate fixture. Suppose an export adds two padding spaces and the receiver treats them as identifier content. Returning that identifier can produce a different internal string. Check both file bytes and the returned identity. Strip padding only where the exchange specification actually defines it as padding.

Proposed cases include AB, AB with trailing spaces, ABCD, ABCDE, and an internal-space code. Check original input, converted representation, character equality, text equality, and LIKE independently. Then test the real driver to discover binding and decoding conversions. None of these database or driver checks were run.
