Why Sequential once Waits Can Miss a Synchronous Event

Trace ready/closed registration order, then separate precreated waits from cancellation, identity, and timeout policies.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-27 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • Register every wait before a producer can emit synchronously.
  • Multiple once waits for one name do not collect successive messages.
  • Define cancellation and listener cleanup after aggregate failure.

Suppose one nextTick callback emits ready and then closed, while the consumer awaits ready before registering its closed wait. By the second registration, closed may already be gone. events.once does not replay earlier events. Register every required wait before awaiting any of them when a producer can emit them in one synchronous batch.

The second listener does not exist yet

The Node.js Events reference explains this ordering trap. EventEmitter invokes listeners synchronously, whereas promise continuations run after the current execution stack. A nextTick batch can also finish before promise tasks. Resolving the first promise therefore does not suspend the producer until the consumer installs its next listener.

This teaching counterexample was not executed. It represents two synchronous emissions, not a real network adapter.

import { EventEmitter, once } from 'node:events';
const bus = new EventEmitter();
async function consume() {
  await once(bus, 'ready');
  await once(bus, 'closed');
}
const completion = consume();
process.nextTick(() => {
  bus.emit('ready');
  bus.emit('closed');
});

First, consume installs ready and pauses. The producer emits ready, resolving that promise, then emits closed before returning. Only afterward does consume resume and install the closed listener. If closed is never emitted again, that wait has no event to satisfy it. Adjacent await statements do not eliminate the asynchronous continuation between registrations.

A slow simulator can conceal the problem. If it places the emissions in separate timers, the consumer may resume between them. A production adapter emitting both inside one call can expose the gap. Test the tightest emission sequence permitted by the interface rather than treating artificial network delays as representative of every producer.

Establish subscriptions before starting production

The documented repair creates all promises before waiting. Registration should also precede a producer's start call if that call can emit synchronously. This unexecuted sketch demonstrates the success-path ordering only.

const ready = once(bus, 'ready');
const closed = once(bus, 'closed');
const completion = Promise.all([ready, closed]);
process.nextTick(() => {
  bus.emit('ready');
  bus.emit('closed');
});
await completion;

Promise.all is convenient, but the decisive change is calling both once functions early. Wrapping the old sequential waits inside another async function does not establish a subscription barrier. A review should identify the actual listener-installation lines and the first point where the producer may emit.

This pattern assumes distinct target events associated with one operation. Creating three once waits for the same event does not collect three successive messages: the first emission can satisfy all three. Continuous consumption needs a queue or iteration contract, including capacity and stopping behavior.

An object may also have completed before the consumer receives it. Subscribing alone cannot recover its earlier close event. A state query or completion promise can address that interface, but the transition between reading state and subscribing must be consistent. Reading state and then installing a listener can itself leave a gap. Do not present that order as a universal repair.

Shared emitters add identity requirements. Ready from one connection and closed from another must not jointly complete an unrelated request. Use per-instance emitters or a protocol associating payloads with the operation. Include a two-connection cross-case in acceptance tests rather than validating attribution with only one producer.

Does Promise.all cancel the other waits after rejection?

No automatic application-wide cancellation follows from an aggregate rejection. The once reference supports AbortSignal for cancelling a wait. An operation can share a controlled cancellation entry among its waits and trigger it when the remaining conditions are no longer needed. Observe the resulting rejections and define resource ownership; do not leave listeners without an owner after the caller has returned.

The error event has special semantics while waiting for another event: it rejects the once promise. Waiting for error itself instead treats it as the target event. Keep these cases separate. Neither rule establishes that every other producer exception reaches the same waiting promise.

Suppose ready arrives but closed never does. A ten-second budget can bound the wait, but must also address listener cleanup, owned resources, and the missing condition's identity. Increasing the timeout does not restore closed if it occurred before registration. The registration repair and the time budget solve different failures.

Verify controlled ordering

A proposed test keeps both emissions inside one nextTick callback and uses an independent detector to observe the unfinished second wait. Then it checks that precreated promises receive both results. The detector's timer itself keeps the test alive, so an unfinished wait is not evidence that the production process would remain alive forever. Check exit behavior in a separate process.

Add synchronous emission inside start, reversed order, a missing condition, early error, cancellation, listener counts, and repeated operations. Whether reversed order is valid is a business rule: Promise.all collects results but does not validate a state machine. A two-connection fixture should ensure an event from B cannot satisfy A's wait.

The inspected reference was v26.12.1. These business examples and tests were not executed. The related async listener rejection article concerns failures returned by listeners that already exist. Here the first obligation is establishing that the listener existed before the event.
