Why Kubernetes Termination Messages Lose Part of a Stack Trace

Explain per-container and shared termination-message budgets, conditional log fallback, and restart-state identity, connecting short summaries to retained logs.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-27 · Estimated read 13 min
Translations

Article

Key takeaways

  • Termination messages have a 4096-byte limit and a shared 12KiB Pod budget.
  • Log fallback requires an empty file and an error exit, retaining only a limited tail.
  • Associate state or lastState with the process instance being investigated.

Suppose a converter writes a six-thousand-byte exception stack to /dev/termination-log, but only part appears in Pod status. Termination messages have a byte limit and a shared Pod budget. Use them for a short failure summary and retrieval clues. Check independent log retention for the complete stack; writing more application output cannot enlarge the status field.

This is a brief final status

The Kubernetes guide to determining Pod failure reasons says kubelet truncates messages exceeding 4096 bytes. Messages across the Pod also have a 12KiB total limit, divided equally among containers. Its example gives twelve regular or init containers 1024 bytes each. Staying below four thousand bytes is therefore insufficient to guarantee completeness in a multi-container Pod.

The unit is bytes, not the editor's character count. Chinese text, emoji, and other encoded content can occupy multiple bytes per character. Even a few lines may be long. Leave space after encoding, and put the error identifier, failed phase, and retrieval reference before generic environment details. This ordering is an engineering choice, not a guarantee that every truncation preserves every field.

This article uses the online guide checked on October 27, 2026. No Pod was run and no real failure log was collected. Check the actual cluster and container runtime when implementing the design. A termination message is neither long-term log storage nor a suitable sole copy of diagnostic information.

Design a summary for a twelve-container task

Imagine a document-conversion Pod with twelve application, initialization, and auxiliary containers. Under the guide's example, each has one thousand and twenty-four bytes available. Copying a six-thousand-byte stack into the application's message file cannot fit in its status message, even if the original file is complete. Do not assume other containers' unused space becomes an exclusive allocation for this application.

Instead write an error category, failed phase, non-sensitive task reference, and a clue for retrieving complete logs. This unexecuted illustrative configuration uses a hypothetical image; it demonstrates the message-file settings, not a complete deployable converter.

apiVersion: v1
kind: Pod
metadata:
  name: conversion-example
spec:
  restartPolicy: Never
  containers:
    - name: convert
      image: example.invalid/converter:demo
      terminationMessagePath: /dev/termination-log
      terminationMessagePolicy: File

Suppose invalid input causes parsing to fail. The application sends full diagnostics to its configured log channel, writes a short summary such as INPUT_INVALID phase=parse ref=job-42, and exits unsuccessfully. An operator can identify the failure class in Pod status and look up the reference in controlled logging. The reference alone does not prove successful log delivery. If collection is delayed or unavailable, report the complete logs as missing rather than treating a link as reconstruction evidence.

The file mechanism can also carry successful final status; the guide describes its use for both successful and failed containers. Avoid writing placeholder text such as “starting work” early and expecting fallback to replace it with a later stack. Source selection has explicit conditions and cannot judge which sentence is more useful.

Why did FallbackToLogsOnError not recover the stack?

The documented fallback requires both an empty termination-message file and an unsuccessful container exit. It then uses the end of container logs, limited to 2048 bytes or 80 lines, whichever is smaller. It supplies a short tail, not a complete log export, and does not merge file content with logs into a larger message.

If the file already contains “starting work,” a later crash does not make that inadequate sentence eligible for automatic replacement. An empty file with a successful exit does not meet the error condition either. If many cleanup lines follow the original exception, the retained tail may mostly describe cleanup. Evaluate output ordering before relying on it.

For an application with controllable exit handling, I would favor an explicit short summary. A difficult-to-modify tool may need error-log fallback as a limited substitute. The former needs reliable error handling and writing; the latter depends on log tails and exit status. Both still need independent logging. A suddenly killed process may have no chance to write anything. An empty message does not establish that no failure occurred.

After restart, inspect state or lastState?

Associate the field with the process instance being investigated. The guide's restart example reads .lastState.terminated.message: the current instance may already be running while lastState describes its predecessor. If the current instance itself is terminated, inspect its current terminated state. Establish container name, current state, and restart count before selecting a field path.

lastState is not an unlimited restart history. Preserve observations with time and instance identity when investigating repeated failures, and use suitable log retention. Label multi-container output with container names so that initialization and application failures remain distinguishable. A healthy restart does not erase the earlier failure, but an old message cannot explain every later input either.

Avoid mixing a structured status envelope with an unbounded stack. If monitoring reads an error code, choose a short, stable format and make the reader tolerate missing fields while retaining the original message for inspection. A potentially truncated JSON document should not be ingested as a guaranteed complete event. Parsing failure should indicate an incomplete summary rather than success. This is a reader-side resilience choice, not permission to reconstruct missing text by guessing.

Proposed checks cover short and oversized files, a multi-container budget, and multibyte text. Exercise empty-file failure, nonempty-file failure, and empty-file success separately. Compare original file, container logs, and status fields, recording actual truncation and fallback outcomes. None of those runs occurred here. The site's termination-budget discussion concerns the opportunity to exit; this article concerns the diagnostic information left afterward. Both designs must work if a summary is to lead operators to evidence that still exists.
