Why a Verified Git Bundle May Not Restore into an Empty Repository

Explain repository-dependent bundle verification with baseline and incremental transfers, an unexecuted recovery path, and boundaries around hashes and local state.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-27 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • Bundle verification checks prerequisites in the current repository.
  • Increments require a baseline; self-contained bundles can bootstrap empty repositories.
  • Hash lists and complete history are not whole-directory backups.

Suppose main is three commits ahead of release-base. A team creates a release-base..main bundle and verifies it successfully in the source repository. The recipient has only an empty directory. That incremental bundle still needs the excluded baseline history. A successful git bundle verify is conditional on the repository where verification runs.

Which object database passed verification?

The Git bundle manual's verify description checks bundle format and whether prerequisite commits exist and are fully linked in the current repository. A complete source repository already satisfies its own baseline requirements. An empty recipient does not. The checked manual last changed in version 2.48.0; the page lists no manual changes through 2.56.0. This does not claim either version was run locally.

A bundle may be self-contained or created with excluded history. An excluded-baseline range requires that baseline and its reachable objects at the recipient. A self-contained bundle without prerequisites can bootstrap an empty repository. Readability, valid format, and available prerequisite history are distinct checks. A transfer checksum establishes matching bytes, not the recipient's object history.

Verification at the recipient can reveal missing history before import. Source-side verification remains useful for generation or file problems, but it uses different premises. An entry saying only “verify succeeded” loses critical information unless it identifies the repository, bundle, and required baseline.

Follow A, B, C, and D through two handoffs

Imagine linear history A, B, C, D, with release-base at A and main at D. A recipient already holding A can advance with an incremental bundle containing the later history. These unexecuted commands describe that scenario; the references must already exist, and paths need a disposable practice environment.

# Source repository with release-base=A and main=D.
git bundle create delta.bundle release-base..main
# Recipient repository that already contains A and its reachable history.
git bundle verify /transfer/delta.bundle
git fetch /transfer/delta.bundle main:refs/remotes/offline/main

The bundle carries new objects and declares prerequisites for excluded history. A matching tag spelling is insufficient. The recipient must actually possess the required commits and connected history. If verification reports missing prerequisites, stop and establish the baseline instead of manufacturing a same-named branch.

For an empty recipient, supply a self-contained baseline or a bundle covering the complete reachable history of the intended ref. In this example, the source could create a self-contained main bundle and the recipient could clone it.

Create the complete main history in the source with git bundle create full.bundle main, then restore it at the recipient with git clone -b main /transfer/full.bundle recovered. Neither step was executed here.

This is a history-recovery entry point, not evidence of a working business environment. Check that recovered main points to expected commit D, then inspect files and normal build prerequisites. A long-running baseline-plus-increments process must identify each baseline and restoration order. A missing intermediate package, replaced baseline, or wrong order can break the recovery chain.

Choose a complete bundle or an incremental chain

For unknown recipients, disaster recovery, or first handoff, a self-contained bundle is easier to explain: no particular prior history is required. It can cost more transfer, and scope still matters. Packaging only main preserves history reachable from that ref, not every independent branch. Inventory required refs before creation.

Increments are useful when recipients have a reliable baseline, bandwidth is constrained, and dependency order can be retained. Reduced transfer comes with dependency management. Keep checksums, included refs, prerequisite commits, recipient identities, and actual recovery results. Choose when to renew a complete baseline by considering retention cost and restoration complexity, rather than treating the smallest file as the best backup.

A failure counterexample verifies an increment in the source, deletes the only baseline copy, and labels the increment a full backup. The file can be valid while the recipient lacks a starting point. Another checks only list-heads, sees main, and declares restoration possible. The ref list describes available entry points; it does not establish prerequisite objects.

Is the prerequisite commit hash enough?

No. A text file containing A's hash identifies what is needed. It does not place A, its tree, file content, or ancestor objects into the recipient's database. Verification requires the commits to exist and be fully linked, which must be satisfied through suitable history transfer. A branch name or a hash pasted into a handoff table cannot replace objects.

Conversely, a target with the required objects may use different local branch names. Verify the actual object relationship rather than rejecting it from names alone. Keep machine-checkable object identities and run verification in the target repository. No bundle creation, clone, fetch, or recovery rehearsal was executed for this article.

What local state remains outside history recovery?

A bundle transfers refs and reachable objects, not an entire development-directory snapshot. Uncommitted working files, index state, repository configuration, and hooks need separate arrangements. External large-file storage, submodule repositories, and build secrets are not backed up merely because the main repository has a ref. Define the recovery target before inventorying dependencies; “full” is not a reason to copy private configuration indiscriminately.

Define where imported refs land as well. The example fetch puts main under a separate offline remote-tracking ref so that the expected commit can be compared before updating a local work branch. It does not automatically replace files being edited. If the recipient has local commits, inspect divergence and integration needs rather than forcing a reset to make names agree. Object import and integration into the working branch are adjacent but distinct steps; the latter still needs normal review.

The site's stash-scope discussion concerns temporary work. This article concerns prerequisite history across object databases. A meaningful rehearsal creates two isolated recipients, one with A and one empty. Verify that the increment requires the former's history, then restore the intended ref from a complete bundle and inspect content. Record repository identities and results so that a valid file can be distinguished from a recovery path that was actually completed.
