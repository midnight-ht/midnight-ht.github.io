The Database Committed. Why Can the Notification Still Be Lost?

Use a transactional outbox to commit business state with delivery intent, then design duplicate handling, event order, relay takeover, and backlog recovery.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-27 · Estimated read 18 min
Translations
zh-CN en

Article

Key takeaways

  • A database transaction can atomically save local state and delivery intent, not an external side effect.
  • A send may repeat after remote success and before local acknowledgement; event identity and consumer idempotency must span the handoff.
  • Polling or CDC still needs an ordering scope, poison-event policy, backlog monitoring, and cleanup rule.

An order and its notification have two commit boundaries: PostgreSQL may confirm the order while the process exits before sending the notification. Putting the calls next to each other does not make the messaging system part of the database transaction. A transactional outbox stores the business change and the intent to deliver it in the same local commit. It does not provide global exactly-once effects, nor does it define duplicate handling, ordering, or backlog ownership. This analysis follows PostgreSQL 18, Debezium documentation, and the transactional outbox pattern; it does not claim that this site ran a message system or measured delivery behavior.

Why can two successful calls still leave a gap?

Suppose a checkout service marks an order as paid and then publishes OrderPaid to a broker. If the process exits after the database commit but before sending the message, the payment state is durable while the broker has no event. Reversing the order is not safe either: the message can be sent before the database transaction fails, leaving consumers with a payment that does not exist. The calls do not share an atomic boundary merely because one function invokes them in sequence.

The PostgreSQL 18 transaction tutorial describes a transaction as an all-or-nothing set of database operations; COMMIT makes the transaction’s changes visible together and durable. That guarantee covers only database changes participating in that transaction. The transactional outbox pattern stores the business entity and pending message together, then uses a separate relay to deliver it. An outbox is an architecture pattern, not a message queue PostgreSQL creates for an application. It aligns local state with delivery intent.

Put the business change and handoff intent together

For a hypothetical payment, the command updates the order and inserts an event record in one database transaction. The record might carry a stable event_id, object type and ID, event type or version, creation time, and only the payload that is necessary. Once the transaction commits, both records exist; if it rolls back, neither does. The point is not to add a nearby flag that the application updates later. Every code path that creates an external event must write the pending record through the same transaction boundary.

The payload must answer a business question: does it mean “this fact was true when payment completed,” or “this is the order’s current state when a consumer handles the message”? The first usually needs enough of an event snapshot to prevent a worker from reading a later-refunded order and changing the meaning of an old payment event. The second should be explicitly described as a state notification, with consumers expected to read the current value by object ID. Either can be valid, but if the choice is implicit, retries and delays silently change event meaning. Copying the entire row has costs too: personal data spreads into messages, logs, and retention systems, while schema changes affect consumers.

The Debezium Outbox Event Router documentation shows one configurable implementation. Its default structure contains a unique event ID, aggregatetype, aggregateid, event type, and payload. The event ID can be placed in a message header for deduplication; aggregateid can be used as the message key to keep related records in the same Kafka partition. The documentation also expects outbox changes to be INSERT operations; it is not intended as an ordinary work queue whose state is freely updated. This is the tool’s default convention, not a database schema every outbox must copy.

The important duplicate window starts after external success

A relay may publish an event successfully and crash before it writes back “delivered.” A replacement sees an unconfirmed local row and cannot know from that row alone whether the broker received the message, so it may send again. A lease or lock can normally ensure one owner at a time, but it cannot eliminate the interval between remote success and local acknowledgement. A timeout cannot distinguish a lost request, a lost response, or a completed operation whose response never arrived.

The event ID therefore has to survive the entire send and consume path. If a consumer can commit its business update and deduplication marker in the same database transaction, a unique event_id can make a replay skip the local change. If the consumer sends email, invokes a payment provider, or performs another external effect, its local deduplication row cannot undo or prevent a side effect in another system. Only when that external service supports an idempotency key or lookup by request ID can the capability become part of the protocol. Otherwise the product must accept duplicates, provide manual reconciliation, or change the workflow so a repeated effect is visible and identifiable.

For an unknown outcome after a timeout, do not blindly repeat the original command. Separate result lookup from resending: first query by event ID, object ID, or external request ID, then decide whether the protocol permits another attempt. If a consumer writes its deduplication row before making the outside call, a crash before the call can incorrectly mark the event complete. If it makes the call before writing the row, a crash can cause a duplicate. Without a shared commit mechanism, ordering can put the risk on one side, but cannot make it disappear.

Ordering, competing workers, and backlog are part of the contract

An order might emit OrderPaid and later OrderRefunded. If the latter arrives first, a consumer that only reads the final state could produce the wrong notification. Define the ordering scope first: global, per tenant, or per order? Global ordering lets one slow message block unrelated objects. Per-object ordering reduces that interference but does not automatically enforce business rules across objects. Debezium’s use of aggregateid as a message key routes related records to the same Kafka partition; the end-to-end order still depends on broker, producer, and consumer configuration. The key alone is not a universal ordering guarantee.

A database-polling relay and a transaction-log CDC relay pursue the same handoff with different operational ownership. With table polling, pending state, retries, and last errors are visible in one place, but the relay still needs a claim/lease protocol, scan indexes, retention cleanup, and attention to query load. CDC captures database changes; Debezium provides an outbox router, but teams must also operate the connector, log retention, offsets, schema compatibility, and backlog recovery. Log tailing may fit a team that already operates a reliable CDC platform. For a small system whose application service owns sending and retries, table polling may be more direct. Neither method defines business deduplication or poison-message handling automatically.

Persistent failures should not be hidden behind infinite retries. Track pending count, age of the oldest event, failure categories, takeovers, and a dead-letter or operator-handling path. Preserve the original event_id when replaying and state whether already completed consumer effects are skipped. Cleanup should wait until retention, consumer recovery capability, and audit needs allow it. Deleting too early removes replay evidence; never deleting lets storage and query costs continue to grow.

How should the handoff be tested?

Test distinct failure windows. Exit before commit and confirm that the order and outbox row roll back together. Exit after commit but before the relay claims the row and confirm another worker can take over. Exit after the broker accepts the message but before the relay records acknowledgement and confirm the consumer recognizes a replay by event ID. Have competing workers claim the same pending item and check for unacceptable parallel effects. Then keep one poison message failing and confirm that it does not starve unrelated objects indefinitely. For each step, define whether evidence comes from the database, broker, or consumer. Only fill in a “passed” result after executing it in a controlled test environment. No such tests were run here, and no throughput or latency figures are claimed.

The checkout command itself can also be retried by its client, creating two different events; the outbox only stores events that were actually inserted and does not deduplicate the API request. Decide how the request’s idempotency key maps to a stable event identity before addressing relay duplicates. Review the related business idempotency contract alongside the handoff. For PostgreSQL’s local atomic boundary, see cross-row invariants and full transaction retries. An outbox is more than a “pending messages” table only when the team can answer who takes over, how duplicates are identified, what scope ordering covers, and when old events may be removed.
