A Server Fetches User URLs: Why Is Domain Validation Not Enough?

Trace SSRF destination policy from URL parsing and DNS through the socket, redirects, retries, and network egress; distinguish fixed integrations from arbitrary fetching.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-27 · Estimated read 19 min
Translations
zh-CN en

Article

Key takeaways

  • Fixed integrations and arbitrary public fetching are different product security models; decide whether the API needs a complete user-supplied URL first.
  • Hostname checks constrain the real network destination only when resolution is bound to the connection and policy covers IPv4/IPv6, redirects, and retries.
  • Controlled acceptance tests need connection-side or egress-denial evidence; this article proposes tests but reports no execution.

Checking a hostname evaluates only one point in the request path. What the server must authorize is the address reached by each actual connection. A safe link preview cannot ask only whether the input resembles a valid URL. It must also ask which host the parser selected, which addresses DNS returned, where the HTTP client connected, and whether redirects, retries, or fallback addresses re-enter the same policy. This article describes defensive design and controlled test cases. No live target was accessed, no attack request was sent, and no security test was run.

First decide what the product needs to reach

The central SSRF risk is not that a string contains a URL; it is that a user influences a server request with more network privileges than the user has. Link previews, remote avatar downloads, webhook callbacks, and server-side rendering of external documents can all create this path. A server may reach a corporate network, management endpoint, or cloud-provided service that an ordinary user cannot access. If the fetcher is freely controlled, it can become a proxy between the user and those networks. OWASP’s SSRF prevention guide distinguishes two cases: an allowlist is viable when destinations are known trusted services; it usually cannot enumerate the target set when the product fetches arbitrary public addresses.

Suppose the product only needs to preview pages from approved commerce partners. It may not need users to paste complete URLs at all. A user could submit a partner ID or page number, while the server chooses the hostname, scheme, and path template from configuration. The user supplies a business object; the server chooses the network destination. If the product genuinely must preview arbitrary external pages, accepting a URL is part of the requirement, and a short allowlist cannot honestly cover the design. Those are different risk models. Separate them at API design time instead of starting with arbitrary fetching and adding exceptions indefinitely.

URL syntax is not access authorization

A URL parser can split an input into a scheme, authority, host, port, path, and query. “Parsed successfully” says only that one library understood the input; it does not say the destination is authorized. RFC 3986 defines generic URI host syntax as an IP literal, IPv4 address, or registered name, and its generic syntax does not itself make a destination safe to contact. The operation is defined by the protocol using the URI. RFC 3986 is a syntax standard, not an outbound access-control policy.

When one service passes a URL string to a validation library and then to a different HTTP client, the two implementations can interpret delimiters, escaping, or authority boundaries differently. OWASP recommends rejecting parser disagreement rather than trying to reconcile the readings with string substitutions. A more controllable API accepts a business identifier or destination ID and constructs the scheme, port, and path on the server. If a full URL is required, use a defined parser, extract its canonical components, reject unsupported forms, and ensure the client that connects does not apply a different interpretation later.

Even an exact hostname on an allowlist is only an input to DNS, not the connection destination itself. If the name resolves to a public address at validation time but the client makes a second DNS lookup before connecting, that second answer may differ. This is the DNS-rebinding or check/use race. OWASP says domain allowlisting alone does not prevent DNS rebinding: resolve the destination, validate the result against permitted networks, and ensure the HTTP client actually connects to the validated address without performing another unchecked lookup. OWASP domain validation guidance

A connection decision should cover all IPv4 and IPv6 answers and use the permitted network scope for the deployment. For a fixed partner integration, intersect resolved addresses with the destinations approved for that service. For arbitrary public fetching, block loopback, private, link-local, and other environment-specific internal resources, then keep using the address that passed the check when opening the connection. Checking just one A record, ignoring AAAA, or validating an answer and letting the client resolve again can separate policy from socket. OWASP also warns that when a chosen IP is used, the original hostname still needs to be retained for HTTP Host, TLS SNI, and certificate verification; changing the connection address is not a reason to disable TLS identity checks. Confirm how the actual client supports both address pinning and hostname identity. curl’s name-resolution documentation illustrates one client-specific mechanism.

Redirects, retries, and fallback paths must pass the gate again

Assume a preview request passes its first destination check and the response is a redirect. If the HTTP client follows it automatically, the next connection can reach a different host or address, outside the initial decision. For fixed integrations, disable automatic redirects. If redirects are required, parse and validate the scheme and host again for every hop, validate the resolved address, and bound the number of hops, total time, and cumulative bytes. OWASP recommends disabling automatic redirect following for allowlisted flows; the OWASP testing guide says to repeat destination checks for each redirect. OWASP DNS rebinding testing guidance

The same rule applies to retries, connection pools, proxies, and failover. Some clients may try another address from the same DNS response after a connection failure. If the application validated only one address, a fallback could use one that was never approved. Do not treat “this hostname passed earlier” as permanently safe for retries. Either reuse a connection pinned to the validated address or re-resolve and re-check every result, with rejection as the failure behavior. If an egress proxy is involved, define both legs: application to proxy and proxy to destination. An application-side check of the first URL cannot govern the proxy’s own DNS resolution or redirect handling unless the proxy enforces the policy too.

Network egress is a second boundary independent of URL validation. Run fetch workers in a network isolated from sensitive services and let a firewall or proxy expose only the destinations or public routes the feature needs. A fixed integration can allow the worker to reach only approved services. Arbitrary public fetching can deny internal networks by default and keep any necessary internal service access explicit. If application validation misses a case, the network policy can still limit the impact. OWASP describes application and network defenses as defense in depth and states that network-layer controls should make only permitted flows available to the worker. OWASP network-layer guidance

How do you test the connection boundary, not only URL parsing?

A controlled test should verify both that an allowed destination completes a preview and that a denied destination causes no connection. For a fixed target, use an isolated environment with a controlled test name and resolution, then confirm the client connects to the exact approved address while retaining the intended HTTP Host, SNI, and certificate checks. Test a name with multiple A or AAAA results and assert the system follows its documented policy rather than silently selecting an unchecked address.

Redirect cases should cover a permitted host redirecting to another permitted host, a redirect to a denied range, and an overlong chain. Retry tests should verify that a connection failure cannot make the client use an address that was not revalidated. A resolution-race test should make validation and connection observe different answers and assert that the connection remains pinned to a validated address or is rejected. Also test that an input interpreted differently by the validation and connection components is rejected rather than resolved using the more permissive reading. Resource cases include slow responses, oversized bodies, unexpected content types, and concurrency pressure; those protect worker capacity and output handling but do not replace destination policy.

Record connection-side evidence for each case, such as the target seen by a controlled proxy, an egress-denial event, or the client’s actual connection callback—not only the parsed URL object. No tests were executed for this article. These are proposed acceptance cases for an authorized isolated environment, not passing results. The product should also bound response size and total duration, never execute remote HTML as trusted application code, and avoid returning raw errors that expose internal addresses, connection details, or sensitive query parameters.

If the product depends on fixed services, the safest change may be to remove “user chooses the network destination” from the interface instead of adding a larger blocklist. For a feature that truly must fetch arbitrary external targets, design parsing-to-connection consistency, redirect and retry rules, network isolation, and resource budgets together. Destination authorization is separate from whether the user may read a business object; see object-level access control. Verifying one does not automatically satisfy the other.
