A Server Fetches User URLs: Why Is Domain Validation Not Enough?

Bound server-side URL fetching through destination policy and redirect checks backed by controlled network egress.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-09 · Estimated read 6 min
Translations
zh-CN en

Article

When a server fetches a user-supplied URL, restrict the destination it can actually connect to, not merely the input’s syntax. Destination policy, redirects, and network egress should work together. This is defensive design analysis without attacks or security tests against a real site.

Establish the necessary access scope

The OWASP SSRF prevention guide separates known trusted destinations from arbitrary external fetching and discusses application and network defenses. If fixed partner endpoints meet the requirement, prefer an allowlist over opening the network and accumulating denials.

A hypothetical link-preview feature lets users choose where a server sends requests. The server may have network access the user lacks. That privilege difference creates the risk; a normal-looking URL does not establish authorization.

Preserve the boundary after validation

A destination can redirect, and DNS can return multiple or changing addresses. Validating the starting string and following arbitrary redirects moves later connections outside the original decision. OWASP warns about redirect bypass. If redirects are required, reapply the destination policy at connection time for every hop and bound their number.

Address handling needs consistent parsing across IPv4, IPv6, representations, and the actual connection library. No bypass payloads are provided here. For public fetching, define environmental restrictions on internal, loopback, and special platform resources.

Isolate fetching workers from sensitive networks and expose only necessary outbound capabilities. A validation defect should not grant access to the entire service network. Actual firewall or proxy rules require environment-specific design.

Bound the work and the disclosure

Set total time, response size, and concurrency budgets. An allowed destination can still exhaust workers. Treat fetched HTML as untrusted content, not an authorized application to execute.

Log the rejecting rule and a redacted task identity rather than complete URLs containing tokens. User-facing errors should not expose internal network details. Support should not need to paste sensitive links into unrelated tools.

Proposed controlled tests cover allowed and denied destinations, redirects, resolution changes, and oversized or slow responses. None were run. They cannot justify a claim that a system is free of SSRF, and production egress must match the tested boundary.

For fixed integrations, accept business parameters and select the endpoint server-side instead of accepting complete URLs. For arbitrary fetching, establish isolation and resource budgets explicitly. Destination authorization is separate from object-level access control.
