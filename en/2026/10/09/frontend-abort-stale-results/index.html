Search Results Went Backward: Cancellation Also Needs a State-Commit Guard

Combine request cancellation with identity guards on results and errors so older search responses cannot replace current intent.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-09 · Estimated read 6 min
Translations
zh-CN en

Article

Prevent stale search results by checking that a response still belongs to the user’s current intent when committing UI state. AbortController can stop unnecessary asynchronous work, but cancellation is not a complete consistency design and does not undo a server-side business operation. No component or performance test was executed here.

A successful response can still be stale

A user searches “architecture,” then “architecture review.” The newer response arrives first, but the older response later replaces it. Both requests succeeded while the displayed results stopped matching the input.

MDN documents abort() for fetch, response-body consumption, and streams. It does not promise transactional rollback on the server. Treat search cancellation and order cancellation as different contracts.

Compare identity at every state update

A candidate implementation increments a request version, captures it with the query, and permits updates only while it matches the current version. Guard result arrays, errors, loading flags, and finally cleanup. An older request can overwrite newer state through any of these paths.

Cancellation reduces unnecessary work when the query changes or a component unmounts. Keep the identity guard because later asynchronous processing may already have started or may not honor the same signal. Let the guard establish correctness rather than assuming every stage stops immediately.

Debouncing reduces request frequency, but each request version should still identify the complete filter state but does not prevent response reordering. Cache entries need explicit query keys. Include pagination, filtering, and ordering when they change the result; a single “last result” variable is insufficient.

Distinguish cancellation from failure

Changing a query normally should not produce a service-failure popup. A real network failure should preserve input and offer a retry associated with that query. Custom abort reasons and wrappers require checking the actual API behavior rather than matching one universal error string.

Keeping old results visible during loading can be a valid UX choice if the pending conditions are clear. That choice is separate from allowing an old request to overwrite current state.

Proposed tests control response order and inspect results, errors, and loading state. Include cleared input, unmounting, changed pages, and cancellation while reading a body. These were not executed. Calling abort is not itself the acceptance criterion; the final screen must match current intent.

For writes, a server may have committed after the browser stopped waiting. Use an explicit cancellation operation or state lookup. See idempotency and unknown outcomes for that separate problem. For search, audit every state-commit point first.
