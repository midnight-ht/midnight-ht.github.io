The Key Was Deleted from Git: Why Is the Incident Not Over?

Separate credential revocation, consumer migration, evidence of rejection, and Git-history cleanup instead of treating source deletion as remediation.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-27 · Estimated read 21 min
Translations
zh-CN en

Article

Key takeaways

  • Source deletion, provider revocation, consumer migration, and copy cleanup are separate states that need separate evidence.
  • Choose revocation and cutover order from credential risk and downtime cost; prioritize containment for high-risk exposure.
  • Closure needs evidence for replacement access, old-credential rejection, audit scope, and unresolved sessions—not a green source scan.

Deleting a secret from a repository proves only that the current file no longer displays it. It does not prove that the provider rejects the credential, that old instances and workflows have stopped using it, or that copies in clones and logs are gone. A defensible response answers four separate questions: Is the credential still valid? What can it access? Which consumers still depend on it? What will happen to exposed copies? Without evidence for each relevant question, “we deleted it” is not a sound incident-closure statement. This article describes a process and its evidence boundaries; no real account, token, incident log, or credential rotation was accessed or performed for this analysis.

Separate four different kinds of change

Teams often describe “deleting the secret” as one action, but at least four layers of state are involved. The first is the current application version: does source, configuration, a build artifact, or a log still contain the value? The second is the credential provider: does it still accept the token, password, certificate, or key, and what permissions and lifetime apply? The third is the consumer set: have CI workflows, deployment jobs, running instances, operational scripts, and recovery environments switched? The fourth is historical copies: do Git history, branches, forks, developer clones, cached pages, tickets, or logs retain a copy?

These layers do not update each other automatically. Removing a string from the latest commit does not ask a cloud provider to revoke a token. Revoking a token does not update every pipeline configuration. Rewriting Git history does not erase another person’s clone or every cached copy. The GitHub leaked-secret remediation guide says removing the secret from code alone is insufficient: revocation with the provider is the most important remediation step. It also treats updating affected services and testing the replacement as follow-up work. the GitHub leaked-secret remediation guide

Start with an inventory rather than a history rewrite. Record the provider, credential type, owner, permission scope, expiration or last-use information, consumers, replacement owner, revocation status, and location of evidence using identifiers that do not reveal the secret. Do not paste a complete token into a ticket, chat, or review JSON. OWASP recommends least-privilege access to secrets and metadata describing a secret’s purpose, intended consumers, lifecycle, and owner. Such metadata helps move a credential without recording its value. OWASP Secrets Management Cheat Sheet

Let risk determine the cutover order

The main sequencing question is whether to revoke the old credential first or issue a replacement and migrate consumers first. If the credential remains active, appeared in a public repository, has broad permissions, or shows suspicious use, containment is the priority; delaying revocation extends the window for unauthorized access. For high-risk credentials, the guide recommends prioritizing immediate revocation. If downtime is a concern, its guide allows generating a replacement, switching the application to it, and then revoking the old token. It does not prescribe a universal overlap period, and habit is not a reliable way to choose one. the GitHub leaked-secret remediation guide

If evidence indicates that a credential is already inactive, appeared only in a controlled private repository, or belongs to an isolated development environment, a team can plan a migration window with a clear end. “Lower risk” still means it needs remediation. The plan should name who creates the replacement, which services switch, when the old credential is revoked, which failure signals will be observed, and what happens to consumers that miss the deadline. Without a verified consumer list and an expiration condition, temporary overlap can become permanent access.

Consider a hypothetical CI deployment token committed to a repository. Assume it is still valid and can publish to production. A cautious response would identify its provider, permissions, last-use data, and exposure status; list the release workflow, manual rollback job, and standby environment that call it; then choose immediate revocation or, only if evidence and availability requirements justify a short transition, issue a token with the same or narrower scope, switch and verify each consumer, and revoke the old value. This is a design example, not a report that any repository or provider account was inspected.

If only the main branch’s workflow secret is updated while an old release branch can still deploy or a nightly job reads the value elsewhere, migration is incomplete. Build the consumer inventory from code references, provider-side secret settings, deployment definitions, runbooks, and owner confirmation. Code search can find static references but may miss platform variables, dynamically issued credentials, or recovery copies. Audit logs can provide evidence of use, but absent records do not automatically prove that no use occurred. Mark entries as confirmed, awaiting provider verification, or unknown; do not turn an assumption into a completed check.

Acceptance should prove both paths

A replacement credential performing its intended operation proves only the new path. Evidence that the old credential can no longer obtain the tested permissions is needed for the revocation side. Prefer provider-reported credential status, revocation results, audit events, or a dedicated safe validation mechanism, and record the identity and scope checked. Do not repeatedly replay a leaked token in an uncontrolled production environment to “test” it, and do not expose the value in test output. GitHub provides automatic or API-based revocation for certain token types and circumstances, but the supported types are limited. Do not extend those rules to every GitHub credential, much less to other providers. GitHub token expiration and revocation documentation

Also, “the old credential is rejected” does not necessarily mean every existing access path has stopped at the same instant. A long-lived connection may continue after authentication. A short-lived token may have been signed by an older key. A cloud access key may have issued a session credential. Certificates have their own revocation and status-check mechanisms. An application installation grant can have a separate key and lifecycle. These details depend on the provider’s implementation. Before testing, identify what is being revoked—a password, access token, refresh token, certificate, session, or derived credential—and consult the relevant provider documentation for cascading revocation, effective timing, and whether existing connections must be re-established.

A useful acceptance record is not “rotation succeeded” but a set of reviewable facts: the new credential identifier and scope; consumers switched and their deployment versions or job configuration; the provider’s reported revocation time for the old credential; safe evidence that the old credential was rejected for the tested scope; unresolved sessions, derived tickets, or copies; and the owner and due date for follow-up. Never include credential values. If the management interface confirms only that a revocation request was accepted, but cannot establish when every session expires, record that distinction instead of claiming immediate global invalidation.

Git history cleanup is a separate workflow

After invalidating the credential, decide whether history also needs rewriting. The repository-cleanup documentation recommends revoking or rotating a secret first; if it can no longer grant access, rewriting history may not be necessary to solve the authorization risk. If public exposure, compliance, or another copy risk still warrants cleanup, assess a tool such as git-filter-repo, but understand that history rewriting changes commit hashes and requires coordination across branches, clones, and contributors. An old clone can reintroduce the sensitive commit if it is merged or pushed carelessly. Forks, cached views, and pull-request references may also remain accessible. A history rewrite neither revokes the credential nor proves every external copy was erased. GitHub guidance on removing sensitive repository data

Cleaning current files, scanning artifacts and logs, coordinating clones, deciding whether to rewrite history, and adding preventive controls are separate tasks. Prevention may include least privilege, short lifetimes or dynamic credentials, push protection, secret scanning, avoiding values in logs, and clear ownership and expiry policies. A scanner finding—or not finding—a string is one piece of evidence; it cannot tell you whether the provider still accepts the credential. OWASP also treats rotation, revocation, and expiration as distinct lifecycle stages and calls for secure revocation of potentially compromised secrets. OWASP’s secret-lifecycle guidance

When can the incident be closed?

Closure is not “the search result is green.” It is a bounded conclusion based on current evidence: the relevant old authorization was revoked or there is a documented compensating control; known consumers have switched or been disabled; the replacement works as intended; the treatment of historical copies is recorded; log review covers a stated time range, resources, and available audit scope; and remaining unknowns have owners and follow-up actions. If the provider cannot say whether existing sessions remain valid, the closure record must preserve that unresolved boundary.

Distinguish “we found no misuse” from “we proved there was no misuse.” If audit retention was too short, logs omitted caller identity, or the relevant resource had no logging enabled, the conclusion is limited by the evidence. Do not write “no data was accessed” merely to make the incident appear closed. No actual logs were examined for this article, so it makes no judgment about past misuse or loss. For a related discussion of GitHub Actions permission scope, see minimum token permissions for GitHub Actions; that article concerns workflow authorization and does not replace revocation or investigation after a leak.
