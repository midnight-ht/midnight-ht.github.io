Why a GitHub Actions Cache Hit Does Not Make a Release Trustworthy

A cache hit restores data; it does not establish cache provenance, lockfile installation, or release-artifact identity. Separate those checks using GitHub Actions cache scopes, cache-mode, and npm ci.

Key takeaways

  • cache-hit means the key matched and path contents were restored; it is not a signature, dependency-consistency check, or release-provenance claim.
  • GitHub Actions caches are scoped by branch or tag. Low-trust triggers default to read-only access to default-branch caches, and an explicit write mode changes that boundary.
  • Caching ~/.npm and caching node_modules are different choices when npm ci is the installation contract; npm ci removes an existing node_modules directory.
  • Caches are for reuse; artifacts preserve or pass outputs. A privileged release still needs to bind a commit, run, and artifact digest.

A GitHub Actions exact cache hit means that the requested key matched and files were restored. That result says nothing about whether a trusted run created them, whether they match the current dependency declaration, or whether they belong to the approved release. Treat a cache as disposable acceleration input, keep installation governed by the project’s lockfile contract, and verify the commit and workflow behind an artifact separately at the privileged publication boundary. This article draws on official GitHub documentation and the npm CLI v12.2.3 reference opened on 2026-11-26. No cache-poisoning, workflow, or installation test was run.

cache-hit reports a lookup result, not trust

GitHub Actions first looks for an exact key. If none is found, it can search prefixes and restore-keys. On a hit, the action restores the cache path to the runner. A fallback hit may contain data created for older inputs. Putting a lockfile digest in a key helps create a new key when the lockfile changes; the operating system, runtime, architecture, or install options may also determine whether a result is reusable. But a key answers “which cache should I look for?” It is not a signature or a review of the bytes. GitHub says cache contents are not signed or verified. A green cache-hit output therefore does not mean “dependencies verified.”

Ask these questions separately: did the key match? Which branch scope supplied the data? Could this run read or write that scope? Will restored files be executed directly? Does the final artifact correspond to the approved commit? A key containing hashFiles('package-lock.json') cannot answer whether its source is trusted, whether the job processed untrusted input, or which build produced the release file. With broad restore-keys, a hit only says that some prefix-matching data was found; it does not turn an older dependency tree into the current one.

Branch scopes and events define cache access

GitHub associates cache scope with a branch or tag rather than isolating it solely by workflow or job identity. Workflows in the same repository and branch can share a cache. A pull request may restore caches visible from its current branch, the default branch, and its base branch. A cache created by an ordinary pull_request run is scoped to the PR merge ref and cannot be restored by the base branch or another PR. “This key is only for the build workflow” is not necessarily an access boundary; inspect the event, branch scope, and path being cached.

For low-trust triggers that resolve to the default-branch cache scope, GitHub defaults to read-only access. Its documentation lists pull_request_target, issue_comment, and workflow_run among such events. Explicitly setting cache-mode: write or write-only bypasses that read-only default and reintroduces cache-poisoning risk. cache-mode can be set at workflow or job level to control reads and saves; a job-level setting overrides the workflow-level one. Reusable workflows also need review: an explicit limit from the caller constrains the called workflow's requested mode.

Consider a hypothetical case. A trusted default-branch push workflow maintains a dependency cache. A low-trust pull-request workflow wants to read the same scope to avoid downloading packages again. With cache-mode: read, it can restore the default-branch cache but cannot write to that scope. If the workflow explicitly changes to write so the PR job can save data, and that job processes files, scripts, or build inputs controlled by the PR, an attacker may influence content later restored by a more privileged workflow. This describes a threat path; it is not an exploit performed for this article. The fix is not to add more random-looking characters to the key. Restrict cache writes to trusted triggers, make low-trust workflows explicitly read-only, or prevent privileged jobs from restoring and executing untrusted cached content.

A cache is not secret storage either. A run that can read a cache can extract its files, and GitHub explicitly warns against putting tokens, credentials, or other sensitive information under a cached path. Even in a private repository, assess who can open pull requests and which workflows can read the data; do not treat “private” as proof that a cache is confidential.

The cached path determines whether you save downloads or skip installation

An npm example makes the distinction concrete. Caching ~/.npm reuses package-manager download data; npm ci still builds the installed directory from the lockfile and package-manager process. npm documents that npm ci requires a lockfile, errors if it conflicts with package.json, removes an existing node_modules before installing, and does not rewrite manifest files. If a workflow restores the entire node_modules directory and then runs npm ci, that restored directory is removed. It should not be counted as a retained installed-tree result. Whether caching download data saves time depends on the project and network; this article includes no timing measurement.

Conversely, if a workflow restores node_modules and skips installation, extra, missing, or stale packages, old native modules, or previous lifecycle-script outputs can remain in the build input. Even a key containing the lockfile digest does not guarantee that this directory was created by a trusted process with the current toolchain. A lockfile-based install helps apply the declared dependency graph; it does not review every package's code, lifecycle script, registry source, or runtime behavior. Supply-chain review needs separate controls for dependency origin, versions, and build permissions.

Start by asking, “Which expensive-to-regenerate data can be reused while remaining safe to rebuild?” If the answer is downloaded package data, caching the package-manager directory while continuing lockfile installation is easier to bound than skipping installation. If you deliberately cache an expanded dependency tree, decide when it is rematerialized, which toolchain inputs belong in the key, who can write the cache, and whether a later job will execute its files. Do not choose the path based only on hit rate.

Release artifacts need more than a cache filename

GitHub describes dependency caches as a way to reuse data that changes infrequently or is expensive to regenerate. Workflow artifacts preserve build outputs and logs or pass outputs between jobs. The features serve different purposes and cannot replace one another. An artifact solves “pass this job's output to another job,” but a successful download does not, by itself, establish its provenance.

A more careful handoff records the approved source commit, build run, output digest, and deployment approval object as related identities. If a team enables GitHub artifact attestations, it can generate signed provenance claims that include the associated workflow, repository, environment, commit SHA, and triggering event; a consumer must verify them against its own policy. These attestations are explicit trust material: using a cache or uploading an artifact does not create one automatically.

A privileged release job should not upload a file named release.tar.gz merely because it exists in a cache. First establish that the file came from the trusted build for the intended commit; then compare its digest with the approved record. If caches hold intermediate files, a trusted job can generate the final artifact again. Do not let an executable directory written by a low-trust trigger cross the publication boundary directly.

Test cases that distinguish the failure modes

Design acceptance around more than a single cache-hit percentage:

  • No cache: can the job download or regenerate data and still install from the declared lockfile? This checks that a miss is only a performance issue.
  • Exact hit: after restoration, does the job still perform the lockfile-governed install and record the dependency graph, toolchain, and artifact provenance independently?
  • Fallback hit: when a broad restore-keys entry matches, is it recorded as fallback data and corrected or rejected by installation if inputs do not match?
  • Low-trust run: can an external pull request only read the default-scope cache? Has any job or reusable workflow explicitly requested write-capable cache-mode?
  • Privileged consumption: does the release job treat a path, filename, or unverified artifact as identity? How are the digest, origin, and approval connected?

These are proposed checks, not tests performed here. This article did not connect to a GitHub repository, run a workflow, or compare cached and uncached builds. Record cache-hit, lockfile-install results, provenance checks, and the final release digest separately; otherwise, a successful cache step can hide that three other claims remain unproven.

Temporarily disabling a cache can create a troubleshooting baseline and help determine whether reused data contributed to an incident. That comparison alone cannot establish that the cache is safe or that it should remain disabled. Clarify the installation contract and provenance boundary first, then decide which rebuildable data is worth caching.
