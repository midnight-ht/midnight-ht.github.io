How Are GITHUB_TOKEN Permissions Calculated for a Job with Workflow-Level Permissions?

Trace GITHUB_TOKEN permissions from organization or repository defaults through workflow and job declarations to event policies. Actions in the same job share that permission boundary.

Updated 2026-11-27 · Estimated read 23 min

Article

Key takeaways

  • An Action without an explicit token input is not proof that it lacks GITHUB_TOKEN access; inspect the job in which it runs.
  • Calculate effective permissions from enterprise, organization, or repository defaults, workflow declarations, job declarations, and trigger-event rules.
  • Once permissions are specified, omitted permissions become none; write includes read.
  • Fork pull_request, pull_request_target, private-repository policies, and Dependabot cannot be reduced to one universal default.

To determine whether a GitHub Actions job can change a repository, do not read only one YAML line. Trace the enterprise, organization, or repository default, then workflow-level permissions, job-level permissions, and finally the trigger event and fork policy. An Action without an explicit token input is not necessarily running without a GitHub identity: GitHub documents that an Action can access GITHUB_TOKEN through the github.token context. The useful review question is therefore what code runs in the whole job, what its token can do, and whether untrusted input can control code on that execution path.

Documentation was checked on November 27, 2026. Both workflows below are hypothetical examples; they were not run in a real repository. No particular repository's organization settings or token permissions were inspected.

Treat the job as the token permission boundary

permissions controls what GITHUB_TOKEN can do to GitHub resources. The workflow syntax reference says a workflow-level declaration applies across jobs. A declaration inside an individual job grants its specified access to Actions and run commands in that job that use GITHUB_TOKEN. An Action referenced with uses: third-party/action@... and the shell command after it therefore cannot be treated as separate security principals simply because the workflow did not put the token in one of the Action's explicit inputs.

The GITHUB_TOKEN guide makes the implication explicit: an Action can access the token through the github.token context even if the workflow does not pass GITHUB_TOKEN to it. That explains why “I did not write a token under with:” is not the end of a permission review. It describes one input field; it does not change the job's identity or token permissions.

This changes what to inspect. Asking only “which input did this Action receive?” is incomplete. Also ask which job runs it, what that job's token can do to the repository, which repository-controlled code runs before and after the step, and whether the job can read other secrets. permissions does not automatically restrict other secrets or turn a shared runner into an isolated sandbox. Token permissions, secret delivery, runner trust, and network access are related but distinct boundaries.

How do effective permissions get calculated?

The first layer is the default configured at the enterprise, organization, or repository level. GitHub documents that an organization can set defaults and repositories can inherit those restrictions. Its documented defaults for newly created personal-account and organization repositories also differ. As a result, neither “GitHub Actions is read-only by default” nor “it is writable by default” is a safe universal statement without the repository and account settings. If those settings have not been inspected, the correct value for that layer is unknown.

The second layer is permissions at the top of the workflow file. When present, it provides a baseline for jobs. The third layer is permissions on an individual job, which can specify a different set for that job. Read the complete YAML structure: moving a declaration from the workflow to a job changes which jobs it covers, not the syntax by which a token is passed to an Action.

Two details are easy to miss. First, once permissions is specified, every permission that is not listed is set to none. Second, write includes the corresponding read capability. For example, contents: write is not merely “can publish”; it also allows reading repository contents. Read and write are not independent switches. If an operation needs only to read source, there is no reason to express that need as contents: write.

The following illustrates configuration structure only. It was not executed and is not a universal project template:

permissions: {}

jobs:
  verify:
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@v6
      - uses: vendor/check@v3
      - run: npm test

  publish:
    permissions:
      contents: write
    steps:
      - run: ./publish-release.sh

The point is not “copy this and the workflow is secure.” The third-party Action, checkout, and test command in verify all run within that job's token permission boundary; contents: write in publish is not assigned only to the final shell line. A real workflow review should list the GitHub API operations each job needs, inspect the source and code version of its Actions, and confirm whether publication needs additional permissions or secrets. Starting with an empty workflow permission set and adding capabilities per job makes intent visible, but it does not replace checking the event and repository settings.

Why can the trigger event change the result?

The workflow file is not the only input. In GitHub's documented calculation, enterprise, organization, or repository defaults come first, followed by workflow-level and job-level configuration, then any adjustment for the triggering event and fork context. For example, a pull_request workflow from a fork is reduced from write to read permissions when the relevant setting to send write tokens to fork workflows is not enabled. Dependabot pull requests are treated as fork requests and, by default, receive a read-only GITHUB_TOKEN and cannot access ordinary repository secrets.

Those rules do not describe every event. GitHub treats pull_request_target as a higher-trust event: the workflow runs from the base repository's default branch and receives the base repository's GITHUB_TOKEN and repository or organization secrets. This can be useful for metadata operations such as labeling or commenting on a fork's pull request. By default, it does not execute the fork's code. If a maintainer checks out the fork's head in that job and runs its build script, dependency installation, or tests, externally controlled code has entered a path with a privileged token and secrets. Checkout alone is not execution; the subsequent command that runs the checked-out scripts completes the risk path.

As of November 27, 2026, GitHub's security documentation also says that, for public repositories without an applicable Actions event policy, its default policy blocking pull_request_target was in evaluate mode, so runs continued. The documented enforcement date is December 2, 2026 for affected repositories that were using the default policy before general availability. The policy does not apply to private or internal repositories and does not replace an applicable event policy already configured. The date and scope are platform policy details that can change; maintainers should recheck the official documentation before acting and should not claim that every repository is already blocked today.

Private-repository fork workflows have their own organization or repository settings. Administrators can control whether those workflows run, whether they receive write tokens or secrets, and whether approval is required; organization-level restrictions may prevent a repository from relaxing them. Copying a public-repository default into a private repository, or the reverse, can produce the wrong effective-permission answer.

Splitting jobs helps, but does not solve every problem

Putting read-only build work and write-capable publication in different jobs allows them to use different GITHUB_TOKEN permissions. That is easier to review than testing and publishing inside one high-privilege job. It creates a handoff to design, though: which commit produced the files, which run produced the artifact, what is checked after download, and what authorizes the write? If untrusted build output is passed to a privileged job and executed as-is, splitting the jobs only changes the YAML layout; it does not cut off the influence of untrusted code.

Conversely, if one job installs third-party dependencies, runs repository scripts, and has contents: write, a least-privilege review should ask whether all that code needs repository write access. Can a read-only job build and test first, then hand an artifact with verified identity and content to a separate publication job? If the workflow cannot be split, can it remove unnecessary token permissions, pin and inspect Action versions, avoid writing credentials to logs, and restrict its triggers? The decision should follow code trust, the target of the write, and the blast radius—not the reputation of an Action's publisher.

GITHUB_TOKEN is scoped to the repository that invokes it. For cross-repository access, an extra personal access token can bring broader capabilities into the runner. The runner-security guidance recommends using the current repository's GITHUB_TOKEN where possible. If cross-repository access is necessary, evaluate a GitHub App or deploy key with only the needed repository and resource permissions. A deploy key mainly provides single-repository Git access and is not a substitute for REST or GraphQL API access. The right identity depends on the operations and required permission granularity; “permission denied” alone is not a reason to add a broad, long-lived PAT.

How can you verify a repository's actual permissions?

Start with the workflow triggers. Mark whether the job can run on push, pull_request, pull_request_target, workflow_run, or manual dispatch, and record the trust conditions introduced by each event. Then inspect the repository, organization, or enterprise Actions defaults and fork policy. Read the YAML from workflow scope down to each job, listing its permissions, uses, run, secrets, and artifact handoffs. The result should not merely say “we use least privilege”; it should state the read, write, deployment identity, and dependency inputs for every job.

In a disposable test repository, verify that required reads succeed and then attempt a write the job should not be allowed to perform. Confirm that the request is denied and preserve the trigger, run ID, permission configuration, and response. Follow repository policy, and do not turn a failed write test into a real data-changing request. Separately inspect secret delivery, whether OIDC is enabled, and runner trust: a token's inability to write does not prove those other boundaries are safe.

This article did not run these workflows or observe a repository's actual token responses. The calculation is a documented review method, not a production security certification. If a project hands build outputs across several workflows or runners, see how artifact identity can be preserved from build to publication. To examine when untrusted code can run in fork events, see the pull_request_target trust boundary.

When a permission error occurs, first list the required GitHub operation, triggering context, and code that will run; then grant only the needed scope to the job performing that operation. If one job both executes untrusted code and must write to a repository, change the execution boundary or artifact handoff first. Explicitly passing a token to one Action—or replacing it with a broader personal token—does not answer either underlying question.
