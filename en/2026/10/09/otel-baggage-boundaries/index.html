Why Should Customer Email Not Go Straight into OpenTelemetry Baggage?

Baggage is designed to propagate request context; the risk comes from the same mechanism. Separate propagation, telemetry storage, trust boundaries, and personal identifiers.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-27 · Estimated read 19 min
Translations
zh-CN en

Article

Key takeaways

  • Baggage is request-associated key-value context that commonly propagates with outgoing requests; it is separate from span, log, and metric attributes, which require explicit mapping or a processor.
  • Incoming baggage can be caller-supplied, and the format provides no integrity proof; do not use its user, tenant, or role values as authentication or authorization evidence.
  • Define allowed fields and removal rules at every trust boundary, then inspect real paths such as auto-instrumentation, manual clients, retries, and asynchronous handoffs.

Baggage is useful because it propagates context across services; customer email is risky for the same reason: automatic instrumentation can carry the request header to downstream services that were not meant to receive it. OpenTelemetry Baggage is key-value context attached to a distributed request. It is neither an authentication credential nor inherently a log or span field. Deciding whether a value belongs there requires separate answers to three questions: which services will see it, whether it crosses a trust boundary, and which components will write it into telemetry backends. This is a design analysis; no customer traffic, SDK configuration, or telemetry backend was inspected.

Separate propagation from storage

The OpenTelemetry Baggage documentation describes Baggage as a key-value store that lives alongside context and can be passed across services and processes. It also states that Baggage is not automatically associated with span, metric, or log attributes. To make a value appear in those telemetry attributes, code must read and add it, or a configured language implementation such as a Baggage Span Processor must do so. “The header travels through the request chain” and “the email is stored in every trace” are different data paths. Inspect both rather than answering one question with assumptions about the other.

An incoming request can have context extracted from its carrier, and a later outgoing request can have context injected into its carrier. The OpenTelemetry Propagators API defines Inject and Extract operations for writing values to and reading values from a carrier; HTTP headers are one common carrier. The W3C Baggage specification defines the baggage HTTP header and recommends that receiving systems pass it to downstream requests. It also allows receivers to add, update, or delete fields by agreement. These are protocol capabilities and recommendations, not proof that a particular team has enabled automatic propagation. Actual behavior depends on language SDKs, propagator composition, client interceptors, and mesh configuration.

Draw a path such as: an external request enters a gateway, the gateway calls service A, A calls service B, and B calls an email provider. Instrumentation in A or B may also read Baggage and add it to a span. At every arrow, ask two questions: which headers accompany this request, and which values does observability code copy into telemetry? If an email exists only between the edge and A, it could still land in A's access logs. If HTTP instrumentation injects Baggage on outgoing calls, the provider could receive it too. Conversely, without a configured propagator or explicit mapping, Baggage may not reach the backend a team expects. Assess the actual components instead of generalizing that “OpenTelemetry always does this by default.”

Email, correlation IDs, and authorization identities are different fields

Raw email is directly identifying, searchable, and easy to copy into error messages, proxy access logs, or debugging exports. Putting it into propagating context means tracking each consumer's access, retention period, export path, and deletion responsibility. Even if the telemetry backend has restricted access, the value may first pass through services or vendors outside the same controls. The risk comes from copies in transit and later reuse, not only from whether the trace UI displays it.

Hashing an email does not automatically make it anonymous. Email spaces are often guessable, and a stable hash can correlate the same person across requests. If an organization still has a mapping or can try candidate values, the result can remain identifying or sensitive. Treat hashing as a specific pseudonymization transformation with decisions about key management, scope, rotation, and authorized lookup—not as a universal redaction switch.

A random, single-request ID is often better suited to correlating events inside one request path, but it still needs an owner, a rule for replacing caller-supplied values at the edge, an expiry, and a decision about whether it appears in long-lived logs or user-visible responses. A stable account or user ID supports analysis across requests. The OpenTelemetry concept documentation even uses user identifiers to illustrate how Baggage can help downstream analysis. That example demonstrates a possible mechanism; it does not mean a raw personal identifier is appropriate for every path, backend, and access policy. Stable identifiers also create cardinality, long-term correlation, and expanded-access costs.

A bounded category such as a validated plan_tier=standard may be easier to aggregate than an email, provided the category itself does not reveal information that should remain private and the caller cannot arbitrarily set it. If the value affects price, tenant isolation, or business priority, an observability field cannot be its authority. Identity and resource permissions must come from verified identity and server-side policy. Baggage can be caller-supplied, transformed by middleware, or deleted downstream; it cannot prove who someone is or what they may access.

Remove data at trust boundaries instead of relying on key-name etiquette

The W3C Baggage specification warns that the header may contain sensitive information. Application owners should avoid storing confidential information there or ensure it is absent from requests crossing trust boundaries. The specification also calls for assessing header abuse and testing all code paths that send Baggage. Its interoperable format limits require propagation when the resulting header contains at most 64 members and is at most 8192 bytes. These are format and interoperability boundaries, not privacy or security thresholds. A particular proxy may have a lower configured header-size limit.

Maintain an allowlist rather than relying only on a list of forbidden key names. For each field, record where it originates, its business meaning and sensitivity, whether it may reach a third party, whether it may be added to spans, logs, or metrics, which team owns it, and how it is removed. Enforce policy at boundaries: accept only permitted keys at ingress, retain only those needed by internal services, and strip the rest before requests to an external provider. Removing Baggage need not mean rejecting the entire business request. If an outbound operation truly needs an email, pass it through an authorized business parameter or controlled credential channel instead of forwarding the entire request context.

“Delete it once at the gateway” may still be incomplete. A background job may restore context from a queue, another runtime may use a custom HTTP client, retry logic may reconstruct a request, or a service mesh may forward the header separately. W3C permits adding, updating, and deleting entries, but an application still needs policy coverage for every carrier and client. The format does not automatically recognize that a key contains an email address.

Verify the policy with a falsifiable test matrix

The following is a proposed validation plan, not an executed test. Start with a dedicated synthetic field such as review_marker=synthetic-7f3; do not use real email or customer identifiers in a rehearsal. Send a controlled request through ingress, then exercise synchronous HTTP calls, retries, a queue task, and a test external endpoint. Collect headers and attributes at ingress, inside services, at egress, and in the telemetry backend. State the expected result for every path: which internal components may see the marker, whether an external destination must not, which spans or logs may retain it, and whether metrics must omit high-cardinality identifiers entirely.

Counterexamples reveal a policy that only works on paper: send a forged tenant field from the client; bypass a shared interceptor with a legacy client; make a retry construct a fresh HTTP request; hand a task across processes or languages; and then check whether the marker appears in outbound headers or queryable telemetry. Also observe how proxies, SDKs, and applications handle malformed or oversized headers. Record component versions and propagator configuration with each run, alongside expected and observed values for inputs, egress, spans, logs, and metrics. These tests were not performed for this article, so no existing policy is claimed to prevent leakage.

If an investigation truly needs to correlate a request with a person, prefer a short-lived, narrowly scoped random correlation key in telemetry and let an authorized operator resolve it in a controlled business system. This still needs access auditing, retention, and key management, but avoids copying raw email throughout every downstream service. If a stable identifier is indispensable, document why, who can resolve it, which boundaries allow it, how it is rotated or removed, and what happens after exposure. The choice is not “never propagate any user ID”; the costs differ by field and boundary.

Review propagation and telemetry handling as two tables. The first records extraction, retention, mutation, and stripping at every hop. The second records when Baggage becomes a span, log, or metric attribute, along with access and retention boundaries. Incoming context must not replace object-level authorization; review this alongside object permissions and IDOR. Observability context explains where a request went. It should not prove that the caller can access customer data.
