Both Transactions Committed: Why Did the Business Invariant Fail?

Use a PostgreSQL 18 staffing invariant to explain write skew, compare constraints, coordination locks, and Serializable, and show how to retry SQLSTATE 40001 safely.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-27 · Estimated read 24 min
Translations

Article

Key takeaways

  • Atomicity says one transaction commits or rolls back as a unit; it does not guarantee that concurrent transactions collectively preserve every cross-row invariant.
  • PostgreSQL Repeatable Read still permits serialization anomalies. Serializable rejects executions it cannot prove equivalent to a serial order, so applications must handle 40001.
  • Retry 40001 by repeating the full transaction and its decisions. Constraint conflicts are not all retryable, and database rollback cannot undo external side effects.

If two transactions each see “one other person is still on duty” and each takes itself off the rota, both may commit while leaving nobody on duty. Atomicity does not turn a cross-row rule into a concurrency constraint. First ask whether the rule fits UNIQUE or EXCLUDE; otherwise consider rechecking under a shared coordination lock or using PostgreSQL SERIALIZABLE, with a full retry path for an aborted transaction. This analysis follows PostgreSQL 18 documentation. The rota and SQL below are hypothetical examples, not results from a database concurrency test.

How two valid transactions can be wrong together

Suppose a team has two on-call people and the rule is “at least one person must remain on duty.” The table contains two rows, A and B, both with on_duty = true. Two requests arrive almost together. T1 reads a count of two and decides to mark A off duty. T2 also reads two and decides to mark B off duty. They update different rows, so there is no write-write conflict on the same row. If the isolation level lets both proceed from their earlier reads, both updates can succeed and leave the rota empty.

Writing the interleaving makes the gap clearer than asking only whether a transaction is atomic:

T1: BEGIN; SELECT count(*) -> 2
T2: BEGIN; SELECT count(*) -> 2
T1: UPDATE rota SET on_duty = false WHERE person = 'A'
T2: UPDATE rota SET on_duty = false WHERE person = 'B'
T1: COMMIT
T2: COMMIT

The row names and values are illustrative, not a test log. Each transaction performed its own read, update, and commit as a unit. The problem is that the rule relates two rows; two different UPDATE statements do not automatically become a conflict on one shared resource. Atomicity asks whether one transaction's writes take effect together. It does not answer whether a group of concurrent transactions has an outcome equivalent to some serial ordering. The transaction isolation manual calls the latter kind of inconsistency a serialization anomaly (PostgreSQL 18 transaction isolation).

Isolation changes the outcome. By default, each PostgreSQL READ COMMITTED statement takes a snapshot at its start, so successive statements can see different committed data; repeating a check inside one transaction does not by itself lock an aggregate condition. REPEATABLE READ keeps a transaction on one snapshot and prevents nonrepeatable reads, but PostgreSQL explicitly says that serialization anomalies can still occur at this level; see the isolation-level table. The write-skew pattern above is a possible snapshot interleaving: both transactions read the same state and write different rows, so a concurrent row-version update does not make them collide. Do not assume that the same-named isolation level in another database has PostgreSQL's behavior.

At SERIALIZABLE, PostgreSQL tracks read-write dependencies among concurrent transactions. If their committed combination cannot correspond to any serial execution order, the server rolls one transaction back with a serialization failure. The guarantee is serial equivalence for successful commits, not that every transaction will commit. Applications must treat the abort as a normal concurrency-control path, not as database corruption or a transient network error.

Choose a mechanism from the shape of the rule

A rule that depends only on the current row is often best expressed with NOT NULL or CHECK, such as requiring an end time to follow a start time. The constraints manual says a CHECK constraint cannot safely read other rows to enforce “at least one person is on duty in the table” (PostgreSQL 18 constraints). Even if a function that behaves like a cross-row check appears to work on inserts, later changes to other rows can invalidate the rule, and dump/restore can expose the problem. The official constraints manual says that CHECK conditions should depend only on the row being inserted or updated.

For “a code must be unique within a tenant,” let the database enforce UNIQUE (tenant_id, code); a partial unique index may fit when uniqueness applies only to active rows. For pairwise restrictions such as non-overlapping ranges, consider an EXCLUDE constraint. These mechanisms enforce the rule at the write boundary instead of relying on every caller to remember a preflight query. Account for NULL semantics, whether the constraint is deferrable, and how an application maps the resulting error into a business conflict. A constraint is not a universal retry switch.

“At least one person remains on duty” is an aggregate cross-row rule that an ordinary unique constraint cannot directly express. One option is a unique coordination row that represents the entry point for rota changes. Every join or leave operation locks that row in the same transaction, then rereads the current rota and checks the invariant before changing a person record. With READ COMMITTED, after a transaction waits for that lock, its next read statement gets a new statement snapshot. This depends on every write path following the same protocol. A background job that bypasses the coordination row, or code that reads before locking and reuses the old decision, breaks the protection. A single global lock can serialize too much; different groups can use different coordination keys to avoid unrelated waiting.

Another option is to run the whole business transaction at SERIALIZABLE, keeping the read, decision, and update together. This avoids manually reasoning about every read-write interleaving, but adds SSI dependency tracking and possible retries. A simple hot write path may be easier to observe with an explicit coordination row. If the invariant spans complex reads and many call sites, SERIALIZABLE may be easier to audit. Without real traffic and conflict rates, there is no basis for claiming which is faster. The manual notes that predicate-lock granularity, connection-pool size, and transaction length can affect serialization failures; a test result is not a production-capacity measurement.

A 40001 retry must repeat the decision

PostgreSQL uses SQLSTATE 40001 for serialization failures (see serialization failure handling). Once a transaction has been aborted, retrying only its final UPDATE is not enough: the earlier SELECT, user choice, quota check, or inventory check may have depended on a stale snapshot. The retry unit is the complete transaction logic: begin a fresh transaction, reread, make the decision again, then issue the corresponding writes. In the rota example, if a retry discovers that only one person remains on duty, the application should reject the leave request or ask for a replacement. It should not replay the previous on_duty = false blindly.

Bound the number of attempts and total elapsed time, and use bounded backoff. Immediate retry loops under contention can add pressure to the same hot spot. Once the retry budget is exhausted, return an understandable recoverable result or put the operation into a queue instead of holding a connection indefinitely. Logs can record the SQLSTATE, business-object key, attempt count, and final outcome without returning parameters, personal data, or internal SQL to the user.

Do not classify every constraint error as “retryable.” PostgreSQL documentation says that retrying 23505 or exclusion violation 23P01 can be appropriate in specific generated-key races, but those errors can also represent persistent conflicts or an intentional business rejection. Retry only when the conflict arose from a concurrent read-then-write decision and the complete business logic can choose again. For example, two requests may both check that a generated identifier is unused and then insert it. The unique constraint lets one fail, but the application must generate a valid alternative; mechanically replaying the same INSERT cannot help. If a user explicitly requested an identifier that is already taken, returning a conflict can be the correct result.

Explicit locks also need a failure path. A deadlock can arise when transactions lock multiple resources in inconsistent orders; PostgreSQL detects it and aborts one participant (see explicit locking). If a lock strategy is chosen, define a consistent lock order, keep transactions limited to the necessary work, and use bounded full-transaction retries for deadlock errors. An advisory lock acquired at transaction scope is released at transaction end. Session-level advisory locks are not automatically released by a rollback, so they require careful connection-lifecycle handling.

A database rollback cannot undo an outside effect

Suppose a transaction updates the rota and directly calls a notification service. If the database later aborts on 40001, the outside notification is not retracted; retrying the transaction may send it again. A safer pattern is to write both the business state and a pending event record in one database transaction, then deliver the notification after commit and make delivery idempotent by event ID. The database can atomically store “state changed” and “notification intended,” but the design still needs recovery for a process crash after delivery, duplicate delivery, and dead-letter handling. See the transactional outbox's boundaries and recovery path.

For payments, email, or webhooks, a provider idempotency key should be associated with the retryable business operation, and the provider's actual scope and retention period must be checked. If the provider offers no idempotency contract, do not assume that an HTTP timeout means the request was not processed. Retrying means repeating a decision, not treating an irreversible side effect like ordinary SQL.

How to validate which rule is protected

Start with an invariant that can be checked: “at least one on-call person remains.” List every path that can change the rota, including the user API, background jobs, import scripts, and operational commands. Then prepare two transactions behind a synchronization barrier so both first read the same initial state and try different updates. For REPEATABLE READ, the test asks whether the declared isolation level still permits that interleaving. For SERIALIZABLE, it checks that a resulting 40001 is recognized and that a retry rereads and recomputes the decision. For a coordination-row design, it must show that every writer waits on the same lock and that the second transaction rechecks against the new state after obtaining it.

Check the database result and the user-visible outcome: was a rejected operation reported as successful, did a retry exceed its budget with a clear status, was a notification duplicated, or was a connection held during backoff? Concurrency tests should run against the PostgreSQL version and transaction wrapper used by the project. An ORM may start transactions, retry automatically, or hide an error; a deployment proxy can affect connection behavior. None of the proposed schedules or checks in this article was executed, and no implementation is claimed to have passed a test or demonstrated a performance result.

Three questions help choose a mechanism: Can the rule be expressed as a row-local, unique, or exclusion constraint? If not, which reads and writes must share a coordination point? Can the caller safely repeat the complete decision after an abort? If those questions have no answers, raising the isolation level or increasing the retry count only hides a design gap. If retries can cause outside effects, first define stable event identity and recovery. If the conflict is a real collision between user choices, returning a conflict may be more correct than retrying. For how query-plan evidence affects the operational path, see the PostgreSQL row-estimate and plan-validation boundaries.
