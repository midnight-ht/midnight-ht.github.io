A Query Is Slow: Check Row Estimates Before Adding an Index

Locate row-estimate errors and actual execution work in PostgreSQL 18 before choosing an index or query rewrite.

Updated 2026-10-09 · Estimated read 6 min

Article

A slow query is not automatically a missing-index problem. Locate the earliest gap between estimated and actual rows, then examine scans, joins, sorts, and waiting. EXPLAIN ANALYZE executes the query, so establish a side-effect and resource budget first. No production performance measurements were taken for this article.

Cost is not elapsed seconds

The PostgreSQL 18 EXPLAIN guide distinguishes planner estimates from execution information and explains that ANALYZE runs the query. A cost value compares candidate plans; it is not directly request milliseconds or a portable benchmark across differently configured databases.

Consider a hypothetical query filtering orders by customer and date before joining details. Underestimating the number of matching orders can make a chosen join strategy expensive. Investigate statistics, correlated data, and predicates before adding indexes indiscriminately.

Follow the first divergence

Read upward from base scans and record estimated rows, actual rows, and loop counts, including the per-execution meaning of repeatedly executed nodes. A cheap operation repeated many times can account for substantial work. Do not judge only its per-execution time or add parent and child timings as independent costs.

Preserve parameters, table scale, database version, and concurrency conditions. Different customers, time ranges, and cache states can produce different behavior. Redact sensitive values while retaining distribution-relevant ranges or categories.

Sequential scans can be reasonable when a large part of a table is required. Forcing an index changes access cost without shrinking the result. A narrow predicate reading many irrelevant rows warrants checking index fit, expressions, and type conversions, but that is an investigation direction rather than a diagnosis of an unseen plan.

Own the execution risk

EXPLAIN ANALYZE on a write statement really executes it. A rollback wrapper is not a complete safeguard for sequences, external functions, or other effects outside ordinary transactional rollback. Read queries also consume resources. Production collection needs authorization and stop criteria.

When a safe collection window is unavailable, inspect a plain EXPLAIN and reproduce in a controlled environment, preserving environmental differences. Application connection-pool queues and database waits may also contribute beyond what a plan explains.

After a change, compare representative parameters, plans, and business metrics under documented conditions. One warmer-cache run does not establish a fixed improvement percentage. Observe write costs too.

Choose one important reproducible query, identify its earliest material estimate error, and propose a falsifiable change. If that change is an online index, include concurrent build waits and cleanup in the release plan.
