A Slow Query Needs Evidence Before It Needs an Index

Find the earliest material row-estimate error in a PostgreSQL plan, then decide whether statistics, query shape, or an index is the right fix.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-27 · Estimated read 20 min
Translations

Article

Key takeaways

  • rows is the planner's estimate of a node's output, not the number of rows it scanned; with repeated loops, actual rows are generally shown as a per-execution average.
  • Correlated predicates on one table may need refreshed or extended statistics; PostgreSQL extended statistics currently do not repair join selectivity estimates.
  • EXPLAIN ANALYZE executes the statement, and its usual timing does not include network delivery to the client; document the measurement boundary.

A slow query is not automatically a missing-index problem. Find the earliest material row-estimate divergence in the plan tree, then determine whether it comes from stale statistics, correlation among columns on one table, query shape, or join estimation. An index belongs on the candidate list only after evidence shows that the access path is a major cost. PostgreSQL 18 is the explicit baseline here, and PostgreSQL 19 documentation was also checked. The orders example and SQL are diagnostic templates: they were not run against a database, and no production performance data was collected.

Read row counts before treating cost as elapsed time

PostgreSQL EXPLAIN output is a tree of plan nodes. At the bottom are usually table scans; nodes above them may filter, join, aggregate, or sort. A node's rows value is the planner's estimate of how many rows it will emit, not how many it will scan. A full table scan can output only a few rows while still inspecting many records. “Few estimated output rows” therefore does not mean “little scan work.” The PostgreSQL 18 EXPLAIN guide also explains that plan cost is an abstract unit used to compare candidate plans, not a direct reading of request milliseconds.

On the first pass, read from leaf nodes upward. Record the estimated rows at important filter nodes, find the earliest material mismatch, and trace how downstream choices depend on it. Estimates are approximate by design; a difference of one or two rows is usually not an incident. A mismatch spanning orders of magnitude, or a small operation repeated many times, deserves investigation. Do not focus only on the top-level row count: an error can begin with a lower-level predicate and compound before a nested loop, hash build, or sort.

With ANALYZE enabled, PostgreSQL executes the statement and reports actual output rows and run time. For nodes with loops greater than one, actual rows and time are generally displayed as per-execution averages; use the loop count to understand cumulative work. An inner index scan returning one row per call can still be expensive when called thousands of times by an outer loop. Node times are inclusive of work in the plan tree, so do not add a parent and its child timings as though they were independent. The EXPLAIN documentation notes that comparing estimated and actual rows is often more useful for finding estimation problems than comparing cost alone.

A LIMIT is a counterexample to simplistic comparison: a node may display its estimate as if run to completion while the upper LIMIT actually requests only a few rows. That display difference is not automatically a cardinality error. Read execution counts, filters, and upstream stop conditions before raising a statistics target because two row numbers differ.

Where can the estimate go wrong in an orders query?

Consider a hypothetical multi-tenant orders table. A query filters by tenant_id and status, sorts by creation time, and returns the newest page. For some tenants, most orders may be open; for others, open orders may be rare. The two columns are not independently distributed. Ordinary per-column statistics can know the approximate frequency of tenant and status values while missing how many rows remain for a particular combination. If the planner underestimates that combination, it may choose a downstream strategy suited to a small result but expensive for the actual larger set.

First ask whether the statistics can represent the current data. Catalog values such as pg_class.reltuples and relpages are not updated on every write. ANALYZE and VACUUM ANALYZE update statistics, but commonly use samples, so the result remains approximate. The PostgreSQL 18 planner statistics guide recommends inspecting the more readable pg_stats view instead of directly reading the privilege-restricted pg_statistic catalog. A plan can change with table scale, distribution, or a later ANALYZE without anything being “wrong” in the SQL text.

In an authorized non-production environment, or a collection window whose cost has been assessed, you might run targeted ANALYZE orders (tenant_id, status) and then generate a plain plan for the same SQL and representative parameter classes. If the estimate changes materially, stale statistics or sample representation may have contributed. If it remains systematically low, investigate whether same-table column correlation is the cause. Do not describe one improved plan after ANALYZE as a stable speedup; it only shows that the estimate changed under those collection conditions.

When strongly correlated columns on one table are the source, extended statistics may be appropriate. For example:

CREATE STATISTICS orders_tenant_status_stats (dependencies, mcv)
ON tenant_id, status FROM orders;
ANALYZE orders (tenant_id, status);

This is a proposal for team review, not a command executed for this article. dependencies models dependencies among strongly correlated columns; mcv records common value combinations. Creating the statistics object declares what should be collected; ANALYZE must collect the data, and sample size and modeling cost belong in the decision. The official docs advise limiting dependency statistics to column groups with strong correlation to avoid unnecessary planning and ANALYZE overhead. A crucial boundary: the PostgreSQL 18 and 19 CREATE STATISTICS manuals say that extended statistics are not currently used for join selectivity estimates. If the first major divergence appears at a cross-table join, adding single-table dependency statistics is not a general fix.

Match the repair to the layer where estimates diverge

If the mismatch starts at a single-table filter node, check that table's statistics freshness, common values, and histogram, then ask whether multiple predicates are correlated. If single-table estimates are reasonable and the join node is where the plan first diverges, record join-key distributions, actual input cardinalities, and skew on both sides. Do not reduce a join-estimation problem to “we need another index.” Extended statistics currently do not cover join selectivity, so query structure, data model, and representative parameter behavior need separate investigation.

If the mismatch appears only for particular tenants or date ranges, check parameter distribution and prepared-statement plan selection. PostgreSQL 19's EXPLAIN documentation includes a GENERIC_PLAN option for inspecting a generic plan that does not depend on parameter values. It cannot be combined with ANALYZE, so it is not execution evidence. Confirm prepared-statement behavior and supported options for the target major version; one parameter's plan is not a proxy for every request.

If estimated rows are close to actual rows but the scan still reads much irrelevant data, examine whether an index's column order, expression, type conversion, sort order, and LIMIT match the predicate. A sequential scan may be the right choice when the query needs much of a table: reading pages in order can be cheaper than many random accesses. An index does not reduce the number of rows the query must return, and it adds storage and write maintenance. Weigh both sides instead of labeling every Seq Scan a defect.

Which measurement boundaries remain outside the plan?

EXPLAIN (ANALYZE, BUFFERS, SETTINGS) can put actual rows, loop counts, buffer hits/reads, and relevant planner settings in one evidence artifact. Upper-level BUFFERS values include child work, so do not add the same buffer counts repeatedly across the tree. Before collecting a plan for a read that may scan a large table, estimate resource use, constrain the parameter range, and define stop conditions.

EXPLAIN ANALYZE on a write statement really runs the write. A rollback wrapper is not guaranteed to undo sequence advances, external function calls, and every effect outside ordinary transactional rollback. Read queries also consume CPU, memory, and I/O. Collection needs authorization and isolation. Record the database major version, parameter class, statistics time, concurrent load, and cache state. Redact sensitive values without deleting the information that explains data distribution.

Plan execution time is not the full request time seen by a user. Results are not normally sent to the client, so network transmission is outside EXPLAIN ANALYZE timing. Output conversion may also be unmeasured by default. PostgreSQL 19's EXPLAIN adds a SERIALIZE option for measuring output serialization, but it still does not deliver the result and therefore does not measure network cost. The application may also wait in a connection pool, proxy, or retry queue; use application-side traces to add that evidence.

Useful validation is not “the plan screenshot looked faster after adding an index.” Preserve before-and-after plans, the same representative parameter classes, table scale, sampling, and load conditions. Check whether row-estimate error shrinks, buffer reads and execution time change, and write costs move separately. Each hypothesis should be falsifiable: if ANALYZE does not correct the mismatch, do not keep blaming stale statistics; if extended statistics improve a filter node but not a join node, inspect the join separately; if row counts are close and the request is still slow, investigate scan work, sort, serialization, network, or application waits. None of the query or validation steps proposed here was executed.

Only put an index on the shortlist when evidence says access-path cost is a major part of the problem. If an online index is selected, include concurrent-build waits, failure states, and acceptance checks in the release plan. That turns “guess an index” into a reviewable causal decision without turning one changed plan into an unsupported performance claim.
