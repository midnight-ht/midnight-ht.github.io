Database Slowness Restarts Every Pod? Match Each Probe to Its Action

Kubernetes liveness failures restart containers, readiness failures make Pods temporarily ineligible for Service traffic, and startup probes protect initialization. Choose by failure location and recovery action instead of turning a shared dependency outage into a restart storm.

Key takeaways

  • Liveness asks whether a process is in a state that may require a restart; readiness asks whether this Pod can serve the requests routed to it now; startup delays the other checks during initialization.
  • A database failure is not automatically a container-recovery problem. Marking every Pod unready can also leave a Service with no eligible backends, so degraded behavior and request paths matter.
  • Validate container restarts, Pod readiness, Service EndpointSlices, and real request outcomes together. The verification plan here was not executed and is not a cluster test report.

When a database slows down, the liveness probe usually should not query it directly. A liveness failure causes the kubelet to terminate and restart a container; a readiness failure means that a Pod should temporarily stop receiving Service traffic; and a startup probe protects a slower initialization period. Choose among them based on whether the fault is local to the process or shared with a dependency, which requests the application can still handle, and what Kubernetes should do when the check fails. This article discusses the design using Kubernetes documentation checked on 2026-11-27; no cluster was created and no fault injection was run.

Similar names, different control actions

Think of a probe as a control signal to the kubelet, not a comprehensive service-health report. A liveness probe checks whether a container remains in a state where it can continue working. Once the configured failure condition is reached, the kubelet kills the container, and the Pod's restart policy governs what happens next. The Kubernetes probe configuration guide describes liveness as a way to handle an application that has reached a state from which it cannot recover on its own. Examples might include a deadlock, an event loop that has stopped making progress, or corrupted local state that a restart could clear.

A readiness probe does not restart the container. A failed check makes the container and Pod report not ready, so a Kubernetes Service stops directing new traffic to that Pod. It answers “Can this instance serve the requests routed here right now?” rather than “Is the process alive?” The Pod lifecycle documentation describes the Ready condition in terms of whether a Pod can serve requests and should be added to the load-balancing pools of matching Services. Readiness changes propagate through the control plane and EndpointSlice path; they are not a synchronous, zero-latency switch.

A startup probe covers a different period: the application may still be loading configuration, restoring local data, or completing initialization, and should not be killed by a liveness timeout intended for steady state. Kubernetes documentation explains that liveness and readiness checks are delayed until a startup probe succeeds. You can express the startup budget as failureThreshold × periodSeconds. The documentation's example uses 30 failures at 10-second intervals, or up to 300 seconds. That explains the fields; it is not a production default. Once startup succeeds, the liveness probe takes over to detect later deadlocks.

The three signals therefore answer three different questions: Is initialization still underway? After initialization, is the process locally unrecoverable without a restart? While it can continue running, should it receive current traffic? If all three are implemented as “call an HTTP endpoint that checks the database,” the code does not account for the cost of the action above it: the same 500 response may lead to restart, traffic removal, or a startup decision.

How a slow database can become a restart storm

Consider a clearly hypothetical order service. Every instance's /health handler synchronously queries the database. The database becomes slow because of connection exhaustion or high latency, and the probe times out. If the same result drives liveness, several instances may fail around the same time and restart. New processes then open connections, load caches, and warm thread pools. That work may increase pressure on a dependency already struggling. Restarting clears local process state but does not repair database capacity or a network fault. This is a possible feedback path, not a customer incident we observed.

The failure can compound if recovery requires the application to reload a large state. A new container may not have finished initialization before liveness checks begin; a second failure starts another restart. Repeating the attempt adds startup work to the busiest period without adding recovery capacity. If every Pod uses the same probe schedule, their retries may also cluster. Whether that produces a synchronized peak depends on probe fields, restart backoff, scheduling, connection pools, and application initialization. A manifest alone cannot establish that it will happen.

Ask what each failure will make another component do. If the event loop is deadlocked while the database is healthy, a liveness failure and restart may help. If the database is briefly unavailable while the process can still serve cache hits, liveness should not fail solely because the database timed out. If a critical operation such as payment confirmation depends entirely on the database, the application may need to report not ready so new requests are not sent to an instance that cannot fulfill the contract. In that third case, if every Pod shares the database and all become unready, a Service may have no Ready backend. Removing those Pods can prevent invalid writes, but it cannot make the service available. Clients, upstreams, and product behavior still need defined timeouts, retries, degradation, or explicit errors; operations also need to treat “no eligible backend” as an alertable outcome.

Readiness should not mean every dependency is green

The routing role of readiness makes the actual request paths the right starting point. If a service has a read path backed by cache and a write path that depends on a database, one Ready bit cannot say “reads work, writes do not.” One choice is to mark the entire service unready and accept that all traffic leaves. Another is to keep serving requests that can be handled safely, return a defined degraded result for those paths, and reject operations that cannot complete. If the two request classes require different backend capabilities, the service or routing boundary may need to be split. The choice depends on interface semantics, consistency, and load-balancing capability; it should not be made just to keep the Pod list green.

This is why database health is not automatically a liveness criterion. Readiness may depend on an external system, but it needs to answer a narrower question: can this instance produce an acceptable result for the requests it is expected to receive? If each probe performs an expensive query, the check itself adds database load. If dependency state is cached, record how old it may be and how long it can take for a recovered dependency to make the Pod Ready again. Application-level circuit breaking, rate limits, and degradation for individual features are usually easier to explain than using one global probe as a substitute for all error handling. Probes are not business retries or a circuit breaker.

Validation should confirm that a probe causes the intended action, not merely that an endpoint returns 200. The following is a proposed plan that has not been executed: in an isolated environment, first record which dependencies and results belong to each important request. Then separately cause a local event-loop stall, refused database connections, elevated database latency, a slow application startup, and database recovery. Before each test, state the expected container restarts, Pod Ready value, corresponding Service EndpointSlice changes, request success/failure category, and database connection trend. If an external dependency fault increases restart counts, inspect whether liveness depends on that dependency. If Ready becomes false while a safe business path remains available, check whether the readiness boundary is too broad. If every instance leaves routing, confirm whether this is an intentional protective action or an unintended outage amplifier.

In a real cluster, inspect Unhealthy and Killing events from kubectl describe pod, then compare kubectl get pods with kubectl get endpointslices -l kubernetes.io/service-name=<service> in the actual namespace. These commands are a verification path, not commands run for this article; their output is not presented as evidence. How quickly EndpointSlices reflect a change, when clients switch, and how existing connections drain still need validation against the target cluster version and network components. Also inspect probe latency, failure reasons, and frequency. A restart total alone cannot distinguish a deadlocked process from a dependency timeout, slow startup, or an overly short probe timeout.

A timing budget is not a recovery guarantee

periodSeconds, timeoutSeconds, failureThreshold, and initialDelaySeconds combine to determine when a condition is detected. Increasing liveness timeouts to accommodate slow startup also delays detection of a steady-state deadlock. Using a startup probe separates the initialization budget from the desired steady-state response. Derive those budgets from the target image, resource limits, observed cold-start and recovery distributions, and an acceptable service recovery time; add margin for a stated reason. An official example shows how fields interact, but it cannot prove that your container needs 300 seconds.

Probes can also create work. An endpoint called every few seconds that runs a complex SQL query or checks several dependencies becomes another source of requests in the service path. Keep probe handlers bounded and predictable. Do not expose internal hostnames, credentials, or detailed database errors through a public health response; put sensitive causes in controlled logs and events. If liveness failures recur soon after each restart, investigate whether the recovery action addresses the cause instead of increasing thresholds indefinitely.

Start by drawing the chain “probe result → kubelet or Service action → user request result → dependency pressure.” Then assign the signals: startup protects initialization; liveness is for a local failure that a restart could repair; readiness is for an instance that cannot handle its routed requests, with an explicit plan for what happens if all replicas fail readiness. After release, observe restarts, Ready conditions, and endpoint changes by fault category to check that behavior matches the design. In-flight requests and termination grace periods belong to a separate recovery stage; see the graceful termination budget as a related follow-up.
