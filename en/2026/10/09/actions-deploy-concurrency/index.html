Why Can an Old Run Still Overwrite a Test Site When Branches Use Separate Locks?

GitHub Actions concurrency groups coordinate only same-named runs in a repository. Map the group to shared environments, then distinguish pending replacement, cancellation, and queue:max semantics.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-26 · Estimated read 18 min
Translations

Article

Key takeaways

  • Two branches can still race on one test environment when each uses a different branch group; choose a key that reflects the contested resource.
  • By default, a group has at most one running and one pending run. A new run replaces the older pending run; cancel-in-progress also cancels the current run.
  • queue: max permits up to 100 pending runs, and additional arrivals are canceled when full; ordering follows when a run began waiting, not workflow dispatch time.
  • A group coordinates only runs in the repository that use the same group. Canceling a run does not undo writes already made to an external system.

Branch names are not always the right key for a deployment lock. If dev and hotfix can both write to the same test site, separate branch groups put them in different concurrency groups. GitHub Actions will not infer that the two groups modify one environment. First identify which runs write the same target, then decide whether the goal is to keep only the latest version or to execute every approved deployment in turn.

This explanation follows GitHub’s official workflow-concurrency documentation accessed on November 26, 2026. The site and timing examples are hypothetical, not observations from a real deployment. No workflow, cancellation, or environment deployment was run for this article.

What does a concurrency group actually serialize?

You can set concurrency at the workflow or job level. GitHub says that among workflows or jobs in the same repository using the same concurrency group, at most one can run at a time. A group can be a string or an expression built from allowed contexts. Its scope is the set of runs that use that group; it does not discover every writer to a cloud environment.

That distinction determines the group key. For example, an expression that includes the branch ref gives dev and hotfix separate groups. This is useful for limiting duplicate builds per branch or keeping only a newer preview from the same branch. It does not by itself protect a test environment that multiple branches share. When all deployments targeting staging use one stable staging group, those runs can coordinate with one another.

Group names are case-insensitive, so staging and Staging are the same group. Different workflows can also use the same group name. GitHub warns that if they should not cancel one another, the group should include workflow identity. Make the decision in both directions: workflows writing the same staging target should share a group; workflows in one repository with different targets should not collide because their names happen to match.

A concurrency group is not a cross-repository lock. It does not stop a console operation, another CI platform, or a workflow that does not declare that group from writing the environment. If several repositories manage one shared target, use a deployment platform queue, environment lease, or version-arbitration rule that covers those writers. GitHub concurrency only coordinates participating runs in the same repository and group.

Why is the default behavior not a complete release queue?

When a group already has a running job, a new run becomes pending. By default, only one run can be pending. A later arrival cancels the existing pending run and replaces it. If cancel-in-progress: true is set, the current running task in that group is canceled as well. This fits a “the old preview no longer matters; move toward the newest commit” policy, but it does not mean every approved version will be published.

GitHub provides queue: max to let more pending runs wait, up to 100. When the limit is reached, additional runs are canceled. The queue is FIFO according to when each run started waiting on the concurrency group; it is not guaranteed to follow the time workflows were dispatched, because runs may reach the waiting point at different times. queue: max cannot be combined with cancel-in-progress: true: one setting preserves queued work while the other asks to cancel the run in progress.

Capacity and delivery promises must be considered together. If a preview only needs to reflect the latest build, replacing the single pending run may be appropriate. Migrations or external side effects that must complete should not be put in a pipeline-wide “cancel when a new version arrives” policy. Even with queue: max, cancellation remains possible beyond 100 pending runs, and FIFO does not mean commit-time order. For a no-loss queue, strict ordering, or cross-repository serialization, use a deployment system with those guarantees instead of describing Actions’ bounded waiting queue as a durable message queue.

Should the group follow the branch or the environment?

Suppose a repository has dev and hotfix branches and both deploy to one staging environment. Grouping by ref allows them to run in parallel; a stable staging group makes them mutually exclusive. The reason to use the environment key is not that environment names are inherently safer. It is that the required invariant—only one writer to this shared target—must be expressed. If the branches deploy to isolated preview-123 and preview-456 environments, they should not be serialized by a shared environment lock.

Consider two workflows: automatic preview and manual release, both able to write staging. If their concurrency group is intentionally the same, they coordinate. If the name includes workflow identity merely to avoid accidental cancellation, they no longer protect staging from each other. One group name cannot solve both goals. Decide whether the system needs “serialize each pipeline independently” or “mutually exclude every staging writer.” Before deployment, also check that the selected commit and artifact digest remain eligible, so an older artifact does not become stale while waiting.

For a latest-only preview, cancellation can be limited to the build or temporary-preview stage. A database migration or an irreversible external request needs a stage-specific policy. A cancelled workflow label does not show that the platform rolled back. If a deploy request times out or the client disconnects, the result may be unknown rather than failed. Query the platform’s deployment ID, target version, and operation receipt before retrying; otherwise, two operators may both mistake “I did not see success” for “no write happened.”

What does a hypothetical timeline reveal?

Assume slow run A comes from an older commit and fast run B from a newer one. They use branch-specific groups on different branches, so both can run. B deploys the new page first; A uploads the old page later. B’s workflow remains green, yet staging ends on A’s version. This timeline is not a real run. It shows why “the workflow succeeded” and “the environment equals the selected commit” are different claims.

If both use one shared staging group, B waits while A runs. But if C arrives under the default pending-replacement rule, B may be canceled as the older pending run. A requirement to apply every update one by one means the default group can still drop pending work. With queue: max enabled, the team must account for the 100-pending limit, cancellations on overflow, and ordering by the time a run reaches the concurrency wait. The product promise must come first: allow replacements if the goal is for the environment to converge to the newest version; if every migration must execute, a bounded queue may be insufficient; if deployments must follow approval order, store that order and artifact identity in a separate record.

How should deployment concurrency be validated?

List every entry point that can write the target: automatic deployments from different branches, manual workflow_dispatch, reusable workflow calls, other repositories, and human operations. For each, record the target, concurrency group, whether it can be canceled, external side effects, and version receipt. A writer that does not use the group is not controlled by that lock.

In a non-production environment, a proposed rehearsal can use slow A, fast B, and a third run C. Observe whether pending runs are replaced, whether queue: max advances according to when each run began waiting, and how a new run is handled at capacity. Then interrupt the runner after a write request and simulate an unknown network result; verify that the environment version can be recovered from the platform receipt instead of redispatching based only on workflow status. This article did not perform that rehearsal; it is a validation proposal, not a reliability result.

For each deployment, connect the source commit SHA, artifact digest, workflow run ID, and deployment platform version. A health check proves that a service responds; checking its version proves whether the observed environment points to the intended commit. When reviewing this together with artifact and rollback target verification, keep three questions separate: who coordinates writes, who verifies artifact identity, and who determines actual state after cancellation. For cache provenance boundaries, see why a cache hit does not make a release trustworthy.
