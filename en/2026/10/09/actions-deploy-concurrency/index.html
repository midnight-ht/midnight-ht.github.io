Two Deployments Overlap: Should the Lock Follow the Branch or the Environment?

Coordinate deployment writers around the target environment and verify final state after cancellation or overlapping runs.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-09 · Estimated read 6 min
Translations
zh-CN en

Article

If two workflows modify the same environment, coordinate around that environment rather than locking each branch independently. Canceling an old run does not undo writes already made. Verify the deployed version afterward. No concurrent deployment experiment was executed here.

Different branches may share one target

If dev and a hotfix branch publish to the same test site, branch-specific groups can still run simultaneously. An older job finishing last may overwrite newer artifacts even while the newer workflow is green. Identify the shared resource rather than relying on workflow names.

The GitHub concurrency documentation describes workflow and job groups and their running and pending behavior. Do not assume default pending behavior retains every publication in a complete queue. Check current queue options, limits, and ordering semantics; dispatch order is not automatically execution order.

Latest-only and sequential execution differ

A preview site may only need the latest commit and permit canceling earlier work. A database migration or external side effect may not be safely interrupted. Canceling a whole pipeline can leave a migration complete while the application update is unfinished.

Separate cancelable construction from controlled environment mutation. Use a stable environment identity for the shared stage and confirm the selected version is still eligible before applying it. Cancellation, queueing, and obsolete-artifact policies should be explicit decisions.

Other repositories or tools may also write the environment. A concurrency group does not automatically coordinate every external system. A platform-level queue or version arbitration may be necessary.

Cancellation leaves an uncertain state to inspect

A canceled label does not prove uploads, database writes, or external requests rolled back. Query receipts and target state before repeating an operation whose result is unknown. Preserve commit identities, artifact digests, and deployment IDs.

Health success only proves the service responds. Connect environment evidence to the intended version and key content. A rollback likewise needs an identified, verified target.

A proposed rehearsal starts slow and fast builds, observes waiting and cancellation, and checks the final environment. It also interrupts mutation to inspect recovery. None of this was executed here; retain actual timestamps and receipts when rehearsing.

Independent tests need not be serialized. Coordinate only stages competing for the same resource, after listing every writer. Combine this with artifact and rollback verification instead of treating a green run as complete online evidence.
