Can a Timed-Out Request Be Retried? Define the Business Idempotency Boundary

Define stable intent and durable deduplication before retrying an order whose outcome is unknown.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-09 · Estimated read 6 min
Translations
zh-CN en

Article

Retry safety depends on whether repetition changes the business outcome and whether the server recognizes the same intent. A client timeout means the result is unknown; it does not prove that an order was never created. This is an order-design analysis, without payment integration or fault-injection results.

An HTTP method is only part of the contract

RFC 9110 section 9.2.2 describes equal intended effects from repeated identical requests. Responses may differ, and each attempt may be logged. Renaming an endpoint PUT does not create a transaction spanning a database and payment provider.

After a timeout, a user may retry the same purchase or change quantity and make a new one. Deduplicating by user alone can suppress legitimate purchases; generating a fresh identifier on every retry cannot recognize the original intent. Define when the identifier is created and how long it applies.

Make deduplication durable

A candidate design stores the identifier, normalized request fingerprint, processing state, and result reference, with an explicit policy for irrelevant payload differences. Identical content can retrieve the existing outcome or an explicit processing state. Reusing an identifier for different content should produce an understandable conflict. Status codes and retention remain contract decisions.

Concurrent attempts must not both observe an absent record and create separate orders. A uniqueness constraint, conditional write, or transactional arbitration must assign ownership. Failure recovery needs durable evidence rather than an in-memory flag on one process.

If the order and deduplication record commit together, a retry can discover the original result after a lost response. Separate writes create a crash window in which the order exists but its record does not. Review every intermediate failure point.

Treat external effects separately

A local transaction cannot by itself guarantee a single external charge. Align with the payment provider’s actual idempotency contract where available. Query and reconcile an unknown outcome before initiating another charge. Notifications and inventory updates need their own duplicate-effect rules.

Order retention, identifier expiry, and provider lookup windows may differ. Specify what an expired retry means: a new intent, a rejected request, or an unresolved outcome requiring investigation.

Proposed tests include simultaneous identical requests, changed payloads, lost responses after commit, worker failure, and expired records. None were executed here. Validate order count, payment state, and response association, not just successful HTTP responses.

Read-only and side-effecting retries need separate policies with bounded time and backoff. First answer “where do we look when the outcome is unknown?” For asynchronous handoff, see the transactional outbox boundary.
