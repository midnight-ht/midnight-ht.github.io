Can a Timed-Out Request Be Retried? Define the Business Idempotency Boundary

Handle an unknown timeout outcome by separating HTTP idempotence, stable intent keys, durable deduplication, and external side effects.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-27 · Estimated read 20 min
Translations
zh-CN en

Article

Key takeaways

  • A timeout means the outcome is unknown, not that the order was not committed.
  • Reuse a stable key for retries of one intent and define payload drift, expiry, and concurrency behavior.
  • Coordinate the local key record and order atomically; external effects still need their own deduplication and reconciliation.
  • Recheck authentication and object authorization before replaying a stored result.
  • Test failures before and after commit, concurrent duplicates, changed payloads, payment callbacks, and key expiry.

Whether a timed-out request can be retried depends on more than whether the client received a response. The server may not have processed it, or it may have committed an order and lost the response on the way back. A retry can return the first result only when the service recognizes the same business intent and records ownership of that intent atomically with its local write. Payment, email, and other external effects still need their own deduplication and reconciliation contracts. The checkout below is a hypothetical design; no payment integration or fault-injection test was performed.

HTTP idempotence does not deduplicate every POST

RFC 9110 section 9.2.2 defines idempotence in terms of the intended effect of multiple identical requests: the intended server effect is the same as for one request. It does not require identical responses, logs, or billing records. Methods such as PUT and DELETE have idempotent semantics under the specification; a POST's business meaning is defined by the application. Allowing a client to retry a POST does not make the endpoint deduplicate requests merely because their text is identical.

A timeout is an observation, not a transaction result. The request might never have left the client, might have been dropped by a proxy, or might have committed to a database before the response was lost. Treat every timeout as “not created” and a client can create another order. Treat every timeout as success and the interface can show an order that does not exist. A sound contract represents the outcome as unknown and gives the client a durable business identifier it can query.

A key names one intent, not each network attempt

Create an idempotency key when a business operation begins and reuse it for every retry of that operation. If the customer changes quantity, address, or another material field, that is usually a new intent and should get a new key. If the old key is reused, the server should detect that the request changed and apply an explicit conflict policy rather than silently attaching new parameters to the old order. Deduplicating forever by user ID is too broad: it can block that user's later, legitimate purchase of the same item.

Scope the key by the tenant or account and operation, and retain a request fingerprint, state, resource reference, and enough response data to reproduce the outcome. Define canonicalization deliberately: JSON field order and insignificant whitespace may be irrelevant, while currency, price, and quantity are part of the transaction intent. Storing a fingerprint does not require storing the full sensitive request again; avoid copying payment credentials or unnecessary personal data into logs or a key table.

An existing key is not a reason to skip authentication or object authorization. The key associates retries with an operation; it should not act as a secret password for reading an order. Before returning a stored result, the server still needs to confirm that the caller can access the relevant tenant and order. Otherwise someone who obtains a key could learn another user's response body, address, or payment state. Apply that check on the replay-read path, not only during the first order creation.

Expiry is part of the API contract too. If a key record lives for only a few hours, a client reconnecting the next day may submit a key that can no longer be associated with its order. Decide whether an expired replay is rejected, treated as a new operation, or requires a status lookup first. If the payment provider retains its keys for less time than the application's recovery window, provider-side deduplication alone does not cover that longer window.

Make the key and local order compete atomically

A testable design is a unique constraint over (tenant_id, operation, idempotency_key), with the key claim and order write competing inside one database transaction. The first request claims the key, creates the order, associates the key record with that order, and commits a reusable result. Concurrent requests cannot each perform a separate “no record found” query and then create their own orders; the database uniqueness constraint, or an equivalent atomic primitive, decides which request owns the intent. PostgreSQL documents unique indexes as the enforcement mechanism for unique constraints and documents INSERT ... ON CONFLICT for handling conflicts. The exact statement and isolation behavior still need validation against the database version in use.

Consider one hypothetical checkout. The browser creates key K and submits a cart version, currency, and final amount. A transaction first claims K with a fingerprint, then creates order O, links the key record to O, and commits. If the response is lost after commit, a retry with K and the same request can find the completed record and return O's stored outcome instead of inserting another order. If the first transaction crashes before commit, both the key claim and O roll back; a retry can claim K and proceed.

The sequence has failure windows. If the server commits a processing row first and creates the order in a later transaction, a crash between them can leave a record stuck in progress. If it writes the order first and the deduplication record second, a crash can leave an order that a retry cannot recognize. Split commits require explicit recovery: for example, a leased processing state, a safely reentrant recovery worker, and a rule for locating any existing order. An in-memory lock or map cannot coordinate other service replicas and disappears when a process restarts.

A local transaction cannot include an external payment

A database transaction can cover the order and local key record; it cannot make a payment provider's charge part of the same atomic commit. One common boundary is to persist the order in a pending-payment state and reliably schedule a payment command through a transactional outbox or equivalent. The consumer may deliver that command more than once, so each payment attempt needs a stable business reference and must follow the provider's actual idempotency contract. If a payment call times out, retain an “unknown” or “pending confirmation” state, then reconcile through provider queries, callbacks, and settlement checks. Do not immediately create another order or permanently record a failure while the first outcome is unresolved.

Notifications also have different consequences. A duplicate email may be inconvenient; a duplicate inventory decrement can change availability. Both cannot be covered by one vague “the API is idempotent” label. When an external system offers no usable idempotency interface, the business needs a queryable operation reference, a compensation path, or manual reconciliation. An idempotency key associates retries of one intent; it cannot prove that two requests with different keys came from a single double-click, and it does not replace order limits, payment verification, or fraud controls.

Give conflicts, in-progress work, and unknown outcomes distinct responses

For the same key and fingerprint after completion, return the saved result. For the same key with a different fingerprint, return a stable and explainable conflict. While the first attempt is still processing, return a queryable pending state or wait briefly according to the API contract. The exact HTTP status and response fields are application decisions. A client should not respond to a conflict by generating a fresh key and submitting again: it can turn one unresolved action into a second real order. A status resource such as GET /operations/{key} makes recovery less dependent on guessing.

Retry policy should also distinguish transport uncertainty from a definite business rejection. A connection reset, gateway timeout, or lost response can leave the outcome unknown; a validation error should not be retried unchanged in a loop. Automatic retries need a deadline, an attempt limit, and backoff, so many clients do not all hit the service at once when connectivity returns. Even when a stable key makes replay safe, excessive polling and replay still consume resources and can prolong an incident.

Verify the business state transition, not just HTTP success

Start acceptance from the state transitions. Send two concurrent requests with the same key and fingerprint; verify that the database ends with one order and that the other request receives the same resource or an explicit pending state. Reuse the key with a changed quantity and confirm the service rejects payload drift. Simulate losing the response after the order transaction commits, retry with the original key, and verify the original order is returned. Terminate the transaction before commit and check that no orphaned processing record remains.

Test payment separately: the provider accepts a charge but its response is lost; a callback arrives late or twice; a local consumer delivers twice; or a provider status query is temporarily unavailable. Check the relationship among the order, provider reference, outbox record, and final response rather than only the message shown to the customer. Also test key expiry, account isolation, authorization failures, and fingerprint canonicalization. These are proposed tests, not results from an executed database or payment fault-injection run.

When a write modifies a representation already read, a version condition has a different job: RFC 9110 section 13.1.1 defines If-Match for preventing an update based on an old representation from overwriting a newer one, while an idempotency key identifies a repeated submission of the same business operation. Both can be useful together. See why two successful saves can still lose an editor's change; this article's central question is instead, “How far did this intent get?”
