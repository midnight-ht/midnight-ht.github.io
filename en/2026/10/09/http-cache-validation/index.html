Why Does no-cache Still Leave Cached Files?

Distinguish no-cache from no-store and private by checking validation and reuse across the actual delivery chain.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-09 · Estimated read 6 min
Translations
zh-CN en

Article

no-cache does not prohibit saving a response. It requires validation before relevant reuse. If the objective is to prohibit storage, understand no-store and inspect the actual caching chain; the directive is not an absolute privacy guarantee. A file on disk alone does not prove a no-cache misconfiguration. This analysis does not measure a CDN provider’s defaults.

Storage and reuse are separate decisions

RFC 9111 defines storage, validation, and Cache-Control directives. Unqualified no-cache requires validation before reuse; no-store addresses storage; private restricts shared caching. They are not interchangeable spellings of one switch.

A homepage might permit storage while requiring the origin to confirm freshness on later requests. A personalized response introduces a different question: where may its information be retained or shared? Validation alone does not settle that.

Verify the delivery chain

Browsers, edge caches, and reverse proxies occupy different layers. An application header is not proof of what the user received. Record the URL, status, redirects, and final headers to locate the responding layer before purging everything.

Validation needs meaningful validators. If content changes while its ETag does not, a cache can follow its contract and still display the wrong representation. Review validator generation alongside content negotiation and deployment versions.

For authenticated pages, decide shared-cache eligibility before optimizing hit rate. Account, language, and permission differences may change the representation. Do not copy a public homepage policy onto an invoice endpoint or assume Vary solves every identity boundary.

Establish evidence of a correct change

A proposed experiment uses a response with an identifiable content version. Record the first fetch, reuse attempt, and fetch after a content change. Inspect validation, returned body, and the browser’s displayed version. This experiment was not run here; one header screenshot is not a complete result.

Specify behavior when the origin is unavailable. A public information page and a transaction status page may have different tolerance for stale content. Honor the chosen directives rather than presenting an old transactional state as current.

Adding no-store later does not prove previously distributed sensitive copies disappeared. Investigate cache purge capability, distributed copies, and access control as appropriate. Headers are not a remote-delete mechanism for every copy.

For a release problem, compare origin, edge, and browser responses and fix the first contract violation. If deployments are overwriting each other, cache purges cannot repair it; inspect deployment concurrency and environment locks.
