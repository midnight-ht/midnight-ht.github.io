Why Can no-cache Still Leave Cached Files?

no-cache permits storage but requires validation before reuse. Trace browser, proxy, and CDN evidence, then choose no-store and private deliberately.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-27 · Estimated read 24 min
Translations
zh-CN en

Article

Key takeaways

  • Separate storage, reuse, and shared-cache eligibility; no-cache requires validation, no-store addresses storage, and private limits shared-cache storage.
  • Use version markers and validators across origin, edge, and browser/Service Worker to locate the first divergence.
  • Examples and proposed checks are hypothetical and were not run in a CDN or production.

Finding a response file on disk is not, by itself, evidence that no-cache is misconfigured: the response may be stored, but it must be forwarded for validation before it is reused. If the goal is to prohibit storage, consider no-store; if a response intended for one user must not be reused by a shared cache, consider private as well. These directives govern different behavior. Stacking all of them in one header is not a substitute for a caching design. Their distinctions are specified in RFC 9111's response directives. The investigation below is based on RFC 9111 and MDN documentation; it is not a measurement of a particular CDN or production system.

First identify the layer where behavior diverges

A browser cache, corporate proxy, CDN, reverse proxy, and Service Worker Cache API are not one observable “cache.” An origin response containing Cache-Control: no-cache shows the policy sent by that origin. A managed cache can have its own rules, and a Service Worker can implement custom storage and response logic. MDN's HTTP caching guide notes that managed-cache products commonly provide their own configuration or management APIs, and some can deliberately use strategies different from the HTTP caching protocol. Therefore, “the browser developer tools show a disk-cache entry” and “the edge returned old content” are clues, not root-cause conclusions.

Prepare a safe, visible version marker for the representation, such as a release-id on a public test page. Record the complete URL, method, status, redirect chain, final response headers, a version marker in the body, Age, ETag, Last-Modified, Vary, Via, and any cache-hit field supplied by the provider. Age can indicate the current age of a response in a shared cache. Fields such as X-Cache are provider-specific diagnostics, not universal HTTP standards. Do not paste a real account response or authorization header into a public issue.

Send comparable requests to the application origin, the public hostname, and a browser context with its existing Service Worker. Use comparable URLs and request headers. If the origin returns the new version while the public edge still returns the old one, inspect CDN cache-key and policy rules. If the edge has the new version but the browser page does not, inspect the browser cache, Service Worker, or page state. If headers change after a redirect, record each hop separately. This layered comparison identifies the first point that violates the intended policy more reliably than purging every cache at once.

What no-cache stores, and what it restricts

RFC 9111's definition of response no-cache says an unqualified directive does not allow a stored response to satisfy a later request without validation. It does not mean “do not write this response to disk.” Suppose a public release-notes page returns Cache-Control: no-cache and ETag: "release-42-en". A browser may store the body and validator. When it needs to reuse that response, it can send If-None-Match: "release-42-en". With an unchanged representation, the origin may return 304 Not Modified, and the cache can keep using its stored body. A changed representation calls for the new body and validator instead. The conditional request and 304 behavior are described in RFC 9111's validation procedure and MDN's conditional requests guide. The file may still exist and a disk-cache entry may still appear even though reuse has been validated.

This design separates “avoid transferring the body again” from “check whether it is still current before reuse.” Validation still costs a network round trip, and correctness depends on the validator. If the body changes while the server keeps generating the same ETag, a cache can faithfully reuse an old representation according to an incorrect version marker. For content-negotiated resources, the validator should correspond to the representation in question. If language or encoding changes the body, the cache key must reflect those inputs; for example, when the response actually varies by Accept-Language, return an appropriate Vary field. Do not keep an unchanged validator merely to obtain 304 responses.

The request directive Cache-Control: no-cache and the response directive with the same name are also different contexts. The request expresses the client's requirements for reuse of stored responses; the response defines constraints for caches handling that representation. During diagnosis, preserve both request and response headers. That shows who required validation, which validator was involved, and how the origin answered.

When to choose no-store, and when to add private

An unqualified response no-store tells caches not to store information from the request or response. It is appropriate when there is a real reason to prevent standard HTTP caches from storing the information, but it is not a remote-delete command for every old copy of a URL. A response already stored by a browser or edge node does not disappear merely because a later response includes no-store. The specification notes a limited exception: a cache implementing must-understand may ignore no-store under the specified conditions after it understands the status code's caching requirements. Check RFC 9111's must-understand/no-store interaction when using that combination instead of describing no-store as an unconditional, global privacy guarantee. MDN's discussion of clearing stored cache distinguishes Clear-Site-Data: cache in a browser from shared or intermediary caches; managed CDNs commonly require their own management interface or API to remove stored objects. Even after a purge, verify the target cache layer and object rather than treating the new header as a purge receipt.

An unqualified response private restricts storage by shared caches. A private cache can still store the response under the conditions permitted by the specification. It is not encryption, and it does not guarantee that an operating system, extension, malicious cache, or network layer cannot see the content. For an account page, one possible policy is Cache-Control: private, no-cache: permit the user agent to store the response, require validation before reuse, and prohibit shared caches from storing it. If the data sensitivity or organizational rules really require preventing standard caches from storing the response, evaluate no-store and its product trade-offs, including back/forward navigation behavior.

Vary helps caches match different representations based on request headers; it is not a general identity-isolation switch. If one public page returns different bodies by language, Vary: Accept-Language can declare that the language request header participates in matching; RFC 9111's Vary cache-key rule requires a cache to compare the nominated request-header values. It cannot replace account authorization or make a shared cache safe for user-specific data. RFC 9111 separately constrains shared-cache reuse of responses to requests containing Authorization: generally, a shared cache must not reuse such a response for a later request unless a response directive explicitly permits shared storage and the cache follows its requirements. Decide whether a representation may be shared before optimizing hit rate or refining Vary.

A three-layer example: who is reusing the old version?

Suppose a team has released an announcement page as release-43, but some visitors still see release-42. This is a hypothetical diagnostic scenario, not evidence about a particular CDN. First request the origin and record its status, ETag, Cache-Control, and body version. An origin response still marked release-42 points first to application deployment or origin routing; the cache is not yet the leading suspect. Once the origin serves release-43, request the public hostname and compare the same fields.

If the public hostname shows an increasing Age and the old body, inspect the CDN's custom TTL for the path, rules that ignore response headers, the cache key, and whether query parameters participate in matching. Compare the edge ETag with the origin's. If the CDN revalidates with the origin and receives 304 even though the representation should have changed, inspect whether the origin validator misses a template, language, encoding, or data-version change. If the CDN still has an old ETag while the origin has a new one, the cache key or revalidation path is the next area to investigate.

If the public hostname already serves release-43, request it again in an isolated browser session that bypasses the Service Worker. If that context shows the new version but the normal page shows the old one, inspect the Service Worker's cache strategy, cache name, and update/activation path. If both contexts receive a new response but the interface still shows old data, the cause may be client state or a static asset rather than HTTP response caching. Each conclusion should point to the observations that support it. If this is only a design exercise, label it as unexecuted, as this article does.

There is a useful counterexample: disabling the browser cache in developer tools and seeing the page update does not prove that the origin's no-cache was ineffective. Developer tools may change request behavior or add request directives, and a Service Worker and CDN may not both be bypassed. A diagnostic record should describe its controls instead of treating one hard reload as a complete cache-policy test.

What evidence should a change pass?

For each representative route, list the intended representation, cache layers allowed to store it, directives, validators, content-negotiation inputs, and fallback behavior when the origin is unavailable. In a staging environment, use the same URL to record an initial 200, a conditional request after no content change, and a conditional request after a change. Check both status and body: after no change, can the stored representation be reused through validation? After a change, did the client receive the new body and validator? Test authenticated and unauthenticated requests, and each language or encoded representation. Do not write masked private headers into logs.

If a CDN is involved, compare the origin and edge with the same request and separately test the provider's purge mechanism. An origin response header does not prove that a CDN policy follows that header. If a Service Worker is involved, test installation, activation, old-cache removal, and the offline branch separately. Any untested layer remains unknown. Without actual samples, do not write “the configuration is fixed” or “users now receive the latest version.”

A change to sensitive content especially should not be handled by adding only no-store. Evaluate existing copies, authorization boundaries, CDN purge scope, and client-side storage. HTTP cache directives specify how caches that follow the protocol handle a response; they are not commands to destroy every copy. To solve a particular stale-page incident, find the first layer that violates the representation contract among origin, edge, and browser/Service Worker, then change that layer. This avoids disabling caching site-wide while still separating data that must not be stored from public content that only needs validation before reuse.

If an old page appears because concurrent release jobs overwrote the environment, also inspect the last commit that wrote that environment in deployment concurrency and environment locks. Cache validation decides when a representation may be reused; it cannot fix a source deployment that has already rolled back to an older version.
