preStop Is Configured but Requests Still Fail: Budget the Whole Shutdown

preStop is not extra grace time. Put hook execution, traffic withdrawal, in-flight work, and process cleanup inside one termination budget.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-27 · Estimated read 24 min
Translations

Article

Key takeaways

  • preStop, application shutdown after the stop signal, and other serial cleanup share terminationGracePeriodSeconds; a successful hook does not prove work has drained.
  • Pod termination and EndpointSlice updates proceed together; there is no single cross-network-component barrier that stops every proxy at once.
  • Define completion, cancellation, retry, or durable handoff separately for HTTP, message consumption, and background tasks, then validate with timestamps and request or message IDs.

Requests can still fail with a preStop hook because the hook is not a waiting period outside the Pod's termination budget. Kubernetes starts the grace-period countdown when termination begins. The hook must finish before the container receives its stop signal. The application then has to stop taking new work, finish or hand off work it has already accepted, and exit within whatever time remains. If any stage exceeds the budget, the container can still be forcefully terminated when the grace period expires.

That makes “the hook completed” and “requests drained” different claims. A hook can finish a command without knowing when a proxy stopped forwarding, whether a response reached its client, or whether a message consumer committed its offset. To budget shutdown, put the timeline, ownership of accepted work, and observable completion conditions on the same page instead of starting with a sleep duration that feels safe.

The grace period is one shared clock

The Kubernetes container lifecycle hooks documentation says that the Pod termination grace-period countdown begins before preStop runs, and the hook must complete before Kubernetes can send the stop signal. Its example uses a 60-second grace period: if the hook takes 55 seconds and the application needs another 10 seconds to stop after receiving the signal, the total requirement is 65 seconds. The container is killed before it can stop normally. The useful lesson is not to choose 60 seconds; it is that hook time and post-signal exit time share the same budget.

The Pod lifecycle documentation describes normal termination as kubelet asking the runtime to send TERM to the main process in each container, followed by KILL to processes that remain after the grace period expires. The default grace period is typically 30 seconds, but a workload can configure another value with terminationGracePeriodSeconds. Use the actual Pod configuration, cluster version, and runtime behavior for a service decision. A default is not an application-level service guarantee.

The official termination flow also says that if preStop is still running after the grace period expires, kubelet requests a one-off two-second grace extension. Treat this as a small emergency allowance, not extra capacity to put into a routine budget. A long hook still needs a deliberate terminationGracePeriodSeconds value and evidence that the remaining steps fit within it.

One useful budget constraint is:

T_hook + T_route + T_work + T_cleanup + T_margin <= T_grace

T_hook is the measured hook duration. T_route is the time after the application stops accepting new work for an ingress, Service proxy, or other consumer to stop assigning work to the instance. T_work is the maximum time allocated to accepted requests or jobs. T_cleanup covers connection closure, required state flushing, and process exit. T_margin accommodates variation. This decomposition is a design method, not a set of Kubernetes-managed phase timers. Some stages can run concurrently; others depend on the prior stage. Draw the actual sequence so that parallel time is not counted twice and required serial work is not mistakenly treated as parallel.

What preStop can do—and what it cannot prove

A hook can trigger a lightweight local action, such as telling the application to enter a draining state or waiting for a short propagation window that has an explicit basis. It is not a business-level drain protocol. A sleep 10 proves only that the process waited for ten seconds. It does not prove that EndpointSlices, node proxies, ingress controllers, service meshes, external load balancers, or clients stopped selecting the instance. Changes to control-plane state are not a synchronous barrier across every data-plane component.

The EndpointSlices documentation says that when a Pod is deleted, its endpoint is marked as terminating. Service proxies normally ignore terminating endpoints, but they may route to endpoints that are both serving and terminating when all available endpoints are terminating. This can avoid losing all Service traffic during a rolling update. ready is generally a shortcut for serving and not terminating, but publishNotReadyAddresses changes that condition. Therefore, a configured hook does not imply that no new request can arrive. The behavior of a particular ingress, proxy, mesh, or external load balancer also depends on its implementation and configuration.

If a hook calls a local management endpoint to switch the application into draining mode, define what “draining” means. What response should new requests receive? Do existing long-lived connections continue? Does a background consumer pause fetching? Can clients safely retry rejected work? The management action should be safe if it times out, is delivered more than once, or runs after part of the process has already begun shutting down. Kubernetes documents at-least-once hook delivery semantics, meaning a hook can rarely be invoked more than once. Side effects such as releasing a one-time lock or changing business state need idempotency or deduplication before they belong in a hook.

Define the outcome for accepted work

For an HTTP service, entering a shutdown state might stop new requests while allowing accepted requests to finish. But “finish” depends on the business protocol. For a streamed download, it may mean writing the final byte. For an asynchronous API, returning 202 means the request was accepted; durable storage and recoverability determine whether the task survives process exit. If a database transaction is in flight when the process is killed, a client may not know whether the commit succeeded. Retries then require an idempotency key, a transaction-status query, or another recovery contract.

Message consumers have a sharper boundary: receiving a message is not the same as completing it. During termination, a consumer can stop fetching, finish and acknowledge the current message, or return its lease to the queue. If the work cannot finish in the remaining budget, the system needs a recoverable redelivery mechanism. Batch jobs must distinguish partial writes from an all-or-nothing commit. Increasing the Pod grace period does not fix missing checkpoints, unsafe duplicate execution, or a dependency that can wait forever.

Editorial judgment: first make non-interruptible business work durable, retryable, and idempotent; then provide a bounded window for a normal shutdown. The termination budget makes a predictable process smoother, but it should not carry the entire burden of data reliability. Force deletion, node power loss, runtime failure, or a shortened grace period can leave no opportunity to run cleanup. State that must survive should not exist only in the memory of the process running preStop.

Calibrate the budget with one concrete timeline

The following is a hypothetical example, not a measurement from a cluster. Suppose a service has a 45-second grace period. Switching the application to draining takes 1 second. An observed window for the ingress and consumers to stop assigning new work is tentatively 6 seconds. The service allows up to 25 seconds for ordinary in-flight requests, needs 5 seconds for connection and process cleanup, and reserves 8 seconds as margin. A conservative serial sum is 45 seconds. If the actual request tail exceeds 25 seconds or the propagation window varies beyond 6 seconds, this budget no longer holds. The team must decide how to cancel or retry a request and whether the margin is sufficient; it should not silently choose a larger grace period and call the problem solved.

If draining and route convergence can truly proceed in parallel, the budget should follow the longest dependency path in the sequence diagram rather than blindly adding every duration. That is safe only when the application will not close dependencies while new work can still arrive. Conversely, if a hook waits ten seconds before TERM can reach the application, those ten seconds are deducted from the time left for normal exit. For the common “wait for propagation” pattern, verify what it is waiting for using endpoint conditions and request traces. Elapsed time alone is not proof of completion.

A controlled measurement can issue termination repeatedly and correlate timestamps for the deletion request or management event, Pod deletionTimestamp, EndpointSlice conditions, application entering draining, the last newly accepted request, completion of accepted work, delivery of the stop signal, and process exit. Associate request or message IDs with outcomes; count failures, duplicates, side effects, and client retries. Use tail percentiles and failure paths to calibrate T_work and T_margin, rather than relying only on average latency. This article did not run such a rehearsal. These are evidence fields to collect, not logs or performance results.

Failure paths that invalidate “graceful shutdown”

The hook stalls. The container can remain in Terminating until the grace period expires. Give the hook an explicit timeout and observable error. Whether the application should continue or exit after a timeout depends on the risk of the work at stake. Kubernetes documentation says a failed lifecycle hook kills the container; do not treat the failure as a harmless warning.

Traffic still arrives. An ingress connection pool, external load-balancer health check, long-lived connection, or cached consumer view can lag behind a Service endpoint update. The application needs a defined response for late work while exiting. A hook cannot collect acknowledgements from every component in the network.

Long-running work exceeds the remaining budget. If the active task cannot be cancelled, design task-level continuation, lease release, or checkpoints. A larger Pod grace period may slow a rollout and still cannot cover an unbounded operation.

The process disappears without a normal notice. Node failure or force deletion can bypass the full shutdown path. Consistency then depends on durability, idempotency, and recovery—not on receiving SIGTERM every time.

Make verification capable of disproving the design

Before release, define success criteria such as the time until no new task is accepted, the fraction of in-flight requests completed or explicitly cancelled, queue redelivery delay, duplicate side effects, and remaining margin at process exit. EndpointSlice observations describe control-plane state; application logs describe process behavior; real client outcomes describe what users experienced. Correlate them on a single timeline. Inspect the rendered Pod's terminationGracePeriodSeconds and hook configuration rather than relying only on a source template.

Test counterexamples too: make the hook slow, make a dependency call time out, keep one request running beyond its ordinary tail, and apply traffic while the application is draining. Observe whether behavior remains explainable as the grace period approaches zero. Run each experiment in a test environment and retain its results. These experiments were not performed for this article, so it does not claim that request loss has been eliminated. Force deletion and node disappearance still need separate reliability mechanisms.

Finally, review shutdown state alongside probe responsibilities. Readiness describes whether service discovery should select a target; liveness describes whether a process should be restarted. Misclassifying a valid draining state as a liveness failure can trigger another restart. Review this with Kubernetes probe responsibilities and distinguish request latency from Pod exit latency using the discussion of resource latency budgets. A reliable shutdown is not a longer preStop; it is clear ownership of work, a bounded time budget, and verification that can expose failure.
