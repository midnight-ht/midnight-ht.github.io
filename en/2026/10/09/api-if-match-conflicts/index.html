Both Saves Succeeded: Why Did One Editor Lose Their Changes?

Use If-Match to reject stale writes, then connect strong ETags and atomic updates to a conflict flow that preserves the user's draft.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-27 · Estimated read 25 min
Translations
zh-CN en

Article

Key takeaways

  • If-Match conditions a write on the current representation and requires strong comparison; the wildcard checks existence only.
  • Put the version predicate in the persisted update; a separate read and unconditional write still race.
  • A conflict response does not save the local draft, and the examples here were not executed in an application or database.

Imagine two people saving the same configuration: the server returns success twice, yet the later stale form erases one person's change. The missing piece is not another HTTP status code: each write needs to say which version it was based on. To prevent a stale representation from silently replacing a newer one, the client can send the strong ETag it received, the server can evaluate If-Match, and the version condition can be part of one atomic persisted update. If-Match expresses “write only if the representation I read is still current.” It does not preserve unsaved input or replace database concurrency control. The configuration scenario and SQL shape below are design examples, not tests run against an application or database.

How two successful saves can erase one change

Assume an alert configuration starts at version seven and contains a recipient and a threshold. Editors A and B read the full configuration at nearly the same time. A changes the recipient and saves. B only means to raise the threshold, but submits the complete version-seven object still in the browser. If the server performs an unconditional last-write-wins replacement, both requests can receive success. The database now contains B's threshold change but restores the old recipient value. B did not intentionally undo A's work; the system treated a stale save as ordinary.

The example depends on two conditions: a client submits a write based on old state, and the server allows that full representation to replace current state without a version condition. An endpoint that submits only changed fields can narrow the conflict surface, but field-level updates still need validation when values are related. The central issue is not that every pair of concurrent requests loses data. It is that the server does not know the basis for a write has gone stale.

An HTTP success status means the server accepted or processed a request according to the endpoint's semantics. It does not prove that all changes the user expected remain present. A service dashboard that watches only the percentage of 2xx responses may call silent data loss healthy traffic. Logging or metrics for version conflicts and rejected stale writes can make the failure visible, but detection is not a substitute for protecting the write itself.

ETag is a representation validator; If-Match is a write precondition

An ETag is an entity tag returned with a representation. The client stores it when reading the configuration and sends that tag in If-Match when updating. RFC 9110's If-Match rule applies against a current representation of the target resource and describes preventing accidental overwrites by parallel user agents as a common use. An origin server evaluates the condition before performing the method. If the condition is false, it must not perform the method and may use 412 Precondition Failed to report the failure.

If-Match requires strong comparison. The entity-tag comparison rule in RFC 9110 defines strong comparison as requiring both tags to be non-weak and their opaque values to match character by character. A weak ETag therefore cannot casually be treated as an exact version token for If-Match. RFC 9110's strong-validator rule also says a strong validator changes whenever representation data observable in a GET response changes. It can use strict revision control or a digest of the representation data; if content negotiation creates distinct representations, the validator needs to distinguish them. A strong ETag is not enough because it looks like a version number: it needs a consistent meaning for the representation the client read.

An API representation does not always map to one database row. A page can combine several tables, calculated fields, permission-filtered values, or content negotiated for different clients. If an ETag is derived only from a primary-table version while a related-table change alters the representation being edited, the tag may not change and If-Match can allow a write that should conflict. Conversely, if the representation includes a non-business value that changes on every request, the validator can reject writes that do not represent a meaningful editing conflict. First define which changes make a client's basis stale; then decide how the validator is derived.

What should the endpoint return when If-Match is missing?

Let the endpoint contract decide. If a resource must be edited from a known version, require a condition. If older clients temporarily need unconditional writes, define a migration window and observe which callers still omit the precondition. RFC 6585 defines 428 Precondition Required as an optional status for a server that requires conditional requests; the standard does not require every server to use it. The If-Match wildcard says that a current representation exists, not that the client read the latest version. Missing conditions, version mismatches, and nonexistent resources need distinguishable handling that does not disclose resource state to an unauthorized caller. Beyond the status code, the client needs a contract for rereading and safely resubmitting.

Checking the version and then writing still races

A common but insufficient implementation reads the current version in application code, sees version seven, then issues an UPDATE without a version condition. Two requests can both pass the version check while the row is still at seven, then overwrite each other. Saying that the code “checked the version” does not close the time window between the check and the write. The resource identity and expected version need to be conditions on the actual update.

Walk through the same hypothetical request sequence. Editors A and B both GET resource 42 and receive the version-seven ETag. A submits a PUT with If-Match for version seven. The server confirms that the current validator still matches, atomically saves A's recipient change, and returns the new version-eight ETag. B then sends the old version-seven precondition. Since the current representation is version eight, the server does not perform B's stale write and returns 412 according to the endpoint contract. B's threshold edit remains in the browser as a draft so the user can compare it with version eight. This is a design example, not a captured network trace.

For PostgreSQL 18, a useful design illustration is a conditional UPDATE that identifies the resource and expected version, increments the version, and changes only validated request fields. If one row is updated, one current row matched the condition. If zero rows are updated, none did. PostgreSQL's UPDATE documentation says that WHERE determines which rows change and describes the command's updated-row count. Its Read Committed documentation says a later concurrent updater waits for the first transaction to finish, then reevaluates its WHERE condition against the updated row version. Putting the version condition into that same UPDATE uses the database's atomic compare-and-write boundary.

The design still has to fit the application. Resource identity, tenant scope, authorization, and the version condition need a consistent treatment; do not reveal whether an inaccessible resource exists merely because a version did not match. Zero rows might mean a version conflict, a missing record, a tenant mismatch, or an authorization denial. Do not decide the public response solely from the affected-row count. The application may record more detailed internal diagnostics while presenting a response that follows its authorization and information-disclosure policy.

A multi-table operation does not become atomic just because the primary row's version matched. If saving the configuration also changes related rules, approvals, or separate records, decide which invariants must hold together and which state belongs in the same transaction. PostgreSQL isolation levels offer different concurrency guarantees, but stronger isolation does not decide what the user should see after a conflict and cannot supply a missing API precondition. List the invariants first, then choose transaction boundaries and isolation behavior.

How to preserve the user's work after a 412

For editor B, a 412 should not mean “clear the form.” Keep the unsaved fields as a draft, fetch the current server representation, and explain what changed. The user can compare the two sets of values and choose to keep, discard, or merge changes. If the recipient and threshold are genuinely independent, the interface may offer a field-level merge. If one value's meaning depends on another, automatic merging can create a combination the business has never allowed.

A common failure path is to issue a new GET, take its latest ETag, and immediately resend the old full request. This bypasses the stale-version condition but also bypasses the user's chance to notice that A already changed the recipient. A success response or automatic retry is justified only when the server can determine that the same change has already been applied and the request semantics really permit replay. The specification leaves a limited allowance for a successful response when a state-changing request appears to have already succeeded; it is not a license to replay every stale update.

The endpoint also needs a stable response for writes that omit If-Match. A new endpoint can require conditional writes and reject requests with no version. An older endpoint may need compatibility, but it should identify clients still writing unconditionally and make the migration boundary observable. If some callers omit the precondition indefinitely, only callers that follow the conditional-write contract are protected; the resource as a whole cannot be described as safe from lost updates.

What should the concurrency acceptance test prove?

A useful acceptance sequence starts with configuration version seven. Clients A and B both read it and receive the same strong ETag. A submits a change and receives success. B then submits its stale edit with the old ETag. The expected result is that B's write cannot erase A's saved state, the server returns the defined conflict response, and the client retains B's unsaved draft. B reads version eight, explicitly compares or merges the changes, and submits again; the version advances to nine. This sequence checks the HTTP precondition, server comparison, persisted state, and client recovery together.

Add reverse checks: does the endpoint reject a missing If-Match according to policy; can a weak ETag be incorrectly accepted; is the wildcard mistaken for “same version”; can two simultaneous requests both succeed with one stale version; what happens if the resource is deleted; does the tag have a clear meaning when permission filtering or content negotiation changes the representation; and can an unauthorized caller infer resource existence from conflict responses? If a zero-row update is used to identify conflicts, integration tests should distinguish a stale version from a missing resource or other internal cause using isolated test data.

No concurrent client, database, or ORM test was run for this article; the SQL is only an illustration of where the condition belongs. The implementation team should add integration tests for its database, driver, transaction isolation, cache, and retry behavior, retaining evidence of operation order and resulting state instead of checking only for a 412 response. For rich collaborative editing, If-Match identifies a write based on an old representation. It does not implement character-level merging, operation ordering, or a real-time collaboration algorithm.

A version precondition and business idempotency have different jobs: the first asks “is the resource still the version I read?”, while the second asks “is this a retry of the same business intent?” An editing endpoint may need both. For key scope, transactions, and external side-effect boundaries, see timeouts and business idempotency.
