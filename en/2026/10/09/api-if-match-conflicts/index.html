Both Saves Succeeded: Why Did One Editor Lose Their Changes?

Combine strong ETags with atomic version checks and a conflict workflow that preserves unsaved edits.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-09 · Estimated read 6 min
Translations
zh-CN en

Article

Prevent silent overwrites by attaching the version originally read as a condition of the write, then comparing and updating atomically, with an explicit policy for writes that omit the version condition. If-Match expresses that condition; it does not replace database concurrency control. The configuration editor below is hypothetical and was not implemented or tested.

Success can hide a lost update

Editors A and B both read version seven. A changes the alert recipient. B changes only the threshold but submits the whole older configuration. Unconditional replacement can make both requests succeed while removing A’s change. HTTP success rates alone miss this business failure.

RFC 9110 defines If-Match using strong comparison and describes preventing lost updates as a use. Send the strong ETag actually returned by the read, not an invented timestamp. An unmet condition normally results in 412; protocol exceptions require their documented semantics.

Compare and write in one operation

Reading a version, checking it in application code, and then issuing an unconditional update still allows an interleaving race. A candidate implementation conditions the database update on both resource identity and expected version. The data change and version increment belong to the same atomic operation. This is a design direction, not an ORM configuration recipe.

Zero updated rows might mean a conflict, missing resource, or denied access. Decide what the API may disclose alongside object authorization. Do not reveal resource existence merely to provide a friendlier conflict message.

After rejection, preserve unsaved input and show the current server version so the user can compare or redo changes. Automatically fetching a new ETag and replaying the old full payload defeats the safeguard. Field-level merging is possible only where those fields can legitimately change independently.

Narrower writes still need business rules

Sending changed fields may reduce conflicts, but related values cannot always be combined freely. A budget ceiling and approval rule may need joint validation. Rich collaboration can require locking, operation-level merging, or specialized algorithms; one header does not solve every concurrent-edit problem.

Version generation must match the representation returned, including content negotiation and field selection. Do not use a weak ETag without accounting for If-Match’s strong comparison.

Suggested acceptance covers two reads of one version, A’s successful save, B’s rejected stale save, and preservation of B’s input. Include unauthorized edits, deletion, and lost-response retries. These tests were not executed here.

A version precondition asks whether this is still the representation read; idempotency asks whether this is the same business intent. Retriable editing may need both. See timeouts and business idempotency.
