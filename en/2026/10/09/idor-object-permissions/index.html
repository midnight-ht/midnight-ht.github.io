A UUID Is Not an Authorization Decision: Four Checks for Every Order Request

UUIDs make enumeration harder but do not prove access rights. Model authorization across actions, tenants, asynchronous work, and static resources, then verify it with a controlled two-principal matrix.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-27 · Estimated read 24 min

Article

Key takeaways

  • An object identifier says what the server should look up; authorization decides whether this principal may perform this action on it.
  • Put the principal, tenant, object, and operation into each request decision, including downloads, bulk actions, asynchronous jobs, and static resources.
  • Use isolated test principals and an allow/deny matrix; this article proposes tests but does not claim a penetration test was run.

A UUID answers which order a request references; it does not answer whether the current principal may do this operation on it. For each authorization decision, the server should evaluate the principal, object, their current relationship, and the requested action together. That boundary must also reach downloads, bulk endpoints, asynchronous jobs, and file distribution. The IDOR and API BOLA guidance explicitly covers integer, UUID, and generic string references: random identifiers do not replace object-level checks. This article organizes design and test practices from official sources; no penetration test against a real system was performed.

Identifiers, identity, and authorization answer different questions

A request may contain /orders/{id}, a query parameter, a JSON field, a filename, or a download token. These values tell the server which object the requester wants to reference. They do not establish who the requester is or what that person may do. Authentication establishes the current principal. Authorization asks whether that principal may perform a particular operation on a particular object. Treating isLoggedIn as canRead(order) is like treating a building entry badge as the key to every room.

A UUID does not change that logic. A reference can appear in logs, email notifications, browser history, screenshots, collaboration links, exported filenames, or another API response. Even if the value is unpredictable, someone who obtains the link may request it with a valid session of their own. If the backend retrieves a row by UUID and returns it without checking the requester's relationship to the object, randomization has hidden only part of the route to the flaw. Conversely, sequential IDs can be safe when the server consistently enforces authorization. Identifier complexity is defense in depth against enumeration; the access decision must stand independently.

That is why hiding an order button in the frontend is not a security boundary. A caller can invoke an endpoint directly, change a request body, or reuse a download URL. Client presentation can improve usability, but it cannot make the decisive access decision. OWASP's authorization guidance says enforcement belongs server-side, at a gateway, or in an equivalent controlled execution layer, and permissions must be checked on each request. API1:2023 also distinguishes object-level from function-level authorization: a caller may be allowed to invoke a type of endpoint while being denied access to the particular object it names (BOLA); calling an administrative function that the caller is not allowed to invoke is a separate function-level problem. Both checks can be needed. A role check does not automatically prove object ownership.

Make the authorization relationship reviewable

A reviewable access decision includes at least four dimensions: who the principal is, which security domain contains the object, what relationship connects the principal to that object, and which operation is requested. For reading an order, a rule might require that the caller be a member of the account that owns it and have read permission. Canceling it may additionally depend on the order's state, the caller's role, and a business deadline. Being allowed to see a summary does not naturally imply permission to change payment details, cancel, export all fields, or read an attachment.

In a multi-tenant system, do not trust a client-supplied tenant_id as proof of context. The server should derive the principal from a verified session, token, or service identity, then establish the tenant relationship from current membership or service authorization. That tenant scope belongs in the object lookup or policy evaluation. For tenant isolation, OWASP lists a composite key such as tenant_id + resource_id as one option, not a universal requirement. The important property is that every path to a tenant-owned resource crosses an enforceable isolation boundary. Database row-level policies may add defense in depth, but they do not prove that the application connection used the correct principal and tenant context, and they do not establish that a static file path follows the same rule.

One common implementation is to locate an object within the set the current principal is already permitted to access. This can make tenant and sharing relationships harder to omit accidentally. Another valid design fetches the object and then calls a centralized policy check. That design must ensure authorization runs before serialization, writes, queue submission, or other side effects, and must handle the distinction between missing and forbidden resources deliberately. Choose based on the framework, relationship complexity, and audit needs; shorter code does not by itself mean the boundary is more complete.

Permission varies by action

An order can support viewing, editing notes, refunding, canceling, exporting, and downloading attachments. List these object-action pairs and specify eligible principals, required relationships, state restrictions, and side effects. A successful read does not prove that an update endpoint is correct. Checking ownership in GET while letting PATCH write by ID still leaves an object-level gap. Administrative or support access also needs a defined scope, rationale, and audit trail; it should not become a universal bypass for tenant checks.

Bulk endpoints need explicit semantics. If a request contains 20 objects and only 18 are authorized, does the service reject the whole request, process only the allowed subset, or return per-object results? This is not merely an implementation detail. Per-item filtering may be acceptable for a read query, while a bulk refund or permission change that partially succeeds can leave the caller believing the whole operation was atomic. Specify atomicity, item-level results, retry behavior, and error disclosure, then apply that contract consistently to exports and background jobs.

Nested routes have a similar trap: permission to read a project does not imply permission to read any attachment named under any project_id. If document_id and the outer project ID do not refer to the same authorized relationship, reject the request; do not merely check that each ID exists. Treat tenant, parent, and child relationships as one authorization question. Whether the public response should merge “missing” and “forbidden” into a 404, or expose a 403 for usability, depends on whether object existence is sensitive and what the client must do next. The internal audit trail can retain a more precise denial reason without logging tokens, sensitive content, or excessive identifiers.

Links and jobs outlive permission changes

Authorization at request time does not automatically grant access to every artifact produced later. A user may have team permission when submitting a report job, then lose membership before the job completes. If the queue message carries a permanent “allowed” decision from creation time, the completed result may still be exposed. Decide the intended product rule: is authorization frozen when a job is created, or is it checked again when the result is downloaded? Sensitive workflows often need to establish trusted principal context and re-check at job consumption, artifact creation, or download boundaries. Which stage must repeat the decision should follow an explicit business rule rather than a vague “check async too.”

A signed download URL is a delegated capability, not a randomized version of an object ID. Before issuing it, check whether the principal may access that specific file and operation; constrain the URL to the required object, method, and duration, and define revocation behavior. Anyone holding the link may be able to forward it during its validity period, so its security model must fit the data sensitivity. Permission at the time of link creation does not turn a permanent storage URL into a safe substitute for current authorization. The multi-tenant sheet also notes that a URL need not expose the tenant identifier when authorization has already occurred before signing.

Static files, thumbnails, object-store downloads, caches, and preview endpoints are all access paths. A correct check in a database API cannot help if the bucket is public, an edge-cache key ignores tenant differences, or a preview service fetches a file by a guessable path. Draw the path from the page through services, storage, and distribution. At each boundary, identify which principal context is available, which resource attributes affect the result, and whether a cache might share a response across users. Cloud storage and CDN settings need provider-specific evidence; general OWASP guidance cannot establish the configuration of a particular service.

A controlled test that can expose omissions

Create two dedicated test principals, A and B, with separate test objects. Write an allow/deny matrix for each operation rather than swapping only one detail URL. A reading A's object should be allowed; A reading B's should be denied; B's access to its own object should follow its role; a low-privilege principal invoking an administrative operation should be denied. Cover attachments, exports, nested resources, bulk actions, and asynchronous results separately. Unexpected responses must not contain protected fields or cause side effects. Use dedicated fixtures and a test environment, never real customer orders as probes.

Include observable sources of references: detail APIs, list responses, email notifications, hidden form fields, filenames, and queued results. For verification, OWASP's IDOR guide recommends multiple accounts with different authorization scopes; IDOR is not limited to sequential integers in URLs. An authorized swap test is not an invitation to probe unrelated services. Restrict the principals, objects, operations, environment, and rollback plan in advance, especially for actions such as deletion and refunds that have side effects.

Test state changes too: an object transfers from A to B, a member leaves a tenant, an administrator loses privileges, a token expires, or a job is queued before permission is revoked. The outcome should follow the authorization point defined by the business rule. If permission is intentionally frozen at job creation, preserve an auditable decision and its narrow scope. If access is re-evaluated at download, the download service must be able to establish the current principal and object relationship. A worker should not trust tenant context copied from an unverified request field.

Finally, make denials attributable without leaking data. An audit event can record an internal principal identifier, object type, tenant scope, action, policy version, and denial code, with access and retention controls. External responses may merge missing and forbidden cases to reduce object discovery, while internal monitoring distinguishes them to detect missed checks and privilege drift. The authorization sheet calls for deny-by-default behavior, validation on every request, and periodic permission reviews. That makes acceptance a recurring practice as endpoints and roles change, not a one-time claim that UUIDs were added.

This matrix is a proposal; no API, database policy, or cloud storage test was run for this article. A real acceptance record should preserve the tested version, principal and scope, object and action, request/response summary, expected and observed result, plus cleanup and rollback evidence. This separates “a check is visible in code,” “some paths were shown to deny,” and “all production entry points satisfy the authorization contract.” Do not report the first as proof of the last. For the separate distribution boundary, compare the related article on cache sharing and validation; its focus is caching, not IDOR authorization.
