The Backup Job Is Green: Why Can Recovery Still Fail?

Validate PostgreSQL 18 recovery from base backup, WAL coverage, and timeline through an isolated instance and business-data checks.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-27 · Estimated read 21 min
Translations
zh-CN en

Article

Key takeaways

  • A green job proves only the step it owns, not business recovery.
  • Manifest checks, server startup, and correct business state are separate evidence layers.
  • Record the target, WAL coverage, and business anchors in an isolated rehearsal.

A green backup job proves that the step it owns returned success. It does not prove that the WAL needed for a target time is continuous, recovery configuration is usable, the instance will start, or the application will see the intended business state. For PostgreSQL, recoverability is an evidence chain from a base backup through archived logs, configuration, and a chosen target to an isolated restore and business checks. This article designs a rehearsal from PostgreSQL 18 documentation; the scenario is a proposal, not an executed restore or a measured recovery time.

What does the green status actually prove?

Start by asking which step the job owns. If it only writes an archive to object storage, success may prove that the process completed the write and received an acknowledgement from storage. It does not prove that retention covers the time when an incident will be discovered or that the recovery identity can still read the object. If the job runs pg_basebackup, success can establish that this base-backup command exited normally. It still does not mean the backup was copied to another host, started as a database, and checked against business data. A dashboard should separate these boundaries; otherwise one green light silently vouches for several untested assumptions.

In the PostgreSQL 18 backup chapter, SQL dumps, file-system-level backups, and continuous archiving are listed as different approaches. A pg_dump logical dump is generally useful for loading into newer PostgreSQL versions or a different machine architecture, but it is not the file-system backup required for WAL replay. pg_basebackup copies a whole database cluster. An incremental backup also depends on earlier backups and must be combined before it can be used directly for recovery. An acceptance plan therefore needs to name the method, restore scope, and version conditions instead of saying only “the database is backed up.”

PITR depends on a continuous chain

Point-in-time recovery (PITR) does not jump from any snapshot to any arbitrary instant. It starts with a base backup and replays the WAL that covers the necessary interval until the target. The manual requires the available archived WAL sequence to reach back at least to the start of the base backup; the recovery target must also be later than the backup’s end time. If the target is earlier than the end of that backup, use an earlier base backup and replay forward from there.

Suppose a team creates a base backup on Sunday, archives WAL during the work week, and discovers a dropped table on Wednesday. It may seem sufficient to find files from before Wednesday. The team still has to prove that the archive continuously covers the WAL required from the base backup through the target, and that the target belongs to the correct timeline. A missing segment, an archive script that reports failure as success, or an omitted history file can leave many objects in storage without proving a complete replay chain. Timeline history files may also be requested; they help choose the correct WAL from an archive containing multiple branches. A drill should record the base-backup identity, timeline, and archive coverage interval, not merely the latest object modification time.

There is also a non-obvious boundary in restore_command. During recovery, the server may request a file that is absent from the archive; the command should return a nonzero status for that lookup, which can be a normal end-of-archive condition rather than a recovery failure. A shell error or abnormal signal can instead abort recovery. A “file not found” log line cannot be marked red or green without context. Check the requested filename, when it was requested, whether the server then stopped at the intended target, and whether the logs show a required gap, corruption, or an unusable command.

Integrity checks and successful recovery are different evidence

pg_verifybackup can compare the backup_manifest produced by pg_basebackup with backup files, check checksums, and parse WAL records needed to recover that backup. It can detect many storage problems and operator errors. The PostgreSQL 18 manual explicitly says these checks cannot cover every check a running server makes when using the backup; test restores and verification of the resulting data are still required. WAL parsing also has a format boundary: the documentation says it is currently unavailable for tar-format backups.

Acceptance should therefore be layered. The first layer checks files and the manifest. The second starts a database on an isolated target and waits for recovery to finish. The third checks important data and application invariants. Passing the first layer supports “manifest and file checks passed,” not “disaster recovery passed.” A process that starts is not enough either: the target time could be wrong, a recent order might be absent, or roles and extensions may not match application requirements. Conversely, one successful business query does not prove that every row is complete, so each check should correspond to an explicit assumption.

What evidence should one rehearsal leave?

Design the rehearsal as a controlled, isolated restore that cannot receive production traffic. Fix its identity and inputs first: base-backup time and digest, required WAL range, PostgreSQL major version, recovery target, tablespace paths, external archive location, and access method. Restore into a new directory or temporary host so the procedure cannot overwrite the only retained backup. If production data is sensitive, restrict network access and identities, protect logs, and define when the rehearsal copy will be destroyed.

Then retrieve the files, check the manifest, prepare recovery configuration, start the server, and replay WAL using a pre-approved runbook. Record each step’s start and finish, tool exit status, database logs, target timeline, and the time the server first becomes available for controlled queries. Do not direct public application traffic to the temporary instance during recovery. Connect first with a read-only identity and inspect business anchors selected in advance: for example, a known completed order recorded before the drill, its detail count, the associated user permission, and one important aggregate. Derive those anchors from business consistency requirements; the mere presence of one row is not proof of a correct database.

If the business needs a state from before an operator mistake, make the target selection explainable. Record which audit event establishes the target time, the expected range of lost changes, and how the business owner will decide whether to accept it. Run the necessary read-only application checks, including timezone, extensions, database roles, and key queries required by that environment. Keep “database accepts controlled connections,” “business checks pass,” and “service may be restored” as three separate timestamps. This reveals whether time was spent retrieving archives, replaying WAL, rebuilding dependencies, or checking business state; it avoids presenting import duration as RTO.

If the drill fails, preserve the original evidence and classify the stage: base backup unavailable, manifest mismatch, missing WAL, wrong timeline, unusable restore command, invalid target, database startup failure, missing roles or extensions, or inconsistent business anchors. Do not turn the dashboard green by skipping a failed step or widening the recovery target. Each failure should create a tracked repair item; the next run should use the same input or explicitly document what changed. This drill was not executed here, and no successful recovery log or duration is claimed.

How do RPO, RTO, and backup type shape the design?

The recovery point objective (RPO) describes the amount of change the business can accept losing; the recovery time objective (RTO) describes how long service may take to return. Taking base backups more often can reduce the WAL that must be replayed, while increasing backup creation and retention cost. Keeping a longer WAL history offers more possible recovery targets, but expands storage, access-control, and cleanup obligations. The choice among logical dumps, physical base backups with continuous archiving, and storage snapshots also depends on whether the goal is cross-version migration, single-database restore, whole-cluster restore, architecture change, or point-in-time recovery. No single “best backup” covers every goal.

Do not join a logical dump and PITR into a chain that does not exist. The PostgreSQL SQL Dump documentation says pg_dump and pg_dumpall are not file-system-level backups and do not contain enough information for WAL replay. A team needing both cross-version migration and whole-cluster point-in-time recovery may need separate logical and physical backup plans, each with its own verification evidence. Restoring to production is also not an ordinary drill: it involves write cutover, timeline branching, client isolation, and treatment of the old primary, and deserves a separately authorized cutover procedure.

Is passing pg_verifybackup enough?

No. Start a restore on an isolated target and check the target time, critical business data, and the permissions and extensions the application requires. The utility is an early layer of evidence, not a substitute for business usability.

Does a missing WAL file in the log mean failure?

Not necessarily. The restore command receives requests for archive files that do not exist, and PostgreSQL documentation requires a nonzero status for that case; a normal end-of-archive lookup can therefore produce a file-not-found message. A required segment missing in the middle of recovery, or a command that cannot execute, must be judged from the specific logs and subsequent recovery state.

Choose the recovery point the business can accept, then make the rehearsal prove that retained inputs can reach it. Account separately for file integrity, database startup, and business results; the next green status will then have a precise boundary. For the database invariants used in post-restore business checks, see cross-row invariants and transaction retries in PostgreSQL. Data recovery is also distinct from deployment rollback; see release artifacts and rollback.
