CREATE INDEX CONCURRENTLY Is Still Waiting: What Should a Release Check?

Plan PostgreSQL 18 concurrent index builds around transaction waits and validity rather than command completion alone.

Updated 2026-10-09 · Estimated read 6 min
Translations
zh-CN en

Article

CREATE INDEX CONCURRENTLY permits ordinary writes to continue, but promises neither immediate completion nor zero operational cost. Observe transaction waits, resource pressure, and index validity instead of relying on a deployment timeout. This PostgreSQL 18 analysis involved no production index operation.

Online builds still have phases and waits

The PostgreSQL 18 CREATE INDEX documentation describes extra scans and transaction waits, additional work, and invalid indexes that can remain after failure. Concurrent construction cannot run inside a transaction block. Check whether a migration tool wraps its entire file in one.

A long-running transaction can delay a build on an orders table. Waiting does not automatically imply a deadlock. Repeatedly canceling and restarting without identifying the blocker leaves the cause intact and adds cleanup work. Identify the owner, wait duration, and stage, with the change owner coordinating any long-transaction intervention before deciding whether to wait or reschedule.

Define when to stop

Record table size, existing indexes, target queries, available storage, and the responsible operator. During construction, monitor application latency and errors alongside database load, waits, and progress. Thresholds need the service’s own operating agreement, not an invented universal percentage.

Build duration is not the same as outage duration. Conversely, avoiding a write-blocking table lock does not remove scan-related resource competition. Evaluate user outcomes rather than declaring safety from the absence of one lock type.

After failure, inspect actual catalog state. An invalid index can consume space and maintenance work even if query plans ignore it. Confirm its table, name, and failure reason before cleanup or rebuilding. Environment-specific commands belong to an authorized operator after preflight.

Completion is not the final acceptance

Verify index validity, then use representative query parameters to inspect plans and service latency. Distribution and cache conditions matter. The optimizer need not choose the index, and write maintenance has a cost. One short local query cannot establish production benefit.

Rehearse transaction wrapping, retry behavior, and logs. A migration that merely skips an existing name without checking validity may label a failed build complete. These rehearsal checks were not executed here.

A small table in an agreed maintenance window may justify the simpler ordinary build. Partitioning and uniqueness require their specific documented restrictions. Track start, waiting, completion, validity, query checks, and cleanup separately. If the rationale is only “the query is slow,” first inspect EXPLAIN evidence.
