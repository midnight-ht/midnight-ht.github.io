FormData Repeated Names: Build a Snapshot From Current Selection

Use field cardinality to choose append or replacement, rebuild multi-select submissions from current state, and check server parsing.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-20 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • Append retains earlier entries under the same name; set replaces all existing values for that name.
  • A multi-select request should be built from current selection rather than accumulated click history.
  • The Node getAll result does not verify browser transmission or server duplicate-key handling.

A user deselects a tag, yet the next submission still contains it. Before blaming the server, inspect whether the page reuses a FormData instance and calls append("tag", value) on every change. Appending records another entry under the same name; it does not revise the earlier entry as a normal object-property assignment would. The right repair starts with the field contract: is this one current value, or a collection of values at submission time?

Repeated names are part of the representation

MDN's FormData.append reference distinguishes two operations. append() adds a value after existing entries with that name, or creates the entry if none exists. set() replaces all prior values under that name. If a multi-select field contains design and delivery, appending both under tag represents that collection. If a single-choice priority changes from low to high, appending high leaves two competing states. A repeated name is neither inherently corrupt nor inherently correct; the allowed cardinality belongs in the endpoint contract.

const data = new FormData();
data.append("tag", "design");
data.append("tag", "delivery");
console.log(data.getAll("tag"));

A minimal script under Node v24.21.0 printed ["design","delivery"] after those appends and ["research"] after a subsequent set("tag","research"). The complete script and raw output are stored with this editorial batch. That is evidence for this Node implementation of the API. It is not a browser submission test or a check of a server parser. On a real page, getAll is still a better first diagnostic than retrieving one value, because one value cannot establish that another entry is absent. Inspect entries() if entry order, file metadata, or contributions from several modules matter.

Replacing every append with set would break a genuine multi-value field: setting the second tag removes the first. A field definition should say whether priority has exactly one value, whether tag permits many, and whether attachment permits several files. It should also say what the server does with repetition where only one is allowed. Parsers and frameworks can expose the first entry, last entry, an array, or an error according to their own interfaces and configuration. The client API does not choose the backend's business rule.

An edit history is not a submission snapshot

The most fragile pattern is using FormData as long-lived UI state. A selects tag A, so A is appended. The user selects B, so B is appended. The user then deselects A, but nothing removes the earlier A entry. The visible state is {B} while the submission object still contains {A, B}. Calling delete("tag") removes all entries under the name, not just the one deselected entry. Rebuilding that name from current selections is therefore often clearer than maintaining a history of compensating mutations.

At submission time, create a new FormData, read the authoritative current selection, and append each selected tag once. Then compare getAll("tag") with the state the user can see before sending. For a single-value field, set can express “replace every earlier value with the current one.” These are design patterns, not evidence of a fix in a particular application. Their advantage is that the request follows current state rather than the number and order of clicks that led to it.

An object created with new FormData(form) needs special attention. Named successful controls may already have contributed entries, including repeated names from checkboxes or a multiple-selection control. Appending a script-level correction does not remove a control's original value. Review the actual flow from HTML controls, through script mutations, to network payload and receiver. If two modules both add tag, give one module ownership or define the merge. Each module can be locally reasonable while their combined output violates the endpoint's cardinality rule.

The timing of the snapshot is a separate decision. If the interface allows the user to change a selection while asynchronous validation is in flight, does the submission represent the state at the click, or the state after validation? Mixing a confirmation screen from one state with a body built from another can mislead the user. Freeze request data at a defined moment or prevent changes during the relevant phase. When several producers own the same name, deleting and rebuilding one field can accidentally remove another producer's legitimate values; field ownership should be explicit.

Values and ordering cross another boundary

MDN says values passed to append that are neither strings nor Blobs are converted to strings. Appending numeric zero does not send a typed number to the server, and appending a boolean does not make the receiver's parser understand a boolean. The receiver must parse and validate according to the field contract. File entries also have filename and content-type concerns. A browser allowing several same-name files does not imply that an upload endpoint accepts a batch.

If order matters, write that into the contract too. append creates entries in call order, but a server that converts them to an unordered set may lose the result of a drag-to-reorder interface. Test a swap of two selected values, not merely whether both values arrive. If order does not matter, avoid treating incidental iteration order as a stable identifier. Multiple values and duplicate values are also different questions: two distinct tags may be legal, while an accidental duplicate of the same tag may still be rejected.

A focused acceptance matrix follows transitions rather than one static append call: change a single selection, deselect an item, submit twice, start from an HTML form with existing names, send an empty collection, remove one file, and reorder two items. Compare the UI state, getAll, the final network payload, and the service's parsed result. Where a field must be single-valued, the server should enforce that rule rather than silently choosing an entry for a consequential operation. These are proposed application checks; only the independent Node API check above was executed. The Blob URL article covers a separate file-preview and saving boundary.

The practical decision is to use append for each member of a currently valid multi-value collection, and use replacement or fresh construction for a single current value. Apply the same cardinality rule at the receiver. Once the request is a snapshot of what the user currently chose, a deselected option has no entry to hide in a reused object's past.
