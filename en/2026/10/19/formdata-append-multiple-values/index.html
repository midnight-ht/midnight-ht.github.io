FormData append keeps repeated names: define field cardinality first

Choose append or replacement from the field contract, then verify how the server handles repeated names.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-19 · Estimated read 8 min
Translations
zh-CN en

Article

Appending the same field name twice can leave both values in FormData. Treating append like ordinary object-property assignment can introduce unexpected repeated entries into an upload form. Before choosing append or replacement, decide whether the field represents a single current value or a collection.

Matching names do not imply replacement

MDN’s FormData.append reference distinguishes the operations: append adds a new value to the end of the existing set, whereas set replaces all existing values for that name. Appending a previously unused name creates the field. A later append is therefore not an update to the earlier value.

const data = new FormData();
data.append("tag", "design");
data.append("tag", "delivery");

This unexecuted example illustrates a collection with two tags. It can match a genuine multiple selection. If the second operation was intended to change a single selected tag, retaining the earlier entry conflicts with the interface. The field contract determines correctness; repeated names should not be removed indiscriminately.

Separate editing state from an event history

Suppose a page reuses one FormData instance and appends a priority every time the user changes it. The interface displays the latest choice, while the object may retain earlier entries. A backend reading one entry might then act on a different value. Whether it takes the first, takes the last, reads an array, or rejects repetition depends on its parser and contract. The browser API does not choose that policy.

For a single-value field, replacing matching entries may be appropriate. For a multiple-selection collection, constructing a submission snapshot from current selections is often easier to reason about. Read the currently selected set rather than copying entries from the old object. When another module contributes fields, identify who resolves matching names instead of allowing both modules to append and leaving the server to guess.

This makes a deselected option absent because of current state, rather than dependent on how many past clicks happened. It is a design recommendation, not a report of a repaired project.

Also inspect objects created from an existing form. They may already contain matching control values. Appending a “corrected value” does not remove the earlier one merely because the programmer intended a correction. Inspecting complete entries is more informative than inspecting the last statement that wrote one.

Values have a type boundary too

MDN explains that values other than strings or Blobs are converted to strings. A boolean or number therefore needs interpretation according to the receiving form protocol. A frontend variable’s type does not establish that the server recognised the same type. File entries and text entries need their own field definitions.

During debugging, inspect all values for a name, then compare the network payload and the service’s parsed result. Reading one value does not prove a second is absent. Sending a request does not prove the service accepted multiple values as intended. For a field required to be single-valued, define whether the service rejects repetition or applies a controlled policy, especially when an operation has consequences.

Proposed checks can cover changing a single selection, deselecting multiple choices, repeated submission, and object reuse. None were executed here, and no backend framework’s repeated-name behaviour was verified. File handling also has a separate output and temporary-object lifecycle; see Blob URLs and file saving. Write the allowed number of values into the interface contract before choosing append or set.
