When PostgreSQL SUM Returns NULL, Count the Inputs First

Keep input-row count, known-amount count, and raw sum together before turning a PostgreSQL NULL aggregate into zero.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-20 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • PostgreSQL SUM returns NULL for an empty input and ignores null amount values.
  • Row count, known-amount count, and raw sum separate no rows, missing amounts, and a real zero.
  • COALESCE cannot create an account row absent from a grouped result.

A refunds report showing zero might describe three different situations. There are no matching refunds. There are refund rows, but none has an amount. Or there are known amounts that cancel to zero. If the API returns only a number produced by COALESCE(SUM(amount), 0), the report can no longer tell its reader which situation occurred. PostgreSQL returns NULL from SUM when there are no input rows; deciding how to display that result is a product decision, not a correction to the database.

Count the population being aggregated

The PostgreSQL 18 aggregate-functions reference describes sum as adding non-null input values. It also states that these aggregates, apart from count, return null when no rows are selected, and that coalesce can substitute a value when needed. “When needed” is the key qualification. A numeric endpoint may deliberately represent no activity as zero. A report that distinguishes missing data from a known result should retain more information before applying a default.

Imagine a hypothetical refunds table with an amount column. With no matching rows, COUNT(*) and COUNT(amount) are both zero and SUM(amount) is null. With two rows whose amounts are both SQL null, the row count is two, the count of known amounts is zero, and the sum remains null. With two known amounts of 10 and -10, both counts are two and the sum is zero. The latter has actual numbers participating in a calculation. These are expected results derived from the documented aggregate semantics, not results from a live database. The separate count rules are explained in the COUNT input article.

SELECT COUNT(*) AS rows_seen,
       COUNT(amount) AS known_amounts,
       SUM(amount) AS raw_total
FROM refunds
WHERE account_id = $1 AND created_at >= $2 AND created_at < $3;

That illustrative query keeps the three measures in one filter scope. When rows_seen is zero, there are no matching records in that scope. When rows exist but known_amounts is zero, records exist without values that can contribute to the sum. With a positive count of known amounts, raw_total is a sum over available values. An application may have draft, voided, or disputed refund states that should not be counted at all; the aggregate cannot choose that policy on its own. Authorization also affects the population. “No records visible to this user in this time range” is not a claim that the database has no refunds anywhere.

Where a default is applied changes the promise

An outer COALESCE(SUM(amount), 0) changes a null aggregate result into zero. It maps both an empty input and an all-null amount set to the same number. That may be acceptable for an endpoint whose documented meaning is simply a numeric contribution, especially if the schema prevents missing amounts in official records. It is too broad for a report that needs to say “amounts await completion.”

Moving COALESCE inside the sum does something else. SUM(COALESCE(amount, 0)) replaces null values in rows that exist. When there are no rows, there is still nothing to feed the aggregate, so its result remains null. The inner version may be particularly misleading when a missing amount means unknown rather than zero: it counts a placeholder as a known numerical contribution. The two expressions are not interchangeable formatting styles merely because both contain the same function name.

One interface rule could be: with no refunds, display “none this period”; with refund rows but no known amounts, display “amount pending”; with valid amounts, show a total and mark it partial when other rows still lack amounts. The API could carry the raw total and a status derived from the counts, leaving the display to the client. Another service may ban null amounts at write time and intentionally choose an outer zero for an empty period. Both can be sound if the contract, stored-data constraint, and user-facing label agree. The choice must be explicit before a query author starts replacing nulls throughout the stack.

Amounts that do exist introduce other constraints. A float type may have rounding behavior unsuitable for money; COALESCE does not fix that. Different currencies cannot be meaningfully summed without an exchange rule. A “month” filter needs a defined time zone and interval boundary. These are not exceptions to the empty-set behavior. They are reasons a numeric sum, even when non-null, still needs an understandable input population. A report that says “no refunds this month” based on a wrong date boundary may be semantically false despite correct aggregate syntax.

A missing group is a missing row

An overall aggregate query without grouping can return a summary row even when no records match. A query grouped by account_id has no group for an account with no matching refunds. There is then no output row on which an outer COALESCE can operate. If the product must list every authorized account, begin from that account population, join the eligible refunds, and aggregate per account. This is a result-shape decision, not a null replacement.

A left join introduces its own counting trap. COUNT(*) can count the placeholder row produced for an account with no refund, while COUNT(refunds.id) counts actual matching refund records. Moving a date filter into an outer WHERE can also discard accounts with no matching refund and unintentionally turn a left join into the behavior of an inner join. The exact SQL depends on schema and access rules; a generic copied query is not a safe substitute. Design the account population and filtered refund population separately, then check that totals and status counts come from the same authorized set.

Exports must carry the same meaning as the page. A UI that says “amount pending” while a CSV exports numeric zero invites a downstream system to treat unknown as confirmed. A machine-readable status and raw nullable total can keep that distinction even if one view later chooses a short label. This does not require exposing every diagnostic count to every audience; permissions and data granularity still matter. It requires the service to retain enough information to explain the number it publishes.

Acceptance cases should include no rows, all-null amounts, a genuine zero, a nonzero sum, and a missing account group. Check overall and grouped queries, then compare the page, API, and export under the same identity and time interval. These are a proposed test matrix, not executed database results. The decision to approve is the statement the report makes about each state. Once that statement is settled, COALESCE can implement a deliberate display choice instead of hiding an unresolved data-quality question.
