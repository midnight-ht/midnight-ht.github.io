When a valid zero disappears, check the default condition

Distinguish missing values, valid zero settings, and invalid input before choosing a default expression.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-19 · Estimated read 7 min
Translations
zh-CN en

Article

A user sets the retry count to zero, but the application uses three attempts. If zero means “do not retry,” the configuration may have been saved correctly and then overridden by a truthiness-based default. A default should supply missing information without silently undoing a valid choice.

Define what missing means

MDN’s nullish coalescing reference explains that ?? uses its right operand only when the left operand is null or undefined. Logical OR, ||, uses its right operand for a falsy left operand. Consequently, 0 || 3 selects the fallback, while 0 ?? 3 preserves zero. The following expression illustrates the language rule; it was not run as a project test.

const retries = settings.retries ?? 3;

It suits a contract in which nullish values mean “not configured.” An interface that uses zero to represent absence has a different contract. An operator’s name cannot decide that contract. A review should ask what an absent field, an explicit null, and zero mean, and whether saving and reading configuration preserve those differences.

Suppose a “disable automatic retries” option saves zero while runtime code selects three. The mismatch between a user’s choice and application behaviour is a concrete reason to change the condition. Calling an expression more modern is not. After correcting it, inspect the displayed value and the point where the application consumes the setting, rather than repairing only a preview.

Empty text and false need their own decisions

MDN highlights that empty strings and zero can be useful values. A boolean false can also express an intentional choice. Applying one truthiness-based fallback can reopen a disabled switch or replace deliberately empty text. Whether empty text is acceptable belongs to that field’s requirements, not a rule copied from a neighbouring field.

For each setting, record the default, whether explicit null is allowed, whether zero is within range, and how empty text is treated. A retry count may allow zero but reject negative numbers. A title may have a default while rejecting user text consisting only of spaces. Both fields have defaults, yet their missing-value conditions need not match.

Nullish coalescing is not validation. Negative values, incorrect types, and out-of-range numbers do not disappear because this operator is used. If a form supplies the string zero, the input layer must decide whether to parse it or reject it. Do not assign that conversion to the default expression. Configuration files, controls, and API inputs should follow a consistent convention.

Defaulting determines what happens without a setting. Validation determines whether a supplied setting is acceptable. Silently replacing invalid input with a default can mislead a user into believing the requested configuration took effect.

Make combinations readable

MDN also states that ?? cannot be combined directly with || or && without parentheses; doing so causes a syntax error. Decide the intended grouping first. If the combination becomes hard to read, named intermediate steps can make the business conditions easier to review.

A proposed check should cover zero, an absent field, explicit null, false, empty text, and invalid ranges, with expectations derived from the field contract. These checks were not executed here. Server acceptance must follow the same rules; see Form validation and server authority. Before submitting the change, write one reviewable sentence specifying exactly when this field uses its default.
