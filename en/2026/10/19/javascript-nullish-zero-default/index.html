Why a Zero Setting Becomes the Default in JavaScript

Define missing, null, valid zero, and invalid input before using a JavaScript default; verify each layer that consumes the value.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-20 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • Logical OR replaces numeric zero; nullish coalescing defaults only on null or undefined.
  • Nullish coalescing preserves invalid values too, so validation has a separate role.
  • The Node v24.21.0 check establishes local operator results, not application behavior.

A user selects zero automatic retries, sees zero in the settings form, and the application still makes three attempts. A likely place to inspect is a truthiness-based fallback such as settings.retries || 3: JavaScript treats zero as falsy and chooses three. Nullish coalescing can preserve zero, but the first design decision is more fundamental. Which input means “no setting,” which is an intentional choice, and which should cause a validation error?

A default has a field-specific condition

MDN's reference on nullish coalescing says that the right operand of ?? is used only when the left operand is null or undefined. Logical OR, ||, uses the right operand when the left is falsy. Thus 0 || 3 evaluates to three, whereas 0 ?? 3 evaluates to zero. False, an empty string, and NaN are also falsy for logical OR. Its truthiness check is not a general test for an absent field.

A minimal script run under Node v24.21.0 confirmed those operator results in that environment: zero became three with OR and stayed zero with nullish coalescing; false and an empty string were preserved only by the latter. The complete script and raw output are retained with this editorial batch. This run is a check of that Node environment, not evidence that a browser form, API, or production configuration path behaves correctly. The configuration scenario in this article remains hypothetical.

Write a semantic table for retries before changing the expression. A missing property might mean use the default of three. Explicit null might mean restore that default, or it might mean erase an inherited setting. Numeric zero might mean disable retries. Positive integers might set the limit. Negative numbers, fractions, strings, and nonnumeric values need a clear acceptance or rejection policy. The expression settings.retries ?? 3 fits only a contract in which both null and undefined mean “not configured.” If an API uses zero for absence, or null for a distinct action, swapping an operator changes behavior rather than repairing it.

The same field can cross storage, API, runtime, and display layers. Look for a fallback at each boundary. Fixing the runtime expression while the form still renders savedValue || 3 may make the application stop retrying but keep telling the user it will retry three times. Conversely, a correct display does not show what the code that performs the retry consumes. Place the expected zero beside the stored value, the fetched response, the rendered control, and the actual retry policy. A single good screenshot is not sufficient evidence for that chain.

Separate parsing, validation, and defaulting

Type conversion is a second trap. HTML form values often enter application code as strings. The string "0" is truthy and not nullish, so both kinds of fallback preserve it as a string. Neither expression checks that it is the number zero. Later addition or comparisons may behave differently from what the configuration review expected. Parse or reject it at a defined input boundary. Do not ask the default expression to decide absence, convert a type, and enforce a range all at once.

For a hypothetical policy that accepts integers from zero through five, a readable decision sequence is: if the input is undefined or null, choose three; otherwise require a number that is an integer in that range; reject everything else. This sequence preserves zero and rejects the string zero unless a prior input parser deliberately converts it. The bound of five is a teaching assumption, not a recommendation for any product. An actual service must derive its accepted range from its own behavior and operational limits. A longer branch can be easier to review than a compact expression because it exposes where invalid input is rejected instead of silently turned into a default.

Multiple configuration sources need another rule. Suppose an organization defaults to three, a user chooses zero, and a task provides no value. A nullish chain in task, user, organization order preserves the user's zero if nullish means “inherit from the next level.” But if an explicit task null means “disable all retries,” the same chain skips that instruction and selects the user value. JavaScript cannot define an inheritance protocol for the product. Name each source and its override behavior, then choose a representation and expression that implement it. Recording which source supplied the final value also helps explain a setting to the user.

Preserving a falsy value can preserve a bad value

An empty string may be an intentional text choice or a violation of a required-title rule. Boolean false may intentionally switch off notifications. NaN is seldom a valid count, yet nullish coalescing retains it. Do not mechanically replace every logical OR default with a nullish one. For a title, whitespace-only input may deserve an error even if an absent title receives a default. For a switch, false must usually survive when default is true. For a retry count, zero, negatives, fractions, and nonnumbers each need an expected outcome. Defaulting answers “what happens without a value?” Validation answers “may this supplied value be used?” They need separate ownership.

MDN also points out a syntax boundary: mixing ?? directly with || or && without parentheses is a syntax error. Parentheses make grouping explicit, but they do not make a truthiness rule appropriate for a zero-valued setting. When several layers and conditions appear, named intermediate values and branches are often easier to check. Optional chaining can handle a missing settings object, but it may also collapse “object absent” and “property undefined” into the same fallback path. Whether that is acceptable follows from the configuration contract.

Serialization deserves its own row in the test table. MDN’s JSON.stringify reference says that with default serialization, an object property whose value is undefined is omitted, while a property explicitly set to null remains present. If a patch API uses absence for “leave unchanged” and null for “clear,” converting the in-memory configuration to a request body can alter the state that the receiver sees. Inspect the transmitted body and the receiver's field-presence decision, rather than comparing only expressions in memory.

The acceptance matrix should include absent, undefined, null, numeric zero, a positive integer, a negative number, string zero, empty string, false, and NaN. For each, say whether the field defaults, survives, or fails; then check saving, reading, display, and execution. The Node operator check above covers only a subset of language outcomes, and no application-level sequence is claimed to have run. Server-side input and authorization checks remain necessary; the form-validation article covers that boundary. A reviewable fix ends with one sentence: this particular field uses its default only under these stated conditions.
