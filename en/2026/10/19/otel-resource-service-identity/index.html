Telemetry Arrived, but Which Service Produced It?

Telemetry delivery does not prove service identity. Check resource names, initialization, and exported attributes separately.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-19 · Estimated read 8 min
Translations
zh-CN en

Article

Successful telemetry delivery does not establish correct service identity. Inspect the resource attributes in exported data before deciding whether the service can be identified as intended. When a default name appears, transport may already be working while the agreed logical service name is still absent. Those are separate acceptance results.

What the default name explains

The OpenTelemetry service conventions, currently labeled 1.44.0, describe the logical service name. Horizontally scaled instances of one service must share that name. If it is unspecified, the convention requires a fallback with the executable name appended; the plain fallback applies when the executable name is unavailable. These are the documented rules, not a claim that every historical SDK behaves identically.

Seeing unknown_service, with or without a process suffix, therefore does not establish an export-network failure. Conversely, an attractive service card in a backend does not prove that its name came from the intended configuration. Troubleshooting needs an identifiable producer, beyond evidence that a telemetry item arrived.

Identical names become a query problem

Imagine an order API and an asynchronous notification process that should be investigated separately. If both retain the same default name, filtering by that name alone cannot distinguish them. This hypothetical example concerns insufficient information in a filter. It describes no incident at this site and assigns no measured investigation cost.

I would first document which deployments belong to one logical service and which must remain distinct. Inventing a new service name on every process start substitutes naming churn for instance identity. Putting a user identifier in the service name answers another question again. Service, instance, and request attributes should each express the entity they are meant to describe. Exact field choices still require checking the actual SDK and backend.

Compare configuration intent with exported output

The resources concept page explains that a Resource describes the entity producing telemetry. Its association with a Provider is established when the Provider is created and cannot later be changed. The page, last modified in February 2026, also recommends setting the service name explicitly. It offers concepts and configuration entry points, not execution evidence for a particular language’s initialization code.

That suggests checking both before initialization and after export. Record the expected name, configuration source, and Provider creation point; then inspect resource attributes from a controlled request. An environment variable in a deployment manifest establishes intent. It does not prove the process received it or that the library read it at the necessary time.

Check whether automatic instrumentation and manual initialization use the same configuration path. This article gives no universal cross-language precedence rule and does not recommend creating duplicate Providers without understanding the implementation. If a backend or intermediary rewrites resource attributes, retain evidence before and after that step to locate the change.

Keep one sample that can be explained

A proposed acceptance check would associate a dedicated test request with its known service, instance, and exported sample. Verify that the intended grouping finds it, then use a different logical service to check that the filter distinguishes the two. These requests have not been executed for this article.

The sample does not need customer email addresses or authorization data. Fields propagated between calls require their own review; see the analysis of Baggage propagation boundaries. Record both “data arrived” and “identity matches the agreement” in the release evidence. If only the first is established, leave the second explicitly unverified.
