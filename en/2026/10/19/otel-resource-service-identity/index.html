Both traces say unknown_service: check export or identity first?

Received spans prove transport, not service identity. Compare Resource attributes at Provider creation, collection, and backend grouping.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-21 · Estimated read 16 min
Translations
zh-CN en

Article

Key takeaways

  • Replicas of one logical service share service.name; instance IDs distinguish replicas.
  • Resource is bound when the Provider is created; compare configuration intent with exported attributes.
  • Trace default or rewritten names through process, collection, intermediary, and backend.

An order API and a notification worker both send spans to the backend, yet the service list shows only unknown_service. Filtering by that name mixes the latency and errors of two different processes. Naming every replica as a separate service would create the opposite problem: one logical service split across several graphs. The question is not only whether telemetry arrived. It is which Resource identity each item carried when produced, and where that identity changed along the pipeline.

Define the logical service before interpreting the fallback

The current OpenTelemetry service semantic conventions page is labeled 1.44.0. Its service.name is the logical service name and must be the same across horizontally scaled instances. If unspecified, the SDK must fall back to unknown_service: followed by the executable name, or plain unknown_service when that name is unavailable. A fallback on a received span therefore does not establish a network export failure. Nor does the backend’s service-card title prove which raw value the SDK sent. Read the actual exported resource attributes before diagnosing a particular SDK or UI version.

Suppose the order API has two replicas, A and B, and the notification worker has one process. A and B should both carry service.name=order-api; the worker should carry service.name=notification-worker. They may share service.namespace=commerce while remaining different logical services. Each order replica has its own service.instance.id. That field distinguishes instances, not services; the convention requires it to be unique for the same namespace-and-service pair. These names and counts are a design exercise, not observations from a deployed backend.

This identity map exposes two errors. If all three processes use the same fallback, a service-name filter merges orders and notifications. If the replicas are named order-api-1 and order-api-2, service-level failure rates are split across two identities. Putting a user ID or request ID into service.name would create a new identity for each event and send high-cardinality, potentially sensitive values into a service index. Logical service, running instance, and request are different levels of description; one field cannot answer all three questions.

Namespace should express a real grouping boundary as well. A separate system may have a component also called order-api; querying name alone could merge them, while namespace plus name can keep them apart. Conversely, putting each build number or deployment environment into the namespace makes one service change identity at every release. Use attributes intended for version and environment instead. An instance ID needs to distinguish concurrently existing instances within the documented pair; avoid exposing an underlying host identifier to every reader just to get a unique string. Attribute design affects both backend grouping and the visibility of resource metadata.

Resource identity is bound when the Provider is created

The OpenTelemetry Resources concept page explains that a Resource is associated with a TracerProvider or MetricProvider at initialization and that this association cannot later be changed. Telemetry produced through the Provider carries it. The page recommends explicit service.name, either in code or through OTEL_SERVICE_NAME. An environment variable in a deployment manifest only records intent. If it never reaches the process, auto-instrumentation creates a Provider before intended configuration, or separate initialization creates another Provider, exported attributes can still differ. Which explanation applies depends on the actual language SDK and startup sequence; a fallback alone does not identify the cause.

An auditable initialization record needs three points: expected service name and configuration source at deployment, the nonsecret configuration actually visible at process startup, and Resource attributes in the exported sample. If the order process reads order-api but the collector receives a fallback-named span, inspect Provider creation and auto-instrumentation timing. If the collector receives order-api while the backend displays a different name, inspect Collector processors, exporter mapping, and backend grouping. If both ends have the fallback, return to process configuration. Do not create duplicate Providers or claim a language-independent precedence rule without checking the implementation.

Make three samples a falsifiable acceptance check

Here is a hypothetical test that has not been run. Send a controlled request to order replica A and another to B, then trigger one controlled notification-worker task. The intended result is three spans at the collection point. A and B share service.name=order-api but have different instance IDs; the worker has service.name=notification-worker and its own instance. A query for service.namespace=commerce plus service.name=order-api should find A and B but not the worker. Querying the worker name should find only its sample. If collection and backend results satisfy those relationships, the evidence establishes that identity is distinguishable, not merely that three spans were received.

Change one input: leave replica A’s OTEL_SERVICE_NAME unset. Under the current convention it may fall back to a name with the executable suffix and vanish from the order-service query; B and the worker still appear under their assigned names. Acceptance should fail because two replicas of one logical service no longer group together. If the backend UI hides the suffix and shows only unknown_service, inspect raw attributes before claiming the SDK emitted the plain fallback. A different counterexample has a Collector rewrite all three names to order-api. The collection-side identities were correct but the backend now merges them. Changing the application’s environment variable would not repair that processor rule.

Test markers should be sufficient to correlate controlled samples without copying customer email or credentials into Resource. A Resource describes the telemetry producer, not the request. Cross-process context propagation has a different policy boundary; the site’s OpenTelemetry Baggage article covers that risk. Make dashboard grouping explicit too. Service name alone can merge same-named components in distinct namespaces; grouping by instance ID can yield a new curve whenever a replica changes. Choose dimensions that answer the investigation question.

Begin acceptance at a raw export sample from one controlled request, checking its Resource and signal type. Keep sanitized samples before and after any Collector processing, then check backend queries and service cards. This locates four possible mismatches: configuration absent from the process, Provider created too early, intermediary rewrite, or display aggregation. Skip the Collector comparison if the deployment has none. If the system exports metrics but not traces, check the Resource relation on metrics rather than inventing a span. No such requests or comparisons were executed for this article. Real results require the process configuration, collection samples, and query output.

The eventual fix depends on the location. A fallback in the raw sample points toward configuration and initialization. Correct raw attributes but wrong backend grouping point toward mapping or queries. Only some replicas present calls for a deployment-difference and sampling/export-path check. Do not remove one unknown_service label by promoting every Pod, user, or request to a new service. A stable logical name, distinguishable instances, and samples traceable to their source turn “telemetry arrived” into a verifiable answer to “which service produced it?”
