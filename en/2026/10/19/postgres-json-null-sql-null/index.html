How do JSON null, SQL NULL, and a missing key differ?

Preserve JSON type and key presence before combining missing fields, explicit clearing, and an absent SQL value.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-19 · Estimated read 7 min
Translations

Article

SQL NULL, JSON null, and an absent object key represent different states. Preserve JSON type information before deciding which states a filter should combine. A blank display does not establish that the stored values are equivalent.

The same word can describe different layers

The PostgreSQL 18 JSON-function reference describes jsonb_typeof as producing the top-level JSON type as text. A JSON null produces the text ‘null’, which must be distinguished from SQL NULL. Its examples also show that applying the type function to an SQL NULL produces SQL NULL.

Imagine an optional profile column called payload. An API might define a whole-column SQL NULL as “profile not received,” a JSON null under a particular key as “explicitly cleared,” and an absent key as “unchanged in this update.” These are hypothetical protocol choices, rather than meanings PostgreSQL assigns automatically. A team may adopt a different contract.

If those states matter, both writing and reading must preserve them. An update endpoint that removes every empty value can destroy the evidence needed to determine whether someone explicitly cleared a field. A later type check cannot recover an intention lost earlier in the pipeline.

Inspect presence and type before extracting display text

These illustrative expressions have not been executed. They assume a JSONB payload and a top-level nickname field in an object:

-- Illustrative only; not executed.
payload IS NULL
payload ? 'nickname'
jsonb_typeof(payload -> 'nickname') = 'null'

The first examines the whole SQL value. In this object context, the second checks for a top-level key. The third examines whether the extracted JSON value is JSON null. The official reference also explains that extraction yields SQL NULL for a missing key or a mismatched structure.

A TRUE result from the third expression confirms that the extracted value is JSON null. A result that is not TRUE does not establish that the key is absent: another JSON type or a null column can also be involved. Confirm the input shape and the field level before interpreting the result.

Include the string “null” in the design. Its JSON type is string, rather than null. Screen text alone cannot distinguish those characters entered by a user from an explicit clearing operation. Objects, arrays, and scalars are all possible JSON shapes; if the endpoint accepts only objects, state that requirement at ingestion.

Text extraction can also collapse distinctions needed later between a missing key and JSON null. Keep the JSON value until the classification is complete, then convert it for display. Combining the states is reasonable when the contract intentionally treats them alike, but should be an explicit protocol decision.

Resolve the meaning before considering an index

Define how a non-object payload is handled: reject it, migrate legacy data, or expose another state. Silently treating a structural error as an omitted update can turn invalid data into apparently normal intent. Preserve that decision with the API version.

The October 10 article on JSONB operators and indexes covers index coverage separately. This article promises no execution plan or speed. Proposed cases should retain SQL NULL, an empty object, JSON null, the string “null”, and an ordinary string, with an expected read display and update action for each. No cases were executed here. Confirm the protocol first, then verify serialization, storage, and retrieval together.
