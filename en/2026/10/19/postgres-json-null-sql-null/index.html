PostgreSQL JSON Null and SQL NULL: Preserve Presence Before Text

Classify SQL NULL, missing keys, JSON null, and the string null before defining patch and display behavior.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-20 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • The text null from jsonb_typeof is distinct from SQL NULL.
  • Check key presence and JSON type before text extraction collapses useful states.
  • A patch contract must assign distinct actions to omission, JSON null, and the string null.

A settings screen can show a blank nickname for four different stored states: the whole PostgreSQL column is SQL NULL; the JSONB object has no nickname key; that key contains JSON null; or it contains the string "null". An update endpoint may need to treat those states differently. Was the field omitted from a patch, explicitly cleared, or set to four literal characters? Keep presence and type until the application has answered that question.

The two nulls belong to different layers

The PostgreSQL 18 JSON functions and operators reference says jsonb_typeof returns a text label for the top-level type of a JSON value. JSON null produces the text null; applying the type function to SQL NULL produces SQL NULL. This is database behavior. Defining a null column as “profile never received,” an absent object key as “unchanged by this patch,” and JSON null as “the user cleared the value” is a possible API protocol, not a meaning PostgreSQL assigns by itself.

Assume a JSONB column named payload that is required to contain a top-level object whenever it is not SQL null. payload IS NULL tests the SQL column. payload ? 'nickname' checks whether that key exists at the object's top level. jsonb_typeof(payload -> 'nickname') = 'null' asks whether the extracted JSON value is JSON null. If the key is absent, extraction returns SQL null and the type comparison is not true. If the key contains the string "null", its JSON type is string. A false or unknown result from the third test alone does not prove absence: a different JSON type, a null column, or a shape mismatch may explain it.

SELECT payload IS NULL AS column_missing,
       payload ? 'nickname' AS has_nickname,
       jsonb_typeof(payload -> 'nickname') AS value_type,
       payload ->> 'nickname' AS display_text
FROM profiles WHERE id = $1;

This is an illustrative query, not an executed database check. The table and column names only make the state classification easier to discuss. column_missing, has_nickname, and value_type preserve separate evidence. display_text belongs after the classification. Text extraction can produce SQL null for both a missing key and a JSON-null value; the string "null" appears as text. Once an API sends only the display text, a later client cannot reconstruct why it was blank. The reference also notes that extraction returns SQL null for absent paths or mismatching structures rather than raising an error. That convenience can hide a malformed document if the application assumes every payload is an object.

Write and read the same patch contract

A partial update makes the distinction practical. Under one possible protocol, {} means do not touch the nickname, {"nickname":null} means clear it, and {"nickname":"null"} means set it to literal text. If the client serialiser inserts null for every untouched field, the server may clear data the user never edited. If the server discards all null properties before applying a patch, an explicit clear request is lost. Once the intention disappears at this boundary, a perfect SQL query cannot recover it. Decide separately whether a whole-column SQL null is allowed, whether an empty object means something distinct, and whether old data needs migration.

A state table makes these choices reviewable. For SQL null, an empty object, a key containing JSON null, a key containing the string null, and a normal string, record what the API returns, what the user sees, how an omitted-key patch behaves, and what an explicit clearing patch does. Several rows can legitimately render as blank while remaining distinct internally for the next operation. If the business truly treats two states alike, merge them intentionally at a documented boundary. A blank screenshot is not evidence that the stored states are equivalent.

If JSON null means “clear,” decide whether the stored current state retains the key with null or removes the key. They can look identical in a simple text field, but the existence operator yields different answers. If an audit trail or later merge must know that clearing happened, deleting the key from the current document loses that evidence unless the action is recorded elsewhere. An event log can preserve intention while the current-state document uses a simpler representation. Conversely, if the protocol explicitly treats null and absence as synonyms, preserving a difference forever may add needless query branches. The choice follows downstream behavior, not the shortest SQL expression.

Shape errors and SQL filtering need their own branches

The ? operator also checks for a top-level string element in a JSONB array. A document that is an array must not be silently interpreted as an object with no nickname if the endpoint contract requires an object. Validate the top-level type at ingestion, or classify legacy non-object values for migration. A nested nickname is another shape: a top-level key test cannot inspect a key inside profile without changing the path. Specify the allowed document shape and depth before copying a predicate into production.

SQL's three-valued logic matters in filters. A comparison such as jsonb_typeof(payload -> 'nickname') = 'null' becomes unknown when extraction yields SQL null; a normal WHERE does not select it as true. To find “key missing or explicitly cleared,” state those alternatives and the whole-column-null policy separately. A COALESCE around a predicate can turn unknown into false, but that transformation is only correct after the intended business set has been defined. Index support for a chosen operator is a further concern, discussed in the JSONB indexing article. Index convenience should not redefine what a user's clearing action means.

A useful acceptance set follows the value through client serialisation, API validation, storage, and retrieval. Include the five states above, plus a non-object JSON value, a missing nested path, and an explicitly empty string. For each, specify whether the system rejects, retains, converts, or displays it, and whether an omitted field leaves the existing value untouched. These are proposed checks; no database execution is claimed here. The protocol can be written in one testable sentence: omit the key to preserve its old value, send JSON null to clear it, and treat the string null as ordinary text. A team choosing different semantics should replace that sentence in its contract and make every write and read path follow the replacement.
