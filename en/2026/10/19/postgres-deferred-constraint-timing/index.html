Why can a deferred constraint fail after the final write succeeds?

Separate writes, deferred checks, and commit confirmation so transaction errors reach the correct application branch.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-19 · Estimated read 8 min
Translations
zh-CN en

Article

A deferred constraint may be checked only when the transaction commits. Success from the last write therefore cannot establish that the business operation is complete. Constraint timing and commit failures need a visible place in application control flow.

Temporary inconsistency needs a repair window

The PostgreSQL 18 SET CONSTRAINTS reference explains that DEFERRED checks occur at transaction commit. A NOT DEFERRABLE constraint is unaffected by this command. Inspect the constraint definition before assuming that adding a timing statement can postpone every check.

Consider a hypothetical import that inserts child records before their parent records. If the relevant foreign key is correctly declared deferrable and is in deferred mode, a temporarily missing reference can remain until checking occurs. No SQL was executed for this example. The final state must still satisfy the relationship; postponement does not permit a permanently missing parent to commit successfully.

That design needs an explicit repair window: which operation temporarily breaks the relationship, which later operation restores it, and what happens when the sequence fails. Without those answers, deferral may simply move a useful statement error farther from its cause without enabling a necessary business operation.

A check point is available inside the transaction

The reference also specifies retrospective checking when a constraint changes from DEFERRED to IMMEDIATE. Pending modifications are checked during SET CONSTRAINTS. If a violation exists, that command fails and the mode does not change. A deliberate check point can therefore reveal an incomplete repair before the final commit.

-- Illustrative only; constraint name is hypothetical.
SET CONSTRAINTS order_customer_fk IMMEDIATE;

This unexecuted fragment needs the actual constraint name. Naming the intended constraint makes the scope easier to review. ALL can include other deferrable constraints, complicating an explanation of which changes are being checked. The transaction design must also cover writes after the mode switch, rather than ending its reasoning at that point.

Passing the check point does not commit the transaction. It establishes the relevant checks at that moment; later statements and final commit have their own outcomes. The October 16 article on RETURNING and transaction boundaries separates returned rows from commit confirmation. Deferred checking adds another timing boundary that should be named in the same control flow.

Keep the scope narrower than “all constraints”

The documented setting affects unique, primary-key, foreign-key, and exclusion constraints under their applicable deferrability conditions. NOT NULL and CHECK are not postponed this way. A constraint’s category alone does not establish that its particular declaration can be deferred or that its current mode is deferred.

Proposed acceptance cases should include both a temporary inconsistency repaired by later writes and an inconsistency left unresolved at a check point or commit. The latter must fail. Exercise the application’s actual transaction entry point, including the code responsible for receiving a commit error, rather than checking only an individual insert.

If a framework wraps transactions, establish whether the caller enters its success branch before or after that wrapper finishes. Catching errors around one write can miss a later commit error. These cases have not been run here. Arrange external completion notices around the confirmed transaction result; any transactional dispatch record needs separate delivery verification. Name the write, check, and commit boundaries before deciding where success belongs.
