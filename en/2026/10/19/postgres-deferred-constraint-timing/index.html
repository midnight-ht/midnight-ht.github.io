Deferred PostgreSQL constraints: when can an application report success?

An order insert can succeed while a deferred constraint later rejects commit. Trace the check, checkpoint, and response boundary.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-20 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • A deferred constraint can reject an otherwise successful sequence of write statements at commit.
  • Changing a constraint from deferred to immediate checks outstanding modifications at that checkpoint.
  • The application success response belongs after the actual transaction outcome.

An INSERT returns a new row identifier, and the application tells its caller that an order was created. Then COMMIT fails because a deferred foreign key is still violated. The write statement succeeded, but the transaction did not. Deferring a constraint gives a transaction room to repair a temporary inconsistency; it also moves some errors closer to the transaction exit. An application must place its success boundary after the check that can still reject the work.

Mark the check on the transaction timeline

The PostgreSQL 18 SET CONSTRAINTS reference distinguishes IMMEDIATE, checked at the end of a statement, from DEFERRED, checked at transaction commit. A constraint may be declared DEFERRABLE INITIALLY DEFERRED or DEFERRABLE INITIALLY IMMEDIATE. A NOT DEFERRABLE constraint cannot be switched into deferred mode with this command. The setting applies within the current transaction, rather than permanently altering the table.

Imagine a migration that must insert an order before inserting its referenced customer. The following SQL is illustrative and has not been run against a database for this article. The schema, values, and constraint name are hypothetical.

BEGIN;
SET CONSTRAINTS order_customer_fk DEFERRED;
INSERT INTO orders (id, customer_id) VALUES (901, 42);
INSERT INTO customers (id) VALUES (42);
SET CONSTRAINTS order_customer_fk IMMEDIATE;
COMMIT;

After the order insertion, customer 42 is absent. An immediate foreign key would reject that statement. A deferrable foreign key, successfully switched to deferred mode, allows the transaction to proceed. The next insertion repairs the relationship. Switching back to immediate mode asks PostgreSQL to check outstanding changes at that point; the final commit remains a separate event. This is useful only because the transaction ends in a valid state. Delaying a check does not authorize permanently broken references.

Now remove the customer insertion. Switching to immediate mode should fail. If that explicit switch is omitted, the failure moves to commit. In both cases the log could say that the order insertion succeeded, yet neither transaction should leave an order behind. A meaningful test needs both the repaired path and this unrepaired path, including a check of the final database state.

A checkpoint is not a commit

The PostgreSQL reference says a DEFERRED to IMMEDIATE switch retroactively checks modifications that have not yet been checked. If a violation exists, the SET CONSTRAINTS command fails and does not change the mode. Placing a checkpoint after a migration segment can therefore reveal an error closer to its cause. It does not guarantee that later statements or the final commit will succeed.

Choose the constraint name deliberately. SET CONSTRAINTS ALL changes every deferrable constraint in the transaction, which may make a failure harder to attribute when a migration touches both foreign keys and uniqueness rules. PostgreSQL also permits the same constraint name on different tables within a schema. An unqualified name is resolved through the schema search path and can match more than one constraint. Before relying on a named switch, inspect the actual definitions, schema and search path used by the transaction.

The setting is narrower than a generic promise to postpone all validation. The documented affected types include unique, primary-key, foreign-key and exclusion constraints. NOT NULL and CHECK are not deferred through this setting. Even for an affected type, the particular constraint must be declared deferrable. A useful debugging sequence is to confirm the DDL, the mode at the point of writing, and the transaction that owns both commands. A line of ORM configuration by itself proves none of those facts.

Follow the boundary through application code

A transaction helper often executes several statements inside a callback and commits only after the callback returns. Sending an API success response, writing a completed-business-event record, or triggering an external notification inside that callback can therefore happen before deferred checks run. The database result should be handled where the helper commits, and the caller should see success only after that boundary confirms it. External mail and queues need their own delivery design; a successful database commit does not prove that a separate provider delivered a message.

Check which layer actually manages the transaction. Some clients autocommit individual statements; frameworks may wrap a request; a connection pool can send two supposedly related commands to different connections if the transaction handle is not passed through. Log the transaction entry and exit and inspect connection ownership before assuming the example SQL maps to the application. Otherwise the timing diagram describes a transaction that the code never created.

A focused acceptance set has three paths. First, insert a temporarily broken reference, repair it in the same transaction, then require the explicit checkpoint and commit to succeed. Second, leave the reference broken and require the checkpoint or commit to fail, with no resulting row. Third, pass an early checkpoint, introduce another violation, and require commit to fail. Run these through the application’s real transaction entry point so that the test sees errors raised when the wrapper exits. Testing only the individual INSERT misses the important failure location.

There is also a design tradeoff. If a batch import or relationship reorder genuinely needs a short repair window, deferred checking can support it. If no temporary inconsistency is necessary, immediate checking usually places an error nearer to the statement that caused it. For a long migration, a deliberate sequence of temporary break, repair and immediate check can make each segment easier to diagnose. Switching to immediate mode affects subsequent statements too; a later segment that needs deferral must explicitly establish that mode again.

The site’s article on RETURNING and transaction boundaries explains why a returned row is not proof of commit. Deferred constraints add another reason to wait: every write statement may have completed while the transaction remains rejectable. Record the declared constraint, mode changes, check failure point and final row state. That evidence supports a success response much better than a successful statement log.
