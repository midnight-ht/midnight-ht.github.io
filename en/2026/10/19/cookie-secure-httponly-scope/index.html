Why a Secure cookie may still be readable by JavaScript

Separate cookie transport, script access, and automatic request attachment before choosing Secure, HttpOnly, and SameSite.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-20 · Estimated read 13 min
Translations

Article

Key takeaways

  • Secure restricts transport while HttpOnly restricts script access.
  • A script can cause an eligible request carrying an HttpOnly cookie without reading its value.
  • Cookie attachment conditions and server authorization require separate tests.

A session cookie has the Secure attribute, yet a script on the page can still read it through document.cookie. This is not necessarily a browser defect. Secure primarily restricts the transport used when the cookie is sent with requests. HttpOnly addresses script access. A security review also needs a third question: under which requests will the browser attach the cookie automatically? Answering only one of these questions leaves the session behavior unexplained.

Put transport, visibility and attachment on one request diagram

The MDN Set-Cookie reference says that a Secure cookie is generally sent over HTTPS, with a localhost exception. It also warns that Secure does not prevent JavaScript from reading a cookie when HttpOnly is absent. HttpOnly prevents access through script interfaces such as Document.cookie, but JavaScript-initiated fetch() or XMLHttpRequest calls can still carry the cookie. “The script cannot read the credential” and “the script cannot cause an authenticated request” are therefore different claims.

Consider this hypothetical response header:

Set-Cookie: session=opaque; Secure; HttpOnly; SameSite=Lax; Path=/

opaque is a placeholder, not a live credential. In a supporting browser, page JavaScript should not obtain this cookie's value through document.cookie. Eligible HTTPS requests may still include it automatically. If a same-origin page has a cross-site-scripting flaw, HttpOnly reduces direct disclosure of the cookie value, but it does not alone stop injected code from calling an endpoint as the user. The server must check identity, object permissions and operation conditions; the page must still address the injection flaw.

Remove HttpOnly while keeping Secure. A script on the HTTPS page may again read the cookie: that is the phenomenon behind the title. Reverse the experiment by keeping HttpOnly and removing Secure. Script visibility changes, but the expected transport restriction no longer follows from the header. These are distinct negative cases. Check the received response and browser behavior with a dummy session value rather than exposing a real token in logs or screenshots.

Other attributes shape where the browser sends it

Domain controls eligible hosts. Omitting it produces a host-only cookie, narrower than a domain cookie shared with subdomains. Path selects request paths, while SameSite controls certain cross-site request contexts. MDN explicitly cautions that Path is not a security boundary against unauthorized reading from another path; the site's Cookie Path article develops that distinction. SameSite can mitigate some cross-site request-forgery scenarios, but it is not a substitute for server authorization. Whether a particular cross-origin API request carries credentials also depends on the request's credential mode and browser rules. The header alone is insufficient to predict every call.

Consider a hypothetical POST /profile/email operation. A script running in an authenticated page could cause the browser to send the session cookie with a request that changes the email address, even though the script cannot inspect the HttpOnly cookie itself. The server must still require the appropriate authorization and any necessary anti-forgery checks. This example is a threat model, not a claim about a particular site's implementation. It explains why protecting the credential from direct reading is valuable but incomplete.

SameSite deserves its own test matrix. MDN notes that some browsers apply Lax by default when the attribute is omitted, and that a permissive version of the default can include recently set cookies on certain POST requests. Relying on an omitted attribute as a stable product contract is therefore risky. If a login redirect, cross-site embed or identity-provider return path requires a particular behavior, set an intentional value and test the target browsers and methods. If cross-site attachment is unnecessary, narrow it to the range the product actually needs.

Cookie name prefixes can constrain accidental configuration in supporting browsers. The documented __Host- prefix requires Secure, Path=/ and no Domain, binding the cookie to the host rather than a parent domain. Prefixes with __Http- also require HttpOnly. These checks do not authorize requests on the server. They can also break an existing cross-subdomain login flow if applied without examining which hosts currently need the credential. Draw the actual host and request routes before changing the name.

Check the header and the behavior separately

First, inspect the real login response: what Set-Cookie fields arrived, whether the same name was set more than once, and whether the response came through HTTPS or the special localhost development case. Then use a test account to inspect whether the cookie is readable by script and which requests carry it: an allowed path, a different path, a relevant subdomain and a cross-site scenario. Record method and credential mode for cross-site tests. Finally check whether a sensitive server endpoint rejects an unauthorized action even when a browser supplies a session cookie.

A migration review should also search for old cookies with the same name but different Domain or Path attributes. A browser can hold more than one such cookie, and a server may see an unexpected value if it assumes a single name uniquely identifies the session. The practical check is to inspect the complete request Cookie header and the response history for a test account, then retire obsolete variants deliberately. This does not change what Secure and HttpOnly mean; it prevents a correctly configured new cookie from being confused with a leftover one.

These are proposed acceptance checks; no live application was tested for this article. A review report should state four separate results: transport restriction, script visibility, request attachment conditions and server authorization. A failure in one points to a different fix from a failure in another. For session credentials, secure transport and blocking script access are often sensible starting points, but the exact host and cross-site settings must fit the product's login routes. A checkbox marked Secure does not answer the original question of whether scripts can read the value or what those scripts can do afterward.
