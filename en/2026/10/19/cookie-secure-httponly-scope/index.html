Can Scripts Read a Cookie Marked Secure?

Secure controls transport; HttpOnly controls script access. Review request inclusion and server authorization separately.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-19 · Estimated read 8 min

Article

A Cookie marked Secure may still be readable by page scripts. HttpOnly is the separate attribute relevant to that access. When reviewing a session Cookie, distinguish its transport channel, script visibility, and eligibility to accompany a request. One security flag does not answer all three questions.

Transport and script access have separate controls

MDN’s Set-Cookie reference explains that Secure restricts transmission to HTTPS requests, with a localhost exception. It does not prevent JavaScript access when HttpOnly is absent. Local HTTP observations therefore also need qualification before being applied to a production domain.

Suppose a server sends Set-Cookie: sid=example; Path=/; Secure. The value is illustrative, and this example has not been executed. HTTPS transport alone does not establish that JavaScript cannot read the value. If it represents a server session and the frontend has no reason to read it, the review should ask why HttpOnly is missing.

With HttpOnly, JavaScript cannot read that Cookie through document.cookie. This is a restriction on an access route. It does not claim equivalent protection for browser developer tools, every form of local device access, or server logs. Seeing a value in a storage panel is therefore different evidence from successfully reading it in a page script.

An unreadable value can still accompany an action

The same reference notes that an HttpOnly Cookie can still accompany requests initiated by JavaScript. Actual inclusion also depends on the destination, credential settings, Cookie scope, and browser rules. That does not mean every cross-site request carries the session. Nor does hiding the value make every authenticated operation safe.

Imagine script injection into a same-origin page. The injected code cannot read the session value, but attempts an operation available to the current user. This is a risk scenario, not an executed attack or a report of a discovered vulnerability. Preventing theft of a value and preventing misuse of an authenticated browser are different objectives. Server-side identity, object authorization, and applicable request protections still need their own enforcement.

If a frontend only needs to display login status, consider an identity endpoint exposing the necessary public state. Displaying a nickname should not require exposing a session secret. The right design depends on the existing protocol, and client-visible login state never establishes server authorization.

Verify the behavior that each attribute promises

A proposed check can use a dedicated test session to examine script access, eligible request inclusion, unexpected requests, and the server response after logout. Record attributes and conditions without copying real session values into a report. This article did not run those checks or certify any site.

If existing pages read the value directly, adding the attribute may reveal that coupling. List each use, separate public state from credentials, and adjust the interface and endpoint accordingly. Keep a page open through renewal and inspect subsequent responses: a successful initial login does not establish that refresh preserves the attributes.

Also inspect session creation, renewal, and deletion paths for inconsistent settings. Multiple same-name Cookies with different scopes can complicate the picture. The site’s discussion of Cookie Path and permission boundaries addresses that separate issue. A useful conclusion names the behavior constrained by each attribute and the layer handling the remaining risk.
