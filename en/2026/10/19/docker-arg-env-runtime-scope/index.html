The ARG Has a Value. Why Is the Container Environment Empty?

A two-stage image traces a build argument into a file, image defaults, and runtime overrides to locate the missing handoff.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-21 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • ARG can feed build instructions but does not automatically appear in the final container environment.
  • A global ARG must be consumed in a build stage; copying a file does not copy that stage's environment.
  • Image ENV values are defaults that runtime input may override; verify the application's effective setting separately.

A build log shows APP_MODE=staging, yet the process in the resulting container cannot read APP_MODE. Docker has not necessarily lost a variable. A build input, image configuration, and a running container are three different handoff points. The Docker build-variable documentation says an ARG does not automatically exist in containers made from the image unless a Dockerfile explicitly passes it into a file or image configuration. An ENV value persists as a default for containers. Diagnose the consumer and the time of consumption before choosing ARG, ENV, or deployment input. Seeing a name in a build log is not proof of runtime delivery.

Follow one value through a complete two-stage image

Use this teaching Dockerfile with a harmless marker. The example uses Alpine 3.24, checked against the official release-branch page, only to demonstrate variable scope; no image was pulled or built here. A real project should choose its own base image, and secrets do not belong in this example:

ARG APP_MODE=production
FROM alpine:3.24 AS build
ARG APP_MODE
RUN printf '%s\n' "$APP_MODE" > /mode.txt
FROM alpine:3.24
COPY --from=build /mode.txt /mode.txt
CMD ["sh", "-c", "cat /mode.txt; printenv APP_MODE || true"]

Suppose someone runs docker build --build-arg APP_MODE=staging -t mode-demo ., followed by docker run --rm mode-demo. From the documented rules, /mode.txt should contain staging: the build stage wrote the argument to a file, and the final stage copied that file. But the argument does not automatically create an APP_MODE environment variable in the final container, so printenv should not report staging as an inherited value. “File has staging; process environment lacks APP_MODE” is the full expected outcome, not stdout observed for this article. Add ENV APP_MODE=production in the final stage and new containers obtain a production default. Supply docker run --rm -e APP_MODE=release mode-demo and the runtime environment can instead contain release. The copied file still contains build-time staging; changing runtime input does not regenerate it.

The first global ARG provides a default when no build argument is supplied; the second ARG APP_MODE inside the build stage lets that stage consume the value. With this example’s explicit --build-arg APP_MODE=staging, the global default could be omitted while keeping the stage declaration. Without the CLI input, removing the global default changes the fallback. Keeping only the global declaration and deleting the stage declaration does not make the value available to RUN. Docker documents that global build arguments are not automatically inherited into stages. A stage that uses one must consume its declaration. In this Dockerfile, RUN reads the value made available in the build stage. The final stage has no ARG APP_MODE or ENV; it copies an already-created file. If a final-stage instruction must use the build argument, declare it there according to the Dockerfile rules. Do not assume an earlier stage’s shell environment carries over.

This also explains why logs mislead. RUN echo "$APP_MODE" proves that one build instruction saw a value, not that the final image configuration includes it. COPY --from=build proves that file bytes were copied, not that environment configuration followed. An image with ENV still does not prove a deployment did not override that default or that the application read it. Label evidence separately as build input, artifact bytes, image defaults, container environment, and the application’s effective configuration. Each layer needs its own observation.

Choose a channel by consumption time

A dependency version used only by RUN may fit an ARG. An application mode read when the process starts is closer to image ENV defaults or deployment environment. A browser endpoint compiled by a frontend bundler into static JavaScript may be fixed in the generated file; changing an identically named runtime variable usually does not alter those bytes. That last behavior depends on the actual build tool and startup script. Some applications template files at startup. Inspect when the application reads and emits the value rather than declaring every web variable build-time or runtime by fiat.

Passing ARG into ENV APP_MODE=$APP_MODE in the final image also requires a product decision. Should every deployment from that image inherit the build-time value? If staging and production use the same image, environment-specific values are often better supplied at deployment. Otherwise a staging default may be baked into an image and used in production if an override is missed. Conversely, if the value selects a compile target and the artifact is immutable, changing the environment later will not rebuild its binary or static assets. “Use ENV for every variable” hides these opposite needs.

Even a container environment is not the application’s final configuration. The program may prioritize a configuration file, command-line option, or built-in default. printenv APP_MODE returning release only proves that the key exists in the process environment. If the app still reports production, trace its reading time and precedence rules. A redacted effective-configuration summary from the application is more informative than dumping the whole environment, especially when other variables are secrets.

Locate the handoff with a harmless probe

In an isolated environment, give APP_MODE a marker with no business meaning. Observe the build instruction, copied /mode.txt, declared image ENV, container printenv, and the application’s reported effective value. If the file says staging while the process environment says release, the artifact and runtime setting took separate paths. If the image has a default but the container differs, inspect the runtime override. If the container environment is correct but behavior is wrong, inspect application precedence. Change one input at a time and rebuild or restart the relevant stage. No command in this walkthrough was executed here; these are predicted observations from the official mechanisms.

A bad counterexample is to put a database password in ARG DB_PASSWORD and print it during RUN. Docker warns that ARG and ENV are unsuitable channels for build secrets: values can appear in image history, provenance, or final image data. Use an appropriate build secret mount or deployment secret-injection mechanism, and inspect the resulting artifact under the project’s threat model. Our earlier article on build secrets and final output discusses the exposure surface. APP_MODE is deliberately harmless so debugging does not create a credential incident.

The delivery record should name each setting’s owner and consumption time: whether the ARG was declared in the stage that uses it, whether it was written into an artifact, whether the final image has an ENV default, whether deployment overrides it, whether the application reads it, and whether a change requires a rebuild or only a restart. A log line showing staging supports only “one build step received staging.” It does not establish the container environment, browser artifact, or live effective configuration. Separate those handoffs to decide whether to edit the Dockerfile, rebuild an artifact, or change deployment input, and assign an acceptance owner to each step.
