Three git clean Previews, Three Different Sets of Files

A concrete draft, build directory, and local config show how -nd, -ndx, and -ndX differ and why scope must match execution.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-21 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • -nd previews ordinary untracked content, -ndx adds ignored content, and -ndX selects only ignored content.
  • Ignored is a tracking category, not proof that local configuration or reports are disposable.
  • Keep directory, pathspec, options, and file state aligned between preview and any execution; verify recovery first.

A team wants to remove build output, but its working tree also contains an uncommitted design draft and an ignored local configuration file. Someone previews git clean -nd, does not see the configuration, and prepares to execute git clean -fdx to “clean more thoroughly.” The scope has already changed: the previewed set and the deletion set are no longer the same. The official git-clean manual defines -n, -d, -x, -X, and pathspecs separately. A dry run is useful only when it answers the same selection question as the intended action.

Compare three candidate sets over one tree

Assume the repository tracks src/app.js and .gitignore, whose rules ignore dist/ and local-config. The working tree also has an untracked notes/draft.md, an ignored dist/bundle.js, and an ignored local-config. This is a teaching fixture, not an inventory of the present project. From the same repository root under the same rules, git clean -nd would select the ordinary untracked notes/ directory. git clean -ndx adds the ignored dist/ and local-config. git clean -ndX selects only ignored content, here dist/ and local-config, not the design draft. Git may print a directory path or individual paths depending on context; these sets are predicted candidates, not captured stdout. The tracked src/app.js is outside all three clean sets.

-n shows what would happen without deleting. With no pathspec, -d lets clean recurse into untracked directories. Lowercase -x does not apply standard ignore rules and therefore includes ignored content; uppercase -X selects only Git-ignored files. The case difference is a scope decision, not style. -x and -X are not simply stronger and weaker versions of one filter. One includes ordinary untracked and ignored content; the other selects ignored content alone. Comparing the sets reveals exactly which files the broader preview adds.

local-config is the negative case. It might hold developer settings recoverable only from that machine, precisely because it should not be committed. Its appearance under git clean -ndX does not make it a cache. Nor does its appearance under -ndx prove a backup exists. Ignore rules answer whether Git normally tracks a path; a human must decide whether its content can be discarded. Preserve a needed local file using appropriately protected storage and verify that copy can be read. If the file’s purpose is unclear, narrowing the target to dist/ is more defensible than selecting the entire tree with -x.

Another premise is easy to miss: an ignore rule does not retroactively make an already tracked file untracked. If someone committed local-config years ago and only later added it to ignore rules, git clean is not a tool for changing its tracked state. Check whether a surprising path is tracked before interpreting its absence from a preview. A file missing from -X might be tracked, outside the working directory, or excluded by the pathspec; absence does not prove safety or nonexistence.

Directory, exclusions, and time can change the set

Previewing from the repository root and executing from a subdirectory changes the starting scope. Previewing with -- dist/ and executing without that path expands it. The manual also says that when a pathspec is supplied, the ordinary no-pathspec role of -d no longer applies in the same way. Do not assume a specified directory is safe merely because -d was omitted. -e <pattern> adds an exclusion and must be considered even when -x is used. A wrapper should print the working directory, complete command, and target paths, then show a dry run with the same options. A “clear cache” button is not a sufficient description of a broad clean.

There is also a time gap between preview and execution. A build can create dist/manifest.json, a colleague can add a note, or a generator can alter ignore rules after the first preview. The old list described an earlier working-tree state. Preview again when anything changes and compare the differences. Even without a change, the dry-run list records candidate paths, not a snapshot of their contents or a recovery copy. Storing the only review list inside a directory about to be deleted can lose even the audit evidence.

Nested Git repositories have an additional guard. The manual says an untracked nested repository containing its own .git directory needs a second force flag before clean will modify it. An unexpected nested repository is a reason to investigate ownership, not to add another -f reflexively. Ordinary untracked files have no such history protection: appearing in git status does not mean Git can restore them. Do not combine clean with unrelated tracked-file recovery commands and call the bundle a single reviewed “workspace reset.”

Match the candidate set to recoverable work

If this example only needs a fresh frontend bundle, first establish that dist/ is reproducible. Preview a pathspec limited to dist/ from the repository root and verify that the candidate set covers only that directory; leave local-config and notes/draft.md alone. If the purpose is a nearly empty temporary build workspace, a -x preview is broader. First establish that every untracked artifact is backed up or disposable, then let the workspace owner decide whether to run it. A CI label alone does not mean its generated reports or debugging artifacts have no value.

An isolated fixture can verify the predictions without touching a working project. Create the tracked, untracked, and ignored states above in a disposable repository. Record git --version, ignore-rule contents, working directory, and the raw output of git clean -nd, -ndx, and -ndX. Dry runs alone suffice to compare the manual’s selection rules. If execution must be rehearsed, use a disposable fixture with its contents preserved first; the real workspace need not be deleted for an article. No such probe was run here, so the set calculation is not presented as a measured list from any existing repository.

Our related article on stash coverage for untracked and ignored files can help choose temporary preservation, but an existing stash entry does not prove every valuable file is inside it. A reviewable decision names the current directory, exact options, current ignore rules, current candidate paths, and a tested recovery copy. If any condition changes, preview again. If a file’s value is unknown, narrow the path. Safety comes from aligning the candidate set, preserved content, and final action with the same concrete files, not from one universal clean command.
