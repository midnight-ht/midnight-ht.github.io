Compare Three Dry Runs Before Using git clean

Compare ordinary, inclusive, and ignored-only previews. Keep the directory and options aligned before choosing files to remove.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-19 · Estimated read 8 min
Translations
zh-CN en

Article

Before cleaning a working tree, preview git clean with the same scope intended for the cleanup. Ordinary untracked files, all untracked files including ignored content, and ignored files alone are different selections. Being ignored describes a version-control rule; it does not establish that a file is disposable.

These commands are unexecuted examples for comparing candidate paths:

git clean -nd
git clean -ndx
git clean -ndX

Three previews answer different questions

The official git-clean manual explains that -n, or --dry-run, shows what would happen without deleting anything. With no pathspec, -d includes untracked directories. Lowercase -x bypasses standard ignore rules and includes ignored content; uppercase -X selects only ignored files. Changing the case changes the scope.

Imagine a repository containing an untracked draft, an ignored build directory, and ignored local configuration. The first preview would normally exclude the ignored content. The second includes it, while the third focuses on ignored content alone. This is a hypothetical directory, not an inventory of the current workspace. Actual output depends on the working directory, path arguments, exclusion patterns, and repository rules.

The third preview cannot be described as “cache only.” Local configuration, test material, and unmanaged large files can also be ignored. Decide whether they can be reconstructed. Conversely, an unignored temporary file may have no lasting value. Tracking categories select paths; the value of their contents determines whether removal is acceptable.

Keep preview and execution scope aligned

Previewing at the repository root and executing inside a subdirectory need not select the same paths. Previewing without -x and adding it during execution expands the scope after review. Confirm the directory, arguments, and exclusions together. If a build or another tool creates files in the meantime, preview again; the old list is not permanent permission.

The manual supports path arguments and additional exclusions. Read their combined behavior before mechanically assembling options. For example, an explicit pathspec changes the role of -d compared with an invocation without paths. A team wrapper should expose the final command and working directory. A button labelled “clean build output” is not enough to explain a broader deletion scope.

Nested Git repositories have additional force protection described in the manual. An unexpected repository is a reason to investigate the boundary, rather than to add more force. This article provides no unconditional deletion command and did not run a forced cleanup.

Saving work and selecting removal are separate checks

Preserve important untracked or ignored content using storage appropriate to its purpose and permissions, and establish that it can be recovered. Git history cannot be assumed to contain files that were never recorded. Committing a secret merely to avoid losing it would create a different problem.

A preview list saves paths, rather than file contents. Keeping it in a work item helps explain the selection but cannot rebuild deleted files. Copy material that needs preservation to a suitable location and check readability. A cleanup script should also avoid keeping its only review list in a directory it will remove.

If temporary shelving is part of the plan, first review stash coverage for untracked and ignored files and inspect the actual entry. Successful preservation and correct cleanup scope are separate conclusions. Decide against current, specific paths. If a file’s purpose is unclear, narrow the target before proceeding.
