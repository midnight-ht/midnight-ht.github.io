Playwright locator.all: Prove the List Is Complete Before Enumerating

Explain immediate enumeration and zero-assertion passes, then choose readiness checks for known counts, unknown totals, and changing lists.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-21 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • locator.all immediately enumerates current matches without waiting for a complete list.
  • An expected count should come from fixture and filter rules, not be copied from the DOM.
  • The returned locator array does not freeze the DOM; changing collections need stable business identity.

A task page should show three records. A test places every assertion inside for (const item of await page.getByRole('listitem').all()). If the request has not returned, all() yields an empty array, the loop runs zero times, and the test can still appear green. Playwright has not verified the absence of errors; no item was inspected. The official Playwright Locator API for locator.all() says it immediately returns the elements currently matching the locator and does not wait for them to appear. A changing list can therefore yield unstable results. await waits for the array to be returned, not for the business list to become complete.

How zero assertions look like a pass

Consider a minimal timeline. The page starts a /tasks request. The test quickly runs const items = await page.getByRole('listitem').all() while no task rows have rendered, so items.length is 0. A loop containing expect(item).toContainText('Pending') has zero iterations and zero item assertions. One hundred milliseconds later the real three tasks appear, but the test has already ended. This is code reasoning, not a browser run or a measurement of a particular network delay. It illustrates a gap between the API's sampling instant and the test's intended claim.

const items = await page.getByRole('listitem').all();
for (const item of items) {
  await expect(item).toContainText('Pending');
}

The returned array contains locators, not a frozen DOM snapshot. Each later locator action resolves against the page state at that time. Even if three positions were present initially, clicking in the loop may delete, sort, or rerender a row; what was position two may no longer refer to the same task. Keep two questions separate: Was the collection complete before enumeration, and will it remain stable during the operations? The first needs a readiness contract. The second needs stable business identity or a fresh check after each change. A fixed waitForTimeout(1000) defines neither and cannot prevent reordering.

When the count is known, source it outside the DOM

If the test fixture explicitly creates tasks T-1, T-2, and T-3, it can first use await expect(page.getByRole('listitem')).toHaveCount(3). The Playwright count assertion reference says the assertion requires an exact number of DOM nodes and uses the assertion's waiting behavior. Then verify the three task identities and titles, or assert the whole list's text directly if that matches the goal. The important part is that expected count three comes from fixture data and the current filter, not the page under test. Reading const n = await rows.count() and then asserting toHaveCount(n) only confirms a momentary value equals itself.

Even reaching three rows does not prove they belong to this query. The previous search might also have three results, appear briefly, and then be replaced by the new results. Bind the assertion to the current filter or record identities: perhaps the current set is T-1, T-2, T-3 and the stale one is U-1, U-2, U-3. If the UI has an explicit Loading state, wait for it to finish before checking the new IDs. If the fixture controls the response, use distinctive data. Count, identity, and loading completion establish different facts; none automatically replaces the others.

When the count is unknown, do not manufacture an expected count from the current DOM. The page needs an observable terminal state: the loading indicator ends, a results heading names the range, pagination reaches its final page, or a clear “No records” state appears. Which one is right is a product contract, not a universal Playwright rule. If loading, genuine zero results, and service failure all look like the same empty panel, the test does not have enough information to decide whether the list is complete. Improving the page's readable states may be necessary before writing a trustworthy UI test. A controlled server response can provide external evidence too, but network completion alone does not prove the component rendered it.

Changing the collection calls for stable identity

Suppose a test clicks Complete on each of three tasks, and completion removes each row. If the returned locators encode positions, removing the first row may shift the second task into the first position; the next action may hit the wrong task or fail to find one. If the fixture knows task IDs, locate each current row by data-task-id or a unique visible name, complete it, and assert that ID disappears before moving on. If the UI provides no stable way to identify a task, ask whether the test can reliably express its intended behavior. The related guide on waiting for action results covers post-click checks; here each action may change what the next locator points to.

A virtualized list has another boundary. The DOM may render ten rows near the viewport while the data source contains one thousand. all() enumerates currently matching DOM elements; it does not scroll and gather the entire dataset. If the test means “the ten visible rows render correctly,” say so. If it means “all thousand records can be browsed,” design pagination, scrolling, or separate data-layer checks. Infinite scroll needs a stopping condition such as an end marker, loaded count matching a total, or a response saying there are no more pages. “Scroll a few times and call all” remains a sample, not proof of completeness.

Locator scope can make a count look complete for the wrong reason. page.getByRole('listitem') may include sidebar navigation, footer links, and tasks. Reaching three could mean three unrelated items. Locate the semantic task-list container first and find rows within it. If the component has no discernible region name or stable attribute, improve its semantics or the test contract. Conversely, a fixture that created three tasks does not imply a filter currently shows all three. Derive the expected set from fixture data plus filter rules. A strong assertion names which three records, in which list, under which filter state.

If the only goal is to check titles, enumeration may add work without value. Known order and content can be asserted at the list level; independent known tasks can be checked by stable ID. all() is convenient when the test genuinely needs to operate on each presently listed item and the collection has been shown complete and stable. Choosing the API after the verification goal is written helps avoid the two extra risks of an empty loop and shifting indexes.

A negative-case matrix should include slow loading, partial results later completed, stale prior-search results, genuine emptiness, request failure, reorder after completing a row, and a virtual list rendering only a slice. For three known tasks, assert count and identity before any necessary per-row action. For an unknown count, first prove a terminal state and scope of results. On failure, retain the page state, task IDs, loading state, and request identifier so the team can distinguish missing product data, a weak readiness contract, and a locator that changed meaning. This article did not run a browser test or measure flaky rates. Its code and timeline are deductions from the documented API behavior. An explainable green result must say where completeness evidence came from and how many items the loop actually inspected—not merely that every line included await.
