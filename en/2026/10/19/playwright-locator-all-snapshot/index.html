Why does locator.all() miss a dynamically loaded list?

Prove list completeness before enumeration, then account for empty loops, changing items, and virtualized views.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-19 · Estimated read 7 min
Translations
zh-CN en

Article

locator.all() immediately obtains locators for the elements matching at that moment. It does not wait for a dynamically loaded list to become complete. Before entering a loop, establish list readiness; awaiting the enumeration call adds no business guarantee that all records have appeared.

An empty loop can look successful

The Playwright Locator reference documents all as added in v1.29. It immediately supplies an array of locators for current matches and does not wait for elements to appear. For a dynamically loaded list that later becomes stable, the guidance is to wait for loading to finish before enumeration. A changing list can otherwise produce unpredictable results.

Imagine a test opening a task page and checking the title of every enumerated task. If no items exist when all is called, the array is empty and the loop body performs no checks. This is an unexecuted control-flow example, rather than a browser test report. A loop without errors establishes nothing about records that were never enumerated.

Partial loading creates another misleading moment. Waiting for the first item establishes that something appeared, rather than that later batches have finished. Increasing a fixed delay merely selects a later sampling time without defining completeness.

Define completeness from the page contract

When a fixture independently specifies three records, a count assertion can wait for three before enumeration. If ordered titles are the requirement, asserting the whole list text may express it more directly. Enumeration should serve the operations required by the case, rather than exist for its own sake. The October 11 article on actions and result waiting provides the broader assertion context.

When the size is unknown, look for a genuine completion signal, such as an ended loading state with a defined result scope. These are candidate designs, rather than controls every page already provides. A valid empty result needs an observable terminal state too; otherwise the test cannot distinguish “not loaded yet” from “no records.” A failed load must not pass as the same blank state.

Count alone has limits. Three items might subsequently be replaced, or they might belong to the previous search. Bind readiness to the current filter, search, or operation and verify record identities. Reading the current count and using it as the expected count copies the unverified moment into the expectation; it cannot establish completeness.

Enumeration does not freeze the page

The array contains locators, rather than a frozen page. If clicks delete, reorder, or reload entries, later operations still face a changing collection. Stable business identifiers or renewed checks after each mutation may be appropriate. Choose according to how the operation changes the set, rather than applying one loop recipe everywhere.

A virtualized list creates a further boundary: currently rendered items may not represent the whole dataset. DOM enumeration should not be reported as full-data verification. Define a scrolling, pagination, or suitable data-checking scope and put that scope in the case description.

No browser cases or stability measurements were run here. Proposed coverage includes slow and batched loading, a genuine empty result, loading failure, and reordering during interaction. Name the signal establishing completeness, then inspect the moment all observes. Waiting and enumeration should each have an explainable responsibility.
