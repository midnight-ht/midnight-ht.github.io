Why a Same-Origin Resource Policy Still Needs base-uri

A strict resource allowlist does not constrain the document base. Review relative URL destinations and choose a policy the page can support.

Updated 2026-10-19 · Estimated read 7 min
Translations
zh-CN en

Article

A restrictive resource policy still needs a separate decision about base-uri. Setting default-src 'self' does not constrain the document’s <base> address through that directive. Resource permission and the starting point used to interpret a relative URL are different parts of the browser’s work.

Work out the address before assessing permission

MDN’s base-uri reference identifies it as a document directive with no fallback to default-src. Leaving it out does not inherit the default resource allowlist. A response-header review that checks only a strict default rule therefore leaves a separate configuration question unanswered.

Consider a hypothetical page at https://app.example/orders/ containing help.html. Without another base, that relative reference points into the page’s directory. An effective <base href="https://support.example/"> changes the starting point, producing a different destination. This address example has not been run in a browser. It also does not imply that every resource can bypass its own loading policy.

The HTML base reference explains that the element specifies the base URL for relative URLs in a document. Review the resulting absolute address, rather than only the relative text in a template. A changed address and a permitted request are two separate conclusions.

Choose a restriction that fits the page

If the product does not need <base>, consider base-uri 'none', which prevents that element from setting a base URI. A product that needs a same-origin base can evaluate base-uri 'self'. Neither choice is a universal recipe. A same-origin restriction does not pin the base to one business directory.

There is a practical cost to check before disabling it. Some pages use a base element to support deployment below a path prefix. Find the component generating the element, the pages relying on it, and the source of that prefix. Removing an unnecessary element and adding a restriction can be reviewed together. A legitimate dependency needs a documented allowed scope.

This restriction also does not replace template escaping or content sanitization. An unexpected element calls for investigation of its entry point. Adding a header does not establish that the underlying injection path has disappeared, and repairing one template does not apply a policy to every response.

Inspect the effective destination

A proposed isolated check should cover valid navigation and an out-of-scope base element. Record the delivered policy, effective base, complete link destination, and browser report. A console warning alone does not establish coverage across the application. No such checks were executed for this article.

Include fragment links in the inspection: an intended in-page reference can also be affected by a base address. Fully absolute destinations need assessment on their own terms. Build the set of examples from the reference types the page actually uses; one script path cannot represent them all.

Keep resource and navigation decisions separate. A script blocked by another directive says something about that request, rather than proving the base stayed unchanged. For forms, continue with the site’s explanation of form-action destination restrictions. Write down both the resolved destination and the rule governing the action.
