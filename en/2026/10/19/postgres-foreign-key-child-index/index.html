A Foreign Key Exists. Why Check the Child-Side Index?

Follow customer deletes into orders, compare composite-index column order, and balance lookup gains against write and build costs.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-21 · Estimated read 16 min
Translations
zh-CN en

Article

Key takeaways

  • A PostgreSQL foreign key does not automatically index child referencing columns; the parent unique index does not settle reverse lookup cost.
  • Composite B-tree order and leading-column constraints matter more than index names alone.
  • Decide from parent deletes/key updates, representative plans, and write/build costs without changing the relationship policy.

orders.customer_id has a foreign key to customers.id, yet deleting a customer is slow. A teammate finds the primary-key index on customers and concludes “the foreign key already has an index,” then proposes changing the delete action to CASCADE. That mixes three separate questions: locating the parent customer, finding child orders that refer to it, and deciding what deletion is allowed to do to those orders. The PostgreSQL 18 foreign-key documentation says referenced columns must meet the documented primary-key or uniqueness requirements, but a foreign-key declaration does not automatically create an index on the referencing columns. Deleting a referenced row or updating its key requires looking for child rows with the old value. Indexing addresses lookup cost; a cascade changes the data lifecycle.

Follow the customer delete in both directions

Suppose customers(id) contains customer 17. orders(id,customer_id,status) has 500,000 rows, three of which belong to that customer: orders 101, 102, and 103. The customers.id primary-key index helps locate the parent and supports the referenced-key lookup when a new order checks that its customer exists. It is not an index on orders.customer_id. If customer 17 is deleted, PostgreSQL must apply the chosen foreign-key action to those three orders. With no ON DELETE clause, PostgreSQL defaults to NO ACTION: a remaining reference usually produces an error, but a deferrable check can allow other statements in the transaction to repair it first. Explicit ON DELETE RESTRICT is stricter because its check cannot be deferred. CASCADE and SET NULL are separate business choices. Each action still requires assessing the matching child rows. Without a suitable child access path, that work can grow with the orders table. Even with an index, matched-row count, locks, triggers, and distribution still matter. The three-order case is an illustrative input; no delete was run.

Ask two directional questions. On INSERT of an order with customer_id=17, does a qualifying customer exist? The referenced table's key index serves that direction. On DELETE of customers.id=17, or an update of that referenced key, which orders still point to the old value? The referencing table's path serves this direction. A review screenshot of customers_pkey answers the first question but cannot establish the cost of the second. A foreign key establishes which relationships are valid; it does not promise a particular reverse-lookup latency.

There is an important negative case. A child table with only a few dozen rows and almost no parent deletes may be cheap to scan. Building an index for every foreign key adds storage and write-maintenance cost. Conversely, a large orders table with time-limited parent-key updates or deletes may benefit materially from a child index. Evaluate parent-operation frequency, child size, key distribution, concurrent writes, and the operation's deadline. The phrase “foreign key” alone does not decide the index.

Existing composite indexes may help—or miss the useful prefix

Inventory orders indexes before proposing orders_customer_id_idx. Suppose an existing B-tree index is (customer_id,status). A lookup constrained to customer 17 has a clear leading-column condition. If the index is (status,customer_id), a query with only customer_id=17 lacks an ordinary equality condition on leading status; the latter ordering is generally less direct for this lookup. The PostgreSQL 18 multicolumn-index documentation says B-tree indexes are most efficient when the leading columns are constrained. It also describes skip scan, which may use a later column in some data distributions. Do not flatten this into “the second index can never be used.” Its usefulness depends on the number of status values, statistics, and the resulting plan.

Names alone are weaker evidence still. idx_customer_status might belong to another table, be partial, have a different column order, or be invalid. For a composite foreign key such as (tenant_id,customer_id), a single index on customer_id may not fit the actual lookup. Inspect the real definition, validity, predicate, expressions, ordering, and relationship columns. If several workloads compete over column order, evaluate the combined benefit rather than adding redundant structures to satisfy one infrequent maintenance command.

A controlled comparison can start with SELECT 1 FROM orders WHERE customer_id=17 LIMIT 1 and then a query covering the full matching set, using representative data in an isolated database. Compare actual rows and buffer activity before and after a candidate index. This SELECT is only an approximation of the child lookup, not the whole work of an internal referential-action trigger. To measure a parent DELETE and trigger timing, use disposable data or a controlled transaction and confirm the final data or rollback state. EXPLAIN ANALYZE DELETE executes the statement; it is not a harmless observation command for production. No SQL was executed for this article, so any concrete plan outcome must come from the reader's environment.

Keep deletion policy separate from index rollout

If the original policy forbids deleting a customer with orders, do not switch to ON DELETE CASCADE merely because the operation is slow. Cascading deletes orders; that is a business-data decision. A child index can improve a lookup path without changing integrity semantics. If an account must be closed but orders retained, soft deletion, anonymization, or a different relationship may need business and retention review. Even when cascading is legitimate, assess how many child rows one parent delete will affect. An index cannot make a large valid cascade costless.

A new child index has its own costs. Order inserts and relevant updates maintain it; it consumes storage; its build uses CPU and I/O. CREATE INDEX CONCURRENTLY may be considered for a live large table. PostgreSQL says it can avoid blocking normal writes as an ordinary build would, but it takes extra scans, waits, and resource load. Our related article on concurrent index creation covers rollout details. Availability of CONCURRENTLY does not mean “zero impact,” and no fixed improvement percentage can be claimed without a workload run.

A reviewable conclusion could say: “This example explicitly configures ON DELETE RESTRICT, so customer deletion with orders is rejected; orders has 500,000 rows and only a (status,customer_id) B-tree; a maintenance job checks the three orders for customer 17; representative isolated plans show that path misses its deadline; (customer_id,status) is a candidate, with additional write cost and a separate rollout plan.” Another legitimate conclusion is: “Parent keys never change, deletion is always soft, the child is small, and no new index is justified yet.” Record what table size or operation change would reopen that decision. Both are better than assuming an index appeared with the foreign key.

Acceptance covers integrity and cost. Verify the new index is valid, the plan actually uses an appropriate path, the target parent action finishes within its budget, and concurrent order writes do not regress unacceptably. For a customer who must not be deleted, verify the foreign key still refuses the operation. If the representative key distribution differs from production or a delete triggers other tables, one customer-17 plan cannot stand in for the whole workload. The historical article's central question remains: why inspect the child-side index separately? Because the relationship rule, parent uniqueness index, and child access path are three different pieces of evidence. Only the last one addresses reverse-lookup support.
