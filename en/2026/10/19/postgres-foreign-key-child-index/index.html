A foreign key exists. Does the child-side index exist too?

Check relationship direction, existing indexes, and parent operations before assuming a foreign key covers lookup cost.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-19 · Estimated read 8 min
Translations
zh-CN en

Article

A foreign key on an orders table does not establish that its referencing columns have an index. Deleting a parent row or updating a referenced key introduces a separate lookup to evaluate. Referential integrity and the cost of checking relationships deserve separate answers in a schema review.

Follow the relationship in both directions

The PostgreSQL 18 foreign-key documentation distinguishes referencing and referenced columns. The referenced columns must satisfy the documented primary-key, unique-constraint, or non-partial unique-index conditions. Declaring the foreign key does not automatically create an index on the referencing columns.

Suppose orders.customer_id references customers.id. Inserting an order requires a matching customer. Deleting a customer or changing its referenced key requires finding orders that refer to the old value. The documentation consequently recommends considering an index on the referencing columns as well. No tables were created and no timings measured for this example; it does not diagnose a particular slow deletion.

A migration review should identify which side each index serves. A screenshot of the customer primary-key index cannot establish that order-side lookups are covered. “Foreign keys and indexes configured” conceals the direction, the columns, and the operation that actually needs support.

Inspect existing definitions before adding another index

The absence of a single-column index is not an instruction to create one immediately. An existing composite index might be suitable, or its definition might not support the lookup being considered. Inspect the full definition, every column in the relationship, and representative plans. An index name, or the appearance of customer_id somewhere in its definition, is insufficient evidence.

For example, another order query might filter on several columns. Whether its composite index also supports customer lookups needs a concrete evaluation. This hypothetical scenario offers no universal column-order prescription. Data distribution, table size, and operation frequency affect the decision to add another index.

Parent-side operations also need a place in the workload inventory. The normal user interface may never delete customers, while deduplication, archiving, or repair jobs modify those relationships. Replaying only ordinary order queries can overlook these infrequent operations with their own deadlines. For a small, slowly changing table, a documented decision against another index can also be reasonable.

Preserve the relationship policy during performance work

Foreign-key actions determine business outcomes. An index addresses lookup implementation choices. Whether deletion is forbidden, cascades, or follows another retention policy should come from the data lifecycle. Removing a constraint or changing its action because a deletion is slow changes the integrity promise and extends beyond the performance problem.

An additional index also consumes storage and adds write and construction costs. Concurrent construction, waiting, and failed-build states are separate release concerns, discussed in the October 9 article on concurrent index creation. This article contains no executed migration, load reduction, or lock-wait improvement claim.

A reviewable conclusion should name the relationship direction, existing index definitions, parent operations to support, representative plans, and exclusions. Verify correctness and timing in an appropriate environment, with stopping conditions for the change. The foreign-key declaration establishes an enforced relationship; the workload evidence establishes whether its lookup cost is acceptable.
