PromQL offset: when is last week a valid baseline?

Map each query point to its real time window, then inspect missing samples, label changes, and denominator rules before alerting.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-20 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • offset shifts sample selection without changing the five-minute window width.
  • Missing history and a genuine zero baseline need different handling.
  • Labels, business timezone and events decide whether a historical line is a useful baseline.

A monitoring panel overlays current request rate and “the same time last week.” One point suggests traffic has doubled. That reading depends on two separate premises: the PromQL expressions actually select the intended windows, and those windows represent comparable business conditions. offset moves where a selector reads samples. It does not establish that historical samples are complete, or that last week’s deployment, holiday and label set match today’s.

Translate one chart point into two real intervals

The Prometheus querying basics reference says offset can modify instant and range vectors and must follow the selector immediately. At evaluation time t, consider these illustrative expressions. The metric and request source are hypothetical; no production storage was queried for this article.

rate(http_requests_total[5m])
rate(http_requests_total[5m] offset 1w)

The first expression selects samples in (t-5m, t]; the second selects (t-1w-5m, t-1w]. Prometheus defines a range selector as left-open and right-closed. The windows have the same width but belong to different real periods. A range query evaluates each expression at successive chart steps, so a historical line can be plotted at today’s horizontal coordinates while its values come from last week’s windows. A legend that merely says “request rate” hides this distinction. Label the offset and record the evaluation range, window width and display timezone.

Placement changes meaning. In sum(rate(http_requests_total{job="api"}[5m] offset 1w)), each selected series is read from a five-minute window a week earlier, its rate is computed, and the rates are then aggregated. Appending offset 1w to an ordinary aggregate expression is not a valid equivalent; the official documentation shows this syntactic distinction. If a selector also uses @ to fix a time anchor, the offset is relative to that anchor. Moving the dashboard’s time range need not move a subexpression anchored at a fixed timestamp. For a complex query, write the anchor and shift next to each selector rather than assigning one vague “historical” label to the whole expression.

A valid query can still describe a bad baseline

Check whether data retention reaches the historical window and whether the relevant targets were being scraped. The Prometheus documentation explains that series can become stale and disappear from query results; instant-vector selection also involves a lookback period. A blank segment in the historical line is not the same as zero user demand. If the display fills absent points with zero or connects across gaps, a percentage calculation can turn an observation gap into an apparent traffic drop. Show the raw current and historical series, including missing points, before summarizing them.

Labels may have changed too. Last week’s job="api" could include a different set of instances from today’s. A deployment might have renamed a route or changed traffic allocation. Two tidy aggregate lines do not prove that the underlying series represent the same population. If a vector binary operation computes a ratio, check matching labels as well as a zero denominator; changed matching can yield an empty or misleading result. Summing everything into one line can conceal service, region or status-code differences. Document the filter and aggregation on both sides of the comparison.

Missing history and zero history require different decisions. Missing data may reflect retention, scrape outages or stale series. A genuine zero rate calls for a defined policy about division by zero and whether a percentage is meaningful at all. An estimate based on too few samples is another condition to inspect. Treating all three as a charting zero and then reporting “infinite growth” does not help an on-call engineer. The alert or panel should state how it handles each case and test those cases with known data.

Even complete samples may be incomparable. A release at today’s peak hour might have no equivalent event last week. Weekdays and holidays, campaign timing and routing changes can all alter the expected level. offset 1w aligns elapsed time, not product state. In a region that observes daylight-saving changes, a fixed one-week shift can also differ from the same wall-clock hour across the transition. Record both UTC timestamps and the business timezone when calendar alignment matters. Choosing a previous day, a week ago, or a multiweek baseline should follow observed traffic patterns and false-alert costs, not query syntax alone.

For multi-instance services, decide whether the comparison should be per service, per route, or per region before choosing aggregation. A global total can hide a sharp regional regression behind growth elsewhere; an individual-series comparison can become noisy when replicas churn. Retain enough labels to represent the decision being made, then aggregate at the level at which someone can act. The chosen labels should be the same on the present and historical side, and the panel should disclose any normalization used for a changing fleet.

The metric itself may answer different questions. A total sum(rate(...)) can rise after adding instances while per-instance load falls. Total demand may be the right signal for product traffic; capacity pressure might require an instance count or distribution as well. offset cannot choose that objective. State the entity being compared and why the selected aggregation reflects it.

Make a comparison auditable before alerting on it

Save the exact query, evaluation range and step, offset, scrape interval, retention coverage, label filters, missing-data handling and denominator policy. Pick two chart points, compute each selector’s real time interval and inspect the underlying samples and target state. For an alert, test a known rollout period, a scrape gap and a zero or missing historical denominator. Record which cases fire and which remain indeterminate. If those cases cannot yet be checked, keep the historical overlay as an investigation aid before using it to interrupt on-call staff.

The site’s explanation of scrape and rule-evaluation clocks covers the timing of sample collection and rule calculation. A five-minute rate window is neither one scrape nor the dashboard step. Keeping those clocks distinct makes “same time last week” a checkable statement. Once the two read intervals, participating series and gaps are visible, the apparent doubling can be judged as an operational signal or set aside as an artifact of the comparison.
