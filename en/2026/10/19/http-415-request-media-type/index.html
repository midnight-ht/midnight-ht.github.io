HTTP 415: Compare the Sent Body, Media Type, and Content Coding

Diagnose HTTP 415 from the same request’s method, body, media type, and content coding, then verify the business outcome.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-20 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • The relevant format support belongs to a method on a target resource.
  • Compare the transmitted body, Content-Type, and Content-Encoding from one failed request.
  • Passing the 415 gate does not establish that fields were read or a business operation completed.

When an endpoint returns HTTP 415, put the request that actually left the client in front of the team. A request header of Accept: application/json describes the response format the client prefers. It does not transform a form body into JSON, nor does it tell the server to accept an upload. The useful unit of investigation is one method, one target resource, and one transmitted body with its content headers.

What the status covers

RFC 9110 section 15.5.16 describes 415 as the origin server declining a request because the content format is not supported by that method on the target resource. The problem may lie in the request's stated Content-Type, its Content-Encoding, or an inspection of the data itself. That is a scope for diagnosis, not a guarantee about the order in which a particular framework checks those conditions. A status code alone cannot name the failing line of server code.

Three fields often appear in the same screenshot but answer different questions. Content-Type describes the media type of the representation being sent, such as JSON or a multipart form. Content-Encoding identifies a content coding applied to that representation, such as compression. The request's Accept header expresses a preference for the media type of the response. If a JSON-only endpoint receives form-encoded bytes, widening the request's Accept value does not change the bytes. Setting the Content-Type label to JSON while leaving the form bytes in place creates a different inconsistency; it is not a conversion.

The method matters even when the path is unchanged. A resource may accept multipart on POST and a JSON representation on PUT. A successful capture for one operation does not establish support for the other. Check whether a client library serialised an object, supplied a multipart boundary, followed a redirect, or changed a header after the application code assembled the request. A documentation example, a snippet of application code, and a response screenshot may describe three different messages. Keep the evidence attached to the same request.

Compare requests without changing the question

Consider a hypothetical contract: POST /imports accepts a JSON object. The client sends item=42&mode=merge with Content-Type: application/x-www-form-urlencoded and receives 415. Record the method and path, the final content and encoding headers, a safely redacted representation of the transmitted body, and the response. Then build a JSON body expressing the same business intent, with a matching type declaration. If the new request passes the 415 gate, the comparison supports a format-related explanation. It does not yet show that the server understood both fields or completed an import.

Change one relevant variable at a time where possible. Changing authentication, endpoint, method, business payload, and media type together makes the status difference hard to interpret. Protect secrets in the record, but retain structural evidence: JSON object boundaries, form field names, multipart part headers, and the presence or absence of a boundary parameter. Inspect the outgoing request in a network capture or client trace, rather than only the options the developer intended to send. Libraries and browsers can add or alter content headers according to the body type.

The second branch is a request with an apparently correct media type that still receives 415. A compressed body may use the right Content-Type while relying on an unsupported Content-Encoding. A body left uncompressed but marked as compressed can also send the receiver down an incompatible decode path. Compare the final declaration with the body construction process. Direct inspection of the payload may reveal a format mismatch even when the header looks plausible. Only the service's error details, logs, or a controlled comparison can establish which check rejected a particular request.

RFC 9110 gives response headers an important directional role. For unsupported request content coding, a 415 response ought to use Accept-Encoding to tell the client which request codings would have been accepted; for 415 responses unrelated to content coding, the RFC says the server must not include that field. When media type is the problem, a response Accept field can identify acceptable request media types. This Accept is sent by the server in the response. It has the same name as the client's preference in the request, but serves a different diagnostic purpose. The absence of such hints does not establish support for any candidate format; consult the endpoint contract and receiver records.

Check the outcome beyond the format gate

A change from 415 to another status may be useful evidence, but it is not automatically success. RFC 9110 distinguishes unsupported content format from content whose media type and syntax are understood but whose instructions cannot be processed, which is the territory of 422. An application may also produce its own error representation or use another status for authorization, conflict, or malformed content. Report the status and response actually observed. Do not infer an internal processing sequence merely because the code moved to a different status.

A compact test matrix for the endpoint should contain at least an accepted body and declaration, an unsupported media type, a correct declaration paired with mismatching body bytes, an unsupported content coding, and relevant empty or incomplete bodies. For each case, specify the expected rejection stage, what the client can show, and whether a business side effect is permitted. The exact expected results follow the endpoint's contract. For multipart requests, check who generates the boundary: hand-writing a bare multipart header without a matching boundary can undermine an otherwise correct form. For JSON, inspect the serialised string, not how the original object looked in a debugger.

After the format change, verify that the receiver read the intended fields and that the defined business result occurred, whether that is a persisted record, a returned identifier, or a controlled rejection. “Not 415 anymore” is too weak an acceptance criterion for an import. The separate client-side question of parsing whatever response arrives is treated in the Accept and response-contract article. The examples here are reasoning cases, not live API tests. When someone suggests “change Accept,” ask whether the proposed change affects request bytes, request coding, or only response preference. That question keeps the investigation on the side of the exchange that 415 describes.
