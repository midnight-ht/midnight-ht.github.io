For HTTP 415, inspect the content you sent before changing Accept

Separate request format and encoding from response preferences when investigating an HTTP 415 response.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-19 · Estimated read 8 min
Translations
zh-CN en

Article

Changing the request’s Accept header after an HTTP 415 response may address the wrong direction. Start with what was sent to the server: whether the method supports that format at the target resource, whether the declaration matches the body, and whether the content coding is supported. Desired response format and actual request content are separate clues.

Keep the two directions visible

RFC 9110 section 15.5.16 defines 415 as refusal to service a request because its content format is unsupported by that method on the target resource. The problem may involve the declared Content-Type, Content-Encoding, or direct inspection of the data. Interpreting it merely as “the response was not JSON” starts the investigation on the other side of the exchange.

A request Accept header normally expresses preferences for response media types. Request Content-Type describes the content being sent. Suppose an endpoint accepts JSON but the client sends form-encoded data. Changing Accept does not transform those bytes into JSON. Relabelling the body as JSON also leaves the original bytes unchanged, so the new label alone does not establish a repair.

This is a hypothetical example; no requests were sent to a real service. During an investigation, capture the method, path, relevant content headers, and actual body or a safely redacted representation from the same request. Combining a documentation example with a response screenshot from another request loses that relationship. Redaction should protect sensitive information while retaining enough structure to examine the format.

A correct type does not settle coding

Compressed and uncompressed requests can declare the same media type while requiring different content-coding support. The RFC explicitly includes Content-Encoding as a possible cause. Finding the expected Content-Type therefore does not finish the investigation. It also does not prove compression caused this particular failure; actual service and intermediary records must establish the rejection point.

For unsupported content coding, the specification says an Accept-Encoding response header ought to indicate acceptable request codings. For an unsupported media type, the response can use Accept to indicate acceptable request media types. That Accept field is in the response. Label its direction in notes rather than confusing it with the client’s response preference.

A service may provide little diagnostic detail. Its absence does not identify the cause, and repeatedly broadening request Accept is not a reliable investigation. Find a minimal accepted request for the same method and target path, then compare how it constructs content. Success at a different upload endpoint does not establish support at the original one. Record that change explicitly, and keep authentication, routing, and business content comparable.

Preserve evidence beyond the status code

“API error” is too broad a record for the next engineer. Connect the client declaration, payload construction, and observed rejection reason without inventing a server processing sequence when logs are unavailable.

After a change, check whether the expected fields were read and whether the business operation reached its defined result. A response other than 415 does not by itself prove an order was created or a file was stored. Error responses also need handling according to their own content type; see Accept and actual response checks. No comparative API tests were executed here. For the next 415, inspect the content sent before changing the content hoped for.
