Why upgrade-insecure-requests cannot replace HSTS

A resource upgrade and a first visit follow different paths. Verify CSP, redirects, and HSTS against the right request.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-20 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • The CSP directive upgrades insecure page resources and fails when an HTTPS endpoint is unavailable.
  • HSTS governs later host connections after a secure response has taught the browser the policy.
  • Test resource loads, first entry, return entry, and cross-site navigation separately.

A page can successfully upgrade every insecure image request and still expose a first visit through an HTTP link. upgrade-insecure-requests and HSTS operate at different moments. The CSP directive governs requests made after the browser has received the page policy. HSTS governs later connections to a host once the browser has learned its transport policy. A migration checklist that treats them as one “HTTPS enabled” switch misses the entry path.

What happens after the page arrives

Consider a hypothetical checkout page at https://shop.example with an image URL of http://cdn.example/logo.png. If the page carries Content-Security-Policy: upgrade-insecure-requests, the browser rewrites that resource URL to HTTPS before sending the request. MDN’s directive reference says the rewrite covers non-navigational first-party and third-party resources. If the CDN cannot serve the HTTPS URL, the resource fails. The browser does not quietly retry over HTTP. That failure is useful evidence: a quiet fallback would make a broken migration look complete.

This behavior does not mean that every http: string encountered by the page is rewritten. A top-level link to a different HTTP site has a different boundary. Nor does it tell us how the customer reached the checkout page. Loading an image from a page and entering that page from an email are separate requests. The latter can occur before the browser has received the site’s CSP. A response cannot retroactively protect the request that delivered it.

That distinction changes incident triage. If a logo disappears immediately after this directive is enforced, investigate whether its HTTPS endpoint exists and whether certificates and redirects work there. Calling the loss a browser compatibility quirk, or removing the directive merely to restore the image, conceals a concrete asset migration task. A site can instead migrate the asset, use an approved HTTPS-hosted copy, or defer enforcement for the affected route while it repairs the dependency.

What happens before a future visit

Strict-Transport-Security is a response header delivered over HTTPS. After the browser records it for a host, it upgrades future HTTP URLs for that host locally, before making the network request. It also stops users from clicking through certificate errors for that host. The MDN HSTS reference describes this as a policy for future requests, not a retrofit of the response currently being read. Browsers ignore an HSTS header sent over HTTP, because an attacker on that insecure path could alter it.

Imagine a customer has bookmarked http://shop.example/orders. A browser that has already learned a valid HSTS policy upgrades that bookmark before connecting. A browser that has never visited the host may send the first HTTP request and then follow the server’s redirect, unless the host was preloaded. The redirect is still needed, but it cannot erase the initial insecure request. A directive on the eventual page says nothing about which journey occurred.

Preloading can narrow the first-contact gap, but it is a separate enrollment and maintenance commitment. Do not add preload simply because the current page renders without mixed content. A long max-age and includeSubDomains require a survey of old administration hosts, upload hosts, certificate renewal, and any subdomain that still depends on HTTP. If a subdomain lacks reliable HTTPS, a parent-domain HSTS policy that covers it can turn an overlooked route into a persistent outage.

Two acceptance paths, with different evidence

Treat asset migration and site entry as distinct work. First, confirm that every business host has a valid certificate and HTTPS route. Then inventory page resources, including third-party assets. If an image provider only supports HTTP, the upgraded request will fail. The decision is to move that dependency, host an approved copy under an HTTPS origin, or stage the policy until the asset has a secure endpoint. An image that appears in a final screenshot proves little about the user’s initial navigation.

For the entry path, check that an HTTP request redirects to the intended HTTPS path and that the HTTPS response carries the intended HSTS policy. Record which host supplied the header; a header observed on a different subdomain is not enough. Start with a short enough max-age to expose routing or certificate omissions before extending it. Removing a header later does not instantly clear a browser’s stored policy. MDN explains that withdrawal requires a new secure response with max-age=0; subdomains can also have independently stored policies.

A useful test matrix has four observations: a first HTTP visit in a fresh browser profile, the same visit after HSTS has been learned, an HTTP resource requested within a protected HTTPS page, and a cross-site HTTP navigation link. Capture the network URL actually requested, any server redirect, and a failure caused by an HTTPS endpoint that does not exist. Mark whether each recorded response was HTTP or HTTPS. The padlock on the final page cannot answer what happened on the first hop. These are proposed checks; no browser or production site was tested for this article.

Scope each claim to the host and response you actually inspected. HSTS learned for the shop host does not automatically establish a policy for the CDN host. A CSP directive on one checkout response does not establish that the login redirect, error page, and static landing page all send the same directive. Test the critical entry routes individually. For a third-party resource, the site owner can change the reference or the supplier; the supplier’s own HSTS deployment remains a separate claim requiring its own evidence.

A team should write two acceptance statements: page assets no longer travel over cleartext, and returning visits to the host upgrade before connecting. CSP, redirects, and HSTS each contribute evidence to a different part of that claim. For the related rollout question, see When can a CSP reporting policy become enforced?. An empty report stream does not replace the entry and network observations above.
