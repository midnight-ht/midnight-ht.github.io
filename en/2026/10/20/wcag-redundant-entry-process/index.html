WCAG 3.3.7: Trace Information Reuse Across a Process

Map prior input, later requests, correction routes, and specific exceptions across one user process.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-20 · Estimated read 12 min
Translations
zh-CN en

Article

Key takeaways

  • Previously supplied information needed again in one process should be populated or selectable unless a specific exception applies.
  • Browser autocomplete alone does not establish reuse of information from the current process.
  • Back navigation, errors, and third-party returns belong in the process-level test.

A checkout asks for a delivery address, then asks for the same address again before payment. The second form may be technically easy to complete, but the user must remember or retrieve information the process already has. WCAG 2.2 Understanding Redundant Entry addresses this specific burden: information entered by or provided to a user and required again in the same process should be auto-populated or available for selection, unless an identified exception applies. The question for a team is therefore not simply whether a field has browser autocomplete. It is what the person has already supplied in this process, why it is requested again, and how the later step lets them use it.

Trace the process before changing fields

Consider a three-step order: contact details, delivery choices, and payment review. The delivery step may need the same phone number supplied on the contact step. If the user must type it from memory, the problem is visible even if the second input has a sensible label and accepts pasted text. Pre-filling the number from the current process, or offering the previously supplied number as a selectable option, gives the user a route that does not demand re-entry. It must remain possible to correct the value where the process allows changes. A copied value that is locked and wrong can create a new failure.

The phrase “same process” matters. A process can cross pages and, depending on the transaction, even domains; a redirect to a payment or identity provider does not automatically end the user's activity. Conversely, a new visit or a separate later transaction is not automatically the same process. Map the activity from the user's goal, including redirects, returns, errors, and back navigation. The criterion does not itself impose cross-session storage. Designing a permanent profile solely to satisfy it could add privacy cost without solving the current flow well.

Browser autocomplete may help some users, but it is not proof that the process uses information it already has. The browser may have no saved value, may offer an old one, or may not know which of two similar addresses the order needs. The design team should inspect the actual later request. If the earlier value can be offered reliably in the current process, a first-party selection or prefill path is easier to verify than a hope that the browser will infer the user's intent.

Ask whether the information is truly the same

“Phone number” is not enough to establish redundancy. A contact phone and an emergency contact phone can have different people and different meanings. Likewise, a billing address and a shipping address can differ, but the user might reasonably want to use one for both. A checkbox such as “Use delivery address for billing,” followed by an editable copy, can expose that choice without silently assuming equality. A field inventory should record the later request, where the information first appeared, whether its meaning is identical, and what reuse route is available. The upstream question of why a form asks for a field at all is explored in the form question protocol.

Some later input is legitimately different. Suppose the user changes from delivery to store pickup and then back. The original delivery address might no longer serve the selected method or area; the system may need confirmation or new information. The exception for information no longer valid should be tied to a concrete state change, not used as a blanket explanation for repetitive forms. Information required for security, such as a secret credential, also needs a field-specific analysis. “Retyping feels safer” is not an adequate reason to make people re-enter every name, address, and non-secret detail.

The mechanism also has a privacy boundary. A value stored in the current controlled workflow can be offered on the next page without being persisted indefinitely or exposed to the next person using a shared device. A cross-domain step should transfer only the information necessary for that transaction. For sensitive fields, the team should decide separately who may read the value, how long it is retained, and how it is cleared. The WCAG requirement does not authorize broad retention, and a convenient prefill should not disclose a prior user's data.

Verify the path the user actually takes

A straight-through test is insufficient. Enter a value, advance, and confirm it is populated or selectable; then change it, return to the previous step, and advance again to see whether the current value wins over a stale snapshot. Trigger an error on the later form and check that valid entries remain available. If an external domain is involved, test the return path as part of the same user activity. Error focus and message design have their own requirements, discussed in the error correction route, but a clear error message does not make repeated entry disappear.

Test the boundary conditions as deliberately as the happy path. When information becomes invalid, explain what changed and let the user correct it. When a security exception is claimed, name the specific risk and the specific field. When a session ends, do not mistake a deliberate lack of cross-session retention for a failure of this criterion. Ask keyboard and assistive-technology users to complete the process, because a selectable prior value that cannot be reached or understood is a poor substitute for typing.

A useful review artifact is an information-flow map rather than a screenshot saying “address cached.” For each repeated request, it shows the original source, the way the later step presents the prior value, the user's correction route, any invalidation event, and the evidence for an exception. This article describes a test design; it does not claim an end-to-end run against a live checkout. The decision to approve a flow should rest on its actual states and data handling, not the presence of an autocomplete attribute alone.
