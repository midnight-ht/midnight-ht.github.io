Why toBeHidden does not prove a DOM node was removed

A hidden assertion accepts absence or nonvisibility. Match the assertion to the UI's removal contract.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-20 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • Playwright toBeHidden passes for either absence or nonvisibility; it cannot establish DOM removal.
  • Use a prior visible assertion and an appropriately scoped toHaveCount(0) when the contract requires no matching node.
  • Visibility, DOM cleanup, cleared input and server-side deletion need separate evidence.

A user closes a dialog containing personal information, and Playwright’s toBeHidden() assertion passes. The team records “the dialog node was removed from the DOM.” That conclusion is stronger than the assertion. The Playwright locator assertions reference defines toBeHidden() as passing when the locator either matches no DOM node or matches a non-visible one. Deleting the node and leaving it mounted with a hidden state can produce the same green result. The first question for the test is what the product actually promises after closing.

Consider a confirmation dialog. This test checks a visible transition reasonably well, but it does not prove that the element was detached:

const dialog = page.getByRole('dialog', { name: 'Delete draft' });
await expect(dialog).toBeVisible();
await page.getByRole('button', { name: 'Cancel' }).click();
await expect(dialog).toBeHidden();

The first assertion matters. If the locator is wrong, or the dialog never appeared, toBeHidden() alone may pass because “no matching node” is an accepted outcome. Showing that the dialog was initially visible, then exercising the real close control, establishes a meaningful transition. The final hidden assertion still cannot distinguish a retained invisible node from a removed node. If the user contract is simply that the dialog no longer appears, retaining a hidden node may be legitimate. Requiring unmounting in that case would make the test brittle by binding it to an unnecessary implementation choice.

If removal is truly the contract—for example, each opening creates a fresh instance and closing must discard the old instance to prevent accumulating listeners—assert an exact node count:

await expect(dialog).toBeVisible();
await page.locator('[data-testid="delete-cancel"]').click();
await expect(dialog).toHaveCount(0);

The Playwright API defines toHaveCount() as checking that a locator resolves to an exact number of DOM nodes. Zero therefore says that this locator no longer finds a matching node. The scope of the locator is crucial. If it identifies the dialog by accessible name and the application merely changes that name, the count can fall to zero while the same DOM element remains. A zero count proves absence within the chosen locator, not that the entire page has no similar element, that personal data has been erased, or that event listeners have been freed. Choose a stable locator tied to the identity the removal requirement concerns.

Playwright also provides toBeAttached() for whether a matched element is connected to a Document or ShadowRoot, but that is a different question and depends on how the locator still points to the target. For a requirement that no matching dialog remains in the page, toHaveCount(0) expresses the outcome more directly. For a requirement that a dialog can remain mounted but must not be visible, toBeHidden() is appropriate. The assertion should follow the requirement, not whichever API name sounds most like “closed.”

A small implementation matrix exposes the blind spots. Removing the node on close and retaining it with a hidden attribute are two plausible implementations. Both can satisfy toBeHidden(), while only removal satisfies toHaveCount(0) for a stable node locator. A third implementation never renders the dialog; a test that only asserts hidden can still pass, but the initial toBeVisible() rejects it. A fourth moves sensitive content into another container; the original locator has count zero, yet the content remains on the page. Neither node count nor visibility is a privacy audit. If the requirement concerns sensitive data, inspect the content, client state, storage and relevant server response with separate evidence.

Timing matters too. A fixed sleep after clicking guesses how long an exit animation or state update will take. Playwright’s locator assertions retry until the required state is reached or the assertion times out. Set the awaited condition to the actual final contract: hidden for visual disappearance, zero matching nodes for removal. A short fade-out can be acceptable; a state that never arrives should fail clearly. A fixed delay can be too short on a slow runner or waste time on a fast one, and it does not explain which state was missing.

A wrong contract creates misleading regressions. If a component changes from unmounting to reusing a hidden node while the user-facing promise remains “closed means invisible,” toHaveCount(0) raises a low-value failure. Conversely, if retained nodes cause duplicate listeners or old input to reappear, toBeHidden() may stay green. Write separate observable promises: “the user can no longer see the dialog,” “the old instance no longer matches the locator,” and “opening again starts with clean input.” Give each promise its own test. Do not compress them into the ambiguous phrase “dialog closed.”

The site’s guide to waiting for the outcome after a click explains why a completed click is not a completed business operation. Here the follow-up question is which operation outcome is expected. Open the dialog through the actual UI, establish its initial state, perform the close action, then assert the chosen endpoint. If the flow also saves data, revokes access or clears a form, check those effects with evidence suited to each one. A screenshot does not prove detachment; a DOM count does not prove server-side deletion.

Repeated matches need attention as well. If several dialogs have the same accessible name, a locator assertion may be ambiguous, or a zero-count requirement may demand that all of them disappear when only one should close. Narrow the locator to the current business object or container and state whether one instance or every instance must be removed. Different viewports and accessibility modes may also have distinct visibility behavior; one desktop browser result should not be generalized to all environments without coverage.

For an application acceptance run, retain the Playwright version, locator, component version, and a failure trace or DOM snapshot. Try controlled cases equivalent to A, B and C to establish that the chosen assertion separates allowed from forbidden behavior. This article checked the official LocatorAssertions definitions of toBeHidden() and toHaveCount(). It did not run a browser or the application here. The strongest supported conclusion from a passing hidden assertion remains narrow: no matching node exists, or a matched node is non-visible. Removal requires a different assertion and a locator fit for that claim.
