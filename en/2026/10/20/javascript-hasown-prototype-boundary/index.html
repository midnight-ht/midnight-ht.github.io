Object.hasOwn: Separate Supplied Fields From Inherited Values

Distinguish own fields, inherited values, and invalid values before applying a JavaScript patch.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-20 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • Object.hasOwn separates own from inherited properties, and own undefined remains present.
  • Null-prototype and shadowed objects make an instance method unreliable.
  • Ownership, value validity, and authorization require separate decisions.

An update handler receives an object with a name field and checks "role" in patch before applying changes. That test can return true even when the client supplied no role at all: JavaScript's in operator includes inherited properties. If a library or another step has attached a prototype containing role, an apparently harmless name update may enter a privileged branch. MDN's Object.hasOwn() reference describes the narrower question: is this property owned by this object? For input contracts, that distinction matters before any business decision about the value.

Presence has more than one meaning

Read patch.role, test "role" in patch, and test Object.hasOwn(patch, "role") on the same object. The first operation returns a value and can follow the prototype chain. The second asks whether the property can be found anywhere along that chain. The third asks whether this object itself has the property. A client-supplied patch usually wants the third meaning: did this input include a field to change? Yet even that answer is only about ownership, not whether the value is permitted.

An own property with the value undefined still counts as own. So patch.role !== undefined conflates “missing” with “present but undefined.” Depending on an API's patch contract, those may have different outcomes: omission may mean leave the current role untouched, whereas an explicit invalid value may require a validation error. A JSON request cannot directly express JavaScript undefined as an object value under ordinary JSON serialization, but in-process objects, form adapters, tests, and merge utilities can produce it. Define the contract at the boundary actually used by the application rather than assuming every object came straight from JSON.

A minimal script run under Node v24.21.0 made these distinctions observable. For an object inheriting role: "admin", reading the field returned admin and the in check was true, while Object.hasOwn returned false. A separate own role: undefined returned true for ownership, as did an own role: null on an object created with a null prototype. The script, command, version, and raw stdout are saved with this editorial batch. These are language-API results in that Node environment, not a finding about any browser input parser or production authorization flow.

Avoid calling a method on the object being inspected

patch.hasOwnProperty("role") looks direct, but it assumes the object inherits that method and has not overwritten it. Object.create(null) produces an object without Object.prototype in its chain. Another object can have its own property named hasOwnProperty, making the apparent method a non-function or an attacker-controlled value. The static Object.hasOwn(patch, key) avoids depending on a member of the inspected object. In a runtime that cannot use the static method, Object.prototype.hasOwnProperty.call(patch, key) is a controlled alternative once compatibility has been checked.

Enumeration adds a separate axis. for...in walks enumerable inherited properties as well as own ones. If a handler must use it, filter each key for ownership. Object.keys(patch) lists only own, enumerable string keys, but that is not identical to Object.hasOwn: the latter also detects an own non-enumerable property, and symbol keys can be owned too. Decide whether the task asks for ownership, enumerability, or a list of allowed fields. Treating one built-in as universally “safer” hides those differing requirements.

A secure patch needs a full decision path

Suppose a user sends {name: "Ada"}. The endpoint should update only the name, regardless of a role found on an unexpected prototype. Suppose the input has an own role: undefined: under a strict contract, report an invalid role or explicitly ignore it, rather than quietly equating it with omission. Suppose the input has an own role: "admin": ownership is true, but a user without permission must still be refused. The three cases test source, value, and authorization separately.

A practical handler can start by constraining the input shape, then iterate an allowlist of fields rather than copying every incoming key. For each allowed field, check ownership, validate type and range, and confirm the current identity may change it. Finally, generate a controlled update. Generic object spread or deep-merge tools deserve their own inspection, especially around prototypes, accessors, and special keys. A getter may execute code when a property is read. No ownership check turns an arbitrary object into inert, validated data.

The same distinction should survive the full request path. If an adapter reconstructs a patch object, inspect whether it turns absent fields into own undefined values. If an ORM writes all keys from a merged model, confirm it does not update a column that the client never submitted. An audit log should report “role not provided” when that is true, rather than treating a role observed on the final object as user input. The related problem of distinguishing missing, null, and valid zero in JavaScript defaults shows why values alone do not establish intent.

For a plain JSON object, a team might never see an inherited role in normal traffic. That is precisely why the unit test should construct one deliberately and then follow it through the same update helper. Also test a value that is own but unauthorized: it catches the opposite mistake, where developers treat Object.hasOwn as an authorization check. If the helper accepts a Proxy or a getter-bearing object, decide whether that is supported input; ownership queries and later reads can invoke behavior that a frozen JSON payload would not have. A schema boundary can simplify the promise by converting external data into known plain values first.

A test matrix should cover normal own fields, inherited fields, own undefined, own null, null-prototype objects, a shadowed hasOwnProperty, non-enumerable own fields, and genuinely absent fields. For each, compare ownership, lookup, and final business action. The local Node run verifies only a few language cases; the actual parser, authorization rule, and write statement still require tests in the application. The final review question is therefore three-part: was this field in this input, is its value valid, and may this identity change it?
