Why two reads in one Read Committed transaction can differ

Follow two transactions to see how statement snapshots, own writes, and concurrent commits shape each read.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-20 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • In PostgreSQL Read Committed, two SELECT statements in one transaction can use different committed snapshots.
  • A preliminary read does not protect a later write; put eligibility into the write or design a stronger transaction strategy.
  • Distinguish concurrent commits from own writes with an ordered two-session reproduction before diagnosing isolation behavior.

Two balance queries run inside the same transaction. The first returns 100 and the second returns 80, although that transaction did not change the balance. This can be expected behavior under PostgreSQL’s default Read Committed isolation level. Each SELECT starts with a snapshot of data committed before that statement begins. BEGIN does not freeze one database image for all subsequent statements. If another transaction commits between the two reads, the second read can see its change.

Make the timing explicit. Wallet 42 starts with a balance of 100. Session A begins a transaction and reads 100. Session B changes that row to 80 and commits. Session A executes the same query again and can read 80. Both reads belong to A’s transaction, but the second statement starts after B’s commit. The PostgreSQL 18 isolation reference says Read Committed is its default level and specifically warns that successive SELECT commands can see different data within one transaction.

-- Session A; assume wallet(42).balance initially equals 100
BEGIN;
SELECT balance FROM wallet WHERE id = 42; -- expected: 100
-- Session B runs UPDATE wallet SET balance = 80 WHERE id = 42; COMMIT;
SELECT balance FROM wallet WHERE id = 42; -- can see: 80
COMMIT;

The comments describe an interleaving to test, not output captured from this environment. A statement reads from its own start-of-command view of committed data. A commit that happens only after that statement has begun should not be imagined as an arbitrary mid-query change to every part of its result. Session A’s own writes are another exception to a simplistic “only earlier commits” description. If A updates the row to 90 and then queries it, A can see its own modification. When reconstructing a surprising value, mark each statement’s start, each concurrent commit and any writes within the reading transaction.

Consider a service that checks inventory twice. The first read says ten units are available. After other work, the second says eight. If the service uses the first number as a stable prerequisite for an order, wrapping both reads in BEGIN has not supplied that guarantee under Read Committed. Define the actual invariant instead: is the page merely showing the latest count, must a two-unit deduction happen only when two units remain, or must several rows satisfy a joint constraint? These are different questions and call for different write and isolation designs.

For a single-row deduction, the qualification can be placed in the write itself:

UPDATE inventory
SET available = available - 2
WHERE sku = 'A' AND available >= 2
RETURNING available;

The application should treat a zero-row result as a failed deduction rather than announcing success based on an earlier read. In Read Committed, an update contending with another writer can wait for that writer, then reevaluate its condition against the updated row. The stored value and final qualification, not a stale preliminary read, determine whether this write proceeds. That still does not prove an entire order workflow is safe: other tables, side effects and transaction rollback need their own rules and tests.

If the requirement is that repeated reads in one transaction use a consistent committed view, PostgreSQL offers Repeatable Read. Its snapshot begins with the first non-transaction-control statement in the transaction, not simply the moment BEGIN is typed. The transaction can still see its own writes. A concurrent update conflict can require retrying the whole transaction. Choosing that level is a decision about a particular consistency promise and its failure path, not a magic switch that guarantees every cross-row business invariant. The site’s isolation and retry guide discusses the larger retry boundary.

The opposite misconception is that Read Committed gives no consistency even within a single ordinary query. The documented boundary is each command’s start. Two separate commands may see different committed states because they have different start times; do not project that observation onto an ordinary SELECT as though every row can be read from a fresh arbitrary instant. Complex writes, triggers and waits introduce their own details. This article’s worked model concerns ordinary reads and the explicit single-row update above. A report that needs a shared view across several queries should be designed for that need rather than patched by caching only its first number.

A useful incident record includes the actual isolation level, transaction boundaries, connection identity, query start and end times, and the competing writer’s commit order. Without that sequence, “MVCC changed the result” is only a hypothesis. The application might have written the row itself, switched data sources, changed query predicates or served a cached value. Build a reproduction with two independent sessions and a deliberate synchronization point; arbitrary sleeps are weak evidence of order. Save the PostgreSQL version, statements and raw outputs when the experiment is run.

Include a negative control. Repeated reads with no own write and no new relevant commit should not change for no reason. Then separately test a concurrent commit and an own-write case. These three observations distinguish the mechanisms that a vague “transaction read changed” report blends together. Check the application endpoint too, because an ORM or connection pool can add behavior beyond the simple SQL schedule.

Different readings are not necessarily a defect. A dashboard that promises current information may appropriately show 100 and then 80. An order approval that promises not to overspend needs its eligibility condition tied to a protected write or a suitable stronger isolation strategy, with its rejection and retry paths specified. The timeline above is a reading of PostgreSQL 18’s official isolation documentation. I did not run a two-session PostgreSQL experiment here, so it is a documented expectation, not a measured result from this environment.

Be precise about what a retry means if the service changes isolation levels. Retrying just the last read while retaining decisions made from an older view cannot restore the transaction’s intended invariant. The unit of retry must include the reads, decisions and writes whose assumptions depended on one another, while external side effects must be handled so they are not duplicated. That design question sits above the narrow snapshot fact, but it is often the practical reason to investigate the fact in the first place.
