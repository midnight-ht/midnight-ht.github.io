Changing Docker USER does not change copied file ownership

A non-root process may still lack write access to copied files. Check the final image and mounted paths.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-20 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • COPY creates root-owned files by default unless ownership is specified.
  • Grant write rights to the directories that actually hold mutable state.
  • Mounted storage needs its own runtime permission check.

USER app changes which user runs later Dockerfile instructions and the container process. It does not retroactively change ownership of files that COPY placed in the image. Docker's Dockerfile reference says that files copied without --chown are created with UID and GID 0. A container can therefore run as a non-root user and still fail to write a directory it can read.

Ask who writes to which path

Imagine an image that copies an application and a cache directory under /app, then switches to UID 10001. At startup the application creates an index in /app/cache. The filesystem checks the effective user and group, directory ownership, and mode bits. A directory owned by UID 0 with a common mode of 0755 permits UID 10001 to read and traverse it, but not create a file there. “Present in the image” does not mean writable by the runtime user; USER is not a recursive ownership command.

This unexecuted example makes the intended permissions visible at build time:

FROM alpine:3.20
RUN addgroup -g 10001 app && adduser -D -u 10001 -G app app
WORKDIR /app
COPY --chown=10001:10001 --chmod=755 ./bin/server /app/server
RUN mkdir -p /app/cache && chown 10001:10001 /app/cache
USER 10001:10001
CMD ["/app/server"]

The copied program needs to be executable but may not need to be writable. The cache directory is the actual write target, so its ownership gets explicit treatment. An application that writes mutable data back into its source directory makes a broad swath of files writable for no clear reason. Keeping program files read-only and assigning separate locations to cache, uploads, and temporary files lets reviewers answer a narrower question: which user needs to write which path? The base image, binary, and command here illustrate the permission relationship, not a tested production image.

What COPY --chown can and cannot settle

--chown sets metadata for copied files at copy time. It does not change a directory mounted later as a volume, and it does not rewrite previously created paths. Docker also documents a name-resolution detail: user and group names need entries in the container's /etc/passwd and /etc/group, whereas numeric IDs do not require that lookup. In a multi-stage build, inspect the COPY in the final stage. The runtime process sees the final filesystem, so changing the source file in a build stage does not by itself establish ownership in the final image.

Now suppose /app/cache in the image belongs to UID 10001, but deployment mounts a host directory or persistent volume at that path. The mount hides the image directory at runtime. The effective ownership and permissions come from the mounted storage and the platform's handling of it. Rewriting the image's COPY --chown will not repair that path. Check the volume's owner, the runtime UID and groups, and the storage driver or orchestrator's permission behavior. A successful no-volume test cannot be presented as proof that production storage is writable.

Running the container as root to make the error disappear grants the process wider privileges without explaining the original permission mismatch. A recursive chmod 777 can be similarly misleading: it may make a local demonstration succeed while opening files that should remain read-only. Neither is a useful diagnostic conclusion.

Ownership is not the only possible cause of a write error. A parent directory may lack traversal permission, a target file may be read-only, the application may write to a different path than expected, the root filesystem may be mounted read-only, or a security policy may deny the operation. Start with the exact failing path. Record the process UID and GID and inspect the path and each parent directory. Then decide whether the fix belongs in COPY, directory creation, volume configuration, or the application's selected write location.

Verify the final runtime shape

A successful image build establishes that the Dockerfile was accepted. It does not establish the runtime write contract. Inspect ownership and mode bits in the final image; start the container as the intended UID and create, read, and remove a temporary file in each required writable directory. If deployment mounts storage, repeat the check with that actual mount. Bind the observation to the final image digest and runtime options, and keep the failed path and stat details when something breaks. These are proposed checks; the example in this article was not run and no production storage result is claimed.

Multi-stage builds add a subtlety. Dependencies may be installed as root in a builder stage, while the final stage copies artifacts and runs as a non-root UID. Inspect the final stage's COPY --from=builder and the final image's metadata. A screenshot of ownership in the builder stage does not establish ownership after the final copy. Record id, stat for the application and writable directories, and an actual write result for the final image. If startup downloads a model or generates migration files, identify that write location explicitly; a read-only root filesystem may expose an accidental write into /app even when ordinary startup worked elsewhere.

The runtime configuration can also override the image's selected user or supply additional groups. Permission checks use the identity of the running process, not merely the USER line visible in the Dockerfile. If an init container prepares a volume, include its result and the exact mounted path in the evidence. A successful main-container start does not establish that it performed its required writes. Conversely, a config file that only needs to be read should not gain write rights merely because a nearby cache directory does.

Finally, inspect path resolution. A relative log path can point somewhere unexpected after WORKDIR or an entrypoint script changes the working directory. Capture the resolved absolute path before changing permissions. That separates a wrong-path configuration from an ownership error and prevents repeated fixes to a directory the application never touches.

The decision is usually not “chown every file” or “make every directory writable.” Program files need read and execute rights, mutable directories need narrowly assigned write rights, and mounted paths need deployment-level verification. When a base image or UID changes, that path-by-path map tells the team what to check again. For a related release boundary, see the site's dependency remediation review: a build result and a runtime acceptance result answer different questions.
