When should pytest.importorskip fail instead of skipping?

Separate a missing optional module from a broken import and account for pytest's version-specific default.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-20 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • pytest 9.1 changes importorskip's default caught exception to ModuleNotFoundError; verify each CI lane's installed version.
  • A missing transitive dependency can still raise ModuleNotFoundError inside an installed package.
  • A full-support lane needs an explicit import gate and behavioral tests, with skips reviewed against its promised feature matrix.

A test suite has an optional database adapter. On a developer machine without it, skipping the adapter tests is sensible. In CI, the adapter is supposedly installed, but its import fails inside the package and the same tests disappear as skips. A broken build has now been presented as an environment without an optional feature. pytest.importorskip() sits at this boundary: it is a policy for when a test may be absent, not merely a way to keep the run green. Its exact behavior also depends on the pytest version.

Suppose my_adapter is an optional accelerator supported on selected platforms. A test module might start like this:

import pytest
adapter = pytest.importorskip("my_adapter", reason="optional adapter absent")

def test_adapter_round_trip():
    assert adapter.round_trip(b"abc") == b"abc"

In an environment explicitly lacking my_adapter, a skip is an honest description: the capability is unavailable there. In a CI job that promises the adapter, a skip is a signal to investigate, even if the process exits successfully. Record the pytest version, whether the target package is installed, the exception type and traceback, and what this job promised to test. A final line saying “passed with skips” cannot distinguish a legitimate optional environment from an installation failure.

The stable pytest API reference says exc_type was added in 8.2 and that the default changed to ModuleNotFoundError in 9.1. Passing exc_type=ImportError explicitly widens the skip behavior to include a general ImportError raised during module import. A project that runs several pytest versions should not assume their defaults match. Consult the documentation for the installed version and preserve the raw result from that version. The version boundary is part of the test contract, not an implementation footnote.

# Widen this only when the test matrix intentionally accepts it.
adapter = pytest.importorskip("my_adapter", exc_type=ImportError)

That explicit argument is not automatically an improvement. Imagine the package is installed, but its __init__.py imports a native extension that a damaged build omitted. Importing my_adapter may raise ImportError or ModuleNotFoundError. If the suite treats every import failure as “optional module absent,” it can silently skip precisely the broken artifact CI was meant to detect. The distinction is based on what the environment promises and where the failure originated, not on whether an exception has a missing-module flavor.

The narrower 9.1 default also needs careful interpretation. ModuleNotFoundError does not by itself prove that the named target package is missing. An installed package can raise that exception when one of its transitive imports is absent. Inspect the exception's missing name, traceback and installed package metadata. If a full-support CI lane requires the adapter, give that lane an explicit installation and import check that fails when it is broken. A helper meant for optionality should not be the only gate for a required dependency.

One practical matrix has two jobs. A base job omits the accelerator by design and permits its dedicated tests to skip; the skip reason should identify the absent capability. A full job installs it, verifies a minimal import, then runs behavioral tests. A skip in that full job requires attention. Import alone is not the behavior test: the round-trip assertion above should still execute and check a real product operation. Conversely, a test whose only assertion is that importorskip produced a module has hardly checked functionality.

The friendly reason text can help humans read reports, but it does not alter which exception is caught. Platform-specific availability should be declared in the job definitions. One broad “optional adapter absent” label should not hide that macOS is optional while Linux is promised full support. If a native extension fails to load on a platform advertised as supported, expose the failure. A temporary decision to skip a known broken platform should be tracked as an explicit, time-limited exception, not buried permanently in exc_type=ImportError.

Where importorskip is called also determines how much coverage disappears. At the top level of a test module, it skips that entire module during collection. If the same file contains unrelated tests, those tests vanish too. Keep optional-capability cases in a focused file, or call the helper at a fixture or test boundary that matches the dependency. Review the collected test nodes and skip counts; a green exit code can conceal a substantial reduction in executed checks.

The site's strict xfail discussion concerns a different way a green pipeline can mask a changed test expectation. The objective here is not to ban skips. Optional functionality really can be absent from a supported environment. The objective is to separate intended absence, accidental omission and an installed but broken package. An isolated validation package could exercise three cases: target package absent, target package importable, and target package present with a failing internal import. Capture collection and execution output under the actual pytest versions the repository supports. I did not run that matrix for this article or establish that a specific project's CI currently misclassifies a skip.

For native extensions, preserve the Python version, operating system, architecture, wheel identity and full internal traceback in private CI artifacts. These details distinguish a platform for which no distribution was promised from a broken distribution on a promised platform. The useful metric is not merely the percentage of skipped tests. One skip on a required path can be severe; many skips can be correct if each matches an explicit environment contract. The version and argument rules in this article come from the official pytest documentation read for this draft; a real repository must check the pytest actually installed in each job.

When reviewing a failure, compare the skipped node list with the intended feature matrix rather than only the aggregate test count. If a wheel was updated, the import check and functional checks should run against that exact wheel in the full lane. If a dependency is deliberately absent, keep the skip visible and explain which supported configuration it represents. This turns a green build from an ambiguous color into a defensible statement about what was actually exercised.
