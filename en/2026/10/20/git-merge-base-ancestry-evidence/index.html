An empty git diff does not prove commit ancestry

Identical trees can have different histories. Use an ancestry check for commit inclusion and separate evidence for behavior.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-20 · Estimated read 13 min
Translations

Article

Key takeaways

  • Equal trees do not establish that the original fix commit is reachable.
  • An isolated fixture produced an empty diff and a negative ancestor check.
  • Ancestry and current behavior answer different release questions.

An empty git diff between two branches answers a content question: their current trees do not differ. It does not establish that one branch's history contains a particular commit. If a release review asks whether fix commit X is included in release commit Y, inspect the commit graph. Cherry-picks, rebases, independently reapplied patches, and reconstructed commits can separate the two answers.

Identical files, different histories

A Git commit records parent relationships as well as a tree. Imagine baseline B, a fix commit X on one branch, and a separate branch that starts at B and independently commits the same resulting file content as Y. X and Y can have identical trees. Y's parent chain still goes through B, not X. git diff X Y can be empty without contradiction: it compares content. The question “is X an ancestor of Y?” follows graph edges. The official Git documentation gives git merge-base --is-ancestor X Y for that question. Exit status 0 means yes, 1 means no; a different nonzero result can indicate an error.

This article includes a small executed fixture, isolated from the site's repository. The archived git-fixture.sh script creates a base commit, an original fix branch, and a replay branch with the same final content committed independently. The archived raw output in git-fixture.txt reports Apple Git 2.50.1, tree_diff=empty, original_ancestor_of_replay=no, and base_ancestor_of_replay=yes. Their merge base is the base commit. That observation establishes only the behavior of this temporary graph; it says nothing about the ancestry of a real release branch.

Why insist on a particular commit when content matches? A change request, review, signature, test receipt, or vulnerability ticket may be tied to X. The independently produced Y does not automatically inherit that evidence chain. A build pipeline may also key an artifact to a commit ID. On the other hand, if the review only asks whether the present file contains the desired fix, a tree comparison or a targeted behavior test may be more relevant. Define the claim first: current content, historical ancestry, or deployed artifact. No single green command answers all three.

Put the ancestry assertion in a check

For known full commit IDs X and Y, run git merge-base --is-ancestor X Y. A zero exit status supports reachability of X through Y's parents. Status 1 says the history does not contain X. Scripts should distinguish 1 from other failures, rather than recording a malformed reference or damaged repository as a clean negative. Resolve the references with git rev-parse --verify first and save the resulting full IDs. Branch names move, and a stale local origin/release may not represent the remote state that a review claims to cover. State which fetch and remote reference were checked.

Plain git merge-base X Y returns a best common ancestor, which is not necessarily the most readable way to assert “X is included.” The documentation notes that criss-cross merges can have multiple best bases; without --all, which one is printed is unspecified. Comparing the base to X is an older idiom. --is-ancestor expresses the actual question through its exit status.

A cherry-pick illustrates a necessary negative result. A new commit X' can carry substantially the same patch into Y without making original X an ancestor. The ancestry check correctly fails, but “the fix is absent” would be an unsupported inference. Record the cherry-pick relationship, inspect the patch and target state, run relevant behavior tests, and tie the target build to its actual commit. Conversely, an ancestry check that passes does not prove later commits kept the behavior intact. A subsequent revert can leave X in the history while removing its effect from the current tree.

Carry the evidence through delivery

Suppose a release note says “includes X.” If the ancestry check returns 1, ask whether the note promises the original reviewed commit object or an equivalent patch. A strict traceability requirement may require a different merge path or corrected wording. A behavior requirement needs evidence from the target branch's actual commit, tests, and build artifact. An empty git diff, a passing test, and a successful ancestor check support different propositions. None alone proves that production is running the desired artifact. Deployment evidence must bind the artifact digest and running version to the target commit.

CI needs a precisely identified pair of references. A pull request's source head, its synthetic merge commit, and the release head can be three different objects. Proving that X is reachable from the source head does not establish that the deployed artifact came from that head. Print the checked target SHA in CI and carry it into the build manifest. If the running artifact later reports another SHA, investigate the release selection rather than arguing about a local diff.

A shallow checkout is another practical boundary. If CI lacks X or part of the parent chain, a failed lookup cannot fairly be recorded as “fix absent.” Confirm that the required objects and history are available, fetch the minimum missing history, and only then run the assertion. A history rewrite can intentionally make an old SHA unreachable, but the old approval and new commit need an explicit mapping and fresh evidence. Do not silently replace a traceability check with a file comparison.

Even substantially identical patches need contextual review. A function can carry the same lines while a different caller or build configuration bypasses it. Ancestry gives a strict historical answer; current tree inspection, behavior tests, and artifact identity cover effects that the graph cannot express.

The temporary fixture shows why a review tied to an approved commit cannot collapse “same files” into “same approval.” It also shows the limit of ancestry checks: they establish that an object is reachable, not that every later change preserved its effect. A useful release record has three columns: target commit ID; required source commit ID and ancestry exit status; behavior test and artifact version. When a rebase or cherry-pick occurs, reviewers can say exactly which column changed. The site's tag push review covers another boundary: local ancestry does not establish a remote tag or a deployed version.
