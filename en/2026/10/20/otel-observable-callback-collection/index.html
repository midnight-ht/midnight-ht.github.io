An Observable callback is not a background scheduler

Registering an observation callback does not make it run per request. Its timing follows the reader and collection path.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-20 · Estimated read 14 min
Translations

Article

Key takeaways

  • Registration supplies observation logic; collection demand triggers callbacks.
  • Reader-specific collection and configuration determine timing, not the request rate.
  • Test state change, callback invocation, and backend display as separate events.

Registering a callback on an ObservableGauge supplies a function that observes a value when metrics are collected. It does not create an independent application scheduler, and it does not promise to run on every business request. The OpenTelemetry Metrics API specification says asynchronous instrument callbacks are invoked on demand and points to SDK collection for the trigger. The request rate belongs to a different timeline from the collection schedule.

An observation callback is not an event hook

Imagine a service with an in-memory work queue. A request adds a task; a worker removes it after processing. The team wants a gauge of the current queue length. Its callback reads the current size and records that observation. If two thousand requests arrive in a minute while a reader collects metrics every fifteen seconds, the callback should not be described as having run two thousand times. It is closer to reading a state snapshot during collection. “Asynchronous” in this metrics terminology does not mean the language's async/await syntax, and registering the instrument alone does not establish a separate background thread owned by the application.

This distinction should shape instrument choice. To count how many tasks were accepted during a period, increment a synchronous Counter in the task-receiving path. To observe how many remain queued at collection time, use an asynchronous Gauge over the current length. A callback that samples the current value can miss tasks that arrive and leave between collections. It cannot reconstruct a complete event count from those snapshots. Conversely, trying to invoke the Gauge callback once per HTTP request treats a collection mechanism as a request hook. First name the measurement: cumulative events, change during an interval, or current observable state.

Collection owns the call timing

The API specification separates MeterProvider, Meter, and Instrument responsibilities. Applications register the callback through an instrument. The Metrics SDK specification requires callbacks to be invoked for the particular MetricReader performing collection; observations made there apply to that reader's collection. It also recommends a timeout to prevent an unbounded callback and requires a callback round for an instrument to finish before its next collection round begins. These are specification boundaries. Scheduling and timeout configuration still depend on the language SDK and version actually deployed.

With two readers, “the callback executes exactly once every fifteen seconds” is an unsafe blanket statement. Readers can have different collection schedules; an explicit collection may also invoke the callback. Placing an expensive database query in that function shifts the query cost into the metrics pipeline and may delay or time out collection. A safer design can maintain a thread-safe, cheap-to-read current value in the business path and let the callback observe it. If an external query is necessary, specify its time limit, failure behavior, and acceptable staleness. Otherwise, the monitoring code becomes a new source of load.

A stronger counterexample is to use the callback to perform business maintenance. Suppose it also deletes expired orders. In an environment without active collection, or after a reader is disabled, the cleanup frequency changes. Order expiry should belong to an explicit job or transaction; instrumentation should observe the result. Even if a particular SDK configuration currently collects at regular intervals, that regularity comes from the reader configuration, not an independent scheduling guarantee created by the Observable instrument.

Trace a value through three moments

An isolated test could start with a controlled queue value of 3, trigger a known reader's collection, and record the callback invocation, observed value, and attributes. Change the queue to 5 between collections, then trigger collection again. The expected distinction is that the next observation reflects the state read at collection time; the state change alone does not automatically produce a new exported measurement. Where the SDK offers manual collection, it is easier to separate “a request happened” from “collection happened” than by waiting for a periodic exporter. Record the SDK version, reader type, collection interval, callback timeout, and whether multiple readers exist before generalizing the result.

Also test a callback that throws, exceeds its timeout, reports duplicate attribute sets, or cannot reach its data source. Error handling and persistence of earlier values require examination in the chosen SDK and backend. Do not turn “no reading” into “zero.” For queue length, a read failure is not an empty queue; reporting zero can falsely suggest that backlog cleared. Attribute choices need scrutiny too. Adding order IDs or user IDs to observations can produce large numbers of metric series in one collection and exceed a team's cardinality budget.

A collected value represents the state observed at a collection point; a blank space between exports is not proof that a queue stayed at zero. With multiple processes, each process reports its own queue. A dashboard must use resource identity and labels to decide whether to sum replicas, display them separately, or show another aggregation. Taking the last Gauge value across all replicas may display only one queue. Summing event counters as if they were current queue lengths is another category error. The callback supplies a process-level observation; cross-replica aggregation belongs to the query and display design.

The queue and test sequence here are proposed, not executed; there is no real SDK output in this article. The specifications establish on-demand invocation and reader-scoped collection. Exact cadence, number of invocations, and failure presentation need verification against the deployed SDK and configuration. The site's Delta and Cumulative temporality article addresses aggregation intervals; this article addresses when an observation is made. They solve different questions.

An acceptance record should separate three timestamps: the business state change, the reader's collection, and the backend's receipt or display. A slow dashboard update might come from the collection interval, export path, or query window. It is not evidence that the callback failed because it did not run inside a request. If every request event matters, instrument the request path with an event counter or appropriate business log rather than increasing an observation callback's frequency to imitate an event stream.
