Secrets do not automatically traverse nested reusable workflows

In an A-to-B-to-C workflow chain, secrets move one call at a time. Review mappings and permissions on each edge.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-20 · Estimated read 15 min
Translations
zh-CN en

Article

Key takeaways

  • A-to-B forwarding does not automatically grant the secret to C.
  • Secret availability and token permissions are separate checks along the chain.
  • Record each mapping, revision, and target result while keeping credentials narrow.

In a GitHub Actions reusable-workflow chain A → B → C, passing a secret from A to B establishes that the directly called B can receive it. C does not inherit it merely because C is the next workflow in the chain. B must explicitly choose what to pass when it calls C, and permissions across nested workflows can be maintained or reduced, not elevated. The GitHub documentation states that secrets are passed only to directly called workflows.

Draw the call chain as edges

Imagine release workflow A calling an organization build workflow B, which then calls signing workflow C. A has a deployment credential and a signing credential. It calls B with secrets: inherit, so B may receive the caller's eligible secrets. If B calls C without passing the signing secret, C will not magically find A's secret in its context. Troubleshooting should ask about two edges, A→B and B→C, not only whether A has a configured secret. Record the target workflow, referenced revision, transmission method, and name mapping on each edge.

This unexecuted, illustrative YAML shows where forwarding occurs. It omits trigger and permission configuration:

# Job in A calling B
jobs:
  build:
    uses: org/repo/.github/workflows/B.yml@main
    secrets: inherit

# Job in B calling C
jobs:
  sign:
    uses: org/repo/.github/workflows/C.yml@main
    secrets:
      signing_key: ${{ secrets.signing_key }}

This is not a recommendation to inherit every secret. GitHub's own A→B→C example makes the narrower point: A can pass all eligible secrets to B while B passes just one to C; the others are unavailable to C. For a signing workflow, forwarding only signing_key is easier to audit than forwarding every deployment and package credential. A real configuration must also check the called workflow's declared inputs, secret names, repository accessibility, and referenced revision. The names in this snippet are placeholders, and no run has verified the YAML as a complete release workflow.

Secrets and permissions need separate maps

Receiving a secret does not grant a job broader GITHUB_TOKEN permissions. GitHub documents that every nested reusable workflow must be accessible to the caller and that permissions can only be maintained or reduced along the chain. A review should list where each secret travels and what each job's token can do to repository resources. C may have an external signing-service credential but lack permission to write a GitHub Release. Conversely, a token with release-write permission will not supply an external signing credential. Treating both failures as “the secret was not inherited” points the repair at the wrong mechanism.

Environment secrets add a different source boundary. GitHub notes that workflow_call cannot pass environment secrets through that trigger; a called workflow job that specifies an environment can use secrets supplied by its own environment configuration. During review, determine whether C read a named secret explicitly forwarded by B or a same-named secret made available by C's job environment. Matching names do not establish matching provenance. A test might appear to prove A→B→C forwarding while actually succeeding because C already had an environment-level credential. Rotation or repository migration can expose that mistake later.

Diagnose absence without exposing the value

First confirm which revision of B actually ran. Then inspect the B→C job's secrets mapping. If C reports a missing signing_key, compare C's expected name with the key supplied by B and check whether B itself can access the source secret in its context. Do not print the secret into logs as a diagnostic. A non-disclosing presence check and a controlled call to the target service can establish more safely where the path fails. Presence alone proves only that a variable is nonempty; it does not establish that the value is current, scoped correctly, or accepted by the target. Record those as separate observations.

A tempting repair is to change both edges to inherit so that C receives everything. That can remove one missing-variable error while spreading deployment, signing, and unrelated credentials to more workflows, actions, and repositories. Instead, give each edge a minimal list of secrets and use explicit mappings where possible. If inheritance is genuinely required, document which caller secrets are eligible and why the called workflow needs that breadth. After changing the configuration, verify the intended operation and verify that C did not acquire unnecessary credentials or increased token permissions.

Another failure mode begins after B has correctly forwarded the credential. C reaches the external signing service, which rejects an expired, revoked, or incorrectly scoped value. That is a credential lifecycle or target authorization problem, not a reusable-workflow propagation problem. The site's secret rotation and revocation article covers the lifecycle. A nonempty value in C is not proof that an artifact was signed, an image pushed, or a deployment completed.

Minimal privilege starts with the workflow's job. Does B need the production deployment credential merely to build an image? Does C need package-registry push access merely to sign an artifact? If a single called workflow combines building, signing, and deploying, a narrow secret list may be difficult. Splitting duties into smaller reusable workflows adds edges but makes each edge's credential purpose explicit. Reviewers can then trace a secret to the task that actually consumes it instead of inheriting all secrets to silence errors.

Cross-repository calls add accessibility and version checks. Correct secret mapping does not help when the called workflow file is unavailable to the caller or its referenced branch has changed unexpectedly. A mutable @main is useful for explaining syntax but is weak as the only revision evidence for a sensitive release chain. A review may pin an approved revision and record the commit actually resolved during the run. If C's interface or secret name changes, that version record turns a vague “GitHub lost the secret” report into a specific compatibility question.

Scope and runtime identity matter as well. Organization, repository, and environment secrets have their own availability settings. If B cannot read a value in its context, a forwarding declaration cannot create it for C. An environment approval that has not completed, a protected branch restriction, or a revoked credential can produce a failure distinct from the one-hop propagation rule. Trace A's eligible input, then A→B, then B→C, and finally the target operation. Preserve redacted evidence at each step; printing the original value is not necessary.

A controlled validation can run two cases in a test repository with narrowly scoped credentials: B→C omits the secret and C follows its expected missing-secret path; B→C forwards it explicitly and the target operation produces its real receipt. Record run ID, A/B/C revisions, mappings, token permissions, and target result without storing secret text. This article did not run GitHub Actions or access a real secret. The conclusion should say which edge passed which secret, whether C used it, and whether the target action completed. “Inheritance is enabled” is too vague to support any of those claims.
