Why a literal percent sign expands a PostgreSQL LIKE search

A bound search value can still contain LIKE wildcards. Escape literal input and test the resulting match set.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-20 · Estimated read 13 min
Translations

Article

Key takeaways

  • Binding a LIKE value does not turn wildcard characters in that value into literal text.
  • A literal contains search must escape user input while leaving its own outer wildcards intentional.
  • The saved probe checks only the conversion string; PostgreSQL result sets still require application-level verification.

A user types 50% into a search box to find prices containing a percent sign. The result list also contains 500 and 50 dollars, neither of which has that character. If the backend inserts the input into a PostgreSQL LIKE pattern, % means any sequence of characters. Binding the value as a parameter keeps user text out of the SQL structure, but it does not decide whether that value should be interpreted as ordinary text or as pattern syntax. Those are two separate responsibilities.

Wildcard syntax lives inside the value

The PostgreSQL 18 pattern matching reference defines _ as one-character wildcard and % as a wildcard for zero or more characters. With neither wildcard in the pattern, LIKE behaves much like equality. It normally matches the entire string, so an application implementing “contains” often adds its own % at both ends. Passing a user’s unescaped 50% then creates a pattern like %50%%. The middle percent sign has become an instruction, rather than the price notation the user entered.

Imagine three illustrative titles: discount 50%, discount 500 units, and 50 units. The intended literal search should return only the first. Its contract is straightforward: the application owns the outer wildcards that mean “any surrounding text”; any %, _, or escape character inside the user’s input remains literal. The following SQL shows one way to use a chosen escape character, !. It has not been executed against PostgreSQL for this article; the table and column are hypothetical.

SELECT id, title
FROM catalog
WHERE title LIKE '%' || :escaped_term || '%' ESCAPE '!';

:escaped_term represents a client-side bound parameter, not PostgreSQL’s native placeholder syntax. Before binding, the application first converts a user’s ! into !!, then % into !%, then _ into !_. For 50%, the fragment is 50!%. The outer percent signs still allow surrounding text; !% denotes the literal percent sign. For a_b, the fragment must be a!_b, or it could also match a1b. Escaping the escape character first matters because an original exclamation mark must not unexpectedly act on the next character.

The transformation itself was checked in an isolated Python 3.11.15 script saved with this editorial batch, with raw stdout. It converted 50% to 50!%, a_b to a!_b, and !% to !!!%. That probe checks string transformation only. It did not run a PostgreSQL query or establish the database result set. The last input is valuable because changing the replacement order can double newly inserted escape characters and produce a different pattern fragment.

Parameter binding and literal matching solve different problems

A common partial fix changes string concatenation into a parameter, for example a query that builds LIKE '%' || $1 || '%'. This is important for keeping user input from changing SQL syntax. Yet when $1 contains %, PostgreSQL still interprets that value as a pattern. Conversely, manually escaping wildcard characters while continuing to concatenate raw SQL strings does not establish protection against SQL injection. Review the fixed query structure and the intended pattern value separately.

Some products deliberately expose wildcard search. An advanced search box might promise that a_b means an arbitrary middle character. In that case, blindly escaping every symbol would break the feature. A plain text box and an advanced pattern mode should state their different contracts; separate controls or endpoints are clearer than asking users to guess how the same input will be parsed. Show the selected mode on the results page so a percent sign is not silently reinterpreted.

ESCAPE '!' is a design choice in this example. PostgreSQL documents backslash as its default escape character and allows another character with ESCAPE. ESCAPE '' disables escaping, which makes literal wildcard matching through that mechanism unavailable. A client language, SQL string literal, ORM template, and bound parameter each create a different layer where backslashes can be misunderstood. Choosing an explicit escape character and preparing a bound fragment is easier to review than counting visually similar slashes in a rendered query.

Test the accepted result set, not only successful execution

Use special inputs as negative tests. A percent-sign query should return titles with an actual percent sign, not every nonempty title. An underscore query should return titles with an underscore, not every title containing any one character. Queries containing the escape marker alone and alongside a percent sign check that the escape character itself can appear. Also test empty input, an ordinary multibyte term, and terms at the beginning, middle, and end of a title. Write down which rows should appear in each case before running the query. “No SQL error” proves far less than “the result set matches the literal search contract.”

Keep input normalization separate. If the UI trims spaces, document whether that happens before escaping and whether users need to search for a literal space. If the column can be NULL, a LIKE predicate will not make those rows match merely because the pattern has wildcards. A product decision that empty input means “show everything” should be implemented deliberately rather than inferred from LIKE '%%'.

ILIKE changes case matching according to the active locale; it does not remove the wildcard roles of % and _. Some collations further complicate what it means for non-wildcard text to compare equally. If the real requirement is ranked full-text retrieval, word forms, or large-scale substring search, literal LIKE escaping is only one small part of the solution. It does not promise a particular index plan or performance outcome. First establish correct semantics with a small contrast set, then inspect plans and data distribution in the actual application.

A useful review artifact has four columns: original user text, escaped bound fragment, final database pattern, and expected matching records. The site’s JSONB query and index discussion addresses a different query-design choice. Here the immediate decision is whether an ordinary search box treats a user’s percent sign as data. Once that is correct, performance and search ranking can be assessed with the real workload.
