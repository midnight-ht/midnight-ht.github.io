Sec-Fetch-Site describes a source, not a user's rights

Fetch Metadata can filter cross-site requests, while identity and object permissions still need separate checks.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-20 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • The header reports the initiator-to-target relationship, not identity or object rights.
  • Use it as an early route-aware filter while retaining authentication and authorization.
  • Handle missing metadata and legitimate cross-site callbacks through explicit route contracts.

Sec-Fetch-Site: same-site describes a relationship between the origin that initiated a request and the origin serving the resource. It does not identify the user, validate a login, or grant access to a particular record. The header can support an early filter for unwanted cross-site requests. Authorization still has to answer a different question: may this authenticated actor perform this action on this object?

The relationship the browser reports

The MDN reference defines four values. same-origin means scheme, host, and port match. same-site can include a different origin within the same site and accounts for scheme. cross-site means a different site. none can represent a user-originated operation such as entering a URL or opening a bookmark. The header is sent on requests to potentially trustworthy URLs, and normal page scripts cannot set the Sec- prefixed header directly.

Those properties make the value useful browser context, not a credential. Imagine app.example serves order details while analytics.example is another origin on the same site. A browser request from the analytics origin to the application may carry same-site. The header does not tell the application whether that origin is fully trusted or whether its script may read a particular customer's order. Even same-origin does not answer the object-authorization question. A signed-in customer should see only their own orders, and an injected script on the application's own origin can still produce same-origin requests.

Where a filter belongs

For a state-changing browser endpoint, an application might reject a reported cross-site request early unless that route has an explicit, reviewed exception. A same-origin request then proceeds to ordinary authentication and object-level authorization. A same-site request needs a route-specific decision: is a different origin under the same site supposed to initiate this operation? The right policy depends on the client's contract. Public images, a transfer endpoint, and an OAuth callback have different legitimate patterns.

This is an unexecuted, hypothetical decision sequence, not middleware ready to paste into production:

for a state-changing browser action:
    reject cross-site unless the route has a reviewed exception
    decide how this route handles missing and none values
authenticate the session or token
check this user's permission for this object and action
apply CSRF protection where cookie authentication requires it

Suppose POST /orders/42/cancel comes from the same-origin order page. Passing the source check merely permits the request to continue. The service still needs to establish that the current account owns order 42, that the order can be cancelled, and that the credential is valid. A cross-site form submission may be stopped earlier by the metadata rule. Yet an endpoint that treats same-origin as full authorization remains vulnerable to an object-permission mistake, and an injected same-origin script can still act through the browser. The header reduces one class of exposure; it does not cast the final vote on business rights.

Missing metadata is a policy decision

Not every legitimate client is a browser page that sends Fetch Metadata. Mobile clients, service calls, test tools, proxies, and browser behavior can affect which headers arrive. The MDN definition explains the meaning of a value when present; it does not guarantee that every legitimate request supplies one. Rejecting every missing value can break a supported client. Trusting every missing value creates an alternate route around a browser-specific filter.

State the contract per route. A sensitive form designed solely for modern browsers may treat missing metadata conservatively while providing a separate, explicitly authenticated API path. A mixed-client API should stand on complete authentication and authorization, using Fetch Metadata as an additional risk signal when available. Nor should none be translated into “trusted internal request.” A direct navigation is not proof that a user may perform a state-changing action.

The difference between site and origin matters when a product hosts uploads, user content, or partner applications on sibling subdomains. Those origins may have a very different trust level even though the browser reports same-site. List the origins and intended operations before adopting a permissive same-site rule. CORS configuration, Cookie SameSite behavior, CSRF tokens, and server-side permissions each address a separate part of the request path. Debug each layer independently rather than deleting one after another appears to work. The site's CSP rollout review covers another case where a browser signal needs a tested business path.

Exceptions deserve a maintained inventory. An external payment return, embedded component, or automation client may legitimately arrive from a different site. Tie any exception to a specific route, method, and authentication mechanism, and make it visible in logs. One exception is not a reason to permit every cross-site state change. Conversely, a public read-only resource may need cross-site access for legitimate embedding. Write down what each route is for before judging a metadata value. During review, ask whether the service rechecks object ownership against the authenticated identity instead of trusting a user ID supplied by the front end. That question finds authorization defects that a reassuring request header cannot reveal.

If a legitimate callback fails the filter, keep the failing request's actual metadata and the route's expected caller in the review record. A blanket bypass hides the contract error. A targeted exception lets the team retest both that caller and an unrelated cross-site attempt.

A practical acceptance matrix covers a same-origin page, a sibling origin, a different site, direct navigation, and a non-browser client with explicit credentials. Record method, route, observed metadata, authenticated user, object owner, and status. Then ask two accounts to request the same object: the source relationship may be identical while the authorization decision should differ. Confirm that a rejection occurred at the intended layer, not because a front-end script happened to fail. These are proposed checks; this article did not send requests to a real application. The result to establish is two separate properties: the source filter follows its route policy, and user and object authorization still work independently.
