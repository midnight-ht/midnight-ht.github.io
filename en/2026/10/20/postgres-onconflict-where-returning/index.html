Why ON CONFLICT can succeed while RETURNING yields no row

Trace insertion, conflict locking, the update condition, and the rows actually returned by PostgreSQL.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-20 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • A conditional ON CONFLICT update can lock a conflicting row yet return nothing when its WHERE predicate fails.
  • An empty RETURNING result identifies a stale update only after checking the exact statement and input cardinality.
  • Returned rows describe statement effects, while transaction commit and later current-state reads are separate evidence.

An inventory write completes without an error, yet the application receives no RETURNING row. The tempting diagnosis is that the driver lost the result, or that a successful upsert necessarily updated the existing record. A conditional ON CONFLICT DO UPDATE ... WHERE has another outcome: PostgreSQL finds the conflicting row, can lock it, then declines to update it because the condition is false. The statement succeeds, but no row qualifies for RETURNING.

This distinction matters in an event consumer that keeps the latest state for each order. Suppose an incoming event carries a version. A new order should be inserted; a newer event should replace an older state; an older or equal event should leave the row alone. The version is an application sequence number, not a PostgreSQL transaction ID. Start with a deliberately small table and a stored version of seven:

CREATE TABLE order_state (
  order_id bigint PRIMARY KEY,
  version bigint NOT NULL,
  state text NOT NULL
);
INSERT INTO order_state VALUES (42, 7, 'packed');

Now an old event for order 42 arrives with version six. EXCLUDED denotes the row proposed for insertion. The condition compares that proposal with the existing conflicting row:

INSERT INTO order_state (order_id, version, state)
VALUES (42, 6, 'created')
ON CONFLICT (order_id) DO UPDATE
SET version = EXCLUDED.version,
    state = EXCLUDED.state
WHERE order_state.version < EXCLUDED.version
RETURNING order_id, version, state;

Follow the statement in order. The primary key identifies order 42 as a conflict. The update path identifies the target row. The existing version, seven, is not less than the proposed version, six, so the WHERE condition fails. No update occurs and RETURNING has no row to report. The PostgreSQL 18 INSERT reference documents both relevant rules: RETURNING emits rows successfully inserted or updated, and a conflict row that was locked but not updated because the update condition failed is not returned. An empty result here is a valid “old event did not replace current state” outcome. It is neither evidence of a lost response nor proof that the proposed state was saved.

Change the proposed version to eight. If it is still newer when PostgreSQL evaluates the condition, the update happens and the returned row contains version eight. Use an order ID absent from the table and the insert path returns the newly created row. Those are three distinct cases: first insertion, accepted advance, and rejected stale update. An API that maps all three to success: true hides whether a write actually occurred. An API that treats the third as a database outage will retry an intentionally rejected old event. The correct response depends on the event contract, but it must preserve this difference.

The placement of WHERE is easy to misread. It does not filter the candidate input before conflict detection, and it does not define which unique constraint is targeted. PostgreSQL evaluates the update condition after identifying a conflicting row as a candidate for update. The unique key chooses the target; the version comparison decides whether to change it. The documentation also says the row can be locked despite the false condition. Therefore, zero returned rows does not mean the statement never touched a contended row. If many workers converge on one key, review lock waits and retry behavior separately from the number of returned rows.

For a single proposed row using this exact DO UPDATE clause, one returned row means the statement inserted or updated one row. Zero rows should first prompt a check of the stale-version branch. If the application must tell a caller the current version, that zero-row result does not contain it. Read the current row under an appropriate transaction design, or make a separate lookup part of the response contract. Do not echo the rejected proposed version six as if it were the stored version seven. A subsequent read may itself see an even newer version after another writer commits; the response wording should not pretend that this lookup is the same instant as the earlier condition evaluation.

Nor should zero rows be treated as a universal diagnosis for every INSERT ... RETURNING. An input query might produce no rows; ON CONFLICT DO NOTHING intentionally returns none for a conflict; an application might consume the wrong result object. First confirm the generated SQL, the input cardinality, the conflict action, and the driver call. An ORM can rewrite a statement in ways that differ from a hand-written example. Log a non-sensitive key, incoming version, returned row count and SQL shape during investigation. “Upsert succeeded” alone is too weak to reconstruct the branch taken.

Equal versions need an explicit rule. If replay of the same event is an expected idempotent duplicate, no update and no row can be the desired result, but the response should say “duplicate ignored” rather than imply a new write. If equal versions with different payloads indicate corruption, the simple < predicate will silently ignore a serious discrepancy. Detect or record that conflict separately. The NOT NULL version constraint in the example also matters: a null version would make the comparison unknown and could be mistaken for an ordinary stale event if the schema admitted it.

There is a second boundary beyond this statement. A returned row reports that this statement inserted or updated a row; an outer transaction can still roll back. The site’s earlier RETURNING and commit-boundary article examines that separate issue. Here the immediate question is why a successful statement returns no row. At the API boundary, use the returned cardinality to describe the statement’s effect, and wait for the transaction outcome before claiming persistence.

An isolated PostgreSQL acceptance check should retain the exact SQL, server version and raw output for at least three cases: a new key returns one row; a higher version updates and returns one row; a lower or equal version returns none and leaves the stored row unchanged. Add two interleaving writers if lock waits or competing versions matter to the service. These are validation steps, not tests performed for this article. I checked the PostgreSQL 18 documentation but did not execute this SQL against a database here, so the example outcomes are documented expectations rather than local measurements.
