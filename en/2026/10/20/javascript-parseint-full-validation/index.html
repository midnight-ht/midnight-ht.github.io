Integer Input: Validate the Whole String Before Parsing

Specify the accepted spelling, safe integer range, and business range before saving numeric input.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-20 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • parseInt accepts an integer prefix even with radix 10; it does not validate the whole string.
  • Full syntax, safe representation, and business range are separate gates.
  • The Node prefix result does not establish browser or server acceptance.

A quantity field receives 12px. Calling parseInt(value, 10) returns 12, so a check such as Number.isInteger(parsed) may accept it. The service then stores twelve units while the person may believe the unit suffix mattered. MDN’s parseInt() reference explains the behavior: parsing stops at a character that is not valid for the radix, and the integer prefix is returned. The function is useful when an integer prefix is the intended input. It cannot, by itself, validate a field whose contract requires the entire text to be a decimal integer.

Define the input language first

Suppose an inventory form accepts a quantity from 0 through 99, in ASCII decimal notation, without spaces, signs, or leading zeroes. A clear parsing path is: check the raw text against a full-string pattern such as ^(?:0|[1-9][0-9]*)$; convert it to a Number; require Number.isSafeInteger; then enforce the 0–99 example range. The pattern answers whether every character belongs to the agreed spelling. The safe-integer check answers whether JavaScript can represent the integer exactly. The range check answers whether the business operation allows it. Those are three different decisions, even when all three happen to reject the same input.

Changing the contract changes the parser. The example pattern includes 0; a shopper order that requires at least one item should reject zero at the business-range step. If leading zeros are accepted and normalized, 012 need not be an error. If localized digits are allowed, an ASCII-only pattern is inadequate, and normalization needs an explicit policy. The point is not to prescribe one regular expression for every product. It is to make the accepted language visible before choosing a conversion function.

Consider a table of raw strings under the example contract. 12 becomes twelve. 12px and 12.5 are rejected even though both yield 12 with parseInt. 1e3 is rejected even though parseInt yields 1. 012, an empty string, and text with leading or trailing spaces are rejected by the example spelling rule. A very large run of digits may pass the pattern but fail the safe-integer or range check. This table is more informative than one happy-path unit test that proves only parseInt("12", 10) === 12.

A minimal script under Node v24.21.0 confirmed the prefix behavior for this environment: 12px and 12.5 produced 12, 1e3 produced 1, 0x10 with radix 10 produced 0, and the empty string produced NaN. A string representing a very large integer with an n suffix was converted to an imprecise Number after parsing stopped. The saved script, command, and raw stdout show exactly what ran. The proposed quantity validator above was not executed in a form or server endpoint, so these API outputs are not application acceptance evidence.

Why other shortcuts do not finish validation

Using radix 10 is good when the intended base is decimal, but it does not require the whole string to be consumed. Number("12px") does reject the suffix, yet Number("") is zero, so it still needs a rule for empty input. A full-match regular expression can reject a suffix, but cannot prove that a very large digit sequence remains exactly representable or within a product’s permitted range. HTML type="number" helps with interface behavior and browser constraints, but requests can bypass the page. The server must enforce its own contract on whatever arrives.

The location of conversion matters as much as the function. If the browser converts 12px into 12 before sending the request, the server cannot recover the original spelling from that numeric payload. Logs that record only the parsed value also conceal why the user entered something else. Keep the raw string through validation at the relevant trust boundary, return an error tied to the original field, and preserve it for correction. Once validation succeeds, create the normalized number. If the API intentionally accepts a numeric payload instead, it still needs to check type, integer safety, range, and authorization independently.

Large integers expose another hidden mismatch. parseInt returns a Number, which has a safe-integer limit. A digit string beyond that limit can be rounded silently. If a product genuinely needs larger integers, it should design a separate BigInt or decimal contract, including serialization and storage, rather than swapping types inside an existing Number field. If it does not need them, rejection is usually clearer than an inaccurate quantity.

Bulk imports make the failure more costly. A row containing 12pcs may appear to import successfully while losing its unit. A strict import should report the row number, column, and original text, then apply the product’s stated strategy for rejecting the entire batch or isolating invalid rows. An error that merely says “invalid” loses the clue the person needs to repair the file. The problem is not stylistic purity about digits; it is a silent change in the meaning of an order or record.

One additional negative case is a field that is valid in a different domain. 1e3 expresses one thousand to many programmers, but the example quantity contract excludes exponent notation; parseInt turns it into one instead. A measurement importer might intentionally accept exponent notation, yet then it needs a grammar and conversion that consume the whole expression, a unit policy, and a safe range. It should not borrow a strict inventory parser or an integer-prefix parser by accident. Similarly, a negative stock adjustment may be legal in an administrative workflow while a shopper order quantity must be positive. Sharing a parser without sharing a contract can either reject valid work or silently accept dangerous input.

Validation should therefore be reviewed at the UI, API, and persistence boundary with the same set of raw examples. Confirm rejected text is not stored, that it remains available for correction, and that accepted values are the ones shown back to the user and recorded in audit data. Form validation authority discusses why a browser check cannot stand in for the service decision. parseInt can remain in code where prefix parsing is intentionally useful; for a strict integer field, complete spelling, representability, and business range must each have an explicit gate.
