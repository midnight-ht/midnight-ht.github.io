Why a half-filled composite foreign key can pass

Compare default null handling with MATCH FULL and choose a constraint that matches the optional relationship.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-20 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • A default composite foreign key can accept a partially null referencing pair without matching a parent row.
  • MATCH FULL rejects mixed nulls while allowing all-null optional relations; mandatory relations need NOT NULL too.
  • Inventory and repair historical partial pairs before claiming a constraint migration has validated existing data.

An event stores both tenant_id and account_id, and the two columns form a foreign key to an account. An import provides the tenant but leaves the account ID null. PostgreSQL accepts the row. That can look like a broken foreign key until you check the default rule for a multicolumn reference: if any referencing column is null, the row need not match a referenced row. The constraint may be working exactly as declared while admitting a state the product never intended.

Consider accounts whose IDs are unique only within a tenant. The parent key must contain both values, and an event may optionally point to an account:

CREATE TABLE account (
  tenant_id bigint NOT NULL,
  account_id bigint NOT NULL,
  name text NOT NULL,
  PRIMARY KEY (tenant_id, account_id)
);
CREATE TABLE event_default (
  event_id bigint PRIMARY KEY,
  tenant_id bigint,
  account_id bigint,
  FOREIGN KEY (tenant_id, account_id)
    REFERENCES account (tenant_id, account_id)
);

Assume (7, 19) exists in account. An event with (7, 19) has a valid reference. An event with (7, 20) must find that different pair or fail. But (7, NULL) is not forced to match a hypothetical account (7, ?). Neither is (NULL, 19). The PostgreSQL 18 foreign-key reference says that normally a referencing row does not have to satisfy a multicolumn foreign key when any referencing column is null. This is more permissive than the common business rule “fill in the complete account, or do not supply an account at all.”

For that business rule, declare the composite foreign key with MATCH FULL:

CREATE TABLE event_full (
  event_id bigint PRIMARY KEY,
  tenant_id bigint,
  account_id bigint,
  FOREIGN KEY (tenant_id, account_id)
    REFERENCES account (tenant_id, account_id) MATCH FULL
);

MATCH FULL changes which null combinations escape the reference check. Both null is permitted as “no account.” Both supplied requires an existing parent pair. A half-filled pair such as (7, NULL) or (NULL, 19) is invalid. It does not make null equal to a real account, and it cannot create a missing parent. The ingestion service must decide whether it has enough information to record a relationship. “The account ID has not arrived yet” is a workflow state, not a sound permanent value for a formally linked row.

The right constraint depends on what the columns mean. If every event must belong to an account, make both referencing columns NOT NULL and retain the composite foreign key; an all-null row should fail too. If an event can be entirely anonymous, MATCH FULL represents exactly two shapes: complete existing relation or no relation. A harder case occurs when tenant_id also means the event’s mandatory tenant ownership but account_id is optional. tenant_id NOT NULL together with MATCH FULL would reject a tenant-owned event without an account. That is a sign to reconsider the model: perhaps ownership needs a separate field or key, rather than asking one pair of columns to mean both mandatory ownership and optional account reference. Do not force MATCH FULL into a schema whose legitimate state it cannot represent.

An application filter can conceal the weakness for months. A report with WHERE account_id IS NOT NULL omits the half-filled rows. Later, an export or reconciliation uses the tenant ID and reveals records that appear to belong to a tenant but no account. Adding NOT NULL to only one member of the pair does not fix the optional relation; the other can remain null, and the default foreign key can still skip the reference check. Application validation gives people better error messages, but the database constraint is the common rule for batch jobs, administrator scripts and future services as well as the current API.

Before changing a production schema, inventory existing rows: fully populated pairs, both-null pairs and each partial-null shape. Decide whether a partial row has a missing value that can be recovered, should have been anonymous, or points to the wrong tenant. Replacing every null with a made-up default account would make the constraint pass by inventing a relationship. Test the migration and its data cleanup in an isolated database; retain rejected examples and the repair decision. If the rollout uses a stage where a new constraint exists but historical data awaits validation, report those two facts separately. This article does not execute a migration or certify current data.

Another question often appears beside composite foreign keys: performance. A foreign key describes an allowed relationship; it does not automatically choose every useful index for queries against the child table. The site’s child-side foreign-key index guide examines that independent concern. MATCH FULL addresses allowed null combinations. It does not improve a lookup plan. Conversely, an index does not stop half-filled references. A custom check that forbids mixed nulls could enforce that one shape rule, but it still needs the composite foreign key to prove a complete pair actually exists.

An acceptance matrix makes the intended behavior observable. Insert an existing complete pair and expect success; try a nonexistent complete pair and expect rejection; insert two nulls into the optional relation and expect success; try each mixed pair and expect rejection. In a mandatory relation, two nulls must fail too. Exercise the same cases through the import entry point to verify that errors identify the missing field and that failed records are not silently discarded. Keep the executed SQL, server version and raw result when doing that work. The outcomes described here follow PostgreSQL 18 documentation; I have not run these SQL statements in this environment.

A constraint failure on (7, NULL) can be useful evidence. It exposes missing source data at the point where the relation would otherwise become ambiguous. An importer can place incomplete records in a clearly named staging table with their raw input and source reference, then promote them only after both key parts are available. That separates “incomplete import accepted for repair” from “formal account relationship stored.” The database can then enforce the latter promise without pretending that every intermediate state is a valid account reference.
