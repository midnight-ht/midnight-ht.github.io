ClientIP affinity cannot own your login session

Service affinity routes by client IP. Test login continuity and revocation across replicas, IP changes, and Pod replacement.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-20 · Estimated read 13 min
Translations

Article

Key takeaways

  • ClientIP selects a backend by observed client IP, not by account identity.
  • Pod replacement and NAT can expose reliance on replica-local session state.
  • Authentication, revocation, and object authorization need an independent design.

Setting a Kubernetes Service’s .spec.sessionAffinity to ClientIP can direct connections from a client IP to the same backend Pod for a period. That is a routing rule. It does not identify a person, own a login session, or decide access to data. If an application stores logins only in one Pod’s memory, stickiness may hide the weakness during ordinary browsing, but it cannot promise session continuity. The Kubernetes Service documentation describes the feature in terms of client IP and backend Pod; the default affinity is None.

What the Service remembers

A Service handles connections and backend endpoints. It cannot read a login cookie or determine whether an IP represents one account or a whole office behind a NAT gateway. Multiple people can share the apparent client IP; one person can change IP on moving from Wi-Fi to mobile data. Treating a network address as an account identifier would be a category error. Even if traffic reaches the same Pod, the application must validate the session credential and check the resulting user’s permissions.

Kubernetes permits .spec.sessionAffinityConfig.clientIP.timeoutSeconds; the documented default is 10800 seconds, or three hours. This is the stickiness window, not a login expiration. A product requirement to keep a user signed in for seven days cannot be derived from it. Conversely, when a user logs out, traffic might still land on the former Pod, but the application must reject the old credential. Revocation belongs to the authentication system rather than the Service’s mapping timeout.

A two-replica failure scenario

Consider a hypothetical login endpoint that keeps session_id → user_id in Pod A’s memory. A customer signs in; their apparent IP is pinned to A, and subsequent requests seem fine. During a rolling deployment, A is replaced. The replacement process does not have the old in-memory map. A change of client IP or the expiry of affinity can route the request to Pod B with the same result. The phrase “same Pod” was never a durable storage promise; Pods and their processes have lifecycles.

Now consider two customers behind one office gateway. Both may be routed to A. Routing them together does not merge their identities. If the application assumes “same IP, same Pod” is enough to trust an earlier login, it creates a security defect. Likewise, a signed-in customer requesting another customer’s order must still be rejected by object-level authorization. Kubernetes Service routing has no knowledge of order ownership.

Choose the state mechanism deliberately

A login intended to survive across replicas can use a shared server-side session store or, for a suitable threat model, bounded verifiable tokens. Either design needs explicit expiration, rotation, revocation, and handling of permission changes. A shared store lets A and B resolve a session identifier against one record, but requires a decision about store outages and cleanup. Tokens can reduce store reads, while adding key rotation and a potentially difficult immediate-revocation problem. Choose based on the product’s tolerance for stale rights, latency, failure recovery, and operational complexity. ClientIP cannot make that choice for the team.

Affinity can still be useful as a performance or compatibility aid, such as preserving a short-lived local cache hit. State that as an optimization. A healthy replica selected without affinity should still make the correct authentication and authorization decision. Long-lived protocols have their own connection-lifecycle considerations; an IP affinity setting alone does not define the application’s session semantics. There may also be an ingress controller or cloud load balancer with its own routing behavior. This article addresses the Kubernetes Service setting, and a real production path needs each layer examined separately.

Test the boundary rather than the happy path

An acceptance plan can hold the login credential constant while changing one routing factor at a time: stable network, changed client egress, Pod replacement, and passage beyond the affinity timeout. Record the destination Pod, observed client IP, authentication result, and authorization result. “The page stayed open” is too weak to explain a failure. Add two accounts sharing one NAT egress and verify that their data stays separate. Log one account out and retry an old credential to verify that revocation is independent of routing.

The observed client IP needs inspection in the real topology. A CDN, ingress controller, or cloud load balancer may sit in front of it. Address translation can make many users appear to come from one proxy IP, concentrating them on a backend rather than distributing them by person. The same user’s requests can also arrive through different egress addresses. Do not equate an application log’s forwarded-address header with the IP used for Service affinity without checking the network path. Capacity and stickiness claims depend on that path.

Moving sessions to a shared store is only part of the login design. Verify that a permission change and logout take effect when requests visit different replicas. A shared cache without expiration or revocation policy still fails the “old credential no longer works” requirement. A signed token may remain cryptographically valid after an employee loses project access; the approval endpoint then needs a deliberate rule about reading current permissions. ClientIP offers no answer to that time-consistency question.

A preproduction exercise can turn affinity off, restart one replica, and run login, refresh, logout, and cross-account access checks. If something fails, preserve the failing request and the location of its session state. That gives the team a state-design task instead of a vague request to lengthen a routing timeout.

If disabling affinity makes a normal business request fail, the application is probably relying on replica-local state. The next step is to repair the state design or explicitly accept and document that failure boundary, not simply make the timeout longer. These are proposed tests; no live cluster result is claimed here. The release record should contain four separate assertions: routing behavior, login continuity, revocation, and cross-account isolation. The site’s dependency release review makes a related distinction: one green build or configuration signal does not verify business behavior.
