WCAG 2.5.3: Keep Visible Words in the Accessible Name

Compare visible text, computed names, and spoken commands across states and languages.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-20 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • A component with a visible text label needs that text in its accessible name.
  • ARIA name sources can override the original label, so review the computed name.
  • Check visible words and speech commands after state and language changes.

A button visibly says “Save,” but its accessible name is “Submit changes.” A person using a mouse can identify it immediately; a person using speech control may try to say the word they can see and fail to activate it. WCAG 2.2 Understanding Label in Name requires the accessible name of a component with a visible text label to contain that visible text. Putting the visible words at the beginning of the name is a best practice. The requirement ties the command available to assistive technology to the label the user can actually read.

Compare the rendered label with the computed name

For a native button written as <button>Save</button>, the text normally supplies its name. Problems often appear after a later layer overrides it. A designer may add aria-label="Submit changes" to explain the action, and a component framework may render it consistently. The visual text remains “Save,” while the calculated name becomes “Submit changes.” The visible word is no longer in the name. A name such as “Save profile changes” retains the visible word and adds context. Better still, when “Save” is too vague, the team should consider improving the visible label itself so both sighted and speech users receive the same promise.

aria-labelledby can similarly make a different piece of page text the name. A nearby heading may look related to a control but may not be the control's own visible label. Reviewers need to inspect the computed accessibility tree, not infer the name solely from DOM proximity. aria-describedby contributes description rather than the primary name; it is useful for format hints or extra instructions, not a substitute for the action word visible on the control. Labels, names, and descriptions serve different jobs.

A concrete table helps during a review. Put the visible text in one column, the computed accessible name in the second, and the phrase a speech user is likely to say in the third. For a button visibly labeled “Export,” a name of “Download report” lacks that word. A name of “Export report” contains it and starts with it. The requirement concerns inclusion of the text, while the preferred order improves predictability. An exact string-matching script can find obvious mismatches, but punctuation, translation, abbreviation, and the behavior of a real speech product still need human inspection.

Treat a changed state as a changed label

An expand button may change its visible text to “Collapse” after activation. If the accessible name remains “Expand,” users of the two modes receive opposing instructions. Test the control both before and after activation, including loading or disabled states if the label changes there. Similar drift appears when localization updates the visible Chinese label but leaves an English aria-label in place. The requirement must be evaluated for the rendered language and the rendered state, rather than only the source component at rest.

Text presented inside an image is still visible text for this purpose. Rendering “Export” as an image does not make the label disappear. Conversely, an icon-only button with no visible words does not have a visible text label to include under this particular criterion, although it still needs an accessible name under other accessibility requirements. An icon beside a visible “Export” caption deserves examination as one control: if that caption labels the button, the name should include it. A toolbar heading such as “File actions” is context, not automatically part of every button's label. The W3C explanation cautions against treating every adjacent word as a label.

The choice of name should follow the user-facing action. A visible “Delete” button that removes an entire project should not hide the scope only in the accessible name while leaving the visible word dangerously broad. Revise the visual promise or add an appropriate confirmation so all users know what will happen. Likewise, enlarging the pointer area, as examined in target size and spacing, can reduce misclicks but cannot establish that a user can speak the control's visible label. These are different checks on the same component.

Test an actual command route

Start with a component inventory that includes forms, toolbar buttons, links styled as buttons, and custom controls. Record visible words and the browser's computed accessible name for each relevant state and language. Check whether the visible text occurs in the name, preferably at the start. Then ask a speech-control user or tester using the supported product to activate the control by the phrase they can see. When the phrase fails, record the browser, operating system, speech tool, control state, and name calculation. A passing accessibility-tree snapshot does not prove every speech engine recognizes every utterance, but a mouse click says almost nothing about this problem.

Also verify that a fix does not erase a useful distinction among repeated controls. A list with several “Remove” buttons may need names such as “Remove invoice 42” and “Remove invoice 43,” while each still begins with the visible word “Remove.” If the visual labels themselves differ, keep the names aligned with those exact words. The extra context should clarify the target without swapping out the command the person sees.

Names can also become stale when a reusable button component accepts both visible children and an independent accessibility-label prop. A copywriter changes the visible text in one language, but the prop remains the old command. A component test can compare rendered text with the computed name for common states, while content review checks whether added context still describes the action. That combination is more durable than patching one screen and leaving the component API able to recreate the mismatch everywhere else.

The acceptance record for this criterion should be a mapping of what appears, what the program names, and what the user can say. This article explains how to build that mapping, but it has not run speech control against a particular live page. A team can approve a specific component only after checking its calculated name and its real interaction states, then maintaining that relationship when copy or localization changes.
