Intl.NumberFormat: Display Rounding Is Not Settlement

Trace original, settled, stored, and displayed values before deciding how a rounded total should read.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-20 · Estimated read 14 min
Translations
zh-CN en

Article

Key takeaways

  • Intl.NumberFormat formats a display string without rewriting the input value.
  • Rounding each line before summing can differ from rounding the raw total.
  • The Node run establishes a local display example, not a production settlement rule.

A price table shows two line items as 1.23 and 1.23, then a total of 2.47. It may look inconsistent if a reader adds the visible rows, but the calculation can be coherent when each original value is 1.234: the raw total is 2.468 and only then is it formatted to two decimal places. The problem is that the interface has not explained which numbers are computed and which are merely displayed. MDN's Intl.NumberFormat options define how a formatter rounds for presentation; the format() method returns a string. Neither operation silently rewrites the source value into an approved business amount.

Follow the number through its layers

Start with the original input. Then identify the point where a product calculates a charge or measurement, the point where it stores a settled value, and the point where it creates a localized display string. A formatter may show two fraction digits while the Number supplied to it retains three or more. If a code path formats first and then parses the display string back into a number, a presentation choice has become a business calculation. Localization makes this even more fragile: a comma, period, grouping space, or currency symbol may have a different meaning or no numeric meaning to the parsing code.

The line-item example has two legitimate possible contracts. One contract rounds each item to 1.23 and then adds those settled amounts, producing 2.46. Another adds the original amounts to 2.468 and rounds the total to 2.47. Which one applies depends on the agreement, tax or billing rules, and the unit being charged. Intl.NumberFormat cannot choose between them. A design review should write the chosen calculation order down, show the unformatted intermediate amounts, and make the display consistent with that rule. If the product wants users to reconcile a visible sum, it may need to show an adjustment, extra precision, or wording that explains the total basis.

A local script under Node v24.21.0 used en-US, minimum and maximum fraction digits of two, and two original values of 1.234. Its stdout recorded both unchanged originals, two displayed strings 1.23, the original sum 2.468, a formatted total 2.47, and typeof the formatted result as string. resolvedOptions() reported halfExpand for that formatter. The script and raw output are retained with the draft. This proves the specific runtime example, not the behavior of every browser, locale, currency format, or production billing service.

Currency defaults are not a billing policy

A common shortcut is to treat every monetary amount as two decimal places. Currencies have different conventional minor units, and a product may have price, tax, quantity, and settlement rules that do not align with the formatter's default currency digits. The formatter's style: "currency" can select a presentation default from a currency code, and its roundingMode can control display rounding. It does not decide how a contract rounds a tax line, when an invoice amount becomes final, or whether a database column should store the original or settled amount.

Representation also matters. JavaScript Number is a binary floating-point type, so not every decimal fraction can be represented exactly. For accounting where exact decimal rules are essential, teams often use a defined smallest-unit integer or a decimal numeric model and apply an explicit rounding rule at the right business boundary. This is an engineering choice to evaluate against the product contract, not a claim that one representation fits every measurement. A percentage, a scientific reading, and a settled payment can reasonably follow different precision policies.

The database can impose another transformation. PostgreSQL numeric rounding examines how a column's declared scale affects stored values. Imagine a browser displaying two decimals, a service computing three, and a database column reducing to two. All three screens may say “two decimal places” while holding different values. Record the original input, calculation intermediate, approved settlement amount, persisted value, and displayed string separately in a review. An export or report should also say whether it contains original precision or settled amounts; otherwise two views of one record can appear contradictory without an obvious explanation.

Test changes, not just screenshots

Use values that already have two decimals and values with a third digit that changes the visible result. Add positive and negative cases, a value near a rounding midpoint, zero, a very large value, and the locales the product supports. Compare the original before and after formatting, the format() return type, resolvedOptions(), per-row displays, total display, and the server or database value. Some localized string details vary across environments, so a cross-runtime test should assert the product's monetary relationship rather than hard-code one space character or grouping mark as universally correct.

Editing creates a more subtle edge. If a form shows 1.23 while its backing value is 1.234, and the user changes an unrelated field, what is submitted: the original 1.234, the displayed 1.23, or an error requesting confirmation? Repeated edit-and-save cycles can repeatedly round if the display string becomes the new input. If people may edit only two-decimal settled amounts, constrain that in the input contract and store the confirmed result. If the number is a read-only approximation, label it or show enough context that it does not masquerade as an exact editable value.

A report export is a useful negative test. If the screen rounds each row for readability while the CSV exports raw values, both outputs may be correct under a declared contract, but the column names and documentation must make that difference discoverable. If the CSV instead exports the displayed strings, downstream software may parse a currency symbol or grouping separator incorrectly. Decide whether the export is machine-readable numeric data or a human-facing view, and test it accordingly.

An acceptance test should finish at the business result, not at “the formatter displays two digits.” Which value participates in the total, where does the rule round it, and what does the user see after persistence and reload? The Node run demonstrates why those questions are separate. It does not validate any real invoice or transaction. Only a product-specific calculation trace can prove that the displayed amount and the recorded amount follow the same declared policy.
