Cache-Control private: Decide Which Cache May Store the Response

Separate browser storage, shared caches, authorization, and freshness for personalized HTTP responses.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-10-20 · Estimated read 13 min
Translations
zh-CN en

Article

Key takeaways

  • Unqualified private bars shared-cache storage while private caches may still store the response.
  • Private does not replace origin authorization, freshness rules, or sign-out testing.
  • Authorization requests have separate RFC 9111 shared-cache reuse conditions and exceptions.

An account API returns Cache-Control: private, yet the browser's network panel later shows a cached copy. That observation does not, by itself, reveal a failed configuration. RFC 9111's private response directive says an unqualified private response must not be stored by a shared cache; a private cache may store it subject to the other caching constraints. The directive distinguishes storage scope. It is not a promise that no device, application component, or log can ever retain the bytes.

Name the cache that may hold the response

A browser's cache normally serves one user agent context and is treated as a private cache. A CDN or intermediary proxy serving many users is a shared cache. For a personalized account summary, the first design question is whether the browser may keep a representation for the current user. The second is whether any shared node may store or reuse it. The third is what happens after the account changes, the user signs out, or another person takes over the same device. Saying only “cache on” or “cache off” collapses these distinct questions.

Suppose a help page is public and identical for every visitor. A shared cache may be useful. An order summary contains account-specific data and should not be made available through a shared cache under a general public rule. A highly sensitive credential response may warrant an instruction that prevents even private-cache storage. These are illustrative resource categories, not risk ratings supplied by the RFC. They help a team articulate the decision before choosing headers. The actual policy depends on the information and the product's threat and freshness requirements.

An unqualified private is not interchangeable with no-store or no-cache. no-store addresses storing by caches. no-cache permits storage but requires validation before reuse under its rules. private concerns which kind of cache may store the response. The related HTTP cache validation guide treats freshness and validation separately. An account summary that may remain in a browser for a short time still needs a rule for what happens after an order is canceled. “Who can store it?” and “How long can this copy be used?” require separate answers.

RFC 9111 also defines a qualified private form that names response header fields. Its scope is not the whole response: a shared cache may be allowed to store the remaining response if other conditions hold. Treating private="Set-Cookie" as protection for a personalized body would therefore misread it. The specification notes limited implementation of the qualified form and that caches may handle it as unqualified private. If the body belongs to an individual account, make the whole-response shared-storage decision clear. Only optimize a genuinely public body with a small private header after testing the particular cache product's behavior.

Storage controls do not authorize a request

A cache directive cannot repair an endpoint that returns another user's information to an unauthenticated request. The origin must decide whether the current request identity may see the resource. Likewise, after sign-out on a shared computer, a private browser cache can still have an older representation. Session invalidation, browser behavior, validation, and sign-out handling jointly determine whether that old view is reachable. private alone does not prove that a signed-out person cannot see an old page. It also does not govern extensions, downloaded files, or logging systems as if they were compliant HTTP caches.

Representation selection is another distinct problem. Vary helps a cache select among representations based on named request fields, as described in the Vary representation guide. It does not replace a rule against shared storage of account content, nor does a Cookie or Authorization value automatically become a safe authorization boundary merely because it appears in a cache key. A public page varying by language may be suitable for shared caching; per-account data asks a fundamentally different storage question. Mixing both in one opaque rule makes review harder.

Requests containing an Authorization header have an additional rule in RFC 9111 section 3.5. A shared cache generally must not use a cached response to such a request for a later request unless the response contains a directive that expressly allows shared caching and the cache follows that directive's requirements. The RFC identifies must-revalidate, public, and s-maxage as directives with that effect. It would be wrong to infer that an authenticated request can never be reused, or to add public casually to an individual's response. If an application uses a Cookie instead of the Authorization request field, this particular rule is not a general substitute for its account-isolation design.

Verify across identities and nodes

Use two accounts and an unauthenticated state against the same path. Capture the actual origin response headers and the headers observed after CDN, proxy, and browser handling. Then inspect whether a shared node creates a reusable entry and whether a later request from the other identity receives its own content or is rejected. In the browser, test refreshing within one identity, back navigation or offline behavior where relevant, sign-out and sign-in as another user, and a state change such as a canceled order. Do not put real private payloads into editorial logs merely to prove the test; use controlled data and minimal identifiers.

A network panel entry labeled “from cache” should be tied to the cache that served it. Conversely, one request reaching the origin does not prove every edge node never stored an earlier response. Age, vendor cache-status fields, configuration, and request traces can help, but none is a universal cross-CDN verdict by itself. The acceptance record should specify the resource's owner, permitted storage locations, reuse and validation conditions, and the sign-out boundary. This article has not run against a live CDN, proxy, or account; its examples are a verification design. The exact directive to ship follows that tested policy, not an assumption that private means absolute secrecy.
