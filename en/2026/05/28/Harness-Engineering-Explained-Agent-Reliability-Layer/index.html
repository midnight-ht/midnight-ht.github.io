Harness Engineering: Put Agent Permissions, Verification, and Stop Conditions Into the System

Using OpenAI’s published case and Agents SDK documentation, this guide separates prompts, runtimes, sandboxes, and approvals, then explains permission, verification, recovery, and failure-boundary design for coding agents.

Key takeaways

  • A harness combines task scope, tools, permissions, checks, and recovery; it is not a longer prompt or a universal product standard.
  • A sandbox limits execution, approvals express authorization, and automatic checks validate rules; none substitutes for the others.
  • Verify agent work with independent tests, scope checks, resumable state, and auditable side effects.

When an agent can edit a repository and run commands, reliability depends on whether boundaries, verification, and recovery are enforced in the execution path—not just on how detailed the prompt is. Harness Engineering is a useful umbrella for that control system: it combines task intake, context, tool permissions, execution environments, checkpoints, approvals, logs, and recovery. It is not merely a longer prompt, nor the formal name of one vendor’s SDK standard.

The distinctions matter. Prompting describes how to express a task. Context engineering determines what the model can read before acting. An agent runtime manages the model loop and tool calls. A sandbox restricts what commands can access. An approval policy decides which actions must pause for authorization. “Harness” describes how a team arranges these controls into an executable and auditable workflow. Products divide the components differently, so no single vendor’s feature list should be treated as a universal architecture.

What OpenAI’s published examples do—and do not—show

OpenAI’s February 11, 2026 post, “Harness engineering: leveraging Codex in an agent-first world,” describes an internal product experiment. The team says it built and shipped an internal beta over about five months, with Codex generating application code, tests, CI, documentation, observability, and internal tools. The authors estimate that development took about one tenth of the time of manual implementation and describe a codebase approaching one million lines. These are OpenAI’s account and estimate of its own work, not an independent controlled study and not a forecast for another team. The more transferable part is the reported mechanism: make the repository a source of context, guide progressive discovery through a small entry point, enforce architecture boundaries with structural tests and linters, and treat documentation maintenance and technical-debt cleanup as recurring work. The original post frames the results in OpenAI’s own internal launch and adoption setting.

An April 15, 2026 Agents SDK update shows a product-level direction. OpenAI describes capabilities for inspecting files, running commands, editing code in a controlled workspace, and sandbox execution. Its example specifies openai-agents>=0.14.0; that is the version condition for the sample in that release post, not a promise that every current SDK version, sandbox provider, or deployment has identical behavior. The update treats the harness and execution compute environment as separate concerns. The current SDK documentation likewise describes a control plane responsible for the agent loop, tool routing, handoffs, approvals, tracing, recovery, and run state, and a sandbox as the plane where files, commands, ports, and snapshots are handled. The Sandbox Agents guide documents a product design; it is not a required architecture for every custom agent.

Trace a control path through one code-change task

Imagine that a developer asks an agent to fix a form-validation bug. The following is a hypothetical design example, not a task executed in a real repository or SDK. Start by turning the request into an acceptance contract: which files may change, which paths are off-limits, what behavior counts as a fix, which checks must run, and what should happen if the requirement is ambiguous or a permission is missing. If the acceptance condition is still “make it better,” even a strong sandbox will only execute an underspecified goal more safely and quickly.

Next, supply context in layers. A repository entry point can lead the agent to an architecture map, the relevant module, formatting rules, and a runbook; the agent then reads what the task needs. The February case emphasizes keeping core knowledge in the repository and using progressive disclosure. In practice, documentation also needs a version, an owner, and a verification method. Otherwise, making the repository the source of truth can simply make outdated instructions easier to copy. For high-impact constraints, encode checks where possible: a change must not cross a module boundary, for example, or a new endpoint must declare its data shape. Documentation explains why; a linter or structural test supplies blocking evidence. Neither replaces the other.

Then narrow tools and permissions. Reading files, searching, applying patches, and running unit tests are distinct capabilities; shell access does not mean that every command should be unconditionally allowed. Tool interfaces should document arguments, results, timeouts, and failure semantics. Give separate approval treatment to side effects such as deleting data, publishing, writing to production, or sending an external message. SDK guardrails can validate inputs, outputs, or tool arguments; human approval can pause a workflow before a sensitive action. They answer different questions—whether an automatic rule passed and whether an action was authorized—and should not be collapsed into one green status. The approval guide presents automatic validation and human review as separate controls. A May 2026 account of OpenAI’s Codex deployment also describes technical boundaries, higher-risk approvals, network policies, and agent-native telemetry; it is a company deployment account, not a universal compliance checklist.

Set the execution boundary and preserve evidence. Give the task a workspace with limited filesystem access, only necessary network routes, short-lived credentials, and time and resource limits. Associate the original request, tool arguments, exit status, test artifacts, denial reasons, and final diff with a stable task ID. For a workflow that can pause across turns, specify what is persisted: conversation history, workspace files, snapshots, approvals, and temporary credentials are different kinds of state. The SDK documentation distinguishes a manifest describing a fresh sandbox’s starting contents from the state of a live session. Reconnection must follow the chosen provider’s lifecycle; saving chat history alone does not prove work can be resumed.

Finally, use a verifier that is independent of the model’s own description. For the example, acceptance should not be “the agent says tests passed.” A controlled command should record its exit status and test report; another check should confirm that the diff touches only approved files, run regression cases, and verify that the failing input now produces the expected result. Green tests still do not establish that the behavior matches user intent, so compare the output with the acceptance contract. Production deployment is a separate side effect and needs its own authorization and rollback plan. Each stage should produce evidence that another process can inspect.

Why a sandbox alone leaves failure paths open

A sandbox can reduce the blast radius, but it does not make every allowed action trustworthy. A November 18, 2026 Codex sandbox article from OpenAI gives an example: an agent might modify an installed local package, such as one under node_modules, which Git often ignores. If an editor later runs that package as a formatter, malicious code could execute beyond the sandbox boundary. The example means teams should inspect ignored directories, editor extensions, install scripts, and host processes—not only the Git diff. The sandbox article says that sandboxing prevents a class of risks and belongs within defense in depth.

Permission configuration also has a difference between “can read” and “can send out.” If a task can access customer files and has broad network access, the model may pass data through an allowed tool even if it cannot write the files directly. Conversely, disabling all network access can block dependency installation, documentation retrieval, or a test environment and tempt operators to grant broad temporary access. Begin with the task’s inputs, outputs, and required destinations; allow the smallest necessary routes, log each authorization, and keep unproven network actions disabled.

Recovery needs its own design. A command timing out does not mean it never ran; retrying can repeat a write. A partial patch may have reached disk before task state was updated. A child test process may outlive the main agent. Use idempotent operations or task IDs, and read current files and remote state before deciding whether to retry, roll back, or hand off to a person. Preserve immutable baselines and checkpoints for important workspaces. Do not bundle credentials into snapshots or long-lived conversation context.

Choose control strength by impact

A read-only assistant that generates code suggestions can often start with repository reading, search, and citations; it does not need a full sandbox workflow. A task that edits files and runs tests needs an isolated workspace, path limits, a time budget, test reports, and diff checks. An agent that handles customer data, installs dependencies, accesses networks, or invokes side-effecting tools also needs credential isolation, outbound policies, approval points, and auditable logs. For production data, payments, identity, deletion, or external publication, authorization and rollback remain separate gates even if the model, tests, and policy checks all return “allowed.”

Evaluate controls through observable signals, not component counts. Track whether out-of-scope attempts were denied, whether sensitive operations paused for review, whether failed tests blocked delivery, whether recovery repeated side effects, whether a human could resume the existing workspace, and whether logs reconstruct a decision. Do not collapse these into an “agent success rate.” A task may produce correct code without traceable sources; it may comply with permissions without meeting the user’s goal. This site’s article on risk-based quality gates discusses setting validation gates according to change impact; this article extends that idea to an agent’s tools and execution lifecycle.

A harness cannot replace model evaluation, human judgment, supply-chain security, or product acceptance. It can turn “do not do this,” “verify before continuing,” and “pause before side effects” into constraints that software can enforce, logs can explain, and recovery procedures can use. Public examples show how one team combines those mechanisms. Other organizations still need to model their own permissions, data, tools, and business impact, then test the boundaries with repeatable failure cases.
