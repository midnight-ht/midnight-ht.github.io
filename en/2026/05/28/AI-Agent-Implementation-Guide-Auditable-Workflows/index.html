From Chatbot to Auditable Agent: Define the Task Before Adding Tools

A hypothetical support-order workflow shows how to choose an agent-suitable task, bound tools and human review, and evaluate outcomes with traceable evidence.

M Midnight Engineering notes on development, quality, security, delivery, and operations. View Author Profile
Updated 2026-11-27 · Estimated read 25 min
Translations
zh-CN en

Article

Key takeaways

  • Choose an agent only when context, exceptions, or hard-to-maintain rules justify model-controlled workflow execution.
  • Decompose order handling into verifiable states, narrow tools, idempotent writes, and separate approval; the example is hypothetical.
  • Use representative tasks and end-to-end traces to evaluate tool choice, authorization, recovery, and acceptance separately.

If you want to turn a chatbot into an agent that can use tools, start by choosing a workflow with stable inputs, verifiable outputs, and a safe handoff path—not by adding more tools. When rules already cover the work, ordinary software automation may be enough. Bring a model into the decision only when the workflow involves exceptions, unstructured material, or contextual judgment. “Auditable” does not mean collecting the most logs; it means being able to answer what the task was, what evidence was used, which tools ran, how state changed, who approved a side effect, and how a person can take over after failure.

Decide whether the task needs an agent

A chat interface does not imply that you need an agent. Single-turn question answering, fixed-field classification, and template-based notifications can often use a model to produce structured output, followed by deterministic validation and processing. The practical guide to building agents, published on January 15, 2026, describes an agent as a system that performs a workflow on a user’s behalf. It distinguishes this from a chatbot or classifier that uses a language model without letting the model control workflow execution. The guide recommends looking for work with contextual or exception-heavy decisions, rules that have become difficult to maintain, or substantial reliance on unstructured material. It also says a deterministic solution may suffice when those conditions cannot be clearly validated. The official guide is product guidance, not independent research into agent success rates.

Turn that advice into reviewable questions before selecting a framework. Are inputs already structured, or must the system extract conditions from email, images, conversations, or long documents? Can rules express the decision, or are exceptions common enough that multiple facts need to be interpreted together? Can the output be checked through database state, policy rules, tests, or human review? Is the action read-only, or can it change an order, payment, permission, or external message? If execution fails, can the system stop and transfer control without leaving an irreversible partial state?

A candidate workflow that mostly reads two fields and updates a status under a clear condition may gain little from an agent and may add uncertainty. Consider instead a support request written in natural language: the system must understand the customer’s description, check an order record and policy, then determine whether the case is a simple query, a return, or an exception. A model can map the description to a bounded workflow branch. It should not automatically own every action that follows: lookup may be safe to automate, while writing, issuing a refund, or promising compensation should remain behind separate rules and authorization.

Turn a vague request into an acceptance contract

Consider the request, “Please handle this order.” This is a hypothetical design example; it was not connected to a support system, run through an agent, or tested with an SDK. First define the goal: the agent may look up the order and prepare a recommendation; a deterministic service checks refund eligibility; an authorized employee confirms submission. Then name the states, such as needs_order_id, lookup_pending, eligible_for_return, needs_human_review, approved, completed, and failed. These states tell the next person where the work stopped and prevent a plausible model response from being mistaken for a completed transaction.

The input contract should specify required fields, acceptable order identifiers, the source of identity verification, allowed data types, and what to do when information is missing or conflicts. If a customer says only “the thing I bought last week,” the system should not guess an order number and call a refund tool. It should ask for a verifiable identifier or transfer the case to a person. Policy references should retain a document version and effective date; if the return window changed, the agent must not rely on an outdated recollection.

Keep tools narrow by responsibility. lookup_order returns a read-only order summary. check_return_eligibility accepts the order ID, verified identity, and policy version, then returns a structured eligible, ineligible, or needs-review result. create_refund_request creates a pending review item rather than issuing money. The actual refund action is available only through an execution service after an authorized employee approves it. Each tool needs parameter validation, identity and resource authorization, timeout semantics, an idempotency key, and an auditable result. Read access should not silently imply write access, and “use carefully” in a tool description cannot replace server-side authorization.

The agent guide recommends rating tools by whether they read or write, their reversibility, required permissions, and financial impact, while preserving human oversight for sensitive or irreversible actions. The Agents SDK guide on guardrails and human review also separates automatic validation from approval: a guardrail can validate inputs, outputs, or tool calls; an approval pauses the run for a person to approve or reject. The documented pause returns an interruption and resumable state; once a decision is made, the application resumes that run rather than pretending it is a new request. The approval guide further notes that agent-level guardrails do not automatically cover every custom tool, so checks for side effects belong close to the tool that performs them.

Work through one failure path

In the return example, the agent looks up an eligible order and prepares to create a refund request. Before the tool runs, a support employee changes the order to “under dispute.” If the system simply continues from the earlier result, it may submit an action based on stale state. The fix is not merely adding “watch out for stale data” to instructions. The write service can re-read the authoritative state or require a matching version; if the state changed, it returns a recognizable conflict so the agent stops and explains that the order needs to be checked again.

A different boundary appears when a tool call times out. The client’s missing response does not mean the server failed to create the request. A blind retry can create a duplicate. Write tools should carry a stable idempotency key, while the state store distinguishes pending, submitted, rejected, and unknown-result states. When the result is unknown, query the existing request before sending another one. If the system cannot establish whether the action completed, ask a person to reconcile it. Recovery should be based on business state and operation identifiers, not on the model’s recollection that it “probably just did” something.

Preserve the evidence needed to reconstruct the decision: the original goal, confirmed order ID, identity principal, policy version, tool name and validated arguments, tool result, approver and time, and a reference to the final outcome. Auditing should not mean copying personal data or full payment credentials into every log. It means keeping the minimum evidence required to explain a decision while following retention and access rules. Conversation history, tool results, and approval snapshots are also different kinds of state; resuming a task means deciding which can be reused and which must be checked again.

When to split into multiple agents

The number of agents is not a measure of project maturity. The Agents SDK orchestration guide distinguishes two patterns: a handoff transfers control to a specialist agent, while calling an agent as a tool lets a manager remain responsible for the final response. Its guidance is to split only when a branch truly needs different instructions, tools, or policy. The orchestration guide documents patterns in that SDK; it does not prescribe an architecture for every organization.

For the order example, lookup, policy validation, and refund approval can start as service tools in a single-agent workflow. If the support process later branches into legal complaints or fraud investigation, those may warrant a specialist or a human queue because their responsibilities and permissions differ. If several agents merely summarize the same order repeatedly, each handoff adds state synchronization and audit cost without creating a useful ownership boundary. Choose manager-style tool calls or a transfer of control based on who owns the final decision, whether each branch can be evaluated independently, and what minimum data must cross between them.

Evaluate evidence from the workflow

Do not evaluate only whether the final answer sounds helpful. Build a representative, de-identified set of tasks: a normal lookup, a missing order number, an identity mismatch, a policy boundary, a changed order state, a tool timeout, a duplicate request, and a case requiring human judgment. For each, specify the expected state, allowed tools, actions that must be denied, the explanation shown to the user, and when retry is safe. Record sample sources and versions so the dataset does not contain only examples where the model did well.

A run should expose at least whether the final state met the acceptance contract, whether the right tool and arguments were used, whether access under the wrong identity was refused, whether an action paused for authorization, whether recovery repeated a side effect, and whether a human received enough evidence to continue. The agent workflow evaluation guide recommends using traces to inspect end-to-end model calls, tool calls, guardrails, and handoffs. Once “good” has been defined, datasets and evaluation runs enable repeatable comparison of changes to prompts, models, or routing. The evaluation guide describes platform features and a workflow; automated graders still need calibration against human-labeled examples.

Keep task completion, tool choice, out-of-scope denials, human escalations, successful recovery, latency, and cost as separate measures. Otherwise, the team cannot see what a change improved. Do not roll them into a single “agent success rate”: an answer can be correct but unauthorized, while a compliant stop can still mean the business task is unfinished. Before a pilot, assign an owner for escalations, a reviewer for failure cases, and a person who can roll back tool changes. The site’s Harness Engineering article discusses execution boundaries and recovery; this article focuses on which work deserves an agent and how to define workflow outcomes.

Start with a narrow pilot

A practical sequence is straightforward: select one frequent but context-sensitive task; collect representative inputs and real failure paths; have people handle them first and record decisions; define testable acceptance; then run the agent in read-only shadow mode. Compare its predictions with human outcomes and identify missing boundaries. Only after those checks should you allow limited writes for low-risk actions, with approval retained for higher-impact actions. The same evaluation examples should run again after every change to model, prompt, or routing.

If shadow runs cannot classify cases consistently, improve the input contract or source material. If classification is reasonable but the tool is often wrong, narrow the tool surface or clarify its parameters. If tool selection is right but state changes are duplicated, fix idempotency and recovery. If people repeatedly overturn policy decisions, keep that decision with a human instead of lowering the bar to meet an automation target. Agree on pilot thresholds in advance—case coverage, denial conditions, escalation response time, and tolerated side effects—so the team can decide whether to expand, revise, or stop.

Public documentation can help teams design agent components, but it cannot prove that a particular business workflow is suitable for automation, much less that deployment will be faster or cheaper. A worthwhile project handles context that rules cannot enumerate, with bounded permissions and clear verification, stop, and handoff paths. If a form, rules engine, or queue already solves the problem reliably, choosing the simpler option is sound engineering.
