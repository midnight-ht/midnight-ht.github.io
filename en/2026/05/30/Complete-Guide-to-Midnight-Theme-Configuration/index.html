Midnight Configuration: Pin the Version, Then Check Overrides and Modules

When a theme setting has no visible effect, check the pinned theme version, Hexo configuration precedence, and any plugin or server endpoint the module requires. Using this site’s locked Midnight source as a bounded example, this guide traces how a value becomes page behavior without treating a switch as proof of a live service.

Key takeaways

  • Check the locked theme version and configuration precedence before deciding whether a key is still supported.
  • A module switch controls theme conditions; it does not provision an endpoint, account, plugin, or backend.
  • Verify generated pages, output paths, and real service behavior; the search-debugging walkthrough is hypothetical.

When a theme setting is present in a file but the page does not change, do not start by copying another “complete configuration.” First identify the Midnight version installed by the site, then determine which Hexo configuration source wins, and finally check whether the option also needs a plugin, a server endpoint, or a real account. A configuration key proves only that a value was written. It does not prove that a feature is running.

The old guide described the theme as v0.1.16 and treated appearance.accent as the current accent-color option. That was a time-bound description, not a safe reference for every release. This site’s package-lock.json pins hexo-theme-midnight to commit ebd48f3e96b55524f0b4cc980e34cbc5ade7166e, while the installed package metadata reports version 0.4.9, as shown in the package.json at that commit. The defaults discussed below are scoped to that commit. This is not a claim about the latest Midnight release, and a future upgrade may change the available keys. For a first check, open the default config pinned by this site instead of copying an older guide found in search results.

Distinguish the three configuration sources

Hexo’s official documentation describes several places where theme settings can come from: the theme’s own _config.yml supplies defaults; the site-root _config.midnight.yml is a dedicated theme config supported since Hexo 5.0; and theme_config in the site’s primary _config.yml has the highest priority. The documented example merges nested objects, with the later value winning for the same key. If a value is written in a higher-priority location, editing the theme default may not change the result. See Hexo Configuration for the exact precedence.

For example, the main site config can select theme: midnight, while the dedicated theme file sets appearance values. If the main config also sets the same field under theme_config.appearance, the higher-priority value is the one to investigate. Search for the full path, such as appearance.default_scheme, across the configuration files; searching only for appearance and selecting a block by eye is unreliable. Also check for repeated top-level YAML blocks such as appearance:, seo:, or comments:. Hexo-theme-midnight's integration guide recommends keeping each top-level key in one block when combining examples, so a later block does not accidentally replace an earlier one.

That is one reason to avoid copying the entire theme default file into the site. The copy looks convenient, but it turns default values into a private snapshot: new defaults do not flow into it after an upgrade, and removed or renamed keys can linger. A more maintainable approach is to keep only the values the site intends to override and pin the theme source in the dependency lockfile. During an upgrade, compare the new default config deliberately instead of letting the theme package and a copied file drift apart silently.

A palette setting shows the difference between presence and effect

In the default config pinned by this site, appearance.skin is ocean and default_scheme is system. The same file marks appearance.accent as deprecated and provides accent_light and accent_dark. The pinned README describes the built-in skins as ocean, jade, and violet, and the scheme choices as system, light, and dark. Its upgrade guidance says to remove the old global accent override; if custom colors are needed, set separate light and dark values and check contrast. The boundary is practical: an old key can remain syntactically valid YAML even after the theme stops reading it.

A narrow override could look like this:

appearance:
  skin: jade
  default_scheme: system

This expresses a preference for a palette and an initial mode. It does not verify that the colors work across every component. If you add custom accent colors, specify light and dark values separately, then inspect the places where they appear: links, buttons, secondary text, code line numbers, and any other visible controls. The built-in palette’s contrast check does not imply that an arbitrary custom color will also be readable. The old article’s recommendation to start with accent is a concrete example of how an option inventory can mislead when a theme changes.

Verification has three steps. First, confirm that the key exists in the defaults or documentation for the exact pinned theme version. Second, confirm that a higher-priority site setting does not override it. Third, regenerate the static site and inspect the relevant rendered attributes, color tokens, or visible styling. Saving YAML alone does not show that a template consumed the value. Conversely, if the generated page still shows the old color, check browser or static-asset caching before assuming that configuration parsing failed. Change one variable at a time so the cause remains observable.

Why can a module still be unavailable after its switch is on?

Midnight’s optional modules render only when their required configuration is present, but each module has different requirements. Search needs both search.enabled: true and a usable search.action; a true boolean without a destination does not make a search form capable of completing a query. The model-session panel needs model_session.enabled and model_session.endpoint. What the theme supplies is a browser-side interface, not a model proxy, authorization, rate limiting, or secret management. A provider API key belongs on the server, never in theme configuration that can be emitted to the browser.

The newsletter page has the same boundary. inner_pages.newsletter can configure a title, description, and form presentation, but without a real form.action the site has no endpoint that receives subscriptions. Rendering a form and securely accepting, storing, and allowing users to unsubscribe from email addresses are separate engineering tasks. Comments also require a provider choice—Giscus, Waline, or Utterances—and the repository, category, or service URL that provider needs. If required values are missing, the component may be hidden. Adjusting CSS will not repair a comment service that has not been connected.

Statistics are particularly easy to conflate. The integration guide treats site analytics scripts, per-article read/comment numbers, and footer page-view/unique-visitor counts as separate configurations. A site analytics report does not automatically become an article counter. Article numbers need a server endpoint that returns the documented data, and footer counters have a different source. If the site has no corresponding backend, it should not enable automatic counting or display guessed values. Verify the endpoint, the switch, and the frontend rendering condition together; do not turn “the boolean is true” into “counting is live.”

Why might a linked sitemap file still be missing?

The theme defaults include sitemap and feed settings. Those can control whether a template displays a link and which path it uses, but a sitemap link in the browser is not evidence that the destination returns valid XML. For a general Hexo site, the README recommends sitemap and feed generators; when Midnight’s language-directory structure is used, the theme also includes generation logic for those routes. Site structures and plugin combinations differ, so neither install every suggested plugin mechanically nor assume a theme switch can replace the generator.

For a sitemap, check more than _config.midnight.yml. The site’s own sitemap.path may override the theme path. Rebuild and confirm that the final public/sitemap.xml exists and contains the expected language-specific article URLs. If the template links to /sitemap.xml but the active generator emits the file elsewhere, the page can look correct while the submitted search-engine URL is missing. Apply the same test to actual feed output instead of inferring it from footer text.

A configuration-debugging walkthrough

Suppose a site enables search, but no search box appears on desktop or mobile. This is a hypothetical diagnostic example, not a configuration experiment performed on the live site. Start by confirming the installed version and its _config.yml entries for search.enabled and search.action. Then locate those paths in the site config and make sure that a higher-priority theme_config value has not disabled the feature or emptied its destination. Regenerate the site and inspect whether the rendered page contains a search form with the expected target URL. If the settings are correct but the template emits nothing, check whether Hexo is actually using midnight and whether the theme source matches the lockfile. If the form exists but queries fail, the fault has moved to the service behind action, not the CSS layer. Each check narrows the failure to configuration, generation, template conditions, or the service.

Order also reduces rework. Start with appearance and site identity because the generated page exposes those changes directly. Then confirm language directories, each post’s lang, and its translation_key. Connect comments, analytics, search, model services, or subscriptions only after their accounts and endpoints, cross-origin rules, privacy obligations, and failure behavior are ready. Finish by checking SEO output and the sitemap/feed files. A useful completion definition is not “the configuration was written”; it is that every enabled option has a corresponding generated artifact or reachable service, and that the site’s failure behavior is known.

Do not treat a configuration screenshot as acceptance evidence. The version identifies which keys belong to the code; configuration source and precedence identify which value wins; generated pages and service requests show whether a feature actually appears and works. Those are different questions and need different evidence. This rewrite checked the theme source pinned by this site and Hexo’s official configuration documentation. It did not run readers’ sites, nor measure palette, search, or backend behavior elsewhere. For the dependency-lockfile side of reproducible upgrades, see the review of npm audit remediation and release inputs; this article focuses on why a theme setting can disagree with expectations.
