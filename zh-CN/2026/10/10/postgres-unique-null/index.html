唯一约束存在，为什么还能保存两个空值？

PostgreSQL 19 默认把唯一约束中的 NULL 视为不同值；应按缺值的业务身份选择 NULLS NOT DISTINCT、非空约束或部分唯一索引。

正文

核心要点

  • 默认 UNIQUE 中多个 NULL 可并存；NULLS NOT DISTINCT 会把缺值纳入相等判断。
  • 复合唯一约束比较完整键组，任一可空分量都可能改变重复判定。
  • 预查改善提示，唯一索引处理并发；改规则前须盘点旧数据并验证迁移。

先问清“缺值”代表什么，再决定唯一约束如何比较它。PostgreSQL 19 的 UNIQUE 默认采用 NULLS DISTINCT：两个 NULL 不因这个字段而互相冲突；改用 NULLS NOT DISTINCT 后，多个 NULL 会按相同值处理。前一种适合许多彼此独立、尚未分配标识的记录，后一种适合“每个租户只能有一个缺省槽位”这类规则。本文的租户配置和外部编号都是假设示例；没有运行 SQL、迁移或并发测试。

NULL 表示缺席，不是一个共同的占位字符串

唯一约束回答的是“哪些行不能同时存在”，它不会替产品定义记录身份。外部系统尚未给客户分配编号，通常表示身份信息还未知。两位不同客户都没有编号，并不意味着他们是同一客户。把这种 NULL 当成同一个值，反而会阻止合法客户先建档、后补编号。

另一类数据表达不同的意思：每个租户最多有一份默认地区配置，地区字段为空表示“这个租户的缺省配置”，而不是某个未知的具体地区。此时同一租户出现第二份空地区配置，可能确实是重复身份。若所有缺省记录都可独立存在，默认语义更合适；若空值对应唯一业务槽位，才应把它纳入相等性规则。

这两个例子说明，不应先看到重复 NULL 就认定数据库出错。应先写下业务判定句：记录由哪些字段标识？字段缺席时，两个记录是否仍然可能是不同实体？“尚未知道”和“业务上只有一个默认项”必须用不同的模型表达。

约束文档（PostgreSQL 19）说明，UNIQUE 默认把 NULL 视为彼此不同；NULLS NOT DISTINCT 会改变这个比较方式。SQL 标准把唯一约束中的 NULL 处理留给实现，其他数据库的行为可能不同。PostgreSQL 官方公告标明该版本于 2026-11-19 发布；这篇旧稿最初以 18 为版本范围，18 的对应条款也可在PostgreSQL 18 约束文档核对。部署仍使用哪个主版本，应以运行环境为准，不能仅凭这篇更新推定。

复合唯一键看的是整组值

假设配置由“租户、地区、配置类型”共同标识，约束可以覆盖三个字段。“租户 A、华东、发票”重复是同一组非空键值，重复应被拒绝；而“租户 A、NULL、发票”在默认语义下包含一个与其他 NULL 不相等的分量，因此第二行可能继续写入。默认复合唯一不是“只要其他字段一样就唯一”，而是比较整组字段，NULL 会影响整组比较。

唯一索引文档（PostgreSQL 19）说，多列唯一索引只有在所有索引列都相等时才会拒绝重复；NULL 默认互相不相等。这个细节常被单列测试掩盖：只测试完整键的重复，无法证明带缺值的组合也符合业务约定。还要注意，PRIMARY KEY 不允许 NULL；它同时要求唯一和非空，因此不能直接替代“可暂时没有外部编号”的可空唯一列。

用规则矩阵选择约束

可以先把典型状态列出来，再挑选数据库机制。下表中的“租户默认项”仅是假设，不代表本站实际数据：

业务状态 两个缺值是否可同时存在 更接近的约束方向
客户等待外部系统分配编号 可以，不同客户尚无编号 可空的普通 UNIQUE；编号到达后阻止相同非空值
每租户只能有一个未指定地区的默认配置 不可以，同租户只有一个缺省槽位 租户范围的复合唯一，并考虑 NULLS NOT DISTINCT
字段对有效记录必须完整 不可以，因为缺值非法 NOT NULL 加 UNIQUE，或用主键语义表达真正标识
只有当前生效记录需要唯一 失效历史可重复，活动记录不能重复 对活动子集使用部分唯一索引

CREATE TABLE 语法（PostgreSQL 19）支持在列级或表级 UNIQUE 约束中声明 NULLS [NOT] DISTINCT。普通 UNIQUE 约束会自动创建用于执行规则的 B-tree 唯一索引；不要再手动创建同列的第二个唯一索引。若规则只覆盖满足条件的行，官方约束文档说明需用唯一部分索引表达，而不是普通表级 UNIQUE。选择机制前，先确认过滤条件和记录生命周期是否属于身份规则的一部分。

如果业务需要“空值唯一”，不要随手用空字符串代替 NULL。空字符串是一个具体文本值，数据库会把两个相同空字符串按普通唯一值比较；但用户输入、旧客户端和导入任务都可能实际传入空字符串。除非字段域明确禁止该字符串且所有入口统一处理，否则它会形成一个可能与真实值冲突的哨兵值。更清楚的设计通常是保留 NULL 的含义、添加明确状态字段，或将“默认项”单独建模。

应用预查不能处理并发竞争

应用可以先查询同一租户是否已经有一份空地区配置，用来提前显示易懂提示，但它不是完整约束。两个请求可能同时查询到“没有”，然后都尝试插入。索引唯一性检查文档（PostgreSQL 19）解释了机制：如果冲突行由尚未提交的事务写入，另一个插入会等待该事务结束；若前者提交且冲突行仍存在，后者得到唯一性冲突；若前者回滚，后者可重新检查并继续。数据库把最终检查放在索引插入路径上，正是为了避免只靠独立预查产生竞态。

因此，应用层和数据库各有职责。预查可以改善用户反馈，也可减少明显无效的写入；唯一索引则保证并发情况下不会留下违反规则的已提交状态。应用必须把特定约束冲突映射成可理解的业务回应，并避免将所有失败都盲目重试。若是两个客户争抢同一个外部编号，重试同一编号不会让它变得不同；如果冲突确实是暂时锁定或事务结果待定，则应按实际错误和事务状态决定是否重试。

修改已有表前先盘点旧数据

从默认语义切到 NULLS NOT DISTINCT，并不只是改一段 DDL。原来允许的多行 NULL 可能马上成为不合法数据；新约束不能在这些冲突仍存在时被安全接受。迁移前应分开统计 NULL、空字符串、只含空格的输入，以及按业务规范化后可能重复的值。大小写、首尾空格、Unicode 归一化是否影响身份，都需要产品和数据所有者定规则，不能让唯一约束替大家猜。

盘点结果也不等于自动清理许可。两个空值行可能代表不同待配置对象，也可能是重复默认项；只有业务确认它们的关系后，才能合并、补值或保留。若有旧客户端仍会写入空字符串，而新版开始写 NULL，先确定兼容期间的写入规范，再启用约束。否则同一业务含义会分散在两个数据库表示中，后续查询和冲突处理都更难解释。

对于大型表，创建或替换索引的锁和失败恢复方案要结合 PostgreSQL 主版本、表规模、写入负载和部署工具核验。本文不提供未经验证的在线迁移命令，也没有执行迁移。可以把流程拆成只读盘点、数据所有者决策、写入路径兼容、清理冲突、建立约束、回读验证几个可回滚步骤；每一步记录目标规则和观测结果，并准备在冲突未解决时停止，而不是在部署窗口里临时删数据。

验收不止测两个非空重复值

改规则前，测试表应体现产品契约，而不是仅把语法跑通。对外部编号场景，确认同一非空编号第二次写入会失败、不同租户是否能各自使用相同编号符合范围、多个未分配编号允许存在、补上编号后冲突有明确反馈。对“每租户一个默认配置”场景，确认首个 NULL 可写入、第二个同租户 NULL 被拒绝、不同租户可分别有一个默认项；若地区与配置类型共同组成身份，还需覆盖同租户不同类型、不同地区以及部分字段为空的组合。

另需测试空字符串与 NULL 的转换规则、更新时把已分配编号清空的行为、历史重复数据的迁移处置，以及两个并发请求同时创建默认项的结果。并发测试要检查最终数据库行数和应用对失败的映射，而非仅断言一个请求返回错误。本文列出的都是待执行验收条件，没有 SQL 成功记录，也没有声称某个索引或迁移在生产环境通过。

读者常问：“复合唯一键里只要有一个 NULL，是不是后续行都能重复？”应拆开字段看：默认 NULLS DISTINCT 下，只要至少一个对应位置是 NULL，两组键就不会在所有列上完全相等，因而可出现多行；但相同的非空完整组合仍然冲突。切到 NULLS NOT DISTINCT 后，空值位置也参与相等判断，冲突范围随之改变。若只想约束一部分行，则还要考虑谓词，而不是只改 NULL 规则。

最后的选择顺序是：定义身份范围，定义缺值业务含义，写出可接受与拒绝的具体行组合，再选普通 UNIQUE、NULLS NOT DISTINCT、NOT NULL/主键或部分唯一索引。对每一租户可有多个未知编号的表，NULL 通常应保留“还不知道”的独立性；对每租户只有一个缺省槽位的表，NULL 才可能需要按相同状态处理。并发、迁移和旧客户端兼容都要单独验证。若冲突来自真正并发写入，可参考事务冲突与重试边界；它不能替业务决定哪些空值算同一个身份。
