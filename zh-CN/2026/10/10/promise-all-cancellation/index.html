Promise.all 已经失败，其他请求为什么还在执行？

Promise.all 首个拒绝只结束聚合承诺，不会停止输入任务；用 AbortController 请求可取消读取，写操作则要按幂等键和业务状态处理。

正文

核心要点

  • 聚合承诺拒绝不等于输入任务停止；任务可能已经启动，业务副作用也可能已经发生。
  • AbortController 只向支持 signal 的 API 请求取消；allSettled 负责等结果，Promise.race 只负责决定先返回哪一个结果。
  • 写操作要通过稳定操作身份、幂等重放、状态查询、事务或受限补偿收口，网络中断不证明对端未执行。

Promise.all 拒绝的是聚合结果，不会替输入任务发出取消信号；已经启动的请求仍可能继续，除非底层 API 支持取消并且调用方主动请求。这个区别不只是界面表现：并行保存时，错误分支可能早于其他操作完成，用户随后重试就可能重复提交已经成功的写入。本文用假设的批量保存解释任务生命期、合作式取消和业务恢复之间的边界；代码示例没有在浏览器、Node.js 或数据库中运行。

聚合承诺的失败不等于输入任务停止

Promise.all(iterable) 返回一个新的聚合承诺。只要某个输入承诺拒绝，聚合结果就以第一个拒绝原因为拒绝状态。其余输入的处理器仍附着在这些承诺上，底层操作也仍按自己的实现执行。MDN 明确说明，拒绝聚合结果不会取消其他操作，也不会移除已经安装的处理器；ECMAScript 规范描述的是结果承诺如何解决或拒绝，没有为任意任务定义通用取消协议。

因此，要把三个层次分开：一是 Promise.all 自己何时兑现或拒绝；二是输入工作何时真正结束；三是外部副作用是否已经发生。第一个层次的状态不能推断后两个层次。拒绝只告诉调用者“完整结果数组不会交付”，并不意味着网络请求、定时任务、文件读取或远端写入回到了开始前的状态。对于后续发生的拒绝，Promise.all 已经给输入承诺安装了处理器；不能把聚合之外仍有工作，简单等同于每个晚到拒绝都会触发 unhandledrejection。

MDN 的 Promise.all 参考明确区分 fail-fast 结果与底层操作，并说明 allSettled 会等待所有输入结束；ECMAScript 2025 的 Promise.all 规范定义了聚合值的兑现和首个拒绝原因。这些来源规范的是承诺结果，不是数据库事务或任意 API 的取消能力。

任务也常在进入聚合器之前就启动。例如，items.map(item => save(item)) 会立即调用每个 save。随后把得到的承诺数组传给 Promise.all，只是开始等待这些已经创建的工作，并没有建立一条可以逐项停止的任务队列。若启动成本需要限制，输入应该是任务工厂，由单独的调度器按并发预算逐个启动；并发数量取决于下游限流、超时和资源预算，不能从 Promise.all 推导一个通用最佳值。

用一次三项保存推演“失败”发生了什么

下面是解释状态的假设场景，不是一次真实测试。页面准备保存三份配置，分别用稳定操作键 save-a、save-b、save-c 标识；服务端允许单项成功，不提供批次事务。时间线可能是：请求 A 已在服务端提交，但响应在回程中丢失；请求 B 因校验失败而返回错误；请求 C 仍在等待处理。B 的拒绝让 Promise.all 很快拒绝，界面进入错误分支时，A 的真实状态仍未知，C 也未必停止。

若界面只把批次标为“全部失败”，用户点击重试时便可能再次写入 A。若服务端没有幂等身份或唯一约束，重复操作可能创建重复对象；若保存的是覆盖式配置，第二次请求也可能覆盖首次保存后的合法修改。即使将相同请求立刻取消，取消信号抵达前 A 也可能已经提交。浏览器放弃等待不等于服务端回滚，网络断开尤其不能证明对端没有执行。

在这种业务里，界面需要表达的是每个对象的已确认状态，而不是只有一个布尔值。A 应显示“结果待确认”，并通过相同操作键查询状态；B 显示校验失败并等待输入修正；C 根据实际取消能力显示“取消请求中”或继续等待。只有服务端明确返回未提交，或操作协议保证同一幂等键重放安全时，才适合直接重试。若业务要求三项要么全成、要么全不成，应把原子性放在服务端事务或明确的批次状态协议内实现，而不是把多个 HTTP 请求并发起来后期待前端聚合器提供事务。

AbortController 是协作信号，不是 Promise 的取消按钮

对搜索建议、预览等可丢弃读取，调用方可以创建 AbortController，把同一个 signal 传给每个支持该选项的 fetch。一项输入失败后，在错误分支调用 abort()，可以请求仍在进行的 fetch 结束。官方示例正是用这个方式清理 Promise.all 失败时的其余读取。它依赖底层操作明确接受并遵守 signal；一个普通 Promise、CPU 密集循环或不检查信号的自定义任务不会因为收到 abort() 就自动中断。

MDN 的资源管理指南给出共享 AbortController 信号的示例；Fetch API 指南说明 abort() 会让相应的 fetch 以 AbortError 拒绝。它们演示的是支持信号的读取操作，不保证对端回滚任何写入。

下面是教学用的未执行伪例，省略了调用方取消、超时和请求策略。需要将 URL 检查、错误类型以及控制器作用域按项目调整：

async function fetchEveryPage(urls) {
  const controller = new AbortController();
  try {
    return await Promise.all(urls.map(async (url) => {
      const response = await fetch(url, { signal: controller.signal });
      if (!response.ok) {
        throw new Error(`HTTP ${response.status}`);
      }
      return response.json();
    }));
  } catch (error) {
    controller.abort();
    throw error;
  }
}

这里的 catch 请求停止兄弟 fetch，但它不能保证远端服务器中止已经开始的计算，更不能撤销已提交的写入。MDN 还指出，fetch 收到响应头后就可能已经兑现；若此时才取消、正文尚未读完，读取正文仍可能以 AbortError 拒绝。另一个容易误判的边界是 HTTP 404：Fetch 通常会兑现一个 Response，需要检查 ok 或 status 后主动决定是否抛错。只有明确检查响应状态，Promise.all 才会把业务定义的 HTTP 失败当成拒绝输入。

取消策略还可能和页面生命周期或批次截止时间合并。Node.js 当前文档把 AbortController 说明为供选定 Promise API 使用的信号机制，并记录它在 Node 15.0.0、14.17.0 加入；AbortSignal.any 的 Node 版本记录是 20.3.0、18.17.0。使用这些静态方法前要核对实际浏览器和 Node 运行版本。不同来源的信号被合并，也不意味着不支持 signal 的任务会停止。

版本记录来自 Node.js Global objects 文档；本文只引用其版本历史来提醒运行环境兼容性，没有据此声称每个被 Node 托管的异步 API 都支持取消。

allSettled、超时和并发队列解决的是不同问题

如果批次允许部分成功，而且用户确实需要知道每个输入的最终结果，Promise.allSettled 会等待所有输入兑现或拒绝，并按输入位置返回状态快照。它适合收集结果，不会取消仍运行的工作、重试失败项或回滚已经成功的项。若某个输入永远不结束，整个 allSettled 也会一直等；这时应设计每项任务的截止时间、可取消接口和“状态未知”的报告方式，而不是无条件等待。

用 Promise.race([work, timeout]) 让界面先显示超时，也只决定哪个承诺先决定竞赛结果，不能自动取消 work。如果真实目标是停止可取消的底层操作，应让超时处理器调用该操作的控制器；如果目标只是停止等待，就要继续负责处理迟到的完成或拒绝，避免它们再次修改已经过期的 UI 状态。如何让过期查询不覆盖新查询，可参照取消请求与过期结果；如何让重试不重复副作用，可参照API 重试与幂等键。

若输入规模大，传入承诺数组意味着所有映射调用可能同时启动。受限队列应接收类似 task(signal) 的函数，而不是已经运行的 Promise：调度器在容量允许时启动下一项，取消后不再启动尚未运行的项，并给正在运行且支持 signal 的项发送停止请求。还要定义排队任务、运行任务和已完成任务在取消瞬间的各自状态。限流不能替代幂等与服务端容量控制；任务创建过程也可能抛出同步异常，调度器应保证已启动任务可被跟踪和收敛。

写操作要靠业务状态收口

对写入类请求，恢复流程不能只依赖 Promise 的异常对象。一个可审查的协议通常需要稳定的操作身份、可查询的终态、幂等重放规则和有界等待。客户端遇到连接中断时，先查询相同操作键；如果状态仍未知，保持待确认，不要创建一个身份不同的新写入。只有确认该业务操作未发生，或服务端规定相同身份的重复请求安全时，才继续重试。批次原子性需要事务或服务端协调；补偿操作则必须检查当前版本或所有权，避免把更新过的对象写回旧值。

验证计划应分别覆盖：第一个输入拒绝、另一个输入延迟完成、多个输入依次拒绝；响应头已到但正文未读时取消；HTTP 错误状态但网络请求本身成功；父页面取消和批次超时同时发生；写入提交后响应丢失并以相同幂等身份重试。还应确认 UI 不会在已切换页面后被迟到结果覆盖，并审计取消异常是否被当成普通业务失败。本文没有执行这些测试或发出任何网络请求，代码也没有成功运行日志。

因此，选择 API 前先回答两个问题：需要的是完整结果、尽早失败，还是停止不再需要的读取？每个输入会不会在外部留下副作用？Promise.all 负责汇总成功值与第一个拒绝；allSettled 负责等齐状态；AbortController 向支持信号的操作提出取消请求；队列控制尚未开始的工作；事务、幂等与状态查询才处理写入的业务恢复。把这些职责写清，才能让“失败”既不掩盖仍在运行的工作，也不把未确认的副作用误报成已回滚。
