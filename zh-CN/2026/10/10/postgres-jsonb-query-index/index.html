JSONB 有 GIN 索引，为什么键存在查询仍可能用不上？

PostgreSQL 18 的 JSONB 索引选择需核对操作符类、表达式和业务查询，不能把更小的索引当成覆盖全部请求的保证。

正文

JSONB 列上存在 GIN 索引，并不意味着所有针对这个文档的查询都能用同一种索引路径。应先核对操作符类、被索引的表达式与实际查询形状，再讨论大小和速度。本文使用 PostgreSQL 十八版文档解释选择，没有创建索引、运行执行计划或测量收益。

操作符类决定支持的查询范围

PostgreSQL JSON 类型文档说明，非默认的 jsonb_path_ops 支持包含和指定的路径查询操作符，但不支持键存在操作符；默认 jsonb_ops 支持的操作符范围不同。原文也讨论不同索引项的组织方式。本篇不把“通常更小”的描述改写成任何数据集都更快的承诺。

假设客服系统把扩展属性放在 JSONB 中，查询“含有某种标签值”与“是否存在某个键”是两个不同问题。团队为第一种请求选了路径操作符类，随后第二种请求上线，并不能只凭索引名字一样就断定它受到覆盖。先把业务过滤条件翻译成真实数据库操作符，再与索引定义逐项比较，比看到列类型就添加一个通用索引更可靠。

表达式也有边界。索引建在整个文档上，而查询先取出某个子对象再判断，是否匹配所建索引需要结合表达式与计划核对。不能把一段应用代码中的“查标签”当成所有 SQL 都有相同形状。不同 ORM 或条件拼装分支可能生成不同表达式，应保存实际发出的查询，而不只保存开发者预想的语句。

先列查询，再决定保留哪些灵活性

可以按读者真正需要的问题整理查询清单：固定字段等值、键存在、嵌套包含，以及结构缺值时的行为。这里只提出分类方法，没有执行这些查询。固定且频繁的业务属性是否适合独立列，也值得讨论；采用 JSONB 不等于禁止列建模，改成列也不自动解决所有数据演进问题。

索引带来写入和存储责任。为每一种临时查询都加索引，可能使更新成本和维护复杂度增加；只留一个最小索引，又可能无法支持关键后台任务。取舍应结合真实频率、过滤选择性和服务时限，不应由索引体积一个数值决定。对很少运行但重要的审计查询，允许较长等待还是提供专门导出，需要业务确认。

文档还指出，路径操作符类对没有值的某些 JSON 结构不会产生相应索引项，包含此类结构的查找可能需要较广扫描。因此数据中“空对象”不是可以从样本里随意删除的噪声。缺键、空对象、空数组和空值可能代表不同业务状态，验收用例应保留这种差别，否则索引评估与真实请求范围不一致。

验证选择，不编造速度

建议先在代表性测试数据上保存索引定义、查询参数和执行计划，确认条件如何进入索引路径，再测量读取与更新的资源成本。规划估算和实际执行结果应分开；实际执行可能产生负载，需要适合环境的安全安排。相关方法见执行计划中的估算证据。

本文没有运行上述评估。上线评审应能回答：这个操作符类为哪些查询服务，哪些查询明确不覆盖，数据结构变化以后谁检查计划。如果只能回答“JSONB 已经有索引”，查询契约仍然没有得到验证。
