CSP 报告为零，不等于可以阻断：上线前要验证三件事

零违规报告不能证明强制 CSP 已就绪。先验证响应头、报告采集链路和关键任务覆盖，再小范围阻断并保留回退。

正文

CSP 报告为零，不能单独作为开启强制阻断的依据。它可能表示当前被覆盖的请求没有违反候选策略，也可能是关键页面没有被真实走过，或报告没有送达、被接收端丢弃。切换前应分别证明策略确实到达目标响应、受控报告信号能走完采集链路、关键用户任务在代表性环境下经过验证；之后再按可回退的小范围启用强制策略。

本文给出的后台管理流程是假设示例，不代表本站配置了 CSP，也不是实际浏览器测试或生产部署记录。

“没有报告”究竟证明了什么？

Content-Security-Policy-Report-Only 让浏览器解析并监测一份策略，但不会按照这份策略阻断请求。W3C 在 2026 年 10 月 27 日发布的 CSP Level 3 仍是 Working Draft；其中明确区分强制响应头和仅报告响应头，并说明开发者可以观察违规，再在获得信心后转向强制模式。草案也指出，Report-Only 是响应头机制，不能通过 <meta> 元素交付。它是工作中的规范草案，不应被描述为已定稿的 Recommendation。(W3C CSP Level 3，2026-10-27 Working Draft)

因此，空白报告列表最多描述了“当前采集界面没有展示事件”。它没有自动回答三件事：候选头是否发给了真实页面，浏览器是否成功产生并投递报告，测试期间是否走过会触发候选策略的请求。把三者混在一起，很容易把“监控没有声音”误读成“策略没有问题”。

报告传输还有一个容易被低估的边界：W3C Reporting API 将投递描述为尽力而为，并明确说明没有送达保证。网络条件可能让报告到不了端点；用户代理也可以因自己的原因拒绝或不投递。成功收到一次受控测试报告，可以证明某条链路在那次测试中可用，却不能证明之后每一条生产报告都会完整到达。(W3C Reporting API，2025-06-11 Working Draft，§1.1)

浏览器接收的指令和端点配置也必须对应。MDN 的 CSP 实践指南建议先用 Report-Only 测试策略；指南最后修改于 2026 年 9 月 4 日。它说明可以通过 report-to 与 Reporting-Endpoints 配置新报告路径，同时保留旧的 report-uri 以兼顾浏览器支持；MDN 将后者标为弃用，但也提醒 report-to 尚未获得完整的跨浏览器支持。不要把“新指令更推荐”误解成“你所有目标浏览器都用同一条路径”。(MDN：CSP practical implementation guide，2026-09-04 更新)

如果站点同时已有一份强制策略和一份新的 Report-Only 候选，二者承担不同职责：旧的强制策略仍可能阻止它不允许的请求，候选策略则报告自己会拒绝的请求。多份强制 CSP 也不是“后写覆盖先写”；请求需要满足每份强制策略。上线记录应写清浏览器收到的每一份头，而不能只记录配置仓库里的最终文本。关于这种交集语义，可参见站内的多份 CSP 强制策略如何共同生效。

第一道门：候选策略是否到达了目标响应？

先不要从报告计数开始。先把候选策略当作一个有版本号的发布物：保存完整头值、变更编号或内容哈希、预期覆盖的路由、所有者和回退版本。然后从实际页面响应取证，而不是仅检查 CDN 配置文件或应用仓库。一个站点可能由应用、反向代理、边缘规则和缓存共同生成响应头；同一路径的登录前后、不同语言、不同缓存状态也可能有不同结果。

假设一个后台有登录页、报表页和富文本编辑页。测试矩阵至少要写出对应 URL、身份状态、关键动作、预期策略版本和浏览器版本。匿名访问 /admin/editor 可能被重定向到登录页，实际策略头就来自登录响应；登录后编辑器又可能由另一条缓存路径返回。如果只在首页看到候选头，不能推断这些后续文档也带着同一策略。

要检查的不是“页面来源相同”，而是各类响应是否真的携带预期策略。对每个响应保存状态码、最终 URL、强制 CSP 头、Report-Only 头、Reporting-Endpoints 头及策略版本标识。确认缓存命中和未命中都符合预期；如果不同页面有意使用不同策略，把差异写进矩阵。Report-Only 若被放进 meta 标签，不会完成这道验证，因为标准不支持这种交付方式。

这一阶段可能立刻揭示空白面板背后的问题：某条边缘规则漏配头，代理只转发强制头而未转发报告端点，或页面版本不同步。只要头没有按预计到达目标响应，后面的“零报告”就没有资格作为策略证据。先修正发行路径，再继续观察；不必先把所有策略放宽或把所有来源加入允许列表。

第二道门：受控违规能否走完报告链？

用一个隔离的测试页面和团队控制的测试资源制造可预测、无害的候选策略违规。例如，页面加载一张由团队测试域名提供的静态图，而 Report-Only 候选的 img-src 不包含该域名。因为策略仅报告，这个请求不应被候选策略阻断；测试也不需要注入脚本或有害内容。测试环境必须先确认没有另一份强制策略已经阻止同一请求，否则你可能只看到现有策略的拦截。

接下来核对从配置到落库的每个环节：页面响应包含候选策略和正确的报告端点名称；端点名称在策略里的引用与 Reporting-Endpoints 定义一致；浏览器产生的事件抵达接收端；接收端接受请求后，解析、队列或存储流程能在可查询界面找到这条测试事件。测试表应记录策略版本、测试浏览器、页面路径、事件时间、端点响应及最终查询位置。本文没有为读者运行该测试，因此没有伪造一条“成功日志”或固定的 HTTP 状态要求。

Reporting API 的发送可能在页面操作之后异步发生，测试不应以“点击后立刻看见记录”为唯一标准。判断链路是否接通，要看端到端证据：浏览器产生预期信号，接收端记录到原始事件，聚合层没有因字段变化、限流或过滤而丢弃它，负责排查的人能用策略版本和路由定位它。若供应商仪表板只显示按域名聚合的计数，还应确认原始事件是否保留了足够的有效指令、处置方式和页面上下文；同时按隐私要求处理 URL、用户代理和其他可能敏感的报告字段。

采集链路的反例比“端点宕机”更常见地隐藏在配置差异里：响应头引用 csp-endpoint，端点列表却定义了另一个名字；报告请求能到 API，却在 JSON 校验或队列写入阶段被静默丢弃；新旧 Reporting 机制只接通了一种浏览器；或者缓存节点仍在返回旧头。只在应用代码中搜索 report-to 无法排除这些故障。每次变更都应由测试事件暴露实际响应，而不是由配置文本推测实际行为。

如果控制信号没有到达最终查询位置，结论应是“报告链路尚未验证”，而不是“没有违规”。修复后再次发出受控信号，并按实际目标浏览器分别记录。一次测试通过的边界也要写清：它证明某个浏览器、页面响应和当时端点能够互通，不证明所有真实设备、网络和用户会话都投递成功。W3C 对该服务的尽力而为说明，决定了报告不能成为唯一的安全验收通道。

第三道门：被覆盖的是关键任务，而不只是首页

策略无违规与业务无故障不是同一件事。未访问的编辑器不会生成违规；只完成首页加载，也不会覆盖登录跳转、上传、导出、支付确认、管理操作或会话过期后的重新认证。应从用户任务而非站点 URL 数量出发，列出关键身份、状态和交互，再标注每项会触发的脚本、样式、图片、连接、工作线程或导航来源。

假设报表页的导出动作会先请求一个同源 API，再由该 API 返回下载文件；编辑器则从合作方域加载脚本，并启动一个 worker。仅打开页面可以覆盖初始 HTML 和部分脚本加载，却可能没有触发导出请求，也没有初始化 worker。若候选策略收紧 connect-src 或 worker-src，这两项任务才会暴露差异。验证记录应指出在哪个用户动作中观察了哪些请求，以及页面最终完成了什么，而不是只记“已访问页面”。

优先级可以同时看失败影响和发生可能性，但低频不等于可忽略。后台登录失败与装饰性图片缺失的代价不同；一个很少使用的财务导出可能仍属于关键任务。对每项流程定义任务完成证据，例如用户到达正确页面、数据加载完整、文件下载正确或保存操作确实完成。候选 CSP 的违规报告帮助发现策略差异，任务结果则判断差异是否会造成业务损坏。

报告中还可能出现浏览器扩展、代理改写和站点之外的来源。它们既不必然意味着恶意攻击，也不应自动转换成允许来源。先用 document-uri、有效指令、阻断目标、浏览器类型和请求发生的业务上下文区分：是应用自身依赖、经过批准的第三方服务、扩展注入，还是暂时无法解释的来源。未解释且涉及关键任务的首方请求应保留为阻断项；不清楚来源时，把域名直接加进通用策略只会把不确定性永久保存下来。

覆盖矩阵要明确它能代表哪些真实条件。可以按浏览器家族和团队支持的版本、用户身份、地区或网络、缓存状态和应用版本分组；每组记录已执行的任务与未覆盖路径。Chrome for Developers 对 Reporting API 给出的支持表显示，CSP 报告的新 report-to/Reporting-Endpoints 路径与旧 report-uri 路径并不等价，且不同浏览器的支持情况有差异。该表针对其文档描述的接口，不替代项目自己的目标浏览器和版本核查。(Chrome for Developers：Reporting API 的支持与配置说明)

通过观察后，也要在受控范围内验证阻断

三道观察门都通过，代表你有理由进入强制模式的试验，不代表所有路由、客户网络和设备都已被证明安全。先选定一个风险可控的页面或稳定用户分组，记录它会收到哪个候选策略版本、谁观察任务结果、如何识别与候选策略相关的失败，以及何种条件触发暂停或回退。具体范围由部署能力和业务影响决定；不存在适用于每个站点的统一流量百分比或固定观察天数。

假设管理后台有独立的报表编辑入口，团队可以先让受控账号走新版强制头，同时保持其他用户使用已知策略。部署系统若不支持按账号分流，也可以用低风险路由作为阶段，但要验证依赖是否跨路由共享；共享脚本或 API 不一定受页面路由隔离。无论怎么分批，都要使用稳定的策略版本和明确的响应头读数，避免把“配置已发布”误当成“测试账号收到新策略”。

强制阶段继续观察用户任务和浏览器的 CSP 事件，而不是期待报告计数归零。请求被真正阻断后，业务错误、任务完成率、客户端日志和安全报告各自提供不同证据。若登录或保存失败与候选策略对应的有效指令吻合，应暂停扩展范围，并恢复预先保存的已知策略；如果失败来自其他因素，也要先查明，不能把所有错误都归因于 CSP。回退方案要能重新发出准确的旧头，同时核对缓存传播，否则回退配置存在并不代表用户已经恢复。

这里要区分两种策略失败：候选策略报告了尚未处理的首方资源，说明观察阶段还有工作；强制策略让关键任务失败，说明试验范围或策略本身需要回退。二者都不应靠增加 *、https: 或 unsafe-inline 一类宽泛授权“消警”。若候选策略使用 nonce，头和页面脚本中的值还必须按响应正确配对；相关边界可参阅站内的CSP nonce 与响应缓存范围。

变更评审应该留下哪些证据？

把“等了几天、没有收到报告”换成一张能复核的记录：候选策略原文及哈希；它在哪些响应和缓存变体中被看见；使用什么受控资源发出预期信号；接收端和聚合界面在哪里确认事件；哪些浏览器版本、身份状态和关键任务已经覆盖；仍有哪些用户路径或第三方依赖未知；第一批强制执行的范围与回退条件是什么。每个空项都应标成未知、未执行或阻断，而不是填成通过。

因此，零报告可以与“准备进入下一阶段”同时成立，但只能在报告链路和业务覆盖已经独立验证后作为补充证据；它本身不是放行条件。实施分阶段上线前，可用按失败影响设计质量门禁检查验证范围是否覆盖关键后果，并参考如何证明部署有效且回滚可用保存策略版本、实际响应和回退结果。评审单应写下具体证据与剩余盲区，再决定谁、在哪个范围内启用强制策略。
