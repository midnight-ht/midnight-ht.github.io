翻页有重复：LIMIT 之外还要约定什么？

PostgreSQL 18 的 LIMIT 需要唯一排序；游标减少位置漂移，但稳定数据导出仍需额外定义快照和可变排序字段。

正文

核心要点

  • LIMIT 之前先核对排序键组合是否唯一；否则同值行没有稳定边界。
  • 游标记录排序边界，不能固定并发写入后的数据集合。
  • 交互列表、短事务报告与长时间导出应按一致性承诺选择不同策略。

先把单页查询排成唯一顺序，再决定用户翻到下一页时允许哪些并发变化进入结果。LIMIT 只限制返回行数；它不会为行分配永久位置。游标分页能把“跳过多少行”改成“从哪个排序边界继续”，但也不会自动固定多次请求看到的数据。下面用假设的订单列表解释这些承诺；SQL 只是教学示意，没有在数据库中执行，也没有性能测量。

排序值相同，LIMIT 仍不知道哪一行在前

PostgreSQL 18 的 LIMIT 与 OFFSET 文档明确建议让 ORDER BY 形成唯一顺序。否则，不同 LIMIT/OFFSET 可能对应不同执行计划和不同子集。比如订单按 created_at DESC 排序，同一批导入记录可能具有相同时间。若页面边界刚好落在这组记录中间，数据库没有理由保证它们每次都以同一相对顺序出现。

可以增加一个稳定且唯一的并列键，例如订单主键：ORDER BY created_at DESC, id DESC。它的职责是区分相同时间的行，不是证明较大的 ID 在业务上一定更晚。若业务排序还包含优先级、名称或金额，也要把所有会影响先后关系的排序项纳入边界定义。只有完整排序键组合确实唯一，才能称为总序；只在末尾随手加一个字段，若该字段不唯一，问题仍在。

NULL 也会改变边界。排序项可以明确写 NULLS FIRST 或 NULLS LAST，但游标比较不能把 NULL 当普通值直接比较：SQL 三值逻辑会让涉及 NULL 的比较得到未知。更稳妥的接口可把空值行分为独立区段，或在排序和游标编码中加入显式的空值标志，并为每一段定义后续条件。不要让应用按一个顺序编码游标，数据库却按另一个默认空值顺序排序。

OFFSET 记录的是位置，插入会推开位置

假设每页 20 条，第一页读完后新订单插入到当前排序最前方。第二次请求 OFFSET 20 会从新结果集的第 21 行开始；原来第一页末尾附近的行可能被再次返回。若第一页之前的订单被删除，后续行向前移动，则一条原本应属于第二页的记录可能被跳过。即使 ORDER BY 完全唯一，两个请求针对的仍是不同集合。

因此排查“偶尔重复”时，应同时保存过滤条件、排序项、页大小、offset/cursor 和请求间发生的写入。只记录某次 SQL 和返回行数，无法重现边界移动。手册还指出，大 OFFSET 被跳过的行仍需由服务端计算；这是需要在实际数据和计划中检查的成本线索，不是任何固定数据规模下的延迟结论。

游标固定边界，不冻结数据集

对于非空、不可变的 created_at 加唯一 id，降序 keyset 查询可以把上一页最后一行的两个值带入下一页：

WHERE created_at < $cursor_time
   OR (created_at = $cursor_time AND id < $cursor_id)
ORDER BY created_at DESC, id DESC
LIMIT $page_size;

这段 SQL 是说明边界关系的草图，未经执行；它假设两列非 NULL、过滤条件相同、排序方向固定，并且创建时间不会被回填修改。比较运算符必须与排序方向一致。若把 id 方向改成升序，等值时间分支中的比较也要随之改变。

Keyset 避免了新行只因排在前面就令“跳过 N 行”的位置整体后移，但边界两侧仍有变化路径：新插入且排序值落在游标之后的行可能出现在后续页；落在已经走过的区间则不会被回看。已返回行若因可变排序字段移动到游标之后，可能再次出现；若另一行移动到游标之前，则可能永远赶不上。删除则让该记录从后续结果中消失。一个仅包含排序值的游标不是数据库快照，也不是授权令牌；服务端仍需按当前用户校验过滤范围，并考虑签名、过期和字段版本。

若排序字段可变，先问读者需要哪种保证。实时工作台往往更关心继续查看当前队列，可以接受插入或状态变化造成的集合更新；审计清单需要的是可重复核对的固定成员集合，单靠游标不够。用 updated_at 排序时，订单状态变更会移动行；可以改用不可变创建时间来保持浏览位置，但这不代表状态内容也被冻结。

一次事务的快照不能跨越任意浏览会话

PostgreSQL 18 的 事务隔离说明指出，默认 Read Committed 下，每条命令取得该命令开始时的快照；连续两个 SELECT 可以看到不同事务提交的变化。Repeatable Read 则让同一事务中的语句看到事务快照。它能解释为什么一段短事务中的多次分页查询可以读取同一视图，但它的边界是数据库事务，不是用户在数分钟后重新发来的 HTTP 请求。

把一个事务和连接一直留给浏览器分页，意味着应用必须管理连接占用、断线恢复、事务超时和客户端离开等情况。另一条路是 PostgreSQL 的游标：普通游标依赖当前事务；WITH HOLD 游标可以在同一数据库 session 中跨过提交继续取数，但官方 DECLARE 文档说明，当前实现会把 held cursor 表示的行复制到临时文件或内存区域。它不是把无状态游标字符串交给任意应用实例就能继续的接口。

对范围有限、必须同一视图的报告，可在服务端短时间内启动 Repeatable Read 事务并完成导出，但需要设定最大行数、超时和失败重试规则。对用户可能停留很久的大型导出，更常见的产品边界是创建异步导出任务：记录任务条件，在固定时点物化目标 ID 或生成文件，返回任务状态与下载链接。冻结 ID 只固定成员，不冻结之后读取的字段值；若字段值也必须与同一时点一致，需要物化所需字段或使用明确的快照策略。导出结果应标记生成时点、筛选条件和过期时间，不能把它伪装成实时分页。

验收要同时覆盖排序和变化策略

可以为假设订单列表写出以下未执行的测试方案，并按产品语义判定结果，而不是默认所有变化都算缺陷：

场景 要固定的约定 检查重点
多行 created_at 相同 id 作为唯一 tie-breaker 连续读取时相同行的顺序一致
两页之间前置插入 OFFSET 或 keyset 的读者语义 OFFSET 是否重复；keyset 是否接受新成员落入后页
两页之间删除 是否要求固定成员集 删除行后其他行的边界是否符合承诺
排序字段被修改 字段不可变，或允许行移动 重复与遗漏是否在接口契约允许范围内
筛选条件变化 游标绑定筛选条件 更换状态筛选后旧游标是否被拒绝或重置
NULL 排序值 明确 NULL 区段和方向 游标是否能从空值段正确继续
稳定导出重试 固定 ID 或物化文件 重试是否继续同一批成员、同一版本

具体查询计划和深页成本要用真实数据验证，可参照EXPLAIN 证据指南。隔离级别、重试边界与事务失败的关系可继续看PostgreSQL 隔离与重试。本文没有运行这些测试；上线前应把产品承诺落实为集成测试，并确认所选索引覆盖完整排序键。

决策顺序很简单：先定义总排序，再选页边界，最后写明跨请求允许的变化。普通浏览可以接受变化时，唯一排序加 keyset 通常是清晰的接口设计；若读者需要可重现的同一份导出，则另建短事务或异步物化方案。游标解决的是“从哪里接着读”，不是“这几页永远代表同一批数据”。
