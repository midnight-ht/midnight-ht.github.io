用了 Docker secret mount，镜像里就绝不会泄露密钥吗？

Docker 构建密钥挂载保护输入通道，仍需审查命令输出、生成文件、镜像层和缓存，防止进程主动复制秘密。

正文

用了 Docker secret mount，仍需要检查构建命令会把秘密写到哪里。挂载解决的是构建时如何提供凭据，不会自动审查进程输出、生成文件或最终复制内容。本文讨论私有依赖下载的假设流程，没有构建镜像、扫描缓存或证明某个镜像不存在密钥。

输入通道与输出内容是两件事

Docker 构建秘密文档说明构建参数和环境变量不适合传递秘密，建议使用秘密挂载或 SSH 挂载；秘密可在构建步骤中以文件或环境方式提供。这里讨论当前 Build 文档的机制，具体功能需要按实际构建器和语法版本核对，不把全部环境变量都说成没有风险。

假设包管理器读取临时凭据下载内部依赖。如果命令把认证配置复制到输出目录，后续再把目录打进镜像，秘密就沿普通文件路径进入产物。挂载本身按预期结束，也不能撤销程序主动生成的副本。同样，打开调试输出、打印请求头或完整配置，可能把凭据送进构建日志，风险并不局限于镜像层。

因此评审应沿数据路径走：凭据从哪里进入，哪个命令读取，命令生成哪些文件，哪些目录被复制，以及日志送到哪里。不要只搜索 Dockerfile 是否出现敏感字符串；构建上下文、依赖工具配置与生成脚本也可能携带内容。秘密不存在于源码字面值，不证明最终产物没有副本。

缩小命令能够接触的范围

可以为需要认证的步骤提供必要凭据，避免无关步骤同时读取。凭据权限与有效期应服务于该步骤的实际需求，不为了安装依赖使用可以修改全部仓库的通用账号。秘密挂载方便交付输入，却不能为不可信下载脚本建立安全边界；执行代码本身也应按照来源与权限审查。

多阶段构建可以减少复制范围，但不是自动清洁机制。假设最终阶段只需要编译结果，就应检查被复制的目录是否包含认证文件、调试包或原始配置。若缓存保留了工具生成的秘密副本，最终镜像不包含它也不能说明处置完成。缓存共享与访问权限需要按真实构建平台核对，不能把缓存当成永远不公开的内部对象。

如果发现泄露，应判断凭据是否已经离开受控范围，并按权限撤销或轮换；删除当前文件不能保证旧日志、镜像和缓存都被清理。相关恢复责任见密钥轮换与撤销。处置记录应写出检查对象与未知范围，不能只写“已经改成 secret mount”。

验证最终产物，也验证交接记录

可以安排待执行检查：使用专门测试凭据构建，观察日志、镜像历史与文件、构建输出和缓存权限，并确认失败路径是否打印了配置。测试凭据仍需受控，检测过程不应把它再次公开。自动扫描可以帮助找已知模式，但未匹配不等于不存在全部秘密，尤其是被转换或分段后的值。

本文没有执行这些检查，也不给出“保证不会泄露”的结论。评审时要求构建负责人同时解释输入挂载和输出去向；只有前者明确，说明凭据送进去了，不能说明它没有被带出来。
