用了 secret mount，为什么还要检查镜像、日志和构建缓存？

Docker secret mount 限制秘密的交付方式，不会约束读取它的构建命令。还要检查命令输出，并注意秘密值变化本身不会让 RUN 缓存失效。

正文

Docker secret mount 保护的是构建步骤如何收到凭据，不是命令读到凭据以后能做什么。命令仍然可以把它复制进普通文件、打印到日志，或生成含有它的产物；此外，BuildKit 不会因为秘密值变化就自动让对应的 RUN 缓存失效。于是安全审查要沿两条线走：秘密从哪里进入、被哪些输出带走；轮换后哪些步骤确实重新执行。本文用假设的私有依赖安装说明检查方法，没有构建 Docker 镜像、扫描缓存或执行容器测试。

挂载控制输入通道，不是进程沙箱

Docker 的 Build secrets 文档建议使用 secret 或 SSH mount 传递构建所需凭据，而不要把秘密放进 ARG 或 ENV。Dockerfile reference 说明，secret 默认以文件形式提供，通常位于构建步骤中的 /run/secrets/，也可通过 target 调整路径。它在指定 RUN 指令期间对构建容器可用。这个边界有用：Docker 不会因为你声明了一个挂载，就把秘密值自动写进最终镜像配置。但挂载不会把命令变成只能读取、不能写出的受限程序。

把构建命令当作数据处理者来审查。它获得了读取凭据的能力，那么同一进程及其子进程就可能把凭据写到其他位置。比如一个假设的 Node 项目需要用私有注册表下载锁定版本的依赖，步骤可以从挂载的配置读取认证信息并运行安装。若安装脚本为了方便，把完整认证配置复制到工作目录；后续指令又把工作目录复制进运行阶段，秘密就沿着普通文件路径进入镜像。挂载点在这一步结束时消失，不会撤回命令已经生成的副本。

另一个反例不需要复制文件：调试时开启 shell 跟踪、输出完整配置，或者让失败消息包含认证头，凭据便可能进入构建日志。日志通常由不同的 CI 系统保存、检索和导出；其访问边界不等同于镜像仓库。即使把最终镜像检查得很干净，也无法由此推出历史日志、构建摘要和外部缓存没有同一份值。反过来，日志中没有明显的原始字符串，也不能证明程序没有编码、拆分或嵌入凭据。

Build secrets 文档列出的挂载能力解决“怎样交给构建步骤”；它没有承诺替命令检查输出。Docker 文档也提醒不要把秘密用 COPY 或 ARG 管理。由此得到的工程判断是：输入层、进程权限、输出目的地是三项不同控制。secret mount 是必要的输入边界，不能单独构成端到端的“不泄露”证明。

用一条依赖安装链路找出实际输出

先画一条最短的数据流：CI 凭据存储提供构建秘密；BuildKit 把它挂到特定 RUN；包管理器访问私有依赖；该步骤产生安装目录；后续构建阶段选取文件；日志及缓存可能上传到远端。每个箭头都要回答两个问题：谁可以读到数据，哪些内容会留下来。只在 Dockerfile 里搜索 token 字面值，找不到工具运行后创建的认证文件，也找不到来自构建上下文的配置。

假设步骤原本只需要读取临时 npm 配置。审查员可以逐行核对是否有 COPY . . 把开发机的 .npmrc 带入上下文，是否有安装脚本把认证信息写进项目目录，输出目录是否会被第二阶段整体复制，以及安装失败时命令是否打印环境变量。.dockerignore 能排除不应进入上下文的本地文件，但它不能阻止一个有权读取挂载的脚本主动生成副本。排除输入与限制输出各有作用，不能把其中一种误当另一种的替代品。

多阶段构建能缩小最终镜像的复制集合。Docker 的 multi-stage 文档说明可以从前一阶段选择性地复制工件。这表示运行阶段不必包含编译器或整个构建目录；它不表示所有中间文件都已从构建缓存、日志或制品仓库消失。若 build 阶段把认证配置写在 dist 里，而最终阶段正好复制 dist，多阶段并不会自动识别哪一个文件是秘密。若文件未复制到最终镜像，其他缓存和日志仍要按各自权限检查。

因此先明确资产类型，再决定检查位置：最终镜像检查文件系统、历史层和元数据；构建日志检查命令回显与失败信息；远程缓存检查导出目的地、共享范围和读取权限；构建上下文检查本地配置是否被 COPY 接收。Docker 将外部缓存作为独立后端处理，并指出需要明确配置导出与导入。不同后端有不同 ACL 和保留期，不能用“只有最终镜像会公开”来缩窄审查范围。另外，RUN 的 cache mount 与 secret mount 是两类挂载：Docker 的缓存优化文档说明缓存挂载会在多次构建之间保留并复用内容。如果把它挂在包管理器自己的状态目录，目录里实际保存了哪些配置、索引和下载数据，要按那个工具的行为检查；这不是说包管理器必然会把 token 写进去，而是不能把持久缓存当作临时秘密挂载。

轮换凭据不等于重新验证凭据

秘密挂载还有一个容易漏掉的缓存边界。Docker 的 build cache invalidation 文档明确说明，秘密内容不参与构建缓存校验；秘密值改变本身不会使缓存失效，秘密 ID 或挂载路径改变则会参与校验。换句话说，给同一个挂载 ID 更新了 token，下一次构建仍可能复用旧 RUN 结果，命令未重新执行，也就没有验证新 token 能否读取依赖。

这不是“缓存里一定存着旧 token”的结论。它说的是缓存键不由秘密值组成，步骤执行与否依据其他输入而定。对于只做身份验证的步骤，这可能是理想的：秘密轮换不必让每层都重建。对于需要验证新的授权范围、确认令牌已撤销，或依赖内容随远端状态改变的步骤，缓存复用又可能给团队一种未经证实的绿色结果。密钥泄露后的处置与构建缓存新鲜度是关联但不同的问题。

选择缓存策略前要先定义验收问题。若问题是“当前 token 是否仍能读仓库”，就让该验证步骤真实执行，使用文档支持的定向 --no-cache-filter、改变无秘密的缓存哨兵，或安排明确的强制验证路径。不要把真实凭据塞进 ARG 当作 cache bust：Docker 文档警告 ARG/ENV 不适合传递秘密，因为它们可能留在最终镜像。一个无敏感含义的随机标记可以触发需要重跑的步骤，但它只证明该步骤重跑了；并不证明输出不含秘密。

如果问题是“依赖内容是否与声明版本一致”，则应依赖锁文件、校验和及包管理器的校验行为，而不是盲目清空全部缓存。无差别禁用缓存会掩盖真正依赖关系，还可能显著延长构建时间。把“授权校验要重新执行”和“所有编译、下载层都从头执行”分开，才能用较窄的失效范围获得需要的证据。

把检查设计成可以证伪的验收

可执行的审查计划先使用一次性、无生产权限的 canary 凭据，并给它一个仅用于检查的唯一标记。该标记不能是真实 token 的副本，也不能访问生产仓库。使用受控构建配置后，分别检查构建日志、输出目录、最终镜像文件、镜像历史、导出的缓存及 CI 制品；如果测试关注轮换，则确保相关 RUN 没有命中旧缓存，并核对新 token 确实参与了验证。每一步记录检查的是哪个输出和哪类读取权限，不能只记一条“Docker build 通过”。

负向路径也需要覆盖：挂载未提供时，步骤是否明确失败；包管理器返回 401 时，错误是否回显认证配置；脚本失败后，部分下载文件是否仍进入下一层；远端缓存导出是否向不该访问该项目的人开放。测试应使用 canary 值搜索精确文本和常见编码形式，但这只是定位已知形式的手段，不能证明所有转换都已发现。不要为了验证日志脱敏而把真实凭据打印到日志里。

如果一项受限步骤将秘密读入内存、只用它完成认证，并且输出是经过校验的依赖工件，那么使用专用 mount、缩小该步骤权限并把最终阶段只复制必要文件，可能已经足够。若脚本来源不可信、安装钩子可运行任意代码，或者构建会发布远程缓存，单靠 mount 显然不足，还要限制代码来源与缓存读取范围。这个选择取决于“谁在读取”和“数据会写到哪里”，而不是 Dockerfile 中是否出现某个关键字。

本文给出的是待执行验收方案，没有运行 Docker build、检查镜像、缓存或日志，也没有声称得到泄露扫描结果。若真实凭据已经出现在日志、镜像或共享缓存中，应优先撤销或轮换凭据，同时根据日志与平台权限确认可能的读取范围，再处理相关产物；删除当前工作目录里的文件不能抹除已经复制出去的历史数据。关于后续处置，可对照密钥轮换与撤销边界以及发布制品和回滚验证。
