readOnly 会自动拒绝写入吗？OpenAPI 3.2.1 允许两种策略

readOnly 是方向性注解，不是通用防写机制。服务端可忽略提交值或拒绝请求，应用仍须明确写入映射、权限和可观察结果。

正文

不能。readOnly: true 本身不是一条会自动阻止数据库更新的安全规则。标题所指的现行 OpenAPI 版本把 readOnly 和 writeOnly 视为注解，允许实现按字段注解、请求或响应方向，以及字段当前值进行扩展校验；资源拥有方可以忽略只读字段，也可以把它当作错误。服务端必须明确选择，应用的写入代码仍要保证只允许预期字段改变。规范原文没有承诺每个校验器默认拒绝。

先分清契约描述、请求校验和写入行为

OpenAPI 文档描述调用者与 API 之间的契约，工具可以据此生成参考页面、客户端类型和校验辅助逻辑。它并不会替应用决定每个用户可以修改什么，也不会自动重写 ORM 的更新语句。这里有三个不同的层次：契约把 status 标成只读；请求校验器是否检查客户端提交的 status；业务处理最终把哪些属性写进数据库。只有前两层有标签，第三层却把请求对象整体复制进持久化实体，标签本身就不能保护字段。

规范版本也会影响阅读方式。OpenAPI 三点零系列的 Schema Object 说只读属性可以出现在响应中，不应出现在请求中；若同时列为 required，该要求只作用于响应。三点一系列接入 JSON Schema 2020-12 后，文档进一步解释注解与方向校验。现行版本还举例说明，PUT 使用同一份资源表示时，如果只读字段必须出现在读取响应里，忽略未变更的回传值可能更容易兼容。不要把旧版的“SHOULD NOT be sent”直接改写成“所有版本、所有服务器 MUST 返回 400”。OpenAPI 三点零系列原文和JSON Schema 注解说明需要放在具体版本里解释。

GET 的完整表示回传 PUT，会让问题变得具体

假设订单读取接口返回 id、status、memo 和 updatedAt。客户端只想把备注从“周一发货”改成“周二发货”，但为了提交完整资源，PUT 请求把四个字段都带回；其中 id、status 和 updatedAt 是服务器维护的属性。这个订单只是解释设计取舍的假设示例，不是实测系统。

此时，“请求中出现只读字段”还不够确定处理规则。值和当前状态是否相同？端点是完整替换还是部分更新？调用者是否有权执行状态迁移？应用只更新 memo，还是把整个对象映射到数据库？如果同一请求里 status 从 approved 变成 cancelled，服务器可以拒绝，也可以忽略该字段并按允许的备注更新；如果两者都不写清，客户端可能收到成功响应，却不知道状态有没有被采用。

请求情况 可选策略 需要防止的误解
PUT 回传原值，字段在响应中必需 忽略字段或接受其未变更值，按正文约定更新可写字段 不能把“忽略”解释成字段更新成功
PUT 提交了不同的系统状态 拒绝请求，或忽略该字段并只更新允许内容 若状态迁移需要业务审批，不能由通用字段映射触发
PATCH 中没有提交系统字段 不改系统状态 缺省字段与显式 null 的含义须由所用 PATCH 契约定义
POST 新建对象时带入服务器生成 ID 报错或忽略并生成服务端 ID 不能把客户端传入的 ID 当作资源归属证明

这是策略比较，不是规范替团队选好的唯一答案。尤其是 PUT 和 PATCH 不应合成同一条规则：HTTP 语义规范把 PUT 描述为按请求表示创建或替换目标资源状态；PATCH 则依据请求媒体类型所定义的补丁文档应用一组变化。RFC 9110 的 PUT 定义与RFC 5789 的 PATCH 定义因此要求不同的字段缺省处理。OpenAPI 的 readOnly 不会替代这些请求语义。

忽略、拒绝、保留原值，取决于调用者和操作

如果已有客户端习惯把 GET 结果原样回传，单纯因为只读字段出现就拒绝，可能使原本只改备注的请求全部失败。此时可以在服务端忽略只读值，或者允许它以当前值回传，但必须把规则写进 API 文档并在响应中反映真实状态。若该字段是关键状态且提交者必须明确遵守“不可修改”，拒绝会更清楚，但客户端应能读取错误并调整行为。规范允许这两种方向，产品兼容性和错误清晰度由接口所有者权衡。

实现里可以把请求映射为一个显式更新对象，例如仅包含 memo。路径参数 orderId 决定要更新的资源，经过授权检查后，业务层再检查该订单是否处于允许修改备注的状态；status 变化则经独立命令或状态转换函数处理。字段是否“可写”与“当前用户是否可写”不是同一问题：某属性对客服开放，不代表访客也可改；标记为可写也不代表可以越过对象归属校验。对象层权限边界可与按对象检查访问权限一起设计。

反例是把请求 JSON 直接解码到数据库实体，再执行整行更新。即使生成的文档隐藏了 status 输入框，旧客户端、手工 HTTP 请求、批量导入入口或后台任务仍可能提交该属性。校验成功只说明校验器按自己的配置接受了数据，不代表权限检查或持久化映射已经安全。相反，另一个失败路径是服务端先更新 memo，发现 status 非法后才报错；若两步不在事务或原子操作中，请求看起来失败，备注却已改变。字段规则应在写入前完整评估，并以事务边界保证错误路径不会留下部分结果。

把规则放进可观察结果，而不是只测 schema

建议把每个端点的策略写成决策表，再将其转换为测试。准备一条订单的初始数据；分别发出“备注合法、系统字段未变”“备注合法、系统字段被改”“备注非法、系统字段被改”以及“用户无权修改该订单”的请求。测试不只检查 HTTP 状态，还要读取持久化值：允许更新时只有 memo 改变；拒绝时所有字段都保持原值；忽略时响应中仍返回数据库的真实状态，而不是回显被忽略的客户端值。

还要覆盖写入入口，不仅是主要 HTTP 路由。批量接口、异步任务、管理端和消息消费者可能复用同一实体更新函数，却不经过同一个 OpenAPI request schema。可以在服务层对允许更新的字段进行白名单映射，并在事务提交前校验状态迁移与对象归属。回归测试应以数据库前后快照为断言对象，必要时再核对审计事件是否记录了被拒绝尝试。本文没有执行这些请求、连接数据库或运行 API 测试；这些是设计建议，不是通过记录。

如果共享读写 schema，必须指定校验器如何获得操作方向、哪些注解会被解释，以及请求的当前值如何参与判断。若读写属性、角色权限或状态机差异很大，分开的 response/request schema 更容易表达边界，但也会引入字段同步和兼容性维护；当两个模型确实共享一部分结构时，可以复用基础 schema，再通过受控的组合或代码生成约束请求模型。不要因为拆分看起来更安全，就默认所有字段复制维护成本都可忽略。

把 readOnly 的责任写给正确的一层

可以用一句简短规则收尾评审：OpenAPI 说明某字段应如何被理解，服务端的映射、授权与状态迁移逻辑决定它实际能否被改。对每个写端点明确“出现时忽略还是拒绝、未变值是否可回传、哪些角色可改、更新失败是否原子”，随后检查数据库的真实结果。生成客户端可以帮调用者少犯错，不能代替服务端的字段白名单和权限验证。

本文核对了截至 2026-11-26 的现行 OpenAPI 与 JSON Schema 原文；标题所指版本发布于 2026-09-10，旧版规范页面发布于 2024-10-24。订单、端点行为和测试表均是假设示例；没有执行框架配置、服务端、数据库、客户端生成或安全测试。要理解只读元数据之外的授权要求，可继续看对象级访问控制与JSON Schema 格式注解并不等于断言。
