配置 SameSite 后，CSRF 还要按哪些路径验收？

SameSite 只限制部分跨站 Cookie 携带。应按写入路由核对请求方法、来源、令牌与业务状态，不能用一个属性替代 CSRF 验收。

正文

配置了 SameSite 之后，仍应按每条会改变服务端状态的路由验收 CSRF 防护。SameSite=Lax 允许一类跨站顶层安全方法导航携带 Cookie；如果账户修改接口把改变状态的动作放在 GET 上，Cookie 属性不会把这个接口变安全。先列出写入路由和真实请求上下文，再决定令牌、来源校验、Fetch Metadata 与 Cookie 属性各自承担什么责任。

本文用假设的账户设置服务说明检查方法，不代表本站有相同认证架构，也没有运行浏览器攻击测试。文中给出的矩阵是待执行的验收计划，不是测试结果。

SameSite 改变 Cookie 何时发送，不改变接口做什么

CSRF 的关键条件是浏览器自动携带某种身份凭据，而服务端把请求当成已登录用户发起的意图。如果跨站页面能够诱导浏览器提交请求，而接口只检查会话 Cookie 就修改状态，浏览器可能替用户带上身份，却没有证明用户是在当前页面主动确认这项操作。对象权限仍是另一件事：请求即使确实由用户发起，服务端也要确认这个用户有权修改目标对象。

这个属性只是 Cookie 的发送条件，不是请求意图证明。(MDN 的 Set-Cookie 文档 对 Lax 的说明包含一个容易被忽略的条件：跨站请求若是顶层导航并使用安全方法，Cookie 仍可随请求发送。GET 通常属于安全方法。于是“Lax 会挡跨站写入”只有在接口也遵守方法语义时才成立；若一个 GET 直接退订、删除草稿或改变账户设置，错误在接口把读取方法当成写入，不在浏览器没有替团队做安全校验。OWASP 的 CSRF 指南也特别要求审查所有安全方法路由是否会改变服务端状态。

Strict 会更严格地抑制跨站 Cookie，但这会影响从外部链接进入站点的登录体验。用户从邮件或文档点进账户页面时，首个请求可能没有会话上下文，随后可能需要重新加载或走重新认证流程。安全属性的选择必须连同登录、支付回跳、身份提供方回调等合法流程一起验证，不能只看攻击路径。浏览器对未声明 SameSite 的 Cookie 可能采用不同默认行为，策略应显式写入，而不是把客户端默认值当作验收证据。若产品必须在跨站上下文发送 Cookie，None 需要同时设置 Secure，并单独核对哪些来源会带上凭据。

还要区分 same-site 和 same-origin。浏览器按站点关系处理 Cookie，并不等于同一注册域的所有子域都由同一安全团队控制。假设应用主机存会话 Cookie，而同一注册域下的内容子域托管用户可控页面；从后者发起的某些请求可能仍被浏览器视作 same-site。即使 Cookie 没有设置宽泛的 Domain，目标请求发往 app.example.test 时，主机范围和请求是否 same-site 仍是两个判断。因此，站点边界不能替组织确认子域所有权、托管责任或失陷风险。

验收单位应该是写入路由，而不是 Cookie 配置页

可以把审查对象拆成一张路由矩阵。假设某个账户服务有三项操作：修改邮箱、导出资料、注销账户。第一列写 HTTP 方法和最终落到的处理器；第二列写浏览器凭什么身份通过认证，例如会话 Cookie、授权头或二者并存；第三列写请求可能从何处发起；第四列写成功时应发生的业务变化，以及被拒绝时数据、审计日志和副作用应保持什么状态。

这张表会立即暴露方法语义问题。导出资料可以是读取，但下载链接是否泄露敏感内容仍需独立权限判断；修改邮箱和注销必须通过非安全方法完成，GET 只负责展示确认页或读取状态。若邮件里的退订链接会直接提交变更，那么即使不考虑恶意攻击，预取、扫描或误点也可能触发动作。把确认步骤改成页面展示后再提交，既符合 GET 的安全语义，也给令牌和身份检查留下明确位置。

矩阵还要记录身份状态。匿名用户进入受保护路径会重定向到登录页，回调返回后执行的是否还是同一操作？后台管理入口是否走另一套中间件？移动客户端是否完全依赖 Cookie？反向代理是否删除 Origin 或 Sec-Fetch-Site？相同 URL 在不同会话、缓存节点和代理链路下可能有不同请求上下文。只验证首页 Cookie 属性，无法回答这些路由是否真的受到保护。

矩阵中应把 Lax 记作一层，而不是整行结论。若会话 Cookie 只需要在本源请求中使用，可显式设置适合该流程的策略，并评估 __Host- 前缀：在支持它的用户代理中，Cookie 必须使用 Secure、Path=/ 且不能带 Domain，从而收窄 Cookie 可被哪些主机设置或覆盖的边界。但这个前缀并不验证请求意图，也不能修复 GET 写入、跨站脚本或对象越权。Cookie 属性缩小凭据暴露范围，服务端仍要判断请求能否执行。

表单、JavaScript API 和子域要用不同证据

传统表单可以发出简单跨站请求，浏览器的 CORS 规则不会因此保证服务端副作用没有发生。Synchronizer Token 的价值在服务端验证：页面或会话中关联的不可猜令牌随写入请求提交，服务端在执行任何部分变更前比对它；缺失或不匹配时应拒绝，并检查数据和副作用确实未发生。令牌不应放进 URL 或普通日志。使用框架内置机制时，仍要确认覆盖的表单、管理路由、API 和例外入口。

如果前端用 fetch 调用 JSON API，自定义请求头或非简单请求可以让跨域请求经过预检；严格的 CORS 允许清单也能限制哪些源获得带凭据访问。但“浏览器无法让攻击页面读取响应”不等于“服务器一定没有处理请求”。简单表单请求仍可能送达；如果服务端允许不受控的凭据来源，或某条写入路由不需要预期的自定义头，保护链就会出现缺口。因此，跨域 API 应明确哪些来源获准、是否携带凭据、哪些方法和头允许，并在服务器端验证受保护路由要求的请求上下文。CORS 是一项配置约束，不是把 CSRF 问题整体外包给浏览器。

如果接口只接收 JSON，CORS 就能代替 CSRF Token 吗？

不能仅凭“请求体是 JSON”关闭 CSRF 评审。应检查所有状态写入是否都拒绝简单请求、是否必须带有预期的自定义头、带凭据的 CORS 是否只允许经过审核的具体源，以及是否存在兼容旧客户端的表单或 URL 编码入口。若某一路径仍接受简单请求，或允许任意来源进行凭据请求，那么 JSON API 的设计意图不会自动约束实际处理器。对经过严格约束的 API，自定义头、预检和来源检查可以成为防线的一部分；令牌是否必需取决于架构与威胁模型，而不是内容类型这一个字段。

Fetch Metadata 可以补充来源判断。Sec-Fetch-Site 能区分 same-origin、same-site、cross-site 或用户直接发起等情形，但代理可能删除头，客户端也可能不提供。缺失头必须有明确策略：敏感写入可以按未知拒绝，也可以回退到 Origin/Referer 与令牌验证；不能把“没有观察到跨站标记”默认为可信。若服务端根据这些请求头改变响应，还要让缓存正确区分响应变体；否则边缘缓存或代理可能让不同上下文复用同一结果。

几种“检查通过”仍可能漏掉攻击路径

最常见的一类漏项，是 Lax 配合会改状态的 GET。检查 Cookie 面板会显示属性正确，但攻击者仍可能诱导顶层安全方法导航；真正应修改的是路由语义，并逐项确认 GET、HEAD 等安全方法只读取数据。第二种是同一注册域下存在未受同等控制的子域。父域策略看似一致，却可能有遗留服务、用户内容托管或 DNS 残留让攻击者影响同站请求。第三种是令牌只在主表单处理器验证，而管理接口、移动端兼容接口或旧版 API 绕过中间件。

第四种是团队用状态码当作唯一证据。某个非法请求返回 403，但后端在拒绝前已写入一部分数据、发送邮件或加入队列；反过来，有些合法请求返回重定向并不代表写入失败。验收应比较请求前后的业务状态，并检查事务、日志、队列和通知等副作用。还应测试令牌缺失、错误令牌、可信来源、跨站来源、同站但不同源、Fetch Metadata 缺失以及登录和回调路径。本文没有运行这些测试，所以不提供浏览器日志或成功率数字。

最后，CSRF 防护不替代 XSS 防护。若攻击脚本已在受信任页面同源运行，它可能调用应用自己的 API、读取页面令牌或借助合法 JavaScript 发请求；这种 Cookie 策略无法区分请求是不是来自用户真正点击。同样，Cookie 的站点策略也不替代对象权限检查：令牌证明请求带有相应防护上下文，不代表调用者有权修改目标记录。

什么时候可以把 SameSite 单独作为主要防护？

OWASP 指南只在一组狭窄条件同时成立时，才把单靠 SameSite 作为合理防护之一：应用所在注册域下没有不受团队控制的主机或服务；所有状态改变都不通过 GET 等安全方法；会话 Cookie 使用 Strict，或采用 Lax 并配合 __Host- 前缀及严格 GET 审查；写入端点另有 Origin 或 Referer 验证；并且团队接受不执行 SameSite 的客户端所带来的残余风险。缺一项就不该把该指南解释成通用放行许可；OWASP 建议在这种情况下再结合令牌或双重提交模式等防护。

选择控制前先问三个问题：浏览器是否自动携带认证凭据？请求能否从不可信来源触发？服务端会不会仅凭 Cookie 就改变状态？如果三个问题的答案都指向风险，再按表单、JS API、子域和浏览器兼容路径选择令牌、来源校验、Fetch Metadata 与 Cookie 属性。验收记录应保存路由、方法、凭据来源、请求站点关系、防护层、拒绝时的业务状态及缺失头回退；这比“Cookie 已设 Lax”更接近真实的安全结论。

与对象权限边界一起评审时，应分别证明请求来自预期上下文，以及当前用户有权修改该对象。令牌或来源头的存在，都不能代替后一个判断。
