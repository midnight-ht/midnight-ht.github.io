改用尾部采样，就能找回已经丢掉的错误链路吗？

尾部采样只能判断 Collector 收到的 span。本文拆解 SDK 丢弃、路由分片、晚到数据与容量淘汰，说明如何验证错误链路究竟缺在哪一段。

正文

不能。尾部采样可以等到一部分 span 到达后，再按错误状态、时长或属性决定是否保留 trace；它不能重建从未被创建、记录、导出或送到该采样器的 span。要判断“错误链路为什么不完整”，必须把采样决策点和它之前的采集路径分开检查。本文依据 OpenTelemetry 规范、概念文档及 Collector Contrib 尾部采样处理器文档整理；没有配置 Collector，也没有执行压测或测量资源成本。处理器文档会随版本变化，文中的具体参数和指标名应以部署所用发行版及版本为准。

尾部采样看到的是已到达的证据

trace 不是服务端一次性导出的一整块对象。数据模型把 span 描述为独立操作，消费者按 Trace ID 将收到的 span 分组，再用父子关系和 links 组织成 trace。因此后端看到的“链路”是对已收到数据的视图。官方数据模型把只收到部分 span 称为不完整 trace，并列出采样未选中、过滤、导出失败或延迟、span/队列/后端限制，以及操作尚未完成等原因。事实 F1、F2

这点决定了尾部策略的能力边界。Collector 的 tail sampling processor 能根据它收集到的 trace 数据评估策略；OpenTelemetry 的采样概念举例包括包含错误的 trace、整体时长以及某些属性。相比在请求刚开始时做头部决策，它能利用稍晚出现的信息，但“稍晚”不等于拥有整个系统中每一个 span。事实 F3

假设一次请求依次经过入口服务、订单服务和数据库。入口 span 已被发送；订单服务因为 SDK 的 DROP 决策而不记录子 span。如果数据库 SDK 继承未采样上下文并据此 DROP，数据库 span 也不会被记录；具体行为取决于子服务的 sampler。假设 Collector 最终只收到入口 span，再增加“包含 ERROR 就保留”的尾部规则，输入集合里仍没有 ERROR span，结果只能基于现有证据判断。SDK 规范明确规定 IsRecording=false 时 span 数据会被丢弃，span processor 不会收到它；如果某个阶段把 span 丢弃，后面的处理器无法恢复其属性、事件或状态。事实 F4

反过来，入口服务本地仍记录了 span，也不保证后续可见。它可能卡在导出队列、被队列限制丢弃、遭到 Collector 前置过滤，或在网络故障后没有成功重试。概念数据模型把失败或延迟导出和配置的 span、队列或后端限制列为不完整 trace 的常见来源。排查时应沿着“span 创建与记录 → SDK 导出 → 接收器 → 前置处理器 → 尾部采样器 → 后端”逐段核对，不能只看采样器的策略配置。事实 F2、F4

路由错误会让同一 trace 被拆成几份

尾部采样处理器需要按 Trace ID 聚合 span，并在有状态的缓冲区里等待决策。Contrib 处理器文档要求同一 trace 的所有 span 到达同一个 Collector 实例；否则每个副本只根据自己收到的片段作判断。处理器文档给出这一要求，部署指南给出的两层模式则是：第一层 Collector 使用按 trace ID 路由的 load-balancing exporter，第二层 Collector 执行 tail sampling。事实 F5、F6

用三段链路说明差别。若入口、订单和数据库三个服务的 span 都送到 Collector A，A 有机会看见 ERROR 状态并保留整组已送达的 span。若普通负载均衡把入口送到 A、订单送到 B、数据库又送到 A，A 和 B 各自维护的缓冲区并不会自动合并。A 可能看见一个没有错误的入口和数据库片段，B 看见孤立的错误片段；其中任何一个结果都不等于完整 trace。这里是机制示例，不代表任何实际环境的测试结果。

扩容会让路由成为持续运行的问题。trace ID 路由避免了同一稳定拓扑下任意分配，但服务发现成员改变时，路由映射可能改变；仍在途的旧 trace 和新 span 可能被送到不同副本。agent-to-gateway 指南因此把多实例尾部采样称为较高级的部署方式，提醒测试路由重新分配和决策一致性，并建议优先考虑单个资源充足的尾部采样网关，除非已有可靠的粘性路由策略。事实 F7

等待窗口只能等到，不会召回

采样器通常会缓冲 trace 一段时间再作决定。Collector Contrib 当前主分支文档将 decision_wait 定义为计时路径的决策等待时间；trace-complete 策略会根据累计数据在计时器处理时评估，等待更久通常也意味着状态保留更久。该文档目前列出的默认值是 30 秒，但这是当前特定处理器文档的版本信息，不是所有 Collector 发行版、所有采样策略都保证使用的通用值。配置前应先确认实际二进制包含哪个处理器版本和功能门。事实 F8

窗口太短，子调用 span 可能在决策后才到；窗口加长可以让更多迟到数据有机会先抵达，却不能让已丢弃数据出现。处理器文档还说明，晚到 span 在原决定仍留在缓冲区时会继承原决定，因此不会影响那次策略判断。决策缓存可以在 span 数据释放后记住 trace ID 的采样结果，但缓存保存的是决定，不是原 trace 内容；它不是恢复机制。没有缓存或对应项已被淘汰时，迟到 span 可能再次经历缓冲并形成新的决定，造成同一 trace 不同片段的处理结果不一致。事实 F9

这让“等多久”成为基于测量的取舍，而不是把时间设得越大越安全。需要关注实际 span 到达延迟分布、trace 持续时间、缓冲区占用和决策处理延迟。官方处理器文档列出提前淘汰计数 otelcol_processor_tail_sampling_sampling_trace_dropped_too_early、缓冲保留时长 otelcol_processor_tail_sampling_sampling_trace_removal_age、决策计时延迟 otelcol_processor_tail_sampling_sampling_decision_timer_latency 和晚到 span 年龄 otelcol_processor_tail_sampling_sampling_late_span_age。监控这些指标能定位采样器自身压力与晚到情况，但不能单独证明上游 span 没有丢失。事实 F10

容量淘汰和单条 trace 上限是两种缺口

增加副本不一定扩大每条 trace 能用的缓冲空间。如果 trace 按 ID 固定路由到某一副本，该副本的 num_traces、内存、CPU 与决策延迟共同决定能否在窗口内持有足够状态。Contrib 文档描述了环形缓冲达到 num_traces 时移除最旧 trace 的行为；被移除的 trace 可能在 decision_wait 到期前就被提前丢弃。它也提供 maximum_trace_size_bytes 这一单条 trace 大小上限，超限时会立即从 tail sampler 丢弃。前者是很多 trace 竞争有限缓冲的压力，后者是单条 trace 过大，调一个参数不一定同时解决二者。事实 F11、F12

因此不要从“错误链路不见了”直接跳到“把等待值翻倍”。如果提前淘汰指标上升，降低等待时间可能减少缓冲压力，但也会更早决定，放弃慢到达的 span；提高容量则会增加内存占用。若最大 trace 大小经常触发，调大 trace 数量未必有帮助，应该先确定异常 trace 是跨度太多、事件属性过大，还是错误数据本身需要例外保护。官方文档建议处理器的下游快速消费输出，避免采样决策和后续流水线处理延长延迟；但实际的容量值、回退策略与安全余量，需要按流量峰值和运行版本测量，而不是照抄示例配置。[事实 F10、F11]

优先解决数据路径的完整性，再谈策略命中率。可以为诊断用的测试请求附加低敏感、稳定的版本或实验标记，以便核对 span 在各级的存在；不要把邮箱、令牌或完整请求体塞进属性来“确保采样命中”。属性隐私与采样规则的具体合规性依业务而定，跨服务上下文的敏感信息边界可参照OpenTelemetry baggage 的传播限制。若策略依赖一个属性，还要核对它由哪个服务添加、在哪些 span 上出现、是否会被处理器重命名或过滤。属性缺席与 span 丢失是不同故障，表现都可能是规则没保留该 trace。

用一个分段验证区分故障位置

下面是待执行的验证方案，不是已运行的实验。准备固定的 trace ID 关联请求，在入口、订单和数据库各产生一个可区分的 span，并在第二个子调用模拟 ERROR。每个阶段记录可核对的 span ID、父 span ID、状态码或测试属性。先让 SDK 和 Collector 不启用采样丢弃，检查三个 span 是否都到达采样器；再单独引入一种故障，比如 SDK DROP、前置过滤、导出队列失败或随机负载均衡。这样一旦后端出现缺口，能定位缺口在采样器之前还是之后。

随后验证时间与路由：令一个服务的 span 延迟到达，分别落在决策窗口前后；观察它是否参与决策、是否继承已有决定。再将同一个 trace 的 span 分批从两个入口 Collector 发出，核对按 trace ID 路由时是否由同一尾部采样实例接收。若生产会扩缩容，在成员变化期间重复检查路由映射；不能以静态拓扑测试替代这一条件。最后在接近峰值的受控负载下观察缓冲提前淘汰、处理器延迟、单 trace 超限和内存变化。若没有这些负载测试证据，就不要声称容量可以覆盖生产尖峰。

验证结果最好拆成三类指标：产生端创建/记录了多少测试 span，尾部采样器实际接收了多少、按什么原因作决定，后端最终存了多少。它们对应不同边界，数字不相等时先查阶段差异，而不是把所有缺口都归因于“采样率”。错误总量也不能直接用被采样保留的 trace 数量推算，因为策略有意偏向错误、延迟或属性群体；整体错误率应由合适的指标或其他未采样汇总数据提供。

何时尾部采样有用，何时它不解决问题

如果 SDK 或前置管道能把候选 span 送到尾部采样器，系统可以接受缓冲与运维成本，并且诊断问题确实依赖请求结束后才知道的错误、时长或属性，尾部策略才提供头部策略无法直接做出的选择。采样概念文档也指出，采样可以组合在不同采集阶段：在高流量下，头部采样先限制进入管道的数据，随后尾部采样再按可见证据作更复杂决定。这个组合能保护遥测管道，但如果头部阶段已经让候选 trace 不再记录或导出，尾部规则只会作用于留下来的子集。关于传播的 sampled 标志与接收端信任边界，可继续看traceparent sampled 标志的信任边界。事实 F3、F13

如果主要问题是服务没有正确创建 span、采样决策在 SDK 阶段丢弃了数据、导出或接收不可靠、路由没有把同一 trace 聚到一起，先修这些环节比再加一个尾部策略更直接。如果真正的问题是高基数、存储费用或只想保留一个统计比例，概率采样、指标聚合或后端提供的方案可能更合适；具体选择取决于能否接受遗漏哪些诊断信息、在什么阶段作决定，以及运维团队能否维护有状态的缓冲服务。

最终可以把承诺写成可验证的范围：“在指定 SDK 未丢弃候选 span、导出链路健康、所有片段到达同一个尾部采样器、并满足等待与容量限制时，按错误属性保留已接收的 trace。”这句话比“保留所有错误链路”更长，但它能让排障者知道缺失证据可能在哪个边界发生。先核对路径和版本，再调策略参数。
