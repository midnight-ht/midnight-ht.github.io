下载到了构建产物，怎样确认它就是本次批准的版本？

GitHub Actions 产物交接应绑定运行身份、不可变产物与摘要，摘要匹配只证明内容关联，不替代来源和发布授权。

正文

下载成功只证明流水线取得了某个产物，不证明它就是审批人批准的构建。交接应把源码提交、运行身份、产物标识和内容摘要绑定起来，再检查部署使用的对象。本文讨论 GitHub Actions 的假设发布流程，没有执行工作流或验证某个真实审批系统。

名称是查找线索，不是完整身份

GitHub 产物存储与共享文档说明第四代产物语义中的不可变性，并描述上传返回摘要和下载时的摘要校验。当前页面中的操作示例会随版本更新，本篇明确引用第四代不可变语义，不把某个旧操作版本称为当前最新，也不推断所有自托管环境自动具有相同支持。

假设测试运行产生一个名为应用构建的文件，后续部署只按名称查找最近一次结果。分支上同时有多个提交，最近一次可能并非审查时看到的那一次。名称可以方便人理解，但审批记录应能定位具体运行和产物，不能依靠“最近成功”来补齐身份。重跑也应记录新的运行尝试，避免把重建文件默认为之前批准的内容。

不可变性降低了同一产物被随意追加修改的风险，却不保证选择的是正确对象。文件也可能在下载后被脚本重新打包或加入环境配置。需要区分可部署的最终产物与中间结果：若发生任何内容改变，摘要与批准对象都要跟着调整，不能继续展示旧摘要作为最终版本的证据。

摘要回答内容关联，不回答信任来源

摘要匹配说明某份内容与预期字节一致，前提是预期摘要本身来自可信记录。如果攻击者同时替换文件和摘要，单纯再算一次并不能识别错误来源。发布流程仍需限制谁能产生、选择和批准对象，核对第三方操作与令牌权限，相关责任见流水线令牌权限。

文档中的摘要比较不应被误写成你的部署门禁必然中止。GitHub 文档说明摘要不匹配会显示警告，并非自动中止保证；应用要明确校验异常是停止、人工处理还是进入其他恢复流程；本篇建议不能在不一致时继续把部署标记为通过。实际工具行为要按选定版本验证，不能只因为控制台出现一个提醒就认为安全责任已兑现。

产物保留和回滚也需要联动。审批等待期间对象过期，应清楚地报告缺失，不能偷偷从不同提交重新构建再沿用旧批准。回滚需要的配置、迁移条件和运行依赖不一定都在归档包中；一个旧压缩包还在，并不保证它能安全运行于现在的环境。

交接记录应能支持反向核对

建议保存待执行验收条件：指定运行下载、摘要不一致、对象缺失、重跑结果与下载后变更。检查部署记录能否反向定位源码和审查版本，且失败场景不会自动退回名称模糊的替代对象。本文没有运行这些测试，没有提供成功日志。

与发布产物及回滚结合时，把批准的最终对象贯穿测试、部署和线上确认。评审人员应能指出“这次发布使用哪一个产物”而不需要猜测时间顺序；否则一次正常下载仍然留下了身份空缺。
