下载到了构建产物，怎样确认它就是本次批准的版本？

下载成功和摘要匹配只能说明产物交接中的一部分事实。把源码提交、工作流运行、产物摘要、来源证明与审批对象分开记录，部署才不会按名称误拿另一个构建。

正文

下载成功不能证明你拿到的是本次审批通过的构建。一个可靠的交接至少要回答三件不同的事：下载的字节是否与上传时一致，产物由什么源码和工作流生成，以及发布审批究竟允许部署哪个对象。摘要主要回答第一件，来源证明帮助回答第二件，审批策略回答第三件。本文用 GitHub Actions 的假设发布流程解释如何把这三类证据接起来；没有运行工作流、生成 attestations 或验证真实审批记录。

把完整身份写成一条可反查的关系

“release.zip”是方便人看的名字，不是完整身份。同一仓库可能有多条分支、多个工作流、重跑尝试和同名产物。若部署任务只取“最近一次成功的 release.zip”，它可能拿到更新的重跑结果，也可能拿到别的分支构建。审核记录里写着某个源码提交，并不自动约束下载步骤最终选中的文件。

发布交接可以把以下字段放进同一份记录：仓库与源码提交 SHA、工作流文件或工作流身份、运行 ID 与尝试号、产物 ID 和显示名称、上传步骤给出的摘要、审批人的决定和目标环境。GitHub 的产物 REST API 示例响应确实包含产物 id、name、digest，以及关联运行的 id、head_branch 和 head_sha；上传动作仓库还说明成功上传会输出可用于 REST API 的 artifact-id 和 SHA-256 artifact-digest。但这些字段本身不会生成审批决定，也没有证明任一团队的策略已将它们绑定。部署任务应从已批准的运行中选择指定产物，下载后再次核对摘要，并记录最终部署使用的摘要。把尝试号、目标环境和审批决定也纳入同一关联，是编辑建议，不是 GitHub 自动替你建立的审批关系。产物 REST API；upload-artifact 的输出说明若下载后解压、重打包、注入配置或重新压缩，字节就变了；最终部署对象应拥有自己的摘要，不能继续沿用上游压缩包的摘要。

举一个纯假设的流程：提交 S1 触发构建运行 R1，该运行产物叫 site-bundle，上传步骤输出摘要 D1。审批记录若只写“批准 site-bundle”，发布工作流仍有歧义；若记录 S1 / R1 / attempt 1 / artifact ID A1 / D1 / production，部署步骤便能验证所取对象是否与审批记录相同。这里的符号不是实际运行 ID，也不代表真实部署系统。

GitHub 当前的工作流产物指南把产物定义为一次工作流运行产生、可在作业结束后保存或传给其他作业的文件或文件集合；跨工作流或工作流运行下载时，文档要求提供令牌和运行标识。指南中的上传示例使用 upload-artifact@v4，下载示例使用 download-artifact@v5；这些是本次查阅到的文档示例版本，不能扩展成“所有环境都具备同样行为”或“这是所有项目唯一可用的版本”。工作流产物指南；存储与共享工作流数据

摘要校验的是字节，不是生产者

GitHub 文档说明，每次使用上传产物动作会返回一个 SHA-256 摘要；下载动作会重新计算摘要并与上传步骤的输出比较。若不一致，工作流界面和日志会出现警告。文档没有保证这个警告一定使后续部署失败，所以发布团队必须自行把处理结果写进门禁：摘要缺失或不一致时停止部署，或者明确进入人工处置；不能让警告存在却仍把本次发布记为通过。验证产物的文档章节

假设部署 job 下载后的文件被再次处理。若处理只是解包到临时目录而部署仍引用原始压缩包，应该验证原始包摘要并证明部署输入确实是从该包解出的预期目录；若脚本改变了压缩包里的文件或重新打包，新的包已经不是 D1 对应的字节，就需要计算新摘要并重新审批。摘要相等能说明被比较的字节相符，但不能说明 D1 是由可信工作流提供、对应的是预期分支，或审批人看过它。攻击者或错误配置若能同时控制文件和“预期摘要”，单独重算不能建立可信来源。

GitHub 文档称 upload-artifact v4 产物不可变：不能把它当作中间目录追加文件。不过，动作仓库也说明，启用 overwrite: true 会以同名产物完全覆盖旧对象，产生一个新 ID，旧对象不再存在。于是“不可变”描述的是既有对象不能被原位改写，不表示同名引用永远指向原对象。若作业变换了文件，应以另一个名称上传最终版本；若有意覆盖，审批记录就必须检查新 ID 和新摘要，不能只复用名称。无论哪种方式，仍需防止部署选择错误运行或审批与选择脱节。名称只解决如何查找；身份记录还要指向运行和产物，摘要则指向内容。upload-artifact 的覆盖说明

来源证明仍然不是发布批准

GitHub artifact attestations 可以把产物与工作流、仓库、组织、环境、源码提交和触发事件等构建信息建立加密签名关联。消费者可以使用 GitHub CLI 的 gh attestation verify 验证 attestation，再根据自己的策略检查来源是否符合预期。比如，策略可以要求仓库、工作流、提交 SHA 和部署环境都匹配审批记录。命令本身不会替团队决定哪些工作流值得信任，也不自动判断软件是否安全。

下面只是文档形态的命令示例，未在本项目或任何仓库运行：

gh attestation verify path/to/release-binary -R OWNER/REPOSITORY

GitHub 官方文档明确提醒，attestation 不是产物安全保证；它把消费者连回构建来源与说明，安全评估和放行策略仍由消费者制定。签发后无人验证，也不会自动产生实际保护。功能适用范围也有限制：本次打开的文档称，当前计划可使用（旧 Bronze、Silver、Gold 计划除外）；Free、Pro、Team 计划只对公开仓库提供，私有或内部仓库需要 GitHub Enterprise Cloud。项目采用前应按当前账号、仓库可见性与计划核实，不能照抄他人的工作流权限配置。Artifact attestations；生成与验证构建来源证明

所以门禁可以分层：先确认下载对象确实来自指定运行和产物；再确认下载摘要与上传输出一致；需要供应链来源保证时验证 attestation 并检查仓库、提交、工作流和环境等策略条件；最后确认审批记录覆盖的是这个摘要或这个经过验证的来源。摘要通过不替代 attestation，attestation 通过也不替代业务或安全审批。测试用临时产物可能只需运行身份和保留记录；要发布给用户运行的二进制，则更有理由验证来源证明。控制强度应和风险、使用者及恢复成本相称。

重跑、缺失与变更怎样处理

最容易被忽略的失败路径不是摘要算法出错，而是发布任务在同名对象中选错了那个。假设 R1 由提交 S1 生成并获得批准，随后有人对同一工作流重跑，或者 S2 又上传了名字相同的产物。如果部署脚本重新查询“最新成功产物”，它可能离开批准边界。记录运行尝试、产物标识和摘要，是避免这种时间顺序猜测的控制建议；审批决定应针对具体对象，而不只是分支名或文件名。

产物缺失、过期或关联工作流运行已删除时，不应悄悄重建一份再沿用旧审批。GitHub 文档说明删除工作流运行会同时删除其产物；产物保留期可受仓库、组织或企业限制。此时应将发布标记为缺少已批准对象，并回到构建和审批流程。新构建即使源码提交相同，也可能受到依赖、运行器、环境变量或构建过程变化影响；只有当审批制度明确以内容摘要为准，且来源证明和其他条件仍满足时，才可考虑复用内容级批准。这是团队策略，不是 GitHub 自动结论。

怎样证明部署确实用了获批对象

可以用一组不依赖“最近一次”的检查设计发布门禁：审批前保存来源提交、运行身份、尝试号、产物 ID 与摘要；部署时按这些标识获取对象；验证下载摘要；对有来源保证要求的发布，检查 attestation 的仓库、工作流、提交和环境条件；若内容经过任何变换，为最终对象重新生成摘要并按审批策略处理；部署记录保存最终被使用的对象标识。缺失字段、摘要不匹配、来源不符合、对象过期或最终内容变化，都应走明确的停止或重新审批路径。

这些是拟议检查，不是本篇执行的测试。可以把验证场景列为：指定运行正常下载；同名但不同提交的产物不能替换批准对象；摘要不匹配会阻止部署；产物缺失时不会静默重建；重跑使用新的运行尝试和内容时必须重做审批绑定；下载后重打包会产生新的最终摘要。再检查部署回执能否反向找到源提交和审查记录。测试应断言系统实际的失败状态，而不只是确认日志里出现了提示。

对于发布与回滚，产物身份只是链条的一段；还要确认运行配置、数据库迁移和回退条件。发布产物与回滚核对讨论了这部分。令牌权限也会影响谁有机会上传、删除或发布对象，可以结合流水线令牌权限检查。引用这些文章不表示本篇的假设工作流已实测。

评审发布流程时，可以让审核人从审批记录出发，反向指出本次上线的源码提交、工作流运行、具体产物、摘要和最终部署目标。如果必须靠“当时最新的那个”或文件名来猜，身份链仍未闭合；如果各项标识能对应，但缺少来源信任策略或授权对象，摘要也没有替团队完成批准。这两种缺口应分别修复。
