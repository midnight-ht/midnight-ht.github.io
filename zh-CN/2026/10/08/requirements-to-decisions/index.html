需求写了“支持导出”，为什么开发、测试和运维理解不同？

把“导出”拆成数据范围、时间语义、文件格式、权限、完成状态和失败责任，再据此制定可观察的验收场景。

正文

核心要点

  • “支持导出”不是完整行为契约；范围、快照时间、格式、授权、状态与失败责任都需要可观察的决定。
  • RFC 4180描述常见CSV格式，不保证所有电子表格和下游解析器一致；CSV语法正确也不能替代面向表格使用场景的公式注入评估。
  • 同步、异步、权限复查和文件保留期应由时限、风险和支持责任决定；示例策略不是实测结论。

导出需求要能验收，至少得说清六件事：谁能导出、哪些数据、以哪个时间点为准、文件采用什么格式、任务怎样完成，以及失败后谁负责。只有“支持导出”四个字时，开发、测试和运维填进空白的答案可能各不相同。先确定用户能观察到的结果，再选择同步请求、后台任务或存储方式；本文中的订单报告只是设计示例，没有实际实施或执行测试。

需求评审里常有这样的对话：产品说“给管理后台加导出”，开发理解成点击后返回 CSV，测试问没有记录时按钮是否可用，安全同事问被撤销权限的用户能否使用旧下载地址，运维想知道任务卡住由谁重试。大家并没有误解“导出”这个词，而是这个词把若干独立决定压缩成了一个动词。

数据范围与时间点要怎样约定？

先写清请求主体、筛选条件、字段、排序和时区。比如“导出订单”可能指当前用户有权查看的订单，也可能指某个部门在指定日期创建的订单；退款状态取下单时、任务开始时还是文件生成时的值，也会改变结果。示例需求可以写成：“对用户选择的部门和日期区间，按创建时间升序导出下单时符合条件的订单；金额使用订单原币种，并包含退款状态列。”这是需要业务确认的候选契约，不是通用规范。

还要选择数据快照语义。假设用户周一发起导出，队列到周二才运行；期间订单被修改。文件应反映周一提交条件时的数据，还是周二执行时可见的数据？前者需要保留足以重建请求时数据的快照或版本依据；后者比较简单，却可能让用户重复运行同一条件得到不同文件。财务对账、后台运营和临时筛查的要求不同。不能只写“导出最新数据”，因为“最新”缺少可验证的时间边界。

CSV、Excel 和下载链接分别承诺什么？

RFC 4180 在 2005 年发布，是信息性 RFC，并明确声明它不是互联网标准。它描述了常见 CSV 约定，例如可选表头、记录分隔和字段中包含逗号、双引号或换行时的引用规则；文件注册类型为 text/csv。RFC 4180 因此“提供 CSV”仍需说明字符编码、分隔符、表头、日期和数值表达、空值，以及团队承诺兼容哪些消费端。RFC 描述常见格式，不保证每种电子表格和下游解析器表现一致。

CSV 的语法正确也不等于对表格软件安全。OWASP 的 CSV Injection 页面指出，不可信数据在单元格开头含有公式触发字符时，电子表格可能把它当作公式；分隔符和引号处理也可能把输入拆成新的单元格。OWASP 还说明不存在同时适合所有表格应用和程序化下游的通用净化策略；针对 Excel 的某些处理会留下影响后续程序导入的数据变化。OWASP CSV Injection 所以需求应记录导出面向“供人用表格打开”还是“供程序继续导入”。如果二者都要支持，可能需要不同的格式或明确的安全转换与兼容边界，不能把一个模糊的“导出”当作两种场景都已满足。

HTTP 响应也有自己的契约。RFC 6266 规定 Content-Disposition: attachment 表示接收方预期提示保存文件；filename 和 filename* 可提供建议文件名，后者处理国际化文件名。RFC 6266 这只解决响应如何表达下载意图和建议文件名，不决定文件内容、权限、保留时间或链接是否安全。验收时需要检查中文文件名、浏览器实际保存行为和服务器端响应头，而不是只看下载接口返回 200。

什么时候同步返回，什么时候建立后台任务？

同步适合能够在请求时限内稳定完成、结果较小、失败可直接重试的任务；它少了任务表、状态接口和清理逻辑。它也必须回答客户端超时后服务端是否继续做事、用户再次点击会不会生成第二份文件。若工作耗时显著或需要显示进度，Google AIP-151 建议长时间 API 操作返回可查询的 operation，而不是让调用方一直等待；operation 的元数据可承载进度和部分失败，执行错误可放在 operation error 中。该 AIP 是 Google API 设计指南，不是所有 HTTP 接口的强制标准；文中约十秒的判断是经验规则，不是通用门槛。AIP-151: Long-running operations

以假设的订单报告为例，若用户选中的范围可在同步请求时限内完成，就返回文件并记录一次请求结果；若耗时可能跨越页面连接，就返回任务标识，状态至少包括 queued、running、succeeded、failed。若仅部分行无法导出，团队需决定是整份失败、跳过并报告，还是生成可下载文件并附带错误清单。不能把部分失败藏在“成功”状态里。任务接口还要定义重复提交：同一幂等键是复用既有任务，还是允许重新生成；空结果是成功的空文件，还是业务错误。以上都是方案设计，不能据此声称某队列或服务已经实现。

后台任务增加了执行队列、进度、重试、超时、结果保存和清理责任。若系统没有人查看积压或处理持续失败，异步并不会自动让功能可靠，只是把用户等待变成运维等待。需求中应给出可执行的操作边界：谁收到积压告警、重试是否可能重复读取或写入、失败记录保留多久、超过多长时间由谁介入。阈值需按实际负载和业务时限确定，不能把示例值直接复制成生产承诺。

权限撤销和文件过期由谁验收？

导出权限至少涉及创建任务和取得结果两个时刻。创建时检查一次，无法自动回答用户几小时后权限被撤销怎么办。一个候选政策是任务按创建者当时的数据范围生成，下载时再次检查当前权限；另一种候选政策是让被授权的受托人下载，但需记录委托关系。需求所有者要在二者中作出选择，并说明审计记录包含什么。长期有效的对象存储地址如果绕过下载鉴权，就可能把链接有效期变成隐式授权期限。

文件也应有保留和删除规则：生成后可下载多久，过期后用户看到什么，后台清理失败由谁监控，工单或审计是否要求保留元信息。文件是否删除与任务状态是否仍可查询是两个问题；清掉文件后，用户可能仍需要看到完成时间、行数或错误摘要。验收可以分别检查“过期文件不可下载”“任务记录仍显示过期”“清理失败可被发现”，而不是用一个含糊的“定期清理”覆盖三者。

空结果、部分失败和格式变化怎么进入验收？

拿“导出 3 月的订单”作假设例子，验收讨论可以逐项设定可见证据：有数据时表头、列类型、排序和行数符合定义；没有数据时文件还是提示由业务决定；用户不能导出其他部门记录；任务等待期间可查询状态；部分行失败时结果和错误清单一致；文件过期后拒绝下载；CSV 中逗号、换行、双引号、非 ASCII 字符和以公式字符开头的外部文本分别进入测试样例。对于程序消费者，还要核对解析后字段与源记录一致，而不只比较文件是否能打开。

反例尤其有用。若测试只断言响应码是 200，空文件也能让测试通过；若只用干净样本，公式注入和引用符边界不会出现；若链接测试都在权限未变化的同一账号下进行，撤权后的结果仍是未知。每个测试应绑定到一条已决规则，失败时能指出是业务范围、编码、授权、任务状态还是交付头部的问题。用规则、示例和未解问题组织验收讨论，可以参考Cucumber Example Mapping，但这不要求项目采用 Cucumber。

评审结束前要留下哪些决定？

最小决策表可以按“问题、选择、验收证据、责任人、未决项”记录：范围和快照决定查询行为；格式和兼容目标决定序列化；同步或异步决定接口状态与值班责任；权限政策决定创建和下载检查；保留期决定存储清理；部分失败政策决定结果和错误报告。每项选择应说明为什么适合当前读者、数据量、时限和合规边界。若答案尚未确定，要写明由谁何时决定；不能把未决规则偷偷交给实现者。

例如，团队可以提出“超出请求时限的报告转为可查询任务、结果保留 24 小时、下载时复查权限、部分失败生成错误明细”的候选方案。24 小时只是示例数字，需依据敏感程度、重跑成本和支持流程确认；它不应被文章读者直接当作建议值。对应验收至少应覆盖任务超时、权限撤销、过期访问和部分失败四条路径。测试用例在这里是待执行的设计，不代表本文实际运行过。

当需求能说出用户拿到什么、为何拿到、何时失效、异常时看到什么以及谁处理失败，开发才有可实现的边界，测试才知道要观察什么，运维才知道报警指向谁。若会上仍只剩“做个导出”，下一步不是挑 CSV 库，而是把那个未回答的问题和决定责任人写回需求单。随后可把已确认规则连接到失败路径质量门禁；它是检查设计承诺的入口，不替代导出本身的业务验收。
