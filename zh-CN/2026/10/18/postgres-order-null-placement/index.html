时间倒序后，为什么没有完成时间的记录排在最前？

补齐 PostgreSQL 降序空值位置、独立列方向与并列规则，用四行输入区分排序、资格和跨页保证。

正文

核心要点

  • DESC 默认空值在前，可显式指定位置。
  • 每列方向独立，末尾 DESC 不回溯到前列。
  • 空值位置不决定记录资格，也不冻结翻页间变化。

按 completed_at DESC 展示最近完成的任务，没有完成时间的行却先出现，这是 PostgreSQL 默认 NULLS FIRST 的结果。写出 NULLS LAST 只解决位置；若列表只能展示已完成记录，还需独立筛选资格。排序方向、空值位置与记录状态，应在同一个列表合同里分别写清。

降序的默认选择也包括空值位置

PostgreSQL 18 排序文档规定，默认排序把空值视为大于非空值，因此 DESC 默认空值在前，其他默认方向空值在后。NULLS FIRST 与 NULLS LAST 可以显式选择位置。本文依据第十八版，没有执行查询或测量数据库性能。

假设管理列表有四条任务：两项在不同时间完成，一项还没有完成时间，另一项与最新任务同一时刻完成。这个输入同时区分时间方向、空值位置和并列顺序，避免只拿两条时间不同的正常数据验证。下方字段和任务均为教学假设。

WITH jobs(id, completed_at) AS (
  VALUES
    (1, TIMESTAMP '2026-10-01 09:00:00'),
    (2, TIMESTAMP '2026-10-02 09:00:00'),
    (3, NULL::timestamp),
    (4, TIMESTAMP '2026-10-02 09:00:00')
)
SELECT id, completed_at
FROM jobs
ORDER BY completed_at DESC NULLS LAST, id DESC;

这段 SQL 未执行。按指定规则推演，顺序应为四、二、一、三：最新时间先，时间相同再按编号倒序，空时间最后。若去掉 NULLS LAST，三会在有时间的行之前；若再去掉编号排序，四与二之间的次序没有在这份查询中明确。验收应对照具体标识，而不只是截图看起来“日期大致倒序”。

数字编号在本例唯一，因此能区分并列。真实查询若连接后同一编号出现多行，或所谓编号只是非唯一业务序号，就不能沿用这个证明。应选择能区分实际结果行的键；编号大小也不能未经业务约定代表完成先后，它在这里仅负责同时间下的稳定区分。

放到最后，不等于从列表中排除

如果栏目严格叫“最近完成”，空时间行仍在第四位，可能依然不符合需求。NULLS LAST 没有筛掉它，只改变位置。可以在业务确认完成时间代表资格的前提下，用相应筛选排除无值行；若系统有独立状态字段，则应按实际状态模型确定筛选，不要自动以某个字段是否为空替代完成状态。

这也说明同一查询可能服务不同产品。一份所有任务总览可以保留空时间，放末尾并显示真实原因；一份待处理队列可能需要未完成项在前；一份完成历史则可能根本不接纳未完成项。三者不应只靠界面标题不同，查询却共享同一个含义不明的默认排序。

空时间还可能来自历史资料缺失或某类任务没有完成阶段。把它统一标成“等待处理”，已经从存储缺失推断了业务状态。应找出空值来源并定义展示；确实未知时保留未知，比让用户误以为还有任务需要执行更准确。排序表达式无法补回缺失的领域信息。

多列方向怎样一起生效？

每个排序表达式独立决定方向和空值规则。ORDER BY completed_at, id DESC 表示前者默认升序、后者倒序，末尾 DESC 不会回溯修饰第一列。这项文档规则值得在评审中直接展开，而不是让维护者根据逗号位置猜测整体方向。

同样，某一列的 NULLS LAST 也不是所有列的统一策略。如果第二列允许空值，还需决定它在第一列相同时放哪边。示例采用非空唯一编号，只为减少这一层分支；真实表是否满足条件要读约束，不能从字段名 id 就认定已满足。

列表还可能先按优先级升序，再按完成时间倒序。此时最新时间只在相同优先级内部比较，不能把整页称作严格全局最新。需求文字应与排序优先顺序一致，否则每列写得都正确，整体含义仍与标题冲突。可以用高优先旧记录和低优先新记录做最小对照。

全部时间相同，或者全部为空，怎么办？

这时首列没有区分能力，后续键就决定顺序。若需求只是有可重复解释的展示，合适的唯一键可以完成此任务；若需求是还原真实业务先后，唯一键并不能凭空创造不存在的时间信息。应明确哪一种保证，不能因为页面每次排列相同就声称历史顺序已恢复。

分页需要再增加变化语义。即使当前结果有唯一顺序，翻页之间新增、删除或修改完成时间，仍可能影响后续页。本站分页顺序与跨页一致性讨论这个边界。本篇没有提供可直接使用的游标条件，也不把 NULLS LAST 当成防止跨页重复遗漏的全部修复。

索引与性能同样需另验。显式排序表达了结果要求，不证明当前数据规模下已经使用合适计划。比较方案时保留实际条件、行数和计划证据；不能仅因添加一个关键字，就宣称查询变快或者变慢，更不应为了利用某个既有索引而悄悄改变空值业务位置。

待执行检查至少覆盖不同时间、同时间、全空值、混合空值，以及多列方向相反的样本。分别核对进入列表的标识集合、完整顺序、空值展示原因与并列键的唯一性。资格检查通过后再检查排序，避免对错误集合排得很整齐，却误记为需求已满足。

用上面四行就能把两种需求分别写成预期。任务总览接纳一到四，顺序为四、二、一、三；若本例把有完成时间作为已完成的资格，完成历史只接纳一、二、四，顺序为四、二、一。两种预期共享同一批输入，却有不同的标识集合。测试若只断言首项是四，两份查询都可能通过，遗漏资格错误；只断言返回三行，也可能漏掉错误保留三而删掉一的情况。应同时比较集合和完整序列，并核对缺失标识的原因。若真实状态字段与完成时间不一致，则先添加对应反例，由业务决定接纳依据，不能拿本例简化条件覆盖生产状态模型。这种分开断言比只在页面看空值移到了底部更能说明修改兑现了什么。

历史文章这次补充了完整输入与反例，但没有真实数据库执行记录。提交列表改动时，应能用一句话说明：哪些记录可以进入，先比较哪列，每列怎样处理方向和空值，还相同的行怎样区分。让这些决定在查询和页面文字中对得上，最近、待处理与未知才不会被同一个 NULL 混成一种状态。
