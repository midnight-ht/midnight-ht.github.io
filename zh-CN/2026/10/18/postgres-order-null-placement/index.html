时间倒序后，为什么没有时间的记录排在最前？

PostgreSQL 降序默认把空值放在前面；将空值位置、多列方向和同值顺序写进查询，并先确认空值的业务含义。

正文

把列表改成完成时间倒序，没有完成时间的记录却排在最前，未必是数据库排序出错。PostgreSQL 的默认规则会让 DESC 中的空值先出现。若界面要表达“最近完成”，应同时写清有值的方向与空值的位置，不能只改一个排序关键字。

DESC 连空值位置也有默认选择

PostgreSQL 18 的排序文档说明，默认把NULL视为比任何非空值都靠后：升序时空值在末尾，降序时空值在前面。可以用NULLS FIRST或NULLS LAST显式指定。这里引用的是第十八版的查询语义，没有对某个实际数据库执行性能测试。

假设一个管理列表有两项已完成记录和一项等待处理记录，等待项的completed_at为空。直接按完成时间倒序，等待项会按默认规则出现在有时间的记录之前。这是假设输入，不是系统故障截图。如果产品真正想先处理未完成项，这个位置可能合适；如果栏目叫“最近完成”，就需要重新确认筛选与排序的含义。

下面只展示一个候选表达式，表名和字段均为示例，本文未执行：

SELECT id, completed_at
FROM jobs
ORDER BY completed_at DESC NULLS LAST, id DESC;

这句话让有完成时间的记录按倒序排列，再把空时间项放后面，并以编号处理相同时间的情况。它没有排除空时间项；若栏目只能出现已完成项，还需由符合业务的筛选条件决定哪些记录进入输入集合。排序位置与记录资格是两件事，不能靠把空值放到末尾就宣称列表全是已完成任务。

多个排序列各自有规则

官方文档还指出，每个排序表达式的方向独立决定。写成ORDER BY completed_at, id DESC，前一个表达式仍默认升序，末尾的DESC不会同时修饰前面的列。空值位置同样应贴着相应表达式理解。多人维护查询时，明确写出关键方向和空值规则，比依赖读者自行补全默认值容易评审。

编号作为次级排序也不是万能答案。它应该能在当前结果集合里区分仍然相同的行，才有助于得到确定顺序；连接后重复的编号、业务上并不唯一的序号，都需要另找合适的键。这个建议针对顺序可解释性，不承诺某个分页方案因此不会重复或漏行。

空值的业务含义先于视觉位置

同一个NULL可能表示尚未完成，也可能表示历史数据没有时间，或者该类型任务根本没有这个阶段。如果把这些记录一起放在最前，并标成“待处理”，界面就从存储缺失推导出了业务状态。需求评审应先确定空值来自什么条件；必要时用独立状态字段表达，不要让排序替代状态建模。

COUNT与非空输入的区别讨论统计时的空值口径，列表同样需要说明哪些行被纳入、空值代表什么。计数和排序不能互相验证全部规则：数量正确，仍可能把一批不属于当前栏目的人或任务排到了正确位置。

验证可以准备不同时间、相同时间、全部空值和混合输入，核对产品约定的顺序；若使用分页，还需观察数据在翻页期间变化的影响。这些测试本文均未执行。查询计划与索引是否合适，也需要用实际数据另行判断，不能从一条语义正确的SQL推导出性能已经达标。

调整列表之前，先把需求写成一句完整的话：哪些记录进入列表，按什么字段先后排列，没有该值时放在哪里，仍然相同的记录怎样区分。SQL中能找到这几个决定，页面上的“最新”才有明确含义。
