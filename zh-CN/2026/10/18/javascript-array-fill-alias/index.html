Array.fill 放入对象，为什么改一项会影响其他项

fill 重复的是同一个对象引用；独立可编辑行需要各自构造对象，并检查嵌套状态和断言预期。

正文

三条编辑行都显示不同位置，改第一条的状态却像把三条一起改了。若数组由 Array.fill 填入一个对象，先检查这些位置是否指向同一对象。数组有三个位置，并不意味着已经创建三个独立的可编辑状态。

重复一个值，不等于反复构造

MDN 的 fill 参考明确说明，如果填充值是对象，每个位置都会引用该对象；fill 也会修改被调用的数组。下面是未经执行的示意代码，用来区分对象先创建一次，与每次调用映射回调时创建对象这两种安排。

const sharedRows = Array(3).fill({ checked: false });
const separateRows = Array.from({ length: 3 }, () => ({ checked: false }));
sharedRows[0].checked = true;

第一行在传入 fill 之前已经求得一个对象，填充时重复使用它。第三行修改这个对象的属性，于是其他位置再次读取同一属性时，也会看到相应值。这里没有三次神秘的修改，也不需要先假设页面事件被重复绑定。先把对象引用关系画出来，往往能缩小排查范围；是否还存在框架或事件问题，需要真实运行证据。

另一种动作是把某个数组位置直接替换为新对象。替换该位置与修改原对象的属性，并不是同一操作。诊断时应查看赋值的左边究竟是数组槽位，还是槽位所引用对象的内部字段；只记录“修改了第一项”，会把两类行为混在一起。

独立外层，还要看内部归属

Array.from 的参数说明描述了逐项调用映射回调的安排。在回调里创建外层对象，可以表达每行有自己的状态。但如果回调把同一个预先创建的标签列表放进每行，标签列表仍是共享的。修复应覆盖真实会修改的层级，不应只比较两个外层对象不相等就停止。也不必为一行只有布尔字段的草稿引入庞大复制工具，增加读者无法解释的状态转换。

如果共享本来就是需求，例如多行都引用同一份只读配置，应把共享关系写清楚，并约定谁可以修改它。不能由“fill 不复制对象”推出“fill 永远不能接对象”。真正的问题是调用者想要独立状态，却把同一份可变状态分配给了多个使用者。

验收要同时守住未修改的行

拟议用例可以只修改第一行，然后检查第一行的目标字段改变，其他行的对应字段保持原值。存在嵌套列表时，再对列表增删进行同类检查。单纯断言第一行修改成功，无法证明其他行没有被连带修改；只检查数组长度，也没有触及对象归属。本篇没有运行 JavaScript 或页面测试，这些是需要落实的验收设计。

预期对象同样需要独立。如果测试预期也引用了正在被修改的对象，实际值与预期可能一起变化，测试就可能失去判断作用。本站十月十三日的参数化输入别名讨论另一种共享输入情境，语言不同，对象归属问题却相通。

修复提交应说明初始化时创建了什么、哪些内部成员仍有意共享，以及验证了哪种修改。若问题仅发生在草稿行，先改草稿行的构造，不要把所有数据无差别地复制一遍。独立性要落在可解释的对象边界上，不能由页面行号或变量名称代替。

如果编辑行最终需要保存，还应按照稳定的业务标识核对提交值。位置上的第一行变化正确，不代表保存时仍对应正确记录；排序或删除行以后，也需要确认独立对象与行身份没有被混为一谈。这是拟议检查，尚未执行。
