Array.fill 复制引用：编辑行与矩阵该怎样初始化

从重复引用解释草稿行、嵌套标签和二维矩阵，补足稀疏map、撤销快照及稳定身份保存的验收边界。

正文

核心要点

  • 数组位置不同不代表可变对象独立。
  • 逐行工厂还需覆盖嵌套列表与矩阵单元格。
  • 行间隔离、撤销快照与保存身份分别验收。

Array(3).fill({ checked: false }) 创建三个数组位置，却只把同一个对象放到这些位置。修改第一项对象的 checked，另外两项再读取时也会看到变化。要让三行能够独立编辑，应在每一行的构造过程里创建它负责的可变状态，再检查嵌套列表或矩阵行是否仍然共享。

fill 重复使用已经求得的值

ECMAScript 的 fill 算法对指定范围的索引写入同一个 value，最后返回接收数组。它没有要求为对象反复构造副本。对象字面量在调用 fill 前已经求值一次，数组的位置再多，也不会让这次求值自动重复。本文以普通可写数组为前提，示例没有执行，不是页面故障实测。

const shared = Array(3).fill({ checked: false });
const separate = Array.from({ length: 3 }, (_, index) => ({
  id: `draft-${index}`, checked: false, tags: []
}));
shared[0].checked = true;
separate[0].tags.push('urgent');

按这份代码推演，shared 的三个位置都能读到 checked 为 true。separate 每次回调创建新的外层对象和新的 tags 列表，第一行增加标签不应改变后两行。这里的 draft 标识只是示意，正式数据的身份规则需要另外定义，不能把数组下标当成持久化记录身份。

排查时应区分“改属性”和“换位置”。shared[0].checked = true 修改多个入口共同引用的对象；shared[0] = { checked: true } 则只让第零个位置指向另一个对象，其他位置仍指向原对象。两种动作都可能被工单写成“改第一项”，但它们沿引用关系造成的后果不同。先记录赋值目标，可以避免把数据共享误判为事件重复触发。

外层工厂没有自动解决嵌套共享

Array.from 的算法规定映射回调逐项产生结果。回调里新建外层对象，可以分开外层身份；若却把一个预先创建的 tags 数组塞进每个对象，标签状态仍然共享。修复范围应沿实际编辑操作寻找，而不是看到两个外层对象不相等就结束。

假设导入预览有三条草稿，允许分别勾选并添加问题标签。如果 checked 在独立对象上，勾选验收可能通过；但 tags 来自同一个模板数组，修改第一行标签仍会影响其他行。一个只检查勾选状态的测试无法证明标签编辑也独立。应先列出用户会执行的修改：改布尔、改嵌套字段、追加列表，再为这些修改确定归属边界。

二维矩阵会把问题放大。Array(2).fill(Array(3).fill(0)) 只构造一次内层数组，再让两行引用它；修改第一行第二列，第二行同一列也能看到。即便最里层填的是数字，外层填充值仍是数组对象。较清楚的构造是在外层回调里创建各自行数组；若单元格本身又是可编辑对象，内层也需逐格创建对应对象。

const matrix = Array.from({ length: 2 }, () =>
  Array.from({ length: 3 }, () => ({ value: 0 }))
);
matrix[0][1].value = 9;

上面只表达两个层级都需要独立可变状态的假设需求，不是所有矩阵的最优实现。若单元格只是数字，内层用数字填充就可以清楚表达初始化，不必为每个数创建对象。若多个单元格有意共享一份不可变规则，应明确共享的规则与可编辑值分开，而不是无差别深拷贝所有对象。

浅复制与深复制也必须对应编辑边界

把 shared 展开成新数组，只复制外层位置，不会切断它们指向同一对象的关系。把模板对象浅展开成每行的新对象，可以分开外层，但内部列表仍可能共享。要不要复制更深，不该按“复制越多越安全”决定；应由哪些成员需要独立修改、哪些身份需要保留，以及数据包含什么类型决定。

盲目通过序列化往返制造所谓深复制，还可能改变未被这份表示支持的数据。与其引入一个难以说明的通用复制动作，草稿模型已知时直接写工厂往往更易审查。对复杂数据可评估合适的复制方式，但应明确它对类型、循环引用与身份的处理，本文没有验证任何通用复制库或性能收益。

拟议验收应只修改第一行，然后同时检查第一行的新值和另外两行未变。对矩阵，既检查同一行的其他格，也检查另一行的对应格；对嵌套列表，检查追加、删除是否只作用于目标。预期数据不能引用正在修改的对象，否则实际与预期可能一起变化。数组长度和外层引用不等，只能证明局部性质，不能替代这些行为断言。

为什么 Array(n).map 工厂没有创建任何草稿？

Array(n) 建立长度，却没有为每个位置创建自身索引属性。map 会跳过不存在的位置，所以不能把 Array(n).map(() => ({...})) 当作逐项构造。可用 Array.from 的类数组长度与映射回调表达意图，或先明确填充再映射；关键是让回调真正覆盖需要创建的每个位置，而不是只看 length 正确。

该追问与共享引用不同：前者可能根本没创建元素，后者创建了多个位置却共同引用一个对象。验收先检查每个预期索引是否存在，再检查对象及嵌套状态是否独立，才能区分“没有草稿”和“草稿共享”。相关的flat 与缺槽讨论转换怎样处理不存在的位置，不应把读到 undefined 当成已构造元素的证据。

撤销功能还会暴露另一类共享。假设页面把当前草稿数组浅复制一份当作初始快照，随后修改第一行对象；若快照仍指向同一对象，点击撤销时拿回的已经不是初始状态。这里即使每条草稿彼此独立，也不代表当前版本与历史版本独立。行间隔离和时间版本隔离，需要分别决定。

若产品支持撤销，应让快照策略覆盖会变化的成员，或者采用能明确保留历史值的状态更新方式，再验证修改后的当前值与撤销目标没有一起变化。测试预期也应来自事先记录的字面状态，而不是那份共享快照。没有撤销需求时，不必为了假想功能引入版本系统；这条反例只是说明独立性的对象边界必须带着实际操作一起定义。

如果编辑结果需要保存，最后还应排序或删除一行，再按稳定记录标识核对提交内容。独立对象不自动保证保存归属正确；对象身份、页面位置和业务身份分别承担责任。本文没有执行 JavaScript、界面编辑或保存流程。修复提交应列明新建了哪些层级、仍有意共享什么，以及目标行变化而其他行保持不变的验收预期。
