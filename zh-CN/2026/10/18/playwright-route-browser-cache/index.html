route.continue 透传了请求，为什么缓存测试仍不可信？

透传路由仍禁用 HTTP 缓存；用同一商品图片设计无路由冷暖访问，区分 Service Worker 和状态码证据，并限定 unroute 的推论。

正文

核心要点

  • 启用 routing 会禁用 HTTP 缓存，continue 不撤销该条件。
  • 暖访问必须在明确的无路由会话中建立首次访问历史。
  • Service Worker、状态码与解除路由都不能单独证明缓存复用。

假设公共 fixture 给每个页面安装 page.route("**/*", route => route.continue())，缓存用例随后连续访问同一张商品图片。即使处理器没有改响应，启用路由已经禁用了 HTTP 缓存，第二次网络活动不能直接归咎于服务器。先检查公共测试条件，再分析缓存头或增加等待时间。

透传保留了请求去向，没有保留所有环境条件

Playwright 的 page.route 参考明确说明，启用 routing 会禁用 HTTP 缓存。这不是只有 fulfill 或 abort 才触发的限制。处理器调用 continue，说明该请求继续向网络前进，并不撤销注册路由所引入的环境变化。

本文于二〇二六年十月二十七日核对在线参考，未启动 Playwright 或采集缓存记录。项目应保留锁定的 Playwright 和浏览器版本，并检查页面、上下文和公共 fixture 的实际配置。不能从本地一段测试源码看不见 route，就推断共享层从未安装路由；HAR 重放等安排也应列入条件清单。

这里需要分开两种有用测试。通过路由构造接口超时或错误响应，可以验证商品页如何提示用户、能否重试。检查浏览器第二次获取同一资源时怎样复用响应，则要有符合该问题的缓存环境。两条用例可以围绕同一页面，但前者通过不能承担后者的结论。问题不在于使用 mock 本身，而在于测试名称承诺了没有被检查的行为。

给同一张图片建立冷、暖访问路径

设想商品详情页引用固定 URL 的图片 /assets/item-42.webp，服务器计划发送允许一定时间内复用的响应。用例要求是在同一受控会话内，首次访问建立状态，随后通过正常页面导航再次请求同一资源。这里的资源、策略和操作均是假设，没有真实浏览器结果。

测试开始时建立一个专用上下文，确保这条路径从未安装页面或上下文网络路由；把离线回放、响应替换和公共拦截 fixture 排除在这份用例配置之外。新的上下文用来解释起点，但不会天然拥有暖缓存。必须先进行首次访问，等待所关心的资源完成，再按既定操作触发第二次使用。每次重新建上下文都会改变会话条件，不能这样“隔离”后还声称正在验证同一会话的暖访问。

第一次记录资源完整 URL、请求条件、响应缓存字段和服务端访问记录的对应关系。第二次保持资源身份不变，记录实际用户动作与相应观察。若应用为每次访问附加不同查询参数，或第二次生成了另一个资源地址，那么测试先改变了资源身份，不能直接把结果解释成同一资源未被复用。若选择刷新，还要说明哪一种刷新操作；不要把具有不同缓存行为的操作混在一个计数里。

下面只是实验结构，未执行，不给出跨浏览器通用的命中断言。

create dedicated context with no network routes
record browser version and Service Worker policy
visit product page; identify exact image response
perform the chosen normal navigation
visit again in the same context
compare resource identity, response information, and server observations
close context after collecting evidence

最终断言应对应被批准的需求。例如验证某个有效期内是否允许正常复用，就需区分完整响应传输、条件验证与客户端复用等路径。服务端计数是有用线索，却可能受代理、预加载和其他请求干扰。只看到页面请求事件或两次显示相同状态码，也不足以定义浏览器到底传输了什么。实际浏览器可取得哪些可靠指标，需要用该版本的工具证据说明。

HTTP 缓存、Service Worker 与页面数据缓存不能混算

同一官方参考说明，page.route 不会拦截已由 Service Worker 拦截的请求，并建议在需要拦截时使用阻止 Service Worker 的配置。这是拦截测试的建议，不是所有缓存验收的默认目标。若产品依赖离线页面，阻止它恰好会移走要验的功能。

可以把目标写得更具体：一条路径检验不含 Service Worker 的浏览器 HTTP 缓存，另一条路径在应用真实的 Service Worker 条件下检验离线或更新策略。前者若主动阻止 Service Worker，应在报告里保留这个条件；后者需要观察安装、激活、控制与资源版本，不用前者的成功替代。二者也不代表某个 CDN 或客户端业务数据缓存已验收。

反例是用 route.fulfill 构造一份带缓存头的响应，再看到页面正确显示图片，就宣称生产浏览器缓存工作正常。这个结果可以验证页面接受了构造内容，却没有恢复路由已改变的缓存前提。另一个反例是只在 Node 的 HTTP 客户端检查响应头。它能证明该次请求收到的字段，不会替浏览器完成存储与后续使用的验证。

先 unroute 再测，能证明环境恢复吗？

不能只凭这一步下结论。这里核对的参考说明启用 routing 禁缓存，并没有提供“移除处理器后，所有缓存状态与从未启用时相同”的通用恢复保证。不要用一个没有文档支持的逆命题安排核心验收。更容易解释的方案是从新的、从未安装路由的专用上下文开始，明确建立首次和后续访问。

这会增加测试路径的维护成本，但能让失败归因更可靠。若必须复用既有复杂 fixture，应先单独验证其缓存条件，保存实际版本和对照证据；不能为了少维护一个 fixture，把有路由的业务测试重新命名为缓存验收。移除路由也不保证缓存一定命中，服务器策略、资源变化与浏览器决策仍须核对。

第二次访问失败时，还要保留“为什么应该允许复用”的前提。若第一次响应要求不得存储，测试应验证这份限制，而不是把未复用当成浏览器缺陷。若业务希望更新后的图片立即可见，则需要另行定义资源版本与失效策略，不能同时要求永久复用同一地址又无条件获得新内容。把缓存有效期、更新动作和用户能看见的版本放在同一份验收条件里，可以减少与页面状态缓存混淆的机会。

失败报告至少保留精确资源身份、两次操作、路由与 Service Worker 条件、有效响应策略，以及客户端和服务器的可对应观察。本站BrowserContext 会话隔离解释了上下文范围；这里的补充是，隔离起点之后仍要主动建立所需历史。把第一次与第二次的证据放在同一条有条件的路径上，才能判断测试工具究竟是在观察缓存，还是先改变了缓存环境。
