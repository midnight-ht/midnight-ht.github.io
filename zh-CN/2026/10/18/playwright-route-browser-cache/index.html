route.continue 透传请求，也不等于还原缓存环境

启用 Playwright 网络路由会禁用 HTTP 缓存；缓存验收应单独保留无路由环境并记录请求层次。

正文

请求在 route.continue 后继续访问服务器，并不说明浏览器缓存行为保持原样。如果目标是验收浏览器 HTTP 缓存，公共 fixture 中的一条透传路由，也可能让测试运行在另一种条件下。先核对测试环境，再解释第二次访问为何仍有网络活动。

观察请求的安排也会改变条件

Playwright 的 page.route 参考明确指出，启用路由会禁用 HTTP 缓存。这是对路由机制的说明，不以处理器有没有修改响应作为条件。因而“没有 mock，只调用 continue”不能单独作为缓存环境仍然有效的证据。这里采用本次查阅的在线文档，具体项目仍需记录其 Playwright 和浏览器版本。

假设一套公共 fixture 为所有页面注册路由，以记录地址并继续请求。某条用例访问两次同一资源，然后从请求数量推断缓存失效。这个推断至少漏掉了测试工具改变的前提：它已经启用路由。示例没有执行，既不证明某个服务器的缓存头错误，也不证明取消路由后该资源一定会被复用。

我建议把这条用例的名称改得更准确：如果它依赖路由注入响应，就验收注入条件下的页面行为；如果它要验收浏览器缓存，就建立没有网络路由的专用路径。两者可以针对同一业务页面，但证据不能混用。把测试分开需要维护成本，却能避免一个绿色结果承担它没有检查的承诺。

先明确正在验收哪一层

检查服务器发送了哪些缓存字段，与检查浏览器是否按预期复用响应，并非同一个问题。前者可以聚焦协议输出，后者还需记录首次访问、后续访问、上下文状态和资源身份。观察到请求也不应只剩下一个计数；验收应说明哪些行为符合需求，以及证据从哪里采集。这里没有给出跨所有浏览器通用的缓存命中判据。

Service Worker 也要单独记入条件。同一份官方参考指出，page.route 不会拦截已被 Service Worker 拦截的请求，并建议在需要请求拦截时阻止 Service Worker。但缓存验收如果本就包含站点离线策略，照抄这一设置会改变目标。因此应该先说明测试要覆盖浏览器 HTTP 缓存、站点离线行为，还是其他缓存层，再决定配置。

失败报告应能还原用例前提

拟议记录包括测试与依赖版本、公共 fixture 内容、是否安装页面或上下文路由、Service Worker 策略，以及两次访问各自的操作和观测。测试前先检查共享配置，可比在失败后无限延长等待更直接。使用新的受控上下文也便于说明起始状态，但它是否适合预期的暖缓存流程，仍需由测试步骤明确建立。

本篇没有启动 Playwright、抓取网络记录或验证任何缓存配置，也不承诺移除路由就能解决所有重复请求。页面在客户端保存的数据与 HTTP 缓存也不应混称；若实际问题来自另一层，应为那一层补证据，而不是用路由文档推断全部原因。

本站十月十七日的下载事件与文件保存也讨论了相近的验收问题：观察到一个事件，不等于目标状态已经成立。缓存用例应在评审中给出环境和证据的对应关系，尤其标出公共路由何时安装；这比笼统写一句“已测试缓存”更可复核。
