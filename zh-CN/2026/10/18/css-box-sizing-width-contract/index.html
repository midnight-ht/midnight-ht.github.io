给组件宽度一个可验收的尺寸口径

内容宽度与边框外沿采用不同计算口径；先确认盒模型，再排查外边距、长内容和布局约束。

正文

组件文档说宽度三百像素，先说明它指内容还是边框外沿。内边距和边框是否计入声明宽度，取决于 box-sizing。把宽度设成百分之百仍出现溢出时，应先核对这个口径，再决定是否缩窄组件。

同一个宽度，装进去的东西不同

MDN 的 box-sizing 文档说明，content-box 的声明尺寸针对内容，内边距与边框加在外面；border-box 把内容、内边距与边框计入声明尺寸，但不包含外边距。属性初始值是 content-box，不过实际元素可能被浏览器样式或项目规则覆盖，因此排查要看最终计算样式。

假设容器可用宽度为三百像素，里面一块普通卡片宽度百分之百，左右各有十六像素内边距和一像素边框。在没有其他尺寸限制的纸面模型里，content-box 的边框外沿合计三百三十四像素。改用 border-box 后，三百像素包含这些内边距与边框，内容可用宽度相应减少。这里的数字用于解释计算，没有运行浏览器或测量真实页面。

示意样式只表达局部组件的选择，不是已经应用到某个项目的修复：

.panel {
  box-sizing: border-box;
  width: 100%;
  padding: 16px;
  border: 1px solid;
}

修改盒模型，也是在修改内容空间

如果设计稿给出的是组件外沿，这种写法容易让声明与验收使用相同单位。但内容区域随之变窄，标题、输入框和错误说明仍需重新排版。不能因为外沿回到容器内，就宣布整个交互已经修好。对固定高度组件尤其应检查内容是否仍有足够空间，而不是顺手把溢出隐藏。

已有组件库可能有自己的约定。对全站增加统一规则之前，先找出依赖内容尺寸计算的部件，并核对嵌入页面与第三方部件的边界。局部修复更容易说明变化范围；统一约定更便于后续使用，两者需要结合存量成本选择。这里没有证据支持“全局改一行一定安全”的承诺。

border-box 没有承诺所有东西都能装下

外边距仍在这个尺寸之外。内容本身的不可断行片段、子元素的固定尺寸，以及父级布局约束，也可能需要单独排查。遇到这些情况，应定位究竟是哪一个盒子超过可用区域，不能继续减少父级百分比，直到某张截图看上去没有滚动条。这样的百分比补丁会把尺寸关系藏在偶然的文字长度里。

拟议检查可先记录容器可用宽度、元素计算后的盒模型和发生溢出的子节点，再使用真实长度的标题、帮助文字与错误消息进行操作。建议同时查看窄窗口和放大后的任务路径，核对用户是否还能读到信息并完成提交。本站十月十三日的放大与重排检查解释了为何一张手机截图不能代替这些验证；本文没有执行它们。

组件接口可以把约定写成一句话：传入宽度指边框外沿，外边距由使用位置负责；若采用其他模型，也应同样清楚地表达。接着给出内容变长时的处理策略和适用容器条件。验收时比较的就不再只是一个 CSS 数字，而是这个数字对应的边界，以及边界内的任务是否保留。

若组件在错误或禁用状态下调整边框粗细与内边距，也要纳入样本。外沿维持同一宽度时，这些变化会重新分配内部空间。建议让状态切换发生在同一段真实文字上，核对换行和操作区是否仍符合组件约定。
