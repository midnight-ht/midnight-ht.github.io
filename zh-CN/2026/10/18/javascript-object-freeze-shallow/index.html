Object.freeze 后，嵌套配置为什么仍会变化？

浅冻结限制当前对象自身的属性；嵌套对象、共享引用和访问器仍需明确边界，再决定是否采用递归处理。

正文

顶层配置已经调用 Object.freeze，嵌套开关却仍能改变，并不矛盾。冻结会处理传入对象自身的属性，不会自动沿着每个引用把整张对象图冻结。评审配置保护时，先分清不能替换一个引用，与不能修改引用指向的对象，是两项不同要求。

固定引用没有冻结引用的目标

MDN 的 Object.freeze 说明把这种行为称为浅冻结。它限制对象自身属性的增加、删除与重新赋值；当属性值是另一个对象时，那个对象的内容仍可能变化。该页标注二〇二六年五月更新，这里引用普通对象属性的行为，不把所有特殊对象都概括成同一种数据容器。

下面是假设配置的说明代码，本文未执行：

const policy = { upload: { enabled: true } };
Object.freeze(policy);
policy.upload.enabled = false;

最后一行改的是upload所指向对象的enabled属性，不是在给policy的upload属性换一个目标。因此，仅检查顶层是否已冻结，不能证明嵌套开关受到保护。若需求是整个配置快照在使用期间保持不变，就需要另外处理嵌套层，或采用适合项目的不可变更新策略。

还要注意共享引用。假设两个配置都指向同一份上传选项，从其中一个入口修改子对象，另一个入口也会读到变化。顶层冻结既不会复制这份子对象，也不会自动切断别名。这个情境同样没有运行；它提示代码评审应追踪对象来源，而不能只搜索某处是否出现freeze调用。

递归处理也需要限定边界

对于完全由普通对象、数组与原始值组成的受控配置树，逐层处理可能符合需要。但把一个递归函数贴到任意运行时对象上，并不能因此宣布深层不可变完成。MDN提醒对象图可能存在循环引用，递归策略需要处理已访问对象，也可能遇到本来不应该冻结的对象。是否遍历函数、访问器或外部持有的共享对象，都需要明确范围。

访问器尤其容易让“值不再改变”这个说法过头。MDN说明，冻结并不停止getter计算出的结果随外部状态变化，也不阻止setter被调用。对于配置输入，若希望快照语义清楚，可以限制数据形状，并在边界处生成受控数据；这是设计建议，不是freeze额外提供的能力。

复制和冻结也不应混成同一个动作。复制关心是否还共享底层引用，冻结关心某个对象上的修改限制。浅层复制后保留同一子对象，再冻结外层，仍没有获得独立且深层固定的快照。如果系统只需约束调用者不要替换顶层字段，浅冻结可能已经足够，没必要为一个不存在的要求引入通用遍历逻辑。

先写允许什么变化，再选实现

可用一个权限配置评审作为假设任务：运行中的请求是否可以看见热更新，历史审计是否必须保留当时值，测试夹具是否允许各用例独立修改？三个用途对共享与变更的要求不同。不能从“配置”这个名字就推导出必须全局冻结，也不能把冻结当成外部授权检查。

从需求到可核对决策强调先确定验收边界。这里的验证也应分别观察顶层替换、嵌套修改、共享别名，以及所选数据形状的边界情况。没有执行这些检查时，应写成待验证项，而不是声称配置已经安全。

本文未运行上述代码，也没有提供经过生产验证的深冻结工具。若下一次评审出现“已经freeze，所以不会变”，可以要求补全对象范围：哪些对象被冻结，哪些引用仍共享，哪些变化本来就被允许。把这三个答案写清楚，才能决定浅冻结是否满足当前需求。
