Object.freeze 后嵌套配置仍会变：先划清快照所有权

从热更新与历史审计拆解浅复制、冻结、共享引用、访问器和递归边界，用对象图而非单个布尔值验收。

正文

核心要点

  • 浅冻结限制当前对象，不会复制或递归冻结引用。
  • 历史快照先分离所有权，再限制自己拥有的数据。
  • 访问器依赖和对象图别名应进入验收。

顶层对象调用 Object.freeze，只能限制这个对象自身的属性，并不会沿引用自动冻结所有子对象。更容易漏掉的是所有权：如果旧审计快照与可热更新配置共享同一个子对象，冻结外层既没有复制它，也没有阻止另一个持有者修改它。先决定哪些值必须独立，才有资格讨论深层冻结。

固定属性引用，不等于固定目标内容

ECMAScript 的 Object.freeze 算法调用 SetIntegrityLevel；完整性级别处理对传入对象的自有属性设置限制，并阻止扩展。普通数据属性不能再通过正常赋值改变，属性不能删除或随意重配。这个处理没有递归调用每一个属性值上的冻结。

本文依据检索当日标为 ECMAScript 2027 的 living draft，示例限定为普通对象与数组，均未执行。假设审计系统要保存“提交当时”的上传限制，而运营仍可热更新当前配置。下面的浅层拷贝与冻结不能形成所需快照。

const live = { upload: { maxFiles: 3 } };
const audit = Object.freeze({ ...live });
live.upload.maxFiles = 8;

外层对象已经不同，upload 指向的目标却仍是同一个。把 audit.upload 替换成另一对象，与修改其目标的 maxFiles，走的是两份不同的属性描述符。冻结 audit 保护的是前者。若审核只断言 audit 已冻结，就会给一个仍变化的历史值错误背书。

不要把这个问题归因于展开语法“不可靠”。展开完成了它的浅层复制合同，只是合同没有包括复制整个对象图。把外层换成其他浅拷贝方式，仍会共享子对象。需要的不是换一个看起来更深的 API 名称，而是写清快照包含哪些值，以及它们来自哪一份可变状态。

先复制边界，再冻结自己拥有的数据

对这个假设场景，若上传配置只有已知的普通字段，可以在审计边界有意构造独立数据，再冻结对应层。下面代码仍未执行，它只针对这一份已知形状，不是通用深冻结库。

具体构造可以先创建只含数值上限的新子对象，对这个子对象调用冻结，再将其放进新的审计外层并冻结外层。两层都由本次构造创建，原来的运营配置保留自己的可变状态。

这里先读取 maxFiles 原始值，再放进独立子对象，因此后续热更新不会通过共享子对象进入 audit。若字段变成含可变列表的对象，构造逻辑也必须跟着调整。不能因为今天只有一个数值字段，就给将来的任意数据形状作深度不可变保证。接口模式变更时，快照构造与验证属于同一项维护责任。

反过来，直接递归冻结 live.upload，可能让运营配置自己的热更新失败。审计函数无意中冻结外部仍持有的数据，会越过所有权边界。复制负责分离身份，冻结负责限制修改；两者要按要求组合。对于本来就允许多个使用方只读共享的规则对象，保留共享并冻结可能合适，但前提是各方同意这份限制。

递归不是一行通用承诺

对象图可能有循环与重复引用。递归遍历若没有已访问集合，可能无法结束；若遇到共享对象，又必须决定自己是否有权冻结它。函数、宿主对象与拥有内部状态的容器，也不能仅凭“是对象”就被归入普通配置数据。本文不提供涵盖所有 JavaScript 值的通用算法。

即使选择递归，遍历哪些属性也需要合同。只遍历 Object.keys 会遗漏不可枚举与符号键；直接读取每个属性值还可能触发 getter。若快照输入应是纯数据，可以在边界限制形状、拒绝访问器并生成受控对象。这个限制把问题从任意运行时对象缩小到可审核的数据，而不是把任意对象变成安全输入。

数组本身被冻结时，修改索引或长度受限，但数组里的对象仍有各自的属性。若权限列表存成对象数组，冻结列表不能自动固定每项规则。站内Array.fill 与共享引用说明多个位置可以指向同一对象；快照设计也要检查一项修改会不会经由别名影响其他位置或历史版本。

冻结访问器，为什么读到的值仍会变？

冻结访问器属性，固定的是描述符本身，不会把 getter 的所有外部依赖都冻结。假设 getter 返回另一个可变变量的当前值，外部变量变化后再次读取仍可能得到不同结果。setter 的存在也不因外层冻结自动变成不可调用。因此“对象被冻结”不能普遍改写成“每次读取都得到同样值”。

如果审计需要记录某次观察，应在边界把观察值保存为普通数据，而不是保存一段以后继续计算的 getter。若业务本来需要动态读取，就应明确它不是历史快照。这两类用途都可能合理，错误在于让同一个“配置对象”名称同时承担动态来源和固定证据，而调用者看不见区别。

严格模式下，某些被禁止的赋值会抛错；其他语境中的失败表现需要按语言规则核对。验证不应只期待错误出现，还要确认目标值没有改变，并确保异常没有被上层忽略后继续错误操作。没有抛异常，不能直接证明修改成功；抛了异常，也不能证明另一条共享引用没有改动子对象。

验收观察对象图，而不只看一个布尔值

拟议检查分别覆盖顶层替换、嵌套修改、外部别名修改、数组项修改、循环输入与访问器依赖变化。Object.isFrozen 可以帮助核对一个对象的完整性级别，但不能代替逐层所有权和读取行为的验证。对于审计快照，还应在热更新以后读取旧快照，确认数值保持提交时的独立预期。

没有运行这些示例、提交审计记录或验证生产配置。下一次评审“已经冻结”时，应要求指出被冻结的是哪些对象、哪些引用仍共享、哪些读取仍依赖外部状态；这三项答案决定它能否作为固定快照。
