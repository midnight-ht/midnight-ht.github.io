LEFT JOIN加上IS NULL，为什么仍救不回这位客户？

用四组客户区分匹配、过滤与补空行，检查明细基数，并构造没有合格订单的名单。

正文

核心要点

  • 没有合格匹配与过滤后没有结果不同。
  • OR IS NULL不会为已匹配客户重新补行。
  • 同时核对客户集合、明细数量和非空缺失标识。

甲有已付订单，乙只有未付订单，丙没有订单。付款条件移到WHERE后再加“订单标识为空”，丙回来了，乙仍然消失：乙已经匹配到未付明细，不会额外生成一条空订单。要保留全部客户并只展示合格订单，应把合格条件纳入匹配定义，而不是事后用空值猜哪些客户该回来。

先把四组客户的预期写出来

PostgreSQL 18表表达式文档区分外连接匹配和后续过滤：左连接为没有任何合格匹配的左侧行补出右侧空值；WHERE再检查所得行，只保留条件为真的结果。它不是看见LEFT JOIN就永久保护客户，而是在特定阶段产生一个保留集合。

增加第四位客户丁：他有两笔已付订单，另有一笔未付订单。若需求是全部客户及其已付明细，预期应保留甲、乙、丙、丁四个客户标识，明细行数则可能是五行。乙与丙分别保留一条没有合格订单的结果，丁保留两条已付明细。客户集合与明细行数从一开始就不是同一个计量单位。

下面是完整的假设输入和一种查询，没有在数据库执行。标识与状态用于纸面推演，订单id在这组数据中非空：

WITH customers(id) AS (VALUES (1),(2),(3),(4)),
orders(id, customer_id, status) AS (
  VALUES (11,1,'paid'),(21,2,'unpaid'),
         (41,4,'paid'),(42,4,'paid'),(43,4,'unpaid')
)
SELECT c.id, o.id AS order_id
FROM customers c
LEFT JOIN orders o
  ON o.customer_id = c.id AND o.status = 'paid'
ORDER BY c.id, o.id;

按文档语义推演，客户一对应订单十一，客户二和三的订单列为空，客户四对应四十一和四十二。这里把状态写在ON中，是因为它定义什么叫合格匹配。不是建立“所有右表条件必须进ON”的通用规范；若报表明确只要有已付订单的客户，排除乙与丙反而可能符合需求。

为什么OR IS NULL只救回一部分？

把ON改成仅按客户标识匹配，再使用WHERE筛已付订单，乙先与订单二十一匹配，然后因状态未付被过滤；丙没有匹配，会得到空值行，但付款比较不为真，同样被过滤。补上“或订单id为空”后，丙的空行能留下，乙的订单id却是二十一，不满足放行条件。

关键在于空值行产生的时机。左连接不是在WHERE删光一个客户的明细之后，再回头补一条空行。它在匹配阶段决定是否没有任何右行满足ON。乙既然已经满足只按标识连接的条件，后面的过滤就不会触发第二次补行。把两步画成数据流，比靠联接名称猜结果更可靠。

反例还包括对右表可为空的业务字段做缺失判断。订单存在，但某个备注或状态字段本身为空，不等于没有订单。判断是否匹配，应选择在真实右表合同中保证非空的标识，或使用更直接表达存在关系的方案；不能把示例中非空id的性质默默推广到任意列。

一客一行是另一个查询要求

丁的两笔合格订单让客户重复出现，这不是左连接失效。若页面要展示客户及每笔明细，重复客户标识是明细结构的一部分；若要每位客户一行，则需明确选择聚合、独立查询明细或存在性判断。随手加DISTINCT可能删去业务需要的信息，或在选择了不同订单列时根本不能去重。

分页也受这个选择影响。按联接明细分页，丁可能占两个位置，客户层面的页大小就不再等于结果行数。应先确定分页对象是客户还是订单，再设计查询与总数。本站的COUNT输入口径讨论如何区别行和非空输入；本题则应先固定客户集合与匹配明细，避免统计函数替错误集合背书。

只核对总数尤其危险。假设乙丢失，同时丁多出一行，总行数可能恰好与预期相同。验收应比较客户标识集合、每客明细数和具体订单标识，不能把“都是五行”当作等价证据。测试样本必须同时含只有不合格明细和完全无明细，两类人在错误查询里可能有不同命运。

怎样只找没有已付订单的客户？

这是不同于“展示全部客户”的追问。可以先在ON中只匹配已付订单，再筛右侧保证非空的订单标识为空。对上述假设数据，预期留下乙和丙，排除甲与丁。丁虽然也有未付订单，但存在已付匹配，不应进入“没有已付”的名单。直接筛未付状态会把丁误收，也会漏掉完全无订单的丙。

也可以用NOT EXISTS表达“没有满足这些条件的订单”。选择哪种写法，应比较可读性、字段约束和实际执行计划，而不是在没有测量时宣称某一种必然更快。若使用左连接缺失检查，要把匹配条件和缺失标识的非空保证一起提交审查；这比只附一行IS NULL更能说明正确性。

权限或租户条件也需要确定作用范围。若客户集合只允许当前租户，左表范围必须本来就符合授权；把租户条件加到订单匹配中，并不会自动缩小客户范围。此处是查询评审的工程边界，不是新增数据库授权证明。不能把保留更多客户当成任何情况下都正确，需求与可见范围先决定应该留下谁。

还有一种误差连客户集合与每客数量都能躲过：错误连接把甲的订单挂给乙，双方仍各有一条明细。此时需要按客户与订单的键值对核对归属，不能只检查两个独立的标识集合。测试结果最好逐组列出预期关系，再比较缺失、多出和错配三种差异；查询排序只便于阅读，不会修正错误关系。

拟议验证先运行完整输入，核对全部客户报表，再核对无合格订单名单；随后增加空业务字段、多笔合格明细和混合状态。保存SQL、版本、原始结果与预期差异，语义确认后再测性能。本文未执行查询，不提供通过记录。评审条件移动时，要求作者解释乙为何应该留下或离开；这个“有明细但没有合格明细”的对象，才是区分匹配与过滤的关键样本。
