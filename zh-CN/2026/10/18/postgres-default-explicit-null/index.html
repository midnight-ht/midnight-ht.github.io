列有 DEFAULT，为什么显式 NULL 仍然留下空值

沿请求到SQL区分省略、DEFAULT与NULL，补齐非空拒绝、更新保留、默认迁移与历史回填条件。

正文

核心要点

  • 省略、DEFAULT 与 NULL 是三种写入意图。
  • 非空约束拒绝空值，不替调用方回落默认。
  • 改变默认不等于回填历史空值。

假设草稿状态默认 pending，API 把未提供的 status 补成 NULL 后发出 INSERT。默认规则仍在表上，却没有收到省略字段的输入。普通列的 DEFAULT 不会把显式 NULL 自动改成默认值；排查需要沿着请求、映射对象和最终 SQL 找到意图在哪里改变。

省略、DEFAULT、NULL 走三条路径

PostgreSQL 18 的默认值规则规定，新行没有为某列提供值时采用默认，数据操作也可以明确要求列默认。INSERT 参考进一步说明省略列的处理。这里讨论普通可空列，不含触发器等额外写入转换，也不把标识列或生成列的特殊规则混入状态字段。

以下是未执行的教学 SQL。三条记录只用来对照写入意图，没有真实草稿服务或数据库运行结果。

CREATE TABLE drafts (
  id integer PRIMARY KEY,
  status text DEFAULT 'pending'
);
INSERT INTO drafts (id) VALUES (1);
INSERT INTO drafts (id, status) VALUES (2, DEFAULT);
INSERT INTO drafts (id, status) VALUES (3, NULL);
SELECT id, status FROM drafts ORDER BY id;

按文档推演，前两条应得到 pending，第三条保留 NULL。第一条没有给状态，第二条明确要求数据库自行计算默认，第三条明确提交空值。它们不能因为界面上都没有显示一段用户输入，就被归并成一种“空”。空字符串又是一个独立的具体文本值，是否允许必须由接口规则决定。

假设客户端原始 JSON 只有 id，DTO 初始化却为每个可选属性填 null，持久层随后把这些键全部写入列清单。数据库收到的是第三条路径，已经无法得知请求曾经省略 status。真正排查应保留经过脱敏的字段存在性、最终列清单与参数类型，不能只对比建表默认是否还在。这个定位方向不代表所有 ORM 都采用同一映射规则。

加上 NOT NULL，为什么也不会替你回落？

如果状态不允许空值，应把业务校验与 NOT NULL 对齐；显式 NULL 会被约束拒绝，而不是自动重试默认。默认负责没有值时采用什么，非空约束负责能否保存空值，两个责任并不相同。给列同时写 DEFAULT 和 NOT NULL，不会创造一条“遇空自动补默认”的隐藏规则。

反例是捕获所有数据库写入异常，再把 status 改 pending 重试。原错误可能来自主键冲突、其他字段约束或连接问题，这种兜底会掩盖真正失败，甚至改变调用方明确要求清空的含义。如果产品决定创建时 null 也代表采用默认，应在接口合同里明说，并在写入前有针对性地映射；不要以宽泛异常处理临时发明这条规则。

另一种做法是在 SQL 值表达式中使用 COALESCE。它可以实现某个显式的空值替换政策，但那是查询写出的政策，不是列 DEFAULT 自动生效。若应用和数据库各维护一份 pending，后来数据库默认改成 queued，两个入口可能分歧。默认的所有者应可识别，迁移时覆盖新旧程序并存的写入行为。

创建时缺省，更新时还要缺省吗？

创建和更新不能共用一份未经讨论的映射。假设记录现为 approved，更新请求只修改标题；如果 DTO 把缺失状态补成 pending，旧状态就被重置。PostgreSQL 的 UPDATE 的列修改规则说明，SET 没提到的列保留原值；应用应决定如何把请求省略映射为不修改，而不是随手复用创建默认。

明确要求重置默认时，可以在适当 SQL 中使用 SET status = DEFAULT；明确清空则是 NULL，但要服从约束。这三种更新意图同样需要对照输入存在性。批量导入、管理后台和旧客户端都应按相同合同检查，不能只让主接口正确，另一个入口继续把所有空白统一处理。

请求里的字符串 DEFAULT 也不是 SQL 关键字。若把它作为普通参数绑定，数据库收到的是文本，不应为了方便把任意客户端字符串直接拼进 SQL 语法。需要“恢复默认”的接口动作时，应定义一个受控的业务操作，由服务端生成允许的语句结构；数据值与指令必须保持可区分。

ALTER COLUMN SET DEFAULT 会替历史 NULL 回填吗？

不会。ALTER TABLE 文档明确说明，设置或移除默认只影响后续相关数据操作，不改变表里已有行。假设三个历史 NULL 分别代表旧导入缺失、用户合法清空和待人工确认，新增默认不提供识别这三种来源的信息，更不等于批准统一回填。

若确需修复，应先用可审查条件圈定哪批行属于错误缺失，记录修复身份、预期范围和回退方式，再以受控更新处理。不能只写 WHERE status IS NULL 就推断选中的都是坏数据。修复期间还要堵住新的错误写入，否则回填完成后仍会继续产生 NULL。这里是数据修复设计建议，没有执行任何批量更新。

拟议验证从四个创建输入开始：省略、显式 null、允许状态、非法状态。逐一核对原始字段存在性、最终 SQL 列清单、参数和落库值，再在可空与非空两种结构下比较接纳或拒绝。更新则先设置 approved，再发送省略状态、清空、具体值和重置默认，确认每条意图都保留。最后改默认检查旧行不变、新写入按新默认处理。

部署顺序同样影响默认所有权。假设数据库先把默认改成排队，旧版应用仍明确写待处理，新版应用开始省略状态，短时间内就会产生两种状态。迁移验收应覆盖这段并存期，确认下游同时理解它们，或先统一应用写入政策再变更默认。不能只验证新版单独运行时正确，就宣布已有入口全部迁移。

观察时可以按应用版本和入口记录写入意图，但不要把完整私密请求直接写入日志。字段是否存在、选中了哪条受控语句路径与关联任务编号，通常比无差别保存原始负载更便于定位。诊断记录的内容、访问和保留期限应跟项目规则一致；本篇没有建立日志采集服务。

这些用例尚未运行，若真实表存在触发器、域约束或特殊映射，应先补齐结构再确定预期。本站行数与非空输入计数解释 NULL 如何影响统计，但统计异常只能提示后果。要修复本题，应能指出调用方表达了什么、SQL 实际传了什么、哪一层有权决定默认，以及历史空值是否真的属于这次修复范围。
