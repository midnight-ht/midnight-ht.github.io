列有 DEFAULT，为什么显式写入 NULL 仍没有默认值

默认值处理省略与显式请求默认值的情况；接口应保留缺省、清空和具体取值之间的差别。

正文

表里已经配置默认值，接口创建的记录却还是空。先看生成的 INSERT：省略字段、写 DEFAULT、写 NULL 是三种不同的输入。默认值不是对所有空值进行兜底替换的规则，数据库也不能替接口猜测调用方的意思。

默认值需要一个触发入口

PostgreSQL 18 的默认值说明指出，新行没有为某列提供值时，该列使用默认值；数据操作也能明确要求默认值。INSERT 参考进一步说明省略列和 DEFAULT 的处理。这些规定没有把显式 NULL 改写为列默认值。这里讨论普通可空列，暂不加入触发器或其他额外写入逻辑。

假设草稿表有状态列，默认状态为待处理。下面三条是说明语义的示意语句，没有建立表或执行 SQL。第一条省略状态，第二条要求默认状态，第三条明确提交空值；在这个假设下，第三条不会因为列有默认值就自动得到待处理。

CREATE TABLE drafts (id integer, status text DEFAULT 'pending');
INSERT INTO drafts (id) VALUES (1);
INSERT INTO drafts (id, status) VALUES (2, DEFAULT);
INSERT INTO drafts (id, status) VALUES (3, NULL);

真正排查时，要拿到应用最终发出的列清单和参数，而不只看建表文件。假设请求中没有状态，但数据访问层把所有缺失字段补成空值后再写入，那么默认值的入口已经在应用中被改掉。数据库配置仍然存在，调用路径却没有采用它。这是待核验的定位方向，不是对任何 ORM 的统一行为判断。

接口先保留字段的三种意思

建议把未提供、明确清空、提供具体状态分别定义。新增操作中的未提供可以采用系统默认；明确清空是否允许，要由业务契约决定。如果不允许，接口应给出能解释的校验反馈，存储约束也需要与之匹配。不能把清空悄悄改成待处理，再告诉调用方输入已被忠实保存。

更新操作还需要单独约定。更新时没传某字段，常见意图是保持原值；把新增时的缺省策略直接搬过来，可能重置已有状态。这是接口设计建议，不是说所有更新协议都必须如此。批量导入、旧客户端和管理后台也应按同一份契约审查，避免某条入口把缺失、空字符串和空值合并成一个状态。

若确实要在应用层填默认值，就明确谁维护默认规则。数据库和应用各写一份可能随版本演进发生分歧。选择数据库作为默认值来源时，应检查实际写入是否省略了该列；选择应用作为来源时，应承认这是应用规则，并为迁移期间的新旧版本安排验证。

验收覆盖从请求到落库的变化

拟议用例需要分别发送省略字段、明确空值、明确状态，以及不被允许的状态，查看最终参数和保存结果。更新场景再补上原值保留与清空检查。本文没有执行这些用例；若表上有触发器、生成列或专用转换逻辑，应先补齐真实结构，再作判断。

已有空值也不应仅凭“表里配置了默认值”就批量回填。先确认旧空值代表未知、历史缺失还是允许清空，再决定数据修复范围；新增写入策略和历史数据处理是两个待审查的决定。空值对数量统计的后果，可继续读十月十七日的行数与非空输入计数。审查应停在一条可追踪的路径上：调用方表达什么，应用传出什么，数据库实际保存什么。
