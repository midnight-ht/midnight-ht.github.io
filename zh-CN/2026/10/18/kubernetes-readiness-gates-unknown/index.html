容器 Ready，Pod 仍等待：readinessGates 要有写入与撤销责任

缺失按 False，Unknown 也不满足门槛；沿注册确认、状态写入、陈旧 True 与恢复责任排查。

正文

核心要点

  • 每条自定义门槛与容器就绪都必须满足。
  • 缺失、False 和 Unknown 是不同诊断入口。
  • 旧 True 的有效期与撤销责任需要业务设计。

容器已经 Ready，Pod 仍可能因自定义 readinessGates 没有满足而等待。所有容器就绪之外，每条列出的门槛都必须为 True；缺失条件按 False 处理，显式 Unknown 也没有满足门槛。排查应沿着条件的生产与更新责任走，而不是只盯着容器探针反复重启。

规格里的名字不是业务结果

Kubernetes 的 Pod 生命周期文档将就绪门槛列为容器检查之外的信号，能力从一点十四版本起稳定。规格声明需要检查的条件类型，状态记录相应结果；仅仅增加一个条件名，不会自动产生负责判断业务状态的控制器。

可以把它理解成两份不同的契约：应用团队声明何时才允许 Pod 被视为就绪，状态写入者提供当前证据。kubelet 根据已存在的记录判断门槛，没有义务替业务联系外部系统或推断注册成功。若没有安排写入者，发布等待恰好符合所声明的要求，而非机制失灵。

缺失、明确为假、无法确定，是三个诊断入口。缺失先查谁应该写以及是否写到正确对象；为假先查业务条件为何没有满足；未知先查写入者无法判断的原因。它们在就绪判断上都没有通过，却不应在故障报告里被合并成一句“探针失败”。

用外部路由注册建立完整状态链

设想未运行的教程：容器能处理内部请求，但平台要求外部路由注册完成才允许整个 Pod 就绪。规格声明以下门槛，名称仅用于示例，没有部署到集群。

spec:
  readinessGates:
    - conditionType: delivery.example.test/RouteRegistered

容器探针先通过，Pod 状态中还没有该条件，此时门槛未满足。注册控制器随后向路由系统发出注册请求，取得能够对应当前 Pod 的确认，再通过有权限的状态更新路径写入同名条件为 True。只看到控制器发出了请求，还不能越过确认阶段；把请求发送成功误记为注册完成，会让门槛失去业务意义。

假设请求被拒绝，控制器应保留可定位原因并写入相应非真状态，而不是无限沉默。若确认超时、无法知道注册是否成功，可以表达未知，并继续按既定策略查询。若状态里的名称拼错，即便有一条 True，kubelet 仍找不到规格要求的类型。排查要把规格条件名、状态类型、Pod 身份与控制器处理记录对齐。

对象身份也不能只用名称。发布替换后可能出现同名业务实例，但它已是不同 Pod；旧注册回执不应未经核对就证明新对象就绪。控制器应让外部对象与当前工作负载身份可靠关联，并防止迟到响应把旧结果写到新对象。这些是工程设计建议，具体实现需按客户端、API 和业务模型验证。

状态更新路径为何要单独验收

官方文档说明应用或操作器可以通过 API 的 PATCH 动作设置自定义条件，并提醒这不同于普通对象修改；实现时要采用适当的状态接口和权限。代码中构造了一个 True 对象，不等于服务器接受了更新，更不等于 kubelet 已经观察到它。

应区分业务确认失败、API 权限不足、更新冲突、类型名称不匹配和观察延迟。每种错误的修复对象不同。直接扩大权限可能掩盖错误的身份设计，持续重启容器也无法修复独立控制器没有权限的问题。先看状态写入响应与实际 Pod 状态，再决定沿业务系统还是控制平面调查。

门槛适合表达确实影响能否承接工作的额外条件。若只是事后统计信息，不应轻易挂到就绪上，让遥测系统故障直接阻止业务服务。相反，若外部注册是正确接流量的必要前提，省略门槛又可能过早宣布可用。选择依据是这条条件与服务承诺的因果关系，而不是多一道检查看起来更严谨。

控制器失联后，旧 True 会自动过期吗？

不能假定自定义条件自带业务租约或失联超时。True 是已经写入的状态；若业务要求确认只在一个有效期内成立，就需要设计负责重新评估和撤销的机制。门槛机制本身不会替团队决定外部注册证据何时过期。

假设路由注册后来被删除，而控制器停止工作，Pod 状态仍留下旧 True。容器探针可能继续成功，两个绿色信号也没有证明路由注册仍存在。设计可要求周期核对、外部事件触发或独立失联检测，但必须说明谁会写回非真、控制器不可用时由谁发现。单个控制器既失联又被期待自行宣布失联，会留下责任空洞。

撤销政策还需要处理短暂抖动。每次查询超时立即摘流，可能扩大依赖故障影响；长时间保留旧 True，则接受了陈旧证据风险。应按业务容忍度选择宽限和告警，不在通用教程里编造统一秒数。无论选择哪种，都把新确认、失效与恢复条件写成可测试规则。

怎样覆盖门槛生命周期的失败分支

拟议验证先让容器就绪，再分别提供缺失、False、Unknown、True 的门槛记录，观察 Pod Ready 是否符合预期。随后安排全部门槛满足但容器未就绪的反例，防止误以为自定义 True 能覆盖容器检查。多个门槛时，任何一个未满足都应保留等待理由。

还需测试注册成功但状态更新失败、状态写错类型、控制器重启、旧响应迟到、业务证据撤销与恢复。每一步分别保留外部确认、API 响应、实际 Pod 条件和目标业务路径，避免用一张绿色控制台替代完整证据。手工改 True 若用于紧急处置，必须有明确业务判断与操作记录，不能称作注册故障已经修复。

本文没有连接集群、修改状态或验证流量。与发布产物及回滚一样，就绪只是交付承诺中的一层；下一步应为每条门槛写清生产者、成立证据、撤销者与恢复办法，再让真实集群验证这些责任能否在失败时持续履行。
