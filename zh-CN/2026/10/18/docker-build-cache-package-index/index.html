Docker 缓存与包索引：同层安装之后，还要决定何时重跑

同层更新安装修正旧索引失配，整层仍可复用；分开选择安装阶段刷新、基础镜像拉取与最终版本核验。

正文

核心要点

  • 合并update与install保证执行时的顺序，不保证每次重新执行。
  • no-cache与pull分别处理构建层复用和基础镜像刷新。
  • 安全更新要追到最终包版本、镜像身份及实际服务版本。

把 apt-get update 与安装写在同一条 RUN 中，可以避免安装步骤重跑时沿用另一层的旧索引；整条指令若命中缓存，仍不会重新访问软件源。Docker 包索引是否新鲜，要看安装层是否执行、基础镜像是否刷新以及实际装入什么版本。重建成功只能证明得到一个构建结果，不能代替这三项判断。

同层解决的是更新与安装脱节

Docker 的 Building best practices以 Debian 系镜像说明，应把索引更新与软件包安装放在同一个 RUN。若先单独更新，随后另一层安装，修改安装清单时，上层索引更新可能被复用。本文于二〇二六年十月二十四日重读官方资料，对原教程作实质修订；以下命令和场景均未执行，不声称已构建镜像或安装安全更新。

假设一个镜像最初更新索引，再安装下载工具。数日后，维护者只在安装行增加压缩工具。索引行没有变化，安装行却发生变化；构建器可能复用前者而执行后者。日志出现安装输出，只说明安装步骤执行，不能推断前一层也重新取过索引。软件源是否仍提供索引指向的版本，又会影响安装结果。

下面将两个有关联的动作放进同一步。示例基于支持这些命令的 Debian 系基础镜像，仅展示安装步骤，不提供完整 Dockerfile。

RUN apt-get update \
    && apt-get install -y --no-install-recommends curl unzip \
    && rm -rf /var/lib/apt/lists/*

连接符让安装以前面的更新成功为前提，清理索引则用于避免把无用索引留在最终层里。但这些动作只有该步骤实际执行时才会发生。没有命中缓存与命中缓存是两条路径，不能把命令文本里写着 update，等同于这一次构建真的执行了 update。

用两次修改检查构建究竟复用了什么

假设第一次采用上面的合并指令构建，第二次没有任何相关输入变化。第二次可以直接复用整层，包括之前已经安装的文件；这时不存在一份本次新下载的索引。第三次把安装清单加入另一工具，合并指令改变，重新执行时才会先更新索引再安装。这个纸面矩阵区分了“同层保证执行顺序”和“每次保证执行”两种承诺。

Docker 的 Build cache invalidation 文档明确说明普通 RUN 缓存不会因为过去一段时间而自动失效，重复相同安装命令并不保证获得较新软件包。若这次发布目标是重新查询软件源，需要主动选择缓存失效范围，而不是等待日历跨过某个日期。

选择可以从交付目标出发。日常只修改应用代码、依赖版本政策没有变化时，复用审定的依赖层可能合理；要求纳入某次安全修复时，应使相应安装阶段重新执行，并检查目标版本是否真的存在于所用软件源。时间间隔由团队政策决定，本文没有一个适用于所有项目的强制刷新周期。

多阶段构建还可以把依赖安装放在具名阶段，按需要使用构建器支持的 --no-cache-filter 限定刷新阶段。完整 --no-cache 则放弃更广的构建缓存。两者影响的步骤与实际项目结构有关，应检查所用构建器的版本和参数支持，不把示意开关当作任何构建环境都通用的操作保证。

禁用缓存会自动拉取新基础镜像吗？

不会仅因 --no-cache 就保证基础镜像是远端最新版本。官方最佳实践另列 --pull 用于尝试获取较新的基础镜像，因此基础镜像选择和后续构建层复用应分别处理。若更新目标包含两者，应明确提出拉取与重新执行的要求，并记录实际解析的镜像身份，而不是只保存一条命令字符串。

固定摘要的基础镜像适合控制输入，但固定不等于自动得到最新安全内容；变更摘要本身需要审核。固定软件包版本也类似：它约束想安装的版本，不保证软件源永远保存该包。复现旧产物与获取新版本是不同目标。对已审定产物直接按身份部署，可能比重新构建更准确地表达“使用这一份版本”。

一个反例是同时添加 pull 和禁用缓存，然后看见构建成功就宣布安全修复完成。实际软件源也许尚未提供目标版本，目标包可能根本没有安装在最终运行阶段，或者运行服务仍指向旧镜像。开关触发了动作，但修复结果必须用最终包版本、镜像身份以及实际服务版本核对，不能用动作数量替代证据。

刷新失败时，不要回退成看起来成功

若索引下载失败，示例中的安装不会继续。此时应该保留失败原因，按发布政策决定延期、使用已经批准的旧产物还是修复软件源；不能为了得到绿色构建，把更新错误忽略掉，再宣称完成本次依赖刷新。旧产物可以有明确的使用决定，但它不应被标成新的更新结果。

同样，重试构建也需要观察它是否再次执行了目标步骤。若第一次失败后更换了构建节点，缓存来源与基础镜像解析可能不同，结果不能仅凭同一个 Dockerfile 名称视为相同。为需复现的构建保存输入身份、软件源策略和实际版本；无法永久重建的外部依赖条件，也应在交付记录中说清楚。

待执行验证可以使用隔离构建：先完成一次合并安装，原样重建检查是否缓存命中，再修改包清单确认该步骤执行。随后按计划刷新依赖阶段，读取最终镜像的软件包版本，并检查最终阶段是否确实包含目标包。若没有执行记录，只能交付这套验证设计，不能填入虚构的镜像摘要或更新成功日志。

构建输入范围另见Git 忽略与 Docker 上下文，部署身份则可接着核对产物与回滚检查。这次发布若需要证明某个包已更新，最终记录应能从安装层执行追到包版本，再追到正在服务的镜像；缓存命中只是其中一个步骤的复用证据。
