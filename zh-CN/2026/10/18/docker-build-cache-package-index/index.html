Docker 构建命中缓存，软件包索引为什么可能已过时

RUN 缓存不会自动因时间失效；同层更新与安装修正局部失配，刷新时机与实际依赖版本仍需明确。

正文

Docker 构建命中缓存，不证明软件包索引刚刚更新。对普通 RUN 指令，过去了一段时间并不会自动要求重新执行。发布需要新鲜依赖时，应明确何时使安装步骤失效；需要复现旧产物时，则应记录版本，不能把这两个目标混成一句“重新构建即可”。

安装清单改了，索引那层可能没改

Docker 的构建最佳实践专门讨论了 Debian 系镜像中的 apt-get：应将更新索引与安装放进同一条 RUN。文档用先单独更新、再单独安装的写法说明，后来增加安装包时，前面的更新步骤可能复用缓存，使安装面对旧索引。

假设镜像先执行一次索引更新，下一层安装一个工具。数日后，维护者在安装清单里增加另一个工具，但没有改变上层指令。重新运行构建时，看见后半段有执行输出，并不足以证明软件源索引也重新下载了。这个场景没有在本文中实际构建，不能当作已复现的失败日志。

这里的误判来自只看“这次构建是否运行”，没有问“哪一步真的运行”。构建是若干步骤的组合，局部执行和完整刷新是不同状态。索引过旧可能造成安装问题或拿到不符合更新预期的版本，具体结果仍取决于软件源与当时缓存。

同层处理修正的是局部失配

把更新和安装放在同一条指令中，可以让安装清单改变并导致该步骤重新执行时，先更新索引再安装。它将两项有关联的工作绑在一起，避免只重跑安装而沿用另一层索引。但若整条指令仍命中缓存，不能声称这次已经连接软件源并刷新。

Docker 的缓存失效说明明确指出，RUN 的缓存不会自动失效；重复执行相同的包安装指令，不保证更新到较新的包。文档列出改变前置层、清理缓存、使用 --no-cache 或按阶段使用 --no-cache-filter 等办法。选择哪种应根据更新目标与构建成本决定，本文没有执行这些命令。

我更倾向于先写刷新政策，再选择开关。例如，安全更新构建是否要求安装阶段重新取索引，日常提交是否可以复用相同阶段，谁负责确认新版本。这些属于团队决策，没有适合所有项目的固定周期。无差别地禁用缓存虽然直观，也会增加构建工作，并不能替代版本核对。

新鲜与可复现需要分别记录

版本固定可以减少意外变化，但固定某个包版本与追求最新包是不同目标。若软件源已经移除所需版本，旧 Dockerfile 也不等于永远能够重建。应将实际安装版本、基础镜像标识、构建输入与生成镜像标识保留下来；这些是交付记录建议，不是本篇已经采集的产物证据。

基础镜像、包索引和应用依赖也不应共用一个“已更新”状态。即使确认安装步骤执行了，仍要检查软件包版本和业务验证结果。相反，如果只是重新使用已审定的镜像产物，就应准确记录它的标识，不必用再次构建制造一份看起来更新的凭据。

构建输入范围的另一个边界，见 2026 年 10 月 11 日发布的Git 忽略与 Docker 构建上下文。到了发布环节，再按产物与回滚检查核对实际服务版本。缓存命中是构建复用证据；依赖是否符合这次更新要求，应由实际版本记录回答。
