两个 worktree 的文件独立，Git 引用和 stash 也独立吗

worktree 的 HEAD 和暂存区分开，常见分支与 stash 引用共享；恢复前应核对记录内容和任务归属。

正文

两个 worktree 有各自的工作目录和暂存区，但没有变成两个完整独立的 Git 仓库。常见分支引用与 refs/stash 属于共享状态。目录不同，不能用来证明最近一次 stash 只属于当前任务；并行工作需要明确哪些操作只作用于当前目录，哪些会改变共同状态。

HEAD 与分支引用不是一回事

Git worktree 官方手册说明，通常伪引用按 worktree 分开，而以 refs/ 开头的引用共享。其中 HEAD 是每个 worktree 自己的；refs/bisect、refs/worktree 和 refs/rewritten 又是共享规则的例外。不能把这个规则简化成“所有引用共享”，也不能从 HEAD 独立推导出分支引用独立。

这一区别使并行目录可以分别保持检出状态和暂存内容，而仍共同使用仓库中的分支与对象。手册还说明，默认会拒绝把已在另一 worktree 检出的分支再次检出，除非使用覆盖保护的选项。保护提示有其原因，协作时不应为了减少一个报错就习惯性强制通过。

假设一个任务修复发布脚本，另一个任务修改页面文案。它们使用两个目录、两个分支，文件编辑不会因为路径相邻就自动同步。但如果双方把“各自环境”理解成“各自拥有同名分支的一份副本”，就会误判分支操作的范围。这里没有建立或修改任何测试仓库，仅用假设说明边界。

最近一次 stash 没有目录归属保证

Git stash 官方说明把最近的暂存记录放在 refs/stash，更早记录放在该引用的 reflog 中。结合 worktree 的引用共享规则，可以推得普通 stash 列表不按工作目录分成两份。这是两份手册共同支持的判断，而不是某个工具界面的偶然显示。

假设两个任务先后保存了未完成改动，后一个任务创建了更新的 stash。此时只凭“最近一次”选择恢复点，不能证明选中的是当前任务刚才保存的内容。应用错误的记录可能造成冲突或带入不属于本任务的修改；具体结果取决于差异和目标状态，本篇没有执行恢复命令，也不声称已经发生数据丢失。

我建议保存时写清任务说明，并在恢复前核对记录内容、来源分支和稳定标识。列表位置会随着新的保存而变化，不适合长期作为任务归属凭据。删除 stash、批量清理或强制变更共享引用前，也应确认其他目录是否还依赖这些记录；文件隔离不提供这种确认。

用 Git 查路径，少猜内部目录

官方手册建议通过 git rev-parse 等命令访问引用与路径，让 Git 处理私有目录和公共目录的区别。linked worktree 顶层的 .git 通常只是指向管理目录的文件，不能假设每个工作目录下面都有一套完整仓库。手动拼出内部路径的脚本，可能绕开它本该处理的共享规则。

交接记录可以只列几个真正影响协作的对象：当前 worktree 的分支和 HEAD、未提交差异与暂存区、需要保留的 stash，以及计划修改的共享引用。还要区分 Git 状态与运行环境：端口、数据库和外部服务是否隔离，需要由项目配置另行证明，不能从 worktree 的名称推导。

关于从源码状态到交付结果的后续检查，可参看 2026 年 10 月 8 日的发布与回滚记录。本文依据核验时在线的 Git 2.56.0 手册，没有运行 Git 变更操作。开始并行任务前，先让每一位操作者知道共享状态在哪里，比给目录起两个不同名字更能避免恢复时的误会。
