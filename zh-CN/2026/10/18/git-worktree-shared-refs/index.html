两个 worktree 的文件独立，Git 引用和 stash 也独立吗

用双任务保存与冲突推演，区分独立HEAD和索引、共享stash位置、稳定对象身份与清理责任。

正文

核心要点

  • HEAD与索引独立，普通引用通常共享。
  • stash列表位置会变化，恢复须核对对象与差异。
  • 恢复内容与清理共享恢复点分别确认。

两个 worktree 有独立的工作目录、索引和 HEAD，但通常共享分支、标签与普通 stash 引用。目录不同，不能证明 stash@{0} 就属于当前任务。并行任务恢复改动以前，应核对保存对象的稳定身份、实际差异和目标目录状态；列表里的“最近一次”只是会变化的位置。

HEAD 独立，不代表分支各有一份

Git worktree 手册的引用规则区分每个 worktree 的伪引用与通常共享的 refs/。HEAD 是各自的；refs/bisect、refs/worktree 和 refs/rewritten 又属于按 worktree 分开的例外。不能简单说所有引用共享，也不能因为 HEAD 独立就把分支当成目录私有副本。

假设甲在一个目录修复发布脚本，乙在另一目录编辑说明页。两者位于不同分支，各自的未提交修改与暂存选择不会因为共用仓库就自动同步。若甲增加一个普通标签，或改动共享的普通分支引用，那就是另一种范围；文件隔离不提供引用隔离。默认禁止把已经在另一 worktree 检出的分支再次检出，正是需要尊重的保护，不应把强制选项当作日常消除提示的办法。

索引独立也很具体：甲暂存一个文件，不等于乙的索引同时出现该文件。反过来，甲的索引干净，也不能证明乙没有未提交工作。交接报告若只写“仓库干净”，应补充检查了哪个 worktree。关于索引与磁盘内容各自如何变化，可对照restore 的来源和目标，它讨论目录内状态，本篇增加目录之间的共享状态。

一次双任务保存，如何让零号条目换主人

Git stash 的说明把最新记录放在 refs/stash，更早记录放在该引用的 reflog。结合通常引用共享规则，普通 stash 列表不会按两个目录分成两套。以下完整过程是未执行的练习推演，没有在当前仓库创建、应用或删除任何 stash。

设想甲在任务分支修了 release.txt，先保存一份带任务说明的 stash，并立即记录其对象标识、源分支与差异。此刻它是零号。乙随后在另一 worktree 保存 docs.txt 的修改，新的零号现在指向乙，甲的条目位置向后移动。甲若仅凭先前记住的“零号”恢复，选中的已不是当时保存的对象。

恢复前，甲应重新列出记录，定位先前记录的对象，再查看内容是否确实是 release.txt 的预期修改，确认目标分支基线与当前差异。描述消息帮助识别，却不唯一；两个操作者可能用了相同消息。对象标识固定内容，任务说明解释归属，两者应一起保存。对象来自正确任务，也不代表能无冲突应用到任意后续基线。

下面都是只读检查示意，未在当前仓库执行；占位符必须换成已确认的对象身份。它们帮助记录差异，不进行恢复，更不删除记录。

git worktree list --porcelain
git status --short
git diff
git diff --cached
git stash list
git stash show -p <verified-stash-object-id>
git rev-parse --git-path HEAD
git rev-parse --git-path refs/stash

若目标目录已经有未提交改动，应先保留可恢复版本，再按精确范围评估应用。不要为了让命令成功而把两个任务的差异一起清理。先使用不删除保存记录的恢复方式，待内容、暂存意图及业务检查都确认后，再单独决定是否清理条目，通常更便于分辨“内容已恢复”与“共享恢复点已删除”。这是协作建议，不能保证任意冲突都可自动处理。

验证恢复结果，还要守住另一个任务

拟议练习可以在可丢弃仓库建立两个分支和两个目录，让甲乙分别保存不同文件。验证列表在两边看到相同的新旧记录，并比较两次保存的对象身份。恢复甲的内容后，检查甲文件确实包含预期修改，乙的目录和索引仍保留自己的状态，乙所需保存对象仍可定位。只看到甲文件出现，不能证明乙的恢复点没有被误删。

检查索引也不能省。stash 保存工作目录与索引状态，但恢复时是否恢复暂存选择取决于使用的选项和可应用条件。若交接要求保留部分暂存，就应保存恢复前后的两份差异，不只比较磁盘文件。列表条目保留与索引选择保留，同样不是一回事。

底层路径应交给 Git 解析。linked worktree 顶层的 .git 常为指向管理目录的文件；手工拼接 .git/refs/stash 可能既猜错位置，也绕过真正的引用存储方式。官方建议通过 rev-parse 等命令处理私有目录与公共目录的差异。查到路径的意义是确认作用域，不是鼓励脚本直接改内部文件。

知道 stash 的对象哈希以后，就可以删除列表条目了吗？

不能由内容可识别推导出所有使用者都已不再需要它。稳定标识解决选择哪份内容，清理则改变共享恢复入口及其可达性条件。若另一任务还依赖该记录，删除条目可能让它失去原有恢复路径；仅把哈希抄进聊天，也不等于建立了持久保护。保留方式、保留期限和最终清理人应在交接中明确，不能把偶尔还能找回当作备份合同。

运行环境也不随目录名自动隔离。两个 worktree 仍可能占用相同端口、数据库或外部凭据，这些需要各自配置和验证。Git 文件隔离解决的是编辑状态，不负责把测试服务变成两套。开始并行工作时，目录、引用与运行资源应分别注明归属。

再加一份独立冲突练习：甲保存后，目标分支对同一文件的同一段作了不兼容修改。应用时即使出现冲突，也不能推导保存对象已经损坏，更不能立即删除旧条目或重置整个目录。应保留冲突现场与原始对象，查看哪些路径发生变化、索引是否包含未合并状态，再按任务归属决定解决方式。

这次练习的结束条件应同时包含：需要保留的内容仍可定位，目标目录没有未经解释的覆盖，另一任务的保存记录和目录状态没有改变。在这些条件未核对以前暂停共享清理，比把失败应用当成无事发生更可靠。冲突处理本身没有在本篇执行，不能把拟议步骤记成恢复成功记录。

本篇依据十月二十四日读取的 Git 官方手册，没有执行 Git 变更命令。恢复完成的证据应指向具体对象、具体目录和实际差异，并确认另一任务仍保有所需恢复点。
