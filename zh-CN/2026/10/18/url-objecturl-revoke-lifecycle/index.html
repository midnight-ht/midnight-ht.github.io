预览还在用，Blob URL 应该由谁释放？

用单一预览所有者示例说明 Blob URL 的创建、替换与释放，并区分图片交互、地址共享、持久文件和下载验收。

正文

核心要点

  • load 结束不等于用户结束使用图片地址。
  • 每次创建的地址需要明确所有者与释放时机。
  • 临时预览、持久保存和内存测量需要分别验收。

图片预览还允许用户保存、打开新标签或继续查看时，不应仅因为 load 触发就撤销 Blob URL。较明确的做法是让预览组件同时拥有地址的创建、替换和最终释放：资源不再供用户使用时，再撤销自己持有的地址。预览可用与文件已经保存仍是两项不同结果。

load 是加载结束，不是所有使用结束

MDN 的 Blob URL 说明提醒，图片加载后立刻撤销地址，会破坏用户右键保存或打开新标签等交互。本文于二〇二六年十月二十九日核对该页，页面标注最后修改于同年九月十七日。这里讨论长时间停留的图片预览组件，不把某种浏览器的一次点击经验写成所有下载都能套用的配方。

假设用户上传证件后先看预览，页面一看到 load 就清理地址。图片已经显示，开发可能以为资源已完成使命；用户却还想放大或保存。二者对“结束”的定义不同。清理需要对应最后一个合法消费者结束，而不是恰好出现一个方便监听的事件。固定延时同样不能表达用户何时停止使用，只是把猜测变成秒数。

MDN 还说明，每次 createObjectURL 都生成一条新地址，即使对应同一个 Blob。只要仍有活动地址，背后的对象就不能被垃圾回收。文档卸载时浏览器会释放，但长页中的反复替换不会自动等到那个时点。主动清理有价值，前提是清理对象属于当前组件，且确实无人继续依赖。

把地址跟预览所有权放在一起

下面是未执行的完整示例，假定页面有一个专用 img，地址只提供给这个预览，不共享给下载队列或独立窗口。set 替换内容，dispose 结束组件使用。调用者在移除组件时必须调用 dispose；函数并没有自动监听所有框架的卸载事件。

export function ownImagePreview(img) {
  let current = null;
  let disposed = false;
  return {
    set(blob) {
      if (disposed) throw new Error('preview disposed');
      const next = URL.createObjectURL(blob);
      const previous = current;
      try {
        img.src = next;
      } catch (error) {
        URL.revokeObjectURL(next);
        throw error;
      }
      current = next;
      if (previous !== null) URL.revokeObjectURL(previous);
    },
    dispose() {
      if (disposed) return;
      disposed = true;
      img.removeAttribute('src');
      if (current !== null) URL.revokeObjectURL(current);
      current = null;
    },
  };
}

set 先创建新地址，再把它交给图片；赋值同步抛错时，撤销这次新建的地址并保留原有记录。成功交接后，旧预览不再由该组件提供，旧地址才被撤销。dispose 先撤下图片来源，再清理当前地址，并拒绝后续重新写入。这里建立的是单一所有者规则，不能在别处复制 current 然后继续声称它仍有效。

这个实现选择在替换后释放旧地址，并不等待新图片解码成功。因此新内容无效时，旧图不会作为自动回退继续提供。若产品要求“新图可用才替换旧图”，需要增加加载确认、并发替换身份和失败回退，不能把这段代码改个提示就宣称具备该能力。图片异步报错也不会进入赋值周围的 try/catch，测试必须分别观察 DOM 状态和加载结果。

这一段限制决定实现是否适用。证件预览可以允许新文件错误时要求重新选择；展示画廊也许必须保留旧图直到新图准备好。两者都应让界面状态与地址所有权保持一致，而不是用更晚的 revoke 偶然获得回退效果。本文没有运行浏览器，也没有证明任何一个真实产品已经采用该控制器。

同一个 Blob 的两个地址会一起失效吗？

每次创建都有独立地址，所以应分别记录、分别释放。若两个组件对同一个 Blob 各调用一次 createObjectURL，撤销甲持有的那条地址，不等于替乙完成清理。反过来，若两个组件共享同一条地址，甲撤销就可能破坏乙的后续使用。共享对象与共享地址不是同一个所有权问题。

因此不要用 Blob 对象相同来省略地址登记，也不要让两个模块都自认为拥有同一地址的最终释放权。确需共享时，可以由一个明确的上层所有者管理消费者结束，或建立可审查的租用协议。这样的设计需要处理消费者异常退出，不能只在成功路径把计数减一。对于简单预览，每组件自己创建自己释放往往更容易审查，但它不是共享大型资源时的通用性能结论。

revokeObjectURL 参考说明，对无效或已撤销地址调用不会产生动作。这方便让清理幂等，却不能证明第一次撤销的时机正确。该接口也不在 Service Worker 中提供；不要因为普通 Worker 能调用就把例子迁移到所有后台环境。

文件保存需要另外一份验收证据

创建临时地址不是向磁盘写入文件。预览显示、触发下载、下载完成、用户得到可再次打开的正确文件，应按产品需求分别验收。尤其不能把下载按钮 click 之后某个固定延时写成普适的安全释放时间；消费者、浏览器和交接方式不同，地址何时不再需要仍要在目标环境验证。

本站Playwright 下载生命周期说明测试框架如何等待和保存下载产物。它能帮助验收文件，却不能替页面决定 Blob URL 的全部使用者。验收导出时应打开真正保存的文件，检查数据范围、编码和版本，再另查页面重复预览与离开后的资源责任。

拟议浏览器测试连续替换多份图片，确认每个旧地址只在不再供预览使用后释放；当前图片加载后仍检查保存与打开交互。再测无效图片、连续快速替换、重复 dispose 和销毁后 set 的拒绝。内存验证需要目标浏览器实际观察，地址数的变化不能直接换算成已节省的内存字节。

地址字符串也不适合存入数据库当作永久下载链接。它表达的是浏览器当前环境里的临时对象引用，刷新或离开后不能要求重新打开仍有效。需要下次会话继续访问的文件，应进入具有授权、保留和删除规则的实际存储；前端只保存业务身份或可重新获取的地址。撤销对象地址则是在解除引用，不承诺任务管理器立刻显示某个固定数值的内存下降，回收观察仍需独立验证。

本文没有运行浏览器或内存测试。先确定每条地址服务哪些消费者，再让最后一个消费者的结束承担释放依据；预览正常只证明其中一个阶段正常。
