POST 跳转后服务端到底收到什么？逐跳看 method、body 和副作用

POST 收到 3xx 后，目标端收到什么由状态码和客户端决定。逐跳核对 method、body、凭据与副作用，再选择 303 或 307/308。

正文

核心要点

  • 301/302 允许客户端因历史兼容把 POST 改为 GET；303 用于读取间接结果，307 自动跟随时保留 method；RFC 7538 为 308 定义了永久对应状态。
  • 保留 method 不等于正文可重放，也不等于跨来源凭据会传递。
  • 3xx 不说明原入口是否提交副作用；需要按跳记录请求与业务操作状态。

跳转不是服务端替客户端搬运原请求。POST 收到 3xx 后，目标端收到什么取决于状态码、客户端是否自动跟随，以及正文和凭据能否安全重放。判断时要按每一跳看 method、body、headers 和服务端副作用；最终地址本身不是业务回执。

3xx 返回的是指令，下一跳仍由客户端发起

一次跳转至少有两个独立 HTTP 请求。第一跳是客户端向旧地址发送 POST，旧地址处理完这次请求后返回 3xx 和 Location。如果客户端决定跟随，它再向 Location 解析出的目标发出第二跳。第一个服务端看见的是原始 POST；第二个服务端看见的是客户端重新构造的请求。即使两个请求由同一个按钮触发，它们也不是同一个服务器进程之间的内部转交。

这也决定了排障要留两段记录。浏览器 Network 面板或客户端 trace 能显示状态码、Location 和跟随链；旧入口与新目标的 ingress 日志则回答请求是否到达各自服务。只看页面最终停在 /orders/123，不能推导 /orders 收到的 method，也不能证明哪一端创建了订单。RFC 9110 将重定向描述为客户端需要采取后续动作，提供新 URI 的服务器并未替客户端验证业务完成。

五种状态码，不是一个“POST 跳转”规则

301 表示资源永久迁移，302 表示临时位于其他 URI。由于历史客户端对 POST 后续请求该不该保留方法曾经分歧，RFC 9110 允许用户代理出于兼容原因把这两种响应后的 POST 改为 GET。这里是允许，而非所有客户端必然按同一方式处理；永久与临时描述的是迁移属性，不是“保留正文”的保证。301 还可能被启发式缓存；308 则默认可缓存，除非显式缓存指令或方法定义另有规定。因此第一次看到的链路和之后请求可能不同，迁移与回滚验证都要考虑客户端缓存。

303 See Other 的用途更直接：原请求产生了一个可以另行读取的结果，客户端可以对 Location 发 GET 或 HEAD。常见的 Post/Redirect/Get 就是 POST 保存表单后返回 303，再让浏览器 GET 确认页。读结果的请求不需要再提交一次原表单，刷新确认页也不应重复创建订单。

如果新地址要继续处理原方法，307（临时）和 308（永久）规定自动跟随时不得改变请求方法。它们告诉客户端保留方法，但不能单凭状态码得出“每个字节都成功重放”“凭据会跨域传递”或“旧地址没有副作用”。307 的规范要求见 RFC 9110 §15.4.8；308 的永久变体定义见 RFC 7538 §3。RFC 还要求客户端谨慎处理不安全方法的自动跳转，用户代理可以不跟随；应用的 redirect mode、客户端选项和安全策略仍然参与决策。

Fetch 与 curl 会给出不同的证据

在浏览器的 Fetch 算法中，301/302 仅当当前 method 是 POST 时改为 GET；303 对非 GET/HEAD 的方法改成 GET。方法切换时 body 变为空，Content-Type、Content-Length 等请求正文相关头也被删除。307/308 不走这条方法改写分支。若正文是无法再次读取的一次性流，标准算法可能以网络错误结束，因为保留方法不等于客户端拥有第二份正文。

跨来源同样要单独看。Fetch 遇到跨 origin 重定向会移除 Authorization，避免初始站点的授权头自动泄漏到另一个 origin。RFC 9110 也要求客户端考虑是否移除 Authorization、Cookie 等可能有安全影响的字段。Cookie 是否发送还受浏览器凭据模式、SameSite、域和路径等约束。于是“307 保留 POST”只回答 method，不回答目标服务最终拿到哪些 headers。

curl 不能代表浏览器。curl 默认不跟随 3xx，需显式使用 -L/--location；带 --request POST 时，--location 会将显式自定义方法带到后续请求，而新版 --follow 才按状态码处理方法转换（官方文档说明从 curl 8.16.0 引入）。因此，同一个 302 在浏览器 Fetch 与 curl -X POST -L 的输出可能不同。复制一条命令看似“验证通过”，如果命令选项与生产客户端不同，得到的只是另一个客户端的行为。

用订单迁移看懂副作用落在哪一跳

设想一个假设的迁移：旧接口 POST /orders 收到请求后，先检查库存并创建订单，然后回 302 Location: /orders/123。浏览器按 Fetch 跟随后向结果地址发 GET。此时旧接口已经执行创建，目标端只是读取订单；POST 变 GET 是合理的结果导航，但若把 GET 页当作“首次处理点”，就会把责任记错。这个例子是假设，不是本站订单接口、生产请求或实测记录。

另一个迁移方式是旧地址尚未执行任何订单操作，只回 307 Location: https://api.example.test/v2/orders。浏览器保留 POST，目标 v2 接口收到重复可读的 JSON body 后才创建订单。这一设计适用于“旧入口纯粹是路由兼容层”的约定；如果旧接口在发 307 前已落库，v2 再处理一次就可能产生两笔副作用。状态码不提供去重。

现在再加入两条故障路径。若 POST body 来自不可重放的上传流，Fetch 即使按 307 保留 method，也可能无法继续；目标端收不到第二跳，客户端只报告失败。若 Location 指向另一个 origin，method 可能仍是 POST，但 Authorization 被移除，目标端可能收到未授权请求；不能把它误判成目标 API 处理了同一身份。旧端和目标端日志必须使用共同的非秘密 request/operation ID，且“收到”“开始处理”“事务提交”要分开记录。

先选业务意图，再选状态码

如果写操作已由当前端点完成，只想显示一个独立、可收藏的结果资源，303 通常表达得最清楚：POST 处理写入，后续 GET 读取结果。若旧地址只是临时路由入口，且它承诺不产生副作用、客户端正文可重放、目标端具备相同认证和幂等边界，307 才适合把同一个 method 送到新地址。准备永久改用新 URI 时可考虑 308，但也要评估客户端兼容、缓存和外部书签。RFC 7538 提醒 308 比 301/302 新，一些旧客户端可能不识别；如果未知 3xx 的回退不符合业务预期，就先确认目标客户端覆盖面。

301/302 可用于导航或历史兼容场景，但若业务依赖 POST 之后目标仍是 POST，就不要靠“某个客户端一直如此”来建立契约。对写操作，优先查明实际实现使用何种客户端、重定向模式和版本，并把预期请求链写进接口合同。目标若由用户输入控制，还要校验目的地，避免 redirect 变成开放跳转；站内重定向目标信任边界说明的是目的地校验，与 method/body 语义相互独立。

即使链路选择正确，失败后的未知结果也需要业务接口处理。若第一跳已经提交，第二跳失败，用户重试整个 POST 仍可能重复；应使用服务端结果查询或同一 operation ID 的幂等契约，而不是从 302、307 或最终 200 推出“只执行一次”。相关的请求重试与业务幂等边界讨论重复意图如何收敛。

验证要记录每一跳，而不是只看最后页面

在隔离环境用无敏感数据的测试端点分别安排四组情况：POST 经 303 后检查第一端收到 POST、目标端收到 GET、正文相关头是否删除；POST 经 307 后检查目标端收到 POST、正文摘要是否一致；把 Location 改成跨 origin，检查 Authorization 和 Cookie 的实际策略；再用一次性 body 测客户端能否重放。每次都记录 client/version、初始 URL、status、Location、下一跳 method、body 是否存在及摘要、origin、响应码和操作状态。不要在日志中保存真实 Cookie、令牌或支付信息。

若要用 curl，应显式记录版本和选项，并把它的结果限定为 curl 的行为；浏览器验证需在 Network 面板中检查真实跟随链。服务端日志可证明某入口收到了哪种方法和业务操作处于什么阶段，但“没有查到日志”只有在日志覆盖完整、时钟与关联键可靠时才支持未到达结论。代理、负载均衡和异步队列可能引入额外边界。本文没有运行浏览器、curl、服务端或业务接口实验，不报告成功日志、性能或订单结果。

POST 跳转后服务端收到什么，最终要由“状态码语义 × 客户端实现 × body 可重放性 × origin/credential 策略”共同确定。先画出每一跳的请求和副作用，再挑 303、307/308 或导航型状态码；别让最后一个 URL 替代整条请求链的证据。
