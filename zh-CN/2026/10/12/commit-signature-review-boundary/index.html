提交显示 Verified，为什么评审批准仍可能对不上版本？

Verified 说明提交签名通过平台验证，不等于评审者批准了当前差异。用提交、评审、检查、产物和部署记录闭合证据链。

正文

提交旁边出现 Verified，能说明 GitHub 按其验证规则验证了该提交的签名；它不能单独证明有人审过这份代码、测试通过，或这个版本已经上线。审查和发布记录必须把签名、批准、自动检查与产物分别绑定到准确的提交或摘要，并确认仓库策略确实把需要的证据设成合并门槛。

Verified 和批准分别证明什么

GitHub 的提交签名状态文档解释，平台会为已签名的提交和标签显示验证状态。默认情况下，使用 GPG、SSH 或 S/MIME 密钥签名且成功验证的提交会标为 Verified。启用 vigilant mode 后，状态还要结合作者与 committer 的关系；例如，提交者和作者不是同一人且作者启用了该模式时，可能显示 Partially verified。文档明确提醒，这种情形的签名并不保证作者同意。因此，徽标是特定签名验证结果，不是对代码质量、作者授权或评审过程的总评。

Git 的签名格式文档把提交签名描述为对 commit object 的签名。提交对象包含树对象标识、父提交、作者和提交者信息以及消息等内容。验证签名可以帮助接收方判断签名是否能由对应密钥验证，以及被签名对象是否保持一致；但“密钥对应谁、此人是否有权批准变更、这次评审覆盖哪些文件”仍取决于身份管理和仓库流程。签名状态并不会自动读取评审评论来补上这些判断。

评审批准回答的是另一类问题：有权限的审查者是否批准了拉取请求中的某组变更，以及仓库是否要求这个批准才能合并。自动检查则回答特定工作流是否针对某个提交报告通过。部署回执还要回答产物来自哪个版本、系统是否接受了部署，以及最终访问的页面是否呈现了这个产物。把四者记成一个“已验证”会丢掉它们的对象与条件。

用两个修订版本看证据如何分叉

考虑一个明确标注的假设场景：拉取请求最初指向提交 R1。R1 有可验证的签名，评审者查看差异并批准，CI 对 R1 报告通过。之后开发者又推送提交 R2，改动了权限判断，但没有更新说明。R2 也由有效密钥签名，页面仍显示 Verified。如果团队只截图徽标和旧批准状态，记录看起来完整；实际上，R1 的签名状态没有回答 R2 的新差异是否被评审，R1 的 CI 结果也没有回答 R2 是否通过。

这里有两个独立状态变化。第一，R1 的签名仍然是 R1 的签名事实，不会因为分支新增 R2 就变成对 R2 内容的签名。第二，R1 批准是否还可用于合并，取决于分支保护或 ruleset 的设置与当前 PR 状态。GitHub 提供“差异变化后废弃过期批准”的可选设置，也提供要求最近一次可评审推送由他人批准的设置；不是所有仓库都启用了同一组选项。若策略没有要求废弃旧批准，界面状态与组织预期之间就可能出现落差，维护者应在合并前按实际规则核对，而不是假设所有后续提交必然触发重审。

同样，CI 的绿灯需要连到运行时检查的提交 SHA 和工作流运行。即使工作流成功，如果它跑的是 R1，而合并分支后来已包含 R2，R1 的成功不能自动覆盖 R2。若有合并队列或合并提交，最终提交 SHA 也可能不同于 PR head；应确认仓库的必需检查针对哪个合并候选执行，并在构建与部署记录中保留实际输入。这个场景只是用于解释状态关系的假设示例，不对应本站或某个客户事故，也没有在仓库中配置这些规则。

签名规则、评审规则和状态检查不要互相代替

GitHub 的 ruleset 文档把“要求签名提交”“要求先经拉取请求合并”“要求状态检查通过”列为不同规则。签名规则会检查目标分支更新中的提交是否有经过验证的签名；评审规则会要求指定数量或来源的批准；状态检查规则会等待指定检查报告。它们可能共同拦截同一条发布路径，但各自的失败条件不同。

可以用一个小表帮助评审策略，而不是把所有控制统称为“已保护”：

控制 它能回答的问题 仍然需要核对
提交签名验证 此提交对象的签名是否按平台规则验证 密钥归属、权限、是否符合团队身份政策
PR 批准 有权限的评审者是否批准当前策略所定义的差异 批准所对应的差异、后续推送、是否允许旧批准继续有效
必需状态检查 指定检查是否为合并候选报告成功 检查所运行的 SHA、工作流可信度、是否覆盖所需风险
部署门槛与回执 指定环境是否接受部署及其输入版本 产物摘要、目标环境、实际线上页面或服务状态

上表是编辑整理的审查框架，不是 GitHub 对所有仓库的统一默认配置。规则的可用性与行为会随规则类型、目标分支、合并方式、权限和产品计划而不同。尤其是绕过权限：某些规则允许指定角色或应用绕过，审计不能只看“规则已开启”，还要查看谁能绕过、何时绕过，以及绕过是否留下可检索记录。

还要防止从“已批准”推导“作者一致同意”。GitHub 对 vigilant mode 的说明在多作者提交时区分 Verified 和 Partially verified。签名验证所表达的是平台能验证的签名关系，并不能替代团队对贡献者、代提交、密钥轮换和发布权限的治理。代码评审者也不必然是签名者，签名者也不必然有权批准合并；两种责任应分别定义。

维护一份能复核的证据账本

如果需要回答“最终上线的代码是谁批准的”，发布记录至少要保存这些字段：拉取请求编号；评审时的 head SHA 或差异状态；批准者与批准时间；提交签名状态和查看该状态的时间；必需检查名称、工作流运行 ID、运行结果及其 SHA；合并提交 SHA；构建产物摘要；部署环境、部署任务 ID 和实际部署输入；发布后验证的 URL、时间及可观察结果。字段可以按系统能力调整，但每条结论应保留原始标识，不能只保存会变化的分支名或截图。

逐项做关联比“所有灯都绿”更有用。比如，评审记录指向 PR 的差异状态，CI 记录指向工作流运行与 commit SHA，构建记录指向 source SHA 和 artifact digest，部署记录指向 artifact digest 与 environment。若构建系统不能记录制品摘要，至少记录输入提交与不可变产物标识，并说明该映射如何保证。若页面通过 CDN 或异步发布更新，部署成功后还应检查实际 URL 返回的内容或版本标记；单有部署 API 的成功响应只证明部署系统报告成功，不证明每个用户看到的页面都已更新。

账本并不意味着每条记录都由同一主体签署，也不保证上游系统可信。它让审核者能指出断点：批准缺失、批准差异已经变化、检查来自错误 SHA、产物无法追溯到源提交，或者公开页面仍是旧内容。根据断点采取动作，比在审计结论中写“GitHub Verified，所以安全”更可复核。

失败路径：CI 通过了，部署却带上另一份代码

继续用假设示例说明：R1 的评审与 CI 都完成后，R2 进入主分支。构建任务却从一个可变分支标签取源码，或者部署任务复用了上一次构建的产物。发布面板可以显示“部署成功”，但这不能证明产物就是 R2。排查时应沿构建日志确认实际检出的 SHA，核对产物摘要是否与发布清单一致，再确认部署任务引用相同摘要。若任一映射缺失，应把发布标为“输入版本未证实”，而不是把平台状态拼成一个笼统的绿灯。

相反，如果评审批准和 CI 都明确指向 R2，构建清单也记录 R2 与产物摘要，部署环境回执又引用同一摘要，那么证据链更完整。但“更完整”仍不等于对所有风险都已验证：例如，测试覆盖不到的业务规则、错误的依赖版本、部署后的配置差异或生产数据问题，需要各自的检查。清楚写出控制边界，能避免把一次提交身份验证夸大成整体安全保证。

实际审查时可以按下面的顺序执行，并保留核验结果而不是只打勾：先固定准备合并的 SHA；查看签名状态及验证理由；确认批准针对的差异和仓库当前的过期批准策略；核对必需检查是否完成于同一合并候选；记录最终合并 SHA；确认构建输入 SHA、产物摘要和部署输入一致；最后请求目标页面或服务并检查版本标识。若仓库使用合并队列，应把队列创建的候选与最终合并状态一并纳入记录。

评审者最常追问的三件事

Verified 到底能证明谁认可了代码吗？ 它能显示签名按平台规则得到验证。它本身不证明签名密钥的现实控制者具备仓库审批权限，也不证明其他作者同意提交内容；GitHub 的 vigilant mode 说明还专门区分了多作者情形。把“身份验证”“内容批准”和“授权发布”拆开问，证据才不会越界。

后续推送是不是一定让批准失效？ 不一定。GitHub 提供可选的过期批准废弃规则，也可以要求最近一次可评审推送由推送者以外的人批准。审核者需要查看这个仓库实际启用的保护规则、规则集和绕过权限。没有这项配置事实，就只能说审批策略需要确认，不能断言任何后续推送必然撤销或保留批准。

截图能作为审计记录吗？ 截图可辅助说明某个时点的界面，但通常不适合作为唯一证据：它可能没有完整 SHA、规则版本、工作流运行 ID、产物摘要或环境。优先保留平台可查询的对象标识和时间戳，必要时再附截图。对长期审计，还要记录查询时点与权限，因为界面、规则和可见性可能改变。

来源与执行边界

GitHub 文档分别说明提交签名验证状态、ruleset 中的必需签名与状态检查，以及受保护分支的必需评审和过期批准选项。Git 的签名格式手册说明签名绑定到 Git 对象。上述官方说明支持“控制分工不同”的结论；证据账本与复核次序是基于这些机制的编辑建议。实际规则因仓库配置而异，应直接核对目标仓库。

本文没有对某个仓库执行签名验证、拉取请求审查、规则配置读取、构建或发布。R1/R2 是假设名称，不是现实提交；流程也不是已运行教程。若要检查具体仓库，应以仓库当前规则、相关 PR 的差异状态、CI 运行与部署记录为证据，并把无法验证的环节保留为未确认。

相关的改进项验收证据说明为什么完成标记不能代替验证结果；补丁系列的范围比较则讨论了代码变更经过改写后如何核对差异。两篇分别补充验收记录和补丁差异，不替代本文对签名与批准边界的解释。
