CHECK 写着大于零，为什么空值仍能保存？把范围、必填和状态拆开

PostgreSQL 的 CHECK 把 TRUE 和 NULL 都视为满足。分别定义值域、必填状态和历史数据迁移，别把未知批量改成零。

正文

核心要点

  • CHECK (quantity > 0) 遇到 NULL 会得到 NULL；PostgreSQL 认为 CHECK 结果为 TRUE 或 NULL 都满足，因此范围规则不会自动禁止空值。
  • 如果必填随记录状态变化，应分别约束状态、数值范围和状态条件，并小心 OR 表达式中的 NULL 仍会通过 CHECK。
  • NOT VALID 可以先约束之后的新写入，再修复旧记录并验证存量；本文 SQL 是方案示例，没有执行。

在 PostgreSQL 里，CHECK (quantity > 0) 遇到 NULL 得到的不是 FALSE，而是 NULL；CHECK 把 TRUE 和 NULL 都视为满足。因此范围检查不会自动变成必填声明。若字段只在某个业务阶段必须出现，还要把“什么时候允许未知”写进状态规则，而不是用一个比较符代替产品契约。

CHECK 只拒绝 FALSE

约束判断有三种结果：表达式为真，约束通过；表达式为假，约束失败；表达式结果未知，也就是 SQL 的 NULL，约束仍通过。官方约束文档明确规定 CHECK 的表达式只要得到 true 或空值就满足。大多数涉及空值的比较会传播未知，所以 NULL > 0 不是假，而是未知。

用同一个列定义观察四种输入：

quantity quantity > 0 的结果 CHECK (quantity > 0)
8 TRUE 通过
0 FALSE 拒绝
-2 FALSE 拒绝
NULL NULL 通过

这不是数据库漏查，而是 CHECK 的设计语义。它回答“表达式有没有明确证明这一行不符合规则”，没有回答“列是否必须有值”。如果业务契约要求所有记录都有数量，应使用 quantity integer NOT NULL CHECK (quantity > 0)。官方文档也说明，显式 NOT NULL 比把 CHECK (quantity IS NOT NULL) 当作同义替代更合适。

默认值又是另一个问题。DEFAULT 0 只在插入语句省略该列时提供值；显式写入 NULL 不会自动变成默认值。另一方面，调用方没给字段可能表示草稿尚未填写，也可能是接口错误。不能把 NOT NULL、CHECK 和 DEFAULT 混成一个意思。站内的显式 NULL 与默认值一文专门区分了写入时省略字段和主动传空值。

空值是否允许，要看记录处于什么状态

下面是一个假设的申请记录，不对应真实业务系统。草稿阶段，数量未知是正常状态；提交后，审核流程需要一个正的数量。此时字段的合法值依赖同一行的状态：草稿可以是空值或正数，已提交则必须为正数，零和负数在两个阶段都不合法。

若把列直接声明 NOT NULL，草稿也无法保存未确认状态；若只写 CHECK (quantity > 0)，提交态的空值仍然通过。一个方案是把数值范围与状态必填分开表达：

CREATE TABLE requests (
  state text NOT NULL,
  quantity integer,
  CONSTRAINT quantity_positive_when_known
    CHECK (quantity IS NULL OR quantity > 0),
  CONSTRAINT submitted_quantity_present
    CHECK ((state <> 'submitted' OR quantity IS NOT NULL) IS TRUE)
);

state 的 NOT NULL 禁止状态本身未知。第一条 CHECK 允许数量未知，但一旦有值就要求大于零；第二条则让草稿可以缺数量，提交记录必须有数量。括号中的 IS TRUE 不能省略：当 state 是 submitted 且 quantity 是 NULL 时，state <> 'submitted' 为假，quantity IS NOT NULL 也为假，合取结果为假，整条规则拒绝这一行。若将同一条件写成 CHECK (state <> 'submitted' OR quantity > 0)，提交态空值会让右侧比较返回 NULL，于是 FALSE OR NULL 仍为 NULL，CHECK 又会放行。把常见的 OR 模式原样复制到三值逻辑里，是状态约束最容易遗漏的边界。

这个模式也需要业务定义先确定。若提交状态可以由其他状态回退，约束只判断当前存储状态，不负责审核是否完成；若状态名会被改写或存在大小写变体，状态值本身需由枚举、受控字典或其他规则保护。字段若是在另一张表记录，不能指望普通 CHECK 查询另一行来保证持续一致。约束文档明确不支持依赖其他行数据的 CHECK；跨行唯一、引用或区间冲突应优先考虑 UNIQUE、FOREIGN KEY、EXCLUDE 等对应约束，其他规则再评估触发器或事务设计。

NOT VALID 只改变迁移节奏，不改变空值语义

如果历史表已经有大量记录，直接加上新 CHECK 可能要扫描旧数据。PostgreSQL 18 的 ALTER TABLE 支持对 CHECK 使用 NOT VALID：添加时跳过历史扫描，但之后新增或更新的行仍要满足这个约束；等历史问题修复后，再执行 VALIDATE CONSTRAINT 扫描现存记录。官方文档说明验证阶段使用 SHARE UPDATE EXCLUSIVE 锁，并且因为新写入已经受约束，不需要阻止并发更新。

这个工具不会把“未知”自动变成“不允许”，也不会修复旧值。假设要求所有提交申请必须有数量，迁移前应先按状态统计空值，并区分草稿、提交记录、导入缺失和源头确实未知。只有找到权威来源时，才把旧值补成具体数量；无法确定的记录应转入补录、退回或人工核验流程，不要批量填零。

可以按这个顺序设计方案：先确认目标规则和已有空值分布；再添加与真实契约一致的 NOT VALID 检查，挡住新的违规记录；接着分批修复有证据的历史数据，并给未知记录安排补录路径；最后运行 VALIDATE CONSTRAINT。如果验证失败，保留失败行清单，查明它们属于合法草稿还是历史异常，再决定修复或调整规则。本文给出的 SQL 和步骤只是迁移设计示例，没有对数据库执行。

还要注意 NOT VALID 约束可能影响旧违规行后续的更新：更新操作产生的新行也要满足正在生效的约束。迁移计划应先找出会被编辑的旧记录，并确认修复、暂缓更新或分阶段清理的方式。若业务要求无论字段何时变化都持续满足跨行条件，CHECK 也不是相应工具；PostgreSQL 只在插入或更新被检查的那一行时运行它，不会在其他行变化后自动重算所有相关记录。

用边界用例验证约束承诺

约束评审不应止于“DDL 里出现了 CHECK”。至少列出状态与输入的组合：草稿加 NULL、草稿加正数、草稿加零、提交加 NULL、提交加正数、提交加负数、状态为 NULL，以及已有历史空值在普通更新时会怎样。每个案例都要写预期是接受还是拒绝，并说明判断来自业务规则还是数据迁移决定。SQL 方案还应检查失败写入是否保持原记录，应用层错误能否让操作者知道需要补什么。

反例是把所有 NULL 更新成零，然后发现 CHECK (quantity > 0) 不再接受空值。数据库约束看似通过，数据含义却被破坏：未知数量被记录成“明确为零”，报表可能据此显示没有需求，审批流程也可能误判为已确认。另一个反例是给状态条件添加 CHECK，却没有覆盖提交空值的实际三值逻辑组合，开发者用正数测试通过后便以为必填已保护。保存前做一次 truth table，比只运行正常路径更能检验规则是否完整。

最终的验收问题应是：哪些状态允许缺值？零、未知和未提供分别表示什么？数据库拒绝的每一种输入是否对应一个明确契约？历史违规如何修复且不制造事实？只有这些问题都有答案，CHECK、NOT NULL、DEFAULT 与迁移步骤才会各守其职。若字段始终必填，直接 NOT NULL 加范围 CHECK 更清晰；若必填随状态切换，就将状态规则单独写出并用实际组合测试。关于空值是否参与重复身份的另一种语义，可参阅唯一约束中的 NULL。

来源与事实边界

本文依据 PostgreSQL 18 的约束文档说明 CHECK 为 TRUE 或 NULL 时满足、NOT NULL 的职责，以及 CHECK 对跨行状态的边界；ALTER TABLE 文档说明 NOT VALID、后续写入约束和 VALIDATE CONSTRAINT。草稿/提交示例、约束组合和迁移顺序属于编辑建议。没有运行 SQL、修改数据库或验证执行计划。
