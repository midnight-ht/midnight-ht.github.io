SKIP LOCKED 查不到任务，就代表队列空了吗？

SKIP LOCKED 的空领取结果只说明本次语句没有取得可锁任务；把待处理、已领取、完成和恢复分开记录。

正文

核心要点

  • SKIP LOCKED 的空结果只说明本次语句没有取得可立即锁定的匹配行，不能证明队列无积压。
  • 事务行锁在事务结束后释放；跨事务的 worker 执行需要持久领取状态、租约与恢复责任。
  • 幂等、顺序、公平性和最终完成是不同承诺，必须通过失败路径和并发测试分别验收。

不代表。FOR UPDATE SKIP LOCKED 返回零行，只能证明这条语句没有取得符合筛选条件且当时可立即锁定的记录；其他事务可能正锁着待办行，任务也可能已经被领取、尚未完成或正在等待恢复。要判断业务队列是否清空，必须同时看持久化状态和恢复规则，不能把一次领取结果当成全局完成证明。

这条语句看到的不是队列全貌

在版本 19 的 SELECT 手册中，SKIP LOCKED 被定义为跳过不能立即锁定的行，因此结果是一个不一致的数据视图；它不适合一般查询，但可用于多个消费者访问队列表时降低行锁竞争。它只改变行级锁的等待行为，语句仍会取得普通的表级 ROW SHARE 锁。这里的“不一致”不是数据损坏，而是查询主动舍弃了当前被其他事务锁住的行。

设一张任务表中有一条 pending 任务。消费者 A 开始事务并锁住该行，随后还没有提交。消费者 B 用 FOR UPDATE SKIP LOCKED 选择一条到期的 pending 任务。若没有其他符合条件的行，B 可能得到零行。这个返回值说明 B 没有领到任务；它不能区分“根本没有待办行”和“唯一待办行此刻正被 A 锁着”。这个并发过程是解释机制的假设示例，没有连接数据库执行，也没有测量实际等待时间。

锁的寿命进一步说明了为什么不能依赖它代表业务处理状态。显式锁文档说明，普通锁通常保留到事务结束。A 提交或回滚后，行锁就不再代表某个 worker 仍在处理任务。若应用在领取事务提交后才调用外部服务，数据库无法单凭先前的锁知道调用是否已经成功；如果把慢速外部调用留在事务内，锁与事务又会被延长，增加其他操作的等待和故障恢复复杂度。

把“能领到”与“还欠着工作”分开

队列至少要能区分待领取、已领取、已完成、可重试和终止失败。具体命名可以不同，但每次状态变化都应有明确条件与责任人。例如，领取时原子地把一条待办记录改为 claimed，写入 worker 标识、租约截止时间和尝试次数，再通过 RETURNING 把实际修改的任务交给调用方。UPDATE 手册说明，RETURNING 返回实际更新行的值。

以下只是讨论结构的伪生产示例，未在数据库执行；字段、隔离级别、索引、时钟来源和错误处理都要按真实表结构设计：

WITH candidate AS (
  SELECT id
  FROM jobs
  WHERE state = 'pending' AND available_at <= now()
  ORDER BY available_at, id
  FOR UPDATE SKIP LOCKED
  LIMIT 1
)
UPDATE jobs AS j
SET state = 'claimed',
    worker_id = $1,
    lease_until = now() + interval '2 minutes',
    attempts = attempts + 1
FROM candidate
WHERE j.id = candidate.id
RETURNING j.id, j.payload, j.lease_until;

关键不是照抄两分钟租约，而是让筛选、锁定和状态转移处在可审查的原子边界中。数据库提交后，worker 可以在事务之外执行较慢的工作。若进程在提交前退出，事务回滚，任务仍可重新领取；若提交后进程退出，行锁早已释放，但持久化的 claimed 状态和租约仍能说明任务需要等待或恢复。租约过期后再次领取，还要增加尝试计数并保留上次失败原因，避免只把任务重置为 pending 后丢失诊断信息。

事务隔离也影响如何理解“当前”。版本 19 的手册将 READ COMMITTED 列为默认隔离级别：普通 SELECT 看到的是语句开始前已提交的数据；同一事务的后续语句会取得新的语句快照。监控中的 COUNT(*) 因而只是那条统计语句可见的已提交状态快照，且随时可能变化。把计数拿来观察待办积压可以有价值，但不能声称它与某次领取语句拥有完全相同的锁定条件或时间点。

外部副作用会留下“结果未知”窗口

假设 worker 领取任务后向支付、邮件或第三方 API 发出请求，外部服务已经完成动作，但 worker 在写回 completed 前断线。数据库里的租约最终会过期，另一个 worker 可能重试。此时任务重做不是数据库锁错误，而是两个系统之间缺少共同原子提交的结果。若业务副作用不可重复，应为任务传递稳定的幂等键，让外部接收端或本地副作用记录识别重复；还需在确认新 worker 已取得所有权后，阻止旧 worker 迟到的完成写入覆盖新状态。仅靠租约时间并不能让已经发出的网络请求失效，必要时应采用单调递增的 fencing token 并由副作用边界校验。

这也解释了为什么“取到一次就恰好执行一次”不是 SKIP LOCKED 提供的承诺。行锁解决多个事务同时修改同一行时的竞争窗口，不替代跨服务事务、幂等设计、结果对账或死信策略。若外部操作返回超时，系统可能不知道对端是否已经处理；把任务标为失败立即重试，和把它标为完成，都可能错。更诚实的中间状态是“结果待确认”，然后借助外部幂等查询、回调、对账任务或人工处理来收敛状态。采用哪种做法取决于副作用是否可重复、对端是否支持幂等，以及业务容忍延迟还是重复。

跳过锁能推进工作，也可能损害公平性

消费者略过队首的锁定行，可能先处理后面的任务。这提升的是当前可用工作的推进能力，不等于严格先进先出，也不等于每条任务都会在某个时限内被处理。持续时间很长的锁、反复失败后重新排队、某类任务持续涌入，都可能让老任务长期落后。给 LIMIT 配一个稳定排序也不能消除这些情况，但能让未被锁定时的选择更可解释。PostgreSQL 文档建议 LIMIT 配合能确定唯一顺序的 ORDER BY；例如按 available_at, id 排序，在时间相同的任务之间用唯一 ID 打破平局。没有唯一顺序时，执行计划可能导致每次选中的子集变化。

如果业务要求账户内严格顺序执行，先问清“后面的任务能否越过前面的任务”。不同账户之间可以并行，账户内部可能需要单独分区、序列号或每键单消费者；不能仅靠一张全局队列表加 SKIP LOCKED 就宣称严格 FIFO。若任务有截止时间，排序优先级也要考虑截止时间和老化策略，否则高频新任务可能反复压过较早的低优先级任务。相反，对于彼此独立、允许短暂乱序的通知，跳过锁定项可能是合理折中。机制选择要由可接受的乱序、延迟、重复和恢复语义决定。

用观测与并发测试证明承诺

仪表盘应把“待领取数量”“最老待领取年龄”“活动租约数”“已过期租约”“重试次数”“结果待确认”和“完成量”分开。某次消费者取到零行，可以作为“当前没有可立即领取的匹配任务”信号；只有在业务筛选条件、持久状态和所有恢复路径都确认没有未完成工作时，才能向用户显示队列清空。若还有过期租约或结果待确认任务，单纯显示 pending=0 会漏报积压。

验收时可在测试环境用两个真实连接复现锁竞争：连接 A 锁定最早任务但不提交，连接 B 执行领取；确认 B 的结果不会把 A 的任务说成完成，也不会误改其他任务。随后分别测试 A 提交、回滚和断开；模拟 worker 在领取前退出、领取提交后退出、外部调用已成功但确认写入失败，以及租约过期后旧 worker 迟到。每个场景要记录状态变化、尝试次数、租约与幂等键，检查旧 worker 是否还能覆盖新所有权，并测量老任务是否因持续跳过而无限滞留。本文没有执行这些 SQL 或测试，列出的是需要由实际实现验证的检查项。

最后再决定是否继续用数据库表做队列。如果需要复杂延迟调度、广泛跨区域消费者、消息保留、可见性超时和大量独立订阅者，比较专门消息系统的语义与运维成本；如果任务量和一致性边界清楚，数据库方案可能更容易与业务事务一起审查。无论选哪种，空领取、无待办、无运行中工作和业务已完成都是四种不同的事实。相关的异步接受与终态可用于明确请求方在任务领取后究竟收到什么承诺。
