structuredClone 以后，原来的 buffer 为什么不能用了？

transfer 不是多复制一份数据，而是把 ArrayBuffer 的使用权交给结果或接收端。看懂对象可达性、同步脱离和异步重试，才能避免把原 buffer 当作备份。

正文

核心要点

  • 不带 transfer 时，ArrayBuffer 的字节会被克隆，源与结果可独立使用；带 transfer 时，资源转给新对象，原 ArrayBuffer 被 detached。
  • transfer 列表只指定哪些资源要转移；资源还必须出现在消息对象图里，否则源端可能失去它而接收端拿不到它。
  • Worker.postMessage 返回不等于 Worker 已完成处理。转移前要确定重试数据从哪里来，并通过请求 ID 和应答状态区分已交接与已完成。

带 transfer 的 structuredClone 在成功完成时会把被列出的 ArrayBuffer 资源交给返回值，并让原 ArrayBuffer 变成 detached。变量名还在，不代表它还拥有原来的字节；这不是“数据被清空”的同义词，也不是调用方又得到了一份可继续读写的副本。选 transfer 之前，应先回答一个接口问题：交接之后，发送方是否还需要这份数据，失败重试又从哪里取回？

复制和转移，结果对象相似，所有权承诺不同

不带 transfer 时，结构化克隆会生成一份可独立使用的对象图。若里面含有 ArrayBuffer，算法会复制其字节；源与结果随后能分别访问自己的缓冲区。带 transfer 时，结果仍然是一个新的对象图，但被指定的 transferable 资源不是再复制一份，而是被移动到结果对象中。HTML Standard 的 StructuredSerializeWithTransfer 先处理 transfer 列表并序列化值，之后才执行转移步骤和 detach；MDN 的 structuredClone 说明也把原对象描述为转移后不可用。两个调用表面上都返回新对象，调用者承担的后续责任却不一样。

可以用一段很小的 Node 检查区分二者。它只验证本机 Node 24.x 的行为，不代表浏览器矩阵或 Worker 端到端验收：

const buffer = new ArrayBuffer(4);
const view = new Uint8Array(buffer);
view.set([1, 2, 3, 4]);
const result = structuredClone({ view }, { transfer: [buffer] });
console.log(buffer.byteLength);        // 0
console.log(result.view.byteLength);   // 4
console.log([...result.view]);         // [1, 2, 3, 4]

运行结果是源 buffer 的 byteLength 为 0，结果里的 view 仍读到四个字节。原来的 view 变量也不会因为它自己被传进了哪个参数而神奇恢复；它依赖的底层 ArrayBuffer 已经脱离发送方。把这个结果说成“字节被清零”会误导排障人员，因为资源此时在结果对象一侧。真正需要维护的是谁持有资源、谁还能访问，而不是变量是否仍能打印出来。

transfer 列表不是发送内容的快捷写法

transfer 列表表示“这些 transferable 要被转移”，并不自动把它们塞进返回对象。接收端要访问数据，ArrayBuffer 或引用它的 view 还必须在被克隆的对象图里。Node 24.x 的另一项检查把 buffer 放进 transfer 列表，却只克隆 { ok: true }；结果只有 ok 属性，源 buffer 的 byteLength 仍变成 0。也就是说，列表和消息对象是两个独立的输入：一个安排资源如何交接，另一个决定接收方得到什么结构。

这条边界会在重构时变成真实故障。原代码可能把 payload.buffer 放在嵌套字段里，后来有人改成只发送 metadata，却保留了 transfer 列表。调用成功后，发送方资源已脱离，接收方对象也没有 buffer。修复应当是根据接口契约决定：要发送，就让资源可从消息对象到达；不再发送，就从 transfer 列表移除；发送给多个消费者，则先判断是否需要普通克隆或额外副本。不能用“transfer 里有它”代替数据流检查。

还要注意 view 和 backing buffer 的范围。Uint8Array、DataView 是对缓冲区的视图；要转移的是它们所依赖的 ArrayBuffer。一个 view 可能只覆盖大缓冲区的一段，转移 backing buffer 会把整个底层资源交出去，而不只是视图显示的几个字节。如果大 buffer 里还有其他区段，接收方也能通过新建 view 访问它们。只想发送一段内容时，可以先按目标范围构造一份精确的新 Uint8Array，再转移它的 buffer；这增加一次复制，却同时明确了数据边界，避免把相邻敏感片段一并交出。

失败要分成“序列化失败”和“交接后的处理失败”

结构化克隆不支持任意 JavaScript 值。比如消息对象里放着函数，structuredClone 会抛 DataCloneError。HTML Standard 的算法明确把序列化放在 ArrayBuffer 的转移和 detach 之前，因此由对象图不可序列化导致的异常，不会先完成这次 buffer 转移。本机 Node 24.x 也实际检查了包含 callback 函数的对象：异常名是 DataCloneError，源 buffer byteLength 仍为 4。这是特定序列化失败路径的结果，不能扩大成“任何 transferable 的任何异常都必定整体回滚”；不同 transferable 还有各自的转移步骤。

更容易漏掉的是异步处理失败。structuredClone 本身同步返回，所以调用成功时结果对象马上可用；Worker.postMessage 则把消息任务排到接收端的事件循环。发送调用已经把资源交出去，不代表 Worker 已执行、已校验或已持久化。MDN 说明消息中的 transferable 会在发送侧不可用，且 Worker 的消息处理是排队任务。若主线程马上释放文件记录或把 byteLength 为 0 的 buffer 当重试副本，Worker 超时后就没有材料可重新发送。

可以把任务状态至少分成“准备好”“已交接”“已确认接收”“处理完成”和“结果未知/需要恢复”。请求 ID 让应答能对应原任务；接收确认与业务完成应是不同状态。如果必须重试，来源可以是尚可重新读取的 File/Blob、存储层中的原始对象，或在交接前明确保留的一份副本。副本会消耗额外内存，不能假装 transfer 同时实现了“没有复制”和“发送端永远保留重试数据”。若数据不可重读且丢失不可接受，转移前就应确定备份成本与保留期限。

一个最小化的发送准备过程可以写成这样：

const sendBuffer = await file.arrayBuffer();
const retryBuffer = sendBuffer.slice(0); // 需要重试时，明确保留独立字节副本
worker.postMessage({ requestId, buffer: sendBuffer }, [sendBuffer]);
// 发送侧的 sendBuffer 已不再是可用副本；等待匹配 requestId 的应答

这个代码段说明责任关系，不是本机 Worker 演练记录。若把 retryBuffer 删除，任务超时后应重新从 file 读取，或把任务标记为无法自动重试；不要从 detached 的 sendBuffer 恢复。已有系统里的重试条件和幂等键也需要一起核对，见接口重试与幂等边界。

什么时候应该复制，什么时候应该转移？

当发送方与接收方都要同时读写，或者请求可能要重新播放时，复制或保留明确的恢复来源通常更符合接口语义。普通 structuredClone 会带来一份独立数据，实际成本应在目标环境测量。只有当发送方交出后不再需要原资源、目标对象确实带上它、失败时能从其他来源恢复，转移才清楚。不要只因输入“很大”就声称 transfer 一定更快：MDN 对 ArrayBuffer.transfer 的说明是，实现可以采用零复制移动或 realloc；实际路径与性能取决于运行时和场景，本文没有做基准测试。

怎样验证接口，而不把一次成功当作完整保证？

可先在非生产环境构造四类用例：普通克隆后两侧字节独立；transfer 后源 byteLength 为 0、结果字节完整；transfer 列表资源没有出现在 payload 时，测试应发现发送方失去访问而接收方没有该字段；对象图含不可克隆字段时，检查错误并确认序列化失败之前的源资源状态。对于 Worker，还要测试消息已排队但没有业务应答、Worker 抛错或被终止、重复 requestId、取消与超时，并确认重试使用的是有效来源，而不是旧 buffer 变量。

本文已运行上文四类相关 structuredClone 观察中的 Node 检查，环境为 Node 24.x；未启动浏览器、未启动 Worker，也没有测量内存或耗时。进入项目验收时仍应在目标浏览器与 Worker 生命周期中执行上述测试，并根据结果核对请求状态机。选择 transfer 的判断落在所有权交接是否符合任务，而不是变量名是否还存在。
