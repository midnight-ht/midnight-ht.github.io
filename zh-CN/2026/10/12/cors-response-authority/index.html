CORS 报错后能直接重试吗？先确认副作用有没有发生

浏览器 CORS 错误无法单独证明服务端未执行。区分预检被拒、实际响应不可读与网络失败，再用服务端操作记录决定是否重试。

正文

核心要点

  • 失败的预检可以挡住本次实际请求；实际响应的 CORS 检查失败发生在拿到网络响应之后。
  • CORS 错误本身不说明业务是否提交，也不适合作为盲目重试的依据。
  • 用操作标识关联浏览器、服务端和业务记录，并为副作用定义查询与幂等恢复。

浏览器出现 CORS 错误，不能单独证明服务端没有执行操作。它说明页面脚本没有得到一个可用的跨源响应，原因可能是预检挡住了本次请求，也可能是实际请求已经发出、响应却没通过浏览器的 CORS 检查；还有些看起来像 CORS 的错误其实来自 DNS、TLS 或连接中断。对有副作用的操作，先查失败阶段和服务端操作状态，再决定是否重试。

浏览器报的是读取结果，不是事务回执

CORS 是浏览器执行的跨源响应共享机制。服务端通过响应头表明哪些来源可以读取响应；浏览器才决定把响应交给页面脚本。WHATWG Fetch 标准把实际网络或缓存响应取回、执行 CORS 检查、把检查失败转换为网络错误，写在同一条 fetch 流程中。因此，页面里的 TypeError: Failed to fetch 或控制台的一条跨域错误，没有携带“服务端一定没收到”这样的业务结论。Fetch 标准的实际 fetch 与 CORS 检查步骤说明的是浏览器暴露响应的规则，不是服务端数据库的提交协议。

这一区分对查询和写入的影响并不相同。一个只读查询没拿到响应，通常意味着页面无法继续展示结果；用户重新查询一般不会再创建一笔业务记录。提交订单、创建支付意图、发放邀请或修改配置则相反：页面失去回执时，操作者不知道服务端是在处理前拒绝、处理后提交，还是根本没有收到请求。UI 可以显示“结果暂时无法确认”，但不能把这种不确定包装成“操作失败”，除非业务端有足够证据。

预检失败与实际响应不可读是两条路径

跨源请求只有在符合一定条件时才需要预检。浏览器把这一步称为 CORS-preflight：用 OPTIONS 询问目标端是否接受接下来的方法和请求头；符合条件的许可结果还可以进入预检缓存。所以你在网络面板中没看到新的 OPTIONS，不必然意味着没有实际请求，之前成功的预检可能仍可复用；简单请求则本来就可以不发预检。Fetch 标准的预检流程与缓存列出了这些区别。

若本次请求需要预检、没有可用缓存，而 OPTIONS 被拒绝或其响应不满足许可条件，浏览器不会继续发出这一笔实际请求。这个结论只覆盖当前这次预检失败的请求，不会替你查明用户之前是否点过提交、客户端是否已经重试，也不排除另一条没有预检的请求。浏览器拿到预检错误后，JavaScript 依旧只得到通用失败；控制台和 Network 面板里的请求顺序、方法与响应头才是定位起点。MDN 的 CORS 错误指南也要求从开发者工具确认究竟是哪一个请求失败。

另一种情况是 OPTIONS 允许了该请求，浏览器随后发出了 POST，服务端已经返回响应，但实际响应缺少匹配的 Access-Control-Allow-Origin。如果请求携带凭据，响应许可还要满足凭据模式的条件。此时 Fetch 算法在实际响应的 CORS 检查处返回网络错误，页面脚本读不到响应状态和正文。服务器可能已完成事务，也可能返回了业务错误，或在提交前失败；仅凭浏览器里的 CORS 提示无法区分。Fetch 标准的 CORS 检查是对响应是否可共享的判定，而非对业务动作成功与否的判定。

还要留出第三类：DNS 解析、TLS 握手、代理断连、浏览器扩展拦截等网络或协议失败。它们可能被界面归入类似的 fetch/network error，但服务器是否收到了请求需要结合实际链路记录。不要看到 Origin 头就认定错误一定来自 CORS；Fetch 标准指出，非 GET / HEAD 的请求也会包含 Origin，它本身不是 CORS 请求成功或失败的证明。

一个假设的 POST 如何造成“用户看到失败，记录已经创建”

假设页面要创建支付意图，发出 POST application/json，并带有应用自定义的操作标识。浏览器先发 OPTIONS；服务端允许来源、方法和请求头，浏览器于是发出实际 POST。应用按操作标识创建意图并返回 201，但出口代理在这个响应路径上漏掉了 Access-Control-Allow-Origin。服务端的记录可能已经存在，浏览器却因响应不能交给脚本而拒绝向页面提供状态码和正文。用户只看到请求失败，再点一次，便有创建重复意图的可能。

这是解释机制的假设例子，不是本次执行的支付请求、真实事故或浏览器测试结果。若实际 OPTIONS 被拒，这一条请求不会走到上述 POST；若 POST 的网络连接在发送前就断开，也可能完全没有服务端记录；若服务器确实接收并提交，再由代理删掉 CORS 响应头，业务结果就可能已改变。相同的界面错误覆盖了不同的执行阶段，正因为它不是业务回执，才不能直接决定重试。

例如创建接口保存了 operation_id，可以把它用于查询“尚未收到回执”的操作状态。键的去重范围、过期时间、请求体不匹配时的行为和并发重复提交规则必须由该 API 明确约定；不能因为客户端随手加了一个名为 Idempotency-Key 的头，就假设服务器已经实现幂等。若服务端没有状态查询或去重契约，客户端应把结果标记为未知，走人工确认或业务规定的恢复路径，而非生成新标识反复提交。

CORS 不是身份授权，也不是通用 CSRF 防线

CORS 控制浏览器是否把响应交给跨源脚本，并不替服务端验证用户是谁、当前用户能否修改这条对象，或这次业务动作是否满足状态条件。非浏览器客户端也不靠浏览器同源策略受约束。OWASP 明确要求像 CORS 不存在一样验证每个请求的认证与授权；它也指出，有些跨源表单 POST 不需要预检，服务端仍可能处理请求，即使调用方读不到响应。OWASP CORS 安全指南把 CORS、访问控制与 CSRF 防护分开讨论。

因此，把 Access-Control-Allow-Origin 改成 * 既不能修复身份授权，也不能让用户可靠地知道一次写入的结果；在凭据场景下，通配符还不符合浏览器的 CORS 规则。正确修复是核对需要读取响应的受信来源、实际响应路径和凭据策略，并对副作用接口应用独立的认证、对象授权、CSRF 防护和操作状态管理。不要为了消除控制台红字而放宽所有来源，更不要以 CORS 预检替代业务权限检查。

先串起浏览器和服务端两条证据链

出现未知结果时，浏览器侧记录页面来源、目标 URL、方法、请求头、是否需要预检、OPTIONS 是否通过、实际请求是否出现、响应状态及 CORS 响应头。可复现时再核对控制台给出的具体原因。Network 面板里的 Cookie、授权头和请求体可能属于敏感信息，留存给团队排查前应先脱敏。用 curl 查看服务器响应头可以辅助定位代理是否漏加头，但 curl 不执行浏览器的 CORS 限制，不能单凭 curl 成功证明浏览器会接受响应。

服务端则用同一个非秘密操作标识，串起入口网关、应用接收、认证授权、事务提交以及响应代理。日志中的“请求已接收”不等于“事务已提交”；响应中的 201 也未必到达页面。把操作状态设计成诸如 received、committed、rejected 的业务阶段只是推荐模式，应以实际系统的事务边界命名，并在提交时持久记录。浏览器请求 ID 用于关联网络尝试，业务 operation ID 用于识别同一意图；如果 API 支持幂等重试，应在契约里写清同一标识重放会返回既有结果还是等待中的状态。

可以为副作用接口定义一个有界的恢复流程：先根据 operation ID 查询现有结果；如结果已提交就展示它，如仍在处理就继续查询或提示等待；只有服务端明确拒绝且没有副作用时才创建新操作。对超时、代理中断这类结果未知状态，不生成新的 ID 盲目再发。该流程是应用层建议，不是 CORS 或 Fetch 自动提供的能力。若业务无法提供查询接口，应明确人工复核入口和需要保存的关联信息，避免把不确定的网络错误转成数据重复。

用四种受控情况验证恢复规则

在隔离测试环境可以安排四个预期不同的用例。第一，使用新操作标识和无有效预检缓存的测试条件，制造需要预检的请求并让 OPTIONS 明确拒绝；确认 Network 面板没有该次实际方法的请求，服务端业务处理器也没有对应操作。第二，让预检通过，但在成功的业务响应中移除 Access-Control-Allow-Origin；确认浏览器脚本读不到响应，同时用服务端操作记录判定事务是否提交。第三，在实际请求发出前中断 DNS 或连接；检查服务端入口是否留下记录，不把浏览器的通用错误当成证据。第四，对明确支持同一 operation ID 幂等语义的接口，用相同 ID 安全重放一次；确认业务系统返回约定的既有结果，而不是创建第二项副作用。

本文没有运行这些浏览器实验、curl 请求、服务端日志查询或业务接口测试，因此没有报告任何网络成功、请求次数或重复交易的实测数据。实施时按真实调用方式复现：若生产代码使用 Cookie、Authorization、自定义头或预检缓存，测试要包含相应条件；否则得到的 OPTIONS 顺序和响应可见性可能不同。重点不是“把 CORS 配对”，而是证明失败在哪个阶段、某个操作标识的服务端结果是什么，以及再次提交是否会复用或新建副作用。

CORS 报错后先不要急着重试：定位是预检、实际响应读取还是传输中断，再用服务端的操作状态判断已发生什么。若这条接口处理副作用，按它真实支持的幂等重试契约恢复；若没有这样的契约，就先把结果保持为未知并查询或人工核对，而不是用页面错误替服务端下结论。
