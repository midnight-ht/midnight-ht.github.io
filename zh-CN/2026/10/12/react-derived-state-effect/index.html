可以算出的 React 状态，为什么还要用 Effect 同步？

React 派生值通常在渲染时计算；区分独立编辑、外部同步与性能优化，避免维护多份重复状态。

正文

一个值如果能够由现有 props 和 state 直接算出，通常不需要再用 Effect 把它同步到另一份 state。先确认它是派生结果还是独立的用户输入，再决定是否保存，能够减少两份状态互相追赶的问题。

同步副本会增加需要解释的状态

React 官方关于不必要 Effect 的说明建议，能够由现有属性和状态计算的值，在渲染时计算，而不要再存入状态。文档同时说明，Effect 仍用于与外部系统同步。这个建议并非禁止所有 Effect，而是区分渲染数据转换与外部同步职责。

假设页面保存原始任务列表和筛选条件，又用 Effect 更新筛选后的列表。此时团队需要解释源列表变化到副本更新之间的过程，以及依赖是否完整。若筛选结果只是当前输入的确定性结果，多保存一份状态就多了一条需要维持的关系。这个例子是设计分析，没有运行组件或测量渲染耗时。

确认数据是否真的能够重新计算

编辑建议是先问：丢弃这个值以后，能否只靠当前输入恢复它？如果答案是肯定的，它可能属于派生数据。如果值包含用户尚未提交的编辑、人工调整或需要保留的历史选择，就不能因为外形与源数据相似，便直接改成每次重新计算。

例如，用户正在编辑的名称与服务器当前名称可能暂时不同。这里的差异可能是有效草稿，而不是同步错误。状态设计必须说明谁是当前编辑的来源、何时接受服务器更新以及什么时候保留本地变化。不能用“减少 state”这一目标掩盖业务中确实存在的多个阶段。

性能优化与正确性分别讨论

计算逻辑昂贵时，可以评估适当的缓存方式，但缓存应帮助减少计算，不应承担建立业务事实的职责。应先保证计算在相同输入下具有明确结果，再考虑是否需要优化。本文没有给出渲染次数、速度提升或特定项目的收益数据。

如果操作需要向外部系统发送变化，应该另行审查同步过程及失败处理。让一个 Effect 既计算展示列表，又发起网络副作用，会使职责更难判断。团队可以分别记录展示所需输入与外部同步目标，再决定实现位置，而不是根据某一段代码是否使用 Hook 来评价设计。

用变化路径检查数据来源

待执行的检查可以覆盖源数据刷新、筛选切换、编辑未提交以及编辑期间收到外部更新。预期显示内容需要先由产品规则确定，不能把当前界面截图当作正确答案。检查还应观察是否存在短暂的旧结果，以及用户编辑是否被意外覆盖。

本文没有执行 React 测试。下一步可以选择一个通过 Effect 同步的展示值，写出它依赖的全部输入，并标记是否包含独立编辑。能够重算的部分才适合简化，真正需要与外部系统同步的部分则应保留清楚的状态与失败责任。

相关的表单状态与服务端规则可帮助区分本地编辑与外部判定的责任。
