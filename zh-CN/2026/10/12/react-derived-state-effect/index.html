React 为什么先显示旧筛选结果，再更新一次？

当列表与筛选条件已经能决定画面时，不要再用 Effect 保存一份结果。理解旧值闪现、独立草稿、性能缓存和外部同步的边界。

正文

核心要点

  • 可由当前 props/state 完整还原的展示值通常在渲染中计算，不另存一份 state。
  • 用户草稿、独立选择和业务阶段可能包含不可还原的信息，需要独立状态与明确生命周期。
  • useMemo 缓存纯计算以回应测量到的成本；Effect 用来同步外部系统，而非代替点击事件。
  • 验证筛选切换、记录切换、被删除的选择和异步旧响应；本文只提出测试方案，没有执行。

任务列表、筛选条件和可见列表，不必各自保存一份。如果可见列表完全由前两者决定，就在渲染时计算；只有用户编辑中的草稿、独立选择或与外部系统同步的目标，才有理由形成另一份状态。把派生结果复制进 state，再用 Effect 追着源数据更新，可能让界面先显示旧结果、提交一次 DOM，再显示新结果，并让开发者维护两份本应一致的数据。

React v19.3 的官方 Learn 文档把 Effect 定义为离开 React 渲染流程、与外部系统同步的出口；列表过滤、姓名拼接等纯转换通常在组件渲染中完成。这个判断不是“Effect 都不好”，而是要问：这段逻辑究竟因为屏幕显示而运行，还是因为一次明确的用户操作而运行，抑或只是把已有输入换一种形式展示？

一份可重算的结果，为什么会出现旧值闪现

先看一个常见写法。页面保存 tasks 和 filter，又用 visibleTasks 保存筛选结果；Effect 在 tasks 或 filter 变化时调用 setVisibleTasks。当用户切换筛选器时，React 先根据新筛选条件渲染组件，但 visibleTasks 仍是上一次提交的值。页面提交后 Effect 执行，再设置新列表并触发下一轮渲染。React Learn 对这条“渲染、提交、运行 Effect、再更新状态”的链路说明了多出来的渲染；如果画面在两次更新之间可见，就有显示旧列表的窗口。

把结果直接放在组件顶部计算即可让所有输入来自同一轮渲染：

function TaskList({ tasks, filter }) {
  const visibleTasks = tasks.filter(task => matches(task, filter));
  return <TaskRows tasks={visibleTasks} />;
}

这里的代码是说明性示例，没有在本仓库运行。关键不在于“少写一个 Hook”，而在于关系只有一条：visibleTasks = f(tasks, filter)。只要 tasks 或 filter 变化，下一次渲染都会重新求值，不需要另外约定谁负责把副本补齐。

副本把一个简单的数据关系改成了同步协议。依赖数组漏掉一个输入，结果就会过期；Effect 运行前有一个提交周期，页面可能短暂显示旧内容；如果 Effect 串联更新多份派生 state，状态变化会形成级联；如果它还启动异步计算，旧输入的结果晚到时就要额外避免它覆盖当前结果。问题并非 Effect 这个 API 单独造成，而是“把可推导的值当成独立事实保存”引入了额外状态转换。

先判断它是否包含独立信息

判断是否存储一个值，可以问一个具体问题：删除它之后，是否能仅凭当前 props 和其他 state 还原？如果能，它通常是派生值；如果不能，因为它包含用户输入、历史意图、人工选择或一个异步操作阶段，它可能是独立状态。名称相似并不代表数据语义相同。

例如，编辑表单有服务端返回的 profile.name 和用户正在输入的 draftName。输入未保存时两者不同是预期行为；若把 draftName 改为每次渲染都从 profile.name 计算，键入内容会消失。反过来，若页面同时保存 firstName、lastName 和由两者拼出来的 fullName，而用户从不能单独修改 fullName，第三份就只是冗余副本。

更难的是服务端数据在编辑期间更新。不要默认“收到新 props 就覆盖草稿”，也不要默认“草稿永远优先”。产品规则需要选择：切换到另一条记录时丢弃旧草稿；同一记录后台刷新时保留本地编辑；或者检测版本冲突并要求用户选择。状态建模应把这几种事件区分开，而不是写一个 Effect 每次复制对象，再期待依赖数组表达业务策略。

如果某项编辑状态属于某个对象的完整生命周期，例如从用户甲的资料页切换到用户乙时，评论框必须连同子组件草稿一起清空，可以把内部编辑组件按 userId 提供 key。React 会将不同 key 视为不同组件身份，重建子树状态。这个做法适用于“换对象就是换编辑会话”的明确边界；若只是同一对象的部分字段更新，重置整棵子树可能误删用户输入。应由身份边界决定 key，而不是把 key 当作通用的状态清理按钮。

持久化源数据还是只存一个选择标识

列表选择是另一个容易制造副本的地方。保存整个 selectedItem 对象，再在 items 更新时用 Effect 清空它，会遇到对象过期、数组引用变化就误重置，或者重复保存一份对象字段等问题。若选择语义是“当前列表中哪个 ID 被选中”，只保存 selectedId，在渲染时从最新列表查找对象，找不到时显示空选择，通常更清楚：

const [selectedId, setSelectedId] = useState(null);
const selectedItem = items.find(item => item.id === selectedId) ?? null;

这也让产品边界变得可见。列表刷新后，仍存在的 ID 会保留选择；已经删除的 ID 不再对应任何可见对象。如果产品要求数据集一变就清空选择，需要把“数据集身份”或明确的刷新事件纳入策略，而不是假设任何新数组引用都代表用户要重新选择。官方状态结构文档建议避免冗余、重复和互相矛盾的 state；这里的 ID 与实体查找就是将稳定意图和会更新的数据分开。

把数据流画成几个节点也有帮助：服务端实体、用户选择的 ID、编辑草稿、派生展示值、外部副作用目标。箭头若是单向计算，展示值通常不需要再成为节点；若存在用户写入，就要说明写入哪一个源；若节点属于外部系统，则需要明确同步、失败和清理责任。这个图不是形式化证明，但能暴露“更新 A 后谁更新 B”这种副本债务。

useMemo 是缓存，不是第二个事实来源

把 Effect 改成直接计算后，有时会担心昂贵转换在每次渲染中重算。React Learn 给出的顺序是先直接计算，再判断是否有性能问题；必要时可用 useMemo 缓存纯计算结果。useMemo 解决的是计算成本，不是正确性或数据归属。它的计算函数仍在渲染中运行，依赖不变时 React 可以复用上次值；它不能替代 state，也不应被当作持久化业务记录。

是否需要缓存，应该围绕真实交互测量。例如，对输入框每次键入时的过滤逻辑计时，比较不使用与使用 useMemo 的更新成本，同时检查生产构建和接近用户设备的运行条件。性能说明还提醒，开发模式的 Strict Mode 会重复调用某些逻辑，开发测量不能直接代表生产表现；useMemo 也不会让首次渲染更快。页面中的毫秒示例是测量建议，不是对你的应用性能的保证。本文没有执行基准测试，不给出任何速度提升结论。

因此选择顺序可以是：先保证计算纯且输入完整；再观察它是否真的消耗显著时间；只有缓存能改善目标交互时，才增加 useMemo。若为了避免重复读取而将派生结果同步到 state，反而需要一套更复杂的更新、恢复和并发策略。省下一个计算，却新增一条一致性约束，通常不是好交易。

Effect 应对准外部系统或显示生命周期

Effect 仍有明确用途。连接聊天服务器、订阅浏览器事件、让第三方图表控件匹配 React 状态，都是组件与外部系统之间的同步。组件显示后建立连接、依赖变化时切换连接、卸载或依赖更改时清理旧连接，描述的是生命周期，而不是把一个值从 A 复制到 B。

网络请求也需要细分。搜索输入变化后，查询结果会与远端数据源同步，Effect 或框架提供的数据加载机制可能适用；用户点击“提交订单”才应发出的 POST，则因明确点击事件而触发，应放在事件处理逻辑中。把点击提交包进 Effect，可能把一次事件变成页面显示时可重复触发的状态推断。应问“为什么这段代码现在运行”：因为界面展示、外部目标变化，还是用户按了按钮？

即使确实需要 Effect，也要检查它的失败和清理路径。旧请求比新请求晚返回时，界面不能把过期结果当成当前查询；订阅要在更换目标时取消；连接失败要有可观察的错误状态；开发模式下重复 setup/cleanup 不应造成永久重复订阅。同步指南把 Effect 作为与外部系统同步的机制，并单独说明清理与开发重复运行。数据来自网络本身不是写 Effect 的充分理由；若使用的 React 框架提供更完整的数据获取机制，应比较其缓存、竞态和错误处理能力。

用状态变化路径验证，而不只盯静态代码

审查或测试时，可以沿四条路径走一遍。第一，改变筛选条件，检查列表是否与新条件同一轮更新，不出现前一筛选的行。第二，编辑草稿时切换对象、刷新同一对象，确认产品定义的保留或丢弃规则。第三，列表移除当前选择项，检查 ID 到实体的解析结果和空状态。第四，快速改变远程查询条件，故意让较早请求晚返回，确认旧响应不会盖掉新结果。每条都应先写预期，不能用当前界面截图反过来猜产品规则。

可以再对实现做一次“故意破坏”的检查：临时注释掉派生计算中的一个条件，测试能否失败；把同一筛选器反复切换，观察是否存在多份列表状态；模拟 Effect 清理后再设置目标，确认没有残留订阅。这里描述的是可执行的验证方案，不代表本篇已经运行这些测试。确定性状态转换可以用单元测试，组件交互用集成测试；真实网络竞态、浏览器订阅或第三方控件则需要在对应边界验证。

列表过滤很慢时，应该把结果存入 state 吗？

不必把性能缓存和业务状态混为一谈。先让派生值在渲染时由完整输入计算，再对目标交互做测量；若计算成本确实影响体验，可使用 useMemo 等缓存方案并复测，而不是用 Effect 把结果写入另一份 state。若结果需要用户独立修改或确认，它已不再是单纯缓存，应为草稿或确认状态制定自己的生命周期规则。

相关的表单状态与服务端规则讨论了本地编辑和外部判定如何分工。遇到 Effect 同步一个 state 时，先把输入节点、用户可写节点和外部系统节点区分开；能从现有输入推导的值留在渲染计算里，需要保留的编辑意图则明确建模。只有最后还存在真正的外部同步工作时，才让 Effect 承担它的职责。
