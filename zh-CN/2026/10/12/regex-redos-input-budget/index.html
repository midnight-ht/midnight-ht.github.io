正则能校验输入，为什么也可能拖住服务？

正则校验也要有可执行的资源预算。本文拆解回溯成本、输入边界、引擎取舍与真正能中断计算的超时设计。

正文

核心要点

  • ReDoS 要看失败路径、模式结构与实际引擎，不能把风险泛化到所有正则。
  • 请求字节、解码字段、模式长度、并发和匹配次数是不同预算，需在各自边界执行。
  • 回溯引擎的超时只有在可中断的隔离执行中才可能停止同步计算；Promise.race 不会抢占同线程代码。
  • 具有复杂度保证的引擎仍要受限于模式规模、文本规模和迭代成本。

一个公开接口用正则校验用户名：几条短样本都通过测试，但遇到前半段接近合法、末尾才失败的输入时，CPU仍可能被匹配占住。正则代码只有一行，并不能说明一次请求的成本有多高。对受信任、边界很小的格式校验，普通正则通常足够；处理外部文本或用户提供的模式时，要看失败路径、引擎复杂度和能实际中断计算的执行边界。单独设置请求超时，未必能救被同步匹配占住的事件循环。

为什么不匹配的输入会更费时间

正则引擎不仅判断“匹配/不匹配”，还要探索表达式允许的路径。回溯引擎在某条路径失败后，会退回先前位置尝试另一种切分。若重复组内部可以用多种重叠方式消费同一段字符，失败输入会让引擎枚举许多近似路径。OWASP 的 ReDoS 说明用 ^(a+)+$ 展示了这种现象：由许多 a 组成、末尾再接一个不匹配字符时，匹配必须排除大量切分方案，工作量可能随输入增长得很快。这个例子说明的是某些模式和引擎组合的风险，不表示所有正则都会指数变慢。

审查时要看失败路径，而非只用正常样本验证格式。以用户名只允许小写字母和数字为例，测试 alice7 能通过、alice! 被拒绝，只能说明两个短样本的结果符合预期。若模式含有嵌套重复或重叠分支，一个更长、前半段几乎都能匹配、最后才失败的字符串，可能触发大量回溯。攻击者并不需要提交数兆字节：当表达式的分支结构不佳，短输入也可能造成高成本；反过来，长度很大的文本也会让即使算法复杂度可控的扫描占用 CPU。因此模式结构和输入上限要分开检查。

把成本拆成可执行的几道边界

先限制 HTTP 请求体字节数，再限制字段解码后的长度。入口字节限制约束应用接受、缓冲和解析的报文体；若要约束链路带宽，还需在网络边缘设置相应限制。解码后的字符长度则对应字段的业务含义。多字节文本会让这两个数不同，应用不能只用 JavaScript 的 string.length 就假定它代表网络字节或用户感知的字符数。明确是在网关、应用框架还是字段校验处执行每一项限制，并确认超限会拒绝请求，而不是静默截断后仍继续匹配。

再盘点模式的来源。固定在代码中的表达式虽然可能存在结构性回溯风险，但其模式长度和编译时机通常可控；让用户在搜索筛选器、路由规则或日志查询中提供模式，则多了一个可操纵的输入面。此时要分别限制模式文本长度、允许的语法和编译资源。只限制被搜索的文本，不能约束用户提交的表达式；只限制表达式，也不能让无限长文本变便宜。OWASP 的测试指南也把“应用处理的表达式”和“用户能否提供表达式”分开列为检查目标。

最后才选择实现策略：简化模式、改用明确的解析器、限制语法，或评估提供复杂度保证的引擎。Google RE2 说明其匹配时间对输入长度给出渐近线性保证，并对解析、编译和执行的内存设置预算；同时它不支持反向引用和前后查找等需要回溯的语法。Rust regex crate 的当前文档（检查版本 1.13.2，2026-11-18 发布）说明单次搜索最坏为 O(m × n)，其中 m 与表达式规模有关，n 与文本字节长度有关；它仍建议为不可信模式限制文本长度和编译后大小。文档还特别指出，迭代所有匹配的某些接口可能达到 O(m × n²)。因此“线性引擎”不等于不需要预算，尤其不能忽略正则规模、重复调用次数和匹配迭代。

超时必须能打断正在运行的那段代码

给 HTTP 请求设置 200 毫秒截止时间，不等同于给同步正则设置了 200 毫秒 CPU 上限。如果正则在 Node.js 主线程同步执行，事件循环被占用时，同一线程无法及时处理负责计时的回调。即使上游代理返回超时，也要确认应用内部的计算是否停止；仅仅不再等待结果，可能留下仍在消耗 CPU 的工作。

可选方案取决于运行模型。优先使用受限引擎或重新设计模式；若业务必须运行可能阻塞的回溯匹配，可把工作放进可以终止的隔离线程或独立进程，并核实取消后任务确实退出。Node.js worker_threads 文档说明 worker.terminate() 会尽快停止 worker 中的 JavaScript 执行，并以 Promise 在退出事件发生后完成。这是线程隔离的原语，不自动提供请求配额、队列上限或整台主机资源保证；调用者仍需限制并发、回收 worker、处理取消竞态，并给服务整体设资源预算。不要把 Promise.race() 包住同步匹配当成中断机制：它可以让调用方先收到超时，但不会抢占同一线程正在运行的 JavaScript。

一个校验接口的设计检查单

假设服务接收一个可选的自定义过滤器和最多数百条记录。下面只是设计示例，不是实际运行过的服务或性能测试。请求入口先按字节拒绝超大报文；过滤器再限制源码长度及语法，记录集也有最大条目数。若过滤器必须采用支持回溯的语法，就在独立 worker/进程中运行，设置单次截止时间和并发上限；如果不需要反向引用或前后查找，则评估 RE2 一类有不同保证的引擎。调用达到预算时返回明确的“规则过于复杂或超出处理预算”，而不是把它伪装成“没有结果”。

这个方案仍需要验证业务语义：改用另一引擎可能改变语法支持、匹配选择和错误行为；限制长度可能拒绝历史上能够提交的合法值；异步隔离也会增加排队、启动和清理成本。迁移前应列出真正需要的正则语法，拿合法边界样本核对行为，再处理编译失败和超时的用户提示。对固定模式，简单的白名单或解析代码有时比复杂正则更容易审查；但自写解析器同样需要边界测试，不能因为没有正则就认为资源消耗自动安全。

怎么验证而不把生产服务当靶场

先静态审查重复组、可重叠分支、未锚定扫描和用户可控模式；工具发现的疑点应由熟悉目标引擎的人复核。针对性性能测试只在获准的隔离环境执行，使用短小、可控的递增样本并设置硬停止，不把攻击字符串投向线上共享服务。记录表达式、运行时/引擎版本、文本字节数、调用方式（单次匹配还是枚举）、并发和停止机制。通过后还要检查负载路径：入口拒绝、异步任务取消、worker 退出、队列不会堆积，以及监控能区分“格式错误”和“处理预算耗尽”。

本文没有执行这些基准测试，也没有测得耗时、CPU 曲线或修复结果。文章引用的是标准组织与运行时/库维护方的文档，方案判断则是编辑建议。要审查一个具体表单，可以从前后端校验职责边界继续，但语义校验和资源保护仍是两项独立验收。真正的上线门槛不是“正则通过了几个样例”，而是输入与表达式都受限、失败路径可被打断、并发成本可控，并且超限时服务能给出可理解的结果。

资料与边界

  • OWASP：Regular expression Denial of Service - ReDoS 解释回溯路径及易受影响模式；示例不代表所有引擎。
  • Google RE2 README 描述线性输入时间、内存预算与语法取舍。
  • Rust regex 1.13.2 文档 给出 O(m × n) 单次搜索边界、匹配迭代的额外成本和不可信模式限制建议。
  • Node.js v26.13.1 worker_threads 文档 说明 worker.terminate() 的终止语义；隔离并不替代并发及总量限制。
