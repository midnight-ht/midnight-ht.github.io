RLS 策略写好了，为什么应用仍能读到所有租户？

行级安全不仅取决于策略文本：运行角色、表所有权、策略合并和租户上下文都会改变实际结果。

正文

核心要点

  • 启用 RLS、授予表权限、查询实际 current_user 是不同检查；所有者、超级用户和 BYPASSRLS 角色的行为也不同。
  • USING 过滤已有行，WITH CHECK 验证写入后的行；permissive 策略按 OR 合并，restrictive 策略按 AND 合并。
  • 连接池中的租户上下文、SET 与 SET LOCAL 生命周期，以及 TRUNCATE 等整表操作都要单独验收。

RLS 策略存在，不等于每条应用连接都会受它约束。排查多租户查询时，先在应用实际使用的连接上确认 current_user、表所有者和角色绕过属性，再检查适用于当前命令的策略；直接改租户谓词，可能是在修错误的那一层。下文按 PostgreSQL 19 官方手册解释机制。代码片段是用于评审的示意，没有在数据库中执行。

先分清应用用户与数据库角色

浏览器请求中的“租户甲用户”和 PostgreSQL 会话角色不是天然相同的身份。应用可能用一个共享服务账号连接数据库，再把请求身份作为参数传入；也可能在事务中切换数据库角色。若只检查连接配置文件，就无法知道查询落到数据库时的有效身份。

PostgreSQL 的 session_user 表示建立会话的登录身份，current_user 是当前权限检查使用的有效身份。执行 SET ROLE 后，后者会改变；在 SECURITY DEFINER 函数执行期间，有效身份也会切换为函数所有者。因而，诊断需要从真实应用连接中取值，而不能从迁移脚本、运维终端或本地管理员连接推断。

可以先让应用在受控诊断路径中执行下面的只读查询，并把结果与部署配置关联起来。它是检查建议，不是本文执行记录：

SELECT session_user, current_user,
       current_setting('role', true) AS role_setting;

如果结果显示的是迁移账号或表所有者，先追踪连接池如何取得凭据、后台 worker 是否复用另一组连接，以及请求经过的函数是否带有 SECURITY DEFINER。不要在普通业务日志中长期记录敏感连接信息；诊断输出应受访问控制并在结束后移除。

所有者和绕过属性在策略文本之外

PostgreSQL 19 的行级安全文档说明：启用 RLS 后，没有适用策略的普通角色默认看不到或不能修改受保护行；超级用户和带 BYPASSRLS 属性的角色始终绕过策略，表所有者通常也绕过。表上设置 FORCE ROW LEVEL SECURITY 可以让所有者也受策略约束，但它不会限制超级用户或 BYPASSRLS 角色。行级安全文档因此把“策略存在”与“当前执行者必须服从策略”分成了两个条件。

还要把 SQL 对象权限与行策略分开：GRANT SELECT 决定角色有没有查询表的权限，RLS 再限制在这项权限内能看到哪些行；RLS 不会代替 GRANT。如果表根本没有启用 RLS，已创建的策略会被忽略，用户只受普通对象权限约束。诊断时应同时检查表的 relrowsecurity、relforcerowsecurity 状态与角色授权，避免把“策略写在目录里”误当成“查询时已执行”。权限文档

还有一个容易漏掉的边界：TRUNCATE 作用于整张表，不逐行经过 RLS 策略；限制它要看对象权限。若运行角色拥有 TRUNCATE，一套严密的行策略也不会把这个整表操作变成按租户过滤。维护角色和业务角色的授权清单应把它单独列出来。行级安全文档

这也解释了一个常见的反例：管理员查询看到所有租户，并不自动证明租户策略失效；相反，如果线上服务用的是拥有表的迁移角色，业务路径才可能真正绕过策略。前者是预期的高权限观察，后者则是部署身份选择问题。两种情况必须通过 current_user、表属主和角色属性证据区分，不能凭结果相似就下同一个结论。

在 PostgreSQL 19 中，可用 pg_roles 检查 rolsuper 和 rolbypassrls，用 pg_policies 查看策略适用角色、命令、USING、WITH CHECK 及策略是否 permissive。策略的目标角色还要结合普通角色成员关系和继承规则判断，不一定只对照 current_user 的单个名字。以下是待执行的检查样例：

SELECT rolname, rolsuper, rolbypassrls
FROM pg_roles
WHERE rolname IN ('app_runtime', 'app_migrator');

SELECT schemaname, tablename, policyname, permissive,
       roles, cmd, qual, with_check
FROM pg_policies
WHERE schemaname = 'public' AND tablename = 'orders';

SELECT c.relowner::regrole AS table_owner,
       c.relrowsecurity, c.relforcerowsecurity
FROM pg_class AS c
WHERE c.oid = 'public.orders'::regclass;

实际项目需要确认调用者有权查看这些目录信息，并核对它们来自与服务相同的数据库和部署版本。只从开发环境拷贝一份角色清单，不构成生产连接的验收证据。

USING 和 WITH CHECK 管的是不同阶段

USING 决定现有行对当前命令是否可见或可被目标操作选中；条件为 false 或 null 时，行会被过滤。WITH CHECK 检查插入或更新后拟写入的新行；条件为 false 或 null 时，写入会报错。只写读取策略，并不能说明新建订单是否被限定在请求租户，也不能阻止更新把现有订单改到另一个租户。

例如，假设 orders.tenant_id 是租户归属字段，策略表达式大意是“行的租户必须等于当前请求租户”。对于 SELECT，检查行能否出现；对于 INSERT，检查新行；对于 UPDATE，既要知道旧行能否被选中，也要确认改完后的行仍满足租户边界。PostgreSQL 的 CREATE POLICY 文档说明，策略表达式按命令和策略类型应用；省略某些 WITH CHECK 时也存在从 USING 推导的规则，因此评审必须读完整策略定义，不能只看一个谓词。CREATE POLICY

策略组合也会改变结论。默认的 permissive 策略按 OR 合并；一条租户限制与另一条宽泛的 USING (true) 同时适用时，后者可能扩大可见范围。restrictive 策略按 AND 合并，但只有 restrictive 策略而没有任何适用的 permissive 策略，并不会凭空授予访问。检查目录时要逐条确认策略作用的命令、角色和组合方式，而不是数策略条数。

共享连接上的租户上下文是一条信任边界

一些服务用共享数据库角色访问数据，并通过事务级参数或函数把当前租户交给策略。这个设计只有在“谁能设置上下文、上下文从何而来、连接复用时何时失效”都明确时才有意义。RLS 可以按数据库收到的租户值执行过滤，却不能替 HTTP 层证明这个值确实来自已认证用户。若客户端能任意选择租户参数，数据库只是忠实执行了错误输入。

连接池会复用会话，因此普通 SET 可能让状态留在连接上，影响后续借用者；PostgreSQL 的 SET LOCAL 则只持续到当前事务结束。要用哪种方式，取决于驱动、事务边界与连接池行为，必须验证提交、回滚、异常退出、事务外查询和连接归还路径。若采用事务局部设置，业务查询必须确实处在同一事务中；若连接在事务开始前已经被借出，回滚也需要确认会话状态按预期清理。SET

一个有用的威胁建模问题是：共享账号下，应用代码是否能把租户上下文改成任意值？如果能，RLS 仍可防止漏写 WHERE 条件，却不能单独防止被攻陷的应用使用另一个租户身份。若系统需要数据库区分请求主体，应进一步设计独立角色、受控函数或可信的身份传递机制，并把权限授予路径一并纳入评审。这里是架构判断，不代表本站检查过某个连接池或证明某方案安全。

用运行角色验收读、写和失败路径

验收表应明确“由谁执行、命令是什么、预期结果是什么”。至少覆盖：租户甲读取自己的行；甲读取乙的行；甲创建带甲租户号的新行；甲试图创建乙的行；甲修改自己行的业务字段；甲尝试改变租户归属；缺失上下文时读写；以及后台任务和导出路径。若适用的租户条件比较结果在上下文缺失时为 null，USING 会隐藏该行，而 WITH CHECK 会拒绝新行；测试要观察这两种不同结果。每个用例都应通过应用实际使用的运行角色执行，并记录数据库版本、连接来源与预期拒绝方式。

还需要一组对照：表所有者或运维身份可能看到全部记录，但应明确标注它是诊断结果，不是普通用户的安全验收。用例要区分“查询返回零行”和“写入因策略拒绝而失败”，并检查应用是否把部分失败错误地报告为成功。异步任务、批量更新和 SECURITY DEFINER 函数都可能走不同执行身份，不能由一个网页列表测试代替。

本文没有访问应用部署配置，也没有执行 SQL；检查表是待运行的验收方案，不是已通过的安全测试。RLS 是数据库行级防护的一层，不能替代认证、业务动作授权、输入验证和对高权限维护路径的管理。真正能回答“应用为什么看到了所有租户”的证据，是同一条实际服务连接上的有效角色、表属主、绕过属性和适用策略，而不是管理员会话中策略看起来有多完整。

如果问题还涉及对象操作是否属于当前用户，可对照对象级授权检查；应用动作授权和数据库行策略需要分别验收。
