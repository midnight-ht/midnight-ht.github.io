关闭动画以后，上传还在进行吗？先把状态和动效拆开

用上传场景拆分业务状态、可见反馈与辅助技术公告；减少动效不应让用户猜上传是否仍在进行。

正文

核心要点

  • 把上传的 idle、uploading、success、error、cancelled 作为业务状态；旋转图标只是可选呈现。
  • 只有上传接口提供真实总量和已传字节时才展示确定百分比；未知耗时应表达为不确定进度。
  • WCAG 2.2 的 SC 2.3.3 是 AAA 的交互触发动效标准，SC 4.1.3 是 AA 的状态消息标准；偏好媒体查询不能替代完整审查。
  • 请求完成与清理不能只依赖 transitionend；切换偏好时改变视觉层，不能悄悄取消或重置业务操作。

设想一个上传按钮：用户点下去后，旋转图标停了，文件却仍在发送。具体到这个假设场景，图标停下不等于任务停止；请求和业务状态才是操作是否仍在进行的依据。问题不在于少了一段动画，而在于业务状态被塞进了装饰效果里。减少动态效果时，应该改变“怎么显示”，不能悄悄改变“操作进行到哪一步”。

先把一件事拆成三层

一个异步操作至少涉及三层：业务状态、用户能看到的反馈、辅助技术能够获知的状态消息。三层可以协作，但不能互相代替。业务层记录任务是否等待、发送、成功、失败或被取消；呈现层选择文字、进度条和可选动画；状态消息层考虑没有焦点变化时，屏幕阅读器怎样收到成功、等待、进度或错误。

拿上传按钮举例，业务状态可以是 idle、uploading、complete、failed 与 cancelled。点击按钮令状态从空闲进入上传；请求响应才决定成功或失败；用户取消则由取消路径收尾。旋转图标不应该决定请求何时开始、何时结束，也不应是判断“正在上传”的唯一证据。这个例子是用来推演设计的假设场景，没有访谈、真实产品记录或用户测试支撑其发生频率。

此时最容易犯的错，是状态只体现在图标的 CSS class 上。组件进入 isLoading，图标开始转，界面没有文字，也没有语义化进度。如果减少动效规则把旋转停止，视觉反馈就变得像静态装饰；如果组件把 isLoading 和动画持续时间绑在一起，偏好变化甚至可能干扰业务清理。先给业务状态明确的来源和转换条件，再决定每个状态如何呈现，会更容易发现这种耦合。

没有真实进度时，不要编一个百分比

反馈应回答用户实际需要的问题，而不是让一个动画看起来很忙。若接口只表示“已接受，后台仍在处理”，页面可以说“正在上传，尚未完成”，但没有依据显示“73%”。只有上传接口能提供已发送字节和总字节时，确定进度才有数据来源。HTML <progress> 的 value 表示实际完成量；没有 value 时，进度是未知的、不确定的。<progress> 通常也需要真正的可访问名称，例如关联的 <label>，元素之间的备用文字不是标签。

完成和失败同样不能只用颜色表达。“已上传 4 个文件”或“网络中断，3 个文件未上传，可重试”比绿色、红色状态更明确。若消息在原页面区域更新而没有转移焦点，应该进一步检查它是否作为状态消息被程序化识别。WCAG 2.2 的 SC 4.1.3 是 Level AA，针对不改变上下文的状态消息；它要求这类消息可通过角色或属性被辅助技术识别，而不是要求每次界面变化都弹出通知。对连续进度的播报还要控制频率，频繁宣布每个字节会让界面变得吵闹。

媒体查询只管它能匹配到的呈现

CSS 可以针对 prefers-reduced-motion: reduce 停用或替换非必要动画；W3C 的 C39 将其列为满足 SC 2.3.3 的一种充分技术示例，同时明确这类技术示例不是唯一实现，也不是单独的合规证书。MDN 对 no-preference 的定义是设备没有报告相关偏好，不代表用户明确同意所有动画。因而更稳妥的设计是：内容和基本反馈以静态状态成立，动画只在允许时增强表达。

这条 CSS 不会自动控制 JavaScript 计时器、Canvas 绘制、Web Animations API、第三方组件或自动滚动。对脚本控制的动效，可以读取 window.matchMedia("(prefers-reduced-motion: reduce)") 的 matches，并监听 MediaQueryList 的 change 事件。偏好在会话中变化时，只调整动画对象的播放、暂停或替代方式；不要把取消上传、清空进度等业务操作混进媒体查询回调。组件卸载时应解除监听，避免重复订阅。若动画是某项工具本身的核心功能，例如动画编辑器预览，是否保留由“移除后是否会改变信息或功能，且无法通过其他方式实现”来判断，不能只凭团队不愿去掉它。

业务结束不该等动画结束通知

还有一个容易漏掉的故障路径：组件等 transitionend 才把忙碌层隐藏、恢复按钮或清除请求标记。MDN 说明，如果没有过渡时长、时长为零、过渡被移除或收到 transitioncancel，transitionend 不会触发。减少动效样式正可能去掉过渡；即使某种具体样式只把时长改成零而不一定覆盖所有实现，业务代码也不应假设动画事件必达。否则真实请求已经失败，按钮仍被锁住；或用户已经取消，界面还留着忙碌标记。

更可靠的顺序是让请求回调或状态管理器负责业务结论：成功就进入 complete，错误就进入 failed，取消就进入 cancelled。动画可以跟随状态开始或结束，但它只是副作用呈现；若结束时需要做视觉清理，可以用不影响业务语义的回退路径，并在卸载、取消和偏好变更时都能完成清理。把这几个责任分开后，动画事件缺失只会让过渡少发生，不会让上传状态卡死。

W3C WCAG 2.2 的 SC 2.3.3 “Animation from Interactions”是 Level AAA 标准，要求用户触发的运动动画可被禁用，除非它对功能或信息是必要的。它与 Level AA 的 SC 4.1.3 关注点不同：前者讨论非必要交互动效能否被禁用，后者讨论不转移焦点的状态消息能否被程序化识别。引用其中一条不代表网站已经满足另一条，也不意味着任一媒体查询单独证明符合 WCAG。

用一张场景表找出耦合

审查时不要只截一张“动画已关闭”的静态图。可以为同一个上传流程记录以下预期，再在正常和减少动态效果两种偏好下逐项验证：

场景 业务状态 必须保留的反馈 动效变化是否可影响操作
点击上传，正在传输 uploading “正在上传”；若有真实总量，展示已完成量 可停止旋转，不应取消请求
总量未知、后台处理中 uploading 清楚说明仍在处理，不伪造百分比 可以没有动画，也不必制造估计值
上传完成 complete 成功结果与文件数量 成功状态来自响应，不等 transitionend
请求失败 failed 可理解的原因和重试入口 错误不能只靠红色闪烁表达
用户取消 cancelled 说明已取消或部分文件结果 视觉收尾不能延迟业务取消
系统偏好在会话中变化 原状态不变 状态文字和真实进度继续存在 只更新动画呈现，随后检查事件监听清理

实际检查还需包含键盘操作、焦点位置和辅助技术。若状态文字在焦点不移动时变化，观察屏幕阅读器是否能收到合适的信息；不要为了“确保读到”把每个微小更新都设成会打断当前朗读的 alert。W3C 也提醒，过度使用 live region 会使应用过于频繁地发声。具体公告语义要由状态对任务的影响、变化频率和实际测试决定。本文没有执行这些浏览器或辅助技术场景，表格是待执行的验收计划，不是通过记录。

可以把这一检查与透明元素的交互状态配合：运动消失、元素隐藏、控件是否可用，是不同层面的状态问题。先把操作状态写出来，再决定是否需要图标旋转；如果一种偏好能让用户误以为上传没响应，说明反馈本来就过度依赖动画。
