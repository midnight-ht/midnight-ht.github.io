随机输入测了很多次，怎样知道断言没有写错？

属性测试会扩大输入探索范围，但不会替团队决定正确性。用行为契约、独立预言机、边界样例和变异挑战检查断言本身。

正文

核心要点

  • 生成器负责探索输入；正确答案仍要来自可审查的行为约定。
  • 固定边界例子、结构不同的参考模型和差分测试能互相补强，但各有共因错误风险。
  • 用错误边界变异挑战断言，并单独审查输入域、缩减结果和拒绝路径。

属性测试可以生成很多输入，但“执行了很多次”只说明测试工具反复检查了你写下的条件，不说明条件本身正确。想判断断言有没有写错，先把行为约定写成独立、可反驳的句子，再用边界例子、参考模型或不同实现挑战它；生成器和缩减器负责探索输入、简化失败，不负责替团队决定什么叫正确。这不是某个框架特有的问题：Claessen 与 Hughes 在 2000 年 ICFP 的 QuickCheck 原始论文就把职责分开，工具生成随机输入并检查性质，测试者提供可自动判断通过或失败的条件。

先把断言翻译成行为约定

考虑一个整数区间筛选函数。产品约定是：给定 lo <= hi，从输入序列中保留所有满足 lo <= x < hi 的元素，顺序与重复次数保持不变；空区间返回空序列。这个约定包含四件事：左右边界的包含方式、元素顺序、重复值和空区间行为。测试应先把它们拆开审查，不能只写一句“输出都在区间内”。

以下样本纯属说明契约的假设输入，不是实际执行结果。输入 [0, 3, 5, 5, 8]，区间 [3, 8) 的期望结果是 [3, 5, 5]。如果实现误把右端条件写成 x <= hi，它会额外返回 8。如果断言只检查“输出每项都在区间内，且长度不超过输入”，错误实现返回空数组也能通过。生成器即使抽到一百万组数据，只要测试条件仍允许空数组，那个错误就仍然被接受。

这个例子说明检查断言的第一步不是数输入，而是问：约定里的每个要点，是否都能被某个反例推翻？右端包含错误应由 x == hi 揭露；左端排除错误应由 x == lo 揭露；出现错误去重时要有重复值；排序或重排要有不同顺序的输入；空集合与 lo == hi 则需要各自的行为约定。对这些点写几个普通例子并不削弱属性测试，反而把业务边界锁定下来。

期望值也可能和被测代码一起犯错

最直接的预言机是按契约构造期望值，例如用清楚表达条件的列表推导式计算筛选结果。它比复制一份复杂生产算法更容易独立审查，但仍要小心共因错误：如果期望计算也把 < hi 写成 <= hi，实现与断言会一起犯错。不要把“测试里有第二段代码”当成独立性的证明；要比较它与需求的来源、结构和失效方式。

可以用几种互补办法降低这种风险。第一，给边界写固定案例，并让预期结果由评审者直接从契约算出。第二，用结构不同的参考模型；例如生产端用索引或数据库查询，测试端用简单的内存集合逐步模拟。在 Hypothesis 官方状态测试文档的示例中，对真实示例数据库执行操作，同时对一个简化的 Python 字典模型执行相同操作，再寻找行为差异。这个示范说明模型能成为比较对象，但不证明模型本身正确；模型也需要由需求和已知案例校准。

第三，若存在另一份独立实现，可以做差分比较，但必须先确认两边实现并非共享相同算法、配置或错误来源。第四，使用关系属性检查多个输入之间的约束，例如排序两次结果应与排序一次一致，或者编码后再解码应恢复允许范围内的原值。这类性质能发现某些错误，却只保证关系成立：两个互相配合但都不符合外部格式的编码器与解码器，依然可能通过往返检查。关系正确不等于绝对行为符合产品合同。

生成器定义了你正在检查的世界

Hypothesis 的当前入门教程把策略作为输入类型和结构的描述，将整数策略与列表策略组合，并展示当浮点输入包含 NaN 时，排序属性会遇到未定义次序的问题。这里的教训不是把 NaN 一律排除，而是先确认接口对它的承诺：若产品允许它，测试应定义排序或拒绝行为；若契约明确禁止它，生成器才应把它排除，并用单独测试验证拒绝路径。

策略中的 .filter() 或 assume() 会缩小实际进入断言的输入域。过滤条件看似只为方便生成，实则可能把最有鉴别力的反例排除。审查时先区分三类值：契约内输入、接口承诺拒绝的输入，以及完全不属于该接口的输入；它们不应混进同一条“正常结果”属性里。

什么时候用 assume 排除输入，什么时候另测拒绝？

只有当输入违反了当前属性的明确前置条件时，排除它才有依据；若接口承诺对这种输入返回错误，拒绝行为本身仍是契约，必须单独测试。沿用区间筛选例子：正常结果属性可以只生成满足 lo <= hi 的端点；如果 API 规定 lo > hi 应报错，就还需要一个独立检查，确认它确实拒绝 [8, 3)，而不是返回空数组或悄悄交换端点。这个分法避免 assume 把“接口必须拒绝的请求”从全部测试里抹掉。它是评审示例，没有执行代码。

据此再检查策略是否遗漏 None、空列表、最大长度、编码边界或非法状态。问清生产入口会接受哪些值、哪些情况必须拒绝，策略才是在表达输入域，而不是只为了让测试变绿。

随机生成对大范围输入的探索很有用，固定例子则负责让关键风险永远可见。快速入门文档（页面版本 6.170.17）说明默认配置生成 100 个随机输入，并可通过设置调整数量；这只是该工具当前文档描述的默认行为，不是所有属性测试框架的通用次数，也不能推导出“100 次足够”。有限抽样是否覆盖某个错误，取决于策略、输入空间、概率分布、运行预算和错误触发条件。遇到必测边界，应显式保留示例，而非押注某次随机运行恰好抽到。

缩减会帮你理解失败，不会替你验证属性

属性测试通常会尝试把失败输入缩减得更小，让人更容易看出触发条件。小反例有助于定位实现：例如一段很长的序列最后缩成只含 hi 的输入，右端边界错误就更清楚。但缩减器优化的是“仍能触发当前失败”的简单程度，不是对照业务规范检查你的断言。若错误属性接受空数组，缩减不会神奇地补出正确的契约；若生成器永远不产生 hi，缩减也没有机会找到该边界。

失败后保存输入、框架版本、配置、随机/数据库状态和完整错误，随后分辨三种情况：实现违反约定；属性写得过弱或写错；输入其实超出契约，策略缺少合理前置条件。不要看到红灯就扩大过滤条件，也不要看到绿灯就宣称证明正确。若失败是预期的拒绝场景，应调整测试结构表达拒绝规则，而不是从正常输入策略中悄悄删掉。

用“故意写错”检验测试能否看见错误

变异测试可以把实现中的 < 暂时换成 <=、删除稳定顺序处理，或让去重逻辑误运行，再观察现有断言是否失败。若错误变异仍通过，说明测试没有把相应行为区别出来。这不是正确性的证明：变异清单未必覆盖真实错误，测试也可能因偶然条件失败；但它能把“断言看起来合理”转成一个可检查的问题：至少这些有意义的错误，能否被拒绝？

验证属性可以采用一张小表：需求来源、输入域、最小反例、参考答案的来源、可能漏过的错误、变异挑战、失败解释。先让熟悉需求的人审查预期行为，再让实现测试扩展输入。对状态复杂的接口，再考虑状态机测试；若每个输入相互独立，普通 @given 可能更简单。官方状态测试指南指出：当规则需要连续且相互作用的操作时，状态机结构才体现价值；独立输入仍可用常规生成测试处理。

有状态接口要比较状态，而不只是单次返回值

如果接口由一串操作组成，逐次只检查函数返回值可能漏掉副作用。用一个假设的键值存储 API 举例：put(k,v) 覆盖旧值，get(k) 在键不存在时返回空值，delete(k) 删除指定键；假设删除不存在的键是幂等操作。一个简单的字典模型可以记录期望状态，但属性不应只比较 delete 的返回值。先执行 put(a,1)、put(b,2)、delete(a)，随后分别读取 a 与 b：预期 a 不存在而 b 仍为 2。若实现误删了“最后插入的键”，单看删除操作成功返回仍可能没有暴露错删。

这仍是明确标注的假设例子，没有运行任何系统。它展示状态机为什么需要不止一条独立输入：操作顺序会改变后续可观察结果。Hypothesis 的状态测试以规则组合生成操作序列，且示例把真实实现与内存模型同步操作，正是为了发现这类序列差异。采用模型前，团队仍要决定覆盖写、缺键读取和重复删除等语义；若把错误语义写进模型，生成再多序列也只会重复比较两个同样错误的答案。对每次操作后的状态做检查更容易定位差异，对只在最终状态检查则可能减少噪声，但也会丢失短暂违反不变量的证据；选择哪种观察点应由接口约定决定。

把一条属性做成可复核的记录

评审记录可以围绕同一条契约留下五项，而不是只存一条绿色流水线：需求出处与语义负责人；属性覆盖的输入域和前置条件；期望结果如何独立算出；哪一个最小输入应当让违约实现失败；以及哪些变异仍然可能漏过。对区间筛选，右端边界样例 [8] 在 [3,8) 中必须变成空序列；输入 [8,3] 应检查返回顺序；[5,5] 应保留两个 5。每一项对应不同承诺，不能用一条“结果都在范围内”替代。

然后把故意注入的错误与应失败的属性配对：把 < hi 换成 <= hi 应被右端案例抓到；直接返回空列表应被完整性检查抓到；按数值排序再输出则应被顺序保持检查抓到。如果变异存活，先检查相应断言是否缺失，再检查样例是否真的进入策略、失败是否被过滤，以及预期结果是否独立。若变异没有存活，也要核对失败是否来自预期断言，不能把任何红灯都记成覆盖成功。

这种记录让“属性测试通过”变成有限而清楚的陈述：在已写明的输入域、观察点、配置与检查条件下，没有发现违约。它没有覆盖契约外的行为，也不意味着变异集完备。比起单独提高随机次数，持续补充被契约要求的边界和能区分错误实现的观察点，通常更能解释测试为什么有意义。

这些建议是评审方法，不是已执行的测试教程；本文没有运行 Hypothesis、变异工具或任何项目代码。团队可以从一条最薄弱的属性开始：写下它来自哪个需求，列出一个会让错误实现通过的具体输入，然后补上独立案例或参考模型，并故意注入对应变异。每次修订后都重新检查输入域与断言是否相互独立。生成次数是预算设置，正确性依据仍然要来自可审查的行为约定。

进一步查看变异测试中存活的错误实现，可把“测试是否拒绝已知错误”与本文的“属性是否有独立依据”连起来审查。
