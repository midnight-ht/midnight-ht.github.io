npm ci 锁住了依赖，为什么两次构建仍可能不同？

npm ci 约束依赖安装，不会固定全部构建输入。把运行时、平台、配置和时间因素列入清单，再定义产物比较方式。

正文

核心要点

  • npm ci 的冻结安装边界是依赖安装及锁文件一致性，不是整个构建过程或产物字节完全相同。
  • 运行时、npm 配置优先级、平台、生命周期脚本、外部输入和时钟都可能进入构建路径；只记录锁文件不足以复盘。
  • 先约定字节相同还是行为等价，再用干净环境、输入清单、哈希和差异解释验证；本文没有执行两次构建。

npm ci 能让依赖安装从锁文件重新开始，却不能替构建过程固定 Node 版本、运行平台、环境变量或生成时间。要判断两台机器是否生成了同一份产物，必须把“安装树是否按约定重建”和“构建读到的输入是否一致”拆成两道检查。锁文件是必要的可追溯输入，不是构建复现的完整证明。

npm ci 实际约束的是安装阶段

npm CLI 11 的官方文档把 npm ci 描述为适合自动化环境的干净安装命令。它要求项目已有 package-lock.json 或 npm-shrinkwrap.json；当锁文件依赖与 package.json 不一致时，命令会报错，而不是替项目改写锁文件；开始前会移除已有的 node_modules；安装也不会写回 package manifest 或锁文件。与 npm install 相比，这些行为让团队更容易检查同一份依赖解析结果是否能被重新安装。

但官方文档同时指出一个容易被流水线忽略的条件：如果创建锁文件时用了会影响依赖树形状的选项，例如 --legacy-peer-deps 或 --install-links，后续 npm ci 需要使用相同设置，否则可能失败。把这种设置放进项目级 .npmrc 并提交，可以让它随仓库审查；不过这并不意味着其他配置来源不会覆盖它。配置还有优先级：npm CLI v11 文档列出命令行高于环境变量、环境变量高于项目配置，后者又高于用户和全局配置。CI 中未记录的 npm_config_* 或额外 CLI 选项可能覆盖仓库里的项目设置，使实际调用和本地不同。

因此，“两边都运行 npm ci”还没有说清输入是否一致。更准确的陈述是：两边按各自有效配置执行了一个干净安装，并在锁文件与项目清单一致的条件下尝试重建依赖树。要把这个观察升级成复现结论，还要记录实际 npm 与 Node 版本、平台、架构、配置来源及安装参数。不要把命令名字相同当成命令上下文相同。

相同锁文件之后，仍有哪些输入会进入构建

下面是一个假设场景，不代表本站运行记录。开发者在 macOS 上提交了锁文件，持续集成在 Linux runner 上安装。两处都执行 npm ci，但使用不同 Node 版本。依赖安装可能成功，后面的 npm run build 仍可能因为运行时行为、原生模块或构建工具条件分支而输出不同内容。此时先检查差异来自哪个阶段：依赖目录、编译结果，还是打包后的文件；“锁文件相同”不能替代这个分层判断。

平台差异也需要具体化。某些包会通过 os、cpu 或 libc 条件声明适用环境，安装器可能只在符合条件的平台上选择可选依赖；原生扩展还可能调用本机编译工具链。不能据此断言每个项目都会生成跨平台不同的产物，但如果项目包含这类依赖，架构、系统库、编译器与安装配置就属于需要核对的输入。对于纯 JavaScript 项目，平台仍可能通过路径分隔、文件排序、换行处理或构建脚本影响输出，是否实际存在要靠检查，而不是推测结果。

安装生命周期脚本和项目自己的构建脚本则把安装之后的外部世界带进流程。脚本可能读取环境变量、下载额外资源、生成当前时间戳、查询本地 Git 状态，或者使用工具自身的默认配置。它们并不因此都是不安全或不确定的；关键在于团队是否知道脚本读取哪些输入、这些输入是否受版本控制或明确允许变化。npm 的冻结安装不会自动把一个构建脚本访问的外部数据变成固定版本，也不会替应用约定哪个环境变量可以改变编译结果。

还要区分“本机没有再下载”与“所有输入被冻结”。npm 缓存解决的是获取包的复用路径，锁文件负责描述解析结果；构建脚本随后读取的 schema、字典、生成器或外部服务数据可能走另一条路径。只有在构建依赖这些数据时，它们才进入复现清单。审计时先看脚本和工具调用，再把实际依赖列入清单，不要把“存在网络”写成每次构建必然受网络影响。

把清单写成可以比较的构建输入

一个可用的构建清单至少要能回答：源代码来自哪个提交？锁文件内容是什么？Node 与 npm 版本各是多少？runner 的系统、架构及相关系统库是什么？执行了哪些安装和构建命令？哪些配置来自项目文件，哪些来自调用方环境？构建有没有读取 Git 信息、生成时间或外部文件？这些不是要求把所有环境转储进日志，而是让团队知道哪几项可能改变输出，以及发现差异时该查哪个来源。

配置清单尤其需要考虑优先级。npm CLI v11 文档说明命令行标志、以 npm_config_ 开头的环境变量以及多种 .npmrc 文件都是配置来源，并按优先级参与解析。项目 .npmrc 可以记录团队共享的非秘密选项，例如影响依赖树的设置；但用户级配置或 CI 调用参数仍要实际检查。可以在执行记录里保存 npm ci 的有效参数、非敏感配置的来源和版本信息。认证 token、私有 registry 密码、签名密钥不能为了“可复现”而原样打印；只记录秘密变量的名称、来源类型和是否存在，权限凭证继续走安全存储。

清单也应区分输入与观察量。提交哈希、依赖锁文件哈希、运行时版本、目标平台和显式配置通常可以说明一次构建所处的条件；进程耗时、下载字节或机器名可能有助于排障，却不一定改变产物。某个值是否是输入，要看构建是否读取它。把所有环境差异都列为不允许，会让复现目标无法执行；漏掉真正参与输出的变量，则会让“同一命令”掩盖不可比较的构建。

先定义“相同”，再拿哈希下结论

两份产物逐字节一致是一种严格定义；页面行为、API 契约或镜像运行效果相同，则属于不同层次。团队应先写清验收对象：是部署目录、压缩包、容器镜像，还是最终可观察行为？目录里哪些文件纳入哈希？若文件包含源代码提交时间、压缩生成时间或镜像标签，是否要求这些元数据也相同？没有这个约定，两个团队可能各自说“构建一致”，但一个比较文件哈希，另一个只比较应用测试结果。

建议的验证流程可以从一条固定源提交开始：记录锁文件、Node/npm 版本、平台、安装参数和受控环境；在两个干净环境里按同一顺序运行安装与构建；分别保存产物清单及每个文件的哈希；对不一致项做内容差异和来源追踪；最后把允许变化的文件或字段写进审计记录。在干净环境里启动，可以避开旧 node_modules、残留生成文件或本机缓存造成的“看似从头开始”。这只是验证方案，本文没有实际跑过两台 runner，因此没有产物哈希或成功结论。

如果差异来自时间字段，应先判断该时间是否有业务意义。Docker 文档说明 SOURCE_DATE_EPOCH 是供构建工具使用的标准化时间变量，并展示如何传给 BuildKit 集成以影响镜像索引、配置和文件元数据。这是 Docker 构建路径中的具体支持，不会自动重写任何任意 JavaScript bundler 输出。只有当实际构建工具读取该值时，它才有作用；把变量设上但没有工具消费，也不能证明输出变得可复现。若时间戳确实是允许差异，可以在比较规范里单独记录和剔除，但不能静默忽略所有哈希差异。

出现差异时按阶段缩小问题

先看依赖安装是否在两边得到同样的锁文件状态和有效参数。如果 npm ci 在一边直接因清单不匹配或选项不一致而失败，问题处于安装契约，尚未进入产物比较。若依赖安装都完成，再核对运行时、平台相关包、环境变量和生命周期脚本。若这些输入均被控制但文件哈希仍不同，就逐文件查看差异，查找时间、路径、排序或未固定外部数据。每一步都要把观察到的事实与假设分开记录，不能从“哈希不同”直接跳到“npm ci 没锁住依赖”。

一个相反的错误做法，是只在 CI 中继续重跑 npm ci，直到最终哈希暂时相同，然后把偶然一致当作保证。另一种做法是直接忽略时间文件，结果把真正影响客户端缓存或许可证信息的字段也排除了。选择验证层级时，发布归档通常需要字节级比较；平台特有构建则可能只要求同一平台内可重复，并对跨平台产物明确不同预期。是否采取这些目标属于工程决策，不能由包管理器命令替团队做出。

实践中可把复现结论拆成三句话：安装阶段有哪些已锁定输入；构建阶段哪些输入已固定或显式允许变化；哪些目标平台与哪种产物经过了重复比较。缺任何一项，就标为部分可追溯或尚未验证，而不是“完全可复现”。依赖缓存信任边界讨论的是缓存是否可信以及能否复用；本篇关注的是锁定安装之后，怎样判断构建产物是否能在受控输入下重复生成。这两个检查相连，但答案不能互相替代。
