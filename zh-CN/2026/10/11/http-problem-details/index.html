错误信息很清楚，客户端为什么还是不知道怎么办？

HTTP 错误文案可读，不代表客户端有稳定的动作依据。RFC 9457 区分问题类型、发生详情与 HTTP 状态；本文说明客户端何时修正、等待、停止或安全退回通用处理。

正文

因为“人能看懂”不等于客户端拥有稳定的判断依据。RFC 9457 用 type 标识问题类别，用 detail 解释这一次发生了什么；客户端应按类型和已定义扩展作判断，不应解析会本地化、会改写的句子。序列化成标准 JSON 只解决了错误如何表达，下一步重试、改输入、停止还是联系支持，仍要由接口契约说明。

先分清 HTTP 状态、问题类别和这次发生

RFC 9457 于 2023 年 7 月发布，是 IETF Standards Track 文档，取代 RFC 7807。它定义 JSON application/problem+json 和等价 XML 表达，让通用 HTTP 状态码之外还能说明具体问题。它允许与任何 HTTP 状态码一起使用，但最自然的是 4xx 与 5xx；若响应本来就是资源表示，应用已有的领域格式可能更合适。标准并没有要求每个错误都包一层 Problem Details。

一个 Problem Details 对象的成员不是同一层信息。type 是问题类型的主要标识；缺省时按 about:blank 处理。若使用受自己控制的绝对 URI，长期稳定的类型地址能帮助客户端和开发者识别语义。RFC 建议 URI 类型在可行时解析到人类可读文档，但消费者不应仅因为响应带了地址就自动抓取它；开发者调试工具可以提供受控的文档查询。客户端不应把某次错误的随机编号塞进 type，否则每次出现都成了一个新类型。

title 是问题类型的简短人类摘要，除本地化外不应随每次发生变化；detail 则解释本次发生的具体情况，且应帮助调用方纠正问题，而不是泄露底层调试材料。规范明确不建议消费者解析 detail，因为人类文案不是可靠的数据协议。instance 用来标识某一次问题发生，可以是对客户端不透明的标识，并不自动等于公开诊断页面或授权凭据。

正文中的 status 成员也容易被误用。它记录源站为这次问题生成的 HTTP 状态，主要是给脱离 HTTP 元数据保存下来的问题对象提供参考；如果生成器写了它，就必须与实际 HTTP 响应状态一致。代理、缓存或网关可能改变客户端最终收到的状态，所以客户端和监控仍要以实际响应为通用 HTTP 语义依据，同时可用正文信息辅助识别传输过程中的变化。一个漂亮 JSON 不能修复状态与正文相互矛盾的问题。

用一次表单错误看客户端能否行动

下面是虚构的 API 设计样例，域名使用保留的 .test，没有真实请求或产品。假设组织登记表里代码格式不正确，服务返回 HTTP 422，媒体类型为 application/problem+json：

{
  "type": "https://api.example.test/problems/invalid-organization-code",
  "title": "组织代码无效",
  "status": 422,
  "detail": "组织代码必须为 8 位大写字母或数字。",
  "instance": "https://api.example.test/problem-occurrences/req-7f31",
  "errors": [
    { "pointer": "/organizationCode", "code": "invalid_format" }
  ]
}

这里 type 表示稳定的问题类别；detail 是给这一次提交者看的解释；instance 关联这次发生；errors 是应用定义的扩展，不是 RFC 9457 强制要求的成员。应用还必须定义扩展字段的结构、兼容策略和权限边界。客户端可以按稳定 type 选择处理分支，再用 errors.pointer 将字段标记到表单，并把 detail 展示给用户。若界面只按“组织代码必须为……”这段文字匹配，一旦换成英文、调整措辞或提供简短屏幕阅读器文案，机器逻辑就可能失效。

样例选择 422 是这份假设 API 契约的决定，不是 Problem Details 的要求。RFC 9110 第 15.5.21 节把 422 定义为服务器理解请求内容类型、语法也正确，但无法处理其中指令的情形；把组织代码格式错误映射到它是可行的应用设计，但不是所有字段错误唯一的状态码。

客户端实际观察到的条件 可设计的下一步 不能假定的事情
已知类型为字段校验错误，扩展中包含字段位置 标记字段并允许修正后再提交 这不是“安全重试原请求”
实际状态为 429，且服务返回 Retry-After 按契约等待后重试 不必从 detail 中提取等待秒数
未知 type 或未知扩展字段 显示通用失败提示并保留诊断标识 不能把未知问题当成功，也不能盲目无限重试
403 仅表示一般写权限不足 解释无权限或提供受控申请入口 不能泄漏资源是否存在或其敏感属性

这张表是编辑给接口评审的设计建议，不是 RFC 对业务动作的规定。HTTP 状态表达通用语义，问题类型和应用扩展细化领域情形，交互再把已知条件映射到用户能理解的动作。对 about:blank，RFC 建议 title 使用相应的 HTTP 状态短语；这种类型没有超出状态码的额外语义，团队不必为了“统一格式”杜撰一个新类别。

再看一个中间层故障的假设反例：源站为字段校验生成 HTTP 422 和 status: 422，网关却把客户端收到的状态改成 502，正文未同步。界面若只读正文，会提示用户修正输入；监控若只读实际状态，会把它记成网关失败。规范还提醒 status 只是问题对象中的提示，通用 HTTP 软件仍按实际状态工作；在这个假设场景里，排查时应保留客户端收到的 HTTP 状态、问题 type、instance 和受控关联标识，而不是把冲突悄悄覆盖成一个“正确值”。由哪个层负责归一、客户端是否呈现通用网关错误，必须由真实部署契约决定，不能从 RFC 推出一条适用于所有代理的规则。

类型稳定不等于所有字段都稳定

问题类型 URI 是契约的一部分。若先发布一个不可解析的临时标识，后来又想让开发者工具访问对应文档，直接把 URI 换成新地址会改变类型身份；旧客户端可能把它当成陌生问题。可以在设计阶段选择由团队控制、可长期维护的类型 URI，给出短标题、适用 HTTP 状态和解决说明。URI 文档可以演进，但类型语义改变到影响客户端动作时，通常应设计显式兼容或新类型，而不是偷偷重用同一个名称。

响应里的 title 可以根据 Accept-Language 协商语言，客户端仍可能收到默认语言。类型身份不随语言变化，detail 可以是该次请求对应的本地化说明，扩展中的 code、pointer 等机器字段则应保持稳定的类型与约束。对不认识的扩展，符合 RFC 的消费者必须忽略，而不是因新增字段就崩溃；这让服务可以在不破坏旧客户端的前提下增加问题上下文。

但“可扩展”不能成为把内部信息塞进公网响应的理由。安全章节要求审慎审查问题类型和实际生成的详情，避免暴露可用于攻击或侵犯隐私的内容，并特别提醒不要通过问题链接公开堆栈转储等实现细节。可以在 instance 或受控关联标识中留下支持排查的线索，再由具备权限的内部工具检索受限日志；不要把 SQL、文件路径、密钥片段、其他用户数据或完整异常对象交给不可信调用者。相关的敏感日志证据边界同样适用：关联信息必须可用，但不等于公开全部证据。

格式迁移还会遇到新旧客户端并存。若老客户端只会读取原有错误体，而新客户端识别 type 与扩展，服务端需要明确媒体类型协商、旧格式保留时间和新旧行为是否一致。仅改变序列化器可能让新字段被忽略，也可能让代理监控误判。应分别观测业务错误、Problem Details 解析失败和客户端未知类型；前者是被拒绝或校验失败，后两者是协议消费路径的问题。错误响应本身若跨服务重放或进入日志，也要遵循同一数据保留与权限策略。

用能推翻设计的测试验证动作

本文没有运行 API 或测试环境。可以提出一组待执行检查：对已知字段类型，确认客户端按 pointer 而不是 detail 文案定位字段；把 title 和 detail 换成本地化版本，确认机器动作不变；向旧客户端增加一个陌生扩展，确认其忽略字段；返回一个未知 type，确认界面展示可理解的兜底说明且不会成功提示或自动循环重试。再经过代理或缓存，检查实际 HTTP 状态与 Problem Details status 不一致时，客户端是否保留真实状态并记录传输差异。

安全路径也要有反例：使用一个本来无权访问的资源，请求错误详情和 instance 关联信息，检查响应是否暴露资源存在性或个人数据；用带内部异常的故障输入，确认公开 detail 没有堆栈、主机路径或密钥。为问题类型 URI 做文档稳定性检查，验证其说明不会被临时发布或部署清理意外删除。以上都是建议的验收方案，不是已执行结果。

评审时可以要求 API、前端和运维分别回答三件事：客户端根据哪个稳定字段分支；用户根据哪段可读说明修正；支持人员如何通过受控标识追踪一次发生。若三者都指向同一段自然语言，格式看似友好，接口仍可能无法安全采取动作。若状态码已足以表达通用拒绝，就保留简单响应；若确有稳定、可区分的领域问题，再定义类型和扩展。Problem Details 是共同表达约定，不替代重试预算、幂等语义或对象授权：这些边界可分别参阅重试与业务幂等和对象级授权。

来源： RFC 9457: Problem Details for HTTP APIs，重点核对第 1、3、4、5 节及 RFC 元信息。标准定义与本文的接口评审建议、假设示例、未执行测试分别标注；本文不承诺某一种服务框架或客户端库会自动实现这些行为。
