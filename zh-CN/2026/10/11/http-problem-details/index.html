错误信息可读，客户端为什么仍无法采取动作？

HTTP 问题详情应区分稳定机器类型与可读说明，核对状态、权限和未知类型处理，不公开底层调试细节。

正文

错误响应要让客户端知道发生了哪一类问题、能否修正以及怎样关联一次失败，而不只是给人一句可读提示。适合机器判断的类型与适合用户阅读的说明应分开；不能让客户端靠匹配翻译后的句子决定重试。下面讨论资料申请接口的假设设计，没有执行请求或上线错误格式。

类型保持稳定，说明服务于这次发生

RFC 9457于二〇二三年发布，定义 HTTP 问题详情格式并替代 RFC 7807，用类型标识与可读字段表达问题。标准强调它不是底层实现的调试工具。本篇采用这一接口表达方式，不声称所有错误都必须新增问题详情，已有状态码足够时可以保持简单响应。

假设资料额度不足和申请格式错误都返回“提交失败”，客户端只能显示同一句话。若类型能够区分额度不足与格式不合法，调用者才可能选择申请额度或引导修正输入。类型应表示稳定的语义，不能在每次发生时加入随机标识，使客户端无法持续识别同一问题。

人类说明可以提供本次失败的上下文，但不应变成机器处理的唯一协议。语言、本地化和措辞修订都会改变句子。客户端应根据明确类型与扩展字段作决定，并对未知类型保留安全的通用处理，不因为没有见过新类型就无限重试或把失败当作成功。

HTTP 状态与正文不要表达相反结论

接口返回成功状态而正文说失败，容易让代理、监控和调用方获得不同判断。应保留 HTTP 状态本身的语义，并核对问题正文里的状态信息与实际响应。中间层可能改写响应，所以排查时要保存真实接收到的状态，而不只看服务端准备发送的对象。

扩展字段需要像正常接口一样定义类型、权限和演进规则。某个字段适合帮助用户修正输入，不代表它可以公开数据库内部名称或完整查询。与敏感日志边界类似，支持排查的标识可以关联受控记录，不必把内部记录全部放进公开响应。

问题类型的说明链接还要考虑信任与生命周期。不能要求客户端无条件抓取响应里出现的任意地址，也不应把正式类型说明放在下一周就失效的临时网页。选择文档组织方式是设计责任，标准化格式不会替团队建立长期可访问的说明站点。

验收客户端采取的动作

可以提出待执行检查：已知类型能否引导正确动作，未知类型是否安全退回通用提示，字段缺失或格式错误是否不会导致崩溃，以及本地化说明改变后机器判断是否稳定。还应检查不同权限的用户看到的细节范围，避免错误接口成为敏感信息查询入口。

这些测试没有在本文执行。格式升级时，应保留旧客户端的迁移安排，明确哪些错误仍采用旧格式，不能只改变服务端序列化器就宣布协议迁移完成。监控应能区分接口失败和错误解析失败，才能发现新格式本身造成的问题。

评审时挑一个真实业务错误，要求前后端说明类型、状态、用户动作和内部关联信息。若只能展示一份漂亮 JSON，却不能说明收到它以后做什么，错误格式仍然没有兑现帮助调用者恢复的承诺。
