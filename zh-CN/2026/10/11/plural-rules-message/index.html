Intl.PluralRules 只选类别，不会替你翻译整句话

复数类别不是译文，也不等于产品空状态。用 Intl.PluralRules 建立完整消息、零值语义、数字格式与运行时测试之间的边界。

正文

Intl.PluralRules 只会根据语言、数字和选项返回 one、few、other 这样的语法类别；它不会替你写出句子，也不知道“没有结果”在产品里意味着什么。可靠的数量文案，需要把数据状态、产品语义、复数类别、完整译文和数字显示分开处理，再把它们组合起来验证。

这个边界很容易被“单数加 s”遮住。英文的 1 file 和 2 files 看起来像规则本身，实际只是一个语言中的一种呈现。把相同的字符串拼接逻辑搬到其他语言，会把英文语法误当成通用数据模型；即使改用浏览器 API，如果仍然只保存名词碎片，或者把加载中的 null 转成 0，界面照样可能说错。

先明确接口返回的是什么

Intl.PluralRules(locale).select(count) 的返回值是类别标识。可参阅 MDN 的 Intl.PluralRules API 说明 以及 ECMA-402 2027 对 select() 的规范。它可以用于挑选与目标语言对应的完整消息，例如某个类别对应“你有 {count} 个待处理文件”，另一个类别对应另一种词形或句法。标识 one 不是“数字恰好等于 1”的跨语言承诺；类别集合也不保证每种语言都有同一批成员。Unicode CLDR 的《UTS #35 Part 3: Numbers》说明，各语言只定义所需类别；例如阿拉伯语可使用 zero、one、two、few、many 和 other，而英文规则只定义 one、other。类别名称是方便实现者沟通的标签，不是供业务代码做算术判断的常量。

类别差异也不总能体现在名词上。CLDR 的复数规则指南用英文 “sheep” 展示：名词单复数拼写不变，但 1 sheep is here 与 2 sheep are here 的动词需要变化；有的语言甚至要改变后续代词。完整消息能让译者调整词序、动词和指代，{count} + noun 的碎片拼接则把这些选择锁死在代码里。因此，应让类别映射到整条消息，而不是映射到一个英文名词的后缀。

计数文案是一条有状态的处理链

考虑文件列表上方的“待处理文件”提示。这里至少有四种不同输入：数据尚未返回、请求失败、服务确认总数为零、服务返回一个有效数量。它们不应该都进入复数选择器。加载中应显示进度，失败应提供重试或解释，只有确认数量为零时才进入产品设计的空状态；正数才适合走计数消息。否则，一个初始化值 0 很容易在网络请求尚未完成时让界面短暂显示“没有文件”，把未知伪装成确定事实。

在计数消息内部，再区分基数和序数。基数回答“有多少文件”；序数回答“第几个文件”或“第几步”。英文序数 1st、2nd、3rd 的类别与基数 1 file、2 files 不是同一套选择。ECMA-402 的《ECMAScript 2027 Internationalization API Specification》为 Intl.PluralRules 定义了 cardinal 与 ordinal 类型，select() 返回类别。一个屏幕上同时出现“3 个未读项”和“第 3 步”，应该用各自的消息模型，而不是复用同一类别后缀。

具体实现时，先验证数量是有限的业务数值，检查消息表中是否有当前类别，再将格式化后的数字注入译文。缺少翻译类别时，应由明示的回退策略处理并在开发或内容校验中报出缺口；不要静默回退到 one，更不要让 undefined 出现在用户界面。other 是 CLDR 类别集合中的兜底类别，但“技术上能回退”不代表这条译文自然、准确或完成过审校。

const messages = {
  en: {
    zero: "No files need attention.",
    one: "{count} file needs attention.",
    other: "{count} files need attention.",
  },
};

function pendingFilesMessage(locale, count) {
  if (!Number.isFinite(count) || count < 0) {
    throw new TypeError("count must be a known, non-negative number");
  }

  if (count === 0) return messages[locale].zero;

  const numberOptions = { maximumFractionDigits: 0 };
  const rules = new Intl.PluralRules(locale, {
    type: "cardinal",
    ...numberOptions,
  });
  const category = rules.select(count);
  const template = messages[locale][category] ?? messages[locale].other;
  const formattedCount = new Intl.NumberFormat(locale, numberOptions).format(count);
  return template.replace("{count}", formattedCount);
}

本次在 Node.js v24.21.0、ICU 78.3 中实际运行了代码块里的函数，对英文数量 0、1、2 分别得到 “No files need attention.”、“1 file needs attention.”、“2 files need attention.”。这验证的是该机器上的这段最小示例输出，不是浏览器兼容测试，也没有验证其他语言译文。

这是展示流程的最小示例，不是完整国际化库。它只含英文消息，业务明确约定文件不可为负数且只显示整数；其他语言必须有自己经审核的完整消息和相同状态语义。若输入来自可计量的小数、货币或精度敏感的值，整数选项就不适用。真实应用还应区分无效输入和服务错误的 UI，而不是只抛异常。

类别中的 zero 与产品空状态，是一回事吗？

不是。zero 是某语言复数规则可能返回的语法类别；“目前没有待处理文件”则是产品可以选择的状态文案。CLDR 指出，即使语言没有独立的零类别，界面仍可能需要特别的零值消息；反过来，语言提供 zero 类别，也不要求产品把所有零值都显示成“什么也没有”。例如，数量为零时，消息可能是“没有待处理文件”，也可能是“已完成 0 项”，具体取决于目标是引导用户开始、报告统计，还是强调筛选条件。前者应由产品语义决定，再由翻译表达，而不是从类别标签推导出来。

这也解释了为何示例中先检查确定的零，再调用类别选择器。若产品希望把零当作普通计数句的一部分，就可以不加这段特殊分支；若需要一个专门的空状态，它就应该是显式的产品分支，不能依赖某个语言碰巧把 0 归入 zero 或 one。空状态还可能带有按钮、插图或下一步提示，已经超出一个名词词形能表达的范围。

数字显示和类别选择要一起验证

数量选择与数字格式化是不同职责，但它们可能受相近选项影响。MDN 的 Intl.NumberFormat 构造器说明 列出了数字位数与舍入选项。Intl.NumberFormat 负责千位分隔符、数字系统、小数位和舍入；Intl.PluralRules 负责依据目标语言选类别。对小数或会舍入的值，若选择类别时按一种精度理解数字，显示时又把它按另一种精度舍入，文案的数字与语法就可能不一致。将兼容的 minimumFractionDigits、maximumFractionDigits、roundingMode 等选项对齐，并以实际目标环境验证，能减少这种偏差；但并不是每种业务数都应该先舍入。比如余额、计量单位和“约数”文案有各自的精度契约，不能为了复数方便改变数值含义。

CLDR 的指南特别提醒，某些语言会根据小数位及其可见尾随零来区分类别；示例包括 1、1.0 与 1.00。JavaScript 的 Number 数值本身不能保留输入文本中“用户输入了几个小数位”这一词法信息。因此，如果产品确实需要表达原始精度，应在解析阶段保留十进制字符串或定点数/十进制类型，再通过适合的消息格式工具处理，不能指望将字符串转成普通 Number 后还能恢复输入精度。若小数精度并不影响语义，则明确采用数值格式化规则，避免把输入格式偶然当作语义。

pluralCategories 能当成翻译键清单吗？

它能帮助测试一套具体运行时配置，但不能当作翻译完成证明。MDN 对 resolvedOptions() 的说明指出，pluralCategories 是当前语言可用的类别数组；它会给出当前语言及基数/序数类型可返回的类别集合。它适合用于生成缺失键检查：消息目录若没有本地化类别，可以告警；测试也可以为每个类别选出能触发它的数值。单纯拿类别数组里的名字逐个“试 select”没有意义，因为类别字符串是输出值，不是测试数字。

本次本地探测使用 Node.js v24.21.0、ICU 78.3：en 的类别集合为 one, other，ru 为 one, few, many, other，ar 为六类；在该环境中法语的 0 与 1.5 都返回 one。这只是本机观察，不等同于浏览器覆盖保证。类别规则来自随运行时提供的国际化数据。Unicode CLDR 49 发布说明日期为 2026-10-22，其中调整了若干语言的复数/序数规则，并修正挪威尼诺斯克语 nn 继承挪威语规则的问题。这说明语言规则会随 CLDR 数据版本变化；应用实际行为取决于浏览器或 Node 所带的 ICU/CLDR 数据，不能只看开发者电脑上的一份列表就假定所有客户端完全相同。目录校验可按项目支持的运行时基线生成，但面向真实用户仍应覆盖目标设备与浏览器，记录版本差异。

验证时先定义产品状态矩阵，再定义语言矩阵：加载、失败、确认零、普通整数、语言规则边界、小数（如果业务允许）、基数与序数分别成组。每个数值要同时检查选择出的类别、渲染的完整句子和最终显示的数字。以俄语为例，官方 CLDR 规则指南展示 1、2、5 和 1.5 可能分别触发 one、few、many、other；这不等于此文给出了完整俄语翻译，只说明只测 1 和 2 会漏掉类别。对阿拉伯语则可从六类集合选择代表性值。实际测试数字应根据目标运行时的 select() 结果确定，并对分数和舍入选项重复验证。

序数也需要单独测试。英文中基数 2 属于 other，序数 2 属于 two；这一差异能作为快速检查，确保代码没有把 type: "ordinal" 和基数消息混用。若产品支持区间（例如“显示第 2–4 项”），不要擅自选范围终点的类别。MDN 的 selectRange() 文档说明了范围类别选择；ECMA-402 为实现定义了 selectRange()，可用时应验证它和完整范围消息的配合；若目标环境不支持，就采用项目明示的兼容策略，而不是伪造统一结果。

自动化测试可以检查类别覆盖、缺少模板、状态分支、异常输入和数字格式化一致性。它不能判断译文是否自然、语气是否正确，或“没有结果”是否比“0 条结果”更有帮助。后两项需要熟悉目标语言并了解产品场景的人审阅完整页面。本文记录的是标准和本地运行时观察，不声称对所有语言、浏览器或用户界面执行了验证。

实现复数消息时，先让产品定义数值状态和零值含义，再决定基数、序数或区间模型；让翻译者提供完整句子；随后把格式选项、运行时矩阵与译文检查接进测试。这个顺序比先写一个 count + (count === 1 ? "" : "s") 更能避免错误被封装进共享工具。若只需要某个受限语言的内部原型，简单规则也许够用；一旦消息面向多语言用户，类别选择和句子生成就应该成为两个清楚、可分别验证的职责。

这和表单校验反馈有相同的设计提醒：技术判断只能回答自己负责的问题，不能替产品决定用户应该看到什么。对于数量文案，API 回答“按当前语言规则归入哪个类别”，应用与翻译流程仍要共同回答“在这个状态下，哪一句话最准确”。
