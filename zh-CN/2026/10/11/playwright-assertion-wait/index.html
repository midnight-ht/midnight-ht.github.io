点击完成了，保存为什么还不能算成功？

Playwright 的 click 等待可操作性和触发的导航，却不替产品定义保存完成。按接口承诺选择可重读的业务结果，并区分受理、持久化和失败。

正文

核心要点

  • click 完成是动作层证据，不能替代保存契约。
  • 重试断言会重新检查 Locator，但已读取的字符串不会自动更新。
  • HTTP 202、提示条和持久化终态各自证明不同阶段。

locator.click() 已经返回，不代表“保存”这个业务承诺已经兑现。

Playwright 的自动等待规则会先等按钮满足可见、稳定、可接收事件、启用等操作条件；点击触发导航时，locator.click() 的 API 说明还规定它等待导航成功或失败。单页应用中的后台请求、队列任务、数据库提交和后续读取，则需要测试另行选择信号。测试不是多等几秒就更可靠，而是要明确自己究竟证明了哪一步。

把“保存成功”拆成不同状态

以编辑文档为例，页面可能依次经历“编辑中、提交中、服务器已受理、持久化成功、读取可见”。也可能在提交后进入“校验失败、权限失效或服务暂不可用”。这些状态不能压成一个绿色提示。按钮变成禁用，只能说明交互状态变化；提示条出现，只能说明前端走到了显示提示的分支；请求返回成功，只能说明响应符合接口当前的成功定义。究竟能否据此叫作“已保存”，取决于产品和接口把成功定义在哪一层。

这个例子是用于说明验收设计的假设流程，没有连接应用或运行 Playwright。假设接口对短任务返回最终内容，测试可以核对响应并检查页面显示；如果接口只返回任务编号和 HTTP 202，测试只能据此说明“任务已受理”，随后还应等待任务接口报告终态；RFC 9110 第 15.3.3 节定义 202 时明确说处理尚未完成。如果用户承诺的是刷新后仍能看到修改，单次 toast 甚至“提交请求成功”都不够，需要验证重新读取的结果。这里的“持久化成功”应以系统可观察的合同定义，而不是测试作者猜数据库何时落盘。

这也解释了为什么“等待一个页面变化”不必然正确。操作开始时按钮禁用很有用，但它通常是过程信号；短暂成功提示适合告诉用户请求已接收，却可能比最终保存更早出现。把任意一个可见变化当成终点，会让用例通过，而核心承诺仍未被检验。反过来，若产品的承诺本来就是“已排队”，坚持等待最终生成可能让正确的受理流程被误报为超时。先写清用户能得到的保证，再决定测试的终点。

重试断言会重读什么

网页断言文档说明，与普通值断言不同，网页断言可以重新检查 Locator。比如 await expect(locator).toHaveText('已保存') 会持续核对元素，直到条件满足或断言超时；断言超时文档当前列出的默认值为 5 秒。Locator 指南说明，每次使用 Locator 都会重新解析当前 DOM，所以页面重绘后仍能定位到匹配元素。不过，断言只知道文本是否符合预期，并不知道它是否来自持久化结果。

相反，若先执行 const text = await locator.textContent()，得到的是当时的普通字符串。之后即使页面重绘，变量也不会自动变成新文本。对这个变量写 expect(text).toBe('已保存')，检查的是捕获值，不是让 Playwright 回到页面重新读取。重试机制能解决“观察值晚一点才出现”，不能修复“选错观察对象”或“观察结果不代表业务合同”。这类差别不是语法细节：前一种失败应检查页面是否按时更新，后一种应重做验收设计。

时间预算也分层：“动作等待”与“断言等待”并非同一个计时器。该测试超时默认是 30 秒，异步 expect 断言超时默认是 5 秒，二者分开配置。某条断言用了 5 秒仍未观察到目标，只能说明条件在这段预算内没有出现；不能单凭超时判定服务端最终失败。给断言随意加到一分钟也不是修复：它可能延后反馈，把系统变慢、状态永远不终结或测试条件写错的问题一起藏起来。站内的超时预算分层按失败耗时区分动作、断言与测试钩子；超时诊断仍不替代业务信号。

先选事件，再执行点击

如果需要核对一次提交触发的响应，事件监听应在点击之前建立，避免响应先到、测试后开始等待的竞态；Playwright 的page.waitForResponse() 示例也按这个顺序注册等待。下面只是未执行的接口形态示意；URL、方法、响应码和页面提示都必须按实际应用合同替换：

const responsePromise = page.waitForResponse(response =>
  response.url().includes('/documents/42') &&
  response.request().method() === 'PUT'
);
await page.getByRole('button', { name: '保存' }).click();
const response = await responsePromise;
expect(response.status()).toBe(200);
await expect(page.getByTestId('save-status')).toHaveText('已保存');

这组检查至多证明：目标请求出现、响应状态是期望值、页面呈现了指定状态。它没有天然证明数据可以从后续读取中恢复。若产品契约规定 200 表示完整保存，响应可以作为一项证据；若 202 表示仅受理，等这个响应反而是正确阶段的结束，测试应继续查终态。站内HTTP 202 的终态契约讨论了受理与完成的不同责任。若响应可能由自动重试、后台刷新或另一条操作触发，还要把请求关联到当前记录和本次动作，不能只按宽泛 URL 抓到任意一条响应。

事件型等待也有适用边界。传统整页导航可以检查 URL 与新页面内容；单页应用通常无需导航，可能应等待用户可见状态；任务 API 则应等待明确的终态。若测试从授权路径以外读取后端状态，应说明凭据、数据隔离与该检查代表的合同，避免把测试专用直连误当成真实用户流程。每种信号都应回答两个问题：它与哪一次操作对应？业务允许在什么状态宣布完成？

toast 出现以后，还需要刷新验证吗？

只有当产品承诺包含“离开页面后仍保留修改”时，刷新或重新进入后的读取才是必要证据。若提示条的文案明确是“已提交”或“处理中”，它不承诺持久化，就不应强行把它测试成完成；若文案是“保存成功”，验收就应检查产品如何定义这个成功，至少覆盖后续读取或等价的持久状态信号。用更准确的提示文案区分“已受理”和“已保存”，通常比让一个状态标记承担两种含义更容易诊断。

相应的失败路径也应被看见：服务端拒绝请求时，成功提示不应残留；任务受理后迟迟没有终态，测试要能区分处理中与失败，而不是永远等；写入成功但页面更新事件丢失时，用例应区分服务端结果与浏览器反馈；同一页面存在多个“已保存”元素时，定位范围必须对应当前文档。点击的严格性检查也要求 Locator 只解析出一个元素。用 .first() 硬选一个匹配项可能压住真正的歧义，反而把断言连到了错误记录。站内的定位器严格性分析说明何时应缩小匹配范围；严格定位能避免错点，却不能证明提交结果。

用验收矩阵检查信号边界

重写用例前，可以先列出“输入动作、预期状态、失败状态、结束条件”四列。对假设的文档保存流程，慢响应应保持处理中直到终态出现；校验拒绝应展示可识别的错误且不得断言成功；HTTP 202 应先显示已受理、最终成功后才出现可读取结果；接口返回成功而刷新后内容消失，则应该让持久化验收失败；并发的其他文档更新不应使当前记录测试误通过。这里是建议的检查矩阵，未在真实应用运行，也没有测试日志或稳定性数据。

验证本身还需要两条边界。第一，测试隔离必须保证读到的是本次写入的文档，避免旧数据让“刷新仍存在”假通过；可用测试夹具提供唯一记录标识，并在结束时清理。第二，等待期限应来自测试环境和产品时限，而不是为消除红色报告反复放大。失败报告最好保留目标 Locator、最后观察到的状态、请求响应和跟踪信息，这样可以分清目标没出现、响应错误、状态尚未终结，还是测试压根没验证承诺。

自动等待让动作和断言更能容忍正常渲染时序，但不会替应用定义成功，也不会把一次提示升级成持久性证明。复查偶发失败时，先把那条断言改写成一句可检验的话：“我在等哪一个操作的哪一个业务状态？”如果答案是“按钮被点击了”，测试停在动作层；如果答案是“这条文档刷新后仍是新内容”，就应等待并读取能证明该状态的信号。本文没有执行示例或应用测试，步骤应在目标项目的接口合同与测试数据隔离条件下验证。
