接口返回 202，什么时候才能说任务完成？

HTTP 202 只确认接受处理。异步接口还要定义持久接受、终态查询、结果授权和不确定性恢复，不能把提交回执显示成业务完成。

正文

接口返回 202，说明服务器接受了请求进入处理流程；它不证明处理已经完成，也不保证请求最后一定会被执行。页面可以显示“已接受”或“处理中”，只有拿到应用定义的终态证据后，才能说明业务结果。这个区别听起来像状态码常识，实际会影响服务端何时可以返回、客户端何时重试、用户能否取回结果，以及权限变更后谁还可以查看任务。

HTTP 已确认的事实，到这里为止

RFC 9110 第 15.3.3 节把 202 Accepted 定义为：请求已被接受处理，但处理尚未完成；请求最后可能会执行，也可能在实际处理时被禁止。该标准还说明，HTTP 没有一种机制能从异步操作完成后重新发送原请求的状态码。标准建议 202 的响应表示当前状态，并指向或包含一个状态监视器，供用户查看进度估计。RFC 9110 于 2022 年 6 月发布，是 HTTP 语义标准；这不是某个队列产品的实现承诺。

因此要把“成功”拆成可分别证明的事实。第一，网络端点返回了 202。第二，应用是否已经持久记录了任务意图。第三，后台处理是否开始。第四，业务结果成功、失败或取消。第五，结果是否仍可被当前用户访问。第六，通知是否被投递或查看。HTTP 202 直接说明的只有接受处理这一层，后面各层必须由应用自己的状态、存储和结果接口说明。

把这几层写成用户界面用语，可以防止服务端与产品文案承诺不同：

服务端观察到的事实 可以展示什么 不能据此展示什么
当前请求完成同步校验，接口返回 202 请求已接受处理 业务结果已成功
任务意图已持久化，状态资源可查询 已提交，并提供状态入口 输出文件已准备好
应用记录成功终态，结果可访问且当前权限通过 结果已就绪或可下载 无条件永久可用

第三行仍受保留期限、撤权和删除策略约束；“成功”不是跳过授权检查的理由。这个表是本文的接口设计判断，RFC 本身只定义协议层接受语义。

一个任务号只是定位线索，不自动证明任务已持久化，更不是授权凭据。若服务在内存中建了对象就立刻返回 202，随后进程在队列写入之前崩溃，客户端拿到的回执可能指向一项永远不存在的工作。相反，如果接受语义承诺“任务已保存，可以恢复执行”，服务端就要先建立可恢复的记录，或把记录和队列投递放入能够处理部分失败的设计里。那通常涉及数据库与消息系统的双写问题，但具体用事务发件箱、工作表轮询还是其他方式，取决于实际技术栈；本文没有实现这些方案。

用资料生成任务看清边界

下面是假设场景，不是真实项目或已运行队列。用户提交一份资料生成请求，服务先验证输入和权限，再创建任务记录，随后由后台 worker 读取。可以把接受响应定义为“请求通过同步校验，任务意图已被持久记录，并有任务标识可查询”。这比“请求已到某个 Web 进程”更强，但仍然不等于文件已生成。

任务记录需要能解释生命周期，而不只是显示百分比。比如，queued 表示等待执行，running 表示 worker 已领取，succeeded 表示结果资源已生成且与任务关联，failed 表示最终错误已记录，cancelled 表示取消被确认。它们只是一个可能的应用模型，并非 RFC 规定的枚举。每个转换都要由实际事件触发：队列消息重复时，worker 是否可以再次领取；worker 在写出文件后、写入成功状态前崩溃时，重试会不会生成第二个结果；失败后重试是继续原任务还是创建新任务。这些问题若不回答，状态字段虽存在，却不能作为业务证据。

把一个中断点走完更容易看出风险：worker 领取任务后写出文件，随后在更新任务状态前崩溃。客户端此时仍会读到 running。重试的 worker 若重新写入另一个文件，可能产生重复结果；若直接把旧状态改成 succeeded，却找不到完整文件，又会发布一个坏结果。一个可讨论的修复是让输出使用稳定的任务派生键，并在发布 succeeded 前检查对象存在且校验完成；再次处理相同任务时复用或核对该对象。这里是设计推演，不是某个存储系统的保证，也没有实际运行。它说明终态应绑定可取回的结果，而不仅仅是 worker 曾经启动。

把状态与结果分开也很关键。succeeded 可以表示应用已登记某个结果标识，但下载端点仍需重新检查当前身份和对象权限。若任务提交时用户有权限，处理期间权限被撤销，结果是否可下载应依照产品和安全策略重新判断。任务 ID 难以猜中可以降低偶然枚举风险，但不能替代每次状态读取和结果下载时的授权。异步等待越久，原请求上下文与当前权限之间的差异越可能影响用户能看到什么。

状态查询、通知和生命周期各自承担不同责任

一个状态监视器可以是任务资源本身，也可以是单独的进度端点。响应中应说明当前状态，并在适合时给出预计完成时间或下一步查询位置；估计值若只是粗略的，应避免写成承诺。客户端还要知道哪些状态是非终态、哪些是终态，以及状态记录何时到期。已过期、从未存在和当前用户无权查看，是否返回相同表现，要在防止资源枚举与可理解错误提示之间做权衡。

轮询不是免费的。若几千个客户端都按很短的固定间隔查询，状态接口会成为新的负载源；如果间隔过长，用户又会长时间看到过时状态。可以采用递增间隔、服务端建议的重试时间或通知，但这些都要结合工作负载设计，不能从 202 推出一个通用秒数。通知也不等于终态本身：通知可能迟到、重复、丢失，用户可能没有打开它。只要用户仍需要恢复查询，系统就应该有状态读取路径，且通知记录最好和任务状态分开管理。

任务资源的保留时间也属于契约。保留过短，用户可能在回来之前就找不到结果；无限保留则增加存储、隐私和删除责任。过期以后，接口需要说明结果是否已清理、能否重新生成，以及怎样避免泄露“某个私人任务曾经存在”。删除任务与删除结果也可能不是同一个操作：后台审计记录可能有保留要求，下载文件却应立即撤销。产品和数据策略决定这里的边界，不是 HTTP 状态码。

客户端超时不能替代任务身份

如果客户端发出创建请求，却在 202 到达前网络断开，它不知道服务端有没有接受。盲目重发可能创建两份昂贵任务；但不重试又可能让用户以为请求丢了。稳定的幂等键可以把同一业务意图的重复提交关联到既有结果，但其作用域、保存期限、参数冲突规则要写进接口契约。相同幂等键配不同请求内容，应明确拒绝或返回原任务，不能默默选择一个。

这里有两个不同的超时。创建请求超时，意味着接受结果不确定；状态查询超时，只说明这次查询没有收到答案。后者不能把任务状态改成失败。界面可以保留“正在确认”的状态，让客户端稍后用同一任务标识继续查询。若任务标识也没收到，客户端可在幂等约定允许时用原业务意图重新查询或重试。具体恢复策略取决于服务器是否保存了幂等记录、记录是否过期，以及请求内容是否足以安全重放。

怎样验证“已提交”不是假终态

一种待执行的验收设计是按边界列出场景，而不是只断言创建接口返回 202：接受记录刚写入时进程重启；消息重复投递；worker 生成文件后、更新状态前失败；处理阶段发现权限已被撤销；通知重复或未送达；创建响应在网络中丢失而客户端重试；状态端点超时；任务或结果到期。每个场景都要检查任务状态、结果资源、再次提交行为、授权决定和用户提示。

验收前还要明确每个测试能证明什么。如果本地测试只模拟 worker 抛错，它不能证明生产队列的重复投递行为；如果端到端测试检查一个失败任务，它也不能证明长时间保留后的清理路径。教程和测试要记录实际环境、输入以及执行结果。本文没有运行队列、轮询、通知或上述测试，列出的只是测试计划，不是通过报告。

评审接口时，可以要求团队逐项回答：返回 202 前持久化了什么；哪一个状态和哪个结果资源代表业务终态；客户端在响应丢失时怎样避免重复任务；权限何时重查；状态记录与结果保存多久；通知失败后用户怎样恢复。只有答案能和实际接口行为对上，页面上的“已接受”才不会被悄悄翻译成“任务完成”。相关的业务幂等边界与对象级访问控制分别处理重试身份和资源授权，不能由 202 代替。
