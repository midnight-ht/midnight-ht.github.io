断点续传怎样避免把两个版本的文件拼在一起？

恢复下载时，偏移量并不代表文件版本。用 If-Range 判断是否可续传，逐项核对 206 的 Content-Range，并把 200 完整响应写入替换流程。

正文

核心要点

  • 偏移量只描述本地已有多少字节；恢复前还要确认它们属于当前选定表示。
  • 206 仍需核对 Content-Range 起点、长度和表示身份；200 完整响应要替换临时对象。
  • ETag 用于表示验证，不自动提供抗篡改证明；完成后仍按可信摘要或签名校验。

断点续传不能只凭本地偏移量追加数据：要先确认已有字节仍属于服务器当前选定的同一表示，再核对响应里的范围确实从本地下一个字节开始。若服务器返回完整的 200 OK，客户端必须走覆盖或新文件替换路径；把它接到旧文件后面，会把两个版本拼成一个无法解释的对象。

偏移量为什么不能证明版本一致？

假设某个导出文件 URL 在周一提供了 10 MiB 的版本 A，客户端收到了前 5 MiB 并把它保存到临时文件。周二同一 URL 被重新生成，仍是 10 MiB，但内容已变成版本 B。恢复程序若只读取本地文件长度，就会请求 Range: bytes=5242880-。服务器返回版本 B 的后半段后，拼接结果仍是 10 MiB；长度检查通过，内容却包含 A 的前半和 B 的后半。这个数字场景是用于说明机制的假设示例，不是运行结果。

偏移量回答的是“本地当前保存到哪里”，没有回答“这些字节来自哪份表示”。恢复状态至少要让资源地址、协商得到的表示、验证器、已持久化范围和临时文件身份彼此对应。如果不同语言、压缩编码或缓存变体可能产生不同字节，下载器还要确保恢复请求仍选择原来的变体；服务端的 Vary、请求头和内容编码属于这个选择上下文。把一个 URL 当作永远对应一个不变的字节序列，是很多混拼问题的来源。

HTTP 的 Range 请求描述的是从所选表示中取一段数据。服务器可以忽略范围；Accept-Ranges: bytes 能作为支持字节范围的信号，却不是对未来每次请求都返回 206 的承诺。RFC 9110 §14.2 明确允许服务器忽略 Range。同样，响应没有 Accept-Ranges 也不能单独证明服务器绝不支持范围。客户端应把实际响应当作状态机输入，而不是把先前探测结果当作永久能力保证。

If-Range 如何把旧字节和当前表示联系起来？

第一次接收内容时，下载器应保存服务器给出的强实体标签，例如假设值 ETag: "release-41"。恢复时同时发送 Range: bytes=5242880- 与 If-Range: "release-41"。RFC 9110 §13.1.5 的语义是：如果验证器仍匹配，服务器按请求处理范围；如果不匹配，服务器忽略 Range，改发当前完整表示，而不是返回一个让客户端误以为可继续追加的局部响应。实现必须把后一个结果当成“从新版本重新开始”的分支。

If-Range 不能使用弱实体标签。若客户端没有对应表示的实体标签，才可以考虑日期形式，而且 RFC 要求该日期是强验证器，并与当前选定表示的 Last-Modified 值精确匹配。许多系统的修改时间精度和更新流程不足以区分同一秒内的多次生成，因此不能把任意时间戳当成强版本号。适合的验证器取决于服务端如何生成表示；客户端拿不到可靠验证器时，完整重新下载通常比猜测更安全，也可以让业务使用包含不可变版本号的下载地址。

版本一致和防篡改也不是同一个目标。实体标签用于 HTTP 条件请求和缓存验证；应用不能仅凭一个 ETag 就声称文件具备密码学完整性。如果需求是检测传输损坏或确认供应方交付的确切文件，应另行取得可信的摘要或签名，并说明该值如何绑定到目标发布物、由谁签发、怎样验证。之后正文会回到这个区别，不把一次范围响应误当成最终安全证明。

收到 206 后，哪些字段决定能否追加？

沿用上面的假设，服务端若确认还是版本 A，恢复请求从字节 5,242,880 开始。预期是 206 Partial Content，其 Content-Range 应描述实际返回的区间，例如 bytes 5242880-10485759/10485760。这里的首个位置必须等于客户端当前已持久化的下一个位置；区间末端不能小于起点；在总长度已知时，完整长度必须大于末端。RFC 9110 §14.4 还要求接收方不要重新组合无效的 Content-Range。下载器不应看到 206 就不再检查。

单段 206 的 Content-Length 通常只表示当前消息这段响应体的长度，不是整份文件的总长度。Content-Range 才说明这段内容位于表示的哪里以及已知总长度是多少。检查时可用 末端 - 起点 + 1 与实际接收字节数对照，再检查新的偏移量等于末端加一。若服务器只返回多段中的一段，或返回的起点比本地偏移量更早/更晚，直接拼接会造成重叠或缺口；应停止组合并重新建立状态，而不是默默丢弃或重复写入字节。

若响应附带 ETag，应将它与恢复状态一并检查；若表示验证器、最终响应地址或内容编码和先前记录冲突，就不能把它写入旧对象。服务端也可能在代理或协商层改变所选表示。应用若决定接受无 ETag 的续传，至少要清楚 If-Range 是由哪个端点以何种验证器条件评估，并保留这一假设；对证据不足的路径选择重新下载，比“看起来范围正确”更保守。

为什么完整的 200 要走替换而不是追加？

沿用前面的 A/B 示例：若版本已变更，条件不匹配，服务器可以忽略 Range 并给出版本 B 的完整 200 OK。客户端若把这一整份 10 MiB 接到旧的 5 MiB 后面，落盘对象会成为 15 MiB；若客户端截断旧内容后写入 B，则得到新的完整对象。两种路径外观上只差写入模式，语义上却决定了版本是否一致。因此响应解析应先分流：合格的 206 才进入追加分支；200 完整响应进入全量替换分支；授权失效、重定向到登录页、服务器错误或意外内容类型进入错误处理，不能当成文件字节保存。

为了不在写到一半时丢掉唯一的旧文件，可以把每次下载写入独立临时对象。替换时先完整写入新临时文件，核对最终长度、适用的可信摘要或签名，再在文件系统支持的条件下切换正式文件名。续传时也可以先将新片段写入临时范围文件，核对偏移、字节数与元数据，再提交进度。原子重命名的行为取决于文件系统、跨卷操作和程序崩溃时点，HTTP 协议不提供本地文件事务；所以实际写入顺序仍要在目标运行环境验证。

并行分段会增加状态组合。若多个 worker 分别下载区间，它们必须针对同一验证器、同一表示选择和兼容的字节坐标工作。任何一段遇到不同 ETag、不同总长度、无效的 Content-Range 或完整 200，都应让整个批次失效，而不是只丢弃那一个分片后继续拼接。否则，一个表面完整的文件可能由几个不同版本各自贡献一段。是否值得并行，要比较网络并发带来的收益与调度、重试、存储锁及全批次重新下载的代价；对小文件，增加分段状态通常没有必要。

收到 416 和 bytes */N 时，能否把本地偏移修正为 N？

不应仅凭这个长度这样做。RFC 9110 §14.4 说明，416 响应中的 Content-Range: bytes */N 表示当前选定表示的长度。它告诉客户端当前长度是多少，却不证明本地临时文件包含了这份表示的前 N 个字节。若本地偏移大于 N，这可能表示服务端版本缩短、本地状态过期或请求选错了变体；直接把偏移改小会掩盖具体原因。若偏移刚好等于 N，也仍要确认这份对象的验证器和完整性条件，而不是把长度相等当作内容相等。

已有文章收到 416 和当前长度，文件就算下完了吗？用同长度不同内容说明长度证据的边界。若业务还需校验完整选定表示与实际响应内容的摘要，可以接着看Content-Digest 与 Repr-Digest 分别覆盖什么。它们回答的是摘要对象范围，不会替客户端自动确认旧的局部文件和当前 URL 指向同一发布版本；下载状态仍要把验证器、范围与完整对象检查串在一起。

如何让进度记录和磁盘内容保持同一步？

即使远端响应处理正确，客户端崩溃也可能使本地元数据和文件内容分离。若先把“已接收到 8 MiB”写进数据库，再把那部分字节写入磁盘，进程在两步之间退出，下一次会跳过并不存在的字节。若先落盘字节，再更新进度，崩溃可能导致重放同一区间；若写入按偏移定位且重复片段可识别，这比跳过缺口更容易恢复，但仍需明确校验策略。可行做法是将片段写入临时文件，确认长度及范围后再提交一个可恢复记录；或用小型日志记录操作开始、落盘和提交标记，在启动时重放/回滚未完成记录。具体设计取决于存储介质和崩溃一致性能力。

每条进度记录最好至少包括稳定任务 ID、最终请求地址或其版本上下文、所选表示的验证器、字节编码/解码策略、已确认区间、临时对象路径及最近一次已提交的文件位置。敏感的签名 URL、Cookie 和授权令牌不应明文写入通用日志；持久化任务若跨登录继续，还要定义令牌过期后的重新授权行为。HTTP 规范不会替应用保存这些状态，也不会保证移动设备断电后文件系统刷新与元数据事务同时成功。

大文件、弱网络或用户可暂停的传输更值得投入恢复状态管理。反之，如果资源小、能快速重下，或者服务端不提供稳定验证器，直接丢弃临时片段并从头开始，通常减少比特级校验和版本状态带来的维护成本。选择依据是重下的时间/流量成本、错误后果、服务端验证器质量、并发复杂度与本地存储可靠性，而不是“所有下载都必须断点续传”。

发布前可以怎样验证状态机？

可以用受控文件和假设版本制作验证矩阵，但没有记录就不能把矩阵说成已执行。先让服务以强 ETag "release-41" 提供固定字节，客户端获取一段后用相同 ETag 恢复，检查服务器返回 206、起始偏移正确且最终字节与从头下载的参考对象一致。然后只改变服务端表示和 ETag，再发送旧验证器：正确路径应收到完整 200，并把临时对象替换成新参考对象；断言最终长度和每个字节，而不只检查状态码。

再让测试服务故意忽略 Range、返回错位 Content-Range、改变总长度、返回 416 并给出 bytes */N，以及在响应中途断开连接。断言任何不完整或身份不匹配的片段都不会进入正式文件。随后在本地写入和进度提交之间注入进程终止，重启后核对恢复算法只可能重发已写区间或重新开始，不能跳过未落盘的区间。最后覆盖 401/403、重定向、过期下载凭证、内容编码变化和磁盘空间耗尽，以确认错误页或不同变体不会被写成“文件的一部分”。

完成证据分为三层：协议响应是否匹配请求，临时存储是否覆盖从 0 到总长度的完整范围，最终对象是否通过应用所要求的内容校验。若信任供应方提供的签名摘要，应验证签名与任务/版本的绑定；若仅有 ETag，就只报告 HTTP 表示验证，不升级成安全完整性结论。本文的数字均为假设例子，测试矩阵也是拟执行方案；这里没有运行下载程序、测试服务器、故障注入或实测传输，因此不声称兼容性、性能、完整性或生产效果已经验证。

评审断点续传实现时，最值得先看的不是进度条能否走到 100%，而是两个写入分支：收到匹配表示的正确范围时，是否按准确偏移追加；收到完整响应时，是否先隔离旧片段再替换。随后再检查持久化进度与字节落盘的先后关系。把这三处状态边界写清楚，才知道失败后应续传、重下还是报告版本冲突。
