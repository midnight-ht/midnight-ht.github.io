逐行保存点之后，如何给出可信的 PostgreSQL 导入回执？

SAVEPOINT 只能局部回滚，不能逐行提交。把输入身份、接受与拒绝明细和任务终态放在可查询的提交契约中，才能在提交失败或断线后返回可信导入结果。

正文

SAVEPOINT 能让一个坏输入回滚到局部位置，然后继续处理后续输入；它不会把每一行变成独立提交。要给部分导入一个可信回执，应用必须把已接受的数据、拒绝原因和最终任务状态放进明确的外层提交边界，并用稳定的任务和输入身份让客户端在确认丢失后查询结果。否则，接口可能报告一批“成功记录”，而数据库最终把整批事务回滚。

保存点解决的是事务恢复，不是产品语义

PostgreSQL 19 的 SAVEPOINT 文档把保存点定义为当前事务内部的标记。ROLLBACK TO SAVEPOINT 丢弃标记之后的命令并恢复事务状态；回滚点本身仍然有效。RELEASE SAVEPOINT 则释放该标记，并把没有回滚的更改合并回上层事务。它不是 COMMIT。官方事务教程说明，外层事务提交前，中间状态对其他事务不可见；外层失败时，多步事务作为整体回滚。

因此，“逐行保存点”描述的是局部恢复策略，不是“每行成功就已持久化”。假设一个通讯录导入要写联系人表，并生成逐条结果。第三行邮箱违反唯一约束时，应用可以回滚第三行的数据库修改，再把它记为拒绝，之后继续第四行。但若第九十行之后结果表写入失败、后续语句因死锁中止，或最终提交失败，那么之前接受的联系人、已经写入的成功明细和拒绝明细都属于同一个外层事务，也会一起消失。

这不是保存点工作错误。保存点提供了“丢弃局部更改、保留事务前序工作”的机制；产品要决定的是输入是否可以部分接受、失败明细要保持多久、最终回执何时可读，以及未知结果时怎样恢复。若业务要求整份文件要么全部有效、要么完全不改，那么逐行跳过错误本身就违背了产品契约，保存点不应被当成默认答案。

先持久化一个可查询的任务身份

把用户提交的文件映射到稳定的 import_id，并记录输入摘要或版本。任务记录可以有 running、committed、failed、needs_reconciliation 等状态；每条输入还需要稳定的 source_key。原文件行号可以作为展示位置，但重排、追加表头或重新导出都可能改变它，因此不能只用行号判断重试时的“同一条记录”。

一个可解释的简化流程是：先在短事务中创建或取得唯一的任务记录，提交后状态为 running；第二个事务处理业务数据、逐条结果以及任务终态；只有第二个事务成功提交后，外部查询才会看到 committed 和完整回执。这样，工作进程崩溃或提交响应丢失时，客户端可以用同一 import_id 查询，而不是新建一个任务把整份文件再写一次。相同身份但输入摘要不同，应该返回冲突或要求新的任务身份，不能悄悄把另一份文件套用旧回执。

以下只是说明事务边界的伪代码，不是可直接复制的完整实现，也没有在 PostgreSQL 上执行。表字段、隔离级别、约束和并发领取方式需要按实际模型设计：

BEGIN
  对每条输入，使用稳定 source_key：
    SAVEPOINT one_input
    尝试写入业务记录
    如果是允许逐条拒绝的输入约束错误：
      ROLLBACK TO one_input
      写入该 source_key 的 rejected 结果
      RELEASE one_input
    否则如果写入成功：
      写入该 source_key 的 accepted 结果
      RELEASE one_input
    其他数据库错误：中止整笔事务
  根据结果表计算汇总，而不是相信进程内计数
  在同一事务内将任务更新为 committed 并保存汇总
COMMIT

写入顺序决定报告能否和数据保持一致。成功路径中，接受结果与业务行在同一个保存点释放之前或同一外层事务中一起写入；否则可能出现联系人已写入、报告却没有对应 accepted 行。失败路径中，先回滚失败输入的局部事务，再写拒绝明细；如果拒绝明细本身写不进去，就停止整批并回滚外层事务。不能把“记录失败原因失败了”吞掉后仍声称回执完整。对于错误分类，也不应把所有 SQL 异常都当作可跳过的坏数据：应用可以把经过确认的输入约束错误（例如指定约束名或 SQLSTATE）列入拒绝白名单；即使数据库机制允许在保存点处回滚其他语句错误，死锁、序列化失败、权限配置错误或结果表故障仍应按系统级失败处理，而不是伪装成用户输入无效。

任务终态要与业务数据和逐条报告在同一事务中更新。客户端看见 committed 时，关联的接受记录、拒绝记录和汇总应当已经一起提交；在提交前，其他会话应该只看到持久化任务仍处于 running。若应用先在内存里累加“接受 90、拒绝 10”，先返回成功，再尝试数据库提交，这个数字只是一次尚未确认的计算，不是回执。

把这个规则落到一个三行的假设输入上：row-A 通过验证并写入联系人，结果记为 accepted；row-B 的邮箱与已有联系人冲突，回滚 row-B 保存点后写入带约束名称的 rejected 结果；row-C 通过验证并写入联系人。提交事务之前，新的 row-A、row-C 和三条结果对其他会话都不可见，持久任务仍是 running。提交成功之后，客户端才读取到两条已接受、一条已拒绝及对应原因。若 row-C 之后汇总更新失败，以上业务变更和逐条结果都不提交，之前创建的任务头仍显示 running，等待重试或核对。数字只是说明数据关系的示例，不是实测结果。

提交确认丢失时，不要盲目重放文件

一种常见边界不是数据库明确返回失败，而是客户端发出 COMMIT 后连接断开：应用没有收到结果，无法仅凭网络错误推断服务器已提交还是已回滚。此时要用原 import_id 查询任务。若状态为 committed，返回数据库保存的报告；若仍是 running，由任务所有者或协调器按租约、心跳和输入摘要判断是否可以安全接管；若短暂不可确定，则返回“处理中/待核对”，不要把未知伪装成失败或成功。

查询和重试必须有并发规则。两个工作进程不能同时用相同任务身份插入同一批结果，再各自把任务置为完成。可使用唯一约束阻止重复的 (import_id, source_key)，并在领取任务时以行锁、租约或等效的所有权机制仲裁；但这些是需要按数据库版本、隔离级别与作业模型验证的设计选项，不是保存点自动提供的保证。若业务数据的写入可重放，唯一键或明确的 upsert 冲突目标可以帮助定义重复处理行为；PostgreSQL 的 ON CONFLICT 面向唯一或排斥约束冲突，不能把类型错误、外键缺失、触发器错误或任意业务校验都变成可忽略错误。

如果任务工作很大，单个外层事务会长时间持有锁并延长回滚窗口。将输入切成多个已提交块可以降低每个事务的规模，但它改变了可见性和取消语义：前面已提交的块不会因为后续块失败而消失，回执必须暴露块边界、游标和重试规则。按块提交不是“优化实现细节”，而是另一种产品承诺。先用数据量、锁等待、失败恢复时间和用户对部分可见结果的接受程度来选择，而不是假定更小事务一定更快。

区分坏输入和整笔事务失败

对预期的逐行数据问题，例如一个字段值无法满足应用定义的合法范围，逐条报告往往有用。对数据库并发导致的死锁或序列化失败，把当前事务记成某行无效则会误导用户。PostgreSQL 文档建议在死锁发生时重试被中止的事务；Repeatable Read 和 Serializable 下的序列化失败也要求从事务开头重试。重试应重新执行完整事务逻辑，并确保任务身份与数据写入具备幂等约束；不能仅从失败语句继续。

也不要把序列主键的空洞当成导入丢行的证据。nextval 分配的值在事务回滚时不会被收回，冲突或故障也可能造成编号间隔。可靠的报告要以任务结果表和稳定来源键为准，而不是用连续 ID 推算已接受的记录数。

如果输入主要是格式转换问题，PostgreSQL 19 的 COPY FROM ... ON_ERROR 提供 ignore 和 set_null 等处理方式；文档将其限定在输入值转换为目标数据类型时遇到的错误，并说明可记录汇总数量，在 verbose 日志级别输出具体行和列信息。它并不等于通用业务验证、外键修复或逐记录结果 API。批量装载到 staging 表、再用集合查询校验，常常更容易保留每行的来源身份和错误类别；但选择 staging 还是逐行保存点，要基于约束复杂度、批量规模、可维护性和测量结果。这里没有运行性能对比，也不能据此声称哪种方式更快。

让回执和副作用共享正确的边界

数据库事务能回滚数据库里的变化，不能撤销已经发出的邮件、HTTP 请求或消息。若每接受一条联系人就立即调用外部服务，后来外层事务回滚时，外部动作仍可能已经发生。通常应把待发送副作用写成同一数据库事务中的 outbox 记录，由提交后的投递器发送，并用稳定事件键处理重复投递；或者明确采用可补偿的业务流程。无论选择哪种方式，都要记录发送失败、重放和补偿路径。不能说“加了 SAVEPOINT 所以整个导入跨系统原子”。

验收要检查状态转换，而不只是捕获异常

在实际实现里，至少验证这些路径：一条可拒绝的输入失败后，后续合法输入是否按产品约定处理；拒绝结果表不可写时，外层事务是否整体失败，而不是留下没有解释的数据；最终提交失败时，客户端是否只看到未完成或可恢复的状态；在 COMMIT 响应丢失后，用原任务身份能否读到真实终态；同一任务、同一 source_key 重试是否会重复插入或重复计数；不同文件错误地复用同一任务键时是否被识别；死锁或序列化失败是否从整个事务重试；自增序列出现空洞时报告是否仍以结果明细为准；日志是否避免泄漏整行个人数据。

测试不仅要断言抛出了异常，还要读取提交后的业务表、任务表和结果明细，确认它们之间的对应关系。也要在不同连接中检查未提交的 running 进度不会被误读为 committed。若使用分块提交，则另加“第 N 块成功、下一块失败”与恢复游标用例，确认产品确实接受部分块已经可见。以上是验收设计建议，本文没有运行 PostgreSQL、SQL 片段或压力测试，不包含实测性能结论。

真正的边界是：只要回执依赖外层提交，它就必须在外层提交之后对外宣称成功；只要任务身份和结果明细稳定，客户端才有办法在超时后确认发生了什么。先决定批次原子、分块可见还是逐条独立提交，再选保存点、staging 表或异步任务状态。对于异步接口，可与202 请求的终态查询契约一起设计；对于客户端重试身份，可参考接口重试与幂等键。保存点是局部恢复工具，可信回执来自一致的状态模型和可验证的提交边界。
