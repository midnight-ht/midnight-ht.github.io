用一张生命周期图选对 PostgreSQL 的 ON DELETE 动作

用订单明细、商品目录和历史快照区分 CASCADE、RESTRICT、NO ACTION 与 SET NULL，并说明如何验证删除范围。

正文

外键的删除动作应按两端对象是否共享生命周期来选：只能依附父记录存在的组成项可以随父项级联；共享对象或仍承载历史意义的对象，应阻止删除、保留快照或解除可选引用。PostgreSQL 会忠实执行声明的引用动作，但不会替产品定义“删除”究竟代表隐藏、归档还是物理销毁。

这也是代码评审里容易被一句“数据库会帮我们清理”带过的地方。外键解决的是引用仍然成立吗；产品操作解决的是用户到底授权删除什么。两件事相关，却不是同一个判断。

外键描述引用，不能证明所有权

设想一个订单系统：订单明细属于一个订单，订单使用的商品却来自共享目录。订单关闭后，明细不再需要独立存在；商品可能同时被许多订单、报价和报表引用。若所有外键都用 ON DELETE CASCADE，删除一个商品可能沿引用图删掉历史明细，而调用方原本只想让该商品停止售卖。

这是用于解释模型选择的假设例子，不是本站记录过的事故。它提醒我们，外键图上的每一条边都需要单独命名语义：这是真正的组成关系、可选属性、共享引用，还是必须保留的历史关联？同一张父表可以连出不同生命周期的对象，不应给整张表统一套用一种动作。

PostgreSQL 19 的约束文档用订单、订单明细和商品说明这个区别：明细可以是订单的组成部分，而订单与商品是不同对象；删除动作应由两表代表的对象关系决定。文档描述的是数据库行为，下面的生命周期分类和评审步骤是编辑给出的建模方法。

从一条删除边开始画生命周期

先不要看“哪种动作最方便”，而是沿着一次业务删除逐边问四个问题：

  1. 子记录离开父记录后，是否仍然有可解释的含义？订单明细通常需要订单语境，可能是专属组成项。
  2. 被引用对象是否可能被多个主体共享？商品目录、人员账号、标签通常可能共享。
  3. 子记录是否保存了无法从当前主表还原的历史事实？订单成交时的名称、SKU、单价往往应作为成交快照保存，而不是在读取历史时重新取商品当前值。
  4. 调用者请求的是不可逆物理删除，还是停止展示、停用或进入待清理状态？如果只是下架，删除目录行通常不是必要动作。

答案会随业务变化。例如，商品可能先被单一订单引用，后来上线批量导入或复用目录；以前看起来安全的级联就会改变影响范围。关系约束是长期数据契约，代码评审应检查未来的共享路径，而不只验证今天的界面操作。

把它画成最小的关系图时，可以先写两条边：orders → order_items（专属组成，CASCADE）；products → order_items（共享引用，RESTRICT）。旁边再标出成交快照和删除请求类型。这样“生命周期图”不是图形装饰，而是一份能和外键声明逐项对照的删除范围表。

用订单明细区分级联与共享引用

下面的结构把订单明细视作订单的组成部分，把商品目录记录视作可被共享的对象。成交时的事实另存为快照；商品行有订单引用时，数据库先阻止物理删除。

CREATE TABLE products (
    product_id bigint PRIMARY KEY,
    sku text NOT NULL,
    discontinued_at timestamptz
);

CREATE TABLE orders (
    order_id bigint PRIMARY KEY,
    created_at timestamptz NOT NULL
);

CREATE TABLE order_items (
    order_item_id bigint PRIMARY KEY,
    order_id bigint NOT NULL
        REFERENCES orders(order_id) ON DELETE CASCADE,
    product_id bigint NOT NULL
        REFERENCES products(product_id) ON DELETE RESTRICT,
    sku_at_purchase text NOT NULL,
    item_name_at_purchase text NOT NULL,
    unit_price_at_purchase numeric(12, 2) NOT NULL
);

CREATE INDEX order_items_order_id_idx ON order_items(order_id);
CREATE INDEX order_items_product_id_idx ON order_items(product_id);

这段 SQL 是设计示意，没有在本次任务中运行。删除订单时，外键可以清理只属于该订单的明细；删除仍被明细引用的商品则会失败，调用方应说明商品仍关联历史订单，并引导使用停用状态。订单明细里的快照字段回答“当时成交的是什么”，当前 products 行回答“现在目录里有什么”，两者不应混为一个读取来源。

如果产品确实允许从目录彻底移除商品，但历史明细必须保留，可把 order_items.product_id 设计成可空，并为这条外键选 ON DELETE SET NULL；快照仍是历史展示依据。这个方案把“当前可追溯到目录行”变成可选信息。若审计或运营流程要求永远保留目录关系，就不应为了让删除按钮顺畅而改成可空。SET NULL 也会受 NOT NULL、复合键及其他约束限制；动作执行后仍必须满足剩余约束。

若所谓“删除商品”只是停售，更直接的命令通常是更新 discontinued_at 或独立的 active 状态。此时订单与目录的外键保持完整，前台查询按销售状态筛选。把停售建模成物理删除会额外引入历史快照、引用解除和误删恢复问题；但软删除也不是免费的，它要求各查询一致处理状态，并明确最终清理时点。

NO ACTION 与 RESTRICT 只在需要时拉开

PostgreSQL 的默认删除动作是 NO ACTION。如果语句结束或约束检查时仍有悬空引用，就会报错；当外键被声明为可延迟时，同一事务可以先删除被引用行，再通过其他语句删除或修正引用，等约束检查时再决定是否仍违反规则。

RESTRICT 则更早拒绝删除已被引用的行，不能把这次检查延后。PostgreSQL 19 的 CREATE TABLE 参考明确区分两者：它们最终都能阻止遗留引用，但对“事务中暂时不满足、稍后修复”的流程并不等价。如果业务不会在一笔事务里暂时打破引用，再统一恢复约束，使用默认 NO ACTION 通常就足够；选择 RESTRICT 是想表达此处不允许删除动作进入这种中间状态。

CASCADE、SET NULL 和 SET DEFAULT 都是数据库直接执行的引用动作；默认值若仍指向不存在的目标，SET DEFAULT 也会失败。复合外键还有更细的边界：PostgreSQL 19 允许 ON DELETE SET NULL (author_id) 只清空指定列，保留仍属于主键的 tenant_id。这是 PostgreSQL 的扩展语法，不能在未核对目标数据库能力时当作跨数据库通用写法。

删除前先核对影响图和失败路径

一次 API 请求可以很短，级联路径却可能穿过多张表。评审时应从被删行出发列出所有下游表，把专属子项、共享引用、历史快照、审计数据分别标出，并回答哪个约束会阻止删除。若路径跨服务，某个服务的本地外键无法替另一个服务保证生命周期一致；就需要明确删除状态如何传播、失败如何重试，以及两边分别保留什么证据。

在可恢复的测试库中先查目标行和相关明细，再用事务演练删除，检查数据库最终状态，最后回滚演练。示意流程如下，须根据真实主键、权限与租户条件改写；本例未执行，因此不代表生产操作或成功日志：

BEGIN;

SELECT order_id
FROM orders
WHERE order_id = 4201;

SELECT order_item_id, product_id, sku_at_purchase, unit_price_at_purchase
FROM order_items
WHERE order_id = 4201;

DELETE FROM orders
WHERE order_id = 4201
RETURNING order_id;

-- 再查询 order_items 与 products，检查级联影响和仍保留的目录记录。
ROLLBACK;

DELETE ... RETURNING 返回被该语句直接删除的订单行，不应把它误读为数据库自动删除的每一条明细清单；演练后要单独查询关联表，判断级联范围是否符合预期。出现 RESTRICT 或 NO ACTION 错误也不一定是约束设计错了：它可能恰好阻止了一个仍被历史记录引用的对象被物理销毁。线上路径还需检查调用方展示、权限、重试、并发请求与备份恢复流程，本文章没有测量这些系统行为。

索引也属于删除路径评审。PostgreSQL 会为被引用的主键或唯一键提供索引，但创建外键不会自动为引用侧列建索引。官方文档指出，对被引用列执行删除或更新时，数据库需要查找引用侧的匹配行，引用侧索引在很多情况下有帮助。索引是否值得建立取决于数据量、写入与查询负担；应使用实际查询和代表性数据验证，本文没有性能测试结果。

“要级联吗”的实际追问是什么

这个问题需要补上标题没有回答的检查条件：如果子记录离开父记录仍有历史或共享含义，不要用级联把它删掉；如果只是可选当前关联，可考虑保留快照并解除引用；如果它只是父记录不可分割的组成项，级联才符合生命周期。动作选择之后，还要在可恢复环境中核对所有受影响表、约束报错与回滚结果。

因此，数据库评审不该只问“这条外键是否正确”，还要问“这个删除动作代表哪个业务主体授权的范围”。先按生命周期标注每条边，再让外键落实该边的约束；不要让一条方便的 CASCADE 替代删除政策。
