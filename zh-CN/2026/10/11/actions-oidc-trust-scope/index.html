GitHub Actions 用 OIDC 后，AWS 生产角色还该信任谁？

GitHub Actions 通过 OIDC 换取 AWS 临时凭据后，仍需分别限制令牌申请、角色信任声明和角色权限；本文解释 subject 格式变化、Environment 分支条件与拒绝路径。

核心要点

  • OIDC 把长期访问密钥换成工作流申请的短期凭据，但不会自行判断工作流是否可信，也不会缩小 AWS 角色获准执行的操作。
  • AWS 信任策略至少要把受信身份约束到预期的 audience 与 subject；使用 GitHub Environment 时，subject 上下文不同，分支限制可能需要单独检查 ref。
  • 2026 年 7 月 15 日后新建的 GitHub 仓库默认使用含 owner ID 和 repository ID 的不可变 subject；旧仓库默认保留旧格式，直到选择加入，改名或转移也要核对。
  • 正确的验证同时覆盖预期作业可换取角色、其他仓库或环境被拒绝、角色不能执行多余操作，以及日志不暴露原始令牌。

OIDC 解决的是“工作流怎样换取短期凭据”，不是“哪些工作流值得信任”。GitHub Actions 接入 AWS 时，至少要分别检查三件事：作业能否申请 GitHub 的 ID token、AWS IAM 信任策略允许哪个身份换取角色，以及这个角色拿到凭据后可以操作哪些资源。删掉长期密钥只改变凭据的取得与生命周期；另外两条边界若仍然宽，生产权限依然可能落到不该获得它的执行路径上。

三层权限不是同一项设置

先看请求端。工作流需要声明 id-token: write，GitHub 才允许该作业向 OIDC 提供方请求 JWT。这个权限针对“请求令牌”，不等于允许写 AWS S3、改 IAM 或部署生产资源。按GitHub 的 AWS 接入说明，认证 action 取得 JWT，再把它交给 AWS STS 的 AssumeRoleWithWebIdentity；AWS 验证签发者、受众和角色信任条件后，才返回临时角色凭据。各步骤的权限含义不能因为 YAML 中出现了 write 就混为一谈。

第二层是角色信任策略。它回答“哪个外部身份可以承担这个角色”。AWS 的官方角色信任示例至少检查 token.actions.githubusercontent.com:aud 与 token.actions.githubusercontent.com:sub。默认 audience 通常是 sts.amazonaws.com，但具体值也取决于使用的 AWS 分区和认证 action 配置。subject 则表示仓库及执行上下文。AWS IAM Access Analyzer明确提醒，若 sub 使用不加约束的通配符，组织外或不受控仓库的 Actions 可能进入角色承担范围。把条件写成方便所有工作流通过的宽泛匹配，等于把移除密钥的收益换成了更大的身份入口。

第三层是该角色实际获得的 AWS 权限。信任策略通过只说明“可以拿到这类临时凭据”，不会自动使其只读或只写一个存储桶。角色的身份策略、资源策略以及可能存在的会话限制，决定了拿到凭据后实际能做什么。假设一个生产发布角色只能由一个固定仓库的生产作业承担，但它仍被授予整个账号的管理员权限，那么身份入口缩小了，误用或工作流被攻陷后的影响面却没有相应缩小。反过来，一个只允许上传指定静态资源前缀的角色，即使信任范围需要多个受控作业，也可能把单次失误限制在较小资源范围内。两层都要独立审核。

subject 必须对应实际工作流上下文

许多旧示例使用 repo:组织名/仓库名:ref:refs/heads/main。它不是适用于每种 GitHub Actions 工作流的固定字符串。GitHub OIDC reference说明，若作业通过 GitHub Environment 运行，默认 sub 会包含 environment:环境名，而不是用分支上下文作为末段。AWS 的指导补充，如果 subject 没有包含分支，例如它只指向 Environment，则应在 token.actions.githubusercontent.com:ref 条件键中另行约束分支。只把旧的 ref subject 搬进新环境作业，常见结果是信任条件不匹配、STS 拒绝承担角色；为了“修复登录”而把 sub 改成 repo:组织/仓库:*，又可能让所有分支、标签或环境共享同一入口。

实际维护可以先用一个身份矩阵代替猜字符串。比如，假设预览作业仅允许从 preview 分支承担预览角色；生产作业则必须关联名为 production 的受保护 Environment，并只允许受保护主分支承担生产角色。这是用于讨论的假设设计，不是本站账户或 AWS 配置。矩阵要分别记录仓库、ref、Environment、audience、角色 ARN 和角色资源权限。然后从 GitHub 文档列出的默认 subject 格式出发，对照实际作业会生成的上下文，再核对 AWS 策略的键和值。名字中的冒号会被 GitHub 按文档规则编码；Environment 名称里的冒号也可能成为匹配失败的来源。策略应精确表达期望的路径，而非在失败后逐步增加 *。

2026 年的默认 subject 变化要核对仓库年龄

GitHub 的OpenID Connect reference当前说明：2026 年 7 月 15 日之后新建的仓库默认使用包含组织与仓库不可变 ID 的 subject，例如 repo:octo-org@123456/octo-repo@456789:ref:refs/heads/main。此前创建的仓库默认仍使用旧格式，除非组织或仓库选择启用不可变 subject；在该日期之后发生的仓库改名或转移也会转到新的不可变格式。GitHub Enterprise Server 不在这项默认格式 rollout 的适用范围内。GitHub 于2026 年 4 月 23 日公布此变化，并在 6 月 10 日更新了 ID 分隔符示例；所以策略评审应以目前 reference 和实际仓库令牌为准，不要复制早期文章中的连字符格式。

这项变化改变了名称稳定性，却没有替团队选择授权边界。不可变 ID 能降低仓库被改名、删除后名称被重新占用时，旧的名称条件意外匹配新仓库的风险；但若策略只限制一个组织 ID、仍允许该组织全部仓库承担生产角色，授权范围仍然很大。相反，如果在仓库改名后继续使用旧 subject，合法作业会被拒绝。修复顺序应是检查仓库创建时间、是否启用自定义格式、是否改名或转移、实际 token claim，再更新信任条件和拒绝测试；不要先扩大模式，之后再指望审计发现遗漏。

另一个边界也值得写进设计说明：GitHub 的 AWS 接入页提示 AWS 不支持 OIDC custom claims，但这不等于 IAM 只能检查 aud 和 sub。AWS 的condition context keys 文档列出了 GitHub Actions 的标准声明映射，包括 repository_id、ref、environment 与 job_workflow_ref，可以据此约束角色。这里要区分“使用发行方提供的标准声明作为 IAM 条件”和“改变令牌 sub 的组成或依赖任意自定义声明”；两者不是同一件事。写策略时核对 AWS 当前映射的键和值，并确认 GitHub 实际签发的 subject 格式，再选择提供方真正支持的约束。如果目标是要求经审批的 Environment，还要确认环境保护规则实际配置。只凭 GitHub reference 的通用模板或一句 custom claims 说明，都不足以代替这两边的核对。

把允许路径与拒绝路径一起设计

一项可审核的变更不应只记录成功部署的作业。应明确列出允许的身份与相邻的拒绝身份。例如，目标生产工作流在正确仓库、主分支、Production Environment 与 audience 下可以承担角色；相同仓库的功能分支、另一个仓库的同名工作流、预览 Environment、错误 audience 和不匹配的旧 subject 都应该得到拒绝结果。如果生产流程依赖人工审批，应确认目标 Environment 实际配置了所需 reviewers，且保护规则通过前作业不会运行；仅凭 YAML 写了 environment: 不能证明审批门禁存在。能够编辑发布工作流、配置 Environment 保护规则或维护云端信任策略的人，都可能改变这条授权链，应把这些控制者列入代码评审范围。

授权成功后还要验证角色边界。对预览构建与生产发布分开使用角色，确实增加 IAM 对象和维护工作，但可以让预览作业无法覆盖生产路径；是否拆分应根据资源边界、发布频率和故障影响面决定。验证可使用 AWS IAM Access Analyzer 的策略检查，并在非生产环境执行代表性允许与拒绝用例。若只静态检查 JSON，仍不能证明 GitHub 实际发行的 claim 与假设一致；若只看到一次成功承担角色，也不能证明越权操作会被拒绝。应分别留下运行身份、被评估策略、STS 结果和最小化权限验证的记录。AWS 的临时凭据 action 文档也把角色信任条件与角色权限作为需要分别配置的步骤。

日志也属于验证边界。不要把未经处理的 JWT、OIDC 响应或短期密钥写进构建日志；应记录可用于关联的运行 ID、仓库/ref、目标角色标识以及拒绝原因摘要，同时遵守云账户的敏感信息规则。原始令牌即使有效期短，也可能在有效窗口内被重放或滥用。短期凭据可以降低凭据长期静置与轮换负担，并缩短暴露窗口，但不能保证工作流脚本、第三方 action、runner 或云资源策略没有问题。是否把 action 固定到完整提交哈希、是否使用托管或自托管 runner，也属于供应链和执行环境评估，不能由 OIDC 代替。

以可重复的验证表收尾

迁移前可把每个角色的验证表写成四列：预期 token 上下文、信任条件、角色获准的操作、应拒绝的邻近上下文。至少覆盖目标分支与 Environment 的允许路径、错误 audience、非目标仓库、错误分支、缺少 Environment 审批以及角色策略不允许的资源操作。执行时先在低风险账号验证，再逐步迁移生产身份；如旧密钥仍有回退用途，要给它单独设置到期、禁用和撤销检查，而不是长期保留两个等价入口。具体策略键和格式会随 GitHub 仓库状态、AWS 分区、工作流上下文和角色设计而变化，表格模板不能替代对真实 claim 的检查。

本文没有配置 AWS IAM、调用 GitHub Actions、执行 STS 请求或进行真实云端 allow/deny 测试；上面的生产/预览路径是明确标注的假设示例。可复核的事实来自 GitHub 与 AWS 当前官方文档：查看仓库对应的 sub 格式，核实 Environment 与 ref 条件，再在目标账号中用策略分析和受控测试验证。若身份交换成功而产物仍可能被替换，发布链路还需要确认部署对象的来源与摘要；可结合构建产物身份校验追踪从工作流到部署产物的关系。OIDC 的价值不是把密钥换成一个不必审查的开关，而是让信任链可以围绕一次具体工作流运行被表达、限制并验证。
