OIDC 不再保存长期密钥，谁还能换到云权限？

OIDC 减少长期密钥保存，仍需限定工作流身份与云权限；核对新仓库 subject 格式和环境审批路径。

正文

GitHub Actions 使用 OIDC 后，仍需限定哪些工作流身份可以交换到哪些云权限。短期凭据减少了长期密钥保存需求，但云端信任条件与角色权限如果过宽，未经预期的执行仍可能获得部署能力。

身份交换与操作授权分两层

GitHub 的 OIDC 文档描述云提供方验证令牌声明后提供短期访问令牌的流程。信任关系允许特定工作流代表云角色申请访问；实际能做什么还由云权限决定。本文没有配置云角色或运行工作流，不把文档能力当成本站已经采用的认证方式。

值得核对的是文档中的时间条件：二〇二六年七月十五日之后新建的仓库，默认 subject 使用包含所有者与仓库标识的不可变格式，且该说明不适用于 GitHub Enterprise Server。照搬旧示例的字符串条件可能不匹配。应读取实际仓库采用的声明格式及对应参考，不能为了让登录成功就扩大成接受任意主体。

谁能改变工作流输入

假设生产角色仅根据一个宽泛的组织条件信任令牌，多个仓库或不同执行路径都可能进入交换范围。这个假设没有真实云账户数据，却提醒维护者检查仓库、环境及工作流治理如何进入信任条件。各云提供方支持的条件键与匹配方式不同，不能将某个平台的配置原样视为所有平台的规则。

身份条件还依赖代码与配置的控制路径。谁能修改发布工作流、哪些环境需要审批、哪些触发来源可以进入敏感步骤，都应纳入审查。短期令牌不会自动判断代码变更是否经过团队认可。第三方动作和执行环境也应被评估，因为它们可能在获权步骤中参与执行。

权限大小仍然要被限制

被允许交换身份，不代表该角色需要所有云资源权限。建议按实际发布操作限定角色动作与资源，必要时区分构建、预览和生产发布。角色拆分增加配置维护成本，但也让失败或误用的影响范围更清楚。不能把“无长期秘密”当成可以省略最小权限检查的理由。

验证计划应包含预期工作流成功交换、其他仓库或环境被拒绝、错误声明格式无法获取权限，以及已获身份不能执行超出角色范围的操作。测试时记录足够的运行身份与结果，但不保存原始令牌。本文未执行这些场景，不提供认证成功日志，也不承诺任意组织结构都能采用相同策略。

发布完成后还需核对实际产物身份，而非只有认证成功。相关的构建产物身份讨论了这一层证据。下一步从一个生产角色开始，列出允许交换的工作流身份与允许执行的动作，再与实际令牌声明、审批路径和部署回执逐项对应；这样才能看清短期凭据究竟缩小了什么风险。
