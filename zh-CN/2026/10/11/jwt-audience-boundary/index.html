JWT 签名正确，为什么仍可能用错了令牌？

签名验证只回答令牌是否通过密码学检查；本文用 RFC 7519、RFC 8725 与 OAuth JWT access-token profile 说明接收方必须如何校验 audience，以及它为什么不能替代授权。

正文

核心要点

  • 签名有效不代表当前 API 就是令牌的预期接收方。
  • 同一发行者面向多个应用发令牌时，应按接收方策略验证 aud；OAuth JWT access token profile 对资源服务器规定了明确校验。
  • Audience 是令牌使用边界的一部分，不能代替令牌类型、scope、租户和对象级授权。

JWT 签名正确，仍可能用错令牌，因为签名验证确认的是令牌内容与验证密钥之间的密码学关系，并不自动确认当前 API 是不是预期接收方。接收方还要按自己的配置验证发行者、受众和令牌用途；请求涉及什么资源、允许做什么，则继续由授权规则决定。把“能验签”直接等同于“能在这里使用”，会把不同系统之间的边界压扁。

同一把可信密钥，不等于所有服务都该接收

设想一家服务同时提供报表 API 和付款 API，认证服务使用同一个发行者标识及签名密钥，为两个资源分别签发 JWT。报表服务发出的令牌确实由可信认证服务签署，付款服务拿到它也可能通过签名检查；但这只证明它来自该认证体系，不证明它的目标是付款服务。若付款入口只验签，令牌就可能被放进原本不适用的上下文。这里是用于解释的假设场景，不是实际攻击案例，也没有声称某个产品存在此漏洞。

问题出在验证策略省略了一道独立判断。密钥可以被多个接收方信任，令牌也可能携带一组看似合法的权限声明；但每个资源仍应回答：“这个凭据是否是发给我的？”RFC 7519 把 aud 定义为 JWT 预期接收方。若令牌带有该声明，而处理方不在其 audience 值中，处理方必须拒绝。该规范也说明 aud 在通用 JWT 中是可选声明，接收方如何解释其值取决于应用。因此，不能只看到一个 aud 字段就推断整个系统已经有了正确策略。

先分清通用 JWT 规则和具体令牌配置文件

RFC 8725 的最佳实践进一步处理共享发行者造成的替换风险：同一发行者可能向多个应用签发令牌时，令牌必须带有可供判断用途的 audience，接收应用必须校验该值；缺失或与接收方不对应时要拒绝。RFC 9068 则规定了 OAuth 2.0 JWT access token 的具体配置文件：资源服务器必须检查 aud 是否包含自己预期的资源标识，并拒绝不匹配的 access token。这个 profile 还要求核对 typ 为 at+jwt 或 application/at+jwt，并校验发行者、签名等事项。

这些规范不是互相替代的“某条 JWT 通用魔法”。RFC 7519 描述 claim 的通用语义；RFC 8725 解释跨应用和跨令牌用途的安全要求；RFC 9068 面向符合其配置文件的 OAuth JWT access token。实际服务是否声明采用 RFC 9068、发行者怎样分配资源标识、旧版本令牌是否还在流通，必须从系统协议与配置中确认。不能因为令牌是 JWT，就假定它天然遵循某个 OAuth profile。

aud 的值可以是一个大小写敏感的字符串，也可以是字符串数组；接收方应按协议约定匹配它自己的稳定标识。把检查写成“包含某段文本”会让相似名称、大小写差异或非预期值绕过原本想表达的边界。实际允许列表应来自服务配置或可信注册信息，而不是由令牌中尚未验证的内容临时决定。多受众也不意味着每个资源都能使用令牌里的全部权限：发行者要表达访问范围，接收方要验证与自己相关的部分。

Audience 不能替代令牌类型和资源授权

Audience 解决的是预期接收方问题。它不会自动识别 ID token 与 access token，也不会说明某个主体可否查看某个订单。RFC 8725 讨论跨 JWT 混淆时，建议令牌种类采用互斥的验证规则；可结合明确的类型标记、不同的必需声明、不同的密钥或不同 aud 值。RFC 9068 用 at+jwt 类型标识其 access-token profile。资源服务器仍要验证该 profile 的要求，而不能只看到匹配 audience 就接受所有 JWT。

即便令牌的签名、发行者、时间、类型和 audience 全部符合策略，权限判断仍未结束。scope 表示的操作可能只对某些受众有意义；用户是否属于当前租户、目标对象是否归该用户管理、当前业务状态能否执行付款，通常需要单独判断。假设一个令牌的 audience 是付款 API，scope 也允许发起付款，它仍不当然允许修改任意账户或支付其他租户的账单。认证、令牌适用范围、对象级授权和业务状态校验是连续但不同的关卡。

站内刷新令牌轮换的重用处理讨论的是授权关系与刷新凭据生命周期；它不能替代每个资源服务器对 access token 接收方的验证。另一个GitHub Actions 到 AWS 的 OIDC 信任边界展示的是发行者、audience 与主体条件如何共同限制云角色信任。两者都涉及“谁能相信什么”，但各自协议的 claim 和接受策略不可直接互换。

把拒绝路径写进验证矩阵

设计检查时，可以先固定接收服务自己的期望发行者、audience、令牌 profile、算法、密钥来源和时效规则，再列出会被拒绝的输入。矩阵至少应区分：签名正确但 audience 指向另一个资源；必需的 audience 缺失；数组中含当前资源和仅含其他资源；只有大小写不同的标识；签名、发行者或时间无效；token type 不符合接入的 profile；以及 audience 正确但 scope 或对象权限不足。第一组问题应在令牌适用性关卡失败，最后一组则要由授权策略拒绝。接口返回 401 还是 403，取决于服务对认证与授权错误的约定，不应拿单一状态码代替内部验证证据。

更新 audience 标识时，还要谨慎处理迁移窗口。若新旧标识同时接受，窗口越宽，旧令牌仍可被哪些服务使用就越难说明。可以按发行方、资源和过期时间安排切换，并在遥测中记录拒绝类别、服务端策略版本和请求上下文；不要记录完整令牌、签名密钥或足以重放的材料。排查日志只能帮助发现哪道策略拒绝，不能反过来把未验证 claim 当作可信输入。

本文依据 RFC 7519（2015 年）、RFC 8725（2020 年）和 RFC 9068（2021 年）原文中的规定说明边界；假设场景仅用于解释。没有运行令牌库配置、资源服务器或渗透测试，因而不能据此宣称某实现已经安全。落地时应先识别服务采用的令牌 profile，再用受控令牌逐项验证正确资源能够通过、错误资源不能通过，并另测对象权限和业务拒绝路径；若规范与所用库的实际行为存在差异，应以部署配置和可复现的检查结果为准。
