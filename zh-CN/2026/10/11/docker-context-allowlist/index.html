文件没有提交到 Git，构建上下文里就没有它吗？

Git 忽略不控制 Docker 上下文；核对实际目录、忽略规则优先级与例外，并单独检查镜像产物。

正文

文件没有提交到 Git，不代表它不会进入 Docker 构建上下文。应根据实际传给构建器的目录或其他上下文来源，检查排除规则与文件范围；版本控制的忽略规则不能替代构建上下文控制。

看清构建输入从哪里来

Docker 的构建上下文文档说明，构建器会使用上下文中的 .dockerignore 排除匹配文件，并介绍 Dockerfile 专属忽略文件的优先级以及模式匹配规则。本文讨论当前在线文档中的上下文行为，没有执行 Docker 构建，也不声称某个镜像已排除全部敏感文件。

假设开发目录里有未提交的调试导出与本地环境文件。团队把它们加入 Git 忽略列表后，误以为构建输入也只剩仓库文件。如果构建上下文来自本地目录，它们仍需被构建规则处理。这个例子没有真实秘密内容；风险来自对输入边界的错误假设，而不是 Git 本身失效。

目录改变会改变范围

使用当前目录和使用上一级目录作为上下文，不只是路径写法不同。后者可能包含其他项目、归档文件或开发工具数据。建议将构建命令、上下文路径与 Dockerfile 一起审查，而不是只看复制指令。远程上下文、命名上下文等配置也有各自边界，应按实际构建入口核对，不把本地目录经验推广成所有模式的保证。

排除文件需要检查规则顺序与例外。某个宽泛排除后面的重新包含规则，可能把原本不希望传入的对象重新带回来。Dockerfile 专属规则也可能使团队以为生效的通用规则被另一份规则替代。维护者需要能够解释哪些文件被允许参与构建，而不是不断往排除列表末尾追加名字。

减少输入还需要检查产物

较小的上下文有助于明确依赖边界，但不会自动证明镜像内容安全。构建过程仍可能下载资料、产生调试输出或写入凭据副本。输入范围检查与最终产物检查应该分别执行，避免把排除规则当成覆盖全部构建风险的工具。真正需要秘密的步骤，还应使用适用的秘密传递机制并检查输出。

建议在可控制的样例目录中准备代表性文件，验证通用规则、例外规则和专属规则的效果，再核对构建产物是否出现禁止内容。本文未执行这些检查，因此不给出上下文大小变化或镜像安全通过结论。测试记录也不应包含真实秘密；采用无敏感值的替代对象，确认路径行为即可。

构建入口变化应触发复核，比如调整工作目录、改用其他 Dockerfile 或增加额外上下文。相关的构建秘密与输出边界解释为什么安全传入也不等于安全产出。下一步审查现有构建命令的上下文参数，列出必要输入与禁止输入，再验证规则与产物；先明确边界，比依赖“没有提交所以不会进去”的直觉更可靠。
