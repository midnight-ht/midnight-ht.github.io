本地文件没有进 Git，为什么仍可能进入 Docker 构建上下文？

本地目录、远程 Git 和命名上下文的输入边界并不相同；用构建参数、有效忽略规则和镜像检查判断文件会走到哪一步。

正文

核心要点

  • 本地目录上下文读取开发机工作树；远程 Git 上下文读取仓库引用，两者不会因 Git 忽略规则自动等同。
  • 最后的位置参数决定上下文，-f 选择 Dockerfile；移动 Dockerfile 不会自动缩小输入范围。
  • .dockerignore 与 Dockerfile 专属忽略文件按上下文和优先级生效，! 规则及后续匹配会改变最终结果。
  • 上下文可见、构建器传输和最终镜像包含是不同边界；要分别验证输入、构建指令与产物。
  • 构建凭据应通过 secret 或 SSH mount 提供，并检查构建命令是否打印或复制凭据。

如果 docker build 最后传入的是本地目录，那么没有提交 Git 的文件仍可能成为构建器可见的输入。决定范围的是命令选择的构建上下文，.dockerignore 再从这个范围里过滤文件；文件能进入上下文，不等于它已经被复制进最终镜像。把这三步分开，才能回答“某个本地文件会不会被带进去”。

构建上下文由哪个参数决定？

Docker 把 build context 定义为构建指令能够访问的一组文件。docker build [OPTIONS] PATH | URL | - 中，位置参数可以是本地目录、远程 Git/归档地址，也可以是标准输入；它不是 Dockerfile 路径。-f 或 --file 用来选择 Dockerfile。因而 docker build -f docker/app.Dockerfile . 的 Dockerfile 在 docker/，默认上下文仍是当前目录 .。改变 Dockerfile 的位置不会自动收窄上下文。Docker 构建上下文文档分别说明了本地、远程和标准输入上下文；镜像构建命令参考也把位置参数和 --file 作为不同输入。

这个区分能解释一个常见误判：.gitignore 让某个未跟踪文件不出现在 git status，只影响 Git 的版本控制处理；它不会把文件从开发机的目录中移走，也不会自动变成 Docker 的排除规则。对于本地目录上下文，构建客户端根据 .dockerignore 过滤输入。相反，如果命令采用远程 Git 仓库作为上下文，Docker 会从指定仓库引用取得源文件，而不是读取你电脑上的未提交工作树；仓库的默认引用、显式分支或提交号，才决定远程输入是什么。把“本地目录构建”和“远程仓库构建”统称为“按 Git 文件构建”，会抹掉最关键的边界。

用同一个仓库比较两种入口

下面是一个假设的 monorepo，不对应真实项目或执行结果：

repo/
├── .env.local                 # 被 .gitignore 忽略，仍在本地磁盘
├── .dockerignore
├── shared/schema/
└── apps/catalog/
    ├── Dockerfile
    ├── package.json
    └── src/

若在仓库根目录执行 docker build -f apps/catalog/Dockerfile .，-f 选中应用的 Dockerfile，而 . 仍把 repo/ 设为默认上下文。.env.local 位于该范围内；是否会传给构建器，要看根上下文实际生效的忽略文件及规则。即使它没有匹配排除规则，也不能据此说它必然出现在镜像里。假设 Dockerfile 只复制 apps/catalog/package.json 和 apps/catalog/src/，其他可见文件没有因此自动成为镜像内容；若使用 COPY . /app，复制范围和结果则不同。

若改成先进入 apps/catalog/，再执行 docker build .，默认上下文就缩到应用目录。根目录的 .env.local 与 shared/schema/ 不在这个默认范围内；但这只是切换了输入边界，不是 Git 对它们起了作用。需要共享代码时，应显式设计输入：例如从 monorepo 根目录构建并精确控制根上下文，或为 BuildKit 增加单独的命名上下文，再在 Dockerfile 中按来源引用。命名上下文把第二个来源写在构建命令里，便于审查“主项目之外还取了什么”，却不会替你判断那个来源是否包含无关文件。Docker 文档的 named contexts 章节给出了 --build-context 与 COPY --from 的方式。

为什么 .dockerignore 不是 Git 规则的镜像？

本地文件系统上下文的 .dockerignore 放在上下文根目录。匹配的文件在传给 builder 前被移出上下文。若有多个 Dockerfile，可以把各自的忽略文件放在 Dockerfile 同目录，例如 docker/app.Dockerfile.dockerignore；在同一构建中它优先于上下文根的 .dockerignore。因此，只审查仓库根的共享忽略文件，可能看不到实际被选用的专属规则。官方语法说明还指出，前后斜线会被忽略，支持 **，而以 ! 开头的规则可重新包含此前排除的对象。

规则顺序会改变安全结论。假设规则先排除所有 Markdown 文件，再用 !README.md 重新允许根目录的说明文件。再往后添加 README-private.md，该文件会因最后一个匹配规则而重新排除；若把 !README*.md 放到最后，私有说明也可能被重新包含。维护者不能只看到规则里写了 *.md 就断言 Markdown 都不可见，而要针对目标路径按从上到下的匹配顺序判断。Docker 还指出，单独的 . 模式因历史原因会被忽略；把它当成“排除整个上下文”的简写会产生错误判断。

构建定义文件也有这个例外：即使规则匹配 Dockerfile 和 .dockerignore，它们仍会发送给 builder，因为构建需要它们；文档同时说明，不能用 ADD、COPY 或 bind mount 把这两个文件本身放入镜像。这是一个容易误读的例外：忽略规则控制上下文里的普通文件，构建定义文件仍需被处理，但它并不会因此被当作应用文件打包。

文件被传给构建器，就等于进入镜像吗？

默认 docker build 在 Docker Engine 的 Windows 容器模式之外、且没有设置 DOCKER_BUILDKIT=0 时使用 Buildx/BuildKit。官方 CLI 文档对两类 builder 的传输行为作了区分：legacy builder 会把整个上下文发给 daemon；BuildKit 只传输构建实际使用到的文件。这个差异会影响传输量和暴露面，但不能作为“这个文件安全”的证据。一个文件被排除规则过滤，是输入层的结论；一个文件存在于上下文但当前 Dockerfile 没有复制它，是指令层的结论；一个文件最终出现在镜像层，则要检查实际构建步骤、各阶段和产物。层级不同，检查对象也不同。Docker CLI 关于 legacy builder 的说明也提醒，这些行为只适用于该页面限定的情形。

反过来，COPY ../shared/schema /app/schema 也不是从小上下文“爬回”仓库根目录的方法。在 COPY 中，源路径相对构建上下文根解释；现代文档说明，越出范围的前缀会被清理，不能以此扩大默认上下文。若缺少文件，应回到命令行检查上下文选择，或明确增加 named context；不要把 ../ 当成权限逃生口。这一边界也见于 Dockerfile 的 COPY 路径规则。

怎样验证一个文件实际走过的路径？

一个可复核的排查不从“是否提交”开始，而从执行入口开始。先记录 CI 或开发机实际执行的命令、当前工作目录、最后一个 context 参数、Dockerfile 选择方式，以及它到底是本地目录、Git URL 还是归档。CI 中的工作目录和上下文路径可能与开发者终端不同；只看 Dockerfile 文件内容，无法推断入口参数。再确定此 context 根目录下哪些 .dockerignore 会生效，若存在 Dockerfile 专属文件，就按它的优先级读取。最后对可能敏感的相对路径逐条演算规则，特别检查 ! 例外和后续匹配。

随后把验证拆成两段。第一段用无害的哨兵文件（例如写着 sample-only 的 local-marker.txt），分别放在上下文内、忽略路径下和上下文外，确认当前入口和忽略规则是否符合预期。可以用最小 Dockerfile 尝试引用它，并观察构建是否因路径不可见而失败；这验证的是输入边界，不是生产镜像安全。第二段在隔离环境中检查生成的镜像文件清单或镜像层，确认被禁止的文件没有被构建步骤复制进去。若使用远程 builder，还要明确哪些上下文文件需要上传；构建日志中的 transfer 大小不能替代对文件内容的审查。

真实凭据不应靠“写进 .dockerignore”来管理。排除规则是防止普通上下文文件被纳入的防线，但团队可能换了 Dockerfile、额外加了命名上下文或改用 CI 归档，旧规则不一定覆盖这些入口。下载私有依赖时，Docker 建议使用 BuildKit secret 或 SSH mount，而不是把令牌放进 ARG 或 ENV；挂载解决凭据交给构建步骤的方式，但仍要审查命令是否打印值或把它复制到输出目录。Docker 构建秘密文档明确区分了 secret mount 与会持久暴露到镜像的构建参数/环境变量。最终仍需检查产物，而不是把某种输入机制当成绝对保证。

本文依据当前可查阅的 Docker 官方文档整理机制，没有在本机或 CI 执行 Docker 构建、没有扫描镜像，也没有观察任何客户或生产环境。实际排查时把“命令选了什么输入”“哪些文件通过过滤”“Dockerfile 消费了哪些文件”“产物留下了什么”分别记录。与其问“这个文件进没进 Git”，不如沿这四个边界给出可以复核的答案。对于秘密可能从构建命令进入产物的另一条路径，可继续看构建阶段 secret mount 的输出边界；两篇分别处理上下文输入和秘密消费后的输出。
