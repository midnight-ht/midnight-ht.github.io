想记录提交时刻？PostgreSQL 19 的 `clock_timestamp()` 不够

`clock_timestamp()` 记录函数取值时刻，不等于事务提交。按事务、语句、观察和提交事件选择时间来源，并看清提交时间追踪的限制。

正文

核心要点

  • CURRENT_TIMESTAMP、now() 与 transaction_timestamp() 表示事务开始时间；同一事务内保持一致是设计语义。
  • statement_timestamp() 表示服务器收到最近命令消息的时点；clock_timestamp() 表示函数被求值时的当前时间，两者都不是提交时间。
  • PostgreSQL 的提交时间追踪需要启动时启用配置，并且历史数据会被 vacuum 清理；它不是默认可长期查询的审计日志。

不够。clock_timestamp() 返回函数被求值时的当前时间；它不会等到事务提交后再回填，因此不能证明提交时刻。在 PostgreSQL 19 中，CURRENT_TIMESTAMP、now() 和 transaction_timestamp() 表示事务开始时间；statement_timestamp() 表示服务器收到最近命令消息的时点。选择哪个函数，要先说清字段要记录哪一个事件。

一个“时间落后”的字段，可能只是记错了事件

设想一个审批事务先开始，随后等待锁、读取规则、更新订单，最后才提交。若 updated_at 使用 CURRENT_TIMESTAMP，它描述的是事务起点；值看起来早于更新语句甚至提交时刻，并不说明数据库时钟停了。这里是解释语义的假设时间线，没有实际服务、等待时长或故障记录。

当前日期时间章节说明，标准当前日期时间函数返回当前事务的开始时间。同一事务多次调用仍得到同一个值，文档明确把这种一致性视为特性：一个事务中的多项修改可以共享同一时间标记。now() 是 transaction_timestamp() 的传统别名，CURRENT_TIMESTAMP 也对应这个时点。

这适合表达“本次事务的共同业务时点”，例如一次原子更新中需要让几张表的修改带相同时间。它不等于每行实际写入的瞬间，不等于执行到某个语句的时刻，更不等于数据库确认提交的时刻。若字段名是 committed_at，却由 DEFAULT now() 填充，名字比值本身承诺得更多。

三个“现在”各回答什么问题

PostgreSQL 19 文档把 statement_timestamp() 定义为当前语句开始时间，更精确地说，是服务器收到客户端最近一条命令消息的时点；它在事务第一条语句中与事务开始时间相同，后续语句可能不同。它适合记录命令进入服务端处理流程的边界，但不是每一行更新的精确时间，也不是客户端点击按钮或网络请求离开客户端的时间。

clock_timestamp() 返回调用时的实际当前时间，同一条 SQL 语句里也可能变化。对观察长语句中某段处理大概发生在何时，它比事务时间更贴近“读表时钟”；代价是同一语句内多行或多个表达式未必共享同一值。官方函数定义没有承诺这个值唯一、单调或能建立并发事务之间的全序，所以它也不是可靠的事件序号。这是根据函数契约得到的设计边界，不是对某个操作系统时钟行为的实测结论。

可把差异放进一段隔离环境的示例。以下 SQL 用于规划验证，本文没有连接 PostgreSQL 执行；输出关系是按官方语义推导，不是实测日志。

BEGIN;
SELECT CURRENT_TIMESTAMP AS transaction_time,
       statement_timestamp() AS command_received,
       clock_timestamp() AS sampled_time;

SELECT pg_sleep(1);

UPDATE approval
   SET status = 'approved',
       transaction_time = CURRENT_TIMESTAMP,
       observed_time = clock_timestamp()
 WHERE id = 42
 RETURNING transaction_time, observed_time, statement_timestamp();
COMMIT;

按文档语义，第二条查询中的事务时间仍与第一条相同；更新语句的 statement_timestamp() 则取最近命令消息的到达时点。clock_timestamp() 在被求值时读取当前时间，它与事务时间之间的差值取决于服务端时钟和执行过程，文档没有保证其大小或顺序，不能在文稿里编造固定数值。更关键的是，更新求值之后，事务仍可能等待约束、提交锁或存储确认，也可能最终回滚。因此返回行里的取样值不能被改名为提交时间。

为什么提交时间不该靠改函数名推出来

提交是事务完成边界，不是前一条 SQL 中某个表达式求值的边界。本站关于 RETURNING 与提交边界的文章解释了类似误读：语句返回行和整个事务已成功提交是不同事实。时间字段也应保持这种区分。应用若要向调用者报告提交成功，应读取 COMMIT 的结果；若在收到成功确认后再取一次应用时钟，字段应叫“提交确认被应用观察到的时间”，而不是数据库精确提交时刻。若要事后查询 PostgreSQL 记录的事务提交时间，则需另看专门的提交时间信息函数。

但这组能力不是无条件审计设施。track_commit_timestamp 配置默认关闭，只能在服务器启动时设置；pg_xact_commit_timestamp 文档说明，只有在配置启用后提交的事务才有可用信息，而且这些信息会被 vacuum 常规清理。它适合在确认运维设置、保留边界和权限后用于特定的事后诊断，不应被当成永久审计日志或可随时查询的业务列。

如果业务必须长期保留“某审批记录由哪个事务、何时最终提交”的证据，通常要在应用审计模型中明确记录事件身份、操作者、请求关联、状态转移和事务结果，并设计留存与不可抵赖要求。数据库提交时间追踪可以补充诊断线索，但不替代这套业务证据，也不自动证明操作者身份或外部动作已完成。设计选择应以审计要求和故障恢复路径为准，不能只因一个函数名字看起来像“当前时间”就启用全局配置。

默认值还有一个部署时刻陷阱

列默认值常见写法是 DEFAULT now()。这确实是函数调用，不会在建表时固定成一个常量；不过它返回的仍是当前事务开始时间。若插入语句位于一个已经运行很久的显式事务里，这个默认值可能明显早于插入语句。相反，在自动提交的一条短 INSERT 中，它通常接近语句所在事务的起点。区别来自事务边界，不是默认表达式悄悄换了含义。

不要把它改写成 DEFAULT TIMESTAMP 'now' 以为只是另一种拼法。文档还提醒，这种特殊字面量会在解析时转换成一个时间常量；若用于后续才执行的列默认值，时间可能固定在建表时。要在每次需要默认值时求值，应使用 now() 或 CURRENT_TIMESTAMP 这样的函数形式，并继续确认事务语义是否满足字段定义。

这是迁移中容易留下的历史错误：表先创建，部署一段时间后才有新行，可默认值却看起来早于第一条业务记录。排查时先查看实际默认表达式与列类型，再在测试表中创建两列不同默认值，间隔一段时间后插入并比较；SQL 的类型转换和会话时区也要一并检查。日期时间类型章节说明 timestamp 与 timestamptz 的含义不同。此处不展开时区建模；关键是不要把字面量解析时点、事务起点和时间点存储混成一个概念。

怎么为审计字段选时间来源？

先在 schema 和事件说明里写下谓词，再选函数：transaction_started_at 表示同一事务开始；command_received_at 表示服务端收到当前命令；sampled_at 表示表达式实际取值时；committed_at 表示只有事务成功完成后才能确认的提交事件。名称只是帮助检查，真正的证明还要看写入代码在哪个事务阶段执行、提交失败是否会留下记录，以及外部通知是否在提交以后发生。

如果目标是让同一批修改共享时间，事务时间通常比逐行变化的墙上时钟更容易解释。如果目标是观察 SQL 的处理起点，语句时间更符合问题。如果目标是采样执行过程，clock_timestamp() 可以提供调用时值，但不能据此推断严格顺序。如果目标是确认提交成功，就检查 COMMIT 结果；如果目标是保存应用何时收到或观察到这个结果，应在确认以后单独取样并明确命名；若要数据库记录的精确提交时间，则评估已启用的提交时间追踪和其限制。不能仅靠把字段改名、改默认值或增加小数秒精度来补足语义。

验证时可以在可丢弃数据库里分别测试：同一事务多次读取、事务内跨多条语句、等待一段时间后再更新、回滚、提交失败、函数默认值与特殊 now 字面量。只比较结果中时间是否相等还不够；要记录事务开始、命令发送/接收、表达式求值、提交确认分别由哪一段代码观察。本文的测试矩阵没有实际执行，具体版本和驱动仍需按目标环境运行。

排查一个看似“时间倒退”的字段，先问它代表的是事务、命令、取样还是提交；再核对函数、默认表达式、事务是否长时间开放以及提交失败路径。这个顺序能把“时钟坏了”的猜测转成可验证的字段契约，也能避免让 clock_timestamp() 承担它从未承诺的提交语义。
