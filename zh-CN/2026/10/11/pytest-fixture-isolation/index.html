扩大 fixture 作用域，测试为何开始互相影响？

pytest fixture 的 scope 延长对象和外部状态的复用寿命，却不提供隔离；从可变状态、清理边界、依赖作用域和并行资源身份判断是否共享。

正文

pytest fixture 的作用域决定一个返回值可以被复用多久；当返回值或它背后的服务状态可变时，扩大作用域也会延长共享状态的寿命。测试隔离不是 scope 自动提供的属性。要先弄清对象由谁拥有、哪些字段会变化、何时重建或清理，再决定复用边界。

scope 管的是生命周期，不是“每次都干净”

pytest 的 fixture 指南把 scope 描述为 fixture 的创建和销毁范围。默认的 function 作用域按测试函数请求；class、module、package 和 session 作用域把复用窗口向外扩大。一个测试请求 fixture 时，pytest 会解析依赖、创建需要的 fixture，并把结果传给测试。因而测试拿到的不是抽象的“准备步骤”，而是一个对象，或指向某个外部状态的句柄。

把 scope 从 function 改为 module，常见动机是昂贵初始化：启动服务、加载大型只读索引、建立测试数据库连接。这个选择减少重复创建，却会改变结果的生命周期。如果对象是只读配置，扩大范围通常只改变成本；如果它包含列表、认证身份、缓存、事务状态或外部记录，两个测试便可能访问同一份状态。问题不是 scope 本身错误，而是复用契约没有说明状态如何回到起点。

pytest 文档还提醒，fixture 参数化会使同一声明范围内出现多个实例。因此，“session 作用域就是整个运行永远只创建一次”也不是普遍保证。需要把参数、依赖和实际缓存行为纳入推理，而不是只看装饰器上的一个词。

一个可推演的污染例子

下面是说明状态边界的假设示例，不是本次实际运行的 pytest 结果：

import pytest

@pytest.fixture(scope="module")
def catalog():
    return {"items": []}

def test_adds_item(catalog):
    catalog["items"].append("alpha")
    assert catalog["items"] == ["alpha"]

def test_starts_empty(catalog):
    assert catalog["items"] == []

两个测试都请求同一个 module fixture。第一个测试把 alpha 放进字典；如果第二个测试在同一模块中复用同一个结果，它期待的空列表就不再成立。把顺序倒过来可能改变哪个断言先暴露问题，却没有改变两个测试共享对象的事实。可将 fixture 缩小为 function scope，让每次请求重新创建字典；也可以共享昂贵的只读底座，然后让每个测试取得自己的可变目录或事务。

后一种拆分通常更有解释力：例如 session fixture 负责连接已经启动的测试服务，function fixture 为当前测试创建唯一租户、记录集或事务，并在该测试边界清理。要先确认服务是否支持并发会话、回滚是否覆盖目标写入、后台任务是否能越过事务边界。只写一个 rollback() 并不能证明所有外部副作用都撤销了。

先划分稳定底座和测试状态

做 scope 选择时，可以把 fixture 的内容拆成两层。第一层是启动成本高而且测试期间应保持稳定的资源，例如已经启动的本地服务进程、只读 schema 或连接池。第二层是每个测试会修改或依赖其初始值的上下文，例如登录身份、订单、队列消息、随机端口映射和临时目录。第一层可以讨论跨测试复用；第二层要提供测试级的创建、命名、复位或销毁策略。

这不是“所有可变对象必须 function scope”的绝对规定。一个模块级对象若被明确封装为只读，或每个测试都通过工厂拿到独立会话，也可能安全。反过来，function fixture 若写入所有测试共用的数据库表，也可能污染后续测试。判断单位应当是可观察状态，而不只是 Python 对象的身份：一个看似只读的客户端，可能仍然持有 cookie、当前用户或缓存；两个独立连接，也可能写入同一行。

给每个宽作用域 fixture 写一份简短契约，通常比笼统地说“它是共享的”更有效：它拥有哪个资源；哪些操作会改变状态；测试之间哪些状态允许共享；复位由谁做；清理在正常结束和异常中分别如何发生；并行 worker 用什么身份区分资源。答案不清楚，就暂时不要扩大 scope。

清理必须落在状态边界上

pytest 的 yield fixture 可把资源关闭代码放在 yield 之后。它适合表达“完成使用后释放资源”，但 teardown 时机仍取决于 fixture 的 scope。module fixture 的最终清理发生在模块相关工作结束时，不能替代两项测试之间的状态复位。如果前一个测试创建的记录会被后一个测试读到，清理应在测试级事务、唯一命名空间或明确的删除步骤中完成。

如果 fixture 在 yield 前失败，yield 之后的清理代码不会执行；已经成功完成的依赖 fixture 仍会尝试 teardown。因此准备阶段不要把多个可能部分成功的写操作塞进一个大 fixture。更稳妥的做法是把“创建一个用户”“启动一个浏览器”拆成各自可清理的 fixture：每次状态改变成功后立刻建立对应的释放路径。pytest 的安全 teardown 指南把一次状态改变与它自己的清理绑定起来，正是为了减少中间步骤失败后遗留资源的窗口。

还要查 autouse。它会让所在可见范围内的测试自动请求 fixture，即使测试签名里没有出现它。自动执行减少了重复声明，也可能让某个共享准备步骤变得隐蔽。排查时不仅搜索测试函数参数，也要查看 conftest.py、目录级 fixture 与 autouse=True，并确认它的作用域是否把影响带到了更广的测试集合。

对外部数据库、云资源或账户，teardown 自身失败也要作为诊断结果保留下来：记录可定位的资源标识，便于清理残留。测试进程退出只结束本地运行，并不能证明远端状态已经消失。

另一个约束是依赖的生命周期必须匹配。高作用域 fixture 若请求更窄作用域的依赖，会遇到 scope 不匹配，因为窄依赖无法在高作用域对象的整个生命周期中持续有效。pytest 的 fixture 参考文档也把实例化次序与作用域、依赖和 autouse 联系起来。不要依赖 fixture 名称、文件顺序或测试函数碰巧先后执行来暗示初始化顺序；把真实依赖写进 fixture 参数，或把资源边界拆开。

并行测试需要给外部资源命名

scope 管理的是 pytest 管理的 fixture 实例和生命周期，不会自动隔离进程之外的数据库、对象存储、测试账户、端口或消息队列。两个 worker 各自拿到不同的客户端对象，仍可能对着同一张表或同一个账户写数据。并行后才出现冲突时，应检查外部资源身份，而不只是缩小 Python fixture 的 scope。

一种策略是用运行标识与 worker 标识组合成独立 schema、目录前缀或租户名，并让测试只访问自己的命名空间。清理时依据同一个标识删除资源。它会增加创建、迁移和回收成本，还要防止标识碰撞与误删共享数据。若系统不能按命名空间隔离，选择串行化相关测试可能比伪装并发安全更诚实，但这会牺牲并行时间。两者都不是通用答案，应由资源能力和运行约束决定。

如何从“单测通过、整组失败”定位原因

先固定可比较的条件：相同代码版本、相同环境变量和外部服务；然后收集失败测试前后有哪些 fixture、全局变量和外部资源被写入。再做几组有区分力的观察：单独与成组运行是否不同；改变顺序后失败跟着某个前序测试移动，还是仍固定在同一测试；失败测试后，另一个只读检查能否看到残留；禁用并行后问题是否消失。每个结果只能缩小调查范围，不能单独证明因果。

例如，单独运行通过、顺序变化时总在共享 catalog 被追加后失败，支持“内存状态泄漏”的假设；如果换成独立临时目录后失败仍在，则应继续查数据库记录或时间依赖。若只在并行执行失败，独立对象没有排除共享数据库键冲突。相反，如果失败稳定跟随某个测试、单独运行也发生，重排并非有效修复方向。这里列的是排查方案，不是已经执行的诊断结果。

pytest 9.2.0 于 2026-10-27 发布。当前稳定版文档在 2026-11-26 核对；该版本说明包含参数化 API 和 fixture 定义方面的更新，但本文讨论的中心仍是生命周期、依赖与状态边界，不把版本更新误写成 scope 语义改变。对于旧版 pytest，按项目实际安装版本复核文档和行为。

作用域选择的实际依据

对一个现有宽作用域 fixture，先列出它返回对象可变的字段、对象指向的外部资源、谁会写入它们，以及写入在测试间是否允许保留。然后依次判断：初始化成本是否真的足以值得共享；共享部分能否变成只读底座；每个测试能否取得自己的事务、身份或命名空间；清理能否在失败时完成；并行 worker 是否会争用同一外部键。若无法描述初始状态和清理责任，先缩小作用域，再按测得成本优化。

本次没有运行 pytest，也没有基于某个项目做耗时或通过率测量。因此，文中的列表污染是解释机制的假设例子，排查清单是建议步骤，不是一次已通过的测试报告。范围扩大值得保留的证据应同时包括：复用带来的实际成本变化，以及跨测试初始状态仍成立的验证。否则少创建几次对象，换来的可能是难以复现的顺序依赖。

相关的事务保存点与局部恢复也强调恢复边界要与数据责任对齐。对 fixture 来说，先写清谁拥有状态、谁负责还原，再决定让它活得更久；scope 是生命周期工具，不是隔离策略。
