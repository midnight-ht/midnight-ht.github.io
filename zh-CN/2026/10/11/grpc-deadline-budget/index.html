上游超时了，下游任务为什么仍在消耗资源？

超时结束的是等待窗口，不会自动杀死任意后台工作。把剩余预算和取消信号传到执行器，并区分可取消计算与已提交副作用。

正文

核心要点

  • Deadline 约束调用方等待的时刻，取消只是信号；执行器退出需要应用合作。
  • 传播剩余 timeout 扣除已耗时间，按实际语言与配置核对是否启用。
  • 请求范围计算可以停，已提交的业务副作用要查询、去重或补偿。
  • 以 RPC、worker 和业务状态三条独立证据验证取消是否完整。

上游请求超时，只能说明调用方不再等结果；它不能证明服务端的查询、线程或第三方任务已经停下。可靠的跨服务预算要同时做两件事：把剩余时间传到下游，并让真正执行工作的代码响应取消。即使工作停了，已经提交的扣款、库存变更或消息发送也不会因此回滚。

这几个状态经常被混为一谈：deadline 是调用方不愿再等的时刻；timeout 是某段操作允许消耗的时长；cancel 是停止请求的信号；worker 退出则是应用实际结束工作的结果。它们之间需要代码和业务契约连接，gRPC 本身不会替应用完成所有连接。

为什么每一跳都重新设置同一个 timeout 会浪费资源？

设一个入口到响应为止有 800 毫秒预算，身份服务用了 120 毫秒，订单读取用了 180 毫秒。现在库存服务拿到的理论剩余预算至多是 500 毫秒；实际还应为编码响应、网络返回和清理资源预留时间。这里的数字只是说明预算如何扣减的假设值，不是生产建议、压测结果或通用阈值。若每一层都重新给库存服务 800 毫秒，下游就可能在入口已经放弃后再运行一段时间。

gRPC 的 Deadlines 指南把 deadline 定义为一个时刻，把 timeout 描述为最大持续时间。截止点比从头开始的固定等待时长更能表达整个请求的预算。指南也指出，gRPC 默认并不替客户端设置 deadline；客户端需要结合系统延迟知识设定合理值，并用负载测试验证。本文没有运行服务或负载测试，因此不提供具体的毫秒配置。

传播截止时间时，时钟也会影响正确性。若服务器把入口传来的绝对时刻原样交给另一台时钟稍有偏差的机器，剩余时间可能算错。gRPC 文档描述的传播机制会把 deadline 换成 timeout，并扣除已经消耗的时间，避免这类时钟偏差。是否自动传播取决于语言实现和配置：文档举例说 Java、Go 默认启用，而 C++ 需要显式开启。团队应核对实际使用的客户端、服务端库、版本和配置，不能因服务之间使用 gRPC 就假设预算天然贯通。

一个值得在代码评审里追问的问题是：预算是在入口初始化一次，还是每个 RPC 都有独立的“新时钟”？如果是后者，应沿调用图追踪超时值的来源，并检查重试、排队和异步边界有没有再次延长它。调用方即使已经拿到 DEADLINE_EXCEEDED，远端工作仍可能继续；状态码说明 RPC 结果没有及时交付，不是后台 worker 的存活证明。

收到 cancel 信号，为什么处理器还会继续工作？

gRPC 可以在 deadline 到达后取消 RPC，但应用负责停止自己为该 RPC 启动的活动。Cancellation 指南说明，库通常无法强行中断应用提供的处理器；处理器要与库协作，长时间运行的逻辑需要周期性检查是否取消，并在取消后停止。某些语言会自动取消后续 RPC，另一些情形需要处理器显式负责。收到信号与占用 CPU 的循环退出、数据库查询被中止、临时文件被删除，并不是一个原子事件。

可以把处理拆成有边界的小段：启动查询前检查取消，数据库调用本身设置与父预算一致的上限；处理分页或批次时在批次之间检查；调用下游 RPC 时传递同一个请求上下文；退出时关闭游标、归还连接或移除临时文件。检查间隔要配合工作粒度。如果一次计算会持续数分钟，循环每个自然分块都不检查，就会在用户离开后继续消耗资源；反过来，如果每个微小操作都同步做复杂清理，取消路径本身也会带来开销。具体分块大小需要按操作成本和取消延迟要求测量，不能照搬某个固定值。

还有一个经常漏掉的边界：服务把工作放进不受请求上下文管理的线程池、进程或队列后，入口 handler 返回不等于工作会收到取消。若这是意外脱离，请把取消令牌或父上下文传给任务，并定义任务在取消时的清理行为。若产品本来就要求用户断开连接后工作继续，例如导出大文件或生成报告，那么继续执行应是一项明确接受的业务操作，而不是“脱离请求的 goroutine”。可以采用持久任务：先确认接收，返回任务标识，服务记录拥有者、状态、重试策略和自己的执行时限，用户再查询结果。站内的异步任务终态设计讨论了如何让这类工作有可查询的终态。

取消后已经发生的副作用该怎么办？

取消解决的是“要不要继续做尚未完成的工作”，不是“撤销已经完成的业务变更”。假设库存服务已经扣减数量，随后客户端在响应抵达前超时。服务端可能正常提交了扣减，只是调用方不知道结果。此时无条件重试可能扣两次；取消请求也不等于数据库事务回滚，因为提交点可能早已通过。

先区分可安全放弃的计算和会改变业务状态的命令。搜索、计算候选项或生成一个尚未保存的预览，通常可以在取消后停止并丢弃中间结果。扣款、创建订单、发出邮件或发布消息，则需要把操作结果变成可查询、可去重的业务事实。常见契约包括由调用方提供幂等键、服务端持久化键与结果的映射、在状态未知时按业务标识查询，或通过补偿操作处理已完成的一部分。选择哪种方式取决于副作用是否可逆、去重状态保留多久、并发请求如何串行化以及客户端是否可以安全重放；“加一个重试”本身不是恢复策略。

重试还会重新占用预算。gRPC 的 Retry 指南将重试描述为失败调用的新尝试，并建议明确哪些操作适合重试、退避参数、最大次数和监控指标。它还指出，收到响应头后 RPC 已提交，不再继续重试。应用层是否能在超时后安全重发，依然要看操作语义与服务端去重设计。即使每次尝试单独有 deadline，若重试策略没有纳入总预算，所有尝试的时间与服务端残留工作可能叠加。

剩余时间不够时，应该失败还是降级？

必要步骤无法在剩余预算内合理完成时，及时失败通常比把请求送进必然超时的队列诚实。只有当接口契约允许部分结果，且客户端能辨认哪些信息缺失时，才适合省略可选信息。例如，页面装饰性推荐或次要统计可能允许暂时空缺；订单金额、库存确认或权限判断则不能为了赶响应而跳过。降级策略应以业务后果和产品优先级为依据，并明确返回状态，而不是静默地拿旧数据冒充新结果。

为每个出站调用留多少返回与清理时间，取决于入口服务目标、调用分布、排队时长以及取消传播的实际速度。用单次平均延迟相加不能代表尾延迟；仅缩短超时也可能让错误更早出现，却没有停止远端计算。应同时看剩余预算分布、取消到 worker 退出的间隔、下游取消率、连接池占用和重试尝试数。这些指标解释的是不同环节，不能只凭上游 timeout 计数判断资源是否释放。

怎样验证“超时后工作真的停了”？

可以先做一张非生产的验证矩阵，记录预期 RPC 状态、执行器状态和业务副作用状态：一是预算在入口前已耗尽，确认必要工作不会启动；二是预算在下游排队期间耗尽，检查排队项是否撤销；三是计算执行中收到取消，确认工作在约定检查点退出；四是在下游副作用提交后、响应返回前取消，确认调用方可查询结果且重试不会重复变更；五是关闭或更改某一语言的 deadline propagation 配置，观察剩余预算是否仍按预期传递。每个用例要分别记录客户端状态、服务端处理器状态、数据库或队列状态，不能拿一条 DEADLINE_EXCEEDED 日志代替三者证据。

还应检查清理是否完成：连接是否回池、锁是否释放、批次是否留下可继续的游标、后台队列是否产生重复工作。若应用无法停止某个外部供应商任务，记录它的独立取消 API 和最大运行时限；父 RPC 取消无法直接保证供应商停止。测试可以在本地或隔离环境构造延迟与取消，但必须留下具体服务、版本、配置和观测记录。本文没有执行这些实验，以上是建议的验证方案，不代表任何资源节省、延迟改善或生产效果。

在接口评审中，最好要求每条“等待超时”的调用路径同时回答三个问题：剩余预算如何传递，取消如何到达实际执行器，以及副作用已经提交但响应丢失时如何确定结果。普通请求就沿这三条路径停止工作；确实需要离开请求继续运行的任务，则把它设计成有确认、有状态、可查询的持久任务。这样才能分清超时信号、执行停止和业务结果。
