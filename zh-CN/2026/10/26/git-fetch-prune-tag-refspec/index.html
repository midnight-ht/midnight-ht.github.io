fetch --prune 为何能删掉自己的标签？

Git 清理跟随 refspec 目标命名空间；区分标签自动跟随、--tags、显式映射与配置，并在删除前保存引用和预演范围。

正文

核心要点

  • prune 范围由引用映射决定，显式标签映射可能覆盖本地自建标签。
  • --tags 与 --prune-tags 作用不同，--no-tags 不取消显式标签映射。
  • 多远程共享标签空间时先确定权威来源，再预演并比较完整引用。

本地实验标签 scratch-a 从未推到 origin，一次 fetch 清理却可能把它删掉。若有效 refspec 将远程标签映射到本地 refs/tags/*，prune 会把远程缺失的本地标签纳入范围，是否由你亲手创建并不提供隔离。先看映射右侧和配置，再判断这次操作会清理哪些引用。

prune 清理的是映射关系

Git fetch 手册的 PRUNING 章节解释，清理依据远程的 refspec，而不是依据“分支”这种对象类别。通常分支映射到 refs/remotes/origin/*，所以日常观察像是在删除失效远程跟踪分支；如果映射变成 refs/tags/*:refs/tags/*，目标命名空间就是本地标签。名字仍在本地，并不说明 Git 能从名字判断它属于哪个远程。

这条边界决定了多远程仓库的风险。不同远程的分支通常分别落到各自远程跟踪空间，但本地标签没有天然的 origin 或 upstream 前缀隔离。若多个来源都写同一标签空间，再以其中一个来源作为清理依据，其他来源独有的标签也可能成为“该远程没有”的对象。审查不能只数远程数量，应看每条映射的右边究竟写到哪里。

一个实验标签怎样进入删除范围

设想一份未经执行的教学仓库：本地有 release-a 和 scratch-a 两个标签，远程只有 release-a。scratch-a 是开发者自己的实验标记。若有效配置只将远程分支映射到远程跟踪分支，不能因此推导这个实验标签会被普通分支清理删除；若显式加入标签映射，再启用 prune，它就可能作为远程缺失的本地标签被移除。

区别不在标签是谁创建，而在本地引用是否落入这次映射覆盖的命名空间。手册也明确提醒，显式标签映射参与清理时，本地被删除的标签多数甚至可能原本不来自该远程。因此，团队说“这个标签是我自己建的，fetch 不该管它”，并不能改变映射规则。

完整处理应先保存标签名到对象 ID 的对应，再检查远程实际标签集合和预演输出。若发现实验标签进入待删除范围，先收窄映射或取消这次标签清理，并查清哪些标签确实由这个远程权威管理。不要等引用消失后才依赖记忆重建；对象可能尚在不等于原标签身份、附注内容及恢复依据都已保存。

自动跟随、全部抓取与显式映射不同

手册区分了几种容易混淆的情况。默认自动跟随获取的标签，以及仅因为 --tags 而获取的标签，不会仅凭这些方式就进入 prune 范围；显式 refspec 获取的标签则会。这意味着 --tags 不是 --prune-tags 的同义写法，不能在脚本里为图省事相互替换。

--prune-tags 是提供标签 refspec 的简写，配合 prune 可清理远程不存在的本地标签。配置中的 fetch.pruneTags、远程级 pruneTags 以及清理相关配置也应一起检查。一个脚本表面只写 fetch --prune，不代表用户全局配置或远程配置没有扩大实际范围。审查命令文本时要把有效配置作为输入，而不是事后解释。

失败反例是把全局启用标签清理当成统一团队环境的办法，但没有询问每个仓库是否把同一个远程当作标签唯一权威。有的仓库保存多个上游版本标记，有的保留未发布实验标签，策略并不相同。若确需镜像远程，应在隔离镜像仓库中明确这种责任，不要把个人开发仓库也默认为可丢弃镜像。

--no-tags 能阻止显式标签映射吗？

不能。它控制默认标签跟随，不会取消显式提供的标签 refspec。手册专门展示了 --no-tags 与显式标签映射同时存在时仍然抓取标签的情况。因而想“这次不碰标签”，需要检查是否还有显式映射或等价配置，而不是再加一个看上去有否定含义的选项。

这一追问也给预演输出定了阅读方式：逐条看目标引用，不只看选项名。若目标仍是 refs/tags/，就要解释这些标签为何在操作范围内。选项的作用边界比它的英文名称更重要；把自动行为关掉，不等于把另一条显式指令撤回。

用引用差异验证，不拿工作区文件作证

拟议的隔离验证可以建立一个临时本地远程和两个测试克隆，分别使用默认分支映射、额外标签映射以及标签清理配置。每种情况先用 git fetch --dry-run --prune origin 查看预期变化，再在可丢弃仓库执行对应 fetch，比较完整引用清单。这里的命令用于说明检查方式，没有在本轮文章中执行，也没有对当前仓库做清理。

验证还应覆盖仅自动跟随、仅 --tags、显式标签映射和 --no-tags 同显式映射组合。输入集合里保留一个只在本地存在的标签，一个只在第二远程存在的标签，以及一个已经从权威远程删除的标签。检查每个结果对应哪条映射，才能证明策略实现了预期范围。不要用“工作区文件没变化”替代引用验证，两者是不同状态。

恢复计划要在操作前可用。记录引用及其对象 ID，必要时使用项目认可的备份方式保留对象和附注标签信息。若标签确实误删，恢复应依据已保存身份并复核下游消费者，不要仅凭相似名字重新指向当前提交。本文没有执行恢复操作，也不保证所有被清理对象在之后都仍可找回。

关于另一方向的范围选择，可阅读推送分支与发布标签。fetch 的安全判断同样落在完整引用名与映射上：先确定谁是标签权威，再决定是否同步删除；远程分支清理的便利不应无意扩展到共享的本地标签空间。
