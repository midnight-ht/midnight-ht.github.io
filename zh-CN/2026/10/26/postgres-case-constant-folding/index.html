CASE 没进入分支，为什么仍可能常量除零

区分计划期折叠与运行时选择，用逐行分母、聚合参数与 NULLIF 明确错误保护的位置和数据口径。

正文

核心要点

  • 运行时分支选择不能禁止所有计划期常量求值。
  • 零分母应按业务定义为缺失、错误或其他明确状态。
  • 保护聚合里的危险运算，应检查输入而非只看外层结果。

CASE 没有进入某个分支，仍可能因为那个分支里的常量除零而失败。PostgreSQL 的运行时条件选择，并不是对计划阶段所有表达式处理的禁止令。面对这种错误，应先问危险表达式在哪个阶段被求值，再决定保护条件应当写在它的外面，还是直接修正表达式的输入。

分支选择与表达式准备有不同时间

PostgreSQL 18 的条件表达式文档先说明 CASE 通常只求值所需的子表达式，随后明确限定：这项原则并非绝对，常量子表达式可能在规划时求值。因此，把 1/0 放进运行时认为不会执行的位置，仍可能在真正扫描数据之前报错。

这不要求把 CASE 理解成无效工具。对逐行变化的分母，条件可以在正常执行时选择分支；问题是团队把运行时选择扩张成了跨越所有准备阶段的承诺。源代码里的文字位置与数据库实际求值阶段不总是同一条时间线。排查时若只打印每行条件为 false，就可能一直看不见发生在行处理之前的失败。

假设一个报表在“没有配置费率”时显示空值，开发者为了占位在备用分支写了常量除零。这段未执行的教学片段只展示风险，不承诺每一种 CASE 形状都会以相同步骤失败。

SELECT CASE WHEN enabled THEN amount ELSE 1 / 0 END
FROM report_inputs;

即使测试数据里 enabled 全为真，也不能据此声称备用分支在任何计划下都不会导致错误。这里缺少的不是更多同样为真的数据，而是表达式本身对“无费率”状态的合法表示。占位应该是合适类型的 NULL、明确状态或另一路错误处理，不能把一定无定义的算术埋在分支里。

把保护放进危险操作的输入

另一个假设报表要计算每件平均金额，输入分别为总金额一百、件数四，以及总金额一百、件数零。若业务选择“零件数没有平均值”，可把零转换成空值，再做除法。下面代码未执行，按给定数字推导的期望是二十五和 NULL。

WITH inputs(total, quantity) AS (
  VALUES (100::numeric, 4), (100::numeric, 0)
)
SELECT total / NULLIF(quantity, 0) AS average
FROM inputs;

NULLIF 在两项相等时返回 NULL，这是同一官方文档给出的语义。这里的选择避免把零当作除法的有效分母，同时保留结果未知。不能未经讨论就再把 NULL 改成零：平均值为零与平均值不存在，不是同一个业务事实。需要对外显示横线或“无件数”时，可以在展示层映射，但统计计算仍应保留定义域区别。

如果件数零本来就属于数据错误，则返回 NULL 可能过于宽容。应在输入校验或数据约束处拒绝，附上能定位记录的错误。算术不报错只代表表达式有了返回方式，不能证明脏数据可以继续结算。选择 NULLIF、业务校验或独立错误状态，要由零分母在领域中的含义决定。

外层 CASE 能挡住聚合里的除零吗？

不能把外层条件当作聚合输入的普遍保护。聚合参数的表达式在聚合得到结果之前就需要处理。假设先计算每行金额除以件数，再把这些值求平均，最后才用外层 CASE 判断是否有零件数；那个判断可能来得太晚。保护应当在每行危险操作发生的地方，或在业务上合理的输入过滤阶段生效。

两种修正并不等价。过滤掉零件数行，会把这些记录从统计对象中移除；给它们产生 NULL，则依赖后续聚合怎样处理 NULL。若报表还要报告异常记录数，直接过滤可能把证据也删掉。评审时应同时写清分子、分母和异常数量的口径，而不是以“查询不再报错”作为唯一结果。

站内布尔聚合与未知输入解释了聚合可以忽略某些未知信息。本题的下一步也是追踪输入：修复除零之后，那一行究竟还在不在，是否仍被计入对象总数，界面能否区分没有数据与存在无效数据。这些问题决定报告是否诚实。

参数不是一张通用的延期求值许可证

把常量改成参数，并不能独自构成可靠的安全合同。参数取值如何进入计划、查询是否被重复使用、函数声明与表达式所处位置，都需要按真实调用方式核对。本文不对某个驱动或预备语句策略作未验证的保证。最容易审查的修复，通常是让危险操作在允许的输入范围内本身有定义。

同样，不应为了阻止折叠就随意改函数的易变性声明。声明承载的是函数真实行为，错误声明可能影响其他查询的优化与正确性。若团队需要精确分析自定义函数的计划期行为，应该补查函数分类和表达式求值文档，并留下实际环境的说明计划；这超出了这里对 CASE 与 NULLIF 的局部讨论。

建议保留一份最小诊断记录：具体数据库版本、原始表达式、参数类型和值，以及错误在准备还是执行时出现。若应用只保留最终异常文字，可能无法区分数据库规划失败与客户端预先计算失败。把这份记录连同独立期望交给评审，比反复增加全为真的样本更能检验修复是否作用在正确阶段。

拟议验证分成三组：常量无效表达式位于未选分支；变量分母为正、零和 NULL；危险除法位于聚合参数而外层有 CASE。每组先写明业务预期，再记录错误发生于准备还是执行。对修正后的查询还要断言有效结果、无效行计数和总记录数。本文没有执行 SQL，也没有证明任何线上报表已修复；“分支没有进入”只能说明一项运行时观察，不能替整个查询的定义域作担保。
