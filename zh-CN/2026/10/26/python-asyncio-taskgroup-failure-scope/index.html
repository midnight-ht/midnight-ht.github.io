TaskGroup 子任务失败：取消范围与清理责任

用双清单导入说明同组失败、取消传播、预期单项错误与组外任务，明确完成和提交之间的边界。

正文

核心要点

  • 非取消失败会取消未结束的同组任务并等待退出。
  • 取消不会回滚已写文件或远端副作用。
  • 捕获为数据的单项失败与组外任务需要独立合同。

同一个 TaskGroup 里的子任务以非取消异常失败时，其他仍在运行的同组任务会被取消，退出上下文时还会等待它们结束。这给并发工作划出失败范围，却不会撤回已经发生的文件写入或远端请求。决定哪些工作属于一组，应该先看它们是否共同构成一次成功，而不是只看能否同时启动。

等待同组结束，才到组外做决定

Python 3.14 的协程与任务文档规定了 TaskGroup 的等待、取消和异常组合行为。本次页面标为 3.14.9；TaskGroup 自 Python 3.11 引入，本文不将各版本新增细节混成一份所有环境都适用的承诺。下面讨论普通非取消异常，特殊基础异常仍应按官方说明处理。

假设导入任务需要同时读取商品清单和价格清单，少一份都不能提交完整版本。两项工作放在同一个组里，可以表达其中一项失败后不再继续等待另一项正常生产新结果。退出组后，再决定是否提交整份导入。但“组已退出”只说明任务完成关系，不证明产物齐全；失败路径会通过异常交给调用方。

下面是未执行的教学代码。read_products 与 read_prices 是待实现的异步函数，不是已完成验证的客户端。代码的提交位置位于正常退出之后；若组失败，这条正常路径不会继续执行。

import asyncio

async def prepare_import():
    async with asyncio.TaskGroup() as group:
        products = group.create_task(read_products())
        prices = group.create_task(read_prices())
    return build_import(products.result(), prices.result())

假设价格读取失败，商品读取正在等待网络。组会请求取消尚未结束的同组任务，并在退出前等待清理。不能据此写出确定的两项完成先后或最大取消耗时：异步任务何时响应取消，取决于代码到达可中断等待点以及自身处理。需要强制时间预算时，还要另外设计超时和外部操作的完成合同。

取消请求不等于外部副作用回滚

假设商品读取已经把半份缓存写到磁盘，随后价格失败。取消不自动删除那份缓存，更不会撤回服务器已经接受的请求。如果两份结果必须同时可见，可以先写各自临时产物，正常退出并验证完整性后再进入单独提交阶段；失败时按本次任务身份清理。这是应用的提交设计，不是 TaskGroup 替文件系统提供事务。

清理应由持有资源的任务负责。例如自己创建临时文件的协程，可在 finally 里关闭或移除自己拥有的资源。共享文件、连接和外部句柄不能因为一次取消就由任何子任务随意关闭。先定义所有权，避免一项失败破坏其他仍合法使用该资源的工作。

Python 文档提醒，结构化并发机制内部使用取消；协程若吞掉 CancelledError，可能破坏预期行为。通常在清理完成后继续传播取消，不把它当作普通业务失败默默转换成成功。捕获只为释放资源，与改变任务结果，是两项不同决定；这项区别需要在代码审查中看见，而不是藏在统一异常装饰器里。

捕获单项错误后，整组还会失败吗？

若子任务在内部把某个可预期异常捕获并正常返回结果对象，组看到的是正常完成，就不会因为这项已经处理的错误自动取消其他任务。这适合允许部分成功的批次，但意味着整组正常退出不再等同所有业务项成功。调用方还要逐项检查返回状态，明确哪些结果能提交。

例如批量检查十个网址，某个网址返回“未找到”可能是需要收集的结果，而不是让其他九项都停止的基础设施故障。可以把预期的未找到表示为数据；连接池整体不可用或数据结构损坏则可能应继续作为异常传播。分类取决于业务合同，不应把所有 Exception 都转换成同一个失败字段，只为保持组表面成功。

反过来，若两份清单必须一起成功，内部捕获价格失败后返回空列表，可能让 build_import 生成看似合法却缺价格的数据。需要给结果状态与内容区分类型，并在提交前检查完整性。容错的目标是保留可解释结果，不是消灭所有异常让正常路径畅通无阻。

组外启动的任务不在这份范围里

通过别处的 create_task 启动、没有加入该组的工作，不会因为处于同一个函数或共享一个请求编号就自动成为组成员。若子任务把另一项工作丢到组外，退出组时的等待结论也不能涵盖它。后台工作需要自己的生命周期、错误接收与停机责任，不能借用 TaskGroup 的名字掩盖未管理的任务。

本站关于异步监听器拒绝的讨论也区分了启动与完成。本题通过 Python 组成员关系给出更具体的范围：谁由 group.create_task 创建，谁的结束会被上下文等待。语言和接口不同，责任问题相同；不能把同步调用返回当成所有后代工作结束。

普通非取消失败在同组任务结束后，按条件组合成 ExceptionGroup 或 BaseExceptionGroup 再抛出；KeyboardInterrupt 与 SystemExit 有特别处理。因此组外错误接收方应保留子异常归属，不要只存一条丢失来源的失败文字。本文不扩展讲解异常组匹配语法，实际处理应核对目标 Python 版本。

拟议验证让两项协程停在受控等待点，再使其中一项失败，记录另一项收到取消、执行清理和组退出的顺序。另测子任务主动取消、内部捕获预期异常、清理失败、组外任务，以及两项近乎同时失败时异常的归属。不要依赖真实网络竞速碰巧产生期望先后。本文没有运行异步任务或故障注入；首先应能核对的是组成员、终态与提交边界，而不是一条“已取消”的界面提示。
