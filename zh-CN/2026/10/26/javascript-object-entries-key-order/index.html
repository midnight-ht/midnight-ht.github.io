Object.entries 的键顺序：数字样式为什么插队

用字段录入、删除重建与撤销说明索引键顺序，区分可枚举性，并为用户顺序建立明确数据。

正文

核心要点

  • 普通对象先枚举数组索引，再枚举其他字符串键。
  • 用户排序应保存成明确位置，不能从属性历史推断。
  • 值更新、删除重建和不可枚举属性需要分别验收。

先录入键 "10"，再录入 "2"，Object.entries 却可能先列出二，再列出十。对普通对象，属于数组索引的字符串键会先按数值顺序出现，其他字符串键再按创建先后排列。若页面需要保存用户录入顺序，应把顺序作为明确数据，不能把它寄存在对象属性创建历史里。

不是所有看起来像数字的键都一样

ECMAScript 的 Object.entries 定义通过枚举自有属性收集键值；普通对象的顺序由 OrdinaryOwnPropertyKeys规定，先处理数组索引，再处理其他字符串键，最后处理符号键。entries 的最终结果只包含自有、可枚举的字符串键对应项，因此符号键不在输出中。

本文依据检索当日标为 ECMAScript 2027 的 living draft，讨论普通对象，不把代理对象或各类特殊对象都承诺成相同输入。数组索引也不是“字符串能变成数字”这么宽。"02"、"-1" 与 "2" 不属于同一类；最大边界也有限制。审核数据模型时，应使用规范里的索引定义，而不是给字段名做一次宽松数字解析来模仿枚举规则。

下面是未执行的教学示例。它依次建立十、二、带前导零的二和普通标签，按上述普通对象规则推导的键顺序为二、十、前导零的二、标签。

const fields = {};
fields['10'] = 'ten';
fields['2'] = 'two';
fields['02'] = 'leading zero';
fields.label = 'label';
const rows = Object.entries(fields);
// Expected keys by specification: ['2', '10', '02', 'label']

这里没有丢数据，变化的是枚举顺序。若表单把 rows 直接作为可编辑行，用户看到的排列就会与录入历史不同。给输出数组再按键排序，只有在业务本来要求按编号时才是修复；若业务要用户自定义位置，排序只是选择了另一种同样不符合需求的规则。

用数据表达位置，而不是猜创建历史

假设一份流程表需要保留用户拖动后的字段次序。我会把每行存成含稳定编号与位置的记录，或保存一份明确的有序编号列表，再用对象承担编号到内容的查找。这样内容更新不必改顺序，顺序更新也不会依赖字段名是否碰巧长得像整数。编号和位置应分别命名，避免后来把二者重新混在一起。

如果只需要插入顺序且不要求 JSON 直接表达同一结构，也可以评估 Map，但序列化、重复键更新和调用方合同仍需明确。选择 Map 不是给所有对象加一个更好的遍历方式，而是选择另一种容器语义。若最终接口仍把数据转成以数字样式编号为键的普通对象，进入下一层后又会回到原来的枚举规则。

对于已经存在的载荷，首先问顺序来源在哪里。服务端可能早已返回 rank，只是页面没有用；数据库也可能根本没有保存用户顺序。后者不能从当前对象的键列表逆推出历史。迁移需要选定一次明确的初始顺序并告知相关使用者，不能把新规则包装成恢复了从未存下的原始操作记录。

站内自有字段与原型继承讨论哪些字段属于输入。本题增加另一条轴：字段属于对象，并不意味着枚举顺序就代表业务顺序。存在性、可枚举性和位置都应该分别验证。用一个“遍历正确”测试覆盖这三项，会留下难以察觉的空白。

删除再添加，会回到原来的位置吗？

对普通对象的非索引字符串键，删除后重新创建会形成新的创建先后，因此可能移到其他字符串键后面。只是改已有属性的值，与删除再创建不是同一动作。数组索引键则仍受索引排序支配，不能靠删除重建把 "2" 稳定移动到 "10" 后面。

这影响撤销实现。假设页面删除一行，再用重新赋值恢复对象属性；内容可能恢复了，但非索引键的枚举位置未必还是原位置。若用户要求撤销连位置也恢复，就应把位置纳入历史快照，不能只保存被删值。测试只断言字段再次存在，会漏掉这项可见行为。

对“更新键值是否移动行”也要有预期。普通字段值变化不应擅自成为排序事件；如果页面把每次刷新转换为一个新对象，再靠创建顺序决定行号，那么上游合并顺序就可能泄漏成界面顺序。明确位置数据后，可以测试内容变更没有影响位置，从而把两个行为真正分开。

不见了的键，需要检查另一条规则

符号键和不可枚举自有属性都不会由 entries 原样列出；继承属性也不属于它的结果。这与索引键先出现是不同问题。如果某项数据完全没有进入输出，应先检查属性描述符与来源，而不是继续修排序。需要检查所有自有键时可以研究 Reflect.ownKeys，但读取值与后续序列化仍有各自的行为，不能把“列全键”直接等同业务导出。

一个可加入边界表的对照是四二九四九六七二九四与四二九四九六七二九五对应的十进制字符串：前者可属于数组索引，后者不属于这类索引。不能简单地说所有非负整数字符串都排在最前面。若字段来自数据库的大编号，越过边界时枚举类别可能变化，这更说明业务顺序不宜依赖键的外观。边界样本应使用字符串原值，避免先转数值再转回而改写前导零等信息。

拟议验证保留一张独立期望表：索引字符串、前导零、负号、普通名称、符号键、不可枚举属性、继承字段；再比较值更新、删除重建和序列化往返。界面层额外验证拖动后保存、刷新与撤销的位置。本文没有执行代码，也没有修复某份表单。可以再设定两个稳定编号：甲的位置为二，乙的位置为一。保存并重新载入后，期望乙在甲前；只修改甲的名称，再次载入仍应保持这个次序。若列表又按编号或对象构造先后排列，就说明持久化位置没有真正进入展示路径。
