多数组 unnest 长度不等：补 NULL 不是拒绝输入

从商品数量导入核对位置配对、内部缺失、独立排序、下界与批次接纳，避免把函数成功当作完整载荷。

正文

核心要点

  • 短数组补未知值，函数成功不代表载荷完整。
  • 数组等长仍可能因独立排序而错配。
  • 提交前同时核对位置关联、行身份和批次失败策略。

把商品编号数组和数量数组交给同一个 unnest，长度不同不会自动拒绝整批。PostgreSQL 会按元素位置展开，较短数组缺少的位置补 NULL。批量写入之前，必须另外证明两个数组确实代表同一份配对清单；看到查询正常返回，不能据此认定载荷完整。

补齐输出不是修复输入

PostgreSQL 18 数组函数文档给出了多数组 unnest 的规则：多个数组并行展开，短数组以 NULL 补齐，这种调用形式用于 FROM。它解决的是如何形成结果行，没有为商品、数量或任何两个业务字段推断对应关系。

假设某次未执行的采购导入包含编号一〇一、一〇二、一〇三，却只提交数量二和五。按位置规则，前两行分别是第一件配二、第二件配五，第三件数量为 NULL。数据库没有知道第三件原本应当有多少，更没有从别的记录借一个数量。若接口把 NULL 默认成一，就已经作出一次没有来源的采购决定。

SELECT *
FROM unnest(ARRAY[101,102,103], ARRAY[2,5])
  AS line(product_id, quantity);

此处代码、商品与数量都是教学假设，本文没有运行查询。应在验收里独立写出三行及第三行未知的预期。若实际协议要求每件都有数量，正确结果不是接受第三行，而是让完整性校验在写入之前拒绝整份不完整载荷，并给调用方指出是哪一列缺了位置。

长度校验要保留空数组与未知数组的区别。两列都为空可能代表合法空批次，也可能是客户端漏传；一列为 NULL 更需要按接口合同解释。可以利用 cardinality 检查元素总量，但总量相等不等于输入形状、元素值与配对身份都正确。本站空数组长度与 cardinality处理数量口径，本题在数量之外还要审核关联关系。

相同长度就能证明商品数量配对正确吗？

不能。假设编号数组保持甲、乙的顺序，数量数组却在前端单独排序，原来的甲配九、乙配一会变成甲配一、乙配九。两个数组长度相同，每个数量也都为正，数据库仍无法发现这项语义错误。若字段长期一起流转，应考虑将每一行表示成同一个结构记录，让编号与数量在传输和编辑时一起移动。

继续使用平行数组也可以，但要说明所有者：谁创建顺序、谁有权重排、序列化过程中能否只过滤其中一列。不要让某个“清理空值”的函数先删掉数量数组中的 NULL，再去配对；中间位置一旦消失，后面的数量会顺次前移，原本可见的缺失反而变成外观合法的错配。

重复商品编号也不能靠 unnest 自动解释。若同一商品出现两次，业务可能允许两条不同用途的行，也可能要求合并数量或直接拒绝。应先定义行身份和合并策略，再生成目标写入。简单按商品去重会丢数量，简单相加又可能把本来分开的配送安排合成一条，均不是函数语义可以决定的。

两个独立展开不是同一项操作

把每个数组各自放在独立的 FROM 项中，再做无条件连接，可能得到所有组合，而不是按位置配对。两件商品和两个数量可以产生四个组合。看到每件商品都有数量，并不表示对应正确；结果行数突然增加，就是需要先检查连接形状的信号。不要通过 DISTINCT 删除重复来修补配对设计。

如果已有独立行源，必须依据明确的行键关联，而不是假定两个流的到达先后天然相同。带位置编号可以帮助诊断和关联，但位置本身不是商品身份。客户端删除第一行后重新提交，原来的第二个位置已不是同一个业务对象；更新既有订单行时，应使用稳定行标识并另外记录展示位置。

批量写入还应在校验与提交之间保持同一份载荷。先校验一个可变数组、稍后再从共享对象重新读取另一个版本，可能让原先的长度结论失效。这是应用设计上的输入快照责任，不是要求 unnest 提供锁。把已验证数据固定为本次操作的输入，才有资格把校验结论带入执行。

数组下界不同，会按下标数字对齐吗？

不会把业务配对自动变成下标相等的连接。这里的展开按各数组的存储元素顺序前进。若一列下界为零，另一列下界为一，第一项仍会与另一列第一项一起出现；不能把数组下标当作已经核验的跨列外键。需要按实际下标关联时，应另外选择能保留下标并显式连接的查询设计。

这项区别对外部系统导入尤其有用。有的生产者把数组当序列，有的把下标当领域编号；即使元素数量相同，二者的合同也不同。接口应选一种解释，并在边界拒绝另一种形状，避免数据库接受了值，却沿用了调用方并未同意的身份解释。这里仅讨论数组展开，不提供通用数据交换方案。

拟议验证覆盖等长、不等长、内部 NULL、空数组、整列 NULL、重复编号、单独排序一列，以及不同下界。对每组同时断言接纳或拒绝、输出行数、编号数量配对和最终写入身份。校验失败时确认没有半批记录落库；若系统允许部分成功，则必须另有逐行回执与重试合同。本文没有执行导入，NULL 补位只是需要识别的语义，不是业务完整性的证明。
