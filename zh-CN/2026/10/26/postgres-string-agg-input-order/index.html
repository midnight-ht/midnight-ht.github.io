string_agg 内部排序：外层 ORDER BY 为什么无效

从签署名单说明聚合输入顺序、并列键、连接扩行与缺失姓名，分别定义名单成员和文本先后。

正文

核心要点

  • 名单内部顺序写在聚合调用中，外层排序只排列结果行。
  • 先确定每份签署记录身份，再处理连接扩行和同名。
  • 可解析交换需要结构协议，展示拼接不证明完整性。

给客户导出签署人名单时，结果行按客户编号排列，并不能保证每行里的姓名也按签署时间排列。string_agg 的内部顺序取决于送进聚合的输入；若顺序属于导出合同，应把排序写在聚合调用内部，并为时间相同的记录补上能决定先后的键。

一行结果里也有自己的顺序

PostgreSQL 18 的聚合函数说明指出，string_agg 等函数的结果依赖输入顺序，默认顺序未指定，可在聚合调用内控制。外层 ORDER BY 排的是聚合已经产生的结果行。若整条查询只有一个汇总行，外层再怎么排序，都没有机会重新排列那个字符串内部的片段。

这不是数据库随机出错，也不意味着表格曾经按某个顺序插入，就应该一直按那个顺序读取。关系查询中需要的业务顺序应由查询表达。某次计划恰好顺着时间索引扫描，只能解释那次观察，不能代替输出合同；索引变化、连接和计划选择都可能让原先看似稳定的结果暴露问题。

假设签署记录只有三条：客户甲在九点由林签署，九点由周签署，十点由陈签署。记录编号分别为十二、十一、十三。业务约定按签署时间升序，同一时间按记录编号升序。因此纸面期望为周、林、陈，而不是名字字母顺序，也不是示例书写的先后。下面 SQL 未执行，数据和预期都是教学设定。

WITH signatures(customer_id, id, signed_at, name) AS (
  VALUES (7, 12, timestamp '2026-10-26 09:00', 'Lin'),
         (7, 11, timestamp '2026-10-26 09:00', 'Zhou'),
         (7, 13, timestamp '2026-10-26 10:00', 'Chen')
)
SELECT customer_id,
       string_agg(name, ', ' ORDER BY signed_at, id) AS names
FROM signatures
GROUP BY customer_id
ORDER BY customer_id;

这条查询里有两份排序责任。聚合内部的时间和编号决定名单，外部的客户编号决定不同客户出现的先后。它们可以同时存在，互相不能替代。若只按时间，九点的两个人仍没有被业务规则区分；增加一个真正唯一且稳定的记录编号，是为了补全先后关系，而不是为了让计划更好看。

先决定记录身份，再拼字符串

名单的顺序正确，不证明名单的成员正确。假设签署记录再连接附件表，一位签署人有两个附件，聚合输入就可能出现两行同一个人。若业务要每次签署一次，就应先恢复到每份签署记录一行，再聚合。随手使用 DISTINCT name 会把同名不同人或同一个人的两次合法签署一起合并，掩盖输入粒度问题。

同样，去重和排序可能要求不同字段。业务若只想列出每个参与人一次，先定义采用该人的哪次签署作为排序时间，例如第一次有效签署，再形成每人一行的中间结果。不能先选择任意一行，再把得到的字符串称为“按首次签署排序”。中间记录身份、取舍规则与最终展示应该能够从同一份输入逐项追踪。

对这份假设导出，我会保留结构化的签署编号与时间，把字符串作为展示字段。逗号拼接不能无损承载姓名中本来就有逗号的情况；如果下游要重新解析，应该选择明确的结构格式和转义协议。string_agg 解决片段组合，不负责替团队定义交换格式。字符串看上去整齐，并不意味着以后能准确拆回原来的记录。

子查询排过序，连接后还能保证吗？

不能把“上游写过 ORDER BY”当成经过所有后续操作的保证。官方文档专门提醒：排序子查询通常能提供所需输入，但外层还有连接等处理时，可能在聚合前改变行的次序。若顺序直接影响聚合含义，把要求贴在聚合调用内更清楚，也使后来的维护者不必追踪多层查询才知道名单为什么这样排列。

这不代表子查询排序永远没有用途。需要先限制候选集合，例如按某项规则选出最近几条记录，再把选中的记录按另一顺序展示，是两个阶段的问题。前一阶段排序参与“选谁”，后一阶段排序参与“怎样拼”。若维护时删除看似重复的一份排序，可能改变被选中的集合，或改变最终文本；应分别给两项职责写预期。

可以把这一点与站内选择一条 DISTINCT ON 记录对照：选代表行需要确定排序，代表行随后进入的聚合也需要自己的顺序约定。两个位置都出现时间字段，不表示它们承担相同责任。讨论性能前，应先确认改写仍选中了同一批签署记录。

NULL、空字符串与分隔符怎么区分？

string_agg 连接的是非空输入。假设周的姓名为 NULL，文本不会自动保留一个“未知姓名”的位置；空字符串则是另一种输入，可能产生相邻分隔符。若导出必须显示缺失，应明确是否把缺失映射成占位文字，并同时保留缺失计数。映射后的“未填写”是展示策略，不能再当作原始姓名。

没有输入记录时，聚合结果的 NULL 与有记录但姓名都缺失，也需要按导出需求区分。可以另带记录总数和姓名有效数，防止调用方把空文本当作“无人参与”。这里不要求每个页面都展示两个数，而是要求决定是否完整时仍有原始证据，不让展示字段独自承担审核职责。

拟议验证先准备时间并列、姓名重复、姓名为空、单人、零人五组输入，独立写出期望记录身份和字符串。随后给一名参与人增加两个附件，确认连接没有扩大名单，再改变原始输入顺序，确认结果仍符合显式排序。本文没有运行数据库或测量查询成本；可验收的承诺是这份 SQL 应表达的成员和先后，不是固定扫描方式或速度。
