file URL 的 pathname 为什么不是可靠本地路径

区分 URL 编码、模块相对基准、平台路径和访问权限，说明 fileURLToPath 与 pathToFileURL 的转换边界。

正文

核心要点

  • 文件 URL 与原生路径需要明确转换边界。
  • 模块位置和启动目录是不同的资源基准。
  • 转换不证明存在、获权或打包版本正确。

new URL(...).pathname 是 URL 的路径部分，不是已经转换好的本地文件路径。空格与中文可能仍以百分号编码出现，Windows 驱动器和网络共享还涉及平台规则。Node 中需要从 file URL 取得本地路径时，应使用 fileURLToPath，而不是只取 pathname 或手工截掉 file://。

文件名与 URL 表示是两层数据

Node.js URL 官方文档明确对照了 pathname 与 fileURLToPath，包含编码字符、Windows 盘符和网络共享示例。本次打开的 current 页面标为 v26.12.1。这里讨论文件 URL 的转换语义，不据此承诺其他版本拥有相同的新增选项，也不推定运行机器一定是 Windows。

假设构建脚本所在目录包含“报告草稿”和空格。它用 import.meta.url 取得当前模块 URL，再拼接一个模板 URL。如果把 pathname 直接交给文件读取接口，读取方接到的可能是带 %20 的文字，而磁盘上的实际文件名含空格。URL 看起来指向正确位置，仍可能因为表示层没有转换而找错文件。

下面代码未执行。它只展示模块相对资源的定位，不证明模板存在、可读或内容正确。

import { fileURLToPath } from 'node:url';
import { readFile } from 'node:fs/promises';
const templateURL = new URL('./templates/report.txt', import.meta.url);
const templatePath = fileURLToPath(templateURL);
const text = await readFile(templatePath, 'utf8');

路径的基准是当前模块的位置，不是进程工作目录。若需求原本是读取用户启动命令所在目录的文件，这段改写可能反而改变含义。先确定资源属于安装包、模块还是调用方的目录，再选择基准。一个“找不到文件”错误，可能来自编码，也可能只是相对位置合同不同，不能统一用路径转换解释。

为什么只做 decodeURIComponent 还不够

百分号解码只是转换的一部分。file URL 包含协议、主机和平台相关表示；Windows 网络共享中的主机有路径语义，驱动器写法也不等于 POSIX 路径。通用字符串解码不会凭空获得这些平台规则。专用转换与文件 URL 接收接口还有自己的输入检查。例如官方文件系统文档中的 readFileSync(new URL('file:///p/a/t/h/%2F')) 在 POSIX 路径示例里报错：URL 对象已经构造，拒绝来自文件 URL 接收路径这一层，而不是通用 URL 构造器。手工解码不能代替转换或接收接口的检查。

转换还应控制次数。假设实际文件名包含字面文字 %20，URL 会为百分号本身编码。如果先手动解码，再交给另一个会处理编码的步骤，就可能把原来的字面字符误当作空格。边界处保留 URL 对象，直到交给专用转换函数，通常比在多层工具之间传递半解码字符串更容易审查。

这也影响日志。排错时可以分别记录脱敏后的 URL 表示和最终路径，并标明二者类型；不要把一段编码字符串直接标成“真实磁盘路径”。日志里的中文可读并不证明身份一致，显示层还可能自动解码。真正需要比对的是转换后的目标和约定的资源，而不是两个界面看上去是否相同。

路径转回 URL，为何不能拼 file://？

反向转换应考虑 pathToFileURL。假设本地文件名含 #，直接拼接可能把它解释成 URL 片段；含 ? 时也有不同的结构含义。专用转换负责把路径中的字符放进合适表示，避免把文件名误拆成 URL 的其他组成部分。这里的原则是对称的：路径不能只靠字符串前缀变成 URL，URL 也不能只靠删除前缀变成路径。

相对路径还有基准问题。把 ./report.txt 原样接在 file:// 后，不是完整的本地绝对定位方案。若系统约定根据工作目录解析，先按该规则得到明确路径，再进行转换；若根据模块位置解析，则用模块 URL 作为基准。不要在错误处理里悄悄换一个基准重试，那可能读到另一份同名配置并制造更难定位的错误。

有些 Node 文件系统接口本来接受 file URL 对象。在它们的正式合同支持时，可以直接传 URL，避免没有必要的字符串中转。需要与只接受原生路径的库交互，或需要做原生路径操作时，再明确转换。两种路线都应围绕接收方的接口合同，而不是把“所有地方都转成字符串”当作统一规范。

转换成功不等于获准读取

fileURLToPath 不证明目标存在，不检查业务权限，也不会把不可信路径限制在某个目录。若输入来自用户，仍需根据实际文件访问设计验证协议、允许范围与目标身份。路径字符串在语法上有效，与某个账户有权读取，是两件不同的事。本文不提供目录隔离或符号链接防护的完整方案。

类似地，读取成功不证明资源属于预期版本。构建脚本可能在开发目录找到模板，打包后却没有把模板一起交付。验收应在实际产物的目录结构里读取预期文件，并核对内容身份。本站文件读取与取消边界讨论读取开始以后的完成关系；本题先明确读取之前究竟定位了什么。

可以把假设产物复制到另一个含空格的安装目录，并从完全不同的工作目录启动命令。若资源属于模块，期望仍读取产物旁的模板，而不是启动目录里的同名文件。验证时给两份模板写不同标记，核对读取内容身份，不只断言调用没有报错。这里给出的是待执行方法，没有实际移动目录或启动构建。若打包工具改写了模块定位，仍需按改写后的真实产物重新验证，不能沿用源码目录里的结论。

拟议检查包括空格、中文、字面百分号、井号文件名、模块基准与工作目录不同，以及适用平台的盘符和共享路径。分别验证转换结果、读取目标和失败类型，跨平台部分要在对应系统执行。本文没有创建文件、运行代码或完成平台矩阵；保留这些条件，比把一条 POSIX 示例称作所有系统都已通过更有用。
