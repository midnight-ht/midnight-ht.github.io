环境变量写了 false，功能为什么仍然开启？

Node 环境值是字符串；明确布尔允许值、缺失和无效策略，在统一边界解析而非依赖真值判断。

正文

Node.js 读取的环境值是字符串，字符串 false 不能直接当作布尔关闭值，配置边界应显式解析与验证。配置文件看起来写了一个布尔词，不代表运行中的 JavaScript 已经获得布尔类型。开关状态需要由明确规则产生，而不是由文本外观决定。

环境文件并不是自动类型系统

Node.js 的环境变量文档说明，其环境文件解析把值解释为文本，例如数字、布尔词和看起来像对象的内容，都会成为字符串，而不是自动转换为对应类型。这里针对 Node 文档描述的解析机制；若项目使用额外配置库，需要继续检查该库是否执行转换以及转换规则。

假设维护者设置一个功能开关为文本 false，程序却直接把环境值放进条件判断。MDN 的 Boolean 参考把非空字符串归为真值；因此文本 false 可能仍让条件进入开启分支。这是未经运行的解释示例，不是某个服务已发生事故的记录。需要检查的不是字母大小写是否醒目，而是值在边界上何时被转换。

允许值和缺失行为写清楚

一个配置解析器应明确接受哪些值，例如是否只允许 true 与 false，是否区分大小写，以及空字符串和未设置分别代表什么。具体选择由项目决定，关键是所有环境使用同一规则。不要为了“友好”接受任意拼写，再让维护者无法知道某个输入最后会启用还是关闭。

对于无效值，可以选择在启动时给出明确失败或采取经过设计的安全默认，但这应与业务风险一致。悄悄把所有未知文本当作关闭，可能隐藏部署拼写错误；悄悄当作开启，则可能扩大影响。日志应说明配置项和判断结果，但不能把整份环境变量连同秘密全部输出。

数值配置也存在类似边界。端口、时间或容量需要类型、范围和单位验证，不能因为字符串可转成一个数字就认为有效。本文聚焦布尔开关，没有验证任何通用解析库，也不提供一套可以不经审查覆盖所有配置的实现。

解析一次并交付明确类型

建议在受控的配置边界完成解析，让业务代码使用已经验证的类型，避免各模块自己解释同一个字符串。有的模块接受大写，有的模块只检查非空，会使同一次部署出现互相矛盾的行为。配置对象及其版本也应可辨认，便于确认运行实例实际采用哪份规则。

修改环境配置后，还需要知道应用何时读取它。启动时快照、请求时读取或额外的动态配置机制，具有不同生效方式。不能仅看到部署平台的值已更新，就推断所有进程立刻改变。具体刷新和重启条件需要查明实际运行环境，本文没有执行这类部署测试。

待执行验收可以覆盖合法开启、合法关闭、缺失、空白、错误拼写和多个运行环境，核对最终类型与功能行为。还要检查错误信息是否足够定位且不含秘密。不要只测试文本 true 成功开启，就认为关闭路径已经可靠。

功能上线后的长期管理可参看功能开关的退出责任。先让输入值变成可解释、可验证的配置，再讨论开关怎样控制业务，才能避免文本 false 带来的相反行为。
