pytest 看不到 INFO 时，怎样判断日志丢在哪一层？

用一个可运行的导入测试区分 logger 门槛、传播和 caplog 阶段。用返回值、批次编号和负对照检验日志归属。

正文

核心要点

  • 同时断言导入结果和可归属的日志记录。
  • 有效级别和向上传播分别影响根捕获。
  • 准备阶段的记录需要按实际阶段查询。

在 pytest 中查不到一条 INFO 日志时，先用独立断言确认业务动作确实完成，再检查发出消息的 logger 是否接纳 INFO，以及记录能否沿传播路径抵达 caplog。调低捕获级别能解决门槛问题。若记录已经在另一条处理路径上结束，继续调低级别也找不到它。

从导入结果回到日志路径

假设一个目录导入函数接收三行，其中两行有内容，业务约定返回接纳行数。测试还要求导入模块记录本次批次编号和接纳数量，方便调查后台任务。返回值与记录分别承担两个承诺。返回值为二能证明这次调用处理了预期输入，批次记录能证明约定的诊断信息进入当前观察点。把两项合并成一句字符串断言，既可能漏掉真正的缺失，也可能被其他模块碰巧发出的同一句话满足。

pytest 日志指南介绍默认日志捕获及 caplog。实际项目可能在配置文件、命令行或 fixture 中改动阈值。定位时先看具体 logger 的有效级别，再看处理器是否收到记录。对于没有显式设级别的命名 logger，有效级别可以沿父级查找。已经由子 logger 接纳的记录在传播时直接交给祖先的处理器，祖先 logger 的级别不会再过滤一次。处理器自己的门槛和过滤条件仍然有作用。Python 3.11 logging 文档

这个区别决定改动位置。如果模块明确要求只生成警告及以上记录，把根 logger 调成 INFO 仍可能观察不到该模块的 INFO。反过来，如果模块允许 INFO，却把传播关闭并将记录写到自己的处理器，单独放宽根处理器的阈值也不改变路径。试验前分别记下来源名称、有效级别、传播设置和预期去向，能够说明哪一处变化真正影响了结果。

一次测试比较三个条件

把下面完整文件保存为 test_import_logging.py。在隔离环境中用 pytest 9.0.2 运行。三个参数分支调用相同函数，先发出一条文案相同的预览日志，再检查导入结果和符合契约的记录数。样本使用无真实数据的批次编号。

import logging

import pytest

logger = logging.getLogger("catalog.importer")
neighbor = logging.getLogger("catalog.preview")


def import_rows(rows):
    accepted = sum(bool(row.strip()) for row in rows)
    logger.info("rows accepted", extra={"batch": "A17", "accepted": accepted})
    return accepted


def is_import_record(record):
    return (
        record.name == logger.name
        and record.levelno == logging.INFO
        and record.getMessage() == "rows accepted"
        and getattr(record, "batch", None) == "A17"
        and getattr(record, "accepted", None) == 2
    )


@pytest.mark.parametrize(
    "level,propagate,count",
    [(logging.WARNING, True, 0), (logging.INFO, False, 0), (logging.INFO, True, 1)],
    ids=["threshold", "route", "captured"],
)
def test_import_capture(caplog, monkeypatch, level, propagate, count):
    monkeypatch.setattr(logger, "propagate", propagate)
    caplog.set_level(logging.INFO, logger=neighbor.name)
    neighbor.info("rows accepted", extra={"batch": "P03", "accepted": 2})
    with caplog.at_level(level, logger=logger.name):
        assert import_rows(["a", "", "b"]) == 2
    assert "rows accepted" in caplog.text
    assert sum(map(is_import_record, caplog.records)) == count

第一组维持 WARNING，导入函数返回二，但目标 INFO 没有越过发出端门槛。第二组允许 INFO，主动关闭目标 logger 的向上传播，返回值相同，根捕获处理器仍然看不到目标记录。第三组同时允许级别和传播，预期只匹配一条导入记录。代码没有在失败组制造虚假的成功业务结果，三个分支都实际调用函数，再独立检验返回值。

这个样本在本地的隔离环境中实际运行，pytest 报告四个测试通过。前三个通过分别代表观察到零条、零条和一条符合条件的记录。第四个覆盖阶段读取。这里的通过只描述这份文件，业务系统的日志配置、异步消费以及外部日志平台需要各自的验证。

三个分支都看得到预览模块的同文案记录。直接搜索 caplog.text，连目标记录确实缺失的两组也会通过。样本改用 logger 名称、级别、格式化消息、批次和行数来识别记录。若实际需求只要求警告代码和任务编号，可以减少断言字段。若重试次数也是契约，应明确记录数量，并把重试触发条件放在测试输入里。时间戳、终端颜色和文件行号通常随着环境或代码移动变化，适合排查时查看，作为稳定断言前需要另外说明依据。

调级应该覆盖哪一段

pytest 的固定版本实现在 at_level 中暂时改变指定 logger 和捕获处理器的级别，退出上下文后恢复。set_level 更适合把级别保持到测试结束。对多个操作连在一起的测试，可以先把调级范围缩到产生目标记录的那一段，再用业务结果和记录归属共同验收。如果同一测试里必须用不同级别观察准备和执行，应分别安排上下文，避免前一处设置使后一处的证据范围发生变化。

应用如果在测试途中替换根 logger 的处理器，pytest 的捕获处理器可能被移除。此时可以在调用前后检查捕获处理器是否仍在预期位置，再根据应用日志初始化的职责决定如何保留它。临时把所有模块调到 DEBUG 会使更多无关记录进入报告，对这种路径变化也无能为力。终端实时日志是另外的输出设置。看到它只能说明对应记录到达了显示端，测试仍要检查实际捕获的记录。如果问题同时涉及直接写标准输出，可沿标准输出与文件描述符的捕获边界另查输出路径。

fixture 明明写了 INFO，为什么在测试体里找不到？

先确认该消息发生在 setup。caplog.records 在测试体里反映 call 阶段。需要在测试体查看先前的准备记录时，可以用 caplog.get_records("setup")。样本的 staging_marker 在 setup 中留下 staging ready，随后测试用两条断言分别检查当前阶段和准备阶段。两条结果一起能识别读错阶段的问题。把这段追加到前面的文件，使用相同命令运行。

@pytest.fixture
def staging_marker(caplog):
    with caplog.at_level(logging.INFO, logger=logger.name):
        logger.info("staging ready")


def test_setup_record(caplog, staging_marker):
    assert not any(r.msg == "staging ready" for r in caplog.records)
    assert any(r.msg == "staging ready" for r in caplog.get_records("setup"))

如果改动把准备动作移进测试体，原有的阶段断言也应随约定调整。

查询过去阶段只会返回当时实际捕获到的记录。测试体随后调低级别，无法补回 fixture 执行时已被过滤的消息。需要检查准备阶段的 INFO 时，可以在产生该消息的 fixture 内设置相应级别，像样本一样把观察条件放在事件之前。记录日志证据时写清产生阶段、预期来源、实际匹配数和业务返回值，下一次遇到空结果就能区分应该改准备时机、传播配置还是断言。
