Git stash后文件还在，哪些内容没有被暂存？

用三份同初态练习仓库比较默认、-u与-a，核对条目身份、部分暂存和恢复冲突，明确本地保存与备份的边界。

正文

核心要点

  • 默认、-u与-a保存和清理的范围不同。
  • 恢复文字不证明原来的暂存划分已恢复。
  • pop冲突保留条目，本地stash不等于跨机器备份。

Git stash 的默认保存不等于整个目录快照。已跟踪修改、未跟踪文件和被忽略文件有不同范围：-u 增加未跟踪文件，-a 还包含忽略文件。临时切换任务前，先核对哪些材料进入哪一个条目，再看工作区还留下什么，不能从部分修改消失推断所有工作已有备份。

文件属于哪一类，先用状态确认

Git stash 官方手册说明保存工作区和索引状态的用途，以及默认、include-untracked 与 all 的区别；后两项还涉及相应工作文件的清理。本文于二〇二六年十一月一日重读在线手册，没有对本站工作区执行 stash、清理或恢复，也没有检查私人文件。

“新文件”不是充分分类。它可能尚未被跟踪，也可能已经 add 进索引，还可能被忽略规则排除。已经跟踪的路径不会因为后来写进 gitignore，就自动变成默认 stash 不处理的忽略材料。gitignore 与跟踪状态解释这个相邻边界，保存前应以真实状态为准。

索引和工作区也要分别看。同一个已跟踪文件，可以有一部分变化已暂存，另一部分仍只在工作区。保存文件内容与恢复原来的暂存划分并非同一验收。若只打开编辑器看到文字回来了，仍不能说明后续提交会包含原先打算提交的那一部分。

用三份独立练习比较保存范围

下面脚本未经执行，只为新临时目录中的三份可丢弃仓库构造同样初态。每份都有已跟踪修改，保证不是只有未跟踪文件却没有可创建条目的场景。所有字符串都是无敏感训练材料；不会连接远端，不对当前工程操作。

demo_root="$(mktemp -d)"
for mode in default untracked all; do
  repo="$demo_root/$mode"
  git init "$repo"
  git -C "$repo" config user.name Training
  git -C "$repo" config user.email training.invalid
  printf 'scratch.tmp\n' > "$repo/.gitignore"
  printf 'base\nmiddle\nbase\n' > "$repo/tracked.txt"
  git -C "$repo" add .gitignore tracked.txt
  git -C "$repo" commit -m initial
  printf 'staged\nmiddle\nbase\n' > "$repo/tracked.txt"
  git -C "$repo" add tracked.txt
  printf 'staged\nmiddle\nunstaged\n' > "$repo/tracked.txt"
  printf 'new training file\n' > "$repo/new.txt"
  printf 'ignored training file\n' > "$repo/scratch.tmp"
  git -C "$repo" status --short --ignored
  case "$mode" in
    default) git -C "$repo" stash push -m scope-default ;;
    untracked) git -C "$repo" stash push -u -m scope-untracked ;;
    all) git -C "$repo" stash push -a -m scope-all ;;
  esac
  stash_oid="$(git -C "$repo" rev-parse 'stash@{0}')"
  printf 'entry %s\n' "$stash_oid"
  git -C "$repo" stash show --include-untracked --stat "$stash_oid"
  git -C "$repo" status --short --ignored
  git -C "$repo" stash apply --index "$stash_oid"
  git -C "$repo" diff --cached -- tracked.txt
  git -C "$repo" diff -- tracked.txt
  git -C "$repo" status --short --ignored
done

纸面预期是默认条目处理已跟踪工作，new.txt 与 scratch.tmp 仍需分别解释；-u 将未跟踪材料纳入，忽略文件仍不因此成为同一范围；-a 则连忽略材料也纳入并清理对应工作文件。实际记录应同时包含保存前状态、条目内容与保存后状态，不能只看最后目录变空了多少。

三份初态独立，避免第一轮清理改变第二轮材料。每份保存后先解析条目对象身份，再检查并 apply；这样后续插入新条目时，不会继续盲目相信 stash@{0} 还是原来的对象。示例没有输出回执，这些差异仍须由真实练习确认，不是本机已完成的测试。

什么时候不应该选择全部包含？

忽略文件可能是缓存、依赖、大型中间产物，也可能包含本地凭据。把 -a 当成最完整也最安全的默认，会把原本不适合进入版本对象存储的材料一起保存。应先清点允许内容，必要时选择明确路径或另行管理数据，而不是为了获得干净工作区无差别纳入。

反过来，默认不包含未跟踪文件也不意味着它们不重要。刚新增的接口样本、设计说明或尚未 add 的代码，可能正是当前任务不可缺少的一部分。清理前应确认它们的去向；不能因为命令没有报错，就在随后切换分支时把残留文件当作可随手删除的垃圾。

选择范围还要考虑恢复地点。一个条目可能依赖当时的基线、目录结构与应用约束，后来分支虽然能接受文本补丁，业务含义仍可能冲突。为准备长期交接的工作，明确分支、提交或其他受控保存方式通常比只留一条无说明 stash 更容易审查；具体选择仍要考虑秘密和权限。

apply --index之后，应该检查什么？

脚本选择 apply，让条目继续保留，再检查工作文件与已暂存差异。--index 表达尝试恢复索引的意图，不是对所有冲突现场的成功保证。实际恢复前若已有其他工作，应先辨认当前变化，避免把两份内容混到一起后再问哪一份被覆盖。

对示例的 tracked.txt，可以分别比对 cached 差异与普通工作区差异，确认阶段划分；对 new.txt 和 scratch.tmp，要按本轮保存范围解释它们来自条目还是一直留在工作区。相同文件名重新出现，不一定证明它曾被保存，可能从来没有离开过。这个对照能发现只看最终内容无法发现的假阳性。

恢复完成还应做正常构建与行为检查。Git 应用补丁成功，只回答文本和索引处理的结果；它不证明新分支的接口、依赖或运行配置都兼容。临时保存的目的在于保留工作，不是给未审查变更提供免验通道。

Git stash pop遇到冲突，条目会自动删掉吗？

官方手册说明，pop 应用失败产生冲突时不会从列表移除条目，需要手动处理冲突后再明确决定删除。不要看到失败就重复 pop，也不要为了让流程继续而直接重置当前工作。先记录条目对象身份与工作区状态，确认哪些内容已进入冲突现场，再选择恢复步骤。

没有冲突而正常 pop 的删除行为，又与 apply 保留条目不同。使用前先决定是否希望恢复后立即从列表移除，不能只因两个命令都能把文字带回来就互换。删除条目前应确认需要保留的材料和暂存状态已经验收，尤其是含未跟踪内容的情况。

stash 仍是本地工作流，不会自动变成跨机器备份。机器损坏、仓库删除或访问权限变化的恢复要求，需要额外存储方案；工作区干净也不能撤销已经暴露的凭据。本文没有执行任何恢复或删除，没有数据安全通过的结论。离开任务之前，能说明保存范围、条目身份、恢复条件与未保存材料，比一次无报错的 stash 更能保护工作。
