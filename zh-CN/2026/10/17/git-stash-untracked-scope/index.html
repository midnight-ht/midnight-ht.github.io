git stash 后文件还在，哪些内容没有被暂存？

stash 的跟踪、未跟踪和忽略范围不同；清理前核对条目，恢复时保留索引与冲突证据。

正文

git stash 的默认范围、包含未跟踪文件和包含忽略文件是不同选择，应先核对范围再执行清理与恢复。看到部分修改消失，不代表工作区中所有重要内容都已保存；临时切换任务之前，需要知道哪些文件进入了哪一个条目。

跟踪状态决定保存范围

Git stash 手册介绍保存工作区与索引状态的用途，并区分相关选项：--include-untracked 包含未跟踪文件，--all 还包含忽略文件；这些选项也涉及随后清理对应工作区文件。默认行为不能被当作完整目录快照。具体使用前应查看实际 Git 版本、状态和选项，不宜根据一次视觉变化推断范围。

假设开发者新增了一个尚未跟踪的配置样本，同时修改已有代码，然后默认保存临时工作并切换分支。新增文件可能仍留在工作区，或后来被误当作无关文件处理。这是未执行的示例，不是当前仓库操作记录。问题在于保存范围没有被确认，而不是 stash 自动知道哪些文件对人重要。

清理之前检查条目身份

临时保存以后，应记录可辨认的条目身份和用途，并在需要时查看其中实际包含什么。多个任务积累的条目如果都只依赖相对序号，后来插入新条目就可能让人选错对象。恢复操作应以实际条目和内容为依据，不能只凭“上一次大概在这里”的记忆。

索引状态与工作区内容也不是完全相同的责任。部分暂存、恢复索引和恢复文件可能受到冲突影响，操作前要知道希望恢复到什么状态。不要把“文件内容看起来回来了”当作暂存范围、分支关系和测试条件都已恢复的证明。

包括忽略文件时尤其需要谨慎。忽略目录可能含有依赖、缓存、大文件或本地秘密，不能因为它们不在常规提交里，就假设适合一起保存。本文没有执行 stash、清理或恢复，也没有检查任何私密文件；这是提醒使用者先清点范围，而非建议无差别加入所有内容。

临时保存不替代长期备份

stash 是本地工作流程的一部分，不应直接视为已经上传的备份。团队交接、跨机器恢复或长期保留，需要明确的存储与权限方案。对于秘密泄露，临时移走文件也不等于撤销凭据或清除历史；应按实际问题采用对应处理，而不是把工作区干净当作事件结束。

待执行验收可以在可丢弃的练习仓库中安排已跟踪修改、未跟踪文件、忽略文件和部分暂存，再比较不同选项的条目及恢复结果。遇到冲突时，应保留当前工作并依据状态处理，不能为了继续流程直接重置覆盖。本文没有运行这套练习，也没有提供成功日志。

恢复后还应核对分支、文件范围和必要构建条件。一个条目创建于旧版本代码，应用到新版本时可能产生语义冲突，即使文本合并没有报错，也需要正常审查。临时保存的目的在于保留工作，不是绕过变更验收。

与忽略规则的另一种差异，可参看gitignore 与跟踪状态。先明确哪些内容已保存、保存在哪里、怎样恢复，再离开当前任务，才能避免把局部成功误当作完整保障。
