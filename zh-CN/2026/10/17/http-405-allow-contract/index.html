收到 HTTP 405，应该修改方法还是检查目标资源？

用完整本地服务与请求矩阵定位资源和方法差异，分开授权、代理入口、跳转与可缓存旧错误，不以 GET 成功替代写入。

正文

核心要点

  • 405 指向目标资源不支持已知方法，源站须返回 Allow。
  • 资源方法能力不能替代当前调用者授权。
  • 成功 GET、路由触达与原业务写入是不同结果。

收到 HTTP 405，应先核对目标资源与请求方法的配对，再结合 Allow 和真实路由判断如何修复。405 表示源站认识这个方法，但该目标资源不支持它；把写请求换成能返回成功的 GET，可能根本没有完成原任务。资源支持哪些方法，与当前身份获准做什么，也必须分别检查。

405 指向资源，不是整个服务器的方法清单

RFC 9110 的 405 定义要求源站在该响应中生成 Allow，列出目标资源当前支持的方法。本文于二〇二六年十月三十一日核对二〇二二年六月发布的 RFC 9110；下面的服务与请求都是未执行的教学示例。

假设订单集合 /orders 允许列举和新建，单条订单 /orders/7 才支持修改。客户端方法名称可能正确，资源地址却选错。另一种情况是网关没有为该方法配置相同路由，应用根本没有收到请求。看到 405 不能直接断言业务代码已经执行，更不能因此重复创建一笔订单来验证。

整个源站不认识或未实现方法，与某个目标不支持已知方法，是不同判断；不要把所有不接受的输入都塞进同一个 405 分支。身份验证和授权也有独立语义，不能用 Allow 替代。具体系统可能不愿暴露资源是否存在，诊断时要按真实安全政策解释响应，而不是要求每次无权限都透露同样的信息。

用一个完整的小服务核对方法与目标

下面的 Python 标准库程序只监听本机，返回固定教学数据。它没有真实订单写入、账户鉴权或生产级服务能力；PATCH 仅返回已接受教学动作的固定说明，不宣称实际修改。保存为 method_demo.py 后可运行，本文没有执行，也没有生成实际成功回执。

import json
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer


class Handler(BaseHTTPRequestHandler):
    def respond(self):
        status, payload, allow = 200, {'id': 7, 'state': 'teaching fixture'}, None
        if self.path != '/orders/7':
            status, payload = 404, {'error': 'unknown teaching resource'}
        elif self.command == 'PUT':
            status, payload, allow = 405, {'error': 'method unsupported here'}, 'GET, PATCH'
        elif self.command == 'PATCH':
            payload = {'demo': 'PATCH route reached; no order was changed'}
        data = json.dumps(payload).encode('utf-8')
        headers = {
            'Content-Type': 'application/json; charset=utf-8',
            'Content-Length': str(len(data)),
            'Cache-Control': 'no-store',
        }
        if allow is not None:
            headers['Allow'] = allow
        self.send_response(status)
        for name, value in headers.items():
            self.send_header(name, value)
        self.end_headers()
        self.wfile.write(data)

    do_GET = respond
    do_PATCH = respond
    do_PUT = respond


if __name__ == '__main__':
    with ThreadingHTTPServer(('localhost', 8765), Handler) as server:
        server.serve_forever()

用另一个终端分别发送这组无正文请求：

base=http://localhost:8765
curl -i "$base/orders/7"
curl -i -X PATCH "$base/orders/7"
curl -i -X PUT "$base/orders/7"
curl -i -X PUT "$base/orders/8"

代码预期前两项进入各自支持的分支，第三项返回 405 并带 GET、PATCH 的 Allow，第四项因目标不同进入 404。这个矩阵把方法差异与资源差异分开；它不覆盖所有 HTTP 方法，未定义的方法仍由标准库处理，不能据此宣布服务具有完整路由合同。测试完成后在服务终端结束程序，确认端口不再由该教学进程占用。

示例刻意不接收真实订单内容，也不提供一个随意接受 JSON 后假装保存成功的处理器。若要验证业务修改，必须另接测试持久层、校验及授权，并在请求后重新读取状态。只看到 PATCH 路由被调用，不应写成订单已更新；这是接口修复最容易越过的证据边界。

Allow 里有 DELETE，就可以让用户删除吗？

不能。Allow 描述资源能力，不是该身份的权限清单。客户端可以用它辅助诊断，却不能因为列表包含 DELETE 就绕过后端授权；隐藏按钮同样不能替代服务端校验。若资源能力随状态改变，还要解释列表对应哪个时点，避免把以前的响应当成永久承诺。

RFC 9110 的 Allow 字段说明还规定代理不得修改这个字段。实际排查仍应捕获入口响应与直连应用响应，确认错误由哪里生成；规范要求不能代替真实部署证据。发现缺少 Allow，应记录为待定位的符合性或中间层问题，而不是自动推断“没有方法可用”。

对授权的验证要另设身份：拥有权限、没有权限、失效凭据与不存在资源各自有预期。上面的教学服务没有身份系统，所以不能声称它已经验证这些路径。真实测试须使用受控账户与独立资源，日志保留必要方法、脱敏目标、请求身份和响应头，不把令牌贴进公开错误报告。

换成 GET 以后能返回数据，算修好吗？

只能说明读取路径有响应。原来要修改记录，却换成读取，业务动作已经改变。客户端应根据接口当前版本确认目标与正确方法，服务器应确认同一入口确实转发该方法；不能以所有请求最终出现一个成功对象作为标准。

重定向也会让最终方法或目标偏离最初请求，应检查完整链条，而不是只盯着最后一个状态。本站HTTP 跳转中的方法契约解释相关差别。修复时分别保存原始请求、跳转后的请求和应用入口所见内容，才能判断该改客户端、路由还是重定向配置。

路由改好了，为什么仍会收到旧的 405？

405 具有启发式可缓存性，但是否真的被缓存，还受方法定义与显式缓存控制影响。不能看到重复响应就断言一定是缓存，也不能默认错误响应从不被缓存。核对实际响应的缓存信息、目标 URL 与入口，再用受控方式比较缓存路径和源站路径。

示例显式给出 no-store，是为了让教学错误响应不承担持久缓存用途，并不替读者决定生产接口策略。临时绕过缓存只是一项定位手段；持续修复应让部署配置和客户端行为符合真实资源能力。还要检查旧客户端、大小写和路径规范化是否进入同一资源，避免表面相似的两个目标被混成一个问题。

同一修复还应检查返回值的业务含义。若入口把所有方法错误统一转成 HTTP 二百和一个空对象，客户端可能继续执行后续支付或刷新，把没有发生的更新当成成功。错误映射需要保留原操作未完成这一事实；用户输入也应保留，方便改正目标或方法后重新提交，而不是错误后清空表单再要求重填。

团队可以把每个回归用例写成三列：请求意图、预期路由响应、预期存储结果。不支持写入方法时，响应应能解释拒绝，存储不应出现相应修改；获准的正确请求则需独立确认提交。这个表让前端、网关和后端在同一任务上核对各自责任，避免其中一层返回绿色，另一层却没有执行原动作。

拟议回归分别验证正确方法、不支持方法、错误资源、无权限身份、入口转发、重定向及旧响应缓存，并核对真实业务状态。本篇没有运行这些用例。完成记录应能证明原任务在正确资源上由获准身份执行，且不支持方法仍给出合适错误；否则只消除了 405，尚未解释原操作的结果。
