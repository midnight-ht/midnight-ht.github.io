收到 HTTP 405，应该修改方法还是检查目标资源？

405 表示目标资源不支持该方法；结合 Allow、实际路由和入口排查，资源能力不等于用户权限。

正文

HTTP 405 指向目标资源不支持该方法，应结合 Allow 和实际路由定位，而不是盲目换成 GET。排查对象应是“这个资源接收这个方法吗”，而不只是“服务器是否在线”。方法被改动，还可能改变请求原本的业务含义。

方法与目标共同构成契约

RFC 9110 第十五节说明，405 表示源站知道该方法，但目标资源不支持；源站必须在该响应中生成 Allow 字段，列出目标资源当前支持的方法。这个定义不同于整个服务器不认识或没有实现方法的情况。收到某个实际响应时，还应确认由哪一层产生，不能仅根据状态码推断应用代码一定已经执行。

假设客户端对订单集合发出修改请求，而真正支持修改的是单条订单地址。即使方法名称本身合法，资源选择仍可能错误。另一个可能是网关路由没有转发预期方法。这些都是未执行的假设，不是某个产品必然如此的结论；诊断需要请求地址、方法、入口和服务配置共同作证。

Allow 不是当前用户的权限清单

字段列出了资源支持的方法，不等于当前身份获准执行所有这些方法。资源能力与身份授权属于不同判断。客户端可以据此帮助定位契约差异，但不能把支持 DELETE 理解为任何用户都可删除，也不应隐藏按钮后就认为后端权限已经落实。

同样，缺少预期 Allow 可能说明响应不符合相关契约，或由中间层生成；它不是足以自动选择替代方法的信号。把所有失败统一重试成 GET，可能把原本的写入意图变成读取，也可能让敏感参数进入地址。修复应该说明为什么目标方法正确，而不是只追求返回成功状态。

排查记录应保留实际方法、规范化后仍可识别的目标、响应状态和必要头部，以及业务任务身份。不要为了复现把令牌或完整个人信息贴进公开日志。对于重定向链，也要确认最终看到的请求是否仍是原先的方法和目标，避免在错误的环节反复改接口。

回归检查应经过真实入口

建议分别验证受支持的方法、不支持的方法、错误资源地址和无权限身份，并观察应用与入口层的行为差异。若接口文档、客户端生成代码和实际路由来自不同版本，还需核对它们是否在讨论同一份契约。本文没有执行这些请求，没有可报告的接口成功结果。

修复服务配置后，应检查旧客户端会怎样表现，以及错误响应是否仍能提供足够诊断。不要把所有不匹配都改成成功对象，否则调用者可能在没有执行原操作时继续下一步。响应内容可以帮助解释问题，但不能虚构已经完成的业务状态。

有些问题实际发生在跳转后方法改变，另一些是资源自身不支持；二者应分开定位。可参看HTTP 跳转中的方法契约。先确认资源与方法匹配，再独立完成权限与业务验收，才能解释 405 的真正修复范围。
