HTTPS 报表页会把哪些地址信息放进 Referer？

同一个报表地址分别打开三个接收入口，核对来源头的路径、查询和源，以及如何判断请求是否真的抵达。

正文

核心要点

  • 同源短地址通常保留路径和查询。
  • 可信跨源导航通常只发送源。
  • 降级用例先确认 HTTP 请求已抵达。

在 strict-origin-when-cross-origin 策略下，HTTPS 报表页向同源地址导航时，接收方仍可在 Referer 中看到报表路径和查询。同一页面向另一个 HTTPS 源导航时，通常只发送源。把同源、可信跨源和安全降级放进同一组验收，能看出哪些字段由策略保留。

假设报表产品要为客户保留从帮助页返回原视图的能力，也要让合作方知道用户来自哪个产品。团队看到两个链接都采用 HTTPS，就把接收方能看到的来源信息写成同一个结论。这个验收条件缺少一项输入：两个链接相对于报表页分别属于什么源。若同源帮助页只需要返回报表入口，收到具体报表编号可能已经超出了它的用途。

固定报表地址，改变接收方

W3C Referrer Policy 编辑草案将这项策略列为默认值。在短地址、浏览器没有进一步限制来源、也没有元素或重定向覆盖策略的条件下，同源请求使用剥离后的来源地址。跨源且目的地址可信时使用来源的源。由可信来源前往不可信地址时，策略不发送来源头。浏览器可因用户设置等原因减少披露，所以这组预期需要和实际浏览器观察对照。

准备一个假设报表页 https://reports.example.test/monthly?case=DEMO-42#chart。在这个页面的响应上明确设置该策略。用三个普通链接分别打开受控接收入口，每次先回到原报表，再发起下一次导航。这里使用保留的示例地址和合成编号，只描述可迁移的测试设计。需要由团队在自己的测试环境配置接收端和证书。本文未运行浏览器，也未向这些地址发送请求。

把报表页的源记为 R，把支持站和旧站记为 S 与 L。支持站使用同一上级域下的另一主机，旧站使用不可信的普通 HTTP 地址。三个入口都用相同的采集路径。这样一眼就能看出请求目标的关系，接收值则以可比较的字段列出。

接收入口 接收请求中的来源头预期
R 的采集入口 R 加报表路径和合成查询，缺少片段
S 的采集入口 R 的序列化值，带根路径斜杠
L 的采集入口 缺失，前提是确实发出了对不可信地址的 HTTP 请求

第一行的控制点是报表编号仍出现，页面片段已经被剥离。来源 URL 剥离算法对来源地址去掉片段和用户信息；只取源时还会去掉路径和查询。第二行特意使用同一个上级域下的不同主机。判断是否同源要比较协议、主机和端口，共享上级域并不能让两个主机成为同源。若帮助入口后来换到不同主机，应重新验收它收到的值。

第三行最容易被误读。浏览器可能把旧入口升级成 HTTPS，也可能拦截导航。若接收端没有收到请求，先记录尚未观测到，再根据浏览器网络面板判断是未发出、被升级还是发生其他错误。只有接收方确实收到那次 HTTP 请求，才可以根据它读到的字段判断该行策略结果。否则，一个配置错误、证书失败或网络超时也可能让日志里找不到来源值。

用接收记录排除观测问题

给每个接收入口一份相同格式的简短记录。保存用例编号、接收协议、接收主机，以及来源头是否存在和其值。测试编号可放在受控接收入口的路径中，用来把浏览器面板和服务端记录对齐。对照项只需比对预先约定的合成字段，别把整页请求、登录状态和用户地址复制到共享缺陷单。若代理会删改头部，分别在边缘和最终应用侧看一次，以确认字段消失的位置。

先执行同源正对照。如果三行全部读不到来源，不能仅据此判定每条策略都严格生效。浏览器偏好、接收日志的过滤和代理改写，都可能得到同样的观察。应先确认同源请求确实抵达，并用浏览器网络面板判断头部是在发送之前就缺失，还是离开浏览器后被清除。隔离变量之后，才比较跨源结果与原先的归因需求。

再故意让一个合成编号出现在目标地址的查询中，同时把来源头限制为不发送。接收应用仍可以从目标 URL 读取这个编号。这是另一条数据路径。它解释了为什么验收不能只检查头部。在真实设计中，若标识无需出现在浏览器地址里，应改成服务端持有或重新设计传递方式。授权仍应核对当前主体是否可读该报表。来源头存在或缺失都不能为访问提供权限。关于诊断产物如何控制保留范围，可以参看保留证据而不扩散秘密。

根据用途决定收件人能看什么

如果合作方只按来源产品归因，先检查它能否使用源级信息。若站内帮助页只负责返回报表首页，可以改成明确的返回入口，避免从来源地址解析当前报表。如果站内和可信的跨源接收方都只需要源，可以评估 strict-origin。假如报表页不允许任何导航携带来源，则评估 no-referrer，并先用同一组用例核对既有功能是否依赖这个字段。策略负责控制这一种浏览器生成的头，不能替代对目标地址和日志的检查。

发布时记录实际策略来自哪层。一个代理可能添加响应头，页面可能有文档内声明，链接也可能自带属性。把接收端可见的输出写入验收条件后，开发者才能在改造任一层时验证是否改变了原来的数据承诺。

能只让一个同源链接不发送来源吗？

可以。若报表页的其他同源导航需要维持当前行为，可给那个普通超链接设置 referrerpolicy="no-referrer"。HTML 的超链接来源策略算法将该属性用于跟随这个链接。验证时保留同一页面上指向同一受控入口的普通链接作为对照，让两个请求只在链接属性上有差别。若应用将点击接管后改用其他请求方式，应核对实际发起的请求，不将原属性当作已验收结果。该补充用例也未执行。
