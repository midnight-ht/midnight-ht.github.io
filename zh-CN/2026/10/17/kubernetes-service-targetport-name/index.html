Kubernetes Service 入口不变，新旧 Pod 怎样使用不同目标端口

用旧新 Pod 双端口示例解释稳定 Service 入口、命名 targetPort 和全部 EndpointSlice 的分层验证。

正文

核心要点

  • 稳定入口可以通过同名目标映射不同后端数字。
  • Service 端口名与 Pod 端口引用分属字段。
  • 全部端点切片、实际监听和两组请求应分别核对。

Kubernetes Service 可以把固定 port 映射到命名 targetPort；新旧 Pod 在各自容器端口上保留同一名称时，可以使用不同数字。前提是名称解析、选择器与实际监听都一致，端口声明不会替应用打开监听。修改服务入口，也不会自动改变应用进程的启动配置。

让稳定入口与后端数字各有责任

Kubernetes Service 文档说明，Service 可把入口 port 映射到 targetPort；省略 targetPort 时默认使用 port 的值。Pod 端口可以命名，Service 用字符串引用该名称。文档明确允许同名、同协议的后端使用不同数字，这为逐步更换应用监听端口提供了空间。

本篇依据二〇二六年十一月五日核对的当前官方页面。页面导航出现的版本号不作为集群版本证明。下文没有创建集群、部署清单或执行请求，数字和对象名称是教学输入。

假设客户端始终访问 report-service 的八十端口，旧应用监听八〇八〇，新应用改为九〇九〇。客户端没有理由跟着内部实现变更访问地址；要保持这一点，Service 的入口不改，targetPort 使用稳定名称 web。旧 Pod 把 web 解释成八〇八〇，新 Pod 则把它解释成九〇九〇，而各自应用确实监听相应数字。

一份 Service，对应两组端口声明

以下 Service 片段选中标签 app=report 的 Pod，协议使用 TCP。它只表达服务与后端的关系，未提供完整工作负载、镜像和运行配置，不能直接作为可运行部署教程。

apiVersion: v1
kind: Service
metadata:
  name: report-service
spec:
  selector:
    app: report
  ports:
    - name: public-http
      protocol: TCP
      port: 80
      targetPort: web

旧、新工作负载容器分别具有下面的字段。两个片段不能合并成一个同时声明两个同名端口的容器，它们是滚动过程中不同 Pod 的定义。应用启动参数也应分别配置真实监听八〇八〇和九〇九〇；containerPort 是描述和引用的一部分，不负责启动监听程序。

# old Pod container fragment
ports:
  - name: web
    containerPort: 8080
    protocol: TCP

# new Pod container fragment
ports:
  - name: web
    containerPort: 9090
    protocol: TCP

这组输入的预期关系很具体：Service 接收八十端口流量，旧组目标是八〇八〇，新组目标是九〇九〇。只把 Service port 改为九〇九〇，既改变了客户端入口，也没有表达两组后端各自数字。若 targetPort 省略，其默认值又会跟随入口，这和本例想要的稳定名称迁移完全不同。

判断选择器时也要看实际对象。两组都标 app=report 才进入本例候选范围；没有匹配标签，正确的 targetPort 名称也找不到应连接的 Pod。反过来，标签匹配不能证明名为 web 的端口存在。两条关系各有输入，不能用“选中了几个副本”替代端口解析检查。

为什么不能只看一个 EndpointSlice

EndpointSlices 官方文档说明，使用命名端口时，同名端口可能在不同 Pod 对应不同数字，需要不同的 EndpointSlice。因而检查一片只看到八〇八〇，并不能直接断言新组九〇九〇没有生效；应枚举关联这个 Service 的全部切片，再按端点身份关联旧、新 Pod。

一个候选只读检查路径是先读取 Service 的实际 selector、port、targetPort，再列出匹配 Pod 的标签、端口名和就绪条件，随后读取带 kubernetes.io/service-name=report-service 标签的所有 EndpointSlice。这里列出要核对的字段，而没有伪造 kubectl 输出或某个集群的地址。

切片中的目标端口说明控制面如何表达后端，不代表网络路径已经验证。还需在允许的环境核对进程实际监听，并对旧、新两组分别发起请求，辨认响应版本和内容。通过稳定 Service 连通一次，可能碰巧只命中旧组，不能证明新组也能服务。采样次数再多，若没有后端身份，也难解释覆盖了谁。

两个 name 必须相同吗？

Service 端口条目的 name 与 targetPort 引用的 Pod 端口名不是同一个角色。本例 public-http 标识服务端口条目，web 才是要解析的后端端口名称；二者不需要为了排版整齐写成相同字符串。真正要保持的是 targetPort 字符串与各 Pod 目标端口名、协议及监听数字的对应。

如果新组把端口名改成 http，而 Service 仍引用 web，即使 containerPort 数字正确，也破坏了名称契约。反例的修复应针对名字与引用关系，而不是盲目扩大选择器。扩大范围还可能纳入另一个应用，把本来的名称问题变成错误路由问题。

声明九〇九〇，进程仍监听八〇八〇怎么办？

应修正应用启动配置与声明的分歧，再验证实际监听。只改 containerPort 不会让进程自动打开另一个 socket；一个整齐的 YAML 不能代替进程证据。还要确认应用绑定地址与访问路径符合环境，避免在端口数字正确后，仍因其他网络条件无法到达。

还可以把失败定位写成明确分支：若新组没有对应目标，先查名称与选择范围；若已有九〇九〇目标却连接失败，再核对新进程监听和网络路径；若连接成功但内容版本错误，检查响应身份与应用行为。不要在三种分支中统一修改 Service 的入口数字，否则会同时改变客户端契约，却未必触及真正原因。

教学验收可以逐项设置名称不匹配、进程未监听、没有选择器匹配和正常响应四个输入。先保存 Service、两组 Pod 和全部相关切片的状态及观察时间，再看实际连接结果。对象状态并非跨组件同时更新，不能把不同时点的快照拼成一个原子结论。故障修改只在自有隔离环境执行，并准备恢复原清单与应用参数。

就绪条件与退出阶段还会影响哪些端点被使用。二〇二六年十月二十四日的EndpointSlice 退出状态文章解释 ready、serving 与 terminating，包含特殊配置例外；本题不把那些状态简化为“切片有地址就可达”。命名端口解析正确，是请求路径中的一步，不是所有发布验收的终点。

当需求只是内部数字变化，保留稳定入口与名称契约能让客户端不必迁移；若外部入口确实需要改变，就应另设兼容与通知计划。先确认变的是哪一层，再分别验收入口、目标解析和真实监听，才能知道流量究竟停在哪里。
