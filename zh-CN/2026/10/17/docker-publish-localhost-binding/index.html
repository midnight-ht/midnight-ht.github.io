Docker 发布端口后，为什么其他机器也能访问？

发布端口需核对绑定、地址族、路由和版本；保留 28.0.0 前 localhost 发布的二层网络例外。

正文

发布端口的宿主机绑定地址决定重要的可达范围，但版本、路由与防火墙条件仍需一起检查。Docker 的发布端口不能被简单理解成“只在这台机器上试用”；没有明确限制时，其他机器也可能通过宿主机入口访问服务。

发布行为与应用监听分开核对

Docker Engine 的端口发布文档提醒，发布端口会把服务暴露到宿主机网络地址；指定 localhost 地址可限制常见的发布入口，但版本早于 28.0.0 时，同一二层网络中的主机仍可能到达发布到 localhost 的端口。文档还讨论直接路由等路径，因此不能把某个绑定设置解释成不依赖环境的绝对隔离。以下围绕其常见桥接网络发布路径，其他网络模式需要单独核对。

假设开发者为本地管理界面发布了一个端口，认为没有配置公网域名就没人能访问。这是未执行的假设分析。域名与网络可达性不是同一件事；排查需要确认实际绑定、宿主机地址、路由和外层规则，而不是只看浏览器用哪个地址打开。

明确需要谁能访问

需求若只是宿主机本地使用，应检查发布地址和 Docker 版本，并在实际网络中验证限制。若需要其他机器访问，则应明确授权人群、认证方式和入口防护。不要为解决一次连接失败就临时扩大到所有接口，再把临时状态当作长期配置留下。

IPv4 与 IPv6 也应纳入清点。测试一个地址族不可达，并不能自动证明另一个地址族具有相同结果。具体映射还与网络模式和配置有关，本文没有给出适用于所有 Docker 环境的统一命令，也没有修改本机网络或启动容器。

还应区分应用在容器内部的监听与宿主机发布。应用没有在正确接口监听，可能造成连接失败；发布范围过宽，则可能造成不需要的暴露。两种问题的修复方向不同。把每个失败都归为防火墙，或者把每个成功都当作权限正确，都缺少必要证据。

从预期访问者和非预期位置验收

建议先列出允许访问路径，再从合适的本地和远程位置检查端口可达性及应用认证。远程检查需要在授权网络进行，使用不含敏感数据的测试入口；本文没有执行端口探测，也没有获得任何生产暴露结果。观察应记录地址族、版本和访问位置。

可达与可用也需要分开。连接建立后，页面是否要求正确身份、敏感操作是否受保护，仍是应用层责任；外层规则也不能代替应用授权。对于确实不应公开的管理服务，应以明确的多层控制与维护责任设计，而不是依赖没人知道端口号。

变更时保留原配置、预期范围和恢复方式。部署工具重新创建容器后，发布设置可能回到配置文件定义的值，因此手工修改一次并不能证明后续发布持续有效。应把期望纳入受版本管理的交付配置，并确认运行实例实际采用它。

容器日志配置也存在默认与实例的差异，可参看已有容器的实际配置。把暴露范围落实到真实网络路径，并保留旧版本例外，才能准确说明谁可以访问发布端口。
