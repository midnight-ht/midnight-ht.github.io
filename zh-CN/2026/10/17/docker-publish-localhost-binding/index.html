Docker只发布到localhost，还应检查哪些访问路径？

用明确回环与未指定绑定的声明，核对旧版本二层例外、双栈和路由模式，再区分既有实例、默认创建配置、Swarm与应用授权。

正文

核心要点

  • 本机可用不证明其他位置被拒，绑定解释需带版本与网络模式。
  • IPv4与IPv6路径以及NAT、routed模式分别检查。
  • 更改默认值不替所有运行实例或Swarm自动完成范围修复。

Docker 发布端口时，宿主绑定地址影响谁能从常见入口连接，但不能脱离网络模式、地址族和版本解释。只在本机打开页面，不证明其他位置不能访问；把端口绑定到 localhost，也不能删除旧版本和直接路由的适用条件。应先列出允许访问范围，再沿真实路径验证。

宿主入口不是容器进程的监听配置

Docker Engine 端口发布指南说明，桥接网络的端口发布通过宿主地址映射到容器端口；没有指定宿主地址时，默认发布范围包括宿主的所有地址。本文于二〇二六年十月三十日重新核对当前文档，没有运行容器或进行远程探测。

宿主机端口、容器端口和应用监听是三件相关但不同的事。应用若只监听容器内部不适合该访问路径的接口，发布配置存在也可能连不上；宿主绑定过宽，则可能让不该到达的来访者先到达应用。前者需要查进程配置，后者需要收紧暴露范围，不能用同一个“放开防火墙”同时处理。

域名也没有替这些层作决定。管理页面没有公网域名，其他机器仍可能通过宿主地址连接。认证另有独立责任：端口可达不意味着用户获准执行敏感操作，绑定较窄也不免除应用身份与对象权限。不能把“别人应该不知道端口号”当作可验证控制。

比较两种桥接发布声明

设想一个只供宿主机管理员使用的测试服务，镜像内应用已经按所需接口监听八〇端口。以下命令只用于纸面比较，IMAGE 需要替换为经过选择的测试镜像；没有在本机执行，也没有声称服务已经存在。

# Bind the ordinary published IPv4 entrance to loopback.
docker run --name local-demo -p 127.0.0.1:8080:80 IMAGE
# Omit the host address: a different exposure intention.
docker run --name broad-demo -p 8081:80 IMAGE

第一份明确限制常见 IPv4 发布入口到宿主回环地址，第二份没有限制宿主地址。它们用了不同容器名与宿主端口，避免在教学比较时争用同一个绑定；实际对照还应固定镜像和网络配置。比较的重点是绑定范围，而不是哪个浏览器 URL 看起来更像本地。

官方保留一项版本例外：早于 Docker 二十八点零的版本，同一二层网段里的主机可能到达发布到 localhost 的端口。不能把这个条件删掉，再将回环绑定描述为所有版本的绝对隔离。需要记录实际 Engine 版本及访问位置；没有授权网络中的对照，就只保留预期，不写远程已被阻断。

IPv6 也要单独检查。一个 IPv4 回环入口测试不能自动证明 IPv6 的映射与路由范围；同一运行配置中可能有不同地址族行为。先读取实际网络与端口映射，再决定从哪些地址测试。不要把一张只显示一行 IPv4 的截图当成完整双栈清单。

为什么绑定之外还要看路由模式？

文档讨论 bridge 的 nat 与 routed 等网关模式。直接路由路径的访问可能面向容器地址，而不是相同宿主端口；在相应路由模式下，宿主端口字段的作用也不同。因此本地绑定分析必须说明采用哪种模式，不能把普通 NAT 发布例子套成全部网络模式的承诺。

例如文档给出 IPv6 routed 与 IPv4 NAT 混合的例子：一个地址族走容器地址与发布的容器端口，另一个走宿主端口映射。若只扫描宿主的某个 IPv6 端口没有结果，并不能由此排除面向容器地址的另一条路径。这里解释路径差别，不给任何现网可达结论，也没有执行地址扫描。

如果产品只允许宿主本地使用，应选择能表达这一范围的网络与发布设置，并用实际路径验证。若确实需要受控远程访问，则要把访问身份、入口控制和应用授权一起写成需求，不要为一次连接失败临时绑定所有地址后就遗忘。网络策略改变后，保留原配置和恢复方式，让变更能够追踪。

改默认绑定，会自动修好已有容器和 Swarm 服务吗？

不能把默认创建配置当作对全部运行实例的追溯修改。应读取已有容器实际映射，并让后续创建或重建明确采用预期设置。手工启动参数、Compose 文件和网络默认值可能来自不同位置；改一处并不证明所有入口都已经统一。原实例仍有哪些绑定，需要实际检查，本文没有修改任何运行对象。

官方还明确指出，默认绑定地址设置不影响 Swarm 服务，Swarm 服务仍有自身暴露规则。若系统同时使用独立容器与 Swarm，就不能用一次 daemon 默认值更改宣布全部服务已变成本地入口。需要按各自机制列清对象，分别设计和验收范围。

这个问题也影响后续发布。今天手工以回环绑定启动，明天部署工具按仓库配置重新创建，可能重新回到更宽范围。应把意图放进持续维护的交付配置，再核对实际实例。本站既有容器与日志驱动默认值讨论另一种默认与实例之差，本题要检查的是端口与网络路径。

拟议验收先在授权隔离环境确认服务监听与允许路径可用，再从本机、适当同网段位置及其他规定位置，分别按地址族检查允许与拒绝。记录镜像、Engine、网络模式、宿主绑定和目标地址；测试只使用无敏感数据的入口。连接通过后另查认证与受限操作，不把一次 HTTP 返回扩大成访问权限全部正确。

拒绝路径也应排除服务根本没启动、地址写错或外部网络断开的假阳性。用同一允许路径先证明服务工作，再改变被检验的来源与绑定条件，才能把失败解释到范围限制。本文没有完成这些检查，也没有生产暴露或隔离验收回执。让允许范围、实际路由与应用授权逐层有证据，比一条看似本地的启动命令更可靠。

配置持久性还可以用一次受控重建检查。先读取当前映射，再让测试部署工具按已保存配置重新创建同一个服务意图，检查绑定是否仍符合预期。如果只有手工启动的容器受限，而自动创建重新发布到全部地址，就应修正真正的配置来源。这个用例要与远程拒绝测试分开记录，前者证明设置能延续，后者证明特定路径的实际范围。
