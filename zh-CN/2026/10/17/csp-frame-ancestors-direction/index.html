伙伴门户已获准，最上层页面为什么仍会阻断嵌入？

用三个本地来源的未执行 fixture 逐层检查 frame-ancestors，并区分父页加载、真实响应交付、self 与用户授权。

正文

核心要点

  • frame-ancestors 检查全部祖先，不只紧邻父页面。
  • 父页加载限制与叶页嵌入许可属于相反方向。
  • 响应头、浏览器展示和用户业务权限需要分别核对。

后台页把伙伴门户列入 frame-ancestors，不表示门户上方的外层页面也自动获准。该指令检查整条祖先链，任何祖先不匹配都可能阻止内层文档加载。排障时应画出谁嵌入谁，再分别检查父页允许加载哪些 frame，以及叶页允许哪些祖先嵌入自己。

先区分两个方向，再列出全部祖先

MDN 的 frame-ancestors 参考说明，它控制谁可以嵌入当前页，与 frame-src 控制当前页可以加载哪里不同；嵌套时检查每个祖先，任意一层不匹配就取消加载。本文于二〇二六年十月三十日核对该页，页面标注最后修改于同年八月二十七日，没有运行浏览器嵌入测试。

假设外层工作台甲嵌入伙伴门户乙，乙再嵌入后台丙。丙的紧邻父页面是乙，但甲也是丙的祖先。只允许乙，就只覆盖了链上的一部分。甲自己的策略允许加载乙，也不会替丙发放“允许被甲嵌入”的许可。每份响应保护自己的文档，两种方向的判断不能互相签收。

W3C CSP Level 2 推荐标准给出遍历祖先的处理说明，标准日期为二〇一六年十二月十五日。本次同时核对的 CSP3 在线版本标为二〇二六年十月二十七日工作草案，不能称作已完成的推荐标准或浏览器部署回执；本篇不靠草案状态宣称新能力。

用三个来源走完一次允许关系

下面是未执行的完整本地 fixture 程序，使用 Python 标准库启动三个仅监听回环地址的 HTTP 服务。同一主机上的不同端口构成三个来源：八一〇一代表外层甲，八一〇二代表伙伴乙，八一〇三代表后台丙。测试环境须确保这些端口可用；它不是生产托管或认证方案。

程序把各页的响应头和正文放在同一份可审查映射里。甲允许加载乙；乙允许甲嵌入并允许加载丙；丙允许甲和乙作为祖先。启动后拟在测试浏览器打开最外层入口，观察后台标记是否可见，按回车结束服务。本文没有启动程序，也没有浏览器结果。

import threading
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

outer = "http://localhost:8101"
partner = "http://localhost:8102"
admin = "http://localhost:8103"
leaf_ancestors = f"{partner} {outer}"
pages = {
    8101: (f"frame-src {partner};",
           f'<iframe src="{partner}/" title="Partner"></iframe>'),
    8102: (f"frame-ancestors {outer}; frame-src {admin};",
           f'<iframe src="{admin}/" title="Admin"></iframe>'),
    8103: (f"default-src 'none'; frame-ancestors {leaf_ancestors};",
           '<p id="fixture-result">Controlled framing fixture</p>'),
}

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        policy, fragment = pages[self.server.server_port]
        body = ("<!doctype html><title>Framing fixture</title>" + fragment).encode()
        self.send_response(200)
        self.send_header("Content-Type", "text/html; charset=utf-8")
        self.send_header("Content-Length", str(len(body)))
        self.send_header("Content-Security-Policy", policy)
        self.end_headers()
        self.wfile.write(body)

servers = [ThreadingHTTPServer(("127.0.0.1", port), Handler) for port in pages]
for server in servers:
    threading.Thread(target=server.serve_forever, daemon=True).start()
try:
    input("Open http://localhost:8101/ in a test browser; Enter stops servers. ")
finally:
    for server in servers:
        server.shutdown()
        server.server_close()

正常配置中，相关祖先条件都满足，才具备这组嵌入关系所需的许可。网络、其他政策和浏览器仍须实际验证。代码返回的 HTTP 头是示例准备交付的内容，不应在未运行时称作已经收到的响应。

第一组负样本把 leaf_ancestors 改成只有 partner，保留其他设置，用于证明检查不止紧邻父页面。第二组恢复完整祖先集合，却让伙伴页的 frame-src 不允许 admin，用于证明叶页许可不能强迫父页加载自己。每次改配置应重启这份受控 fixture 并保存各页实际响应，不能在同一次观察里同时改动两个条件。

严格 default-src 和 meta 为什么不能代替？

MDN 明确说明 frame-ancestors 不回退到 default-src。default-src 'none' 可以严格限制其他加载，却没有自动形成这份祖先拒绝清单。上面丙同时写出两项，是因为它们各自承担不同责任，不是给同一限制重复命名。查看页面内部有没有 iframe，也不能判断外部页面能不能把它嵌进来。

该指令还不支持通过 meta 设置。若静态模板里加入一行策略，但托管服务没有发出对应响应头，就不能依据源码宣布嵌入已被禁止。应检查实际文档响应，识别应用、代理、静态托管等交付层贡献的政策，再核对浏览器结果。若存在多份 CSP，也不能假定新加一份宽松政策就覆盖所有旧限制。

对正常业务嵌入被阻断的修复，应先找哪个文档、哪条指令、哪个来源不满足。不要为了恢复画面就关闭整份 CSP，或者把所有来源都放开。来源迁移和伙伴关系结束也会改变允许集合，需要与真实业务入口同步维护，不能让一次部署登记永久代表以后环境。

frame-ancestors 的 self 指谁？

它相对被保护文档的来源理解。对后台丙而言，self 指后台自己的来源，不会因为紧邻父页是伙伴乙，就自动把乙当作 self。伙伴页面自己的 self 又属于伙伴响应的判断；这些文字一样，指代对象却不同。

因此本例若需要跨来源嵌入，应审查明确来源，而不能只把各页都写成 self 就认为相互允许。来源含协议、主机与端口，测试环境和生产环境若不同，也不能凭域名看起来相似就直接沿用。本文不提供宽泛域名通配符的通用许可建议，允许范围应来自已确认的嵌入需求。

HTTP 请求返回 200，就能验收嵌入吗？

不能。取回文档与浏览器允许它在这条祖先链中展示，是两项结果。验收需要同时保留各页真实响应头、嵌套来源结构、浏览器阻断诊断与最终可见状态；仅有成功响应或 iframe 的某个事件，不足以证明预期内容已展示。不要用子页加载事件当成后台业务操作已经完成的证据。

拟议矩阵包含直接伙伴嵌入、三层全允许、遗漏外层祖先、父页禁止子页、仅有 meta 文本，以及合法来源但用户无业务权限。前几项验证嵌入关系，最后一项验证许可没有越过用户授权。本站报告模式与强制执行讨论政策是否真正阻断的另一项区别，不能用没有报告代替全部矩阵。

直接在新标签打开后台成功，也只能作为另一项控制：它证明该路径能取回并显示文档，不证明在伙伴祖先链里也有许可。测试时保留同一个后台响应，分别直接打开、由伙伴打开和经外层再打开，避免三组其实访问了不同环境。来源列表中的每个条目都应有真实业务理由；测试端口只是隔离来源的办法，不能照搬成生产伙伴名单。未确认的新外层来源，应先回到允许关系的决定，而不是临时放宽全部入口。

本文不报告安全通过或发现点击劫持事故。先列全部祖先和每页保护方向，再在真实交付头部与浏览器结果中核对同一份允许合同；一个获准的近父页面，不能替整条链作出保证。
