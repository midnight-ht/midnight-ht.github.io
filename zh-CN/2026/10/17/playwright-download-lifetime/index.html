Playwright下载事件来了，文件为什么还是丢了？

补充完整下载保存测试，区分事件、临时文件、saveAs、内容验收和CI留存，并说明远程path限制。

正文

核心要点

  • download在开始时发出，不是保存完成回执。
  • 主流程等待saveAs并检查本次内容。
  • 远程path限制与CI制品上传需要单独处理。

download事件在下载开始时触发，不能证明文件已保存；让主测试等待saveAs，并在上下文关闭前完成需要的保留和检查。点击导出成功、获得下载对象、保存文件与内容符合任务，是四个可以分别失败的阶段。

Playwright下载指南要求先开始等待事件，再触发点击，随后等待下载对象并保存。指南提醒，产生下载的浏览器上下文关闭时，所属下载文件会被删除；事件回调另开一条异步控制流，也可能在主场景结束时尚未完成。本次重写保留原发布日期与地址，补充完整教学测试和失败分类，没有运行真实导出。

先给临时文件与测试产物分配不同位置

Download API参考说明，事件在下载开始时发出，完成后才能取得可用路径。saveAs把下载复制到指定位置，在下载仍进行时也可以调用，并会按需要等待完成。这个等待应出现在主测试可以追踪的控制流里，而不是只有一个无人等待的监听器。

临时下载归浏览器上下文所有，测试输出目录则由测试运行与后续CI流程管理。把文件复制到测试指定位置，可以明确本次保存目的地；但测试结束后的清理、上传和留存仍需要流水线负责。saveAs返回不等于文件已经进入远程制品库，更不等于真实导出服务的业务结果已验收。

文件名同样需要分工。suggestedFilename是浏览器按响应头或download属性等计算出的建议名称，不同浏览器可能有不同逻辑。可以把它作为体验检查，但本地保存路径由测试控制更容易避免并行覆盖或把不受信任名字拼进任意位置。下载文件名的信任边界讨论这个相关责任。

一个有明确内容预期的完整教学测试

下面Playwright测试未执行，没有调用真实导出接口。它在页面里构造固定CSV，验证事件等待、saveAs以及保存后的字面内容。教学CSV只有固定两列，比较原始文字是刻意的；真实CSV存在引号、换行或不同编码时，应采用对应解析器与业务断言，不能直接套用这个简化合同。

import { test, expect } from '@playwright/test';
import { readFile } from 'node:fs/promises';

test('preserve a teaching download', async ({ page }, testInfo) => {
  const csv = 'record_id,status\nteaching-42,ready\n';
  await page.setContent(`<!doctype html><html lang="en">
    <meta charset="utf-8"><button type="button" id="export">Export fixture</button>
    <script>
    document.querySelector('#export').onclick = () => {
      const text = ${JSON.stringify(csv)};
      const link = document.createElement('a');
      link.href = 'data:text/csv;charset=utf-8,' + encodeURIComponent(text);
      link.download = 'teaching.csv';
      document.body.append(link);
      link.click();
      link.remove();
    };
    </script></html>`);
  const pending = page.waitForEvent('download');
  await page.getByRole('button', { name: 'Export fixture' }).click();
  const download = await pending;
  const destination = testInfo.outputPath('teaching-export.csv');
  await download.saveAs(destination);
  const failure = await download.failure();
  expect(failure).toBeNull();
  const saved = await readFile(destination, 'utf8');
  expect(saved).toBe('record_id,status\nteaching-42,ready\n');
});

等待器在点击前建立，避免快下载先发生而后开始监听。保存目的地来自该次测试的输出路径，没有使用建议文件名决定目录。最后的字面断言来自预先声明的教学合同，包含记录身份与状态，不是从刚下载的内容里再推导一份相同预期。

这个例子可以说明一条完整控制流，却不能证明某个生产报表导出正确。真实场景还要核对请求范围、用户权限、对象身份、必要列和数据版本。若服务器返回一张登录页，文件仍可能存在，名字仍可能像CSV；仅有saveAs成功无法判定它属于本次任务。

保存失败时，上例会在saveAs处失败，不会继续执行后续断言。若项目需要保留更细的诊断，可在异常处理中读取合适的下载失败信息并附加原始错误，但不要用后续错误盖住最先失败阶段。本文没有生成文件或stdout，不能把代码注释当作运行回执。

为什么一个异步监听器仍可能丢文件

page.on注册一个async回调，只表示事件发生后会运行那段函数，不自动让测试主体等待回调里的保存结束。主函数已经返回，fixture开始清理上下文，临时下载便可能不再可用。应让主流程拥有完成Promise，或像样本一样直接等待事件对象和保存。

固定睡眠也没有定义完成条件。小文件可能早已完成，大文件或慢网络可能仍在进行；等待一段时间后关闭，只能证明时间过去。选择超时应来自实际导出要求，并记录事件等待、下载、保存与内容检查分别在哪里失败，不给所有阶段套一个“导出超时”的名字。

并行用例需要独立输出位置。两个测试都写同一份全局report.csv，后完成者可能覆盖先完成者，导致错误内容恰好满足另一条断言。测试身份、导出对象与目标文件应能对应；重试也要保留尝试归属，不能只留下最后一次文件覆盖先前失败证据。

远程浏览器为什么不能依赖path？

当前API明确说path在远程连接时抛错。即使本地模式能取得临时路径，也不能把它当成所有运行方式都能访问的稳定产物地址。saveAs表达的是把文件复制到调用方指定位置的责任，应按实际连接模式验证它和输出收集方式，而不是在本地找到路径就宣布远程CI也通过。

failure会按需要等待下载结束并返回错误或null；cancel可以取消下载，成功取消后failure会给出canceled。这些是浏览器下载对象的状态，不自动取消服务端已经创建的导出任务。取消后立即再点击是否安全，需要真实接口的任务查询与重复操作合同，本文没有实现这类服务。

什么时候可以说导出测试完成？

待执行验收应分别覆盖没有事件、取消或失败、保存目录问题、错误内容以及并行输出。正常路径要留下本次保存文件和内容判断，失败路径要保留最先失败的阶段、对象身份与原始错误。若CI随后上传制品，再核对上传结果，不能把本地保存算成远程留存。

点击后的断言等待解决状态何时可观察；下载还多一层文件生命周期。让主测试等待保存，核对本次内容，再由流水线确认保留，才有依据把按钮动作提升为文件交付证据。
