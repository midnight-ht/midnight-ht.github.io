Prometheus 出现 exported_job，哪一方标签被保留下来了？

用本地端点与两份抓取策略追踪 Prometheus job/instance 冲突，区分来源、查询身份和 external_labels。

正文

核心要点

  • false 与 true 选择不同标签定义者。
  • 查询条件应匹配变更后的实际序列身份。
  • external_labels 不替代本地抓取冲突策略。

honor_labels 决定抓取样本与服务器附加标签冲突时的优先关系。默认 false 会给冲突的抓取标签加 exported_ 前缀，再附加服务器值；true 则保留抓取值。先追踪两个来源，不能为去掉前缀直接改变身份策略。

一项标签，可能有两个定义者

Prometheus 配置参考将这项开关限定在抓取标签与服务器附加标签的冲突处理，包括 job、instance、手动目标标签和服务发现产生的标签。本文于二〇二六年十一月六日核对当前在线说明，没有启动 Prometheus 或查询真实指标；不能从 rolling 页面推断部署版本。

假设指标端点给出 job=exporter-job，而抓取任务也有自己的 job 名字。默认策略并不是默默扔掉端点值，而是为冲突的抓取标签换名，再保留服务器管理的值。查询里出现 exported_job，因而可能是采集阶段的输出，不表示应用端点原本就暴露了两份 job。

true 改的是这份优先关系。它不是格式美化开关，也没有验证端点标签的业务真实性。某个受控联邦或 Pushgateway 场景可能需要保留目标定义的标签；普通应用抓取是否如此，应先决定谁负责定义观测身份，再评估下游使用者。

用本地端点给出可区分的原始输入

下面是未执行的完整教学端点，要求 Python 标准库与空闲本地端口。将其保存为 exporter.py，只监听本机，不读取业务数据。它稳定返回数值七与两项刻意冲突的标签；额外 scope 用于辨认原始样本，不表示任何真实服务状态。

from http.server import BaseHTTPRequestHandler, HTTPServer

BODY = b'demo_value{job="exporter-job",instance="exporter-instance",scope="raw"} 7\n'

class Exporter(BaseHTTPRequestHandler):
    def do_GET(self):
        if self.path != "/metrics":
            self.send_error(404)
            return
        self.send_response(200)
        self.send_header("Content-Type", "text/plain; version=0.0.4")
        self.send_header("Content-Length", str(len(BODY)))
        self.end_headers()
        self.wfile.write(BODY)

HTTPServer(("localhost", 18080), Exporter).serve_forever()

在一个独立终端运行 python exporter.py，并先确认本次端点实际返回这段样本。若端口被其他程序占用，应停止练习并更换自有端口，不要把已有服务的内容归到这个 fixture。原始暴露内容是比较的第一份证据，不能省略它后只看最后的图例。

另一份文件 honor-demo.yml 使用同一个端点，建立两个不同的抓取任务。demo_case 不与端点冲突，作为稳定的对照选择器；两个 job 的冲突策略则不同。

global:
  scrape_interval: 15s
scrape_configs:
  - job_name: server-false
    honor_labels: false
    static_configs:
      - targets: ['localhost:18080']
        labels:
          demo_case: 'false'
  - job_name: server-true
    honor_labels: true
    static_configs:
      - targets: ['localhost:18080']
        labels:
          demo_case: 'true'

在另一个终端，从保存配置的目录启动匹配本机的 Prometheus，使用全新存储和独立监听端口。程序以前台运行，查询在其他终端或浏览器中进行；练习结束只停止这份进程与 exporter，不处理任何原有监控数据。

honor_data=$(mktemp -d)
prometheus --config.file=honor-demo.yml --storage.tsdb.path="$honor_data" \
  --web.listen-address=localhost:19090

这条命令没有执行，目录创建与进程启动也没有实际回执。配置能解析只说明语法层成立；还需确认实际进程加载了这个文件、端点可达并已发生抓取。端口冲突或错误配置路径会在更早阶段失败，不能被解释成标签选择产生了空结果。

两份结果应该在哪些字段不同

对 false 任务，纸面预期是 job=server-false、instance=localhost:18080，同时保留 exported_job=exporter-job 和 exported_instance=exporter-instance。对 true 任务，job 与 instance 则保留端点给出的两项原值；服务器同名值被忽略。两份结果仍有不同的 demo_case，且 scope=raw 不因这个冲突规则被换名。

这些不是数据库输出，只是给定简单输入下的预期表。示例没有预先暴露同名 exported_ 字段，因此也不讨论更复杂重名链的实现。加入新的冲突标签或同时修改端点与目标配置后，应重新推导，不能照抄这张有限表。

查询时可用不冲突的选择器分别观察，避免先把待验证的 job 身份写死：

demo_value{demo_case="false"}
demo_value{demo_case="true"}

如果仍按 job=server-true 查询第二份，可能找不到预期样本，因为 true 正是在保留端点的 job 值。这个空结果不能直接说明目标没被抓取。应先查看完整标签，再核对查询条件；不要为了让旧查询恢复结果就随手丢弃维度，造成不同来源合并。

还应准备一个没有冲突的负对照。若另一次教学输入只暴露demo_plain与scope，没有job和instance，服务器仍有自己的目标标签可附加。两份策略不应仅因开关不同就凭空制造exported_job。这个对照能检查“所有样本都会带前缀”的错误预期；运行前先核对实际暴露内容，不能把指标本来没出现误当过滤成功。

再单独改变端点的job值，而保持服务器任务名与demo_case不变。false路径的服务器job仍适合作为原来的选择条件，但按exported_job筛选的查询需要面对新原值；true路径中，job本身随端点值改变。两种策略都需要看完整标签，不能因为某一个服务器字段稳定，就断言所有使用者的身份条件都未变。

这两项变化应分开进行。一次改原始样本，一次改冲突开关，保存每一步的原始文本与实际配置，才能解释输出由谁改变。若同时换了任务名、目标地址和指标标签，再用最终图例判断honor_labels，实验已经失去单一可解释的对照。

何时值得让端点保留同名值

决定依据是身份所有权。联邦输入可能已经携带需要保留的来源身份，但来自不受控制端点的任意标签，不应因此升级成授权或可信业务声明。保留值与证明值准确是两件事；配置只能规定谁优先，不能替团队核验数据来源。

变更前先列出依赖 job、instance 的看板、记录规则、告警与路由。改动会让后续序列具有不同标签身份，历史数据不会自动被重写。验收要同时检查新样本和依赖它们的查询，而不只看目标页面显示成功。必要的兼容与回退应按实际使用者安排，不承诺一个通用切换顺序。

修改 external_labels 能修掉本地的 exported_job 吗？

不能替代抓取冲突策略。官方说明 external_labels 不受 honor_labels 影响；与外部系统通信时，它们只为尚无该标签的序列补值，已有值则保留。它不是重新解释本地抓取结果中 job 来源的另一种写法。

例如为外部传输补 cluster，并不会把本例已存储的 exported_job 变回 job。需要检查的是抓取策略、原始样本与下游选择器。把通信阶段的补充信息与采集阶段冲突混在一起，可能改了远端标签，却完全没有触及眼前图例的来源。

二〇二六年十月十五日的记录规则标签文章讨论表达式和规则怎样再次改变身份。本题处理更早的抓取冲突。保留原始暴露、实际配置、最终标签与查询条件四份材料，才能解释前缀来自哪里，以及改变优先关系后谁需要跟着调整。
