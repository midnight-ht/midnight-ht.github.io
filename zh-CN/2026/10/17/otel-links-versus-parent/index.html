一个批次来自多条链路，Span 应该选谁当父级？

多来源批次用真实操作边界表达关系；链接创建时机可能影响采样，关联不保证目标 Span 可见。

正文

多个来源不能都挤进单一父级关系；Span Link 可记录同一或不同 trace 的关联，并应考虑创建时机与采样。批量处理若只是随意挑一条输入当作全部工作的父级，可能让图形看起来连贯，却丢掉其他来源的因果信息。

关系应表达真实处理方式

OpenTelemetry 1.61.0 的 Trace API 规范允许 Span 关联其他 SpanContext，链接可来自同一条或不同的 trace。创建 Span 时提供的链接可能参与采样判断，创建后增加的链接则可能不被采样器考虑。这里描述规范能力，具体语言 SDK、后端展示和限制还需核对，不能从接口存在推断所有关联一定被展示。

同项目的规范概览区分 Span 的父级和链接，说明批量操作可以通过链接关联多条来源。假设一个批次读取多条独立消息，再执行一次汇总。若只把第一条消息上下文作为父级，其他输入就可能在这份记录中失去明确关联。这是未经运行的建模示例，不是对某个消息系统的强制埋点方案；实际父级与链接选择还要结合处理语义及适用的语义约定。

先定义一次操作覆盖哪些输入

批次大小、重试方式和部分成功都会影响关联。需要明确这个 Span 表示一次读取、整个批次处理，还是某个子步骤。不同操作边界可以采用不同结构，不能为了少写几行埋点，把所有处理都压进一个长 Span，再期待后端自动拆解输入关系。

链接也不应携带不必要的业务秘密。SpanContext 用于追踪关系，附加属性则需要遵循数据最小化和实际规范。把完整消息正文或客户资料塞入链接属性，并不会使关联更可靠，却可能扩大观测数据中的敏感范围。

如果处理跨越异步队列，还应确认上下文从哪里提取、在哪一段建立操作边界，以及重试是否使用同一个业务身份。重新创建 Span 不等于业务只执行一次，链路关系也不替消息确认或去重机制。观测描述发生了什么，不能替业务完成状态作保证。

创建时机影响可利用的信息

当链接对采样决策重要时，应尽量在符合 SDK 契约的创建阶段提供已知信息。事后补齐可能改善部分记录，但不能承诺找回此前未记录的数据。也不要为了等齐所有可能来源而无限延迟操作记录；需要根据实际处理过程说明已知与未知。

建议验收多个来源、同 trace 与跨 trace 关联、部分输入失败和重试等场景，检查导出数据及后端能显示什么。还要核对采样设置、链接数量限制和丢弃信息。本文没有运行 SDK 或后端测试，因此没有完整链路可见性的成功证明。

链接存在不意味着目标 Span 一定仍在保存范围内。采样、保留期、导出失败或访问权限都可能影响可见性，界面应允许用户理解这种缺失，而不是把没有跳转目标解释成业务没有发生。诊断需要结合其他任务证据。

关于采样与丢失数据的边界，可参看采样不能找回的链路。先确定操作与来源的真实关系，再选择父级和链接，追踪结构才不会为了画得漂亮而改写事实。
