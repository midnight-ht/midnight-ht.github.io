用内存导出检查批次追踪：父级、三条链接与单条重试

用实际Python内存导出核对三来源批次与B单条重试，分开父级、链接、业务结果和目标可见性，并说明HTTP环境上下文边界。

正文

核心要点

  • 先定义本次操作边界，再分别选择父级和各条来源链接。
  • 创建时已知的链接有助于采样判断，数量和导出仍受实际配置限制。
  • 本地关系断言不证明消息成功、确认、目标可见或恰好一次交付。

一个批次有三条来源，不表示它应该有三个父级。先定义这个 Span 覆盖的一次操作，再把来源 SpanContext 作为链接记录；后台批次可以没有父级，已有执行上下文时则需另行选择。用内存导出器核对实际父级、链接身份和重试范围，比只看追踪图是否连通更可靠。

先把操作和来源放在不同位置

假设后台工作者把消息 A、B、C 合成一次汇总，三条消息分别带着不同生产链路的上下文。Span 的父级位置描述它放在哪个执行树中，链接则补充其他关联。随手选 A 当父级，也许让图上多出一条连线，却不能说明 B、C 属于 A 的子操作。应先解释选择依据，而不是把后端画得整齐当成关系正确。

OpenTelemetry Tracing API 的 Link 章节允许链接同一或不同 trace 中的 SpanContext。二〇二六年十一月十日核对的规范站点标识为一点六二点零；这不是 Python 软件包的版本，也不表示所有语言实现和可视化后端都具有同一行为。父级、链接和目标是否能被查询到，需要分开验证。

一次 Span 还要有明确的工作范围。它是拉取消息、处理这三条输入，还是只覆盖汇总写入？若 B 在处理阶段失败，写入阶段根本未执行，用一个含糊的成功标签概括全批就会误导调查。链接负责留下来源关系，不会替应用确定成功、确认消息、提交位点或执行去重。

下面把范围限定为背景批次的追踪结构。预期先写好：第一个操作没有父级，恰有 A、B、C 三条链接；假设仅 B 需要重试，第二个独立操作仍没有父级，但只链接 B。重试的业务假设不是脚本执行了消息处理，代码只创建并导出这些观测对象。

一个实际运行的内存导出例子

本地使用 Python 三点十一点十五及 opentelemetry-api、opentelemetry-sdk 一点四五点二，安装在独立临时虚拟环境中，没有改变本站依赖。包版本来自实际运行记录；规范版本与语言包版本采用不同编号，不能相互替代。

完整程序如下。上下文编号都是人为构造的非零示例值，不是真实客户或生产者身份。显式空 Context 让两次操作独立起根；ALWAYS_ON 与八条链接的上限只是本例配置，不代表生产采样和容量建议。导出器只保存在当前进程的内存里，不连接 Collector、消息系统或查询后端。

import json
from opentelemetry.context import Context
from opentelemetry.trace import Link, SpanContext, TraceFlags
from opentelemetry.sdk.trace import TracerProvider, SpanLimits, sampling, export
from opentelemetry.sdk.trace.export.in_memory_span_exporter import InMemorySpanExporter

# Synthetic identifiers; no producer or broker is contacted.
origins = {
    name: SpanContext(trace_id=number, span_id=number + 16,
                      is_remote=True, trace_flags=TraceFlags(1))
    for name, number in zip(('A', 'B', 'C'), (1, 2, 3))
}
exporter = InMemorySpanExporter()
provider = TracerProvider(sampler=sampling.ALWAYS_ON, span_limits=SpanLimits(max_links=8))
provider.add_span_processor(export.SimpleSpanProcessor(exporter))
tracer = provider.get_tracer('example.batch.links')
scenarios = (
    ('batch-process', [origins[key] for key in ('A', 'B', 'C')]),
    ('retry-B-only', [origins['B']]),
)
for name, contexts in scenarios:
    span = tracer.start_span(name, context=Context(),
                             links=[Link(context) for context in contexts])
    span.end()

def identity(context):
    return context.trace_id, context.span_id

finished = exporter.get_finished_spans()
observed = [
    (span.name, span.parent is None,
     [identity(link.context) for link in span.links])
    for span in finished
]
expected = [
    ('batch-process', True, [(1, 17), (2, 18), (3, 19)]),
    ('retry-B-only', True, [(2, 18)]),
]
assert observed == expected, observed
operation_ids = [identity(span.context) for span in finished]
assert operation_ids[0][1] != operation_ids[1][1]
print(json.dumps(observed))
provider.shutdown()

程序实际退出码为零。按预先写定的身份检查，导出结果分别是 batch-process 的三个来源对，以及 retry-B-only 的单个 B 来源对；两次操作都没有父级，并有不同的操作 Span ID。没有用随机生成的新 ID 来反推预期，也没有把控制台打印成功当成业务已经重试成功。

这里特意没有创建或导出 A、B、C 对应的生产者 Span。因此，在本地导出集合里只会找到两个新操作，不能点击到三个上游对象。关系字段存在与目标记录存在，本来就是两项检查。即使某条上下文的 sampled 标志被置位，也不能从这个字段断言目标已被采集、传送并保留到当前查询范围。

重试必须对应这一次的输入范围

只重试 B 时，把 A、B、C 三条链接原样复制过去，会让重试看起来仍处理全部输入。反过来，第二次操作若重新生成一个毫不相关的 B 来源身份，也可能切断调查线索。保留哪一份创建上下文，应来自真实消息及其生命周期，不能为了让两次操作有相同链接数量而补造来源。

但相同的业务任务也不一定永远对应同一个创建上下文。重新投递原消息与业务系统重新发布一条替代消息，可能具有不同传播材料。应用应保留可以解释的任务与尝试身份，按实际协议建立关联；链接不是一个可以强行合并所有尝试的全局业务主键。

验证部分失败时，除了查关系，还要查应用实际处理、持久保存和消息确认的结果。第一次已成功的 A、C 是否会被再次执行，是业务重试合同；导出器中的两个 Span 无法回答。若只在测试里检查 Span 数量，三条输入被错误当作一次全部成功，也可能得到同样的两个对象。

创建时提供信息，导出时检查损失

API 建议在创建 Span 时就提供已经知道的链接，因为头部采样只能利用创建时可见的信息。Tracing SDK 的 ShouldSample 与 Span Limits分别说明初始链接输入和链接数量限制。后加关联不能被承诺为重新作出原来的头部采样决定，更不能保证此前未记录的目标恢复出现。

本例用 ALWAYS_ON，因而没有验证一个真实采样策略会怎样取舍；八条上限也没有被三条输入触及。接入系统后，应把输入数、可提取的上下文数、创建时提交的链接数及实际导出数放在一起核对。输入多但上下文缺失、SDK 达到限制、导出丢失和后端不显示，发生在不同位置，不能全部归因于采样。

也不要为补足关联而无限等待批次。先明确一次操作在什么时刻确定成员，晚到消息是下一个批次、补偿还是更新，需要业务规则。把后来才知道的来源暗中写进先前的成功叙述，会改变记录含义。超过容量时如何截断、保留哪些调查字段以及怎样说明丢弃，应依据实际 SDK 和采集策略验证，而非把规范默认值当成容量保证。

已有 HTTP 服务 Span，批次必须另开一个根吗？

不必。这里新增的是主例没有的条件：消息处理发生在一个有效的 HTTP 服务上下文之内。若它描述的是该请求发起的处理操作，可以保留这个执行上下文为父级，同时用链接记录各条消息的创建上下文，而不是一律清空 Context。前面的显式空上下文只属于背景示例，不是所有批次的通用建议。

消息 Span 语义约定当前标为 Development，核对时为一点四五点零。它以链接作为关联生产者与消费者的默认机制，并说明单消息父级替代方式及已有环境上下文的处理；不能把这些条件改写成所有自动埋点已经按同一种方式运行。

实际接入时先确认当前上下文由谁建立，再读所用埋点库对父级和链接的配置。给出“无环境上下文”和“有 HTTP 上下文”的两份独立预期，检查真实导出字段；后者未在上述程序中执行。若页面缺少上游对象，可结合采样不能找回的链路继续定位，但不要把一次本地关系验证扩大成跨服务可见性、业务成功或恰好一次交付的证明。
