输入框禁用了，提交时为什么收不到原来的值？

比较原生FormData与手工对象，补充fieldset继承、布尔属性、readonly范围和禁用时机。

正文

核心要点

  • 原生条目构造会跳过禁用控件。
  • 自身disabled属性不覆盖全部fieldset继承状态。
  • 控件锁定不冻结脚本状态或替代服务器校验。

支持disabled的控件会被原生表单条目构造排除，即使屏幕仍显示原值。排查缺失地区之前，先确认请求来自原生序列化还是脚本另外组装。显示、可编辑、原生提交和服务器可信状态，是需要分别说明的责任。

值可见，不代表值会被发送

HTML的禁用控件规则定义禁用状态及约束验证边界；同一文档的条目构造算法明确跳过禁用字段。以下诊断样本依据标注二〇二六年十月三十日更新的原文，没有运行浏览器或接口。

disabled是布尔属性，判断属性是否存在，不靠字符串内容表达真假。写成disabled="false"仍然指定了该属性，不等于恢复编辑。用脚本设置相应IDL属性为false与在标记里写字符串false，也不能当成同一操作。

另一个容易遗漏的条件是fieldset。子控件可能因为祖先fieldset被禁用，而自身没有disabled属性；相应规则对该fieldset首个legend元素子节点内的后代有例外。排查不能只看输入框自己那一个属性，否则会遇到“代码读到false，页面仍不能编辑”的错觉。

用两种收集方式看同一份表单

以下完整静态样本未执行，没有订单接口。地区和姓名均为虚构教学值。保存为HTML后，按钮会展示两种收集结果；它不会发送请求，也不能证明服务器保存了什么。

<!doctype html>
<html lang="zh-CN">
<meta charset="utf-8">
<title>禁用与收集数据示例</title>
<form id="order">
  <label>配送地区
    <input id="region" name="region" value="北区" disabled>
  </label>
  <label>联系人
    <input id="contact" name="contact" value="演示联系人" readonly>
  </label>
  <label>备注<input id="note" name="note" value="教学备注"></label>
  <button type="submit">比较待发送数据</button>
</form>
<pre id="result"></pre>
<script>
const form = document.querySelector('#order');
form.addEventListener('submit', event => {
  event.preventDefault();
  const nativeEntries = [...new FormData(form).entries()];
  const { region, contact, note } = form.elements;
  const manualObject = {
    region: region.value,
    contact: contact.value,
    note: note.value
  };
  document.querySelector('#result').textContent =
    JSON.stringify({ nativeEntries, manualObject }, null, 2);
});
</script>
</html>

按标准推导，nativeEntries中没有region，支持readonly的联系人文本输入仍可参与相应条目，备注也会收集。manualObject却直接读取region.value，因此仍包含北区。这不是矛盾：后者没有承诺遵循原生表单的字段筛选规则。最终网络载荷还取决于发送代码，本样本只对比收集对象。

因此，定位实际问题时应保存提交路径、字段收集方式和真实请求，而不是凭灰色输入框推测载荷。框架可能从状态对象生成JSON，可能调用FormData，也可能在提交事件中补字段；不同路径需要各自检查。原生排除不能自动约束开发者手动读取对象的行为。

不可编辑的地区应该由谁提供？

若地区是服务器已经确认的订单状态，可以让客户端展示它，提交时由服务器依据订单身份读取并核对。这样不必要求用户重新发送一份无法编辑的副本，但服务器仍需判断当前用户能否操作这份订单、地区是否允许改变，以及订单版本是否仍适用。

若接口确实需要客户端提供某字段，应选择适合字段类型的传递方案。readonly只适用于相应控件状态，不能给select或checkbox机械替换就期待同样行为；input的readonly规定有明确适用范围。普通文本展示、支持readonly的输入与禁用交互，各自表达不同需求。

隐藏字段可以传送值，但不是可信来源。用户仍能改请求，服务器不能因为页面没有可编辑入口就接受任意地区或价格。禁用状态也不冻结客户端数据，标准明确允许脚本改变相应值或勾选状态。界面锁定与授权判断必须各自有依据。

子输入disabled是false，为什么仍然不提交？

先检查祖先fieldset，而不是立即给序列化库补一个特例。自身disabled属性反映的状态，不足以表示继承造成的全部禁用条件；可以同时记录属性是否存在、相应IDL值与:disabled是否匹配，再对照真实祖先。首个legend例外还需要看实际树结构，不能把任何标题元素都当成例外。

例如字段组禁用以后，组内开关放在首legend里，可能仍承担恢复操作；普通字段则继续被禁用。这是原生规则的适用场景，不表示可以把全部输入塞进legend来规避状态设计。层级和可用性需要共同表达用户能够做什么，例外不能代替完整交互方案。

拟议复验可以在原样本外包一层fieldset并设置disabled，移除region自身disabled，再比较region.disabled与状态选择器以及条目结果。随后把一个输入放入首legend观察差异。这里给出的是待运行变体，没有实际控制台记录，不写成已通过兼容性测试。

什么时候禁用，也会影响收集结果

保存中为了阻止重复操作而禁用整组字段，若随后才调用FormData，可能把原本需要的数据一起排除。应明确先取得哪份有效输入、何时切换交互状态，以及失败后如何恢复。不要只修“保存按钮不能再点”，却让请求失去本次输入。

这不意味着永远先收集后禁用就是通用答案。数据可能在异步预检期间变化，服务器状态也可能更新；应用需要绑定本次提交的对象、版本和动作，再按合同核验。有关原生提交者与校验路径，可对照requestSubmit的动作与校验。

动态依赖也要规定旧值去向。用户改变上游地区类型，原来的下游字段被禁用，是保留为历史草稿、清除还是等待重新选择，应由业务说明。恢复编辑后不能无声发送已经不适用的旧值；失败时也不应让用户修正一个仍无法聚焦的控件。

载荷里的缺失与空字符串也不能合并理解。若地区未提交，服务端按合同可能保留原状态、从订单读取，或者拒绝缺字段；发送空地区则可能表达清空请求。两种输入应分别验证，不要在解析层无条件补成同一个默认值。

样本保留原生条目的数组形态，避免把同名字段直接压成普通对象后丢掉多值。实际表单有多个同名checkbox时，还要按字段合同读取全部值。此处缺字段的排除机制与重复字段的表示机制不同，补一个隐藏输入之前应先确认它会不会制造额外同名值。

拟议验收覆盖初始禁用、提交中禁用、重新启用、fieldset继承、readonly文本、手工JSON与原生条目，记录界面值、实际载荷和重新读取的服务器状态。本文没有执行网络与持久化验证。下一次遇到“看得见却收不到”，先辨认收集算法与禁用来源，再决定该补字段还是该改数据责任。
