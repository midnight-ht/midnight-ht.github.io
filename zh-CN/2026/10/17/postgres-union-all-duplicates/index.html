两条不同事件值相同，UNION 为什么会少算？

UNION 比较整个投影行，不推断事件身份。用四条独立事件推演两行三十与四行五十，再区分来源列、业务去重和限制子句的作用范围。

正文

核心要点

  • 整个投影行相等不等于业务事件相同。
  • 来源和事件身份是否保留，会改变去重结果。
  • 业务去重、输出排序和 LIMIT 范围需分别定义。

两条事件的投影值相同，不代表它们是同一条事件。UNION 会消除整个投影行的重复，UNION ALL 则保留行的重数；合并事件后发现少算，先检查查询保留了哪些列，再判断业务是否真的应该去重。

PostgreSQL 18 的集合查询说明明确指出，不写 ALL 的 UNION 会去掉重复行。这里的“行”是查询输出的那组值，不是数据库替你识别出的事件身份。若把事件编号投影掉，只留下日期和金额，数据库就只能按剩余值判断相等。

四条合法事件，投影后只剩两种值

假设两个来源记录了四条独立事件。来源甲有编号甲一、甲二，发生日期都是十一月六日，金额都为十；来源乙有编号乙一，同日同金额，另有乙二，十一月七日金额二十。这个例子的前提是四条事件都真实独立，不是同一事件被重放四次。

下面用虚构数据构造完整只读查询。日期显式指定类型，金额为整数。结果是按集合操作规则推演的预期，没有声称数据库已执行，也不涉及任何现有业务表的修改。

WITH a(event_id, day, amount) AS (VALUES
  ('A1', date '2026-11-06', 10),
  ('A2', date '2026-11-06', 10)
), b(event_id, day, amount) AS (VALUES
  ('B1', date '2026-11-06', 10),
  ('B2', date '2026-11-07', 20)
), u AS (
  SELECT day, amount FROM a
  UNION
  SELECT day, amount FROM b
), ua AS (
  SELECT day, amount FROM a
  UNION ALL
  SELECT day, amount FROM b
)
SELECT 'UNION' AS method, count(*) AS row_count, sum(amount) AS total
FROM u
UNION ALL
SELECT 'UNION ALL', count(*), sum(amount)
FROM ua
ORDER BY method;

第一种结果预期为两行、合计三十；第二种为四行、合计五十。三条十一月六日的十，在只投影日期和金额后完全相等，于是第一种只保留一行；十一月七日的二十是另一行。少掉的二十来自丢失两个合法观测，不是 SUM 把十加错了。

这里用了 count(*) 显示合并后的行数，重点是合并时的重数已经改变。统计函数面对的输入集合不同，再检查聚合内部的空值处理并不能恢复已经消失的事件。若要区分计数函数自己的输入口径，可另读COUNT 怎样处理空值输入，不要把两个诊断层混在一起。

给投影加列，会改变相等的定义

若只加来源列，甲的两条十仍然相等，会合成一行；乙的十和甲的十因为来源不同不再相等，加上乙的二十，总共三行，合计四十。来源列有帮助，却仍不足以保住同一来源内的两条独立事件。这可以直接从完整投影行逐项比较得出，不是另一次测量。

若把来源与各自事件编号都保留，例子的四条事件就彼此不同，合并后的重数得到保留。新增列不是给数据库一个抽象的“别去重”提示，而是改变了参与比较的值。调试时应把每个分支真正输出的列展开看清，不能只看底层表是不是有主键。

因此，表有唯一事件编号，也不保证上层 UNION 不会丢事件。编号一旦没有出现在投影中，就不会参与该层的行相等判断。先在子查询里去掉身份，再指望外层聚合识别独立记录，信息已经不够。修复应回到信息丢失的位置，而不是在最后的总数上补一个系数。

反过来，不能为了避免合并就随手给每行添加随机值。那会让重复行不再相等，却没有说明哪些行应当作为独立业务事实保留，还可能让同一输入每次重算都不同。保留有意义的身份与来源，和人为制造一个永不相等的字段，是不同的数据治理选择。

UNION ALL 会自动处理跨来源的同一事件吗？

不会；它保留行，业务身份和冲突规则需要另行定义。如果另一个数据集中的两个来源确实报告了同一事件，选择 UNION ALL 只会把两个报告都保留下来，不能自行判断谁应该被采用。

这时先确定共享业务标识，而不是把来源内编号直接当成跨来源身份。两个来源可能使用不同编号描述同一事件，也可能恰好使用相同编号描述不同事件。还需要决定重复报告的金额不一致时如何处理、是否保留审计记录、哪一种冲突必须拒绝。集合关键词并不替你回答这些产品和数据质量问题。

在明确规则前，把来源信息和事件信息保留下来，至少能让差异可追查。过早按日期金额折叠，既可能损失独立事件，也可能把两个互相冲突的报告压成看似干净的一行。选择去重键必须有业务依据，不能仅因为一组字段“目前看起来一样”就承诺它们表示同一个事实。

结果顺序与 LIMIT 另有作用范围

官方说明也提醒，集合合并不保证先返回第一个分支的行。UNION ALL 保留重数，并不把来源优先级转换成输出顺序。如果后续逻辑需要最早、最新或某个来源优先，就必须给出明确排序和选择规则，不能读取第一行后推断它来自先写的分支。

LIMIT 也需要明确是限制某个分支，还是限制合并结果。下面两个完整只读例子使用简单整数，避免把事件身份问题与限制范围混在一起。第一条在每个分支选一行，第二条在全部合并后只选一行；输出仍是纸面预期。

(SELECT n FROM (VALUES (1), (2)) AS a(n) ORDER BY n LIMIT 1)
UNION ALL
(SELECT n FROM (VALUES (3), (4)) AS b(n) ORDER BY n LIMIT 1)
ORDER BY n;

SELECT n FROM (VALUES (1), (2)) AS a(n)
UNION ALL
SELECT n FROM (VALUES (3), (4)) AS b(n)
ORDER BY n
LIMIT 1;

预期前者返回一和三，后者只返回一。同一官方条款对括号的说明正是为了区分分支上的子句与整个集合结果上的子句。括号改变作用范围，最终排序规定展示顺序；这两者都不会替事件定义业务去重身份。

先列原始事件，再核验合并后的行

实际验证可先运行虚构数据查询，记录真实数据库版本与输出，再增加一条合法同值事件，重新计算两种操作的行数和合计。不要仍沿用两行与四行的基线答案；输入变了，期望也应重新推导。随后分别加入来源、加入事件编号，检查到底是哪一列改变了相等关系。

两个分支还必须输出相同列数，对应位置的类型应兼容。这是查询可组合的前提，不是字段含义相同的保证。列名像不像、类型能否转换、两列是否表达同一个业务维度，需要分开检查，避免语法通过但语义对错位置。

最终选择应从需求落定：确实需要完整投影行的集合语义时用 UNION；需要保留合法独立观测的重数时用 UNION ALL；需要业务事件去重时，先定义身份和冲突政策，再设计选择步骤。不要让一次不带身份的投影，替整个事件系统决定什么叫重复。
