JSON.stringify 后字段消失，undefined 应该改成 null 吗？

用完整 JSON 文本与纯函数补丁矩阵区分对象省略、数组 null、顶层 undefined 和保持清空协议，检查自定义转换与真实请求边界。

正文

核心要点

  • 默认对象属性省略与数组 null 是不同位置规则。
  • undefined 改 null 会改变表示，不能替接口批准清空。
  • 输入对象、JSON 文本、接收结构与持久结果分别核对。

JSON.stringify 默认省略对象中值为 undefined 的属性，却把数组相应位置写成 null。把 undefined 全部改成 null，并不是通用修复：更新接口可能把省略解释为保持，把 null 解释为清空。应先定义动作，再检查实际 JSON 文本与接收后的字段存在性，不能拿发送前对象的外观代替请求证据。

同一个值，位置不同会怎样？

ECMAScript 的 JSON 序列化算法分别规定对象和数组的处理。MDN 的 JSON.stringify 参考也用例子说明 undefined、函数和 Symbol 值的差异。本文于二〇二六年十一月一日核对当前 ECMAScript 2027 草案与该参考，下面程序没有执行。

在普通对象的默认序列化中，不可表示的属性值不会形成对应成员；数组则需要保留位置，在这些位置产生 null。直接序列化顶层 undefined，返回值还是 undefined，而不是 JSON 字符串。调用方若无条件把返回值交给需要文本的发送接口，已经失去“这里一定存在有效 JSON 文本”的前提。

这些规则不说明业务字段该怎样更新。假设资料里已有备注，用户点击清空，前端给 note 赋 undefined。默认序列化随后省略 note，后端按省略保持处理，旧备注便可能仍在。序列化完成了自己的规则，失败的是业务动作与传输表示没有对齐，不能把结果说成 JSON 自动选择了保持。

反过来，统一把 undefined 替换成 null，会把一些本来没有提交的可选字段变成明确空值。如果后端把 null 当清空，未编辑字段也可能受到影响。看起来载荷更完整，不代表原意更准确；修复应逐字段说明省略、空值和空文本各代表什么。

一个完整的序列化与补丁矩阵

以下是未执行的 Node.js ESM 教学程序，保存为 note-patch-demo.mjs 后可以运行，不需要服务或第三方依赖。它通过纯函数定义一份假设协议：省略保持，null 清空为存储空值，字符串更新。它没有模拟已上线接口或数据库，也没有声称这份协议适用于所有产品。

const { stringify, parse } = JSON;
const owns = Object.hasOwn;
const original = { id: 'demo-1', note: 'keep this' };

function applyNote(before, patch) {
  if (patch === null || typeof patch !== 'object' || Array.isArray(patch)) {
    throw new TypeError('patch must be an object');
  }
  if (!owns(patch, 'note')) return Object.assign({}, before);
  const value = patch.note;
  if (value !== null && typeof value !== 'string') {
    throw new TypeError('note must be null or text');
  }
  return Object.assign({}, before, { note: value });
}

const cases = [
  ['missing', {}, 'keep this'],
  ['undefined', { note: undefined }, 'keep this'],
  ['null', { note: null }, null],
  ['empty', { note: '' }, ''],
  ['text', { note: 'new' }, 'new'],
];
for (const [name, input, expected] of cases) {
  const wire = stringify(input);
  if (typeof wire !== 'string') throw new TypeError('JSON text required');
  const received = parse(wire);
  const result = applyNote(original, received);
  if (result.note !== expected) throw new Error('unexpected patch outcome');
  console.log(name, wire, owns(received, 'note'), result.note);
}

const positional = stringify([undefined, () => 1, Symbol('demo')]);
if (positional !== '[null,null,null]') throw new Error('position mismatch');
if (stringify(undefined) !== undefined) throw new Error('top-level mismatch');
try {
  applyNote(original, { note: 42 });
  throw new Error('invalid type was accepted');
} catch (error) {
  if (!(error instanceof TypeError)) throw error;
}

矩阵同时保留输入、实际生成的文本、解析后是否有该键与最终字段值。undefined 那行在传输后与缺失那行采用同一个保持分支；null 那行保留成员并进入清空分支。这里的清空定义为将字段设为 null，不是删除键；真实系统如果要删除字段，应另行定义并验证那一动作。

这份程序刻意没有调用网络。生成 wire 并打印，不等于请求真的发送；纯函数返回新对象，也不是数据库提交。它能帮助检查序列化与假设协议的衔接，真实验收仍要沿接口解析、授权、持久化和再次读取走完，不能把本地矩阵通过改写成某个端点已修复。

直接调用 applyNote 并给 note 一个数字会被拒绝；但 undefined 在进入该纯函数之前已被默认序列化移除。这个对照说明校验的位置会改变能看见的事实。如果业务需要把“调用方显式给 undefined”判为错误，就应在丢失该信息之前检查，而不能要求接收端区分两段已经相同的 JSON 文本。

属性存在，为什么仍不是发送证据？

对象可以有一个自有属性，其值为 undefined；也可以完全没有这个属性。内存里可用字段存在性检查区分，默认 JSON 文本却可能不再保留差别。调试记录应标明观察的是原始对象、序列化文本，还是服务端解析结构，否则不同阶段的值会被拿来互相证明。

日志本身也可能经过不同序列化器。开发者工具展示一个可展开对象，不保证它就是发送时的字节快照；请求包装器又可能在另一个时点转换。应在受控环境保存必要的脱敏文本或结构证据，并用任务身份把各阶段对应起来，不把完整个人资料复制到公开日志。

对于必填字段，发送前与接收端都应校验各自掌握的信息。客户端发现用户意图无法用当前协议表达时，应明确拒绝或转换为已约定动作，而不是悄悄省略；接收端则应拒绝不符合请求合同的数据，不能从旧日志猜补字段。这两层责任不因使用同一个类型声明而合并。

replacer 把 undefined 变 null，就解决清空了吗？

它只改变表示，不能保证后端愿意接收或按预期修改。自定义 toJSON 与 replacer 还会改变默认流程，应该用实际对象和项目封装重新核对，不能拿普通对象的默认结果为所有实例背书。尤其对象自己的转换可能先产生另一份值，再交给后续处理。

若计划引入统一 replacer，需要列出受影响的请求、缓存、日志和签名材料。相同工具函数被多处调用，不代表它们都允许缺失变空值；一个为了表单清空做的修改，可能改变缓存身份或其他接口的验证结果。上线迁移应按真实调用方逐一检查，而不是只替换一个函数就宣布结束。

命名也应具体。接口若有独立的清空操作，可以明确表达那个动作；若采用部分更新文档，则应把省略与明确空值的语义写进契约。不存在一种序列化器默认值能替所有字段决定保持、删除、继承或重置，这些是实体自己的业务含义。

数组变成 null，可以直接过滤掉吗？

先确认位置是否参与关联。若数组与另一份编号列表按位置对应，过滤一项会让后面所有对应关系偏移；保留长度也不代表该项仍有有效内容。需要按稳定身份建模时，应把身份和数据放在同一记录，避免把序列化空位当成可以任意删除的噪声。

如果业务集合本来就允许忽略缺失项，也应有意选择过滤时点，并检查结果是否仍满足数量、身份和顺序要求。不要先过滤到请求不报错，再倒推用户原本就想删除那些位置。对空数组、只有空值与没有提交数组，也应按产品需要区分。

数字表示还有另一条独立边界，可参看JSON 解析与长编号。本题解决的是哪些字段穿过边界，不是数字精度；即使字段存在，也不能据此保证其内部数值没有变化。

拟议验收包括省略、undefined、null、空文本、数组位置、顶层不可表示值，以及真实 toJSON 或 replacer。逐项记录发送文本、接收结构、补丁动作与最终读取结果，另外覆盖校验失败和旧客户端。本文没有运行这些检查。清空操作的完成依据，应是接口约定的动作确实生效，而不是对象里曾经出现过某个属性名。
