对象里有 undefined，JSON 请求为什么少了字段？

默认 JSON 序列化对对象和数组中的 undefined 处理不同；缺失、null 与清空应有明确接口语义。

正文

JSON.stringify 对对象中的 undefined 属性会省略，对数组里的对应值则转换为 null，接口应明确缺失与清空的区别。发送前看到的 JavaScript 对象，不一定就是服务端收到的 JSON 数据；调试与验收需要检查真正的序列化结果。

同一种值在不同位置有不同处理

MDN 的 JSON.stringify 文档说明，undefined、函数和 Symbol 不属于有效 JSON 值；在对象属性中会被省略，在数组中会转换为 null。直接对某些这类值序列化，还可能得到 undefined，而不是一段 JSON 文本。文档同时介绍 replacer 和 toJSON 等自定义行为，所以本文讨论默认机制时，不把所有项目封装都视为完全相同。

假设设置表单允许用户删除一个可选备注，前端把属性设置成 undefined，并期待服务器清空旧值。如果请求里这个字段被省略，而接口把缺失解释为“不修改”，旧备注就可能保留。这个场景未经接口测试；结果取决于实际更新协议，不能反过来把它说成 JSON 本身规定了业务更新语义。

缺失、空值与空文本由接口定义

属性没有出现、属性值是 null、属性值是空字符串，可能分别代表保持、清空和输入为空，也可能有其他含义。必须在接口契约里明确，而不是让前后端各自选择习惯。把所有 undefined 统一改成 null，虽然能让属性出现在文本中，却可能触发此前不会发生的清空或校验行为。

数组中的位置也有业务含义。如果一个值变成 null，而不是整个元素被删除，后续处理就应检查是否允许该位置没有有效内容。不能只比较数组长度没变，就认定输入完整；同样，自动过滤空值也可能改变位置对应关系。序列化规则与业务集合规则应分开设计。

若使用自定义转换，应审查它是否同时影响日志、缓存和请求。某个调试工具展示完整对象，不代表真正发送时用了相同转换。记录中还应说明观察的是转换前对象、JSON 文本还是接收后结构，否则团队可能对着不同阶段的证据争论。

在网络边界检查实际承诺

建议测试正常值、属性缺失、显式 null、空文本以及数组内的不可表示值，分别写清服务端应该如何处理。对自定义 toJSON 或 replacer，还需检查它们是否隐藏必要字段或改变类型。本文没有运行这些测试，也没有提供某个项目已经通过的序列化日志。

提交逻辑应在发送前验证必需信息，服务端仍需独立验证接收数据。不要因为前端对象里有同名属性，就跳过请求级检查；更不要依据日志中的旧对象补猜用户原始输入。对于可能改变持久状态的请求，保留任务身份和明确的错误反馈，比默默填默认值更有助于恢复。

接口迁移时，需要检查旧客户端对缺失与空值的依赖。新增清空语义可能影响已有数据，不能只调整一个序列化工具函数就认为改动结束。应把字段契约、调用方与持久化行为一起验收。

数字精度则是另一条独立边界，可参看JSON 解析与长编号。本篇要解决的是哪些字段真正跨过了请求边界，以及服务端如何解释它们，而不是让序列化过程代替业务决定。
