URLSearchParams把加号变空格，原始值该从哪一层传入？

补充加号、空格、百分号与重复键的完整查询往返，区分原始值、编码文本和原始串身份。

正文

核心要点

  • 查询文本的加号按表单规则解析为空格。
  • 参数方法接收原始值并负责序列化。
  • 值相同不保证原始查询串相同。

解析查询文本时加号按表单编码变成空格；传原始值给append或set，才能让序列化层把数据加号编码为百分号形式。同样一个字符串，在“已经编码的查询文本”和“尚未编码的参数值”两个入口，承担的含义不同，不能任意交换。

URL标准的表单编码解析算法先把名称和值中的加号字节换成空格，再进行百分号解码。这不是URLSearchParams随机删掉字符，而是它按所接收的查询文本运行相应规则。原始值A+B如果先被拼成q=A+B，调用者已经没有明确表达那个加号是数据。

损失发生在读取之前，也可能发生在再次编码时

URLSearchParams参考用含加号的Base64示例比较了插值构造与append。前者解析查询语法，后者接收原始参数值并在序列化时处理特殊字符。修复应调整入口，不是每次读出后把所有空格改回加号；原值里也可能真的有空格。

假设分享标识允许加号、空格和百分号。原始值A+B C%中，两种空白相关字符并不等价。若解析后再统一替换空格，原来的空格也会被改成加号。接收方查不到对象时，应对照原始值、实际序列化文本与解析后值，而不是只看地址栏像不像一个有效链接。

反向错误是先对值执行encodeURIComponent，再把结果传给参数接口。它会把里面的百分号也当成数据编码；原始A+B就可能在一次解析后仍是字面A%2BB。重复解码看似能救这个样本，却无法判断另一份合法业务值是否本来就包含%2B。解码次数必须来自协议，不能靠结果“看着像编码”来猜。

一份带独立预期的完整往返样本

下面Node模块未执行，不发送请求，也不接触真实分享数据。每一行都预先写明原始值和期望序列化，不从待测解析结果再生成预期。保存为.mjs后可以用Node运行；它只检查该运行环境的URLSearchParams行为，不验证服务端框架或签名系统。

import assert from 'node:assert/strict';

const samples = [
  { raw: 'A+B C%', query: 'q=A%2BB+C%25' },
  { raw: '%2B', query: 'q=%252B' },
  { raw: '中文+ space', query: 'q=%E4%B8%AD%E6%96%87%2B+space' }
];
const observations = [];
for (const sample of samples) {
  const params = new URLSearchParams();
  params.append('q', sample.raw);
  const serialized = params.toString();
  assert.equal(serialized, sample.query);
  const parsed = new URLSearchParams(serialized).get('q');
  assert.equal(parsed, sample.raw);
  observations.push({ raw: sample.raw, serialized, parsed });
}
const preencoded = new URLSearchParams();
preencoded.set('q', encodeURIComponent('A+B'));
const encodedText = String(preencoded);
const repeated = new URLSearchParams([['tag', 'a+b'], ['tag', 'c d']]);
const repeatedText = String(repeated);
const counterexamples = {
  interpolated: new URLSearchParams('q=A+B').get('q'),
  encodedText,
  encodedValue: new URLSearchParams(encodedText).get('q'),
  repeatedText,
  tags: new URLSearchParams(repeatedText).getAll('tag')
};
assert.deepEqual(counterexamples, {
  interpolated: 'A B',
  encodedText: 'q=A%252BB',
  encodedValue: 'A%2BB',
  repeatedText: 'tag=a%2Bb&tag=c+d',
  tags: ['a+b', 'c d']
});
console.log(JSON.stringify({ observations, counterexamples }, null, 2));

正确路径让名称与值一直保持结构，只有序列化时才形成查询文本。重读之后与原始字面值比较，可以同时发现加号损坏、百分号被多解一层和中文处理问题。错误路径的断言也有价值：它证明教学样本期望发生什么，而不是把失败输入排除在报告之外。

重复键另有集合合同。get读取一项，不能替getAll验证全部标签是否保留，顺序是否有意义则由业务决定。参数API允许表达多值，不替服务端选择取首个、取末个还是数组。后端若采用不同解析方式，需要使用同一组输入独立验证，不能把本地往返通过外推到所有接收端。

代码中的console输出只是待执行格式，不是现有运行日志。实际执行时应保留版本、原始stdout与退出码，并将检查范围限定到这段纯API路径。它没有浏览器导航、网络传输、后端保存或真实分享入口；这些阶段各自需要对应证据。

参数里本来就有字面%2B，应该自动再解码吗？

不应自动猜测。它可能就是合法数据，参数协议需要说明收到的值处于哪一层。样本第二行刻意保留字面%2B，序列化成百分号也被编码的形式，重读后仍应是原来的三个字符。若接收端再解一次，就改变了这份原始值的含义。

因此，组件之间最好明确传原始值还是完整查询文本。一个函数接收“标识值”，就不应要求调用方自行拼q=；一个函数接收已有URL，则应先按URL结构取searchParams。URL基地址解析说明完整地址不是字符串连接结果，查询也不应该吞掉路径和片段的独立边界。

迁移时还应保留旧链接样本，而不是只测试新生成的正确值。旧生成器可能已经把加号写成了裸字符，接收方无法凭一个空格可靠判断原来是哪一种字符。是否提供兼容入口、重新签发链接或拒绝无法确定的数据，需要协议所有者决定；不能用全局替换悄悄改写历史身份。

业务值一样，原查询字符串也一定一样吗？

不保证。URL的search与URLSearchParams序列化可以对空格等采用不同合法表示；方法参考展示过修改或排序参数以后，值不变而地址文本变化的情况。按照值比较的业务逻辑与按照原始字节比较的签名、缓存身份，不是同一份合同。

若某层签名的是原查询文本，就要核对排序、编码形式和重复键表示是否属于签名输入。这里是条件化检查，不是声称任何序列化变化都会让所有签名失效。接收端若本来就按约定规范化，可能采用另一套一致规则；关键是两边实际使用相同的协议，而不是各自多做一次“清理”。

创建可点击链接也没有自动建立持久资源。Blob URL生命周期讨论另一种地址责任，不能因为字符串能放进href就认为它适合永久保存。查询参数本题关注值是否保留，访问权限、有效期和资源存在还要独立确认。

日志应使用明确无秘密的教学值。为了定位一个加号问题而公开完整签名链接，会引入另一项责任；可保留足够的脱敏表示与字符差异，而不把真实令牌写进构建产物。本文的固定样本不代表任何实际用户数据。

待执行验收依次比较正确原始值入口、错误插值、预编码再传、重复键与原始查询表示变化。每项写清比较的是值还是字节，并检查真实接收端是否遵循同样规则。本次重写保留原发布日期、translation_key与URL，没有运行网络或业务测试。先确定输入层次，再让唯一明确的一层编码，才能保住加号而不误改空格和百分号。
