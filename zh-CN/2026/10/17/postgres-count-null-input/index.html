COUNT(*) 和 COUNT(字段) 为什么给出不同数量？

COUNT 的行数与非空输入口径不同；先检查过滤、连接基数和指标单位，再讨论数量与性能。

正文

COUNT(*) 统计输入行，COUNT(表达式) 统计表达式非空的输入，指标名称和查询应采用同一口径。两种数量不同，不一定是数据库算错；先确认每一行代表什么，以及被计数表达式是否允许为空，再判断差异是否符合预期。

同一批输入也能得到不同数量

PostgreSQL 18 的聚合函数文档分别定义两种 count：星号形式统计输入行数，表达式形式统计该输入值不为 NULL 的行数。这个区别针对聚合接收到的行集合；数据在此前被过滤或连接后，输入集合本身也可能已经变化，不能把最终计数直接理解为原始表的记录数。

假设报表显示“已提交申请数量”，查询却统计某个可选联系方式。没有填写该字段的申请不会被这项表达式计入，于是数量少于实际提交记录。这里是未经执行的分析示例，不代表某张真实报表存在错误。如果指标原本就是“提供联系方式的申请数”，同一个查询反而可能符合用途。

先给指标写出完整句子

指标定义最好说明对象、筛选条件、观察时间与计数单位。是申请记录、不同申请人，还是具有某项信息的申请？这些问题需要不同查询，不能只通过把字段替换成星号解决全部差异。一个人提交多笔申请，按行统计与按人统计也不是同一指标。

连接查询尤其需要审查输入基数。连接后同一申请可能对应多条明细，COUNT(*) 会统计这些输入行，而不自动恢复为一笔申请。要得到业务对象数量，应根据真实关系选择聚合方式并验证，不能在看见数字偏大以后随手加入去重，掩盖关系建模或条件错误。

把空字段替换成零，也不是通用计数修复。若表达式结果从 NULL 变为非空，计入范围就可能改变；这应是明确的业务决定，而不是为了让两个数字看起来一致。未知、未提供和实际为零，在不少业务中需要保持区别。

用小而有解释力的样本验收

建议准备字段完整、字段为空、多条明细对应同一对象、以及没有匹配数据的样本。先人工写出预期输入行和各项指标，再检查查询结果。这里没有执行 SQL，也没有测量查询性能；样本只是验收设计，不是数据库输出记录。

对外报告也应保存查询版本和字段含义。今天把指标改成另一种 count，可能让历史曲线出现变化，但这不证明业务增长或流失。若要比较前后，应说明口径变化并在可行时重算，而不是把技术修复包装成真实产品成效。

性能优化应在语义确定以后讨论。索引、查询计划和数据规模会影响成本，不能凭函数名称承诺哪一种总是更快。为了一个较低执行时间改变指标含义，得到的是另一个问题的答案，而不是原指标的可靠优化。

数组总量与维度长度的差异可参看数组计数口径。计数验收的关键是让数字能够被输入集合与业务定义解释，而不只是让两列数字碰巧相等。
