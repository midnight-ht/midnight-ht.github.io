COUNT(*) 和 COUNT(字段) 为什么给出不同数量？

用部门申请报表对齐 PostgreSQL 行数、非空联系方式与不同申请人数，检查左连接占位行、空文本和附件扩行。

正文

核心要点

  • COUNT统计的是到达聚合阶段的输入，不自动恢复原表对象数。
  • 左连接空部门需数右侧非空身份，空字符串仍是非空输入。
  • 申请、申请人和联系方式采用不同单位，附件扩行后重新核对。

COUNT(*) 数聚合输入行，COUNT(字段) 只数该字段非空的输入。数量不同时先确认每行是什么；若输入来自左连接，星号还可能数到没有申请的部门占位行。把可选字段换成星号，可能修正漏计，也可能让另一个指标开始多算。

假设后台要同时显示各部门的申请数、提供联系方式的申请数与不同申请人数。三个数字可以来自同一批数据，却不必相等。申请人可能提交多次，可选字段可能为空，没有申请的部门也可能需要留在列表里。查询前先给这些输出命名，比看到差异后随手加 DISTINCT 更容易解释结果。

COUNT 接收到的行，已经经过过滤与连接

PostgreSQL 18 聚合函数文档分别定义星号形式与表达式形式：前者统计输入行，后者统计表达式非空的输入。这里说的不是原表永远有几条，而是到达聚合阶段的集合。WHERE 可能先删掉行，连接也可能增加行，函数不会自动恢复业务对象的原始数量。

同版聚合表达式说明还说明 COUNT(DISTINCT 表达式) 统计不同的非空输入值。若指标叫申请人数，通常应围绕真实申请人身份定义；按名字去重可能把同名不同人合并，按申请编号去重则仍是在数申请。

所以评审需要一句完整口径：在指定部门、状态、观察时间与授权范围内，数申请记录，还是申请人，还是提供某项信息的记录。日期或状态条件也要和返回指标一致。更换函数无法替团队决定哪些草稿、撤销记录或不可见对象属于分母。

一份同时保留空部门的完整查询

下面是未执行的教学 SQL。示例约定真实申请编号非空；部门三没有申请，部门一同一人申请两次，其中一条没有联系方式。部门二的联系方式是空字符串，刻意和 SQL NULL 分开。

WITH departments(id) AS (VALUES (1), (2), (3)),
applications(id, dept_id, applicant_id, contact) AS (
  VALUES (11, 1, 101, 'ada@example.test'::text),
         (12, 1, 101, NULL::text),
         (21, 2, 201, ''::text)
)
SELECT d.id AS department,
       count(*) AS joined_rows,
       count(a.id) AS applications,
       count(a.contact) AS nonnull_contacts,
       count(DISTINCT a.applicant_id) AS applicants
FROM departments AS d
LEFT JOIN applications AS a ON a.dept_id = d.id
GROUP BY d.id
ORDER BY d.id;

按输入推演，部门一的四项计数应为二、二、一、一；部门二为一、一、一、一；部门三为一、零、零、零。部门三的星号数一，是因为左连接保留了一条右侧补空的结果行，不是系统凭空产生了申请。count(a.id) 在该例的非空编号约定下才表达真实匹配申请数。

这组结果应按部门分别验收，不能只比较总和。丢掉一个空部门、又把另一个部门扩成多行，汇总数量可能碰巧接近预期；实际输出对象却已经错了。应同时核对部门集合与每项计数对应的申请、申请人身份。

空字符串算没填写，COUNT 会自动排除吗？

不会。空文本是非空输入，部门二的 contact 因而仍被计入。如果业务把空字符串视为未填写，应明确加入这一条件，例如在正式查询中用 FILTER 同时要求 contact IS NOT NULL 与 contact 不等于空字符串。这是新增口径，不是 COUNT 原来算错。

只有空格的字符串是否算已填写，还需要独立规则。自动去除空白也会改变保存值或比较含义，应由输入校验与规范化合同决定。不能把“非空数据库值”直接命名为“有效联系方式”：格式正确、能够联系到本人、已经验证过，是更强的业务条件，需要各自证据。

COALESCE 也不是计数补丁。将 NULL 换成空字符串后，count 表达式会看到非空值，甚至可能将左连接占位行计进去；它没有发现新的申请，只是改变了输入是否非空。若只是希望页面显示数字零，count 在无匹配输入时本就有零这一结果，不应为显示而改写被计数字段。

加上附件后，为何申请数又涨了？

假设申请十一有两个附件，申请十二有一个附件。直接把申请再连附件，部门一可能出现三条明细，星号和非空申请编号都会重复计入申请十一。联系方式也可能随之重复，虽然申请人根本没有补填第二份号码。先前对空值的理解没有失效，变的是聚合输入粒度。

如果指标仍然按申请计数，应先形成每申请一行的集合；附件只是过滤条件时，可以考虑存在性判断，若要附件数量，则单独按对应粒度汇总。count(DISTINCT a.id) 可以表达某种唯一申请数，但不应成为隐藏错误连接的统一修法；其他金额、状态或联系方式指标仍可能被扩行影响。

筛选位置同样重要。若要保留所有部门并仅统计已提交申请，应把“什么叫合格匹配”定义清楚；把右表状态放到 WHERE，可能让无匹配部门消失。站内二〇二六年十月十八日的LEFT JOIN 条件位置进一步区分匹配、过滤与补空行，本篇不把换一个 count 当成连接修复。

把指标验收写成身份集合

拟议验证先列出每个部门应有的申请编号集合、联系方式满足条件的申请集合与申请人集合，再计算各自大小。加入 NULL、空字符串、同一人多申请、空部门、一申请多附件五类样本，分别检查结果值与行是否存在。本文没有执行 SQL，以上数字都是给定输入下的纸面预期。

修改口径后应保存查询版本与适用日期。旧曲线突然增加，可能只是从非空字段数改成申请数，不能据此宣称业务增长。若需要历史可比，应说明差异并评估能否按新口径重算。性能则在语义确定后另用实际计划与负载比较，不凭函数名承诺某种形式总是更快。

导出文件与页面还应采用同一口径。如果页面显示申请数，导出却继续统计联系方式，下游就会拿两个都叫“数量”的字段作错误对账。可以在接口或报告说明里保留指标名称、范围与版本，让接收者知道自己拿到哪一种集合的大小；不要求向每个用户暴露全部内部数据。可靠计数应能回到这些定义，而不是让几列数量勉强相等。
