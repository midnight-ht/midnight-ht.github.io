容器停机信号为什么没到应用进程？

排查停机先确认容器主进程和信号接收者，再分别验证包装脚本、应用清理与平台宽限期。

正文

核心要点

  • docker stop 作用于容器主进程，入口层级会决定应用是否直接收到信号。
  • exec 会把包装进程替换成应用，信号接收者改变，但不会替应用实现优雅退出。
  • Docker 的停止超时和 Kubernetes 的终止宽限期属于等待预算，不能修补错误的进程树。

容器收到了 SIGTERM，服务日志却没有退出记录；这时先看进程树，而不是先把宽限期加长。排查要回答三个不同问题：运行时把停止信号发给谁，应用是否实现了停止接单和收尾，以及平台会等多久。把三件事混在一起，常见结果是服务仍没处理完任务，超时却被延长了。

先确认信号发给了谁

Dockerfile 的 ENTRYPOINT 有 exec 和 shell 两种形式。Docker 官方 ENTRYPOINT 文档把 exec 形式写成 JSON 数组，例如 ENTRYPOINT ["node", "server.js"]；shell 形式则是普通命令文本。对 shell 形式的 ENTRYPOINT，Docker 文档明确说明它会作为 /bin/sh -c 的子命令启动，shell 不会把信号传给目标可执行文件。因此 docker stop 发给容器主进程的 SIGTERM，不等于应用进程收到 SIGTERM。这里要看实际启动结构，而不能只从“容器已收到停止请求”推断应用已经被通知。

ENTRYPOINT 和 CMD 也要一起读。exec 形式的 ENTRYPOINT 可以接收 CMD 或 docker run 追加的参数；shell 形式的 ENTRYPOINT 则忽略这两处提供的命令行参数。如果 exec 形式的入口配上 shell 形式 CMD，Docker 会把 CMD 包装成 shell 调用，入口程序收到的参数形态就可能与预期不同。exec 形式不会自动运行 shell，所以 $HOME 这类变量替换不会凭空发生；确实需要 shell 语法时，应该显式调用 shell，并把这层进程写进设计和排查记录。

实际运行时还可能覆盖镜像默认命令或入口。比如本地用镜像默认配置启动，集群启动配置却传了 command/args；这时只检查 Dockerfile 得到的不是最终进程树。排查清单至少要记录镜像中的 ENTRYPOINT/CMD、运行时覆盖值、容器内 PID 与 PPID，以及服务进程的子进程。本文引用的是 Linux 容器语境；不同运行时、操作系统和平台配置要按各自文档核对。

exec 解决进程交接，不负责应用收尾

包装脚本并不天然有错。它可能需要检查挂载、渲染配置、设置权限或校验密钥。问题在于脚本完成这些工作之后，怎样把主进程责任交给应用。若脚本只执行 node server.js 并等待，shell 或脚本仍可能位于应用之前；信号是否被转发取决于实际进程关系和脚本行为。把最后一步改为 exec node server.js，会让当前脚本进程被应用替换，如果 wrapper 原本就是容器主进程且前面没有 init，应用会成为该 PID 上的接收者；配置了 --init 时，信号先到 init，再由它转发。Docker 的 exec 形式 ENTRYPOINT 则直接指定容器入口可执行文件。

这个交接带来一个很实际的取舍：exec 之后原脚本不会再以父进程身份运行。若脚本原本打算在应用退出后删临时文件、汇总退出码或执行补偿，那么用 exec 后这些代码不会继续执行。需要后置监督时，应明确采用可正确转发信号、等待并回收子进程的 supervisor，或把可安全重入的清理移动到容器外部的生命周期机制。不能既认为 wrapper 已被替换，又期待它继续在应用退出后做父进程工作。

一个假设场景：镜像启动时先从只读挂载读取模板，生成运行配置，然后启动 Node API。配置生成失败时，入口应以非零状态退出，不能继续启动一份拿到旧配置的服务。配置成功后，若 Node API 是唯一需要长期运行的进程，脚本可以 exec 交接；如果应用还会启动 worker 子进程，就要继续判断应用能否转发停止信号、等待 worker 结束，以及退出时谁负责处理未确认的任务。这个例子是设计推演，不是本文实际构建或运行过的镜像。

PID 1 和多个子进程是另一类问题

把应用放到 PID 1 的位置，只解决“谁直接作为主进程运行”的问题，不自动证明它会按期望处理信号、退出码和子进程。Linux 对 PID 1 有特殊的信号与孤儿进程收养语义；应用对默认信号动作的依赖可能与普通进程不同。一个进程监听 SIGTERM 并开始关闭，也不等于它会把信号继续传给所有 worker，或者等待它们结束。需要依据应用运行时的进程模型验证这些行为。

若容器里确实有需要管理的多个进程，Docker 的 --init 可在容器内提供轻量 init。Docker run 文档说明该选项会在容器内运行 init 进程，承担转发信号和回收进程等初始化责任；这能解决部分 PID 1 与 zombie 回收问题，但不能代替应用定义数据库事务、队列确认或 HTTP 请求的关闭语义。另一种做法是用专门 supervisor，但它增加了一个需要配置、监控和测试的生命周期组件。判断依据不是“多进程看起来不规范”，而是是否有明确的父子关系、信号传播与退出等待责任。

反例是将单个服务命令改成 exec 后，团队看到主进程能收到 SIGTERM，就认定停机问题已结束。若服务在处理请求时立刻退出、队列消费者提前确认了消息、或子进程仍被强制终止，信号传递这一层通过了，业务排空仍失败。进程级检查与业务级检查要分别设计：前者观察信号、进程状态和退出码；后者观察停止接单、在途操作完成、消息确认或可重试状态。

停机时间不能修补错误的信号路径

Docker container stop 文档说明 docker stop 会向容器主进程发送停止信号，等待配置的宽限时间，再在期限到达后发送 SIGKILL；可通过 STOPSIGNAL 或运行时选项改变停止信号及超时。增加超时只会给已经收到信号的进程更多时间。如果应用没有收到信号，它可能在等待期间继续工作，直到最后被强制结束。因此先确认信号接收者和进程路径，再根据真实关闭工作估算预算。

Kubernetes Pod 终止流程又增加了一层编排步骤：容器配置 preStop 时，hook 必须在 TERM 发出前完成，宽限期倒计时从 hook 之前就开始；默认宽限期是 30 秒。默认路径下，kubelet 请求运行时向各容器的 PID 1 发送 TERM，超过宽限期仍未结束才强制终止；镜像 STOPSIGNAL、运行时以及受版本和 feature gate 限制的容器 stopSignal 配置都可能改变实际信号，必须核对集群条件。一个 Pod 有多个普通容器时，kubelet 的停止请求由运行时异步处理，顺序不能被假定为固定。Kubernetes 对声明为 sidecar 的容器另有特殊终止规则：它们会等主容器结束后再接收停止信号，并按定义顺序的逆序处理；“业务上叫 sidecar”本身不足以证明使用了这项容器生命周期语义。平台的 hook 和总预算可以协助排空流量，却不能绕过入口 shell 或让一个未实现优雅退出的应用自动变得正确。

选择 hook 还是应用内停机逻辑，要看副作用和协调边界。preStop 适合触发与容器外部可见的准备动作，例如让实例暂时退出就绪流量，但它不是一个无限期的清理窗口；应用接到信号后仍需关闭监听器、处理在途请求并停止后台 worker。若 hook 与应用各自等待同一件事，时间会相加并挤占同一个宽限预算。设计时要写出总时间线：hook、流量摘除传播、应用排空和进程退出各自可能耗时多少，并为波动留出余量，而不是把整个宽限期重复分配给每一步。

按责任分层验证

Kubernetes 容器生命周期钩子文档还明确指出，preStop 和正常停止共用同一个宽限期，hook 耗时过长会挤压应用接收 TERM 后的剩余时间。下面是一份建议的验证计划，不代表已经在本机或生产环境执行。先在受控环境启动与目标镜像相同的命令，记录进程树和入口参数。触发停止时，让应用处在空闲状态和有在途工作的状态各执行一次，分别记录信号到达时间、是否停止接受新请求、现有工作如何完成、进程退出码与总耗时。再模拟配置生成失败和启动后取消，确认失败不会误报为成功启动，也不会留下孤儿 worker。每一步都应使用可观察的信号日志或进程状态，而不是只看编排平台显示的“正在终止”。

如果测试只在空闲容器成功，业务请求中的关闭路径仍是未知；如果 Docker 本地通过而 Kubernetes 失败，应检查 command/args 覆盖、preStop 时间、就绪状态变化和 grace period，而不是立即再改入口。如果进程确实收到 SIGTERM 但超时退出，重点转到应用关闭流程和正在等待的资源；如果主进程退出后 worker 留下，则回看父子进程管理或 init/supervisor 选择。每个观察结果只支持它所在的那一层，不能用一次通过替整个容器生命周期背书。

完成上述观察后，才决定是否增加 Docker stop timeout 或 Kubernetes terminationGracePeriodSeconds。若新增预算，应注明依据的实测工作项与上限，并确认部署平台实际采用了该配置。滚动更新期间的流量排空预算还涉及平台侧状态变化，可参阅终止宽限期的预算。本文未执行 Docker 或 Kubernetes 实验，没有虚构日志、退出耗时或生产故障案例。结论可以落在一张具体的进程关系图和关闭验收表上：谁收到信号、谁负责子进程、谁等待哪些工作、超时后谁会强制结束。EOF

A container receives SIGTERM, but the service has no shutdown log. Inspect the process tree before increasing the grace period. Three separate questions need answers: which process the runtime signals, whether the application stops admission and finishes its work, and how long the platform waits. Mixing them often produces a larger timeout while requests or jobs still fail to drain.

First identify the signal recipient

Dockerfiles support exec and shell forms for ENTRYPOINT. Docker documents the exec form as a JSON array, such as ENTRYPOINT ["node", "server.js"]; the shell form is a command string. Docker's reference says a shell-form ENTRYPOINT starts the command as a subcommand of /bin/sh -c, and that shell does not pass signals to the target executable. Therefore a SIGTERM sent by docker stop to the container's main process does not establish that the application received it. Inspect the actual launch structure instead of inferring delivery from the fact that a stop request began.

Read ENTRYPOINT and CMD together. An exec-form ENTRYPOINT can receive arguments appended by CMD or docker run. If CMD is shell form, however, Docker wraps it in a shell invocation, so the entrypoint may receive different arguments from the bare command and parameters you expected. Exec form also does not invoke a shell automatically: variable expansion such as $HOME does not happen by itself. If shell syntax is required, call a shell explicitly and include that process in the design and diagnostic record.

Runtime configuration can override the image defaults. A local run may use the image's default command while a cluster supplies command or args; inspecting only the Dockerfile then does not reveal the final process tree. Record at least the image ENTRYPOINT/CMD, runtime overrides, container PID/PPID relationships, and the service's children. The claims here concern Linux container behavior in the cited documentation; verify other runtimes, operating systems, and platform configurations against their own specifications.

exec transfers process ownership, not cleanup behavior

A wrapper is not inherently wrong. It may check a mount, render configuration, set permissions, or validate a key before starting the service. The important decision is how it hands the long-running process responsibility over. If a script simply runs node server.js and waits, a shell or script may remain in front of the application; whether signals are forwarded depends on the actual process relationship and wrapper behavior. Changing the final step to exec node server.js replaces the wrapper process with the application. The application then occupies that process position and becomes the direct recipient. Docker's exec-form ENTRYPOINT is another way to specify an executable directly.

That handoff has a concrete tradeoff: after exec, the original script no longer runs as the parent. If it was expected to remove temporary files, collect an exit code, or perform compensation after the application exits, that code will not continue after replacement. When post-exit supervision is necessary, use a supervisor that correctly forwards signals, waits for children, and reaps them, or move safe cleanup to an external lifecycle mechanism. Do not assume both that the wrapper has been replaced and that it will later resume parent-process work.

Consider a hypothetical image that reads a template from a read-only mount, renders a runtime configuration, and then launches a Node API. If rendering fails, the entrypoint should exit nonzero rather than start a service with stale configuration. If rendering succeeds and the API is the only long-running process, the script may hand off with exec. If the application also starts workers, determine whether it forwards termination, waits for each worker, and handles unacknowledged work on exit. This is a design example, not an image built or run for this article.

PID 1 and child processes are separate concerns

Putting the application in the PID 1 position addresses which process runs as the container's main process. It does not prove that the application handles signals, exit status, or children correctly. Linux gives PID 1 special signal and orphan-adoption semantics; relying on a default signal action may behave differently from relying on an ordinary process. A process can handle SIGTERM and begin closing without forwarding it to every worker or waiting for them. Verify those behaviors against the application's process model.

When a container genuinely needs to manage multiple processes, Docker's --init option can provide a lightweight init process. Docker documents it as handling init responsibilities such as signal forwarding and reaping processes. That can address some PID 1 and zombie-reaping concerns, but it does not define how the application closes database transactions, acknowledges queue messages, or stops HTTP admission. A dedicated supervisor is another option, but it adds a lifecycle component that must be configured, observed, and tested. Choose based on explicit parent/child relationships, signal propagation, and exit-waiting responsibilities—not a blanket rule that multiple processes are always wrong.

A counterexample is changing a single service command to exec, seeing the main process receive SIGTERM, and declaring shutdown fixed. The service might exit immediately during a request, a queue consumer might acknowledge a message too early, or workers might still be killed forcibly. Signal delivery passed; business draining did not. Design separate process-level checks (signal, state, exit status) and business-level checks (stop admission, finish in-flight work, acknowledge or make messages retryable).

A longer timeout cannot repair a missing signal path

The Docker CLI documentation describes docker stop as sending a stop signal to the container's main process, waiting for its configured grace period, and then sending SIGKILL if the deadline expires. The stop signal and timeout can be changed through STOPSIGNAL or runtime options. A longer timeout gives more time only to a process that received the signal and is shutting down. If the application never received it, it may continue working until it is forcibly ended. Establish the recipient and process path first, then estimate the budget from actual shutdown work.

Kubernetes adds an orchestration layer. Its Pod lifecycle documentation says that when a container has a preStop hook, the hook runs first and consumes time from the Pod's termination grace period; the documented default grace period is 30 seconds. The kubelet and runtime then send the termination signal to the container's main process, and force termination follows when the grace period expires. With multiple ordinary containers in a Pod, do not assume a fixed shutdown order. A sidecar is not guaranteed to finish before the application. Hooks and total budgets can help drain traffic, but cannot bypass an entrypoint shell or make an application with no graceful-shutdown behavior correct.

Choose between a hook and in-process shutdown logic based on side effects and coordination boundaries. A preStop hook can trigger externally visible preparation, such as making an instance unready, but it is not an unlimited cleanup window. After receiving the signal, the application still needs to close listeners, drain requests, and stop workers. If the hook and application each wait for the same action, both periods consume one grace budget. Write a timeline: hook execution, readiness propagation, application draining, and process exit each have a possible duration. Leave room for variation instead of allocating the full budget repeatedly to each step.

Verify each responsibility separately

The following is a proposed test plan, not a test performed on this machine or in production. In a controlled environment, start the same command as the target image and record the process tree and entrypoint arguments. Trigger termination once while idle and once with work in flight. Record signal arrival, whether new requests stop, how current work completes, the exit code, and total duration. Also simulate configuration-render failure and cancellation after startup; verify failure is not reported as a successful launch and that no worker is orphaned. Observe signal logs or process state rather than relying only on an orchestrator's “terminating” status.

If only an idle container stops cleanly, the business-work path remains unknown. If Docker works but Kubernetes does not, inspect command/args overrides, preStop duration, readiness changes, and the grace period before rewriting the entrypoint again. If the process received SIGTERM but timed out, examine application shutdown and the resources it is waiting on. If the parent exits while workers remain, revisit process management or the init/supervisor choice. Each observation supports only its own layer; one passing test cannot certify the entire container lifecycle.

Only after those observations should you decide whether to increase Docker's stop timeout or Kubernetes' terminationGracePeriodSeconds. Tie any added budget to the measured work item and upper bound, and verify that the deployed platform actually applies the setting. Rolling-update draining also depends on platform state transitions; see Kubernetes termination budgets. No Docker or Kubernetes experiment was executed for this article, and no logs, exit times, or production incident are claimed. The deliverable can be a process diagram and shutdown acceptance table: who receives the signal, who owns each child, who waits for which work, and who enforces the final deadline.
