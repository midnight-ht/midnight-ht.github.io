工作流被路径过滤跳过，为什么 PR 仍在等检查？

工作流过滤跳过可能让必需检查待定；区分作业跳过与实际成功，让门禁对应当前提交和真实结果。

正文

GitHub Actions 工作流因路径过滤没有运行，不等同于它所对应的必需检查已经成功。分支规则仍可能等待该检查，导致 PR 无法合并。设计门禁时，需要区分工作流没有触发、作业被条件跳过和作业实际通过，避免把三种状态混成一个绿色结果。

跳过发生在哪一层很重要

GitHub 的必需状态检查排查文档说明，因路径、分支或提交信息过滤而跳过的工作流，其相关检查会保持待定并阻止合并；被条件跳过的作业则报告成功。文档还提醒，依赖失败作业的后续作业可能被跳过，需设计能够识别前置失败的必需检查。这些行为不能用“反正没跑”统一解释。

假设仓库把某个构建检查设为必需，同时只在特定目录变化时触发工作流。一条只改其他目录的 PR 并没有触发它，但分支规则仍等待同名结果。这时等待更长时间不会产生原本没有调度的检查。本文没有修改某个真实仓库的规则，也没有执行这种 PR 场景。

首先应核对必需检查名称、工作流触发条件与实际变更路径，而不是反复重新提交相同内容。当前提交身份也很重要，旧提交上曾经通过的检查不能代表后来修改后的提交已经通过。门禁要与准备合并的版本对应，避免把历史绿标当作当前批准。

优化成本不能让门禁失去结果

团队可以只运行受影响的测试，但必需门禁仍需要对每次相关提交产生清楚、可信的结论。一种设计方向是保持汇总检查可观察，内部再根据影响范围决定执行哪些工作。这里是流程建议，不是复制即可正确的工作流配置；实际实现还要处理失败、取消、条件跳过与检查命名。

汇总作业存在，也不表示它会正确识别所有失败。如果前置任务失败后它直接被跳过，或只是无条件报告成功，就可能留下错误的门禁含义。应明确哪些任务未运行是预期，哪些未完成应阻止合并，并在汇总时检查真正的结果，而不是只检查后续作业是否被调度。

对变化后的规则重新验证

拟议验收可以覆盖相关目录变化、无关目录变化、前置失败、取消与新提交。每一类都应记录预期门禁结果，并核对当前提交上的检查。若仓库使用合并队列，还需按该机制核对相应事件配置，不能以普通 PR 的结果推断队列场景已经覆盖。

这些检查没有在本文中执行，因此不提供合并成功或节省时间的数据。也不宜为了立即解除阻塞，悄悄取消本来需要的安全或质量门禁。应先决定哪个检查真实代表发布要求，再让触发与结果契约保持一致。关于同一版本发布任务的调度，可阅读部署并发与取消，门禁存在与部署完成仍是不同证据。
