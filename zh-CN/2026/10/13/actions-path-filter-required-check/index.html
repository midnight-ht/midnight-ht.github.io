路径过滤跳过了工作流，为什么必需检查还在等？

GitHub Actions 的 paths 过滤可以不创建工作流运行，因此必需检查可能一直待定；用始终可见、检查真实依赖结果的门禁保留安全边界。

正文

核心要点

  • 工作流级路径过滤不创建运行；关联必需检查可能保持 Pending 并阻止合并。
  • Job 级条件跳过会报告 Success，所以不能让可跳过的测试 job 单独代表完整门禁。
  • 把触发范围、受影响测试和最终必需结论分开设计，并把失败、取消和合并队列纳入验证。

如果 PR 只改了文档，GitHub Actions 因 paths 没有创建工作流运行，而分支规则又要求该工作流中的 build 检查，PR 可能显示“Waiting for status to be reported”。这不是构建慢，也不是重跑按钮能解决的问题：触发被过滤在工作流之外，必需检查没有得到可供分支规则判断的结论。让门禁可用的关键，是每个适用提交都能产生一个可识别的最终结果；节省测试时间应放在门禁内部，而不是让整个必需工作流消失。

“没有运行”发生在哪一层，决定状态含义

GitHub 在 push 和 pull_request 上支持 paths 与 paths-ignore。两者是工作流触发过滤器：若分支、提交信息或路径过滤让工作流整体跳过，相关检查会保持 Pending，要求该检查通过的 PR 会被挡住。官方还规定，同一事件不能同时写 paths 与 paths-ignore；要同时包含和排除路径，应使用 paths 内的正向与 ! 负向模式，且模式顺序会影响最终匹配。

Job 条件是另一层。GitHub 文档说明，job 被条件跳过时会报告 Success；一个 job 失败或跳过后，默认依赖它的下游 job 也会跳过，除非下游的条件允许继续执行。于是，“没跑测试”至少有三种不同情况：工作流没启动，某个测试 job 因为改动范围不相关而跳过，或上游故障让汇总 job 一起跳过。把它们都当成“测试通过”或都当成“还在等待”，都会误读门禁。

假设仓库把 build 设为必需检查，但工作流仅在 services/api/** 有改动时触发。一次只改根目录 README 的 PR 不匹配路径条件，工作流不会创建；分支规则仍然要求 build，所以不会自动把“不相关”解释成通过。等待更多时间不会补出缺失的运行。相反，如果工作流已经启动，而 build job 的 if 条件判定本次改动不影响它，GitHub 可能把这个 job 标成 Success。后一种状态确实结束了，但它只证明该 job 被跳过的规则执行完毕，不证明构建实际运行过。

把“做多少工作”和“门禁给什么结论”分开

较稳妥的结构是：对 PR 和需要检查的提交保持工作流触发稳定；先识别本次变更影响哪些测试；只对受影响范围运行昂贵任务；再由一个命名稳定的汇总门禁检查检测任务与所有相关测试的实际结果。这个汇总门禁才是分支规则要求的检查。路径选择可以减少无关测试，但对“不受影响”应有明确、可审核的判定路径，不应靠工作流完全不出现来表达。

汇总也不能只写“最后一个 job 成功就算成功”。例如 unit 因源码错误失败后，依赖它的 required job 按默认依赖规则可能一并跳过；若规则要求的是另一个名字，PR 又可能等那个永远不会报告的结果。GitHub 提供 needs 查看直接依赖的结果，也允许在 job 条件中使用 always() 让依赖失败或跳过后仍运行汇总逻辑。但 always() 即使在取消时也为真，GitHub 建议谨慎使用；它不该把“用户取消了验证”转换成放行。设计时要明确处理 success、failure、skipped、cancelled：只有受影响测试确实通过，或有证据的“不受影响”判定成功，最终门禁才成功；失败必须失败，取消至少不能变成成功。

这是一种结构建议，不是可直接复制到任何仓库的工作流配置。检测变更的 job 可能自身失败，矩阵测试可能部分执行，人工取消与并发取消也会改变结果。把测试 job 的名字直接设为必需项、又允许其条件跳过，往往让读者看到一个绿色状态，却看不见到底有没有执行。更清楚的契约是让必需项表示“针对本次提交，所需验证已经完成且结果满足策略”，而不是“某个名为 build 的 job 曾经启动”。

一个改动很小的例子，如何推演结果

设有 docs/**、app/** 两类改动。规则规定只改文档时可以不跑应用单测，但 required-ci 必须对每个 PR 给出结论。工作流不在顶层使用 paths 来屏蔽文档 PR，而是在运行开始后由变更识别步骤输出 app_changed。当它为真时执行测试；为假时将测试标记为预期跳过。required-ci 依赖变更识别和测试结果，并在适当状态条件下运行，逐项校验：识别失败就失败；app_changed=true 而测试失败或取消就不成功；app_changed=false 且识别成功时，才按已定义策略接受“无需应用测试”。它的对外检查名保持不变。

这项设计还容易漏掉一种边界。如果共享工作流文件、依赖锁文件或测试工具本身变化，而检测规则只关注 app/**，变更识别就可能错误地认定“无需测试”。因此测试范围不是目录匹配的同义词：应该把会改变测试含义的配置纳入影响映射，并对映射本身设有评审和回归样例。若路径规则用了否定模式，要按声明顺序检查正反例；GitHub 对分支与路径过滤同时配置时要求两类过滤都满足，不能以只通过其中一类推断工作流会运行。

怎样验证它不会放行失败，也不会卡住

在启用规则前，至少准备以下假设输入：只改 docs/**；只改 app/**；两类目录同时修改；修改影响映射或 workflow 本身；测试 job 失败；变更识别 job 失败；运行被取消；提交新 commit 后检查结果刷新。对每个输入先写预期：哪些任务应执行、哪些允许跳过、最终必需检查应是成功、失败、取消还是未报告。然后在测试仓库或受控 PR 上观察工作流运行与分支规则看到的检查名称和结论。本文没有在某个仓库执行这些验证，所以不声称该示例通过，也不提供节省时间或成功率数据。

如果使用 GitHub 合并队列，还要单独确认所需检查是否响应 merge_group 事件。GitHub 文档明确指出，合并队列需要独立的 merge_group 触发；普通 pull_request 检查并不自动代表队列生成的合并组也经过验证。否则 PR 页面上已有绿色检查，进入队列后仍可能没有队列要求的结果。

选择原则可以收敛为一句话：允许内部测试按影响范围跳过，但让外部必需检查持续可观察，并且只为真实通过或经过审核的“不适用”结论返回成功。每次调整触发器、路径模式、检查名称、依赖关系或合并队列配置，都要以最新提交重新验证这个契约。关于同一提交上的部署取消与互斥，另见部署并发与取消；部署任务是否完成，和 PR 必需检查是否给出可信结论，是两件事。
