下载文件名为什么不能直接当作本地路径？

把 Content-Disposition 文件名当作显示建议：由客户端独立决定写入目录、存储标识和可打开类型，并验证解码、路径边界与重名处理。

正文

核心要点

  • RFC 6266 把响应文件名定义为建议；解析出 filename* 或去掉路径片段，并没有授予它选择客户端写入位置的权限。
  • 更稳的设计先确定固定受控目录和服务端或客户端生成的存储标识，再把解码后的名称作为展示字段处理。
  • 展示名、内部身份、文件内容类型与打开策略是不同判断；安全扩展名也不能证明内容可信。

下载响应头里的文件名只是一条显示建议，不能替客户端决定写到哪个目录、覆盖哪个对象，或用什么程序打开内容。实现时应把四件事拆开：按 HTTP 规则解析名称；用本地策略生成展示名；用受控目录和独立标识确定实际存储位置；依据业务允许类型决定预览或打开方式。RFC 6266 明确要求接收方把 filename 与 filename* 当作 advisory，并确保名称不能让写入越过授权位置。编码解析成功，只说明字符如何表示，不代表路径、扩展名或内容可信。

响应头给的是名称，不是文件系统权限

Content-Disposition: attachment 可以附带 filename 或 filename*，供接收方在保存交互中构造建议名称。关于文件名参数的那一节说明，当两者同时存在且客户端支持扩展参数时，应优先选 filename*；这能携带更广的字符集，但老旧用户代理可能只看 filename。RFC 8187 定义扩展参数的 charset'language'value 形态，并要求发送端对扩展值使用 UTF-8、百分号编码不在允许字符集合内的字节。它解决的是 HTTP 参数的编码互通，和“这个字符串是否可以作为本地完整路径”是两项独立工作。

标准的安全边界不是模糊的字符串清洗建议：接收方不能因此写入自身无权访问的位置。规范列出 / 与 \\ 作为路径分隔符，并指出可以去掉目录片段，只保留最后一段作为候选名称；还要求警惕控制字符、首尾空白、点目录片段、波浪号、管道符和设备名等有特殊含义的值。只删掉当前操作系统习惯的分隔符并不充分，因为服务端名称可能跨系统传递，随后由另一种平台处理。关键是，即使名称中完全没有分隔符，也不能把它拼进任意目录或当作存储对象的唯一身份。

先决定存储位置，再处理候选展示名

设想一个桌面同步工具要下载合作方生成的月度报表。响应给出两个父目录片段、一个 shared 子目录和一个可执行文件扩展名，业务界面希望展示可辨认的名称。脆弱的路径是“下载目录 + 响应文件名”：它把远端输入同时交给了目录选择、对象命名和扩展名决定。只删除一个父目录片段也不可靠；嵌套编码、反斜线、绝对路径、平台特殊文件名或替换后残留的片段，都可能令不同层理解不一致。

更可控的流程先由应用配置固定下载根目录，再为本次任务分配随机 ID 或其他不可由响应控制的存储名，例如 job-8f31.bin。远端给出的名称经解析和展示规则处理后，仅作为元数据保存；确认完成后，界面把它显示为“2026年10月报表”，而不是用它反向重建目标路径。若产品确实要允许用户指定相对名称，先完整解码一次，按目标系统解析成绝对规范路径，再确认结果仍位于下载根目录之内，并只使用已经验证的那个解析结果。OWASP 的路径遍历指南主要讨论应用把不可信输入用于服务器文件系统路径；这里借用的是同一条路径包含原则，不代表该指南定义了桌面客户端规则。它提醒，简单过滤父目录片段会漏掉反斜线、后续解码和绝对路径；客户端仍须按自己支持的操作系统验证解析结果。如果业务允许，优先以 ID 查表映射真实路径。

这套例子是设计说明，不是本机下载程序的实测结果。它也不要求用户看到随机 ID：存储身份可以隐藏，展示名称可以保留中文。分开两者能够解决两个不同的问题：ID 防止两个远端文件同名时互相覆盖；展示名仍可表达来源和时间。若产品选择“同名时询问”，询问策略需要覆盖跨目录重名和 Unicode 归一化后相同的名称；若选择自动改名，应明确采用序号、时间戳还是冲突 ID，并保证用户可找到原对象。静默覆盖不应作为默认的兼容补救。

filename* 可读，不等于内容可以安全打开

该标准还警告，依赖扩展名决定文件类型的平台不能直接信任服务端后缀；规范举例说明，不安全的扩展名可能导致文件保存后被危险地打开。一个响应可以提供 filename*=UTF-8''report，同时标注看似合理的媒体类型，但这些信息都来自同一响应，并不能独立证明字节确实是 PDF，也不能说明它适合当前客户端自动打开。文件名应该先展示给用户；是否允许预览、交给何种处理器、是否隔离或扫描，需要由产品的内容策略与验证步骤决定。

例如，一个只接受 PDF 的报表入口，可以把不匹配预期的下载保存在隔离区域，或者拒收并说明原因；如果要标记为 PDF 扩展名，必须先有能支持“内容属于允许类别”的检查。只根据响应头把可执行文件扩展名改成 PDF 扩展名只是改标签，并没有转换或验证字节；Content-Type 与后缀即使彼此一致，也仍然是响应元数据，不等于对负载格式的独立验证。反过来，格式检查通过也不能使一个来自不可信来源的宏文档自动变得安全。是否预览、隔离或打开，还要遵循产品的内容策略。若客户端并不检查内容，不要把“已下载”写成“文件安全”。

名称解析还需要明确失败策略。缺少两种 filename 参数、重复参数、非法百分号序列、无效 UTF-8、首尾空白、控制字符、点目录名以及超长名称，都应该落到固定的产品决策：使用“download”加受控 ID 的默认展示名、仅展示可安全渲染的文本，或拒绝这次保存。该标准把重复同名参数列为无效字段；具体客户端选择忽略、降级还是拒绝，应明确记录。不要在解析失败时回退到未经校验的原始 header，也不要对同一字符串在解析、路径检查和最终写入之间反复解码。对于文件系统会特殊处理的名称，跨 Windows、macOS、Linux 的具体规则和浏览器行为必须在目标平台测试；RFC 指明了风险种类，却不保证各实现的名称清理方式完全一致。

如何验证，而不是只看保存提示

先建立一张职责表：响应 parser 负责按 RFC 6266 / 8187 取候选值；展示层负责控制字符与可辨识显示；存储层决定根目录、对象 ID、重名和覆盖；内容处理层决定媒体类别、预览、打开与隔离。测试时可以使用一个临时目录，依次覆盖 filename 与 filename* 同时出现、中文及空格、缺失或冲突参数、父目录片段、反斜线、绝对路径、百分号编码、点目录名、设备名、首尾空白、控制字符、极长字符串、同名文件与伪造扩展名。对每一例记录最终解析名称、目标绝对路径、是否在根目录中、对象是否被覆盖、实际响应字节的类型检查决定，以及用户看到的错误。

测试路径边界时不能只断言名称“不含父目录片段”；应检查实际解析后的路径组件，并包含编码解码顺序和符号链接的适用条件。OWASP 指南建议先规范化完整目标并验证其仍在固定基目录下，而且后续直接使用已经检查过的路径；如果目标平台允许路径中出现符号链接，还要考虑检查与打开之间的竞态。对于直接由浏览器保存的普通下载，应用本身可能无法控制操作系统最终选择的保存位置，因此应把安全承诺限定为“响应提供建议名”，而不要声称网页控制了用户机器上的目录权限。

RFC 与安全指南提供的是协议边界和实现设计建议，不是对任意浏览器、桌面程序或文件系统的兼容性保证。本文没有执行攻击测试、跨系统保存测试或文件类型识别测试。上线前应在产品实际支持的平台上检查目标目录、同名覆盖提示、Unicode 名称显示和自动打开行为，并保存测试记录。有关入站文件的服务端边界，可参见上传文件的隔离与检查。
