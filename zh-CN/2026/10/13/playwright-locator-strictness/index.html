Playwright 定位到两个按钮时，什么时候才该用 first？

严格性错误先说明测试没有唯一目标；先用记录身份缩小范围，只有位置本身属于需求时才使用 first 或 nth。

正文

核心要点

  • 单元素操作遇到多个匹配会失败，count 等多元素操作可以接受多个结果；报错是在要求目标更明确。
  • 先用业务记录和语义区域定位按钮；first、nth 只适用于排序位置就是产品要求的场景。
  • 自动等待检查元素何时可操作，不会推断测试想操作哪条记录；验收还要核对实际改变的对象。

Playwright 的单目标操作匹配到两个按钮时，通常不该立即加 first()。严格性报错表示测试表达式还没有指出要操作哪个业务对象。先把订单、用户或对话等记录身份写进定位范围；只有“当前排序结果中的第一条”本身就是被测需求时，位置选择才有理由。即使点击成功，也要断言实际改变的是预期记录。

严格性报错是在拒绝猜测

Playwright 官方定位器文档把 locator 解释为在页面上查找元素的方式。对 click() 这类必须作用于一个 DOM 元素的操作，多个匹配会触发严格性错误；count() 等集合操作则允许多个匹配。first()、last()、nth() 能明确选择一个位置，文档同时提醒页面变化可能让位置指向另一个元素。因而，报错不是测试框架要求每个页面按钮都全站唯一，也不是把所有多元素查询都判为错误。它是在写操作前阻止代码替人作出身份猜测。

设想一个订单列表里有六条记录，每行都有“取消”按钮。getByRole('button', { name: '取消' }).click() 返回多个匹配时，正确的问题不是“怎么让它先通过”，而是“测试打算取消哪笔订单”。如果目标是编号 A-204 的订单，就先识别对应行，再在该行里取名为“取消”的按钮。此时测试意图能被读者复核；订单换序也不会静默改变目标。这个订单场景是假设例子，本次没有在实际业务页面执行，也不代表真实记录发生过取消。

如果把 first() 加在全局定位器后，代码只记录了 DOM 顺序，没有记录业务目标。今天第一个按钮也许属于 A-204，明天一条置顶的待处理订单、错误提示里的快捷操作或另一个筛选结果插到前面，它就会改指其他订单。危险处不只是测试变脆，而是测试可能仍绿，却操作了错误对象。严格性把这种潜在的假通过提前变成一个可诊断的红灯。

先识别业务区域，再识别控件

好的定位分两层：外层确定记录，内层确定动作。页面若为每行提供有意义的记录标题或可访问语义，可用 getByRole() 选择行，再用 filter({ hasText: '订单 A-204' }) 或包含唯一子元素的 filter({ has: ... }) 缩小到目标区域，最后在该区域内查找按钮。Playwright Locator API 将 locator.filter() 标为 v1.22 新增，并展示了文本或后代元素筛选；该筛选要求内外 locator 属于同一 frame。若项目使用更早版本，应先核对已安装 API，再选择该版本支持的身份定位方法。使用时还要确认筛选条件真能唯一识别记录：订单摘要可能在桌面表格和移动卡片各出现一次，也可能一行同时含原单和退款单的相同编号。

这也暴露出一个页面语义问题。按钮都叫“取消”，对单个记录而言名称可以是正确的；但测试外层若没有可识别的订单区域，缺的是上下文而不一定是按钮标签。若用户在页面上也无法看出按钮属于哪条记录，应让产品界面增加真实的行标题、关联说明或可访问名称。给测试单独塞一个 data-testid 可以建立稳定的工程契约，但不能用测试标识掩盖用户同样无法区分的操作。Playwright 文档建议优先选择接近用户感知方式的 locator；当角色或文本不足以表达测试契约时，test id 才是明确的补充。

外层筛选同样可能歧义。用 filter({ hasText: '待处理' }) 选出的若是三个订单，内层按钮依然会匹配三个。不要连续叠加 selector 直到数量刚好为一，而要找出对业务身份具有区分力的字段，并核对页面是否把它呈现出来。稳定的定位器是在编码出目标身份，不是把错误藏进更长的 CSS/XPath 链。

什么时候 first() 才是在表达需求？

如果产品要求就是“处理当前排序后排在最前的任务”，first() 或 nth(0) 可以表达该要求。前提是排序和集合已成为可验证的产品契约，而不只是当前 DOM 恰好如此。此时测试应显式规定排序字段、升降序、过滤范围以及并列时的规则，再确认列表确实只包含符合条件的任务。第一名是业务语义，页面碰巧排第一是实现细节。二者只有在排序契约明确时才一致。

一个可复核的测试可以先按创建时间降序加载待处理任务，确认列表第一条的唯一编号，再点击该行内的操作，并断言该编号对应的状态发生变化。如果测试仅在按钮集合上使用 first()，它没有验证过滤和排序结果，也无法解释为什么位置改变后目标仍正确。nth(2) 同理，它表达的是从零开始的第三个匹配；除非“第三个”是需求的一部分，否则它只是硬编码当前页面布局。

位置在有序、受控的有限集合中也可能合适，例如固定顺序的导航项测试。它不适用于数据顺序未约定、存在异步插入、分页追加或虚拟滚动重用节点的场景。选择位置之前，先说明集合是什么、顺序由谁保证、列表变化后测试预期如何变化；若答不出这三个问题，应回到身份定位。

自动等待和身份是两种不同故障

Playwright 的自动等待会在 click() 前确认 locator 解析为一个元素，并检查可见、稳定、接收事件、启用且非 inert；条件到超时仍不满足才失败。这些检查回答的是“这个已识别的元素现在能不能点”，不回答“测试应该点哪个订单”。timeout 加倍可以等一个按钮加载完成，却不能把六个“取消”按钮自动变成一个目标。

因此诊断时先按失败信号分类：严格性错误先看匹配数量和每个匹配对应的记录；超时再看元素可见性、动画、遮挡或启用状态；点击后没有业务结果则查看请求、响应和目标记录状态。把三类失败都归因于“页面慢”会错过身份错误；盲目使用 force 还会跳过接收事件等部分动作性检查。关于操作条件与断言重试的界限，可参阅自动等待与断言条件；它说明何时等结果，不替代对操作对象的选择。

验收应检查动作后改变了谁

建议把测试拆成四个可观察步骤：建立初始集合和排序条件；用稳定的业务身份找到目标区域；执行局部控件；从页面或可信的测试接口确认目标对象发生预期状态变化，同时检查邻近对象未被误改。以“取消订单”为例，点击无异常只证明一次动作调用完成；订单 A-204 变为已取消才证明结果对象正确，而 A-205 仍保持待处理能发现错误定位造成的副作用。

可进一步在空列表、同名重复记录、过滤后新增一条记录、排序并列、响应慢及移动布局中覆盖测试。它们分别检验无目标、身份重复、异步插入、顺序约定、可操作性和语义区域是否稳定。这是一份拟议验证清单，不是已经运行的 Playwright 测试结果。实施时记录浏览器版本、数据夹具和筛选排序条件，以便失败能够重现；若接口或页面结构变化，也应复核 locator 是否仍表达同一身份。

对动态列表，先等待集合达到有业务含义的状态，再用定位器读取集合或以自动重试断言检查目标可见；不要用一次性的 all() 快照或固定睡眠来伪装加载完成。官方 Locator API 提醒 all() 不等待匹配项，动态集合中容易产生不可预测结果；计数断言可用于检查集合大小，却不说明每项身份。可靠的验收组合是“范围有依据、对象可识别、动作条件满足、结果归属于该对象”。

结论不是永远禁止 first()。当顺序属于产品契约时，它是诚实的位置表达；当它只是让严格性报错消失时，它是在把未知交给 DOM 排序。先回答测试要操作哪条记录，再决定定位范围；点击完成后检查真实业务对象。这样失败会指出身份、等待或结果中的哪一层出了问题，也避免一条绿灯测试掩盖错误的操作目标。
