write 返回 false 后，Node.js 流应该怎样继续？

write() 返回 false 后停止继续写，等 drain 再恢复；它是缓冲压力信号，不是拒收或业务完成。

正文

核心要点

  • write() 返回 false 后停止继续写，等待 drain；不要重发已经提交的 chunk。
  • highWaterMark 是按流类型计量的背压阈值，不是总内存硬上限。
  • 本地 drain、远端接收和业务确认是不同状态；停滞还要由 deadline 或取消结束。

在 Node.js 26.13.1 中，可写流的 write(chunk) 返回 false 时，正确动作是暂停发起后续写入，并等待该流发出 drain 后再继续。刚才传入的 chunk 已进入可写流处理路径；false 表示缓冲压力已到需要生产方配合的程度，不是“这一块没写进去”，也不是要求重发。忽略它会把上下游速度差转成不断增长的待处理数据。本文讨论 Node.js Writable；第三方流可能有不同约定，必须看各自文档。

false 看的是写入后的队列状态

highWaterMark 是让流开始施加背压的阈值。流文档描述：写入缓冲低于阈值时，write() 返回 true；当前缓冲达到或超过阈值时，返回 false。因此检查发生在本次数据进入队列之后。比如文件读取器每秒产生 40 MB，而网络目的端只能处理 5 MB：短时间内调用方可能获得若干次 true，随后收到 false。那次写入已经被接收；如果应用立即重试同一 chunk，可能造成重复；如果继续取下一块，积压还会更快。

当已缓冲数据处理到可以继续时，流会发出 drain。此处的“处理完成”只在 Writable 的本地语义内成立。对于 socket，这个事件表示缓冲数据已排空、被操作系统接受继续发送；这不等价于远端应用已经读取、校验、持久化，更不等价于一次业务事务成功。若上传界面需要告诉用户“文件已入库”，还要等待服务端的应用级确认，不能把 drain 当确认回执。

每次 write() 的 callback 也不是 drain 的替代品。callback 对应单个 chunk 何时被底层处理，并可能以错误参数告知写入失败；返回值则让生产方在队列达到阈值时尽早停止继续供给。若循环仅仅等每一块的 callback，当然可以形成一种更保守的串行策略，但它改变了并发度与吞吐行为，不能简单当作与背压相同的机制。若任务希望在允许的缓冲范围内连续写入，仍应依据返回值暂停，而不是把“收到 callback”误解为“对端已确认”。

阈值也不是不可越过的块大小限制。检查发生在当前写入进入缓冲后；单次 chunk 本身若大于阈值，这一次写入仍会被纳入队列，随后返回 false。因此如果调用者能产生任意大的对象或 Buffer，仅等待 drain 并不能阻止单个输入造成内存尖峰。生产源应按可控块拆分大对象，并同时限制单次对象大小与未完成任务数量。

让生产循环真正停下来

手工写入时，循环只在 write() 返回 true 时继续取下一块；返回 false 后，只登记一次恢复事件，然后再继续。下面是说明控制关系的伪代码，不是本站执行过的教程：

for await (const chunk of source) {
  if (!writable.write(chunk)) {
    await once(writable, 'drain', { signal });
  }
}
writable.end();
await finished(writable);

events.once() 在等待期间遇到流的 error 会拒绝 Promise，AbortSignal 也能取消等待。不过这个短例子仍需按具体流补上提前 close、取消后销毁资源、超时和清理逻辑；如果源流在读数据、目的流已经结束，不能让生产任务永远悬挂。也不要在写入返回 false 后循环轮询 writableLength：忙等既不让底层变快，又占用事件循环。

多数源—转换—目的的流水线不需要自行写这个循环。stream/promises 的 pipeline() 会在各段之间协调流动，并以 Promise 表达完成或错误；同一版本文档还展示了把 AbortSignal 作为选项传入、取消时销毁 pipeline 中底层流的做法。这里可以优先选官方编排 API，把精力放在取消信号是否传递、目标文件的部分结果如何处理以及错误由谁报告。只有当应用确实要控制每次取数、加入队列策略或维护业务状态时，手动循环才值得承担更多生命周期细节。

阈值不是内存上限

highWaterMark 不会普遍地给整个进程设置硬内存上限。普通字节流按字节计，object mode 按对象数量计，未解码字符串流按 UTF-16 code unit 计。十个对象可能只是十个短记录，也可能每个都引用一大段缓冲区，所以对象数不等于内存字节数。Duplex 和 Transform 两侧各有独立缓冲；应用层的待提交批次、重试队列和闭包引用也会继续保留对象。

举例说，一个假设的数据导出链路包含文件读取、压缩 Transform 和 socket 写入。每个阶段都可能暂存数据，应用还可能把等待服务端确认的记录另存一个数组。把每一段的 highWaterMark 相加，只能得到非常粗的队列估算，不能证明 RSS 上界；更不能把“整个系统在用流”当成常量内存的证据。应先明确最大 chunk、每段允许积压的单位、同时在途任务数，以及业务确认队列是否有界。接收方停止读取时，TCP socket 可能长期不再 drain；无限等待可以避免继续增加写入量，却仍可能让请求和上游资源一直占用。背压需要和 deadline、取消与清理策略一起设计。

哪些观测能验证它

验证应让消费者速度发生变化，而不是只看一个成功的文件输出。可以为自定义 Writable 设计可控延迟的测试替身：记录每个 chunk 调用、返回 false 的时刻、drain 次数及 writableLength；减慢消费后，检查生产是否暂停、取消能否结束等待、错误能否被调用方识别。再让消费者拒绝、提前关闭目的流或触发 AbortSignal，确认任务以错误或取消结束、没有继续取数，也没有留下等待 drain 的 Promise。此处是测试设计建议，本文没有执行这些实验，也没有测出内存或吞吐结果。

还应把本地流检查和业务确认分开：人为让 drain 正常出现，但让模拟服务端不发确认，页面就不应把任务显示为已保存；反过来，确认丢失后重试也要靠幂等键或业务协议避免重复提交。用 writableLength、writableNeedDrain、暂停时长和取消原因诊断本地积压，但不要依赖文档明确标为内部实现细节的缓冲区字段。阈值是否合适，最终取决于对象大小、阶段数、目标速度和可接受延迟；提高它可能减少暂停频率，却会容许更多等待数据。解决问题的第一步是确保暂停信号从目的端一路回到生产源，而不是先把阈值调大。

如果还要处理网络字节块被拆开时的字符解码，参见跨块 UTF-8 解码与消息分帧；字符解码和写入背压是两条不同的数据路径。
