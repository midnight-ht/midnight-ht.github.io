write 返回 false 后，Node.js 流应该怎样继续？

write 返回 false 后等待 drain；highWaterMark 是阈值，背压与取消、缓冲预算及业务确认需要分别设计。

正文

Node.js 可写流的 write 返回 false 后，生产方应暂停继续写入，等待 drain 再恢复。false 是背压信号，不能当成这块数据完全没有被接受。持续忽略这个信号，会把生产速度与消费速度的差距转成不断积压的内存，而不是让接收方变快。

阈值不是容量承诺

Node.js 流文档说明，highWaterMark 是阈值，不是一般意义上的严格内存上限；文档同时要求在 write 返回 false 后，不要继续写入更多块，直到 drain 事件出现。这里核对的是所读取的二十四版本分支文档，不能由此推断所有第三方流实现都具有相同的资源行为。

假设程序把大文件读出后逐块写入较慢的网络连接。若循环只检查读取是否结束，而从不响应写入结果，数据可能在本地堆积。提高阈值有时会改变缓冲行为，却没有消除速度不匹配。对于始终不读取的远端，等待排空也可能长期无法完成；背压控制还需要与取消、超时和错误处理共同设计。

可写流接受数据与数据抵达对端，是不同层次的状态。即便本地缓冲排空，也不能凭此宣称对端业务已经保存或处理成功。需要应用级确认的场景，应保留对应确认机制；把底层传输信号直接变成订单完成或文件入库，会扩大流接口的承诺。

让暂停路径与失败路径都能结束

拟议实现应确保暂停时不会继续启动新的写入，同时能够响应错误、连接关闭和调用方取消。恢复事件只解决正常消费速度恢复后的继续生产，不替代失败处理。若业务自行组合多个流，还应核对各段错误如何传播，避免上游继续读取而下游早已不可用。本文没有执行这样的组合代码，因此不提供成功日志或内存数字。

检查资源预算时，不能只看一个 highWaterMark。转换流的读写两侧各有缓冲，应用也可能保存尚未提交的批次、解析对象或重试内容。每一层都可能增加保留数据，业务对象大小也不必等于字节块大小。所谓“流式”并不自动等于固定内存占用，需要看实际保留了哪些对象。

根据业务界定完成

验证计划可以使用逐渐变慢的消费者和提前关闭的连接，观察生产是否暂停、取消能否结束等待、错误能否被调用方识别。测试得到的结果只能覆盖所用实现和条件，不能据此保证任意网络环境下的吞吐或稳定性。对于必须确认接收结果的业务，还要分别测试成功确认缺失和重复确认。

面向使用者的进度也应该区分读取、写入、传输与业务确认，避免显示一个模糊的百分之百。若出现积压，先核对生产与消费关系以及保留对象，再决定是否调整阈值。有关运行过程中怎样报告真实状态，可阅读进度与最终结果的区别。
