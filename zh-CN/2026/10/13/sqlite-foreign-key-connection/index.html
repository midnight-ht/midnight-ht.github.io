SQLite 表有外键，不代表每条连接都在执行

SQLite 的外键声明保存在模式中，约束是否执行取决于当前连接。逐个初始化并读回连接设置，再用受控写入和历史数据检查补齐证据。

正文

SQLite 的外键定义属于数据库模式；这条约束在某个写入请求里是否执行，却取决于处理请求的那条数据库连接。应用应为每一条新建连接启用外键、在事务开始前读回状态，并用受控的非法关系写入核对真实写入路径。只在启动时检查一条连接，不能证明连接池、后台任务和迁移脚本使用的其他连接也受保护。

一份表定义，为什么还不够？

外键描述子表中的值应对应父表中存在的键。例如订单表的 customer_id 引用客户表 id，数据库便能拒绝引用不存在客户的订单。SQLite 官方文档把外键约束的定义与运行时启用分开说明：应用必须在构建支持外键的 SQLite 库上，通过 PRAGMA foreign_keys 设置连接状态。官方文档还明确指出，状态按每条数据库连接分别启用；SQLite FAQ 说明历史默认值是关闭的，但官方文档同时提醒，未来默认值可能改变，编译选项 SQLITE_DEFAULT_FOREIGN_KEYS 也能改变构建默认值。因此可靠做法不是背一个默认值，而是让应用显式设置并读回需要的值。

这会产生一个容易漏看的差别：同一个数据库文件可以有多个连接，但每条连接各自持有当前外键执行状态。连接 A 读到 1，只证明 A 当前启用；它不能替连接 B、后来新建的连接，或维护脚本的独立连接作证。若某个连接被丢弃后由池补建，新连接也必须走相同初始化路径。表模式说明“应该有什么关系”，连接状态说明“这次写入有没有执行它”，两者是不同证据。

一个探针如何给连接池造成错觉？

设想服务启动时，为健康检查单独打开连接 A，执行 PRAGMA foreign_keys 并读到 1。真正的请求由连接池中的 B、C 处理；后台任务还会自行建立连接 D。若 A 的检查没有覆盖 B、C、D 的创建过程，启动日志至多说明 A 正常，不能说明所有写入口都正常。

用订单和客户作为假设例子：客户表里只有 id 为 12 的客户，订单的新写入却把 customer_id 设为 700。若这次请求落到没有启用外键的连接，表中的 REFERENCES 声明不会自动替该连接打开执行开关，孤儿引用可能被写入；如果落到启用了约束的连接，同一关系应被拒绝。这里描述的是 SQLite 的机制，不是本站实际运行过的插入实验，也不是某个现网系统已经发生故障的记录。

这个差异也解释了为什么“迁移成功”不能当作“运行保护已开启”。迁移能证明建表语句通过并写入模式；它不决定后来打开数据库的每条连接是否启用外键。反过来，只检查一条连接的状态，也不能证明数据库里已有的每一行都符合这些关系。

为把连接范围从推理变成可见结果，我在隔离的共享内存库上实际跑了一次 Python sqlite3 检查：Python 3.11.15 链接 SQLite 3.53.1，连接 A 设置外键后读回 1，未触碰的连接 B 读回 0；B 写入一个不存在的父键后被接受，A 执行 PRAGMA foreign_key_check 返回 child、行号 1、parent、外键编号 0；随后在 B 的事务里尝试启用，读回仍是 0；事务结束后再设置，读回 1，同一非法写入得到 IntegrityError，消息为 FOREIGN KEY constraint failed。这些是本地一次性实验的实际结果。它证明该运行库中的连接隔离与事务时序，不证明本站使用的驱动、生产连接池或其他编译方式具有相同默认值。完整脚本和原始结果随本批审查记录归档。

设置必须发生在事务外

SQLite 文档指出，连接进入多语句事务后再切换 foreign_keys，不会改变当前状态，也不会因这个原因返回错误。因而，先 BEGIN，再执行 PRAGMA foreign_keys = ON，最后只看语句没有报错，是一种特别容易留下假阳性的检查。

连接初始化应有明确顺序：创建连接，设置外键，查询 PRAGMA foreign_keys 的结果，确认返回值为 1，之后才把连接交给业务代码或启动事务。如果读取不到 1，不要把它转换成普通警告后继续写入；应按业务关系约束要求拒绝该连接进入写入路径。若查询没有返回 0 或 1，而是没有结果行，SQLite 官方文档把这视为当前库可能不支持外键的信号，常见条件包括过旧版本或编译时省略相关功能。此时需要检查实际运行库和驱动构建，而不能仅凭 SQL 文件认定保护存在。

连接池实现的具体钩子随数据库驱动而异，文章没有假定某个框架的配置项。审查时要能指出“每个新连接在哪里创建、设置、读回，以及失败后如何阻止借出”。还要覆盖连接回收和重建：若应用代码可能在运行期改动 pragma，或测试代码曾关闭外键，池归还连接前应复核或重置策略。对于单连接程序，初始化只需覆盖这一条连接，但独立的迁移器和维护脚本仍然是新的入口。

读回开关、拒绝非法写入和检查旧数据，分别证明什么？

可把验证拆为三层。第一层是在每个实际连接创建路径上查询 PRAGMA foreign_keys，确认该句柄的状态。它证明开关值，不证明表声明正确，也不证明旧数据干净。第二层是在一次性数据库或可回收测试库里，建立一对父子表，让子行引用不存在的父键。上面实际运行的共享内存实验已经覆盖了两条连接：未配置的 B 接受了错误引用，启用后的 B 拒绝了同一关系。产品验收还应经由请求处理器、后台作业和迁移或维护入口分别测试，而不是只用命令行连接试一次；本文没有连接本站应用或生产数据库，因此这部分仍是待实施方案。保存 SQLite 版本、驱动和连接路径，并确认拒绝原因确实是外键而非另一个约束。

第三层是检查已有关系。PRAGMA foreign_key_check 会返回违反已声明外键的记录，并给出包含 REFERENCES 子句的子表、子行 rowid（WITHOUT ROWID 表中这一列为 NULL）、被引用的父表以及外键编号。它能帮助发现约束从未开启期间留下的关系问题，但它不会替未来新建连接启用开关，也不会判断数据库设计中没有声明的业务关系。找到记录后，修复、隔离还是保留，需要按业务事实处理；不能为了让检查输出为空而随意删除数据。若数据库从未收集足以重建关联的信息，报告数据缺口比伪造一个父行更诚实。

这三层可以定位不同失败：连接探针读回 0，说明初始化没有完成；写入试验在某个路径成功，说明该路径没有按预期拒绝关系；foreign_key_check 返回旧记录，说明历史数据需要单独评估。不要把它们压缩成一个“外键测试通过”，否则团队不知道证据覆盖的是开关、写入时行为，还是旧数据。

上线前的检查如何落到连接生命周期？

先列出会打开数据库的入口，而不是只列服务进程：普通请求池、队列消费者、计划任务、管理命令、迁移脚本、测试工具和恢复脚本。为它们确认使用的库版本与驱动构建选项。然后检查每条入口的连接创建函数，在业务事务之前设置和读回外键状态；对连接池再验证补建连接时也会触发初始化。接着在临时副本上分别做有效关系和无效关系的写入，确认前者按设计通过、后者按预期失败。最后对既有数据执行 foreign_key_check，并保存结果与处理决定。

文章中的父表与子表记录是为隔离实验设计的测试数据；该实验已在 Python 3.11.15 与 SQLite 3.53.1 的共享内存库上运行，但没有在本站应用或生产数据库执行。如果团队无法通过测试钩子让每条池连接都单独创建，可以针对每种创建配置与重连机制安排测试，并检查实际初始化代码；这仍是有边界的覆盖证据，不能推成所有未来版本必定正确。升级 SQLite、切换驱动或改变连接池构造方式后，应重新运行对应检查。

还要看索引和业务语义吗？

要，但它们回答的是另外的问题。父键必须符合 SQLite 的主键或唯一键要求；若子键没有索引，删除或更新父记录时，SQLite 可能需要在子表查找引用行，较大表的操作成本会增加。子键索引通常有性能价值，却不会打开外键执行开关，也不能代替正确的引用关系。可参考SQLite 外键检查与结构检查的边界；如果要分析父表变更时子表查找的成本，可看PostgreSQL 外键与子表索引，但后者针对的是另一种数据库，不能直接照搬其实现行为。

外键也有业务边界。子键允许 NULL 时，SQLite 文档说明该行不必对应父行；如果产品语义要求“必须属于某个客户”，还要使用 NOT NULL 等约束来表达这一要求。启用外键不能自动修复旧数据、不能取代授权规则，也不能判断某个缺失客户应由谁恢复。上线审查应分别留下模式定义、每连接启用状态、写入拒绝证据和历史数据处理记录，而不是用一次启动探针代表整套关系保证。
