CSP nonce 应该跟着构建，还是跟着响应变化？

CSP nonce 应随每次发出的策略重新生成，并让响应头与获准标签保持一致；纯静态脚本可评估内容哈希。

正文

核心要点

  • nonce 要随每次发出的策略更新，响应头与获准标签必须一致。
  • 固定静态脚本可评估内容哈希；动态内联内容才需要逐响应 nonce。
  • 边缘缓存要分别检查值新鲜度、头体匹配、未授权拦截和跨响应复用。

CSP nonce 应跟随实际发出的策略和 HTTP 响应变化，而不是在构建时生成一个值再让它长期进入缓存。若页面内容固定、可以提前计算脚本哈希，静态站点通常应先评估哈希许可；若服务端需要放行响应中的内联脚本，nonce 就必须在生成响应时创建，并确保策略头和被许可标签来自同一份响应。关键不是“动态一定安全”或“缓存一定不行”，而是每次授权值的生命周期、响应的一致性和脚本来源是否能被解释。

nonce 的契约是按策略发放，不是按版本发放

CSP Level 3 的安全考虑明确要求：服务器每次发送包含 nonce-source 的策略时，都生成唯一值；值应至少有 128 位随机数据，并使用密码学安全随机数生成器。MDN 对响应头的说明也把 nonce 描述为服务器为每个 HTTP 响应生成的随机值。浏览器将策略中 nonce-... 的值与目标 script 或 style 元素上的 nonce 属性比较，匹配才允许相应元素通过该策略检查。这两份资料定义的是机制和建议，不是对某个应用已经正确实现的证明。

因此，一个 nonce 可以同时出现在同一响应的策略头和多个被明确批准的脚本标签上；它不应作为构建产物中的长期常量，跨响应复用。把“每次部署换一次”当作“每次响应唯一”会混淆两个时间尺度。用户每次刷新收到相同 HTML 与相同策略，仍然是在重用授权值。值随机也不够：如果生成在构建阶段、由时间戳拼出、或者被日志/模板无意泄露，生命周期与不可预测性仍可能不符合安全目标。

需要同时检查策略头、HTML 和生成点

可以把 nonce 的流转拆成三个动作：生成、注入、交付。生成动作应使用安全随机源；注入动作应只处理应用明确允许执行的脚本或样式；交付动作应保证 Content-Security-Policy 响应头与这些标签属于同一份页面响应。只在模板中搜索到 nonce= 不能证明三步相连，浏览器控制台没有报错也只能说明当次页面执行没有显露某些问题。

设想一个页面模板固定输出旧 nonce，边缘函数却按请求更新 CSP 头。浏览器看到的头和标签不匹配，原本合法的内联脚本会被拦截。反过来，如果边缘只重写 HTML 标签、没重写头，结果仍不一致。再设想共享缓存把一个带有请求 A nonce 的 HTML 和响应头交给请求 B：它可能在功能上匹配，却把 A 的授权值复用于后续访客，违反每次发送策略都生成唯一值的要求。这里是按协议机制推演的缓存风险，不是本文运行过的 CDN 故障或真实攻击。

这并不意味着所有共享缓存都不能与 nonce 共存；关键是缓存返回时，是否仍能为这次发出的策略生成新值，并把最终响应头与可信 HTML 一起更新。若缓存只重复交付上游已生成的头体，它就会重复授权值；若边缘层只改其中一部分，合法脚本又会被拦截。工程团队还需审查压缩、流式响应、模板片段缓存、错误页和重试路径是否绕过同一处理。若架构无法保证这些环节协同，就不要为了让缓存命中而固化 nonce；选择可验证的动态渲染边界，或重新考虑静态哈希方案。

静态哈希和动态 nonce 的选择条件不同

MDN 的 CSP 实施指南建议：能动态生成内容时可使用 nonce；需要提供静态内容时可使用哈希。哈希授权针对脚本或样式的实际内容计算，代码内容变化后，策略中的哈希也必须同步更新；对于带 src 的外部资源，还涉及 integrity 属性。它不是把动态脚本放过的万能替代物，也不必每个页面请求重新随机生成。相对地，nonce 的维护责任落在服务器或边缘响应链路，需要每次重新生成，并把同一个值准确插入策略和被授权标签。

假设一个预渲染站点只有一小段稳定的内联启动脚本。发布流程可以在构建时根据确切脚本字节计算哈希，再让策略随产物一起发布；内容变更时构建检查应发现哈希漂移。若页面包含按请求变化的内联配置，静态哈希就会随内容变化而难以维护，动态 nonce 可能更适合，但页面就需要请求时渲染或可靠的边缘改写。Next.js 13 Pages Router 的文档也是这个特定版本和路由模式的示例：它建议每次页面查看生成新 nonce，并指出需要动态渲染。不要把这个框架版本示例外推成所有框架、所有路由的统一实现方式。

一个缓存场景如何定位不匹配

假设源站渲染 HTML，反向代理缓存部分页面，边缘层设置 CSP。排查时可以逐层记录四个事实：源站生成了哪个值，HTML 标签带了哪个值，最终响应头列出了哪个值，缓存命中是否跨用户复用了页面。若三个值相同但请求之间重复，页面可能运行正常，唯一性仍有问题；若头和标签不同，合法脚本会被阻止；若某个未知标签也被模板批量补上 nonce，注入的脚本可能借用许可。CSP Level 3 还讨论了 nonce 劫持和泄露，因此“给所有 script 标签自动加值”不能代替可信模板边界。

这个例子是待验证的架构推演。它没有在本项目或某个 CDN 上执行，不能据此宣称某种缓存配置已经安全。实际系统需要明确哪些响应可缓存、哪些响应必须动态化，以及是否由边缘把响应头与正文作为一个不可分割的表示更新。若错误页、预取请求或非 HTML 路径不经过同一逻辑，验证范围也必须覆盖这些分支。

以能暴露错误的检查来验收

先按 MDN 的渐进实施建议用 Content-Security-Policy-Report-Only 观察当前页面会出现哪些违反，再决定强制策略；报告阶段能帮助发现兼容问题，但不等于已经阻止攻击。随后设计至少这些测试输入：连续的两个页面响应；同一响应中的头和标签；一次缓存未命中及命中；模板片段复用；包含不受信任内容的页面；脚本内容修改后的静态哈希；失败页和取消/重试路径。检查结果应分别回答“值是否更新”“是否匹配”“非授权内容是否仍被挡住”“缓存是否跨响应复用了授权”。不要把“页面没有报错”当作完整验收。

验证时也应注意 MDN 对 nonce 属性的说明：浏览器会隐藏 nonce 内容属性的普通 getAttribute() 返回值，脚本若确有需要应通过元素的 nonce 属性读取；这种隐藏用于降低通过属性选择器等方式窃取 nonce 的风险，但不能抵御所有注入或泄露。因此 nonce 不能替代输出编码、模板安全、依赖治理和最小权限。

选择可以归纳为一个维护责任问题：静态、固定脚本且构建链路能准确同步内容哈希时，优先评估哈希；响应中确有必须放行的内联内容且服务器能逐响应同步生成、注入、发送时，才使用 nonce。若缓存或模板无法保证这一契约，先调整交付边界，而不是把 nonce 变成永久白名单。关于上线前如何逐步观察违规与执行策略，可参阅 CSP 报告模式的渐进切换。
