先 rate 再 sum：Prometheus 聚合为什么要保留实例的重置

先按原始时间序列处理 counter reset，再按业务维度聚合，才能避免实例重启被合计掩盖；同时说明 rate 外推、标签变更、仪表与直方图的边界。

正文

核心要点

  • rate-before-sum 保留的是每条原始序列识别重置的机会；提前 sum 可能抹掉单实例的下降。
  • rate 是有窗口并会外推的估计值，不是单条请求日志的精确计数；假设样本算例不能替代实际查询。
  • 最终 by/without 标签、counter/gauge 类型和比率分母仍由业务问题决定。

一台实例的请求计数从 10 回到 1，另一台仍从 1,010 增长到 1,020；如果先把两台的原始 counter 相加，合计仍可能继续上升，看不出刚发生的重置。因此官方建议先对每条序列计算 rate()，再按业务维度聚合。这个顺序保留了重置发生在哪条序列上的信息；它不是为了让 PromQL 看起来整齐，也不是所有指标都无条件套用的一条口诀。

一个被合计遮住的重启

假设 Prometheus 在四个等间隔时刻观察两个实例。实例 A 的计数是 8、10、1、3；在第二个采样点之后，进程重启并从 0 附近重新计数。实例 B 的计数是 1,000、1,010、1,020、1,030，一直增长。把同一时刻的数据先相加，得到 1,008、1,020、1,021、1,033。这条总序列没有下降。仅从合计值看，查询端无法知道其中一个成员刚从 10 回到 1。

把 A 和 B 视为独立 counter 序列时，A 的下降可被识别为重置：简化地按边界样本计算，A 在这段观察期内有 2、1、2 的增量，共 5；B 增加 30；合并后的理想化计数增量是 35。若先把原始值相加，首末样本只相差 25。两种结果不相等，差异来自重置前后的序列身份被过早折叠。

这个表只是用来手算信息丢失的假设例子，不是一次 Prometheus 查询结果。真实 rate() 会根据时间戳、样本间隔、窗口边界和数据缺口进行外推，因此不能直接把这里的 35 除以采样间隔，就声称得到了某个精确的每秒速率。例子的作用只有一个：合计会不会保留原始序列下降这个信号，取决于你何时把序列身份合并。若读者还需要核对整数计数器为何能得到小数，可以接着看窗口外推与 increase 的纸面算例；那篇讨论的是窗口边界，不替代本篇的跨实例重置问题。

Prometheus 3.13 的官方函数文档和 2.55 版文档都说明，rate() 以 range vector 为输入，按每条时间序列计算每秒平均增长率，能校正计数器重置，并将结果向查询窗口边界外推，以适应漏抓取或采样与窗口未对齐。两个版本的函数说明还明确指出：把 rate() 与聚合操作结合时，应先计算 rate()，否则聚合后的序列可能不再暴露目标重启造成的 reset。若你的服务运行其他版本，应以部署版本对应文档核对；这里没有将两个已查版本扩展成“所有未来版本都相同”的承诺。

聚合前后，rate 看到的是不同对象

常见目标是“所有 API 实例每秒处理多少请求，同时按 job 保留分组”。可写为：

sum by (job) (
  rate(http_requests_total{job="api"}[5m])
)

rate()先看到带有 instance、pod 等标签的原始序列，各自处理重置，再由 sum by (job) 将结果汇总为 job 级别。查询运算符文档说明，by 只保留括号内标签并丢弃其余维度。若你需要保留区域或请求类型，应在标签列表里表达；若目标是“除 instance 与 pod 外，其余维度继续区分”，可用 sum without (instance, pod)。选 by 还是 without 不是格式偏好，它决定了输出向量还能回答哪些问题。

如果想演示“先 sum 后 rate”，不能写成 rate(sum(...)[5m]) 这种不完整表达，因为普通 range selector 直接附在向量选择器后。对聚合表达式使用 range vector 时，需要 PromQL subquery，例如：

rate(
  sum by (job) (http_requests_total{job="api"})[5m:]
)

subquery 会在一段时间范围和分辨率上反复计算内部 instant query，再把结果作为 range vector 提供给外层函数。官方基础语法说明，省略 [5m:] 中的分辨率时，会使用全局 evaluation interval。因此，这个反例多了一层子查询评估网格，并非在完全相同的抓取时刻上做一个纯代数换序；真实比较时应把该分辨率条件也固定下来。这里外层 rate()看到的已是 job 合计曲线，而不是各实例 counter。若一台重启、另一台增长使总曲线仍单调，重置就没有机会被识别；若合计曲线也出现下降，外层函数又可能把整条 job 曲线当成一次统一的 reset 修正。两种情况下，它都无法还原每个实例原本发生了什么。

这也解释了一个看似反例的场景：某些窗口里先聚合再求导可能“看起来没坏”，因为合计仍留着下降或实例根本没有重启。它不证明两种顺序等价。对变化平滑的那段历史，两种写法可能碰巧接近；只有在每条序列独立保留时，rate()才有材料根据各自的下降校正。函数参考把顺序要求直接限定在“否则无法检测目标重启时的 counter reset”这一原因上。

rate 能校正重置，但不能补回没有采到的数据

Counter 是累计事件数或累计字节数，进程重启时可以复位；Gauge 表示可上可下的状态，例如当前排队任务数或正在处理的请求数。Instrumentation 指南建议按这种语义区分类型：对累计 counter 使用 rate()，不要把会自然下降的 gauge 当 counter。假如把排队任务数套上 rate()，一次真实的队列排空会被解释成重置，数字并没有因此变成“每秒完成任务数”。

rate()处理的是观察到的样本，不会凭空恢复最后一次抓取后、进程重启前尚未暴露的增量。短窗口会降低平滑程度，也可能因为可用样本较少而没有足够证据；长窗口能平滑短时波动，但会把部署后的新状态和较早历史混在一起。官方指南没有给所有服务规定一个最佳窗口。选择窗口时，应结合 scrape interval、告警需要的响应时间、缺样本模式和规则评估间隔，并在仪表盘说明中保留这个条件。

实例 label 也不是永恒的进程身份证。若滚动发布给新 Pod 分配新的 instance 或 pod 值，旧序列可能变为 stale，新序列从新的 label set 开始。逐序列求 rate 可以保留两个生命周期各自的样本，再聚合仍存在的速率；但它不会让没有样本的时间段自动补齐，也不会证明一条新序列已积累足够数据。排查时先按实例或 Pod 查看原始值、resets()、up 与部署事件，再检查总速率。只看平滑总线会把“旧实例消失”“新实例刚启动”和“计数器重置”混成一个无法追责的变化。

irate()也不是 rate() 的快速替代品。官方文档说明它使用最后两个数据点，适合观察波动较快的 counter 图形；短时变化可能让告警的 for 条件反复重置，官方建议告警与变化较慢的 counter 优先使用 rate()。因此比较查询时，不只换算子，还要确认用途是看瞬时趋势、做告警还是记录规则。

直方图的 sum 与 count 不能先算成平均值

对于经典直方图或 summary，_sum 和 _count 是两组不同的累计序列。若要算一组实例的平均观测时长，Prometheus 的 histogram 指南给出的思路是：先分别对每个 _sum 与 _count 序列求 rate，按需要聚合，再用总和相除。概念上可写为：

sum by (job) (rate(http_request_duration_seconds_sum[5m]))
/
sum by (job) (rate(http_request_duration_seconds_count[5m]))

不能先算每台实例各自的平均值再做无权平均，因为每台实例的请求数可能不同。也不能把平均值加总成平均值。分子累计时长与分母观测数应分别保留，最终的比率才对应“总体请求的平均时长”。这仍是平均值，不是 p95；分位数需要看直方图桶并按官方表达式计算。本站已有为什么不能把各实例的分位数直接求平均，这篇只补充求 rate 时重置信息与分母的责任边界。

另一个容易忽略的条件是：如果经典直方图或 summary 接受负值观测，_sum 可以真实下降。Histogram 指南指出，这种下降会触发 counter reset 的解释，从而使 rate(_sum) 结果失真；该问题不适用于以整体形式处理的 native histogram。先 rate 再 sum 并不能修复错误的指标契约。遇到这类观测，应重新设计指标拆分或表达式，而不是把聚合顺序当成万能修补。

用同一组输入检查查询与 recording rule

改一条生产规则前，可以先用 Prometheus 表格视图分别观察原始 counter、resets(counter[窗口])、每实例 rate(counter[窗口]) 和最终聚合结果。把部署时间、采样时间戳和序列 labels 放在同一份诊断记录里。目标不是只验证“总数有值”，而是确认目标维度是否保留、重启那条序列是否被分别处理，以及窗口边缘的缺样本是否影响读数。

需要固定回归时，可根据官方 promtool test rules 格式构造输入序列：一条 counter 在窗口中下降，另一条持续增加；分别断言 per-series rate、job 聚合和输出 label set。再增加一个负向样例：把 metric 改成会下降的 gauge，或让实例 label 改变，确认测试不会误把没有观测到的数据解释为平稳。文中没有编写或执行这份 fixture，也没有查询实际 Prometheus；这些步骤是建议的验证方案，不是测试通过的报告。

Recording rule 还需要稳定的输出标签和可理解的名字。规则命名指南建议名称表现出聚合级别、原指标及已执行的操作，并明确被聚合掉的标签。比如规则输出叫 job:http_requests:rate5m，就应检查它的 label set 是否真的只有 job 等承诺保留的维度。若把 instance 删除了，后来就不可能仅凭这个新序列判断是哪台实例发生了重置。把这种信息损失当成设计选择，而不是再去添加临时补丁，排查路径会更清楚。

实际评审一条查询时，先回答三个问题：原始 metric 是否遵守 counter 契约；counter 的标签是否在重启后仍能区分各序列；聚合后的 by/without 与直方图比率的分母是否对应同一个业务范围。若这三项未核对，就算表达式能执行、图线看起来连续，也不能证明它反映的是目标总速率。rate-before-sum 的价值在于保留可用于重置识别的底层证据；它不替你决定测量对象、标签身份或统计口径。
