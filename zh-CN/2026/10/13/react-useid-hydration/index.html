useId 不是通用唯一键：先分清 DOM 关联、数据身份和水合树

React useId 用于组件内可访问性关联；列表 key 来自数据，SSR 水合还要求两侧树相同，多根页面需匹配 identifierPrefix。

正文

React 的 useId 不是通用的唯一编号。例如密码输入框可以用 aria-describedby 指向帮助文字；这个 ID 不应变成地址行的列表 key 或数据库主键。它适合把同一组件里的控件与说明、错误提示等 DOM 元素关联起来；列表项仍应使用数据身份，业务记录也应有自己的主键。服务端渲染时，如果客户端首次输出的 React 树与服务端不一致，useId 不会替你修复结构。把这三类身份分开，才知道应该检查什么。

先说清 useId 给谁一个身份

React 的 useId 参考文档把它定义为生成可用于可访问性属性的 ID。比如一个密码输入框通过 aria-describedby 引用说明文字。问题是页面关联：浏览器中的输入元素引用哪段帮助内容。组件可能在页面上出现两次，因此把固定字符串写死会让不同实例的关联撞在一起；在组件顶层调用 useId，再把同一个值用于输入属性和说明元素，两个实例各自维护自己的关联。

import { useId } from 'react';

function PasswordField() {
  const hintId = useId();
  return (
    <>
      <label>
        Password
        <input type="password" aria-describedby={hintId} />
      </label>
      <p id={hintId}>Use a long phrase that you can remember.</p>
    </>
  );
}

这段示例说明一个 Hook 调用如何同时接到两个相关元素。它没有数据库写入，也没有列表映射；代码在这里是机制示意，没有在某个应用或辅助技术环境中运行过。若一个表单还要关联错误提示，可以在同一组件中用 useId 生成另一个前缀或分别生成 ID，再明确把它们放入恰当的 ARIA 属性。ID 字符串只是关系的端点；文字是否清楚、错误是否在适当时机出现，仍要单独验收。

调用位置也属于这个契约。useId 和其他 Hook 一样，应在组件顶层调用，不能在循环或条件分支里按字段数量动态调用。如果一个地址表格要为每一行生成说明 ID，通常由每行自己的组件调用一次 Hook，再把结果交给该行的输入和说明。把 Hook 放在 map 回调里，既违反 Hook 的调用规则，也会把“每个列表项的组件身份”和“字段到说明的 DOM 关联”混为一谈。拆成独立行组件不是为了让 ID 看起来不同，而是让每行都有固定的 Hook 调用位置，同时让数据 key 继续由地址记录提供。

“列表里的这一行要沿着排序和插入保持同一条记录”是另一种身份。React 文档明确建议列表 key 来自数据，而不是用 useId 生成。比如地址有稳定的 address.id，就应让该数据标识决定列表项身份；如果排序只按数组下标标 key，编辑草稿可能跟到另一条记录。useId 不能补上数据契约，也不应当成为接口或数据库主键。可参看记录切换时的 React key 与草稿边界，那篇讨论的是组件状态何时重置，不是 DOM 说明文字的关联。

同一棵树怎样让服务端与客户端对上

服务端先输出 HTML，浏览器随后调用 hydrateRoot 接管这份 HTML。如果服务器和客户端初次渲染的树形状相同，React 能按对应的组件路径生成匹配的 useId。React 文档解释，这些 ID 与调用组件的父路径有关；这能避免用一个全局自增计数器去赌客户端水合的先后顺序。多个客户端组件的水合顺序可以和服务器吐出 HTML 的顺序不同，但只要同一组件树结构对应，父路径仍能把调用位置配起来。

这一保证有明确前提：两侧要渲染同一棵树。假设服务端输出“标题、邮箱字段、说明、提交按钮”，客户端在 hydrateRoot 之前根据 window.matchMedia 或本地存储改成“标题、提示面板、邮箱字段、说明、提交按钮”。一个额外的兄弟节点改变了后续组件的父路径；不能因为邮箱字段仍调用 useId，就推断它生成的 ID 一定和服务器 HTML 中的那个相同。hydrateRoot 文档要求渲染内容与服务器 HTML 一致，并指出并非所有属性差异都会被修补。

遇到这种问题，先找造成首次树差异的输入：是不是服务器没有的本地状态、时钟、随机值、尚未同步的用户数据或浏览器能力判断。修复应使首屏服务器和客户端采用一致的数据与结构，再在水合完成后按产品需要更新客户端状态。不要只换成 useId、抑制一条提示或删除关联属性。提示不再出现只说明诊断输出改变，并没有证明 DOM 关系正确或用户仍看得到应有内容。本文给出的分支是排查推演，没有实际 React 应用、水合日志或浏览器结果。

两个独立 React 根还要检查前缀

多根场景和单根场景也不同。一个站点可能把账单面板和客服小部件分别挂到两个 DOM 容器。它们各自的组件树可以内部一致，但如果两个应用都生成相同范围的 ID，文档中的元素仍可能冲突。useId 文档说明，可以给 createRoot 或 hydrateRoot 设置 identifierPrefix，让不同应用的生成 ID 使用不同前缀；若这棵根也在服务器渲染，服务器渲染和客户端 hydrateRoot 必须使用同一个前缀。只有一个 React 应用时，通常不需要额外设置这个选项。

可以把这个边界记录成一张假设配置表，而不是笼统地“全站加个前缀”：

独立根       服务端前缀     客户端 hydrateRoot 前缀
账单应用     billing-       billing-
客服应用     support-       support-

这里每一行是一组服务端与客户端配对；两行的前缀不同，是为了区分独立根；同一行左右相同，是为了让该根自身水合时使用相同配置。若只在服务器侧改了账单前缀，客户端仍用默认值，树即使相同也可能在 ID 上分叉。这个表只是配置思路，并非已运行的代码或经过生产验证的部署方案。

把列表 key、业务 ID 和 DOM ID 分开验收

可以按四步检查。第一，重复渲染两个密码字段，检查每个 aria-describedby 目标确实存在，并且它只指向自己对应的帮助文字；不要只检查 ID 字符串非空。第二，插入或重排一组地址数据，验证输入草稿继续跟着稳定的数据 key，而不是跟数组位置或 useId 一起移动。第三，针对 SSR 检查服务端 HTML 与客户端首次 render 的 DOM 结构和数据是否相同；再单独测试浏览器状态加载后允许发生的后续更新。第四，若页面包含多个 React 根，逐根确认 identifierPrefix 全局互异，并确认每根服务器配置与自己的 hydrateRoot 配置一致。

第一步还可以拆成两个可观察条件：属性的值能在当前文档中找到目标元素；目标元素的文本确实是该输入的帮助，而不是另一个字段的说明。出现重复 ID 时，单纯确认某个查询能找到元素仍然不够，因为浏览器返回第一个匹配节点也可能让错误链接看起来存在。对错误提示还要检查它何时添加、何时清除，以及表单提交后用户是否能定位到错误字段。这些检查不要求 ID 具有业务稳定性，却要求控件、属性和目标节点在当前渲染中保持明确的一一关系。

这份验收计划区分了 id 属性重复、引用目标错误、业务行身份错配和 hydration 树不匹配四种故障。用浏览器控制台没有警告来代替全部检查，会漏掉静默的属性差异和业务数据错位；反过来，看到一条 hydration 提示也不能直接断定是 useId 引起的，还要检查文本、属性、条件分支和初始数据。React 页面在本次查看时显示 v19.3 文档导航；这只记录官方文档页面当时呈现的版本标签，不代表本站项目安装了该版本，也不承诺 ID 在组件生命周期、列表重排或跨版本间作为持久业务号稳定。

组件与记录的状态关系还有一层边界：可计算状态与 Effect讲的是状态应由谁拥有；这里的 useId 则只解决同一 React 树中哪些 DOM 元素互相引用。为页面关联生成了 ID，并不等于记录身份正确、树形结构一致或 hydration 已通过。
