Delta 并不比 Cumulative 脆弱：关键是转换状态放在哪一层

Delta 报告相邻区间的变化，Cumulative 覆盖共同起点至当前；选型要看状态、断档与重启由哪一层承担。

正文

核心要点

  • Delta 覆盖相邻时间窗，Cumulative 覆盖共同起点到当前；重叠累计点不能直接相加。
  • Delta 将聚合状态推向接收端，Cumulative 要发送端保存先前测量；选择取决于哪一层能承担状态与恢复。
  • 起点、间隔、重复窗口和逻辑写入者身份都影响点的含义；验收应验证这些失败路径。

Delta 并不比 Cumulative 脆弱，Cumulative 也不会自动让指标可靠。两者描述的时间区间不同，也把保留状态的成本放在不同位置。接入时应先保留指标身份、起止时间和重启语义，再决定由 SDK、Collector 还是后端完成转换；把这些信息剥掉后再相加，数值即使看起来平滑，也可能已经重复计数。

先看一个会双计的序列

设想某个服务在 10 秒内处理了 8 个请求，下一段 10 秒又处理 11 个。Delta 点分别表示两个不重叠区间，值是 8、11，两段合计 19。Cumulative 点如果从同一时刻开始，则依次表示“起点到第 10 秒”为 8、“起点到第 20 秒”为 19。把这两个累计点直接求和会得到 27，前 10 秒的 8 个请求被计算了两次。

这个小序列是解释语义的假设例子，不是本站采集的生产数据。它说明问题不在于选了哪种英文标签，而在于点的时间窗是否重叠。只拿到 metric name、数值和单位，接收方无法判断 19 是新发生的 11 个请求，还是从启动以来的总量。图表若只显示数值和横轴，错误也未必显眼。

类型也要先核对。OTLP 的 Sum 与 Histogram 支持 Delta 或 Cumulative；Sum 还区分单调和非单调。Gauge 表示某个时点采样到的值，模型在时间对齐时使用窗口内最后一次样本，并没有默认的加法聚合语义。把温度或当前队列长度这样的 Gauge 当成区间增量累加，时间性选得再准确也会得到错误答案。Histogram 是一段观察值分布的压缩表示；跨时间或实例合并时，要核对属性和聚合结构是否兼容，不能把两个分位数直接相加。Temporality 只回答“这个可加和量覆盖哪段时间”，不证明两个对象在其他方面可以合并。

OpenTelemetry Metrics Data Model 把 TimeUnixNano 定义为测量生效的时间，把可选的 StartTimeUnixNano 用于表达序列的起始和连续性。Delta 的相邻点推进 start time，覆盖相邻区间；Cumulative 的连续点重复共同 start time，覆盖范围逐步扩展。这个时间信息是值含义的一部分，不应在 Collector 转换或后端汇总时被当成可删的附带字段。OpenTelemetry 指标数据模型当前文档导航标示规范版本 1.63.0；其中 Temporality 小节为 Stable，而 Resets and Gaps 小节仍标为 Development，本文按这一区别限定表述。

选择的是状态放置位置

Cumulative 的发送方需要记住此前测量，并持续报告自共同起点以来的值。OpenTelemetry 规范指出，累计单调和的收集出现间歇失败时，缺口可以从前后累计测量间接恢复为较大的区间变化；代价是发送端要按序列基数保留先前测量。对于实例数多、属性维度高的指标，这笔状态可能不小。

Delta 发送方只报告新时间窗里的变化，不必在本地维持从起点算起的累计状态。状态可以转移到下游，转换器也可以不重建累计序列，而直接计算区间变化率。这样做会让接收端承担状态与重聚合成本，或者让查询端必须正确理解每个区间。官方数据模型列出的用例包括无状态客户端发 Delta、由有状态的服务端 Collector 聚合为更长窗口或转成 Cumulative；这是一种设计路径，不是所有 SDK 或后端都会自动采用的默认行为。

因此先问状态应由谁承担，而不是先问哪种 temporality 更好。客户端是否会频繁扩缩、进程内存是否受限、Collector 是否有稳定持久化、导出丢失能否接受、后端能否识别区间、采集流是否可能重放，都会改变选择。状态保存在哪里，就要说明它何时建立、在重启后如何恢复、丢失时发出什么信号，以及重复数据怎样识别。

例如，短命任务不断创建且 attributes 基数较高时，让每个客户端都保留完整累计状态，可能把内存成本分散到许多进程；改发 Delta 可以把聚合状态交给集中 Collector。但集中层若重启并丢掉了“已经见过哪些窗口”的状态，随后收到重放数据时就可能重复累加。相反，长时间运行、单进程持有稳定序列的服务，可能更容易维护 Cumulative；但它仍需记录 reset，并避免多个副本争用同一身份。这个比较只说明成本在哪里，不据此断言哪种方案在特定部署中更省内存或更可靠；这些结论需要在目标 SDK、Collector、属性规模和交付方式下验证。

重启、断档和双写不是一个问题

累计值从 500 变成 12，不能简单解释为负 488 次请求。它可能是进程重启后从新起点重新累计，也可能是两个写入者交替上报相同序列。看 start time 与 point time，接收方可能识别新序列或部分缺口；但 OpenTelemetry 把 resets and gaps 的规范状态标为 Development。不要只凭“遵循 OTLP”就假定所有后端对未知起点、丢失首点、乱序或覆盖写入采用相同算法。

重启后的第一个累计点还有一个边界：当 StartTimeUnixNano 等于 TimeUnixNano 时，模型把它表示为起点未知的新序列，点本身是零时长，不能把它直接当成一个普通区间的增量。若这个首点丢失，后续累计点可能被误认为一次已知起点的真实重置，接收端有机会把变化算多。规范建议的这类起点状态仍处在 Development；在真实后端验收时应单独构造“新序列首点丢失”用例。

Delta 也不会因区间短就自然免疫丢点。假设 10 到 20 秒的点成功送达，20 到 30 秒的导出失败，30 到 40 秒的点又到达。若接收端只把相邻值相加，却不检查区间边界，就可能把缺失的 10 秒隐藏在一个看似正常的总量中。它不应默默将缺口补成零；是否补值、插值或标记未知，是存储与查询策略，必须明确。

还有多写入者问题。两个实例如果错误地使用相同 Resource 与属性身份，可能同时写同一个时间序列；交错的累计点看起来像重置，Delta 窗口则可能重叠或重复。OpenTelemetry 的 Single-Writer 小节要求一个逻辑写入者，并把多个写入者视为错误状态；因此转换器不能只根据 metric name 合并，还应保留 Resource、Scope 和 attributes 等序列身份。去掉 service.instance.id 这类维度做空间聚合，也要确保聚合结果只由一个逻辑位置写出。

把时间语义写成接入契约

给新指标开接入单时，下面这组字段比一句“这是计数器”更有用：

字段 需要说清的内容
数据类型与单位 Sum、Histogram 等类型，以及单位是否一致；单位不同的流不能直接相加。
Temporality Delta 或 Cumulative；说明点表示相邻区间还是共同起点至当前。
序列身份 Resource、Scope、metric name 和 attributes；哪些维度可删除，删除后如何避免多写入者碰撞。
时间戳与起点 谁生成 start/end，重启或新序列如何表示；接收端如何识别缺口。
转换状态 在 SDK、Collector 还是后端转换；状态按什么键保存，处理器重启后丢失意味着什么。
交付语义 重试、重复导出、乱序和部分丢失如何检测或标记；不可判定时是否拒绝、告警或保留缺失。

这不是 OpenTelemetry 要求的固定表单，而是根据数据模型字段与状态权衡整理的工程检查项。转换也不是只有加减法：Delta 到 Cumulative 需要对同一序列正确累积不重叠窗口；Cumulative 到 Delta 则需要前一个可比较点，并处理重置和缺失。OpenTelemetry 允许在适用条件下转换 temporality，但不会替具体团队决定状态存储、交付恢复和告警策略。

对于 Delta，接收端可以把“序列身份加起止时间”作为检查重复窗口和发现间隔的依据。这是防御性设计建议，不是规范要求固定某个去重键。如果同一窗口因重试到达两次，盲目累加会把它算两遍；如果较晚的窗口先到，接收端至少应能把乱序与真实空窗区分开，或把状态标成待处理。对于 Cumulative，接收端更关心共同起点是否变化、数值是否由同一逻辑写入者推进，以及重启后的首点能否代表已知的变化量。两边都需要可靠的序列身份；只按 metric name 去重，可能把不同实例压成一条，也可能把同一实例拆散。

验收可以用可控输入覆盖连续两段、漏掉中间点、重复发送、累计重启、转换器重启和两个写入者重叠。每一例都记录输入时间窗、预期输出以及应产生的告警或缺失标记。这里只提出测试方案，没有执行 Collector 或 SDK 实验，也没有测量可靠性、延迟或内存；上线前应在实际组件版本和配置中验证。验收的重点是故障后还能解释“这个数字覆盖什么”，而不是仅确认导出 API 返回成功。

传输时间性也不会决定查询端应如何汇总。对于累计计数器，先在每条源序列上解释时间变化，再做跨序列聚合，通常比直接把重叠累计值相加更符合数据含义；相关查询边界见为什么计数器要先求速率再聚合。选择 Delta 或 Cumulative 的落点，应由状态、交付路径和故障恢复能力共同决定，并在接入契约中写明。
