手机布局过关，为什么 400% 放大后还会丢内容？

移动端截图不能代替放大重排检查。用 320 CSS 像素视口核对内容、任务和例外区域，避免把隐藏溢出误当修复。

正文

手机宽度下能看见页面，不代表桌面浏览器放大后仍保留同样的信息和操作。检查放大重排时，应把视口收窄到相当于 320 CSS 像素，沿着真实任务核对内容是否仍可读、控件是否仍可用；只有确实需要二维布局来理解或操作的局部内容，才适用二维滚动例外。单看横向滚动条消失，很容易把“内容被藏起来”误判成通过。

手机视口和浏览器放大检查的是不同状态

手机测试通常改变设备或浏览器视口，并可能触发响应式断点。桌面浏览器放大则会缩小可见 CSS 视口，同时改变文字、组件和固定区域的占用。两种状态最终都可能变窄，却不一定经过同一组布局规则：页面可能专门为手机改成单列，却在桌面放大时仍保留最小宽度；也可能在手机断点隐藏侧栏，但放大状态下连侧栏里的唯一搜索入口也被移除。

W3C 的 WCAG 2.2 成功准则 1.4.10 Reflow（AA）要求：纵向滚动内容在相当于 320 CSS 像素宽的视口中呈现时，不丢失信息或功能，也不要求用户为阅读内容同时横向、纵向滚动。W3C 说明，从 1280 CSS 像素宽度起放大到 400% 是达到该宽度的一种等效方式。它是尺寸等效解释，不是说所有浏览器、操作系统工具栏和实体屏幕上的“400%”都会得到完全相同的可视区域；验收应看实际 CSS 视口和页面表现。水平书写方向的内容是本文讨论的主路径；为水平滚动内容设计的页面，对应高度条件是 256 CSS 像素。

例如，一个后台订单页在手机断点下把三栏改成卡片，移动截图看上去没有溢出；桌面放大后，页眉、固定操作栏和表格最小宽度却占满了横向空间。用户滚动时，订单号能看到，负责提交的按钮却被固定栏盖住。这里至少有两个独立问题：内容是否能在窄视口中阅读，以及任务最后一步是否仍能操作。响应式视觉截图只回答了部分问题。

因此测试记录应写下采用的视口宽度或放大路径、页面状态、滚动方向，以及完成了哪些操作。本文的订单页是用于推演的假设例子，没有对某个实际产品执行浏览器缩放测试，也不构成任何网站的合规结论。

先追踪任务，再判断溢出

测试一个页面时，先选一条需要跨多个区域的任务路径。例如订单处理可以是：找到指定订单、确认金额和收件信息、读取错误提示、执行提交、确认结果并返回列表。随后在默认桌面、窄手机视口和放大至目标等效宽度下重复相同路径。不是每一步都需要截图，但要能回答：信息在哪里、控件是否可见和可触达、状态变化后是否仍有下一步。

逐项检查比全页只看滚动条更可靠。固定高度容器可能把末尾说明裁掉；overflow: hidden 可以让滚动条不出现，却会一并截断按钮或错误消息；固定页脚可能遮住焦点所在的控件；侧栏可能在窄状态消失，却没有折叠入口；宽度固定的输入框可能把标签挤出可视区。页面没有横向滚动只是一个观察结果，不能单独证明内容仍然可用。

一个实用记录方法是把每个任务步骤写成“预期信息或操作—实际位置—到达方式—观察到的阻断”。比如“提交失败后读取原因—错误文本在表单下方—向下滚动可到达—固定底栏覆盖重试按钮”。这个描述更能指导修复：问题可能是容器裁切、层叠顺序或固定区域占位，而不是笼统地“移动端不适配”。修复后用同一条路径复测，避免换掉测试对象后把缺陷当作已关闭。

横向滚动例外只覆盖需要二维关系的局部

WCAG 2.2 的 Reflow 准则允许对“使用或含义需要二维布局”的内容保留二维滚动。W3C 给出的例子包括地图、理解内容所需的图像、视频、游戏、演示文稿、数据表（但不是其中每个单元格），以及操作时需要同时看到工具栏的界面。例外的判断点不是开发实现是否困难，而是去掉二维关系会不会损害信息理解或功能。

假设某财务页面有一张列很多的对账表。每行的金额和多个期间之间存在横向对应，压缩为卡片会让用户难以比较同一行，因此表格区域可以单独保留水平滚动。但页面标题、筛选条件、说明文字和“导出”按钮并不因此自动取得例外。它们仍应在窄视口内可访问。表格单元格本身也应检查文字是否被裁剪；W3C 的解释说明二维例外适用于表格关系，并不意味着单元格内容可以随意消失。

地图同理。地图本体可能需要两个方向平移，但地点名称、筛选控制和结果列表可以采用单列排列；若地图是理解地点的唯一来源，还应检查用户能否通过文字列表或其他等价交互获得关键信息。这里的替代形式是产品设计与验证问题，不能简单用“地图属于例外”结束审查。

界线也有反例。若普通文章正文被包在一个固定宽度的内部面板里，导致读者必须先横向拖动才能读完每一行，单纯给该面板加上“这是二维内容”的标签，并不能证明文字本身需要二维关系。相反，代码缩进、嵌套列表等可能需要保留某些二维结构；应尽量让容器适配视口，并单独判断局部内容的必要性。例外要具体到区域和理由，不能扩展成整页的通行证。

视口、缩放和内容都要可复现

W3C 用 CSS 像素而不是设备物理像素定义目标尺寸。设备像素比、操作系统缩放、浏览器工具栏和滚动条都会影响可视区域；将屏幕分辨率设置为 1280 像素，并不保证网页 viewport 仍有 1280 CSS 像素。实际检查时可以直接使用开发者工具设置约 320 CSS 像素宽度，也可以从合适的基准宽度放大，并确认最终 viewport 确实达到目标。记录工具、初始宽度和最终视口，其他人才能复现。

用真实内容填充状态也很关键。短标签、空表单无法暴露长地址、较大金额、错误原因和多行说明引起的换行问题。构造测试数据时不必假装是真实用户记录，可以在测试环境填入代表性长文本；应明确这是测试数据。检查所有关键状态：默认、验证失败、加载后、成功后、权限不足、列表为空，以及需要确认的弹窗。尤其要确认隐藏或折叠的内容有可操作入口，并且键盘焦点不会落在用户看不到的控件上。

一个可复核的验收表可以只记录必要证据：页面和状态、目标 CSS viewport、开始和结束任务步骤、发现的信息损失或操作阻断、相关区域是否主张二维例外及理由、修复版本和复测结果。若测试环境或浏览器无法提供标准要求的尺寸，应记录无法覆盖的范围；这不能凭空变成通过结论。单项 Reflow 检查也只覆盖 WCAG 的一个成功准则，不能推出页面符合整套 WCAG。

修复后检查容易被牺牲的内容

常见修复包括让布局改为单列、允许文本和控件换行、移除不必要的固定高度、把固定页脚改为参与文档流，或为局部二维内容保留独立的滚动区。选择哪一种取决于该区域的功能和操作顺序。给整个页面添加 overflow-x: hidden 可能暂时消除滚动条，却会剪掉内容；把所有字体缩小也可能让窄屏截图更紧凑，却削弱放大所要解决的可读问题。先定位失效机制，再改最小范围。

复测必须包含原先失败的视口和路径，也要回到窄手机布局确认没有引入新的遮挡或顺序变化。对比修复前后时，保留同一组长文本、错误状态和任务步骤。若信息通过折叠区域、对话框或另一视图提供，应验证入口清楚、内容完整，并能返回原任务。W3C 的 F102 失败技术明确指出，宽视口下可见的内容在 320 CSS 像素重排后不再显示，且没有其他方式到达，是一种失败情形；隐藏组件必须有等价信息或功能路径。

这套检查能找出布局与任务连续性问题，但不替代键盘操作、屏幕阅读器、文本调整和其他无障碍准则的验证。如果团队需要继续检查覆盖样式后文本会否裁切，可参考文本间距设置后的内容损失；表单错误和业务状态的验证边界见表单校验与服务端权威。

一个可执行的重排验收顺序是什么？

先选任务与代表性状态，再把页面设置为目标等效视口；沿任务路径记录内容、控件、反馈和下一步是否仍可访问。对每个被移除或改为横向滚动的区域，说明它是否确实依赖二维关系，以及相同信息是否可通过合理路径获得。修复后复测原失败点和手机布局，并保留视口、状态、步骤和结果。这样得到的是一份可以复查的 Reflow 验收记录，不是整站无障碍认证。
