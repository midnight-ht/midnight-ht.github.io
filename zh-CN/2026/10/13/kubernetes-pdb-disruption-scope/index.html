配置 PDB 后，哪些中断仍然可能发生？

PodDisruptionBudget 只约束经过 Eviction API 的自愿驱逐。节点故障、直接删除与控制器滚动更新各有不同边界。

正文

核心要点

  • PDB 保护特定 Eviction API 自愿驱逐，不能阻止非自愿故障，也会被直接删除绕过。
  • drain 因预算等待时，检查 selector、可用副本、替代 Pod 调度与不健康 Pod 策略，不能假定删除预算就能恢复容量。
  • 百分比预算向上取整；把实际副本数代入计算，并将容量、readiness 与滚动更新策略分开验证。

PodDisruptionBudget（PDB）只约束通过 Kubernetes Eviction API 发起的特定自愿驱逐；它不会阻止节点突然故障、直接删除 Pod，也不会替 Deployment 控制滚动更新速度。配置 PDB 的实际问题不是“集群里还会不会掉副本”，而是“哪些操作者走了受预算保护的 API，预算按哪些 Pod 计算，以及剩余副本是否真的能继续提供服务”。

PDB 管的是请求路径，不是所有结果

Kubernetes 文档把中断分为自愿和非自愿两类。节点硬件故障、内核崩溃、节点网络分区以及节点资源耗尽造成的驱逐，都可能让 Pod 不可用；这些非自愿中断不能被 PDB 阻止，但会计入预算。维护者通过 Eviction API 请求移走 Pod 时，API 会根据预算检查是否允许该次自愿中断；节点 drain 通常使用这条路径，预算暂时不允许时，驱逐请求会被拒绝，工具可以重试直至成功或超时。

因此，PDB 更像维护操作的准入门槛，而不是副本的防护罩。若一个副本所在节点突然失联，PDB 不会把该 Pod 搬回来，也不能阻止故障扩散；它只能让后续遵守预算的驱逐请求看到当前可用状态。另一方面，直接删除 Pod 或删除 Deployment 会绕过 PDB。管理员脚本、云厂商维护工具和人工命令是否尊重预算，取决于它们是否请求 Eviction API；不能从集群里存在一个 PDB 对象推断每个删除动作都受它约束。

官方文档标注 PDB 自 Kubernetes v1.21 起稳定。本文核对的是当前 Kubernetes 文档页面，未连接集群，也未执行 drain 或删除操作。具体集群版本、托管平台与维护工具的调用方式仍需单独确认。

用一次节点维护看预算如何变化

设想一个 Deployment 的期望副本数为 3，三个 Pod 分布在三个节点，PDB 的 minAvailable 为 2。这里的数字只是机制示例，不代表任何实测容量。第一次 drain 其中一台节点时，Eviction API 在其余两个副本可用的前提下允许一个 Pod 进入终止流程；预算中的可用余量随之减少。控制器创建替代 Pod，但替代 Pod 尚未 Ready 时，它不能被当作可用副本。若此时维护者又请求驱逐另一台节点上的副本，第二次请求可能被拒绝，因为那会使可用副本跌破 2。

重试并不等于集群有能力完成维护。若调度器无法给替代 Pod 找到资源，替代副本会持续 Pending，预算也可能持续不恢复，drain 最终等待到超时。此时“预算阻止了继续驱逐”是正常信号，后续决策应检查节点可分配资源、Pod 的 requests、亲和与拓扑约束、存储绑定和就绪状态，再决定补充容量、调整维护并发还是安排有记录的例外。强行删除预算只会移除这道门槛，不会让 Pending Pod 获得节点，也不会提高服务容量。

如果在开始维护前已有一个副本不健康，结果也可能不同。文档说明 PDB 无法挽回该故障，而当前可用数会影响后续预算。对于不健康 Pod 的节点驱逐，默认策略可能等待 Pod 恢复后才允许继续；官方建议评估 unhealthyPodEvictionPolicy: AlwaysAllow，使 drain 能驱逐行为异常的 Pod。选择它意味着维护流程可能继续处理不健康副本，不能把它理解为恢复能力或无风险开关；是否适用要结合业务是否承受剩余副本减少、故障是否持续以及回滚路径评估。

minAvailable 数字不等于真实服务能力

PDB 按 Pod 的可用状态和工作负载期望副本数计算预算。它不知道每个副本的吞吐差异、请求是否经过正确的 Service 端点、多个 Pod 是否落在同一机架，或依赖的数据库是否已经过载。三个 Ready 副本也可能共享单一故障域；两个剩余副本可能因为连接池、CPU 或下游限流而无法承接当前流量。预算只回答 Kubernetes 能否接受某个受保护的驱逐请求，不回答应用的服务等级是否仍被满足。

选择整数和百分比也会改变边界。官方配置说明对百分比向上取整：例如 7 个期望副本配置 minAvailable: "50%" 时，至少要保留 4 个；maxUnavailable: "30%" 也按向上取整计算。因此比例阈值并不总是保守的“精确百分比”。期望副本只有 1 个时，maxUnavailable: "30%" 仍可能允许驱逐这 1 个副本，实际不可用比例会达到 100%。对小规模或仲裁型服务，评审时应把实际副本数代入并写出整数结果，不要只审 YAML 中的百分比字符串。

这也解释了为什么副本分散、探针语义和容量测试要与 PDB 一起设计。反亲和或拓扑分布策略降低多个副本同故障的概率；readiness 决定哪些 Pod 被视为可接收流量；负载验证判断剩余实例的真实承载能力。三者互相补充，却都不能由 PDB 字段代替。尤其是 readiness 过于宽松时，预算可能把不能处理请求的副本算作可用；过于严格时，维护可能长期无法推进。要校验探针与业务服务能力的对应关系，需要真实流量或具代表性的测试证据，不能只看 YAML。

滚动更新为什么仍需单独设置策略

应用滚动更新产生的不可用会反映在预算相关状态中，但 Deployment 和 StatefulSet 执行自己的滚动升级时，不受 PDB 直接限制；更新中失败如何处理由各工作负载对象的更新策略配置。换言之，PDB 可能显示预算已经消耗，却不一定能阻止工作负载控制器继续按自身策略替换 Pod。发布期间应分别检查 maxUnavailable、maxSurge、就绪门槛与进度期限，并核实它们是否适配应用的启动时间和容量。把 PDB 当作 Deployment 的滚动更新闸门，会留下一个错误的安全假设。

同样，终止过程还有独立边界：Eviction API 发起的驱逐会遵守 Pod 的 terminationGracePeriodSeconds，但宽限期只提供退出时间，不保证进程一定完成排空，也不替代连接切换与进行中任务处理。相关机制可参阅应用进程退出与平台终止预算。

维护前应验证什么

先盘点副本由哪个控制器管理、PDB selector 实际匹配哪些 Pod、期望副本数和当前可用数，再检查维护工具是否走 Eviction API。随后在测试环境或受控维护窗口验证：单次驱逐被允许时预算如何变化；已有副本不可用时请求是否被拒绝；替代 Pod 因资源不足无法调度时 drain 如何等待和超时；不健康 Pod 策略改变后会发生什么。记录集群版本、工具版本、每一步 API 或事件以及恢复条件。本文没有执行这些操作，以上是验证计划而非运行结果。

如果预算长期不允许维护，先分辨是 selector 选错、真实可用副本不足、替代副本无法调度，还是健康策略令不健康 Pod 阻塞；然后分别处理对应原因。若必须临时突破预算，应说明谁批准、移除的是哪一道约束、预计暴露的业务风险、观察信号和恢复时间，并确保服务侧有独立保护。PDB 的价值是把特定维护请求与当前可用状态连接起来。它不能替代故障域设计、滚动更新策略、容量规划、监控或应用自身的容错。
