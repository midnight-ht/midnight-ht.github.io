pytest 参数化用例为何互相污染？先查对象共享，再选隔离方式

pytest 参数化值按原样传入，不会自动复制。沿对象身份追踪列表、嵌套引用和预期值，再决定每例构造、fixture 或复制。

正文

pytest 参数化的值按原样交给测试函数，不会自动复制。若参数表第1行与第2行引用同一个列表，第一条用例的原地修改会改变第二条看到的起始值。修复前先沿对象身份检查共享发生在哪一层，再决定每例构造、fixture 工厂、浅复制还是深复制；顺序调整只能暴露问题，不能定义隔离边界。

参数表有两行，不代表有两份对象

pytest 的参数化文档明确写出：参数值原样传递，不做复制；测试修改列表或字典后，修改可能反映在后续测试调用中。Python 的赋值与复制说明补上了语言层的原因：把一个对象赋给另一个名字，建立的是绑定关系，不会创建对象副本。

看一个用于说明机制的假设例子。下面只是代码推演，没有实际运行，也不是某个项目的失败记录：

import pytest

shared_items = []

@pytest.mark.parametrize(
    "items, item, expected",
    [
        (shared_items, "A-7", ["A-7"]),
        (shared_items, "B-2", ["B-2"]),
    ],
)
def test_append_one_item(items, item, expected):
    items.append(item)
    assert items == expected

参数表中的两个元组是不同的，但它们的第一个位置都指向 shared_items。第一条调用把 A-7 加到那个列表里；第二条开始时，列表已经含有 A-7，再追加 B-2 后得到两个值，而该行预期只含 B-2。原因不是参数名 items 重复，也不是 pytest 应替测试清理输入，而是两行把同一个可变对象交给了两次调用。

反过来，两个列表内容相同也不等于身份相同。若参数行写成 ([], "A-7", ["A-7"]) 和 ([], "B-2", ["B-2"])，两个列表字面量分别创建，顶层输入不会因这条路径彼此共享。排查要问的是“这两个位置是否指向同一对象”，而不是“打印出来是不是一样”。在 Python 中，临时使用 Python 的身份运算符 is 能回答两个引用是否指向同一对象；== 只比较内容。

别只检查外层字典

共享不一定一眼可见。考虑 template = {"cart": {"items": []}, "currency": "CNY"}。copy.copy(template) 会创建一个新的最外层字典，但嵌套的 cart 和 items 仍是原对象中的引用。若一条用例执行 payload["cart"]["items"].append("A-7")，另一份浅复制仍会看到这个项目。只对最外层做 is not 断言，就会误以为测试数据已经完全隔离。

Python copy 文档把差别说得很清楚：浅复制创建新的复合对象，再把内部对象的引用放进去；深复制则递归复制所包含的对象。这个定义不是“浅复制不安全、深复制总正确”。如果对象图里有循环、自定义复制行为、文件句柄、连接或有意共享的只读对象，通用深复制可能失败、复制过多，或不符合对象本身的语义。测试也可能无意中把每个用例都变成昂贵的独立资源构造。

选择时先列出会被测试修改的字段和对象所有者。若输入只含标量和短列表，为每条参数行分别创建输入通常最直观；如果只有外层容器需要分开、内部成员是不可变值，浅复制可能足够；若嵌套结构确实属于每例独立的可变状态，可以选择深复制，但应把复制成本和自定义类型语义纳入判断。不要为了省事从一个大型模板复制整棵对象树，却没有说明哪些成员应该共享。

需要运行时构造时，让参数描述与对象分开

参数本身可以是不可变的描述，而不是已经准备好、并可能被多例共用的可变对象。例如参数行提供一组初始项目和操作名称，测试开始时再构造列表。若构造要做验证或较昂贵的准备，可以让 pytest fixture 接收参数后创建对象：官方间接参数化示例说明，indirect=True 会把输入送到 fixture，并通过 request.param 读取。

这里隔离是否成立，仍取决于 fixture 具体创建了什么。函数作用域 fixture 默认在每个测试结束时销毁，适合需要按测试重新建立的对象；但若 fixture 返回一个外部共享容器、使用更宽的作用域，或把同一嵌套成员塞进每例结果，直接采用 fixture 这个词并不能消除别名。fixture 的作用域描述资源实例何时创建和销毁，不是对任意参数对象做深复制的承诺。

一个实用模式是只把不可变规格放进参数表，再由每次 fixture 调用创建可变输入：

@pytest.fixture
def payload(request):
    return {"items": list(request.param)}

@pytest.mark.parametrize(
    "payload, item, expected",
    [
        (["seed-a"], "A-7", ["seed-a", "A-7"]),
        (["seed-b"], "B-2", ["seed-b", "B-2"]),
    ],
    indirect=["payload"],
)
def test_append(payload, item, expected):
    payload["items"].append(item)
    assert payload["items"] == expected

这个写法仍要根据对象层级审查：list(request.param) 只创建新的外层列表；示例里的成员是字符串，因而无需再复制内部可变对象。若参数规格本身含有嵌套字典或列表，fixture 应针对需要独立的字段进行显式构造，而不是默认浅复制就够。

预期结果也要拥有自己的来源

输入和预期值如果共享可变对象，测试可能把正确答案一起改掉。比如用参数输入的同一个列表派生 expected，被测函数再原地修改列表，断言两边可能同步变化。这样的断言即使通过，也没有独立判断实现是否正确。把预期写成独立的不可变值，或由明确的规格计算，能减少这种自我认可；但也不要复制被测实现的算法来生成预期，否则同一逻辑错误会同时污染两边。

若业务行为本来就是有状态的连续过程，多个操作共享同一对象可能正是测试目标。此时不要把这些步骤伪装成互不相关的参数用例：可以在一个测试中显式按顺序执行状态转换，逐步断言每个中间状态。关键不是消灭所有共享，而是让共享和状态演进成为测试契约的一部分，不能靠参数列表的偶然顺序暗示。

用验证检查对象边界，而不只看测试变绿

一组有针对性的检查应覆盖几个不同问题。首先检查两行顶层参数及嵌套成员的身份，确认哪些值应该相同、哪些必须不同。其次让一条用例修改可疑字段，再观察另一条开始时是否仍满足独立初始条件。随后分别运行可疑案例与成组运行，改变相邻案例，确认结果没有依赖此前留下的内容。最后确认预期值并非从同一可变输入别名而来。上述都是建议的验证步骤，不代表本文执行过 pytest 或得到了通过/失败日志。

若单独运行通过、成组运行失败，顺序敏感是线索，仍可能是 fixture、模块变量、缓存、数据库或其他外部状态。相邻问题可以参看fixture 生命周期与测试隔离以及Mock 调用参数的可变引用；前者关心资源作用域，后者关心一次调用后的引用快照，不应把它们混成同一个 pytest 参数化故障。

最后的选择可以很具体：参数只需保存输入值时，直接使用每行独立构造的数据；参数代表昂贵的运行时资源时，用 fixture 按明确作用域创建；只需要断开外层容器时用浅复制；嵌套可变数据必须独立时才考虑深复制或逐字段构造。无论采用哪种方式，都保留一条能证明每例起始状态与预期值独立的检查。
