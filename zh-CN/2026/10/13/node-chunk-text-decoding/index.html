网络分块切断中文字符，应该在哪一层处理？

先用带状态的 UTF-8 解码器保留跨块字符，再按协议拼消息；解码正确仍不代表记录完整。

正文

核心要点

  • 字节块不是字符边界；用 StringDecoder 或 Readable.setEncoding 让 UTF-8 解码跨块保留状态。
  • 解码和消息分帧是两步：解析换行或长度字段，并为未完成记录设上限。
  • 流结束时要分别处理 decoder 残留字符和最后一条未结束消息；替代字符不等于原文恢复。

网络读取给应用的是任意长度的字节块，不是完整字符或业务消息。处理 UTF-8 时，Node.js 的 StringDecoder 或 Readable 的 setEncoding('utf8') 可以保留跨块的字符状态；换行、长度前缀、JSON 文档或其他记录边界仍要由协议解析器处理。字符解码解决“这些字节怎样组成文本”，不会自动回答“这条消息在哪里结束”。

为什么一次 Buffer.toString() 可能切坏字符

UTF-8 字符由一到四个字节组成，读取流的块边界由缓冲区、网络和调度决定，与字符边界无关。假设一个三字节字符的字节分别落在三个 Buffer 里。对每个 Buffer 独立调用 toString('utf8') 时，第一块末尾缺少后续字节，解码器没有跨调用状态可供等待；结果可能出现替代字符，随后两块也不会自动把它修回原字符。只要任意多字节字符能跨块，代码就不能假定“一个 data 事件等于一段完整文本”。

Node.js v26.13.1 的 node:string_decoder 文档说明，StringDecoder.write() 会把 Buffer 末尾尚未构成完整多字节字符的字节留在内部，等待下一次 write() 或 end()；文档示例把欧元符号的三个 UTF-8 字节拆成三次写入，最后一次通过 end() 输出字符。stringDecoder.end() 还会处理未完成残留：若字节最终仍组成不了有效字符，会依编码规则输出替代字符。它保住连续输入中暂时被切开的字符，却不能恢复已经丢失、乱序或协议规定为非法的输入。

这不是只适用于中文。UTF-8 的其他非 ASCII 字符、UTF-16 的代码单元也可能跨块；具体解码器支持哪些编码应按 Node 文档核对。下面是一个说明状态交接的最小片段，本文没有在部署环境或真实 socket 上执行：

const { StringDecoder } = require('node:string_decoder');
const decoder = new StringDecoder('utf8');

const pieces = [Buffer.from([0xE4]), Buffer.from([0xBD]), Buffer.from([0xA0])];
let text = '';
for (const piece of pieces) text += decoder.write(piece);
text += decoder.end();
// 按 UTF-8 编码，这些字节共同表示“你”；此代码仅作机制示意，未执行。

关键不是三块怎样划分，而是同一个逻辑输入要持续使用同一个解码状态。若每次回调都创建一个新 StringDecoder，残留字节仍无法与下一块合并；若把互不相关的连接共用一个 decoder，连接甲的残留又可能混入连接乙。通常应让 decoder 的生命周期与一个连续字节流一致，并在结束、取消或错误时按调用方策略完成或丢弃这份状态。

选择 setEncoding 还是 StringDecoder

如果你消费的是 Node.js Readable，并希望之后收到字符串而不是 Buffer，可以在读取数据前调用 readable.setEncoding('utf8')。Node.js v26.13.1 的 Stream 文档明确说，Readable 会正确处理跨块到达的多字节字符；设置编码后，data 事件给的是字符串，未设置时通常给 Buffer。这样可把字符解码留在流对象中，适合后续处理确实以文本字符串为单位的消费方。

如果应用需要接触原始 Buffer、在多个 Transform 之间显式放置解码阶段，或自行维护消息解析器，可以用 StringDecoder，由应用清楚决定何时调用 write() 和 end()。两种方式都不替代消息分帧，也不负责判断编码协议是否正确。若协议规定 UTF-8，就固定使用 UTF-8 并定义无效序列的处置；不要尝试多种字符集直到文本“看着像对的”，因为可读外观无法证明原始字节被无损解释。

另一个重要选择是保留字节还是尽早转成字符串。如果协议长度字段以字节计数，必须在解码前按字节读取头部并精确截取指定数量；若长度以字符计数，则需要在按约定解码后计数，并确认协议中的“字符”究竟指 Unicode 码点、UTF-16 代码单元还是别的计数单位。否则多字节文本会造成边界偏移。解码器只能把字节映射为文本，不能替协议定义长度单位。

解码之后还需要一台分帧状态机

以换行分隔的文本为例：完成字符解码后，将输出附加到 pending，循环提取其中完整的 \n 行，把未遇到换行的尾部继续留在 pending，等下次解码输出补上。一个 Buffer 可能只包含半行，也可能同时包含多行；解码器每次返回的字符串都不等于一条记录。若直接把每次输出交给 JSON 解析器，记录刚好跨块时就会被拆坏，几条记录同块时又会被误合并。

分帧器还要定义 \r\n 与 \n 的处理，剥离分隔符是否属于协议语义，以及同一输入结束时仍留有 pending 的处理规则。最后一行若没有换行，是有效记录还是截断消息，应由协议决定。不能因为连接发出了 end 就擅自补一个分隔符，再把半条业务消息交给下游。

缓存也必须有可验证的上限。若对端一直不发分隔符，只保存未完成尾部会逐渐占用内存；因此按协议定义单条消息的最大字节数或文本长度，并在超出时拒绝、关闭或转入明确的错误路径。对于用户提供的数据，还需同时考虑语义解析、权限和验证。设定上限时应记录使用的计量单位；把 pending.length 当成精确的输入字节数并不成立。

EOF、错误与状态清理要分两次判断

一个输入正常结束时，先把剩余 Buffer 交给 decoder 的 end()，再把它输出的字符串交给分帧器；然后再问分帧器的尾部是否构成合法记录。前一个判断是字符有效性，后一个判断是消息完整性。若 decoder 输出替代字符，字符输入可能不完整或无效；若 decoder 正常结束但 pending 仍有文本，则它可能是一条未结束记录。两种错误不能合并成“末尾文本有问题”，因为修复路径不同。

例如，持续接收传感器文本行的客户端可以在每个连接上配置独立 decoder 和行缓冲：一旦输出完整行，就进行字段验证并提交给后续逻辑；若连接中途被 reset，则记录 decoder 残留字节和未完成行分别有多少，按协议选择重试、丢弃或报错。连接重试开始后不能沿用旧连接的半字符或半行；否则即使新的字节本身有效，也可能和旧尾部拼出伪造记录。这是设计示例，不是某个真实设备或客户系统的执行结果。

怎样验证，而不把“不报错”当作正确

测试应构造同一段合法 UTF-8 文本的不同切块方式：按每个字节边界切开一个多字节字符；把一条换行记录拆成数块；一次输入包含多条记录；最后一块恰好结束在完整字符后但消息没有分隔符；以及 EOF 落在不完整字符中。比较各切块方式产生的解码文本和最终记录序列是否一致，并单独断言不完整字符和不完整消息的策略。再加入无分隔符超长输入，确认缓存上限会触发预期处理，而不是继续增长。

检查日志也应区分“输入字节数”“解码后文本长度”“已提交记录数”和“拒绝原因”。看到一个替代字符，不足以推断是网络截断、编码声明不符还是上游本来就发了无效字节；看不到异常，也不代表解析出的记录边界正确。本文只提出了测试办法，没有执行网络实验或代码片段，不能据此宣称某个 Node 版本或协议实现已经通过验收。输入端的字符与消息状态处理好后，输出端仍要遵守写入背压；可参阅可写流背压的继续条件。
