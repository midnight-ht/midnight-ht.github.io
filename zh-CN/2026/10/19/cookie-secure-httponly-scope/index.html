Cookie 加了 Secure，脚本为什么仍可能读到？

Secure 约束传输，HttpOnly 约束脚本读取；两者都不能替代请求条件与服务端权限检查。

正文

Cookie 设置 Secure 后，页面脚本仍可能读取它；限制脚本读取需要另看 HttpOnly。评审会话 Cookie 时，应分开回答传输通道、脚本可见性与请求能否携带三个问题，不能把浏览器工具中的一个安全标记当成全部防护。

HTTPS 传输与脚本读取各有开关

MDN 的 Set-Cookie 参考说明，Secure 将发送限制在 HTTPS 请求，localhost 有例外；它不阻止缺少 HttpOnly 时的脚本访问。因此，在本地 HTTP 环境观察到的行为，也不应未经核对直接外推到正式域名。

假设服务端返回 Set-Cookie: sid=example; Path=/; Secure，其中值只是示意。即使这个会话值随 HTTPS 请求传输，也不能据此断言页面中的 JavaScript 看不到它。若它用于服务端会话，且前端没有读取值的业务需求，评审就应问清为什么没有使用 HttpOnly，而非仅确认 HTTPS 已开启。

加入 HttpOnly 后，脚本不能经由 document.cookie 读取这个 Cookie。它约束的是访问途径，并不代表浏览器开发者工具、终端设备的所有本地访问或服务器日志都被同一属性保护。检查时应写明使用了哪种访问方式，避免把“我能在存储面板看到”误报为属性失效。

读不到值，仍可能发起带凭证的动作

同一份参考还指出，带 HttpOnly 的 Cookie 仍可随 JavaScript 发起的请求发送。是否实际携带，还受请求目标、凭证设置、Cookie 范围及浏览器规则影响。这里不能推导任意跨站请求都会带上会话，也不能推导脚本读取受限后，业务操作就自动安全。

设想同源页面存在脚本注入，攻击脚本读不到会话值，但尝试调用当前用户能访问的操作接口。这个场景是风险推演，没有执行攻击或报告真实漏洞。它说明防止值被读走和防止借用登录状态做事有不同目标；服务端仍需验证身份、对象权限与适用的请求防护，不能让某个 Cookie 属性承担这些职责。

因此，前端若只需要知道是否登录，可评估由身份接口返回必要状态，避免为了展示昵称就让脚本直接接触会话秘密。具体设计应结合现有协议，不能简单把所有前端状态都塞进 Cookie，也不能把客户端显示的登录状态当成服务端授权结论。

把验收对象写成行为

若旧页面已经依赖直接读取会话值，补上属性后可能暴露这项耦合。应先列出读取用途，区分真正需要的公开状态与不应暴露的凭证，再调整接口和界面。一次登录成功也不足以覆盖会话续期；保持页面打开、等待刷新后再次检查，才能发现后续响应是否丢失了属性。

拟议检查可以使用专门的测试会话，分别观察脚本读取、合规请求携带、非预期请求和注销后的服务端响应。不要把真实会话值复制进报告；记录属性、请求条件与结果即可。本文没有运行这组检查，因此不声称任何站点已通过安全验收。

还应查看设置、刷新与删除会话的各个响应，防止某一路径重新发出缺少属性的版本。同名值存在不同范围时，单看一次响应容易漏掉旧记录。范围问题可参看Cookie Path 与权限边界。交付结论至少说清哪个属性限制哪种行为，剩余风险由哪一层处理。
