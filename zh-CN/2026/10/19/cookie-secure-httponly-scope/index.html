Secure Cookie 为什么仍可被脚本读取？

拆开 Cookie 的传输、脚本可见性和自动携带条件，解释 HttpOnly、SameSite 与服务端授权的边界。

正文

核心要点

  • Secure 限制传输通道，HttpOnly 限制脚本读取，两者职责不同。
  • HttpOnly Cookie 仍可随 JavaScript 发起的合格请求发送。
  • Cookie 的发送范围和服务端授权需要分别测试。

会话 Cookie 带了 Secure，审查者在页面里却仍能用 document.cookie 读到它。这不是浏览器忽略了安全标记：Secure 主要约束 Cookie 随请求在何种传输通道发送；阻止页面脚本读取是 HttpOnly 的职责。真正的安全评审还要继续问第三个问题：浏览器什么时候会自动把 Cookie 带到请求里。

把三个问题放在同一张请求图上

MDN 的 Set-Cookie 文档说明，Secure Cookie 通常只经 HTTPS 发送，localhost 有特殊规则；它并不阻止脚本读取未设置 HttpOnly 的 Cookie。HttpOnly 禁止通过 Document.cookie 等脚本接口访问，但 JavaScript 发起的 fetch() 或 XMLHttpRequest 请求仍可携带这种 Cookie。因而“脚本读不到值”和“脚本不能借用户会话发请求”是两个不同结论。

设一个假设性会话头：

Set-Cookie: session=opaque; Secure; HttpOnly; SameSite=Lax; Path=/

这里的 opaque 只是占位符，不是真实会话。浏览器接收后，脚本不应通过 document.cookie 取得这个 Cookie 的值；符合条件的 HTTPS 请求仍可能自动携带它。若同源页面有 XSS，HttpOnly 减少会话值被直接读走的风险，却不能保证攻击脚本无法调用用户已获授权的接口。服务端仍须检查身份、对象权限与操作条件，页面仍要处理 XSS。Secure 与 HttpOnly 不能互相替代。

现在把 HttpOnly 去掉，仅保留 Secure。HTTPS 页面里的脚本仍可能读取 Cookie，正是标题里的现象。反过来只保留 HttpOnly、去掉 Secure，脚本可见性变了，但传输限制未随之建立。这两个负样本应在测试浏览器和服务端响应里分别检查，而不是只看开发者工具某一列打勾。测试时使用假令牌，避免在日志、截图或文章里泄露会话值。

自动携带还受哪些范围影响

Domain 决定哪些主机可接收，省略它形成更窄的仅当前主机范围；Path 决定匹配的请求路径，SameSite 调节跨站请求是否携带。MDN 特别说明 Path 不是阻止同源其他路径读取的安全措施，因此本站Cookie Path 的边界强调服务端权限检查。SameSite 可减轻部分跨站请求伪造风险，但不是授权判定。实际请求是否带 Cookie，还受请求目标、浏览器策略和跨源凭据配置影响；不要从头字段单独推定每种调用都一定携带。

还有命名前缀可以帮助收紧意外配置。MDN 记载，受支持的浏览器要求 __Host- 前缀 Cookie 同时具备 Secure、Path=/ 且不带 Domain，从而约束它只能由当前主机设置并回送该主机；__Http- 前缀还要求 HttpOnly。前缀不是服务器端访问控制，也不能替代逐项核对浏览器兼容性。若系统有多个子域共享登录，贸然改成 __Host- 还会改变原本依赖 Domain 的行为，迁移前要画出真实请求主机。

用两个观察点验证配置

第一处看响应：实际登录接口返回的 Set-Cookie 是否包含预期属性，是否意外重复设置同名 Cookie；响应来自 HTTPS 还是开发环境的 localhost 例外。第二处看浏览器行为：在允许的请求路径、另一条路径、相关子域和跨站场景分别记录请求头是否携带；再用测试页面检查脚本是否能读到目标 Cookie。跨站测试须把请求方法和凭据模式记录下来，否则结果不能解释 SameSite 的作用。这里是验收设计，未对真实应用执行。

任何“被脚本读取不到”的结果都不等于 XSS 已修复；任何“只在某条路径发送”的结果也不等于另一条路径没有办法调用敏感接口。评审报告最好把四项结论分开：传输限制、脚本可见性、请求携带条件、服务端授权结果。若出现异常，才能知道该改 Cookie 属性、前端调用方式，还是后端权限规则。

读不到 Cookie 也可能做出有权限的请求

假设应用允许 POST /profile/email 修改邮箱，浏览器会自动携带会话 Cookie。若页面脚本被注入，HttpOnly 能阻止它直接调用 document.cookie 取出会话值，却不能单凭这个属性阻止它在当前页面上下文发起修改请求。服务器必须检查操作权限和必要的防伪措施，页面也必须处理输入注入。这里的接口只是威胁模型示例，并未指向本站实际系统；它说明浏览器保存凭据与服务器批准动作是两个阶段。

另一方面，跨站网页试图诱导浏览器向该接口发请求时，SameSite 的模式、请求方式及浏览器的默认行为会影响 Cookie 是否被带上。MDN 说明某些浏览器默认采用 Lax，且默认的宽松变体在设置后短时间内对部分 POST 有特殊行为。因此不能把“没写 SameSite，所以应该如何”当成稳定部署契约。若业务依赖某种跨站登录或嵌入流程，必须明确设置并实测目标浏览器；若不需要跨站携带，则应按业务可接受的范围收紧。

还有一个容易误判的排查场景：开发环境在 localhost 用 HTTP 看见 Secure Cookie 行为，于是推断线上 HTTP 子域也一样。文档明确给 localhost 特例；线上域名测试应使用真实 HTTPS 配置和真实主机结构。若服务端通过代理识别协议，代理到应用之间的配置也会影响 Set-Cookie 是否正确生成。审稿报告应记录客户端实际接收的头和请求携带结果，而不只转述服务端代码中的选项名称。

最终决策不是给每个 Cookie 填满属性，而是写出威胁与业务需求：哪些主机必须共享、哪些跨站入口必须工作、脚本是否真的需要读取、服务端是否在每个敏感接口重新授权。对会话凭据通常很难给脚本读取找出必要理由；若确有前端状态需求，可以将非敏感显示状态与真正会话凭据分开，不要为了 UI 便利撤掉会话 Cookie 的 HttpOnly。

对会话 Cookie，一个常见起点是安全传输、禁止脚本读取、按业务需要收紧主机与跨站范围，并验证服务端仍独立授权。但最终属性组合必须与登录跳转、子域结构、跨站嵌入需求一起测试。只给 Secure 打勾，会遗漏最初那个最直接的问题：脚本能否读到值，以及读不到值以后还能做什么。
