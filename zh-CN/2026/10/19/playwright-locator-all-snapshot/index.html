Playwright locator.all：先证明列表完整，再枚举

解释 all 的即时采样与零次循环假绿，并按已知数量、未知终态和集合变化选择验证方式。

正文

核心要点

  • locator.all 立即枚举当前匹配项，不等待列表加载完整。
  • 已知数量时预期应来自夹具与筛选条件，不能从当前 DOM 反推。
  • 返回的定位器数组不冻结 DOM，操作中重排需稳定业务身份。

任务页有三条记录，测试把断言写在 for (const item of await page.getByRole('listitem').all()) 中。若请求尚未返回，all() 得到空数组，循环执行零次，测试仍可能显示绿色。这不是 Playwright 替你验证了“没有错误”，而是根本没有检查任何条目。Playwright Locator API 的 locator.all() 文档说得明确：它立即返回页面当前匹配项，不等待元素出现；动态变化的列表可能给出不稳定结果。这里 await 等到数组返回，不等到业务列表完整。

零次断言如何变成假通过

看一个最小的推演：页面发起 /tasks 请求，测试很快执行 const items = await page.getByRole('listitem').all()；此时渲染尚无任务行，items.length 是 0。后面的循环里即使写了 expect(item).toContainText('待办')，没有任何 item 被迭代，断言次数仍是 0。再过 100 毫秒，页面出现三条真实任务，测试早已结束。这个时序例子没有运行浏览器，不宣称具体网络延迟；它展示的是 API 的采样点与循环逻辑之间的缺口。

const items = await page.getByRole('listitem').all();
for (const item of items) {
  await expect(item).toContainText('待办');
}

all() 返回的是定位器数组，不是冻结的元素快照；每个 locator 后续动作仍会在当时页面解析。因而就算一开始得到三项，列表若在循环中删除、排序或重新渲染，用位置索引描述的第 2 项可能已不是最初的第 2 条任务。要把两个问题分开：枚举前是否完整，枚举后集合是否稳定。前者靠就绪合同，后者靠稳定业务身份或每步重新核对；给外层加固定 waitForTimeout(1000) 既不定义完整，也不能防重排。

已知数量时，把预期写在页面之外

若测试夹具明确创建任务 T-1、T-2、T-3，可以先用 await expect(page.getByRole('listitem')).toHaveCount(3)。Playwright 的数量断言文档定义它会检查精确 DOM 数量，断言机制会等待条件满足。随后再检查三个任务的可见业务标识及标题，或直接对整个列表做文本断言。关键是数字 3 来自测试夹具和本次过滤条件，不是从正在被测的 DOM 读出来。若代码先 const n=await rows.count() 再 toHaveCount(n)，它只证明页面当前数量等于自己，并未证明数据加载完整。

达到三条也不保证内容已经属于本次查询。上一次搜索恰好也有三条，旧结果先闪现，随后才替换为新结果；只看数量会过早通过。断言应绑定请求的筛选条件或记录身份，例如本次任务 ID 集合是 T-1、T-2、T-3，而旧集合是 U-1、U-2、U-3。若列表有显式“正在加载”状态，可在它结束后核对新 ID；若测试能控制返回数据，保留一组独特文本。数量、身份、加载终态分别证明不同事情，不能互相代替。

未知数量时，不要从页面现值制造“预期”。页面必须提供可观察的终态：加载指示结束、结果标题给出范围、分页到末页，或“没有记录”的明确空状态。选择哪一个由产品契约决定，而不是 Playwright 统一规定。如果 UI 把加载中、真正空结果和服务失败都显示成同一片空白，测试没有足够信息判断列表已完整，这首先是产品状态设计问题。可以修正页面暴露可读的状态，再让测试观察它；也可借助受控测试夹具的服务端响应作为外部依据，但不要把一次网络响应结束简单等同于组件已完成渲染。

枚举后集合变化要换身份策略

假设测试在三条任务里逐条点“完成”，完成后该任务从列表消失。若数组中三个定位器按位置保存，第一轮删除第 1 条后，原第 2 项可能移到第 1 位；下一轮定位可能指向错误任务或找不到元素。更稳的方式是先从夹具掌握任务 ID，以 data-task-id 或可见唯一名称定位当前目标，完成后确认该 ID 消失，再处理下一个；若页面不暴露稳定身份，则应质疑测试是否能可靠表达业务要求。站内动作与结果等待讨论点击后的断言；这里强调每次操作都可能改变下一次定位对象。

虚拟列表还有一层：DOM 只渲染视口附近的十条，数据源实际上有一千条。all() 最多枚举当前 DOM 匹配项，不会自动滚动并收集全量。若测试目标是“当前可见十条样式正确”，要在名称里说明范围；若目标是“全部一千条数据可被浏览”，需设计分页、滚动或后端与 UI 分层验证，不能把十个 locator 写成全量证据。无限滚动场景还要定义停止条件：已到末尾标志、总数与已加载数一致，或服务明确返回无更多页。没有终点的“滚几次再 all”仍是取样。

定位范围也会制造假完整。page.getByRole('listitem') 可能同时匹配侧边导航、页脚链接和任务列表项，数量刚好达到三，却不是三条任务。应先定位本次任务列表的语义容器，再在容器内取行；若任务组件没有可识别的区域名称或稳定属性，应改进页面语义或测试契约。反过来，过滤器会把已完成任务隐藏时，夹具里原本创建三条，不代表当前筛选结果仍应是三条。预期集合应由夹具数据加筛选规则计算，不能把初始化总数硬套到每个视图。真正好的断言会说明“哪三条、在哪个列表、在什么过滤状态下”。

如果测试只想检查每条标题，没有必要先取定位器数组再循环：对已知顺序和内容，列表级文本断言更直接；对已知独立任务，用稳定 ID 各自断言；只有后续操作确实要针对当时每个条目，且集合已经完成并稳定，all() 才带来便利。选择 API 前先写出验证目标，可以避免为了沿用一段循环模板而引入零次执行和索引漂移两类额外风险。

负例矩阵应覆盖慢加载、先有部分结果后补齐、旧搜索结果闪现、真正空结果、请求失败、完成一条后重排，以及虚拟列表只渲染局部。对三条已知任务的用例，先断言数量和身份，再执行必要的逐项动作；对未知数量，用终态和结果范围先证明稳定。测试失败时保留页面状态、当前任务 ID、加载标志与请求标识，便于知道是产品数据缺失、就绪合同错误，还是定位对象发生变化。本文没有运行浏览器测试或统计 flaky 比例；所有代码和时序是基于官方 API 行为的推演。可解释的绿色结果必须能指出“完整性来自哪条外部证据”和“循环实际检查了几项”，而不能只说每行代码都加了 await。
