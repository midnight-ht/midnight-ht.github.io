CSS sticky 排障：滚动祖先、inset 与活动空间

用侧栏祖先链定位 sticky 的滚动参照，再检查非 auto 偏移、包含块空间和窄屏遮挡。

正文

核心要点

  • sticky 可参照最近具有滚动机制的祖先，即使页面实际滚动的是别处。
  • 目标轴至少需要一个非 auto 的 inset，且包含块要留出活动空间。
  • 修复 overflow 或改 fixed 前应测裁剪、遮挡和不同视口。

侧栏已有 position: sticky; top: 0，页面滚轮也在动，它却始终像普通块一样向上消失。增加 z-index 只影响堆叠，不会改变粘附参照；直接换成 fixed 又会把元素移出原布局。先找它究竟相对哪个滚动区域计算。MDN 的 position 文档说明，sticky 会相对最近具有滚动机制的祖先粘附；overflow: hidden、scroll、auto 或 overlay 都可能建立该机制，即使那个祖先并不是用户正在滚动的区域。

用一段祖先链定位参照

想象 body 中有一个页面布局容器 shell，它为裁剪圆角设置 overflow: hidden；shell 里面的两栏网格左侧放侧栏 aside。用户滚动的是整个文档，开发者却期待 aside 在视口顶部停住。此时 shell 可能成为 sticky 的最近滚动机制祖先，侧栏以它的滚动口作为参照；如果 shell 本身没有发生可供观察的滚动，页面滚动不一定触发预期的视口粘附。关键不是“有没有看见滚动条”，而是计算后的 overflow 与实际滚动对象是否是同一层。这个 DOM 是推演例子，不是已在浏览器中执行的复现。

.shell { overflow: hidden; }
.sidebar { position: sticky; top: 0; }

排查时从 .sidebar 向外逐层记录：元素的 position 和 top 计算值、每个祖先在横纵轴的计算 overflow、其可滚动内容与客户端高度、用户操作使谁的 scrollTop 改变。还要留意一个轴的设置可能影响另一轴的计算值，不能只搜索源码里有没有 overflow-y: auto。样式可能由组件库或响应式断点注入，源码片段和最终计算值也不一定相同。开发者工具临时关闭 shell 的 overflow，若侧栏开始随页面粘附，可作为根因线索；还应恢复设置并验证裁剪需求，不能把试改直接提交。

若产品原意是“表头跟随内部表格面板滚动”，最近的局部滚动祖先恰好可能是正确的。此时测试应滚动面板，不是滚动整个页面。反过来，若需求是侧栏随文档停在视口附近，隐藏裁剪层必须重新设计或与 sticky 分离。选择不是 overflow: hidden 一律删掉，而是先写清用户滚动哪个容器、元素应相对哪个边缘停住，以及改变裁剪后是否会露出溢出内容。组件同时承担滚动、圆角遮罩和粘附参照时，拆分容器职责常比逐项覆盖 CSS 更稳定。

参照正确仍可能没有粘附区间

MDN 还要求目标轴至少有一个非 auto 的 inset，例如纵向的 top 或相应逻辑属性。若 top 与 bottom 都是 auto，纵向行为会像相对定位；因此只写 position: sticky 不足以触发纵向粘附。top: 0 也不是万能：sticky 先参与正常文档流，到达阈值才偏移，并会被包含块的相对边界限制。侧栏与容器几乎一样高，或父容器只比侧栏高几像素时，能移动的区间很短，肉眼可能看不到期望中的长距离固定。应把元素高度、包含块高度、上下偏移和滚动距离一起量，而不是继续增大 z-index。

例如桌面窗口高 900 像素，侧栏高 300，包含块高 1200，页面可滚动足够长，它有机会在某一段保持顶部偏移。窗口缩到 500 像素、帮助说明展开后侧栏高 620，仍设置 top: 0，用户可能在窄视口里看不到侧栏底部操作。即使浏览器按规范粘附，产品效果仍不合格。可以限制侧栏最大高度并使其内部可滚动，或在窄屏改回普通流；但这会引入嵌套滚动和键盘访问问题，必须基于内容任务选择。修复应验证最短和最长文案、放大与响应式尺寸，而不是只在默认桌面截图上判定。

还有相反方向的反例：页面上一个固定顶部导航高 64 像素，侧栏 top: 0 确实粘住了，却被导航遮住标题。这里不是 sticky 失效，而是偏移与遮挡预算错误。可以把顶部安全间距纳入 top，并检查滚动到容器末端时是否仍有空间；若存在可变高度横幅，固定 64 像素可能再次不够。要从用户能否读到内容来定义成功，而不是只检测元素矩形的 y 坐标不再变化。

把试改转成可回归的修复

诊断顺序是先确定纵向还是横向粘附，再找到最近滚动机制祖先和实际滚动对象，再核对非 auto inset，最后量包含块的活动空间与遮挡。每一步失败对应不同改法：滚动参照错时重排容器职责；偏移缺失时补正确轴的 inset；空间不足时调整布局或需求；遮挡时重算偏移和层级。仅换成 fixed 会让元素脱离正常流，占位、宽度、底部边界和窄屏遮挡都要重新设计。MDN 也说明 fixed 不为元素保留原布局空间，因此这不是等价替换。

实际验收可记录三组视口：常规桌面、窄屏、放大后的短视口。每组分别滚动预期容器与外层页面，观察首次粘附位置、容器底边退出时机、内容是否可读以及键盘焦点是否被隐藏。站内放大与重排的布局检查可帮助界定短视口场景。若侧栏里有展开内容，先展开再测；若父容器需要裁剪，验证拆分后圆角和溢出没有回归。自动测量位置只能证明几何结果，不能代替人工确认遮挡和可操作性。

要把这个诊断写成可重复的检查，可在滚动前、中、后记录 .sidebar 与 .shell 的 getBoundingClientRect().top、window.scrollY 和 .shell.scrollTop。若 window.scrollY 增加而 .shell.scrollTop 始终为零，侧栏却相对 .shell 的滚动口受约束，就能解释为何“页面确实在滚”仍没有预期轨迹。临时移除裁剪样式后再做同一组测量，观察变化是否只影响侧栏，而不是碰巧改变了整体页面高度。测量是定位证据，不能单凭某一个 top 数值推断符合可用性：侧栏内部按钮是否可见、是否被导航盖住也要看。

如果设计同时要求圆角裁剪与页面级粘附，可以让外层负责页面布局和粘附范围，让更内层只裁剪装饰内容；但需要逐项确认哪一层建立包含块、哪一层被裁剪。随便把 overflow 移到 sticky 元素本身也可能裁掉内部焦点轮廓或展开菜单。对依赖门户、弹层和下拉选项的侧栏，要在展开状态检查是否被新的裁剪边界截断。布局修复是否正确，最终取决于完整交互，而不是 top 在一张截图里停住。

本文没有运行目标页面或浏览器探针，DOM、尺寸与修法均为可执行的排障设计。交付记录应保存实际祖先链计算值、滚动对象、改变前后截图或测量，以及不同内容高度下的结果。sticky 的关键不是某一句声明是否存在，而是参照、触发阈值、包含块边界和用户正在滚动的区域是否构成同一条可解释的链。
