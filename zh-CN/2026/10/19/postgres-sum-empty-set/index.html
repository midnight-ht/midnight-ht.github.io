SUM 得到 NULL 后，先数输入行

空集与全空金额都能让 SUM 得到 NULL；保留行数和有效金额数，再决定是否补零。

正文

核心要点

  • PostgreSQL 18 的 SUM 在没有输入行时返回 NULL，空金额也不参与求和。
  • COUNT(*)、COUNT(amount) 与原始 SUM 能区分无行、全空金额和有效零。
  • GROUP BY 缺席的账户没有结果行，COALESCE 不会生成账户行。

“本月退款总额”显示零，可能指三件不同的事：没有任何匹配退款、匹配了退款但金额全部未填写，或者确有金额且正负抵消为零。若接口只返回一个经 COALESCE 补成零的数字，页面会失去解释这三种状态的能力。PostgreSQL 的 SUM 在没有输入行时返回 NULL；补不补零应是业务展示决定，不能被写成数据库纠错。

先数参与聚合的是什么

PostgreSQL 18 聚合函数文档定义 sum 对非空输入求和，并指出除 count 外，这些聚合在没有选中行时返回空值，sum 的空集结果不是零。文档也建议在需要时用 coalesce 替换。这里的“需要时”取决于接口承诺：如果要展示确定的数字零，补值合理；如果要保留“尚无数据”或“金额缺失”的区别，直接补零就会抹去信息。

以假设的 refunds(account_id, amount, created_at) 为例，先把三种输入写清楚。无行时，COUNT(*) 为零、COUNT(amount) 为零、SUM(amount) 为 NULL。两行的 amount 都是 SQL NULL 时，行数为二，有效金额数为零，总额仍为 NULL。两行有效金额分别为 10 与 -10 时，两个计数都是二，总额是零。三个结果在报表上或许都可以用零占位，但含义不相同。有关 COUNT(*) 与 COUNT(列) 的口径，可参见本站的COUNT 输入口径。这些数值是演绎用例，未在真实库执行。

SELECT COUNT(*) AS rows_seen,
       COUNT(amount) AS known_amounts,
       SUM(amount) AS raw_total
FROM refunds
WHERE account_id = $1 AND created_at >= $2 AND created_at < $3;

这个查询让三项指标来自同一过滤范围。rows_seen = 0 可以解释为该范围内没有匹配记录；rows_seen > 0 且 known_amounts = 0 表示有行但金额没有可参与求和的输入；known_amounts > 0 时 raw_total 才是有效数值求和的结果。若模型另有“退款撤销”“草稿”状态，还需在过滤或状态分类中明确，不能让聚合替业务选择哪些行算退款。权限过滤也会影响这些计数：对某用户无可见记录，只能说“在本次授权范围内无匹配项”，不能宣称整库从未有退款。

补零的位置会改变信息量

COALESCE(SUM(amount), 0) 是在聚合结果层补零。它把无行与全为空金额两种 NULL 都映成零，适合确实把两者视为零的数值接口。SUM(COALESCE(amount, 0)) 则只在存在输入行时，把该行的空金额换成零；若输入集合完全为空，仍没有任何行送进 SUM，结果仍是 NULL。这两个表达式不能因都出现 COALESCE 就互换。若业务允许金额为空表示“待补录”，内层补零甚至会把缺数当成确定的零参与统计。

一种更诚实的接口可同时返回 raw_total 和状态。显示层在 rows_seen = 0 时写“本期无退款”，在 rows_seen > 0 && known_amounts = 0 时写“金额待补”，在有有效金额时显示总额；若存在部分缺金额，既显示已知部分合计，也标注“尚有未填金额”，避免把部分数据当完整总额。这个设计是建议，不是数据库强制的唯一含义。另一个产品也可能在写入时禁止空金额，使“全为空”状态不可能进入正式数据；在这种经过验证的约束下，外层补零更简单。关键是把约束和展示承诺对应起来。

零本身也需要留意符号与精度。金额字段若是浮点类型，报表是否接受舍入误差另有要求；这个问题不能靠 COALESCE 修复。货币合计还要确定单位一致，不可把不同币种直接相加。它们不是 SUM 空集规则的例外，而是有值时仍必须满足的输入条件。若筛选时间用半开区间，还要在接口定义中明确时区和端点范围，否则“本月无记录”的结论可能只是过滤条件写错。

GROUP BY 中缺席的行要另建骨架

不分组的聚合查询即使无匹配行，通常也会给出一行汇总结果，可在那一行上补零。但按账户 GROUP BY account_id 时，某账户没有匹配退款就没有对应分组行；COALESCE(SUM(amount), 0) 不会凭空生成它。若报表要求列出所有获授权的账户，再显示每个账户的退款状态，应从账户集合出发，左连接同范围的退款，再聚合。此时 COUNT(*) 可能把左连接产生的占位行算成一行，必须数退款表真实主键或有值字段；日期条件若放在外层 WHERE，还可能把左连接无匹配的账户过滤掉。

可把查询设计成“先确定应展示账户，再为每个账户汇总允许范围内退款”的两阶段问题。具体 SQL 要按表结构与权限策略编写，这里不提供假装可直接上线的完整查询。验收时至少检查一个无退款账户、一个金额全空账户、一个有效合计为零账户和一个非零账户；再分别检查无分组总额与有分组列表，确保行是否存在也被纳入断言。用同一身份与时间窗口核对页面、API 和 SQL，才能证明状态字段与金额来自同一集合。

是否补零的最终决定，应落在产品可解释的句子上：“本期没有退款时展示零”还是“本期没有可计算金额时显示待确认”。在这一句批准前保留原始总额与计数，通常比急着在每层写 COALESCE 更容易发现误报。本文没有执行数据库测试，文中的输入和输出是依据 PostgreSQL 18 文档推演出的验证目标。

报表导出还应保留与页面相同的状态口径。若页面写“金额待补”，CSV 却把该账户导成 0，下游财务系统就可能把未知当成已确认的零。接口可以提供机器可读的状态字段和原始空总额，由不同客户端决定显示文案；即使最终产品选择展示零，也应能追溯是“没有记录”还是“记录存在但金额缺失”。这不是要求永久暴露所有底层计数给每个用户，权限、隐私和数据粒度仍应由接口设计控制。要测试的关键是同一授权范围内，页面和导出对状态的解释不互相矛盾。
