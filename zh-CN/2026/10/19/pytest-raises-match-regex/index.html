pytest.raises 的 match 为什么会放过错误消息？

解释正则搜索、异常注释与子类匹配怎样扩大断言范围，并用负样本定义真正要验的错误。

正文

核心要点

  • pytest.raises 的 match 使用正则搜索，不等于消息完全相等。
  • 异常注释和正则元字符可能扩大一条绿色断言接受的消息集合。
  • 用必须拒绝的负样本与真实失败入口共同验证断言。

测试预期抛出 ValueError("code E.42")，于是写了 pytest.raises(ValueError, match=r"code E.42")。测试绿了，读者可能以为整句和错误码都被锁定。实际上 match 会做正则搜索：它允许目标文字只出现在一段更长消息里，而模式中的点可以匹配任意字符。绿色只能证明当前异常满足这条搜索规则，不能自动证明它是想验收的那一种错误。

先写“哪些异常可以通过”

pytest 当前的异常断言指南明确使用 re.search() 检查异常的字符串表示，也会匹配 PEP 678 的 __notes__。这给测试两层可能的宽松：一是子串搜索，二是匹配材料不止异常首行。被测代码若在错误原因前加上 unexpected prefix: ，或把 code E.42 放在 note 而主体变成另一种错误，原模式仍可能符合搜索条件。这里说的是规则推导，示例函数与消息均是假设。

Python 正则参考还说明模式元字符的意义。r"code E.42" 的 r 只让 Python 更直接地书写反斜杠，绝不会自动转义正则的点。E-42、E/42 之类字符组合都可能落入那一点的范围。对从日志复制来的句子，还应检查方括号、圆括号、问号和反斜杠；“看起来一样”不是正则审查方法。

先决定消息属于哪种契约。如果要求完整字符串稳定且完全相等，抓到异常后做显式相等比较，语义最清楚：

# 说明性例子；parse_code 是假设函数，未运行。
with pytest.raises(ValueError) as excinfo:
    parse_code("bad")
assert str(excinfo.value) == "code E.42"

这个断言只要求异常对象的字符串完全相等，不声称检查 notes。若 notes 是产品承诺的一部分，应为其单列要求。若诊断描述会随版本改变，锁死整句反而让测试脆弱；可以只验稳定错误码，但必须定义前后允许出现什么。例如允许 code E.42: <细节>，就把前缀、字面点和后续格式写入模式，并拿不应通过的消息校验。用 re.escape() 处理一段本应视为普通文本的消息，也比手写逐个反斜杠可靠。

一个反例比十次绿色更有用

针对 code E.42，至少准备四类负样本：code E-42 验字面点，prefix code E.42 验开头边界，code E.42 extra 验结尾边界，以及主体错误不同、目标词只在 note 里的异常。测试团队要先解释每个样本为什么应被拒绝或允许，然后选相等比较、锚定正则或局部搜索。否则只是根据当前实现结果反向宣布契约。

比如完整字符串要求可以写 assert str(excinfo.value) == expected_message；只检查主体中的稳定前缀，可以在捕获异常后比较 str(excinfo.value).startswith(expected_prefix) 并另外验证错误码结构。若选择 match，可以用 ^、$ 等边界和转义构造模式，同时留意换行、结尾换行及 notes 参与匹配的情况。锚点能表达意图，但不能代替对实际匹配材料的核对。最小负样本集应真的拿正则引擎或测试环境跑一遍，读一眼模式并不足以证明范围。

异常类型也不是附属细节。pytest 指南说明 raises(SomeError) 接受该类型及子类；如果精确类型有业务意义，还需检查 excinfo.type is SomeError。把期待值放宽成 Exception 会让被测函数在更早步骤因配置错误失败时也进入消息判断；即使文本恰好出现同一个编号，也不是目标路径。对异常组，单个内部异常“包含”检查还可能忽略其他成员，pytest 文档专门提醒要使用适合异常组结构的断言。

从真实失败入口验证，而非替身消息

最容易失真的测试是把会失败的函数替换成一个直接抛预写消息的替身，然后宣布解析器的错误分支已验收。那只能证明断言代码如何处理一个构造出的异常。应保留一条通过真实输入进入目标分支的测试，核对触发条件、异常类型和稳定消息部分；再用少量纯模式测试穷举边界。这样测试既不会被第三方诊断文字的细小变化拖垮，也不会把另一个失败原因误认作预期错误。

若异常来自不受控制的第三方库，且消息没有稳定承诺，优先寻找受文档支持的结构化错误码、属性或业务包装结果。没有这些接口时，可明确只检查类型和关键上下文；不要假造“精确匹配”带来虚假的确定性。决定验什么，是接口契约问题，不是 match 字符串该加几个通配符的问题。

正则模式怎样写才不扩大承诺

如果业务只保证错误码而不保证解释文本，可以把错误码当作独立字段优先断言；没有字段时，至少让模式表达代码边界。例如消息约定为 code E.42: 开头，后接任意非空解释，那么模式需要转义字面点、锁定开头，并显式要求冒号及空格。若解释可能换行，普通的点是否跨行也要按 Python 正则规则核对。把 .* 加在两端看似“保险”，实际是让无关前后文通过；要宽松也应明确宽松在哪一段。

更稳妥的构造方法是先用几条普通字符串测试模式自身，再接入真实异常。比如测试预期模式对 code E.42: bad field 为真，对 Xcode E.42: bad field、code E-42: bad field、code E.420: bad field 为假。这个小集合不是替代产品测试，而是让评审者能检查正则语义。运行时还要确认被测分支确实抛出目标异常；若 with pytest.raises(ValueError) 的代码块包含多步准备工作，早一步抛出的同类型异常也可能让测试过关。缩小上下文管理器里的代码范围，是一种便于定位的做法。

处理 notes 尤其需要先问产品是否把它们当公开诊断内容。若只验主消息，捕获异常后直接检查 str(excinfo.value)，就不会让 note 中恰好出现的短语满足 match。若确实验 notes，应查看异常对象的 __notes__ 并定义顺序和内容要求，不能依赖一个模糊搜索顺带覆盖。无论选哪条路，都把“错误类型”“主消息”“补充说明”写成三个可分别失败的断言，失败报告才指出哪一份契约破了。

本站近似断言的容差契约讨论过参数如何改变接受集合。异常断言也是同一个审稿动作：把“允许通过的集合”和“必须拒绝的邻近集合”并排写出，再看 pytest.raises 的实际规则是否恰好覆盖前者。最后保留运行结果和 pytest 版本，才知道这份验收在当前项目里真正通过了什么。
