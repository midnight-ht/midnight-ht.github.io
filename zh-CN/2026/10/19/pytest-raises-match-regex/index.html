pytest 的 match 写了整句，为什么仍可能匹配错？

pytest 的 match 是正则搜索；用明确的消息契约和负样本，检查子串、元字符及异常注释的接受范围。

正文

pytest.raises 的 match 使用正则搜索。写入一段预期消息，并不表示异常文本必须与它完全相等。测试要先决定接受哪个错误，再选择消息比较方式，否则绿色结果可能只是证明某几个字符出现过。

两种放宽，可能同时发生

pytest stable 的异常断言指南说明，match 使用 re.search，检查异常的字符串表示，还会匹配 PEP 678 的异常注释。这意味着搜索范围与完全相等不同，匹配对象也不应被想当然地缩成第一行消息。

假设预期错误是 “code E.42”。没有边界的模式可能允许前后附加其他文本；其中的点又是正则元字符，不只表示字面上的句点。两种放宽叠在一起，可能让并非预期的消息被接受。这是规则推导示例，本篇没有运行 pytest，不能把它写成某个项目已经出现的漏测。

Python 正则文档区分字符串转义与正则语法。在 Python 字符串前加 r，也不会把正则变成普通文本。原始字符串解决的是字符串字面量的一层转义书写问题，进入正则引擎后仍按模式解释。复制报错文本到 match 之前，应特别检查点号、括号、方括号等字符是否有意作为模式。

要相等，就明确比较相等

如果完整消息本身属于稳定契约，可以取得异常对象，再单独检查字符串。这种写法把异常类型与消息内容两个要求分开，避免读者猜测模式的边界。下面是未执行的说明性代码，被测函数与消息均为假设。

# Illustrative only; not executed.
with pytest.raises(ValueError) as excinfo:
    parse_code("bad")
assert str(excinfo.value) == "code E.42"

这条比较只检查异常对象的字符串，不声称检查了 notes。若注释内容也属于需要验证的信息，应另列要求。相反，若只要求稳定标识而允许诊断文字变化，完整消息相等可能过于脆弱；可以选择有意设计的模式，并说明允许变化的是哪一段，而不是一遇到失败就加上任意匹配。

异常类型也有范围。官方指南指出，raises 接受指定类型及其子类；若确实要求精确类型，要显式检查。不要为了消息检查方便就扩大到 Exception，否则被测代码在错误的步骤抛出另一种异常，也可能满足过宽的测试。这里的建议是收窄契约，不是要求每项测试都锁死完整文本与精确子类。

让意外消息成为负样本

评审时可以拿几条“必须拒绝”的假设消息反查模式：相似错误码、前面附加失败原因、后面增加另一种错误，以及仅在注释里出现目标文字。要明确每一条为什么应拒绝。若某条原本就允许，应记录理由，不能仅凭模式碰巧接受就倒推它符合需求。

反查模式与验证真实错误路径，是两件事。前者可以发现匹配范围过宽，后者还要证明正确输入到达预期失败分支，并得到规定的异常。只让一个替身抛出预写消息，无法验证被测函数是否真的识别了错误条件。

这里的负样本是拟议验收输入，没有执行日志。对文本极不稳定的第三方异常，也可以优先验证稳定的异常类型、结构化属性或业务包装结果；前提是这些确实属于所用接口的保证，不是测试临时造出的替代标准。

本站十月十八日的近似断言容差提醒，参数决定接受范围。match 也一样：审查对象应是允许哪些错误消息通过，而不只是这次测试已经变绿。
