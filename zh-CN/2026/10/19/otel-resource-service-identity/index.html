两条链路都叫unknown_service，先查导出还是命名？

遥测到达只证明部分传输成功；用Resource原始属性、Provider创建时机与前后样本定位服务身份错误。

正文

核心要点

  • 同一逻辑服务的副本共享service.name，实例ID负责区分副本。
  • Resource在Provider创建时绑定；配置意图要与原始导出属性对照。
  • 从进程、采集端、Collector和后端逐段定位默认名或错误聚合。

订单接口和通知 worker 都已把 span 送到后端，服务列表却只出现一个 unknown_service。如果值班员按这个名称筛选，两种进程的耗时和错误会混在一起；若把每个副本都命名成不同服务，又会把同一个逻辑服务拆碎。问题不是“有没有收到遥测”这一问，而是每条数据在产生时带着什么 Resource 身份，以及这个身份在哪一段管道里变了。

先定义逻辑服务，再看默认名

OpenTelemetry 服务语义约定当前页面标注 1.44.0。其中 service.name 是逻辑服务名，同一服务的水平扩展实例必须保持相同值；未显式设置时，SDK 应回退到 unknown_service: 加可执行程序名，拿不到进程名才回退到 unknown_service。因此，看到默认名并不说明导出网络坏了：数据已经到达，至少有一段传输成功。它也不说明所有 SDK 或后端版本都按相同页面渲染，定位时应看实际导出的资源属性，而不是仅看服务卡片标题。

假设订单 API 有两个副本，通知 worker 只有一个进程。团队希望前两个副本都归到 service.name=order-api，worker 归到 service.name=notification-worker。若以 service.namespace=commerce 表示这一组业务，三个进程仍可在同一命名空间下分成两个逻辑服务。两个订单副本再分别有唯一的 service.instance.id；该字段用于区别同一服务中的实例，不应被拿来替代服务名。规范要求同一命名空间与服务名组合下的实例 ID 唯一。这里的名称和数量是设计示例，未在任何真实后端观察到。

这张身份表能立即暴露两类反例。如果三个进程都叫 unknown_service，按服务名分组会混合订单和通知；如果订单两个副本分别叫 order-api-1、order-api-2，按服务名看失败率又会把同一服务拆成两条曲线。再把用户 ID、请求 ID 填进 service.name，每次请求都会产生新的服务身份，既不能稳定聚合，也把不该进入服务级身份的高基数值带进索引。服务、实例、请求本来是三个不同粒度，不能用一个字段完成全部查询。

命名空间也要按组织的真实边界使用。若另一套完全不同的系统同样把某个组件叫 order-api，只看名称可能误合并；把 service.namespace 纳入查询可表达两个系统的归属。反过来，不要把每个环境、每次构建都塞进命名空间，导致同一服务在每次发布时换身份；部署环境和版本可用各自约定的资源属性表达。实例 ID 只需在规范要求的组合内唯一，值应稳定到足以区分同时存在的实例，且不应把可能敏感的宿主机标识直接暴露给所有读者。字段选择既影响后端分组，也影响谁能看到资源元数据。

Provider 何时创建，资源就何时绑定

OpenTelemetry Resource 概念文档指出，Resource 在初始化时与 TracerProvider 或 MetricProvider 关联，之后不能再改这份关联；由该 Provider 产生的 span 或 metric 会带着它。文档也建议显式设置 service.name，可通过代码或 OTEL_SERVICE_NAME 环境变量表达。发布清单中写了环境变量，只说明部署意图；若变量实际未进入进程、自动埋点在配置前创建了 Provider，或某段初始化另建了一个 Provider，导出样本仍可能不符合期望。究竟哪种原因成立，要看目标语言 SDK 和启动顺序，不能凭一个默认值直接定性。

一份可审的初始化记录应有三端：部署时预期的服务名与配置来源，进程启动时实际读到的非敏感配置，以及导出数据里的 Resource 属性。若订单 API 进程启动日志显示读到 order-api，但采集端收到的 span 仍叫默认名，下一步查 Provider 创建时机和自动埋点是否抢先初始化；若采集端已经是 order-api，而后端变成别的名称，就应核对 Collector 处理器、导出器和后端映射规则。两端都叫默认名时继续排查进程配置。不要在不了解 SDK 的情况下重复创建 Provider 或声称某个跨语言统一的环境变量覆盖顺序。

让三条样本形成可反驳的验收

以下是未执行的假设验收。给订单副本 A 和 B 各发一条带不同测试标识的请求，再触发一次通知 worker 的受控任务。预期三条 span 都到达采集端：A、B 的 service.name 同为 order-api，但实例 ID 不同；worker 的服务名为 notification-worker，实例身份另列。按 service.namespace=commerce 加 service.name=order-api 查询应找到 A、B 而不包含 worker；再按 worker 的服务名查询应只找到通知样本。若采集端与后端均符合这些关系，团队得到的是“身份按设计可区分”的证据，而不只是“有三条 span”的收货回执。

现在把 A 的 OTEL_SERVICE_NAME 故意留空作为反例。按当前语义约定，A 可能回退到带可执行名的 unknown_service:...，并从订单服务查询中消失；B 和 worker 仍按原名出现。预期验收应失败，因为同一逻辑服务的两个副本未聚合。若后端只显示 unknown_service 而隐藏后缀，也不能推断 SDK 一定输出了纯默认值，必须查看原始资源属性。另一种反例是 Collector 把三个名字统一改写为 order-api：采集端的身份正确，后端却错误合并；此时改应用环境变量不会解决中间层重写。

为了不让“验收样本”污染用户数据，测试标识只需能在受控环境内关联样本，不要把客户邮箱或令牌塞进 Resource。Resource 描述遥测产生者，不是请求上下文；若要跨进程传递上下文字段，另有传播策略，站内OpenTelemetry Baggage 边界讨论了它的风险。仪表盘分组规则也要明示：若只按服务名聚合，两个命名空间里同名服务可能合并；若按实例 ID 聚合，则每次副本变化都可能出现新曲线。查询维度应与本次排障问题对齐。

验收顺序建议先从单个受控请求的原始导出样本开始，确认 Resource 属性及信号类型；然后在 Collector 前后各保留一份无敏感数据的样本，最后核对后端查询和服务列表。这个顺序能够区分“配置没有进进程”“Provider 建立太早”“中间处理改写”和“后端展示聚合”四类位置。目标部署若没有 Collector，就省去中间对照；若只收指标不收 trace，就用同一资源关系查指标而不假装已有 span。文章没有运行这些步骤，真实结论必须附上进程配置、采集样本与查询结果。

最终决定也应分层：默认服务名出现，先修身份配置与初始化；原始数据正确而后端聚合错误，修映射与查询；只见部分副本，查部署差异与采样/导出路径。不要为了消掉一个 unknown_service 标签，把每个 Pod、用户或请求都升级成新服务。稳定的逻辑名、可区分的实例和能追到来源的样本，才让“遥测已经送达”变成“它属于谁”这个可验证的答案。
