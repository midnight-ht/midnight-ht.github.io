语句成功了，延迟约束为什么还能让提交失败？

延迟约束可能到提交才检查；明确可延迟定义、主动检查点与失败处理，避免提前宣布业务完成。

正文

延迟约束可能在提交时才检查，所以最后一条写入成功，还不能成为业务完成的依据。应用需要知道约束何时检查，也需要让提交失败进入正常错误处理，而不是把它归为不可能发生的尾声。

允许暂时不一致，是为了完成一组修改

PostgreSQL 18 的 SET CONSTRAINTS 文档说明，DEFERRED 模式把相关约束检查推迟到事务提交；NOT DEFERRABLE 不受这条命令影响。是否可以推迟，先看约束定义，不能只在业务代码里加一行设置就假定所有约束都会改变时点。

假设一次导入先写子记录，随后写它引用的父记录。如果相应外键被正确声明为可延迟，并在事务中处于延迟模式，中途的暂时缺引用可以留到检查时再判断。这个说明性场景没有执行 SQL；它表达的是最终状态必须满足约束，绝不表示缺失父记录也能成功提交。

延迟检查因此需要一个明确的修复窗口：哪一步暂时破坏关系，后面哪一步恢复关系，失败时整组修改如何结束。若团队无法说明这三个问题，使用延迟模式可能只是把容易定位的语句错误挪到了更远的位置，而没有获得实际业务好处。

可以设检查点，但它不是提前提交

官方文档还规定，从 DEFERRED 切换为 IMMEDIATE 会追溯检查尚未检查的修改；若违反约束，这条 SET CONSTRAINTS 命令失败，模式不会改变。因此可以在一组数据修复完成后主动检查，而不是一直等到提交才发现关系仍然破损。

-- Illustrative only; constraint name is hypothetical.
SET CONSTRAINTS order_customer_fk IMMEDIATE;

这个片段未经执行，名称必须换成实际约束。选择明确名称也便于说明本次检查范围；随意使用 ALL 可能把其他可延迟约束一起纳入，不利于理解失败来自哪组修改。模式切换后还会发生什么写入，应一并放入事务设计，不能只看检查点之前的数据。

检查点通过也不是提交完成。它只确认当时受影响的约束检查通过，后续语句和最终提交仍各有结果。本站十月十六日的RETURNING 与事务边界讨论返回行和提交的区别；这里进一步要求记录是哪一种延迟检查在什么时候给出结果。

不要扩大成所有约束都能延迟

同一份文档列出受设置影响的约束种类，包括唯一、主键、外键和排除约束；NOT NULL 与 CHECK 不按这种方式推迟。写“事务中的约束都等到最后”会给读者错误预期。具体约束仍要满足可延迟的声明条件，不能从种类名称直接推断当前模式。

建议拟议验收覆盖两条相反路径：暂时不一致被后续写入修复，以及暂时不一致一直保留到检查点或提交。后一条必须失败，才能说明测试没有只覆盖方便通过的路径。测试还应经过应用实际管理事务的入口，确认提交异常能返回合适结果，而不是只验证单条插入。

若事务由框架包装，检查调用方究竟在包装器结束前还是结束后触发成功分支；不能只在单条写入附近捕获异常，遗漏最终提交的错误。

本篇未执行这些验收。对外完成通知应依据提交结果安排；若使用事务内待发送记录，也要另行验证其交付流程。先把“数据写入、约束检查、提交确认”这三个时点写清，才知道成功提示应该出现在什么位置。
