提交才失败的延迟约束：PostgreSQL 应用何时能宣布成功？

用外键先写后补的事务例子解释 PostgreSQL 延迟约束的检查时刻、主动检查点和提交失败处理。

正文

核心要点

  • 延迟约束允许事务内暂时不一致，但提交仍可能拒绝整组修改。
  • 从 DEFERRED 切到 IMMEDIATE 会追溯检查尚未检查的修改。
  • 应用应在事务提交确认后才向调用方宣布数据库写入成功。

一次事务里，INSERT 已返回成功，应用也拿到了新行的标识；随后 COMMIT 才报告外键不成立。如果成功响应在前一刻已经发给调用方，数据库最终却没有接受这组变更。延迟约束要解决的是事务内部暂时不一致的写入顺序，代价是把一部分错误推迟到更靠近事务出口的位置。业务“完成”的判断必须跟着真正的检查结果走。

先画出检查时刻，再看 SQL

PostgreSQL 18 的 SET CONSTRAINTS 文档把模式分为 IMMEDIATE 与 DEFERRED。前者通常在每条语句结束时检查，后者到事务提交时检查。创建约束时可以声明 DEFERRABLE INITIALLY DEFERRED 或 DEFERRABLE INITIALLY IMMEDIATE；NOT DEFERRABLE 不会被 SET CONSTRAINTS 改成延迟。SET CONSTRAINTS 只改变当前事务，不是对整张表永久改规则。

设有订单表引用客户表，迁移程序必须先放入订单，再在同一事务内补入客户。下列模式是说明性 SQL，没有在本站数据库执行；表结构、键值和约束名也是假设。

BEGIN;
SET CONSTRAINTS order_customer_fk DEFERRED;
INSERT INTO orders (id, customer_id) VALUES (901, 42);
INSERT INTO customers (id) VALUES (42);
SET CONSTRAINTS order_customer_fk IMMEDIATE;
COMMIT;

第三行结束时，客户 42 尚不存在。若这个外键不可延迟或仍处于即时模式，错误会在那条插入语句附近出现。若它确实可延迟且切换生效，事务可以继续；第四行补齐引用后，再主动切回 IMMEDIATE，未检查的修改会当场接受检查。最后提交仍是单独的完成事件。这里的关键不是“先插后补”这种顺序本身，而是最终引用关系确实成立。

反过来，删掉补入客户的一行，切回即时模式时就应失败。若省略主动切换，失败点通常推到提交。应用日志里同样写着“订单 INSERT 成功”，两种结局却不同：一个事务能提交，另一个必须回滚。这是评审中应该保留的负样本，而不是只证明快乐路径能跑通。

检查点可以提前暴露错误，却不会替你提交

官方文档说明，从 DEFERRED 改为 IMMEDIATE 时，尚未检查的修改会被追溯检查；若有违规，SET CONSTRAINTS 失败，模式也不会改变。因此在数据修复段后设置检查点，有助于把错误定位到该段，而非延迟到事务包装器退出时才看到。但该语句通过之后，后续写入仍可能出错，提交也仍可能失败。检查点和提交有不同职责。

约束名称要认真选择。SET CONSTRAINTS ALL 会改变事务内所有可延迟约束；一个迁移同时触碰外键与唯一键时，宽范围会让错误来源更难辨认。官方还提醒：同一 schema 中约束名不必全局唯一，未限定 schema 的名称按搜索路径查找，可能命中多个同名约束。因此“按名字切换一个约束”不能只凭肉眼推断；评审前应核对表定义、schema、搜索路径和本事务实际使用的名称。

也不要把“可延迟”扩大成“任何不合法数据都能先写”。PostgreSQL 文档列出的相关种类是 UNIQUE、PRIMARY KEY、外键和 EXCLUDE；NOT NULL 与 CHECK 不通过这项设置推迟。即使属于列出的种类，也需要约束本身声明为可延迟。排查时先查约束定义，再查当前模式，最后查某条语句处于哪个事务，不要只看 ORM 里的一句开关调用。

应用程序真正需要捕获哪一次失败

典型事务包装器在回调内部执行几条 SQL，回调返回后才提交。如果业务层在回调里写入“创建成功”日志或触发外部通知，就可能早于最终检查。更稳妥的边界是：数据库提交确认后，调用方才收到成功；提交异常进入与其他事务失败一致的错误分支。对外部邮件或队列投递，还需单独设计提交后的发送或可靠的待发送记录，不能从数据库提交直接推论外部动作已交付。

验收可以分成三条可判定路径。第一，暂时缺少被引用行，随后在同一事务补齐，检查点与提交应成功。第二，始终缺少被引用行，切回即时模式或提交应失败，最终不得留下订单。第三，在检查点通过后再次制造违规，最终提交仍应失败。这三条要经由应用实际事务入口执行，尤其让测试观察包装器退出时的异常；仅调用单条 INSERT 的测试抓不到最重要的失败位置。

若目的是批量导入或重排关联记录，延迟检查能给事务一个受控的修复窗口。若根本没有“暂时不一致、随后修复”的必要，默认即时检查通常让错误更靠近原因，也更便于定位。写设计时明确窗口从哪一步开始、在哪一步恢复、在何处强制检查、谁负责处理提交失败，比笼统说“开启延迟约束更方便”更可操作。

把事务边界放进调用链

在代码评审里，最该问的不是“SQL 有没有 COMMIT”，而是谁实际控制它。有的数据库客户端自动提交每条语句，有的框架在回调结束后统一提交，还有的事务被上层请求或任务包装。若 SET CONSTRAINTS 在一个连接上执行，而写入却被连接池分配到另一个连接，预期的时序根本不存在。排查要记录同一事务中的连接、起止位置与约束模式；把示例 SQL 复制进应用而不确认连接绑定，不能证明效果。

数据库拒绝提交后还要决定如何向调用方表达。应区分约束冲突这种可解释的业务或数据错误，与连接中断时提交结果未知的情况；后者不能贸然重试一整组可能已成功的外部动作。若同一请求还修改缓存或发送通知，回滚数据库并不能自动撤销那些动作。把通知放在提交后，或采用可审计的待发送模式，是为了让外部观察顺序与事务事实一致。这里不声称某一种模式能独自保证端到端交付，具体重试与去重需要另外验收。

批量迁移时还可用分段检查帮助定位：在一个逻辑批次完成后切回即时，核对通过再继续下一段。不过从这时开始该约束会按即时模式检查后续语句，若下一段还需暂时不一致，必须再次明确切换。随手在事务开头设成延迟然后忘掉，往往把最后一条违规留到最难诊断的位置。设计文档最好画出每个批次的“暂时破坏—修复—主动检查”三点，并给失败批次一个可重试的输入标识。

本站的RETURNING 与事务边界解释了返回行为什么不等于提交。本题再加一层：即使所有写入语句都返回成功，延迟约束仍可能在事务出口否决整组修改。验收记录应写清实际约束声明、模式切换、失败时点和最终库状态；只有后两者一致，成功提示才有依据。
