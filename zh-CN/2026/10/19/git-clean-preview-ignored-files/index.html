三次 git clean 预览，为什么删的不是同一批？

用草稿、构建目录与本地配置演算 -nd、-ndx、-ndX 的候选差异，并核对路径、忽略规则与恢复副本。

正文

核心要点

  • -nd 预览普通未跟踪项，-ndx 还含忽略项，-ndX 只看忽略项。
  • 忽略只表示跟踪规则，不代表本地配置、报告或其他文件可删除。
  • 预览与执行要保持同一目录、pathspec、选项和文件状态，并先确认可恢复内容。

团队想删掉构建产物，工作区却同时放着未提交的设计草稿和被忽略规则排除的本地配置。有人先跑 git clean -nd，清单里没看到配置，于是准备执行“清干净一点”的 git clean -fdx。这一步已经换了范围：dry-run 看过的对象与将要删除的对象不再相同。Git 的clean 官方手册把 -n、-d、-x、-X 和路径参数的含义分开说明；预览的价值不在于命令里有 -n，而在于它与最终动作是同一个选择问题。

在同一组文件上比三份候选清单

设仓库根目录已跟踪 src/app.js 和 .gitignore，规则忽略 dist/ 与 local-config。工作区另有未跟踪的 notes/draft.md、被忽略的 dist/bundle.js、被忽略的 local-config。这是教学用目录状态，不是当前项目文件清单。若在同一根目录、同一规则下分别预览，git clean -nd 的候选是普通未跟踪的 notes/；git clean -ndx 还会把被忽略的 dist/ 与 local-config 纳入；git clean -ndX 只会选忽略项，即 dist/ 和 local-config，而不是设计草稿。具体终端行可能以目录或文件路径显示，不应把上述集合描述冒充实际 stdout。已跟踪的 src/app.js 不属于这三份 clean 候选。

这里的 -n 是只显示不删除，-d 在没有 pathspec 时让未跟踪目录进入范围；小写 -x 不使用标准忽略规则，因而可选中忽略内容，大写 -X 则只选被 Git 忽略的文件。大小写是一种实质性选择，不是参数写法偏好。-x 与 -X 不能作为“更强一级/更弱一级”的线性等级理解：一个包含普通未跟踪与忽略项，另一个只看忽略项。把三份候选做差，才看出扩大的范围具体多了哪些文件。

local-config 是负面案例。它可能包含只能从本机恢复的开发配置，恰恰因为不应提交才被忽略。git clean -ndX 把它列入候选，不代表它是缓存；git clean -ndx 也不会替团队确认是否有安全备份。忽略规则回答“Git 默认是否追踪”，文件价值回答“能否删除”，两者需要不同的人核对。对于被忽略但必须保留的内容，可以先做有权限的备份、验证可读性，再考虑清理；若用途不明，缩小目标到 dist/ 比泛用 -x 更合理。

还有一个容易被忽略的前提：忽略规则并不会把已经被 Git 跟踪的文件重新变成未跟踪文件。如果团队早年曾提交 local-config，后来才把它加入忽略规则，git clean 并不是处理其已跟踪状态的工具。排障时应先查该路径的跟踪状态，再解释它为何不在任何预览里。不能因为 -X 没列出某个敏感文件，就断言文件不存在或已被保护；它可能是已跟踪文件、在当前工作目录之外，或者未匹配本次 pathspec。候选清单必须与文件清单和权限审查配合阅读。

路径、排除模式和时间都影响范围

预览从根目录运行，执行时在子目录运行，起始范围已变。预览命令带 -- dist/，执行时省略路径，范围又被放大。手册还说明，指定 pathspec 后 -d 的通常递归限制不再按无路径时的方式起作用，所以不能凭“我没有加 -d”就推断一个显式目标目录内部安全。-e <pattern> 可额外排除匹配项，而且与 -x 组合时仍应单独核对规则。团队脚本应在日志中打印工作目录、完整参数和目标路径，再让使用者看同参数的 dry-run，而不是只显示“清理缓存”按钮。

还有预览与执行之间的时间窗口。第一次预览后，构建工具可能新建 dist/manifest.json，同事可能在 notes/ 里写新文档，生成器也可能更新忽略规则。旧清单只代表当时状态；若文件有任何变化，应重新预览并看差异。即使没有变化，dry-run 输出的是“将操作哪些路径”的候选，不是这些路径的内容快照，也不是可恢复凭证。把清单保存在将被删除的目录中，执行后连核对证据也会失去。

嵌套 Git 仓库另有保护：手册说对含 .git 子目录的未跟踪仓库，即使已有一次 -f，仍需第二次强制才允许修改。看到这样的路径时应先查它是否是独立工作区，而不是机械补第二个 -f。相反，普通未跟踪文件没有被版本历史保护；git status 看得见它，不代表可从 Git 恢复。git clean 与对已跟踪修改使用的其他恢复命令也不是一回事，不要把“一次清理工作区”混成无法审查的一串命令。

把候选范围与保存证据分开

在本例，如果目标只是重新生成前端 bundle，可先验证 dist/ 真的可重建，然后从仓库根目录对 dist/ 做带 pathspec 的同范围预览，核对候选只覆盖该目录；保留 local-config 与 notes/draft.md。若目标是恢复一份尽量空的临时构建工作区，-x 的候选会更广，先确认所有非跟踪内容已经被备份或确实不需保留，再由具备工作区所有权的人决定是否清理。不要从“这次是 CI 机器”直接推断无价值文件；有些 CI 工作区也会持有生成报告或调试证据。

可做一个隔离验证而不触碰实际项目：在临时仓库建立上述跟踪、未跟踪和忽略状态，记录 git --version、忽略规则文件内容、工作目录及三条 git clean -nd、-ndx、-ndX 的原始输出；只用 dry-run 对照手册预测。若要演练执行，应使用可丢弃夹具且先保存内容；不需要在真实工作区为文章测试删除。本文没有运行这个探针，因此不把集合推导包装为现有仓库的实测清单。

站内stash 对未跟踪和忽略文件的范围可帮助选择临时保存方式，但 stash 条目存在也不自动证明每份需保存的内容都在里面。真正可执行的审批应对应当前目录、当前参数、当前规则、当前候选路径和已核验的恢复副本。若其中一个条件变化，重新预览；若某项文件价值不明，先缩小路径。安全不是一条万能的 clean 命令，而是让预览清单、保留内容与最终动作指向同一批具体文件。
