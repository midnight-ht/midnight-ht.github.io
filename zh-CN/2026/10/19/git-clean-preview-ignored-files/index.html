用三个 dry-run 对照清理范围

用 dry-run 区分普通未跟踪、包含忽略与仅忽略文件，按同一目录和参数核对真正的清理范围。

正文

清理工作区前，应使用与计划清理范围相同的 git clean 预览参数。普通未跟踪文件、包含忽略文件和只清理忽略文件，是三种不同选择。文件被忽略，表达的是提交规则，不能据此判断它是否可以丢弃。

下面三条命令是未执行示例，只用于比较清单，不会在本文中实际清理仓库：

git clean -nd
git clean -ndx
git clean -ndX

三份清单回答三个问题

Git clean 官方手册说明，-n 或 --dry-run 只显示将要执行的操作，不实际删除。-d 在未指定路径条件时让命令进入未跟踪目录；小写 -x 不使用标准忽略规则，因此包含忽略文件；大写 -X 则只选择被 Git 忽略的文件。大小写改变的是范围，不能凭印象替换。

假设仓库中有未跟踪的说明草稿、被忽略的构建目录，以及被忽略的本地配置。第一份预览通常不会包含后两类；第二份会把忽略内容也纳入；第三份只关注忽略内容。这是假设目录，不是当前工作区清单。真实输出仍取决于当前位置、路径参数、排除模式与仓库规则。

尤其不能把第三份理解成“只删缓存”。本地配置、测试素材或尚未纳入管理的大文件都可能被忽略，它们是否可重建需要人判断。反过来，未被忽略的临时文件也可能没有价值。跟踪分类帮助选择路径，文件价值决定是否允许删除，两者不能互相代替。

预览与执行必须保持同一个范围

从仓库根目录预览，与切到子目录后执行，不一定对应同一组路径。预览时没有 -x，执行时再加上它，也相当于临时扩大范围。建议在确认目录、参数与排除条件后保存清单；如果这期间构建或其他工具产生了新文件，再次预览，不把旧清单当作永久批准。

手册允许用路径参数缩小目标，也允许额外排除模式。此时应重新读取各选项的组合含义，而不是机械拼接短参数。例如，指定路径后，目录选择不再完全依赖无路径时的 -d 规则。团队脚本若封装清理命令，应让使用者看得到最终命令和工作目录，避免“清理构建产物”这样宽泛的按钮名称掩盖实际范围。

涉及嵌套 Git 仓库时，手册还有额外的强制保护。它不是建议增加强制次数的理由；清单出现意外仓库，应先确认边界。本文不提供一条无条件执行删除的命令，也没有运行强制清理。

保存工作与移除文件要分别核对

清单本身只保存路径，并不保存文件内容。把预览输出留在工单里，有助于说明当时选择了什么，却不能在误删后重建那些文件。真正需要保留的内容，应先存到适当位置并核对可读性；清理脚本也不应将清单文件自身放进随后会被删除的目录。

准备清理前，需要保留的未跟踪或忽略文件，应先按其用途选择存储与权限方式，并确认内容可恢复。不要假定 Git 历史会包含从未被记录的文件，也不要把秘密文件随意加入提交来换取安全感。

若计划用临时保存，可先阅读stash 的未跟踪与忽略范围，再核对条目实际内容。保存成功与删除范围正确是两个结论。最终决定应对应当前预览中的具体路径；某项用途不明，就先缩小清理目标，而不是扩大参数尝试把工作区一次清空。
