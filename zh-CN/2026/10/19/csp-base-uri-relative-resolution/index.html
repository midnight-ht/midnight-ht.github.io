同源 CSP 下，相对链接为什么还需要 base-uri？

通过相对链接解析过程区分 CSP 资源许可与 base-uri，给出浏览器验收和同源路径边界。

正文

核心要点

  • base-uri 限制文档采用的 base URL，default-src 不会为它提供回退。
  • 同源 base 仍可改变相对路径指向的目录。
  • 浏览器验收应同时记录原始相对值和解析后的绝对地址。

一页文档只允许从本站加载脚本和图片，团队便认为相对链接也只会落在本站。随后模板里出现一个 <base href="https://example.net/">，原本写作 href="help" 的链接会按新的基准解析。CSP 的资源许可与浏览器怎样解释相对 URL 是两道不同的判断；审查 default-src 'self' 时漏看 base-uri，会把“允许加载什么”误作“地址会指向哪里”。

地址先解析，再进入各自的请求规则

MDN 的 base-uri 文档说明，这个指令限制文档 <base> 元素可使用的 URL，且不受 default-src 回退控制。没有声明 base-uri，并不会因为 default-src 'self' 自动得到同源的 base 约束。<base> 元素参考说明 href 为文档内相对 URL 提供解析基准，连片段链接也可能受影响。

假设页面地址是 https://app.example.test/account/，页面有 <a href="settings">设置</a>、<form action="save">，以及 <script src="/app.js">。未设置 <base> 时，前两者按页面位置解析；若注入或错误模板把 base 改成 https://other.example.test/path/，settings 与 save 的目标会跟着变化。以斜杠开头的 /app.js 则按 base 的源和根路径解析，也可能改变完整 URL。这里的域名和标签是说明性例子，未在浏览器运行；实际项目应以开发者工具读出解析后的绝对地址。

即便 CSP 对脚本加载的限制最终挡住异源 /app.js，普通导航、表单目标和其他相对地址仍有各自的处理规则。也就是说，“某个资源请求被拒绝”并不能证明 base 改写毫无影响。尤其不能把 default-src 当作表单提交目的地的总闸：本站关于 form-action 的说明单独解释了该目的地限制。两个指令分别约束 base 的选择与表单提交位置，评审时应两者都看。

base-uri 'self' 解决什么，仍留下什么

如果业务根本不使用跨源 base，设置 base-uri 'self' 可以限制 <base> 采用非同源 URL。若页面没有使用 <base> 的正当需求，更严格的 base-uri 'none' 也可评估，但要先确认生成器或历史页面是否依赖它。指令不是一键修复所有链接：同源下仍有不同路径；已经写成绝对 URL 的链接有自身目的地；资源、导航和表单还受其他浏览器及 CSP 规则。安全审查应按目标类型逐个检查，而非只数 CSP 标头里有几个 'self'。

<base> 文档还提示两个细节。若有多个 <base>，只有第一个 href 和第一个 target 被采用；给页面末尾再补一个“安全 base”并不能覆盖更早的值。片段链接如 href="#details" 也按 base 解析，可能不再是原文档内部跳转。对模板、Markdown 渲染器或富文本容器，应该检查它们是否允许输出 <base>、输出位置在哪里，以及最终 DOM 中的第一个值是什么。只读源模板不能覆盖客户端后来插入的节点。

审查步骤可以落到一次明确的浏览器实验：载入带有相对链接的测试页，记录 document.baseURI，再读取每个元素解析后的 href、action 或 src；分别在无 <base>、允许的同源 <base>、应被拒绝的异源 <base> 下比较。观察控制台的 CSP 报告与实际请求目标，确认是 base 被拒绝，还是某种后续加载被拒绝。测试环境不应指向真实敏感接收端，表单也不必提交真实资料。这些是拟议验收步骤，本篇没有执行浏览器验证。

还有一个容易被忽略的迁移场景：应用从根路径搬到 /portal/ 后，用 base 简化相对路径，随后把 base-uri 'none' 直接复制到所有页面。安全策略看起来更紧，导航却可能被破坏。应先盘点哪些页面确实需要 base，再选择允许的源或去掉依赖，并做真实页面回归。反之，若只为修复断链而放宽 base-uri *，相对目标被改写的风险也跟着回来。策略应服务于文档的真实 URL 模型。

用相对地址类别定位影响范围

评审时可以把页面里的地址分为四类。settings 这类相对路径会以当前 base 路径为起点；/app.js 这类根相对路径会取 base 的源与根；#details 这类片段看似只动当前页面，也受 base 影响；完整的 https://... 绝对地址不需要 base 才能解释。这个分类可以直接指导代码搜索和测试样本。模板里若大量使用相对 action，改变 base 的影响与只有绝对路径的页面完全不同，不能凭一个资源加载演示外推整站。

也应区分“允许同源 base”和“允许任意路径上的 base”。base-uri 'self' 检查的是可用源，它不表示所有相对链接仍指向原来的目录。比如从 /account/ 改为同源 /legacy/，CSP 仍可能允许，但 settings 的完整地址已变。若业务要求固定路由，应在生成器中输出正确绝对路径或约束模板的 base 值，再用路由测试验证；CSP 只守它被定义要守的边界。

安全场景里也不能略去前提：攻击者要能影响 <base> 才会触发恶意改写。若页面所有 HTML 都可信，主要风险可能是模板迁移导致的误配置；若富文本或拼接 HTML 可以插入节点，风险则包括相对导航与表单目标漂移。base-uri 是限制影响面的一个层次，还需修复不可信 HTML 注入入口。策略以 HTTP 响应头发送时，要确认实际页面、重定向后页面和预览环境得到的是同一套预期值；只检查源代码配置不够。

最后要看浏览器里“发生了什么”，而不只看 CSP 违规日志。被拒绝的 base 可能让浏览器回退到文档 URL 作为基准，于是相对路径仍然能导航；成功拒绝异源 base 与业务页面完全正常是两项独立结果。记录两者才能避免修安全策略时引入断链，又能证明确实限制了不可信目标。

最终判定要用一张小表记录：原始相对值、预期绝对 URL、浏览器实际解析 URL、适用的 CSP 指令及其结果。这样可以区分解析错误、资源加载被挡和目标提交被挡。只有这些位置都写清楚，base-uri 才从一个孤立的安全关键词，变成可以验证的地址约束。
