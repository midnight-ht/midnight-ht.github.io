JSON 的 null 与 SQL NULL，怎样分开判断？

区分 SQL NULL、JSON null、缺键与字符串 null；先保留类型信息，再决定筛选和更新语义。

正文

SQL NULL、JSON null 与对象缺键不是同一种状态。筛选之前先保留 JSON 类型信息，才能决定哪些状态应该合并。页面都显示为空，并不能说明数据库里存着同一种值。

同一个 null 字样，处在不同层

PostgreSQL 18 的 JSON 函数文档说明，jsonb_typeof 返回顶层 JSON 值的类型文本；JSON null 对应文本 ‘null’，不要与 SQL NULL 混淆。它的例子也展示，对 SQL NULL 调用类型函数仍得到 SQL NULL。因此，类型名称为空值与函数没有值，是两个不同结果。

假设资料扩展列 payload 存放用户设置。整列 SQL NULL 可以由接口约定表示尚未收到资料；对象里的某个键值为 JSON null 可以表示用户明确清除；对象没有这个键则可以表示此次更新没有涉及。这里只是假设的协议，不是 PostgreSQL 自动规定的业务含义，团队完全可以约定另一套规则。

若协议需要区分这些状态，查询和写入都应保留差别。一个更新接口先把所有空值删除，另一个读取接口再试图恢复用户是否明确清除，就已经没有足够信息。数据类型解释不能补回上游丢掉的意图。

先看存在与类型，再决定是否取文本

以下表达式用于说明判断层级，未在数据库执行。假设 payload 为 JSONB，查询目标是对象顶层的 nickname。

-- Illustrative only; not executed.
payload IS NULL
payload ? 'nickname'
jsonb_typeof(payload -> 'nickname') = 'null'

第一项看整列是否为 SQL NULL；第二项在这里用于检查顶层对象是否有键；第三项检查提取出的 JSON 值是否为 JSON null。官方文档同时说明，提取操作在结构不匹配或键不存在时会得到 SQL NULL。第三项为真时，说明提取出的值确实是 JSON null；但它不为真时，不能直接推断键不存在，还可能是其他类型或整列为空。使用前应确认输入对象的形状及所需层级。

也要加入字符串 “null”。它的 JSON 类型是 string，不是 null；把屏幕上的字样直接当成类型，容易把用户真的输入了这几个字符与明确清空混在一起。对象、数组与标量都可能是合法 JSON 值，若业务只接受对象，应在入口明确约束，而不是让每一个查询各自猜测。

用文本提取操作符之后再判断为空，可能已经合并了缺键与 JSON null。我的建议是把类型判断放在文本展示之前：需要区分时保留原 JSON 值，需要显示时再转换。若业务本来就规定两者同义，可以合并，但应写成有意的协议选择，不能说数据库天生没有区别。

还应约定整列不是对象时怎么处理：是拒绝写入、迁移旧数据，还是当作另一种状态返回。不要把结构错误默默变成缺键，再让它沿用“本次没有更新”的动作；那会把坏数据解释成正常意图。这个约定应随接口版本保存。

查询语义确定后，再讨论索引

索引能否服务条件，是另一个问题。本站十月十日的JSONB 操作符与索引讨论键存在查询的索引范围。本篇不以某一种判断表达式承诺执行计划或速度，尤其不能为了迁就现有索引而改变“用户清除了字段”的含义。

拟议用例应保留整列为空、空对象、显式 JSON null、字符串 “null” 和正常字符串，并逐项写出读取文案与更新动作。没有运行结果时，这张预期表仍只是设计。先让接口负责人确认哪些状态必须区分，再验证序列化、存储和读取全过程，避免只在 SQL 局部看起来正确。
