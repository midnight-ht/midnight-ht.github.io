字段缺失和显式清空，先别提取成文本

区分 SQL NULL、缺键、JSON null 与字符串 null；先保留类型，再定义更新语义。

正文

核心要点

  • jsonb_typeof 的文本 null 与 SQL NULL 是不同结果。
  • 键存在检查和 JSON 类型检查应先于文本提取，避免合并缺键与显式清空。
  • 部分更新必须约定省略键、JSON null 和字符串 null 各自的动作。

设置页上“昵称为空”看起来只有一种状态，写进 PostgreSQL 的 JSONB 后却可能有四种：整列是 SQL NULL，对象里没有 nickname 键，键存在且值是 JSON null，或者键存在且值是字符串 "null"。若更新接口把它们都映成“空”，就无法判断用户是未提交该字段、明确清除它，还是输入了四个字母。先保留类型与存在性，再决定哪些状态可以合并。

null 处在两套类型系统中

PostgreSQL 18 JSON 函数与操作符文档说明，jsonb_typeof 返回顶层 JSON 值的类型文本，其中 JSON null 对应文本 null；对 SQL NULL 调用类型函数，结果仍是 SQL NULL。这一层区别是数据库机制。把整列 SQL NULL 定义为“尚未取得资料”、对象缺键定义为“本次未修改”、JSON null 定义为“用户要求清空”，则是应用协议的选择，并非 PostgreSQL 自动附带的业务含义。

假设列 payload 约定只保存顶层对象，以下条件要按次序理解：payload IS NULL 看整列是否 SQL 空值；payload ? 'nickname' 在这个对象约束下看顶层键是否存在；jsonb_typeof(payload -> 'nickname') = 'null' 看提取的 JSON 值是否确为 JSON null。若键缺失，提取操作得 SQL NULL，类型检查也不为真。若键存在但值是字符串 "null"，类型是 string。文档还指出，JSON 结构不匹配或路径不存在时，提取操作会返回 SQL NULL 而非报错，所以只凭第三个判断为假，不能反推键不存在。

SELECT payload IS NULL AS column_missing,
       payload ? 'nickname' AS has_nickname,
       jsonb_typeof(payload -> 'nickname') AS value_type,
       payload ->> 'nickname' AS display_text
FROM profiles WHERE id = $1;

上面的查询是未执行的语义示例；假定 payload 是 JSONB 且非空时为对象，profiles 与字段只是说明用名称。column_missing、has_nickname、value_type 分别记录不同维度。display_text 应放在这些判断之后使用：文本提取可能让缺键和 JSON null 都表现为 SQL NULL，而字符串 "null" 则显示为文本 null。若只把 display_text 传给页面，前两者的来源差异已被消除；页面后续再做字符串比较，也恢复不了原来的类型。

更新语义要和读取语义同表定义

最容易踩坑的是部分更新。例如请求体 {} 表示此次不碰昵称；{"nickname":null} 表示用户主动清空；{"nickname":"null"} 表示设置成字面文本。这只是一个可选协议，但若团队选择了它，前端序列化不能把未填写字段一律带上 null，服务端也不能在解析时把 null 属性一律删除。否则“没提交”和“清空”的区别在入库前就丢失了，SQL 查询再精细也无能为力。整列 SQL NULL 是否允许更新、是否表示资料从未创建，应另写规则。把空对象 {} 与整列 SQL NULL 当同义也可以，但要明确迁移和读取方如何处理。

可以做一个状态矩阵帮助接口评审：整列 SQL NULL、空对象、键值为 JSON null、键值为字符串 null、键值为正常字符串，分别列出“接口返回什么”“用户看见什么”“收到省略字段的补丁后怎么变”“收到显式清空补丁后怎么变”。如果每一行都显示成空白，仍可保留内部状态用于下一次操作；用户界面相同不强迫存储语义相同。若业务确实不需要区分某两项，可以在边界层有意合并，并记录为何不会影响操作，而不是凭 UI 截图宣布它们相等。

还要防止结构错误被误判为“键不存在”。? 操作符也可检查 JSON 数组中的顶层字符串元素；若业务只允许对象，数组不应悄悄走对象缺键逻辑。入口可以拒绝非对象，或者在迁移旧数据时单列异常状态。对嵌套键，顶层 ? 'nickname' 并不能检查子对象内部；应先规定路径和父对象形状，再使用相应提取或存在性判断。不要把一个针对顶层对象的例子直接套到任意 JSON 文档。

SQL 的三值逻辑也会影响筛选。payload IS NULL 是判断整列的谓词；jsonb_typeof(payload -> 'nickname') = 'null' 在提取结果为 SQL NULL 时得到未知，不会在普通 WHERE 中当真。若要查询“缺键或显式清空”，应把两种条件明确写出来，并处理整列为空的分支。把条件包在 COALESCE 里虽然可以得到布尔值，却也可能提前把未知与假合并；应先决定业务集合，再选择 SQL 表达式。索引是否覆盖所选操作符，另见JSONB 操作符与索引；索引策略不应反过来改写用户清空字段的含义。

验收需要贯穿客户端序列化、API 校验、数据库存储和读取，而非只在 SQL 控制台看一个表达式。用上述五种状态准备输入，另加非对象 JSON、嵌套路径缺失与显式空字符串；逐项核对是否被拒绝、保留或转换，并确认补丁请求对未提交字段没有副作用。这些是拟议用例，没有真实数据库执行记录。最终可把约定写成一句能够检验的话：省略键保持原值，JSON null 清除该键，字符串 null 是普通文本；若团队选择不同语义，就以自己的接口合同替换这句话，并让写入和读取一致。

若采用“显式 JSON null 表示清除”，还要决定落库动作是保留键并写入 null，还是删除键。两者对当次页面显示可能一样，但下一次查询的 ? 结果不同；如果审计、同步或补丁合并需要知道用户做过清除，删除键会丢失这一层证据。可以把用户意图记录在独立事件或审计字段，而把当前状态按查询便利度存储，但不能依赖一个已删除的键继续证明清除发生过。相反，若协议明确把 null 与缺键视为同义，强行保留二者差异只会增加查询分支。决定应来自后续读取和更新行为，而不是某一种 SQL 写法是否短。

数组、对象与字符串空值还会影响 API 的错误处理。一个 JSONB 列能存储这些顶层类型，不代表资料接口都应接受。若 payload 必须为对象，写入时可以验证类型；已有不合约束的旧值则需要迁移或显式异常响应。把结构不匹配产生的 SQL NULL 当成“用户没填昵称”，会让坏数据悄悄混进正常空状态，之后的统计也无法区分。先把类型错误作为单独状态处理，再讨论缺键与清空是否合并，查询结果才有可解释的前提。
