配置里的 0 为什么变成默认值？

空值合并保留零；先定义缺省、显式空值和非法输入，再逐层验证保存与执行。

正文

核心要点

  • 逻辑或把数字零视为假值；空值合并只在 null 或 undefined 时使用后备值。
  • 空值合并会保留无效负数或错误类型，默认与校验必须分开。
  • Node v24.21.0 的最小检查只证明该环境的运算符结果，业务链路需另验。

用户把自动重试设为零，页面回显也是零，运行时却重试了三次。若读取配置时写成 settings.retries || 3，零会被当成需要补默认值的假值。改用空值合并往往能保留零，但真正该先确定的是业务约定：哪一种输入算“没有配置”，哪一种是用户明确选择，哪一种必须报错。

默认值的条件由字段定义

MDN 对空值合并运算符的说明很明确：左侧为 null 或 undefined 时，空值合并才返回右侧；|| 在左侧是假值时返回右侧。于是 0 || 3 是 3，0 ?? 3 是 0。false、空字符串、NaN 也会被 || 视为假值，不能把 || 当成“字段缺失”的通用检测器。这里是 JavaScript 语言规则；配置场景是设计示例。为核对运算符，已在 Node v24.21.0 上运行最小脚本：零经逻辑或得到三，经空值合并仍为零；假值 false 和空字符串也只在后者保留。脚本与原始输出存于本批审校材料，这项执行不证明浏览器或业务服务的行为。

先为“重试次数”写一张语义表：属性完全缺失时采用三次；明确传 null 是否允许重置为默认；数字零表示关闭重试；正整数表示最多重试次数；负数、小数、字符串和非数字是否拒绝。只有当这张表规定 null 与缺失同义时，使用空值合并才恰好符合默认条件。若 null 表示“清除继承配置”，它可能需要单独处理；若接口用零表示“不指定”，直接换运算符反而改变约定。跨层修改前应找出持久化、API 和运行时对同一值的解释。

更隐蔽的是输入类型。浏览器表单常把数字输入作为字符串交给应用，"0" 既不是数字零，也不是假值。"0" || 3 会保留字符串，把字符串零作为空值合并的左侧也会保留字符串；两者都没有完成范围和类型校验。若运行代码后来做加法或循环比较，错误可能移到更远处。入口应先按接口规则解析并检查整数范围，再为真正缺失的值补默认。不要用一个表达式同时承担三项职责：判断字段有无、转换类型、确认业务有效。

按配置来源逐层追零值

一个可审查的读取函数可先分开未提供与已提供的输入。以下代码只演示“缺省或显式空值走默认，其余必须是零到五的整数”的假设规则；它未在项目中运行，实际上限应来自业务要求。

判断顺序可以明确写成三步：输入为未定义或显式空值时返回默认三次；其余输入必须是数字、整数，且落在假设的零到五区间；不满足条件则返回校验错误。零在第二步合法通过，字符串零在类型检查处被拒绝。实际产品的上限要从业务规则取得，不能照抄这个假设值。

这样的分支比一个默认表达式长，却把无效值与缺省值分开。零明确返回零；字符串零明确拒绝，由调用者决定是否在更靠近输入的一层解析。若服务允许最多五次，验证上限是业务合同的一部分，不能照抄示例。若应用有环境变量、用户设置和组织策略三层优先级，还要规定哪层的零能够覆盖上层、显式 null 是跳过该层还是清除继承值；简单把多个 || 串起来会让“关闭”一路被后面的默认值吞掉。

举一个层级推演：组织默认三次，用户明确设为零，当前任务未给值。读取顺序若是任务配置、用户配置、组织配置依次空值合并，在“空值表示继承”的协议下结果为零，符合用户选择。若任务字段为 null 且协议把它定义为“禁用所有重试”，这串表达式会错误地跳过它。语言运算符不会替应用定义继承规则；出现多个配置源时，先把状态机写出来，再选表达式。这样的显式判断还有助于记录到底是哪层配置生效，而不是只得到一个没有来源的最终数值。

保留假值不等于接受坏值

空串可能是用户有意输入的标题，也可能是违反必填规则的无效内容。布尔 false 可能是明确关闭通知，NaN 却很少是合法计数；空值合并会原样保留它们。一个配置字段适用空值合并，不意味着所有字段都能机械替换。对标题，如果空白字符串应视为错误，就在校验中处理；把空串默默换成默认标题会掩盖用户输入问题。对开关，默认开启与用户关闭必须分别测试。对计数，零、负数和小数应按产品规则单独列出。默认条件只回答“没给值时怎么办”，校验回答“给了这个值能否接受”，两者在读写链路上都要有位置。

MDN 还指出，空值合并不能直接和 || 或 && 混写而不加括号，否则会产生语法错误。括号可以说明运算顺序，但若括号里的真假判断仍把零吞掉，语法正确也不会使业务正确。表达式跨越多个来源或规则时，拆成命名变量与分支通常更便于评审。可选链配合空值合并可以处理设置对象不存在的情况，但可选链也会把“对象不存在”和“属性值为 undefined”并到同一默认路径；这是否合适仍要由数据协议决定。

验收不该只断言 零经空值合并后的语言结果。为同一个字段准备缺失、undefined、null、零、正整数、负数、字符串零、空串、false 与 NaN，写明每项应默认、保留还是拒绝；再穿过页面保存、API 读取和真正消费配置的位置。零在界面上可见却运行时被覆盖，说明只看回显不够。服务端仍需独立执行自己的输入与授权检查，详见表单校验与服务端权威。这组用例是建议的验证计划，尚无执行结果。最终要能向评审者说清一句话：这个字段仅在什么条件下才采用默认值。

还有一个经常被忽略的写入边界：MDN 的 JSON.stringify 说明指出，在默认序列化下，对象属性值为 undefined 时会从 JSON 结果中省略，而 null 值会保留。若更新 API 用“未出现”表示不修改，用 null 表示清空，配置对象从内存到请求体的转换会改变可观察状态。评审不应只比较运行时表达式，还应核对最终发出的 JSON 与服务端接收后的字段存在性。若要把配置回填到表单，显示层也应从已校验的有效值读取，而不是再次用 || 渲染默认值，否则运行逻辑虽已修复，界面仍会把零显示成三。把保存、读取、显示和执行四处的预期列在同一张用例表，才不会让修复停在某一层。
