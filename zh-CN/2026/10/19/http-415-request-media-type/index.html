415 排查顺序：媒体类型、内容编码、正文

HTTP 415 指向请求内容格式；对照同一请求的声明、编码和实际载荷，再验证业务结果。

正文

核心要点

  • 415 的支持范围绑定目标资源和方法，不由请求 Accept 决定。
  • Content-Type、Content-Encoding 与实际正文要在同一条失败请求中对照。
  • 状态不再是 415 后仍需核对字段读取和业务结果。

接口返回 HTTP 415 时，先把“这次实际发送了什么”放到桌面上。请求里写了 Accept: application/json，只说明客户端偏好怎样的响应；它不会把表单正文变成 JSON，也不能替服务器决定是否接受上传。415 的判断点在目标资源、请求方法与请求内容的组合，排查要从同一条失败请求取证。

415 指向哪一层

RFC 9110 第 15.5.16 节说明，服务器因目标资源上的该方法不支持请求内容格式而拒绝服务时使用 415；格式问题可能来自请求所声明的 Content-Type、Content-Encoding，也可能来自检查数据本身。这是状态码的语义范围，不等于每个框架都以相同顺序做检查，更不能凭一个状态推断根因。

先分清三种信息。Content-Type 描述发送的表示的媒体类型，例如 JSON 或 multipart 表单。Content-Encoding 告诉接收方正文在媒体类型之外经过了什么内容编码，例如是否压缩。请求 Accept 表达客户端愿意收到的响应媒体类型。这三个字段都可能出现在排查截图里，但方向和责任不同。假设一个上传接口只接受 multipart，调用方却用 JSON 序列化了文件描述；提高请求 Accept 的优先级不改变发送字节。反过来，写上 multipart 头却仍发送 JSON 文本，也只是制造一个声明与正文不一致的请求。

“同一路径”仍需看方法。一个资源可能允许 POST 上传 multipart，却只允许 PUT 接受 JSON 的完整表示；在前者成功的抓包不能证明后者应接受同样内容。还要确认实际请求有没有被网关改写、重定向或客户端库自动序列化。把 API 文档里的样例头与运行中另一个请求的正文拼成证据，最容易让团队围绕一条根本不存在的报文讨论。

用一组可比较的请求定位

以下为假设情境，没有向真实服务发送请求。服务契约规定 POST /imports 只接受 JSON 对象，调用方提交的正文却是 item=42&mode=merge，请求头标为 application/x-www-form-urlencoded。首先记录方法、路径、请求 Content-Type、Content-Encoding、脱敏后的正文结构和响应状态；下一步从契约取得允许的格式，构造一个内容仍表达同一业务意图的 JSON 正文并匹配类型声明。若第二次不再返回 415，只能说格式相关改动有帮助，仍应验证服务确实读到了 item 与 mode，并检查业务处理结果。

这个对照要求一次只改一个与假设有关的层面。若同时换了路径、认证身份、请求方法和正文，状态改变就不能归给媒体类型。安全上无需保存秘密值，但脱敏不能抹掉格式证据：JSON 的对象结构、表单字段名称、文件部分与 multipart 边界应有足够信息供复核。实际诊断还要看网络工具显示的最终请求，而非源码里打算设置的选项；浏览器和客户端库可能根据 body 类型自动决定某些头。

另一个常见分支是“头看上去正确，仍得 415”。若实际正文压缩了，Content-Encoding 与服务器所支持的请求编码要相符；即便媒体类型正确，编码仍可能不受支持。若未压缩却错误声明了编码，接收方按声明解码也会走错路径。检查时把原始正文的构造流程与最终头字段一起核对，不能只对比 Content-Type 字符串。具体服务也可能检查正文实际格式后拒绝；需要错误响应、服务日志或可控对照才可进一步定位。

RFC 对 415 响应里的提示也有方向上的细节：若拒绝源于不支持的内容编码，响应 Accept-Encoding 应说明可接受的请求编码；因其他原因返回 415 时，规范要求服务器不要在该响应中带这个字段。若源于媒体类型，响应 Accept 可以说明可接受的请求媒体类型。这里的 Accept 是服务器写在响应里给客户端的线索，与客户端预先写在请求里的偏好同名而异向。没有提示时不能反推服务器一定支持哪种格式，仍应查接口契约与接收端记录。

不要把格式修复误写成业务成功

415 与相邻错误有不同含义。正文格式已经可理解，但内部指令不合业务约束时，RFC 的 422 语义更贴近；目标资源或版本冲突可能落在其他状态。应用也可能自定义错误响应，排查笔记应报告观察到的状态和文本，不应替服务器重分类。若修复格式后得到 400、401 或 422，这反而提示请求进入了另一个检查阶段，却不自动证明原先的每个字段都正确。

团队可以把排查结果固化为一个小测试矩阵：契约允许的媒体类型与正文、声明正确但正文格式错误、不支持的媒体类型、编码不受支持，以及空正文或边界不完整的情况。每一格要写预期由谁拒绝、客户端显示什么、服务端是否发生业务副作用；具体预期依该接口契约定。对 multipart，尤其要检查客户端是否负责生成边界，手写一个不含匹配边界参数的头可能破坏请求。对 JSON，检查序列化结果而非对象在调试器里的外观。

修完之后，至少核对同一方法和路径实际送达的字段、服务返回的业务标识，以及相关状态是否落库；不能用“已不是 415”替代这些证据。若要进一步核对客户端对响应的处理，可接着看请求 Accept 与响应检查。下一次有人提出“改 Accept 试试”，先请他指出要改变的是请求内容、编码，还是响应偏好；只有前两者直接落在 415 的主要排查范围内。
