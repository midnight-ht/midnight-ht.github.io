多选取消后还提交旧值，查 FormData 的条目

同名字段可保留多值；按字段基数决定替换或从当前选择重建，并核对服务端解析。

正文

核心要点

  • append 会保留同名旧条目，set 会覆盖该名称的全部既有值。
  • 多选取消后应从当前选择生成提交快照，避免复用对象积累旧值。
  • Node v24.21.0 的 getAll 输出不代表浏览器请求或后端重复键行为。

页面上的标签已经取消，提交请求里却仍有那一项。先别假设服务端读错了：若前端复用同一个 FormData，每次选择变化只调用 append("tag", value)，旧条目仍留在对象中。FormData 更像按顺序保存的表单条目集合，而不是同名属性只保留最后一次赋值的普通对象；要修复，先确定字段允许几个值，再决定如何生成一次提交的快照。

append 和 set 对同名字段做了什么

MDN 的 FormData.append 文档区分得很清楚：append() 把值接在该名称已有条目之后；set() 用新值覆盖该名称此前的全部值。如果这个名称还不存在，追加会建立新条目。假设一个多选输入允许 design 与 delivery 两个标签，连续追加两个 tag 是合理的；若 priority 是单选字段，用户从 low 改成 high 时再追加，就保留了两个相互冲突的状态。

const data = new FormData();
data.append("tag", "design");
data.append("tag", "delivery");
const selected = data.getAll("tag"); // 语义预期为两个值

这段代码是说明 API 语义的示例；在 Node v24.21.0 的最小脚本中，追加后 getAll("tag") 实际输出 ["design","delivery"]，随后 set("tag","research") 输出 ["research"]。原始脚本和 stdout 留在本批审校材料。它只验证该 Node 环境中的接口行为，不能替代浏览器请求与服务端解析验收。getAll 比只读一个值更适合诊断重复字段，因为只看单个条目不能证明集合里没有其他同名值。网络面板还应查看实际发送的载荷；日志里打印一个对象名称，不等于列出了全部条目。需要复核顺序时可迭代 entries()，并把名称、值的类型和文件名纳入观察，但勿把敏感内容原样写进共享日志。

set 也不是多值字段的通用替代品。若用户选中了两个标签，对第二个值调用 set("tag", "delivery") 会删掉前一个标签。一个明确的接口契约应写出每个字段的基数：priority 恰好一个，tag 可多项，attachment 是否允许多个文件；再写重复键到达服务端后的规则。不同解析器或框架可能返回首个、末个、数组，或触发校验失败。浏览器提供多值条目，并不替业务接口决定重复键该如何解释。

事件累积不是提交快照

容易出错的设计是把 FormData 当作长寿命状态容器。第一次选中 A 时追加 A，第二次选中 B 时追加 B，后来取消 A 时没有对应的移除动作；此时页面状态是 {B}，表单对象状态却是 {A, B}。即便补一个 delete("tag")，它会删除该名称的所有值，随后还得依据当前选择重建。相比维护一套操作日志，对多选字段从当前权威状态构造新的提交对象更直观：提交开始时创建 FormData，遍历当前选项各追加一次，核对 getAll("tag") 与界面选择集合一致。

单值字段可以用 set 表达“以当前值替换以前所有同名条目”。但也要考虑初始对象来自 <form>：new FormData(form) 已经包含有 name 的成功控件条目。再 append 一次“修正值”不会覆盖原有控件；若控件本身是多选或复选框，生成对象时可能已经产生多个同名条目。评审应从表单控件、脚本追加和服务端解析三个位置画出数据流，不能只审最后一行代码。若两个模块都负责加 tag，要明确谁拥有这个字段；否则每个模块在自己的局部看起来正确，合在一起却重复。

删除所有旧条目后重建同名字段也有代价：如果其他模块合法追加了该名称，清理会连它的值一起删掉。接口设计最好给字段建立唯一责任边界，或用明确的名称区分来源。对于提交中途用户又改变选择的界面，快照的取值时刻也要定义：点击提交时冻结当前状态，还是等待异步校验后重新读取？后一种可能让用户看到的确认内容与真正发出的条目不一致；可通过禁用提交期间的编辑或生成一次不可变请求数据来处理。

值被发送前还会发生转换

MDN 说明，传给 append 的非字符串、非 Blob 值会转成字符串。追加数字零不意味着服务端收到数字类型，追加布尔值也不意味着服务端已经收到布尔类型。若协议要求整数，应由接收方按明确规则解析和校验，不能用前端变量类型作为保证。文件条目还有文件名等元数据；同名的多个文件需要端点明确支持，不能因为浏览器允许追加就假定后端允许批量上传。有关预览与保存的生命周期，可参看Blob URL 与文件保存，但预览成功也不能替代本次表单载荷的验收。

一个可执行的检查矩阵可以围绕状态变化，而不只测静态两次追加：单选改选后旧值是否消失，多选取消后是否只剩当前选项，表单控件与脚本是否叠加同名字段，连续提交是否带上上次条目，空集合是零条目还是一个空字符串，以及文件列表删除后的条目。每项都比较界面状态、getAll、实际网络载荷和服务端解析结果。服务端应按字段基数拒绝不允许的重复项，而非默默取某一个值完成高风险操作。此处列的是验证方案，没有针对某个后端或浏览器执行。

最后的判断很简单，但不能省略前面的语义：多值字段用 append 表达当前集合中的每一项，单值字段用 set 或一次性构造保证只有当前值；在服务端再以同一份基数契约验证。这样“用户取消了什么”会体现在真正发出的条目里，而不会藏在一个复用对象的历史里。

对于排序敏感的多值字段，还应约定顺序是否有意义。append 按调用顺序增加条目，但服务端若把它转为无序集合，拖拽排序的结果就可能丢失。若顺序属于业务语义，前后端要约定数组顺序或显式序号，并用“交换两项位置”验收，而非仅检查两个值都存在。若顺序无意义，客户端也应避免把偶然的遍历顺序当成永久标识。这个决定与是否允许重复值不同：同名多值可以合法，同名同值重复却可能仍是错误提交。
