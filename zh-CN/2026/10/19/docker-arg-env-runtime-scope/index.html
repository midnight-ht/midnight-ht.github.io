构建能读到 ARG，容器启动后为什么没有？

ARG 不会自动成为容器环境变量；按构建阶段、镜像默认值与运行时消费方式核对配置交接。

正文

构建步骤能读到 ARG，不代表镜像启动后的进程会继承同名环境变量。ARG 主要为 Dockerfile 的构建指令提供参数；需要写入镜像的运行默认值时，应明确使用相应配置，而需要随部署变化的值还要由运行环境提供。

先问这个值在哪里被消费

Docker 构建变量文档说明，构建参数不会自动出现在由镜像创建的容器里，除非 Dockerfile 显式把它传入镜像文件或配置。ENV 则会保留为镜像创建容器时的环境默认值。两者都叫变量，但生效阶段不同。

考虑下面这个未执行的 Dockerfile 片段，它只演示非敏感参数的传递关系，不是可直接构建的完整文件：

ARG APP_MODE=production
RUN echo "$APP_MODE"
ENV APP_MODE=$APP_MODE

其中构建命令能够读取参数；后面的环境声明才把值作为默认环境写入镜像配置。删除最后一行，不能因为日志里曾出现参数，就期待运行进程自动得到它。日志证明某个步骤看到了值，不证明应用最终采用了预期配置。

这个区分会改变交接方式。依赖版本可能只在构建中使用；监听端口可能在进程启动时读取；浏览器端接口地址又可能被打包工具编译进静态文件。评审应逐项说明谁读取、何时读取、结果存在哪里，而不是为整个项目选择一种变量后就结束。

多阶段构建还有声明范围

文档也说明，在 Dockerfile 全局范围声明的构建参数，不会自动被每个构建阶段继承。若阶段内要使用全局参数，需要在该阶段消费相应声明。排查“参数明明传了却为空”时，要同时看构建调用和实际使用位置，不能只搜索文件顶部出现过一次名称。

复制上一阶段生成的文件，也不等于复制它的全部环境配置。一个阶段把值写进产物，另一个阶段再复制产物，传递的是文件内容。若后续进程需要读取环境变量，应单独确认最终镜像与运行配置；若值已经编译进网页文件，则运行时同名变量未必会重新生成它。

后一点属于应用构建方式带来的判断，需要查实际工具和启动逻辑。这里没有指定某个框架，也没有把修改环境后自动生效当成通用行为。把变量打印出来可以辅助定位，但对秘密值不应采用这种做法。

运行默认值不是部署事实

例如，可选用专门的非敏感标记，分别查构建输入、生成文件与进程报告的有效设置。若文件仍含旧标记而进程环境已改变，下一步应检查产物生成阶段；若文件无需变化而程序仍用旧值，则应追踪读取时机。这样的分叉能决定应该重建镜像还是调整启动配置。

即使镜像设置了 ENV，部署仍可能提供不同环境值；应用是否读取它、是否有配置优先级，也取决于程序实现。建议在交付说明中区分镜像默认配置与部署实际配置，并用非敏感的有效配置摘要观察采用结果。不要把镜像检查输出写成线上配置已经生效。

构建参数和环境变量都不适合充当构建秘密的通道，相关输出风险可阅读构建秘密与最终产物。本文没有执行构建或容器启动。待验证的重点是：同一个值从输入到产物再到进程，究竟跨过了哪一步，哪一步仍需要显式传递。
