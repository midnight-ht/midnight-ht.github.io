ARG 有值，容器环境为何为空？沿三次交接排查

用完整两阶段镜像追踪构建 ARG、产物文件、镜像 ENV 与运行覆盖，定位同名配置在哪一步失联。

正文

核心要点

  • ARG 可供构建指令使用，但不会自动成为最终容器的环境变量。
  • 全局 ARG 须在使用它的构建阶段消费；COPY 文件不等于复制上一阶段环境。
  • 镜像 ENV 是默认值，部署可覆盖；应用有效配置还要由进程本身验证。

构建日志显示 APP_MODE=staging，镜像启动后的进程却读不到 APP_MODE。这不一定是 Docker 丢了变量，而是构建输入、镜像配置和容器运行环境属于三个不同的交接点。Docker 构建变量文档明确说，ARG 若没有被 Dockerfile 显式写进文件或镜像配置，不会自动存在于镜像创建的容器；ENV 则会作为容器环境默认值保留。排查时先问这个值由谁、在什么时候消费，再选 ARG、ENV 或部署输入，而不是看构建日志里出现过同名字符串就宣布交付完成。

用完整的两阶段镜像追踪一个值

考虑这个只用非敏感标记的教学 Dockerfile；示例使用经官方发布分支页核对的 Alpine 3.24，仅演示变量作用域，本文未拉取或构建镜像；真实项目应自行选定基础镜像，且不要把秘密放进去：

ARG APP_MODE=production
FROM alpine:3.24 AS build
ARG APP_MODE
RUN printf '%s\n' "$APP_MODE" > /mode.txt
FROM alpine:3.24
COPY --from=build /mode.txt /mode.txt
CMD ["sh", "-c", "cat /mode.txt; printenv APP_MODE || true"]

假设执行 docker build --build-arg APP_MODE=staging -t mode-demo .，然后 docker run --rm mode-demo。按文档语义推导，/mode.txt 会含 staging，因为 build 阶段把 ARG 写成文件并由最终阶段 COPY；但最终容器里没有因为这个 ARG 自动出现名为 APP_MODE 的环境变量，printenv 不应把 staging 当作继承值。这个“文件有值、进程环境无值”的组合就是案例结果，并非本文真实执行的 stdout。若最终阶段另外写 ENV APP_MODE=production，新容器的默认环境才有 production；运行时用 docker run --rm -e APP_MODE=release mode-demo 又可提供 release。文件仍是构建时写入的 staging，不会因运行环境改变自动重建。

首行全局 ARG 给出未传参时的默认值，build 阶段内的 ARG APP_MODE 才让该阶段的指令消费它。若像本例显式传入 --build-arg APP_MODE=staging，可省去全局默认声明而保留阶段声明；若未传参，删掉全局默认就会改变默认行为。反过来，只留全局声明而删掉阶段声明，不能让 RUN 自动获得该参数。Docker 文档说明，全局范围声明的构建参数不会自动进入每个构建阶段；阶段内要使用它，必须在该阶段消费声明。这个片段里 RUN 读取的是 build 阶段可用的值。最终阶段没有 ARG APP_MODE，也没有 ENV；它只复制已经生成的文件。若要让最终阶段的指令再读取构建参数，应在那个阶段按语义重新声明并核对值，而不是误把上一个阶段的 shell 环境当作自动延续。

这也说明日志为何会误导。RUN echo "$APP_MODE" 可证明那条构建指令看到变量，不能证明最终镜像的配置里有它；COPY --from=build 可证明文件被复制，不能证明环境变量一起复制；镜像配置里即使写了 ENV，也不能证明部署平台没有覆盖它，更不能证明应用读取了该值。评审时把证据分别标为构建输入、产物字节、镜像默认、容器环境和应用有效配置，每一层都留一次可核验的观察。

不同消费时刻要选不同通道

依赖版本若只用于 RUN 选包，ARG 可能合适；应用启动时读取监听模式，镜像 ENV 默认或部署环境更接近消费点；浏览器网页里的接口地址如果在构建时被前端工具编译进静态 JavaScript，则运行容器的同名环境变量通常不会改动已生成文件。最后一种行为还取决于具体构建工具和启动脚本：有些项目启动时会模板替换文件。不要把“网页变量必定构建期固定”写成所有框架的规则，要看实际代码在什么时候读取和输出它。

选择把 ARG 经 ENV APP_MODE=$APP_MODE 传到最终镜像时，也要问是否真的希望所有基于该镜像的部署继承这个构建时决定的默认值。若 staging 和 production 共用一个镜像，环境特定配置更适合在部署阶段提供；否则一次构建会把 staging 默认烙进镜像，生产若忘记覆盖就可能跑错模式。相反，若值代表编译目标且产物不可变，运行时再改环境也不会改已有二进制或静态文件。统一的“变量都用 ENV”会掩盖这两个相反需求。

环境变量也不等于应用最终采用的配置。应用可能有配置文件、命令行选项或自身默认值，优先级由应用定义。容器里 printenv APP_MODE 显示 release，仅能证明进程环境存在该键；若应用仍报告 production，要追它的读取时机、覆盖规则或打包产物。最有用的运行时证据是应用报告一份脱敏的有效配置摘要，与预期配置项逐一核对，而不是将完整环境和秘密打印进日志。

用非敏感探针判定交接断点

在隔离环境里可以给 APP_MODE 使用无业务含义的标记，分别观察构建指令输出、复制的 /mode.txt、镜像声明的 ENV、容器 printenv 和应用报告的最终值。若文件是 staging 而进程环境是 release，说明构建产物与运行配置走了两条路径；若镜像有默认值而容器环境不同，先查运行时覆盖；若容器环境正确但应用行为不对，查应用优先级。每次改变一个输入并重建或重启相应阶段，才能定位哪一步消费了旧值。本文没有执行这些命令，以上输出均为按官方机制推导的验证预期。

反例是把数据库密码也放进 ARG DB_PASSWORD，再用 RUN echo 检查。Docker 文档警告，ARG 和 ENV 都不适合作为构建秘密通道，值可能进入镜像历史、来源证明或最终镜像。秘密应使用适当的构建 secret mount 或部署秘密注入机制，并按威胁模型审查产物。站内构建秘密与最终产物进一步说明了输出面。这个例子刻意只用无害的 APP_MODE，避免为排障制造凭据泄露。

最终交付单应列清每项值的所有者与消费时刻：构建参数是否在使用阶段声明、是否写入产物、最终镜像是否设默认、部署是否覆盖、应用是否实际读取，以及改值需要重建还是重启。若只有构建日志证明 staging 出现，结论最多是“某个构建步骤收到 staging”。它不能推出容器环境、网页产物或线上有效配置。把这些层次拆开，才能决定修 Dockerfile、重建产物，还是修改部署输入，并明确各步骤的验收负责人。
