allocUnsafe 分配以后，哪些字节可以发送？

区分容量、已写长度和完整负载，以短写、错误日志及共享视图生命周期检查Buffer初始化边界。

正文

核心要点

  • 分配容量不代表字节已经初始化。
  • 有效长度与消息完整性分别验证。
  • subarray共享存储，复用要遵守消费时序。

Buffer.allocUnsafe(size) 分配了容量，却不保证这些字节已初始化。只有你能证明已写入的范围，才可以作为负载读取、记录或发送。不能可靠维护这个范围时，应优先考虑零填充的 Buffer.alloc。判断安全性要覆盖短写和错误分支；某次成功路径写满缓冲区，不代表每条路径都满足条件。

容量、有效长度与内容不是一个数

Node.js 22 的 Buffer 参考说明，allocUnsafe 返回的内存可能包含旧数据，必须在读取前覆盖。这里的“可能”不能写成必然泄露某种秘密，也不能凭某次看到零字节就判断分配器会永远清零。文档提供的是初始化责任，不是可预测的旧内容。

假设服务为回复准备一千字节容量，而实际短文本只占八十字节。把整个缓冲区交给发送函数，会把剩余区域也当成回复。那部分既不是文本本身，也没有因为容量已分配而获得业务含义。正确长度需要来自实际写入结果，不能只取输入字符串字符数，因为文本编码后的字节数与字符数量不是同一个计量。

下面是未执行的说明代码，使用固定短文本，并且只暴露写入返回的字节范围。它没有连接网络，也没有读取未初始化区域。真实协议仍需按字段、编码与大小上限完成设计。

const text = 'example reply';
const storage = Buffer.allocUnsafe(64);
const written = storage.write(text, 0, storage.length, 'utf8');
const payload = storage.subarray(0, written);
// Only payload is eligible for a later, separately defined send step.

若协议要求完整文本，切到已写长度仍不足以证明内容完整：容量可能限制写入，输出只是前缀。需要在分配前计算或限制编码后的长度，并在写入后核对是否完整。初始化边界防止越界公开旧内容，完整性边界防止把截断回复当作成功，两个检查不能互相代替。

错误处理也可能把内部容量变成公开负载

反例是一段编码函数先分配大缓冲区，随后写头部、正文和校验字段。正文处理中途抛错，捕获函数为了帮助调试，把整个缓冲区转成字符串放入错误日志。即使正常发送路径只用有效长度，这条诊断路径仍绕过了边界。日志、追踪附件和错误响应都属于读取出口，不能只搜索网络发送调用。

另一个反例是复用写入计数。上一条消息写了五百字节，下一条只写八十字节，却继续使用旧计数。发送范围可能落在已分配容量之内，仍包含不属于当前消息的内容。范围合法与数据归属正确不同；每条消息的长度和缓冲区所有权应随同一次操作初始化，失败时不能沿用上一请求的计数。

如果操作分段填写缓冲区，只记录最大写入位置也不够。头部写在开头，尾部写在末尾，中间可能仍有未填区域。完整覆盖需要证明连续区间都写过，或先初始化整块再逐项覆盖。为了省掉一次初始化引入复杂覆盖账本，未必值得；没有实际测量的收益，不足以支持增加维护者无法审查的状态。

何时选择零填充，何时保留显式覆盖

Buffer.alloc 提供确定的零填充内容，适合不容易证明每个字节都被覆盖的路径。它不会把容量自动变成协议长度，也不会修复错误字段、截断文本或跨请求复用。选择它是缩小初始化责任，而不是宣布序列化已经正确。若手头已有完整字节来源，评估是否直接用符合复制或共享需求的构造方式，通常比先分配再手动追踪更清楚。

只有完整覆盖能够被控制流与测试证明，并且确有分配方面需求时，才考虑保留不初始化分配。文档也提供强制零填充启动选项，但不能把某台机器的启动参数当作所有部署的代码合同。审查库代码时，调用方环境可能不同；测试配置和生产配置不一致，更容易让一次观察产生虚假的稳定感。

验证不应通过打印“看看旧内存里有什么”完成。可以在可控测试中先填充已知标记，再模拟短写，检查公开负载只包含当前消息的预期字节；或者对编码函数的每个分支断言有效长度和完整内容。这样检验的是路径能否守住边界，而不是碰运气等待敏感内容出现。本文没有执行这些用例，也不提供泄露样本。

用 subarray 限制长度以后，还需要管所有权吗？

需要。它创建的是共享同一存储的视图，而不是独立副本。假设异步发送尚未消费字节，生产方已经把原缓冲区交给下一条消息重写，视图内容也会随之变化。是否需要复制、延迟复用或把所有权交给发送方，应依据下游接口消费时机确定；只把范围切对，没有定义生命周期。

一个更明确的夹具是固定容量十六字节，先用已知标记初始化，再分别编码短消息甲和更短消息乙。预期负载由独立的固定字节清单给出，而不是从编码器自己的长度字段生成。核对乙只含自己的内容，不包含甲的尾部或标记，并确认返回长度与协议声明一致。夹具先初始化是为了控制输入，不是在真实旧内存中搜寻秘密。

共享视图的时序另设用例：让拟议消费者暂停在读取之前，保留一份发送意图记录，然后尝试复用底层存储。若契约要求字节在消费完成前保持稳定，测试应观察到复用被阻止，或消费者获得独立副本。仅在同步回调里立即比较内容，会错过真实异步接口的生命周期要求。

这两个用例分别回答当前消息范围与存储生存期，不能互相替代。若实现改变分配大小或编码方式，预期清单应按协议重新审查，而不是自动接受实现产生的新输出。

本站的分块字符解码处理输入流中的字符边界，本篇处理输出存储中的初始化和归属边界。两者都需要长度信息，却不能共用一句“缓冲区正确”作为验收结论。本篇依据标为 v22.23.4 的文档，无代码或网络执行记录；交付时应能说明每个出口使用哪段字节、谁写过它，以及何时允许复用底层存储。
