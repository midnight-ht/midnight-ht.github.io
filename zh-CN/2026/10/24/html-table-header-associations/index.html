表头已经加粗，读到一个数字时还能知道它属于谁吗？

用季度费用表解释 scope 与显式关联的选择，检查缺失值、重排、移动卡片及真实导航。

正文

核心要点

  • 数据格需要找回对应地区、季度与指标。
  • 复杂关系可用唯一表头标识与显式引用。
  • 移动端和数据变更后必须重新检查含义。

把表头加粗，不能让一个独立读到的数字自动带上地区、季度和指标。HTML 数据表格需要让数据单元格与对应表头建立可确定的关系：简单行列可以使用表头与作用范围，复杂多层关系可能需要显式标识。先判断每个值究竟回答什么问题，再决定标记方式，比把所有第一行都换成粗体更可靠。

一个“二十”为什么可能有三种含义？

W3C WAI 的多层表头教程说明，复杂关系可以为表头设置文档内唯一的 id，并在数据格的 headers 属性中列出关联标识。不规则表头教程则展示跨行、跨列及行组、列组的标记方式。这些结构不是装饰信息，而是为离开视觉网格后仍能识别数据提供线索。

在屏幕上，读者沿着行列寻找标签；逐格导航时，如果只得到一个金额，就可能不知道它属于哪个地区、哪个季度、哪项费用。单位与统计口径也可能藏在表格外。评审要还原完整问题，例如“北区第二季度的已付金额是多少”，再检查这个值能够找回哪些上下文。

表格标题可以说明整张表展示什么，却不能替每一格建立行列关系。一份“费用汇总”即使有 caption，仍可能把预算、实付和差额混在同一个阅读序列中。反过来，简单二维表也未必需要给每格都写长串 headers；复杂度应由真实数据关系决定，避免以最繁琐标记作为质量象征。

沿一笔季度费用核对关联

设想一张地区费用表：行是北区、南区，列按第一季度和第二季度分组，每个季度又有预算与实付两列。数字均为假设，没有业务报表或辅助技术运行记录。读者希望核对北区第二季度实付，正确语义应保留北区、第二季度、实付以及表格说明中的单位。

如果结构规则、分组明确，可以研究列组表头与对应范围，地区作为行表头。若表格中途重复标题或一格关联多个不规则表头，就考虑显式关系。例如为北区、第二季度、实付设置不重复的标识，再让相应数据格引用需要的表头。写完属性不等于实际朗读顺序已通过，应在目标组合中核对。

继续任务：用户从北区第一季度预算横向移动到第二季度实付，再向下比较南区同一指标。检查横向移动能否保留季度与指标差别，纵向移动能否识别地区变化。只有从表格左上角连续朗读一次，无法证明这些跳跃比较都清楚；任务应包含真实的比较方向。

如果第二季度没有实付记录，显示破折号还需要说明它代表未产生、缺失还是零。表头关联能帮助定位这一格，却不能替数据口径解释缺失值。应在适当位置提供明确含义，并让空值与有效零区分；不要把“读得出来”误写成“业务解释一定正确”。

合并单元格为什么最容易留下假象？

视觉合并可以表达分组，但跨越几列的标题不自动证明每个子列的关联都正确。复制模板后新增一列，原来的列组跨度或 headers 引用可能没有同步，页面看起来还很整齐，读者却把实付听成预算。生成表格的代码需要把结构与数据变更一起处理，不能把可访问性属性固定在旧模板里。

显式 id 也有失败路径。一页放多张复制表格时，重复 id 会破坏关系的明确性；删除某个表头后留下引用，会让元数据与可见内容分离。这里建议把唯一性和引用存在性作为静态检查，但它们只能筛查结构错误，不能代替人理解“这一格应该关联哪个季度”。

还有布局表格的反例：用 table 排列按钮或页面卡片，再强加行列表头，不会自动变成合理的数据表。先确定资料是否确实需要二维比较；不需要时，普通结构可能更直接。若数据关系太复杂，拆成按季度排列的小表也可能比继续添加关联更易理解，但要评估跨季度比较是否因此变困难。

移动端改成卡片后，还能沿用原关联吗？

不能只看桌面模板作保证。若移动端渲染成卡片，应该明确展示地区、季度、指标和单位，不把原来的视觉表头隐藏后假设关系仍然存在。若仍保留原生表格而改变 CSS 呈现，则需要检查实际可访问结构；选择哪条实现路径，应结合目标浏览器与辅助技术结果。

例如一张卡片只显示“实付：二十”，季度标题在另一张可横滑面板上，用户就可能丢失比较对象。可以在卡片中保留必要标签，让信息单独出现时仍然成立；这不要求机械重复整张表的所有说明，而是保留足以解释该值的上下文。重排不能改变数值所属的对象。

交付前怎样证明关联对应实际数据？

动态表格尤其需要避免把位置当作身份。假设排序以后北区移到第二行，代码仍按第一行的固定编号生成 headers，表头引用可能存在且唯一，却指向另一地区。检查不能只问引用是否有效，还要把该格的数据对象与表头对象对照。筛选后的合计行也要重新确认口径，避免可见部分的数据与全量总额在同一标签下混用。

拟议检查先挑三个容易混淆的数据格，为每格写出完整业务问题与预期表头。再读取真实渲染的 th、scope、id、headers、合并跨度与 caption，核对引用和可见内容。随后用目标屏幕阅读器逐格、跨行和跨列完成比较，记录实际得到的标签，检查排序、筛选和分页后是否还一致。

这些验证尚未执行，不对任何组件库给出兼容结论。与字段问题协议要求说明收集用途类似，报表也要说明每个值回答什么问题。下一步不是给所有格子堆属性，而是选中最容易误读的那个数字，确认它在桌面、移动端和数据更新后都能找回同一套含义。
