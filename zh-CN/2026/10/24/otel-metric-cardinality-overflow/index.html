OpenTelemetry 指标溢出：总量还在，细分身份去了哪里

解释 SDK 基数限制、溢出属性和同步累计指标的测量保留；二千是规范建议，具体 SDK 支持与端到端交付需另验。

正文

核心要点

  • 溢出保留聚合贡献，不保留每个原始属性的身份。
  • 规范建议默认二千，不等于所有SDK已启用该运行上限。
  • 同步累计、Delta和异步指标不能套用同一保留推断。

OpenTelemetry 指标达到基数限制时，某些属性组合可能不再单独输出，而进入 otel.metric.overflow=true 的合成聚合。对同步指标，规范要求溢出期间每次测量恰好进入一个聚合器，不能重复计算或丢弃；这项保证并不保留每个原始属性的身份。看不到某个新租户的独立序列，不能直接解释成它没有请求。

上限约束的是哪一条指标流

OpenTelemetry Metrics SDK 规范的 Cardinality limits 一节在本次读取中属于一点六二版本，章节状态为 Stable。基数是不同属性组合的数量，限制针对指标在一次采集周期内可以收集的数据点；规范建议在属性过滤后实施限制。本文于二〇二六年十月二十四日核对在线原文，没有运行任何语言 SDK。

配置优先级包括匹配 View 的流级限制、Reader 的相应默认值，以及没有前述配置时建议采用的二千。原文使用 SHOULD，不宜写成所有 SDK 都已启用二千，也不能把章节稳定当作本项目运行库已经支持。具体语言、版本、Reader 和导出器仍需核对。页面其他章节可能有不同成熟度，本文没有把整个 SDK 页面统一称为稳定实现。

限制还不能简单解释成“整个监控系统只会有这么多序列”。一个进程可以有多个指标、多个 Reader，多个实例又各自采集；导出格式也可能将一个指标点展开成不同后端序列。SDK 聚合的控制范围与后端总规模需要分别预算。降低其中一个数值，不能证明采集器、网络和存储的全部成本都获得同一上限。

用同步累计 Counter 看清保留了什么

设想一个隔离实验：只建立一个同步 Counter，使用累计时间性、一个 Reader，没有属性过滤或转换。假定该实现支持并正确采用基数上限四，先为租户甲记录五次、乙记录七次，采集一次。随后为十个不同的新租户各记录一次，再采集。初始两种属性组合没有超过上限，规范要求此时不发生溢出；后续十二种组合则需要限制处理。

这些数字是未执行的输入设计，不是 SDK 输出。累计同步指标在溢出前已观察到的属性组合要继续导出，因此甲和乙的独立累计记录应继续保留。不能独立聚合的新组合会被合成到仅含溢出属性的数据点。具体保留了哪些后来的普通组合，不应在没有实现证据时预写成某种固定选择顺序。

在所设条件下，全部记录合计为二十二。验证重点是普通聚合与溢出聚合的总贡献能否对应二十二，并且甲、乙的身份仍可观察；不是要求每个新租户都有一条线。这里讨论的是 SDK 聚合保证，不是经过网络、Collector 或后端之后的端到端无损承诺。任何额外过滤或导出失败，都要在证据链中单独检查。

小上限用于让隔离实验更容易出现溢出，不能据此预写具体普通组合的数量或身份。验收时同时核对限制配置、未超限时无溢出的保证以及实际输出，避免只看到一个特殊属性就推断其余组合已经按某种固定顺序保留。

总量看起来正常，细分仍可能失真

溢出桶可以保留聚合贡献，却不再带着每个租户、路由或错误分类的完整身份。若告警只筛选某个新租户，它可能观察不到进入溢出的请求；若整体计数包含溢出，又可能看起来一切正常。两者不矛盾，因为一个问题问总量，另一个问归属。仪表盘应该让溢出可见，而不是静默过滤掉这个特殊属性。

反例是为了找回租户明细，直接把限制提高几个数量级。这样可能暂时保留更多组合，也会增加聚合与后端资源压力，而且没有修正无界身份进入指标的设计。若业务只需要按套餐类别采取行动，优先考虑过滤租户标识、保留有限类别；具体事件关联可放在有权限和保留规则的日志或链路中。选择要从排查动作出发，而非单纯追求每条数据都有标签。

属性过滤也有代价。把租户移除后，两位租户的请求可能进入同一属性组合；这是一项有意的聚合选择，不是数据凭空恢复。应核对剩余标签仍能回答哪些问题，以及哪个系统保留单次事件证据。指标的上限、隐私和排查粒度，需要同一份设计说明承接。

能从 overflow 数字还原具体租户吗？

不能仅靠这个合成值恢复已经合并的原始身份。即使知道有十个新租户，也不能从总贡献反推出每个租户的请求分配；不同分布可能产生相同总量。恢复明细需要独立事件证据，而不是对溢出值做一种新的查询。不要在告警里把它随意命名成“其他租户零请求”。

时间性和 Instrument 类型也影响解释。同步累计的旧组合保留保证，不能原样外推到同步 Delta；规范允许 Delta 选择任意属性子集以满足限制。异步指标另有建议优先保留回调中先观察属性的规则。若正在分析 Observable 的当前值，不应直接套用这里二十二次事件贡献的 Counter 例子。

待执行检查应保存 SDK 精确版本、View、Reader、时间性、输入属性和 SDK 原始导出，再检查 Collector 与后端是否继续保留溢出点。对照过滤前后输入，确认限制真的作用于预期指标流；再测试没有超限的边界，避免把普通缺失误认为溢出。完整采集后才可报告当前实现怎样处理，本文不提前给出运行结论。

关于维度为何会无界增长，可接着阅读指标标签预算；关于累计与增量，见时间性边界。先为一个真实指标确定需要保留的行动维度，再让溢出成为可观察的失去明细信号，别用总量还在代替明细仍可信。
