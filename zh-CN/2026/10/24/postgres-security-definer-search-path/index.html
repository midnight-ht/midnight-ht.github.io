SECURITY DEFINER 的 search_path 为什么要固定？

以可信schema、临时表顺序与事务化执行授权，审查高权限函数的名称解析和调用边界。

正文

核心要点

  • 高权限执行仍需可信名称解析。
  • 可信schema必须排除低权限创建，pg_temp明确放末尾。
  • 创建函数与收紧执行权限要一起审查。

SECURITY DEFINER 函数以所有者权限执行，但未限定对象名仍需要解析。PostgreSQL 18 官方安全编写建议指出，这类函数的 search_path 排除不可信用户可写的 schema，并把 pg_temp 明确放在末尾。否则调用者可能影响高权限代码实际找到哪个对象。固定路径只是名称解析防线，函数执行授权和业务身份校验仍要分别设计。

权限提高了，表名却可能仍由调用环境决定

CREATE FUNCTION 的安全编写章节把风险说得很具体：不可信用户创建的表、函数或运算符，可能遮蔽作者原本想使用的对象。给函数加上定义者权限，不会自动把其中每个名字绑定到作者预期的 schema。调用者没有直接读取受保护表的权限，也不代表他无法影响函数做出的判断。

假设管理员维护一张允许操作名单，函数接收成员编号并返回是否允许。目标是读取可信 schema 里的名单。如果函数内部只写未限定表名，而调用者可以创建同名临时表，名称解析可能偏离作者预期。这里是依据官方机制设计的威胁模型，没有向任何在线数据库注入对象，也不声称本站存在该漏洞。

审查时不要只看函数定义所在的 schema。函数存放的位置与函数体里未限定名称如何查找，是两件事。把函数命名为 admin.allowed，并不能单独证明内部查询的 allowed_members 来自 admin。应检查函数附带的配置、每个对象引用，以及这些 schema 实际允许哪些角色创建对象。

为什么只写可信 schema 仍不够

临时表 schema 是这个问题里容易漏掉的条件。官方示例说明，只把 admin 写进路径而不列 pg_temp，仍可能被同名临时表影响。把 pg_temp 明确列在最后，才让可信对象优先于临时对象。这里并不是建议关闭所有临时表，而是明确它在高权限函数解析中的顺序。

下面是未执行的结构示例。它假定私有练习库已经存在受控角色、schema 和名单表；不是可以直接部署的完整授权系统。名单表、拥有者与调用者的创建和权限配置，都应由单独迁移审查。

BEGIN;
CREATE FUNCTION admin.member_allowed(member_id bigint)
RETURNS boolean
LANGUAGE sql
SECURITY DEFINER
SET search_path = admin, pg_temp
AS $$
  SELECT EXISTS (
    SELECT 1 FROM admin.allowed_members AS m WHERE m.id = $1
  );
$$;
REVOKE ALL ON FUNCTION admin.member_allowed(bigint) FROM PUBLIC;
GRANT EXECUTE ON FUNCTION admin.member_allowed(bigint) TO app_reader;
COMMIT;

示例既限定了表名，也声明了路径，使审查者能看见两种意图。但 admin 必须确实是可信且不可由低权限调用者写入的 schema。若应用角色仍有创建对象能力，把它写在路径首位只是在配置中重复了不安全假设。权限验收应以实际角色检查，而不是按 schema 名字里的“管理员”含义推断。

发布函数时，还有一个默认开放窗口

官方文档提醒，新建函数默认向 PUBLIC 授予执行权限。如果目标只允许特定角色调用，应撤销默认权限后明确授予。把函数创建、撤销和授权放进同一事务，是为了避免对象先公开出现，随后才收紧的中间窗口。只在迁移脚本末尾看见一行撤销，不能证明前面的提交点没有暴露它。

这也影响失败路径。假设函数创建成功后，下一条权限语句拼错，脚本又没有事务包裹。发布工具报告失败，并不说明前面创建的函数消失。维护者需要核对实际数据库状态，而非根据进程退出码推断“什么都没改变”。事务化迁移应同时测试授权语句失败时对象是否留下，以及普通角色是否始终无法越权调用。

函数所有者也应按所需能力选择。若只需读取一张受保护表，就不应默认给函数超级用户拥有者。减少所有者权限不能替代可信路径，却能限制设计错误的影响范围。本站关于RLS 运行角色讨论同样需要核实的身份问题，但这里关注的是被调用函数的有效权限与对象解析，不能拿普通连接角色测试代替函数调用测试。

表名已经完全限定，还要继续检查哪些地方？

还要检查函数调用、运算符解析、动态 SQL 和参数授权。限定一个表名只解决那一个引用，不应据此宣布整个函数安全。动态 SQL 若把输入当标识符或表达式拼接，固定路径也不会自动将其变为受信任输入。是否允许调用者查询任意成员，还是只能查询自身成员身份，同样属于业务授权，不是 search_path 能回答的问题。

拟议验证应建立一个低权限调用角色，在只读业务预期下调用函数，再构造同名临时对象作为负例。对照函数应始终读取可信表；未授权角色应无法调用；授权角色也不能通过另一个成员编号获得越权结果。测试记录要保留函数定义、所有者、schema 创建权限、执行授权和实际返回值，避免只保存管理员成功查询的一张截图。

练习前应写一份实际权限表：函数所有者能读取名单，调用角色能使用函数所在schema并执行指定签名，调用角色不能在可信schema创建对象，也不能直接读取受保护名单。先证明被允许的函数调用成功，再验证无权限调用失败。否则一个缺少schema使用权限的角色可能什么都调用不了，看起来拦住攻击，却没有测试到预期函数边界。

还应准备可信名单允许成员甲、不允许成员乙的固定输入，然后给调用者的临时同名表放入相反数据。安全配置下返回值应继续来自可信名单，而不是只检查函数没有报错。测试应恢复相同初始状态，避免第一次调用或临时对象残留改变下一次输入；审查完整函数定义和实际授权，与记录的测试角色对应。

这些检查并不要求应用向普通用户暴露完整名单。函数只返回受限结果时，测试证据也应遵守相同信息边界。管理员为了准备预期值看到的内容，不能自动成为应用角色应该得到的内容。

本篇核对 PostgreSQL 18 官方文档，没有建库、授权或执行攻击验证。实际交付应证明三个选择都符合需求：谁的权限在执行，解析到了哪些可信对象，以及调用者被允许请求什么结果。只配置其中一项，就不宜把高权限入口视为验收完成。
