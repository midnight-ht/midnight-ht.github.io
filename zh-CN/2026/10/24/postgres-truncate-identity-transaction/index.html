TRUNCATE 清空后，编号和回滚会怎样变化？

区分清空数据、重启序列与会话最近值，核对事务回滚、锁、外键范围及旧快照边界。

正文

核心要点

  • 默认清空保留序列进度。
  • RESTART的事务恢复与currval会话观察分别检查。
  • 整表范围、阻塞与旧快照需要独立验收。

TRUNCATE 清空表时默认保留序列进度，只有明确选择 RESTART IDENTITY 才重启被清空表的列所拥有的序列。在 PostgreSQL 18 中，表数据清空及这次隐含重启都能随外围事务回滚；但同一会话的 currval() 可能仍显示失败事务里取得的值。判断恢复是否正确，要分别检查数据、序列和会话观察，不能只看下一条编号。

清空数据与重新发号是两个决定

PostgreSQL 18 的 TRUNCATE 参考把默认行为写为 CONTINUE IDENTITY。这里的重启范围是被清空表中列所拥有的序列，不是数据库里全部名称看起来相关的序列。维护脚本若只写一句清空，再凭习惯认为下一条记录从一开始，就已经把未选择的行为当成了合同。

假设一个可丢弃练习库有批次表，身份列使用默认起点，已有两行，编号分别为一和二。普通清空后再插入一行，预期编号沿原进度继续；重建相同初始状态，改用重启身份选项，才应检验重新开始的效果。这里的编号只是便于推演的假设，不代表业务主键必须连续。序列是否有缓存、是否被其他入口调用，都要在真实环境单独确认。

下面是未执行的说明性 SQL，仅供独立练习库复现。先在一个事务中清空并插入，再回滚，让数据恢复与编号观察同时暴露出来。它没有在本站数据库运行，也不是生产清理建议。

CREATE TABLE scratch_batches (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  label text NOT NULL
);
INSERT INTO scratch_batches(label) VALUES ('A'), ('B');
BEGIN;
TRUNCATE scratch_batches RESTART IDENTITY;
INSERT INTO scratch_batches(label) VALUES ('C') RETURNING id;
SELECT currval(pg_get_serial_sequence('scratch_batches', 'id'));
ROLLBACK;
SELECT id, label FROM scratch_batches ORDER BY id;

按文档，回滚应撤销清空及隐含序列重启，原来的两行应恢复。事务内插入返回的编号只能证明当时分配了一个值，不能证明那行仍存在。回滚后若直接在原会话读取最近序列值，它还可能反映失败事务中的分配；这项会话记忆不应被误读成序列恢复失败，也不能用来识别已提交记录。

为什么普通序列空洞规则不能直接套过来

本站关于序列编号与事务回滚讨论普通取号不会因为事务失败就回收。这里增加的是另一个操作的特定合同：重启身份引出的序列重启本身按事务执行。两者并不矛盾，差异在于究竟观察普通取号，还是观察清空命令所做的重启。

验证时应先保存初始表内容及序列配置，在失败事务内记录插入返回值，然后在回滚后检查原行。若要再插入核对后续发号，必须在隔离练习中明确那次插入会再次消耗编号；不要在共享库里反复调用取号函数，最后拿被诊断动作改变过的进度作为原始故障证据。独立会话的首次最近值查询还可能没有定义，因此也不能把它当成通用观测入口。

另一个反例是清空后立即向外部系统宣布“编号一可复用”，随后事务回滚。数据库能够恢复本地状态，外部已收到的消息却不因此消失。即使练习库可以重新开始编号，外部链接、审计记录与缓存也可能把旧编号当成稳定身份。是否重用身份必须按系统边界决定，不能由表空了推导。

选择命令以前，先确认阻塞与关联范围

该命令会对涉及的表取得排他级别很高的锁，文档明确说明它阻止表上的其他并发操作；重启的序列也会独占锁定。需要持续并发访问时，官方建议考虑 DELETE。这不是在两条语句之间只比较写法长短：如果业务只删除部分过期行，需要行级条件，整表清空本身就不满足要求。

外键也会改变操作范围。默认 RESTRICT 会拒绝遗漏引用表的清空；CASCADE 则可把关联表加入。为了消除报错而追加级联选项，会把一个范围问题变成更多数据被清空的问题。较清楚的维护方案应列出准确表清单，核对引用关系和预计行数，再确定是否允许整组清空，而非把级联当成修复按钮。

触发器需要另查。官方参考区分清空触发器与删除触发器；依赖逐行删除审计的系统不能假设清空会走相同路径。预检应列出真正依赖的副作用，再在可恢复环境验证它们。事务可回滚也不能自动证明命令满足原业务流程，尤其当某些触发逻辑会碰到库外服务时。

有事务保护，就能让旧快照继续看到清空前数据吗？

不能从可回滚推导出这种保证。文档明确说明清空不是 MVCC 安全的，使用清空前快照的并发事务可能看到空表。数据恢复合同与并发快照合同分别成立。若应用需要跨维护过程保留一致读取，应先设计维护窗口或选择符合读取要求的操作，再用两个受控会话核对，而不是把一次回滚成功当作并发验收。

还可以把练习拆成四份独立初始状态：保留身份后提交、重启身份后提交、保留身份后回滚、重启身份后回滚。每份都从相同的两行和相同序列配置开始，避免上一轮插入影响下一轮。提交组检查旧行确实消失且新行存在，回滚组检查旧行恢复且新行不存在；之后才按所选身份行为核对发号。这样每个断言都有明确来源，不会把表恢复与序列恢复混成一个数字比较。

维护过程还要定义等待上限。假设另一个会话持有访问所需的锁，清空任务可能先停在锁等待，而不是已经完成一半。应按维护要求设置可接受的等待和执行期限，并记录失败后事务是否仍待结束。未取得预期终态时，不应继续发布重置完成通知。超时究竟中止哪条语句、应用如何结束事务，要按实际会话配置验证。

普通取号与会话最近值的区别，可直接对照十八版本序列函数说明。这里引用它是解释观察来源，不是建议通过修改序列来修正一次看起来不连续的输出。

本篇只依据十八版本文档推演，没有执行 SQL、锁等待或并发快照实验。实际验收至少要解释初始行、清空范围、身份选项、事务终态和观察会话五项。选择整表重置之前，先证明业务确实允许这些状态一起变化。
