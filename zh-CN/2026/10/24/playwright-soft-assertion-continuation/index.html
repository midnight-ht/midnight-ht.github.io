Playwright 软断言：继续收集错误前，先划清执行边界

软断言会继续执行并保留失败；用订单预览例子区分独立观察、写入门槛、等待预算与清理责任。

正文

核心要点

  • 软断言失败会让测试失败，但后续语句仍可能产生副作用。
  • 先用硬断言确认共同前提，独立观察后在写入前检查错误。
  • 清理依赖确切夹具身份，普通动作异常不受 soft 保护。

expect.soft 失败后，Playwright Test 会记录错误并继续执行后续语句，测试仍被标记为失败。它适合一次收集多项独立观察；当后续操作依赖已经失败的前提，尤其会产生写入、付款或删除时，应先用硬断言阻止继续。选择软断言，等于选择哪些证据值得继续收集，也是在决定失败后还允许发生什么。

继续的是代码，不是前提的可信度

Playwright 的 Assertions 指南区分了默认断言与软断言，并说明软断言只适用于 Playwright Test runner。这里讨论的是该测试运行器的错误收集语义，不是给任意 JavaScript 异常增加恢复机制。本文核对了二〇二六年十月二十四日的在线指南，以下用例没有执行，也没有通过率或耗时测量。

假设订单确认页需要显示收货人、地址和配送时间。三个字段都从已经载入的同一份订单数据展示，检查一个字段不改变另一个字段。收货人显示错误时，继续读取地址和配送时间仍有诊断价值，能帮助判断是单个组件问题还是整份数据错误。此时把三项观察写成软断言，可以减少一次运行只留下第一个字段错误的局限。

但如果下一步是点击付款，含义就变了。收货人或地址不正确时，付款操作已经失去安全前提。页面按钮可能仍然可点击，测试脚本也可能顺利走完，二者都不说明继续付款是合理的。测试最终呈红色，无法撤销运行途中已经提交的请求。执行许可必须在副作用发生之前表达，不能期待最终报告替流程把关。

在独立观察后设置一道明确检查点

下面是未执行的 TypeScript 示意，假定订单由隔离夹具建立，金额不涉及真实支付，页面定位器及文字仅用于说明。普通网页断言与软网页断言都应正确等待；省略等待会让代码顺序偏离测试作者原本的判断。

import { test, expect } from '@playwright/test';

test('review before sandbox payment', async ({ page }) => {
  await page.goto('/orders/example-42/review');
  await expect(page.getByTestId('order-id')).toHaveText('example-42');
  const fields = [
    ['recipient', '示例收件人'],
    ['address', '测试地址'],
    ['delivery', '次日达'],
  ] as const;
  for (const [id, expected] of fields) {
    await expect.soft(page.getByTestId(id)).toHaveText(expected);
  }
  expect(test.info().errors).toHaveLength(0);
  await page.getByRole('button', { name: '沙箱付款' }).click();
  await expect(page.getByText('已受理', { exact: true })).toBeVisible();
});

订单身份先用硬断言确认，因为后面三个字段都以“正在检查这笔订单”为前提。如果实际打开另一笔订单，继续收集它的地址错误容易形成误导。随后三个软断言保留各自诊断，检查点再要求当前错误集合为空，才允许发送付款。最后的受理状态也只证明页面展示受理，是否需要持久结果应另按支付沙箱契约验收。

指南展示了通过 test.info().errors 检查软断言失败的做法。这是当前测试已经记录的错误集合，不是自动按某一组字段隔离的局部计数。如果此前已有其他软失败，零长度检查同样会阻止后续执行。团队需要决定这是否正是期望：前面任何检查失败就禁止提交，还是应把独立目标拆成不同测试，避免一份脚本承担几种互不相干的许可逻辑。

不建议为了让后半段继续跑，随手保存当前错误数，随后只判断“没有新增错误”。这种写法可能把前面的失败前提排除在门槛之外。只有能解释旧错误为何与当前写入无关，且测试隔离、数据归属都明确时，才值得设计更局部的判定；否则拆分用例更容易审核。错误数量是诊断工具，业务前提仍要由测试设计者选择。

一个等待失败，可能消耗多少后续观察时间

软断言并不代表立即记录一次不匹配后跳过。对于会自动重试的网页匹配器，它仍会按配置的等待预算观察条件，失败后再继续。若多个字段都不存在，顺序检查可能依次消耗预算。把整页所有元素都改为软断言，会收集很多同源错误，也可能把真正原因埋进长报告。

因此应先辨认共同前提，再判断独立性。页面根本没载入、订单身份错误、登录已失效，这类前提失败后，几十个字段检查通常没有相应的信息增量。保留少量硬前提，让软断言集中在已经成立的业务上下文里。具体超时要结合环境核对，不能凭本文示意承诺总运行时间，也不能通过无限放宽等待掩盖错误入口。

清理也要被失败检查点拦住吗？

通常不应把必须释放的测试资源放在付款许可之后才处理。测试夹具或清理钩子应承担隔离数据回收，且清理权限和对象需要独立限定。硬断言让测试主体停止后，资源依然可能存在；若靠脚本最后一行删除测试订单，前面的失败就可能令那一行到不了。这是清理责任的设计问题，不能通过取消业务门槛解决。

反过来，清理不能盲目复用页面上当前显示的任意订单号。前面的身份检查正可能已经失败，应使用创建夹具时保留的确切对象身份，并在授权范围内回收。对真实付款、真实删除等不可轻易撤回的路径，应采用明确的测试环境与数据隔离，不能因为最终测试注定失败，就允许它继续制造副作用。

待执行验收至少需要两个输入：一个字段故意不符时，确认其他独立观察仍留下记录，而付款请求没有发送；全部字段正确时，确认门槛之后才发出预期请求。再让页面加载失败，检查硬前提能否阻止无意义的字段错误扩散。应同时保存报告中的错误与副作用接口的调用记录，不能只看末尾有没有绿色提示。

也要区分软断言与普通动作异常。后续点击如果失败，仍可能中止当前执行，不能因为前面用了 soft 就认为整段脚本进入了容错模式。独立检查的集合应尽量只读；需要修改页面才能继续观察时，先说明这种修改会不会改变后面要检查的对象，否则多收集到的错误也可能来自测试自己的状态变化。

现有的异步断言等待分析回答何时读取结果；这里多加了一层决定：读到失败后，还允许脚本做什么。先在测试代码中标出第一次写入，再往前寻找它必须依赖的检查点，这比按“重要字段硬、次要字段软”机械分类更可靠。
