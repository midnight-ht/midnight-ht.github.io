Object.assign 与对象展开，谁会调用目标 setter？

分别核对源getter、目标setter和对象身份，解释浅拷贝、属性描述符及中途抛错后的副作用。

正文

核心要点

  • assign的目标Set可触发setter。
  • 展开创建数据属性，但仍会读取源getter。
  • 部分写入与源读取副作用不会因后续抛错自动撤销。

Object.assign(target, source) 向现有目标写值，可能触发目标上的 setter；对象展开把源值放进新对象时，创建的是数据属性，不沿用这种目标赋值路径。两者都会读取源属性，因此源 getter 仍可能执行。把 assign 改成展开之前，应分别确认需要保留哪种读取、写入和对象身份，而不能只按语法长短替换。

同一个字段名，发生的是不同操作

ECMAScript 的 Object.assign 算法读取源对象可枚举的自身属性，并对目标执行 Set。与之相对，CopyDataProperties 算法读取相应源值后创建数据属性。这个差别决定目标访问器是否参与，而不是两种写法碰巧在某个引擎上返回不同结果。

假设一份受控配置对象通过 setter 校验音量，并把合法变更写入内部状态。调用 assign 可以进入这条写入路径；把同名字段展开到新普通对象，只会得到一个值，不会替原目标调用校验。若代码评审把两者称为完全相同的“合并”，就会掩盖被删除的副作用。

以下是假设性的未执行代码。它用数组记录调用意图，没有请求外部服务，也不代表任意配置系统都应依靠 setter 做验证。

const calls = [];
const target = {
  set volume(value) { calls.push(value); }
};
const source = { volume: 7 };
Object.assign(target, source);
const copy = { ...source };
// Proposed checks: calls contains one 7; copy has an own data property.

拟议断言不应只比较读取到的值。示例目标只有 setter，没有对应 getter，读取 target.volume 与读取 copy.volume 本来就不是同一个观察。应检查 setter 调用次数、传入值和新对象属性描述符，才能证明目标写入协议是否执行。若真实 setter 更新内部状态，还要核对那份状态，而不是要求两个对象读起来完全一样。

展开不会让源读取自动变成无副作用

换到源对象一侧，情况又不同。假设 source.volume 是 getter，每次读取都会计算当前值或记录访问。assign 和展开都需要取出这个可枚举自身属性的值，因此都可能触发 getter。展开后的新对象通常保存那次读取的结果，不是把 getter 本身搬过去。之后源状态变化，副本中的这个原始值也不会自动重新计算。

这给快照设计带来两个选择。如果目标是获取当下的普通数据，应先明确允许哪些 getter 运行、抛错如何处理，再生成数据形状受控的对象。如果目标是保留访问器行为，值复制不是相应工具。把 getter 的返回值叫作“保留原对象属性”，容易让后来维护者误以为描述符也被复制了。

对象身份也不同。assign 返回并修改传入目标，其他持有该目标的人可以观察修改；展开创建另一对象，旧引用仍指向旧对象。把更新逻辑改成新对象后，若调用者没有接住返回值，可能根本没有更新正在使用的配置。是否需要新身份、是否依靠引用变化触发订阅，应由真实组件契约决定，不从“不可变更好”推导统一选择。

中途抛错，不会把先前副作用收回

设想源依次提供三个字段，目标前两个 setter 已经执行，第三个 setter 因输入不合要求抛错。assign 没有事务回滚功能，先前写入可能已经留下。调用者捕获异常后告诉用户“配置未改变”，就需要额外依据；语句没有正常返回，并不证明目标保持初始状态。

展开表达式若在读取某个源 getter 时抛错，虽然完整的新结果没有交给调用者，先前 getter 的外部副作用也不会自动撤回。因而“先展开到临时对象，再整体替换”可以改变目标发布时机，却不能保证读取过程完全无副作用。受控纯数据、显式校验和清楚的发布步骤，通常比依赖隐式访问器更便于审查；这是设计取舍，不是语言强制规则。

两种方式也都是浅层处理。嵌套对象仍可能被源与结果共同引用，不能因为使用新外壳就宣布整份配置独立。本站关于浅冻结与嵌套变化讨论引用目标是否固定，本篇讨论复制发生时执行哪些操作；二者解决不同阶段的问题。

如果确实要保留 getter 本身，该怎样选择？

应评估属性描述符相关 API，而非把值复制误称为访问器复制。先明确哪些属性可复制、目标原型是什么、不可配置属性如何处理，再选择相应创建或定义操作。保留 getter 还意味着保留它访问的外部状态或闭包关系，并不自动得到独立快照。若 getter 原本依赖私有实例状态，迁到另一对象后是否能工作，也需要单独验证。

针对本篇的最小验收，可以分别放入源 getter、目标 setter、嵌套对象和会抛错的后续字段。检查读取次数、写入次数、属性描述符、原目标是否改变，以及失败前是否已留下修改。对象代理、自定义原型和特殊对象会引入额外路径，本篇的普通对象示例不替它们提供兼容结论。

失败用例可以单独准备一个初始目标：字段甲和乙允许写入，字段丙的setter拒绝输入。按固定顺序提供三项，捕获异常后逐项核对甲乙已经改变、丙没有接受新值，并记录各setter调用次数。每次测试重建目标，不能在上次失败留下的半成品上重复测试，再把结果当作相同初始状态。若业务要求全部成功才发布，必须把校验与公开修改安排成可兑现该要求的步骤。

源读取失败也应独立准备：让第二个getter抛错，检查第一个getter留下的计数是否仍然存在，以及调用方是否拿到了完整新对象。这个对照说明，替换目标发布方式不等于撤销源读取副作用。对于带外部操作的getter，测试应使用明确的受控替身记录意图，不在教程里伪造真实发送或保存成功。

即便采用描述符复制，也不能把它当成输入验证。描述符说明属性怎样工作，不说明值是否满足业务要求；保留访问器与接受访问器所返回的内容，仍是两个待决定的行为。

本文依据二〇二六年十月二十四日读取的 ECMAScript 在线规范，没有执行 JavaScript。一个可审查的替换提交，应明确说出原目标的 setter 是否仍应运行、源 getter 是否允许运行，以及调用者最终持有哪一个对象；只写“统一成展开语法”不足以解释行为变化。
