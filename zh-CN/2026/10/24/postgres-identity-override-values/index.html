导入 identity 列，OVERRIDING 应该保留谁的值？

先决定迁移保留身份还是复制生成新身份，再验收序列后续发号、父子映射与重复批次。

正文

核心要点

  • SYSTEM保留显式身份，USER改用目标生成值。
  • 导入行与后续序列分配分别验收。
  • 父子映射和重试要依赖稳定源身份。

导入 PostgreSQL 的 identity 列时，先决定旧身份是否仍代表同一个对象。OVERRIDING SYSTEM VALUE 允许输入身份值覆盖序列生成值；OVERRIDING USER VALUE 则忽略提供的身份值，让目标表重新生成。前者适合明确保留身份的迁移，后者适合创建新对象的复制。两种选项都不替你修复外键映射，也不证明后续自动发号与导入数据不会冲突。

ALWAYS 限制的是通常写入，不是永远不能迁入

PostgreSQL 18 的 INSERT 文档区分 GENERATED ALWAYS 与 GENERATED BY DEFAULT。对于前者，直接插入非默认的显式身份值会报错，除非选择相应覆盖选项；对于后者，接受显式值本来就是常规行为。覆盖的两个名字容易看反，记忆时应看被覆盖的是系统生成值，还是调用方给出的值。

设想练习库的旧目录有商品甲，旧编号为四十二。数据迁移希望历史链接继续指向同一商品，保留四十二可能符合需求。另一项“复制成新模板”的任务即使复制相同名称，也应产生新对象；把旧主键原样带入，可能撞上已有记录，或者让维护者误以为两份模板拥有同一身份。这两种任务看起来都是复制数据，却需要相反的身份选择。

以下为未执行的说明 SQL，表名仅用于可丢弃练习库。两次插入分别表达保留与重生，实际新编号应以返回值为准，不在文中预设它必须等于哪个数字。

CREATE TABLE scratch_catalog (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name text NOT NULL
);
INSERT INTO scratch_catalog(id, name)
  OVERRIDING SYSTEM VALUE VALUES (42, 'example') RETURNING id;
INSERT INTO scratch_catalog(id, name)
  OVERRIDING USER VALUE VALUES (42, 'copy') RETURNING id;

第一条让显式四十二进入身份列，第二条忽略输入的四十二而采用默认生成值。若把第一条的覆盖子句删去，它就是检验 ALWAYS 限制的负例。若把第二条用于必须保留身份的迁移，语句可能成功，业务关系却已经改变。数据库接受输入与迁移满足身份合同，必须分开验收。

导入行成功，为什么下一次普通创建仍可能失败

显式填入身份值，不应被视为已经把关联序列推进到所有导入编号之后。导入既有编号与自动分配后续编号是两项状态。假设导入占用了某个未来自动生成值，随后普通创建再取得这个值，主键约束才会暴露碰撞；仅查看导入批次全成功，会漏掉后续入口。

维护方案应在隔离副本检查目标序列、当前表最大身份、并发写入是否被暂停，以及后续普通插入的结果。若需要调整序列，先识别真正关联的序列和它的配置，再制定独立维护步骤，不能机械复制“设到最大值”的单行脚本。起点、增量、方向与已分配但未提交的值，都可能让简单猜测失效。本篇没有执行序列调整，不把这段说明当成完整迁移工具。

身份列也不能代替显式唯一性要求。示例把主键约束写出来，是为了说明冲突由什么规则拒绝。若真实表只有生成属性，没有所需唯一约束，导入可能产生重复身份而不按维护者预想报错。检查建表定义时，应分别确认生成方式、非空要求和唯一性，不要只搜索 identity 这个词。

子表引用必须跟着身份方案变化

假设旧商品四十二有两条价格记录。保留商品身份时，价格记录仍须核对它们引用的是迁入后的同一商品。重新生成商品身份时，旧四十二与新返回值之间需要可靠映射，子表写入必须使用映射结果。把父表用 USER 选项重生，再把子表外键原样复制，会得到拒绝，或更危险地关联到目标库原有的另一商品。

一个可审查方案可以先为每个导入对象保留稳定的源标识，写入父表时记录源标识到目标主键的对应，再按该映射处理子表。是否允许批次重试、源标识在什么范围唯一、映射何时提交，需要按业务约束决定。不能依赖返回行的偶然位置，把两份批量结果按数组下标拼在一起；一旦过滤、冲突或排序发生变化，位置关系就可能不再成立。

如果是只复制非身份字段，明确列清单通常比 SELECT * 更利于审查。表结构改变后，全列复制可能增加新的身份或敏感字段，也可能改变列对应关系。覆盖子句只处理目标身份列，不会自动替新增字段做权限与业务语义选择。本站的缺省、DEFAULT 与显式空值讨论相邻的输入区别，本篇关注身份归属与关联映射。

批次重跑时，重新生成编号就不会重复对象吗？

不会。重生主键只是得到另一身份，重复的业务对象反而可能更难发现。假设同一源商品因为超时被再次导入，两次 USER 插入都生成新主键，主键约束不会告诉你它们来自同一个源对象。需要以合适的源身份或业务键定义重复判断，保留批次结果，再决定重试是补缺、跳过还是明确更新。覆盖选项没有提供幂等合同。

映射验收可以准备两个来自不同源目录、但局部编号同为四十二的对象。如果源身份范围包含目录，就必须把目录与局部编号一起作为映射键，不能让后一项覆盖前一项。再让其中一个源对象出现重复输入，检查系统是否按既定规则拒绝、复用已有映射或明确更新。选哪一种可以由产品决定，不能在写入子表时才靠碰撞猜测。

对缺失映射的价格记录，应在写入之前保留可定位的失败，指出源目录、父对象和子记录。若业务要求整批原子性，就应验证该失败能阻止批次提交；若允许部分成功，就应列出已提交部分与待处理部分。把外键拒绝统一转换成成功行数减少，会丢失修复所需信息，也让重跑难以选择准确范围。

身份列章节明确区分生成属性与唯一约束；序列函数章节说明发号状态与修改方式。将两份来源和实际建表定义一起审查，才能判断导入是否需要另行处理后续分配。

拟议验收应覆盖三条入口：导入保留身份、复制重生身份、导入后普通创建；另加父子关系与批次重跑负例。核对返回身份、实际行、引用归属和后续写入，而不是仅记录受影响行数。本文依据十八版本文档，没有建表、导入或执行 SQL；最终选择必须回答旧身份是否还指向同一个业务对象。
