Promise.any 等到的是成功请求，还是业务有效结果？

把候选校验放在兑现之前，按输入身份解释AggregateError，并处理空输入、永久等待和晚到结果。

正文

核心要点

  • any选择最先兑现，不校验业务有效性。
  • 全部正常候选拒绝时，原因按输入顺序关联。
  • 截止时间、取消和晚到结果需要独立生命周期规则。

Promise.any 选择最先兑现的候选，不选择最先结束的候选，也不理解业务意义上的“有效结果”。普通输入都拒绝时，它以包含拒绝原因的 AggregateError 拒绝。若候选可能兑现为不可用数据，应把校验放进每个候选承诺内部，让无效数据变成该候选的拒绝，再交给 any；否则最快返回的错误内容也可能成为胜者。

一个拒绝不会让另一个候选失去机会

ECMAScript 的 Promise.any 规范区分首个兑现与全部拒绝。假设从三个只读镜像获取同一份目录：甲先拒绝，乙仍在读取，丙稍后兑现。只要丙是首个兑现的候选，它就可以成为结果；甲更早结束，不会单独让 any 立即失败。这和选择首个结算结果的 race 是不同需求。

但“承诺兑现”不等于“目录合格”。假设读取客户端把一份过期目录也作为正常返回值，any 不会检查版本、字段或签名。它忠实选择那个值，应用却可能误把最早的数据当成最新的可用目录。选择函数之前，应先定义每个候选到底承诺交出原始响应，还是通过校验的业务对象。

以下是未执行的结构示例。readCatalog 和 validateCatalog 是需要由项目实现的业务函数，没有暗示具体 HTTP 客户端会把哪些状态当作拒绝。验证器必须在不合格时抛错，合格时才允许候选兑现。

const mirrors = ['mirror-a', 'mirror-b', 'mirror-c'];
const candidates = mirrors.map(async (mirror) => {
  const raw = await readCatalog(mirror);
  validateCatalog(raw);
  return { mirror, catalog: raw };
});
try {
  const selected = await Promise.any(candidates);
  consumeCatalog(selected);
} catch (error) {
  handleCatalogFailure(error);
}

这里把镜像身份和目录一起返回，便于解释采用了哪个来源。consumeCatalog 和 handleCatalogFailure 也需自己的异常合同；示例不是完整客户端。若校验只是返回 false，却没有被调用方转成拒绝，候选仍会兑现，代码外观上多了一次检查，实际选择条件却没有改变。

全部失败时，原因按输入归属，不按失败到达排序

规范的 PerformPromiseAny 为每个候选保存输入索引，再把拒绝原因放到对应位置。假设乙先失败、丙其次、甲最后，聚合错误的 errors 仍应按甲乙丙的输入次序关联，而不是按到达时间。诊断代码若另行按错误到达顺序拼镜像名称，就可能把超时记在错误来源上。

可审查的故障记录应在启动前保留稳定来源身份，明确输入顺序与每项原因的对应，并把内部详情与用户提示分开。错误对象可能包含不宜公开的地址、参数或堆栈；聚合失败不代表可以把所有内部诊断原样返回。记录哪些来源不可用，和向用户说明目前没有合格目录，是不同表达任务。

空输入也是需要显式选择的失败路径。没有候选时，普通 any 返回拒绝的承诺，聚合错误里没有候选原因；它不会因为“不存在失败请求”而成功。若配置缺失导致镜像数组为空，应该给出能定位配置的说明，而不是报告网络全部超时。入口配置错误与三个真实请求都失败，不宜合并成一种故障。

选择首个有效结果，不代表停止了其他工作

any 不提供取消底层任务的协议。一个镜像兑现以后，其他读取可能继续消耗连接和解析预算。如果需要取消，应由客户端或任务接口另行定义，而且取消等待不能证明远端工作已经撤回。本站关于Promise.all 与任务取消解释聚合结果与底层生命周期的区别，本篇的首个成功策略同样不能跳过它。

这也是不宜随意把多镜像写入放进 any 的原因。若三个候选都在创建同一个订单，首个兑现只结束调用者的选择，并没有把另外两笔写入变成未发生。只读冗余获取与有副作用操作有不同的业务风险；后者应先解决幂等、终态查询和补偿，而非靠挑出一个成功结果隐去其余状态。

两个候选已拒绝，一个永远 pending，何时会报告全部失败？

仅靠 any 不会得到“全部拒绝”，因为那个候选尚未拒绝，也没有任何兑现结果。需要独立定义每个候选或整个读取任务的截止时间，再决定超时意味着当前候选不可用，还是整个选择不再值得等待。超时不应被翻译成远端从未执行；它只说明在本次合同内没有得到合格结果。

拟议验证可以用受控承诺固定顺序：先拒绝甲，再兑现丙，确认乙尚未结束也能选出丙；另一次让全部拒绝且颠倒到达顺序，核对原因与来源；再覆盖空数组、无效值兑现和永久等待。不要依赖真实网络的偶然快慢证明算法，更不要把捕获到了一个错误当作每个候选均已终止。

全拒绝得到聚合错误的说明针对正常候选承诺的结算，不意味着任意可迭代输入或定制构造器的所有失败都必为同一错误类型。输入迭代过程本身抛错，就属于另一条入口失败路径。若接口只接受已验证的普通数组，可以把这项输入边界写清楚；通用捕获分支仍应保留无法归类的异常，而不是直接假设总有errors列表。

校验失败也应携带稳定来源身份。例如甲返回过期目录，乙返回缺字段目录，丙在期限内没有返回；三者都不可采用，但修复方向不同。诊断中保留版本不符、结构不符和等待超时，才能选择更新镜像、修复转换或检查网络。不要为了统一错误结构丢掉这些区别，也不要把内部详细内容直接公开。

整体截止时间到达时，负责结束等待的组件还应明确如何处理晚到结果，避免旧任务稍后覆盖新一轮选择。记录本次选择身份，并在提交到界面或缓存前核对其仍有效，这属于业务生命周期控制，不是any隐含提供的能力。

本文依据二〇二六年十月二十四日读取的 ECMAScript 在线规范，没有请求镜像、执行代码或测量延迟。接受 any 之前，应能说明每个候选何时有资格兑现、何时停止等待，以及其他候选的最终状态由谁负责。首个结果的选择正确，只是冗余读取合同的一部分。
