GitHub Actions 缓存命中，为什么仍不能直接信任发布制品？

缓存命中只说明数据被恢复；缓存来源、锁文件安装和发布制品身份是三个不同检查。用 GitHub Actions 的分支作用域、cache-mode 与 npm ci 拆开这条信任链。

核心要点

  • cache-hit 表示缓存 key 匹配并恢复了路径内容，不是签名、依赖一致性或发布来源证明。
  • GitHub Actions 缓存按分支或标签共享；低信任触发对默认分支缓存默认只读，显式写权限会改变这个边界。
  • 若 npm ci 是安装契约，缓存 ~/.npm 与缓存 node_modules 不是同一种选择；npm ci 会移除已有 node_modules。
  • 缓存用于复用，artifact 用于保存或跨 job 传递输出；特权发布仍要确认提交、运行和制品摘要的对应关系。

GitHub Actions 精确缓存命中说明请求的 key 匹配并恢复了文件，不能证明它由可信运行生成、符合当前依赖声明，或属于这次获批的发布。把缓存当作可丢弃的加速输入，仍按项目的锁文件契约安装，并在特权发布阶段单独确认制品来自哪个提交和工作流。下面依据 2026 年 11 月 26 日打开的 GitHub 官方文档及 npm CLI v12.2.3 文档解释设计边界；没有运行缓存投毒、工作流或安装测试。

cache-hit 说明找到了数据，不说明数据可信

GitHub Actions 先按 key 查找精确匹配；找不到时可以按前缀和 restore-keys 继续寻找。精确命中后，action 将缓存路径恢复到运行器。回退键命中时，恢复的数据甚至可能对应较旧的输入。键中放入锁文件摘要，有助于在锁文件变化时生成不同的键；操作系统、运行时版本、架构和安装选项也可能决定一份数据能否复用。但键表达的是“要找哪一份缓存”，不是对缓存字节的签名或审查。GitHub 还说明缓存内容没有签名或验证。换言之，绿色的 cache-hit 不是“依赖经过验证”的同义词。

这几个问题应分开回答：缓存键是否匹配？数据来自哪个分支作用域？当前运行是否有权读或写该作用域？恢复的文件会不会被直接执行？最终产物是否对应获批提交？一个键即使包含 hashFiles('package-lock.json')，也不能回答来源是否可信、该 job 有没有处理不可信输入，或制品来自哪个构建运行。使用较宽的 restore-keys 时，命中只说明找到一份前缀匹配数据；它并不把旧依赖变成当前依赖。

分支作用域和事件共同决定缓存读写边界

GitHub 将缓存作用域与分支或标签联系起来，而不是只按 workflow 或 job 身份隔离。同一仓库、同一分支上由不同工作流创建的缓存可以共享。拉取请求可以读取当前分支、默认分支以及基分支可见的缓存；由普通 pull_request 运行创建的缓存则属于 PR merge ref，不能被默认分支或其他 PR 读取。因而，“这个缓存键只给构建工作流使用”并不一定构成访问隔离；要查看事件、分支作用域和实际缓存路径。

对会落在默认分支缓存作用域的低信任触发，GitHub 默认将缓存访问设为只读。官方列举的触发包括 pull_request_target、issue_comment 和 workflow_run。显式设置 cache-mode: write 或 write-only 会绕过只读默认值，重新引入缓存投毒风险。cache-mode 可在 workflow 或 job 上配置，控制读取和保存；job 级设置会覆盖 workflow 级设置。复用工作流也要检查调用方有没有明确限制它的最大访问模式。

可以想象一个假设场景：可信的默认分支 push 工作流维护依赖缓存；低信任的 PR 工作流需要读取相同作用域以减少重新下载。保持该 job 为 cache-mode: read 时，它可恢复但不能写默认分支缓存。如果为了让 PR job 保存数据而显式改成 write，并且该 job 处理了 PR 控制的文件、脚本或构建输入，攻击者就可能影响稍后被高权限工作流恢复的内容。这是一条威胁路径说明，不是本文执行过的利用。修正方式不是给键加上更多看似随机的字符，而是把写缓存限制在可信触发，低信任工作流显式只读，或不让高权限 job 恢复并执行不可信缓存内容。

缓存也不是秘密存储。任何能读取某份缓存的运行都能取出其中的文件；GitHub 明确提醒不要把令牌、凭据或其他敏感信息放进缓存路径。即使仓库是私有的，也要根据实际可发起 PR 的主体和 workflow 读写权限判断谁能读到数据，而不是假设“私有”就等于“缓存保密”。

缓存路径决定它是在省下载还是跳过安装

npm 场景能看出缓存目标与安装步骤的关系。缓存 ~/.npm 是复用包管理器下载数据；之后仍运行 npm ci，依赖目录由锁文件和包管理器的安装过程重新形成。npm 文档规定 npm ci 需要已有 lockfile；当 lockfile 与 package.json 不匹配时会报错；开始前会移除已有 node_modules，且不会改写清单文件。因此，如果工作流先恢复整个 node_modules，紧接着执行 npm ci，恢复的安装目录会被清掉，不能把它算成保留的安装结果。是否缓存下载目录能节省时间取决于项目和网络，本文没有做耗时测量。

反过来，若工作流恢复 node_modules 后就跳过安装，缓存中的额外包、缺失包、旧的原生模块或安装脚本产物都可能留在构建输入里。即便缓存键包含锁文件摘要，它也不能保证这个目录是由可信流程按当前工具链完整生成。锁文件安装有助于落实声明的依赖图，但也不等于审查了每个包的代码、生命周期脚本、注册表来源或运行时行为。要验证供应链，还需要依赖来源、版本和构建权限方面的其他控制。

因此先问“复用哪种成本最高、又能安全重建的内容？”若答案是下载数据，缓存包管理器目录并继续锁文件安装通常比跳过安装更容易界定；若确实要缓存已经展开的依赖树，就应明确何时重新物化、哪些工具链输入必须进入键、谁可以写这份缓存，以及后续 job 是否会执行其中的文件。不要只根据命中率决定路径。

发布制品不应只凭缓存文件名取得信任

GitHub 将 dependency cache 定位为跨运行复用不常变化或重新生成成本较高的数据；workflow artifact 用于保存构建产物和日志，或在 workflow 的 job 之间传递输出。这两类存储用途不同，也不能互相替代。Artifact 解决“把这个 job 产生的文件交给另一个 job”这一问题，但仅仅下载成功仍不能证明来源可信。

一个较稳妥的交接会记录获批源码提交、构建运行、输出摘要和部署审批对象之间的对应关系。若团队启用了 GitHub artifact attestations，还可以生成带签名的构建来源声明，其中包括关联 workflow、仓库、环境、提交 SHA 和触发事件；消费者必须按自己的信任策略验证声明。Attestation 是显式生成并验证的信任材料，不会因为 workflow 使用了缓存或上传了 artifact 就自动存在。

高权限发布 job 不应仅因缓存中有一个叫 release.tar.gz 的文件就上传它。先确认这个文件是本次可信构建输出，再检查摘要与审批记录一致。若缓存中保存了中间文件，可由受信任 job 重新生成最终 artifact；不要让低信任触发器写入的可执行目录，直接穿过发布边界。

用能区分故障原因的情形验收

缓存策略至少应按以下情形设计验收，而不是只看一条“命中率”指标：

  • 无缓存：重新下载或生成后仍按声明安装，构建能否完成？这证明缓存缺失只是速度问题。
  • 精确命中：恢复后仍运行锁文件约束的安装，依赖图、工具链和产物来源是否被独立记录？
  • 回退命中：命中较宽 restore-keys 时，日志是否仍报告为“回退数据”，并由安装过程修正或拒绝不匹配输入？
  • 低信任运行：外部 PR 是否只能读取默认作用域缓存？是否存在 job 或 reusable workflow 显式请求了可写 cache-mode？
  • 特权消费：发布 job 是否把某个缓存路径、名称或未经验证的 artifact 当成身份？摘要、来源和批准对象如何关联？

这些只是建议的验证方案，本文没有连接任何 GitHub 仓库、运行 workflow 或比较命中与未命中的构建。记录的 cache-hit、锁文件安装结果、来源核验和最终发布摘要应分开，否则一个成功的缓存步骤可能掩盖另外三个环节尚未被证明。

遇到缓存故障时可以临时禁用缓存建立对照，但这只能帮助定位复用数据是否参与问题，不能证明缓存安全或永久无需缓存。等安装契约和来源边界清晰后，再判断哪些可重建数据值得缓存。关于 PR 代码怎样进入高权限工作流，另见默认分支工作流也不能把 PR 代码当成可信输入；关于构建文件的身份和审批交接，参见怎样确认下载的产物就是获批版本。
