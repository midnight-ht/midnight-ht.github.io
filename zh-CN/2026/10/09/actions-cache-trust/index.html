依赖缓存命中了，为什么仍要重新校验安装？

GitHub Actions 缓存应视为可丢弃的加速输入，锁文件、来源与信任边界仍需验证，不能代替发布制品。

正文

依赖缓存命中只能证明找到了可恢复的数据，不证明它符合当前锁文件，也不证明可以作为可信发布制品。构建流程应在缓存缺失时仍能完成，并独立检查依赖安装与制品来源。以下依据 GitHub Actions 文档作设计分析，没有对任何仓库进行缓存投毒实验。

缓存回答的是复用问题

GitHub 的依赖缓存文档解释缓存键、恢复范围和访问限制，也提醒低信任触发方式可能涉及缓存投毒风险。缓存是速度优化，不能因为 key 名称里有某个版本号，就把内容当作已经审核的供应链输入。

假设工作流恢复了旧依赖目录，却跳过按锁文件安装。即使构建成功，使用的依赖也可能与这次提交的声明不同。另一个常见问题是把运行平台、工具链或安装选项从键中遗漏，使表面相同的依赖在不同条件下不兼容。键应该反映复用条件，而不是仅追求命中。

锁文件不能只当键的一部分

把锁文件摘要放进缓存键有助于区分版本，但实际安装仍应由包管理器按项目契约执行。恢复的数据应经适当校验或重新物化，不能因为缓存存在就跳过所需的一致性检查。具体缓存下载目录还是已安装目录，需要理解对应工具的行为与跨平台边界，并避免把构建缓存与秘密存储混为一谈。

恢复键越宽，越容易拿到不完全匹配的旧数据。是否接受这种退化，取决于后续安装能否安全校正，以及错配的成本。不要把“回退恢复成功”展示成“精确依赖已验证”，否则日志中的绿色命中会让排查者错过真正的版本差异。

缓存中也不应放凭据和私密配置。能访问缓存的工作流范围可能比日常发布者更广，尤其需要考虑外部贡献触发的运行。访问限制要按当前平台规则检查，不能以私有仓库或某个分支名作为秘密绝不会泄露的证明。

高权限阶段要重新确认来源

构建缓存与待发布制品应有不同责任。前者可丢弃、可重建；后者应关联本次提交、构建流程与内容摘要。高权限发布 job 不应因为从缓存取出了某个文件，就自动执行或上传它。跨信任边界的交接需要核对来源，不能由文件名替代身份。

缓存故障也不应让流程悄悄更改依赖版本来“修好构建”。缺失时从明确来源重新安装，出现不一致时保留错误。若删除缓存确实解决一次问题，只能说明复用数据参与了故障，仍应查清键、安装方式或输入变化，否则下次命中还可能复现。

建议验收包含无缓存、精确命中、回退命中和不兼容缓存四种情形，比较最终依赖和构建产物是否符合预期。再按权限范围验证不可信运行不能影响高权限消费路径。本文没有执行这些检查，不能声称已消除供应链风险。

是否应该完全禁用缓存？可以为排障建立无缓存基线，但长期选择应依据可复现性、耗时与运维成本。先确保移除缓存不会改变依赖契约，再优化命中率。涉及发布身份时可继续看令牌与 job 权限，把加速、身份与发布责任分别说明。
