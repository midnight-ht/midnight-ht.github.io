搜索结果倒退了：取消请求还不够，提交状态也要验身份

前端搜索怎样处理乱序响应：取消无用请求、识别当前意图，并保护成功、错误和加载状态的写入。

正文

核心要点

  • AbortController 可停止部分浏览器异步工作；请求身份检查负责拒绝旧结果写入，两者解决不同问题。
  • 身份必须标记一次用户意图而不只是查询字符串，并覆盖结果、错误、加载状态和 finally 清理。
  • 取消请求不会回滚已经发生的服务端操作；本文代码思路与测试场景均未在真实应用中执行。

搜索“架构”后马上改成“架构评审”，新结果先到、旧结果后到；只调用 abort() 并不能证明最后一次状态写入来自当前意图。稳妥的前端搜索要同时做两件事：用 AbortController 尽量停止不再需要的异步工作，再给每次用户意图一个身份，让结果、错误、加载状态和清理逻辑都只能由当前请求提交。下面的请求序列和代码形态是设计示例，没有在真实应用里运行。

两次查询都成功，为什么屏幕反而退回旧结果

假设搜索框当前为空。用户先输入“架构”，界面为请求 A 生成身份 17；还没等它返回，用户继续输入“架构评审”，界面为请求 B 生成身份 18。B 先返回，页面展示了“架构评审”的结果。稍后 A 也返回，如果回调无条件调用 setResults(data)，屏幕就重新显示“架构”的结果。两次 HTTP 请求都可以成功；错的是页面接受了已经过期的 A 的状态提交。

竞态不要求网络或浏览器出错。响应时间受缓存、服务器负载、代理和数据量影响，后发请求先结束很常见。只在发起请求时设置“正在加载”，或只在成功分支比较一次查询字符串，也不够：A 的错误提示可能盖掉 B 的成功结果，A 的 finally 还可能把 B 正在使用的 loading 清成 false。同一请求的多个异步阶段需要遵守同一条提交规则。

请求身份应代表一次意图，而不只是文本

最小方案是为每次新的搜索意图递增一个代次号，发请求时捕获该号，异步操作完成后检查它仍是当前代次。更适合复杂界面的做法，是把代次号放进状态动作，让 reducer 或集中状态层拒绝旧动作：

function reducer(state, action) {
  if (action.requestId !== state.requestId) return state;

  switch (action.type) {
    case 'succeeded':
      return { ...state, status: 'success', results: action.results, error: null };
    case 'failed':
      return { ...state, status: 'error', error: action.error };
    case 'finished':
      return { ...state, loading: false };
    default:
      return state;
  }
}

这段伪代码省略了动作创建与初始化，只说明门禁位置：每次异步完成时，先确认 requestId 与当前状态相同，再允许更新。started 动作要建立新的当前身份；过期请求的 succeeded、failed、finished 都应被丢弃。这样做比只在成功分支检查更完整，也便于测试错误、加载和清理路径。

为什么不直接比较查询字符串？用户可能先搜索“架构”，换成“架构评审”，再返回“架构”。第一次和第三次文本相同，但代表两次不同的当前意图；第一条慢响应不应因为文本碰巧相同就重新获得提交资格。查询键和请求身份用途不同：查询键可用于缓存，代次号则回答“当前界面允许哪一次操作更新状态”。

一个身份通常要覆盖影响结果的全部输入，例如查询文本、筛选项、排序、页码、租户或语言。如果页码改为第二页，而旧的第一页响应仍能写回列表，屏幕照样会把新筛选和旧结果混在一起。可以把这些条件组成规范化查询键用于缓存，同时独立递增每次意图的身份。若页面有多个互不相关的搜索区域，身份也应按区域隔离；一个全局计数器可能让面板 A 的搜索误使面板 B 的结果过期。

取消减少工作，身份门禁决定谁能写入

AbortController.abort() 可以中止尚未完成的 fetch、响应体消费或流操作。切换查询时取消旧 controller，能减少浏览器继续等待或读取旧结果的工作。但它不是 UI 一致性的证明：旧回调可能已经开始执行，其他转换或缓存处理也可能继续；而且 abort 发生得越晚，越不能假设此前没有任何状态更新。

响应头到达并不总意味着响应体已经读完。比如 fetch() 已返回 Response，代码接着执行 await response.json()；在读取 body 期间信号仍可能中止操作。因此需要在会产生 UI 写入的边界检查身份，而不是只在 fetch 发出前或响应头返回后检查一次。如果解析被中止，错误路径也要按请求身份过滤，不能把一次由新输入触发的正常取消展示成网络故障。

默认 abort reason 是 AbortError，调用方也可以给出任意 JavaScript 值作为原因。多个信号合并或封装库介入时，不应依赖“所有取消都具有同一个错误字符串”。可以检查这次操作自己的 signal.aborted，同时记录应用层的取消来源：输入已改变、组件卸载、用户点了取消，还是请求期限结束。是否向用户展示提示，取决于来源和当前身份；旧意图的异常通常不应打扰新查询。

如果使用 React 的 useEffect，官方文档在依赖变化时先以旧值运行 cleanup，再以新值运行 setup；手动 fetch 的示例用局部 ignore 标记阻止过期结果写入。这个标记是提交门禁的一种实现。AbortController 可以作为额外的资源控制，但不能替代门禁。React 文档也提示，如果框架已经提供数据获取机制，通常优先使用框架方案；这里讨论的是原生异步状态设计，不要求所有项目都在 Effect 中发请求。

防抖、缓存和请求身份各自解决什么

输入防抖让用户暂停输入一小段时间后才发请求，主要减少请求数量。即使只剩两个请求，它们仍然可能乱序，所以防抖不能保证展示正确。取消可以尽量停止已过期的操作；如果服务器已经开始处理，客户端调用 abort 也不等于服务端回滚。身份门禁则负责让旧响应不能覆盖当前视图。

缓存又是另一层：旧请求即使不再适合直接展示，其结果仍可能是某个明确查询键的有效缓存数据。应用可以允许旧响应更新对应缓存，但只有当前查询键和身份匹配时，才能把它提交到当前屏幕。若缓存与可见状态共用一个“最近结果”变量，就容易把“响应可以保存”误当成“响应可以展示”。

新请求加载时，旧结果要不要留在屏幕上？

可以留，但要让用户看得出它属于上一组查询，不能把旧结果计入新筛选的数量，也不应让它冒充新结果触发批量操作。如果结果会改变权限或资金决策，界面应清空、冻结操作，或明确标注旧数据，直到当前请求完成。保留旧结果是避免页面闪空的体验选择；身份门禁则仍需阻止旧响应把当前状态覆盖。

因此选择顺序可以很具体：先决定哪些参数定义一次查询、何时创建新身份；再决定是否需要防抖和取消以控制负载；最后规定缓存写入与界面展示的不同门禁。只有单请求且没有快速切换的静态页面，方案可以简单些；可组合筛选、分页和并行区域较多的界面，更值得把请求身份放进显式状态机或 reducer。两种方案都需要测试，不是复杂代码越多越可靠。

失败路径：旧请求的 finally 把新请求关掉

假设 B 还在加载，A 的 promise 因为切换查询而进入 catch，随后执行 finally { setLoading(false) }。即使 A 的错误没有显示，加载指示也会提前消失，让用户以为 B 已经结束。可见结果、错误和 loading 必须共享当前请求身份；否则你只挡住了最显眼的结果数组，却留下另一种过期写入。

另一个容易漏掉的情形是清空输入。清空本身应创建一个新的当前意图或显式回到 idle，取消旧请求并清除旧结果。否则旧请求稍后成功，页面会在输入为空时重新出现旧列表。卸载组件也要阻止失效实例继续提交；React cleanup 的 ignore 示例说明了这个生命周期边界。若输入变化只触发取消，而状态层没有更新当前身份，某些尚未被中止的回调仍可能写回。

缓存命中也要考虑身份：用户从查询 A 转到 B 再回到 A 时，可以立刻显示 A 的缓存作为占位，但这不意味着最早那次 A 的在途响应可以无条件覆盖后来状态。应用需要定义数据新鲜度和当前意图的规则，例如先显示标明来源的缓存，然后让本次 A 的请求更新，旧代次 A 则只能更新其缓存条目。缓存值是否展示是产品策略，旧异步动作能否改当前状态是正确性约束。

怎样验收而不是只断言调用了 abort

测试应人为控制 promise 完成顺序，而不是依赖网络快慢碰运气。先发出 A，再发出 B，让 B 成功后让 A 成功；检查屏幕仍显示 B。然后复用相同请求顺序，让 A 失败、B 成功；错误提示不应覆盖 B。再让 A 的 finally 先结束而 B 仍待处理，loading 仍应属于 B。本文没有运行这些测试，下面是可实施的验收计划而非通过记录。

还要覆盖查询文本恢复为相同字符串、筛选或页码变化、清空输入、组件卸载、响应体读取期间 abort、真实网络错误，以及防抖和缓存同时启用的情况。断言不只是“旧数据没有出现”，还要检查 query 标识、结果、错误、loading、缓存条目是否符合各自约定。可以把每个状态动作的 requestId 和原因写入测试记录，定位是哪条动作越过了门禁。

最后，搜索 GET 和下单 POST 不应共用“取消就撤销”的解释。浏览器停止等待写请求时，服务端可能已经提交；要撤销业务变化，必须使用业务支持的撤销接口或查询操作状态。这个边界与超时后的幂等与结果查询有关；写入基于旧表示时，还可参阅If-Match 条件写入与并发冲突。
