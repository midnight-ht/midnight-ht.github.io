设置 no-cache 后仍有缓存文件，是配置错了吗？

no-cache 允许保存但要求重用前验证；本文用分层请求证据区分浏览器、代理和 CDN，并说明 no-store 与 private 的边界。

正文

核心要点

  • 区分是否保存与能否直接重用；no-cache 需要验证，no-store 涉及存储，private 限制共享缓存。
  • 通过源站、边缘和浏览器/Service Worker 的版本标记与验证器定位首个偏离层。
  • 示例与验收方案均为假设，未在 CDN 或生产环境执行。

看到磁盘上还留着响应文件，不足以证明 no-cache 配错：响应可以被保存，只是再次使用前必须沿请求链路转发验证。若目标是禁止缓存存储，要考虑 no-store；若担心共享缓存复用面向单一用户的响应，还要考虑 private。这三个指令约束不同，不能靠在头部里把它们全部堆上去代替设计。规范对三者的区别见 RFC 9111 的响应缓存指令。以下示例是按 RFC 9111 与 MDN 文档整理的排查方案，没有在某个 CDN 或生产环境实测。

先判断问题发生在哪一层

浏览器本地缓存、公司代理、CDN、反向代理和 Service Worker 的 Cache API 不是一个可以从响应头直接观察完的“总缓存”。应用从源站返回 Cache-Control: no-cache，只能说明源站给出了这个策略；托管缓存还可能有自己的规则，Service Worker 也可以按脚本自定义存储与响应。MDN 的 HTTP 缓存指南明确指出，托管缓存产品通常还提供配置或管理 API，部分实现可以选择与 HTTP 缓存协议不同的策略。因此，“浏览器开发者工具显示磁盘缓存”或“边缘响应还是旧内容”都只是线索，还不是归因结论。

先为要排查的表示准备一个安全、可见的版本标记，例如公开测试页面中的 release-id。记录完整 URL、方法、状态码、重定向链、最终响应头、响应体里的标记、Age、ETag、Last-Modified、Vary、Via 或服务商提供的缓存命中字段。Age 可以提示共享缓存中响应的当前年龄；X-Cache 一类字段则是特定服务的诊断信息，不是统一标准。不要把带真实账户信息的响应体或认证头复制到公开工单。

把同一个请求依次发往应用源站地址、公开域名以及带着现有 Service Worker 的浏览器环境，并让每次观察使用可比较的 URL 和请求头。若源站已返回新版本而公开边缘仍返回旧版本，重点查 CDN 的缓存键和规则；若边缘已有新版本、浏览器页面仍旧，查浏览器缓存、Service Worker 或页面自己的状态。若响应头在重定向后发生变化，也要按每一跳分开记录。这个分层比较比一次性清空所有缓存更能指出第一处偏离策略的位置。

no-cache 保存了什么，又限制了什么

RFC 9111 对无参数响应 no-cache 的定义是不允许缓存未经验证就用来满足后续请求。它不等于“不得写入磁盘”。假设一个公共版本说明页返回 Cache-Control: no-cache 和 ETag: "release-42-en"。浏览器可以保存正文和验证器；下一次需要使用时携带 If-None-Match: "release-42-en"。如果源站确认表示未变，可以返回 304 Not Modified，缓存继续使用已存正文；如果表示改变，则返回新正文与新的验证器。条件请求和 304 的配合可参照 RFC 9111 的验证流程及 MDN 条件请求指南。于是文件仍然存在、磁盘命中仍可能出现，而重用过程已经经过验证。

这个设计的价值在于区分“省掉正文传输”和“保证再次使用前检查新旧”。一次验证仍需要网络往返，而且正确性依赖验证器。若正文改变却继续生成相同的 ETag，缓存可能忠实地按照错误的版本标识复用旧表示。对经过内容协商的资源，验证器应对应具体表示；如果语言或编码会改变正文，缓存键也必须反映这些输入，例如响应实际按 Accept-Language 变化时返回合适的 Vary。不能为了出现 304 而让服务器用一个不随表示变化的标记。

请求上的 Cache-Control: no-cache 和响应上的同名指令也不应混为一谈：前者表达客户端请求时对已存响应的复用要求，后者定义缓存处理该响应的约束。排查时保存请求头与响应头两份记录，才能知道是谁要求验证、验证器是什么，以及服务端最后怎样回答。

何时选 no-store，何时加 private

无参数响应 no-store 是禁止缓存存储该请求或响应信息的指令。它适合确有理由不让标准 HTTP 缓存保存的内容，但不是“把这个 URL 的所有历史副本远程删除”。一个浏览器或边缘节点过去已经存下来的响应，不会仅因为后来新发了 no-store 就自动消失。规范还说明，少数实现 must-understand 的缓存可在确认状态码缓存要求后，于规定条件下忽略 no-store；部署这类组合时要按 RFC 9111 的 must-understand 与 no-store 交互规则单独核对，而不要把 no-store 描述成无条件的全局隐私保证。MDN 对已存缓存的清理边界指出，浏览器的 Clear-Site-Data: cache 与共享或中间缓存不是同一清理范围；托管 CDN 通常要通过它自己的管理面或 API 处理已存对象。即使做了清理，也要验证目标缓存层和目标对象，而不能把新头部当成清理收据。

无参数响应 private 则限制共享缓存存储该响应；私有缓存仍可以在规范允许的条件下保存。它不是内容保密加密，也不保证操作系统、扩展、恶意缓存或网络层无法看到内容。对用户账户页面，一个可能的策略是 Cache-Control: private, no-cache：允许用户代理保存，同时每次重用前验证，并禁止共享缓存保存。若数据性质或组织要求确实禁止标准缓存保存，才再评估 no-store 及回退、浏览器历史等产品影响。

Vary 适用于按请求头区分不同表示的缓存匹配，不是身份隔离的万能开关。比如同一公开页面按语言返回不同正文，Vary: Accept-Language 可声明语言请求头参与匹配；RFC 9111 的 Vary 缓存键规则要求缓存比较该字段列出的请求头值。它不能替代账户授权，也不能把一个可能含用户数据的公共共享缓存安全化。RFC 9111 对带 Authorization 请求的共享缓存另有约束：共享缓存一般不得把响应复用于后续请求，除非响应中有明确允许共享存储的指令且缓存遵守相应规则。实践中，先决定响应是否可共享，再谈命中率和 Vary 细化。

一个三层排查例子：旧版本到底是谁在复用

假设团队更新了公告页，发布流水线显示版本 release-43，部分访问者仍看到 release-42。这只是一个待验证的假设案例，不代表某家 CDN 的实际行为。第一步请求源站并保存状态、ETag、Cache-Control 与正文版本。如果源站仍给 release-42，问题在应用部署或源站路由，缓存还不是第一嫌疑。若源站给 release-43，继续请求公开域名并比较同样的字段。

公开域名若显示 Age 持续增加且正文仍旧，查看 CDN 对该路径的自定义缓存 TTL、忽略响应头规则、键以及是否将查询参数纳入匹配；同时比较边缘返回的 ETag 是否与源站一致。若 CDN 回源验证后得到 304，但内容本应变化，重点审查源站验证器是不是漏掉了模板、语言、压缩形式或数据版本。若 CDN 命中的是旧 ETag，而源站新 ETag 已变化，缓存键或回源验证路径才是进一步方向。

若公开域名已经是 release-43，在绕过 Service Worker 的独立浏览器会话中再次请求。无控制器会话显示新版本而正常页面显示旧版，下一步看 Service Worker 的缓存策略、缓存名称和更新/激活流程；两种会话都收到新响应但界面仍显示旧版，则问题可能在客户端状态或静态资源，而非 HTTP 响应缓存。每一结论都应引用这组实际记录；如果只是设计演练，要像本文一样标明尚未执行。

这条路径还给出一个反例：直接在浏览器里“禁用缓存”后发现页面变新，不能证明源站的 no-cache 无效。开发者工具可能改变请求方式或添加请求指令，Service Worker 和 CDN 也不一定同时被绕过。排查记录应说明控制条件，而不是把一次强制刷新当作缓存策略验证。

改完之后用什么验收

为每个代表性路由列出预期表示、允许缓存的层、指令、验证器、内容协商条件和源站不可达时的回退策略。然后在预发布环境用同一 URL 采集首次 200、未变更后的条件请求、内容改变后的条件请求，并检查正文与状态：未改变时是否能通过验证复用，改变时是否拿到新正文和新验证器。分别检查带和不带身份的请求，以及各语言或压缩表示；不要把被掩码的私密头写入日志。

如果使用 CDN，再对源站与边缘进行相同请求对比，并用服务商的清理工具做单独验收；响应头由源站生成，不代表 CDN 配置会按该头工作。若使用 Service Worker，也要单独测试安装、激活、旧缓存清理和离线分支。测试未覆盖的层必须记为未知。没有实际采样记录时，不要写“配置已修复”或“用户已收到最新版本”。

发布后的敏感内容变更尤其不能只补一个 no-store：还要评估既有副本、授权边界、CDN 清理范围和用户侧缓存。HTTP 缓存指令规定的是遵守该协议的缓存应如何处理，不是对所有副本的销毁命令。要解决一个具体旧页面问题，应从源站、边缘、浏览器/Service Worker 三个观察点找出首个不符合契约的层，再针对它修改；这样既能避免全站盲目禁用缓存，也能把确实需要禁止存储的数据与只要求重新验证的公共内容分开。

如果旧页面恰好在发布期间由并发任务覆盖，还需检查部署并发与环境锁中最后写入环境的提交。缓存验证解决的是表示何时能重用；它不能修正源站已经回退到旧版本的发布顺序。
