设置 no-cache 后仍有缓存文件，是配置错了吗？

区分 HTTP 缓存的存储与重用：解释 no-cache、no-store、private，并按实际请求链路验证策略。

正文

no-cache 不等于禁止保存响应。它要求缓存重用相关响应前完成验证；如果目标是禁止存储，应理解 no-store 的语义，并核对实际缓存链路；该指令也不是绝对的隐私保证。文件仍在磁盘上不能单独证明 no-cache 配错。以下依据 HTTP 缓存规范作设计分析，没有测量某家 CDN 的默认行为。

先分开保存和再次使用

RFC 9111分别定义缓存存储、验证和 Cache-Control 指令。无参数 no-cache 要求重用前验证，no-store 指向不存储，private 约束共享缓存。它们不是同一个“开关”的不同写法，不能把名称按日常英语理解后随意替换。

假设发布后的首页需要尽快检查新版本，团队可能允许保存响应，却要求再次请求时向源站确认。这样与不保存任何内容是两种策略。另一方面，包含个人信息的响应需要考虑存储和共享范围，不能因为有验证机制就忽略数据曾经落入哪里。

响应头正确也要看链路是否遵守

浏览器、边缘缓存和反向代理可能处于不同层。应用返回的响应头是设计输入，不是最终用户一定收到同样内容的证据。建议记录实际 URL、响应状态、重定向和最终头部，按链路确定是哪一层产生了响应，而不是一看到旧页面就清空所有缓存。

条件请求也要有合适的验证器。服务端根据表示变化生成 ETag 或相应更新时间，才能让验证结果有业务意义。如果内容变化而验证器没变，缓存按契约复用也可能继续显示错误版本；问题在契约的生成，而不只是缓存保存了多久。具体实现需要与应用版本及内容协商一起核对。

对于带身份的页面，要先确认是否允许共享缓存，再考虑命中率。不同账号、语言和权限可能改变表示，缓存键和共享策略必须保留必要边界。不能把某个公共首页的配置整段复制到用户账单接口，也不能把 Vary 当作所有身份隔离问题的通用答案。

怎样判断一次变更真的生效

可以先选择一个具有可识别内容版本的响应，再记录第一次请求、再次请求和内容修改后的请求。检查是否发起验证、是否返回新的正文，以及浏览器最终看到的版本。本文未执行这一实验；设计记录应包含预期和真实结果，不能只截图开发者工具中的单个请求头。

如果服务端不可达，还要明确是否允许旧内容继续显示。公共说明页与交易状态的容错边界可能不同，选择应来自业务风险而不是追求统一命中率。涉及强制重新验证的语义时，应按规范限制处理，不擅自用旧内容假装最新状态。

已经公开的敏感数据，后来加 no-store 能否收回？不能把新的指令当作历史清理证明。应调查已分发副本、缓存清理能力和访问控制，必要时按数据事件处理。缓存头是预防与传输契约的一部分，不是所有副本的远程删除按钮。

对发布故障，先比较源站、边缘和浏览器实际响应，找出第一个不符合契约的位置，再做定向处理。若问题来自互相覆盖的发布任务，清缓存也无济于事，需回到部署并发与环境锁检查哪个版本最后写入了环境。
