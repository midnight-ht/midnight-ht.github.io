UUID 不是订单授权：服务端每次要核对哪四个维度？

UUID 只能降低枚举可能，不能证明请求者有权访问对象。本文把授权决策拆到操作、租户、异步任务和静态资源，并给出可控的双账号验收矩阵。

正文

核心要点

  • 对象标识回答服务端要找什么；授权回答当前主体能否对它执行这个操作，两者不可互换。
  • 把主体、租户、对象和操作放进每个请求的授权决策，并检查下载、批量、异步及静态资源入口。
  • 用隔离的两个测试主体和正反向权限矩阵验证允许与拒绝路径；这篇建议不是已执行的渗透测试。

UUID 只能回答“请求指向哪笔订单”，不能回答“当前主体能不能对它做这件事”。服务端每次授权都应把主体、对象、两者当前关系和请求操作放在同一个决策里；之后还要把这个边界延伸到下载、批量接口、异步任务和文件分发。OWASP 的 IDOR 与 API BOLA 指南明确指出，整数、UUID 和普通字符串都可能成为对象引用，随机编号不能替代对象级检查。本文依据官方指南整理设计与测试方法，没有对真实系统执行渗透测试。

标识、身份、授权是三个不同的问题

一个请求里常有 /orders/{id}、查询参数、JSON 字段、文件名或下载令牌。它们告诉服务端“请求者想指向哪个对象”，并不能回答“请求者是谁”或“请求者被允许做什么”。认证通常建立当前主体；授权则要检查该主体对具体对象、具体操作的权限。把 isLoggedIn 当作 canRead(order)，相当于把进入应用的门票误当成每个房间的钥匙。

UUID 不改变这个逻辑。编号可能从日志、邮件通知、浏览器历史、截图、协作链接、导出文件名或另一处 API 响应中泄露。即使它不可预测，拿到链接的人仍可能带着自己的合法会话请求目标对象。如果后端只按 UUID 查库并返回记录，随机性只是隐藏了入口的一部分，没有消除授权缺口。反过来，连续编号也可以在严格的服务端授权下安全使用。标识复杂度可以作为减少枚举的纵深措施，但权限判断必须独立成立。

这也是为什么“前端不显示订单按钮”不是权限边界。调用者可以直接请求接口、改请求体或复用下载地址；客户端展示逻辑只改善体验。OWASP 的授权指南要求把决定放在服务端、网关或等价的受控执行层，并在每个请求上验证权限。API1:2023 还区分了对象级越权与功能级越权：能调用某类端点，却把对象 ID 换成别人的对象，是 BOLA；本来就无权调用管理员功能，则是不同的功能授权问题。两种检查可能同时需要，不能用角色检查替代对象归属检查。

把授权写成可评审的关系

可审查的授权问题至少包含四个维度：主体是谁、对象属于哪个安全域、主体与对象是什么关系、当前操作是什么。对订单读取，规则可能是“订单所属账户的成员，且具有订单读取权限”；对取消操作，则可能还要检查订单状态、操作者角色和业务时限。一个人能看摘要，不自然意味着可以改收款账户、取消订单、导出全部明细或读取附件。

多租户系统不能信任请求里由客户端自行声明的 tenant_id。服务端应从受验证的会话、令牌或服务身份建立主体上下文，再依据当前成员关系确定可访问租户。然后把这个租户范围放入对象查找或授权策略。OWASP 多租户指南把复合键（例如 tenant_id + resource_id）列为一种选择，而非普遍强制的方案；关键是每条租户对象访问路径都经过可执行的隔离边界。数据库行级策略可以成为纵深防护，但它不能代替验证应用连接使用了正确的主体和租户上下文，也不能证明静态文件路径受同一规则保护。

常见实现方式是先把查询限制在当前授权集合中，再定位对象：例如“当前主体可访问的订单集合中，是否存在该 ID”。这减少了忘记做后置判断的机会，并能自然表达租户和共享关系。另一个合法设计是先取对象、再调用集中式策略检查；它需要确保在序列化、写入、队列投递或产生副作用之前完成授权，并处理资源不存在与无权访问的差别。选哪种方式要看框架、关系复杂度和是否需要统一审计；不能仅凭代码更短判断边界更完整。

权限是按操作变化的，不是给对象贴一张通行证

同一订单可能有查看、编辑备注、退款、取消、导出和下载附件等动作。建议把对象类型与操作列成清单，并为每个动作写清允许主体、必要关系、状态限制和副作用。读操作的成功不能证明更新接口正确；只在 GET 检查 owner、却让 PATCH 直接按 ID 写入，仍是对象级缺陷。管理员或客服访问也需要限定范围、理由和审计方式，不能成为绕过所有租户检查的万能角色。

批量接口尤其需要明确整体语义。如果一批 20 个对象里只有 18 个允许访问，接口是全部拒绝、只处理允许部分，还是返回部分结果？这不是纯技术细节：查询可以容忍逐项过滤，而批量退款或权限变更出现部分成功时，调用方可能误以为整批原子完成。响应还可能泄露哪些对象存在。契约应规定原子性、逐项结果、重试方式和错误信息，并以相同规则覆盖批量导出与后台作业。

嵌套路径也不能因外层对象已授权就自动放行。例如用户可以读取某个项目，不表示他能读取路径中任意 project_id 下的附件；若 document_id 与外层 project_id 不匹配，服务端要拒绝，不能只检查两项 ID 各自都存在。租户/对象/子对象的关系应作为一个整体校验。错误响应是否统一返回 404 或分别返回 403/404，要结合对象存在性是否敏感、客户端是否需要可操作的提示来决定；无论选哪种外部响应，内部都可记录细粒度拒绝原因，但要避免记录令牌、敏感正文或过度暴露的标识。

链接和任务会跨越权限变化的时间

一次请求通过授权，不代表之后生成的所有产物都持续可访问。用户提交报表任务时可能仍有团队权限，任务完成前成员关系却被撤销；如果队列消息永久携带创建时的“允许”结论，完成后的结果下载可能继续泄露数据。团队应先确定产品语义：创建任务时冻结当时授权，还是下载时按当前关系重新授权。敏感数据常需要在任务消费、产物生成或下载入口再次建立可信主体上下文并检查权限，但是否重复检查哪一环要符合明确的业务规则，而不是随手加一个“异步也检查”。

签名下载 URL 是委托能力，不是对象 ID 的随机版本。签发前先判断主体能否访问具体文件和动作，再把链接限定到所需对象、方法和短期用途，并规定撤销行为。持有链接的人在有效期内可能可以转发访问，所以链接的安全模型要和数据敏感度相匹配；创建链接时的会话权限不能自动延伸到永久可用的存储地址。OWASP 多租户建议也强调，已在签名之前完成授权时，URL 本身不一定要暴露租户标识。

静态文件、图片缩略图、对象存储下载、缓存和预览端点都属于资源访问路径。数据库 API 检查做得正确，如果文件桶公开、边缘缓存键忽略租户差异，或者预览服务根据可猜路径取文件，数据仍会越界。审查时画出从页面到服务、存储和分发层的路径，确认每一层拿到的是哪个主体上下文、哪些资源字段会影响结果，以及缓存何时可能跨用户共享。这里需要针对使用的云存储或 CDN 另查厂商的访问控制配置，OWASP 通用指南不能替代具体提供商的配置证据。

一组能揭露遗漏的受控测试

建立两个专用测试主体 A、B，并各自创建一组测试对象。先为每项操作写矩阵，而不是只交换一条详情 URL：A 读取自己的对象应允许；A 读取 B 的对象应拒绝；B 对自己对象的权限按其角色决定；低权限主体进行管理操作应拒绝；附件、导出、嵌套资源、批量与异步结果应分别覆盖。任何异常响应都不应包含受保护的字段或副作用。测试使用专用数据和测试环境，不能把真实客户订单作为探针。

测试输入应包含可观察的对象引用来源：详情接口、列表返回、邮件通知、隐藏表单字段、附件名和队列结果。OWASP 指南建议用不同授权范围的多个账号验证访问检查，因为 IDOR 不限于 URL 中的连续整数。受控交换测试并不是鼓励探测陌生服务；它只适用于有授权的系统和测试数据。为避免测试本身扩大影响，先限制主体、对象、操作、环境和回滚办法，尤其是删除、退款等有副作用的动作。

测试还需检查状态变化：对象从 A 转给 B，成员被移出租户，管理员降权，访问令牌过期，任务排队后权限被撤销。结果应取决于业务规则中指定的授权时点。若团队选择任务创建时授权，应保存可审计的授权决定及其有效范围；如果选择下载时再判，则下载服务必须能恢复当前主体和对象关系。不能让任务执行器只凭可伪造的请求字段信任租户上下文。

最后，要让拒绝可归因但不泄密：审计事件可记录主体内部标识、目标类型、租户范围、动作、策略版本和拒绝原因代码，并限制访问日志的权限和保留期。外部错误信息可合并“不存在”与“无权”的场景以减少对象探测，但内部观测仍应区分，便于发现漏检和权限漂移。OWASP 授权指南要求默认拒绝、每次请求验证并定期复核权限；这些要求说明验收不是一次性的“UUID 已换好”，而是随新增入口和权限变更重复执行的治理工作。

这篇测试矩阵只是建议，本文未运行 API、数据库策略或云存储测试。实际验收应保存执行版本、主体及授权范围、对象与动作、请求/响应摘要、预期与观察结果，以及失败后的清理和回滚记录。以此区分“代码中看到了检查”“测试证明某些路径拒绝”和“所有生产入口符合授权契约”，不要把前一种证据说成最后一种结论。接下来可对照多租户隔离与对象作用域检查缓存键和共享分发路径；该内链主题涉及缓存边界，不应被误读为 IDOR 专题。
