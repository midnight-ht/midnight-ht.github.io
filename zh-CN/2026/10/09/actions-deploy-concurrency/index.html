两次发布交叉执行：并发组该锁分支还是环境？

部署并发分组应对应共享环境，取消任务不能替代状态核验，也不能默认当作完整发布队列。

正文

两个工作流如果写入同一个环境，并发控制应围绕该共享环境设计，而不是各自只锁自己的分支。取消旧任务也不等于撤销已经写入的状态，发布结束仍要核对实际运行版本。以下讨论 GitHub Actions 的工作流设计，未执行并发部署实验。

分支不同，资源可能相同

假设 dev 和修复分支都能部署到同一个测试站点。如果并发组包含分支名，两者属于不同组，仍可能同时修改同一目标。若较旧任务最后上传制品，新提交的工作流即使显示成功，网站也可能被旧版本覆盖。问题在共享资源归属，而不在工作流名字是否不同。

GitHub 并发控制文档说明可在工作流或 job 层配置并发组，也说明运行与等待任务的处理规则。默认等待行为不应被想当然理解为保留所有发布的完整队列；需要队列能力时应按当前文档核对选项、数量限制与顺序语义，不能假设提交顺序就是执行顺序。

先区分只需最新与必须逐个执行

普通预览站点可能只关心最新提交，允许取消旧的等待或运行任务。数据库迁移或有外部副作用的发布则未必能够中途停止。把整个流水线统一设为新任务到来就取消，可能在迁移完成而应用尚未更新时留下中间状态。

候选方案是把可取消的构建与需要受控完成的环境变更区分开。环境变更阶段使用稳定环境标识协调互斥，并让部署者在开始前确认待发布版本仍符合策略。是否取消、是否排队以及怎样处理过时制品，都应写成可审查的规则，而不是由 YAML 表达式偶然决定。

同一环境如果可以由多个仓库或外部工具修改，还要确认并发组的作用范围。工作流内的锁不能自动协调所有系统，可能需要部署平台提供统一排队或版本仲裁。不要因为一个仓库的运行列表很整齐，就断言环境没有并发写入者。

取消之后留下什么证据

取消标记说明任务执行受到中断，不证明上传、数据库写入或外部部署请求已经回滚。操作若返回结果未知，应先查目标平台回执与实际状态，避免马上重复发布放大不确定性。部署过程可以保存提交标识、制品摘要和平台部署标识，帮助判断哪一步真正完成。

发布验收应连接工作流版本和环境版本。页面健康返回成功只说明服务能响应，最好还能核对版本标识与关键内容。如果目标是最新 dev，观察到的版本必须对应这次选择，而不是任意一个可工作的旧构建。回滚也要明确它选择了哪个已经验证的版本。

受控演练可以安排一个慢构建和一个快构建，观察等待、取消与最终部署结果；再检查变更阶段中断后的恢复路径。本文未执行这些演练，不能以描述代替可靠性证明。记录应保留真实开始、结束和平台回执，而不是补写想象中的时序。

是否所有测试都应该串行？不必。只有竞争同一共享资源的阶段需要协调，独立测试仍可并行。先列出环境的全部写入入口，再给每个入口明确互斥责任。后续验证方式可结合制品与回滚核验，不要把绿色工作流当作线上版本的唯一依据。
