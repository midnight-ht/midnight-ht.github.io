分支锁住了，为什么同一测试站还可能被旧任务覆盖？

GitHub Actions 并发组只协调同仓库中使用同组的运行。按共享环境选择组键，再区分默认 pending 替换、取消运行和 queue:max 的有限队列语义。

正文

核心要点

  • dev 与 hotfix 即使分别按分支分组，只要都能写同一测试环境，仍可能交叉部署；组键要反映真正被争用的资源。
  • 默认并发组最多一个运行中和一个 pending；新运行替换旧 pending，cancel-in-progress 还会取消同组当前运行。
  • queue: max 最多容纳 100 个 pending，队满后的新任务会取消；排序按开始等待组的时间，不是工作流派发时间。
  • 并发组只协调本仓库里主动使用同名组的运行；取消任务不等于撤销已经写入外部系统的状态。

分支名并不总是发布锁的正确键。dev 与 hotfix 如果都能写入同一个测试站，按分支建立两个并发组就把它们分开了，GitHub Actions 不会替这两个组判断它们正在修改同一环境。先确定哪些运行会写同一目标，再决定要允许“只保留最新版本”，还是每个获准的部署都必须依次执行。

以下说明依据 2026 年 11 月 26 日查阅的 GitHub Actions 官方并发文档。假设中的站点和任务时序只是用于解释，不代表实际实验；本文没有运行 workflow、取消任务或部署环境。

并发组实际互斥的对象是什么？

可以在 workflow 或 job 上设置 concurrency。GitHub 文档说明，同一仓库里使用同一个并发组的 workflow 或 job，同一时刻最多只有一个运行中。并发组名称可以是字符串，也可以由允许的上下文表达式组成。作用范围是“使用这个组名的运行”，不是自动发现同一云环境的所有写入者。

这一区别决定组键怎么写。比如表达式把分支 ref 拼进组名，dev 与 hotfix 就各有自己的组。这样适合限制每个分支重复构建，或让同一分支只保留较新预览；它不适合单独保护一个被多条分支共同写入的测试环境。反过来，如果所有目标是 staging 的部署都使用稳定的 staging 组，它们才会互相等待或替换。

组名不区分大小写，因此 staging 和 Staging 实际是同一个组。多个 workflow 也可能使用相同组名；GitHub 文档提醒，若本来不希望它们互相取消，应让组名包含 workflow 身份。设计时必须做一个反向判断：两个流程若同写 staging，应该共享组；两个流程若虽然同属一个仓库但目标不同，则不该因偶然相同的名字而互相等待。

并发组不是跨仓库锁，也不会阻止手工控制台操作、另一个 CI 平台或没有声明该组的 workflow 写入环境。若几个仓库共同管理一个共享环境，需要一个覆盖这些写入者的部署平台队列、环境租约或版本仲裁规则。GitHub 并发组只能解决参与同一仓库同一组的运行之间的协调。

默认行为为什么不等于完整发布队列？

同组已有一个运行时，新任务会进入 pending。默认最多保留一个 pending；再来一个新任务，会取消旧 pending 并由新任务替代。若设置 cancel-in-progress: true，还会取消同组当前运行中的任务。这个默认策略天然适合“旧预览不再值得发布，尽量推进最新提交”的需求，但不等于每一个已获准的版本都会发布。

GitHub 提供 queue: max 来允许更多 pending 运行等待，最多 100 个。达到上限后，再到达的运行会被取消。排队顺序按运行开始等待并发组的时间采用 FIFO，不保证按 workflow 被派发的时间排序；任务真正到达并发等待点的时间可能不同。queue: max 不能与 cancel-in-progress: true 组合，因为一个要求保留排队任务，一个要求取消正在执行的任务。

所以容量和交付承诺要一起看。若预览环境只需要接近最新的构建，默认单个 pending 的替换可能正合适；若每个迁移或外部副作用都必须完成，则不要把它们放进“新版本来了就取消”的整体流程。即使 queue: max 打开，100 个 pending 之后仍会发生取消，FIFO 也不代表按提交时间排序。需要不丢任务、严格排序或跨仓库串行时，应使用具有相应语义的部署系统，而不是把 Actions 的有限等待队列描述成永久消息队列。

组键该跟分支还是环境？

假设一个仓库有 dev 和 hotfix 两条分支，两者都部署到同一个 staging。按 ref 分组会让它们并行；稳定使用 staging 组则会让它们互斥。选择环境键的理由不是环境名称天然更安全，而是“同一共享目标只能有一个写入者”这一不变量需要被表达出来。若两个分支实际部署到隔离的 preview-123 和 preview-456，它们不应为了环境锁而串行。

再看两个 workflow：CI 预览和手工发布都能写 staging。如果二者的并发组故意相同，它们共享互斥；若只是为了命名空间避免意外取消，可以在组键里加入 workflow 名称，但这又会让两个流程不能互相保护 staging。不同诉求不能同时靠一个名字解决。应决定系统需要的是“每条流水线只串行自身”，还是“所有 staging 写入者共同互斥”。发布之前还要核对被选中的提交和制品摘要，避免等待期间另一个新版本让旧制品变得过时。

对只想保留最新版的预览任务，可以把允许取消的范围收窄到构建或临时预览阶段；对数据库迁移、不可逆外部调用等副作用，取消策略应按具体阶段判断。工作流显示 cancelled 只说明运行被取消，不能据此推断目标平台已经回滚。若部署请求返回超时或客户端失联，结果可能是未知而非失败；先查询平台部署 ID、目标版本和操作回执，再决定重试，避免两个操作者都把“没有看到成功”误当成“没有发生写入”。

一条假设时序会暴露什么？

假设慢任务 A 来自较旧提交，快任务 B 来自较新提交。两者按分支键分组，而分支又不同，于是可同时运行。B 先把新页面部署成功，A 随后才上传旧页面。B 的 workflow 仍然是绿色，但 staging 最终显示 A 的版本。这个例子没有真实运行记录；它说明“workflow 成功”和“环境等于选定提交”是两个不同断言。

若两者改用共享 staging 组，A 运行时 B 会等待。但若默认 pending 替换策略下又到来 C，B 可能作为旧 pending 被取消。如果每次更新都要逐个经过环境，单靠默认组仍会丢掉待执行项；改用 queue: max 后又必须考虑最多 100 个 pending、超额取消和按到达并发等待点排序。系统必须先定义产品承诺，再选语义：只要环境最终接近最新版本，允许替换；每个迁移都必须执行，有限队列可能不够；按批准次序发布，则要把批准顺序和目标制品身份存进独立记录。

发布并发要怎样验收？

先列出能写目标环境的所有入口：不同分支的自动部署、手工 workflow_dispatch、workflow_call 的复用流程、其他仓库和人工操作。给每个入口标出目标、并发组、是否可取消、外部副作用以及版本回执。若有写入者没有使用该组，它就不受这把锁约束。

在非生产环境可以安排假设中的慢 A、快 B 和第三个 C，观察 pending 是否被替换，启用 queue: max 后队列是否按开始等待时间前进，达到容量边界时新任务如何处理。再在写入请求发出后模拟 runner 取消或网络结果不明，检查系统是否能从平台回执恢复目标版本，而不是仅凭 workflow 状态重新派发。本文没有执行这组演练；这是一份待验证方案，不是已经证明的可靠性结果。

每次发布至少把提交 SHA、制品摘要、workflow run ID 与部署平台的目标版本对应起来。检查服务健康只证明它能响应，检查页面当前版本才能证明观察到的环境指向预期提交。与制品和回滚如何核对目标版本一起评审时，还要分开回答是谁负责互斥、谁确认制品身份、取消后谁判断实际状态。缓存来源风险另见缓存命中为什么不能证明发布可信。
