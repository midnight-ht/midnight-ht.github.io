链路上下文方便透传，为什么不能直接塞客户邮箱？

Baggage 的用途就是跨请求传播上下文；风险也来自同一机制。把传播、遥测存储、信任边界和个人标识分开设计，才知道邮箱会到哪里。

正文

核心要点

  • Baggage 是请求相关的键值上下文，通常沿出站请求传播；它与 span、log、metric 属性分开，写入遥测数据需要显式映射或处理器。
  • 入口 baggage 可以由请求方提供，且规范没有提供完整性证明；不要把其中的用户、租户或角色值当认证授权依据。
  • 在每个信任边界定义允许字段和清除策略，并验证自动埋点、手写客户端、重试和异步交接等实际传播路径。

Baggage 的便利来自跨服务传播，而客户邮箱的风险也来自同一条传播路径：自动埋点可能把请求头带到并非预期的下游服务。OpenTelemetry Baggage 是附着在分布式请求上的键值上下文，不是认证凭据，也不是天然的日志或 span 字段。是否允许传递某个值，要分别回答它会经过哪些服务、是否会离开信任边界，以及哪些组件会把它写入遥测后端。本文讨论的是设计边界；没有检查真实客户流量、SDK 配置或数据后端。

先把传播和存储分开

OpenTelemetry Baggage 文档把它描述为与上下文并存的键值存储，可跨服务和进程传递。文档也明确说，Baggage 与 span、metric、log 的属性没有自动关联；要让一个值出现在这些遥测属性中，必须读取并显式添加，或者使用语言实现中配置的 Baggage Span Processor 等处理器。因而，“请求头一路传下去”和“邮箱一定保存在 trace”是两种不同的数据路径，都要检查，不能用一个答案代替另一个。

入口收到请求后，传播器可以从载体提取上下文，并在后续出站请求中注入上下文。OpenTelemetry Propagators API把 Inject 和 Extract 定义为向载体写入、从载体读取值的操作；HTTP 请求头只是常见载体之一。Baggage 的规范定义了 baggage HTTP 头，并建议接收系统将它传给下游请求，也允许接收方按约定添加、更新或删除字段。这是协议能力和惯例，不是某个团队已开启自动传播的证明；语言 SDK、传播器组合、客户端拦截器和网格配置决定真实行为。

可把数据路径画成：外部请求进入网关，网关把请求交给服务 A；A 调用服务 B，B 再调用邮件供应商；服务 A 或 B 的仪器代码可能读取 Baggage 并附加到 span。每一条箭头都要问两件事：这个请求带了哪些头，观测代码又把哪些值复制进了遥测？若邮箱只在入口到 A 之间存在，它可能仍进入 A 的访问日志；若 HTTP 自动埋点将 Baggage 加到出站头，第三方接口也可能收到它。反过来，如果配置没有传播器或显式映射，Baggage 可能没有到达预想中的后端。安全评估需要依据实际组件而非“OpenTelemetry 默认如此”的泛化判断。

邮箱、关联 ID 和授权身份不是同一类字段

原始邮箱容易被人直接识别，通常可搜索、可复制，也会在错误消息、代理访问日志或调试导出中留下副本。把它放入可传播上下文，意味着要追踪每个消费者的访问权限、保留期、导出路径和删除责任。即使遥测后端限制了访问，数据仍可能先经过不受同一控制的服务或供应商。风险来自沿途复制和后续使用，不只来自“有没有在 trace 页面显示”。

把邮箱做哈希也不自动等于匿名。邮箱空间往往可猜测，稳定哈希可以跨请求关联同一个人；只要组织里还有可用映射或能尝试候选值，它仍可能构成可识别或敏感数据。哈希更适合被视为一种特定的假名化变换，需要说明密钥管理、作用域、轮换和授权查询，而不是通用脱敏开关。

随机的单次请求 ID 通常更适合在一次请求的服务链路中关联事件，但仍要定义由谁生成、入口是否覆盖客户端自填值、多久失效、是否被用户可见或写入长期日志。稳定的 account ID 或 user ID 能支持跨请求分析；OpenTelemetry 的概念文档也以用户标识说明 Baggage 可以帮助下游分析。这个例子说明机制可用，不代表原始个人标识在任意链路、后端和访问策略下都合适。它还可能带来高基数、长期关联和访问范围扩大的成本。

有限类别（例如经过业务校验的 plan_tier=standard）可能比邮箱更便于聚合，但前提是分类本身没有泄露不应暴露的信息，且入口值不能被任意覆盖。如果值影响价格、租户隔离或业务优先级，就不能把观测字段当权威来源。授权身份和资源权限必须来自已验证的身份及服务端策略；Baggage 可以被请求方提供、被中间件变换，也可能被下游删除，它不能证明某人是谁或该主体有何权限。

在信任边界做减法，而不是靠字段名称自律

W3C Baggage 规范提醒实现者，头部可能包含敏感信息；应用应避免在 Baggage 中放置机密数据，或确保跨越信任边界的请求不携带这些数据。它还要求评估头部滥用风险，并检查所有会发送 Baggage 的代码路径。规范中的通用格式限制包含最多 64 个条目、总长度 8192 字节的互操作要求；这些是格式/实现边界，不是隐私或安全上限。实际代理也可能设置更低的头部长度限制。

因此可以维护一份允许清单，而不是仅列出“绝对不能叫 email 的键”。每个字段应记录产生位置、业务含义、敏感级别、是否允许跨到第三方、是否允许进入 span/log/metric、责任团队和清除规则。策略按边界实施：入口只接受允许的键，内部服务可以按需要保留，发往外部供应商前再执行出口剔除。清除 Baggage 不必等于丢弃整次请求；如果出站操作确实需要邮箱，把它放在经过授权的业务请求参数或受控凭据通道中，而不是把整条请求上下文一并透传。

“只在某个网关删一次”也可能不够。后台任务从队列恢复上下文，另一个语言运行时用自定义 HTTP 客户端，重试逻辑重新构造请求，或服务网格单独转发头，都可能绕过其中一条清理路径。W3C 规范列出的修改能力允许增加、更新和删除键值，但删除策略仍须覆盖所有载体和客户端；规范不会替应用自动识别哪个字段是邮箱。

用一个可证伪的测试矩阵验证策略

下面是建议的验证计划，不是已执行的测试。先建立专用测试字段，例如 review_marker=synthetic-7f3，避免拿真实邮箱或真实客户 ID 演练。以受控请求从入口进入，分别触发同步 HTTP 调用、重试调用、队列任务和一个外部测试端点；在网关入口、服务内部、出站边界和遥测后端采集头部与属性。对每条路径写明预期：哪些内部组件应看到 marker，第三方出口是否必须剔除，哪些 span/log 可保存，metric 是否应完全不带高基数标识。

反例能检验策略是否只是配置表面正确：从客户端发送一个同名的伪造租户字段；让某个旧客户端绕过共享拦截器；让重试创建新的 HTTP 请求；使一个任务跨进程或跨语言继续；再检查出口头和可查询遥测是否出现 marker。还应检查畸形或超长头部如何被代理、SDK和应用处理。每次验证要固定组件版本和传播器配置，保留输入、出口、span/log/metric 的预期与实际差异。本文未运行这些测试，不声称已有策略阻止了泄露。

如果某次排障必须把请求关联到个人，优先让观测数据保存短期、范围明确的随机关联键，再由获准人员在受控业务系统中查询映射；这种方案仍需要访问审计、保留期和密钥管理，但能避免把原始邮箱复制到每个下游。若稳定标识确实不可替代，应记录为什么、谁可查询、哪些边界允许、如何轮换或删除，以及泄露后的处理流程。决定不是“永远不能传任何 user ID”，而是不同字段在不同边界有不同代价。

审查这类设计时，把“传播策略”和“遥测处理策略”列成两张表：前者逐跳记录提取、保留、修改、剔除；后者记录何时把 Baggage 变成 span、log 或 metric 属性以及相应的访问和保留边界。入口字段不能替代对象级授权；相关安全边界可结合对象权限与 IDOR检查。观测上下文解释一次请求经过了哪里，不应成为证明请求方有权访问客户资料的依据。
