节点 CPU 不忙，容器请求为什么仍然变慢？

Kubernetes requests 与 limits 作用不同，节点平均利用率不能替代容器限流、内存及请求排队证据。

正文

节点平均 CPU 利用率低，不能排除某个容器因自己的限制而变慢。排查时应把容器限流、请求排队和实际时延关联起来，同时区分调度用的 requests 与运行时 limits。下面依据 Kubernetes 当前资源管理文档分析 Linux 容器情形，没有采集真实集群指标或进行压测。

节点余量不等于容器没有边界

Kubernetes 资源管理文档说明调度器使用资源请求选择节点，CPU 限制通过限流执行，内存限制的处理方式不同。容器可能在节点仍有余量时触及自己的 CPU 上限。因此“机器不忙”不能独自推翻资源约束假设。

假设接口在突发并发下变慢，节点分钟平均曲线仍很低。短时尖峰、容器级配额和应用排队都可能被这条平均线掩盖。应缩小到具体工作负载、容器及时间窗口，并保留节点聚合与容器指标的区别，再判断请求耗时上升是否和限流同时出现，而不是直接从节点概览跳到修改所有服务配置。

请求与限制不能混成容量数字

requests 参与调度和资源分配考虑，limits 决定不同资源的运行边界。把两者设成相同值有时便于某类管理，但不代表适合所有应用；把请求设得过低也可能让调度结果与真实需要偏离。是否突发、如何共存以及集群策略，都需要进入容量讨论。

候选排查可以先保留实例数、容器资源配置、工作负载分布、请求延迟和队列长度，再观察 CPU 限流信息与内存事件。不同监控工具的口径可能不同，必须注明采样窗口和计数含义。不能把任意一个限流百分比直接换算成用户延迟增加多少。

内存问题也不能按 CPU 的逻辑解释。内存限制附近的终止、应用堆配置、缓存增长和临时文件都应检查。提高上限可能暂时推迟故障，却不解决持续增长。先确定是合理工作集还是泄漏假设，再安排对应验证，避免把资源配置当作一切异常的修复按钮。

调整之前先写预期变化

如果怀疑 CPU 约束，应预先写出调整后的观察：相似负载下限流减少、排队缩短、关键时延改善，同时没有把同节点其他工作负载挤入异常。若只有其中一条变化，应继续调查，不要在发布说明里提前写固定提速比例。

对延迟敏感与批处理任务，策略也可能不同。前者关心尾部时延和恢复速度，后者可能接受较长完成时间以控制共享资源。不要把一次批处理的资源配额复制给在线接口，再用平均吞吐解释用户超时。容量选择应与业务结果绑定。

验收可以在可控环境安排稳定负载、短时突发与资源约束变化，保留配置和前后指标。本文未运行这类实验，不能宣称某个 requests/limits 组合已经可用。真实生产调整需要明确回退条件，并观察其他租户或工作负载受到的影响。

是否直接取消 CPU limit？没有环境与策略资料，不能给出统一答案。应评估共享、公平性和平台约束，再选择限制方式。先从一个明确受影响的容器建立证据链；业务指标的定义可参看从用户结果设计 SLO，避免只把机器曲线变绿当作恢复。
