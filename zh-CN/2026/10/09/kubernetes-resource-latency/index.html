节点 CPU 不忙，容器请求为什么仍然变慢？

节点平均 CPU 低不代表容器没有被自己的 CPU limit 限流。把请求时延、容器用量、限流周期、requests 与内存事件放到同一时间线，再决定是否调参。

正文

核心要点

  • requests 参与调度容量判断，CPU limit 是容器运行时上限；节点空闲不能说明每个容器都能使用那部分空闲 CPU。
  • 先按工作负载、容器和相同时间窗口核对时延、排队、用量与 throttling，再区分配额限流、节点争用和应用自身等待。
  • CPU 限流与内存 OOM 是不同机制，单独增加 limit 或删除 limit 都不是无需验证的通用修复。

节点面板显示 CPU 利用率很低，容器里的接口仍可能排队变慢，因为节点总量和单个容器可用量不是同一个边界。在 Kubernetes 中，requests 参与调度器对可放置容量的计算；Linux 上的 CPU limits 则由内核按容器限制执行限流。排查时要把业务请求时延、队列、容器 CPU 用量和限流证据对齐到同一时间窗，不能用节点分钟平均值替代这些数据。本文核对的是 Kubernetes 当前 v1.37 文档，所有故障场景均为分析示例，没有访问集群或运行压测。

先拆开节点、容器和时间窗口

“CPU 不忙”通常来自一条聚合曲线。它可能按节点所有核数归一化，也可能按一个采样窗口求平均；即使整个节点平均只有少量用量，单个容器仍可能在短时间内用完自己的配额，或者在共享 CPU 的任务之间等待。调度器也不承诺把图表上未使用的容量立即变成某个容器的专属资源。节点整体、Pod、容器和单个进程的统计要分开看，采样频率也必须和接口时延尖峰对应起来。

官方资源管理文档明确区分 requests 和 limits：调度器按资源请求总量判断节点能否容纳 Pod；实际运行时，如果节点有余量，容器可以超过自己的 request 使用资源；Linux CPU limit 由内核限流执行。这个机制解释了两个看似矛盾的现象：request 低会影响调度时的容量估算和共置关系，而 limit 低会在运行时限制突发 CPU。二者都可能造成“节点看着有空闲，接口却卡住”，但证据和处理方式不同。

先把时间线缩到一次真实的时延上升：哪一批请求的 p95/p99 开始恶化，工作负载当时部署了多少副本，容器是否集中在少数节点，CPU 限流的计数是否同时变化，队列深度或并发数是否先于延迟上升。若容器 CPU 用量上升到限额附近、throttling 同时增加且请求排队增长，配额限流是一个值得验证的假设；若用量并不高、队列却加深，等待可能在锁、线程池、连接池、磁盘或远程依赖。相关性缩小排查范围，但不能仅凭两条曲线断言因果。

requests 和 limits 各自回答什么问题

requests.cpu 是调度与资源分配的请求值，不是“应用只能用这么多”的硬上限。官方 CPU 配置示例让容器 request 为 500m、limit 为 1 CPU，并让进程尝试使用 2 CPU；文档说明在它有更多 CPU 需求时会被 throttling，容器使用不会超过 limit。这个示例展示了 request 与 limit 不相等时的突发空间，但不是所有集群都应复制的默认组合。实际请求要考虑负载波动、节点分布、其他租户和平台策略。

可把 request 理解为调度器在安排 Pod 时采用的容量账本，把 CPU limit 理解为容器运行期间的限制。request 设得明显低于长期需要，可能让调度器把更多工作负载放在同一节点，使节点争用变得更常见；limit 设得过紧，则即便节点仍有空闲，某个计算密集的容器也可能被限制。反过来，提高 limit 会允许更长的突发，但在节点资源被其他任务使用时，不能保证这些 CPU 一定可用；同时，也会改变同机工作负载的竞争条件。

因此调查面板至少要同时保留四层：节点的 CPU 使用与可分配容量；Pod 的 request/limit 和副本分布；目标容器的用量与 throttling 指标；应用侧队列、并发、请求延迟及依赖等待。不同监控系统的计数单位和窗口定义可能不同，先确认“节流周期”“节流时长”或“节流比例”具体代表什么。一个限流百分比不能直接换算成延迟增加百分比，因为请求可能是 CPU 密集，也可能大部分时间在等待 I/O。

用对照场景区分限流与其他等待

设想一个假设的 API：流量突然增加，实例数还没有扩上来，序列化和规则计算消耗 CPU。若容器 limit 较低，短时间内线程可运行的 CPU 时间受约束，队列继续接收请求，用户看到的尾延迟上升。与此同时，节点聚合平均可能因为采样粒度较粗或其他节点空闲而保持偏低。这个情形应在目标容器和同一时间窗口里看到限流与排队变化，调高 limit 后才有可能改善，但还要确认节点是否真的有未分配 CPU、邻近工作负载是否受影响。

再看一个反例：接口延迟升高，容器 CPU 用量没有接近 limit，throttling 也没有同步增多，但数据库连接池排队变长。此时调大 CPU limit 不会增加数据库连接，也不会缩短等待；如果它允许额外并发进入应用，反而可能将更多等待请求压向数据库。另一个不同的情形是节点 CPU 已经争用：提高容器 limit 只提高上限，不创造节点 CPU；request 太低则可能让调度时低估真实需求。三类问题需要各自证据：容器限流、节点争用和应用依赖/队列阻塞不能用单一“CPU 百分比”混为一谈。

最小化试验应先固定一个明确工作负载和可回退的配置。记录当前 request、limit、实例数、节点位置和版本；对照一组相近请求量的稳定负载与短时突发，观察业务时延分位数、队列长度、容器用量、throttling、节点剩余量和同节点其他服务的变化。若限流下降但 p99 不变，CPU 限制可能不是主要瓶颈；若 p99 改善却让同节点另一个服务出现超时，调整只是把成本转给了邻居。需要避免同时改副本数、缓存或应用线程池，否则无法判断哪项变化带来效果。本文没有运行这样的实验，所列结果是应观察的信号，不是已测结论。

别把 CPU 限流和内存 OOM 当成同一种限额

CPU limit 的典型后果是被限制执行速度：进程仍然运行，只是可获得的 CPU 时间受边界影响。内存 limit 的执行则不同。官方资源文档说明 Linux 内核可能在内存压力出现时触发 OOM kill，超出 limit 不一定立即被杀；Pod QoS 页面还说明资源压力驱逐与容器超过 limit 是不同路径。观察到重启时，应查看容器状态、Last State、OOMKilled、事件和重启次数，而不是把重启直接归因于 CPU throttling。

内存增长还要区分应用堆、缓存、页缓存、临时文件和本地代理等组成。提高 memory limit 可能给正常工作集留出空间，也可能仅仅推迟泄漏或增长失控；CPU 限流图无法判断哪种情况。反过来，如果应用只是被 CPU 节流，盲目加内存也不会缩短计算时间。资源调整前先认清信号所属的机制，防止一次参数变更掩盖真正故障。

选配置时把目标、代价和回滚写在一起

面向延迟敏感的在线服务，团队可能愿意为更准确的 request、适当的 CPU 突发空间和可解释的扩缩容付出节点容量成本；批处理任务则可能更关注总吞吐与资源公平，容忍较长的完成时间。若平台要求强隔离，CPU limit 可能是组织策略的一部分；若采用共享集群且希望任务利用闲置 CPU，是否配置上限又要与租户公平和节点管理策略协商。Kubernetes 文档介绍的是机制，不会替业务定义可接受的 p99、成本或隔离级别。

调整前先明确要改善的用户结果，例如某个接口的 p99 或队列清空时间，同时定义不可接受的邻居影响和回滚阈值。分阶段修改单个 Deployment 的一个容器，使用相同的观测窗口比较基线与试验组；不要把 CPU 使用率下降当成成功，也不要用一次无流量时的低延迟证明配置有效。出现节点争用、其他服务回退或目标请求没有改善时，回滚并继续检查工作负载需求、并发和依赖瓶颈。对于 SLO 的业务结果定义，可参看从用户结果设计 SLO；真正恢复的是用户请求，不是图表颜色。

实际操作时，可以从 kubectl describe pod 查看 requests、limits 和最近终止状态，再对照目标容器、节点及应用指标；命令输出受集群版本、运行时和监控采集配置影响。每项数据都要记录命名空间、容器名、时间窗、单位和查询范围。若只能拿到节点均值，就把结论保持为“尚未定位”，不要把它包装成容器已得到充分 CPU 的证据。找到特定容器同时间窗内的限流、排队与请求时延关联后，才有依据提出一次小范围配置试验。确认资源变更后的发布安全和回退方式，也应纳入发布并发控制的检查链。
