数据库提交成功了，通知为什么还是可能丢？

用 PostgreSQL 18 事务发件箱保存业务变化与交付意图，再设计重复投递、事件顺序、relay 接管和积压处理。

正文

核心要点

  • 一个数据库事务只能原子地保存本地状态和待交付意图，不能把外部副作用并入提交。
  • 外部发送成功但确认未写回时可能重发，事件 ID 与消费者幂等要贯穿交接。
  • 选择轮询或 CDC 时，还需明确排序范围、毒消息处理、积压监控和清理条件。

订单和通知走两套提交边界：PostgreSQL 已确认订单提交，进程却可能在发出通知前退出。把两次调用排得再近，也不会让消息服务加入数据库事务。事务发件箱的作用，是把业务变化与“需要交付什么”的记录放在同一次本地提交里；它没有替外部系统提供全局恰好一次，也没有替团队定义重复、顺序和积压如何处理。以下依据 PostgreSQL 18、Debezium 文档和事务发件箱模式资料讨论设计，不代表本站运行过消息系统或验证过投递表现。

两个成功调用为什么仍有丢失窗口

假设结账服务先把订单标记为已付款，再向消息代理发布 OrderPaid。如果进程在数据库提交后、消息发送前退出，数据库里付款状态已经持久化，代理却没有事件。把顺序交换也不安全：先发消息、后提交数据库，提交若失败，消费者会看到一个并不存在的付款。两段操作各自成功或失败，不会因为写在一个函数里就有共同的原子边界。

PostgreSQL 18 事务教程把事务描述为一组全有或全无的数据库操作；COMMIT 使本事务的更改一起对其他会话可见并持久化。这个保证只覆盖参与该事务的数据库更改。事务发件箱模式把业务实体和待发消息一起保存，再由独立 relay 发送。发件箱是架构模式，不是 PostgreSQL 自动替应用创建的消息队列；它提供的是本地状态与交付意图的一致性。

把业务状态和交接意图放在一起

以假设的订单付款为例，命令在一个数据库事务内更新订单并插入事件记录。事件可包含稳定的 event_id、对象类型和对象 ID、事件类型或版本、发生时间，以及最少必要的负载。提交成功后，两条记录要么一起存在，要么一起回滚。这里的关键不是在订单表旁边再添一个随手更新的标记，而是让所有会产生外部事件的业务路径都通过相同的事务边界写入待交付记录。

事件负载要回答一个业务问题：它表达“付款已完成时发生的事实”，还是“消费者处理时订单现在的状态”？前者通常需要保存足够的事件快照，避免工作者稍后读到已退款订单后把旧付款事件改写成另一个含义；后者则应明确它是一条状态通知，消费者要按对象 ID 回查当前值。两种语义都可能成立，但若不作选择，重试和延迟会悄悄改变事件含义。只复制整行也有成本：个人数据会扩散到消息、日志和保留系统，字段演进也会影响消费者。

Debezium Outbox Event Router 文档展示了一类可配置的实现：默认结构含唯一事件 ID、aggregatetype、aggregateid、事件 type 和 payload；其中事件 ID 可作为消息头，用于去重，aggregateid 可作为消息 key 以保持 Kafka 分区内的相关顺序。文档也说明该路由器预期 outbox 变更为 INSERT，不应把它当成可随意更新状态的普通工作队列表。这个结构是该工具的默认约定，不是所有发件箱必须照搬的数据库模式。

外部发送成功以后，重复才真正出现

Relay 取出事件并成功写入代理后，可能在写回“已交付”状态前崩溃。恢复者只看到本地记录仍未确认，无法仅凭数据库行知道远端是否已接收，于是可能再次发送。即使 relay 使用租约或锁保证同一时刻通常只有一个所有者，也不能消除“外部已成功、确认尚未保存”的窗口。分布式系统里，等待超时也无法区分请求丢失、响应丢失和对方已经完成。

因此事件 ID 必须贯穿发送和消费。若消费者的业务写入和去重标记可以在同一数据库事务中提交，event_id 可有唯一约束：已处理过的重放不重复执行本地变化。若消费者要发邮件、调用支付或执行其他外部效果，本地去重记录也无法自动撤销或阻止另一系统的副作用；只有当外部服务支持幂等键或按请求 ID 查询结果时，才能把该能力纳入协议。否则产品必须接受重复、设计人工核查，或改变业务流程，让用户看到可重复但可识别的状态。

对于超时后的“结果未知”，不要盲目重做原命令。把查询状态和重新发送分开：先用事件 ID、对象 ID 或外部请求 ID 查找已有结果，再按协议决定重试。消费者若先写去重表后执行外部调用，调用前崩溃会把事件误标为完成；若先执行外部调用再写去重表，崩溃则可能产生重复。没有共同提交能力时，顺序选择只能把风险放到某一侧，不能让风险消失。

顺序、多个工作者和积压也属于交付协议

同一订单可能先产生 OrderPaid，再产生 OrderRefunded。若后一个事件先到，消费者只看最终状态可能处理出错误通知。先定义排序范围：是全局、每个租户，还是每个订单？全局顺序会让一个慢事件拖住无关对象；按对象排序减少相互等待，却不能自动满足跨对象业务约束。Debezium 文档把 aggregateid 用作消息 key，是为了将相关消息路由到同一 Kafka 分区；具体顺序保证仍受 broker、producer 和 consumer 配置影响，不能只看 key 字段就承诺端到端顺序。

轮询数据库的 relay 与读取事务日志的 CDC 解决同一交接目标，但值班责任不同。轮询较容易从一张状态表看到待办、重试次数和最后错误，也要设计领取并发、扫描索引、清理保留与查询压力。CDC 能按数据库变更捕获事件；Debezium 提供 outbox router 转换，但还要维护 connector、日志保留、偏移量、schema 兼容和恢复积压的能力。已有可靠 CDC 平台且团队会运行它时，日志读取可能合适；规模小、希望由应用服务持有发送和重试逻辑时，轮询可能更直接。两者都不会自动定义业务去重和毒消息处理。

长期失败不能只靠无限重试掩盖。要有可观察的待处理数量、最老事件年龄、失败类型、接管次数和死信或人工处理入口；重放时保留原 event_id，明确是否跳过已完成消费。清理只能发生在保留期限、消费者恢复能力和审计需求都允许之后。删除太早会失去重放依据，永不删除则会让存储与查询成本持续增长。

怎样测试交接，而不是只测试事务

验收可按时间窗口注入故障：事务提交前退出，确认订单与 outbox 同时回滚；提交后、relay 获取前退出，确认新 worker 能接管；代理接收后、确认写回前退出，确认消费者按事件 ID 识别重放；并发 worker 领取同一待办时检查是否出现不可接受的并行副作用；再让一条毒消息持续失败，确认它不会让其他对象的事件无限饥饿。每一步都需定义从数据库、代理和消费者哪一侧读取证据，测试环境中真实执行后才能填入通过结果。本文没有运行这些测试，也没有给出吞吐或延迟数据。

结账命令本身还可能被客户端重试，形成两个不同事件；发件箱只能保存实际写入的事件，不能替 API 去重。应先确定业务请求幂等键如何映射为稳定事件身份，再处理 relay 的重复投递。相关边界可结合业务幂等契约审查；PostgreSQL 本地事务的原子边界，可参见PostgreSQL 跨行不变量与完整事务重试。只有当团队能回答谁会接管、重复如何识别、顺序按什么范围成立、旧事件何时可清理，发件箱才不只是增加了一张“待发送”表。
