两个人都保存成功，为什么一个人的修改消失了？

用 If-Match 阻止旧版本静默覆盖：从强 ETag 和原子条件更新，到 412 冲突后的草稿恢复。

正文

核心要点

  • If-Match 表达写入依赖的当前表示版本，RFC 9110 要求使用强比较；星号只检查资源存在。
  • 版本条件必须落在同一次持久化更新中；单独先查再无条件写仍有竞态。
  • 冲突响应不会保存本地草稿；本文示例未在真实应用或数据库中执行。

设想两个人先后保存同一份配置：服务端返回了两次成功，最后却只剩后一份旧表单。问题不是 HTTP 少一个状态码，而是写入请求没有说明它基于哪个版本。防止这种静默覆盖，需要让客户端带回读取时的强 ETag，由服务端验证 If-Match，再把版本条件和数据更新放进一个原子写入。If-Match 能表达“只有我读到的版本仍是当前版本才写”，但它不自动保留未提交的输入，也不会替代数据库竞争控制。下文的配置场景和 SQL 形态都是设计示例，没有在应用或数据库中执行。

两次成功怎样覆盖一次修改

假设一份告警配置最初是版本七，字段包括接收人和阈值。甲和乙几乎同时读取完整配置。甲把接收人从值班组改为新同事并保存；乙只想把阈值调高，却把浏览器里那份旧版本七的完整对象提交。若服务端按“最后写入覆盖整行”处理，甲的请求和乙的请求都可以得到成功响应。数据库最终留下乙提交的阈值，同时把接收人还原成旧值。乙并没有主动撤销甲的编辑，系统却把这个结果当成正常保存。

这个场景依赖两个条件：客户端基于旧状态提交，而服务端允许完整旧表示无条件覆盖当前状态。如果接口只提交需要改变的单个字段，冲突范围会不同；如果字段之间有业务约束，局部更新也仍要校验组合。这里讨论的核心不是“并发请求一定会丢数据”，而是服务端不知道这次写入的依据已经过期。

HTTP 成功状态只说明服务器按接口语义接受或处理了请求，不代表用户期望的所有修改都保留。监控只看 2xx 比例，可能把数据覆盖当成健康流量。要观察这种错误，需要把版本冲突、被拒绝的旧写入和最终业务状态纳入日志、指标或审计；但审计发现问题不能替代写入时的保护。

ETag 是表示校验器，If-Match 是写入前提

ETag 是服务端随表示返回的实体标签。客户端在读取配置时保存它，后续更新时把该标签放入 If-Match。RFC 9110 第 13.1.1 节规定，If-Match 针对目标资源的当前表示进行判断，通常用于阻止多个用户代理并行修改造成的意外覆盖；服务器在执行方法之前评估这个条件，条件为假时不得执行请求方法，并可以用 412 Precondition Failed 表示条件失败。

强比较是 If-Match 的要求。RFC 9110 第 8.8.3.2 节规定，两边都不能是弱标签，且标签内容必须逐字符相同。因此，读取响应如果给出弱 ETag，就不能把它当成可用于 If-Match 的精确版本令牌。对强校验器的变化条件，RFC 9110 第 8.8.1 节进一步规定：只要 GET 响应中可观察到的表示数据发生变化，标签就必须改变。标签可以来自严格修订标识或表示数据摘要；若同一资源经过内容协商会产生不同表示，校验器还应区分它们。强 ETag 不能只是看起来像版本号的字符串，它必须对客户端实际读取的表示具有一致含义。

表示与数据库行并不总是一一对应。一个页面可能由多个表、计算字段、权限过滤或内容协商组合而成。若 ETag 只根据主表的版本列生成，但另一个表的变动会改变客户端正在编辑的表示，那么标签可能没有随相关内容变化，If-Match 就会放行本该冲突的更新。反过来，若表示包含每次请求都会变化的非业务字段，标签持续变化也会制造没有实际编辑冲突的拒绝。团队需要先定义“哪些变化意味着客户端基于过期状态”，再决定标签生成依据。

缺少 If-Match 时应该返回什么？

应由端点契约决定：如果资源必须基于读取版本修改，就要求客户端带条件；如果为旧客户端暂时兼容无条件写入，就明确迁移期限并监测仍未升级的调用。RFC 6585 的 428 Precondition Required 是可选状态，可用于要求条件请求，但标准没有要求所有服务器一律返回它。If-Match 的星号只表示资源存在，不表示客户端读到最新版本。缺少条件、版本不匹配和资源不存在应有可区分且不泄露权限信息的处理路径；状态码之外，客户端还需要重新读取和安全重提的协议。

先查版本再写，竞态仍然存在

一种常见但不够的实现是：应用先读取当前版本，发现还是七；随后再发出一个不带版本条件的 UPDATE。甲乙两个请求可能都在版本七时完成检查，然后先后覆盖整行。虽然应用代码“检查过版本”，检查和写入之间仍留着时间窗口。并发控制的关键不是多写一次 SELECT，而是让目标行标识与预期版本共同成为实际写入条件。

用一组假设请求把完整路径走一遍：甲和乙都对配置资源 42 执行 GET，响应的 ETag 是版本七。甲先提交 PUT，并发送 If-Match 对应的版本七；服务端确认当前标签仍相同，原子保存甲的接收人修改并返回新 ETag 版本八。乙随后发送同样基于版本七的 If-Match。因为当前表示已是版本八，服务端不执行乙的旧写入，并按接口契约返回 412。乙的阈值修改仍保存在浏览器草稿中，用户比较版本八后再决定怎么合并。这是设计示例，不是抓取到的真实网络日志。

以 PostgreSQL 18 为例，可以把下列形态作为设计示意：根据资源 ID 和期望版本执行条件 UPDATE，同时把版本加一，并只提交请求中的已验证字段。若更新结果是一行，表示该条件命中了一个当前版本；若零行，则没有任何行满足这个条件。PostgreSQL 的 UPDATE 文档说明 WHERE 只更新条件为真的行，并给出实际更新行数；Read Committed 文档进一步说明，并发更新时后一个更新会等待前一个事务结束，再对更新后的行重新检查 WHERE。把版本检查写进同一 UPDATE，才能利用这个比较和写入的原子边界。

这个设计仍需要和实际应用配合。资源 ID、租户范围、授权检查与版本条件必须按一致顺序处理；不能因为某个版本不匹配，就把用户无权访问的资源是否存在泄露出去。零行可能对应版本冲突、记录不存在、租户不匹配或权限拒绝。对外的响应不能仅凭“影响行数为零”就随意区分这些原因。应用内部可以记录更细诊断，面向调用者则按权限与信息泄露策略决定是否合并响应。

一个多表业务也不能因为主记录的版本匹配就自动获得整体原子性。若保存配置还要更新关联规则、审批项或独立表中的字段，事务要覆盖哪些状态、如何锁定和验证，需要结合业务不变量决定。PostgreSQL 的隔离级别提供不同并发保证，但更严格的隔离并不会自动定义冲突后应该让用户看到什么，也不会替接口设计缺失的版本前提。先列出需要共同成立的约束，再选择事务范围和隔离级别。

412 之后怎样保住用户正在编辑的内容

对乙而言，412 不意味着表单应该清空。客户端应该把尚未提交的字段保留为草稿，重新读取当前服务端版本，并说明哪些内容发生了变化。用户可以比较两份值后选择保留、放弃或合并。若只有接收人和阈值两个互不依赖字段，界面可能提供字段级合并；若一个字段的含义依赖另一个字段，自动合并就可能拼出一个从未被业务允许的组合。

直接重新 GET 一份最新 ETag，然后把原来的完整请求再发一遍，是常见的失败路径。这样做确实绕过了旧版本条件，但也同时绕过了提醒用户甲已经保存过接收人修改的机会。只有当服务端能证明同一变化已经应用、且请求的业务语义确实可以重放时，才有理由返回成功或重试；RFC 9110 对“似乎已成功应用”的状态变更请求保留了有限的成功响应空间，不能据此把任意过期更新自动重放。

对没有带 If-Match 的更新，接口同样需要给出稳定行为。新端点可以要求条件写入并拒绝缺失版本的调用；旧端点若要兼容，必须识别哪些客户端仍在无条件写，并为迁移期设定可观测的边界。长期允许一部分写请求不带版本前提，相当于只保护遵守条件契约的调用方，不能宣称整个资源已经避免丢失更新。

怎样验收这条并发保护

一个能暴露问题的验收序列是：创建配置版本七，甲乙两个客户端分别读取并取得同一个强 ETag；甲先提交变更并获得成功；乙随后带旧 ETag 提交。预期结果是乙的旧写不能覆盖甲的状态，服务端返回所定义的冲突响应，而客户端仍保留乙的未提交草稿。随后乙读取版本八，明确比较或合并后再提交，版本推进到九。这个序列同时检查了协议前提、服务端比较、持久化状态和前端恢复。

还要做几个反向检查：缺少 If-Match 时是否按端点策略拒绝；弱 ETag 是否被错误接受；星号是否被误解为“版本相同”；两个请求同时到达时数据库是否只允许一个过期版本成功；资源删除后旧请求怎样处理；读写表示因权限过滤或内容协商不同，标签是否仍有清楚含义；没有权限的调用是否能从冲突响应推测资源存在。若用零行更新判断冲突，还应在隔离的测试数据中区分版本不匹配与资源不存在等内部状态。

本文没有运行并发客户端、数据库或 ORM 测试，SQL 仅用于说明条件应该落在写入语句中。实现团队应按实际数据库、驱动、事务隔离、缓存与重试逻辑补充集成测试，保留操作顺序和数据快照证据，而不是只验证接口返回了 412。对复杂协同编辑，If-Match 适合识别基于旧表示的写入，不负责字符级合并、操作排序或多人实时协同算法。

版本前提与业务幂等的职责也不同：前者回答“我读到的资源还是当前版本吗”，后者回答“这是同一次业务意图的重试吗”。编辑接口可能需要两种保护。关于后者的键作用域、事务和外部副作用边界，可参阅超时与业务幂等。
