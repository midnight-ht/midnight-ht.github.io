慢查询先加索引？先看估算行数错在哪里

先沿 PostgreSQL 计划树定位最早的估算行数偏差，再判断统计信息、查询形状或索引是否是正确修复。

正文

核心要点

  • rows 是计划节点预计输出的行数，不等于扫描行数；actual rows 在多次 loops 时通常显示每次执行的平均值。
  • 同表相关谓词可能需要刷新统计或扩展统计；PostgreSQL 的扩展统计目前不能修复 join 的选择率估算。
  • EXPLAIN ANALYZE 会执行语句，且常规计时不覆盖结果发送到客户端的网络时间；必须记录采集边界。

慢查询不等于缺索引。先定位计划树里最早出现的明显行数偏差，再判断它来自过期统计、同表字段相关性、查询形状还是连接估算；只有确认访问路径本身是主要成本后，索引才是候选方案。本文以 PostgreSQL 18 为明确基线，并核对了 PostgreSQL 19 文档。下面的订单例子和 SQL 都是诊断模板，没有在数据库实例执行，也没有生产性能数据。

先读行数，不要把 cost 当成耗时

计划输出是一棵 EXPLAIN 节点树。底部通常是表扫描；上层可能是过滤、连接、聚合或排序。节点中的 rows 是优化器预计该节点会输出多少行，并不是它扫描了多少行。全表扫描即使只输出很少结果，也可能必须检查表里的大量记录。因此，“估算输出很少”不能推导出扫描工作也很少。PostgreSQL 18 的 EXPLAIN 指南也说明，计划中的 cost 是用于比较候选计划的抽象成本单位，不能直接读成请求花费的毫秒数。

第一遍先从叶节点向上读：记录关键过滤节点的 rows，找到第一个与其下游结果明显不一致的位置，再沿父节点看这个误差如何影响后续选择。计划估算本来就是近似值，差一两行通常不是问题；当误差跨越数量级，或者重复执行后累计工作很大，才值得优先解释。不要只看顶层总行数，因为错误可能从某个底部谓词开始，并在嵌套循环、哈希构建或排序前被放大。

打开 ANALYZE 后，PostgreSQL 会实际执行语句，并显示实际输出行数和运行时间。对 loops 大于 1 的节点，显示的 actual rows 和时间通常是每次执行的平均值；理解累计工作时还要结合循环次数。比如内侧索引扫描每次只返回一行，但被外层循环执行数千次，单次看起来轻的节点仍可能累计很重。节点时间彼此包含，不能把父节点和子节点的耗时简单相加。EXPLAIN 文档还提醒，估算行数与实际行数的比较比单独比 cost 更能发现估算问题。

另一个反例是 LIMIT：计划节点可能按完整执行展示估算行数，而上层 LIMIT 实际只取前几行。这种显示差异不自动证明基数估算错了。读计划要把节点的执行次数、过滤条件和上层停止条件一起看，而不是看见 rows 与 actual rows 不同就马上调统计目标。

假设订单查询，偏差可能从哪里来？

假设一个多租户订单表，查询按 tenant_id 和 status 过滤，再按创建时间排序并取最近一页。若某些租户的绝大多数订单都处于 open，而另一些租户很少有未完成订单，那么这两个列并非独立分布。普通单列统计分别知道租户值和状态值的大致频率，却可能无法估计某个租户与某状态组合会留下多少记录。优化器如果因此低估候选行数，可能选择一个对小结果合适、对实际大量行却昂贵的后续方案。

先确认统计信息是否有机会代表当前数据。pg_class.reltuples、relpages 等目录值不是每次写入实时更新；ANALYZE 和 VACUUM ANALYZE 会更新统计，但常见情况下只抽样，结果仍是近似值。PostgreSQL 18 统计信息说明建议检查可读性更好的 pg_stats，而不是直接读取受权限限制的 pg_statistic。同一条计划在不同表规模、不同数据分布或一次新的 ANALYZE 后发生变化，并不奇怪。

可以先在授权的非生产环境，或经过明确评估的采集窗口里，对需要的列执行针对性 ANALYZE orders (tenant_id, status)，随后使用相同 SQL 和代表性参数重新生成普通计划。如果计划估算明显改变，问题可能是统计陈旧或样本不足；如果估算仍系统性偏小，再确认它是否为同表列相关性。不要把一次 ANALYZE 后的计划变好写成稳定提速证据；它只说明这组采集条件下估算发生了变化。

当同一张表中的强相关列确实是误差来源时，可以评估扩展统计，例如：

CREATE STATISTICS orders_tenant_status_stats (dependencies, mcv)
ON tenant_id, status FROM orders;
ANALYZE orders (tenant_id, status);

这是供团队审查的示例，不是本文实际执行的命令。dependencies 用于强相关列的依赖关系；mcv 用于常见值组合。统计对象只是声明要收集什么，数据需要由 ANALYZE 收集，采样大小和建模成本也要纳入判断。官方文档建议只为确实强相关的列组创建依赖统计，以免增加 ANALYZE 和后续规划开销。还要注意一个边界：PostgreSQL 18 和 19 的扩展统计文档都说明，目前扩展统计不会用于 join 选择率估算；如果偏差第一次出现在跨表连接处，给单表增加依赖统计不是通用解法。

估算偏差在哪一层，修复也要对应哪一层

如果偏差从单表过滤节点开始，检查该表统计更新时间、pg_stats 的常见值和直方图，再判断是否为同表多列相关性。若单表行数估算合理，到了连接节点才开始偏离，就记录连接键分布、两边实际基数和数据倾斜；不能把连接问题简单说成“缺一条索引”。扩展统计当前不覆盖 join 选择率，因此要结合查询结构、数据模型和实际参数另找验证方法。

如果偏差只对特定租户或时间范围出现，检查参数分布与预处理语句的计划选择。PostgreSQL 19 文档提供 GENERIC_PLAN 选项，可查看不依赖参数值的通用计划；该选项不能与 ANALYZE 同用，所以它不能代替实际执行证据。不同版本的 prepared statement 行为和选项要按目标主版本确认，不能拿一个参数的计划代表所有请求。

若估算行数接近实际数，但扫描仍读了大量无关数据，再评估过滤条件与索引的列顺序、表达式、类型转换、排序和 LIMIT 是否匹配。顺序扫描也可能是合理选择：当查询需要大部分表时，逐页读取比大量随机访问便宜。建立索引不会减少查询必须返回的结果数量，还会增加存储和写入维护；需要比较读写两侧的代价，而不是把“计划里出现 Seq Scan”直接当成故障。

实际计划暴露哪些测量边界？

EXPLAIN (ANALYZE, BUFFERS, SETTINGS) 可以把实际行数、循环次数、缓冲区命中/读取以及相关规划设置放在同一份证据里。BUFFERS 的上层节点会包含其子节点的使用量，不能把父子缓冲区计数重复相加。若读查询可能扫描大表，先估算资源消耗、限制参数范围并准备停止条件。

对写语句运行 EXPLAIN ANALYZE 会真的执行写操作。回滚事务也不一定能撤销序列推进、外部函数调用等所有副作用；生产环境采集应有授权和隔离方案。读查询也会真实消耗 CPU、内存和 I/O。采到的数据需要记录数据库版本、参数类别、统计时间、并发负载和缓存状态，敏感值脱敏后仍保留决定数据分布的信息。

计划执行时间也不等于用户看到的完整请求耗时。通常结果不会发给客户端，网络传输时间不包含在 EXPLAIN ANALYZE 中；结果类型转换成本默认也可能未测量。PostgreSQL 19 的 EXPLAIN 提供 SERIALIZE 选项测量结果序列化，但它仍不发送结果，因此不测网络成本。应用还可能在连接池、代理和重试队列等待，这些都要用应用侧追踪补充。

有效的验证不是“改了索引后截图看起来更快”，而是保留前后计划、同一组代表性参数、数据规模、采样和负载条件；检查行数偏差是否缩小、缓冲区读取和执行时间是否变化，并单独观察写入成本。每个假设都要能被结果否定：刷新统计没有修正偏差，就不要把问题归因于统计陈旧；扩展统计只改善过滤节点、连接节点仍偏差，就继续检查连接；行数接近却请求仍慢，就把调查转向真实扫描、排序、序列化、网络或应用等待。本文提出的查询与验证步骤均未执行。

只有当证据显示访问路径成本是主要问题，才把索引加入候选。需要在线建索引时，再把并发构建的等待、失败状态与验收纳入发布计划。这样，慢查询调查会从“猜一个索引”变成能复核的因果判断，而不是把一次计划变化误写成确定的性能收益。
