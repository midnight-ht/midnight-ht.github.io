生产建索引用了 CONCURRENTLY，为什么还在等？

PostgreSQL 并发建索引不挡普通写入，却仍有扫描、事务等待和失败状态。按阶段看进度，再用索引有效性和查询验证决定是否验收。

正文

核心要点

  • CONCURRENTLY 减少普通写入被建索引挡住的时间，但增加扫描、等待和资源消耗；命令耗时不能单独判断故障。
  • pg_stat_progress_create_index 的 phase 和计数是诊断入口；阶段切换时计数语义会变化，不能把单个百分比当总进度。
  • 命令失败后要核对 pg_index 状态；无效索引可能继续占空间并增加写入维护成本，唯一索引还可能已开始约束写入。

CREATE INDEX CONCURRENTLY 不会像普通建索引那样挡住表上的常规写入，但它并不承诺立即完成，也不承诺没有资源代价。它需要额外扫描，并等待可能影响构建的事务或旧快照结束。看到命令持续运行时，先看阶段，再判断是在等待、扫描还是被业务负载拖慢；不要只凭超时就取消重跑。本文的原始版本边界是 PostgreSQL 18，下面也核对了 PostgreSQL 19 文档；没有连接数据库或实际执行这些示例。

并发建索引绕过了什么，又增加了什么？

普通 CREATE INDEX 通常会在构建期间阻止该表上的写入。CONCURRENTLY 选择另一种取舍：让普通 INSERT、UPDATE、DELETE 尽量继续，同时把工作拆成多个事务阶段，执行两次表扫描，并等待已有事务在特定阶段结束。额外扫描会消耗 CPU 和 I/O，所以“不挡写入”不等于“应用延迟不变”。在写入繁忙、磁盘带宽紧张的库里，索引构建可能和业务查询争资源，即使没有一个明显的长锁挡住写请求。

PostgreSQL 18 和 19 的 CREATE INDEX 文档都描述了这些扫描与等待阶段。PostgreSQL 19 于 2026-11-19 发布；它另有 REPACK 命令，但 REPACK 与 CREATE INDEX CONCURRENTLY 不是同一项操作。不能因为版本升级，就把这篇针对创建新索引的说明套用到重整表空间或重建既有索引的流程。执行前应确认数据库主版本，再读相应版本的命令限制和进度字段。

一个并发构建会先把索引登记为暂时无效的目录对象，再分阶段扫描和验证。建索引进程需要等可能改动表的事务结束；完成第二次扫描后，还会等持有较早快照的事务结束，才把索引标成可供查询使用的有效状态。因此，一个事务拖住最后阶段，并不说明扫描线程停止工作，更不能由此推断数据库已经死锁。阶段名回答“当前在做什么”，等待对象和事务开始时间则帮助回答“为什么还没过去”。

怎么分辨在等事务，还是扫描本身很慢？

PostgreSQL 18、19 都提供 pg_stat_progress_create_index，每个正在执行 CREATE INDEX 或 REINDEX 的后端有一行状态。视图会报告 phase；在扫描阶段可观察 blocks_done、blocks_total 等计数，在等待阶段则有 lockers_done、lockers_total 和 current_locker_pid。一个只读观察查询可以是：

SELECT p.pid, p.command, p.phase,
       p.blocks_done, p.blocks_total,
       p.tuples_done, p.tuples_total,
       p.lockers_done, p.lockers_total, p.current_locker_pid,
       a.state, a.wait_event_type, a.wait_event, a.xact_start, a.query
FROM pg_stat_progress_create_index AS p
LEFT JOIN pg_stat_activity AS a USING (pid);

这是供操作人员按环境核对的查询样例，本文没有在 PostgreSQL 实例里执行；权限、视图字段和连接方式都应对照目标主版本检查。building index 时先看扫描计数是否变化，并观察数据库 I/O、CPU 和业务延迟。计数只描述当前阶段；从一次扫描切到验证阶段后，计数可能重新对应另一个工作单元，所以“完成 70%”不能当作整个并发流程的可靠剩余时间估算。等待阶段则先记录 phase、当前等待的 PID、事务开始时间和业务所有者，再确认该事务是否确实需要处理。

尤其要区分 heavyweight lock 等待和“waiting for old snapshots”。pg_blocking_pids() 能返回阻止某会话获取锁的进程 ID；但一个空数组不能证明并发建索引已没有事务等待，因为旧快照等待与锁阻塞不是同一个观察问题。进度视图中的阶段和 locker 信息应与 pg_stat_activity 一起看，必要时再和事务负责人核实。统计信息、查询文本也可能受权限影响；不要把观测查询当作能自动识别所有根因的诊断器。

假设订单表需要按创建时间与状态查询建立索引。团队观察到构建停留在 waiting for writers before validation，并发现一个事务持续打开数小时。此时的合理动作是确认事务所属任务、是否处于空闲事务、能否由业务负责人安全结束，并同步评估继续等待的写入负载；直接重复启动只会再次进入相似等待。若阶段是 building index，但计数缓慢且磁盘读写繁忙，重点则应转向资源竞争与变更窗口，而不是只找一个持锁会话。这里是解释诊断分支的假设场景，不是实际发生的生产故障。

命令失败之后，为什么不能只看迁移日志？

CREATE INDEX CONCURRENTLY 失败时，数据库可能留下无效索引。pg_index.indisvalid 表示索引能否安全供查询使用；indisready 表示索引是否已准备好接受写入维护。它们不是同一个布尔值。无效索引可能不能用于查询，却仍占用空间或产生写入维护开销。检查时应同时限定 schema、表、索引名，并查看实际定义和状态，不能只凭命令报错就断定“对象不存在”。

唯一索引还有一个更隐蔽的失败路径：并发构建到第二次扫描附近时，唯一性约束可能已开始影响其他事务，即使最终命令失败，遗留的无效唯一索引仍可能继续拒绝重复值。对业务来说，这意味着失败不总是“没有发布”；操作人员要评估写请求是否已经看到约束行为，再选择清理或重新构建。普通的非唯一索引不会产生相同的唯一约束副作用，但无效对象仍要处理。

迁移系统也要匹配数据库命令的事务语义。CREATE INDEX CONCURRENTLY 不能放在事务块中；若迁移工具把整个脚本自动包进一个事务，命令会报错。重试逻辑若只写 IF NOT EXISTS，也不代表已有同名索引的列、条件和有效状态符合预期；PostgreSQL 文档明确提醒，同名关系可能与本次想创建的索引完全不同。迁移回执应能区分“执行成功、失败遗留、已存在但定义不符、索引有效但查询未采用”等状态。

什么情况下普通建索引反而更合适？

CONCURRENTLY 的价值是缩短常规写入被建索引阻塞的窗口，不是任何情况下都更快。小表、低流量系统或有明确维护窗口的服务，普通建索引可能更简单、总工作量也更少；如果不能接受写入阻塞，再比较并发方式产生的扫描与资源开销。选择依据应是可承受的写入停顿、表规模、业务峰值、磁盘余量、长期事务情况以及失败清理能力，而不是“生产表一律 CONCURRENTLY”的口号。

每张表同时只能运行一个并发索引构建，构建期间也不允许对表做其他 schema 修改；这会影响批次并行度。分区表上的并发创建还有单独限制，应看对应版本的 CREATE INDEX 文档，不能把普通表的操作流程直接复制过去。若新索引的理由只是“某查询慢”，先用代表性参数检查EXPLAIN 计划证据，确认索引条件、数据分布和写入成本再排发布窗口。

命令返回成功也只是一个门槛。要核对 indisvalid、indisready，再观察具有代表性的查询是否采用索引、延迟是否变化，以及写入维护和存储成本是否可接受。表达式索引可能还需要更新统计信息。建议在预演环境覆盖长事务等待、资源变慢、客户端超时、唯一冲突、迁移重试和失败后清理；本文列出的计划没有实际执行，不能当作通过记录。发布回执应分别记录构建阶段、数据库目录状态、查询计划和应用侧结果，避免把“命令不报错”写成“索引带来性能提升”。
