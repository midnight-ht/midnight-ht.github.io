生产建索引用了 CONCURRENTLY，为什么还在等？

PostgreSQL 18 并发建索引仍有事务等待、资源开销和失败状态，需要以有效性及业务负载验收。

正文

CREATE INDEX CONCURRENTLY 允许常规写入继续进行，但并不承诺立即完成或完全没有业务代价。生产变更应同时观察事务等待、资源负载和索引有效性，不能只等部署脚本的超时。下面按 PostgreSQL 18 文档讨论变更计划，没有在生产库执行索引操作。

在线构建为什么仍然会等待

PostgreSQL 18 的 CREATE INDEX 文档说明，并发方式需要额外扫描和事务等待，工作量比普通方式更多；失败时也可能留下无效索引。它不能在事务块中执行。因此迁移工具若默认把整个文件包在一个事务里，必须先确认支持这种操作的运行方式。

假设订单查询需要新索引，而库里仍有长时间未结束的事务。构建过程等待不必然意味着数据库已经死锁，也可能是在等待满足阶段条件。此时盲目取消再运行，既未消除原因，又增加了清理责任。应该先找到等待对象、持续时间及拥有者，并由变更负责人协调处理长事务，再决定继续、取消还是调整窗口。

上线计划需要包含停止条件

候选计划可以先记录表规模、现有索引、预期查询、剩余存储空间和变更负责人。执行期间观察业务延迟与错误、数据库负载、等待事件和构建进度。阈值必须依据本服务的约定，不抄一个“通用安全百分比”就视为可用。

构建耗时也不等于业务不可用时长。反过来，即使写入未被常规表锁挡住，额外扫描仍可能争用资源，使业务变慢。应把数据库侧状态与用户结果放在一起判断，避免因为“没有锁表”就忽略明显的服务退化。必要时先降低其他后台任务的资源竞争。

失败处置要看目录里的真实状态。无效索引可能占空间并带来维护成本，不能因为查询计划没有使用它就当作不存在。清理或重建之前，确认索引名称、归属表和失败原因，防止脚本误操作同名但不同用途的对象。具体命令应由有权限的操作人员在确认环境后执行。

命令完成之后还要验证什么

索引有效只是第一步。还要用真实代表性的查询参数检查计划选择及业务耗时，考虑数据分布和缓存条件。新增索引不保证优化器必定采用，也不保证所有查询更快；写入维护成本需要在变更后持续观察。不要把一次本地短查询当作生产收益证据。

对迁移工具，建议在预演环境检查事务包装、失败后的重跑行为和日志归档。如果重跑只看到对象已存在就跳过，而不检查有效性，可能把失败状态固化成“迁移完成”。本文未执行预演，这些是上线前需要补齐的验收项目。

什么时候不用并发方式？可控维护窗口中的小表变更，普通构建可能更简单；是否接受写入阻塞应由业务安排决定，而不是默认所有表都必须并发。更复杂的分区和唯一性场景还需逐项阅读对应限制，不能把本例扩展成通用数据库发布脚本。

把索引变更当作有阶段状态的操作：开始、等待、完成、有效、查询验证和清理各自留证。若新增索引的理由仍只是“查询慢”，先回到EXPLAIN 的证据检查，确认主要问题确实来自访问方式。
