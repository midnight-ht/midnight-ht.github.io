请求超时后能否重试？先定义业务幂等边界

超时后的结果未知怎样处理：区分 HTTP 幂等语义、业务意图标识、持久化去重与外部副作用。

正文

核心要点

  • 超时意味着结果未知，不能据此断言订单没有提交。
  • 业务键须跨同一意图的重试保持稳定，并约定参数漂移、过期和并发时的行为。
  • 本地键记录与订单应通过数据库原子机制协调；外部副作用仍需单独去重和对账。
  • 回放已保存结果前仍要校验身份与资源授权。
  • 验收要覆盖提交前后故障、重复并发、请求变更、支付回调及记录过期。

请求超时后能否重试，不能只看客户端有没有收到响应。服务端可能尚未处理，也可能已经提交订单，只是在回包途中断线；只有把同一次业务意图标识出来，并把“占有该标识”和本地业务写入原子地记录，重试才有机会返回第一次操作的结果。外部支付、短信等副作用仍需各自的去重与对账契约。下面用订单创建作假设示例，没有接入支付平台，也没有执行故障测试。

HTTP 幂等不等于所有 POST 自动去重

RFC 9110 第 9.2.2 节讨论的是重复相同请求对服务端的预期效果：一次执行与多次执行的预期效果相同。它不要求每次响应、日志或计费记录都相同。PUT 和 DELETE 等方法按协议具有幂等语义；POST 的业务含义由应用定义。一个 POST 即便允许客户端重试，也不会因为请求文本相同就天然变成去重操作。

超时描述的是观察结果，不是服务端事务结果。请求可能没离开客户端，可能在代理排队时被丢弃，也可能已在数据库提交后丢失响应。客户端把这几种情况都当成“没成功”并重新生成订单，就可能重复下单；把任何超时都当成成功也会错误展示尚不存在的订单。合理的接口要能表达结果未知，并提供一个可查询的业务标识。

标识代表一次意图，不能由每次网络尝试生成

幂等键应在一次业务操作开始时创建，然后随该操作的每次重试保持不变。用户改变商品数量、收货地址或业务内容后，通常已形成新意图，应该获得新的键；如果仍复用旧键，服务端需要识别“键相同但请求内容不同”，并按冲突处理，而不能把新参数悄悄套到旧订单上。按用户 ID 永久去重则太粗，会把用户之后合法购买同一商品也拦掉。

服务端要限定键的作用域，例如租户、操作类型和客户端键的组合；还应保存规范化请求摘要、状态、资源引用和必要的原始响应信息。摘要规则要明确哪些字段构成业务意图：JSON 字段顺序或空白通常不应造成不同，但币种、价格、商品数量等会影响交易的字段不能被忽略。保存摘要不等于保存完整敏感请求；日志和键表也不应因此复制支付凭据或不必要的个人信息。

命中已有键也不等于可以跳过身份与对象授权。键是关联同一次操作的标识，不应被当成读订单的秘密口令。服务端在返回已保存结果前仍要确认当前调用者有权访问对应租户和订单，并避免把另一用户的响应体、地址或付款状态泄露给拿到键值的人。这个检查最好发生在结果读取与返回的路径里，而不只是第一次创建订单时。

过期策略同样属于接口契约。若去重记录只保留几小时，客户端在隔天恢复网络时再次提交相同键，服务端可能已经无法关联到旧结果。团队需要确定过期后是拒绝、重新视作新操作，还是要求先查询订单状态；若外部支付方的键保留期短于订单重试窗口，单靠支付方去重也不足以覆盖长期恢复。

本地去重记录要和订单写入一起竞争

一种可检验的实现思路，是以 (tenant_id, operation, idempotency_key) 建立唯一约束，并在同一数据库事务内竞争写入键记录和订单。第一个请求取得键后创建订单并保存可复用的结果；相同键的并发请求不会各自先查出“没有记录”再都创建订单，而是由数据库唯一性约束或同等原子机制决定谁拥有该意图。PostgreSQL 的唯一索引文档说明，唯一约束通过唯一索引阻止重复值；INSERT ... ON CONFLICT 文档说明该子句如何处理冲突写入。具体语句和隔离级别仍需按所用数据库版本验证。

以一次假设的结账为例，浏览器创建键 K，请求包含购物车版本、币种和最终金额。事务先尝试写入 K 与摘要，成功后创建订单 O，把键记录关联到 O，并提交。若事务提交后响应丢失，浏览器再次用 K 和相同内容请求，服务端读到已完成记录，返回 O 的原结果，而不是再插入一张订单。若第一次事务在提交前崩溃，数据库回滚键记录和 O，重试则可以重新取得 K 并执行。

此设计也有失败边界。若服务端先单独写一条 processing 记录，随后才写订单，两步之间崩溃会留下永久处理中；如果先写订单，再单独写去重记录，崩溃可能留下订单但无法识别重试。分开提交时必须有明确恢复机制，例如带租约的处理状态、可安全重入的恢复任务，以及按订单 ID 检查既有结果的规则。进程内的 Map 或锁在多副本部署中不能协调其他实例，也不会在进程重启后保留记录。

事务之外的支付不能被本地幂等性包住

数据库事务能覆盖订单表和本地键表，不能把外部支付服务的扣款也纳入同一个原子提交。常见边界是先持久化订单和待支付状态，再通过事务发件箱或等价机制可靠地安排支付请求；消费者可能重复投递，因此每个支付尝试应使用稳定的业务关联标识，并遵守支付提供方实际支持的幂等规则。支付调用超时后，状态应保持“待确认”或“结果未知”，随后查询、回调和对账共同收敛状态，而不是立刻再次创建订单或把失败结论写死。

出站通知也要单独想。邮件重复通常是体验问题，库存重复扣减可能是资金或可售数量问题；二者不能用同一个模糊的“接口幂等”标签带过。若外部系统没有可用的幂等接口，业务需要考虑可查询的操作引用、补偿流程和人工对账。幂等只能把重复请求关联起来，不能证明不同键代表的两个请求一定来自一次双击，也不能代替业务层订单限制、支付核验或反欺诈策略。

冲突、处理中和未知结果应有不同响应

相同键、相同摘要、已完成时，可以返回之前保存的结果；相同键对应不同摘要时，应给出稳定、可解释的冲突响应；相同请求仍在处理时，可返回可查询的处理中状态或让客户端短暂等待。具体 HTTP 状态码与响应字段由 API 契约选择。客户端不应拿到一个冲突响应就自动生成新键再提交，否则同一个未知操作会变成第二笔真实订单。提供 GET /operations/{key} 一类状态查询，也比让客户端靠猜测更容易恢复。

重试策略还要区分传输失败和确定的业务拒绝。连接重置、部分网关超时或响应丢失，常常意味着结果未知；明确的参数校验错误则不应原样循环重试。自动重试要有截止时间、上限和退避，避免网络恢复时大量客户端同时冲击服务端。即便请求安全地复用一个键，盲目高频重放也会消耗资源并扩大故障。

怎样验证它真的保护了业务意图

验收应从状态转移出发，而不只是断言某个请求返回 200。先让两个并发请求携带同一键和同一摘要，确认数据库最后只有一个订单，另一个请求得到相同资源或明确处理中状态；再复用该键提交不同数量，确认服务端拒绝参数漂移。模拟订单事务提交后切断响应，使用原键重试，确认仍指向原订单；在提交之前终止事务，确认不会留下孤立的处理中记录。

支付流程还要单独覆盖“支付方已受理但回包丢失”“回调晚到或重复”“本地消费者重复投递”和“支付查询暂时不可用”。检查订单、支付方引用、发件箱记录与最终响应之间的关联，而不是只看客户端提示。最后验证记录过期、账号隔离、权限拒绝和请求摘要规范化。本文提出的是设计与验收方案，没有运行数据库或支付故障注入，因此这些步骤不是已通过的测试结果。

如果写操作本身是对已读取资源的修改，版本条件也有不同职责：RFC 9110 第 13.1.1 节中的 If-Match 防止基于旧版本覆盖新修改，而幂等键识别同一业务操作的重复提交，两者可以同时使用。相关的版本冲突处理见两个人都保存成功，为什么一个人的修改消失了？；本篇的核心检查则是“这次意图已经执行到哪一步”。
