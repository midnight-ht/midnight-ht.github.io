请求超时后能否重试？先定义业务幂等边界

超时后的结果未知怎样处理：区分 HTTP 幂等语义、业务意图标识、持久化去重与外部副作用。

正文

请求超时后是否可以重试，取决于重复执行是否会改变业务结果，以及服务端有没有把同一业务意图识别出来。客户端没收到响应，只能说明结果未知，不能证明订单没有创建。以下是创建订单的设计分析，未接入支付平台或进行故障实测。

方法名回答不了所有业务问题

RFC 9110 第 9.2.2 节定义的是多个相同请求对服务端的预期效果与单次相同。响应可以不同，日志也可以记录多次。这个语义不能替代应用自己的订单、扣款和通知约束；把创建接口改名为 PUT，不会让数据库与支付平台自动形成一次事务。

假设用户按下购买按钮后等待超时。他可能在重试同一笔订单，也可能改变数量后重新下单。如果服务端只按用户身份去重，就可能误删合法购买；如果每次重试都产生新标识，又无法识别原来的意图。因此业务标识的生成时机和生命周期，应由接口契约明确。

去重记录要和业务状态一起讨论

一个候选方案是保存请求标识、规范化后的请求摘要、处理状态和结果引用，并约定摘要忽略哪些无业务意义的差异。同一标识配同一内容，返回已有结果或明确的处理中状态；同一标识却改变内容，则返回可解释的冲突。这是设计建议，具体状态码和保存期限需要客户端、业务与存储负责人协商。

真正难点在并发。两次相同请求几乎同时到达，不能先各查一次“没有记录”，再各创建一张订单。唯一约束、条件写入或事务中的竞争裁决，需要让其中一个取得处理权。锁放在哪里、异常后谁接管，都要能从记录中解释，不能只依赖一台进程的内存标记。

还要考虑业务已提交、响应却丢失的窗口。若去重记录与订单一起提交，客户端重试可以查到原结果。若二者分开写，服务崩溃可能留下订单存在、记录缺失的状态。审查时应画出写入顺序，逐个假设中途停止，而不是只验证成功路径。

外部扣款为什么仍要单独处理

本地数据库事务不能单独保证外部支付只发生一次。如果支付端支持自己的幂等契约，应对齐标识及保留时间；如果结果未知，就查询和对账，避免在不了解前次结果时盲目再扣。邮件和库存操作也要分别定义重复执行的后果，不能共享一句“接口已幂等”作为验收。

保存期限也不是越长越好。订单数据保留、请求标识过期和支付查询范围可能不同，团队必须约定过期重试怎样响应。若允许重新创建，要让客户端知道它已成为新业务意图；若不能确定，应给出人工核对或状态查询入口，而不是返回含糊的成功。

测试时可以设计同标识并发、同标识不同参数、提交后断开连接、处理中进程退出和记录过期等情形。本文没有执行这些测试；预期应由订单约束决定，并同时检查实际订单数、扣款状态和响应关联。仅有两次 HTTP 成功不足以证明正确。

重试是否应该自动开启？对只读查询与有副作用操作应分开决定，重试次数和退避也要受请求总期限约束。先补齐“结果未知时查哪里”这一条契约，再考虑客户端自动化；涉及异步交接时可继续看事务发件箱的责任边界。
