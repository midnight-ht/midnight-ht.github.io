流水线没传令牌，第三方 Action 就拿不到权限吗？

GitHub Actions 的令牌可通过上下文访问，需按 job 明确最小权限，并区分只读构建和写入发布。

正文

工作流没有显式把令牌作为输入传给第三方 Action，不代表它无法取得令牌。GitHub Actions 提供令牌上下文，权限设计应按 job 的实际任务声明最小范围，并将只读构建和写入发布分开。以下依据官方文档作审查建议，未修改或执行任何示例工作流。

传参不是权限边界

GitHub 的 GITHUB_TOKEN 指南明确说明，Action 可通过 github.token 上下文访问令牌，即使工作流没有显式传入；指南建议用 permissions 限制访问。因而审查不能只搜索 secrets 字段，还要理解 job 中哪些代码会执行、它们拥有怎样的身份。

假设一个 job 安装依赖、运行测试，然后提交生成文件。为了最后一步写仓库，它获得了写权限。前面的第三方 Action 和构建代码也处于这个执行环境中。仅把最后一步命名为“发布”，并不会让之前的步骤自然变成不同权限的主体。

把所需能力写清楚

候选设计是让测试与构建使用只读权限，发布 job 只获得发布所需的特定写入能力。制品在两者之间交接时，需要验证对应提交、来源和内容，而不只信任一个同名文件。否则拆了 job，却可能让不可信输入经制品进入高权限阶段。

声明权限之前，先列出每一步需要的 API 操作。读取代码、写评论、创建发布与部署云服务不是同一个权限。若内建令牌不满足需求，再评估 GitHub App 或其他受控身份；不要把遇到权限错误统一解决为添加一个广权限长期个人令牌。

还要检查仓库与组织设置、触发事件和来自 fork 的输入，实际权限会受到这些条件影响。文档中的某个示例不是所有仓库的默认状态证明。尤其在有外部贡献代码的流程中，先明确何时执行了不可信代码，再决定是否可以提供写权限或秘密。

第三方组件也是执行代码

使用 Action 前，应核对来源、更新方式和实际执行内容。固定到可审查的提交能让版本可追溯，但不能自动证明代码安全；还应确认仓库与提交确属预期来源。更新依赖和更新 Action 都需要适当审查，不能因为名字来自常见组织就跳过其能力范围。

日志脱敏也不能作为泄露不可能发生的保证。即使终端输出隐藏了某些值，运行代码仍可能使用其拥有的权限发起请求。因此应该减少可获得的权限与秘密，而不是只要求脚本不要打印它们。调试时也要避免开启会把敏感上下文完整输出的命令。

怎么验收最小权限？在受控仓库运行所需读操作，确认能够完成，再验证不应允许的写操作确实被拒绝，并保存权限配置与执行证据。本文没有运行这样的检查，不能把建议写为已证明安全。平台设置变化后，应重新核对，而不是永久依赖一次成功。

拆分 job 是否会增加维护成本？会，制品验证和身份管理需要额外设计；小型流程仍可先从显式权限声明开始。优先拿掉构建不需要的写能力，再完善阶段隔离。涉及缓存交接时，继续检查缓存与供应链信任，不要把提速数据误当可信发布输入。
