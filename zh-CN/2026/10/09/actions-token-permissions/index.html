workflow 写了 permissions，job 实际拿到的 GITHUB_TOKEN 权限怎么算？

按组织或仓库默认值、workflow 声明、job 声明和触发事件逐层计算 GITHUB_TOKEN 权限；同一 job 中的 Action 也共享这条权限边界。

正文

核心要点

  • Action 没有显式 token 输入，不足以证明它没有 GITHUB_TOKEN 权限；检查该 Action 所在 job 的权限。
  • 有效权限要结合企业、组织或仓库默认值、workflow 级和 job 级声明，再考虑事件与 fork 策略。
  • 一旦写出 permissions，未列出的权限会变为 none；write 包含 read。
  • fork pull_request、pull_request_target、私有仓库策略与 Dependabot 不能用一个默认规则概括。

要判断一个 GitHub Actions job 能否改仓库，不能只读一行 YAML。按企业、组织或仓库的默认权限、workflow 级 permissions、job 级 permissions，再按触发事件和 fork 策略逐层核对。Action 没有显式 token 输入，也不能据此判定它没有 GitHub 身份：GitHub 文档说明，Action 可以通过 github.token 上下文访问 GITHUB_TOKEN。因此，真正需要检查的是整个 job 中会执行什么代码、这个 job 的令牌能做什么，以及这个令牌是否会进入不可信输入可以控制的执行路径。

以下判断依据 2026 年 11 月 27 日查阅的 GitHub 官方文档。文中的 workflow 是假设示例，没有在真实仓库运行；文中也没有检查任何特定仓库的组织设置或令牌实权。

先把 job 当作令牌权限边界

permissions 控制的是 GITHUB_TOKEN 对 GitHub 资源的权限，不是只给紧挨着它的那一步授予能力。workflow 语法文档写明，workflow 级声明会作用于各 job；在具体 job 内声明权限时，该 job 中使用 GITHUB_TOKEN 的 Action 和 run 命令都会得到相应权限。换句话说，uses: third-party/action@... 和后面的 shell 命令若在同一个 job 中运行，不能因为令牌没有放进该 Action 的某个显式输入，就把它视为一个隔离主体。

官方 GITHUB_TOKEN 指南进一步明确：Action 即使没有被显式传入 GITHUB_TOKEN，仍可通过 github.token 上下文访问令牌。这个事实解释了为什么“我没在 with: 里写 token”不是权限审查的结论。它只说明一个输入字段没有这样传值，不会自动改写 job 的身份或令牌权限。

这也改变了审查对象。逐步问“这个 Action 收到了哪个输入”还不够；还要问它运行在哪个 job、该 job 的 token 对仓库拥有什么权限、该步骤之前和之后执行了哪些受仓库控制的代码，以及它能否读取其他 secrets。permissions 不会自动收窄其他 secret，也不会把共享 runner 变成隔离沙箱。令牌权限、secret 传递、runner 的信任与网络访问是相关但不同的边界。

有效权限怎样逐层算出来？

第一层是企业、组织或仓库所设的默认权限。官方设置文档指出，组织可以设置默认值，仓库会继承相应限制；个人账户新建仓库的默认令牌权限与组织新建仓库的继承行为也不完全相同。因此，“GitHub Actions 默认只读”或“默认可写”都不能脱离仓库设置和账户类型当成通用事实。没有查看设置页面或策略配置时，只能说未知。

第二层是 workflow 文件顶层的 permissions。如果在那里声明一组权限，它会作为各 job 的基线。第三层是 job 自己的 permissions；它能为这个 job 指定另一组权限。审查时要读完整的 YAML 结构，因为把一份声明从 workflow 移到某个 job，改变的是它适用的作业范围，不是令牌输入的语法形式。

还有两个容易漏掉的规则。其一，一旦写出 permissions 并列出权限，未列出的权限就会被设为 none。其二，write 包含对应范围的 read。例如，contents: write 不只是“可以发布”，也具备读取仓库内容的能力；不能把读写理解成彼此独立的开关。若操作只需要读取代码，就没有理由用 contents: write 来表达。

下面只说明配置结构，不是已执行或适用于所有项目的模板：

permissions: {}

jobs:
  verify:
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@v6
      - uses: vendor/check@v3
      - run: npm test

  publish:
    permissions:
      contents: write
    steps:
      - run: ./publish-release.sh

这个例子要传达的不是“照抄就安全”。verify 中的第三方 Action、checkout 和测试命令都处于同一 job 的令牌权限范围内；publish 的 contents: write 也不只给最后一行 shell 命令。实际项目还要列出每个 job 调用的 GitHub API 操作，检查 Action 的来源与代码版本，并确认发布步骤是否需要其他权限或秘密。将权限写成空对象后再逐 job 增加能力，是一种能看清意图的起点，但不能替代事件和仓库设置核查。

为什么触发事件会改变结果？

官方权限计算说明先取企业、组织或仓库默认值，再应用 workflow 级和 job 级配置，最后根据触发事件及 fork 情况调整。例如，来自 fork 的普通 pull_request 工作流在没有允许 fork 写 token 的相应设置时，会把写权限收窄为只读。Dependabot 的 pull request 也按 fork 的限制处理，并且默认使用只读 GITHUB_TOKEN、不能访问普通仓库 secrets。

但这些规则不适用于所有事件。GitHub 把 pull_request_target 作为高信任事件：它运行来自基础仓库默认分支的 workflow，并获得基础仓库的 GITHUB_TOKEN 与仓库、组织 secrets。这个事件适合基于元数据给 fork PR 贴标签或评论；默认不执行 fork 的代码。若维护者把 fork head 检出到该 job 并运行其中的构建脚本、依赖安装或测试，就让外部控制的代码进入了拥有高权限令牌和秘密的执行路径。检出动作本身不是执行，但随后运行被检出的脚本会完成这条风险链。

截至 2026 年 11 月 27 日，GitHub 的官方安全文档还说明：对尚无适用 Actions 事件策略的公开仓库，pull_request_target 默认阻断策略当时处于 evaluate mode，运行仍会继续；文档列出的 enforcement 日期是 2026 年 12 月 2 日，适用于此前使用该默认策略的受影响仓库。该策略不应用于私有或内部仓库，也不替代已配置的适用事件策略。这个日期和范围会随平台政策变化，维护者应在采用前重新核对官方文档，不能把它写成所有仓库今天都已经被阻断。

私有仓库的 fork workflow 还有单独的仓库或组织设置：管理员可以控制是否运行 fork 工作流、是否发写 token、是否发送 secrets、是否要求审批，而且组织层限制可能不允许仓库自行放宽。把公开仓库的默认限制复制到私有仓库，或反过来，都可能算错实际权限。

拆 job 有用，但没有解决所有问题

把只读构建与写入发布放进不同 job，能让两者拥有不同的 GITHUB_TOKEN 权限；它比在一个高权限 job 里先测试、后发布更容易审查。代价是需要定义两阶段交接：发布 job 使用哪个提交生成的文件、制品来自哪个运行、下载后验证什么，以及谁或什么条件授权写入。只要把不可信构建输出原样交给高权限 job 执行，拆分 job 就只是换了 YAML 位置，没有切断不可信代码的影响。

相反地，如果同一个 job 既安装第三方依赖、运行仓库脚本，又拥有 contents: write，最小权限审查就应该追问：这些代码是否都需要写仓库？能否先在只读 job 完成构建和测试，再把经过身份与内容检查的产物交给单独发布 job？如果不能拆分，能否去掉不必要的权限、固定并审查 Action 版本、避免把凭据写入日志，并限制触发来源？这些选择依据是代码信任、写操作对象和故障影响范围，不是 Action 的供应商名气。

GITHUB_TOKEN 默认针对调用它的仓库。跨仓库读取或写入时，额外个人访问令牌可能把更广的访问能力带入 runner。GitHub 的 runner 安全文档建议优先用当前仓库的 GITHUB_TOKEN；需要跨仓库访问时，再评估只授予所需仓库和资源权限的 GitHub App 或部署密钥。部署密钥主要限于单仓库 Git 读写，不能替代 REST 或 GraphQL API。选哪种身份取决于实际操作和粒度，不能因为“权限不够”就长期塞入一个宽权限 PAT。

怎样核验仓库中的真实权限？

先从 workflow 的触发器开始，标出 push、pull_request、pull_request_target、workflow_run 或手工触发，并记录这些事件会引入的信任条件。再查看仓库、组织或企业的 Actions 默认权限与 fork 策略，沿 YAML 从 workflow 顶层读到每个 job，列出其 permissions、uses、run、secrets 和制品交接。输出不应只是“我们有 least privilege”，而应具体到每个 job 的读取、写入、部署身份和依赖输入。

在可丢弃的测试仓库中，可以先验证必要的读取操作成功，再尝试一个该 job 不应允许的写操作，确认请求被拒绝，并保存触发事件、运行 ID、权限配置与返回结果。测试必须遵守仓库策略，不把失败的写请求改造成真实数据写入。还要分别检查 secret 是否传递、OIDC 是否启用、runner 是否可信；令牌拒绝写入不证明这些边界也安全。

本文没有运行这些工作流，也没有观察某个仓库的实际令牌响应。文中的权限计算方法是依据当前官方文档整理的审查步骤，不是生产安全认证。若项目同时从多个 workflow 或 runner 交接构建产物，继续看制品身份如何贯穿构建到发布；若关注 fork 事件下何时会执行不可信代码，再看pull_request_target 的信任边界。

遇到权限错误时，先把需要的 GitHub 操作、触发上下文和执行代码列清，再只在承担该操作的 job 上授予所需范围。若一个 job 同时运行不可信代码又必须写仓库，先调整执行边界或制品交接；单纯把 token 显式传给一个 Action，或换成更宽的个人令牌，并不能回答这两个根本问题。
