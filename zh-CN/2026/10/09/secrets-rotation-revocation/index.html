删掉仓库里的密钥，为什么泄露处置还没结束？

从凭据授权范围、消费者切换与旧凭据失效证据，到 Git 历史副本治理，区分泄露处置中容易混淆的步骤。

正文

核心要点

  • 源码删除、提供方撤销、消费者切换和副本治理是不同状态，必须分别核实。
  • 先撤销还是先切换取决于凭据风险与停机代价；高风险暴露应优先遏制。
  • 关闭处置需要新旧两条路径、日志范围与未决会话边界的证据，不把扫描变绿当作无滥用证明。

从仓库删除一行密钥，只能证明当前文件不再显示它，不能证明服务端已经拒绝这个凭据，也不能证明旧实例、流水线或克隆仓库不再保存它。处置至少要分别回答四个问题：凭据还有效吗、它能访问什么、哪些消费者仍依赖它、暴露过的副本如何处理。任何一个问题没有证据，都不应把“删掉了”写成事件已关闭。本文说明流程与验证边界，没有访问真实账号、令牌或安全事件日志，也没有执行凭据轮换。

先把四种动作分开

工程里常把“删除密钥”当成一个动作，实际至少涉及四层状态。第一层是应用当前版本：源码、配置、构建产物和日志中是否还含有这个值。第二层是凭据提供方：令牌、密码、证书或密钥是否仍被接受，权限和有效期是什么。第三层是消费者：CI 工作流、部署任务、运行实例、运维脚本和恢复环境是否已切换。第四层是历史副本：Git 历史、分支、fork、开发者克隆、缓存页面、工单和日志是否留下了副本。

这四层的变更不会自动联动。删掉最新提交中的字符串，不会通知云平台撤销一个访问令牌；撤销令牌也不会自动改好每条流水线的配置；重写 Git 历史更不会清理其他人的克隆或所有缓存。GitHub 的泄露修复指南明确说，单从代码库删除并不足够，关键步骤是联系凭据提供方撤销；它也把更新受影响服务、用新凭据测试列为后续工作。GitHub 泄露密钥修复指南

因此先建立一张处置表，而不是先改历史。表里用不含秘密值的标识记录提供方、凭据类型、所有者、权限范围、过期或最后使用信息、消费者、替换负责人、撤销状态和证据位置。不要把完整令牌复制进工单、聊天或审查 JSON。OWASP 建议对秘密访问应用最小权限，并记录秘密的用途、预期消费者、生命周期和责任人；这些元数据可以支持迁移，不必记录秘密本身。OWASP Secrets Management Cheat Sheet

用风险决定切换顺序

切换顺序的核心分歧是：先撤销旧凭据，还是先发新凭据并迁移消费者。若凭据仍有效、仓库公开、权限较大或有异常使用迹象，首要目标是遏制未授权访问，拖延撤销会延长攻击窗口。GitHub 的指南建议对高风险凭据优先立即撤销；如果停机风险需要考虑，可以先创建新凭据，让应用使用新凭据，再撤销旧值。它没有给所有凭据规定统一并存时长，这个时长也不应凭习惯拍定。GitHub 泄露密钥修复指南

如果证据显示凭据已停用、只在受控私有仓库中出现，或属于隔离的开发环境，可以规划一个有明确截止点的迁移窗口，但“低风险”不等于不处置。窗口需要写明谁负责生成替代凭据、哪些服务切换、何时撤销旧凭据、观察什么失败信号，以及过期后如何处理仍未迁移的消费者。若没有可验证的消费清单或截止条件，允许新旧长期共存会把临时兼容变成常驻权限。

设想某个 CI 部署令牌被提交到仓库。假设它仍有效，且可向生产环境发布。一个保守的处置推演是：安全负责人确认令牌提供方、授权范围、最后使用时间和公开暴露状态；平台负责人列出调用它的发布工作流、手动回滚任务和备用环境；再根据风险选择立即撤销，或在确认无异常使用且可接受短窗口时，先生成同等或更小权限的新令牌、逐个切换并验证发布链路，随后撤销旧令牌。这里是设计示例，不是我们访问了任何仓库或平台。

若只更新主分支里的工作流秘密，而一个旧 release 分支仍能部署、夜间任务仍从另一处变量读取旧值，切换就尚未完成。消费者清单应从代码引用、平台秘密配置、部署定义、运行手册及负责人确认中交叉整理。代码搜索能找到静态引用，却未必能发现平台变量、动态生成的凭据或人工保存的恢复副本；审计日志能提供使用证据，但缺少记录也不自动证明没有使用。清单应保留“已确认”“待平台核实”“未知”等状态，不能把猜测填成完成。

验收要同时证明新旧两条路径

新凭据能完成预期操作，只能证明新路径可用；旧凭据无法再执行原权限范围内的操作，才是撤销侧的证据。优先使用提供方的凭据状态、撤销结果、审计事件或专用验证机制，明确记录检查的身份和权限范围。不要为了“验证旧值失效”，在不受控的生产环境里重复尝试泄露令牌，也不要将秘密写入测试输出。GitHub 对其支持的部分令牌类型提供泄露后的自动或 API 撤销机制，但适用类型有限；不能把这一规则推广成所有 GitHub 凭据，更不能推广到其他服务。GitHub Token expiration and revocation

此外，“旧凭据拒绝”不一定等于所有已建立的访问同时中断。长期连接可能在认证后继续存在；短期令牌可能由旧密钥签发；云访问密钥可能换发会话凭证；证书有自己的撤销和吊销检查机制；应用安装授权也可能拥有独立的密钥与生命周期。具体边界取决于提供方实现。验证计划必须先说明对象是什么：原始密码、访问令牌、刷新令牌、证书、会话还是派生凭据，再依据其官方文档确定撤销是否级联、何时生效、现有连接是否需要重连。

一个有用的验收记录不是“轮换成功”，而是几个可复核事实：新凭据标识和权限范围；哪些消费者已切换及对应的部署版本或任务配置；提供方显示旧凭据已撤销的时间；安全、受限的旧凭据拒绝证据；仍未核实的连接、派生票据或副本；负责后续清理的人和截止时间。记录中不放凭据值。若管理界面只确认收到撤销请求，却无法证明所有会话已过期，就应写明这个差异，而不是夸大为全球立即失效。

Git 历史清理是另一条工作流

凭据失效后，再判断是否需要重写历史。GitHub 文档建议先撤销或轮换秘密；如果凭据已不能访问，清理历史未必是解决授权风险所必需的步骤。若仓库公开、合规要求或其他暴露面仍要求清除历史，可以评估使用 git-filter-repo，但这会改变提交哈希，需要协调分支、克隆和协作者。旧克隆若直接合并或推送，可能重新带回敏感提交；fork、缓存视图和拉取请求引用也可能仍可访问。历史重写不能替代凭据撤销，也不能承诺清空每个外部副本。GitHub 从仓库中移除敏感数据

清理当前文件、扫描构建产物和日志、协调克隆、评估历史重写、打开后续防护，是不同的任务。后续防护可以包括最小权限、短有效期或动态凭据、推送保护、秘密扫描、避免把值写入日志，以及明确的秘密所有者和到期策略。扫描器发现或未发现字符串，都只能作为一种证据；它不能替凭据提供方回答授权是否还有效。OWASP 的指南也把轮换、撤销和到期列为不同生命周期阶段，并指出潜在泄露时应安全撤销秘密。OWASP 秘密生命周期

读者追问：事件何时可以关闭？

处置关闭不是“搜索结果变绿”，而是基于当前证据做出的边界清楚的判断：风险对应的旧授权已撤销或有明确替代控制；已知消费者已切换或被停用；新凭据按预期工作；历史副本处理方式已记录；日志调查覆盖了明确的时间、资源和可用审计范围；剩余未知项有负责人和后续动作。若提供方不能说明现存会话是否继续有效，关闭记录就要保留这个未决边界。

还应区分“没有发现滥用”和“证明没有滥用”。如果审计保留期不足、日志字段不含调用者身份，或相关资源未开启记录，结论只能是证据有限。不能为了让事件看起来结束而写“没有数据被访问”。本文没有检查任何实际日志，因此不对是否发生过滥用或损失作判断。与 GitHub Actions 权限边界有关的配置，可另见为 GitHub Actions 设置最小令牌权限；那篇讨论的是工作流授权范围，并不替代泄露后的撤销与调查。
