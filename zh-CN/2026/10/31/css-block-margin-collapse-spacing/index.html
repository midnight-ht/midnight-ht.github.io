CSS外边距：两个24像素为何没有相加成48？

用普通块样本和正负计算解释相邻外边距，分开父子与兄弟边界，再选择padding或格式化上下文。

正文

核心要点

  • 满足条件的垂直外边距可能合并而非相加。
  • flow-root隔离父子边界，不消除内部兄弟合并。
  • 间距修复应同时检查尺寸、裁切和内容。

两个普通块各有相邻的二十四像素外边距，间距不一定相加成四十八。满足条件的垂直外边距会合并。排查应先确认布局和相邻关系，再决定内部留白或外部间距由谁提供；反复增大margin无法说明正在修哪条边界。

相邻不是“看起来靠近”

CSS 2.2的外边距合并规则定义了相邻条件与合并计算。以下讨论限定常见水平书写模式中的普通块流，不把结论直接推广到横向外边距、Flex或Grid项目。视觉上两个对象靠近，不足以证明它们的margin属于同一个合并组。

对于两个满足条件的相邻正外边距，合并结果采用其中较大者，不是相加。因此二十四和二十四形成二十四，二十四和十六也形成二十四。存在负值时，要考虑正值最大者与负值绝对值最大者之间的关系，不能简单挑“数字看起来更大”的一项。

这解释的是布局计算，不是浏览器随意忽略声明。开发者工具可能同时显示两个元素都声明了二十四，而边框之间距离仍是二十四；两份声明都在参与同一个结果。只检查样式面板里有没有被划掉的属性，可能找不到原因。

用完整样本分开观察父子和兄弟

以下静态文件未在浏览器运行。尺寸都是教学参数，可以保存为HTML后逐项修改；先不要添加全局reset，避免不知道哪条默认规则参与计算。

<!doctype html>
<html lang="zh-CN">
<meta charset="utf-8">
<meta name="viewport" content="width=device-width,initial-scale=1">
<title>外边距合并样本</title>
<style>
  body { margin: 0; }
  .panel { margin-top: 40px; background: #eee; }
  h1 { margin: 24px 0; }
  p { margin: 24px 0; }
</style>
<div class="panel">
  <h1>演示卡片</h1>
  <p id="first">第一段普通块内容。</p>
  <p id="second">第二段普通块内容。</p>
</div>
</html>

先观察两个段落相邻边框间的距离：在本样本的普通流条件下，两个二十四像素外边距预期合并成二十四。再只把第二段的上边距改成负八，按正负合并规则推导，这一对外边距形成十六。这里是纸面预期，没有测量结果，也不能把它套到任意已经存在边框、清除或布局约束的页面。

父子是另一个观察对象。panel没有顶部padding或border，标题又是首个流内块，标题的上边距可能与父边距合并。背景从哪里开始、父边框实际位于哪里，需要按这组关系观察，而不是把“标题向下二十四”想象成永远发生在灰色背景内部。

若设计要求灰卡片内部固定留白，应考虑由panel的padding表达，并重新审视标题自身外边距。若要求卡片与外部对象保持距离，则由外部margin承担。两种留白的归属不同，不能因为最终截图间距相同就视为同一个组件接口。

flow-root隔开的是什么？

CSS Display三级规范的flow-root建立新的块格式化上下文。用于这个样本时，它可以改变父子之间的外边距合并关系；但不会把内部所有普通兄弟块之间的合并都取消。这个边界对诊断非常关键。

如果给panel加display:flow-root，两个段落间仍是二十四，不足以证明属性没生效。父子边界与段落之间是不同关系：前者可能已经被隔离，后者仍在新上下文内部。应分别记录panel与标题的位置、第一段与第二段的位置，不要只读其中一个数字。

把容器改成Flex或Grid，也可能改变项目边距关系，但那是布局模型变更。它同时影响尺寸、对齐和排列，不能仅因为得到四十八的距离就宣布这是无代价修复。若页面原本是普通文章流，先确定是否真的需要新的布局模型，再考虑gap等间距机制。

为什么不直接加overflow:hidden？

一些overflow设置会建立相关格式化上下文，因此常被拿来顺带处理边界问题。它们也有自身的显示与滚动含义。隐藏溢出可能裁切下拉面板、长内容或焦点外轮廓，修好了上方间距却损失了另一项任务。需要隔离格式化上下文时，应考虑目的更明确的方案，并实际检查内容。

这不是说任何隐藏溢出都错误。如果产品确实要求裁切某区域，隐藏可能是有依据的选择；但其理由应包括内容策略，而不是把它写成“所有margin异常统一加这个”。已有的sticky与滚动祖先讨论过overflow对另一个机制的影响，改属性后需要一起检查相关祖先关系。

边框或padding也会改变父子相邻条件，但给容器塞一条透明边框来“挡住合并”，仍会改变尺寸合同。可以使用有明确设计意义的边框或留白，不能为了凑数字引入隐藏规则，又不告诉组件使用者。组件维护者应知道哪些空间属于内容区，哪些属于外部布局。

空块和多个负边距，为什么更难猜？

满足条件的空块可能让外边距穿过自身，参与合并的对象不一定只有直接看到的两条。多个负值也不是逐个累加后抵消正值。遇到这种情况，应列出实际合并组，再按规范关系计算，不能只看鼠标当前选中的那个节点。

因此建议先做最小对照：保留两个非空段落，排除额外祖先边距；然后逐步恢复空占位、标题、错误说明和组件包装。每恢复一个对象，记录变化与所涉及的关系。这个方法是诊断建议，没有运行日志或跨浏览器测量支持，不能包装成已经修复某个真实页面。

拟议验收同时比较声明值与边框坐标，覆盖普通兄弟、父子、负边距、空块，以及增加flow-root后的两类边界。对真实卡片还要放入长标题与错误状态，确认内容没被新裁切。横向margin不按这里的规则合并；使用逻辑属性或其他书写模式时，也应重新核对轴向条件。

交付可以写成一条明确约定：容器负责内部padding，段落间距按选定的流布局规则处理，外部margin由调用方管理。这样下一位开发者不会为了得到四十八而继续叠加二十四，而能先问这四十八究竟应该由哪一层负责。
