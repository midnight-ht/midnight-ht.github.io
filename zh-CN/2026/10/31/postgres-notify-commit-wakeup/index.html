NOTIFY 可以唤醒工作者，不能替它保存未完成任务

区分 NOTIFY 发送与接收两侧事务、同事务折叠和重连恢复，用两会话示例说明唤醒提示不能代替任务清单。

正文

核心要点

  • NOTIFY 在发送事务成功提交后生效，监听者事务也能延后接收。
  • 重复提示和初始重复读取不能直接变成重复副作用。
  • 重连恢复应读取持久工作状态，提示只负责唤醒。

NOTIFY 适合告诉工作者“有变化，去查一下”，不能单独承担断线后仍可恢复的任务清单。发送事务提交之前不会投递通知；监听连接自己的长事务也会延后客户端收到通知的时点。需要保证工作者重连后补处理，应把未完成工作保存下来，把通知作为唤醒提示。

为什么语句成功，通知还没有到？

PostgreSQL 18 的 NOTIFY 命令说明把两侧事务都列为投递条件：发送者事务成功提交后通知才生效；监听会话处于事务中时，要等它结束后才把通知交给客户端。本文于二〇二六年十月三十一日核对这份十八版文档，讨论数据库内通知，没有运行数据库或通知驱动。

这意味着应画两条时间线。发送端已经执行 INSERT 和 NOTIFY，但还没 COMMIT，另一端暂时收不到是符合语义的；发送者回滚，本次通知就不应出现。另一种情况是发送者早已提交，监听者却打开事务后一直做其他工作。只查发送端日志，会把接收端的事务等待误认成网络问题。

把通知与业务修改放在同一事务，可以让回滚的修改不发出这次提示，但这没有建立消费确认。通知交给了某条连接，不能说明工作者已处理表中的记录，更不能说明邮件或第三方调用已经完成。接收状态、认领状态、业务结果应保留各自的依据。

两条会话怎样把时点分开？

下面是未执行的教学步骤，使用 psql 连接同一个隔离数据库。两条终端分别保持各自会话；名称和数据为假设，不要直接粘贴进真实业务库。先在会话甲建立最小工作表并提交监听：

CREATE TABLE demo_work (
  id integer PRIMARY KEY,
  state text NOT NULL DEFAULT 'pending'
);
BEGIN;
LISTEN demo_work_changed;
COMMIT;

会话乙执行以下内容，但先停在提交之前：

BEGIN;
INSERT INTO demo_work(id) VALUES (1);
NOTIFY demo_work_changed, '1';
-- 先检查另一条会话，再单独执行下一行
COMMIT;

会话甲随后执行一条普通查询，让 psql 有机会读取并展示异步通知，同时核对表状态：

SELECT id, state FROM demo_work ORDER BY id;

预期关系来自文档推演：提交之前不能把通知当作已交付；提交后，甲应能够查询到已提交记录。终端什么时候打印异步通知，还受客户端读取连接的时机影响，不应把某行输出恰好出现的秒数写成数据库延迟测量。另开一轮用 id 为二并把乙的 COMMIT 改为 ROLLBACK，核对行与通知都没有成为这次已提交变化。

再让甲先 BEGIN，保持事务不结束；乙提交一条新记录后，甲在 COMMIT 前后分别观察通知交付。这个对照用来验证接收端事务边界，不能靠给乙重复执行 NOTIFY 来“修复”。测试结束后，在甲执行 UNLISTEN demo_work_changed;，再删除教学表；删除前确认它确实由本次实验创建。

为什么不能按通知条数核对任务条数？

同一事务中，对同一频道发送相同 payload，重复通知可能折叠。假设一次事务更改三条记录，三次都发送固定文本 changed，不能预期收到三次才算成功。改成不同 payload 能避免这一种折叠，却没有解决工作者离线时如何恢复，也没有引入消费者的完成确认。

因此，工作表需要保留任务身份与未完成状态；收到提示后按表中实际待处理记录工作，而不是根据提示次数加减计数。多个工作者还需要自己的认领、重试与幂等约定。通知机制没有替它们选择锁，也没有把外部副作用并入数据库事务。本站事务发件箱的交接边界讨论持久意图与外部交付；这里增加的是数据库唤醒信号本身的可见时点。

允许错过的在线界面刷新可以只依赖通知，前提是产品允许错过提示，并有再次查询或刷新取得当前状态的路径。不应为了一个可丢失提示先引入复杂队列；同样，不应因为提示够快，就拿它承担需要逐项追踪的履约工作。

监听应该先注册，还是先读取待处理记录？

先提交监听注册，再读取初始状态，然后依据通知继续回查。LISTEN 命令的 Notes特别说明首次注册的竞态：注册生效的时点与查询所观察的状态并不完全重合。先查表再监听，会留下查询结束到监听生效之间的变化窗口。

按推荐顺序仍可能初期收到已经在初始查询中见过的变化，所以工作身份与状态判断要允许重复发现。发现同一记录两次不是允许执行两次副作用；认领或幂等需要在真正处理的位置落实。重连时重新走建立监听、补读持久状态的过程，不把旧连接的内存标记当作恢复依据。

payload 放完整用户数据，可以少查一次表吗？

不宜把广播提示当成私密载荷。NOTIFY 文档说明通知对数据库用户可见，默认 payload 长度还受到字节上限约束。更容易审查的选择是发送受控标识，再由工作者按自己的查询权限读取必要内容；标识本身也要评估是否泄露信息，不能只去掉姓名就宣布已经脱敏。

还可以做一个不靠计时的恢复测试：暂停工作者的读取，让发送事务先提交，再主动断开监听连接。重连以后仅凭工作表中的 pending 记录重新发现任务，检查同一任务的最终状态与外部效果次数。这个实验验证的是恢复设计，不要求某个通知恰好在几毫秒内到达；如果实际客户端尚未接收提示，也不应阻止它通过持久状态补查。

若同一个工作者在处理记录后、写回完成之前退出，后继工作者可能再次发现它。测试应明确这次是重复发现还是重复执行，并保留同一业务身份，不能通过生成新任务编号掩盖恢复窗口。需要外部效果只发生一次时，还必须由接收方幂等、结果查询或明确补偿安排支持；收到一次通知并不能作为这项保证。

验证时分别记录发送提交、监听事务结束、客户端接收、工作认领和最终结果，并测试断开后重连、重复提示以及没有提示时的补查。没有运行这些步骤，本篇不报告交付成功率。评审可以先问一句：工作者完全没收到提示时，重启后靠什么知道还有哪一条没做？如果答案只有内存里的通知列表，恢复合同还没有成立。
