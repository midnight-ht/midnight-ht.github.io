HTML复选框显示半选，提交的是第三种值吗？

用完整本地全选示例分开半选、勾选与原生条目，解释激活重算、分页范围与三态业务值。

正文

核心要点

  • 半选状态独立于checked，不增加第三个提交值。
  • 全选控制器应总结明确的子项集合。
  • 过滤、恢复与数据变化后需要重新计算。

全选框显示横线，原生表单不会因此发送一个mixed值。indeterminate独立于checked，表达部分选择时，应用应同时管理参与计算的子项集合与这两个状态。先看实际勾选了谁，再检查提交内容，不能从横线外观反推业务值。

半选不是第三个提交值

当前HTML标准的input定义明确区分indeterminateness和checkedness。前者影响复选框的呈现与无障碍语义，不只是涂一个装饰符号；但它并没有增加第三种checked值。标准页面标注二〇二六年十月三十日更新，不能沿用“纯视觉、没有语义影响”的过窄解释。

原生表单条目构造规则则按勾选状态决定复选框是否进入相应条目，选中的值来自value等适用规则。这两套规则可以同时成立：主控处于混合状态，而载荷只包含实际勾选的子项。视觉摘要与业务明细分别承担责任。

因此，设计稿里的空框、横线、勾号，需要对应一份明确状态表。对全选控制器，可以约定零项被选时两个状态都假，部分选择时checked假而indeterminate真，全部选择时checked真而indeterminate假。这是示例的应用选择；不要把这个约定误读成浏览器会自动发现所有子项并计算。

一个完整的本地通知设置例子

以下文件可保存为HTML样本。它没有后端，没有发送通知，也未在浏览器运行。三种渠道只是教学选项；提交处理会阻止导航，在页面显示原生FormData收集到的子项值。

<!doctype html>
<html lang="zh-CN">
<meta charset="utf-8">
<title>通知选择示例</title>
<form id="prefs">
  <fieldset>
    <legend>接收哪些教学通知</legend>
    <label><input id="all" type="checkbox">全选这三项</label>
    <label><input class="item" name="channel" value="mail" type="checkbox">邮件</label>
    <label><input class="item" name="channel" value="sms" type="checkbox">短信</label>
    <label><input class="item" name="channel" value="inbox" type="checkbox">站内消息</label>
  </fieldset>
  <button type="submit">查看待提交值</button>
</form>
<pre id="result"></pre>
<script>
const form = document.querySelector('#prefs');
const [master, ...items] = form.querySelectorAll('input');
const total = items.length;
function sync() {
  const selected = items.filter(item => item.checked).length;
  master.checked = total > 0 && selected === total;
  master.indeterminate = selected > 0 && selected < total;
}
master.onchange = () => {
  for (const item of items) item.checked = master.checked;
  sync();
};
for (const item of items) item.onchange = sync;
form.onsubmit = event => {
  event.preventDefault();
  document.querySelector('#result').textContent =
    JSON.stringify(new FormData(form).getAll('channel'));
};
sync();
</script>
</html>

主控刻意没有name，它是一个改变子项的操作，不是第四种通知渠道。先勾邮件，按示例算法推导，主控显示半选，输出数组包含mail；再激活全选，预期三个子项都被选择，输出三项。取消其中一个后再次同步，主控恢复半选。这些是依据代码的预期，尚无实际运行记录。

原生用户激活会改变checked并清除indeterminate；应用再根据子项重算主控。因此，从半选状态点击后究竟全选还是清空，必须与产品操作约定一致。本例在部分选择时把checked设为假，激活后走全选路线。框架若另行覆盖点击或重建节点，需要在最终输出上复验，不能只看状态变量名称。

一个失败写法只设indeterminate=true，从未更新checked。若该主控还有name并保持checked真，就可能把主控值也加入请求；横线并没有替你关闭勾选。另一个失败是只更新主控外观而不改变子项，页面看似全选，提交集合却没有变化。逐项比较DOM状态和实际条目能把两类问题分开。

筛选后点全选，是选谁？

例子把范围固定为这三项，所以计算简单。实际列表可能分页、过滤或包含不可操作项。全选当前可见记录与全选全部搜索结果，是两份不同承诺，不能由indeterminate属性替产品选择。按钮文案、计数和最终请求都需要说明同一个范围。

假设搜索得到一百条，只显示当前十条。用户勾了三条后切到下一页，主控的混合状态可能表达当前页，也可能表达全部结果。若界面没有说清，算法即使没有错误也会产生误解。应记录已选身份集合、当前可选集合和批量动作范围，避免仅从当前DOM里有几个checkbox推导全部选择。

禁用子项也要明确。是排除出全选范围，还是保留为已选但暂不能修改，取决于业务。若排除，计数分母和提交允许集合应同步；若保留历史选择，需解释它是否仍会生效。已有的复选框逐项必填与组约束处理至少选一项的问题，本篇不把那个校验规则混进半选计算。

数据更新后也应重算。某渠道被移除、恢复草稿后出现旧标识、或者组件重新挂载，都可能改变参与集合。不要在初始化时只写一次横线，然后让它随DOM生命周期失真。同步职责应随着真实数据变化执行，而不是假设浏览器知道哪个主控属于哪些子项。

后端确实需要三态，能直接发送主控吗？

如果业务值是允许、拒绝、继承三种含义，应定义明确的枚举与交互，不要把全选控制器的半选当成继承。两者可能视觉相近，含义却不同：部分子项被选，是对集合的摘要；继承某个上层设置，是字段自身的策略。请求应能区分这些实体。

拟议验收覆盖零、部分、全部选择，主控鼠标及键盘激活，取消一个子项，过滤切页和数据重新加载。记录checked、indeterminate、FormData以及最终保存身份集合。真实服务还要验证允许值与权限；本地输出数组不构成发送或持久化证据。

当参与集合为空时，“全部已选”不能只按已选数量等于总量推导，因为零等于零并没有选中任何对象。样本用总量大于零作为checked的额外条件。真实页面还应说明为什么没有可选项，并决定全选操作是否暂不可用；不要只留一个能切换的空控制器，让用户误以为已经完成选择。

保存失败也有两份状态：用户当前的选择，与服务器最后确认的选择。主控应继续总结当前可修改集合，同时明确尚未保存；不能把请求失败后恢复的旧数据悄悄当作用户刚才的答案。若服务明确拒绝某个已选项，应指出该对象及修正路径，再重新计算摘要，不要用清空整组来掩盖失败。这些恢复行为需要真实业务合同，本地样本没有实现持久保存。

辅助技术验收也应检查主控名称是否说清范围、混合状态能否被理解，以及子项是否保持可操作。本文没有读屏或兼容性结果。交付时应让测试能回答“横线总结哪组选择”和“请求提交了哪组身份”，两者一致才表示半选状态在服务实际任务。
