用了 Decimal，0.1 为什么仍变成一长串小数？

通过标准库完整程序区分十进制文本、已有 float、上下文算术精度和 FloatOperation 陷阱，避免把类型选择当成来源恢复。

正文

核心要点

  • 由 float 构造 Decimal 精确保留的是已有浮点值。
  • 上下文精度不等于对任意构造输入截短。
  • 浮点陷阱有明确例外，入口合同仍需独立验证。

Decimal(0.1) 接收的是已经形成的二进制浮点数，随后准确保存那个值；它不会恢复调用方原本想输入的十进制文本。若接口要求十进制输入语义，应从入口保留字符串或使用不会先变成 float 的解析方式。调小 Decimal 上下文精度，也不能把构造步骤当成自动修复浮点输入的舍入器。

精确保存，为什么仍有很长的小数？

Python 3.14 decimal 参考说明，由 float 构造的 Decimal 会准确转换那个浮点值。本文于二〇二六年十月三十一日核对的页面标为 Python 3.14.10；没有执行下列程序，也不以示例决定任何金额、税费或结算规则。

字面量 0.1 先由 Python 创建为 float，再交给 Decimal。二进制浮点不能准确表示这个十进制分数；Decimal 把已获得的二进制近似值准确展开，所以结果看起来比输入长得多。问题发生在交接之前，不能要求后一个类型猜出前一个类型丢掉的意图。

Decimal('0.1') 则从十进制文本构造。两者的区别不是 Decimal 有时精确、有时失效，而是接收到的数据不同。来自外部测量的 float 可能就是应当保留的值；来自用户十进制输入的 float 可能已经偏离接口约定。选择依据应是来源合同，不是打印结果是否够短。

显式的 Decimal.from_float 可以表达“我有意保留这个浮点数”的选择。把所有 float 都先转字符串再交给 Decimal，则是采用该 float 当前字符串表示对应的十进制数，不能恢复之前的原始文本、尾随零或输入格式。因此，不宜把它宣传为适用于所有历史数据的精度恢复公式。

上下文 precision 在哪个阶段生效？

官方文档区分构造与算术：新 Decimal 保留的数字由输入决定；上下文的精度和舍入在算术运算等相应操作中起作用。把 precision 设为三，不表示任意字符串构造后都只剩三位有效数字，更不表示自动变成三位小数。有效数字与小数位是不同约束。

下面是未执行的完整教学程序。它不读写文件，不连接服务，所有输入都直接给出。输出值应由实际运行记录；程序重点是验证关系，而不是复制一段看似真实的终端日志。

from decimal import Decimal, FloatOperation, localcontext


def main():
    from_text = Decimal('0.1')
    from_binary = Decimal(0.1)
    explicit_binary = Decimal.from_float(0.1)
    print('text:', from_text)
    print('float:', from_binary)
    assert from_binary == explicit_binary
    assert from_text != from_binary

    with localcontext() as ctx:
        ctx.prec = 3
        exact_input = Decimal('1.23456')
        rounded_sum = exact_input + Decimal('0')
        print('construction:', exact_input)
        print('arithmetic:', rounded_sum)
        assert exact_input == Decimal('1.23456')
        assert rounded_sum == Decimal('1.23')

    with localcontext() as ctx:
        ctx.traps[FloatOperation] = True
        try:
            Decimal(0.1)
        except FloatOperation:
            print('implicit float input rejected')
        else:
            raise RuntimeError('expected FloatOperation')
        intentional = Decimal.from_float(0.1)
        print('explicit conversion:', intentional)


if __name__ == '__main__':
    main()

第一组比较明确区分文本与浮点来源。第二组先保留输入，再做一次加零运算，让算术精度作用的位置可见。加零看似不改变数学值，却经过了上下文运算；若团队在不同阶段重复计算或舍入，结果策略需要单独约定。示例中的三位只用于说明机制，不是业务精度推荐。

第三组把 FloatOperation 设为陷阱，帮助发现不小心的浮点构造。使用 localcontext 让示例的配置限于本范围，避免改变后面不相关代码所依赖的上下文。程序中的断言用于教学关系，不能替代生产入口的显式拒绝逻辑；生产校验不应依赖可被解释器优化关闭的 assert。

FloatOperation 能阻止所有浮点混入吗？

不能把它理解成通用污点追踪。文档对混合操作有具体规定：设置陷阱后，部分构造与大小比较会报错，但相等比较以及显式转换存在例外。示例有意调用 from_float，即使陷阱开启也表达允许的显式转换。审查者仍要沿序列化、解析、计算与持久化追踪类型，不应看到一个配置就宣布整条链没有 float。

如果接口只接受十进制字符串，可在边界先检查输入类型，再按明确语法解析，随后检查有限值与业务范围。Decimal 可以表示非有限值，不代表业务字段允许 NaN 或 Infinity。非常长的输入也需要资源预算；这些条件应由真实字段规则决定，本篇没有替项目制定最大长度或合法格式。

如果上游必须发 JSON 数字，应核对具体解析器是否先构造 float，以及能否按协议直接生成十进制类型。不要在已经变成 float 的下游才补一个 Decimal，然后宣称原始十进制无损。接口也应说明输出是字符串、整数最小单位还是其他明确表示，避免发送时再次丢掉类型选择。

Decimal(str(value)) 能恢复用户输入吗？

不能据此恢复来源。它只能依据当前 value 的字符串表示创建十进制值。用户可能提交过更多小数、指数形式或末尾零，这些信息在早先转换时可能已经丢失。若审计必须知道原始表示，应在允许的范围内保留它，或从可信原始记录重建；不能从一个较短结果伪造曾经收到的文本。

已有的PostgreSQL numeric 与输入舍入解释存储列比例为什么不等于输入拒绝规则。这里是更早的 Python 构造边界：数据库尚未接触数据，应用可能就已选择了另一种数值。两层都要核对，不能把最终数据库类型正确当成前面没有损失的证据。

入口测试还应区分数值相等与表示相同。假设协议允许字符串零点一和零点一零，业务数值可能相同，但若用户指定的小数位参与后续展示或计量语义，就需要保留这一差异。是否合并必须由字段合同决定；既不能只靠数值比较证明原文没变，也不能反过来把所有末尾零差异都判为错误。

另一组反例应从真实请求字节开始：把同一字段分别以字符串和 JSON 数字发送，记录解码后类型、进入计算前的表示、算术结果与数据库参数。若测试直接在函数里构造 Decimal 字符串，会跳过最容易引入 float 的解析层。测试成功最多覆盖明确的那条输入路线，不能替另一种客户端序列化方式背书。

拟议验证覆盖字符串构造、float 构造、显式转换、小精度算术、陷阱与例外、非有限值，以及请求解析到数据库参数的实际类型。测试预期应来自输入合同，并与被测实现分开保存。本篇未运行这些测试。决定使用 Decimal 后，还要回答它接到的究竟是哪一种值；类型名称不能代替这一段来源说明。
