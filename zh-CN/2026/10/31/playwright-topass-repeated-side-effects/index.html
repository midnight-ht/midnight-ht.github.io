Playwright toPass重复点击，为什么可能创建多条记录？

用可独立准备的本地测试分开一次创建与多次观察，比较toPass、poll和超时及不确定结果恢复。

正文

核心要点

  • toPass可能重复执行整个回调。
  • 写操作的可重复性需要真实业务合同。
  • 局部观察超时不会延长外层测试预算。

创建工单的点击和“工单已出现”检查一起放进toPass，检查失败后整块代码可能重跑。等待结果的测试由此变成再次创建的测试。先把触发副作用与重复观察分开，才能判断重试究竟在等待什么、又可能改变什么。

重跑的单位是一段代码

Playwright断言文档的expect.toPass说明，它可以重试代码块直到通过。同一文档也提供expect.poll，用于反复取得观察值再检查条件。不能因为两者出现在断言章节，就认为传入的回调只会运行一次，或只重试最后那句expect。

假设回调先点击创建，再立即读取列表数量。如果首次读取太早而失败，下一次执行会从点击重新开始。服务已经接受的第一次创建，不会因为测试断言失败而被撤销。这个推论来自回调重跑与业务副作用的组合，不是Playwright承诺所有页面一定创建重复记录。

风险取决于真实动作。切换一个本地显示面板可能可重复，提交一笔不可撤销申请则不同；有幂等合同的命令又有自己的条件。评审应看回调里每个动作做什么，不能仅凭函数名叫“检查状态”就假定它没有写操作。

一个可以独立准备的观察样本

以下是未执行的完整Playwright Test样本。它用本地DOM模拟延迟显示，不访问接口，不代表后端工单服务。准备新空目录，执行下面命令安装测试工具，并把代码保存为observe.spec.mjs，再运行指定文件。命令、依赖下载和测试均未在本文执行；实际项目应使用自己的锁文件与版本策略。

npm init -y
npm install --save-dev @playwright/test
npx playwright install chromium
npx playwright test observe.spec.mjs --workers=1

import { test, expect } from '@playwright/test';

test('create once, then observe one local record', async ({ page }) => {
  await page.setContent(`
    <button id="create">Create demo record</button>
    <output id="attempts">0</output>
    <ul id="records"></ul>
    <script>
      let attempts = 0;
      const [button, counter, list] = ['create', 'attempts', 'records'].map(
        id => document.getElementById(id)
      );
      button.onclick = () => {
        attempts += 1;
        counter.value = String(attempts);
        const record = document.createElement('li');
        record.dataset.recordId = 'demo-' + attempts;
        record.textContent = 'Pending';
        list.append(record);
        setTimeout(() => { record.textContent = 'Ready'; }, 100);
      };
    </script>
  `);
  await page.getByRole('button', { name: 'Create demo record' }).click();
  const [record, records, counter] = [
    '[data-record-id="demo-1"]', '#records li', '#attempts'
  ].map(selector => page.locator(selector));
  await expect(record).toHaveText('Ready');
  await expect(async () => {
    expect(await records.count()).toBe(1);
    expect(await counter.innerText()).toBe('1');
  }).toPass({ timeout: 2_000, intervals: [100, 250] });
});

创建动作在可重试回调外。等待Ready使用会重新检查目标的定位器断言，随后toPass里只有读取和比较。示例给出局部两秒预算，只是教学设置，不是产品性能目标。record身份由本地样本明确产生，不存在未定义接口或假设已经登录的浏览器夹具。

这个样本也有边界：它证明的目标是本地创建次数与延迟文字，不是持久化或跨服务完成。真实项目应从经过确认的业务契约取得对象身份，再观察相同对象的终态。不能照抄demo-1作为生产选择器，更不能把本地DOM变化称为工单已经入库。

多个条件需要一起等，应该选什么？

如果目标只是页面文字变成某个值，优先研究相应的自动重试定位器断言，不必为了“更稳”再包一层。需要从API或其他来源反复取一个值时，可以考虑poll；需要一组观察和断言一起通过时，可以研究toPass。选择依据是观察合同，而不是哪个方法名字听起来更强。

一组观察也不必然构成跨系统原子快照。先读列表数量、再读状态，两次读取之间应用可能变化；某次回调全部通过，只说明这次检查满足了所写条件。若业务需要同一版本数据的联合证明，应由接口或测试数据安排提供相应一致性，不能让toPass三个字代替它。

测试整场重试又是不同层次。已有的重试通过与首轮证据讨论worker重建与多次测试尝试。本篇的toPass可以在同一次测试内重复回调，不能拿worker重建来解释每次探针；诊断记录应分别标识测试尝试与回调观察。

超时配置会继承expect吗？

当前官方指南特别说明，toPass默认timeout为零，不遵守自定义expect超时。需要给这段观察设置局部上限时，应明确配置并核对实际版本。局部配置也不能延长整条测试已经耗尽的时间；外层测试预算仍可能先到期。

这里不提供一组适用于所有CI的等待数字。例子选择两秒只为让边界可见，真实环境要说明状态何时应该出现、为什么允许等待这个时间、失败时保留什么。无限扩大预算无法修好一个永远观察错对象的条件，只会把错误更晚送到报告里。

创建请求超时，还能直接再点一次吗？

创建结果不确定时，再次执行可能产生新的副作用。应依据真实服务的查询、请求身份或幂等机制确认先前结果，再决定恢复动作；测试框架不会把超时解释成服务保证没有接受。这里没有实现一个通用业务重试器，也不假造接口支持幂等键。

如果确实在测重复点击防护，就应有意识触发多次，并断言产品承诺的记录数量与反馈。那是一条独立测试，不能把意外重复点击当作增强测试覆盖。一次动作、多次观察适合等待原动作的结果；多次动作则需要自己的业务预期。

“读取”也需要检查实际成本。某个看似查询的接口可能触发刷新、消耗配额或访问外部服务；把它放进高频探针，不会因为测试称它为观察就自动变得无害。应采用项目认可的可重复读取合同，并为频率留出合理间隔。样本只读取本地DOM，所以没有远程调用的这些责任。

清理也不是回调失败的自动回滚。真实测试若留下临时记录，应按可追踪的测试身份清理，并保存清理失败；不能让后续重试误把旧记录当新成功。延迟任务在测试结束后是否仍运行，也需要由真实环境处理，本文的本地页面样本不能替服务端生命周期作保证。

拟议验证可以把样本的延迟拉长，记录每次动作和观察时间，并故意将点击移入回调比较次数变化。保留源文件、实际工具版本、命令与原始结果，才能报告执行结论。本文未运行这些变体。交付前先圈出toPass回调里的每个写操作，逐一说明它为何可以重复；解释不清的，应先移出重试边界。
