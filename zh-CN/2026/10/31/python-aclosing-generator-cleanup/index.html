用 aclosing 把异步生成器的关闭留在当前任务内

用提前 break 和消费者异常两条完整路径检查 aclosing 的关闭时点，说明借用所有权、异步清理与取消时限的区别。

正文

核心要点

  • 结束 async for 消费不能直接声称生成器已关闭。
  • aclosing 在拥有者范围退出时 await aclose。
  • 借用对象的关闭权与清理耗时需要独立约定。

拥有异步生成器的调用方，提前结束 async for 时，应明确等待它关闭，而不能只把 break 当作清理已完成。contextlib.aclosing 在 async with 退出时 await 对象的 aclose，让生成器的异步退出代码留在迭代时的上下文中。它安排的是关闭责任，不提供远程回滚或硬性清理时限。

停止消费，不等于关闭生产者

Python contextlib 的 aclosing 说明专门覆盖异步生成器因 break 或异常而提前退出的确定性清理，并说明退出逻辑在与迭代相同的上下文中执行。该工具从 Python 三点十提供；本篇于二〇二六年十月三十一日核对 Python 3.14.10 文档，没有运行异步程序。

异步生成器可以多次 yield，把数据逐步交给消费者。暂停时，它自己的 finally 还可能需要 await，例如归还一个异步资源。消费者只取到第一条就离开循环，说明“不再取下一条”，不能据此声称那个暂停的生产者已经完成退出逻辑。生命周期需要由持有资源的范围明确表达。

不能把这种不确定性描述成“所有 break 都永久泄漏”。垃圾回收、引用保留与事件循环收尾会影响实际观察到的时点。问题是调用方能否承诺在当前范围结束前清理完成，而不是某个解释器最终有没有做善后。若关闭依赖请求上下文或同任务资源，拖到外围收尾可能已经离开这些依赖的有效期。

相反，完全消费且正常完成的生成器，可以自然走到自身退出；由更高层统一管理的共享来源，也不能由每个借用者擅自关闭。因此，使用 aclosing 的前提应是这里确实拥有这次对象的关闭责任，而非只因出现 async for 就机械加包装。

在当前范围内等待关闭

下面是未执行的完整标准库示例，使用列表记录控制流，不连接真实数据库或网络。finally 里的 sleep 只创建一个需要 await 的清理步骤，不代表测量了任何资源归还耗时。

import asyncio
from contextlib import aclosing


async def values(events):
    try:
        yield 1
        yield 2
    finally:
        await asyncio.sleep(0)
        events.append('closed')


async def consume_one():
    events = []
    async with aclosing(values(events)) as source:
        async for item in source:
            events.append(f'read:{item}')
            break
        events.append('loop ended')
    if events != ['read:1', 'loop ended', 'closed']:
        raise RuntimeError(f'unexpected cleanup order: {events!r}')
    print(events)


async def consume_with_error():
    events = []
    try:
        async with aclosing(values(events)) as source:
            async for item in source:
                events.append(f'read:{item}')
                raise ValueError('consumer rejected item')
    except ValueError:
        if events != ['read:1', 'closed']:
            raise RuntimeError(f'cleanup missing: {events!r}')
        print('consumer error preserved', events)
    else:
        raise RuntimeError('consumer error disappeared')


async def main():
    await consume_one()
    await consume_with_error()


if __name__ == '__main__':
    asyncio.run(main())

第一段在循环退出后先登记 loop ended，离开 async with 时才等待生成器关闭，随后检查 closed 已存在。检查放在范围之外，验证的是对外返回之前的关闭责任，而不是只观察 finally 曾经打印过一行。第二段让消费者抛错，预期关闭仍发生，并且原消费者错误没有被伪装成正常成功。

这些顺序是依照代码与文档的预期，不是本次运行日志。若换成实际客户端资源，应验证该资源的 aclose 合同：它可能只释放本地句柄，也可能需要等待远程协议结束；同名方法不能自动扩张成“服务端已经撤销所有动作”。示例列表标记只能验证控制流，不能证明真实连接归还。

没有 aclosing 的对照应该观察什么？

对照可以去掉外层 async with，保留生成器引用，提前 break 后立即观察 events，再由测试明确 await source.aclose，比较前后状态。保留引用是为了让实验问题集中在关闭时点，避免垃圾回收时机掩盖它。不要编造所有平台都会打印完全相同的延迟顺序。

资源借出次数、关闭完成与消费者异常，是三份不同断言。只有正常路径经过 finally，还不能证明消费失败时同样清理；只有捕获到了 ValueError，也不能证明清理没有漏掉。示例把二者放在同一条异常路径检查，实际项目还应注入关闭函数自身抛错，核对异常链和日志保留原始原因。

本站同步 contextmanager 的单次 yield 协议讨论的是一次借用的进入与退出。本题的异步生成器却可以产生多条数据，aclosing 只负责在拥有者退出时结束它；不要因为都用了生成器，就把单次 yield 限制套到这里。

借来的异步迭代器，也应该一律关闭吗？

先核对对象是否提供 aclose，以及关闭权归谁。异步迭代能力不等于所有对象都带同样的关闭方法；共享的订阅或由调用方继续使用的生成器，也不能由内部辅助函数随意终止。函数接口可以明确约定“接管并关闭”或“只借用，不负责关闭”，让调用者知道返回后是否还能继续消费。

假设一个解析函数只需查看前两项，然后把迭代器交给下一阶段。如果它包上 aclosing，下一阶段可能接到已经关闭的来源。若预期本来就是放弃余下内容，则关闭合理；若要继续，应该把关闭放到真正拥有整段流程的外层。清理越早不必然越正确，正确时点取决于谁还需要使用资源。

对于请求级资源，可以由入口统一创建来源、完成消费与关闭，再把已经取出的纯数据传给其他函数。需要长时后台消费则应建立任务身份和独立生命周期，不能通过返回一个生成器就默认后台拥有者已经存在。这是所有权设计建议，不是 aclosing 自动提供的任务管理功能。

aclosing 会让清理立刻结束吗？

它会 await 关闭，不承诺关闭函数的耗时。清理如果阻塞、抛错或在取消中再次被中断，调用方仍须有明确的可观察结果。本站wait_for 超时与取消结算说明等待预算与清理完成不能混为同一时点；在 aclose 外再加一个超时，也不等于资源已经释放。

测试拥有权时，可以让辅助函数只消费一条，然后由外层继续读取下一条。若合同是借用，第二次读取应该仍可按约定工作；若合同是接管并放弃余项，外层就不应再依赖继续读取。这个对照测试的是接口承诺，而不是单纯统计 aclose 被调用了几次。关闭次数正确，放错位置仍可能破坏后续阶段。

同样应区分清理启动与清理完成。让 finally 在一个测试事件上等待，确认外层范围仍未退出，再释放事件，检查外层随后结束。这样不必规定某台机器几毫秒内打印日志，就能证明调用方真的等待了关闭。若关闭抛错，则需要检查调用方观察到失败，而非只留下 closed started 标记便进入成功流程。

拟议验证应覆盖完全消费、首项后 break、消费者异常、关闭异常、调用方取消与共享借用。分别检查最终标记、错误传播、资源计数和后续使用是否符合合同。本文没有执行这些检查。评审时先在代码里找出真正的拥有者，然后让它在离开自身有效范围前等待关闭；若无法等待，就应明确交接剩余责任，而不是依赖事件循环最后替所有人收拾。
