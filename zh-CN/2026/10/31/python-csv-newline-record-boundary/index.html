CSV 只有两条记录，为什么 splitlines 数出三行？

用完整 CSV 往返程序区分文本换行转换与带引号记录语法，保留多行字段，并分别报告记录号与物理行号。

正文

核心要点

  • CSV 带引号字段可跨物理行，文本行数不等于记录数。
  • newline 空串让 CSV 管理换行，不是删除内容中的换行。
  • 字段往返、格式拒绝和下游解释需分别验证。

一条 CSV 记录可以在带引号字段里包含换行，所以文本行数不等于记录数。不要先用 splitlines 拆成“一行一条”，再要求 CSV 解析器恢复已经丢掉的边界。使用 Python csv 模块读写文件时，以 newline='' 打开，让 CSV 层管理换行，并分别核对字段内容与记录数量。

两层换行处理，分别负责什么？

Python csv 文件读写参考要求文件对象按上述 newline 方式打开，并说明嵌入换行与额外回车的相关问题。本文于二〇二六年十月三十一日核对 Python 3.14.10 文档，没有运行程序，也没有对 Windows 与其他平台给出兼容性通过结果。

文本文件层负责把字节解码成文本，并可能按 newline 设置转换行结束形式。CSV 层则还要识别引号、分隔符、转义及记录终点。当一个字段处于引号内，遇到换行可能是字段内容；在相应语法位置遇到换行，才是记录结束。两层各自“帮助处理”而没有约定，可能让内容或行结束被重复改变。

newline='' 不是禁止文件里出现换行，也不是把换行符变成空字符串。它是文件打开配置，让 csv 模块按自己的规则处理行结束。若把这个参数解释成“读入后删除换行”，刚好会破坏需要保留的多行备注。处理后的文字看起来更整齐，不等于与原始数据相同。

假设客服备注是“门口无人”换行“请电话联系”。这两行共同属于一条客户记录，而不是两位客户。若按文本行计数，第二行可能被错误当成缺少编号的新记录；若简单拼回，也可能把两个词之间应有的换行或分隔关系改掉。应让知道 CSV 引号状态的解析器决定边界。

写出再读回，怎样保留多行字段？

下面是未执行的完整标准库程序。它在本次临时目录里创建文件，写入两条假设记录，再读取并比较结构；没有依赖未定义的数据库、外部接口或手工生成的旧文件。

import csv
from pathlib import Path
from tempfile import TemporaryDirectory


def main():
    original = [
        ['101', 'Lin, Mei', 'first line\nsecond line'],
        ['102', 'He said "hello"', 'single line'],
    ]
    with TemporaryDirectory() as directory:
        path = Path(directory) / 'customers.csv'
        with path.open('w', encoding='utf-8', newline='') as output:
            writer = csv.writer(output)
            writer.writerow(['id', 'name', 'note'])
            writer.writerows(original)

        with path.open('r', encoding='utf-8', newline='') as source:
            reader = csv.reader(source, strict=True)
            header = next(reader)
            restored = []
            for record_number, row in enumerate(reader, start=1):
                if len(row) != len(header):
                    raise ValueError(f'wrong field count: record {record_number}')
                restored.append(row)
                print('record:', record_number, 'physical line:', reader.line_num)

        if restored != original:
            raise RuntimeError('CSV round trip changed fields')
        print('records:', len(restored))


if __name__ == '__main__':
    main()

writer 决定哪些字段需要引号，reader 按同一默认 dialect 读回。第一条备注中的换行应保留，姓名里的逗号不应成为额外列，第二条姓名里的引号也应保留。程序比较的是完整嵌套列表，不只比较有没有抛异常。临时目录在离开范围后清理，结果若要交给后续系统，必须在清理前完成交接或另存为有保留政策的产物。

strict=True 用于让某些格式错误明确抛出，但不等于完整业务验证。三列并不证明编号合法、姓名属于当前租户或备注满足长度规则。示例的字段数量检查只是固定教学结构的一个额外条件；真实导入还应约定是否允许空字段、空记录、缺少表头和重复列名。

reader.line_num 是第几条记录吗？

它统计从源迭代器读取的物理行数，不等于返回的记录数。跨行字段会让一次 reader 结果消耗多行。示例因此同时打印 enumerate 维护的记录号和 reader.line_num，不用一个数字混称“第几行错误”。

向使用者报告失败时，可说清“第几条记录，结束于第几条物理行”，必要时保留起止范围。如果有表头，记录号是否包含表头也要约定；否则用户按电子表格显示的行号查找，客服却按文本编辑器行号定位，两边都说同一个编号却看着不同内容。错误报告不应直接复制敏感备注，使用受控标识与必要片段即可。

这也解释了为什么先对源文本 splitlines 再逐条单独解析不可取。分割后丢失的换行，解析器无法知道原本是字段内容还是记录边界。即便某个简单文件恰好能处理，换一个合法的带引号多行字段就会破坏假设。若产品采用严格的自定义逐行协议，应明确它不接受哪些 CSV 特性，而不是沿用 CSV 名称却省去条件。

文件多出空行，删掉所有空字符串就修好了吗？

先定位是哪一层增加或转换了行结束。在某些平台上，写文件层再处理 CSV writer 已给出的行结束，可能产生额外回车。按文档配置文件入口，比事后过滤更接近原因。过滤策略还可能误删业务允许的空记录，或者改变保留空白有意义的字段；删掉后导入成功并不能证明内容没变。

编码、dialect 和记录语法也要分别验证。newline 配置不会修复错误编码；选择逗号分隔也不代表所有供应方文件都使用相同引号规则。针对真实来源建立小样本，包含逗号、引号、嵌入换行、空字段和不完整引号，逐项核对是否接受以及得到的字段。不要根据前几行推测出的格式，就对整份文件作无条件承诺。

与本站网络分块中的字符解码相比，这里多了一层记录语法：字节正确变成字符之后，换行是否结束记录仍需要 CSV 规则回答。二者可以出现在同一导入链，但修好其中一层不代表另一层成立。

验收样本最好有两份只在字段换行上不同的数据：一份备注是真正的换行，另一份备注是反斜杠加字母组成的两个可见字符。它们在界面日志里可能被相同转义形式展示，原始字节和解析字段却不同。只有比较保存后的内容，才能避免把打印格式当成数据本身。

记录数量还要与字段位置共同核对。假设一条姓名含逗号，错误拆列后仍可能恰好凑出两条记录，单独检查数量会通过。应按稳定编号找到每条结果，再比较姓名和备注，而不是依赖输出顺序。对于格式错误的文件，保存拒绝原因与足够定位的信息，并确认没有把失败样本悄悄改写成另一份看似合法的数据。

向电子表格交付时，还需另行处理公式解释等安全规则。一次 CSV 往返一致只验证本程序的结构与内容，不证明其他应用如何解释单元格。本文未执行往返、异常文件或跨平台测试；验收应保存输入字节、解析记录与预期字段，而不是用“文本行数终于对了”代替数据正确。
