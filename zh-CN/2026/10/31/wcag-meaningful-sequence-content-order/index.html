WCAG有意义顺序：两栏说明为何线性读出串线？

用两套办理说明解释非交互文字的线性关系、独立块的合理换序与响应式和连续阅读验收。

正文

核心要点

  • 有意义的内容顺序应可由程序确定。
  • 独立块可以换序，依赖步骤不应交错。
  • Tab路线不能替代普通文字的阅读验证。

左栏讲初次申请，右栏讲续期，视觉上各有三个步骤。源代码若先放两个第一步，再放两个第二步，线性阅读就可能把两项流程混在一起。应先保护每份说明的内容关系，再决定怎样分栏；Tab能走完按钮，并不能证明普通文字的阅读顺序正确。

哪些先后关系会改变含义？

WCAG 2.2 SC1.3.2要求，在呈现顺序影响含义时，正确阅读序列可以由程序确定。这是A级要求，关注的不只是可聚焦控件。步骤、条件和解释即使没有一个按钮，仍可能需要稳定的阅读关系。

有意义顺序的理解文档说明，可存在多种正确顺序；独立文章的先后可以不影响意思，但各篇内容不应交错。它不要求所有页面只有一种从左上到右下的唯一排列。验收需要解释哪些关系必须保留，而不是把所有视觉坐标写成规范。

初次申请的“先取得资格编号，再填写申请”，与续期的“先核对旧记录，再补新材料”，各自包含依赖。若读成“取得编号、核对旧记录、填写申请、补新材料”，读者可能以为四件事属于一套流程。问题不是声音读得慢，也不是两栏间距太小，而是系统提供的线性序列没有保持两件事的边界。

把两份说明组织成完整内容块

下面是未执行的静态示例，办理规则是假设，没有接入真实服务。保存为HTML文件后可作为待验证样本；标记完整包含文档语言、标题、两份说明和布局规则。

<!doctype html>
<html lang="zh-CN">
<meta charset="utf-8">
<meta name="viewport" content="width=device-width,initial-scale=1">
<title>申请与续期说明</title>
<style>
  main { display: grid; grid-template-columns: repeat(2, minmax(0, 1fr)); gap: 2rem; }
  @media (max-width: 40rem) { main { grid-template-columns: 1fr; } }
</style>
<h1>先选择要办理的事项</h1>
<main>
  <section aria-labelledby="first">
    <h2 id="first">初次申请</h2>
    <p>适用于没有资格编号的申请人。</p>
    <ol><li>取得资格编号。</li>
      <li>填写申请。</li>
      <li>核对后提交。</li></ol>
  </section>
  <section aria-labelledby="renew">
    <h2 id="renew">续期</h2>
    <p>适用于已有有效记录的申请人。</p>
    <ol><li>核对旧记录。</li>
      <li>补充新材料。</li>
      <li>确认续期。</li></ol>
  </section>
</main>
</html>

这里先完整放置初次申请，再放续期，Grid仅决定两块如何显示。若设计希望续期在左、初次申请在右，应重新核对源结构与视觉方案是否共同表达任务，不要在内容被打散后只靠绝对定位拼回两列。两套说明的外部先后可以讨论，各自内部的条件和步骤仍应完整。

反例是把源结构写成两个标题、两个条件、两个第一步，再借网格坐标分到两边。视觉上可能像原图，连续阅读却交错。只比较桌面截图会漏掉这个差异；把每个段落加tabindex也没有重写普通阅读序列，反而给键盘导航增加无意义停靠。

如果内容是行列关系明确的比较数据，表格可能更合适；若是有先后依赖的两套步骤，各用有序列表能表达不同关系。不能因为表格可以横向排版，就把整篇办理说明放进无语义的布局表格。元素选择应由内容关系决定，视觉空间再由样式安排。

如何区分阅读顺序和焦点顺序？

连续阅读可能经过标题、条件、说明和链接；Tab通常只经过可聚焦对象。两条观察路线都需要，但不能互相代替。假设每份说明最后有一个办理链接，Tab先走申请再走续期，只证明这两个入口有某条聚焦路线；它没有检查链接前的六个步骤被怎样读出。

已有的焦点顺序与任务归属讨论控件之间的操作关系。本篇的检查对象包含从不获得Tab焦点的文字。测试报告应分别写“连续读出初次申请的条件与三步”以及“激活初次申请入口”，避免用一个“顺序正常”覆盖不同证据。

样式变化也是必要输入。宽屏两栏变成窄屏单栏时，原本靠空间分离的两组文字可能暴露交错。关闭布局样式可以帮助发现源顺序问题，但不能单靠这一技巧宣布所有辅助技术通过；生成内容、组件语义和实际读取方式还应在目标组合中检查。

异步插入说明同样可能改变关系。例如在两份说明之间增加“此前申请失败的人先联系支持”，如果它只适用于续期，就应明确归属并放入对应内容关系。不能让它视觉上靠近右栏，却在源结构中成为无法判断对象的独立提示。更新内容后需要重新走完整阅读，而不只检查新增句子是否出现。

侧栏在主文之前，一定不合格吗？

不一定。独立导航、旁注或另一篇文章可能有多个合理位置，理解文档明确承认这种情况。审查重点是换序会不会影响理解，以及至少是否存在可确定的正确序列。不能因为模板先输出侧栏，就自动判失败；也不能因为侧栏“独立”就允许它插进一句未完成的说明中间。

设想旁注解释“编号在哪里”，读者可以在办理说明前读，也可以在后读；只要主文清楚引用，未必只有一种顺序。另一条提示“没有编号请先停止填写”则会改变后续操作，它与相关步骤的关系需要更明确。这是具体内容判断，不是只按DOM节点类型就能完成的检查。

拟议验收先让两位评审分别按源顺序复述两项任务，确认谁适用、先做什么、最后做什么。再在宽屏、窄屏和目标浏览器/读屏组合中连续阅读，记录实际输出与是否发生串线。不同观察的结果应分别留存，本文没有执行这些步骤，也没有真实兼容性结论。

内容管理系统里的拖动排序也要按最终输出检查。编辑器可能只保存视觉位置，服务器模板却仍按旧字段顺序输出；也可能移动整个section，保持内部步骤完整。两种实现需要不同证据。发布前可以让编辑在不看两栏位置时读一遍导出的正文，确认每个条件属于哪项办理；真正的辅助技术验收仍另行进行。若允许多种排列，把允许移动的单位写成完整内容块，避免后续只拖走标题而留下步骤。

如果两个序列都能保留意义，就把允许变化的块和不可拆开的依赖写进内容规则。这样后续设计可以调整两栏位置，编辑也能知道新增条件应该归哪里。交付的是可说明的内容关系，不能只交付一张恰好没有暴露错误的桌面截图。
