RUN断网，远程ADD为什么仍可能下载？

用完整Dockerfile区分RUN命令断网与构建输入获取，解释缓存如何掩盖依赖，并为局部或完整离线目标选择验收范围。

正文

核心要点

  • RUN网络设置不能代表构建器全部获取路径。
  • 温缓存没有下载，不证明定义没有远程输入。
  • 离线验收必须声明预置材料与实际控制范围。

RUN 使用 network none，只约束该条命令的网络环境，不能证明整次镜像构建没有外部获取。基础镜像解析、远程 ADD 和其他构建输入，可能发生在这条 RUN 之外。看到构建仍访问网络时，先定位请求属于哪个阶段，再判断断网设置有没有作用。

命令运行与输入获取不是同一个阶段

Dockerfile reference 的 RUN 网络与 ADD 章节分别定义命令执行时的网络模式和远程来源的获取。RUN 的 none 模式不给该命令网络访问，但保留隔离的回环接口；ADD 可以使用远程网址。本文于二〇二六年十月三十一日核对在线参考，针对支持相应语法的 BuildKit 构建，不把它解释成宿主机所有网络行为的统一开关。

一个 Dockerfile 不是只有 shell 命令。构建器先要理解定义，取得相关基础镜像和上下文，遇到远程来源时还要获取材料，随后才有命令能消费那些文件。网络请求由哪个主体发出，决定了应检查哪里。把所有请求都归到 RUN，会让本来正确的局部设置看起来失效，也可能让未受约束的获取被忽略。

这里没有否定命令断网的作用。依赖已准备好时，它能让某个安装步骤不依赖临时访问外网；但需要的材料如果在前一步下载，那次下载仍是构建输入的一部分。评审要说清目标是“安装步骤不联网”，还是“整个构建器不产生外联”，两种目标需要不同范围的证据。

一份能看清边界的完整定义

以下示例未经执行。可在一个可丢弃目录中创建仅含下列内容的 Dockerfile；机器需有支持 BuildKit 的 Docker，且构建器能够取得所选镜像和公开文档。示例不是生产供应链方案：镜像使用标签，远程内容没有固定摘要，不能据此声称可复现或可信输入已经得到认证。

# syntax=docker/dockerfile:1
FROM busybox:1.37
ADD https://www.rfc-editor.org/rfc/rfc9110.txt /material/rfc9110.txt
RUN --network=none test -s /material/rfc9110.txt

在该目录中的拟议构建命令是：

docker buildx build --no-cache --progress=plain --load -t network-scope-demo .

ADD 请求公开文本，RUN 只检查材料非空。即使最后一条命令没有网络，构建器仍需要先取得 ADD 的来源，基础镜像也可能需要解析或下载。非空检查只验证文件有内容，不验证发布方身份、固定版本或业务正确性；它被刻意选得很小，是为了让读者分清“材料已在文件系统里”和“该命令可以联网”。

这个示例也没有测量网络封锁。如果在某台机器上成功，能证明哪些获取实际发生，仍要结合构建日志、已有缓存与获准的网络观察。若失败在基础镜像获取，不能用这个失败推断后面的 RUN 已经得到执行。若材料缺失，应该保留对应步骤的错误，而不是把所有失败统一叫断网成功。

缓存为什么会掩盖输入来源？

缓存命中时没有新下载，不代表定义里没有远程依赖。今天构建器已经有基础镜像和获取结果，明天换一台干净机器就可能需要网络。一次温缓存构建成功，可以支持该环境下这次运行的结论，却不能自动支持离线迁移或灾难恢复。

no-cache 主要用于避免复用构建步骤结果，不能把所有镜像材料、前端与构建器状态都假定为空。要验证完整离线能力，应先列出允许预置的材料，并记录实际构建器范围。将“带预置镜像的受控环境”和“从零获取所有输入”分开，才能解释两者为什么会有不同结果。

构建上下文的允许范围讨论哪些本地材料能进入构建；本题进一步要求记录远程获取。即使上下文只有一份干净 Dockerfile，它仍可能声明远程输入。两项审查相互补足，不能用目录里没有依赖文件来证明没有外部依赖。

该选择哪一种离线边界？

若需求是防止安装脚本临时下载未声明依赖，可先由受控流程准备依赖包，把必要材料交给构建阶段，再限制对应 RUN。验收关注安装所需材料是否完整、缺失时是否明确失败，以及脚本是否还有替代下载路径。准备流程本身的来源校验仍需要保留。

若需求是整条构建不访问外部网络，需要把基础镜像、语法前端、远程上下文、ADD 和其他输入都纳入清单，并在真正覆盖构建器的网络策略下验证。具体控制位置取决于本地或远程构建器的部署，不能只在命令运行环境里设置一个参数，就宣称远端服务也被隔离。

拟议验收先保留一个允许获取的基线，确认材料与构建定义本身有效；再在相同输入条件下检查受限制路径，记录请求主体、目的地址与失败阶段。只看到构建失败没有足够信息：网址本来失效、证书问题或镜像不存在，都可能产生同样表象。本文没有运行上述构建或抓取网络流量，不报告隔离成功。

对照实验要固定哪些身份？

可以设计两份观察记录：同一份Dockerfile、同一个远程来源与同一目标内容身份，一份在已准备材料的构建器运行，另一份在单独控制的构建器检查缺失输入。记录不能只写“第一次慢、第二次快”，还应列出哪些步骤实际执行、哪些结果被复用，以及每次获取的主体。时间差本身不能区分缓存、网络和远端负载。

若远程内容可变，两次拿到的文件可能已经不同，离线对照就混入了输入变化。真正要求固定材料时，需要以所选工具支持的摘要或受控归档确认内容，再比较网络策略。本文的公开文本示例没有建立这种固定性，所以它只用于解释阶段，不用于证明两次构建产物相同。

网络观察的位置同样影响结论。本地客户端没有外联，不代表远端构建服务没有请求；只看某个RUN的日志，也可能漏掉构建器取得材料的动作。验收记录应写出观察覆盖哪个进程或服务，无法观察的范围保持未知。这样即使构建成功，也能准确说明成功依赖了哪些预置条件。

命中缓存时没有请求，能证明断网吗？

不能单凭请求缺席作这个结论。先说明哪些输入已预置、哪些阶段实际执行，再设计会触发必要获取的受控检查。若要求的是安装步骤不联网，就验收该步骤；若要求构建器全程不外联，就把构建器自身的获取也纳入观察。让结论与控制范围一致，才能避免把局部断网配置变成一份过大的交付保证。
