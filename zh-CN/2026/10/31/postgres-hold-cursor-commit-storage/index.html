WITH HOLD 结束了长事务，却没有取消导出的资源账单

用 SQL 取数序列区分事务、会话与 held cursor 结果保留，对照连接池、keyset 分页和独立导出产物的恢复责任。

正文

核心要点

  • WITH HOLD 跨成功提交继续使用，但仍限原数据库会话。
  • 小批 FETCH 不表示剩余结果没有服务端存储成本。
  • 需要跨进程恢复时，应评估独立导出身份与产物。

WITH HOLD 让 PostgreSQL 游标在创建事务成功提交后继续取数，但没有取消导出的资源责任。游标仍属于原会话，当前实现还会把结果保存到临时文件或内存区域。它可以避免让消费全过程一直停留在原事务里，却不能同时承诺跨任意连接续读、无限结果和没有服务端存储成本。

提交之后留下的是什么？

PostgreSQL 18 的 DECLARE 参考区分普通游标与 held cursor：默认 WITHOUT HOLD 只在创建它的事务内可用；WITH HOLD 在成功提交后可以由同一会话的后续事务访问。本文于二〇二六年十月三十一日核对该文档，范围是 SQL 命令级游标，不将 PL/pgSQL 内部游标或任意驱动的同名对象混为一谈。

先分开三个寿命：事务的寿命、连接所代表会话的寿命，以及结果被保留的寿命。事务结束并不推出会话结束，游标跨提交可用也不推出它变成持久对象。按文档，held cursor 在显式 CLOSE 或会话结束时关闭；创建它的事务若回滚，游标会被移除。

假设后台生成一份报表，浏览器每次只下载几百行。普通游标可以在事务中逐批读取，但慢客户端会延长这段事务的存在时间。WITH HOLD 改变了事务边界，剩余结果却仍要由数据库保留。不能从“每次 FETCH 很小”倒推出服务端只保存了这一小批；客户端批次与服务端保留量是不同问题。

文档说明，当前实现会把 held cursor 代表的行复制到临时文件或内存，以供后续事务读取。这是机制依据，不是某个数据规模下的内存或磁盘数字。本篇没有测量物化时间、临时文件大小，也不提供调大某个参数就能无限导出的建议。

一个会话内怎样验证提交边界？

下面是未执行的完整 SQL 教学序列，可以在隔离数据库的同一条 psql 会话中运行。它使用生成数据，不依赖已有业务表，数字只用于看清取数位置：

BEGIN;
DECLARE demo_report NO SCROLL CURSOR WITH HOLD FOR
  SELECT n, 'item-' || n::text AS label
  FROM generate_series(1, 5) AS t(n)
  ORDER BY n;
FETCH FORWARD 2 FROM demo_report;
COMMIT;
FETCH FORWARD 2 FROM demo_report;
FETCH FORWARD 2 FROM demo_report;
CLOSE demo_report;

预期第一批为一与二，提交之后下一批接续三与四，最后一批只剩五。这里的顺序由明确的 ORDER BY 保证；结果来自文档与查询推演，没有实际输出。应核对每批内容、提交是否成功、最后一批行数与关闭后的行为，不能只看第一批拿到了两条。

要做对照，换一个名字声明 WITHOUT HOLD，并在提交后再 FETCH，观察它不能越过原事务边界。回滚对照则在 WITH HOLD 声明后执行 ROLLBACK，再尝试读取。每个预期错误都应单独结束当前测试阶段，不把失败后的事务状态继续带入下一组。最后确认同一会话中没有实验留下的游标。

另一个有价值的对照是关闭原连接，再用新连接尝试同名 FETCH。新会话不能因为游标名字相同就继续旧结果；若驱动复用了后端，单看应用连接对象的新旧还不够，需要确认实际会话身份。这里没有运行连接池，不能宣称任何具体池模式已经兼容。

连接池为什么改变导出方案？

持有游标的导出需要在其有效期内回到同一数据库会话。普通请求池可能让相邻调用落到不同连接；事务池还会在事务结束后重新分配后端。应用把游标名存进下载令牌，并不能让任意后端找到那份会话结果。选择 WITH HOLD 前，要查池的实际模式与驱动对会话固定的支持。

如果为了导出专占一条连接，就需要决定最大同时导出数、闲置取消、关闭失败与用户离开后的处理。这里不规定通用阈值，应根据连接预算与数据规模验证。仅给 HTTP 请求设超时，若资源持有者没有接收退出指令，游标可能仍由后端会话保留；反过来直接断开会话虽然结束游标，也让后续接续失去依据。

小而有界、在单会话内完成的查询，可以接受这种资源安排。需要长时间暂停、跨进程恢复或允许用户隔天下载的任务，更适合评估独立导出产物与可查询任务身份。那会增加产物存储与清理工作，但把保留策略从一个隐含的数据库会话，变成可登记和可恢复的对象。

与接口里的游标分页是同一回事吗？

不是同一份状态。接口里的 keyset 游标通常记录排序边界，每次发起新的查询；SQL DECLARE 则创建属于会话的游标对象。本站分页顺序与跨页一致性讨论排序值、数据变化和快照承诺，不应把其中一个可编码的边界值直接当成数据库会话句柄。

keyset 方案不必长期保存 SQL 游标，但排序字段发生变化时仍可能影响跨页结果；held cursor 保留查询结果，也要承担存储和会话责任。比较时应先问需要浏览最新数据还是导出固定集合，再列出中断恢复、快照要求与资源保留。两种方案都不因为名字里有游标就自动满足另一种合同。

WITH HOLD 可以边读边锁住待修改记录吗？

不能将它与查询中的 FOR UPDATE 或 FOR SHARE 同用。需要编辑的界面应另行安排授权、版本比较和事务，而不是把一份可能长时间保留的报表游标当作编辑锁。这条限制也帮助划清报表结果与当前业务状态：用户看到的旧结果，不应无条件批准对现在记录的写入。

结果的新鲜程度也应进入交付说明。假设导出开始后，另一条连接把商品名称改了；保留的结果不能被当作用户稍后打开页面时的最新业务状态。报表可以注明它对应的查询范围与生成任务，而编辑操作应重新读取当前版本。这样保留旧结果是有意选择，不会被误报成数据库没有更新。

验证资源清理时，不只测试显式 CLOSE 的成功分支。可以让客户端下载半份后离开，检查拥有者是否收到取消、是否尝试关闭、是否登记失败，以及专用连接何时归还。没有可观察关闭证据时，状态应保留为待收尾。给任务写一个完成时间，只改变应用记录，不会凭空释放数据库会话里的结果。

拟议验收包括成功提交后续读、创建事务回滚、显式关闭、断开会话、连接池切换以及较大结果的资源观察。资源数字需在目标环境测量，本文未执行这些测试。方案评审至少应能说清：谁持有会话，结果保留在哪里，什么条件下关闭，以及断线后是重建导出还是允许恢复。只有“已经避免长事务”，还没有回答剩下三项责任。
