CSV 在本机，COPY FROM 为什么找不到文件？

先区分服务器文件 COPY 与客户端文件读取，再用完整 CSV、建表和 psql 命令核对数据路径、权限、字段与提交。

正文

核心要点

  • COPY 文件名按数据库服务器的文件环境解释。
  • psql 反斜杠 copy 是客户端元命令，驱动应使用自己的 COPY 接口。
  • 读取成功、复制行数和业务提交需要分别核对。

CSV 在自己的电脑上，不代表远程 PostgreSQL 的 COPY FROM '路径' 能读取它。带文件名的 COPY 由数据库服务器打开文件，路径与操作系统权限都按服务器所在环境解释。本机文件要经过客户端传入，可以选择 psql 的 \copy，或由应用驱动使用 COPY STDIN 协议；先确定文件由谁打开，再检查权限。

同一个绝对路径，属于哪台机器？

PostgreSQL 18 的 COPY 参考区分文件名与 STDIN：前者让服务器直接读写文件，后者让数据经过客户端与数据库的连接。本文于二〇二六年十月三十一日核对十八版文档，没有执行导入，也没有检查任何真实主机上的文件权限。

假设运维人员在笔记本保存了 /tmp/customers.csv，使用 psql 连接云数据库，再执行 COPY 指向这个路径。SQL 语句穿过网络，文件内容并没有随路径一起穿过去。服务器会找自己能看到的文件；即使两台机器恰好都有同名路径，也不说明内容相同。给数据库角色增加权限，不能让另一台机器自动获得本机文件。

容器也增加一层路径解释。宿主机的目录存在，不意味着数据库容器挂载了它；容器内同名目录又可能是另一份内容。诊断应写出客户端进程、数据库进程、文件所在位置与挂载关系，再决定哪一端应该拥有读取能力。不要为了消除报错，把所有目录改成任意用户可读。

服务器文件 COPY 仍有合理用途，例如受控的批处理节点已经把数据放到数据库可访问的位置。它需要符合部署环境的权限与数据管理规则。选择客户端入口也不意味着不需要权限：操作者仍须有目标表所需的数据库权限，并对输入内容、允许列与业务范围负责。

在本机读取 CSV，用什么最小流程？

下面是未执行的教学示例，要求本机安装 psql，并事先通过受控方式设置好测试数据库连接。不要在示例里写密码或令牌。先在本机新建目录，将以下文本保存成 UTF-8 的 customers.csv：

external_id,display_name
101,"Lin, Mei"
102,"He said ""hello"""

启动 psql 并连接独立测试库，在该会话中建表。类型与列数只为说明数据路径，不代表真实客户模型：

CREATE TABLE demo_customer_import (
  external_id integer PRIMARY KEY,
  display_name text NOT NULL
);

在 psql 里执行下面这一行元命令，把绝对路径改成刚刚创建的本机文件。整个命令保持一行，避免把 psql 的元命令语法误当成普通 SQL 的多行规则：

\copy demo_customer_import(external_id, display_name) FROM '/absolute/path/customers.csv' WITH (FORMAT csv, HEADER true, ENCODING 'UTF8')

随后核对实际列值，而不是只看复制了几行：

SELECT external_id, display_name
FROM demo_customer_import
ORDER BY external_id;

按文件与 CSV 引号语法推演，第一条姓名应保留逗号，第二条应保留引号。这里没有运行结果，读者执行后应记录 psql 版本、连接的数据库、文件摘要和查询输出。若期望两条而只核对总行数，列错位或内容误解仍可能漏过；需要逐项比较标识与字段。

psql 的 \copy 说明将文件访问放在客户端。这不是把文件复制到数据库服务器的某个永久目录，而是通过连接传输数据。服务端仍执行表写入与约束检查，客户端可读不等于每条记录都能被接受。

通过应用驱动调用时，能发送反斜杠命令吗？

不能把 psql 的 \copy 当作服务器 SQL 发出去。反斜杠命令由 psql 自己解析；HTTP 后端或其他数据库驱动应使用该驱动支持的 COPY 输入接口，把字节流写进 COPY FROM STDIN 操作，或在数据量合适时采用参数化 INSERT。具体方法名、取消方式与事务集成必须查所用驱动版本，这里不虚构一段通用 API。

这项选择也涉及连接的占用时间。持续上传的 COPY 会使用连接，失败或取消后应依照驱动合同结束该操作与事务，再归还连接。不能只因为浏览器已经关闭上传页面，就认为数据库端已经退出。若输入需要先核验或允许部分接受，可以考虑暂存与显式校验，但这属于导入合同，不是路径修复自动附带的能力。

哪些失败应该分开处理？

本机文件不存在，应查客户端路径、当前目录和文件保留时段；服务器报文件不存在，应先确认是否误用了服务器文件 COPY。权限失败要区分本机操作系统读取、服务器操作系统读取和数据库表权限。格式失败则核对编码、分隔符、引号、列顺序与类型。把这些都显示成“请提升权限”，会把无关配置一起改掉。

HEADER true 也不应成为列映射的想当然保证。这里用显式列清单固定导入顺序；表后来增加字段时，应重新审查 CSV 与列清单，不能只因第一行看起来像列名就宣布映射安全。若其他字段依赖默认值，还要核对被省略字段的真实默认与约束，而非复制另一张表的假设。

失败之后是否可以保留已经导入的部分，须由事务边界与产品规则共同决定。本站保存点与部分导入说明讨论接受与拒绝结果如何解释；不能因为修好了路径，就把原来要求整体成功的导入偷偷改成部分成功。

COPY 返回成功，就是业务导入已经完成吗？

还要确认事务提交、预期记录集合以及后续读取。若 COPY 处于显式事务内，随后回滚就不能把那次复制当成持久成功；如果后端还要执行关联检查，也需要等检查结果。行数只能回答数量，不证明姓名、外部标识和归属关系完全正确。

导入前还可以建立一份只描述文件的清单：文件摘要、编码、列顺序、预期记录标识与创建来源。摘要相同帮助核对两端讨论的是同一份字节，不能证明内容可信；来源授权与业务校验仍须独立完成。若操作者临时重新保存了 CSV，应生成新的清单，而不是继续沿用旧文件的行数预期。

对于需要整体成功的演练，可以在明确的测试事务中完成复制与核对，再选择提交或回滚，并从另一条只读连接验证可见结果。错误出现后应先处理当前事务状态，再进行下一组实验。测试库里观察到两条记录，只能覆盖该文件与该执行路径；不能外推为大文件传输、驱动断线恢复或生产数据映射已经通过。

拟议验证包括本机可读而服务器不存在、客户端无读取权限、重复主键、字段引号与换行、编码不匹配和中途取消，分别核对最终表与连接状态。本篇未执行这些测试。修复记录应能明确说出：哪一个进程读取了哪一份文件，哪些列经过哪次提交进入了目标表，而不只是命令终于不报错。
