Import map：同一个import为何加载不同模块？

从完整静态文件树解释scopes按引用者URL映射、嵌套回退和产物搬家后的版本边界。

正文

核心要点

  • scope匹配引用模块URL，不是页面路由。
  • 更具体范围与全局映射共同决定解析。
  • 版本映射不能代替状态或安全隔离设计。

旧编辑器与新工作台都写import工具包，却需要两份实现。原生import map的scopes可以按引用模块URL提供局部映射；判断时应看谁发起import，而不是地址栏当前路由，也不是依赖文件最后存在哪个目录。

先画出引用者，再谈版本隔离

HTML的import maps章节定义全局imports与局部scopes，并解释局部映射按引用者的URL前缀应用。当前页面标注二〇二六年十月三十日更新。本文限定浏览器原生模块解析，没有验证任意打包器会如何处理同名配置，也没有实测目标浏览器支持。

这套机制能让模块图的不同部分解析到不同依赖，但它不是根据当前函数调用栈动态继承一个版本环境。一个共享模块内部发起的import，应看该共享模块自己的URL；不能因为它最早被旧编辑器加载，就认定它后续所有依赖都沿用旧编辑器的scope。

如果架构讨论只画“页面甲用版本一，页面乙用版本二”，就可能漏掉共同引用的工具模块。更可靠的表格至少列出引用模块URL、specifier、命中的局部映射、最终依赖URL。每行是一条引用关系，迁移评审才能看见哪里真正发生切换。

一个可独立准备的静态目录

以下是未执行的完整教学样本，不依赖框架路由或远程包。新建空目录，按文件名保存这些内容，使用可用的Python3运行python3 -m http.server 8000，再打开本地HTTP页面。命令与浏览器步骤均未在本文执行，端口占用时需要自行选择空闲端口。

index.html放在目录根部：

<!doctype html>
<html lang="zh-CN">
<meta charset="utf-8">
<title>局部模块映射示例</title>
<h1>检查两个入口的依赖版本</h1>
<p>在开发者工具控制台查看教学标签。</p>
<script type="importmap">
{
  "imports": {
    "formatter": "/deps/formatter-v2.mjs",
    "label": "/deps/label.mjs"
  },
  "scopes": {
    "/legacy/": { "formatter": "/deps/formatter-v1.mjs" }
  }
}
</script>
<script type="module" src="/legacy/entry.mjs"></script>
<script type="module" src="/work/entry.mjs"></script>
</html>

创建legacy/entry.mjs：

import { version } from 'formatter';
import { label } from 'label';
console.log('legacy', version, label);

创建work/entry.mjs：

import { version } from 'formatter';
import { label } from 'label';
console.log('work', version, label);

再创建deps/formatter-v1.mjs、deps/formatter-v2.mjs与deps/label.mjs，内容分别为：

// deps/formatter-v1.mjs
export const version = 'v1-demo';

// deps/formatter-v2.mjs
export const version = 'v2-demo';

// deps/label.mjs
export const label = 'shared-demo';

按映射规则推导，legacy入口中的formatter解析到版本一，work入口使用全局版本二；两个入口的label都使用全局映射。局部scope没有列出label，不表示这个标识符立即失败，它仍可以从更宽的适用映射寻找。此处标签是教学输出预期，不是已经取得的控制台日志。

样本使用从站点根开始的URL，所以服务应以这个新目录为根。把这些文件放到某个现有站点的子路径，再照抄根路径，不会自动得到相同文件位置。需要部署在子路径时，先统一映射地址与服务根，不能把解析失败统统归因于scopes不工作。

嵌套scope怎样选，遗漏项怎样找？

标准解释更具体的适用scope先被考虑，再到较宽scope与全局imports。可以把/legacy/editor/作为比/legacy/更具体的范围，只覆盖某个标识符；其他标识符仍可能沿较宽映射找到。评审不要把一层scope误读成必须重复列出所有依赖的封闭对象。

为了检查这一点，可以在教学目录增加更深入口，并先写出预期解析表：formatter是否被更具体范围覆盖，label是否仍回退全局，未提供任何映射的裸名称如何失败。不要同时修改十个路径再只看页面最终是否出现，逐条引用关系更容易定位错误。

这里的“更具体”也不等于对目录名做业务判断。scope键本身按标准归一化和匹配，字符串前缀的写法应有意识选择。目录范围宜保留相应斜杠，不要把看似相近但边界不同的路径都想当然纳入。生产发布更应保存解析表，而不是只看配置文件里存在legacy几个字母。

页面路由没变，产物搬家为何仍要检查？

假设客户端仍显示/legacy/edit，构建却把旧入口移到/assets/editor-abc.mjs。原来的/legacy/范围未必再覆盖这个引用者，formatter就可能落到全局版本。地址栏保留旧页面名，并不能证明模块图仍处于旧映射范围。

应以实际请求和模块URL为证据。打包器可能提前改写import，也可能把依赖内联进一个产物，使浏览器不再解析原来的裸名称；这种情况下，原生import map不一定处在讨论中的控制点。先确认最终产物保留了什么，再选择构建期别名、独立产物或原生映射方案。

相对URL还受其适用基址影响，相关基础可对照URL与基址解析。本篇新增的是specifier映射与引用者范围，不应把所有地址组合规则重复成另一篇URL入门。检查表里同时写实际绝对引用者和最终目标，可以减少基址与scope混淆。

分开模块版本，共享状态也自动隔离吗？

scopes提供解析规则，不是安全沙箱，也不负责定义应用的共享状态。不同最终模块URL可能形成不同模块实例，随之影响单例、类身份或缓存关系；这些是需要在具体模块设计中检查的后果，不能由“版本分开了”一句话替代接口兼容性验证。

如果两个入口都依赖根目录下同一个共享模块，这个共享模块对formatter的引用按它自己的URL解析，可能继续使用全局版本。想让旧功能全程使用版本一，需要审视完整依赖边，而不是只给入口所在目录加配置。反过来，无意复制所有公共依赖也可能破坏原本想共享的状态。

发布顺序也需要明确。新映射先上线而对应版本文件尚不存在，会把解析正确的URL变成加载失败；只回退HTML而删掉旧资源，也可能影响仍持有旧页面的访问者。迁移计划应把映射文件、两套依赖的可用期与回退目标放在一起，不把版本字符串修改当成完成发布。这里是基于静态依赖关系的发布建议，没有缓存命中率或线上可用性证明。原生解析表可以说明资源应该去哪里，真实部署还必须确认那个地址确实提供预期内容。

拟议验收先在上述隔离目录核对两个版本标签与Network中的实际URL，再改变一个入口目录、增加嵌套范围，并故意使用未映射裸名称，保存每次预期与实际差异。最后才在真实构建产物中复验同一关系。本文没有运行这些步骤，不报告迁移成功。交付时给下一位维护者一张能解释每条import走向的表，比只说“旧页面已经隔离”更可核对。
