清单没写CPU请求，Pod为什么自己多出requests？

比较提交清单与准入后Pod，使用完整命名空间示例解释默认注入、请求限制冲突与政策更新不回写存量的边界。

正文

核心要点

  • 模板缺字段，不证明最终Pod没有资源请求。
  • 默认限制与显式请求组合后仍须有效。
  • 政策更新不回写旧Pod，新对象需重新核对。

提交清单没有写 requests，准入后的 Pod 却可能有 CPU 请求，因为命名空间的 LimitRange 可以注入默认请求和限制。排障时先比较原始清单、命名空间策略和实际 Pod 对象，不要只从仓库文件推断调度输入，也不要看到资源问题就先提高配额。

字段来源要沿准入过程核对

Kubernetes 的 Limit Ranges 文档说明，LimitRange 准入可以补默认资源值，并检查对象的最小值、最大值及比例等约束。本文于二〇二六年十月三十一日核对当前页面；网站导航展示一点三十七，不等于该网址固定到这一发布版。实际集群应继续核对自己的版本和启用的准入设置。

这里有三份相关材料：开发者提交的模板、控制面处理后的对象、调度过程使用的资源声明。它们有关联，却不能假定逐字相同。控制器产生 Pod 时仍会经过准入；因此模板里没写某个字段，不足以说明最终对象也没有这个值。审查部署输入，应把默认来源作为可追踪配置一起保存。

这与命名空间总量限制不同。ResourceQuota 的请求账目回答累计还能申请多少；本题先问某个 Pod 的请求值从何而来。默认注入可能影响后续账目，但把两种政策都叫“配额”会丢掉真正需要修复的配置位置。

用一个完整的纸面配置看默认值

以下是未经执行的教学材料。它包含独立命名空间、一个容器级 LimitRange 和一个没有显式 resources 的 Pod；假定相应准入功能已启用，且没有其他策略改变这些值。示例镜像只用于展示对象结构，没有运行或验证镜像可拉取性。

apiVersion: v1
kind: Namespace
metadata:
  name: limitrange-demo
---
apiVersion: v1
kind: LimitRange
metadata:
  name: cpu-defaults
  namespace: limitrange-demo
spec:
  limits:
    - type: Container
      defaultRequest:
        cpu: 100m
      default:
        cpu: 500m
---
apiVersion: v1
kind: Pod
metadata:
  name: defaulted
  namespace: limitrange-demo
spec:
  containers:
    - name: demo
      image: registry.k8s.io/pause:3.10

在隔离集群中验证时，应先让命名空间与策略实际存在，再申请 Pod，并读取控制面保存的 Pod 资源字段。纸面预期是 CPU 请求得到默认值、限制得到默认值；不能将这段 YAML 当成已经创建成功的回执。若环境还有其他准入变更，应保存最终结果并调查来源，而不是强迫观察符合简例。

默认请求一百毫核不是推荐的容量配置。这组数只用于说明来源与请求、限制是不同字段，不能用于真实应用的容量评估。是否足够要靠工作负载证据；把默认值设置得很小可能让对象更容易放行，却不自动减少真实消耗。

显式请求与默认限制可能冲突

再考虑在同一例子里把 Pod 的 CPU 请求显式写为七百毫核，而不写限制。默认限制仍可能补入五百毫核，组合后的请求超过限制，形成无效的有效配置。此时应检查实际 API 响应、控制器事件和对象是否存在，先确定停在准入或校验阶段，不能预先断言一定会产生一个 Pending Pod。

官方页面用一组请求大于默认限制的配置说明这种不一致。这里据此解释字段组合，而没有运行 API 请求，也不承诺所有版本都返回相同错误文本或状态码。若对象根本没有被接受，等待调度不会修复问题；若已经存在而未被放置，又应继续读对应调度原因。

修复可以是为该工作负载明确声明合理的请求与限制，也可以是重新评审命名空间默认政策。选择取决于谁拥有默认、谁承诺应用资源，以及同一策略影响哪些消费者。不要只为当前 Pod 调低请求，再把放行当成容量正确；也不要随手调高共享默认而忽略其他应用。

模板没变，替换后的副本怎样对照？

可以设想先创建旧Pod，再调整默认请求，最后由同一份未改模板创建新Pod的对照。记录至少包括模板身份、命名空间策略内容、两个对象的创建时间与实际保存的资源字段。旧对象仍用旧值、新对象得到新值，是政策在创建阶段生效的预期方向；不是已经运行的进程自己修改了资源。

若观察与预期不同，先排除新Pod来自另一份模板、策略尚未存在或还有其他变更者。名字相近的两个Pod不一定属于同一次交付，截图里缺少创建时间也不能证明先后关系。对照应沿控制器归属与对象身份核对，而不是凭列表顺序判断哪个是旧副本。

这个记录还能指导选择迁移方式。若现有副本必须保持原有资源承诺，应先评估新默认对替换的影响；若要求统一到新值，应明确由谁安排工作负载更新并检查结果。单改默认政策既不能完成存量迁移，也不能保证之后每次重建都采用原来的资源。将默认政策当成有版本的发布输入，才更容易解释差异。

改了 LimitRange，旧 Pod 会一起变吗？

不会因为默认政策修改就自动回写已经存在的 Pod。文档明确限定检查发生在 Pod 准入阶段，存量 Pod 继续保留原配置。应按创建时间区分新旧对象，比较实际资源字段，而不是看到 LimitRange 已更新就宣称迁移完成。

控制器模板不变时，替换 Pod 仍可能遇到新的默认政策。因此一组副本在滚动替换过程中，可能同时包含按不同政策创建的对象。这个现象要通过对象与创建记录核对，不能仅看一份 Deployment 模板截图。需要资源一致性时，应把默认变更与工作负载更新作为有责任人的变更安排。

多个 LimitRange 也可能带来不确定默认。官方文档说明，同一命名空间有两个或更多这样的对象时，默认值选择不确定。不要依赖对象名字排序或最近修改来推断赢家；应整理政策来源，减少互相竞争的默认，并用新对象检查预期。

拟议验收覆盖无显式值、显式值、默认组合冲突，以及政策更新前后的新旧 Pod。每个用例记录提交内容、当时策略、实际响应、最终对象和后续事件。本文没有连接集群或执行这些用例，不报告成功创建、调度或服务就绪。先把新增字段的来源解释清楚，再处理它造成的预算和调度影响，排障才不会一直修改错误的一层。
