RBAC只允许一个对象，为什么get成功而list仍被拒？

把目标身份、命名空间、动词与名字条件放在同一授权检查中，区分按名读取、列表字段选择器和顶层创建，并追查额外绑定。

正文

核心要点

  • 按名读取与集合请求携带的授权信息不同。
  • 资源名不能表达顶层创建只允许某一名字的合同。
  • 额外绑定、客户端缓存和对象不存在需独立排查。

服务账号可以读取指定 ConfigMap，却不能列出同类对象，不一定是授权记录尚未生效。RBAC 的 resourceNames 要与请求的动词和形态一起解释：按名字 get、集合 list、顶层 create 不是同一种授权问题。需要一个对象时，先确认客户端实际发了什么请求，再决定是否增加权限。

名字限制不是查询结果的自动过滤器

Kubernetes RBAC 文档的资源名字说明允许对部分请求用 resourceNames 限定对象。受名字限制的 list 或 watch，请求必须带匹配的 metadata.name 字段选择器才能授权；它不是先允许读取整个集合，再由 RBAC 帮调用者筛掉不准看的对象。本文于二〇二六年十月三十日核对官方说明，没有连接集群或执行权限检查。

get 通常把目标名字放在资源路径上，list 则面向集合。调用者在界面上点击“查看一个配置”，不代表底层一定使用按名 get；客户端可能先列出全部配置再挑选。若规则只允许一个名字，这种实现方式就需要重新评估。业务意图相同，不等于请求提交给授权器的信息相同。

观察应保留账号、命名空间、资源、子资源、动词和名字条件。不要只用一个宽泛的“能读配置”描述权限。若工具先查询发现接口、再访问资源，前置调用失败与目标对象访问失败也要分开，不能因一个最终错误就直接授予全部读取能力。

一份只服务于特定配置的假设授权

设想 test 命名空间已有 ConfigMap my-config，服务账号 config-reader 只需读取它。以下完整 Role 与随后绑定命令均未应用；账号、对象与测试凭据须在隔离环境另行准备。

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: named-config-reader
  namespace: test
rules:
  - apiGroups: [""]
    resources: ["configmaps"]
    resourceNames: ["my-config"]
    verbs: ["get", "list", "watch"]

使用以下未执行命令绑定同一角色与主体：

kubectl create rolebinding named-config-reader --namespace=test \
  --role=named-config-reader --serviceaccount=test:config-reader

在只有这份相关授权的前提下，按名 get my-config 与按名访问另一个对象应得到不同结果。集合读取则要区分带匹配字段选择器和不带选择器；前者如 kubectl get configmaps -n test --field-selector=metadata.name=my-config 表达了名字条件。命令还需使用目标服务账号的真实身份，本篇没有提供凭据或执行回执。

不能在管理员上下文里跑完命令，再宣布 config-reader 权限通过。管理员可能从其他绑定获得更大权限，掩盖这份 Role 的范围。测试身份和请求形态要同时固定，否则对照改变了两个因素，结果无法归因。也要保存原始状态码与拒绝原因，避免把对象不存在和没有权限压成同一种“读不到”。

把 create 加进去，能限制只创建这个名字吗？

官方说明不能用资源名限制顶层 create 或 deletecollection；顶层创建时对象名字可能尚不能用于授权。它同时明确，create 的这一限制不应笼统推广到子资源，例如 pods/exec 可以使用 resourceNames。这里必须同时保留请求层级和资源范围，不能只记住一个动词字符串。

这不意味着在带名字的规则里写 create 就会自动允许任意名字创建。它意味着不能靠这种写法表达“只允许创建 my-config”的合同。若要控制可创建对象的内容或命名，需要评估适用的准入政策等机制，并查清当前版本与权限边界；本文没有提供已经成立的替代实现。不能为了让客户端继续，就把名字条件整个删掉而不说明暴露范围变化。

选择修复应先看任务。只需固定对象读取的客户端，可以采用直接 get；必须使用 list/watch 的客户端，需要确认能够传递匹配字段选择器，并核对其后续重连请求。若客户端实现只能全量列举，应改变客户端、调整资源隔离方案，或明确接受更宽的授权，而不是把本来的最小范围悄悄扩成默认全读。

为什么改完这条 Role，仍能访问其他对象？

RBAC 的权限可以来自多条角色与绑定，缩小一条 Role 不会撤销其他许可。应核对服务账号实际身份、所属主体以及相关 RoleBinding 和 ClusterRoleBinding。局部规则没有写允许，并不是一条全局拒绝。

例如 config-reader 还被另一个绑定授予命名空间全部 ConfigMap 的读取能力，按名规则仍然存在，也没有承担限制另一条授权的作用。故障记录应能够解释哪个绑定提供了额外许可，而不是只截图被修改的 Role。删除其他绑定前需要确认其用途和依赖；本文未执行任何权限变更。

拟议验证使用隔离账号，安排目标名字 get、其他名字 get、带字段选择器 list、无选择器 list，以及需要持续更新的 watch 重连。再分别加入、移除一条额外许可，观察范围是否符合预期。对顶层 create 单独测试，不把它的结果推导成其他名字全部允许。保存实际身份与完整请求条件，避免在测试报告中泄露 token。

对象授权与接口返回值还要分开：获准 get 不保证配置内容符合业务，也不保证后续写入获准。与订单对象权限一样，随机或固定名字都不能替代对应授权；本题多出的要求是让请求形态表达出规则实际检查的名字条件，再用目标身份验证。

watch 的首次请求通过以后，还需要检查断线后的重连。某个客户端第一次按名字查询，后来重新建立监听时省略了字段选择器，会在运行一段时间后才暴露拒绝。测试不要只保存首次订阅成功，应让同一客户端完成一次受控重连，记录它仍然提交相同范围；不能为了减少重连报错就全量授予 watch。

对照对象必须事先确实存在。若“另一个名字”根本不存在，读不到不能单独证明授权拒绝；应分别安排存在但不获准、获准且存在、获准但不存在三种输入，比较相应响应。对象名只用无敏感测试材料，结果也不应泄露无权读取的配置内容。这样才能把权限与对象状态分开验收。

排障过程中还要固定客户端缓存。页面显示旧配置，可能来自之前的读取结果，而不是当前请求仍获许可；观察网络实际请求与服务器拒绝比只刷新界面更有解释力。若权限刚变更，保存绑定版本和请求时点，等待实际系统观察到配置以后再形成结论，不用一份静态Role证明所有后续请求。
