NetworkPolicy 新增 deny-all，为什么前端的新连接仍被允许？

用同一账本Pod的前端许可与空入口策略计算允许并集，解释为何deny-all不覆盖旧allow，再分别检查源出口、插件执行和新连接。

正文

核心要点

  • 同方向适用策略的允许项取并集，空入口规则不覆盖其他许可。
  • 源出口和目标入口分别决定连接能否建立，策略存在不等于插件已执行。
  • 用普通Pod的新连接及健康正对照验证，既有连接另查实现语义。

给同一个 Pod 新增一条没有 ingress 规则的 NetworkPolicy，不会覆盖另一条策略已有的允许项。标准 NetworkPolicy 按流量方向合并所有适用策略的允许集合；要收紧访问，应检查并修改产生许可的规则，而不是把 deny-all 放在最后创建。本文只讨论新建连接，既有连接受策略修改后的影响由实现决定。

先确认策略确实有人执行

Kubernetes 的网络策略文档说明，集群需要支持 NetworkPolicy 的网络插件。只创建资源而没有执行它的实现，不会产生预期过滤。本篇于二〇二六年十月三十日重新核对官方原文，没有访问集群。本文没有运行验证或安全效果测量。

策略对象被 API 接受，只证明声明存在。插件是否支持、控制器是否工作、配置是否已经被观察，是另外的证据。测试前应记录 Kubernetes 和网络插件版本，以及采用的是标准 API 还是供应商额外策略；后者可能有自己的优先级或拒绝语义，不能拿来解释标准 NetworkPolicy 的并集规则。

策略选择器先决定目标 Pod，再由 policyTypes 指定入口、出口等方向。一个 Pod 的入口被隔离，不表示出口也同时隔离；源端与目的端分别有自己的控制面。这里的隔离是连接受到限制，不是承诺阻断所有网络路径。节点流量、主机网络等情况还有专门边界，因此下面固定使用普通 Pod 之间的新建 TCP 连接。

两条策略选中同一个账本服务

设想 test 命名空间已有一个 app=ledger 的普通 Pod，应用确实监听八〇八〇端口。同命名空间有 role=frontend 的调用方，以及标签不同的对照调用方；两者最初都未被出口策略隔离。以下两份完整策略清单仅用于推演，没有应用到集群，也没有准备对应工作负载。

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: ledger-from-frontend
  namespace: test
spec:
  podSelector:
    matchLabels:
      app: ledger
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector:
            matchLabels:
              role: frontend
      ports:
        - protocol: TCP
          port: 8080
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: ledger-empty-ingress
  namespace: test
spec:
  podSelector:
    matchLabels:
      app: ledger
  policyTypes: [Ingress]
  ingress: []

第一条允许同命名空间满足来源标签的 Pod 连接目标八〇八〇端口。第二条同样选择账本 Pod，但没有贡献任何允许项。两条策略一起生效时，入口允许集合是前端许可与空集合的并集，前端许可仍在。空列表不是一条拥有更高优先级的拒绝动作，后创建也不会把此前许可减掉。

对照调用方若没有被其他规则允许，就不能仅靠这两条策略取得同样许可。这个预期有明确前提：全部匹配策略只有这两条，来源出口未隔离，测试走的是普通 Pod 的新连接。若另有一条允许全部来源的策略，允许集合会扩大；若来源被单独限制出口，前端也可能连接失败。不要把孤立阅读两份 YAML 的推演当成真实集群的完整结论。

单独留下空入口策略，且不存在其他适用许可时，才表达本例入口的默认拒绝。反过来，如果把两条策略都删掉，又没有其他入口策略选择该 Pod，它可能回到未被入口隔离的状态。删除策略不是总会更加严格，应先计算删除之后留下的集合与隔离条件。

应该收紧旧许可，还是扩大默认拒绝范围？

若目标是不再允许前端访问，应修改或移除产生前端许可的那条规则，同时保留需要的隔离基线。若只是要缩小可访问端口，就收紧允许规则里的端口，而不是新增一个名字更严厉的策略。策略名称帮助人理解，但执行依据是选择器、方向和规则内容。

若目标是为整个命名空间建立默认入口隔离，可以在独立方案中使用空目标选择器，再为必要服务添加允许规则。但这会影响更多工作负载，必须列清依赖和恢复办法；它也仍然不能覆盖其他适用策略的允许项。不能把作用范围更大误认为优先级更高，或在不核对依赖时把单服务排障升级为全命名空间变更。

评审最好针对某一个目标和方向列出策略全集。逐项写出它选择谁、允许哪些来源和端口，再求并集；同时核对当前标签，而不是只看上周部署时的模板。标签变化可能使另一条宽泛规则突然匹配，连接变通并不一定意味着新策略失效。诊断应能指出究竟是哪一个允许项解释了结果。

入口已经允许，为什么新连接仍然失败？

官方文档明确，源 Pod 的出口与目标 Pod 的入口都必须允许该连接。假设前端后来被一条空出口策略选择，即使账本入口仍允许前端，源端也可能不允许发起该连接。应独立检查前端的出口策略集合，而不是继续放宽账本入口；否则只会扩大目标暴露面，未修复真正阻断位置。

网络许可也不会让应用自动监听端口。若连接建立失败，应把策略允许、路径可达与进程监听分别取证；通过 Service 访问时还要核对实际目标，相关区别见Service 入口与 targetPort。直接使用目标 Pod 地址的对照可以减少服务发现与转发因素，但不因此成为生产访问方案，也不能跳过身份与应用响应核验。

拟议验证在隔离环境中固定普通 Pod 身份、标签、协议和端口，分别观察仅有前端许可、再加入空入口策略、移除旧许可三个阶段。每阶段都从前端与对照 Pod 重新建立连接，保存全部匹配策略、来源出口状态和连接结果；再交换两条策略创建顺序，验证结果不依赖最后创建者。策略传播与实现就绪需要真实观察，不能把一次过早尝试当成稳定结论。

受控对照还应先确认测试工具确实发起新连接，并在已知允许条件下取得预期应用响应。若服务本身没有监听，所有来源都会失败，不能用这种结果证明空入口策略生效。策略收紧后再次放回同一条必要许可，可帮助检查故障是否仍来自应用或路径；全过程固定应用版本与目标地址，不把重建Pod带来的其他变化混入判断。

最后另设既有连接的用例，明确它与新连接验证分开。官方将策略变化是否作用于已有连接留给具体实现；保持一条旧连接还能通信，不能单独证明新连接也被允许。本文未执行上述任何检查。先找出真正贡献许可的规则，再验证新连接与应用结果，才能避免用更多 deny-all 名称掩盖同一份旧允许。
