把 tar 提取留在暂存区，再验收完整产物

按 Python 3.14 的 data 过滤规则说明 tar 暂存提取、部分失败、errorlevel 与重复成员，区分受控样本和不可信上传服务。

正文

核心要点

  • 默认 data 过滤器不等于完整的不可信归档策略。
  • 提取中止可能留下文件，正常返回也要核对成员。
  • 资源预算、重复名政策和产物移交由应用另行安排。

Python 3.14 默认使用 tar 的 data 提取过滤器，不表示不可信归档可以直接解压到正式目录并发布。过滤器限制部分危险文件特性，应用仍需检查来源与成员、约束资源，并负责失败后的部分产物。更明确的交付流程是先在新的暂存目录处理，再验证完整结果，最后单独完成产物移交。

默认改变了什么，没有改变什么

Python tarfile 文档说明，三点十二版加入提取过滤器，三点十四版把默认策略从相当于 fully_trusted 改为 data。本文于二〇二六年十月三十日核对页面，文档头标为 Python 3.14.10；补丁版本也可能修改路径处理，不能只记录一个大版本号就认为实现细节完全相同。

data 继承部分 tar 过滤行为，并额外拒绝指向绝对路径或目标目录之外的硬链接、符号链接，拒绝设备等特殊文件，还调整部分元数据。这不是“凡是看起来以斜杠开头就一律同样报错”的简单规则；官方另有前导斜杠处理与归一化说明。需要精确接受集合时，应依据所部署版本逐项测试，而不是重新发明一个字符串前缀检查。

文档同时警告，没有一个现有过滤器挡住全部危险归档；即使使用 data，也不适合在没有事先检查的情况下提取不可信文件。过滤器的默认升级是有用的保护，却没有批准某份上传包、确认预期文件清单或替系统提供磁盘和 CPU 预算。把它当成完整安全策略，会把原来显式的信任假设藏进默认值。

先用自有小样本验证提取与结果核对

下面是未执行的完整教学程序。归档内容由程序中的固定字节构造，属于自有受控样本，不接收用户上传，也不是通用安全解包服务。它用独立暂存目录、显式 data 与内容比对展示正常路径，结束后临时目录清理，不产生可长期下载的文件。

import io
import tarfile
from pathlib import Path
from tempfile import TemporaryDirectory

expected = {"note.txt": b"example\n"}
with TemporaryDirectory() as directory:
    root = Path(directory)
    archive = root / "sample.tar"
    stage = root / "stage"
    stage.mkdir()
    with tarfile.open(archive, "w") as output:
        for name, content in expected.items():
            member = tarfile.TarInfo(name)
            member.size = len(content)
            output.addfile(member, io.BytesIO(content))
    with tarfile.open(archive, "r") as source:
        source.errorlevel = 1
        source.extractall(stage, filter="data")
    observed = {p.name: p.read_bytes() for p in stage.iterdir() if p.is_file()}
    assert observed == expected
    print(sorted(observed))

这里的断言只核对这份已知小样本的普通文件内容，不能升级成任意归档的验证器。它没有实现完整目录与链接白名单、重复名政策、解压资源上限或持续受攻击目录的保护。真实上传流程必须在选择提取之前建立相应检查和隔离，不能把函数名改成 safe_extract 就宣布安全完成。

显式 filter 还能让代码评审者看见策略，不必依赖别处是否设置了 extraction_filter。两种入口的参数类型也应按文档核对：调用方法可以接收命名过滤器，类或实例默认属性则有自己的要求。示例只在 extractall 调用处传字符串，不把它复制到所有配置位置。

后面一个成员被拒绝，前面的文件会撤回吗？

不会自动形成事务回滚。官方说明，提取中止可能留下已经提取的部分，库不会替用户清理。过滤器拒绝成员时的异常和继续行为还受 errorlevel 影响。不能只看到“发生异常”就断言目录里没有文件，也不能看见目录存在就把它标成检查通过。

应用应给暂存对象明确身份和状态。失败时可以按规则删除自己拥有的整个暂存范围，或在受控位置保留诊断并安排到期清理；只有确认的完整产物才能进入正式交付目录。若目录在提取过程中还被其他参与者修改，过滤检查与文件系统变化之间又有独立风险，新建隔离目录有助于缩小范围，却不等于操作系统隔离已全部完成。

这个追问影响用户可见状态。接收归档、开始检查、提取中、拒绝、验证完成和移交成功，不应都压成“上传成功”。后台任务失败后若还有一部分可下载文件，用户可能把它误当完整版本。文件暂存与公开访问应使用不同的权限和状态规则，而不是靠不可猜的路径名表达许可。

同一路径出现两次，谁决定哪份正确？

tar 文档提醒，归档允许同一文件多次出现，后面的成员可能覆盖前面的版本。这是格式用途之一，data 过滤器不会替业务决定哪一份内容是获准版本。若产品要求一个预期文件只能出现一次，应事先检查重复成员并拒绝，而不是在提取后只数最后留下几份文件。

大小写不敏感文件系统还可能让不同名字指向同一目标。允许字符、路径长度、成员数量与扩展类型应根据用途定义，不要把样例里的一个文件扩展成所有系统的白名单。对只需要一份固定格式报告的业务，限制为预期成员集合通常比开放所有 tar 特性更容易审查，但具体集合仍需产品确认。

资源策略同样独立。官方明确说预定义过滤器不防止拒绝服务，建议考虑外部的磁盘、内存和 CPU 限制，以及成员数、总提取大小与单文件大小。归档压缩后的上传体积不能替代展开成本。本文不提供一个通用安全阈值，也不把预检元数据中声称的大小等同真实执行成本。

拟议验证从自有正常样本开始，再在隔离环境加入被拒链接、特殊成员、重复名称、预期外成员和中途失败，核对暂存状态、残留内容与交付是否被阻断。资源上限和并发目录变化需要独立受控验证，记录解释器补丁版、平台和配置。没有执行这些测试，就不能给出攻击防护或资源节省效果。

尤其要核对 errorlevel 为零的配置。文档说明，过滤器拒绝可在该设置下记录错误、跳过成员而继续提取；于是“函数正常返回”也不能自动代表每个成员都被接受。示例显式使用会让此类拒绝中断的设置，只为了让受控样本的预期可见，不意味着其他风险消失。真实交付若允许跳过某些成员，应把跳过清单纳入验收，而不是从最终目录中悄悄删除失败证据。

本站上传对象的隔离与交付讨论一般文件入口；本篇把范围具体到 tar 提取过滤器。本文没有运行解包、恶意归档或生产服务测试。让过滤规则、资源预算、部分失败与产物移交各自可解释，才能说明默认 data 真正保护了哪一段。
