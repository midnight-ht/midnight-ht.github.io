hosts 里能找到地址，Node.js resolve 为什么仍失败？

用固定 IPv4 的系统映射与 DNS A 查询对照，解释 Node.js lookup、resolve 的来源、结构和错误差异，并保留连接身份边界。

正文

核心要点

  • lookup 使用系统解析，resolve 系列询问 DNS。
  • 比较来源时应控制地址族，不能同时改变两个条件。
  • 解析成功或某个错误码不能替代连接与授权判断。

dns.lookup() 与 dns.resolve() 回答的不是完全相同的问题。lookup 使用操作系统名称解析设施，可能采用 hosts 等系统配置；resolve 系列发起 DNS 协议查询。一个名字能被本机其他应用找到，不表示直接 DNS 查询也会得到同样答案。替换接口前，应先确定需要哪一种解析合同。

系统名称解析不等于一次 DNS 查询

Node.js DNS 文档说明，lookup 不一定使用 DNS 协议，也可能不需要任何网络通信；需要与同一系统其他应用相似的解析行为时，使用这一系统设施。本文于二〇二六年十月三十日核对的二十四版本分支头标为 v24.22.2。下面没有执行解析、容器或网络测试。

设想开发环境在 hosts 中给内部测试名安排了地址，而 DNS 服务没有这条记录。浏览器或采用系统解析的程序可以找到它，改用 resolve4 的诊断脚本却失败。两者都可能符合各自接口合同，并非某个库“丢掉了域名”。排障需要记录回答来自系统名称服务还是指定 DNS 查询，不要把应用窗口里成功打开网页当成两种 API 应等价的证明。

操作系统的名称解析来源也不只一份文件。实际顺序和配置取决于平台，因此不能把 lookup 定义为“只读 hosts”，也不能从一个 Linux 容器的结果推断所有 macOS 或 Windows 机器相同。文章的判断是来源范围不同，不是宣布某个固定系统查找顺序。

在同一程序里保留两个问题的结果

以下是完整但未执行的比较脚本。它要求调用方提供测试名称；测试环境应事先约定系统映射和受控 DNS 数据，不能拿一个碰巧在公网失败的名字当作可靠负样本。脚本分别保存成功与失败，不因一个失败就丢掉另一个结果。

import { lookup, resolve4 } from 'node:dns/promises';

const hostname = process.argv[2];
if (!hostname) throw new Error('provide a controlled test hostname');

const results = await Promise.allSettled([
  lookup(hostname, { all: true, family: 4 }),
  resolve4(hostname),
]);

for (const [index, result] of results.entries()) {
  const operation = index === 0 ? 'system lookup' : 'DNS A query';
  if (result.status === 'fulfilled') {
    console.log(JSON.stringify({ operation, value: result.value }));
  } else {
    console.log(JSON.stringify({ operation, error: result.reason.code }));
  }
}

一种拟议输入是：隔离环境的系统映射包含测试名到某个回环地址，而受控 DNS 明确没有相同名称的 A 记录。另一种是两边都有记录但值不同。两组都能检查应用是否真的区分来源。本文不提供预先编造的输出；系统配置、DNS 回答和实际运行结果都应保存在执行记录里，不能只留一张终端截图。

还要看返回结构。lookup 的 all 选项在此返回地址和地址族对象列表，resolve4 返回 A 记录地址列表；即使地址文本相同，也不能让调用方继续按旧结构读取字段。代码迁移应同时检查错误分类、IPv4/IPv6 要求和依赖方需要单地址还是地址集合。将数组第一项直接作为唯一服务地址，也是一份需要说明的选择政策。

异步写法不代表底层路径相同

文档的实现说明指出，lookup 底层使用 getaddrinfo，并在 libuv 线程池执行同步设施调用；resolve 系列使用不同实现，执行 DNS 查询，不走相同的 getaddrinfo 路径。这个差异可能影响某些负载，但不能简单写成“resolve 永远更快”。两种接口可能获得不同答案，先改变语义再比较耗时，已经不是同一个任务的性能对照。

若应用确实遇到解析与其他线程池工作争用，应先确认观察对象和实际负载，记录并发量、耗时分布、配置与失败。增加线程池大小或替换解析器都需要项目评估；一次短脚本的时间不能证明生产连接延迟会下降。本文只说明实现路径，不提供资源消耗和吞吐数字。

需要 DNS 记录类型，例如 A、AAAA 或 MX，应该选择对应查询接口，并处理该记录的语义。需要应用连接时的系统名称解析，则应先检查连接库使用哪个入口。有些网络接口允许替换 lookup，但这项能力不代表替换后自动保留所有原行为。要证明兼容，需要实际连接合同一起检查。

lookup 的 ENOTFOUND 就是 DNS 没有记录吗？

不能这样反推。官方文档提醒，该错误也可能来自其他解析失败，例如可用文件描述符耗尽。即使业务把它显示为“找不到服务”，内部诊断也应保留接口、原始错误码和环境状态，避免把本机资源故障写成权威 DNS 不存在的事实。resolve 的错误同样应按对应接口解释，而不是统一抹成网络不可用。

这个追问会影响重试和支持流程。系统故障反复重查 DNS 未必有用；记录不存在则可能需要修复配置。要决定重试，先知道失败在哪条解析路径，以及观察是否来自受控服务。不要因为两个方法都在 dns 模块里，就认为它们的每个错误都能一一映射。

有了 IP，HTTPS 目标就可以随便替换吗？

解析结果只提供地址信息，不替代 HTTP 主机、TLS 服务身份或应用目的地授权。若将原始名称改成 IP 连接，需要核对连接库如何保留服务器名称与证书校验合同，不能通过关闭证书验证换取“连接成功”。本站ExternalName 与证书名称讨论了另一层名称关系，本篇不提供跳过 TLS 校验的写法。

服务端抓取用户地址时，还要让解析检查与实际连接遵守同一目的地政策。lookup 或 resolve 成功都不证明目标已获授权，也不自动防住解析变化与重定向；相关设计见出站目的地边界。不要把换解析器当作完整安全修复。

这份来源对照应先固定同一种地址族，因此示例把 lookup 限定为 IPv4，与 resolve4 的 A 查询对应。否则一个返回 IPv6、另一个只问 IPv4，就同时改变了两个条件，无法把差异归因于 hosts 或 DNS 来源。确认这层对照后，再独立加入双栈与排序用例；不要为了得到相同结果，事后删除所有“不喜欢”的地址。每项预期都应先来自受控配置，而不是从程序当前输出倒推。

拟议验证分别覆盖仅系统映射、仅 DNS、两边不同答案、A 与 AAAA 差异和可解释的解析失败，再观察真实连接采用哪组结果。每轮记录系统配置与解析库版本，不能把开发者工作站缓存混成服务器事实。先让每次回答的来源可解释，再考虑是否改变 API；名称相同，问题未必相同。
