投射token文件已经更新，Pod为什么还在发送旧凭据？

把投射文件刷新推进到客户端请求实际采用，检查启动缓存、旧头闭包、subPath和重开路径，并将受众验证与对象授权分开。

正文

核心要点

  • 文件由平台刷新，应用必须让真实请求采用新凭据。
  • 旧句柄、复制文件和固定请求头可能绕过加载意图。
  • 凭据有效性、受众与资源权限分层检查，不记录可重放内容。

投射的 ServiceAccount token 文件已经换新，应用仍可能继续发送启动时缓存的旧凭据。kubelet 负责刷新文件，应用负责重新加载并让请求实际采用新值。重启暂时恢复只能提示消费路径值得调查，不能证明需要把短期凭据改成长久有效。

自动轮换到了哪一步？

Kubernetes 的服务账号配置说明写明，kubelet 代 Pod 请求、保存投射 token，并在临近到期时主动刷新；文档同时明确应用负责在轮换时重新加载。它描述的主动轮换条件包括超过总有效期的百分之八十或超过二十四小时。本文于二〇二六年十月三十日核对来源，没有读取、打印或保存真实 token，也没有访问集群。

这两个责任中间存在消费交接。应用启动时读取一次文件，把字符串交给 HTTP 客户端，后来即使挂载路径已经更新，内存里的值也不会因此自动改写。如果每个请求的 Authorization 又由启动时闭包生成，另一个刷新任务读到了新文件，也可能没有更新真正发送的那份头。

调查应区分文件刷新、应用加载、客户端采用与接收方验证。只看到文件修改时间变化，不能证明请求用了新值；只看到一次认证失败，也不能证明原因一定是到期。需要保留非敏感时间与状态线索，避免为了比对凭据把完整令牌复制进日志，制造新的泄露副本。

把投射声明与消费者放在一起看

以下未执行片段描述 token 的来源和路径。它不是完整应用部署：build-robot 服务账号、教学镜像及接收方都需要另行准备；receiver.example 表示假设的受众合同，不是一个已经接通的供应商。

spec:
  serviceAccountName: build-robot
  containers:
    - name: worker
      image: example.invalid/worker:demo
      volumeMounts:
        - name: receiver-token
          mountPath: /var/run/receiver
          readOnly: true
  volumes:
    - name: receiver-token
      projected:
        sources:
          - serviceAccountToken:
              path: token
              expirationSeconds: 7200
              audience: receiver.example

假设接收方确实认可该签发者和 audience，客户端应该从 /var/run/receiver/token 取得适当凭据。错误消费者可以概括为“启动时读取，永久复用”；候选消费者则在受控时机重新打开该路径，更新后续请求所用凭据，并对读取失败作明确处理。两小时是说明性的请求期限，不是本篇建议，也不能替代实际签发结果的条件。

完整交接要等到真正的请求入口。设想刷新器更新了共享变量，旧客户端对象却在构造时把原值固化；日志会显示“加载成功”，请求仍旧。验证应追踪哪个组件为每次请求生成头，而不是只在刷新函数里加一行成功日志。也不能靠持续重建客户端掩盖所有权问题而不观察连接和并发行为。

投射卷说明另有一个明确边界：用 subPath 挂载投射卷来源的容器不会收到这些来源的更新。把 token 复制到普通临时文件再永远读取副本，也不是继续读取原投射路径。应用加载前，先确认它消费的到底是哪条路径和哪种挂载，不把文件来源错误混成刷新间隔问题。

每次读取，还是维护有界缓存？

每次请求重新读取更容易表达“采用当前文件”，但要考虑读文件成本、并发和读取失败。维护缓存可以减少重复读取，却需要明确刷新触发、最大陈旧时间和原子交接。官方提供周期重载的思路，但实际周期应与有效期、客户端能力和故障政策协调，不能把某个示例分钟数当作全部业务的安全承诺。

若读取新文件失败，不能无条件永久退回旧值并继续宣布刷新正常。候选策略可以在已知剩余有效范围内短暂保留，或者让新请求清楚失败并进入恢复，但需要有明确规则。多线程更新也要保证一个请求拿到完整一致的凭据，而不是将读取和替换拆成可能暴露中间状态的共享操作。

换成长期 Secret 不是对消费错误的直接修复。它改变凭据有效期和撤销风险，没有证明旧客户端会采用任何新值。若团队另有特殊需求，需要按受众、权限和保留规则评审，不应为减少一次重载开发就默默扩大凭据寿命。关于一般泄露处置可参看密钥轮换与撤销，但本题没有真实泄露事件。

重新加载后仍被拒绝，是否应该继续换 token？

先定位拒绝原因。签发者、受众、有效期验证与 RBAC 的对象操作权限不是同一层；一个新鲜且能认证的 token，仍可能没有读取目标资源的权限。不断轮换不能自动补出一条缺失授权。也不要仅凭某个状态码就固定归因，应结合接收方实际错误合同和服务端记录。

前面的 receiver.example 是假设外部接收方的受众，它的授权应遵循自身合同。另举 Kubernetes API 的例子时，必须先使用该 API 接受的受众并通过认证，再讨论账号是否有权读取目标 ConfigMap；权限不足应核对角色与请求。若受众不符，则先检查投射声明和接收方约定，不能假设外部受众令牌可以直接用于这个 API。两种修复不能互相替代。诊断资料应保留请求身份的非秘密标识、操作范围与拒绝阶段，不附上完整 bearer 值。

拟议验证在隔离环境安排旧值缓存消费者与重载消费者，观察文件轮换之后谁实际采用新值。加入读取失败、旧头闭包、subPath 与普通投射挂载的对照，再分别制造受众错误和权限不足。全程不记录真实 token 内容，使用受控审计与非敏感时间线；本文未运行这些检查，也不声称认证可用性已经验收。把文件更新推进到请求真实采用，才是应用需要完成的那段交接。

重新读取也要说明操作的是路径还是旧句柄。若进程一直持有早先打开的文件对象，对这个对象再次read不一定等同于重新打开当前投射路径。具体更新机制需要按挂载与客户端验证，不应仅凭函数名叫reload就认定采用新文件。对照应让两种消费者明确不同，再观察接收方的认证时间线。

采用证据可以是加载时刻、客户端配置版本和受控接收方的身份结果，不必保存可复用凭据。若需要关联多个请求，应设计不泄露秘密的运行标识，并规定保留时间；把token全文或可直接重放的认证头放进调试报告，会使一次轮换排查变成新的凭据副本管理问题。
