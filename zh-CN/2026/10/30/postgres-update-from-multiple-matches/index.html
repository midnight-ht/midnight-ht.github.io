UPDATE FROM 匹配两条来源，PostgreSQL 到底用哪条更新？

区分目标主键与连接来源唯一性，用改价示例说明 UPDATE FROM 的多匹配选择、零来源差异、预检和并发边界。

正文

核心要点

  • 目标表有主键，不证明每个目标只匹配一条来源。
  • 先拒绝或明确归并重复来源，再执行连接更新。
  • 标量子查询与 FROM 在零来源时的行为不同。

PostgreSQL 的 UPDATE … FROM 若让同一目标行匹配到多条来源，只会采用其中一条连接结果，采用哪条并不容易预测。目标表有主键也不能消除这种歧义：主键约束目标身份，不约束每个目标连接到多少条报价。批量改价前，应先证明来源匹配唯一，再讨论价格是否获准采用。

没报错，不代表数据库选了最新报价

PostgreSQL 18 的 UPDATE 说明要求使用 FROM 时确保每个待更新行至多产生一条连接输出。若产生多条，只有一条用于更新，但选择不可据此预测。本文依据二〇二六年十月三十日核对的固定版本文档；下面没有执行数据库查询，所有结果关系都是教学推演。

假设商品甲当前价格十元，导入批次里同时有十二元和十五元两条报价。开发看到目标商品编号唯一，就直接按编号连接更新。这个唯一键只证明商品甲不是两条目标记录，不能证明候选报价只有一条。语句成功返回也没有替产品决定“最新”“已审核”或“取最低价”。这些词需要业务字段和规则，数据库不会从连接写法猜出来。

给来源加排序，也不能把任意执行过程当成正式选择合同。若业务要求最近审核的一条，应先说明审核时间、版本、并列时的优先级和异常处置，再形成每个商品一条来源。若重复报价本来就是导入错误，拒绝这批候选通常比偷偷挑一条更能保留证据。确定性和业务正确性分别需要条件。

用唯一来源构成一个可以审查的更新

下面是未执行的完整示例，只适合隔离数据库。它演示已经通过业务确认的单批报价，不表示创建表就完成了审批。此处只有一个批次，来源表以商品编号唯一；多批系统还需把批次和租户等实际身份写进结构与连接条件。

CREATE TABLE example_products (
  product_id bigint PRIMARY KEY,
  unit_price numeric NOT NULL
);
CREATE TABLE example_approved_prices (
  product_id bigint PRIMARY KEY,
  unit_price numeric NOT NULL
);
INSERT INTO example_products VALUES (1, 10), (2, 20);
INSERT INTO example_approved_prices VALUES (1, 12);

BEGIN;
UPDATE example_products AS p
SET unit_price = s.unit_price
FROM example_approved_prices AS s
WHERE p.product_id = s.product_id
RETURNING p.product_id, p.unit_price;
SELECT product_id, unit_price FROM example_products ORDER BY product_id;
ROLLBACK;

按定义推演，第一件商品有一条匹配报价，第二件没有匹配，因此第二件不会由这次连接更新。ROLLBACK 用于撤销这次教学改价，不应把 RETURNING 的内容解释成最终提交证据。来源主键限制了相同商品的第二条来源；它没有证明报价金额合法、审批未过期或当前操作者有权限。这些仍属于其他检查。

作为负样本，可在重新初始化的隔离库中去掉来源唯一约束，插入同一商品的两种价格，再先执行相同条件的 SELECT 连接，观察候选行。不要把某次 UPDATE 恰好采用十二元写成规则；改变插入顺序或执行计划仍不能补出业务承诺。负样本的验收目标是发现多匹配并阻止它进入正式更新。

预检只能报告问题，不能自己锁住未来

可以先按真实目标身份统计连接行数，找出大于一的对象，保留候选来源编号和冲突原因。检查应使用最终更新的同一份连接键与过滤条件；仅在原始文件里按商品编号分组，却在写入时额外跨租户连接，不能证明实际连接唯一。全表左右行数相等也无意义，关键是每个目标对应几条来源。

一条预检 SELECT 不会自动阻止别的会话随后加入重复来源。若依靠预检保护写入，应让已确认批次在相关阶段保持不可变，或使用能够维护该唯一关系的约束及事务设计。这里的建议没有提供通用锁模板；需要按真实修改入口设计，不能把“先查了没有重复”升级为并发期间一直没有重复。

如果输入允许多个合法版本，可以先在暂存区形成明确的选择结果，再加约束证明结果一目标一行。不要直接对金额求最大值就带上另一行的审批人，也不要随便 DISTINCT 隐藏不同报价。本站代表行的选择依据讨论了为什么组内优先级必须先定义；本篇进一步要求这个选择成为写入前的前提。

换成标量子查询就完全等价吗？

不等价。官方 UPDATE 文档规定，用作赋值的子查询不能返回多于一行；没有行时会把相应目标列赋为 NULL。FROM 连接没有匹配时，目标行通常不会进入该连接更新。对于允许空价格的列，这可能把旧价格清空；本示例的非空约束则可能让该赋值失败。不能为抓住多行问题，就忽略零行时行为已经改变。

因此选择子查询需要同时定义零条、一条、多条来源的合同。若要求没有报价就保持旧值，应明确表达该条件，并验证未匹配商品仍保留。若没有报价就是错误，则让接口报告缺失，而不是借 NULL 偶然触发后续失败。多行报错只是一个安全性质，不能代替全部结果分类。

拟议验收从每个目标零条、一条、两条候选开始，先手写应保留、应更新或应拒绝的预期。加入同商品跨租户、审核并列、源批次被修改和目标在更新前已变化的情况，分别核对连接输入、实际修改与最终提交。若业务只允许覆盖特定旧版本，还需在更新条件中表达版本合同；唯一来源本身不会防止覆盖过时目标。

预检若只寻找多来源，可以直接检查候选内连接并按目标分组；零来源则应从目标集合另外寻找未匹配对象。如果为了保留零来源而使用 LEFT JOIN，不能把占位行的 count(*) 当作来源数量，应明确数哪个非空来源身份。两种预检可以分别返回重复与缺失，不必把它们挤成同一个数字。报告还应保留目标和候选来源编号，让维护者能回到原始批次纠正，而不是只收到“有重复”的总数。

本文没有运行这些 SQL，也不报告性能改善或生产故障。审查连接更新时，先要求说明每个目标的来源身份为何唯一，再检查选择理由、缺失处理和提交结果；“目标有主键”只能回答第一张表的身份问题。
