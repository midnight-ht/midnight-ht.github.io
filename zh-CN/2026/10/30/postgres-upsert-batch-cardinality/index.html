两条数据各自能 upsert，放进同一条 INSERT 为什么失败？

解释同一条 PostgreSQL 冲突更新为何不能重复影响一个目标，区分批内重放、版本选择、冲突拒绝与拆分语句的代价。

正文

核心要点

  • 单条 DO UPDATE 不能对同一目标行重复生效。
  • 批内归并需要身份、版本和内容冲突政策。
  • 拆分语句可能改变原子性与中间可见状态。

两条输入各自执行 upsert 可以成功，不表示把它们放进同一条 INSERT … ON CONFLICT DO UPDATE 仍会成功。PostgreSQL 不允许这条语句对同一目标行重复生效；本批候选若重复冲突键，可能触发基数错误。修复入口是确定批内同一身份的处理规则，而不是无限重试同一份输入。

一条语句有自己的基数合同

PostgreSQL 18 的 INSERT 文档把带 DO UPDATE 的冲突插入称为确定性语句：同一已有行不能在该命令中被影响多次，发生时抛出 cardinality violation，并要求拟插入行不要在冲突仲裁键上互相重复。本文于二〇二六年十月三十日核对固定版本说明；没有运行以下 SQL，也没有真实批量导入事故记录。

这个限制与“表上只有一行同键记录”并不矛盾。目标唯一约束已经找到了那条记录，问题是同一句命令带来了两个都想修改它的候选。单条 SQL 没有被授权替业务决定最后一行赢、最高版本赢或把两笔金额相加。把业务归并规则藏在文件顺序里，会让换一种分批方式改变结果。

先分清三种重复。相同身份、相同版本、相同内容也许是可忽略重放；相同身份、不同版本也许应选择较新状态；相同版本、不同内容可能是数据冲突。数据库基数错误不会替团队完成这三类分类。即使某个分支允许丢弃重复，也要保存它为什么可以忽略的依据。

用同一个已有订单作两条候选的对照

以下是未执行的完整教学输入，只用于隔离库。目标表已有订单四十二的一版状态，随后一条语句同时提交它的两个新版本。两次候选都命中同一个冲突目标，不能把第二次更新当作自然的“继续推进”。

CREATE TABLE example_order_state (
  order_id bigint PRIMARY KEY,
  version integer NOT NULL,
  state text NOT NULL
);
INSERT INTO example_order_state VALUES (42, 1, 'created');

BEGIN;
INSERT INTO example_order_state(order_id, version, state)
VALUES (42, 2, 'packed'), (42, 3, 'shipped')
ON CONFLICT(order_id) DO UPDATE
SET version = EXCLUDED.version, state = EXCLUDED.state;
-- 观察语句失败后，结束本轮事务：
ROLLBACK;

这里预期的是语句基数错误，不给出伪造的客户端错误日志。具体驱动怎样暴露异常、失败后事务能否继续使用以及如何回滚，应由隔离测试记录。测试驱动不能遇错继续执行其他写入，再把它们的结果混成原语句输出。尤其不要在不知道当前事务状态时自动发下一条业务 SQL。

假设产品已经确认同一订单采用最高版本，且最高版本唯一、内容符合状态规则，那么可以在前置阶段形成只有三版的一条候选，再执行同样的 upsert。下面展示的是经过确认后的写入，不是从两条输入自动推导业务授权的算法。

INSERT INTO example_order_state(order_id, version, state)
VALUES (42, 3, 'shipped')
ON CONFLICT(order_id) DO UPDATE
SET version = EXCLUDED.version, state = EXCLUDED.state
RETURNING order_id, version, state;

正式实现若还要求不接受过期事件，可以额外加经过确认的版本条件，但那不会代替本篇的批内身份检查。本站条件冲突更新与空 RETURNING明确讨论单行输入的更新拒绝；本题则在该逻辑之前问：一个命令里到底提出了几次同一目标的修改。

先形成可解释候选，再进入目标表

批次暂存应保留原始行身份、业务键、版本和必要的来源信息。先按真正的冲突键分组，找出重复候选，再按业务合同合并、选择或拒绝。冲突键若包括租户，不能只按订单号归并；若采用表达式唯一索引，还要核对归并所用的身份是否与数据库仲裁方式一致。

选择“最后一条”时必须说明顺序来自哪里。网络到达顺序、文件行号和业务版本可能不同；上游重试或并行读取也会改变到达顺序。最高版本也不是完整答案：最高版本并列且内容不同，需要拒绝、人工处理或另一个正式规则。不能为了生成一条候选就对状态取最大文本值，制造从未被任何输入提出的组合。

完全相同的重复可以按已确认政策压成一条，但导入报告仍应解释哪些原始行归并到了哪个候选。归并后的行数减少不是丢数据的唯一判断，必须看业务要求是不是把它们视为同一事件。反过来，不同事件即使字段偶然相等，也不应仅凭全行 DISTINCT 当作同一身份。

拆成多条语句就算修复了吗？

拆开可能避开单条语句的重复目标限制，却改变了观察与事务条件。若每条都自动提交，其他读者可能看到中间版本；后面失败时，前面已写入的状态仍在。即使放在同一个事务里，依次覆盖的顺序仍是一份业务选择，需要产品确认，不能把“拆后不报错”当作选择规则正确。

同理，不要把 DO UPDATE 的说明机械推广成 DO NOTHING 的全部行为。二者对冲突采取不同动作；若需求只是忽略已存在身份，需要独立验证忽略范围、返回结果和是否隐藏同键不同内容。改用另一分支是接口语义改变，不是消除错误消息的小补丁。

拟议验收先固定已有目标，分别提交一个候选、两个相同候选、两个不同版本和同版本不同内容；再测试新目标与已有目标混合的一批。对每组先写下应新建、应更新、应归并还是应拒绝，再核对异常、返回行与最终落库。把输入顺序反转、批次拆分和重放加入控制，确认业务结果不依赖未经声明的排列。

数据库抛出的基数异常也不是一份逐条业务报告。若接口允许告诉用户哪些行需要修正，应在写入前把重复组与原始行关联，并明确整批拒绝还是只处理已确认子集。选择部分处理会增加提交与重试责任，不能在捕获异常后把剩下行随意再发一遍。预检发现重复不等于发现全部非法输入，字段校验和状态转换仍须执行；导入结果应分别表达身份冲突、输入错误和实际写入。

数据库事实与导入报告也应分开保存。语句成功和返回行说明这次 SQL 的效果，整批接受、拒绝与归并说明业务处理；最终提交另有证据。本文不提供吞吐或幂等效果数字。先让每个被写入的身份只有一个明确候选，再让数据库执行那次已获确认的修改。
