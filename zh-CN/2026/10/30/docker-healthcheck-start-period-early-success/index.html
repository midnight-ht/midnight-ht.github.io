start-period还没过，Docker为什么已经把容器判成unhealthy？

沿失败、成功、再连续失败解释启动宽限如何结束，区分检查频率、超时、Engine版本与真实可服务条件，不把健康变化当自动重启。

正文

核心要点

  • 启动期内提前成功后，后续连续失败会开始计数。
  • 检查频率、超时与重试次数不是同一个控制量。
  • 健康状态仅说明所问条件，恢复动作和业务路径另行验证。

Docker 的 start-period 不是一段无条件免于健康失败的倒计时。启动期内一次检查成功，会改变后续失败的计数：容器被视为已经启动，接下来的连续失败开始计入重试上限。看到窗口还没结束就变成 unhealthy，先查成功与失败的顺序，而不是只把启动期调得更长。

失败宽限与推迟检查不是一回事

Dockerfile 的 HEALTHCHECK 说明规定，健康状态独立于正常运行状态，初始为 starting；检查通过会变成 healthy，连续失败达到条件后变成 unhealthy。启动期为初始化提供宽限，其间失败不计入最大重试次数，但提前成功以后，后续连续失败开始计数。本文于二〇二六年十月三十日核对在线文档，没有启动容器或测量探针时间。

因此，start-period 不表示“先睡到截止时刻再第一次检查”，也不保证这一段内永远不能 unhealthy。检查确实运行，成功结果也确实会被采用。若应用初始化过程中暂时让一个简单端点返回成功，随后才继续加载关键数据，那个成功可能过早结束了原先期望的宽限。

这是探针问题与业务准备问题的交叉。TCP 能连接、主页面能返回、必要数据已装载，可能是不同条件。选择检查时，要说明哪个条件足以让后续失败按正常阶段处理；不能因为一个接口成本低，就不经判断把它当成所有初始化完成。反过来，探针也不宜执行昂贵写入或重复初始化，免得检查本身改变服务状态。

一次短暂成功如何改变时间线？

设想镜像提供只读脚本 /usr/local/bin/check-ready，应用需要一段初始化时间。以下 Dockerfile 片段没有执行；基础镜像与应用构建需在项目中准备，脚本不能靠这一行声明自动出现。

HEALTHCHECK --interval=10s --timeout=2s \
  --start-period=60s --start-interval=5s --retries=3 \
  CMD ["/usr/local/bin/check-ready"]

假设启动期内前两次失败，随后一次成功，再有三次连续失败。成功前的失败处于宽限，不计入同一重试累计；成功后容器已被视为启动，随后三次失败会按正常规则计数。即使从启动到第三次后续失败尚不足六十秒，也不能据此否定 unhealthy 的可能性。此处描述检查结果序列，不承诺每次恰好发生在哪个墙上时钟秒数。

真实调度还包含检查耗时、超时和执行器行为。官方给出检查间隔与前一次完成时刻的关系；不能直接把 retries 乘某个 interval 就写成精确恢复期限。应记录实际检查的开始、结束、退出信息和状态转换，再解释结果。只拿容器创建时间减去当前时间，会丢掉最重要的那次提前成功。

一个有效对照是固定其他选项，只改变启动期内是否出现成功。全程尚未成功的启动序列，与先成功再失败的序列，预期计数不同。若测试时顺便改了检查脚本、镜像和间隔，就很难证明差异来自哪个输入。本文没有运行这些对照，不报告状态转换已通过。

应该延长窗口，还是改变探针条件？

如果初始化真的更慢且始终未通过必要检查，适当宽限可以减少过早失败判断，但时长应来自实际启动特征。若问题是探针先宣布成功、应用后来仍未具备必要能力，单纯延长 start-period 未必修复：提前成功这个条件仍会结束失败豁免。应先核对成功究竟代表什么。

start-interval 控制启动期检查频率，文档注明需要 Docker Engine 二十五版或更新；不能把含该选项的示例无条件交给旧 Engine。interval、timeout、retries 也分别控制不同变量：更频繁不等于更可靠，更长超时也不等于业务会恢复。配置兼容与服务语义要各自验证，不要把构建能解析当成运行行为证明。

健康状态改变仍不是独立 Docker 自动重启的统一承诺。本站健康失败与重启条件已说明进程退出与 unhealthy 的区别，本篇不把提前计数误写成重启触发。若有外部恢复控制器，还要单独验证它实际消费了什么状态、执行了什么动作以及是否打断进行中的工作。

把探针改成固定 sleep，能证明初始化完成吗？

不能。固定时间过去，只说明等待结束，不证明数据、权限和依赖已满足。若每次检查只是睡眠后返回成功，就会让状态变绿而缺少被检查条件；如果睡眠超过 timeout，还可能直接变成检查失败。应选择与本地可服务能力有关、成本受控且结果可解释的观察。

有些依赖短暂失败可以由应用自行恢复，不应不加区分地让全部副本同时退出服务。探针条件与恢复策略需要相互协调，但这里不提供所有服务的统一检查端点或阈值。让业务团队说明哪些初始化步骤是不可缺少的，再由实现验证这些步骤何时真正成立，比复制一个六十秒参数更可靠。

拟议验收保留镜像身份、Engine 版本、实际健康配置和只读探针结果，分别安排从未成功、提前成功后连续失败、成功后偶发单次失败以及探针超时。检查连续失败如何被成功打断，并观察现有恢复执行者的行为。没有这些证据时，只能说配置表达了某个意图，不能说启动保护或故障恢复已经成立。

还应保留检查范围与业务范围的区别。假设只读探针能确认本地服务响应，但某项需要外部权限的业务仍失败，healthy只证明前一条件。为减少误判而把全部业务写进周期探针，也可能增加依赖耦合和检查成本。应让启动判定需要的最小条件清楚可解释，再为其他用户路径安排独立验收。

探针诊断输出通常是有限记录，不适合当作完整事故档案。记录成功与失败原因时保持简短，不输出凭据或整个配置；需要更长上下文应由受控日志提供，并与容器身份和时刻关联。缺少一段输出不自动意味着检查没发生，仍要结合实际健康记录与状态变化判断。
