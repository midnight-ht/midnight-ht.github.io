手动工作流里选了false，为什么条件分支仍会运行？

沿手动输入、表达式、shell环境与步骤输出检查类型，解释非空字符串为何不能替代布尔开关，并用无副作用工作流验证分支。

正文

核心要点

  • 手动输入的类型需要由声明和消费上下文共同保持。
  • 进入文本通道后要重新核对格式，不能沿用原有布尔假设。
  • 分支判断正确不等于生产审批或操作授权已经成立。

手动工作流里取消了布尔开关，条件分支却仍运行，先检查读取的上下文是否保留布尔类型。workflow_dispatch 的 inputs 可以保留 false，github.event.inputs 中对应值则是字符串。非空的“false”不能直接承担布尔 false 的判断，修复应从声明、消费到输出交接逐段核对。

相同内容不一定是相同类型

GitHub Actions 工作流语法明确区分这两个上下文：inputs 保留布尔值，github.event.inputs 会转成字符串。choice 也是字符串，不能因为选项文字写成 true 或 false，就把它视为布尔类型。本文于二〇二六年十月三十日核对在线文档，没有触发任何工作流。

官方表达式说明列出假值，包括布尔 false、零、空字符串和 null；其他非假值会转为真。字符串“false”并不是空字符串。因此，条件直接消费事件字符串，可能与界面取消勾选的意图不一致。这是类型转换问题，不表示 GitHub 在界面上替用户重新选择了 true。

调查时最好记录触发事件、输入声明和最终条件表达式。只截取运行页面里的一段文字“false”，无法说明它在表达式里是什么类型。不同触发器、复用工作流与步骤输出也有各自合同，不能用一次手动输入的结论覆盖全部运行来源。

一个只有诊断输出的完整工作流

下面是未执行的教学配置，限定手动触发和布尔声明；步骤只写诊断文字，不包含部署、写入外部服务或生产凭据。

name: inspect-boolean-input
on:
  workflow_dispatch:
    inputs:
      show_details:
        description: Show optional diagnostic details
        type: boolean
        required: true
        default: false
jobs:
  inspect:
    runs-on: ubuntu-latest
    steps:
      - name: Explain selected branch
        env:
          TYPED_VALUE: ${{ toJSON(inputs) }}
          EVENT_VALUE: ${{ toJSON(github.event.inputs) }}
        run: printf 'typed=%s event=%s\n' "$TYPED_VALUE" "$EVENT_VALUE"
      - name: Optional details
        if: ${{ inputs.show_details }}
        run: printf 'Optional details selected\n'

设想开关为 false，最后一步应按布尔条件跳过；开关为 true 时才进入。两个 env 使用序列化形式帮助观察类型，但它们进入 shell 环境后仍是文本，不能拿 shell 里的字符串表示反推上下文对象本身。这里没有展示真实 stdout，预期来自文档与声明。

对照错误是把条件改成直接使用事件上下文中的开关字段，却没有明确比较。把一个非空字符串交给条件，就可能进入与布尔 false 不同的分支。若确实要读这个事件上下文，应根据明确的字符串合同比较，而不是依靠“看起来像布尔值”的内容。最好保持一种可审查的输入路径，避免不同 Job 各自选择不同转换方式。

显式比较，还是进行 JSON 转换？

对于本例已经声明的布尔输入，直接使用 typed inputs 最清楚。对于明确只允许“true”“false”文本的外部交接，可以选择显式字符串比较，或在验证格式后转换为布尔。两种方案应约定空值、拼写错误和缺失字段如何失败，不应为未知值默默采用更高权限的分支。

fromJSON 可以解析合法 JSON，但不是把任意文本都可靠猜成布尔的工具。一个格式错误的值可能导致表达式失败；一个合法数字或对象又不是本来承诺的布尔。需要的是受控的格式与类型合同，不是到处插入转换函数就宣布问题消失。本文不提供适用于所有外部输入的通用转换器。

步骤输出尤其容易重新引入字符串边界。某个 Job 先把布尔值写成输出，后续 Job 再读取时，不能只因前一阶段原来是布尔类型就跳过核对。应检查输出语义、序列化与消费表达式；正常 false、正常 true、空值及非法值分别验证。数据跨过一个文本通道，原有类型不会仅凭同名自动保留下来。

对诊断日志也要限制内容。本例开关不敏感，可以显示其类型线索；真实输入若含秘密、客户信息或目标标识，不应把整个事件对象输出到日志。定位类型只需相关字段与非敏感状态，不能为了看清一条布尔值而复制所有运行上下文。

开关判断正确，就能代替生产审批吗？

不能。布尔类型正确只证明这条分支按输入语义选择，不证明运行者有权发布、目标环境受到保护或产物属于已审查提交。即使用户选择 true，也需要独立的权限和环境规则；false 更不能被当成撤销已经执行副作用的命令。该问题是类型修复之外的授权边界。

例如把 show_details 改成一个名字叫 deploy 的开关，并不会自动出现保护规则。仍应核对触发者、工作流权限、目标环境和部署对象。本站环境、工作流与产物的三项检查讨论的是这一层责任，本例没有执行那种发布，也没有声称它已获批准。

拟议验证先用两次手动输入比较 typed 条件的分支，再安排事件字符串对照，保存输入声明、工作流版本和步骤跳过状态。随后把值经过一个步骤输出，检查消费端是否按既定格式还原。验证只需无副作用诊断，不应该为了证明分支正确而尝试一次真实生产发布。让类型、分支与权限各自留下证据，才能知道修好的是哪一项。

还要区分表达式求值与shell求值。上下文里的布尔false被序列化放进环境变量后，shell拿到的是文字；仅检查变量非空仍会得到与布尔开关不同的判断。应选一个明确的判断位置，把后续文字通道看作交接格式，而不是让两套真值规则各自猜测同一输入。

工作流如果后来增加push等触发，也不能假设每次运行都有同一份手动输入。应明确哪些事件允许进入该分支，缺少输入时是跳过、失败还是采用已定义默认；默认值不能悄悄扩大操作权限。这里的示例只声明手动触发，不证明其他事件已得到相同配置。

迁移已有工作流时，可以先在无副作用诊断中并排记录旧条件和新条件的选择结果。若false这一组两者不同，就保留证据并修正消费者；若true两者相同，也不能据此跳过false与缺值检查。一个成功分支只覆盖一种输入，不能为类型合同的其余分支作担保。
