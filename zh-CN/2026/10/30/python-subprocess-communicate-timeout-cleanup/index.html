communicate 超时了，Python 子进程为什么还在运行？

对照 Python run 与 Popen 的超时清理，用直接子进程示例说明终止、管道收尾、返回码、输出预算和后代边界。

正文

核心要点

  • 通信等待超时不等于直接子进程已经退出。
  • 终止后仍应完成管道通信并记录最终状态。
  • 进程树、输出预算和外部副作用需要独立合同。

Popen.communicate 抛出 TimeoutExpired，不表示子进程已经停止。这个接口超时后不会自动杀死子进程，调用者仍需终止目标并完成管道处理。subprocess.run 的合同不同：它会杀死并等待直接子进程，再抛出超时。先确认使用哪个入口，才能分配清理责任。

同一个 timeout 参数，不是同一份收尾服务

Python subprocess 文档分别描述 run 与 Popen.communicate 的行为。本文于二〇二六年十月三十日核对页面，文档头为 Python 3.14.10。这里讨论直接子进程和受控少量输出，没有运行子进程、信号或跨平台测试。

设想图片转换工具由 Python 启动，父进程等待输出一秒后收到异常。若代码只向用户返回“转换超时”，没有管理 Popen 对象，转换器可能继续占用 CPU 或写临时文件。异常说明等待预算耗尽，不说明进程或文件已达终态。能让请求尽快失败，与能收回子进程资源，是两项不同结果。

反过来，不能把 communicate 的规则套到 run，然后声称所有 TimeoutExpired 都留下活跃子进程。高级接口已经承担部分清理，低级接口则把控制权和责任交给调用者。若 run 足以满足需求，通常不必为了多几行配置就改用 Popen；需要交互或分阶段控制时，再明确接手这些责任。

一个直接子进程的完整失败路径

下面是未执行的完整教学程序。子进程只输出一小段固定文本再等待，不启动后代、不访问网络、不处理真实文件。延时与超时都是假设输入，不是已测的精确总耗时。

import subprocess
import sys

def stop_and_collect(child):
    child.kill()
    return child.communicate()

child = subprocess.Popen(
    [sys.executable, "-u", "-c",
     "import time; print('started', flush=True); time.sleep(60)"],
    stdout=subprocess.PIPE,
    stderr=subprocess.PIPE,
    text=True,
)
timed_out = False
try:
    try:
        output, errors = child.communicate(timeout=1)
    except subprocess.TimeoutExpired:
        timed_out = True
        output, errors = stop_and_collect(child)
    print({"timed_out": timed_out, "returncode": child.returncode,
           "stdout": output, "stderr": errors})
finally:
    if child.poll() is None:
        stop_and_collect(child)

超时分支先对持有的直接子进程调用 kill，再继续 communicate，完成管道处理并取得 returncode。finally 为意外离开正常路径时仍活跃的直接子进程提供清理尝试。它不是跨平台进程树终止器，也没有把清理本身包装成严格的一秒总上限。真实资源若无法及时退出，应另有可观察的恢复政策。

按官方说明，捕获超时后继续通信不会丢掉已经读取的输出。因此示例直接使用后一次 communicate 的完整结果，不把异常里可能已有的片段再机械拼一次，避免重复。文档也提醒，不应在超时后的后续 communicate 再提供 input；本例子从一开始没有交互输入，不展示不确定的重送行为。

记录里的 timed_out 与 returncode 回答不同问题。前者保留父进程曾经超时，后者表示最终观察到的退出状态；后一次成功收集管道并不会让转换任务从超时变成业务成功。应用也应区分成功产物、诊断文字和部分输出，不能发现 stdout 非空就把它当成完整结果。

为什么不能只在超时后 wait？

当前文档要求在 communicate 超时后继续用 communicate 完成管道与返回码处理，而不是仅调用 wait。等待进程终止与处理 stdout、stderr 是不同责任；一般情况下，若子进程写满管道、父进程却只等退出，还可能形成彼此等待。清理设计需要把进程和所有通信端一起考虑。

但 communicate 会把读取内容缓存在内存，不能因此用于任意巨大或无限输出。若转换器可能持续产生日志，应选择适当的文件或流式消费，并限制输出与存储预算。这个改变会增加取消、错误和资源回收的设计，不能在示例外面套一个线程就宣称实现了固定内存。上面的固定小文本只是为了隔离超时收尾机制。

对于只关心一个返回码、不需要捕获输出的任务，也应按接口前提选择标准流去向，而不是无论何时都创建 PIPE。每多一个管道，就多一个需要关闭和消费的通信对象。把不需要的输出丢弃、保存到受控日志文件或流式读取，分别意味着不同的可观察性与保留合同。

kill 之后，所有后代都会结束吗？

不能从这个示例推导。Popen 对象描述启动的那个进程；它是否又创建子进程、后代是否继承管道、如何跨平台管理整个进程组，都需要额外设计。直接子进程已退出，仍不一定表示继承端点全部关闭，后续通信的结束条件也可能受影响。本文不提供复制到所有系统都成立的进程组清理命令。

同样，终止进程不会撤销它此前写入的文件或远程请求。若业务重试可能重复提交，应先确认产物与任务身份，决定恢复、重建还是拒绝重放。必要文件交付应在独立的完整性检查与移交步骤完成，不能靠杀死转换器清理全部外部状态。

run 的 timeout 也不是进程创建阶段可被精确中断的保证。官方说明，某些平台的初始进程创建无法被中断，因此异常可能要等创建动作结束后才出现。提出硬总预算时，应同时审查启动、运行、终止与输出收尾，而不是只改一个 timeout 数字。

拟议验证用独立父进程记录启动身份、超时分支、最终 returncode、完整标准流和资源状态。分别准备正常退出、非零退出、受控超时和管道输出压力，再把需要的后代场景作为单独测试。每组预期应先写清楚，不能把一段“已超时”日志当作退出回执。

对子程序启动状态的预期也应谨慎。父进程成功创建 Popen 对象，不保证子程序已经打印 started；调度和启动过程仍可能占用时间。若要单独验证“进入工作后超时”，应增加可控的就绪交接，再启动相应观察，而不是要求每次都先看到那行文本。反过来，缺少标记也不能单凭它认定进程从未启动。保留启动身份、就绪事件与最终退出，才能把启动慢和运行超时分开。

本站asyncio 的取消结算讨论协程的另一种等待合同；本篇不把协作取消与操作系统子进程控制混用。所有示例尚未执行。调用者应能说明等待何时结束、直接子进程何时退出、管道何时收齐，以及外部产物由谁验收，再决定这次超时是否已经处理完。
