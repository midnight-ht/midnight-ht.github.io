改了export-ignore，为什么release归档仍带着那个目录？

用同一release树比较默认属性和工作区属性，核对本地覆盖、额外文件与最终清单，避免把导出选择误作历史删除或敏感内容证明。

正文

核心要点

  • 默认属性来自被归档的树，本地改动不会自动改写旧树的导出规则。
  • 显式采用工作区属性时，提交身份之外还要保存属性输入。
  • 排除一个目录不证明整包安全，也不撤销已经传播的内容。

工作区已经给 tests 目录加了 export-ignore，按旧 release 提交生成的归档却仍可能带着它。git archive 默认使用被归档树里的属性，而不是你刚改的工作区规则。先固定归档提交与属性来源，再查看真正导出的文件清单，才能解释本地修改为什么没有改变交付包。

归档树与工作区是两份输入

git-archive 官方手册说明，带 export-ignore 属性的路径不会加入归档，属性默认从被归档树的 .gitattributes 读取。需要采用工作区属性时，可以显式使用 --worktree-attributes；仓库的 info/attributes 还可以提供额外属性来源。本文于二〇二六年十月三十日核对手册，页面标示该手册最后更新于二点五十四版本，没有执行打包。

因此“我本地已经改了规则”和“目标提交的规则已经改了”是两个事实。选择 release-base 作为 tree-ish，归档围绕那个树生成，不会因为当前目录里恰好有一份新属性文件，就自动把新规则应用到旧提交。相反，显式采用工作区属性又引入额外输入，交付记录若只写提交哈希，也可能不足以复现文件选择。

这里讨论的是导出快照，不是修改仓库。export-ignore 不会从提交历史删除文件，更不撤销已经传播的秘密。若敏感文件过去已经提交，归档里看不到它不能完成泄露处置。这个边界也意味着它不等同于 .gitignore：路径已经被跟踪，仍可能按归档属性被排除；版本跟踪和导出选择分别判断。

同一个提交，比较两种属性来源

设想 release-base 已提交 src/app.js 和 tests/check.js，提交内没有排除 tests 的属性。工作区后来增加一行 tests/ export-ignore，尚未提交。以下命令只描述隔离练习，不在本仓库执行；release-base 必须在样例仓库中事先存在。

# Same tree-ish, default attributes from the archived tree.
git archive --format=tar --output=default.tar release-base
# Same tree-ish, explicitly use working-tree attributes.
git archive --worktree-attributes --format=tar --output=worktree.tar release-base
# Read archive member lists without extracting into an application directory.
tar -tf default.tar
tar -tf worktree.tar

在没有其他属性覆盖或额外文件选项的假设下，默认包仍按 release-base 的属性导出；第二份才会采用这次工作区排除。预期差异是 tests 是否进入清单，不是源码提交内容被改了。这是根据手册的纸面推演，不能冒充实际 tar 输出，也没有承诺所有归档格式的字节摘要相同。

如果两份清单出乎意料地相同，应先核对 tree-ish、实际属性文件、路径匹配和 info/attributes，而不是立即认为选项失效。若目录名或工作目录改变，匹配条件也要重新检查。命令成功只证明生成了某份归档，不能说明被选文件符合交付约定。

额外加入文件是另一条路径。手册提供向归档添加非跟踪文件的选项，发布脚本还可能在归档后加入配置或重新压缩。最终包已经不是只由那一个提交描述的原始输出。应记录这些步骤和输入，不把“来源是 Git”当成所有内容都来自已审查提交的保证。

应该提交规则，还是使用临时覆盖？

长期发行策略适合随源码提交属性，让审查者能够看到哪些路径被排除，并让后续发布沿相同规则解释。代价是属性调整本身也要进入正常版本管理，旧提交的默认导出不会因为后来改了规则就追溯变化。若对历史版本重新打包，应明确选的是原有发行规则还是后来修订的交付政策。

临时或不同渠道的导出可以评估工作区覆盖，但要保存属性内容、运行环境和实际清单。否则同一提交在两台机器上可能因不同的本地规则得到不同交付范围。info/attributes 属于更容易被忽略的仓库本地输入，也应进入复现检查；不能只审查项目根目录那份文件。

两种方案都需要验收使用者实际需要什么。测试目录可以不进入某个运行包，却可能对源代码发行、许可审查或接收方构建有价值。排除内容不是包越小越好，应让交付目的决定允许清单。缺少必要模板、证书材料或构建脚本，会让一个格式正确的归档无法完成接收方任务。

排除了测试目录，就能证明发行包没有敏感内容吗？

不能。排除某个路径仅说明相应导出规则被采用，没有对所有剩余内容作机密分类。普通源码、生成配置、额外加入文件和重新打包步骤仍可能带入不该交付的信息。可在无敏感值的样例中设置代表性标记，核对禁止路径和必要路径，再对最终交付包做独立内容审查。

测试也要检查“不该少”的文件。只有禁止项不见了，仍可能因过宽模式把正常源码排除。为每项明确它来自哪个树、是否被属性排除、是否在后续加入，能把清单差异转成可解释的决定。不要用一个 zip 文件存在或哈希已生成，替代这些语义检查。

拟议验证固定提交和归档格式，先比较默认属性与工作区属性，再改变一个排除项，观察对应路径的变化；单独覆盖额外加入文件与本地属性来源。所有命令都待执行，没有发布回执。关于历史传输可对照bundle 的前置对象，但 bundle 恢复历史和 archive 导出文件树是不同交付目标。把提交、属性来源与最终清单一起保存，才知道接收方拿到的究竟是哪一份内容选择。

属性诊断还要避免问错来源。默认在工作区检查某条路径的属性，得到的可能正是刚修改的规则，不能由此证明旧树归档一定采用它。应把诊断工具的来源选项与归档的来源对齐，或直接检查目标树内的属性文件，再用真实归档成员清单验证。属性查询和归档结果是两项相邻证据，不是同一个动作。

如果交付记录附带提交身份，也应说明导出的是该树经过哪些排除后的子集。身份关联方便追溯，不代表接收方得到了全部历史或每个已跟踪文件。工作区里正在编辑的内容、暂存但尚未提交的修改，又不是固定release引用的同一份树；比较前先说明选中的对象，才能让差异可解释。
