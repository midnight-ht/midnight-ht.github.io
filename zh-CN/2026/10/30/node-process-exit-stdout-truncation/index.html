Node.js 打印完就 exit，管道里的 JSON 为什么少了一截？

区分 Node.js 强制退出与退出码，用受控 CLI 说明 stdout 在不同目标下的交付、活跃资源和 exit 监听器限制。

正文

核心要点

  • 强制退出可能截断尚未完成的标准输出。
  • 设置退出码不会替应用关闭所有活跃资源。
  • 退出状态、输出字节与业务交付需要分别验收。

Node.js 程序把 JSON 交给 stdout 后立刻调用 process.exit()，接收端仍可能拿到不完整内容。stdout 写入在某些平台和目标上是异步的，而 exit 会强制结束进程。设置失败退出码与立即终止不是同一个动作；CLI 应分别验收退出状态和完整输出。

终端看见内容，不代表管道也收齐

Node.js Process 文档明确列出调用 exit 可能截断 stdout 的反例：写入有时跨多个事件循环轮次完成，强制退出会阻止后续写入。本文于二〇二六年十月三十日核对 v24.22.2 分支说明，没有运行 CLI、管道或跨平台输出测试。

设想命令行工具生成一份较大的 JSON，测试者直接在终端看到开头和末尾都在，就认为输出已经交付。流水线通过管道接收时却解析失败。终端、文件和管道的写入行为可能不同，操作系统也参与决定同步或异步。不能把 stdout 永远说成异步，也不能用终端中的一次成功否定文档描述的截断风险。

这与测试框架有没有保持进程存活是不同问题。即使还有待完成的写入，显式 exit 也会要求进程结束；它不是在询问所有工作是否已经完成。成功或失败退出码只表达进程状态，不包含接收端拿到多少字节、更不包含另一端业务是否已处理内容。

把输出和退出状态安排成两条责任

下面是完整但未执行的示例程序，用假设的诊断数据构造输出。固定非零退出码仅表示示例选择以失败状态结束，不代表这些数据来自真实检查。它不主动 exit，让业务入口走到文件末尾；真实工具还须关闭自己持有的资源。

import process from 'node:process';

const result = {
  status: 'example_failure',
  items: Array.from({ length: 10000 }, (_, id) => ({ id, note: 'example' })),
};

process.stdout.on('error', () => {
  process.exitCode = 1;
  process.stderr.write('stdout write failed\n');
});

process.stdout.write(JSON.stringify(result) + '\n');
process.exitCode = 1;

作为反例，可在同样的隔离程序中把最后一行改为 process.exit(1)。父进程分别捕获完整字节、退出状态和错误流，比较能否解析 JSON、项目数量是否符合假设输入，以及内容摘要是否匹配预先生成的预期。本文不声称这两个程序已经运行，也不保证任意输出大小都能稳定触发截断。

示例只做一次较大写入，不是通用大数据导出方案。若结果可能无界增长，应另行采用适当的分段输出和资源预算，并遵守流的背压。不能为了避免退出截断，就把所有数据永久积在内存中。本站可写流的背压讨论生产速度与消费速度的关系；本题增加的是强制结束进程可能提前切断交付。

错误监听也不应被当成“输出已经正确”的证明。它只让这个简例对写失败保留非零状态和诊断；接收端仍须检查实际内容。真实协议若要求一个结构化结果，不应把调试日志混入 stdout 破坏 JSON，应按合同将诊断放到适当通道。两条通道都需要处理自己的失败，而不是互相覆盖。

只改 exitCode，为什么程序可能不退出？

exitCode 选择自然结束时采用的状态，不负责关闭服务器、连接或引用中的计时器。如果业务入口继续调度工作，程序当然还可能存活。修复方向是让入口结束后不再启动新任务，并按所有权关闭需要关闭的资源，而不是用显式 exit 隐藏没有收尾的句柄。

例如 CLI 初始化了一个监听端口，却在诊断结束后忘记关闭。把 exit 换成 exitCode 会暴露原本被强制终止掩盖的问题；这不是说明新写法错误。应让拥有服务器的模块提供可等待的关闭结果，给必要清理一个合理预算，并说明预算耗尽如何报告。本文不提供适用于所有库的统一停机控制器。

也不要把所有计时器 unref 就宣称清理完成。unref 改变活动是否维持进程，而不是等待任务交付；本站计时器的存活责任说明了这种区别。对于允许放弃的统计和必须完成的结果输出，需要分别确认承诺，不能只以退出速度决定。

在 exit 事件里异步刷新能补救吗？

不能依赖它。官方文档要求 exit 事件监听器只执行同步操作，监听器结束后进程就会终止，排队的异步工作不会因此获得等待。把 flush 的 Promise、定时器或网络发送放进 exit 回调，不会把强制退出变成可等待的异步收尾。

清理应在仍可正常运行的生命周期里开始，并让调用方观察其完成或失败。beforeExit 又是另一个事件，不能因为它允许某些新工作，就推断显式 exit 会先经过同样过程。事件名字相似，触发条件不同；若产品依赖它们，实际脚本需要独立验证，而不是凭一个回调出现过就宣布所有退出路径可靠。

拟议测试由独立父进程驱动，避免借用测试框架的其他句柄。对每份相同输入分别通过管道、文件重定向和受控终端观察，记录 Node 版本、平台、字节数、JSON 解析、内容身份和退出状态。增加提前关闭接收端与写失败的路径，确认工具没有把部分 JSON 作为完整结果提交。

父进程的观察也有边界。它捕获全部 stdout，可以证明这次子进程与父进程之间取得了预期字节，不等于下游系统已持久保存，更不等于结果内容符合真实业务。若后续还要上传、入库或发送通知，应各有对应结果，不能从 CLI 结束状态一路推导。

父进程的断言还应预先写明，本例允许“完整诊断 JSON 加非零退出状态”。如果测试只接受退出零，便会把正确表达失败的完整输出也判成传输问题。内容预期最好来自固定样本与独立的协议检查，不能仅复制生产序列化逻辑再比较两个相同错误。分别报告协议解析失败、内容不符和退出状态不符，才能知道截断是否真是本轮差异，而不是检查器把两项合同混在一起。

本文没有运行输出或停机实验，不给出“多少字节必然截断”的阈值。审查时先找到显式退出的位置，确认它之前是否仍有必须完成的工作；再把退出码、字节交付和必要资源关闭分别放入验收，而不是用一个 process.exit 收掉所有未说明的责任。
