DOM事件已调用preventDefault，为什么defaultPrevented仍是false？

按cancelable与passive双条件解释取消标志，用未执行的EventTarget例子区分回调运行、取消成立与真实滚动结果。

正文

核心要点

  • 取消标志需要事件可取消且当前监听器不是passive。
  • 收到事件、设置取消标志和默认动作结果应分别观察。
  • 合成事件的标志检查不能代替目标设备真实输入验收。

处理器确实运行，也调用了preventDefault，事件却没有变成已取消。先检查cancelable和当前监听器是否passive，再讨论后续默认行为。回调出现、取消标志成立和页面没有滚动，是三个需要分别观察的结果。

设想一个可横向浏览的卡片区域。开发者在滚轮回调里写了取消调用，日志也能看到，页面仍向下移动。此时若只加更多日志或换成stopPropagation，就容易在错误层次上修补：前者证明代码经过，后者控制传播，都没有直接回答这次调用是否允许设置取消标志。

DOM Living Standard的preventDefault算法给出了两个条件：事件的cancelable为真，并且当前不处于passive监听器中，才设置取消标志。因此，可取消是必要条件，却不足以保证这一个监听器能够取消。一个声明为被动的监听器，即使收到可取消事件，也不能通过这个调用建立取消结果。

先用一个小例子分开条件

下面是未执行的推演代码。它只比较DOM事件的标志，不模拟浏览器滚动，也没有证明任何手机上的交互行为。

const observer = new EventTarget();
const controller = new EventTarget();
function inspect(event) {
  event.preventDefault();
  console.log(event.cancelable, event.defaultPrevented);
}
observer.addEventListener('probe', inspect, { passive: true });
controller.addEventListener('probe', inspect, { passive: false });
observer.dispatchEvent(new Event('probe', { cancelable: true }));
controller.dispatchEvent(new Event('probe', { cancelable: true }));

按照规范条件，第一个新事件可以取消，但监听器处于passive状态，调用后取消标志不会由它设置；第二个新事件满足两项条件，可以建立取消标志。两个目标、两个新事件，让前一次处理不会把已取消状态带进后一次比较。若把事件构造时的cancelable改成false，后一个监听器也不能把它变成可取消事件。

这个例子有意没有使用同一个事件反复分发。实际诊断里，同一分发过程的其他监听器可能已经取消事件，你看到的defaultPrevented为真，并不能反推出当前监听器成功设置了它。最好记录进入处理器时和调用之后的值，并说明当前注册选项，而不是只截取最后一行日志。

真实问题还要找对监听器

回到卡片区域，首先确认回调接到的确实是发生问题的那次事件。页面上可能同时有外层容器、内部组件和文档级监听；某个观察回调运行，不意味着负责交互的那个监听器绑定正确。记录事件类型、目标、当前处理目标与组件实例，才能把日志接回用户那一次动作。

其次查看实际注册位置的选项。不要只搜索函数定义：组件封装可能替你注册监听，重新挂载也可能走另一条分支。代码里另一个同名函数使用passive:false，不能证明当前这条监听也是如此。浏览器对特定目标和事件类型的默认处理还需要结合实际环境核对，不能把没有写选项一概解释为同一种承诺。

当需求只是统计或观察输入时，监听器不需要取消默认行为，保留被动观察就能表达意图。当一个明确的受控交互确实需要取消时，应在对应监听器上说明这一要求，再检查事件是否可取消。把所有监听器统一改成非被动，会把局部需求扩散为全局策略；本文也没有测量这种改变的性能收益或代价。

接着观察默认动作本身。cancelable为真描述的是事件能力，defaultPrevented描述的是取消标志，区域是否滚动描述的是用户可见结果。目标滚动容器选错、交互规则没有覆盖某个输入方向，或实际收到另一类输入，都可能让第三项与预期不同。验收记录应写清鼠标滚轮、触控板或触屏，以及发生动作的容器。

别让传播控制替代取消判断

stopPropagation设置传播方面的状态，不能替passive监听器绕开取消条件。它可能改变其他监听器是否收到事件，从而让现象变得更复杂，却没有把这一个取消调用变得有效。旧的按钮默认提交讨论也提醒过传播与默认动作要分开；这里进一步需要检查监听器所处的被动状态。

同样，不应为了让测试看起来通过而手动修改日志值，或用一个自行构造的事件替换真实交互。若组件卸载后又注册了一次，问题可能是监听器生命周期；若另一个监听器先取消，问题可能是归因错误。这些失败路径需要保留事件身份与前后状态，不能用一次总分式的“事件正常”覆盖。

一个可复核的检查顺序是：确认用户动作与事件对应，找到实际注册，记录cancelable，比较处理前后的defaultPrevented，最后观察相应默认行为。每一步都回答一个更窄的问题；其中任何一步失败，都能说明下一步该看什么，而不是继续盲目添加取消调用。

dispatchEvent成功，手机就不会滚动了吗？

如果监听注册由第三方封装负责，应用层未必能直接改变选项。应先确认封装公开的能力、当前实例的注册方式和清理时机，再决定局部替换或交互调整。不要同时叠加第二个监听器碰碰运气；两处回调相互影响以后，取消结果更难归因，组件退出时也更容易留下旧处理器。

还不能这样推断。上面的合成事件例子能够验证处理器对取消标志的逻辑，但没有生成用户的触摸输入，也没有重现浏览器为该输入安排的默认动作。即使它得到已取消结果，仍需要在目标设备和真实输入路径上检查滚动区域、监听选项与可见行为。

反过来，某次页面没有移动，也不一定证明取消有效：内容可能本来没有可滚动空间，或者动作落在另一个区域。验收应同时保留标志证据和具有实际滚动条件的操作结果。这里提供的是诊断机制和未执行的例子，不是已经完成的浏览器或设备测试记录。
