Playwright截图禁用动画，为什么transitionend仍会触发？

以完整但未运行的Playwright spec说明有限动画结束事件、无限动画恢复与截图状态，检查活动过渡前提，并保留认可基准和业务完成的证据边界。

正文

核心要点

  • 有限动画快速完成可能触发结束事件和相关页面逻辑。
  • 无限动画取消到初始状态，截图之后再恢复播放。
  • 稳定截图不提供后台任务完成的额外证据。

截图断言把animations设为disabled，并不意味着页面停在调用那一瞬间。Playwright会让有限动画快速到达结束位置，过渡结束事件也可能因此触发；无限动画则按另一套规则处理。截图前后的页面状态，需要把这些动作算进去。

设想一个报告面板，展开时有一段过渡。代码在transitionend回调里把“展开中”改为“已展开”，同时显示下一项操作。测试先触发展开，再调用截图断言，希望得到过渡中间的页面。作者以为禁用动画只是去掉视觉抖动，却发现截图里的操作已经出现，于是把它归因于请求太快。

Playwright的toHaveScreenshot动画选项文档给出了更直接的解释：disabled会将有限动画快速推进到完成，以触发transitionend等结果；无限动画会被取消到初始状态，截图之后再恢复播放。选项覆盖CSS动画、CSS过渡和Web Animations，并非只改某一个CSS属性。

一段纸面例子暴露状态依赖

下面是一份完整但未执行的report-panel.spec.js示例，使用@playwright/test的page夹具，在页面内定义按钮、面板、CSS与结束处理器，再从测试侧操作它。按钮放在面板外，避免点击目标本身随过渡变化；页面不发请求，因此这里没有后台完成状态可以被截图“证明”。

import { test, expect } from '@playwright/test';

test('capture the expanded report panel', async ({ page }) => {
  await page.setContent(`
    <!doctype html>
    <html lang="en">
      <head>
        <meta charset="utf-8">
        <style>
          body { margin: 24px; font-family: sans-serif; }
          #open { margin-bottom: 16px; }
          #panel {
            box-sizing: border-box;
            width: 320px;
            padding: 16px;
            border: 1px solid #333;
            opacity: 0.2;
            transition: opacity 30s linear;
          }
          #panel.is-open { opacity: 1; }
        </style>
      </head>
      <body>
        <button id="open" type="button">Open report</button>
        <section id="panel" data-testid="panel" data-phase="closed">
          <h1>Report preview</h1>
          <p>No remote request is part of this example.</p>
        </section>
        <script>
          const panel = document.querySelector('#panel');
          const button = document.querySelector('#open');
          panel.addEventListener('transitionend', (event) => {
            if (event.target === panel && event.propertyName === 'opacity') {
              panel.dataset.phase = 'expanded';
            }
          });
          button.addEventListener('click', () => {
            void panel.offsetWidth;
            panel.dataset.phase = 'opening';
            panel.classList.add('is-open');
          });
        </script>
      </body>
    </html>
  `);

  const panel = page.getByTestId('panel');
  await page.getByRole('button', { name: 'Open report' }).click();
  await expect(panel).toHaveAttribute('data-phase', 'opening');

  const hasActiveFiniteTransition = await panel.evaluate((element) =>
    element.getAnimations().some((animation) =>
      animation.playState === 'running' &&
      animation.effect !== null &&
      Number.isFinite(animation.effect.getComputedTiming().endTime)
    )
  );
  expect(hasActiveFiniteTransition, 'active finite transition before capture')
    .toBe(true);

  await expect(panel).toHaveScreenshot('report-panel-expanded.png', {
    animations: 'disabled'
  });
  await expect(panel).toHaveAttribute('data-phase', 'expanded');
});

页面脚本只在事件目标是面板本身、结束属性是opacity时标记expanded，避免子元素的结束事件误改状态。测试先单独检查opening，再检查元素上是否存在正在运行且结束时间有限的动画，随后调用具名截图断言，最后检查expanded。前置条件失败时，应先调查过渡是否开始或已经自然结束，不能跳过它后仍把结果归因于截图策略。

这里的三十秒只是让有限过渡更容易被观察的示例时长，不是生产建议，也不保证任意调度环境中调用截图时仍在过渡。前置检查与截图之间仍有时间经过；这份例子展示待验证的路径，不宣称单凭一次后置状态就隔离证明因果。

运行截图断言还需要对应环境下已审阅认可的基准图。本文没有运行测试、生成PNG或记录基准批准；不能自动生成一个新基准，再把它当成独立认可的正确结果。完成代码结构不等于已经获得测试通过证据。

如果面板的有限过渡在截图准备时被推进到结束，结束处理器就可能执行。此时出现expanded可以是截图策略参与了状态变化，而不是后台任务完成的证据。反过来，如果回调没有执行，也要检查相关过渡是否仍活动，不能只看到选项名称便断言每一个处理器必然运行。

有限与无限不能合并解释

有限动画有一个结束位置，快速完成可以把页面推进到相应视觉终点，也可能触发依赖结束的逻辑。无限旋转的加载图标没有同样的自然终点，文档说明的是取消到初始状态，并在截图后重新播放。因此，截图中旋转图标静止，不代表它绑定的工作已经完成。

这个差异会影响断言解释。一个报告下载的加载图标在截图里看起来不动，可能只是捕获策略对无限动画的处理；网络请求、文件生成或权限判断仍可能处于原状态。如果测试把“没有旋转”解释为“报告已生成”，就把视觉处理误写成业务完成条件。

面板展开与报告生成也可能同时发生。展开过渡完成，可以合理使面板进入展开状态；它不能替另一个异步请求宣布结果。产品状态应由对应任务的真实结果驱动。截图可以检查已知状态如何呈现，但不应单凭动画被处理后的外观确认后台完成。

为截图指定想要的状态

测试作者应先写下截图要证明什么。如果目的是“报告加载完成后的面板”，先等待应用提供的明确完成状态，再截图；完成状态本身还需有针对结果的断言。如果目的是“展开后的布局”，确认展开状态，再让截图策略处理剩余运动。如果要检查动画过程，则需要另设适合该目标的观察方法，不能期待默认禁用策略保留中间帧。

不要把延长固定等待当成这一判断的替代。等待久一点可能让例子偶然落在结束以后，却没有解释为什么截图准备还会触发事件。也不要为让截图稳定而删除真实的结束处理器：先判断它承载的是呈现生命周期，还是误放的业务状态，然后分别验证行为与视觉。

实际检查可以记录项目使用的Playwright版本、断言调用前的状态、相关动画是否有限、事件处理器做了什么，以及断言后的状态。当前文档没有在这一条目为所有项目指定一个固定版本，本文也没有读取读者的依赖文件；记录自己项目版本才能解释不同环境中的表现。

一个失败路径需要独立保留

假设面板的transitionend事件从子元素冒泡，处理器又没有筛选目标，页面可能提前标记展开。这是处理器作用域的问题，与截图是否禁用动画可以同时存在。先用事件目标与属性信息查清触发条件，再检查截图策略怎样影响这一条件，避免把所有变化都归给工具。

另一个失败路径是测试之后页面继续执行：无限动画恢复播放，依赖持续观察的后续步骤仍会看到运动。若一个测试共享页面状态，不能拿前一张静止截图保证下一步也处于冻结环境。截图断言的动作范围与后续业务观察应分别记录。

本文没有执行这些测试，也没有给出稳定率提升或像素差异统计。上面的检查设计用于解释原因并建立可验证的条件，实际项目仍需用真实页面、相关浏览器和已记录版本运行。

截图稳定了，就能删掉完成状态断言吗？

不能仅凭稳定外观作这个决定。有限动画被完成、无限动画暂回初始位置，都可能使图像更容易比较，却没有增加后台结果证据。保留任务完成的行为断言，再用截图检查这个状态的呈现，才能知道失败发生在结果、状态映射还是像素表现。

这也给测试维护一个明确边界：修改动画时，复核截图准备是否触发生命周期；修改请求与业务结果时，复核完成状态。两类检查可以合作，但应各自保留可说明的证据。
