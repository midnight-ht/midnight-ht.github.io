SQLite 脚本报错后回滚，前一笔 Python 写入为什么还在？

限定 sqlite3 的遗留事务控制模式，拆解 executescript 入口提交、脚本内事务与外层回滚范围，用独立数据库示例安排验证。

正文

核心要点

  • 遗留模式下，脚本入口可能先提交已有事务。
  • 脚本内 BEGIN 无法撤销此前已经完成的提交。
  • 事务模式、未提交状态与连接交接需要实际核对。

在 Python sqlite3 的 LEGACY_TRANSACTION_CONTROL 模式下，executescript() 遇到已有未提交事务，会先隐式提交它，再执行脚本。脚本随后失败，回滚也不能撤销入口处已经提交的那部分。排查“回滚后为什么还留着数据”，应先标出连接模式和每个提交时点，而不是只数源码里出现了几个 with。

脚本入口也可能是提交边界

Python 3.14 sqlite3 参考明确限定：autocommit 为 LEGACY_TRANSACTION_CONTROL 且存在待提交事务时，执行脚本前先 COMMIT；脚本内部没有其他自动事务控制，需要的事务语句应写进脚本。本文于二〇二六年十月三十日核对的页面标为 Python 3.14.10，不把遗留模式的规则直接套到所有 autocommit 设置。

设想迁移函数先写入一条操作记录，再用 executescript 创建或填充其他内容。调用者以为后面任何一步报错都会让前面的操作记录消失；实际上，脚本入口可能已把它提交。脚本里即使再有 BEGIN，也只能开启后续事务，无法把此前提交的写入重新放回去。这是接口时序，不是 SQLite 随机漏掉回滚。

从三点十二版起，Python 提供 autocommit 属性作为事务控制入口。旧 isolation_level 与新属性共同出现时，必须先说明当前处于哪种模式。仅看到 isolation_level 的字符串，或者看到 SQLite 支持事务，不能推断整段 Python 操作属于同一个原子单元。版本和实际连接配置应进入诊断记录。

把脚本前与脚本内的两行分开观察

下面是未执行的完整教学程序，要求支持 autocommit 参数的 Python。它使用独立临时数据库，不连接真实业务库。失败由缺失表故意触发；输出的意义应按实际运行记录核对，本文没有提供任何实测输出。

import sqlite3
from pathlib import Path
from tempfile import TemporaryDirectory

with TemporaryDirectory() as directory:
    path = Path(directory) / "example.db"
    con = sqlite3.connect(
        path, autocommit=sqlite3.LEGACY_TRANSACTION_CONTROL
    )
    try:
        con.execute("CREATE TABLE events(id INTEGER PRIMARY KEY)")
        con.commit()
        con.executemany("INSERT INTO events VALUES (?)", [(1,)])
        print("before script", con.in_transaction)
        try:
            con.executescript("""
                BEGIN;
                INSERT INTO events VALUES (2);
                INSERT INTO missing_table VALUES (3);
                COMMIT;
            """)
        except sqlite3.Error:
            con.rollback()
        print("after rollback", con.in_transaction)
        print(list(con.execute("SELECT id FROM events ORDER BY id")))
    finally:
        con.close()

按文档推演，脚本前的一号行在入口隐式提交，二号行位于脚本显式开启的事务内，后者失败后由 rollback 撤销。重点是两行分属不同事务，而不是给出一条“所有错误后都保留第一行”的通用口诀。若把初始化、连接模式或脚本内容改了，就应重新确定预期。

in_transaction 能帮助观察底层当前是否有未提交事务，但一个时点的布尔值不会告诉你过去提交过哪些业务动作。需要把阶段标记和具体行身份关联起来。如果要证明其他连接已经看见一号行，可另开观察连接，在明确的提交时点读取；不要让观察器自己持有长读事务后，再误解它的可见性。

谁应该拥有这次原子操作？

若所有写入必须共同成功，较简单的方向是选定一种事务管理方式，让所有相关语句落入同一个受控范围。固定语句和数据值可以使用 execute 或 executemany 配合参数绑定，不必为“多行 Python 代码”自动换成 executescript。数据值与任意 SQL 脚本文本也不应互相替代。

若确实需要迁移脚本，可以让脚本明确拥有 BEGIN、COMMIT 和失败恢复，并确保必须一起提交的前置写入也在这个合同中。不要先在调用方留下待提交工作，再假定脚本会悄悄加入它。脚本运行前是否允许已有事务，可以成为受控前置条件；发现状态不符时报告配置错误，而不是擅自提交调用者并不想提交的内容。

脚本中放 BEGIN 并不意味着遇错会自动恢复到干净状态。调用者仍须处理异常、确认当前事务、回滚相关未完成工作，再决定连接能否继续借给下一个任务。连接关闭与事务成功也不是一回事，必须明确自己在保存什么、放弃什么。上面的 finally 关闭只是资源清理，不是成功提交的替代。

外层 with connection 为什么保不住之前的写入？

连接上下文在退出时处理相关的未完成事务，不能倒转已经完成的 COMMIT。如果在 with 内调用 executescript 并触发入口提交，随后异常导致的回滚仍只能作用于当时尚未提交的部分。因此问题不是“with 没有用”，而是它的保护范围被中间的提交改变了。

反过来，也不能为解决这个问题机械嵌套更多 BEGIN。当前连接是否已有事务、autocommit 由谁控制、脚本是否含事务语句，都可能使嵌套尝试不成立。应先画出一条时间线，再删掉互相争抢控制权的层次；不要靠捕获“已经在事务中”异常后继续执行来维持表面成功。

legacy 模式说明还提醒，executescript 的入口提交不由 isolation_level 的取值直接取消。把它改成 None，并不能在存在明确开启事务的情况下自动获得想象中的回滚范围。这个结论仍限定遗留控制；使用其他 autocommit 模式时，应按对应章节独立设计并验证，不通过修改一个选项宣称所有模式等价。

拟议验证覆盖没有前置事务、有前置写入、脚本成功、脚本中途失败和脚本自身不含事务控制。每轮使用新库或恢复相同初始状态，记录 Python 与 SQLite 版本、连接配置、每阶段 in_transaction、观察连接读取和最终行集。失败之后停止本轮业务推进，避免后续自动提交的查询或写入掩盖真正边界。

连接被复用时，还要确认脚本实际拿到的就是已检查模式的那条连接。初始化函数里的默认设置、适配器后来改写的属性和任务执行时的状态可能不同。可以在受控入口记录不含业务数据的模式与事务阶段，并在借出连接前拒绝未结束的上一任务状态。测试每次新建连接只能证明那条新连接，不能替连接池交接验收。失败路径也应核对没有把待提交工作带给下一位调用者。

本站SQLite 等锁与事务重试讨论失败后的另一种责任。本篇没有运行迁移、回滚或驱动测试，也不证明某份生产脚本具有原子性。验收应能说清每条必须共同成败的写入在哪次提交里，而不是仅用“外面包了事务”作为完成结论。
