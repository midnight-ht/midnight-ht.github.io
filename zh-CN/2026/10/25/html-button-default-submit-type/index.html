点“预览”却提交了表单，先查按钮的 type

按当前 HTML Auto 条件、表单归属和实际渲染类型，区分预览、提交、重置及键盘路径。

正文

核心要点

  • 缺失类型为 Auto，是否提交需按当前标准条件判断。
  • 局部动作与真正提交入口显式声明类型。
  • 核对组件最终DOM、表单归属、请求及持久状态。

点“预览”却提交了表单，先检查实际渲染的按钮类型和表单归属。普通表单中的按钮若没有明确声明局部动作类型，可能成为提交按钮；它的点击处理函数不会因为写了打开弹窗，就自动取消浏览器的提交行为。应把提交、重置和页面内操作分别声明，再验证真实激活路径。

当前标准里的缺省类型是什么？

HTML Living Standard 的 button 定义在当前版本中把缺失与无效类型的默认状态列为 Auto。当类型为 Auto、没有 command 和 commandfor 属性、且父节点不是 select 时，它属于提交按钮；显式 submit 也属于提交按钮。因此，对常见表单按钮说“漏写类型会提交”有实际警示意义，但把所有按钮一概描述为无条件默认 submit，会遗漏当前规范的条件。

显式 button 类型没有内建的提交或重置动作，适合预览、展开帮助、切换显示等局部交互。submit 用于提交表单，reset 用于重置表单。文字写“取消”不会赋予按钮取消语义，图标画成眼睛也不会使它自动成为预览。浏览器看的是元素状态、属性和表单关联，不会从文案推断产品意图。

按钮是否在视觉边框里面，也不能替代表单归属判断。组件可能通过 form 属性关联到指定表单；开发者需要检查真实 DOM 与属性。一个工具栏在表单外观之外，仍可能连接到那个表单。反过来，没有相应表单归属时，也不能仅凭按钮缺少类型就断言一定发生某次网络提交。

怎样修复“预览申请”引发的提交？

设想申请页有联系人输入框、“预览申请”和“确认送审”两个按钮。预览处理函数负责打开只读弹窗，送审负责提交当前申请。下面是未执行的示例流程。若两个按钮都漏写类型，用户点击预览后可能先看到弹窗，再触发表单校验或提交，造成“还没确认就送出”的感觉。

先给预览声明 type="button"，给送审声明 type="submit"，再把表单提交逻辑放在明确的提交处理路径。输入一份有效申请，激活预览，预期只打开弹窗，不发出送审请求，不改变服务端状态；关闭弹窗后输入仍在。随后激活送审，预期才进入校验、请求与结果反馈，并能在重新打开申请时核对同一状态。这条完整路径同时检查局部动作与业务承诺，而不是只确认弹窗出现。

再故意留空必填联系人后点击预览。如果产品允许预览未完成草稿，预览不应因为意外进入提交路径而被浏览器必填校验拦住；确认送审则应按契约拒绝缺失信息。这里的预览规则是假设产品要求，需要团队确认，不能把所有预览都必须绕过业务校验当作 HTML 要求。

失败反例是只在预览事件里调用一个业务函数，然后认为函数结束就结束点击。默认行为是另一个需要明确处理的环节。另一个反例是修了页面里的原生按钮，却没有修设计系统组件：组件忽略传入的 type，最终 DOM 仍是缺省状态。代码审查应看输出元素，不只看调用端传了什么属性。

拦住 click 能替代类型声明吗？

取消默认行为能影响一次事件的默认动作，但用正确类型表达组件职责通常更容易维护。若只在某个处理器里取消，后续重构、条件分支或事件路径改变，都可能让原来的保护消失；类型则直接写在控件上。不能把停止事件传播与取消默认行为混为一谈，它们处理的是不同问题。

团队可以约定通用按钮组件要求显式选择职责，或采用适合本项目的明确默认值。选择默认 button 能降低局部操作意外提交的风险，却要求所有真正提交入口明确声明 submit；选择沿用浏览器行为，则必须审查表单中每个辅助操作。不存在一个组件默认值能代替所有页面验收，关键是输出行为符合调用者预期，且例外可见。

对于表单级提交处理，仍要覆盖键盘路径。用户可能通过键盘激活按钮，也可能在输入时触发表单的隐式提交行为；只给鼠标点击加逻辑，不能证明整个提交路径一致。应以表单的实际提交事件、请求和持久状态为证据，不要把按钮的点击次数当作申请数量。本文未在特定浏览器执行这些事件测试。

表单外的按钮还能提交吗？

可以存在这种关联，需检查 form 属性与对应标识。假设页面底部固定工具栏位于表单元素之外，送审按钮通过 form="application" 指向申请表单。它仍承担提交职责；若预览按钮复用了相同属性又未明确局部类型，外观上的分离不能提供保护。检查时应列出按钮所属表单、类型、禁用状态和提交相关覆盖属性。

重置按钮也应单独评审。reset 的用途是表单重置，不等于关闭弹窗或返回上页，也不承诺清除服务端已保存草稿。若界面写“取消”，产品想保留输入并关闭，却实现为重置，会发生另一种默认动作与业务意图错位。应先决定保存范围，再选择控件行为。

本站的按钮文案与状态承诺关注点击后对象进入什么业务状态，本篇补足浏览器为何进入提交路径。验收记录可以逐项对照预览、取消、保存和送审：鼠标及键盘激活后发生什么事件、是否请求、服务端是否变化、失败后输入是否保留。把类型修正和这些状态结果一起核对，才能证明预览仍是预览、送审确实由指定入口触发。
