SQLite WAL 回写不等于文件缩小：先查读事务，再选 checkpoint 模式

用双连接时间线区分回写、日志复用与物理截断，解释 PASSIVE 返回、长读事务和维护模式的边界。

正文

核心要点

  • PASSIVE 首列为零不证明全部日志已经回写。
  • 逻辑回写、可复用和物理截断需要分别验证。
  • 缩短读事务必须保留导出一致性与版本修复边界。

SQLite 执行过 checkpoint，不等于 WAL 文件已经缩小。先分清三件事：日志内容回写到哪里，旧读事务是否仍需要日志，以及本次模式是否要求截断文件。长读者可以限制回写和复用；即使全部回写，保留原有文件长度用于下次覆盖，也可能是正常行为。不能只凭一次返回或文件大小判断失败。

长读事务保留的是什么

SQLite 的 WAL 文档说明，读事务会固定开始读取时的提交边界，使它持续看到同一快照。后续写入可以追加日志，但 checkpoint 不能为追赶新写入而破坏旧读者所依赖的内容。因此，读写并发可用与日志能否及时回收，是不同约束。

这里的寿命是读事务的寿命，不是界面是否还显示加载。导出程序取完一批数据后等待网络上传，如果事务仍然打开，就可能继续占着快照。连接池归还对象、关闭游标和结束事务在具体绑定中是什么关系，应查实际接口；不能看到查询函数返回，就假定数据库事务已经结束。

本文的两连接流程仅用于解释机制，未运行。拟议并发验证应采用包含官方 WAL-reset 修复的运行库：官方页面列明三点五十一点三及以后版本，并提供三点四十四点六与三点五十点七的回补。供应商回补需另查证，不能只看系统命令版本代表应用嵌入版本。增长还可能有写入量、维护配置、锁竞争或版本问题，长读者不是未经观察即可宣布的唯一根因。

两个连接怎样复现这条责任链

在可删除的测试数据库中，连接乙先启用 WAL 并确认返回模式，暂时关闭自身自动 checkpoint，建立表并提交一条初始记录。这样做是为了让手动实验的时间线容易解释，不是生产配置建议。接着连接甲开始显式读事务，真正执行一次查询取得快照，并保持事务不结束。

-- Connection B: isolated setup, not executed.
PRAGMA journal_mode=WAL;
PRAGMA wal_autocheckpoint=0;
CREATE TABLE sample(id INTEGER PRIMARY KEY, value INTEGER);
INSERT INTO sample VALUES(1, 0);
-- Connection A: establish and keep the read transaction.
BEGIN;
SELECT value FROM sample WHERE id=1;
-- Connection B: commit a later version, then inspect progress.
UPDATE sample SET value=value+1 WHERE id=1;
UPDATE sample SET value=value+1 WHERE id=1;
PRAGMA main.wal_checkpoint(PASSIVE);

代码应分别送到标明的连接，不能整段粘在同一个会话。假设甲仍依赖旧 WAL 快照，乙已把较新版本提交到其边界之后，PASSIVE 可以推进允许的部分，却不能越过保护旧读者的边界。甲在同一事务再次查询，应仍看到原快照，而非乙的新值。实际日志页数取决于页面和既有状态，本文不给出伪造的固定返回行。

然后甲明确提交或回滚读事务，确认相关语句已释放，乙再尝试 checkpoint。若没有其他读写者和错误，原来的读者障碍消失；还要观察实际结果，不能仅根据甲点击“完成”就登记回收成功。需要验证物理截断时，可由乙在这个隔离窗口请求 PRAGMA main.wal_checkpoint(TRUNCATE)，并把返回与文件长度一起记录。

-- Connection A: explicitly release the read transaction.
COMMIT;
-- Connection B: compare progress after release, then request truncation.
PRAGMA main.wal_checkpoint(PASSIVE);
PRAGMA main.wal_checkpoint(TRUNCATE);

PASSIVE 的首列为零，证明什么

wal_checkpoint 的 PRAGMA 定义返回三个整数：首列对应是否遇到阻止指定操作完成的忙状态，后两列描述日志中的页数与已完成回写的页数。PASSIVE 不等待读写者，也不调用忙处理器；首列为零仍可能只做了部分工作，必须结合后两列判断。

后两列是该次结束时日志与已回写进度的描述，不应把第三列当作“这一次新增搬运量”，再把多次结果累加。两列相等支持当时逻辑回写已追上该日志范围，却没有承诺物理文件为零，也不保证下一次写入不会马上产生新日志。非 WAL 等场景可能出现负一，应先核对模式和错误，不能算成负积压。

同样，目录中一个较大的日志文件可能已经可供覆盖复用。把字节长度当作未回写工作量，会把正常预留误报为积压；只看页数差，又可能忽略磁盘容量压力。监控应分别保存逻辑进展、文件长度和采样时间，解释各自承担的判断。

FULL、RESTART 与 TRUNCATE 怎么选

checkpoint 接口文档区分了等待目标。FULL 等待写者结束以及读者达到最新快照，再完成回写；RESTART 在此之外等待读者不再使用 WAL，以便下一位写者从头复用；TRUNCATE 再增加成功完成前将日志截成零字节的要求。更强模式可能等待并影响写入，不适合因为文件大就无条件放进请求路径。

后台希望少干扰业务，可选择尽力推进的 PASSIVE，并监控读事务寿命和进度；维护窗口明确需要空间归还，才评估带等待预算的截断。忙处理器拒绝继续等待时，较强模式可能仅完成部分工作并报告忙，不能把发出 TRUNCATE 当成已经清零。另一个 checkpoint 占用检查点锁时，也可能直接失败，调长忙超时不能保证所有锁竞争都会等待。

不要直接删除活动数据库的 -wal 文件。尚未回写的已提交内容可能仍在其中，手工删文件绕过了 SQLite 的一致性管理。磁盘告警应触发识别持有者、限制新工作及受控维护，不能把删除日志当作“清缓存”。这一失败路径与模式选择是同一份运维责任。

提前结束导出读事务，会丢掉快照一致性吗？

可能改变语义。若导出要求整个结果来自同一时点，分批结束再开始事务会让后续批次看到新提交，简单缩短事务可能产生前后不一致的文件。可评估更快消费同一快照、先生成受控中间结果，或按业务允许的版本边界分批；每种选择都要交代一致性、额外空间与恢复成本。

每连接外键开关处理连接初始化，本篇则要求沿实际读事务追踪释放责任。不要为了解决空间问题悄悄牺牲导出合同，也不要让用户等待期间无期限占着事务而无人知晓。

自动阈值能当作 WAL 文件硬上限吗？

不能。自动 checkpoint 的页数阈值是触发维护的条件，默认自动操作属于 PASSIVE；遇到持续读者，不保证一次追平，更不等于每次都物理截断。应为容量、最长读事务、维护延迟分别设观察与处置依据，而不是把阈值乘页大小当作绝不会超过的磁盘预算。

待执行验收应保留运行库身份、数据库模式、两个连接的事务时间线、每次三列结果、文件长度及等待和错误。分别覆盖甲保持旧快照、甲释放、并发维护争用和成功截断，并确认业务查询结果正确。本文没有创建数据库或执行命令；先证明哪个事务限制了哪一步，再让维护模式兑现回写、复用或物理回收中的明确目标。
