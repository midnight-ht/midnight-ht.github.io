JOIN USING 少了一列，接口为什么跟着变了？

连接匹配相同，星号投影仍会改变列数与顺序；用显式字段、来源标志和消费者验收守住结果合同。

正文

核心要点

  • USING合并连接列并改变星号投影顺序。
  • 显式投影让接口变更可以独立审查。
  • 合并键不能单独证明外连接记录的来源。

把 JOIN ON a.id = b.id 改成 JOIN USING (id)，匹配的行可能相同，SELECT * 的输出列却会改变。USING 会把列出的同名连接列合并成一个输出列；原来分别来自左右两表的键不再各占一列。若报表导出、接口序列化或下游程序依赖列数与列顺序，这就已经是结果合同变更。

缩短条件，也改变了投影

PostgreSQL 18 表表达式文档说明，ON 形式输出左侧所有列，再输出右侧所有列；USING 先输出列清单里的合并列，顺序与清单一致，然后是左侧剩余列，最后是右侧剩余列。本文讨论该版本的结果形状，不宣称某种写法总是更快。所有 SQL 均为未执行示例。

假设客户表列顺序为 id、name，积分表为 id、points。前者有客户一和二，后者有客户一和三。内连接使用等值 ON 时，星号投影的列是 id、name、id、points；使用 USING 时则是 id、name、points。客户一仍是同一匹配对象，但第四列变成第三列，重复列名也少了一个。只比较返回行数，发现不了这个变化。

WITH customers(id, name) AS (
  VALUES (1, 'A'), (2, 'B')
), credits(id, points) AS (
  VALUES (1, 20), (3, 30)
)
SELECT * FROM customers c JOIN credits r USING (id);

按这份数据推演，结果只含客户一，三个输出值依次是一、A、二十。若旧导出器用第四个位置读取积分，它将面对一个不存在的位置。若驱动按列名转换对象，重复 id 原先怎样处理还取决于驱动，不能把某一种覆盖规则当作 PostgreSQL 的通用承诺。数据库结果与对象转换应分开验证。

对于多个连接键，顺序更容易被忽略。USING (tenant_id, id) 把租户键放在业务键前，即使它们在原表中的位置相反也如此。把清单顺序调整成看似更漂亮的格式，就可能改变位置式消费者的解释。共享查询一旦作为 CSV、报表或函数返回记录的基础，列清单应像接口字段一样接受审查。

显式投影让内部重构更容易解释

如果需求是返回客户标识、客户名称与积分，可以显式写出 c.id AS customer_id, c.name, r.points。这样，连接条件的改动不会顺便依赖星号展开规则来定义接口。若需要左右来源的键，也分别选择 c.id AS customer_id 与 r.id AS credit_customer_id，不要让相同名字掩盖来源职责。

显式投影也有维护成本：新增业务字段需要更新查询与消费者合同。但这种成本恰好让变化可见。是否可用星号，取决于结果是不是临时探索、是否有人依赖固定结构，以及是否有可靠的版本边界。不能把“不要用星号”当作全部解释；探索查询用它快速查看数据，和稳定接口长期暴露它，承担的责任不同。

另一个反例是两张表都有 status，却分别代表客户状态和积分账户状态。名字相同不说明含义相同，不能随手放进 USING。NATURAL JOIN 更会自动把所有同名列纳入匹配：日后两边新增同名字段，查询条件就可能随模式变化。USING 的列名是显式的，新增无关列不会自动加入匹配，但星号输出依然可能增加字段。

因此需要区分两种漂移：连接条件漂移决定哪些行匹配，投影漂移决定结果含哪些列。USING 限制了前一种自动扩张，却不替星号接口冻结后一种。审查时分别问“匹配依据变了吗”和“消费者看到的字段变了吗”，比争论某个关键字是否安全更具体。

验收列合同，不能只验收数据值

拟议测试应保存字段名称、顺序、数量与业务含义，再独立核对行集合和字段值。对于位置式读取，用旧消费者读新结果，确认没有静默错列；对于对象式读取，查看驱动返回的列元数据及重复字段处理。不要只把结果转成无序对象比较，这可能提前丢掉待检查的重复名称或顺序信息。

在数据样本中准备左侧独有、右侧独有和双方匹配的键，并准备非键同名字段。改动前后逐项说明哪些差异允许、哪些必须阻断。接口若需要新增字段，可以明确升级合同；如果只是内部代码简化，就应保持对外投影不变。本文没有运行驱动、CSV 导出或数据库，所以这些仍是验收设计。

FULL JOIN 合并键以后，怎样知道记录来自哪一侧？

不要只看合并后的 id。完整外连接会保留双方未匹配的行，合并键可在其中有值，却不足以单独说明来源。可以显式选择左右两侧的非空主键为独立字段，或在输入侧增加来源标志，再在结果中按约定输出。来源判定字段必须能区分真实空值与没有匹配行；随便挑一个允许为空的业务字段会造成歧义。

以客户一、二和积分一、三为例，完整外连接会让一表示双方匹配、二表示只有客户、三表示只有积分。若只输出合并 id，三行都有 id，无法据此判断谁缺失了哪一侧。把左右键分别保留后，可以为一、二、三写出独立的来源预期，再验证序列化层没有再次把它们合并。这是新增的溯源需求，不应靠字符串列名猜测。

可空连接键还需要独立说明。两边键都为空，不意味着等值连接会把它们视为同一个实体；合并输出列的规则没有改变匹配条件对空值的处理。假设两边各有一条缺失客户编号的记录，不应因为它们都显示为空，就让消费者把它们解释为已经关联成功。缺失身份也可能本来就应被输入约束拒绝。

如果需求确实要求空状态之间也有某种匹配关系，应明确写出相应条件并审查多对多扩张，而不是期待合并列替业务补全身份。结果验收可添加两边都有空键的样本，同时检查匹配行与来源标志。这样既能证明列合同没有错位，也能避免把输出中的一个空单元格当成双方身份一致的证据。

本站的LEFT JOIN 条件位置关注行为什么被过滤；这里关注行还在时字段为何已经不同。提交连接重构时，附上改前改后的输出列合同，确认消费者依赖的是哪一种。行数相同可以是一项检查，却不能作为结果兼容的结论。
