bool_and 为 true，为什么仍不能放行整批？

用非空输入、未知项与空批次拆解布尔聚合，把对象覆盖率和检查版本一起写入放行合同。

正文

核心要点

  • 已知项全通过不证明所有对象完成检查。
  • 汇总必须基于完整且版本明确的应检集合。
  • 空批次与全未知批次需要分别定义。

bool_and(ok) 得到 true，只能说明参与计算的非空值全部为真，不能证明每条原始记录都完成检查。若一个批次既有 true 又有 NULL，未知项不会把结果变成 false。把这个结果直接映射为“整批可发布”，就把检查是否通过与检查是否覆盖全部对象混成了一件事。

先分清失败、未知与没有对象

PostgreSQL 18 聚合函数文档分别定义了 bool_and、bool_or 与 count 的输入口径。布尔聚合关注非空输入；没有可聚合的非空布尔值时，结果为 NULL，而不是自动得到业务上的通过。本文使用该版本文档解释语义，下面的 SQL 和批次数据是未执行的教学示例，没有数据库验收记录。

假设发布系统要确认三份材料全部审核通过。甲为 true，乙为 NULL，丙为 true。若 NULL 表示审核尚未返回，bool_and 的 true 只能回答“已经有结果的材料是否全部通过”。它没有回答乙什么时候完成，也没有证明乙可以忽略。若另有 false，结果会是 false；全为 NULL 则得不到已知结论。这几种状态应该在接口里分别可见。

空批次还需要另外定义。没有任何材料与有材料但全部待检，都可能得到 NULL，却具有不同的业务含义。前者也许禁止创建发布任务，后者需要等待或调查检查器。统一显示“审核中”会把输入配置错误伪装成正常等待。因此我会让汇总返回总对象数、已知结果数、失败数与布尔结果，最后再按明确规则计算能否放行。

把覆盖率写进放行表达式

下面假设每个批次的 checks 已经是一份完整且每对象一行的检查集合。代码单独展示甲批次，实际多批汇总还需要明确批次主表与明细的连接方式。

WITH checks(item_id, ok) AS (
  VALUES (1, true), (2, NULL::boolean), (3, true)
)
SELECT count(*) AS total,
       count(ok) AS known,
       count(*) FILTER (WHERE ok IS FALSE) AS failed,
       bool_and(ok) AS known_all_passed,
       count(*) > 0 AND count(ok) = count(*)
         AND bool_and(ok) IS TRUE AS releasable
FROM checks;

按上述输入纸面推演，总数三、已知数二、失败数零，已知项全部通过，但不能放行。这里明确选择了非空批次、每项有结果且全部为真的协议。如果业务允许没有材料的任务通过，就应有意修改非空条件，并给这种例外单独命名，而不是由聚合默认值替产品作决定。

这条表达式依赖输入完整。若上游先写 WHERE ok IS NOT NULL，待检行已经消失，两个 count 会重新相等；汇总没有能力恢复它们。若只从检查结果表出发，从未建立检查任务的材料也可能不存在于输入。要证明所有应检对象都完成，起点应是应检对象集合，再关联检查结果，并区分缺少结果记录与已有记录但结果未知。

一对多连接同样会改变分母。假设每份材料有多次复检记录，直接连接可能把同一对象算几次，或同时留下旧失败与新成功。此时先定义采用哪次检查，例如明确的当前版本结果，再形成每对象一行的输入。不能靠 count 恰好相等就宣称覆盖完整，更不能随手加去重隐藏版本归属。

把 NULL 当 false 是策略，不是还原事实

bool_and(COALESCE(ok, false)) 可以让已有未知行阻止通过，适合“没有明确通过就不允许”的策略。但是它把待检与失败压成同一个聚合结果，调用方如果需要显示重试、补材料或继续等待，仍然需要各自计数。聚合内的替换改变输入语义，聚合外的 COALESCE 则只是在替换最终的未知结果，二者处理的位置不同。

把最终 NULL 替成 true 尤其需要解释。对于空集合，这可能表达数学上的空真；对于审核队列，它也可能成为意外放行。数据库函数不会替团队决定哪种解释合法。若目的只是让页面永远显示布尔值，可以在展示层提供单独状态，而不必改写存储或授权判断中的未知含义。

已有的COUNT 输入口径文章解释数量为何不同；本篇进一步要求数量参与决策。一个“全部通过”字段应能回答它覆盖哪些对象、采用哪版检查、未知项有几个。只保留布尔结果，后来很难判断是全部真，还是部分结果尚未到达。

聚合内把 NULL 变 false，空批次也会被拒绝吗？

不能只靠这一处替换。空输入没有任何一行供 COALESCE 处理，bool_and 仍可能返回 NULL。若要求函数返回严格布尔值且空批次拒绝，可明确组合非空条件与 IS TRUE，或对最终结果选定 false 默认值。选择前应先确认空集合是错误、无需检查还是允许通过，不能让客户端如何解释 NULL 偶然决定业务行为。

这个追问还影响批次列表。没有 GROUP BY 的标量聚合会返回一行汇总；按批次分组时，完全没有输入行的批次可能根本没有对应组。此时仅处理聚合值仍不够，需要从批次集合保留那些对象。验收应同时检查结果值与是否返回该批次，不要把“没有这一行”误读为“这一行的值是 NULL”。

还有一个容易被汇总字段隐藏的条件是观察时点。假设检查汇总完成后，材料内容又被编辑，原来三项通过未必还能支持新内容发布。完整性应绑定到被检查的材料版本，而不只是对象编号；若版本已经变化，就应让该项重新进入待检状态。这里提出的是发布协议设计，并未实现并发控制。

因此结果接口可以分别携带被检查版本与汇总时点，让授权路径核对它们是否仍适用于当前任务。页面缓存里保留的绿色标记只能帮助展示，不应自动获得新的放行权。验收需加入“汇总后修改一项材料”的假设路径，确认旧结果没有被错误沿用。这样检查既覆盖了对象集合，也没有把一次观察扩张成持续有效的保证。

建议先手写五组独立预期：全部 true；true 加 NULL；false 加 NULL；全部 NULL；零行。再准备漏建检查记录、重复复检与上游过滤三条失败路径，逐项核对总对象集合。本文没有运行这些查询，也不提供性能比较。放行规则的第一份验收证据，应是每一种未知或缺失都能得到预先约定的状态，而不是只看一组全真数据变绿。
