字段从 NULL 变成文本，为什么变更检测没有命中？

用五组更新前后状态解释空值差异比较，避免哨兵碰撞，并保留部分更新中省略字段与显式清空的区别。

正文

核心要点

  • 空值参与普通不等比较时会得到未知。
  • IS DISTINCT FROM明确区分单侧空与双侧空。
  • 请求省略字段的含义必须在比较之前保留。

用 old_value <> new_value 检测可空字段变更时，从 NULL 首次填写文本、或从文本清空成 NULL，都可能没有被条件选中。普通不等比较遇到 NULL 会得到未知。若业务需要把“两边都是空”看作没变、“只有一边为空”看作已变，应该考虑 IS DISTINCT FROM，并先定义输入缺失与显式清空的区别。

变更检测要比较完整状态

PostgreSQL 18 比较函数与运算符文档说明，IS DISTINCT FROM 对两个非空值按不等比较；两边都是 NULL 时为 false，只有一边为 NULL 时为 true。相反的 IS NOT DISTINCT FROM 对两个 NULL 返回 true。这是一份明确包含空状态的比较协议，不是把 SQL 的所有未知值普遍改成相等。

假设资料审计记录联系人备注的更新前后状态。第一位用户原来没有备注，现在填入“晚间联系”；第二位原来有这段备注，现在明确清空；第三位前后都没有备注。业务要求前两位产生变更，第三位不产生。若只写普通不等条件，前两位也不会得到 true，审计就漏掉真正的状态迁移。

下面给出完整假设输入与比较列。代码没有执行，结果解释是依据文档的纸面推演，不是数据库日志。

WITH changes(id, old_value, new_value) AS (
  VALUES (1, NULL::text, 'evening'),
         (2, 'evening', NULL::text),
         (3, NULL::text, NULL::text),
         (4, '', NULL::text),
         (5, 'same', 'same')
)
SELECT id,
       old_value <> new_value AS ordinary_different,
       old_value IS DISTINCT FROM new_value AS changed
FROM changes
ORDER BY id;

按这份输入，changed 对一、二、四为真，对三、五为假。第四行故意加入空字符串与 NULL 的区别：若空字符串是合法的已提供值，转成 NULL 就应被记录。普通比较在前四行都受到空值影响，无法单独给出期望的二值变更标记。第五行则保留了普通非空相等的基准，避免测试只检查含 NULL 的例子。

COALESCE 哨兵可能吞掉合法变更

常见补丁是把两侧 NULL 都替换成空字符串，再用不等比较。它会把第四行转换成空字符串对空字符串，于是把一项真实变化判成没有变化。换成某个特别的字符串也只是把冲突推迟到该值进入数据时。若字段没有约束保证哨兵永远不可能出现，比较过程就在悄悄合并两种真实状态。

如果业务有意把空字符串、全空格与 NULL 统一成“未提供”，应先定义正规化规则，在边界明确处理，并决定是否保留原始输入用于审计。此时两种存储状态被视作相同是产品决定，而不是为了让 SQL 返回布尔值做的临时替换。IS DISTINCT FROM 同样不会替团队完成空白裁剪、大小写归一或电话格式转换。

比如用户把带空格的备注改成不带空格的相同文字，是否产生审计事件，取决于比较原始输入还是规范化结果。若既要保留用户动作，也要避免内容相同的重复更新，可以分别记录请求事件与规范化状态变化。把两种目的塞进一个 changed 字段，会让以后的人无法判断它代表点击保存，还是存储内容真正不同。

条件更新与审计仍有各自的责任

对于只在备注真正改变时才更新的假设接口，可以把字段比较纳入 UPDATE 的 WHERE 条件，同时按稳定记录标识定位目标。这样表达的是“目标存在且当前字段与新值不同才更新”。但没有更新行可能表示内容相同，也可能表示记录不存在或其他筛选条件不满足，不能直接把零行翻译成“资料原本就一致”。

审计还需要绑定实际变更的旧值、新值、操作人及事务归属。一次 SELECT 比较正确，不证明后来的 UPDATE 使用了同一版本状态，也不证明审计与变更一同提交。本文不提供完整事务实现或并发控制方案；它只解决字段差异比较的语义。实际服务仍需按当前授权、更新协议和事务设计验证结果，不能把一个谓词当作整套审计系统。

拟议验收先写出五行示例的独立结果，再补充两个不同非空文本、普通相同文本、空字符串对空字符串。检查值之外，核对被更新的业务标识与审计条数。不要只验证一次从文本到另一个文本，因为最容易漏记的首次填写与清空根本没有经过那条路径。这里没有执行 SQL 或测量是否减少写入成本。

接口省略字段和显式传 NULL，能用同一比较处理吗？

不能先把二者都变成 NULL 再期待数据库还原意图。对于部分更新，省略备注通常可表示保持原值，显式 NULL 则可能表示清空；这是需要由接口明确规定的假设合同。应用必须先保留字段是否存在，再决定是否把新值送入比较。比较谓词只看到收到的两个值，不知道请求里原先有没有这个字段。

假设已有备注为 evening，甲请求完全不含备注字段，乙请求明确包含备注且值为 NULL。前者应按合同跳过备注更新，后者才比较 evening 与 NULL 并产生清空事件。若服务把甲缺失字段也默认赋成 NULL，两条请求就会意外做同一件事。测试因此要覆盖原始请求形状，而不只是直接调用数据库时的参数值。

响应协议也要保留这份区别。假设客户端重复提交相同备注，服务可以报告内容未变化，但仍应先确认目标与访问权限，而不能仅凭更新零行就透露或推断记录状态。若需要把不存在、不可访问与无变更统一呈现，也应是明确的安全和产品选择，而不是查询偶然给出同一个计数。

审计验收则可准备连续两次相同请求，核对实际变更事件没有被误记两次，同时保留接口确实收到两次请求所需的操作证据。请求次数与状态变化次数不必相同，两份记录可以服务不同调查目的。这个例子不承诺自动获得幂等处理；请求身份、事务与重复副作用仍需实际实现。先把事件名称写清楚，比让所有记录都叫更新成功更利于核查。

本站的NOT IN 与 NULL解释集合筛选里的未知传播；这里的读者问题是更新前后状态怎么比较。不要因为都涉及 NULL，就把一种改写复制到全部查询。提交资料变更修复时，应交付输入存在性规则、空值等价规则与每种状态迁移的预期，再验证更新和审计确实遵循同一份规则。
