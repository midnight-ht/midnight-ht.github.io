数值在范围内，为什么仍然 stepMismatch？

用步长与基点解释范围内拒绝，区分 value 内容属性、当前值、any 与服务端精度规则。

正文

核心要点

  • 范围限制与步长网格是独立条件。
  • 步长基点优先有效min，再看初始value内容属性。
  • any不规定金额精度或替代服务端业务校验。

数值落在 min 与 max 之间，仍可能因为不在允许的步长网格上而触发 stepMismatch。对 number 输入框，范围与步长是不同约束；应先确定步长基点，再检查当前值与基点之差是否是步长的整数倍。只把最大值调大，通常不会修复网格不匹配。

步长从零开始算，还是从最小值开始算？

HTML 标准的 Number 状态把默认步长设为一，但这不等于无条件只接受整数。同一文档的 step base 算法优先使用有效的 min 内容属性，再使用可解析的 value 内容属性，之后考虑该类型的默认基点，最终才回落到零。对普通数字控件，基点与步长共同决定允许的序列。

可以把它想成一把刻度尺：步长决定相邻刻度间隔，基点决定尺子放在哪里。范围则只切掉尺子两端之外的部分。假设 min 为零点二，max 为三，省略 step，网格中的候选是零点二、一点二、二点二等；一点三虽然在范围内，却不在这条序列上。反过来，一点二不是整数，也可能满足这个步长约束。

这段推演是按规范解释的数学示例，没有执行浏览器交互。实际页面可能还有 required、自定义错误、输入解析和服务端规则；即使步长满足，也不代表全部校验通过。诊断时需要读取具体 validity 标志，而不是把任何红色错误提示都归到 stepMismatch，或看到 false 就猜一定是小数位太多。

一份重量输入怎样写出可核对的规则？

设想一个材料申领表要求重量在零点二到三千克之间，每次增量为零点一千克。下面是假设业务合同。前端可以明确设置 min、max 和 step，候选输入一点三此时位于以零点二为基点、间隔零点一的序列上。服务端也按同样单位与精度规则判断，不把浏览器提供的数字输入外观当作可信验证。

完整路径从填写一点三开始：页面应按设定检查范围与步长，提交后服务端解析约定格式，保存业务批准的数，再在核对页显示同一重量。测试应比较输入值、各项有效性、请求载荷、保存值与显示值。若页面显示一点三但实际载荷因另一个格式化函数变成一，说明问题发生在转换链路，不能单凭输入框步长正确就批准整个流程。

再输入一点三五，它处于范围内但不落在上述网格上，预期应按合同拒绝或提供明确修正建议，而不是静默变成邻近值。浏览器在特定步长不匹配情况下可以采用规范允许的舍入行为，但业务不能据此承诺所有输入方式、所有实现都自动修成同一数。若产品需要由用户确认近似值，应把原输入、建议值与确认动作说清楚。

失败反例是看到小数被拒，就把 step 改成 any，却继续声称只允许一位小数。这只是移除了步长限制，规则的承诺与实现已经分离。另一个反例是服务端只检查最小最大值，让浏览器通过与接口直接调用形成两套接收规则。边界应在权威接收方重新验证，客户端用于及时反馈。

修改 value 会把整条网格一起移动吗？

要区分 value 内容属性与当前 value 属性。基点算法考虑的是可解析的 HTML 内容属性，并不意味着用户每输入一个当前值，基点就随之移动；否则步长约束会变成自我满足。若有有效 min，基点优先来自 min，设置初始 value 也不会越过这个优先级。

假设省略 min、step 为二、初始内容属性 value 为一，允许序列可以包含一、三、五。用户改成二时，不能用“当前值二就是新基点”来解释它合法。若脚本直接改变内容属性，或者框架重建元素并改变初始属性，则需要重新检查最终 DOM 与基点来源。评审要保存实际属性和值，避免只看框架状态变量就猜浏览器采用哪条规则。

选择基点应来自业务单位和最小有效值，而非为了让当前报错样本通过而临时添加一个 value。对于必须允许任意小数的测量值，可考虑 any 并在其他层定义范围、有限数值及业务精度；对于明确离散的包装数量，则应给出固定步长与起点。两类场景的区别在于真实允许集合，不在于输入框是否有上下箭头。

step=any 能代替金额与精度校验吗？

不能。它不规定结算精度，也不定义展示舍入、服务端数值类型或持久化方式。金额输入如果需要最小货币单位，必须先确定单位、精度和转换规则，再选择控件约束。本站的显示舍入与业务舍入说明为什么看见两位小数不等于业务值已按两位结算；同样，步长通过也不能证明后续计算口径正确。

标识符也不要因为只含数字就自动使用 number。若前导零、固定字符长度或字符串身份有意义，应按标识符设计输入与验证，而不是给它一条算术增量序列。选择控件时问“这个值是否参与数值增减”，比问“用户会不会输入字母”更接近实际对象。

待执行的验证应至少包含位于网格上的边界值、范围内但不在网格上的值、超范围值、空值，以及具有初始 value 而没有 min 的情况。记录有效属性、当前值、stepMismatch 与其他标志、脚本改属性前后变化，再以同一组输入调用接收接口。本文没有运行这套浏览器或接口检查；交付判断应限制在规范语义与假设算例。先把刻度间隔和起点写清楚，再决定错误究竟来自范围、步长还是后续转换。
