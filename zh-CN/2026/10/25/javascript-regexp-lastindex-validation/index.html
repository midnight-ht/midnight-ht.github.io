相同输入交替通过：检查正则的 lastIndex

用连续test与g/y位置对照解释游标状态，把独立校验、扫描、空匹配推进和验证记录分开设计。

正文

核心要点

  • g和y模式的lastIndex会参与后续调用。
  • 去掉扫描标志不自动得到完整字段规则。
  • 零长度匹配需要扫描循环明确推进。

同一个正则对象对相同字符串反复 test，结果可能依次为 true、false、true。先检查是否带 g 或 y：这两类匹配会读取并更新对象的 lastIndex。字段验证若只需要判断当前输入是否合法，复用一个带扫描游标的对象，会让上一次调用参与下一次判定。

隐藏输入不只有待检字符串

ECMAScript 的 RegExpBuiltinExec 算法描述了内置匹配如何处理 lastIndex。普通的非全局、非粘连正则从零开始匹配；带全局或粘连标志时，成功会把游标写到匹配结束处，失败时相应地重置为零。这里以普通内置 RegExp 行为为前提，不覆盖自行重写 exec 的对象。

下面是未执行的教学示例。代码旁的预期来自规范推演，没有把它写成浏览器或项目测试输出。

const check = /x/g;
const first = check.test('x');
const afterFirst = check.lastIndex;
const second = check.test('x');
const afterSecond = check.lastIndex;
const third = check.test('x');
// Expected: true / 1, false / 0, true.

第一次从零位置找到 x，结束位置为一。第二次对同样的单字符输入从位置一继续，没有匹配，于是失败并把游标重置。第三次又从零开始，所以通过。字符串没有改变，正则状态改变了。若只记录输入与布尔结果，不记录对象标志与调用前游标，就容易把这个确定的状态变化误判为偶发错误。

这也解释了为何在 map 或 filter 中复用全局正则会使不同字段互相影响。假设三个字段都是 x，一个共享正则按顺序检查，后一个字段读到前一次留下的游标。问题不需要多线程或异步并发才能发生，同一事件循环内的连续调用已经足够。把失败字段重试一次后恢复，也不能证明输入曾经不合法。

校验与扫描应分开设计

若需求是每次独立判断完整字段，优先使用符合字段语法、没有 g 和 y 的表达式，并独立处理类型、长度与业务范围。去掉 g 只消除了这一类游标依赖，不会自动把子串查找变成整串验证。/x/ 仍能在较长字符串中找到 x，完整字段规则需要另外定义。

若确实需要逐段扫描，例如词法分析器从某个位置开始识别标记，lastIndex 就是有用状态。全局匹配会从指定位置尝试并寻找后续匹配，粘连匹配则要求从游标处匹配，不会跳过当前位置去寻找更后面的起点。不能把 y 当成“更严格所以无状态”的校验开关；它同样会更新游标，只是扫描规则不同。

一种修复是每次测试之前显式把 lastIndex 置零，但这要求所有调用路径都遵守约定。若正则被扫描器和表单共用，校验重置还可能破坏扫描器的位置。比到处补重置更清楚的做法，是让独立验证拥有无状态规则，让扫描任务各有自己的正则实例与游标生命周期。重新构造正则是否值得，属于实际工作负载的成本问题，本文没有基准数据。

假设校验器在页面输入时调用一次，提交前又调用一次。验收不能只证明第一次输入通过；需要让同一合法输入在重复调用、不同字段交错调用和失败后重试时保持相同判定。测试应检查产品期待的结果，而不把当前正则调用一次得到的值当作全部预期，否则状态错误会被复制进断言。

把状态日志放到能解释失败的位置

拟议诊断可记录正则 source、flags、调用前后的 lastIndex，以及经过隐私处理的输入类别与长度。敏感字段不要为了排查直接写全文日志。只打印调用后的零也不够，因为失败会重置游标；若没有调用前的一，就看不出为什么相同字符串这次失败。日志字段应能重建状态转移，而不是只有最终红绿灯。

另外要审查正则对象的归属。模块级常量若带全局标志，所有调用者可能共享它；每次函数执行内部创建的新实例则有不同生命周期。const 只限制变量重新绑定，不会让 lastIndex 只读。把变量命名为 VALIDATOR，也不会改变对象自身的可变行为。代码审查应看创建位置、标志和实际调用关系。

已有的整数字段完整校验讨论解析成功为何不等于整串合法；这里增加的是即使语法规则正确，跨调用状态仍能破坏重复判定。这两种问题应分别验收：一组检查允许哪些输入，另一组检查相同输入在不同调用历史下是否保持相同结果。

允许空匹配时，exec 循环为什么可能不前进？

内置 exec 成功会把 lastIndex 设为匹配结束位置；零长度匹配的结束位置可能与开始相同。因此不能假设每次成功都必然推进游标。若手写循环一直调用能匹配空串的全局正则，就需要明确的前进策略，否则可能重复停在同一位置。这个问题来自扫描循环，不是前面交替通过示例的另一次失败。

处理时要考虑 Unicode。简单加一按 UTF-16 代码单元移动，可能与希望按完整字符推进的规则不同。可选方案是约束模式不产生空匹配，使用适合任务的内置迭代接口，或按相应 Unicode 模式设计推进逻辑；不能只贴一行 lastIndex++ 就宣称所有文本扫描都安全。采取哪种方式，需与允许的模式和目标运行时一起验证。

一个有解释力的扫描反例是输入包含分隔符后才有目标字符，而当前游标停在分隔符之前。假设目标是字母x，输入为短横线后跟x，游标从零开始：全局搜索可以寻找后面的x，粘连搜索却会因零位置不是x而失败。若扫描器要求每个位置都有合法标记，允许跳过分隔符可能掩盖非法字符；若任务只是查找出现位置，要求当前位置立即匹配反而过严。

测试这两种需求时应独立列出匹配起点与结束位置，别只比较最终布尔值。相同的成功结果也可能来自不同位置。记录允许跳过哪些文本、失败后是否重试以及谁推进游标，能让维护者判断换标志是否改变了协议。这些是待执行的验证场景，不是声称某款浏览器已经覆盖所有Unicode组合。

本文没有执行正则脚本或表单。建议验收表同时包含连续相同输入、两个字段交错、一次失败后恢复、g 与 y 的位置差异，以及允许空匹配时的终止条件。最终提交应说明正则是独立判定器还是有状态扫描器，并让它的生命周期与这个职责一致。
