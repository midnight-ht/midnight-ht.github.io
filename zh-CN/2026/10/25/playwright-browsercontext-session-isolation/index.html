Playwright 两个 page 串登录态：把角色隔离放到 BrowserContext

两个页面不等于两个浏览器身份；用独立上下文建模双角色，再单独验证账号、服务端数据与权限。

正文

核心要点

  • 同一上下文内新增页面不会自动生成独立身份。
  • 独立上下文加载同一快照仍是同一账号。
  • 浏览器隔离不能隔离服务端购物车和权限。

在同一个 BrowserContext 里再开一个 page，并不会得到另一个独立登录身份。要同时扮演买家与审核员，应建立两个独立上下文，再分别打开页面。page 表示页面，context 才是 Playwright 用来组织浏览器会话隔离的边界；把角色按页面分配，容易让共享 cookie 改写另一个角色的请求身份。

页面为什么会共享身份

Playwright 的隔离指南说明，浏览器上下文提供类似独立浏览配置的隔离。Playwright Test 默认为每个测试创建上下文，并在其中提供默认页面。这项默认行为不能推广为“任何一次 newPage 都创建隔离身份”：通过已有上下文创建的页面仍属于它。

具体共享什么还要遵守 Web 存储的作用域。相同上下文内，cookie 按域、路径等规则适用，localStorage 按源区分；不同源的数据不会仅因属于同一上下文就相互公开。sessionStorage 又涉及页面会话，不能把所有存储都说成同上下文页面之间无条件共享。真正需要跨测试隔离时，使用独立上下文比手工枚举每类存储更能表达意图。

登录态快照文章解决保存了什么、能否恢复的问题。本篇处理快照之外的边界：正在并行操作的两个页面，究竟是不是同一浏览器身份。即使完全不保存文件，也可能出现角色串用。

一个双角色审批示例怎样建模

设想未运行的订单测试：买家提交订单，审核员批准，买家再查看状态。若两个页面都从同一个上下文创建，审核员登录写入同域会话 cookie 后，买家页面后续请求可能也携带审核员身份。页面仍显示买家头像，不代表网络请求使用的还是买家凭证；旧展示状态恰好会掩盖隔离错误。

应在两个上下文中分别完成各自获准的登录，再检查受保护接口返回的身份。下面只有生命周期骨架，没有真实站点和登录实现，未执行。

const buyerContext = await browser.newContext();
const reviewerContext = await browser.newContext();
try {
  const buyer = await buyerContext.newPage();
  const reviewer = await reviewerContext.newPage();
  // Perform the application's authorized login separately in each page.
  // Verify each identity before creating and approving a dedicated order.
} finally {
  await Promise.all([
    buyerContext.close(),
    reviewerContext.close()
  ]);
}

完整的验收还需建立业务数据链：买家创建带本次运行标识的订单，记录其标识；审核员只审批该订单；买家查询同一个订单并断言状态变化。另加一条反例，让买家尝试审核操作，期望被权威接口拒绝。两个页面都能打开，只证明浏览器对象创建完成，不能证明角色权限正确，更不能证明整个审批链完成。

如果登录状态来自快照，应为两个角色分别选择正确且有效的文件。两个独立上下文若加载同一身份快照，仍会作为同一个用户访问服务器；隔离的是浏览器状态容器，不是自动为文件创造不同用户。文件名写着 buyer，也不能代替接口返回的身份核对。

为什么清 cookie 不是等价替代

在共享上下文中切换角色前清 cookie，看似能重置身份，却可能遗漏其他状态，或者让仍在执行的另一个页面突然退出。两个角色的动作一旦交错，清理与登录之间还会出现竞争。测试需要的是并存身份时，独立上下文直接表达该需求，也便于分别关闭和诊断。

若测试目标恰好是同一用户的多标签页退出同步，就应该保留同一个上下文，而不是为了“隔离最好”强行拆开。此时共享是被测条件：一个页面退出，另一个页面如何处理缓存展示、下一次请求与重新登录，应按产品契约断言。独立身份测试与同身份多页面测试，应由要证明的行为决定模型。

此外，不应把上下文隔离宣传为操作系统级安全沙箱或远端租户隔离证明。它适合测试浏览器会话边界，应用后端、网络代理、共享数据库和第三方账户仍有各自状态。浏览器隔离通过，服务端对象授权也可能失败。

两个独立 context 用同一账号，还会互相影响吗？

会有这种可能。上下文不能隔离服务器保存的账户资料、购物车或会话撤销政策。假设两条测试使用同一买家账号，各自创建上下文，一条清空购物车，另一条正准备结算。浏览器存储各自独立，服务端购物车仍可能是同一份，两条操作照样冲突。

选择账号策略时先问哪些状态会被修改。只读检查可评估复用账户；修改订单、角色或购物车的测试通常需要独立账号、独立数据标识或受控串行。若产品规定新登录会撤销旧会话，两个上下文再次登录同一账号后旧会话失效，可能恰好是预期行为，不应通过延长等待掩盖。

还要区分会话复制与账户复制。相同快照复制到两个上下文，得到的是相同凭证的两个本地副本；一端登出是否令另一端失效，取决于服务器撤销机制与客户端检查时机。它没有生成第二个独立业务用户。

怎样留下可判断的隔离证据

拟议验证先记录角色、上下文标识、页面归属和独立业务数据标识，不保存令牌值。每个角色登录后检查身份，在另一个角色登录与执行动作后再次检查，确认没有被意外替换。随后分别测试授权与拒绝分支，最后关闭上下文并按数据归属清理测试对象。

还可以用一个有区别的诊断动作：在不修改服务器数据的前提下关闭并重建买家上下文，再重新登录。如果错误身份随本地状态消失，调查重点偏向上下文复用；若独立登录后仍读到错误订单，则要继续查服务端查询条件与授权。这个对照只能缩小范围，不能单凭一次恢复就断言根因，因为重新登录本身也可能改变服务器会话。

失败时优先比较实际身份响应与页面展示，再查看上下文创建位置及公共夹具是否复用了对象。不要只凭页面名称或变量名判断身份。本文没有启动浏览器、执行审批或验证任何真实账户。下一条双角色用例应先画清每个 page 属于哪个 context，再确认账号与服务端数据是否也满足并发隔离要求。
