promisify 之后 this 丢了，应该绑定哪一层？

把接收者、错误优先回调与custom覆盖分开审查，明确Promise的成功形状及旧接口迁移验收。

正文

核心要点

  • 包装方法不自动保留原实例接收者。
  • 非标准回调和多个成功值需要明确适配协议。
  • custom指定实际返回函数，已有Promise接口通常无需重复包装。

util.promisify(client.load) 把回调接口变成返回 Promise 的函数，却不会替这个函数记住 client。原方法若依赖 this 读取实例字段，包装后直接调用仍可能失败。修复首先要保留接收者，再核对回调是不是最后一个参数、是不是错误优先，以及成功时究竟应该返回什么。

方法所属对象不会跟着函数引用移动

Node.js v24 分支的 util.promisify 文档给出了类方法失去接收者的例子，并展示使用 call 或 bind 的处理。本文核对的页面标为 v24.22.1。下面是没有执行的假设客户端代码，不是某个 SDK 已通过迁移的记录。

import { promisify } from 'node:util';
class Client {
  constructor(prefix) { this.prefix = prefix; }
  load(key, callback) {
    callback(null, `${this.prefix}:${key}`);
  }
}
const client = new Client('draft');
const load = promisify(client.load);
const value = await load.call(client, 'A');
// Expected value by inspection: 'draft:A'.

这里 client.load 取出的是方法函数。原来以 client.load 调用时，调用表达式提供 client 作为接收者；存到独立变量后直接调用，这个关系就没有自动保留。示例通过 call 显式提供接收者。若要把函数传给不支持指定接收者的调用方，可以在完成 promisify 以后把返回函数绑定到 client，再对外暴露。

不要把这项修复解释成“Promise 会让 this 消失”。丢失调用关系是函数被提取的结果，同步调用也可能遇到。Promise 包装只让问题在迁移时暴露。验收必须使用两个具有不同前缀的实例，确保各自的 load 得到各自数据；若只测一个实例且结果又是常量，就可能漏掉意外绑定到全局对象或另一个实例的错误。

错误优先是适配前提，不是自动识别能力

默认 promisify 面向最后一个参数为 (err, value) 回调的函数。发生错误时，回调首参承担拒绝原因；成功值来自约定的成功位置。若旧 API 把成功回调和失败回调分成两个参数，或回调形如 (value)，不能因为函数能被传入就认为语义已经适配。把一个成功字符串误当错误，会让正常结果变成拒绝。

还要确认业务是否需要多个成功参数。假设旧回调提供错误、正文和响应头，调用方后来只拿到正文，就可能丢掉用于分页或校验的信息。迁移前应给 Promise 设计明确的返回对象，例如 { body, headers }，不要依赖“回调全部参数会自动成为数组”这种未经约定的假设。具有库自定义行为的 API，要读该库的协议，而不是用通用例子推定它的返回形状。

当默认规则不合适，可以手写一层返回 Promise 的适配器，明确参数顺序、接收者和成功字段。错误优先接口可在回调里先检查错误，再把需要的多个值合成对象；分离成功失败回调的接口，则分别连接 resolve 与 reject。这个选择增加了一点代码，却把原本隐藏的协议写成可审查的契约。新适配器仍需处理实际 API 的同步抛错与完成约定，不能宣称通用包装消除了所有旧接口问题。

custom 会替换返回函数，不能当作装饰说明

文档说明，原函数存在 util.promisify.custom 时，promisify 返回该属性指定的函数；属性存在却不是函数会报错。这意味着 custom 不是给默认转换补一个提示，而是直接选择另一条实现。它可能改变接收者要求、成功返回值与错误行为，所以审查要把它当作真正被调用的函数来读。

如果某个方法先被 bind 生成了新函数，再交给 promisify，不能假定原函数上的 custom 属性会自动成为新函数的属性。较清楚的检查顺序是先查看原方法是否提供自定义转换，再确认 promisify 实际返回哪一个函数，最后决定怎样向该函数提供接收者。文档中的通用绑定例子并不替所有第三方 custom 实现承诺相同的 this 语义。

假设一个旧接口的默认回调返回正文，但 custom 版本返回正文与校验信息组成的对象。如果迁移测试只检查结果非空，就无法发现返回类型已经改变。应预先写明调用方需要的字段、类型与失败方式，再按真实分支检查。对 custom 的验证也不能只断言属性存在；要确认调用到了自定义函数，并核对它实际兑现的协议。

原函数已经返回 Promise，还应该交给 promisify 吗？

不应把重复包装当作默认迁移步骤。所读取的 Node 文档记录，自 v20.8.0 起，对返回 Promise 的函数调用 promisify 已被弃用。一个只返回 Promise、从不调用末尾回调的函数，并不会因为外面又套一层就自动符合回调协议。先判断原 API 的正式异步接口；已有合适的 Promise 版本时，通常直接使用它更清楚。

对于同时支持回调与 Promise 的混合 API，要按库文档决定选哪条调用方式，而不是用函数名猜测。特别是错误监控与资源释放，必须跟随实际完成关系。本站的finally 如何改变最终结果讨论完成后的清理；本篇先确保被等待的 Promise 本身代表正确的调用与返回协议。

接收者正确与回调正确应交叉测试，而不是只各测一个成功示例。假设两个租户客户端都能返回各自前缀，但其中一个在查询失败时把错误放在第二个参数；绑定修复能解决前缀，却不能解决这个协议差异。反过来，完全符合错误优先约定的函数，也可能因为绑定到了错误租户而返回一份结构正确、归属错误的数据。

因此迁移验收可以按实例、输入和完成方式分别列预期：甲实例成功返回甲的数据；乙实例成功返回乙的数据；各自失败都保留可辨认的错误。需要哪些错误字段，应按接口正式合同定义，不能把示例里的字符串当成统一格式。异步结果形状正确以后，还应由调用方继续核对数据归属；包装器没有授予跨实例读取或跨租户访问的权限。

拟议验收应覆盖两个实例的接收者隔离、成功返回、错误回调、非标准回调的显式适配、custom 覆盖，以及多成功值是否完整保留。独立写出预期对象，不从被测结果反向生成预期。这里没有执行客户端、SDK 或端到端迁移。能够 await 只是语法入口，接收者、成功形状与错误责任都明确以后，迁移才有可审查的完成条件。
