pytest 在 yield 前失败：先为已创建资源建立清理责任

区分交付前失败、已完成夹具收尾与远端创建未知，用资源边界选择拆分夹具或登记终结器。

正文

核心要点

  • yield 前失败不会运行该夹具的后置清理。
  • 每次成功获取资源后尽早建立清理责任。
  • 远端创建结果未知需要查询和补偿契约。

yield 之前抛出异常，pytest 不会继续执行该夹具写在 yield 后面的清理代码。创建资源、配置资源、交给测试，看起来是一次准备动作，却可能在交接之前失败。修复这类泄漏，应让已经成功取得的资源尽早拥有清理责任，而不是只在函数末尾补一条删除语句。

清理为何没有覆盖整个准备过程

pytest 夹具指南明确区分两条路径：当前生成器夹具尚未运行到交付位置便失败，其后置清理不会执行；同一个测试已经成功准备的其他夹具，框架仍会尝试正常清理。不能从一条删除没有发生，推断所有夹具都失去了收尾机会。

这不是把 yield 换成 return 就能修好的语法问题。框架必须先得到夹具交付的对象，才把它的后半段当作后续清理来驱动。若前半段连续完成多个有副作用的操作，其中一步失败，前面成功的部分并不会自动回滚。测试函数甚至尚未开始，准备阶段已经制造了外部状态。

最接近的夹具隔离讨论关注共享对象活多久。本篇处理另一个时间窗口：资源已经存在，但负责删除它的路径还没建立。缩小作用域可能减少共享污染，却不能单独关闭这个窗口。

从一条失败的邀请流程拆开责任

设想未执行的教程：测试先创建临时团队，再邀请成员，最后把团队交给断言。创建成功后，邀请接口因权限错误抛出异常。如果删除团队放在交付之后，这次准备失败便留下团队。下次复用同名团队可能遇到冲突，维护者却只看到邀请失败，很容易把后续冲突归为随机问题。

更合适的拆法是让团队夹具只负责创建与删除，邀请夹具依赖它。团队创建并交付成功后，邀请再失败，团队夹具已经具备正常收尾资格。以下为未运行的示意代码，api 是项目自己提供的测试客户端，不是 pytest 内置能力。

import pytest

@pytest.fixture
def team(api):
    created = api.create_team()
    yield created
    api.delete_team(created.id)

@pytest.fixture
def invited_team(api, team):
    api.invite_member(team.id)
    return team

def test_member_list(invited_team, api):
    assert api.member_count(invited_team.id) == 1

成功分支中，测试拿到已经邀请成员的团队，结束后删除团队。邀请失败分支中，测试正文不运行，但已经完成准备的团队夹具仍会被清理。创建本身失败，则团队夹具尚无可交付对象；是否已经产生远端资源，要看创建接口的事务和超时契约，不能由这段 Python 代码猜测。

删除团队能否连带删除邀请，也必须由业务接口约定。如果邀请另建了需要独立撤销的对象，应再分配一个清理责任，不能因为两者出现在同一段测试里就假定级联关系。拆分有价值的前提，是资源与逆操作的对应关系清楚，而非把每一行都包装成夹具。

什么时候使用直接登记的终结器

同一份指南允许通过 request.addfinalizer 登记清理函数，并说明一旦登记，后面准备失败仍会调用它。因此登记位置应紧跟真正需要清理的成功操作，而不是在尚无资源时提前登记一个可能引用未赋值对象的闭包。

例如一个夹具必须在同一流程中取得多个句柄，可以在每次成功取得后立即登记对应关闭动作。这比等全部配置完成才统一登记更接近实际资源边界。简单的一次获取、一次释放，仍可优先采用易读的生成器夹具；选择依据是失败中途有哪些资源已存在，而不是哪种写法显得更高级。

若资源在本地同步创建，也可以在成功获取后进入 try/finally，把后续配置和交付置于保护范围。这依赖 Python 控制流能够正常展开，不能保障进程被强制杀死后继续执行。远端资源还应有可追踪标识、过期政策或受控巡检，作为进程异常终止后的补偿机制；这些是系统设计建议，不是 pytest 的自动功能。

创建超时但服务端已经建好对象怎么办？

此时单纯调整 yield 位置不够。客户端没有收到对象标识，却不能证明服务端没有提交创建。可评估为创建请求分配测试运行标识或幂等键，通过获准的查询接口确认结果，再按明确归属清理。不要扫描并删除所有同名前缀对象，尤其当多个工作进程或开发者共享环境时。

假设客户端发送创建团队请求，服务器已经提交，响应在网络中丢失。重试一个不具备幂等契约的请求可能创建第二个团队；只删除第二个，仍有第一个残留。验收需要区分“没有创建”“创建结果未知”“已知创建成功”三种状态。未知应进入查询或人工处理队列，不能在报告里写成创建失败所以无需清理。

删除请求失败该怎样处理？

清理请求失败同样要保留对象身份和错误。建议让报告同时显示原始准备错误与清理失败，防止后者覆盖前者，也不要静默忽略后者制造干净环境的假象。重复删除能否安全、未找到是否可视为已清理，应由接口契约确定。

怎样验证修复确实关闭了窗口

可以在隔离测试环境安排创建失败、创建成功后配置失败、测试断言失败、正常通过、删除失败五条路径。每次按运行标识查询资源是否存在，并检查测试正文是否应当执行。只看测试退出码不能判断资源是否残留：预期的准备失败，本就应该产生失败结果，但资源仍应按责任回收。

还应观察相互依赖的夹具清理次序，确保删除父对象之前先撤销依赖对象。并行验证使用独立命名和归属，避免一个测试的清理掩盖另一个测试的泄漏。本文没有运行这些代码、调用远端接口或证明环境已清空；交付的是失败模型和验证设计。先挑一条真实的多步骤准备流程，标出每次成功创建与清理登记之间的距离，再决定拆夹具还是登记终结器。
