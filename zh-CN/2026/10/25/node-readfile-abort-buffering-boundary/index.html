readFile 取消了，为什么不能宣称磁盘读取归零？

限定AbortSignal对readFile内部缓冲的作用，把Promise拒绝、任务结果采用与FileHandle清理分别验收。

正文

核心要点

  • 取消readFile内部缓冲不等于撤回每个系统读取请求。
  • 超时结束等待不自动通知原任务取消。
  • 外部FileHandle的关闭责任需要显式合同。

readFile 收到取消信号并以 AbortError 拒绝，不等于操作系统已经撤回每一次文件读取。Node 文档把作用范围写得很具体：取消的是 readFile 内部的缓冲处理，不是逐个中止操作系统请求。因此，“用户不再等待”“读取 Promise 已拒绝”“资源清理完成”应该是分别能解释的状态。

取消发生在哪一层

Node.js 文件系统文档的 fsPromises.readFile 小节说明该接口支持 AbortSignal，并明确上述操作系统请求边界。本文读取的是标为 v24.22.1 的页面；它记录 signal 支持加入 v15.2.0、v14.17.0。下面讨论路径读取和调用者持有的 FileHandle，不扩展成所有流、设备或第三方库的统一保证。

假设后台导入一个文件，用户在文件尚未读完时点击取消。应用可以向这次读取传递 signal，并在取消后停止把结果交给解析阶段。若取消确实在请求完成前生效，返回的 Promise 会以 AbortError 拒绝。但这不能证明磁盘活动当场归零，也不能从文档推算还有多少读取、多久结束或何时内存一定回收。没有测量时，不应给取消按钮附上这些资源承诺。

下面是未执行的示意代码。它展示如何把信号交给原操作，而不是用等待界面的结束代替取消原操作。文件、定时预算与处理函数均为假设。

import { readFile } from 'node:fs/promises';
async function loadDraft(path, signal) {
  try {
    return await readFile(path, { encoding: 'utf8', signal });
  } catch (error) {
    if (error.name === 'AbortError') return null;
    throw error;
  }
}
const controller = new AbortController();
const pending = loadDraft('./draft.txt', controller.signal);
controller.abort();
const text = await pending;

这里选择 null 表示取消，真实 API 可以返回带状态的结果对象，避免与正常空内容混淆。代码没有调用解析器或保存数据，也没有证明任何实际文件被关闭。立即 abort 用来说明连线关系，不承诺每次真实竞速都由取消获胜；如果读取已经完成，后来发信号不能把既成成功改写成未发生。

超时不等于把信号送到了工作方

仅用 Promise.race 在读取与超时之间选先完成者，会让调用者较早结束等待，却不自动把取消请求送给 readFile。原任务可能继续进行。需要取消时，应显式持有控制器、传入信号，并处理原任务最终的完成或拒绝，不能让超时分支把它变成无人认领的后台工作。这里比较的是完成关系，不是性能基准。

同样，取消读取不负责撤销后续解析或已经写出的数据库记录。假设读取完成后，解析器开始处理文本，用户随后点击取消；signal 是否还能影响解析器，要看解析器有没有独立支持以及应用怎样连接。若业务需要整批撤销，还需定义提交边界与恢复协议，不能把文件层 AbortSignal 当作事务回滚。

界面可以显示“已请求取消”，随后依据任务状态更新为“已取消”或“已完成”。若工作在取消请求之前完成，应按明确策略报告实际结果，避免一边保存成功、一边提示可放心重试。给每次任务一个身份，防止旧任务的迟到结果覆盖新任务，也是调用方责任。底层取消和结果归属相关，但不能互相替代。

缓冲预算应在取消以前设计

readFile 的普通用途是把文件内容读入结果，适合已知可接受大小的文件。给它加上取消能力，不会让这条接口自动成为按块消费、固定内存的方案。若导入文件可能很大，可以评估流式读取与增量解析，但仍要预算下游缓冲、业务对象与并发任务数，而不是只看到“流”就宣称内存恒定。

本站的Node 流背压说明生产者何时暂停。这里强调取消处理的层级。背压、取消和并发上限解决不同的资源问题；某个请求停止缓冲，不证明同时存在的其他读取也停止。取消后立即无上限重试，仍可能让资源占用超出预算。

对已知小配置文件，路径形式 readFile 通常更容易表达所需读取。若需要精细控制位置、分块与资源所有权，应选择相应接口并核对文档。本文不推荐某个固定文件大小阈值，因为可接受范围取决于运行环境、编码转换、并发和解析后数据，而这些都没有在此测量。

传入 FileHandle 后，取消会替调用者关闭它吗？

不要把取消当成显式关闭。调用方通过 open 持有句柄时，应为它安排自己的关闭责任，并等待相应清理完成。同一文档的 filehandle.close 小节说明，close 会等待该句柄的待处理操作完成后关闭。调用读取与调用关闭是两个动作，AbortError 也不是关闭回执。

假设函数自己打开文件，就可在明确的清理分支等待关闭；若句柄由外部传入，函数是否有权关闭应写进接口合同。把外部共享句柄悄悄关闭，可能破坏其他使用者；反过来，双方都以为对方负责，也会留下归属空白。还要考虑清理自身失败怎样报告，不让关闭错误掩盖原始取消或读取错误。示例没有演示完整的句柄管理器，不能据此宣称这些责任已实现。

可以再用两次导入区分这份责任。假设第一次读取较慢，用户取消后马上选择第二个文件。即使第一次最终仍产生某种完成通知，界面也不应拿它替换第二次的文件名、预览和按钮状态。比较任务身份应发生在采用结果的入口，而不只是按钮点击时；取消信号是否及时生效与旧结果能否被采用，需要分别受控。

第二次任务若失败，不能把第一次的迟到成功当作自动回退，除非产品明确允许并告诉用户来源。验证应同时检查展示内容对应哪个文件，以及保存动作究竟绑定哪次导入。仅观察一次取消提示消失，没有覆盖这条交错路径。这里没有模拟真实磁盘时序，更没有给出两次任务之间的最大等待时间。

拟议验证分开检查预先取消、读取中取消、成功后才取消、普通读取错误，以及清理失败。记录 Promise 的状态、解析是否被启动、句柄清理是否完成和旧结果是否被采用，资源观测另列环境与时间窗口。本文没有执行文件读取、取消或资源测量。验收结论应限定为确实观察到的层级，不把一个拒绝结果扩大成整个磁盘、内存和业务流程都已经停止。
