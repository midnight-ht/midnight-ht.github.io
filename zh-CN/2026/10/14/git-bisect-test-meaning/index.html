二分定位到了提交，为什么还不能直接宣布根因？

二分定位依赖可信好坏判定；环境失败应区分，跳过与不稳定性保持未知，提交身份不等于根因。

正文

git bisect 的结果取决于好坏判定是否可靠。它能缩小某种可观察性质发生变化的提交范围，但测试环境失败、依赖不可用或用例不稳定，都可能让判定偏离真实回归。定位到一个提交以后，还需要检查实际差异与机制，不能直接宣布已经找到全部根因。

二分需要可信的两端与判定

Git 的 bisect 文档介绍在已知好坏提交之间搜索，也允许用于其他性质变化。自动运行时，退出码具有特定含义，其中一百二十五用于标记当前版本无法测试并跳过。不能把无法安装、无法构建与业务断言失败全部交给同一个失败码，让工具误把环境问题当成回归。

假设旧提交依赖的构建工具已不适配当前运行环境。用例还没运行，构建就结束失败；若判定脚本把这当成坏版本，二分范围会受到错误证据影响。这里没有执行仓库搜索，也不提供已经找到故障提交的记录。先验证判定程序能区分准备失败与目标行为，是安排自动搜索的前提。

已知好端也需要对应当前问题。如果团队只凭某次历史构建成功就选它，而目标功能当时从未检查，那份绿灯不能证明目标性质良好。应在可复现条件下确认两端，再记录测试输入、运行环境和判断依据，避免让搜索看起来精确，实际上从起点就没有共同标准。

无法测试时保留不确定范围

跳过提交可以让搜索继续，但靠近变化边界的版本无法测试时，可能不能唯一确定变化位置。报告应该保留候选范围与跳过原因，不把最后输出包装成完全确定结论。尝试让旧版本可测试时，也要说明临时环境或辅助修正是否改变了被测性质。

不稳定用例同样需要先处理。一次通过、一次失败的判断难以支持可靠范围缩小；机械重复运行并只取喜欢的结果，会把随机性变成假确定。是否需要重复、如何判断一致，应该由失败模式决定，不依据工具名称承诺一定找到唯一责任提交。

提交身份不是因果解释的结束

找到变化点后，应检查它怎样影响输入、状态或依赖，再用针对性验证支持原因。一个提交可能同时包含多个动作，或触发之前潜伏的条件。归责给提交作者，不能替代机制分析；修复也应说明修正了哪个条件，而不是只回退后等待问题不再出现。

拟议记录可保留判定脚本、两端提交、跳过版本、搜索日志和最终差异，方便别人重现。本文没有运行这些步骤，因此不报告定位成功。有关复盘如何让改进项具有验收条件，可阅读复盘行动与风险验证。二分提供定位证据，真正的修复结论仍要经得起失败条件的再次检查。
