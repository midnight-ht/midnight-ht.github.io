Git bisect 找到一个提交，也可能留下未确定的根因范围

git bisect 的提交结论依赖一致的性质判定；构建错误、行为回归与跳过提交需要区分。本文说明退出码契约、候选边界和因果验证。

正文

核心要点

  • 把性质、两端和测量条件写具体，避免从无关的构建失败推断行为坏了。
  • `git bisect run` 的 0、125、其他状态具有不同分类；126/127 不会自动变成“无法测试”。
  • 跳过边界附近的提交会保留不确定范围；定位提交还需要差异分析和机制验证。

git bisect 只有在两端和每个中间版本都按同一目标可靠分类时，才能把搜索缩成可信范围；构建失败、测试失败和无法测试不是同一种证据。即使它报告一个提交，也只定位了某个可观察性质的转变，仍需看差异、验证机制，不能直接宣布这个提交或作者就是全部根因。

先定义要找的性质

截至 2026-11-25 查阅的 Git git-bisect 手册页面显示版本 2.56.0（页面标注 2.56.1 无改动）；这是文档版本，不代表读者机器上的 Git 版本。手册说明它可以搜索从已知 good 到 bad 的变化，也可用 old/new 找其他性质的变化。这里的性质要足够具体，例如“同一输入下接口返回 p95 超过阈值”，而不是含糊的“系统变慢”。每个提交要按照相同输入、相同测量规则和可比环境回答这个性质是否存在。若好端从未测过目标路径，或坏端的症状并不符合判定条件，二分只会精确缩小一组错误前提。

对自动化搜索而言，判定脚本也是测量仪器的一部分。测试断言失败可以支持 bad；编译器没装、依赖源不可达、数据库没启动或测试进程没真正执行，则没有回答目标行为。把这些情况都压成非零退出码，会把“不能测”伪装成“行为坏了”。

退出码表达的是分类，不是日志摘要

Git 文档给 git bisect run 规定了退出契约：0 表示 good/old；1 到 127 之间除 125 外表示 bad/new；125 表示当前版本不能测试并跳过；其他状态会中止搜索。这个规则不检查失败日志，也不猜测是断言失败还是测试准备失败。尤其是 POSIX shell 用 126、127 表示命令不能执行或找不到，但对 bisect run 来说它们仍落在 bad/new 的数值区间，除非外层脚本先把它们映射为 125 或让搜索中止。

因此脚本必须理解测试工具本身的约定。一个只有 build && test 的短命令不一定足够：若构建失败就以 1 结束，Git 会把该提交标成 bad；若测试命令缺失返回 127，也可能被当作 bad。更稳妥的包装器先校验工具和环境，环境不可用时返回 125 或中止；只有目标探针真正运行并且满足已定义的失败条件，才返回代表 bad 的状态。探针本身如果把超时、断言错误和外部依赖故障都报成同一个 1，包装器仍然无法还原区别，必须先改进探针的分类。

一次假想搜索如何保留证据

假设团队要定位一个接口延迟变化。已知较早版本在可复现输入下符合目标阈值，当前版本超过阈值。团队把“同一请求样本超过阈值”作为 predicate，而不是仅依据一次监控截图。每个候选提交都固定请求样本、测量步骤和依赖服务版本，记录实际数值与环境。

搜索中有一版旧构建工具在当前环境无法启动。包装器确认失败发生在接口探针开始以前，把该版本标记为 untestable，按文档使用 125 跳过；其他候选上，探针能运行且稳定复现超阈值时才标记 bad，符合阈值时标记 good。这是说明分类过程的假设例子，没有运行 git bisect 或某个服务测试，也没有得到实际回归提交。

如果跳过的是靠近 good/bad 变化边界的提交，Git 文档明确警告，可能不能唯一确定第一个 bad 版本。此时应记录最后一个已确认 good、最早的已确认 bad、跳过的提交和可能边界；不能把工具输出中较近的某个提交包装成唯一答案。若环境可以修复，也要确认修复只让旧版本可构建，没有改变延迟性质本身。否则测到的是“加了兼容补丁后的版本”，其结论适用范围更窄。

定位结果还要经过因果验证

一个提交可能同时改了查询、缓存和日志；回归也可能来自更早改动与新配置的交互。Git 的二分是基于提交历史和给定判定做定位，它不会读懂业务机制。编辑判断：若目标性质沿历史多次变化，例如先慢、后快、又慢，单一“首个 bad”问题要先改写成要找的那一次变化，或分别搜索明确的时间区段。把提交身份直接等同于根因，会跳过这一步。

定位后检查候选差异，找出能解释目标输入为何越过阈值的具体路径，再设计能区分不同机制的验证：关闭某项变化、固定依赖版本、比较相同输入下的查询计划，或把候选改动拆开重放。这些动作是后续因果分析方案，不是二分自动提供的证据。简单回退后症状消失是线索，但如果回退同时撤销多个改动，就不能证明其中哪一个是必要原因。

保存可纠正的搜索记录

至少保留两端提交及其验证方式、predicate、Git 版本、环境镜像或依赖锁定方式、每个候选提交的分类、跳过原因、脚本版本、输出日志和最终差异。对于超时或波动测试，还要保存重复次数与分类规则，避免别人只看到最终 bad 标记却无法判断证据强度。Git 提供 git bisect log 记录会话；发现误判后，可编辑记录并用 git bisect reset、git bisect replay 重建纠正后的会话。记录可重放不等于实验自动可复现，环境和测量输入仍要留档。

验证结果应写成有边界的结论：“在该环境、这些端点与该 predicate 下，变化位于已确认 good 和 bad 的这个范围；其中某提交解释了目前观察到的差异，原因由后续验证支持。”若中间有跳过版本，就把候选范围留在结论中。关于定位之后如何给修复动作安排验收，可参见复盘行动与可验证的风险降低。本文没有对当前仓库运行搜索；案例和分类步骤都是审查方法，不是一次已完成的排障记录。
