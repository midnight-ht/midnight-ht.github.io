镜像中的文件换了，挂载卷里为什么还是旧内容？

Docker 只会在空卷首次挂载时默认复制目标目录内容；已有卷会遮住新镜像文件。本文给出核对挂载、迁移状态与安全回退的方法。

正文

核心要点

  • An empty volume copies destination contents by default; a non-empty volume masks image files, while volume-nocopy disables that empty-volume copy.
  • Inspect the actual mount source and destination before concluding the image update failed.
  • Docker does not migrate persistent business state when an image changes; test ownership, recovery and rollback separately.

更新镜像里的文件，不会持续同步到已经挂载的卷。Docker 官方文档说明：一个空卷挂到容器已有内容的目录时，Docker 默认会先把目标目录中的文件复制进卷；等卷有了自己的内容，后续挂载会用卷遮住镜像同一路径。容器重建、镜像升级和数据迁移是三件不同的事。遇到“镜像明明更新了，容器里还是旧文件”，先查实际挂载类型、卷身份和目标路径，再决定要不要迁移数据；不要先删卷或覆盖用户状态。

先分清镜像目录、容器可写层和卷

同一个容器路径可能看起来只有一份文件，实际却由不同存储来源提供。镜像层保存构建时写入的默认文件；容器可写层记录该容器自己的变更；卷由 Docker 管理，可在容器被删除后继续存在；bind mount 则把 Docker daemon 所在主机的某个路径挂进容器。它们的生命周期和文件所有权不同。挂载发生时，目标路径显示的是挂载源的内容，而不一定是镜像里原本位于那里的一份文件。

这会造成两种方向相反的误判。一个新建的空卷挂到有默认模板的目录，第一次启动时看起来像“Docker 自动把镜像文件写到了数据卷”；这确实是卷初始化的默认行为。之后把镜像模板升级，却仍挂载同一卷，容器显示的可能还是卷里初始化时的版本。另一个情况是卷本身并非空的，挂载会遮住镜像底层文件，所以在容器中看不到镜像里已经更新的新版本。两者都不证明镜像拉取失败，也不证明文件损坏。

Docker 官方卷文档把这两条规则分别写在挂载现有数据和挂载选项中：非空卷遮住容器目录中原有文件；空卷默认接收目标目录内容；volume-nocopy 可以关闭这次复制。这个选项改变的是空卷初始化方式，不会为已有卷执行合并或升级。若禁用复制，应用必须有自己的初始化路径；目标目录为空时应用的行为需要另外验证。

用一次模板升级走完排查

设想一个应用把默认通知模板随镜像发布在 /app/templates，首次部署时使用一个空的命名卷 notice-data 挂到同一路径。Docker 在首次挂载时将当时的模板复制进空卷。镜像之后改了模板措辞并构建了新版本，但部署仍然把 notice-data 挂回 /app/templates。新镜像带着新模板，卷保留旧模板；容器看到卷的文件，所以界面继续显示旧内容。这个过程是基于文档机制的假设示例，没有在本站或任何生产环境运行。

排查时先确定运行中的容器实际挂载了什么。可以查看容器 inspect 信息里的 mount type、name/source 和 destination，再确认应用读取的路径是否正好等于挂载目标。若类型是 volume，继续核实卷名和卷 inspect 信息；若是 bind mount，检查主机源路径。对于 Docker Desktop 或远程 daemon，bind mount 指的是 daemon 一侧可见的路径，不一定是当前终端所在客户端的同名目录。Docker 的 bind mount 文档对此有说明。容器里的文件名和镜像标签只能证明最终看到了什么，不能单独识别这些字节来自镜像、卷还是主机目录。

再把镜像默认文件与卷中的文件分别取证：记录镜像 digest 或构建标识、卷身份、挂载目标、文件内容哈希或内部版本标记，以及应用实际读取的配置路径。若对照发现卷中保留的是首发模板，而新镜像里的路径确实更新，问题是默认文件升级责任没有定义，不是 Docker 应自动同步却漏做。若文件不是来自预期卷，则继续查部署定义和运行容器，而不是先调整复制选项。建议在测试环境用新建的卷和样本文件重现；不要用用户的持久卷来验证机制。

默认文件可以复制，业务状态需要迁移契约

有些目录适合默认复制，例如首次运行的只读词典、静态模板或可安全重建的初始配置；有些目录含有用户编辑、数据库文件、上传物或应用运行后生成的状态。把二者放在同一持久目录，会让镜像默认值与卷内真实状态争夺文件所有权。更新镜像时简单复制新模板可能覆盖用户调整；完全不复制则可能让新配置项缺失。选择前先给每类文件标注所有者、能否重建、升级顺序、回退兼容性和是否允许覆盖。

一个更容易演进的安排是把随版本发布的默认模板保留在镜像只读路径，把需要保留的数据放到卷内单独的数据路径。应用启动时读取模板和数据各自的来源，并对用户状态执行明确版本迁移，而不是假设 Docker 会持续更新卷。若必须把默认文件初始化到卷，应保存初始化版本或迁移标记，检查目标文件是否已有用户改动，并让迁移具备幂等性：重复启动不会重复追加或覆盖；部分失败可被识别；下次启动知道从哪个步骤恢复。标记应在迁移数据与校验完成后写入，不能先记录完成再中断写入。

迁移之前需要知道怎样恢复。Docker 官方文档提供卷备份、还原和迁移示例；生产流程仍需自己确定静止写入时机、快照一致性和恢复验收。仅把一个归档文件生成出来，不等于已经验证恢复。若数据可以在线写入，备份过程中还要考虑并发修改；若迁移不可逆，升级记录应包含旧镜像能否读取新数据，或明确安排数据快照与回退转换。恢复旧镜像只会换回代码；它不会自动把卷恢复到旧内容。旧程序若不兼容已迁移数据，镜像回退可能启动失败或误读状态。

volume-nocopy、空卷和删除卷分别解决什么

volume-nocopy 适合应用需要一个真正空的卷，并由自身初始化逻辑填充的场景。

需要再区分“空卷状态”与“曾经挂载过”：默认复制取决于挂载当下的卷是否为空以及本次是否启用 volume-nocopy，不是 Docker 为某个卷永久记下一次性迁移标记。若此前某次 volume-nocopy 挂载后应用没有写入数据，这个卷仍然为空；以后在没有该选项的情况下把它挂到有文件的目标路径，应按新的挂载条件重新核对是否会初始化复制。不要把过去使用过哪个参数当成卷内容当前状态的替代证据。它不等于“每次挂载都采用镜像目录”，也不会把已有卷替换成镜像内容。如果应用误以为模板已由 Docker 准备好，关闭 copy-up 后会遇到缺文件；这类故障应该由启动检查明确报告，不能悄悄创建一个不完整的空配置。

删除并重建卷也不是通用的修复按钮。卷可能同时保存用户更改或业务记录，且容器删除和卷删除在 Docker 文档中是分离的生命周期操作。删卷会让原有数据路径发生变化。只有先确认数据归属、做好经验证的备份，并获准放弃或迁移旧卷，才考虑新建卷。排查阶段可使用只读检查、隔离环境或新的测试卷；不要把 volume prune 一类清理动作当作查看文件版本的方法。

验收应覆盖首次、复用和回退

可在隔离的测试环境创建一个空卷，把带有 template-v1 标记的镜像目录挂进去，检查首次挂载后的目标路径，再构建一个带 template-v2 的镜像并复用同一个卷，观察卷是否仍提供原内容。随后再换一个明确的新空卷，看首次复制结果；若配置了 volume-nocopy，则确认目录确实为空且应用能安全初始化。这个测试区分“首次复制”“已有卷遮蔽”和“关闭初始化”三种行为，不会把删除生产卷当成测试前置条件。本文没有运行该测试，因此它是验证方案，不是已通过结果。

对持久业务数据还要额外测试迁移中断后的再次启动、重复执行、备份恢复和旧镜像读取。记录镜像 digest、卷名或 ID、挂载来源、迁移版本、输入输出检查点与结果文件哈希。日志里的“启动成功”不能证明使用了新模板；容器内的路径内容也不能说明其来源。只有路径、来源、版本和应用行为对得上，才能判断更新是在镜像、卷初始化还是数据迁移的哪一层生效。

相关的配置更新与实际消费讨论配置已投递后应用是否真正读取；本文解决的是镜像路径与挂载存储由谁提供文件。镜像更新成功、卷中内容变化、迁移完成和业务采用新配置是不同状态，应该分别留证。
