每组只取一条，排序才真正定义“代表行”

PostgreSQL DISTINCT ON 按组内排序保留第一行。把候选资格、业务优先级、并列和最终展示顺序分开定义，才能说明这行代表什么。

正文

核心要点

  • DISTINCT ON 只保留排序后的组内第一行；资格条件、业务优先级和并列规则仍需由产品定义。
  • WHERE 会改变候选集合，内层挑选顺序与外层展示顺序是两份不同契约。
  • 用并列、空时间、迟到数据、无候选和分页案例验证；SQL 与 EXPLAIN 示例本文均未执行。

每组只取一条记录时，先定义这条记录代表什么。PostgreSQL 的 DISTINCT ON 只按排序保留每组第一行；它不会替产品决定哪种时间叫“最新”、哪些状态有资格、并列时谁优先。把候选资格、业务优先级、平局处理和最终展示顺序分别写清楚，查询才可解释。

第一行来自排序，也受候选资格影响

本文核对的是 PostgreSQL 19 的 SELECT 文档；该版本于 2026-11-19 发布，文档说明，DISTINCT ON (device_id) 在设备 ID 相等的行中保留第一条。若 ORDER BY 没有保证目标行先出现，选择不可预测；DISTINCT ON 表达式还必须匹配 ORDER BY 的最左侧表达式。后续排序项才表示同一设备内部的优先级。DISTINCT ON 是 PostgreSQL 的扩展，不是可直接移植到每种数据库的标准 SQL。

假设报告表记录设备、报告时间、接收序号、发布状态与唯一的 report_id。产品说“显示最新报告”时，报告时间可能是源系统声称事件发生的时间；接收序号表达系统何时收到它。迟到消息可能先发生、后到达。页面若用于还原事件时间，应按报告时间选；若用于解释系统最近观察到什么，则接收时间可能更符合问题。不能仅凭字段都叫时间就互换。

同一时间出现两份报告，还要有业务上的优先级。若经审核的版本应优先，可以先按审核状态排序；最后再用唯一 report_id 打破剩余并列。唯一键能让结果在相同输入下稳定，却不能证明这个平局规则合理。若需求是保留所有并列第一，不能再用唯一键把它们变成唯一赢家。

候选过滤会改变“最新”的意思。WHERE visibility = 'published' 表示只在已发布报告中选择最新一条；它不是“所有状态中最新的一条”。如果最新报告正待审核，过滤后页面会回退到旧的已发布报告。产品需要的究竟是“最新可见版本”还是“最新状态”，应先定下来，再选择在排序前过滤，还是选出代表行后再展示状态。SQL 谓词放在何处，就是集合定义的一部分。

空时间不是无关紧要的默认值

排序章节说明，降序默认 NULLS FIRST。若未知报告时间应排在已知时间之后，需要明确写 NULLS LAST；另一种选择是在候选条件中排除空时间，但那会让某些设备没有代表行。若一个组的时间全为空，接收序号或 ID 仍可决定一条稳定记录，却不能让未知时间变成已知时间。产品应决定是显示“时间未知”的候选，还是展示没有可选报告。

此外，组内所选记录的所有字段必须来自同一行。GROUP BY device_id, MAX(reported_at) 可以计算每组最大时间，但最大时间不携带那一行的状态和载荷。将它再连接回原表，若两行共享最大时间，就会返回两行；如果查询继续用任意 LIMIT 1 截断，未定义的选择只会转移到另一个位置。需要组汇总时应保留聚合语义；需要一份完整报告时应选中同一行的字段。

用排序次序表达一个完整选择

假设产品定义为“每台设备最新的已发布报告；事件时间相同则选后来接收的；全部仍并列时以唯一 ID 稳定结果”。对应的查询草案如下，本文没有连接数据库执行：

SELECT DISTINCT ON (device_id)
       device_id, report_id, reported_at, received_seq, status, payload
FROM device_report
WHERE visibility = 'published'
ORDER BY device_id ASC,
         reported_at DESC NULLS LAST,
         received_seq DESC,
         report_id DESC;

这个排序从设备组键开始，满足 DISTINCT ON 的最左前缀约束；然后按事件时间倒序、明确把空值排后，再按接收序号倒序，最后按假设唯一的 report_id 决定剩余并列。这里每个字段都对应一条能向产品解释的规则。若“最新”要表达系统收到时间，就替换业务时间字段；若待审核报告也必须成为“最新”结果，不能在 WHERE 中提前排除；若审核状态本身优先，就把状态规则放入时间之前，并同步改变产品对“最新”的解释。

组内选出代表行后，如何再按全局时间排序而不改变选中规则？

上面的 ORDER BY device_id, ... 首先用于让数据库挑出每组的代表行。它不会让最终页面自动按所有设备的报告时间从新到旧排列。PostgreSQL 关于查询行排序的文档指出，结果只有在明确指定外层 ORDER BY 后才有可依赖的输出顺序。可将组内选择包进 CTE，再在外层排序：

WITH chosen AS (
  SELECT DISTINCT ON (device_id)
         device_id, report_id, reported_at, received_seq, status, payload
  FROM device_report
  WHERE visibility = 'published'
  ORDER BY device_id ASC,
           reported_at DESC NULLS LAST,
           received_seq DESC,
           report_id DESC
)
SELECT *
FROM chosen
ORDER BY reported_at DESC NULLS LAST, device_id ASC;

内层排序决定每组留下哪一条，外层排序决定这些代表行如何呈现；两者不冲突，也不能互相替代。对应的验收要分别问：所选 report_id 是否符合每组业务优先级？页面是否按全局时间排序？只看最终屏幕上的顺序，无法证明组内选对了行。

哪些需求更适合窗口函数

若查询要每组前 N 条，row_number() OVER (PARTITION BY device_id ORDER BY ...) 可把每个组内的顺序显式编号，再由外层过滤 row_number <= N。如果并列第一必须全部保留，rank() 可保留相同排序键的并列名次；把唯一 ID 放进排名排序又会拆开并列，因此需要根据“恰好一条”还是“全部同级”选择函数。窗口函数与 DISTINCT ON 都不会替业务决定候选过滤、空值位置或排序语义。

如果需要可跨数据库迁移的写法，窗口函数通常比 PostgreSQL 专属 DISTINCT ON 更容易适配，但目标数据库的窗口语法与执行计划仍需确认。若需求是平均值、总额或所有异常成员，窗口函数与 DISTINCT ON 都不应被误作代表行查询；聚合或保留完整成员才符合输出要求。选择语法的依据是结果契约，不是偏好较短 SQL。

设计能改变赢家的验证案例

给同一设备准备不同报告时间、相同时间但状态不同、接收顺序与事件时间相反、空时间以及所有时间都为空的情况。再加入没有已发布候选、刚出现待审核新版本，以及多条同时间并列的输入。每个组先写下期望 report_id 与理由，然后检查输出是否符合候选、优先级、平局与全局展示规则。只有一个候选的测试组无法暴露缺失的排序条件；测试应改变可能改变赢家的字段。

查询计划是另一个问题。索引排序章节指出，B-tree 可以提供排序输出，但规划器会在索引扫描与显式排序之间权衡；读取大量数据时，显式排序可能更合适。因此先在实际数据和参数上观察 EXPLAIN，再决定索引列顺序及是否覆盖空值排序。本文没有运行 EXPLAIN 或基准测试，不对性能提升作断言。若结果要分页，页间稳定性另有排序契约，可参阅分页与排序边界；它与每组挑选代表行需要分别验收。
