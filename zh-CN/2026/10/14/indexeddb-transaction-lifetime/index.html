await fetch 后还能用旧 IndexedDB 事务写入吗？先看它的状态

IndexedDB 请求处理完并回到事件循环后，旧事务可能自动提交；网络等待应放在短本地写事务之前。

正文

核心要点

  • 事务对象仍被引用，不表示事务仍处于 active 状态。
  • 先完成网络请求，再在短事务中校验本地 revision 并写入。
  • 请求 success、事务 complete 与服务端副作用是不同状态。

如果 IndexedDB 请求已经处理完、没有其他数据库请求待处理，代码随后等待 fetch()，那么恢复后再用旧事务写入可能已经太晚。原因不是 await 语法一出现就必然关闭事务，而是 IndexedDB 事务按自己的活动状态和请求队列运行：控制权回到事件循环后，事务可能进入自动提交。此时 JavaScript 变量还引用着 IDBTransaction，并不能把它重新变成活动状态。更可靠的顺序是先完成网络等待，再建立短事务，并在事务内核对本地版本后写入。

事务对象存在，不代表还能继续发请求

IndexedDB 把事务状态分成 active、inactive、committing 和 finished。W3C Indexed Database API 3.0 草案写明：事务创建时为 active；关联请求派发 success 或 error 事件期间也会重新 active，脚本可以在这个事件处理器里继续排入请求；控制权回到事件循环、当前没有请求事件派发后，事务变为 inactive。inactive 状态不接受新请求。待处理请求全部完成且结果已处理、没有排入新请求时，用户代理必须尝试提交。这个生命周期不等于一个 async 函数从进入到返回的时间。该规范页面当前标注为 2026-10-30 的 W3C Working Draft，仍是工作草案；这里引用它说明规范文本状态，不把草案说成已发布的 Recommendation。 Indexed Database API 3.0，§2.7.1

MDN 的 IDBTransaction 参考也说明，事务在创建任务和请求成功、错误事件处理任务里活动，其他任务中不活动；若活动时没有新请求且没有其他未完成请求，会自动提交。关键是状态转换与请求，而不是变量是否还在作用域中。事务仍是可引用的对象，但它可能已经提交，或者已处于不允许排入请求的状态。transaction.objectStore("drafts").put(...) 在这种情况下会抛出状态错误；错误发生在后续 put 处，不代表 fetch 本身失败。

为什么外部等待容易越过本地事务边界

把时序拆开看更清楚。页面创建 readwrite 事务并从 drafts 读取一条记录；读取请求成功后，浏览器派发 success 事件。若处理器没有排入下一个 IndexedDB 请求，读取请求也已完成，事务就没有待处理工作。控制权离开事件任务后，浏览器可以尝试提交。与此同时，业务函数正在等待网络服务器返回预览数据；几百毫秒后 Promise 才恢复，函数此时拿着的仍是旧事务引用。要把新结果写入，就需要一个仍然接受请求的事务，因此旧引用不能承担这一步。

这是一个解释状态顺序的假设场景，不是本次执行过的复现。规范允许在请求事件处理期间继续排请求；因此“只要 await 就绝对不行”会误导读者。若 Promise 由某个 IndexedDB 请求封装而来、续写发生在请求事件所关联的处理时段，具体调度与封装实现也需要按实际代码核实。更稳妥的判断不是看源码里有没有 await，而是问：从这笔事务创建到下一次 .get() 或 .put() 之间，是否让事件循环继续运行了？此前的 IDB 请求有没有全部处理完？后续请求有没有在事务仍 active 的时机排入？MDN 的 IndexedDB 使用指南特别强调事务依赖事件循环，并且在返回事件循环且没有继续提出请求时会失活。

不要用定时器、空请求或循环写入来“保活”。这种做法会把一次短小的本地原子操作改成持续占有事务的工作，还让并发读写的范围更难估计。它也无法让远程 HTTP 操作加入 IndexedDB 的原子提交：服务器已经收到请求、写入数据库失败时，浏览器回滚不了服务器副作用。保持事务短，才容易说清楚哪些更改一起提交、哪些仍需补偿。

先等待远端，再在本地事务中检查版本

假设编辑器要向服务端请求一个预览，并把预览写回本地草稿。可以先请求远端，再打开一个 readwrite 事务；事务里读取草稿的当前版本，并在同一请求成功处理器中决定是否写入。以下顺序是设计示例，未在浏览器里运行：

const response = await fetch(previewUrl);
if (!response.ok) throw new Error("preview request failed");
const preview = await response.json();
if (taskId !== currentTaskId) return; // 用户已切换或取消

const tx = db.transaction("drafts", "readwrite");
const store = tx.objectStore("drafts");
const read = store.get(draftId);
let stale = false;
read.onsuccess = () => {
  const draft = read.result;
  if (!draft || draft.revision !== requestedRevision) {
    stale = true;
    tx.abort();
    return;
  }
  store.put({ ...draft, preview, revision: draft.revision + 1 });
};
tx.oncomplete = () => showSaved();
tx.onabort = () => stale ? showConflict() : reportStorageFailure(tx.error);

这里有两个不同保护。请求开始前记录 taskId，防止用户切换页面后旧 Promise 把结果写到新界面；读取成功事件里再比较 revision，避免网络等待期间本地草稿已被另一个编辑动作更新。读取和 put 都在同一笔事务里，版本比较之后才排入写请求；这比在事务外检查版本、随后另开事务写入少了一段竞态窗口。若数据库里草稿不存在或版本不一致，示例主动中止，并把它作为“过期结果”展示，而不是静默覆盖本地内容。失败时保留编辑器内尚未提交的文本，给用户重新获取预览、合并或放弃的选择。

读写事务的 scope 应只包含确实要操作的 object store。IndexedDB 不会替应用跨网络请求和本地存储协调一致性。若还要向服务器发送动作，可先把本地草稿与一条带稳定业务键的 outbox 意图写进同一笔事务；等 complete 后再发送，服务端按该键去重。这样仍不是分布式事务：发送成功但回执丢失时，重试去重和状态对账仍由应用与服务端契约负责。对一个缓存预览来说，简单重试通常足够；对扣款、外部消息或不可逆动作，则需要服务端幂等键、对账记录和明确的补偿流程。

请求成功、事务完成与持久化承诺是三件事

IDBRequest 的 success 事件只说明那一个请求成功取得结果或被数据库处理；同一事务后续请求仍可能失败。应用若在首条 put 的 success 事件里显示“全部保存完成”，说得太早。应在建立事务时就注册 complete 与 abort 处理，然后以事务 complete 作为这组本地请求成功提交的边界。MDN 的 complete 事件文档将其定义为事务成功提交后触发；W3C 草案也描述待处理请求完成、处理结果且没有新请求后尝试原子提交。失败请求如未由脚本按 IndexedDB 错误事件规则处理，可能使整笔事务中止，应用需要把 abort 当成整体失败检查。

事务 complete 也不应被扩大成“任何情况下数据都已永久写入硬盘”或“远端已同步”。IndexedDB 的 durability 选项是用户代理在提交时考虑的提示；默认行为由实现决定。文章只陈述页面可观察到的事务成功，不替代各浏览器对持久化的承诺，也不代表服务端动作已完成。关闭页面、存储配额耗尽、设备故障和浏览器清理都属于不同问题。若产品需要更强的保存承诺，应核对目标浏览器实际支持的 durability 选项、用户代理行为以及服务端副本策略，而不是延长一个事务来等待网络。MDN 的 IDBDatabase.transaction() 文档列出 transaction scope、模式与 durability 选项，并提醒传入的对象存储范围应限制到实际需要的集合。

怎样验证这条边界

针对目标浏览器运行一个可控测试：先发出一个 IDB get，确保该请求 success 后不再立即排入请求，然后让 fetch 由测试服务延迟返回，再尝试使用旧事务写入；分别记录 get success、事务 complete 或 abort、网络响应和写请求事件的先后次序。第二组测试在 get 的 success 处理器里同步排入 put，确认该事务可以在请求事件期间继续扩展。第三组让写请求触发唯一索引冲突，确认应用观察到事务 abort，而不是把前一条请求 success 当作整组成功。最后测试用户取消、版本冲突、网络超时和重试去重。上述步骤是待运行的验证方案，不是本批次已经执行的浏览器测试；不同引擎与封装库需要按实际部署矩阵记录。

实际实现时，把网络等待、JSON 解析、用户取消与任务身份检查放在本地事务之前；把相关本地读取和写入集中在范围窄、时间短的事务内；并把“本地事务完成”“服务端收到动作”“服务端已对账”作为分开的状态。只有后一段本地数据库操作才由 IDBTransaction 保护。页面异步结果的任务身份问题也可参看取消请求与旧结果提交。
