为什么调用 `sort()` 后，原数组的顺序也变了？

`sort()` 会修改原数组并返回同一引用；复制可保留容器顺序，但不会自动隔离数组中的记录对象。

核心要点

  • sort() 修改数组容器；变量名不同不代表数组引用不同。
  • toSorted() 或浅拷贝只创建新容器，记录对象仍可能共享。
  • 选择按容器所有权、比较器契约、目标运行时和字段归属决定，并在实际环境验证。

因为 Array.prototype.sort() 会就地改写被调用的数组，并返回同一个数组引用。只要时间线、缓存或另一个组件仍持有这份数组，它就会观察到新顺序。若要生成仅供某个视图使用的排序结果，应先决定谁拥有原数组；toSorted() 或复制后再 sort() 能保留容器顺序，但浅拷贝不会隔离数组中的对象记录。

同一数组被谁持有

设订单服务给页面一份 orders。时间线按创建时间显示，金额排行按金额显示。如果两个模块都拿到同一个数组对象，金额排行执行 orders.sort(compareByAmount) 后，改变的是这份数组本身。变量名不同、组件不同，都不会自动复制底层数组。时间线下一次读取时，看见的是已经按金额排列的顺序；若它此前保存了单独的索引或分页游标，视图还可能出现顺序与游标不匹配。

可以把关系画成“时间线 ─┐”“金额排行 ─┴→ 同一个数组”。sort() 的返回值仍指向右侧这一个对象，而不是另一个排序视图。这是一个语义示例，没有在某个框架或浏览器里运行，也不声称发生过真实线上故障。它说明排查时要问的是“谁持有这份容器”，而不是只问“谁调用了排序”。

调用代码可以把这种影响藏在短表达式里：

const ranking = orders.sort(compareByAmount);

ranking 看起来像新结果，其实和 orders 指向同一个数组。再次对 ranking 排序，原 orders 也随之变化。MDN 对 sort() 的说明明确写出它返回原数组引用；因此如果函数承诺“返回一个视图”，却对输入调用 sort()，实现就违背了调用者可能依赖的所有权边界。

复制容器没有复制订单

若把结果改为 orders.toSorted(compareByAmount)，新数组拥有独立的顺序，原数组的排列保留。运行环境较旧、不支持 toSorted() 时，也可用 [...orders].sort(compareByAmount) 或 Array.from(orders).sort(compareByAmount)。MDN 将 toSorted() 标为自 2023 年 7 月起跨浏览器广泛可用；这不替代项目运行时、嵌入式 WebView 和测试环境的兼容检查。

但这只是浅拷贝。新数组中的订单对象仍可能与原数组共享引用；排序后，同一对象可能出现在不同的索引位置。若金额排行为了显示临时标签而写入 sorted[0].displayAmount，原数组中对应位置的对象也会出现该字段。这样，时间线顺序没有被改，订单记录却仍被共享修改。要不要复制每条记录、采用不可变数据，或只在渲染层计算标签，应由字段的业务归属决定，不能从“用了 toSorted()”推出“数据已隔离”。

这一区别也影响故障诊断。若第二个列表顺序变化，先追踪数组容器引用和所有排序调用；若顺序没变但记录字段变了，再追踪对象引用和字段写入。把两类变化统称为“深拷贝问题”，容易把修复放在错误层。关于结构化复制和资源转移的另一种所有权机制，可参阅结构化克隆与资源转移边界；它们并不是每次列表排序都应采用的替代方案。

比较函数决定的顺序也有契约

不传比较函数时，sort() 会把元素转成字符串，再按字符串顺序比较。MDN 给出的数字示例中，默认排序得到 [1, 100000, 21, 30, 4]，而不是数值升序。若金额是数字，应显式写出比较方向，例如 (a, b) => a.amount - b.amount；如果金额可能缺失、为 NaN 或以不同类型进入，还要单独定义这些值排在前面、后面还是被拒绝。

ECMAScript 要求排序比较器保持一致。对同一对值应返回同一结果，比较过程不应修改被比较对象；自反、反对称和传递关系也要成立。比较器的调用顺序和次数由实现决定，所以不能在比较器里递增业务计数、发请求、修改对象或依赖“先比较哪两项”。一个常见错误是 (a, b) => a > b ? 1 : 0：当 a 大于 b 时返回正数，交换参数却仍可能返回零，破坏反对称性。MDN 展示了这种比较器在 V8、JavaScriptCore 和 SpiderMonkey 中产生不同结果的例子。排序结果不一致时，修正比较器比更换引擎更接近问题根因。

自 ECMAScript 2019 起，排序是稳定的：比较结果为零的元素保持它们在排序前的相对顺序。稳定性有用，但不等于业务顺序天然可重复。如果同金额订单此前来自不确定的分页合并顺序，那么稳定排序只会保留那个不确定顺序。需要跨请求一致时，应把明确字段加入排序键，例如先按金额、再按创建时间、最后按不可变订单 ID 排序。稳定性保留已有顺序；比较器的次级键才定义相同金额时的产品规则。

何时复制，何时原地排序

如果数组来自缓存、状态容器、函数参数，或会被多个视图读取，默认把排序结果视为派生数据：用 toSorted()，或先浅复制再排序。若代码独占一份临时数组，排序后不再需要原始排列，并且调用约定允许修改输入，原地 sort() 可以更简单。这里的选择依据是所有权和生命周期，不是“不可变总是更快”或“原地总是省内存”这样的未经测量结论。复制会额外保留一个数组容器；排序算法的临时空间与实际成本还取决于运行时和数据规模，应在目标环境测量。

还要把排序容器与行对象的职责分开。如果金额排行只改变呈现次序，不应顺手写回业务记录；如果用户执行的是“永久调整优先级”，这就不是纯展示排序，应走明确的保存操作、权限校验和冲突处理。界面操作的表述也应与数据动作一致：预览排序与保存排序不能共用一段含糊逻辑。

怎样验证顺序所有权

可为现有测试设计一个最小矩阵：准备有稳定 ID 的订单，记录输入 ID 序列；调用排序视图函数后，再检查输入序列是否保持原样。然后检查排序结果是不是一个新容器，并确认它的订单对象是否仍与输入对象相同。最后分别测试相同金额的并列项、缺失金额、默认比较器反例，以及另一个消费者在排序后读取到的顺序。比较器可单独用成对和三元组样本检查符号反向与传递关系，避免把引擎某一次输出当作证明。

这些是建议的验证步骤，本次历史稿重写没有执行浏览器、Node.js 或业务测试，也没有测量内存和性能。若测试通过，只能说明所用数据和运行环境下这些断言成立；它不能证明所有消费者都已找到，也不能证明共享记录字段不会从别的写入路径变化。长度、对象身份和生命周期三条线分别记录，才有助于把“顺序被改”定位为数组容器副作用，而不是误判成排序算法随机或复制方法失效。
