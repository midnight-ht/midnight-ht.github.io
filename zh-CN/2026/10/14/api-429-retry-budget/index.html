收到 429 后，什么时候重试才有依据？

429 说明请求受到限流，不会替客户端决定重试次数。结合 Retry-After、请求副作用、取消和总时限，设定有上限的重试与清楚的结束状态。

正文

核心要点

  • 429 的配额范围并未由状态码规定，Retry-After 也不是成功承诺。
  • 只有请求允许重放且整体截止时间、取消状态和剩余预算都允许时，才安排下一次请求。
  • 服务端等待提示不能被客户端提前缩短；达到期限后应停止并给出查询或恢复路径。

收到 HTTP 429 后，客户端不应立刻再发一次相同请求。该状态表示一段时间内请求过多，服务端可以在响应中提供 Retry-After；这个提示可能不存在，也不保证等待结束后下一次调用会成功。客户端必须把它与请求能否安全重放、用户是否取消、整项操作还剩多少时间，以及重试预算一起判断。本文所举的批处理场景是推演，不代表真实系统或已执行的压测。

状态码说明了什么，没有说明什么

RFC 6585 第 4 节规定，429 表示用户在一定时间内发送了过多请求；响应内容应说明触发条件，并且可以带 Retry-After。但标准没有规定服务端如何识别“用户”或如何计数。配额可能按单个资源、凭据、整个服务器或一组服务器计算。因此，看到某次请求收到 429，不能据此得出“这个账户每秒固定能发几次”或“每个浏览器标签页各有一份配额”的结论。服务文档没有公开的部分应继续标为未知，而不是填进客户端常量。

429 也不是业务成功或失败的通用证明。读请求通常可以按接口契约重新获取；写入请求是否可以重放，则取决于服务端怎样处理幂等键、重复提交以及操作结果查询。假如请求在网络中断前已经被处理，但响应没有到达客户端，随后某个错误响应或网关超时就不能单独证明副作用没有发生。重试预算负责限制继续施压，幂等契约负责解释重复操作是否会造成第二次效果，两者不是同一个控制。关于后一边界，可参阅本站超时与业务幂等说明。

另一个容易忽略的标准边界是缓存。RFC 6585 规定 429 响应不得存入缓存。这并不意味着所有中间层配置都自然正确；实施仍要核对客户端缓存、代理行为和接口文档，不能把某个缓存命中误判成新的服务端限流信号。

Retry-After 是等待依据，不是结果承诺

RFC 9110 第 10.2.3 节规定，Retry-After 可用 HTTP 日期或非负整数秒表示。RFC 6585 对 429 说服务端“可以”发送它；因此缺少字段并不自动代表零等待。若字段语法无效，客户端也不应把解析失败悄悄变成立即重试。具体兜底由客户端策略决定，可以进入本地退避，也可以将本次交互结束为待后续查询，但不应伪造服务器给出的精确时间。

例如，假设一个交互式批量导出收到 Retry-After: 8，而整个前台操作只给十秒截止时间。等待八秒之后只剩两秒，还要容纳下一次连接、服务处理和响应。如果请求本身必须多次上传内容，或者每次尝试还有独立超时，两秒显然不足以保证完成。合适的行为可能是遵守服务端等待下限，停止前台重试，并显示“稍后查询”或“在任务页恢复”的路径。不能为了让界面看起来更积极，把八秒缩成两秒后提前请求；也不能说“服务器稍后会成功”，因为提示只谈等待，不承诺届时配额空出或服务成功。

截止时间需要覆盖整个业务操作，而不只是单次 HTTP 连接。客户端可以把它拆成：单次尝试上限、重试之间的等待、总尝试次数和最终截止时刻。每次准备重试前，重新计算 deadline - now，确认等待之后还剩下足够时间完成一次尝试；如果用户已经取消，任务就进入取消状态，不再因定时器到期而继续请求。这个判断是客户端的产品策略，需依据实际接口的响应时间和用户可接受时长制定；本文没有给出通用秒数。

多个调用者为何需要退避与预算

一个账户可能同时在多个标签页、后台刷新器和服务端作业中发请求。每个调用者都认为“只重试一次”，若它们在同一时刻收到 429，又安排同一时刻再次请求，就可能形成新的尖峰。Google 的 SRE 手册把随机化指数退避和限制每次请求的重试次数列为避免级联故障的建议。这是工程建议，不是 HTTP 标准规定的 429 客户端算法。

策略可以按提示来源区分：有有效 Retry-After 时，把该值当作不能提前的等待下限，再在允许范围内加入随机分散；无提示时，使用有上限的本地退避并为单次请求设置有限次数。采用随机值的范围、指数增长倍率和最大次数要按实际服务配额、用户任务长度和系统容量评估，不能从示例直接抄成“最佳参数”。若同一个账户下的多个调用确实共享配额，服务端或协调层还可以考虑共同的限流状态；把状态共享到所有租户会误伤彼此独立的配额，而完全不共享则可能协调不了同一账户的重试。选择共享粒度之前要先查清配额作用域。

重试也应有明确的终态，而不是只有一个循环计数。至少要区分：提示时间超过用户预算、用户取消、达到最大尝试次数、接口结果未知、再次限流、请求最终成功，以及不能安全重放。对于结果未知的写操作，应先通过接口规定的状态查询或幂等键恢复，而不是盲目发起一笔新副作用。用户界面也应区分“本次自动等待结束”“操作尚未确认”和“服务确认失败”，避免把内部计时器结束直接显示成业务失败。

用可观察的测试结果验证策略

可以为支持的客户端和接口建立一组待执行验收：分别测试没有 Retry-After、以秒数表示、以 HTTP 日期表示、语法无效和提示时间超过前台截止时间；再测试用户中途取消、多个调用者同时收到 429、重试预算耗尽、幂等写入以及结果未知的非幂等写入。每个场景都要写清预期请求次数、是否存在更早的重试、界面状态和后续查询入口。它们是本文提出的测试计划，当前没有向真实 API 发请求，也没有运行压测或浏览器测试。

日志和指标应能解释“为什么客户端等了这么久或停止了”，但不需要记录秘密令牌或完整敏感请求体。可记录操作 ID、尝试序号、等待来源（响应提示或本地退避）、提示解析类别、截止时间剩余量、取消信号以及终态分类。统计 429、重试次数和停止原因能帮助发现策略是否过于激进；它们不能单独证明配额计算正确，也不能推出某项调整提升了吞吐量。

把决策顺序固定下来，团队评审会更容易：先核对 429 与 Retry-After 的含义，再判断请求是否允许重放，然后检查取消、总截止时间与剩余次数；满足所有条件才排定下一次尝试，否则进入可解释的终态。这样，重试就从“报错后再试几次”的习惯，变成遵守服务提示、限制负载并向用户说明结果的明确契约。
