revert 之后，原来的提交为什么还在历史里？

revert 新增反向提交而不删除历史；合并父节点和当前差异需审查，源码变化不代替运行恢复。

正文

git revert 用新的提交记录反向修改，不会把原提交从历史中删除。它适合让共享分支保留撤销过程，但源码发生反向变化，不等于生产服务、数据库或外部结果自动回到过去。撤销代码与运行恢复需要各自对应具体版本和证据。

历史仍然保留原来的动作

Git 的 revert 文档说明，它反转指定提交引入的修改，并记录新的提交；文档也区分 reset、restore 等操作。因而在历史里继续看到原提交，是保留记录的结果，不是撤销没有生效。本文没有对用户仓库执行 revert，也不会以解释命令为由重写共享历史。

假设一个提交改变了界面校验，随后团队决定恢复原行为。新的反向提交能说明谁在什么版本上撤销了改动，后续修复仍可基于这份历史讨论。若原提交包含秘密资料，反向提交并不删除历史中的资料，也不撤销已泄露凭证；需要独立执行相应处置，不能把 revert 当成清理泄露的万能办法。

当原修改之后已有其他变更，反向应用也可能与当前内容不一致。需要审查实际差异和冲突解决，而不是期待一个旧提交的逆向动作天然适配今天的代码。反向结果必须表达团队现在想恢复的行为，不能只追求命令结束没有报错。

合并提交需要明确参考父节点

文档说明，撤销合并通常需要指定主线父节点，反向变化依据选定父节点计算。选择的意义取决于合并结构，不应把一个固定编号当成所有仓库的标准答案。团队还需评估撤销合并对之后再次合并相关历史的影响，不能未经检查就承诺原分支随时可以无条件重新引入。

这里不提供可以直接运行的撤销脚本。具体选择应先查看提交图和目标差异，再准备可审查的结果。尤其不要因为故障压力就跳过版本确认，把错误提交撤掉后再用强制覆盖来掩盖新的问题。

源码回退以后仍有交付工作

构建、部署和公开验证需要重新指向反向提交产生的版本。只把它推到开发分支，不能说明线上已经采用。数据库结构、已有记录和外部副作用，也不一定随代码反向修改回到旧状态；恢复计划应说明哪些可逆，哪些需要补偿或保留。

交付记录可以关联原提交、反向提交与实际部署产物，说明三个身份各自承担什么证据。若发布过程采用的不是反向提交构建出的版本，应明确标记差异，而不是继续沿用源码已经撤销的结论。

拟议验证应核对差异、关键行为、部署版本和实际用户路径。没有执行时不提供恢复成功日志。有关发布后怎样确认回滚能力，可阅读产物、部署与回滚验收。共享历史保留的是可追溯动作，真正恢复了什么，仍由运行证据回答。
