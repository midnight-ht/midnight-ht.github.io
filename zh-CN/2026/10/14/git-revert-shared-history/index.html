Git revert 留下反向提交，怎样确认代码真的恢复？

git revert 保留原提交并新增反向变化；核对提交树、合并父节点、构建产物与运行状态，才能说明恢复到哪一层。

正文

核心要点

  • 原提交保留并新增反向提交，不代表操作失败。
  • `-m` 选择合并主线；被撤销合并的祖先关系会影响以后再次合并。
  • 代码树、构建产物、运行版本和外部状态需要分别验证。

git revert 会保留目标提交，并在当前分支上记录一个应用反向变化的新提交。它既不是删除历史的按钮，也不是线上回滚的证明。判断它是否完成了需要的恢复，要分别看提交图、反向后的代码树、构建产物和运行中的版本；数据库记录、已发消息或凭证泄露还可能需要单独补偿。

反向提交改的是当前状态，不是把分支倒带

Git 的 git-revert 手册把 revert 描述为反转一个或多个已有提交引入的变化，并记录新的提交。手册当前版本入口显示文档最后更新于 2.54.0，2.54.1 至 2.56.1 标记为无改动；这是文档版本，不代表读者安装的 Git 版本。原提交仍留在祖先历史中，因此 git log 看到它是预期现象。

反向补丁也不是把当前文件强行复制回目标提交的父版本。假设图中 A 是共同基线，B 为登录界面增加了校验，C 在相同文件里重构错误提示，团队随后在 C 上创建 R 来撤销 B。R 要把 B 引入的差异反向应用到 C 的当前树。B 的界面校验可能被撤销，但 C 的提示重构仍应保留；如果两处改动重叠，Git 可能要求人工解决冲突。最终树可以仍包含 C 的其他改动，既不必等于 A，也不一定自动恢复团队想要的行为。

这段图是解释算法的假设例子，没有在本站仓库执行 git revert。实际审查应对照 B 的原始差异、C 到 R 的结果和预期行为。一个干净退出只说明 Git 能形成提交或工作树变化，不说明反向补丁恰好覆盖业务上的全部影响。

revert、reset、restore 分别移动什么

共享分支上若要留下可审查的撤销记录，revert 创建新提交，保留已有提交的身份和顺序。Git 的 git-reset 手册说明，带提交参数的 reset 会改变 HEAD 指向；不同模式还会同步索引或工作目录。尤其 reset --hard 会用目标提交覆盖文件，也可能覆盖未跟踪文件。若这些提交已经推给协作者，强行改写分支会让其他人的提交基于另一条历史，需要协调恢复，不能把它当成与 revert 等价的“撤销”。

只想取回某几个路径时，restore 的作用范围也不同于移动整条分支。选择哪条命令，先问需要改变的是：共享历史、当前分支指针、暂存区，还是指定文件内容。命令名字都含有恢复意味，不代表它们改的是同一层状态。

多提交场景还要看命令的索引边界。git revert -n 把反向变化放入索引和工作目录而不自动创建提交；手册指出，这种方式按操作开始时索引的状态应用。若索引中已有别的暂存内容，批量反向前应确认最终暂存快照包含什么。否则“撤销几项提交”可能把不相关改动一起放进待提交结果。

合并提交的主线父节点会影响以后合并

普通提交的差异有单一父节点作为基准；合并提交有多个父节点。git revert -m <parent-number> 指定以哪个父节点作为主线，反向变化就相对于所选主线计算。父节点编号由该合并提交的父节点顺序决定，不能从“主分支通常是 1”推断当前仓库一定适用。先查看提交图与各父节点之间的树差异，确认要撤销的是从哪一侧带来的变化。

Git 手册还说明，撤销一个合并意味着声明不再需要该合并带来的树变化。之后再合并时，Git 只会引入那些不是该已撤销合并祖先的提交所引入的树变化。由此可见，把原 topic 分支再合并一次，通常不会自动重新应用当时已经成为祖先的旧提交。若确实要重新引入，团队要明确选项：审查并反向撤销原 revert，或以新提交实现所需变化，再检查新 diff；不能只因为“分支又合了一次”就认为旧功能已经回来了。具体冲突与最终树仍要以实际提交图为准。

怎样证明源代码变化已经到达用户

一个可审查的验证顺序是先确定提交身份，再确定产物身份，最后检查运行效果。第一步记录被撤销提交、R 的完整 SHA、R 的父提交，并审查 R^..R 的差异，确认只反向了预期内容且保留必要的后续修改。第二步在 R 上运行与故障或功能有关的构建和测试；若命令没有执行、依赖不可用或测试不稳定，应记录为环境问题或未知，不把它算成通过。

第三步把构建产物摘要与源提交 SHA 绑定。只确认 dev 上有 R 仍不能证明部署使用了基于 R 生成的文件。部署后核对发布平台记录的提交或工件身份、实际路由的版本和用户可见行为。若新代码没有被选中、缓存仍指向旧产物，或另一个更晚提交覆盖了撤销效果，源分支上的反向提交都不能证明线上恢复。

第四步列出 Git 之外的状态。迁移已经写入数据库的数据时，反向应用 schema 文件可能不会自动删除记录或恢复旧格式；已经发往消息队列的事件不会因为提交被撤销而从消费者处消失；外部付款、通知或权限变更需要依据其补偿机制处理。秘密误提交到共享历史时，revert 也不会抹掉历史副本或撤销已泄露凭证，应另行轮换密钥并评估仓库镜像与访问者。

例如，一个假想版本发布了过宽的权限校验，R 只恢复了源码条件。要声称用户权限问题已恢复，至少还需确认 R 构建出的工件已经部署，公开路径返回预期权限结果，缓存和后台作业没有继续使用旧规则；若错误期间已写入敏感记录，还应评估数据暴露和后续处置。上述是验证方案，不是本站或真实服务的已执行结果。

撤销合并后，重新合并之前要先看什么？

先确认旧合并和它的主线父节点，再列出该分支在旧合并之后增加的提交。文档中的祖先规则意味着旧提交不会因再次执行 merge 就自动变成新改动；新提交、反向 revert 的提交，以及冲突解决后的树共同决定最终代码。可以通过 diff、测试和部署身份验证需要重新出现的行为，而不靠分支名推测。

共享历史需要能说明“哪个提交改变了源代码”；部署记录要说明“哪个构建正在运行”；数据与外部副作用则需要自己的恢复记录。git revert 解决的是第一层的提交记录与代码变化。对于发布产物、回滚演练和线上验收，可继续阅读部署产物与回滚验收。本文没有对当前仓库执行 revert、部署或生产恢复，也没有宣称任何服务已经回滚。
