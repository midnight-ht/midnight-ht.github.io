给 PUT 与 PATCH 加一张请求契约表

PUT 用请求表示目标状态，PATCH 按指定补丁格式应用修改指令。契约表核对省略字段、null、数组与版本冲突；并发条件和领域命令仍需单独设计。

正文

核心要点

  • PUT 的请求表示与 PATCH 的修改指令是不同契约；稀疏对象不能自行定义省略字段的含义。
  • Merge Patch 的 null 表示移除、数组整体替换；显式 null、元素级列表操作可能需要别的格式。
  • 版本条件、重放安全、权限与业务状态验证不会由 PATCH 方法名自动提供。

PUT 与 PATCH 的边界应写进一张更新契约表：PUT 由请求表示目标状态，PATCH 按指定补丁格式应用修改指令。PATCH 不会自动替接口定义空值、数组、并发冲突或重放行为。真正的选择依据不是“只改了一个字段”，而是客户端提交的数据究竟是完整表示，还是一份有明确格式和规则的修改指令。

先把资源表示说清楚

HTTP 里的资源不是数据库表的同义词。接口可以把多张表、计算字段和派生状态合成一个可读表示，也可以只公开数据库中的一部分字段。RFC 9110 对 PUT 的定义，是请求把目标资源的状态创建或替换为请求内容所表达的状态；RFC 5789 则把 PATCH 定义为应用请求中一组修改指令。标准确定了操作意图，却没有替某个业务接口规定“没有出现在请求体中的每个数据库列要如何更新”。团队必须先定义资源表示，再说明接口从表示到持久化状态的映射。

假设个人资料资源当前表示为：

{
  "displayName": "Lin",
  "biography": "喜欢徒步",
  "locale": "zh-CN",
  "notifications": ["security", "product"]
}

用户只改了简介。若客户端把 { "biography": "喜欢公路骑行" } 发给 PUT，服务端不能靠“大家都知道这是局部更新”来理解它。若该接口把请求体视为完整表示，缺失的 displayName、locale 和 notifications 就不再由客户端提供；服务端可以按资源约束拒绝不完整表示，也可能按已经公开的表示规则产生替换结果。关键是契约必须明确哪一种行为成立。不能把“服务端当前恰好保留了几个字段”当成标准保证，也不能把一个稀疏对象悄悄解释成完整替换。

PATCH 仍然需要具体的补丁格式

PATCH 只说明请求携带修改指令，不表示所有 PATCH 请求体都采用同一种结构。服务端要按媒体类型理解补丁，并应通过接口文档或 Accept-Patch 等能力信息说明支持的格式；客户端不能只因为方法名是 PATCH，就推断字段省略、null 或数组有统一意义。

JSON Merge Patch（RFC 7396）用类似目标 JSON 的对象表达变化：对象中未出现的成员保持原值，普通值会新增或替换，成员值为 null 时表示移除目标成员。它适合主要由对象构成、且不需要把显式 null 当作普通数据值的文档。数组不能被逐项合并；补丁中的数组值会替换整个目标数组。如果目标字段允许“存在且值为 null”，Merge Patch 的 null 删除语义就无法单独表达“把这个字段设成显式 null”。

JSON Patch（RFC 6902）则是操作序列，例如 add、remove、replace、move、copy 和 test。操作按数组顺序执行，路径用 JSON Pointer 表达。test 可以把预期旧值放进补丁里；例如先断言 locale 仍为 zh-CN，再改简介。但它增加了操作顺序、路径转义和失败处理的复杂度。若任何操作无法应用，服务端对整个 PATCH 仍须遵循 RFC 5789 的原子性要求：不能只留下部分变更。选择这种格式之前，要确认服务端实现与资源模型确实支持这些操作。

用一个假设场景区分省略、清空和替换

继续使用资料资源。产品需要三种不同意图：只换简介、清除简介、把通知偏好整组替换。若使用 Merge Patch，第一种可以只提交 biography；第二种可以提交 "biography": null，但接口必须同时说明这代表“删除/清除简介”而非普通空值；第三种提交完整 notifications 数组，数组整体替换，不能期待只合并一个元素。若业务需要保留显式 null，或者要表达数组里单独增加、删除一个值，应考虑 JSON Patch 或专门设计的领域操作，并把允许的路径和操作范围写进契约。

请求情形 契约需要明确的含义 典型验收结果
PUT 缺少公开字段 这是无效的完整表示，还是资源定义的一部分？ 拒绝或按完整表示规则产生确定结果；不能默认为保留
Merge Patch 省略字段 省略是否表示不修改？ 未出现的对象成员保持原值
Merge Patch 显式 null 表示删除还是可保存的空值？ RFC 7396 中该成员会被移除
Merge Patch 数组 改一项还是替换整个数组？ 数组值替换目标数组
条件更新版本过期 是否禁止基于旧状态写入？ If-Match 不匹配时不执行，可返回 412

这个例子是接口设计推演，没有连接实际 API、数据库或浏览器执行。它说明了请求体怎样表达意图，不证明某个服务已经实现了相同行为。若客户端发送 { "biography": "" }，空字符串又是另一种值；除非文档定义，否则不能把空字符串、null、字段省略和删除请求互换。服务端验证也不能只检查 JSON 语法，还要检验字段是否可写、值是否满足业务约束，以及修改后整个资源是否仍然有效。

并发冲突与重复发送是另一层契约

即便 PATCH 精确表达了“改简介”，两个客户端仍可能从同一旧版本出发。客户端 A 读取版本 ETag "v7"，客户端 B 先改了 locale 并把资源推进到 "v8"；如果 A 后来不带条件地覆盖完整旧表示，B 的修改就可能丢失。对需要基于某个已知版本计算的修改，客户端可以携带 If-Match: "v7"。RFC 9110 规定 If-Match 使用强比较；当前表示不匹配时，服务器不得执行请求，可返回 412。客户端应重新读取、合并用户意图，再让用户决定如何处理冲突，而不是自动把旧内容再发一遍。

PATCH 方法本身不保证幂等；但某一种具体补丁可以被设计为幂等。把字段设为固定值通常与“把计数加一”这样的指令有不同重放后果。网络超时也不能证明服务端没有执行修改：如果响应在返回途中丢失，客户端盲目重发可能再次产生副作用。需要依据端点契约判断是否可以安全重试，必要时采用 If-Match、幂等键或结果查询。把 HTTP 方法、补丁格式、并发条件和业务重放规则混为一谈，会让错误恢复变成猜测。

PUT 同样可以和 If-Match 配合，防止基于旧读取结果的完整替换覆盖他人变化。它的优势是完整表示便于比较和重复提交时保持目标状态；它并不意味着不会有并发冲突，也不保证数据库事务之外没有其他副作用。若只是字段局部编辑而客户端没有完整表示，选择 PUT 会迫使客户端获取、修改并提交整个资源，或让服务端定义非标准的稀疏 PUT 行为。后一种做法可能能工作，但调用者必须知道这不是从方法名直接推出的语义。

哪些情况不适合直接采用通用 PATCH

通用补丁格式不是每种领域操作的最佳接口。将购物车数量加一、批准一笔付款、领取一次奖励，都更接近带权限和业务前置条件的命令，而不是任意修改表示。若让客户端通过 replace /status 把订单改成 paid，服务端就可能暴露一个绕开支付验证的路径。更安全的接口通常把动作表达成具名命令，由服务端验证调用者权限、当前状态、资金或业务规则以及重复请求处理方式。

同样，某些对象的字段彼此约束。例如“开始时间早于结束时间”，或通知偏好只允许若干合法组合。逐字段应用补丁可能在中间状态暂时违反约束。RFC 5789 要求一个 PATCH 内所有直接修改原子生效，但原子性不等于业务校验自动正确；服务端仍须在一次受控事务中校验最终状态，并考虑相关资源、副作用是否在同一事务边界内。跨外部系统的副作用通常无法仅凭数据库回滚保证一致，需要明确补偿或状态查询策略。

用验收矩阵固定接口承诺

实现前可以为每个公开字段列出请求含义和错误条件：完整 PUT 中缺字段应拒绝还是按完整替换处理；PATCH 中省略字段是否保持；显式 null 是删除、合法值还是验证错误；数组是整体替换还是使用单项操作；只读字段被修改时如何返回；两个版本竞争时是否返回 412；补丁的中间操作失败时是否确保没有部分保存。对外接受哪些补丁格式也应有明确媒体类型和文档，不能由某个客户端库默认值代替。

测试可以从一份初始资源和预期结果开始，而不是只检查 200。逐一验证完整 PUT 替换、PUT 不完整表示、PATCH 省略字段、null、空字符串、数组变更、只读字段、格式错误、JSON Patch 的 test 失败、If-Match 过期，以及响应丢失后查询结果的流程。每项都记录发送前状态、请求和 Content-Type、期望状态码、完整结果表示、是否有任何副作用、重放是否安全。本文列出的是待执行验收设计，当前没有运行 API 测试或性能测试。

真实接口要选 PUT，就让请求体完整表达它负责替换的资源表示，并清楚写出更新约束；要选 PATCH，就先确定补丁格式、字段语义和并发处理。不要把“客户端这次只动一个输入框”误当成协议已经定义了局部更新。

相关的版本冲突实现边界可参阅条件更新与版本冲突；本文讨论的是资源更新意图与补丁文档本身。
