只改一个字段，为什么不能把 PUT 当作局部更新？

PUT 替换表示与 PATCH 修改指令不同；明确省略、空值、重复执行和并发条件，避免由实现偶然决定更新含义。

正文

只修改一个字段的需求，不应默认用一份稀疏对象表达 PUT。PUT 请求的是目标资源状态由所给表示创建或替换；PATCH 则携带修改指令。接口还需要明确缺失字段、空值与具体补丁格式的含义，不能只因为两种方法都能改变数据，就把它们视作同一个更新动作。

替换表示与修改指令不同

RFC 9110 的 PUT 说明描述创建或替换目标资源状态的意图。RFC 5789进一步区分 PUT 提交修改后的表示，与 PATCH 提交产生新状态的指令集合。标准并不要求所有资源都与一张数据库表完全对应，团队仍要定义资源表示包含哪些字段。

假设用户只修改个人简介，客户端提交一个只有简介的对象。如果接口把它当作完整替换表示，未提供的字段要怎样处理就成为契约问题。默默保留、清空或报错都不应由某段数据库更新代码偶然决定。例子是设计假设，本文没有发送实际更新请求，也没有观察真实用户资料丢失。

还要区分字段省略与明确传入空值。它们可能分别表示不涉及该字段和清除字段，但具体含义取决于接口与补丁格式。不能仅凭 JSON 中没有某个键，就推断所有服务都会保留旧值。契约应该让客户端能够在操作前知道结果，而不是通过一次线上修改试探行为。

PATCH 不自动获得全部更新保证

RFC 5789 说明 PATCH 本身并非必然幂等，但请求可以设计成幂等。把方法名称改成 PATCH，不会自动消除重复副作用。给某个字段设固定值，与要求某个计数增加一次，重复执行时可能具有不同结果；应按实际修改指令判断，而不是只看请求方法。

多个客户端修改同一资源时，还需要并发条件。即便单次更新语义清楚，基于过期版本提交仍可能覆盖他人的变化。条件请求或业务冲突策略解决的是另一层责任。本文不提供一套已经运行的通用更新实现，也不承诺某种补丁格式适合所有业务对象。

验收围绕客户端意图展开

拟议检查可以覆盖完整替换、字段省略、明确清空、重复提交和旧版本提交，核对接口结果与文档一致。对于不允许修改的字段，还应检查服务端规则，不能因为客户端没有显示编辑控件，就认为该字段天然受保护。成功状态需要与真正接受的更新范围一致。

返回更新后的表示时，也应说明它对应处理时的状态；其他客户端可能随后继续修改，不能把一次响应写成永久不变的确认。相关并发讨论见条件更新与版本冲突。先让更新动作有确定含义，再决定怎样限制竞争与重试，才能让失败时的恢复依据完整。
