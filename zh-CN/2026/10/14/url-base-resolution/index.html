先约定基地址和相对路径，再拼接口 URL

URL 构造器按路径引用规则解析地址；基路径末尾斜杠、根相对输入和绝对输入会产生不同结果。

正文

核心要点

  • `/v2` 把 v2 当作可被替换的最后一段；`/v2/` 才表达目录边界。
  • `users`、`/users`、绝对 URL 是不同引用形式，后两者可能离开服务前缀或改变 origin。
  • 构造成功只说明解析成功；目的地授权、重定向与网络边界要另行处理。

new URL("users", "https://api.example.test/v2") 会替换 v2；基地址改为 /v2/ 才会保留这个目录。若调用改用 /users，又会回到源站根路径。接口地址是否正确，至少要同时说清基地址的目录边界、引用是相对还是根相对，以及最终目的地是否获准。下面的示例域名只用于说明规则，不代表真实服务。

最后一段路径不自动成为目录

URL 构造器接收一个 URL 引用和可选基地址，然后按 URL 的路径解析规则得到结果；它不是把两个字符串直接连起来。MDN 的 URL 构造器说明明确对比了基地址没有结尾斜杠与有结尾斜杠的情况。前者最后一段是路径叶子，解析普通相对引用时会被替换；后者以斜杠结束，表达当前目录，下一段会接在它后面。这个区别不是视觉格式，而会改变请求目标。

例如基地址为 https://api.example.test/v2，输入 users 后得到 https://api.example.test/users。v2 被当成需要替换的最后一段。如果基地址写成 https://api.example.test/v2/，同一个 users 才得到 https://api.example.test/v2/users。把版本前缀储存在配置中时，少一个尾斜杠就可能让所有相对接口退出版本路径。反过来，如果基地址代表单个资源而不是目录，尾斜杠也会改变含义，不能靠格式化工具一律补上。

这解释了为什么开发环境看似正常，部署到带路径前缀的网关后接口却返回 404：本地配置可能直接指向源站根路径，生产配置则包含 /service/v2；如果调用点又在某些请求中传入根相对路径，前缀仍会被抛弃。此时加重试、改超时或在代理里临时重写，通常只会让不同输入继续表现不一致。应该先找出基地址从哪来、引用由谁构造、预期前缀在哪一层负责。

三种引用形式会落到不同位置

users 或 ./users 是相对当前目录的路径引用。对目录形式基地址 https://api.example.test/v2/，结果保留 /v2/。如果基地址是 https://api.example.test/v2，最后的 v2 被视为叶子，结果会成为源根下的 /users。因此接口配置若打算让所有 endpoint 相对同一 API 目录，建议把“这是目录”的约定写进配置校验，并让调用只接收相对接口名。

/users 是根相对引用，从 origin 的根路径解析。无论基地址路径是 /v2/ 还是 /service/v2/，它都会指向同一 origin 下的 /users。它适合确实要访问站点根目录资源的场景，却不适合一个必须保留网关前缀的客户端。不要把它和相对路径混成“带斜杠的 endpoint”这一种含糊输入。

绝对 URL，例如 https://other.example.test/users，不使用基地址来组成结果；以 // 开始的 scheme-relative 引用则沿用基地址的协议、替换主机。它们会改变固定 API origin 调用的目的地：即便开发者原本只想补路径，外部输入也可能使最终 origin 变化。基地址不是限制器，传入它并不会把所有输出锁在该 origin。

父目录引用 ../health 会从当前目录向上退一层，再追加 health；多个 ../ 继续向站点根方向移动。查询部分也遵循引用规则：新引用带自己的查询参数时，结果采用新查询；非空引用通常会清掉基地址的查询，而空引用会保留它。依赖查询参数时应把它们作为明确输入，而不是希望字符串拼接替你合并。MDN 相对引用指南与构造器 API 给出了这些形式的解析例子；具体业务还要决定哪些形式可以进入调用链。

把地址组合写成可检查的契约

下面是在本地 Node.js v24.21.0 中实际执行的纯解析片段。它只构造 URL，没有发出 HTTP 请求，也没有验证示例域名是否存在。输出分别确认了缺少尾斜杠、目录形式、根相对、父目录和绝对引用的结果；相对输入缺少基地址时，构造器抛出 TypeError。Node.js v26.13.1 的 URL API 文档说明其 URL 类遵循浏览器使用的 WHATWG URL Standard；本次实际输出只证明本地 v24.21.0 环境中的这些输入行为。

const cases = [
  ["leaf base", "users", "https://api.example.test/v2"],
  ["directory base", "users", "https://api.example.test/v2/"],
  ["root relative", "/users", "https://api.example.test/v2/"],
  ["parent relative", "../health", "https://api.example.test/v2/users"],
  ["absolute", "https://other.example.test/users", "https://api.example.test/v2/"],
  ["new query", "users?limit=10", "https://api.example.test/v2/?tenant=staging"],
  ["empty reference", "", "https://api.example.test/v2/?tenant=staging"],
];

for (const [name, reference, base] of cases) {
  console.log(name, new URL(reference, base).href);
}

try {
  new URL("users");
} catch (error) {
  console.log("missing base", error.name);
}

实际输出顺序是 /users、/v2/users、/users、/health、另一个 origin 的 /users、带 limit=10 而不带基地址 tenant 查询的 /v2/users，以及保留 tenant=staging 的 /v2/，最后是 TypeError。该检查只覆盖构造器的解析结果。它没有证明某个 API 路由存在，也没有证明浏览器、反向代理和后端使用同一前缀，更没有测试重定向、DNS 或访问权限。

落到项目中，配置契约可明确写成：“服务基地址必须是绝对 URL，并以斜杠结束；endpoint 只能是没有前导斜杠的相对路径；调用后校验期望的 origin 与业务路径范围。”如果业务需要根相对路径或绝对 URL，应把它作为另一种明确接口，而不是静默接受。只对字符串调用 endsWith("/") 是很弱的校验：它没检查协议、主机、路径是否被编码，也没判断输入是否属于允许的服务。更好的做法是先解析配置，核验它是预期的 HTTP(S) origin 和目录，再用约束过的 endpoint 构造目标。

解析成功，应用就可以访问这个地址吗？

不可以只凭解析成功作这个判断。解析器回答“这个引用按 URL 规则对应到什么地址”；应用策略回答“这个调用是否允许到那里”。例如固定 API 客户端可以把结果与预期 origin 比较，并检查路径是否位于明确的 API 前缀下；判断路径前缀时也要尊重路径段边界，避免把 /api-evil 误当成 /api 子路径。对用户提供的完整 URL，除 origin 外还需规定协议、端口、凭据、重定向以及解析后主机地址等边界。

浏览器客户端和服务端代理不是同一种安全场景。浏览器的同源限制、CORS 或页面 CSP 不等于后端发起请求时的目的地授权。服务端若接受 URL 并代为访问，攻击者可能利用重定向、私网地址、DNS 变化或非常规地址形式越过单次字符串检查。本文不把 new URL 包装函数称为 SSRF 防护；更广的出站请求边界见用户网址与出站请求校验。

测试应覆盖哪条边界

下表的值是以 https://api.example.test/v2/ 为基地址的解析预期。它展示了路径结构，不能代替对实际服务路由的集成验证。

输入引用 解析结果路径/地址 要检查的契约
users /v2/users 普通 endpoint 保留服务前缀
/users /users 根相对引用有意跳过 /v2/，否则应拒绝
../health /health 父目录引用越出版本前缀，只有明确允许才接受
https://other.example.test/users 另一个 origin 绝对引用改变目的地，固定 origin 客户端应拒绝
users?limit=10 /v2/users?limit=10 新查询替换基地址查询，不自动合并 tenant
空字符串 /v2/?tenant=staging 空引用保留基地址查询，并指向目录本身

可以将这些输入放进纯单元测试，断言解析后的 origin、pathname 和查询字段；再用服务路由的契约测试验证真实 endpoint 路径。若系统支持 /service/v2/ 子路径部署，还要以该配置重复检查，不能只测 /。对允许名单与重定向的验证应在发请求的那层做，并模拟拒绝分支；单元测试构造出正确字符串，不代表代理或服务完成了访问控制。

本文示例中的 URL 构造器输出已在 Node.js v24.21.0 本地运行核对，真实 HTTP 请求、浏览器集成和后端安全测试均未执行。实施时把基地址作为“origin + 目录”的配置项，把 endpoint 的引用形式作为接口约定，再独立检查最终目的地。斜杠问题由此成为一条可测试的输入边界，而不是上线后靠猜测排查的偶然差异。
