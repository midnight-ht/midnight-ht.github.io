固定 Date、快进和推进时钟，不是同一种测试

Playwright 的固定日期、快进、逐步推进和系统时间跳变会产生不同的回调行为。先说明测试要验证的时间语义，再选择 API 并断言业务结果。

正文

核心要点

  • setFixedTime 固定 Date 读数但让定时器继续运行；它不模拟经过时间。
  • fastForward 对到期定时器最多触发一次，runFor 会推进区间并触发相关回调。
  • 浏览器时钟不替服务端推进时间；先核对 Playwright 版本与时间边界。

固定了 Date，定时器仍可能继续跑；把时钟快进，也不等于把中间每个定时回调逐一执行。测试先要说清想模拟的是日期显示、经历了一段时间，还是一次系统时钟跳变。否则“把时间调快一点”会把不同的产品承诺塞进同一个测试设置里，失败后也很难判断是页面行为错了，还是测试选错了时钟操作。

固定日期值不等于停止定时器

Playwright 当前的 Clock 指南把 setFixedTime 用于固定 Date.now() 和 new Date() 返回的时间，同时让定时器照常运行。它适合日期标签、账单周期日期或活动开始时间等只关心“现在显示哪个日期”的场景。它不会替你暂停 setTimeout、setInterval，也不会让时间差自动经过。

举个示意页面：每秒触发一次 render()，函数读取 Date.now() 并计算“距离结束还有几秒”。如果只固定 Date，回调仍会运行，但每次算出的时间差仍来自同一个固定读数。屏幕可能持续显示相同倒计时。此时再把断言等待时间从一秒改成十秒，并没有让业务时钟前进，只是让测试多等了九秒。相反，如果页面每秒只把固定日期格式化并写回文本，定时器持续运行但显示值不变，正好符合“固定日期、定时刷新”的契约。

因此要拆开两个问题：当前时间值应该是什么，回调又应该在何时执行？只检查一个固定文本不足以证明倒计时的时间推进；只看到回调触发也不能证明截止状态正确。先写出业务规则，例如“页面启动后五分钟无操作便显示退出提示”，再决定测试是否需要推进五分钟、推进期间是否应运行每次间隔，或者只需要跳到到期点。

安装时机也是被测页面的输入

如果要控制时间值和定时器，Playwright 的 page.clock.install() 会安装一组可控的浏览器时间函数。当前文档列出的范围包括 Date、setTimeout、setInterval、动画帧回调、performance 和事件时间戳等；Clock 安装在整个 BrowserContext 上，因此同一个 context 里的页面和 iframe 共用时钟。它不只作用于某一个断言或一个 tab。

安装顺序会改变页面启动条件。Clock API 文档建议在导航页面前安装时钟，并把初始时刻设在目标时间之前；页面加载完成后，再暂停在要检查的时间。原因很实际：应用可能在启动脚本里创建周期任务、等待一个延迟回调，或根据经过时间初始化状态。如果页面先用原生时钟注册了这些工作，之后再替换时钟函数，测试已经让一部分逻辑在另一套时钟下启动。当前指南还要求 install() 必须先于测试中其他相关 Clock 调用，否则顺序未定义。

下面是一个示意流程，只用来说明时钟边界，没有在真实项目或浏览器中运行：

await page.clock.install({ time: new Date('2026-01-01T11:55:00Z') });
await page.goto('/session');
await page.clock.pauseAt(new Date('2026-01-01T12:00:00Z'));
await expect(page.getByText('Session expired')).toBeVisible();

它表达的是：让页面从一个早于截止点的时间自然加载，再跳到截止点并暂停。真实测试仍要按产品定义处理时区、登录状态和等待页面初始化；示例 URL 和提示文本是假设值，本文没有执行该脚本。若应用的服务端负责会话过期，单独控制浏览器时钟不能验证服务端是否会拒绝请求。

快进、逐步推进和改系统时间的区别

API 名字相似，不代表经过同一条回调路径。fastForward() 像设备休眠后醒来：把时间跳到未来，只让到期定时器最多触发一次。它适合检查“截止点过后最终进入什么状态”，但不能用来证明区间里每秒更新一次的动画或轮询都执行了五次。

runFor() 则推进指定时长，并运行这段时间中相关的时间回调。它适合验证周期任务、重复更新或多个定时器之间的顺序。若页面每秒更新一次，运行五秒与直接快进五秒的观察结果就可能不同：前者会逐次处理回调，后者只让到期任务最多触发一次。测试选择应来自页面的真实语义，而不是哪个 API 运行得更快。

setSystemTime() 又是另一件事。文档说明它改变当前系统时间，但不会因此触发定时器，可用于检查时钟突然改变、夏令时切换或时区变化时页面如何反应。它不等价于让应用经历这段时间。若测试要验证超时回调，就应选择能推进并触发相应定时任务的操作；若测试关注日历时间被向前或向后调，才考虑系统时间跳变。

当前 Playwright API reference 标明这些 Clock 方法从 v1.45 起加入。维护旧项目时先查锁文件中的实际版本和对应版本文档，不要把当前站点的接口直接写成任何旧版本都支持。还要记住 Clock 控制的是浏览器 context 中列明的时间相关 API；服务器、数据库、消息队列或独立进程的时钟不在这个对象里。

用一个截止时间例子确定断言

假设产品要求用户连续五分钟没有操作时，界面显示“会话已过期”。这不是用户案例，而是一个说明测试设计的假设。可以先确认页面加载后倒计时出现，再执行一次会重置活动时间的操作，随后推进四分五十九秒并断言仍未过期，最后推进最后一秒并断言提示出现。这里的关键不在于照抄这个时间表，而在于每个断言都对应一条明确的产品边界。

如果实现使用 Date.now() 与 setTimeout() 的组合，测试需要选一个能让两种时间机制一致前进的 Clock；只固定 Date 会让差值卡住，只跳系统时间又不会触发到期回调。若要检查“笔记本休眠后回来”一类的跳时语义，可以比较快进后到期任务的最终状态，但不能据此断言期间所有轮询步骤都发生过。要观察逐次计时，则使用能逐一推进回调的路径，并把 setInterval 次数或实际界面状态作为结果证据，而不是只断言测试时钟的方法被调用。

还有一种容易误判的反例：前端时钟已到期，页面显示退出，但服务端仍接受请求；或浏览器时间被回拨，服务端截止时间却保持不变。它可能是架构预期，也可能是安全缺陷，需要产品契约和服务端测试来判断。浏览器 Clock 能隔离前端时间逻辑，不能代表后端真实时钟已经改变，更不能替代请求结果断言。

先写时间语义，再写等待

动手前把断言归到一类：格式化日期读取固定值；重复倒计时需要时间推进和周期回调；休眠后跳到未来只检查到期后的状态；系统时间被调整则检查突然跳变；服务端截止规则另用可控制的服务端时钟或明确的 API 契约。随后确认 Playwright 版本、clock 安装先后、BrowserContext 共享范围，以及页面启动时是否创建定时器。

验证不必制造很大的等待。为每个阶段断言可见业务状态，并覆盖截止点前、边界时刻、边界后与取消/重置任务的路径。如果 callback 在时间推进后没有执行，检查所选 API 的语义、安装时点和调用顺序；如果界面变化但业务请求仍成功，检查服务端时间来源，而不是继续改浏览器超时。有关异步检查的条件选择，可参看Playwright 自动等待与结果条件。时间 API 只安排测试条件，真正的断言要回答用户在该时间边界上看到了什么、系统又做了什么。
