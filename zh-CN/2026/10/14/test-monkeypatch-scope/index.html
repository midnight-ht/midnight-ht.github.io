monkeypatch 会撤销函数替换，但不会撤销测试做过的事

pytest 会在测试或 fixture 生命周期结束时撤销它管理的替换；线程、已启动的子进程、缓存配置和外部副作用仍需要各自的边界与清理。

正文

核心要点

  • 补丁按代码查找依赖的名字生效，fixture scope 决定恢复时点。
  • 线程、子进程和导入时缓存配置有独立生命周期。
  • 恢复引用不撤销已发生的文件、网络或数据库副作用。

如果测试结束了，后台回调仍拿着替代函数，或者一个请求已经被发送，monkeypatch 不会把这些事情倒回去。pytest 管理的是它记录的临时名字、字典项和环境映射；测试任务、线程、子进程以及文件或网络副作用各有自己的生命周期。设计补丁时，先问“谁会在什么时候读取这个名字”，再问“退出时我需要恢复什么”。

补丁恢复的是引用，不是整个进程状态

monkeypatch.setattr(module, "read_config", fake) 的效果，是让 module.read_config 在一段时间里指向 fake。fixture 保存原来的属性，并在请求它的测试或 fixture 结束时撤销这些改动。pytest 文档列出的对象属性、字典项、环境变量、当前目录和导入路径修改，都属于可以记录和撤销的对象。pytest 的 monkeypatch 指南也提醒：补丁会影响实际读取被替换名字的代码；它不会自动知道哪些读取属于“测试目标”。

因此，补丁位置要跟被测代码的查找位置一致。如果 worker.py 在导入时执行 from gateway import fetch，之后调用的是 worker.fetch 这个名字；仅把 gateway.fetch 换掉，未必改变已经绑定在 worker 里的引用。pytest 的 API 文档明确说，属性替换需要针对系统实际使用的名字。这是一个常见反例：测试写了补丁，补丁也成功，但被测调用没有经过替身。先读一次依赖如何绑定，再选择要替换的属性，通常比增加第二个全局补丁更清楚。

只需在几行代码里替换依赖时，可以用 pytest 提供的局部补丁上下文：

def test_uses_fallback(monkeypatch):
    original = service.use_cache
    with monkeypatch.context() as patch:
        patch.setattr(service, "use_cache", False)
        assert service.use_cache is False
    assert service.use_cache is original

这是示意代码，本文没有在项目中运行它。离开该上下文时，会撤销它记录的修改；pytest 提供的 fixture 通常在测试结束时统一清理。官方指南建议对可能影响 pytest 自身的标准库补丁尽早清理。不要在共享 fixture 中随手调用同一个 monkeypatch.undo()：API 说明同一 fixture 实例可能被测试函数和 fixture 共用，undo() 会撤销这实例记录的所有改动。若确实需要局部结束一部分替换，单独的 context 能让撤销边界更可见。

fixture 的结束时间不等于任务的结束时间

fixture scope 决定清理时点：默认 function 在单个测试结束时销毁；class、module、package 和 session 会延长到相应容器结束。fixture 文档还说明，yield 后的清理会在 fixture 成功 yield 后、测试完成时执行；如果 fixture 在 yield 之前失败，它自己的 yield 后代码不会运行。可见“清理由框架管理”也有精确边界：成功建立了什么、清理登记在哪里、它属于哪个 scope，都需要设计者说清楚。

再看一个假设场景：测试把 mailer.send 替换成只记录参数的函数，随后启动一个线程处理队列消息。测试函数退出时，补丁恢复了；线程可能仍在运行。如果线程已经捕获了替代函数对象，它仍能调用那个对象；如果线程执行时重新查 mailer.send，它则可能看到恢复后的真实函数。两条路径都取决于代码如何保存和读取依赖，不能仅靠退出 context 推断。本文未启动线程验证这两种情况。更稳妥的做法是让测试等待任务完成，再离开补丁范围；如果要测试并发隔离，给每个 worker 显式传入依赖，或用独立进程避免争用同一份模块全局状态。

这个区别也解释了副作用为什么不会自动回滚。补丁可以恢复 mailer.send 的函数引用，却不能撤销已发送的邮件、写入的文件或已经提交的数据库事务。外部效果应使用单独的清理契约：临时目录由资源 fixture 删除，事务由数据库测试回滚或专用测试库隔离，远程资源由创建它的 fixture 安排删除。安全 teardown 指南建议把每个 fixture 限定为一个状态改变动作，并把该动作和清理放在同一 fixture 中；这样中途 setup 失败时，已成功建立的资源仍有自己清理路径。补丁撤销和资源清理是两份责任，不能用一份断言代替另一份。

环境变量也有读取时机

调用 monkeypatch.setenv("APP_MODE", "test") 会改变当前 Python 进程的 os.environ 映射，fixture 清理时再恢复旧值。Python 的 os 文档说明，该映射在 os 模块导入时从进程环境捕获，后续直接修改它会同步调用底层环境接口。应用自身则可能在导入配置模块时把值复制到常量里：

# settings.py
MODE = os.getenv("APP_MODE", "prod")

测试若先导入 settings 再调用 setenv，settings.MODE 不会因为环境映射变化而自动重新赋值。此时测试到的是“导入时配置已捕获”的行为，而不是 setenv 失效。可选择在导入被测配置前设置变量、把读取推迟到函数调用，或把设置对象作为参数传入；选择取决于应用真实的配置契约，不能为了让测试通过就无条件清除模块缓存。

子进程构成另一条边界。Python subprocess 文档说明，子进程默认继承启动时的当前环境，也可以通过 env 显式提供映射。假设测试在补丁期间启动子进程，它拿到的是启动时提供的环境；父进程之后恢复变量，不会追溯修改已经运行的子进程。测试子进程配置时，应显式构造 env，并检查进程退出和清理，而不是只断言父进程的环境还原。

应该怎样选作用域并验证退出

依赖本来就是组件输入时，注入一个替身通常比改模块级名字更容易推理。单个测试需要短暂替换某函数时，用 pytest fixture 管理；替换标准库或可能影响测试框架的函数时，把局部补丁上下文放到最窄的调用块。需要模块级共享资源时，先判断被共享的是不可变数据、受控连接，还是会在测试间变化的全局依赖；不要仅为减少初始化次数就把补丁 scope 延长到整个模块或 session。

验证至少分两层。第一层，在 context 内确认目标调用使用替身，退出后用身份或行为断言确认名字回到原实现；异常路径也要能退出 context。第二层，检查补丁范围内启动的工作是否已经结束，文件、数据库或远程对象是否由独立 fixture 清理。若实际调用会跨线程或进程，测试要检查这些边界上的依赖传递与结束条件。这里给出的是验证设计，不代表本文在 pytest 项目或外部服务上执行过测试。

一个可复用的判断是：补丁工具只替你恢复它记录的状态；你必须自己定义测试中启动的工作何时结束，以及它留下的资源由谁清理。如果问题来自全局依赖难以传入，逐步引入依赖注入可能比继续加宽补丁更合适，但遗留系统的改造成本与风险仍需单独权衡。资源生命周期的相关讨论见pytest fixture 的隔离与清理。

补丁会自动影响另一个线程或子进程吗？

线程共享同一进程里的模块对象，因此补丁生效期间，其他线程若读取同一个被替换属性，可能看到替身；已有局部变量则可能仍持有先前捕获的对象。子进程有独立地址空间，通常在启动时获得父进程传给它的环境和参数，但之后父进程的属性恢复不会改写子进程内存。两种情况都不应靠 pytest fixture 的 teardown 推断结果，而应查看依赖在哪一刻被读取、它被复制到哪里，以及任务是否已结束。
