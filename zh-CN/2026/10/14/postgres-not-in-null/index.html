NOT IN 为什么没有返回预期的未匹配记录？

右侧 NULL、空子查询和左值 NULL 会让 NOT IN 走出不同的三值逻辑结果。先明确未知身份的业务含义，再验证 NOT EXISTS 改写与约束假设。

正文

核心要点

  • NOT IN 要求每项比较都确定不等；右侧 NULL 可使无匹配结果变成 UNKNOWN。
  • 空右侧时 NOT IN 为 TRUE，即使左值是 NULL；WHERE 则丢弃 UNKNOWN。
  • NOT EXISTS 改写、复合键和空值约束必须按业务状态验证；本文 SQL 未执行。

NOT IN 的右侧只要出现 NULL，又没有找到相等值，整项判断就可能是 UNKNOWN，而不是 TRUE；WHERE 只保留结果为真的行，于是看起来像“没有返回未匹配记录”。修复前应先定义空值代表什么，再在 NOT IN、NOT EXISTS 或显式空值条件之间选择；这些写法只有在相同的空值规则下才等价。

NOT IN 实际上要求每一项比较都能判为不等

PostgreSQL 19 的子查询表达式文档把 x NOT IN (subquery) 定义为与子查询返回的每一行比较；有任何一行相等时结果为假，只有所有比较都为不等时才为真。如果没有相等项，却至少有一次比较是 UNKNOWN，最终结果是 UNKNOWN。它等价于 x <> ALL (subquery)，所以这不是偶发的执行计划问题，而是逐项比较之后的逻辑结果。

先看一个刻意缩小的假设例子。待处理任务的编号是 10、20、30；排除表里有 20 和 NULL。对 10 而言，10 <> 20 为真，10 <> NULL 为 UNKNOWN；真 AND UNKNOWN 仍是 UNKNOWN；PostgreSQL 19 的逻辑运算符真值表也列出了这一结果。对 20 而言，一项比较为假，整项 NOT IN 为假。对 30 而言，比较结果同 10，仍是 UNKNOWN。三者中只有 20 已确定匹配，10 和 30 却不能通过 WHERE 的真值筛选。这一小表是按规则推导的示例，没有连接数据库运行。

这解释了一个常见误区：开发者脑中使用的是二值集合差，“表里没有这个编号”就等于“可以输出”；SQL 比较还要表达未知。NULL 不是一个特殊编号，不与另一个 NULL 相等，也不是所有未知值共有的哨兵。右侧 NULL 可能代表尚未关联、数据缺失、映射待补，或约束失效；每种含义都会影响产品是否能把记录称为未匹配。

把逻辑值和业务结果分开

SQL 谓词的结果至少要按 TRUE、FALSE、UNKNOWN 三种情况检查。PostgreSQL 19 的WHERE 文档规定，只有条件为 TRUE 的行才保留；FALSE 和 NULL 都会被丢弃。因此查询页面中没有某一行，并不能据此断言该行已经匹配、已经完成，或不存在。它可能只是“无法确定是否未匹配”。如果下游流程把查询结果当作可自动重试对象、账务候选或待人工核验清单，这三种业务状态就不应压缩成“出现/没出现”。

恢复查询前，先问两个独立问题：左侧身份为空时，这条任务应否进入结果？右侧映射身份为空时，应忽略这条映射、阻止处理，还是把相关任务标为待核对？若架构规定排除表的身份永远非空，可以用约束保证此不变量；若这只是数据导入目标，则查询应继续考虑不变量未成立时的状态。把脏数据过滤掉可以让 NOT IN 返回更多行，却也可能掩盖坏数据，因此不能只把它当作语法补丁。

改写为 NOT EXISTS 会改变哪一件事

若需求确实是“找不到一个有效的相等关联”，相关子查询常把比较局部化：

SELECT t.task_id
FROM task AS t
WHERE NOT EXISTS (
  SELECT 1
  FROM exclusion AS e
  WHERE e.task_id = t.task_id
);

EXISTS 判断子查询是否产生行。这里的等值关联只有在比较为 TRUE 时才算找到匹配，所以排除表中 e.task_id IS NULL 的行不会凭空匹配某个非空任务号；对非空的 t.task_id，它也不会像 NOT IN 那样把其他候选一并变成 UNKNOWN。相关的子查询文档说明，EXISTS 只关心是否至少有一行，选择列表通常不影响它的结果。

但如果 t.task_id 自己是 NULL，e.task_id = t.task_id 不为 TRUE，子查询不会找到匹配，NOT EXISTS 因而为真，NULL 身份的任务可能进入结果。原来的 NULL NOT IN (...) 则可能是 UNKNOWN。若产品要排除身份未知的左侧任务，就必须另写 t.task_id IS NOT NULL；若要保留并单独标记，查询与输出列都应表达这一状态。换成 NOT EXISTS 不是无条件等价改写，而是选了“只有确切相等才算已排除”的语义。

假如目标是丢弃右侧尚未关联的记录，并且左侧身份不允许为空，也可以显式加 e.task_id IS NOT NULL 后继续用 NOT IN。这个条件必须对应数据规则并受约束或监控支持。若目标是让未关联映射阻止批处理、提示数据修复，那么过滤掉 NULL 反而错了；应单独查询或计数 NULL，而不是把它混入排除集合后指望主查询报告问题。

子查询为空和相关多列比较也要单独验收

NOT IN 的右侧是空集合时，结果为真，包括左值为 NULL 的情况，因为没有任何一行供它比较；官方文档也把空子查询列为 NOT IN 为真的情况。SQL 谓词上的 TRUE 仍不等于产品已经知道 NULL 身份不匹配：若业务要求排除身份未知的记录，应显式处理左值，而不能依赖空集合碰巧没有比较项。这个边界很容易被只测试“右表有数据”的用例漏掉，尤其在过滤条件可能让排除子查询变为空时。

如果排除条件由两个字段组成，例如租户与外部编号，行构造器比较还会把每一列的 NULL 按 SQL 布尔规则合并。在 PostgreSQL 19 的[比较文档]中：行中的对应列全部非空且相等时行相等；只要有可确定不等的列，行不等；否则比较未知。因此 (tenant_id, external_id) NOT IN (...) 不会自动得到“任意空列都忽略”或“空值彼此相同”的含义。应决定哪些列属于身份、哪些缺失需要隔离，必要时用显式连接条件、IS NOT DISTINCT FROM 或数据约束表达该政策；但这些选择之间并不等价。

PostgreSQL 19 的优化说明不能代替语义保证

版本时间也要核对：PostgreSQL 19 于 2026-11-19 发布。版本说明提到，优化器在 NULL 不存在时可以把 NOT IN 转为 anti join。这是有前提的实现优化，不是放宽 NOT IN 空值规则，也不是承诺所有语句都会改写或变快。读者若看到旧版本、当前版本或计划节点不同，应分别核实服务器版本、约束、数据分布与实际 EXPLAIN；不能依据这一条发布说明把含空值的查询直接换写。本文的示例没有在 PostgreSQL 实例上执行，也没有比较查询计划或性能。

用能改变结果的用例验证改写

建立一张小型决策表时，至少覆盖：左值有且匹配、左值有但不匹配、右侧包含 NULL 且没有匹配、左值为 NULL、排除子查询为空、右侧既有 NULL 又有匹配，以及复合键的一部分为空。逐行写下三值逻辑结果，再写下产品期望的业务状态，然后分别检查原查询和备选写法。关键不是某种语法“更安全”，而是每种数据状态都只能进入指定结果。

更接近真实数据的验证还应查询空值来源：空值来自哪个导入批次、何时写入、是否有稳定的来源标识、修复后是否可能重新出现。可在测试数据上比较结果 ID 集合和差集，不要只比总行数；总数相同也可能是一边漏一条、另一边多一条。如果把 NOT EXISTS 与 NOT IN 声称等价，记录等价依赖的约束，例如左右连接键都非空、运算符语义一致、关联谓词相同，并用反例破坏这些条件确认测试会失败。

最后把决定写进字段约束、导入校验和业务状态定义。若 NULL 合法，就让它在接口或报表中成为可见的“身份未明”；若 NULL 不合法，尽早阻止新增并对旧数据修复告警。查询的责任是按明确规则求结果，而不是替团队猜测“未知”究竟应被当作“不匹配”。关于约束对 UNKNOWN 的处理边界，参见CHECK 与未知值的边界；它解释的是约束是否接受 UNKNOWN，不能直接推出 WHERE 或排除查询会保留该行。
