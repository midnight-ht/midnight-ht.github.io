CDN 脚本有 integrity 仍加载失败，怎样区分哈希与 CORS 问题？

跨源脚本带 integrity 仍可能被浏览器拒绝。按请求模式、CORS 响应头、最终响应字节和摘要逐层排查，并为失败设计有边界的回退。

正文

核心要点

  • 跨源 SRI 同时依赖预期字节匹配和 CORS 请求条件；HTTP 200 不能证明浏览器会执行资源。
  • 先核对浏览器实际请求模式与 Access-Control-Allow-Origin，再对照发布产物生成 integrity，避免从开发文件或猜测版本取哈希。
  • 摘要只标识被固定的字节，不替代代码审查；发生故障时不要无条件移除 integrity 或切换到未审查镜像。

跨源 CDN 脚本带了 integrity 仍加载失败，先把问题拆成两条：浏览器取得的字节是否符合声明的摘要，以及跨源响应是否满足 CORS。HTTP 状态码为 200，只说明服务器返回了响应；它既不证明浏览器允许这次跨源读取，也不证明资源内容与摘要相同，更不等于脚本已经执行。排查应从浏览器实际请求开始，再分别核对 CORS 响应和最终字节，不要先删除完整性属性来换取表面恢复。

这里的 SRI 是 Subresource Integrity，子资源完整性。HTML 的 integrity 属性声明一个或多个摘要，浏览器用取得的资源字节计算摘要并比较；匹配后才继续处理资源。W3C 当前的 Subresource Integrity Level 2 工作草案在 2026 年 3 月 20 日发布，页面明确说明它仍是 Working Draft，并非已经定稿的 Recommendation。本文用它核对机制，不把草案中新加入的策略接口当成所有浏览器都已支持的能力。

两道门分别检查内容身份和跨源许可

integrity 回答的问题很窄：资源内容是否匹配页面声明的摘要。它不负责授权跨域请求，不负责判断代码是否值得信任，也不负责允许页面执行某段脚本。浏览器对脚本继续处理时，还可能受到内容安全策略、资源类型、JavaScript 语法和运行时错误影响。把所有失败都叫作“哈希不对”，会把不同阶段混成一个猜测。

对跨源且启用 SRI 的资源，规范要求请求使用 CORS 或 same-origin 模式，原因包括避免页面借由“摘要命中或失败”推测跨源内容。普通经典 <script> 在没有 crossorigin 属性时，默认跨源请求通常处于 no-cors 模式；MDN 的 SRI 与 CORS 说明解释了为什么这种组合不能用于跨源 SRI。设置 crossorigin="anonymous" 会让元素使用 CORS 请求，而资源服务器仍须返回允许该页面来源的 Access-Control-Allow-Origin。对面向任何站点的公开静态库，服务端通常可以返回 Access-Control-Allow-Origin: *；若只允许指定来源，就应返回匹配的来源值。

这两道门会产生不同失败。响应体与 integrity 不一致时，CORS 已通过也会被完整性校验拒绝。响应体完全匹配，但请求仍是 no-cors，或响应没有允许来源的 CORS 头，浏览器也不能按跨源 SRI 路径使用它。因此，命令行能下载文件、CDN 文件名没变、或者开发环境没报错，都不能单独证明线上页面的资源能够加载。

一个假设发布例子如何拆成两种失败

假设某个页面从 https://cdn.example.invalid/lib/4.2.1/app.min.js 加载一个固定版本的公开库。.invalid 是本文的假设地址，不代表真实 CDN。发布流水线对最终的 app.min.js 产物计算 SHA-384，把结果写进 integrity="sha384-…"，并把元素标为 crossorigin="anonymous"。CDN 响应需要允许匿名的跨源读取；对于公开、无凭据的资源，通配来源通常是合适配置。此处不需要把用户 Cookie 发给 CDN。

现在假设浏览器 Network 面板显示 GET 返回 200，但 Console 报 CORS 相关错误。先检查最终响应是否有 Access-Control-Allow-Origin，以及页面实际是不是使用了 crossorigin="anonymous"。即使 curl 可以把文件下载到本机，它不会替浏览器执行同一套 CORS 限制。若服务器缺少该响应头，手工算出的摘要再准确也不能补上跨源许可。

反过来，如果 Network 面板显示 CORS 已允许，而 Console 指向 integrity mismatch，就把浏览器请求的最终 URL、重定向结果和流水线参与计算的产物版本逐一对上。相同路径可能被发布流程覆盖成新字节；CDN 边缘代理也可能重写资源。W3C SRI 草案的代理章节明确提醒，中间代理若修改响应内容，就必须同步摘要，或只发送与完整性声明相对应的规范版本。若变更后的文件仍沿用旧摘要，正确行为是浏览器拒绝执行，而不是悄悄接受新代码。

从请求到脚本执行的排查顺序

第一步看浏览器，而不是只看发布流水线的下载日志。记录页面 URL、资源最终 URL、请求是否跨源、是否经过重定向、元素上的 integrity 和 crossorigin，以及 Console 的具体错误。开发者工具显示的 200 和浏览器允许脚本执行是不同观察点。若是模块脚本，还要记住模块加载本身使用 CORS；不能把经典脚本默认 no-cors 的行为直接套到模块上。MDN 的 crossorigin 说明列出了匿名和带凭据两种模式。

第二步核对响应头与请求凭据模式。公开 CDN 资源一般不需要跨源凭据，crossorigin="anonymous" 使跨源请求不携带目标站点的 Cookie 等凭据，服务器可为公开内容返回 Access-Control-Allow-Origin: *。只有确实需要凭据时才考虑 use-credentials：此时服务器必须返回明确的允许来源，并设置 Access-Control-Allow-Credentials: true；通配符来源与凭据请求不能组合。如果服务器按 Origin 动态返回允许值，还应检查 Vary: Origin，避免共享缓存把某个来源的响应误用到另一个来源。MDN 的 CORS 指南和配置建议分别说明了这些条件。

第三步把摘要绑定到真正要发布的文件。仓库中的未压缩源码、构建目录文件、CDN 实际返回的最终文件可能不是同一份内容。包版本升级、压缩器差异、发布脚本重写、边缘代理变更都会使旧摘要失效。发布清单应保留资源 URL、锁定的版本、最终产物摘要、生成它的构建标识，以及是否允许对响应做变换。下面只是命令形态示意；本文没有运行它，也没有对任何 CDN 实测：

curl -fsSL 'https://cdn.example.invalid/lib/4.2.1/app.min.js' \
  | openssl dgst -sha384 -binary \
  | openssl base64 -A

命令输出需要加上 sha384- 前缀，才能与 HTML 中相同算法的 integrity 值比较。但下载工具与真实浏览器可能遇到不同的重定向、缓存、请求头或边缘配置，所以命令只能作为产物核对手段，不能取代浏览器验收。测试环境可以分别制造错误摘要、缺少 CORS 头和成功配置，确认失败各自发生在哪一层；这些是建议的测试设计，不是本文已执行的结果。

更新和回退要保留相同的安全意图

固定完整性摘要更适合明确版本的资源：更新库版本时先审查变更，再从最终构建文件生成新摘要，最后让 URL、锁文件或版本清单与它一起变更。如果 URL 始终指向 latest 这样的可变别名，页面却固定旧摘要，就把“自动跟随最新内容”与“只接收固定字节”这两个相互冲突的目标放在一起。可变 URL 不是绝对不可用，但必须有生成新摘要并审核发布的明确流程。

失败时不要把 integrity 删除后当作普通恢复。如果故障源是 CORS，删除摘要可能恰好绕过一项安全检查，却没有修复服务器配置。如果摘要确实不匹配，换到另一个未经审查的镜像则把供应链信任转移给新的来源。更稳妥的退路是：关键功能使用本地已审查且同样固定摘要的副本，或阻止关键操作并说明资源不可用；非关键增强功能才可降级。选择取决于缺失脚本会影响什么，而不是页面是否仍能显示外壳。

同样，摘要命中不能替代依赖审查。若最初选定的代码含有问题，SRI 只会确认浏览器拿到的正是那份代码，不会让它变安全。代码来源、版本更新、业务测试、CSP 和 SRI 要分别负责各自的边界。关于执行许可而不是资源字节的另一层约束，可参阅响应范围内的 CSP nonce；其中的 nonce 也不能替代 SRI 的内容摘要。

同源资源也需要 crossorigin 吗？

不一定。这里的附加 CORS 条件针对跨源 SRI 请求；同源资源走 same-origin 请求模式，规范的完整性校验算法也接受该模式。跨源第三方脚本则需要把 integrity、适当的 crossorigin 值和服务器 CORS 响应一起检查。不要为了“安全”机械给所有资源加同一种属性，先按资源来源和凭据要求确定请求模式。

出现“有 integrity 但没加载”的情况，先保存浏览器实际请求与响应信息，再分开确认 CORS 是否放行、响应字节是否匹配最终产物、以及后续策略是否允许执行。每种失败各修各的条件，回退时继续保留经过审查的字节身份；不要用删掉属性或换地址来掩盖尚未定位的问题。
