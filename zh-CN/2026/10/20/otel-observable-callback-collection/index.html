Observable 回调不是独立后台定时任务

注册只提供采集时的观测逻辑；调用时机由 Reader 的采集决定，不能假设每次请求执行。

正文

核心要点

  • Observable 回调按采集需求调用，注册 Instrument 不等于创建业务定时任务。
  • MetricReader 发起的采集决定回调观测范围，多个 Reader 不能用一个固定频率概括。
  • 用可控状态与显式采集区分业务事件、回调观测和后端展示。

创建 ObservableGauge 并注册回调，意味着应用提供了“采集时如何观察数值”的函数，不意味着应用自动多了一个独立后台定时任务，更不意味着每次业务请求都会执行该函数。OpenTelemetry Metrics API 规范明确说异步指标回调按需调用，并指向 SDK 的采集过程。何时调用要看实际 MetricReader 与采集配置；应用请求的频率是另一条时间线。

注册的是观测逻辑，不是业务事件钩子

设想服务维护一个内存队列。请求进入时把任务放入队列，工作进程完成后移除；团队想用异步 Gauge 展示当前长度。回调读取队列当前大小并记录一个观测值。若一分钟有两千次请求，而采集器十五秒收集一次指标，回调不应被理解为“被请求调用两千次”，它更接近在每轮采集时读取某个状态快照。规范里的“异步”指测量发生于采集需求触发的回调，而不是语言层的 async/await，也不保证额外后台线程由业务 API 创建。

这个区别直接影响选型。要统计这段时间接收了多少任务，应在任务接收事件上用同步 Counter 增加；要看采集时刻仍有多少待处理任务，可以用异步 Gauge 观察队列长度。把“累计到达量”写在只采样现值的回调里，既可能漏掉两次采集之间入队又出队的任务，也会混淆“当前存量”和“期间流量”。反过来，在每次请求里为当前队列长度执行一次 Gauge 回调，也不是 API 约定的调用方式。度量对象首先要回答是事件累计、变化量，还是当前可观察状态。

真正决定调用时机的是采集链

Metrics API 把 MeterProvider、Meter、Instrument 等对象分层；应用通过 Instrument 注册回调。Metrics SDK 规范的 callbacks 部分进一步要求回调为发起采集的特定 MetricReader 调用，其观测只属于该 Reader 的采集。SDK 还建议为回调设置超时，避免无限等待，并要求同一 Instrument 下一轮采集开始前完成上一轮回调。这些是规范约束，具体 SDK 的调度、导出间隔和超时接口仍须查所用语言及版本实现。

因此有两个 Reader 时不能偷懒说“回调每隔十五秒必然执行一次”。不同 Reader 可能有不同采集时机；一次显式采集也可能触发回调。若应用把昂贵数据库查询塞进回调，每次采集的成本会落在指标管线里，甚至拖慢采集或超时。设计时可让业务流程维护一个线程安全、读取成本可控的当前值，回调只读取它；如果必须查询外部系统，应明确时限、失败处理和数据新鲜度。否则观察代码本身会变成新的负载来源。

另一个反例是把回调当作周期任务来更新业务状态。假设每次回调顺手清理过期订单：当某环境没有启动采集、Reader 被停用或导出链路变化时，清理频率也会变化。业务清理应由明确的任务调度或请求事务承担，指标回调只观察；可观测性不应成为业务正确性的隐藏前提。即使某个 SDK 在默认配置下确实每隔固定时长调用，原因也来自所配置的采集器，而不是注册 Observable 本身给出的独立调度承诺。

从一个数值追到可验证的时刻

在隔离测试里，可建立一个可控队列状态：先置为 3，触发一次已知 Reader 的采集，记录回调调用次数、读到的值与输出的属性；再在两次采集间把状态改为 5 并触发下一次采集。预期是观测值反映采集时读取的状态，而不是每次业务状态变化都自动产出一条记录。若 SDK 支持手动采集，用它比等待定时导出更容易区分“请求发生了”和“采集发生了”。执行时还要记录 SDK 版本、Reader 类型、采集间隔、回调超时设置，以及是否存在多个 Reader，避免把一次演示外推到所有环境。

测试还应覆盖回调抛错、耗时超过采集窗口、返回重复属性集和数据源短暂不可用。该怎样上报错误以及是否保留上一轮值，应按 SDK 行为和仪表盘语义核验，不要自称“没数据等于零”。对队列长度而言，读取失败不是空队列；若强行上报零，运维人员可能误判积压已清除。对于属性标签，用户维度、订单 ID 等高基数信息也不应未经预算就塞进回调输出，否则一次采集可能产生大量序列。

这里的队列例子是未执行的设计推演，没有真实 SDK 输出。规范支持的是回调按需、Reader 采集范围与超时等边界；具体是否每十五秒、一次采集中调用几次、失败后如何呈现，必须用当前 SDK 和配置实测。相关阅读是站内 Delta 与 Cumulative 指标时间语义：那篇处理聚合区间，本篇处理观测何时发生，两者不能互相替代。

还有一个采集层面的边界：异步指标的观测值通常代表某次采集看见的状态，不能凭两次导出之间的空白推断队列一直为零。若同一队列由多个进程分别观测，每个进程的数据还要按资源与标签区分，再决定仪表盘是否应求和。把所有进程的 Gauge 不加辨别地取最后一个值，可能只看到某个副本；把每个副本的累计事件计数当当前队列长度相加，同样会误读。采集回调负责提供本进程此刻的测量，跨副本聚合和显示窗口属于后续查询设计。

给监控需求写验收条件时，最好把三个时间点分别记录：业务状态何时变化，Reader 何时启动采集，后端何时收到并展示数据。数据更新慢，可能是采集间隔、导出链路或查询窗口，并非回调“没有在请求里执行”的缺陷。若产品真正需要每个请求的事件计数，就在请求处理路径记录同步指标或业务日志，而不要提高异步回调频率来模仿事件流。
