Object.hasOwn：把自有字段与原型继承分开

自有字段、继承字段和值为 undefined 各有不同语义；按输入合同和权限分别验证。

正文

核心要点

  • Object.hasOwn 区分自有属性与继承属性，自有 undefined 仍算存在。
  • 无原型对象或覆盖 hasOwnProperty 的对象不能安全依赖对象自身的方法。
  • 字段自有、值有效、身份获授权是三道不同的更新判断。

配置对象读到 role，不等于这次输入真的提供了 role。JavaScript 查找属性时可以沿原型链取得值；若业务问的是“当前请求是否明确带了这个字段”，必须检查自有属性。MDN 的 Object.hasOwn 文档说明，自有属性返回真，继承属性或不存在的属性返回假；自有属性的值即使是 undefined 或 null，仍算存在。这个区别是输入合同的边界，不只是选择一个较新的 API 名称。

三种“有”不能混用

假设一个处理更新请求的函数收到对象 patch。"role" in patch 询问对象及其原型链上是否能找到这个名称；Object.hasOwn(patch, "role") 只问对象自身是否直接声明该属性；patch.role !== undefined 则看读取到的值是否不为 undefined。三者回答不同问题。属性继承而来时，前两项可能相反；自有属性明确设为 undefined 时，后两项也可能相反。若更新语义是“省略 role 就不改角色，提供 role 则校验并更新”，只看读取结果会把这两种情况混在一起。

一个说明性对象可以用 Object.create({ role: "admin" }) 建立原型，再在对象自身只加 name。读取 patch.role 会得到 admin，"role" in patch 为真，自有属性检查却为假。若服务端因此把继承值当成用户提交的权限变更，就越过了输入来源边界。示例表达风险机制，不代表只加 Object.hasOwn 就完成安全防护：服务端仍要检查身份、权限、允许字段和值的合法性，不能把“自有”直接等同“可信”。对无信任输入尤其应避免把原型链读取当作用户意图。

反过来，自有属性 role: undefined 也是存在的。若补丁协议规定显式 undefined 为非法，Object.hasOwn 应先让它进入校验，再由校验拒绝；不能因为值是空就把它当作省略。若协议真的把 undefined 和省略视为同义，可以在边界处有意合并，但要明示原因。JSON 传输不会原样表示 undefined 对象属性，因此内存对象与 HTTP JSON 请求的可达状态也不同；此处讨论 JavaScript 对象语义，实际接口需检查序列化后的载荷。类似的“缺失和值为空要分开”问题，可参考有效零值与默认配置。

为什么不直接调用对象自己的方法

patch.hasOwnProperty("role") 看似简短，但某些对象以 Object.create(null) 创建，没有从 Object.prototype 继承这个方法；另一些输入对象可以自有一个名为 hasOwnProperty 的字段，覆盖方法。MDN 推荐静态的 Object.hasOwn(obj, key)，正因为它不依赖待检查对象身上的同名方法。旧环境里可用 Object.prototype.hasOwnProperty.call(patch, key) 作为受控替代，但要确认目标运行时和兼容性要求。检查属性存在，不应该先相信不受信任对象上可调用的成员。

还有枚举问题。for...in 会遍历可枚举的继承属性；若不得不用它处理输入，应在循环里以自有属性检查过滤。若需求只是列出对象自身可枚举的字符串键，Object.keys(patch) 更贴近目的。Object.hasOwn 也会对不可枚举的自有属性返回真，而 Object.keys 不会列出它。它们不是彼此“更安全”的无条件替代，而是自有性与可枚举性两条轴。符号键也能是自有属性，但 JSON 载荷字段通常是字符串键；审查时要认清源数据类型。

一条更清楚的更新路径可以写成：先把传入值限定为预期对象形状；按接口允许字段白名单遍历，而不是无差别复制输入所有键；对每个允许字段检查它是否自有；若自有，再校验其类型、范围与当前用户权限；最后生成受控更新。若使用对象展开或通用深合并工具，还要检查它们对原型、访问器和特殊键的行为。Object.hasOwn 是此路径的一道判断，不是序列化器、模式校验器或授权器。

工作示例里，用户提交 {name:"Ada"}，业务应只改名字，不应因为某个库给它接上含 role 的原型就改变角色。用户提交 {role:undefined}，则按已声明协议拒绝或明确忽略；用户提交 {role:"admin"}，虽然 role 是自有属性，仍必须因权限不符拒绝。三项预期分别验证来源、值和授权，避免一个“属性存在”测试假装覆盖三层。若对象有 getter，读取属性可能运行代码；在不信任对象上枚举或读取时还需考虑访问器副作用，不能把纯粹的属性判断误当作无副作用的完整数据提取。

可执行的测试矩阵应包括普通自有字段、继承字段、自有 undefined、自有 null、无原型对象、覆盖 hasOwnProperty 的对象、不可枚举自有字段，以及真正无此字段。对每项分别断言 in、自有性、读取值和最终业务动作。静态方法的局部语义可在 Node 中独立验证，但实际请求解析器、ORM 或合并库怎样构造对象，仍需在项目入口检查。本文的流程是设计建议，不宣称任何生产端点已修复。

在 Node v24.21.0 的独立脚本中，上述继承示例实际得到 read:"admin"、inOperator:true、own:false；自有 undefined 的检查返回 own:true；无原型对象上的自有 role:null 也返回真。脚本、命令与原始 stdout 保存在本批审校材料。这只核对当前 Node 环境中语言 API 的局部语义，不能说明浏览器中的对象来源或某个后端的授权逻辑已经正确。

把这个结果带回补丁接口时，应让失败路径也可观察。例如请求只带姓名但某个合并步骤从原型读到角色，审计日志应记录“角色字段未提交”，而不是把最终对象展开后的角色当作用户输入；若服务拒绝自有 role:"admin"，应有明确权限错误而非静默忽略。运行测试可以在解析器入口和实际更新 SQL 之间分别观察字段存在性，确认白名单过滤没有因中间对象重建而改变含义。这样才能发现“语言级自有检查正确，数据层仍写入了不应修改的列”的断裂。

最后把“字段在对象里”改成能审查的问法：它是这次输入自有的字段吗？它的值合法吗？这个身份能改它吗？三个问题有三个答案，才能阻止原型链上的偶然值或恶意值混进业务更新。
