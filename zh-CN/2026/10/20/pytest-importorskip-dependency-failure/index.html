依赖装坏了，pytest.importorskip 为什么不该静默跳过？

区分可选模块缺席与模块内部导入失败，并标明 pytest 9.1 默认异常范围的变化。

正文

核心要点

  • pytest 9.1 文档将 importorskip 默认捕获范围收窄为 ModuleNotFoundError；跨版本作业必须检查实际版本。
  • ModuleNotFoundError 仍可能来自包内部缺失的传递依赖，不能单凭异常类名认定目标包可选缺席。
  • 完整支持的 CI 作业应先验证依赖导入再跑真实行为测试，并审阅跳过节点。

测试套件里有一个可选数据库驱动。开发机没安装它，相关测试跳过很合理；CI 明明安装了驱动，但驱动导入内部模块时坏掉，整组测试也被跳过，就会把打包事故伪装成“环境没有可选能力”。这个跳过函数恰好站在这条边界上：它应该表示何时允许跳过，而不只是减少红色测试。尤其要看运行的 pytest 版本，因为默认捕获的异常范围在 9.1 发生了变化。

设 my_adapter 是产品声称在某些环境支持的可选加速模块。测试文件中通常会这样调用：

import pytest
adapter = pytest.importorskip("my_adapter", reason="optional adapter absent")

def test_adapter_round_trip():
    assert adapter.round_trip(b"abc") == b"abc"

若目标环境明确不安装 my_adapter，跳过是测试契约的一部分：该平台根本没有可测的功能。若 CI 的依赖清单明确安装了它，测试却跳过，结果就值得追查。你需要同时记录 pytest 版本、目标模块是否可定位、导入异常的类型与消息、以及该环境是否本来承诺运行这组测试。只看最终“通过且若干跳过”无法分辨正确豁免和配置错误。

pytest 稳定版 API 文档写明：exc_type 参数从 8.2 起存在；9.1 起默认值变为 ModuleNotFoundError。显式传 exc_type=ImportError 可以扩大范围，让模块导入期间抛出的普通 ImportError 也导致跳过。在旧版和新版都运行的项目，不应凭印象判断行为；先锁定实际版本并阅读对应文档与测试输出。本文讨论的是当前稳定文档所述的 9.1 默认规则，不把它倒灌到过去所有 pytest 版本。

# 需要有意识地选择，而非为了让 CI 变绿随手扩大异常范围
adapter = pytest.importorskip("my_adapter", exc_type=ImportError)

这段显式写法并非通用改进。设包已安装，但它的 __init__.py 写了 from .native import encode，而某次构建没有生成 native 扩展。导入 my_adapter 时可能抛出 ImportError 或 ModuleNotFoundError。若一律把导入错误解释为“可选模块缺席”，测试会安静消失，恰好避开了本该测试的坏构建。相反，若该环境原本不承诺安装这个模块，跳过才是合法结果。区别由发布矩阵和失败来源决定，不由“异常类名看起来像缺包”单独决定。

还要谨慎理解新版默认的 ModuleNotFoundError。它比捕获所有 ImportError 更窄，但不能仅凭异常类型断定“缺的就是传给 importorskip 的目标包”。已安装包内部又导入了一个不存在的传递依赖，也可能产生 ModuleNotFoundError。诊断时查看异常的缺失模块名称、堆栈和包元数据，再与环境安装契约核对。若测试矩阵要求加速模块必须可用，更直接的做法是该 CI 作业显式检查依赖安装与导入，并让坏导入失败；不要期待一个可选跳过工具替必需依赖把关。

一种清晰的矩阵可以分为两个作业。基础作业不安装加速模块，允许针对该模块的测试被跳过，并断言跳过原因确实是目标可选能力未提供。完整作业安装加速模块，先做最小导入检查，再运行实际功能测试；此作业出现跳过应被视为需要调查的信号。导入成功也不等于功能正确，所以还需要覆盖一个真实行为，例如给定字节输入能否稳定往返。反过来，如果测试只断言 importorskip 返回模块对象，它几乎是在复述导入操作，没有验证产品行为。

把跳过原因写成“optional adapter absent”只能帮助人读报告，不能改变异常语义。对于依赖在不同平台有条件可用的项目，可以在作业定义中明确哪些平台允许缺席；不要用同一个泛化理由遮住每个平台的不同承诺。若包存在但其本地扩展加载失败，产品在该平台其实宣称支持它，测试应该显露失败。若团队选择临时允许这种故障跳过，应把它当作可追踪的限期例外，而不是永久写进 exc_type=ImportError 后忘记。

这里还有收集阶段的时机问题。模块顶层的 importorskip 会使整个测试模块在收集时跳过；如果一个文件混放不依赖适配器的普通测试，那些测试也一起消失。把可选能力测试单独成文件，或在需要它的测试/fixture 边界调用，才能让跳过的作用域符合真实依赖关系。一个带很多无关断言的文件若突然整文件跳过，统计上的“通过率”会高估覆盖。审阅跳过数量和测试节点清单，比只看退出码可靠。

站内 严格 xfail 门槛 讨论了另一种容易让绿色流水线掩盖变化的测试标记。这里的重点不是拒绝所有跳过：可选功能在未安装环境中确实不应把整套测试打红；重点是测试矩阵必须能区别有意缺席、意外漏装和已安装但损坏。验收可建立一个小型隔离包：目标包完全不存在、目标包存在且正常导入、目标包存在但内部导入失败，分别记录不同 pytest 版本的原始收集与执行输出。当前环境未运行这样的 pytest 矩阵，也未声称任何特定项目的 CI 已经误跳过。本文对版本与参数的陈述来自当日读取的 pytest 官方文档；真实仓库应以锁文件和作业镜像中安装的版本为准。

如果故障发生在平台特定的二进制扩展，诊断报告最好保留 Python 版本、操作系统与架构、wheel 名称和完整 traceback。这样才能分辨“这个平台没有分发包”与“分发包在声称支持的平台上损坏”。不应把完整堆栈中的私密路径或令牌直接发到公共页面，但内部 CI 工件应足以还原异常位置。对维护者而言，关键判据不是跳过比例低不低，而是每个跳过是否都对应明示的能力缺席。一次跳过也可能掩盖关键路径；一百次跳过若全是矩阵允许的环境差异，也未必是缺陷。
