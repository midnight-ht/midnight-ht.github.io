upgrade-insecure-requests 不能代替 HSTS

页面内资源升级与用户进入站点是两条时间线；用 CSP、重定向和 HSTS 分别验证资源与入口。

正文

核心要点

  • 升级指令改写页面发起的不安全资源请求，目标不支持 HTTPS 时资源会失败。
  • HSTS 在浏览器通过 HTTPS 学到策略后约束该主机的后续连接，首次接触另需处理。
  • 分别验收资源加载、首次入口、已学习 HSTS 的入口与跨站导航。

给页面配置 upgrade-insecure-requests，浏览器会把页面发起的不安全资源请求改写到 HTTPS；它并不能保证用户第一次通过外部 HTTP 链接进入站点时，顶层导航已经受保护。这里有两条不同的时间线：一条发生在浏览器拿到页面策略之后，另一条发生在浏览器取得这个策略之前。把它们混在一张“全站 HTTPS 已完成”的检查表里，最容易漏掉入口。

页面已经打开后，指令处理什么

假设 https://shop.example 的结算页仍有一张图片写成 http://cdn.example/logo.png。页面响应包含 Content-Security-Policy: upgrade-insecure-requests，浏览器在网络请求发出前把资源 URL 改成 HTTPS。MDN 明确说明这种改写覆盖页面里的第一方与第三方非导航资源，而且目标没有 HTTPS 时请求会失败，不会回落到 HTTP。这个失败并非意外副作用：回落会让迁移期间的“看起来正常”掩盖明文传输。迁移负责人应把失败资源列为待修复资产，而不是关闭指令让页面勉强显示。MDN 的指令说明。

这个规则不等于“字符串里所有 http: 都会被改”。例子中的页面链接若指向第三方站点的 HTTP 地址，跨站顶层导航有不同的处理边界；不能把资源升级截图当作外部链接也安全的证据。尤其要区分两个看起来相近的动作：结算页在加载自身资源，以及用户从邮件或另一站点点击链接进入结算页。后一个动作可能发生在浏览器获得本站 CSP 之前，目标页面无从向过去的请求发指令。

用户尚未取得页面时，HSTS 处理什么

Strict-Transport-Security 是 HTTPS 响应给浏览器的主机策略。浏览器记住该主机后，未来遇到它的 HTTP URL 会先在本地改为 HTTPS；遇到证书错误也不能让用户点击继续。它约束的是后续连接的入口，而非只在当前文档内发生的资源加载。MDN 的 HSTS 说明还特别指出：浏览器忽略 HTTP 响应里的 HSTS，初次未获知策略时仍有首次接触窗口。把 HTTP 到 HTTPS 的服务端重定向做好是必要的入口处理，但首次 HTTP 请求已发出，重定向不能倒转这段历史。

假设用户收藏了 http://shop.example/orders。在已经收到有效 HSTS 的浏览器中，下次打开收藏时先升级 URL；在从未访问的浏览器中，若域名不在预加载列表，浏览器可能先发 HTTP 请求，再跟随重定向。upgrade-insecure-requests 对这两个浏览器的差异没有解释力，因为它属于页面响应中的策略。HSTS 预加载可以缩小首次接触窗口，但涉及独立申请与长期承诺，不能因为页面已正常加载就顺手加上 preload。长期 max-age、includeSubDomains 之前，必须盘点仍只支持 HTTP 的子域与证书更新责任。

迁移方案要拆成两条验收链

一个可操作的迁移清单应先确认每个业务主机都有有效证书与 HTTPS 路由，再检查页面和第三方资产。比如图片库目前只能用 HTTP，加入升级指令后它会直接失败；工程选择可以是迁移供应商资源、在受控域重新托管合规资产，或者暂缓该页面的强制策略。把失败解释为“浏览器兼容性问题”会错过根因。对于站点入口，则检查 HTTP 请求是否重定向到同一目标路径、HTTPS 响应是否带正确 HSTS，以及子域是否准备接受覆盖。

策略值也要按风险分阶段。初期较短的 max-age 便于发现证书或路由遗漏；延长后浏览器缓存的策略不会因为服务器暂时删掉响应头而立即消失。MDN 说明撤销需要浏览器再次通过 HTTPS 收到 max-age=0，已经存储的策略还可能独立存在于各子域。带 includeSubDomains 的顶级域配置尤其要检查上传、旧后台、邮件点击落地等边缘主机。某子域无法稳定提供 HTTPS 时，不应先把整个域名树锁定。这个取舍是对回退能力的审查，不是对 HTTPS 目标的让步。

验证时分开记录四类观察：从全新浏览器或清理相关站点状态的环境发起首次 HTTP 入口；在已收到 HSTS 的环境重复入口；在受保护页面加载 HTTP 资源；点击一个跨站 HTTP 导航。网络面板要看实际发出的 URL、是否发生服务端重定向、是否因升级后目标不存在而失败。响应头记录应标明来自 HTTP 还是 HTTPS；只看最终地址栏锁标，不能证明首次请求没有经过明文。这里的四类观察是测试设计，本稿没有运行浏览器或检查任何真实站点。

还要检查策略真正覆盖的是哪一个主机。shop.example 的 HSTS 不自动替 cdn.example 设置长期规则；页面里的 CDN 资源被 CSP 升级，只说明这一页发出的请求按本页策略走 HTTPS。若 CDN 的 URL 另被用户直接访问，或者供另一站点引用，它是否有自己的入口保护，需要独立核验。同样，某个页面带 CSP 并不保证站点所有路径都带同样策略：错误页、登录跳转和静态落地页可能由不同服务返回。验收清单应以实际响应和主机为单位，抽到关键入口，而不只在一个正常页面看一次响应头。对于第三方资源，团队能控制的是本站引用和替代供应商的决策，不能把对方的 HSTS 配置写成自己的上线成果。

因此，验收报告里的每个“已升级”都应附上对应请求的发起点和目标主机。

把“页面资源不再走明文”和“用户入口以后直接走加密连接”写成两项独立验收条件，才能分别归责 CSP、重定向与 HSTS。相关的观察模式上线问题可参看站内文章 CSP 报告没有告警，就能直接切到强制阻断吗？；报告为空不能替代上述入口与网络验证。
