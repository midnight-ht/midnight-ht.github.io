ClientIP 不能替代共享登录状态

Service 按客户端 IP 选择 Pod，不认识用户或 Cookie；用重建、换 IP 和共享出口验证登录方案。

正文

核心要点

  • ClientIP 亲和以客户端 IP 为键，默认亲和配置是 None，超时并非登录期限。
  • Pod 重建、出口地址变化或共享 NAT 会揭示本地内存会话的缺陷。
  • 登录续存、撤销与对象授权需由应用状态设计独立保证。

把 Kubernetes Service 的 .spec.sessionAffinity 设成 ClientIP，可以让同一客户端 IP 的连接在一段时间内倾向同一后端 Pod。这是流量路由规则，不是用户身份、登录会话或者数据所有权的规则。若应用把登录信息只放在某个 Pod 内存里，“粘住”或许暂时掩盖问题，但不能给出登录持续性承诺。Kubernetes 的 Service 虚拟 IP 文档明确将该能力描述为按客户端 IP 把连接送往同一 Pod；默认值是 None。

Service 实际记住了什么

Service 入口面向连接与后端端点工作，不读取登录 Cookie，也不知道一个 IP 背后有几个账号。ClientIP 的键是网络看到的客户端 IP；同一台办公网关之后的多名用户可能共享这个键，同一用户换移动网络后又可能出现不同键。把网络地址与账号一一对应是错误假设。流量走到同一个 Pod，并不会自动让 Pod 拥有正确、最新的认证状态；应用仍要从可信会话凭据解析身份并检查该身份的权限。

文档允许设置 .spec.sessionAffinityConfig.clientIP.timeoutSeconds，默认 10800 秒，即三小时。这个超时是亲和保持时间，不是登录过期时间。产品需求说“登录保持七天”，不能从这里推导为七天；反过来，用户已退出登录时，流量仍可能被送到原 Pod，但应用必须立即拒绝旧凭据。把路由超时错写为会话超时，会直接混淆安全事件的处置：撤销登录是认证系统的职责，不能等 Service 映射自然过期。

一个双副本的假设故障

设想登录接口把 session_id → user_id 存在 Pod A 的内存。用户首次登录后，来源 IP 被亲和到 A，连续访问看起来正常。发布滚动更新时 A 被替换，新的 Pod 没有原内存数据；客户端请求即使继续落在“同一个”网络意义上的后端选择，也不是原进程，登录状态丢失。若代理更换了来源 IP，或者亲和窗口届满，请求可能落到 Pod B，同样会失败。更危险的是团队因表面稳定而没有覆盖多副本、重启和撤销路径，直到高峰期才发现状态设计依赖路由偶然性。

另一个反例是多人共用出口 IP。A 用户和 B 用户都被粘到 Pod A，Service 并不会把两个人变成一个登录会话；若应用因为“同 IP 同 Pod”而省掉身份检查，就会制造越权。ClientIP 也不能替代针对对象的授权：同一个登录用户请求别人的订单，仍须在应用或服务端按订单归属拒绝。Service 没有这些业务数据。

状态应该放在哪里

需要跨副本延续的登录可以采用服务端共享会话存储，或在合适威胁模型下采用可验证的有界令牌；两者都要明确到期、轮换、撤销和权限变化如何生效。共享存储方案让 Pod A 与 Pod B 根据同一会话标识查询状态，但要设计存储故障时的处理与过期清理。令牌方案可减轻每次读存储的需求，却要处理签名密钥轮换、泄露后撤销窗口与权限变化。哪种方案合适取决于产品对即时撤销、延迟、故障恢复和运营复杂度的要求，不能由 ClientIP 这个路由开关替团队决定。

仍可保留亲和用于特定性能或兼容需求，例如短时连接的局部缓存命中，但必须把它写成优化条件。应用在任一健康副本上应能给出正确的认证与授权结果。某些长连接协议另有连接生命周期问题，不能把 Service 的 IP 亲和直接泛化为应用协议层的会话粘性。部署链上若还有入口控制器或云负载均衡器，它们可能另有自己的亲和规则；此文只讨论 Kubernetes Service 的这一配置，生产路径需逐层核对实际来源 IP 与路由行为。

用故障注入检验边界

测试设计应先固定真实登录凭据，再分别观察稳定网络、切换客户端出口、滚动替换 Pod、等待亲和超时后访问。记录请求到达的 Pod、客户端 IP、认证结果和对象授权结果，避免只用“页面没掉线”一句话代替证据。还需两个账号在同一 NAT 出口下并发访问，确认它们的身份和数据没有互串；退出登录后重复旧凭据，确认撤销由认证系统执行。若关闭亲和后业务立刻失效，说明应用状态依赖副本局部内存，应修正状态方案或明确业务接受的故障边界，而不是简单调长超时。

测试时还需知道 Kubernetes Service 真正看到的客户端 IP。用户浏览器之前可能有 CDN、入口控制器或云负载均衡器；它们的转发和地址转换会影响亲和键。若所有外部请求在 Service 层看起来来自同一代理 IP，亲和可能把大量不同用户集中到同一个后端，而不是按最终用户分散。反过来，同一用户的请求若经多个出口 IP，亲和并不稳定。应用日志中的 X-Forwarded-For 值和 Service 用来做路由的 IP 不能随意画等号；前者可能经过代理添加，后者取决于实际网络路径。容量评估要以真实拓扑为准。

登录方案如果采用共享存储，还要确认同一用户从两个副本访问时，权限变更和登出是否及时同步。只把会话对象从 Pod 内存移到共享缓存，不设置到期与撤销策略，仍不能满足“退出后旧令牌失效”。若采用令牌，签名有效也不等于当前业务权限有效；比如员工被移出项目后，订单审批接口要决定是否实时读取权限。ClientIP 对这类时间一致性问题没有帮助。

实施时可先在预发布环境关闭亲和并重启单个副本，运行登录、刷新、登出和跨账号访问的自动化，再决定生产是否仍需亲和。若关闭后发现问题，应记录具体失败请求和状态存储位置。这样修复任务会落到真实状态边界，而不是给路由参数加一个更长的秒数。

这些是未执行的验收设计，本文没有真实集群结果。实际交付可把“路由是否稳定”“登录是否持续”“撤销是否生效”“跨账号是否隔离”列成四个不同断言。站内 依赖审计修复后的发布检查 同样提醒发布不能只凭一个绿色信号：这里配置生效也只证明路由层行为，不能代替业务会话验收。
