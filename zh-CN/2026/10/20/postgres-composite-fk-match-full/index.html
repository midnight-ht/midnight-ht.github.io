复合外键只填了一半，为什么还能通过？

解释默认复合外键遇到 NULL 的匹配规则，以及 MATCH FULL 和 NOT NULL 对可选关系的不同约束。

正文

核心要点

  • PostgreSQL 默认复合外键在任意引用列为 NULL 时可跳过父行匹配，半填数据可能通过。
  • MATCH FULL 只豁免所有引用列均为 NULL 的可选关系；必填关系仍需 NOT NULL。
  • 迁移前必须清查两种半填组合，不能用虚构默认账户制造约束通过。

一条订单明细同时保存 tenant_id 和 account_id，两列合起来引用账户表。某次导入只给了租户编号，账户编号是 NULL，插入却没有触发外键错误。查不到对应账户并不是数据库验证疏漏；对于 PostgreSQL 默认的多列外键，只要引用列中有任意一个为 NULL，这行就不必满足引用匹配。若业务要求“账户关系要么完整填写，要么完全不填”，默认语义比产品契约宽松。

先把问题具体化。账户 ID 只在租户内唯一，因此账户表以 (tenant_id, account_id) 为联合主键。事件表可选地指向账户，且将两个编号分别存储：

CREATE TABLE account (
  tenant_id bigint NOT NULL,
  account_id bigint NOT NULL,
  name text NOT NULL,
  PRIMARY KEY (tenant_id, account_id)
);
CREATE TABLE event_default (
  event_id bigint PRIMARY KEY,
  tenant_id bigint,
  account_id bigint,
  FOREIGN KEY (tenant_id, account_id)
    REFERENCES account (tenant_id, account_id)
);

假设账户表已有 (7, 19)。事件填 (7, 19) 时，外键要求找到该组合；填 (7, 20) 且没有对应账户时应失败。关键反例是 (7, NULL)：默认多列外键不会强迫它去匹配 (7, ?), 因而可以通过外键检查。(NULL, 19) 同样属于部分空值，不能因为另一列看起来像真实编号就认为引用有效。该行为来自 PostgreSQL 18 外键文档 的原文规则：引用列中任何一列为空，引用行通常便不需满足外键约束。它不同于“整组为空才表示无关系”的常见业务想象。

如果“可选账户”只允许完整的一对或全部为空，把外键写成 MATCH FULL。同一张表的示意约束如下：

CREATE TABLE event_full (
  event_id bigint PRIMARY KEY,
  tenant_id bigint,
  account_id bigint,
  FOREIGN KEY (tenant_id, account_id)
    REFERENCES account (tenant_id, account_id) MATCH FULL
);

这个选项改变的是空值豁免条件：只有所有引用列都为 NULL，才能免于引用匹配。于是 (NULL, NULL) 表示没有账户，允许；(7, 19) 表示完整关系，必须在账户表中存在；(7, NULL) 和 (NULL, 19) 都是半填状态，不能通过。它没有让空值等于任何实际账户，也不会自动创建缺失的账户。写入路径必须在发送 SQL 前决定到底是不关联账户，还是有足够信息建立关联，不能把“暂时还没拿到 account_id”作为永久半填数据存下来。

表设计要从业务语义倒推，而不是看到 MATCH FULL 就一律加上。如果事件必须属于账户，两列都设 NOT NULL，再加复合外键；这样连全空也会被拒绝。若事件可以完全匿名，MATCH FULL 表达完整或全空两种有效状态。若 tenant_id 本身还承担事件归属租户的必填字段，而 account_id 可选，就不能简单把同一对列同时当“必填租户”与“可选的整组引用”：tenant_id NOT NULL 加 MATCH FULL 会使 account_id NULL 的匿名事件失败。可能需要独立的归属字段、不同键设计，或重审“匿名但仍属某租户”的模型。约束应该准确表达关系，不该为了通过迁移而牺牲可表达的状态。

再看一个容易掩盖问题的应用层条件：WHERE account_id IS NOT NULL 的报表会把半填行排除，于是数据看起来“没有坏”；等到对账、导出或跨租户关联时，孤立的 tenant_id 才冒出来。单列非空检查也不足以完整解决可选关系：只给其中一列 NOT NULL，其余仍可为空，而默认外键依旧可能跳过匹配。应用验证可以给用户更好报错，但数据库约束是所有写入入口共用的最后一道关系规则，包括批处理、管理脚本和未来新服务。

已有表不能只改 DDL 然后相信历史数据自动变好。先统计两种半填组合和全空组合，逐条确认它们代表“缺字段但应补齐”“本来应该匿名”还是“错误租户”。修复方式依赖事实来源，不能把所有 NULL 都填成一个默认账户，否则会制造假的外键成功。迁移时应在隔离环境运行相同的约束变更与验证，记录违例样本及修复结果。若想先加约束再逐步清理，也要理解待验证约束和最终验证之间的阶段，避免把“新写入受到限制”说成“历史行已全通过”。本文没有执行这类迁移。

多列外键的另一条独立问题是性能。外键保证引用关系，却不会自动替应用的每种查询安排合适的子表索引；账户删除或更新时的访问路径要单独评估。站内 子表外键索引检查 讨论这层性能问题。MATCH FULL 解决的是数据允许哪些空值组合，不是查询会不会走索引；两个决策不能互相替代。也别把它与普通 CHECK (tenant_id IS NULL = account_id IS NULL) 简单等同：即使写出空值组合检查，还需复合外键验证完整的一对确实存在。

验收可以把输入矩阵写成数据库测试：插入现有完整键成功，不存在的完整键失败，全空在可选关系表中成功，两种半填组合都失败；必填关系表则全空也失败。再通过应用导入入口提交相同矩阵，核对是否把数据库异常映射成能定位字段的错误，同时保存服务与数据库版本。这里根据 PostgreSQL 18 官方文档推导预期，并未连接数据库运行这些 SQL；设计判断应由实际迁移数据和业务方确认。若现有模型允许半填只是为了暂存导入中间态，考虑专门的暂存表与明确的状态转换，别让正式表的外键承诺变得含糊。

最后别把约束错误当成坏事本身。导入作业因为 (7, NULL) 被拒绝，意味着原来隐形的资料缺口终于出现在可观测位置。对入口可提供“缺账户编号，不能建立租户账户关系”的可操作提示；对后台批处理可把失败行写入待修复队列，保留原始输入与关联来源。若业务确实允许导入阶段的部分数据，可以先落在明确标记为未完成的暂存实体，待键值齐备后再转入受复合外键保护的正式表。这样验收时能分别证明“暂存允许不完整”和“正式关系不可半填”，避免一个松散约束承担两种互相矛盾的职责。
