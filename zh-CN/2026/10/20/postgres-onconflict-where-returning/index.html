ON CONFLICT 没报错，RETURNING 为什么没有行？

区分插入、冲突更新和条件拒绝更新，解释锁定但未更新的行为什么不会进入 RETURNING。

正文

核心要点

  • 条件冲突更新可能锁住目标行，但因 WHERE 为假而既不更新也不返回该行。
  • 只在确认单行输入及具体 SQL 分支后，才能把空 RETURNING 解释为旧版本被拒绝。
  • RETURNING 描述语句效果；外层事务的最终提交和当前版本读取仍需分别验证。

一条库存写入语句成功返回，应用却拿到空的 RETURNING 结果。常见误判是把“没有报错”翻译成“原行被更新”，再把空结果解释为驱动漏读。更值得先查的是 ON CONFLICT DO UPDATE … WHERE：冲突行可以已经被找到、锁定，最终却因为条件不满足而没有发生更新。此时语句正常结束，RETURNING 也确实没有那一行。这不是数据库丢掉结果，而是写入契约里本来存在的一条分支。

假设接口接收外部事件，表中每个订单只有一条当前状态。新事件带版本号，只有版本比已保存版本更大时才覆盖。简化表结构如下，order_id 是唯一键，version 是业务版本而非数据库事务 ID。

CREATE TABLE order_state (
  order_id bigint PRIMARY KEY,
  version bigint NOT NULL,
  state text NOT NULL
);
INSERT INTO order_state VALUES (42, 7, 'packed');

写入使用一条 upsert。EXCLUDED 指本次拟插入的数据，条件比较拟插入版本与冲突行当前版本，RETURNING 只要求把本次实际写入后的行交给调用方。

INSERT INTO order_state (order_id, version, state)
VALUES (42, 6, 'created')
ON CONFLICT (order_id) DO UPDATE
SET version = EXCLUDED.version,
    state = EXCLUDED.state
WHERE order_state.version < EXCLUDED.version
RETURNING order_id, version, state;

预期路径是：唯一键 42 命中冲突；更新分支找到目标行；已有版本 7 并不小于候选版本 6；WHERE 为假，所以没有更新；最后 RETURNING 没有行。PostgreSQL 18 的 INSERT 文档明确写明，RETURNING 只返回成功插入或更新的行；因 ON CONFLICT DO UPDATE … WHERE 不满足而“锁住但未更新”的行也不会返回。这里的空集可以表达“旧事件被拒绝覆盖”，不是异常或持久化成功的证据。

现在把输入版本改为 8。如果它在条件评估时仍高于目标行版本，更新发生，RETURNING 才会给出版本 8 的行。若换成一个尚不存在的 order_id，插入路径也返回新行。三条路径的应用语义不同：插入是首次建立，更新是接受较新的事件，空结果是没有发生这两种写入。把它们压成单一的 success: true，会让上游误以为版本 6 已生效；把空结果一律当数据库故障，又会对正常过期事件反复重试。

WHERE 的位置容易被读错。它不是在扫描输入行之前就筛掉候选值，也不是指定唯一冲突目标的条件。PostgreSQL 说明更新条件在确定冲突目标后才评估。因此需要区分“冲突如何识别”和“识别后是否允许更新”。唯一约束保障只有一条候选目标；业务版本条件决定是否改变它。条件失败的行可能被锁定这一点还关系到并发：空结果不能推导出“写入完全没有接触那一行”或“它不会影响另一笔并发操作”。如果为高吞吐队列设计重试与锁等待，需要同时看冲突热键和锁行为，不能只数 RETURNING 行数。

一个清晰的调用接口应先约定结果分类。对于单行 VALUES、DO UPDATE 且带上述版本条件的语句，返回一行表示本次插入或更新发生；返回零行首先检查它是否命中旧版本拒绝路径。若产品要给出“当前版本是多少”，零行本身没有携带这个值；可以在适当事务边界再查，或设计返回当前行的独立读取。不要凭空把候选版本 6 写进响应，冒充库里的版本 7。若并发写者仍在推进版本，后续读取也可能看到更新值，响应文案应避免假装获得与写入条件完全同一时刻的快照。

还要避免反向过度推断。一个普遍的 INSERT … RETURNING 返回零行，原因不只这一种：输入可能是零行，语句可能用了 DO NOTHING，应用甚至可能读错了结果集。只有确认 SQL 是单行输入、冲突动作是这段有条件的 DO UPDATE，并且没有别的过滤路径，才能把零行解释为条件拒绝。查看日志时记录无敏感信息的键、提交版本、受影响行数与 SQL 版本，比只记录“upsert 成功”更可复核。若调试语句被 ORM 改写，还应核对实际发往数据库的 SQL，而不是仅看代码中声明的参数。

RETURNING 的另一个边界是事务提交。它告诉你本条语句实际插入或更新了什么；如果外层事务随后回滚，曾返回的行也不代表最终持久化。站内关于 RETURNING 与提交边界 的文章讨论的是另一层问题。本篇聚焦语句内部的零行分支，调用方既要正确解释行数，也要在事务结束后才宣布业务写入已提交。把这两层混淆，容易在接口日志中同时留下“成功写入”和“最终未提交”的矛盾记录。

上线前可用一个隔离的 PostgreSQL 测试库验收三组输入：新键插入返回一行；同键较高版本更新返回一行；同键较低或相同版本返回零行且存量内容不变。再加一个竞争用例，让两位写者交错提交，确认应用对锁等待和最终版本的处理符合业务设计。保留执行的 SQL、数据库版本和实际输出；只靠本文的推理不能声称生产驱动、ORM 或并发调度已经通过。本文核对的是 PostgreSQL 18 官方文档的语义，没有运行上述数据库语句，因此示例结果是基于文档的预期，而非本环境中的实测记录。

版本规则也要写清楚相等值的处理。如果相同版本的重放事件被视作幂等重复，那么“零行且无更新”是合理的，但响应可以是“已忽略重复”，不该暗示发生新写入；如果同版本而内容不同代表数据冲突，仅靠 version < EXCLUDED.version 会静默忽略这个差异，还需要显式校验或冲突记录。版本为 NULL 的情形则应被表定义挡住，否则比较得到未知值，条件仍不会为真，却把输入质量问题伪装成普通旧事件。示例中的 NOT NULL 因而承担业务判定的一部分，不是随手加的装饰。

验收记录还应拆开数据库事实与接口决策。数据库事实是实际写入行数和返回行；接口决策是把零行归为旧事件、重复事件或需要进一步读取的冲突。前者可由测试库输出证明，后者要由业务规则和响应契约证明。特别是消费者收到重试时，不应根据一次空 RETURNING 就确认所有先前处理步骤已完成；它只描述这条 SQL 的本次写入效果。把状态机的每一步对应到可观察证据，才能在故障排查时回答“版本没有变”究竟是有意拒绝，还是流程漏跑。
