git diff 为空，不等于包含那个提交

文件树相同与提交可达是不同命题；用隔离 DAG 和 merge-base 退出码明确发布审查要证明什么。

正文

核心要点

  • 文件树一致不能推出原修复提交位于目标分支父链。
  • 隔离临时仓库实测 diff 为空而祖先断言为否，脚本与原始输出已留存。
  • 祖先存在也不证明后续提交未撤销修复；还需当前行为和产物证据。

git diff 显示两个分支没有文件差异，只能回答当前文件树是否相同；它不能证明目标分支的历史包含某个具体提交。发布审查若要求“修复提交 X 已进入 release”，要检查提交图的祖先关系。两个结论会在 cherry-pick、重做补丁、rebase 或独立产生相同内容时分开。

同一份内容可以有两条历史

Git 的提交对象记录父提交关系，文件树记录内容。假设基线 B 上有修复提交 X，另一分支从 B 出发重新做出相同的两行文件内容，得到 Y。X 和 Y 的树可以一样，但 Y 的父提交链只回到 B，不经过 X。git diff X Y 没有输出并不矛盾：这是树的比较。问“X 是否包含在 Y 的祖先中”则是在遍历另一张图。Git 官方 merge-base 文档给了直接的 --is-ancestor 模式：第一个提交是第二个的祖先时退出码为 0；不是时为 1，其他非零值可能表示错误。

为避免把想象写成实测，我在与本站仓库隔离的临时 Git 仓库执行了一个最小例子；脚本 git-fixture.sh 与原始输出 git-fixture.txt 保存在本批次审校归档中。环境报告为 Apple Git 2.50.1。脚本创建基线、original 修复分支和从相同基线独立提交同内容的 replay 分支。实际输出是 tree_diff=empty、original_ancestor_of_replay=no、base_ancestor_of_replay=yes；两分支的 merge base 是基线提交。这个结果只证明该临时 DAG 的性质，不是本站某个发布分支的验证。

为什么发布团队仍要关心具体提交？如果变更请求、代码审查、签名、测试回执或漏洞工单绑定的是 X，那么 Y 虽然内容相同，却不自动继承 X 的审核链。Y 可能被重新提交后又改了父链，或者部署流水线按提交 ID 关联产物。反过来，审查目标若只是确认某一文件当前具有修复后的内容，树差异或针对性行为测试可能更贴题。先确定要证明的是“内容”“血缘”还是“产物已部署”，再选命令；不能拿一个命令的绿色结果回答另一个问题。

祖先断言怎样写进检查

对于已知完整提交 ID X 和当前目标提交 Y，可以运行 git merge-base --is-ancestor X Y。退出码 0 支持 X 可从 Y 沿父链到达，退出码 1 表示不能到达。脚本应分别处理退出码 1 与异常退出，避免把仓库损坏或参数错误也写成“未包含”。还要先用 git rev-parse --verify 确认引用解析到了预期对象；分支名会移动，审查记录最好保存最终解析出的完整提交 ID 与目标远程引用状态。只比较本地过期的 origin/release 可能漏掉远端已更新的提交，需先明确拉取/核验范围。

git merge-base X Y 返回的是共同祖先，通常不是“X 已合入”的简单证明。存在交叉合并时可能有多个最佳共同祖先，官方文档也说明不加 --all 时返回哪一个并不确定。用“输出的 merge base 等于 X”作为判断虽是旧式惯用法，但 --is-ancestor 把问题与退出码写得更清楚。若 X 只是被 cherry-pick 到目标分支，目标有一个新提交 X’，原 X 通常不在祖先链上。此时断言失败不等于修复内容不存在；需要关联 cherry-pick 记录、补丁比较、针对性测试与目标构建回执。

从代码审查到交付，证据链不能跳级

假设发布说明说“包含 X 修复”。若检查返回 1，应先问发布说明指的是原提交对象，还是同等补丁。若工单要求严格追溯原审核对象，就应处理合并路径或更新声明；若业务只要求修复行为，就用目标分支上的实际提交、测试和构建工件建立新的证据。git diff 空、测试通过、--is-ancestor 为 0，分别支持内容、行为样本和历史可达；它们没有一个单独证明生产已经部署。部署还需要把产物摘要和实际运行版本绑定到目标提交。

临时例子中虽然 original 与 replay 文件相同，original 的提交 ID 与 replay 的提交 ID 不同。这样的反例提醒我们：若依赖关系来自“某个经过批准的提交”，不要把“文件一样”压缩成“已经批准”。但也不要把祖先断言当成安全魔法，祖先存在不说明后续提交没有撤销修复。对于重要变更，目标树和行为仍需复核。祖先检查回答“曾经包含这个对象”，最终树与运行验收回答“现在仍有预期效果”。

若要把检查放进 CI，还要明确被检查的是哪一对引用。比如拉取请求的合并结果、源分支头和部署用 release 分支头可能是三个不同对象；检查源分支含 X，不能推断合并结果已发布。CI 应把目标提交 SHA 打印在日志里，并在构建清单中写入同一个 SHA。发布后若运行工件报告另一个 SHA，就要追查流水线选择，而不是继续争论本地 git diff。这个步骤让祖先断言与最终交付之间有可追溯的接点。

浅克隆也是脚本中的实际边界。CI 若只抓取少量历史，目标仓库可能没有 X 或 X 到 Y 的完整父链，命令失败或判断受限。应先确认所需提交对象在本地，按最小必要范围补足历史，再执行断言；不能把对象缺失解释为“修复未合入”。对于重写过历史的分支，旧 SHA 不再可达可能是预期变更，但原审查记录与新提交之间需要新的映射，不能静默把检查改成只比较文件。审查目标改变时，记录为什么变、由谁确认以及新的测试回执。

如果补丁内容相同但依赖上下文不同，也不能只靠补丁标识推断行为相同。相同函数在新分支中可能被另一个调用路径绕过，或者配置在构建时选择了不同功能分支。内容比较可缩小差异面，行为测试和产物版本仍要跟上。祖先关系为审查链提供严格的历史回答，内容和运行证据则覆盖它无法表达的当前效果。

做发布审查时，可把三列放在一份记录中：目标提交 ID；要求的来源提交 ID 与祖先退出码；针对修复行为的测试与产物版本。这样遇到 rebase 或 cherry-pick 时，审查人员能准确说明哪一列变化了。站内 分支推送成功，发布标签为什么还没到远程？ 讨论的是远程引用的另一层证据；本篇的祖先断言也不替代远端标签或部署状态的确认。
