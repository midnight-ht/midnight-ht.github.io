个性化响应的私人缓存与共享缓存边界

private 限制共享缓存存储，但不禁止浏览器缓存；按身份、新鲜度与退出路径验收。

正文

核心要点

  • 无参数 private 禁止共享缓存存储响应，但私人缓存仍可能存储。
  • private 不能代替源站授权、新鲜度规则或退出后的浏览器行为验收。
  • Authorization 请求的共享缓存复用另有 RFC 9111 条件和显式指令例外。

用户资料接口返回 Cache-Control: private，浏览器里仍能找到缓存副本，不足以说明配置失效。RFC 9111 对私人响应的规定规定：无参数的 private 要求共享缓存不得存储该响应；私人缓存则可以在其他缓存约束下存储。它区分的是缓存使用范围，不是“任何地方都不落盘”的承诺。对个性化响应，先确定哪些节点可能存储，再决定是否允许当前用户的浏览器复用、是否允许代理或 CDN 存储，以及退出登录后应如何处理。

从使用者画出缓存位置

假设登录用户打开 /account/summary，响应包含姓名、订单摘要和本次身份可见的操作。浏览器自己的缓存通常属于面向单个用户的私人缓存；公司代理或 CDN 边缘节点可能为多个人服务，是共享缓存。若该响应误入共享缓存并被另一个用户取到，后果与“同一浏览器返回旧数据”不同。前者是跨使用者泄露边界，后者是当前设备上的会话与陈旧性问题。两者需要不同的控制和验收，不应都用“缓存错了”概括。

无参数 private 是告诉符合规范的共享缓存不要存这份响应，同时允许私人缓存按其余约束处理。若业务要求浏览器也不应保存敏感响应，应考虑 no-store 的语义；若允许保存但每次复用前必须向源站验证，应理解 no-cache，它并不等于禁止保存。本站的HTTP 缓存验证分别讨论这些指令。选择时先写清资源类别和风险，而不是把所有响应统一打成“最严”的头：公共静态资源与账户资料面对的读者、更新频率和存储范围不同。

RFC 也定义带字段名的限定版 private，它只限制列出的响应头字段进入共享缓存，其他部分在满足条件时仍可能被共享存储。把 private="Set-Cookie" 当成“整个页面都是私人内容”会误读限定范围；规范还提醒，这种限定形式的特殊处理并未被广泛实现，许多缓存会把它当成无参数 private。若正文就是个性化数据，优先让整份响应的共享存储规则清晰，而不是寄希望于缓存精确剥离一个响应头。对非个性化正文和少量私人头的优化，也应在具体缓存产品上做实测，不能仅凭 RFC 允许就推断部署已如此运行。

private 不能替代身份与新鲜度

另一条常见误解是把 private 当权限校验。缓存头只给遵循 HTTP 规则的缓存提供存储与复用指令，源站仍必须按当前请求身份与资源关系决定可见内容。若 API 在匿名请求就返回他人资料，加 private 不会让返回本身合法。若登录后在共享电脑退出账号，私人缓存中可能仍有旧表示；产品需要结合会话失效、浏览器行为、重新验证与退出清理策略决定是否允许重新查看。这条指令单独无法证明“退出后不可再见”。无参数 private 也不保证恶意或失效缓存、浏览器扩展、下载文件、日志都不会保存数据；RFC 对该词的注释明确说它控制的是存储位置，不是信息绝对私密。

个性化选择与缓存键也要分开。Vary 可帮助缓存按某些请求头选择不同表示，但不能代替 private 对共享存储的限制，更不能把某个 Cookie 或 Authorization 值自动变成可靠的用户授权边界。若响应内容对每个账户不同，先决定共享缓存是否根本应该存；若只随语言变化的公开页面，则可按真实表示选择规则设计缓存键，见HTTP Vary 与表示匹配。把公开语言版本和私人账户数据放在同一套缓存规则里，常导致条件复杂到无法审计。

工作例子可写成一张决策表：公开帮助页可允许共享缓存，账户摘要禁止共享存储但可能允许浏览器短时复用，包含高敏感凭据的响应连私人存储也不希望发生。表中的类别是假设，不是 RFC 替具体产品作出的安全评级。账户摘要若允许私人缓存，还要规定新鲜度：订单刚取消后是否必须重新验证，浏览器后退时是否可以显示旧摘要，重复使用的旧值是否会误导操作。这条指令回答的是“谁可存”，max-age、验证规则与应用状态回答“多久可复用”，不能把它们混成一个开关。

验证同一内容在不同节点的行为

验收应准备两个不同账户和一个未登录状态，在同一路径取得内容。首先检查源站实际响应头，以及 CDN、反向代理和浏览器最终看到的头是否一致；接着观察共享节点是否为私人响应产生可复用条目，再用另一身份请求同一路径，确认它收到自己的表示或被拒绝，而不是上一位用户的正文。浏览器侧分别检查同一身份刷新、断网或后退、退出再进入，以及订单状态变化后的重用。日志中只留必要标识和哈希，避免为了证明无泄露而把真实私人数据写进审校档案。

网络面板里看到“从缓存读取”还不够，要确认是浏览器的私人缓存还是代理返回的共享缓存；相反，只看到某次响应来自源站，也不能证明所有边缘节点都没有保存。Age、产品提供的缓存状态头和节点配置可以提供线索，但应与具体平台文档和实际请求关联，不能把单一头当作跨 CDN 的通用判定。

Authorization 请求还触发 RFC 9111 的另一条共享缓存复用规则：共享缓存通常不得用它的响应满足后续请求，除非响应中的特定指令明确允许。规范列出的允许复用指令包括 public、s-maxage 和 must-revalidate，各自仍带有相应的新鲜度或验证要求。这不等于“只要带登录头就绝不会进入共享缓存”，也不等于可以给每个身份的正文随手加 public。审查时要把请求是否带 Authorization、源站实际返回的每个缓存指令、缓存节点的存储与复用行为并列记录；当用户身份来自 Cookie 而非该请求头时，更不能把这条特定规则误当通用隔离机制。

这些是设计与测试路径，本文没有接入任何实际 CDN、代理或账户。最终要批准的策略应逐类写出：这份响应包含谁的数据，哪类缓存允许存，复用前是否需验证，退出或换身份后如何隔离。因此它只是一个有精确范围的工具；当要求是“任何缓存都不得存”，或要求是“用户绝不能看到旧状态”，需要分别选择和验证相应机制。
