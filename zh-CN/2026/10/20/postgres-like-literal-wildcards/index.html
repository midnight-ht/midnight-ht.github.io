用户搜索百分号，PostgreSQL LIKE 为什么匹配了更多记录？

解释 LIKE 通配符、参数绑定与字面转义的不同责任，用百分号、下划线和转义字符验证结果集合。

正文

核心要点

  • LIKE 参数中的百分号和下划线仍是模式通配符，参数绑定不会自动把它们当字面文本。
  • 字面包含搜索应只保留应用添加的首尾通配符，并转义输入内部的百分号、下划线和转义符。
  • 本批次只实测了字符串转换，返回记录集合还需要在 PostgreSQL 与真实应用入口验证。

用户在搜索框输入 50%，本意是找含有百分号的价格说明，结果页面返回了 500、50元 等没有百分号的记录。若后端把输入拼进 PostgreSQL LIKE 模式，% 在这个位置代表任意长度的字符序列。参数绑定能防止输入变成 SQL 代码，却不会替应用决定“用户输入应按普通文本还是按模式语言解释”。这两个边界要分别处理。

模式语法发生在值里面

PostgreSQL 18 模式匹配文档规定：LIKE 的 _ 匹配一个字符，% 匹配零个或多个字符；没有这两类通配符时，模式才像普通相等比较。LIKE 默认匹配整个字符串，若要查“包含某词”，应用常在两端主动加 %。于是用户原样输入 50% 后，模式变成 %50%%，中间那个百分号也参与匹配，不再是“价格后面的符号”。

假设有三条示意数据：折扣50%、折扣500元、50元。我们需要的集合只包含第一条。把“包含字面输入”的语义写出来就是：首尾的 % 由搜索功能提供，输入内部的 %、_ 与转义字符都要当普通字符。下列 SQL 展示一种选择自定义转义符 ! 的写法，表名和数据均是假设，本文没有在 PostgreSQL 实例执行：

SELECT id, title
FROM catalog
WHERE title LIKE '%' || :escaped_term || '%' ESCAPE '!';

这里的 :escaped_term 是客户端绑定参数的占位说明，不是 PostgreSQL 原生占位语法。应用应先按顺序把用户输入中的 ! 变成 !!，% 变成 !%，_ 变成 !_，再绑定结果。输入 50% 得到 50!%；最终模式的外层百分号负责“任意前后文”，!% 才代表字面百分号。输入 a_b 同理要把下划线变为 !_，否则它会匹配 a1b。必须先转义 !，否则用户原有叹号可能被误当成后续字符的转义前缀。

字符串转换可单独核对：本批次的 like_escape_probe.py 在本机 Python 3.11.15 执行了转义函数，保存了脚本与原始输出；并未连接 PostgreSQL，因此不能把输出当作查询结果。

在这组输入下，50% 变为 50!%，a_b 变为 a!_b，!% 变为 !!!%。最后一例尤其能检验“先转义转义符”的顺序；若先处理百分号，再把新产生的叹号翻倍，数据库读到的就不是同一个模式片段。真实客户端仍须把函数结果作为绑定值交给采用相同 ESCAPE '!' 的查询。

绑定参数和字面搜索各做一半

很多修复只把字符串拼接改成参数绑定，例如 WHERE title LIKE '%' || $1 || '%'。这一步很重要，因为用户文本不再能改变 SQL 结构；但传入 % 时，数据库仍会按 LIKE 模式解释这个参数值。反过来，手写转义却继续拼接 SQL 字符串，也不能据此宣称注入问题解决。评审要分别检查 SQL 结构是否固定、绑定值是否表达了产品承诺的字面搜索。

另一种产品设计是让用户主动使用通配符。例如高级搜索允许 a_b 代表任意单字符时，就不该无条件转义。关键在于界面契约：普通搜索框通常承诺输入即文本，高级模式可以显式标注语法。把两者混在一个未说明的输入框里，会令“找百分号”和“用百分号扩展匹配”无法区分。若要同时提供两种行为，应使用独立模式开关或独立查询入口，并在结果页展示当前解释方式。

ESCAPE '!' 是本示例的具体选择，而不是数据库的唯一配置。官方文档说明 PostgreSQL 默认反斜杠为转义字符，也可用 ESCAPE 选择别的字符；ESCAPE '' 会禁用转义机制，使字面 % 与 _ 不能以这种方式表示。跨语言客户端经常还有字符串字面量、ORM 模板与传输参数各自的转义层，容易把一个反斜杠数错。选一个明确的转义字符，并在应用层生成绑定值，比猜最终 SQL 文本里该出现几个反斜杠更便于审核。

负样本要覆盖三个特殊输入

验证不应只用普通字母。第一组输入 %，应匹配含字面百分号的标题，而不匹配所有非空标题。第二组 _，应匹配含下划线的标题，而不匹配任何单字符标题。第三组 ! 与 !%，用来确认转义字符本身可以安全出现，且不会吞掉后续字符。再测空字符串、包含多字节字符的普通词，以及词位于开头、中间、结尾的位置。每组都应写出预期返回的记录集合，而不只断言“查询没报错”。

大小写和排序规则是另一个判断。ILIKE 会按当前区域规则做不区分大小写的匹配，文档说明它是 PostgreSQL 扩展；换用它不改变 % 与 _ 仍是模式字符这一事实。有些非确定性排序规则还会让“相等”如何理解更加复杂。若搜索需求是全文检索、词形变化或海量文本排名，LIKE '%词%' 可能不是合适的索引与语义方案；这篇的转义只解决字面符号，不承诺查询性能或相关性。

生成模式时还要确认搜索层的责任

应用可以把转义函数放在查询构造层，避免六个接口各写一套规则。但函数的输入和输出必须明确：输入是用户原始文本，输出只是供 LIKE ... ESCAPE '!' 使用的片段，不含首尾的搜索通配符。若函数同时负责加首尾 %，调用方再加一遍，就会形成多余的通配符；语义虽可能仍能匹配，审查却难以还原。选择一个责任边界，并给函数附上 %、_、! 的单元样本。

若搜索字段允许 NULL，LIKE 的三值逻辑也应进入结果预期：空字段不会因为模式中有 % 就自动变成匹配行。若业务希望“空输入显示全部”，应由产品规则明确处理空输入，不要依赖 LIKE '%%' 的偶然行为；它对 NULL 仍不成立。若用户输入前后空白会被裁剪，也要说明是在转义之前裁剪，并测试真正需要搜索空格的场景。这样可以把输入正规化、模式转义和结果策略分别审查。

查询计划验证应在语义正确之后进行。LIKE '%term%' 与前缀匹配、相等匹配有不同索引可能性，具体取决于索引、排序规则和数据分布。没有生产数据与执行计划，不应因加入转义而宣称性能改善或退化。先用小型对照数据证明集合正确，再用项目实际表与查询计划评估是否要换搜索实现。

做评审时，我会把输入到 SQL 的变换拆成四格：原始用户文本、应用转义后的绑定值、数据库实际模式、预期记录集合。任何一格缺失，都很容易把参数安全与匹配语义混为一谈。站内PostgreSQL JSONB 查询与索引讨论另一个查询选择问题；本题应先保证普通文本搜索不会意外扩展集合，再根据真实数据量决定索引和搜索方案。
