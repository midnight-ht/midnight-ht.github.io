reusable workflow 的 secret 不会自动穿透下一层

嵌套工作流的密钥逐跳传递；用 A→B→C 的映射核对最小授权和实际目标回执。

正文

核心要点

  • A→B 的传递不使 secret 自动到达 C，B→C 需要再次显式选择。
  • secret 传播与 GITHUB_TOKEN 权限是不同检查；权限链只能保持或降低。
  • 逐跳保留映射、版本和目标操作回执，避免用 inherit 扩大无关凭据范围。

在 GitHub Actions 的 A → B → C 可复用工作流链里，A 把 secret 传给 B，只能说明直接被调用的 B 收到了它；C 不会因为处在下一层就自动继承。B 调用 C 时要显式选择传递哪些 secret，而且整条链的权限只能维持或减少，不能靠嵌套调用升高。GitHub 官方复用工作流文档明确写出“secrets only passed to directly called workflow”的一跳规则。

把调用链画成有向边

假设仓库 A 的发布工作流调用组织内的构建工作流 B，B 又调用签名工作流 C。A 持有部署凭据和签名凭据，向 B 使用 secrets: inherit，B 因而可能拿到调用方可传递的 secrets。若 B 调用 C 的 job 没有继续传递，C 的 secrets 上下文里不会凭空出现 A 的签名凭据。排障时不要只问“A 有没有 secret”，而要逐条记录 A→B 与 B→C 两条边，包含目标 workflow、引用版本、传递方式和名称映射。

一个未经本站仓库运行的示意片段只展示传播位置，省略触发器和权限设置：

# A 中调用 B 的 job
jobs:
  build:
    uses: org/repo/.github/workflows/B.yml@main
    secrets: inherit

# B 中调用 C 的 job
jobs:
  sign:
    uses: org/repo/.github/workflows/C.yml@main
    secrets:
      signing_key: ${{ secrets.signing_key }}

这不是建议把所有 secret 都 inherit。文档给出的 A→B→C 示例正说明：A 可以把全部可继承 secret 给 B，而 B 只把一个传给 C；其它 secret 对 C 不可用。对于签名工作流，B 只传 signing_key 通常比再给 C 全部 secret 更容易审查。真实配置还须检查被调用工作流声明的输入、密钥名称、仓库或组织可访问性，以及固定引用版本。示意代码里的名称和仓库只是占位，并未验证可运行。

secret 与权限是两张表

收到 secret 不意味着 job 获得更高的 GITHUB_TOKEN 权限。GitHub 文档说明嵌套可复用工作流必须对调用方可访问，而且链中权限只能保持或下降，不能升高。发布链审查要分别列出“哪个 secret 走到哪一层”和“每一层 token 对仓库资源有什么权限”。比如 C 拿到用于外部签名服务的密钥，却可能没有写 GitHub Release 的 token 权限；反过来，有写权限的 token 也不会自动补出外部服务的凭据。把两类缺失都叫“secret 没传过去”会误导修复方向。

环境 secret 还有自己的来源边界。官方文档提醒，workflow_call 不支持通过该触发器传递环境 secret；被调用工作流 job 如果指定环境，环境里的 secret 可能按该 job 的环境配置生效。审查时应核对 C 实际读取的是从 B 显式传入的命名 secret，还是 C 所在 job 环境提供的同名 secret。名称相同不等于来源相同；若误读，可能以为 A→B→C 传递成功，实际却是 C 的环境里恰好已有凭据。此类混淆在轮换或迁移仓库时很容易暴露。

缺凭据时怎样定位且不泄露

先确认 B 的调用 job 是否在预期 workflow 与引用版本上运行，再看 B→C 的 secrets 映射。若 C 报“missing signing_key”，检查 C 声明的名称与 B 提供的键是否一致，B 自身能否在它的上下文读取对应 secret。不要在日志里打印 secret 明文来测试；可以用不暴露值的存在性检查和受控的目标服务调用结果确认路径。存在性只能说明变量非空，不能证明值有效、权限足够或目标服务接受，因此要把这几项验证分开记录。

错误修复的反例是为了让 C 通过，直接在 A→B 和 B→C 都改成 inherit，把部署、签名与其它无关凭据扩散到每个下游。这样可能使眼前的缺失报错消失，却扩大了每层工作流、第三方 Action 和被调用仓库的暴露面。更稳妥的选择是给每条边列一个最小 secret 清单，用显式映射传递；若确需继承，写明可访问范围和理由。工作流配置变更后，要核对 C 的具体任务能完成，同时确认它未获得不需要的 secret 或提升后的 token 权限。

另一种失败路径是 B 已把密钥传给 C，但 C 调用的外部签名接口仍拒绝。此时传递链路可能正确，问题转向凭据撤销、过期、作用域或目标环境。站内 删除源码密钥之后的轮换与撤销 处理的是凭据生命周期；本篇处理工作流调用链上的交付范围。不要因为某层能看到非空值，就宣称发布签名、镜像推送或线上部署已经成功。

审批人员还要问密钥的目标与任务是否相配。B 只是构建镜像时，是否需要知道生产部署凭据？C 只是签名制品时，是否需要读取包仓库的推送令牌？把这些问题对应到每条调用边，可以把“缺什么就继承全部”的临时修补转成职责清晰的配置。若一个下游工作流同时承担构建、签名和部署，密钥清单难以缩小，就应考虑把职责拆成更窄的可复用工作流；拆分后的边数增加，却能让每一步只接收完成任务所需的凭据。

在跨仓库调用时，还要检查调用方是否有权读取被调用工作流所在仓库，以及引用的分支或标签是否指向预期版本。密钥映射写得正确，工作流文件不可访问或版本变化，也会表现为整条链失败。反过来，引用可变的 @main 适合说明语法，却不适合作为高敏发布流程唯一的稳定性证明；评审可以选择固定可审核的版本，并保留实际运行解析到的提交。这样当 C 的接口变更或 secret 名称调整时，可以从调用关系和版本证据定位，而不是猜测平台“丢了密钥”。

还需区分 secret 的作用域与运行身份。组织级、仓库级和环境级凭据可见性受各自设置影响；即使 B 的 YAML 写了转发，B 没有读到值也无法凭空传给 C。环境审批未通过、分支不满足保护规则或凭据本身被撤销，都是不同于“嵌套不会自动穿透”的原因。定位时先确认 A 的任务拿到应有输入，再核对 A→B，最后核对 B→C 和目标服务结果，每步保留脱敏证据。不要用打印原值的办法缩短排障时间。

验证可在受控仓库和最小权限凭据下做两组任务：一组 B→C 不传密钥，应观察 C 的受控缺失路径；一组显式传递预期密钥，应观察目标操作的真实结果。记录运行 ID、A/B/C 的引用版本、传递映射、token 权限和最终目标回执，日志只留必要的脱敏状态。本稿没有运行 GitHub Actions，也没有接触真实 secret；示意 YAML 仅用于解释边界。交付结论应精确到“哪一跳已传递、哪一层已使用、目标操作是否完成”，而不是一句“继承已打开”。
