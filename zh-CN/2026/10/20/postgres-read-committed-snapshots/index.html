同一事务查两次，Read Committed 为什么会看到不同值？

用两个事务的时间线解释 PostgreSQL Read Committed 的语句级快照，并区分自身写入与并发提交。

正文

核心要点

  • PostgreSQL Read Committed 的普通 SELECT 使用语句开始时的快照，同一事务内两次查询可能看到不同提交状态。
  • 先查后写的旧读数不能代替受并发保护的实际写入条件与返回行数。
  • 判断异常需记录两会话提交顺序、自身写入和隔离级别；本稿时间线尚未在数据库实测。

一笔事务里连续查两次账户余额，第一次是 100，第二次是 80。两条查询之间本事务没有更新余额，开发者便怀疑连接切换或缓存失效。对 PostgreSQL 默认的 Read Committed 隔离级别来说，这种变化可能完全正常：每条 SELECT 在开始执行时取得自己的快照，而不是在 BEGIN 那刻锁定一张贯穿整个事务的照片。另一笔事务在两次查询之间提交，第二条语句就可能看见它。

先用两个会话写出时间线，避免把“同一事务”理解成“同一快照”。账户 id=42 初值 100。会话 A 执行 BEGIN，随后 SELECT balance FROM wallet WHERE id=42，读到 100；会话 B 把该行改成 80 并 COMMIT；会话 A 再执行相同 SELECT，可以读到 80。两次读都发生在 A 的事务里，差别在于第二次语句开始时，B 的提交已经可见。PostgreSQL 18 隔离文档明确说 Read Committed 是默认隔离级别，也明确指出同一事务内连续的 SELECT 可以看到不同数据。

-- 会话 A，预设 wallet(42) 的 balance = 100
BEGIN;
SELECT balance FROM wallet WHERE id = 42; -- 预期 100
-- 会话 B 在此完成 UPDATE wallet SET balance = 80 WHERE id = 42; COMMIT;
SELECT balance FROM wallet WHERE id = 42; -- 可见 80
COMMIT;

上面是可复现的调度说明，不是本环境的执行记录。SELECT 看到的是它开始前已经提交的数据；在它运行过程中才提交的另一笔事务，不应被简单想象为随时插入到同一条查询的任意位置。反过来，A 自己在事务内先 UPDATE 为 90，随后查询又会看到自己的写入；“语句级快照”不意味着本事务刚刚写过的值被隐藏。解释某个读数时，先标出每条语句的起点、其他会话的提交点和本事务自己的写入，才有可能判断变化来自哪里。

这对“先查再决定”的业务逻辑影响很具体。假设请求先查库存 10 件，处理其他工作后再查得到 8 件，代码若把第一次结果当作整笔事务的稳定前提，就可能基于过时数量计算承诺。把两次读放在一个 BEGIN 内并不能自动满足“期间数值不变”的需求。应该先确定真正要保护的业务不变量：只是显示最新信息，还是必须基于当前行原子地扣减，或必须对一组跨行条件给出一致判断。不同承诺对应不同写法，不应把隔离级别当作含糊的保险开关。

对于单行扣减，可把资格条件放到实际写语句里，例如 UPDATE inventory SET available = available - 2 WHERE sku = 'A' AND available >= 2 RETURNING available，并以实际返回行数判断是否扣成。这样检查与修改在同一条写语句的逻辑内，而不是相信先前读出的数量永远没变。并发更新同一行时，PostgreSQL 的 Read Committed 写语句可能等待其他事务，并在对方提交后针对更新后的行重新评估条件；因此代码必须处理零行结果，不能用旧 SELECT 的结果宣布成功。这里的 SQL 仍须在真实表、约束和并发负载下测试，不能仅凭单条语句替整套订单流程做一致性担保。

如果需求是一个事务中多次读取保持同一已提交视图，可以考虑 Repeatable Read。PostgreSQL 对该级别的快照建立时机是事务中第一条非事务控制语句，而非仅仅敲下 BEGIN；后续普通读取使用这个事务视图，同时仍可看到本事务写入。切换级别还意味着遇到并发更新冲突时可能收到需要重试的错误。它不是把任何跨行业务约束自动变真，也不是免费消除竞争。站内 事务隔离与重试 从另一侧讨论何时要把完整事务作为重试单位。

还有一种误读是以为 Read Committed 连单条查询也不一致。文档描述的是每个命令开始时所取的快照；同一条常规 SELECT 不应像两条先后查询那样，分别用两个不同开始时间的视图拼接结果。但包含复杂写入、触发器或并发等待的语句仍有细节，不宜把一句“语句级快照”推成所有 SQL 都只有简单静态画面。本文仅讨论普通读和明确的单行写示例。若报表必须把多个表的读数固定在共同边界，需设计事务级视图及其失败重试，而非只在应用层缓存第一次读数。

诊断时记录隔离级别、连接标识、事务边界、每条查询起止时间以及另一个写者的提交顺序。只有知道先后关系，才能把第二次 80 归于并发提交；没有对照证据，把“偶发变化”归罪于 MVCC 也可能遮盖应用自己更新、读副本切换或缓存问题。复现脚本应让两个独立会话通过人工屏障或确定性的同步点交错，保留服务器版本、SQL 和原始输出。不要用任意睡眠时间代替并发顺序的证明。

读数改变未必是缺陷，错误的是把未经保护的读数当作稳定承诺。如果界面只是展示余额最新状态，两次不同读数可能正符合期望；如果业务在第一次读后批准了不能超额的操作，就需要把批准条件绑到受并发保护的写入或更高隔离级别，并验证失败分支怎样回滚和重试。本文依据 PostgreSQL 18 官方隔离文档给出预期时间线，没有在本环境连接 PostgreSQL 跑双会话实验；应用的正确策略仍取决于其实际不变量、事务边界与错误处理。

测试还应覆盖“没有并发提交”这一负例：在同一事务内重复读取，如果没有自己的写入、也没有其他已提交变化，预期值不应凭空改变。若此时变了，先检查查询条件、连接路由、数据源和应用缓存，而不是把一切交给隔离级别解释。再单独验证“本事务自己写入”路径，避免为了修复第二次查询可见新提交而意外误解自写可见性。这样三组对照——无变化、并发提交、自身写入——能把一句抽象的隔离定义变成可追踪的故障判定表。
