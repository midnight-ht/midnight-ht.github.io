USER 不是 chown：复制文件仍可能不可写

运行进程改成普通用户后，COPY 文件仍可能属于 root；按实际写入路径核对最终镜像与挂载卷。

正文

核心要点

  • 不带 --chown 的 COPY 默认创建 UID/GID 为 0 的文件，USER 不追改这些元数据。
  • 将程序只读文件与缓存等可写目录分开授权，按失败的绝对路径诊断。
  • 卷挂载会改变运行时可见路径，最终镜像权限测试不能替代有卷部署测试。

USER app 改的是后续构建指令和容器启动时采用的用户身份，不会把前面由 COPY 放进镜像的文件自动改属主。Docker 官方说明：不带 --chown 的 COPY 创建的文件默认 UID、GID 都是 0。于是“容器进程已非 root”和“它能写某个路径”可以同时一个真、一个假。Dockerfile 的 COPY 文档。

报错发生在谁写、写到哪一层

设想一个镜像在构建阶段把应用和空的缓存目录复制到 /app，最后一行切换为 UID 10001。应用启动后试图在 /app/cache 创建索引，操作系统按进程有效 UID、目录属主、组和权限位判断。如果目录属于 UID 0，权限是常见的 0755，UID 10001 可以读取和进入，却不能在目录中创建文件。文件“在镜像里”不代表对运行用户可写；USER 也不是递归 chown。

一个未在本站环境执行的示例可以把意图写在 Dockerfile 内，而非只靠运行时碰运气：

FROM alpine:3.20
RUN addgroup -g 10001 app && adduser -D -u 10001 -G app app
WORKDIR /app
COPY --chown=10001:10001 --chmod=755 ./bin/server /app/server
RUN mkdir -p /app/cache && chown 10001:10001 /app/cache
USER 10001:10001
CMD ["/app/server"]

这里 --chown 对复制的程序明确设置属主，但程序本身只需执行，未必需要可写。真正需要写的是 /app/cache，所以为目录授予最小的必要权限。若应用把可变缓存写回源代码目录，往往会把可读文件和可写状态搅在一起。更清楚的设计是程序层保持只读，缓存、上传和临时文件各自有可写位置；这样权限审查能按路径回答“谁需要写什么”。示例中的基础镜像、二进制与运行命令只是说明权限关系，不能当作已经验证可运行的产品镜像。

COPY --chown 的边界在哪里

--chown 是复制时的元数据设置，不会修改随后挂载进来的卷，也不会追溯此前已经存在的目录。Docker 文档还说明：使用用户名或组名需要容器文件系统里能解析 /etc/passwd 与 /etc/group；使用数字 UID/GID 则不依赖名字解析。团队在多阶段镜像里从构建阶段复制二进制到运行阶段时，应看最终阶段的 COPY，因为运行进程面对的是最终文件系统。只在构建阶段修改源文件权限，不能推断最终镜像里同一路径仍保留这些元数据。

再看一个容易误判的场景：镜像内 /app/cache 已归 UID 10001，编排系统运行时却把宿主目录或持久卷挂在 /app/cache。挂载后的目录取代了镜像里那个路径的可见内容，其权限由实际卷或宿主文件系统决定。此时重写镜像的 COPY --chown 没有针对性；要检查卷的属主、运行时 UID、组策略以及存储驱动和平台对权限的实现。不要把“构建时权限修好了”写成“生产卷一定可写”。同样，容器以 root 启动来掩盖挂载权限问题，会扩大进程权限范围，却没有解释为什么状态目录原本不可写。

有时文件报不可写并非属主问题。父目录缺少搜索权限、目标文件权限为只读、应用写到了预期之外的路径、只读根文件系统或安全策略拒绝操作，都能形成类似症状。诊断应从实际失败路径开始，记录进程 UID/GID、该路径及每一级父目录的权限，再判断需要改 COPY、改建目录步骤、改卷配置，还是改应用写入位置。否则一次宽泛的 chmod -R 777 可能让本地演示通过，却把镜像内其它本应只读的文件一并开放。

验证要在最终运行形态上做

镜像构建成功只证明指令合法。验收至少分三层：检查最终镜像中的文件属主和权限；以目标 UID 启动容器，尝试创建、读取、删除一条临时数据；若部署挂卷，再在实际挂载条件下重复。测试命令和预期输出要绑定最终镜像摘要与运行参数，避免把一个无卷容器的结果套到有卷部署。失败后查看实际报错路径和 stat 信息，不要只看 Dockerfile 文本。本站没有执行上述示例，也没有产出容器权限实测回执。

多阶段构建还有一个常见细节：构建阶段以 root 安装依赖，运行阶段以非 root 启动，而 COPY --from=builder 又把产物放入最终镜像。要检查的是最终阶段这一条 COPY 的属主，以及程序运行时实际需要写入的路径。即使构建阶段通过 chown 改过目录，只要最终复制语义重新生成文件，不能凭构建阶段的截图宣称最终层相同。可以把最终镜像里的 id、stat /app、stat /app/cache 和实际写入结果放在一份验收记录，而不只保留 Dockerfile。若应用在启动时下载模型或生成迁移文件，更要确认它是否无意间把可变数据写进 /app；这类写入点在只读根文件系统里会再次失败。

在容器编排环境，数字 UID 的选择还应与运行时配置一致。镜像用 USER 10001:10001，部署却覆盖了运行用户或补充组，最终权限判断会按运行时身份进行。卷的权限如果由初始化容器准备，也应记录初始化步骤的退出状态与挂载路径；仅看到主容器成功启动，不能推断写入操作真的执行过。反之，如果业务只需读取配置，给配置文件写权限反而扩大了被攻陷进程能修改的范围。权限方案的验收点应来自应用真实读写清单。

还有一种定位方法是先在失败容器里确认路径解析：若日志写入目标是相对路径，WORKDIR 或启动脚本改变当前目录后，报错文件可能并不是预想中的缓存目录。先打印或记录应用解析后的绝对路径，再检查该路径的挂载和权限。这样可以把“用户身份问题”和“路径配置问题”分开处理，避免在错误目录上不断修改权限。

实际选择通常不是“所有文件都 --chown”或“所有目录都开放写入”。静态程序文件给运行用户读取和执行；可变目录给必要用户或组写权限；卷由部署侧确认；临时数据可考虑明确的临时挂载。以路径和运行身份为单位作决定，才能在更换基础镜像或 UID 时知道该复核哪些点。涉及发布镜像与依赖风险，可对照站内 依赖审计修复后的发布检查：构建通过与运行验收是两张不同的凭据。
