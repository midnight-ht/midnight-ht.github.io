Sec-Fetch-Site 的 same-site 不是授权

来源关系能辅助拦截跨站请求，却不能证明登录身份和对象权限；按路由设计缺头与例外。

正文

核心要点

  • same-origin、same-site、cross-site 和 none 描述请求来源关系，不包含用户身份。
  • 敏感操作可用来源关系做早期过滤，但服务端仍需核验凭据、对象归属和动作权限。
  • 缺失头和合法跨站回调需按路由契约处理，不应全局放行或全局拒绝。

Sec-Fetch-Site: same-site 说明请求发起方与目标资源处于同一站点关系；它不说明发起者是谁、登录是否有效，更不说明此人有权访问哪条记录。这个请求头很适合做一层跨站请求过滤，但把它当成授权通过条件，会把“请求从哪里来”和“请求可以做什么”混为一谈。

来源关系只回答一个问题

浏览器为符合条件的请求附上 Fetch Metadata。MDN 将 Sec-Fetch-Site 的值分为 same-origin、same-site、cross-site 和 none：同源要求协议、主机和端口一致；同站包括同一站点下的不同源，并包含协议；none 可出现在用户直接输入地址或使用书签等操作。服务器可用这个关系决定是否接受某类请求。MDN 的请求头说明还指出它只随发往潜在可信 URL 的请求出现，且 Sec- 前缀使普通网页脚本不能直接设置该请求头。

这些性质让它成为有价值的浏览器上下文信号，而非用户凭证。假设 app.example 提供订单详情，analytics.example 位于同一站点。浏览器从分析子域发到应用子域的请求可被标记为 same-site。这并不告诉应用分析子域的脚本是否可信，也不告诉它能否读取某个用户的订单。即使请求是 same-origin，一个已登录用户也只能访问自己的订单；一个同源页面中被注入的恶意脚本同样可能发出同源请求。授权仍必须依据服务端已验证的身份、资源所属关系和动作权限。

作为过滤层，它该放在哪里

可以为有状态的网页接口设计一个入口规则：对修改数据的请求，如果浏览器报告 cross-site，先拒绝或进入更严格的例外；对 same-origin 继续做身份与资源授权；对 same-site 检查业务上是否真允许同站跨源调用。这里的关键不是一条万能条件，而是服务端知道自己有哪些合法客户端。一个公共图片接口、一个需要登录的转账接口、一个 OAuth 返回入口，对跨站请求的合理处理不同。仅以站点关系建立全局白名单，通常会伤及合法导航，也可能漏掉同站不可信源。

下面是未执行的假设性策略片段，用于说明判断顺序，不是可直接复制到生产的中间件：

if request is a state-changing browser action:
    reject cross-site unless route has an explicit reviewed exception
    handle missing or none according to the route's client contract
authenticate session or token
check the user's permission for the requested object and action
apply CSRF protection where cookie-based authentication needs it

例如 POST /orders/42/cancel 来自同源订单页，头部关系检查允许继续，服务端仍须核对当前用户是否拥有订单 42，订单是否可取消，以及请求携带的凭据是否有效。若攻击者从外站诱导浏览器提交，cross-site 可让入口更早拒绝；但若取消接口错误地只检查 same-origin，受害用户已登录时仍可能出现越权或被注入脚本滥用。头部降低部分跨站攻击面，不承担业务授权的最后一票。

缺失值与 none 不能靠猜

浏览器支持范围、非浏览器 API 客户端、代理层和请求类型都会影响你能否看到这些头。MDN 的语义只说明存在时的关系，不承诺所有合法请求都必须带值。若服务端把“缺头”一律当攻击，会破坏移动应用、服务间调用或测试工具；若把“缺头”一律当可信，又会给同一接口留下绕过支路。应按路由声明客户端契约：只允许浏览器的敏感表单，可对缺头采取保守处理，同时留出明确认证的 API；面向多种客户端的接口应依赖完整的认证与授权，并把 Fetch Metadata 用作额外风险信号。none 常与直接导航有关，不能机械地视为“内部可信”，更不能用于允许一次改变状态的请求。

还要注意“同站”不是“同源”。若产品把上传、用户内容或合作伙伴应用放在同站不同子域，同站请求仍可能来自控制程度较低的环境。部署前先列出这些子域和它们能发起的请求，再决定 same-site 是否进入敏感操作。跨源资源共享策略、Cookie 的 SameSite 属性、CSRF 令牌和服务端授权各管不同环节；调试时应分别记录它们，而不是看到一个头就把其它检查删掉。站内 CSP 报告模式上线审查 也体现了相同的原则：浏览器给出的上下文信号需要与实际业务路径一起验收。

设计评审还应追问例外如何维护。若某个支付回跳、嵌入式组件或外部自动化确实需要跨站发起请求，例外应绑定到明确路由、方法和认证方式，并在日志中能识别；不要因为一个例外就把所有 cross-site 放行。相反，如果接口实际是公开只读内容，直接拒绝跨站读取可能影响合法嵌入或搜索场景。先给路由写明业务意图，才有可能判断请求头该提供哪种额外保护。审查人员看到 same-origin 时也要问：服务端有没有基于用户身份重新查询资源，而不是依赖前端传来的用户编号？这个具体问题比“头部看上去安全”更能发现越权。

一个有用的测试矩阵包括同源页面、同站不同子域、外站、直接导航和明确认证的非浏览器客户端。逐条记录请求方法、目标路由、实际头值、登录身份、资源所属者与最终状态码；对于拒绝，确认拒绝发生在预期层而非偶发的前端错误。再用两个不同账号访问同一个资源，验证“来源关系相同、授权结果不同”。本稿未对真实应用执行这些请求，示例均为设计推演。验收的结论应是：来源过滤是否按策略工作，以及独立的身份和对象授权是否仍然工作。
