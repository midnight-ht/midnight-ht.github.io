整数字段验收：先完整匹配，再解析

parseInt 会接受整数前缀；完整输入、数值安全范围和业务范围要逐层验证。

正文

核心要点

  • parseInt 会接受有效整数前缀，指定十进制基数仍不检验整串。
  • 完整语法、安全整数和业务范围是三道独立的输入门槛。
  • Node v24.21.0 的前缀解析结果不等于表单或服务端验收。

用户在“数量”栏输入 12px，parseInt 却得到 12。若程序只检查解析结果是不是数字，这份不合法的完整输入就被当成合法数量。MDN 的 parseInt 文档明确说明：遇到不属于指定进制的字符，它会停下并返回之前成功解析的整数前缀。这个行为适合从有单位的字符串中提取前缀，不适合单独证明整串输入符合一个纯整数字段。

“能解析”与“全串合法”是两个问题

假设订单数量只能用十进制非负整数表示，12px、12.5、1e3 都不是这份输入合同允许的字面形式。parseInt("12px", 10) 会取前缀 12；小数点和指数记号也会在各自位置让它停止。写明基数 10 是正确的可读性选择，但它仅说明数字前缀按十进制解释，不会自动要求字符串全部被消耗。NaN 检查只能发现开头没有可解析数字等情况，无法找回已经被丢弃的尾部。

不能因此把 parseInt 定性为坏 API。显示值 "12px" 若业务本来要提取像素数，前缀解析也许正好符合需求；但这时应明确允许的单位与转换规则，不能把“随便什么尾巴都忽略”当成通用单位解析。对于数量字段，先写允许的文本语法，再写数值范围。假如允许零或不带前导零的正整数，语法可以是 0 或以 1–9 开头、后接数字的整串；若允许前后空格，要决定由输入层裁掉还是报错。这个决定会影响 " 12 "、"012" 和空串的结果，不能藏在解析函数的默认行为里。

一条可审查的处理顺序是：确认输入确为字符串；按产品规则处理空白；用完整匹配验证十进制字面形式；转换为数值；检查是否安全整数；最后核对业务上限与下限。比如库存一次最多购买 99 件，100 虽然语法和数值都合法，业务范围仍应拒绝。若允许负数或千位分隔符，就要另写语法，而不是直接把示例正整数表达式贴进别的字段。客户端同样规则可以给即时反馈，服务端仍需按可信数据源与当前库存重新校验，参见表单校验与服务端权威。

function parseQuantity(input) {
  if (typeof input !== "string" || !/^(?:0|[1-9][0-9]*)$/.test(input)) return null;
  const value = Number(input);
  if (!Number.isSafeInteger(value) || value > 99) return null;
  return value;
}

这段代码只示范一种不允许空格、负号、前导零且上限为 99 的假设协议；null 在这里表示解析失败，真实接口应给可修正的错误原因。还要注意值为零是否有业务意义：库存订单也许要求最少一件，此时应把下限改为 1，而不是让正则承担业务决策。代码不是某项目已部署的校验器；需针对实际输入和目标环境运行验证。

字符串看似数字，数值仍可能不可靠

大整数字符串是另一条边界。JavaScript Number 对超过安全整数范围的数值无法精确表示，parseInt 的结果也是 Number。MDN 给出带 BigInt 后缀的输入会在 n 前停止并可能失去精度的例子。订单数量通常不该大到这种程度，但用户输入、外部配置和恶意请求仍可能触及边界。先验证全串，再用 Number.isSafeInteger 检查可表示性，比“能得到一个整数”更能防止静默变值。若业务确实需要大整数，应单独设计 BigInt 存储、序列化和范围协议，不能在现有 Number 字段上悄悄换类型。

不同写法也各有陷阱。Number("12px") 不会像 parseInt 那样接受这个尾巴，但 Number("") 会得到零，若空串是缺失或错误仍需前置校验。正则完整匹配可以拒绝尾随内容，但无法判断数值是否安全、是否在业务范围内。HTML 的 type="number" 提供界面和浏览器交互，不阻止绕过页面直接提交请求。单测只测 parseInt("12", 10) 得到 12，会让所有这些边界保持未知。

建议建立一张以原始文本为主键的验收表："12" 接受为 12；"12px"、"12.5"、"1e3"、"012"、空串、前后空格，在上述示例协议下拒绝；"0" 是否接受由业务决定；超出安全整数或 99 上限拒绝。再添加误差提示检查：不能只返回“非法”，应告诉用户需要十进制整数和允许范围。若要支持本地化数字或不同语言的输入，应设计另一套正规化流程，并避免把本地化展示字符串直接送进纯 ASCII 的校验器。

在 Node v24.21.0 的独立脚本中，基数明确传 10 时，输入 "12px" 与 "12.5" 都得到 12，"1e3" 得到 1，"0x10" 得到 0，空串得到 NaN；带 n 的大整数字符串还被转成失去原始精度的 Number。脚本和原始 stdout 已保存。这个结果只证明该 Node 环境的解析行为；上面的 parseQuantity 函数尚未在项目表单或服务端执行，也没有用这些输出充当业务验收。

一次实际修复应沿请求路径继续看。用户输入 12px，页面若先解析成 12 再发给 API，服务端看到的已经是整数，无法从载荷恢复用户原来写了单位；日志若只记解析值也会掩盖错误来源。较好的顺序是在可信入口保留原始文本至校验结束，校验失败给用户原字段的纠错提示，校验成功才生成规范化数值。服务端即使收到前端已转换的数字，也须独立核对类型、范围和权限；若端点直接接受文本，则应重复完整语法检查，不能假定浏览器校验一定运行。验收既看错误被拒绝，也看失败后原输入能否保留供用户修改。

对批量导入，错误位置同样关键。假设一行的数量为 12pcs，解析前缀会让整批表面成功，却把这行变成 12。若导入合同要求严格整数，应报告行号、列名与原字面值，并保持受影响记录的提交策略可解释：整批拒绝或逐行隔离由业务决定。这样完整校验不是为了挑剔输入格式，而是为了避免一个被截断的前缀悄悄进入后续计算和审计。

最终目标是让存储值、界面回显和审计记录指向同一个输入决定。若输入 12px 被截成 12，用户可能以为系统理解了单位，服务却只保存数量；这个语义错位比函数是否返回 NaN 更值得修。把“完整字面形式、数值可表示、业务允许”三道判定分开，parseInt 才会回到它适合的位置：明确需要读取整数前缀的场景，而非纯整数字段的唯一门卫。
