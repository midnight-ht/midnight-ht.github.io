toBeHidden 通过，元素真的从 DOM 移除了吗？

说明隐藏与不存在都能满足 Playwright 隐藏断言，并按产品承诺选择可见性或节点数量验收。

正文

核心要点

  • Playwright toBeHidden 接受无匹配节点或匹配节点不可见，不能证明节点已移除。
  • 需要证明移除时应先确认目标出现，再用稳定定位器与 toHaveCount(0) 验证无匹配节点。
  • 隐藏、DOM 移除、旧输入清除和服务端数据删除是不同验收目标，不能由单一 UI 断言互相推导。

用户关闭一条带有个人信息的弹窗，Playwright 的 toBeHidden() 断言通过。团队于是写下“弹窗节点已从 DOM 移除”的验收结论。这个结论超出了断言证明的范围：Playwright 官方定位器断言文档中，定位器没有匹配到任何 DOM 节点，或匹配到一个不可见节点，都能满足 toBeHidden()。同一个绿色结果，可能来自删除节点，也可能只是 display: none 等不可见状态。测试必须先问产品真正承诺的是什么。

设确认框在点击关闭后应消失。下面的测试适合检查视觉上的消失，却不足以证明 DOM 清理：

const dialog = page.getByRole('dialog', { name: 'Delete draft' });
await expect(dialog).toBeVisible();
await page.getByRole('button', { name: 'Cancel' }).click();
await expect(dialog).toBeHidden();

第一条断言很重要：如果选择器写错，或者弹窗从未出现，单独运行 toBeHidden() 也可能通过，因为“没有节点”属于它接受的结果。先证明可见、再触发关闭、最后检查隐藏，才覆盖了一个有意义的状态转换。但最后的 toBeHidden() 仍没有区分关闭后保留隐藏节点还是删除节点。若产品只要求不再占据可见界面，保留节点可能完全符合契约；为了追求更“严格”的测试去要求移除，反而会把合法实现细节钉死。

若真实要求是节点必须不再存在，比如每次打开都会新建实例、关闭必须清除旧实例以免事件监听累积，可以用定位器数量表达移除后的状态：

await expect(dialog).toBeVisible();
await page.getByRole('button', { name: 'Cancel' }).click();
await expect(dialog).toHaveCount(0);

Playwright 文档把 toHaveCount() 定义为定位器解析到精确数量的 DOM 节点；0 才是在该定位器范围内没有匹配节点。这里仍要注意选择器本身的范围：如果它只匹配带某个名称的对话框，产品可能把节点保留但修改了可访问名称，这也会让计数变零。一个断言证明的是“这个定位器找不到匹配节点”，不等于整个页面无同类节点、无残留个人信息，或后台资源已释放。需要把定位器锚在稳定、与验收目标一致的节点身份上。

另一种需求是对话框从页面断开，但界面可能继续保留模板节点供复用。Playwright 提供 toBeAttached() 检查节点是否连接到 Document 或 ShadowRoot，不过它仍依赖定位器可以指向目标节点。对于“全页面无此对话框”这种契约，toHaveCount(0) 更直接。对于“存在但不可见”，toBeHidden() 更贴切。选择哪个断言应来自需求描述，而非哪个 API 名字听起来更像“关闭”。不必为了简单的视觉隐藏引入脆弱的 DOM 结构测试，也不能拿视觉隐藏为数据清除做证明。

负例可以揭示断言盲区。实现 A 在关闭时执行 node.remove()；实现 B 只给节点加 hidden 属性。两者都可能让 toBeHidden() 通过，只有 A 会让针对该节点的 toHaveCount(0) 通过。实现 C 根本没渲染对话框，但测试直接断言隐藏，仍会得到绿色；前置的 toBeVisible() 能把 C 挡住。实现 D 把内容移动到另一容器，原定位器数量变零，却未清理敏感文本；这说明定位器数量也不能代表隐私擦除。若安全目标涉及敏感信息，应另行检查内容、状态、存储与服务响应，不能用一个 UI 断言替代。

断言的等待机制也会影响测试质量。不要在点击后用固定延时猜测动画结束；Playwright 的定位器断言会在期限内重试，等待目标状态。只需把等待条件设成最终契约：视觉消失用隐藏，真实节点移除用零数量。若应用允许淡出动画，点击后短暂可见是合理的，断言的自动等待可容纳它；如果始终未达到状态则应失败。固定睡眠既可能在慢机器上不足，也可能在快机器上浪费时间，还不能告诉维护者究竟哪个状态没有发生。

错误的测试契约会影响回归判断。组件重构从卸载改为复用隐藏节点，若用户体验契约仅是“关闭后不可见”，toHaveCount(0) 会制造无价值的红灯。反之，某个组件因为残留节点产生重复监听或旧输入泄漏，toBeHidden() 仍可能绿。审查测试时把需求写成可以观察的句子：“关闭后用户看不到弹窗”“关闭后定位器匹配零个节点”“再次打开不会沿用旧输入”，再给每句配独立断言。不要把这三句话揉成一个含糊的“弹窗已关闭”。

站内 点击后等待业务结果 讨论过为什么点击完成不等于后续状态完成。本篇进一步区分后续状态究竟是不可见还是不存在。测试应该从首次打开验证目标节点，再执行真实关闭入口，最后确认所选状态；如果业务还涉及网络保存、权限撤销或表单清空，分别用能观察那些结果的证据验收。一个截图不能证明节点被卸载，一个 DOM 计数也不能证明服务端数据被删。

在真实应用验收中记录 Playwright 版本、测试定位器、组件实现版本、失败时的 DOM 快照或 trace，并分别运行 A、B、C 类型的可控组件反例。这样可以证明所选断言确实区分需求允许与禁止的实现。本文核对的是 Playwright 官方 LocatorAssertions 文档对 toBeHidden 和 toHaveCount 的定义，未在本环境运行浏览器或应用页面；示例代码展示预期测试契约，不是已通过的端到端结果。准确的结论应与断言同宽：隐藏断言通过只证明没有匹配节点或匹配节点不可见，不能自动升级为 DOM 移除。

实践中还需关注重复匹配。若页面上同时有多个同名对话框，单个定位器断言可能因严格模式或目标含糊而失败，或者 toHaveCount(0) 要求所有匹配者消失，这与只关闭当前实例的需求不一致。测试应先限定当前弹窗容器或业务对象，再说明是清除一个实例还是所有实例。若不同视口或辅助技术下可见性表现不同，也应按用户可观察的契约分别验收，而不是把一次桌面浏览器的绿色结果推广为所有环境均已达标。
