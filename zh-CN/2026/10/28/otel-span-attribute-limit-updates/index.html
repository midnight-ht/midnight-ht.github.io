Span 属性满额后，旧键还能更新吗？

用两个槽位的假设区分同键更新与新增超限，保留 SHOULD 和 MUST 的强度，检查字段顺序、不同集合预算与实际导出。

正文

核心要点

  • 属性预算计算集合数量，不是 SetAttribute 调用次数。
  • 同键覆盖是 SHOULD，新增超数量限制的丢弃是 MUST。
  • Span、事件、链接和值长度预算不同，实际 SDK 配置与后续传输需另查。

假设一个仍在记录的 Span 已达到属性数量上限，随后代码更新已有键 status。已有键的值替换与增加一个新键是两件事，不能把所有后续 SetAttribute 都视为新增槽位。排查字段缺失时，先分清是在更新哪个已有键，还是试图写进另一个键，再检查 SDK 的实际预算。

数量限制约束集合，不是在数调用次数

OpenTelemetry 通用规范的 Attribute Limits要求：若添加属性会使集合数量超过限制，SDK 必须丢弃该属性；否则不得因这项数量限制丢弃。规范还建议，设置与已有属性相同的键时，应覆盖已有值。这里要保留强度区别：同键覆盖使用 SHOULD，超数量限制的丢弃规则使用 MUST，不能把前者随手改成所有实现都无条件保证。

本文读取的规范页面标示 1.62.0 版本，讨论接口与 SDK 规范，不代表某个语言实现已经按项目配置采用。通用参数给出的属性数量默认值为一百二十八，实际运行仍要核对语言 SDK、版本和配置。示例为方便观察改用上限二；这个小数字不是生产推荐，也没有运行相应 SDK。

唯一键集合与写入次数不同。给同一个键先后写两次，意图是在同一身份上更新值，而不是让后端获得两个同名属性槽位。规范默认要求导出的属性集合键唯一；不能因为业务想保存两次状态，就依赖重复键同时留下。若需要时间顺序，应选择有相应语义的记录，而不是期待属性覆盖保留历史。

用两个槽位区分更新与新增

设想 Span 仍可记录，属性上限为二，先写 job.kind=import 和 job.phase=queued。随后将已有的 job.phase 更新为 running，再尝试添加新键 job.ticket。按同键覆盖的规范建议，更新已有阶段不会增加唯一键数量；新增 ticket 则会把二变为三，触发数量限制的丢弃规则。

# 语言中立伪代码，未执行；limit=2 需由实际 SDK 配置
set("job.kind", "import")
set("job.phase", "queued")
set("job.phase", "running")  # existing key
set("job.ticket", "T-7")     # new key beyond the limit

预期检查不是“第四次调用一定消失”，而是比较集合中的键和值：阶段是否按实现处理更新、ticket 是否因为新增超限被丢弃、已占用键是否仍在。若测试只数调用次数，会把第三次更新也算成新属性，无法区分故障。还应先在没有达到上限时写入 ticket，确认它并非被另一个过滤规则一直删除。

字段写入顺序因此有实际代价。若大量可选诊断键先占满预算，后续才新增必需的分类键，就可能缺少后者。可以在创建 Span 时提供当时已知且必要的稳定信息，再为扩展诊断分配有限预算。Trace API还说明，采样器只能考虑创建时已有的信息；晚写字段不能追溯改变原先的采样决定。这不是要求提前编造尚未知道的最终状态。

Span 看得见，不代表每个属性都送到了后端

缺失属性可能发生在 SDK 记录阶段，也可能发生在之后的转换、导出或后端展示。某个 Span 已经可见，只证明该记录的一部分走到了当前查看位置。若本地早已因预算丢弃新键，增加网络重试不会把它从不存在的属性集合中恢复出来。排查要先拿到最接近 SDK 的受控导出，再逐层比较。

也不要把所有限制合成一个数字。Tracing SDK 的 Span Limits另外列出事件、链接以及每个事件和链接的属性预算。Span 自身属性达到上限，不等于某个事件的属性集合使用了同一批槽位。反过来，事件能被记录，也不证明它携带的全部属性完整保留。核对的是具体集合和具体配置。

反例是看到后端缺少 job.ticket，立即把所有上限扩大数十倍。这样没有确认丢失位置，也没有判断字段是否值得长期采集。如果 ticket 具有高唯一性、含敏感标识或根本无法被排查动作使用，更大预算只会保留更多不必要内容。先决定必要键和稳定命名，再对真实成本与隐私范围作选择；本文没有测量内存或后端费用。

把大段 JSON 放进一个属性，就避开所有限制了吗？

没有。数量与值长度是不同预算，通用规范另有属性值长度的配置与截断规则。把很多信息编码进一个字符串，只会让集合看起来少了键，不会自动获得无限长度，也会改变后端按字段查询的方式。若采用这种表示，应定义长度、截断后的可解释性和敏感内容处理，而不是把它当成绕过约束的捷径。

生命周期还要单独核对：本文示例限定 Span 仍在记录，结束后的修改不在此范围。本站Span 结束与 Context 作用域解释另一个独立边界；不要因为同键更新不增加数量，就推导它能在任意时点改变已经结束的记录。

隔离这项规则还需要控制记录前提。测试如果采用会拒绝记录该 Span 的采样配置，所有属性都可能不可见；若在结束之后才写入，也不能把缺失归因于数量预算。应先用低于上限的两个稳定属性确认本次 Span 的记录与导出路径，再只改变新增键数量，避免同时修改采样器、处理器和后端查询条件。这里是拟议实验设计，不为某个采样器预写输出。

还可以交换第三次和第四次操作：先尝试添加 ticket，再更新已存在的 phase。即使新增项因数量上限失败，后续更新仍应按同键操作的规则判断，不能把一次超限当成整个 Span 后续一律不可修改的标志。比较两种次序时，保留同样的已有键与预算，才能知道差异是否来自实现对更新的处理，而不是测试输入不同。若需要记录被丢弃数量，也要核对所用导出格式实际提供什么字段，不凭后端空白推算丢弃次数。

待执行验收应保存 SDK 精确版本、实际生效上限、写入次序与原始导出，分别覆盖上限之前、刚好满额、同键更新和新增超限四种状态，再观察后续 Collector 与后端。若同键行为与 SHOULD 建议不同，应记录实现与条件，不用规范措辞伪造运行结果。本文没有执行这些检查；可交付结论是明确集合预算和丢失位置的方法，而不是所有 SDK 都已通过属性保留测试。
