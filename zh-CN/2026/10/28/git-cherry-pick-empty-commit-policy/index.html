cherry-pick 变空后，--allow-empty 为什么还不够？

区分原本为空与回补后冗余的提交，比较 stop、drop、keep 及 skip、abort 的结果，把历史策略与修复验证分开。

正文

核心要点

  • 原本空提交和重放后变空需要分别选择策略。
  • empty=keep 隐含 allow-empty，drop 与 stop 不单独允许原本空提交。
  • 保留历史记录不能替代目标修复行为与产物验证。

一个原本有补丁的提交，在目标分支已包含相同改动时可能变空。--allow-empty 主要保留原本就空的提交，这与重放后才冗余的情况需要分开处理。先确定空来自哪里，再决定停下检查、丢弃，还是保留一条记录；不要只为让回补脚本继续而统一跳过。

原本没有树变化，与重放后没有树变化

Git 的 cherry-pick 手册把最初就是空的提交，解释为它记录的树与父提交相同。--allow-empty 允许保留这类提交，却不单独解决原本有改动、因当前历史已有对应变化而变空的提交。后者由 --empty=drop|keep|stop 表达策略。本文核对当前手册及官方仓库文档，不声称读者安装的旧版本都支持相同选项。

空提交消息是另一回事。一个提交可以没有文件变化却有完整说明，也可以有文件变化但消息为空。--allow-empty-message 针对的是后者的消息规则，不能用来修复补丁冗余。排障时至少区分来源提交树、来源消息和应用后的目标树，三个条件不能因中文都叫“空”而混在一起。

以下只讨论常规提交回补，不使用快进路径，也不处理合并提交主线选择。手册对快进保留空提交另有条件，因此这里的默认行为不能扩大成所有组合的断言。任何拟采用命令先核对 git --version 与该版本帮助；本站仓库没有为本文执行 cherry-pick，示例中的提交名都是假设身份。

把两个来源提交放进一张决策表

假设基线 B 上产生提交 X，将 timeout 配置由十改为二十。维护分支后来经由另一条路径也已采用同样改动。再次回补 X 时，它原本有补丁，但在这个目标上下文里可能没有新增变化。这是“变成空”的候选，应该问当前分支是否已经有等效修复，以及是否需要保留这次回补的历史记录。

再设提交 M 是有意创建的里程碑记录，树与自己的父提交完全相同，消息说明某次人工检查。M 从一开始就没有补丁。若政策要求在维护分支保留这样的标记，需要允许原本空的提交；若政策只关心实际变更，则应另外处理这个来源对象。不能用“重复修复自动丢弃”的策略，悄悄替团队决定里程碑记录没有价值。

这两个例子都没有执行。它们的差别不在于文件名或消息写得是否漂亮，而在于来源提交是否原本改变树。自动化应在任务策略里区分两类意图，避免一次新的 Git 退出提示就触发无条件重试。重试同一补丁没有增加解释；先保留来源与目标完整提交标识，才有后续核对的基础。

drop、keep 与 stop 分别承担什么代价

当前手册说明，--empty=stop 是对重放后冗余提交的默认处理：在应用时停住，让操作者检查。drop 丢弃该提交；keep 保留它，并隐含允许原本空提交的选项。drop 与 stop 并不单独允许最初就空的提交。因此，选择自动丢弃冗余项，不等于所有空提交都能无条件走完。

stop 适合还需要解释为什么变空的交互式回补，但无人处理时会让流水线停在那里。drop 适合明确接受“目标已具备变化，不再制造记录”的流程，代价是少一条回补提交。keep 可以保留事件记录，但这条新记录没有新增文件差异，不能把它计成又实现了一次功能。选择应落在历史与审核要求上，而不是单纯追求提交数少或多。

如果已经停住，先确认当前序列、工作树和索引，再决定后续动作。手册中的 --skip 跳过当前提交并继续余下序列，--abort 则取消操作并返回序列前状态。两者不是同义的“清除错误”。若后面还有几个依赖补丁，跳过这一项会让后续继续；取消则是在放弃这次序列。执行前应知道是哪一种结果符合任务。

反例是任何非零退出都执行 skip。冲突、非法引用或其他错误不等于“已经有相同补丁”，而真正的冲突解决还可能改变业务行为。脚本应该保留明确错误与状态，并按被授权的场景处理；不能让一个宽泛的失败分支成为自动丢变更的入口。本文没有给出可直接用于生产的自动处理脚本。

保留空提交能证明修复仍然生效吗？

不能。它可以记录一次决定，却不能证明目标当前行为符合修复要求。目标可能有等效代码，也可能只是在冲突处理时被人为清空；随后提交还可能再次撤销行为。需要检查目标树、相关调用路径和针对性验证。历史记录与运行结果分别提供证据，不能用一个漂亮的回补消息替代后者。

本站空 diff 与提交祖先关系讨论内容与历史可达的区别。本篇新增的是空提交策略：即使已经判断两份内容等效，仍要决定是否保留回补对象。原提交标识与新提交标识通常不同，报告应记录实际目标对象，不把消息中的来源行当作原提交成为祖先的证明。

一份可交接的回补记录可以直接列出来源 X、目标起点、处理空项的选项、作出决定的理由和剩余补丁列表。若选择丢弃 X，补充目标已具备所需变化的证据；若选择保留，说明这条空记录承载什么追溯要求。后续补丁若依赖的是功能行为而非某个提交对象，也要在目标分支重新验证，不能因序列继续运行就认为依赖自动成立。这些字段让停下来的任务能被下一位维护者解释。

待执行验收可以在临时仓库准备 X 与 M 两类输入，固定目标基线，分别观察默认停止、丢弃冗余、保留空记录及允许原本空提交的结果。每次从干净且已知的起点重建序列，保存命令版本、退出码、最终树和提交图，再用一个真实冲突负例确认脚本不会自动误跳。本文没有运行这些场景。回补完成的结论应同时说明如何处理空项、保留了什么历史，以及目标修复行为验证到哪里。
