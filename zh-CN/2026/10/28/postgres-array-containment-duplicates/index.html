一个库存单位为什么能“包含”两个相同需求

解释 PostgreSQL 数组包含不计重复次数，比较标签、数量与数组相等，给出配货校验的选择边界。

正文

核心要点

  • 数组包含检查元素存在，不为重复需求分配独立单位。
  • 总长度相同与双向包含都不等于数量满足。
  • 数组相等、标签集合和库存分配需要独立合同。

ARRAY[1] 与 ARRAY[1,1] 在 PostgreSQL 的数组包含判断中可以互相包含。这个运算检查每种元素是否出现，不替你核对库存数量。若一表示一种商品，一件库存不能因为包含判断为真，就被解释成足够交付两件同款。

包含运算没有替重复值计数

PostgreSQL 18 数组运算文档把 @> 定义为：右侧出现的每个元素，都能在左侧找到相等元素。重复值不会被特殊对待。本文依据第十八版讨论普通整数数组，示例没有执行，也不把未知元素、多维形状或其他类型的比较规则一起压成同一种业务集合。

假设一个简单原型用商品编号数组表示可用单位，左侧只有编号七，需求数组含两个七。下面的包含判断按元素存在性可以成立。右侧第二个七不要求左侧再提供一个独立单位，两个需求位置可以由同一种值的存在满足。

SELECT ARRAY[7] @> ARRAY[7,7];
SELECT ARRAY[7,7] @> ARRAY[7];
SELECT ARRAY[7] = ARRAY[7,7];

前三行不是运行结果记录。按文档规则推导，前两项包含为真，第三项数组相等为假。把这些推演作为待执行测试的明确预期，可以防止验证只检查“查询有返回”，没有检查业务真正关心的数量差别。演示数字没有对应真实订单或仓库。

这不意味着数组包含是坏工具。若商品只有一份去重标签集合，需求是同时具有“可回收”和“促销”，关注的是两类标签都出现。标签重复一般不提供额外价值，包含语义可能正好符合要求。错误发生在把这种存在性合同搬到数量合同，却继续使用同样的判断名称。

接口里将字段命名为 items 也不足以决定语义。它可能表示商品种类、订单行、可售单位或任意重复的历史事件。先确定一个元素代表什么，再决定重复是否有信息；不要在查询之后才用返回值倒推产品想表达哪一种数量。

同样元素数量，并不保证同样配货

只比较两个数组总长度也不能修复这个问题。假设库存是七和八，需求是七和七；两边都有两项，但第二个商品种类不同。若先做总量相等，再做“存在任意交集”，仍会接受一份缺货的需求。需要的是按商品分别比较需求数量与可用数量。

一种可讨论的数据模型是每个商品有显式数量，或者每件可追踪单位有独立身份。前者适合按商品汇总，后者适合序列号、批次或必须辨认单件的场景。选哪种取决于库存合同。本篇没有提供并发扣减 SQL，数量校验通过也不能独自证明后续写入不会与另一个订单争用同一库存。

若继续用重复数组表达数量，可以先按元素分组计数，再比较每种值的计数是否足够；这只是语义层设计建议，还需明确空输入、未知输入和非法编号怎样处理。不能在计数前随手去重，因为去重恰好删除了待核对的数量。也不能遇到未知商品就静默略过，否则“全部可满足”只描述被留下的子集。

把验证与分配分开也很重要。页面展示“目前可满足”，与提交订单时保留库存，是两项不同承诺。允许并发下结果变化的预览，应给出适当文字；承诺已经保留，则需要有实际持久状态和失败恢复规则。一个布尔包含表达式无法承担后者。

双向包含能当作数组相等吗？

不能。双向包含不会自动比较重复次数或原始顺序。数组本身的相等比较保留数组的结构与元素信息，官方文档还说明维度信息也参与数组比较。不要把为标签集合选择的等价关系，推广为“任何数组都一样”。

例如七、八和八、七可以互相包含，但不是同一顺序的数组；七与七、七也可以互相包含，但长度不同。若业务明确把普通非空整数标签规范化为去重且按固定方式排序的集合，可以建立自己的集合比较合同，但必须承认规范化已经丢弃了顺序和次数。需要保留这些信息的记录不能使用该合同。

下界和多维形状如果携带领域含义，也要留在输入验证中。即使展示出来的数字相似，结构不同仍可能来自不同协议。最稳妥的评审方式是列出允许忽略的差异，再选择操作；不要以某一条包含结果碰巧相同，推导出所有差异都无关。

本站空数组长度与总元素数讨论计数口径，与本题有关但不能替代它。总量能帮助描述输入规模，不能说明某种商品出现几次，更不能证明它们属于可售状态。统计、包含和分配应各自有清楚名称。

待执行用例可从四个反例开始：一件同款对两件需求、同总量但商品种类不同、顺序相反、重复次数不同。分别写明标签筛选、数量满足和原始数组相等的预期，避免只维护一套真假断言却用于三种接口。再加入空输入、未知来源与非法商品，确认错误不会被包装成正常不匹配。

可以把这个差异写成一张待验证的计数账：可用商品七为一件、商品八为三件，需求商品七为两件、商品八为一件。总库存四件大于总需求三件，但商品七仍缺一件，商品八的余量不能补成另一种商品。正确拒绝理由应指向商品七，而不是笼统报告总量不足。若需求按不同配送日期分组，同一种商品也未必能够跨日期合并；分组键应包含实际分配约束。把计数键写成商品编号只是本例的简化，不是要求忽略仓库、批次或可用状态。验证时故意让总量足够而单种不足，可以证明校验没有退化为总数比较；再让总量与各组都满足，确认合法需求不会因为原始重复表示而被误拒。

若实际实现按数量分组，验证还应核对拒绝原因能定位到具体商品和缺少数量，而不是只给“数组不包含”。这会让调用方知道应该减少数量、补库存，还是修正输入。本文没有执行这些检查；决定采用 @> 前，先写出“重复的一项是否代表更多需求”，就能排除这类最小但危险的语义误用。
