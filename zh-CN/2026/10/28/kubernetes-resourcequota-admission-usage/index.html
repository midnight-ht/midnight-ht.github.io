节点 CPU 很空闲，新 Pod 为什么仍被命名空间配额拒绝？

用显式 requests.cpu 预算算例区分节点实际用量与命名空间配额，沿 Deployment、Pod 准入、调度和就绪定位失败。

正文

核心要点

  • 节点实际空闲不能抵扣命名空间的请求账目。
  • Deployment 创建成功不代表管理的 Pod 已全部创建。
  • 配额变更不自动回收已有资源，放行后仍需检查调度与就绪。

假设节点监控显示实际 CPU 用量很低，新 Pod 却收到 exceeded quota。ResourceQuota 检查命名空间被计入的资源声明与硬限制，节点实际空闲不能说明这项配额还有余额。先核对拒绝消息指向的配额项目，再决定是调整声明、释放占用，还是申请更多预算。

节点曲线与配额账目在回答不同问题

Kubernetes 的 Resource Quotas 文档将资源配额定义为命名空间内聚合资源消耗和对象数量的约束。创建或更新违反配额的资源时，控制面会以 HTTP 403 Forbidden 拒绝请求，并在错误中解释约束。这里讨论当前在线文档的机制，不把网站更新日期当成集群版本，也没有连接真实集群。

限制的名字很关键。requests.cpu 约束的是相应请求的合计，不能拿监控中的实际处理器使用量来抵扣。对象数配额又是在数相应对象，不是数正在处理业务的进程。排障记录应保留配额名称、资源项目、硬限制、已用值及本次请求增量，而不是把所有拒绝概括成“机器不够”。

以下限定一个没有 scope 的命名空间配额，只讨论显式 CPU requests；不展开默认注入、Pod 级预算或混合初始化容器的计算。实际对象如果超出这个简例，应先查自己的最终配置和相应版本文档。源模板不一定就是最终提交或准入后的对象，不能只从仓库里的一行配置估算所有占用。

两个空闲副本，也可能用完声明预算

设想命名空间的 requests.cpu 硬限为二个 CPU，已经有两个被计入的 Pod，每个显式请求一个 CPU。账目合计为二，第三个同配置 Pod 再请求一个，新的合计就超过硬限。即使监控显示前两个副本此刻各只实际使用很少的 CPU，也不改变这笔声明账目。这是未执行的配置推演，不是集群返回结果。

这个例子没有声称“已用小于硬限也一定拒绝”。若硬限提高为三个，且没有别的占用或约束，例子中的这一项不再因合计超过三而拒绝。但放行还可能受别的配额项目和准入政策影响，所以不能把通过 CPU 一项写成所有条件都通过。反过来，硬限二、已用一点五，也要比较新增请求；不能仅看还有零点五就断言能放入一个完整 CPU 的请求。

选择修复方式要对应预算的来源。若副本确实需要这份请求，应评估提高命名空间预算或减少不再需要的占用；若请求明显高于合理需求，应通过应用与负载证据调整它。为了让部署通过而随意把请求调小，改变的是资源承诺，未必减少实际需求，还可能改变后续调度安排。本文没有测量该应用需求，不给出应该减到多少的建议。

Deployment 成功不是每个 Pod 都存在

官方文档特别说明，创建 Deployment 等工作负载对象可以成功，但它管理的 Pod 未必都能创建。控制器之后申请 Pod 时仍要经过相应约束。流水线若只检查 Deployment 创建请求成功，就可能把没有达到副本目标的发布记为完成。需要观察控制器状态和事件，确认失败发生在哪个对象请求上。

假设目标从两个副本增到三个，工作负载声明更新成功，而第三个 Pod 因配额被拒。这时不断等待一个根本没有创建出来的 Pod 进入 Ready，容易遗漏真正的失败位置。应从控制器的失败事件找出拒绝原因，再核对相关配额账目。已有 Pod 的日志可能完全正常，因为拒绝的是新对象，旧进程没有经历同一次错误。

这种定位也影响恢复动作。重新构建相同镜像、重启已经正常的旧副本，不会自动增加命名空间预算。若决定暂时减少目标副本数，应说明业务容量和可用性影响；若决定提高预算，则要确认共享集群的容量与管理授权。配额变更是一项配置动作，不能代替对服务恢复结果的观察。

下调配额会终止已经创建的 Pod 吗？

不会因为这次配额下调就自动处理已经创建的资源。文档明确说明，争用或配额变化不影响已经创建的资源。因此，下调后的账目即便看起来超过新上限，也不能推导系统会自动删除旧 Pod 或把它们的请求缩小。存量回收需要有明确对象和业务后果的工作负载操作，而不是等待配额替管理员作决定。

同理，释放占用时要核对实际对象和更新后的账目，不能仅凭应用已经不忙便认为预算已归还。若准备删除闲置工作负载，应先确认其所有者、业务用途与恢复材料。这里没有执行删除；建议表达的是要把“决定不再需要”与“配额记录已反映结果”分成可核对的状态，避免基于过时截图再次提交。

提高配额以后，为什么仍可能调度失败？

配额准入与节点放置是不同阶段。提高配额可以解除本例的命名空间预算限制，却不为 Pod 创造合适节点。节点可分配资源、已经承诺的请求以及其他调度条件仍需分别检查。本站普通 init 容器的请求计算提供另一种可能放大有效请求的情况；本例没有把那套简式混进配额算例。

还要固定账目观察时点。假设两个发布任务先后读取同一份余额，随后各自申请一个副本，较早截图并不能保证两次申请都能满足预算。这里不预测控制面处理顺序，只要求记录本次拒绝发生时的相关对象与最新状态。若团队按流水线预检查配额，预检查应作为提示，而不能被写成随后创建必然成功的承诺。重新提交前也要确认不是另一个发布占用了原先空余。

待执行验收应保存配额 hard 与 used、显式请求、目标副本数、控制器事件和最终 Pod 状态。先安排第三副本因本例预算不足而失败，再在隔离环境改变一项预算，确认对应拒绝消失，并继续检查调度与就绪；若仍失败，保留新的原因。本文没有执行这些步骤，不报告发布通过。验收结论应明确停在准入、调度还是服务就绪，而不是只附一张 CPU 空闲图。
