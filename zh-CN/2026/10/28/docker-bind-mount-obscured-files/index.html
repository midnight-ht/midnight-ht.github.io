镜像里有配置，bind mount 后为什么不见了？

从空宿主目录遮蔽镜像文件入手，比较 --mount 与 -v 的默认缺失路径行为，核对 daemon 来源和只读边界。

正文

核心要点

  • 绑定源遮住镜像目标内容，空宿主目录不会自动复制默认文件。
  • 不存在的源在 --mount 与 -v 默认调用中有不同结果。
  • 绑定源属于 daemon 主机，读取来源与写权限应分别核对。

假设镜像在 /app/config 放了默认文件，把一个空宿主目录挂到这个位置后，容器看到的却是空目录。bind mount 遮住目标目录，并不会把镜像默认文件复制进宿主目录。先核对挂载来源和目标，再重建镜像；否则镜像里的文件即使更新，也仍然不在当前可见视图里。

文件被遮住，不等于文件从镜像中删除

Docker 的 Bind mounts 文档说明，在已有文件的容器目录上绑定宿主路径，会遮住原有内容。常规做法是重新创建一个不带该挂载的容器，以重新看到镜像文件；在运行中的容器里直接移除挂载并不简单。本文解释当前 Engine 文档的语义，没有启动 Docker 或修改任何用户目录。

把镜像内容与容器当时的挂载视图分开，问题就更具体了。镜像目录提供一组文件，绑定源提供另一组；绑定生效后，目标位置展示后者。宿主源目录为空，不意味着 Docker 会自动从镜像填充它。空的命名卷默认初始化是另一种机制，不能因两者都能写成挂载参数就互相套用。

本站空卷首次复制与后续更新讨论的是命名卷初始化、已有持久数据和迁移。本篇关注绑定的源路径怎样遮住视图，以及路径错误何时被发现；不把迁移策略再写成一篇新题。诊断中先确认 mount 的类型，才能知道自己是否根本用错了复制预期。

同一个镜像，两种读取结果

设想镜像的 /app/config/default.json 保存默认配置，宿主机的 /srv/demo-config 是一个事先创建的空目录。将它绑定到 /app/config 后，应用去读取 default.json 会找不到该文件。这个例子是未执行的路径推演，文件名与目录均为说明用途，不是某个服务的真实失败记录。

对照方法是从同一个确定镜像标识创建两个临时容器：一个带绑定，一个不带绑定，分别检查目标目录。预期差别来自挂载，而不是标签恰好指向两个镜像。验证时记录镜像摘要、源路径、目标路径、挂载类型与文件清单。不要只看容器名或一个可变标签，否则两组输入是否相同都无法确认。

如果应用需要合并产品默认配置与现场覆盖项，可以为两者使用不同目录，再由应用按明确优先级读取。也可以预先准备完整的宿主配置，再只读挂载给容器。前者需要处理缺省和覆盖冲突，后者需要配置分发与完整性检查；这都是工程选择，Docker 不会自动执行这种合并。直接复制整个默认目录还需决定覆盖权限和已有改动的归属。

拼错源路径时，两种语法暴露错误的方式不同

文档区分 --mount 与 -v 的默认行为。绑定源不存在时，--mount 默认报错；-v 会创建相应目录，而且即使原本想挂一个文件，创建出来的也是目录。对于必须事先存在的配置输入，这个差异可能把一个清楚的路径错误变成稍后的应用文件错误。

# 示意：源目录应事先存在；未执行
 docker run --mount type=bind,src=/srv/demo-config,dst=/app/config,readonly IMAGE

这里的 IMAGE 需要换成实际经过审核的镜像标识，示例不是完整应用启动教程。当前文档还提供显式创建源的选项；“默认报错”不能扩成“任何配置都永远禁止创建”。如果团队有意让工具创建目录，应把这个意图与校验方式写清楚，而不是让拼写错误与正常初始化产生同一种成功表象。

最容易误判的是源文件名拼错。运维以为挂的是一个配置文件，运行时却得到一个新目录，应用可能报告类型不符或目标读取失败。排查时除了名称，还要检查源的文件类型和目标预期类型。添加更长启动超时不会把目录变成文件；重建镜像也不会改正绑定源名称。

远程 Docker 绑定的是本机路径吗？

不是以命令行客户端的本地文件树为准。绑定源属于 Docker daemon 所在的主机；远程 daemon 不能因为客户端上有 /srv/demo-config，就直接读取那个客户端目录。Docker Desktop 通过自己的共享机制处理本机与虚拟环境路径，仍应按其受支持方式核对，而不是把远程 daemon 的规则理解成所有桌面路径都不可用。

因此，应记录 daemon 身份和连接目标。开发者电脑上确实存在的目录，与远端构建机或运行机上同名目录，可能有完全不同内容。路径字符串相同不等于来源相同。若切换 Docker context 后故障出现，先确认命令发到了哪里，再检查那个 daemon 能读取的源；不要把本地文件清单作为远端输入证据。

绑定默认允许容器修改宿主内容，文档因此提醒其对宿主文件的影响。只需读取配置时可采用只读绑定，但它既不验证配置内容，也不会保证所有宿主文件都因此安全。应用需要写缓存或状态时，应给它明确的写入位置；把整份配置目录改可写，只为消除权限报错，会扩大这条绑定能影响的范围。

例如应用默认配置给出监听端口和一个辅助服务地址，现场只需要覆盖地址。若把只有地址文件的目录直接挂到整个默认目录上，端口文件仍会被遮住。分目录读取时，可以约定缺少覆盖项就采用产品默认，但已经提供却格式无效的覆盖项应报告错误，而不是默默退回另一个环境地址。合并到键级还是文件级，也会改变删除和恢复的语义；应让应用配置契约明确说明，不能从绑定挂载本身推导。

待执行验收可以用无敏感内容的临时目录覆盖四种输入：正确且非空、正确但为空、不存在、文件与目录类型不符。每组保留实际创建参数、daemon 目标和容器可见文件；再核对只读设置是否按预期阻止修改。本文没有运行这些检查。先证明容器读到的是哪一个来源，再判断配置是否正确，才能避免用一轮又一轮镜像重建处理同一个宿主路径错误。
