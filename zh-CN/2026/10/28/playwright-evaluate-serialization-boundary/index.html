page.evaluate 为什么读不到测试里的变量？

把测试与页面环境分开，用明确 arg 和精简返回数据验证价格，说明当前函数暴露选项、句柄与 Promise 等待的范围。

正文

核心要点

  • 默认调用中测试变量需要显式传入页面回调。
  • 数据返回与页面侧句柄有不同目的，当前新选项需核对项目版本。
  • Promise 完成与业务就绪不同，快照值不会自行重新读取页面。

测试里定义了 expected，evaluate 回调里直接使用它却不会形成跨进程闭包。需要把值作为参数传进页面环境，并明确哪些结果要作为数据带回测试。看到同一段 JavaScript 中的变量名，不代表浏览器页面与测试进程共享作用域；延长等待也不会修复缺少的输入。

回调写在测试文件里，执行位置却在页面

Playwright 的 Evaluating JavaScript 指南说明，测试脚本与页面脚本在不同环境、虚拟机和进程中运行，甚至可能位于不同电脑。page.evaluate 在网页上下文执行函数，因此可访问页面的 window、document，却不能直接使用测试作用域里的变量。值需要显式作为参数传入。

这里讨论当前文档下的默认调用方式，不开启函数暴露选项。当前 Page API另列出1.62 版本新增的 options.exposeFunctions，默认关闭；启用时可把 arg 中的函数暴露给页面调用。因此，不能把常规的数据传参规则写成“任何版本永远只有一个附加参数”，也不能说函数在所有配置下绝对不能跨过去。采用新选项仍要先核对项目安装版本。

测试文件里熟悉的导入也受这道边界约束。一个本地价格计算辅助函数不会只因在回调外可见，就自动成为页面的函数。若要测试真实页面计算，应读取页面可观察结果；若需要预期值，可在测试侧计算后传入。把两份同源算法一起搬进测试，不一定能发现页面算法本身的错误，需要让期望来自独立的业务约定。

把输入与返回数据都写清楚

假设商品页有一个标识唯一的价格元素，以 data-cents 保存当前价格的整数分值；需求规定优惠后应为八百分。下面是未执行的示意，只说明跨环境传参和精简返回，不证明任何商品页面或优惠规则已经验证。真实页面是否有这些属性，需要由项目契约确认。

const expected = 800;
const observation = await page.evaluate(({ expected }) => {
  const element = document.querySelector('[data-testid="price"]');
  const raw = element?.getAttribute('data-cents');
  return {
    expected,
    raw,
    present: element !== null,
  };
}, { expected });

返回的是存在性和原始文本，不是把 DOM 元素当作完整对象搬回测试进程。测试侧可以先断言 present，再验证 raw 符合页面约定的整数格式并与 expected 比较。不要直接把空字符串转成零后当作合法价格，这会把缺失属性与真实零价格混在一起。若测试价格精度，还要另行规定货币与分值单位，不能只看文字含某个数字。

这个例子有意保留原始观测与期望两列。把页面值和期望先在回调中合成一个布尔值，失败时通常只剩 false，难以看出元素缺失、格式错误还是数值不符。返回必要的无敏感小数据更便于定位，但也不应为了排障导出整页内部状态或凭据；选择范围应与当前断言有关。

一个数据入参，可以组合值与句柄

指南中的常规 evaluation arg 可以混合可序列化值和 JSHandle，句柄进入回调后会转为它代表的页面侧值。多个期望字段可以打包成一个对象，再在回调参数里解构；命名要与传入对象一致。无需为了传两个数字拼接脚本字符串，这会让转义和输入解释更难审查。

如果需要继续操作页面中的对象，可使用 evaluateHandle 得到页面侧引用，再按句柄 API 使用并清理。它与 evaluate 返回数据的目的不同。Page API 说明，函数返回非 Serializable 值时，普通 evaluate 会得到 undefined；同时支持负零、非数字和无穷等额外值，因此也不能把这套传输简单等同于 JSON.stringify 的所有限制。

拿到句柄不代表它可以永远使用。页面导航或对象所在环境变化后，应按实际生命周期重新获取适用引用，不能把上一次文档的对象当成下一页同名对象。本文不提供所有失效场景的异常列表，也没有运行句柄用例；工程上应让引用的取得、使用与清理贴近同一项操作，减少身份混淆。

evaluate 等待了 Promise，业务就准备好了吗？

不一定。evaluate 会等待回调返回的 Promise 完成，但那个 Promise 代表什么由回调决定。若回调只等待一次 fetch 返回，页面随后是否完成渲染、数据是否持久化、异步任务是否成功，仍是另外的问题。等待能力不是业务终态定义；应该给真正要验证的结果配置对应断言。

前面的价格示例也是一次快照。普通值断言不会因为网页后来变化就自动重新执行 evaluate。若价格在加载后异步形成，应按可观察状态使用适当的重试断言或轮询，而不是对已经保存的 observation 等更久。本站点击与业务结果等待解释这一点；本题先解决的是数据怎样越过环境边界，之后才是何时读。

反例是为消除 expected 未定义，把预期值改成从同一个 DOM 属性再读取一次。这样两个值总是一致，却丢掉独立预期。另一种反例是把缺失元素直接回传为成功默认值，让测试绕过原本要检查的渲染。正确的失败路径应让元素不存在、格式不符和价格错误分别可见，而非压成一个永远真或难以解释的布尔值。

可以把观察结果也做成明确对照：元素存在、raw 为字符串800且符合格式，才进入预期价格比较；元素存在但没有属性时，raw 为 null，说明配置不完整；元素根本不存在时，示例的可选链使 raw 为 undefined，应保留 present 为 false 的解释。若 raw 为900，问题是数值不符，而不是定位失败。这些是假设返回状态，未在浏览器运行。按字段保留差异能让失败指向缺失、格式或业务值，避免每次都先调整等待。

待执行验证可分别安排外部变量未传的负例、对象参数正确传入的路径、价格属性缺失与错误数值，以及异步更新迟到的情况。保存安装版本、回调输入、精简观测和断言结果，不保存敏感页面数据。本文没有运行浏览器，不报告通过率。先确认输入来自哪里、代码在哪执行、返回了什么，再选择等待策略；这些问题不能由一个更长超时共同回答。
