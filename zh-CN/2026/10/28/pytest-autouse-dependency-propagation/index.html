没请求数据库 fixture，测试为何还是连接了数据库

追踪自动 fixture 的普通依赖，使用类内与类外对照解释适用范围，并区分可见性、寿命与实际业务状态。

正文

核心要点

  • 自动 fixture 会为适用测试请求普通依赖。
  • 依赖不会因此变成所有上下文的全局自动 fixture。
  • 请求计划、业务状态与资源隔离需分别验证。

一个自动应用的登录 fixture 若依赖数据库 fixture，能看到它的测试也会请求这条依赖链。数据库 fixture 没写 autouse，并不意味着只会被测试参数直接触发。排查意外连接时，应从适用的自动 fixture 追依赖，而不是只搜索测试函数的参数。

普通依赖可以被自动请求带进来

pytest 的 fixture 参考文档说明，自动 fixture 请求的普通依赖，对它适用的测试也会有效地成为自动请求。本篇核对的 9.0.2 官方原文同时强调，这种影响不会自动扩展到所有能引用普通依赖的上下文。这里没有运行 pytest，也没有建立数据库连接。

假设数据库准备函数创建一个教学替身，再由自动登录 fixture 请求它。为了让触发链可见，下面仅向列表写入标记；db 名称不代表真实数据库客户端。代码未执行，预期依据文档推导。

import pytest

@pytest.fixture
def trace():
    return []

@pytest.fixture
def db(trace):
    trace.append('db')
    return object()

class TestSignedIn:
    @pytest.fixture(autouse=True)
    def login(self, db, trace):
        trace.append('login')

    def test_page(self, trace):
        assert trace == ['db', 'login']

class TestPublic:
    def test_page(self, trace):
        assert trace == []

在第一个类，测试没列 db 或 login，仍可通过自动 login 的依赖请求 db。第二个类能引用模块级 db，但看不到另一个类内部的 login，因此不因那条自动链请求 db。这里比较的是谁适用自动请求，不是把 db 的装饰器偷偷改成了全局 autouse。

替身列表只能说明请求关系，不能验证真实登录成功或数据库状态正确。实际项目还要在被测入口断言身份、数据和资源关闭行为。不要看到两个标记就把外部依赖验收写成通过，也不要因为外部连接失败就假定自动链本身一定错了；某些集成测试本来就需要它。

谁看得到，与资源活多久，不是一件事

fixture 的可见范围决定测试能请求哪些定义，scope 决定实例缓存与清理的边界。类中定义的自动登录，与把模块级连接设为较大 scope，是不同决定。扩大资源寿命不会自行解释为什么一个公开页面测试开始请求登录资源；应先画出请求边，再讨论复用成本。

如果将 login 从类内移到全局 conftest，更多测试可能进入它的适用上下文。这是实质行为变化，不只是整理文件。移动前列出受影响目录与测试，确认公开路径是否仍需保持没有登录前提；否则一个看似便捷的全局准备会让测试永远处于已登录状态，掩盖匿名访问问题。

反过来，把 db 改名或把定义挪到文件末尾，也不会切断 login 对它的依赖。触发关系应通过显式参数和适用位置调整，不能依赖书写顺序。官方文档把执行顺序归于 scope、依赖与 autouse 等关系，而不是函数名排列或源码先后。

若有两个 fixture 都会修改状态，又没有明确依赖关系，不应通过重排定义去“固定”偶然顺序。需要先定义谁必须先完成，再选择能表达该关系的结构。依赖图有意义的边，比一个碰巧在本机通过的打印顺序更能说明合同。

去掉 autouse 后，显式请求还会生效吗？

会，fixture 仍可按可见性被显式请求；改变的是原来不用列出的自动进入方式。若只希望少量集成测试登录，可以让那些测试明确请求 login，或者使用项目认可的显式准备形式。但修改后应找出全部确实需要身份的入口，避免只修当前失败用例，留下未准备状态的测试。

显式请求也不等于可以绕开普通依赖。login 需要 db，测试请求 login 时仍要满足其依赖链。若希望某类测试完全不连接外部系统，应为它提供符合该测试目标的独立入口或替身，并清楚声明验证范围。仅在 db 中返回空对象让报错消失，可能破坏 login 本来依赖的能力。

还有一种不同问题：数据库资源按会话共享，但测试之间保留了可变身份。那是状态隔离，不能仅靠去掉 autouse 修复。本站fixture 作用域与隔离讨论这项寿命责任。本题先解释为什么请求被触发，之后还要另查每次测试获得的初始状态。

用请求计划验证，别只统计运行时间

官方原文推荐用 pytest --setup-plan 查看给定测试的 fixture 计划。可先对类内测试和类外测试分别运行，再对两者成组运行，比较 db 与 login 是否出现在预期位置。这个命令在本篇没有执行，输出也未伪造；真实验证需保存 pytest 版本、项目插件与所选测试节点。

计划用于查看准备关系，不会替代真正执行后的业务断言。自动登录若没有完成身份切换，计划里出现 login 也不能证明页面以正确用户运行。可以在隔离环境记录实际获取、使用和清理，再核对匿名测试确实不携带身份。这项验证应触及真实入口，不能只打印 fixture 名称。

失败路径也应在适合的环境观察。若 db 准备失败，依赖它的登录测试不能假装继续；如果不相关的类外测试仍被拉入数据库准备，就应再次检查是否还有更外层的自动 fixture 或插件引入请求。请求来源可能不止一条，删除眼前的一条边不保证所有外部依赖都已消失。

例如类外公开测试虽看不到 login，却又由模块级自动 health_check 请求同一个 db。移走类内 login 后，数据库仍会被准备，这并不推翻类可见性的规则，而是存在第二条可见请求链。排查时可把每个目标测试的请求来源分别列出，先断言哪些链必须保留，再删除误用的边。不要为了让“公开页不连接数据库”通过，就直接禁用共享 db 的全部用途；确实需要健康检查的集成用例可能因此失去验证。若要求某组测试完全无外部访问，应另用可观察的访问记录验证，而不只是看不到某一个 fixture 名称。名称检查能帮定位，但外部调用还可能来自导入或插件初始化，需要与产品入口和有效配置一起核对。

待执行用例覆盖类内自动链、类外无链、类外显式请求普通依赖、移动自动定义后的影响，以及依赖准备失败。分别断言请求集合、业务状态和资源清理，不用耗时变短替代正确性。先找到那条自动请求边，才能判断它是合理测试前提，还是遮住了本应独立的场景。
