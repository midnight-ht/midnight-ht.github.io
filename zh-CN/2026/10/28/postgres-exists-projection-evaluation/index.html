EXISTS 里的 SELECT 为什么不适合放审计副作用

区分存在性结果与投影执行，给出 INTERSECT 例外，并设计明确的审计尝试、结果和重试责任。

正文

核心要点

  • EXISTS 通常只关心有无行，不承诺投影副作用。
  • INTERSECT 等集合运算可能让投影内容影响结果。
  • 审计应显式定义尝试、完成、失败与重试记录。

把记录审计的函数写进 EXISTS 的 SELECT 列，并不能保证每次检查都会写一条日志。存在性判断只需要确认有没有行，投影表达式通常不是它的结果合同。需要可靠记录判断过程时，应设计显式的记录动作，不能借用查询投影的副作用。

有一行，与计算那一列，是不同要求

PostgreSQL 18 的 EXISTS 文档说明，子查询返回至少一行时结果为真，没有行时为假。输出列表通常不决定真假，常见惯例是 SELECT 1。文档还特别警告，子查询通常只执行到足以确认存在，不宜放置依赖执行次数的副作用。本篇按第十八版讨论语义，没有执行数据库探针。

假设业务要判断某订单是否存在可用凭证，开发者把一个审计函数放进子查询的投影，希望检查时顺便记录一次访问。函数名是教学假设，不是本站已有数据库函数。下面的写法把两个要求绑在了一起：是否存在符合条件的凭证，以及是否完成一条审计记录。

SELECT EXISTS (
  SELECT write_audit_note(v.id)
  FROM vouchers AS v
  WHERE v.order_id = 42 AND v.active
);

这段代码未运行。它的问题不是审计函数写得不够快，而是调用方依赖了 EXISTS 没有提供的执行承诺。即使某次观察到函数被调用，也不能推出所有计划、所有数据和所有执行分支都同样调用。把审计计数写成“一次查询必有一条”验收，会把一个偶然轨迹误当成接口保证。

更清楚的存在性表达可以用常量投影，把关联条件留在筛选中。常量的作用是让读者看出这里只问有没有行，不是对引擎指定某种性能技巧。把 SELECT id 改成 SELECT 1，不能未经测量就声称扫描更少、延迟降低，更不能修正遗漏的关联条件。

SELECT EXISTS (
  SELECT 1
  FROM vouchers AS v
  WHERE v.order_id = 42 AND v.active
);

若忘记订单关联，只检查任意可用凭证是否存在，返回值可能在别的订单有凭证时变成真。投影写成一，查询仍然回答了错误问题。评审应先复述外层对象、关联键和有效条件，再考虑表达是否简洁；约定式写法不是业务正确性的证明。

可以无条件把投影换成一吗？

不能。官方文档明确列出使用 INTERSECT 的子查询可能是例外。集合运算会利用输出值决定哪些行相交，因此输出内容可能影响是否还有结果。不要把“通常无关结果”删成“永远无关结果”。

下面是未执行的最小推演，不包含真实业务表。第一条两侧输出不同值，没有公共行；第二条把两侧都改成一，有公共行，外部 EXISTS 的真假也随之改变。

SELECT EXISTS (SELECT 1 INTERSECT SELECT 2);
SELECT EXISTS (SELECT 1 INTERSECT SELECT 1);

这个例外提供一个具体评审动作：替换投影前，先检查子查询是否仅仅筛选行，还是内部还要按值进行集合运算。若是后一种，需从完整运算推导结果，不能套用普通关联 EXISTS 的局部规则。这里没有承诺所有其他复杂子查询都能逐字替换；应先保证原结构的含义，再考虑统一格式。

也不要用投影“无关结果”推断筛选表达式都不执行。关联与筛选决定哪些行存在，它们与输出列承担不同职责。本题拒绝的是某个不受保证的副作用设计，不是鼓励在任何 SQL 位置随意放副作用再猜测执行顺序。对确实允许的表达式，仍需核对函数自身的合同和完整查询语义。

需要记录每次判断，应该在哪里写？

把记录作为显式业务步骤，并先定义“每次”指什么。若要记录成功完成的一次判断，可以让应用在得到判断结果后，以明确字段写入请求标识、对象标识和结果；若要求判断与记录共同成功，则要设计适合该要求的事务与失败路径。这是应用设计建议，不是本文已经验证的审计实现。

假设判断为真后记录失败，接口该返回失败，还是返回结果并另行补记？假设调用方超时重试，同一业务请求能否生成两条日志？这两项选择会决定幂等键和恢复动作，不能由投影函数恰好执行了几次来决定。审计如果包含外部服务，还需另外处理数据库事务与外部写入不能天然一起提交的边界。

也可能要求记录“尝试”，包括查询本身失败的请求。只在成功拿到结果后写记录便不够，需要在更外层区分开始、结果、错误和记录失败。开始记录存在，不证明判断完成；记录里写了结果，也要能关联到当次输入，防止下一次重试覆盖了上一回的失败。先选择记录语义，再选择存储方案。

验证应分开准备：无匹配、单匹配、多匹配、错误关联对象、记录步骤失败和请求重试。存在性部分断言真假及对象归属，记录部分断言明确约定的次数和状态。不能用“日志多了”作为存在性查询正确的唯一断言，也不能让一条真实匹配掩盖另一订单的错误关联。

审计记录还应避免一个数量陷阱。假设请求甲第一次查到真，但响应传回前连接中断，调用方重试后再次查到真。若合同记录每次尝试，两条尝试记录可以合理；若合同记录每个逻辑请求的一次最终决定，就需要把同一请求身份与不同尝试身份分开。只断言日志总数等于二，无法知道是否重复创建了一个本应唯一的决定。待执行断言可以检查同一逻辑请求有两次尝试、至多一个按合同接纳的最终结果，并保留第一次响应未知的状态。若重试期间凭证可用性改变，还要决定是重新评估，还是返回先前已持久化的决定；后者需要真实保存结果，不能仅保存请求编号。本例是设计推演，未发生真实断线。

关于观察计划与执行结果的区别，可读本站执行计划证据。本篇没有运行上述查询，也没有实现审计事务；交付检查应保留输入、语义预期与实际执行证据，分别证明存在判断和记录动作兑现了各自承诺。
