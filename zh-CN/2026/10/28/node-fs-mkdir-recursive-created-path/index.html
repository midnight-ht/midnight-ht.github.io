mkdir recursive 返回路径，为什么不是最深目录

分开 mkdir 的目标与首次新建路径，解释 undefined 的正常分支，并区分目录准备与唯一工作区。

正文

核心要点

  • 递归 mkdir 返回首次新建目录，不是目标路径回显。
  • 已有目录时 undefined 不等于操作失败。
  • 准备共享路径与分配唯一工作区是不同要求。

请求创建 /tmp/demo/a/b，recursive 的返回值可能是最先新建的 /tmp/demo。把它当成目标目录继续写文件，就可能把输出放错层级。递归 mkdir 返回的创建信息，与调用方原先选择的目标路径，应分别保存。

返回的是创建信息，不是目标路径回显

Node.js v24.22.1 文件系统文档说明，fsPromises.mkdir 成功时，非递归模式得到 undefined；递归模式得到首个创建的目录路径。若没有创建任何目录，例如目标原本存在，也可能得到 undefined。回调接口文档进一步明确了这种没有新建路径的情况。这里按二十四版语义写教学示例，没有运行文件操作。

假设 /tmp 已存在，demo、a、b 都不存在。创建目标时，首先需要建立 demo，因此返回值可能指向 demo，而最终请求的目录仍是 b。若 demo 已存在而 a 不存在，首个新建层又会变为 a。返回信息依赖本次开始时的目录状态，不能作为目标的稳定别名。

下面代码未执行，目录名是演示用的假设。target 决定报告去哪里；firstCreated 只用于表达这次准备是否创建了某层。即使第二次执行没有新建目录，报告目标也不应发生改变。

import path from 'node:path';
import { mkdir, writeFile } from 'node:fs/promises';

const target = path.resolve('demo-output', 'daily', 'reports');
const firstCreated = await mkdir(target, { recursive: true });
await writeFile(path.join(target, 'report.txt'), 'example\n');
console.log({ target, firstCreated });

这段完整成功路径仍没有提供业务文件发布协议。重复调用会写同名文件，示例不保证保留旧内容、独占写入或跨崩溃耐久性。代码展示的是应把哪个路径传给后续操作，不能把一次 await 正常结束扩写成导出交付已经完成。

一个常见反例是把 mkdir 的返回值赋给 outputDir，再传给 path.join。新建多层目录时可能写到较浅层；目标已存在时，返回 undefined 又可能使后续路径调用失败。同一段代码于是呈现“首次能跑、再次失败”，而实际文件落点在首次就可能已经错误。先核对变量承担的身份，比增加重试次数更有用。

返回 undefined，应不应该抛出失败？

不应仅凭这个值抛失败。对 Promise 形式，成功完成与拒绝才是操作结果的基本分界；返回路径说明是否以及首先在哪层发生了创建。递归模式允许已存在的目标目录，因此“不需要新建”可以是正常结果。把布尔转换当成成功判断，会破坏重复准备的合理用途。

这不表示应该吞掉所有错误。如果目标位置是普通文件、某个父路径不能作为目录、权限不够或设备空间不足，真实错误仍应保留。不要捕获后统一返回 target，让调用方误以为目录已经准备好；后续写入可能以更难理解的方式失败，原始原因却被丢了。

也不必先调用存在检查，再决定是否 mkdir。事前检查只是某一时点的观察，不能保证调用时目录状态未变。若需求就是确保目录可用，可以直接使用相应创建操作并处理它的结果；但这也不能保证稍后的写入一定成功，目录可能被改动，写入还有自己的权限与资源条件。

日志应区分目标目录、首个新建目录、是否未发生创建，以及创建失败。若日志只写“created undefined”，读者既不知道目标是什么，也容易把合法复用理解成错误。建议保留原始错误类型与阶段，避免一个笼统的“生成失败”覆盖路径准备、内容生成和最终写入三个位置。

mkdir 成功，能证明拥有独占工作区吗？

不能。两个任务可以对同一目录使用 recursive mkdir，并都成功。这种复用满足“路径存在”的准备要求，不会为每个任务分配独立名字。若两者随后写相同 report.txt，隔离问题仍然存在，不能从创建成功推导“这个目录只属于我”。

同版 mkdtemp 文档提供创建唯一临时目录的接口。需要临时工作区时，可以按其前缀规则考虑该接口，并把返回的实际目录作为任务资源身份。它与 mkdir 的返回值含义不同：不要因两个名字相近，就把“首个新建父层”与“新分配的临时目录”混成一种结果。

唯一目录也需要所有权和清理策略。任务失败后该删除哪些路径、保留哪些诊断产物，应从实际分配记录判断，不能拿一个可能指向共享父层的 firstCreated 去递归删除。特别是多个任务共用父目录时，错误清理范围可能影响其他任务。本文没有提供删除脚本或生产清理实现。

如果工作目录必须固定，例如多任务共同生成一个发布目标，则不一定应改成临时目录；可能需要串行发布或明确的合并协议。这是另一种共享写入合同。不要为了消除碰撞就随意改变产品要求的目标位置，也不要为了保留固定位置就假定创建操作已经提供锁。

待执行验收应在隔离目录中覆盖全新多层、部分父层已有、目标完全已有、目标为普通文件与创建失败。分别断言最终目标身份、实际文件落点和返回信息，至少重复一次准备过程。并发隔离另测两个任务的名字与产物归属，不把两个 fulfilled 当作隔离通过。

准备收据可以保留三种具体前置状态：所有子层缺失、只有末级缺失、目标已经存在。三次请求的 target 可以完全一样，firstCreated 却分别位于不同层或不存在。这说明它是一次操作的变化信息，而不是资源的长期身份。验收时先保存目标绝对路径，再检查文件确实位于该目录下，不能用“返回了某个目录”代替实际落点。若运行器在不同工作目录启动，相对 target 的解析也会变化，应在准备前选定基准并记录；首个创建路径不能补回原先未明确的基准。生成报告的失败回执则要带上稳定 target 与失败阶段，让恢复者知道该检查目录准备、内容生成还是最终写入，而不是根据一个有时为空的返回字段猜测。

本站rename 与文件交付继续讨论写好之后如何发布。本篇没有创建目录或写文件；先让目标变量保持稳定，再为创建信息选择准确名称，可以在交付流程开始以前消除这一层路径误用。
