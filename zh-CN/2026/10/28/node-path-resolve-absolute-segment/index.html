path.resolve(base, input) 为什么会丢掉 base

按 Node.js v24 的右向左规则解释绝对参数与工作目录，并区分路径形式、词法归属和文件系统授权。

正文

核心要点

  • resolve 从右向左处理，遇到足够的绝对路径即停止。
  • isAbsolute 与字符串前缀不证明允许目录归属。
  • 词法检查不冻结符号链接与文件系统状态。

把 /srv/uploads 和 /tmp/report.csv 作为下方 POSIX 调用的两个参数，结果以右侧绝对路径为依据。传入一个基目录，不等于约束后续参数只能留在这个目录里。该方法负责生成绝对路径，允许访问哪里仍是调用方的合同。

参数从右向左，不是一直往基目录后拼

Node.js v24.22.1 的 路径解析文档说明，参数从右往左处理，直到形成绝对路径。若所有参数处理后仍没有绝对路径，才使用当前工作目录。本篇固定讨论所读的二十四版本文档，并用 posix 例子避免把当前操作系统的路径风格藏在推导中。

下面是未执行的教学代码。第一条的最右参数已经绝对，不需要再依赖左侧的 uploads；第二条右侧是相对路径，需要左侧基准，得到 uploads 下的报告。变量名 base 没有改变解析规则。

import path from 'node:path';
path.posix.resolve('/srv/uploads', '/tmp/report.csv');
path.posix.resolve('/srv/uploads', 'report.csv');

按文档推演，结果分别为 /tmp/report.csv 与 /srv/uploads/report.csv。这里没有创建文件，也没有向任何真实目录写入。对一个允许用户提交路径的接口而言，若产品只准写 uploads，第一条结果已经违反接口目标；但 resolve 本身仍完成了其正式任务。

相对参数也不天然受限。给基目录加上 ../private/report.csv，规范化后可能离开 uploads。只拒绝以斜杠开头的输入，最多堵住一类形式，不能证明相对输入都安全。相反，如果调用方本来允许指定任意绝对输出路径，右侧覆盖基准可能正是需要的行为，不能为了统一习惯一律拒绝。

也不应把同样描述套给 join。join 和 resolve 是不同方法，不能因为都接受多个字符串，就推导它们遇到绝对参数时有相同算法。修复前先确定想要哪一种路径合同，再读相应接口；更换方法名而不核对输入和输出，会把一个误解换成另一个误解。

先决定接口接收文件名，还是接收路径

若上传产品只需要调用方给出一个展示文件名，可以把实际存储位置交给服务端生成，输入中不接受目录结构。展示名称、存储标识和磁盘目标分开，能减少调用方表达不必要路径的机会。具体允许字符、扩展名与重复名称规则仍要按产品决定，不是简单去掉斜杠就算完成。

若接口确实要接收允许根目录内的子路径，可以讨论词法归属检查。例如得到 candidate 后，用同一平台风格的 relative 计算它相对 base 的表示，检查是否以一个完整的上级目录段离开，或仍为绝对路径。这只是字符串层的检查思路，本文没有提供可直接部署的访问控制函数。

不能用 startsWith(base) 代替路径分段。uploads-backup 与 uploads 可以共享字符串前缀，却不是同一个目录树的子目录。分隔符、大小写、Windows 驱动器和网络共享还会影响不同平台的解释。针对 POSIX 写出的推导，不能作为 Windows 已验证的安全证明。

同一文档中的 isAbsolute明确说，它只判断字面路径是不是绝对形式，不适合用来缓解路径穿越。为真不证明属于允许区域，为假也不证明不会通过上级段离开。调用方需要的是归属和权限，返回值回答的却是形式。

candidate 恰好等于 base，可以允许吗？

要看操作目标。若接口是“写入一个文件”，空相对路径可能意味着目标就是存储根本身，通常还需要单独拒绝。若接口是“列出允许根目录”，相同位置可能完全合法。把空字符串一律当失败或一律当合法，会混淆文件操作与目录操作的合同。

这个问题也涉及空输入。该解析方法会忽略零长度参数；若相对路径没有提供足够绝对基准，它可能落回工作目录。接口不应把缺失文件名静默转换为另一个可写目录。先验证必填条件，再进行所需解析，错误信息应区分未提供名称、形式非法和目标不允许。

路径还可能来自文件 URL。本站file URL 与本地路径转换解释了表示转换。转换得到一个语法正确的原生路径，仍没有完成本篇的归属检查；同样，归属检查也不能替 URL 接收边界选择正确的解码规则。

词法检查之后，文件系统仍可能改变目标

假设 uploads 内有一个符号链接，指向目录外。路径字符串看起来留在根内，文件系统实际访问却可能跟随链接到别处。真实路径检查可以帮助核对已存在对象，但待创建文件、父目录权限和检查后发生的目录变更，都需要更完整的访问设计。字符串计算不会锁住文件系统状态。

如果攻击者或其他进程能在检查与打开之间替换目录，先检查再打开可能出现竞态。应按部署系统选择合适的权限隔离、打开方式和可信目录所有权，并验证真实访问对象。这里指出证明边界，不把一段 relative 判断包装成完整目录沙箱，也不提供未经验证的符号链接防护实现。

工作目录对照应有两组输入。给定固定绝对基目录与相对文件名，改变进程启动目录不应改变本例推导出的目标；只提供相对片段时，工作目录才会进入解析，目标随启动位置变化。这可以区分“基准没传进来”和“右侧绝对参数取代了基准”两个错误来源。测试不应在报错后悄悄切换工作目录重试，否则可能读到另一份同名文件并把错误隐藏。可以在两个隔离目录放不同标记，记录实际读取哪份；只核对 basename 都是 report.csv 没有证明身份。若路径随后交给另一进程，还应确认传递的是约定的绝对表示，或明确把工作目录一起纳入协议，避免生产者与消费者各自补上不同基准。

待执行验收可保存输入、平台风格、工作目录、解析输出与实际访问对象，覆盖普通文件名、右侧绝对路径、上级目录段、前缀相似目录、等于根目录、空输入和符号链接。合法输入要读到预期标记文件，非法输入要在写入前拒绝。跨平台部分应在对应系统执行；本篇没有运行这些代码或访问测试。
