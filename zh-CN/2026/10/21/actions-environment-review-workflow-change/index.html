把发布保护分成环境、工作流和输入三道检查

GitHub Environment审批放行的是部署job；工作流改动和制品来源需要分别审查，才能确认实际发布内容。

正文

核心要点

  • 环境必需审批者中只有一人批准就能放行该job，具体设置需核对。
  • 工作流目录的所有者审查与环境审批承担不同职责。
  • 批准前绑定commit SHA、run ID、制品摘要和环境目标。

生产环境的 GitHub Actions job 停在“等待审批”，看起来发布已经有一道闸门。可同一个提交还改了 .github/workflows/deploy.yml：原本下载构建流水线产出的制品，现在改为下载另一个运行编号的制品。审批人若只看环境名称和绿色检查，可能放行的已不是自己理解的发布内容。要守住这个边界，需要分别核对环境、工作流文件和发布输入。

环境审批拦住的是 job 启动

GitHub 环境管理文档规定，引用 environment 的 job 必须遵循该环境的保护规则；在规则放行前，环境秘密不会交给这个 job。可以配置必需审批者、分支或标签限制等，但可用功能受仓库可见性和计划约束，实际配置必须在目标仓库检查。必需审批者可以列多个候选，官方规则只要求其中一位批准该 job；若组织要求两人复核，不能把“列了两个人”误读成“两票都必需”。防止自我审批也是需要单独启用的选项，不能靠口头约定代替。

这道闸门回答“这次 job 是否获准进入指定环境”，不自动回答“工作流文件是谁改的”“脚本实际发布了哪个制品”或“部署目标是否仍是约定账户”。批准者看到的是一个待审批运行；在这一刻给出的批准，并不等于对该提交中 .github/workflows 的变更进行过代码审查。环境保护规则也不能追溯修复 job 启动前已经运行的其他高权限步骤。若构建、签名或制品选择在另一个 job 中完成，应把那个 job 的输入与权限单独纳入评审。

审批时尤其要记录运行的提交 SHA、触发事件、目标 ref、所引用的 environment 名称和 job 使用的工作流修订。相同的“生产发布”显示名称可以指向不同 YAML 内容；相同制品名称也可能来自不同运行。若工作流允许 workflow_dispatch 输入选择制品或目标，输入值同样是待确认的发布定义的一部分。把这些字段固定在审批记录里，后续才有办法回答究竟批准了哪个版本，而不只是“某天有人点过 Approve”。

工作流文件与制品分别有自己的边界

GitHub 的安全使用文档建议用 CODEOWNERS 保护 .github/workflows 目录。这个建议只有和要求代码所有者审查的分支保护或规则集一起生效，才能形成实际阻断：未经指定维护者批准的工作流改动不能合并。还要保护 CODEOWNERS 文件本身，避免提交者在同一改动里移除所有权规则。评审不应只看 YAML 语法可解析；应逐项比较触发器、permissions、第三方 action 来源、制品下载位置、部署命令、环境名及任何可写目标。

制品是另一道边界。即使 deploy.yml 没有改，发布 job 若通过可变的名称、任意 run ID 或手工输入拿制品，也可能发布与预期提交不一致的内容。设计评审可以要求制品与目标提交 SHA、构建运行 ID、存储位置及签名或校验值建立可核对的关系；是否使用签名取决于现有供应链能力，但“文件名叫 release.zip”本身不是来源证明。审批者需要看到实际解析后的标识，而不是模板表达式的字面文本。若下载来自另一个仓库或工作流，还要核对该来源的权限和保留策略。

这些控制点的责任不同：环境规则决定 job 什么时候能继续，代码审查约束工作流定义如何变化，制品核验约束被部署的字节从哪里来。把三个动作都叫“审批”会掩盖空隙。并发控制也只决定运行如何排队或互斥；本站的部署并发文章讨论的是这个执行顺序问题，它不会替代本篇的变更与输入核对。

用一次假设发布检验三道检查

以下案例是审查演算，没有实际运行工作流或发布生产环境。设主分支的提交 abc123 改动了服务代码，构建 job 产生摘要为 sha256:AAA 的制品，准备通过 deploy.yml 发布到 production。预期路径是：受保护分支要求工作流目录的代码所有者审查；构建记录把 abc123、运行 ID 417 与制品摘要绑定；发布 job 明确下载运行 417 的该摘要；环境必需审批者在看到这些值后批准，随后 job 才能取到环境秘密并执行部署。预期结果是生产环境收到 abc123 对应的字节，审计记录能同时指出文件审查、制品身份和 job 放行的证据。这个结果仍是设计预期，不能写成已经观察到的部署回执。

现在让同一个提交把下载来源改成运行 ID 402，其制品摘要为 sha256:BBB，但 job 名和环境名仍叫“production deploy”。环境规则可能依旧正常等待并接受一位审批者；它不会自动判断 402 是否属于批准的提交。若工作流目录没有受保护的所有者审查，变化可能在合并前无人发现；即使文件审查挡住这次改动，若下载 ID 仍可由手工输入任意指定，输入路径还留着缺口。对这次审批的正确处理是停下，查清 402 的来源和提交关系，必要时拒绝运行并修正工作流或输入约束，而不是因为环境审批界面可点就先放行。

还有一个容易混淆的情形：团队把所有候选审批者列在环境中，以为每次必须有两人同意。官方规则只需其中一人放行，因此需要“双人复核”的组织必须另设确实执行两人审查的流程，并验证实际设置；不能在文章或审计表里假定 GitHub 原生环境审批提供了多票门槛。同样，防止自审、管理员绕过、分支限制各有独立设置。不同计划和仓库可见性下可用性也可能不同，设计图上的控制不等于目标仓库已经开启。

审核运行而不是审核一个按钮

落地时先在测试仓库或非生产环境查看当前计划允许哪些保护规则，保存实际环境设置、分支规则和 CODEOWNERS 匹配结果。用一条只改工作流制品来源的测试 PR，验证没有所有者审查时是否被阻断；再用受限环境的测试运行，确认待审批前环境秘密不可用，批准后是否只放行预期 job。最后记录 run ID、commit SHA、制品摘要和部署目标，比较它们是否与审批时显示的值一致。测试应使用无生产凭据的制品，避免把验证本身变成一次危险部署。

这篇文章讨论的是批准一次部署时的信任范围，不把 environment 当成所有供应链检查的总代名词。若当前工作流不从外部选择制品，最先要守的是工作流文件与权限；若部署包经过多级流水线转交，制品身份可能是主要风险。无论哪种情况，审批者应能回答“哪个提交定义了执行步骤、哪个运行产生了字节、我放行的是哪个环境 job”。答不上来时，暂停批准并补齐证据，比事后拿一张绿色审批截图推测发布内容可靠得多。
