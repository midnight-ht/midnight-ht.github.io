WebAuthn的rpIdHash通过，为什么还要核对origin？

父域RP ID可覆盖兄弟子域；rpIdHash不标识具体网页，服务端仍须核对clientDataJSON.origin的允许列表。

正文

核心要点

  • 父域RP ID允许符合后缀规则的子域调用凭据，不等于授权每个子域登录。
  • 签名和rpIdHash通过仍需服务端核对完整origin与挑战。
  • 按实际登录页设置精确origin允许列表，并分别测试兄弟子域与外域拒绝路径。

登录页放在 https://auth.example.test，产品为了让多个子域复用同一通行密钥，把 WebAuthn RP ID 设为 example.test。有人看到服务端已核对 rpIdHash、挑战和签名，就删掉了 clientDataJSON.origin 校验：既然凭据属于这个父域，发起它的网页也该可信吧？这个推论混淆了凭据作用范围与网页来源授权。若同一父域下另有独立管理的 evil.example.test，它也可能满足浏览器对 RP ID 的域名关系检查，却不应该成为登录页。

父域 RP ID 扩大的是凭据作用范围

W3C WebAuthn Level 2 规范说明，RP ID 默认取调用页面 origin 的有效域名；调用方可以改用该有效域名的可注册域后缀或相同域名。规范同时要求 HTTPS 来源，端口不限制。对于认证子域，选择父域作为 RP ID 符合“父域后缀”的关系；假设恶意兄弟子域由另一方控制，它与该父域 也有相同关系。浏览器在调用 navigator.credentials.get() 时可根据这条关系准许请求继续，并不表示服务端已经批准这张网页参与账户登录。

RP ID 决定认证器使用哪组凭据。认证器返回的 authenticatorData 含 rpIdHash，服务端应核对它是预期 RP ID 的 SHA-256 值。这个哈希对上述两个子域都是父域 RP ID 的哈希，不能表达网页是认证子域还是恶意兄弟子域。若业务根本不需要跨子域共享凭据，使用更窄的认证子域作为 RP ID 可以缩小浏览器准许的来源范围；一旦已为父域注册大量凭据，迁移 RP ID 又涉及凭据重新注册和用户体验，不能仅改服务端配置就假定旧凭据可用。

这里还有两种不同的“来源”。RP ID 是域名作用域，不包括协议和端口；clientDataJSON.origin 是发起 WebAuthn 调用的网页 origin，包含协议、主机及适用端口。服务端若只比较 rpIdHash，等于把同父域下每个符合条件的页面都留给后续验证；若将 origin 写成覆盖父域下所有子域的宽泛通配规则，仍可能把不受控的兄弟子域一起放入。应在服务端维护明确的允许来源，例如只允许认证页的完整 HTTPS origin，需要第二个登录页时再独立审查并添加完整 origin，而不是根据父域自动放行。

签名保护了 origin 字段，却不替你决定是否允许

认证断言的验证不是只验一个哈希。服务端先要确认待验证的是 webauthn.get，挑战与当前待完成的认证仪式一致，凭据属于要认证的用户，然后读取 clientDataJSON.origin 并按预期 RP 来源核对；还要核对 rpIdHash、用户在场或所需用户验证标志，并用已登记公钥验证签名。WebAuthn Level 2 的认证验证步骤把 origin 检查与 rpIdHash 检查列成不同步骤。注册阶段也有相应的来源与 RP ID 检查，不能只在登录时补这道门。

签名覆盖 authenticatorData 与 clientDataJSON 的哈希，因此攻击者不能在取得合法断言后简单把其中的 origin 字符串改掉而仍让签名通过。这恰恰说明服务端应该检查那个未被篡改的来源值：浏览器如实记录恶意兄弟子域的完整 HTTPS origin，签名也可以有效，但来源不在业务允许列表。挑战用于把断言绑定到一次认证尝试并阻止旧断言直接重放；如果挑战是服务端为攻击者控制的登录会话新发的，挑战检查本身不会说明通行密钥操作发生在哪个网页。签名、挑战、RP ID、origin分别回答真实性、新鲜度、凭据作用域和发起来源，缺一项就不能用其他项替代。

设一个未执行的假设流程。攻击者控制恶意兄弟子域页面，但不控制认证子域或认证器私钥。他知道受害者账户标识，从服务端取得一笔为自己登录会话发出的新挑战，并把挑战与父域 RP ID 参数带到恶意兄弟子域。受害者若打开该页并主动完成通行密钥提示，浏览器可以针对父域 RP ID 生成断言；其 clientDataJSON.origin 如实是恶意兄弟子域的完整 HTTPS origin，rpIdHash 则仍是父域 RP ID 的哈希。攻击者把断言交回与那笔挑战对应的会话。若服务端核对挑战、哈希和签名却忽略 origin，这几个检查可能全部通过，导致错误的登录接受；若允许列表只含 认证页的完整 HTTPS origin，应在 origin 核对处拒绝。这里的受害者交互、挑战取得、会话对应都是前提，不是声称任意兄弟子域能无交互盗取私钥或自动登录。

再换一个反例：https://evil.other.test 不是该父域的子域。按 Level 2 的 RP ID 后缀规则，浏览器不应允许它直接以该父域作为 RP ID 发起该 WebAuthn 操作。这个浏览器侧拒绝与前一例服务端拒绝发生在不同边界；不能因为外域页面被浏览器拦住，就推断所有兄弟子域也被拦住。反过来，即使 RP ID 改窄到认证子域，服务端仍应按规范检查 origin，避免配置漂移或错误客户端数据被误接受。

如何选择 RP ID 并验证允许列表

选择时先列出实际承载登录仪式的页面。如果只在认证子域登录，窄 RP ID 简化作用域；如果确需第二业务子域和认证中心共用凭据，可考虑父域 RP ID，但需盘点谁能创建或控制父域下的其他子域、哪些 origin 才被允许发起认证，以及不同环境是否误共用同一 RP ID。预发、测试和生产域名若交叉信任，允许列表也要跟部署配置一起审查。不要把“同站”Cookie 行为与 WebAuthn 来源校验混为一谈；站内SameSite 与 CSRF 边界讨论的是另一层浏览器策略。

实现上应把允许列表当作精确值集合，并先用可靠的 URL 解析方式规范化后比较，不能用主机名后缀匹配或任意字符串包含判断。前者可能接受不该接受的子域，后者还会混淆主机名和路径文字。若服务通过反向代理提供挑战，也不要直接把未经可信代理约束的 Host 或 X-Forwarded-Host 当作“期望 origin”；期望值应来自服务端受控配置。一次认证仪式选定了哪个 RP ID 和哪些可用 origin，要在挑战会话中保持一致，避免开始时按生产配置发挑战、验证时却按测试配置核对。多租户服务尤其需要按租户隔离这些配置，不能把一张全局父域白名单当成所有租户的登录授权。

一个可审的测试矩阵应分别覆盖：允许的认证子域在正确挑战、RP ID 与签名下通过；不允许的恶意兄弟子域在其他字段相同条件下因 origin 被拒；外域 evil.other.test 在浏览器调用阶段因 RP ID 关系不合被拒；错误挑战、错误 rpIdHash、错误签名各有独立拒绝结果。测试要记录服务端实际解析的完整 origin、预期 RP ID、挑战所属会话及拒绝原因，同时避免在公开日志里泄露可重放材料。本文未执行浏览器或认证器测试，结果需由目标实现的真实测试回执证明。

本文以 2021 年 4 月发布的 WebAuthn Level 2 推荐规范为依据。不能把其他版本的相关来源机制不加版本区分地套进这条后缀规则，也不能把 OAuth 回调地址或 CORS 响应头的配置经验当作 WebAuthn 认证验证步骤。最终需要守住的是两条独立判断：浏览器准许凭据在哪个 RP ID 下使用，服务端只批准哪些完整网页 origin 可以用这次断言登录账户。
