rename 成功后，配置文件真的交付了吗？

拆开临时文件替换的可见切换、文件与目录同步、跨设备失败及恢复收据，不把成功返回误作断电保证。

正文

核心要点

  • rename 成功说明路径操作完成，不单独证明文件内容和目录项已跨断电持久化。
  • 目标同目录临时文件、内容校验、文件同步、rename、目录同步是需按平台验证的分层流程。
  • 跨设备 EXDEV 与目录同步失败都应有可恢复的状态和准确收据。

构建程序先把 config.json.tmp 写好，再调用 fsPromises.rename(tmp, 'config.json')，Promise 正常结束，日志打印“交付完成”。使用者此时能读到新文件，值班同事却问：如果机器立刻断电，新名字与内容是否还在？这两个问题需要不同的证据。Node.js 文档只把 rename 成功描述为路径重命名成功；它没有因 Promise fulfilled 就承诺目录项与文件内容已经跨断电持久化。要设计交付流程，先拆开可见切换、同步请求与故障恢复。

以一个配置替换为例

假设目录内当前 config.json 的内容为 {"version":1}，目标是 {"version":2}。程序在目标同一目录创建唯一临时文件 config.json.tmp-42，写入完整字节，关闭或同步该文件，然后把临时路径重命名到 config.json。在适用的同一挂载文件系统语义下，Linux rename(2) 文档说已存在的目标会被原子替换，其他进程不应在切换瞬间看到目标路径消失。若写入未完整就提前 rename，读者可能看到截断的版本 2；rename 只能改变名字，不能替写入阶段验证内容。先解析 JSON、检查版本和校验和，再决定是否发布更稳妥。

从进程视角，await rename(tmp, target) 返回代表这次重命名操作成功。它是发布路径可见性的一个关键节点，但不等于“所有存储介质已经确认新目录项”。Node filehandle.sync() 文档写的是请求把打开文件的数据刷至存储设备，并明确实现受操作系统与设备影响。Linux fsync(2) 手册进一步指出：同步文件自身也不一定让所在目录的目录项落盘，目录还需要显式同步。这些原文形成的是平台内的操作边界；它们不能替没有执行的断电实验作担保，更不能直接推广为所有 macOS、Windows、网络文件系统的同一承诺。

若业务要求尽量缩小断电后丢失窗口，可在支持的目标平台设计这样一条顺序：在目标目录创建临时文件；写完并校验后对文件句柄调用 sync()；关闭句柄；把临时路径 rename 到目标；打开目标所在目录并请求同步目录；然后再记录交付收据。每一步都要 await，前一步失败就不要继续宣称后一步完成。writeFile 某些版本有 flush 选项，但其默认值并非总是启用，且只处理文件数据同步问题，不能让开发者省略目录持久性判断。目录同步是否可用、报错模式和设备是否兑现写入，必须按部署 OS 与文件系统单独验证。

一个具体失败路径可看出收据应该写什么。假设写入临时文件时空间不足，文件只包含 {"version":，解析校验失败，应删除临时文件并保留现有版本 1；若 rename 之前进程崩溃，版本 1 仍是已发布目标，遗留 tmp 可在下次启动清理；若 rename 成功但目录同步失败，运行中的新路径可能已经指向版本 2，程序却不能把它记为已达到目标耐久级别。此时盲目重试同名 rename 可能找不到原临时文件，恢复逻辑应先读目标内容与收据，辨认已生效与尚未证实的状态。上述是设计推演，不是机器断电演练结果。

不同路径布局会改变承诺

临时文件放在系统 /tmp 而目标在另一个挂载点时，Linux rename(2) 可返回 EXDEV；“复制过去再删除旧文件”不是同一个原子替换操作。若跨设备不可避免，需改成目标目录内先建立临时文件，或接受分阶段复制和恢复协议。目标同目录也不能从逻辑上保证所有环境的原子与耐久语义相同：网络挂载、容器卷、Windows 文件占用和权限规则都可能改变可用操作。先识别真实部署文件系统，再写平台特定验收，而不是把 Linux 手册当全平台证书。

替换文件还有读者语义。已经打开旧 config.json 的进程可能继续持有旧句柄；随后按路径重新打开的读者才看到新版本。若应用要所有工作线程同时切换配置，文件 rename 只是存储层发布点，还需要应用层通知、版本号和回退策略。先前文章流写入与背压讨论为什么写出缓冲不能当作落盘；在这里，即使完整字节已经交给写入 API，路径与耐久两个边界仍要分别确认。

也要区分“崩溃一致”与“业务接受”。即便版本 2 的文件名和内容在故障后可恢复，它可能包含未获批准的配置。构建程序应在 rename 前完成 schema 解析、关键字段范围检查、版本递增及依赖文件配套检查；如果配置与另一个文件必须一起更新，单次 rename 只能原子替换一个路径，不能使两份文件成为跨文件事务。可把配置集合放在版本目录，最后切换一个清单指针，或用数据库事务管理元数据，但新设计还需同样审查同步与恢复语义。

用故障点定义验收

安全的验证不应只运行一次成功路径。建立隔离测试目录，分别在写入完成前、文件同步后、rename 前、rename 后、目录同步前注入进程退出，检查目标究竟是版本 1、版本 2 还是需清理的 tmp；再用不同文件系统路径触发跨设备失败，并检验失败收据不冒充成功。进程退出测试证明进程级恢复，不能证明断电后真实介质行为。若项目要承诺断电耐久，需在明确 OS、文件系统、挂载参数和设备条件下另做受控断电测试，记录原始命令、版本和结果。本文没有运行此类探针。

最终收据应使用精确措辞：字节写入并校验、文件同步请求完成、rename 返回成功、目录同步请求完成、重启读取校验通过，分别是不同级别的证据。若业务只需要进程运行期间的可见原子切换，可以少做某些耐久步骤，但应把可丢失窗口写明；若交付用于不可重建的凭证或账务，要求更高，甚至不该仅凭单文件方案。不要把一个 API 的 resolved Promise 扩写成“任何故障后绝不丢失”，也不要因无法证明极端故障而否认 rename 在同一文件系统上提供的有用可见性边界。
