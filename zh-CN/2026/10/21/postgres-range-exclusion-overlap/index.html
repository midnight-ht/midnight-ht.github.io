让数据库拒绝同房重叠预约

用 tstzrange 与 GiST 排斥约束验证相邻可订、交叠拒绝、不同房可并行，并解释 NULL、空区间和并发边界。

正文

核心要点

  • 同房同一时段的约束是 room_id 相等且 during 重叠，UNIQUE 开始时间不能表达。
  • tstzrange 的 [) 边界允许前一预约结束点等于后一预约开始点；空区间和 NULL 要另设规则。
  • btree_gist 为整数房间号提供 GiST 等值支持，排斥约束负责最终拒绝冲突写入。

同一间会议室，甲预订十点到十一点，乙预订十点半到十一点半。两笔记录的开始时间不同，UNIQUE (room_id, starts_at) 可以让它们同时入库；房门却不能同时交给两组人。预约系统真正要禁止的是“同一房间且时间区间有交集”的记录对，而非某个标量值重复。PostgreSQL 的范围类型与排斥约束可以把这条业务规则留在数据库里，令所有写入路径接受同一裁决。

把“相邻可用、交叠不可用”写成表约束

以下是独立的教学表。预约时刻用 tstzrange，其端点是带时区的时间戳；输入显式写 +08，避免把会场当地时间和连接的会话时区混为一谈。[) 表示包含开始点而排除结束点，因此十点到十一点与十一点到十二点共用的十一点不构成重叠。这个边界定义需要产品和场地运维共同确认：若退场、清洁占用五分钟，应把缓冲计入区间，不能指望约束替业务猜出它。范围边界的包含与排除含义，见前述范围类型文档的边界小节。

CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE room_booking (
  booking_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  room_id integer NOT NULL,
  during tstzrange NOT NULL,
  CONSTRAINT room_booking_nonempty CHECK (NOT isempty(during)),
  CONSTRAINT room_booking_no_overlap
    EXCLUDE USING gist (room_id WITH =, during WITH &&)
);

这里 room_id WITH = 问两行是否订了同一房间，during WITH && 问两个范围是否有共同时间点。排斥约束禁止两个条件同时为真；房间不同或时段不重叠，至少有一个比较为假，便不冲突。btree_gist 给整数房间号提供 GiST 等值运算符类，时间范围的 GiST 则支持重叠判断。它不是额外的唯一索引：普通 B-tree 唯一性只能排除相同键，而重叠有无数种不同的端点组合。官方房间示例确认这种组合；btree_gist 扩展说明列出整数的 GiST 运算符类。

四次插入，逐项核对规则

先执行下面第一条，房间 7 从 10:00 至 11:00 被占用。第二条仍订房间 7，却从 11:00 开始，按 [) 边界预期成功。第三条把 10:30 至 11:30 放回房间 7，和前两条都相交，应被名为 room_booking_no_overlap 的约束拒绝。第四条改订房间 8，即使与房间 7 的时段相同，仍应成功。为便于逐条观察，四条语句应分别提交或在失败后处理当前事务状态；若把它们放在一个未设保存点的事务里，第三条的错误会使后续语句无法照原样继续。

INSERT INTO room_booking (room_id, during) VALUES
  (7, tstzrange('2026-11-02 10:00+08', '2026-11-02 11:00+08', '[)'));

INSERT INTO room_booking (room_id, during) VALUES
  (7, tstzrange('2026-11-02 11:00+08', '2026-11-02 12:00+08', '[)'));

INSERT INTO room_booking (room_id, during) VALUES
  (7, tstzrange('2026-11-02 10:30+08', '2026-11-02 11:30+08', '[)'));
-- 预期：违反 room_booking_no_overlap，不插入这一行

INSERT INTO room_booking (room_id, during) VALUES
  (8, tstzrange('2026-11-02 10:30+08', '2026-11-02 11:30+08', '[)'));
-- 预期：成功；房间不同

这些是依据 PostgreSQL 18 官方规则推演的预期，并非本站对该脚本或生产库的实测输出。读者可以在隔离数据库中运行后查询 SELECT booking_id, room_id, during FROM room_booking ORDER BY booking_id，应只见第一、第二、第四次的三行；第三条应报排斥约束冲突。生成的 booking_id 可能有缺口（参见序列编号为什么没有退回去？），因此别以 ID 连号作为验收条件。也可单独用 SELECT tstzrange(...,'[)') && tstzrange(...,'[)') 检查临界点，官方范围运算符表把 && 定义为两个范围有共同元素。

为什么先查询空档仍会失败

界面需要先查空档以便显示可选时段，但这个查询只是用户体验，不是最终完整性规则。假设两个事务几乎同时请求房间 7 的 14:00—15:00：各自的“是否存在重叠预约”查询都可能看不到另一方尚未提交的写入，于是两端都认为可订。若只靠应用中的 SELECT 后 INSERT，便留下检查与写入之间的竞争窗口。把上述排斥约束建在表上，冲突写入必须通过数据库约束；应用要把最终的冲突错误转换为“此时段刚被占用，请重新选择”，并对支付、通知等后续动作按提交结果协调。

不要把这个例子简化为“第二个事务必然立刻失败”。冲突检测和等待取决于并发事务的具体提交或回滚顺序。想验证自己系统的用户体验，应在隔离环境用两个连接分别执行冲突插入，观察等待、提交、回滚与返回错误，再验证失败请求没有发送确认邮件或扣款。单连接按顺序插入，只能证明约束判断了既有行，不能证明并发路径的错误处理。排斥约束自动创建相应索引；不能另建一棵普通查询索引便以为获得相同强制语义。排斥约束的索引创建与比较逻辑在 PostgreSQL 18 的约束文档中有明确说明。

空区间、NULL 与无限边界是不同决策

NOT NULL 放在房间号和时间范围上有实际理由。排斥约束的定义是任意两行比较时至少一个运算结果为假或空；若 room_id 或 during 可以是 NULL，不能据此承诺“所有未知房间或未知时间都互斥”。这个表把未知预约视为无效输入，故分别禁止两列为 NULL。CHECK (NOT isempty(during)) 处理另一种漏洞：空范围不包含任何时间点，和已有预约不会重叠；若业务把“十点到十点”当作有效预约，它会绕开原本想表达的占用规则。isempty 正是判断范围是否为空的官方函数。

还有无上界范围。tstzrange 允许省略端点，这代表向过去或未来无限延伸，可能意外锁死房间。若业务要求每笔预约都有明确开始和结束，应另外检查 lower_inf(during)、upper_inf(during) 均为假。是否限制最长预约时长、是否允许跨夜、取消后的记录是否继续参与冲突，都属于业务模型，不由这一条约束自动完成。若保留取消记录，常见选择是给约束加 WHERE 条件只覆盖有效状态；那会改变哪些行受保护，需要单独设计状态迁移和重复预约测试，不能机械地把本文 DDL 拷进已有表。

上线前先验证已有数据与写入路径

新表可以从零建立；已有预约表则先查出同房重叠的历史行并决定如何修复，不能假定 ALTER TABLE 会替人合并两张有效订单。可用自连接以 a.booking_id < b.booking_id 去重，并匹配 a.room_id = b.room_id AND a.during && b.during；先人工确认冲突代表重复写入、改期遗漏，还是业务允许的共享时段。随后在隔离副本上试建约束，记录建索引耗时与锁等待，再规划生产变更窗口。对写路径做接口测试：相邻与异房应可提交，同房重叠应得到明确冲突反馈；对更新路径也要测改房间、延长时段和取消后重订。约束解决的是表内完整性，不能替代用户可读错误或跨系统补偿。

如果用户必须抢订同一间房，数据库约束给出最后一道确定裁决；如果需求变成一间房允许多个座位、或两场活动共享空间，这条规则本身就不再正确，应改建资源容量模型。先把“什么叫冲突”写成可复核的输入和结果，再选择约束，比先堆一个唯一键更容易发现错误承诺。本文示例未在真实 PostgreSQL 实例执行，并发、迁移锁与部署权限仍须按目标版本和环境实测。

预约上线前的两个追问

取消预约后，怎样释放时段但保留记录？

可以只约束仍然有效的预约，而不是删除取消记录。假设为教学表增加 status text NOT NULL CHECK (status IN ('confirmed', 'cancelled'))，把原来的排斥约束替换为带 WHERE (status = 'confirmed') 的同房同区间排斥约束，就能让取消状态的行不参与冲突判断。这是另一种表设计，不能在原有无谓词约束还存在时，仅加一个带条件的新约束便期望取消生效。CREATE TABLE：EXCLUDE（PostgreSQL 18） 说明，谓词把检查限制在表的子集，内部建立部分索引。

应补测的是状态恢复，而不只是首次取消：先把房间 7 的十点预约改为 cancelled，再建立相同时段的新 confirmed 预约；若随后把旧记录恢复为 confirmed，按此设计应因重叠被拒绝。应用需要明确告知用户恢复失败，不能先发送“恢复成功”的通知。上述状态名和操作顺序是假设设计；真实表还要决定待付款、过期等状态是否占用资源，并在隔离库验证迁移及并发路径，本文未执行这一改造。

按预约开始月份分区，还能阻止跨月重叠吗？

不能把普通表上的同房间排斥约束直接当成跨分区保证。在 PostgreSQL 18 中，分区层级的分区键列必须包含在排斥约束中，并使用等值比较，使可能冲突的行落在同一分区。假设按开始月份分区，房间 7 从十月三十一日 23:30 预约至十一月一日 00:30，另一笔从十一月一日 00:00 至 01:00：两笔开始月份不同，却在现实时间上重叠。只给各月分区建立局部同房间约束，无法据此保证这一对记录互斥；把月份等值也加入比较，又使它们因月份不同而不满足全部冲突条件。

选择分区键时，需要先证明同一资源的潜在冲突不会跨分区，例如评估让同一房间的记录归入同一资源分区的方案，而不是为了按月归档就默认完整性仍成立。验收应专门包含跨月、跨年和更新跨分区键的用例；确实需要按时间切分时，应另行设计全局预约裁决路径。这个反例依据 PostgreSQL 18 的分区排斥约束限制 推导，不能代替目标表的实测。
