PKCE通过了，为什么API仍要拒绝这枚令牌？

PKCE保护授权码兑换，客户端认证确认相应客户端，资源API仍须逐次核对令牌受众、动作和对象权限。

正文

核心要点

  • PKCE绑定一次授权码兑换，不是客户端长期身份凭据。
  • 机密客户端认证与访问令牌受众、动作约束需分别验证。
  • 错误资源或动作的令牌应由目标API拒绝，并检查业务状态未改变。

一枚访问令牌由启用 PKCE 的授权流程签发，订单 API 仍可能必须拒绝它。PKCE 检查的是这次授权码兑换者能否交出与请求时挑战相配的验证器；它不替 API 判定令牌面向谁，也不替业务判断用户能否修改这张订单。把三个答案写成一个“OAuth 已通过”，最容易在集成测试里漏掉错用令牌的请求。

授权码兑换时，PKCE究竟绑定了什么

设想一个移动客户端准备访问资料 API。它在发起授权请求前生成一次性的 code_verifier，由它计算 S256 挑战值，把挑战随请求交给授权服务器，并在本地保留验证器。用户完成授权后，客户端取得授权码，再向令牌端点提交授权码和原验证器。服务器把两者与记录的挑战关系核对；若攻击者只截到授权码，却拿不出对应验证器，兑换应失败。这一层解决的是授权码被截取或注入后被错误兑换的问题，不是客户端软件身份认证。RFC 9700 §2.1.1要求公共客户端使用 PKCE，建议机密客户端也使用，并指出当前能避免在授权请求中暴露验证器的挑战方法是 S256。

“服务器验证了一个秘密”这句话容易造成误会。公共客户端的验证器是每次流程新生成、随这次授权码使用的值，不是机构发给某个应用实例的长期凭据。攻击者若能完整控制自己安装的公共客户端，也能为自己发起一次合法 PKCE 流程；通过挑战校验不能证明运行的是未篡改的官方二进制。另一方面，机密客户端若能够安全保管凭据，令牌端点仍应按注册的客户端认证方法识别它。RFC 9700 对可建立凭据发放和保密流程的部署提出客户端认证建议，并推荐考虑非对称方法；这项检查与 PKCE 可以并存。审核时要分别记录“验证码关系是否成立”与“按客户端类型要求的认证是否成立”，不能用其中一项代替另一项。

回调页也不是权限判决点。客户端需要把一次授权响应和自己的会话关联，避免把别人启动的流程接到当前浏览器会话；若把 PKCE 用作跨站请求伪造防护，还要确认授权服务器确实支持并强制它，不能允许省略挑战后降级。已登记的回调地址与实际兑换地址如何匹配，是另一个需要单独测试的约束，详见本站的OAuth 回调精确匹配讨论。这些步骤共同减少授权流程被劫持的机会，却仍没有回答一枚签发后的令牌能进入哪个 API。

API 拿到令牌后再做一遍属于自己的判断

继续用一个假设系统演算。授权服务器为资料 API https://api.example.test/profile 签发访问令牌：它的受众指向资料服务，允许读取本人资料。移动端随后误把这枚令牌发到 https://api.example.test/orders/42/cancel。请求头格式正确，令牌也未过期，签名或内省结果均真实；订单 API 仍应拒绝，因为受众不是订单服务，而且“读资料”不能授权“取消订单”。理想的集成测试结果是资料读取成功，订单取消被拒，订单状态保持原值。这是设计期的假设用例，不是对任何线上令牌的实测。RFC 9700 §2.3明确要求资源服务器对每个请求确认令牌是否为自己而发，并核对具体资源和动作。

受众限制与动作限制各管一件事。受众把令牌收窄到资源服务器，防止一个服务拿到的令牌被另一个服务接纳；scope 或更细的授权信息再限定这个服务内允许的操作。一个合法指向订单 API 的令牌，也不能自动取消所有人的订单：服务必须结合当前主体、订单所有权、业务状态和所请求动作判定。若系统使用不透明访问令牌，API 可通过受信内省结果获得这些属性；若使用 JWT，则还需按所采用的令牌规范验证签名、发行者、受众和用途。无论载体是哪一种，PKCE 都不是 API 对资源授权的快捷键。

再看另一个反例：一台后端服务作为机密客户端，凭正确认证取得了只读令牌。它自己可能完全可信，然而令牌里的权限仍是只读；如果资源服务器把“客户端已认证”解释成“可写”，就是把令牌端点的身份判断错误迁移到业务端。反过来，公共客户端虽然不能依赖长期客户端秘密，也不意味着它拿到的访问令牌无需受众、期限和动作限制。按客户端类型区分认证方式，与按资源需求限制令牌，是两个正交的工程决定。

怎样把三层检查落到测试合同

先把测试对象写成三列：授权请求与兑换列记录挑战方法、验证器和授权码的一次性关系；客户端列记录注册类型及相应的认证要求；资源列记录受众、允许动作和对象所有权。对第一列，正常验证器应换得令牌，改一个字符或省略挑战的请求应被拒，具体错误形态遵循服务器实现。对第二列，给机密客户端删除或替换凭据，令牌端点不得因为 PKCE 正确就放行；对公共客户端，不把客户端标识当作可保密的认证证据。对第三列，在一枚真实签发的令牌上换目标 API、换动作、换对象，预期均由资源服务独立拒绝，不要求先制造一个坏签名来触发失败。

这些负例最好用独立的测试身份与隔离资源执行，并核对拒绝后没有发生写入。如果只是断言返回了 401 或 403，却没检查订单是否已被取消，仍可能漏掉“先写入后报错”的缺陷；HTTP 状态码的选择还要遵循服务的认证和授权合同。记录服务器发行令牌的实际受众与权限，再和 API 配置的允许集合比较，能比“扫码登录成功”更准确地暴露集成差异。

选择是否额外采用发送方约束，也应基于泄露威胁，而非为了给 PKCE 补一个漂亮名称。RFC 9700 讨论了 mTLS、DPoP 等把访问令牌与持有方绑定的办法，它们处理的是泄露令牌被他人重放的问题，部署成本与客户端支持另算。对只能使用持有者令牌的系统，优先确保 HTTPS、短期令牌、受众与最小权限、撤销与异常监测；这些措施各有作用，不能宣称单独一种就消除重放。

最后的责任划分很朴素：授权服务器核对授权码与验证器，并按客户端类型认证、限制签发的令牌；客户端保护当前流程和收到的令牌；每个 API 在每次请求上验证令牌属于自己、用途正确、动作与对象被允许。如果测试报告只留下“PKCE 已开启”一个勾，它还没有验证后三项，也无法说明订单取消请求会得到什么结果。
