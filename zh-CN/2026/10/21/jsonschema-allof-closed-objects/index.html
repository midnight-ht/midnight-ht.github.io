JSON Schema allOf：封闭对象扩展时怎样安放字段

用地址对象实测 additionalProperties 与 allOf 的交互，并比较 unevaluatedProperties 和显式字段集合。

正文

核心要点

  • allOf 要求每个分支独立通过，不能当成继承扩展。
  • additionalProperties 只认识同一子模式声明的属性。
  • Draft 2020-12 中可用 unevaluatedProperties 在组合后限制未评估字段。

订单地址对象原本允许 street，团队用 allOf 叠加一个 kind 字段后，输入 {"street":"Main","kind":"business"} 竟被判“kind 是多余属性”。字段明明写在外层模式里，为什么内层拒绝？原因是 allOf 不是把几个模式合并成一张全局字段清单；实例必须分别满足每一个子模式，而 additionalProperties: false 只看与自己在同一子模式声明的 properties 和 patternProperties。JSON Schema 官方对象说明明确指出这一局部作用域；组合说明也提醒 allOf 不是面向对象继承。

看见外层字段，不代表内层放行

设想基础模式只声明 street 且设 additionalProperties: false。应用在外层用 allOf 引入基础模式，再在外层声明 kind。完整对象先经过基础模式：它认识 street，却不认识 kind，于是已经失败；外层的 kind 约束通过，也不能撤销子模式的失败。若只把外层再加一个 additionalProperties: false，还会引出另一种拒绝，因为外层也未必能把子模式声明过的 street 当成同层已声明属性。报错位置和关键字比“我们明明定义了这个字段”更有诊断价值。

下面的简化片段展示冲突；它是说明性模式，不是本站 API 的实际合同：

{
  "allOf": [{
    "type": "object",
    "properties": {"street": {"type": "string"}},
    "required": ["street"],
    "additionalProperties": false
  }],
  "properties": {"kind": {"enum": ["business", "residential"]}},
  "required": ["kind"]
}

以 {"street":"Main","kind":"business"} 校验，内层会把 kind 视为未声明。它不是说业务上不能有 kind，而是说当前模式把一个被封闭的子模式当成可扩展基类来用了。把 allOf 读作逻辑与就容易理解：同一个输入必须同时符合“只有 street”的限制和“需要 kind”的要求；两项条件在当前结构下彼此冲突。

两条修法，取决于能否改基础模式

如果基础模式可修改，把封闭规则移出可复用的基础定义，让基础模式先只约束它认识的字段，再在组合完成的位置关闭对象。采用支持 unevaluatedProperties 的草案时，外层可以在 allOf 与 properties.kind 之后设置 unevaluatedProperties: false。该关键字会考虑成功验证的子模式中已被评估的属性，因而能识别 street 和外层 kind，同时拒绝无关的 extra。它不是魔法补丁：如果内层仍保留 additionalProperties: false 并因此失败，外层新关键字不能让失败的内层变通过。先调整封闭位置，再重新跑矩阵。

另一条路线适合必须兼容不支持 unevaluatedProperties 的校验器：在最终封闭模式的同一层重新声明允许字段，再放 additionalProperties: false。这可能需要复制 street、kind 等名称，带来字段清单漂移的维护成本；若内层仍旧封闭，外层重声明也救不了内层，应重构基础定义或避免用它来扩展。选择前确认实际 JSON Schema 草案版本与验证器实现。官方说明标注 unevaluatedProperties 自 2019-09 草案引入，不应把新关键字塞进旧草案却假定生效。对已有大量消费者的模式库，迁移草案和重构基础模式可能比复制几项字段影响更大，需要评估。

编辑验证使用隔离的 Python jsonschema 4.26.0 与 Draft202012Validator 运行了最小局部例子。闭合内层对 {"street":"Main","kind":"business"} 返回无效，报 kind 是多余属性；移去内层封闭并在外层用 unevaluatedProperties: false 后，同一输入有效；再加 extra:1 无效；去掉必填 kind 也无效。探针脚本与原始输出保存在编辑审校记录中；这些结果只覆盖该校验器和所写模式，不证明项目中的别名、$ref、条件子模式或运行时工具都按同样方式配置。

让验收覆盖两个方向的错误

修完“合法新增字段被拒”后，还得防止“未知字段全被放行”。测试表至少包含：只有基础字段、基础字段加合法新增字段、再加未声明字段、缺少必填新增字段，以及新增字段的错误类型。每项记录通过与否及失败发生在哪个子模式，避免只把第一例改绿。若使用条件关键字，某字段只在 kind="business" 时允许，那么住宅地址即使字段名被某个分支认识，也未必应通过；成功评估的条件决定 unevaluatedProperties 能收集哪些字段。这个边界要结合具体草案和验证器运行，不靠静态扫一眼字段名。

上游还需明确是校验输入对象，还是接受任意扩展元数据。对外部 API 来说，严封闭能拦住拼错的键，却也让向后兼容新增字段更难；开放模式便于演进，却可能掩盖客户端拼写错误。可把稳定合同字段与单独的扩展对象分开，让扩展范围和大小受控，而不是把所有顶层未知键悄悄忽略。allOf 本身只组合条件，不替产品选择兼容策略。若已有消费者依赖旧 schema，改变封闭位置还应检查他们是否原本故意拒绝外层 kind，不能只凭新测试通过就宣称无回归。

条件分支要验证“谁评估了字段”

再加一条真实的条件约束：只有 kind="business" 的地址可以且必须有 department，住宅地址不认识这个字段。模式用 if 判断 kind，在 then 中声明并要求 department，外层仍以 unevaluatedProperties: false 收口。隔离探针在同一 jsonschema 4.26.0、Draft 2020-12 环境得到五个结果：{"street":"Main","kind":"business","department":"Sales"} 通过；同样的商业地址缺 department 时因必填失败；{"street":"Main","kind":"residential"} 通过；住宅地址附带 department 因未被成功分支评估而失败；商业地址再附带 extra:1 也因未评估属性失败。

这个矩阵不是给任何分支列出一个字段名就放行。then 只在条件匹配时参与，因而住宅地址里的 department 不会因为商业分支认识它而合法。若把 department 误放到外层 properties，住宅输入也可能被当作已评估，封闭规则便不再承担“只允许商业地址填写部门”的职责。业务规则和额外字段规则需各自验证：还要测 department 为数字、kind 为未知枚举，以及 kind 缺失的情况；不能只用上述五个样例外推全部条件组合。

实际排障时先保留失败实例、模式版本、校验器版本及精确错误路径，然后找 additionalProperties 所在层和 allOf 组合关系。若旧版本合同不可改，应考虑发布新模式版本或取消这种继承式扩展，而不是删掉全部封闭规则。本站OpenAPI readOnly 的执行边界讨论另一种“文档写了约束，实际工具如何执行”的问题；同样不能用模式文本取代针对所用工具链的测试。对本文的对象组合，最可靠的结论是：先让每个子模式能独立接受预期实例，再在正确层级决定哪些额外字段应被拒绝。
