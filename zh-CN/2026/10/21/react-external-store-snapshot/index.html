外部 store 的快照，为什么必须稳定？

以购物车数量拆解 subscribe、getSnapshot 和 getServerSnapshot：缓存不可变快照、通知顺序与 SSR 水合初值。

正文

核心要点

  • 外部 store 未变化时 getSnapshot 要返回同一值，可变底层数据应缓存不可变快照。
  • subscribe 的函数身份与快照身份是不同契约，通知须让 React 读到新版本。
  • SSR 与水合阶段的 getServerSnapshot 必须给出相同初值，再由客户端订阅后续变化。

页面顶部的购物车数量来自 React 之外的 store。用户在商品卡片点“加入”，store 里的 count 从 2 改到 3，顶部组件应该跟着变；服务端先输出的页面还要在浏览器接管时对得上。useSyncExternalStore 提供了连接这两套状态的接口，但三个函数不能随意拼：subscribe 负责通知，getSnapshot 负责给 React 一份稳定的可比较值，getServerSnapshot 负责服务端与水合阶段的共同初值。React 官方文档把这些契约写得很明确，关键不在于“监听成功”，而在于每一次读值能否表达同一个状态版本。

快照身份代表状态是否变化

先设 store 保存 {count:2, items:[...]}。组件只需要数量，可以让 getSnapshot 返回原始数字 2；只要数量没变，重复调用就是同一个基本值。用户加入一件后，store 改为 3，通知订阅者，React 再读到 3，于是更新显示。若组件需要对象快照，不能每次调用都 return {count: store.count}：即使 count 仍是 2，这也是新对象，Object.is 会认为不同。React 文档指出，未变更期间 getSnapshot 必须返回同一值；底层数据可变时，只有数据真的变化才创建新的不可变快照，否则返回缓存的上一份。

可把版本号当成实现线索，但不能只靠版本号口号。store 在每次语义变更时更新 version，缓存 {count, items} 的冻结或不可变拷贝；getSnapshot 发现版本未变就返回同一个缓存对象，变了才构造新对象。通知要在状态写入之后发出，使回调触发的新读取得到新版本；订阅函数则返回真正移除监听器的清理函数。具体代码还要保证 items 不在原对象里被原地改动，否则外层对象身份没变，内部内容却悄悄变化，破坏快照语义。若状态来源本身已用不可变更新，直接返回那份不可变数据可能更简单。

用一个完整小例子演算：初始 store 版本 5、购物车数量 2，缓存快照 S5={count:2}。顶部组件订阅后读到 S5，显示“2”。商品卡片追加一件，store 先把数量设为 3、版本设为 6，再发通知；下一次 getSnapshot 创建 S6={count:3}，顶部改为“3”。之后搜索框无关的重渲染再次调用 getSnapshot，仍返回 S6，React 不会因一个新造的同值对象而认为购物车又变化。这里的步骤是按官方契约推导的教学路径，并非对某个真实店铺进行了浏览器测量。

反例能定位两种不同的身份错误。若 subscribe 写在组件函数体内，每次渲染都创建新的函数，React 会重新订阅；这带来不必要的清理与安装，文档建议把稳定的订阅函数放在组件外。若 subscribe 稳定，但 getSnapshot 每次返回新对象，依旧可能反复渲染并触发 React 提示缓存快照的错误。反过来，缓存对象却原地修改它的属性，React 可能看不见应有的变化。订阅身份和快照身份是两份独立契约，不能修好一个就宣布外部状态接入完成。

服务端与水合要读同一初值

服务端渲染时没有浏览器里那份现成 store。假设服务器用会话数据输出购物车数量 2，而浏览器启动时本地 store 默认 0。若 getServerSnapshot 在服务端返回 2、水合时却返回 0，初始视图不一致；如果省略第三个函数却仍尝试在服务端渲染该组件，React 文档说会抛错。合理做法是把服务端用于输出的初始数据安全地序列化给浏览器，并让客户端水合时的 getServerSnapshot 返回同一数值 2，之后正常客户端 getSnapshot 才跟随后续 store 变化。序列化必须考虑用户隔离与转义，不能把另一用户购物车塞进共享缓存页面。

还要处理初始 HTML 生成后、浏览器完成水合前购物车发生变化的情况。服务端初值 2 仍用于匹配第一帧，浏览器 store 若已收到数量 3，应在接管后通过订阅或再次读取更新到 3；不要为了即时显示 3 而把水合用的初值偷偷改成 3，使它与 HTML 上的“2”冲突。若初始数据来自用户会话，缓存键与序列化脚本都要按请求隔离。这个时序判断比简单地把第三个函数写成常量更重要，因为同一常量只适合真正与用户无关的初值。

如果页面只是浏览器专属的在线状态徽标，服务端没有真实 navigator.onLine，可以选择定义一个一致的展示初值，或明确只在客户端渲染。关键是产品决定第一帧代表什么，而不是让服务器猜一个值、客户端再随机改掉。服务端初值相同也不等于远端数据永远同步：水合之后网络响应、跨标签页消息、库存更新仍应通过 store 的正常变更通知进入快照。useSyncExternalStore 解决的是 React 与外部源的读取和订阅桥梁，不替业务处理冲突合并或跨端权限。

应先判断外部 store 是否必要。若数量本来就在组件树的 props 或 context 内，直接按 React 数据流计算可能更简单；站内可计算状态与 Effect讨论过为何不必把能推导的值再同步一份。只有数据确实由框架外对象、浏览器 API 或第三方订阅源拥有时，才需要这套桥接。别为“避免 props 传递”凭空造第二份权威数据，否则两份状态谁先谁后会比 Hook 本身更难解释。

用可重复的状态序列验收

测试应构造可控 store，先多次调用 getSnapshot，在无变更时断言返回值按 Object.is 相同；修改数量后触发通知，断言读取到新不可变对象或新基本值，并在卸载组件后确认监听器被清除。对象里有数组时，再检查老快照仍保留旧内容，防止共享可变引用。SSR 测试则把服务端 HTML 与传给浏览器的同一初始数据配对，确认水合第一帧一致，然后模拟一次客户端更新。还应故意让初值不一致，确认测试能暴露这个错误，而不是只跑成功路径。

边界要记录清楚：React 文档还说明，外部 store 在非阻塞 Transition 期间变更时，React 可能重新读取快照并改用阻塞更新，以保持界面版本一致。这不是业务事务或数据库快照。本文没有运行 React 渲染探针，也不声称这些步骤在特定应用中测过；给出的是官方 API 契约、购物车状态推演及应执行的测试。交付标准是读者能指出每次变更的版本、通知、快照身份与水合初值，而不是只看到订阅回调被调用一次。
