OpenAPI 3.1：nullable 迁移要测缺失、null 和字符串

将 nullable 迁移为 JSON Schema 类型数组，并用三态输入核对描述、生成器和服务端行为。

正文

核心要点

  • OpenAPI 3.1 用包含 null 的类型数组表达可空值。
  • 允许 null 与允许字段缺失由不同约束决定。
  • 迁移验收要对比实际请求字节、生成器类型和服务端状态变化。

旧 OpenAPI 3.0 描述把 nickname 写成 type: string 加 nullable: true，测试会发送 {"nickname":null}。升级文件头到 3.1 后，如果仍沿用原写法，新的 JSON Schema 语义工具可能只看到字符串约束，把 null 判为非法。OpenAPI Initiative 的迁移说明明确建议用类型数组替换 nullable: true；OAS 3.1.1 规范将 Schema Object 与 JSON Schema Draft 2020-12 对齐，null 是可明确列出的类型。迁移目标不是“YAML 看起来差不多”，而是客户端、服务端与生成器对字段状态达成相同合同。

先固定三个不同输入

对一个用户资料更新，至少把字段缺失、显式 null、普通字符串分开。{} 表示请求没有 nickname；{"nickname":null} 表示明确给出空值；{"nickname":"Ada"} 表示给出文本。它们是否分别表示“不改”“清空”“设置”，由 API 的 PUT/PATCH 合同决定，Schema 类型只回答传来的值是否合法，不能替产品定义更新动作。若还有空字符串 ""，它依然是字符串，不等于 null；是否允许须另加长度或业务规则。站内PUT 与 PATCH 的替换边界讨论方法语义；本篇聚焦描述版本升级时别把状态合并。

一个最小对照足以说明语法变化：

# OpenAPI 3.0 中的属性
nickname:
  type: string
  nullable: true

# OpenAPI 3.1 中的属性
nickname:
  type: [string, 'null']

若这个属性还放在对象的 required: [nickname] 里，缺失键仍应失败，即便 null 可作为值通过；若不在 required 里，缺失通常可通过，但显式 null 仍需看类型集合。“允许 null”与“可以省略”是两条正交规则。把 nullable 直接删掉而不把 null 加到类型集合，会把原本合法的显式清空变成错误；反过来，为所有可选字段都加 null，会让原本只允许省略的字段突然接受清空。迁移清单必须逐字段决定，而非全局搜索替换。

该规范里的另一个关键点是类型约束需要明确。format 或 pattern 作用于相应类型的实例，不会自动把其他类型判错；只写 format: date-time 却删掉 type: string，可能得到比预期宽的模式。对于 nickname，如果原本还有 minLength，即使类型数组允许 null，长度限制主要针对字符串，不能拿它证明 null 被拒。检查最终 schema 必须看类型、必填、枚举及相关约束组合，不能只数有没有 nullable 单词。

迁移不是只改一个字段

团队可能在响应和请求里用同名模型，却对 null 有不同语义。响应里的 null 或许表示“用户未设置昵称”，更新请求里的 null 则可能表示“清空昵称”；若某个字段由服务器计算，请求根本不应接受它。迁移时按每个请求体、响应体和操作分别列状态矩阵，不宜凭共用组件一次性改出所有上下文。$ref 指向的组件、allOf 包裹的约束也要追踪到最终有效模式。生成器可能依赖旧版本扩展或缓存；即使规范允许 type 数组，部署的工具版本也要实测是否正确产生可空类型、序列化 null 和保留省略。

默认值尤其容易被误读。一个 schema 写了 default: "guest"，并不等于服务端必然在缺失时填入 guest，也不等于客户端发 null 时可自动替换。默认值属于描述性注解或具体工具行为，不能取代明示的请求处理规则。测试应分别捕获原始请求、验证结果、服务器持久化值和响应；只看生成的 TypeScript 类型出现 string | null，还不足以证明服务端清空操作生效。若服务器使用 JSON 序列化器省略 undefined，也要确认 omission 没被误送成 null。

还有非 JSON 位置。查询参数、路径参数与表单字段最终通过字符串或表单编码传输；即便 schema 允许 null 类型，如何把它编码为线上字节、与空字符串区分，未必能照搬 JSON 请求体的办法。该规范对参数序列化中的 null 处理明确留有实现定义空间。因此若迁移主题是 JSON body，可直接用 JSON null 作矩阵；若是 ?nickname=，就要额外定义“参数不存在、空值、字符串 null”的编码合同，不要把 JSON 模型的验证通过外推到 URL。

迁移还需要一张差异表，不能只拿升级后的 schema 单独自测。对 nickname，旧合同可能允许缺失与 null、拒绝数字；新合同应保留这些结果，除非产品明确改变了含义。若同一组件被十几个操作引用，先列出引用点和每个位置的 required 列表。对象层 required 与属性层 type 分处不同位置，自动替换脚本若只遍历属性节点，可能漏掉嵌套的数组元素或组合模式。适合先在测试仓库选一个最小组件跑差异，再扩大到全部引用；每扩一次都保存哪些测试用例从通过变为失败、反之亦然，并让 API 负责人决定是否允许行为变化。

若团队把 OpenAPI 用于生成 SDK，还要分别检查两种语言的“未提供”表达方式。有的语言用可选字段承载缺失，用可空类型承载 null；有的生成器把两者都折叠为一个指针或 Optional。这时模型声明正确仍可能在序列化时丢失区别。给生成器一个对象含原值、一个显式清空和一个缺失字段的输入，抓取真实 HTTP body，才能知道合同是否落地。响应方向也要反测：服务端返回显式 null 时，SDK 是否把它保持为 null，还是误判为字段缺席。测试应固定生成器版本与模板配置，避免下一次工具升级偷偷改掉三态映射。

把对照变成可执行验收

先保留一份旧描述和真实兼容输入集：缺失、null、有效字符串、空字符串、错误数字。对迁移前后两个版本分别跑描述校验与实例校验，记录每项是否通过；对生成的客户端或服务桩，再检查类型、实际请求字节和响应解析。若一个生成器把 type: [string, 'null'] 解释成只能有字符串，就不能仅说“规范是对的”，要明确工具版本不支持当前合同并选择升级、替换或暂缓迁移。错误数字若因遗漏 type 意外通过，同样是阻断。

对 PATCH 清空路径，完成一次真实应用验收还要验证数据库列、业务校验和审计事件的最终含义：发送 null 后读取是否为空，发送缺失后原值是否保持，重复提交是否幂等，权限不足是否被拒。这些是发布时应做的测试设计，本文没有调用某个 API 或执行规范工具链；本稿的 YAML 是说明性对照，不是已运行的迁移脚本。迁移报告应把“Schema 合法”“生成器能用”“服务行为正确”分开列证据。只有三者指向同一组输入状态，nullable 的替换才不是一次只在文档里成功的语法转换。
