旧数据未清完，如何上线 CHECK 约束

用订单金额案例拆开 NOT VALID 的新写入拦截、历史清理和最终验证，说明旧行更新、NULL 与锁的边界。

正文

核心要点

  • NOT VALID 跳过添加约束时的存量扫描，提交后仍检查后续插入与更新。
  • 历史坏行须先按业务含义清理，再以 VALIDATE CONSTRAINT 成功证明全表满足约束。
  • CHECK 的 NULL 语义、旧坏行更新和验证阶段的锁都应进入迁移验收。

订单表里已经有负金额，团队准备增加 CHECK (total_cents >= 0)。直接添加约束会检查存量行，第一条违规订单就使迁移失败；先把所有旧订单清完又可能持续几天，期间新写入仍能制造同样的问题。NOT VALID 解决的是这个时间顺序：先让数据库对后续写入执法，再另开一次验证去确认历史数据。PostgreSQL 18 的 ALTER TABLE 文档明确说，添加时跳过初始扫描，但约束仍作用于后续插入或更新。它绝不是“暂时不检查约束”。

先挡住新坏行，再证明旧行

先把三种状态写在迁移单上。开始前，旧行和新行都可能违规；执行 ADD CONSTRAINT ... NOT VALID 并提交之后，新写入必须满足条件，而旧行尚未整体证明合规；执行 VALIDATE CONSTRAINT 成功之后，数据库才可以把整张表视为满足该约束。这个状态分界比“SQL 执行成功”更有用。只看到 ADD 成功，不能向依赖方宣称历史数据已清洁；只看到批处理清理完成，也不能跳过数据库最终验证。

用具体订单演算。orders 中有三行：编号 41 的金额为 1200 分，编号 42 为 -300 分，编号 43 为 0 分。产品规则允许零金额优惠单，却不允许负数。先确认规则确实如此：如果零金额也应被拒绝，表达式该是 > 0，而不是在部署当天凭印象改运算符。迁移先运行 ALTER TABLE orders ADD CONSTRAINT orders_total_nonnegative CHECK (total_cents >= 0) NOT VALID;。提交后尝试插入编号 44、金额 -1 分，会被约束拒绝；插入编号 45、金额 50 分可以通过。编号 42 仍留在表内，这正是待清理的存量，不是 ADD 漏执行。

清理前先解释旧值

接着找出异常订单以及业务归因。SELECT id,total_cents FROM orders WHERE total_cents < 0 ORDER BY id; 是定位这个具体条件的候选查询。若旧值是退款冲回，不应简单改成零；可能需要把退款表示为独立记录，或修正此次约束原本不适合这张表的事实。若是导入错误，先在审计记录中保留原值和更正依据，再将编号 42 修为经确认的数值。最后运行 ALTER TABLE orders VALIDATE CONSTRAINT orders_total_nonnegative;。当编号 42 仍为 -300 分，验证会失败，约束保持未验证状态；修复后重试验证才有完成证据。这里的数值和结果是按 PostgreSQL 文档机制推演的教学案例，并非在生产订单表实测。

需要特别看更新旧行的路径。NOT VALID 并不授权应用继续对编号 42 做任意更新。文档说约束作用于随后的更新，因此即使只是改订单备注，新的行版本仍须满足金额检查，可能先被拒绝。清理任务若把负数从 -300 改为 -100，同样不会因“正在修数据”而获豁免。迁移窗口中如果业务必须修改这类旧行，就要安排一次使整行合规的修复，或者改变迁移顺序；不要把错误重试归咎于偶发锁竞争。

执行前还应做一遍 NULL 语义检查。CHECK (total_cents >= 0) 对 NULL 得到未知，而不是 false，可能让空金额通过。若金额必须存在，需要另有非空约束及其迁移计划，不能靠这个 CHECK 偷渡。已有文章CHECK 与 NULL 的区别解释了为何写着大于零的检查也可能保存空值。本例把“允许零”与“允许 NULL”分开决定，免得验证成功后产品仍出现没有金额的订单。

验证阶段仍有扫描与锁

NOT VALID 的另一层价值是降低长时间初始扫描对并发更新的影响，而不是无锁。PostgreSQL 文档说明，普通添加约束的存量扫描会把相关更新挡到命令提交；跳过该扫描可以尽早提交 ADD。后续 VALIDATE CONSTRAINT 仍需要扫描表，并获取 SHARE UPDATE EXCLUSIVE 锁。这个锁级别和日常读写的兼容性、与其他维护任务的冲突，必须结合实际业务和版本评估。迁移单应记录预计扫描规模、超时与重试方式，以及当验证因坏数据或锁等待失败时如何恢复，而不能写“一次 DDL 零影响”。

约束类型也不能混用。文档列出的 NOT VALID 适用范围是外键、CHECK 和非空约束；它不是任意 UNIQUE 或主键迁移的通用开关。若改为外键，添加约束还会在被引用表取锁，验证也涉及被引用关系；不能把单表金额 CHECK 的运行窗口原封不动套到订单与客户的外键上。团队在上线清单中应写出本次约束的准确类型和触及的表，不把语法能通过当作并发风险评估。

两阶段迁移还要确定失败后的“留在何处”。如果 ADD 语句失败，数据库尚未建立挡新写入的栅栏，不能开始以为后续都干净的清理；先查 DDL 错误并重试。若 ADD 已提交而批处理失败，约束仍继续拦截新违规写入，修复任务可以安全续跑，但业务上可能持续有旧行的非金额更新失败。若 VALIDATE 失败，保留约束、检查具体违规行并再次验证通常比撤销约束更符合目标；撤销会重新放开新写入，需另有明确理由和回滚授权。不要把三个阶段放在一笔长事务里等待人工清理，免得本来要缩短的锁窗口被事务延长。

以阶段证据结束迁移

验收也要按状态分开。上线前抽取代表性旧行，确认零、正数、负数、NULL 的业务预期，检查应用是否仍有负数生成路径。ADD 提交后用隔离的测试表或受控环境验证负数插入、正数插入和修改旧违规行的预期；这些探针不能拿生产真订单随意做。清理期间按约束条件盘点违规数量并保存批次进度、异常理由。最后以 VALIDATE CONSTRAINT 成功和数据库目录中已验证状态为完成信号，同时观察锁等待、写入错误及回滚请求。这里只给出验证方案，未声称执行了数据库实验或取得生产锁耗时。

如果系统允许历史行永远不修，NOT VALID 可以长期保持“新行受管，旧行未证”的状态，但下游不能把全表当成一致数据。报表按总金额统计时仍会纳入负数旧行，API 也可能读到它。迁移负责人应把这种暂态写进数据契约，给清理明确责任和截止条件；否则一个看似成功的 schema 变更会变成永久的数据质量分叉。真正的完成点，是约束表达了已确认的业务规则、旧数据被正确处理、最终验证成功，而且相关读写路径都接受这个规则。
