默认分支工作流，并不让PR检出内容可信

pull_request_target适合处理PR元数据；检出并执行PR head代码会让提交者控制的文件进入高权限job。

正文

核心要点

  • 默认分支提供可信工作流定义，不会使PR head文件可信。
  • 元数据操作与PR代码测试应分开权限和触发路径。
  • 审查事件字段、checkout内容、缓存和后续制品的信任传递。

pull_request_target 的工作流文件来自基础仓库的默认分支，不能因此把外部 PR 的文件也当成可信代码。一个只给 PR 加标签的任务，若顺手检出提交者的 head 并运行测试脚本，执行主体就从维护者审查过的工作流切换成了提交者可修改的文件。风险不在“检出”这两个字本身，而在高权限 job 接下来怎样读取、解析或执行检出的内容。

两种来源进入了同一个 job

假设仓库希望给外部贡献者的 PR 自动标注 needs-review。基础仓库默认分支里的工作流订阅 pull_request_target，收到 PR 编号、目标分支等事件字段，调用 GitHub API 更新标签即可。这个流程不需要构建补丁，也不需要运行 PR 的脚本。GitHub 事件文档说明，该事件在基础仓库默认分支上下文运行，而不是像 pull_request 那样处于合并提交上下文；它适合给来自 fork 的 PR 贴标签或留言，明确提醒需要构建或运行 PR 代码时应避免使用这一事件。

现在有人为“节省一个工作流”添加检出：把 actions/checkout 的 ref 指向 PR 的 head SHA，再执行 npm test。YAML 的确仍从默认分支装载，但 package.json、安装脚本、测试文件和依赖解析配置由 PR 作者控制。若 job 还保留写权限的 GITHUB_TOKEN，或能读取其引用的秘密，执行 PR 文件便跨过了原本为元数据处理设置的信任边界。GitHub 官方警告，在 pull_request_target 中运行不可信代码可能带来缓存投毒及意外取得写权限或秘密的风险。不能把“工作流定义可信”推成“此 job 的所有输入可信”。

审查时最好画出一次执行的来源表：触发器和工作流 YAML 属于基础分支，事件 payload 来自 GitHub 但包含提交者可控制的标题、分支名、文件名等值，PR head 的内容直接由提交者控制，令牌和环境秘密属于基础仓库。可信的 API 不会自动消毒可控字段：如果把 PR 标题直接插进 shell 命令，即使完全不 checkout，也可能在解释命令时出问题。元数据任务要把用户字段当数据传递给固定参数的 API，而不是拼成代码、查询语句或 shell 片段。身份和数据流分别检查，才看得出边界在哪里跨越。

一个只处理元数据的假设流程

设 PR #42 从外部 fork 指向仓库的主分支。需求只有两步：根据事件中的 PR 编号读取已有标签；若缺少 needs-review，写回这个固定标签。设计中的 job 把 permissions 收窄到读取仓库内容和为 PR 写标签所需的范围，调用固定的受信动作或 API，不检出 PR head、不执行项目脚本，也不从 PR 文件里加载配置。期望结果是 PR #42 多了这个标签，仓库文件、制品与部署状态不变。该案例是设计演算；这里没有运行 GitHub 工作流，也没有给真实 PR 加标签。

这个做法并非声称“标签 job 因为没有 checkout 就绝对安全”。如果动作版本不受控、使用了不安全的表达式插值，或者标签逻辑把提交者文字变成动态命令，仍可能发生注入。第三方动作同样是在 job 权限下运行，权限应按实际 API 调用设置并审查动作来源。若只读 PR 事件就足够，不应为了方便把 contents: write、actions: write 或部署凭据交给它。关于 GITHUB_TOKEN 即使未显式作为参数传递仍可被动作上下文访问的边界，可接着读本站令牌权限文章。

反例同样用 PR #42：它修改了项目测试脚本。高权限 job 检出该 head 后跑 npm test，将会执行提交者控制的脚本；即使维护者没有手动写出恶意 shell 行为，脚本及其依赖安装步骤仍是代码执行入口。预期的安全审查结论是拒绝这一组合，而不是先运行再看日志是否有可疑输出。若同一 job 还缓存依赖，受污染内容还可能影响后续构建；这与泄露秘密不是同一种结果，但共享同一信任边界。不要用“fork 的 PR 默认拿不到秘密”来反驳：这个说法描述普通 fork PR 工作流的限制，不能套到特意选择了基础仓库上下文的 pull_request_target。

需要测试补丁时，把信任与权限拆开

测试 PR 代码的需求仍可满足。把构建、依赖安装与测试放进由 pull_request 触发的低权限 job，明确 permissions，不提供部署秘密，也不把它产生的缓存或制品直接当作高权限发布输入。另一个 pull_request_target job 只做标签、评论等元数据工作。分离不只是在 YAML 里写成两个 job：还要看是否通过 workflow_run、制品下载或共享缓存把低信任输出接回高权限步骤。如果后续确实要消费 PR 产生的结果，需要先定义结果格式、验证身份和内容、固定可信执行代码，并重新审查相应触发器的权限。GitHub 对 workflow_run 执行不可信代码也有独立警告。

谁拥有 PR head 的修改权是选择触发器的关键，不是贡献者看起来是否友好。同仓库成员提交的 PR 也可能修改测试脚本；若组织愿意让这类代码以某些权限运行，那是经审查后的信任政策，不是事件名称自动提供的保证。外部 fork 的正常测试可在受限权限下先得到失败和日志；需要维护者授权的写入动作则留在不解释 PR 代码的独立路径。对管理员开关、第一次贡献者运行审批等 GitHub 设置，也应以仓库当前配置核对，不能当作替代 job 设计的普适保护。

审核一个拟议的改动时，可以用四个问题复盘：这一步实际运行的可执行文件来自哪个提交？当前 job 的令牌与秘密能做什么？提交者可控的标题、路径或制品以数据还是命令进入？输出是否会被后续高权限工作流继续信任？准备一个不含秘密的假设 PR，它只把测试脚本改成写入显眼标记，静态检查应发现高权限 job 不会调用该脚本；在允许的隔离测试仓库中再观察低权限 job 会运行它，但不能触及写权限。本文没有执行该测试，观察结果必须由目标仓库实际回执填写。

具体选择取决于所需动作。只读写 PR 元数据，留在不触碰 head 的基础仓库上下文；需要测试 head，使用低权限执行路径；需要把测试结果用于发布，再建立独立的制品来源与权限核验。把所有步骤塞回 pull_request_target，只能减少 YAML 文件数，不能减少 PR 作者对执行内容的控制权。
