strict-markers 抓得住标记拼错，还漏什么？

以 integration 漏跑案例说明注册标记、strict_markers 与 -m 零选集校验各自负责什么。

正文

核心要点

  • 注册自定义标记并启用 strict_markers，可让未知装饰器标记在收集时失败。
  • 严格标记不证明 -m 表达式选中预期测试，专用 job 应检查选集和关键 node ID。
  • selected、skip、xfail 与 pass 是不同证据，不能只看流水线绿色。

CI 约定用 pytest -m integration 运行集成测试。某位开发者给新用例写了 @pytest.mark.intergration，把标记名误拼成另一个词；本地直接运行全套测试时它仍会执行，但 CI 的筛选表达式找不到这项标记，测试可能悄悄落选。strict_markers 可以把“使用未知装饰器标记”变成错误，却不能单独证明 -m 表达式真的选中了预期的用例。要防漏跑，需要注册词表和检查选择结果两道门槛。pytest 官方自定义标记文档明确建议注册标记，并说明严格模式会把函数标记的拼写错误当作错误。

先给标记名字一个受控词表

假设仓库有快速单元测试和依赖本地数据库的集成测试。配置文件可登记 integration: requires local database 与 slow: may exceed normal unit budget；测试函数使用 @pytest.mark.integration。这样 pytest --markers 可以列出团队认可的名字及含义。若开发者改成 @pytest.mark.intergration，启用 strict_markers 后，收集阶段就会因未知标记报错，而不是只给警告、继续运行一个未被 -m integration 命中的用例。明确注册也让代码审查知道“集成”究竟意味着什么环境，而非只看一个装饰器单词。

最小案例有三个测试：test_total 未标记、test_db_insert 标记 integration、test_db_update 误标 intergration。CI 执行 pytest -m integration 的目标原本是运行两条数据库测试。若未启严格标记，收集可能给未知标记警告，筛选只选出 test_db_insert；结果一条通过，流水线绿，但 test_db_update 从未运行。启用严格标记并只注册正确的 integration 后，误拼在收集阶段导致错误，流水线不能把“一条通过”误作完整集成测试。这里是基于文档规则的推演，不是该仓库真实 CI 的输出。

可以把配置写得具体一些。在 pytest.ini 的 [pytest] 下加入 markers = 列表，逐行注册 integration: requires local database 和 slow: long-running scenario，并设置 strict_markers = true。团队也可使用命令行 --strict-markers，但固定在仓库配置能让本地、CI 和不同入口保持同一约束。标记说明应描述筛选意图而非环境秘密，且应与实际用例同步维护；删除一个旧标记时先迁移用例再删注册，避免把预期失败误作测试问题。

严格注册没有校验筛选表达式

现在换一个反例：所有函数都正确使用 @pytest.mark.integration，但 CI 命令误写成 pytest -m intergration。测试源码没有未知标记，strict_markers 不会因为命令里的字符串拼错就替团队保证“应该有两条被选中”。实际命令可能收集到用例却 deselect 全部；不同退出码、插件和封装脚本的处理还可能让结果更难看懂。因此 CI 需要针对“目标套件至少选中了多少条”另做断言，保留 collected、selected、deselected 的原始输出。不能只看整个命令是不是打印了绿色符号。

例如为 integration 组维护一条可审查的最低门槛：在专用 job 中先运行 pytest --collect-only -q -m integration，读取实际选中 node ID，若为零就停止并给出清晰错误；随后正式执行同一表达式。若团队知道本应有两项核心测试，可检查指定 node ID 是否存在，而不仅是“大于零”。数量门槛能抓空选集，不能判断选到的是不是正确用例；核心用例列表又需要随测试演进更新。两种检查可以分层使用，别把固定数量硬编码成永远不变的测试覆盖率指标。

标记表达式的逻辑也会误伤。-m 'not slow' 会选中未标记测试，不等于“只跑快速单元测试”；-m 'integration and not slow' 则会排除同时带 slow 的集成测试。模块级 pytestmark、类标记、参数化单个参数的标记也会影响最终选集。审查一个 job 时应看实际收集结果，而不是仅凭命令文本想象覆盖范围。若因为环境缺少数据库而把所有 integration 用例 skip，被选中也未必完成了有效断言；selected 数与 passed 数必须分开报告。

如果仓库既有 integration 又有 integration_api，不要把名称前缀当层级继承。-m integration 匹配的是标记表达式里的具体名字，不会自动把名称相近的用例一起纳入。更稳妥的是给必须进入集成 job 的用例统一加 integration，细分标签作为第二个标记，或建立两个明确表达式并分别审查选集。同理，用例从一个目录搬到另一个目录后，路径参数可能先把它排除，随后 -m 根本无机会选择它；标记正确也救不了路径过滤。把路径和标记的交集列成实际 node ID，才能知道 job 到底覆盖了哪些测试。

站内xfail 严格门槛解释了预期失败恢复后如何避免流水线误绿；这里的风险发生得更早，是测试根本没被选中。为了诊断，将收集失败、零选中、运行后 skip、xfail 与真正 pass 作为不同状态。发布前给 CI 保存 pytest --markers 和收集摘要、pytest 版本与配置来源，可在标记清单发生变更时比较差异。只有通过 strict_markers 和选择数量仍不等于覆盖充分，但至少能让一类静默漏跑变成可见失败。

在隔离夹具中验证门槛

用最小项目建立三条上述测试与正确注册配置，先故意保留 intergration 装饰器，预测严格模式下收集报错；修正装饰器后确认 -m integration 精确选出两条；再故意把命令写成 -m intergration，确认自己的零选中门槛报警。保存完整配置、命令、pytest 版本和原始 stdout，才能把这些预期称为实测。本文没有运行 pytest 探针，因此没有伪造选中数或退出码；上线到具体仓库时还要检查插件是否注册了额外同名标记、测试发现路径是否遗漏以及 job 是否吞掉非零退出。

最终团队政策可以很短：新增标记先在配置中定义含义，严格模式拒绝未知装饰器；每个 -m 专用任务在收集阶段校验目标用例存在，运行阶段核对实际 pass、skip、xfail 与失败；变更筛选表达式时审查完整选集。这样 test_db_update 若被误标，会在收集时暴露；若命令拼错，会在选集门槛暴露；若数据库不可用，则会在运行状态暴露。三个问题需要三种证据，不能被一个“绿色 CI”合并成同一结论。
