CloudEvents 去重：把 source 与 id 当一对身份

用跨仓库事件和失败重送解释 source 加 id 的身份边界，以及消费端事务与保留窗口。

正文

核心要点

  • CloudEvents 要求生产者为不同事件保证 source 与 id 组合唯一。
  • 只按 id 或 data 去重会误吞合法事件或漏掉重送。
  • 消费端需把身份记录与业务副作用原子化或另设补偿。

一个库存变更事件经消息系统重试两次，下游计数器却增加了三次。团队在日志里看到三个相同的 id，便准备把 id 当全局主键。这个修补仍可能误删另一来源的合法事件。CloudEvents v1.0.2 规范给出的身份边界是 source 与 id 的组合：生产者必须保证这一对值对不同事件唯一；重复发送同一事件时可以沿用同一 id，消费者可以把同一对值视为重复。身份规则能让消费端识别重送，却不会自动替业务操作实现恰好一次。

从一条订单事件看重复的定义

假设 /warehouse/east 发布订单 O-41 的库存扣减事件，id 是 evt-901，首次投递后消费者完成了扣减，但确认消息在网络中丢失。代理再次投递，事件的 source=/warehouse/east、id=evt-901 均保持不变。消费者查到已处理的这对键，应返回成功或已处理结果，避免再扣一次。若 /warehouse/west 恰好也发布 id=evt-901，它是另一对身份；只按 id 去重会误吞西仓事件。若东仓随后真的发生第二次独立库存变化，则必须分配新的 id；重复使用 evt-901 会让消费者有理由把新变化当旧事件。

{"specversion":"1.0","type":"com.example.stock.debited","source":"/warehouse/east","id":"evt-901","subject":"orders/O-41","data":{"sku":"S-7","quantity":2}}

这段 JSON 是说明性事件，并非生产投递记录。source 标识事件发生的上下文，通常由生产者选择；id 在该上下文内承担唯一性。subject 可以帮助定位订单，却不能替代身份键，因为一个订单会产生多次合法变化。type 描述事件种类，也不能成为唯一性的一部分：同类型会反复发生，类型变化也不应使同一重送突然成为新事件。规范只规定生产者的身份承诺与消费者可作的重复假设，并没有规定数据库该保留记录多久。

身份键的规范性还取决于上游如何生成它。若生产者在每次重试时调用随机数生成器产生新 id，消费者收到的就是两对不同身份，无法知道它们对应同一次业务变化。生产端应在业务变更形成时固定事件身份，并让发送重试复用已持久化的事件记录；若使用 outbox，事件内容与身份应跟业务提交一起存下，发送器只负责重复取出和投递。若业务动作本身重试导致两次数据库变更，那是命令层的幂等问题，不能指望事件层去重弥补。两层身份分别回答“同一个命令是否执行过”和“同一个事件是否消费过”，需要用业务追踪号把它们关联，而不应偷换为同一个键。

排查时还应保留原始事件字节或足够的规范化摘要，但不要用摘要直接代替 (source,id)。如果相同身份下 payload 不同，正好说明生产者身份约束或传输链存在异常；把摘要加进唯一键反而会让两份冲突事件都进入业务处理。消费者可以在已处理记录中保存不可变字段摘要，重复到达时先比对，若冲突则隔离并告警。这个附加校验帮助发现错误，不改变规范给出的事件身份。

把去重和业务提交放进同一事务

消费端常见做法是在业务数据库建立 (source,id) 唯一键。处理事件时，同一事务先插入接收记录，再执行库存变化；若唯一冲突，读取已有处理结果并结束。关键不是语句先后，而是原子性：如果去重记录提交了、库存扣减却失败，后续重试会被错误丢弃；如果库存扣减提交了、去重记录却没落库，重试又会重复扣减。数据库无法将外部系统写入纳入同一事务时，需另设业务幂等键、outbox/inbox 或状态机，并明确每一步可重试的结果。站内API 重试与幂等边界讨论请求层语义；事件消费还要处理生产者与消费者两侧持久化的间隙。

例如计数器更新 stock = stock - 2 若无保护就会随重送重复执行。把事件身份与订单变更版本一起写入账本，并对同一 (source,id) 返回既有结果，能防止这个具体重复；但若生产者把同一真实业务动作错误地发成两个不同 id，事件去重无法推断它们属于同一动作。反过来，两个合法动作即使业务字段完全相同，也不能靠比对 data JSON 当作重复。data 可能因补充字段、序列化顺序或脱敏而变化；身份承诺才是此层的判据，业务层另有其自然键与约束。

还有一个经常漏掉的时间问题：如果只保存最近七天的去重键，八天后到达的旧事件可能再次生效。应根据传输系统最大重送窗口、离线回放、灾备导入与业务不可逆性确定保留策略。无确定上界的场景，不能只声称“七天后不会重复”；可保存紧凑的长期事件账本，或让业务更新本身由版本约束保护。回放历史流时要决定是重建新投影，还是向已有投影补事件；前者可清空投影并按顺序重建，后者必须继承已处理身份，避免再次执行副作用。

验收时同时制造重复与非重复

最小测试集应有四项。先把同一事件投递两次，断言账本只有一对身份且库存只扣一次。再用相同 id、不同 source 投递，断言两条都被接受；再用相同 source、新 id 且相同 data 投递，断言它仍是第二次合法变化。最后，在“业务写入成功但确认失败”处人为断开，恢复后重送并观察事务与响应。这组负例比只测“相同 JSON 进两次”更能找出错误的全局 id 主键和基于 payload 的误去重。

消费者还应记录 source、id、处理版本、首次接收时间、最终结果与失败原因，方便区分重送、真正的新事件和业务拒绝。日志中看到同一键多次出现并非一定错误；重复投递可能是传输保证的一部分。真正需要报警的是同一键映射到相互冲突的不可变业务内容、同一键导致多次副作用，或生产者对不同事件复用了身份。对冲突应隔离并调查，而不是让“先到者赢”悄悄遮盖数据错误。

因此，选择去重键时先问事件身份由谁承诺，再问副作用是否和记录原子提交，最后问旧事件可在多久之后回来。本文的 JSON 和仓库例子用于解释规范，并未运行消息代理或数据库事务；上线前还需用实际 CloudEvents SDK、传输协议、存储约束和故障注入确认。CloudEvents 给出跨生产者的身份坐标，应用仍须自己证明在这个坐标上如何只执行一次副作用。
