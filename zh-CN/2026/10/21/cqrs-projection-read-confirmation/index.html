CQRS 写入后：用版本或状态确认读侧是否跟上

把写入提交与读投影追上拆开，用操作版本、投影水位和失败分支设计可信反馈。

正文

核心要点

  • 写端成功不证明分离的读投影已经显示新值。
  • 投影水位必须代表相关变更已成功应用，不能只是见过最大版本。
  • 页面应区分待同步、已确认、被拒绝与超时查询状态。

用户提交地址修改，写入接口返回成功，随后立刻刷新资料页，却仍看见旧地址。若系统使用 CQRS 分开写模型和读投影，这个画面未必意味着写失败：读侧可能尚未消费更新。微软的 CQRS 模式说明明确指出，读写数据库分离时，读数据可能不会立即显示最新更改。设计要回答的是“用户如何知道写已被接受、读侧何时跟上”，不能把一个成功 HTTP 响应当作两个状态都完成的证据。

把“成功”拆成两个可观察事实

设用户把配送地址由 A 改成 B。写模型验证权限与地址后提交版本 v18，返回 operationId=op-73 和 writeVersion=18。事件随后进入投影器，读库当前仍停在 v17，页面查到 A。写入已持久化与读投影已追上是两个事实；前者可由写库提交证明，后者需要读侧水位或所需字段版本证明。若客户端马上把 A 渲染为“修改失败”，可能诱使用户再次提交并造成重复。若客户端直接永久显示 B 而从不核对投影，又会掩盖投影故障。

一个可用的合同是写接口返回操作身份与版本，读接口附带 projectionVersion。客户端在资料页比较目标 writeVersion=18 与当前 projectionVersion=17：若读侧落后，显示“地址已提交，正在同步”，保持本次输入 B 的局部预览但标明其来源；当读侧达到或超过 18 且返回地址 B，再改为“已在资料页确认”。若等待超时，给可查询的操作状态和支持路径，避免只让加载动画旋转。版本必须属于可比较的同一聚合或流；把全站无关事件的计数与单个用户地址版本直接比较，可能错误地认为已追上。

{"operationId":"op-73","writeVersion":18,"status":"accepted"}
{"address":"A","projectionVersion":17}
{"address":"B","projectionVersion":18}

这些响应是设计示例，不是某个现成 CQRS 框架的标准字段。第一行如果返回 HTTP 202，根据 RFC 9110 的 202 定义，它表示请求已接受处理，但处理未完成；实际写库是否已经提交，要由 API 自己明确定义。同步写入已完成也可以返回其他合适状态码，不能把 202 当成强制的 CQRS 信号。更重要的是，页面必须能区分“写被接受”“写已提交”“读已同步”“业务被拒绝”这些状态，不能一律写“保存成功”。

水位可用的前提与失败分支

投影器应在应用完事件及相关读模型事务后推进水位，不能先更新水位再写地址；否则页面看到 projectionVersion=18 却仍得到 A。若多个投影分别更新资料页和搜索索引，应分别有水位，不能用资料页水位证明搜索结果已更新。若更新过程中发生重试、乱序或重复，投影器还需凭事件身份及聚合版本防止旧值覆盖新值；水位单调增长的承诺要在对应投影的数据写入之后成立。跨分片系统没有单一可比较的全局版本时，可返回每个聚合的修订号，或直接提供按 operationId 查询的投影确认状态。

考虑一个反例：写入版本 18 对应地址 B，但投影错误地跳过该事件，随后处理无关版本 19 并把水位写成 19。如果系统只比数字，页面会误判 B 已可见。因此水位必须表达“到该版本为止需要的变更均已按序且成功应用”，或对目标操作另存已应用标记；不能把“见过最大版本”冒充“连续完成版本”。业务还需要定义投影永久失败时如何告警、重放与纠正，以及读侧无法恢复时是否改用写侧查询作为临时确认路径。微软的模式页提醒处理消息时还要考虑重复、失败和重试，正是这类错误可能延长不一致窗口。

另一个反例是写入本身被异步业务规则拒绝。如果 API 只表示“已接收命令”，客户端不能马上断言地址 B 已持久化。操作状态需要区分 pending、committed、rejected，并提供可解释的拒绝原因；若写端同步完成权限和数据校验，响应可直接返回已提交修订号。站内条件写入与冲突处理讨论并发覆盖的写侧边界；本篇讨论的是写端已经做出决定后，读侧怎样给用户可信反馈。

为产品选择确认策略

不是所有读页面都需要等待。新闻浏览、趋势报表能接受数秒延迟时，可显示更新时间并让读侧自然收敛。编辑后的个人资料、转账收据或权限状态更接近“读己之写”的期待，可暂时用写响应构成局部回显，并在后台核对投影；对高后果操作，应提供可审计的操作状态，而非仅靠乐观 UI。若必须同步读到新值，可以短时轮询目标投影水位或按操作号等待，但要设超时与退避，避免大量客户端在慢投影上同时猛刷。超时并不自动等于写失败，错误文案必须保留这个区别。

接口文档最好把轮询终点写成判定式。例如 GET /operations/op-73 返回 writeStatus=committed 及 profileProjection=applied，同时给出应用的修订号 18。页面只有在状态为 applied、读模型实际含 B 且版本可对应时，才宣布“资料页已更新”；若状态是 rejected，显示原因并撤回局部预览；若状态长期 pending，保留操作编号供客服与用户复查。这一设计比“每两秒刷新资料”更容易发现投影漏处理，因为刷新次数只说明客户端试过，操作状态才说明服务端处理到了哪一步。

当然，操作状态服务也可能落后或故障。它不能独自充当资金到账、权限生效等高后果事实的唯一证据。对这类流程，需要明确最终权威记录在哪里、读投影是否只是展示，以及异常时由哪个后台流程对账。若用户在两个设备上操作，第一台的局部回显不会自动出现在第二台；服务端的操作编号和可查询状态则能跨设备保持同一解释。这样 UI 设计不是简单增加一个“同步中”徽标，而是给最终一致性的各个阶段建立可追踪的事实来源。

验收测试应先故意暂停投影器：提交 B 后确认写端修订号为 18、读端仍为 17、页面显示待同步而不是失败。再恢复投影，确认资料页真的返回 B，且水位证明对应操作已应用。随后注入重复事件、乱序、投影写入失败和操作拒绝，检查是否错误确认或无止境等待。还应测重启后水位持久化与同一操作查询结果是否稳定。本文没有连接真实读写库或运行故障注入；这些是产品合同和验收方案，实际延迟、版本粒度与状态 API 需按现有架构实现。只有用户可见的状态能和系统内部事实一一对应，CQRS 的最终一致性才不会变成“刷新试试”的托词。
