WeakMap 不提供存活清单，也不能替资源按时收尾

区分对象附属元数据、可枚举缓存和显式资源生命周期，用编辑器面板示例检查强引用与清理责任。

正文

核心要点

  • WeakMap 需要已知键，无法提供存活对象清单。
  • 弱关联不承诺回收时机，也不关闭外部资源。
  • 枚举、容量与确定性清理要有显式管理机制。

如果需求是“列出当前缓存的所有对象，再按时关闭它们的连接”，WeakMap 不适合作为唯一管理结构。它允许凭已知键查找附属值，却不提供枚举键的接口，也不承诺不可达对象何时被回收。弱引用关系可以减少由映射本身造成的保留，不能替代资源关闭、容量限制或可观察的存活清单。

弱键解决的是哪条引用

ECMAScript 的 WeakMap Objects 规范说明，观察条目需要提供对应的键，不能从容器获得键的枚举；从不可访问到实际移除之间也允许由实现决定延迟。本篇按读取时的在线规范讨论对象键这一常见用法，不把垃圾回收的具体时机写成语言保证，也不推断所有运行时的内存曲线相同。

假设编辑器为每个面板对象保存一次昂贵计算的布局结果。面板仍由界面持有时，可以用该对象作为键读取结果；面板被移除且其他地方也不再保存它后，不希望布局表成为唯一让它一直存活的原因。这里的元数据天然跟随面板身份，没有“给我所有面板”的业务要求，WeakMap 就符合这个关联方式。

// 说明性代码，未运行
const layoutByPanel = new WeakMap();
function remember(panel, layout) {
  layoutByPanel.set(panel, layout);
}
function read(panel) {
  return layoutByPanel.get(panel);
}

现在产品增加一个“所有打开面板”的管理视图，需要数量、排序与逐一关闭。不能从上面的映射推导出这张清单；调用者必须已经有 panel 才能查值。若为枚举再建立一个长期保存所有 panel 的数组，这个数组又成为强引用来源。新增数组可能是业务所需，但此时应承认生命周期由显式注册与移除负责，不能仍宣称弱映射保证这些面板会自动消失。

这里还要区分键相等与业务身份。两个内容相同、分别创建的面板对象不是同一个对象键。若重新解析数据生成新对象，再拿它查旧条目，不能因为字段相同就期待命中。按业务编号跨请求复用缓存时，通常需要另一个以编号为键、具有明确失效规则的结构；对象附属元数据和跨对象缓存不是同一个问题。

为什么清理责任不能交给回收器

假设面板打开时启动了一个轮询计时器，并持有网络订阅。关闭面板时应有明确动作取消计时器、解除订阅、更新可见清单。仅把元数据放进 WeakMap，不代表这些外部动作已发生。若计时器回调仍强引用面板，它本身还可能让面板继续可达；检查弱映射不会消除来自其他地方的引用。

反例是“每十秒读取 WeakMap 的 size，把少掉的数量当作连接已经关闭”。WeakMap 没有这样的 size 清单，回收延迟也不是计时合同。即使借助运行时诊断观察到某次内存下降，也不能外推每次关闭都在十秒内完成。验收应看明确的关闭路径是否撤销实际资源，不应把不可预测的回收当作业务确认。

对于缓存预算，选择也不同。若要求最多保存若干条、淘汰最久未用项或展示命中率，强引用 Map 配合明确的容量和删除策略更易表达合同，但需要承担保留责任。如果只是为外部拥有的对象添加私有元数据，不需要枚举与数量，WeakMap 更符合关联目的。选择标准是是否需要管理集合本身，而不是哪个名字看起来更省内存。

有时两种结构可以共存：可枚举注册表仅保存当前开放面板，关闭时明确移除；弱映射保存跟随对象的辅助计算。评审时为每一份引用写出持有者和移除时机。这样注册表的必要保留就不会被误判成泄漏，而漏掉的注销也不会被 WeakMap 掩盖。对象数量、资源数量和业务任务数量最好分别定义，避免拿一种指标代替另一种。

能验证什么，不能证明什么

确定性测试可以创建一个面板对象，保存布局，凭同一对象读取，再用显式 delete 验证业务失效路径。另建字段相同的对象，确认它不会凭字段相等命中。这些结果验证映射操作和身份设计，不验证垃圾回收完成。清理测试则应调用实际关闭接口，检查计时器、订阅和注册表是否被释放，重复关闭是否保持可解释状态。

内存诊断可以检查意外保留路径，例如全局数组、闭包或事件监听器是否仍指向关闭对象。需要比较多轮打开关闭后的趋势并保留运行时版本，但单次快照不能证明所有引用已消除。压力大小、回收策略和工具本身都会影响观察。本文没有执行内存快照或运行垃圾回收，更没有测得所谓降低多少内存的效果。

并发工作仍可能让大量数据合法存活。一个等待消费的任务即使使用弱映射保存附属信息，也可能被队列本身持有。相关的Node.js 背压与保留数据从生产速度解释资源预算，适合排查“结构已经换弱，内存为什么还高”的另一半原因。弱键不是对整条处理链的容量承诺。

如果必须在关闭时执行操作，还能用 WeakMap 吗？

可以保存附属数据，但关闭操作应由明确的生命周期接口负责，并在需要时持有执行动作所需的对象。状态应区分尚未关闭、正在关闭、关闭失败与已关闭，不以条目是否仍可查代替资源状态。如果资源关闭失败，应按业务设计重试或报告；对象以后是否回收不能把失败改写成成功。

显式删除还需要一个业务对照：两个模块持有同一个面板对象，模块甲删除它在弱映射里的布局，模块乙再次凭该对象读取，预期应看不到那份布局。对象仍由乙持有并不妨碍这个显式失效动作；同样，失效动作也没有关闭乙拥有的任何资源。这样能把映射状态、对象可达性和外部资源状态分成三个可观察的问题。

若模块乙仍需要布局，可以按业务规则重新计算并写回，而不是把 miss 一概解释成回收器已经工作。测试应记录是谁调用 delete、谁负责重建及重建失败怎样反馈。一个可解释的失效合同，比尝试从条目缺失猜测内存状态更稳定，也更适合跨模块协作。

本文是对象关联与资源管理的设计推演，没有运行示例。交付前应先回答是否需要枚举、是否需要容量、是否需要确定时机的外部动作。三者只要有一项成立，就要提供相应的显式管理机制，不能把它们留给弱映射的名字去承诺。
