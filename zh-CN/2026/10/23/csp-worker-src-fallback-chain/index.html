CSP Worker 限制：读懂 worker-src 的回退顺序

从缺席回退、Blob 入口和后续请求三个边界，定位 Worker 创建与任务失败。

正文

核心要点

  • worker-src 缺席才依次回退。
  • Blob 入口按实际方案和目标 API 验证。
  • 入口许可不等于后续数据请求许可。

页面脚本能从允许的域加载，不表示 Worker 入口也会被同一条规则放行。检查 CSP 时，先找是否存在 worker-src；它缺席时才按 child-src、script-src、default-src 的顺序寻找回退规则。找到一条适用指令后被拒绝，不会因为后面另有宽松规则就继续获得许可。

回退发生在指令缺席时

MDN 的 worker-src 说明列出了这条回退顺序，并说明指令约束 Worker、SharedWorker 与 ServiceWorker 脚本来源。CSP Level 3 工作草案给出对应指令与来源匹配机制。引用的草案版本为二〇二六年九月十六日，具体浏览器实现还应在产品支持范围中验证；本文没有运行浏览器安全策略实验。

假设页面来自 app.example.test，响应头声明默认只允许自身，页面脚本另外允许一个资源域，同时给 child-src 配置禁止。此时没有 worker-src，Worker 判断先遇到 child-src 'none'，不再拿后面的宽松脚本来源当许可。主脚本照常运行与工作线程入口被挡，可以同时成立。这是根据回退机制推演的配置反例，不是真实站点故障日志。

Content-Security-Policy: default-src 'self'; script-src 'self' https://assets.example.test; child-src 'none'

这个头部只用于解释冲突，不是一份可直接部署的完整安全模板。若需求确实允许本站的专用 Worker 入口，应评估显式配置 worker-src，让它与框架用途分开表达。这样修改的是 Worker 来源边界，不需要为了一个工作线程随手放开全部子资源。是否还要允许其他来源，应根据真实构建输出和信任关系判断。

明确回退也方便评审升级。过去没有 worker-src 时，团队也许一直依赖 script-src；后来添加 child-src 管理框架，可能改变 Worker 的有效回退来源。配置文本看似只新增了一种资源限制，实际影响却跨到另一个入口。修改前列出依赖回退的资源类型，修改后再核对真正生效的响应，能避免把隐含约定留给浏览器替团队决定。

blob 入口要按真实 URL 方案评估

假设构建工具把一段代码变成 Blob，再通过 blob: 地址创建专用 Worker。此时网络面板上主脚本来自资源域，并不能说明 Worker 入口也是那个 HTTPS 地址。应查看创建 Worker 时实际使用的 URL 类型。如果需求允许这种生成入口，可评估类似 worker-src 'self' blob: 的显式方案许可；这里不假定所有浏览器都会以相同方式把 blob 归入 'self'。

允许 blob: 的代价也要说清楚：它扩大了可被用来启动 Worker 的来源表达式范围，并不验证生成代码的业务用途。若工具链可以产出独立、可维护的同源 Worker 文件，也值得比较路径可审计性和部署成本。选择不应只看哪一行能让控制台错误消失，还要能解释被允许执行的代码来自哪里。

示意来源列表不能越过 Worker API 自身的限制。给某种 URL 方案 CSP 许可，不等于该方案对所有 Worker 类型、所有注册方式都有效；尤其不能把专用 Worker 的 Blob 示例直接推广成 ServiceWorker 注册保证。应分别记录目标 API、入口地址、构建方式和支持浏览器，验证这一具体组合，而不是泛称“全部 Worker 已开放”。

入口放行后，内部 fetch 也会自动放行吗？

不会仅因入口被允许就得到任意网络权限。Worker 脚本入口和内部请求属于不同检查对象，需要分别核对适用的 CSP、网络来源、跨源策略和服务端授权。普通网络加载的 Worker 与 Blob 等特殊入口的策略继承方式也需要区别；排查时查明保护哪一个执行环境，不把页面响应的一条来源列表当成所有后续请求的通行证。

比如报表 Worker 已启动，却在读取报表数据时失败。应先观察错误属于入口创建、脚本依赖加载还是数据请求，再核对该步骤实际受哪项策略影响。盲目向 worker-src 继续添加数据接口域，可能完全没有修改真正失败的规则。反过来，放宽数据连接规则也不会补上被禁止的 Worker 入口。

CSP 响应头参考进一步说明 Worker 的策略归属和多策略组合。若页面同时收到多个 CSP，新增一条宽松策略不等于覆盖原有严格限制。代理、应用与静态托管层都可能交付头部，调查应保存实际响应头组合并识别每条限制的来源。报告模式只报告潜在违反，也不能当成强制模式已允许或已阻止的行为。本站十月十日的报告模式发布检查可以帮助把配置观察和真正阻断结果分开。

验证可建立四个受控样本：同源静态专用 Worker、构建产出的 Blob 专用 Worker、未允许来源的入口、入口成功但内部数据请求被拒绝。分别记录收到的政策、实际入口方案、创建结果和后续工作结果。再从真实发布入口读取响应，防止本地配置正确却在代理层收到另一版本。

策略归属也影响回滚。若应用团队添加了显式Worker许可，边缘代理仍交付旧政策，回滚应用代码可能既不能解释也不能解除阻断。维护记录应能定位最终响应由哪一层生成，哪一层添加额外限制，以及该配置何时刷新缓存。测试阶段可以分别保存直接源站与公开入口的头部，再说明用户真正经过哪个入口；两份都拿到并不代表任意入口都可被绕过使用。

对于功能降级，也应在创建失败处给用户明确结果。报表线程被拦时，可以提供重试、较小任务或由服务端生成等已经实现的替代路径；如果没有替代能力，就准确提示当前任务不可用。不要让界面一直显示正在准备，也不要在后台反复启动同一被禁止入口。安全策略拒绝是需要被产品处理的状态，不是只能留在开发控制台的一条消息。替代路径本身仍需权限和数据完整性验证，不能因为被称为降级就免除检查。

这些样本都未在本文执行。验收要能回答“哪条指令通过哪条回退链约束哪次请求”，以及“Worker 是否真正完成了所需任务”。把指令补全是配置变更，启动成功是运行结果，任务完成还需要单独的业务证据。
