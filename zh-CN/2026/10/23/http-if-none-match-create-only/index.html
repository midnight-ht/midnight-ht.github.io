先查不存在，为什么仍可能覆盖别人创建的资源？

用条件创建解释并发竞争、412 后的恢复以及删除后名称复用的边界。

正文

核心要点

  • 先查后写无法单独消除竞争。
  • 星号条件与业务幂等回答不同问题。
  • 删除后同名重建需要独立身份策略。

先查询资源不存在，再发一个普通 PUT，并不能保证只创建而不覆盖。两次请求之间，另一位客户端可能已经创建了同一地址。若业务意图是“仅在目标尚无当前表示时创建”，可以用带星号的 If-None-Match 表达前置条件，但服务端必须真正评估它，并在写入竞争中保持条件有效。

星号表达的是不存在，不是某个旧版本

RFC 9110 第 13.1.2 节说明，星号用于判断目标资源是否存在当前表示；该条件为假时，不能执行请求方法。对于 PUT 这样的非 GET、HEAD 方法，条件失败对应 412；不要把缓存验证场景的 304 拿来表示创建冲突。星号也不能与实体标签列表混合成一个合法条件值。

这里的判断对象是请求目标资源，不是数据库中任何看起来相关的记录。假设地址表示某租户下的配置文件，服务端需要明确租户和名称如何组成资源身份。如果路由忽略租户、大小写归一规则不一致，或者两个别名指向同一业务对象，头字段本身不能修复这种身份歧义。先有稳定对象，条件才有可解释的作用范围。

下面是未执行的并发创建例子。两个部署客户端都想在同一租户创建一份名为 nightly 的计划。甲准备的内容是每晚一点运行，乙准备的是每晚两点运行。它们先后查询，都得到不存在，然后几乎同时发送创建请求。如果普通 PUT 允许替换，最终可能只留下后写入的一份，而先前的成功响应不能解释配置为何改变。

若两个请求都带只创建条件，服务端应在同一竞争边界裁决存在性和创建。甲先取得创建资格后，乙不能再依据自己稍早的查询结果覆盖甲；乙收到条件失败，保留原草稿，并展示当前计划供人比较。谁先成功由真实执行顺序决定，示例没有预设某一客户端永远获胜。

一种候选存储实现是用与资源身份对应的唯一约束配合原子插入，把唯一冲突映射为符合条件请求的结果。另一种是有条件写入的存储接口。关键不是工具名字，而是检查不存在和提交之间不能让第二个创建者也得到相同资格。只在应用进程内加一个锁，多实例部署时未必覆盖竞争；应核对锁实际保护的范围。

有了条件创建，重试就一定返回原来的成功吗？

不一定。假设甲已经创建，但响应在网络中丢失。甲重试相同条件请求时，目标已经存在，因此可能得到条件失败。这不说明甲第一次没有成功，也不保证当前资源就是甲创建的那份。客户端需要查询并比较业务关联信息，判断是自己的既有结果还是别人的对象，不能看到 412 就自动改名重建。

若业务希望相同意图重放时拿到原结果，需要另外定义请求标识、内容摘要和保存期限。只创建条件避免的是覆盖已经存在的目标；业务幂等处理的是重复意图怎样关联。两者可以配合，但不能把一个请求头当作跨数据库、通知和外部系统的一次执行保证。若创建还触发发送邮件，应分别处理竞争失败和已提交但回执丢失的副作用。

反例是客户端为了让第二次成功，去掉条件再发送普通 PUT。这把用户的“不要覆盖”改成了“可以替换”，即使接口最后返回绿色成功，也违反了最初意图。若用户确实决定替换，应先看到已有对象、确认差异，并走明确的更新流程。有关完整表示与局部修改，可参看PUT 与 PATCH 的更新契约。

删除后重新创建，还是原来的对象吗？

这是头字段无法替业务回答的追问。原对象被删除后，地址可能重新没有当前表示，因此只创建条件可以再次成立。但旧链接、旧任务或外部系统若仍把这个名字视为同一计划，就可能误关联新对象。需要决定资源身份是否包含不可复用标识，删除后是否保留名称占位，以及恢复与新建怎样区分。

例如旧计划已经触发一批执行，随后删除同名新建。若后台仅按名称查配置，就可能让旧任务读到新的两点计划。更清楚的设计是为每次创建分配不可混淆的业务身份，将名称作为可读入口，或在不允许复用时保留相应约束。这里是生命周期分析，不是规范要求所有接口使用同一种主键。

验证可以并发发送两个内容不同的条件创建，确认只有一个资源版本取得创建结果，另一个没有覆盖，也没有触发创建后通知。再测试响应丢失后的重试、先删除再创建、路由别名和不同租户。记录实际表示内容及副作用，不能只数一个成功状态和一个失败状态便结束。

服务端还应明确缺少前置条件的写请求是否允许替换。如果只有新客户端携带保护，旧脚本仍可无条件覆盖，同一资源就存在两套互相破坏的约定。可以为只创建入口拒绝不符合约定的请求，或把创建与更新明确分流，并给维护脚本同步迁移计划。验收应让旧入口也参与竞争，检查保护是否覆盖全部写入者，而不是只证明某个新界面的两次点击碰巧安全。

本文没有运行 HTTP 服务或数据库并发测试。实际接入时还应核对框架是否读取条件头、代理是否传递、服务是否在提交前真正执行判断，以及错误映射是否向客户端保留恢复信息。只有从请求意图一直到持久化竞争都证明“存在就不覆盖”，这个头才成为有效契约；否则它只是网络面板里一行没有执行力的文字。
