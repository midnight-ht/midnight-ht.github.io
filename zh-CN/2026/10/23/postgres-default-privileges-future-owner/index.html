PostgreSQL 默认权限没给新表：先查建表时的角色

以迁移角色和读取角色为例，区分已有表授权、未来对象默认权限及角色成员关系，并设计正反向验证。

正文

核心要点

  • 默认授权只影响未来对象，已有表需单独评审。
  • 建表时当前角色决定采用哪组默认权限。
  • 用不同创建角色和真实读取角色验证授权边界。

迁移账号已经加入表所有者角色，新表却仍然拒绝报表账号读取，先查创建对象时的当前角色。PostgreSQL 18 的默认权限按创建角色应用；成员关系不会把其他角色的默认权限自动叠加进来。修复应同时回答两件事：已有对象缺什么授权，以及以后由谁创建对象，不能用一次默认设置代替这两份检查。

默认权限在哪个时刻生效

PostgreSQL 18 的 ALTER DEFAULT PRIVILEGES 文档明确把它限定在未来创建的对象。可以为当前数据库全局设置，也可以限定到指定模式。它不是持续运行的权限同步器，修改规则后，已经存在的表不会重新计算授权。因此，“执行命令成功”和“旧表能够查询”没有直接的因果保证。

对象创建时只采用当前角色的默认权限，不继承它所属角色的默认权限。这里需要分清登录身份、当前执行身份和对象所有者。在部署脚本里记录一个账号名仍不够，连接建立后是否切换角色、切换发生在建表之前还是之后，都会影响应检查哪组规则。若迁移工具每次新开连接，前一连接的角色切换也不能当作后一连接的证据。

假设数据库里有 app 模式，owner_role 负责拥有表，migrator 可以切换到它，reporter 只需要读取。角色和模式已由管理员按最小权限准备好，以下是尚未执行的推演。先由 migrator 直接创建 app.before，再给 owner_role 设置默认 SELECT 授权。app.before 的权限不会因此补齐；随后若仍由 migrator 创建 app.after，也不能仅凭 migrator 是 owner_role 的成员就期待 reporter 得到权限。

正确的设计可以选择统一创建身份：迁移事务里先切换到 owner_role，再创建 app.future。默认权限也明确针对 owner_role 配置。或者团队确实允许多个创建角色，就分别维护它们的默认授权。两种方式的差别是维护对象数量，不是一个命令更有权威。不要在故障后随手给 PUBLIC 全部权限，这会把一个报表读取需求扩大成所有用户的访问。

-- 说明性 SQL，未执行；需由有权修改该角色默认权限的身份运行
ALTER DEFAULT PRIVILEGES FOR ROLE owner_role IN SCHEMA app
  GRANT SELECT ON TABLES TO reporter;
-- 旧对象需要另行评审其对象级授权
GRANT SELECT ON app.before TO reporter;

这个例子还假设 reporter 已具备访问 app 模式所需的 USAGE。表的 SELECT 不负责替代模式访问权限；否则默认授权可能已经正确，读者仍在另一个门槛失败。把表名写成模式限定名也有价值，它避免搜索路径把验证查询引向另一张同名表。管理员查得到数据只能证明管理员的访问，不能代替 reporter 的结果。

为什么在模式里撤销仍未收紧

同一份官方文档说明，按模式设置的默认权限会加到全局默认权限之上。如果全局已经授予某权限，在单一模式里 REVOKE 不能把全局授予抵消。需要先理解现有来源，再决定是否修改全局规则以及怎样恢复其他模式的合法需求。这种加法关系使“只改 app 一行”未必能表达团队想要的例外。

例如团队希望 reporter 默认读大部分模式，但禁止读 payroll。若全局规则已给 reporter 未来表的 SELECT，直接给 payroll 配一条模式级撤销，并不能构成拒绝例外。可评审的方案是撤掉过宽的全局默认授予，再对确实需要的模式逐一授予，并检查既有表。这里没有建议直接变更任何现有数据库，例子用来指出授权模型是否能表达需求。

方案选择还要看对象类型。对表配置的默认权限不等于已经为序列、函数或其他对象完成授权；不能为了省事把所有对象类型都给同样的权限。若业务只做只读分析，就先交付表读取这一条合同。业务写入需要什么序列权限，应由实际语句和对象模型决定，再单独验证。范围清楚，比一段看似完整却无业务根据的授权模板更可维护。

如何证明以后不会再漏一张表

在可丢弃数据库安排三个对象：规则设定前的旧表、由预期角色新建的表、由另一个角色新建的对照表。保存创建时的 current_user、对象所有者、默认权限清单和 reporter 的实际查询结果。预期应在执行前写下：旧表依赖显式授权，预期创建角色的新表应可读，对照角色不应因成员关系凭空获得相同默认规则。验收应包含拒绝路径，不能只看一次成功查询。

还应重新开一个迁移连接重复创建，用来发现角色切换只发生在手工会话里的问题。连接池、迁移框架与定时任务可能采用不同入口，验收样本要来自真正的建表入口。核对失败原因时，区分模式访问、对象权限和行级安全；相关的运行身份与 RLS 检查解释了表权限通过之后的另一层边界。

改默认权限后，是否要把所有旧表一起授权？

不应从“默认规则改了”直接推出这个动作。先列出 reporter 的业务范围，再筛选旧对象；历史表可能包含不应进入报表的数据。未来对象和已有对象可以采用同一份权限意图，但它们的执行步骤与检查结果要分别保存。若需要批量补齐，先审查具体模式、表集合与回退方案，避免把不相关的旧表带进来。

权限交接时还应保留创建过程的记录，而非只查询今天的所有者字段。假设发布后有人把表所有权转交给统一维护角色，最终清单能说明当前归属，却不能单独还原创建时采用了哪个角色的默认规则。可在迁移日志中记录切换角色与建表操作，配合变更编号保存当时的默认权限快照；下一次排查才不必从最终状态猜测历史。

验收通过后也要给创建入口指定维护者。新增第二个迁移工具或后台分区任务时，应重新核对它的创建身份，而不是沿用报表账号上次查询成功的结论。权限规则的变更审查需要同时列出受影响创建者与读者：只知道谁获得权限，不知道谁负责产生对象，仍然容易在下一次发布遗漏新表。

本文核对的是 PostgreSQL 18 官方机制，没有创建角色、执行迁移或运行查询。最小交付证据应能把创建身份、未来规则、已有授权和读取结果关联起来；只有默认权限命令的成功回执，仍不足以说明下一次迁移会按相同身份工作。
