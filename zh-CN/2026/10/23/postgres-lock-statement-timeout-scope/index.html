PostgreSQL 等锁超时与语句超时：两个预算怎样配合

用双会话迁移推演区分每次锁等待和整条语句预算，检查事务局部设置、取消后的回滚与连接复用。

正文

核心要点

  • 锁等待限制按每次获取锁的尝试计时。
  • 语句期限与客户端总期限覆盖不同阶段。
  • 错误后处理事务，再验证连接复用与参数恢复。

一条迁移只愿意等锁半秒，但允许拿到锁后运行数秒，应分别设置锁等待预算与整条语句预算。PostgreSQL 18 的 lock_timeout 只在等锁时计时，并分别约束每次获取锁的尝试；statement_timeout 约束语句处理时间。把两个值设成相同大小，通常会让语句超时先发挥作用，失去区分故障阶段的意义。

预算覆盖的时间段不同

PostgreSQL 18 客户端默认设置文档区分了这两个参数。锁等待既可能来自显式锁定，也可能来自语句隐式需要的锁。lock_timeout 不是整条事务累计等待上限，更不是查询运行时间上限。若语句多次获取不同锁，每次尝试都有自己的预算，不能把某个值直接当成整次迁移的最长耗时。

statement_timeout 则从服务端收到命令到完成进行约束。文档还区分简单查询消息与扩展查询协议的计时细节，因此应用从点击按钮到收到结果的总时长，不能直接与服务端参数画等号。连接池排队、网络传输和应用重试可能发生在这个计时范围之外。产品若承诺请求期限，还要给这些阶段留出明确预算。

假设 inventory 表已有数据，会话甲开启事务并持有阻碍结构修改的锁。会话乙准备为它增加一列：业务允许这项迁移稍后再试，不愿长时间堵在锁队列；拿到锁后的语句则允许较长时间处理。以下数值仅是未执行示例，不是生产推荐值，也不构成耗时测量。

-- 会话乙；说明性步骤，尚未运行
BEGIN;
SET LOCAL lock_timeout = '500ms';
SET LOCAL statement_timeout = '5s';
ALTER TABLE inventory ADD COLUMN review_note text;
COMMIT;

若甲持续占锁，乙预期先遇到锁等待限制。若锁及时释放，乙继续执行，五秒语句限制仍可约束后续处理。反例是把锁限制设为十秒、语句限制仍为五秒：长锁等待尚未走完自己的额度，语句期限已经到达。没有报锁超时，不能据此判断语句未曾等待锁。

取消以后，连接是否还能继续用

不要把超时异常等同于自动完成业务回滚。应用在显式事务里收到错误后，应按实际事务状态结束或恢复事务，再把连接交回池。若采用局部恢复，保存点必须在可能失败的语句前建立，恢复边界也要符合业务允许的原子性；不能在失败后继续发送下一条业务语句，假设它一定可以执行。

SET 文档说明 SET LOCAL 的效果到当前事务结束为止，无论提交还是回滚。这使它适合一段迁移或一个事务的预算，而普通会话级设置可能在提交后继续影响复用连接。局部设置也不是永久属性：如果回滚到设置之前的保存点，相应设置会被撤销，恢复后需要核对当前值。

例如批处理在保存点之后设置短锁等待，失败后回到更早的保存点，再运行另一项变更。若代码只记得“前面已经配置过”，第二项可能在不同预算下执行。设计时可选择在稳定的外层事务入口设置，或者在每次局部重试前显式重建预算。选择依据是恢复路径，而不是减少几条 SQL 的美观程度。

失败报告也应保留哪个期限触发、语句身份、事务动作与重试安排。迁移超时可以表示本轮没有完成，不能直接显示“新增列成功”。对于连接中断造成的结果未知，先查最终模式状态和迁移记录，再考虑重试。本文没有执行锁竞争，未证明任何特定驱动已经正确处理这些状态。

用对照实验分开验证两种限制

拟议验证需要两个独立会话。甲先持锁，乙使用上述局部参数运行目标语句，记录服务端错误、开始结束时间与事务状态；确认乙结束事务后，再释放甲。接着在没有竞争的情况下重复目标操作，用一条适合测试环境的耗时语句检查语句期限。两种失败分别制造，才能知道处理器是否把它们都误判成连接丢失。

还要测试“等锁很短、执行很长”的路径，以及同一语句需要多个锁的路径。不能仅拿一个阻塞例子推断全局累计上限。检查客户端自身的取消期限，确保它与数据库预算的先后关系是有意设计的：若客户端更早放弃，却没有取消服务端操作，应用看到失败而数据库继续工作的情况仍需处理。

连接复用验证可以在事务结束后查询当前参数，并运行一条普通请求，检查短迁移预算是否污染后续业务。把参数值和真正使用的数据库身份一同保留，避免测试连接与运行连接不一致。需要局部继续处理时，可参考保存点与部分导入报告，该文讨论的是结果合同，本篇解决的是等待与执行的预算范围。

超时后能否立刻自动重试？

只有当操作的重试语义、事务恢复和总期限都已定义时才适合安排。若锁来自持续运行的维护任务，立即反复重试可能只是重新排队；若多个实例同步重试，还会形成额外竞争。可以按业务选择延后、退避或交给人工窗口，但次数和间隔应来自运行约束，本文不指定通用秒数。需要保留已耗费的总预算，不能让每次新语句都把用户期限重新开始。

预算还应包含失败收尾。假设客户端给本次操作六秒，语句上限已经用去五秒，应用还需要处理错误、回滚并返回可解释结果。若清理阶段没有剩余额度，不能简单把连接放回池当作结束。数值仍是假设，具体余量应由真实驱动和运行环境的观察确定；设计重点是取消发生后还有动作需要完成。

可以让测试在取消后立刻发起下一项独立工作，检查它是否取得干净连接、是否被残留事务或错误设置影响。同时保留原操作的终态与清理结果，避免新请求成功覆盖了旧请求清理失败的事实。若连接无法确认可复用，应由连接管理层按明确规则处置，而不是让业务代码猜测它已经恢复。

这份说明限定 PostgreSQL 18 文档，没有运行双会话实验、驱动取消或连接池测试。验收时先确认等待、执行、事务恢复和客户端期限各由谁负责，再记录各自证据。一个超时参数只能约束它定义的时间段，无法独自承诺整次操作何时安全结束。
