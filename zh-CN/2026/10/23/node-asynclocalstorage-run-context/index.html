AsyncLocalStorage：用 run 划定请求上下文的入口

从两个同步事件监听器解释 run 与 enterWith 的范围差异，设计异步创建点、上下文丢失及跨请求对照检查。

正文

核心要点

  • 在 run 回调内创建需要继承上下文的工作。
  • enterWith 会影响当前同步执行余下部分。
  • 交错完成、嵌套恢复和异常桥接需要独立验证。

请求日志需要携带编号时，优先在请求入口用 AsyncLocalStorage.run 包住启动工作的回调。enterWith 会改变当前同步执行余下部分的上下文，同一个事件里后续监听器也可能读到它。把“设置一次编号”当成局部变量赋值，容易遗漏这个影响范围；选择 API 前，先画出工作在哪里创建、谁应该继承编号。

上下文边界跟着执行路径走

本篇核对的是Node.js v26.12.1 的异步上下文文档，只讨论 run、enterWith 和 getStore，未把新增接口套给旧版运行时。run 在给定存储值的上下文里同步调用回调，其中创建的异步操作能够沿相应路径访问存储；离开这段调用范围后，外围同步代码不应被当成同一请求继续使用。上下文不是每个 JavaScript 模块都能随意共享的请求身份变量。

假设服务收到甲、乙两个请求，编号分别为 req-a 与 req-b。每次入口创建独立存储对象，在 run 回调里启动读取配置、数据库调用和响应记录。甲的数据库较慢，乙先返回。希望看到的是两条链各自保持编号，完成顺序可以交错，而不是把进程最近一次收到的编号放进全局变量。这个例子没有运行，编号与先后顺序是说明性输入。

import { AsyncLocalStorage } from 'node:async_hooks';
const context = new AsyncLocalStorage();
function handle(requestId) {
  return context.run({ requestId }, async () => {
    await performWork(); // 示例业务函数，未实现也未执行
    return context.getStore()?.requestId;
  });
}

这里 handle 返回 run 回调的返回值，调用者仍需等待或处理该 Promise 的失败。上下文传播不负责把异步操作变成成功，也不负责取消它。若入口只启动工作却丢弃 Promise，编号可能仍然正确，业务错误却没有接收方。两类问题都应进入验证，但不能用一条带编号的日志证明整个请求已经完成。

enterWith 的反例发生在同一次同步分发里

官方文档给出明确提醒：在一个事件处理器里 enterWith 后，后续事件处理器也会在这个上下文执行，除非已明确绑定其他上下文。因此文档建议没有强理由时优先用 run。这里并不需要两个网络请求恰好并发，单次同步事件分发就足以出现超出预期的可见范围。

例如通知总线上第一个监听器为订单甲 enterWith，第二个监听器只是统计通知数量，开发者以为它不属于订单处理，却从 getStore 读到了订单甲。随后第二个监听器创建异步任务，错误标签还可能继续传播。判断错误发生在“哪个监听器有权设定上下文”，而不是日志库是否正确打印了对象。run 可以把第一个监听器的工作包在明确回调内，让同步外围保有原来的上下文。

也不能从“对象独立”推断内容自动不可变。把同一个存储对象分配给不同请求，或让下游任意改写其 requestId，会破坏原来的归属设计。建议每个入口创建最小的上下文，把稳定编号与可变业务数据区分开。上下文用于关联，不是可信授权凭证；用户传入的编号应与认证得到的身份分别处理，避免调试便利演变成身份来源。

如果已有库需要跨边界调用后来保存的回调，就检查回调执行时的上下文，而不是只看注册时。自定义 thenable、回调桥接和第三方异步机制可能需要按官方的上下文丢失排查方法定位，再评估 AsyncResource 等桥接工具。不要在每个丢失点随手 enterWith，这可能修好一条日志，同时扩大另一段同步执行的范围。

怎样验证编号不串也不丢

拟议测试给甲乙两条工作链设置受控等待，先让乙完成，再释放甲。每个阶段记录预期编号与 getStore 的实际值，断言归属而不是断言日志顺序。再增加嵌套 run：内层返回后，外层同步代码应重新看到外层值；最外围则按初始化状态判断。这样能检查恢复范围，避免只覆盖单一成功链。

事件总线测试可以安排两个同步监听器，分别比较 enterWith 与 run 包裹第一监听器工作的结果。保留第二监听器读到的值，作为范围差异证据。异步丢失测试则在每个可疑桥接边界前后读取 getStore，找到第一次改变的位置。需要用实际运行时和依赖版本执行，不能只依据示例注释认定某个库已兼容。

运行配置也会影响复现。测试若从启动参数、环境变量或工作进程入口改变初始化方式，应记录最终使用的配置，而非配置文件外观。相关的环境变量字符串解析说明如何避免把文本开关误当布尔值；它不解决上下文传播，却能帮助确认用于复现的入口真的启用了预期行为。

能靠上下文自动传递到另一台服务吗？

不能把当前进程中的异步存储当成网络协议。跨服务调用需要明确将允许的关联信息写入约定的请求字段，再由接收方校验并建立自己的上下文。哪些字段可传播、哪些要重新生成，应按信任边界决定。进程内编号连贯，与分布式链路可关联，是不同的验收目标；本文的 run 示例没有实现网络传播。

创建点的对照尤其有用：一组工作在进入请求入口之前就已启动，另一组在 run 回调内才启动。不要把外围预先启动的任务，仅因后来在回调里等待它，就假设整个任务来源都已改变。测试应在各自真实回调中读取上下文，分别核对预期；若确需把外部任务结果关联到请求，在受控接收点明确建立归属，而不是修改任务的历史。

异常恢复也要有自己的记录。让嵌套回调同步抛错，再在外层捕获位置读取存储，检查外围上下文仍符合设计。另让异步工作拒绝，确认错误处理日志保留正确请求编号，调用者又能收到真实失败。编号没有丢与异常没有丢是两个断言，只检查其中一个容易把日志正确误认成处理完整。

本文没有执行 Node.js 请求、事件分发或依赖桥接测试。交付时应提供入口、异步创建点、嵌套恢复和异常路径的实际记录。先让每条工作链的边界可解释，再用日志判断任务进展，才能避免编号打印得整齐却指向了错误请求。
