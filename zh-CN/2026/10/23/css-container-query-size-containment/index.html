屏幕很宽，侧栏卡片为什么仍然挤成一团？

从槽位分配、尺寸包含和祖先选择解释容器查询，并验证长文本与基础回退。

正文

核心要点

  • 组件可按所在槽位而非整个视口调整。
  • 设置包含之前先说明尺寸来自哪里。
  • 查询匹配不能替代真实内容与浏览器验证。

卡片放在宽屏侧栏里仍然拥挤时，先检查它按哪个尺寸切换布局。视口查询看到的是整个窗口，容器尺寸查询看到的是选中的祖先容器；同一组件出现在主栏和侧栏，可以因此采用不同布局。但查询生效之前，容器需要具有可推导的尺寸，不能一边让内容决定宽度，一边又用该宽度反过来决定内容布局。

谁来给组件分配空间？

CSS Conditional Rules Level 5 的容器查询章节定义查询容器及相关属性。设置 inline-size 类型可以建立内联轴尺寸查询容器，同时引入相应包含行为；查询作用于后代，而不是让容器用自己的尺寸条件改写自己。本篇核对的是二〇二六年十月八日工作草案，不能把草案文字视为所有浏览器版本的实现保证。

资料位置也有版本边界。旧资料常把容器查询指向 CSS Containment Level 3，当前编辑稿已把相关内容迁往 Conditional Rules Level 5。因此维护文档时应追到实际定义所在章节，不只因为旧链接还能打开便继续当作现行定义。这不意味着旧教程中的所有代码都失效，而是核验依据需要更新；最终仍要对照目标浏览器验证实际使用的特性。

假设一张商品卡有图片、名称、价格和操作按钮。以下代码与尺寸均为未执行示例。它在主栏获得较宽槽位，在侧栏只获得较窄槽位。若使用“大于某视口宽度就横排”的规则，两张卡会同时横排，侧栏却根本没有足够空间。容器查询让布局判断移到槽位，从而表达“这里有空间才横排”。

.card-slot { container: product / inline-size; }
.card { display: grid; gap: 1rem; }
@container product (min-width: 32rem) {
  .card { grid-template-columns: 10rem minmax(0, 1fr); }
}

这里的三十二只是示意阈值，不是通用手机或平板断点。槽位由外部页面网格分配宽度，卡片先采用单列，命名容器达到条件后才使用双列。外层负责空间，内层负责内容，这个分工比在组件里反复猜测侧栏宽度更容易复用。阈值应该从真实内容在何处开始拥挤来选择，而不是照抄设计稿设备名称。

为什么加完包含属性，布局反而缩了？

尺寸包含会改变内容参与尺寸计算的方式。如果容器原本靠内部内容撑开内联尺寸，增加内联尺寸包含后，再期待同一批内容决定它的宽度，前提就发生了变化。应检查父级网格轨道、伸缩分配、明确尺寸或其他外部约束，确认容器从哪里得到空间，而不是看到塌缩就一味减小查询阈值。

也不要为图方便把所有容器都设成同时查询两个轴。块轴如果原来依赖内容自然增长，引入更强尺寸约束可能改变高度计算，需要另有尺寸来源。仅按横向可用空间调整普通卡片时，通常先考虑内联轴；需要高度条件时，再解释高度是谁提供的。这是组件设计取舍，不是某一个属性值能普遍解决布局问题。

反例是在卡片自己上建立容器，并试图在自己的查询条件中改变同一卡片。若期望它选中自己，就会误解祖先查询边界。另一种情况是嵌套组件增加了更近的合格容器，未命名查询开始根据另一层尺寸生效。给重要槽位命名，并在开发工具中确认实际选中的祖先，可以让封装变更后的行为更容易解释。

同一个断点为何装不下另一种语言？

假设中文商品名很短，英文名却有较长型号；两列布局在同一槽位宽度下，按钮可能被挤出。容器查询只根据条件选择规则，不会替团队评估文字是否清楚或操作是否可达。要用长标题、无空格编号、价格变体和放大文字检验布局，并处理最小内容尺寸、换行与溢出，不能把查询命中当作内容验收。

这也决定回退策略。先写可使用的单列基础布局，再把增强规则放进查询，可以让不支持该查询的环境仍有合理内容顺序。是否需要额外特性检测，应结合目标浏览器与实际 CSS 决定；不要为了演示新特性删除基础样式。某个浏览器支持属性，也不代表所有相关查询功能、嵌套和单位都已覆盖，应测试实际用到的组合。

验证应在同一个视口内同时放主栏卡和侧栏卡，分别改变槽位宽度，检查它们能否独立切换。随后调整窗口、改变字体大小、切换长文本，并检查边界宽度前后是否抖动或溢出。若出现异常，记录实际容器尺寸、匹配规则和选中祖先，不只截一张“宽屏正常”的图片。先记录每个盒子的真实尺寸，才能判断是外层分配不足还是内部内容无法换行。

插槽边框和内边距也需要明确口径。设计稿分给侧栏的总宽度，并不一定等于卡片可用的内容宽度；若在外层增加留白，阈值可能提前或推后触发。建议把外层分配尺寸、容器可查询尺寸与内部文字区域分别记录，避免同一个“三百像素”在评审中指向三个边界。具体计算可接着看组件宽度与盒模型契约，再决定容器应放在含留白的外壳还是内层槽位。

本文没有运行浏览器或渲染测试。交付前还要在支持清单内记录实际浏览器版本、失败样式和回退结果。先证明槽位从外层取得尺寸，再证明组件按这个尺寸变化，最后检查内容与操作仍可使用；这三步之间少掉任何一项，都可能留下一个语法正确、实际却挤成一团的容器查询。
