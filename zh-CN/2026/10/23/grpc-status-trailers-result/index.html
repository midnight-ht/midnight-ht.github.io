HTTP 已经返回 200，gRPC 调用为什么仍然失败？

结合尾部终态、部分消息与代理监控，避免把响应开始当成调用完成。

正文

核心要点

  • 首部与消息不能替代调用终态。
  • 部分结果的使用必须有明确业务契约。
  • 指标应按最终调用状态分类并避免重复计数。

gRPC 调用收到 HTTP 200 或第一条消息，都不能直接记为调用成功。应用需要继续等待调用的最终状态，区分正常完成、业务拒绝和传输中断；监控也应读取同一层结果。如果代理只记录响应首部就结束计数，失败可能被藏在一片绿色的 HTTP 成功率里。

为什么状态放在消息后面？

gRPC over HTTP2 协议说明的响应部分允许首部、零到多条消息和尾部，也允许立即报错时只发送尾部形式的响应。最终状态位于尾部，即使正常完成也要发送。这里讨论原生 gRPC 的 HTTP/2 传输，不把浏览器侧其他封装协议当作相同报文格式。

流式调用开始返回内容时，服务端可能还没有完成全部工作。后续读取失败、权限条件不满足或计算错误，都可能发生在首部之后。因此首部回答的是一次协议响应已经开始，终态才回答整个调用怎样结束。把首条消息当成终态，会抹掉后来失败的事实；把 HTTP 成功率换个名字叫 RPC 成功率，也不会修复这种信息缺口。

设想库存服务向调度系统流式返回三个仓库的可用量。以下是未运行的假设时序，不是真实抓包。响应先发出 HTTP 200，随后返回甲仓和乙仓的数据，读取丙仓时发生错误，最后以非成功的调用状态结束。调度系统已经收到两条合法消息，但不能因此宣称三个仓库的查询全部成功。

可把这个时序压成一段未执行的报文示意：先是 :status: 200，接着两条仓库消息，最后是 grpc-status: 13。其中十三是 INTERNAL；若调用正常结束，终态可为 grpc-status: 0，即 OK。编号含义可核对 gRPC 状态码表。这不是实际抓包，也不表示所有第三仓读取错误都应映射为 INTERNAL；这里选择它只为演示首部成功后仍可终态失败。零代表调用正常完成，业务还需按返回内容判断是否有货，不等于调拨或扣库存已经发生。

消费端可以选择暂存收到的数据，等终态正常后一次提交完整结果；也可以按接口约定逐条展示，并在失败时明确标注不完整。两种策略的区别不在于谁更先进，而在于用户是否允许利用部分结果。如果调度必须比较所有仓库才能分配订单，就不能在看到甲仓有货时偷偷结束等待；如果用途只是逐仓展示状态，则可保留已经确定的部分，同时显示未完成范围。

完整例子还需要给失败留位置。假设终态失败时，页面把两条数据保留下来，提示“已收到两个仓库，第三个未完成”，并阻止“按最低库存分配”这一依赖全集的动作。重试入口应注明是重新获取全部仓库，还是只补缺少的一个；合并时按仓库标识和查询版本判断，不能把新查询的一条记录与旧快照两条记录拼成一个看似同时刻的总量。

没有收到尾部，是否意味着默认成功？

不能。在网络中断、代理不兼容或服务端异常退出时，客户端可能没有获得可用的最终状态。协议栈会按其规则报告错误，应用应读取所用库暴露的完成状态，不能自行把缺失尾部补成成功。若做诊断工具，还需区分真实收到的状态与库根据异常合成的状态，避免把推导结果写成服务端的原始回执。

最容易遗漏的是监控链路。网关在首部出现时记一次二百，业务客户端随后收到失败；两套指标都可能忠实反映各自观察，但“服务全部成功”的结论超出了前者范围。应明确分母：进入网关的请求数、已经结束的调用数，以及按最终 RPC 状态分类的调用数。仍在流中的调用不应过早算入已成功完成。

反例是服务端捕获所有异常后强行返回正常状态，只在普通消息中塞一个错误字符串。客户端若按正常状态统计，就会认为协议层成功。业务可以有自己的结果类型，但必须在契约中明确哪些结果属于调用成功、哪些需要失败状态；不能让不同团队各自猜测。协议状态并不能替代业务含义，业务文本也不能让丢失的协议终态恢复可观察性。

收到失败后可以直接重试整条流吗？

先看前面的消息有没有触发副作用。若每条库存消息都让消费者创建一项调拨，重试可能重复创建前两项。即使读取本身没有副作用，旧数据已经进入用户决策，也需要说明替换还是追加。应定义关联查询、去重标识与重试范围，而不是把某类错误统一写成“再连一次”。这里是消费端设计建议，协议没有替应用保证一次业务效果。

调用超时又是一条独立边界。截止时间与下游停止讨论等待何时结束和工作是否停止；本篇讨论收到的结果能否代表完整成功。客户端已经报超时，不证明远端事务回滚；收到正常终态，也仍需要按业务返回值确认具体操作结果。这两项检查应在验收中分别命名。

拟议测试应覆盖无消息正常结束、单条正常结束、多条后失败、立即失败，以及首部后连接中断。分别记录客户端完成回调、收到的消息数量、最终状态、代理访问日志和指标分类。再将请求经过真实待用代理，确认其不会丢掉尾部；直连可用不能证明整条生产路径可用。本文没有执行服务、代理或抓包测试，不提供特定语言库的兼容保证。

还要定义调用何时从进行中进入统计终态。如果仪表盘先按首部计成功，结束时再补一条失败，分母就可能重复。可为每次调用保留唯一关联，在完成边界提交一次最终分类，并单独观察正在进行的数量和持续时间。长连接业务尤其不能把尚未结束的流永久当作成功样本；否则某一批失败只有关闭连接时才突然集中出现，曲线的时间含义也会改变。

交付时可以挑一个“二百之后失败”的场景，让业务界面、调用日志和告警都显示同一事实。若只有抓包工具知道失败，使用者仍看到全部完成，那么状态虽然在网络上存在，却没有进入产品判断。先把终态送到真正决定成功的那一层，再谈成功率目标；否则更漂亮的图表只会更稳定地记录错误答案。
