Playwright 登录态快照：IndexedDB 要显式纳入，sessionStorage 另算

区分认证快照覆盖、独立上下文恢复与服务端授权，避免把文件存在当成登录成功。

正文

核心要点

  • IndexedDB 快照选项需要支持版本并显式启用。
  • sessionStorage 需要额外恢复契约。
  • 以独立上下文和受保护读取验证恢复。

登录步骤显示成功，保存的状态文件也存在，新建浏览器上下文却又跳回登录页，先核对凭证实际存在哪里。Playwright 的 storageState 不是整个浏览器会话的镜像；应用依赖 IndexedDB 身份数据时，要在支持的版本里显式保存它，而 sessionStorage 不属于这个快照接口的持久化范围。

快照覆盖什么，要从应用身份路径反推

BrowserContext API为 storageState 的 indexedDB 选项标注了一点五十一版本的加入时间，启用后将 IndexedDB 纳入状态快照。当前在线 API 还有其他随版本增加的选项，因此不能把某个旧教程列出的字段当成永久完整清单。本文聚焦 cookies、localStorage、可选 IndexedDB 与未自动覆盖的 sessionStorage；先查项目锁定的版本，再决定接口能保存哪些真实需要的状态。

官方身份验证指南另外说明，sessionStorage 需要按应用需求自行保存与加载。这个区别不会因为文件名叫 auth.json 就消失。应先观察登录完成后客户端从哪类存储恢复身份，再看应用是否还需要向服务端交换会话或刷新令牌。页面显示头像可能来自本地缓存，不能单独证明下一次受保护请求已经通过。

假设一个测试应用把会话相关数据放在 IndexedDB 中，进入订单页前会从那里读取身份并向服务器确认。测试在真正登录完成、订单身份区域出现后调用下面的示意接口，然后使用文件创建独立上下文。代码没有执行，不包含真实账号、凭证或生成的认证文件。

await context.storageState({ path: 'playwright/.auth/order-user.json', indexedDB: true });
const restored = await browser.newContext({
  storageState: 'playwright/.auth/order-user.json'
});
const restoredPage = await restored.newPage();
await restoredPage.goto('https://example.test/orders');

保存动作只是中间状态。随后应断言受保护页面显示预期账户，再执行一个只读的受保护请求并核对返回对象权限。若只在原上下文里刷新页面，旧的内存状态、仍打开的页面或会话资源可能帮助它继续工作，无法独立证明文件足够恢复身份。新上下文应从快照开始，不能沿用原页面作为成功证据。

为了定位缺失，可以先保存一次不含 IndexedDB 的对照快照，再保存显式包含它的版本，只比较是否覆盖身份所需的存储类别和恢复结果，不把实际令牌写进报告。假设前者回到登录页而后者能读取订单，这支持的是该应用在该环境里的存储依赖判断；并不说明所有登录失败都由这个开关导致。

哪些失败与快照内容无关

若服务端会话已经过期，再完整的本地数据也可能只能换来未授权响应。另一个反例是快照生成在重定向尚未结束时：文件确实可解析，却捕捉到临时身份。还有应用把关键状态放在 sessionStorage 或纯内存中，启用 IndexedDB 对它没有帮助。先区分“缺字段”“保存太早”“凭证失效”和“恢复后应用没有采用数据”，才能选择修复位置。

快照还与源有关。测试从一个域保存 localStorage，再从另一个测试域打开页面，不应预期原源的数据自动变成新源身份。环境切换也可能改变 cookie 作用域与服务器会话。应把生成入口、恢复入口和账户用途一起记录，避免拿开发环境文件解释测试环境授权失败。

对于确实依赖 sessionStorage 的应用，可以评估官方指南中的自定义初始化办法，但要限定目标源和初始化时机，不能给每个子框架无条件注入身份。此时需要维护的是一套额外恢复契约，不能在报告里说 storageState 已经自动处理。本站十月十五日的标签页存储生命周期进一步解释了 opener 副本和后续独立修改，复制数据与恢复业务会话不是同一件事。

服务端撤销后，旧文件还应该能登录吗？

不应该把旧文件能恢复页面当成撤销失败的唯一证据。先检查服务端是否拒绝了受保护请求，再看客户端是否及时清除旧展示并返回正确入口。若只是缓存头像还在，属于展示状态；若真实接口仍允许被撤销会话读取受保护订单，才是需要继续调查的授权结果。验收必须同时观察界面和权威响应。

反过来，不能为了让测试稳定而无限延长真实会话寿命。测试账号应有明确用途，快照按环境、权限与有效期管理，失效时重新执行获准的登录路径。并发测试若共享一个会被修改的服务端账号状态，即使各自浏览器上下文隔离，也可能互相改变订单和权限。只读场景与有副作用场景应按业务隔离需求选择账号策略。

认证文件可能足以让持有者获得会话能力，应避免进入源码仓库或公开构建产物。日志只记录文件标识、生成时间、环境和恢复结果，敏感值不应成为调试截图。删除本地文件不等于服务端会话撤销，服务端撤销也不保证所有本地缓存立即消失，两项管理动作要分别验收。

还可以为状态生成单独设置失败条件：若账户区域出现但受保护读取被拒绝，生成任务就不应把文件标为可复用。若用户在生成与消费之间修改角色，恢复测试应接受权限已变化的事实，而不是通过缓存旧角色强行满足断言。文件管理记录可以保留预期权限类别，却不能替服务器决定当前权限。把这项检查放到状态生产端，能减少后续很多测试同时拿到坏文件而形成的噪声；但每条敏感业务测试仍要观察自己的授权结果。

本文没有生成或恢复真实登录态。建议记录一次完整的登录完成条件、快照选项、独立上下文恢复、受保护读取和失效路径，并保留失败分类。文件存在回答的是“写入过”，独立恢复与授权结果才回答“这份状态是否足以支持预期测试”。
