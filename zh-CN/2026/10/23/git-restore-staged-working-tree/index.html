git restore 先选来源，再决定改索引还是工作区

用三份不同文件内容解释取消暂存与丢弃工作区修改的区别，给出部分暂存、路径范围及前后差异验证。

正文

核心要点

  • 来源与恢复位置分别决定操作效果。
  • 取消暂存保留工作区，但会改变差异比较基准。
  • 用磁盘内容和两份 diff 验证精确路径。

只想取消暂存并保留文件修改时，git restore --staged 的目标是索引；默认不带目标选项的 git restore 则恢复工作区内容。两者不能凭“撤销一下”互换。操作前把来源和写入位置分别说清楚，尤其是在同一个文件既有已暂存修改、又有未暂存修改时，才能避免把保留工作误做成覆盖工作。

一个文件有三份可比较的状态

Git 的 git-restore 官方手册说明，指定 --staged 时默认从 HEAD 恢复；否则默认来源是索引。未选择目标时，恢复位置是工作区；同时指定 --staged 和 --worktree 会恢复两处。--source 可以显式指定另一份来源。这里的“恢复”不是历史搜索，也不保证找回所有曾经写过但未保存的文本。

设想一个已经跟踪的 config.txt。HEAD 里写的是 mode=old，暂存区已经改为 mode=review，工作区又继续改为 mode=experiment。三个名字代表三份不同内容，以下为未执行的练习推演。若执行只针对索引的取消暂存，索引回到 old，而工作区仍是 experiment；review 那份不再作为本次提交的暂存内容存在。

若在最初三份状态下直接恢复工作区，默认来源是索引，因此文件会变成 review，未暂存的 experiment 会被覆盖。若同时恢复索引与工作区，默认来源是 HEAD，两者都会向 old 对齐。命令作用不同，错误选择不会因为都叫 restore 就变得可逆。真实重要修改应先保存可恢复副本或形成经过审查的提交，再做可能覆盖文件的动作。

# 说明性命令，未在当前仓库执行；path/to/file 为待确认的精确路径
# 仅取消暂存，保留工作区内容
git restore --staged -- path/to/file
# 以下会覆盖该路径工作区中的未暂存修改，执行前必须确认意图
git restore --worktree -- path/to/file

命令后的路径分隔符有助于把路径与选项区分开，但不能替你判断范围。把具体文件换成点号会扩大到目录范围，多文件任务里可能影响别人的改动。若团队共享工作区，应先逐项核对文件归属；“只操作一个仓库”并不意味着仓库里所有修改都属于当前任务。

部分暂存为什么让结果更难读

同一文件的不同片段可能分别进入索引与工作区。取消整个文件的暂存，会改变这些片段的提交选择，但保留工作区当前内容；它并没有自动恢复“上次编辑前”的文件。交互式补丁模式可以选择片段，却仍需理解它比较哪份来源与哪处目标，不能当作无风险的撤销按钮。

一个实际选择问题是：要把某段修改从下次提交拿出来，还是要从磁盘文件删掉它？前者针对索引，后者涉及工作区内容。若只想重组提交，先选择索引操作，然后重新查看暂存差异；若确实想放弃实验代码，先核对工作区差异并确认需要保存的部分，再选择精确范围。把提交编排和文件清理混成一次命令，通常更难审查。

还应考虑显式来源。指定某个旧提交作为来源而不移动分支，可以把那个版本的路径内容写到选定位置；这不是把仓库整体回到旧版本，也不会自动撤销之后提交的业务效果。旧文件放进新代码可能产生接口不匹配，需要正常测试。若目的是撤销已经共享的提交，应另行选择适合共享历史的方案，不能把恢复一个文件当成完整历史反向操作。

用两份差异验证，而不是只看状态字母

拟议练习应在可丢弃仓库准备 old、review、experiment 三种内容。每次操作前保存 git diff 与 git diff --cached，分别记录工作区相对索引、索引相对 HEAD 的差异，再记录文件实际内容。操作后重复比较，确认目标变化和应保留部分同时成立。状态列表只能概括哪里有变化，不能解释保留下来的具体文本。

测试时还要加入一个无关已跟踪文件，确认路径范围没有波及它。若要研究新建文件、删除文件或合并冲突，应分别准备独立场景，不把正常已跟踪文件的结果直接套过去。官方手册还有未合并路径及来源缺失时的规则；在这些状态下先理解具体选项，避免用常规流程强行覆盖冲突证据。

取消暂存也不是临时备份。若准备切换任务，需要保存工作区与索引选择，应评估相应保存方式。相关的stash 跟踪范围讨论未跟踪与忽略文件是否进入条目；它与本篇的来源目标模型相邻，但不提供 restore 已覆盖内容的自动救援保证。

取消暂存以后，为什么 diff 里反而出现更多修改？

因为比较基准改变了。原来工作区只比索引多出的 experiment 部分，在索引回到 HEAD 后，会连同原先已经暂存的修改一起出现在工作区差异中。差异变多不等于文件被额外改写。查看磁盘内容和暂存差异，才能判断是显示范围变化，还是实际内容变化；这正是保留两份差异的原因。

如果执行顺序颠倒，结果也可能不同：先取消暂存再恢复工作区，后一步的默认索引来源已经变成 HEAD；而在初始状态直接恢复工作区，来源仍是 review。应把每一步之前的真实状态当作输入，不能仅记住命令名称。需要重复实验时从同一套初始内容重建，而不是在上一次结果上继续比较。

如果取消暂存是为了拆成两个提交，后续应按本次提交的意图重新选取片段，再看完整暂存差异，而非把原文件整体加入一次了事。举例说，配置修正应先提交，实验开关要继续留在工作区；重新暂存后需要同时确认前者确实进入索引、后者确实没有进入，文件整体能构建却不能代替这两个选择断言。

检查还可保留一份本次计划说明，列出预期提交路径和暂不提交内容。若工具自动格式化同一个文件，应重新核对片段边界，因为格式变更可能让原本独立的修改连在一起。最终提交预览应对应当前索引，不能拿取消暂存之前保存的差异截图作为批准对象；截图里的内容可能已经不再是下一次提交的真实输入。

本文没有执行 restore 或改动当前仓库，练习结果仍待实际验证。操作结束的最小证明应包含所用来源、目标位置、精确路径、保留的磁盘内容和最终暂存差异。这样“取消暂存”才是一个可核对的结果，而不只是看到终端没有报错。
