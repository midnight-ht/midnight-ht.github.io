OpenTelemetry 跨服务传播：注入格式和提取格式必须相认

按注入、传输、提取和操作创建定位断链，同时保留并发归属与信任边界。

正文

核心要点

  • 传播与导出是两条不同路径。
  • 格式相同还要正确采用父上下文。
  • 并发归属与外部字段信任需要单独检查。

两个服务都安装了 OpenTelemetry SDK，仍可能各自产生一条链路。先核对发送端写入载体的传播格式，是否正是接收端读取的格式，再确认接收方用提取结果创建了正确的父子关系；安装 SDK 本身没有证明这几个边界已经连通。

传播是一次格式约定，不是后台拼图

OpenTelemetry 上下文传播说明把发送端向载体写入上下文称为注入，把接收端从载体读取上下文称为提取，并以 W3C Trace Context 的 HTTP 头为例解释跨服务关联。载体可以是请求头，也可以是双方约定的消息元数据。应采用适合实际协议与 SDK 的传播器，而不是期待采集后端根据请求时间自动猜出父级。

传播和导出在不同位置。传播把上游身份送到下一个操作边界，导出把已经形成的遥测送到接收系统。两个服务都能把 Span 发到同一后端，只说明各自出口可工作；若入站没有获得上游上下文，后端仍可能看到两条独立 trace。反过来，父级传递正确也不保证所有 Span 已被采样、成功导出并留在查询范围。

假设订单服务调用库存服务。订单侧创建出站操作后，用 W3C 格式把当前上下文写进 HTTP 请求；库存侧却只按另一种格式读取。请求业务可以成功，库存侧也可以生成自己的 Span，但提取不到预期上游身份，因此无法仅凭“双方都有数据”断定它们应该已经连起来。这是未运行的机制示例，没有调用真实订单服务。

把格式差异具体化：发送端按 W3C Trace Context 推荐标准写入 traceparent，接收端仅启用 B3 多头格式，读取 X-B3-TraceId 与 X-B3-SpanId。例如下面只有 W3C 字段的假设输入，没有接收器期待的 B3 字段；这不是抓包，也未运行任何 SDK。

traceparent: 00-11111111111111111111111111111111-2222222222222222-01

为这个例子设计一条完整检查链：先确认订单侧注入时的当前操作；再核对出站载体是否有预期字段；到库存入口确认字段未被网关过滤；接着核对所用提取器与格式；最后在库存操作创建时检查父上下文是否来自提取结果。每一步都要有自己的观察，不能只看链路界面最后是否画出一条线。

格式相同，也可能在下一步丢失

假设现在两端都采用 W3C 格式，入口也确实收到字段，但库存代码先创建根 Span，随后才提取上游上下文。此时修好传输没有修好建模顺序；需要按所用 SDK 契约在创建操作时采用正确上下文。另一个反例是在异步分支中丢掉当前上下文，导致后来发送请求时注入的是空上下文或另一个任务。单请求演示正常，不能覆盖并发任务的归属错误。

因此验证应至少交错两笔不同订单。分别记录安全的请求身份与导出的 trace、span、parent 关系，检查下游没有把订单甲的上下文带入订单乙。只用一个请求反复重试，往往能证明“有字段”，却无法证明“字段属于这次工作”。这里建议的关联字段不要包含完整客户资料或认证令牌；追踪身份本身也要遵守访问范围。

网关、代理和消息中间件是第三种边界。业务字段可以通过，不代表传播元数据也被保留。若消息系统没有专门元数据位置，需要明确双方编码、大小限制和提取时机，避免把传播内容混入业务负载后直接交给业务解析。不要为了接上线条而随意改变消费者协议；协议兼容与追踪关联都应有自己的验收对象。

升级格式时应一次切换所有服务吗？

不一定。一次全量切换减少过渡组合，但要求各方同时发布；分阶段迁移则需要明确哪些边界接收旧格式、哪些发送新格式，以及两种输入并存时怎样选择。具体组合传播器的能力和冲突规则应依据所用 SDK 核对，不能凭“支持多个格式”推导出会自动合并冲突父级。

评审可以列出三种请求：只带旧格式、只带新格式、同时带两种且身份不同。前两种验证迁移覆盖范围，第三种迫使团队写清优先级和拒绝策略。若没有冲突处理约定，双写也可能把一次调用解释成不同关系。该测试是迁移设计，不是本文已经完成的多 SDK 兼容认证。

还要把父子关系与多来源关系分开。单次同步调用可以延续明确的上游上下文；多消息合成一个批次时，不能因为传播器提取到多份身份，就把它们都当成单一父级。本站十月十七日的Span Link 与父级关系讨论了这种建模选择。传播保证有材料可用，如何表达因果仍由操作边界决定。

外部传来的 baggage 应该原样转发吗？

不应把格式合法当成内容可信。应按信任边界决定接收、过滤和转发哪些字段。传播文档提醒外部上下文可能被伪造，出站信息也可能暴露内部身份或业务信息。业务授权必须由认证与权限机制决定，不能因为 baggage 写着管理员或某个租户，就据此放行请求。

为接入边界设计允许字段与大小策略，区分内部调用和公开入口。需要调试时，保存是否存在、采用哪种格式、如何处置以及对应配置版本，避免把任意入站内容复制进无保护日志。删掉不必要的传播数据可能使部分关联变少，但这是可说明的信任选择，不应暗中回填虚构父级让界面看起来完整。

错误调查时也别用业务请求标识代替传播字段直接拼接 trace。请求标识有助于跨系统查找同一业务，但一次业务可能经过多次重试与异步批次，未必对应单一父子树。可以把它作为独立检索条件保留，并据实际操作关系解释不同 trace 为什么属于同一调查。这样即使传播暂时失效，仍有调查入口，也不会把修复观测等同于修改历史因果。需要恢复关联时，应标明补充线索的来源和局限。

本文没有运行 SDK 或采集后端。验收记录应包含两端版本、传播器配置、载体通过情况、提取结果、操作关系和导出查询结果，失败时标出哪一步断开。把“有 SDK”“有请求头”“有 Span”和“关系正确”分开，才知道下一次改动要修哪一段。
