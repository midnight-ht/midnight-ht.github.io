GitHub Actions 步骤失败后，outcome 与 conclusion 应该读哪个？

区分容错前的测试结果与容错后的步骤结论，用完整工作流保留报告并显式阻断，再检查跳过、取消与脚本吞错。

正文

核心要点

  • outcome保留容错前结果，conclusion描述应用容错后的结论。
  • 报告可以继续生成，核心检查仍应要求明确成功。
  • 上下文字段无法恢复被脚本吞掉的失败或证明报告属于本次运行。

GitHub Actions 的步骤加上 continue-on-error 后，原始执行失败与最终步骤结论可能不同。要判断测试是否真的通过，应读取容错前的 outcome；要解释流水线为什么继续执行，再查看应用容错后的 conclusion。报告收集可以继续，发布条件仍应保留测试失败这件事实。

同一个步骤为什么有两个结果？

GitHub Actions 的 steps 上下文说明区分两种属性：outcome 是应用 continue-on-error 之前的结果，conclusion 是应用之后的结果。文档给出的典型情形是原始失败而最终结论成功。本篇依据二〇二六年十月二十九日核对的在线文档讨论步骤级容错，没有运行托管工作流，也不把步骤语义推广成所有 Job 级策略。

这两个字段回答不同问题。测试命令返回非零，说明该命令没有按成功条件结束；允许继续则表示维护者希望后续步骤仍有机会执行。后者可以用于收集报告、清理临时资源或运行补充诊断，却不能替测试重新作出通过判断。若部署条件只检查被容错改写后的结论，就可能在报告还写着失败时继续发布。

先明确失败是否真的允许被忽略。一个实验性兼容性检查可能暂时不阻断合并，但团队应明确它的性质和退出计划。核心测试则不应因为需要保留报告就被永久改成可忽略。两种情形都能使用相同的语法，差别来自项目的质量承诺，而不是字段名称自带的授权。

让报告继续，让门禁保留失败

下面是没有执行的最小示意工作流，不依赖项目仓库和第三方 Action。它用固定失败命令演示状态交接；实际项目需替换成自己的测试，并核对报告保存方式。

name: inspect-step-result
on: workflow_dispatch
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - name: Deliberate failure
        id: tests
        continue-on-error: true
        run: exit 1
      - name: Record result
        if: ${{ always() }}
        env:
          STEP_RESULT: ${{ toJSON(steps.tests) }}
        run: printf '%s\n' "$STEP_RESULT"
      - name: Enforce successful test
        if: ${{ !cancelled() && steps.tests.outcome != 'success' }}
        run: exit 1

假设第一步正常启动并执行 exit 1，原始状态为 failure，容错后的结论可以为 success。第二步输出两个状态，目的只是保留可解释记录。最后一步要求测试必须为 success，因此原始失败会重新成为阻断条件。报告显示成功写出，并不覆盖测试结果。这个设计刻意让“执行完诊断”和“达到质量要求”成为两项分别可观察的结果。

示例最后检查的不是仅仅等于 failure，而是不等于 success。原因在于步骤结果还可能是 skipped 或 cancelled。若某个前置条件让测试根本未运行，不能用“没有失败”代替“确实成功”。工作流取消的处理需要明确政策：此处不在已取消时故意制造另一个执行步骤，取消状态本身也不能作为可发布证明。

报告上传若需要即使上一步失败仍执行，应按所选 Action 和条件语义安排。但不应在所有步骤上机械添加 always。已经取消的运行若继续进行昂贵网络操作，可能拖延停止；已经失去所需文件的步骤也可能只制造第二个错误。报告步骤的运行条件与部署步骤的运行条件需要分别评审。

哪一种容错方案适合当前检查？

如果失败后只需要默认停止，保留普通失败传播通常最直接。若只是想保留诊断材料，可以让收集步骤使用适当的状态条件，而不改变测试步骤本身的失败结论。若确实要在同一 Job 里继续更多诊断，再使用步骤级容错并在末尾集中核对原始结果。第三种方案更灵活，也增加维护责任：新增一个检查后，要记得把它纳入最终判断。

失败路径里容易出现另一个漏洞：测试脚本自己捕获异常、写出一份报告，然后返回零。此时 outcome 也会是 success，它不能看穿脚本已经吞掉的错误。要修复的是命令退出约定，不能期待读取另一个上下文字段恢复丢失的信息。Shell 管道、包装脚本和测试工具各自的退出行为，也需要在项目环境里验证。

把 Job 级 continue-on-error 与步骤级机制混为一谈同样危险。Job 的依赖、矩阵汇总、必需检查和部署入口有自己的条件。本文例子只处理单 Job 内的步骤结果；跨 Job 传递时，要明确输出来自哪里、取消如何表示，以及哪个 Job 真正承担最终阻断。不要因为一个步骤演示成立，就宣布整个仓库的分支保护已正确。

原始退出码怎样进入报告？

outcome 能区分成功、失败、取消和跳过，但它不是命令的完整退出码。如果需要区分测试断言失败与运行器错误，可以在受控包装脚本中记录退出值到文件或步骤输出，再按约定返回或交给末尾门禁。记录动作必须发生在原始命令结束之后、Shell 提前退出之前；否则“准备写出退出码”的脚本也可能根本没执行到那一行。

这种包装应保持两个通道：机器可判断的最终退出状态，以及供人调查的退出码与报告。报告文件存在只能证明生成过某份内容；还应绑定运行、提交和检查身份，避免拿上次生成的文件解释这次失败。本文没有提供实跑回执，不建议未经对照就把包装脚本复制到生产发布流程。

待执行验证至少覆盖明确成功、明确失败、前置条件导致跳过和人工取消；每种输入都分别核对原始状态、最终结论、报告是否产生以及发布入口是否被阻断。另加一个故意吞错返回零的对照，确认团队知道上下文不能修复脚本承诺。关于报告与部署制品的身份交接，可参看构建产物身份核对。先让失败证据持续存在，再决定哪些后续动作获准继续。

还要决定报告生成本身失败是否阻断。若质量判断依赖这份材料，不能只因原始测试成功就放行；应分别保存测试结果与报告结果，再由明确规则汇总。假设磁盘写满使报告丢失，界面应显示证据缺失，而不是沿用旧报告。受控验证可故意让报告目录不可写，确认最终结果符合项目约定，并且诊断步骤不会把原始失败覆盖成一个含糊的后续错误。
