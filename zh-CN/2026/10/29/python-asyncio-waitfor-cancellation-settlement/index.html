Python wait_for 一秒超时，为什么一秒后还没返回？

区分 asyncio wait_for 的超时触发、取消完成和清理责任，用 finally 示例说明额外等待、清理异常及 shield 的所有权。

正文

核心要点

  • wait_for 超时后等待取消完成，耗时可能越过阈值。
  • 清理异常与超时异常不能随意合并。
  • shield 改变取消范围，也需要明确后台任务负责人。

asyncio.wait_for(..., timeout=1) 并不保证整个调用在一秒内返回。达到超时条件后，它会取消被等待的任务，并等待取消完成；任务退出时还有清理工作，就可能继续等待。设计请求预算时，要区分开始取消的时点与资源收尾完成的时点。

超时触发取消，不是终止进程

Python 协程与任务文档说明，wait_for 在超时时取消等待对象，并等待实际取消，所以总等待时间可能超过 timeout；取消期间发生的异常会继续传播。本文于二〇二六年十月二十九日核对 Python 3.14.10 文档。等待取消完成的规则从三点七版开始，三点十一版起超时抛出内置 TimeoutError，旧版本代码不能只凭相同函数名混用说明。

设想文件导出协程正在等待远程读取，超时后需要关闭连接、删除临时文件。调用方想尽快回答用户，资源持有者却不能在工作做了一半时凭空消失。如果把“一秒开始退出”写成“一秒所有工作结束”，需求会同时要求两个不同结果。更明确的合同应写出什么时候停止接收新结果、清理由谁负责、服务最多还愿意等待多久，以及清理失败如何被观察。

取消是协作过程。任务需要到达能够响应取消的机会，finally 才能接手。若协程里执行长时间同步计算，事件循环无法及时运行超时逻辑，也不会因为加上 wait_for 就成为能被强制终止的工作。需要独立执行边界时，应按工作类型设计进程或其他控制方式，不能把一个参数当成通用抢占器。

用清理顺序解释额外的等待

下面是未执行的完整教学程序。延时只是构造可见阶段的假设，不是本文测得的性能数据；运行时的调度耗时也不保证精确等于两个延时相加。

import asyncio

async def export_report():
    try:
        await asyncio.sleep(60)
        return "report"
    finally:
        print("cleanup started")
        await asyncio.sleep(0.2)
        print("cleanup finished")

async def main():
    try:
        await asyncio.wait_for(export_report(), timeout=1)
    except TimeoutError:
        print("caller observed timeout")

asyncio.run(main())

按文档语义推演，超时会使 export_report 进入 finally；wait_for 等待其取消完成后，调用方才走超时处理。这个示例的判断重点是清理开始、清理结束与调用方观察超时之间的关系，而不是宣称屏幕上某行日志恰好在第一秒出现。真实程序的清理函数可能自己失败、取消或阻塞，必须把这些状态加入设计。

如果把 finally 改成抛出 RuntimeError，不能仍只预期 TimeoutError。官方说明取消过程中产生的异常会传播；调用方应保留能定位清理失败的错误，而不是一律换成“超时，请重试”。这也影响资源责任：用户界面可以把本次请求标成失败，但后台仍须记录哪份临时产物由谁处理。失败提示并不自动完成清理。

捕获 CancelledError 后直接返回正常结果同样不是无害优化。它改变了任务对取消的响应，可能让外层得到与原本期望不同的结果。通常应在清理后继续传播取消；若业务有意允许任务在取消后完成，调用方也必须接受这份明确的协议，不能一边吞掉取消，一边宣传它提供硬截止时间。

包上 shield 以后，超时任务由谁结束？

同一份文档的 shield 章节说明如何保护内部任务不被外层取消。它可以改变 wait_for 超时所取消的范围，但内部工作不会因此自动获得管理者。调用者应保留任务引用，并决定稍后等待、接收错误，还是在另一个时点明确取消。若只是把 shield 加上以便快速返回，导出工作可能在用户已经离开后继续占用资源。

例如先创建 task，再对 shield(task) 设置等待预算，外层超时仅表示不再等待这次结果。之后仍需要一个可查的任务状态和收尾入口。把它当后台作业时，应给出作业身份、重试与结果保留规则；把它当请求内工作时，则应考虑是否真的允许超出请求生命周期。两种选择都可能合理，关键是不能让任务无主。

这也是本题与TaskGroup 失败范围的区别。后者决定一组任务如何共同失败和退出；这里即使只有一个任务，也必须区分等待预算、取消请求和取消完成。共享“取消”这个词，不代表它们提供相同的时间保证。

验证顺序比追求一秒误差更有用

拟议测试可以用事件屏障替代真实网络：让任务确认已进入工作等待，触发超时，再让清理停在一个受控事件上。此时检查外层是否仍未完成，释放清理事件，再确认终态。这个用例验证等待结算，而不依赖某台机器恰好在一秒附近打印。另测清理抛错、内部吞取消、shield 后内部继续运行和外层本身被取消，分别核对任务最终由谁收回。

如果要记录耗时，应采用适当的单调时钟并保留 Python 版本和运行环境；事件顺序与耗时分布是两类证据。一次本地延时实验不能证明生产请求存在相同上限，更不能证明已发送的远程写入被撤销。超时以后，远端是否提交仍应通过远端协议查询；重新发起之前，需要业务幂等或结果身份。

若还要为清理设置第二层预算，预算耗尽后的状态也必须有名字。可以停止向请求等待者承诺同步清理完成，并把剩余资源登记给明确的恢复流程；不能只再套一层超时就宣称文件已删、连接已关。清理是否允许再次被取消、被中断后能否安全重试，都需要资源接口支持。这些选择改变任务合同，不能在通用装饰器里悄悄添加。验收应有一条清理迟迟未结束的路径，证明调用方既不会永久等待，也不会把未确认清理标成完成。

本文没有执行异步程序或测量时间。审查一份“一秒超时”的需求时，应先把它拆成用户等待多久、何时请求取消、谁等清理和谁确认外部结果四项，再决定 wait_for 是否正好承担其中那一项。
