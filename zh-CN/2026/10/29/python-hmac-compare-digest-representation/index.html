签名用了 compare_digest，为什么仍然一直不匹配？

用 Python HMAC-SHA256 示例区分摘要字节、十六进制字符和同类型比较，并限定时序承诺、输入格式及重放边界。

正文

核心要点

  • 同类型还不够，比较双方也必须使用同一种摘要表示。
  • compare_digest 避免内容提前退出，不保证整个服务恒定时间。
  • 消息认证不等于新鲜度检查或业务去重。

hmac.compare_digest() 不会自动把十六进制文本解码成摘要字节。签名校验一直失败时，应先检查双方比较的是原始摘要还是编码文本、使用什么类型和格式，再检查比较函数。换成适合密码学比较的接口，并不能替协议解释签名的表示。

三十二字节和六十四字符不是同一份输入

Python hmac 文档区分 digest 返回的摘要字节与 hexdigest 返回的十六进制字符串，并要求 compare_digest 的两端使用相同类型：ASCII 字符串，或者字节类对象。本文于二〇二六年十月二十九日核对 Python 3.14.10 文档。这里讨论 HMAC-SHA256 的比较阶段，不重新定义提供方的签名协议。

假设协议把三十二字节摘要编码成六十四个十六进制字符。服务端计算 hmac.digest(key, body, 'sha256') 得到字节，收到的请求头却是字符串，不能直接比较。即使把字符串 encode 成字节，也得到十六进制字符的字节序列，并没有恢复原来的三十二字节。类型统一只解决一层问题，表示也必须统一。

另一条合法路线是服务端生成 hexdigest，再与协议要求的文本比较。选择哪条路线取决于协议有没有固定大小写、前缀、分隔符和算法标识。不能为了让自己的代码通过，就把收到的任何字符都随意 strip、lower 或忽略前缀。协议允许规范化时才规范化，否则宽松处理是在扩大可接受输入集合。

把格式验证和认证比较写成两个步骤

下面假设自有协议明确要求六十四个小写十六进制字符，不带前缀。密钥与待认证消息以字节传入；它们的获取、轮换和传输限制属于外层合同。这是未执行的完整函数，不是已通过攻击测试的验签组件。

import hmac
import re

HEX_SHA256 = re.compile(r"[0-9a-f]{64}")

def verify_message(key: bytes, body: bytes, signature: str) -> bool:
    if not isinstance(signature, str):
        return False
    if HEX_SHA256.fullmatch(signature) is None:
        return False
    received = bytes.fromhex(signature)
    expected = hmac.digest(key, body, "sha256")
    return hmac.compare_digest(expected, received)

fullmatch 限定整段文本的长度和字符，随后 bytes.fromhex 把合法表示解码成摘要字节，最后双方都是同一摘要格式。它没有比较请求头字符串的视觉外观，也没有把任意长度文本塞进比较函数碰碰运气。若对接的真实协议允许大写或包含算法前缀，应按该协议修改解析器与测试，不能直接宣称这个示例兼容所有 Webhook。

假设调用者拿错误密钥计算签名，即使格式完全合法，也应该在比较阶段失败；格式错误则在解析阶段拒绝。这两个失败原因有不同的工程定位价值，但公开错误响应是否区分，仍需按接口策略决定。内部诊断不应记录密钥或完整敏感消息，可以记录算法、格式分支和请求身份，以便检查是否拿错了签名版本。

compare_digest 隐藏了哪些时间差？

官方文档说，它采用避免按内容提前退出的比较方式，适合密码学使用；同时提醒，长度不同或发生错误时，理论上仍可能暴露类型与长度信息。因此不能把使用了这个函数写成“整个接口恒定时间”或“没有任何侧信道”。前面的正则、解码、取密钥和消息读取同样存在各自分支，函数级承诺不能升级成完整服务保证。

拒绝畸形签名通常不需要先把它填成固定长度假摘要。若威胁模型对响应差异有额外要求，应围绕完整实现做审查与测试，而不是根据函数名猜测安全性。这里的判断是让表示先明确，再使用受支持的比较接口；它不是对网络条件下可观测时序的测量。

从普通相等比较切换到 compare_digest，也不要留下偷偷绕过它的成功分支。例如开发时发现某种编码不匹配，先试字符串相等，失败后再试字节比较，会把协议解析变成多条不清楚的接受路径。更可审查的做法是一种受控格式对应一条确定转换；需要同时兼容两个正式版本时，明确版本选择，再各自使用对应算法和密钥。

比较通过后可以接受重复 Webhook 吗？

不能仅凭消息认证作这个决定。一条以前确实由持钥方发送的消息，可以再次拥有正确摘要；compare_digest 没有检查当前时间、事件身份或业务是否已处理。若协议提供时间戳，应按它定义的签名覆盖范围和允许窗口检查；事件去重还需要自己的持久身份与重复响应规则。这些是协议设计判断，不是本文已经实现的重放防护。

本站Webhook 原始正文校验解释参与计算的消息为什么不能先解析再重序列化。本篇补充另一端：即使消息字节正确，比较的摘要表示仍可能不一致。诊断时分别保留消息获取、签名解析、密钥选择和摘要比较四个阶段，才能区分错误来自哪一层。

拟议测试先用固定的非生产密钥和消息生成一份合法签名，再逐项修改消息一个字节、密钥、摘要字符和长度。添加大写、空格、非 ASCII、合法格式但错误内容，以及把原始摘要误当十六进制文本的负样本。预期必须在测试之前按协议写好，不能因为实现接受了某种格式就倒过来宣布兼容。

签名字段固定长度，也不表示消息处理成本固定。调用本函数之前，应按接口合同限制请求体大小，并避免让不受信任的算法名称直接决定服务端如何计算。若需要兼容多个算法，先从受控配置选择协议版本与密钥，再进入对应解析器。这里提出的是边界安排，没有增加一个未经审查的自动算法协商功能；格式验证通过仍不能让超大消息绕过原有资源限制。

测试同一个函数的输出，只能验证这份实现面对所列输入的行为。生产验收还需检查提供方算法、消息覆盖范围、密钥来源、轮换和重放政策；不用真实密钥写入测试记录，也不把一组绿色测试宣传成绝对安全。本文没有执行代码、提供方回调或时序实验。先把比较双方写成明确的类型、编码与长度，再判断失败是否真出在比较过程。
