access 已通过，Node.js open 为什么仍报 ENOENT？

解释 Node.js access 与 open 之间的竞态，用直接读取和 wx 排他创建示例区分缺失、权限、覆盖与句柄清理。

正文

核心要点

  • access 的观察结果不会锁住后续操作。
  • 创建且不覆盖应在 open 中表达 wx 条件。
  • 实际读写、关闭和文件交付仍有独立失败路径。

fs.access() 通过之后，open() 仍可能失败，因为检查没有替后一次操作锁住路径。读取配置文件时，应直接打开并处理这次操作的错误；如果要求创建新文件且不覆盖已有文件，则把排他创建意图交给打开标志。先检查再使用，不能免掉实际使用时的错误处理。

检查结果属于上一次观察

Node.js 文件系统文档明确不推荐先用 access 检查可访问性再 open，因为其他进程可能在两次调用之间改变文件状态。本文于二〇二六年十月二十九日读取的文档头标为 Node.js v24.22.2，下面只讨论本地可信目录中的普通文件，不把路径校验和应用授权混入可访问性判断。

假设服务先检查配置可读，再读取内容。检查返回时文件存在，另一个进程随后做轮换，把旧文件移走，新文件尚未出现，读取就会得到缺失错误。检查先失败也不代表稍后的读取必然失败，文件可能随后被创建。两种次序都说明观察有时点，不能把某一刻的状态升级成未来操作的保证。这是可构造的竞态，不是本文观察到的生产事故。

多加一次检查不会消除窗口，只会把窗口向后挪。同步版本同样不能锁住其他进程：阻塞当前 JavaScript 执行，不等于冻结操作系统文件命名空间。锁属于另一份协议，必须由各参与者遵守。若需求只是“读得到就用，否则返回缺失”，直接让读取操作决定结果通常更清楚。

让错误紧挨真正要做的动作

下面是未执行的完整示例。路径由应用提供，调用者已在其他地方完成目录选择和访问授权。缺失在这个假设接口中是允许的状态，其他错误继续交给调用方，而不是全部伪装成没有配置。

import { open } from 'node:fs/promises';

export async function readOptionalConfig(path) {
  let file;
  try {
    file = await open(path, 'r');
  } catch (error) {
    if (error.code === 'ENOENT') return { status: 'missing' };
    throw error;
  }
  try {
    const text = await file.readFile({ encoding: 'utf8' });
    return { status: 'loaded', text };
  } finally {
    await file.close();
  }
}

这里故意把打开和读取分开。只有 open 的缺失被解释成 missing；打开后的读错误不会被同一个宽泛捕获当成“没有配置”。finally 为已经拿到的句柄安排关闭。返回 loaded 表示取得了文本，不表示 JSON 合法、配置版本正确或业务已经采用它；这些判断应在各自步骤继续做，不能让文件可读性替配置验收签收。

这个例子也没有承诺读取期间内容绝不会被其他写者修改。得到句柄缩小了“再次按路径找文件”的歧义，却没有替所有写者建立一致的更新协议。若需要一份完整配置快照，可以进一步约定写入临时文件、检查内容、再原子替换的方式，并验证目标文件系统语义。本站rename 与文件交付讨论的持久化边界仍需要单独核对。

创建且不覆盖，要把条件放进 open

另一类错误是先检查文件不存在，再用普通写模式创建。两个进程都看到不存在，随后都写入，后者可能覆盖前者。Node 文档给出的方向是直接以 wx 打开，路径已存在时处理 EEXIST。以下函数同样未执行，只展示排他创建、写入与关闭，不声称已经实现断电安全或完整交付。

export async function createNewText(path, text) {
  let file;
  try {
    file = await open(path, 'wx');
  } catch (error) {
    if (error.code === 'EEXIST') return { status: 'exists' };
    throw error;
  }
  try {
    await file.writeFile(text, { encoding: 'utf8' });
    return { status: 'written' };
  } finally {
    await file.close();
  }
}

排他创建解决的是“这次创建时已经存在则失败”，不是“从此无人能修改文件”。写到一半失败时还可能留下当前进程创建的不完整文件，需要按任务身份决定保留诊断还是清理，不能随手删除可能已由其他流程接管的路径。Node 还说明排他标志可能不适用于网络文件系统，因此共享盘上的验收不能直接沿用本地文件实验结论。

也不能把 wx 当成目录安全检查。用户输入若能改变目标目录，创建在错误位置依然是错误；目录权限、符号链接和应用允许写入的对象范围需要独立设计。本文不提供一个处理任意不可信路径的安全文件服务。它只把“先不存在才创建”从两次观察改为一次带条件的操作。

access 是否应该从项目里完全删除？

不必。如果目的只是向用户显示当前可访问状态，或者可访问性本身是另一个进程提供的信号，access 仍可能有用途。差别在于，这份状态不能让后续读取省略错误处理。界面显示“目前可读”，真正点击读取时仍可能失败，产品应显示对应失败并保留重试或重新选择入口。

Windows 还有独立限制：文档指出 access 不检查目录 ACL 的全部限制，报告可访问也可能仍被访问控制拒绝。因此不能把 access 当作身份授权的真相来源。系统权限与业务权限分别由实际访问和应用规则处理；删除检查并不是放宽业务授权。

拟议验证应使用受控交接而不是随机睡眠：让一个测试执行者检查成功后停在屏障，另一个移走文件，再放行 open，确认得到预先约定的缺失状态。再测无权限、打开后读失败和两个创建者竞争，分别确认异常保留、句柄关闭和一个 EEXIST 分支。Windows 与网络文件系统另设目标环境检查，不能从本机推断。

还需要明确关闭失败的报告政策。这个最小函数让关闭异常自然传播；如果读取也失败，finally 抛出的关闭异常可能遮住原始读错误。真实服务若要求同时保留两项诊断，应显式收集并关联它们，而不是为了保持成功状态吞掉关闭错误。测试中分别注入读失败、关闭失败与两者同时失败，核对调用者拿到哪一项原因。这样的检查与先做 access 没有关联，属于句柄交付后的独立责任。

本文没有运行文件操作或并发测试。审查时先找到那条“检查通过，所以后面不会失败”的假设，把需要保证的条件移到实际操作或明确的协调协议里，再为仍可能发生的错误留下可解释结果。
