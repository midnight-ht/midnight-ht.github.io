PostgreSQL 18 新建生成列，省略 STORED 会怎样？

核对 PostgreSQL 18 新建表中生成列默认 VIRTUAL 的条件，对照 17 版，并用订单行金额区分派生、默认值与历史快照。

正文

核心要点

  • 18 版新建声明省略类型时默认使用虚拟生成列。
  • 已有存储生成列不会仅因升级自动变成虚拟列。
  • STORED 改变计算时机，不代替历史数据修改权限。

在 PostgreSQL 18 新建表或重建表的 DDL 中，生成列省略 VIRTUAL、STORED 时默认采用 VIRTUAL。需要写入时计算并存储的列，应把 STORED 明写出来。这是建表声明的解释规则，不表示数据库升级会把已有存储生成列自动改成虚拟列。

先看版本，再看省略了什么

PostgreSQL 18 生成列文档区分两种类型：存储生成列在写入时计算并占用存储，虚拟生成列在读取时计算，默认选择后者。本文于二〇二六年十月二十九日核对固定版本文档。对照十七版说明，该版仅实现存储生成列，要求写 STORED；不能把新版省略规则倒灌成旧版有效语法。

设想团队整理迁移文件，认为 STORED 只是冗余字样而删除。旧环境可能直接拒绝这份声明；十八版则可能成功创建虚拟生成列。构建成功并不能证明重建后的列仍沿用原来的计算时机。审查应比较部署版本、实际 DDL 和创建后的列属性，而不是只看迁移没有抛错。这里是假设的迁移风险，没有声称本站执行过升级。

也不应把“生成列会自动更新”误解为它与普通 DEFAULT 相同。默认值通常在插入且没有提供该列值时采用；生成列由表达式派生，不能由调用方随意覆盖。两者都能减少应用重复计算，但表达的是不同的数据所有权：一个允许写入者选择具体值，一个要求值由数据库规则决定。

用一行内的确定派生说明两种选择

下面是未执行的完整教学 SQL，明确使用 STORED，使期望不依赖省略写法。数量与成交单价都存放在这一行，金额只表达它们的乘积，不涉及税率、折扣或跨表价格。

CREATE TABLE order_lines (
  id bigint PRIMARY KEY,
  quantity integer NOT NULL CHECK (quantity > 0),
  unit_price numeric(12,2) NOT NULL CHECK (unit_price >= 0),
  line_total numeric GENERATED ALWAYS AS
    (quantity * unit_price) STORED
);
INSERT INTO order_lines(id, quantity, unit_price)
VALUES (1, 2, 12.50);
UPDATE order_lines SET quantity = 3 WHERE id = 1;
SELECT quantity, unit_price, line_total FROM order_lines WHERE id = 1;

按定义推演，修改数量后金额随表达式改变；不能因为应用没在 UPDATE 中指定金额就认为金额保留旧值。若改为 VIRTUAL，同样是派生值，差别在读取时计算而非把计算结果作为普通存储字段保留。此例只说明语义，不提供读取速度、写入成本或节省空间的测量，也不能据此替真实负载选择更快的一种。

另设一个负样本，尝试直接向 line_total 写入任意数值。官方文档说明生成列不能这样直接指定值，数据操作中可使用 DEFAULT 表达由生成规则处理。这里 DEFAULT 是语法允许的标记，不是给生成列另外安装一份普通默认值。若接口接受用户传入的总金额，服务端应先决定该字段是被忽略、核对还是拒绝，不能靠数据库报错临时决定 API 合同。

immutable 不是把任意函数标一下就行

十八版要求生成表达式只使用 immutable 函数，不含子查询，也不能引用当前行之外的数据；还不能引用另一生成列。虚拟生成列额外不能使用用户定义类型或函数，包括通过运算符、类型转换间接引用的情况。存储与虚拟的选择因此不只影响计算时点，也影响表达式能否合法建立。

例如让金额随当前汇率、另一张商品表最新价格或系统时钟变化，就不是这个行内乘法示例。同一行输入不变而结果应随外部状态变化，已经与固定派生规则的要求冲突。把用户函数草率标为 immutable，不会让真实依赖消失，只会把错误承诺藏进数据库定义。需要动态查询的值，可以考虑查询时计算或视图；需要业务时点快照，则保存当时确认的输入与结果，并明确更新权。

这里的方案比较首先看数据含义。普通列适合独立记录事实，生成列适合由当前行确定的关系，视图适合查询表达；是否需要索引、复制或权限分离，还应读取对应版本章节并在项目里验证。本文不把这几种方案排列成通用性能名次。

订单金额是否应该总用生成列？

不应因为能写乘法就把所有金额都生成。若 unit_price 保存的是下单时成交价，这份输入快照与数量相乘可以表达行金额；若它只是当前商品价的查询结果，后来价格变化是否应改历史订单就是另一个需求。税额、优惠分摊和人工调整还可能有独立的确认时点与舍入规则，不能把演示中的简单金额扩成结算承诺。

这个追问要求同时审查输入的生命周期。即使 line_total 在写入时存储，后来更新 unit_price 仍会使它随规则变化；STORED 不等于永久冻结历史结果。若业务要求已确认订单不可修改，应通过独立的状态与权限规则约束输入列，不能借列类型代替业务锁定。

本站普通 DEFAULT 与显式 NULL解释省略值的含义，本篇没有改变那条规则。生成列需要另一份合同：哪些输入属于当前行、何时允许改、由哪种计算时机派生，以及谁可以读取结果。把两种字段都称为“自动填值”，会掩盖这些差异。

拟议验证应分别在目标十七版与十八版隔离数据库运行明确类型和省略类型的建表用例，记录成功或拒绝，不预先把两版结果混成相同。十八版再比较插入、修改输入、直接写派生列、用户函数和跨行依赖的情况。检查创建后实际列定义，性能判断则另用真实查询与写入负载测量。

若剩下的选择确实只是计算时机，可以把同一份输入、同一表达式和同一查询集合用于对照，分别观察写入延迟、读取延迟、存储占用与变更频率。不要让虚拟方案顺带少查几列、存储方案又多一个索引，却把差异全归给列类型。先保证结果一致，再比较成本；是否值得交换读写成本取决于实际访问，而非示例中乘法看起来简单还是复杂。

本文没有执行数据库迁移或性能实验。对一份准备投产的十八版建表脚本，先把生成列类型写明，再核对它是否表达了真正允许随输入变化的事实；已有列的状态要从实际结构读取，而不是从升级版本号猜测。
