Headless Service 返回多个地址，谁选择下一个 Pod？

区分端点发现、客户端选址和长连接更新，用三地址单连接反例比较无头服务与统一入口，并安排同进程验证。

正文

核心要点

  • 无头服务通过DNS提供端点，平台不承担该服务的代理分流。
  • 多个地址不会强制既有长连接迁移或均匀使用副本。
  • 在同一客户端观察解析与连接，分别检查发现刷新和连接生命周期。

Headless Service 返回多个 Pod 地址，并不意味着 Kubernetes 会替客户端把每个请求均匀分给它们。无头服务提供端点发现，客户端直接连接自己选择的地址。排查流量集中时，应沿 DNS 返回、地址选择和连接生命周期检查，不能只因为有三个副本就预期自动三等分。

少了一个虚拟地址，也少了一项平台职责

Kubernetes Service 的无头服务说明指出，clusterIP 显式设为 None 时不分配集群 IP，kube-proxy 不处理这类服务，平台不为其执行代理或负载均衡。带选择器的无头服务通过 EndpointSlice 与 DNS 提供指向后端 Pod 的地址。本篇依据二〇二六年十月二十九日核对的在线说明分析，没有创建集群或测量分流。

它适合让客户端看见具体端点，并按自身协议作选择。例如某种客户端必须识别成员，而不是只连接一个统一入口。这个能力同时带来责任：地址列表怎样使用、旧端点怎样剔除、连接失败怎样切换，都不能从“DNS 查到了地址”自然推导出来。

普通 ClusterIP 与无头服务不是同一条网络路径换了个名称。前者有统一入口的服务抽象，后者让端点直接暴露给客户端选择。选择哪一种，应由协议和客户端能力决定。若应用从来只理解一个稳定服务地址，贸然切到无头模式并不会自动获得更精细的流量控制。

三个地址，只有一条长期连接

设想测试命名空间里有三个带 app=catalog 标签的 Pod，都监听八〇八〇端口，并满足服务选择条件。下面只展示 Service；工作负载与客户端需要另行准备，清单未应用。

apiVersion: v1
kind: Service
metadata:
  name: catalog-peers
  namespace: test
spec:
  clusterIP: None
  selector:
    app: catalog
  ports:
    - name: http
      port: 8080
      targetPort: 8080

假设客户端解析名称得到三个端点，但实现只取列表中的第一个地址，建立一条长连接，并把后续请求都复用在这条连接上。那么流量集中在那个端点，符合客户端策略。DNS 返回了其他地址，只说明它们在发现结果中，不能证明客户端轮换过连接。这个例子不预测任何 DNS 记录顺序，也不把首地址选择归为所有语言运行时的默认行为。

下一步假设该 Pod 被替换，DNS 结果随后发生变化。已经存在的连接不会仅因 DNS 记录变化就自动迁移到新地址。客户端可能继续复用旧连接，直到关闭或发生错误；它何时重新解析、是否缓存结果、是否尝试其他端点，需要查具体实现。只在命令行运行一次 DNS 查询，无法证明业务进程已经使用新结果。

所以调查应同时保存解析结果和客户端实际连接目的地。若前者已有新 Pod，后者仍指旧地址，优先检查连接池和发现更新；若 DNS 本身没有正确端点，再查选择器、EndpointSlice 和就绪条件。把这两层分开，能避免为了修连接复用而反复改 Service 端口。

该改客户端，还是换回统一入口？

若协议不要求成员身份，团队又希望平台承担统一入口的转发，可以评估普通 ClusterIP。它也不自动承诺每个业务请求严格平均，长连接和协议行为仍需检查；不过不必让应用自己实现全部端点选择。不能为了追求一张完全平坦的流量图，就不断更换服务类型。

若确实需要直接识别成员，客户端应有明确的选择策略。轮换、按负载或按分片选择是不同业务设计，重试可能还涉及幂等与期限。发现一个列表后随意挑选，不一定符合数据归属；对有主从角色或分片路由的系统，随机分配甚至可能把请求送到不承担该操作的成员。

失败切换也要限定范围。连接建立失败可以尝试另一个端点，但一个已发送的写请求在响应丢失时可能已经执行。此时换地址重试并不能证明业务只写了一次。无头服务没有提供业务去重协议，客户端需要按接口身份查询结果或采用适用的幂等设计。读取与写入的验证路径不应混成同一条“连不上就换一个”。

长连接什么时候应该重新选择端点？

这属于客户端连接管理合同，而不是 DNS 的自动承诺。可以在连接失败、连接达到约定寿命、发现结果变化或明确的成员事件后重新选择，但每一种方案都有代价。连接寿命太短会增加握手和重连，太长可能使新副本很久没有工作。具体阈值应来自协议、客户端能力和测量，不应从本篇假设写入生产配置。

发现更新还要考虑无端点的短暂状态。客户端应明确是等待一段有限时间、返回可识别失败，还是按协议保留已知连接；不能无限保留已经移除的成员又宣称发现已更新。为旧地址保留何种宽限，需要考虑该成员是否仍有权处理操作，而不只是连接是否还活着。

拟议验证先从同一个业务进程读取解析结果与实际连接，覆盖三个稳定端点、新增端点、移除当前端点、单个连接失败和暂时无端点。每种情况记录地址选择、连接创建时间、重试次数与最终业务结果。本文没有运行这些检查，也不提供均匀分流或故障切换成功结论。

最后检查服务名字与协议身份。本文与ExternalName 的 DNS 别名和 TLS 身份不同：这里关注直接端点发现后的选择责任，不是把内部名字改写成外部 HTTPS 身份。发现、连接和正确业务结果都能单独失败；让每一层留下证据，才能决定该修 DNS、客户端，还是所选服务抽象。

为了区分解析缓存与连接复用，可在同一客户端实现中安排两个对照：一个只记录新的解析结果，另一个明确新建连接并记录选中的目的地址。不要使用另一种语言写的临时工具替代业务解析器，因为缓存和地址排序策略可能不同。新连接能使用新地址而旧连接仍停留原处，证据指向连接生命周期；连新的解析结果都陈旧，则应先查发现刷新。两个结果不能用同一张DNS截图概括。
