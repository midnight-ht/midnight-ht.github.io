SQLite REPLACE 改了姓名，旧记录为什么算被删除？

解释 SQLite REPLACE 在唯一性冲突时的删除与插入语义，用客户导入对照 UPSERT，并核对备注、编号、触发器和关联行。

正文

核心要点

  • REPLACE 遇到唯一性冲突可能删除旧行再插入。
  • 只修改姓名，应把允许变化的列写进 UPSERT。
  • 最终行内容与删除审计需要分别验证。

SQLite 的 INSERT OR REPLACE 发生唯一性冲突时，可能先删除冲突的旧行，再插入这次提供的新行。它不能按“只改几个字段”的 UPDATE 来理解。若导入客户姓名时需要保留客户编号、备注与关联关系，应先判断自己要保留哪条记录的身份，再选择冲突处理方式。

相同邮箱，不等于同一次行更新

SQLite 冲突处理参考把 REPLACE 列为冲突解决算法：遇到 UNIQUE 或 PRIMARY KEY 冲突，先移除造成冲突的已有行，再继续插入或更新；NOT NULL 等情况有各自规则，不能把所有约束失败都说成删除。本文于二〇二六年十月二十九日核对官方页面，页面标注更新于二〇二五年十一月二十二日。

设想客户表把邮箱设成唯一键，后台每晚导入姓名。业务说“邮箱相同就刷新姓名”，开发却写成替换整行。邮箱只是寻找客户的线索，旧行上可能还有人工备注和稳定编号。删除后插入的新行即使仍有同一个邮箱，也不能据此证明旧行的其他信息被保留。这是下面假设示例要审查的区别，并非本站发生过的数据事故。

以下 SQL 为完整说明性示例，未在数据库运行。故意给备注默认值，并让第二次插入省略编号和备注，让 REPLACE 的影响可以被观察。

CREATE TABLE customers (
  id INTEGER PRIMARY KEY,
  email TEXT NOT NULL UNIQUE,
  name TEXT NOT NULL,
  note TEXT NOT NULL DEFAULT 'unreviewed'
);
INSERT INTO customers VALUES
  (7, 'a@example.test', 'Alice', 'verified manually');
INSERT OR REPLACE INTO customers(email, name)
VALUES ('a@example.test', 'Alicia');
SELECT id, email, name, note FROM customers;

按这份定义推演，旧行会因邮箱冲突被删除，新行的 note 采用默认值；省略的整数主键按插入规则分配，不能要求它继续等于七。不要把新编号必然不同写成通用结论，因为编号选择还受表中现有内容等条件影响。真正必须拒绝的误解是：这条语句没有承诺保留旧编号与旧备注。即便某次编号碰巧相同，也不足以证明执行了 UPDATE。

只更新姓名，就把修改范围写在语句里

如果目标是现有客户仍为同一条记录，可以在重新建立的同样初始数据上对照下面的写法。这里不应接着前一段已经替换过的数据运行，否则无法比较原备注是否保留。

INSERT INTO customers(email, name)
VALUES ('a@example.test', 'Alicia')
ON CONFLICT(email) DO UPDATE SET name = excluded.name;

SQLite UPSERT 文档说明，这类语法在插入发生指定唯一性冲突时选择更新或不操作，excluded 表示原本试图插入的值。这里只设置 name，便把“保留其他列”变成语句可审查的范围。没有邮箱冲突时仍执行正常插入，因此新客户还会使用默认备注。若产品其实要求覆盖备注，就应显式加入该列；没有提交备注与明确清空备注也应在导入协议里分开。

UPSERT 同样不是所有错误的兜底。指定邮箱冲突，并不表示其他唯一约束、非空约束或外键错误都可以变成成功。假设新增了独立的客户号唯一键，导入行的邮箱属于甲、客户号却属于乙，这是身份冲突，应由业务决定拒绝还是人工处理。不能看到语法叫“冲突处理”就把两个客户自动合并。迁移前应列出每个唯一键的业务含义和可能组合。

删除触发器没执行，能证明没有删除吗？

不能。官方冲突处理页对 REPLACE 有特别说明：由它删除记录时，删除触发器只有开启 recursive triggers 才会触发；update hook 对这些被删行也有例外。文档还提醒这些特殊行为未来可能变化。因此，若审计代码依赖触发器或更新钩子，必须核对当前 SQLite 版本和连接设置，不能用“没有看到删除日志”反推“旧行没有被删”。

这个追问补充的是观察证据的边界。检查最终行内容与检查审计链是否完整，是两个用例。可以给隔离测试库加上删除审计表，对照 recursive_triggers 开关，记录触发器是否产生条目，同时核对最终数据。不能只统计客户端显示“影响一行”就结束，因为变更计数和 REPLACE 的内部删除并不等价。本文没有执行触发器实验，也没有把它写成任何版本的实测回执。

如果旧行还有子表引用，应另外核对外键是否启用、删除动作和触发器会造成什么后果。本站SQLite 连接级外键检查解释为什么声明外键不代表每条连接都检查。这里不预设所有子表都会被删除，也不建议为了绕过错误关闭外键；应当在真实结构上证明替换行为是否符合对象所有权。

让导入验收观察身份和遗漏字段

验证先从新建的隔离数据库开始，每种方案恢复相同初始数据，记录 SQLite 版本、表定义、触发器和相关 PRAGMA。分别运行普通插入、邮箱冲突、另一个唯一键冲突、缺少非空字段和带子表引用的情况。每次检查客户编号、姓名、备注和关联行，而不只检查没有异常。再加入重复导入同一批数据，确认业务期待的幂等范围。

若接口会返回导入结果，还应区分新建、更新、未改变和拒绝，不能把每条未报错记录统一算作新增客户。决定采用 UPSERT 后，也要审查应用是否把省略字段预先补成空值，再将它们全写进更新集合；SQL 选对了，映射层仍可能丢掉人工信息。失败报告应保留可定位的行身份和错误原因，避免把包含客户隐私的整份文件写入日志。

如果一批导入允许两种唯一键定位同一个客户，预检应列出它们指向同一行、不同的行和都不存在三类情况。指向不同客户时保留原始记录并返回身份冲突，不应把 REPLACE 当作合并工具。修复导入前也要确认文件本身有没有重复身份，避免一批数据里的后行悄悄覆盖前行。重复输入的选择政策应由产品确认，验证时检查每一行的最终归属，而不是只核对整批行数。

REPLACE 适合可以按删除再建理解的对象；它是否适合某张表，取决于那张表的身份和关联合同。对只想更新姓名的客户导入，先选择只更新姓名的语句，再用编号、备注和关联关系的证据验收。
