SQLite 配了五秒 busy_timeout，为什么写入仍失败？

用未执行的双连接步骤解释 SQLite busy handler 的等待预算、潜在死锁例外、每连接覆盖规则与失败后事务入口。

正文

核心要点

  • 超时配置是有限等待政策，不是写成功保证。
  • 每连接只有一个 busy handler，新设置会替换旧设置。
  • 报忙后须确认事务状态，再决定从哪里重新执行。

SQLite 设置 busy_timeout=5000，不表示每次写入都会等满五秒后成功。它为连接安装有限等待的 busy handler；等待仍可能以 SQLITE_BUSY 结束，而且为避免潜在死锁，SQLite 有时不会调用 handler。排查应先找到谁持有冲突的锁、哪条连接安装了什么处理器，再决定等待还是结束并重试事务。

预算是等待政策，不是成功预约

sqlite3_busy_timeout 官方参考说明，该接口安装的处理器会分次睡眠，累计睡眠达到指定毫秒数后停止继续尝试，并让操作返回 SQLITE_BUSY；非正数关闭处理器。本文于二〇二六年十月二十九日核对 SQLite 的在线 C 接口文档，页面没有给出固定发布版本，因此实际项目仍需记录所用 SQLite 库版本。

这里的累计睡眠与应用从发起请求到返回的总耗时不同。执行 SQL、调度、读取数据和其他工作也消耗时间，不能把五千毫秒当成精确墙钟上限或最低等待时间。更不能从返回得很快就断言配置没有生效；是否调用 handler 还取决于冲突的性质。应先保留具体错误与事务状态，再解释时间。

busy_handler 文档专门说明，如果调用处理器可能造成死锁，SQLite 可以直接返回 SQLITE_BUSY。例如两个连接各持有对方前进所需的锁，双方都继续等不会有进展。这个规则意味着延长超时并不是所有锁问题的解法，有时必须让一个事务退出，释放它已经持有的资源。

用两条连接说明持锁者和等待者

以下为未执行的双会话教学步骤，假定使用同一目录下的同一数据库文件、普通本地文件系统，没有额外后台写者。先在初始化连接执行建表，并在没有未完成事务时关闭它。

CREATE TABLE counters(id INTEGER PRIMARY KEY, value INTEGER NOT NULL);
INSERT INTO counters VALUES (1, 0);

接着在连接甲执行下面两句，暂时不提交。甲已经进入写事务，等待乙完成观察之后才结束。

BEGIN IMMEDIATE;
UPDATE counters SET value = value + 1 WHERE id = 1;

连接乙设置自己的等待策略，再尝试进入写事务。下面的每条失败都应由执行环境读回错误，不能在 BEGIN 失败后不检查状态就把后续 UPDATE 当作仍处于所想的事务里。

PRAGMA busy_timeout = 5000;
BEGIN IMMEDIATE;
-- 只有 BEGIN 成功才继续：
UPDATE counters SET value = value + 1 WHERE id = 1;
COMMIT;

如果甲持续持锁，乙可能在其等待政策允许的重试结束后报忙；如果甲及时提交，乙则可能继续。示例不提供实测耗时或固定输出。观察完之后在甲明确 COMMIT 或 ROLLBACK，再让乙从新的事务入口尝试。这样可以区分“等得太短”和“持锁者一直没退出”，而不是只把数值越调越大。

这个简单例子没有构造锁升级死锁，不应拿它证明所有忙错误都经过完整睡眠预算。若真实应用先读再写，旧读事务与另一个写者之间的关系可能不同。应先复现目标事务次序，再查看相应错误码与日志；不能把 BEGIN IMMEDIATE 的一次实验概括为 SQLite 的全部并发行为。

两个库都设置 handler，会叠加吗？

不会。官方文档规定每条数据库连接只有一个 busy handler，设置新的会清除之前的处理器。调用 busy_timeout 或执行对应 PRAGMA 都会改变它。因此连接初始化代码装了自定义处理器，稍后某个库再设超时，不能假设两套策略会按先后依次运行。

这个追问补充的是配置所有权。团队需要查清连接由谁创建、哪个适配器在何时初始化、借用连接后是否还有库改写策略。检查一条连接的 PRAGMA 值，不足以证明连接池里其他连接也采用相同设置；不同连接的政策必须分别可追溯。相关断言应放在实际创建或交接连接的位置，而不是仅写进部署文档。

自定义 handler 也不适合在回调里通过同一连接执行补救 SQL。文档说明它不可重入，不能修改调用它的连接，也不能在其中关闭连接或语句。若需要结束事务或重新决策，应让失败回到应用的受控错误路径处理。把回调写成复杂业务恢复引擎，反而会让锁与所有权更难解释。

报忙以后，重做哪一段？

这取决于事务边界和已经发生的动作。若失败前根据数据库旧值作出了业务决定，仅重发最后一条 UPDATE 可能沿用过时判断；通常应先确认当前事务状态，按约定结束或恢复，再从正确的决策入口重新读取。若同一流程已经调用外部接口，数据库重试不会撤销或去重那个副作用，需要另外的业务身份与幂等规则。

这里不能给所有 SQLite 错误套用同一套自动重试模板。锁冲突、约束失败、文件权限和磁盘故障的处置不同，SQLITE_BUSY 与其他状态也应区分。可以给允许重试的操作设置总预算、次数与退出状态，耗尽后返回可解释的暂时失败；不要无限等待到请求已经失去主人。

本站WAL checkpoint 与读事务讨论为什么读者影响回写。那不是把 busy_timeout 调大就能取代的分析：日志回写、写事务争用与应用重试分别有不同对象。先确认这次阻塞的是哪一项，再选择相应观察点。

拟议验证记录每条连接的库版本、事务次序、超时设置、开始结束时间和错误码。分别让甲早提交、持续持锁、回滚，以及让其他初始化代码改写 handler；再设计目标应用真实存在的锁升级次序。用受控屏障决定甲何时释放，避免依赖随机睡眠碰巧重现。本文没有运行双连接实验，也没有提供生产吞吐比较。

编排这份双会话实验时，还应避免客户端的“遇错继续”模式。乙的 BEGIN 若失败，测试驱动应立即记录并停止这一轮，不能让 UPDATE 在自动提交模式下另起一次未被标记的尝试，再把最终 COMMIT 报错当作原问题。每一轮都应从已确认没有未结束事务的状态开始，保存本轮身份和语句结果。这样观察的才是等待策略，而不是测试脚本意外创造的另一段写入。

超时配置可以是一种合理的短期等锁策略，但验收应能指出持锁者、等待者和结束条件。只有数值，没有事务退出与失败后决策，不能构成一次可靠的写入合同。
