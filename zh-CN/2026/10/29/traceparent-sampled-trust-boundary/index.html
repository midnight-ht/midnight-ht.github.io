sampled 是建议：公网 traceparent 的采样信任边界

按W3C有日期的推荐标准区分格式、可信身份与记录预算，说明盲从采样位的成本面、内部调用边界和独立验证。

正文

核心要点

  • 采样位是调用者建议，不是身份或成本授权。
  • 公网入口与可信调用方需要明确可验证的采样策略。
  • 必要审计与独立资源观察不能只依赖被采样的导出链路。

公网请求在 traceparent 中设置 sampled 位，并不要求接收服务无条件为它完整记录链路。这个位表达调用者的采样建议，不是身份凭据，也不是记录成本授权。入口需要同时考虑链路连续性与自身预算，不能把用户可填写的请求头当作无限记录的开关。

格式有效与值得信任是两项判断

W3C Trace Context 二〇二一年十一月二十三日推荐标准说明，trace-flags 中的控制位是调用者建议，理由包括信任与滥用、调用方错误以及两边负载不同。本文使用这个明确日期的一级推荐标准讨论信任边界，不把编辑草案当作已部署能力；没有测试任何 SDK 或网关。

格式校验首先回答能否正确解析。版本、标识长度和取值不符合规范的输入，需要按协议处理。但一个格式完全合格的 traceparent，也可能由未知客户端随意生成。它能提供链路关联线索，不能证明这个客户端拥有某个账号、来自内部服务，或有权要求昂贵的诊断记录。

这里容易出现一种隐蔽的权限混用：服务使用正常登录凭据决定业务能否执行，却把采样位直接交给另一个没有预算控制的记录分支。业务访问仍然受保护，遥测开销却可以被外部输入左右。采样策略也需要自己的信任模型，不能因为主接口有认证就默认所有可选请求头都已获授权。

走完一次公网入口的假设决策

设想一个搜索 API 同时接收浏览器用户和受控内部调用。一个外部请求带来语法合格且 sampled 为一的上下文。以下是未实现的设计推演，不是某个框架的通用配置：入口先完成格式解析，再确定请求来自何种可信连接与认证身份，然后按该入口的记录策略作本地采样决定，最后才传播适当的上下文。

如果本地预算允许保留，该请求可以进入正常记录路径，并维持可解释的关联。如果预算或策略决定不保留，就不能把“调用者要求采样”作为绕过本地上限的理由。具体如何与 SDK 的父级采样器、传播器及供应商机制配合，要按选定实现验证；本文不保证任意 ParentBased 配置都会自动完成入口信任判断。

假设另一个请求把 sampled 改为零，它也不应获得关闭全部安全审计的权限。业务审计与分布式链路采样承担不同承诺，不能让外部调用者通过一个遥测位决定关键操作是否留下必要记录。需要保留的审计内容仍应遵守自身的权限、留存和敏感信息规则，不必复制完整 trace 内容。

同一标准的拒绝服务章节提醒，公开 API 若天真地继续所有带 sampled 标志的链路，攻击者可能放大记录开销、污染链路关联或增加托管记录费用，并建议考虑认证与未认证请求的不同策略及记录限速。它说明的是攻击面，不是本文已经观察到的事故，也不提供适用于所有服务的安全流量阈值。

保留所有上游决定，还是在入口重新选择？

完全尊重上游采样有利于跨服务一致性，适合信任关系与成本责任已经明确的场景。若上游可以由公网用户任意冒充，盲目延续就把预算决定交给了未知调用者。另一端的极端做法是抹掉一切上下文并重建，它可能减少部分关联风险，却也会破坏跨边界的诊断连续性。两者都不该只因配置最短就被采用。

更合适的选择是把边界与目的写清。哪些内部入口接受经过身份确认的上游决定，哪些公开入口需要独立预算，出现压力时能否降低记录比例，怎样保留必要的跨边界关联，都应成为可评审策略。某个方案是否能保留父子关系或需要建立新的链路，需要按具体传播和采样语义核对，不能只改最后一位就称作规范兼容。

记录上限还应覆盖多个资源面。限制导出字节，不一定限制应用创建事件和属性的成本；限制请求数，也不一定限制每个请求的链路体积。可按入口、租户或可信调用方设计适合的预算，但不要用未经验证的任意分类误伤关键操作。限速自身也需要可观察状态，避免记录缺失长期被误判成业务没有问题。

内部上游可信，是否就可以直接沿用它的采样？

可以把可信上游作为策略输入，但“内部”必须由可验证的连接与身份关系定义，不能由一个同名请求头自我声明。若外部流量经过反向代理后看起来都来自内网地址，而原始上下文又原样透传，仅检查网络来源可能没有区分真正的调用者。需要明确在哪一层完成身份判断，以及可信标记是否能被用户覆盖。

即使来源可信，两边负载和记录成本也可能不同。一个上游选择全部保留，不代表下游仍有同样资源。应协调采样承诺和降级条件，并向调查者暴露实际决策，防止把不完整链路解释成下游根本没有执行。完整性承诺需要沿整条采集与导出链验证，不能从入口采样一项配置推导。

拟议验证使用无敏感数据的受控请求，固定相同业务操作与请求量，分别改变缺失上下文、非法格式、sampled 零与一、可信来源与未知来源。观察实际解析、本地决定、导出量和资源消耗，而不只看响应是否成功；再制造预算压力确认业务结果与必要审计仍满足约定。本文没有执行这些测试，不报告成本节省或攻击防护效果。

排障时还要保留选择偏差：被采样留下的链路，不自动代表全部请求的错误分布。业务计数与必要审计应有各自可靠来源。与尾部采样的数据接收范围结合阅读时，先问谁有权决定记录成本，再问链路是否完整；二者都不能单靠一个 sampled 位证明。

压力验证还应有独立观察通道。只统计成功导出的链路，可能看不到在应用端已经产生却未导出的工作。可在受控环境中观察进程资源、队列和供应商接收量，并明确各自分母；不要让同一条被限额的遥测链既作为被测对象，又独自证明没有额外成本。若监控本身缺测，就把效果保留为未知。
