Cookie 的 Path 只能缩小发送范围，不能隔离同源权限

Cookie Path 决定浏览器在哪些请求中附带值，不是授权或同源隔离边界。本文拆解路径匹配、同名 Cookie、迁移清理和服务端权限验证。

正文

核心要点

  • Path 按请求路径筛选 Cookie 发送，不构成授权或同源隔离。
  • Cookie 请求头不带 Path 元数据；同名不同 Path 的值可能并存，服务端不得依赖排列顺序。
  • 迁移和注销要按旧 Domain 与 Path 清理各范围，并在服务端撤销旧会话。

给后台会话设置 Path=/admin，只能让浏览器少在其他路径请求里附带它；它既不代表服务端收到的值来自 /admin，也不能把同一个 origin 下的前端页面变成互不信任的安全域。Cookie 的 Path 是发送筛选条件，不是授权规则。若团队把它当作权限隔离，既可能漏掉同源脚本的访问路径，也可能在应用迁移时留下仍可被服务器接受的旧会话。

浏览器按路径边界筛选，不识别业务权限

Cookie 的 Path 描述请求 URI 中哪些路径可以携带该 Cookie。RFC 6265（2011 年 4 月发布）给出了路径匹配算法：路径相同可以匹配；Cookie 路径以 / 结尾时，符合此前缀的请求路径可匹配；否则前缀后面必须是路径分隔符 /。因此，Path=/admin 会匹配 /admin、/admin/ 和 /admin/users，不会匹配 /administrator、/ 或 /console。MDN 的 Set-Cookie 说明给出了同类例子，并明确指出 Path 不是安全措施。浏览器的决定是“是否把一个值放进这次请求”，不是“请求方是谁”或“这次操作是否应该获准”。

省略 Path 时也并非没有规则。浏览器根据设置 Cookie 的请求路径计算默认目录。例如在 /account/settings/profile 的响应中创建 Cookie，默认 Path 是该请求路径的目录，而不是一个表示“只允许设置页”的权限声明。代理重写、应用挂载前缀、末尾斜杠和路由迁移都会让团队对有效路径产生误解；实际请求应以浏览器最终访问的 URL 为准，不应只看应用代码里的路由名。

更关键的是，浏览器发出的 Cookie 请求头通常只有名称和值，不把创建时的 Path、Domain、Secure 或 HttpOnly 元数据附回来。服务端收到 SID=...，不能仅凭这段头部证明它原先绑定到哪个路径。路径筛选由用户代理在发送前执行，而身份验证和授权由服务端执行；两种职责之间没有自动继承关系。对某个资源的操作是否允许，必须从已验证的主体、资源归属、操作类型和当前状态判断；OWASP API1:2023 对象级授权指引也要求每个接收对象 ID 并执行操作的 API 检查用户对该对象和动作的权限。请求路径只是路由信息，也不能代替对象级权限检查。

同源页面仍然不是彼此隔离的应用

假设一个站点把公共页面放在 /，把管理界面放在 /admin，并把管理会话 Cookie 设置为 Path=/admin。公共页面上运行的普通脚本不会因此在每次 / 请求中自动收到这枚 Cookie；这是窄 Path 的实际价值。但同一个 scheme、host、port 组成的 origin 仍然是浏览器的信任边界。MDN 对 document.cookie 的安全说明指出，Path 不能阻止其他路径对可由脚本读取的 Cookie 进行未授权读取：同源脚本可以在 DOM 中创建一个指向 Cookie 路径的 iframe，再访问该文档的 Cookie。这个机制有前提，不能泛化成“任何跨域页面都能读”；跨 origin 访问仍受同源策略限制。若 Cookie 设置了 HttpOnly，JavaScript 不能通过 document.cookie 读取它，但这也不等于 Path 成为授权边界，浏览器仍会在匹配请求中附带 HttpOnly Cookie。

OWASP 会话管理指引一方面建议对 Domain 和 Path 使用尽可能窄的范围，减少凭证在无关请求中的发送；另一方面明确提醒，不应把不同安全等级的应用仅靠同一主机下的不同路径来隔离。其他同源应用可能通过脚本接口接触可读 Cookie，也可能为该主机上的任意路径设置 Cookie。这里的设计判断是：窄 Path 可以作为流量和意外暴露面的收敛措施，但不能成为“公共站点被攻破仍无法触及后台”的安全承诺。如果两个应用确实互不信任，应优先评估独立主机名或独立注册域带来的 origin 边界，同时审查跨域登录、CSRF、部署、证书和运营成本。子域名虽然是不同 origin，但如果会话 Cookie 使用 Domain=example.com，它仍可能被发送到多个子域；无需共享时应省略 Domain，让 Cookie 保持 host-only。仅仅把 /admin 改成 /console 不会创建新的浏览器安全主体。

路径迁移时，名称相同不等于状态相同

Cookie 的一个容易忽略的身份细节是，存储中的替换键由名称、Domain 和 Path 共同组成。名称相同但 Path 不同的 Cookie 可以同时存在；请求头中它们可能以同名字段出现，RFC 6265 还要求服务器不要依赖这些字段的序列化顺序。因为请求头没有带回 Path，后端若用“取第一个同名值”或“取最后一个同名值”来决定会话，就把未定义的排列当成了权限规则。不同语言、框架、中间件或代理对重复名称的解析方式也可能不同，必须针对部署栈验证。

设想应用将入口从 /admin 迁到 /console。旧版本曾设置 SID 且 Path 为 /admin，新版本又在 /console 设置同名 SID。浏览器可以保留两份不同 Path 的状态；某些请求只携带其中一份，也可能在一个能同时匹配的请求中出现重名值。这个例子是用于设计评审的假设场景，不是对某个真实系统的测试结果。安全做法不是依赖哪份值排在前面，而是安排明确的迁移窗口：新会话可使用新名称或有明确版本的会话载荷；服务端对旧会话设定接受期限；到期后撤销旧服务端记录；并分别向浏览器发送旧键和新键的过期响应。

删除 Cookie 也要精确。RFC 6265 的示例说明，若要让浏览器移除一个 Cookie，过期响应中的 Path 与 Domain 必须和创建时使用的值相匹配。只对 /console 发一条同名空值，不会自动清除 /admin 下那份旧键；反过来，在 /admin 响应删除，也不会清理 / 下另一枚不同范围的同名 Cookie。注销流程应检查应用历史上实际发过哪些组合，而不是只按现在配置生成一条删除头。若此前修改过 Domain 或路径，可能需要按旧属性逐项失效；服务端撤销会话依旧是必要动作，因为清除当前浏览器的一个值不能撤回已复制到别处的凭证。

怎样安排验证，才能分清发送与授权

不要用“浏览器在 / 页面没有显示后台 Cookie”作为后台接口安全证明。一个可审查的验证矩阵至少分四层。第一层检查浏览器发送：用干净会话逐一请求 /admin、/admin/、/admin/users、/administrator、/console 和根路径，记录每条请求实际携带的 Cookie 名称；测试不同前缀和斜杠，确认应用部署前缀没有改变预期。第二层检查同名状态：同时创建同名、不同 Path 的测试 Cookie，验证各路由发送情况以及当前框架、中间件和代理如何解析重复名称；不要把观察到的一次顺序写成协议保证。

第三层必须直接测服务端授权。对已登录主体、未登录主体、无权主体以及资源所有者分别调用敏感端点；交换对象 ID，检查读取、修改、删除等不同动作是否各自拒绝。令 Cookie 缺失、过期、无效和有效但权限不足分别触发可区分的服务端结果。若前端隐藏了管理按钮，仍然要直接请求接口，因为界面条件只能控制显示。第四层检查迁移与生命周期：用旧 Path 会话登录，部署新 Path 后重新登录，执行注销，在新旧路由各自请求，验证旧会话在服务端失效，并检查浏览器端的旧键确实被按原属性清除。还要覆盖同一用户开两个标签页、代理缓存和回滚版本等容易复活旧状态的路径。

以上是建议的验收设计；本文没有在浏览器、框架或线上服务中执行这些测试，也不声称任一系统已经通过。自动化测试可以固定 Cookie 头与权限矩阵，浏览器端测试验证用户代理的发送行为，服务端集成测试检查真实授权，中间件观测则应避免记录完整会话值。测试日志应分别记录“请求是否带值”“服务器是否认出会话”“资源操作是否获准”，不能用其中一项替代另外两项。

窄 Path 仍有用，但要放在正确位置

如果同一应用有清晰的路由分区，缩窄 Path 能减少 Cookie 出现在无关请求中的机会，也能让开发者更容易发现请求是否越过预期范围；这是合理的最小化措施。它不能抵御同源脚本攻击，不能保护服务器免于接受伪造或旧会话，不能取代 Secure、HttpOnly、SameSite 等各自不同的属性，也不能取代 CSRF 防护和每次资源操作的授权检查。安全审查应问“谁创建了这次请求、服务器按什么主体和资源规则作出决定”，而不是只问“浏览器的 Cookie 写了哪个目录”。

在同一主机挂载互不信任或风险等级不同的应用时，Cookie Path 只能做发送范围管理。真正的隔离需要清楚的浏览器 origin 边界、单独的会话体系、严格的服务端授权和可验证的撤销策略。团队仍可以设置窄 Path，但应把它写进部署与迁移清单，说明创建路径、清理旧键的属性、服务端接受期限，以及验证旧值无法继续授权的证据。这样 Path 就回到它可靠的职责：控制浏览器何时带上一个值，而不是替整个系统宣告权限边界。
