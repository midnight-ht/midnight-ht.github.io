记录规则有结果，原来的实例标签为什么不见了？

记录规则输出的是新序列；聚合、向量匹配和标签覆盖都可能改变身份。按表达式、规则组与下游查询逐层排查。

正文

核心要点

  • 记录规则输出新序列，数值存在不代表保留原始 instance 身份。
  • 聚合、向量匹配、规则标签覆盖和规则组漏跑是不同故障路径。
  • 把指标名、输出标签和下游查询作为一个契约，并用规则测试断言标签和值；本文方案未执行。

记录规则即使成功产出样本，也可能不再带着源序列的 instance 标签：表达式决定哪些维度留下，规则标签随后还可以新增或覆盖输出标签。看到记录指标有值，却按原来的实例过滤不到结果时，不要先把它归为抓取故障。应把原始序列、PromQL 表达式结果、记录后的序列和规则组运行状态分开核对；这几层分别回答“采到了什么”“计算保留了什么”“规则是否及时写出”。

记录结果是一条新序列，不是原始序列的副本

Prometheus 的数据模型用指标名与一组标签共同识别时间序列，增加、删除或改变任意标签值，都会形成不同序列。数据模型文档因此是排查的起点：在图表中看到相同的数值，并不意味着两个时间序列代表同一组对象。

记录规则把表达式的结果按指定的记录名保存为一组新序列。记录规则文档说明，规则按周期计算，输出指标名来自 record 字段；结果标签则取决于表达式以及规则配置。记录规则的价值是预先计算常用或昂贵表达式，降低重复查询的工作量。它不是给原始序列添加一个别名，也不承诺复制所有输入标签。

看一个假设例子。采集序列可能是 api_http_requests_total{job="checkout",instance="api-1",path="/pay",method="POST"}。若表达式按路径和方法汇总不同实例，表达式结果不再区分 instance，但仍可以保留 job、path、method。随后记录规则以一个新的指标名保存这个输出。此时按实例筛选没有结果，可能是聚合本来就消除了该维度；数值存在与实例可追溯性是两项不同的契约。

Prometheus 的规则命名建议把 level、指标与运算写成 level:metric:operations，其中 level 表示输出聚合层级及保留的标签。规则命名与聚合建议还建议写出 without 中被移除的标签，以保留其他标签，例如 job。比如 sum without (instance) 表示把实例维度聚合掉，同时让其余标签继续参与分组；它不是“保留 instance 的求和”。这也是名称和表达式需要一起审查的原因：名字说是路径级，标签却意外带了某个实例，读者就会收到相互冲突的身份信号。

标签在哪一步消失，要按转换顺序找

先单独查看原始指标，确认目标时间和筛选条件下是否存在预期标签值。再运行规则中的表达式本身，观察输出标签集；最后查看记录指标，判断记录名之外是否又发生标签变化。每一步都应固定时间范围和匹配条件，否则查询窗口不同也会把“没有样本”伪装成“标签丢了”。

第一种路径是聚合。sum by (job, path) 会明确将输出按列出的维度分组；sum without (instance) 则表达移除 instance、保留其余维度的意图。两种写法在其他标签集合变动时有不同维护特性：by 更适合输出维度必须被明确封闭的契约，新增输入标签不会自动进入分组；without 适合只想剔除少数已知维度并保留其他有意义标签的场景。选择不是格式偏好，而是在定义未来标签变更会不会悄悄改变结果身份。

第二种路径是向量匹配。算术表达式把左右两侧向量按标签匹配；on(...) 指定用于匹配的标签，ignoring(...) 指定从匹配条件中排除的标签。官方操作符文档指出，没有匹配对象的元素不会出现在算术结果中。向量匹配说明给出的例子中，错误率与请求总量按 method 匹配，只有两边都存在的方法才返回结果。于是某个标签值“不见了”可能是分子或分母没有对应序列，而非规则配置删除了标签。若使用 group_left 或 group_right，还要确认一对多关系真的符合数据语义；它们不能被当作修补不匹配数据的通用开关。

第三种路径是规则标签。规则组可以在保存结果前添加或覆盖标签；单条规则的标签也可以添加或覆盖，且遇到冲突时规则级标签覆盖组标签。若表达式已经输出 environment="prod"，某条规则再把 environment 固定为 test，记录值仍可能正常，但身份已经被改写。把 instance 固定写成 all 也不会恢复源实例信息，只会制造一个新的、含义不同的维度。需要保留原身份时，应从表达式输入与聚合层级上设计，而不是在末端伪造同名标签。

结果缺失也可能是规则没有按期完成

“标签不存在”和“这一时刻没有记录样本”要分开调查。规则组内规则按顺序执行；如果一次组评估没能在下一次间隔前完成，Prometheus 会跳过后续迭代，直到前一次完成或超时，并增加 rule_group_iterations_missed_total。规则执行说明指出，这种慢评估会让记录指标出现时间缺口。

因此按原 instance 过滤没有样本，至少有几种不同解释：表达式聚合移除了实例；向量匹配没有配对；规则标签覆盖了原值；输入本身在该时间段缺样本；或者规则组错过了迭代。逐层查可以把这些情况拆开：看源序列是否新鲜，表达式是否返回预期标签，记录指标是否存在，再查看规则评估错误与 missed-iteration 指标。若表达式即时查询有结果而记录序列在若干评估时刻缺失，应优先检查规则调度和评估耗时；若记录值持续存在但标签集始终不同，则更像契约设计或配置覆盖。以上是诊断顺序建议，并非来自某一真实现场。

还要避免将空标签和值为空字符串混为一谈。Prometheus 数据模型将空标签值视同标签不存在。查询中期待 zone="" 不一定是在查找一个明确的空值身份；在解释标签缺失前，应核对采集端到底省略了标签、输出配置是否添加了空值，以及选择器实际匹配规则。

下游查询把标签契约当成接口

记录指标常被多个面板和告警复用。若旧面板依赖 instance，把记录规则改成跨实例汇总，即使新规则计算正确，面板也无法继续回答“哪台实例有问题”。告警如果按 service 路由，而规则把它覆盖成固定值，通知可能仍会发出，却不再带有正确服务归属。只检查规则 YAML 可被解析，不能证明下游语义没有改变。

改动前可以从消费者反向列出契约：哪些查询要求逐实例定位，哪些面板只看路径总量，哪些告警依赖环境、集群或服务标签。再决定这条记录规则的级别。如果要服务总体趋势，移除 instance 可能合理；如果要故障定位，就需要另一个保留实例维度的序列或回到原始指标。并非每条记录指标都必须携带全部标签，因为高基数维度也会增加序列量与存储成本。选标签要同时回答“谁会据此分组或路由”和“这个值在聚合后仍然真实吗”。

要注意记录规则的命名与输出标签需要配套。Prometheus 的命名建议用 level 表达聚合层级，而不是只按内部实现给规则起名。提交变更时可将新旧规则的输出标签集写在评审说明里，例如：旧规则按 instance、path 区分，新规则按 job、path 区分；确认哪类消费者不再能逐实例定位，哪些消费者不受影响。这样的描述比“优化了指标”更便于团队评估风险，也更容易在回滚时判断恢复的究竟是哪一项语义。

用规则测试验证精确标签，而不只检查数值

Prometheus 提供 promtool test rules 对规则文件执行测试；测试格式可以提供输入序列，并声明 PromQL 表达式预期返回的样本。规则单元测试文档支持用期望样本检查具体标签和值。对于标签契约，测试断言应同时覆盖记录指标名、保留标签、移除标签和标签值，不要只断言最终数值等于某个数字。

一个尚未执行的测试设计可以放入两台实例、两个路径的假设输入：先检查实例级中间规则仍包含各自 instance；再检查 sum without(instance) 的路径级输出没有 instance、但保留 job 与 path；最后加一条规则级 environment 标签，并单独构造与组标签冲突的情况，断言优先级符合预期。另一个用例为向量运算的一侧缺少 method 值，确认没有匹配项时结果集合按预期减少，而不是误以为输出补了零。这里描述的是测试矩阵，不是本文实际运行过 promtool 的结果。

静态规则检查和样本级规则测试回答的问题也不同。promtool check rules 可在不启动 Prometheus 服务的情况下快速检查规则文件语法；通过只能证明语法有效，不能证明标签集合符合仪表板需求。单元测试能够验证给定输入和评估时间下的结果，但也不能证明生产中的采集配置、查询负载、规则耗时或所有历史标签值都与测试夹具相同。因此上线前仍要看目标环境的规则组状态和真实消费者查询，必要时在维护窗口观察输出变化。

建议把评估失败、组耗时、错过迭代、源指标新鲜度和输出标签集作为不同观察项记录下来。若输出少了一项，先确认是结果数值为零、向量里没有元素，还是序列有样本但标签身份不同；三者在图表上都可能显示为空，却需要完全不同的处理。前者涉及算式，第二种通常涉及匹配或输入可用性，第三种涉及身份契约。调试时保留原始查询和改动前后的输出样本，可以让修复依据可复查。

结论：明确记录规则输出“代表谁”

记录规则成功并不意味着输出仍能逐实例定位。表达式决定哪些输入维度参与分组，向量匹配决定哪些元素能够成对计算，规则组与规则标签又可以改变保存后的键值；评估漏跑则会造成某些时间点没有新样本。看值之前，先画清这条变换链，分别确认序列身份、标签来源、计算匹配和运行状态。

设计时只保留对输出语义有用且真实的标签，为每个被删除或覆盖的维度说明原因；将名称、标签集和下游看板/告警一起做变更评审，并用规则测试断言预期标签和值。本文依据 2026-11-25 查阅的 Prometheus 当前官方文档；官方下载页当日列出 3.16.0（2026-11-04）为 Latest、3.13.5（2026-10-21）为 LTS。文中的规则行为描述的是所链接的当前文档，不宣称只适用于 3.16，也不自动外推至兼容产品。本文没有实际运行 Prometheus、promtool、生产查询或告警验证，假设序列与测试矩阵均为解释用途。更多标签维度的资源取舍可参阅标签基数预算；下游告警窗口与规则消费者见多窗口 SLO 消耗率告警。
