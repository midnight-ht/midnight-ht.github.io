标记 xfail 的测试恢复通过，为什么流水线仍可能放行？

默认 XPASS 会被报告但不一定让套件失败。严格设置改变门禁，不证明断言仍覆盖原缺陷；按 pytest 版本核对配置并保留退出依据。

正文

核心要点

  • 默认 XPASS 通常只进入报告；strict=True 或 strict_xfail 才会把它变成套件失败。
  • XPASS 可能表示实现修复，也可能表示断言或测试条件已失效。
  • 移除标记前要验证原要求、当前配置、pytest 版本和目标提交。

默认情况下，pytest 会报告意外通过，但不会因此让整个测试套件失败；严格 xfail 能把它变成门禁失败，却不能证明断言仍覆盖原缺陷。看到流水线变绿，或者把 XPASS 改为失败，都只是测试结果的一部分。要判断例外是否可以移除，必须回到被保护的需求、测试实际走过的路径、当前 pytest 配置和准备合并的提交。

XPASS 可见，但默认不一定失败

xfail 标记表达的是“这个测试预计会失败”。当测试实际通过时，pytest 把它报告为 XPASS；当它仍按预期失败时，会报告 XFAIL。pytest 当前稳定文档明确说明，默认情况下 XFAIL 与 XPASS 都不会让测试套件失败。也就是说，XPASS 不是普通的 PASS，但如果没有调整严格性，CI 仍可能以成功状态结束。pytest 的 skip/xfail 指南把 XPASS 描述为预期失败测试意外通过后的单独报告结果，并列出控制行为的 strict 参数。

这解释了表面上的矛盾：报告中能看见一个本应被注意的标记，退出状态却仍符合流水线设置。默认策略适合先把意外通过暴露出来而不立即中断旧套件，但如果团队把绿色门禁视为已经处理完所有例外，XPASS 就容易成为长期噪声。反过来，单纯让每个 XPASS 都令构建失败，也可能在大量旧例外上一次性制造工作队列；严格性需要配合维护责任和修复顺序。

严格性改变门禁，不改变断言含义

局部方式是在特定测试上指定 @pytest.mark.xfail(strict=True)。该测试如果意外通过，会让整个测试套件失败。它的影响范围较窄，适合已经有明确缺陷编号、且团队希望在该条件消失时收到阻塞信号的用例。需要注意，严格模式失败并不代表 pytest 判断业务正确性；它只按照标记契约指出“本来预期失败的测试现在通过了”。

项目也可以设置全局默认值。当前稳定文档使用 strict_xfail = true，用于让所有未单独覆盖严格性的 xfail 标记在 XPASS 时失败。API 参考列出 strict 参数与 strict_xfail 配置，并说明默认值为 false。局部显式值与项目默认值的优先关系应按当前配置和 pytest 版本核对，不要只看某个装饰器就推断整套测试的行为。

这里有一个版本迁移细节：pytest 9.0 将配置名从 xfail_strict 改为 strict_xfail，同时保留旧名称作为别名。稳定文档的变更记录还显示，pytest 9.2.0 在 2026-10-27 发布；这是本次核对文档时列出的当前稳定版本背景，不代表 xfail 严格行为始于 9.2。pytest changelog与 API 参考是依据。老项目如果锁定较早的 pytest 版本，应查看对应版本文档与实际运行环境，不要把新配置名复制进去就认定设置已经生效。

也要避免把 --strict 当成“只让 XPASS 失败”的快捷写法。pytest 9 起，较宽泛的 strict 选项会启用多个严格性配置；API 参考提醒，未来新增的严格选项也可能受其影响，因此只有在版本锁定并接受整体范围时才适合启用。若目标只是维护 xfail 行为，显式配置更容易解释门禁为什么改变。

同一个意外通过，可能来自两个相反原因

假设一个跨租户读取测试因为已知授权缺陷被标记为 xfail。后来 XPASS，存在至少两种解释。第一种是实现修复：请求现在正确拒绝另一个租户的数据。第二种是测试不再经过原来的授权路径，例如 fixture 被改成同一租户、路由不再调用受保护的读取函数，或者断言只检查响应结构而不再检查数据访问。两者都能让测试函数不抛出预期异常，但它们对发布的意义完全不同。这里是分析示例，没有执行真实测试或声称项目曾发生该缺陷。

这种区分要求先恢复 xfail 的由来：原来希望看到什么输入、哪项业务结果、为什么预期失败、关联了哪个缺陷或支持范围。然后把这些条件与当前测试代码逐项比对。确认身份、租户和目标资源仍处于原来的跨界组合；确认调用仍经过真正负责授权的入口；确认断言直接检查“不可读取”的业务结果，而不是只检查某个错误对象或状态字段存在。

如果当前测试不再检查原要求，应修复测试，再观察它在目标提交上是 PASS、FAIL 还是 XPASS。若修复后的有效测试仍 XPASS，这才是实现可能已改变的证据之一；仍需要独立确认生产代码、接口合同及相关权限路径。若测试仍然按预期失败，则 xfail 可能还有必要，但它的原因与范围也要重新确认。删除标记本身不是修复，标记继续存在也不是自动接受风险。

将 xfail 当作维护中的例外记录

pytest 提供 reason、raises、run 与 strict 等标记参数，但没有内建的到期日期、责任人或缺陷完成状态。团队可以在标记文本或相邻代码审查记录中保存可追溯的缺陷编号、预期行为、适用条件、责任人和结束条件；这些属于团队约定，不是 pytest 自动验证的字段。结束条件应该可检查，例如“目标缺陷修复后，该测试在受支持的 Python 与依赖版本上重新验证”。单纯添加一个未来日期，不会让 pytest 到期时自动执行或删除标记。

raises 能把预期失败范围缩小到指定异常类型；否则某个与缺陷无关的异常也可能被误认为“符合预期”。如果测试函数因为已知段错误不能安全运行，run=False 会让它不执行并始终标为 xfail。这两种用法都与“正常运行但意外通过”不同。特别是 run=False 的测试没有验证当前实现，所以不得把它报告成刚刚通过的证据。

还应区分 xfail 和 skip。skip 表示条件不满足时不运行测试，例如所需数据库不可用；xfail 表示测试运行但预期会失败。把环境不具备条件的测试标成 xfail，可能产生误导的 XFAIL/XPASS 记录。反过来，把实际执行后发现的失败改成 skip，也会隐藏代码行为。测试计划需要明确“是否执行”和“执行后结果”两件事。

对历史标记较多的项目，启用全局严格模式可能一次揭示许多旧 XPASS。此时应分批定位原因，先确认每个用例是否仍覆盖需求，再选择本地 strict、全局默认或保留宽松模式。不要只为恢复绿色而把全部异常归类成可接受，也不要把全局严格失败数量直接当作缺陷数量：其中可能混有已修复、测试退化、条件变化或配置错误。

验证标记和流水线真正使用的配置

可以提出一组未执行的验证步骤：准备一个明确会失败的用例与一个会通过的用例，分别套用 marker-level strict 和项目级 strict_xfail；观察报告中的 XFAIL/XPASS 分类及最终退出状态。当前文档建议用 -r 选项显示额外结果，例如 pytest -rxXs，可以让汇总更清楚，但报告格式本身不能代替断言审查。还应确认文件被收集、测试实际运行、marker 确实应用，且 CI 没有调用另一个工作目录、环境或配置文件。

若想临时验证某个配置值，可在受控命令中覆盖 ini 选项，但实际参数名称要匹配当前 pytest 版本；pytest 9 文档中的示例使用 -o strict_xfail=true。在版本升级前后，最好记录 python -m pytest --version、配置文件路径、运行命令、测试选择器和提交 SHA，再对目标提交运行完整相关测试。这里只给出建议，没有执行这些命令，也没有实际 XPASS 输出。

决定移除标记时，保留证据指向真正准备合并的代码和环境。另一个分支或较新的依赖环境中通过，不能自动证明当前提交满足同一条件；问题单关闭也不是测试断言仍有效的证明。strict xfail 的价值是把“预期失败已经改变”变成可见信号，后续的人仍要判断信号的原因和应采取的动作。

若希望继续核对测试是否能发现真实回归，可阅读变异测试与断言缺口。XPASS 负责提示预期与实际不再一致，不负责说明业务缺陷是否已经修复；门禁、断言和需求证据共同决定能否移除例外。
