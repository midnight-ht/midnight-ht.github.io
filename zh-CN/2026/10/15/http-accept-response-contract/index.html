Accept 是偏好，不是保证：客户端如何核对实际 HTTP 响应

Accept 表达客户端愿意接收哪些表示；响应状态、Content-Type、正文语法和业务结构仍须分别检查，406 也不是服务器必须返回的结果。

正文

核心要点

  • Accept 表达媒体类型偏好，不保证响应采用该类型；服务器可以忽略协商字段，或在不愿提供默认表示时返回 406。
  • 按状态决定是否读取正文，再分别核对 Content-Type、语法、schema 和业务状态；204 不携带额外响应内容。
  • 只有表示确实随 Accept 变化时才让 Vary 参与缓存变体；本文测试矩阵是未执行方案。

请求写了 Accept: application/json，拿到响应后却在 JSON 解析处失败，这不能直接证明服务端“返回了坏 JSON”。客户端声明的是对响应媒体类型的偏好；它还需要检查 HTTP 状态、实际 Content-Type、正文语法以及业务结构。把这些边界都塞进一次 response.json()，会让错误被压成一个模糊的解析异常。

偏好与实际选择要分别记录

Accept 出现在请求中时，表达发送方对响应媒体类型的偏好，例如更愿意处理 application/json。服务端可据此进行内容协商；选定表示后，响应中的 Content-Type 用来说明实际发送的媒体类型。RFC 9110 的 Accept 定义定义 Accept，Content-Type 定义定义 Content-Type。两者方向不同：前者说“我偏好什么”，后者说“这次实际给了什么”。它们都不描述 JSON 对象有哪些业务字段。MDN 的 Accept 文档也指出，浏览器会根据请求上下文设置不同的默认值，所以某个浏览器请求成功不能证明其他客户端发送相同偏好或得到相同表示。

偏好可以带质量值。例如 Accept: application/json, text/html;q=0.2 表示 JSON 的相对偏好高于 HTML；未写 q 时默认权重为 1，q=0 则把相应范围标记为不可接受。没有 Accept 不是“客户端不懂任何类型”，而是该协商维度没有偏好。通配符 / 会扩大愿意接收的媒体类型范围，却不会让调用方的解析器突然具备处理图像、HTML 或二进制数据的能力。

更容易被误解的是 406 Not Acceptable。它不是服务器发现不匹配后必须返回的唯一结果。RFC 9110 的协商字段处理规则允许源站在没有可接受表示时返回 406，也允许源站忽略该协商字段，把请求当作不受它影响；406 定义将 406 限定为服务器不愿提供默认表示的情形。因此，即使请求偏好 JSON，调用方也必须准备好实际返回其他表示。反过来，服务器可能返回 406，而响应正文仍采用 JSON 描述错误；状态码和错误正文格式是两项独立约定。

一个可靠的客户端不要先假定“有响应就解析成成功对象”。先看请求是否正常完成，再按接口契约区分状态。对于 2xx，继续判断该状态是否预期携带正文；例如 204 定义 中的 204 表示请求成功且没有额外响应内容，调用方不应无条件读取 JSON。对于 4xx 或 5xx，应走错误处理分支，但也不能从错误状态推断正文一定是 JSON。API 可能用 JSON 描述验证错误，反向代理或 CDN 也可能提供 HTML 错误页面；这类情况是常见故障路径的假设示例，本文没有对某个真实服务执行请求。

这样分层能防止错误归因。若超时或连接失败，问题处在传输层；若收到了 401，调用方应执行授权失败策略，而不是把它记成 JSON 语法错误；若状态为 200、类型为 text/html，则状态是成功而表示契约不符；若类型声明为 JSON 但字节不是合法 JSON，才是语法解析失败。每种错误都可能需要不同的重试、用户提示、日志字段和告警分类。单一的 catch 可以兜底，但不应抹去此前已经取得的状态与头信息。

放宽接受范围也有代价

通配类型让请求愿意接收更广内容，但不会自动让业务解析器具备处理这些内容的能力。若产品只支持某种结构，仍需对实际输入做相应判断。扩展媒体偏好时，应同时检查解析、错误提示和安全处理范围，不应为了让服务器不再拒绝就无条件接受任何响应。

Content-Type: application/json 是发送方对表示格式的声明，不是对每个字节、对象字段或业务含义的证明。application/json; charset=utf-8 的参数不应让客户端误以为媒体类型换了；检查时通常需要解析媒体类型的本体，而不是脆弱地用字符串完全相等。但媒体类型检查只是选择解析器的门槛：JSON 能解析为 {}，并不代表它符合接口所需的 {id, state} 结构；结构符合，也不代表 state 在当前操作中允许。

浏览器 Fetch 的 Response.json() 按 Fetch 标准消耗响应正文并从字节解析 JSON，正文不是合法 JSON 时可能以 SyntaxError 拒绝。该方法本身没有替调用者执行“声明的 Content-Type 必须是 JSON”这一契约检查，也不会验证业务 schema。由于响应正文是一次性流，先调用 json() 再调用 text() 通常不能取得同一正文的第二份副本。若诊断确实需要保留文本，应在读取前设计一次性读取策略，考虑大小上限、敏感信息脱敏和日志留存，不能为了排障无限记录正文。

用 Fetch 写客户端时，适合把处理顺序显式化。下面是实现设计而非运行结果：先检查 response.status，区分预期成功、无正文状态和错误状态；再检查 Content-Type 是否属于该状态允许的表示；随后选择解析器，最后验证 schema 和业务约束。204 等无正文状态应在正文读取前单独处理。若错误响应也支持多种格式，应定义独立的错误解析分支；未知或错误的类型应返回可诊断的“不支持表示”结果，而不是连续尝试多个解析器，直到某一个碰巧不抛异常。示例没有在本地或线上执行。

对媒体类型的允许集合也应由接口定义，而不是写成无边界的猜测。有的服务只允许 application/json，有的服务明确采用其他 JSON 媒体类型。若要支持结构化语法后缀，应把这种行为记录成接口约定并测试；不能因为某个类型名字看起来像 JSON，就假设其对象结构与现有模型兼容。HTTP 头也不替代安全验证：不能仅因类型为 JSON 就信任输入、跳过大小限制、schema 校验或授权判断。跨源响应还受 CORS 可见头限制：即使服务器发了自定义头，浏览器脚本也可能无法读取。MDN 的 CORS 响应头说明指出，Access-Control-Expose-Headers 用来把额外响应头加入 JavaScript 可访问列表；因此诊断时应把“头不可见”与“头缺失”区分记录。

用真实返回组合验收

与其写一个“接口返回 JSON”的笼统断言，不如为每个操作列出状态与表示组合。下面是建议的测试矩阵，尚未在项目或目标 API 上执行：成功的 200 JSON 应通过语法、schema 和业务状态检查；204 应返回无正文结果；401 JSON 错误应进入身份处理分支；502 HTML 代理页应保留状态和类型并走可诊断的上游失败处理；200 HTML 登录页不能被当作成功 JSON；JSON 语法有效但缺少必需字段的正文则应失败于 schema，而不是媒体类型。

这些例子能明确几个常被漏掉的分支。若客户端跟随重定向，最后到达的响应可能来自登录页或另一资源，最终 URL 与响应头应纳入诊断。若 Content-Type 缺失或错误，RFC 9110 §8.3 允许接收方按约定假定通用类型或检查数据；但 MIME sniffing 可能得出错误结论并引入安全风险。若实际收到重复字段，调用方还需要明确容错与拒绝策略，不能悄悄把嗅探结果当作 API 契约。对服务端来说，也要测试客户端不发送 Accept、发送具体媒体类型、发送通配符、以 q=0 排除类型以及不支持类型等请求，确保它实际采用的回退与 406 策略有文档可依。

测试的断言应包括状态、Content-Type、必要的响应头、解析结果分类和用户可见行为；只检查“Promise 成功”会漏掉 404 页面被错误解析，只检查解析异常则可能把预期的 204 当故障。还要区分“客户端不能读取正文”的安全策略和“正文格式不支持”的协议结果，避免把 HTML 错误页完整写进日志。未执行的契约测试只能作为测试设计，不能报告为通过。

若同一 URL 会依据 Accept 返回 JSON 或 HTML，共享缓存需要知道所选表示依赖了哪个请求字段。RFC 9110 的 Vary 规则用于表达这种选择条件；服务确实按 Accept 变化时，应核对缓存配置是否把它纳入变体键。不是每个带有 Accept 的请求都必须添加 Vary: Accept：如果响应表示根本不随该字段改变，机械加上它可能制造不必要的缓存碎片。缓存键、响应声明和源站的实际协商行为必须一致。相关的表示选择与缓存键分析见同一 URL 的 Vary 表示键。

排查时可以按这个顺序保留证据：请求方法与最终 URL、Accept 偏好、HTTP 状态、响应 Content-Type 与 Vary、正文解析结果、schema 结果，再到业务状态。这个顺序不会替服务定义契约，但能让团队知道失败发生在哪一层。Accept 帮助双方协商表示；响应处理代码负责验证实际结果。两者缺一不可，也不能互相替代。
