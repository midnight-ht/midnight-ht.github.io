新标签页里的 sessionStorage，为什么会带着旧值？

sessionStorage 通常按源和标签页会话隔离，但有 opener 的新辅助上下文可以获得初始副本；要按任务身份区分新建与恢复，不按键是否存在决定。

正文

核心要点

  • sessionStorage 不是每次打开页面都清空；opener 初始复制、后续独立修改和重载保留是不同事件。
  • 草稿要绑定任务 ID 和恢复意图，新建流程不能仅因键存在就自动采用旧值。
  • 存储可能受策略限制或写入失败，恢复方案应给出可见降级和验证边界。

新标签页出现旧值，不必然说明 sessionStorage 在标签之间持续同步：有 opener 的新辅助浏览上下文可以先拿到 opener 存储的副本，随后两边各自变化；重载又会保留当前页会话。WHATWG HTML Standard 与 MDN 的 sessionStorage 文档描述的关键不是“标签页永远互不相干”，而是页面会话与打开关系共同决定初始化。应用应把草稿绑定到明确的任务身份，并区分“新建”和“恢复”；不要只因键值存在就自动填入新任务。

按源和顶层浏览上下文划分，不等于必定空白

MDN 将 sessionStorage 描述为按 origin 与浏览器标签页会话划分的存储。同一顶层页面里的同源文档可以使用该页面会话对应的存储；跨源嵌入文档则使用自己的源对应区域。它与只按 origin 隔离的 localStorage 不同。所谓“标签页作用域”说明了常规并行页面之间的边界，不是说新建页面时浏览器一定把所有初始状态抹掉。

WHATWG HTML Standard 在 sessionStorage getter 的规则中指出，创建新的辅助浏览上下文和文档后，会复制 session storage。MDN 对这个场景的说明更直接：新页如果有 opener，会先得到 opener sessionStorage 的副本；两者仍是分离的，之后一方修改不会同步到另一方。这里有三个时间点：打开者已有的数据被复制、子页初始化、子页和原页分别继续写入。只观察子页第一次读取到的旧值，会把第一步误判为后续持续共享。

是否存在 opener 与应用打开页面的方式有关。站内脚本调用新窗口、带 target="_blank" 的链接以及用户直接在地址栏输入，并不应该不加区分地归为同一实验条件。若产品不需要 opener 能力，可以使用移除 opener 的方式降低复制路径；但这应按实际浏览器与链接配置验证，不能把“我看到一个新标签”当作足够的证据。更值得单独判断的是，浏览器的初始复制只解释数据从哪里来，不说明产品是否应该采用它。

页面会话还能跨刷新和恢复继续存在，直到相应标签页或窗口会话结束；关闭后才结束这份会话数据。因此，重载后旧值仍在与“打开一个带 opener 的新辅助上下文时初始复制”是两种不同原因。排查时应记录页面的创建方式、opener 状态、origin、存储键的读写时点和是否经历重载，而不是只记一个“新标签”标签。

用两个并行订单说明为什么需要任务身份

HTML Standard 的 Web Storage 介绍用并行购买窗口说明按页面会话隔离的用途：如果所有窗口共享一个代表当前机票的值，用户在两个窗口切换时可能把第二笔订单的状态覆盖到第一笔上。下面进一步构造一个假设流程，不代表本站真实产品或已执行操作。

假设用户在窗口 A 填写去程日期和乘客信息，然后从“另开一个订单”入口打开窗口 B。若 B 由 A 创建且带有 opener，它最初可能拿到 A 中当前的 sessionStorage 副本。假如 B 的初始化只做 if (sessionStorage.getItem("draft")) restore()，那么 B 会把 A 的草稿当作自己已经开始填写的订单。用户在 B 改日期后，A 不会因此自动改变，因为复制之后两边的存储已经分开。此时用户看到的是“带入了一次旧状态”，不是“窗口间实时同步”。

修复点不应是盲目将 draft 换成 bookingDraftV2：如果子页复制了整个 opener 存储，新键也会一起复制。可维护的合同至少要描述任务 ID、创建或恢复意图、草稿版本和适用用户。新建流程生成一个新的任务身份，读取时只接受明确属于该身份的记录；恢复流程由用户显式选择一个待恢复任务，且必须再次确认当前身份与服务端权限。应用还应避免把尚未确认的本地表单自动提交为已保存订单。

一种简化设计是把每份草稿包装成带 taskId 和 schemaVersion 的记录，并让“新建”动作先创建新 ID，而不是沿用从 opener 复制过来的 ID；“继续编辑”则带着用户选择的草稿 ID进入恢复路径。应用可把当前任务 ID 放在该页面的路由状态或业务上下文中，再比较记录上的 ID。若版本不兼容，显示可理解的恢复选项，而不是把旧字段默默拼进新模型。哪些字段要重新确认，应根据业务风险定义，例如付款方式、收件地址或影响价格的选项。

这不是说所有场景都要添加一套复杂版本系统。单个标签内刷新恢复一个短表单，可能只需一个有边界的草稿键和明确的清理点。允许用户并行开启多笔交易，才需要多份任务身份和选择器。判断依据是并行任务是否真实存在、草稿是否需要跨刷新恢复、丢失或串用的代价以及是否能安全重新读取，而不是 sessionStorage 这个名字让人联想到“临时”。

什么时候应该清理，什么时候应该保留

如果每次页面启动都执行全局 sessionStorage.clear()，新建流程可能更容易变成空白，但刷新、返回和意外恢复也会丢掉用户希望保留的输入。全局清除还可能删除同一标签页中其他功能自己的状态，例如正在进行的多步流程标记。反过来，如果任何非空键都自动恢复，旧任务就可能被带入一个新任务。这两种策略都把不同用户意图压成了“有值/没值”一个条件。

更可控的生命周期是按产品动作清理具体命名空间或具体任务：用户明确选择“新建”时为新任务分配身份，并使当前编辑器不再读取旧任务；用户选择“恢复”时只读取被选中的任务；成功提交、主动放弃或业务规定的超时发生后，删除对应草稿。删除旧任务前，应确认产品是否需要撤销能力或提交后返回页面。如果同一会话还承载其他流程状态，就避免用 clear() 代替有范围的清理。

sessionStorage 也不是可靠持久化服务。WHATWG 规则和 MDN 都说明存储访问可能因不透明 origin 或用户代理策略而抛出 SecurityError；存储空间受限或被禁时，写入也可能失败。产品如果把“调用 setItem”作为“草稿已安全保存”的证据，就会在异常路径上误报。界面可以显示本地保存不可用，并提供继续编辑但暂不承诺恢复的反馈；对丢失代价高的草稿，考虑服务端保存或其他有清晰授权、冲突和保留合同的机制。

改用 localStorage 也不是自动修复。它可以跨窗口共享且生命周期更长，恰好会使并行任务的键碰撞更容易成为跨窗口共享状态问题。需要大量或长期数据时可以评估 IndexedDB 或服务器端草稿，但更换介质会引入自己的事务、过期、冲突和身份验证边界。本站IndexedDB transaction lifetime讨论的是另一种持久化生命周期；存储 API 不会替业务定义何时算新任务、何时允许恢复。

怎样验证“旧值从哪来”，以及没有执行的部分

建议为目标浏览器和产品支持范围建立矩阵。先在窗口 A 写入一个带唯一测试任务 ID 的值，再用产品真实入口打开窗口 B，记录 B 第一次读取的值、opener 是否存在、两窗口后续写入是否互相可见。再以没有 opener 的方式重复，比较是否仍出现初始副本。所有这些应在无敏感数据的测试环境进行；不能依据某一浏览器的一次操作推断全平台表现。

接着分别测试刷新、浏览器恢复、关闭标签页后重新打开、切换用户、新建任务、恢复旧任务和存储策略拒绝。每个场景都写清期望：刷新是否保留、恢复是否需要用户确认、新建是否得到全新 task ID、关闭后是否依产品定义结束、写入异常时界面说了什么。还应验证 opener 子页清理自身命名空间不会影响打开者，任务 A 与任务 B 的修改不会混合，旧版本草稿不会被静默当作当前格式。

这些是拟议验收，不是已执行结果。本文没有运行真实浏览器、隐私模式或本站代码，也没有测量数据保留率。若测试发现受支持环境与标准预期不同，应把浏览器版本、入口方式、opener 状态、策略设置和实际事件顺序一并记录，再决定是改产品流程还是调整兼容策略。不要把“键读到了值”作为完整的恢复通过条件；还要核对它属于谁的任务、是否允许当前用户采用，以及后续保存是否仍能写入。

结论可以落实为一个实现审查问题：这次打开代表继续旧任务还是新建任务？存储值如何证明自己属于那个任务？浏览器无法读写时用户会看到什么？回答清楚这三点，旧值就不再只是浏览器行为的谜，而成为可以选择、恢复和验证的任务状态。
