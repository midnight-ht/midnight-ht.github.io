主任务成功了，finally 为什么仍能让调用链失败？

finally 清理抛错或拒绝会改变返回链的状态，但不能说明外部写入是否提交。分开记录主任务、清理结果和重试依据。

正文

核心要点

  • finally 正常完成时保留原状态与值；清理拒绝时返回链改为拒绝。
  • 链拒绝不等于外部副作用回滚或未提交。
  • 重试要依赖操作身份、状态查询或幂等契约，而不是猜测清理异常。

一次写入已经成功，finally 中的清理却抛错，调用方看到的链仍会拒绝；这并不能证明写入没发生。Promise 描述的是异步链如何完成，不是远端数据库、文件系统或支付服务是否已经提交。要避免把清理错误变成重复操作，必须分别表示主任务结果、清理结果和是否允许重试。

finally 保留结果有一个条件

Promise.prototype.finally() 在原 Promise fulfilled 或 rejected 后运行回调，并立即返回一个新 Promise。MDN 的说明和 ECMAScript 算法都规定：如果回调正常结束，新的链保留原 Promise 的状态；fulfilled 时保留原值，rejected 时保留原拒绝原因。回调返回的普通值会被忽略。它不像 then() 的成功处理器那样把返回值替换为新值，也不把主任务的值或原因作为参数传给清理回调。MDN 对 finally() 的说明和 ECMAScript 规范算法都写明了这条传播规则。

“正常结束”并不表示回调只要被调用就算完成。如果 finally 返回一个 Promise，返回链会等待它 settled。它若 fulfilled，原状态和值或拒绝原因被接回；它若 rejected，返回链也以清理的拒绝原因 rejected。回调同步抛错也会让新链 rejected。于是有两条路径：清理成功时结果透明，清理失败时清理结果覆盖调用方看到的最终 rejection。调用者观察到的是链的完成状态，不是每个阶段的审计记录。

这与 then() 的规则不同。then(onFulfilled) 会把处理器返回的值作为新链的 fulfilled value；抛错会拒绝新链。finally() 的用途是不依赖主任务结果做收尾，所以既不传原值，也不把普通清理返回值作为业务值。MDN 对 then() 返回 Promise 的说明可用来对照。若清理本身需要根据主任务是否成功选择不同动作，就应将成功和失败处理写得明确，而不是期待 finally 获得原结果参数。

最终 rejection 不是回滚回执

设想一个报告保存流程：调用方提交 operationId = R-42，服务端完成保存后，客户端的 finally 释放本地临时占用。释放函数发起的远端请求超时并被拒绝。调用方拿到的 Promise 是 rejected，这只说明被观察的链没有正常 fulfilled；它不能推出服务端的写入回滚了，也不能推出写入一定提交。HTTP 超时、断连或客户端取消都可能发生在服务端已经处理之后。这里是一个假设示例，没有调用真实服务，也没有声称发生过重复保存。

这一区别可以写成两列，而不是一个状态：

主任务 清理 Promise 链可能表现 可采取的下一步
成功 成功 fulfilled，保留主任务值 展示已完成；确认清理不再需要额外检查
成功 失败 rejected，原因来自清理 先按操作身份核对提交状态；不要直接重放写入
失败 成功 rejected，保留主任务原因 根据主任务失败分类恢复或修复输入
失败 失败 rejected，通常只露出清理异常 同时记录两个阶段的错误和关联 ID，定义用户下一步

表格最后一列是应用设计，不是 Promise 规范自动给出的策略。尤其双失败时，finally 的返回链可能只保留清理拒绝。若原始操作失败也需要保留，必须在业务边界分别采集它；不能等链结束后再从一个 rejection reason 推回两个失败。可以把阶段日志挂上相同的 operationId，记录主任务是否收到明确确认、清理是否完成、错误发生在哪个阶段以及时间顺序。日志也不是事务证明，但能让恢复流程不至于丢掉已知事实。

清理职责决定错误该如何呈现

清理不是一种统一等级的动作。关掉加载动画通常不会改变业务写入是否完成；释放分布式锁或归还租约却可能影响后续请求能否安全执行；临时文件清理失败可能形成空间占用，但不一定意味着生成文件失败。设计时应问：清理失败会破坏资源所有权吗？是否会阻止后续任务？是否有独立重试机制？用户需要知道的是主任务未完成、主任务已完成但环境降级，还是两者都未知？

以刚才的报告保存为例，界面可以将结果表达为“保存状态待确认，清理任务失败”，再提供只查询状态的路径；如果服务端按 operationId 支持幂等重试，客户端可根据合同重放同一操作，而不是生成新的身份。若没有读取接口，也没有幂等约定，那么安全做法可能是停止自动重试并交给恢复流程处理。具体选择取决于远端服务合同，Promise 不会替应用创造幂等性。

对于不影响资源与后续正确性的次要清理，团队可以决定记录告警但不让用户把主任务当成未完成。若决定吞掉清理 rejection，也要明确吞掉范围、监控与补偿策略。把所有清理都加 .catch(() => {}) 会隐藏锁未释放等关键故障；把所有清理 rejection 都向用户报告成主任务失败，则会诱导错误重试。正确策略不是“永远吞”或“永远抛”，而是让阶段状态和用户动作相匹配。

如果主任务失败而清理失败，保留两种诊断信息更利于恢复。一个可维护的边界可以在业务函数内部先捕获主错误，再尝试清理，并以结构化对象返回或抛出包含 primaryError 与 cleanupError 的聚合错误；具体错误类型取决于项目运行时和兼容目标。也可以选择以主任务错误为控制流，同时把清理错误写入独立事件。无论采用哪种接口，都应保证日志关联、敏感字段过滤和错误因果顺序明确。不要只保留“最后捕获到的那个”而没有原始异常上下文。

异步清理必须进入等待关系

一个经常遗漏的差别是“启动清理”和“等待清理结束”。下面的写法没有把异步工作返回给 finally：

work().finally(() => {
  releaseReservation(); // 如果返回 Promise，这里没有 return
});

这种写法可能在 releaseReservation() 尚未完成时就让 finally 回调正常返回；之后清理的 rejection 不会沿这条链传播。若调用方必须等待释放并观察失败，应返回该 Promise：

work().finally(() => releaseReservation());

这会让链等待清理，但也带来前述语义：若释放失败，调用方拿到清理拒绝，原成功值不会作为最终结果出现。return 解决的是完成关系和错误可见性，不是如何决定重试、如何保存原始结果，也不提供对多个远端步骤的原子性。若业务需要同时报告两阶段结果，通常应在外层明确组织状态，而不是依赖单条 Promise 结果承载所有含义。

还要考虑 async 函数。finally(async () => { await release(); }) 会返回一个 Promise，因此链会等待。若该 async 清理内部拒绝，效果与返回拒绝 Promise 相同。反过来，调用了异步函数却不 return，或异步函数内部自行吞错，观察者就可能看不到原本期望的失败。审查时应沿调用链追踪返回值，而不是只凭函数名带有 async 就断言已等待。

用操作身份解决“写入究竟发生了吗”

当外部副作用的提交结果不确定时，重试判断必须有独立依据。常见设计是让客户端为一次逻辑动作生成稳定的操作身份，服务端记录该身份及最终状态；读取接口查询它，或者服务端明确承诺重复提交相同身份不会再次执行副作用。只有在合同存在、作用范围清楚且状态存储可靠时，才能把这一能力称为幂等。把同一个任意请求 ID 放入日志并不自动构成幂等机制。

这个方案也有边界：操作记录可能过期；相同身份如果允许携带不同负载，服务端必须定义冲突行为；跨服务副作用可能不能被单个服务的记录覆盖；查询接口也可能暂时不可用。恢复流程要区分“确认已提交”“确认未提交”和“当前未知”，不要把未知压成失败。若系统无法判断，就应暂停自动重复写入，并采用对账、人工处置或补偿流程；后续补偿也不等于回滚原操作。

因此，清理错误应进入独立的恢复策略：可以重试清理本身，可以报告主任务已成功但资源处于降级，也可以阻止新的相关操作直至租约/锁状态澄清。不能因为 finally 方便就假设清理与主写入共享同一个事务。两者的存储、失败窗口和所有权都可能不同。

如何验证这条边界

可以为四种组合设计测试：主任务 fulfilled 且清理 fulfilled 时，新链应 fulfilled 并保留原值；主任务 fulfilled 而清理 rejected 时，新链应 rejected，业务记录仍需单独检查；主任务 rejected 且清理 fulfilled 时，应保留主错误；两者都拒绝时，应检查调用方是否能获得设计所需的两个错误上下文。再为清理返回普通值、返回 fulfilled Promise、同步 throw、返回 rejected Promise分别补边界用例，并确认未 return 异步清理时系统的实际等待行为符合接口意图。

如果主任务代表远端写入，测试层还需使用可控假服务或契约环境模拟“服务端提交后响应丢失”：同一个操作身份查询应能区分已提交与未提交，重放应符合服务端文档的幂等合同。这样的验证不能靠 Promise 单元测试替代。本文只提出验证矩阵，没有运行测试、远端服务或生产写入，也没有成功日志。

最后，若主任务本来就是并发组合，组合中的一个 rejection 是否取消其余工作是另一项语义；可继续阅读Promise 聚合失败与取消边界。把并发任务是否结束与 finally 清理是否成功分开观察，调用方才不会把一个异步链的最终状态误当成整套操作的完整审计结论。
