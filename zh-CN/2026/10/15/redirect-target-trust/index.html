登录后返回地址，怎样避免变成任意跳转入口？

把登录回跳当成独立的导航信任边界：优先服务端目的地映射；确需 URL 时按解析后的组件许可，并把内部路径授权与失败落点分开。

核心要点

  • 能用服务端目的地 ID 时，不把完整 URL 当成登录参数。
  • 解析只提供 URL 结构；协议、origin、端口和必要路径还要按产品策略许可。
  • 导航许可不能代替登录后的对象级授权；无效目标要落到固定安全页面。

登录入口在本站，并不意味着登录成功后的下一跳也可信。returnTo、next 或 redirect 参数会影响浏览器最终打开的位置，因此必须在写入 Location 之前决定目的地是否属于产品允许范围。优先使用服务端维护的目的地编号；确实要接收 URL 时，使用与浏览器跳转一致的解析规则检查协议、规范化 origin、有效端口及必要的路径，再用同一个已验证结果完成跳转。登录证明身份，目的地策略限制导航，目标页面仍须独立检查用户权限。

先把问题说准：这是导航信任，不是密码验证

OWASP 将“应用接受不可信输入，并据此把请求重定向到输入指定 URL”归为未验证重定向。风险之一是钓鱼：用户点击的链接以熟悉站点开头，登录后却被带到攻击者控制的页面。入口域名带来的信任被借给了下一跳。这里讨论的是浏览器导航；如果服务器会主动请求用户给出的地址，那是另一个服务端网络边界，不能用本文的跳转校验替代相应防护。

登录流程中至少有三个不同判断。第一，凭证或身份提供方是否验证成功；第二，产品是否允许把浏览器导航到请求的目的地；第三，目的地对应的页面或 API 是否允许这个用户访问具体功能和对象。它们可能在同一条请求链中发生，却不能共用一个布尔值。例如，/admin/reports 是站内路径，满足“同 origin”仍不说明普通用户有权限查看管理报表。相反，用户有权使用某个功能，也不意味着可被悄悄带去一个未批准的外部域名。

这个拆分也会影响错误处理：身份验证失败不应该执行成功后的跳转；目的地校验失败可以按产品规则回到默认页；目标页授权失败则应由目标页返回自己的拒绝结果。若把三种拒绝揉成一个“URL 无效”，排查日志就无法说明是凭证、导航规则还是对象权限挡住了流程。

目的地数量有限时，映射比传完整地址简单

设想一个假设的产品有三个合法登录后入口：个人工作台、待办列表、组织选择。页面收到 destination=tasks，服务端用固定映射把它解析为本站路由，然后才创建响应。外部调用者能提交的只是一个短标识，不能自由指定 https://…。OWASP 也优先建议由用户提交短名称、ID 或 token，再由服务端映射到完整目标；它还提醒映射 ID 本身要避免被枚举成可发现的跳转目录。

映射不应只是把危险字符串换一个名字，而要有明确的产品合同。每个 ID 对应哪个目的地、由谁维护、哪些入口可以使用，最好是代码或受控配置中的有限表。对多租户系统，可以把“组织选择”作为目标，但不能把用户提交的 tenant ID 未经核验地拼进路径。映射告诉系统“去哪类页面”，会话与目标接口仍要确认“当前人是否可到达该组织”。标识值是否可猜不是唯一风险；若攻击者能观察到已知 ID，它是否暴露敏感信息、改变权限或跳到外部站点，才决定是否需要每次请求绑定会话、用途或一次性状态。

完整 URL 有时确实必要：产品支持多个经过审核的外部身份提供方回调，或者返回地址来自受控工作流。此时需要维护的不是“看起来像我们”的字符串，而是有限的目的地许可规则。如果规则无法解释成一张小而清晰的表，就应先重新审视产品是否真的需要任意 URL。

解析解决结构问题，策略才决定是否允许

Node.js 当前 URL 文档描述 WHATWG URL 类会把地址拆成 protocol、hostname、port、pathname、search 和 origin 等组件。相对输入需要 base；绝对输入会忽略 base。文档还明确建议：输入可能是绝对地址时，即使提供了 base，也要核对解析出的 origin 是否符合预期。解析器能避免团队对同一串字符作出不同切分，但它不会替应用决定允许哪些协议、主机或路径。

例如，假设站点名是 app.example.test，代码只检查原始文本是否以它开头。https://app.example.test.attacker.invalid/ 仍以这段字符起始，实际主机却不是该站点；带有 userinfo 的 https://app.example.test@attacker.invalid/ 也可能让人把主机和用户名混为一谈。OWASP 因此明确反对原始前缀或后缀匹配，建议用维护中的 URL 解析器，比较协议、规范主机和有效端口，并在需要时限制路径；拒绝 userinfo 和含义不清的输入。以上字符串是解释用的假设示例，没有在本站或其他系统中发送、测试。

如果产品只允许同源相对路径，策略可以要求解析结果与预先固定的本站 origin 一致，并限制到明确的页面范围。注意：把字符串交给 new URL(input, siteBase) 并不会自动把它变成站内地址；绝对 URL 会忽略 base，带主机的相对引用也可能解析到其他 origin。团队应读取解析结果而不是把 URL 对象序列化后再用另一套逻辑拼接或规范化；否则验证时判断的值与最终响应 Location 里的值可能不是同一个。对允许外部目标的场景，应显式列出批准 origin、协议、端口和所需 path，而不是只验证 HTTPS 或主机名中“包含公司域名”。

用一次假设登录流程看规则怎样落地

假设用户访问 /login?returnTo=...，登录成功后后端将参数直接写入 302 响应。若参数值是外部地址，浏览器会离开产品站点。安全调整可以分两种：如果目的地属于三个固定页面之一，就让入参变成 destination=tasks，服务端查表并生成受控的站内响应；如果业务允许一个外部集成回调，就先将候选值按与最终响应兼容的 URL API 解析，检查 https:、精确的规范 origin、有效端口和该集成允许的 path，然后使用解析后的目标生成跳转。找不到映射、解析失败、组件不满足规则时，不再尝试“修一修原字符串”，而是回到固定的本站默认页面。

这两种方案的运维成本不同。映射表容易审阅和回滚，但新增目标需要部署或变更受控配置；外部 URL 白名单能支持更多目的地，却要求有人持续维护域名迁移、子域、端口、路径和退出提示。若允许用户把地址保存在个人配置中，还要区分“保存成功”与“每次登录都准许跳转”；产品可能需要对目标变更重新确认。若映射标识里包含临时授权数据，记录完整参数可能把凭证写入日志，因此日志只需记录规则编号、决定结果和拒绝类别，不要默认保存原始查询串。

外部目标的离站确认页可以显示将离开本站的明确目的地，再由用户点击继续。OWASP 将它列为一种方案，但提示页不是所有场景都适用，也不弥补错误的认证回调配置。对于 OAuth/OIDC 等协议回调，要使用该协议规定的精确 redirect URI 注册和匹配规则；普通登录 returnTo 的站内白名单不能取代身份提供方配置，反过来也一样。

失败时回到哪里，决定体验是否绕开安全边界

校验失败不应退回“原样重定向”，也不应把未经验证的值塞进错误页面中的另一个链接。更可控的处理是使用固定的本站落点，说明返回位置不可用，并提供用户主动进入常用页面的导航。对于登录成功后必须继续交易或表单的流程，丢弃状态可能带来实际损失，因此应在业务层设计可恢复的状态 ID 或草稿恢复机制；不要为了保留全部状态而把任意 URL 和敏感查询数据原封不动保存在客户端。

校验、登录成功和跳转执行最好共用清楚的决策结果：允许目标、拒绝类别、固定 fallback。这样日志可以表达“目标不在许可表”“origin 不匹配”“用户未获准访问目标功能”等不同事实，而无需输出完整 URL。注意，过度模糊日志会让排查失效；但日志也不应记录密码重置 token、一次性 code、邮箱地址等可能随查询串传递的敏感值。实际字段要根据本系统数据分类确定。当前文章没有审计真实日志实现。

怎样验证，而不是只看一条 startsWith 断言

测试应围绕“请求输入、解析结果、策略结论、最终响应 Location”建立矩阵，并明确每一行预期。可包含：映射表内有效目标；映射外 ID；本站同源相对路径；绝对外站 URL；同主机但不同端口；包含 userinfo 的 URL；解析异常或空值；允许的外部集成路径与相邻但未批准的路径；以及校验通过后中间件是否会重新改写目标。每项都检查响应最终去向，不能只断言辅助函数返回 true。

还要加一行目的地在站内但用户无权访问的情形：导航许可可能通过，下一页仍必须给出授权拒绝。另测身份失败时没有成功后的跳转，验证失败时 Location 固定在预期落点，日志里不出现原始敏感参数。这些是拟议验收项，本文没有运行测试，没有声称实现已经阻断攻击。

若出现兼容性问题，先找出哪条业务路径真的需要完整 URL，再把那条路径单独纳入许可策略。不要因为一条旧客户端发送了绝对地址，就全局开放任意 origin；可在明确版本窗口内转换已知格式，同时对未知格式采用安全默认。上线监测应关注拒绝类别和版本分布，不把“拒绝数下降”当作安全性的直接证明，因为它也可能意味着检测逻辑被绕过或使用方式变化。

选择顺序可以落到三个问题：目的地集合是不是有限？如果是，使用映射。谁能维护外部白名单，变更是否能审阅？若无人负责，就不要支持任意站点。即使合法抵达，目标还会不会读取其他用户或租户的数据？会，就在目标接口继续做对象级授权。关于 URL 的 base 与目录边界可参阅URL 的目录边界与 base 参数；关于认证通过后仍需独立权限判断，可参阅订单编号换成 UUID，就能防止越权访问？。

可以把本文的结论压缩成一道审查问题：返回地址是谁提供的、服务端依据什么准许它、校验后的同一个值怎样进入响应，以及到达后由谁检查资源权限？这四个答案都清楚，登录回跳才是可审计的导航功能；少一个，就应把它列为未解决的边界，而非靠“本站发起”或“HTTPS 安全”替代判断。
