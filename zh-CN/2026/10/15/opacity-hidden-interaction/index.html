按钮透明了，键盘还在走：隐藏状态得同时管三条路径

opacity: 0 只改变视觉合成，不会自动停止点击或 Tab 焦点；应按单控件、整块区域和动画过渡选择真正的状态机制，并单独核对辅助技术路径。

核心要点

  • opacity: 0 让元素看不见，但 DOM、指针命中和顺序键盘焦点仍可能存在；opacity 本身不向屏幕阅读器表达隐藏语义。
  • pointer-events: none 只处理指针目标；单个原生表单控件可用 disabled，整块暂不可交互的子树可评估 inert。
  • 隐藏前要安排焦点去向；用真实浏览器和辅助技术分别检查动画中、隐藏后及恢复时的行为。

把提交按钮的 opacity 淡到 0，截图上它已经消失；但如果节点还在 DOM 中，它仍可能挡住下面的点击，也可能在按 Tab 时获得焦点。问题不在于透明动画“没生效”，而是视觉状态变了，交互状态没有一起变。判断一个操作是否真的隐藏，至少要分别检查指针命中、键盘焦点和辅助技术能否访问；若操作涉及权限或提交，还得另外检查业务端是否允许执行。

截图只能回答视觉这一层

opacity 控制元素及其内容整体的透明度。MDN 对 opacity: 0 的说明很直接：元素看不见，但仍在 DOM 中，仍可接收指针事件；如果它原本位于 Tab 顺序中，仍会获得键盘焦点。opacity 参考文档还指出，非 1 的透明度会形成新的 stacking context；MDN 也提醒，opacity 本身不应被用来向屏幕阅读器传达信息，若内容还需从屏幕阅读器隐藏，应单独选择合适机制。CSS Color Module 4 对 opacity 的描述把它视为元素渲染后的合成操作，并明确说 opacity 值不影响 hit testing。改变透明度既不负责移除布局，也不负责改写指针命中。因此“肉眼看不到”“不占位置”“不能触发”和“屏幕阅读器不可访问”是不同主张，不能由一张截图互相代证。

设想一个抽屉面板在关闭时淡出。动画结束后，面板透明了，但没有设置 display: none、hidden 或其他交互状态。如果它仍覆盖页面的一块区域，鼠标点到那里的目标可能还是面板里的按钮；键盘则会按 DOM 的焦点顺序继续访问面板内控件。截屏、鼠标和键盘看到的实际状态因此可能不同。这里是按浏览器规则构造的假设场景，没有运行某个真实页面，也不意味着每个透明元素都会造成重复提交。

一个透明控件有三条入口

先把容易混在一起的路径拆开。指针路径看“当前位置的事件会命中谁”；键盘路径看 Tab、Shift+Tab、方向键或脚本焦点会到哪里；辅助技术路径看节点是否仍在可访问性树中、名称和状态是否可被理解。另有业务路径：即使客户端按钮不可操作，服务器仍应按自身规则验证授权和请求，不可把 CSS 或 HTML 属性当作权限控制。

机制 指针命中 顺序键盘焦点 辅助技术与业务含义
opacity: 0 元素仍可能接收 仍可能获得焦点 不负责向屏幕阅读器表达隐藏语义，也不验证业务权限
pointer-events: none 通常不成为指针事件目标 仍可能被 Tab 聚焦 只改变指针命中；可放行的子元素和事件冒泡仍需留意
原生控件 disabled 控件不可交互 控件不能获得焦点 适合按钮、输入框等支持该属性的控件；禁用的表单值也不会随表单提交
容器 inert 子树不能被点击 子树退出焦点顺序 子树也从可访问性树中移除；属性本身不会提供视觉提示
hidden 或 display: none 不作为可呈现控件交互 通常不进入焦点顺序 内容不呈现给辅助技术；但隐藏的后代脚本仍可执行、表单仍可能被提交
aria-hidden="true" 本身不改变指针行为 本身不阻止键盘焦点 只从辅助技术树中移除；不能加在可聚焦元素或其祖先上

这不是一张可随便拼属性的“隐藏配方”。pointer-events 文档明确写到，pointer-events: none 不会自动让元素退出 Tab 焦点顺序。如果随后再给一个仍可聚焦的子树标记 aria-hidden="true"，键盘用户可能仍能走到一个屏幕阅读器不会报告的控件。aria-hidden 文档明确警告不要对可聚焦元素或其祖先这样做。修复一条入口，不能推断另外两条已同步。

按对象范围选择真正的状态

如果只是一个“保存”按钮在请求期间暂不可用，且它是原生 button，通常应优先考虑 disabled 并配上可见的等待或禁用反馈。它会阻止用户对该控件进行通常的交互，也让浏览器按控件语义暴露不可用状态。不过 disabled 控件不会参与表单提交；若请求依赖该按钮的 name/value，不能只加属性就假定提交数据保持不变。MDN disabled 说明列出了支持它的表单控件及其不接收焦点、不提交值等边界。原生属性也不能替服务器挡住伪造请求。

如果一整块背景区域在模态对话框打开期间都不能交互，可以评估把对应子树设为 inert，并让对话框接管焦点。MDN inert 文档说明，inert 会令元素及其 flat-tree 后代不能点击、不能聚焦，并从 Tab 顺序和可访问性树中移除；它本身没有可靠的视觉提示。WAI-ARIA 模态对话框模式要求打开时将焦点移入对话框、把 Tab 顺序限制在对话框中，关闭时通常回到触发它的控件。只添 aria-modal="true" 不会实现这些行为；MDN 也将 aria-modal 解释为向辅助技术表达模态状态的语义，而非自动拦截背景交互的脚本。

若内容只是当前不相关，hidden 或布局属性可能更贴合目标。MDN 提醒，hidden 内容原则上不呈现给任何用户，包括屏幕阅读器，但若 CSS 又声明 display: block，呈现可能被覆盖；对需要支持“页内查找后展开”的折叠内容，hidden="until-found" 还有不同语义。隐藏也不等于脚本或表单逻辑被冻结：MDN 说明隐藏后代中的脚本仍可执行，表单控件仍可能参与提交，所以程序逻辑仍要按业务状态单独约束。反过来，aria-hidden 常适合隐藏重复或纯装饰内容，而不是拿来关闭一个还在视觉上或键盘路径中的按钮。选机制前先写清“只不响应指针”“不再允许操作”“暂时不呈现”还是“模态之外都不可用”，再核对其真实效果。

抽屉关闭是状态迁移，不是一条样式

把一个侧边抽屉的关闭过程拆成状态，有助于避免只照顾动画最后一帧。下面的流程是实现思路，不是经过浏览器测试的组件代码：

  1. 用户触发关闭时，先决定抽屉里的操作从这一刻起是否可用。如果应立即不可用，就同步切换对应交互状态；只等 transitionend 才改变状态，会留下动画期间仍能操作的时间窗。
  2. 如果当前焦点在抽屉内部，先把焦点送回打开抽屉的触发按钮，或送到关闭后最符合流程的位置。否则抽屉已视觉退场，用户的下一次键盘输入却没有一个明确、可见的落点。若触发按钮已不存在，应按实际任务选一个后续位置，而不是盲目恢复一个失效引用。
  3. 让视觉反馈表达它正在关闭或已经关闭。若交互已锁定而面板还在淡出，需确保视觉提示足以让用户理解；HTML 标准对 inert 子树也提醒，不要让无法感知的活动内容留在可见区域。
  4. 动画完成后再做布局清理，例如将元素设为 hidden。重开时要按相反的生命周期恢复：先让内容重新呈现，再按当前状态解除禁用或 inert，最后将焦点置于预期的控件。是否恢复到关闭前焦点，取决于关闭原因和重新打开后的任务，不应只按历史 DOM 节点机械回填。

反例很有辨识度：关闭动画开始时就给整个根节点设置 aria-hidden="true"，但未迁走焦点、也未禁止交互。截图仍能看到面板渐隐；键盘却可能继续在面板里移动，屏幕阅读器又不再报告它。此时三条路径给出了互相矛盾的状态。另一个反例是给容器加 pointer-events: none，却在里面保留一个显式恢复指针事件的子元素；MDN 指出，子元素接到的事件仍可能经过父级监听器。此类问题要根据 DOM 和实际事件路径检查，不凭 CSS 属性名猜结果。

怎么验证动画中和动画后都一致

以下是建议的测试矩阵，不是本次已经执行的测试。对一个从可见变为不可用的控件，至少记录起始焦点、触发关闭的动作、动画期间的状态、最终状态和重新打开后的焦点：

检查 要观察的证据 常见漏项
鼠标或触摸 点击面板占据的位置时，命中的实际目标及动作结果 只在完全透明后检查，漏掉过渡期间
键盘 连按 Tab/Shift+Tab 的焦点顺序与可见焦点指示 仅看 pointer-events，忘了它不改变 Tab 顺序
辅助技术 名称、角色、状态及隐藏后是否仍可遍历 只检查 DOM 属性，没有听实际读屏输出
焦点移出 关闭开始前焦点在哪，结束后是否落在逻辑上的下一步 面板消失了，但焦点仍指向其中节点或落到页面起点
恢复 重新打开后是否恢复正确的操作能力和焦点 视觉显示恢复了，但 disabled/inert 仍留着，或焦点落错位置
模态背景 对话框打开时背景控件能否点击或获得焦点，关闭后焦点是否回归 只设置 aria-modal，没有实际限制背景交互

调试时可以配合浏览器开发者工具观察 document.activeElement、DOM 属性和 computed style，但这些检查各自只证明一部分。屏幕阅读器树和真实键盘操作仍需在目标浏览器、输入方式及辅助技术组合中检查；自动化断言也要说明是在测 DOM、焦点还是用户看到的状态。本篇没有对具体浏览器、屏幕阅读器或应用组件执行测试，不能据此宣称满足某项完整无障碍验收。

一个实用的选型顺序是：单个受支持表单控件暂时不能操作，用原生 disabled 并给出状态提示；一整个区域不可用，用有清楚视觉反馈的 inert；内容确实不应呈现时用 hidden 或相应布局方式；只需从辅助技术树中省去冗余装饰时再考虑 aria-hidden，且不要包住焦点控件。若需要模态交互，验证完整的焦点进入、限制、退出和恢复流程。对于转场，明确哪个状态在开始时变化、哪个在结束时清理。要减少动画时，可参考减少动态效果与状态反馈；动画偏好改变呈现方式，不替代交互状态。透明只是像素变淡，用户能否继续操作仍要由对应的机制负责。
