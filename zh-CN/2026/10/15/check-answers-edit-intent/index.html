核对页的“返回修改”不是导航问题，而是事务状态问题

核对页的修改操作要保留同一任务、重算失效的后续答案，并把最终提交与浏览器返回、刷新和网络重试隔离。

正文

核心要点

  • 返回修改应恢复原任务和未受影响的答案，不能把浏览器历史当作业务状态。
  • 修改会改变后续问题时，要显式重算依赖并标记失效答案，而不是一律保留或清空。
  • 核对、保存修改、最终提交是不同状态；服务端版本检查和幂等处理保护并发与重试。

核对页里点“修改”看起来只是换一页，实际需要系统回答三件事：编辑的是哪份任务、哪些答案仍然有效、什么时候才真正提交。本文说的“事务状态”指申请从填写到确认送出的业务生命周期，不特指数据库 ACID 事务。实现时应保留原任务和未受影响的答案，对依赖已修改字段的后续问题做显式重算，并将最终提交设为独立的、由服务器确认的状态转移。浏览器后退、刷新或超时重试都不能替代这条业务规则。

核对页不是一张只读摘要

GOV.UK Design System 的 Check answers 模式建议在最终确认前提供核对页，在每条信息旁提供用途明确的“修改”链接，进入原问题时预填已有答案，改完后返回核对页。如果改动意味着需要补问新问题，应先完成补问再回到核对页；跳过的可选问题则显示“未提供”，不要让空白看起来像数据丢失。对于很长的事务，也可以考虑分段核对，并验证这种安排是否适合实际使用者。

这不是“返回到一个 URL”就结束的交互问题。设想一个申请人先选择“个人”，填写姓名、联系方式和地址，再到核对页把类型改成“组织”。系统随后才知道需要组织名称和登记编号。合理的结果不是让用户从头重填，也不是把原先个人申请的答案与组织字段拼在一起直接发送；应保留仍适用的联系信息，把受类型影响的字段标为需要重新确认，补问组织字段，再展示一份反映当前版本的核对页。此例是设计假设，没有在本站或真实服务中执行，不代表已测得的错误率变化。

工程上至少要分清三样东西：任务身份、答案数据、流程状态。任务身份说明当前修改的是哪份申请；答案数据保存每个字段的值、来源和版本；流程状态说明它仍在填写、待核对、等待补充，还是已经提交。若这些概念只存在于浏览器页面栈里，清缓存、换设备或打开第二个标签页就会让“返回”含义改变。页面路径可以重建，服务端的任务记录才是是否仍可编辑、是否已经提交的依据。

一种可讨论的状态设计是 draft、review_ready、needs_more_answers 和 submitted。这些名字不是标准，也不是已部署系统的现状；它们用来提醒团队分别定义状态入口、允许的动作和退出条件。例如，review_ready 表示必需字段已通过当前规则检查并可供核对，并不表示用户已经授权提交。核对页请求应只读取该版本；修改请求携带任务 ID 和所见版本号；最终提交是另一种显式操作。这样，用户浏览、保存、确认不再被混成一次“下一步”。

哪些答案应保留，哪些需要重新确认？

不要把“保留已有数据”理解成所有旧值都继续有效。把问题视作有向依赖关系会更清楚：申请类型决定展示哪些问题，所在国家影响地址格式，选择某种交付方式才会出现时间段。类型改变后，系统需要重算哪些节点变成适用、哪些答案已不再回答当前任务。尚未受影响的姓名、电话号码可以保留；个人税号可能与组织申请无关，应删除、隔离或要求重新确认，具体取决于领域规则。不能让隐藏字段因为还留在 JSON 里，就被当成用户对当前申请作出的确认。

依赖处理最好有明确策略，而不是在页面组件里零散地清空字段。每个答案可关联它适用的条件、最后修改版本和验证状态。一个假设的规则是：当 applicant_type 从 individual 变为 organization，保留 contact_email，将个人身份材料标为“不再适用”，添加组织登记问题，并使核对版本失效。用户完成新增问题后再生成新核对页。若业务无法判断某字段是否仍有效，宁可说明“请检查此项”并让用户确认，也不要静默地把旧状态包装成新选择。

这需要谨慎处理删除与保留的副作用。若修改上游选择导致下游答案失效，系统应说明哪些信息需要重填；如果保留信息是为了减少操作，也要在页面和服务端都把它标记为“待确认”，不能仍然呈现为已经核对。相反，若每改一项就清空整份申请，既增加负担，也可能丢失用户有意保留的内容。产品判断应逐字段回答：它是否依赖变化的答案、能否安全复用、复用前是否需要确认、用户怎样看到这一变化。

核对、保存和提交是三个动作

核对页应展示“此刻正在提交的版本”，但显示本身不应改变业务状态。保存编辑也不等于提交：它只更新草稿并返回核对状态。最终提交则要在服务端重新确认任务仍可提交、当前版本仍有效、依赖问题已完成且调用者有权操作。GOV.UK 示例把确认文本与明确的“Accept and send”按钮分开；对工程实现来说，这种可见承诺应映射到明确的服务器端动作，而不能由一次页面渲染触发。

最常见的反例是用户双击提交，或者第一次请求已抵达服务器、响应却在网络中丢失，浏览器随后自动重试。前端禁用按钮能减少部分重复点击，却无法证明服务器只执行了一次。若这次提交会创建记录、扣款、发通知或触发外部任务，服务端需要识别重复请求。常见设计是由客户端为一次明确提交生成幂等键，服务端把键与任务、请求内容和处理结果关联；同一键重试时返回既有结果，不再重复执行副作用。键的作用域、保存时间和冲突处理应根据业务约束定义，不能仅凭“加一个 UUID”就声称所有系统都安全。

并发编辑是另一个常被忽略的失败路径。用户在两个标签页打开任务版本 12，标签 A 修改地址并保存为版本 13；标签 B 仍基于版本 12 修改电话。如果服务器无条件接受 B 的整份旧表单，它可能把刚更新的地址覆盖回去。可以让写操作提交 expected_version=12，服务端只在当前版本仍是 12 时接受；发现已经是 13 就返回冲突，让用户刷新并决定如何合并。也可以按字段保存并做更细的并发控制，但那增加了比较和合并的复杂度。选择哪种方式取决于字段是否互相依赖，以及丢失更新的代价。本文没有运行该事务示例，也不宣称它是某种数据库或框架的唯一做法。

对支付、提交申请等有后果的动作，还要防止“显示成功但实际未提交”和“实际提交但页面未显示成功”两种错位。提交端应以任务状态为准：第一次成功后将状态变为 submitted 并记录结果；之后同一任务的重复提交根据业务规则返回既有确认或明确拒绝，不能再创建第二份。若写数据库后还要发消息，需考虑这两个动作之间的失败窗口：记录已提交但消息没发出，或消息已发但数据库回滚。事务发件箱、可重试消费者等方案是可能的工程选择，不是每种简单表单都必须引入的组件；只有存在跨资源副作用及可恢复性要求时才值得承担这份复杂度。

校验不能只在浏览器里发生

浏览器可以给用户及时的格式提示，但提交到服务器的数据仍需要重新验证。W3C WAI 的表单验证教程明确指出，客户端验证本身不能确保安全，还要做服务端验证；自定义控件还要用可访问的方式通知错误。对于核对页，这意味着“已显示正确答案”不能成为信任标记：服务器需要按任务当前状态验证必填项、分支条件、权限和答案版本。比如用户从个人切换到组织后，组织字段必须是当前申请所需且已确认的值；不能只检查请求里有没有一个 organization_name 字段。

任务 ID 也不是授权凭证。若请求把 /applications/123 换成 /applications/124 就能读写另一份申请，即使界面没有暴露该地址，系统仍有越权风险。OWASP API1:2023明确把篡改对象 ID 后访问或修改他人对象列为对象级授权问题，并建议每个接收对象 ID 的操作都核验当前用户对此对象的权限。读取核对页、保存改动和提交都需要按当前用户及业务角色检查对象级权限；服务端不能把隐藏表单字段、浏览器会话中的旧状态或客户端传来的 answers_checked=true 当作授权结论。请求里的状态信息只能提示意图，最终状态由服务端读取并验证。

交互文本也属于正确性的一部分。反复出现的“修改”链接要让人知道改哪一项；GOV.UK 示例使用隐藏补充文本区分各链接，W3C 对标签与说明的指南则区分给所有用户可见的信息和程序化关联。辅助技术可读的名称并不能自动替代所有用户都能看到的操作说明。对复杂项目，可把“修改组织名称”作为可见文本；如果视觉上必须保持简短，也要为链接提供准确的程序名称，并验证键盘、屏幕阅读器和放大视图下的路径。可选但未填写的答案应有明确标记，避免空值被误解为尚未保存或已确认留空。

用失败路径验收，而不是只走一遍顺流程

一个可执行的验收表至少应覆盖下面的状态变化。它是本文提出的测试计划，不是已经在某个应用上运行的结果：

场景 应检查的结果
核对页修改一个无依赖字段 任务 ID 不变；其他答案保留；保存后回到当前核对版本
修改控制分支的问题 依赖重新计算；不再适用的值不被悄悄提交；新问题完成后再核对
两标签页使用同一旧版本保存 后到写入发现版本冲突或按明确规则合并，不静默覆盖
提交请求超时后重试 用户看到可恢复的状态；同一提交不会再次创建副作用
会话过期、换账号或任务 ID 被替换 重新认证或拒绝；不能读取或提交无权访问的任务
未回答可选题、格式错误和服务器校验失败 页面说明具体字段和下一步；已有安全保存的数据不无故丢失

测试应覆盖服务端状态和实际页面提示，而不只断言“页面已返回 200”。比较修改前后的任务版本、答案适用状态和提交记录；在故障注入中分别模拟请求未到达、已处理但响应丢失、重复消息以及旧版本写入。对答案依赖多的流程，可从规则表生成分支用例；测试数据要区分“不适用”“未填写”“待补充”和“明确留空”，否则一组空字符串会把不同状态混在一起。

在页面层面，测试 Change 链接是否对应正确问题、返回时是否保留预填内容、出现新问题时是否先完成补问、成功提交后是否展示确认而不是回到可编辑草稿。需要屏幕阅读器或键盘验收时，记录真实的浏览器、辅助技术和测试步骤。本文没有执行这些验证，所以不能说这套方案已达到某个无障碍等级，也没有错误率、完成率或重复提交率的实测变化。W3C 指南提供的是检查依据，不是本页面的合规证明。

哪些场景不该把所有答案堆在一个末尾页面？

对于字段较少、由一人完成的事务，末尾统一核对往往容易理解。很大的多章节申请可能需要章节末尾先核对，避免用户到最后才发现早期信息有误；多人分别补充的任务，则要明确谁能查看、修改以及确认他人提供的信息。GOV.UK 对不同章节分工的情形建议测试这种分段核对是否有帮助，并没有宣称一种布局适用于所有服务。若信息高度敏感、编辑会立即产生不可逆后果，可能需要在具体操作旁设置确认或撤销，而不是只依赖最终总览。

因此，选择布局前先画出状态和权限：哪些角色能编辑哪些字段，哪些回答依赖上游选择，哪些变更需要其他人确认，何时产生外部副作用。若答案之间没有依赖、事务短且提交可撤销，简单的摘要页可能足够；如果字段关系复杂或多人参与，先分区并定义状态变化，再考虑界面组件。无论界面如何组织，都应能追溯每条当前答案属于哪份任务、哪个版本、是否适用以及由谁确认。

核对页上的修改如何与整段旅程衔接？

修改路径解决的是“这一段交互如何继续”；它不能代替跨团队交接中的责任、状态与确认。需要多人接手时，还应定义谁拥有下一步、未完成资料怎样暴露、超时后由谁处理。相关的页面成功之后的交接责任讨论的是更大范围的交接边界，本篇聚焦单份申请在核对与提交之间的状态。

最后可以用一个具体问题检查设计：用户第二次看到核对页时，系统能否证明这是同一任务的当前版本，而且尚未提交？如果不能，就先补齐服务端任务身份、版本和状态模型；不要用浏览器返回按钮去弥补业务状态缺失。
