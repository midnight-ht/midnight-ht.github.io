为什么解压后的正文长度可能和 Content-Length 不同？

响应头长度以所选表示的八位字节为准；内容编码、HTTP/1.1 分帧与 JavaScript 字符串长度处在不同层，不能直接比较。

正文

核心要点

  • 先标明长度的表示层、处理阶段和单位，再决定是否可比较。
  • HTTP/1.1 Transfer-Encoding 负责消息分帧，与 Content-Encoding 的表示编码不同。
  • 传输完整、文本解码、业务解析和本地保存要分别判断。

解压后的正文长度可能与 Content-Length 不同，这通常不是传输错误：头部中的长度以八位字节描述 HTTP 所选表示，存在 Content-Encoding 时相关元数据指向编码后的形式；应用解码后又会得到另一组字节或字符串单位。HTTP/1.1 的 Transfer-Encoding 还负责消息分帧，不能与内容编码混为一谈。排查时先写清每个数字测量的对象、阶段和单位，再判断它们能否比较。

先给长度标上层次

“正文大小”常被用于几个不同对象。第一种是资源在内容编码前的表示数据，例如原始 JSON UTF-8 字节；第二种是应用 gzip 或 br 后的表示字节；第三种是 HTTP/1.1 为传输消息加上分块标记后的消息体；第四种是客户端解码得到的字节；第五种才是业务解析出的字符串、记录或对象数量。它们之间可能有转换，但不是同一测量。

RFC 9110 的 Content-Length 定义说，该字段是关联表示数据长度的非负十进制八位字节数；当表示作为内容传输时，它还可用于定界。若没有传输内容，字段也可能表达所选表示的当前长度。因此把它简单写成“网络线上总共经过了多少字节”并不准确：TLS 记录、TCP/IP 头部、链路层开销不是该字段所统计的对象。

Content-Encoding 是表示元数据。资源经过内容编码后，MDN 的 Content-Encoding 参考说明，除非另有声明，其他元数据（例如 Content-Length）针对编码后的形式。接收端按编码标记还原内容格式。相反，在 HTTP/1.1 中，Transfer-Encoding 是消息在这一跳如何传送和分帧；RFC 9112 的分帧规则明确把它与表示编码区分。二者名字都带 Encoding，却处在不同层。

沿一次压缩下载追踪五个数

设有一份可下载的文本报告。为讨论方便，把内容编码前的字节数记为 A，服务端选用 gzip 后的表示字节数记为 B，HTTP/1.1 chunked 消息体上的块尺寸与分隔记为 C，客户端去掉内容编码后得到的字节数记为 D，解码成 JavaScript 字符串后的 length 记为 E。这里是变量示意，不是某次实测的文件或压缩比例。

如果响应带 Content-Encoding: gzip 且使用 Content-Length 定长分帧，该字段通常对应 B，而非 A、D 或 E。若服务端改用 HTTP/1.1 的 chunked transfer coding，分块大小行和 CRLF 属于消息分帧；RFC 9112 规定终止块用于标记完成，同时发送方不得再发送 Content-Length。这是另一条分帧分支，不是上一句头部组合的补充字段。客户端看到的传输字节流可能含有 framing 结构，而应用库交给 response.text() 的却是已经处理后的内容。不要把抓包工具在某一观察点显示的字节数，直接拿来与响应头字段比较，除非先确认工具是否已去掉 chunk framing 或做了解码。

再看 E。JavaScript 的 String.length统计 UTF-16 code units，不统计 UTF‑8 字节，也不总是等于用户感知的字符数。举例说，一个单独的 😄 在 JavaScript 中 length 为 2，但它是一个 Unicode code point；把它交给 TextEncoder 编码后，得到的是 UTF‑8 字节数组。于是即使 D 与 E 都来自同一份解码内容，二者也不能直接做数值相等断言。

一个常见的误报路径是：下载器把 Content-Length 保存为“应收字节”，页面拿 response.text().length 当作“已收字节”，随后两个数字不等，监控便标为文件损坏。该断言混合了 B 与 E。比较响应内容完整性时，应在相同表示和相同字节边界上比较；如果业务目标是文本字符数，就先定义要数 Unicode code points、grapheme clusters、UTF-16 code units 还是编码字节。目标不同，检查就不同。

没有 Content-Length 与传输中断不是一回事

动态生成或流式输出时，发送头部时可能还不知道最终长度。对于这类 HTTP/1.1 消息，chunked framing 可以逐块传输；读取端以终止块判断分帧是否完成。没有 Content-Length 本身不等于响应没有正文，也不一定意味着消息无法知道何时结束。同一规范还规定，若有效 Content-Length 声明了预期长度，而实际收到的八位字节更少，响应应视为不完整；chunked 消息若没有收到零长度终止块，也是不完整消息。

与 HTTP/1.1 不同，HTTP/2 不使用 chunked 分块语法；MDN 对 Content-Length 的版本说明指出，HTTP/2 可由 DATA frames 推断内容长度，因此该字段可能是冗余的，但仍可能为兼容性出现。工具、代理与应用日志若处在不同协议层，报告的“收到字节”也不一定有相同口径。遇到长度不匹配，要记录协议版本、内容编码、传输编码、状态码、请求方法和读取 API，再定位具体哪一层观察到了提前结束。

HEAD 是容易误读的反例。MDN 的 HEAD 说明指出，成功响应没有正文；但 RFC 9110 允许响应携带 Content-Length，且其值只能等于相同请求若使用 GET 时本应发送的内容八位字节数。因此，HEAD 返回一个长度并不表示 HEAD 消息自己带着这些正文，也不保证随后的 GET 一定使用完全相同的协商表示或缓存状态。它是元数据提示，不是已经下载并校验的文件。

进度、完整性和资源预算分别看什么

如果用户界面要表达网络传输进度，分子和分母必须同属明确的传输口径；有可信的预期长度时，才能呈现有分母的百分比。没有总量时应显示不确定进度，而不是把已解压大小临时当总量。即便收到完整传输，也只说明传输阶段到达边界，不说明解压、字符解码、JSON 解析或本地保存成功。把这些阶段拆成状态，遇到错误时才知道应重试下载还是修正业务数据。

如果目的是限制意外膨胀的压缩输入或解析内存，压缩后的 B 不是足够的预算指标；至少还要限制解码后的 D、解析后对象数量或应用特有的嵌套层级。这里是工程设计建议，不是某一通用安全上限。内容编码可以让小型传输表示展开为更大的资源，但具体增长取决于输入和算法，本文没有测量比例。实现应在实际解码和解析边界累积计数，并在超过业务配置的限制时中断处理；对流式 API，还要确认背压、取消和异常路径会释放临时缓冲区。

如果目的是文件身份或完整性，单独的 Content-Length 只回答长度，不回答字节是否来自预期文件。两个不同文件可以长度相同；错误的头部也可能与实际内容冲突。应由应用协议选择适合的摘要、签名、版本标识或业务校验，并说明它覆盖的是编码前资源、编码表示还是下载后的文件。校验和也必须在约定的边界计算；发送端对原始资源计算摘要、客户端却对 gzip 字节求摘要，二者当然不能直接比较。

怎样验证而不把计划写成结果

为目标客户端建立一组小型、可重复的夹具：同一文本资源分别返回 identity 与 gzip 表示；文本同时含普通 ASCII、多字节汉字和补充平面 emoji；再分别测试已知长度、HTTP/1.1 chunked、HEAD、提前关闭连接、缺少终止块以及解码失败。每次把响应头、协议版本、库暴露的原始/解码数据、TextEncoder 字节数、字符串 length、解析结果和保存状态分栏记录。重点不是让所有列的数字相等，而是确认每一列都符合它的定义。

完整性测试需要检查失败路径：若声明长度为 L 而只收到更少八位字节，客户端是否把消息标为 incomplete 并丢弃或隔离部分文件；如果采用 chunked，缺终止块是否拒收；如果响应正常完整但 JSON 语法错误，错误是否落在解析阶段；若 HEAD 的长度与随后 GET 不同，是否检查了内容协商、缓存和资源版本，而非先认定某一请求违反协议。具体浏览器、代理和 HTTP 客户端库可能暴露不同层次的观测接口，因此验收时要绑定版本和真实调用方式。以上是待执行的验证方案，本次没有运行下载或跨客户端测试。

落地时先把指标名称改成带单位与阶段的名字，例如“编码表示八位字节”“解码后 UTF‑8 字节”“JS UTF-16 code units”，再决定哪个指标支撑进度、资源保护或业务完整性。只要日志仍把它们都叫作 body size，团队就会继续把不同数据误当成同一个总量。有关无正文元数据请求的更多边界，可参阅站内的 HEAD 与 GET 正文验证。
