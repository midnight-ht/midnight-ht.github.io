文件写进 gitignore，为什么改动仍然会被 Git 看到？

gitignore 不改变已跟踪文件；停止跟踪、清理历史与撤销秘密分开，干净检出还需初始化证据。

正文

gitignore 主要描述不应跟踪的路径，不会让已经被 Git 跟踪的文件自动消失。把文件名加入规则以后，原来已提交的内容与后续修改仍需要按跟踪状态处理。停止跟踪、删除工作文件、清理历史和处置秘密泄露，是不同动作，不能由一条忽略规则同时完成。

规则不改变既有跟踪事实

Git 的 gitignore 文档明确说明，已经跟踪的文件不受忽略规则影响。文档也区分仓库共享规则、本地排除与用户级规则。选择哪种规则要看它应当影响谁，不能只因为本机不再显示某个新文件，就宣布团队仓库已经采用相同约定。

假设开发者把本地配置加入忽略规则，却发现已提交的配置修改仍出现在状态中。首先应检查它是否已经跟踪，而不是反复修改通配符。规则生效与既有文件退出跟踪是两项问题。这个例子没有执行任何删除或索引操作，本文不会改变用户工作区或共享历史。

决定不再跟踪以后，还要考虑其他成员下一次更新会发生什么，以及项目如何获得必要配置。可以保留不含秘密的示例和清楚的初始化说明，但示例应真实反映所需字段。不能为了让源码整洁，就让新环境缺少启动条件而没有可解释的错误。

忽略不是秘密防护

一个未被自动加入的文件，仍可能被其他动作、构建上下文或复制流程使用。Git 的路径规则不覆盖全部发布渠道，不能把它当成秘密永远不会外泄的保证。已有历史中的凭证也不会因为最新版本不再跟踪就失效，需要独立撤销和调查。

对确实需要历史处理的事件，应先确认影响范围、协作条件与恢复方案，不在日常维护中随意重写共享分支。文件从当前版本消失，与过去版本还能否读取，必须分别核对。本文没有执行历史清理，也不提供保证清除所有副本的命令。

用干净检出验证团队约定

拟议检查可以在受控环境中核对新生成文件是否被忽略、必要示例是否存在、初始化能否给出明确结果。对既有跟踪文件，先检查索引与历史状态，再决定需要什么操作。不要只看当前机器因为已有本地文件而能启动，就宣布新的检出也一定可用。

还应分别确认工作目录中是否存在文件，以及索引是否继续跟踪它。两份状态可以不同，界面只显示本地文件仍在，并不能回答它是否会进入下一次提交或历史中是否已有副本。

这些验证未执行，不报告项目清理已经完成。有关构建上下文为何可能包含 Git 之外的资料，可阅读构建输入的允许范围。忽略规则解决版本管理的一部分选择，发布内容和敏感资料仍需要各自的边界与证据。
