写入 .gitignore 后仍被跟踪：先分清规则、索引和工作文件

.gitignore 只影响尚未跟踪的路径。用索引和工作目录分别确认状态，再决定如何停止跟踪、保留本地配置或处理已泄露秘密。

正文

核心要点

  • 忽略规则描述哪些未跟踪路径不应进入索引；文件一旦被跟踪，新增 .gitignore 规则不会改变索引里的既有事实。
  • 先用 git ls-files、git status 和 git check-ignore --no-index -v 分别查跟踪、改动与匹配规则，再决定是否把文件从索引移除。
  • git rm --cached 只移除索引项并保留当前工作文件；提交后的协作者检出、密钥轮换和历史清理仍是不同事项。

把路径写入忽略规则后，git status 仍显示改动，不要先加第二条通配符。先问：这个路径是不是已经在索引里？忽略文件主要排除未跟踪路径，不会自动把旧索引项拿掉。文件要从本机继续保留、从后续提交移除，还是连历史中的凭证都要处置，是三种不同决定。

先把三个状态拆开

理解这个问题的关键，是不要把磁盘上存在一个文件、索引中准备提交一个文件、某个提交曾经包含一个文件，统称为“Git 正在跟踪”。工作目录是本地文件状态；索引是下一次提交将采用的快照；提交历史则记录过去的快照。忽略文件参与发现未跟踪路径时的排除判断，已在索引里的条目不会因此自动退出索引。Git 的 FAQ 对“规则写了仍被跟踪”的回答也明确建议：要停止跟踪，应从索引移除该路径，并保留匹配它的忽略规则。

因此，git status 看到某文件被修改，首先只说明工作目录与当前提交所代表的内容存在差异；它没有告诉你为何忽略规则没生效。检查一个具体路径时，可以用 git ls-files --error-unmatch -- path/to/config 询问它是否在索引中。该命令成功通常表示索引里已有这个路径；失败表示索引找不到完全匹配的路径，但还需要留意大小写、子模块、路径拼写和仓库根目录。这个检查不读懂团队对该文件的用途，也不证明历史中没有旧版本。

再用 git status --short -- path/to/config 查看当前差异。若文件在索引中并且内容修改，改动可能进入下一次提交；若未跟踪但没有被排除，则状态通常会以未跟踪路径呈现。状态输出不是安全扫描器，也不会告诉你该文件是否带有口令。一个含有真实值的本地配置，即使没有出现在状态输出里，也可能是因为它被忽略、被全局排除，或路径不在当前工作树范围内，不能据此推断它从未进入仓库历史。

规则从哪里来，为什么只改通配符会绕圈

忽略规则可能来自命令选项、路径附近的 .gitignore、仓库的 .git/info/exclude，以及用户配置的全局排除文件。Git 文档指出，项目成员都应遵守的共享规则通常放在受版本控制的忽略文件；只服务一个仓库本地工作流的规则可放在 .git/info/exclude；编辑器备份等个人偏好可使用全局排除。选择范围会影响“为什么我这里看不到、同事那里仍看到”的诊断结果。

当文件尚未跟踪而规则匹配结果不确定时，git check-ignore -v -- path/to/file 可显示匹配来源、行号和模式。但默认情况下，已跟踪文件不作为普通忽略候选展示。为诊断“这条模式实际上是否匹配这个已跟踪路径”，可以显式用 git check-ignore -v --no-index -- path/to/file；--no-index 只改变这次诊断是否参考索引，并不会把条目从索引删除，也不会更改仓库内容。命令输出里的来源很有用：如果规则来自用户全局配置，本机的结果不等于团队已经共享了它。

模式的作用范围也可能不同于直觉。没有斜杠的名字可匹配该规则层级以下多个目录；带斜杠的模式按规则文件所在目录定位；目录被整体排除后，再对子目录写反向 ! 规则并不总能重新纳入文件，因为 Git 不遍历已排除目录中的文件名。把“tracked 仍显示”归咎于这些模式边界，会把诊断带偏：先查索引状态，再分析模式，顺序更省事。

去掉索引条目，不等于删掉本机文件

假设团队曾跟踪 config/local.json，后来才决定把它作为每位开发者自己的配置。若当前工作副本中的文件内容是要保留的，Git 提供的 git rm --cached -- config/local.json 会把路径从索引移除，而保留工作目录中的文件。随后再添加覆盖该路径的共享忽略规则，并查看 git status，确认索引变更表现为从仓库移除，而本机文件仍在磁盘。--cached 的边界就是索引；它不是删除工作文件的快捷写法。

把这个迁移拆成检查和变更，比盲目执行命令安全。以下仅是说明流程的假设例子，未在本文对应的业务仓库执行：先用 git ls-files --error-unmatch -- config/local.json 判断索引是否有该路径，再用 git check-ignore -v --no-index -- config/local.json 查看哪条规则会匹配；确认希望停止共享以后，才考虑 git rm --cached -- config/local.json，并把实际路径写入项目的忽略文件。随后分别检查状态和工作文件是否还在。命令输出各自回答不同问题，不能把某个成功退出码当成迁移全部完成。

执行之前仍要确认路径和当前内容。命令没有“猜测这是不是秘密”的能力。若仓库里本来就应该有一份共享默认配置，更好的结构可能是继续跟踪 config/example.json，把私人配置路径排除，并让启动步骤从示例复制一个本地文件。示例必须去掉秘密值，字段与必填条件也应与当前程序一致。否则维护者只看到文件被移除，却不知道新克隆后应如何启动。

提交索引移除以后，其他协作者的下次更新会拿到仓库删除该路径的变更；他们本机若有未提交改动，Git 的安全检查可能要求先处理冲突。因此，要在团队公告、模板、部署配置和本地初始化之间安排迁移顺序。发布前还应检查构建上下文是否通过 Docker、归档工具、复制脚本或 CI 工件把同名本地文件重新带出去。忽略规则只约束 Git 的某些路径发现流程，不会自动过滤每一个打包渠道。

文件已经包含秘密时，要按泄露事件处理

把 .env 加入规则并从索引移除，只能影响之后的仓库快照；过去的提交仍可能保留其字节，分支、标签、分叉、缓存、构建工件和他人的克隆也可能留有副本。更重要的是，凭证若已被他人读取，它的有效性不会随最新提交变化。第一步应在对应服务或凭证签发方撤销、轮换密钥，并确认新凭证部署到需要它的运行环境。要轮换的范围取决于凭证权限和可访问资源，不能只根据被误提交文件的文件名判断。

清理提交历史与停止当前跟踪属于不同操作。重写共享历史会改变提交标识，并要求协作者协调重新同步；它也不能证明外部缓存和克隆都已删除。按仓库维护者的既定流程评估是否需要历史清理、由谁执行、怎样保留可恢复副本，以及如何通知依赖这些提交的分支。本文没有执行历史重写，也没有扫描任何仓库或部署环境；不提供“清一次就保证所有副本消失”的承诺。

用可复核的检查收尾

一次有边界的验证可以列出四项：索引里是否还有路径、忽略模式由哪个文件提供、工作目录文件是否仍存在、干净检出是否能按文档创建有效配置。前三项分别用 git ls-files、git check-ignore -v --no-index、文件系统检查和 git status 交叉确认。若团队需要本机配置，可在临时目录重新克隆仓库，按项目说明复制样例并运行既有的配置校验；这会验证初始化说明，不是生产秘密处置结果。本文没有执行这些项目专属检查，命令用途基于 Git 文档解释。

意料之外的全局匹配若来自 git check-ignore，修复团队协作问题时不应只改本地全局规则；把公共约定写入仓库并让团队接受变更。索引查询若仍找到路径，则模式再精确也不会自动改变索引。路径若从当前索引消失、却仍可在旧提交中检出，说明当前状态与历史状态已区分开。每个结果对应不同下一步，避免把“界面不显示”“仓库不再跟踪”和“秘密已安全”混成一个结论。

开发者本地设置可能只需要移除索引、提供样例和校验；影响共享运行行为的文件，应先提供安全默认值与迁移说明；含有有效凭证时，则应立即撤销或轮换，再评估历史清理和外部副本。这三个情形的选择依据是团队是否需要版本化该信息、能否安全复建，以及历史值是否仍有权限，而不是忽略规则写得多复杂。对于构建打包范围，还可以对照构建上下文的输入边界，不要让 Git 排除规则代替发布前的输入检查。
