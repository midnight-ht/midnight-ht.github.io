numeric(4,2) 会舍入多余位，为何 99.995 仍报越界？

PostgreSQL numeric(p,s) 先把值舍入到声明的小数位，再检查整数位容量。存储舍入不等于输入校验；两种拒绝规则需要在转换前区分。

正文

核心要点

  • numeric(p,s) 先舍入到 s 位，再检查舍入后是否超过 p-s 位整数容量。
  • 拒绝非零多余精度与拒绝原始文本多写小数位是两种不同规则。
  • 想校验原始表示，必须在类型转换抹掉该信息之前检查。

PostgreSQL 的 numeric(4,2) 会先舍入到两位小数，再检查结果是否还能容纳两位整数：99.994 变成 99.99，而 99.995 舍入成 100.00 后整数位变成三位，于是溢出。声明的小数位数是存储转换规则，不是“多写一位就拒绝”的输入校验器。

numeric(p,s) 到底限制什么？

PostgreSQL 19 Numeric Types把 precision 定义为数字总位数，把 scale 定义为小数点右侧位数。对常见的非负 scale 且 s <= p 的声明，整数位容量是 p - s。因此 numeric(4,2) 最多能保存两位整数和两位小数，最大正值为 99.99。无约束的 numeric 则不会把输入强制到固定小数位。

这里有两个顺序不同的动作。写入声明了 scale 的列时，如果输入的小数位数超过 s，PostgreSQL 先舍入到 s 位；随后才检查舍入结果的整数部分是否超过 p - s 位。若超过，数据库报错。它不会先拿输入字符串的小数长度与 2 比较，再决定是否拒绝。

为什么 99.994 能存，99.995 却越界？

把例子拆成两步就能看出原因。假设目标列是 numeric(4,2)：

输入值 舍入到两位 整数部分位数 结果
99.994 99.99 2 在 numeric(4,2) 的范围内
99.995 100.00 3 超过两位整数容量，报溢出

第一行说明“输入有三位小数”本身不必然失败；舍入后仍在范围里。第二行则在小数精度处理时进位，结果越过整数范围。对负数也要检查相同边界：PostgreSQL numeric 在正好一半时按远离零的方向舍入，所以 -99.995 会到 -100.00，同样无法放进 numeric(4,2)。这些结果是按官方文档规则推导的示例；本文没有运行真实 INSERT。

另一个容易混淆的概念是“多于两位”。如果产品要求的是数值不能因舍入而改变，1.234 是问题，而 1.2300 与 1.23 数值相等。如果产品要求原始输入文本最多出现两个小数位，那么 1.2300 也应拒绝，即使舍入并未改变其数值。这两条规则看起来都叫“小数位数限制”，实际接受集合不同。

这一区分会反过来影响接口契约。若客户端把金额作为 JSON 数字传输，服务端解析后通常拿到的是数值对象，而不是原始字符序列；1.2300 中最后两个零是否还存在，取决于解析器和后续类型。若产品要拒绝“输入文本写了三位”，只检查数据库里的数值不够，应该在解析前保留原始字段文本，或把金额定义为十进制字符串并在边界按明确语法解析。字符串方案也不是天然正确：需要规定是否接受前导正号、空白、指数记法、千位分隔符和负零，并拒绝无法解释的形式。否则 API、批量导入和后台任务会形成不同的有效输入集合。

为什么写入后的 CHECK 可能已经太晚？

如果列本身声明为 numeric(4,2)，数据库在把值写入该列时已经执行了 scale 转换。之后的行约束面对的是经过目标类型处理的值，无法可靠判断用户原来提交的是 1.23、1.2300 还是 1.234。例如，在这个受限列上比较 amount = round(amount, 2)，可能看起来像在拒绝额外小数，但 amount 到达约束前已被转换；校验看不到原始输入。

如果要拒绝的是“会改变数值的额外位”，可先在无固定 scale 的 numeric 接收边界检查，再进入定宽列。一个未执行的设计示意是：

-- Illustrative only; not executed against PostgreSQL.
CREATE TABLE amount_stage (
  raw_amount numeric NOT NULL,
  CHECK (raw_amount = round(raw_amount, 2))
);

CREATE TABLE invoice_amount (
  amount numeric(4, 2) NOT NULL
);

在无约束 numeric 上比较 raw_amount 与两位舍入结果，表达的是“数值不得被改动”；因此 1.234 不满足，而 1.2300 数值相等，可以通过。若要求连多写的尾随零也拒绝，PostgreSQL 文档中的 scale(numeric) 可检查小数位数，例如 scale(8.4100) 返回 4；但必须确认应用与驱动把原始表示送到数据库时没有先把它变成另一个数值表示。若请求先经 JavaScript Number 或其他解析器，文本中的尾随零可能已经消失，数据库就无从恢复。

接收表是否长期保存原始值也需要业务决定。原始文本可用于拒绝理由、审计或重放，但它可能包含不必要的数据，应限定访问与保留时间。若不需要长期留存，可以在请求边界验证后，只把规范化结果写入业务表，并保留规则版本与拒绝原因的最少必要记录。

实现时还要决定校验与最终写入是否处于同一事务。若应用先验证 raw_amount，随后把同一个经过解析的值写入 numeric(4,2)，但两步之间又允许其他代码改写该值，验证结论就不再对应最终存储值。一个较容易审计的边界是：同一事务内把输入转换成无固定 scale 的十进制值，执行精度策略，再插入目标表；或者使用一段数据库函数封装校验和写入。若请求本来是文本且需要保留文本 scale，则还应把“语法校验”和“数值范围校验”拆开记录：前者判断输入表示，后者判断数值。这样拒绝日志能说明是多写小数位、舍入改变了值，还是超过 99.99 的列范围，而不是只留下一个含义模糊的“金额无效”。

舍入规则也要与后续计算一致

PostgreSQL 19 的 Mathematical Functions 文档说明，round(numeric, s) 在正好一半时远离零；文档还指出 double precision 的一半处理通常是最近偶数，且浮点类型是近似值。不要把应用语言中的浮点运算、数据库 numeric 舍入和展示格式默认当成同一套规则。

若业务选择舍入，应明确舍入发生在哪一步、采用什么规则、结果是否用于后续税额或比例计算，以及再次处理时是否会改变结果。numeric(4,2) 的隐式舍入符合 PostgreSQL 的列类型规则，但不替业务选定银行家舍入、截断或其他结算政策。若约定要求另一规则，应在明确的计算层实现并测试，同时让最终列范围仍能接住结果。

怎么验证拒绝规则真的生效？

建议把输入边界分成两组：数值值会改变与只改变文本 scale。至少覆盖 99.994、99.995、-99.995、1.234 和 1.2300，分别记录原始请求、进入 PostgreSQL 前的值、接收边界判断、目标列结果或 SQLSTATE。再检查刚好等于 99.99、超出最大值、空值、指数表示以及多个写入入口是否采用同一规则。

测试时不要只断言“请求失败”或“SQL 成功”。对每个输入同时断言三个观察点：解析后保留的文本（若策略依赖原始表示）、无约束 numeric 的策略结果、定宽列接受或拒绝的结果。比如，若规则是拒绝数值变化，1.234 应在策略边界失败，1.2300 可通过精度策略但仍须通过范围检查；若规则是文本最多两位，1.2300 应在语法边界失败。99.995 则揭示顺序：无约束数值可以先按两位策略变为 100.00，而目标 numeric(4,2) 最终会因整数容量不足拒绝。把这些断言放进 API、导入任务和数据库写入路径的契约测试，能避免某个入口悄悄采用另一套舍入规则。

如果拒绝责任放在 API，数据库仍可能被后台任务或人工 SQL 绕过；如果所有写入都先经过接收表或统一存储过程，则要验证旁路入口同样无法直接写进最终列。最终验收应分别证明“规则拒绝了哪些输入”“目标列存下了什么”“应用有没有改写数值”，不能把插入成功当成原始输入合法的证据。本文建议的 SQL 和测试矩阵尚未执行，实际约束应在目标 PostgreSQL major 版本、驱动和数据入口上验证。若还要处理 CHECK 遇到 NULL 的接受语义，可参阅PostgreSQL CHECK 约束与空值；那是另一项约束边界，不会替代原始精度策略。
