JSON 解析没报错，长编号为什么还是变了？

JSON 数字语法正确不保证长编号精确；在数值转换前保留身份，逐层核对而不从舍入值猜原文。

正文

核心要点

  • RFC 8259 的 JSON 数字语法允许比 JavaScript Number 能精确表示的整数更大的值；解析成功不等于每一位仍可区分。
  • 稳定身份通常应从 API 契约起用字符串；现代 JSON.parse reviver 的 context.source 可恢复特定原始数值文本，但运行时支持和字段语义必须先核验。
  • BigInt、字符串、整数数值各有序列化、排序和客户端兼容边界；需在真实传输链逐层验证。

JSON.parse 不报错，只能说明输入符合解析器接受的 JSON 语法，不能证明每个数值都被当前语言精确保留。JavaScript 的 Number 对安全整数有明确边界；超过边界后，相邻整数可能映射为同一个 Number。若字段表达的是订单号、用户号、外部资源 ID 等身份，最稳妥的默认契约通常是从 JSON 发送端开始把它定义为字符串，而不是等浏览器解析后再修复。

先区分 JSON 数字语法和运行时数值

RFC 8259 §6规定 JSON 数字以十进制文本表达，并允许实现对可接受数值的范围和精度设限。它特别指出，在广泛使用 binary64 的实现间，[-(2^53)+1, (2^53)-1] 范围内的整数可以精确互操作。这里的重点不是 JSON 只能写这么大的数，而是不同实现对更大值未必能保留同一数值。

ECMAScript 2026 的 Number.MAX_SAFE_INTEGER 是 9007199254740991。规范把安全整数定义为：没有另一个整数会得到同一个 Number 值。规范给出 9007199254740992 与 9007199254740993 都求值为前一个 Number 值的例子。于是一个符合 JSON 数字语法的整数进入 JavaScript Number 后，可能已经失去与相邻身份值的区分能力。

这个变化不会必然触发 SyntaxError。解析器能把文本转成一个 Number，所以结构检查继续通过；问题在于业务需要的是原始十进制身份，而运行时对象只包含舍入后的数值。接着调用 String(value) 只会把舍入后的 Number 格式化成字符串，不会恢复原始末位。Number.isSafeInteger 对已经解析的值仍有用途，但它不能逆推出被映射到该值的原文，也不能代替 API 设计。

一个实际运行的最小例子

本次在 Node.js v24.21.0 中执行：

const raw = '{"id":9007199254740993,"small":9007199254740991}';
const parsed = JSON.parse(raw);
console.log(parsed.id, parsed.small, Number.isSafeInteger(parsed.id));

输出为 9007199254740992 9007199254740991 false。这是本机运行结果，不是浏览器矩阵或生产接口测试。原始 JSON 里的 id 末位为 3，进入 Number 后打印为 2；相邻整数因此无法再由 parsed.id 唯一确定。相反，最大安全整数 9007199254740991 仍可被 Number.isSafeInteger 识别为安全。

如果把身份直接作为 JSON 字符串传输，例如 {"id":"9007199254740993"}，常规 JSON 解析会保留字符串的每一个字符。代价是使用方必须把契约当成身份处理：定义长度、允许字符、规范化方式和空值语义，避免有的服务把它当数值排序、有的客户端保留前导零、有的校验器又转回 Number。若编号允许 000123，数值语义会丢掉前导零；而 RFC 8259 的 JSON 数字语法本身不允许这种带前导零的整数写法。若上游先把身份转成 123 再序列化，丢失发生在发送之前。字符串可以保留它，但只有业务明确规定它有意义时才应保留。

reviver 为什么通常来不及

传统 JSON.parse(text, reviver) 的回调处理的是已经解析出的值。MDN 文档指出，数字在 reviver 收到前就转成 JavaScript Number，可能已经丢精度。因此回调若仅看到 9007199254740992，无法知道源文本原来是 9007199254740992 还是 9007199254740993。

较新的 ECMAScript 2026 规范为 reviver 的原始值调用提供 context.source，其中包含对应 JSON 值的源文本。运行环境实现该能力时，可以对已知字段从原始十进制字符串构造 BigInt：

const value = JSON.parse(raw, (key, parsedValue, context) => {
  if (key === "id" && typeof parsedValue === "number" && context?.source) {
    return BigInt(context.source);
  }
  return parsedValue;
});

同一逻辑已在本机 Node.js v24.21.0 执行，context.source 取到原文 9007199254740993，BigInt 转换后保留该值；这只证明本机运行时支持，不是其他浏览器或服务端版本的兼容矩阵。该处理只适用于字段契约确认其语义为整数身份的情况。部署到其他运行时前应做特性测试并保留兼容路径。还应限制字段键和允许的原始数字形式，不要把所有数字无差别转为 BigInt：金额小数、测量值、计数和版本字段可能拥有不同类型约定。

即使拿到了 context.source，它也只是解析时保存的原始数值文本，不自动证明字段含义。把它转成 BigInt 会改变后续算术类型；Number 与 BigInt 不能直接混合运算，而且原生 JSON.stringify 默认不能序列化 BigInt。若接口输出仍要求 JSON，需要明确定义将其序列化为字符串、使用经过约定的自定义序列化方案，或由 schema 将身份声明为字符串。解析端能恢复某个值，不代表所有下游系统都能无损表达它。

不同表示方案解决不同问题

方案 适用情形 需要承担的边界
JSON 字符串 身份、邮编、账号、带前导零的代码；主要目标是逐字保真 需要定义字符集、最大长度、校验与排序规则
JSON 数字并保留为 Number 值确实要在 JavaScript 做数值运算，且接口值限定在双方安全范围内 服务端生成及每个中间层都必须遵守同一范围
context.source 转 BigInt 已知字段确为整数、目标 runtime 实现 source context、并需要整数运算 运行时兼容、字段识别、BigInt 运算和 JSON 输出格式都要单独处理
原始 JSON token/高精度解析器 需要保留更广数值语法或自行控制解析类型 增加库、审计、版本、错误处理和 schema 适配成本

JSON Schema Validation 2019-09 的互操作性条款允许任意精度 JSON 数字，且其 integer 类型按数学值是否有零小数部分判断；但规范中的数学模型不会强迫某个用 JavaScript Number 实作的验证器或应用保留任意精度。schema 写了 integer，并不等于运行时一定能逐位保存。RFC 8785 的 JSON Canonicalization Scheme 则要求其规范化数字可表示为 IEEE 754 binary64，并建议需要更高精度或更长整数的应用改用 JSON 字符串。若数据要签名、哈希或规范化后比较，不能让不同运行时各自解析大整数后再期待字节结果一致。

另一个常见误区是把数据库中的 BIGINT 直接投影成 JSON number。数据库精确存储并不意味着驱动、服务语言、JSON 序列化、网关、浏览器和客户端模型全都使用同一种整数类型。某一层先转成 Number 后，后面的 PostgreSQL 或 BigInt 字段再精确也无法找回丢掉的数字。检查链路应从持久层的类型与值开始，一直走到最终消费端，并在每个跨类型边界记录输入、输出类型和字符串形式。

验收要沿真实身份链路逐段比较

接口测试不能只断言“响应能被 JSON.parse”。先明确哪些字段是身份，哪些是数量；对身份字段构造超过安全边界的相邻值，例如 9007199254740992 与 9007199254740993，检查序列化文本、传输响应、服务端模型、网关、客户端解析对象、日志和再次请求的值是否仍可区分。若字段定义为字符串，还要用 "000123" 验证前导零、长度与非法字符规则；若字段是数值，验证范围拒绝在第一次可能舍入前发生，而不是解析后只检查格式。

故障路径也要测：中间件可能将字符串 schema 强制转为 number；日志采样或分析仓库可能把长数字识别成浮点字段；客户端把字符串转成 parseInt 再用于排序；导出 CSV 或表格软件会自动转换标识符。这些现象不能仅靠前端页面快照发现。应选取相邻但不同的 ID，经过写入、读取、序列化、分页游标和重新提交后逐位比较；只看单个测试 ID 恰好没有改变，不能证明整个范围安全。

身份和数量的排序也不同。字符串 "100" 与 "20" 的词典序不等于数值顺序；如果产品需要按数值排序，应由明确支持该精度的服务端完成，或采用经过定义的排序键，不要为了排序把身份强制转换成 Number。前导零是否规范化、大小写是否折叠、Unicode 数字是否允许，都应由接口契约回答，不能让多个语言的默认转换替业务做决定。

如果历史数据已经被舍入，恢复必须依赖另一个可信来源，例如原始请求日志、上游系统或审计记录。当前值 9007199254740992 可能来自多个不同原文，补一位或根据格式猜最后数字都不是恢复。本文没有执行迁移，也没有验证任何真实数据源；修复前应对候选影响范围、回填依据和无法恢复的行分别留证。有关“唯一”与“精确”仍是不同保证，可参阅PostgreSQL 唯一约束与 NULL 的行为。

长编号要不要在 JSON 中写成字符串？ 如果它表达身份、要求逐位一致且无需由 JavaScript 直接做算术，字符串通常是跨语言更稳妥的契约；若它是计算量，应该把数值范围、精度和舍入规则写清。context.source 是目标运行时支持时的一种解析补救机制，不会取代契约、兼容性测试与跨服务验收。
