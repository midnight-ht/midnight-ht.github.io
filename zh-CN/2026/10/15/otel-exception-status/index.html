记录异常后，Span 为什么仍是 Unset？先判断这段操作是否失败

`recordException` 写入异常事件，不会自动把 Span 状态设成 Error。按 Span 的操作边界、最终结果和当前语义约定，决定是否记录异常、设置错误状态或保留 Unset。

核心要点

  • RecordException 只记录事件，Span status 需独立设置；默认 Unset 不等同于显式 Ok。
  • 先定义 Span 代表的操作，再按最终结果和适用语义分类；已恢复尝试不会自动成为整个请求的失败。
  • Recording errors 当前标为 Development；Span 异常语义约定页已标为 Deprecated 并指向日志，具体处理需核对 SDK 版本与迁移配置。

在 OpenTelemetry JavaScript 手动埋点里，span.recordException(ex) 记录的是一个异常事件；它不会替你调用 span.setStatus({ code: SpanStatusCode.ERROR })。所以控制台仍显示 Unset，可能是漏设状态，也可能是这段 Span 描述的操作恢复成功。先问 Span 代表哪项操作、操作结束时结果如何，再决定要写入哪些信号。

两个 API 写入的是不同证据

RecordException 是 AddEvent 的专用形式。它把一个名为 exception 的事件及异常属性加入 Span；SetStatus 则修改 Span 的状态字段。OpenTelemetry API 将它们定义成两个独立操作，因此前一个调用不会暗中执行后一个。JavaScript 官方埋点指南也把两步分开演示：在 catch 中调用 recordException，再将状态设为 SpanStatusCode.ERROR。这是 API 层的分工。Trace 的异常语义页面说，异常若在 Span 结束时仍未处理并导致 Error，才建议作为该 Span 的事件记录；而当前Span 异常语义约定已标为 Deprecated 并转向日志信号。具体自动埋点库是否另外处理异常，仍要看该库版本与迁移配置。

Unset 是 Span 的默认状态，不能直接翻译成“明确成功”。Trace API 的 Set Status 章节说明，状态通常保持 Unset；需要表达错误时按语义约定设为 Error，应用开发者可以在确实验证成功时显式设为 Ok。因而排查面板时要分别看：事件是否存在、状态是否设置、该 Span 描述的操作是什么，以及它是否被采样并成功导出。只搜到 recordException 这行代码，不能证明后面几项都成立。

先定操作边界，再定错误状态

异常对象回答“发生了什么”，状态回答“这一段操作最终怎样”。真正容易出错的不是 API，而是 Span 的边界含混：一个 Span 可能描述单次下游尝试，也可能覆盖带重试的完整请求；这两段的结论并不必然相同。

设想一个订单服务先访问主库存源，第一次请求超时，随后从允许的备用源取到一致数据，订单最终成功。若外层 Span 定义为“完成一次订单读取”，只凭第一次异常就把它设为 Error，会让外层错误率把成功回退误算为失败。若确实为每次尝试建立独立 Span，团队需要为“尝试”这个操作定义是否失败，并遵守该操作对应的语义约定；不能简单把子 Span 的判断复制到父 Span。这个例子是假设情形，没有运行代码或采集数据。

相反，如果备用源也失败，订单读取没有返回可用结果，那么外层操作结束时确实失败，即使代码把异常 catch 住并转换成错误对象返回。是否抛出异常不是唯一标准：OpenTelemetry 当前的 Recording errors 页面也把错误码等其他错误返回纳入“操作失败”的判断。Recording errors页面标记为 Development，团队应记录采用的版本和领域约定，不能把这条建议写成所有库的强制自动行为。

Span 所代表的操作结束结果 事件与状态的判断 需要避免的误读
异常未处理并导致这段操作失败 依当前语义约定记录异常；将该 Span 设为 Error 不能只记录事件而假设状态自动改变
某次异常被重试或回退处理，完整操作正常完成 描述完整操作的 Span 不应仅因瞬态异常被归为失败；诊断细节按适用信号和规范处理 不能为了“留下异常”把已完成操作的错误率抬高
业务上的预期拒绝，例如资源已存在 按该操作定义分类；可能是业务结果而非错误 不能把所有语言层面的 Exception 都当故障
没有异常，但操作通过错误码或结果类型失败 可按领域约定设为 Error，并设置适用的错误类型信息 不能把“没有 catch”当成成功证明

表格不是把所有异常归入同一处置规则。OpenTelemetry 的 Recording errors 示例区分了已处理的 ResourceAlreadyExistsException 与向调用方传播的 IOException：前者示例不把操作 Span 标为 Error，后者设置 Error 和 error.type。这说明业务上下文和 Span 所代表的范围会改变判断。一个“未找到”在查询资源是否存在时可能是正常答案，在必须读取该资源的请求中则可能意味着失败。

JavaScript 手动埋点应该在哪儿设状态

若应用自行管理 Span，可以把结束判断集中在操作所有者处，而不是在每个底层 catch 块里无条件标错。下面是用于说明生命周期的伪代码，未在某个 SDK、运行时或后端执行；导入路径和具体异常类型须按项目锁定版本核实。它显式等待异步操作结束后才调用 end()，但省略了 Context 激活与子 Span 传播；真实代码需要按语言 API 的 context 机制补齐。

const readInventory = async () => {
  const span = tracer.startSpan('inventory.read');
  try {
    try {
      return await readPrimary();
    } catch (primaryError) {
      // 是否记录尝试级诊断，取决于尝试 Span 与日志约定。
      return await readReplica();
    }
  } catch (finalError) {
    if (finalError instanceof Error) span.recordException(finalError);
    span.setStatus({ code: SpanStatusCode.ERROR });
    throw finalError;
  } finally {
    span.end();
  }
};

示例的意图是把外层状态留给最终失败分支。真实实现还必须回答：主源失败是否有独立子 Span；两次尝试是否都属于 inventory.read；备用源返回空值是业务拒绝还是故障；错误最终通过异常、错误对象还是响应码交给调用方；状态设置发生在 end() 之前吗。若这些答案缺失，把状态设置塞进通用异常处理器通常会让不同业务操作被同一规则误分类。

另一个反例是 catch 中记录异常但继续正常返回，同时外层随后又无条件设为 Error。异常可能只是一次被容错吸收的尝试；这样的埋点把内部过程当成最终结果。反方向也会发生：catch 后返回 { ok: false }，但只有 recordException，Span 留在 Unset；调用链最终失败，后端却没有 Span 错误状态。修复应先给每个 Span 写清操作名、输入输出、结束条件和失败定义，再把这些条件映射到代码路径，而不是先看平台上的红色图标。

有事件，不代表事件已经出现在查询结果里

从调用到可查询数据，中间至少有几道边界。所用 Span 必须处于可记录状态；异常记录必须发生在正确 Span 上，并与该操作的生命周期相符；采样决策可能让数据不进入导出；处理器、导出器、传输和后端存储也可能丢弃或延迟记录。Trace API 还指出，End 后继续调用 Span 方法通常应被忽略，虽然后端实现存在流式场景的例外。因此“源代码执行了方法”不是“后端已显示事件”的同义句。

排查时可按顺序核对：应用捕获到的对象是不是语言层的 Error；当前上下文取到的 Span 是否就是预期操作；事件和 status 是否都在结束前写入；Span 是否 recording；采样和处理器如何配置；导出响应和后端查询使用了什么时间范围与过滤条件。若自动与手动埋点同时启用，还要检查同一异常是否被记录多次。这里还要区分 API 与语义约定：Trace API仍定义 RecordException 这一 Span 事件操作；但当前exceptions on spans 语义约定页面标为 Deprecated，并指向日志信号。迁移说明允许既有仪表库暂时保留旧行为，甚至提供阶段性双写；具体某个库是否启用哪种路径，要核对版本和配置。不要据一个 API 方法存在，就推断新旧仪表库都应把异常写成 Span 事件。

异常消息可能包含用户输入或业务数据；OpenTelemetry 的异常属性约定明确提示 exception.message 可能含敏感信息。堆栈和其他上下文也应按本系统的数据分类规则处理。异常 Span 属性约定给出了异常类型、消息和堆栈等属性约定，也提示消息可能包含敏感信息；这不意味着 SDK 会自动替所有采集链路脱敏。团队要在记录前核对属性白名单、采集配置、导出器和存储权限；必要时保留错误类型和关联标识，避免复制原始敏感文本。不能为获得更完整的调试信息而默认上传整个异常对象。

如何验证“状态没变”是哪一层的问题？

先用单元级测试断言不同结果分支：未处理异常最终失败时，预期的异常事件与 Error 状态是否存在；回退后完整操作成功时，外层 Span 是否没有被瞬态异常错误污染；业务拒绝是否按明确契约分类；只有错误码的失败是否也能被检测。断言要针对同一个 Span ID，并记录哪个层级的操作被测，不能只断言导出数据里“有一个 exception 字符串”。

然后再分别验证 SDK 与导出链路。使用可控的内存或测试导出器检查事件、状态、属性、结束时间和重复记录；确认 Span 在调用期间仍 recording；最后用集成环境检查采样、批处理、网络、后端索引和查询过滤。每一层都回答不同问题：单元测试证明代码分支写入了预期字段，导出测试证明 SDK 输出结构包含这些字段，后端检查才说明实际查询可见。本文没有运行这些测试，也没有观测真实生产链路，不能据此声称任何特定数据已被修正。

异常事件应当放在父 Span 还是子 Span？ 先看问题要回答什么：若要解释一次具体尝试，就需要让该尝试有可区分的边界，并按它的语义记录；若要判断整次用户请求是否成功，父 Span 应以用户请求结束时的契约分类。一次子操作的失败可以成为父操作恢复过程中的诊断材料，但不因此自动成为父操作的最终错误。若所用语义约定要求已处理异常不记在描述完整操作的 Span/指标上，需按该约定执行；若团队需要保留重试尝试的痕迹，应明确它属于尝试级诊断，并检查是否与当前异常日志迁移规则冲突。

错误状态的可读性来自边界清楚，而不是把每个 catch 都涂成红色。团队可以在埋点约定里为每个 Span 写一句“什么结果算失败”，再为恢复、业务拒绝、错误码失败和最终抛出分别补测试。相关的日志身份与链路关联也会影响排查，可参阅日志关联与链路保留；但这类关联同样需要结合实际 SDK、采样和后端查询配置验证。
