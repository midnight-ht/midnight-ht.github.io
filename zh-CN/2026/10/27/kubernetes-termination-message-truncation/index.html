容器的终止消息少了一半，先检查字节预算

说明终止消息的单容器与共享字节预算、错误日志回退条件和重启后的状态归属，把短摘要连接到完整日志。

正文

核心要点

  • 终止消息受 4096 字节及全 Pod 12KiB 平分预算约束。
  • 错误日志回退需要文件为空并错误退出，且只保留有限尾部。
  • 重启诊断要将 state 或 lastState 对应到实际进程实例。

假设一个转换容器把六千字节的异常栈写到 /dev/termination-log，Pod 状态中却只剩一部分。终止消息有字节上限和整个 Pod 的共享预算，适合放故障摘要与查询线索。要找完整栈，应先核对日志留存；反复扩大应用写入量不会扩大状态字段的容量。

这里存的是简短终态

Kubernetes 的 Pod 失败原因指南说明，kubelet 会截断超过 4096 字节的终止消息；整个 Pod 的消息总量还受 12KiB 限制，在各容器间平分。指南以十二个普通或初始化容器为例，每个容器只有 1024 字节空间。因此，单个容器写入四千字节以内，也不能在多容器 Pod 中直接假定完整可见。

单位是字节，不能按编辑器显示的字符数推算。中文、表情和其他编码内容可能占多个字节，行数少也可能很长。诊断设计应给实际编码后的摘要留余量，把最重要的错误码、阶段和查询标识放在前面；不要让几十行通用环境信息把唯一有用的故障位置挤到末尾。这个排序是工程选择，不是承诺任何截断位置都能保住所有字段。

本文依据二〇二六年十月二十七日核对的在线指南，未运行 Pod 或读取真实故障日志。部署前仍需核对实际集群和容器运行时条件。终止消息不是长期日志存储，也不应被当成诊断数据唯一副本。

一个十二容器任务怎样留下有用摘要？

设想一个文档转换 Pod，包含应用容器和若干初始化、辅助容器，总数为十二。为了推导预算，按指南给出的例子，每个容器可用空间为一千零二十四字节。转换阶段失败时，应用若把一份六千字节的异常栈直接写入终止文件，即使文件落盘完整，状态中的消息仍无法承载全部内容。其他容器暂时没有写满，也不应当作应用可以独占总预算的依据。

可以改为写一份短摘要，例如错误类别、失败阶段、任务的非敏感查询编号，以及完整日志的检索线索。下面是未执行的说明性配置，镜像和内容均为假设；它只展示消息文件的使用方式，不代表完整可部署的业务任务。

apiVersion: v1
kind: Pod
metadata:
  name: conversion-example
spec:
  restartPolicy: Never
  containers:
    - name: convert
      image: example.invalid/converter:demo
      terminationMessagePath: /dev/termination-log
      terminationMessagePolicy: File

假设任务进入解析阶段后遇到损坏输入，应用先把完整诊断写入已经配置的日志渠道，再把 INPUT_INVALID phase=parse ref=job-42 这样的小摘要写入终止文件，并以失败状态退出。值班人员从 Pod 状态判断错误类别，再按查询编号到受控日志系统定位。编号本身不是日志已经上传成功的证据：若日志采集延迟或不可用，报告要明确完整日志缺失，不能凭一个链接宣称故障已可重建。

若需要成功退出的摘要，文件机制同样可以表达最终状态，指南说明文件内容可用于成功和失败的容器状态消息。不要让“没有错误”等占位文字在失败路径之前提前写入，然后期待日志回退自动用异常栈覆盖它。消息来源选择有自己的条件，并不理解应用叙事里哪一句更重要。

为什么 FallbackToLogsOnError 没有补齐栈？

官方规则要求两个条件同时成立：终止消息文件为空，而且容器以错误状态退出，此时才取容器日志末尾作为消息。回退日志还限制为 2048 字节或 80 行，取较小者。它提供最后一小段线索，不是完整日志导出功能，也不会把文件内容与日志合并成更长的消息。

因此，文件里已有“开始处理”，随后程序崩溃，回退并不会因为这句话信息不足而自动替换它。若文件为空但程序正常退出，也不能据此期待错误回退。若异常发生后又输出许多清理日志，日志末尾可能主要是清理信息，真正的触发原因反而不在那一段。选择这种策略前，要明确它对应用输出顺序的依赖。

我会优先让能够控制退出路径的应用主动写短摘要；对难以改造的工具，才把错误日志回退作为有限补救。前者需要可靠的错误处理和写入路径，后者依赖日志尾部及退出码。两种方案都应保留独立日志渠道。若进程突然被杀，应用可能来不及写摘要，这时应结合退出原因和其他证据，不能把空消息解释成无故障。

容器重启后，该看 state 还是 lastState？

要让字段对应实际那一次进程。指南中的重启诊断示例读取 .lastState.terminated.message：当前实例可能已重新运行，而前一次的终止信息在 lastState 中。若当前实例本身已经终止，则应检查当前 state 中的 terminated 信息。先确认容器名称、当前状态和重启次数，再判断消息属于哪一次；不能仅复制一个字段路径应用到所有状态。

lastState 也不是无限次重启的历史账本。若需要追查连续多次失败，应及时保存带观察时间和实例身份的状态，并依赖适当的日志留存。多容器输出应带容器名，避免把初始化失败与应用失败的摘要混在一起。重启后的正常运行不能抹去前一轮失败，同样也不能用前一轮消息解释新一轮不同的输入。

应用摘要还应避免一半是业务状态、一半是无法解析的长栈。若监控程序需要读取错误码，采用简短、稳定且可容忍缺失字段的格式，并在读取端保留原始消息供人工排查。不要把一个可能被截断的 JSON 文档直接当作完整事件入库；解析失败应显示“摘要不完整”而非“任务成功”。这是读取方的容错选择，具体格式仍由团队定义，不能让状态展示层擅自猜测被截去的内容。

待执行检查可以构造短消息、超过单容器上限的消息、多容器共享预算和多字节内容，再分别安排空文件错误退出、非空文件错误退出、空文件正常退出。比较原文件、容器日志和状态字段，记录截断与回退实际结果；不要把这些预期当成本篇的运行日志。本站终止时间预算讨论的是退出机会，本题讨论退出后留下多少诊断信息。两项设计都要成立，摘要才能把值班人员带到仍然存在的证据。
