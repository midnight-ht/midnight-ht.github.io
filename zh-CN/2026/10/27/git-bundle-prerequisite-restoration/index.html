bundle 在源仓库验证通过，空仓库为什么恢复失败？

用基线与增量包解释 verify 的当前仓库前提，给出未执行恢复路径，并区分对象历史、哈希清单和开发目录备份。

正文

核心要点

  • verify 的前置对象检查取决于当前仓库。
  • 增量包需要既有基线，自包含包可用于空仓库起步。
  • 哈希清单和完整历史都不等于整个开发目录备份。

假设 main 比 release-base 多三个提交，团队生成 release-base..main 的 bundle 并在源仓库验证成功。接收方只有空目录，这份增量包仍需要被排除的基线历史。git bundle verify 的通过结论与执行校验的当前仓库有关，不能当作任意空仓库都能恢复的证明。

先问校验是在哪个对象库里通过的

Git bundle 手册的 verify 说明要求检查包格式，以及前置提交是否存在并在当前仓库完整连接。源仓库原本就有完整历史，满足前置条件并不意外；空接收仓库没有这些对象，结论就不同。这里核对的手册最后变更于2.48.0 版本，页面列出直到2.56.0 版本没有该手册变更，不代表本机已经运行了这些版本。

bundle 可以自包含，也可以在创建时排除一部分历史。带排除基线的范围要求接收仓库已有该基线及其可达对象；没有前置条件的自包含包才可以从空仓库开始恢复。文件可读取、格式有效和目标拥有必要历史，是不同检查。文件传输校验和只回答传到的字节是否相同，也不能证明接收仓库满足对象前提。

把验证安排在目标侧，可以较早发现缺失历史。它不是贬低源侧检查：源侧依然能发现包生成或文件损坏问题，但两处检查使用的前提不同。交接单若只写“verify 成功”，却不记录校验仓库、包身份和所需基线，就丢掉了最能解释恢复失败的信息。

用 A、B、C、D 走完两种交接

设想提交历史依次为 A、B、C、D，release-base 指向 A，main 指向 D。接收仓库已经保存 A 时，可以用从 A 之后到 D 的增量包推进。下面的命令只表达这份假设，不在当前仓库执行；引用名称必须事先存在，路径也需按隔离练习目录调整。

# Source repository with release-base=A and main=D.
git bundle create delta.bundle release-base..main
# Recipient repository that already contains A and its reachable history.
git bundle verify /transfer/delta.bundle
git fetch /transfer/delta.bundle main:refs/remotes/offline/main

增量包携带推进到 D 所需的新对象，并声明被排除历史的前置条件。接收方不是靠 tag 的相同拼写满足条件，而是其对象库确实拥有所需提交及连接历史。目标侧 verify 若报告缺失，应先停止导入流程并核对基线，不要为了继续操作去伪造一个同名分支。

若接收方确实是空仓库，就改为交付自包含的基线包，或者直接交付覆盖目标引用完整可达历史的包。仍以这个假设为例，可先在源侧创建 main 的自包含包，再让接收方克隆该包。

在源仓库用 git bundle create full.bundle main 创建完整 main 历史包，接收方再用 git clone -b main /transfer/full.bundle recovered 恢复。这两步同样未执行。

这两条命令描述历史恢复入口，不证明业务环境已能运行。克隆后应核对恢复出的 main 是否指向预期 D，再检查文件内容和项目所需的正常构建条件。若计划长期使用“基线加增量”，则每个增量都要关联明确的基线身份和顺序。少一份中间包、基线被替换或恢复顺序错误，都可能破坏整条离线恢复链。

完整包和增量链怎样选择？

接收方状态未知、灾难恢复或首次交接时，自包含包更容易解释：接收方不需要事先拥有特定历史。代价是传输可能更大，且打包范围仍需明确。只打包 main 代表保留该引用可达的历史，不自动包含其他未被它覆盖的分支；需要哪些引用，应在创建前清点。

接收方已有可靠基线、带宽受限且能保存恢复顺序时，增量有实际用途。节省传输量的代价是管理依赖链。建议保留包校验和、所含引用、前置提交、对应接收方和实际恢复记录；何时生成新的完整基线，应按保留成本与恢复复杂度决定。不能仅看某份包很小，就认定备份设计更优。

反例是在源仓库 verify 后立即删除唯一的基线副本，再把增量包称为全量备份。包本身可能完全有效，但接收方没有重建历史的起点。另一个反例是只检查 bundle 的 list-heads 输出，看到 main 就宣布可恢复：引用清单说明包提供什么入口，不证明前置对象已经具备。

拿到前置提交的哈希，就够了吗？

不够。文本里写着 A 的哈希，只是告诉接收方需要哪个对象，不会把 A、其树、文件内容和祖先对象放进对象库。verify 要求的是所需提交存在且完整连接，必须通过合适的历史传输满足。相同分支名称也不能弥补缺失对象，复制一个哈希到交接表更不能代替传输。

反过来，如果目标已经有这些对象，即使本地分支名称不同，也应以实际对象关系验证，而非只凭命名宣布不兼容。恢复流程应保留机器可核对的对象身份，并让目标仓库实际执行验证。本文没有执行打包、克隆、fetch 或任何恢复演练；命令预期属于依据手册设计的检查路径。

历史恢复还缺哪些本地状态？

bundle 传输引用及可达对象，不等于整个开发目录快照。未提交的工作区内容、索引状态、仓库配置和 hooks 等需要单独安排。外部大文件服务、子模块仓库及构建所需秘密也不能因为主仓库有一个引用就被视为已备份。先定义恢复目标，再清点依赖，避免为了“全量”二字把私密配置随意装进传输包。

恢复演练还应明确目标引用如何落地。示例 fetch 把远端 main 放在单独的 offline 远端跟踪位置，便于先比较目标提交，再决定如何更新本地工作分支；它没有自动覆盖接收方正在编辑的文件。若接收方有本地提交，应先查看分歧和合并要求，不能为了让分支名一致而强制重置。对象导入成功与工作分支完成集成是相邻而不同的步骤，后者仍要经过正常审查。

本站stash 保存范围讨论的是临时工作，本题讨论提交历史在不同对象库间的前提。真正的验收应在隔离目录分别模拟“已有 A”和“完全空白”两种目标，验证增量只在前者满足条件，再从完整包恢复目标引用并核对内容。保留每一步的仓库身份与结果，才知道交接的是一份有效文件，还是一条真正能走通的恢复路径。
