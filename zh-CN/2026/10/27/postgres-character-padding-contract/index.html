char(4) 里的 AB：为什么相等却不能照猜 LIKE

区分char补齐、character等值比较、LIKE与显式转换，避免文件宽度改变商品码身份。

正文

核心要点

  • char 的等值、模式匹配和转 text 要分别检查。
  • 固定文件宽度不等于业务码长度。
  • 超长拒绝应放在显式截断之前。

假设商品码存为 char(4)，输入 AB 后按等号查询能找到，换成 LIKE 条件却得到不同判断。排查应同时看类型和运算符，而不是只看客户端显示的两个字母。PostgreSQL 的固定宽度字符具有补空格和忽略尾空格的特定规则，这些规则没有统一覆盖所有字符串操作。

同一份码，为什么出现两种观察？

PostgreSQL 18 字符类型文档说明，character(n) 会把短值补空格到声明宽度。两个 character 值比较时，尾部空格没有语义意义；转成其他字符串类型时，尾空格被移除。LIKE 和正则匹配中的尾空格则有意义。必须保留“两个 character 值”这个条件，不能将它改写为所有文本比较都忽略空格。

下面是未执行的教学查询，比较对象和显式转换都写在语句内，避免依赖驱动绑定参数时推断出的类型。这里没有真实商品库，也没有提交查询结果。

SELECT 'AB'::char(4) = 'AB  '::char(4) AS same_code;
SELECT 'AB'::char(4) LIKE 'AB' AS exact_pattern;
SELECT ('AB'::char(4))::text LIKE 'AB' AS after_text_cast;

依照文档推演，第一个表达式应为真；第二个模式没有消费补入的空格，不能因为等号为真就推断它也为真；第三个先经过文本转换，观察的是去掉尾空格后的文本。验证时应逐条记录布尔值和表达式类型。界面把尾空格隐藏起来，或者表格列宽刚好挡住空格，都不能替这些表达式解释差异。

长度也是观察规则的一部分。产品所说的“码有四位”，可能指四个有效输入字符，也可能只指文件里占四个位置。类型补齐只保证它所定义的存储表示，不能证明用户曾输入四个非空格字符。若业务要求恰好四个有效字符，应该先给出允许字符集和空格政策，在转换前检查输入。数据库类型无法从已经补齐的值恢复用户原来输入了几位。

文件宽度放在哪一层？

假设上游只允许两位或四位码，外部固定宽度文件却要求每条码占四个位置。内部用 text 或 varchar 保存规范码、导出时按文件规范补齐，是一种可审查的选择。它让数据库中的业务身份与文件布局分别维护。代价是导出程序必须处理编码、分隔和补齐，不能把所有格式责任交给列类型。

如果既有系统确实依赖 char 的比较语义，保留它也可能合理。但要明确哪些查询比较 character、哪些查询显式转 text，以及接口是否保留尾空格。迁移时只改列类型可能改变匹配结果，不能假设原查询仍然表达同一份身份规则。代码评审应找到实际操作符和参数类型，而不是只看建表脚本上的四位声明。

反例是把所有查询都加 rtrim，声称这样最一致。如果尾空格在某个来源里属于合法标识，这会主动合并原本不同的输入。相反，如果码不允许任何空格，直到查询时才修剪又可能让错误数据长期存在。修剪是业务规范化决定，应写明位置和可逆性，不能充当不了解类型差异时的通用补丁。

同样，不要为了让 LIKE 找到短码就随手追加百分号。AB% 也会接纳其他以 AB 开头的码，扩大了原来的精确匹配条件。假设有 AB 与 ABCD 两个码，模糊查询可能同时选中它们，随后一笔更新就不再只针对原来的商品。修复匹配差异时，必须保留调用方要找哪一个身份的要求。

显式转成 char(n) 会拒绝超长商品码吗？

不会可靠地替你做这项输入校验。官方文档规定，显式转换为 char(n) 或 varchar(n) 时，超长字符串会被截到指定长度，而不是因超长报错。假设调用方提交 ABCDE，先转成 char(4) 后只剩前四位；下游再检查长度，已经看不到第五位。这与普通向列赋值遇到非空格超长字符时的报错路径不同。

这个追问改变了验证位置：若产品要求拒绝超长原文，应在显式转换之前断言输入，并让导入失败记录保留可定位的行号。是否允许尾部多余空格也要单独写清，不能依赖数据库关于全空格超长部分的例外，偷偷替产品选定宽容策略。错误提示应说明违反哪条码规则，而非只回显数据库异常。

拟议验证准备 AB、AB加尾空格、ABCD、ABCDE，以及含内部空格的码。分别检查原始输入、类型转换后的值、两个 character 的等号、文本等号和 LIKE，给每种表达式独立写期望。再经过真实驱动读写一次，确认绑定参数和输出字符串有没有增加转换。本文没有执行这些查询或驱动检查，不能把上述推演记成已通过。

迁移字符类型时，唯一性也需要预演。假设旧列把带尾空格与不带尾空格的两个输入视作相等，新列保留了尾空格的差异，业务是否允许它们成为两个身份需要明确。反向迁移也可能把原本不同的文本合并到同一种比较结果。不能只用迁移语句能够执行证明身份关系未变，应在变更前对候选数据做冲突分析，并让业务确认合并或拒绝方式。

还要检查导出再导入的往返。假设文件格式补了两个空格，接收系统又把它们当作码的一部分，回传时产生与内部规范码不同的字符串。验收应同时核对文件字节布局和回传后的业务身份，避免只验证导出文件看起来对齐。若选择在边界剥离填充，先确认该格式确实把它定义为填充，而不是擅自删除来源数据。

本站的数值舍入与输入校验也讨论类型转换会丢失原始信息，但字符比较还有操作符这一层。最终需要留下的不是“长度正确”四个字，而是允许哪些输入、按什么类型比较、在哪个出口补齐，以及哪组反例必须被拒绝。
