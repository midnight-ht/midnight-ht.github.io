两个 NULL 先 UNION，为什么后面的 1 救不了类型

解释UNION两两解析如何先把unknown变text，比较分支声明类型、ALL与外层转换的不同作用。

正文

核心要点

  • 两个unknown分支可能先解析为text。
  • 空分支也应遵守报表列类型合同。
  • UNION ALL 与外层 CAST 不能替代分支类型声明。

假设报表生成器拼出 SELECT NULL UNION SELECT NULL UNION SELECT 1。前两个分支会先单独确定类型，最后一个整数不会让整条链重新推导。PostgreSQL 把多个 UNION 作为两两嵌套的集合操作处理，全是 unknown 的那一对先得到 text，随后就可能与 integer 冲突。

不是等全部分支出现后再投票

PostgreSQL 18 类型解析文档规定，解析逐个输出列进行；全部输入都是 unknown 时选 text。多个 UNION 则按成对嵌套处理。文档直接给出了两个 NULL 后接整数失败的例子。NULL 在这里缺少明确类型，不代表它天然属于所有最终结果类型，也不代表已经被赋成整数空值。

将语句写成括号形式，更容易看见失败位置。下面是未执行的教学查询，结果说明来自文档规则推演，没有数据库运行回执。

(SELECT NULL AS amount UNION SELECT NULL)
UNION SELECT 1;

内层先处理两个未定类型输入，amount 被解析为 text；外层收到的是“文本类型的一列”与“整数类型的一列”。此时内层不再是一张可以随意重新选择类型的空白纸。外层不能匹配这两种输入，就在执行出报表行以前报错。生产系统应保留原始错误和实际 SQL，以免把解析失败误报为没有销售记录。

假设生成器按月份拼金额列，一月和二月没有数据，生成占位 NULL；三月有整数金额。问题不在三月金额值太大，也不在前两个月数量为零，而在占位分支没有携带声明的输出类型。即使每个单独分支看起来都可以执行，组合后的类型仍然需要在局部解析点满足条件。

在最早的空分支声明金额类型

如果合同明确金额输出为 integer，可给最左边的 NULL 显式标类型。更稳妥的生成器让所有分支遵循同一个列契约，不把类型正确性依赖在偶然存在的某个月份数据上。

SELECT NULL::integer AS amount
UNION SELECT NULL::integer
UNION SELECT 1;

这个修正让空值从一开始就是整数空值。示例仍未执行。它表达的是 integer 合同，不是建议所有金额都用整数；金额单位、精度和取值范围需要另行确定。若实际报表要求 numeric，就应从占位到真实分支一起选择 numeric，而不能为了消除报错随手换成能容纳当前样本的类型。

把带类型的真实分支挪到左侧，有时也能改变推导结果，但这种修复对生成顺序很脆弱。下个版本可能先拼两个空月份，问题又回来。显式类型更便于评审者看见预期，也让“所有月份都空”的报表仍有稳定元数据。对提供给驱动、导出器或其他视图的查询，空结果时列类型稳定也是接口的一部分。

UNION ALL 与外层 CAST 分别修什么？

将 UNION 改成 UNION ALL 改变重复行保留方式，却不撤掉对应列的类型兼容要求。报表需要保留每条明细时可以选 ALL，但应独立验证类型。反例是开发者把所有集合操作都改成 ALL，看到某一组样本不再去重，就以为类型问题也被解决；两个 NULL 先解析的根源没有改变。

也不要在整条失败查询外包一层 CAST，期待它修复内部。外层转换必须先拿到一个可解析的内层表达式；如果内层在 text 与 integer 匹配时已经失败，就没有输出可供外层转换。应该在决定类型的分支位置处理，而不是等输出之后。这个追问增加的是解析先后关系，不能用“最后都转整数”概括。

相反，把某个分支显式转 text 虽然可能让类型兼容，却会改变报表接口。后续按字符串排序时，数字的字符顺序不等于数值大小；下游如果期望金额计算，还可能重新解析。团队应先选数据含义，再选转换，不能把“不报错”当作类型选择的唯一标准。

多列和空数据怎样验？

解析按列发生，所以两列报表需要分别检查金额与来源名。给第一列加 integer 不会顺便修复第二列的未知类型。可以在独立环境里先对前两个分支形成的子查询调用 pg_typeof，再加入第三个分支，比较不带类型、只最左声明、每分支声明、外层才转换这几种情况。每个用例都应有列类型和接受或拒绝的明确预期。

数据覆盖包括三个分支全空、最左有值、最右有值、某分支错误返回文本金额，以及金额范围超过原类型。最后一项用于检查合同本身是否过窄，不应通过把类型一律改 text 来掩盖。真实生成器还要核对参数绑定的类型，因为带参数查询的推导条件可能不同于直接写出的字面量。本文没有运行 SQL 或驱动测试。

金额列的名称同样值得固定。假设最左分支原来来自真实月份，后来改为空占位，列别名若随生成顺序变化，导出器可能继续按旧字段名读取而得到空栏。类型修好只让查询可解析，不保证输出名称和单位保持稳定。可以由生成器维护一份输出列声明，同时规定名称、单位和类型，再让每个分支按该声明投影。

这种声明还方便审查新增来源。假设另一个系统把金额作为含货币符号的文本传入，应先在来源边界明确解析与非法值拒绝，再转换成目标数值类型。把所有分支一起放宽成字符串会让错误更晚出现，也失去逐行解释非法输入的机会。类型契约应尽早揭露不兼容来源，而不是让每一条新数据都迫使下游重新猜测。

UNION 的去重与行身份解决合并后为什么少行，本题解决的是为什么连合并结果都尚未产生。排查记录先保留嵌套结构、每列类型和最早的已定类型分支，再讨论保留重复行、排序和报表业务口径，才不会在错误的阶段调整正确的开关。
