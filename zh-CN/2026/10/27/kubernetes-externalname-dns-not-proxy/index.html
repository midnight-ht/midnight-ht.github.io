集群里的 HTTPS 别名为什么会证书不匹配？

解释 ExternalName 的 DNS 别名与 HTTP、TLS 身份差异，用账单查询定位失败，并比较客户端地址与代理方案。

正文

核心要点

  • ExternalName 返回 DNS 别名，不承担 HTTP 改写或代理。
  • 解析成功仍需分别验证 TLS 身份、HTTP 路由与业务读取。
  • 固定 IP 与内部 URL 需求各需明确的配置及恢复责任。

假设账单服务把 https://billing.prod.svc.cluster.local 指向 api.vendor.example，DNS 已能解析，HTTPS 却仍报证书名称不匹配。ExternalName 只给 DNS 别名，不会把客户端使用的主机身份改成供应商域名。应沿名称解析、请求身份和服务端响应分别定位，而不是继续修改 Service 的端口。

CNAME 解决了哪一步？

Kubernetes 的 Service 文档中 ExternalName 一节说明，这种 Service 把服务映射到一个 DNS 名称，返回相应 CNAME；重定向发生在 DNS 层，不经过代理或转发。本文按二〇二六年十月二十七日核对的在线说明分析，未创建集群。具体环境仍需记录 Kubernetes、DNS 和客户端实现版本，不能用在线文档替代连接测试。

DNS 查询回答的是“这个名称可以继续向哪里解析”。客户端实际发出的 URL 仍可能使用内部名称，HTTP 请求携带的 Host 以及 TLS 校验针对的名称，也没有被这条 DNS 记录改写。供应商能够提供外部域名的证书，不表示它也持有内部服务域名的证书。文档专门提醒 HTTP 和 HTTPS 存在这种主机名差异问题；解析成功只能把排障推进到下一层。

这里有一个容易混淆的成功条件。若测试仅查询内部名称并取得外部名称，DNS 别名已符合预期；若业务要求客户端通过该内部 HTTPS 地址完成账单查询，还要满足服务器名称识别、证书和应用路由等条件。两项需求可以分别验收，不能把第一项通过写成整个外部 API 已接通。

走完一次账单查询的假设诊断

设想调用方运行在 prod 命名空间，希望使用服务完整名称访问供应商。下面是说明性的清单，没有应用到集群，也没有真实账单数据。

apiVersion: v1
kind: Service
metadata:
  name: billing
  namespace: prod
spec:
  type: ExternalName
  externalName: api.vendor.example

调用方先查内部服务名，检查获得的别名及后续地址解析。如果这一阶段失败，排查名称拼写、命名空间、集群 DNS 与外部解析条件；没有地址时，讨论 HTTP Host 还为时过早。若这一阶段正常，就记录实际请求 URL，确认客户端仍然在使用哪个主机名，而不是只保存最终连接的 IP。

下一步检查 TLS 错误发生在何处。假设供应商证书只包含 api.vendor.example，调用方仍按内部名称验证，那么名称不匹配就是可解释的结果。这不证明证书失效或供应商服务不可用。切换到供应商正式域名进行受控对照，可以帮助区分别名身份与外部服务本身，但应使用正常验证，不能通过关闭证书检查来制造“接通”的结果。

再设想使用明文 HTTP 作教学对照，供应商按主机名区分租户。连接建立后，内部名称对应的 Host 不被识别，可能得到意外站点或错误响应。TLS 校验和 HTTP 虚拟主机是两层问题：只解决其中之一，并不证明另一层已符合供应商接口约定。实际错误码由服务实现决定，本文不预言某个统一状态码。

最后用没有真实写入副作用的查询验证响应身份和内容：确认请求到达正确 API、返回符合约定的数据结构，并且认证范围仍属于目标账号。一个可解析名称或一个成功握手，都不能代替这一步。失败报告应保留各层的观测顺序，避免把多种失败压成“ExternalName 不工作”。

是改客户端地址，还是增加代理？

如果目的只是方便集中管理供应商地址，而应用可以使用供应商正式 URL，直接让客户端采用该域名通常更容易保持原有身份契约。配置管理仍可统一维护 URL，但它不必表现为一个内部 HTTP 主机别名。代价是应用配置需要明确携带外部地址，而不是假定所有依赖都能靠 Service 名访问。

如果产品或现有客户端必须保留内部 URL，且需要改写应用请求身份，就应评估具有相应能力的受控代理。它要明确上游名称、TLS 校验、请求头、超时、认证与错误传播；增加这层也带来维护、容量和故障责任。ExternalName 没有替代这些职责，不能因为清单更短就宣布功能相同。某个具体网关是否支持所需改写，仍须查其版本和配置，并做真实验证。

反例是在客户端里关闭 TLS 验证，再因为查询返回了内容就提交修复。这样绕开的是身份判断，未解决别名与供应商身份的矛盾；中间得到的数据也未必来自期望服务。另一个反例是反复增加 targetPort。普通 Service 的端口映射是另一套机制，不能给 DNS 别名附加原本不存在的 HTTP 代理能力。

如果供应商只开放固定 IP，可以把 externalName 写成 IP 吗？

不能把它当成直接映射 IP 的方式。官方说明，形似 IPv4 的 externalName 仍按由数字组成的 DNS 名称解释，不作为 IP 地址处理。若确实需要表示固定外部地址，应按环境选择适当的无选择器服务及端点等方案，并单独核对其维护方式；这不是把字符串换成数字就完成了迁移。

即使最终能到达固定 IP，应用协议中的主机身份仍需单独成立。供应商换地址、证书续期或租户路由变化时，应有明确负责人更新配置和执行检查。IP 可达解决的是一层路径，不能让 HTTPS 名称问题自行消失。

还有一个对照需要固定认证条件。若直连供应商域名用的是另一组凭据，返回成功并不能只归功于域名变化；应在允许的受控范围内保持账号、路径和请求内容一致，只改变要验证的名称条件。若客户端自动跟随重定向，也要记录最后到达的位置，避免供应商先返回一个页面跳转，就被误认为内部别名直接支持了原接口。这个对照设计只缩小解释范围，不替真实供应商的接入文档作决定。

待执行验证先记录内部名称、CNAME 目标、客户端 URL 与供应商认可的名称，再分别检查解析、正常 TLS 校验和受控业务读取。修改方案前后用同一调用身份比较，保留失败分支，不写入敏感凭据。本站Service 入口与目标端口的区别讨论的是代理型服务的端口契约；本题先确认所选服务类型根本是否承担那层职责，再选择客户端配置或代理方案。
