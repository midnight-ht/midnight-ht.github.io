临时表提交后还在：连接池下一位借用者会遇到什么

按真实后端会话、池重置和ON COMMIT策略检查临时表行、结构与名称遮蔽，给出显式事务例子。

正文

核心要点

  • 请求结束不等于数据库会话结束。
  • PRESERVE、DELETE ROWS 与 DROP 留下不同状态。
  • ON COMMIT DROP 需要覆盖使用过程的事务窗口。

假设批次甲在池连接里建了 stage_ids 临时表，提交后归还连接；批次乙借到同一数据库会话，再建同名表。TEMP 不会因一次请求结束就自动消失。PostgreSQL 默认保留临时表及其行直到会话结束，提交动作需要用 ON COMMIT 另外定义。

先把请求、事务、会话分开

PostgreSQL 18 CREATE TABLE 文档说明，临时表通常在会话结束时删除，也可以选择在事务结束时删除。这里的会话必须是同一个数据库后端会话。应用把连接对象归还池、结束一次 HTTP 请求，都不能单独证明这个后端会话已经关闭。

甲和乙如果确实落到不同会话，各自的临时表彼此独立，不会因为名称相同就共享行。连接池如果归还时执行了有效的会话重置，也可能清理临时对象；具体效果要查实际池配置和重置命令。事务池化还可能让相邻事务使用不同后端。因此，“用了连接池就会串数据”同样不准确，风险成立需要后端复用、对象残留及后续查询这几个条件同时出现。

假设连接池只有一个后端，甲创建表并放入订单编号101，提交后没有清理。乙在相同会话执行无条件 CREATE TEMP TABLE，可能遇到关系已存在；如果改成 IF NOT EXISTS 后直接追加编号202，又没有核对旧行，就可能处理甲的101。后者不是容错成功，而是绕过创建错误后继续使用残留状态。这里只作机制推演，没有运行连接池或导入任务。

三种提交策略留下什么？

ON COMMIT 章节给出三种策略。PRESERVE ROWS 是默认值，提交不做特别处理；DELETE ROWS 在每次提交清除行，表结构仍在；DROP 在当前事务提交时删除表。选择需要同时回答是否保留行、是否保留结构，以及下一事务是否还需要这个对象。

假设导入只在一笔事务里暂存本批订单，可以把范围直接写进 SQL。以下代码未执行；订单表和实际导入步骤需要按项目补充，这里只演示临时对象的生命周期。

BEGIN;
CREATE TEMP TABLE stage_ids (id integer) ON COMMIT DROP;
INSERT INTO stage_ids VALUES (101), (102);
SELECT id FROM stage_ids ORDER BY id;
COMMIT;
-- 此后在同一会话查询 stage_ids，预期不再存在。

中间 SELECT 应在表存在时读取本批编号，COMMIT 后表结构消失。若任务确实跨两笔事务使用同一批暂存行，这个策略就不合适；应重新审查为什么需要会话级暂存、谁拥有会话，以及失败后谁回收对象，而不是机械替换所有临时表为 DROP。

DELETE ROWS 适合保留结构而不保留上一事务行的设计，但下一位借用者仍会面对已存在的表。创建语句的列结构若发生版本变化，IF NOT EXISTS 不会验证现有表就是新结构。升级前后同时运行时尤其要小心：不能把“没有抛创建错误”当作表字段已经迁移。必要时按连接初始化版本或显式检查结构安排清理。

自动提交模式下，为什么创建后表就没了？

如果每条语句都是一个独立事务，CREATE TEMP TABLE 后那次隐式事务就会提交。此时 ON COMMIT DROP 会立即删除刚创建的表，后面的 INSERT 运行在新事务里，已经没有可用对象。因此需要上例的显式 BEGIN，把创建、使用和提交放在同一事务窗口。这个追问不是更换清理选项，而是检查事务包装是否符合设计。

回滚路径也要独立验证。在事务内新建的临时表，创建会随该事务回滚而撤回；已经存在的会话临时表，则不能仅凭一次失败回滚就推断其结构必然被删除。不要用一条 finally 里的 ROLLBACK 来证明所有会话状态干净。清理代码应按当前对象来源和选定生命周期判断，并保留清理失败的可观察结果。

查询还可能碰到同名正式表

官方说明默认搜索路径把临时 schema 放在前面，同名永久表可能被临时表遮住。假设 public.stage_ids 是正式业务表，当前会话又有临时 stage_ids，未限定 schema 的查询可能读到临时对象。需要正式表时写明 public.stage_ids；需要临时表时，也应在设计中确认目标归属。改成 DELETE ROWS 只能清行，不能消除名称遮蔽。

拟议测试应固定物理后端，记录 pg_backend_pid()，让甲提交后由乙继续借用，分别检查对象存在、行内容和再次创建。再用第二条真实会话作对照，验证临时对象不共享。最后分别开启池重置和事务池化配置，重复同一组观察，避免把驱动层对象编号当作后端身份。本文没有执行这些测试，不报告实际池清理能力。

连接池验证还应带上两个不同的业务身份。让甲的暂存编号与乙的允许范围完全不重叠，乙的结果只能来自自己的清单；只断言条数正确，可能让一条甲的记录替代一条乙的记录而未被发现。若导入权限在正式表连接阶段才检查，仍要证明残留暂存行不会扩大操作范围，不能把临时表私有于会话当作业务用户隔离。

连接归还失败也要有处理：假设提交成功后清理报错，应用不应把这条状态不确定的会话当作已清洁资源继续借出。可由连接管理层按实际能力隔离或销毁会话，并保留任务与后端身份以供排查。这是需要结合池实现验证的设计选择，不代表任意连接池已经提供该机制。

测试报告应写出每次借用对应的后端编号，以及清理发生在提交、归还还是销毁阶段。若没有这些证据，就只能列出待验证的复用条件，不能把会话残留风险升级为已发生的数据泄露。

临时表批量装载后还应根据复杂查询需要评估 ANALYZE；文档说明自动维护进程不能访问临时表，不能盼望它自动补齐所有统计工作。本题不提供任何性能收益或阈值。相关的会话咨询锁与连接池解释另一类会话状态；两者都要求认清后端寿命，但锁的释放次数与临时表的行、结构清理需要分别验收。
