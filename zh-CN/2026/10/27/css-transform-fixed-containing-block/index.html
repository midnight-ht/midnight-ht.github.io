fixed 遮罩为什么只盖住卡片，还会跟着页面滚动？

解释非 none transform 如何建立 fixed 包含块，使用支付卡片对照定位参照，比较移除变换与外部宿主，并分开 z-index。

正文

核心要点

  • 普通可变换祖先的非 none transform 会建立 fixed 后代包含块。
  • translateX(0) 仍有结构性作用，不等于 transform:none。
  • z-index 改排序而非定位参照，弹层修复还要验证焦点与范围。

假设支付确认遮罩写着 position: fixed; inset: 0，却只铺满四百像素宽的卡片。卡片祖先上的 transform: translateX(0) 虽没有明显位移，仍会建立 fixed 后代的包含块。要修复覆盖范围，应先检查祖先计算样式和弹层挂载位置，而不是继续加大遮罩的 z-index。

fixed 先找的是包含块

CSS Transforms Level 1 的渲染模型规定，能够应用变换的元素在 transform 为非 none 时，为其后代建立包含块，padding box 用来布局绝对定位、固定定位后代及有关背景。本文针对普通可变换 HTML 卡片中的普通 fixed 后代，不把顶层对话框或其他特殊呈现机制一起纳入结论。

这解释了“视觉没有变化，定位却变了”。translateX(0) 的位移为零，但 transform 的值仍然不是 none；是否建立包含块，不能只凭肉眼观察矩阵有没有移动像素。组件库为动画准备的样式、某个断点的过渡状态，都可能在不显眼的时候改变弹层的参照。

CSS Positioned Layout Level 3 的包含块规则说明，fixed 盒采用最近建立固定定位包含块的祖先；在连续媒体中，如果没有这样的祖先，才使用布局视口。这与“所有 fixed 都相对视口”不同。这里核对的是二〇一九年二月十四日的 Transforms 候选推荐及二〇二五年十月七日的 Positioned Layout 工作草案，未把标准文档当成目标浏览器验收。

用一张支付卡片重建问题

下面是未执行的教学例子。卡片内有确认按钮，打开后显示普通 DOM 遮罩；它不是调用 showModal 的原生顶层对话框，也没有用门户移到页面别处。假设页面还有足够内容可滚动，卡片宽四百像素、高三百像素。

<main class="page">
  <section class="payment-card">
    <button type="button">确认支付</button>
    <div class="overlay">确认订单与金额</div>
  </section>
</main>

.payment-card {
  width: 400px;
  height: 300px;
  transform: translateX(0);
}
.overlay {
  position: fixed;
  inset: 0;
  background: rgb(0 0 0 / 60%);
}

按这些条件推演，遮罩的四边偏移依据卡片建立的包含块计算，并不会因为 fixed 这个单词就自动铺满页面视口。页面滚动时，卡片与其中这份定位参照一起移动，遮罩看起来便不像预期的全屏固定层。实际尺寸还受卡片的 padding、border 和其他样式影响，不能把四百乘三百的外观描述当成精确矩形测量结果。

本例假定没有其他建立固定定位包含块的因素；transform 只是可能条件之一。真实诊断应从遮罩向外核对所有实际生效的包含块条件，不能只因较远祖先有 transform，就跳过更近的有效参照。然后逐层检查计算后的 transform，确认它在本例中的作用；不要只在当前组件文件里搜索，它可能来自通用动画类。临时把该值切换为 none，再保持同样视口和滚动动作比较遮罩矩形。如果参照改变，说明这条样式与症状有关；随后恢复原值，核对动画为何存在，不能把开发者工具试改直接当作最终修复。

这个对照也需要完整任务。打开确认层，检查它是否覆盖预期背景、是否能读到订单与金额、取消能否回到原按钮。若页面滚动或改变窗口后露出可点击背景，仍未满足全屏模态要求。几何定位只是其中一项，覆盖像素不等于外部键盘交互已受限制。有关焦点行为应结合站内弹窗的焦点流程单独验收。

删除变换，还是把遮罩移出去？

若 transform 是已经不需要的遗留优化，移除它可能是最直接的选择，但应检查正常状态、动画进入退出和响应式断点，避免修好遮罩却破坏侧栏或卡片动画。用另一个同样非 none 的恒等变换替换，不能消除这份包含块职责；把 translateX(0) 换成 scale(1) 仍不等同于 none。

若祖先变换确实是产品效果的一部分，可以把页面级弹层挂到变换祖先之外的专用宿主。需要检查宿主自己的祖先链，不能只移动一层就默认已到视口参照。移动 DOM 或使用组件框架的门户，还可能影响样式继承、主题变量、事件组织和焦点返回；这些属于方案成本，应在组件接口中说明，而不是把挪节点当成没有代价的 CSS 修补。

还有另一种合理需求：遮罩原本就只应覆盖卡片，允许页面其他区域继续操作。此时局部包含块可能符合目标，问题反而是名字叫“全屏确认”而行为是局部覆盖。先明确覆盖范围和交互范围，再选择局部层或页面层。不能因为某个技术行为常被称为坑，就一律删除所有祖先 transform。

z-index 更大，能重新相对视口吗？

不能。z-index 处理堆叠顺序，不会把当前 fixed 元素的包含块改成视口。Transforms 规范还说明非 none transform 会创建堆叠上下文，后代的层级值受到祖先上下文边界影响。一个极大的数字既不能扩大几何覆盖范围，也不能无条件越过其他祖先上下文中的元素。

应分别记录两个问题：遮罩的矩形以谁为参照，以及它在相关层之间怎样排序。前者要检查包含块和挂载位置，后者要检查堆叠上下文关系。把遮罩搬到外层可能同时改变二者，但仍需分别验证，不能从“现在盖住了”倒推两个机制本来是同一回事。

测量时应避免另一个假阳性：页面内容不足以滚动，遮罩即使跟着卡片，也可能在静态截图里看似固定。练习页面应先确认文档实际发生了滚动，再比较遮罩与视口、卡片的相对位置；测试还要保持卡片结构和内容高度一致，避免切换样式时顺便改变了文档总高度。定位依据的判断来自一组有对照的轨迹，不是从某一次 top 值恰好为零推断。

组件发布前也应检查实际使用位置。同一个遮罩在独立预览里可能没有变换祖先，放进带动画的业务壳层后才出现问题。组件说明可以要求页面级宿主，并保留一个嵌入变换容器的失败样例，防止今后的重构再次把宿主移回原处。这个约束针对覆盖目标，不意味着所有弹层都必须挂到 body；局部弹层仍可有自己的包含块合同。

待执行验收可以固定初始视口，保存卡片与遮罩的 bounding rect，再滚动文档、缩小窗口、打开长内容，比较 transform 非 none、none 和外部宿主三种路径。记录遮罩是否按目标范围覆盖，取消与提交后焦点和业务对象是否正确，失败提示是否仍可见。本文没有运行浏览器探针，也没有改动支付页面。交付时应带上祖先计算值和实际测量，才能说明修复的是定位参照，还是仅在一张截图里碰巧遮住背景。
