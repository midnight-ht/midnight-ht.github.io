lru_cache 是线程安全的，为何同一参数仍计算两次

区分缓存结构一致、同键在途合并与持久幂等，解释内部锁为何不自动重新检查缓存。

正文

核心要点

  • 结构线程安全不保证同键首次执行只有一次。
  • 内部串行锁不自动把调用退回缓存入口。
  • 跨进程副作用需要超出内存缓存的合同。

假设两个线程同时读取商品42的价格，缓存尚未填入，读取函数还在等待远端。缓存可以保持结构一致，同时允许两次底层调用重叠。Python 的 lru_cache 线程安全描述缓存自身的数据结构，不承诺同一键在并发未命中时只执行一次。

两位调用者怎样同时越过未命中？

Python functools 文档明确说明，多线程更新时缓存保持一致，但如果第一次调用尚未完成并缓存，另一线程仍可能再次调用被包装函数。本次打开的页面标为 Python 3.15.2。这里讨论普通线程调用，不把它直接套用于协程对象缓存或其他缓存库。

设线程甲查询键42，缓存没有完成结果，甲进入读取函数等待远端；线程乙也查询42，此时甲仍未返回，乙也可能进入读取函数。两次调用最终分别返回，缓存结构仍然可以正常保存某个结果。结构没有损坏，与业务函数被调用几次，是两条不同的验收要求。不能用一次缓存命中统计替代对底层调用数的观察。

以下代码只展示这个允许出现的窗口，未执行，也不承诺任何特定调度必然产生两次调用。fetch_price 是待定义的依赖，不代表真实价格服务。

from functools import lru_cache

@lru_cache(maxsize=128)
def price(product_id):
    return fetch_price(product_id)

如果 fetch_price 是纯计算，重复工作可能只增加资源消耗；如果它每次向收费接口发请求，就有额外调用成本；如果它包含扣款，问题已经超出缓存优化。是否接受重复，必须从函数副作用和业务合同判断，不能因为装饰器写着线程安全就统一放行。

缓存键也需要先对齐。文档说明，参数必须可哈希，不同参数模式可能成为不同条目，关键字参数顺序也可能导致分开的缓存项。排查“同一商品为什么两次调用”时，先记录规范化后的实际参数，区分同键并发未命中与根本使用了不同键。日志里的商品编号相同，不能独自证明函数调用形状相同。

允许重复、串行化与合并在途请求

若计算可重复且成本可接受，可以保留 lru_cache，明确它减少已完成结果的重复读取，而不是消除全部重叠。这个选择维护成本较低，但应为突发未命中安排资源预算。命中率很高不代表冷启动或热门键失效时也安全，验收需要看那段最容易重叠的窗口。

若需要同一键的调用者共享一项正在进行的工作，可以另外维护在途状态：第一位建立某键的执行记录，后续调用者等待同一结果；完成后再写已完成缓存。这常被称为 singleflight 思路。它还需要定义失败是否共享、等待者取消是否取消生产者、记录何时移除，以及结果缓存失效后如何重新选执行者。本文没有交付一个完整实现，不能把这段结构描述当作可直接上线的库。

全局锁是更容易理解但更粗的取舍。若在调用缓存包装器之外持锁，再在锁内调用它，后到者串行进入时可能看到前一次已填入的结果；同时不同键也会互相等待。是否接受这种阻塞，要按调用时长和并发需求判断。按键锁可以缩小影响，却增加锁记录生命周期和异常清理责任，不是无代价的替换。

在被缓存函数内部加锁，等待者会重新查缓存吗？

不一定。假设甲和乙都已通过装饰器的未命中判断，进入原函数后才争抢内部锁。乙获得锁时，执行位置仍在原函数里，并不会自动回到外层缓存入口重新检查。它可能串行完成第二次 fetch_price，只是从同时重复变成先后重复。把锁放进去解决了并发执行，却未必解决重复执行。

如果确实要在内部协调，必须让等待者在协调协议中取得第一位的结果，或者把缓存检查放到正确的锁保护范围。需要特别审查递归与异常，避免同一线程等待自己尚未产生的结果。不能靠在函数里加一行锁就声称已经实现每键只调用一次。这个追问检查的是控制流位置，而不是锁对象是否创建成功。

跨进程又是另一层。每个工作进程的内存缓存和在途表各自独立，一个进程内的协调不会自动限制另一个进程。重启后结果也可能丢失。对不可重复副作用，需要服务端的业务身份、持久记录与重试规则；缓存无法替这些提供跨故障的幂等承诺。不要把减少计算次数的工具提升为扣款去重依据。

验证不要依赖碰巧撞到同一时刻

拟议测试用两个工作线程和受控闸门：让第一个底层调用进入后停住，再让第二次调用有机会到达相同入口，记录底层调用计数。只有两个调用都已进入时才释放闸门，否则测试可能因为调度偶然串行而误判。测试的等待应设置独立超时和清理，不能把一个错误的屏障变成测试永远挂住。

随后再做单线程重复读取，检查完成结果能否命中；改成两个不同键，检查协调是否错误阻塞；注入第一位失败，确认等待者收到什么，以及下一次调用是否能重新开始。返回可变对象时还要另审共享修改，不要把结果缓存当成结果不可变。本文没有执行线程测试、计费调用或性能测量，不能报告消除了多少远端请求。

本站TaskGroup 的失败范围关注协程组成员的取消，本题关注线程间同键工作的合并。两者都需要明确谁等待谁，但不能互换机制。缓存审查先写清允许重复什么、按什么键、在哪个进程范围，再检查真实调用次数；“线程安全”四个字不能代替这份合同。
