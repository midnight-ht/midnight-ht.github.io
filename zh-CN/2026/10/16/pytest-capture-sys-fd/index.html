pytest 没捕获到输出，应该选 capsys 还是 capfd？

先看写入边界，再确认快照时刻：capsys 观察 Python 流，capfd 观察文件描述符；子进程重定向仍需单独读取。

正文

核心要点

  • capsys 与 capfd 的分界在写入路径，不在终端是否显示。
  • readouterr() 是持续捕获过程中的快照；它不负责等待任务结束。
  • 子进程重定向、字节输出和日志 handler 应按各自出口验证。

先看内容写到了哪里：Python 的 sys.stdout、sys.stderr 用 capsys；直接写操作系统文件描述符 1、2 的库或继承这些描述符的子进程，更适合 capfd。如果 readouterr() 返回空值，还要检查读取时机，因为它只快照当前输出，不负责等异步任务或子进程完成。

两种 fixture 观察的不是同一层

pytest 的标准输出捕获指南与fixture 参考把 sys 捕获和 fd 捕获分开说明。capsys 替换 Python 的标准流对象；capfd 面向操作系统文件描述符 1、2，能捕获直接写这些描述符的输出；但若子进程被显式重定向到独立管道，仍应从该管道读取。文档同时说明，默认的全局捕获属于 fd 层，但这不意味着测试函数请求的每种 fixture 都覆盖所有输出来源。

假设包装函数打印“开始”，调用的原生库又直接向 stderr 写入诊断。断言只检查 capsys.readouterr() 时，Python 的提示可能出现，原生库的文字却不在结果里。在假设的继承描述符场景中，改用 capfd 才能覆盖两种路径。这个例子是解释机制的假设，没有实际执行。反过来，如果只是普通 Python 函数写字符串，capsys 更贴近接口承诺，也更容易让测试读者理解。

判断时不要只看终端是否出现文字。还要问：输出是由 print()、sys.stderr.write()、os.write(2, ...) 还是日志 handler 产生？子进程是否继承了 pytest 接管的 fd，还是启动时将 stdout 重定向到了另一个 pipe 或文件？网络日志、写文件的 handler 不属于 capsys 或 capfd 自动覆盖的标准出口。若进程输出被显式重定向，测试应从对应 pipe 读取并等待该进程，而不是希望任一 fixture 能越过重定向边界。

readouterr() 是快照，不是等待器

readouterr() 返回调用时已经捕获的 stdout 和 stderr，并继续捕获之后产生的内容。它不会等待一个 coroutine、后台线程或子进程跑完。于是某个测试在启动子进程后立刻读取，得到空字符串，并不能说明 fixture 层级错了：程序可能还没写，缓冲区可能还没刷新，或者任务尚未结束。正确顺序取决于任务接口，例如等待 communicate() 返回，或等待明确的完成信号，再断言捕获结果；不能用固定 sleep 把调度竞态伪装成稳定同步。

多次读取也应按阶段命名。第一次快照可以检查“初始化完成”，后一次检查“最终结果”；两个快照是两个观测点，不是自动合并的完整日志。若要求输出严格按 A、B、C 顺序出现，就要确认被测接口本身保证此顺序，并在事件并发时用可控同步安排，而不是从一次本机输出倒推出契约。

文本、字节和临时放行

文本 fixture 返回字符串，二进制 fixture（capsysbinary、capfdbinary）返回 bytes。若协议本身是字节流，先按系统默认编码解码，再比较可读文本，可能掩盖错误编码或截断；若接口明确给用户文本，则应写清编码策略和错误处理。选择 binary fixture 只是保留了观察到的字节，不替应用定义哪些内容合法。

需要在测试中短暂看到输出时，捕获指南说明 fixture 的 disabled() 上下文可以临时放行输出。它适合调试观察，不是修复捕获断言的办法，也不应该成为把敏感诊断打印到 CI 日志的理由。密码、访问令牌、个人信息应在进入失败报告前脱敏。测试报告可能被长期保存或在协作平台可见，fixture 观察得越宽，日志治理越重要。

把“看不见”还原成可以复现的路径

例如，一个命令行适配器先用 print() 输出任务编号，再调用 C 扩展写出错误码。若断言只对 capsys 做比较，任务编号出现而错误码缺失，是一种能定位到写入层的结果；若两条都缺失，就需要检查 fixture 是否读得过早、调用是否发生、流是否被应用替换。把期望写成“既有编号也有错误码”并不能替代这些诊断，因为两者的生产者和出口不同。测试名也可以指出它证明的是 Python 流契约还是底层诊断契约，让失败时团队知道该检查哪段代码。

再看子进程。若子进程继承 pytest 正在接管的文件描述符，capfd 才有机会观察它的标准输出与错误；若父进程把输出传给 subprocess.PIPE，数据由 CompletedProcess.stdout 或 communicate() 返回，捕获 fixture 就不是这条数据通路的所有者。还有一种常见分歧是程序先写入管道、测试很快快照：此时应等待进程完成或等待协议中的结束标志，而不是更换 fixture。反例是子进程根本没有被启动，或者退出码非零并在写入前失败；此时捕获为空是结果，不是捕获器漏掉输出。把退出码与输出一起断言，才不会将启动失败误诊为文本问题。

输出顺序同样有边界。Python 标准流可能缓冲，而直接 os.write 通常绕过该层缓冲；并发线程和子进程也可能交错写入。即使两种文字都在 capfd 结果中，也不代表每次都会以同一顺序排列。若输出协议要求顺序，应让被测代码显式同步或分阶段发出事件，并测试该承诺；否则测试只检查必要元素，不对偶然顺序过度约束。某些输出写到日志文件或 socket，fixture 无法从“系统上别处”自动收集，应该用日志接口或文件/网络测试替身观察。

用最小矩阵定位空输出

可以构造四类独立情况：Python print 和 sys.stderr.write；直接 os.write(1, bytes)；继承 stdout/stderr 的子进程；将子进程输出主动重定向到 PIPE 的子进程。前 3 类分别用相应的 fixture 验证；最后一类要读取 PIPE 并等待子进程退出，不能依赖 capfd 猜测重定向后的流。若目标是 Python logging，还要检查 handler 的目标；使用 pytest 的 caplog 是另一种观察方式，不能把 logger 事件与 stderr 混为一谈。

每个测试应同时写明预期出口和完成条件。例如断言一个稳定诊断码，比锁定包含临时路径、时间戳和线程号的整份输出更能表达契约；但若输出格式本身是公共接口，就需要有意验证格式，不要为了减少易碎性删除关键断言。一个有效的诊断过程是先识别生产者与实际出口，再确认 fixture 覆盖层级，之后确认任务是否完成，最后判断断言约束的究竟是稳定契约还是偶然格式。每一步都能提出可复现的反例，避免连续追加 sleep 或改成 -s 后“看起来好了”却未解释原因。

运行 pytest 时，全局 --capture=sys、--capture=fd、--capture=tee-sys 和 -s 影响会话级表现；请求 capsys 或 capfd 的测试则有自己的局部观测能力，文档说明 fixture 的使用优先于禁用全局捕获的选项。不要从 CI 命令行推断 fixture 必然捕获相同对象，需核对所用 pytest 版本。本文按 2026-11-24 打开的 stable 官方文档整理，stable 页面本身会随版本更新；项目实际版本未知。

本文的例子和矩阵是验证建议，没有在具体项目中执行。真正验收时应记录 Python/pytest 版本、启动命令、输出写入 API、子进程重定向、读取快照前的等待条件，以及断言的 stdout/stderr/bytes 内容。对失败路径也要验证：子进程非零退出、未刷新缓冲区、任务超时、异常提前抛出、目标输出被重定向，以及敏感内容是否进入报告。完成后再决定用 capsys、capfd、二进制变体还是直接读取管道。相关的 fixture 生命周期问题参见pytest fixture 的测试隔离。
