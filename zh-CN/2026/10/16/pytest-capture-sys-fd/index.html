pytest 没捕获到输出，应该选 capsys 还是 capfd？

capsys 与 capfd 观察不同输出层；快照不等待任务完成，字节、文本与日志出口需要明确。

正文

pytest 中选择输出捕获方式，应先确认内容写到了哪一层。capsys 面向 Python 的标准流，capfd 可以捕获文件描述符层的输出，包括直接写到文件描述符一、二的库，以及沿用这些输出描述符的子进程。没有捕获到文本，不足以证明被测程序没有输出，也不意味着应该直接关闭所有捕获。

输出去向决定检查工具

pytest 的标准输出与错误捕获指南介绍 capsys 和 capfd 等 fixture，并说明 readouterr 会取得截至当时的输出快照，之后继续捕获。需要读取非文本数据时，文档还提供对应的二进制 fixture。这些机制帮助确定测试边界，并不把文件、网络日志和标准错误自动归为同一个出口。

假设 Python 包装函数调用一个底层工具，终端能看到提示，使用某个流捕获 fixture 的断言却拿不到。这里是待分析的假设场景，没有运行记录。先检查内容由 Python 写入，还是通过底层文件描述符输出，再检查进程是否已结束及内容是否写到预期出口，比增加等待时间更有针对性。

捕获快照也有时间边界

readouterr 读取的是已经发生的输出，并不替调用方等待异步任务或子进程完成。如果程序还在运行，得到空快照可能只是观察得太早。测试应使用适合该任务的完成条件，再对相应阶段的输出做断言，避免把调度时机变成偶尔出现的失败。

多次读取时，也应明确每次想验证哪个阶段。初始化提示、处理过程和最终结果可能需要分别检查。不要把早期快照与后期快照不加区分地拼接，又据此声称某个文本顺序已经得到证明。对顺序的要求应来自接口契约，而不是来自一次碰巧出现的输出排列。

文本与字节边界也值得保留。如果被测接口承诺输出原始字节，先任意解码再断言，可能掩盖编码错误；若接口承诺用户可读文字，则需要确定编码及错误处理方式。使用二进制捕获只是提供正确观察对象，不自动决定业务该接受哪些内容。

断言应关注需要承诺的部分

建议测试核对稳定且有意义的输出，例如必要诊断标识或明确的结果字段，而不是把带时间、路径或环境差异的整份输出当作永远不变的金样。哪些内容应稳定，仍需由接口用途决定；也不能为了让测试通过就删除所有断言，只保留“进程没崩溃”。

临时禁用捕获可以帮助人工观察，但不等于问题已经定位。对于子进程输出，还应检查启动参数、重定向和退出状态；对日志系统则需要核对它真正写向哪里。工具名称相似，不代表它们覆盖相同层次。本文没有执行这些检查，也没有测试某个具体第三方库。

把程序输出打印进失败报告前，要处理口令、令牌和个人信息。捕获能力更强，也可能扩大泄露范围；保留必要上下文与限制公开范围应同时设计。不能以“只在测试里”为由假设构建产物不会被其他人看到。

实际验收可以分别安排 Python 流输出、文件描述符输出、二进制内容和分阶段输出，确认所选观察层与任务完成条件一致。相关隔离问题可参看pytest fixture 的测试隔离。先选对观察边界，再解释输出是否符合预期。
