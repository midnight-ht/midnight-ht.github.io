npm 开了 ignore-scripts，为什么 npm test 仍会运行？

npm CLI 11.9.0 的实测显示，ignore-scripts 会跳过安装脚本和 pre/post 钩子，但显式 npm test 仍执行目标脚本。

正文

核心要点

  • ignore-scripts 控制自动生命周期触发，不是代码沙箱。
  • 显式 npm test 仍执行目标 test，但对应 pre/post 钩子不运行。
  • 用干净 fixture 分别检查依赖、脚本副作用和命令目标。

ignore-scripts 不是“这个项目不能执行代码”的总开关。npm CLI 11 文档把它定义为跳过 package.json 脚本，但也明确保留显式命令所指向的脚本：npm test 仍跑 test，npm run build 仍跑 build；在该选项开启时，这些命令对应的 pretest、posttest、prebuild、postbuild 不会随之运行。它控制的是一类自动触发，不是沙箱，也不是对后续命令的授权判断。

我在本机 npm 11.9.0 上用临时目录做了一个最小复现：安装一个只含本地文件依赖的 fixture 时启用 --ignore-scripts，依赖仍被放进 node_modules，依赖的 install 和 postinstall 标记文件没有出现；随后用同一选项运行 npm test，test 标记出现，而 pretest 与 posttest 标记没有出现。这个结果只证明该版本、这组无网络 fixture 的行为，不是依赖安全审计，也不代表项目或 CI 已被隔离。

同一个参数，保护的是哪一段？

npm CLI v11 配置文档把 ignore-scripts 的默认值列为 false。设为 true 时，npm 不运行 package.json 中的脚本；紧接着文档又列出例外：npm start、npm stop、npm restart、npm test 和 npm run 等明确要执行某个脚本的命令，目标脚本仍会执行，只是不再带上前置或后置脚本。这里应按 CLI v11 解释，不能直接推成所有 npm 历史版本或其他包管理器的完全相同行为。

这条边界容易被忽略，因为“安装时关掉脚本”和“流水线不会执行仓库代码”听起来很接近，实际不是一回事。安装阶段自动触发的依赖生命周期脚本被压住后，流水线下一行仍可能显式运行项目自己的测试或构建脚本。只要该命令加载了仓库文件、依赖模块或构建插件，代码仍在当前用户和当前容器权限内执行。参数不会替你检查目标脚本的内容，也不会自动撤掉已经注入环境的令牌。

哪些钩子会一起消失？

npm 的脚本文档把普通命令的钩子列得很具体：执行 npm test 时，正常顺序是 pretest、test、posttest；执行用户定义脚本时也有相应的 pre<name> 和 post<name>。但是，ignore-scripts 下显式运行 npm test 的例外只保留目标 test，不保留这组前后置钩子。

假设一个团队把测试数据准备放在 pretest，把结果清理放在 posttest，然后 CI 加了 npm --ignore-scripts test。此时测试主体会运行，但准备和清理都不再按预期发生。若测试碰巧用到了上一次构建留下的数据，它甚至可能通过；这不是 npm 文档保证的结果，而是一个需要在干净目录验证的故障路径。反过来，如果团队把安全扫描只藏在 pretest，显式 npm test 也不能替代那条扫描。关键并非“要不要使用开关”，而是检查和准备到底依赖哪一个事件。

包安装也存在类似误判。npm install --ignore-scripts 可以把包安装到目录里，同时跳过其自动脚本。一个包可能依赖安装脚本编译本机绑定、下载平台产物或生成运行文件；目录存在并不证明这些动作发生，更不能证明省略它们之后程序仍可用。安装退出码回答的是 npm 安装流程是否以成功状态结束，不是所有包的后续运行条件是否齐备。

用一个干净 fixture 验证边界

下面的实验不需要接入外部注册表。给临时根项目写入三条脚本，并让一个本地文件依赖拥有 install、postinstall 两条脚本：

npm install --ignore-scripts --offline --no-audit --no-fund
npm --ignore-scripts test

在我执行的 fixture 中，前一条命令退出码为 0，依赖目录存在，但依赖脚本的标记文件不存在；后一条命令退出码也为 0，只产生 test 标记，没有 pretest 或 posttest 标记。项目的 package.json 脚本使用 echo 写标记，依赖来自本地 file: 路径，没有下载真实第三方包。这个实验把安装阶段和主动运行阶段分开观察；它没有证明恶意代码无法通过别的入口运行，也没有覆盖 workspace、Git 依赖、不同 npm 版本或平台上的全部生命周期组合。

复现前应先清空输出目录和旧依赖，再检查三个层次：目标依赖是否存在、自动生命周期的副作用是否发生、显式目标命令以及它的前后置钩子各自是否发生。若只看命令退出码，或者只看 node_modules，两种相反的误判都可能出现：以为脚本被完全禁用，或以为依赖准备已经完成。记录 npm 版本、精确命令和每个标记文件，才能把文档语义变成可复核的工程证据。

把安装政策和执行政策分开

如果目标是减少安装阶段自动运行依赖脚本，ignore-scripts 可以作为一个有边界的控制；如果目标是阻止不受信任代码取得发布令牌，单独设置它不够。显式测试、构建、打包、代码生成器，以及被它们导入的插件，仍需要单独审查。更稳妥的流水线设计是把依赖安装与验证/发布分成不同任务：安装任务不注入发布凭据；需要执行仓库脚本的任务使用最低权限、短生命周期凭据和受控网络，并从干净工作区生成可检查的产物。是否采用这些控制要按威胁模型决定，本文没有验证任何生产 CI 配置。

审查清单也不应只写“启用了 ignore-scripts”。至少要列出 npm 版本和配置来源、安装命令、显式执行的脚本名、实际运行的前后钩子、由跳过脚本带来的产物差异，以及测试失败时是否会遗留旧文件。配置来自命令行、环境或项目设置时，流水线应把最终生效值和调用命令一起记录；不能只凭某一台开发机的 .npmrc 推断发布环境的行为。

“删掉开关，构建通过”也不是一个闭合的验证。它可能只是让缺失产物重新生成，也可能重新启用了未经审查的依赖脚本。应先确认哪一份输入缺失、哪个生命周期负责生成，再在隔离 fixture 中验证替代步骤，并检查构建输出是否来自当前提交。遇到可疑脚本时，要按真实执行时间检查日志、文件和凭据暴露范围；后来打开或关闭配置，都不能撤销此前已经发生的动作。

什么时候这条结论不够用？

此文的代码与日志是本机 npm 11.9.0 临时 fixture 的执行记录。官方文档给出的是 CLI v11 的配置与脚本约定；具体项目是否缺少生成物、是否泄露秘密、是否需要某个钩子，仍需检查它的 package.json、依赖内容和实际任务环境。别的包管理器有自己的配置和生命周期模型，不应照搬这个参数名去推导它们的行为。

如果需要进一步确认安装输入是否固定，可以看npm ci 与安装输入。锁文件、一致性安装、脚本跳过和显式代码执行审查解决的是不同问题。把每一个动作、权限与产物证据写清楚，才能判断开关到底减少了哪段自动执行，又留下了哪段需要负责的执行路径。
