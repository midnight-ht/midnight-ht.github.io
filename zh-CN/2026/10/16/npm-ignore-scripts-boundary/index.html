npm 开了 ignore-scripts，为什么仍能运行项目脚本？

ignore-scripts 不阻止显式目标脚本执行；安装准备、构建产物和执行权限应分阶段审查。

正文

npm 的 ignore-scripts 用于控制自动脚本执行，并不是阻止项目运行任何代码的隔离环境。即使启用该设置，显式运行 npm run 或 npm test 等命令时，目标脚本仍会执行。审查安装流程时，必须把自动生命周期与后续主动执行分开看。

开关的范围要按文档理解

npm CLI 十一版的配置文档说明，ignore-scripts 启用后，不运行 package.json 中的脚本；同时明确列出显式执行特定脚本的命令仍会运行目标脚本，但不会运行对应的前置或后置脚本。这里引用的是该版本配置语义，不代表任何历史版本或其他包管理器都完全相同。

假设构建环境在安装依赖时启用了该配置，团队便认为后面的测试命令也不会执行依赖或项目代码。这个推断把安装阶段的控制扩大到了整个流水线。本文没有运行相关命令，也没有对某个依赖做安全鉴定；示例只用于说明控制措施应覆盖实际执行阶段。

安装完成不等于产物完整

有些项目依赖安装脚本准备本地组件或生成所需文件。禁用以后，依赖目录存在，不能单独证明后续构建和运行条件齐备。团队应检查哪些准备工作是必须的、它们来自哪里，以及是否有经过批准的替代步骤。不能因为某次安装退出成功，就推断所有功能已经可用。

恢复某个步骤时，也不要为了方便一次性放开整个环境。先说明目标脚本、输入来源、运行权限和输出用途，再选择适当执行方式。这是审查建议，不是本文验证过的安全方案。不同项目需要不同控制，单一配置既不替代来源核验，也不替代执行权限和秘密范围设计。

显式运行测试和构建同样应列入代码执行清单。脚本名称叫 test，并不自动保证其没有网络请求、写文件或其他副作用。需要检查真正执行的脚本和相关调用链，而不是根据名称推断行为。尤其在处理外部贡献时，凭据与环境权限应按实际信任边界设置。

让配置与证据对应

建议记录 npm 版本、实际命令、配置来源和环境差异，避免开发者本地、持续集成和发布环境使用不同设置却难以解释。排查缺失产物时，先确认安装阶段是否跳过必要准备，再决定是否运行已审查的步骤。不要直接删除配置重试，然后把成功当成风险已经消失。

验收应覆盖禁用自动脚本后的依赖可用性、显式执行时目标脚本的行为，以及前置后置步骤是否符合预期。还需检查失败时产物是否处于可辨认状态，避免残留文件让第二次构建偶然通过。以上没有实际执行，不能作为项目已完成安全验证的回执。

如果已经发生可疑脚本执行，仅在下一次安装中加上该开关，也不能撤销过去的行为。应根据执行范围检查环境和凭据，不能把未来控制描述成历史事件已经修复。这里不假定存在事件，只说明时间边界需要保留。

与安装输入稳定性相关的另一层问题，可参看npm ci 与安装输入。锁定输入、限制自动脚本、审查显式执行和验证产物各有用途。准确说明每项控制能证明什么，比给一个配置开关赋予全部安全责任更可靠。
