forEach 里写了 await，外层为何提前结束？

用可控的本地例子观察 forEach 的返回值，再按任务依赖选择逐项等待、并行汇总或逐项记录结果。

正文

核心要点

  • 回调返回的 Promise 不参与 forEach 的完成。
  • 调度决定开始顺序，汇总决定如何等待。
  • 只有可核对的结果才能确认写入。

数组的 forEach 会调用每个存在的元素对应的回调，却不等待异步回调返回的 Promise。回调里的 await 只暂停该回调；外层如果要等一批工作真正结束，要么逐项等待，要么保留各项 Promise，再等待汇总结果。选哪一个取决于后项能不能先启动，以及界面要向用户报告什么。

遍历结束时，回调可能刚走到第一处等待

ECMAScript 的 Array.prototype.forEach 算法检查元素是否存在，调用回调，继续下一个索引，正常结束时返回 undefined。它没有把回调的返回值放入容器，也没有等待这个返回值。普通回调直接抛错会打断遍历；异步函数体内抛错体现为返回的 Promise 被拒绝。外层如果从未取得这个 Promise，就少了一条接收任务失败的路径。

可以把这个区别缩到两个任务。下面用未解决的 Promise 当作闸门，把「开始」和「完成」拆成两个可观察的事件。字母只是测试标识，没有网络请求，也不依赖定时器的快慢。保留 work 是为了等实验收尾；真实的错误写法通常连这组引用也没有。

import assert from 'node:assert/strict';

let release;
const gate = new Promise(resolve => { release = resolve; });
const events = [];
const work = [];
const outer = ['A', 'B'].forEach(id => {
  work.push((async () => {
    events.push(`start:${id}`);
    await gate;
    events.push(`done:${id}`);
  })());
  return work.at(-1);
});
assert.equal(outer, undefined);
await outer;
assert.deepEqual(events, ['start:A', 'start:B']);

release();
await Promise.all(work);
assert.deepEqual(events, ['start:A', 'start:B', 'done:A', 'done:B']);

第一条数组断言发生在释放闸门之前。两个任务已经进入函数体，正等待同一个 Promise；外层甚至执行了 await outer，仍然没有等到任务，因为这里等待的是 undefined。第二条数组断言成立，需要测试代码先释放闸门，再等待保存下来的两项工作。以上三条断言在 Node v24.21.0 本地通过；实验只验证这组受控事件，没有测量接口响应时间。

先决定后项能不能启动

设想导入表格的每一行先保存到服务端，其中有一条地址行依赖上一条账户行返回的标识。对这两行直接使用 map，会在账户结果尚未返回时调用地址任务。可把它们放在一个明确的依赖链里：先等待账户保存结果，取出标识，再把标识交给地址保存操作。若账户保存失败而异常继续向外传播，这一链的地址操作就还没有开始。简单的 for…of 搭配循环体里的 await 可以表达逐项的依赖；必须先确认被等待的函数真的返回了代表那一步的 Promise。

如果每行都是独立的标签更新，允许调用重叠，await Promise.all(rows.map(saveRow)) 则能等待这组结果都成功。对普通数组，调用 saveRow 的动作发生在 map 中；汇总器接收的是已经创建的 Promise。规范的 Promise.all 算法为各输入接入履约与拒绝处理，全部履约时按输入顺序交付结果。输入顺序对上了，也不说明服务端是按这个顺序写入的。需要控制最大同时操作数时，让派发逻辑在有空位后才启动新项，别先把所有操作交给 map 再期待汇总器替你限速。

两种写法也可以组合。一份文件里可能有多个相互独立的账户，每个账户下的地址要等本账户建立完成。先把账户和地址划为同一组，组内依次等待，组间限制正在处理的组数。若一个账户下的地址有多项，还要决定地址之间是否真有先后关系，不能把账户之间的并行直接套给组内。导入界面应保留原始行号和所属账户，失败时才能告诉用户哪条有直接错误、哪条由于缺少前置结果还没尝试；二者不能用同一条「保存失败」覆盖。

批次报错时，还有哪些结果没确认？

假设独立的两行已同时发出：第一行立即收到服务端拒绝，第二行仍在等待。若使用 Promise.all，外层收到拒绝时，第二行不因此停下。关于等待失败和取消的区别解释了这个边界。此时界面可以先说明批次遇到错误，但不应宣布第二行也失败并立刻重发。如果第二行在服务端完成，而浏览器没有收到确认，重发可能重复修改记录；应该先按业务提供的查询或去重机制核对结果。取消请求也不能单独证明已经做的写入被撤销。

如果产品要求先把每行结局交给用户再退出界面，可以保留每个任务的完成结果并等它们都结束，例如使用 Promise.allSettled。这些 Promise 各自要么履约，要么拒绝；调用方可以逐项读取结果；若一个返回值只表示「作业已入队」，它就不会另外等后台写入完成。导入确认页需要明确定义用哪个响应或状态确认成功；在确认信号缺失时把行保留为待核对。带截止时间的界面可以结束等待并给出后续查询入口，但截止时间不能代替这项业务证据。

验收时除了正常成功，还应让一项先报错，另一项在测试主动发信号前保持等待，最后再观察后者能否被确认。让模拟接口为失败、完成、未知分别返回不同结果，断言页面按原始行号显示状态，并检查重试集合是否遗漏没运行的行或包含已经确认成功的行。空输入也值得单测：产品可以定义为无任务可做，别把没有失败自动解释成完成了导入。测试通过的条件应写成事件或结果，避免用固定时间猜测异步链何时结束。

为什么外层的 try/catch 没抓到失败？

把 try/catch 放在 forEach 外面，可以接住遍历过程直接抛出的异常；它接不到某个回调返回的拒绝。要让同一个 catch 接收拒绝，在对应的 try 块内等待该 Promise；如果把拒绝处理交给任务本身，结果也要明确地报告给批次。一个只调用任务却不返回它的封装，同样会让上层丢掉这条路径。排查时从设置「导入完成」的那一行倒着追：当时等待的是哪个值，那份值覆盖了哪几项，哪一层将保存操作的 Promise 丢掉了？找到第一个断点，比在每层再加一遍 async 更能解释为什么成功提示抢跑。
