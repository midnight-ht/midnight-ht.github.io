分支推送成功，发布标签为什么还没到远程？

用临时接收仓库对照三次推送，解释如何选择标签并核对发布回执。

正文

核心要点

  • 分支与标签分别选择。
  • 自动跟随按标签类型及提交可达性筛选。
  • 远程标签解析到的提交须匹配发布记录。

发布流程要分别核对远程分支和远程标签。分支更新只会更新这次选中的引用。即使远程已经有版本对应的提交，发布任务按标签名查找时仍可能查不到。如果流水线以指定版本为输入，让推送显式选择这个标签，再核对远程标签最终指向的提交。

同一个提交，可以有两个独立的名字

假设候选版本对应主分支顶端，工程师在本地创建附注标签，然后推送主分支。提交本身从分支到达远程，但分支引用和标签引用各自有名字。查看远程提交记录能回答这个提交是否出现在分支上。它不能回答下游能否通过版本标签找到同一个提交。这两个问题可以在远程仓库里独立验证。

Git push 手册把推送的源和目的写成引用映射。分支推送选择分支引用。若配置启用了自动跟随标签，范围可以扩大，所以排查时也要看实际参数和配置。显式写出源标签与目标标签，能够让发布记录说清用户授权的是哪个版本名。在同一个仓库存在同名分支和标签时，完整引用还避免了短名解析的歧义。

把三次推送放在同一个接收仓库里比较

下面用一个临时裸仓库模拟接收方。裸仓库没有要检出的工作区，这里只关心它的引用。工作仓库建立一个空提交，在同一提交上放两个标签。附注标签叫 release-a，轻量标签叫 local-marker。每轮都向同一个目录推送，随后读取这个接收方的标签列表。前四项检查分支指向与标签范围，最后一项再核对附注标签解析后的提交。

set -eu
tmp=$(mktemp -d)
trap 'rm -rf "$tmp"' EXIT
export GIT_CONFIG_NOSYSTEM=1 GIT_CONFIG_GLOBAL=/dev/null
git init -q --bare "$tmp/receiver.git"
git init -q -b main "$tmp/work"
cd "$tmp/work"
git -c user.name=Fixture -c user.email=fixture@example.invalid \
  -c commit.gpgsign=false commit -q --allow-empty -m base
git -c user.name=Fixture -c user.email=fixture@example.invalid \
  -c tag.gpgSign=false tag -a release-a -m 'release candidate'
git -c tag.gpgSign=false tag local-marker
git -c push.followTags=false push -q "$tmp/receiver.git" main
test "$(git ls-remote "$tmp/receiver.git" refs/heads/main | cut -f1)" \
  = "$(git rev-parse HEAD)"
test -z "$(git ls-remote --tags --refs "$tmp/receiver.git")"
git push -q --follow-tags "$tmp/receiver.git" main
actual=$(git ls-remote --tags --refs "$tmp/receiver.git" | cut -f2)
test "$actual" = refs/tags/release-a
git push -q "$tmp/receiver.git" refs/tags/local-marker:refs/tags/local-marker
actual=$(git ls-remote --tags --refs "$tmp/receiver.git" | cut -f2)
test "$(printf '%s\n' "$actual" | wc -l | tr -d ' ')" -eq 2
test "$(git ls-remote "$tmp/receiver.git" 'refs/tags/release-a^{}' | cut -f1)" \
  = "$(git rev-parse 'release-a^{commit}')"
printf '%s\n' 'All five assertions passed.'

五项断言在本机 Git 2.50.1（Apple Git-155）通过。第一次推送关闭了自动跟随，远程已经接到主分支，标签列表仍为空。第二次增加自动跟随后，接收方出现附注标签。轻量标签指向同一个提交，仍没出现在标签列表里。最后显式选择该轻量标签，才观察到远程有两个标签名。这个结果只覆盖两个标签都指向当前主分支提交的假设，没有执行第三方托管仓库上的标签保护和发布触发。

手册对自动跟随还有可达条件。它额外选择远程没有的附注标签，提交要能从本次推送的引用到达。假设团队在一条待合并的维护分支上打了附注标签，只推送不包含那段历史的主分支时，不能靠自动跟随带上这个标签。本例没有另建维护分支。要验证这个反例，可以在新接收方上运行相同流程，确认主分支确实到达，再查维护标签是否出现。这样能将没有选中标签与整次推送失败区分开。

先决定流水线拥有哪些版本名

如果发布审批针对一个明确版本，可以把目标标签名作为参数，并在执行前检查它解析到已经验收的提交。推送阶段只把这个标签纳入范围，也便于按发布人授权复核请求。应用把分支构建和发布构建放在同一个仓库也不影响这项判断。分支作业可以默认走主干，而负责交付安装包的作业应把批准的版本标签写入自己的输入。

如果一组附注标签由多个维护分支共同管理，自动跟随更方便，但要明确当前这次会推哪些引用，以及哪些候选提交不在这些引用的历史里。一次推送打算包含多个标签时，可以先列出预期名字及提交，再判断是否全部允许发布。全量标签选项会选择本地所有标签引用，适合确实要同步整个标签集合的工作。它可能顺带发布试验名，不能作为找不到单个标签时的默认补救。

已有同名标签的情况会改变处理方式。手册规定自动跟随只补远程缺少的符合条件的附注标签。检查发现同名指向不同提交时，先保留两边的指向供发布负责人核对，避免继续触发产物生成。旧标签可能已被下载地址、构建缓存或其他仓库引用。修复时应按照版本政策处理，已经发布的版本可考虑发布新的修正版本，并在变更记录里说明关联。这个决定不该由一次自动重试顺手做出。

远程标签应该进入可核对的发布回执

把「远程有标签」落实成两个断言。第一项确认期望名字存在，第二项用远程实际解析的提交和批准记录里的提交比较。保存命令目标及核验时间，留给下游查看当时查的是哪个仓库。解析结果匹配后，仍要记录构建输入和产物标识之间的对应关系。比如构建任务可以写出检出的提交，产物清单则记录生成的归档文件校验值。这样下游拿到归档以后才能把它与这次构建对应起来。

在系统测试中，可以故意让目标指向另一个已存在的提交，再看流程是否把这个状态当作发布条件失败。能找到同名标签这一条检查在这里仍会通过，只有第二项可以发现偏差。还可以验证接收方根本没有同名标签时，流程能给出缺失的版本名，而不是触发一个临时的分支构建来掩盖问题。产物到部署的验证可接着参看部署有效与回滚可用的检查方法。

为什么附注标签同名却有两行输出？

Git ls-remote 手册区分附注标签对象和它剥离后指向的对象。没有使用只列引用的选项时，输出可出现标签引用本身和带剥离标记的第二行。对指向提交的附注标签，第二行可用来与批准的提交标识比较。第一行有它自己的用途，比如核对签名对应的标签对象。两行记录属于不同层的证据。若允许发布标签指向非提交对象，还需要先确认对象类型符合这条发布流水线的输入约定。
