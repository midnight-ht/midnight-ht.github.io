分支推送成功，发布标签为什么还没到远程？

分支推送不证明标签已到远程；区分标签选择范围、可达条件和源码到产物的发布证据。

正文

分支推送成功，只能说明相应引用和对象按该次推送范围完成更新，不能证明期望的发布标签也已到远程。发布流程应显式选择需要的标签，并核对远程标签指向。不要因为提交对象已经上传，就假设远程存在同名标签引用。

标签引用需要进入推送范围

Git push 手册说明，--tags 会推送所有 refs/tags 下的引用；--follow-tags 则额外推送远程缺少、并且指向本次推送引用可达提交对象的附注标签。两者的范围不同，后者并不等于把所有本地标签一起上传。讨论命令时还应检查实际 Git 配置，因为配置也可能影响默认行为。

假设团队创建一个本地版本标签，随后只推送开发分支，看到成功信息便启动发布页面。远程发布工具可能找不到期望标签，或者读到不同版本。这里是未执行的解释示例，不是本项目已经发生的发布故障。排查应确认推送请求中到底包含哪些引用，而不只检查提交是否存在。

选择范围要与发布意图一致

如果目标只涉及一个明确版本，显式选择该标签通常更便于审查。若计划采用自动跟随附注标签，需要理解可达性与远程缺失条件；不能假设所有轻量标签、其他分支的标签或已有但不同的标签都会按期望处理。本文没有执行任何标签创建、推送或改写。

使用范围更大的选项前，应检查本地是否还有实验标签、内部标记或其他无意发布的引用。便利选项能够扩大交付范围，也可能把与本次发布无关的内容带出去。命令成功不等于范围选择正确，审查应发生在执行之前，而不是发布后再清理。

还要区分标签名与它最终指向的内容。版本名称符合格式，不说明它对应已验收的提交。附注标签包含标签对象，检查时应明确是在核对标签对象还是其指向的提交，避免把不同层级的标识直接比较后误报不一致。

发布回执保存远程证据

建议发布记录包含目标仓库、标签名、预期提交及远程实际解析结果，并关联构建产物。静态站点、安装包或镜像都可能有另一套产物标识；只有把源码和产物联系起来，才能回答用户实际得到哪个版本。标签存在也不能证明下游构建或部署已经成功。

验收可覆盖指定标签、自动跟随的附注标签、不满足条件的标签，以及不应上传的本地实验标记。执行前先写清预期范围，执行后核对远程引用与产物版本。这些是建议检查，本文没有运行命令，因此没有远程推送成功日志可展示。

若发现已发布标签指错，不宜立即改写。先判断消费者是否已经使用、仓库策略是否允许移动，以及后续版本怎样表达修正。移动引用可能让同一个名字在不同时间表示不同内容，影响审计与复现。具体处置应遵循项目发布政策，不能把强制推送当作默认修复。

推送标签与工作区文件管理是不同问题，相关 Git 状态边界可参看gitignore 与已跟踪文件。让每次发布明确选择引用、核对目标并保存产物证据，才能避免把“分支已推送”误报为“版本已交付”。
