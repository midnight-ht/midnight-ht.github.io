HTTP 204 成功后，为什么不该继续解析 JSON？

204 没有响应正文，仍可能包含有用元数据；解析、界面提示和重试应依据接口契约。

正文

HTTP 204 表示服务器成功处理请求，并且没有响应内容可供继续解析。客户端应按状态和接口约定走无正文分支，不要因为统一调用 JSON 解析失败，就把这次操作显示为失败。尤其在写操作之后，错误提示可能诱发用户再次提交。

无正文是成功契约的一部分

RFC 9110 第十五节规定，204 响应在头部结束处终止，不能包含内容或尾部字段；响应头中的元数据描述操作后目标资源及其选定表示。标准还举出 PUT 成功后通过 ETag 提供新表示标识的情况。因此，无正文不等于响应毫无信息，也不等于客户端可以忽略所有响应头。

假设设置页面保存成功后得到 204，通用请求封装却接着解析 JSON。解析错误进入统一失败处理，页面出现“保存失败”，但服务端可能已经完成更新。这是协议机制下的假设场景，本文没有运行该接口。修复重点是识别成功状态和内容契约，而不是给空正文补一段伪造的成功对象。

封装层不要替业务猜内容

设计请求函数时，可以把无正文结果与有内容结果显式区分，让调用者知道何时没有可读取的数据。具体类型或返回形式取决于项目，但应避免要求每个成功响应都具有同样的 JSON 字段。若业务必须获得更新后的对象，需要修改接口契约或另行查询，不能从 204 里推断出未发送的数据。

同样，不宜把所有空响应都当作正常结果。有些接口约定必须返回对象，实际缺失可能是服务端错误；状态、媒体类型、响应内容和业务约定需要一起判断。统一吞掉解析异常，会把真正的格式问题也隐藏起来。应该只在明确允许无内容的分支跳过读取，而不是遇到任何解析错误都宣布成功。

页面状态也要相应调整。保存成功可以清除待提交标记并保留用户当前视图，但是否重新获取最新值、如何处理并发编辑，需要业务另行定义。如果响应提供更新后的版本标识，应在后续编辑逻辑里正确传递；不能仅因页面还显示旧值，就要求用户重复执行写操作。

错误恢复先确认发生在哪一层

建议的验收场景包括：正常 204、按约定返回 JSON 的成功响应、服务器错误、正文格式不符，以及写入成功后客户端展示失败。检查提示信息能否区分请求未完成、解析不符合契约和业务已确认成功。以上是待执行的检查建议，不是已经通过的测试报告。

重试策略尤其需要谨慎。客户端看到异常，并不能单独证明写入没有发生。对可能产生外部副作用的操作，应结合接口幂等设计、请求身份和状态查询判断下一步。204 本身表达目标操作成功，但不替整个系统证明后续通知、结算或其他异步环节都已结束。

还应检查封装升级后的调用点：旧代码可能依赖一个实际上不存在的返回对象，日志也可能把空内容错误分类为异常。把这些假设显式改掉，才能让协议层修复传到用户界面。关于异步受理与最终结果的区别，可参看HTTP 202 的终态确认。
