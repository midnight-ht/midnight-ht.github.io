HTTP 204 成功后，为什么不该继续解析 JSON？

用本地 HTTP 服务对照 204 和两种 200 响应，区分保存成功、返回元数据与 JSON 解析异常。

正文

核心要点

  • 204 成功后返回明确的无内容结果。
  • 保留下一次操作需要的响应头。
  • 按接口承诺处理异常响应。

HTTP 204 已经表示目标操作成功，响应里没有内容可供 JSON 解析。收到 204 时，请求封装应返回一个明确的无内容结果，并保留业务需要的响应头。如果接口约定成功时返回 JSON，继续按该约定读取其他状态。这样，共用请求封装就不会把一次成功保存变成提示用户重试的错误。

状态码先说明是否应该读响应内容

在 RFC 9110 的 204 小节里，204 响应到头部结束处就结束，没有响应内容和尾部字段。没有内容并不意味着服务端没有返回信息。规范举了一个更新文档的例子。如果 PUT 成功拿到 204，而且带有 ETag，那么那个标签指向操作后的新表示。保存界面可以维持当前文档视图，给出成功反馈，并把返回的元数据应用到活动表示上。

设想设置页保存主题配色。浏览器收到成功状态以后，共用函数接着调用 JSON 解析。因为没有可供解析的数据，调用抛错，界面显示「保存失败」。此时，服务端完全可能已经接受了更新。用户看到错误后重复点击，产生的是第二次写请求。重复调用对设置值的影响和通知、审计等副作用是否重复，要看该接口的业务契约。解析错误本身无法回答这些问题。

同一个封装要区别三条响应路径

下面的示例只在回环地址启动临时服务。PUT 更新由计数器记录，返回 204 和一个假设的版本标签。两条读取路径分别返回有效的 JSON 和一个截断的对象。先对保存响应的副本调用 JSON 解析来观察旧行为，再交给修订后的解码器。解码器首先检查响应是否成功，然后处理这一份接口约定中允许的空结果，其余成功响应仍要求是 JSON。

import assert from 'node:assert/strict';
import { createServer } from 'node:http';
import { once } from 'node:events';

const host = '127.0.0.1';
let writes = 0;
const jsonHeaders = { 'Content-Type': 'application/json' };
const server = createServer((req, res) => {
  const saving = req.method === 'PUT' && req.url === '/settings';
  if (saving) writes++;
  const status = saving ? 204 : 200;
  const headers = saving ? { ETag: '"v2"' } : jsonHeaders;
  const content = saving ? undefined : req.url === '/broken' ? '{' : '{"theme":"dark"}';
  res.writeHead(status, headers);
  res.end(content);
});

server.listen(0, host);
await once(server, 'listening');
const base = 'http://' + host + ':' + server.address().port;

async function decode(response) {
  if (!response.ok) throw new Error('HTTP status: ' + response.status);
  if (response.status === 204) {
    return { kind: 'no-content', etag: response.headers.get('etag') };
  }
  return { kind: 'json', value: await response.json() };
}

try {
  const saved = await fetch(base + '/settings', { method: 'PUT' });
  await assert.rejects(saved.clone().json(), SyntaxError);
  assert.deepEqual(await decode(saved), { kind: 'no-content', etag: '"v2"' });
  assert.deepEqual(await decode(await fetch(base + '/settings')),
    { kind: 'json', value: { theme: 'dark' } });
  await assert.rejects(async () => decode(await fetch(base + '/broken')), SyntaxError);
  assert.equal(writes, 1);
  console.log('Five assertions passed');
} finally {
  server.close();
}

以上五条断言在 Node v24.21.0 本机通过。直接解析 204 抛出语法错误。按该状态分支处理可以读出版本标签。有效的读取响应得到设置对象，截断的读取响应仍报错。最后计数器保持为一，表明这段测试没有发出第二次保存请求。示例没有运行浏览器界面、网关或真实设置存储，也没有验证服务端的条件写入。

Fetch 标准关于无正文状态的定义将 204 列入其中。这里特意只给这个更新接口约定中的 204 写分支，因为同一个封装也许同时服务多种接口。它不应该用「读不到」概括每一种状态。比如专门查询资源的接口返回非成功状态，如果统一转成空值，调用端可能按没有记录来呈现，丢掉真正的错误。接口若还支持 HEAD，应该从请求方法和接口契约判断预期内容，不能只看这段解码器中的状态判断。

保存成功以后，哪些状态需要留下？

保存页面可以在拿到无内容成功结果时清除待保存标记。这个动作依据的是接口成功状态。服务器如果会规范化输入，页面仍想显示规范化后的值，那么另发读取或约定返回表示比从空响应猜字段可靠。要是服务端的处理本身尚未完成，就应按接口的状态契约设计完成判断。可参看 HTTP 202 的终态确认 中对异步受理和完成的区分。

保存与重新读取之间还可能夹进一次本地编辑。假设用户提交深色主题，保存请求还在路上时又选回浅色。收到第一份成功响应时，只能清除深色那次提交的等待状态，浅色草稿仍需保留。若后台重新读取到深色，也不能拿它覆盖用户尚未提交的浅色。验收时让第一次保存和后续读取的返回顺序受测试控制，在两次返回之间改变输入，然后检查已确认的服务端值与未提交草稿各自显示正确，还应检查保存按钮依旧能提交新草稿。这是建议的界面测试，本地 HTTP 示例未测这段交互。

对于允许并发编辑的接口，返回的 ETag 可以参与下一次写入，但需要先确认服务器约定：客户端会基于哪个表示编辑，写入时采用哪种条件，冲突后如何让用户处理旧版本。若接口明确把强标签用于 If-Match，客户端可保存这次返回的标签作为下一次请求的版本依据。标签既不包含文件正文，也不会自动解决两次编辑之间的冲突。接口没返回标签时，封装应暴露缺失状态，由调用者决定是否需要读取一次表示。

错误反馈应保留阶段差异。收到 HTTP 错误状态、还没有收到可靠响应时请求中断、以及已经收到成功状态但返回内容不符，意味着不同的恢复选择。第一类可以按接口说明显示拒绝原因。第二类需要考虑写入结果未知，必要时先查状态。第三类应在日志注明收到的状态和失败阶段，让维护者定位服务端契约或客户端解码。对于已经确认成功的 204，界面没有必要为了得到一个对象而重复提交。验收可用仓库里同样的计数器探测是否有二次请求，再另外测真实界面的按钮状态。这一部分界面验收没有在例子中执行。

200 也没有正文，可以当作 204 处理吗？

要看该端点承诺的响应形式。对于承诺每次 200 返回 JSON 设置对象的读取接口，空体属于契约异常，应该保留错误以便修复。若另一个端点明文允许 200 零长度内容，可以为它单独定义无内容分支，并让测试覆盖同状态下的空体和有效对象。判断不能只靠 JSON 解析是否报错，截断的对象也会报错。维护这种端点时，把读取、状态码和返回类型放进同一份接口测试，比全局吞掉解析错误更能保护调用者。
