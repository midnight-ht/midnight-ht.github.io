Docker 默认日志驱动已改，为什么旧容器仍用原配置？

用容器编号、实际日志配置和独立事件检查，区分 Docker 默认值已更新、实例已替换和日志链路可用。

正文

核心要点

  • 已有容器保留创建时的日志配置。
  • 对照原编号与替换后的实际配置。
  • 用独立事件核对采集和查询。

修改 Docker daemon 的默认日志驱动以后，老容器继续使用创建时的日志配置。重启同一个容器也不会重新选择驱动。迁移是否生效，先看运行实例自己的驱动和选项，再检查它写出的事件能否到达排障人员使用的查询入口。

假设一个导入服务有两个副本，运维在一台测试主机上把默认驱动改成 local，希望限制容器日志在本地的增长。daemon 应用新配置后，主机报告的新默认值已经正确，两个旧副本却还在使用原来的驱动。团队随后只替换了其中一个副本，主机便进入新旧配置并存的阶段。此时如果仍用主机默认值填写验收表，就会漏掉另一份仍在运行的旧配置。相反，如果只观察一个旧副本，也可能误判默认值变更本身失败。

用容器身份定位配置选择时点

Docker Engine 日志驱动配置说明，改变 daemon 默认驱动或选项，影响随后创建的容器。已有容器保留创建时的设置。如果创建时指定了驱动，选择还受实例的显式设置影响。把主机默认、创建声明和实际容器设置放在三列，可以看出谁决定了当前结果。文档还要求 daemon 配置里的日志选项值使用字符串。变更后何时需要重启 Docker，应按主机上的运行方式落实，避免误把应用容器的重启当成 daemon 已应用配置。

例如，部署清单显式要求旧驱动时，新建副本也能继续采用旧驱动。相反，若实例没有覆盖设置，使用新默认创建的副本应按新策略启动。两种情况下容器都可能拥有新的编号，因此看到实例换代只是中间证据。仍要读取实际日志配置，确认声明是否真正传入了创建过程。部署文件与命令行由不同角色维护时，把显式设置的来源写到验收记录里，可以避免临时命令通过而下一次常规发布恢复旧配置。

在隔离主机留三份证据

用不承载业务的测试环境模拟变更。下面是验证设计，本文没有执行 daemon 重启、容器创建或业务切换。设初始默认是 json-file，建立一个不显式指定驱动的测试实例 A，留存完整容器编号和日志配置。然后按该环境的运维流程把默认改为 local 并使 daemon 应用。用只读命令比较主机默认与容器配置，示例中的标识需要替换为实际测试值。

docker info --format '{{.LoggingDriver}}'
docker inspect --format '{{.Id}} {{.HostConfig.LogConfig.Type}} {{json .HostConfig.LogConfig.Config}}' demo-log-a

第一项预期是主机报告 local，而 A 仍报告 json-file。随后在测试环境重启 A，再读它的编号和驱动，预期两项都与重启前一致。用相同镜像新建一个不带覆盖项的实例 B，预期编号不同、驱动为 local。最后独立新建实例 C，在创建声明里显式指定 json-file，预期它虽然比 A 更新，却仍使用该驱动。这一行检查能否识别显式配置，不能用作生产环境的驱动推荐。

给每行保存编号、预期驱动、实际驱动和必要的选项。若没有看到主机默认值更新，先检查是否连到了正确的 daemon，以及该主机有没有应用变更。若默认已经变了而新建的实例仍不同，查创建声明和实际参数。只有编号保持不变的旧实例才可用来验证重启不切换配置，避免把编排系统顺手换掉的副本当成原实例。

把日志验收和流量切换分开

新驱动通过检查以后，让测试应用向标准输出或标准错误写出一条带合成编号的事件。分别观察事件在容器侧的可读入口、采集端和日常排障查询端是否出现。让新旧实例使用不同的事件标识，避免一个旧副本的日志让人误判新副本已经接通。若容器侧读到事件而采集端找不到，应核对采集器支持的读取路径。若采集端已经收到而查询仍为空，则查看时间范围、实例标签和索引条件。一次查询命中只验证这一条事件的去向。

假设变更编号为 L17，新实例写出的事件编号为 B9。验收时要求结果同时关联这次变更、实例 B 和事件 B9，并落在切换之后的时间窗里。只按服务名查到一条消息，可能读到旧副本积压后才送达的事件。可以先验证旧事件在同一查询中确实能被区分，再生成 B9 并追踪各站的接收时间。如果采集器仍在缓冲，保留容器侧已写出与采集端尚未收到两项记录。这样可以定位需要等待或排查的位置，也能在恢复时知道哪一段需要重测。

准备替换生产副本时，先找出需要保留的挂载、启动参数、依赖和恢复步骤。选一份可隔离流量的副本作为变更起点，核对新实例配置、事件和业务探测各自的预期，再考虑扩大范围。若新实例健康而日志查询不可用，暂停扩展，并按已有发布计划决定是否恢复原配置。恢复动作也需要确认对象身份和数据状态。若依赖旧容器的日志调查问题，先按照保留要求保存所需证据。关于进程失败与再次启动的区别，可参看容器退出与重启的边界。

驱动名字相同，只改轮转参数，也要重新创建吗？

要把新的创建选项应用到旧实例，仍需以目标选项重新创建。可以用两个都采用 local 的隔离实例做对照，让一个保留旧的文件上限，另一个显式设置新的上限。检查实际选项，并用无敏感内容的测试输出观察轮转。Docker 的 local 驱动选项说明列出单文件大小、文件数量和压缩设置。配置值验证与实际轮转观察应分别记录。这个补充用例也未执行。
