Docker 改了默认日志驱动，旧容器为什么没变？

日志默认值只影响新容器；核对实际实例配置，带数据和恢复计划安排重建并验证日志出口。

正文

Docker daemon 的默认日志配置改变后，已有容器不会自动采用新配置。应检查每个实际容器创建时使用的日志驱动和选项，再安排必要的重建。只看到默认值已更新，不足以证明当前运行实例的日志出口和轮转策略已经变化。

默认值主要影响新创建的实例

Docker Engine 的日志配置文档明确说明，修改默认日志驱动或选项，只影响配置变更后创建的容器；已有容器保留原创建配置，更新需要以期望选项重新创建。文档还提醒 daemon.json 中的日志选项应采用字符串值。具体部署方式仍应按运行环境核对，不宜把某个平台的重启步骤当成所有主机的操作手册。

假设团队希望控制日志增长，修改了 daemon 配置，看见默认驱动符合预期，就认为所有服务已经完成调整。旧容器可能仍沿用原设置。这个情境没有在本文执行，不能据此判断某台机器正在失控；它只说明配置文件、默认值和实例实际配置属于不同证据。

清点日志链路而不只看驱动名称

检查时应关联容器身份、服务版本、创建时间、实际驱动与选项，以及日志后续流向。驱动名称正确也不代表收集器已接收，收集器收到也不代表查询和保留政策正确。需要沿业务排错实际依赖的链路确认，而不是把某个局部状态作为最终验收。

如果不同服务有显式配置，daemon 默认值可能根本不是它们的来源。应保留配置优先关系和维护责任，避免后来重建时被另一个编排文件覆盖。审查报告最好能说明每个实例为何采用该设置，而不是仅附一份期望中的配置模板。

日志内容也应与结构变化一起检查。应用是否写向被收集的出口、敏感内容怎样处理、错误时是否能识别具体实例，都影响实际可用性。减少日志量不能以丢失关键诊断为代价，但也不能为了排错无限保留全部请求正文。

重建是发布动作，需要恢复计划

文档要求重新创建，不代表可以直接删除容器。重建前应确认持久化数据、服务依赖、启动参数和恢复方式，并考虑旧日志怎样保留或交接。本文没有执行删除、重启或重建命令，也没有验证某个业务可以无中断切换。

建议先在合适环境检查新实例的实际配置，产生一条可识别且不含秘密的诊断事件，沿收集与查询路径核对，再评估推广。对生产实例安排替换时，还需要确认流量切换与业务状态。事件能被查到只是日志链路证据，不能替代应用健康或任务完成检查。

失败时应能区分配置没有生效、日志没有产生、转发中断和查询条件错误。若没有这些区分，团队可能反复改默认设置，却一直没有触碰真正阻塞的环节。记录变更前后的实例与配置，比只记录执行了某个命令更有价值。

日志调整与恢复策略相邻但责任不同，可参看Docker 退出与重启边界。把期望配置落实到正在运行的容器，再验证实际日志路径，才算完成这次配置交付。
