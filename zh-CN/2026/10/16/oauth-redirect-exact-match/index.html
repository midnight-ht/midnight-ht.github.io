OAuth 回调在同一域名下，为什么仍要精确匹配？

同域名不等于同一接收端点。RFC 9700 要求精确匹配 OAuth 回调，并限定原生应用本地回环端口例外。

正文

核心要点

  • 授权服务器应把 redirect_uri 与该客户端的登记值精确比较，同 host 或路径前缀不能代替。
  • RFC 9700 保留原生应用本地回环地址的动态端口条件，并允许在请求来源和完整性已验证时有条件信任该请求。
  • 回调精确匹配仍要配合禁止开放重定向、token 端点值一致性和适用的代码保护机制。

OAuth 回调只在同一个域名下，并不能证明授权响应一定会交给正确的客户端页面。当前 OAuth 安全最佳实践 RFC 9700 要求授权服务器将收到的重定向 URI 与登记值做精确字符串匹配；原生应用本地回环地址的动态端口是一个很窄的例外。若授权服务只检查 host 或路径前缀，同域内的另一条路径就可能成为第二个接收点，甚至把响应继续转发到外部。

host 不是回调端点

把 OAuth 的 redirect_uri 想成“本站域名”，会把真正的安全判断压缩到错误的层次。URI 不只有 scheme 和 host，还包括端口、路径、query，应用对每一段的路由行为也不同。对于授权服务器来说，https://login.example.test/oauth/callback 和 https://login.example.test/redirect?next=... 虽然来自同一 origin，却不是同一个接收位置。后一条路径如果会读取 next 并返回外部 Location，它还是一个开放重定向器。

授权服务器在交付授权响应前，需要判断这个客户端究竟登记了哪些接收地址。2025 年 1 月发布的 RFC 9700《OAuth 2.0 Security Best Current Practice》在第 2.1 节要求对客户端预登记 URI 做精确字符串匹配；第 4.1.3 节把这作为应对重定向 URI 验证攻击的措施，并明确要求服务端不得暴露可以将浏览器转向任意 URI 的开放重定向器。规范原文 这里匹配的是客户端登记表里的地址，不是“看起来属于这个品牌”的域名，也不是用户登录后想去的站内页面。

一条通配规则怎样绕过“同域”判断

该规范的重定向验证示例，用一条具体的授权码/访问令牌泄漏路径解释宽松模式的代价。假设授权服务为客户端登记了类似 https://client.somesite.example/cb?* 的模式；客户端站点的 /cb 处理器又接受 redirect_to 参数，并对其值发出 HTTP 303 跳转。攻击者构造请求，让回调先命中该域名和路径，再把 redirect_to 指向攻击者控制的页面。授权服务认为 URI 命中了通配模式，于是返回授权响应；站内跳转器随后把浏览器送到外部地址。如果授权响应把访问令牌放在 URL fragment，而且下一条 Location 不带自己的 fragment，浏览器还可能把原 fragment 接续到新地址，攻击者页面便能读取它。

这不是“同域名总是危险”的结论，也不是本机执行过的攻击。它是 RFC 9700 对特定配置组合的规范分析：登记模式放宽、回调路径可继续跳转、响应类型允许令牌经浏览器 URL 传递，几件事合起来才形成这条泄漏路线。它说明为什么授权服务器不能把 host 相同当作安全证明，也说明精确匹配之外还要检查已登记端点自己的行为。一个完全精确登记的 /redirect 如果本身接受任意目的地址，仍然不是合格的 OAuth 回调。

RFC 6749 与 RFC 9700 的规则层次

RFC 6749 在 2012 年定义 OAuth 2.0 时，已经要求重定向 URI 是绝对 URI，并限制 fragment；如果登记的是完整 URI，授权服务器要按 RFC 3986 的简单字符串比较。它也写明：若无法要求登记完整 URI，服务器可以登记 scheme、authority 和 path，只让 query 部分动态变化。RFC 6749 第 3.1.2 节 这是协议早期兼容灵活配置的规则背景。

后续发布的安全最佳实践更新并扩展了 OAuth 安全建议。它把模式匹配描述为更复杂、也更容易在实现和管理中出错，并要求授权服务器使用精确匹配。RFC 3986 第 6.2.1 节把 simple string comparison 解释为字符逐个比较；这不是让每个服务自行用宽松正则去猜测 URI “看起来等价”。因此，注册值和授权请求应使用一致、可审查的序列化形式。不要在一个环境里把默认端口省略，另一个环境又附上端口，再靠授权服务的自定义归一化碰运气。若要接受多个合法地址，把多个完整地址逐项登记，比扩大成 host 通配或前缀规则更容易评审。

回调值也不应只在授权端核对一次。RFC 6749 第 4.1.3 节要求：若初始授权请求带了 redirect_uri，客户端兑换授权码时必须再次提供同一个值，授权服务器要确认二者一致。RFC 6749 第 4.1.3 节 因而服务端需要把授权请求中实际使用的回调关联到授权码或事务状态，不能在兑换时接受另一个“同域地址”。

端口例外只解决原生应用的本地监听

桌面原生应用常在用户设备上临时打开一个本地端口接收回调。RFC 8252 第 7.3 节描述了回环接口重定向，例子使用 127.0.0.1 或 [::1]，端口由操作系统临时分配；授权服务器必须允许这种回环 IP URI 在请求时使用相应端口。RFC 8252 第 7.3 节 RFC 9700 将可变端口写作原生应用 localhost URI 的特例，并交叉引用 RFC 8252。它不是网页应用的“任意端口可用”，更不表示 host、路径或协议 scheme 都可以改变。

这个区别影响注册设计。Web 客户端把生产和测试回调拆成精确登记值；桌面原生客户端则按其回环形式实现临时监听，并在协议明确允许的范围内容纳端口变化。RFC 8252 还要求应用只监听回环接口，并在收到响应后关闭端口；它指出某些操作系统上其他应用仍可能尝试拦截同一回环接口，因此端口例外不取代授权码保护。把 native app 例外复制给浏览器站点，属于应用类型错配。

如何测试拒绝路径

先为一个测试客户端登记一个完整回调，例如 https://login.example.test/oauth/callback，再针对授权端定义输入和预期结果。精确登记值应该继续成功；同 host 的 /oauth/callback/extra、长得相似的 /oauth/callback-evil、另一个 scheme、未登记端口，以及指向开放重定向处理器的地址，都应按策略拒绝。若产品确实有多个 callback，就把每一个完整地址登记为独立项，而不是用 startsWith() 或 *.example.test 代替授权清单。

实现层面的伪代码可以表达这种选择，但下面并没有连接任何真实授权服务器，也不是可直接使用的 SDK：

registered = registrations[client_id]
if request.redirect_uri is not an exact registered value:
    reject authorization request
else:
    continue the authorization flow

验收不能只观察“登录页面显示了错误”。还要确认拒绝时服务端没有把浏览器重定向到请求方提交的 URI；兑换码时再次验证同一 redirect_uri；并在应用的 callback 端点检查是否存在任意目标跳转。对 RFC 9700 所述的完整性保护授权请求，也要按该节的适用条件核验：如果授权服务器能验证授权请求的来源与完整性，例如使用带客户端认证的请求对象或 PAR，RFC 9700 允许在特定情况下信任 URI，而不是把这个例外扩展到所有客户端请求。

验证清单的结果应记录客户端 ID、登记配置版本、使用的授权请求、实际拒绝原因及是否产生外部跳转。不要把授权码、访问令牌或完整敏感 query 写进日志。一次错误响应只能证明那个输入在那个环境下被拒绝；它不证明其他身份提供商、客户端类型或配置分支也遵守相同规则。本文没有实际运行这些授权请求。

returnTo 能代替 redirect_uri 吗？

不能。redirect_uri 是 OAuth 授权响应送回客户端的协议接收地址；应用自己的 returnTo 通常是在登录完成后决定用户浏览器去哪一页。两者位于不同跳转阶段，应分别校验。把用户输入的 returnTo 拼进回调地址，不会让它自动成为已登记的 OAuth URI；把协议回调精确登记，也不会自动让应用内跳转安全。关于后一段导航的信任边界，可参看返回地址的信任判断。

精确匹配把授权服务器允许接收响应的位置限定在客户端登记集合里；开放重定向、代码保护、客户端类型和应用内导航仍各有自己的验证责任。需要动态回调时，先确认是否确有协议要求，再选择多个明确登记值、原生应用的本地端口规则，或 RFC 9700 明确给出的完整性保护条件，而不是把同一个域名当作通配授权。
