PostgreSQL RETURNING 返回行，就代表事务已提交吗？

RETURNING 描述一条修改语句返回的行；显式事务仍须等 COMMIT 成功，外部消息也另有交付边界。

正文

核心要点

  • RETURNING 提供当前修改语句的行结果；在显式事务里，这不等于整个事务已经提交。
  • PostgreSQL 自动提交模式下，单条语句成功完成时隐式事务才提交；驱动的事务配置仍须核对。
  • 要对外声明业务完成，应依据提交结果；邮件或消息交付还需要单独的可靠交付与去重设计。

不一定。RETURNING 让调用方读到当前 INSERT、UPDATE、DELETE 或 MERGE 修改的行；如果语句处在显式事务块中，返回行时事务仍可能开放，随后还能 ROLLBACK，也可能在 COMMIT 时失败。只有把语句结果、事务结果和外部交付结果分开，接口才不会把“数据库给了行”误报成“业务已经完成”。

RETURNING 回答的是哪一个问题

官方 PostgreSQL 19 RETURNING 章节说明，数据修改命令可以在修改时返回行数据，不必再发起一条查询来猜测哪些行改变了。INSERT 通常可返回新行，UPDATE 返回修改后的行，DELETE 返回被删除行；表达式可以像 SELECT 输出列表那样取列或计算值。若目标表有触发器，文档还说明可返回的是触发器修改后的行。因此它很适合拿数据库实际生成的主键、状态或计算字段。

但这份结果的范围是“这条修改语句所处理的行”。它本身不声明外围事务的最终命运，也不说明另一个系统是否收到了邮件、队列消息或 webhook。把结果集当作成功凭据，实质上是把三个不同问题混成一个：语句影响了什么、事务是否提交、事务之后的外部工作是否交付。

BEGIN;
UPDATE orders
   SET status = 'paid'
 WHERE id = 42
 RETURNING id, status;
-- 此处仍可能执行更多语句，也可能回滚
COMMIT;

这段 SQL 只用于解释边界，本文没有在 PostgreSQL 实例中执行。从事务视角看，返回行可供当前会话的后续代码读取；不过显式事务块仍要等到结束，整组更新才算已提交。事务教程把 BEGIN 到 COMMIT/ROLLBACK 描述为一个 all-or-nothing 单元：后续步骤失败时，先前修改也可能一起撤销。应用可以暂存行结果，却不能仅凭它就向调用方承诺“付款已完成”。

显式事务中，真正的边界是 COMMIT

BEGIN 开始事务块后，语句属于同一事务，直到显式 COMMIT 或 ROLLBACK。第一条更新有返回行，只能证明该语句产生了可供当前事务使用的结果；后面仍可能有库存扣减、审计记录或业务规则检查。任何一个步骤报错，都可能让整个事务进入 aborted 状态。PostgreSQL 19 事务教程指出，处于该状态时，除 COMMIT 和 ROLLBACK 外，其他命令都会被拒绝；而在 aborted 状态下发出的 COMMIT 与回滚效果相同，命令标签会是 ROLLBACK。

还有一种不那么显眼的路径：约束检查可能被延后。SET CONSTRAINTS 参考说明，处于 deferred 模式的约束会推迟到事务提交时检查。此时 DML 语句可以先返回行，最终 COMMIT 却因约束不满足而不能提交。语句结果显然不同于“事务最终可提交”的信号。数据库定义和当前事务设置决定是否存在 deferred 约束，不能由某个返回行推断。

因此，显式事务的应用流程应把 COMMIT 的结果纳入业务控制路径。只有事务结束操作成功，才把本地状态记为已提交。不要把一条 DML 的返回对象先传给 HTTP 层并立即发送成功响应，然后才在后台尝试提交；如果提交失败，客户端已收到的承诺就无法通过回滚撤回。需要提前准备响应内容时可以先构造候选响应，但发送时机应在提交确认之后。

自动提交时为什么看起来像是 RETURNING 就成功

没有显式 BEGIN 时，PostgreSQL 默认使用自动提交模式：每条语句在自己的隐式事务里运行，成功时在语句结束时提交，失败时回滚。这是 BEGIN 文档写明的模式。于是，单独执行一条 UPDATE ... RETURNING，如果客户端确认整条语句已成功完成，通常同时跨过了该语句的隐式提交边界。容易造成误解的是，开发者把“我收到返回行”当作规则，却忽略了完整语句是否结束、驱动是否开启了事务、框架是否把多条语句放进事务。

这不是说每个客户端库都具有完全相同的调用时序。事务教程特别提醒，有些客户端库会自动发出 BEGIN 和 COMMIT，调用方可能在未显式写这两个命令时仍处于事务块。连接池的 autocommit 设置、ORM 的 unit-of-work、框架中间件和批处理 API 都可能改变边界。判断时应查所用驱动/ORM的事务文档，并在测试中确认一条语句是否独立提交、显式事务何时结束、错误后连接的事务状态如何恢复。只读 SQL 字符串而不看调用层配置，不能证明实际执行模式。

业务响应与提交确认之间的完整流程

考虑一个创建订单的接口。请求进入后，服务生成订单行并用 INSERT ... RETURNING id, status 取得数据库分配的 id。业务还要写一条审计记录，并登记一个待发送的订单事件。一个可靠的数据库内流程是把订单、审计记录以及 outbox 事件写入放在同一个显式事务：订单语句返回 id 后，服务使用这个 id 写后续记录；所有步骤完成后请求提交；只有提交操作确认成功，HTTP 层才返回“订单已创建”。本文的流程是设计示例，不表示已运行某个服务或驱动。

如果审计写入失败，事务回滚，订单和 outbox 记录都不应被其他事务当成已提交数据看到。若服务在 COMMIT 时收到明确失败结果，就应按失败路径返回或记录错误；不能因为前面的 RETURNING 有值就跳过。若提交请求发出后网络连接断开，调用方可能只知道“没有收到确认”，未必知道服务器是否已完成提交。客户端观察到的超时并不总等价于数据库回滚，这是跨网络请求的状态不确定性。稳妥恢复方式不是盲目重放创建，而是用稳定的幂等键或业务请求 ID 查询结果，再决定是否补做。

outbox 解决的是另一段边界：数据库事务可以原子地保存业务变更和待交付事件，但不能把数据库提交与外部邮件系统的接收变成一个原子操作。提交成功后，后台投递器读取 outbox 并发送；发送失败可重试，接收端或投递层需要去重。若邮件已经发出而投递器在标记完成前崩溃，重试可能再次发送，因此事件 ID 和消费者幂等策略需要明确配置。可以继续阅读事务发件箱的交付边界；那种设计也不声称“消息恰好发送一次”会自然发生。

返回零行、多行或断线时分别意味着什么

若 UPDATE ... RETURNING 返回零行，首先说明没有符合语句条件并被返回的行。可能是订单 ID 不存在，也可能是状态条件不匹配或并发请求先改变了状态。它是不是业务失败，由接口契约决定。例如，条件写成 WHERE id = $1 AND status = 'pending' 时，零行可以用于区分“未处于待处理状态”；但若服务把它无条件转换成“数据库故障”，就会丢失可处理的业务语义。相反，若接口约定必须更新一行，服务也不能悄悄把零行当成功。

多行返回同样需要明确基数。批量更新中，返回了 37 行只说明这条语句修改并报告了 37 个行结果，并不自动说明后续的每个通知都已交付，也不说明外围事务提交成功。若业务期望仅一条，应用应检查基数，并决定多行代表冲突、批处理还是数据模型问题。通配列虽然方便，但 RETURNING * 会把不必要字段带进应用内存、日志或后续调用；稳定接口通常显式列出所需字段。

断线则更棘手。客户端只看到连接异常时，异常本身未必说明服务器已经执行到哪一步；它可能丢失在提交请求发出之前，也可能丢失在数据库已处理请求但确认未到达之后。若 COMMIT 已发出却确认丢失，应该把结果标成“待核实”，借助请求 ID 查询持久记录。此处是面向分布式调用的恢复建议，不是对所有网络故障和驱动实现的统一保证；具体驱动对连接断开、重试和事务状态的行为需要按版本验证。

如何验证系统真正遵守了这个边界

先确认代码路径而不是只看 SQL：记录 ORM 是否自动开事务、数据库连接是否启用 autocommit、HTTP 成功响应发生在提交之前还是之后、提交异常如何转换，以及是否存在延迟约束。再准备一组隔离测试：单语句自动提交并读取返回行；显式 BEGIN 后获得 RETURNING 行再 ROLLBACK；在事务中制造后续语句错误；对确实配置为 deferred 的约束验证提交失败；检查零行和多行路径；模拟提交期间连接断开后用同一幂等键查询。外部事件测试还要分别覆盖提交失败不发送、提交成功后暂时发送失败可重试，以及重复投递可去重。

以上是建议的验证矩阵，本次重写没有连接数据库、执行 SQL 或运行驱动级网络故障测试。它不能替代具体应用的集成测试。最小的验收断言应分别记录 statement_rows、transaction_outcome、external_delivery_state，而不是只留一个 success 布尔值：行数可为零或多；事务结果可为 committed、rolled_back、failed 或 unknown；外部交付可为 pending、delivered、retrying。字段命名可以不同，但三者语义不能混为一谈。

读者追问：单条 SQL 没写 BEGIN，拿到 RETURNING 行是不是就可以响应？ 若确认连接和框架处于 PostgreSQL 自动提交模式，且驱动已把该语句报告为成功完成，则单条语句的隐式事务也会在成功结束时提交；不过是否确实自动提交，要看调用栈配置。对显式事务则必须等待提交结果。即使数据库事务已确认，外部通知也仍需单独的交付状态。接口可以将“订单已持久化”和“通知已发送”作为不同事实返回或异步更新，避免用一个含混的“完成”掩盖边界。

对 RETURNING 最准确的用法是把它当作修改行的数据库结果，而不是万能成功信号。先查清语句属于哪条事务，再等到相应提交边界得到确认，最后单独核对外部工作。排查时若只能检查一个地方，优先查 HTTP 成功响应与 COMMIT 返回之间的先后关系；这个顺序能直接揭示接口是否把候选结果提前说成了已完成事实。
