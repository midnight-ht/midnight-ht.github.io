Playwright 重试通过后，第一次失败还要保留吗？

测试重试转绿不等于首次失败已修复。按 Playwright 的 worker、trace 保留模式与尝试编号，决定留下哪些证据。

正文

核心要点

  • 重试成功表示某次后续尝试通过；它不会抹去首轮失败，也不能单独证明缺陷已修复。
  • Playwright 重试会重建 worker 和浏览器，但不会自动回滚外部数据库、消息或共享账号状态。
  • 按问题选择 Trace 保留方式，并分别验证生成、清理、上传与报告展示；本文的配置建议未执行。

要保留。测试重试后转绿，只说明后一次尝试通过；第一次失败仍是一个真实测试结果。把它压成单一的“通过”，会丢掉失败发生在哪个环境、重试改变了什么，以及这条测试是否仍不稳定。发布判断至少应区分首次通过、重试后通过和耗尽重试仍失败，并让每一种结果都能追到对应尝试和产物。

重试并不是同一进程里再点一次运行

Playwright 的重试文档说明，某个测试失败后，Test Runner 会丢弃整个 worker 进程及其浏览器，随后启动新 worker；配置了重试时，新 worker 会先重跑失败测试。beforeAll 也会随新 worker 再运行。官方文档把第一次失败、之后重试通过的测试归为 flaky，而不是普通的 passed。

这改变了“重试通过”的含义。新的浏览器和 worker 可能清掉了浏览器进程内的状态，却不会自动回滚数据库记录、消息队列、第三方服务调用或共享测试账号。假设一个下单测试首轮等待订单状态超时，随后重试成功：第二次可能只是等到了较慢的服务，也可能是新 worker 重跑了初始化，还可能读到了第一次已经写入的订单。仅看最终绿勾，无法区分这些机制。

因此，第一次失败不能简单被称作“环境偶发”，重试成功也不能直接算作产品缺陷已修复。它们都是待解释的观测结果。原因可能在断言等待条件、共享状态、并发资源、产品响应、测试数据清理或外部依赖中。重试的作用是让测试流程继续，并给间歇故障一个再次出现或消失的机会；它不自动提供根因。

先给每次尝试一个稳定身份

排查要把测试身份和单次尝试分开。测试身份至少包括提交版本、项目或浏览器组合、文件与用例名；尝试身份还应包括 retry 编号、worker 编号、开始时间及本轮生成的附件。文档中的 testInfo.retry 可在测试和 hook 中读取重试编号，报告里的 TestResult.retry 也表示顺序编号；TestResult 还有 workerIndex、startTime、status 与 attachments 等字段。它们不是根因结论，但能避免把首轮与后续运行混成一条记录。

例如，报告可以保留“同一 commit、同一 Chromium 项目、该用例首轮 retry=0 在等待 order.status=paid 时超时，worker=2；retry=1 在新 worker=5 通过”的结构。具体字段需由实际 reporter 与现有报告链路确认。时间线比“偶发失败”更有用：维护者能看到是否跨 worker，失败和成功尝试是否对应同一测试输入，重建的 setup 是否改变了前提。

但 worker 重建并不等于环境隔离。若用例通过一个固定邮箱创建账号，第一次失败后账号留在共享数据库，第二次 beforeAll 再次创建可能撞上唯一约束；如果测试又捕获并忽略该错误，它甚至可能走到另一条状态路径。相反，重试时清理缓存或删除记录也会改变运行条件。清理可以是有意的恢复策略，但必须被报告为重试行为的一部分，不能再把第二次通过描述成“原条件下重复验证成功”。

Trace 模式决定你能比较哪些运行

保留截图、视频或 Trace 时，要按问题选择模式，而不是只因为“CI 上有重试”就认为首轮证据一定存在。Playwright TestOptions 的 trace 参考区分了几种容易混淆的设置：on-first-retry 只在第一次重试上录制 Trace；它通常给出重试的现场，不会自动保存第一次失败的 Trace。retain-on-failure 会为每次运行录制，但只留下失败运行的 Trace；如果第一次失败、第二次通过，首轮会留下，转绿的那轮通常不会留下。retain-on-failure-and-retries 会为每轮录制，并保留失败轮和重试轮，适合比较失败与后续成功，但会产生更多附件。

这些模式的取舍很具体：只想在重试现场快速看页面时，on-first-retry 可能够用；只要留下失败本身，retain-on-failure 较省空间；需要并排比较首轮失败和重试通过时，才考虑保留失败轮与重试轮的模式。v1.59 发布说明将 retain-on-failure-and-retries 列为新 Trace 模式，当前 TestOptions API 参考也列出了这些选项。使用更旧版本时应以锁定依赖版本对应的文档为准，不要把新文档中的配置直接复制到旧版。

示例配置如下，说明语法和证据选择，不代表本文已在某项目执行，也不保证适用于所有 Playwright 版本：

import { defineConfig } from '@playwright/test';

export default defineConfig({
  retries: process.env.CI ? 1 : 0,
  use: {
    trace: 'retain-on-failure-and-retries',
  },
});

“录制”和“保留”是两件事。某些模式会在每轮运行期间产生 Trace，之后再按最终结果决定删除哪些文件；若报告上传步骤只收集仍存在的 test-results 目录，或 CI 在测试进程结束前中断上传，文档配置正确也不保证附件进入可用报告。配置、生成、清理、上传、报告展示构成一条证据链，需要分别验证。

只看最终状态，会把不同故障折叠成一种

Playwright 在启用重试时会把测试结果分类为首次通过、重试后通过的 flaky、以及所有重试仍失败。若 CI 页面只展示最终状态并把 flaky 一律涂成绿，趋势面板会隐藏不稳定性。若相反，把每个重试失败都当成独立测试用例统计，又会把一次测试的多个尝试重复计入分母。团队应先确定统计单位：例如以用例在一次 CI run 中的最终分类为单位，同时另行保存每次尝试。这样重试次数和失败次数不会混为一谈。

还要检查自己的聚合逻辑是否保留 Playwright 已给出的 flaky 分类。官方 reporter 文档说明，报告可包含重试后通过的 flaky 测试；JSON reporter 也可输出完整测试运行结果。若自定义脚本只读取最后一个 result，或者 onlyFailures 一类过滤和上传规则配置不一致，就可能得到“测试框架知道它 flaky，仪表盘却显示全绿”的分歧。这里不是建议把某个比例设成通用发布阈值；支付、权限、数据迁移和普通展示用例的影响不同，门槛应由项目风险来定。

怎样调查一条首轮失败、重试通过的记录？

先确认报告中有两个 attempt，而不是一条被重写的最终记录：核对测试身份、commit、项目、retry 编号、worker、开始时间和各自的错误。再对照 Trace：首轮在哪个动作失败，页面、网络和断言看到什么；后一次在同一逻辑位置是否通过，或者是否因为 beforeAll、重试专用清理、数据残留而走了不同路径。Trace 解释的是浏览器侧时序与动作，不会自动证明服务端数据库状态或外部服务行为；必要时用同一 correlation/test identifier 对照受控的服务端日志，但不要把敏感数据写进长期构建产物。

随后把失败归为可验证的假设，而不是直接贴 flaky 标签结案。例如，若失败是“等待短暂固定时长后读取状态”，可以检查应用状态是否有明确的可观测条件，再决定使用基于条件的 web-first assertion；相关取舍见Playwright 断言等待的边界。若 Trace 显示两个 attempt 使用同一业务标识，则检查数据隔离和幂等清理。若失败跨多个测试同时出现，检查共享服务、worker 并发与资源限额。每个判断都应指出支持它的观测，也要写出尚未排除的解释。

最后做一次有边界的复核：修复后在相同项目和受控输入下重复运行，比较失败是否消失、报告是否继续保留各轮身份，以及附件是否能在 CI 结果中下载。这个验证计划需要真实执行才能形成结论；本次没有运行 Playwright 测试，也没有观察任何团队 CI。若系统没有保留首轮 Trace，不能事后从重试轮倒推出首轮浏览器状态。报告中应明确缺失证据，而不是补写一个听起来合理的原因。

需要保留多少轮，取决于问题和产物成本。对偶发故障只保留失败和重试轮，通常比每轮长期保留视频更节省；对难以重现、影响关键业务的路径，短期采集更完整的 trace 或服务端关联数据可能值得。附件可能含页面快照、请求数据和个人信息，保留期、访问权限、脱敏方式应跟 CI artifact 的实际设置一起检查。证据太少无法比较，证据无限期堆积也会扩大隐私与存储风险。

重试通过后，发布应该怎样处理？

将“最终通过”和“首轮稳定”作为不同事实进入发布判断。低风险用例可以允许流程继续，但仍应产生 flaky 记录、负责人和调查期限；关键授权、扣款或数据完整性路径是否阻断发布，应由风险策略决定，而不是由重试次数暗中决定。任何例外都应可追踪，并且在问题复现或修复后有退出条件。增加重试次数只能改变再次运行的机会与 CI 时间，不能提高对首轮失败原因的解释能力。

如果你现在只能看到最后一轮，先不要调大 retry。先在一个可控用例中核对 Trace 保留模式、报告中每个 attempt 的 retry/worker 身份，以及附件上传结果。确认这些证据能回答“第一次在哪里失败，第二次改变了什么”之后，再依据业务风险决定 flaky 是记录、人工复核还是阻断发布。没有保留下来的观测，就保持原因未知；这比把绿色结果写成修复完成更可靠。

读者追问：on-first-retry 会保存第一次失败吗？ 不会把它当作首轮失败 Trace 的替代品；该模式的录制对象是第一次重试。需要首轮失败本身时，核对 retain-on-failure；要对照失败与重试的完整轨迹，再评估 retain-on-failure-and-retries 的附件成本和隐私边界。
