多语言列表排序，为什么需要明确 Collator 的语言？

用德语和瑞典语的本地对照，明确语言协商、比较平局与可重复名单的边界。

正文

核心要点

  • 按读者目的明确排序语言。
  • 比较相等时保留独立记录身份。
  • 记录实际参数并定义平局顺序。

多语言列表需要按照读者的使用目的选择排序语言，并把实际采用的语言和选项记录下来。Intl.Collator 提供语言比较，但它返回相等只说明两段文字在当前比较规则下没有顺序差别。记录身份仍由业务字段确定，跨页顺序还需要稳定的平局规则和一致的数据来源。

明确语言，才能说明用户看到的顺序

MDN 的 Intl.Collator 文档展示了德语和瑞典语的差别。带变音符的字符在不同语言下可以处在不同位置。产品需要先决定名单跟随界面语言、名单本身的主要语言，还是由用户选择。没有这个决定，工程师只能说明自己机器上看到了什么，无法据此判断测试者报告的「顺序不对」。

ECMA-402 的字符串比较定义描述了比较结果与当前排序配置的关系。消费比较结果时，应判断负数、零或正数。业务如果只在返回值等于负一时认定排在前面，就给接口添加了不必要的数字假设。把比较函数直接传给排序操作，或仅查看符号，能让代码对应接口的顺序含义。

一个字符，两个排序位置和一组平局

下面的名单完全是假设数据。德语与瑞典语都使用基础比较强度，以便观察相同字符的相对顺序。两条记录的数字标识是本例的唯一有限整数，平局时按标识升序。代码复制数组再排序，保留调用者的输入次序。断言分别检查两种语言的顺序、德语下的平局，以及平局后的记录顺序。

import assert from 'node:assert/strict';
const collators = ['de', 'sv'].map(locale =>
  new Intl.Collator(locale, { sensitivity: 'base' })
);
const [german, swedish] = collators;
const [de, sv] = collators.map(value => value.compare);
assert(de('ä', 'z') < 0);
assert(sv('ä', 'z') > 0);
assert.equal(de('a', 'ä'), 0);
const rows = [
  { id: 20, name: 'ä' },
  { id: 10, name: 'a' }
];
const ordered = [...rows].sort((a, b) =>
  de(a.name, b.name) || a.id - b.id
);
assert.deepEqual(ordered.map(row => row.id), [10, 20]);
console.log(JSON.stringify({
  locales: collators.map(value => value.resolvedOptions()),
  icu: process.versions.icu, ids: ordered.map(row => row.id)
}, null, 2));

四条断言在本机 Node v24.21.0 通过。这里的德语比较将 ä 排在 z 前，瑞典语比较将它排在 z 后。德语下 a 与 ä 比较为零，但最终名单仍保留两个数字标识。输出还记录了运行时的 ICU 版本和两份实际参数。这只是本机这组样本的观察，尚未运行浏览器、数据库或用户自己的姓名数据。

resolvedOptions 的定义提供了检查实际设置的入口。请求的语言可能经过匹配或后备选择，因此测试记录既要写请求值，也要写实际值。遇到不一致时，先核对测试者的语言与选项是否相同，再看运行时提供的本地化数据。把「浏览器支持 Intl」当作所有语言排序都完全相同的证据，会跳过这里真正要检查的条件。

相等以后，还需要决定哪些事？

名单按读音或文字显示时，忽略某些字形差异可能符合使用习惯。账号合并、权限判断和数据库唯一约束却需要自己的身份规则。示例中两条记录即使名称比较相等，仍以不同标识参与最终输出。若把比较为零直接当作同一个人，就可能从一个展示功能引入记录丢失。产品评审可以把「文字近似候选」和「最终选中的记录」分别呈现，确认最终提交始终携带原记录身份。

平局规则同样要与任务一致。数字标识适用于示例里的确定性对照，真实记录未必有这种字段。有的名单需要按创建顺序处理，有的需要按组织层级再比较。同名记录完全相同的附加字段还会形成新的平局，所以可重复的输出最终需要一个在当前结果集内唯一、稳定的字段。规则一旦进入导出或排序链接，应能在后续重现时说明采用了什么方向。

这里还存在数据时间的问题。翻页期间若记录修改名称或新增数据，即使比较器和唯一标识规则都不变，结果也可能移动。界面排序测试只能覆盖当时的固定集合。跨页稳定需要接口定义游标、快照或其他读取政策，由负责分页的数据来源执行。游标需要能对应当次使用的排序政策，语言或平局字段调整后，接口可以拒绝旧游标并让用户从新列表开始。这个选择需要写入接口约定，再用旧游标样本验证，而不是只更新客户端比较器。客户端只拿到一页后再排序，会改变本页展示，却无法重新决定其他页的记录归属。

怎样验收一项排序政策变更？

先挑出能区分新旧政策的少量样本，而不是用大量普通 ASCII 名称证明两边一致。示例里的字符相对位置和平局正好分别覆盖两个决定。产品测试还应包含空名称、合法但少见的字符，以及多个同名记录，写清缺失名称如何处理。用假设数据可以减少无关个人资料的暴露，真实生产样本应按团队规则处理。

如果服务端负责页序，前端应通过接口返回顺序展示，导出也应取同一约定下的排序结果。不要期待数据库的某个排序规则天然等同于 JavaScript 的某组选项。需要一致时，将关键样本同时送到两边比对，并记录数据库、本地化库和客户端版本。本文没有执行这套跨环境测试。改排序可能影响历史导出的对照，因此变更说明应描述可见差别和适用记录，而不是只说升级了一个依赖。数组所有权的另一条检查可参看 排序与原地修改。

文件名里的数字，能直接按数字大小排序吗？

Collator 的 numeric 选项可用于数字式比较，但是否启用仍由名单目的决定。它适合让某些含数字的显示标签按读者预期排列，并不替代业务解析器。若数字片段是固定长度标识的一部分，产品可能希望保持字符顺序。验收时用第九项与第十项这类能区分政策的标签，连同前导零和非数字片段一起检查。数字式比较之后仍可能有平局，最终记录身份与附加顺序继续按上面的约定处理。
