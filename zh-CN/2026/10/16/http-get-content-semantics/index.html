GET 请求带了筛选正文，为什么服务链路未必理解？

用本地 Request 构造解释 GET 正文的客户端边界，再核对查询身份、缓存和兼容期输入。

正文

核心要点

  • 公开契约需要定义筛选条件的位置。
  • 请求构造通过后仍需验证真实入口。
  • 重复查询键需要明确单值或多值规则。

GET 请求内容没有通用定义的语义，源站接受这种写法也不能保证客户端和中间节点按同一套条件筛选。面向多种客户端的搜索接口，应在公开契约里定义筛选输入的位置和结果身份，先确认真实调用路径能表达这些条件，再决定使用查询参数还是有明确正文约定的操作。

浏览器使用的接口规则还多了一层

RFC 9110 的 GET 定义指出，消息内容不能改变 GET 的含义或目标。标准为直连且源站预先明确支持的情形留下条件，也提醒源站不要依赖私下约定，因为各参与者未必知道链路里还有哪些中间层。这并不是承诺某条链路一定丢弃正文，是否接受、怎样解析和怎样区分结果，需要回到具体实现验证。

应用还会受到客户端 API 的规则约束。Fetch 的 Request 构造步骤要求，在 GET 或 HEAD 方法下存在非空请求体时抛出类型错误。因此，后端直连脚本能发出某种请求，无法直接推出网页里的 Fetch 也能发送它。接入时要先区分请求有没有离开客户端。请求尚未发出时，源站日志里自然找不到对应记录，调整服务器 JSON 中间件也不能修复这条构造路径。

先在本地确认请求是怎样构造的

下面用两个不同部门的假设搜索条件比较请求身份。地址使用保留的无效域名，脚本只创建请求对象，不调用网络。第一处断言保留错误写法，后面给出一种接口约定允许查询参数时的构造方式。最后两项演示重复键读取，为迁移时的边界检查留下对照。

import assert from 'node:assert/strict';

const base = new URL('https://example.invalid/search');
assert.throws(() => new Request(base, {
  method: 'GET',
  body: JSON.stringify({ department: 'support' })
}), TypeError);

const makeQuery = department => {
  const url = new URL(base);
  const params = url.searchParams;
  params.set('department', department);
  params.set('state', 'open');
  return url;
};
const first = new Request(makeQuery('support'));
const second = new Request(makeQuery('sales'));
assert.equal(first.body, null);
assert.notEqual(first.url, second.url);
assert.equal(new URL(first.url).searchParams.get('department'), 'support');

const repeated = new URL('?tag=a&tag=b', base);
const query = repeated.searchParams;
assert.equal(query.get('tag'), 'a');
assert.deepEqual(query.getAll('tag'), ['a', 'b']);
console.log('Six assertions passed');

六条断言在 Node v24.21.0 的 Fetch 实现上通过。GET 带正文在构造时抛错，两份无正文请求拥有不同 URL。重复键的单值读取与全值读取也给出不同结果。它们证明的是当前运行时的构造行为和这几个值的读取，没有运行浏览器、代理、CDN 或生产搜索接口。网页接入仍需使用实际支持的浏览器验证报错位置以及最终发送的地址。

查询身份还要在缓存和权限层讲得通

RFC 9111 的缓存概述规定，缓存键至少由请求方法和目标 URI 组成，也允许缓存纳入其他材料。假设源站私下约定 GET 正文里的部门决定结果，而某个缓存只使用方法和 URI，那么两份部门条件不同的请求可能被它认作同一个键。这个例子说明要检查键包含什么，没有在本文演示任何厂商缓存失效，也没有证明某个上线配置确实会复用错误结果。

验收这样的接口，可以使用数据完全不同的两个测试部门，在实际入口提交搜索。先记录传到服务端的筛选值，再检查响应中属于各部门的记录。若有缓存层，用它提供的观察机制核对命中和键，而不是只根据响应速度猜测。还应测试同一筛选在不同用户下的权限范围，确认查到的资源归属符合服务端身份。把部门放进参数只是表达查询条件，服务端仍要根据用户身份确定哪些部门允许访问。

短且适合分享的公开条件适合放入可书签的目标地址。条件包含隐私值、结构很复杂或查询长度不适合现有入口时，可以设计正文定义明确的搜索操作，并约定返回结果、分页、错误和缓存策略。采用 POST 不自动决定是否保存结果，也不自动让操作满足应用所需的重试性质。这些应写进该接口自己的契约。团队若需要一个可反复读取的搜索结果资源，也可以先提交查询，返回资源标识，再通过约定的读取接口取结果。增加资源和过期管理的成本应进入评审。

兼容期的两个输入位置怎样退出？

假设旧客户端发送正文，新版改发参数。兼容层可以先识别调用版本，再选唯一的解析方式。允许两处同时传值时，应明确拒绝冲突还是规定优先级。比如参数指定支持部门而正文指定销售部门，两层各自取一个值会使日志与实际查询不一致。这个冲突属于请求校验问题，应在进入查询前给出可定位的失败信息，例如注明部门字段在参数和正文两处取到了不同值。日志保留字段名和输入位置即可定位这次拒绝，敏感值是否记录仍需按应用规则处理。

迁移测试应同时保留旧版、新版和冲突样本，经过真实入口运行，记录最终送进查询的数据结构。只确认新版返回 200，可能漏掉旧版仍在产生访问量。退出兼容前需要从已知客户端和入口日志判断旧路径使用情况，并由接口负责人决定何时移除。本文没有采集本站或其他项目的调用数据，也没有给出适用于所有服务的退出天数。对元数据和表示的另一个边界，可参看 HEAD 的元数据契约。

重复查询键是覆盖，还是多个筛选值？

这要由接口定义。示例中同一个 tag 出现两次，单值读取拿到第一项，全值读取保留两项。前端因此不能只凭字符串里出现了两次键，就假设服务器也按多值筛选。后端有的参数绑定方式会保留一个值，有的会形成列表。若业务允许多标签，定义它们表示同时满足还是任意满足，并用两个值各自匹配不同数据的样本验证。若只允许单值，重复输入可直接作为校验错误处理，避免调用端与日志工具各取不同值而掩盖含义。
