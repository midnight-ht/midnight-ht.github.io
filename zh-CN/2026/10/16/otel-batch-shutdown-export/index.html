Span 已结束，进程退出前还需要刷新导出吗？

有序退出通常等待 provider 关闭完成；分清主动刷新与关闭清理，也别把导出成功误当成后端持久化。

正文

核心要点

  • Span.End 只结束 Span，不代表它已导出。
  • 常规退出应核对所用 SDK 的 provider 关闭契约；规范要求处理器关闭包含 ForceFlush 的效果。
  • 刷新或关闭返回成功的证据边界取决于导出器和接收端，不能直接等同于后端可查询或永久保存。

通常不必在每个 Span 结束后立刻调用 ForceFlush。Span.End() 结束的是 Span 记录；批量处理器可能仍把它放在进程内队列里。对于一次有序退出，应核对语言 SDK 的 provider 关闭契约并等待它的成功、失败或超时结果。OpenTelemetry Trace SDK 于 2026 年 9 月发布的规范要求 SpanProcessor.Shutdown 包含 ForceFlush 的效果。单独刷新更适合平台可能在计划导出前暂停进程的特殊边界。即使调用成功，也不能据此断言后端已经索引，或数据会永久保留。

“结束”之后还有几段路

把一次 Span 交付拆开看，至少有五个状态：业务代码调用 End()；处理器收到结束事件；批量处理器把可导出的记录排入队列；导出器尝试发送；接收端接受后，后端再处理、索引并让查询读到。它们不是一个原子动作。第一步完成，不能证明第二步以后都完成；导出器返回成功，也只按该导出器与传输协议的含义解释。

同一版规范描述，OnEnd(Span) 在 Span.End() 调用中同步执行。这个同步回调并不等于网络导出也在 End() 返回前完成。批量处理器负责把多个已结束 Span 组成批次，通常等定时条件、队列达到批量阈值，或收到 ForceFlush 请求后导出。于是，一个短作业在最后一个 Span 刚结束时立刻退出，确实可能赶在计划导出之前；但如果后端没有显示这条 Trace，也可能是没有采样、上下文传播中断、队列已满、导出失败、接收端延迟或查询范围不对。缺失结果本身不能定位故障阶段。

规范还给出标准批处理参数的默认参考值：最大队列 2048、计划延迟 5000 毫秒、最大导出批量 512、导出超时 30000 毫秒。它们是规范里的可配置默认值，不是所有语言 SDK、所有版本和应用部署的实测配置。队列到达上限时处理器会丢弃 Span；若某种语言实现或环境改过参数，排查时应读取实际配置，而不是拿默认值解释现场。

有序退出时先核对关闭契约

该版规范规定，每个 TracerProvider 实例的关闭接口只应调用一次；provider 至少要调用内部处理器的关闭接口，并建议向调用方提供成功、失败或超时的结果。SpanProcessor 的关闭接口则必须包含 ForceFlush 的效果，且应在某个超时范围内完成或中止。基于这个通用契约，常规关闭的首选动作通常是调用 provider 的 Shutdown 并检查结果，而不是先对每个请求逐一刷新，再在退出时额外刷新一次。

这里的“通常”有边界：具体语言 SDK 会把规范映射成不同 API、异步模型和配置入口；处理器也可能是自定义实现。本文不能替某个未指定版本的 SDK 保证具体方法名、返回类型、并发行为或超时单位。应先查实际使用版本的官方 API，再确认 provider 的关闭会作用到哪些处理器。Shutdown 是生命周期终点；规范不允许处理器在关闭后继续收到新的 OnEnd 或 ForceFlush 调用。应用要先停止接收新工作、按业务策略结束在途操作，再关闭遥测，避免关闭与持续产生日志/Span 相互竞跑。

什么情况下才要单独调用 ForceFlush？

调用 provider ForceFlush 也有明确用途：例如某些 FaaS 平台可能在一次调用结束后、计划导出发生前暂停进程。此时函数仍需在挂起边界前尽量推进尚未导出的 Span。规范把它描述为提示，要求在给定超时时优先遵守时间限制，必要时可以跳过或中止部分导出。它不是“把数据永久写盘”的命令。批处理器进入关闭后再调用刷新也不是稳妥补救：关闭后再接收刷新本身可能违反生命周期契约。

一个带假设条件的退出时间线

下面的数字只用于解释状态，不是执行记录。假设任务采用规范默认的 5000 毫秒计划延迟和 512 条批量阈值；在某个假想时间点，队列只有 3 个已结束 Span，应用开始退出。由于阈值远未达到，不能假设它们已经形成一次定时导出。应用随后调用 provider Shutdown，处理器尝试在自己的关闭预算内完成队列与导出器工作。若导出器在预算内报告成功，应用可以记录“SDK 关闭调用成功”；能否说“服务端收到”还要看这个导出器成功的定义；能否说“后端已索引”则需要后端或查询端证据。

再假设宿主只给进程 2 秒终止宽限，而导出器配置的超时是 30 秒。30 秒是允许调用等待的上限，并不会把宿主的 2 秒变成 30 秒。强制终止可能早于 SDK 自己报告超时。正确的预算关系不是抄一个固定数字，而是把业务停止接入和收尾、provider 关闭、传输等待及宿主终止期限放进同一条时间线上，并为无法完成的情况留下可观察结果。这个例子没有实际运行，也不证明 3 个 Span 一定会丢失；它只展示时间预算互相冲突时的机制。

ForceFlush 成功与 Trace 可见之间的反例

考虑一个刷新调用返回成功，但目标查询暂时找不到 Span。这个结果不一定自相矛盾。对协议导出器而言，规范描述的成功通常表示数据已通过网络发送并交付到目标服务器；接收服务器后续的持久化、索引和查询可见不是同一个确认。另一个反例是 Span 没有进入采样结果：即便正常关闭，刷新也不会创造本来没有被记录的 Span。队列已满时的丢弃、导出失败或超时，则分别发生在其他阶段。遇到缺失数据，应把 Span.End、采样决定、队列/丢弃信息、导出结果、接收端确认和后端查询条件分开检查。

重复调用也有成本。若 provider 的关闭已经负责调用处理器关闭，而处理器关闭按规范包含刷新效果，那么“ForceFlush 成功后立刻 Shutdown”通常只是重复请求，并不能把接收端确认提升为长期保存证明。相反，在一次 FaaS 调用准备挂起但 provider 仍将继续存活的边界，显式刷新可能有用。选择动作时先问：这是正常进程结束，还是运行时即将暂停？使用的 provider 方法是否保证调用所有处理器？处理器或导出器是否有额外缓冲？返回状态代表哪一跳？这些答案比“每次 End 后都刷一次”更能决定是否需要 ForceFlush。

怎样验证自己的 SDK，而不伪造结论

先固定语言、SDK 与 exporter 的准确版本，阅读对应版本的官方配置文档，确认 provider Shutdown 是否关闭所有注册处理器、方法是否阻塞、超时参数用什么单位、关闭结果如何表达。再在隔离测试里使用可控 exporter：创建并结束一个 Span，分别观察正常关闭、导出器失败、等待超时和队列压力；为每种场景记录处理器是否收到结束事件、导出器是否被调用、返回结果以及进程是否在宿主期限前退出。不要只看后端 UI，也不要在测试日志中记录令牌、个人属性或业务敏感字段。

这些是建议的验证方案，本次没有执行它们，也没有测试任何特定语言 SDK。Go SDK 主分支的实现源码可以帮助理解一个实现如何处理队列、关闭和刷新，但主分支会变化，不能代替对生产依赖版本的核对。若业务要求是审计或账务级保存，应另选具有明确确认、重试、持久化和保留合同的记录机制；Trace 的导出状态应承担诊断证据的职责，而不是未经设计地代替业务账本。

如果你还在判断异常 Span 应写事件还是设置状态，可参阅异常事件与 Span 状态。关闭问题则从生命周期、导出器合同和宿主期限三处取证；只有它们实际确认到的边界，才应该写进“数据已送达”的结论。
