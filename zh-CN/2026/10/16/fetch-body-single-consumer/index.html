Fetch 的 bodyUsed 还是 false，为什么读不了正文？

用三个本地响应区分正文锁定、已读和克隆，并为业务解析与诊断指定明确的消费顺序。

正文

核心要点

  • 未读的正文仍可能被读取器锁定。
  • 释放未读取的锁可以恢复读取。
  • 在消费之前决定是否克隆。

读取器可能已经锁定正文，即使它还没有读取任何字节。此时 Fetch 的 bodyUsed 可以是 false，而 json 方法仍会拒绝读取。判断这个响应能否交给解析器，要沿调用路径找到持有读取器的代码，并确定是否已经开始读取或取消。

假设导入页面的请求封装要给下载显示进度，又把相同响应交给通用解析器。诊断模块先取得读取器，准备等界面订阅后再读。业务层收到成功状态，检查 bodyUsed 为 false，就开始解析。两处代码都还没有拿走内容，业务仍可能立即失败。这里要查的是谁已经取得流的读取权。单看业务解析附近有没有第二次调用，会漏掉更早的持锁点。

两个状态分别说明什么

Fetch Standard 的 Body 定义把持有锁或已经受到扰动的非空正文视为不可用于再次消费。已用标记 bodyUsed 反映流是否已经受到扰动。它不会把尚未读取的独占锁计作已用。可以同时看响应正文流的 locked 属性，提供排查线索；最终由负责交付正文的代码管理读取器及其生命周期。

Streams Standard 的锁定说明指出，一个可读流同时只能有一个活动读取器。获取读取器就锁定了流。释放没有读过的读取器后，后续读取方可以再向同一个流申请访问；一旦已经读取，释放锁不会还原取走的内容。在生产代码里，采集状态和真正调用解析之间还可能发生新的操作，所以不要把两个属性拼成并发控制。先定下来哪个模块会读，另一个模块接收必要结果。

用本地响应观察三种路径

以下程序只构造 Node 的本地 Response，不向网络发请求。两次独立的失败断言各有输入和恢复条件。先取锁而不读，确认 bodyUsed 为 false；再尝试业务解析，应得到类型错误。释放读取器后解析相同响应，得到计数二。第二个响应在释放前确实读一次。虽然锁已经解除，第二次解析仍应失败。最后在开始消费前克隆，让两个分支各完成一次读取，并验证已消费以后再克隆会抛错。

import assert from 'node:assert/strict';

const payload = '{"count":2}';
const fresh = () => new Response(payload);
const parse = response => response.json();
const stream = response => response.body;
const locked = fresh();
const reader = stream(locked).getReader();
assert.equal(locked.bodyUsed, false);
assert.equal(stream(locked).locked, true);
await assert.rejects(parse(locked), TypeError);
reader.releaseLock();
assert.deepEqual(await parse(locked), {count: 2});

const disturbed = fresh();
const consumer = stream(disturbed).getReader();
await consumer.read();
consumer.releaseLock();
assert.equal(stream(disturbed).locked, false);
assert.equal(disturbed.bodyUsed, true);
await assert.rejects(parse(disturbed), TypeError);

const original = fresh();
const copy = original.clone();
assert.equal(await copy.text(), payload);
assert.deepEqual(await parse(original), {count: 2});
assert.throws(() => original.clone(), TypeError);
console.log('locked, disturbed and clone assertions passed');

这段代码在 Node v24.21.0 本地执行，全部断言通过。第一个解析拒绝可以只用锁定来解释，响应中是相同且合法的 JSON，刚构造时也没有经过中间件。把相同内容分别交给三条路径，就排除了服务端响应格式差异。第二条路径同时断言 unlocked 和 bodyUsed，防止把失败归错给遗留锁。跨浏览器行为和网络流的取消链路没有在这个样本执行。

将这个实验移入请求封装测试，可以把业务结果、日志采集和正文解析错误放进不同断言。准备固定计数二的成功数据，打开诊断后依旧要取得计数二，再检查诊断只有任务编号和允许的摘要。把格式改成非法 JSON 时，调用方应得到解析错误；让诊断持锁但不读时，记录失败阶段和持锁责任。两个负例的返回都可能没有业务值，修复位置完全不同。格式和封装控制用例是建议，未在这个本地样本执行。

给封装里的同一次请求保留三个时间点：响应交给诊断模块时、读取器交还时、业务解析开始时。假设诊断只取得锁就异常退出，第二个时间点缺失，业务不能按解析错误处理。若诊断已经读完正文并正常交还，释放记录仍会存在，但第三个时间点显示正文已用。两次失败可以分别回看是谁取得锁以及谁读走内容。一个有代表性的修复是让职责清楚到函数参数里：进度模块要么收到专门负责读取的对象，要么只收到进度事件。验收用独立响应分别模拟这两个分支，再对比有无进度订阅时业务值是否一致。这是封装测试设计，未执行。

让诊断接收结果而非抢先读流

如果业务只要结构化字段，让请求边界完成一次解析，并给诊断发经过筛选的摘要。明确定义交付的数据和失败状态，读下游可以依赖的是业务对象，以及一个可关联到请求的诊断编号。不要为定位正文消费错误转而记录原始凭据、用户对象或整份导入记录。若确实要独立保存下载内容，先确定谁负责每个分支、数据生命周期和取消后的处理，再决定是否使用克隆。

失败恢复也取决于操作含义。从本地已消费的响应里重新读取，并不能重放网络请求。如果封装自动重新发送请求，可能触发一次新的业务操作。进度回调关闭后也可能留下持锁的读取器，释放与取消需要按读取方约定处理。在测试里把“网络请求成功”“正文解析成功”“业务验证通过”作为独立观察点，可以定位该恢复正文、重试请求还是报告数据错误。业务类型允许没有正文时，还要在消费之前处理协议状态。HTTP 204 的空响应契约

克隆后只读业务分支，诊断以后再读可以吗？

两个分支有独立的消费接口，但不等于慢分支没有资源成本。底层数据向两个分支分发时，一边继续读、另一边跟不上，未读数据可能在后者排队。短响应的本地实验只证明两个消费者都拿到对应值。对于大文件，应另测一方暂停、恢复及取消的行为，决定是否把诊断限于元数据，或在明确资源预算下使用两条读取路径。这里没有测量缓冲大小、网络背压或运行时的内存分配。这一判断依据 Streams Standard 的 tee 与背压规则。
