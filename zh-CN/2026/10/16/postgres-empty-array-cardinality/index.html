空数组的 array_length 为什么是 NULL？何时该用 cardinality

array_length 回答指定维度有多长，cardinality 回答总共有多少元素。理解空维度、缺失维度和 SQL NULL，才能避免过滤与业务状态被悄悄改写。

正文

核心要点

  • 空数组的指定维度长度由 array_length 返回 NULL；cardinality 对空数组返回 0。
  • 多维数组中 array_length 只统计一个维度，cardinality 统计所有维度的总元素数。
  • COALESCE 只有在业务明确要合并状态时才应把 NULL 映射为 0；未知输入和确认空集合常常不同。

空数组的指定维度长度是 NULL，而它的 cardinality 是 0；前者描述维度，后者回答总元素数。PostgreSQL 19 的 array_length 文档明确把空数组或不存在的维度列为返回 NULL 的情况，而 cardinality 返回数组所有维度的元素总数，空数组时为 0。若查询的问题是“有没有任何元素”，应优先考虑 cardinality；若要读取某一维的行数或列数，才用 array_length，并明确维度编号。

两个函数名相似，测量对象不同

把 array_length(arr, 1) 读成“数组里有几个东西”很容易，尤其在一维数组上它看起来和总元素数相同。但这个函数的第二个参数不是可选装饰，而是问题的一部分：它要求回答指定维度的长度。cardinality 没有维度参数，因为它把数组各维的元素数合并为一个总数。对一维非空数组，两个结果常常相同；这只是数据形状让两个口径暂时重合，不代表函数可以互换。

对空数组请求第一维时，PostgreSQL 文档规定 array_length 返回 NULL，而不是 0。cardinality 的问题则不同：总共有多少个元素？空数组的答案可以确定为 0。对于非空数组请求一个实际不存在的维度，array_length 同样返回 NULL；那表示该维没有可报告的长度，不表示整只数组为空。读者若只记住“空数组要 COALESCE”，就很容易把空集合和维度错误合成同一种状态。

PostgreSQL 19 文档的例子可概括为：array_length(ARRAY[10,20,30], 1) 得到 3，cardinality(ARRAY[10,20,30]) 也得到 3；但 array_length(ARRAY[]::integer[], 1) 得到 NULL，而 cardinality(ARRAY[]::integer[]) 得到 0。这里的行为以 PostgreSQL 19 官方文档为据。没有在本文环境运行这些 SQL；部署版本不同的项目应查看自己锁定版本对应的函数文档。

NULL 会改变 WHERE 的筛选结果

这个差异会从展示问题进入查询结果。假设功能开关数组 flags 中，空数组表示“已经确认没有启用任何开关”，而 SQL NULL 表示“数据还没有被计算”。开发者写 array_length(flags, 1) = 0 来筛选没有开关的记录，可能发现空数组没有被选中。原因不是筛选器漏读了零，而是左侧对空数组返回 NULL；普通比较遇到 NULL 得到的仍是 NULL，也就是 unknown，而非 true。WHERE 只保留条件为 true 的行，所以这一行不会进入结果。

如果问题确实是“数组是否没有任何元素”，cardinality(flags) = 0 对空数组返回 true。SQL NULL 输入仍然需要单独定义：当 flags 为 NULL 时，条件不是“确认空”，而是未知，因而不会被这条谓词选中。业务若希望把未计算也视作空集合，可以主动合并；若两者代表不同生命周期状态，就应让查询保持区别。关于 NULL 如何影响约束和数据域，也可参阅CHECK 与空值域。

使用 COALESCE 不会让这个选择自动正确。COALESCE(array_length(flags, 1), 0) = 0 会把 array_length 对空维度或不存在维度返回的 NULL 映射为 0。若 flags 本身可能是 SQL NULL，应在状态分支中显式用 flags IS NULL 处理，不要让默认值替产品定义“尚未计算”是否等于“确认没有元素”。在验证或状态统计里，未经定义就把不可计数映射为零，会把未知伪装成已确认的空集合。更清楚的做法是先处理状态，再计算数量，例如先识别 flags IS NULL，再用 cardinality(flags) = 0 识别已知空值。

二维数组说明为什么总数不是任一维长度

考虑一个两行三列的矩阵。第一维长度是 2，第二维长度是 3，总元素数是 6。array_length(matrix, 1) 和 array_length(matrix, 2) 分别回答行、列的长度；cardinality(matrix) 回答矩阵中一共有多少元素。这几个数字不会互相矛盾，它们只是单位不同。若页面要显示“2 行 × 3 列”，用两个维度长度；若想统计单元格数或判断整只矩阵是否没有元素，用 cardinality 更直接。

SELECT
  array_length(ARRAY[[11,12,13],[21,22,23]], 1) AS rows,
  array_length(ARRAY[[11,12,13],[21,22,23]], 2) AS columns,
  cardinality(ARRAY[[11,12,13],[21,22,23]]) AS total;

上面是解释文档语义的 SQL 片段，没有在本次任务中执行。另一个反例是对一维数组读取第二维：array_length(ARRAY[10,20,30], 2) 是 NULL，但 cardinality 仍是 3。把“缺少第二维”误认为“数组里没有值”，会让结构检查和数量统计混淆。要检查数据是不是有预期维数，应先看 array_ndims 或 array_dims，再验证各维长度；不要把某个维度长度的 NULL 改成零以后就宣布形状有效。

数组下标也不一定从 1 开始。PostgreSQL 文档展示了下界为 0 的数组，例如 [0:2]={1,2,3}，它有三个元素，但第一个下标是 0。读到 array_length 返回 3 时，它表示该维度跨度中的元素数，不表示最大下标是 3。若程序需要边界索引，应查看 array_lower 和 array_upper；若只要计数，使用维度长度或 cardinality。把上界直接当作数量，会在非默认下界的数据上出现偏差。

声明了维度，不等于运行时形状受约束

还有一个容易被忽略的失败路径：列声明成 integer[3][3] 并不会自动保证实际值永远是三行三列。PostgreSQL 19 数组文档说明，当前实现忽略声明中的数组尺寸，也不强制声明的维数；对于同一元素类型的数组，尺寸和维度数量不会因此形成不同的数据类型。这样的声明可以作为人的说明，却不是完整的运行时形状校验。

假设一个接口约定矩阵必须为 3×3，但历史记录里混有一维数组、2×3 数组和空数组。查询如果只用 array_length(matrix, 1) = 3，最多证明第一维长度是 3；它不能证明第二维也为 3，更不能单凭 NULL 结果判断数据是已知空矩阵还是值尚未生成。校验应针对实际契约：是否允许 NULL、是否允许空值、维数必须是多少、各维度长度是否固定。把这些状态拆开后再决定约束、写入验证或拒绝策略。本文不提供未经验证的生产 CHECK 表达式，因为 SQL NULL 在约束中的处理边界需要与应用的空值语义一并确认。

一个可复核的业务口径例子

假设一张任务表以 integer[] 保存已确认选择的规则编号。产品规定：NULL 代表尚未完成选择计算；空数组代表计算已经完成，但用户没有选任何规则；非空数组才表示具体选择。报表现在要统计“确认没有选择”的任务数。用 array_length(rules, 1) = 0 会漏掉空数组，因为结果是 NULL。另一个错误写法是把 rules IS NULL OR cardinality(rules) = 0 作为“已确认无选择”条件；它会主动把尚未计算的任务并入结果。若数组契约保证是一维并且问题只涉及总元素数，应以 rules IS NOT NULL AND cardinality(rules) = 0 表达已知空数组。这样把状态判断写在谓词里，不需要依赖默认值替产品合并状态。

这个结论依赖业务契约和谓词语义，不代表 PostgreSQL 能替业务推断“未计算”。如果不同系统在写入时把 NULL 统一改成空数组，数据库之后无法知道哪些行原本是未知；如果同一列还允许多维数组，cardinality 可以统计全部元素，但不会告诉调用方行列边界。遇到这些情况，要么修正数据契约和上游写入，要么分别保留计算状态及数组内容。一个返回整数的表达式不能替代状态模型。

用小样本验证自己的口径

在项目上线前，可设计一组隔离样本：SQL NULL、空数组、一维单元素数组、一维多元素数组、二维 2×3 数组、下界不为 1 的数组，以及对一维数组查询第二维。对每个样本记录 array_length 的每个维度、cardinality、array_ndims、是否满足业务筛选，以及 API 最终输出的状态。这样能检验的不只是函数值，还包括数据库 WHERE、ORM 映射和前端展示有没有把 unknown 变成 empty。

这是一份待执行的验证方案，而不是本次跑出的结果。实施时还要确认连接到的 PostgreSQL 版本、驱动将 SQL NULL 映射成什么值、序列化是否把 NULL 变成缺失字段，以及空数组有没有被 ORM 默认值覆盖。若测试只在应用内存中创建 JavaScript 空数组，不会验证 PostgreSQL 的维度函数语义。相反，直接查数据库却不检查 API 响应，也无法发现映射层的状态折叠。

什么时候选哪个函数？

要回答“某个维度多长”，用 array_length(array, dimension)，并把维度不存在或空数组时可能得到 NULL 的情况纳入逻辑；要回答“总元素数是多少”，用 cardinality(array)，它对空数组给出零；要回答“输入是不是数据库 NULL”，用 IS NULL 单独表达；要检查维度边界和形状，查看 array_ndims、array_dims、array_lower、array_upper，再根据契约校验。只有在产品明确规定未知也按零计数时，才在那个具体边界使用 COALESCE 合并。

读者追问：能不能始终写 COALESCE(array_length(a, 1), 0)？ 可以，但它表达的已不是“第一维的长度”，而是“第一维长度无法报告时按零计”。如果下游把零当成已确认没有选择，就会抹掉空数组和缺失维度的差异；若 a 本身允许 SQL NULL，还应先明确该输入的业务状态并单独处理。先定义需要保留的状态，再决定是否合并；不要用函数返回值替代业务含义。
