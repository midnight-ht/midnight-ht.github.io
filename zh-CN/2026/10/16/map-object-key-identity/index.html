Map 里存过对象，换一个相同对象为什么找不到？

用本机核对的十项结果区分对象引用、业务编号与 undefined 成员状态，并明确跨刷新选择的范围和失效规则。

正文

核心要点

  • 对象重建不保留引用身份。
  • 业务键需要明确租户与编号类型。
  • 用 has 区分未登记和已存 undefined。

Map 的对象键识别同一个实例；重新创建字段相同的对象，仍然会查不到原条目。排查时先用原引用验证条目是否存在，再决定这份映射要识别页面里的某个实例，还是跨刷新识别同一条业务记录。两种需求需要不同的键，不能只改一次 get 调用就当作缓存设计已经完成。

相同字段没有重新创建同一个键

MDN 的 Map 键相等说明把对象键的相等归于对象身份。对业务来说都是用户七号，对语言来说可能是两个不同对象。接口响应、对象展开、列表重新映射都可以创建新的实例；字段值一致，并不会让这些创建过程共享一个引用。

下面用虚构的页面选择状态演示。容器以第一次收到的对象为键，随后页面复制了对象，并修改原对象的名字。代码把十项观察放在同一份记录里，一次比较预期；前三项检验原引用能找到、复制品找不到、原对象修改字段后依旧能找到，后面的范围与成员结果在下文解释。这里没有调用服务器，也没有套入任何前端框架。

const assert = require('node:assert/strict');
const original = { tenant: 'north', id: '7', name: 'Lin' };
const copied = Object.assign({}, original);
const byObject = new Map([[original, 'selected']]);
const originalPresent = byObject.has(original);
original.name = 'Chen';
const byTenant = new Map([
  ['north', new Map([['7', 'selected']])],
  ['south', new Map([['7', 'idle']])],
]);
const { tenant, id } = copied;
const pending = new Map([[original, undefined]]);
const observations = {
  originalPresent,
  copiedInstance: byObject.has(copied),
  renamedInstance: byObject.get(original),
  refreshedRecord: byTenant.get(tenant).get(id),
  otherTenant: byTenant.get('south').get('7'),
  numericId: byTenant.get('north').has(7),
  registeredValue: pending.get(original),
  registeredPresent: pending.has(original),
  absentValue: pending.get(copied),
  absentPresent: pending.has(copied),
};
assert.deepEqual(observations, {
  originalPresent: true, copiedInstance: false, renamedInstance: 'selected',
  refreshedRecord: 'selected', otherTenant: 'idle', numericId: false,
  registeredValue: undefined, registeredPresent: true,
  absentValue: undefined, absentPresent: false,
});

名字改变后的命中，是区分两类故障的关键：条目还在，不代表条目里的计算结果仍然适用。假如保存的是由名字计算出的展示标签，原对象改名以后，容器不会主动重算标签。要处理的是值的刷新规则，而不是把查不到和结果过时混成同一种问题。

反过来，如果编辑器需要区分两份独立打开的节点，即便两份节点指向同一个数据库编号，引用键也可能正合适。把键统一换成编号，会让两个面板的临时选择互相干扰。先写明希望合并什么、隔离什么，再决定键；容器不会替产品补上这条规则。

跨刷新识别记录，先规定编号属于哪个范围

如果要求列表刷新以后还保留同一用户的选择，就需要一个不依赖实例重建的身份。以下方案采用租户与用户编号两层 Map，而非把任意对象整体序列化。假设租户与编号在这个接口里都明确为字符串，北区和南区各有一个七号用户，两条选择必须隔离。

复制后的对象仍带有同样的租户和字符串编号，因此可以查到北区的选择。南区同号用户得到另一份状态。numericId 为 false，说明数字七不等于字符串七；如果服务端变更编号类型，旧状态可能查不到。这不是 Map 在查询时随机转换类型，而是接口边界没有保持一致。

这里用两层映射是为了把范围写出来，不是说所有系统都要采用这份结构。若编号已经全局唯一，外层也许多余；若状态只允许在某次会话内复用，还需要把会话生命周期纳入存放位置或清理规则。示例直接调用内层 get，因为两个租户预先存在。实际输入可能来自未知租户时，应明确返回未找到还是按需求建立容器，不能照抄示例后把异常当作权限判断。

全对象字符串化也不是通用替代方案。名字是可变展示字段，是否应该影响身份，与对象的属性书写顺序无关。若两个对象代表同一条记录但只包含不同的字段子集，整体编码也可能得到不同结果。选择参与身份的字段，是业务协议的一部分，应写成可核对的规则，而不是寄希望于序列化函数发现业务含义。

查询修好了，刷新和失效仍要单独处理

回到一次列表更新：旧对象曾被选中，新响应重建了所有对象。若仍以旧引用保存选择，新对象查询失败符合既定规则；换用上述业务键后，选择可以在这次重建之间保留。但如果用户已经离开租户，旧状态是否应清空？如果记录被删除又重新创建，而编号被复用，原来的选择是否仍应继承？这些问题没有由 Map 自动给出答案。例如业务明确不允许继承删除前的选择，就可以在删除事件中清理条目；如果删除与重建事件可能漏接，应考虑把记录的世代标识纳入键，或让整份状态在重新拉取后重建。世代由数据协议提供，不能用当前时间随意代替。这是设计建议，示例没有实现事件接收。

可以把验收过程写成一组有明确预期的输入变化：仅改显示名字应保留选择；换租户必须隔离；删除记录后移除相关条目；重新进入会话按产品规则重新初始化。若存储的是权限计算而非界面选择，还要另行规定策略版本和重新确认时机。命中相同业务键，只能证明找到了保存的值，不能证明授权仍然有效。

排查日志应保存足以解释变化的身份信息，例如租户、编号类型、对象创建环节与会话标识，而不是倾倒完整用户对象。先复现哪一步创建了新实例，再看更新后的代码是否符合所选身份；单独看到一次命中，并不能说明跨租户和删除后的状态也正确。与复制对象的边界有关的背景，可参看结构化克隆与所有权转移。

get 返回 undefined，是否就说明对象键不存在？

不能这样判断，undefined 本身也可以是 Map 保存的值。ECMAScript 的 get 算法在未找到键时返回 undefined，而 has 算法回答成员是否存在。前面代码的最后四项结果中，registeredValue 与 absentValue 都是 undefined，而 registeredPresent 为 true、absentPresent 为 false；相同查询值具有不同成员状态。

如果业务允许“已经请求，但尚未写入结果”用 undefined 表示，只看 get 就可能误判为根本未登记，从而触发重复工作。是否存在与结果是否可用应分开表达；采用明确的状态对象通常也更方便解释。这个选择取决于业务状态模型，示例没有运行网络请求，也没有证明去重或并发控制已经实现。

本文一个断言比较的十项结果，已在本机 Node.js v24.21.0 通过。它们验证虚构数据上的语言行为，未测试框架更新策略、真实权限缓存或内存占用。实际接入时，应把上文的生命周期预期写入项目测试，再检查究竟应保留同一个实例、同一条记录，还是重新生成状态。
