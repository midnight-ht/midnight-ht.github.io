Harness Engineering 详解：AI Agent 可靠落地的工程外壳

一篇面向开发者的 Harness Engineering 深度拆解，解释它和 Prompt Engineering、Context Engineering、Agent Runtime 的区别，以及如何用约束、工具、反馈、验证和沙箱让 AI Agent 可靠落地。

很多人第一次听到 Harness Engineering，会以为它只是给 Agent 写一份更长的说明书。

这正是误解开始的地方。

在真实项目里，Agent 出问题通常不是因为提示词少写了一句，而是它缺少一个能工作的环境：不知道从哪里读上下文，不知道哪些文件不能碰，不知道怎么验证修改，不知道失败后如何恢复，也不知道什么时候该停下来等人确认。

Harness Engineering 要解决的不是“怎么把模型哄好”，而是“怎么给模型套上一套能执行、能约束、能反馈、能复盘的工程外壳”。

直接答案：Harness Engineering 是 Agent 的运行控制系统

可以先用一句话理解：

Harness Engineering 是围绕 AI Agent 构建环境、约束、工具、反馈、验证和审计机制的工程实践。

如果把 Agent 写成一个简化公式，大概是：

Agent = Model + Harness + Environment

模型负责理解、推理和生成动作。环境提供文件、命令、浏览器、数据库、日志、测试和外部系统。Harness 夹在中间，决定 Agent 能看见什么、能调用什么、怎么调用、做完后怎么验证、失败后怎么继续。

没有 Harness，Agent 很容易变成一个会写代码、会调用工具、但没有边界感的实习生。它看起来很努力，输出也很多，但你不知道它为什么改这个文件，也不知道它有没有把系统改坏。

这个概念为什么突然重要

2026 年 2 月，OpenAI 发布了 Harness engineering: leveraging Codex in an agent-first world。这篇文章里有一个很硬的案例：OpenAI 内部团队用 Codex 构建一个真实软件产品，约 5 个月内生成了接近百万行代码，过程中人类不直接手写代码，而是负责指定意图、设计环境、补反馈环和审查结果。

这个案例值得关注，不是因为“AI 写了很多代码”。代码量本身不稀奇，Agent 最擅长的就是制造大量文本。

真正有价值的是 OpenAI 把人的工作重新定义了：工程师不再只是在编辑器里写实现，而是在构建让 Agent 能稳定工作的系统。

到 2026 年 4 月，OpenAI 又在 Agents SDK 更新 里提出 model-native harness 和 native sandbox execution，让 Agent 可以在受控环境里读文件、跑命令、编辑代码、处理更长周期的任务。

这两件事连起来看，方向很清楚：Agent 工程化正在从“会不会调用工具”，走向“能不能被长期托管、观察、约束和恢复”。

Harness 不是 Prompt，也不是简单的工具封装

为了避免概念打架，可以把几个相近词拆开。

Prompt Engineering：写给模型的任务表达

Prompt Engineering 解决的是“怎么把需求说清楚”。它关注角色、目标、约束、输出格式、示例和反例。

它仍然重要，但它只覆盖 Agent 工作的一小段。

如果一个 Agent 要修改代码，单靠提示词很难保证它：

  • 只修改允许修改的模块。
  • 不绕过测试。
  • 不把临时调试代码留在仓库里。
  • 出错时能回滚到安全状态。
  • 在生成 PR 前完成自检。

这些不是提示词能长期兜住的问题。

Context Engineering：让模型拿到正确上下文

Context Engineering 解决的是“模型执行前应该读什么”。它包括 RAG、代码搜索、文档索引、记忆、会话历史、系统状态和权限信息。

上下文很关键，但上下文本身不等于执行控制。

一个 Agent 读到了完整架构文档，不代表它会遵守架构边界。它读到了安全规范，也不代表它不会调用危险工具。知识需要被转成可执行的约束，才会变成 Harness 的一部分。

Tool Calling：让模型能做事

Tool Calling 解决的是“模型可以调用哪些能力”。比如读文件、查数据库、跑测试、发消息、提交 PR。

但工具一旦接进来，风险也进来了。

如果没有 Harness，工具调用只是把模型的影响范围放大。Agent 原来只是说错话，现在可能会删错文件、改错配置、触发错误流程。

Harness Engineering：把 Prompt、Context、Tools 编进一个可控流程

Harness Engineering 的重点不是某一个提示词、某一个工具或某一段记忆，而是把这些东西组织成一个可运行系统：

任务入口
  -> 上下文发现
  -> 计划拆解
  -> 工具调用
  -> 中间验证
  -> 失败处理
  -> 结果审查
  -> 交付或回滚

它关心的是 Agent 怎么跑完一件事，而不是怎么答好一个问题。

一个 Agent Harness 应该包含什么

可以把 Harness 拆成八个组件。

1. 任务边界：先定义什么不做

很多 Agent 失败，是从任务入口就开始的。

用户说：“帮我优化一下项目。”

这个任务太大。Agent 可能改性能、改目录结构、改依赖、改 UI、改构建配置。每一项都像是在帮忙，但合在一起就会变成不可审查的改动。

Harness 需要把入口收窄：

  • 这次任务的目标是什么？
  • 不在范围内的内容是什么？
  • 可以读哪些目录？
  • 可以写哪些目录？
  • 能不能安装依赖？
  • 能不能访问网络？
  • 交付物是报告、补丁、PR，还是可运行页面？

好的 Harness 会让 Agent 在动手前先拿到边界，而不是靠它自己猜。

2. 仓库知识：给 Agent 一张地图，而不是一本厚手册

OpenAI 在 Harness Engineering 文章里提到一个经验：不要把所有规则塞进一个巨大的 AGENTS.md。大文件会挤占上下文，也容易过期。

更好的做法是让 AGENTS.md 变成入口地图，把详细知识放到可维护的文档结构里：

AGENTS.md
ARCHITECTURE.md
docs/
  design/
  product/
  reliability/
  security/
  runbooks/
  decisions/

AGENTS.md 告诉 Agent 去哪里找什么。架构边界写在架构文档里，安全要求写在安全文档里，运行手册写在 runbook 里，重要决策写在 ADR 或 decision log 里。

这里的关键不是文档多，而是文档能被 Agent 找到、引用、验证和更新。

如果团队的重要知识只存在于聊天记录和某个人脑子里，对 Agent 来说这些知识等于不存在。

3. 工具清单：工具越强，接口越要窄

Agent Harness 里的工具不应该只是函数集合。每个工具都应该有清楚的输入、输出、权限和失败语义。

以文件编辑工具为例，一个粗糙的接口可能是：

write_file(path, content)

它能写，但风险很大。Agent 可能覆盖整文件，丢掉用户刚改的内容，也可能把生成结果写到错误路径。

更适合 Agent 的接口通常会更窄：

read_file(path)
search(pattern, path)
apply_patch(patch)
run_tests(command, timeout)

apply_patch 比 write_file 更适合很多代码任务，因为它要求 Agent 明确说明修改位置和差异。工具设计得越像“可审查动作”，后续的日志、回滚和审查就越容易。

4. 执行环境：隔离是默认值，不是高级配置

Agent 一旦能跑命令，就必须考虑执行环境。

最小的隔离要求包括：

  • 独立工作目录。
  • 明确的文件读写权限。
  • 网络访问默认关闭或白名单。
  • 凭据不直接暴露给模型。
  • 每次任务有独立日志和产物。
  • 高风险命令需要拦截或确认。

OpenAI 2026 年 4 月的 Agents SDK 更新强调 native sandbox execution，就是因为长任务 Agent 需要一个受控的工作空间。Agent 可以在里面读文件、跑命令、编辑代码，但不能默认拿到宿主机的一切权限。

如果你在本地让 Agent 拿着完整 shell 权限、完整仓库权限、完整网络权限，然后还把生产密钥放在 .env 里，这不是高效，这是在赌运气。

5. 反馈回路：让 Agent 自己看到结果

人写代码时，会跑测试、看页面、查日志、读报错、再修改。Agent 也需要同样的反馈。

一个只会“写完就交付”的 Agent，很难用于真实工程。

Harness 应该把反馈变成标准流程：

  • 改代码后自动跑相关测试。
  • 前端改动后打开页面或截图检查。
  • 后端改动后查启动日志和接口返回。
  • 性能任务需要读指标。
  • 文档任务需要检查链接和格式。
  • 发布任务需要验证构建产物。

OpenAI 的案例里，他们让 Codex 能访问应用 UI、DOM 快照、截图、日志、metrics 和 traces。这个细节很重要。Agent 不是靠想象判断页面有没有坏，而是直接观察运行结果。

6. 验证门：把“建议做”变成“必须过”

提示词里写“请确保测试通过”没有太大约束力。真正有用的是验证门。

比如：

提交前必须满足：
- npm run lint 通过
- npm run test 通过
- npm run build 通过
- 没有新增 TypeScript any
- 没有修改 public API，除非更新文档
- 没有新增未使用依赖

这些规则最好能机械执行。能用脚本检查的，就不要只写在文档里。

Harness 的一个核心动作，就是把人类审查里重复出现的意见固化成检查。每固化一条，Agent 下次就少犯一次，人的注意力就少消耗一点。

7. 记忆与计划：让长任务不靠聊天上下文硬撑

长任务 Agent 最怕只靠会话上下文。

上下文会变长，会被压缩，会丢细节。一个跑 2 小时的任务，如果所有状态都塞在对话里，失败后很难恢复。

更稳的做法是把计划和状态外部化：

  • 当前目标写进计划文件。
  • 已完成步骤实时更新。
  • 关键决策写进 decision log。
  • 失败原因写进任务记录。
  • 可恢复检查点保存到工作区。

这样 Agent 断掉后，下一个 Agent 或人类可以接着看，不需要从聊天记录里考古。

8. 审计与复盘：每个动作都要能解释

生产环境里的 Agent 不能只交付结果，还要留下过程。

至少要能回答：

  • 它读了哪些文件？
  • 它调用了哪些工具？
  • 每次工具调用的参数是什么？
  • 哪些验证通过了？
  • 哪些验证失败后又被修复了？
  • 哪些动作经过了人工确认？
  • 最后为什么认为任务完成？

没有审计，Agent 成功时你不知道为什么成功，失败时也不知道从哪里修。

一个最小 Harness 可以怎么搭

如果你不是在做大型平台，而只是想让团队里的代码 Agent 更可靠，可以从一个很小的 Harness 开始。

第一步：写一个短的 AGENTS.md

不要写成长篇教材。先写这些：

# AGENTS.md

## 项目目标
说明这个仓库是做什么的。

## 常用命令
- 安装依赖
- 本地启动
- 测试
- 构建

## 目录地图
- src/ 业务代码
- tests/ 测试
- docs/ 文档

## 修改规则
- 不要直接修改生成文件
- 不要绕过测试
- 涉及公共接口必须更新文档

## 完成标准
- 相关测试通过
- 构建通过
- 输出变更摘要

它的作用是导航，不是替代所有文档。

第二步：把常用验证脚本固定下来

在 package.json、Makefile 或脚本目录里固定命令：

npm run lint
npm run test
npm run build

如果项目复杂，可以补一个统一入口：

npm run verify

Agent 不怕命令多，怕的是不知道哪条命令代表“这次改动已经过关”。

第三步：给危险动作加闸门

先列出 Agent 不能自动做的事：

  • 删除大量文件。
  • 改部署配置。
  • 改数据库迁移。
  • 访问生产凭据。
  • 安装不明依赖。
  • 推送代码或发布版本。

这些动作可以允许，但要人工确认。Harness 的目的不是让 Agent 什么都不能做，而是让风险动作可见。

第四步：把反馈写回仓库

如果你连续三次在 PR 里提醒 Agent “不要把业务逻辑写进组件”，就别继续提醒了。把它写成规则，最好写成检查。

可以从文档开始：

docs/architecture.md
docs/frontend.md
docs/testing.md
docs/security.md

等规则稳定后，再变成 lint、测试或脚本。

第五步：让 Agent 做自检报告

每次任务结束时，让 Agent 输出固定格式：

变更摘要：
验证结果：
未验证内容：
风险点：
后续建议：

注意，“未验证内容”很重要。一个可靠 Agent 应该能说明自己没有验证什么，而不是假装一切都稳。

Harness Engineering 和传统 DevOps 的关系

Harness Engineering 很像 Agent 时代的 DevOps，但它不是简单换名。

DevOps 关注人写的软件如何构建、测试、部署、监控。Harness Engineering 关注 Agent 如何理解任务、执行动作、接收反馈、修复错误、交付结果。

两者会重叠：

  • CI 是 Harness 的验证门。
  • 日志和 tracing 是 Harness 的观察能力。
  • 权限系统是 Harness 的安全边界。
  • 运行手册是 Harness 的可读知识。
  • 回滚机制是 Harness 的恢复能力。

区别在于，传统 DevOps 默认操作者是人。Harness Engineering 默认操作者可能是 Agent，所以所有隐含知识都要显式化，所有操作边界都要机器可读。

以前你可以说：“这个地方大家都知道不能乱改。”

在 Agent 工作流里，这句话没有意义。Agent 不知道“大家都知道”。

常见错误

错误一：把 Harness 当成超长系统提示词

超长提示词会变成新的垃圾桶。什么规则都往里塞，最后 Agent 抓不住重点，人也没人维护。

更好的方式是短入口、分层文档、可执行检查。

错误二：一开始就做多 Agent 协作

多 Agent 不是 Harness 的起点。

如果单 Agent 连任务边界、工具权限、测试反馈都没有，多 Agent 只会把混乱放大。先让一个 Agent 在一个窄任务里稳定工作，再谈分工。

错误三：只看产出速度，不看熵增

Agent 很擅长快速增加代码量。问题是，代码量不是资产，能维护的代码才是资产。

如果 Harness 没有架构规则、测试、文档更新和删除机制，Agent 生成越多，技术债越厚。短期像加速，长期像堵塞。

错误四：把人工审查完全拿掉

更合理的目标不是“人类不看”，而是“人类只看值得看的地方”。

Harness 应该把机械检查交给脚本和 Agent，把边界判断、产品取舍、安全风险留给人。

如何评估一个 Harness 是否有效

不要只问 Agent 能不能完成 demo。可以看这些指标：

  • 任务完成率：交付结果是否满足验收标准。
  • 一次通过率：无需人类指出基础问题的比例。
  • 验证覆盖率：多少任务跑过自动检查。
  • 回滚成本：失败后恢复需要多久。
  • 人工审查密度：每个 PR 需要多少条人工评论。
  • 重复问题率：同类问题是否反复出现。
  • 上下文命中率：Agent 是否能找到正确文档和入口。
  • 工具误用率：是否调用了错误工具或越权工具。

一个 Harness 变好，不一定表现为 Agent 更会说话。更常见的表现是：同类错误减少，任务恢复更容易，人的审查意见更少重复。

对开发者的实际建议

如果你今天想开始做 Harness Engineering，不需要先搭一个大平台。

先做四件事：

  1. 给仓库补一个短而准的 AGENTS.md。
  2. 把构建、测试、格式化、链接检查做成统一命令。
  3. 把危险动作列出来，默认需要确认。
  4. 把反复出现的审查意见写成文档或脚本。

等这些跑顺了，再考虑更复杂的东西：沙箱、任务队列、持久化状态、多 Agent、自动评审、运行时观测、成本控制。

Harness Engineering 最容易被讲成一个宏大的新岗位。其实它的第一步很朴素：让 Agent 在你的项目里少猜一点，多验证一点，失败时可恢复一点。

FAQ

Harness Engineering 和 Prompt Engineering 最大区别是什么？

Prompt Engineering 关注如何表达任务。Harness Engineering 关注任务如何被执行、验证、约束和复盘。前者主要发生在模型输入层，后者覆盖 Agent 的整个运行流程。

Harness Engineering 只适合代码 Agent 吗？

不是。客服 Agent、数据分析 Agent、内容生产 Agent、运维 Agent 都需要 Harness。只要 Agent 会调用工具、影响外部系统，就需要边界、反馈和审计。

小团队有必要做 Harness 吗？

有必要，但不需要做重。小团队可以从 AGENTS.md、统一验证命令、权限边界和任务自检报告开始。越早把规则固化，后面越少靠人肉提醒。

Harness 会不会限制 Agent 的创造力？

会限制不必要的随机性，但不应该限制局部实现自由。好的 Harness 管边界、接口、验证和风险，不规定每一行代码怎么写。

最小可用 Harness 的标志是什么？

Agent 能读到项目地图，能调用明确工具，能运行验证，能说明未验证内容，能在高风险动作前停下来。做到这些，已经比大多数“裸跑 Agent”可靠很多。

结尾

Harness Engineering 的本质，是把对人的工程管理经验，翻译成 Agent 能理解、能执行、能被检查的系统。

以前团队靠规范、评审、CI、文档和老同事的经验来控制软件质量。Agent 进入流程后，这些东西不能消失，反而要更清楚、更机械、更可观察。

真正的分界线不在模型参数，也不在提示词写得多漂亮。

分界线在于：你的 Agent 是不是跑在一个能约束它、帮助它、纠正它、记录它的 Harness 里。
