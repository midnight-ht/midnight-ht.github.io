Harness Engineering：把 Agent 能做什么、怎么验证和何时停下写进系统

从 OpenAI 的公开案例和 Agents SDK 文档出发，区分提示词、运行时、沙箱与审批，给出编码 Agent 的权限、验证、恢复设计及失效边界。

正文

核心要点

  • Harness 是任务、工具、权限、检查与恢复的组合，不是更长的提示词或统一产品标准。
  • 沙箱限制执行面，审批表达授权，自动校验检查规则；三者不能互相替代。
  • 用独立测试、变更范围检查、可恢复状态和副作用审计验收 Agent 工作。

当 Agent 能改仓库并运行命令时，可靠性取决于边界、验证和恢复能否在执行链路中强制，而不只取决于提示词写得多详细。工程上可把任务入口、上下文、工具权限、执行环境、检查点、审批、日志和恢复的组合称为 Harness Engineering。它不是一份更长的提示词，也不是某一家 SDK 的正式标准名称。

这个定义需要保留边界。Prompt 说明任务如何表达，Context 说明模型执行前能读到什么，Agent runtime 管模型循环和工具调用，sandbox 限制命令能访问哪些文件或网络；审批策略决定哪些动作要停下等待授权。这里的 Harness 是把这些控制安排成可运行、可查证的路径这一工程抽象。具体产品如何拆分这些组件会不同，因此不能把某个厂商的功能列表当成所有 Agent 系统的标准架构。

OpenAI 的公开案例说明了什么，又没有说明什么

OpenAI 在2026年2月11日发布的《Harness engineering: leveraging Codex in an agent-first world》记录了一项内部产品实验。文章称，该团队在约五个月里构建并发布内部测试产品，代码、测试、CI、文档、可观测性和内部工具由 Codex 生成；作者估计开发时间约为手工编写的十分之一，并称代码规模接近一百万行。这些数字来自 OpenAI 对自身项目的描述和估计，不是独立对照实验，也不能直接预测其他团队的交付速度。更可迁移的部分是他们描述的机制：仓库成为 Agent 可读取的知识来源，用目录地图引导渐进式发现，以结构测试和 lint 执行架构边界，并把文档维护和技术债清理放进持续流程。原文明确将结果限定在 OpenAI 自身的内部发布与采用情境。

2026年4月15日的 Agents SDK 更新则展示了产品层面的实现方向：官方介绍可在受控 workspace 中检查文件、运行命令、编辑代码，并提供 sandbox execution；文章示例注明需要 openai-agents>=0.14.0。这表示该次更新文章中的代码示例有相应版本要求，不代表当前所有 SDK 版本、所有 sandbox provider 或部署方式都共享完全相同的能力。更新说明把 harness 控制循环与运行计算环境的分离列为主题。当前 SDK 文档也把 Harness 描述为负责 Agent 循环、工具路由、handoff、审批、tracing、恢复及运行状态的控制面，把 Sandbox 描述为文件、命令、端口和快照等实际执行的计算面。Sandbox Agents 文档是产品指南，不是所有自建 Agent 的强制架构。

用一个代码修改任务拆出控制链

设想一名开发者要求 Agent 修复一个表单校验问题。下面是用于解释设计的假设场景，并没有在真实代码库或 SDK 中执行。第一步不是让模型直接写代码，而是把任务变成可验收的合同：目标文件和允许触碰范围是什么，不能改哪些路径，什么行为算修复，必须运行哪些检查，遇到需求歧义或权限缺失时如何停下。若验收条件仍是“让它更好用”，再强的 sandbox 也只会把模糊目标安全地执行得更快。

第二步为 Agent 提供有层次的上下文。入口文档指向架构图、相关模块、格式规则和运行手册；Agent 再按任务读取必要资料。OpenAI 的案例强调把核心知识放进仓库，并用小而稳定的入口实现渐进式披露。实践中还应给文档版本、所有者和检查方式，否则“仓库是事实来源”会退化为把过时文档复制得更快。对高风险知识，可把关键约束写成机器检查：例如变更不得跨越模块依赖边界，新增接口必须声明数据形状。文档解释原因，lint 或结构测试提供阻断证据，两者不能相互替代。

第三步收窄工具和权限。读取文件、搜索、应用补丁、运行单元测试属于不同能力；能调用 shell 不意味着任何命令都应无条件获准。工具接口宜显式说明参数、返回值、超时和失败语义；对删除文件、发布、写生产数据、发外部消息等副作用单独设审批。SDK 文档中的 guardrail 可验证输入、输出或工具参数，人工审批可在敏感动作前暂停工作流；这两种控制分别回答“自动规则是否通过”和“这个动作是否得到授权”，不能混为一个绿色状态。官方审批指南将自动验证与人工审查作为不同手段。OpenAI 于2026年5月发布的 Codex 安全实践也将技术边界、高风险审批、网络策略和 Agent 原生遥测并列描述；这是该公司的部署经验，不是通用合规清单。

第四步定义执行边界和留痕。为任务提供隔离工作目录、最低限度的网络访问、短期凭据、资源和运行时间预算，并将原始请求、工具调用参数、退出状态、测试产物、拒绝原因和最终 diff 关联到一个稳定任务标识。若 Agent 需要跨轮暂停，必须明确哪些状态保留：会话对话、工作区文件、快照、审批结果和临时凭据不是同一类状态。OpenAI SDK 文档区分 manifest 对新 sandbox 起始内容的描述与运行中的 session 状态；重新连接时需要按实际 provider 的生命周期处理，而不能只保存聊天记录就声称能够恢复工作。

最后，用独立于模型自述的验证器检查结果。对上例，验收不应是“模型说测试通过”，而是由受控命令记录返回码和测试报告，检查 diff 是否仅涉及批准文件，运行回归用例并验证缺陷原输入现在得到预期结果。测试通过仍不能证明需求符合用户意图，所以还要比对接受条件；而生产发布这种副作用应有单独的批准和回滚策略。每个阶段都应产出能由另一过程检查的证据。

为什么只加沙箱仍会留下失败路径

沙箱能缩小影响面，却不能保证被允许执行的内容可信。OpenAI 在2026年11月18日的 Codex sandbox 工程说明举例指出：Agent 可能修改本机已安装的包，例如被 Git 忽略的 node_modules 目录；如果编辑器随后运行了这个包中的格式化程序，恶意代码可能在沙箱边界之外被触发。这个示例提醒团队检查被忽略目录、编辑器插件、依赖安装脚本和宿主进程，而不是只审查 Git diff。Codex sandbox 文章也明确指出沙箱只阻止一类风险，安全仍需纵深防御。

权限配置还有“看得到”与“可外传”的差异。若任务可以访问客户文件，又可访问宽泛的网络域名，模型即使没有直接文件写出权限，也可能通过允许的工具把读取结果发往外部系统。反过来，完全断网可能让依赖安装、文档查询或测试环境不可用，诱发绕过流程的临时授权。合理配置应先按任务列出输入、输出和必需目的地，再给最小通路，并记录每次授权；无法证明必要性的网络动作应保持关闭。

恢复也需要设计：命令超时不等于命令未执行，重试可能重复写入；部分补丁可能已经落盘，任务状态文件却未更新；测试进程可能在主 Agent 退出后仍运行。操作应使用可重入或可识别的任务标识，先读取当前文件和远端状态，再决定重试、回滚还是转人工。高价值工作区应保留不可变基线和阶段性快照；凭据则不应打包进快照或长期对话上下文。

依据影响范围选择控制强度

只生成代码建议的只读助手，通常可从只读仓库、检索和引用来源开始，不需要完整 sandbox 工作流。需要编辑文件和运行测试的任务，应增加隔离 workspace、路径白名单、时限、测试报告和 diff 检查。会接触客户数据、安装依赖、访问网络或调用有副作用工具的 Agent，还需要凭据隔离、出站策略、审批点和可审计日志。触及生产数据、付款、身份权限、删除或对外发布时，即使模型、测试与策略都给出“允许”，仍应把授权和回滚作为独立门槛。

控制是否有用要看可观测指标，而不是组件数量。可以分别统计越界尝试是否被拒绝、需要审批的操作是否暂停、测试失败是否阻止交付、恢复后是否重复执行副作用、人工接管是否能继续已有工作区、审计记录能否重建一次决策。不要把这些指标合成“Agent 成功率”：一项任务可以代码正确但来源不可追溯，也可以权限合规但没有满足用户目标。本站关于风险导向质量门的文章也讨论如何依据后果为不同变更设置不同验证门槛；这里进一步把门槛放进 Agent 的工具和执行生命周期。

这套机制不能替代模型评估、人工判断、供应链安全或产品验收。它能做的是把“不要这样做”“先验证再继续”“遇到副作用时停下”变成能被程序执行、被日志解释、被恢复流程引用的约束。公开案例展示了某团队如何组合这些机制；其他组织仍需按自身权限、数据、工具和业务影响做威胁建模，再用可重复的失败用例验证边界。
