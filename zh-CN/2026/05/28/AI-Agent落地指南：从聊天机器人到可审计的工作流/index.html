从聊天机器人到可审计 Agent：先定义任务，再开放工具

用一个明确标注为假设的客服订单流程，说明怎样判断任务是否需要 Agent、设置工具与人工边界，并用可复核的工作流证据验收。

正文

核心要点

  • 先判断任务是否含语境、例外或难维护规则；规则明确时普通自动化可能更合适。
  • 把订单处理拆成可核验状态、窄工具、幂等写入和独立审批；假设案例不是实测。
  • 用代表性任务集和端到端 trace 检查工具、授权、恢复与验收，不压成单一成功率。

把聊天机器人改造成能调用工具的 Agent，第一步不是添加更多工具，而是选定一个输入稳定、输出可验收、失败可交接的工作流。若任务大多能由明确规则完成，先用普通程序自动化；只有当步骤需要处理例外、理解非结构化材料或结合上下文判断时，才值得让模型参与决策。Agent 的“可审计”也不是日志越多越好，而是每次执行都能回答：目标是什么、依据来自哪里、调用了什么、状态如何变化、谁批准了副作用、失败后怎样接手。

先判断任务是否真的需要 Agent

“需要聊天界面”不等于“需要 Agent”。单轮问答、固定字段分类、模板化通知，通常可以由模型输出结构化结果，再交给确定性程序做校验和后续处理。OpenAI 2026 年 1 月 15 日发布的《A practical guide to building agents》把 Agent 描述为能够代表用户完成工作流的系统，并明确指出：如果应用只是接入语言模型，却没有让模型控制工作流，它仍可以只是聊天机器人或分类器。该指南建议优先评估三类任务：决策含有语境和例外、规则集合已经难以维护、或大量依赖非结构化材料。它也提醒，若这些条件无法清楚验证，确定性方案可能足够。官方指南是产品团队的建议，不是 Agent 项目成功率的独立研究。

把判断变成可检查的问题，会比先选框架更有用。第一，输入里是否有固定字段，还是必须从邮件、图片、对话或长文档提取条件？第二，决策是否能被规则完整表达，还是常出现需要结合多项事实的例外？第三，输出能否通过数据库状态、规则、测试或人员复核验证？第四，动作是否只读，还是会改订单、付款、权限或对外发送内容？第五，执行失败能否停止并交还给人，而不会留下难以逆转的部分状态？

一个候选流程若主要是“取两个已知字段、按确定条件更新状态”，Agent 带来的可能只是额外不确定性。反过来，若客服需要理解用户对订单的自然语言说明，核对订单记录与政策，再判断属于查询、退货还是例外申请，模型可负责把模糊描述归纳到有限的工作流分支。它仍不应直接决定所有后续动作：边界清楚的查询可以自动进行，写入、退款或承诺补偿则应有独立规则和授权。

把模糊请求拆成可验收的工作流

下面以“帮我处理这笔订单”为例。它只是用于设计讨论的假设场景，没有连接客服系统、运行 Agent 或测试任何 SDK。第一步先界定目标：Agent 可以查订单并整理处理建议；退款是否符合政策由确定性服务核验；退款提交前由有权限的员工确认。再划分状态，例如 needs_order_id、lookup_pending、eligible_for_return、needs_human_review、approved、completed 和 failed。这些状态让接手者知道工作停在哪里，也避免把“模型给出一段听起来合理的话”误当成交易已完成。

输入契约需要写清必填项、可接受的订单标识、身份校验来源、允许的数据类型，以及缺失或冲突时的处理。比如用户只说“上周那件东西”，系统不能猜订单编号后调用退款工具；它应该补问一个可核验标识，或转交人工。对政策文本的引用应保留文档版本与适用日期。若退货期限刚更新，Agent 不能只凭模型记忆沿用旧规则。

工具则按职责拆窄。lookup_order 只读订单概要；check_return_eligibility 接收订单 ID、当前身份与政策版本，返回结构化的允许/拒绝/需要核对结果；create_refund_request 创建待审核申请，而非直接退款；真正的退款动作只暴露给授权员工确认后的执行服务。每个工具都需要参数校验、身份和资源授权、超时语义、幂等键及可审计结果。读权限不应自动变成写权限，工具描述中的“请谨慎操作”也不能替代服务端鉴权。

OpenAI 的官方 Agent 指南建议按读取或写入、可逆性、所需权限和财务影响评估工具风险，并对敏感或不可逆动作保留人工监督。Agents SDK 的 Guardrails 与 Human Review 文档也把自动校验和人工批准分开：校验可以检查输入、输出或工具调用；审批则暂停运行，等待人批准或拒绝。暂停状态会以 interruption 和可恢复 state 返回，决定后继续同一运行，而不是伪装成另一个新请求。官方审批文档还提醒，Agent 级 guardrail 不会自动围住所有自定义工具，因此副作用检查应放在实际产生副作用的工具边界附近。

一个具体的失败路径

仍以退货请求为例：Agent 查询到订单符合条件，随后准备创建退款申请；在工具调用前，订单状态被客服后台改成“争议处理中”。如果系统只根据先前读取的结果继续，可能提交过期操作。解决方法不是在提示词里加一句“注意数据过期”，而是让写入端重新读取权威状态，或者要求版本号匹配；状态变化时返回可识别的冲突，让 Agent 停止并解释需要重新核对。

另一个常见边界是调用超时。客户端没有收到回复，不代表服务端没有创建申请。直接重试可能产生两条记录。写工具应携带稳定的请求幂等键，状态存储也应保留“待处理、已提交、已拒绝、结果未知”等状态；结果未知时先查询既有请求，而不是再发一遍。若系统无法证明请求是否完成，应交给人核对。失败恢复的依据是业务状态与操作标识，不是模型上下文里“我好像刚刚执行过”的文字。

这类流程最好把证据一起保存：原始用户目标、经确认的订单 ID、身份主体、政策版本、工具名和经过校验的参数、工具返回状态、审批人及时间、最终结果引用。日志不应无差别复制个人信息或完整支付凭据；可审计意味着能重建决策所需的最少证据，同时遵守数据保留和访问控制。历史上下文、工具结果、审核快照也不是一回事，恢复同一任务要明确哪些状态可以继续使用，哪些必须重新查验。

什么时候拆成多个 Agent

多 Agent 不是项目成熟度的刻度。OpenAI Agents SDK 的编排文档将两种模式区分开：handoff 把对话控制权交给专门 Agent；把 Agent 作为 tool 调用，则由管理 Agent 继续负责最终答复。官方建议只有当某个分支确实需要不同指令、工具或策略时才拆分。编排文档描述的是该 SDK 的模式，不能直接推成所有团队必须采用的架构。

对于前例，订单查询、政策核验和退款审批首先可作为普通服务工具和单 Agent 流程。若支持流程后来分出法律投诉、欺诈调查等责任明确且权限不同的分支，才评估专门 Agent 或人工队列；如果只是想让多个 Agent 重复总结同一订单，额外交接只会增加状态同步和审计成本。选择管理器调用还是转移控制权，要看最终决定由谁持有、分支能否独立验收，以及跨分支需要共享哪些最小数据。

用工作流证据做评估

不要只测回答是否听起来有帮助。先构造一组经过脱敏的代表性任务，包括正常查询、缺失订单号、身份不匹配、政策边界、状态冲突、工具超时、重复请求和需要人工裁定的情况。对每种情况写下预期状态、允许调用的工具、应该拒绝的动作、用户看到的解释以及可以重试的条件。记录样本来源与版本，避免只保留模型表现好的例子。

一次运行至少要能观察：最终状态是否满足验收条件，是否调用了正确工具及参数，是否在错误身份下拒绝读取，是否把需要授权的动作暂停，失败后是否重复产生副作用，人工接手是否拿到足够证据。OpenAI 的工作流评估指南建议先用 trace 检查模型调用、工具调用、guardrail 和 handoff 的端到端路径；当“什么算好”已有定义后，再用数据集和评估运行重复比较提示词、模型或路由改动。评估文档提供的是平台能力与流程建议，自动评分器本身仍需用人工标注样本校准。

将结果拆成任务完成、工具选择、越权拦截、人工升级、恢复成功、延迟和成本等不同指标，才能看出改动究竟改善了哪里。不要把这些拼成一个“Agent 成功率”：成功答复可能没有经过授权，合规停下也可能意味着业务任务未完成。上线之前要先确定谁负责处理升级队列、谁审核失败案例、谁能回滚工具改动。本站Harness Engineering 文章继续讨论运行边界和恢复；本文关注的是在什么任务值得采用 Agent，以及如何定义工作流结果。

从小范围试点开始

落地顺序可以很朴素：选一个高频但包含真实语境判断的窄任务；收集代表性输入和真实失败路径；先由人处理并记录决策，形成可测验收；再用只读工具做影子运行；比对预测、人工结果和漏掉的边界；确认效果后，才在低风险动作上开放有限写入，并为高影响动作保留批准。模型和提示词可逐步调整，但每次变化都应重新跑同一组评估样例。

如果影子运行无法稳定分类，先修输入契约与知识来源；如果分类可靠但工具经常选错，收窄工具表面或说明；如果工具正确而状态重复，修复幂等和恢复协议；若需要频繁人工纠正政策判断，保留人工决策而不是为了全自动目标降低门槛。阶段性成功条件应在试点前约定，例如任务类型覆盖、拒绝条件、人工升级处理时限和副作用容忍度；没有这些阈值，就无法判断试点该扩大、调整还是停止。

公开文档能帮助团队设计 Agent 的基本构件，但不能证明某个业务流程适合自动化，更不能证明上线后一定更快或更便宜。真正值得投入的项目，是在有限权限下能处理规则难以穷举的语境，同时保留清楚的验证、停止和交接路径。若一个普通表单、规则引擎或队列已经能稳定解决问题，选更简单的方案本身就是合格的工程判断。
