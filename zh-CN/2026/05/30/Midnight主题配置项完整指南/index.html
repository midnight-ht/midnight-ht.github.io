Midnight 配置指南：先锁定版本，再核对覆盖与模块

主题配置写了却没生效，先核对已锁定的主题版本、Hexo 覆盖顺序，再查模块所需的插件或服务端接口。以本站固定的 Midnight 源码为例，说明配置值如何变成页面行为；不把开关当作已上线证据。

核心要点

  • 先检查依赖锁定的主题版本和配置优先级，再判断字段是否仍受支持。
  • 模块开关只控制主题条件，不会替站点创建接口、账号、插件或后端。
  • 验收配置要检查生成页面、资源路径和真实服务结果；文中的搜索排错是说明性假设。

主题里写了配置，页面却没有变化，第一步不是再复制一份“完整配置”。先确认站点实际装的是哪一版 Midnight，再看 Hexo 从哪几处读取主题设置，最后检查这个设置是否还需要插件、服务端接口或真实账号。配置键存在，只能证明文件里有这段数据，不能证明功能已经运行。

这份旧指南把主题说成 v0.1.16，并把 appearance.accent 当作当前强调色配置。那是文章写作时的版本描述，今天不适合作为通用操作依据。这个站点的 package-lock.json 把 hexo-theme-midnight 固定到提交 ebd48f3e96b55524f0b4cc980e34cbc5ade7166e，安装包元数据报告版本 0.4.9，见该提交的 package.json。下面谈到的默认值都限定在这个提交；它不是“Midnight 最新版指南”，也不保证下一次升级后每个键仍相同。第一次排查时，可以先打开本站锁定的主题默认配置，而不是搜索到一篇旧文章就照抄。

先区分三份配置，而不是把默认文件搬进站点

Hexo 官方文档把主题配置分成几处来源：主题自己的 _config.yml 是默认值；站点根目录的 _config.midnight.yml 是 Hexo 5.0 之后支持的专用主题配置文件；站点主 _config.yml 中的 theme_config 优先级最高。文档给出的对象示例会合并嵌套字段，后出现的值覆盖同名值。因此，同一个键如果在高优先级位置又写了一次，改主题默认文件也可能看不到结果。具体机制见 Hexo Configuration。

例如，站点主配置选择 theme: midnight，并在专用主题文件中设置外观；如果主配置的 theme_config.appearance 里又覆盖了同一字段，实际生效的会是更高优先级的值。排查时把键写成完整路径，例如 appearance.default_scheme，逐处搜索，不要只搜索 appearance 后凭肉眼挑一段。还要检查 YAML 顶层有没有重复的 appearance:、seo: 或 comments: 块。集成指南也提醒，拼接示例时应将同一顶层配置保留为一个块，避免后写的块覆盖前面的字段。

这也是不建议把主题完整默认配置复制到站点的原因。复制当下看似方便，但它把一整份默认值变成了站点自己的旧副本：主题升级新增的默认项不会自动进入副本，删改后的键也可能继续留在其中。更稳妥的方式是只维护需要覆盖的少量值，并把选择的主题提交固定在依赖锁文件里。升级时再对照新版本默认配置做一次有意的变更，而不是让主题包和站点副本在不知不觉中分叉。

用一个配色问题看“配置存在”和“配置生效”的差别

这个站点锁定的默认配置把 appearance.skin 设为 ocean，default_scheme 设为 system；同一文件把 appearance.accent 标为弃用，并提供 accent_light、accent_dark。主题 README 说明内置皮肤为 ocean、jade、violet，明暗模式可选 system、light、dark；从旧版升级时应移除旧的全局 accent 覆盖，若确实要自定义，则分别提供浅色和深色颜色值并检查对比度。这里的操作边界很具体：把旧键留在 YAML 里，文件仍然合法，但主题代码可能已不再读取它。

一个小范围覆盖可以写成：

appearance:
  skin: jade
  default_scheme: system

这段只表达“希望采用哪套皮肤、首次访问跟随什么模式”，不会替你验证颜色是否适合全部组件。若加上自定义强调色，要分别指定浅色和深色值，再查看链接、按钮、辅助文字和代码行号等实际使用位置。默认皮肤通过对比度检查，不等于任意自定义颜色都会自动满足可读性。旧文把 accent 当成推荐首选项，正是版本变化会让“配置项清单”误导读者的例子。

可以把验证分成三步：先确认键名出现在当前锁定版本的默认配置或文档中；再确认它没有被站点更高优先级的同名值覆盖；最后重新生成静态站点，检查页面是否出现对应的 data-skin、颜色令牌或可见样式。只看到配置文件被保存，不代表模板真的读取了它。反过来，如果生成页面仍使用旧颜色，先检查是否浏览器缓存或 CSS 静态资源缓存，再考虑配置解析问题；每次只改变一个变量，才能分清是哪一层产生了差异。

开关打开后为什么仍然没有功能？检查模块依赖

Midnight 的可选模块遵循“配置齐备后再显示”的思路，但每类模块需要的东西不一样。搜索除了 search.enabled: true，还需要有效的 search.action；没有可用的目标地址，启用布尔值不等于搜索表单能完成查询。文章中的模型会话面板需要 model_session.enabled，也需要 model_session.endpoint。主题提供的是浏览器端界面，不负责创建模型代理、鉴权、限流或密钥管理；服务商 API Key 必须放在服务端，不能写进会进入浏览器的主题配置。

订阅页也有同样边界：inner_pages.newsletter 可以配置标题、说明和表单外观，但如果没有真实 form.action，页面并没有一个接收订阅的后端。把表单画出来和把邮件地址安全地接收、保存、退订是不同的工程工作。评论则需要先选 Giscus、Waline 或 Utterances，再准备相应平台要求的仓库、分类或服务地址；缺参数时组件可能被隐藏。这时继续调 CSS 不会修复一个未接通的评论服务。

统计尤其容易把不同数字混为一谈。主题集成指南把站点分析脚本、文章阅读/评论数字、页脚 PV/UV 视为不同配置。站点报表脚本不能自动变成文章阅读数接口；文章数字接口需要服务端返回协议要求的数据，页脚计数又是另一个来源。项目若没有实现对应后端，就不应打开自动统计并展示猜测数字。配置里的空 endpoint、统计开关和前端展示条件要一起核对，不能把“开关为 true”写成“计数已上线”。

sitemap 链接出现了，目标文件为什么仍可能不存在？

主题默认配置里有 sitemap 和 feed 设置。它们可以控制模板是否显示链接、使用什么路径，但浏览器里出现一个 sitemap 链接并不能证明那个地址返回了有效 XML。主题 README 推荐为一般 Hexo 站点安装 sitemap 和 feed 生成器；而使用 Midnight 的语言目录结构时，主题自身也包含对应生成逻辑。不同站点结构和插件组合会不同，所以不要机械地同时安装插件，也不要假定主题开关可以替代生成器。

以 sitemap 为例，检查路径不仅要看 _config.midnight.yml，还要看站点自己的 sitemap.path 是否覆盖了它，然后重新构建并确认最终 public/sitemap.xml 存在，里面包含预期的语言文章地址。若模板链接指向 /sitemap.xml，实际生成器却把文件放在另一路径，页面看似正常，提交给搜索引擎的却是空缺 URL。Feed 也应按同样方法检查实际输出，而不是根据页脚文字推断。

一个可复用的排错过程

假设某站启用了搜索，但桌面和手机都看不到搜索框。这个例子是排查演示，不是本次对线上站点执行的配置实验。先检查安装版本及其 _config.yml 是否包含 search.enabled、search.action；再在站点配置里找到对应路径，确认高优先级 theme_config 没有把它关掉或改成空地址。然后用该站自己的构建命令重新生成，查看生成页面里是否输出带目标地址的搜索表单。若设置正确但模板仍不输出，检查主题是否真的切到 midnight、所用主题源码是否与锁文件一致；若表单存在而查询失败，问题已经落在 action 对应的服务，而不是样式层。每个检查结果能把故障缩小到配置、构建、模板或服务四个边界之一。

顺序也能减少返工。先改外观和站点身份，因为它们可以直接从生成页面验证；再确认语言目录、文章 lang 与 translation_key；随后才连接评论、统计、搜索、模型服务或订阅。这些外部模块有账号、接口、跨域、隐私和失败处理，只有当服务端路径和实际访问权限都已准备好时才适合启用。最后检查 SEO 输出与 sitemap、feed 文件。一个有用的完成定义不是“配置写完”，而是给每个启用项找到对应的生成产物或实际可访问服务，并记录失败时页面会怎样呈现。

不要把配置截图当作验收证据。版本号回答“这一套键名属于哪份代码”；配置来源和优先级回答“最后读到哪个值”；构建页面和服务请求回答“功能是否真的出现并工作”。这三个问题各有不同证据。本文只核对了站点锁定的主题提交和 Hexo 官方配置文档，没有替任何读者运行自己的项目，也没有测量配色、搜索或服务端点在其他站点上的结果。准备从头搭站的读者可以继续看Hexo 与 Midnight 的博客发布链路，而这篇文章聚焦的是已有站点配置为什么会与预期不一致。
