Hexo + Midnight 博客怎么部署：先选源码构建还是静态文件发布

持续写博客的关键不只是选 Hexo 和 Midnight，还要分清源码仓库、public 构建产物、Vercel 部署与 Cloudflare DNS。本文比较两种发布链路，并给出可恢复的检查方法。

正文

核心要点

  • 先决定 Vercel 从源码构建，还是接收 Hexo 生成的 public；两条链路的提交与回滚边界不同。
  • 把 Node 主版本、package-lock、主题版本和构建命令固定下来，才能让另一台机器重建同一站点。
  • Cloudflare 的 DNS-only 与代理模式职责不同；自定义域名目标值应从 Vercel 项目检查，不能套用通用 IP。

本地首页能打开，只能证明这台电脑曾生成页面。要确认线上更新，至少对上三项：源码提交、生成的 public/ 文件和生产部署对应的 SHA；域名能打开，不足以证明它们属于同一次发布。长期维护 Hexo + Midnight 博客，先把四件事分开：Markdown 与配置属于源码，Hexo 把它们生成到 public/，托管平台把某个构建结果发布为页面，DNS 再把域名指向托管服务。源码仓库和生成文件可以放在同一个仓库，也可以分开；区别在于你要验证哪一个提交最终成为线上版本。

这篇文章比较两条链路：把源码仓库交给 Vercel，由它安装依赖并构建；或先在本地/CI 运行 Hexo，再把 public/ 推到单独的静态仓库。它们都能工作，但提交、预览和回滚的证据不同。下文的命令和假设示例用于说明配置边界；没有在一个全新 GitHub 与 Vercel 账号中从零执行完整注册流程。本文实际运行的 Hexo 站点构建会在发布记录中单独说明，不能替代新账号端到端验收。

先画出源码、构建和线上版本的边界

Hexo 读取站点配置、主题、插件和 source/ 中的文章，生成静态文件到 public/。主题负责页面结构与呈现，不负责为文章仓库提供版本恢复，也不自动替你配置托管平台。Midnight 官方 README 的安装方式是把 hexo-theme-midnight 加入 Hexo 项目，再在站点 _config.yml 中设置 theme: midnight；它还明确提醒，主题前端配置不应放服务端密钥。语言切换则依赖文章的 translation_key，对应译文可有各自的路由。

可以把链路想成：

文章和配置 ──Hexo──> public/ 静态文件 ──托管部署──> 线上域名
     Git 源码提交          构建产物提交/部署提交          DNS 与 HTTPS

这个拆分能解释常见误判。hexo generate 成功，不代表托管平台收到了新 public/；Vercel 显示部署成功，也不代表文章链接、canonical 或英文路由正确；域名可以访问，更不代表它指向最新部署。每一层都需要有自己的证据：源码提交、构建日志和产物、部署对应的提交，以及公开页面的返回状态与内容。

建项目时先固定可重建的输入

Hexo 8 官方文档列出的最低 Node.js 版本是 20.19.0。Node 项目的支持状态会变化，因此不要把“用最新版”写成多年不变的建议；在 2026 年 11 月 27 日查阅时，Node 官方版本表把 24 和 26 都列为 LTS。一个团队应选择仍受支持、与依赖兼容的 LTS 主版本，再把本地和构建环境对齐。可用 .nvmrc 或运行时文件记录主版本，并在 Vercel 项目设置里选择同一主版本；升级时再单独测试依赖。

先创建 Hexo 项目并安装主题：

npm install -g hexo-cli
hexo init my-blog
cd my-blog
npm install
npm install hexo-theme-midnight

然后在 _config.yml 设置主题名。Midnight README 还列出 sitemap 和 feed 插件作为推荐站点插件；按站点需求添加，不必为了“看起来完整”装一整套插件。提交 package.json 与 package-lock.json，不要提交 node_modules/。npm 官方说明，npm ci 适合自动化环境：它要求 lockfile 与 package.json 一致，安装前会移除现有 node_modules/，且不会改写这两个清单。它让依赖树按锁文件安装，但不冻结 Node 主版本、操作系统、CPU 架构或原生构建工具；所以还要记录运行时并验证目标构建环境。主题依赖也要锁定：若通过 npm 安装，让 lockfile 固定实际包版本；若使用 Git URL，就固定到经过审查的 commit，而非不断变化的分支。

本地运行时至少分两种检查。hexo server 让你看页面；hexo clean 后再运行项目定义的构建命令，则检查站点是否能从当前源码重新生成。不要把“电脑上还留着旧 public，浏览器看起来正常”当成构建通过。对多语言站点，还要检查每个 translation_key 是否有对应内容、切换链接是否指向真实翻译页。

两种部署方案，选一种作为主链路

方案 A：Vercel 从源码仓库构建

源码仓库保存文章、配置、主题依赖、锁文件和 package.json。把仓库连接到 Vercel 后，在项目设置中检查 Root Directory、Build Command、Output Directory 和 Node.js Version。Vercel 文档说明，部署只会提供配置的输出目录中的文件；对 Hexo 来说通常需要让构建命令生成 public/，并让输出目录与其一致。若项目已有 build 脚本，先核实 Vercel 检测到的命令；如果 Hexo 项目没有脚本，就显式设置，例如运行 npx hexo generate，而不是假设平台知道要执行什么。

这个方案的好处是源码提交和构建记录天然靠近：分支可以触发预览，生产分支则对应生产部署。Vercel 也支持按具体 Git commit SHA 发起部署。回滚时要记录目标部署及其源提交，不要只看“最新成功”字样。它适合构建依赖能在平台安装、项目配置明确、需要预览环境的博客。

反例是项目依赖 Git 子模块、构建前要读取平台不提供的本地文件、或构建脚本把文件写到意外目录。此时 Vercel 的部署可能因 Root Directory、安装命令或输出目录不匹配而失败；即使构建显示成功，如果输出目录里是空站点或旧文件，也不能把它当正确发布。先在预览部署核对生成目录和页面，再切生产域名。

方案 B：把 Hexo 生成的静态产物单独发布

另一条链路先由本地或 CI 构建，再把 public/ 推到一个专门存放静态文件的仓库。Hexo 的 hexo-deployer-git 配置包含目标仓库与分支；官方示例把默认 GitHub 分支写为 gh-pages，其他托管目标可能不同。若静态仓库再连接 Vercel，Vercel 项目就要按它接收的是已构建文件来配置，而不是再把文章源码当 Hexo 项目构建一次。GitHub Pages 也提供 branch/folder 发布与 Actions 构建两种做法；选择后应按对应平台的要求设置。

这条方案让静态产物成为可单独检查的快照，也可以把构建和上线审批拆开。但它多出一条需要留证的边界：源码提交与静态仓库提交不是同一个 SHA。排查时需要同时记录“哪个源码提交生成了它”和“哪个静态提交正在服务”。如果只保留静态仓库，文章修改过程和锁文件变更就难以追溯；如果只看源码仓库，也不知道线上文件是否已更新。部署脚本应在推送前核对目标分支当前提交、生成树和预期提交关系，禁止用强制推送覆盖远程历史。

不要同时让两套链路无约定地发布同一个域名。例如，Vercel 从源码分支自动构建，同时又由 hexo deploy 把文件推到另一项目，可能产生两个生产部署来源。若确实保留两步，应定义谁是唯一生产入口、哪个提交是发布凭据、谁有回滚权限，并在每次发布后逐篇核对 URL。

用一个假设例子说明为什么要记录两个提交

假设一篇中文文章和英文译文都已进入源码分支 S。Hexo 构建得到静态目录 public/，选择方案 B 后，这些文件被提交到静态仓库，形成提交 A。Vercel 再从静态仓库的生产分支构建出部署 D。如果英文页面显示旧正文，排查顺序不是先清 CDN，而是核对 S 是否包含译文、public/ 是否生成正确、A 是否包含对应文件、D 是否确实由 A 创建。任何一项不匹配，缓存清理都不能修复缺失的构建输入。

换成方案 A，链路缩短为源码提交 S → Vercel 构建 → 部署 D，但仍要验证构建输入与产物。两种方案都应保留浏览器实际读取的页面结果；只看 Git 绿色状态不够。本文没有把这个例子伪装成真实站点事故，它只是按各平台文档中定义的源码、构建和部署边界构造的假设排查路径。

Cloudflare 是可选的 DNS/代理层，不是“再加一层就更快”

当域名由 Cloudflare 管理、站点放在 Vercel 时，先在 Vercel 项目中添加域名并执行域名验证，再到 Cloudflare 配置验证结果给出的记录。Vercel 官方文档明确要求使用项目域名设置或 vercel domains verify 返回的 A/CNAME 值；外部 DNS 提供商应在其控制台配置，不能把文档示例值当成所有项目共用的地址。随后再次验证 DNS 与 SSL 状态。Cloudflare 文档区分 DNS-only 与 Proxied：前者只返回源站地址，HTTP/HTTPS 不经过 Cloudflare；后者会把流量送过 Cloudflare 网络并启用其代理能力。是否打开代理应由缓存、WAF、访问路径和证书配置决定。

如果启用 Cloudflare 代理，还必须让 TLS 两段都正确。Full (strict) 模式要求 Cloudflare 到源站的连接加密并验证有效证书；错误地使用 Flexible 可能让“浏览器到 Cloudflare”看起来安全，但不能证明后端连接也按预期加密。不要复制别人的 DNS IP 或在证书未就绪时凭感觉切换模式。改 DNS 前记录原值，改后分别检查 DNS 解析、证书、HTTP 跳转、静态资源加载和页面 canonical。

若博客不需要 Cloudflare 的代理规则或 DNS 管理，先只用 Vercel 域名也能完成部署；多加一层就多一组配置和故障边界。关于回滚，还可以参考站内构建产物、线上版本与回滚验证；若团队要在 CI 中固定依赖输入，可继续看锁文件与可复现安装的输入边界。

发布前怎么证明这条链路可恢复

检查分为四层，避免把一个绿勾解释成全部成功：

  1. 源码层：git status 干净，文章、主题配置、package.json 和锁文件都已提交；不能把密钥放进仓库或主题前端配置。
  2. 构建层：在干净状态执行 npm ci、npm run clean 和项目的 build 命令。检查 public/ 包含主页、文章、CSS、图片、语言路由和 sitemap；如果本地是方案 A 的构建，不要默认 CI 与它使用相同 Node 与环境变量。
  3. 部署层：确认生产部署的源 SHA；若有静态仓库，也记录生成它的源码 SHA。部署失败时保留日志和当前生产提交，不要直接强推新的目录覆盖历史。
  4. 访问层：用无缓存请求核对首页、中文和英文文章、canonical、hreflang、结构化数据与内链。一次 200 只证明该 URL 当时能返回响应；仍需比较正文与审核版本，并确认专题/归档能找到文章。

Hexo 官方文档说明，hexo clean 会清除缓存和生成文件，hexo deploy 才执行部署器。两条命令承担的责任不同。新项目的具体脚本、Vercel Root Directory、输出目录、Cloudflare DNS 模式都要按你的仓库和账户实际填写；这份指南没有在一个全新的账号和域名上执行完整上线路径，也不声称本文读者复制命令后已获得部署成功。

原文章中的个人经历和截图占位没有可追溯的现场记录，因此本次重写将它们移除。当前可复用的判断是：把源码、静态文件、生产部署和 DNS 分层，选定一条主链路，然后用相邻两次提交与公开页面证明它。若无法回答“线上这份 HTML 是由哪个输入生成的”，先补齐构建与部署记录，再考虑增加评论、统计或 CDN 配置。
