用 Hexo 和 Midnight 主题搭建一个能长期更新的博客

一篇从零搭建 Hexo + hexo-theme-midnight 博客的实操记录：用 GitHub 管版本，Vercel 自动构建托管，Cloudflare 接管 DNS、HTTPS 和 CDN。

我见过不少博客死在第二个月。

搭的时候兴致很高，主题换了三遍，首页调到半夜。等真要写第三篇文章时，发现自己忘了怎么部署，本地环境也变了，最后干脆把博客放进收藏夹吃灰。

所以这篇不讲“为什么你需要一个博客”，只讲一条能重复、能恢复、适合长期写下去的链路：

  • 用 Hexo 写静态博客；
  • 用 Midnight 主题做技术写作站点；
  • 用 GitHub 管源码和文章；
  • 用 Vercel 自动构建和托管；
  • 用 Cloudflare 接管 DNS、HTTPS 和 CDN。

配好之后，日常发文就回到一件事：写完，提交，推送。

配图占位 1：最终博客首页截图。建议截 Midnight 主题首页第一屏，让读者先看到完成后的样子。

先分清这几个工具各自负责什么

这套组合容易配乱，是因为几层能力看起来有重叠。我的理解很简单：

角色 工具 负责什么
静态站点生成器 Hexo 把 Markdown 编译成 HTML、CSS、JS
博客主题 Midnight 决定首页、文章页、多语言、评论、SEO 等展示能力
版本管理 GitHub 保存源码、文章和配置，记录每次改动
构建与托管 Vercel 监听 GitHub，自动安装依赖、构建、发布
DNS 与 CDN Cloudflare 管域名解析、HTTPS、缓存、防护和访问统计

这里有个判断要提前说清楚：Vercel 本身就自带全球边缘网络。再套 Cloudflare，不是为了让速度“翻倍”，而是为了拿到 Cloudflare 的 DNS 管理、缓存规则、防火墙和统计能力。

如果你只想尽快上线，一个 GitHub + Vercel 就够了。加 Cloudflare 的意义在于控制权更集中，后面换服务商、加规则、看访问情况都会方便。

第 0 步：准备环境

先把本地环境对齐。后面很多构建失败，都是本地能跑、线上不能跑，或者线上 Node 版本换了导致依赖装不上。

需要准备：

  • Node.js：建议用 24.x LTS；
  • Git：能正常 git --version；
  • GitHub 账号；
  • Vercel 账号，可以直接用 GitHub 登录；
  • Cloudflare 账号；
  • 一个域名，注册商不限，但 DNS 后面交给 Cloudflare 管。

先检查版本：

node -v
npm -v
git --version

配图占位 2：终端检查 Node、npm、Git 版本的截图。

第 1 步：初始化 Hexo 站点

全局安装 Hexo CLI，然后创建站点：

npm install -g hexo-cli
hexo init blog
cd blog
npm install

先跑一次默认站点，确认 Hexo 这一层没问题：

hexo clean
hexo server

打开 http://localhost:4000，如果能看到默认的 Hexo 页面，说明本地环境是通的。

配图占位 3：hexo server 启动成功的终端输出，重点截到 http://localhost:4000。

配图占位 4：默认 Hexo 页面截图，用来和后面 Midnight 主题效果对比。

第 2 步：安装 Midnight 主题

Midnight 主题仓库是：

https://github.com/midnight-ht/hexo-theme-midnight.git

主题已经发布到 npm，直接安装即可：

npm install hexo-theme-midnight

然后安装站点地图和订阅源插件。Midnight 的 README 里也推荐了这类插件，对搜索引擎收录和订阅比较有用：

npm install hexo-generator-sitemap hexo-generator-feed

接着打开站点根目录的 _config.yml，把主题切到 Midnight：

theme: midnight

这里有个容易改错的地方：不要去改 node_modules/hexo-theme-midnight/_config.yml。npm 安装的主题一更新，node_modules 里的改动就可能丢。

更稳的做法是在站点根目录新建：

_config.midnight.yml

Hexo 会把这个文件作为主题配置覆盖项。一个够用的起步配置可以这样写：

appearance:
  logo: ""
  logo_text: 我的博客
  nick: 你的昵称
  default_scheme: light

i18n:
  default_lang: zh-CN
  route_strategy: auto
  languages:
    - zh-CN

nav:
  home:
    name: home
    path: /
  items:
    - name: 技术
      path: /tags/技术/
      style: pill
  archives:
    name: archives
    path: /archives/
  about:
    name: about
    path: /about/

comments:
  enabled: false
  provider: giscus

model_session:
  enabled: false
  endpoint: ""

我会建议初期先把 comments 和 model_session 都关掉。评论系统可以等站点跑通以后再接；model_session 需要你自己准备服务端代理，API key 不能写到前端配置里。

改完再跑：

hexo clean
hexo server

如果首页已经换成 Midnight 的样式，这一步就完成了。

配图占位 5：切换到 Midnight 后的本地首页截图。

配图占位 6：项目文件树截图，标出 _config.yml 和 _config.midnight.yml 的位置。

第 3 步：把 Hexo 项目交给 GitHub 管版本

个人博客最怕的不是部署麻烦，而是两个月后你忘了当初怎么配。一旦用 GitHub 管起来，至少源码、文章、配置都能找回来。

先确认哪些文件应该提交：

应该提交：
- source/
- scaffolds/
- themes/（如果你手动放了主题）
- _config.yml
- _config.midnight.yml
- package.json
- package-lock.json

不应该提交：
- node_modules/
- public/
- db.json
- .deploy_git/
- *.log

.gitignore 至少应该包含：

node_modules/
public/
.deploy*/
db.json
*.log
.DS_Store

去 GitHub 新建一个空仓库，假设叫 blog。然后在本地执行：

git add .
git commit -m "init: build hexo blog with midnight theme"
git branch -M main
git remote add origin git@github.com:你的用户名/blog.git
git push -u origin main

到这里，博客源码就有了云端版本。以后换电脑，或者本地环境坏了，重新 git clone、npm install 就能恢复。

配图占位 7：GitHub 仓库文件列表截图，能看到 source/、_config.yml、_config.midnight.yml、package.json。

第 4 步：用 Vercel 自动构建和托管

Vercel 这一步的价值，是把“本地生成 public 再上传”变成“推送代码后自动上线”。

操作顺序：

  1. 登录 Vercel；
  2. 用 GitHub 授权；
  3. 点击 Add New -> Project；
  4. 选择刚才的博客仓库；
  5. Import 项目。

构建配置建议这样填：

配置项 值
Framework Preset Other
Build Command npm run build 或 hexo generate
Output Directory public
Install Command npm install

如果你的 package.json 里还没有脚本，可以补上：

{
  "scripts": {
    "build": "hexo generate",
    "clean": "hexo clean",
    "server": "hexo clean && hexo server"
  }
}

建议同时锁定 Node 版本。最直接的方式是在 package.json 里加：

{
  "engines": {
    "node": "24.x"
  }
}

这样 Vercel 构建时就不容易因为运行环境变化出问题。

部署成功后，Vercel 会给一个 xxx.vercel.app 的临时域名。先打开这个域名看一遍首页、文章页、归档页，如果都正常，再去接自定义域名。

配图占位 8：Vercel 项目的 Build & Output Settings 截图。

配图占位 9：Vercel 部署成功后的 Ready 页面截图。

配图占位 10：xxx.vercel.app 能正常访问博客的截图。

构建失败时不要急着改一堆配置，先看 Vercel 的 Build Logs。常见问题就两类：

  • Node 版本不一致；
  • 本地装了插件，但 package.json 或 package-lock.json 没提交。

第 5 步：让 Cloudflare 接管域名和 CDN

Cloudflare 这一步要慢一点配。它和 Vercel 都会处理 HTTPS，SSL 模式配错，最常见的结果就是无限重定向。

5.1 把域名 DNS 交给 Cloudflare

在 Cloudflare 里添加站点，它会给你两条 Nameserver。去域名注册商后台，把原来的 Nameserver 改成 Cloudflare 给的两条。

改完之后等 Cloudflare 显示站点 Active。这个过程可能几分钟，也可能几个小时。

配图占位 11：Cloudflare 站点显示 Active 的截图。

5.2 在 Vercel 添加自定义域名

进入 Vercel 项目：

Settings -> Domains

添加你的域名，比如：

blog.example.com

或：

example.com

Vercel 会提示你需要添加哪种 DNS 记录。

5.3 在 Cloudflare 添加 DNS 记录

如果用子域名，比如 blog.example.com：

Type: CNAME
Name: blog
Target: cname.vercel-dns.com
Proxy status: DNS only（先灰云）

如果用裸域，比如 example.com，可以按 Vercel 提示添加 A 记录，常见写法是：

Type: A
Name: @
IPv4 address: 76.76.21.21
Proxy status: DNS only（先灰云）

这里建议先把 Cloudflare 的代理关掉，也就是灰云状态。等 Vercel 验证域名通过之后，再切回橙云，让 Cloudflare 开始代理和缓存。

配图占位 12：Cloudflare DNS 记录截图，标出 CNAME 或 A 记录，以及灰云/橙云状态。

5.4 SSL 模式一定选 Full strict

进入 Cloudflare：

SSL/TLS -> Overview

模式选：

Full (strict)

不要选 Flexible。Vercel 侧本来就是 HTTPS，如果 Cloudflare 用 Flexible，可能出现浏览器和 Cloudflare 之间是 HTTPS、Cloudflare 到 Vercel 之间是 HTTP 的错配，最后就是重定向来回跳。

配图占位 13：Cloudflare SSL/TLS 选择 Full (strict) 的截图。这张建议一定补。

5.5 缓存规则不要一开始就配太狠

Hexo 是静态站，CSS、JS、图片适合缓存久一点。但 HTML 如果缓存太久，新文章可能发了半天还看不到。

初期可以先只用 Cloudflare 默认缓存。等你确认发布链路稳定后，再加规则：

  • 静态资源长缓存：*.css、*.js、图片；
  • HTML 保守缓存，或者每次发文后手动 Purge；
  • 更新主题样式后，记得清 Cloudflare 缓存。

配图占位 14：Cloudflare Caching 页面或 Purge Cache 页面截图。

跑通之后，日常发文流程就很短

前面所有配置，都是为了让后续写文章不再分心。

日常流程可以固定成这样：

hexo new post "我的第一篇文章"
hexo clean
hexo server

本地预览确认没问题后：

git add .
git commit -m "post: 我的第一篇文章"
git push

git push 之后，Vercel 会自动拉取 GitHub 最新代码，安装依赖，执行构建，把 public 目录发布出去。Cloudflare 负责前面的域名解析、HTTPS 和 CDN。

配图占位 15：hexo new post 后生成的文章文件和 front matter 截图。

配图占位 16：Vercel 因为一次 git push 自动触发部署的记录截图。

我会提前做的几个取舍

第一，先别急着开多语言。Midnight 支持 translation_key 和语言路由，这很好，但对刚开始写博客的人来说，多语言会让目录、链接和维护成本一起上升。中文先写稳定，再考虑英文。

第二，评论系统可以晚点开。Giscus、Waline、Utterances 都能用，但评论不是博客上线的前置条件。先让写作和部署链路顺起来。

第三，Cloudflare 是为了控制权，不是为了玄学加速。Vercel 已经很快，Cloudflare 真正值钱的是 DNS、规则、防护和统计集中在一个地方。

第四，能锁版本就锁版本。Node 锁 24.x，主题锁一个明确版本，package-lock.json 提交进仓库。个人博客的稳定，很多时候不是靠复杂架构，而是靠少一点不可控变化。

这套链路搭完，你得到的不是一个“看起来很酷”的博客，而是一个能长期更新的工作台：文章有版本，部署可重复，域名和缓存可控。剩下的难题就很朴素了：下一篇写什么。
