collation警告消失后，旧索引就恢复了吗？

以两个索引清单与只读目录查询，区分版本警告消失、依赖对象恢复和业务排序检查。

正文

核心要点

  • 刷新登记不检查对象重建。
  • 按实际依赖保存逐对象恢复证据。
  • 版本代理不能排除发行版回移变更。

REFRESH VERSION 可以让 collation 版本警告消失，却不会检查依赖对象是否已按新规则重建。操作系统或 ICU 升级后，应先确认排序规则变化及影响范围，恢复依赖这些规则的对象，再登记新的版本。警告消失是一份元数据状态，不能单独作为旧索引恢复的验收。

假设维护窗口结束后，数据库开始提示某个命名 collation 的版本不匹配。值班人员执行提示中的刷新命令，下一次查询不再出现警告，于是把升级任务关闭。这里可能遗漏的不是另一条消警告命令，而是数据库中已存对象仍按什么比较规则组织。下面讨论 PostgreSQL 18 官方说明，没有升级系统、重建索引或执行 ALTER。

版本登记与已有结构为什么会分开？

PostgreSQL 18 的 ALTER COLLATION 说明指出，创建 collation 时记录提供者的版本，使用时比较实际版本，不匹配会产生警告。排序定义改变可能破坏索引等已有对象依赖的顺序假设。数据库保存的结构不是每次比较时自动按新规则完整重做。

文档要求重建所有依赖受影响 collation 的对象，例如使用 REINDEX，然后刷新版本。刷新只更新目录中记录的版本，不实际检查重建是否正确完成。于是“命令成功”“目录版本对齐”“结构已按新规则重建”必须分别留证。把它们压缩成一个绿色状态，后来就无法知道遗漏发生在哪一步。

也不能反向推断每次操作系统升级都一定改变了每个排序关系。需要保留实际系统包、提供者库与版本身份，再根据供应方说明和依赖范围安排处理。没有精确环境时，随便列两个字符并声称升级前后顺序必然反转，同样不是有效验收。

两个索引如何形成一份恢复清单？

以下是教学假设：app.name_sort 的已登记版本为 v-old，运行库报告 v-new；customer_name_idx 依赖它，customer_email_idx 使用另一套 C 规则。两个版本字符串只是标记，不对应某个真实 ICU 发行版。清单必须按实际依赖确定，不能因为两个索引在同一表上就自动认定都受同一命名规则影响。

对象 本例依赖 仅刷新版本后能否证明已恢复
customer_name_idx app.name_sort 不能，缺少重建与检查回执
customer_email_idx C 不能由前一个命名规则直接判为受影响对象

这份例子的独立预期是：只刷新后，警告可能消失，但第一项的重建证据仍为空；第二项是否另受系统变化影响，需要自己的范围判断。通过条件不是“两个都出现了绿色图标”，而是每个实际受影响对象都能关联到对应恢复与验证记录，没有把未涉及对象冒充已重建。

下面一份只读 SQL 把规则版本与直接登记的依赖放在同一行，便于把每项恢复回执关联到具体规则，尚未运行。模式名区分同名对象；LEFT JOIN 保留没有直接依赖的规则。对依赖类型的筛选放在 ON 中，不能放进 WHERE 后再误删空依赖行。实际行数与对象名未知，不提供伪造输出。

SELECT n.nspname AS schema_name, c.oid, c.collname,
       c.collprovider, c.collversion,
       pg_collation_actual_version(c.oid) AS actual_version,
       pg_describe_object(d.classid, d.objid, d.objsubid) AS dependent_object
FROM pg_collation AS c
JOIN pg_namespace AS n ON n.oid = c.collnamespace
LEFT JOIN pg_depend AS d
  ON d.refclassid = 'pg_collation'::regclass
 AND d.refobjid = c.oid
WHERE c.collname = 'name_sort'
ORDER BY schema_name, dependent_object;

实际处理时应选定模式与对象身份，把名称查询缩小到批准范围。目录查询是清单入口，不是自动修复器；扩展对象、默认规则及特殊依赖仍要核对。官方说明另有数据库默认 collation 的对应刷新命令，不能以一个命名对象的依赖查询声称覆盖了整个数据库的所有排序影响。

恢复时到底需要哪一份证据？

可以让清单分别保存提供者前后身份、受影响依据、恢复动作、结果与业务检查。恢复动作可能是回到预期的提供者库，也可能是在新库下重建对象，选择取决于升级目标、可用窗口及实际依赖。无论哪条路线，都不应先把目录更新当作问题已经解决，再希望后续有人补上恢复。

重建本身也需要计划。二〇二六年十月九日的并发建索引等待与有效性解释了在线构建仍有资源和失败状态，本题不重新给出一套未经环境确认的 REINDEX 操作脚本。维护者应按真实版本的命令限制、对象类型和业务窗口决定执行方式。

验证可以覆盖代表性排序查询、使用该比较规则的相等或唯一性约束，以及关联业务读写。保留语句、参数类别与实际提供者版本，确保检查针对本次变化。查询计划里选中了索引，只说明优化器使用它；有效标志为真也不是排序语义已正确的独立证明。若比较规则变化使原本可共存的值出现冲突，应按真实业务身份政策解决，不能靠刷新登记掩盖。

站内二〇二六年十月十六日的多语言排序政策讨论显示语言与身份的区别。数据库升级还多出一个时间维度：既有结构可能按旧政策建立，新查询已经使用新库。验收需要解释这两份状态如何重新一致。

版本号相同，是否就能跳过排序语义检查？

不能据此保证。官方说明，GNU C 库的版本只是 collation 版本的代理，发行版可能把新的排序定义回移到旧库版本中。应把实际库与发行包身份保留在升级证据中，不能只保存一个相同字符串就宣布不存在变化。这一提醒针对该提供者的局限，不是说所有版本信息都没有用途。

完成记录应让下一位维护者看清：哪些规则被检查、哪些对象确实需要恢复、哪次恢复覆盖了它们，以及刷新登记发生在什么证据之后。若只读查询或恢复尚未执行，就把对应状态保留为待验证。本例没有真实目录输出或重建回执；可交付的是能把警告消失与对象恢复分开核查的清单，而不是一次已经完成的升级。
