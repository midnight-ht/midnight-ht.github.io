给Saga安排补偿结果，而不只画一条失败箭头

以预留确认、付款拒绝和释放超时的Saga轨迹定义补偿未知、查询确认及人工处理，明确补偿是新的业务动作而非跨服务回滚。

正文

核心要点

  • 后一步失败不自动撤销此前已提交的动作。
  • 补偿超时应保留未知状态，查询确认后才能结束。
  • 不可逆动作需要业务更正流程，不能只调用通用反向方法。

Saga 的补偿也可能失败或结果未知。把流程画到失败箭头，并没有说明前面已提交的库存预留是否释放；完成条件应落在每个业务动作的权威结果，而不是编排器最终抛出了什么异常。

假设订单 O-17 已在库存服务取得预留 R-8，随后付款步骤明确拒绝。编排器应处理已有预留的释放责任，却不能因为付款失败就臆造一笔退款。若释放请求超时，此时订单不能直接标成全部撤销。下面采用 AWS 的 Saga orchestration 指南解释模式，再给出作者提出的结果合同；没有调用 AWS、库存或付款服务。

已提交步骤不会因下一次异常自动消失

AWS Saga 编排模式指南描述由协调者顺序组织多个本地事务，在后续步骤失败时执行补偿事务。参与者需要能够安全重复执行，以处理崩溃和编排器失败后的重试。补偿不是把所有服务拉回一笔数据库事务，而是在已发生事实之后安排新的业务动作。

库存预留和释放尤其不能简写成“恢复旧库存数字”。预留之后可能已有另一张订单成功占用库存。若释放 R-8 时直接把总量写回最初读取的旧值，就可能覆盖别人合法的变化。更合理的业务合同是对特定预留身份完成释放，并让重复释放同一预留不会再次增加可用量；怎样实现需要库存服务自己的事务与约束，本篇没有实现它。

同一指南指出 Saga 缺少事务隔离，并建议考虑语义锁。这里的含义不应被偷换成“在编排器加个全局锁就够了”。订单处于预留或取消途中时，哪些操作可进入、哪些必须等待或拒绝，要由相关服务共同遵守。只在一个调用入口检查状态，另一个入口仍可出库，不能由一张正确的流程图补救。

把补偿超时留下来，而不是覆盖成失败终点

本例给出 pending、reserved、compensating、compensation_unknown、compensated 等状态。这些名字是作者的教学合同，不是 AWS 的标准枚举。reserved 表示已确认取得特定预留；付款明确拒绝后承担释放责任；释放超时进入未知；只有查询证实 R-8 已释放，才认定补偿完成。

这份合同还保留两个独立出口。正常付款确认可进入 completed；明确不可自动处理的释放错误进入 manual_review，带着预留身份交给负责人，而不是无限循环。付款本身超时则是 charge_unknown，不能冒充 rejected，更不能从一条客户端超时推导出应该直接退款或重新扣款。

下面完整 Python 3 文件只根据输入的既定结果演算状态，没有发送任何命令，也没有实现服务幂等存储。它覆盖补偿未知、查询后完成、人工处理、正常完成和付款未知五条独立轨迹。预期列表在演算之外写定，不把程序打印当作真实服务成功回执。

"""Unexecuted local contract reducer. No services, AWS or payment calls.
Events describe already established outcomes; timeout does not establish rejection.
Only the modeled order/reservation is owned. This is not an idempotency store.
"""
def reduce_trace(trace):
    reservation, state = None, 'pending'
    for event, identity, outcome in trace:
        if event == 'reserve' and outcome == 'confirmed' and state == 'pending':
            reservation, state = identity, 'reserved'
        elif event == 'charge' and state == 'reserved':
            state = {'confirmed': 'completed', 'rejected': 'compensating',
                     'timeout': 'charge_unknown'}[outcome]
        elif event == 'release' and identity == reservation and state == 'compensating':
            state = {'released': 'compensated', 'timeout': 'compensation_unknown',
                     'permanent_error': 'manual_review'}[outcome]
        elif event == 'lookup_reservation' and identity == reservation and state == 'compensation_unknown':
            state = {'released': 'compensated', 'held': 'compensating'}[outcome]
        else:
            raise ValueError('Outside modeled contract; do not invent a result')
    return state

prefix = [('reserve', 'R-8', 'confirmed'), ('charge', 'P-9', 'rejected')]
cases = [
 prefix + [('release', 'R-8', 'timeout')],
 prefix + [('release', 'R-8', 'timeout'), ('lookup_reservation', 'R-8', 'released')],
 prefix + [('release', 'R-8', 'permanent_error')],
 [('reserve', 'R-8', 'confirmed'), ('charge', 'P-9', 'confirmed')],
 [('reserve', 'R-8', 'confirmed'), ('charge', 'P-9', 'timeout')],
]
expected = ['compensation_unknown', 'compensated', 'manual_review',
            'completed', 'charge_unknown']
if __name__ == '__main__':
    assert [reduce_trace(trace) for trace in cases] == expected
    print(expected)

第一条在释放超时处结束，必须保留 compensation_unknown。第二条增加权威查询已释放，才变为 compensated。第三条不再自动重试，而进入人工处理；这并不表示库存已经恢复。第四条是付款确认的正常分支。第五条付款超时，示例停在 charge_unknown，后续付款查询协议没有在函数里实现。

查询也必须有足够含义。若响应只说“没有找到 R-8”，可能是查错租户、数据已归档或预留从未创建，不能自动解释为已释放。业务服务应返回可解释的权威终态或保留审计依据，并明确查询权限与保留时间。这是作者给结果合同增加的设计要求，不是声称 AWS 指南规定了这些字段。

哪些步骤值得拆成 Saga

如果订单、库存和相应规则可以在同一数据库事务中可靠处理，未必值得为了使用一个模式拆成多个服务。已有独立存储和生命周期、业务可以定义补偿时，才应评估编排成本、重试责任和缺乏隔离的代价。不能将 Saga 当成同时拥有本地事务原子性、跨服务隔离和任意回滚能力的总开关。

本站事务发件箱处理本地提交与交付意图的交接；它可以帮助发送后续动作，却不替业务定义如何补偿已经成功的预留。事务隔离与整事务重试讨论同库并发判断，隔离级别也不会自动撤销外部动作。两种已有机制可以参与实现，不能覆盖本篇的补偿终点问题。

运行记录应把订单、原动作身份、补偿身份、尝试及确认结果关联起来。恢复工作者需要知道哪些动作已经确认、哪些只是发出、哪些尚待查询。若只留下最终 error 字符串，重启后很难区分应该重试释放、查询付款还是交给人工。指南对可观测性与重复执行的要求，正需要这样的具体责任来兑现。

已经发出的通知，需要用补偿把它删除吗？

不能假设它可被撤销。应按渠道与业务定义更正通知，关联原订单与原消息，或者把不可逆动作安排在足够确定的阶段。删除本地发送记录不会让收件人没看见先前内容，也不能证明外部系统已经撤回。

这类动作决定了流程的真实边界。已经发货可能需要退货流程，而不是一个 inverse 方法；已经发生的人工决定可能需要审核更正。是否允许补偿以及补偿意味着什么，应在开发前由业务确认，不用“最终一致”四个字替代这些答案。关于同一意图的重复执行，可接着核对请求幂等边界，但幂等本身也不会让不可逆动作变可逆。

拟议验收应在每个已确认步骤之后中断，保存权威业务状态，再验证恢复者是否只承担对应身份的补偿。重复释放不能影响其他预留；释放超时不能直接标成成功；付款未知必须保留查询出口；永久错误应能交接给明确负责人。这里的代码与五个预期均未执行，尚未证明任何服务、付款提供方或实际编排部署满足这份合同。
