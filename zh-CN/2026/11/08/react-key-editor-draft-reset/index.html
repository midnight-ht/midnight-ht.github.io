记录切换了，React 编辑框为什么还留着上一条草稿？

记录 props 改变不一定重置同位组件状态。用完整编辑器与 A/B/A 操作预期说明 key 的子树重建范围，并把草稿丢弃、保留和后台保存分开。

核心要点

  • 稳定记录 key 表达父级范围内的组件身份。
  • 重建子树可能清除不止一个输入状态。
  • 返回恢复草稿需要更长寿的保存所有者。

同一位置上的编辑组件可以收到新记录，却继续持有旧局部状态。先决定切换要丢弃还是保留草稿，再把组件身份和记录身份对齐。给编辑器加记录 key 能重建对应子树，但它不是草稿归档，也不会替用户保存尚未提交的内容。

React 关于保留与重置状态的官方说明把状态关联到渲染树中的位置，并解释组件类型和 key 怎样参与身份。当前获取的页面显示 v19.3；页面没有明确的文章更新日期，不能只凭版本导航就声称每个段落刚刚修订。

业务记录变了，树中的位置未必变

假设详情页始终在同一个位置渲染 Editor，只把 record 从 A 换成 B。对应用来说，这是另一位客户；对 React 来说，同类型组件仍处在原位置，原来的局部编辑状态可以继续存在。于是标题已经显示 B，输入框里却还是 A 的未保存文字。

用 useState 接收 record.name 作为初值，不等于每次 props 变化都重新初始化。初值与以后每次数据同步是两份合同。若用 Effect 无条件把新名称写回，又可能在同一记录刷新时覆盖正在编辑的草稿；不能只为了让标题与输入看起来相同，就替产品决定所有本地变化都可丢弃。

派生状态与独立编辑已经说明草稿可能是合法的独立状态。本题的增量在于身份边界：哪一次记录切换应创建新的编辑实例，这个实例的全部子状态要不要一起退出，以及返回原记录时草稿由谁持有。

一份明确采用丢弃策略的完整编辑器

下面完整组件尚未在 React 运行环境执行。它只有客户端局部编辑，没有保存、接口或持久化。教学政策是切换记录就丢弃该编辑器的未保存草稿；这项政策必须先适合产品，不能从代码行为倒推用户已经同意丢弃。

import {useState} from 'react';
const records = [{id: 'a', name: 'Alpha'}, {id: 'b', name: 'Beta'}];
function Editor({record}) {
  const [draft, setDraft] = useState(record.name);
  return <label>{record.id}: <input value={draft}
    onChange={e => setDraft(e.target.value)} /></label>;
}
export default function App() {
  const [id, setId] = useState('a');
  const [renders, setRenders] = useState(0);
  const record = records.find(item => item.id === id);
  return <main>
    <button type="button" onClick={() => setId('a')}>A</button>
    <button type="button" onClick={() => setId('b')}>B</button>
    <button type="button" onClick={() => setRenders(n => n + 1)}>
      Parent update {renders}</button>
    <Editor key={record.id} record={record} />
  </main>;
}

独立验收序列应先写在组件之外：初始 A 显示 Alpha；输入 A-draft；点击无关父级更新，仍保留 A-draft；切 B，显示 Beta；输入 B-draft；再切回 A，显示 Alpha。回到原记录时没有恢复 A-draft，是所选丢弃政策的结果，不是保存失败。

失败对照是只去掉 Editor 上的记录 key，保持组件位置与类型不变。按官方规则推导，切 B 时标签可以变成 b，输入却仍保留 A-draft。对照应同时看标签身份与输入值；只检查新标题出现，会漏掉最危险的记录与草稿错配。本篇未取得这些浏览器输出，不把推导表述成已经测过。

key 重建的范围比一个输入框更大

官方文档说明，更换 key 会从头创建对应组件及下方子树的状态与 DOM。这意味着若 Editor 内还有折叠区、选择项或校验状态，它们也可能随实例一起重置。只想清空某个输入，却给整个工作区换 key，可能意外丢掉别的应保留状态。

应把重建边界放在真正共享生命周期的子树上。例如记录相关的编辑表单可以换身份，工作区筛选或用户选择的布局却可能应留在父级。先列出哪些状态属于记录、哪些属于工作区，再决定 key 放置位置；不要把“父组件上随便加一个 key”当作通用修复。

同一记录收到服务端新名称又是另一条路径。记录 id 未变，稳定 key 不会替应用强制清空草稿。产品需要决定未编辑时能否刷新、正在编辑时是否提示冲突，以及何时接受远端版本。用服务端更新时间拼进 key 会把任何刷新都变成重建政策，可能正好覆盖本来要保留的输入。

返回上一条记录时还要恢复草稿，key 能单独完成吗？

不能。组件卸载后的局部草稿需要更长寿的保存位置。官方页面的保留状态讨论列出把草稿提升到父级、按记录保存等选项；这样子组件即使退出，父级仍可持有 A 与 B 各自的内容。key 继续表达不同记录身份，但不承担内容保存。

若要求关闭页面后也恢复，则还需另定持久化位置、账号隔离、过期与版本冲突规则。把文本写入浏览器存储与服务端确认不是同一结果；示例没有实现这些路径。也不能为了“保存草稿”保留所有记录的隐藏组件，却不评估大量 DOM、订阅和权限变化的维护成本。

useId 的身份边界讨论过页面关联编号不能代替列表键。这里同样应使用稳定的业务记录身份表达同一父级内的实例，不能在每次渲染随机生成新 key。随机 key 会让无关父级更新也重建编辑器，用户只是点了别处就丢文字。

状态重置不等于后台工作取消

如果旧编辑器已经启动自动保存，更换 key 只改变前端子树身份，不自动撤销服务器写入。保存请求仍需携带记录 id、版本和结果归属，退出时的处理也应明确。否则旧 A 的响应到来，仍可能被错误写进当前 B 的公共状态。

组件定义的位置也要检查。把 Editor 函数定义在 App 每次执行的内部，可能让组件类型身份不稳定，从而发生与业务切换无关的重置。把定义放在稳定位置，与使用稳定记录 key 是两项互补条件；修正一项不能证明另一项自然成立。

待执行验证覆盖 A/B/A、同记录更新、无关父级渲染、子状态重置范围以及草稿保留政策。存在自动保存时再单独加入旧响应路径，不把本地输入清空当作服务器停止的证据。评审最终应能逐个指出每份状态由谁保存、何时丢弃，以及哪些动作会建立新实例。
