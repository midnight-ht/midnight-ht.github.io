集合成员删了又回来：先问并发新增该不该赢

用两次添加身份及完整教学模型解释成员重现，并比较共享标签与撤销政策的不同要求。

正文

核心要点

  • 观察删除只覆盖已见的添加。
  • 副本收敛不证明全局撤销。
  • 把教学标签模型与ORSWOT存储分开。

离线副本删除了自己见过的成员，另一个副本同时新增；在加法获胜的 OR-set 中，合并后成员仍可存在。选择这种集合前，应明确并发新增是否应胜过删除。副本最后一致，只证明它们按所选规则收敛，不能替业务证明“删除已全局撤销所有加入”。

假设两人离线维护共享标签。甲删掉 team-red，乙与此同时重新加入同一个标签，恢复同步后标签出现。对共享整理场景，这可能是合理的新加入；若集合表示权限撤销，界面却承诺从此禁止访问，相同结果可能不符合要求。问题首先在集合动作的业务含义，不在于所有冲突都必须由一个最近时间戳裁决。

删除究竟观察到了哪次添加？

Basho 的 riak_dt_orswot 源码明确说明，并发添加与删除时添加获胜。实现为添加记录 actor 与计数构成的点，并结合版本向量判断另一个副本是否见过它。一个副本上没有该成员，既可能是还没见过新添加，也可能是已经见过并删除；这两种原因不能只靠成员是否显示来区分。

源码中的带上下文删除会减去上下文已经见过的点，合并也会用对方时钟过滤点。因此删除不是对某段显示文字签发永久禁止令，而是在具体因果知识范围内移除添加。这里限定的是 ORSWOT 这类加法获胜的观察删除语义，不能推广成所有 CRDT 集合都采用相同冲突规则。

Riak 的集合使用文档在删除例子里先读取上下文，再把它随删除传回。实际 API 中的上下文是 opaque 数据，应按客户端约定保留。不能把下面教学例子中的 a1、b1 自己拼成真实服务的上下文，也不声称这些旧项目文档证明当前生产支持状态。

两条添加身份构成完整反例

以下未执行的 Python 模型使用带标签的观察删除集合，显式保存已删除标签，便于看见因果关系。它不实现 ORSWOT 的无 tombstone 存储；后者通过点与时钟压缩这类知识。模型只演示此处的加法获胜结果，不是可投产的 CRDT 库。

# Unexecuted tagged OR-set semantics model, not ORSWOT storage.
from dataclasses import dataclass

@dataclass(frozen=True)
class State:
    adds: frozenset
    removed: frozenset

def merge(left, right):
    return State(left.adds | right.adds, left.removed | right.removed)

def visible(state):
    return {member for member, tag in state.adds - state.removed}

a1 = ('team-red', 'a1')
b1 = ('team-red', 'b1')
initial = State(frozenset({a1}), frozenset())
replica_a = State(initial.adds, frozenset({a1}))
replica_b = State(initial.adds | {b1}, frozenset())

assert visible(replica_a) == set()
assert visible(replica_b) == {'team-red'}
combined = merge(replica_a, replica_b)
assert combined.adds == frozenset({a1,b1})
assert combined.removed == frozenset({a1})
assert visible(combined) == {'team-red'}
assert merge(replica_b, replica_a) == combined
assert merge(combined, combined) == combined

removed_after_observing_both = State(combined.adds, combined.adds)
assert visible(removed_after_observing_both) == set()

独立预期可直接从两份身份写出：初始添加 a1 被甲删除，乙新添加的 b1 不在甲的观察范围内。合并后添加身份有 a1、b1，删除身份只有 a1，因而 team-red 可见。随后在已经见过两次添加的状态中删除，二者都被覆盖，可见集合为空。不能因为显示值始终只有一个 team-red，就断言系统只有一次添加动作。

交换两份输入后合并结果相同，重复合并自己也不改变结果。这两条断言验证模型在该输入上的交换与幂等，不能证明完整实现对任意故障与输入正确。生产选择仍需实际库测试、节点身份管理、因果上下文保存和数据持久化检查。

为什么不能只测“最后两边相同”？

甲乙最终都看见 team-red，完全可能符合收敛规则，却不符合产品写下的撤销承诺。反过来，强行让任何删除永久压过将来所有添加，又可能妨碍共享标签重新加入。集合算法需要先知道并发冲突应怎样解释，不能由“避免冲突”四个字替所有动作选择同一个结果。

二〇二六年十月九日的条件更新与版本冲突采用另一种政策：旧版本写入被拒绝，用户获得重新比较的机会。OR-set 可以让离线动作各自接受后合并，这减少了一类同步前提，却把并发添加保留为明确结果。两个方案对可用性与冲突处置的承诺不同，不是简单地把 ETag 换成集合名。

若业务要求撤销必须立即约束其他节点，就需要定义权威撤销状态、验证位置、传播延迟与离线访问政策。一个暂时无法连接权威来源的节点应拒绝、暂缓还是按旧授权继续，必须由业务明确选择。本例没有设计完整授权系统，也不建议把权限交给这段集合模型；它只是说明不能从集合收敛推出即时全局撤销。

同一天的事务隔离与业务不变量也要求先写不变量再选保护。这里的不变量可能是“并发新标签不能丢”，也可能是“被禁入成员不能重新获得资格”。先把两种需求分清，才知道加法获胜是否是期望行为，以及哪些动作应离开集合层单独处理。

可以给最后一个条件再写一个独立结果：在已观察两次添加并删除的状态后，新增身份 c1 应让 team-red 再次可见；旧的 a1、b1 仍在删除集合中，没有被取消。这不是旧数据恢复造成的复活，而是模型按规则接受了第三次新动作。验收应单独展示 c1 的创建时点，不能把时间线上的每次出现都混称同一种同步错误。若产品此时要求拒绝 c1，就应让禁入政策在接纳新动作时生效，而不是期待先前的删除自动表达未来限制。

c1 = ('team-red', 'c1')
future = State(
    removed_after_observing_both.adds | {c1},
    removed_after_observing_both.removed
)
assert future.removed == frozenset({a1,b1})
assert visible(future) == {'team-red'}

等同步完成后再删一次，能保证以后不再出现吗？

只能移除这次已观察到的添加。之后新的合法添加仍是新动作；若业务要求禁止重新加入，需要单独定义禁入或撤销政策，不能只依赖一次集合删除。第一个代码块中对 removed_after_observing_both 的空集合断言，只证明观察 a1 与 b1 后能够删除它们；后一个代码块则单独证明新增 c1 会再次可见，两者都不把一次删除当成永久禁入。

验收至少要保存并发添加、观察全部后删除、删除后新加入三条时间线。每条都先写业务预期，再核对模型或实际库；真实客户端测试还需保存读到的上下文、发送的操作和合并结果。本文没有启动 Riak、运行 Erlang 或执行 Python。可审查的交付应指出采用哪种集合语义、哪次添加被谁观察，以及哪些撤销要求另有权威机制负责。
