保留姓名原文，单独定义Unicode比较键

保留原始姓名并生成NFC比较键，用五项独立预期解释兼容合并、碰撞处理与拼接后再次归一化。

正文

核心要点

  • 规范等价、兼容等价与记录身份是不同判断。
  • 比较键应有字段用途，原文保留以支持回显和重建。
  • 独立归一化的片段拼接后仍可能需要再次归一化。

多语言姓名需要更容易检索时，可以保留用户原文，另行定义 Unicode 比较键。肉眼相同的字形未必有相同代码序列；但选择一种归一化形式，也不等于已经定义了身份、大小写或安全规则。先说明允许合并哪些差异，再决定比较键怎样生成与维护。

相同显示为什么不等于严格相等？

一个 é 可以用单个代码点表示，也可以由 e 和组合尖音调组成。在 JavaScript 中，严格字符串比较不会因为它们看起来一样而自动合并。问题并不是少调用一次排序比较器，而是应用要求怎样的等价关系：需要统一规范等价的表示，还是还想忽略兼容字符、大小写或其他区别？这些选择不能用“统一处理文本”一笔带过。

Unicode 标准附录第十五号“归一化形式”区分规范等价与兼容等价。此处核对的文档为 Unicode 18.0.0、修订五十八，日期为二〇二六年八月十二日。NFC 与 NFD 保留兼容区别；NFKC 与 NFKD 会进行兼容分解，可能消除格式区别。附录明确提醒，不应把后两种形式不加判断地应用于任意文本。

JavaScript 的 String.prototype.normalize 规范允许 NFC、NFD、NFKC 和 NFKD，默认采用 NFC，其他形式名会抛出 RangeError。链接指向二〇二七版语言规范的当前草案快照，不是对已部署浏览器 Unicode 数据版本的承诺。下面使用的是长期存在的字符，没有借新规范版本宣称所有设备刚刚增加了某种能力。

原值与比较键怎样分开？

假设产品需要在姓名搜索中合并规范等价的写法，但仍保留原始输入用于回显。以下完整的只读示例未执行，不写数据库、不访问账户，也不根据比较结果授予权限。输入中的转义明确指出字符序列，避免仅从屏幕字形判断发生了什么。

const a = '\u00E9';
const b = 'e\u0301';
const original = [a, b, '\uFF21', 'A'];
const byForm = new Map(
  ['NFC', 'NFKC'].map(form => [
    form, original.map(text => text.normalize(form))
  ])
);
const keys = byForm.get('NFC');
const compatibility = byForm.get('NFKC');
const fragments = ['e', '\u0301'].map(text => text.normalize('NFC'));
const joined = fragments.join('');

console.log([
  a === b,
  keys[0] === keys[1],
  keys[2] === keys[3],
  compatibility[2] === compatibility[3],
  joined === joined.normalize('NFC')
]);

五项独立预期依次为 false、true、false、true、false。前两项区分原始序列和 NFC 比较键；第三、四项比较全角大写 A 与普通 A，NFC 保留两者差异，NFKC 会把这个兼容区别合并。第五项用于后文的拼接边界。这里列出的是按规范推演的期望数组，不是运行输出。

original 仍保留四份原字符串，keys 只用于已声明的检索。即使前两个键相同，原记录也不必删除或覆盖；可以让它们都成为搜索候选，再由实际记录标识定位。若数据模型要求唯一性，需要在权威接收侧规定碰撞处理，不能让前端把搜索结果相似直接解释成同一个人。

为什么不能把 NFKC 当成万能清洗？

本例全角 A 合并为普通 A，可能符合某种受限代码字段的目的，却不自动适合所有姓名、题目或需要保留全角、上标等区别的文本。保留原文使团队能够重新解释旧数据；原地覆盖后，若后来发现某项区别需要保留，就未必能够还原。选择兼容合并应是字段合同，而不是看见“更统一”便全局替换。

反例是上线一个统一清洗函数，将姓名原文、搜索键和账户标识同时 NFKC，然后把新键冲突的两条记录自动合并。即使 API 返回了预期字符串，也没有证明两个人身份相同。归一化只改变所选等价关系中的表示，不完成同形欺骗检测，也不处理所有大小写、语言转换或业务授权问题。

既有的Collator 排序政策讨论语言顺序和比较平局。本题的区别是先建立一种有明确用途的字符串表示，再比较或检索。不要把 Collator 返回零、NFC 键相同、用户记录相同这三种判断混成一个布尔值。界面可以显示近似候选，最终操作仍应携带稳定记录身份。

检查的是字符序列，不是截图

拟议验证应保存原值、代码点表示、所选形式、比较键与命中的记录。对照上述五项预期，检查前后端是否使用同一字段合同；不要只截图两个 é 看起来一样。对于不同运行环境，记录实际运行时和 Unicode 数据条件，必要时使用同一组受控样本验证，不能凭一台浏览器推断所有接收端相同。

已有索引迁移也要先查看碰撞。假设旧索引区分两种 é，新索引合并比较键，重新建键可能让更多原记录落在同一项。搜索服务可以保留多条候选并显示足够上下文，唯一字段则需单独解决冲突。不要为了让迁移无错误，静默丢弃后写入的一条，也不要先修改原文再寻找需要保留的区别。

失效恢复同样需要版本信息。若客户端采用新比较政策、服务端仍按旧规则查询，可能出现预览能找到而提交定位失败。应把比较键策略与索引版本纳入发布、回退和重建计划，并明确原值仍可用于重新生成。本文没有执行索引迁移或跨端兼容测试，这些仍是设计与验证步骤。

分别归一化两个字段，再拼成检索键，还需要处理一次吗？

如果合同要求整串处于所选正规形式，应在拼接后再次归一化。Unicode 附录说明，正规形式不对任意字符串拼接保持封闭。一个已经是 NFC 的 e，与一个独立也为 NFC 的组合尖音调，拼起来仍可进一步组合成 é。这就是示例第五项为 false 的原因，不是归一化函数不稳定。

因此，比较键应从最终组装的输入生成；若为了性能做分段处理，需要有真实边界规则与验证，不能仅靠“每段都处理过”。另一个独立问题是字段之间是否需要分隔符、分隔符怎样转义，防止不同字段组合产生同样字符串；归一化不会替应用定义组合身份。本篇不把这个附带问题伪装成已经实现的编码协议。

交付时保留原文、声明比较键的用途与形式，给出碰撞处理和拼接后的生成位置，再用独立字符样本检查实际结果。若团队只需要合并规范等价表示，就先把这一条规则做清楚；增加兼容合并、大小写或安全策略时分别评审，避免一个文本辅助函数承担未经定义的身份决定。
