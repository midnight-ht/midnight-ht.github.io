autospec 还没调用业务，为什么真实 property 已经执行？

autospec 建立规格时可能读取真实属性。用本地异常哨兵和窄接口对照，区分内省、签名约束与真实业务验证。

正文

核心要点

  • 规格内省本身可能触发 getter，不能只检查业务调用。
  • 窄接口可保留签名检查，但仍需验证与真实实现一致。
  • 类规格不自动包含仅由初始化创建的字段。

给客户端实例创建 autospec，业务方法还没调用，真实的 property 已经报错。替身没有接管每一次读取：建立规格时，unittest.mock 需要查看原对象的属性。对带有连接、读取配置或延迟初始化动作的 getter，检查接口本身就可能成为执行入口。

替身为什么还要读取原对象

Python 的 Autospeccing 文档说明，autospec 会递归约束替身的接口，并让被模拟函数保留原来的调用签名。它通过访问规格对象来了解属性；沿替身读取属性时，内部还可能沿原对象做相应遍历。本文于二〇二六年十一月七日核对的页面标注 Python 3.15.2，不代表读者本机解释器的版本。

普通 Mock 可以在读取时生成许多不存在的属性，容易让旧接口的测试继续通过。autospec 要缩小这个接受范围，就得取得原接口的信息。这里有两种动作：读取规格对象以获得约束，以及在约束内调用替身。没有发生第二种动作，不能据此否定第一种动作已经执行。创建规格时也可能读取实例属性，不能把文档所说的惰性递归理解成“创建时绝对不访问 getter”。

假设一个客户端把 connection 做成 property，第一次读取才打开连接。维护者只想模拟 read(key)，却把已经初始化的整个客户端实例交给 create_autospec。此时若内省触发 connection，连接尝试可以发生在测试准备阶段。真实连接会带来什么结果取决于客户端实现；本文不连接服务，改用本地异常哨兵暴露这条读取路径。

一份只有本地动作的完整对照

下面的单文件示例未执行。保存为 autospec_probe.py 后，可在独立目录用标准库 Python 运行；先记录解释器版本。第一组故意提供不能安全检查的实例，第二组提供只描述 read 方法的窄接口。代码没有访问网络、读取秘密或构造生产客户端。

from unittest.mock import create_autospec

class LiveShape:
    @property
    def connection(self):
        raise RuntimeError("inspection reached getter")

try:
    create_autospec(LiveShape(), spec_set=True)
except RuntimeError as error:
    assert str(error) == "inspection reached getter"
else:
    raise AssertionError("getter was not observed on this interpreter")

class ReadPort:
    def read(self, key):
        raise NotImplementedError

safe = create_autospec(ReadPort, instance=True, spec_set=True)
safe.read.return_value = 7
assert safe.read("item-1") == 7
try:
    safe.read()
except TypeError:
    pass
else:
    raise AssertionError("missing key was accepted")

第一组的独立预期是出现给定 RuntimeError，虽然代码从未主动读取 connection，也未调用业务方法。末尾的 else 是解释器行为不同的显式失败入口，不能删掉以后声称验证通过。我们不要求 getter 被访问恰好一次；具体访问次数不是这份测试要验收的接口，也可能随实现变化。

第二组按明确配置返回七；漏掉 key 应被签名检查拒绝。七来自测试设置，不是读服务真实返回的值。这一组证明接口约束和一个配置结果能够同时保留，不证明数据读取正确，更不证明生产对象与 ReadPort 始终一致。若接口改名而窄规格没有同步，仍需集成检查发现两者漂移。

该换规格，还是去掉 autospec

先判断真正需要约束的调用范围。测试只用 read(key)，可以把这个可见、无副作用的边界作为规格，而不是把完整运行对象交给内省。ReadPort 的方法体没有被调用；它在这里提供名字与签名。真实系统是否适合用这份接口，取决于调用方职责，不能由示例自动批准一次生产重构。

直接关闭 autospec 能避开一条读取路径，也会放宽替身允许的接口。若测试原本依靠它拒绝错误方法名和错误参数，关闭以后应重新说明这些错误由谁检查。相反，给每个 patch 都统一打开 autospec，也忽略了规格对象可能具有的行为。选择标准应是接口可见、检查安全，以及保留了哪些断言，而不是只比较两个设置的严格程度。

官方同一章节还提醒，实例里仅由 init 创建的属性可能不在类上。改用类规格可以避免直接检查那份活动实例，却不能让不存在于类定义中的字段凭空可见。维护者可能需要安全的独立规格、明确配置的属性，或改变依赖边界。不要为了让字段出现，就在测试准备时初始化一个会连接真实环境的客户端。

还有一种失败来自误解 spec_set：它限制为规格上不存在的属性赋值，却不是让所有动态字段自动获得合法身份。先确定字段是否属于当前规格，再讨论读写行为。若生产客户端确实按运行状态动态增加字段，窄规格应说明测试覆盖的状态；一份静态形状不代表全部生命周期都已检查。

只捕获 getter 异常能把问题处理好吗？

不能把广泛捕获当成安全内省的替代。异常发生前，getter 可能已经写了文件或发起请求；吞掉错误不会撤回这些动作。对本例的 RuntimeError 可以准确捕获，因为它是专门设计的本地哨兵。真实代码则应先查清 getter 的行为和是否已经产生副作用，再选择可安全检查的规格。

这条追问增加了准备失败后的处置条件：看见异常，不等于知道执行停在哪一行。调查记录应同时包含异常栈、被检查对象的类型，以及创建规格之前是否已有初始化动作。日志中不应输出客户端保存的凭据；类型、属性名和本地哨兵通常足够定位读取阶段。

怎样界定这次验证的终点

拟议验证先保存单文件、Python 版本和命令退出值，分别观察哨兵分支、配置返回七、漏参拒绝三项结果。若第一组没有触发异常，保留原始输出，检查当前版本的内省行为，不要把另一次运行的堆栈移来解释本轮。再为实际调用方保留一条独立的真实接口检查，确认规格没有长期落后于实现。

补丁查找位置文章回答替换哪个名字，补丁范围文章回答持续多久以及何时恢复。此处要补上的证据在它们之前或旁边：创建那份替身时究竟读取了什么。先让规格可以安全地被检查，再让测试依赖它提供的签名限制；本文没有运行这些示例或验收任何真实客户端。
