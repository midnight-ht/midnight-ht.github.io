轮换后新日志为空，先看写者还握着哪个文件

用本地文件顺序演算解释轮换后仍写旧文件，以及copytruncate窗口的记录丢失；不把示例当成真实logrotate运行。

正文

核心要点

  • 重命名与创建新路径不会改变已有打开描述符。
  • copytruncate复制到截断之间的新增记录可能丢失，create此时无效。
  • 轮换验收要核对应用重开、文件内容与采集结果。

把 app.log 改名再创建同名文件，不会让已打开的写者自动换文件。轮换要同时安排写者重开，否则它可能继续写进旧文件。看到新日志为空，先核对进程实际持有的文件，再判断是没有产生日志，还是日志仍写在另一个对象上。

名字变了，打开的文件没有跟着换

Linux rename 手册说明，重命名不会改变已经打开的文件描述符。此次页面属于 Linux man-pages 6.19，手册日期为二〇二六年二月八日，网页渲染于九月九日。这里使用本地 POSIX 文件语义分析，不把网络文件系统的失败结果或其他操作系统默认行为一并当作已验证。

应用打开 app.log 后持有一个文件描述符。轮换程序把这个名字改为 app.log.1，再用 app.log 创建新文件，目录里现在有两个名字和两个文件对象；应用原来的描述符仍指向原对象。它继续追加的内容就进入被改名的文件。检查者只读新名字时，可能误以为应用停止记录，实际上旧文件还在增长。

logrotate 上游手册源规定，create 在轮换后、postrotate 脚本前创建同名新文件。本篇固定到二〇二六年三月四日的该文件提交；它仍是含版本占位符的上游源，不代表某台主机安装的具体发行版。创建完成只证明新路径已准备好，不能证明应用已关闭旧描述符并打开新路径。

先用固定顺序看清文件内容

下面的完整 Python 示例未执行。它使用标准库，在自动清理的独立临时目录内演算两种顺序，不调用 logrotate，不给真实进程发信号，也不写生产日志。第一段展示重命名与重开，第二段人为把一条记录放在复制和截断之间，避免依赖偶然的并发时机。

from pathlib import Path
from tempfile import TemporaryDirectory
import shutil

def emit(stream, record):
    stream.write(record + "\n")
    stream.flush()

with TemporaryDirectory() as directory:
    root = Path(directory)
    active = root / "app.log"
    rotated = root / "app.log.1"

    def state():
        return tuple(path.read_text() for path in (rotated, active))

    observed = {}
    with active.open("a") as writer:
        emit(writer, "A")
        active.rename(rotated)
        active.write_text("")
        emit(writer, "B")
    observed["renamed"] = state()
    with active.open("a") as reopened:
        emit(reopened, "C")
    observed["reopened"] = state()

    active.write_text("A\n")
    shutil.copyfile(active, rotated)
    with active.open("a") as late_writer:
        emit(late_writer, "B")
    with active.open("w"):
        pass
    observed["truncated"] = state()
    assert observed == {
        "renamed": ("A\nB\n", ""),
        "reopened": ("A\nB\n", "C\n"),
        "truncated": ("A\n", ""),
    }

候选命令是在独立目录将文件保存为 rotation_probe.py 后运行 python3 rotation_probe.py，同时保留解释器版本和真实退出状态。没有执行回执时，不能把代码里的 assert 写成已经通过。这个例子没有模拟服务重开接口；关闭第一个 writer 再打开 active，只是明确展示重开动作本身改变了后续写入对象。

emit 把一条记录的追加与 flush 放在一起；state 按“旧文件、新文件”读取完整快照，observed 按 renamed、reopened、truncated 标出三个检查点，再与预先写定的三组内容比较。最后用 w 模式打开并关闭原文件，明确表示截断，不省略任何丢失步骤。第一段的独立预期在执行前就能确定：旧文件应含 A 和 B，新文件在重开前为空，重开后只有 C。理由是 B 仍通过原描述符写入，C 才使用新路径打开。若只检查最终两个文件都存在，就没有检验写者究竟换过没有；若两个文件的内容恰好一样，也可能是测试准备或路径选错，必须保留输入顺序。

第二段先复制只有 A 的文件，随后追加 B，最后把原文件截为空。副本只有 A，原文件为空，B 两边都不存在。这里的丢失是人为确定的顺序演算，不是对某台服务器丢了多少条日志的测量，也不是一次真正的并发压力实验。它提供一个反例：复制成功与截断成功可以同时成立，却仍丢掉两者之间的新增记录。

copytruncate 换掉了哪一项协调

上游手册说明，copytruncate 在复制后原地把原文件截为零，适合不能通知关闭日志文件的程序；它也明确警告，复制与截断之间存在一个很短的时间片，部分日志可能丢失。使用它时 create 不起作用，因为原文件留在原处。不要把两项同时出现理解为“既保留描述符，又获得一次新文件切换”。

它解决的是写者继续持有原文件时怎样释放部分文件内容，不是无损协调协议。窗口实际多长、在特定负载下是否观测到丢失，需要真实环境测量；“很短”不等于业务允许丢一条。对于诊断日志，可接受性取决于排障要求；对于必须证明订单状态的记录，则不应只靠这份可能丢失的文件承担唯一事实来源。

另一条路线是重命名、创建，然后使用应用明确支持的重开合同。有的服务有专用命令或信号，有的没有。不能把 HUP 当作所有应用通用的重开按钮：它可能没有对应处理，也可能触发退出或其他行为。应该先查应用版本文档，确认命令作用于哪个进程、什么时候完成，以及失败如何返回，再把它接到轮换流程。

文件权限改好，就能让已有写者换到新文件吗？

不会自动换。权限关系影响下一次打开能否成功，已有描述符仍指向原文件；必须同时核对实际重开动作及其失败结果。

这增加了一个容易漏掉的失败分支：postrotate 已通知应用，应用却因为新文件的属主或权限无法打开它。轮换脚本结束，不代表写者已经切换。应同时观察新文件的实际权限、应用对重开请求的结果和后续唯一序号落在哪个文件；别把再次放宽权限后的成功，反写成最初轮换从未出错。

如果应用继续写旧文件，立即压缩或移走那份文件也需要审查。日志采集器可能正在读取旧描述符，保留策略与应用重开完成时点要协调。本文不提供通用压缩等待秒数，也不根据文件名推断哪些数据可以删除。先确定真实写者与读取者都完成交接，再决定后续保留动作。

轮换验收需要把写入身份接起来

拟议的隔离验收给每条日志带本轮标识和递增序号，分别保留轮换前、轮换中、重开后的有界输入。观察路径、文件对象身份、进程打开描述符与两份文件内容，并记录轮换程序和重开动作各自的退出结果。只查看 app.log 的大小下降，不能区分正确轮换、仍写旧文件和直接丢失数据。

还应确认采集端是否读到了这些记录。文件中存在不等于查询端可见；反过来，查询缺失也未必发生在轮换窗口。journald 的窗口限流讨论处理另一种入口丢弃，Docker 日志驱动讨论处理运行实例采用哪份配置。它们的诊断结论不能直接互换。

最终选择取决于应用能否可靠重开、记录是否允许丢失，以及交接是否能被观察。支持重开时先评估协调路径；不支持时，明确接受 copytruncate 的窗口或更换输出方式，而不是把方便写成无损保证。本篇没有执行 logrotate、变更生产配置或证明日志链路完整；先让路径、描述符和每条测试记录的去向对应，再宣告轮换确实完成了写者交接。
