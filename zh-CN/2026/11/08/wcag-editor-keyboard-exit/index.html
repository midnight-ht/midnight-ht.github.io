Tab只缩进不离开：编辑器怎样给键盘用户出口？

以接管Tab的内联编辑区和完整本地页面，定义Escape交接、后续导航、模式拦截及真实键盘验收范围。

正文

核心要点

  • 接管Tab不自动失败，但键盘出口和必要提示必须成立。
  • 外部按钮存在，不等于能从编辑区到达。
  • 验收应覆盖按键、焦点终点与下一步，并保留模式条件。

编辑器把 Tab 用来缩进，并不自动构成键盘陷阱；真正需要核对的是，用户进入后能否只用键盘离开，并知道如何离开。一个放在编辑区后面的“退出编辑”按钮，如果始终无法从编辑区到达，就没有给后续预览与提交建立路径。应把退出动作、焦点终点和下一步一起定义。

Tab 是命令，出口由谁负责？

WCAG 2.2 成功准则 2.1.2“无键盘陷阱”要求，可经键盘进入的页面组件，也能经键盘离开；若需要超出未修改方向键、Tab 或其他标准退出方式的方法，应告知用户。该条为 A 级要求。这里依据二〇二四年十二月十二日的推荐标准，不把单个例子当作整页合规证明。

W3C 对该准则的理解文档解释，模态框暂时限制焦点可以有合理目的，但仍需可知、可用的离开方式。文档也举出富文本编辑区接管 Tab 的例子。哪些按键属于标准退出方式会受硬件、浏览器和系统影响，不能从一个示例组合推导所有平台通用的快捷键。

内联编辑器与模态框的任务不同。用户可能要在页面里编辑说明，然后到外部预览；不需要先关闭整张页面。组件不能因为自己能处理很多键盘命令，就把到其他区域的导航视为宿主页面的责任。集成时应明确谁拦截按键、谁结束编辑模式、谁获得焦点，尤其当编辑器来自第三方而外部按钮由应用生成时。

一份有实际退出处理器的本地示例

下面的教学页面没有保存、网络或业务提交，代码未执行。Tab 插入两个空格，Shift+Tab 在光标前有两个空格时删除它们，两者都被编辑器接管；Escape 将焦点交到外部按钮。说明在可见正文中保留，也通过描述关联到编辑框。真实产品仍需检查自己的平台与组件，不应直接照此宣布兼容。

<!doctype html>
<meta charset="utf-8">
<label>Title <input value="Demo"></label>
<p id="help">Tab inserts two spaces. Shift+Tab removes two preceding
spaces when present. Escape exits editing.</p>
<label>Body <textarea id="editor" aria-describedby="help">x</textarea></label>
<button id="leave" type="button">Exit editing</button>
<button type="button">Preview</button>
<button type="button">Submit</button>
<script>
const editor = document.querySelector('#editor');
const leave = document.querySelector('#leave');
editor.addEventListener('keydown', event => {
  if (event.key === 'Escape') {
    event.preventDefault();
    leave.focus();
    return;
  }
  if (event.key !== 'Tab') return;
  event.preventDefault();
  const start = editor.selectionStart;
  const end = editor.selectionEnd;
  if (!event.shiftKey) {
    editor.setRangeText('  ', start, end, 'end');
  } else if (start === end && start >= 2 &&
             editor.value.slice(start - 2, start) === '  ') {
    editor.setRangeText('', start - 2, start, 'end');
  }
});
</script>

完整输入顺序是从标题进入编辑区，将光标放在初始 x 后面，按 Tab，再按 Shift+Tab，再按 Tab，最后按 Escape。独立预期为文本从 x 变成 x 加两个空格，恢复为 x，再增加两个空格；Escape 不改变文本，焦点变成退出按钮，随后两次普通 Tab 依次到预览和提交。所有结果都是待验证预期，不是实际浏览器回执。

退出按钮在此作为焦点交接点，按 Escape 的处理器已经完成交接，所以无需再激活它才算离开。它没有额外点击行为，也没有模拟保存。生产组件可以选择更合适的终点，例如编辑器工具栏或明确的后续操作，但必须让用户继续原任务；把焦点送到隐藏节点，再靠鼠标找提交，不是完整交接。

反例不是少一个说明文字

删掉 Escape 分支，保留两种 Tab 的拦截和原来的帮助，就得到一个可区分的失败版本：界面承诺能退出，代码却没有履行。仅检查页面含有“Escape”字符串会漏掉问题。另一个失败是只加外部按钮，却没有从编辑区到该按钮的任何键盘路径；按钮存在与路径存在必须分别验证。

真实编辑器还有模式叠加。自动补全菜单可能先消费 Escape，第一次只关闭建议层；搜索面板、全屏模式或输入法状态也可能改变按键去向。应记录每个受支持状态的退出规则，不能因为默认空编辑器中按一次可用，就保证用户编辑到一半仍能离开。若需要不同方法，应在相应条件下告知，而非藏在只有鼠标能打开的帮助菜单。

修复时也不必一律禁止 Tab 编辑。若用户并不需要该命令，让标准导航离开通常更直接；若缩进确实属于任务，保留命令并提供可靠出口可以兼顾两种需求。选择应有实际任务和支持平台依据，不能为了通过某一条自动扫描而删除用户需要的编辑能力，也不能把“专业用户应该知道”当成通知机制。

验收从进入一直走到后续任务

保存浏览器、系统、编辑器版本、起始焦点、按键序列、每一步的活动元素和文本变化。用键盘完成进入、编辑、退出、预览和返回，不仅检查焦点是否在某一瞬间落到页面外。反向导航也要看：回到编辑区后，帮助是否仍可获取，选择范围与内容是否按设计保留。

接着覆盖建议层开启、只读状态、错误提示出现，以及宿主页面重新渲染后出口元素被替换。若目标已经不存在，focus 调用并不能交出预期结果，应选择仍有意义的终点。这些是待执行测试，不是对某个编辑器库的已发现故障；没有实际记录时，不写支持所有键盘或辅助技术。

既有的模态焦点工作流讨论对话框进入、内部循环和关闭后返回。本题增加的是内联组件接管导航键之后，如何离开编辑区域继续同页任务。两种检查可以共用记录方法，却不能用一个模态框关闭成功的结果替代编辑器出口的验证。

有“退出编辑”按钮，但 Tab 永远到不了它，有用吗？

按钮存在不能替代到达路径。需要从编辑区可执行的键盘动作，把焦点交到可用出口；在编辑区后面追加按钮，仍可能永远到不了。相反，如果组件已有标准且实际可用的离开方式，也不必为按钮数量而再加一个重复出口，应先核对该方式及必要提示。

交付时把“按什么、到哪里、接下来做什么”写成一条可重放记录。提示和实现同时检查，模式变化后的路径也有结果，才能说明用户可以结束编辑并继续工作。代码中出现一个焦点调用只是检查入口，完整的任务路径才是本次集成需要证明的结果。
