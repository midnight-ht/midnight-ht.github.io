CONFIGURE_DEPENDS 解决重查，不替代源码清单的取舍

对照显式列表、普通 GLOB 和带 CONFIGURE_DEPENDS 的列表，确认新增源码如何进入构建图，并保留生成器支持与成员误匹配的取舍。

正文

核心要点

  • 重新执行 GLOB 与真正编译新增成员需要分别观察。
  • 官方提醒生成器可靠性和每次检查成本，不应许诺通用等价。
  • 成功运行未调用新增函数的程序，不能证明新增源码已编译。

CONFIGURE_DEPENDS 可以让构建检查重新执行带标记的 GLOB，并在匹配结果变化时重新生成构建系统；它没有取消源码清单的维护取舍。新增文件是否进入本轮编译，要看清单何时展开、生成器是否支持该检查，以及实际构建图有没有更新。

文件出现，不等于构建图已经知道

CMake 的 file(GLOB) 文档说明，CONFIGURE_DEPENDS 自三点一二加入，作用是把重跑 GLOB 的逻辑加入主要构建系统检查目标；匹配输出改变时，再重新生成构建系统。本文于二〇二六年十一月七日读取的页面标题为 CMake 4.5.0-rc3，不能把这份文档版本称作读者本机已安装的稳定版。

普通 GLOB 在配置时形成列表，随后生成的构建图使用那份结果。源码目录新增一个文件，不会自动编辑已经展开的列表。若同时改了 CMakeLists.txt 或其他配置依赖，恰好重新配置，新增成员可能被发现；那不能证明普通 GLOB 独立监测了目录变化。对照应控制配置输入，而不只观察最后有没有编译成功。

同一官方条款不推荐用 GLOB 收集源码列表，并提醒 CONFIGURE_DEPENDS 不保证对全部生成器可靠，即使工作正常，每次重建也有检查成本。这里没有基准数据，不能说它一定很慢，也不能反向断言所有现有生成器都会失败。选择是在项目生成器与维护责任范围内作出的，不由一个开关替团队决定。

三种成员来源使用同一份程序

以下是未执行的完整教学项目。准备三个新的源码目录 probe-explicit、probe-glob、probe-tracked，每个都保存相同 CMakeLists.txt 与 main.cpp；开始时都没有 extra.cpp。要求 CMake、可用的 C++ 工具链和 Ninja，配置声明的三点二十只是示例下限。构建树分别放在三个独立目录，不复用旧 cache。

cmake_minimum_required(VERSION 3.20)
project(MembershipProbe LANGUAGES CXX)
set(MEMBERSHIP_MODE "explicit" CACHE STRING "explicit, glob, tracked-glob")
if(MEMBERSHIP_MODE STREQUAL "explicit")
  set(inputs main.cpp)
elseif(MEMBERSHIP_MODE STREQUAL "glob")
  file(GLOB inputs LIST_DIRECTORIES false "${CMAKE_CURRENT_SOURCE_DIR}/*.cpp")
elseif(MEMBERSHIP_MODE STREQUAL "tracked-glob")
  file(GLOB inputs LIST_DIRECTORIES false CONFIGURE_DEPENDS
       "${CMAKE_CURRENT_SOURCE_DIR}/*.cpp")
else()
  message(FATAL_ERROR "unknown MEMBERSHIP_MODE")
endif()
message(STATUS "members=${inputs}")
add_executable(membership_probe ${inputs})

// main.cpp
int main() { return 0; }

从这三个源码目录的共同父目录，候选配置与构建命令如下。cmake_step 在命令失败时立即保存退出值并退出当前 shell，阻止后续配置或构建继续；成功才进入下一步。三组分别使用各自的 probe 与 build 路径，不用另一目录的旧产物补位。本文没有运行这些命令，也没有取得编译记录。

cmake_step() {
    if cmake "$@"; then
        return 0
    else
        cmake_status=$?
        printf 'cmake failed: %s\n' "$cmake_status" >&2
        exit "$cmake_status"
    fi
}
for variant in explicit glob tracked; do
    case "$variant" in
        tracked) mode=tracked-glob ;;
        *) mode=$variant ;;
    esac
    cmake_step -S "probe-$variant" -B "build-$variant" \
        -G Ninja -DMEMBERSHIP_MODE="$mode"
    cmake_step --build "build-$variant" --verbose
done

首轮的独立预期是三组都只有 main.cpp 成员，且只需要编译这份源码。随后在三个源码目录各加入下面同样的 extra.cpp，保持 CMakeLists.txt 不变，再用下面的构建循环分别重跑；此时不要重新执行上面的配置循环，否则会替普通 GLOB 主动发现新增成员，破坏对照。它是一个可编译的独立函数，不与 main 形成链接所需的引用，刻意使“构建成功”无法单独暴露遗漏。

// extra.cpp, added only after the first build
int extra() { return 7; }

for variant in explicit glob tracked; do
    cmake_step --build "build-$variant" --verbose
done

这一轮继续使用同一 shell 中已经定义的 cmake_step。新增后只调用 build；若要再测删除匹配文件与加入不匹配文件，也应在各自独立源目录改变单一输入，然后使用这份构建循环，保留每次的成员与编译记录。

显式组仍只列 main.cpp，除非维护者明确把 extra.cpp 加进清单；普通 GLOB 没有因这次目录变化独立登记重查条件，要等重新配置才更新匹配结果。带标记组在生成器支持相应检查的条件下，应发现列表改变、重新生成，并把 extra.cpp 纳入编译。这里描述的是预期分支，不是保证读者环境已经得到这份输出。

程序运行成功，能证明新增文件已编译吗？

不能。本例 main 不调用 extra，遗漏 extra.cpp 仍可链接并正常返回零。应保存本轮 members 输出、重新生成记录与 extra.cpp 的实际编译命令，再确认产物属于这份构建树。只运行可执行文件，就缺少能区分三种成员集合的观察点。

这个追问增加了验收依据：用于识别构建成员的信号，应确实随成员变化。若改成 main 必须调用 extra，普通组遗漏时可能链接失败，那能暴露另一种依赖关系，却不能替代当前这个“未使用源码也要求纳入发布”的合同。两种测试都可以有意义，应先决定项目到底要求什么。

自动发现的便利由谁承担

显式列表让新增成员进入构建配置差异，评审者可以讨论为何发布需要这份文件。代价是新增文件时必须更新清单；遗漏更新也会形成缺陷，不能把显式写法宣传成不会出错。它把成员决定放在可评审位置，而不是自动验证每份源码应不应该发布。

GLOB 减少手工维护，但匹配集合也可能纳入 scratch.cpp、合并临时文件或不应参与发布的实验。若文件名满足同一模式，自动重查会把它视作普通新增成员。需要限定目录与模式、检查实际集合，并为项目支持的生成器验证新增和移除。开关负责发现变化，不理解文件的业务用途。

把目录内所有文件都视为可信输入，也可能掩盖生成文件与源码的边界。若构建过程自己向匹配目录写文件，下一轮集合变化就需要重新解释。本文例子把三个源目录与构建目录分开，避免用构建副产物制造额外成员；真实项目应检查自己的路径，不因为示例分开就认为生产布局已经正确。

生成器变化后需要重新确认什么

先保存 CMake 版本、生成器和完整配置命令，确认当前生成器的检查确实参与常规 build。再覆盖新增匹配文件、删除匹配文件、加入不匹配文件三项输入，分别保存重生成和编译结果。检查成本若是决策因素，应在相同工程与环境下测量，不能用本文未执行的例子给出性能结论。

生成器配置文章处理 Debug 与 Release 在哪个阶段选择。本题决定的是哪些源码进入图，两者都依赖生成器身份，但不是同一问题。可复现构建文章要求固定比较输入；如果连源码成员集合都未确认，单独固定构建时间也无法说明比较对象一致。

最终记录应回答三个问题：配置时看到了哪些成员，目录变化后图有没有重新生成，本轮编译实际使用了哪些文件。本文没有配置或编译工程，也没有验证某个生成器版本。先把这些观察与同一份源码、构建树关联，再决定手工清单的维护成本，是否值得换成受约束的自动发现。
