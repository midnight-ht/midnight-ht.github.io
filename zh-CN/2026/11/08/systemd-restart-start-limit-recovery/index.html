启动限流窗口过了，systemd不一定会再自动重启

解释systemd重启政策、启动限流与新触发的交集，给出三次有界启动单元，并区分清计数、进程运行和业务就绪。

正文

核心要点

  • Restart=always仍受单元启动预算约束，手工启动也计入该限制。
  • 窗口结束不单独产生新的自动启动请求。
  • 清计数、启动成功与业务就绪分别需要证据。

服务因启动限流停下来，等窗口过去不会单独产生一次新的启动请求。后续人工、timer 或 socket 触发可再启动，但必须先处理持续失败的原因。Restart=always 描述重启政策，不能把启动预算和新的触发来源一并省略。

always 仍然要经过启动限流

systemd.service 的 Restart 条款明确说明，服务重启受单元的启动速率限制约束。此次于二〇二六年十一月八日核对的 latest 手册页面标识 systemd 262，不表示读者主机已经具有相同版本或全部选项。排查应保存管理器版本、有效单元及 drop-in，不能只看仓库里的原始文件。

重启政策先判断退出原因是否需要再次尝试，单元限流再约束新启动能否获准。二者可以同时正确：主进程确实以失败状态退出，Restart 也要求重启，但下一次启动已经超过当前窗口预算。因此，看见进程没有回来，不能立即推断 Restart 配置没有加载，更不能把 always 理解为不受限制的无限循环。

systemd.unit 的 StartLimit 条款还说明，限制适用于各种启动，包括手工启动，不只由 Restart 发起的尝试。值班时反复执行启动，也可能继续遭到同一道门槛。默认窗口与次数可来自管理器配置；单元又能显式设置，必须核对实际生效值，不能把网上某个默认数字当成本机事实。

窗口结束只是允许条件变化

手册指出，配置 Restart 的单元一旦达到启动限制，便不再继续尝试自动重启；窗口过去之后，后来的人工、timer 或 socket 触发仍可以启动。这里的“后来可以”不是管理器已经排好一个窗口到期的启动任务。若再没有任何触发源，等待本身不等于出现下一次尝试。

这一区别会决定告警是否有人接手。假设依赖故障使进程短时间连续退出，服务最终触顶停下；依赖随后恢复，但服务没有新启动。只监控依赖变绿，会漏掉应用仍未运行的状态。应同时保留停止自动重试的单元信号与恢复责任，让接手者知道需要确认根因、选择触发并验证业务，而不是把“再等等”当作恢复计划。

也不要反过来看到一次人工启动成功，就宣布限流设置已被移除。窗口可能已经结束，失败状态或计数也可能被清理，单元垃圾回收还可能影响计数保留。诊断记录要绑定同一单元的引用与运行历史，解释这次为什么允许，而不是根据一次结果重写所有生命周期规则。

一份三次启动的有界教学单元

下面的单元未安装、未启动。它只让本地 Python 打印一个标记并以一退出，不连接服务或改业务数据；需要隔离 Linux 环境，且 /usr/bin/python3 存在。当前工作环境没有因此新增单元或改变服务状态。

[Unit]
Description=Bounded restart teaching fixture
StartLimitIntervalSec=60s
StartLimitBurst=3

[Service]
Type=simple
ExecStart=/usr/bin/python3 -c "print('ATTEMPT', flush=True); raise SystemExit(1)"
Restart=always
RestartSec=1s

三次失败都发生在六十秒窗口内，是这组演算的明确前提；如果主机调度、启动等待或其他事件使它不成立，就不能仍套用次数预期。还要求没有其他手工启动、timer、socket 触发，没有改变退出解释的覆盖项，也没有把该单元卸载后重新计算历史。示例不包含 Install 段，不负责开机启用。

独立预期是在这份有界输入下观察三次真实 ExecStart 标记，之后新的启动受限，自动尝试停止。检查应关联每次启动身份、退出状态、单元状态和原始 journal，不能只数终端里有几行相同文字。日志也可能受采集政策影响；标记数不足时，需要先解释证据是否完整，不把缺失日志直接当成启动没有发生。

达到限制以后，保留足够覆盖窗口结束的观察区间，但不额外发启动请求。要检查的是没有仅因时间过去就产生第四次启动，而不是要求某个字段永远保持同一个字符串。真实的 Result、ActiveState 与重启相关计数应原样保存。本文没有执行，也不预填 NRestarts 的显示值，因为把排程请求与实际进入主命令混计，会让一个数字掩盖不同事件。

随后另设恢复阶段：先把退出原因改成教学环境中可解释的正常长运行程序，再按计划等待预算恢复或清计数，显式请求启动。保存这次请求和实际进程证据，最后用它真正承担的业务探针验证。这个阶段必须与原始故意失败组分开记录，不能只留下最后一次成功，抹去最初触顶的事实。

清计数为什么不能修复持续退出

如果程序仍然立即退出，反复 reset-failed 加 start 只会重开一轮失败。它可以暂时让计数与状态看起来干净，却不会恢复缺失配置、文件权限或不可用依赖。把窗口调长、把次数调大或设为零禁用该限流，也需要容量与故障政策依据；这些选项存在，不代表它们都是适合现场的修复。

另一种误判是直接用 systemctl stop 制造异常退出测试。Restart 对管理器发起的停止有例外，手工停服务不能简单等价于主进程自行失败。本篇教学程序主动返回一，就是为了把退出输入写清。实际故障调查还应核对 SuccessExitStatus、RestartPreventExitStatus 等设置，确认某个退出值在当前单元里被怎样解释。

条件检查也需要分别看。ExecCondition 的退出讨论处理的是条件命令允许继续、跳过或失败的协议。unit 条件检查与 ExecCondition 不能混成一项；手册关于条件未满足不计入启动限制的说明，不应凭名称相近就套到所有准备脚本。这里示例直接让主程序失败，没有依赖这种类比。

reset-failed 返回成功，就代表服务恢复了吗？

不代表。它可清理失败状态与启动计数，但服务仍要有新的启动和业务就绪证据；原退出原因还在时，清计数只会允许下一轮失败。

手册明确说明 reset-failed 会清空服务的启动速率计数。报告应把这项管理动作、随后的实际启动和最终业务结果分别列出。新进程存在，也可能仍在准备或等待依赖；本站的就绪通知讨论关注何时可以承诺启动完成，不能由清理标记替它签收。

拟议验收保留有效配置、管理器版本、每次失败、触顶时点、等待区间、修复内容与新触发身份。这样才能区分预算未恢复、没有触发、启动又失败以及进程已运行但业务未就绪。本文没有执行服务恢复或给出生产可用结论；先查清为什么停止尝试，再安排能被观察到的一次恢复，而不是把时间过去当作已有人完成处置。
