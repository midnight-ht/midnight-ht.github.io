预览页仍写着sandbox，为什么子页能解除限制？

用未执行的两文件fixture比较同源iframe权限组合，核对移除sandbox、重载生效与不可信HTML的专用来源。

正文

核心要点

  • allow-same-origin保留内容真实来源，并不把任意外站变成父页同源。
  • 同源父子同时允许脚本和真实来源时，子页可移除sandbox再重载。
  • 属性变更不能证明已加载文档立即撤权或先前动作回滚。

同源子页同时获得 allow-scripts 和 allow-same-origin 时，可以访问父页里的 iframe 元素，移除 sandbox 再重载。属性存在并不足以证明这份组合隔离了不可信脚本。判断这条逃逸链，必须同时看父子来源、允许的权限与下一次导航。

两个权限怎样组合出父页面访问

HTML 标准的 iframe 条款明确警告：当被嵌入页面与父页面同源，同时设置这两个关键词，子页可以移除 sandbox 并重载，从而摆脱沙箱。此次核对的 Living Standard 标注最后更新于二〇二六年十一月六日；这不是某个浏览器版本的实测结论。

没有 allow-same-origin 时，sandbox 会把内容放入不透明来源；有这个关键词时，内容保留它本来的来源。它不是把任何外部网站变成与父页同源的开关。比如第三方网站保留自己的真实来源，通常仍与后台不同源；而后台自己的预览路径保留来源后，就与后台相同。若再允许脚本执行，子页就有机会沿同源 DOM 关系找到装载自己的容器。

因此不能只数“允许了几个 token”，也不能把所有带 allow-same-origin 的嵌入一律称作可逃逸。这里的组合前提是父子确实同源，并且脚本能够运行。父页与子页的协议、主机和端口应作为实际输入记录；路径换成 uploads 或 preview 不改变这三项。本站的Cookie Path 边界讨论也说明目录不是独立信任区，但不替代本题的沙箱权限分析。

两份本地文件走完移除与重载

下面的教学 fixture 未执行。它只对自建页面中的 iframe 操作，不读取用户数据，不联系外部站点。把两份文件放在独立目录，经 HTTP 同源提供；不要直接用 file URL，因为文件来源处理不能作为这个实验的相同前提。

<!-- parent.html -->
<!doctype html>
<title>Sandbox parent</title>
<p id="parent-marker">parent-visible</p>
<iframe title="demo"
  sandbox="allow-scripts allow-same-origin"
  src="child.html"></iframe>

<!-- child.html -->
<!doctype html>
<title>Sandbox child</title>
<p id="result"></p>
<script>
const out = document.querySelector("#result");
let result = "";
try {
  const frame = window.frameElement;
  if (!frame) {
    result = "parent frame unavailable";
  } else if (frame.hasAttribute("sandbox")) {
    frame.removeAttribute("sandbox");
    result = "reload requested";
    location.reload();
  } else {
    result = "sandbox absent after reload";
  }
} catch (error) {
  result = "parent access blocked: " + error.name;
}
out.textContent = result;
</script>

候选运行方式是在该目录使用 python3 -m http.server 18181 --bind 127.0.0.1，然后在测试浏览器打开 http://127.0.0.1:18181/parent.html。前提是本机端口空闲且 Python 标准库可用，结束时停止这个教学服务器。这里没有启动服务器，也没有浏览器截图或通过日志。代码中的标记只是拟议观察点，不是已经发生的结果。

完整双 token 组的独立预期是：子页找到容器，移除属性并重载，随后显示第二次加载的标记。检查者还应从父文档中查看该 iframe 的实际属性，确认它确实不再具有 sandbox；单听子页自报“已解除”不足以证明状态。重载前后的导航与控制台也要保存，以免把上一轮页面缓存或旧进程误当成本轮结果。

第二组只把父文件的属性改成 allow-scripts，保持文件与访问来源不变，再重新加载父页面。子页被置于不透明来源，不能像第一组那样访问同源父容器；其自身读取结果可能表现为拿不到 frameElement，或相应访问受阻。验收重点是父 iframe 的 sandbox 没被子页移除，不能把某一种报错文字当作跨浏览器唯一答案。示例专门区分“容器不可用”和“容器已无属性”，避免把空引用错误报告成逃逸成功。

第三组只保留 allow-same-origin，不允许脚本，重新加载父页面。脚本不执行，结果段落保持空白，父容器仍有限制。空白不能单独证明原因；还要排除子文件没取到、语法错误等其他失败，因此同时核对实际响应和浏览器诊断。三组每次只改一项，才能让现象对应权限组合，而不是同时更换域名、文件内容和策略以后猜测哪个设置起效。

从已加载页面撤权限有什么时点限制

标准说明，相关 flags 在 iframe 内容导航时生效。移除 sandbox 不会直接改变已经加载的文档，这正是例子还需要重载的原因。若观察者只在开发者工具里删除属性却没有导航，不能根据页面暂时没变化断言限制永远不可移除；若脚本先前已经执行，也不能用后来补回一个属性证明先前动作被撤销。

这条时点关系会影响产品切换。后台若复用同一个 iframe，先加载宽权限内容，之后只修改属性却继续沿用旧文档，就需要明确哪次导航真正建立了新限制。敏感预览可以在装载前确定最少权限，再建立受控的新文档。是否重建元素、重新导航或改变承载来源，应按真实生命周期设计，而不是在出现异常后随手叠加 token。

加载以后才删掉 allow-scripts，能立刻停止已有脚本吗？

不能据此保证。标准说明这些 flags 在 iframe 导航时生效；应在导航前设好权限，遇到不可信已加载内容时重新建立受控文档，而不是把属性变化当作运行时撤权回执。

即使旧文档已经被替换，它此前发起的外部请求、提交的业务写入或父页面代办动作也不会因此自动回滚。对这类结果要按相应资源查证，不能只看 iframe 消失。这一追问增加的是撤权时点与已发生动作的处理，和“两个 token 能否组合逃逸”不是同一个问题。

来源布局比临时补权限更先决定信任范围

HTML 标准建议把潜在恶意 HTML 放在独立的专用域。理由还包括直接访问：用户若在顶层打开文件，就不再受父 iframe 属性保护；专用来源能限制内容对应用来源的触及。它不是授权、内容净化和跨来源通信检查的替代。专用域是否携带不应出现的凭据、是否能导航到同源应用，也需要按部署核对。

若业务必须让可信组件读取父 DOM，就应承认它已经进入父页面信任范围，不能继续把相同配置作为对恶意文档的隔离保证。若内容不可信，则先限制来源与脚本能力，再按需求逐项考虑允许的功能。为恢复一项预览效果同时放开脚本和真实来源，可能消除了原本依赖的隔离前提。

父页面允许加载谁、子页面允许被谁嵌入，仍由其他政策分别约束。frame-ancestors 的祖先链讨论解决的是嵌入许可，不会替 sandbox 决定脚本能做什么。最终记录应包括真实父子来源、装载前权限、导航时点、容器属性与敏感动作结果。这里没有执行浏览器测试或安全验收；先明确内容被当作可信代码还是不可信文档，再选择能兑现这份判断的来源与权限。
