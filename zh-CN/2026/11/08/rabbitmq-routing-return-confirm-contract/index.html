RabbitMQ已ACK，消息为什么没有进入队列？

按RabbitMQ 4.1的AMQP 0-9-1合同区分不可路由退回、发布确认与结果未知，用完整本地轨迹说明为什么后到的ACK不能覆盖return。

正文

核心要点

  • 无匹配队列的发布也可能得到代理确认。
  • 退回事实必须保留，不能被后来的ACK覆盖。
  • 确认、路由与消费者业务完成需要各自的证据。

RabbitMQ 的发布确认可以在没有任何队列匹配时到来。收到 ACK 后仍找不到消息，应先查交换机路由结果，不能把确认直接解释为目标队列已保存，更不能解释为消费者完成了订单。

假设订单事件发送到一个已经存在的 direct exchange，routing key 却拼错了。发布端只等待 confirm，随后把发件箱记录改成已交付。这个错误可能不会表现为网络异常：代理已经处理了发布，只是找不到可以接受它的队列。本篇固定讨论 RabbitMQ 4.1 文档中的 AMQP 0-9-1，最小案例没有 alternate exchange；没有连接代理或执行消息投递。

无路由与拒绝处理，是两种结果

RabbitMQ 4.1 发布确认文档的确认时机说明明确区分可路由与不可路由的消息。交换机判断没有匹配队列后，也会给不可路由消息发确认。若发布设置了 mandatory，代理先发送 basic.return，再发送 basic.ack；负确认也遵循先退回的规则。

因此，ACK 不能单独充当“存在目标队列”的断言。它在这个分支上确认的是交换机已经处理了路由判断。相反，存在匹配队列时，文档说确认在消息被所有路由目标队列接受后发出；持久消息、耐久队列与 quorum queue 又有相应的接受条件。不要把这些有前提的条件压缩成“收到 ACK 就永久安全”。

mandatory 负责暴露另一种情况。同版本发布者指南的不可路由处理说明，默认的 false 会让无路由消息被丢弃，或者送往已配置的备用交换机。true 会让消息退回，发布者必须安装退回处理器。给属性赋值却没有接收和保存退回结果，仍然可能让业务日志只剩一条成功确认。

本例排除备用交换机，是为了让“没有匹配队列”具有单一解释。若系统实际配置了备用路由，必须同时检查它去了哪里。进入兜底队列可以符合运维策略，却不等于订单工作队列已经收到；是否允许把这种状态标为完成，应由交付合同决定。

让后来的 ACK 保留退回事实

发布账本至少要能区分代理拒绝、已退回和结果未知。为发布尝试保存 channel 与发布序号，给消息放入稳定的 message_id；序号用于关联确认，message_id 用于关联退回内容。重连后不能只凭相同数字，把旧 channel 的确认套到新 channel。

下面是完整、未执行的 Python 3 合同示例。它不实现 AMQP 客户端，只对显式给定的事件轨迹分类；限制为单 channel、一次只有一条发布在途。输入中的 ACK 和 return 是教学数据，不能作为真实代理回执。真实应用还须接入客户端回调、连接生命周期和持久账本。

"""Unexecuted local contract fixture. No AMQP connection or broker simulation.
Single channel, one publication in flight; returns correlated by message_id.
ACK correlation is channel+sequence; real asynchronous client needs full adapter.
"""
def classify(message_id, publish_key, events):
    acked = returned = False
    for kind, key in events:
        if kind == 'return' and key == message_id:
            returned = True
        elif kind == 'ack' and key == publish_key:
            acked = True
        elif kind == 'nack' and key == publish_key:
            return 'broker_rejected'
        elif kind == 'disconnect':
            break
    if returned:
        return 'returned_unroutable'
    return 'broker_accepted_no_return' if acked else 'outcome_unknown'

cases = [
    ('p1', ('ch1', 1), [('ack', ('ch1', 1))]),
    ('p2', ('ch1', 2), [('return', 'p2'), ('ack', ('ch1', 2))]),
    ('p3', ('ch1', 3), [('disconnect', None)]),
]
# Independently specified oracle. None certifies consumer completion.
expected = ['broker_accepted_no_return', 'returned_unroutable', 'outcome_unknown']
if __name__ == '__main__':
    actual = [classify(*c) for c in cases]
    assert actual == expected
    print(actual)

第一条轨迹只有匹配的 ACK，分类为代理接受且没有退回证据；这仍不是消费者处理完成。第二条先退回再确认，最终必须保留无路由结果，不能因为最后一条事件叫 ACK 就改成成功。第三条在确认之前断线，分类为未知。未知不同于明确拒绝：消息可能已经被接受，只是回执没有到达，不能据此证明它没有发生。

这三个预期不是从同一个分类函数反算出来的。它们分别依据文档中的可路由接受、无路由先退回后确认，以及断线不能证明接收结果的条件预先设定。账本设计应能把这些结果交给发件箱工作者，使其决定修复绑定、查询或重试，而不是把所有未成功情况都当成相同的网络错误。

最小示例省掉的并发责任

生产发布者往往同时发送多条消息。确认可以用 multiple 覆盖同一 channel 上不大于给定序号的一组发布，而且不同消息的确认不保证按发布顺序到来。官方确认文档对此有专门的顺序说明。因此，不能把“收到第三个确认”直接映射为“第三条消息完成”，也不能用一张跨 channel 的整数表关联所有尝试。

上述函数不处理 multiple，也不处理重连后的并行回调。若要扩展，应维护 channel 内尚未确认的序号集合，按确认范围更新对应尝试，再保留每条已经关联的退回事实；不能靠扩大一个最大成功数字跳过尚未解释的记录。这里给出的是需要实现的责任，没有声称这段教学函数已经覆盖它。

重试还要区分消息身份和发送尝试身份。同一业务事件换连接重发，可以拥有新的 channel 序号，却不应无理由变成另一个业务事件。本站二〇二六年十月二十一日的CloudEvents 身份去重讨论接收端如何识别重送。本篇的路由判断不能替代那层去重，也不建议把所有未知结果盲目重新生成身份后发送。

没有消费者在线，mandatory 会把消息退回吗？

不会仅仅因为消费者离线就退回。只要消息可以路由到已存在的队列，是否有在线消费者是另一项条件。若业务要求确认某个消费者确实执行了订单，需要消费者侧或业务侧的结果协议，不能把 mandatory 当作在线性检测。

发布确认与消费确认的官方边界说明，两种机制彼此独立、互不感知。发布端的 ACK 可以帮助结束发送尝试，却不会自动携带库存扣减或订单处理结果。对用户显示的“已受理”“已发送”“已处理”应从相应的权威状态取得。

验证计划可以在独立 RabbitMQ 4.1 环境中建立一个已绑定与一个未匹配的 routing key，均使用已存在的交换机。先安装退回处理器并开启确认，再分别发布，保存消息身份、channel 序号、退回内容和确认先后。第二组应观察到退回不会被后来的确认覆盖；再保留队列但关闭消费者，检查发布确认与消费处理的区别。不存在的交换机属于 channel 错误，不能混进无路由对照里。

还应在确认之前切断连接，核对应用是否保留未知结果和后续处理入口。这些检查尚未执行，没有兼容性或投递成功率结论。与事务发件箱的交接责任结合时，先写清每个发送终态对应什么证据，再让工作者据此更新记录；仅凭一个 ACK 布尔值结束交付，会丢掉本来已经可观察的路由失败。
