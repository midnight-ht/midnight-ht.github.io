Bloom filter说用户名已存在，可以直接拒绝注册吗？

用两张期望计数表与确定碰撞模型，决定概率正结果何时需要权威来源确认。

正文

核心要点

  • 假阳性率不等于正结果错误比例。
  • 不可接受误拒绝时精确确认正结果。
  • 负结果不代替原子唯一约束。

如果误拒绝合法名字不可接受，Bloom filter 的正结果就需要精确查询确认。它回答的是“可能已经加入过”，不是“数据库已经证明这个名字被占用”。把正结果直接作为注册拒绝或事件丢弃依据，相当于业务接受了假阳性的代价；这份接受不能由一个很小的 error_rate 自动代签。

假设注册入口在数据库查询前增加过滤器，希望减少读请求。输入名字得到正结果，前端立即显示已占用。这条路径的确省去查询，却也可能拒绝一个从未注册的名字。需要先决定误拒绝是否允许，再谈省多少资源；本文没有连接 Redis 或测量任何延迟。

正结果中的错误比例为什么不是配置值？

Redis 的 BF.RESERVE 命令说明把 error_rate 定义为期望的假阳性概率，并提供容量参数。假阳性针对实际不存在的查询；“所有正结果中有多少是错的”还取决于真实命中的比例。两者的分母不同，不能互换。

给定一万次查询，实际存在一百次、不存在九千九百次。假设不存在查询的假阳性率为百分之一，按期望计数得到九十九次假阳性；真实存在的一百次也回答正，总正结果一百九十九次。因此错误占正结果的九十九除以一百九十九，约百分之四十九点七五，而不是百分之一。

若换一份流量，一万次中九千次确实存在、一千次不存在，在相同假阳性率假设下得到十次假阳性，总正结果九千零十次，错误占正结果约百分之零点一一一。配置相同，正结果的可信程度差别很大。这里是期望计数思想实验，不保证任何有限样本恰好出现这些整数。

下面的完整算术程序尚未运行。预期计数直接写在断言中，不能把实际模拟结果当成指定比例的证明。整数规模选成便于手算，不代表真实注册站点的流量组成。

from fractions import Fraction

def expected_table(present, absent, false_positive_rate):
    fp = absent * false_positive_rate
    tp = Fraction(present)
    return tp, fp, Fraction(absent) - fp, fp / (tp + fp)

assert expected_table(100, 9900, Fraction(1,100)) == (
    Fraction(100), Fraction(99), Fraction(9801), Fraction(99,199)
)
assert expected_table(9000, 1000, Fraction(1,100)) == (
    Fraction(9000), Fraction(10), Fraction(990), Fraction(1,901)
)

官方 Bloom filter 指南确认，未实际加入的项目仍可能出现正结果。该指南开头用“每若干正答有一个错”的概括容易让人误读分母；这里采用命令对假阳性概率的定义，并把每格计数显式写出，不把那句概括作为正结果精确率的保证。

用一个确定碰撞验证误拒绝路径

不需要随机生成百万个用户名才能理解故障。下面的教学位集合固定两次哈希位置：已加入的 a 使用一、三，未加入的 b 也使用一、三，未加入的 c 使用二、三。代码不实现 Redis 哈希算法，也不用于预测 Redis 某个具体字符串会不会碰撞；它只把一个可能的错误输入确定下来。

# Unexecuted collision illustration, not Redis internals.
hash_positions = {'a': (1,3), 'b': (1,3), 'c': (2,3)}
exact = {'a'}
bits = set()
for item in exact:
    bits.update(hash_positions[item])

def may_contain(item):
    return all(bit in bits for bit in hash_positions[item])

assert may_contain('a') is True
assert may_contain('b') is True
assert ('b' in exact) is False
assert may_contain('c') is False

独立结果是 a 正且确实存在，b 正却不存在，c 负且不存在。验收业务处理时，应让 b 走到权威来源确认，而不是止于“重复”分支。若系统明确允许少展示一条推荐，跳过 b 也许可以接受；同样的近似却不能未经批准用于丢弃一条新事件。

二〇二六年十月二十一日的CloudEvents 身份与去重讨论确定身份及业务提交。本题不更换身份键，而是追问：即便键选对，是否允许用概率成员结果代替确切处理记录？唯一事件被假阳性误丢，与重复事件未被拦住，是不同的失败方向。

哪条查询路径真正能够省掉工作？

对于已完整覆盖权威集合的过滤器，负结果可以帮助排除一部分查询，正结果则交给精确存储确认。过滤器带来的节省取决于流量组成、实际假阳性与查询成本，不能从上述计数直接写出固定提速百分比。若多数请求真实命中，很多查询仍需精确确认；减少错误拒绝与减少查询量需要一起评估。

权威存储的拒绝也应具有明确含义。数据库确认名字被占用，可以让用户选择另一个；事件账本确认处理过，可以返回既有结果。过滤器自身只应提供辅助分支，不应凭借一个 true 创建已经完成业务的回执。查询失败时，不能把未知结果伪装成“肯定存在”或“肯定不存在”。

还必须区分数学结构与系统同步。对已加入且仍完整保存的数据，标准 Bloom 结构不会因为哈希碰撞产生假阴性；但应用可能漏更新过滤器、连接错实例，或在重建期间查询不完整集合。BF.EXISTS 的返回说明也把缺失键包含在负结果情形中。因此负结果不能无条件推导当前数据库没有该名字。

二〇二六年十一月八日的Redis 容量驱逐与权威状态处理键丢失的另一条原因。本篇假阳性即使在键完整、同步正确时也存在；修好持久化与容量并不会取消概率误判。两组检查需要保留独立结果。

过滤器回答不存在，能跳过数据库唯一约束吗？

不能。即使过滤器完整同步，检查之后仍可能有并发创建；缺键或重建中的过滤器还可能没有覆盖数据库当前成员。最终创建应由权威层原子约束，客户端不能把一次预查询当作永久预约了名字。

实际验收应分别检查真实存在、确定碰撞、真正不存在、缺键、重建版本及并发创建，并用独立精确集合给出答案。记录假阳性的分母是不存在查询数，同时另外记录正结果精确率。先让每种错误对应一条被允许或被阻止的业务后果，再选择容量、error_rate 和查询优化；这里的程序与数字尚未成为 Redis 运行证据。
