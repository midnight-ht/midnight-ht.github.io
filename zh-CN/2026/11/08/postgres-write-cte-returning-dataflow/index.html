WITH已经更新价格，后面的SELECT为什么仍读到旧值？

用两份完整临时表SQL核对基础表旧价、返回关系新价与审计输入，并界定重叠写入。

正文

核心要点

  • 同句基础表读取与返回关系不同。
  • 从RETURNING交接本次修改值。
  • 零消费行不会阻止数据修改CTE执行。

同一条 WITH 里更新价格，再从基础表读取，不等于执行了两条先后可见的 SQL。在 PostgreSQL 18 的数据修改 CTE 中，子语句与主查询共享快照；要让本次修改后的值进入后续数据处理，应读取修改语句的 RETURNING 关系。把代码排在后面，不会自动建立一次读后写交接。

假设后台要把商品一的价格从一百加到一百一十，同时把新价交给审计。开发者把 UPDATE 放进 changed，主查询却重新 SELECT 原表，结果拿到一百。如果只看 UPDATE 没报错，就可能把旧价写入本应表示本次结果的记录。这里的问题不是事务回滚，而是同一句命令中选择了哪个数据来源。

一份快照里有哪些输出可以读取？

PostgreSQL 18 的 WITH 查询第七点八点四节说明，数据修改子语句与主查询使用相同快照，不能通过目标表看到彼此的修改；RETURNING 数据是它们传递变化的通道。文档给出更新价格后读取基础表与读取返回关系的对照。

这不是说事务里永远看不到自己刚写的值。普通情况下，下一条 SQL 能看到本事务先前修改；本题限定的是一条含数据修改 CTE 的语句内部。二〇二六年十月二十日的Read Committed 快照讨论连续语句的可见性，不能把那个时间顺序直接套给 WITH 的书写顺序。

下面是完整、未执行的隔离库教学输入。临时表在事务里建立，最后回滚；不包含序列、外部函数或触发器。两个商品提供一个受影响和一个不受影响的对照，返回来源名称使相同编号的两份价格可辨认。

BEGIN;
CREATE TEMP TABLE price_probe (
  id integer PRIMARY KEY,
  amount integer NOT NULL
);
INSERT INTO price_probe VALUES (1,100),(2,200);

WITH changed AS (
  UPDATE price_probe SET amount=amount+10
  WHERE id=1
  RETURNING id,amount
)
SELECT 'base' AS source,id,amount FROM price_probe WHERE id=1
UNION ALL
SELECT 'returned',id,amount FROM changed
ORDER BY source;

SELECT id,amount FROM price_probe ORDER BY id;
ROLLBACK;

独立预期：第一份结果包含 base、一、一百，以及 returned、一、一百一十；第二条 SELECT 得到商品一的一百一十和商品二的二百。前两行展示同句不同数据入口，后一次查询展示跨语句的自身写入可见性。它们都不是已经运行的客户端输出，不应用注释伪装实际成功日志。

审计应接哪条数据流？

如果要保存本次实际更新的新价，审计 INSERT 可从 changed 读取明确列出的 id、amount，而不是重新从 price_probe 取一份猜测的新状态。下面给出完整的独立变体，同样未执行，需要在可丢弃环境单独运行，不应直接接在上段已经回滚后的语句中。

BEGIN;
CREATE TEMP TABLE price_probe(id integer PRIMARY KEY, amount integer);
CREATE TEMP TABLE price_audit(id integer, new_amount integer);
INSERT INTO price_probe VALUES (1,100),(2,200);
WITH changed AS (
  UPDATE price_probe SET amount=amount+10 WHERE id=1
  RETURNING id,amount
)
INSERT INTO price_audit(id,new_amount)
SELECT id,amount FROM changed;
SELECT id,new_amount FROM price_audit ORDER BY id;
ROLLBACK;

预期审计只有一行，编号一、新价一百一十；不匹配的商品二不应凭空产生审计。把更新条件改为 id=99 时，changed 没有行，因此审计也没有输入行。需要返回“未找到”“状态冲突”还是允许无操作，应由业务定义，不能为了凑一份审计而用旧对象补出成功结果。

这个写法建立的是同一数据库语句内的值交接。二〇二六年十月十六日的RETURNING 与提交边界提醒，返回值不单独证明显式事务已经提交。审计表写进了事务，也不代表外部消息已经交付；不要把这段 SQL 扩成跨系统原子性的保证。

能否按书写顺序连续修改同一行？

官方文档指出，子语句的实际更新顺序不可预测；同一语句试图两次修改同一行不受支持，不能可靠预测哪次生效。这包括主语句与兄弟 CTE 的重叠修改。把第一段命名为 first、第二段命名为 second，只增加了阅读提示，没有增加数据库执行保证。

若业务需要先更新一行，再基于更新结果执行第二次修改，可以考虑在一个明确事务里使用分别执行的语句，让下一步依据真正取得的状态作判断。仍需处理并发与约束，但至少没有把不受支持的同句重复修改当成顺序脚本。如果一次修改就能形成最终值，也可以先组合表达式，减少对同一目标的反复操作。

不应为不确定写法编造一个固定预期值，再依赖某次实测碰巧吻合。负例的验收目标是识别并拒绝重叠写入设计，而不是寻找一种执行计划让它暂时按期望运行。可通过检查各写入条件和目标身份，把可能相交的行集作为代码审查项。

站内二〇二六年十月二十一日的CTE 物化与过滤下推限定了普通无副作用 SELECT 的优化取舍。MATERIALIZED 或 NOT MATERIALIZED 不是让数据修改 CTE 变成按行号顺序脚本的工具，本题应按数据修改章节的规则判断。

可把零消费者预期写成另一份完整输入，避免只在文字中假设外层没有取数据。主查询返回零行后，第二条查询仍应读到编号一、价格一百一十。再从头初始化，只把更新条件改为编号九十九，第二条查询则应保留一百。两条控制仅改变匹配行条件，分别证明“没有消费”与“没有修改对象”不是同一原因；测试工具不应看到第一次零行就跳过后续查询。执行时仍需保留实际输出，不把这些推演写成测得结果。

BEGIN;
CREATE TEMP TABLE zero_consumer(id integer PRIMARY KEY, amount integer);
INSERT INTO zero_consumer VALUES (1,100);
WITH changed AS (
  UPDATE zero_consumer SET amount=amount+10 WHERE id=1
  RETURNING id,amount
)
SELECT id,amount FROM changed WHERE false;
SELECT id,amount FROM zero_consumer ORDER BY id;
ROLLBACK;

外层查询不读取 changed，更新还会执行吗？

会。数据修改 CTE 执行一次且执行完成，不由外层是否消费返回行决定。不能把普通 SELECT CTE 按需读取的直觉带进来，也不能指望外层 LIMIT 零或返回零行就阻止内部写入。

拟议负例可从原价一百重新建表，执行含 UPDATE 的 CTE，但让主 SELECT 使用 WHERE false。即使客户端收到零行，也应检查下一条查询中价格已为一百一十。这个用例尚未运行，执行前必须确认在隔离库。正式验收应同时保留基础表入口、返回关系入口、下一语句、零修改行和零消费行的预期；每一项都指向一个不同的误判，而不是只给某条 SQL 贴“事务正确”的标签。
