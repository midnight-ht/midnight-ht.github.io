把PostgreSQL逻辑迁移验收拆成行、结构和下一次写入

PostgreSQL 18逻辑订阅追平不涵盖DDL、序列状态与大对象。用完整只读盘点和独立数值对照划清读副本与写入切换的验收条件。

正文

核心要点

  • 表内identity值复制不等于序列分配状态同步。
  • DDL和大对象需要按逻辑复制范围另作核对。
  • 只读盘点与行数一致都不能单独证明写切换可用。

PostgreSQL 逻辑订阅的表行追平，不足以证明目标库可以接管写入。切换前至少要分别核对表结构、编号分配与复制范围外的对象；这些依赖不由同一个“延迟为零”信号覆盖。

假设两端订单都已有编号一和一百，行数也一致，应用却在新库第一次创建订单时发生冲突。一个可能原因是行里的 identity 值已经复制，而目标序列的分配状态没有同步。本篇固定依据 PostgreSQL 18 文档分析迁移验收，未建立发布订阅、切换流量或修改序列。

行值到达，不代表生成它的状态也到达

PostgreSQL 18 逻辑复制限制明确说明，serial 或 identity 列的表内数据可以复制，序列本身的状态却不复制。订阅库若只读，通常不构成问题；若准备切换为可写库，就需要适当更新序列状态。不能把“列值中已经出现一百”直接解释为“下一次本地分配一定大于一百”。

也不要立刻把解决方案写成对每个序列执行 max(id)+1。实际序列可能有不同步长、缓存、循环、已有分配和其他消费者；旧库仍有写入时，刚算出的边界还会继续变化。本篇的正整数例子只解释一项不充分证据，不提供覆盖所有序列的在线重置脚本。

十八版 pg_sequences 说明还提醒，last_value 是写到磁盘的最后序列值，使用缓存时可以大于实际已经发出的值。它为 NULL 可能是尚未读取、查询者缺少相应权限，或特定未记录日志序列在备用服务器上的条件。看到空值不能未经核对就宣布序列从未使用，也不能把 last_value 原样当成下一次分配值。

结构变化有另一条交接链

同一限制文档说明，DDL 与数据库结构不会随逻辑复制传播。若发布端修改结构后传来的数据不适合订阅端表结构，应用复制会报错，直到订阅端结构更新。许多增加式变更可以先在订阅端应用，避免这个窗口；这不是所有 DDL 都必须反序执行的通用规则。

例如发布端从只有 id 变为 id 加 note，而订阅端还只认 id。旧行曾经追平，不能证明后续带新结构的变化也能应用。迁移方案应记录两边的结构版本、变更顺序和停止后的恢复入口，而不只比较一次行数。本站分阶段上线约束关注单库约束扫描与验证，两阶段名称相近，也不能替两端结构同步作证。

大对象同样应单独盘点。官方限制说明 large objects 不复制。即使表的一列存着某个大对象编号，并且这个普通列值到了目标库，也不能由这个编号证明对应内容已经迁移。这里的大对象是 PostgreSQL 的具体对象类型，不是泛指任何比较大的 text 或 bytea 列；不能误写成“大字段都不支持逻辑复制”。

只读盘点能发现什么，不能证明什么

下面完整 SQL 尚未执行，使用只读事务，不调用 nextval、setval 或任何结构变更。editorial_example 是需要使用者明确选定的练习 schema，不应把这个占位名误当真实应用位置。运行权限、数据库身份与实际连接都需核对；没有查询结果，就不报告某个目标库的状态。

-- Unexecuted PostgreSQL18 read-only inventory. No sequence allocation/reset.
-- Restrict to a schema explicitly selected for the exercise; change name deliberately.
BEGIN READ ONLY;
SELECT current_database(), current_setting('server_version');
SELECT schemaname, sequencename, sequenceowner, start_value, increment_by,
       min_value, max_value, cycle, cache_size, last_value
FROM pg_catalog.pg_sequences
WHERE schemaname = 'editorial_example'
ORDER BY sequencename;
SELECT c.relname, a.attname, a.attnum, a.attidentity,
       pg_catalog.format_type(a.atttypid, a.atttypmod) AS column_type
FROM pg_catalog.pg_attribute a
JOIN pg_catalog.pg_class c ON c.oid = a.attrelid
JOIN pg_catalog.pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'editorial_example'
  AND c.relkind IN ('r','p') AND a.attnum > 0 AND NOT a.attisdropped
ORDER BY c.relname, a.attnum;
SELECT count(*) AS large_objects_seen FROM pg_catalog.pg_largeobject_metadata;
-- An illustrative VALUES case; this does not assert a live sequence next value.
WITH cases(label, rows_equal, allocated_next_candidate, max_id) AS (
 VALUES ('caught_up_but_unsafe', true, 1::bigint, 100::bigint),
        ('candidate_only', true, 101::bigint, 100::bigint)
)
SELECT label, rows_equal,
       allocated_next_candidate > max_id AS clears_this_numeric_example
FROM cases ORDER BY label;
-- Expected: candidate_only true/true; caught_up_but_unsafe true/false.
-- Even candidate_only is NOT a full cutover certificate: increments, writer fencing,
-- cached allocations, cycles, permissions and application behavior remain unverified.
COMMIT;

前半部分盘点序列声明、列定义及大对象元数据数量。pg_attribute 的官方十八分支原始定义说明普通列从正数 attnum 开始，已删除列仍可能保留目录条目，所以查询排除系统列与已删除列。字段类型与 identity 标记有助于对比结构，但这组查询没有完整覆盖权限、扩展、函数或所有依赖，不能单独签署整库迁移验收。

同一官方目录源文件中的 pg_largeobject_metadata 定义区分元数据与实际内容，因此数量相同不证明字节内容或引用完整。序列 last_value 也必须结合前述权限与缓存含义解释。盘点的用途是发现需要进一步核对的对象，而不是用一个 count 给它们颁发完整性证书。

后半部分 VALUES 刻意提供两条独立假设记录。caught_up_but_unsafe 的 rows_equal 为真，候选编号一却不大于已有最大编号一百，因此数值检查为假。candidate_only 的候选一百零一通过这项比较，却仍不证明所有切换条件成立。这两项预期在注释里预先写定，不是复制演练输出，更不是对真实序列的预测。

写入权威切换，需要自己的完成点

如果准备把新库设为写入权威，应先有阻止旧入口继续写入的方案，再确认最终复制进度、序列处理和应用路由。这里的停写或隔离必须覆盖后台任务与其他编号消费者，不能只让前端按钮变灰。如何执行、多久中断及能否回切，都依赖目标系统，不由本篇只读查询保证。

验收也不能只探测一张表。应按已盘点的身份列、独立序列、结构变更和大对象依赖选择代表路径，保存实例、数据库、应用版本与批准的写入范围。检查应用确实写入新权威并能读回关联内容，同时确认旧路径不再继续生成冲突事实。回切若涉及两边都发生写入，必须另有数据处理方案，不能简单把连接地址改回去。

本站UNLOGGED 的备用库限制讨论日志与物理备用库上的内容，本题则关心普通表的逻辑复制合同；两者不能混用。同样，序列空洞解释回滚后不回收编号，也不同于序列状态根本不在逻辑订阅中同步。

订阅库永远只读，还必须把序列推到最新吗？

若没有本地分配编号的路径，序列落后通常不影响只读用途，官方限制文档也保留了这个条件。一旦计划切写，或后台任务在此使用序列，就应重新列入切换要求；过去只读不是未来可写的证明。

拟议演练可以在独立的十八版双实例中复制带 identity 的行，分别核对表值与实际序列状态，再安排受控的增加列顺序对照。切写演练应在明确阻止旧写入后，按计划处理序列并使用授权测试业务验证下一次写入及关联内容。本文没有执行 SQL 或这些流程，没有零停机、数据完整复制或切换成功结论。需要批准的是各项依赖的实际证据，而非一个曾经显示零的复制延迟数字。
