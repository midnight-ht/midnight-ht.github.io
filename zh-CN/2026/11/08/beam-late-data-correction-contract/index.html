让迟到数据改报表之前，先约定累积结果还是增量

以Apache Beam事件时间窗口的五、十二和错误十七演算迟到修订，区分累积替换与增量叠加，说明触发、保留、定稿和补记的边界。

正文

核心要点

  • 事件时间决定归窗，水位之后同窗到达的元素属于迟到数据。
  • 累计pane应按合同替换旧结果，不能把两版总额直接相加。
  • 超过保留范围的业务更正需要独立的审计与补记流程。

迟到事件可以修订已经输出的窗口，但接收方必须知道收到的是累计版本还是新增贡献。同一个窗口先输出五、再输出十二，若把两版都当增量相加，报表就会得到十七；延长等待时间并不能修复这个写入合同错误。

假设订单按发生时间统计每分钟金额，网络延迟让部分订单晚到。看板希望尽早出数字，也允许两分钟内更正。这里需要共同决定事件归属、何时输出、保留多久，以及输出怎样落到报表。下面依据当前 Apache Beam 编程指南设计一份合同，示例没有运行 Beam SDK、TestStream 或任何 runner。

水位描述进展，不负责选择接收方的写法

Apache Beam 编程指南的窗口与迟到数据说明区分事件时间与处理时间。前者来自元素时间戳，后者是处理系统的时钟；事件不保证按发生顺序到达。窗口按事件时间分配，水位表达系统对输入进展的判断。水位经过某窗口末尾后，再到达且属于该窗口的元素被视为迟到。

这不是“服务器时间到整分，就永久证明数据完整”。水位由数据源及流水线决定，不能把指南里的简化延迟举例当成所有来源的固定计算公式。一个十点零一分收到、发生在十点零零分四十秒的订单，仍可能属于上一分钟；把到达时间直接覆盖事件时间，会改变统计问题本身。

同一指南的触发器章节说明，默认窗口配置不允许迟到，允许迟到需要设置保留范围，并由适合的触发器输出相关结果。只把 allowed lateness 改成正数，却没有核对触发器是否还会响应，不能向报表方承诺一定收到更正。实施时应固定 SDK 与 runner 版本，检查它们对所用策略的实际支持；当前指南页面本身不是某个运行环境的验收回执。

两种 pane，要求两种接收合同

Beam 把窗口每次触发输出的内容称为 pane。其累积模式保留此前已经输出的元素，后一次结果是同窗口截至当时的累计值；丢弃模式在每次触发后不再把那些元素放进下一 pane。是否累计不只是内存选项，它决定接收方应该替换还是叠加。

教学窗口是从第零秒到第六十秒之前，金额单位统一为整数分。先有事件 a，时间十秒、金额二；再有 b，时间三十秒、金额三。水位到六十一秒时，首次总额是五。随后 c 到达，事件时间四十秒、金额七，仍属于原窗，但相对水位已经迟到。若允许迟到一百二十秒并响应这条元素，累计结果应为十二；若输出的是丢弃模式的新贡献，此次贡献则是七。

所以接收方应在合同里明确：同一窗口及分组键的累计结果是替换旧版本，还是每个 pane 是可以相加的一段增量。仅有窗口起止时间还不够。如果采用增量且投递可能重送，还需稳定的 pane 身份或其他重复处理保护；不应把“丢弃模式”误解成外部数据库天然只写一次。

下面完整的 Python 3 文件只演算累计替换合同。水位和事件都作为明确输入，不根据本机时间猜测；它没有模拟 runner，也不声称复现 Beam 内部触发调度。预期值来自二加三、再加七的独立手算。最后一条事件 d 的金额是十一分；这些金额不是实际订单或实测日志。

"""Unexecuted arithmetic fixture, not Beam SDK/runner validation.
Window [0,60), lateness120; explicit watermark advances are inputs.
Output policy is accumulating replacement; expiry threshold is watermark>180.
"""
inputs = [('event', 10, 2), ('event', 30, 3), ('watermark', 61),
          ('event', 40, 7), ('watermark', 181), ('event', 50, 11)]
def evaluate(events):
    watermark = -1
    total = 0
    emitted = []
    rejected = []
    on_time_fired = False
    for event in events:
        if event[0] == 'watermark':
            watermark = event[1]
            if watermark > 60 and not on_time_fired:
                emitted.append(total)
                on_time_fired = True
        else:
            _, timestamp, value = event
            if not 0 <= timestamp < 60:
                raise ValueError('Fixture only owns one window')
            if watermark > 180:
                rejected.append(value)
                continue
            total += value
            if on_time_fired:
                emitted.append(total)
    return emitted, rejected
expected = ([5, 12], [11])  # 2+3; then2+3+7; never add5+12.
if __name__ == '__main__':
    assert evaluate(inputs) == expected
    print(evaluate(inputs))

事件 d 的时间戳是第五十秒。轨迹先把水位推进到一百八十一秒，已经越过窗口末尾加一百二十秒的保留范围；教学合同便把 d 放进超期处理集合。它不宣称真实 runner 必然把元素写到一个名为 rejected 的外部渠道，真实超期记录如何收集需要实现和验证。

先确认报表要的是快数，还是不可变结算

近实时看板可以按窗口和分组键保存累计版本，界面标出仍可修订的阶段。后到十二替换五，最终为十二。若接收方执行加法，五加十二得到十七，就是一个具体的重复统计错误；即使每个事件在流水线中只处理一次，接收合同不匹配仍然能制造它。

不可变结算则要明确何时定稿，以及定稿后发现的旧业务事实怎样处理。无限增加允许迟到会增加状态保留责任，却不会让不受控来源承诺永远没有更晚事件。允许早出结果、暂存窗口和后续更正，是用延迟与成本换取一种可解释的完整度，而非消除全部不确定性。

本站二〇二六年十月二十一日的CQRS 读侧确认也使用“水位”一词，但那里关心的是相关修订已经连续应用。本篇事件时间水位表达输入进展，不能把一个最大的订单版本号直接拿来关闭时间窗口。名称相同不建立可替换的语义。

迟到期限过了，业务还能补记这张订单吗？

可以另走有审计身份的重算或调整流程，但不能假设流窗口仍保留着可直接修订的状态。应给补记关联原始订单、原统计窗口和修订原因，让下游区分重放一段历史与追加一次调整。它是新的业务合同，不是把已经回收的窗口自动叫醒。

例如 d 在本例中没有进入累计十二，业务却确认它确实应计入该期。可以重新计算该期并发布新版本，或者按既定规则生成调整记录。两种方案都要防止原始数据和调整同时重复计入。对外说明“最终值”的接口，应同时约定版本替换与保留旧结果的方式，不能只把未知补成零；有关未知与零的差别，可参看空集合汇总口径。

拟议验证应使用真实 Beam TestStream 输入上述时间戳并显式推进水位，固定窗口、迟到范围、触发器与累积模式。检查每个 pane 的内容，再检查 sink 最终行，而不只数输出次数。对照累计输出五和十二时最终为十二，以及错误累加为十七；另测超期元素、重复投递和不同分组键。保存 SDK、runner、配置与实际输出后，才能报告这些条件下的行为。本文只保留未执行的合同与手算目标。
