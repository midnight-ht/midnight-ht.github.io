removeEventListener 已经运行，为什么旧组件还收到事件？

移除监听器需匹配目标、事件名、回调身份与 capture。完整计数探针区分新函数、错误选项和信号中止，说明重新挂载的生命周期。

正文

核心要点

  • 相同源码的新函数不是原注册回调。
  • options 对象可替换，capture 匹配仍需正确。
  • 已中止信号不可复位，重挂载需新的生命周期。

移除调用可以正常返回，却没有匹配任何注册。先把目标、事件名、回调对象和 capture 对回原注册，再判断组件是否真的退出。清理函数执行过，只证明控制流经过那里，不能证明浏览器找到了要移除的监听器。

DOM Living Standard 的移除算法先读取 capture，再在当前目标的监听列表中匹配类型、回调和 capture。本文依据二〇二六年十一月四日更新的标准，讨论原生 EventTarget；库的订阅函数与 Node EventEmitter 不应直接套用这份合同。

函数写得一样，不是同一个回调对象

假设组件安装窗口监听时写了一个箭头函数，退出时又写一个内容相同的箭头函数。第二次求值创建了另一个对象，源码相似不使它变成原来的注册回调。每次调用 bind 得到的新函数，也有相同身份问题。清理需要保留那次安装实际使用的回调，而不是重新制造一个看起来相同的函数。

目标同样不能省略。注册在 window 上，移除却发给 document，即使其余参数都相同，也是在检查另一份监听列表。真实问题中组件封装可能改变注册目标，单独搜索处理函数定义不够，需要核对实际安装入口。

被动监听诊断提醒过找到真正注册的重要性。本题进一步给出精确配对条件：类型、回调对象和 capture 共同决定这一份注册；passive 影响取消行为，却不是移除时的匹配字段。

options 对象可以换，capture 不能随意换

安装用 capture 为真，退出省略选项，默认的假就不会匹配。反过来，使用一个新对象表达同样的 capture，不要求它与安装时的 options 对象身份相同。不要把“回调必须同一对象”错误推广成“所有参数对象都必须同一引用”。

标准还规定，添加监听器时不会为相同类型、回调和 capture 追加重复注册。因此仅用同一回调再次添加、换一个 passive，并不能假定旧注册已经被改写。需要更改选项时，应明确移除与重新安装，或按所用封装的公开接口处理。

下面完整 JavaScript 探针尚未执行，可在支持这些原生接口的目标浏览器控制台检查。它不依赖真实点击、滚动或服务器，不声称某个组件已经通过卸载验收。三个移除用例分别建立独立目标，signalCounts 另外保存共同生命周期的累计次数。

function removalCase(label, chooseCallback, options) {
  const target = new EventTarget();
  let calls = 0;
  function handler() { calls++; }
  target.addEventListener('probe', handler,
    {capture: true, passive: true});
  target.dispatchEvent(new Event('probe'));
  target.removeEventListener('probe', chooseCallback(handler), options);
  target.dispatchEvent(new Event('probe'));
  return {label, calls};
}
const cases = [
  removalCase('fresh callback', () => () => {}, true),
  removalCase('wrong capture', original => original, false),
  removalCase('matching capture', original => original,
    {capture: true, passive: false})
];
const target = new EventTarget();
const controller = new AbortController();
const signalCounts = [];
let signalCalls = 0;
function signalHandler() { signalCalls++; }
function install() {
  target.addEventListener('probe', signalHandler,
    {signal: controller.signal});
}
function fire() {
  target.dispatchEvent(new Event('probe'));
  signalCounts.push(signalCalls);
}
install();
fire();
controller.abort();
fire();
install();
fire();
console.log({cases, signalCounts});

独立预期是三个移除用例的 calls 依次为二、二、一。每例第一次分发已调用一次；新函数与错误 capture 均留下注册，第二次继续调用；正确 capture 配上新 options 对象则成功移除。信号部分另有累计预期一、一、一。这些是规范推导，不是已取得的输出。

这个反例有意不使用页面移除来判断清理。节点从 DOM 离开与监听器登记属于不同合同；持有引用的代码仍可能对它分发事件。更常见的窗口监听还根本不属于被移除的子节点。只看组件元素消失，无法判断外部长寿目标上的订阅是否退出。

清理测试要先排除别的退出原因

三个匹配用例各自创建目标，让前一个失败移除不会污染下一个预期。每例先分发一次证明安装有效，再尝试移除并分发第二次。若只在退出以后观察零次调用，却没有安装后的正对照，也可能只是监听器从未装上、事件类型写错，或者测试根本没有触发目标。

真实组件还应使用不同记录身份检查重挂载。例如第一次绑定记录甲，退出后第二次绑定记录乙；下一次事件只应影响乙。即使总计只运行一次，若闭包仍捕获甲，数量断言也会误判成功。监听匹配负责是否获得通知，业务身份负责通知作用于谁，这两项必须同时成立。

一组监听器可以由共同的退出信号拥有

标准的 signal 步骤规定，关联信号中止时移除监听；若信号已经中止，则不再添加该监听。信号用例先用新信号注册并分发一次；中止后再分发不增加；复用已中止信号尝试安装后，第三次分发仍不增加。

这适合一个界面同时安装多条、共同结束的原生监听。专用 controller 可以表达这次挂载的所有权，减少分散配对。但不要将同一个 controller 交给无关组件，否则退出其中一个可能让另一个也失去监听。共同退出应当是明确需求，而不是为了少声明变量形成的偶然关联。

每次重新挂载需要新的有效生命周期。AbortSignal 不能复位，旧信号再次传入不会自动开启下一轮。若业务需要仅替换其中一条监听，显式移除可能更清楚；信号分组与精确移除是两个可选工具，不必把所有清理统一改成同一种写法。

同一回调用 capture 真和假各注册一次，移除一份就够吗？

不够。它们是两个不同注册，必须按各自 capture 移除，或事先让两份注册关联同一个专用信号。只成功移除其中一份，不能据此报告整项订阅已经结束。

还要区分停止后续通知与撤销正在运行的工作。中止信号或移除监听不会自动回滚回调先前发送的请求，也不使已经保存的业务状态恢复。若回调启动异步工作，应另有结果归属与退出政策，而不是让监听器清理承担所有取消责任。

待执行验收依次覆盖挂载、退出、重新挂载，分别触发新事件，检查实际回调次数与每次绑定的业务对象。再加入错误目标、新回调、错误 capture 和已中止信号，确认失败分支能被测试看见。集合与节点引用讨论过树连接和对象仍被持有的区别；这里同样不宣称已经做过堆分析或清除了所有泄漏。能证明的是某条具体注册何时不再获得通知，而不是清理函数曾被调用。
