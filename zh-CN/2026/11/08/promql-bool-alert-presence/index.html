PromQL 算出 0，告警为什么仍然 active？

PromQL 的 bool 比较保留零值元素，告警则按结果元素的存在性激活。用两个目标比较三份表达式，分清过滤、等待和缺失。

正文

核心要点

  • 零值元素仍然存在，可以激活对应标签的告警。
  • for 等待持续存在，不能修正错误选择的集合。
  • bool 不会为缺失目标自动生成零值序列。

up == bool 0 可以为正常目标返回数值零，但这条零值序列仍在结果里。直接把它用作 Prometheus 告警表达式，正常目标也可能成为 active。告警判断的是表达式是否产生对应标签的向量元素，不是把样本值再转换一次真假。

比较可以过滤，也可以保留零和一

PromQL 比较运算符文档说明，向量比较默认过滤不满足条件的元素；加上 bool 后，能匹配但比较为假的元素保留为零，真的元素变成一。本文于二〇二六年十一月七日核对 rolling latest 文档，例子只使用浮点样本与标量比较，不扩展到原生直方图的全部运算。

这使得同一个比较可以服务两种用途。状态看板可能需要每个已知目标都有零或一，以便显示正常和异常；故障列表则需要移除正常对象，只保留待处理成员。如果把看板表达式原样搬到告警里，就可能把“展示一个正常状态”变成“存在一个待告警对象”。问题在结果集合的合同，而不是零这个数值被算错。

告警规则说明明确，表达式在某个时点产生一个或多个向量元素时，对应标签集合的告警成为 active。没有 for 时，可以在首次评估进入触发状态；有 for 则需要元素在等待期间持续存在。通知还要经过后续组件，不能从 active 字样直接推导值班人员已经收到消息。

两个输入目标，三个完整结果

下面是未运行的教学输入，没有查询监控服务。假定同一评估时点存在两条浮点 up 样本，标签只列与例子有关的 job 和 instance。实际环境还可能有其他标签，必须在本轮查询里保留，不能把表格里的简写当成完整生产身份。

up{job="demo",instance="a"} = 1
up{job="demo",instance="b"} = 0

目标 a 本次抓取成功，b 本次抓取失败；这只是 up 的采集层信号，不能直接称为用户业务可用性。三份查询分别如下，第二层括号不是额外采集动作。

up{job="demo"} == bool 0
up{job="demo"} == 0
(up{job="demo"} == bool 0) == 1

第一份结果保留 a=0 和 b=1，所以直接用作告警时，两者都具有活动元素。第二份仅保留 b=0，仍然可以对 b 激活，因为元素存在而不要求值非零。第三份先产生零一映射，再用默认比较过滤，最后只保留 b=1。这里的零与一是给定输入下的独立推演，不是已取得的 Prometheus 输出。

可以把前两种意图写成一份完整的教学规则文件。它没有 for、keep_firing_for 或附加标签，方便先看成员选择；生产规则需要另行定义告警身份、持续时间和路由。以下 YAML 未加载到任何服务器。

groups:
  - name: presence-demo
    rules:
      - alert: BoolPresence
        expr: up{job="demo"} == bool 0
      - alert: FilteredFailure
        expr: up{job="demo"} == 0

在给定输入与成功评估的前提下，BoolPresence 对 a、b 都有活动结果；FilteredFailure 只有 b。实际告警标签还包含各自 alertname，不应只数有几个实例而忽略它们属于不同规则。修正目标是让第一份不再错误选择正常对象，不是把第二份的零值强行改为一才能“让它真的告警”。

加上 for 能让正常零值目标自动退出吗？

不能。只要 a 的零值元素持续留在表达式结果里，等待条件仍可能满足。更长的等待会推迟同一个错误集合，而不会把正常成员移除。应先确定哪些标签集合应该进入告警，再为这份集合选择合适的持续时间；持续时间不是修复查询选择错误的办法。

这个追问也改变验证方法。只看告警在等待期间尚未 firing，可能误以为已排除误报；实际上它还处于 pending。应同时保留表达式原始结果、active 或 pending 状态与最终 firing 状态，用同一评估时间解释，不能混用刚修改后的查询和几分钟前的状态截图。

空结果不能用 bool 自动补成零

官方比较条款还指出，没有匹配或涉及不合法直方图比较的元素仍可能没有结果，而不是变成零。本例若不存在目标 c，bool 不会替清单创建 c。希望发现预期目标消失，需要另一份可靠的目标集合和缺失判断；不能让看板中两个已有目标都有数值，就代表采集覆盖完整。

缺失指标文章讨论没有样本与测得零的区别。本题再往后一步：即使已经有一个正确的零值样本，告警也按元素存在性处理它。两层判断不可交换，也不应通过把所有未知补零来统一界面。

该保留哪份表达式

需要零一序列参与展示或算术时，bool 有明确用途；要根据故障条件激活告警时，通常应在最终边界过滤掉不满足的元素。如果先做零一映射再过滤，也应说明为什么需要中间表示，并核对最终输出标签，不必为了形式统一让每个查询都多一层转换。

如果零一映射已经保存成记录规则，例如 demo:target_down:bool，不必为了修正告警删除看板仍需要的中间序列。可以让展示继续读取它，而告警使用 demo:target_down:bool == 1 做最后过滤。假定该记录规则在同一时点确实输出 a=0、b=1，过滤后只剩 b=1；若记录规则没有最新结果，则先查评估状态，不能沿用旧看板值来宣布本轮选择正确。这个设计把中间数据的复用与最终故障成员分开，但仍需核对记录规则实际保留的标签，避免两条规则在不同维度上比较。

失败还可能来自标签匹配、规则评估错误或规则输出限制。规则超限文章说明整条输出被丢弃的情况，与本例保留正常目标恰好相反。诊断时先保存同一时点的输入向量和查询结果，再解释规则状态，避免看到告警消失就归为业务恢复。

拟议验收应覆盖 a=1、b=0，随后让 a 失败、b 恢复，再安排目标缺失。每次分别核对标签、值、结果元素数与规则状态；通知投递另存实际回执。记录 Prometheus 版本与有效规则，不伪造评估日志。本文没有启动服务器、运行 promtool 或验证通知到达，结论限于文档语义和这组完整输入的预期集合。
