把资源身份与访问URL分开，接口换版本时少一份歧义

按Google AIP-122区分局部ID、相对和完整资源名及访问URI，用父级冲突、版本映射与调用者别名说明长期引用应携带的范围。

正文

核心要点

  • 局部ID需要明确父级与所属API范围。
  • 资源身份与访问版本、端点应按合同分别表达。
  • 查找别名解析后应返回并保存规范资源名。

资源的长期引用应和某次访问它的 URL 分开约定。一个对象可以通过不同版本或入口访问；若把完整访问地址默认当成身份，端点迁移就可能被误认为新资源。采用这种设计时，也要把局部编号属于哪个父级、哪个 API 说清楚。

假设两个出版社各有一本局部编号为 b7 的书。跨项目任务只保存 book_id=b7，后续处理器还得从别处补回出版社上下文；若补错，语法正确的请求也会指向另一对象。下面使用 Google AIP-122 的资源命名约定分析引用合同。它是特定 API 设计规范，不是所有 HTTP 服务必须遵守的标准；示例没有请求真实接口。

局部 ID、资源名和访问地址回答不同问题

AIP-122 资源名称指导要求其约定内的资源名在一个 API 中唯一，通常交替使用集合段与资源 ID。publishers/p1/books/b7 与 publishers/p2/books/b7 中，最后一段相同，但完整相对资源名指向两个不同对象。只保留 b7 就丢掉了区分它们所需的范围。

这里的 name 不是用户可以随意修改的展示标题。AIP 还明确区分 display_name 等其他名字，并要求引用已有资源的字段使用相应资源名。接口可以把人看的书名与机器引用分开：书名改成新版说明，不必因此把所有引用当作另一本书。至于资源移动父级如何影响身份，需要该 API 的演进合同，不能从这个简单例子擅自推出。

同一份指导区分相对资源名与 full resource name。前者适合所属 API 已知的场合；存在跨 API 歧义时，完整资源名还带上 service name。访问 URI 则另有协议、API 版本及具体 endpoint。服务名称与访问端点相关，却不是同一项身份字段。

因此，不能编一个“删掉任意 URL 的 v1 段就得到资源名”的通用函数。只有服务合同明确端点、版本及资源模式的对应关系时，才能做这种映射。未知主机、未知前缀应保留为未知或拒绝处理，而不是把看起来相似的字符串合成同一个对象。

先让输入和响应携带足够的范围

一个按 AIP 风格设计的列表请求可以使用 parent=publishers/p1，返回每本书的 name，而不是只返回一个无上下文 book_id。若另一个字段引用书架，应按该资源类型保存对应名称，不把整份书架对象嵌进书里当永久快照。对象嵌入还涉及独立生命周期和权限，不能只因为少调用一次接口就忽略。

这不是要求旧系统无条件换字段。单一服务里已经有明确且稳定的 ID 范围，调用方也不会跨父级传递时，继续使用局部 ID 可能更简单。关键是哪些上下文由字段携带、哪些由接口保证，不能靠每个调用者记住一份未声明的元组。如果引用需要进入通用日志、任务队列和跨服务字段，显式范围通常更容易复核。

下面完整、未执行的 Python 3 文件固定两个允许的版本入口，只认已列出的两本教学资源。代码不是通用 URL 规范化器，也不做对象授权。预期是两条明确映射的版本 URI得到同一个完整资源名，而两个父级的 b7 仍不相同。

"""Unexecuted local mapping fixture, not a universal URL normalizer or auth check.
Service/endpoint/version bindings are explicitly declared and cannot be inferred.
"""
from urllib.parse import urlsplit
resource = 'publishers/p1/books/b7'
other_resource = 'publishers/p2/books/b7'
SERVICE = 'library.example'
allowed = {
 (SERVICE, '/v1/'): SERVICE,
 (SERVICE, '/v2/'): SERVICE,
}
def resolve_declared_uri(uri):
    parts = urlsplit(uri)
    if parts.scheme != 'https' or parts.query or parts.fragment or parts.username:
        raise ValueError('Not an allowed fixture URI')
    for (endpoint, prefix), service in allowed.items():
        if parts.netloc == endpoint and parts.path.startswith(prefix):
            relative = parts.path[len(prefix):]
            if relative not in {resource, other_resource}:
                raise ValueError('Unknown fixture resource')
            return '//' + service + '/' + relative
    raise ValueError('Unknown endpoint/version mapping')
uris = ['https://library.example/v1/' + resource,
        'https://library.example/v2/' + resource]
expected = '//library.example/publishers/p1/books/b7'
if __name__ == '__main__':
    assert resource != other_resource
    assert [resolve_declared_uri(u) for u in uris] == [expected, expected]
    aliases_by_caller = {'u42': {'users/me': 'users/u42'},
                         'u99': {'users/me': 'users/u99'}}
    saved = aliases_by_caller['u42']['users/me']
    assert saved == 'users/u42'
    assert saved != aliases_by_caller['u99']['users/me']
    print(expected, saved)

允许表承担了这里真正的语义：这两个入口属于同一 service，并对应同一份资源数据。示例没有发现这个事实，而是把它作为输入合同写定。对另一个 API，v2 可能有不同数据或完全不同的迁移策略，不能套用这份表的结果。

这也决定了日志字段的用途。访问日志可以保留实际 endpoint 与版本，业务引用则保留规范资源名；两者关联起来，既能调查某次请求走了哪里，又不把换入口当成新对象。资源名公开可见也不授予权限，本站对象级授权解释了为何身份复杂度与访问许可必须分别判断。

查找别名要在返回时变成规范身份

AIP-122 允许 users/me 这类便捷别名，但要求返回数据使用 canonical resource name。me 依赖调用者；代码中 u42 的别名解析为 users/u42，另一个调用者则解析为 users/u99。若把 me 原样存进共享任务，下一次执行时就可能引用另一个人。

所以教学示例保存解析后的 users/u42，而不是保存这次请求的拼写。这个结果也不是认证证据：实际服务仍须根据当前调用者、授权和资源状态决定是否允许解析与访问。别名解析解决指向谁，不解决谁有权做什么。

有关“范围加局部 ID”的事件场景，可参考CloudEvents source 与 id。那里的对象是事件身份，本篇是长期资源引用与访问 URI，不能直接把资源命名规则当事件去重算法，或把一次发送尝试当资源生命周期。

服务换成区域或 mTLS 入口，完整资源名要跟着改吗？

按 AIP-122，同一服务可以有区域、mTLS 或私有访问入口，而完整资源名保持不变。客户端仍要知道入口映射与访问条件；不能看到一个新主机，就自行推测它与旧服务共享身份和权限。

例如业务字段已经引用某个规范资源名，连接配置随后改到批准的私有入口。引用字段不必仅因端点变化而重写，实际请求仍需选择正确地址、证书与访问规则。这里没有配置私有网络或证书，源文档的命名约定也不替真实连通性与授权验收作证。

版本信息也应按实际页面核对。该 AIP 页面的表头 Updated 仍写二〇一九年，实质变更记录则包含二〇二五年三月十日移除不鼓励 UUID 用户 ID 的指导。本文不把表头当成最后一次语义修订，也不声称该规范禁止 UUID。选取字符串形状前，应阅读当前完整条款，而非复制一个旧摘要。

拟议验收应检查两父级同局部 ID 不碰撞、已声明的两版本映射不增加资源身份、别名响应使用规范名，以及未知 endpoint 被拒绝。再用真实客户端和服务端验证字段、权限及错误路径。本文仅提供教学映射与独立预期，没有 API 兼容性、迁移成功或线上授权通过记录。
