stopPropagation 调过了，为什么同一按钮的另一个回调还在跑？

同节点后继监听与跨节点传播需要分别判断。用三条自定义事件预期轨迹，区分即时停止、默认取消与已完成副作用。

正文

核心要点

  • 同节点普通监听序列与后续节点分发分别判断。
  • 即时停止不撤销先前处理器的副作用。
  • 合成事件轨迹不替代真实输入与默认动作验收。

同一按钮注册两个非捕获监听器，第一处阻止传播，第二处仍可能执行。先区分当前监听序列与后续节点，才能决定该拦哪一层。这项传播控制不表示“这次事件的其余代码全部停止”，也不会把先前已经完成的动作撤销。

DOM Living Standard 的事件接口算法规定，stopPropagation 设置传播停止标志；stopImmediatePropagation 还会设置即时停止标志。当前核对的标准更新于二〇二六年十一月四日，下面讨论普通原生 DOM 分发，不把框架的合成事件层直接视为同一套注册。

当前监听序列与下一个节点是两件事

假设按钮内注册了组件处理器，页面又在同一按钮上注册一个统计处理器，父容器还使用事件委托。组件处理器调用 stopPropagation，可以使事件不再继续到后续的父级冒泡调用，但它没有让当前普通监听器序列立即结束。因此页面的同节点处理器仍能运行。

标准内部调用算法在调用监听器后检查即时停止标志，设置了才中断这个循环。两项方法差别就在这里。不能只看到日志来自同一个事件对象，就认定所有回调都属于同一个可随意撤销的动作。

注册顺序也进入合同。本文限定同一目标上的两个非捕获监听器按先后注册、没有在分发中修改注册。先运行者可以影响后继，后运行者不能回到过去。真实界面若有捕获监听、监听器增删或影子树，应先还原实际调用位置，不能直接把本例的三个名称套到全部阶段。

被动监听与默认取消已经区分传播和取消。本题新增的是当前节点内部谁还会得到调用：即使没有任何默认动作，同节点第二处回调仍值得单独解释。

把三种预期序列完整列出来

下面完整 HTML 尚未执行。它使用自定义 probe 事件，没有网络、保存或按钮点击默认动作；三轮都创建新事件，避免前一轮标志影响后一轮。页面按钮只是一个清楚的目标节点，不把脚本分发当作真实用户点击。

<!doctype html>
<meta charset="utf-8"><title>Listener trace</title>
<div id="parent"><button id="probe" type="button">Probe</button></div>
<pre id="log"></pre>
<script>
const [container, button, output] = ['parent', 'probe', 'log'].map(
  id => document.getElementById(id));
let mode = 'none';
let trace = [];
const registrations = [
  [button, event => {
    trace.push('first');
    if (mode === 'stop') event.stopPropagation();
    if (mode === 'immediate') event.stopImmediatePropagation();
  }],
  [button, () => trace.push('second')],
  [container, () => trace.push('parent')]
];
for (const [owner, handler] of registrations) {
  owner.addEventListener('probe', handler);
}
const rows = [];
for (mode of ['none', 'stop', 'immediate']) {
  trace = [];
  const event = new Event('probe', {bubbles: true, cancelable: true});
  const returned = button.dispatchEvent(event);
  rows.push({mode, trace: [...trace], returned,
    canceled: event.defaultPrevented});
}
output.textContent = JSON.stringify(rows, null, 2);
</script>

独立预期是：none 顺序为 first、second、parent；stop 为 first、second；immediate 只有 first。三个返回值都应为真，defaultPrevented 都为假。这来自两类停止标志与取消标志分开的规则，不是捕获的浏览器输出。

dispatchEvent 的返回规则与取消状态有关，不报告“还有多少处理器运行”。所以返回真不能证明父级也收到了事件；同样，父级没有出现也不能证明默认动作已经被取消。本例没有取消调用，正适合把这两种错误推论排除在外。

用动作所有权区分两种重复

再看一个未运行的对照：第一处监听只记录统计，第二处负责保存，两处日志都是必要的；即时停止会把正常保存一起压掉。若第一处与第二处都负责同一次保存，则真正问题是动作被两个入口共同拥有。两者虽然都显示两行日志，正确修复恰好不同，不能用回调数量直接决定拦截强度。

登记表因此同时列出目标与处理器，并按数组顺序完成安装。评审者可以先验证同节点两条记录的顺序，再检查父级那条登记，而不用从散落的调用猜来源。将保存入口集中以后，统计仍可观察事件，父级仍可按协议路由；是否要阻止后继，需要再由明确的界面行为决定。这份表没有重命名或隐藏原生接口，注册仍由完整 addEventListener 调用完成。

强拦截之前，先确认谁拥有动作

如果需求仅是卡片里的独立按钮不触发父卡片跳转，传播边界可能符合意图。但父级跳转也可以先检查实际命中的动作元素，再决定是否执行，避免让整个页面依赖后代处处拦截。选择哪种方式，要看组件是否公开了清楚的事件协议、父级是否拥有路由规则。

若同节点有第三方监听器，即时停止可能使埋点、辅助交互或另一个组件的清理缺席。它不认识哪个回调重要，只会按分发规则停止后继。不能因为接口被调用两次，就不调查注册来源而统一加上更强方法；重复保存可能来自重复安装，也可能来自两个本来不同的入口。

更直接的修复通常是让业务动作有一个明确入口，其他处理器只表达自己的职责。如果统计只是观察，应避免让它再次发起保存。如果组件反复挂载产生旧监听器，应解决注册生命周期；压制后继只能掩盖某次分发，不能让不该存在的注册消失。

祖先捕获监听已经执行，即时停止能撤回它吗？

不能。它控制之后的分发，不回滚已经发生的调用或副作用。祖先捕获早于目标普通监听器执行时，即使目标随后即时停止，先前发出的请求也不会因此自动取消。请求是否可取消、服务器是否已经提交，需要另外的业务合同。

这个条件也说明测试应保留处理器名称、节点与阶段，而不只记录总调用次数。同样三个回调，如果顺序不同，拦截能控制的对象就不同。把执行点移到另一个阶段可能改变现象，但也可能阻止原本应有的输入处理，应以明确的动作资格决定，而不是追求日志最短。

分发状态的寿命解释过 currentTarget 只描述当前调用。排障时可在同步回调记录它与 eventPhase，把同节点、祖先和结束后的观察分开；不应在下一任务读到空值，就补造一个节点身份来解释先前调用。

待执行验证先核对三条自定义序列，再按实际界面记录注册选项和真实输入。随后加入祖先捕获处理作为新的对照，并检查它已执行的动作是否被错误描述成撤销。本文没有浏览器或设备运行记录；交付标准是每个应执行、应被阻止以及已经无法撤回的处理器，都能指出具体位置与原因。
