旧刷新令牌已经失效，为什么还要撤销新的？

用三步状态演算区分拒绝旧刷新令牌与撤销活动令牌，说明合法并发、丢失响应、公共客户端选择和访问令牌边界。

正文

核心要点

  • 轮换需要保留新旧值的授权关系，重用检测不能识别哪一方是攻击者。
  • 合法客户端也会因并发或未知刷新结果重复提交旧值。
  • 撤销刷新能力与已经签发的访问令牌失效需要分别核对。

刷新令牌轮换不只是替换一段字符串。旧值被再次使用时，服务器无法辨认是哪一方重用了它，因此需要处理同一授权关系下的当前刷新令牌。只拒绝旧值，可能仍把续期权留给最先拿到新值的一方。

拒绝旧值和终止授权续期是两件事

RFC 9700 的刷新令牌条款描述了这项取舍：每次刷新签发新刷新令牌，令旧值失效，同时保留它们之间的关系。如果被盗令牌后来被攻击者和合法客户端分别使用，总会有一方提交已经失效的值。服务器据此发现重用，却不能判断哪一方才是攻击者，于是撤销活动刷新令牌，代价是合法客户端也需要重新取得授权。这里依据的是二〇二五年一月发布的规范，没有对真实身份服务执行续期。

先设想攻击者抢先使用旧值，取得新值；合法客户端随后提交旧值。如果服务器只是返回“旧值无效”，攻击者手上的新值仍可能继续换取访问令牌。把错误请求拒绝掉，不等于终止了这条泄漏后的续期链。反过来，合法客户端先刷新成功，攻击者随后重用旧值，同样会触发这项处置。服务器观察的是令牌关系和使用状态，不能从请求先后顺序直接认定合法身份。

这也解释了为什么不能只保留一个当前值，再把所有旧记录直接丢弃。服务器需要能够把收到的失效值关联到对应授权关系，否则即使知道它不能再用，也未必知道应撤销哪一个当前值。实际存储不一定是逐条明文令牌表；规范允许在受完整性保护的令牌中携带授权关系信息。选择存储形式时，还得考虑泄漏保护、并发裁决和保留期限，不能把下面的纸面表当成完整的令牌存储设计。

用三次提交检查同一条授权关系

下面是未执行的状态演算。F1、R0 和 R1 都只是教学标识，不是可用凭据；授权服务器采用刷新令牌轮换政策，且每一步的状态变更先完成，再进入下一步。访问令牌的具体内容、签发算法与网络响应码不在这张表里。

步骤 提交值与开始状态 独立预期
一 提交 R0；F1 当前值为 R0 接受刷新，发出 R1，令 R0 失效并保留关系
二 再提交 R0；F1 当前值为 R1 拒绝旧值，识别重用，撤销 F1 的活动刷新令牌 R1
三 提交 R1；F1 已被撤销 拒绝续期，要求按服务合同重新授权

预期在实现或调用之前按规范写定。第二步不能只看返回错误就宣布通过；还需要在获准的隔离接口中核对活动刷新状态，并用第三步确认 R1 确实不能继续续期。测试身份与授权关系应独立于真实用户，报告只保存匿名关联标识、步骤与结果，不复制刷新令牌正文。这里没有真实请求、服务器状态查询或通过记录。

一个有诊断意义的反例是：第二步正确拒绝 R0，第三步却仍能用 R1 成功刷新。这说明失效值检查存在，但重用后的活动值处置没有按这份轮换合同完成。另一个反例是：所有未知字符串都让 F1 被撤销，那可能把无法归属的输入错误关联到了当前授权。测试应另设一个不属于 F1 的无效值，确认它不会凭空变成这个令牌族的重用证据。

状态变更还必须考虑竞争。若两个请求都在提交前读到“R0 当前有效”，之后各自签发不同后继值，系统就不能仅靠一张顺序表声称正确。需要数据库事务、条件更新或其他能裁决同一个旧值使用权的措施，并记录竞争结果。本文没有给出并发安全实现，也不把某种数据库锁写成规范唯一要求；真正的验收目标是只能按约定产生一个可解释的后继关系。

合法客户端也会提交旧值

两个浏览器请求同时发现访问令牌过期，分别启动续期，就可能发生这种情况。第一份响应保存了 R1，第二个请求仍携带 R0。这不证明发生盗取；它说明合法并发也能生成与重用相同的服务器输入。客户端可把一次续期作为共享中的单一任务，让等待者复用结果，并把新的访问令牌与刷新令牌一致地保存。多标签页、多进程或多设备是否共享同一份刷新凭据，需要先查客户端架构，不能以单个函数里的互斥锁代表全部竞争已消失。

客户端串行化也不应被宣传为服务器可以省略重用检测的理由。恶意请求不会遵守客户端的锁，服务器仍需自己的原子接受规则。反之，为了掩盖并发退出而私自接受所有旧值，会改变泄漏检测的效果。若提供方确有重用宽限或恢复政策，应按它公布的条件测试；不能凭一篇通用文章给任何服务增加固定秒数的宽限窗口。

刷新响应丢失后，客户端能直接重试旧值吗？

不能无条件重试。服务器可能已经轮换；先按提供方公布的恢复合同处理未知结果，否则旧值重用可能撤销当前令牌，客户端需重新授权。连接超时只说明客户端不知道结果，不能证明令牌端点没有提交变更。

这条追问增加的是保存与恢复顺序。假设服务器已从 R0 换到 R1，响应却没有到达，客户端仍只有 R0；它没有可靠依据自行构造 R1。此时应保留“续期结果未知”，进入提供方支持的恢复或重新授权，而不是无限重发旧值。本站的请求重试与业务幂等讨论解释未知结果为什么需要自己的合同，但不代表 OAuth 令牌端点自动支持文章中的业务幂等方案。

轮换不是唯一方法，也不撤销所有既有事实

RFC 9700 要求授权服务器为公共客户端使用发送方约束或轮换来检测刷新令牌重放。它不是要求每个客户端只能采用轮换。发送方约束需要客户端实例持有相应的密码学材料，部署与恢复成本应另行评估；无法保管长期秘密的公共客户端，也不能靠填一个客户端标识就完成这项约束。授权码兑换阶段的PKCE 与 API 授权边界是相邻问题，不能代替这里的刷新令牌处置。

最后还要分别核对已发出的访问令牌。撤销刷新令牌停止后续续期，并不在所有令牌格式、缓存与资源服务器中立刻撤回已经签发的访问权限。访问令牌的期限、内省或撤销传播各有合同。密码修改、授权服务器登出等安全事件可以成为自动撤销刷新令牌的理由，但规范的“可以”不是所有提供方已经这样实现的证明。验收应记录本服务确切采用哪种政策，再把失效旧值、识别重用、撤销活动值、后续访问四项结果分别查清。
