为事件调查和采集排障分别选日志时间

Timestamp 与 ObservedTimestamp 分别属于源事件和采集观察。三条完整记录说明单时间出口的选择、缺失来源和跨时钟差值边界。

正文

核心要点

  • 事件调查与采集排障应分别说明使用哪个时间字段。
  • 单时间出口可按建议回退，但缺失的事件时间仍然未知。
  • 跨时钟的两字段差值不能直接归为网络延迟。

调查事件发生窗口，应先看已知的源事件时间；调查采集器何时见到记录，则看观察时间。OpenTelemetry 的 Timestamp 和 ObservedTimestamp 分别表达这两件事。保留两个字段以后，还要核对查询与界面实际用了哪一个，不能把刚到达的日志直接写进“刚刚发生”的事故叙述。

时间单位相同，读的却不是同一只钟

OpenTelemetry 日志数据模型把 Timestamp 定义为事件发生时、由源端时钟测得的时间；源时间未知时可以缺省。ObservedTimestamp 则记录采集系统观察事件的时点，使用观察方的时钟。本文于二〇二六年十一月七日核对的规范为一点六十二，日志模型状态标为 Stable，不代表某个 SDK 或后端已经正确完成字段映射。

对于直接通过 OpenTelemetry 产生的事件，观察时间通常在生成时设置，与事件时间相同。对于从外部文件等来源采集的事件，观察时间是 OpenTelemetry 代码见到它的时间。不能把第二种语义一概叫作“最终数据库入库时间”：记录随后还可能经历队列、导出和存储，那些阶段需要自己的证据。

假设应用上午写下一条错误，采集器下午才读取文件。事故调查按事件时点搜索，才能先找到它所属的发生窗口；采集排障按观察时点搜索，才会看见下午的读取活动。如果后端只展示观察时间，这条旧错误会显得刚发生。这里是未运行的假设，并没有某条真实生产日志或事故可供归因。

三条记录，明确选值和不能选出的信息

下面的完整本地示例未执行，保存为 timestamp_probe.py 后只需标准库 Python。数字是纪元附近的假设整数纳秒，刻意便于独立计算；它不是 OTLP JSON 报文，不能把字段写法直接当成线缆编码。每条记录的 id 只用于教学身份，不是规范要求字段。

records = [
    {"id": "late", "Timestamp": 1000000000,
     "ObservedTimestamp": 6000000000},
    {"id": "unknown", "ObservedTimestamp": 7000000000},
    {"id": "skew", "Timestamp": 9000000000,
     "ObservedTimestamp": 8000000000},
]

def one_timestamp(record):
    if "Timestamp" in record:
        return record["Timestamp"], "event"
    if "ObservedTimestamp" in record:
        return record["ObservedTimestamp"], "observed-fallback"
    return None, "unknown"

expected = [
    (1000000000, "event"),
    (7000000000, "observed-fallback"),
    (9000000000, "event"),
]
assert [one_timestamp(item) for item in records] == expected

同一规范的 ObservedTimestamp 条款建议，转换到只支持一个时间戳的格式时，有 Timestamp 就优先使用它，否则使用 ObservedTimestamp。函数表达这份选择，并带回选择来源；它没有补造缺失的事件时间。预期列表由明确输入独立给定，没有把函数输出复制回去当正确答案。

late 选出一秒的事件时点，其原始观察减事件差为五秒；unknown 选出七秒的观察替代值，差值无法计算；skew 选出九秒的事件时点，原始差为负一秒。这三项是纸面预期，不是运行结果。函数没有做时间字符串解析、时区推断或纳秒范围校验，不能把它外推成完整日志转换器。

差五秒为什么不能直接叫网络延迟

两个字段可能来自不同机器的时钟。差值可以包含源文件积压、采集周期、进程暂停、传输，以及时钟偏差。即使算术得到正五秒，也不能只凭两个字段把五秒全部归给网络；得到负数，也不必先认定记录顺序被程序改坏。应先检查源时钟与观察时钟的同步条件、字段读取位置和单位转换。

如果希望测量某段传输，应在该段明确起止观测点、身份和可比较的时钟依据。现有字段可以提供调查线索，却没有自动覆盖这份测量合同。把负值钳成零会让图表好看，却抹去时钟或映射异常；若展示层确实需要特殊处理，应保留原值与说明，不能把处理后的数叫作真实耗时。

还有一种常见误用是按观察时间排序后推断事件因果。缓冲、并发和重放都可能改变到达顺序；源时间也可能因时钟偏差不具备跨机器严格顺序。事故叙述需要请求、任务或其他可信身份连接事件，不能因为两条记录在图上靠得很近，就宣布前者导致后者。

只有 ObservedTimestamp，能把它补成事件时间吗？

可以按单时间出口的建议使用它作为替代值，但不能因此声称源事件时间已知。若界面展示七秒，应标明它来自观察字段；查询要恢复真实事件窗口时，这条记录仍缺少那个证据。把替代值再写回 Timestamp，会让后续使用者看不出最初缺失，制造不该有的确定性。

这条追问决定转换时保留什么。目标后端若允许额外属性，可以保存字段来源或原始值；若完全只有一个时间字段，就应在接口合同和导出记录里说明损失。具体存放方式取决于后端，并非本文发明一项通用属性标准。缺失两者的记录也不应无声填入当前时间后冒充原始事实。

字段正确，查询仍可能选错

采集转换保留两个字段，而默认搜索只按观察时间筛选，仍可能找不到上午的错误。验收应读取真实后端的过滤条件与展示列，分别核对事件窗口和观察窗口，不只检查导出 JSON 里两个键都存在。若有保留或重放政策，也要说明旧事件会在哪个窗口出现。

日志严重性文章区分源文本与统一比较数值；日志链路关联文章区分标识存在与完整链路可见。双时间同样要求字段语义、转换实现与后端使用各自有证据。字段名看起来正确，不会替最后的查询作决定。

拟议验证使用已知事件时间、缺失事件时间、延迟观察和时钟偏差四类输入，保存源记录、转换后的两字段、采集器版本与出口选择来源。再到后端检查同一身份在两个查询窗口中的结果。本文没有启动采集器、导出日志或测量延迟；先确认每份记录的时间是谁观察的，再把它写进事件经过。
