隐藏表格行后，nth-child 条纹为什么还是断着的？

隐藏行仍可能参与结构奇偶计数。完整四行样本对照外部筛选与 nth-child 的 of 集合，给出匹配名单、状态切换与兼容分支的验收条件。

正文

核心要点

  • 外部筛选不会重新定义 nth-child 的编号集合。
  • of 子句执行显式选择器，不检测所有不可见状态。
  • 按匹配身份验收，并单独覆盖不支持语法的分支。

隐藏一行会改变可见布局，却不自动把它移出兄弟序号。要按保留记录重新排奇偶，需要把筛选条件放进计数集合。nth-child 外面的类或属性条件，与写在 of 子句里的同样条件，回答的是不同的匹配问题。

Selectors Level 4 的 nth-child 定义规定，在匹配指定选择器集合的元素兄弟中按一开始编号；不写 of 时默认考虑全部元素兄弟。当前原文为二〇二六年一月二十二日的工作草案。标准定义与目标浏览器支持是两项证据，不能看到规范存在就省略兼容检查。

看不见，不代表离开结构计数

假设表格有四条记录，第二条设置 hidden。页面只呈现第一、第三、第四条，但它们在完整元素序列中的编号仍是一、三、四。对奇数编号着色，第一和第三条都会命中，于是可见的前两行得到相同底色。

问题不一定出在颜色声明被覆盖。先检查选择器匹配了谁，再检查获胜的样式。层叠层优先级讨论的是已经匹配的声明之间谁获胜；给当前条纹规则加权重，不能改变 nth-child 原本数了哪些兄弟。

换成 nth-of-type 也不会理解业务含义。它按相同元素类型编号，若数据行、隐藏行和说明行都是 tr，仍属于同一类型序列。类型选择适合不同标签混排的部分需求，不能代替“只数当前记录”或“排除显式隐藏项”的筛选合同。

先数后筛，与先筛后数

外部写 tr:not([hidden]):nth-child(odd)，仍先按完整元素兄弟的位置判断奇数，再要求当前元素是没有 hidden 的 tr。把条件移入 :nth-child(odd of :not([hidden]))，编号集合才变成没有 hidden 属性的元素兄弟。两者可能有相同权重，却匹配不同对象；原文也用重要列表项和隐藏表格行说明这个区别。

这份条件是属性合同，不是通用可见性判断。某行被别处的 display 样式隐藏、被遮罩挡住或透明度变零，只要没有 hidden 属性，就仍符合 not([hidden])。产品若用业务类表示当前筛选，应把同一明确状态放进 of 集合，或者直接由筛选后的数据生成条纹。

下面完整 HTML 尚未执行，没有浏览器截图或性能结果。它保留四行的明确身份，先检查语法支持，再决定是否查询带 of 的选择器；不支持时报告缺少能力，不让备用分支仍执行同一条会出错的查询。

<!doctype html>
<meta charset="utf-8"><title>Filtered row indexing</title>
<style>
[hidden] { display: none !important; }
@supports selector(:nth-child(odd of :not([hidden]))) {
  #rows > :nth-child(odd of :not([hidden])) { background: #e0e7ff; }
}
</style>
<table><tbody id="rows">
<tr id="r1"><td>One</td></tr>
<tr id="r2" hidden><td>Two</td></tr>
<tr id="r3"><td>Three</td></tr>
<tr id="r4"><td>Four</td></tr>
</tbody></table><pre id="out"></pre>
<script>
const rows = document.getElementById('rows');
const ids = selector => [...rows.querySelectorAll(selector)].map(n => n.id);
const report = {outside: ids(':scope > tr:not([hidden]):nth-child(odd)')};
if (CSS.supports('selector(:nth-child(odd of :not([hidden])))')) {
  report.inside = ids(':scope > :nth-child(odd of :not([hidden]))');
} else {
  report.inside = 'syntax unsupported; no DOM query attempted';
}
document.getElementById('out').textContent = JSON.stringify(report, null, 2);
</script>

独立预期先从纸面序列推导：完整 r1、r2、r3、r4 中奇数为 r1、r3；排除 hidden 后，序列是 r1、r3、r4，其中奇数为 r1、r4。因此 outside 预期得到前一组，支持语法时 inside 得到后一组。预期不依赖读取背景色，也不是把查询结果再喂回同一查询作答案。

属性切换以后，需要重新取得哪一份结果？

去掉 r2 的 hidden，四行重新进入集合，两种选择器此时都应得到 r1、r3。再次隐藏 r2，of 的新查询应回到 r1、r4。CSS 样式会按当前匹配关系处理，但DOM 对 querySelectorAll 的定义明确返回静态结果；先前保存的成员集合不会因为属性改变就变成另一组成员。

动态与静态集合已解释保存查询结果的边界。本例的 ids 每次都发起新查询，便于检验状态变化；若真实程序缓存了旧 NodeList，不能拿旧结果解释当前条纹。这不是 nth-child 有时不刷新，而是观察通道没有重新查询。

还可以在行间加入空白文本作为对照，元素兄弟编号不应因为格式化换行而增加。加入一条说明 tr 则不同：默认编号会改变；若它也没有 hidden，当前 of 条件仍会把它计入。这时应进一步明确只数记录行，而不是误以为“没有隐藏”与“业务记录”永远等价。

删行与藏行为什么要分别验收？

在原四行样本里，如果不是设置 hidden，而是真正移除第二行，完整元素序列会变成 r1、r3、r4，默认奇数索引也应命中 r1、r4。相同的可见内容，此时两种计数合同恰好给出相同名单；这不能证明它们在隐藏但保留节点时等价。测试只有删除路径，就容易漏掉筛选所用的隐藏路径。

还要覆盖筛选结果为空以及只剩一条记录。空集合没有条纹目标；唯一保留项的集合位置是一，即使它在原表中排第四，也应属于筛选后奇数项。这个反例把业务筛选与原始顺序分开，能检验渲染层备用类是否仍沿用旧位置。上述名单都由结构推导，没有执行页面操作。

说明行和记录都是 tr，还能只给记录交替着色吗？

可以，但必须把业务记录身份也写进 of 的集合，不能只排除 hidden。另设一份未执行的独立输入：下表五个元素都是 mixed 容器的直接 tr 子元素，按表中顺序排列；record 与 notice 是明确的类名，不从显示文字推断。

元素 id class hidden 属性
m1 record 无
note notice 无
m2 record 有
m3 record 无
m4 record 无

只用 :nth-child(odd of :not([hidden]))，进入编号的是 m1、note、m3、m4，独立预期命中 m1、m3。改为 :nth-child(odd of .record:not([hidden]))，进入编号的是 m1、m3、m4，独立预期命中 m1、m4。说明行不再抢走记录的偶数位置。两组查询都应限定 mixed 的直接子元素，避免把单元格或别的表格纳入。

这项新增条件说明隐藏状态与记录资格要分别表达；不能把没有 hidden 的每一行都默认为记录。它不改变前面原四行样本的预期，也不把假设名单称作浏览器输出。若应用把说明也算作条纹的一部分，则应采用更宽集合；这是产品选择，不由 tr 标签自动决定。

对不支持目标语法的浏览器，可以让渲染层在筛选数据后按位置添加交替类。这样编号由数据渲染合同拥有，新增记录、换页与排序后都要重新计算。不能只在第一次载入时给全部原始数据编号，再期待隐藏部分记录以后类名自动重排。

选择 CSS 或渲染层方案，主要看支持范围、筛选状态由谁维护，以及是否已经有稳定的数据渲染流程。两种方案都应保留明确记录身份作为验收依据；为了视觉相间而打乱真实 DOM 顺序，会把一个装饰问题变成阅读与操作顺序问题。条纹也不应成为唯一的成功、失败或权限提示。

待执行验证先比较两组匹配名单，再覆盖隐藏切换、空白文本、说明行和不支持分支。目标是证明筛选集合、结构位置与当前查询相符，而不只是截到一张看起来间隔着色的图片。本文提供定义、完整样本与独立预期，没有把这些步骤记成已通过的浏览器验收。
