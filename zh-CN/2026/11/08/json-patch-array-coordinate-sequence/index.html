JSON Patch 2026-11-08

勾选B和D，JSON Patch为什么删掉了B和E？

用五项列表解释多选删除的坐标变化，比较倒序、test、版本条件与稳定身份的保护范围。

正文

核心要点

  • 补丁索引针对逐步变化的文档。
  • 倒序删除不保护外部版本竞争。
  • 失败后核对整份资源的持久状态。

原列表是 A、B、C、D、E。想删除 B 和 D，却先删索引一再删索引三，JSON Patch 最后会删掉 B 和 E。每条操作都作用于前一条操作完成后的文档，索引不会一直指向最初选中的记录。根据同一版本的原始位置生成纯删除操作时，可以倒序删除；业务要求按记录身份操作时，应另行提供稳定身份与并发条件。

问题并不在于 JSON 对象字段排列。补丁中的操作数组有顺序，单个操作对象里的 op、path 等成员则没有这种先后意义。客户端若把界面勾选位置直接映射为正序操作，即使服务端完全按标准实现，也会准确执行一份错误的删除意图。

第二个索引究竟指向谁？

RFC 6902 第三节规定，操作按数组顺序逐一应用，产生的文档作为下一操作的目标。第四点二节进一步说明，删除数组成员后，较高索引的元素向左移动。这是具体补丁格式的规则，不能仅凭 HTTP 方法名 PATCH 推断。

下面给出完整、未执行的请求数据。外层文档有一个 items 数组，所有索引从零开始。第一条删除 B 后，数组成为 A、C、D、E；第二条删除当前索引三，也就是 E，得到 A、C、D。预期结果由逐步位置推导，不是接口实际回执。

{
  "document": {"items": ["A", "B", "C", "D", "E"]},
  "patch": [
    {"op": "remove", "path": "/items/1"},
    {"op": "remove", "path": "/items/3"}
  ],
  "expected_stages": [
    {"items": ["A", "C", "D", "E"]},
    {"items": ["A", "C", "D"]}
  ]
}

若只查看补丁里的数字一和三，它们恰好等于原始 B、D 的位置，很容易在评审中放过。更有效的检查是给每条操作标注执行前的完整数组，再圈出目标元素。预期应先独立写为删除哪些记录，不能从已经生成的操作重新算出一个结果，然后把它当成正确答案。

下面的版本先检查 D 再删 D，随后检查 B 再删 B。对应两个删除后的完整数组依次为 A、B、C、E，以及 A、C、E。test 不修改文档；它确认的是操作到这一刻，目标位置仍具有给定值。

[
  {"op": "test", "path": "/items/3", "value": "D"},
  {"op": "remove", "path": "/items/3"},
  {"op": "test", "path": "/items/1", "value": "B"},
  {"op": "remove", "path": "/items/1"}
]

倒序不是任何补丁的通用排序器。如果操作中还包含插入、移动或对同一位置的替换，机械按 path 数字排序可能改变原先意图。RFC 的 move 被定义为先从来源移除，再添加到目标；计算目标时同样要考虑前一步已经改变文档。这里仅给“同一快照上选中多个位置并做删除”提出倒序方案。

test 失败后，前面的修改能留下吗？

RFC 6902 第五节说明错误处理，并援引 HTTP PATCH 的原子要求：补丁中 test 失败时，不应把先前成功的操作作为部分修改留在目标资源。这个承诺属于通过 HTTP PATCH 应用整份补丁的语义，不能推成任意内存库都会自动撤销对输入对象的原地修改。

服务端可以先在隔离副本上应用并校验，再用合适的原子写入保存；也可以采用能够覆盖所需修改的事务。具体设计还要处理版本竞争。如果库已改了共享对象才报错，而持久层又分步保存，标准要求不会替应用恢复现场。验收应检查失败后的真实资源，而不是只断言库抛了异常。

负例可用 stale 文档 X、A、B、C、D、E。上面的首条 test 在索引三读到 C，应失败，资源应保持原来的六项。还应准备“前一条修改成功、后一条 test 失败”的补丁，确认没有留下半份结果。本文没有运行 HTTP 服务、库或数据库，列出的都是待验证输入与独立预期。

站内二〇二六年十月十四日的PUT 与 PATCH 更新合同区分完整替换与修改指令。本题是在已经选定 JSON Patch 后，进一步明确每条位置指令的计算时点。换成 PATCH 并不会替客户端纠正位置。

倒序删除解决不了哪一种竞争？

如果另一位用户在请求到达前把 X 插入列表开头，原来的索引三已不再是 D。倒序只处理同一补丁内部的坐标变化，不保护生成补丁所依据的资源版本。需要整份资源保持原版本时，可结合实际强 ETag 和 If-Match；服务端还必须把版本判断与修改原子地连接起来。

二〇二六年十月九日的条件更新与版本冲突讨论这一写入前提。版本匹配解决外部改动，test 解决操作时的特定值预期，倒序解决一组删除之间的位移。三者的保护范围不同，不能因为其中一个检查通过，就删掉另外两个问题的验收。

当业务语义是“删除编号四十二的成员”，提供按编号寻址的业务动作可能比暴露数组位置更直接。这样仍需对象权限、是否允许删除和并发处置，但客户端不用把一个身份翻译成可能过期的位置。若接口服务的是通用文档编辑器，保留位置补丁也合理，只要版本、操作序列和失败保存规则写清楚。

还有一项输入不能与空列表成功混淆：对五项数组移除索引五，目标不存在，应失败，而不是自动忽略。路径末尾的减号在 add 操作中表示追加，不是任何操作都可用的“最后一项”缩写；remove 使用它也不能据此获得删除末项的含义。验收要明确把不存在位置的删除列为错误，并检查错误发生后原资源未变。若产品需要“无论成员是否存在都算完成”，应另设业务合同，不能偷偷把 JSON Patch 的失败变成成功。

两个条目显示同一个名字，test 还能确认删对人吗？

只测试名字不能。应测试包含稳定标识的对象，或改用以标识寻址的业务动作；显示文字相同不代表记录相同。两个都显示“值班组”的条目可能有不同成员编号，名字相等会让 test 通过，却仍未证明操作对象正确。

正式验收可把显示值换成含 id 的对象，保留同名不同 id、缺失位置和旧版本三种输入。记录期望删除的 id、每一步目标数组、失败后的持久状态及客户端保留的选择。先核对身份，再核对位置，最后核对整份补丁是否一次保存；不要把某次返回成功解释成用户勾选意图已经得到验证。
