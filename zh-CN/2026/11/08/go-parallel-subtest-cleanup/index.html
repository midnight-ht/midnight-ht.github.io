父测试函数返回，不等于整个Go测试已经结束

区分Go父函数返回与测试树完成，以完整预期失败/通过对照核对并行子测试的资源寿命，并限定Setenv的进程范围。

正文

核心要点

  • 直接Run可在孩子调用Parallel时返回，不代表孩子用完资源。
  • 父Cleanup等待当前测试和全部子测试，defer只跟随函数返回。
  • 恢复进程状态不等于隔离，Setenv仍受并行祖先限制。

Go 父测试函数可以已经返回，而它的并行子测试还在等待恢复。defer 跟随前一个时点，父 t.Cleanup 跟随测试与全部孩子完成的时点；共享资源要绑定真正的使用者寿命。只看到 t.Run 返回，就关闭孩子还要使用的资源，可能让失败确定地出现在恢复之后。

函数返回与测试结束是两个边界

Go 语言规范的 defer 条款把延迟调用绑定到外围函数返回前，而不是测试框架管理的整棵测试树。此次核对的规范标识语言版本 go1.27、日期二〇二六年五月二十六日。这个语言规则需要和 testing 的调度规则一起读，不能从函数名叫 Test，就推断它的 return 已经等待所有孩子。

官方子测试说明指出，子测试调用 Parallel 后，执行暂停，直到调用它的父测试函数返回。与此同时，一个测试需要自己的函数返回、所有子测试完成，才算完成。文章发表于二〇一六年十月三日；这里采用其中的调度解释，不照搬旧文里与本题无关的循环变量写法。父函数先返回，孩子才继续，正是 defer 可能先关资源的原因。

直接调用 Run 的等待条件也要说完整。testing 的 Run 与 Cleanup 文档说明，Run 等待子函数返回，或者等到它调用 Parallel 成为并行测试；后者发生时，不表示孩子的业务断言已经运行完。登记的清理函数则在当前测试与全部子测试完成后调用，多个清理按后登记先执行的顺序运行。本次页面标识 go1.27.3、发布于二〇二六年十月二十日，并提示它不是模块最新版本；这不是本机工具链版本探测。

两条子路径保留同一个资源使用要求

下面的完整教学项目未执行。它用本地原子标志表示资源是否已关闭，不创建文件、网络连接或数据库。两个命名子路径共用同一份资源开放断言，唯一政策差别是父函数 defer 或父级登记清理；defer 路径故意违反要求，预期失败，不能为了得到全绿而把断言改为“已经关闭才正确”。

// go.mod
module example.test/cleanupdemo

go 1.19

// cleanup_test.go
package cleanupdemo

import (
    "sync/atomic"
    "testing"
)

func TestResourceLifetime(t *testing.T) {
    cases := []struct {
        name       string
        useCleanup bool
    }{
        {"defer", false},
        {"cleanup", true},
    }
    for _, tc := range cases {
        tc := tc // capture for the declared Go 1.19 language version
        t.Run(tc.name, func(parent *testing.T) {
            var closed, used atomic.Bool
            closeResource := func() {
                closed.Store(true)
            }
            if tc.useCleanup {
                parent.Cleanup(func() {
                    if !used.Load() {
                        parent.Error("child never used resource")
                    }
                    closeResource()
                })
            } else {
                defer closeResource()
            }
            parent.Run("child", func(child *testing.T) {
                child.Parallel()
                if closed.Load() {
                    child.Error("resource closed before child used it")
                }
                used.Store(true)
            })
        })
    }
}

表中 name 与 useCleanup 把失败和成功路径明确命名。tc 在进入闭包前保存本轮副本，以兼容模块声明的 Go 1.19 循环捕获规则。外层 t.Run 的 case 回调没有调用 Parallel，所以它等待本 case 的孩子完成，再进入下一行；里面的 parent.Run 则会在孩子调用 Parallel 时返回。closeResource 保留真实的原子 Store，两个孩子共用同一段开放检查，used 条件仍在正例的父清理中核对。

例子要求至少支持 atomic.Bool 的 Go 版本。sync/atomic 的类型说明标注它自一点一九加入，零值为 false，首次使用后不得复制。这里把关闭标志留在各子路径自己的变量里，没有复制已使用的值。该清理方法本身自一点一四加入，不能因为这个例子用到一点一九的类型，就把一点一九误写成 Cleanup 的引入版本。

把两段保存为同一独立目录中的 go.mod 与 cleanup_test.go，分别运行下面按“顶层测试／case／孩子”选择的候选命令。此处没有运行输出，命令退出值必须在实际执行时立即保存，不能用随后列目录的成功代替测试结果。若一起运行整个项目，第一组仍会令整体失败；那是教学负例的预期，不是第二组一定没有执行。

go test -count=1 -run '^TestResourceLifetime$/^defer$/^child$' -v
go test -count=1 -run '^TestResourceLifetime$/^cleanup$/^child$' -v

第一条独立预期为测试失败：孩子在 Parallel 之后恢复，读取到 closed 为 true，资源开放断言报错。第二条独立预期为通过：孩子读取 false，记录自己已使用资源；父 Cleanup 随后检查 used，再设置关闭标志。两个结果都从相同业务要求和调度条款推导，不从脚本当前输出反填。它们也不证明真实连接关闭、文件耐久性或所有并发问题已经解决。

不用睡眠也能推导的四步顺序

在第一组，孩子到达 Parallel 后暂停，直接 Run 可以返回；父函数随后到达结尾，defer 把标志改为已关闭。孩子恢复后，才执行后面的读取与断言。因此不能通过加一个很短的 sleep 让子测试“抢先用完”，这会把确定的生命周期错误伪装成机器速度问题。

第二组在同样的位置暂停，但父函数返回不会立即执行已登记的父 Cleanup。框架仍等待孩子；孩子完成资源开放检查并设置 used 后，父清理才进入。used 检查让提前清理或孩子根本没到使用位置的情况可见，不能只把“暂时没看到关闭”当成成功。标志使用原子类型，是为了避免教学代码额外引入普通共享布尔值的数据竞争，不代表把任意真实资源改成原子变量就能安全使用。

还要看登记的是哪个 t。若一个资源由父测试准备、供多个兄弟使用，却把关闭登记在某个较短寿命的孩子上，就没有表达父级拥有关系。选择清理位置之前，应列出谁取得资源、哪些子测试会用到它、最后一个使用者何时结束，再把登记绑定到能够覆盖这些人的测试节点。

defer 什么时候仍是合适选择

函数内取得、函数返回前就不再需要的资源，仍可用 defer。另一种合法结构是先用不调用 Parallel 的 group 子测试包含那些并行孩子；官方说明里的外层 Run 会等这组后代完成后返回，组外可以安排收尾。它和直接登记一个会调用 Parallel 的孩子不同，不能把“Run 会等待”压成不带条件的一句话。

若共享资源确实由父测试拥有，父 Cleanup 通常能直接表达这份寿命，减少让读者自己记住分组等待的前提。它负责时点，不负责为外部系统实现删除、权限或重复关闭合同。本站的yield 前准备失败讨论关注资源已创建但清理责任尚未建立的另一窗口；本题中资源与清理都存在，错的是父函数寿命短于并行孩子的使用寿命。

登记清理后，就可以在并行测试中使用 t.Setenv 吗？

不能。Setenv 影响整个进程，官方禁止用于并行测试或具有并行祖先的测试；登记清理负责恢复时点，不提供进程全局状态隔离。需要隔离环境时，可按约束选择单独进程、明确传入配置或调整并行范围。

这条限制也适用于“最后总会恢复，所以中间谁改都没关系”的推断。两个并发使用者在恢复前仍可能读到同一份进程状态，正确收尾不能消除中途相互影响。不要把移到另一个嵌套函数当成已经去掉并行祖先；应沿实际测试树核对。共享状态的fixture 隔离问题与清理结束时点有关，但不是同一项验证。

正式验收保留工具链版本、模块文件、完整源代码、两个独立命令及真实退出结果。实际资源集成还需检查取得、使用、关闭错误与残留状态，不能把原子标志例子的通过扩大为业务资源清理成功。本文没有编译或执行项目；交付的是一个预期失败的反例、一个预期通过的对照，以及为何它们不同的调度依据。
