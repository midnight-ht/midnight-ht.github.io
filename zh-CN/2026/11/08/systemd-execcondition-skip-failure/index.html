ExecCondition 返回 1，systemd 为什么没把服务判失败？

ExecCondition 的默认退出范围区分继续、跳过和失败。用完整教学单元核对三种结果，并保留 SuccessExitStatus 与 ExecStopPost 的影响。

正文

核心要点

  • 默认一至二五四可跳过启动而不标失败，二五五或异常退出失败。
  • SuccessExitStatus 覆盖与有效单元必须一起审查。
  • 主命令未运行时，ExecStopPost 仍需能安全处理收尾。

ExecCondition 返回一，后面的启动命令可以被跳过，而服务不因此被标记为 failed。这是 systemd 条件命令的退出协议，不等于脚本成功执行了业务。维护者需要区分“这次不适用”和“无法完成检查”，否则两种情况都只表现为主进程没有出现。

非零退出为什么不只有失败一种含义

systemd.service 的 ExecCondition 条款说明，条件命令在 ExecStartPre 之前执行。默认情况下，退出码一至二五四使剩余启动命令被跳过，不把单元标为失败；退出二五五或异常结束，例如超时、被信号终止，则按失败处理。零以及匹配 SuccessExitStatus 的退出结果可以继续后面的命令。

本文于二〇二六年十一月七日核对 rolling latest 手册，选项条目标注自版本二四三加入。这不证明读者主机具有当前手册的全部细节，也不证明某份实际配置没有覆盖默认结果。调查时要读取管理器版本、有效单元和附加配置；只看到脚本最后一行 exit 1，还不足以解释整个启动事务。

设想一个只应在存在待处理清单时运行的本地任务。没有待办，可以是正常的不适用；清单文件损坏、无法读取，则可能意味着根本无法判断是否有待办。若脚本把这两种结果都写成一，管理器看到的是同一种跳过协议。失败告警可能看不到后者，业务却仍有未处理工作。问题不是非要把所有空清单都报警，而是先定义谁能够判断“不需要运行”。

一份没有业务副作用的教学单元

下面是未安装、未执行的完整单元文本。它只使用本地 Python 退出和 printf 标记，不读取清单、不连接服务、不修改业务数据。假设隔离 Linux 环境存在对应绝对路径，管理器支持 ExecCondition；在考虑实际启动前，应先用该环境的单元解析器核对路径、参数和版本。本文不提供把它写入系统目录或启动服务的执行步骤。

[Unit]
Description=Condition exit teaching fixture

[Service]
Type=oneshot
ExecCondition=/usr/bin/python3 -c "import sys; sys.exit(1)"
ExecStart=/usr/bin/printf "MAIN-ENTERED\n"
ExecStopPost=/usr/bin/printf "POST-ENTERED\n"

默认的一是本组输入。另存两份独立配置，只把 sys.exit 的参数分别改为零和二五五；其余文本保持一致。示例没有 Restart、SuccessExitStatus、SuccessAction 或 RemainAfterExit，也不声称真实服务应照搬这些选择。三组都只观察命令调度和管理器状态，不生成任何实际报表。

零值组的预期是条件检查允许继续，主命令输出 MAIN-ENTERED；正常 oneshot 生命周期结束时还应观察收尾。退出一的组不进入主命令，不因这个条件结果标记失败，并运行 ExecStopPost。二五五组同样不进入主命令，却会把本轮启动视为失败，也运行收尾。这里是条款推演，没有相应 journal、systemctl 输出或测试通过记录。

不要只记录 Python 自己的退出值。它说明条件命令如何结束，却不是启动作业、单元状态和业务结果的总汇。拟议观察至少包括条件命令结果、MAIN 与 POST 标记、启动作业结果，以及单元的 Result 和 ActiveState。字段实际返回什么，应由那轮环境保留原文，不能为了符合预期先写好一份“成功日志”。

主命令被跳过，ExecStopPost 也一定不会运行吗？

不会有这种保证。手册明确说明，非零或异常退出的 ExecCondition 还会运行 ExecStopPost。收尾逻辑必须能够面对主进程从未启动、某些资源没有创建的状态。若收尾脚本假设主进程必然产生了某个临时目录，再不加判断地清理，跳过启动也可能产生额外错误。

这条追问补充了副作用边界：没有 MAIN 标记，不代表整轮转换没有任何动作。示例的 POST 只输出本地文字；真实 ExecStopPost 可能清理资源或发送消息，仍须有自己的范围、权限和重复调用合同。不能因为主业务被跳过，就自动批准收尾中的外部动作。

当前手册还强调，ExecCondition 的跳过不等同于 Unit 段 Condition 检查未满足。前者属于激活转换的一部分，并可能遵从 SuccessAction；后者阻止激活，不触发相同的成功动作。因而把条件命令搬成另一类配置，不一定只改变写法。应先解释需要哪种生命周期后果，再选择条件表达位置。

谁应该决定一个错误可以变成跳过

条件脚本的作者应给出退出表，让调用者知道哪些输入可以判为不适用，哪些表示检查本身失效。比如已验证为空的待办清单可以跳过；权限拒绝无法读取清单，则应保留错误并按约定失败。具体业务码不是本文替团队指定的，关键是不能在一个广泛 except 后无条件返回一。

如果配置了 SuccessExitStatus，必须重新检查退出表，因为匹配的退出值可以被当成允许继续。维护者若只根据通用范围推演，就可能把本机实际会进入主命令的结果误判为跳过。审查要绑定完整有效配置与脚本版本，而不只是复制一张默认表。

相邻的就绪通知文章讨论主程序何时能报告启动完成；持久定时器文章讨论错过周期后如何补触发。它们都不能替条件脚本决定本轮是否适用，也不能把主命令没运行解释为历史工作已经完成。

怎样保留能让接手者判断的证据

拟议验证在自有隔离环境覆盖零、一、二五五，再按项目真实配置增加覆盖值和异常结束路径。每组保留有效单元、管理器版本、脚本身份、启动结果和两种标记。收尾失败也单独记录，避免后续错误覆盖最初条件。这里只规划观察，不把语法校验当作这些分支已经执行。

若实际目标是恢复未处理工作，还要把清单身份、适用判断与处理结果关联起来。一个未失败的单元，最多说明管理器按当前合同接受了这次转换；它没有证明清单为空或任务已完成。先决定哪些事实足以允许跳过，再让脚本退出与监控依赖同一份可解释协议。
