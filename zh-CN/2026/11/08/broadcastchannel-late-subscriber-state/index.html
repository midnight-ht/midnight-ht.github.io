晚开的标签页，为什么收不到先前的BroadcastChannel消息？

从发送时的接收者选择解释晚加入不重放、发送对象不自回声，并用两页教学示例区分通知与当前状态来源。

正文

核心要点

  • 频道在发送时选择接收对象，不为后来页面重放历史。
  • 发送对象本身不接收自回声，本页更新应有直接路径。
  • 当前状态读取与变化通知需要分别定义并处理初始化窗口。

晚开的标签页收不到先前的 BroadcastChannel 消息，通常不需要先找重连参数。频道在发送时选择已经存在、符合条件的接收对象，并没有为以后出现的页面保留一份历史。多标签页偏好同步应另有当前状态的读取来源，再用广播提醒已打开的页面检查变化。

接收者在哪一刻确定？

HTML Standard 的跨浏览上下文广播算法先检查发送对象能否参与消息，再进行结构化序列化，查找符合条件的频道对象。接收对象需要匹配频道名和存储键。发送对象本身会从接收列表中移除；之后才为各接收者排入异步任务。这里核对的是二〇二六年十一月五日最后修改的规范快照，不是一次浏览器兼容性测试。

这个顺序解释了“后来连接”的限制。假设甲页发送时只有甲自己的频道，接收列表便没有乙。乙一秒以后建立同名频道，也不会加入已经确定的旧列表。再次发送是另一次选择，可以找到此时存在的乙。规范没有在构造频道时读取“最后一条消息”的步骤，因此不应把频道名当作保留主题的名称。

参与条件也不能缩成“浏览器窗口没有关闭”。规范要求相关文档完全活动，工作者则有相应的关闭与可暂停条件。排队以后，接收对象若已经关闭，投递步骤会中止。开发者观察到发送函数正常返回，得到的是本次调用没有同步抛错；它不是各页面均已显示新状态的回执。

用两个页面区分晚加入和投递失败

下面是未运行的本地教学页面。它只写页面日志并发送合成版本号，没有登录、存储或远端请求。把同一文件通过可信本地 HTTP 源提供，在同一浏览器打开两个页面；不要以文件地址的来源行为代替正常站点条件。

<!doctype html>
<meta charset="utf-8">
<button id="send" type="button">Broadcast v2</button>
<pre id="log"></pre>
<script>
const out = document.querySelector('#log');
const channel = new BroadcastChannel('a-nov7-local-demo');
channel.onmessage = event => {
  out.textContent += JSON.stringify(event.data) + '\n';
};
document.querySelector('#send').onclick = () => {
  channel.postMessage({type: 'changed', version: 2});
  out.textContent += 'sent locally\n';
};
addEventListener('pagehide', () => channel.close());
</script>

先只打开甲，按一次发送，再打开乙。按算法独立推演，乙不应因为加入同名频道而得到那条旧消息；它的日志应保持空白。等乙完成加载，再按甲的发送按钮，乙才有机会接收新的对象，日志显示其中的类型与版本。甲自己的那一个频道对象不接收自回声，甲页面里的发送记录来自按钮处理器，不能拿它当作消息事件成功的证据。

这组顺序比同时打开两页、随意点几次更容易判别问题。若第二次乙仍无记录，应分别核对两页实际来源、频道名、对象是否关闭、监听是否已经安装，以及支持环境中的消息事件。记录每个页面加载、发送和接收的先后，而不是只留一张最终截图。以上结果是依据规范给出的预期，本文没有运行这些步骤，也没有伪造浏览器日志。

页面为了演示在离开时关闭频道，没有实现恢复缓存中的页面重新建立订阅。实际产品若支持导航返回，应验证恢复后是否重建对象和监听器；这个极小页面不能直接当作完整的生命周期适配层。保留这项边界，才能解释为什么首次发送可用，却不代表返回页面后仍然可用。

广播提醒变化，谁提供当前值？

假设偏好原先为浅色，甲将它改成深色，乙在之后才打开。若乙的初始化逻辑是建立频道后一直等消息，它可能永远停在默认浅色。更可审查的设计是初始化时读取产品已定义的当前偏好，广播收到变化时重新读取，必要时按版本避免把旧读取结果提交到新界面。这里的读取来源可以是已有的受控存储或服务接口，具体选择取决于偏好要跨标签页、账户还是设备保存。

本文没有提供这样一个真实接口，也不把函数名当成已实现的状态服务。设计审查需要另行说明读取权限、失败反馈和版本规则。如果通知在读取过程中到达，接收端可以记录需要重新读取，或通过实际协议确认读取版本覆盖了通知所指的变化；只说“先读再监听”会在这两个动作之间留下一个需要处理的时间窗口。

反例是把每条广播消息直接作为永久状态。甲关闭以后，任何后来打开的页都无从恢复；另一个同源页面也可能发送相同类型的数据。频道名称既不确认当前业务账户，也不授予修改偏好的权限。只广播必要的变化提示，核对数据形状，再到有明确授权与生命周期的状态来源读取，比在频道中传播整份个人资料更容易控制范围。

如果每条事件都必须在页面重开后补齐，需要设计持久事件记录、消费位置和恢复规则。广播没有这些能力。若任务涉及多个客户端的锁或复杂资源协调，规范也建议考虑共享工作者等更合适的安排；不要仅靠一次“谁先广播”的时序宣布拿到了唯一写入权。已有的标签页会话存储说明讨论的是初始副本与后续独立，不是本题这种实时通知的历史保留。

发送页自己也要更新，应该等自己的 message 事件吗？

不应依赖同一个发送对象收到自回声，算法明确将它排除。先执行本页已定义的状态变更和界面更新，再发送通知，接收事件用于其他频道对象的路径。同一个页面若另建一个符合条件的同名频道，它仍可能收到消息，所以准确的边界是“发送对象”，不是“发送页面”。

把这一区别写进检查能避免两种相反修复：一种为了让甲更新而不停重发，另一种用全局标记跳过甲页面所有消息，连其他合法频道也一并屏蔽。测试应记录对象身份，而不只写标签页名称。消息顺序也不要外推为所有代理间的完整全序；规范只约束部分创建顺序，业务合并仍需自己的版本语义。

验收结束时，分别交付晚加入、已订阅接收、发送对象本地更新、关闭后不再投递以及导航恢复的记录。没有跑过的浏览器和分区条件留待验证，不能用“同源”两个字盖过实现差异。先让新页面能够读取现在的状态，再验证通知怎样使已打开的页面重新检查；这两份结果齐全，才足以支持偏好同步的承诺。
