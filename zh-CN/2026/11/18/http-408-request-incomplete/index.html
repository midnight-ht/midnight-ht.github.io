HTTP 408 和客户端等待超时，是同一件事吗？

用已收到 408 与本地期限耗尽的两种记录，区分服务器收请求和客户端等响应。

正文

核心要点

  • 408 表示接收方未及时收到完整请求
  • 本地期限耗尽不意味着收到远端状态
  • 用实际响应和请求合同决定恢复

文档客户端有两条记录，都显示「请求超时」。第一条保留了服务器返回的 HTTP 408。第二条只有本地等待期限到达，记录里没有 HTTP 状态。这两条的排查方向不同。先保存确实收到的响应，再决定是哪一侧等到了自己的期限。

408 说的是服务器没有收完请求

RFC 9110 将 408 定义为服务器未在自己准备等待的时间内收到完整请求消息。此处服务器在等的是请求从客户端过来。若客户端实际收到了 408，这个响应可以告诉它拒绝来自接收请求的一侧。仅凭状态仍不应猜测哪段数据尚未到齐，或者哪一层设置了具体时限。

客户端的时间预算可能发生在另一段。比如请求发出后，应用等待返回直到本地十五秒期限，最后主动结束等待。若没有收到 HTTP 响应，就没有收到 408 的证据。客户端知道的是自己的期限已用尽，不知道远端完成了多少工作。

很多界面会将这两种状态写成同一句面向用户的文案。诊断记录应保留它们的区别。否则值班工程师会先去查服务端收包窗口，而真正的问题可能是客户端期限过短，或者服务已经接受请求、回传却延迟。先读状态来源可以缩小排查范围，不必靠错误文本猜测时间发生在哪一边。

给两种观察保留不同的记录

用一个假想文档读取来比较。路径不变，客户端使用相同的界面提示。第一条输入由测试明确给出已收到 408，第二条没有任何响应状态，只有本地期限耗尽。第三条有 200 作对照，验证正常响应也保留其实际状态。以下脚本只处理这些固定记录，未发送 HTTP，也未模拟实际计时过程。

import {deepEqual} from 'node:assert/strict';

function record({receivedStatus, deadlineExpired}) {
  if (receivedStatus === 408) return ['http-response', 408];
  if (receivedStatus !== undefined) return ['http-response', receivedStatus];
  if (deadlineExpired) return ['client-deadline', 'remote outcome unknown'];
  return ['pending'];
}

const observations = [
  [{receivedStatus: 408, deadlineExpired: false}, ['http-response', 408]],
  [{deadlineExpired: true}, ['client-deadline', 'remote outcome unknown']],
  [{receivedStatus: 200}, ['http-response', 200]],
];
for (const [input, expected] of observations) deepEqual(record(input), expected);
console.log('Response, client deadline, and successful control passed.');

本机三项断言通过。第一条进入 HTTP 响应类并保留 408。第二条进入客户端期限类并记录远端结果未知。第三条是 HTTP 响应 200。二者都可以对人用一个较简短的提示，但程序的重试分支和运维记录不宜只使用同一个文本字段。

可以给实现写两种独立接口测试。让模拟响应入口确实收到 408 时，确保客户端不把它抹成普通异常。再让本地等待结束时没有任何响应，验证日志没有凭空生成远端状态。若两种用例只能走进同一个结果对象，后续记录即便写上了当前时刻，也看不出哪个观察成立。

对多层入口，记录收到响应的那一层也有价值。客户端直接看到的 408 来自某个接收方，是否由真正的文档源站生成，要看端到端可用证据。不要从状态语义推断源站已经参与。可以保存匹配的请求标识和响应元数据，拿同一时间段的记录核对来源。

接下来如何决定是否再发

RFC 9110 允许客户端重提在途请求。这个许可和应用的重试决定不同。例子讨论的是读取文档，是否还值得重试可结合用户是否仍在当前操作、请求预算及最新结果判断。状态的出现不自动延长客户端总期限，新的尝试也需要记录实际结果。

如果原操作是会产生业务效果的写入，尤其要按已约定的业务合同处理。本地没有响应不能证明操作从未发生。若产品有原操作结果查询或明确的重复提交规则，可以按这个路线恢复。不要把「收到 408」或者「没收到响应」单独写成已经回滚的证明。

对于可重放的读取，可以保留一次真实重试前后的证据。原响应分类、是否还在时间预算内和新请求的结果，都应有可查记录。若再次超时，应按当前剩余期限决定停下，而不是默认每次得到相同文本就重新开启一轮等待。

同一客户端还可能对连接建立、请求发送和响应等待分别设期限。若这个信息已经由库明确提供，可以作为额外字段保存，避免把没有开始发送的请求和已经开始读响应的请求误合并。不过只有本地阶段标记时，仍不要顺手补上远端状态。用例可以分别模拟发起前就到期与发出后没有响应，确认两种情况都能解释清楚。

做服务指标时也为真正返回的 408 和客户端自行结束的请求分别计数。如果先用文案合并，再把总数当作服务端拒收率，客户端配置的调整就可能被误读为服务器故障增长。可以在同一份报告上并排看两个数字，但要标明各自的采集入口和分母，避免拿客户端范围与入口服务器范围作直接比较。

原 HTTP/1.1 连接已经失去请求边界，还能在上面重发吗？

不要在已经不可用的连接上继续发送。这个新条件限定为原连接不再能可靠区分请求边界。RFC 9110 在 408 条款中用 HTTP/1.1 的这种情况举例，说明当当前连接不可用时，重发应使用新连接。连接怎么管理属于实现，不能从示例里的布尔值推断真实连接存活。

若客户端没有证据判断连接状态，可以让 HTTP 实现按其连接生命周期决定。验收时分别记录前一条请求是否已经结束和下一条实际用了哪个连接，别把同一个界面按钮当成已经验证的复用结果。这里没有运行请求或连接池。

如果问题是源站不愿在某条连接上为目标地址给出权威响应，可另读HTTP 421 与更换连接条件。
