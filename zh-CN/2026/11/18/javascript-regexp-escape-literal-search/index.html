搜索 A+B 时，怎样让正则按字面理解加号？

用 A+B 和 AAAB 对照原模式与字面转义，精确检查完整标题的匹配结果。

正文

核心要点

  • 先转义搜索词，再组合外层模式
  • 同时检查正确命中和错误命中
  • 文字搜索与正则模式应有明确入口

文档库支持按完整标题查询。用户输入 A+B，要打开有加号的那份说明，结果列表却只给出 AAAB。标题没有在保存时被改写。查询层将输入直接交给正则构造器，加号便参与模式解释。若搜索界面承诺按普通文字查找，就应在输入进入模式片段的地方保留字面含义。

先把搜索词和模式结构分开

实现想把整条标题都匹配上，于是在搜索词外面放了起点和终点断言。这两部分是开发者有意加入的匹配结构。中间的 A+B 来自搜索框，用户没有要求写正则。对未转义的模式，A 后面的加号表示前一项匹配一次或多次，后面才是 B。因此 AAAB 符合它，带实际加号的 A+B 反而不符合。

ECMAScript 的 RegExp.escape 接收一个普通字符串，返回适合用于正则模式的字面文本片段。把输入交给它，随后仍可在结果外面加上程序选择的起点与终点断言。这样外层模式决定在哪里匹配，搜索词本身则决定找什么字符。若把整个拼好的模式交去转义，原来负责定位的符号也会变成待匹配文本。

处理顺序也关系到回归测试能否说清出错点。先取出用户最终提交的纯文本，再将文本转换成片段，最后和程序负责的模式合成。保留能复现问题的最小查询，不必记录带个人信息的真实标题。只要还看得到输入含加号以及命中的记录，测试就能检查原来的错误有没有回来。

用本地标题分别验证错误命中和正确命中

下列脚本只搜索三条固定标题。第一项用原字符串作为片段，第二项加入字面转义，第三项改用没有标点的 North。三项都用相同的 Unicode 模式标志和同一份标题列表。只改变这一个片段，把错误定位在输入怎样进入正则。

import {deepEqual} from 'node:assert/strict';

const titles = ['A+B', 'AAAB', 'North'];
const plain = 'A+B';

function select(fragment) {
  const pattern = new RegExp('^' + fragment + '$', 'u');
  return titles.filter(title => pattern.test(title));
}

const tests = [
  [plain, ['AAAB']],
  [RegExp.escape(plain), ['A+B']],
  [RegExp.escape('North'), ['North']],
];
for (const [fragment, expected] of tests) {
  deepEqual(select(fragment), expected);
}
console.log('Raw pattern and literal search checks passed.');

本机三条断言通过。直接使用 A+B 只得到 AAAB。转义后只得到 A+B。普通的 North 经过相同转义仍能匹配原来的标题。只测试 North 没办法发现这次问题，因为用户最常输入的字母刚好也能被解释成字面模式。

测试时既要看应该出现的记录，又要看原来会误命中的记录是否退出。假如实现同时返回 A+B 和 AAAB，只核对首项存在不够。检验完整结果也能发现有人换了正则标志、放宽匹配范围以后，把同一搜索意图变成了另一种查询。

例子没有改变大小写选项，也没有处理模糊搜索、别名或文字规范化。产品如果要忽略大小写，应从自己的搜索合同决定规则，再独立验收这种变更。字面匹配只确定符号不会被当作模式指令，并不选择应用应该怎样理解相似文字。

选择是否真的需要组合模式

若产品只需要查找固定子串，普通字符串查找通常就足够，不必为了每个词创建模式。这里之所以保留正则，是因为场景本来设计了独立的模式结构。代码评审可以先问这一层是否确实需要模式，再确认只有明确被设计为模式的内容参与语法解释。

支持正则与文字两种搜索的界面，应让用户知道当前选择哪一种。例如切换到模式查询后，才允许 A+B 表示重复项；切回标题文字，保留输入但改用字面解释。两种模式的结果不同并不构成故障，错误发生在界面与实现对当前解释方式意见不一致时。

如果查询结果稍后还要高亮，显示阶段应继续使用真实文本片段。不要把生成的转义字符串带回输入框，给用户造成标题已被改写的印象。用于模式的字符串和用于显示的字符串可以来自同一个查询，却承担不同作用。本地样本不涉及 HTML 拼装或搜索服务性能。

部署搜索组件前还要检查两边的运行环境。如果服务端和浏览器都在构建模式，某个入口能调用这个函数不代表另一个也能。可先在各支持环境运行同一份三条标题的测试，再为确实需要的环境选择已有兼容实现，或采用产品允许的普通字符串查找。仅凭现在的脚本不能给旧浏览器写出兼容结论。

还有一个可以单独守住的行为：用户用相同词查询两次，第二次应与第一次对同一批标题给出相同结果。本例没有使用全局匹配标志，也没有跨调用复用匹配游标。如果真实搜索需要取一行里的多个位置，应分别检查扫描和筛选函数怎么获取结果，不要在处理字面片段的时候顺便改变重复查询的行为。

为什么结果还会把首字母 A 写成十六进制？

规范会对首个 ASCII 字母或数字使用十六进制转义。原因是这个片段可能被接到一段已有转义的模式后面，直接拼接首字符会让前一个转义有机会继续消费它。规范不只处理加号等常见元字符，还要让片段起点在多种组合里保持清晰边界。

因此通常应断言生成的正则能匹配目标文本，而不是要求它只能在标点前加一根反斜杠。如果项目另外保存模式文本用于审查，要区分这是构造器输入，还是用户看到的搜索词。首字母不同的书写形式不改变原来的匹配字符。

如果问题来自同一个正则对象被连续调用，可另读为什么 lastIndex 会改变校验结果。
