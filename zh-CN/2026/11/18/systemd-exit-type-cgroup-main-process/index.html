主进程退出后，systemd 为什么还认为服务在运行？

用同样的父子进程解释 systemd 的 main 与 cgroup 生命周期，并分开核对应用交付。

正文

核心要点

  • main 模式以确定的主进程为观察点。
  • cgroup 模式会观察仍存活的组成员。
  • 应用输出需要单独核对。

主进程已经退出，systemd 仍可能把服务视为运行中。用 ExitType=cgroup 时，管理器关心的是整个服务控制组是否还有进程存活。默认的 ExitType=main 则以主进程退出为生命周期的终点。查清这项设置，才能解释主进程号与服务状态为什么会给出不同的观察。

例如交付脚本启动一个任务包装器，它派出子进程后很快返回。监控记录了包装器退出，就报告服务的工作已经结束。等到下一步移动输出目录时，真正的执行进程也许正在写。另一个部署却把包装器退出当作服务结束，并清理了组里的进程。相同的进程树可以对应不同的生命周期合同。先用不写业务文件的对照确认管理器在观察谁。

给两份服务相同的进程树

在可丢弃的 Linux 测试机上，用 systemd 250 或更新版本。在 /run/zy18-exit-lab/ 创建 worker.sh。启动子进程后，父脚本等三秒，打印一个退出前的标记再正常返回。子进程若能继续，会在更晚的时点打印另一条标记。父进程退出标记用来找到观察窗口，子进程完成标记则用于第二次核对。

(
  sleep 18
  printf 'zy18-child-complete\n'
) &
printf 'zy18-child-start pid=%s\n' "$!"
sleep 3
printf 'zy18-main-returning\n'
exit 0

把下面的定义保存为 /etc/systemd/system/zy18-exit-main.service。为另一个单元复制相同定义到 zy18-exit-group.service，只将 ExitType=main 改成 ExitType=cgroup。实验用 Type=exec。两份定义用同样的停止清理模式，省得把进程清理配置也当成一项变化。

[Service]
Type=exec
ExitType=main
KillMode=control-group
ExecStart=/bin/sh /run/zy18-exit-lab/worker.sh

在有管理权限的实验终端启动，记录每个单元的属性和日志。下面的等待只试图提供一个可观察的窗口。机器负载异常或记录与标记时间不符时，应读本轮日志确认处在哪个阶段，再另开一趟比较。不要为了凑点位把未退出的主进程当作已经退出。

systemctl daemon-reload
systemctl start zy18-exit-main.service zy18-exit-group.service
sleep 7
systemctl show zy18-exit-main.service zy18-exit-group.service \
  -p Id -p MainPID -p ActiveState -p ControlGroup
sleep 14
for unit in zy18-exit-main.service zy18-exit-group.service; do
  systemctl show "$unit" -p ActiveState
  journalctl -b -u "$unit" --no-pager
done

在父脚本已经正常退出、子进程还没执行完时，预期 main 单元已停止，组内留下的进程会按设置清理。cgroup 单元预期仍然 active，尽管已经没有存活的主进程。可用子进程起始日志记录的 PID 和服务控制组路径确认仍是原来的尝试，接着用完成标记判断子进程有没有走到自己的最后一条语句。等存活的子进程退出后，cgroup 单元也应停止。实验预期只基于手册和这份定义。本文没有运行 Linux 管理器，不能把等待秒数或状态组合当成观测回执。实验结束后在该临时机器停止单元并撤掉文件。

服务还在运行，接手人该继续查什么

对一个有稳定常驻主进程的服务，主进程退出通常就是需要处理的事件。此时可保留默认判据，把健康状态和主进程监督结合起来。如果应用没有能可靠定位的单一主进程，而一组子进程才完整表达它还在工作，cgroup 判据会使管理器覆盖剩余的运行阶段。改配置之前先给剩余的进程确认职责。比如有一个误留的调试进程，它也会延长整个组的存活，活动状态就不能说明应用仍在产生需要的业务输出。

验收时可以把管理器判断和应用完成时间记在一份时间线上。保留本次启动身份、父进程退出记录、子进程完成标记和相关的管理器状态。若本轮开始之前有过旧实例，先界定日志窗口，以免把上次的完成标记抄到现在。出现“状态仍 active，但文件写入早就结束”的问题，应验证哪一个组成员还活着。出现“状态已 inactive，输出缺尾”时，再查子进程是否被清理，以及应用是否为中断提供了可恢复边界。

还有一个可独立检查的反例。假设一份导出必须写完十个分片，管理器最后看到了组内所有进程退出。这只能看到生命周期终点。若一个子进程写到第五个分片后提前返回，生命周期终点并不能告诉读者缺了哪些文件。给交接脚本一份预期清单，在它准备接收输出之前核对实际分片身份和内容。需要时还要检查导出程序的退出原因。这个业务反例未运行，实验只给两个过程标记。

为发布选择 cgroup 时，明确运维动作从哪个事件开始。若清理工具只需要确认没有旧进程持有目录，可以将管理器的停止和组成员核对用作准备信号。若清理改成移动归档，还要独立检查归档已完成。这两个任务看的是同一服务，却可以有不同的成功条件。把实验中的父返回和子完成当作两个不同的时间点，是为了让交接人确定自己真正依赖哪个。

在采用统一 cgroup v2 的机器上，可以用初次日志输出的子进程 PID 读对应的 /proc/PID/cgroup。查询应记录时间，并核对统一层级的路径与单元属性中的 ControlGroup。若进程已经消失，这一个读数不可用；若数字已经被另一个进程重用，单凭号码相同也不能用于证明存活。安排对照时，把子进程执行时间留得足以观察，并保留本轮的日志时间段。这个成员归属查询未实际运行。

能给 Type=oneshot 也用 ExitType=cgroup 吗？

不能。手册对这个组合单独设了限制。若现在的单元类型是 oneshot，而任务需要在主脚本返回后继续用整个进程组来表示运行中，要重新选能表达持续进程生命周期的服务类型，再验启动、完成和停止。主实验统一使用 Type=exec，因此没有覆盖 oneshot。也不要为了让后续任务尽早开始，随意将运行中的工作改成没有生命周期约束的后台活动。
