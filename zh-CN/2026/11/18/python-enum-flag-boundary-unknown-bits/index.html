旧客户端读到新位，EJECT 为什么返回了 int？

用同一个含未知位的整数对照四种策略，核对保留的位与构造结果的类型。

正文

核心要点

  • EJECT 保留原整数但失去标志类型
  • KEEP 同时保留位和标志类型
  • 按本地解释或回传需求决定策略

旧阅读器只认识预览和字幕两项设置。新版本又加了一位，收到的标志整数变成九。程序以为调用枚举构造器总会拿到带 value 属性的对象，下一行却发现手里只是一个 int。这个入口采用了 EJECT，它会在看见未知位时将原数值交还给调用者。

数字保留了，返回类型可能已经改变

假设预览位是一，字幕位是二。整数九表示预览已打开，并带有权重为八的一位。旧客户端可以识别第一位，无法根据旧定义解释八的含义。处理过程需要先决定是拒收、保留原数值、只理解已知部分，还是让结果仍保持枚举身份。

Python 三点一一引入的 FlagBoundary 管理 Flag 及其子类如何处理超出定义范围的值。STRICT 会引发 ValueError。CONFORM 丢掉未知位，在本例中留下值为一的枚举。两种方式都不会让结果继续包含权重为八的位，但前者直接拒绝，后者允许应用处理自己认识的内容。

EJECT 保留九这个整数，失去标志类型。KEEP 同时保留位和标志类型。假如测试只看日志中的数字，这两个分支似乎完全相同。后来调用者读取 value 或需要知道对象是否属于目标枚举时，差异就会显现。若应用希望 EJECT 的结果能沿原数据管线回传，应明确区分原整数和已经解释完成的枚举结果。

固定两项成员，核对两组输入

下面的本地脚本构造四种枚举，成员相同，只改变边界策略。先给同一个已知值一，再给包含未知位的九。结果分别记录被拒绝、普通整数与枚举值。示例的阅读软件和数据交换是假的，断言只依赖 CPython 标准库。

from enum import Flag, STRICT, CONFORM, EJECT, KEEP

members = {"PREVIEW": 1, "CAPTIONS": 2}
policies = (STRICT, CONFORM, EJECT, KEEP)
classes = [Flag(policy.name, members, boundary=policy) for policy in policies]

def inspect(flag, number):
    try:
        result = flag(number)
    except ValueError:
        return ("rejected", None)
    if type(result) is int:
        return ("int", result)
    return ("flag", result.value)

assert [inspect(flag, 1) for flag in classes] == [("flag", 1)] * 4
expected = [("rejected", None), ("flag", 1), ("int", 9), ("flag", 9)]
actual = [inspect(flag, 9) for flag in classes]
assert actual == expected
for policy, result in zip(policies, actual):
    print(policy.name, *result)

本机 CPython 三点一四执行通过。已知值一在四种策略中都是枚举。收到九时，STRICT 拒绝，CONFORM 得到值一的枚举，EJECT 得到普通整数九，KEEP 得到值九的枚举。这里用精确类型判断识别 EJECT，才决定能否访问 value。

回归也要保存阴性路径的原始输入。若程序在构造之前就把九裁成一，四种策略都能通过，测试无法说明旧客户端收到未知位时会选择什么。检查入口真正收到的整数，再核对返回类型与数值，才能把解析决定和上游已经裁剪的结果分开。

从入口职责选择处理动作

如果这个结果只给旧版阅读器决定预览区域是否出现，忽略未识别位可能是明确可接受的行为。保存收到的原值和用于展示的解释值。两组读数分别说明传来了什么，以及旧程序阅读到了什么。不要把界面可以显示当成新位已经得到理解。

读完再写回则是不同的责任。假设用户只想关闭预览，服务端未交给旧版管理的位仍需保留。若把构造后的一当成完整可回传数据，再关闭预览，调用方可能不小心连同八一起从设置中移除。接口需要先定义旧版拥有修改权的位，再用新版本重读回传数据来验收。

对必须理解完整设置的操作，可以选择明确拒绝并告诉用户换用支持该配置的版本。对只负责透传的操作，可以保留原整数，等具有新定义的一侧处理。保留未识别位与认定它代表某个已知能力是两回事。回传保留了一个数字，并没有为它赋予旧版的名称。

需要诊断时可以记录枚举定义版本、策略、原始整数与返回的类型。单独打印九，无法说明当前代码是用 KEEP 构造了枚举，还是经 EJECT 退回了数字。少一个类型读数，开发者解释下一步的属性读取时就容易归错原因。

未来新版本如果真正给权重八的位起了名字，同样的九会成为它能理解的组合。验收应分开构造两份定义，在旧版核对当前策略，在新版核对已识别字段。不能用新版构造成功来替旧版通道判断，也不能把旧版的原因记录带到新定义后继续当作固定结论。

还有一种实际错误来自重复经过不同的处理入口。一次旅程里，阅读页为显示取已知位，保存页却把这一份展示结果当成完整原始值。如果日志没有保留入口和对象用途，就很难发现丢位发生在哪一步。可为这两个数据对象使用不同字段，回传测试单独读取源数据与用户修改范围。

若定义由多个模块共享，建议在回归里保留一个不含未知位的组合值。只检查一能通过，还不能发现字幕位被误删。再用三验证两项已知能力可以一起读取，用九固定新增位的处理。本文脚本只用一作为正对照，组合值可在实际接口验收时再补。

省略 boundary，将 Flag 改成 IntFlag 会怎样？

默认策略会随基类改变。Flag 默认采用 STRICT，按这份旧定义读九会拒绝。IntFlag 默认采用 KEEP，同样的输入会保留未知位与枚举身份。IntFlag 同时是 int 的子类，因此宽泛的整数实例检查可能两边都成立。要确认是纯整数还是标志对象，就按调用方合同检查精确类型或目标枚举身份。

主例的所有类都指定了策略。这一问省略参数，新增的是基类默认的差异。迁移代码时用同一份整数验收保存了哪些位、下游获得哪个类型。仅检查结果打印出来还有九，无法守住两项合同。

如果你在处理数据库中新值何时能被读取，可另看 PostgreSQL 新增枚举值何时在事务中可用。
