另一个 realm 的数组，为什么 instanceof Array 可能是 false？

用相同记录对照不同 JavaScript realm 中的数组，区分 instanceof 原型检查与 Array.isArray 类型判断。

正文

核心要点

  • 跨 realm 数组可能不通过本地 instanceof
  • 普通数组类型可以用 Array.isArray 判断
  • 通过类型检查后还需校验成员

导入工具收到两项数据，调试器展开就是一只数组。类型守卫却说输入无效。同样的两个值由本地代码构造时，又能通过这条守卫。先看做判断的代码是不是在用当前环境的 Array 构造器。从另一个 JavaScript realm 取来的数组可以是普通数组，同时没有继承这一侧的数组原型。

一只数组可以属于不同的创建环境

设想插件和主页面各有一套 JavaScript 内建对象。插件构造自己的数组，回调将它交给主页面。数组所包含的值没有变化。主页面如果执行 instanceof Array，默认比较依赖当前的 Array 构造器，并沿被检查对象的原型链寻找这个构造器的 prototype。另一个环境创建的数组通常会指向那边的 Array.prototype。

因此这个判断在本地样本上为真，在跨环境样本上可以为假。它回答了对象的原型链是否连接到指定构造器的原型，并没有直接问该对象在规范中是不是数组。检查端的构造器引用是一项可变输入，不能因为两个环境都把全局属性叫 Array 就认为它们是同一个对象。

Array.isArray 走另一条规则。它调用规范的 IsArray 检查输入。普通数组具有数组对象的内部身份，跨到另一侧以后仍保有它。这个操作不需要匹配本地数组原型，可以直接回答接口需要的数组类型问题。

另一方面，某个对象即使有数字下标与 length 属性，也不必是普通数组。表单导入器如果本来只收数组，不能为防止跨环境误拒就退回到检查 length。这样会让原本应拒绝的类数组对象进入后续处理。换守卫之前应先写下哪些输入合同需要保留。

对同一批值运行两种判断

下面的本地脚本只用 Node 的独立执行环境求出一只固定数组。被执行的文本是例子写死的数组字面量，不读取插件或用户提交的代码。另建一个本地数组和一个只具有下标、长度的普通对象，用完全相同的两项检查比较。

import {deepEqual} from 'node:assert/strict';
import {runInNewContext} from 'node:vm';

const samples = [
  [['A', 'B'], [true, true]],
  [runInNewContext("['A', 'B']"), [false, true]],
  [{0: 'A', 1: 'B', length: 2}, [false, false]],
];

for (const [value, expected] of samples) {
  deepEqual([value instanceof Array, Array.isArray(value)], expected);
}
console.log('Local, cross-realm, and array-like checks passed.');

本机三组断言通过。本地数组的两项值都为真。独立环境创建的数组在 instanceof 检查里是假，在数组类型检查里是真。普通对象两项都是假。两个数组里的文字完全相同，只有创建环境变化，所以可以把第一项判断的差别放回构造器身份看。

测试不需要把跨环境的值重新转换一遍。如果先生成一个当前环境的新数组再检查，新对象可以通过本地实例判断，却遮住了原来输入的情况。把保护条件写在实际消费的边界，测试也应将未改的对象送进相同入口，才能验收它是否还会被误拒。

实际产品还要决定数据有没有跨过序列化边界。如果浏览器直接交给页面一个来自另一环境的对象，与收到一段 JSON 再在本地解析，是两种不同路径。后者已经在接收处创建新值，不能用它替代前者做回归。本文未运行浏览器或插件，证明来自本地独立执行环境。

数组判定之后，还有哪些合同要检查

通过类型检查只能说明这里收到的是数组。输入内容里是否至少有一行、每项是不是记录、是否有稳定编号，需要分别检查。比如业务要求至少两个可展示的名字，空数组不会因为通过类型守卫就满足规则。把类型检查和逐项检查分开，报错时也更容易指出是整个结构的问题，还是其中一条数据的问题。

如果产品明确接受多种可迭代输入，可以为那个入口设计转换规则。例如对于一个非数组的列表接口，是否允许它返回一次就耗尽的迭代器，需要在消费之前决定。跨环境案例的修复只是保留对普通数组的支持，不能从中推出任何有迭代协议的对象都能提供相同语义。

写运行记录时，可以同时显示类型判断与输入来源，但不要仅靠对象展开猜它来自哪个环境。用可控测试先建两边对象，再检查本地构造器和传入对象的原型身份。若项目自有框架对实例判断做过额外定制，回归也应从实际使用的守卫入口跑，而不是只检验文中普通内建对象。

如果原来的判断还有一层业务意图，也不要直接替换每一处。某个内部缓存可能只接收本模块创建并登记的对象，这个限制比数组类型更窄。应把创建来源的约定单独表达，用数组检查确认数据形态，再按真正的登记信息确认归属。这样既能接收插件合法送来的数组，也不会误以为语法级的数组检查完成了应用自己的成员校验。

Uint8Array 也能按下标读，它能通过数组守卫吗？

不能。这个新条件给入口的是一只类型化数组，而不是主例里的普通数组。它有长度，也可以用数字下标读取字节，但 数组类型检查对它返回假。两者都可按索引读取，不代表它们共享同一个普通数组类型。

若业务确实允许字节数据，给这个入口单独写清楚支持何种表示，再按需要读取或转换。不能只改一条布尔判断就认为下游会按相同行为处理它。对一个普通记录导入器，先明确拒绝字节视图，反而是更容易验证的合同。
