sync.Once 的 f panic 后，为什么第二次 Do 没重跑？

用调用计数、配置状态和新实例对照，看 sync.Once 在 panic 后做了什么，以及上层何时应另做重试。

正文

核心要点

  • 同一个 Once 在首次函数 panic 后不会再次调用传入的函数。
  • 另行核对初始化产物与失败状态。
  • 确需恢复后重试时，由应用维护重试状态。

Go 服务第一次加载本地配置时发生 panic，调用方捕获之后重新执行同一个 sync.Once 的 Do。第二次调用顺利返回，配置却仍然没有写入。这里需要把“这次 Do 已经返回”和“初始化已成功”分开看：第一次调用发生 panic 也会消耗这一个 Once 的执行机会。

恢复 panic 改变的是调用方的控制流

设想初始化函数读取本地配置并把解析后的结构保存到内存。读文件尚未完成就发生 panic，捕获它的调用方选择继续运行。现在已有一份错误记录，没有一份可供业务读取的有效配置。如果调用方立刻以同一个 Once 再调用 Do，即使换了一个简单的初始化函数，后续函数仍不会被调用。把 recover 放在哪并不能撤销 Once 已经记录的这次调用。

Go 的契约针对一个 Once 实例。Do 调用传入函数，只限该实例第一次调用的那次；如果传入函数 panic，Do 把它视为已经返回，后续调用会直接返回。这个实例能帮助多个使用者围绕同一次初始化汇合。它不会保留一个代表业务成功的值，也不会把初始化函数的异常重新传播给后续调用者。若调用端在 Do 之后默认已经有配置，第二次抛错的原因可能是读取未初始化状态，而非初始化函数再跑了一次。

常见的误导证据是只统计 Do 返回次数。首次调用发生了 panic，调用者恢复之后能继续做自己的工作。后续三个调用也可能全部返回，但这四条日志无法说明配置加载过。如果需要判断当前能不能处理请求，应另查加载产物、业务错误或状态字段。这里的延时不是决定条件：文件立即恢复、几秒后恢复或者永远读不到，都不会改变同一实例后面是否再次调用函数。

用另一个函数和另一个实例拆开验证

下面的顺序夹具未在 Go 运行。第一段只包住一次调用，在调用者这一层捕获约定的 panic；之后给原 Once 传入一个不同的函数，让它一旦执行就写入 loaded。再给新建的 Once 传入相同的写入函数，形成不共享状态的控制组。

package main

import "sync"

func firstAttempt(once *sync.Once, attempts *int) (failure any) {
    defer func() { failure = recover() }()
    once.Do(func() {
        *attempts += 1
        panic("temporary config failure")
    })
    return
}

func main() {
    var once, fresh sync.Once
    attempts := 0
    loaded := false
    if firstAttempt(&once, &attempts) != "temporary config failure" {
        panic("first call did not report the expected panic")
    }

    load := func() { loaded = true }
    once.Do(load)
    if attempts != 1 || loaded {
        panic("the original Once should not run load")
    }

    fresh.Do(load)
    if !loaded {
        panic("fresh Once should run load")
    }
}

第一个断言要求确实遇到了准备好的 panic。若初次调用没有跑，或者因为完全不相干的原因抛错，样例会直接停下来。接下来要同时看到 attempts 等于一、loaded 仍为假，才能确认已经尝试过一次，而且后来那个写入函数没有进入。最后 fresh 让同一函数成功写入。这样就不必猜测函数本身是不是空实现，或者正文的状态标志是否根本无法更新。

反过来，若测试只写一次 recover 后再调用 Do，程序没有退出，仍不足以证明重试成功。若它只检查没有再次 panic，也会得到一样的误判。为服务验收加一个实际消费者更稳妥，例如在返回就绪之前明确读到配置版本，并让失败路径报告未加载。这个夹具只推导顺序调用与简单变量变化，没测多个 goroutine 同时进入、线上日志收集或任何 I/O 恢复能力。

选用 Once 前，写清一次意味着什么

允许尝试一次的初始化，可以把持久结果分成加载值和失败状态，等 Do 完成以后再把同样的结果交给后续请求。比如进程必须取得静态配置版本才能接单，初始化失败后就保持不可用并让部署控制器决定是否重启。这种情况下，Do 可以管理一次函数执行，而就绪检查仍由应用从真实状态决定。不要让请求路径因为 Do 返回就直接宣布能读配置。

如果业务要求配置恢复以后在同一进程内重新加载，应另外编写支持失败和重试的状态逻辑。要先决定谁发起下一次、并发调用者怎样等结果、成功以后用哪份配置，以及失败多少次后才向上报告。受控验收至少给出两个条件：初次读取失败并留下错误；下一次在明确恢复之后，消费者能读到新的版本，并且可见的成功次数与应用约定一致。把它化简为每次请求都新建一个 Once，只会丢掉请求之间这份共同初始化的边界。

还能从诊断日志里直接区分“尝试过”和“加载好”两个状态。给真实加载函数记录开始与结束，在调用方分别记录恢复结果和可读版本。这样即使同一服务里有多个互不相干的初始化，也能查到当前失败属于哪一项。若发现最后只有一次函数开始日志、一次初始化错误，却有许多 Do 返回日志，应先检查应用如何解释这几条事件。本站Go AfterFunc 的停止与完成介绍另一种布尔结果和业务完成时刻之间的区别，这里的检查对象是一次初始化的状态。

如果初始化函数内部又调用同一个 Once 的 Do 呢？

这种调用会一直等待。首次 Do 要等它的函数运行完才返回；内部调用又要等这次正在执行的函数结束；两者互相依赖。比如加载器为了读默认配置又调用上层的初始化入口，恰好复用了同一个 Once，恢复 panic 的分支也救不了这次等待。应把真正读配置的过程与控制一次调用的外层入口拆开，避免加载器再回到该入口。上面的程序没有执行这个反例，排查时可直接检查静态调用链与每个 Once 的实例身份。
