CTest 看到进程退出非零，为什么却显示跳过？

用三个独立进程区分 CTest 的通过、跳过和失败，并用单项结果验收真实覆盖。

正文

核心要点

  • 测试进程和 CTest 各有退出值。
  • 绿色汇总可能包含未运行的测试。
  • 按关键用例名称核对真实分类。

测试进程返回非零，CTest 仍可能把这个测试标为跳过。给该测试设置 SKIP_RETURN_CODE 后，进程正常退出并给出指定值时，CTest 会将它分类为未运行。测试命令被调用和测试主体完成验收是两件事。要判断流水线是否真的验证了某项能力，必须读到单项分类。

这个问题会出现在有可选能力的测试矩阵里。比如一组基础构建没有安装模拟器，测试启动后先查找需要的工具，发现前置条件缺席就退出。另一个完整作业本应验证模拟器上的交互。把两条作业的绿色状态放在一起，并不能证明它们都执行了同一断言。应当先让测试程序说出它走了哪条路，再让 CTest 准确传递结果。

代码返回和运行器结果各留一份

创建一个空目录，保存下面的 CMakeLists.txt。这个项目不需要编译器，Unix 风格的本地系统要能找到 sh。三个测试各自退出零、一和七十七，只有 optional 明确登记了跳过值。这个值是示例协议，团队应选择自己的专用返回值并避免同普通失败冲突。

cmake_minimum_required(VERSION 3.20)
project(SkipFixture NONE)
enable_testing()
find_program(SHELL_PROGRAM NAMES sh REQUIRED)

add_test(NAME available COMMAND "${SHELL_PROGRAM}" -c "exit 0")
add_test(NAME broken COMMAND "${SHELL_PROGRAM}" -c "exit 1")
add_test(NAME optional COMMAND "${SHELL_PROGRAM}" -c "exit 77")
set_tests_properties(optional PROPERTIES SKIP_RETURN_CODE 77)

从这个目录运行下列 Shell 脚本，分别收集 CTest 的输出和退出值。测试进程的数值已经直接写在配置里。函数检查的第二个数是运行器自己的退出值，而非进程退出码。把三项分开执行，是为了给每个外层返回值配到唯一测试，避免因为其中一项失败便无法判断另两项发生了什么。

set -eu
work=$(mktemp -d)
trap 'rm -r "$work"' EXIT
ctest --version
cmake -S . -B "$work/build"

probe() {
  status=0
  ctest --test-dir "$work/build" -R "^$1$" --output-on-failure || status=$?
  printf 'case=%s ctest_exit=%s\n' "$1" "$status"
  test "$status" -eq "$2"
}
probe available 0
probe optional 0
probe broken 8

本地 CTest 4.2.3 实跑给出三种单项分类。available 显示 Passed，CTest 退出零。optional 显示 Skipped，随后把它列进未运行清单，CTest 还是退出零。broken 显示 Failed，外层实测退出八。八是这个版本、这组命令的回执，不能当作测试进程本身的退出码，也不把它写成跨版本通用保证。配置已明确 broken 的进程退出一；两条数字同时正确，因为它们来自不同层。

最值得看的是 optional 那次控制。其汇总同样显示百分之百，下面却还有一行 The following tests did not run，列名正是 optional。这个测试没有成功执行它原本要覆盖的行为。它只演示测试进程报告可选前置条件缺席。对于只解析百分比和退出值的收集器，这一份结果会与真正通过混在一起。接入之前用这俩案例检查收集器，再用 broken 确认真实失败继续阻断。

官方文档还给出两条边界。超出 TIMEOUT 的测试仍会失败。段错误、信号中止等系统级异常即使碰巧表现为数值相同，也可能判失败。因此用专用返回值报告明确缺环境，比把任意异常通过外层包装折成跳过更可靠。上面的夹具只执行正常返回分支，未模拟超时或信号。

哪些跳过会让发布验收失效

先按环境决定哪些用例可以缺席。工具不属于基础作业的合同，跳过可以保留成可见记录，不过接手人仍应看到测试名与具体原因。如果模拟器是完整作业的验收前提，该作业出现同一条跳过就说明这次没有得到承诺的验证证据。可在任务准备阶段直接检查工具是否能启动，并在收尾时确认预期测试被执行。环境存在和真实用例通过需要各自的证据。否则安装了模拟器却在测试选择中过滤掉用例，依然会留下假绿灯。

把收集规则拿到一次受控故障里试试。比如在完整作业里故意拿掉一个前置能力标记，让某项开始返回约定的七十七。若收集器只有退出值，任务仍有可能放行。增加按名称的分类断言后，这次应当因缺失预期结果而被标出来。再提供正确的标记和可用环境，直到该项目的真实断言执行并通过。这个交付扩展是验证收集器的方法，本文只运行了三个最小进程，没有运行产品或模拟器。

测试代码也应把七十七限定在清楚的前置条件分支。若先跑功能断言，失败后再用“模拟器不可用”覆盖错误，维护者就拿不到真正的首个故障。把前置能力检查放在行为测试之前，用不同的状态记录异常。评审回执同时列出在基础环境允许跳过的 test 名称和完整环境期待通过的 test 名称，有助于避免默认允许所有可选项缺席。以后交付合同扩展到新架构，只修改实际受影响的能力规则，并用可控的一项缺席检查测试选择是否还正确。

在不同配置间比较时，也要保留本次期望出现的测试名集合。设想同一个用例在基础作业里跳过，在完整作业里应通过，后者却只留下了另一组测试的绿色结果。收集器应对比明确的用例标识，发现该结果缺席后检查测试选择参数与实际测试清单，而不是把缺席当成显式跳过。只有找回预期身份和结果，才能说清楚是环境不足、选择遗漏，还是测试自己遇到了真实故障。此处是日后可加入流水线的核对。

如果测试无法设置专用退出值，只能输出诊断呢？

可以考虑 SKIP_REGULAR_EXPRESSION。它能根据标准输出或标准错误的匹配把该测试分类为跳过，但超时依然失败，系统异常也仍可能失败。另一个独立夹具用一条确定的 UNAVAILABLE: simulator 消息和进程退出一，本地实际得到 Skipped 与 CTest 退出零。这不是把原来七十七换了个数字。接受条件变成了输出证据，同样的退出一也可以是真失败。使用窄且稳定的专用诊断，避免让别的错误恰好匹配宽泛字样。
