收到 HTTP 300，客户端必须跳去某一个地址吗？

对照网页和打印版两条候选，看 300 如何交付选择、何时提供首选地址，以及客户端怎样验收。

正文

核心要点

  • 300 提供具体表示的选择信息
  • 首选地址与候选清单分别核对
  • 自动选择依赖可理解的响应格式

安装说明有在线阅读版和打印版。客户端访问通用入口，收到 HTTP 300 和两条可选地址。处理代码习惯在每个重定向响应中查找一个唯一目的地，找不到就报告接口故障。这里收到的是一份选择清单。要继续操作，可以由用户或者理解这份清单的客户端挑出合适的表示。

通用入口提供选择，每份表示有自己的地址

RFC 9110 用 300 表示目标资源有多种表示，各自有更具体的标识。响应提供这些候选的信息，供接收者选出合适的一种。与先发送偏好、由服务器完成主动协商的交互不同，这里把选择机会留给读到响应的使用者或程序。

例如文档组为同一份安装指南维护一份网页和一份分页 PDF。这两份内容服务于相同任务，但后续操作不同。在线版本适合站内阅读，打印版带纸张尺寸与页码。通用入口可以同时列出两份表示。客户端读到清单后，是否拿打印地址，还取决于用户在做什么。

若服务端自己有首选项，规范建议用 Location 提供那个引用。客户端可以用它自动跳转，却不因此丧失文档约定的其他候选。没有首选的接口可以不给出这个字段。对本例而言，缺少 Location 并不能推翻清单已经交付、且有两条可用路径的事实。

对于本例的 GET，规范建议在内容里给出表示元数据与引用列表。它没有为程序自动选择规定一个统一正文格式。即使客户端认识 300，也要确认收到的媒体类型和接口约定。若返回的是给人读的选择页，程序不能凭状态码把它送给自己只支持 JSON 的解析器。

安装指南的两条候选怎样验收

下列本地夹具假设团队已经约定一种选择清单的数据结构。两条候选各带标签、媒体类型和站内相对地址。函数只在样本清单中按已知类型查找。它不发出 HTTP，不验证服务端响应头，也不代表浏览器确定会自动选择某个版本。

import {deepEqual} from 'node:assert/strict';

const choices = [
  {label: 'Read online', type: 'text/html', uri: '/guides/setup/web'},
  {label: 'Print', type: 'application/pdf', uri: '/guides/setup/print'},
];
const response = {status: 300, choices};

function choose(reply, type) {
  if (reply.status !== 300) return null;
  return reply.choices.find(choice => choice.type === type)?.uri ?? null;
}

const inputs = [
  ['application/pdf', '/guides/setup/print'],
  ['text/html', '/guides/setup/web'],
  ['text/plain', null],
];
for (const [type, expected] of inputs) deepEqual(choose(response, type), expected);
console.log('Both known choices and the missing choice passed.');

本机三个断言通过。请求打印功能对应 PDF，函数得到打印路径。请求在线阅读对应 HTML，得到网页路径。查找一个未提供的纯文本版本则返回空值。这些结果只计算已知清单中的查找，脚本不会沿选中的地址再发第二个请求。

如果产品确需发下一次请求，可以让验收独立核对通用入口、实际选定的候选与返回的文档。例如模拟用户选择打印后，确认它去的是打印版本而非网页；再核对得到的实际表示符合接口的媒体类型和展示约定。第一次响应只能说明选项被公布，不能代替第二次读取的结果。

另外保留一条例子里的缺失分支。当用户找纯文本版时，界面可以显示已有的两种方式，让他重新选择。直接取数组的第一项当默认值，虽然不会报错，却可能把一个阅读工具送到不支持的格式。测试需要断言没有找到指定类型时不会默默改用任意另一项。

让候选列表和请求意图对得上

若团队需要稳定处理这种响应，给每条候选保留可以识别的语义，而不只存一个链接。比如在选择页显示「打印版」，程序合同另提供媒体类型与表示标识。两个客户都能看到选择，可根据各自任务作出决定。固定优先级需要在产品合同里明确，不能靠数组的排序偶然得到。

如果上线时还有一个服务端首选，可安排有首选与无首选的两个验收用例。前者核对偏好地址确实属于当前可用的版本；后者核对客户端仍能在清单里自行选择。不能通过只访问默认版本，就证明其他地址正确或者清单信息完整。

遇到客户声称跳转失败时，可以索取三份独立记录：初次响应是状态加清单还是另有优先地址，客户端为何选中某项，以及再次读取返回了什么。诊断会落在响应缺列表、客户端不会解析、或具体表示不可读中的某一步。把所有情况归为「重定向错误」，会失去恢复方向。

上线前还可以模拟清单指向旧版本的情况。比如打印服务已经切到新版本，通用入口却继续公布旧地址。此时客户端选择逻辑可以完全正确，失效的是维护清单的发布链。记录候选生成时采用的目录版本，再实际读取每个地址，能比重复改变客户端的选择规则更快发现问题。对于被下架的版式，还应检查它已从清单上消失。

对同一资源发 HEAD，还应期待收到清单正文吗？

不应期待正文。这一问改变了请求方法。HEAD 响应不包含内容，300 的候选列表正文建议也明确将 HEAD 排除。只看到状态和响应字段时，不能因没有读到清单就判断可用表示只剩一个，或向用户宣称打印版不存在。

如果客户端真正要向用户展示候选，应走能取得清单的读取合同，例如文档端点已经约定的 GET。将 HEAD 用来读取元数据时，单独记录它能验证哪部分。脚本只对照本地列表，不包含 HEAD 响应或后续选择请求。

若排查的是跟随重定向能否改变请求方法，可另看HTTP 重定向的请求方法合同。
