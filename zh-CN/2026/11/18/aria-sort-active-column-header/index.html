表格换了排序列，为什么旧表头的 aria-sort 要移除？

用名称和数量排序得到不同结果，核对换列后的行顺序、排序方向与旧表头属性。

正文

核心要点

  • 把排序状态放在当前表头
  • 切列时从原表头移除属性
  • 分别核对行顺序与表头状态

库存表原来按产品名称升序。用户改点数量表头，行已经重新排列，名称表头却仍声明自己是升序。开发者如果只看新箭头或第一行数据，容易漏掉这个旧状态。对只允许一列作为当前排序的表格，行顺序、箭头和表头的语义都应跟着同一次操作更新。

负责触发的按钮和表示状态的表头

原生表格里的列标题负责告诉用户这一列是什么。若希望用户改变排序，可以在其中放一只按钮，让鼠标与键盘都从同一入口触发。用 aria-sort 表达该表头的当前排序状态。把属性放到表头，而不是把排序方向想成按钮自己的开关值。

WAI-ARIA 1.2 给这个属性定义了方向与其他排序状态，并建议同一个表或网格一次只给一处表头设置。W3C 的可排序表格示例在切换列时先从原来的表头移掉属性，再设置到新表头。这里采用同样的一列现行规则。列具备排序按钮，不代表它现在就排了序。

如果应用还画一个小三角，当轮到数量列后，旧名称列的三角和语义应该一起退出。箭头可以作为视觉反馈，辅助技术仍需通过结构和状态获取对应信息。这个示例把箭头视为装饰，并使用 aria-hidden 使它不进入按钮名称。按钮名称仍告诉用户这是哪一列。

属性本身不会重排行。先按确定的业务规则生成行顺序，再把同一份排序结果所对应的列和方向呈现出来。仅设置升序属性却没有重排行，和只重排但不更新属性，都会让不同证据互相矛盾。验收需要逐个读取。

选择不会碰巧排成相同顺序的输入

夹具用三个产品 A、B、C，数量为九、二、五。初始按名称升序，行依次为 A、B、C。这样一来，改成数量升序后，预期将明显变化。两列如果碰巧得到相同顺序，是否触发了真正的排序就不能只凭那三行看出来。

<!doctype html>
<meta charset="utf-8">
<title>Sortable stock table</title>
<table id="stock">
  <caption>Stock. Select a column button to sort.</caption>
  <thead><tr>
    <th scope="col" aria-sort="ascending">
      <button type="button">Product <span aria-hidden="true">▲</span></button>
    </th>
    <th scope="col">
      <button type="button">Count <span aria-hidden="true"></span></button>
    </th>
  </tr></thead>
  <tbody>
    <tr><td>A</td><td>9</td></tr>
    <tr><td>B</td><td>2</td></tr>
    <tr><td>C</td><td>5</td></tr>
  </tbody>
</table>
<script>
const table = document.getElementById('stock');
const headers = Array.from(table.tHead.rows[0].cells);
const [body] = table.tBodies;

function sortRows(header, column) {
  const ascending = header.getAttribute('aria-sort') !== 'ascending';
  const read = row => row.cells[column].textContent;
  const rows = Array.from(body.rows);
  rows.sort((a, b) => {
    const order = column === 0
      ? read(a).localeCompare(read(b), 'en')
      : Number(read(a)) - Number(read(b));
    return ascending ? order : -order;
  });
  for (const row of rows) body.append(row);
  for (const cell of headers) {
    cell.removeAttribute('aria-sort');
    const indicator = cell.querySelector('span');
    const arrow = ascending ? '▲' : '▼';
    indicator.textContent = cell === header ? arrow : '';
  }
  header.setAttribute('aria-sort', ascending ? 'ascending' : 'descending');
}

headers.forEach((header, index) => {
  header.querySelector('button').onclick = () => sortRows(header, index);
});
</script>

按一次 Count，预期行变为 B、C、A，活动表头是数量升序，名称表头不再有属性或三角。再按一次 Count，预期顺序为 A、C、B，同一个表头更新为降序。此时没有第二只表头参与声明。按 Product 后又能进入新列的升序路径。这里没有连接库存系统，初始数据是固定的。

这些是代码的预期，不是已观察到的浏览器与读屏表现。正式验收先用键盘到达按钮并激活，再核对行次序、活动表头的属性和可见指示。对辅助技术，另外观察用户能否辨认当前列和方向，具体播报应以产品支持的组合为准。

这个过程还可以检测焦点是否在重排时消失。示例只把现有行移到新的顺序，没有替换头部按钮。若真实应用重建了整个表格，键盘下一次操作可能找不到原入口。即使排序状态正确，也应独立检查是否仍可在同一个表头继续操作。

让新数据和排序状态同时提交

如果排列工作走异步服务，用户点击表示请求发起，还不能证明表格已经更新。可以保留原来的排序状态，让忙碌提示说明更改尚未完成。新行到达之后，再一起换掉顺序、当前列和方向。否则读者可能先听到一套未来状态，却浏览到旧行。

若用户很快先后选了两列，应让显示状态对应当前仍有效的返回。比如先选名称，后选数量，旧名称请求最后才结束。不能仅因为它最后回来就替换数量表头。这个夹具同步操作，不涉及旧响应竞争，但正式组件测试可以人为控制完成顺序来验收。

为回归留下初始与切换后的两份简短记录，包括行的身份与数量、活动表头、方向、可见图标和焦点。仅记录「排序成功」无法检查是哪一列实际改变了视图。检查新属性有值的同时还要查旧属性不存在，才能抓出一处变两处的故障。

对分页结果还要约定排序的范围。若服务端提供整批库存的顺序，点击数量后应在相同规则下选择当前页，再更新表头。若应用只重排已经加载的三行，界面不应让用户以为已经找到整批库存里最少的一项。两种功能可以共用表头状态，但验收样本需有跨页相对次序。

如果还有恢复默认的入口，确认它的名称与结果一致。恢复按产品名称排序，就同时恢复旧列的升序状态和指示。恢复成没有主动排序的原始顺序，则不应保留某个方向。按钮可以一直留在表头上，等待用户下一次选择。

先按数量，同数量再按名称，可以给两列都设置吗？

不应把两处 aria-sort 当成描述排序优先级的方式。这里新增一个条件：有两条记录数量相同，需要名称作为次级比较。表格仍可以在当前主要表头保留本例的排序方向，用说明文字补充「先按数量升序，同数量时按名称升序」。这样用户既知道当前主要方向，也能理解为什么相同数量的行有先后。

加这个规则后，应另造两行数量相同、名称不同的输入。只检验原先九、二、五的三条数据，次级比较根本不会运行。新用例要检查该两行的相对顺序和说明文字，并仍确认没有两个表头同时简单宣称自己是当前排序。

如果排查 JavaScript 排序是否改变源数组，可另看原地排序与不可变输入。
