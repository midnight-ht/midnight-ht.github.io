同一份 Dockerfile，Buildx 默认到底构建哪个阶段？

用 Buildx 查询默认阶段，再分别导出默认和明确目标，确认发布任务真正交付的文件。

正文

核心要点

  • targets 报告可选阶段和默认项。
  • 发布可明确选择交付目标。
  • 实际导出内容需要独立读回。

多阶段 Dockerfile 没传 --target 时，可以先用 docker buildx build --call=targets 查看实际标注的默认阶段。此调用列出可选择的目标。若发布期待另一个阶段，还要显式选它并读回实际导出文件。阶段目录负责回答“会选谁”，制品负责回答“交付了什么”。

一种实在的故障是开发者往 Dockerfile 最后补了一个便于检查的阶段。本地调试更方便，已有发布命令却没写要交付的阶段。发布任务仍能跑完，看输出目录也确实有文件。直到下游找不到运行时入口，团队才想到阶段选择可能变化。可以在不运行镜像、不上传的样例上验证这个路径。

两个独立阶段，各提供一份不同文件

在空目录保存以下 Dockerfile。两个阶段都从 scratch 开始，没有相互复制的依赖。另创建 runtime.txt 与 inspection.txt，内容分别是一行 runtime-marker 和一行 inspection-marker。把这两份输入和 Dockerfile 放进同一构建上下文。明确知道哪份内容只由哪个阶段提供，读回时就能判定选错。

# runtime is the shipping file set
FROM scratch AS runtime
ARG MODE=delivery
LABEL demo.mode=$MODE
COPY runtime.txt /runtime.txt

# inspection is the local inspection file set
FROM scratch AS inspection
COPY inspection.txt /inspection.txt

从这个目录运行下面的脚本。要有支持 targets 调用和 local 导出的 Buildx builder，使用单平台构建。第一条查询观察阶段名和默认标记。后两次调用才真正构建并导出文件。各自使用空的目标目录，避免上次产物残留。实验最后各检查一份该有的明确内容和一份本不该出现的文件。

set -eu
work=$(mktemp -d)
trap 'rm -r "$work"' EXIT
docker buildx version
docker buildx build -q --call=targets .
docker buildx build --progress=plain --output "type=local,dest=$work/default" .
docker buildx build --progress=plain --target runtime --output "type=local,dest=$work/runtime" .
test "$(cat "$work/default/inspection.txt")" = inspection-marker
test ! -e "$work/default/runtime.txt"
test "$(cat "$work/runtime/runtime.txt")" = runtime-marker
test ! -e "$work/runtime/inspection.txt"
printf 'default=inspection explicit=runtime\n'

本地 Docker Desktop 与 Buildx v0.37.2 执行时，阶段报告把 inspection 标成 default，同时列出 runtime。没有指定目标的首次导出只能读到 inspection 标记。明确指定 runtime 后，导出只含对应的运行时文件。脚本退出零，是因为两份内容和两项缺席都符合预期。没有上传镜像、运行容器或验证生产构建结果。

这份样例也说明阶段报告里的描述从哪里来。Dockerfile 中紧靠阶段前、以阶段名开头的注释可以被方法显示。描述写了交付用途，仅代表作者给出的说明，无法改变默认项。只从描述里看到 shipping 就推断发布目标已选中，会在这个练习里选错。执行时要看默认标记或明确的参数，再用独属文件核对相应的选中结果。

把发布合同变成两项独立的核对

有时开发团队希望默认构建用于开发，本身不需要纠正这个默认选项。发布作业则应保存要交付的阶段名，例如 runtime，并在构建命令里明确指定。安排一次 CI 演练故意去掉这个参数，看门禁能否拒绝只含 inspection 的产物。随后恢复选择并验证运行时文件内容。这个故障路径在本文用两次本地导出模拟过；真正的 CI 门禁、打包和发布还没有执行。只有目录出现或命令成功的验收条件，无法区分两份导出。

另一种选择是让正确的发布阶段成为默认，这适合默认入口本来就承诺生成客户用制品的项目。此时先检查目标表的默认标记，防止重排或插入阶段改变选中结果。发布阶段默认正确也需要核对文件。阶段名可以保留不变，后来有人却从该阶段删除一个文件或改变其内容。报告里的目标可见并不说明旧版清单仍然成立。给接收方交接时保留构建配置身份、选中的阶段以及从最后产物读回的文件清单，三项各有来源。

若团队使用不同容器构建前端，还应先用 --call=subrequests.describe 查看该前端是否支持目标查询。用于默认项验收的命令与正式构建应使用同一份 Dockerfile 和相同的前端输入。例如单独调用 -f Dockerfile.dev 得到的表不能用来解释 Dockerfile.release 的选择。发生不匹配时，先保留实际选择的文件，再验证目标标记，确定是运行参数拿错还是交付内容变了。调用前端信息的方法不构建示例制品，也不保证对每种 Dockerfile 都无须解析基础镜像相关信息。

如果下游确实要发布镜像，验收对象需要切换到实际发布输出。例如本地用文件导出核对了入口，下游仍应该在独立的镜像构建和接收回执中核对目标是否正确，并为镜像运行另行测试。文件系统导出不会展示完整的镜像元数据。想确认启动入口，检查最终镜像自身配置或启动它做受控测试。本文只有 local 导出，没有做那些验收。

可以再测试阶段清单与调用参数的拼写是否真能阻断。保留相同的 Dockerfile 和上下文，把明确的 --target runtime 换成不存在的 --target delivery，导出路径另取一处。本机这次构建退出一，日志表明找不到目标阶段，输出目录也没有创建。这是另一种失败。省略目标时仍能成功导出 inspection，拼错明确目标则连输出都没有。排障记录如果只留“产物不符合要求”，就不能区分该去修任务参数还是修实际阶段配置。分别记录缺省或显式形态、进程退出和产物读取结果，下次就能直接复查这两条路径。

已确定目标名，怎么查它接受哪些构建参数？

使用 docker buildx build -q --call=outline --target runtime .。outline 会列出该阶段消耗的构建参数和其默认值。本地对这份样例另行执行，输出 runtime 与 MODE delivery。这给交付者一个新信息，说明当前运行时阶段读取了哪个参数及其默认值。主流程只识别阶段并验证该阶段的文件。别把这条参数表当作运行配置的读回，最终参数能否形成期望行为，还要由对应的制品验收。
