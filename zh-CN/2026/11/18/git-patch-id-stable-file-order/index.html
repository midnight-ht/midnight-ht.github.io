两个补丁调换文件顺序，Git 还能认出是同一次改动吗？

交换 Git 补丁里的完整文件块，再改单个内容，复核 stable 和 unstable 补丁标识的用途。

正文

核心要点

  • stable 值不受文件 diff 块重排影响。
  • 区分补丁身份与提交身份。
  • 留存指纹模式和比较端点。

把两个文件的 diff 块调换顺序，Git 的 stable 补丁标识仍然可以相等。它计算的是排序变化不会影响的补丁指纹。要检查回移植或重做的补丁，先选定模式，再保留两份输入的比较范围。仅仅看到两串标识不一样，不能断定某处代码逻辑变了。

这种误判容易出现在工程交接中。团队重新生成了一组补丁，工具先列出第二个文件，上一版却把第一个文件放在前面。直接比较原始文本会看到整段移动。若发布门禁收的是已评审补丁的指纹，重排可能触发一次无意义的退回，也可能暴露门禁采用的是另一种哈希模式。两种判断都可以在一个不需要提交历史的小仓库中分开测。

保持编辑不变，只交换完整文件块

把下面的脚本保存成 check.sh，用支持 --stable 和 --unstable 的 Git 运行。它创建一次性仓库，把初始文件内容放进索引，再只改工作区。两次 git diff 比的是同一个索引和同一个工作区，各自仅选择一个路径。这里重排的是两份完整补丁块，内部的行号、上下文与改动行保持原样。不要把同一个文件内部的新增、删减或上下文行当成可随意调换的块。

set -eu
lab=$(mktemp -d)
trap 'rm -r "$lab"' EXIT
cd "$lab"
git init -q
git version
first=a.txt
second=b.txt
printf 'a before\n' > "$first"
printf 'b before\n' > "$second"
git add "$first" "$second"
printf 'a after\n' > "$first"
printf 'b after\n' > "$second"
git diff --no-ext-diff -- "$first" > a_diff
git diff --no-ext-diff -- "$second" > b_diff
cat a_diff b_diff > ab_diff
cat b_diff a_diff > ba_diff

patch_id() {
  git -c patchid.verbatim=false patch-id "$1" < "$2" |
    cut -d' ' -f1
}
stable_ab=$(patch_id --stable ab_diff)
stable_ba=$(patch_id --stable ba_diff)
unstable_ab=$(patch_id --unstable ab_diff)
unstable_ba=$(patch_id --unstable ba_diff)
printf 'stable ab=%s ba=%s\n' "$stable_ab" "$stable_ba"
printf 'unstable ab=%s ba=%s\n' "$unstable_ab" "$unstable_ba"
test -n "$stable_ab"
test "$stable_ab" = "$stable_ba"
test -n "$unstable_ab"
test -n "$unstable_ba"
test "$unstable_ab" != "$unstable_ba"
printf 'b distinct\n' > "$second"
git diff --no-ext-diff -- "$second" > changed_diff
cat a_diff changed_diff > changed-ab_diff
changed=$(patch_id --stable changed-ab_diff)
printf 'stable changed=%s\n' "$changed"
test -n "$changed"
test "$stable_ab" != "$changed"

本地 Apple Git 2.50.1 实跑时，stable 的 ab 和 ba 都以 d98bfeff 开头，脚本比较了完整字符串。两条 unstable 的结果不同。随后只把 b 的新内容改为 distinct，沿用 a 的原块并重新生成 b 的 diff，stable 值也变了。这样同一个样例有两项互相独立的验收。顺序变化不应改变 stable 结果，真实编辑则能被这组输入检出。前缀是本次观测的简写，复跑应比较两条完整输出之间的关系。

unstable 对照给出一个实用的故障线索。若团队原本保存的是旧版工具生成的标识，新任务刚切到 stable，即便输入的文件顺序没有发生变化，也不能直接把旧值当作新模式的已知答案。官方手册特地说明这两种模式的兼容范围。为跨版本回执写明模式，给旧索引与新索引各保留一小组能重新生成的输入，直到新结果确实可验证。必要时用同一份补丁同时读取旧值和新值，再逐步切换消费方。已经无法从旧记录找回输入时，留出迁移缺口，由新的受控样本建立基线。

用它筛查补丁差异，留下另外两份证据

假设一个修复已在主干评审，随后有人把它移植到维护分支。两侧的提交对象不同很常见，父版本、提交者时间或说明都可能不一样。希望快速定位可能重复的编辑时，先把两侧的父版本与目标版本分别固定，按同一规则导出补丁，再查是否得到相同 stable 标识。把两个父或基准对象和命令版本写在记录里。另一个人只拿当前工作区重新比较，不一定能还原这两份输入。

指纹相同之后仍需阅读移植落点。例如一侧都通过同一个校验函数打开配置，另一侧在调用校验前有不同的默认值。两份补丁可能修改的是同一行，完整程序运行的行为却可能不同。此时先检查被改文件和有关调用点实际存在于发布分支，再以该分支的输入复跑验收。指纹缩小的是人工需要核对的差异，提交身份用来定位历史，测试结果用来证明被测试的场景。三份材料互相支援，也各自有明确对象。

还有一种团队会把纯缩进规范作为这个门禁的审查目标。此时 stable 的空白规则本身就需要写入采用条件。倘若由格式化器调整的空格必须由人工确认，不能把一个相等的 stable 值当作审查已经完成。反过来，如果交付只关心补丁可能重复，顺序变化便可以从退回理由里移除。先给门禁写出它打算拦下哪一种变动，再用一个故意错误的补丁和一份重排补丁校准，检查它能否既放过应通过的输入，也拒绝实际编辑被改变的版本。

日志可以只展示短前缀，机器记录则宜保存完整值和补丁出处。若某次失败显示两个值不同，先确认两条结果确实由同一模式生成，再看是否混入了本不在交付范围里的第三个文件。只有这些输入相符，才能继续解释哪一段补丁造成了差异。按这个顺序复核比重新生成一份无法确认来历的补丁更容易复现问题。

如果门禁输出的是一张审核表，可以给这次样例单独写下两条预期。重排补丁仍可引用既有内容审核，但回执要陈述两次比较是否用了同一个指纹模式。内容改变的对照必须要求重新审核，并把新的改动行保留给接手人。如果启动新模式的任务只返回不同标识，审核者还有第三种解释，即比较方法换了。这个分支可以用同一份补丁对照两种模式，不需要为了复现去改发布分支。本文没有运行门禁本身。

如果审查希望行尾空格也参与标识，怎么办？

可以用 git patch-id --verbatim。它保留输入里的空白，并采用 stable 的排序处理，且不能与 --unstable 一起使用。在同一 Git 版本上另跑了一个单文件对照，从 mode=old 分别改成 mode=new 和行尾额外有一个空格的同一行。stable 的完整结果相等，verbatim 的完整结果不同。这次控制改变的是内容里的空白，主例的重排完全没有动任何文件块内部的字节。把启用该模式的规则写进回执，别拿默认空白策略的旧结果作对照。
