testzip() 返回 None，导入为什么仍缺清单？

用完好、载荷损坏和缺清单的三个 ZIP 对照 testzip()、成员名单与格式识别。

正文

核心要点

  • 分别记录坏成员和缺失的必需文件。
  • 只有格式识别成功，仍需读取成员并核对交付合同。
  • 清单存在时，仍应另行校验必需的业务字段。

归档已经过了 testzip()，导入器还是找不到 manifest.json。打包少了一份清单时，归档里已有的文件完全可以都没坏。要把故障指给正确的人，就得分别记录成员能否通过完整性检查，以及交付要求的文件是否都出现了。

归档里已有的文件，检查到哪一步

Python 的 ZipFile.testzip() 会读取归档里的文件，检查文件头和 CRC。发现坏成员时，它返回第一个坏文件的名字；没有报告坏成员时，返回 None。它检查的对象来自归档本身，所以不会自动知道导入方要求一个叫 manifest.json 的文件。清单从未被打进去，在这项检查里也就没有对应条目可以读。

归档的中央目录能被读出来，同样不必然说明每个成员的内容都可读。打开归档以后，你能列出成员名，但只有读取并检查成员数据，才有这里的 CRC 结果。实际排障至少会遇见三个不同观察：外层打不开、外层能开但成员损坏，以及外层和现存成员都没有报错但交付缺件。运行工具时把这些观察分开保存，打包者就能判断是重新传输、重新打包，还是核对下游收到的版本。

有一条措辞也值得留意。库文档说它返回的是第一个坏文件，适合回答“先看到哪个坏成员”。如果刚发现一项损坏，就不能假定其他成员都被完整检查过。把这个名字当作诊断线索即可；若有人要统计全部坏文件，还要设计独立的逐成员检查与异常策略。遇到完全打不开的文件，也应把打开阶段的失败和返回成员名称的情形分开记录。关闭后的 ZipFile 调用 testzip() 甚至会直接抛出 ValueError，不会给出成员名。

三份输入故意让两个检查分别失败

用内存构造归档，选不压缩的 ZIP_STORED 方便只修改真实载荷的一个字节。先确认这段载荷在文件中只出现一次，再等长替换首字节；原来的目录和文件头没有随改动重写，存下来的 CRC 对应的是旧内容。缺清单的样本重新创建为完整的 ZIP，避免因粗暴删除字节让它同时变成坏归档。

from io import BytesIO
from zipfile import ZIP_STORED, ZipFile, is_zipfile

payload = b"UNIQUE-LOCAL-ZIP-PAYLOAD"
required = {"manifest.json", "payload.txt"}

def make_zip(with_manifest):
    out = BytesIO()
    with ZipFile(out, "w", compression=ZIP_STORED) as archive:
        archive.writestr("payload.txt", payload)
        if with_manifest:
            archive.writestr("manifest.json", "{}")
    return out.getvalue()

def inspect_archive(blob):
    with ZipFile(BytesIO(blob)) as archive:
        missing = required - set(archive.namelist())
        return archive.testzip(), missing

complete = make_zip(True)
assert complete.count(payload) == 1
bad = complete.replace(payload, b"X" + payload[1:], 1)
assert inspect_archive(complete) == (None, set())
assert inspect_archive(bad) == ("payload.txt", set())
assert inspect_archive(make_zip(False)) == (None, {"manifest.json"})
assert is_zipfile(BytesIO(bad))
print("intact, corrupted payload, and missing manifest distinguished")

三个结果可以交叉看。完好的归档返回 None 且缺失集合为空；被改动的归档中两份成员都还在，但检查返回 payload.txt；第三份归档仍返回 None，缺失集合却包含 manifest.json。刚好两份输入返回 None，说明这个返回值自己无法区分交付完整与交付遗漏。两种失败原因分别由不同字段暴露出来，导入入口可以把它们归为不同错误。

这个夹具没有扩大到数字签名、传输认证或恶意改动检测。它只展示单字节变动能让这份人工样本报出 CRC 问题。独立的身份校验要问这份文件是否确实来自批准的构建；同一个名字和能通过 CRC 的内部内容，仍然可能属于另一次构建。本站的构建产物身份核对描述为这一层留下可复核记录的方式。

先列交付合同，再给每个失败选去向

如果导入工具只接受带有一份清单和一份载荷的 ZIP，可以在入口记录文件级读取结果和要求的成员名单。报告某份载荷损坏时保留成员名；发现清单缺件时列出缺掉的路径。相同的“压缩包错误”通知很难让调用方行动，因为它不能告诉对方是应恢复传输，还是应修改构建流程。保留分开的证据，就算有多个上游入口，也不必靠人工重演每一种错误才能判断。

比如导入方通常把第一份拒绝记录显示给发包人，内部接收报告则可以保存已完成的检查。若归档打不开，报告应标明成员检查没有开始，不应把坏文件字段写成全部正常。若已经读到成员名但某一项损坏，可以同时记录已取得的名单检查结果，再明确内容加载已停止。两个检查不都能执行时，应留下未执行的状态，下一次发包才能复验同一阶段。

完整性和成员名单之外还有内容合同。即使三项检查都表明归档能打开、CRC 正确、文件齐全，清单的 JSON 仍可能没有业务所需的字段。若导入需要声明格式版本，就应另写读取、解析及字段断言，把版本缺失的错误和物理文件缺失分开。示例里的清单内容只是一个空对象，为了让例子保留两个断言层；它没有模拟一个真正的清单模式。

还可以用同样的思路区分多余文件。如果交付允许附带其他文件，检查要求项的子集便足够。如果下游只接受固定包形状，验收还需要列出意外成员。对目录、同名归档项或不同路径大小写的规则，则应先定格式，再选适当的数据结构。这个简单夹具用集合检查缺名，因而没有验证同名条目的数量，也没有为文件系统制定解包策略。

如果上游只调用 is_zipfile，能发现这次载荷改动吗？

夹具最后一条断言表明那个改过载荷的样本仍能通过 is_zipfile。该函数依据 ZIP 的识别信息做判断，能用于判断是否有可识别的 ZIP；它不会代替读每个成员并检查 CRC 的那个步骤。比如上传界面先把非 ZIP 拦在入口，后面仍须检查归档成员，才能在载荷坏掉时报告 payload.txt。验收也可以把本例两个独立结果留下：格式识别为真，成员完整性返回坏成员名。这样调用者不会拿第一项表示导入已经通过。
