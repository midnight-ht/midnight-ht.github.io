并发上限设成 1，为什么 Semaphore 后来可以进两次？

对照普通和有上界的 asyncio 信号量，验证重复归还如何改变后续可用额度，并检查取消路径的归还责任。

正文

核心要点

  • 用独立实例检查多余归还与随后能取得的额度。
  • 上界只核对总数，每次归还还需要明确持有者。
  • 手动管理时，获取成功后才进入负责归还的保护区。

信号量初始化时只有一个名额。工作结束后归还一次，退出函数前又归还了一次。普通 asyncio.Semaphore 接受了多出来的归还，结果下一轮两次获取都能立即成功。要复现这类并发上限失效，先查归还操作，再看是哪里应该拥有这份额度。

初始计数为一，归还之后可以变成多少

Semaphore 保存一个内部计数。获取额度会减少计数；计数为零且调用无法立即取得额度时，获取会等待。释放则增加额度，并可能唤醒正在等待的任务。普通 Semaphore 允许释放调用多于获取调用。所以在这个没有等待者的例子里，原本只有一份额度，取走再归还回到一，多归还一次就得到二。没有任何任务显式改过并发配置，运行状态却已经能容纳两份工作。

BoundedSemaphore 继承了获取与释放的用途，同时在释放时维护初始上界。若归还会让计数高于初始化的数值，release() 抛出 ValueError。计数从零恢复到一属于正常归还；计数已有一，再试图释放则会失败。异常发生在多余归还这一侧，可以顺着调用堆栈去找是哪段清理逻辑多走了一次。

上界是一条总量规则。它不能知道哪一个任务正在使用额度，也不会检查谁调用了 release。如果初始值为二，两个任务都已取得额度且没有其他等待者，某个任务把自己的额度归还两次，计数仍然可能只到二；第二次错误归还就没有超过该上界。之后真正持有另一个额度的人再归还，报错地点可能已经离开第一次犯错的路径。若要追查这类问题，记录获取方与归还方的任务标识比仅统计异常次数更可靠。

在没有排队者的循环里做两个对照

下面创建两个独立的信号量，每个从一开始。每次先获取并正常归还一次，再尝试额外归还。夹具不启动后台任务，也不使用定时等待。它用 locked() 检查当下是否还能立即获取，因此不需要让一个故意多余的 acquire 卡住整个测试。

import asyncio

async def exercise(make_semaphore, bounded):
    sem = make_semaphore(1)
    take_permit = sem.acquire
    return_permit = sem.release
    await take_permit()
    return_permit()
    try:
        return_permit()
    except ValueError:
        assert bounded
    else:
        assert not bounded

    await take_permit()
    assert sem.locked() is bounded
    if not bounded:
        await take_permit()
        assert sem.locked()
        return_permit()
    return_permit()

async def main():
    await exercise(asyncio.Semaphore, bounded=False)
    await exercise(asyncio.BoundedSemaphore, bounded=True)
    print("ordinary admitted two; bounded rejected extra release")

asyncio.run(main())

普通实例第一次尝试无异常，接下来取得一份额后仍可立即获取第二份，这两次都在上面的夹具里执行过。达到两份占用后才不能立即再取。带上界的实例则在额外归还时抛错，之后取得唯一的一份就进入不能立即获取的状态。用两个新实例分别验证，避免在已经被错误归还污染的计数上混入其他并发行为。

这个例子还保护了正常归还的路径。第一次释放放在捕获异常的语句块之外，如果出错，测试会直接失败。这样可以防止有人只断言出现过一次 ValueError，却没有证明究竟是哪一步抛出的。最后再按真实取得的额度数量清理，便于把例子扩展为同一个循环中的多个独立场景。实测范围是单事件循环里的初始额度及重复释放，不测任务公平性、线程安全、吞吐或真实网络负载。

归还的那行代码应由谁负责

一次常见的错误是两层函数都安排清理。外层任务进入临界区时先持有额度；内层函数完成工作，为了“保险”也归还一次；外层退出时再执行自己的清理。等到很多任务同时运行，看到后来的接口限额变宽，很难把原因追回其中某次多余释放。处理这种交接时，可以留一个明确的约定：取得额度的一层也负责归还，内层只处理工作结果。

如果业务能把获取与归还包在同一个代码块，用 async with 管理信号量可以减少手动安排的分支。若确实需要跨函数或跨对象交接，测试应锁住几条不同路径，包括成功返回、业务抛错，以及清理入口被重复调用。每条路径分别观察后续可用名额和归还次数。带上界实例可以在部分错误上提前报警，但要检查所有权，仍要根据取得记录看是否每份额度只归还一次。

可以用一个独立的服务级控制验证这条约定。让首个请求获取额度后停在应用可控的门上，确认第二个请求尚不能进入；再让业务支路失败，并观察哪一层归还。只有原持有者的退出允许第二个请求进入。这个验收关注服务的临界区，比夹具里直接调用信号量多了一层实际职责。本站TaskGroup 的取消范围与清理讨论组内失败的传播，这里关注取消或退出之后哪个调用点有权归还额度。

等待 acquire 时被取消，finally 应该放在哪里？

把 await sem.acquire() 放在手动 try/finally 之前。只有获取成功返回以后，才进入包含工作逻辑、并在退出时归还的保护区。如果等待本身就被取消，调用者没有取得额度，因而无需执行自己的 release。相反，如果工作已经开始，随后取消要沿工作代码所在的保护区退出并清理。不要把尚未取得额度的等待也包进一个无条件归还的 finally。

对取消的验收可以分两条；在第一条里用一个已持有的额度阻住等待方并取消等待方，确认原持有者仍独占额度。第二条让工作方在成功获取后停在一个可控制的等待点，再取消它，随后新任务应能正常获取。这个检查要看两条独立的取消时机。文章里的运行夹具只走了同步顺序的获取与释放，两条取消验收是建议验证的行为，没有代替读者运行它们。
