同一句断言移进辅助模块，pytest 为什么只剩 AssertionError？

固定同一失败输入，对照 pytest 注册辅助模块前后的断言诊断和进程结果。

正文

核心要点

  • 普通辅助模块可能没有断言改写。
  • 先注册模块，再首次导入。
  • 独立核对失败结果与诊断内容。

同一句断言移进普通辅助模块后，pytest 的失败详情可能少掉比较表达式，只在异常行显示 AssertionError。默认断言改写并不会覆盖每个被导入的文件。要给这份辅助模块恢复比较值，先把模块名称注册给 pytest，再让测试导入它。

这类变动经常出现在测试重构里。多人把公共断言提炼成函数，可以少维护几处同样的业务逻辑。重构前后，用例都仍然遇到同一个失败；差异落在值班或评审者接手报告的那一刻。以前能直接看到实收与预期的比较，现在要先打开测试，再找函数参数和失败的判断。下面把业务失败固定住，仅改变 pytest 是否改写辅助模块，让报告质量成为可以检查的一项结果。

让两次失败使用同一对值

在空目录创建 helper.py。断言只做最简单的相等判断，没有自定义消息。这样能看到 pytest 提供的表达式内省，而不是字面报错文本变化。

def check_total(actual, expected):
    assert actual == expected

另存为 test_total.py。这两个参数有意不同，两次启动都应该失败。如果其中一趟成功，说明已经观测到别的变化，不能用来比较诊断差异。

from helper import check_total


def test_total():
    check_total(7, 9)

在本机同一隔离环境从此目录运行。关闭第三方插件自动加载和缓存插件，避免另一份测试配置参与。第一趟还没有 conftest，运行下列命令并保存其输出和退出值。

export PYTEST_DISABLE_PLUGIN_AUTOLOAD=1
python -m pytest -q -p no:cacheprovider test_total.py

第二趟先在同目录写 conftest.py，内容如下。不要在这条注册语句前导入 helper。然后另启一个 pytest 进程，运行同一个命令。新进程保证第一次试验导入的模块不会沿用到下一趟。

import pytest

pytest.register_assert_rewrite("helper")

本地 Python 3.11.15 和 pytest 9.0.2 上，两趟均退出一。第一趟的异常详情在 helper.py:2 对应 AssertionError，没有 pytest 生成的 assert 7 == 9 比较行。第二趟出现这条比较行。报告的其他位置仍可能展示形参或调用值，不能把第一趟概括成整份报告完全没有数值。我们查的是失败位置有没有经过改写生成的比较表达式。这样独立验证报错内容，而退出值验证业务失败仍在。

找到首次导入，才能改变报告

pytest 的导入钩子在符合规则的源模块载入时改写断言语法树，编译后失败才有额外信息。测试模块通常在覆盖范围内，普通辅助模块未必在。注册接收模块路径，如 helper，不会因为函数叫 check_total 就决定检查哪个文件。若模块属于包内子模块，传入可导入的完整模块名，再确认 pytest 最终载入的文件路径是所预期的那份。

一个典型失败是先导入共享函数，随后才注册它所属的模块。函数的已导入定义已经形成，晚来的注册不能为该次导入重新生成断言。维护者可能看到注册行存在，却一直得不到比较值。把注册放进能更早加载的入口，重新启动独立进程，再比同一失败文本。这里的第二个样本只演示正确顺序，未把晚注册分支写成另外一次实跑。若工程里不清楚谁先导入模块，可先查插件和 conftest 的导入链，收窄到第一处引入。全量工程里同名模块之间的路径冲突还要另外定位。

还要决定谁会使用这份助手。仅在 pytest 内诊断时，显式注册对测试便利。若同一个函数要在调试工具或别的运行器里直接调用，可以提供清楚的断言消息，或使用该调用入口自身支持的比较机制，并在那个入口重新验证。不能把 pytest 专有报告当作所有调用者都能看到的结果。比如一个打包验证工具直接用 Python 导入函数，先执行该入口并确认异常足以让接手者定位实收值。本文的两次 pytest 回执并不测试那个外部工具。

在 CI 中为迁移留一个短的负向用例，让不等的两个总数产生可识别的诊断。第一次执行保留未注册版本的真实结果，第二次执行保存改写行和测试节点。以节点与比较值双重核对，能防止把另一条失败里的相同数字误认为本检查的结果。不要让故意失败成为日常产品套件的红灯，可以在独立的自检命令中预期失败，再核对报告。这项自检安排是建议，文章只跑了示例进程。用报告说明了哪条断言、哪两个值和在哪个入口复现，读者才可以查回原始判断。

即使注册成功，仍要区分源代码里的断言和手写异常。比如辅助函数改成先用 if 判断，然后显式抛出带固定文字的 AssertionError，注册不会从普通分支和一条异常语句反推比较式。若测试团队要求报告保留实收和预期，这种写法就需要消息显式带值，或把相等判断留给真正的 assert。复核时先验报错行对应的源代码，再试同一组不相等输入。这个额外分支没有执行；它解释了排查注册已生效但仍缺比较行时，下一步该看什么。

断言就写在直接加载的 pytest 插件模块里，还要注册吗？

作为 pytest 插件直接加载的模块属于可改写范围。它继续导入的普通辅助文件需要按自己的导入路径判断。另一个本地对照把比较函数直接写在 plugin_entry.py 的 fixture 里，使用 -p plugin_entry 加载该模块，不添加 conftest 注册。其不相等的输入也得到 assert 7 == 9。这次改变的是断言所在模块的加载角色，前两趟仍对比同一个普通助手。把插件入口与辅助模块区分开后，才知道应该在哪里注册。
