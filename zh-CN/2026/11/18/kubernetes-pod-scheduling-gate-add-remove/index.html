一个 Pending Pod 明明有空闲节点，为什么不开始调度？

对照一个带门和一个无门的 Pod，核对调度门释放、节点分配和应用就绪各自的证据。

正文

核心要点

  • 调度门未移除时等待放行。
  • 用 PodScheduled 和 UID 核对释放效果。
  • 容器就绪另行验证。

一个 Pending Pod 即使遇到空闲节点，也可能还没进入节点分配。只要 spec.schedulingGates 里还有未移除的门，通常的调度流程就会等待。先查实际门清单与节点分配状态，可以区分“尚未允许调度”和“允许了但找不到节点”。

这个问题容易在外部准备慢的时候露出来。交付任务先创建 Pod，再等待一次与节点选择无关的准备动作。Pod 已经能被查询，任务报告也显示提交成功，调度却没有开始。有人看见 Pending 就去扩容，结果新增节点也无法关闭由另一个流程掌管的门。下面用一个无门的对照和一个有门的 Pod，验证看似一样的等待能否被精确描述。

固定节点条件，只给一个对象加门

在可丢弃的 Kubernetes 测试环境中做以下实验。PodSchedulingReadiness 自 Kubernetes 1.30 起稳定。环境要允许创建新的命名空间和 Pod，选择默认调度器，并有至少一个满足这些 Pod 约束的节点。例子不指定 nodeName，假设准入过程也不会修改此字段或加别的门。把这份清单保存为 pods.yaml。

apiVersion: v1
kind: Pod
metadata:
  name: ordinary
spec:
  containers:
  - name: pause
    image: registry.k8s.io/pause:3.10
---
apiVersion: v1
kind: Pod
metadata:
  name: gated
spec:
  schedulingGates:
  - name: example.com/prepared
  containers:
  - name: pause
    image: registry.k8s.io/pause:3.10

为降低误操作，让命令明确使用之前核对过的实验上下文。将 LAB_CTX 设成该上下文，以下内容存为 Shell 脚本。先以 ordinary 的 PodScheduled 条件作为节点分配的正向对照。即使镜像尚未拉取，这条条件也比容器是不是 Ready 更适合判断这个阶段。随后查看 gated 的理由与实际字段，确认无节点分配。最后一组断言要在移除门后执行。预期过渡发生在同一个 Pod UID 上。

set -eu
: "${LAB_CTX:?set LAB_CTX to the disposable cluster context}"
ns=zy18-scheduling-gate
lab() { kubectl --context "$LAB_CTX" -n "$ns" "$@"; }
kubectl --context "$LAB_CTX" create namespace "$ns"
lab create -f pods.yaml
lab wait --for=condition=PodScheduled pod/ordinary --timeout=90s

status_path='{.status.conditions[?(@.type=="PodScheduled")].reason}'
lab wait --for="jsonpath=$status_path=SchedulingGated" pod/gated --timeout=90s
node_path='{.spec.nodeName}'
uid_path='{.metadata.uid}'
gate_path='{.spec.schedulingGates[0].name}'
observed_gate=$(lab get pod/gated -o "jsonpath=$gate_path")
test "$observed_gate" = example.com/prepared
test -z "$(lab get pod/gated -o "jsonpath=$node_path")"
before=$(lab get pod/gated -o "jsonpath=$uid_path")

lab patch pod/gated --type=merge -p '{"spec":{"schedulingGates":[]}}'
lab wait --for=condition=PodScheduled pod/gated --timeout=90s
after=$(lab get pod/gated -o "jsonpath=$uid_path")
test -n "$after"
test "$after" = "$before"
lab get pod/gated -o wide

先期待 ordinary 获得节点。gated 应报告调度门仍在、无节点分配，并给出 SchedulingGated 原因。在移除唯一的门之后，它才进入普通调度。只要仍有合适的节点，预期可看到该 Pod 的 PodScheduled 成为 true，且 UID 与移除前相同。若门已移除但条件仍未满足，应查资源、约束和调度事件。移除这个门没有多给它任何资源，也没有为后续时刻保留一个位置。九十秒是客户端等待上限，不能拿它当平台调度承诺。

这份实验没有连接集群，也未运行上述命令。需要在自己的测试集群验收时，保存两条初始观察和释放后的同 UID 观察。如果执行后发现 ordinary 也没分配节点，先解决对照缺失的问题，别把两个对象都未调度写成门有效。实验完成后删除只为它创建的命名空间；核对该动作仍指向临时上下文。

让移除操作有清楚的所有者

调度门适合表达可以在调度前观察的条件。比如负责准备数据的控制器得到本次输入已登记的回执，再移除自有门。写一条可复核的释放规则。若仅根据 Pod age 到了多少秒就删除，准备作业可能还未结束。反过来，如果准入给了一个没人负责的门，正确调度的 Pod 会一直没有机会。观察该门发生了什么，要从业务前置条件和控制器操作两处取证。

验收还应保留一个相反的输入。准备系统给出明确失败时，应让门留在清单里，同时让读者知道等待的原因。日常运维可以给这类任务加上独立的告警时限，到点查负责者和准备过程，而不是无限等到 Pod 进 Running。准备成功之后，另外观察调度成功和应用可用。容器镜像拉取失败、进程退出或 readiness 未达到，都可能发生在分配节点之后。把 readiness 信号当成调度门已释放的日志，会让接手的人漏掉真正的核对点。

准备回执还需要能识别当前对象。譬如发布脚本删除一份等待过久的 Pod，然后用同样的名字重建。准备系统稍后返回了前一份输入的成功消息。如果只用名字查找对象并释放门，可能把还没拿到新输入的任务提前放行。一个稳妥的交接把准备工作绑定到本次对象身份或业务批次，释放前再核对这份身份。看到名字相同而批次不同就保留门，由准备方重新出具正确回执。这一故障例不涉及实际集群操作。

若需要两个独立前提，可以分别赋予门名和负责者。例如资料已生成由存储流程确认，处理许可由编排流程确认。先拿到资料时只移掉对应的门，另一个前提尚未满足就仍需等待。控制器要复读实际门清单和准备结果。对于由多个流程管理的真实对象，不能把本例清空整个列表的补丁原样照搬。实验知道清单只有自己创建的一项，正式流程则应只移除自己负责的那一项。

值班报告最好记录门清单何时变化、调度条件何时成功以及应用何时可服务。如果一个窗口内看不到应用请求结果，可以直接写应用验收未完成；已经能确认节点分配时，仍可把这个阶段如实交接。由此分出需要交给准备系统、调度运维或应用负责者的证据。

先移除了门，事后可以再加回原 Pod 吗？

不可以。官方文档规定创建时初始化门，已创建对象只允许移除现有门。可以在同样隔离环境中，对已释放的 gated 提交一次新增 example.com/prepared 的补丁，预期 API 拒绝，并再次读取门清单确认没有写入。这个对照没有运行。计划需要重新等待时，应让后续的新 Pod 按正确前置条件创建，或设计独立的应用状态控制。调度门的删除不能作为可来回切换的暂停按钮。
