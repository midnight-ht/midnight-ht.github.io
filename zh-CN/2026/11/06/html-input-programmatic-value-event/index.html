HTML脚本改了input.value，input监听器为什么没运行？

按HTML事件规则区分脚本赋值、用户编辑和导航恢复，让本地预览通过明确双入口保持同步。

正文

核心要点

  • 脚本赋值不自动发送input或change。
  • 程序恢复与用户编辑可共享派生计算。
  • 合成通知不等于写值或真实键入。

脚本改变控件值不会自动触发input或change；把派生显示更新放到明确的共享函数，让用户编辑和程序恢复都调用，而不是等待不存在的事件。恢复草稿后输入框已经换了文字，预览却没有动，先检查更新入口是否只接在input监听器上。

HTML输入事件规则明确说明，这些事件不响应脚本对表单控件值的修改。标准给出的理由之一，是便于脚本回应用户操作而更新控件，不必再过滤自己的改动以避免循环。赋值和通知本来就是分开的行为，不需要用更长等待把它们凑成一个动作。

同一份当前值，可以来自不同入口

假设编辑器提供输入框、草稿恢复和清空三个动作。用户实际编辑普通文本框，可以通过input监听更新本地预览；草稿按钮自己写入value时，应主动调用同一预览规则。清空也是程序动作，不能只把value设为空，再期待旧预览自行消失。

这不表示每个入口都应模拟用户事件。业务代码已经知道自己刚写了什么，可以直接维护派生状态。若所有程序赋值都再派发input，而监听器又根据input修改value，团队还需要解释是否会重复更新或形成自己的循环。先把谁拥有原始值、谁计算预览说清楚，比补一个看似通用的事件更容易维护。

还要区分value属性与HTML内容属性。当前用户可编辑值、默认值和框架状态并不总是一份东西。本文限定普通text输入的当前值读取，不把textarea长度、数字解析或复选框勾选合同混在一起。output重置与默认结果讨论另一类基线恢复，本题先处理程序写入没有通知到派生显示。

用一个共享计算接住三个入口

下面是未执行的完整HTML，没有form、网络请求或保存实现。所谓草稿只是代码里的固定教学字符串，不是从用户账号恢复的真实记录。预览直接显示当前文本，不计算字数或解释富文本，也不通过innerHTML把输入变成标记。

<!doctype html>
<html lang="zh-CN">
<meta charset="utf-8">
<title>值写入与预览更新</title>
<label for="draft">教学草稿</label>
<input id="draft" type="text" value="初始教学文字">
<button id="restore" type="button">恢复教学草稿</button>
<button id="clear" type="button">清空教学草稿</button>
<p>当前预览：</p><pre id="preview"></pre>
<p id="observed">收到的input事件：0</p>
<script>
const [input, restore, clear, preview, observed] =
  ['draft', 'restore', 'clear', 'preview', 'observed'].map(
    id => document.getElementById(id)
  );
const on = (node, type, handler) => node.addEventListener(type, handler);
const write = (node, text) => { node.textContent = text; };
let inputEvents = 0;
function refresh() {
  write(preview, input.value === '' ? '（当前为空）' : input.value);
}
on(input, 'input', () => {
  inputEvents++;
  write(observed, `收到的input事件：${inputEvents}`);
  refresh();
});
on(restore, 'click', () => {
  input.value = '恢复的教学文字';
  refresh();
});
on(clear, 'click', () => {
  input.value = '';
  refresh();
});
refresh();
</script>
</html>

初始refresh让预览对应页面当前值；用户输入路径收到事件后计算；恢复和清空路径在写值以后主动计算。事件计数只是这个监听器实际收到多少通知，不是编辑次数、用户动作次数或保存次数。一个用户操作可能产生多种更新，不能从这行演示计数推算业务行为。

错误对照是删掉恢复处理器中的refresh。输入会改变，而预览可能留在之前的文字；后来用户再键入，input到来才使预览突然追上。这个现象不是恢复数据“过一会儿才生效”，而是两份可见状态采用了不同触发条件。加固定延时后再读值，也不会替已经漏掉的预览更新建立明确责任。

反过来，若恢复按钮调用refresh却忘了先写入value，预览仍正确反映旧值。共享函数不能推断调用者希望恢复哪段文字；它只根据当前权威输入计算。测试因此要同时比较输入框值与预览，而不是只确认某个函数被调用了一次。

派发new Event("input")会替我改字段值吗？

不会自动提供待写入的文字。dispatchEvent派发构造的事件，监听器可能由此执行，但它不是输入值赋值器。若应用确实需要向外部模块发送一次合成通知，应先说明值在哪里更新、事件是否冒泡以及接收者该如何解释来源，而不是假装重放了用户打字。

DOM标准区分用户代理分发与脚本创建、分发的事件，构造事件的isTrusted初始为false。这个字段也不是业务安全校验：它帮助理解通知来源，不替接口认证或对象权限。本文只用它划清测试证据，不设计依靠事件真假授予业务能力的规则。

合成通知仍可能适合某些组件协议，例如模块约定写值后通知订阅方。但协议需要保证调用次数与责任范围，避免共享refresh已经更新一次，订阅方又做同一项副作用。对应用自己拥有的纯预览计算，直接调用通常更清楚；对于外部框架，则应使用框架公开的状态入口，不直接改DOM后期待它自动接管。

浏览器后退恢复值，也一定发input吗？

不能这样假定。HTML原文明列，导航中的状态恢复也不发送这些事件。它与脚本赋值的原因不同，却同样说明“监听input就能覆盖所有值变化”过宽。真实系统需要在实际恢复入口同步派生状态，并核对浏览器究竟恢复了哪些控件。

不要为解决这项问题，直接把所有观察职责交给MutationObserver。变更通知批次说明它观察的是所配置的DOM变更，当前控件值、属性与通知不是可互换的通道。某个属性日志出现，不能替代预览已经对应当前编辑值的检查。

如果用户在异步恢复草稿期间继续输入，还需要决定后到的草稿能否覆盖新编辑。共享refresh只保证“预览读取当前值”，不解决“哪份值应成为当前值”。可以要求恢复前确认，或按本地已修改状态拒绝旧恢复结果；不能把最后返回者无条件当成用户最新意图。样本没有异步读取，因此不宣称实现了这项竞争处理。

待执行检查分别真实键入、恢复固定文字、清空、连续恢复，再观察只赋值和只派发事件的反例。每步保留当前value、可见预览与实际事件记录，浏览器导航恢复单独测试。本文没有这些运行结果；交付要让每一种值来源都有明确的派生更新入口，而不是让input替所有程序动作承担通知承诺。
