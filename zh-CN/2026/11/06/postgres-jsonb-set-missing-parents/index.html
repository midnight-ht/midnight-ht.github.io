jsonb_set 开了 create_if_missing，为什么深层字段仍没出现？

jsonb_set 只创建最后的路径项。用缺父、空父和已有值区分正常返回与字段写入，再为缺失或不兼容的父对象制定明确策略。

核心要点

  • create_if_missing 不会递归补齐父路径。
  • 对象构造应明确拒绝或迁移已有不兼容类型。
  • 行数和前后相等都不能单独证明目标路径后置条件。

jsonb_set 的 create_if_missing 为 true，只允许创建路径的最后一项，不会替你递归补齐缺失的父对象。要写入 profile.color，profile 这一步必须已经存在；否则 PostgreSQL 返回原来的 JSON，语句本身可以正常完成。

这会让一个普通的资料更新接口显得很奇怪：数据库没有报错，更新也找到了目标行，但再次读取时，颜色仍然不存在。排查时若只盯着布尔参数，很容易反复把 false 改成 true，或者怀疑缓存。真正需要核对的是路径的每一层，而不是参数是否已经开启。

三个输入，分别走哪条路径

下面是供 PostgreSQL 18 使用的只读例子。输入是虚构资料，输出按官方函数规则推演，未把它写成实际数据库执行记录。它没有修改现有表，也不涉及数组下标。

WITH inputs(label, doc) AS (VALUES
  ('missing', '{}'::jsonb),
  ('empty', '{"profile":{}}'::jsonb),
  ('existing', '{"profile":{"color":"old","name":"Ada"}}'::jsonb)
)
SELECT label, doc,
       jsonb_set(doc, '{profile,color}', '"blue"'::jsonb, true) AS result
FROM inputs
ORDER BY label;

missing 的结果仍是 {}。路径最后要访问 color，但在到达它之前，profile 已经缺失。empty 的结果是 {"profile":{"color":"blue"}}：父对象存在，最后的键可以新增。existing 则得到 {"profile":{"color":"blue","name":"Ada"}}，已有颜色被替换，同级的名字保留。

这三种结果不能用“没有键就新增”概括。缺的是目标键，还是到目标之前的父路径，决定了函数会不会改变对象。官方文档对 jsonb_set 的限定正是：更早的路径步骤都必须存在，否则原样返回目标。这里的 true 已经起作用，只是它负责的范围比接口作者想象的小。

先决定父对象缺失是不是合法输入

如果业务规定资料初始化时必须建立 profile，那么缺失父对象就是数据不满足前置条件。合理的处理是报告资料结构不完整，或交给明确的数据修复流程。继续执行一次返回原值的写入，再给客户端一个“颜色已保存”，会把数据库层的正常返回误当成业务层的成功。

另一种产品约定是：旧资料没有 profile 也可以直接设置颜色。这时需要显式构造父对象。该决定属于应用的数据结构策略，不能靠函数参数自动推断。尤其要先区分父对象缺失与父值已经是字符串、数组或 JSON null；后几种情况可能包含旧版本数据，直接换成空对象会删除信息。

下面把这种策略限定得很窄：根必须是对象；profile 只能缺失，或者已经是对象。其他输入返回拒绝状态，不提供可写入的新值。它仍是一个独立的只读转换例子，没有用宽泛的合并操作掩盖类型迁移。

WITH inputs(label, doc) AS (VALUES
  ('missing', '{}'::jsonb),
  ('object', '{"profile":{"name":"Ada"},"enabled":true}'::jsonb),
  ('scalar', '{"profile":"legacy"}'::jsonb),
  ('json-null', '{"profile":null}'::jsonb)
), checked AS (
  SELECT label, doc,
         jsonb_typeof(doc) = 'object'
         AND (NOT (doc ? 'profile')
              OR jsonb_typeof(doc -> 'profile') = 'object') AS allowed
  FROM inputs
)
SELECT label,
       CASE WHEN allowed THEN 'accepted' ELSE 'rejected' END AS status,
       CASE WHEN allowed THEN
         doc || jsonb_build_object(
           'profile',
           COALESCE(doc -> 'profile', '{}'::jsonb)
             || jsonb_build_object('color', 'blue')
         )
       ELSE NULL END AS candidate
FROM checked
ORDER BY label;

按这段规则，缺失父对象会被构造出来；对象父值里的 name 与根上的 enabled 都得到保留。字符串和 JSON null 两行被拒绝，candidate 是 SQL NULL，表示这里没有给出可采用的候选对象。它不是要求把资料更新成数据库空值。接入真实更新流程时，必须只采用已接受的候选值，不能把所有返回行一概写回。

这里的 COALESCE 只处理读取缺失键得到的 SQL NULL。它并不会把 JSON null 变成空对象，类型检查才是拒绝该输入的依据。若这两个空值容易混淆，可先对照JSON null 与 SQL NULL 的区别。本次转换的目标是明确父对象策略，不是重新定义“清空资料”的接口协议。

两层合并，各自保留什么

这段构造有两个 ||，并不是重复做同一件事。内层以已有 profile 对象为左侧，把新的颜色对象放在右侧，因此颜色被新值替换，名字等其他键保留。外层再把完整的新父对象放回原来的根对象，保留 enabled 这类根上的其他字段。两次合并对应两层不同的兄弟关系。

如果省略内层合并，只把新建的 {"profile":{"color":"blue"}} 合到根上，根上的 enabled 仍可能保留，但原有 profile.name 会消失。这不是递归合并出了错，而是对象连接本来只合并顶层；重名键采用右侧值，整个旧父对象被新父对象替换。官方 JSON 操作符表明确说明了这一点，所以保留哪个层级的兄弟字段，需要在表达式里逐层体现。

也不要把类型检查拿掉，认为连接符总能把输入修成对象。对象与数组、标量的组合还可能走到数组连接规则，并不能提供资料对象所需的结构。这里先缩小允许输入，再利用对象与对象的连接性质，是为了让输出形状能由读者逐项核对。若资料包含更多嵌套层，必须逐层决定保留和覆盖的规则；多加一个路径项并不自动扩大这个例子的保证范围。

用后置条件核验，不用行数猜测

真实更新应至少核对两个问题：输入是否满足允许的结构，结果的目标路径是否具有所需值。返回 UPDATE 1 只能说明更新处理了一行，不能证明深层字段从缺失变为存在；这两件事处于不同层面。数据库驱动的成功状态也不会替接口完成这项领域判断。

反过来，结果与输入相等也不能单独证明“父对象缺失”。如果原有颜色已经是 blue，再次设置同样的值也可能得到相等的 JSON。验证时应保留初始结构，并检查 jsonb_typeof(doc -> 'profile') 与结果的 #> '{profile,color}'，再对照期望的 JSON 字符串值，而不是只计算前后是否不同。

可在自有测试库中先运行两个只读例子，再加入一个已有蓝色的输入。随后把父值依次换成数组、数字和 JSON null，确认应用选择的是拒绝还是显式迁移。每次改变输入都重新写出预期，尤其要检查旁边不应改变的字段是否仍在。示例只给出了待核验的推演，没有声称这些变体已经执行通过。

父值是字符串时，应该直接换成空对象吗？

只有明确的数据迁移契约允许时才这样做，普通字段更新不应静默删除旧值。若 "legacy" 仍承载旧格式资料，应先确定它的含义、转换目标和失败处理，再决定是否替换；“为了让颜色写进去”不足以说明这些信息可以丢弃。

这种迁移还需要单独考虑并发更新。前面的只读转换没有证明把对象读到应用、改完再整块写回是安全的，也没有实现通用递归补丁。对当前问题，先固定一个可检查的边界就够了：父路径必须存在，或者由明确的对象构造规则建立；不兼容的已有值交给另一项有名字的迁移处理。
