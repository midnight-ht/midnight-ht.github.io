S3 Object Lock 开着，为什么同一个 key 仍然能出现新版本？

S3 Object Lock 保护的是指定对象版本，而不是冻结 key 名。新版本和 delete marker 仍可能改变当前视图；审计必须围绕 version ID、保留模式和权限。

正文

核心要点

  • Object Lock 仅对请求指定的对象版本应用保留或 legal hold。
  • 它要求开启 S3 Versioning，但不阻止创建新版本或在其上添加 delete marker。
  • key 当前不可见与受保护旧版本已销毁是两件事。

S3 Object Lock 保护的是指定的对象版本，不是把一个 object key 永久冻结。AWS 文档说明，Object Lock 只能用于开启版本控制的 bucket；保留期或 legal hold 只保护请求中指定的 version。它不会阻止同一 key 写入新版本，也不阻止在对象上方创建 delete marker。因此“当前 key 看不到对象”不能证明旧版本已被删除；“某版本受保留保护”也不能证明使用者看到的当前内容仍是该版本。

key 是名称，版本才是保留策略的单位

在启用 Versioning 的 bucket 中，重复写同一个 key 会产生不同 version ID。Object Lock 的保留元数据附着到具体版本。Bucket 默认保留策略可以让新写入版本获得默认期限，但单个对象版本仍可以具有各自的 retain-until date、治理/合规模式或 legal hold。审计时如果只记录 reports/monthly.csv，缺少 version ID，就可能把几个不同时间、不同保留状态的对象误当成一个。

AWS 还指出，已有受保护版本时对同一 key 再执行 PUT，会创建新版本，旧版本仍按原保留配置锁定。新版本不会自动继承旧版本的保护设置，除非写入或 bucket 默认配置为它应用新的保留策略。于是同一个 key 可能同时对应一个受保护的旧版本和一个较新的未保护版本。控制台或不带版本号的 GET 展示当前版本，不能替代逐版本审查。

假设时间线：受保护对象上方出现 delete marker

假设 archive/receipt.json 的 version A 处于 30 天 retention。操作者执行不带 version ID 的简单 DELETE。AWS 文档说明，此类 DELETE 可返回 200 并插入新的 delete marker；marker 成为当前版本，而受保留保护的 A 仍在历史版本列表中。普通对象列表可能不再展示内容，应用的 GET 也可能表现为对象不存在，但这并不等于 A 被永久销毁。

同样，对同一 key 的新 PUT 可以创建版本 B；之后 key 当前内容可能指向 B，而 A 仍受到保留。若只做 key 级别清单，恢复人员可能误以为锁失效，或者把 B 的保留设置错误地套到 A 上。示例是依据文档构造的假设操作，不是对真实 bucket 的调用结果。恢复和销毁都必须明确区分版本 ID、当前标记和版本状态。

Governance、Compliance 与 legal hold 要按威胁模型选

AWS 将 governance 模式描述为允许拥有特定绕过权限的主体调整或删除受保护版本的模式；compliance 模式在保留期间提供更严格的删除限制；legal hold 没有自动到期时间，需要有权限的主体明确解除。具体权限和例外要按当前账户策略与操作确认。把“Object Lock 开启”当作单一安全属性，会忽略谁可以修改保留期、谁可以添加新版本、谁有权解除 hold，以及谁能删除 marker。

若业务要求不可变留存，应把写入主体、保留设置、版本记录、复制目标和生命周期规则放在同一审计模型中。一个受保护版本并不会阻止有人上传一个错误新版本并令其成为当前内容；应用端需要校验版本、对象摘要或签名，以决定是否信任该版本。要实现法律留存、恢复窗口或防勒索目标，应分别定义“不能删除旧证据”“不能替换当前业务对象”和“普通用户不可访问”等要求，它们需要不同的策略组合。

怎样验证保留到底附着在哪个对象？

在非生产 bucket 上开启 Versioning 和 Object Lock，写入一个测试对象并保存返回的 version ID。对该版本设置短期测试保留或 legal hold，然后尝试四件事：用 version ID 永久删除；不带版本号简单 DELETE；对同 key 再 PUT；查询当前 key 与历史 versions。验证每次响应、当前 marker、对象版本列表和保留状态。对 governance bypass、合规模式和 legal hold 的测试需使用专用测试账户和最小权限，不能在生产数据上试探性执行。

验收记录至少保存 bucket 版本控制状态、Object Lock 配置、版本 ID、retain-until 时间、模式、legal hold 状态、执行身份和 API 操作时间。清单或备份系统应把 key 与 version ID 成对保存，恢复流程也要明确恢复哪个版本。生命周期规则须按当前和非当前版本分别审查，不能因 key 当前不可见就自动清理全部历史版本。

选择依据与限制

Object Lock 适合给版本化对象提供 WORM 保留属性，但不等于 key 锁、应用权限系统、备份复制或不可变审计日志。需要防止误删时，选具体版本的保留期与 legal hold；需要防止普通操作者改变保留时，评估 compliance 或治理权限；需要保留当前业务指针时，还要控制谁能写入新版本和 marker。版本化删除标记的恢复机制已有独立说明，本文聚焦的是锁保护的对象单位。

本文根据 AWS S3 官方用户指南核对了版本级保护、新版本和 delete marker 的边界；没有连接 AWS 账户或运行 API。实施前应检查真实 bucket 配置、IAM 权限、复制与生命周期策略，并对每个版本留存审计证据。Object Lock 可以限制指定版本的变更/删除，但无法单独证明业务 key 当前指向正确数据，也不代表数据已被跨区域备份。

复制策略也必须按版本逐一审查。源 bucket 中某版本存在 Object Lock，不应被笼统推断为所有复制副本、跨账户归档和备份生命周期都具有同样的保留期。检查目标 bucket 是否开启版本控制、复制是否保留对象锁设置、目标版本 ID 是否记录、复制失败是否告警，以及谁能修改目标保留策略。法规留存的证据链必须能说明每个副本的锁状态，单看源 key 的当前对象无法证明所有副本都不可变。

延伸阅读：本站版本化 S3 删除标记恢复。两篇都要求操作记录包含目标 version ID；只看 key 和 API 成功状态无法证明留存或删除完成。

恢复计划应把目标数据版本与 key 当前指针视为两个结果。恢复旧的受保护版本时，可能需要将它复制为新的当前版本；这会创建新的 version ID，并需要单独决定新版本的保留策略，而不是把旧版本原位移回。操作记录应包含源版本、目标版本、保留模式和执行身份。这样“恢复成功”的通知就不会掩盖用户现在读到的是否为预期内容，以及历史证据是否继续受保护。
