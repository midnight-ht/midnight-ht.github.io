AWS 目标角色允许 12 小时，第二跳凭证为什么仍只有一小时？

AWS role chaining 的限制取决于凭证来源：用一个角色的临时凭证再 AssumeRole 时，会话最长一小时；这不适用于从用户凭证进行的初次角色假设。

正文

核心要点

  • 角色临时凭证再用于 AssumeRole 才构成 role chaining。
  • 链式角色会话被限制为一小时，即使目标角色配置允许更长。
  • 初次从用户凭证假设角色和 EC2 instance profile 场景不应套用同一限制。

当程序用一个角色的临时凭证再调用 AssumeRole 获取另一个角色时，AWS 称之为 role chaining，链式会话最长限制为一小时。目标角色的最大会话时长即使设得更长，也不能取消这项限制。反过来，若是用户凭证第一次假设角色，或 EC2 实例通过 instance profile 获取角色凭证，则不能因为看到“一小时”就断言所有会话都必须在一小时结束。排查时先追踪凭证来源链，再看目标角色配置。

先把角色链画出来

常见链路包括：用户或联合身份先获得角色 A 的凭证；应用使用 A 的临时凭证调用 STS AssumeRole；STS 返回角色 B 的另一组临时凭证；应用再用 B 访问目标资源。第二次调用是“已有角色凭证再假设另一个角色”，因此属于 role chaining。目标角色的 MaxSessionDuration 是一个配置边界，却不是链式调用能绕过一小时限制的通行证。

另一条路径是用户凭证直接假设角色 A，没有“角色 A 临时凭证再调用 AssumeRole”这一跳。AWS IAM 文档明确指出，一小时限制不适用于从用户凭证初次假设角色；也不适用于 EC2 instance profile 上运行的应用。身份联合、工作负载身份与角色链的具体边界，需要按实际 STS API 和凭证提供程序确认，不能只看最后获得的 AccessKey 以 ASIA 开头或看目标角色名称。

假设的长任务：跑了 70 分钟后突然拿到过期错误

假设一个 CI 作业先从 OIDC 联合身份取得角色 A，再 AssumeRole 到部署角色 B；部署任务需要 90 分钟。若把 B 的最大会话时间设成 12 小时，开发者可能预期 B 的凭证会一直有效。实际链式限制仍可能让该会话最多持续 1 小时。前 55 分钟部署正常，后续上传调用因临时凭证过期失败。把目标角色配置改大不会延长这条链的有效上限。

若任务在第 55 分钟刷新凭证，还要确认凭证提供程序能重新获取上游 A 凭证、调用链每一步都仍有授权，并且刷新不会改变目标账户或角色。若重新假设角色时源凭证已过期，或工作流 token 已不可用，刷新逻辑也会失败。这里是依据 AWS 限制构造的假设时间线，并非某次 CI 事故报告。

长任务的三个设计方向

首先减少不必要的角色跳数。如果一个受信任工作负载可以直接获得最小权限的目标角色，可能无需中间角色；但这会改变信任策略和账户边界，不能仅为延长会话而扩大权限。其次设计短时凭证续期：在会话过期前通过可持续验证的身份来源再次请求凭证，并确保每次 AssumeRole 都满足信任关系与会话策略。最后把任务拆分为可恢复阶段，使阶段间保存状态而非依赖一组固定凭证跑完整个长流程。

续期并不等同于长期密钥。临时凭证应尽量短寿命、只具备所需动作与资源范围，刷新日志不能包含 secret access key 或 session token。也要考虑每次角色假设的 session tags、外部 ID、source identity、MFA 或权限边界，保证续期后的会话不意外扩大授权。若无法刷新或需要人工审批，任务应停在可审计、可重试的阶段，而不是静默使用过期凭证。

怎样从日志和配置证明这是 role chaining？

为每次凭证获得记录非秘密的身份信息：调用主体 ARN、目标角色 ARN、AssumeRole API、请求时长、会话名、source identity 与 CloudTrail 事件时间。不要记录完整凭证。对照调用序列确认第二跳的调用者本身是否为角色临时身份；仅看目标角色最大时长不足以判定。检查 AWS 错误是否指向超过链式限制，并确认客户端时钟偏差不是另外的过期原因。

在隔离账户用两种路径对照：用户凭证直接假设角色与角色 A 凭证再假设角色 B；分别申请超过一小时的 duration，并验证服务端实际返回的过期时刻。再测试任务运行期间续期、上游身份撤销、STS 暂时不可用和目标信任策略变化。不要把一次模拟测试结果推广到组织内所有 SSO 或 OIDC 提供程序，尤其是其调用链可能有隐藏中间角色时。

什么时候减少链路，什么时候定期刷新？

短任务或可阶段恢复的工作，最简单的是接受一小时上限并设计清晰的失败处理。长任务若必须跨账户，应选显式续期或拆分阶段，并把主体链写入运维手册。直接角色假设可以降低复杂度，却可能改变安全边界；额外中间角色可以隔离信任，但增加凭证续期和审计复杂度。选择依据是授权最小化、身份来源可靠性、任务恢复能力和审计要求，而不是只看一个角色配置里的时长。

本文根据 AWS IAM 文档解释 role chaining 的一小时边界，没有访问 AWS 账户或执行 AssumeRole。上线前应检查真实 OIDC/SSO/EC2 凭证链和 CloudTrail，确认哪些调用属于第二跳。凭证能否续期、是否允许用户身份长期存在以及作业的业务幂等性，都是单独的设计问题。

刷新权限也应从源身份到最终资源逐层审计。应用续期成功，只说明 STS 返回了新凭证；它不保证新凭证仍具有预期 session policy、tags 或 resource scope。对比刷新前后的 caller/role ARN、过期时间、权限模拟结果与 CloudTrail 事件，确认角色链没有因 fallback provider 选错身份而回到开发者个人凭证。失败时应明确停止、告警或转入人工恢复，不要把获取长期静态密钥作为自动续期兜底。

延伸阅读：本站刷新令牌重用与 token family 撤销。STS 角色会话不是 OAuth token，但两类凭证链都不应通过长期静态密钥掩盖来源不明的问题。
