Python 3.14 buffersize 限制了并行提交，却没有改变结果顺序

Executor.map 的 buffersize 在 Python 3.14 限制已提交但尚未 yield 的任务数量；map 仍按输入顺序交付结果。它提供有界背压，不是完成顺序流。

正文

核心要点

  • 没有 buffersize 时，Executor.map 会先收集输入 iterable。
  • 达到 buffersize 后会暂停继续取输入，限制未交付结果对应的已提交任务。
  • 结果仍按输入顺序 yield；慢的早期任务会造成队头等待。

Python 3.14 的 Executor.map(..., buffersize=n) 可以限制并行 map 已提交、但结果尚未交付的任务窗口。它会在窗口达到上限时暂停从输入 iterable 继续取值，避免无限输入被一次性变成大量 Future；但结果仍按输入顺序 yield。也就是说，它提供有界提交与背压，不会把 map 改成“谁先完成就先返回”。选择它之前，要确认调用方要的是有序输出，还是按完成时间消费结果。

buffersize 限制的是什么？

传统 Executor.map 在没有缓冲限制时，会收集输入 iterable 后提交任务。对有限的小列表这很方便；对数据库游标、文件流或无限生成器，它可能提前读取大量项目并创建大量待处理工作。Python 3.14 增加 buffersize：当已提交任务中尚未被结果迭代器 yield 的数量达到此值，输入迭代会暂停，直到有结果被取出、空出窗口。这个参数改变的是从输入到结果迭代器之间的在途工作量，不是线程数或进程数本身。

max_workers 与 buffersize 作用在不同层面。前者控制执行器中可并行工作的 worker 数；后者控制允许积压多少个已提交且尚未从 map 迭代器取走结果的任务。比如设置 8 个 worker 和 16 个 buffer，通常意味着最多允许约两个 worker 波次在前后排队，但真实内存还受到每项输入、结果大小、任务内部缓存和执行器实现影响。不能用 buffer 值直接推导进程内存上限。

为什么有 buffer 仍会被慢结果卡住？

官方接口保持输入顺序。假设任务 0 需要 20 秒，任务 1 到 15 只需 100 毫秒。尽管后面的 Future 很早完成，迭代器仍会先等待任务 0，然后才逐个交付后续结果。窗口中结果未 yield 的任务会持续占用 buffer 槽位；当这些槽位填满后，生产端暂停读取新输入。这种头部阻塞不是 buffersize 的错误，而是顺序交付语义与有界缓冲一起产生的背压。

如果业务要求“尽快处理任一完成项”，Executor.map 可能不是最合适的抽象。可以使用 submit 和 as_completed 管理 Future，或者自己维护一个有上限的待处理集合；但改成完成顺序就失去了按输入位置自然对齐的结果。需要将输入 ID 与 Future 显式关联，再在消费时决定是否要重排。选择之前应明确顺序是产品正确性要求、方便性，还是偶然依赖。

假设例子：慢首项与大结果的内存权衡

假设一个生成器逐条读取压缩日志，每条任务解析成大型对象，调用方按源文件顺序输出报表。max_workers=8、buffersize=8 可以让初始任务并行执行，同时限制未取回结果的窗口大致维持在一个执行波次。如果任务 0 格外慢，后续完成结果会占据窗口，生成器暂停继续读取文件。这限制了输入和结果积压，但也降低了利用空闲 worker 继续预读的机会。提高 buffer 可能改善波动情况下的利用率，也会保留更多未消费结果；降低 buffer 则更省积压空间，却可能使 worker 等待输入。数值是解释权衡的假设，不是性能推荐。

另一个失败情况是消费者读取结果后阻塞在网络写入。此时 map 迭代器无法及时 yield 结果，窗口继续满，生产端背压是预期行为。如果系统把暂停误报成“线程池卡死”，排障会去扩大 worker 数，却没有解决慢消费者或输出端积压。应该分别记录输入生产、任务执行、结果交付和下游写入的时间，确认瓶颈位于哪一步。

怎样选择窗口并验证背压？

先估计任务处理峰值、单项输入和结果的典型/极端大小、消费者速度，以及能容忍多少已提交但未消费的结果。buffer 不宜只按 worker 数照抄；它还要容纳偶发慢任务与消费者短暂停顿。可从一个 worker 波次开始，在隔离环境逐步增大，观察执行器占用、内存峰值、输入读取速率和结果等待时间。若结果对象很大，较小窗口的收益可能超过多几个并行任务的吞吐；若工作负载稳定且结果很轻，稍大的窗口可能减少 worker 饥饿。

测试至少覆盖：惰性生成器是否在 buffer 满时停止读取；早期任务慢时是否仍按输入顺序产出；任务抛出异常时异常在迭代哪个结果时暴露；消费者放慢时窗口是否回压；取消或关闭执行器后剩余 Future 如何处理。不要只测试 list(executor.map(...)) 的最终结果，因为把输出一次性收集会隐藏消费者节奏和内存窗口。教程中的数值和时间线均是假设，本文没有运行基准或 Python 任务测试。

它适合什么，不适合什么？

buffersize 适合保持输入顺序，同时让输入源和待交付结果都有明确上限的任务，例如有序转换流、批量文件处理或外部游标消费。若输入天然有界且很小，默认行为可能更简单；若任务需要立即消费任意完成项，显式 Future 管理更直接；若想要严格的端到端内存预算，还需要限制输入对象、任务内部缓存和下游队列。它只约束 map 提交窗口，不负责关闭数据库游标、取消远程任务或恢复失败副作用。

在版本边界上，buffersize 是 Python 3.14 的新增参数；旧版本调用会拒绝该关键字。部署时应按实际解释器版本检测，而不是只根据开发机文档更新代码。本文依据 Python 3.14 官方库文档，没有声称在项目环境执行。最终选择取决于顺序语义、对象体积和消费者节奏，而不是把一个整数误当作通用“并发度旋钮”。

如果输入 iterable 会产生副作用，例如读取游标时推进 checkpoint，暂停消费就不只是内存选择，也会改变上游资源的持有时间。窗口满导致生成器停顿时，数据库事务或文件句柄可能保持打开；应让生产器能够安全暂停、关闭和恢复，避免把背压传播成锁占用。也要确认异常后结果迭代器关闭时，输入源是否执行清理。将 buffersize 纳入端到端资源预算时，任务队列、源连接和结果缓冲都要一起估算，而不是只统计 Future 数量。

版本测试也要包括异常退出。若消费方在第 k 个结果处抛异常，for 循环结束不一定意味着所有已提交工作已停止；任务可能仍在运行或结果仍被 Future 持有。将 executor 的关闭策略、取消待运行任务与生成器清理作为独立验收项。buffersize 约束映射窗口，但不等于自动取消、超时或资源回收。对会修改外部系统的任务，关闭执行器前还要定义正在运行调用的结果未知时如何幂等恢复。

延伸阅读：本站Semaphore 被过量释放的并发故障。Executor.map(buffersize=...) 限制映射提交窗口；它既不是 asyncio semaphore，也不会定义任务关闭和取消语义。
