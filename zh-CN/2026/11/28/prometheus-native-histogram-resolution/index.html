Prometheus 原生直方图合并后桶变少，为什么不是采集丢数？

原生直方图 schema 决定指数桶分辨率。向下缩放会合并桶并减少细节；理解 schema、插值假设和存储预算，才能解释查询结果差异。

正文

核心要点

  • 标准 schema 的数字越高，相邻指数桶越密；增加 1 会把桶分辨率加倍。
  • 兼容缩放可合并相邻桶，减少细节但保留总体范围。
  • 分位数估算依赖桶布局和插值假设，不能把 schema 变化当成原始样本变化。

Prometheus 原生直方图查询后桶数变少，不一定代表样本丢失。原生直方图的 schema 决定指数桶分辨率；在标准 schema 中，schema number 增加 1 会把分辨率加倍，边界更密。为了合并不同分辨率的数据或控制存储和传输成本，桶可以向下缩放并合并，细节因此减少。排查时先比较 schema、缩放与查询路径，再判断是否真有观测丢失。

schema 表示的是桶空间分辨率

指数直方图将正值和负值范围拆分到对数尺度相邻桶。标准 schema 号定义相邻边界之间的倍数关系；schema 越高，区间被分得越细。Prometheus 的 Native Histograms 规范解释，增加 schema number 1 相当于将桶分成两个、分辨率加倍。这个参数不是“样本精度”或“单位时间采样率”，也不意味着每个观测都以更高精度被测量；它控制的是聚合桶边界的密度。

缩放到较低 schema 时，相邻细桶可以合成更粗的桶，以便表示不同分辨率的数据或控制数据体量。合并不会凭空改写观测总量，但会丢掉区分细桶内部位置的细节。若 SLO 阈值刚好落在被合并的区间中，分位数估计可能更粗。查询端对桶内分布使用插值假设；Prometheus 文档说明标准 schema 使用指数插值，假设细分后新增桶平均获得相似人口。真实数据分布若高度偏斜，这个假设就影响估计。

假设例子：阈值落在合并区间附近

假设某服务跟踪请求延迟，p99 目标是 500ms。较高分辨率 schema 在 450ms 与 510ms 附近有多个桶；某个接收端为了兼容较低分辨率，把数据向下缩放，附近桶被合并成一个更宽区间。查询仍能给出分位数估计，却无法从该桶恢复每个观测落在 470ms 还是 505ms。图表可能出现轻微变化，即使原始请求分布并未同步改变。

此时错误做法是把新旧 quantile 差异直接叫作“延迟恶化”，或反过来认为“桶总数没变就没有问题”。应对齐同一时间窗口的 schema、sum/count、正负桶、零桶和查询函数，检查采集、远程写入、存储与查询是否有不同的缩放。示例数值是假设说明，没有运行 Prometheus 或测量真实延迟。

分辨率与成本如何权衡？

更高分辨率会更准确地定位阈值附近分布，但对每个样本群组可能产生更多非空桶；数据量、远程传输和聚合成本可能随工作负载增加。降低 schema 可缩小桶数、提高合并兼容性，却使边界附近的分位数估计变粗。选择时以决策需求为准：若告警只区分“明显高于 500ms”，较粗粒度也许够用；若产品决策要求区分 490ms 与 505ms，必须验证分辨率足以支撑该差异。

不要先按平均桶数估算成本，再把统一 schema 套到所有指标。低流量端点、高基数标签或双峰/长尾分布可能形成不同的非空桶模式。应在目标采集、压缩、remote write、存储和查询版本上测量真实样本，结合保留期、标签数和查询频率评估。Native Histogram 的支持与配置在不同 Prometheus 版本和组件中有边界；只有实验通过并不代表整个生产链路都保留相同分辨率。

如何定位桶差异来自哪里？

保留原始样本管道中各阶段的 schema 与直方图字段：应用生成、scrape、remote write、接收端存储、读取 API 和 PromQL 结果。比较每一步的 count、sum、schema、零桶与正负桶边界；若 count 一致而 schema 降低、桶合并，则更可能是分辨率缩放而非观测数量丢失。若 count 也下降，要检查采集失败、过滤、限流、队列溢出和时间窗口对齐。

设计一个受控数据集，在预设阈值两侧放置观测，然后用多种 schema 写入与合并，比较输出桶与 quantile。确保测试覆盖边界附近的集中分布、长尾、稀疏值与零值。记录查询端插值策略和组件版本。不要用仪表盘像素变化替代数值验证；绘图分辨率、查询步长和插值都会影响视觉曲线。

什么时候可以接受降分辨率？

当存储预算、网络或聚合兼容性比边界估计更重要，且业务阈值相对宽，降低 schema 可能合理。对需要高精度阈值判断的 SLO，应使用匹配的分辨率并监测下游是否发生缩放；若无法保证，就把告警设计成对估计误差有容忍度。不要把 histogram schema 与传统 bucket histogram 的显式边界混为一谈，它们具有不同的表达与合并方式。

本文依据 Prometheus Native Histograms 规范说明标准 schema、合并与插值，不包含基准或真实集群观察。落地需要在实际 Prometheus/remote write 版本、采样配置和负载下测试桶增长、查询准确度与存储成本。桶变少可能是缩放的有意结果，但是否能接受取决于决策阈值，而不是桶数本身。

聚合规则要保持可追溯的分辨率变化。若 recording rule 把多个来源的直方图合并，查询结果的 schema 可能由最粗输入和转换能力共同决定；只在 dashboard 查询时检查原始 scrape schema 不够。将聚合前后 schema 与 count 写入回归样本，可以在升级 Prometheus、remote write 或规则配置时发现意外降采样。若阈值告警对近边界结果敏感，应以更粗粒度的输入做保守测试，而不是只测试理想最高分辨率。

延伸阅读：本站Prometheus 记录规则的标签合同。聚合前后应分别核对标签身份与 histogram schema，避免把实例合并误认为分辨率变化。

比较时不仅要对齐 schema，也要对齐样本群体。若 recording rule 改了标签，即使 count 相近，新旧直方图也可能代表不同 endpoint 集合。比较分位数前先固定时间窗、标签集合、reset 边界和 schema，再检查阈值落在一个粗桶内还是跨越多个细桶。这样复核才能回答两个问题：代表的请求群体是否变化，以及桶布局是否丢失了决策所需的细节。
