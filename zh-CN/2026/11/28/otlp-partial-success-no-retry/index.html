OTLP 部分成功后，为什么不能把整批遥测再发一次？

OTLP 的 populated partial_success 表示一次请求可能已有部分数据被接收；协议要求客户端不要重试整个请求。将拒收统计、错误原因和可重试响应分开处理。

正文

核心要点

  • partial_success 报告被拒绝的信号项，不是普通的全量暂时失败。
  • OTLP 规范规定 populated partial_success 响应不得重试整个请求。
  • 应观测 rejected 数量并处理数据质量，而不是用全量重发掩盖拒收。

OTLP 响应中的 partial_success 已填充时，客户端不能把原请求整批重试。OpenTelemetry Protocol 规范明确要求 client MUST NOT retry 这种请求：服务器可能已经接收其中一部分，只拒绝了其余 signal items。把它当成普通 503 或网络断开来做全量重发，会让已接收的 span、metric 或 log 再出现一次；而把整批丢掉，又会连同被拒绝项之外的有效数据一起损失。处理逻辑应按协议区分部分接受、可重试状态与永久无效数据。

partial_success 表达的是部分结果，不是事务回滚

OTLP 的 partial success 结构可包含 rejected_spans、rejected_data_points、rejected_log_records 或 rejected_profiles 等计数，以及服务器给出的错误说明。它描述拒绝了多少项目；并不提供能让客户端安全重放整个请求的事务 ID，也不表示服务器撤销了其余已接受数据。一个 request 可能含有多种有效和无效记录，服务器对每个信号类型的处理按规范定义，但客户端不能据此假设“没成功的那部分可以连同其他内容一起重试”。

规范还允许服务器在完整接收请求时使用 partial_success 字段传达警告或建议；在这种情况下，拒绝计数必须为 0，错误说明应非空。因此不能只根据 partial_success 对象存在就认为有数据丢失。读取 rejected count、错误说明和响应状态，按字段语义确定是全量接受但有提示，还是部分拒收。协议版本和 exporter 对响应字段的支持也要核对。

假设批次：100 条 span 中 3 条被拒绝

假设 exporter 发送包含 100 条 span 的 OTLP 请求，collector 报告其中 3 条被拒绝。剩余记录可能已经接收。若 exporter 因看到“错误消息”而重发 100 条，就可能让其余已接收 span 重复进入下游；若直接把整个 batch 标成成功，则 3 条丢失的数据也没人跟踪。可行做法是停止整批自动重发、增加 rejected 计数指标并保留错误分类，再检查被拒绝数据的共同属性，例如字段类型、资源属性或容量限制。这里的数字仅是说明协议语义的假设示例，没有运行 collector。

另一个失败模式是 exporter 把 partial success 映射成无错误返回。上层会认为所有数据都到达，拒收数却被隐藏；或者 exporter 把它映射成一般可重试错误，导致全量重放。集成测试应验证确切响应字段如何经过 exporter、队列与告警系统，而不是只测 HTTP 状态码。上游文档和 collector 日志都应保留足够信息，避免只出现“部分失败”这一模糊文本。

为什么不能只挑出被拒绝的数据自动重试？

协议计数告诉客户端拒绝了多少项目，却未必提供每个具体记录的稳定索引或可重放批次 ID。因此从 rejected_spans=3 不一定能直接还原哪三条；若 exporter 自己保留了原始 batch 和精确拒绝映射，理论上可以有更细粒度的恢复设计，但不能假设服务器响应已经提供这种映射。任何自定义重试都要确保不会把原先接受的记录再次发送，也不能无限保存敏感遥测 payload。

遇到数据永久无效时，OTLP 规范要求按相应错误处理而不是重复发送同一无效数据。Exporter 可将丢弃计数、错误原因和 resource/scope 标签纳入监控；若问题来自可修复的配置或 schema，应修复后只处理确实未被接收的数据来源。若无法确定接受边界，需记录“结果部分已知”的状态并通过 collector 观测、下游去重或数据审计补足，而不是假装 exactly-once。

如何设计测试与告警？

构造至少四种响应：全量成功且没有 partial success；rejected count 为零但带 warning；部分拒收并包含非空错误说明；不可重试的永久错误。验证 exporter 对每种情况的返回、队列确认、丢弃策略和重试次数。特别确认 populated partial_success 不触发整个请求重发，rejected 计数会增加，响应仍能被关联到导出批次。测试还应覆盖进程重启后队列持久化，以免“没有重试”变成静默丢失。

告警不应只盯 HTTP 失败率。可以追踪按 signal 类型拆分的拒收项数量、拒收比例、错误类别和连续窗口趋势；采集端的请求数与 collector 接收量需要用同一窗口比较。比例上升可能来自 schema 更改、限流、资源属性变更或 exporter bug，不能一看到拒绝就扩容 collector。本文没有执行 SDK、exporter 或 collector 测试，只有协议文档证据；具体行为以项目使用的 OTLP 版本和实现为准。

什么时候才能重试？

应区分协议指定的可重试传输状态、部分成功和永久坏数据。对于 partial success，按规范不要重发完整请求；对于暂时不可用且规范允许重试的响应，使用有上限的退避与队列策略；对于格式错误或永久拒绝的数据，记录并丢弃或进入受控隔离流程。恢复边界必须有稳定证据：客户端能识别未接受的具体项目，或业务层有可验证的去重键，否则拆批重发也可能形成重复。

OTLP 不是一个事务数据库接口。它没有承诺一次 Export 对所有遥测记录原子提交，也不提供业务意义上的唯一接收保证。Exporter 的职责是遵循规范、暴露被拒收信息并防止错误重放；运维者的职责是调查拒收原因和数据完整性边界。把这两者分别设计，才不会用简单的“失败即重试”掩盖部分接受事实。

拒收计数还要与 exporter 内部队列指标配合。若 rejected_spans 上升而队列长度稳定，问题可能集中在数据格式或 collector 策略；若队列也不断增长，说明发送速率、接收能力与重试策略可能同时失衡。把拒收率按 instrumentation scope、resource attributes 和 exporter 版本拆分，能定位最近变更，但要限制标签基数。保存错误信息时应避免把用户数据原文写入日志；采样和脱敏不应删除用于修复的字段类型与错误类别。

延伸阅读：本站尾部采样能否找回已经丢失的链路。先判断数据是在生成前过滤，还是在传输或接收阶段消失，才能选择检查采样、exporter 队列还是 collector 响应。
