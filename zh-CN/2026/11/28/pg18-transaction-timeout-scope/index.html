PostgreSQL 18 事务超时，为什么会把连接一起结束？

PostgreSQL 18 的 transaction_timeout 限制的是一次事务占用会话的总时长，触发后会终止会话。理解它与语句超时、空闲事务超时的比较关系，再决定按角色或连接设置。

正文

核心要点

  • transaction_timeout 触发时终止会话，不只是取消当前 SQL。
  • PostgreSQL 18 会比较事务超时与语句、空闲事务超时，较长的一项可能被忽略。
  • 全局配置会影响所有会话；应先界定工作负载，再用受控范围验证断连与重试行为。

PostgreSQL 18 的 transaction_timeout 不是“慢 SQL 到点就取消”的另一种写法：事务持续时间超过阈值时，服务器会终止该会话。事务中的应用连接因此不再可继续执行后续语句，连接池也必须把它视为失效连接。要不要启用它，首先要回答的不是“阈值设几秒”，而是“哪些事务类型允许占用连接多久，以及被终止后业务如何恢复”。

三种超时保护的是不同区间

statement_timeout 针对单条语句从服务器收到到完成的执行时间；idle_in_transaction_session_timeout 针对事务已经打开、但客户端暂时没有发出语句的空闲时间；transaction_timeout 则覆盖事务存在的总时长。一次事务可以先运行几条各自都没有触发语句超时的 SQL，中间再停顿一会儿，最后仍因为累计时长越界而被终止。它的目标是把事务占用会话的时间封顶，并不告诉你具体哪条语句慢，也不能替代锁等待、查询计划和连接池治理。

PostgreSQL 18 文档明确指出，transaction_timeout 同时适用于显式事务和对应单条语句的隐式事务；默认值 0 表示关闭。如果它短于或等于 statement_timeout 或 idle_in_transaction_session_timeout，较长的那个超时会被忽略。这种比较意味着不能把几项配置各自看一遍就认为三项保护都会按预期独立触发。应把它们放在同一条时间线上，问清谁先到期、到期后的连接状态是什么。

假设时间线：一条请求跨过了事务上限

假设服务把一次用户操作包在事务中：先读一行，等待外部系统返回，再更新余额。读和更新分别只花 100 毫秒，但外部等待持续 4 秒。若语句上限为 2 秒、事务上限为 3 秒、空闲事务上限为 5 秒，单独看每个 SQL 都很快，却不能推出整笔事务安全：外部等待期间可能处于事务空闲状态，或者事务累计跨度达到上限；具体哪个超时先发生，取决于它们开始计时的时点与连接当前状态。这里的数值只是用于解释时序的假设，并非推荐配置。

当 transaction_timeout 到期，客户端可能看到连接断开，事务是否提交不能靠“请求超时了”推断。若客户端只做一次盲目重试，服务端可能已在客户端观察到断连前完成提交，也可能根本没有提交。安全恢复需要业务幂等键、事务状态查询或可重放的命令模型；数据库端终止会话并不会替应用提供恰好一次的业务保证。更合适的事务通常也不应跨越网络调用：先在数据库中读取必要状态，完成外部工作后再用版本条件或幂等键提交，能缩短连接被占用的窗口。

为什么不应直接把它写进全局配置？

PostgreSQL 文档不建议在 postgresql.conf 全局设置 transaction_timeout，理由是它会影响所有会话。迁移脚本、交互运维会话、批处理、长查询和在线接口的合理事务时长可能完全不同。一个对在线请求有效的短值，可能把批处理正常工作切断；把值调很大来保护批处理，又可能让交互会话长期占用连接。全局值会把这些不同合同压成一个数字。

更稳的做法是先统计工作负载的事务跨度分布，并按连接角色、数据库或事务入口划分保护范围。优先从服务连接池的专用角色开始，在预发布环境验证事务被终止后的驱动错误、连接淘汰、事务回滚及重试路径。若使用会话级设置，还要检查连接池复用连接时设置是否会泄漏到下一位请求；若用角色级默认值，需用该角色实际建立连接，确认服务器最终生效的值。不要仅凭配置文件改动就认为现有连接已按新策略运行。

怎样验证配置真正起作用？

先记录当前 PostgreSQL 主版本和三类超时的有效值，再用隔离测试事务覆盖四种路径：单条语句先达到 statement_timeout；事务先空闲达到 idle 超时；多个短语句使总事务跨度越过 transaction_timeout；配置关系使一项较长超时被忽略。每个测试都应同时收集服务器日志、客户端错误、连接池健康状态与事务结果。测试后确认该会话确实终止、池中新请求取得新连接，并检查已执行写入是否回滚。

验证期间不要只看 SQL 客户端弹出的“取消”消息。驱动可能把断线、取消和服务端错误映射成不同异常；应用层若把它们都归为可重试错误，容易重复执行非幂等操作。将连接标记失效、事务结果设为未知、业务重试交给幂等策略，是比自动重发整段 SQL 更保守的状态设计。具体行为还取决于 PostgreSQL 驱动、连接池和事务边界，本文没有对某个生产栈做实测。

选择依据和适用边界

如果主要风险是遗漏的长事务或客户端在事务中等待太久，transaction_timeout 可以提供总跨度上限；若问题是单条查询消耗资源，statement_timeout 更直接；若问题是事务打开后应用不再工作，idle_in_transaction_session_timeout 更贴近原因。三者不是互斥选项，但必须结合优先关系和故障恢复设计。运行长时间分析任务的系统可能需要单独角色或独立连接策略，而不应悄悄提高所有在线请求的上限。

本文说明的是 PostgreSQL 18 官方参数语义，不是任何集群的推荐秒数。上线前应核对实际主版本、参数生效范围、驱动与池的断连处理，并通过可回滚的隔离测试确认提交不确定路径。超时能限制资源占用，却不能证明事务安全、请求可重试或业务结果唯一；这些仍要由应用的事务设计和幂等合同承担。
