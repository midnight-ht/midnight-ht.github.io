CORS 权限改了，浏览器为什么还会沿用旧预检结果？

Access-Control-Max-Age 缓存的是预检中的方法和请求头许可，浏览器还可限制其最大时间。策略调整不等于立即清空所有客户端缓存，服务端授权仍需独立执行。

正文

核心要点

  • Fetch 将 Access-Control-Max-Age 定义为预检方法和请求头信息的缓存秒数，缺省为 5 秒。
  • User agent 可以施加更低的上限；服务端不能假设所有浏览器都缓存同样久。
  • CORS 预检许可不是身份验证或服务端授权，实际请求仍要检查权限。

改变 CORS 配置后，浏览器不一定会立刻重新发送预检请求。Access-Control-Max-Age 指定预检得到的方法与请求头许可可缓存多少秒；Fetch 标准规定缺省 5 秒，user agent 可以施加自己的最大值。因此策略刚撤销时，已有客户端可能还在有效缓存窗口中沿用旧预检结果。它不意味着浏览器忽略服务端，也不意味着跨域请求已经获得用户身份或业务授权。

预检缓存保存的是什么？

当浏览器要发送需预检的 CORS 请求时，会先发送 OPTIONS，询问服务器是否允许来源、方法和请求头组合。服务器可通过 Access-Control-Allow-Methods 和 Access-Control-Allow-Headers 表示允许范围；Access-Control-Max-Age 为这些预检信息提供缓存时间。Fetch 的预检缓存不是一般 HTTP 响应缓存，也不等于把业务 API 的响应缓存起来。它让浏览器在缓存匹配时减少重复 OPTIONS，但实际请求仍会发到服务器。

标准规定缺少 max-age 时默认 5 秒；若值超过浏览器施加的上限，浏览器按自己的较低上限处理。不同客户端最大值可能不同，开发者不能只按服务端返回的秒数推算真实窗口。预检缓存匹配还涉及请求来源、URL、凭据模式、方法与请求头等条件；修改一个请求条件可能产生另一条缓存记录，不应把它简化成“这个域名缓存了 CORS”。

假设撤销：服务端新规则生效，浏览器仍发出实际请求

假设 API 原先允许 https://admin.example 使用 PATCH 并携带 X-Change-Reason，预检 max-age 是 600 秒。部署时撤销该方法许可，但某用户浏览器在 30 秒前已成功预检。只要其缓存条目仍有效，浏览器可能跳过新的 OPTIONS 并发送实际 PATCH。服务器新策略若只在 OPTIONS handler 上返回“拒绝”，却不在 PATCH handler 检查账户与操作权限，业务写入仍可能发生。

反过来，若实际 PATCH 的响应缺少正确 CORS 头，浏览器可能不把响应暴露给脚本，但服务器可能已经执行了写操作。CORS 主要控制浏览器是否把跨源响应共享给页面脚本，不是防止所有跨站请求的身份校验机制。开发者看到 JS 报 CORS error，不足以证明服务器没有接收或处理请求。这里是协议边界示例，没有对真实服务做请求实验。

凭据请求让规则更严格

带凭据请求时，Access-Control-Allow-Origin 不能简单使用 * 并同时允许凭据；服务器需要返回匹配的具体 origin，并正确处理 Access-Control-Allow-Credentials。允许哪些方法和头部也要明确列出，通配符对含凭据的请求受限制。若允许来源是动态列表，响应还要处理缓存键与 Vary: Origin，避免共享缓存把一个来源的允许响应泄漏给另一个来源。

缩短 max-age 可以让配置变更更快传播，但会增加 OPTIONS 流量；延长它可减少预检请求，却扩大客户端继续使用旧许可的窗口。若要紧急撤销一种危险写操作，仅调小新响应的 max-age 不能立即改变已有缓存；需在实际业务处理端撤销授权、使用版本化 API/路径或部署即时拒绝条件。不要把 CORS 缓存作为安全撤销机制。

怎样验证撤销窗口和服务端真实行为？

在目标浏览器建立一组预检缓存测试：先完成允许的预检并重复同一请求，观察 OPTIONS 是否省略；改变方法、请求头、origin 或 credentials mode，检查是否生成不同预检；更新服务端规则后，在缓存过期前与过期后分别验证浏览器行为。记录请求时间、OPTIONS 与实际请求是否到达、服务器状态和响应头。使用干净 profile 只能测试冷缓存，不能替代已有用户的热缓存路径。

更重要的是，直接对实际 API 发送没有合法身份或权限的请求，确认服务端拒绝，即使测试环境人为跳过浏览器 CORS 限制。检查授权中间件是否在写入前运行，审计日志能否区分“预检拒绝”与“业务操作拒绝”。如果只观察浏览器 console 的报错，会把响应共享失败与服务器拒绝写混为一谈。

选择 max-age 的依据

低风险、变更频繁的 API 可以使用较短缓存以缩短策略传播窗口；稳定、读取为主且 OPTIONS 成本明显的请求可以评估较长缓存，但要先确认客户端上限与紧急撤销方案。真实选择取决于浏览器分布、预检负载、策略变更频率和 API 本身的服务端授权。max-age 不应用于隐藏不一致的 CORS 配置，也不是替代访问令牌轮换或权限撤销。

本文按 WHATWG Fetch Standard 的预检缓存语义说明，未运行浏览器测试或服务器实验。实现时请按目标浏览器测量实际缓存上限，并验证 CORS、认证、授权和写入执行的不同层。即使浏览器复用了缓存许可，服务器仍必须对每个实际业务请求做身份与权限判断。

预检结果被缓存时，授权头与业务 token 的轮换也要分开看。预检缓存允许的方法/头部是一种浏览器协议状态；Access token 到期、撤销或服务端账户权限变化是另一种状态。即使浏览器不再发 OPTIONS，服务器仍可在实际请求中拒绝旧 token 或已撤销权限。若服务器把 OPTIONS 的 allow 结果当作后续 PATCH 的授权票据，缓存窗口会变成安全缺陷，而不是性能参数。

延伸阅读：本站个性化响应的私人与共享缓存边界。预检许可缓存与代理响应缓存存放的对象不同；一个层命中不代表另一层已经授权请求。

因此策略回滚要看两条时间线：浏览器预检缓存决定新的跨域请求何时可以跳过 OPTIONS，应用授权检查决定此刻能否执行操作。新规则撤销后，已有缓存的客户端可能仍会发送请求，但服务端可以立即拒绝该操作。部署期间分别记录预检响应和业务授权决定，值班人员才能区分浏览器中的旧许可提示与真实访问控制故障，不必等待所有客户端缓存过期。
