Go context 被多个原因取消，Cause 为什么只留下一个？

WithCancelCause 让 Go 调用方提供取消原因，但它不是原因列表：最先生效的取消决定 Context 的 Cause。把控制流取消与多原因诊断分开，避免日志把竞态解释成因果。

正文

核心要点

  • Context.Err 表示通用取消状态，context.Cause 返回第一次生效的具体原因。
  • 父级和子级取消竞速时，一个 Context 不会自动积累所有取消原因。
  • 若需要解释多个候选原因，应另记结构化事件，而不是把 Cause 当审计历史。

Go 的 WithCancelCause 允许调用方给取消操作附上原因，但 context.Cause(ctx) 不是多个原因的集合。一个 Context 只保留第一个影响它的取消结果；父级 deadline、客户端断连和本地策略取消若同时发生，最终 Cause 取决于哪个取消先到达该 Context。ctx.Err() 与 context.Cause(ctx) 回答的问题也不同：前者说明它已经取消，后者提供具体 cause。把 Cause 当成完整故障记录，会把并发竞态误写成唯一因果。

为什么两个取消查询会返回不同内容？

旧的 Context API 用 Err 表示 context.Canceled 或 context.DeadlineExceeded 这类通用结束状态。WithCancelCause 增加了由调用方指定具体错误的路径；取消后，Err() 仍用于控制流判断，而 context.Cause() 返回附带的原因。代码因此可以用 errors.Is(ctx.Err(), context.Canceled) 判断是否应停止，同时在日志里记录更具体的“用户断开”或“配额取消”。原因不会改变取消这个事实，也不会自动携带整个上游调用链的所有失败。

Go 的实现有一个重要的首次取消规则：对于一个派生 Context，父级或子级取消中最先生效的原因决定相应 Context 的 Cause；之后的取消不会把原因追加成列表。父级先取消时，子 Context 通常继承父级原因；子 Context 已先由自己的 cancel cause 取消，后续父级取消不会覆盖它。这个语义适合一次性控制流结束，不适合把多个同时失败的依赖压缩成完整诊断模型。

假设竞争：断连与 deadline 几乎同时出现

假设一个 HTTP handler 为下游 RPC 建立带 cause 的 Context，并同时监听客户端断连和内部 deadline。某次请求在 deadline 到达附近断开。若断连回调先调用 cancel，Cause 可能是“客户端离开”；若计时器先取消，它可能是 deadline 错误。一次运行中只有胜出的第一个原因出现在该 Context 上。日志记录 Cause 是有用的，但不能由此断言另一个条件从未发生；它只是没有成为这个 Context 的终止原因。

更清晰的设计是把“控制流主因”和“观测到的事件”分开。Context cause 可以选择一个用于停止工作的终止原因；诊断事件流则可在单独的结构化日志或 span event 中记录 deadline 已触发、连接断开已观察到、哪个下游已返回。每条事件带时间戳、request ID 和来源，后续就能区分“最先使任务停止的原因”与“期间出现的其他信号”。示例展示设计方法，不是从生产追踪中提取的真实事件。

怎样让父子 Context 的原因可预测？

先规定取消策略：父级请求取消是否必须压过局部失败？局部限额触发是否只停止某个子任务？超时是否应该映射成可重试状态？这些是业务合同，不能单靠 API 自己决定。若多个子任务并行运行，可以让各子任务的 Context 表达各自停止原因，再在汇总结果中收集多个 error；不要期望单个父 Context Cause 记录所有子任务错误。Go 1.20 起的取消原因 API 与 errors.Join 等错误聚合应各自承担不同职责。

取消原因还会影响错误分类。把客户端断连标为普通内部故障，会导致告警噪声；把服务端 deadline 与用户取消合并，又可能掩盖超时上升。可以用稳定的原因类型或哨兵错误定义语义，日志中附带可变化的细节，但不要把原始请求参数、凭据或个人数据塞进 cause 文本。cause 会沿 Context 传递，生命周期可能超出调用栈，诊断文本应遵守隐私和保留策略。

如何验证 first-wins 而不测试偶然调度？

用确定顺序的单元测试分别取消父级和子级：先取消父级并确认派生 Context 的 Err/Cause；另一个测试先调用带 cause 的子级 cancel，再取消父级，验证子级原因不被替换。对并发竞争，不要断言调度器每次都选定某一原因；应只断言最终 Context 被取消、Cause 属于预期候选集合，并测试单独事件记录能保留两个观察结果。测试还应覆盖 WithCancelCause 的 cancel 函数传入 nil 的语义，以及 deadline/cancel 的错误分类。

最后检查业务调用者如何消费结果：如果只检查 Cause != nil 并按文本重试，就把原因文本变成不稳定协议；如果不记录 request ID 和子任务错误，cause 也无法重建完整事件链。推荐把 Context 用于传播停止信号，把返回值与观测事件用于结果汇总。本文依据 Go 官方源码核对 API 语义，没有运行并发测试或真实服务；具体版本需以项目采用的 Go 文档为准。

还需避免把 cancel cause 放进跨请求共享的可变错误对象。若多个 goroutine 都持有同一个 error wrapper 并在取消后修改其字段，日志读到的内容可能与取消瞬间不一致；Context 的 first-wins 只约束哪次取消写入了 Cause，不会冻结错误对象内部的可变状态。使用不可变的 sentinel 或构造独立错误值，再把变化信息作为带时间戳的事件记录。这样，错误分类稳定，日志仍能保留后续观察到的 deadline、断连或依赖失败，而不会暗示它们都曾成为终止原因。

还有一个容易遗漏的边界：取消通知是协作式的。cancel 会关闭 Done，但不会强制中断正在执行的函数；下游只有在检查 Context、使用支持 Context 的 I/O，或自行监听 Done 时才会停止。因此 Cause 表示停止信号在 Context 树中的归属，并不证明远端请求已经撤回、数据库事务已经回滚，或 goroutine 已经退出。服务需要分别记录取消请求、依赖响应和工作结束时间，才能判断取消是否及时传播。测试时可以让模拟依赖在收到 Done 后回报退出，再检查调用方是否等待清理完成；不要仅凭 Cause 已设置就认为资源释放已经结束。

延伸阅读：本站脱离请求取消并限制清理时间。这与本篇“谁先取消”的 Cause 选择不同：前者建立独立清理期限，后者描述取消原因在 Context 树中的胜出规则。
