pg_stat_io 有读写计数，为什么还不能直接说磁盘慢？

PostgreSQL 18 的 pg_stat_io 按 backend、I/O context 和目标对象拆分集群级统计，并有明确的未覆盖路径。先确定观察窗口、计数口径和排除项，才可能把指标用于排障。

正文

核心要点

  • pg_stat_io 的每行是 backend type、I/O context 与 target object 的组合，而不是整库的单一磁盘速度。
  • 绕过 shared buffers 的某些 relation I/O 不在该视图中。
  • 累积量需要固定窗口并比较同一维度；指标本身不证明瓶颈在磁盘。

pg_stat_io 有读写计数，并不等于它能直接回答“磁盘是不是慢”。PostgreSQL 18 把集群级 I/O 统计按 backend type、I/O context 和 target object 分行；你看到的数字首先是某类 PostgreSQL 工作负载在统计区间内累积了多少事件，而不是设备延迟、吞吐上限或某条查询的因果证明。排障前先把维度、时间窗口和视图的未覆盖路径写下来，才不会把计数误读成根因。

每一行代表一种工作角色组合

官方视图对每行的定义是 backend 类型、目标 I/O 对象与 I/O context 的组合。合理组合才会出现；pg_stat_io 主要覆盖 relation 与 temporary relation 对象，不应把 WAL 统计混进来。PostgreSQL 将 WAL 活动放在单独的 pg_stat_wal 视图，并提供独立的 track_wal_io_timing 配置。这个切分本身很重要：用户 backend 执行的 relation 读取，与后台进程或检查点相关工作，不应在没有说明的情况下合并成一个“数据库读盘数”。如果某时段 checkpointer 的写入升高，而应用连接的 shared-buffer 命中情况稳定，单一总和会让两个不同问题看起来像一个问题。

其次，pg_stat_io 不是块设备监控。文档明确说，绕过 shared buffers 的 relation I/O，例如把表移动到另一个 tablespace 时发生的 I/O，目前不被跟踪。视图没有记录的事件不能被解释为零，也不能推断“数据库没有发生 I/O”。同理，计数视图不能直接说明物理设备队列、云盘限速、操作系统页缓存命中或存储端延迟；这些需要与 PostgreSQL 统计之外的观测源结合。

先定观察窗口，再看计数差值

统计值通常是累积状态。假设某个 backend/context/object 行在采样开始时有 10,000 次读取，五分钟后变成 10,600。增量 600 只说明这个观测窗口内该组合计数增加了 600；要进一步得到每秒速率，需要除以实际经过时间，并确认两次采样之间没有统计重置、实例切换或维度变化。拿两个不同运行时长的快照直接比较绝对值，会把“运行得更久”误当成“更忙”。

对比窗口还必须匹配工作量。比如上午请求量是下午的三倍，即便下午每分钟 I/O 次数更低，也不能只凭绝对计数断定优化有效。可将统计增量按请求数、事务数或处理的行数归一化，但归一化分母要来自同一服务实例与同一时间边界。若一侧采集的是集群聚合、另一侧采集单节点，或者一侧包含重启前的累计量，计算结果会得到看似精确却不可比较的数字。

假设示例：写入增量上升，先不要归因于磁盘

假设一个版本上线后，某个写入相关组合的计数比上一窗口增加 40%。这是一个需要追问的信号，不是“存储慢了”的结论。可能原因包括同样请求发生更多页写、checkpoint 工作量变化、批量任务与在线服务重叠，或采样窗口的流量结构改变。先将 backend、context、target object 原样保留，再与事务数、请求率、检查点观测、等待事件和主机/云盘指标对齐，才能判断变化发生在哪一层。

反例是先把所有 reads、writes 相加，再把总数当作磁盘 IOPS。这样既混合了不同 backend，也忽略了调用是否经过 shared buffers、实际 I/O 延迟与设备合并行为。若后续发现云盘延迟升高，仍要排查是否只是更大的工作集或更高的请求量导致；若 PostgreSQL 视图计数不变而主机 I/O 上升，还要检查未被该视图覆盖的路径、日志、临时文件或其他进程。这里是分析方法示例，并非来自生产数据库的测量。

用一张采样表保留因果线索

可以在每次采样记录时间戳、实例标识、PostgreSQL 主版本、backend type、context、目标对象、各计数的前后值和采样间隔。另存同一窗口的请求量、事务量、等待类别、checkpoint 相关指标以及主机 I/O 观测。出现计数回退时不要把负差值解释成负 I/O；应检查实例重启、统计重置、导出器标签映射和采样对象是否已更换。聚合之前保留原始分组，可让后续重新计算和审计仍有可能。

验证流程应先在非生产环境对照已知操作：执行受控的普通表读取、写入或 checkpoint 工作，确认预期行的增量方向；再用独立主机观测核对设备活动。要有意验证视图盲区，设计会绕过 shared buffers 的操作时，不应要求 pg_stat_io 必须出现对应关系 I/O。测试的价值在于确认采集管道、标签和解释方式一致，而不是证明线上每个 I/O 都能由单个视图解释。

什么证据才足以支持“磁盘是瓶颈”？

至少需要互相吻合的几类证据：同一时间段的 PostgreSQL 统计增量、查询或后台工作的等待现象、主机或存储侧延迟/队列、工作量分母，以及排除重启和重置的连续采样。若计数升高但延迟没有变化，可能是吞吐增加而非退化；若应用变慢但 I/O 计数稳定，瓶颈可能在锁、CPU、网络、连接池或视图未覆盖的活动。不能从一个累计计数推导用户看到的 p95 延迟，也不能把一个统计列命名成某个设备指标。

本文根据 PostgreSQL 18 文档解释视图的维度与范围，没有连接数据库、查询 pg_stat_io 或测量磁盘。实际系统应核对运行版本、视图字段、采集间隔与实例拓扑，再用受控工作负载验证指标映射。它适合回答“哪类 PostgreSQL 工作在累积 I/O 统计”，不单独回答“哪块盘慢了”或“这次发布造成了多少性能回退”。

采集系统还要记录统计视图重置边界。部署更新、手工重置或实例切换会让相邻快照不再属于同一累计序列；若直接相减，负值或异常跳变可能来自计数器生命周期，而不是 PostgreSQL 执行了反向 I/O。建议把数据库系统标识、启动时间和 reset 事件一并写入采样维度，并让导出器在标签改变时开始新序列。对于集群滚动升级，先按节点分别核对，再汇总同一时间窗的速率。这样能避免把一个节点重启前的历史计数与另一个节点的当前状态混在一起，也给复盘留出重新计算原始差值的材料。

延伸阅读：本站节点 CPU 不忙但容器仍变慢。pg_stat_io 记录数据库 I/O 事件，不能替代节点、容器和存储路径的延迟指标。
