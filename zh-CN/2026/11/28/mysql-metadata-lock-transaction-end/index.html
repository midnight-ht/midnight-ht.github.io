MySQL DDL 卡住时，前一条失败语句为什么还会挡路？

MySQL 8.4 中，语法有效但执行失败的语句可能仍把 metadata lock 持有到事务结束；autocommit 下则随语句结束释放。查 DDL 等待时要追踪事务和持锁连接，不只看最后一条 SQL。

正文

核心要点

  • 表元数据锁保护对象定义并可能阻塞不兼容的 DDL。
  • 语法有效但执行失败的语句不一定提前释放已取得的 metadata lock。
  • 显式事务结束才是重要边界；autocommit 下每条语句构成事务。

MySQL 8.4 中，某条语句报错不代表它此前取得的 metadata lock 已经消失。官方手册说明：语法有效、执行阶段失败的语句如果取得了元数据锁，锁不会提前释放，而是延迟到事务结束；autocommit 下每条语句本身是一个完整事务，锁通常随语句结束释放。因此 DDL 等待时，只看正在运行的 SQL 或应用日志最后一行，可能找不到真正阻塞者；要把等待的 DDL、持锁会话和事务边界连起来看。

metadata lock 在保护什么？

Metadata lock（MDL）用于协调表、视图等对象定义上的并发访问。查询或修改表时，服务器需要保证执行期间对象定义不会以不兼容方式被更改；DDL 则需要取得能够改变定义的锁。若一个事务仍持有与 DDL 冲突的锁，ALTER TABLE、DROP 或类似操作就可能等待。等待并不必然表示 DDL 执行慢，也不一定表示存储引擎正在处理大表；冲突可能来自另一个连接早先访问表后一直没有结束的事务。

InnoDB 行锁和 MDL 也不是同一个锁。行锁服务于记录级并发控制，MDL 管理对象定义的协调。排查时仅查询某种行锁视图，可能看不到导致 DDL 阻塞的元数据锁等待。应用的一条 SELECT 即使很快返回，若它位于一个显式事务内，连接仍可能保留该事务取得的 MDL，直到事务提交或回滚。

为什么执行失败仍可能留下等待链？

MySQL 8.4 手册特别描述了一个容易误判的边界：语法有效但执行期间失败的语句不会因失败就立即释放已取得的 metadata lock。文档解释这是为了保护 binary log 一致性，因为失败语句仍会写入 binary log；锁释放仍推迟到事务结束。语法解析阶段就拒绝的语句与已经进入执行阶段的语句并非同一条路径，因此不要把“错误返回”当作“事务已结束”的证据。

设想会话 A 先开启显式事务，执行一条访问 orders 的有效语句，执行过程因为约束或数据错误而报错。应用捕获异常后只记录错误，却没有回滚，也继续将连接留在连接池中。会话 B 随后执行需要改变 orders 元数据的 DDL，就可能排在 A 的锁后面。A 的业务日志看起来早已结束，数据库中的事务却仍是打开状态。这里是基于官方机制构造的假设时间线，不是一次真实故障记录。

排查时同时确认等待者和持有者

第一步是确定哪个 DDL 在等待，以及它等待的对象和时间；第二步是识别持有冲突锁的会话；第三步是检查该连接是否处于未提交事务、事务开始时间、最后活动时间及应用实例。MySQL 的 Performance Schema 提供 metadata lock 相关观测接口，具体表和权限要按当前 8.4 小版本与启用情况核对。连接 ID 需要映射回连接池、服务实例和请求日志，否则你知道“一个事务在持锁”，却不知道谁负责结束它。

不要用“杀掉所有慢查询”作为默认处理。终止持锁连接会回滚其事务，可能影响仍在执行的业务；取消等待 DDL 则会让发布操作没有完成。决策应取决于变更窗口、事务是否可安全重试、回滚成本与服务影响。对可控的迁移任务，可以设置等待上限并在超时后停止变更、告警并重试；对长期业务事务，先修复事务清理和连接池归还逻辑，而不是反复重启 DDL。

一个小型验证怎样暴露这个边界？

在隔离实例上准备一张测试表，然后由会话 A 开启事务并访问该表，让会话 B 尝试需要冲突元数据锁的 DDL。分别测试两种结束方式：A 在访问后提交；A 执行有效但失败的语句后仍保持事务打开。观察 DDL 的等待是否持续到 A 提交或回滚。再重复相同语句但使用 autocommit，确认 statement 结束后锁释放范围不同。测试前后用 Performance Schema 的锁等待记录和连接状态定位，而不是只依赖客户端耗时。

实验应使用独立对象，设定清理时限，并在失败路径中主动回滚。不要在生产表上制造长事务来“确认”文档行为，也不要把测试环境某个小版本的输出直接推广到所有部署。应用侧还需确认 ORM 或驱动在语句异常后是否自动回滚；如果只有数据库错误处理而没有事务清理，连接池复用就会把一个局部错误扩展成后续 DDL 排队。

哪些设计选择能减少重复故障？

在线请求应尽量缩短显式事务，不要在事务内等待外部 API、用户输入或队列消息；错误路径需要明确提交还是回滚，并在归还池连接前检查事务状态。迁移工具应先检测长事务和元数据锁等待，设置明确的等待策略，在发布窗口外停止而不是无限等待。应用监控可以把事务年龄、连接 ID、请求 ID 与 DDL 发布记录关联，但日志不能替代数据库锁证据。

本文描述的是 MySQL 8.4 手册所述语义。不同语句类型、事务模式、存储引擎与小版本可能带来不同等待行为，部署前需要针对实际连接池与迁移工具验证。核心判断是：SQL 语句的错误状态和事务生命周期是两个不同状态。只有事务结束，才可以根据这里讨论的规则确认对应 MDL 生命周期到达了结束边界；日志里最后一次错误不足以证明这一点。

处理等待时还要区分语句错误与事务错误。某些数据库错误会让应用主动回滚，但不能只根据异常类型假定驱动已经替你结束事务；连接池可能在回滚完成前继续占有会话。运维流程最好记录事务开始时间、当前状态、锁等待对象以及所属应用实例，并先确认是否存在未结束的请求。对连接执行 KILL 前，判断它是正在处理重要写入、已经空闲却忘记提交，还是因异常进入异常状态。不同情形的回滚代价与恢复方法不同；一条统一的“清长连接”脚本会把元数据锁问题转成业务中断问题。
