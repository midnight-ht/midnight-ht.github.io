npm trusted publishing 换成 OIDC，为什么还不能说发布链路安全？

npm trusted publishing 把受信任的 CI 身份与短时 OIDC 发布凭据关联，减少长期 token；它不证明 workflow、依赖或发布产物没有恶意内容。

正文

核心要点

  • npm 配置的可信发布者绑定 CI 提供方、仓库、workflow 文件名，可选绑定 environment。
  • GitHub Actions 需要 id-token: write 以获取 OIDC 身份令牌。
  • 身份交换减少长期 token，但代码审查、工作流权限和产物核验仍是独立安全门。

npm trusted publishing 可以让受支持的 CI 身份通过 OIDC 换取短时发布凭据，减少仓库里长期保存 npm token 的需求；它并不证明发布 workflow、依赖树或最终包是安全的。npm 侧的可信发布者配置将身份与提供方、仓库和 workflow 文件名绑定，GitHub Actions 还需 id-token: write 权限。若 workflow 本身可被不受信任的改动控制，OIDC 只会更方便地把真实发布权交给错误代码。

OIDC 证明的是谁在请求，不是代码值得信任

传统发布方式常把长期 token 放进 CI secret。可信发布机制改为让受支持的 CI 提供身份令牌，npm 验证其声明是否与包配置的可信发布者匹配，再交换为短时发布凭据。npm 文档目前列出 GitHub-hosted Actions、GitLab.com shared runners 和 CircleCI cloud 等支持提供方；自托管 runner 当前不在支持清单内。GitHub Actions 配置要包含 id-token: write，但不应因此给整个工作流额外扩大 contents、packages 或其他写权限。

这个流程把“哪些 workflow 身份可以发布”变成一项明确配置，却不会审阅 workflow 中的 shell 命令。若发布 job 下载未固定版本的第三方 action、执行来自 pull request 的脚本、从可写分支加载发布配置，或者把构建和发布权限放在同一无保护 job 中，OIDC 身份仍可能被滥用。身份断言可证明本次请求与某个仓库/工作流声明匹配，不证明工作流输入、依赖、源代码和包文件经过可信审核。

假设发布链：可信身份也可能运行不可信步骤

假设一个 GitHub Actions workflow 在 main 的 release tag 上发布，但 tag 仍允许普通写权限用户创建。可信发布者绑定了仓库与 publish.yml，因此符合条件的 workflow 可以请求 OIDC token。若发布步骤先拉取一个未经固定 SHA 的 action，或在安装依赖时执行了被替换的脚本，发布身份验证成功并不会自动拦截这些供应链风险。攻击者利用的是“合法身份运行了错误内容”，并不需要伪造身份声明。

改进应从多个边界入手：保护 release tag 和 environment，限制谁能修改发布 workflow，对 action 固定完整 commit SHA，使用受控 lockfile 和构建输入，将测试/打包产物与发布步骤绑定，并审计 npm 包版本、来源提交和 provenance 关联。还要明确环境审批是否真的应用于该 job；npm 文档把 environment 名称作为可选可信发布者字段，但只有配置与 CI 实际环境一致时它才发挥约束作用。此示例是威胁模型推演，没有执行发布或安全审计。

迁移时要逐字段核对身份匹配

npm trusted publisher 配置包含 CI 提供方、GitHub 用户或组织、仓库名、workflow 文件名，可选 environment，以及允许直接 npm publish、npm stage publish 或管理 dist-tag 的权限。workflow 文件名只填文件名并需位于 .github/workflows/；名称或组织迁移后，身份匹配也要同步调整。对于 workflow_call 复用发布工作流或父子 workflow，npm 文档提醒调用方名字和 OIDC 权限配置会影响校验；不能只在最终包含 npm publish 的文件中添加权限就假定通过。

迁移测试不要一开始删除旧 token。先在隔离包或预发布包验证真实 CI 事件、声明 audience、workflow 与 environment 名称，以及发布权限；观察 npm 是否成功识别身份并完成短时交换。随后检查发布失败时的恢复路径，确认没有把长期 token 留在日志、缓存或备份中。迁移完成后再按最小范围撤销旧 token，并审查组织中是否还有其他工作流使用它。

Provenance、来源证明与安全结论要分开

构建 provenance 可以把包与某个仓库、构建环境或工作流关联起来，帮助消费者追踪来源；它不等于独立代码审计，也不证明依赖没有漏洞或构建过程没有被攻陷。trusted publishing 说明的是发布凭据如何获得和授权；provenance 说明产物来源声明；签名/校验说明数据完整性；人工审查与测试说明流程检查。把这些机制混称“供应链安全”会隐藏各自的保证边界。

发布包验收应核对包名、版本、tarball 内容、来源提交、CI run、身份声明和权限；不要只看命令退出码为 0。对于含有构建步骤的包，还要确认发布的是已验证的不可变 artifact，而不是发布阶段重新下载依赖后生成的一份新内容。本文没有执行 npm publish 或验证 provenance 产物；上述核对清单是建议，不是实测证明。

什么时候值得切换？

如果目前依赖长期 npm token，且项目使用 npm 支持的 CI 提供方，trusted publishing 能减少静态凭据保管与轮换负担。但它需要稳定且受保护的 workflow 身份、正确权限和可审计 release 事件。若当前自托管 runner 不受支持，不能硬称 OIDC 方式已经可用；应先评估受支持的执行环境，或保留最小权限、严格范围的备用凭据管理方案。

本文依据 npm trusted publishers 官方文档核对支持提供方与 GitHub 权限要求。上线前应在目标包和目标 workflow 验证配置，不要把身份匹配成功解释成包无恶意、依赖安全、发布可复现或人工批准。短时凭据减少暴露面，但发布代码本身仍需可信构建、审核和来源核验。

发布权限是另一个常被忽略的粒度。npm 文档允许为可信发布者指定哪些操作可用，直接 publish、stage publish 与 dist-tag 管理不是同一权限。审查时应只启用任务需要的动作，确认测试 job 不继承发布 identity，并避免发布 workflow 在任意分支或未审批 tag 上执行。验证阶段可用无权限分支试运行，确认它拿不到 OIDC token；但不要把“请求失败”本身当作全部策略正确的证据，还需检查仓库环境规则和 GitHub token permissions。

延伸阅读：本站npm ci 的安装输入边界。可信发布改变发布身份凭据，不会让变化的 lockfile、生命周期脚本或构建输入自动变可信。

一个有用的发布不变量是：发布前审核的字节，应与消费者拿到的字节一致。在受保护的 job 中构建一次，保存不可变 artifact 并计算摘要；发布步骤应消费这个 artifact，而不是拿到凭证后重新安装依赖或重新构建。随后将包 tarball 与 provenance 对到源提交和运行身份。OIDC 缩小谁可以请求 npm 发布的范围；artifact 身份与可复现构建检查回答实际发布了什么。若身份合法但包内容异常，两类证据缺一不可。
