Compose Watch 同步了依赖文件，容器为什么还是跑旧依赖？

Compose Watch 的 sync、rebuild 和 sync+restart 对应不同变更。同步文件不会自动重建镜像或安装新依赖；选错动作会让开发循环一直验证旧进程。

正文

核心要点

  • Compose Watch 要求 Docker Compose 2.22.0 或更新版本。
  • sync 只同步文件；依赖或编译产物变化通常需要 rebuild 或同步后重启。
  • 路径规则、忽略项和容器用户写权限会决定观察到的结果。

Docker Compose Watch 同步了 package.json，不代表容器里已经安装新依赖。Watch 的动作决定变更如何进入运行中的服务：sync 复制文件，rebuild 重建服务镜像，sync+restart 先同步再重启。只同步依赖清单可能让容器看到新文件、继续运行旧的 node_modules 和旧进程。Compose Watch 文档要求 Compose 2.22.0 或更高版本；配置规则之前，先判断变更影响的是源文件、镜像构建输入还是进程配置。

三种动作解决的是不同开发反馈环

sync 适合应用能直接热加载的源码或静态资源。它不重新运行 Dockerfile，也不会自动执行依赖安装命令；如果新增包需要写入镜像层，仅把清单文件复制进容器不会更新已安装依赖。rebuild 则重新构建服务镜像，适用于依赖清单、编译工具链或镜像内文件改变的场景。sync+restart 适用于文件要同步到容器，同时进程需要重新启动读取配置或加载内容的情况。

这三种动作也不意味着所有文件都应该被观察。Docker 文档定义路径相对于 Compose 项目目录，支持的 watch 规则受 .dockerignore 影响；目录变更会递归处理。容器内服务用户需要对目标路径有写权限，否则同步动作可能失败或表现得不完整。只配置 host 侧路径却忘记镜像内工作目录、忽略规则和 USER 权限，很容易得到“保存了但容器没变化”的假象。

假设例子：源码热更新与依赖更新不能用同一条规则

假设 Node 服务把 src/ 挂载为热更新目录，把 package.json 与 lockfile 用另一条规则同步+重启。修改 src/handler.js 时，sync 可让开发服务器重新加载代码；修改依赖版本时，仅同步两份清单并重启，仍可能启动已有镜像里的旧 node_modules。若这条变更需要 npm ci，正确动作应触发 rebuild，或由明确、可审计的开发启动流程安装依赖。开发者要观察实际镜像/安装状态，而不只是看容器里清单文件的内容。

另一个反例是对所有 src/ 改动都 rebuild。反馈循环会变慢，而且把源码变化误当镜像结构变化；若编译产物不会在容器内自动生成，重建镜像也未必解决文件映射问题。应根据每种文件的消费者来配置：运行中的解释器、构建阶段、启动配置读取器或静态服务器。示例展示配置决策，没有执行 Compose 项目或测量构建耗时。

一个简化的规则组合

可以将可热重载的源码目录配置为 sync；将依赖清单、Dockerfile 和编译工具版本配置为 rebuild；把需要重新读入的配置文件配置为 sync+restart。实际 YAML 的 pattern、target 和 action 要按当前 Compose 版本验证，不能照搬示意规则。若 image: 使用预构建镜像、没有本地 build context，watch 不会因为本机文件变化就凭空重建上游镜像；服务需要与本地源码构建配置建立明确关系。

配置排除路径时要避免把秘密、缓存、生成物或大目录同步进容器；同时确保忽略规则不会把必须观察的源码屏蔽。服务以非 root 用户运行时，目标目录可写性是开发环境契约的一部分，不要为修复同步失败就把整容器切回 root。Compose 文档的 prune 行为与 dangling 镜像清理也需要按当前配置查看，避免开发机清理动作造成对构建缓存的错误预期。

怎样验收开发循环没有悄悄跑旧内容？

在实际 Compose 版本下分别修改一段源码、依赖版本、镜像构建文件和运行配置。每类变更都观察：Watch 是否匹配文件、动作是否启动、容器目标路径是否变化、依赖或镜像 ID 是否更新、服务进程是否重新加载，以及测试请求实际返回了新行为。日志里应明确记录 rebuild 或 restart 的发生，而不能只看到文件监控提示就判断成功。

还要检查失败和边界：文件被 .dockerignore 排除、目标目录只读、多个规则同时匹配、服务没有 build context、watch 路径大小写/相对根错误，以及重启期间健康检查失败。改变依赖后可检查容器内 lockfile 与已安装包版本；改变编译器后检查镜像摘要和二进制版本。未做这些核对时，最容易出现本地源码新、容器二进制旧的分裂状态。

什么时候选 sync，什么时候选 rebuild？

如果运行进程能直接消费同步后的文件，且不涉及镜像层或依赖安装，sync 通常最轻；若变更影响镜像构建或安装状态，rebuild 才覆盖该边界；若只需让当前进程重新读取同步文件，sync+restart 更贴切。目标是把每个动作与变更语义配对，而不是让所有保存操作都触发最重的构建。

本文根据 Docker 当前 Compose Watch 文档，包含 2.22.0 的最低版本要求。没有在本项目启动 Compose、验证具体 YAML 或运行 benchmark。应用团队应在真实 Compose 版本和容器用户下测试路径、权限、忽略规则、依赖状态和健康恢复；“文件被复制”不等于“应用已使用它”。

多规则匹配要通过配置测试固定下来。对某一文件同时命中 rebuild 和 sync，实际效果可能产生重复构建或顺序竞争；不要依赖 YAML 顺序来决定动作。可以把关键路径做小型改动测试，并将容器镜像摘要、进程启动时间与源码提交写入本地诊断输出。多人共享 Compose 文件时，还应确认 watch 规则不要求开发者本地文件权限以外的特权，也不会把宿主机凭据同步进容器。

延伸阅读：本站Docker COPY、chown 与运行用户。Watch sync 更新容器路径，但不会自动改变属主、安装依赖或修复服务进程的读取权限。

应在变更所在的层检查结果。依赖更新时，对比 build context 中的 lockfile、运行容器已安装的包版本、镜像摘要和进程启动时间。如果 lockfile 已变化但镜像摘要与依赖版本未变，watch 规则就没有刷新依赖层。源码同步时镜像摘要可能保持不变，应改查服务返回的新行为或热加载事件。单一“容器正在运行”的健康检查不能同时验收这两条路径。
