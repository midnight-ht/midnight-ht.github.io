sendBeacon 返回 true，为什么仍不能证明服务端保存了数据？

navigator.sendBeacon 的 true 表示 user agent 已将数据成功排入传输队列，数据总量上限为 65,536 字节；它不返回服务器收据，也不证明已持久化。

正文

核心要点

  • sendBeacon 返回 true 的承诺止于浏览器排队，不含服务器接收或写入确认。
  • 排队数据总量限制为 65,536 bytes，超限时 API 可返回 false。
  • 必须获得持久化确认的事件需要有响应、重试和去重合同的传输路径。

navigator.sendBeacon() 返回 true，只说明浏览器 user agent 成功把数据排入传输队列。它不表示服务器已收到请求、应用已解析数据或数据库已提交。MDN 还指出，排队数据总量限制为 65,536 字节；队列无法接受时方法会返回 false。因此 beacon 适合页面结束时尽力发送小型遥测，不适合被当成“关键业务操作已保存”的确认协议。

返回值对应的是哪个阶段？

sendBeacon(url, data) 会异步发送 POST 请求，不阻塞页面继续导航；其布尔返回值说明 user agent 是否接受这份数据进入传输队列。队列成功后，网络仍可能断开，设备可能离线，浏览器进程可能终止，服务端也可能返回错误或在处理时崩溃。API 不提供响应对象给页面读取，因此调用方拿不到 HTTP 状态码、响应 body 或业务持久化收据。

把 API 返回值命名成 sent=true 会误导后续监控。更准确的状态是 queued；服务端观察到请求时才可以记录 received，完成持久化时记录 stored。这些状态来自不同参与方，页面无法单靠一个 Boolean 将它们合并成“成功”。

假设例子：页面关闭时发出一次关键埋点

假设用户刚提交了付费订单，页面准备关闭并调用 sendBeacon 发送 purchase-confirmed 埋点。函数返回 true 后，前端界面可以记录“已排队”，但不能把订单 UI 改为“支付记录已写入分析库”或据此停止对订单服务查询。若分析系统没有收到请求，页面可能已经销毁，无法重发；若浏览器在响应未知时再次尝试，可能产生重复事件。业务订单应由支付/订单接口的服务器端状态作为事实来源，beacon 只补充尽力而为的观测。

数据体积也需要按 UTF-8 字节而不是字符数估算。一个汉字通常不止一个字节，序列化成 JSON 后还会增加键名、转义与结构开销。多个并发 beacon 的总排队量共享 65,536 字节限制，不能只检查每个 payload 单独小于上限。达到上限时应丢弃低价值字段、合并事件或选择另一种传输方式，而不是在页面卸载事件中无限拆分请求。

失败路径和重复路径都要设计

网络失败可能使服务端完全没有看到事件；服务端已处理但客户端不知道结果时，重试又可能重复写入。Beacon 本身不提供幂等或 exactly-once。若遥测可以容忍少量丢失，系统可接受 best-effort 并通过总体采样和缺口监控判断；若单条事件需要审计或结算，就需要服务端确认、可靠队列或业务状态重查。即使换成 fetch keepalive，也要确认具体 API 行为和 payload 限制，不能想当然地把它当作无限可靠通道。

可在 payload 内加入事件 ID，服务端按 ID 去重，并将原始接收和入库状态分开记录。但客户端无法知道去重发生了，所以这只能保障服务端对重复投递的处理，不能为用户界面提供实时保存确认。页面应在有响应的请求路径中等待业务回执；离页前 beacon 只作为辅助补发。

如何验证排队、接收与持久化三种状态？

在测试页面记录 sendBeacon 的布尔值与 payload 字节大小，同时在服务端记录到达的请求 ID、解析结果和提交状态。通过断网、后台挂起、进程关闭、超过队列上限、服务端返回错误与入库失败等路径，比较这三类证据是否分离。测试时不要只依赖浏览器网络面板，因为页面关闭后面板状态也可能不完整；可用服务端日志和可查询的事件 ID 对照。

true 且无服务端记录表示排队不等于到达；服务端记录存在但未提交表示接收不等于持久化；提交存在却缺少客户端确认则表示结果对页面未知。反之，返回 false 时也要检查数据是不是被策略主动缩减，而不是无限重试。本文没有运行浏览器或服务器实验；测试路径是建议，不是已观察结果。

什么时候选 beacon，什么时候用确认协议？

页面卸载附近的小型性能遥测、诊断信号或可丢失分析数据，适合使用 sendBeacon 的非阻塞队列语义。订单、支付、权限变更、法律同意或需逐条审计的数据，需要有响应、身份验证、持久化确认与重试/去重设计的 API 或可靠消息通道。选择依据是数据丢失与重复的业务成本，而不是调用是否方便。

本文依据 MDN API 文档说明返回值和数据上限，不声称任何事件已投递或保存。应用指标应明确区分 queued、received、stored 和 dropped；通过这种状态拆分，运维人员才能判断问题发生在浏览器队列、网络、服务端处理还是持久化阶段。

隐私和容量也要算进离页遥测。页面关闭时一次发送多个对象，JSON 可能包含完整 URL、用户输入或标识符；把它们序列化进 beacon 会增加传输体积并延长敏感数据保留。先用字段白名单与采样控制内容，再按 UTF-8 byte size 限制打包。对于不应发送的数据，应在生成 payload 前删除，而不是只依赖服务端丢弃。分批压缩或重试策略仍要核对 64 KiB 队列总额以及浏览器结束页面时的生命周期。

延伸阅读：本站尾部采样无法恢复已丢失链路的边界。离页事件应有独立 ID，并区分客户端排队、服务端接收和持久化阶段；采样缺口则是另一种观测原因。

事件 ID 应贯穿可能发生重试的生命周期。页面退出前生成 ID；如果之后由另一条授权路径调和同一事件，应复用该 ID，否则即使服务器能对相同 payload 去重，客户端重试仍可能创建第二个逻辑事件。服务器应为去重键设置覆盖预期迟到窗口的保留期，并记录该键是新值、重复值还是格式错误。这能改善重复处理，但仍不会把已排队的 beacon 变成页面可见的持久化回执。
