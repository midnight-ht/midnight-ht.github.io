Go 1.25 的 WaitGroup.Go 省了 Done，为什么仍要求函数不能 panic？

Go 1.25 的 WaitGroup.Go 把启动 goroutine 与任务计数关联起来，函数返回时自动完成计数；它没有提供错误收集或 panic 恢复。

正文

核心要点

  • WaitGroup.Go 在新 goroutine 中调用 f，并在 f 返回时移除任务计数。
  • 文档要求 f 不得 panic；Go 1.25 的新方法不是 panic containment。
  • 空 WaitGroup 上启动任务必须先于 Wait；错误和 panic 策略仍需由调用方设计。

Go 1.25 的 sync.WaitGroup.Go(f) 将启动一个 goroutine 与 WaitGroup 任务计数关联起来：f 返回时，该任务从组中移除。它省掉了手写 Add(1) 和 defer Done()，却没有提供错误收集、panic 恢复或任务隔离。官方文档明确要求传入的函数不得 panic。若工作函数可能 panic，应先定义它由谁恢复、怎样报告失败，再决定是否直接使用 Go。

它解决的是计数生命周期，不是完整任务监督

旧写法需要调用方在启动 goroutine 前增加计数，并在所有返回路径上执行 Done()。若忘了 defer 或提前 return，Wait() 可能永久阻塞；若 Done() 多次执行，计数可能变成负数并 panic。WaitGroup.Go 把“任务开始”和“任务函数返回时任务结束”放到同一方法里，减少了这类配对错误。Go 标准库文档建议优先考虑此方法，且标记为 Go 1.25 新增。

但 WaitGroup 只回答“跟踪的任务是否结束”。它不保存任务返回值，因为 f 没有返回类型；也不定义多个错误如何聚合。它不取消其他 goroutine，不限制并发数，不恢复 panic，也不保证任务副作用成功。把 Wait() 返回解释成“所有子任务成功完成”，是把计数屏障误当成任务结果协议。

为什么 panic 约束重要？

文档规定 f 必须不 panic。goroutine panic 若未在该 goroutine 内恢复，通常会使整个进程进入 panic 终止路径；WaitGroup 的计数生命周期不能把它转换成可观察的 error。使用 WaitGroup.Go 不能默认获得“一个 worker panic，其他 worker 继续，最后返回 error slice”这类隔离语义。若团队期望局部失败，不捕获 panic 就不是完整的失败策略。

假设一个批处理用 wg.Go(func(){ process(record) }) 并在后面调用 wg.Wait()。某条记录的解析代码因 nil 指针 panic。开发者可能以为 WaitGroup 会自动 decrement 后向调用方返回失败；实际上方法文档只谈 f 返回时任务计数移除，并且明确排除了 panic。若 panic 未恢复，它可能导致进程崩溃，调用方没有机会读取一个结构化错误。示例为风险说明，没有执行真实批处理。

如何显式定义 panic 和错误边界？

若函数可正常返回业务错误，可让每个任务把 error 写入有同步保护的结果槽，或把结果发送到有容量约束的 channel；等待结束后再按业务规则聚合错误。若确实要把 panic 转成局部失败，必须在同一个 goroutine 的函数边界中 recover，将 stack、任务 ID 与恢复后的错误传给调用方。recover 只能在 deferred 函数中生效，且不应吞掉运行时不变量破坏或把进程状态假装安全。

若使用 worker pool，还需单独处理并发上限、取消与队列背压；WaitGroup 不会限制 goroutine 数量。可以将启动函数放在 semaphore 获取之后，在取消时停止提交并等待已启动任务。发生一个任务失败后是否停止其他任务，取决于业务语义；这与 WaitGroup 的计数无关。需要取消与错误聚合时，比较 errgroup 等更高层抽象，但要阅读其自身的错误和取消合同，不要假定它吞掉 panic。

Go 的启动与 Wait 顺序仍有规则

当 WaitGroup 计数为零时，Go 必须在 Wait 之前调用。若组仍非空，文档允许任务在其他 goroutine 中继续调用 Go；复用同一 WaitGroup 等待多个独立任务集合时，上一轮 Wait 必须先返回后再开始新一轮。误在一个空组的 Wait() 已经开始后才启动任务，可能使调用者认为等待覆盖了任务，但同步关系并不成立。

对照 Add/Done，Go 的方法把启动与计数绑定，但没有消除共享 WaitGroup 的生命周期约束。WaitGroup 不能在首次使用后复制；新任务的启动位置仍要对并发控制可见。测试应覆盖零任务、启动后等待、嵌套任务启动、任务集复用、错误返回和 panic 边界，而不是只验证 Wait 最终返回。

什么时候用 Go，什么时候仍写 Add/Done？

当工作函数不 panic、只需等待一组已启动任务结束，且并发数量由上层控制时，WaitGroup.Go 能减少样板并降低计数配对错误。若需要在启动时登记外部创建的 goroutine、把任务计数与执行函数分离，Add/Done 仍可能更合适。需要返回错误、取消同伴或限制并发时，应使用具备明确合同的任务协调器，而不是期待 WaitGroup 承担它没提供的职责。

本文依据 Go 1.25 release notes 与标准库文档核对方法引入版本、panic 要求和生命周期规则；没有运行并发实验。项目需要确认最低 Go 版本、调用点的错误与 panic policy、以及 WaitGroup 是否跨阶段复用。方法更短不代表任务边界自动变安全。

方法也不提供超时等待。Wait() 会阻塞到计数为零，没有 context 参数，也不会在截止时间到达时取消任务。若任务可能卡在网络调用，调用方需要让工作本身接收 Context、配置客户端超时，并单独管理取消与清理；给 WaitGroup 包一层 goroutine 再 select，只能让调用者停止等待，不能让底层工作自动停止。评估任务生命周期时，应把 goroutine 结束证据、外部副作用状态和 WaitGroup 计数分开记录。

检查结果也不应该只剩一个聚合 error。若多个任务写回同一个切片，必须先建立明确的同步关系；一种简单做法是按输入索引预先分配结果槽，每个 goroutine 只写自己的槽，随后主 goroutine 在 Wait 返回后顺序读取。若任务数巨大，则逐个保存完整错误可能耗尽内存，此时应定义首错、错误上限或带背压的结果 channel，并明确其关闭者。WaitGroup 不替应用决定这些数据所有权和容量策略。假设输入包含重复记录，按输入位置保存结果还能保留重复项的身份；用记录 ID 作 map key 则可能覆盖其中一个结果。这个选择属于结果合同，不是计数器行为。

延伸阅读：本站Go Rows.Next 结束与 Rows.Err。并发任务汇总也应保留每个工作单元的错误，而不能把计数归零写成业务数据已完整读取。
