Passkey 登录没有弹出候选，conditional mediation 应怎样降级？

WebAuthn Level 3 的 conditional mediation 是一种可选登录体验能力。先检查客户端是否支持，再保留可见的替代流程；候选界面出现不等于服务器已验证身份。

正文

核心要点

  • Level 3 建议在将 mediation 设为 conditional 前检查客户端能力。
  • isConditionalMediationAvailable 检查的是 get() 认证流程，不等价于 conditional create 支持。
  • 客户端候选选择后仍必须由 RP 验证 challenge、origin、RP ID 与 assertion。

WebAuthn 的 conditional mediation 是一种可选的凭据选择体验，不能假设每个浏览器、设备或嵌入环境都支持。WebAuthn Level 3 建议 relying party 在 navigator.credentials.get() 将 mediation 设为 conditional 前，先调用 PublicKeyCredential.isConditionalMediationAvailable() 检查能力；不可用时要让用户仍能走普通登录路径。即使浏览器展示了 passkey 候选，身份也尚未完成认证：服务器仍需要核对 challenge、origin、RP ID 和签名断言。

conditional mediation 改变的是用户介入时机

传统 get() 流程通常由页面在用户点击按钮后发起凭据请求，页面进入等待，认证器再展示选择或验证 UI。conditional mediation 则允许网页在凭据选择界面尚未由用户明确触发时启动等待式请求，浏览器可把可用凭据候选整合进输入体验。用户最后选择凭据后，请求继续完成；如果没有凭据或用户不选，页面需要处理请求仍在等待或被取消的情况。

这不是绕开用户同意，也不是服务器自动知道用户账户。页面仍要从服务器取得短时 challenge，按 RP ID 和当前 origin 配置请求选项，再将结果送回服务器验证。Level 3 的 isConditionalMediationAvailable() 返回 Promise，结果是布尔值；若方法不存在，规范说明 conditional mediation 不可用。文档还区分 conditional get 与 conditional create：这个方法检查的是 navigator.credentials.get() 的认证能力，不说明 create() 注册 ceremony 是否支持条件式创建。

假设登录页：能力检查失败时仍然保持可用

假设登录页有邮箱输入框和 passkey 入口。页面加载后先从后端获取 request options，然后检查条件式 mediation 能力；能力存在时才启动带 conditional mediation 的 get()，并允许浏览器把凭据建议与邮箱输入结合。若能力缺失、Promise 拒绝、请求被浏览器策略阻止，邮箱+密码、显式 passkey 按钮或其他已批准的登录方式仍应可见。若代码把唯一登录入口藏在候选弹层里，能力检查失败就会让整个账户不可达。

另一条失败路径是页面在候选开始显示时就把用户标记为“已登录”。候选选择只说明浏览器找到并返回了某个凭据响应；恶意客户端可以伪造请求体，过期 challenge 也可能被重放。浏览器端的用户体验状态不能成为授权依据。服务器必须验证 challenge 是本次签发且未使用、origin 和 RP ID 符合预期、credential ID 属于可接受账户，并验证 authenticator data 与签名。示例说明协议职责，不是某个认证库的完整实现，也没有实际演练。

如何处理请求等待、取消与页面导航？

条件请求可能与页面生命周期重叠：用户切换账号、导航离开或选择另一个登录方式时，应用要决定是否取消挂起请求，如何避免旧 Promise 完成后覆盖新状态。请求对象应带本地操作 ID 或状态代次；结果返回时，仅在它仍属于当前登录尝试的情况下更新 UI。否则，一个较早的 passkey 请求晚到，可能覆盖用户后来输入的账号或错误提示。

不要把条件请求无限期放在不受控的组件生命周期里。页面卸载时清理监听器、重置等待状态，并确保重复渲染不会启动多份 get 请求。若浏览器对 concurrent credential requests 有限制或返回错误，应向用户提供可解释的操作，而非反复自动重试。具体错误名称和行为受浏览器版本、平台认证器和用户设置影响，需在目标环境测试。

能力探测的结果不能代替兼容性矩阵

能力检查回答“此时此客户端是否报告支持这项 mediation”，不证明所有账户都有可用凭据，不证明某种平台认证器可用，也不保证 UI 一定能显示。W3C Level 3 还提供 capability discovery 的相关概念；但产品仍需测试不同浏览器、操作系统、密码管理器、跨设备凭据和 iframe/嵌入场景。跨源 frame 的 Permissions Policy、RP ID 与祖先关系等约束，也不能从一个 Boolean 中推断。

建议至少覆盖能力返回 true、false、方法不存在、Promise 异常、用户取消、无匹配凭据、credential 返回但服务器拒绝，以及成功断言八类测试。记录的是客户端和服务端各自状态，不要把“候选出现”压成“passkey 已验证”。需要注册流程时，单独评估 conditional create，而不是复用 authentication 的 availability 检查。

什么时候值得启用？

如果主要登录表单以用户名为中心，且用户设备、浏览器与 RP 配置经过验证，conditional mediation 可减少显式跳转并让 passkey 作为候选自然出现。若用户需要明确选择账户、设备支持不稳定或嵌入场景限制较多，显式按钮更容易解释并测试。两种体验可以并存：能力检查决定是否启动静默等待式 get，请求结果仍由服务器验证，失败后回到明确的可见登录方式。

本文依据 2026 年 8 月 25 日的 WebAuthn Level 3 W3C Recommendation。文中没有执行浏览器兼容性测试或认证流程。落地时应对实际浏览器矩阵验证能力探测、用户取消、导航竞态和服务器拒绝路径；conditional mediation 只是 UI/请求介入方式，不改变 WebAuthn 的信任边界。

后端 challenge 也应和前端操作代次对应。若用户发起条件式请求后又改用密码登录，旧 challenge 可以在服务器端失效或标记未完成；若断言稍后返回，不能把它自动并入新会话。challenge 的随机性、一次性消费和账户绑定属于服务器校验，不应由浏览器是否显示候选决定。测试需覆盖用户取消后再次尝试、多个标签页同时登录以及旧请求迟到，确认 UI 状态和认证会话都只采用当前授权的那次结果。

延伸阅读：本站可访问认证的逐步检查。它不代替 WebAuthn 签名验证，而是帮助设计能力探测失败后的可用回退。

请求生命周期还应绑定明确的登录尝试代次。用户切换到密码登录后，应将更早的条件请求标为过期，避免它迟到后覆盖当前界面。服务器签发的 challenge 要有短时有效期，并只对预期账户和 relying party 消费一次。若旧断言在用户开启新尝试后才返回，应拒绝或单独处理，不要把它附到碰巧处于活动状态的会话。这样可以让降级路径可预测，也不会把浏览器取消请求误当成服务器已丢弃 challenge 的证据。
