EventBridge Archive 重放历史事件，为什么副作用可能再发生？

EventBridge archive replay 会把选定时间范围的事件重新送回原 event bus，不会撤销消费者已有副作用，也不保证与原到达顺序一致。重放前要限定目标并保护下游写入。

正文

核心要点

  • EventBridge archive 只能重放到最初接收事件的 event bus。
  • 重放事件按 event time 分钟区间处理，不保证与归档到达顺序一致。
  • replay-name 可识别重放事件，但消费者副作用仍需幂等或隔离。

EventBridge Archive 的 replay 会把选定时间范围内的历史事件重新发送到原先接收它们的 event bus。它不撤销消费者之前已经完成的副作用，也不保证事件按最初进入 archive 的顺序再次到达。若消费者收到事件会发邮件、扣款、创建工单或更新状态，重放前必须决定怎样防止重复副作用；“这是恢复操作”不会自动让消费者知道它已经处理过这条业务事件。

Archive 保留与 replay 范围是两个选择

创建 archive 时可以用 event pattern 过滤要保存的事件，并设置保留期限；AWS 文档指出默认可无限期保存，具体配置仍应按实际账户验证。启动 replay 时要指定要重放的时间范围，也可选择原 event bus 上的规则。Archive replay 只能回到最初接收事件的 bus；不能把它当成任意目标 bus 的导出工具。事件重放后仍留在 archive 中，可多次重放，直到超过保留期或 archive 被删除。

这意味着重放是再次投递，而非移动或“撤销后恢复”。AWS 会为 replayed event 添加 replay-name 元数据，并用它避免重放事件再次进入 archive。消费者可以用该值区分实时与历史重放流量、选择隔离处理或写入审计字段；但该标记本身不是业务幂等键，也不会阻止同一事件产生第二次付款或邮件。

假设场景：恢复历史订单事件却重复发通知

假设一个消费者原先处理 OrderPaid 后发送收据邮件，并将订单状态推进到 notified。部署中断导致一部分事件未成功送达，运维人员准备重放过去 30 分钟的 archive。部分事件可能其实已被消费者处理，只是 ack 或下游指标丢失；重放后同一订单的消费者再次运行，若邮件发送不幂等，用户会收到第二封收据。若处理函数把订单状态从 paid 改写成 paid，数据库结果看似无变化，也不代表外部邮件没有重复。

修复要把事件传输 ID 与业务副作用幂等键分开。消费者在发送邮件前可记录与订单/通知类型关联的去重键，并将外部发送状态与数据库事务设计成可恢复流程；若邮件服务没有幂等支持，需要 outbox 或人工核对边界。replay-name 可标注这批恢复事件，但仍需要对照业务事件 ID 与副作用记录。这里是架构推演，没有对真实订单系统进行 replay。

时间窗口不是原始接收顺序

AWS 文档指出，archive 到达可能有延迟，并建议在 replay 前等待 10 分钟，确保事件已进入 archive。重放按事件中的时间字段分批处理，以一分钟区间推进；覆盖 20 分钟范围时，会先处理较早的一分钟区间，然后下一个区间。即使范围顺序是时间递进，每个区间内部也不应假设与原始 archive arrival 顺序一致。事件的业务时间与投递时间也可能不同。

如果系统依赖严格顺序，如账户余额变更必须先开户再扣款，仅按 replay 时间范围不能自动重建该顺序。需要在消费者端按聚合 ID 版本检查、拒绝旧状态更新，或把事件送到专用验证流程后再批准副作用。检查 DescribeReplay 的进度以及 EventLastReplayedTime，但不要把最后重放时间戳解释成所有目标都已经完成业务处理。

重放前如何缩小影响范围？

先核实 archive 的 event pattern 与保留期限，确认被选时间段和事件来源。再枚举原 event bus 上会匹配的规则与目标：哪些消费者会接收，哪些会造成外部副作用，哪些只是分析或重建索引。可以选择规则范围控制 replay 目标，但规则改动本身也需要评审与回滚计划。高风险消费者可以先在隔离目标或 dry-run 逻辑中解析事件，统计候选数量、重复业务 ID、时间范围和无法关联的记录。

准备幂等策略、速率限制、暂停开关和停止条件。AWS 说明 replay 可能与 PutEvents 额度分离，但账户与区域仍有并发 replay 数量上限；吞吐应按当前 quotas 和目标容量规划。若发现下游重复率上升、顺序冲突或状态回退，应停止 replay 并保留进度证据，而非继续扩大窗口。重放的事件按分钟处理意味着暂停与恢复也应以 replay 状态、处理时间段和业务确认对齐。

怎样验收恢复而不把投递完成当业务完成？

在测试 event bus 上构造一条事件，先正常消费一次，再对包含它的范围做 replay；验证目标消费者看到 replay-name，幂等键使副作用保持唯一，同时记录投递次数与业务写入次数。再覆盖事件延迟进入 archive、同一时间段重复 replay、消费者处理失败、某个规则被排除、以及 event time 与创建顺序不一致等情况。验证前要确认 archive 里的数据符合实际过滤规则。

生产恢复验收需要同时看 EventBridge replay 状态、目标投递指标、消费者处理结果和业务副作用台账。服务返回“重放已完成”只证明 AWS replay 过程状态，不证明所有 Lambda、队列、HTTP 端点或外部系统完成了业务操作。本文没有访问 AWS 账户或执行 replay；具体配额、目标延迟和错误恢复应针对当前区域与消费者实现验证。

适用边界

Archive replay 适合在消费者修复后重新处理保留事件、或让新逻辑回看历史输入。它不是事务回滚、全局事件排序器、跨 bus 复制机制或去重服务。若历史事件会触发现实副作用，先让目标规则和消费者能识别 replay、具备幂等处理和停止控制，再选择窗口。恢复正确性的最终证据是业务状态与副作用台账一致，而不是单独一个 replay 状态变成 COMPLETED。

目标规则也可能在 replay 期间被同时修改。若运维人员为了缩小范围临时禁用一条规则，另一条默认规则仍可能把事件送到副作用目标；因此要在启动前枚举事件 bus 上所有匹配规则，并记录 replay 中规则配置的变更。区域内并发 replay 有上限，等待队列或分阶段重放也要纳入事故时间线。暂停操作只能停止后续处理，无法撤回已经交付给 Lambda、队列或外部 HTTP 服务的事件。
