虚拟列表只渲染三项，怎么标记真实位置？

用六十项集合中的两个三行窗口核对真实位置、总数和未知总数的表达。

正文

核心要点

  • 集合位置从一开始计算。
  • 在部分渲染的列表中应区分可见行数与集合大小。
  • 总数未知时保留可确认的位置。

课程列表有六十项，页面只把第21到23项渲染成三行。对可访问的列表项来说，窗口第一行可以是集合里的第21项。采用窗口化渲染时，aria-posinset 应跟随当前集合中的真实位置，aria-setsize 应描述该集合大小；不能让三行的 DOM 下标改写两份信息。

先定“这一组”包含哪些成员

WAI-ARIA 的 aria-posinset 定义描述成员在当前集合中的位置，首项从一开始。若所有成员都已在文档结构中，作者通常无需另外声明位置。只有部分项渲染时，程序无法从眼前的三行推断它们在六十项里的位置，作者可以把已知值写在支持该属性的角色上。这里用普通列表项，没有把只读目录变成列表框或选择控件。

aria-setsize 的定义描述当前集合的大小。对同一个窗口里的三个条目，应使用同一个实际总数。在测试数据中，六十来自完整目录模型，绝不取当前列表元素有几个孩子。这一点和位置信息互相约束：若一个条目自称位于第21位，又说整个集合只有三项，数据计算就错了。应该在一个明确集合对象里同时维护这两个值。

有筛选和排序时，先确定“当前集合”指什么。假设完整目录有六十门课，而筛选“已开始”后剩十二门。若组件向用户呈现的是筛选结果列表，位置应按这十二项的当前顺序计算，不能保留同一课程在未筛选目录的第21位。课程自己的业务编号仍可以不变，应用用它识别该条目；展示位置随着排序和筛选变化。把它们分开能避免刷新后重新编号顺便改掉业务身份。

给窗口的两次渲染写独立预期

下面是完整的本地 HTML，尚未在浏览器或辅助技术中执行。程序用六十条固定名称构造目录，只渲染其中三项。先看第21到23，再点按钮显示第24到26。按钮留在列表外，示例没有在一个已聚焦的列表项上替换它，也没有模拟浏览器滚动。它只隔离一个窗口化渲染最容易错用的计算：本地行下标与集合位置。

<!doctype html>
<html lang="en">
<meta charset="utf-8">
<title>Course window positions</title>
<h1>Course catalog</h1>
<button type="button" id="next">Show items 24 to 26</button>
<ul id="courses" aria-label="Courses"></ul>
<pre id="log"></pre>
<script>
const byId = id => document.getElementById(id);
const [list, button, log] = ['courses', 'next', 'log'].map(byId);
const catalog = Array.from({ length: 60 }, (_, i) => 'Course ' + (i + 1));
const { length: total } = catalog;

function render(first) {
  const rows = [];
  for (let position = first; position < first + 3; position++) {
    const row = document.createElement('li');
    row.textContent = catalog[position - 1];
    row.setAttribute('aria-posinset', String(position));
    row.setAttribute('aria-setsize', String(total));
    rows.push(row);
  }
  list.replaceChildren(...rows);
  log.textContent = JSON.stringify(rows.map(row => [
    row.getAttribute('aria-posinset'), row.getAttribute('aria-setsize')
  ]));
}
button.onclick = () => render(24);
render(21);
</script>
</html>

预期初始窗口的三份记录分别是位置21、22、23，总数均为60。点击后应变为24、25、26，总数仍为60。当前文档节点数始终是三。标题中的课程编号也能用来核对两组对应关系，不能只断言从三行变成了另一组三行。页面上的日志是程序读取属性的记录，浏览器和读屏是否把这些属性解释给用户，仍需独立验证。

负例可以保留课程标签，让属性位置用窗口索引一、二、三，集合大小用当前可见行数三。每一行仍有合理的课程名，视觉截图甚至可能和正确结果一样，但位置已改成另一个集合。验收应从固定的六十项记录推导两个窗口的预期，避免直接用已经存在的属性拼成“预期”后自我通过。站内定位器只枚举当前匹配项讨论了测试如何看见当前 DOM，这里的三行是刻意的呈现边界，不能作为集合大小证据。

把窗口更新和集合变更分别验收

仅切窗口时，总数保持不动。若筛选条件改变或目录收到数据刷新，先算新集合再渲染，避免页面标题已经说有十二门课，属性还报告六十。一个可核对的顺序是先给窗口一份集合身份和版本，再用那一版本的排序结果、已知总数和当前偏移生成属性。较早查询的响应晚到时，也要确认它是否仍属于当前筛选。这个版本检查属于应用逻辑，ARIA 不会替团队发现旧结果。

一些窗口组件复用已有的行节点，只替换标题和少数属性。此时应检查同一行从“课程21”换成“课程24”以后，文字、位置与集合大小是否在同一次更新中一致。举例说，快速滚动时界面可能拿到新标题，却因为一条缓存的模板属性继续报告原位置。测试可以暂缓下一批数据，观察过渡期间有无错误组合；等更新完成后，再从课程编号找到节点并核对实际位置。无需把短暂没有数据解释成该列表永久少了几项，但项目应清楚规定等待期间显示旧集合、空占位还是正在更新。

还应区分列表项可阅读与列表可操作。示例保持普通列表语义，位置和大小不会让每项自动可选，也不会让不可见的数据自动加载。真实窗口若回收当前焦点所在的节点，应另行检查下一次键盘动作落在哪个对象。只记录正确序号不能证明键盘流程连续。可以按实际支持组合检查完整的找课任务：进入列表，确定当前项位置，移动到下一窗口，确认焦点仍可找回，最后核对选中的课程身份。示例没有执行这一用户路径。

知道它是第21项，但还不知道总数怎么办？

如果应用能够确认位置而总数未知，可以保留 aria-posinset 为21，并按规范将 aria-setsize 标记为负一。负一表示未知，不是当前已加载三行，也不是还有一行。主例有固定的六十项，这个条件改成后端只给当前范围和真实起始位置。若后端连位置也没有提供，不能把局部行索引写成绝对位置；要先完善接口或调整列表承诺。等确认总数以后，应按同一集合版本更新位置与大小，并重新验证辅助技术实际如何呈现。
