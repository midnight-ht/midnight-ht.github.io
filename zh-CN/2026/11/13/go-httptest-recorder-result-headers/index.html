Go 测试明明看到响应头，为什么 Result 里没有？

用 Go httptest 的写入前后对照，区分处理器可修改的头表和 Result 的响应头快照。

正文

核心要点

  • Recorder 的 Header 是处理器可修改的头表。
  • 处理器结束后用 Result 读取普通响应头快照。
  • 需要真实传输证据时，另测经过实际服务的响应。

Go 的处理器在写正文之后才设置普通响应头时，Recorder 的可变头表可以看见新值，Result 里的响应快照却没有它。要验证处理器交付了什么，应等处理器返回，再读取 Result 的响应头。

假设下载接口在生成内容后记录一个完成标记。测试直接调用处理器，检查 Recorder 头表里有 X-After，便认为客户端能收到它。浏览器请求却看不到。先把两条观察放到同一测试里，一条检查处理器当前还能修改的表，一条检查第一次写入时留下的响应快照。这样可以把处理器设置时点的问题，和代理删头、测试环境配置等其他问题分开。

两个观察点记录了不同时间

ResponseRecorder 的 Header 方法实现了处理器可用的 ResponseWriter 接口。返回的头表供处理器修改。Go 的 httptest 文档要求在处理器执行结束后调用 Result。返回响应的头是在第一次写入时取的快照；如果处理器从未写入，才在调用 Result 时取快照。本文只讨论普通头，不使用尾部字段，也不借本地 Recorder 推断真实连接的表现。Go net/http/httptest。

若报告接口先写入正文，后来才修改普通头，那么头表的当前内容仍可以更新。在同一次测试中，读取这个表只能说明最后的赋值发生了。即使状态码、正文和早期头都符合预期，它也不能替代 Result 里的晚期头断言。修复通常是把已经能确定的头移到写出前。若某个值只有整个计算结束才知道，就得选择延迟提交响应，或给客户端定义另一份合适的合同。

让两个处理器路径只差赋值时点

下方测试为未执行教学样本。把文件放在独立 Go 测试目录，可用支持 io.ReadAll 的工具链执行 go test。样本先在可用头表设置 X-Before；两个分支都写出 ok，再分别在写出前或后设置 X-After。所有输入是本地构造的请求，样本没有启动 HTTP 服务器。

package recorderdemo

import (
    "io"
    "net/http"
    "net/http/httptest"
    "testing"
)

func report(w http.ResponseWriter, r *http.Request) {
    h := w.Header()
    h.Set("X-Before", "ready")
    if r.URL.Path == "/fixed" {
        h.Set("X-After", "done")
    }
    _, _ = io.WriteString(w, "ok")
    if r.URL.Path != "/fixed" {
        h.Set("X-After", "done")
    }
}

type observation struct {
    status int
    body, mutableLate, responseEarly, responseLate string
}

func TestReportHeaders(t *testing.T) {
    for _, tc := range []struct {
        path, sent string
    }{{"/late", ""}, {"/fixed", "done"}} {
        t.Run(tc.path[1:], func(t *testing.T) {
            rec := httptest.NewRecorder()
            report(rec, httptest.NewRequest(http.MethodGet, tc.path, nil))
            res := rec.Result()
            defer res.Body.Close()
            body, err := io.ReadAll(res.Body)
            if err != nil {
                t.Fatal(err)
            }
            mutable, response := rec.Header(), res.Header
            got := observation{
                status: res.StatusCode, body: string(body),
                mutableLate: mutable.Get("X-After"),
                responseEarly: response.Get("X-Before"),
                responseLate: response.Get("X-After"),
            }
            want := observation{http.StatusOK, "ok", "done", "ready", tc.sent}
            if got != want {
                t.Fatalf("got %+v, want %+v", got, want)
            }
        })
    }
}

预期两个子测试的状态码都为二百，正文都是 ok，X-Before 都等于 ready。两个 Recorder 的可变头表最后也都有 X-After: done。差异只出现在 Result.Header。晚赋值路径的 X-After 为空，前置赋值路径为 done。如果只保留可变表断言，两条路径都会通过，测试就失去发现这个错误的能力。正控制可以证明测试确实读了正确的头名并能看到赋值完成后的响应。

这里用 Header.Get 比较有非空值的哨兵字段。如果生产合同还要求区分头缺失和头存在但值为空，应该额外检查规范化后的键是否存在，以及它有几项值。空字符串是这份教学样本对缺少哨兵的简洁表达。扩大到业务接口时还要约定同名多值的预期，避免把两次 Set 或 Add 写出的状态误判为同一个结果。

把断言放到消费者真正看到的对象上

对于只关心处理器逻辑的测试，Recorder 可以把普通响应头、状态和正文的证据留在一个地方。不要对完整 Response 做深度相等比较。Go 文档允许 Result 将来填充更多字段，逐项验证实际合同更稳定。若需求还包括中间件重写，要让测试入口经过那条中间件链。进一步需要核对真实传输、客户端兼容或反向代理的处理时，应分别用真实 HTTP 连接和相应部署测试来验证。这个样本没有观察到它们。

可以再加一个应用侧反例。假设接口通过同一组件处理成功与失败，错误分支可能先写错误状态，再尝试附上请求编号。只测试成功路径会让请求编号的断言看似全覆盖。对错误路径提供独立请求，核对错误状态、正文形状和编号是否进入最终头表快照。如果编号只能由统一中间件提供，就把中间件纳入测试入口。把头的设置留在最后的 defer 回调也应当按实际写入时序检查；函数收尾并没有替它抢在第一次写入之前执行。

验收记录可以保存两份观测而只把其中一份用于判定网络合同。可变表帮助定位代码确实完成赋值，最终响应快照用来判断赋值是否赶上发送边界。若失败路径需要保留原始证据，应记录响应写入点和对应请求类型，随后再到服务集成层复查。并行子测试的测试资源寿命也是一个时点问题，但这里比较的是一份响应的可变对象与快照，不能用测试结束来推断头在何时固定。

如果真正的完成标记只能在导出末尾得到，可以先用小数据验证一次缓冲版本。让一条请求在生成文件前失败，另一条在数据齐备后成功。检查失败时有没有提前送出成功状态，成功时是否保留完成标记与完整正文。这个决定还涉及等待时间与内存，因此流式下载不能照搬小响应的方案。若客户端有独立的完成查询，也可以在那条接口里核对生成结果，不要求普通响应头承担生成完成后的通知。主例没有使用缓冲、流式或独立查询，这组输入只给这些选择提供验收条件。

处理器从未写正文，也没有调用 WriteHeader，会怎样？

给一个新的处理器分支只写入 X-Before 的值，随即返回，明确不调用 Write、WriteHeader 或 Flush。文档规定这样的分支会在调用 Result 时取头快照。用独立的 Recorder 验收应得到 ready，正文为空。不要在同一个 Recorder 上先执行写正文的路径再执行空分支，也不要在处理器仍在执行时提早调用 Result。这个追问是未执行的边界测试，它没有声称真实 HTTP 服务的空响应行为已经验证。
