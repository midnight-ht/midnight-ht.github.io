收到 HTTP 103 Early Hints，为什么还不能算请求成功？

用本机回环的一次 103 和最终 404 分开记录提示头、完成状态和响应内容。

正文

核心要点

  • 103 可以给客户端准备所需的提示。
  • 最终状态和最终头决定响应处理。
  • 回环事件不验证浏览器实际资源加载。

服务器先发出 HTTP 103，提示客户端可能需要 style.css，最后却返回页面不存在。记录里应该保留两件事：收到一次准备提示，页面请求最终得到 404。103 不是请求成功，提示里的 Link 也不会自动成为最终响应头。

这次准备能用到什么信息

RFC 8297 的 Early Hints 定义描述的是一种信息响应。服务器还在生成最终结果时，可以提前告诉客户端某些可能出现的头部字段。客户端可以据此做推测性准备，例如处理一个预加载关系。最终响应的处理仍须以它自己的字段为准。服务端在得知原计划不合适时可以给出不同的最终头，也可以只在提示里提供一部分信息。

IETF HTTP 语义中的 1xx将这类状态作为最终响应之前的临时信息。本篇讨论 103，不涉及切换协议，也不假定所有代理都保留它。应用只看到一次信息响应就更新页面状态时，容易把“收到准备材料”误写成“拿到了可用文档”。进度显示可以记录发生过提示，成功、失败和正文解析则等待最终结果。

举例来说，产品页面的服务器还要等一个查询，才能知道这条地址对应的页面是否存在。提前提示的样式在多数成功路径上会用到，但查询结果可能让同一个请求以失败结束。客户端应能区分“提前看到了样式线索”和“成功拿到此地址的文档”。如果让 Link 字段覆盖一份通用头部映射，后续日志很难判断某个值究竟来自哪一层。

用一个回环请求保留两份记录

以下是完整的本地 Node 示例，服务器绑定回环地址的临时端口。它给一次合法请求发一个带 Link 的早期提示，然后返回不带 Link 的 404 和文本 missing。客户端分别观察 information 事件和最终响应，读取正文结束后才比较。预期不是从运行日志反推：请求的设计先明确一次 103、一个最终 404，且两份头刻意不同。

import { deepEqual } from 'node:assert/strict';
import { createServer, get } from 'node:http';
import { once } from 'node:events';

const link = '</style.css>; rel=preload; as=style';
const server = createServer((request, reply) => {
  reply.writeEarlyHints({ link });
  reply.writeHead(404, { 'Content-Type': 'text/plain; charset=utf-8' });
  reply.end('missing');
});
server.listen(0, '127.0.0.1');
await once(server, 'listening');

try {
  const { port } = server.address();
  const events = [];
  const final = await new Promise((resolve, reject) => {
    const request = get({ hostname: '127.0.0.1', port, path: '/' }, reply => {
      reply.setEncoding('utf8');
      let body = '';
      reply.on('data', chunk => { body += chunk; });
      reply.once('end', () => resolve({
        status: reply.statusCode, link: reply.headers.link ?? null, body,
      }));
      reply.once('error', reject);
    });
    request.on('information', ({ statusCode, headers }) => {
      events.push({ status: statusCode, link: headers.link });
    });
    request.once('error', reject);
  });
  deepEqual(events, [{ status: 103, link }]);
  deepEqual(final, { status: 404, link: null, body: 'missing' });
  console.log(JSON.stringify({ events, final }));
} finally {
  await new Promise((resolve, reject) => {
    server.close(error => error ? reject(error) : resolve());
  });
}

两个断言有不同的职责。第一项验证提示确实带有预期的资源关系，第二项验证最终状态、头与正文。如果只检查信息事件数组非空，就算最终响应从未完成，也会误以为请求成功。另一个错误是把信息头拼进最终头，得到一个看似携带 Link 的 404，样本里的最终字段判据能直接发现它。代码只用 Node 客户端观察协议事件，不会启动浏览器或请求样式文件。

实用的记录结构可以用一个请求标识关联两类事件，分别存储信息响应的序号、状态和头，以及最终状态和读取结果。若网络中途失败没有获得最终响应，应明确标记结果未取得，不把最后一个看到的临时状态当作最终码。如果监控要统计成功率，也应该从最终请求结果定义分母和分子。资源预加载是否开始、是否命中缓存、页面是否更快，还需要另外的浏览器观测。

还可在日志里为最终响应的头部和内容保留各自的采样点。收到最终头时状态已经可识别，完整内容却可能尚未读取完。假设上层必须在文本验证成功后才能显示文档，就应把收到最终头与完成正文读取分别记录。这样既能定位中断发生在提示之后还是正文中间，也不会在一切都转成“请求结束”的事件名后失去判断依据。本文的固定样本在读取完文本才作最终断言，实际生产客户端则应按自己的失败状态报告。

上线前检查两条证据链

先在应用边界核对没有 103 时的正常最终结果、带 103 后成功、以及带 103 后失败。此时服务端负责发出协议事件，接收方负责把它归到正确请求。然后才检查浏览器是否接收到提示、是否安排了资源请求，以及最终页面是否使用了那个资源。两类测试可以用相同地址，却有不同的观察点和通过条件。这个回环样本不经过反向代理，不能证明网关、协议转换和真实 CDN 会保留同样行为。

如果接入网关后只有客户端一侧看不到提示，先在网关两侧用同一个请求标识对应记录，并把是否收到最终响应单列。源站看到已经发出提示，可以定位出站动作，客户端看到最终响应，可以确认请求完成；两者都不能独自说明中间环节传递了哪份信息。

资源选取也应有自己的适用条件。若某份样式只用于少量用户最后会得到的视图，猜错资源就可能产生不必要的准备工作。先选择长期稳定、在目标最终结果中确实需要的资源，使用真实链路核对提示是否值得做。不要用本地示例的输出推算时间节省。它只说明 103 和最终响应可以分别被读取。站内100 Continue 上传协商讨论客户端何时发送请求正文，本篇关注下载方向上的准备信息和最终处理。

两次 103 的第二份没有重发第一个 Link，第一份还算数吗？

准备阶段可以考虑两次提示。比如第一次给 style.css，第二次给 script.js，规范允许服务器发送多次 103，也不要求后一份重复已经发送的字段。最终响应如果没有 Link，客户端不应把两份提前提示拼成它的头部。这个新例改变提示的数量，主样本只发过一次。验收时可以记录两条分别带资源的提示和独立的最终状态，再根据客户端真实行为观察是否采用提示，不从第二份缺字段推断第一份已被撤销。
