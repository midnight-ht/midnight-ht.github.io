Intl.Segmenter 已用 word，为什么词数还算多了？

用带标点的固定文本比较所有词粒度片段和 isWordLike 过滤后的词数，并核对原字符串坐标。

正文

核心要点

  • word 粒度会返回可遍历的片段。
  • 应用可按 isWordLike 筛出词状片段。
  • 产品需要约定语言和实现的计数口径。

文本 Tea, cake! 读起来有两个词，用词粒度遍历却能得到五个片段。Intl.Segmenter 也会返回逗号、空格和叹号。要按这份分段实现统计词数，应从词粒度结果中选出 isWordLike 为真的片段，再计数。保留片段的原文位置，才能把计数和标注核对到同一份输入。

词粒度也描述词与词之间的内容

ECMA-402 的分段方法用选定语言和粒度创建可遍历的分段结果。片段记录的定义包含原始输入、切出的文本及起点。选择 word 时另有 isWordLike。规范说明分类依赖实现，并建议按语言调整。只含空格或标点的片段通常不被视为词状，但这个事实不能推出所有语言的所有输入都遵循一份固定的词典。

设想一款校对工具同时显示词数和需要复查的词。原来通过计算所有片段的长度得到五，点击第二个计数项却落到逗号。若产品的计数口径是当前语言环境的词状片段，计数与高亮就该使用同一组过滤结果。需要标记标点时可以另保留完整片段，而不是把用于计数的数据视作全文的全部成分。这样用户看到的是一份有明确范围的数值，也能解释为什么高亮位置没有越过标点。

让词数、片段与原文互相对照

下面的本地 Node 程序只用固定英文输入。可先手工列出 Tea、逗号、空格、cake 和叹号，确认这五段拼回原文。再从零起数原串，Tea 从零开始，经过三个字母、逗号与空格，cake 从五开始。两个预期在代码外可先算出来，避免对当前实现的输出照抄一份断言。

import { deepEqual, equal } from 'node:assert/strict';

const text = 'Tea, cake!';
const { Segmenter } = Intl;
const segmenter = new Segmenter('en', { granularity: 'word' });
const pieces = Array.from(segmenter.segment(text));
const labels = pieces.map(({ segment }) => segment);
const words = pieces.filter(({ isWordLike }) => isWordLike);
const positions = words.map(({ segment, index }) => [segment, index]);

deepEqual(labels, ['Tea', ',', ' ', 'cake', '!']);
deepEqual(positions, [['Tea', 0], ['cake', 5]]);
equal(labels.join(''), text);
const { version, versions: { icu } } = process;
console.log(JSON.stringify({ version, icu, labels, positions }));

对这个输入，把全部片段计数会得到五；只按空格切分看似得到两个，却把逗号和叹号夹在词内。如果界面还要定位 cake，第二种做法得再定义如何处理标点与位置。词状过滤保留的是两条原文记录。高亮时用原字符串坐标切出对应区域，而不是将已经过滤的两个词重新拼成字符串以后，再以那个短字符串的偏移写回原文。

把两种结果都保留能减少另一个常见误诊：条目数量变少不意味着文本丢了。原始片段仍能拼回完整文本，过滤列表仅用于计算这个指标。若数据处理过程还做了大小写变化、删除空格或 Unicode 正规化，应在明确的阶段计算并保留对应坐标。比如把原串中的连续空格压成一个后再标注，后面的起点可能整体提前。需决定高亮针对处理前还是处理后的文本，并让位置基于同一份值。

给产品指标指定口径

文章字数提示、审核词数限制和全文搜索切词看起来都在数词，实际目标不同。只在阅读界面给近似长度提示时，可以在明确的语言和版本内采用这份词状统计。若同一个上限会在接收端拒绝提交，应给两侧同一份可复核规则，并用实际运行环境记录差异。搜索还可能依赖词干或词典处理，不能把这个页面的统计片段直接当索引合同。

固定英文例子用来判断数据管道有没有把空格和标点一起数入，不用来宣称中文、泰文或混排句子应有固定词数。可以记录运行时版本、ICU 版本、实际选择的语言，以及每一段的文本、位置和分类。升级后用原始字符串复跑，若变化影响限制或统计报表，先决定指标如何迁移，再决定是否重新计算旧结果。这里没有收集生产文章和使用者数据。

如果页面显示还剩一个词，提交后服务端却拒绝，应保留双方实际使用的原文和语言，而不是仅记录两个整数。先确认服务端有没有在校验前替换换行、去掉前后空白，或者为同一语言选择另一种分段实现；再比较词状片段差在何处。若新版本打破旧合同，可明确将旧稿按旧口径展示，或让全部视图改用接收方的新计数，并把差异说明在编辑页面上。对已经超过限制的草稿，优先提示修改位置和采用的单位，避免静默截断。这样的故障定位不需要宣布哪套分词最正确，只需要说明哪份数据在哪一步获得权威判定。

验收时再准备一份全为空格和标点的输入，以及一份包含多个连续空格的混排输入。两份都检查结果拼回原文，并观察适用环境怎样判定词状成分。根据产品要求，可以把标点输入是否算零词写成自己的接收合同，但不要从这份固定英文例推断所有环境已经满足。本站原生 textarea 的长度单位解释浏览器表单的代码单元上限，本篇的词状统计解决的是另一类显示和编辑需求。

一个表情在词前面，index 能当代码点位置吗？

不能直接这样用。把输入改成 😀、一个空格和 Tea，表情占两个 UTF-16 代码单元，空格占一个。Tea 的片段起点是三。按代码点数前缀只有两个，直接把这个数字传给使用代码单元位置的字符串切片会从空格开始。主例里所有字符都只有一个代码单元，因此不能区分这两个坐标。

import { equal } from 'node:assert/strict';

const text = '😀 Tea';
const { Segmenter } = Intl;
const words = new Segmenter('en', { granularity: 'word' });
const [, , last] = words.segment(text);
const { index, segment } = last;
equal(segment, 'Tea');
equal(index, 3);
const prefix = text.slice(0, index);
equal(Array.from(prefix).length, 2);
equal(text.slice(index), 'Tea');
console.log('Tea starts at UTF-16 offset 3 and code point offset 2');

应在接口中给位置明确命名，例如声明从原字符串起算的代码单元偏移，或在需要代码点位置的消费者边界做转换。不要用当前单词长度猜它前面出现了多少代理对。真实输入中的组合序列还可能让感知字符位置不同，因此要按下游实际用的坐标单独验收。
