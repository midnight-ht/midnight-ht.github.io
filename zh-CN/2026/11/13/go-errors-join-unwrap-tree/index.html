errors.Join 包了两个错误，为什么 errors.Unwrap 返回 nil？

用直接合并和外层包装两个路径，核对 Go 单步解包、错误树匹配与阶段报告的边界。

正文

核心要点

  • Unwrap 帮助函数只识别返回单个错误的方法。
  • Is 与 As 可以检查错误树。
  • 完整阶段报告应保留每个失败的归属。

Go 的 errors.Join 把多个错误放进一棵错误树，errors.Unwrap 却只调用返回单个错误的解包方法。直接对 Join 的结果调用它，会得到 nil。判断原来的错误是否仍可识别，应使用能遍历错误树的 errors.Is 或 errors.As。

假设导出文件的主操作失败，随后清理临时资源也失败。服务想把两个错误都交给上层，于是调用 Join。旧日志工具不断调用 Unwrap，遇到 nil 就认定里面没有原始错误。拿到合并值之后，它突然只能显示最外层文字，按原错误分类的指标也停止增长。先检查代码在问什么。单步解包是在问是否有一个可以直接返回的子错误；按错误身份匹配是在问树中有没有符合条件的节点。

两种解包方法不能互换

Go 标准库文档定义了两类包装方法。一类返回 error，一类返回 []error。Join 在返回非空错误时实现第二类方法。errors.Unwrap 只识别第一类，所以即使一个合并结果包住两个非空错误，帮助函数仍返回 nil。相反，Is 和 As 会检查错误自身，并按先序深度优先检查每个子节点。这个规则让错误树既能表达普通的单层包装，也能表达多个失败一起返回的结果。Go errors 包参考。

一个常见层次是把 Join 返回的错误再用带单个 %w 的 fmt.Errorf 包装。最外层可以被普通 Unwrap 解开，得到合并对象；继续对合并对象使用同一函数，就会返回 nil。这个 nil 来自方法选择，不能用它证明整棵树没有子错误。如果迁移前的工具用线性循环累计错误种类，应该按它真正需要的输出重新检查路径。

给主操作和清理各留一个独立身份

下面是未执行的 Go 教学程序，要求 Go 1.20 或更高版本。示例只创建本地错误，不生成导出文件，不运行清理，也不调用外部日志平台。两种包装层分别拥有固定的单步预期，但都应该保留对两个 sentinel 的匹配。

package main

import (
    "errors"
    "fmt"
)

func main() {
    exportFailed := errors.New("export failed")
    cleanupFailed := errors.New("cleanup failed")
    joined := errors.Join(exportFailed, cleanupFailed)
    outer := fmt.Errorf("finish export: %w", joined)

    cases := []struct {
        label string
        candidate, expectedChild error
    }{
        {"joined", joined, nil},
        {"outer", outer, joined},
    }
    for _, c := range cases {
        child := errors.Unwrap(c.candidate)
        if child != c.expectedChild {
            panic(fmt.Sprintf("%s: unexpected child: %v", c.label, child))
        }
        for _, target := range []error{exportFailed, cleanupFailed} {
            if !errors.Is(c.candidate, target) {
                panic(fmt.Sprintf("%s: missing %v", c.label, target))
            }
        }
        fmt.Printf("%s: child as expected, both sentinels found\n", c.label)
    }
}

直接针对 joined，预期单步结果为 nil，两个身份匹配都为真。针对 outer，预期单步得到先前的 joined，两个匹配仍然为真。程序在任一条件失效时终止。它没有靠打印出的错误文字确认匹配，预期对象就是创建的两个具体错误。若有人把其中一个错误改成字符串拼接再创建新错误，合并文字可能保持不变，针对原对象的 Is 断言却应失败。这个变体只用来说明怎么发现身份丢失，并未执行。

要验证真实调用路径，可以在同一个导出测试中让主操作和清理依次产生独立错误，再到调用者拿到的结果检查两类身份。另准备只失败一次的输入，确保服务没有把未发生的失败也记进指标。尤其要核对清理是否确实被调用，不能仅给函数预先制造两个 sentinel，就宣布实际资源的异常路径已经走完。这里的程序只覆盖标准库错误结构和匹配。

按调用者要做的决策选观察方法

如果上层只需要知道某类失败有没有发生，可以针对明确的目标分别调用 Is。两个分类可能同时匹配，若指标要记录两个阶段，互斥分支就会漏掉其中一个。如果调用者需要读取某一类错误里的结构化字段，As 可以找到匹配的值。若要交付一份完整的阶段报告，就让主操作和清理各自保存阶段信息，或按两种包装合同遍历并保留每条路径。一次匹配成功并不能代表报告包含所有失败。

不要依据换行或标点反推子错误。错误消息仍然适合给用户或排查日志阅读，程序识别则应依赖明确的包装和匹配约定。验收可以把两种不同错误做成相同的展示文字，并核对应用仍分别识别它们。反过来，同一错误若增加了操作上下文，业务分类也不应因为文本变化就失效。站内的 Go QueryRowContext 错误边界 用另一个 sentinel 例子说明查询缺失如何分类；这里增加的是多个原始错误可同时存在。

如果团队确实需要检查树的每条分支，可以先为普通包装和多子错误各留一组结构用例，再测试两者嵌套。输出应能说明阶段身份和值来自哪条路径。若只需要通用分类，直接用标准库匹配通常比重复写遍历更简洁。本篇没有实现自定义遍历器，也不把错误树当成能够恢复清理动作的执行日志。

一个调用者回归可以把失败矩阵做成四条具体请求。主操作失败、清理成功时，只增加导出失败计数；主操作成功、清理失败时，只增加清理失败计数；两者都失败时，两项都增加。没有失败的请求则应走成功出口。测试记录两个计数的差值，再单独核对调用方收到的结果。若页面只允许显示一个故障提示，可以定义提示的优先级，但记录层仍应按其契约保留第二个失败。两类指标都没有读取展示字符串，用户文案后续调整也不会让身份断言改变。这组调用者用例未执行，主程序也没有启动任何指标系统。

两个分支都符合 As 的目标类型，会返回哪一个？

假设主操作和清理各自包装同一种指针错误类型，两个值的 Step 字段分别是 export 和 cleanup。只要外层节点本身不匹配，按导出在前、清理在后构造 Join 时，As 应选到前者。把顺序反过来后，预期读到 cleanup。可以分别构造两棵树，每次传入新的目标变量，核对具体 Step 值。这个追问未执行。第一项匹配只能回答这次查找停在哪里；若业务需要两项都展示，就另保留阶段记录。
