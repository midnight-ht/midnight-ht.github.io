CMake 延迟调用为什么读到了后改的变量？

用 CMake 配置输出核对 DEFER 的参数求值时机，以及何时需要固定登记时的值。

正文

核心要点

  • 普通变量引用会在延迟调用执行时求值。
  • 需要旧值时应显式传入登记时固定的参数。
  • 配置期输出与构建执行证据分开核对。

登记时还是 first，打印出来已经是 second。CMake 的 DEFER 把参数里的变量引用留到调用执行时求值。要让结束时执行的动作拿到登记时的值，得显式留下那份值。

设想一个构建配置维护者依次处理两组制品，准备在当前目录结束时打印第一组的标签。登记回调时标签正确，后面复用变量保存第二组，日志便把后一组的值写进第一组的记录。看到变量写在一对双引号中，容易以为它已经变成当时那段文字。普通调用的这种直觉不能直接用在 cmake_language(DEFER CALL ...) 上。手册把参数中引用的求值放在执行时。 CMake 的 Deferring Calls

让两个回调看同一轮赋值

下面的完整配置只使用文字标签。它分别记下立即执行、普通延迟调用和登记时先生成字面量的输出。保存为一个独立目录下的 CMakeLists.txt，执行 cmake -S . -B out。本地使用 CMake 4.2.3 实际配置，三个标签依次为 now=first、late=second、frozen=first，配置命令退出为零。没有执行后续构建。DEFER 从 3.19 提供。

cmake_minimum_required(VERSION 3.19)
project(deferred NONE)

set(label first)
message(STATUS "now=${label}")
cmake_language(DEFER CALL message STATUS "late=${label}")
cmake_language(EVAL CODE "
  cmake_language(DEFER CALL message STATUS [[frozen=${label}]])
")
set(label second)

普通延迟调用登记了一条稍后执行的命令，并保留了变量引用。等它执行时，目录已经将标签设为 second。另一条延迟调用由 EVAL 生成。构造那段 CMake 代码的过程中，当前标签先被插入，排队的命令实际收到了 bracket 参数里的文本 frozen=first。括号形式让后续执行阶段按字面量处理该参数。这里使用的是受控的短标签，不能把这个写法扩展成将任意不可信内容插入 CMake 代码。 CMake 的 Deferred Call Examples

三个预期分担不同的检查。立即日志证明登记前的值已经准备好，普通延迟日志证明后来的赋值可以影响它，固定日志证明同一次赋值没有改掉登记时的快照。若两条延迟日志都打印 first，要进一步检查最后一次赋值是否真的在这次配置中执行。若固定日志也变成 second，查生成的延迟命令是否仍携带变量引用。仅保留整个配置的退出值，读不出哪个标签进入了回调。

把写死的正确值作为反例

例如有人把固定回调改成直接传 first。对当前样本来说，输出完全一样。这个修法不能证明脚本正确接住了登记时的输入。应另做一轮，把首次设置改成 alpha，保持后续值为 second。新的独立预期是立即输出 alpha，普通回调仍为 second，固定回调为 alpha。如果固定行继续打印 first，测试就抓到了写死值的实现。这个输入变更是建议的额外对照，未包含在上述本地执行中。

还可用原样重跑核对是否真的在读这轮输出。命令若在独立构建目录运行，保存实际源目录和目标构建目录，以及本轮代码摘要。查看生成步骤结束前那三条输出，而不是从旧日志截取一条看起来正确的值。若项目同时有构建期的自定义命令，可给配置诊断加具体前缀；这样生成时出现一条消息，也不会被写成构建工具已经运行过该动作。本文的证据只覆盖 CMake 配置执行，不覆盖生成的构建命令或产物。

从回调的职责决定读取时点

如果延迟调用负责打印目录结束时收集的总结果，执行时读值正合用途。目录中的后续逻辑可继续修改列表，末尾才需要定案。若动作对应单一登记项，例如记录当时分配给某制品的标签，就要保留登记时的输入。先给两种行为起可辨认的日志名，再写各自的独立预期。对一串登记项只检查最后一行，可能漏掉前面所有条目都被后一次赋值覆盖。

把单项扩成两项时，可给每条登记记录一个固定身份，再保留期望值，例如第一个归档项对应 alpha，第二个对应 beta。配置结束前再把共用的工作变量改成 gamma。若两个记录都落成 gamma，就能说明回调仍共享后来更新的变量。若观察到 alpha 和 beta 却分别写到错的项下，问题转成登记身份配错，不能单靠固定值解决。这个对照可按整行比较身份和标签，避免只搜索日志是否出现过两个单词。它是对真实配置的拟议验收，本地样本仍只跑了上面的一组登记。

检查这种多项输出时，保留两份材料也很有用。一份记录哪条命令负责登记和当时对应的项，另一份记录回调开始时读到了什么。只有在二者按同一个身份对齐时，才能说明错误发生在取值或归档。仅在回调末尾打印当前变量的值，可能找不回它原来应该归给哪个目标。

项目若要保存含复杂语法的值，先考虑在登记时将其写入显式管理的数据，例如按稳定身份保存记录，再让回调读取相应项。这样可以避免把通用输入拼进可执行代码。上面的 bracket 定界只适用于固定语法的演示。值的来源、括号定界和后续读取范围都需要检查。若怀疑的是变量实际来自普通绑定还是缓存，可以看缓存已更新，普通引用为什么仍是旧值。这里的两条延迟调用共享一个普通变量，差异来自两次不同的求值时点。

在目录里提前 return()，已经排队的调用会被跳过吗？

手册明确说明延迟调用在目录收尾时仍会执行，即使先遇到 return()。可以另存一份配置，把提前返回放在末尾赋值之前，保留回调登记，再比较输出。后面的 second 赋值没有机会执行，因此本例的普通延迟读取应回到 first，回调本身仍应出现。这个路径尚未执行。要避免触发后续动作，应在确定不需要时避免登记，或按手册单独安排取消，而不是依赖提前返回自然丢掉它。
