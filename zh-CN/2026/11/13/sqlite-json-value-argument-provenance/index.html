SQLite 拼 JSON 时，数组为什么多了一层引号？

用六条实际验证的类型结果区分 SQLite 嵌套数组与数组文本，并给自由文本单独保留字段合同。

正文

核心要点

  • 普通 SQL 字符串会作为 JSON 字符串插入。
  • 直接传入 json() 或单箭头的结果能保留嵌套结构。
  • 检查输出路径类型，再验收具体元素和消费端。

SQLite 里，把普通 SQL 文本交给 json_object 当值时，长得像数组的字符串也会被包进引号。要让它成为嵌套数组，可以把 json() 的结果直接交给外层函数。直接来自箭头运算符的值，还要分清用的是哪一种箭头。

假设报表接口要交付一个对象，其中 items 是编号数组。表里保存着序列化文本，控制台显示方括号和两个编号。开发把这一列传给 json_object 之后，前端收到的是一段文字，要再解析一次才能取出两个元素。修复从字段合同开始。接收者要遍历数组，就应直接收到数组；如果页面要原样显示用户写下的文字，就应继续收到字符串。

同一段文本可以进入两种值位置

SQLite 文档把这类参数叫 VALUE 参数。普通 SQL 字符串作为值时，会在生成的 JSON 中成为带引号的字符串，即使内容本身符合 JSON 语法。如果参数直接来自另一个 JSON 函数，或者直接来自单箭头运算符，外层函数会把它当成 JSON 值嵌进去。双箭头给出的则是 SQL 表示。对本例中的数组而言，那是普通 SQL 文本，在外层 VALUE 参数中会按字符串处理。SQLite JSON 函数 VALUE 参数。

区别可以在字段的类型上观察。一个结果里，items 的类型是 text，接收方拿到的值是字符组成的方括号表达式。另一个结果里，items 的类型是 array，两个元素各自仍可被查询。调试时不要只打印提取出的文本，因为某些提取方式会把两种形状又变成看起来相同的字符串。针对生成的外层文档查路径类型，更容易把哪一个环节多加了引号定位下来。

让六种输入接受相同的类型检查

下面的教学 SQL 在同一个临时表与查询里列出六个标签。每个标签有自己的独立预期。代码需要能提供 JSON 函数的 SQLite，单箭头与双箭头从三点三八版起可用。运行记录见下文。

CREATE TEMP TABLE item_payload (raw TEXT NOT NULL);
INSERT INTO item_payload VALUES ('[1,2]');
WITH objects(label, doc) AS (
  SELECT 'literal', json_object('items', '[1,2]')
  UNION ALL
  SELECT 'parsed', json_object('items', json('[1,2]'))
  UNION ALL
  SELECT 'arrow', json_object('items', '{"v":[1,2]}' -> '$.v')
  UNION ALL
  SELECT 'double-arrow', json_object('items', '{"v":[1,2]}' ->> '$.v')
  UNION ALL
  SELECT 'stored', json_object('items', raw) FROM item_payload
  UNION ALL
  SELECT 'stored-parsed', json_object('items', json(raw)) FROM item_payload
)
SELECT label, json_type(doc, '$.items') AS nested_type
FROM objects ORDER BY label;

按查询的标签排序，arrow 预期是 array，double-arrow 是 text，literal 是 text，parsed 是 array，stored 是 text，stored-parsed 是 array。存取对照只涉及明确声明为 TEXT 的列。它不依赖临时表之外的来源，也没有把某个内置函数在一次表达式中传递 JSON 的性质延伸到任意查询层或客户端。这里实际执行了同一份 SQL。Python 3.11.15 的标准库 sqlite3 使用 SQLite 3.53.1，归档断言逐一验证了六个标签的类型。业务序列化和下面的额外探针没有执行。

另一个实用验收点是检查数组的元素。对确定应该嵌入的 parsed 和 stored-parsed，先查 items 的类型，再检查位置零和一的两个整数。把原来的字符串作为负对照，保证测试工具不会悄悄重新解析字符串后仍然宣布契约通过。这样能分别发现外层类型变了、元素顺序变了和数字被改成文本。这个元素验收只是拟议扩展，归档的主查询只检查目标路径类型。

解析应当跟着字段约定走

在样本里，同一段文本先存入普通 TEXT 列，读出后才决定它是不是嵌套值。如果写入的内容来自受控的配置字段，服务可以明确要求该列表示 JSON 数组，在读取后把它解释为数组，并对元素的业务类型单独检查。反过来，如果一列是自由输入的备注，长得像 JSON 不构成转换它的理由。否则某个用户碰巧写了两个方括号，读接口就可能开始返回与其他用户不同的类型。

要在已有接口上修这个错误，先查调用方目前是否手工二次解析。有的消费者已经把旧字符串当成合同，直接改成数组会让它继续尝试解析一个已经解码的对象。可以在测试数据里保留一个旧消费者实际收到的响应，再对新字段写出数组断言，分别确认两条读取路径是否需要兼容。只检查数据库里的文本、或者只看前端渲染后的两个编号，都可能错过接口层的变化。

保存验收记录时，带上生成对象的那条 SQL、目标路径和每个输入的类型预期。如果业务代码后来改成在应用中组装对象，就仍在 API 返回处检查同一个字段。此时 SQLite 查询的通过只能解释旧的组装路径。至于 JSON 缺键与空值怎样建模，站内另有字段存在性和 JSON 类型 的案例；这里固定同一段非空数组文本，只检查嵌入方式带来的值类型。

如果配置列里还有迁移前遗留的坏文本，修复不能只验证正常数组。可以准备三行配置，分别是两个编号的数组、一个合法但不符合字段要求的 JSON 对象，以及一个没有结束括号的数组文本。先按实际 SQLite 版本检查有效性，再把合法文档的根类型与接口合同核对。三行的预期应该独立，第一行组装成数组，第二行进入类型错误出口，第三行进入解析错误出口。具体是拒绝整批还是报告个别坏行，应由导出功能的错误处理约定决定。这样可以避免修掉额外引号以后，一份坏配置反过来拖垮所有条目。

若导出需要兼容两个客户端版本，还可以把相同输入送到两个明确的返回路径。旧版断言收到 JSON 字符串和原字节，新版断言收到数组及两个整数。切换后检查客户端拿到的版本号与断言配对，防止测试误把旧版返回当新版。这里没有实现版本协商，也没有验证实际坏文本的错误信息。

备注恰好是 true，可以统一套 json() 吗？

假设同一张导出表还含自由文本 remark。有一行的备注正好是四个字母 true。普通文本放到外层对象里时，路径类型应是 text；把它先交给 json() 再直接嵌入，路径类型应变成 true，消费者读到的是布尔值。两边都可以组成合法 JSON 文档，区别在于字段的值已经改变。给这个新字段保留一条同文本正反对照，可以发现某次重构把数组列的转换逻辑错误套到了备注列。这个额外检查没有运行。
