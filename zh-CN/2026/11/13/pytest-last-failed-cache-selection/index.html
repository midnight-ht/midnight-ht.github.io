pytest --lf 一片绿，为什么刚加的测试没跑？

复现 pytest 的缓存失败项选择，比较局部绿灯与本次完整测试集合。

正文

核心要点

  • 缓存失败项会改变这次运行的用例集合。
  • 把已执行节点和退出值一起记录。
  • 正式门禁需要对照它自己承诺的覆盖范围。

上一轮失败项重新通过，新用例却没有进入这个回合的执行集合。pytest 的 --lf 按缓存复跑已知失败；判断改动有没有通过测试，先看它选了谁。

测试维护者修好昨天的失败，顺手加了一条覆盖新需求的用例。为节省时间，他重跑上次失败项，终端返回成功。若把这行结果贴进发布记录，下一位读者可能理解成新增用例也已验证。实际只知道被选中且执行的那部分通过。比较运行范围与代码变化，会比继续查看失败用例的断言更快定位问题。

让遗漏的用例本身会失败

在一次性目录中保存下面的测试文件为 test_selection.py，放一份只有 [pytest] 的 pytest.ini 以隔离项目配置。示例需要 pytest，验证时关闭外部插件自动装载和环境附加选项。先运行普通的 python -m pytest -v，等待故意失败的旧用例写入本目录的缓存。

def test_old():
    assert False

def test_stable():
    assert True

保持目录和文件名不变，把测试文件替换成下面这个完整版本。第一条改成通过，新增用例固定失败。

def test_old():
    assert True

def test_stable():
    assert True

def test_new():
    assert False

执行 python -m pytest -v --lf，然后再执行一次不带选择选项的普通运行。保存三次输出，逐次记录退出值。以下是 Python 3.11.15 和 pytest 9.0.2 的本地实际结果。归档的独立驱动按顺序写入相同的两版文件，并分别断言子进程结果。

执行 关键观察 退出
建立缓存 旧用例失败，稳定对照通过 一
修复后复跑 旧用例通过，其余两项没有执行 零
修复后全量 新用例失败 一

外层驱动通过表示它看到了预期结果，其中两次 pytest 故意失败。把发布记录里的返回值指向实际被采用的进程，不能用驱动验证成功覆盖全量测试失败。

表面上，修正后的测试文件完全相同，为什么能同时有绿和红？pytest 的缓存指南把 last-failed 定义为重跑失败项。这里前一轮留下了旧用例的 node ID，旧用例的名字在改动后仍可解析。新用例虽然已进入当前文件，却不在那个已知失败集合中。打开详细输出能够看到实际执行了哪些节点；保留全量的独立结果才能证明另一条确实会失败。只比较命令是否打印成功，漏项看起来就和通过一样。

这个反例刻意让未选中的项目失败。如果它恰好是通过用例，读者可能仍然把局部绿灯看成可以接受的替代。真实门禁里，漏掉的用例可能对应新的输入边界、修复后的另一种请求，或一次与旧失败没有关系的回归。应保留用例标识和真正的执行结果，明确哪条验证尚无本次证据。这个样本的测试都放在一个文件，以免把缓存选择与调用时指定的文件范围混在一起。

复跑失败与安排回归可以是两条命令

本地排查一条已知失败时，用快速复跑缩短反馈路径。修正完成后，如果仍想先看到失败项，又要执行其余选中的测试，可以查看 --ff。缓存指南说明它把已知失败项排到前面，同时继续执行其余项目。这里没有运行这个对照。若命令本身只指定了一个文件，或用选择条件排除了部分节点，这个顺序选项也不会把它们补回来。发布门禁应使用符合本轮承诺的入口，再检查节点集合。可以把复跑和回归分成两条日志，避免后来的审查只剩一个合并的绿色状态。

在 CI 中，缓存可能来自工作目录本身，也可能是上一步恢复的数据。若测试变了名字或路径，需用当前的节点标识理解选择结果。报告可以附上本次目录、实际命令和收集到的节点，再将收集、选中与真正执行分开记录。例如同一个文件能被发现，不代表其中每条用例都执行过；反过来，一个从未选中的用例没有结果，也不能作为已知失败或已通过统计。这一套判断与预期失败为何会放行不同，后者讨论运行了的用例怎样分类。

当复跑结果会参与合并决策时，可以拿本轮新增用例的 node ID 作为一道明确的检查。它应该在正式门禁的执行记录里出现，并有结果和本次提交关联。如果一组按参数展开的测试新增了第二种输入，只搜函数名可能命中之前那一项，仍然不能证明新的参数被执行。应记录完整节点身份，并选择能区分两项的报告。与此同时，若快速重试需要保留原来的失败缓存，给它单独留一个步骤，不让发布汇总拿错那份结果。

保留缓存也有价值。若想复现局部绿灯的成因，就不要在取证前先清理。将有缓存的一轮和完整测试放进明确的独立步骤，能观察原来选择了哪些节点，又能补齐发布证据。验证时也要检查日志来自同一个版本。旧执行回执里同名的用例通过，只能说明那个版本的结果，不能回答新用例是否已经覆盖。需要验证的是本次改动的哪些行为，就用这些行为反推该出现在记录里的节点。

没有已知失败时，--lfnf none 会怎样？

这个新条件改变选择为空时的行为。缓存指南描述 none 会不执行测试，并写成成功退出。在另一份干净目录里用同一固定版本实际执行 --lf --lfnf none，输出显示收集一项、排除一项、选择零项，pytest 进程返回五。外层验证脚本确认这些值后返回零。9.0.2 的缓存选择实现清空选中集合，同版主程序对本路径中的零收集返回 NO_TESTS_COLLECTED。以实际运行版本和选择数验收，不能据文档这句措辞承诺所有版本都返回成功。
