assertLogs 已通过，为什么日志处理器一条都没收到？

用一份实际运行的 unittest 样本，区分 CPython 的临时捕获与常规日志处理器收到的记录。

正文

核心要点

  • assertLogs 验证临时捕获点。
  • 常规处理器是否收到消息需要独立测试。
  • 临时配置恢复与并发隔离有不同的验证范围。

在 CPython 的 unittest 中，assertLogs 可以断言一条消息已被捕获，同时原来的 handler 一条都没收到。测试上下文会临时替换目标 logger 的处理器。要验证常规处理器的交付，应让它在另一个测试窗口里接收记录。

设想导出模块既要告诉开发者一项任务已受理，又要让日志路由把记录交给后续处理器。测试用 assertLogs 看到了正确的消息和级别，就把“常规处理器已经收到”的要求一起判通过。这两项证据可能指向不同结果。第一项说明所选 logger 的消息进入了临时捕获，第二项需要观察实际配置的处理器。加宽字符串断言或在捕获上下文里找更多记录，都不会把一个观察点变成另一个。

捕获临时改了谁的配置

unittest 文档规定，这项断言检查指定 logger 或其子 logger 上符合级别的记录。进入上下文以后，至少一条匹配记录就能使断言通过。返回对象的 records 保存 LogRecord，output 保存格式化文字。选用这个入口时，可以读取记录的来源、级别和字段，明确到底是哪条消息满足了合同。Python 3.14 unittest 参考。

具体到 CPython 三点十四点十的源码，进入上下文时会先保存目标 logger 的 handlers、level 和 propagate。它安装捕获处理器，设定捕获级别并关闭目标 logger 的继续传播。离开时再恢复原有处理器、级别和传播状态。这里说的是该固定实现对选中 logger 的处理。它没有永久修改整个日志体系，也没有说明其他 Python 实现一定用相同方式实现公开合同。CPython v3.14.10 的日志断言实现。

让常规处理器与捕获记录各有一条消息

样本创建一个独立 logger 实例和内存处理器。不改全局根 logger，不启用线程，不连接任何日志服务。下面同一份标准库程序已在本地 CPython 3.11.15 运行；运行回执与引用的三点十四点十源码属于不同证据。代码的实际断言覆盖这一个样本。

import logging
import unittest

class MemoryHandler(logging.Handler):
    def __init__(self):
        super().__init__()
        self.events = []

    def emit(self, record):
        self.events.append(record.getMessage())

class TestLogDelivery(unittest.TestCase):
    def test_capture_and_normal_handler(self):
        audit = logging.Logger("fixture.audit", logging.WARNING)
        ordinary = MemoryHandler()
        audit.addHandler(ordinary)
        try:
            with self.assertLogs(audit, level="WARNING") as captured:
                audit.warning("export accepted")
                while_captured = tuple(ordinary.events)

            restored = audit.handlers == [ordinary]
            audit.warning("export complete")
            observed = {
                "during": while_captured,
                "capture": [event.getMessage() for event in captured.records],
                "restored": restored,
                "after": ordinary.events,
            }
            self.assertEqual(observed, {
                "during": (), "capture": ["export accepted"],
                "restored": True, "after": ["export complete"],
            })
            print(observed)
        finally:
            audit.removeHandler(ordinary)
            ordinary.close()

if __name__ == "__main__":
    unittest.main()

在捕获上下文里发送 export accepted。临时捕获应取得它，常规处理器的消息列表仍为空。离开后先记录原 handler 是否已恢复，再发送 export complete。此时常规处理器应只收到后者，前面的捕获结果保持原样。归档的程序通过了这组断言。例子用两个不同文本标记两个观察窗口，因此即使误把两段内容都累加进一份列表，也能发现读错了结果。

内存处理器只记下收到的格式化消息文本。真实日志交付还可能包括过滤、格式器、缓冲、进程之间转发和外部服务。要验收其中某一段，可以把独立的观察器放在实际目标处理器之后，核对发出的字段、去向和条数；若只断言捕获文字，测试就没有经过那段路径。这个样本也没有替业务定义哪些内容可以写进日志。

分别决定要验证的是事件还是交付

如果需求只说模块在拒绝输入时发出一条警告，可以用 assertLogs 核对那个明确命名的 logger、级别与记录字段。对于会改写字段的正式处理器，再给它独立的测试入口。先把预期写成可观察结果，例如目标处理器收到一条具有批次标识的记录，而不是一句含糊的“日志正常”。这样一次失败能显示是事件没产生、选错了 logger，还是路由和处理器改变了数据。

还可以给测试加入一个错误来源的同文案消息。如果只检查捕获列表里有没有 export accepted，另一个 logger 恰好发出相同文本也会让断言通过。真正关注的日志合同可以把来源名、级别和独立的业务标识一起作为条件。交付测试则应从捕获上下文外发出同样结构的事件，核对常规处理器收到了正确记录；两个检查不要共享会重写目标 logger 的上下文。站内的pytest 日志捕获层级解释了级别与传播的另一处边界。

在工程里若多个测试共用同一个命名 logger，还应考虑它的配置是否同时被其他调用读写。即使退出后恢复成功，中间的临时改变也可能影响另一条执行路径。教学样本用独立实例明确避开这个问题。若项目必须保留真实共享配置，测试时记录原设置和恢复结果，避免为了让断言通过而修改常规处理器的实际路由。它不能凭一次串行通过给并发日志路径背书。

若常规处理器最终要把记录转给另一个应用组件，可以为它单独安排一份接口探针。用含稳定批次号的记录触发一次正常路由，核对接收方只看到一份，并且批次号和处理状态仍完整。再让一个格式化器产生同样的可读文本但丢失批次号，检查结构化断言能报告这一失败。把这些探针放在实际配置路径上，不能在临时捕获环境中代替那段转发。对于异步交付，还要等实际消费点确认，而不是把发出调用返回的时点当成消费已经结束。归档的程序仅证明内存处理器收到一条消息，没有测试这些路径。

被测代码抛出异常时，常规 handler 会恢复吗？

在所引用的 CPython 实现里，上下文先恢复原设置，再让异常继续传播。可以另写一个未执行的对照，用 assertRaises 在外层期待 RuntimeError，内层进入 assertLogs 后直接抛出。退出后向同一个 logger 发送一条新消息，确认它到达原 handler。保留两份独立断言，一份检查异常没有被吞掉，一份检查配置已恢复。上面的实际运行只覆盖正常退出，没有执行这个异常变体。
