客户没有子记录，为什么 array_agg 给了 {NULL}？

用三个客户对照 PostgreSQL 左连接的补空行、真实空备注和空数组交付。

正文

核心要点

  • array_agg 可以收进左连接补出的空元素。
  • 按非空子键过滤能保留真实记录的空字段。
  • 空输入、空数组和含 NULL 的数组需要分别验收。

客户没有任何备注，PostgreSQL 的 array_agg 却给了一个含 NULL 的数组。左连接为这位客户补出一条右侧全空的行，数组聚合会收下它。想保留真实备注里的空字段，应按非空子键过滤补出来的行。

假设一个客户导出接口总要返回客户标识与备注列表。客户一没有记录，客户二有一条备注但暂未填文字，客户三有两条备注。只看文本列时，前两位都表现为空。业务若需要显示“没有备注”和“有一条待填写备注”，两种情况就必须有不同数组。关键是保留子记录是否存在的证据，不能让聚合只看一个允许为空的展示字段。

左连接已经给聚合准备了一行

PostgreSQL 的左连接保留没有匹配项的左侧行，并把右侧列补成 NULL。这里 array_agg 使用的是非数组参数的重载，会把输入值收进数组，NULL 也是一个元素。如果客户没有备注，聚合仍看到一条行，所以会得到带一个空元素的数组。真正的零输入才会让该聚合产生 SQL NULL。它与含一个空元素的数组，以及长度为零的数组，分别是三种状态。PostgreSQL 18 聚合函数。

可以在聚合调用里用 FILTER 只接纳满足条件的行。测试条件选备注编号，因为真实备注的编号必有值；补出的右侧行没有编号。这个过滤不会移除外层客户。如果把条件改成备注文本非空，客户二的真实备注也会消失。如果把子键非空放在整个查询的 WHERE，客户一在分组之前就会被淘汰。两种错误放置各自改变了不同的结果。PostgreSQL 18 聚合表达式。

给三位客户各自验收一行

下面是未执行的 PostgreSQL 18 教学查询。值列表给出全部数据，并约定真实备注编号非空。样本用编号决定聚合顺序，刻意让文本按编号得到 beta、alpha，以便发现下游误用字母顺序。数组最后只在合同明确需要时把 SQL NULL 换成空数组。

WITH customers(customer_id) AS (VALUES (1), (2), (3)),
     notes(note_id, owner_id, label) AS (
       VALUES (21, 2, NULL::text), (31, 3, 'beta'), (32, 3, 'alpha')
     ),
     rollup AS (
       SELECT customer_id,
              array_agg(label ORDER BY note_id) AS raw,
              array_agg(label ORDER BY note_id)
                FILTER (WHERE note_id IS NOT NULL) AS matched,
              count(note_id) AS actual_notes
       FROM customers LEFT JOIN notes ON customer_id = owner_id
       GROUP BY customer_id
     )
SELECT customer_id, raw, matched, actual_notes,
       coalesce(matched, ARRAY[]::text[]) AS response_array
FROM rollup
ORDER BY customer_id;

客户一的 raw 预期为 {NULL}，matched 为 SQL NULL，实际备注数零，response_array 为 {}。客户二的 raw 与 matched 都是 {NULL}，实际备注数一，response_array 也含一个 NULL。客户三两份聚合结果都是 {beta,alpha}，实际备注数二，交付数组保留这个顺序。先比较客户标识集合，再在每个客户之下比较长度、首个元素是否为空和数组顺序。只断言三位客户都返回了，无法发现客户一的输出形状错误。只断言客户二有一条，也不能替代其元素为空的验证。

在应用解码层，还要看驱动如何区分三个状态。可以分别保留 matched 的 SQL 空值、一个带空元素的数组，以及 response_array 的空数组，观察序列化到底输出什么。客户端若只检查字段能否被迭代，可能在解析时直接丢弃了空元素。对业务合同要求可编辑占位的情况，这会隐去一条真实备注。主样本只是 SQL 的独立预期，没有验证实际驱动或接口响应。

选择空值政策以前，先核对子记录身份

先从消费者的操作反推数组形状。如果只需要列出已填备注，按文本过滤是合理的，但要明确它不会展示仍待补充的记录。如果要按备注编号编辑，数组里仅有文本其实也不足以定位条目，可以按明确合同另行返回带编号的对象。这里的非空编号只在 SQL 里作为存在标记，没有假定消费者已经能拿它编辑。把空数组做成默认值时，也不要让另一个有意义的缺失状态意外变得和“已知没有备注”相同。

验证时可以用同一份客户输入分别运行两个错误对照。把 FILTER 的条件改成文本非空，预期客户二的真实空元素被删。把条件放进外层 WHERE，预期客户一整行消失。和正确查询对照以后，先定位错误是元素消失，还是客户行消失。站内的 LEFT JOIN 条件位置 解释匹配与后置过滤，这里让同一个判断落实到数组的输入与输出。

多租户查询还要检查子表的关系范围。若备注编号只在租户内唯一，就应按实际身份定义去关联，不能只拿样本中的一个数字套用到生产。验收可以加两位编号相同但分属不同租户的客户，再核对各自数组只包含所属备注。这个额外设计未执行，主例没有租户条件。

还可以给消费端单独保存三组约定。第一组在没有备注时返回空集合，页面不提供可编辑项。第二组保留编号为二十一的未填项，页面可以把它送进补录路径。第三组返回两条备注，验证页面的展示顺序仍与 SQL 的编号顺序一致。若 SQL 文本数组本身不带编号，第二组的编辑需要另取身份列，不能从数组位置推断数据库主键。前后端一起验收时，把页面是否显示空文案、是否存在编辑入口和返回项的身份分开判断。只看三张页面的文字相同，不能定位序列化或模型映射在哪一步丢了证据。这些消费端对照都是设计，未启动页面或服务。

再关联一张标签表后，同一备注出现两次怎么办？

假设客户二的备注二十一有两个标签。直接把两个标签都关联到备注输入，真实编号会出现两次，FILTER 会把两行都收下。先检查聚合前每个备注编号出现几次，再决定先在标签侧收成一行，或者先完成备注聚合后另算标签。给两个不同编号放同样的备注文字，验证修复没有用文本去重把它们误合并。这个反例独立于补空行，未执行。修复目标是每条符合合同的备注贡献一次，而不是让某次输出恰好只剩一条。
