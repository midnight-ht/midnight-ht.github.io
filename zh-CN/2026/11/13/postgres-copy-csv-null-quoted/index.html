CSV 看起来都是空白，为什么 PostgreSQL 导入后一个是 NULL？

用三行 PostgreSQL CSV 教学输入区分缺失、空字符串和单个空格，再核对组合 FORCE 选项的结果。

正文

核心要点

  • 默认 CSV COPY 用引号区分空字符串和 SQL NULL。
  • 行标识、空值谓词和文本长度能给出独立结果。
  • 更改标记或 FORCE 选项应重新验收每种输入。

PostgreSQL 按默认 CSV 规则执行 COPY FROM 时，未加引号的空字段读成 SQL NULL，带双引号的空字段读成空字符串。两项在预览里都可能显示成空白。要查差别，回到实际 CSV 字节，再用查询区分字段是否为空值以及文本有多长。

设想工单导入表里有个备注字段。缺少备注表示来源没有提供这一项，空字符串表示来源有意填写为空。预览把两种行都画成一格空白，操作人员只看到导入了两条，误以为它们的存储值也一样。导入协议若依赖这个差别，就要明确生产方怎样写出每种字段，并核对数据库读回来的两个状态。

空白由引号和 NULL 标记共同决定

PostgreSQL 18 的 COPY 文档把默认 CSV NULL 标记设为未加引号的空字符串。带引号的空内容属于非 NULL 文本。这里讨论的是普通 CSV 模式的默认选项。更改 NULL 标记、FORCE_NULL 或 FORCE_NOT_NULL 会改变解释。一般 CSV 并没有一份统一的空值约定，不能从电子表格显示、文件扩展名或其他导入器推断这一份文件的语义。PostgreSQL 18 COPY 的 CSV 格式。

对代码评审而言，引号在输入里承担实际业务区别。处理 CSV 的库如果在读入时把两种字段都变成同一个值，再把它们重新写入，原始区别就可能丢失。排查时先保留一份小的输入样本和生成方法，再检查字节里有没有那对引号。随后在数据库中按行标识核对结果。只记录复制完成的行数，会让两份含义不同的文件得到相同的通过结果。

三行输入分别说明什么

以下是未执行的 psql 教学输入。在自有测试库打开新的会话，把整段交给 psql。命令使用临时表和 COPY FROM STDIN。数据行没有表头，第三行的引号内正好有一个普通空格。反斜杠加点单独成行，结束本次 psql 的内联输入。这个输入方式不能直接作为通用数据库驱动的一条查询执行。

CREATE TEMP TABLE copy_notes (
    id int PRIMARY KEY,
    note text
);

COPY copy_notes (id, note) FROM STDIN WITH (FORMAT csv);
1,
2,""
3," "
\.

SELECT id, note IS NULL AS missing, length(note) AS chars
FROM copy_notes
ORDER BY id;

独立预期如下。第一行的 missing 为真，chars 是 SQL NULL。第二行的 missing 为假，chars 为零。第三行的 missing 也为假，chars 为一。第一和第二行的差别不是显示宽度，第三行专门检测预览或清洗程序有没有把单个空格悄悄当成空字符串。输入约定如果允许修剪空格，应另测明确经过修剪的那条路径，再决定是保留空文本还是转成缺失。

核对时可以让测试直接断言布尔值与长度，而不是从终端表格的空格反推数据。若导入之后还有默认值填补或数据归一化，在那一步以前先留原始结果。比如下游把所有 NULL 显示为“未填”，同时把空文本显示为空白，那么显示行为是新的业务约定，不能替代 COPY 输入解析验证。本文没有启动 PostgreSQL 或实际导入，也没有验证页面的状态。

自定义标记之前先写清上游合同

若输入系统无法保留引号差异，可以约定一个显式的缺值标记。先写清原始标记怎样表达缺失，再检查用户需要提交同样的普通文本时怎样保留它。用一行未加引号的标记、一行带引号的相同文字做对照。按默认的 CSV 引号规则配合自定义 NULL 标记时，这两条输入可以表达不同结果。准备样本时最好保留上游实际生成的文件，避免手写的教学文件能区分两种值，但真实导出总把它们写成一样。

例如，生产方可以约定未加引号的 MISSING 代表没有值，而带引号的 MISSING 代表用户真的输入了这个单词。若它只能发固定文本，完全不能控制这个值是否加引号，就要另选不会与自由文本冲突的表示，或把缺失状态放到独立字段里。不能依赖数据库从相同输入字节猜出两种意图。另设一条空字符串作为对照，检查采用新标记后，空字符串仍然是允许的文本。如果生成器无法产出三份独立输入，应让生产者和导入者先共同确认字段协议。这个方案没有实施，也没有覆盖生产者对其他需要引用字符的处理。

文件交付经过重新保存时，也要检查是否更换了生产方式。某些工具可能去掉空内容的引号，或先把空字段合并，再输出一份合法 CSV。可以用同一三行样本经过真实生产器和交换环节，再比较数据库中的三个标志。若第一和第二行变得一样，先确认哪一步改了字节。不要单看新的 CSV 是否能被导入。站内的 COPY 客户端与服务器文件路径 说明文件由谁读取，本篇只讨论读到这些字节以后怎样解释字段。

错误报告也应保留独立证据。对每个失败行标识记录预期为空值还是空文本、实际字段长度、采用的导入配置和样本文件摘要。如此可以区分来源把标记写错、导入用了另一组选项，或者后续程序把两种值合并了。对空格政策还有要求时，让第三行一直留在验收里。主示例没有验证真实驱动的 COPY 接口，也不代替业务数据保留规则。

同一列同时指定两个 FORCE 选项，两个空字段会怎样？

PostgreSQL 18 允许在 CSV COPY FROM 的同一列同时指定 FORCE_NULL 与 FORCE_NOT_NULL。保持默认空标记，带引号的空字段会变成 SQL NULL，未加引号的空字段则成为空字符串。可以在另一份独立临时表上重复前两条输入，在 WITH 选项中同时指定 FORCE_NULL (note) 和 FORCE_NOT_NULL (note)，核对第一条的 missing 为假且长度零，第二条的 missing 为真且长度空。该变体未执行。不要在已经写入原示例的表里直接追加相同主键，否则主键冲突会掩盖要观察的解析差别。
