基础层改了，Docker 的制品复制层还能复用吗？

固定制品输入，比较 Docker 普通复制和 COPY --link 对前置层变化的依赖。

正文

核心要点

  • 独立复制层减少对前置状态的依赖。
  • 观察缓存是否命中之外还要检查最终文件。
  • 先确认目标路径和复制需要的前置文件系统状态。

编译制品相同，更新运行时仍可能让普通复制步骤失去原有缓存。支持 COPY --link 的构建器可以把制品复制做成独立层，再和变化后的前置镜像状态组合。

维护构建的同事只换了一项运行时设置，应用压缩包没有改，却发现复制步骤重新处理了同一份内容。他希望保留已构建的制品层，同时能确认最终镜像包含新的运行时。这里有两个结果需要独立检查：构建器是否用了已有层，以及镜像能不能读到应该出现的文件。缓存日志可以回答前一个问题，最终镜像文件内容才回答后一个。

把复制结果从前置状态中拆开

Dockerfile 的 COPY --link 文档把这个选项描述为先把源文件复制进空的目标目录形成一层，再将该层叠到先前状态之上。普通复制依赖先前状态，前面的命令发生变化时，已有复制结果可能失效。独立复制减少这份依赖，构建器若有适用的缓存，就能尝试复用相同制品层。这里说的是前置状态变化没有同样的直接失效作用，缓存是否保留、是否被当前构建器看见，需要从实际构建取证。

这类区别可以出现在多阶段构建。构建阶段已经产出应用，最终阶段另设运行时文件，再从前面取制品。若只换运行时，制品仍相同，复用它符合输入合同。若应用本身已经重新打包，前面的独立性不会让旧制品仍可冒充新制品。可以为两种改动分别建立对照，避免把不同缓存输入混在同一次尝试中。站内包索引与安装缓存讨论的是同一条安装命令何时重跑，这里关注复制结果与前置状态的依赖。

固定制品，改变一个前置文件

下面是完整教学 Dockerfile，未运行构建。它要求支持该选项的 BuildKit 和 Dockerfile 前端。保存到一个空上下文，再建一个内容为 artifact-v1 加换行的 payload.txt。两个最终阶段共享前置阶段，但复制语句不同。例子故意使用普通目录，输出位置一开始不存在。若基础镜像标签在两轮间移动，也会带入额外变化；可提前固定本地已解析的基础镜像摘要，或记录两轮解析结果并确认相同。

# syntax=docker/dockerfile:1
FROM alpine:3.22 AS earlier
ARG BASE_MARK
RUN printf '%s\n' "$BASE_MARK" > /runtime-mark

FROM earlier AS regular
COPY payload.txt /opt/demo/payload.txt

FROM earlier AS linked
COPY --link payload.txt /opt/demo/payload.txt

在同一构建器、同一上下文和同一平台下，分别构建两个目标。先把 BASE_MARK 设为 old，记录构建步骤；然后改为 new，保留原有缓存，再跑同样的两个目标。完整命令如下，需在独立教学环境使用这些镜像名。

set -eu
for mark in old new; do
  for target in regular linked; do
    docker build --progress=plain --target "$target" \
      --build-arg "BASE_MARK=$mark" -t "copy-lab:$target-$mark" .
  done
done

循环遇到失败就退出。先保留失败目标的输出，再继续解释缓存，避免后一项成功掩盖某份镜像没构建。

检查两份 new 镜像时，读取 /runtime-mark 和 /opt/demo/payload.txt。前者都应为 new，后者都应与上下文文件相同。可以在样例镜像内用 cat 读取，也可在自己的镜像验收方式中比较文件摘要。保留四次构建的输出和最终镜像标识，才能把某次显示已缓存的步骤对应到某份镜像。若只比较两个最终镜像的摘要，很可能看到完整镜像因前置内容更新而发生变化，无法凭此判断制品层有没有复用。

预期的构建对照是普通复制受前置变化影响，独立复制在可用缓存中仍有可复用的结果。未得到缓存命中时，先确认构建是否落在同一实例、平台和输入上，并核对该步骤的日志。仅凭使用了选项就承诺每次命中不准确；两轮能输出一样的制品，也可能只是两次都重新复制。若环境已有其他构建留下的缓存，也要在记录里注明来源，免得把别处取得的结果误记成第一轮和第二轮之间的复用。

再做一个负对照。保持运行时标记为 new，把制品内容换成 artifact-v2，重复两个目标。预期最终文件都变成 v2，即使上一步运行时层可以复用。这一格检验的是制品输入变化有没有传到最终镜像。若只看到日志说运行时已缓存，不应该把这行信息外推到制品身份。更完整的验收可以同时读取两份旧镜像，确认它们保留 old 标记和 v1 制品，再与新版本对照。四份数据给维护者一个可核对的映射，避免镜像标签被覆盖以后找不回本来要比较的对象。

在生产配置里只迁移能够独立的复制

若目标只是将已构建文件安装到明确的普通目录，独立复制能表达制品层的边界。迁移前先看是否还有后续命令需要从该目录读取配置、改权限或验证安装结果。这些步骤仍应保留，并在新的镜像上用目标用户运行适当的读取检查。复制层能复用不代表容器能启动，也不证明镜像仓库接收了预期版本。对制品路径和读取权限的验收，应该来自最终目标镜像。

有的团队会用不同构建节点生产分支镜像。此时可以先记录当前构建器如何取得前一次的缓存，再决定要不要改变跨节点缓存策略。没有取得旧数据时，复用条件不成立。为了判断这个选项是否有收益，可以把前置变化与制品变化分别记录，而不是拿一次构建总耗时给所有环境下结论。样例没有计时、没有导入远程缓存，也没有观察仓库重组镜像的行为。

目标目录经过前一层的符号链接，还会跟随吗？

COPY --link 不会读取先前状态来跟随目标路径上的符号链接。按手册，该模式创建的目标路径只由目录组成。假设基础镜像通过符号链接把 /opt/current 指向实际版本目录，把制品复制到前者时需要先判断合同要求写入哪里。若要沿用该链接，保留普通复制；若要独立复制，选择明确的物理目录并检查最终读取位置。主例使用普通路径，没有替这个新条件做验证。
