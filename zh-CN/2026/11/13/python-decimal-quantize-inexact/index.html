为什么 Inexact 拒绝 1.234，却接受 1.230？

用三个实际运行的 Python Decimal 输入核对量化后的值、指数、Rounded 与 Inexact，区分数值校验和原始写法。

正文

核心要点

  • Rounded 可以记录只丢弃零的操作。
  • Inexact 可阻止数值变化。
  • 限制原始写法时，应在文本仍存在时验收。

Python 把 Decimal('1.230') 和 Decimal('1.234') 量化到两位时，都需要丢掉最后一位。第一个只丢掉零，数值没有改变。因此 Inexact 陷阱只拒绝第二个输入。要求原始输入至多两位小数的接口，还需要单独检查表示。

举个库存导入的假设场景。外部设备提交测量字符串，后台按百分之一单位保存。工程师打开 Inexact 陷阱，想阻止导入时悄悄改变读数。之后，他用三个小数位的输入验收，发现带尾零的读数仍可通过。如果字段合同关心可保存的数值，这正符合需求；如果接收方明确只允许至多两位小数的字面表示，尾零也需要走拒绝路径。两种合同可能使用同一个输出格式，验收输入却不同。

先决定拒绝哪一种变化

Python 的 quantize 将结果调整到第二个操作数的指数。对有限数使用 0.01 时，成功结果的指数为负二。Rounded 在丢弃数字时置位，即使丢弃的全是零。Inexact 则标识舍入丢弃了非零数字。对已经是两位的 1.23，这两个信号都不出现。对 1.230，Rounded 出现，Inexact 不出现；对 1.234，两个信号都出现。默认的比较运算无法表达这份差异，因为第一个和第二个的数值相等。Python Decimal 的 quantize 与信号。

可以用一个本地上下文观察信号，也可以把 Inexact 配置成陷阱以中断会改变数值的量化。在读取 flags 前，要清除上一轮留下的记录；一次量化的信号并不会因为下一次没有舍入而自动消失。示例把精度和舍入模式显式写出，先观察结果、指数与信号，再打开陷阱。它不会把当前运行环境的默认舍入政策当作应用协议。

给三个输入各自的预期

以下完整程序的输入是十进制文本。程序在 Python 3.11.15 本地运行，归档记录包含实际输出与精确代码哈希。它不接触文件导入服务、数据库或其他解析器。

from decimal import Decimal, Inexact, Rounded, ROUND_HALF_EVEN, localcontext

cent = Decimal("0.01")
cases = [
    ("1.23", "1.23", False, False),
    ("1.230", "1.23", True, False),
    ("1.234", "1.23", True, True),
]
with localcontext() as ctx:
    ctx.prec = 12
    ctx.rounding = ROUND_HALF_EVEN
    ctx.traps[Inexact] = False
    ctx.traps[Rounded] = False
    for text, rendered, rounded, inexact in cases:
        ctx.clear_flags()
        actual = Decimal(text).quantize(cent)
        observed = (str(actual), ctx.flags[Rounded], ctx.flags[Inexact])
        assert observed == (rendered, rounded, inexact), (text, observed)
        assert actual.as_tuple().exponent == -2
        print(text, observed, actual.as_tuple().exponent)

    ctx.traps[Inexact] = True
    ctx.clear_flags()
    assert Decimal("1.230").quantize(cent) == Decimal("1.23")
    try:
        Decimal("1.234").quantize(cent)
    except Inexact:
        print("1.234 trapped")
    else:
        raise AssertionError("expected Inexact for 1.234")

三组都得到可显示为 1.23 的值，指数都是负二。程序逐条检查 Rounded、Inexact 与这一指数，再打开 Inexact 陷阱。第二个输入仍成功，第三个抛出预期异常。这里选择的半偶舍入在第三个输入也会给出 1.23，因为丢弃的数字是四；示例没有验证边界值恰好落在中间时的选择。如果团队同时更改舍入政策，就为边界值另外写预期，不能用这三个值给新策略背书。

代码里的断言适用于无优化运行的教学样本。业务入口如果要拒绝数值变化，需要显式处理陷阱触发以及不允许的输入格式。若报告需要知道哪一条读数不合规，保留记录标识和相应的错误分类。不要在同一异常分支里混合无法解析、精度不够和确实丢弃非零数字的情况。三者要求的后续处理可能分别是修复导入格式、检查范围合同或要求上游重发读数。

词法要求要在保留原表示时验证

假设校验从“可精确保存”改成“用户只能写至多两位小数，并且不允许指数记法”。单看 Decimal 的最终指数也未必能判断原文用了什么写法。可以给新的解析入口独立准备 1.23、1.230 和 123E-2。第一条符合样本格式；后两条是否允许由明确写出的词法合同决定。即使后两者的数值能无损落在百分之一网格，也不能据此认可两种原始写法。数值许可与文本许可分开给预期，测试错误时才知道该改哪一层。

对已有代码，也要查看量化是在解析入口调用，还是在读取一段已经格式化过的文本后才调用。后者只能观察当前值里的尾零，无法反推原始字节。一个导入测试应记录解析前的令牌和返回的错误类别。面向业务界面的测试则核对返回格式、测量值和来源标识。接收端如果只需要已经规范化的数值，可以选择允许多余的零，但应仍拒绝改变数值的输入。本站的Decimal 浮点构造边界讨论更早的输入类型问题，本例全程使用十进制字符串。

还可以单独测试同一个上下文中先量化 1.234，再量化已经符合格式的 1.23。如果两次中间忘了清 flags，第二次读到的 Inexact 仍可能来自第一次。在真实导入链里，不应把一个历史标志直接写成后一条记录的错误。把观测窗口绑定到单次运算，或把拒绝策略交给相应陷阱，每条记录都能得到有独立含义的结果。这个重复调用对照属于扩展，主例只运行了逐次清理的版本。

遇到来源会先格式化的设备，还可以给同一读数写两份输入回执。设备一份保留尾零，另一份在传输前去掉尾零。如果服务收到的文本已经相同，即使两边都通过量化，也只能证明传入值可以无损保存，不能证明两个设备按同一词法输出。想验收设备格式，应在转换前的读取边界留下受控样本，并记录使用的是哪一版格式配置。这个对照不会要求数据库保留所有原字节；保留多长时间应由测试需求或产品协议决定。

输入已经是两位，为什么仍可能抛 InvalidOperation？

把上下文 precision 设为二，再量化 Decimal('1.23') 到 0.01，预期会遇到 InvalidOperation，前提是该陷阱保持启用。结果系数需要容纳三个数字。这个限制和尾数是否发生数值变化无关。设计校验时可以给允许的最大整数部分留出足够系数位，或者将范围错误与 Inexact 分开上报。这个小精度变体未运行；主程序的精度十二和三个短输入没有覆盖超出系数容量的情况。
