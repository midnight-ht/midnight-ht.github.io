都没有正文，HTTP 205 为什么要恢复录入视图？

以非空默认分类对照 204、205 和失败，说明重复录入界面何时恢复原始视图。

正文

核心要点

  • 205 表示服务器希望恢复触发请求的录入视图。
  • 恢复原始值可能保留非空默认字段。
  • 应用需要为失败或稍后出现的新编辑选择处理方式。

重复录入界面的分类默认是“图书”，用户本轮改成“文具”。提交后如果服务器返回 HTTP 205，并且应用按该状态恢复录入视图，分类应回到原来的“图书”。空正文只说明响应没有附带内容；恢复原始状态可能把一个非空默认值重新带回来。

RFC 9110 的 205 定义表示服务器已经完成该请求，希望用户代理将触发请求的文档视图恢复到从源站收到时的状态。它为连续录入表单、记事区域或画布提供一个明确的响应意图，服务器不得在这份响应中生成内容。客户端不应期待服务端用响应正文传回要清空的字段表。原始状态是什么，需要由录入界面和它所属的文档决定。

204 同样没有内容，但没有这个专门的恢复含义。站内的204 响应解析边界介绍了为何不能统一解析 JSON。本篇把解析问题放在一旁，只比较已收到成功响应以后，视图究竟是保留本次值还是恢复原始状态。在别的产品里，204 后也可能根据自有合同更新视图；样本里的保留分支是有意选择，并非状态码禁止修改页面。

把原始值、当前值和保存结果分开

设想工作人员不断录入教学物品。表单加载时默认分类为图书，说明为空；当前记录将分类改成文具、说明改成 pen。应用把这份当前值提交。在示例合同中，204 保留已经输入的内容并报告保存成功，205 报告成功并恢复为默认分类与空说明，500 保留值并将本次保存记为未确认。失败处理不推断服务端绝对没有副作用，后续是否查询应由实际接口决定。

以下是完整的本地 Node 状态转换。它使用手写的三个状态作为输入，不运行浏览器、发送 HTTP 或写入持久化。独立预期从业务状态表给出：只有第二种恢复视图；该视图的分类不是空字符串。普通对象用来表达组件的本地模型，不能被读成某个框架的表单自动行为。

import { deepEqual, notDeepEqual } from 'node:assert/strict';

const original = { category: 'Books', note: '' };
const draft = { category: 'Stationery', note: 'pen' };

function afterSave(status, values) {
  if (status === 205) return { outcome: 'saved', values: { ...original } };
  if (status === 204) return { outcome: 'saved', values };
  return { outcome: 'unconfirmed', values };
}
const outcomes = [204, 205, 500].map(status => afterSave(status, { ...draft }));
deepEqual(outcomes, [
  { outcome: 'saved', values: { category: 'Stationery', note: 'pen' } },
  { outcome: 'saved', values: { category: 'Books', note: '' } },
  { outcome: 'unconfirmed', values: { category: 'Stationery', note: 'pen' } },
]);
notDeepEqual(outcomes[1], {
  outcome: 'saved', values: { category: '', note: '' },
});
console.log(JSON.stringify(outcomes));

负例把两个字段都清空。若测试只检查备注为空，就会误把这个分支判对，因为恢复成功与全部清空都会让备注为空。对照必须包含有默认值的字段、没有默认值的字段和失败状态。还可以在真实界面上检查打开下一轮时应该保留的独立状态，例如已经保存的记录编号出现在回执区域，而本轮草稿恢复成可继续录入的默认值。保存回执和录入控件是不同区域，重置其中之一并不要求删除另一个。

如果应用选择调用原生表单 reset，还应核对它的实际作用范围。HTML 的表单重置算法会处理所属的可重置控件，重置事件可以取消。组件若在外部管理了受控字段值、校验提示或未同步的草稿，仍需让这些状态与恢复动作一致。只从页面截图看字段为空，无法确认受控值不会在下一次渲染中回写。验证时应读取真实控件值，也读取下次提交所用的模型值。

重置的边界应由录入任务决定

把触发请求的视图当作恢复范围有助于厘清哪些状态要留下。假设连续录入界面旁边还有仓库筛选列表，表单内默认分类来自该筛选。在该合同中，可以保留列表筛选并恢复它对应的表单默认值。若原始视图由另一个数据版本建立，而用户已切换仓库，应先确认返回的响应还属于当前录入对象，避免旧默认值跨界写进新表单。这是应用对视图身份的约定，不是 HTTP 状态码本身提供对象跟踪。

验收可从同一初始值分别走三个状态分支，再把三份记录和实际的请求结果关联起来。验证所需证据包括当前视图标识、恢复前后字段值、可见回执和下一次提交的内容。只看界面清空会漏掉默认值错误；只看保存提示会漏掉录入无法继续。若页面还有自动保存入口，另检查两种操作是否共用同一个恢复合同，不要让某次后台保存意外打断当前输入。

录入流程还要检查恢复后第一步能否立即继续。假设用户保存后仍在提交按钮上，恢复默认值之后可以按已定义的键盘顺序继续输入下一条。若应用决定把焦点移回第一字段，应同时保留可感知的保存回执，防止用户只看到原表单而以为本轮内容消失。这个选择需要在产品场景中核对，状态码并未规定具体焦点位置。另一项检查是确认旧字段的错误提示何时撤销。如果分类已经恢复为默认值，页面仍显示上一轮文具输入的错误，下一次提交会让状态难以解释。应把恢复后的字段值、错误关联和下一次编辑动作写进同一份验收，而不把所有视图状态简化为对象有几个键。

205 晚到时，用户已经输入了下一条，是否还要清掉？

应用应先核对响应对应的是哪一轮草稿。假设提交时草稿版本为七，等待期间用户继续编辑，当前版本变为八。旧响应可以确认版本七的提交。若产品允许等待期间编辑，恢复动作只应作用于仍属于版本七的录入视图，不能把八当成刚刚提交的内容。另一种明确设计是请求期间暂时阻止编辑，恢复之后才允许进入下一轮。主例没有并行编辑，这个新增条件需要独立验证较晚响应和新输入的归属。
