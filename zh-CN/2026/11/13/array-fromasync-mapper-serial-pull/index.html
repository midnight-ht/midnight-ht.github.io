Array.fromAsync 在等待 mapper 时，会先读取下一项吗？

用可控放行点观察异步迭代器的下一次读取，区分结果保序、映射串行与已启动的工作。

正文

核心要点

  • 映射尚未完成时不会拉取下一项。
  • 最终结果顺序不能证明任务何时启动。
  • 已经启动的工作不受收集方式追溯控制。

异步来源的第一项 A 已进入 mapper，却卡在一个尚未放行的等待点。此时下一次读取有没有开始？fromAsync 会等当前 mapper 完成，再拉取下一项。最后的数组保持 A、B 顺序，单看这个顺序并不能证明工作是何时开始的。

先看下一次读取，而不是结果数组

ECMAScript 对 fromAsync 的定义区分异步可迭代对象、同步可迭代对象和类似数组的对象。这里先只看第一个分支。方法调用当前迭代器的 next，等待它给出迭代结果，从结果中取得 value。若传入 mapper，方法调用它并等待返回值，然后将转换结果写入数组，再进入下一轮。读下一条之前，有一个由当前转换结果决定的等待点。

设想一份小型目录的读取适配器。每次 next 只产生一条记录，mapper 将这一项转换为可供列表显示的文本。若适配器把自己的读取也做成惰性的，第二次 next 尚未发生，就不会由本次遍历开始第二条读取。这个判断只描述由迭代动作触发的工作。来源可以自己预取，也可以由别的调用者提前启动任务；收集函数并不能把已经开始的操作重新放回队列。

这样的先后关系需要单独测试。结果中的 A 在 B 前面，既可能因为 B 等 A 完成后才启动，也可能因为两项都先启动、收集者最终按输入位置组合。依赖顺序的项目应记录调用与完成点。只比最后数组，可能把两个不同的调度方案都判为符合合同。

用一道显式门固定观察时点

以下是一个独立的本地 Node 示例。异步迭代器只给出 A 和 B，随后结束。A 的 mapper 宣布自己已开始，再等测试主动放行。测试收到这个开始信号后立即核对记录，避免通过睡眠若干毫秒猜测 mapper 是否已进入。值都是教学字符串，没有访问目录服务。

import { deepEqual } from 'node:assert/strict';

const gate = () => Promise.withResolvers();
const { promise: waiting, resolve: release } = gate();
const { promise: began, resolve: markStarted } = gate();
const order = [];
const record = item => order.push(item);
const values = ['A', 'B'];
let index = 0;
const input = {
  [Symbol.asyncIterator]() { return this; },
  async next() {
    const value = values[index++];
    record(value ? 'pull ' + value : 'done');
    return { value, done: value === undefined };
  },
};
const result = Array.fromAsync(input, async value => {
  record('start ' + value);
  if (value === 'A') {
    markStarted();
    await waiting;
  }
  record('finish ' + value);
  return value.toLowerCase();
});
await began;
deepEqual(order.slice(), ['pull A', 'start A']);
release();
deepEqual(await result, ['a', 'b']);
deepEqual(order, [
  'pull A', 'start A', 'finish A', 'pull B', 'start B', 'finish B', 'done',
]);

const { promise: parallelGate, resolve: releaseParallel } = gate();
const launched = [];
const tasks = values.map(async value => {
  launched.push(value);
  if (value === 'A') await parallelGate;
  return value.toLowerCase();
});
deepEqual(launched, ['A', 'B']);
releaseParallel();
deepEqual(await Promise.all(tasks), ['a', 'b']);
console.log(JSON.stringify({ order, launched }));

在打开门之前，预期只有 A 的读取和 mapper 开始。打开后，A 先结束，才会出现 B 的读取与转换，最后还有一次表示完成的 next。断言所用的完整序列来自已知输入和指定等待点，不由日志反推出预期。另一组先对普通数组调用 map 创建两个承诺，随后才等待整体结果；A 依然没有放行时，B 已在调用过程中开始。两组最后都得到小写的 a、b，所以这是一个能排除错误解释的对照。

代码还特意让生产者只记录 next 的调用，而不只记录 mapper。假如生产者已经读取第二项，只把 B 的转换延到第一项结束，两个 mapper 的起止日志看起来仍会串行，实际来源已经预读。这对可能产生网络或存储操作的适配器有区别。检查生产者日志能确认第二项还没有交给收集器，至于来源自己的后台预取，需要在来源内部另作记录。

什么时候值得用这个顺序

如果每次转换依赖上一次的提交结果，先完成再读取下一项能让依赖清楚地落在代码中。若单项工作互不依赖且成本很高，也可能选择限定并发，明确什么时候开始下一项，以及排序依据是什么。示例用两项任务展示并发启动，不能据此把没有上限的任务批量发出。对于无限或很大的来源，也要考虑逐项消费和提前停止；最终必须物化成数组的接口不适合没有结束条件的输入。

还可以在验收时将两个顺序要求分开写：一个是结果按原始编号排列，一个是在上一项转换未完成前不得读取下一项。若需求只关心前者，第二条不该意外变成限制；若来源需要严格控制拉取，它才是一条不可省略的断言。本站异步 forEach 的完成问题说明外层何时等待回调，本篇增加的是生产者和转换函数之间的具体时序。

如果生产者本身给每次读取分配编号，可以在 mapper 开始时记录同一个编号，而不是用日志先后猜测对应关系。比如两个记录的展示文字恰好相同，只打印文字无法看出哪个转换结果对应哪次拉取。应给测试输入保留不同编号，比较每个编号从拉取到转换完成的路径。这里的固定字符串已经不同，真实重复内容的验收则需补这层身份。计时数字可以在之后用于性能观察，不能代替这份因果顺序。

失败时也应写出独立的可观察条件。例如固定让 A 的转换拒绝，在这一有限迭代例里检查收集 Promise 的拒绝，并确认 B 未被由该循环拉取。是否有来源资源需要关闭，还要根据迭代器协议和应用持有的资源确定。已经由独立任务启动的操作，不能从收集者的拒绝推断它也被撤销。以上是拟议的失败验收，和上方固定成功路径的断言不是同一份运行结果。

自定义 async iterator 的 value 本身是 Promise，会自动解包吗？

要看输入路径和有没有 mapper。直接的异步迭代分支等待 next 返回的迭代结果；无 mapper 时，它从结果对象取出 value 并存入数组，并不会为那个字段再加一层等待。同步数组要先经同步迭代器的异步适配步骤，其中会采用 value。给直接异步来源提供一个返回原值的 mapper，也会走等待 mapper 返回结果的步骤。

import { deepEqual, strictEqual } from 'node:assert/strict';

const inner = Promise.resolve('A');
const { fromAsync } = Array;
const collect = fromAsync.bind(Array);
function direct() {
  let used = false;
  return {
    [Symbol.asyncIterator]() { return this; },
    async next() {
      if (used) return { done: true };
      used = true;
      return { value: inner, done: false };
    },
  };
}

const [carried] = await collect(direct());
const [adopted] = await collect([inner]);
const [mapped] = await collect(direct(), value => value);
strictEqual(carried, inner);
deepEqual([adopted, mapped], ['A', 'A']);
console.log('direct value retained; sync wrapper and mapper awaited');

这段对照改变的是每项值的形状，前面的门控用例只用普通字符串。检查时分别比较对象身份和最终字符值。外层已经拿到数组，可以与数组元素仍是 Promise 同时成立；若调用接口明确要字符串，应使转换或验证覆盖这个差异。
