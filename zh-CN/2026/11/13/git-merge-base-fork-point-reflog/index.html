上游重写之后，Git 为什么多算了一笔主题提交？

用一份隔离提交图和两条本地跟踪引用，核对 Git 上游改写后的重放范围。

正文

核心要点

  • 普通共同祖先和历史分叉点可能落在不同提交。
  • 用完整提交列表核对将要重放的范围。
  • 本地没有旧尖端记录时要单独确认切点。

上游把旧提交移出了分支，普通共同祖先仍给出有效答案，却会让待重放列表多一笔。在这种形状下，Git 的 merge-base --fork-point 可以借本地跟踪引用的旧尖端找到更贴近原开发起点的边界。

你从当时的上游尖端开始改一个主题，准备在新的上游上重放。查看范围时，除了自己的改动，还看见一笔上游曾经带来、后来主动撤回的改动。这条提交现在的确只从主题一侧可达。问题出在用“当前两侧都能走到哪里”替代了“我当时从哪里开始”。改命令前，先问发布者撤回的旧改动是否还应该出现。

从同一条图读出两种答案

设共有的基础提交为 R。旧上游在它之后有 U，主题分支从 U 再写下 T。上游随后回到 R，换成另一笔 V。此时普通共同祖先是 R，用 R 到主题尖端的范围会得到 U 和 T。若本地的上游跟踪引用确实曾指向 U，引用日志就保存了一个图上没有标签的线索。分叉点模式把该引用的旧尖端也纳入计算，在这张图上得到 U，于是范围只剩 T。 Git merge-base 手册的分叉点说明

两个答案各自回答了不同的问题。若想找两个当前尖端之间的合并基点，R 正是这张图上的共同祖先。若要挑出 U 以后自己在主题上做的工作，则应该从 U 截断。本例没有执行重放，只检查传给后续步骤的提交集合。即使切点正确，新上游内容也可能让补丁发生冲突，应用的结果还需单独验收。

两条跟踪引用指向同一个提交

下方脚本在一个临时仓库创建四个提交。提交都使用空树，例子只观察图和引用日志。它在 Apple Git 2.50.1 实际运行，普通范围为 U、T，分叉点范围为 T，没有旧尖端记录的引用退出为一且没有输出。整个脚本退出为零。没有访问远程仓库，也没有改动已有分支。

set -eu
case_dir=$(mktemp -d)
trap 'rm -rf "$case_dir"' EXIT
cd "$case_dir"
git init -q -b base
git config user.email fixture@example.invalid
git config user.name Fixture
git config commit.gpgSign false
git commit -q --allow-empty -m R
r=$(git rev-parse HEAD)
git commit -q --allow-empty -m U
u=$(git rev-parse HEAD)
git update-ref --create-reflog refs/remotes/origin/main "$u"
git switch -q -c topic
git commit -q --allow-empty -m T
git switch -q -c rebuilt "$r"
git commit -q --allow-empty -m V
v=$(git rev-parse HEAD)
git update-ref refs/remotes/origin/main "$v"
git update-ref --create-reflog refs/remotes/other/main "$v"

graph_base=$(git merge-base origin/main topic)
fork=$(git merge-base --fork-point origin/main topic)
test "$graph_base" = "$r"
test "$fork" = "$u"
ordinary=$(git log --reverse --format=%s "$graph_base..topic")
selected=$(git log --reverse --format=%s "$fork..topic")
test "$ordinary" = "$(printf 'U\nT')"
test "$selected" = T
set +e
missing=$(git merge-base --fork-point other/main topic)
status=$?
set -e
test "$status" -eq 1
test -z "$missing"
printf 'ordinary:\n%s\nfork-point:\n%s\nmissing: exit=%s, bytes=%s\n' \
  "$ordinary" "$selected" "$status" "${#missing}"

脚本分别核对了计算出来的对象身份和范围内容。实际使用时还应输出完整提交 ID，因为两个主题提交可能有同样的标题。先保存当时解析到的主题尖端和当前跟踪尖端，再按从旧到新的次序列出候选提交。观察是哪一笔变成了额外条目，以及那一笔是否来自上游。只有看到整个候选范围，才容易发现范围里同时混有一笔已经确认应撤回的改动。

负例中的第二条引用也指向 V，仓库里的提交和主题尖端都没有变。它从未指向 U，因此没有这条旧尖端记录。这个设置比只检查图更能说明为何一位同事找到分叉点，另一位却没有。实际排查时可查看 git reflog show origin/main 并核对具体引用名。历史可能已过期，或这份仓库根本没见过曾经的尖端。返回失败时要保留诊断，避免把空变量交给接下来的命令，也不要悄悄把普通共同祖先当成等价的备用值。

决定需要保存哪一种边界

在团队能追到原起点的场景中，可以使用经确认的原始完整提交 ID。证据可能来自分支创建记录、发布说明里绑定的上游对象，或者团队保存的构建输入。若唯一线索是当前图，先列出候选范围，逐笔核对来源，再决定哪段工作值得搬过去。对照另一位维护者手上的引用日志时，仍要确保讨论的是同一份主题尖端，免得把主题分支后续添加的提交也算成分叉点的差异。

真正准备重放时，给主题分支留一个能复查的起点。将切点、目标尖端与预期提交清单一起保存，核对自己写的提交确实都在候选范围。此处的四提交图没有合并节点，因此列出来的两个范围没有合并处理的问题。复杂主题若合并过其他分支，应先决定需要保存线性改动还是合并结构，简单范围中的候选集合只提供起始证据。对新上游做完变更后，还应按项目自己的验收判断新内容的行为。需要证明某个具体对象已经进入目标分支时，可以另看文件树一致与提交祖先的区别。

同样的命令如果被放进自动化，建议分别留存三个退出结果。引用解析失败时连输入都未确定，分叉点无输出时只有历史证据不足，列出范围失败时则没有拿到可审查的集合。将这三种情况放在同一个“没有提交”标签下，维护者就难以区分没有新增工作和根本没找到起点。

也可以先保存一份未改动的候选列表作为审查材料。假设某笔撤回的上游提交仍被列出，而另一笔属于自己的修复恰好和它改了同一个文件。只比最后的文件差异，有可能把这两个历史来源混成一个结果。对照完整提交 ID 再决定取舍，可以把“上游有意舍弃”和“本次要恢复”这两个决定分别留档。若原起点尚不能确认，就在记录里写明这一步待核实，后续的人才能知道为什么还没有执行重放。

主题从当时上游尖端的父提交分叉，日志完整也够吗？

分叉点模式需要主题所基于的提交曾经是指定跟踪引用的尖端。假设那条引用最早就指向 U，开发者却显式从 U 的父提交 R 新建主题，日志再完整也没有把 R 记成旧尖端。普通共同祖先仍可以是 R，分叉点模式却不应凭这条日志猜出 R。这样的主题要用明确保留的起点或可核对的提交范围，不能用“日志还在”来替代它曾记录那个对象的证据。
