跨区域列表成功，却有 unreachable，能当完整结果吗？

用两页跨地区读取区分分页完成与来源覆盖，保留 AIP-217 每页报告的不可达证据。

正文

核心要点

  • 跨集合成功结果仍可有暂不可达范围。
  • 按页保存缺口和后续恢复证据。
  • 翻页到末尾不能独自证明覆盖完整。

跨地区目录返回成功，东区给了两项，西区却出现在 unreachable 字段里。调用者可以使用已经收到的条目，但这份结果不能证明西区没有记录。采用 AIP-217 的接口应当把读到的条目和暂不可达的范围一并传给使用者，客户端也要让它们在分页结束之后仍然可区分。

成功说明返回了可读结果，覆盖另有证据

Google AIP-217 的指导描述了跨集合读取发生暂时不可达时，如何在响应中报告相关资源名称。字段使用服务相对名称，内容不携带语义顺序。一个条目指到西区，可以表示这次调用发现该区域无法访问；它不提供该区记录总数，也不解释具体故障原因。查询如果本来就只针对一个具体父集合，而该父集合不可达，指导要求整个请求失败。不能为了沿用跨区界面把它改写成一份没有条目的成功结果。

这一区别对目录浏览和完整导出有不同影响。浏览界面可以展示可读条目，并在列表旁说明暂缺哪个范围。要求把某一批源记录全部核对的导出则应保留缺口，等待恢复或明确交付的是部分结果。两者都可以把同一份成功响应读对，区别是产品对完整性的承诺不同。服务端如果没有提供更详细的错误证据，客户端不要用“零条”给暂不可达区域填空。

最后一页没有缺口，前一页的缺口还在

假设读取东、西两个地区的课程目录。第一页返回 east-A 和 east-B，报告西区不可达，并给出下一页标记 p1。第二页返回 east-C，没有报告新的不可达范围，也没有下一页。这里不能只保存第二页的字段。它说明第二页没有报告这项缺口，不能倒推前一页没有遇到缺口。页终止条件和本次返回是否覆盖全部范围，是两份不同证据。

以下是完整的本地 Node 程序，直接用这两份固定响应核对聚合结果。它不连接目录，也没有调用分页服务；响应顺序是样本的输入。独立预期可以从两行纸面记录算出：条目为东区三项，已经读到最后一页，第一页报告西区不可达。代码把状态命名为“报告过缺口”，没有把它作为永久区域状态。

import { deepEqual, equal } from 'node:assert/strict';

const west = 'projects/demo/locations/west';
const pages = [
  { items: ['east-A', 'east-B'], unreachable: [west], next_page_token: 'p1' },
  { items: ['east-C'], unreachable: [], next_page_token: '' },
];
function reviewPages(replies) {
  const items = [], pageGaps = [];
  let atEnd = false;
  for (const [page, reply] of replies.entries()) {
    const { items: found, unreachable, next_page_token: next } = reply;
    items.push(...found);
    if (unreachable.length) pageGaps.push({ page: page + 1, scopes: [...unreachable] });
    atEnd = next === '';
  }
  const coverage = pageGaps.length ? 'gap reported' : 'no gap reported';
  return { items, atEnd, pageGaps, coverage };
}
const report = reviewPages(pages);
deepEqual(report, {
  items: ['east-A', 'east-B', 'east-C'],
  atEnd: true,
  pageGaps: [{ page: 1, scopes: [west] }],
  coverage: 'gap reported',
});
const lastOnly = pages.at(-1);
equal(lastOnly.unreachable.length, 0);
console.log(JSON.stringify(report));

负例只查看最后一页。最后的不可达列表长度是零，若用它覆盖旧值，界面可能错误显示完整。另一个不充分的断言是检查总共三项后立即通过。如果真实西区也有记录，恰好拿到的三项仍可能不完整。测试应保存每页的条目身份、页标记与缺口，记录哪个范围在什么页面没有得到覆盖。本站带续页标记的空页解决什么时候继续请求；本篇即使已经按正确标记到终点，也还需要独立判断覆盖。

还要看缺口名称有多细。若服务无法把缺失位置准确缩到单条资源，可以按规则报告更高一层的范围。指导也允许在向上归并之后仍超过文档上限时限制名称数量，这个上限与调用者设置的每页条目数分别计算。这样客户端便不能把缺口数组长度理解成少读了几门课，也不应据它逐项生成精确的资源重试。对于报告区域的接口，界面可以给出区域级恢复入口，并注明目前无法知道区域内具体缺多少条。编写监控时记录“出现报告”与“报告列了几个范围”，两个数都不能冒充实际丢失记录数。

如果后续查询找回西区部分数据，可以更新一个明确的恢复记录，指出新结果覆盖了哪些先前缺失的范围。别一律保留“当前不可达”的告警，也别仅凭字段没再出现就删除缺口。历史观测、本次仍缺哪些结果、恢复后哪些记录确实已纳入，是不同的问题。对于实时数据，完成一次分页也不能提供跨页快照；要核对统一时刻的全量，应由项目提供额外的读取合同。

兼容迁移时给旧调用方保留失败条件

已有接口可能把任一区域不可达定义为整次请求失败，旧调用方据此把成功理解为所有范围都已处理。直接改成默认部分成功，会让它们原有的结果判断失效。AIP-217 对迁移要求同时加入请求的 return_partial_success 和响应的 unreachable，保留既有默认行为。需要继续使用可达数据的调用方明确选择部分成功，并实现对缺口的处理，再开始依赖新分支。迁移说明也应明确这个选择在哪种查询范围受到支持。

可以给旧客户端与新客户端各写一条对照。制造同一个西区不可达条件，旧请求维持其既有失败结果，新请求只在选择新合同并且范围受支持时拿到可达条目与缺口。在界面验收中再增加一项要求：用户能否区分西区查询失败与查询成功但确实没有课程。两个结果即使都没有西区卡片，也不应显示同一句话。上述是项目采用规则后的验证设计，本文只运行了两页固定对象的聚合。

西区在第二页恢复，但它的条目本应排在第一页，应该补进来吗？

如果补入会违背既定分页排序，不应强行塞进第二页。AIP-217 的分页指导要求恢复后的资源只有满足分页条件才进入后续结果，默认排序也算在条件内。主例没有恢复数据；这个分支增加可达性变化和已确定的排序边界。若需要查回它，应另起符合排序和范围约定的读取，再按项目的覆盖条件合并。仅知道区域已经恢复，不足以宣布此前的遍历自动补齐。
