Node 测试里的时钟被推进了，为什么 Promise 还没完成？

Node test runner 的 MockTimers 推进虚拟 timer/Date 时钟，但 setTime、tick 和 Promise 微任务不是一个概念；先明确要驱动哪种等待。

正文

核心要点

  • MockTimers 可控制选定的 timer API 与 Date，不会自动推进所有异步工作。
  • setTime 改变虚拟时间但不触发到期 timer；tick 才按时长推进 timer。
  • 每个 test context 的 mock tracker 会自动恢复，但手动管理 fixture 时仍要防止真实 timer 泄漏。

Node.js node:test 的 MockTimers 可以让测试推进虚拟 timer 与 Date，不用为 setTimeout 等待真实秒数；但改动时钟和触发定时器不是同一件事。官方 API 中 setTime() 改变 mock clock 的时间，却不触发在过去或当前时刻到期的 timer；tick() 才让时间向前走并执行到期回调。若把两者混为一谈，Promise 仍 pending 并不说明 mock 失效。

先列出测试要控制的时间来源

一个“过期”逻辑可能依赖多种时钟：Date.now() 判断业务截止时间，setTimeout() 安排重试，setInterval() 更新心跳，node:timers/promises 返回可等待 Promise。MockTimers 默认可模拟 setInterval、setTimeout、setImmediate 和 Date，也允许通过 apis 明确选择；指定某个 timer API 时，它对应的 clear 函数也会一起模拟。不要因为 mock 了 Date，就假定外部库里所有时间来源或 performance.now() 都随之冻结。

可控测试的第一步是给每个行为标出其时间依赖、预期触发边界和副作用。例如，失败后 500ms 重试，应验证 499ms 时没有发起第二次请求，跨过 500ms 后才发起；TTL 到期后拒绝读取，则要分别检查虚拟 wall clock 与 timer 回调是否一起推进。这个具体边界比“把时间快进一下”更可审查。

setTime 与 tick 的差别

假设测试先用 mock.timers.enable({apis:['setTimeout','Date'], now: 0}) 建立虚拟时钟，再安排一个 1000ms timer。调用 setTime(1000) 后，Date.now() 可显示新的时间，但该 timer 不会因为时钟跳到了截止点而自动运行。调用 tick(1000) 则推进计时器经过的时长，使到期回调执行。这个区别适合模拟手动改系统时间与真实经过等待时长的不同业务语义。

日期边界的测试还应决定是否要跨越日历日、时区偏移、夏令时或月末；单纯把毫秒数增加 24 小时不总等于业务上的“明天”。MockTimers 只替换选定的 API，并不自动替应用定义日期语义。若代码把 Date 与真实网络响应、数据库时钟或原生扩展混用，虚拟时钟可能只控制了测试的一部分。

timer 回调、微任务和 Promise 仍需观察

timer 到期回调若调用 resolve()，Promise 的 continuation 通常会在微任务队列里继续；测试应等待对应 Promise 或按 Node 文档提供的 mock timer 方法推进相关任务，不要把“回调执行”与“所有异步链结束”当成同一个观测点。Node 的测试 runner API 版本会改变可用方法和稳定性状态，当前引用的文档页面为 Node.js v26.13.1；功能从 v20.4.0、v18.19.0 引入，MockTimers 在 v23.1.0 标为稳定。若项目跑 Node 20 或 22，应读对应发行文档，不能直接复制最新 API 语法。

也要留意 node:timers/promises 的 setTimeout()、AbortSignal 中断、同一 deadline 安排多个 timer 的顺序，以及 setInterval() 跨多个 tick 的行为。测试只推进一次 tick 后断言服务逻辑已完成，可能漏掉 Promise settling 或后续 interval 触发。把各阶段断言拆开：时间读取、timer callback 次数、请求次数、Promise state、清理动作，能定位究竟是钟没变、回调没跑还是异步 continuation 未完成。

一个可复现重试边界的测试设计

设一个请求函数第一次拒绝，第二次成功；生产逻辑通过 setTimeout(retry, 500) 重试。测试应在每个测试上下文创建 mock timers，执行一次请求，然后在 499ms 检查调用仍为一次，接着再推进 1ms，并等待重试 Promise，最后检查第二次调用与最终结果。再增加取消路径：在到期前 AbortSignal 取消，确认 timer 被清理且不会继续执行副作用。这里是建议设计，没有执行 Node 命令或观察测试日志。

同样重要的是负向情况：若测试在断言后没有恢复 timer 行为，模拟状态可能污染共享 fixture；若只 mock setTimeout 而代码实际用了 timers/promises，测试依旧会等待真实时间；若 timer callback 安排另一个 timer，只推进一个间隔未必触发第二个。Node test runner 将 mock tracker 绑定到测试上下文，并会在 test 完成后恢复模拟，但你手工创建的外部 clock、第三方 fake timer 或跨上下文对象仍需自己管理。

选择标准：测试逻辑时间，别制造全局假象

优先使用 node:test 内置 MockTimers，当目标是验证 Node 自带 timer API、Date 边界和本测试的重试行为。仅选择需要 mock 的 API，让其他真实异步依赖保持清楚；用 now 设置明确 epoch，在每个测试中设定独立初始值。若组件自带时钟抽象，注入 clock 可能更适合跨运行时或纯函数测试。不要同时叠加几种 fake timer，除非已明确哪一层替换了哪个全局对象。

验收时记录 Node 版本、测试运行器、启用的 API、初始时间、每次 tick/setTime、回调次数和异步完成点。本文没有实际执行示例；它给出基于最新 Node 文档的行为解释，不能当作项目测试通过证据。测试应精确描述“虚拟时钟现在是什么”和“哪些 timer 已经运行”，避免一个笼统的 fast-forward 把环境真实机制遮住。

把虚拟时钟测试写成状态转换表

对边界敏感的逻辑，测试设计可以先列出状态而不是先写 tick：初始时刻、注册了哪些 timer、deadline、deadline 前的期望、到期后的回调、Promise continuation、最终副作用。以重试为例，第一次调用失败后注册 500ms timer；虚拟时钟处于 499ms 时调用数仍为 1；再经过 1ms 后 timer 回调应启动第二次调用；随后还要等待并断言第二个 Promise 的结果。这样可以把“定时器按期运行”与“业务异步链收敛”分别验证。若 Node 当前版本提供了运行 pending timers 或执行微任务相关的 API，必须按对应版本文档核对其语义，不要把某个测试工具的 flush helper 当成所有 Node 版本都具备的功能。

另一个容易漏掉的边界是相同 deadline 的多个 timer。代码可能依赖注册顺序，也可能在一个 timer 中创建新的 timer；一次 tick 的目标区间是否包含终点、到期回调创建的后续 timer 是否会在本次推进中继续执行，都会影响测试写法。最稳妥的是设计几个小测试，直接记录每个 callback 的顺序，并逐次推进有限时间，再与当前 Node 版本的公开 API 行为核对。本文没有运行这些实验，所以不能断言特定版本中所有嵌套 timer 的调度顺序。

MockTimers 的边界也能帮助判断何时应改用依赖注入。若被测模块同时读 Date.now()、浏览器性能时钟、数据库服务器时间和第三方库的私有调度器，mock Node 全局 timer 只覆盖了一部分时间源。把业务 deadline 包装成显式 clock 接口，能在单元测试里注入可控时间，再用少量集成测试核对真实适配器。相反，若目标只是验证 Node setTimeout/Date 的交互，内置 mock 可减少额外假时钟实现的维护成本。测试报告中列出被替换的 API 和仍然真实运行的时钟，能避免把局部虚拟时间误当成全系统时间冻结。
