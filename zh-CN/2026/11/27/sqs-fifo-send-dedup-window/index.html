SQS FIFO 的五分钟去重保护的是发送重试，不是业务副作用

Amazon SQS FIFO 按消息去重 ID 在五分钟窗口内避免重复入队；它不替消费者保证一次性扣款或数据库写入，内容哈希也不包含消息属性。

核心要点

  • 五分钟窗口绑定 FIFO 消息发送去重，不等于业务效果只执行一次。
  • 内容去重模式只对消息体做 SHA-256，消息属性不参与。
  • 关键业务副作用仍需由消费者的幂等键或事务记录保护。

Amazon SQS FIFO 的去重窗口解决的是发送端不知道 SendMessage 是否成功、于是重试同一条消息时可能多入队的问题。按相同去重 ID 在五分钟窗口内重发，SQS 不会再加入一份重复消息；这不保证消费者只执行一次扣款、发邮件或数据库写入。消费者侧仍可能遇到重投、超时和副作用之后未删除消息等情况，因此要把“队列接收去重”和“业务操作幂等”分开设计。

五分钟窗口从哪里开始？

假设订单服务要把订单 o-817 的“准备出库”事件发送到 FIFO 队列。服务发送后网络断开，没有收到响应，无法确定消息是否已经到达。它使用 order:o-817:ready:v1 作为 MessageDeduplicationId 重试。如果重试落在同一个五分钟去重区间，SQS 会把它识别为重复发送，不再把第二份放入队列。这让客户端可以对不确定的发送结果进行有限重试，而不用假设每个网络超时都代表第一次请求失败。

这个保证有明确边界：它作用在 FIFO 的发送去重机制和时间窗口内。五分钟之后，相同 ID 的发送不再享有这个窗口内的抑制保证；业务系统要能处理延迟重放、人工重发或更长时间后的恢复。消息发出后消费者是否成功、是否处理到一半、是否把副作用提交后崩溃，都不是发送去重本身能证明的事情。AWS 页面用 “exactly-once processing” 描述 FIFO 能力时，正文具体展开的是避免在短窗口里重复入队，阅读时不能把标题扩大成端到端事务语义。

内容去重会看哪些字段？

启用 content-based deduplication 时，SQS 用消息体计算 SHA-256 去生成 deduplication ID；消息属性不参与该哈希。因此，两条消息的 JSON body 相同，但 tenant、trace-id 或 schema-version 属性不同，仍可能因为生成的去重 ID 相同而被当作重复。如果这些属性改变业务含义，不能默默依赖 body-only 的内容去重。可以显式提供包含业务版本的 MessageDeduplicationId，或者把语义字段纳入经过规范化的消息体；设计时要说明稳定的事件身份是什么。

反过来，如果两条文本 JSON 的字段顺序不同，虽然业务数据可能相等，字节内容也可能不同，内容去重就可能得到不同 ID。内容去重不是 JSON 语义比较器，不会替应用排序字段、规范数字格式或去掉不影响业务的元数据。对于一次业务动作，显式构造稳定的事件 ID 往往比期待哈希自动理解“语义相同”更容易审计。示例中的 ID 格式仅为设计假设，未发送到 AWS 队列。

显式 ID 也需要避免“过度复用”。如果系统仅把订单号 o-817 当去重 ID，同一订单的 ready 与之后合法的 cancelled 两种不同事件可能在五分钟内撞到同一身份，第二个发送会被抑制。更有解释力的身份通常包含聚合对象、事件类型和产生该事件的稳定版本或序号；它既要让网络重试保持一致，也要让不同业务变化彼此区分。反例是在每次重试时随机生成一个新 UUID：这会把同一业务事件伪装成多条新消息，失去重试去重的效果。具体字段应由事件模型定义，而不是单纯照搬示例字符串。

一个副作用时间线如何越过发送去重？

设消费者收到订单事件后先调用支付服务，再把消息删除。假设支付已成功，但消费者在 DeleteMessage 前崩溃，消息之后可以重新交付。FIFO 仍按队列顺序交付，但消费者可能再次调用支付服务。去重窗口描述发送端重复提交消息的行为，不会自动检查外部支付系统是否已经扣款，也不会让支付调用与消息删除形成同一个原子事务。

更稳妥的消费者合同是：将稳定的 event_id 写入业务侧处理记录，并与业务变更放在同一数据库事务里；如果副作用发生在外部服务，则把该 ID 作为下游幂等键传递，或先写 outbox 再由有去重能力的下游执行。数据库唯一约束可以阻止同一事件被第二次登记，但不能凭空撤销一个已经完成、而下游又不支持幂等的外部动作。具体做法取决于副作用边界，不存在由 SQS FIFO 单独提供的通用分布式事务。

处理记录还要定义状态转换。比如，第一次收到事件时建立唯一的 event_id，业务事务提交后把记录标为完成；第二次收到相同事件时，若查到完成记录就不重复调用外部服务。若只记录“处理中”而消费者崩溃，租约过期后还要允许恢复或人工核对，不能让这个状态永久占住事件。这个数据库状态设计是消费者责任，SQS 的五分钟发送去重不会替它维护。

如何验收发送者和消费者的不同保证？

发送端测试应分别覆盖：首次发送已成功但响应丢失、窗口内相同 ID 重试、不同业务 ID 的消息、窗口过后再次发送，以及属性不同但 body 相同的内容去重情形。消费者测试应覆盖：处理前崩溃、业务副作用成功后删除前崩溃、同事件再次交付、幂等记录已存在，以及下游暂时失败。测试的目标不是证明任何真实队列恰好执行一次，而是证明每一层在自己声明的合同内处理重试。

本文没有创建 SQS 队列或运行 AWS 客户端；时间线和检查项是根据官方文档组织的假设案例，不是实测日志。部署前还应核对队列是否启用 content-based deduplication、显式 ID 的生成规则、FIFO 消息组顺序，以及消费者的可见性与删除策略。把五分钟发送去重当作一层减轻重复入队的保护，再独立设计业务幂等，才不会把一个局部机制误当成端到端“只执行一次”。

发送端仍需记录业务事件 ID、SQS 返回的消息 ID 和重试原因。去重 ID 应来自稳定的业务操作标识，而不是每次重试都重新生成的随机数；但若两个不同事件错误复用同一个 ID，窗口内的第二条消息也可能被当作重复发送而抑制。消息体哈希去重也有相反边界：同一正文、不同消息属性仍可能命中相同正文去重值。先定义消息唯一性是“相同命令只出现一次”还是“正文相同只出现一次”，再选显式 ID 或内容去重。
