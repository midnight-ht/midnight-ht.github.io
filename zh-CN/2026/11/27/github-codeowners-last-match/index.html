CODEOWNERS 规则不是累加的，最后一个匹配行会改变审查人

GitHub CODEOWNERS 按路径匹配并由最后匹配规则决定 owner；同一模式的多个审核人必须写在同一行，且 PR 使用目标分支版本。

正文

核心要点

  • 后面的匹配模式覆盖前面的 owner，不会自动把全局团队累加进来。
  • 同一模式要请求多个可选 owner，需写在同一行；不同匹配行只采用最后提到的 owner。
  • PR 使用 base branch 中的 CODEOWNERS，规则文件本身也需受到保护。

GitHub 的 CODEOWNERS 规则会按路径模式分配审查人，多个匹配并不会自动把前面每一行的团队都累加起来；最后一个匹配的模式优先。同一模式如果要让多个 owner 都可被请求，必须把他们写在同一行。若把同一模式拆成两行，GitHub 只采用最后提到的 owner。这是审查路由规则，不是 YAML 列表，也不是“所有匹配团队都要会签”的表达式。

一个全局默认值怎样被覆盖？

假设仓库希望所有变更都由平台团队负责，再把支付目录分配给支付团队。示意规则是：第一行 * @org/platform，后面一行 /services/payments/ @org/payments。修改支付目录文件时，后一个更具体且匹配的规则优先，GitHub 请求支付团队；平台团队不会因为它也匹配 * 而自动保留在审查请求里。若政策要求平台与支付团队都能处理同一改动，可以在最后匹配行把两个 team 放在同一行；但 CODEOWNERS 自动请求本身仍不是强制双人批准。

更隐蔽的错误是把两个 owner 拆行：

/services/payments/ @org/platform
/services/payments/ @org/payments

看上去像“平台和支付都负责”，实际匹配结果只采用第二行的 @org/payments。如果团队要表达两个候选 owner，应改成 /services/payments/ @org/platform @org/payments。这个区别会影响谁收到 review request，也会影响配置分支保护时“任何 owner 通过就足够”的理解。GitHub 文档明确表示，当要求 code owner review 时，任意一个 owner 批准即可满足该要求。

规则来自哪一个文件、哪一个分支？

仓库可以在 .github/CODEOWNERS、根目录 CODEOWNERS 或 docs/CODEOWNERS 放置文件；多个位置同时存在时，GitHub 按 .github/、根目录、docs/ 顺序搜索并使用找到的第一个。每个分支都可以有自己的文件。Pull Request 的审查路由使用目标分支，也就是 base branch 中的 CODEOWNERS。因此同一个 PR 里修改规则文件和受管路径时，新规则不会自动成为这一条 PR 的最终审查事实；要先将规则更新合入目标分支，再验证后续 PR 的请求是否符合预期。

Fork 场景同样受 base branch 影响。来自 fork 的 PR 若目标是上游分支，就使用上游目标分支里的 CODEOWNERS；若目标指向 fork 自己的分支，则 owner 需要在那个 fork 上拥有明确写权限，才会触发请求。不能只看 fork 的 head branch 上新增了谁，就认定 GitHub 会向他们请求审查。

路径和 owner 拼写错误会怎样？

CODEOWNERS 路径区分大小写，即便开发者在默认不区分大小写的 macOS 文件系统上编辑，GitHub 仍使用区分大小写的文件系统解释路径。模式写成 /Services/Payments/ 而实际目录为 /services/payments/ 时，规则可能匹配不到。某一行语法无效会被跳过；指定的用户或团队不存在，或缺少仓库写权限，也不会分配 owner。看起来正确的文本不等于有效路由。

同样要认识 CODEOWNERS 语法和 .gitignore 只有“大部分相同”。GitHub 文档明确指出，! 取反规则、[ ] 字符范围以及对 # 开头模式的反斜线转义并不能照搬。将熟悉的 gitignore 片段复制到 CODEOWNERS，可能生成一条被忽略的无效规则。复杂排除最好拆成可读目录规则并通过实际 GitHub 的文件错误提示或 API 反馈验证，而不是靠本地 glob 库猜测最终 reviewer。

目录通配符的边界也值得用样例明写：官方例子中，docs/* 匹配 docs/ 下一层文件，不匹配更深的 docs/build-app/troubleshooting.md；写成 /docs/ 才覆盖根目录下的该目录及子目录。另一个高风险习惯是觉得“更具体的规则天然总会赢”。CODEOWNERS 的判定重点仍是最后一个匹配模式；后来新增的宽泛模式也可能改变前面精细规则的结果。评审规则变更时应拿实际文件路径逐条推演，不能只按文本排列出一棵看起来合理的目录树。

自动通知和强制门禁有什么差别？

CODEOWNERS 默认对修改受管代码的非草稿 Pull Request 自动请求 review；要把 owner 审批变成合并条件，还需仓库管理员在分支保护规则中启用“Require review from Code Owners”或配置等效 ruleset。即便启用，任一被请求的 owner 批准通常就满足要求。若合规规则要两个部门共同签署，CODEOWNERS 本身不表达这种人数或角色门槛，应使用支持相应审批策略的系统。

规则文件还要保护自身。若任何人能通过未审查的改动把 CODEOWNERS 的保护范围删掉，仅保护业务代码就不完整。GitHub 文档建议把 .github/CODEOWNERS 放在受保护位置，并为该文件或整个 .github/ 目录指定仓库 owner，再通过分支保护要求 owner 审批。

怎样验证一组修改？

建立一张路径—预期 owner 矩阵，覆盖普通文件、特殊目录、大小写边界、多个同模式 owner、目录排除和无效 team。先在默认分支读取实际生效的 CODEOWNERS 文件位置，再对照 PR 的 base branch 验证通知对象；之后分别测试草稿转 ready、普通 PR、fork PR 和启用必需审批时的合并结果。修改规则的 PR 需要由当前规则覆盖，而不是依赖尚未合入的新内容。

本文没有调用 GitHub API 或创建仓库 PR，矩阵是验收设计，不是实际收到 review 请求的证据。最终确认应检查 GitHub 页面显示的 owner、CODEOWNERS 错误提示、分支保护设置和 PR 中实际生成的 review 请求。把匹配顺序、base 分支、路径大小写、owner 访问权与强制审批分开核对，才知道门禁是“发出了提醒”还是“真的阻止了未批准的合并”。

如果仓库同时维护多个长期分支，还要把规则变更的传播路径写清楚：默认分支里的新 owner 不会自动改写已经创建的 PR 所使用的 base 版本；release 分支也可能暂时保留旧规则。可以在变更模板中列出目标分支和预期 reviewer，并在合并前后分别确认请求对象。不要只在 head 分支提交一份“修复后的 CODEOWNERS”，然后把那条 PR 当前收到的 owner 当作新规则生效的证据。
