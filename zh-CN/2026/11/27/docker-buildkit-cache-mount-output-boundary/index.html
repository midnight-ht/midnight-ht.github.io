Docker 构建缓存有了 mount，为什么 CI 每次还是重新下载？

BuildKit cache mount 是构建器本地的可回收性能缓存，不写入镜像层，也不随 --cache-to 导出；CI 新建 builder 时可能为空，构建不能依赖其内容正确性。

正文

核心要点

  • Cache mount 与可复用 instruction layer 是不同缓存机制。
  • cache mount 通常保留在同一个 builder 的本地存储，不属于 --cache-to/from 导出的构建缓存。
  • 构建必须在空缓存或内容被回收时仍正确；缓存只应加速，不应成为构建输入的唯一来源。

BuildKit 的 RUN --mount=type=cache 提供给构建命令一个持久化目录，适合缓存包管理器或编译器的重复下载；它是构建器本地、可被回收的性能缓存，不写进最终镜像层，也不随常规 --cache-to 导出。CI 每次启动全新 builder 时缓存可能为空，所以“配置了 cache mount”不等于跨 runner 复用缓存。正确的构建必须能在缓存缺失或被清理时仍生成正确产物。

Cache mount 和 instruction layer 不是同一个东西

Docker 的普通构建层按指令及其输入命中缓存；若前面的 COPY 输入变了，后续层可能失效并重新执行。Cache mount 则是在某条 RUN 指令执行期间，把一个缓存目录挂入容器，例如 /root/.npm 或编译器缓存。命令重跑时，包管理器可以复用已下载文件，减少网络请求，但 mount 目录里的内容不是该指令输出层的一部分。

可以把它们理解为两种状态：layer cache 重用上一次指令的结果，cache mount 为重新执行的指令提供可用的临时积累数据。指令没有失效时，Docker 可能直接复用层，命令根本不运行；指令失效时，mount 可能帮助加速重新运行。这两者的命中条件、存储位置和导出方式不同，不能用“镜像层缓存了”推断“cache mount 在新机器上存在”。

为什么 CI 会从空目录开始？

Docker 文档说明，cache mount 存在 BuildKit builder 的本地存储，不包括在导出的外部 build cache 中，也不会由 --cache-from 恢复。如果每个 CI job 都创建全新的 builder，cache mount 起点就是空目录。即使同一 builder 的内容会在构建间保留，也可能被其它并行构建覆盖，或被 builder 的垃圾回收清除。Dockerfile reference 要求构建对 cache mount 的任何内容都保持正确，不能假设它永远包含上次写入的结果。

因此要先确认 CI 是否复用了同一个 BuildKit daemon/builder，再确认外部 cache 配置和 cache mount 本地持久化是两个单独机制。仅添加 cache-from / cache-to 不代表 mount 目录会在新 builder 中复原。若希望 CI 跨新 builder 共享包下载，可以使用适合的 CI cache 导入导出方案、外部包仓库或构建器持久化策略；具体效果依赖 Docker/BuildKit 版本和 CI 平台。

让缓存失效只影响速度，不影响正确性

示例 Dockerfile 可以为 npm cache 挂载 /root/.npm，然后执行 npm ci。项目依赖仍须由 lockfile 确定，npm ci 每次按锁文件安装；cache mount 只帮助复用 package tarball 等下载内容。若 mount 被清空，命令可能更慢，但不能因此改变依赖版本或成功与否。若将 cache 目录当成唯一保留 node_modules 的位置，而构建后续步骤依赖它，mount 生命周期结束后内容可能不在预期层中。

并发访问也要匹配缓存客户端的行为。sharing=shared 允许多个 writer 并行使用同一 mount，private 可为并发 writer 创建独立缓存，locked 则让后续构建等前一个使用者释放。Docker 文档以 apt 缓存为例建议 sharing=locked，因为包管理数据需要互斥访问。不要为所有目录盲目设同一个 sharing 模式；应根据包管理器的锁、并发写入安全性和容错能力选择。

一个缓存配置正确却没有加速的例子

开发者在 Dockerfile 中加了 cache mount，本地连续 build 变快，随后在 CI 看到每个 job 仍重新下载。若 CI runner 每次新建 builder，官方约定的本地 mount 缓存不会从 --cache-from 恢复；构建行为符合设计，不代表配置语法无效。更合适的诊断是记录 builder 身份、生命周期、cache mount ID、目录路径、是否命中、下载量和 RUN 指令是否真正执行，再决定需要复用 builder 还是外部包缓存。

另一个反例是把 /root/.npm 的缓存内容当成供应链验证。缓存可能被另一个构建写入，内容可被清理或陈旧；lockfile integrity 校验、包来源、依赖审查和最终 build artifact 身份仍应独立验证。缓存可提高重复操作效率，却不自动提高依赖安全性，也不证明两次构建产物可复现。

验收方法：空缓存、并发和导出三个路径

在测试 runner 先记录 builder ID，执行两次相同构建并观察 cache mount 是否保留；再使用新 builder 执行一次，确认空缓存仍能成功。明确打出每条 RUN 是否命中 layer cache，避免把层复用误当成 cache mount 命中。接着使用 --cache-to 导出并在新 builder --cache-from，验证 mount 起始状态；根据预期配置共享 builder 或 CI cache。最后并发执行两条构建，检查包管理器缓存是否需要 locked。

本文未运行 Docker build，也没有测量下载时间。验收应记录 Docker/BuildKit 版本、Dockerfile syntax directive、builder driver、cache id、sharing、外部 cache backend 与命令结果；性能改善必须来自实际 CI 对比，不能根据文档机制推算。将 cache mount 设计成可被清空、覆盖或回收的数据目录，构建仍保持确定性，才把性能优化和构建正确性分开。

cache ID 也决定哪些构建共享目录

不同 RUN --mount=type=cache 可以通过 id 指定缓存身份；不显式设置时，默认身份与目标路径有关。多个分支、项目或并发任务若意外共用相同 builder 与缓存 ID，可能读到彼此积累的包数据。为缓存指定稳定但按工具/项目隔离的 ID，并根据写入并发选择 shared、private 或 locked；这些选项控制的是缓存访问，不是依赖完整性。配置 uid、gid、mode 时还要让构建用户实际有权读写挂载目录，否则冷缓存阶段可能与热缓存阶段表现不同。

Cache mount 也不应承载凭据或租户专属数据。即使目录只存在于 builder 存储，builder 的复用范围仍决定哪些构建可以再次挂载它；共享 builder 上的缓存内容需要按同一信任域管理。对私有仓库下载凭据使用 BuildKit 的 secret mount 等专门机制，避免把认证材料写入可复用缓存。本文没有对任何 runner 做隔离测试，这里是基于 Dockerfile mount 选项与 CI 信任边界的设计判断。

缓存键还要与内容格式兼容。升级包管理器或改变缓存布局后，沿用旧 ID 可能让新工具读到无法识别的状态；可将工具主版本或格式代号纳入 id，并在清理旧缓存前确认冷构建路径可用。反过来把每个 commit SHA 都放进 ID 会让缓存永远无法复用。选择 key 的目标是隔离不兼容数据，同时保留可信分支间合理的复用。
