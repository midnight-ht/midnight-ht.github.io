Server-Side Apply 冲突说明字段有人负责，不等于配置无法更新

Kubernetes SSA 按字段记录 manager；改动他人管理且值不同的字段会冲突，强制覆盖会转移所有权。先厘清控制器与发布工具的职责，再决定是否 force。

正文

核心要点

  • SSA 冲突是字段所有权保护信号，不是普通资源版本冲突。
  • 多个 manager 对同一字段声明相同值时可以共享所有权，之后任一方改值仍会冲突。
  • force-conflicts 会覆盖值并转移字段所有权，应作为明确的管理权接管操作。

Kubernetes Server-Side Apply（SSA）冲突通常是在保护另一方已经声明负责的字段：新 apply 想把字段改成不同值，而现有 manager 仍持有该字段。先看 managedFields、字段值和每个控制器的职责，再决定应修改清单、调整 manager，还是用 --force-conflicts 有意接管。把所有冲突都自动 force，可能让 GitOps、operator 和人工运维不断互相覆盖配置。

SSA 记录的是字段管理关系

传统客户端 apply 借助 kubectl.kubernetes.io/last-applied-configuration 注解保存过去提交的配置，再拿新旧清单对比。SSA 则让 API server 记录一个 manager 对哪些字段作出声明，管理信息保存在对象的 metadata.managedFields 中。manager 是客户端提供的身份字符串，可以是 kubectl、部署控制器或自定义工具；它不是 Kubernetes 身份验证账号，也不单独授予 API 权限。

例如，平台控制器设置 spec.replicas 和 spec.template，自动扩缩容控制器改变副本数，而发布工具更新镜像。若多个客户端都用不协调的 apply 配置声明同一字段，SSA 可以在更改值时报告冲突，让团队看见管理边界的重叠。冲突不是 API 服务器完全拒绝这个对象，也不一定说明字段当前值错误；它表示本次 apply 可能推翻另一方仍在维护的声明。

官方文档指出，另一个 manager 变更且仍拥有的字段会冲突；如果双方声明同一字段且值相同，可以共享所有权。共享所有权也不是永久豁免：只要其中一方之后尝试把值改成不同值，就会再次冲突。若某 manager 在 apply 请求中不再包含自己管理的字段，它会放弃这部分声明；当没有其他 manager 持有该字段时，服务器可能清除字段值或回到默认行为。对可选字段，这种“从清单删除”可能是语义变更，不只是清理文本。

先判断是职责重叠还是有意接管

设想一个 Deployment 的镜像由发布流水线负责，副本数由 HPA 调整，标签由平台治理工具维护。某次 kubectl apply 同时带入镜像、副本数和标签。如果清单保留了副本数的旧值，apply 可能与 HPA 的字段声明冲突；若给整个对象换一个 manager 名称，原有的字段所有权并不会因此自动按团队意图重新整理。正确处理是缩小发布清单的字段集合，让每种控制器只写自己负责的部分，并观察目标字段是否仍符合应用所需状态。

另一种情况是旧控制器已下线，新控制器被明确指定接管字段。此时 force 可能合理，但应先确认旧 manager 不会继续运行、变更提交中写明接管范围，并记录接管后的字段归属。kubectl apply --server-side --force-conflicts 会覆盖冲突值并把字段管理转给当前 manager；它不是“重试一下”的无害参数。若旧控制器还在工作，force 只会让来回覆盖更隐蔽，甚至在每次 reconcile 时重复冲突。

还有一个容易混淆的边界：普通 PUT 或非 apply 的更新与 SSA 冲突处理不同。Kubernetes 文档说明，普通 update 修改已被其他 manager 管理的字段不会因 SSA 字段冲突而失败，但会改变该字段的管理记录。因而不能用一次普通更新成功，推断 SSA 后续也不会冲突；同样，不能把 managedFields 解释成审计历史，它描述当前字段管理状态，不提供每次变更的完整历史账本。

用一个最小冲突复现管理边界

可以在可丢弃的测试集群中创建一个 ConfigMap，让 manager-a 通过 server-side apply 设置 data.color: blue，再让 manager-b 用不同值 green apply 同一字段。预期第二个请求返回字段冲突；若两个 manager 对字段都提交 blue，所有权可共享，但随后任一个 manager 改成 green 仍会冲突。最后在明确接受接管的测试对象上加入 force，读取对象确认值变化和 managedFields 中 manager 变化。以上是建议的实验设计；本文没有连接集群执行命令，不能把预期结果写成实际日志。

上线排查可从 kubectl get -o yaml 查看对象值和 managedFields，再用 kubectl apply --server-side --field-manager=<name> --dry-run=server 对目标清单做服务端预演。Dry run 可以暴露部分冲突和校验问题，但不是完整发布验证：准入 webhook、并发 reconcile、权限、后续控制器行为仍需考虑。调试时不要手工改 managedFields，Kubernetes 文档明确将它作为 API server 管理字段。

选择标准：消除双写，或保留有审计的接管

如果两个系统需要长期管理同一字段，先问是否能拆开职责、使用不同字段，或让其中一个系统只观察而不写入。如果产品语义确实由多个管理者共同保证，就让它们声明相同值并测试未来变更如何协作；这不是跨团队审批机制。若是迁移旧 controller，则把 force 当一次权限移交，限制到具体对象和字段，并检查后续每个 manager 是否停止重复声明。

反例是把“apply 返回冲突”归类为部署失败后无条件追加 force。流水线虽然变绿，字段责任却从自动扩缩容或 operator 转走；下次控制器再次 reconcile 时，团队仍会看到副本数跳动或重复冲突。更稳妥的发布记录包括 manager 名称、冲突字段、旧 owner、新 owner、是否 force、提交 SHA 和回滚方式。这样团队可以区分清单过度声明、manager 名称变化、控制器并存和确实需要接管等不同故障路径。

SSA 的价值在于把声明式工具之间的字段争用变成可见冲突。它不能替团队决定哪一方应当拥有字段，也不记录业务授权。先建立稳定的字段责任图，再通过服务端预演与测试集群验证接管，能让错误在部署时暴露，而不是等多个 reconciler 反复争夺对象后才从线上漂移中发现。

交接时可先用即将接管的稳定 manager 名称执行 server-side dry-run，记录字段冲突清单；由当前 owner 收窄自己的 apply 清单并再次预演，确认仍由旧 owner 声明的字段不会被新配置意外清空。只有明确完成交接的字段才使用 force，再读回 live object 和 managedFields 对照提交中的预期。若 dry-run 后控制器又把字段写回，说明仍有持续写入者，不能把一次 force 视为职责迁移完成。
