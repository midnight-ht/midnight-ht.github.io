Python audit hook 能记录和中止事件，但不能把解释器变成沙箱

Python 3.12 的 sys.addaudithook 面向运行时审计；钩子安装本身可能被已有钩子拒绝且不显式报出，安全边界仍须放在解释器之外。

正文

核心要点

  • 审计事件适合观察内部动作并在受控条件下中止。
  • RuntimeError 可能使新钩子未被添加且被抑制，调用方不能据此认定安装成功。
  • 恶意代码可绕过 Python 层钩子；安全边界要由进程外控制。

Python 的 audit hook 适合观察解释器和库发出的审计事件，也能按策略记录、拒绝某些操作；它不是运行陌生 Python 代码的沙箱。更容易被忽略的是安装行为：Python 3.12 文档说明，如果已经存在的 hook 在添加新 hook 时抛出 RuntimeError，这个异常会被压制，新 hook 不会加入。调用者因此不能把 sys.addaudithook() 返回或未报错，直接当作“我的检查器已经生效”。

审计事件提供什么，不提供什么？

事件可携带事件名和参数。比如 os.chdir 事件带有目标路径；hook 可以写日志、抛出异常中止这次操作，或者终止进程。事件名和参数类型被文档视为公共稳定 API，但这不等于任意第三方库的所有业务动作都有对应事件，也不等于一条事件就能完整描述用户意图。审计日志适合观察解释器内部或原本不容易看见的动作，仍需按照应用的威胁和业务事件设计补充记录。

选事件时应把信号和决策分开。例如，打开路径 /srv/jobs/tenant-42/report.csv 可以说明解释器尝试访问了某个文件，但不一定说明请求属于哪个用户、为何授权、最终是否成功。路径还可能包含客户标识，直接写入长期日志会引入隐私风险。可以先对参数做范围允许列表与脱敏，再用请求关联号连接到应用层审计记录；不能通过记录一个文件路径，就推断该请求一定合规或一定有恶意。是否接受、拒绝或触发人工检查，仍要建立在明确策略之上。

以一个文档转换命令为例，团队希望知道处理过程中是否改变了工作目录、打开了哪些文件，以及加载了哪些模块。可以根据 CPython 提供的事件表，选取与目标行为相关的事件，先把事件名、参数脱敏规则、记录位置和失败处理方式写成表，再实现 hook。这个例子是设计方案，没有运行在本文机器上的真实项目，也没有覆盖所有 Python 库的系统调用。若团队想记录“用户点击了导出”或“报告包含哪些租户数据”，这些是业务语义，应在应用自己的受控入口记录，不能等待解释器事件替业务做判断。

安装钩子失败为什么可能被静默掩盖？

设想程序启动时添加一项用于记录文件访问的 hook，之后根据记录判断某些输出能否交付。若有另一个已安装 hook 在处理 sys.addaudithook 事件时抛出 RuntimeError，Python 会抑制这一类异常并不添加新 hook。调用端继续启动，看起来没有安装错误，但期望的记录器实际不存在。依赖插件若可以提前安装 hook，就会影响之后安装的观察器。顺序、初始化阶段和加载来源都属于审核问题。

不能简单地用“调用前后比较 hook 数量”来确认成功，因为 Python 没有给纯 Python 代码一个安全、受支持的 hook 枚举接口。比较稳妥的应用层做法是限制初始化顺序：在加载不受控插件前安装必要的观察器；对关键的安全控制，不能依赖这个纯 Python 添加路径；为进程启动流程保留可核对的配置与诊断。测试时，构造一个已有 hook 对添加事件抛出 RuntimeError 的夹具，确认程序不会把未安装状态报告成安全成功。这个负向测试可以验证当前 CPython 版本中的特定失败路径，但不能证明每一种 hook 和所有解释器扩展都行为相同。

为什么它不是 Python 级别的沙箱？

Python 3.12 文档直接说，sys.addaudithook() 不适合实现 sandbox，恶意代码可以轻易禁用或绕过由该函数添加的 hook。官方进一步指出，安全敏感的 hook 至少要通过 PySys_AddAuditHook() C API 在运行时初始化前添加；会任意修改内存的模块，例如 ctypes，需要完全移除或密切监控。这个要求本身就表明，应用在解释器启动后装一段 Python 函数，不足以建立对抗恶意代码的信任边界。

若你控制的是自己编写的工具和依赖，audit hooks 有助于把内部动作纳入审计或辅助策略检查。若执行的是用户提交的代码、未知插件或攻击者可影响的表达式，必须让隔离位于进程外，例如独立操作系统身份、受限文件系统、网络边界、资源上限和可销毁的执行环境。容器是否构成足够边界，取决于配置的挂载、权限和内核接口；不能仅凭“运行在容器里”作出绝对判断。

如何验证日志和拒绝规则没有混为一谈？

把验收拆成三类：事件是否触发、记录是否足以解释上下文、拒绝动作是否真的让操作失败。用允许的路径和禁止的路径各构造一个样例；检查系统调用失败、上层异常传播、部分文件是否被留下，以及日志中是否泄露凭据或个人数据。若 hook 只负责观察，就不能把有日志解释成操作已被阻止；若 hook 拒绝事件，也要检查调用方是否捕获并忽略异常后继续执行。

本文没有执行这些程序或构造夹具，因而上述内容是基于 Python 3.12 文档的验证方案，不是运行结果。对于安全敏感部署，应固定解释器小版本，确认所有 hook 在何时、由谁安装，检查原生扩展和 ctypes 等能修改进程状态的组件，并把剩余风险交给外层操作系统隔离。这样做不会让 audit hook 失去价值，而是把它放回其真实职责：提高可观察性并辅助策略执行，而不是单独承担恶意代码隔离。

部署验证还要确认每个预期执行的解释器都加载了 hook：主服务、异步 worker、管理命令和测试进程可能分别创建解释器。只在 Web 入口启动时安装，不能证明后台队列也有相同观察能力。可以在启动诊断中保留 Python 版本、启动方式和 hook 初始化阶段的可审查记录，但不应把事件的敏感路径写入健康端点。覆盖多个进程时，进程启动器和容器权限比父进程中的一段 Python 代码更适合作为安全策略来源。
