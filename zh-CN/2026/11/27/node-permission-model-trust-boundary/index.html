Node.js 权限模型能收紧进程权限，但不是运行陌生代码的沙箱

Node.js 22 的 --permission 适合减少可信程序误用文件、子进程和 Worker 的机会；官方明确不把它当作抵御恶意代码的安全边界。

正文

核心要点

  • 权限模型的设计对象是可信代码的意外动作。
  • 依赖包仍属于被信任并运行的代码。
  • 隔离恶意代码应放在操作系统或独立容器边界。

Node.js 22 的 Permission Model 可以把一个进程允许访问的文件、子进程、Worker、原生插件等资源收紧，适合降低可信程序误操作的范围；它不能把不可信 JavaScript 变成安全代码。官方文档明说，这个模型采取“seat belt”思路，不承诺对抗恶意代码。设计时要先问运行的程序是否可信，再决定权限旗标，而不是把 --permission 当成通用沙箱开关。

它要防的是哪一种错误？

设想一个本地文档转换服务：它读取项目上传目录，把转换结果写入专用输出目录，还加载几个项目依赖。某个新版本的可信转换器因为路径拼接错误，意外覆盖了同一主机上的用户配置。权限模型的价值是把可读、可写范围缩小，让这种误操作更难越过设计边界。它表达的是“程序原本可信，但不能随便触碰其他资源”，类似给一名可信员工一把只开特定房间的钥匙。

换一个前提：攻击者能控制转换器执行的 JavaScript，或者某个依赖本身就是恶意代码。此时代码会主动寻找可利用的路径，不能只靠应用自己声明的权限来保证隔离。Node.js 的安全策略明确把运行请求交给用户的代码视为可信；Permission Model 文档也提示，恶意代码可以绕过模型执行没有被许可的操作。把前一种误用保护套到后一种对抗场景，会把边界放错位置。

本文核对的是 Node.js v22 文档当前显示的 v22.23.5。该模型从 v20.0.0 加入，在 v22.13.0 后不再是实验性功能。旗标与可用权限会随发行线演进，本文不把当前 v22 的范围泛化为所有 Node 版本，也不假定不同平台的文件系统、原生模块行为完全一致。

用权限清单表达最小需要

假设服务入口在 /srv/converter/app.mjs，输入来自 /srv/converter/inbox，输出只写入 /srv/converter/outbox。上线前可以列一张权限表：入口脚本与依赖读取属于启动需要；inbox 只读；outbox 可写；访问其他用户目录不需要；转换器若不调用 shell，就不授予创建子进程；若不使用 Worker，就不授予 Worker。启动命令再按 Node v22.23.5 的权限旗标语法，为这些路径和动作明确开通。

这是一个配置设计示例，没有在本文所处环境对真实转换项目执行，也没有证明每个依赖都能在该限制下启动。实际收紧时应该先在隔离的测试环境运行代表性任务，观察被拒绝的资源访问，再判断它是合理功能还是隐藏依赖。不能为了让进程“跑起来”就一次性授予整个主机目录的读写权；那会让最小权限失去作用。每次新增许可都应写明哪个代码路径需要它、怎样验证没有更窄的范围。

依赖为什么也改变信任边界？

进程权限按运行进程生效，而不是只针对你亲手写的入口函数。某个依赖被加载后，可以在它的执行路径上尝试使用进程拥有的能力。因此，清单里写“我们的代码只读一个文件”不足以得出“这个进程只会读这个文件”。依赖升级、可选插件启用和构建脚本变化都可能带入新的资源需求，应当跟随版本更新重新核对权限。

一个常见反例是给 CI 中执行的任意 Pull Request 代码加上写入部署目录和读取生产凭据的许可，然后以为 --permission 会阻止它利用所有可能的方式把数据带走。权限模型不是针对恶意代码的安全边界，不能据此放开凭据。真正不可信的贡献代码应与部署秘密、宿主机凭证和生产网络隔离；使用操作系统用户权限、容器或虚拟机时，还要检查挂载、内核能力、网络策略和宿主机接口。隔离强度由这些外部边界决定。

怎么验证收紧没有破坏所需功能？

将权限作为可审查配置，而不是一次性的启动技巧。记录 Node 精确版本、启动参数、允许路径和被拒绝的访问；用测试输入分别覆盖读取、写入、转换失败、临时文件以及需要子进程的可选功能。如果某项功能确实需要额外权限，先判断能否用受控接口替代，再授权对应目录或动作。权限查询 API 可以帮助运行中代码了解某个范围是否可用，但“返回允许”只证明策略状态，不证明业务代码安全。

验证也要覆盖负面路径：尝试读取范围外文件，预期应看到权限拒绝；尝试写到输出目录之外，也应失败；再运行实际需要的转换步骤，确认必要操作仍工作。测试样例和命令在本文没有执行，因此这些是建议的验收方案，不是现成的成功日志。生产落地还需以你的操作系统、Node 构建方式、依赖树和部署模型重复验证。

何时应选择外部隔离？

若你运行的是自有服务代码、依赖经过审查，主要担心路径错误或误触发子进程，Node 权限模型可以作为纵深防御的一层。若工作负载会执行用户脚本、插件市场代码、未知 npm 包或外部提交内容，就要从“最小权限进程”升级为“即使代码恶意也尽可能无法越界”的安全设计。后者通常需要操作系统和部署平台共同控制身份、文件系统、网络、资源上限与生命周期。Node 自身的限制不应替代这一层。

因此决策记录应该写清威胁模型：哪些代码被当作可信，哪些输入是攻击者控制的，进程能接触哪些主机资源，逃逸后影响是什么。把这些问题回答完，再决定是否启用 --permission、授予哪些范围，以及外部沙箱要负责什么。它很有用，但只有放在正确的信任边界内，才不会给人一种“陌生代码已经被关住”的错觉。

本文的配置和验证流程属于设计示例，没有声称执行过转换服务或生产环境验证。
