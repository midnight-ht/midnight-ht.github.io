Terraform for_each 改了 map key，为什么计划要重建云资源？

for_each 的 key 成为 Terraform resource address 的实例身份；改 key 默认表示旧实例离开、新实例出现，需用 moved block 或 state mv 表达重命名。

正文

核心要点

  • map key 或 set 元素写进实例地址，必须稳定且不能含敏感值。
  • 仅重命名 key 会产生地址变化，plan 可能提出销毁和新建。
  • 用 moved block 声明旧到新地址映射，并审阅 plan 后再 apply。

配置中的 for_each map key 或 string-set 元素会进入 resource address，作为某个实例在 Terraform state 中的身份。把 key 从 west 改成 us-west，即使配置指向同一个云资源，Terraform 也可能把它理解成旧地址消失、新地址出现，并计划销毁与重建。若变更只是重命名实例身份，要用 moved block 或受控的 terraform state mv 表达地址迁移，再审阅计划而不是直接 apply。

key 是地址的一部分，不只是循环变量

假设资源块定义 for_each = var.regions，map 中包含键 west 和 east。Terraform 会形成类似 aws_instance.worker["west"] 的实例地址；each.key 可以用于配置，each.value 带入该键对应的值。key 因此是状态定位合同：它必须在 plan 阶段已知，也不能来自敏感值，因为地址会出现在 plan、日志和 UI 输出中。

这也是 for_each 和 count 的主要运维差别。count 用整数索引，列表重排可能改变索引与资源对应关系；for_each 用集合键指向更具语义的实例身份。它并不意味着 key 可以随命名规范调整而无成本变化。地址用于把配置块与 state 中记录的对象匹配；名称变化会影响 Terraform 的资源寻址，而非仅仅改变展示标签。

for_each 输入还必须在远端资源操作开始前就可确定。若 key 依赖本次 apply 才创建的云资源 ID，Terraform 无法提前知道应建立哪些实例地址，计划会报出依赖未知值错误。impure 函数如 uuid、timestamp 也不能生成稳定 key；含敏感值的 map/set 不允许，因为 key 会被暴露。先用稳定的业务标识建 key，再把动态资源 ID 放在 value 属性中。

一个命名重构为何变成 destroy/create？

原配置有 regions = { west = {...} }，state 中对象地址为 aws_instance.worker["west"]。后来团队只将键改成 us-west。从当前配置角度看，它只剩 aws_instance.worker["us-west"]；state 仍登记旧地址。默认计划会将新地址视为尚不存在的对象、旧地址当作配置已移除的对象，因此计划可能提出 create 与 destroy。是否最终替换取决于资源和 provider 变化，但地址映射本身已改变。

Terraform v1.1 及更高版本支持 moved block，可以声明：

moved {
  from = aws_instance.worker["west"]
  to   = aws_instance.worker["us-west"]
}

下次 plan 会先检查 state 中旧地址，并将现有对象按新地址继续计算；move 本身不会销毁对象。它是 state 地址迁移声明，不会自动修改云资源名称，也不证明其它配置变更一定无替换。团队仍要检查完整 plan 里 provider 属性是否另外要求 replacement。Terraform 1.1 之前应使用 state mv 命令路径，并在使用前做好 state 备份和锁定。

如何区分身份变化和资源属性变化？

对于同一个远端对象，可以同时发生两种差异：实例 key 变化导致 state address 改名，或者实例配置属性变化导致 provider 更新/替换。moved block 处理前者；它不会屏蔽后者。将重命名和大规模属性升级拆成两个变更，plan 中先审阅 moved 的地址映射与对象保留，再审阅下一次属性变更，更容易判断是谁提出了 replacement。

反例是看到 plan 里既有 destroy 又有 create，就直接手工改 state 或在流水线自动 apply。destroy 可能来自地址没有迁移，也可能来自实例类型、网络或磁盘属性确实不可原地更新；两种情形风险不同。还要确认不同 workspace、模块调用和环境的 key 命名一致，不能只为一个 workspace 添加映射，却让另一个环境仍把地址解释成新资源。

验收实例重命名而不误删对象

在可丢弃的测试 workspace 中先用固定 map key 创建资源，保存 terraform state list 与完整 plan；修改 key，先不执行 apply，观察地址变化带来的默认计划。加入 moved block 后再次 plan，检查输出是否显示地址 move、是否仍计划替换远端资源，并核对 state 中对象 ID。然后在另一个测试分支故意变更一个不可原地更新的 provider 属性，确认 move 与属性替换出现在计划的不同部分。

对生产变更，把 from、to 地址、workspace、模块路径、对象 ID、计划文件和审批提交绑定记录。移动声明要保留在共享模块中，直到所有使用者完成迁移；HashiCorp 文档提醒移除 moved block 属于破坏性变更，旧配置使用者可能重新看到 destroy。本文未运行 Terraform 或操作云资源，这些步骤是建议验收方案，不是实际 plan 记录。

如果 key 真的代表资源重新分配，而非展示名称变化，那创建新对象并删除旧对象可能是正确计划；例如对象所有权、网络隔离或生命周期确实改变。若只是更稳定的命名或标签调整，则应把地址迁移表达清楚。对每次 key 变更都问：state 中的同一个对象还应该继续由新地址管理吗？回答“是”时，用显式迁移保持身份连续性；回答“否”时，先验证替换影响再执行。

从 count 转成 for_each 要逐实例映射

将 resource.example[0]、[1] 迁移为 resource.example["api"]、[worker"] 时，不能只把 count 改成 map。每个旧索引都应映射到对应的新 key；映射错位可能让 state 把 API 实例交给 worker 配置。先从当前 state 和业务清单建立旧地址到新地址的逐项表，在测试 workspace 加入相应 moved 声明，再审阅完整 plan，确认对象 ID 与实例角色一一对应。还要检查是否有索引实例已不存在、是否有新 key 没有旧地址，以及模块路径是否同时改变。只有当状态映射与现实资源身份相符时，地址迁移才安全；自动按列表顺序生成映射并不能证明业务对应关系正确。

迁移记录最好保存旧地址、新地址、state 中的远端对象 ID 和 plan 文件摘要。复核者可以据此确认不是把两个相似实例交换身份，也能在 apply 前检查配置分支是否含有迁移声明。对多个 workspace，应为每个 workspace 单独保存计划与映射验证；同一 HCL key 并不证明每个环境中的旧对象角色完全一致。本文没有生成真实 plan，提到的映射表是验收设计。

在执行迁移前，逐项比对 terraform state list 中的旧地址、业务资产清单里的对象用途与新 map key；名称相近并不能证明两个对象身份相同。先在一个 workspace 验证，再按环境复制映射并保留各自的 plan 作为审批材料。
