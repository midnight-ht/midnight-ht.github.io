指标图上看到尖峰，却找不到请求：OpenTelemetry exemplar 连接了什么？

Exemplar 是附在指标数据点上的一次代表性观测，可带 trace_id 和 span_id 帮助从聚合指标跳到 trace；它不增加每个请求都要存储的 span。

正文

核心要点

  • Exemplar 关联单个代表性指标观测与上下文，直方图统计仍包含其值。
  • Trace exemplar 必须有可用的 trace/span context，且导出、存储与查询端都要支持。
  • exemplar 是抽样诊断线索，不是每个指标样本都有完整 trace 的保证。

指标图上看到延迟尖峰却找不到对应请求时，OpenTelemetry exemplar 可以把一个被选中的指标观测值与当时的 trace 上下文连接起来。Exemplar 是指标数据点携带的代表性观测，可包含时间、观测值、过滤属性，以及可选的 trace_id 和 span_id；它不是给每个请求都额外生成一个 span，也不保证每个指标点都有 trace。

为什么需要从聚合数值跳到单次请求？

直方图告诉你一段时间内请求时长的分布：bucket count、count 和 sum 适合回答“尾延迟有没有变差”“发生了多少次”。但聚合值本身不能指出哪个请求经过了慢 SQL、哪个用户上传了大文件，或某个下游连接超时。若把所有请求都留成 trace，诊断会更直接，但采样、存储、索引和隐私成本也会上升。

这种记录在两种信号之间保留稀疏关联。采集指标时，SDK 可以记录某次观测的数值，并附加当时 span 的 trace ID 和 span ID。后端在展示直方图时，用户可从某个 bucket 或时间点跳转到对应 trace。OpenTelemetry 规范将它定义为 Metric 内与一次测量关联的记录；对直方图而言，exemplar 的值已经包含在 bucket_counts、count 和 sum 中，不能再把它加一次，否则总量被重复计算。

这个关联让团队可以把“整体哪个方向变差”与“单个样本发生了什么”分层排查，而不必把每个 request 的完整属性都放进高基数 metric label。记录中的 filtered_attributes 可补充观测时上下文，但要审查其中是否含用户 ID、请求参数或凭据。关联 trace 也受采样和导出链路影响：指标里留了 ID，并不保证查询系统仍保存着对应 trace。

一个慢请求如何留下可点击的关联？

假设服务记录 http.server.request.duration 直方图。请求正在活动 span 中运行，SDK 按 exemplar filter 选择一个测量，并把其持续时间和 trace context 附到对应指标点。指标导出器需要保留 exemplar；接收端和存储后端需要支持该数据；图表界面还要把 trace ID 链接到相同环境、租户隔离域与时间范围的 tracing backend。任何一环丢字段或换了 trace 存储地址，用户都会看到指标尖峰，却无法完成跳转。

指标数据模型明确，exemplar 包含 recorded value、观测时间、过滤属性以及可选 trace/span IDs。若 trace context 不可用，exemplar 仍可能存在为数值观测，但它不再具有 trace 导航能力。若样本关联到 trace，却被 head sampling 丢弃，链接仍可能无法解析。团队应区分“没有选中 exemplar”“有 exemplar 无上下文”“有 ID 但 trace 未保存”和“后端/UI 未连通”，不要把它们都归为指标采集失败。

抽样规则不等于指标采样率

Exemplar filter 决定哪些测量成为 exemplar，指标 SDK 的 aggregation 决定如何汇总测量，trace sampler 决定 span 是否被保留；这是三个不同控制面。提高 exemplar 数量不会自动提高 trace retention；保留更多 trace 也不意味着每个指标观测都会被标为 exemplar。OpenTelemetry 规范定义数据模型，而具体 filter 的策略和实现支持取决于语言 SDK、版本和 exporter。

例如，团队可以选择 trace-based filter，只在存在有效 trace context 时保存 exemplar。这样有助于从指标深入 trace，但在无活动 span、异步上下文丢失或采样限制时仍会缺少关联。另一策略可能强调异常或高值测量，但不能假设所有 SDK 以同一算法选择。配置之前查看语言 SDK 文档并用已知 trace ID 的请求做端到端实验。本文没有部署 exporter、后端或仪表盘；这里是基于规范的设计判断，不是实际截图或性能结果。

验证连接链，而不是只检查指标数值

在测试环境发出带已知 trace ID 的请求，观察指标点是否出现 exemplar，检查其时间和值是否与直方图数据对应，并在后端跟踪系统中搜索同一 trace ID。再发一个没有活动 span 的测量，确认指标统计仍在，而 trace link 缺席的原因被理解。将 trace 采样、指标导出失败、后端过期和错误环境标签分别作为负向测试，记录何处丢失关联。

监控成本时，比较 exemplar 占用、metric cardinality 和 trace retention，而不是把它宣传为“免费获得全量请求追踪”。不要将 trace ID、span ID 放入普通 label；那会把每个请求都变成高基数序列。这种设计的价值恰在于保留少量样本的跨信号连接，同时让聚合指标继续承担趋势与告警职责。

最后验证查询界面能否在相同项目、region、service 和时间窗内打开关联 trace，并检查权限隔离是否一致。可见一个 trace ID 不代表查询者自然有权访问 trace 内容。Exemplar 是排查路径的入口，不是访问控制、保留策略、追踪完整性或告警规则本身。将关联成功率、 trace 缺失原因和后端查找时延列为独立验收项，才知道信号链是否真的可用。

采集链路的验收要拆成可定位的断点

落地时可以把一条 exemplar 的路径画成四段：SDK 观察测量并选择样本、metrics exporter 编码、collector 或接收端转发、查询界面解析 trace 标识。每段都需要独立验收，而不是只在最终仪表盘里看一眼。比如在测试服务中给某条请求附上固定 trace context，记录其延迟值，然后检查导出的 metric payload 是否仍包含 exemplar；接着检查经过 collector 后 trace/span 标识是否保留；最后验证链接指向预期的 tracing 数据源。规范定义了字段模型，具体 exporter 是否传递、后端是否索引则属于实现与配置问题。

失败路径也应有区分：exemplar filter 没选中样本时，聚合分布仍正常；测量被选中但当时没有有效 span 时，可能没有 trace ID；有 ID 但 trace sampler 未保存该 trace 时，链接会成为不可解析的指针；数据源环境名不一致时，ID 可查但落到错误租户或集群。为每类情况设置可观测计数或测试断言，比把“点击无结果”统称为 tracing 故障更容易处理。这里描述的是建议的验收设计，并非对某个 collector 的实测。

选择 exemplar 策略时还要把隐私和抽样偏差纳入判断。附加属性并非免费上下文：用户标识、查询参数和租户 ID 可能进入长期保留的指标存储。高延迟优先的 filter 会让尾部样本更容易被观察，但并不能代表总体分布；随机或 reservoir 策略又可能在低频异常发生时刚好没有留下样本。应先明确要回答的是“慢样本如何走到这里”还是“总体请求是什么比例”，再决定 exemplar 的筛选和 trace 保留策略。前者依赖稀疏导航线索，后者依赖指标聚合本身，二者不能互相替代。
