CRD YAML 提交成功，字段却消失：先检查结构化 schema 的裁剪

apiextensions.k8s.io/v1 的 CRD 需要结构化 schema；未声明字段默认可能在 API server 持久化前被裁剪，保留未知子树必须显式设计并测试。

正文

核心要点

  • kubectl 接受对象不代表 API server 会持久化未声明字段。
  • CRD 默认裁剪 schema 未识别字段，v1 要求结构化 schema。
  • 保留任意 JSON 只适用于明确配置的子树，并会影响 CEL 可见性与后续字段验证。

Kubernetes CRD 的 YAML 提交返回成功，并不保证每个输入字段都存进 etcd。对于带结构化 OpenAPI schema 的自定义资源，API server 会按 schema 校验对象，未声明的字段默认可能在持久化前被裁剪。排查“字段写进 YAML 却从 GET 结果消失”，先比较客户端发送对象、CRD schema 和 API server 返回对象；不要先怀疑控制器把字段删了。

从客户端对象到持久化对象，中间有 schema 边界

假设一个 CronTab 自定义资源需要 spec.schedule 与 spec.image，CRD schema 只声明了这两项。客户端提交对象时额外写入 spec.retryPolicy，kubectl 可能先依据集群公开的 OpenAPI schema 拒绝未知字段；若使用 --validate=false 绕过客户端校验，API server 仍会根据 CRD 的 schema 对象执行服务端验证和裁剪。官方示例展示了 someRandomField 在创建结果中消失。

这使得“命令退出码为零”“请求通过 schema”和“期望字段已持久化”成为三件不同的事。客户端版本、验证开关、CRD 版本与对象版本都影响观察到的错误位置，但关闭客户端验证不会关闭 API server 行为。最可靠的诊断是将同一个对象发出前的 JSON/YAML 与 kubectl get -o yaml 的返回值比较，并查看当前生效的 CRD openAPIV3Schema。

为什么默认裁剪通常比随意保留安全？

结构化 schema 给 Kubernetes 和控制器提供可读的字段形状：类型、嵌套结构、列表语义和校验条件。未知字段如果被无条件保存，拼写错误可能静默进入集群，控制器却仍按默认值运行；版本升级时，旧的任意字段也难以判断由谁维护。默认裁剪让 API 边界的“声明过的合同”与可持久化数据更接近，并尽早暴露 schema 与作者意图之间的分歧。

但裁剪也可能毁掉有意设计的扩展字段。例如 operator 需要在 spec.providerConfig 保存云厂商定义的任意 JSON。Kubernetes 支持在结构化 schema 的明确子树设置 x-kubernetes-preserve-unknown-fields: true，从该节点起保留未知结构；若子树里再次声明 properties 或 additionalProperties，这些已声明部分会重新进入 schema 处理。这个标记不是全局“关闭验证”，类型约束与其它声明仍需按实际 schema 阅读。

保留未知内容还有边界：官方文档指出，保留的未知字段不能被 CEL 表达式访问。若团队同时希望任意扩展和基于 CEL 的字段规则，必须重新设计数据形态，例如把不透明扩展放在有限、明确的 JSON 字段下，把需要校验的业务字段声明成结构化属性。不能预设“API server 存得下”就意味着 admission、策略和控制器都能理解它。

一个字段为什么在提交后不见了？

具体排查可以按时间线进行。首先查看客户端实际发送的资源对象和 apiVersion；其次查看 CRD 的 spec.versions[].schema.openAPIV3Schema，确认字段位于哪个对象层级，是否被 schema 声明，是否处于 preserve-unknown 子树；再用 kubectl get <resource> -o yaml 读取服务端对象。若命令报告未知字段，可能是客户端验证阶段；若关闭客户端验证后命令成功但字段未出现在服务端对象，则检查服务端裁剪和实际 CRD 版本。

对于多版本 CRD，还应确认转换 webhook 和 storage version。某个版本中的字段有 schema，不表示另一个版本中的字段也存在；版本转换代码也可能丢弃不能表示的数据。CRD 更新后的既有对象与新创建对象要分别测试：schema 变更影响服务端后续读写行为，但已有数据迁移和转换结果取决于具体版本与存储过程。以上是需要在目标集群中验证的路径，并非本文执行过的 kubectl 实验。

反例是因为字段在 GET 中消失，就在整个 spec 上加入 x-kubernetes-preserve-unknown-fields: true。这会让拼写错误和不受控配置更难被 API schema 发现，并可能让 CEL 规则无法检查扩展区域。应先确认哪些字段确实由外部系统定义，再把不透明部分放在最小子树；其余字段继续声明类型和校验。CRD schema 是 API 合同的一部分，结构化程度越高，客户端校验、审查和升级越容易做确定性验证。

验收时测试“字段保留”与“错误被发现”两条路径

在测试集群准备一个含已声明字段和故意拼错字段的样例对象。使用普通客户端验证观察 schema 错误，再用 --validate=false 仅用于定位服务端行为；读取最终对象，记录哪些字段被拒绝、哪些被裁剪。接着在专门的 preserve-unknown 子树中提交相同结构，确认保留范围只覆盖预期字段，并确认其他字段仍受类型约束。若使用 CEL，再对未知子树做规则测试，验证不会把不可见字段当成可校验字段。

发布 CRD schema 变更时，比较新旧版本字段路径、默认值、列表合并语义、转换行为和 CEL 表达式；选择代表性老对象做读取与写回测试。仅看 CRD 文件语法通过或某个 kubectl apply 成功，不足以确认字段合同兼容。清楚地区分客户端拒绝、API server 裁剪、转换丢字段和业务控制器覆盖，才能找到实际责任层。

还应区分“未声明字段被裁剪”和“声明的字段校验失败”：前者可能让创建请求成功但返回对象缺少属性，后者通常让 API server 拒绝整个写入。客户端本地验证更早失败时，也不能据此推断服务端存储行为。排障记录保留发送对象、API 响应、服务端读回对象、CRD 的 resourceVersion 与 schema 版本，才有条件复现差异。对于外部控制器生成的对象，检查其实际发送的 API 版本，而不只是仓库里的模板。

对于需要在未来版本结构化某个原先不透明的子树，升级也需要分阶段。先盘点已存对象中这个子树实际出现的键，再发布带有明确属性的 schema 和转换逻辑，验证旧写入方是否仍提交额外字段；过早收紧会使后续写入失败或让字段被裁剪。若服务端转换 webhook 读写多版本对象，应在同一变更中检查它能否保留新字段。这样的兼容性清单不是只对 schema 做静态 lint 就能替代的。
