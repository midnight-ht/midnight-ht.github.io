SQS 心跳续租能减少抢重消息，但十二小时上限不会重置

SQS visibility timeout 是暂时隐藏消息的租约式机制，不是处理锁；续租仍受首次 ReceiveMessage 后十二小时上限约束，消费者要为重复投递和慢重试设计。

正文

核心要点

  • 处理超时会重新让消息可见，无法证明第一次消费者已停止。
  • 周期性 ChangeMessageVisibility 只能延长租期，不能把十二小时期限重新起算。
  • 先提交可恢复的业务状态，再删除消息，并为重复投递保留幂等路径。

Amazon SQS 的 visibility timeout 会在消费者收到消息后，暂时让它对其他消费者不可见；它不会锁住消息，也不会证明原消费者还活着。任务处理超过超时时间后，消息可以重新出现并被另一个消费者取走。ChangeMessageVisibility 可按处理进度续租，但从第一次 ReceiveMessage 开始计算的十二小时上限不会因为续租而重新计时。长任务因此必须同时考虑重复执行、慢重试和硬性最长处理时长。

过短和过长分别制造什么问题？

假设消费者从 SQS 收到一个需要调用外部渲染服务并写入归档的任务，预计通常两分钟完成，偶尔需要十分钟。如果初始可见性超时只有三十秒，原消费者还在等待渲染时，消息就可能重新可见，第二个消费者也开始执行。两个任务可能争用同一个对象，重复写入或重复触发下游计费。这不是消息丢失，而是租期短于实际工作时间导致的并行重投风险。

相反，如果给每条消息配置十二小时超时，但消费者在一分钟后崩溃，恢复任务可能要等很久才再次可见。大超时减少了“活着的慢消费者”被误判的机会，却延长了故障恢复等待时间。标准队列的交付本来就可能重复；visibility timeout 不是恰好一次锁。设置值要联系任务耗时分布、下游幂等能力和重试时效，而不是只看平均处理时间。

心跳续租能延长多久？

如果处理耗时难以预测，可以先设一个较短的初始可见性时间，再由仍在工作的消费者周期性调用 ChangeMessageVisibility。例如，每分钟检查处理状态并把剩余可见性延长到两分钟，可减少一项仍在推进的长任务被过早重投。这个数字只是解释机制的假设例子，不是 AWS 推荐所有业务照搬的参数，也没有在真实队列上执行。

续租的计时边界容易误解：SQS 文档规定，最大可见性时间从队列首次收到 ReceiveMessage 请求时起最多十二小时；连续更改不会把这个上限重新起算。网络排队、处理器启动和续租调用自身的延迟，也会占用可用时间。如果预计工作可能超过该上限，应拆成可恢复的小步骤，或使用能表达长流程状态的编排服务，而不是每分钟续租并假定期限会无限延长。

心跳自身也可能失败。进程暂停、网络不通、权限被撤回或 AWS 调用超时，都会让租约没有按计划延长。此时另一个消费者可能开始处理，而第一个消费者尚未意识到租约已失效。应用应为同一业务键准备并发处理防护，记录最近一次成功续租时间，并在越过内部安全余量后停止发起新的不可逆副作用。单靠本地定时器显示“还在工作”，并不能证明 SQS 已接受续租。

若单项工作确实无法在十二小时内结束，应把一个不可中断的大任务改成带持久检查点的阶段。每完成一个阶段就提交可恢复状态，再开始下一段；重启后从最后确认的阶段继续。AWS 文档将拆小任务或使用 Step Functions 作为超过上限时的考虑方向。这样改变的是工作模型，而不是试图把有限租约伪装成无限锁。

还有一个边缘情况：首次收到消息后立刻把单条消息的可见性设置成完整十二小时，也可能因为 ReceiveMessage 到续租请求之间已经过去的时间而被拒绝。十二小时是从接收请求开始计算的上限，不是每个 ChangeMessageVisibility 请求都能独立拿到的新额度。续租器需要按服务返回值判断成功，并为请求延迟留余量；不要只把参数填成最大数值就当作延长期限成功。

业务状态应该先提交还是先删消息？

若消费者先删除消息、之后才提交数据库状态，提交失败会造成消息已移除但业务结果不存在。若先提交业务结果、之后删除消息，删除请求失败或响应丢失时，消息可能重投，消费者需要辨认结果已经存在。后者通常更容易构造恢复流程：把事件 ID 和业务变更放入同一事务，提交成功后再删除；重投时查到已完成记录，就跳过重复副作用并再次尝试删除。外部 API 若支持幂等键，应把同一个事件身份传递下去。

这里仍有边界：数据库记录与外部付款、邮件发送不在同一个本地事务里；如果外部服务既不支持幂等键也不提供查询凭证，系统不能只靠 SQS 顺序消除“对方已执行但本方未收到响应”的不确定性。应使用 outbox、下游幂等接口或人工对账策略。visibility timeout 只管理再次可见的时机，不负责分布式业务原子性。

怎么验收续租和故障恢复？

在非生产队列验证一条短任务、一条超过初始超时的任务、一次续租 API 失败、消费者中止、副作用提交后进程退出、十二小时边界以及死信队列路径。观察消息是否再次可见、重复处理是否被业务幂等层吸收、DLQ 是否保留了足够诊断信息，并对照 AWS 请求结果而不是本地心跳日志判断续租是否成功。故障测试应清楚区分“第一次消费者已经退出”和“只是在当前监测时间内没有进展”。

本文未创建队列或运行 AWS 请求，上述项目是验证清单，不是执行结果。部署前还需核对队列级默认值、消息级覆盖、SDK 是否自动删除消息、接收请求开始时间、队列并发额度与可见性策略。将 visibility timeout 看作有限租约、而非排他锁，才能同时为正常慢任务和异常重投留出正确路径。

可观测字段应包含接收次数、消息的 receive timestamp、每次续租请求及响应、业务处理阶段和删除消息结果。单看队列的可见消息数量，很难区分消费者积压、处理太慢、续租失败与消息反复重投。若处理器进程在完成数据库副作用后、删除消息前崩溃，下次投递仍会重复执行；可见性窗口不能消除这个故障区间。应把消费幂等记录和业务事务放在一起设计，并在消息删除失败时保留可追踪的重复处理证据。
