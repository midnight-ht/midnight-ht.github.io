kubectl debug 能往运行中的 Pod 加容器，为什么还要单独授权？

Kubernetes ephemeral container 通过 pods/ephemeralcontainers 子资源加入既有 Pod；能 patch Pod 并不必然等于能执行这个诊断操作。

正文

核心要点

  • 临时容器用于排障，不能替换现有容器，也不能修改 Pod 的普通 spec。
  • 添加临时容器走 pods/ephemeralcontainers 子资源，RBAC 要授权该子资源。
  • 诊断镜像和权限会进入既有 Pod 的安全边界，应记录操作人与镜像并清理关联风险。

kubectl debug 可以为正在运行的 Pod 增加 ephemeral container，用来观察没有 shell、工具或已崩溃主容器的工作负载；但这项能力不是普通的 Pod patch 的自然延伸。Kubernetes 通过 pods/ephemeralcontainers 子资源处理添加操作，用户还需要针对这个子资源的权限。把“可更新 Pod”与“可注入诊断容器”分开授权，可以避免宽泛调试能力悄悄扩大到普通部署权限之外。

临时容器改变的是现有 Pod，而不是替换它

普通容器随 Pod 创建，Deployment 等工作负载控制器会用新 Pod 替换旧 Pod；ephemeral container 是在 Pod 创建后追加的诊断容器。它适用于 distroless 镜像缺少 shell、容器启动后快速崩溃而 exec 无法进入等情况。它共享目标 Pod 的部分命名空间能力，可观察现有进程或网络，具体效果取决于调试配置和运行时权限。它不是常驻 sidecar，也不是另一个独立工作负载。

ephemeral container 的生命周期受限制：不能像普通容器一样从既有 Pod 删除，也不能通过更新它来修正镜像或命令；通常需要创建新的 Pod 才能回到不含诊断容器的状态。它不会加入 Pod 的普通容器列表语义，也不能配置端口、探针等常规容器字段。调试命令成功后留下的容器可能与 Pod 一起持续存在，直到 Pod 被替换，因此“排障结束”并不一定意味着对象立即恢复原样。

RBAC 权限为何单独存在？

官方文档说明，添加临时容器通过 Pod 的 ephemeralcontainers 子资源发出更新请求；仅允许 patch Pod，不会自动授权添加临时容器。这个子资源也不在默认面向用户的 admin 和 edit ClusterRole 中。管理员需要明确授予相应的 patch，通常还包括 update verb，作用资源限定为 pods/ephemeralcontainers。具体权限应以集群版本的 RBAC 规则和实际请求验证。

这个设计把诊断能力变成可审核的动作，而不是把 debug 看成无副作用的命令。临时容器镜像会在目标 Pod 的身份、网络、卷或共享进程命名空间边界下运行；如果镜像含额外工具或执行内容不可信，注入行为本身就有安全影响。拥有这项权限的人也可能观察敏感进程信息，或在共享上下文中访问本来不提供给普通调试账号的资源。应限定命名空间、主体、时间范围和镜像来源，必要时记录审批和审计事件。

选择调试方式前先确认要观察什么

如果只是查看应用日志或容器环境，kubectl logs、事件和受控指标通常不需要改变 Pod。若主容器仍运行且包含 shell，kubectl exec 可能足够，但它依然需要 pods/exec 权限。若容器持续崩溃或镜像刻意不含工具，临时容器能在原 Pod 生命周期中提供诊断环境。若需要调试节点、网络策略或 sidecar 交互，应先确定需要共享哪些命名空间和权限；不要仅为了方便就给临时容器 privileged 或主机挂载能力。

调试配置会影响诊断结果。例如，--target 可尝试让临时容器加入目标容器的进程命名空间，但其行为取决于容器运行时是否支持相应功能；若不支持，调试容器可能仍启动，却看不到预期进程。故障排查记录应保留集群与运行时版本、完整脱敏后的调试参数、诊断镜像摘要、权限拒绝或成功响应，以及观察目标。本文没有在集群执行 kubectl debug；这里描述的是官方机制与建议的验证项，不是实际命令结果。

怎么验证最小授权和清理边界？

在测试命名空间用一个无生产数据的 Pod 验证：普通的 get/logs 权限能否完成基础查看；只有 pods/patch 而无 pods/ephemeralcontainers 时，调试请求是否被 RBAC 拒绝；授予子资源的限定权限后，预期的 kubectl debug 操作是否成功；无权访问其他命名空间的主体是否仍被拒绝。再验证诊断结束后，团队如何识别遗留临时容器，以及通过替换 Pod 回到期望模板状态。

反例是把 patch pods 直接授给所有开发者，因为他们“需要偶尔排障”。普通 Pod patch 还允许修改更多字段，范围可能大于注入一个临时容器所需。另一个反例是允许任意镜像来源，然后默认其只读、无害；工具本身可以与目标工作负载共享运行上下文。将权限单独限定到 pods/ephemeralcontainers，采用审核过的短期调试镜像，并把操作人与目标 Pod 绑定到审计记录，能让诊断能力和普通应用发布权限保持可区分。

这种调试容器解决的是如何在特定运行容器中补上观察工具，不解决应用故障原因，也不等价于隔离环境。RBAC、镜像可信度、运行时 namespace 支持和 Pod 生命周期都要同时核验。只有当团队知道要观察什么、调试容器能看到什么、结束后怎样恢复，kubectl debug 才成为受控的排障手段。

控制器和准入层也要纳入验证。调试文档还提醒，某些 admission policy 或 webhook 可能没有检查 ephemeralContainers 字段；如果它只审普通 Pod 创建与更新，子资源请求可能没有经过团队预期的容器镜像或安全上下文校验。将调试子资源纳入相应准入检查，并对照 Pod Security admission 的 profile 测试，是最小授权之外的另一道边界。否则 RBAC 允许的操作可能仍超出镜像治理策略。

操作后的复核可以读回 Pod 的 spec.ephemeralContainers，核对名称、镜像和安全上下文是否与获批请求一致，再检查事件与审计日志里对应的子资源请求。用户界面显示“debug 成功”只说明客户端流程完成；若团队的 webhook 未观察该子资源或 runtime 不支持进程共享，实际可观察范围仍可能与预期不同。需要把配置值和运行时观察结果分开记录，不要从容器已创建推断诊断目标已被看见。
