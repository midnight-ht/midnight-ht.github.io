S3 分段上传返回的 ETag 为什么不能当成整文件 MD5？

S3 multipart ETag 标识组合对象，却不保证等于整文件 MD5；应在创建上传时选择 checksum 算法与 full/composite 类型，再按存储的校验值验证完整性。

正文

核心要点

  • 分段对象 ETag 不是整对象 MD5，不应直接拿它比较本地文件摘要。
  • multipart checksum 可选择 full object 或 composite，算法支持范围不同。
  • 上传发起时声明算法，并在完成和下载验证路径核对实际 checksum。

Amazon S3 multipart 上传完成后返回的 ETag 可以标识组合对象，但不能普遍解释为整个对象字节的 MD5。AWS 文档明确说明，multipart 上传产生的对象 ETag 不是整文件 MD5，与加密方式无关；单次上传时 ETag 在特定条件下才可能等于对象 MD5。若要验证大文件完整性，应显式选择 S3 支持的 checksum 算法和校验类型，并确认 checksum 在上传时被服务端验证、保存，随后能在读取时用于核对。

一个三段文件为什么容易误验？

假设本地文件拆成三个部分分别上传，客户端从 CompleteMultipartUpload 响应取得一个 ETag，例如外观上可能包含引号和连字符。直接对原始整文件运行 MD5，然后与这个 ETag 字符串比较，可能不相等；这不自动证明上传损坏。对于某些上传方式，ETag 由各部分的摘要信息组合而来，而不是对完整拼接对象直接做一次 MD5。AWS 还说明，对于 multipart 上传，ETag 不会是整个对象的 MD5，无论使用哪种加密方式。不能将某次 SSE-S3、小文件或单段对象上的经验外推到分段上传。

同时，ETag 可以作为对象版本表示的一部分，帮助识别对象内容是否改变，但不等于通用完整性协议。对象元数据变化和对象字节变化也不是一回事；仅因 ETag 看起来像十六进制串，就把它当成“可信强哈希”使用，容易把缓存标识、并发条件与传输完整性检查混为一个合同。先定义要验证的是哪个属性：每段传输未损坏、最终对象等于期望字节、对象是否发生变化，分别需要可验证的字段与流程。

full object 与 composite checksum 有什么不同？

S3 multipart checksum 支持 full object 和 composite 类型，但并非每个算法都支持两种类型。当前文档列出 CRC-64/NVME 可用于 full object 而不支持 composite；CRC32、CRC32C 可用于两者；SHA-1、SHA-256、MD5 与若干 XXHash/SHA-512 算法只支持 composite。Full object checksum 代表完整拼接对象的校验值；composite checksum 则由分段校验信息组成，不能一概当作普通整文件摘要。验证系统应保存算法名称、校验类型和对象版本等上下文，不能只存一串没有解释的字符。

使用 multipart API 时，发起上传阶段应指定 checksum 算法和类型，再对每段提供该算法的校验信息。AWS 文档特别提醒，对较新的 checksum 算法，如果只在 CompleteMultipartUpload 提供校验头，却没有在 CreateMultipartUpload 指定算法，完成请求会失败；一些既有算法在未于发起时声明的情况下，完成阶段提供的校验值可能不被验证或保存。安全做法是从上传启动就建立校验合同，避免误以为最后一个请求带了值便完成了服务端验证。

把全对象校验作为需求时，完整流程可以这样定义：上传前从原始文件计算所选 full-object checksum，将算法、类型、期望值和对象 key 绑定到同一任务记录；创建 multipart upload 时声明支持该组合的算法和校验类型；各段上传成功后保存 part 编号和响应；完成后读取对象所保存的 checksum 字段，与任务记录中的算法和期望值核对。如果计算值不匹配，S3 会以校验错误拒绝完成，而不是让系统把有疑问的对象标记成功。该流程仍要按所用 SDK 的字段支持实际验证。

如何把现有的 ETag 比较迁移为校验合同？

假设原系统把本地 MD5 与 S3 ETag 字符串相等当作上传成功条件。迁移时可以为上传任务增加期望的 checksum 算法、值、类型和对象 key；启动 multipart 时声明该算法，逐段上传并收集响应中的部分状态，最后完成上传。随后调用对象元数据读取接口，核对服务返回的 checksum 字段与预期算法和类型一致。对于下载检查，再按保存的校验算法验证读回的字节。这个流程需考虑 SDK 版本、checksum 字段是否请求返回、multipart checksum 组合规则与对象加密方式，不能仅仅替换字段名。

一个反例是选了 SHA-256 composite，却把它与本地整个文件的一次性 SHA-256 直接相等比较。Composite checksum 的含义不同；如果需求是整文件 SHA-256，而算法不支持该上传类型的 full object 校验，就应设计另外的全对象校验路径，不能重命名 composite 值掩盖差异。当前文档对 CRC-64/NVME 提供 full object 路径，选择时仍需考虑客户端 SDK 和接收流程支持。

旧对象若没有保存所需的 checksum 元数据，也不能仅凭 ETag 相似或不同就回填“已验证”状态。可在数据清单中把它标成校验证据不足，再根据风险选择重新下载计算、与可信来源摘要比对，或重新上传并建立新合同。这个状态分类是迁移中的保守判断，不代表旧对象必然损坏；它只避免把没有证据误说成通过完整性检查。

保存“未验证”原因，后续迁移才可复查。

如何验收一次上传？

在测试桶用固定字节输入，分别覆盖单次 PUT 和多段 multipart；记录上传发起时声明的算法、类型、各段 checksum、完成响应和后续对象 checksum 字段。人为修改一段字节、交换段号或让完成请求缺少某一段，确认错误路径能阻止对象被错误标记为已验证。再验证加密方式、SDK 升级和旧对象没有 checksum 元数据时，系统会如何分类，而不是用 ETag 猜测。

本文未创建 S3 桶或运行 CLI/SDK；输入和步骤是设计验收方案，不是执行日志。最终规则要以当前 AWS 文档、SDK 行为和实际上传协议为准。把 ETag 当对象标识线索，把明确声明的 checksum 当完整性证据，并保留算法与校验类型，能避免将表面相似的十六进制字段当成同一含义。

并发覆盖也要绑定版本身份。假设流程完成上传后读取 checksum，但同一 key 紧接着被另一个任务覆盖；如果读取未指向此次上传的对象版本，系统可能把后来对象的摘要误当成刚完成任务的证据。任务记录应保存完成响应中的版本信息（桶版本控制状态会影响可用字段），后续验证再对准同一版本。算法选对了仍不够，证据也必须对应正确对象。
