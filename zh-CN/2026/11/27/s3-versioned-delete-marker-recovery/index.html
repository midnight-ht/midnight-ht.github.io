版本化 S3 对象 DELETE 返回成功，为什么旧文件还在？

启用版本控制的 S3 桶中，不带 versionId 的 DELETE 通常创建 delete marker，让对象表现为已删除；恢复要精确移除当前 marker，永久删除旧版本则是另一项操作。

正文

核心要点

  • 版本化桶中的无版本号 DELETE 通常新增 marker，并不抹除以前的对象版本。
  • 要恢复对象，应识别并删除当前 delete marker 的 versionId。
  • 不带 versionId 再删一次可能再创建 marker，版本生命周期规则也会永久删除非当前版本。

在启用版本控制的 Amazon S3 桶里，不带 versionId 的 DeleteObject 通常不会永久抹掉已有对象版本，而是创建一个新的 delete marker，让普通 GET 看起来像对象已删除。恢复时要先找到当前 marker，再明确删除它的版本；对同一个 key 再发一次不带版本号的 DELETE，可能只会创建第二个 marker。删除“当前可见对象”和永久清除历史版本是两种不同操作。

Delete marker 改变当前视图，不是对象内容

对象版本控制启用后，同一个 key 可以有多个版本。无版本号删除在当前版本前放入 marker，使普通读取不再返回旧内容；旧版本仍可能保留，并继续占用存储。marker 本身也有 version ID，作为该 key 的一个当前版本。S3 返回成功说明删除请求被接受，不代表此前的字节数据已经物理清除。

这解释了控制台、API 和应用日志之间常见的误读：控制台的对象列表可能不再显示 key，HEAD 或 GET 返回 404，但按历史 version ID 查询仍能找到以前的数据。此时“用户不可见”成立，“数据永久删除”不成立。若合规要求是不可恢复地销毁，必须考虑旧版本、复制目标、备份、Object Lock 保留期和生命周期规则，不能仅凭一次 DeleteObject 事件判断删除完成。

恢复操作必须针对 marker 的版本号

先通过版本列表找到该 key 的版本序列，确认最新条目是 delete marker，并记录其 version ID；再对该 key 发起带此 version ID 的删除请求。marker 被移除后，较新的非 marker 版本重新成为当前版本，普通 GET 会返回该对象。恢复不是把旧版本复制成新对象，也不是撤销整个桶上的版本控制开关。

陷阱在于再次调用不带 version ID 的 DELETE。AWS 文档指出，如果当前版本本身是 delete marker，这个请求不会删除它，而会再 PUT 一个新的 marker。于是列表里 marker 数量继续增加，对象仍返回 404。版本 ID 为 NULL 的 marker 还有特例：请求必须显式传 NULL 才能删除该 marker；未传版本 ID 时可能创建另一条带唯一 ID 的 marker。恢复脚本若只按 key 删除而未读取版本状态，可能重复制造“删除记录”。

删除数据与撤销隐藏的状态不同

永久删除某个具体历史对象版本时，应向 DeleteObject 指定那个对象版本的 versionId。删除 marker 只是让较老版本重新可见；它不自动删除那些较老版本，也不会绕过 Object Lock。被保留或处于 legal hold 的对象版本可能拒绝永久删除；无版本号删除在受保护对象上仍可能成功创建 marker，使对象从普通视图隐藏，却没有销毁受保护数据。

生命周期配置也有两类动作需要区分：当前版本过期在版本化桶里可以通过新增 marker 表达，非当前版本过期则会永久移除历史版本。若 marker 下方还存在对象版本，marker 不是“过期 marker”；只有对象版本已清除、只剩一个过期 marker 时，特定生命周期动作才可能自动删除该 marker。设置错误的生命周期规则可能把暂时隐藏与永久清理混为一谈。需要结合恢复窗口、存储成本、审计保留期和 Object Lock 设计，而不是让所有旧版本都由一个统一天数规则处理。

事件示例：上传服务把 DELETE 当成撤销上传

假设应用删除某张图片以撤销用户上传。请求在版本化桶成功，应用将数据库状态写成 deleted=true，用户界面不再显示图片。数月后做恢复演练，团队发现通过版本列表仍能读取图片；这并不表示 S3 没执行请求，而是应用的“已删除”含义只是当前版本被 marker 隐藏。正确的数据合同应区分 hidden_from_current_reads、recoverable_version_retained 和 permanently_deleted 等状态，并明确是谁负责清理非当前版本。

如果业务真的需要恢复，可以由受控恢复程序读取对象版本列表，验证当前 marker 的 key 和版本 ID 与事件记录匹配，再删除指定 marker。操作前先核对账户、桶、区域和版本号；不可只靠 key 搜索结果猜测，因为并发上传和另一次删除会改变“当前版本”。如果业务要永久销毁，则应检查每个版本、marker、复制目标和保留策略，审批和结果记录也要绑定具体版本 ID。

本文没有访问 AWS 账户或运行 S3 API。上述过程基于 S3 文档，实际恢复步骤需在当前桶版本控制状态、权限、Object Lock 与 SDK/API 行为下验证。不要把示例步骤当作对任意桶都可执行的恢复脚本。

验证恢复流程时保留反例路径

在非生产测试桶先启用版本控制，上传两份不同内容到同一 key，记录两个版本 ID；无版本号 DELETE 后确认普通 GET 的结果与版本列表变化；再删除当前 marker 的确切 version ID，确认较旧内容恢复为当前版本。额外测试“对 marker 再做无版本号 DELETE”、NULL version ID、对象被锁定、非当前版本生命周期过期，以及上传和删除并发等路径。记录响应中的 version ID、delete-marker 标志和对象读取结果，不要只记录 HTTP 状态码。

生产验收应区分三类承诺：客户端隐藏、可恢复删除、永久清除。事件、数据库状态机、对象版本清理、备份和复制策略要使用相同术语。若系统把一次成功的 DELETE 映射成永久清除，恢复演练会暴露语义缺口；若把 marker 恢复误当成重新上传，则可能覆盖现有对象。把“当前可见”“历史保留”和“不可恢复”分开命名，才能让应用的删除按钮与 S3 版本状态一致。

审计字段至少应把 bucket、key、版本 ID、发起主体、请求时间、请求类型和返回的 delete-marker 状态对应起来。对批量删除，逐项结果比汇总 HTTP 成功码更重要：逐项结果能区分 key 失败、marker 新增和指定历史版本删除。恢复前再读一次版本清单能降低竞态风险，但仍应使用事件中识别出的版本 ID，而不是假设“当前最新那条”在任意时刻都安全。使用具体版本 ID 可把恢复动作约束到单一对象变更。
