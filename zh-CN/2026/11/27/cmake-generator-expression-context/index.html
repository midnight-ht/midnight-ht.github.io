CMake 生成表达式写对了语法，为什么仍没有展开？

Generator expression 在生成阶段、且只在支持它的属性或命令上下文中求值；命令参数解析早于求值，含分号或空格时还要先正确引用。

正文

核心要点

  • 生成表达式不是配置阶段变量替换，求值时点是生成构建系统时。
  • 不是每个属性都支持生成表达式，需看该属性文档。
  • 分号、空白和嵌套表达式受命令参数解析影响，必要时引用整个参数。

CMake generator expression（生成表达式）语法正确，却没有按预期展开时，先查三个边界：它是否已经进入生成阶段、当前目标属性或命令是否支持生成表达式，以及表达式经过 CMake 命令参数解析时有没有被空格或分号拆开。它不是配置阶段变量插值；写出 $<...> 本身也不保证每个 CMake 参数都会在合适的上下文求值。

它在生成阶段处理配置相关信息

生成表达式可以根据 build configuration、target 属性、平台或其它可查询信息生成构建规则。常见例子 $<$<CONFIG:Debug>:DEBUG_BUILD> 会在 Debug 配置生成相应编译定义；表达式通常在构建系统生成时求值，而不是 CMakeLists.txt 配置命令执行到这一行时立即替换。因而配置阶段打印一个变量或把字符串写进 message，不一定能看到最终值。

这解释了一种困惑：target_compile_definitions() 中保存着 $<CONFIG:Debug>，配置命令成功，开发者却在 configure log 里没看到 DEBUG_BUILD。它不是漏执行，而是值还要等到生成器根据实际配置产生规则时确定。对于多配置生成器，同一个 build tree 可能同时支持 Debug 和 Release，最终判断需要看生成阶段构建的每个配置，而不是只查看配置时某个字符串。

属性或命令上下文决定表达式能否求值

CMake 文档说明生成表达式可用于许多 target 属性与填充这些属性的命令，但并非所有属性都支持。最直观的失败形式是把一个合法表达式放入没有对应求值上下文的地方，最终文本保留 $<...> 或在生成时报错。需要查目标属性页面对 generator expressions 的明确说明，而不能依据相邻属性支持，就推断同一命令的所有参数都支持。

生成表达式里的 target 引用也有时点与目标依赖约束。表达式可能读取目标属性，或在不同配置生成时解析 target 名称；目标还未创建、上下文不允许引用、属性值为空等情况，都可能改变输出。通用地说“CMake 会自动展开”，缺少了关键条件：由哪种生成器、在哪个 property、针对哪个 target、以哪个配置求值。

命令参数解析先于表达式求值

生成表达式一般在命令参数解析之后处理。如果表达式含空格、换行、分号或可能被解释为命令参数分隔符的字符，CMake 官方文档要求将整个表达式作为一个引用参数传入。比如：

target_compile_definitions(app PRIVATE
  "$<$<AND:$<CONFIG:Debug>,$<BOOL:${ENABLE_TRACE}>>:TRACE_ON>"
)

这里的引号是为了先把复合表达式作为一个参数传给命令；配置条件仍在生成阶段判断。若先被解析器切成多个参数，最终报错可能看起来像表达式语法问题，实则是参数边界已改变。分号尤其要谨慎：CMake 把分号用于列表分隔，文档提供 $<SEMICOLON> 等转义表达式处理字面特殊字符。

表达式允许嵌套，但嵌套越深越难审。CMake 4.5 文档新增 $<ARGS:...> 处理 CMake 列表到表达式预期参数格式的转换，部分表达式还对字符串逗号有约束。不能把看起来像普通 shell 插值的字符串任意组合；应基于目标 CMake 版本查表达式可用性，再用小型 configure/generate 工程验证实际参数形状。本文没有运行 CMake 工程，代码只是语义示意。

把“未展开”拆成可定位的三类问题

第一类是时点不对：在 configure 阶段期待一个 generator expression 立即变成配置值。应把观察点移到 generate/build 输出，例如开启详细构建输出并查看生成的命令。第二类是属性不支持或上下文不匹配：查看具体属性文档和错误位置，确认生成表达式是否允许。第三类是参数解析阶段把表达式切开：检查引号、分号、换行与 list expansion，尽量将复杂表达式封装成一个参数。

反例是把 ${CMAKE_BUILD_TYPE}、shell $VAR 与 $<CONFIG:...> 当作同一阶段的变量。前者是 CMake 变量，shell 变量由命令运行环境展开，generator expression 由 CMake 在生成构建规则阶段处理；它们可能出现在同一个 CMakeLists.txt，但时点和执行者不同。修改错误阶段的变量不会修正另一个阶段的表达式。

验收方案要固定版本、生成器和上下文

在干净目录创建一个最小 CMake 项目，记录 CMake 版本、生成器、目标属性、配置集合和具体 build config。对一个文档明确支持表达式的属性加条件定义，再对一个已知不支持的上下文做负向用例；在生成文件或 verbose build log 中观察表达式最终结果。随后用含空格与分号的表达式验证引用边界。每一步保留完整命令和退出状态，不能从旧 build tree 的 cache 推断新配置结果。

若换生成器后行为变化，应先查它支持的配置模型和属性范围，而不是立即改表达式内容。若只有某个 target 失败，检查目标创建次序、属性是否继承、生成器表达式中引用的 target 是否存在。若表达式文本原样留在结果中，确认该位置是否实际进行 generator evaluation。把求值阶段、上下文和输入解析依次检查，通常比反复改 $<...> 内部逻辑更快定位问题。

用最小工程区分解析错误和求值错误

复现时先只保留一个 target 和一条属性赋值，再分别记录 configure 与 generate 的退出结果。若配置阶段就失败，先查变量、列表和命令参数解析；若配置通过而生成失败，检查表达式是否可在该属性和所选生成器中求值。然后把包含空格与分号的参数拆成两个实验：先用完整引用确认参数边界，再用文档支持的转义形式测试字面分号。多配置生成器还要逐个生成实际构建配置，查看最终命令，而不能只检查 CMakeCache.txt。这套缩减顺序能把解析阶段、属性支持和配置值三个假设分开。本文没有运行该工程，结果仍须由目标版本的 CMake 实测。
