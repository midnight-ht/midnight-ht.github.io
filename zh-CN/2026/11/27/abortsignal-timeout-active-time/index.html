页面挂起后 AbortSignal.timeout 为什么还没超时？

AbortSignal.timeout 使用活动时间而不是简单墙上时钟；文档进入 BFCache 或 Worker 挂起时计时会暂停，不能把它当作服务器端绝对期限。

正文

核心要点

  • timeout 参数表示活动毫秒数，不保证从创建时刻起经过同样的墙上时间就触发。
  • BFCache 和挂起 Worker 会暂停该计时，恢复页面后操作可能仍未超时。
  • 需要可取消计时或服务器绝对截止时，应明确另设相应的责任层。

该 API 返回一个在指定活动时间后自动中止的 signal；这里的时间不是简单地从创建时刻开始数墙上时钟。MDN 文档说明，页面进入 back-forward cache（BFCache）或 Worker 被挂起时，这个计时会暂停。因此，一个页面离开后过了十分钟再返回，请求仍可能没有得到 TimeoutError。它适合约束浏览器活动期间的异步操作，不应替代服务器端截止时间或业务有效期。

活动时间和墙上时间的差别

假设用户打开订单详情页，页面在后台发起一项可取消的数据读取，并设置 AbortSignal.timeout(5000)。若 JavaScript 执行环境持续活动，约五秒后 signal 会以 TimeoutError 中止等待；但用户把页面导航到另一个页面，浏览器将原页面放入 BFCache 后，计时会暂停。十分钟后用户返回时，五秒活动时间可能还没有累计完成，读取仍在等待。这个行为不是“浏览器忘了计时”，而是 API 明确按活动时间计算。

这一区分影响文案与故障诊断。如果产品要求“用户当前页面等待最多五秒”，活动时间与体验目标相符；如果合同写的是“从服务器接受请求起五秒内，后台工作必须终止”，仅在客户端创建 timeout signal 就不能兑现。页面冻结、设备休眠、进程调度和网络延迟都与服务端执行的生命周期不同。前端 signal 能请求浏览器侧异步操作中止，也不等于远端服务器已停止处理。

signal 组合能处理什么？

请求可能因用户取消，也可能因活动时间超时。组合 API AbortSignal.any([userSignal, timeoutSignal]) 可以把多个原因组合，让 fetch 等支持 AbortSignal 的操作在任一 signal 中止时收到取消请求。调用方仍要根据 signal.reason 判断原因，分别处理用户主动离开和等待超时；两者都以 AbortError 统称会让界面错误地展示重试提示，甚至把用户主动取消记录成网络故障。

组合范围也要与操作生命周期一致。若一个页面同时加载彼此独立的头像和订单详情，共用一个极短 timeout signal 会让头像故障也取消订单读取；反过来，把多个需整体成功的步骤放在同一个 signal 下，才表达它们共享一个等待预算。创建 signal 前先画出取消传播关系：谁发起取消、哪些请求随之停止、哪些后台写入不能靠浏览器中断回滚。这样 signal 的共享不只是代码方便，而是可检查的操作合同。

组合 signal 不会替你停止所有资源。AbortSignal.timeout() 的计时不能直接取消；如果操作提前完成，timeout 仍可能继续待命。MDN 还提醒，timeout 有 abort 监听器时 signal 会保持存活，长超时和未移除监听器可能延迟垃圾回收。如果应用需要确定性地提前清理计时器，可以由自己创建 AbortController 和 setTimeout()，在操作完成时调用 clearTimeout()，并移除不再需要的监听器。该选择解决资源生命周期问题，不会自动把浏览器计时改成服务器时钟。

若产品策略确实要求页面恢复时先检查一个墙上时钟截止点，可以在发请求时保存客户端可读的截止时间，在 pageshow 或页面可见状态恢复后再核对是否已经过期，并主动取消已过期的本地工作。这只是浏览器重新获得执行机会时的补充检查，会受设备时钟调整和页面长期不运行影响；它不能在页面冻结期间运行代码，也不能代替服务器自己拒绝过期写入。不要把“我本地保存了截止时间”写成“服务端保证及时停止”。

如何表达服务端的绝对截止时间？

对有服务端副作用的请求，应该在服务端定义期限或取消合同。客户端可以把绝对截止时间作为业务参数或协议约定传给服务端；服务端再检查自身时钟、排队时间和处理进度，并在适当边界停止工作。示例：假设导出任务必须在请求创建后二十秒内获得结果，前端可在页面显示倒计时并在用户继续等待时取消请求，但服务端仍需持有创建时间、截止时间和任务状态，超时任务不得仅靠浏览器 tab 关闭而继续无限运行。

如果只是希望用户不再等待当前 fetch，signal 足以表达本地取消意图。如果需要保证数据库写入不会在期限后提交，应在事务提交边界重新核对服务端截止时间；网络请求被中止并不能撤回已提交事务。若服务端任务排队后还会异步运行，还需要保存取消状态，并明确取消是否只是“停止返回结果”还是“尽最大努力停止副作用”。这些语义必须写进 API 和业务状态机，而不是依赖毫秒参数自行推导。

怎么验证冻结和清理路径？

在支持 BFCache 的浏览器中构造页面返回场景，分别比较一直停留页面、离开再恢复、Worker 挂起恢复的 signal 触发情况；记录创建时间、页面恢复时间、活动操作时间和 signal.reason。测试请求自然完成时 timeout listener 的清理，测试用户取消是否保持与超时不同的表现，并确认服务端对客户端取消后的状态仍可查。具体兼容行为应以目标浏览器版本实际测得为准，不能从一个开发者工具会话推断所有平台一致。

本文未运行浏览器自动化或网络请求，时间线是依据 MDN 与 DOM 标准整理的假设例子，不是实测结果。实施时应区分三种时间：页面活动时间、客户端观察到的经过时间、服务端执行期限。分别由它们所在的运行时负责，才能解释为什么一个看起来已经过了五秒的请求还没有被 AbortSignal.timeout() 中止。
