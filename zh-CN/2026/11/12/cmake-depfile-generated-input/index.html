生成器读过配置，CMake 为什么还沿用旧产物？

用同一生成脚本和两份 Ninja 构建图，检查子配置变更是否使已有报告失效。

正文

核心要点

  • 生成脚本实际读取的输入应进入构建依赖。
  • 第一次成功不足以验收增量构建。
  • 对照日志与报告内容，避免只检查依赖文件存在。

第一次生成报告成功。第二次改了生成器读取的子配置，构建却显示没有工作可做。先检查构建图里有没有这份输入。自定义命令在运行时打开一个文件，构建工具仍要通过已经声明或记录的依赖，才能在后续构建中知道何时重跑命令。

入口清单与读到的内容各有位置

假设生成器收到一份清单，里面写着子配置的文件名。命令知道怎样读完这两份文件，但调用方只能从命令行直接看到清单。若构建规则的 DEPENDS 只登记清单和生成脚本，修改子配置不会改变这些已登记的输入。初次构建因为目标不存在而执行，输出完全正确。这恰好解释了为何干净环境总能得到正确结果，重复构建却留着旧内容。

可以直接把所有已知输入列进 DEPENDS。如果输入成员由生成器处理内容时确定，可以让生成器另外写一份 depfile，再让自定义命令通过 DEPFILE 将它交给支持的构建生成器。官方手册把这一文件定义为自定义命令的依赖清单，格式与 GCC 的依赖输出兼容。这里限定普通 Ninja 与 CMake 3.20 或更高版本，版本下限用于采用示例所需的策略。普通 Ninja 对该关键字的支持从 CMake 3.7 起已有。CMake 自定义命令手册

两种登记方法解决的是同一件事，使用场景不同。输入列表短小且固定时，显式列出能让评审者直接看到构建合同。文件名来自清单或子文件的内容时，把依赖报告放在实际执行者那里可以避免重复实现一份解析器。仍要检查生成器有没有记录它确实读过的路径，以及旧输入移除后生成的依赖清单是否随之改变。命令偶然读取一次文件，不会替你登记将来所需的边。

两份构建图共用一条生成命令

下面是一份尚未运行的最小项目。选一个没有空格、井号或美元符号的独立目录。四个文件在同一目录，manifest 内容为 fragment 加换行，fragment 内容为 blue 加换行。示例刻意使用简单路径，使依赖清单里无需手写转义规则。

# CMakeLists.txt
cmake_minimum_required(VERSION 3.20)
project(ReportProbe NONE)
option(TRACK_READS "Attach the dependency file" OFF)

set(report "${CMAKE_CURRENT_BINARY_DIR}/report")
set(deps "${CMAKE_CURRENT_BINARY_DIR}/inputs")
set(extra)
if(TRACK_READS)
  list(APPEND extra DEPFILE "${deps}")
endif()

add_custom_command(
  OUTPUT "${report}"
  COMMAND "${CMAKE_COMMAND}"
    "-DSOURCE=${CMAKE_CURRENT_SOURCE_DIR}"
    "-DREPORT=${report}"
    "-DDEPS=${deps}"
    -P "${CMAKE_CURRENT_SOURCE_DIR}/generate.cmake"
  DEPENDS "${CMAKE_CURRENT_SOURCE_DIR}/manifest"
          "${CMAKE_CURRENT_SOURCE_DIR}/generate.cmake"
  ${extra}
  VERBATIM
)
add_custom_target(report_probe ALL DEPENDS "${report}")

# generate.cmake
file(READ "${SOURCE}/manifest" child)
string(STRIP "${child}" child)
set(input "${SOURCE}/${child}")
file(READ "${input}" value)
file(WRITE "${REPORT}" "${value}")
file(WRITE "${DEPS}" "${REPORT}: ${input}\n")
message(STATUS "generated report")

set -eu
cmake -S . -B without-edge -G Ninja -DTRACK_READS=OFF
cmake -S . -B with-edge -G Ninja -DTRACK_READS=ON
cmake --build without-edge
cmake --build with-edge
cat without-edge/report with-edge/report

cmake --build without-edge
cmake --build with-edge

printf 'green\n' > fragment
cmake --build without-edge --verbose
cmake --build with-edge --verbose
cat without-edge/report with-edge/report

两边首次都应输出 blue，随后没有输入修改的构建应复用产物。第三轮只写子配置，不修改清单和生成脚本。没有接入 DEPFILE 的一边预计仍是 blue，接入的一边预计变成 green。两边都会生成名为 inputs 的文件，因此磁盘上存在依赖清单本身不能作为成功条件。关键是第二份构建图会把清单交给 Ninja，最后一次构建日志与报告内容都应反映这条边。

如果第三轮两边都重跑了，先确认你只改了子配置，构建目录没有被清理，配置命令也没有重新执行。若两边都不重跑，检查报告是否仍是第一次的版本，确认修改时间已经被文件系统记录，再检查依赖文件左边的目标是不是正在构建的 report。测试时保留原始退出值和日志，命令失败与增量边缺失需要不同的处置。

生成器和构建目录一起验收

生成脚本依然要用显式依赖记录，因为它自身是定义生成行为的入口。清单也是静态入口，改成另一个子配置名时需要触发重跑并产生下一份依赖报告。若团队只把子配置写入依赖文件却不登记清单，重新选择文件这一变化仍可能漏掉。对于已有工程，可以在不改公共构建配置的临时树中建立这一对照，先确认观察值来自同一次构建。

验收表可按输入变化分行记录。无变化时两边是否都跳过，改清单时两边是否都重新读入口，改子配置时依赖报告是否产生差异。最后加入一份从未被读取的文件，检查它没有造成额外重跑。相比目录扫描，这一做法能说明重建与哪条实际输入边有关。源文件成员发现是另一项验证，可以在构建图生成阶段单独查看。站内 CMake 源成员集合对照

实际故障可沿两条路径拆开看。先让生成器单独运行一次，核对依赖报告是否包含这次读取的子配置。如果生成器产出的清单里就缺文件，应修生成器的读取记录，再重做一次变化试验。如果清单确实列出文件，问题可能在规则没有接入这份报告，或者报告指向了另一个构建目录里的目标。此时不要改输入内容来试运气，先把生成器写出的路径、规则声明的路径与本轮构建目标逐一对应。

本例的子配置从第一次生成前就已经存在。若项目中的子配置本身还要由另一个目标生成，第一次运行报告命令之前也必须安排它出现。依赖文件要等报告命令执行才能产生，不能让尚未发生的报告反过来满足首次执行的输入顺序。应把这个已知生产者与报告规则建立明确联系，另做一次从空目录开始的验收，然后再测试一次真实输入更新。这样可以把首次拿不到文件和下一次复用旧报告分到各自的证据里。

挪到子目录后，相对 DEPFILE 从哪里算？

对采用 CMP0116 NEW 的 Ninja 生成器，相对的 DEPFILE 参数和清单里的相对路径以当前的 binary dir 为基准。CMake 在命令运行后生成转换后的内部依赖文件，原始清单仍保留。迁移时把子目录中的输出路径和输入路径都核对一遍。尤其要确认路径是相对当前二进制目录，而非仓库根目录。本文的样本使用绝对路径，只有把命令移入子目录并改用相对路径，才会触发这个额外验证条件。CMake CMP0116 策略
