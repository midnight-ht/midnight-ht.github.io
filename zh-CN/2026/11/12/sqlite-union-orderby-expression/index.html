SQLite 的 UNION ALL 为什么拒绝 ORDER BY lower(name)？

核对 SQLite 复合查询排序项怎样对应结果列，用三条已执行查询核对外层排序和辅助列，并追问跨分支别名。

正文

核心要点

  • 复合查询的排序项需要对应结果列。
  • 外层简单 SELECT 可计算排序键并保持原列形状。
  • 跨分支同名排序别名按从左到右寻找匹配。

SQLite 的简单 SELECT 可以直接按 lower(name) 排序。用 UNION ALL 组合多个 SELECT 后，最终 ORDER BY 的规则变了。除列序号和可解析的结果列别名外，排序表达式需要匹配某个分支的输出表达式。如果原输出只有 name，可以先完成合并，再让外层简单 SELECT 按 lower(name) 排序。

设想一个本地目录把缓存条目和刚导入的条目一起显示。两个来源都只需要输出名字。维护者加上合并语句后，应用才开始报排序项找不到对应列。检查数据会发现每条名称都存在，也能在两个来源上单独调用 lower。问题不在某个名字，而是合并后排序项所在的查询层。

先判断排序项属于哪一层

SQLite 的 SELECT 参考区分简单 SELECT 与复合 SELECT。简单查询的 ORDER BY 可以使用任意表达式。复合查询把排序项解析为输出列。正整数可以指定位置，输出别名可以指定某一列，其他表达式则必须与分支中的结果表达式相同。仅把 name 放进结果，不能让对 name 的任意计算自动成为一个输出项。

这意味着报错不一定能通过换函数或改数据修复。把 lower 改成 upper，或者让所有名字都已经是小写，只要排序表达式仍未匹配输出项，结构问题仍在。另一方面，如果需求只想按原名称排序，使用已输出的 name 就足够。先确认产品是否真的需要按变换后的文字排序，再决定在哪一层计算。

也要保留普通排序的稳定性要求。两个名字变成同一个小写值以后，主要排序项已经打平。假如界面希望这两项顺序确定，就补充明确的第二排序项。示例选择原始名称与 BINARY 排序规则，限定为 ASCII 名称。如果真实目录使用其他字符或特定地区的排序规则，需要核对应用连接中的实际环境与产品期望。

把同一份输入送过三种查询

以下教学 SQL 已在 Python 3.11.15 内置 sqlite3 的内存数据库中执行，SQLite 版本为 3.53.1。在一个自有内存数据库新建两张空表，录入固定数据。第一条 SELECT 是独立负例，测试器应捕获它的预期错误，再分别执行后面的两条；若命令行配置为遇错即停，后续语句应在保留相同表数据的条件下单独提交。不要用第一条报错来推断后面的两个正例已经验证。

CREATE TABLE cached(name TEXT NOT NULL);
CREATE TABLE incoming(name TEXT NOT NULL);
INSERT INTO cached VALUES ('beta'), ('Alpha');
INSERT INTO incoming VALUES ('alpha');

SELECT name FROM cached
UNION ALL
SELECT name FROM incoming
ORDER BY lower(name);

SELECT name
FROM (
  SELECT name FROM cached
  UNION ALL
  SELECT name FROM incoming
) AS merged
ORDER BY lower(name), name COLLATE BINARY;

SELECT name, lower(name) AS sort_key FROM cached
UNION ALL
SELECT name, lower(name) AS sort_key FROM incoming
ORDER BY sort_key, name COLLATE BINARY;

第一个复合查询的排序项没有匹配结果列，预期拒绝。外层版本返回单列，顺序是 Alpha、alpha、beta；前两个小写值相同，显式的第二项决定大写 A 在前。投影版本也按相同名称顺序返回，但多了 sort_key 一列，其值依次为 alpha、alpha、beta。逐行检查这两份结果，既验证排序，也验证消费者究竟收到了几个字段。

两个正例服务不同的接口。导出协议只接受原来的一列时，外层 SELECT 可以保留列形状。下游确实需要审计计算出来的键时，显式投影更容易检查。两种修法都应在最终对外输出的查询层写出有效的 ORDER BY，避免让内部表的扫描次序承担显示承诺。

对于 UNION 而非 UNION ALL，改变输出列也会改变参与行比较的字段。不要为了让排序通过，就擅自为每个来源添加身份列再沿用去重预期。如果排序键只是同一输出值的确定函数，重复行不一定因此分开。站内的集合合并与行身份已经展开投影去重的合同。这个例子保持 UNION ALL，便于单独观察复合排序的限制。

让输出形状也进入验收

客户端常按位置读取列。一次修复即使保留页面上的名称顺序，额外字段也可能影响 CSV、接口解码或数据绑定。测试时给两个正例各写一份列名和行值预期，不让同一张截图同时代表两种协议。如果另一个调用方只需要排序后的名称，外层查询可以继续投影单列，而不要求它理解排序键的含义。

遇到驱动捕获错误后自动尝试无排序查询的接口，还要验收失败传播。可以先记录第一条语句是否返回错误，再单独执行去掉排序的合并，确认它仍保留三条输入。这组无排序检查只比较行的多重集合，不检查固定位置。若应用把备用查询的成功当作排序修复，用户可能仍然看到不确定的排列。正例应显式比较名称顺序，失败例应保留原始错误类型，两条结果各自有自己的验收入口。

保存对照应包括 SQLite 版本和实际执行入口。应用嵌入的引擎、测试命令行和客户端包装层可能各自不同。先确认错误来自数据库对最终复合 SQL 的解析，再检查驱动有没有重写排序或只返回了一部分错误。归档断言只检查本节三条查询，覆盖第一条的错误类型和后两条的输出列名、行值与顺序。适配器回退与文末别名追问仍是独立预期，未运行。

两个分支把同一个别名用在不同输出位置，会选哪列？

SQLite 对复合查询的非整数排序项从最左分支开始查找匹配，找到后便把它作为相应结果列的别名。举个新例，左支写 SELECT 2 AS k, 1 AS b，右支写 SELECT 1 AS a, 2 AS k，再接 UNION ALL 的最终 ORDER BY k。最左分支的 k 指向第一列，故预期先出现第一列为一的行，再出现第一列为二的行。右支把第二列叫 k，并不会让同一个排序项按分支使用不同位置。

实际维护时可以给每列选择唯一且一致的别名，或在外层把要排序的列名写清。加入新的分支时，核对现有排序名称与位置是否仍对应原合同。这个追问针对排序项已经找到匹配后的绑定位置，前面的失败例则根本找不到匹配。两种问题需要分别用行序和列形状验收。
