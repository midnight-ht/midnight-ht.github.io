SSE 重连带回 Last-Event-ID，服务端能确认什么？

用两条通知继承同一个事件 ID 的回环样本，区分 EventSource 自动重连游标和应用处理确认。

正文

核心要点

  • 完整 SSE 事件块可以更新浏览器维护的续传游标。
  • 后续消息可沿用最近的事件 ID。
  • 服务器需要另行定义重放与业务确认。

浏览器重连通知流时带着 Last-Event-ID: 41。服务端收到的是 EventSource 上次保存的游标，如何恢复由端点决定。这个头不能证明应用的消息回调已经完成，更不能证明写入已提交。要决定重放哪些通知，先把浏览器维护的游标与应用自己的确认条件分开。

从两条消息看同一个游标

HTML 标准解释 SSE 事件流的算法按行识别字段，遇到空行处理已经读到的事件块。不含空字符的 id 字段值会写入事件 ID 缓冲区。浏览器处理空行时会把它写进 EventSource 保存的 ID；创建消息时，消息对象带有这个值。下一条消息可以只有 data，于是继续沿用上一次 ID。字段名看起来像每条消息的编号，实际还要看服务器有没有为每条都明确分配。

假设一个进度流先发送 stage-a，并设置 id 为四十一，随后发送 stage-b，不给新的 id。两个消息内容不同，预期却都报告同一个 lastEventId。若客户端只用这个值作为唯一去重键，就会漏掉 stage-b。若确实需要识别每条业务消息，可以让应用消息携带其自己的稳定身份，并写明它是否与流的续读位置相同。协议不会替项目把两个概念合成一个键。

还要把事件边界与传输分块分开。一个读取可能拿到几行，也可能只拿到半行，应用不能把每次网络读取当成一个完整的事件。本例让服务器一次写出两个由空行分隔的块；它们由文本结构而不是调用次数隔开。如果删掉第二块末尾的空行，结束响应不足以派发这个未完成的事件，服务端日志里写过 stage-b 也不能替客户端证明收到它。

本地观察三份记录

下面是完整的单文件 Node 示例，尚未运行浏览器重连验证。服务器只在本机回环地址监听，浏览器页面与事件端点同源。保存为 server.mjs，运行 node server.mjs，打开终端提示的地址。每轮只打开一个标签页，并重启进程再重复，否则已设置的 opened 状态会把第二次独立试验当作重连。示例用关闭响应触发重新建立连接，随后返回 204 停止该样本继续重连。不要把教学的重连延迟当作生产建议。

import { createServer } from 'node:http';

const page = `<!doctype html>
<meta charset="utf-8">
<title>Reconnect cursor example</title>
<pre id="events"></pre>
<script>
const log = document.getElementById('events');
const stream = new EventSource('/events');
stream.onmessage = ({ data, lastEventId }) => {
  log.append(JSON.stringify({ data, lastEventId }) + '\\n');
};
</script>`;

let opened = false;
const frameA = 'retry: 100\nid: 41\ndata: stage-a\n\n';
const frameB = 'data: stage-b\n\n';

createServer(({ url, headers }, res) => {
  if (url === '/') {
    res.writeHead(200, { 'Content-Type': 'text/html; charset=utf-8' });
    res.end(page);
    return;
  }
  if (url !== '/events') {
    res.statusCode = 404;
    res.end();
    return;
  }
  const { 'last-event-id': cursor } = headers;
  console.log('EventSource request cursor:', cursor ?? '(absent)');
  if (opened) {
    res.statusCode = 204;
    res.end();
    return;
  }
  opened = true;
  res.writeHead(200, { 'Content-Type': 'text/event-stream' });
  res.end(frameA + frameB);
}).listen(8765, '127.0.0.1', () => {
  console.log('Open http://127.0.0.1:8765/ in a browser');
});

规范预期有三个独立的观察。第一次事件请求不带上次 ID；页面出现两个 JSON 行，分别是 stage-a 和 stage-b，lastEventId 都为四十一；随后服务器收到带该头的重连请求。重连请求携带保存值的依据是Last-Event-ID 的重连规则，适用于该 EventSource 的自动重连。没有访问实际浏览器时，不能把这份预期写成已经捕获的日志。

实际跑例时要分别保存服务器请求和页面通知，二者的数量和到达时刻回答不同问题。浏览器可以先处理流里的字段和空行，把消息派发排进任务，再由页面回调执行。即使两条消息最终都显示在这个教学页面，重连请求携带的是浏览器的状态。服务器只看到这个头时，并未得到页面回调是否执行完成的证据。这个样本也没有实现返回旧事件的逻辑，重连被观察到不说明业务已恢复。

选择游标使用范围，再定义确认

如果服务端把游标用作重放边界，需要规定流身份、游标定位的对象和保留范围。以同一个通知面板为例，四十一可能代表持久化日志的一条位置，也可能只给出最近一次同步点。后者的恢复方式可能是先读快照，再从新位置继续。若服务端保留期有限，旧位置已不可恢复时应定义新的读取入口或明确提示，不要把返回空流当成已经赶上。这里是接口设计建议，没有假定 SSE 规定重放方案。

页面如果收到通知后还要把结果写入浏览器存储或调用自己的确认接口，要单独验证这些动作。设想回调开始处理 stage-b 后抛出错误，界面可能没有提交新进度，而游标仍可保留四十一。是否需要恢复该消息，取决于应用如何表示已处理位置，以及服务器是否保有对应数据。站内CloudEvents 事件身份讨论重复投递与业务事务，本例补的是浏览器 HTTP 重连携带的标记和应用确认之间的差异。

验收可以先用样本验证重连头，再用项目自己的持久化路径制造一次处理失败。预期分别写成“服务端看到游标”“界面没有写入成功状态”“恢复路径重新取得需要的信息”。只保存第一项会让网络行为掩盖业务结果；只保存最后一项则无法知道是协议续读还是刷新快照帮应用恢复。如果业务确认另走一个请求，还可对照两条连接的日志。让通知流正常断开、确认请求单独失败，预期服务端仍会看到流的续读游标，但确认记录不会新增。生产方案还应区分同一个 EventSource 的自动重连与页面主动创建新对象，本例只覆盖前者。

只有 id: 42 和一个空行，会派发消息吗？

不会派发消息，但会更新续读游标。给教学服务器首次响应末尾额外加上字面量 id: 42、一个换行与一个空行，其他两块仍照原样发送。此时浏览器处理新块时先记录四十二，因为没有数据缓冲，不会新建第三条消息。原来的两条消息仍各自携带四十一；随后重连预期带四十二。这一组与主例只改变最后一块，可以独立验证消息数量和续读位置不必一起变化。注意只增加一个 id 行而不结束事件块，不能替代这里的空行条件。
