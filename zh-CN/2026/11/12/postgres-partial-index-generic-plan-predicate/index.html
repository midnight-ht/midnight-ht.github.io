字面量用得到部分索引，绑定状态后为什么不行？

对照 PostgreSQL 预备语句的通用和定制计划，核对状态谓词、部分索引资格和实际选中的路径。

正文

核心要点

  • 通用计划不能按这次的状态实参证明部分索引谓词。
  • 定制计划可以利用实际参数；最终路径仍取决于成本。
  • 只固定业务状态的专用查询仍可以绑定负责人。

同一条待办查询传入 pending 时，两次执行都可以返回相同的任务，计划却可能不同。定制计划可以根据这次传入的值判断部分索引是否够用；通用计划需要覆盖调用方随后传入其他状态的情况。

假设后台有个任务页面，用户可以在待办和已完成之间切换。数据库只给待办任务建立了部分索引，以免索引还收录大量已经完成的记录。排查时有人把日志里的参数替换成字面量，发现这条改写可以使用索引，随后又拿着原来的预备语句看到顺序扫描。两份计划的输入条件需要先还原。字面量查询提供了一个固定谓词；原接口的查询有可能重用一份必须对所有状态都有效的计划。

先用三条记录约束两次执行

下面的 SQL 没有执行。建表和 PREPARE 只需在测试会话里做一次。固定相同的任务记录和同一组实参，只在各自事务内改变计划模式。EXPLAIN 负责查看计划；独立的 EXECUTE 给出结果，避免计划展示代替行值验收。

CREATE TEMP TABLE plan_jobs (id int, status text, owner int);
INSERT INTO plan_jobs VALUES (1, 'pending', 8), (2, 'done', 8), (3, 'pending', 9);
CREATE INDEX plan_jobs_pending_owner ON plan_jobs (owner) WHERE status = 'pending';

PREPARE list_jobs (text, int) AS
SELECT id FROM plan_jobs WHERE status = $1 AND owner = $2;

BEGIN;
SET LOCAL plan_cache_mode = force_generic_plan;
EXPLAIN (COSTS OFF) EXECUTE list_jobs ('pending', 8);
EXECUTE list_jobs ('pending', 8);
COMMIT;

BEGIN;
SET LOCAL plan_cache_mode = force_custom_plan;
EXPLAIN (COSTS OFF) EXECUTE list_jobs ('pending', 8);
EXECUTE list_jobs ('pending', 8);
COMMIT;

两次执行的预期都只返回任务一。任务二虽然归属相同的人，但状态已经完成。任务三虽然待办，但归属另一人。先分别核对这两个排除项，才能确认两种模式比较的是同一个查询。若驱动对每条 SQL 分别换连接，预备语句和事务本地设置可能无法落在同一会话；先用固定数据库会话做对照。

通用计划需要同时适用于状态为 done 的一次调用。那次应返回任务二，而待办部分索引根本没有这条记录，因此规划时不能把这个状态参数当成 pending 来证明索引覆盖全部候选。定制计划把这次的实际状态代入查询，pending 可以满足索引谓词。即使如此，在三行样本上顺序扫描也可能是更便宜的选项。索引具备使用资格和计划最终选用它是两个判断，不能用一次顺序扫描同时证明两者。规则见 PostgreSQL 18 部分索引 和 PREPARE。

怎么读两份计划

在 EXPLAIN EXECUTE 输出里，通用计划仍显示参数符号；定制计划会代入实际参数值。先找计划过滤条件或索引条件，再看扫描的对象。看到待办字面量可以说明定制计划拥有这次的状态值，看到目标索引名才说明它实际选择了那个索引。一次诊断可以保留两个输出，不必通过改变成本设置去强迫索引出现。

这组样本的职责是对照谓词和行值。扩大到代表性数据量时，再分别测量各状态、归属分布和不同计划的耗时。假如生产表上待办比例很高，甚至某些负责人拥有大量待办，定制计划即使识别了部分谓词，也可能因访问太多记录而选择别的路径。遇到这种结果要保留真实计划和参数频率，避免从三行样本推导生产响应时间。站内的覆盖索引与可见性讨论已经选定索引后为何仍可能访问堆，属于另一处验收点。

若产品必须让用户自由选择状态，可以保留预备语句并以真实的状态分布评估通用和定制计划。还可以比较完整索引的写入和空间成本，确认它是否服务同一接口的其他状态。为了孤立本例的问题，只在事务本地强制一种计划。测试结束后再把设置交给原会话配置，不把这个诊断手段当成全局上线参数。在应用里复查时，先记录驱动究竟提交哪份 SQL、是否在服务端建立可重用的预备语句，以及 EXPLAIN 在哪个连接执行。两个页面碰巧共用一份日志格式，并不能证明它们实际重用了同一计划。

数据库迁移也可能留下看起来相似的索引。采样前从实际实例取得索引定义，把索引谓词与预备语句的 WHERE 条件并排记录。如果实际谓词还要求任务未归档，当前查询就必须另外满足未归档这一条。只看到名称中有 pending，不能推断两个条件相同。遇到条件等价但写法复杂的情况，先用与实际谓词相同的简单表达式做隔离样本，再逐段恢复生产写法，观察在哪一步失去可识别的关系。这里的三条记录没有归档列，不能用来判定那套新谓词。

计划排查记录可以分成两张表。一张按实参保存预期和实际任务编号，覆盖待办、已完成、另一个负责人，以及没有记录的人。另一张按同一组实参记录会话、计划模式、估算行数、扫描节点和实际使用的索引。先从第一张排除业务结果差异，再解释第二张中的访问路径差异。任何采样如果同时改了参数和计划模式，都要补上原值对照，才能判断变化来自哪里。

如果只绑定负责人，状态写成固定字面量呢？

假设后来有个独立待办接口，从产品上就没有切换状态的功能。可以单独预备 SELECT id FROM plan_jobs WHERE status = 'pending' AND owner = $1，并继续绑定用户提供的负责人值。即使走通用计划，已写明的状态仍能满足索引谓词，负责人参数只改变这个范围内要找谁。验收给负责人八传参，期望任务一，再给负责人九传参，期望任务三。这个对照也未执行；两种负责人即使得到预期行，计划仍可能依据成本选择顺序扫描。原接口仍需要接受 done，这条专用查询只适合独立的待办入口。绑定外部输入的方式保持原样，固定状态来自预先定义的 SQL 文本。
