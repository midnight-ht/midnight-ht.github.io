systemctl reload 返回了，应用为什么还在用旧配置？

用两个配置代次复查信号命令和通知式重载的完成时机。

正文

核心要点

  • 保存命令结束时间和应用切换代次的证据。
  • 应用完成配置切换之后再发送完成通知。
  • 用同步重载命令或应用通知让管理器等待。

ExecReload 如果只发信号，命令可能先退出，应用稍后才读完配置。

发布脚本先更新配置，再执行 systemctl reload。终端回到提示符时，状态接口仍然显示旧配置的代次。想定位这个间隔，可以把三个时刻分开记下来。第一个是发送重载信号的命令退出。第二个是应用接收配置并切换当前代次。最后一个是服务管理器确认这次重载完成。只保留 shell 的退出码，后两项没有留下证据。

把重载完成交给知道结果的一方

常见的单元配置是 ExecReload=kill -HUP $MAINPID。命令完成的是发送信号，后续读取和应用配置仍由主进程完成。重载命令成功时，发送信号这一步已经走完；进程什么时候处理、解析结果是什么，不能从这次命令的退出码里读出来。若已有控制工具能够请求重载并同步等待结果，单元可以用那个工具作为重载命令。服务手册建议同步执行重载，或使用下面的通知协议，以便依赖关系中的重载也能正确排序。

支持 Type=notify-reload 的服务可以让管理器等待主进程。管理器发送重载信号，默认是 SIGHUP。应用进入重载后，发出同一条消息中的 RELOADING=1 和当前单调时钟微秒值 MONOTONIC_USEC。配置真正应用完毕以后，应用再发送 READY=1，管理器据此结束重载。这个类型也沿用启动通知，所以下面的进程会先安装信号处理器、读完初始配置，再报告启动完成。这里依据 systemd 262 手册，试用前确认机器上的管理器和应用均支持所需协议。

给新旧代次一个可查的交接点

下面是隔离 Linux 主机上的演练，未在当前机器上运行 systemd。程序只读取字符串代次，把结果写到同一个目录里的 active。为了稳定观察先后关系，它在应用配置前等待读者创建 release 文件。这是演练用的同步点。请将脚本保存为 /var/lib/reload-lab/app.py，先创建该目录，再把 old 写入同目录的 wanted，并确保 release 不存在。

import os
import signal
import socket
import time
from pathlib import Path

wanted, active = Path("wanted"), Path("active")
pending = False

def notify(message):
    address = os.environ["NOTIFY_SOCKET"]
    if address.startswith("@"):
        address = "\0" + address[1:]
    with socket.socket(socket.AF_UNIX, socket.SOCK_DGRAM) as sock:
        sock.sendto(message.encode(), address)

def on_hup(signum, frame):
    global pending
    pending = True

def apply():
    generation = wanted.read_text().strip()
    temporary = active.with_suffix(".next")
    temporary.write_text(generation + "\n")
    temporary.replace(active)

signal.signal(signal.SIGHUP, on_hup)
apply()
notify("READY=1")

while True:
    if pending:
        pending = False
        now_usec = time.monotonic_ns() // 1000
        notify(f"RELOADING=1\nMONOTONIC_USEC={now_usec}")
        print("reload entered", flush=True)
        while not Path("release").exists():
            time.sleep(0.05)
        apply()
        print("generation applied", flush=True)
        notify("READY=1")
    time.sleep(0.05)

把下面的文件安装为专用测试单元 reload-lab.service，执行 systemctl daemon-reload 后启动它。按系统的权限要求运行管理命令。开始重载之前确认 active 是 old，然后把 new 写到 wanted。在一个终端执行 systemctl reload reload-lab.service，在另一个终端用 journalctl -u reload-lab.service -f 观察程序记录，同时检查 active。

[Unit]
Description=Reload completion lab

[Service]
Type=notify-reload
NotifyAccess=main
WorkingDirectory=/var/lib/reload-lab
ExecStart=/usr/bin/python3 /var/lib/reload-lab/app.py

预期看到 reload entered 时，管理命令仍在等待，当前代次仍是 old。接下来创建 release，程序替换代次文件并发送完成通知，命令才应成功返回。这里对照的是两项独立证据。一个终端能看见命令何时返回，另一个终端能读出应用在那个时刻报告的是哪一代。只查日志里的进入记录，甚至只查管理器显示服务仍然运行，都不能代替读取代次。若演练一开始就忘了移除开关文件，等待步骤会被跳过，也就难以从终端先后次序观察差异。

演练中的代次文件由同一个目录里的临时文件替换，读者可以用它观察旧值到新值的交接。最好在开关文件不存在时先读一次，并在管理命令返回以后再读一次。若命令先返回，暂时别创建开关，把当时的文件值和命令结果并排留存。若命令仍在等待，先记下等待状态和旧代次，再解除开关。这样既能证明读到的旧值发生在预定的交接点前，也能把另一个终端的观察时间还原出来。开关文件应只用于这个隔离演练，真实进程的切换时机由它自己的配置校验和提交步骤决定。

重跑一次只发信号的路径

停止测试单元后，把类型改成 notify，并在服务段加入 ExecReload=/bin/kill -HUP $MAINPID。重新加载单元，恢复初始文件，再启动同一个程序。启动通知仍能使用，重载改由发送信号的命令完成。用同样的动作写入新代次，发起重载，先不创建开关文件。此时预期管理命令已经成功结束，而 active 还会保持旧值；创建文件后才会看到代次改变。这个错例把应用侧的行为固定住，只换了管理器等待完成的方式。

接入真实服务时，先从服务已有的控制接口判断它能否同步反馈重载结果。有可靠的同步命令就能沿用命令式重载。若由应用实现通知，则需要确认发通知的进程有权限、完成消息在应用成功切换后发送，以及手上的系统版本支持这种服务类型。演练脚本只处理读取成功的一次代次替换，生产程序还要定义无效配置怎么反馈、当前代次怎么查询和并发重载如何处理。发布验收可以同时保留管理器结果、应用当前代次和一个能体现配置变化的请求。只用其中一项，很难区分配置内容错了、应用未切换或管理器还在等通知。若问题发生在服务首次启动，可以对照启动通知如何影响就绪判断。

试验完成后，停止专用测试单元，再移除为它新建的单元和数据目录，重新加载单元定义。两组记录应分别标记使用的是哪一种服务类型，避免日后把先返回的那次重载错归到通知版本。手册把这两种约定分别写在重载命令和服务类型的条目中，时限的说明也在同一份文件里。 systemd.service 服务单元手册

等重载完成也受 TimeoutStartSec 约束吗？

这个时限也适用于重载。按手册，超时会令该次重载失败并返回失败状态，已有服务继续运行。失败状态说明管理器没有在时限内看到所需的完成结果。接下来还要读应用代次和日志，再决定是否重试。比如在演练里，开关文件未及时出现时，仍需检查应用停在等待、已经应用，还是后来又走了其他路径。
