同一个组件排到前面，为什么又执行了一次初始化？

用同一原生自定义元素比较 insertBefore 和 moveBefore 的回调，再检查断开树中的首次插入限制。

正文

核心要点

  • 节点引用和列表最终顺序不能区分两种生命周期。
  • 实现 connectedMoveCallback 的组件可在符合条件的移动中避免兼容性的断开再连接。
  • 首次插入与已有节点移动需要不同操作。

列表把 B 排到 A 前面，B 的对象引用没变，组件仍可能再次运行连接回调。对于已经插入的原生自定义元素，insertBefore 和 moveBefore 能得到相同的顺序，却走不同的生命周期路径。判断重复初始化来自哪里，应同时看移动方法和组件定义了哪些回调。

同一个对象能经过两次连接

普通插入可以把已经有父节点的元素移到新位置。DOM 的节点插入规则处理已有父节点的情况时，要经过相应的移除和插入过程。设想队列行的连接回调用来建立订阅，断开回调负责清理。移动时如果依次运行清理和建立，即使界面没有丢失行对象，也会发生额外工作。是否重复建立订阅、是否重置内部数据，取决于组件如何写这些回调。

DOM 标准定义的移动方法改用移动算法。对本篇所用的普通已连接树，如果元素定义了 connectedMoveCallback，移动会触发它。HTML 对自定义元素移动的说明同时保留了兼容路径：没有这个回调的旧组件，在这种移动中仍可收到断开和连接回调。仅替换调用者使用的 DOM 方法，未必能改变现有组件的初始化行为。

因此，不能把连接回调的调用次数直接当成对象创建次数。它也可以反映同一个组件曾断开再接入。反过来，连接次数没有增加，也不足以说明整个组件对位置变化毫无感知。如果组件依赖新容器提供的上下文，可以在移动回调里重新读所需信息，只更新受位置影响的部分。让移动回调调用整套初始化，仍可能复现应用原有的重置。

把顺序、身份和回调分三项核对

下方是一个完整的独立 HTML 文件，尚未在浏览器执行。两个容器都从 A、B 开始，使用同一个自定义元素定义。定义完成后初始连接会写入日志，点击按钮时先丢弃这批记录，再分别重排。日志中的身份用元素 ID 区分，顺序则从容器子元素读取。示例只观察原生 DOM，不依赖列表框架或远端服务。

<!doctype html>
<meta charset="utf-8">
<title>Custom-element reorder comparison</title>
<section id="insert"><x-order-row id="ia">A</x-order-row><x-order-row id="ib">B</x-order-row></section>
<section id="move"><x-order-row id="ma">A</x-order-row><x-order-row id="mb">B</x-order-row></section>
<button id="run" type="button">Compare once</button>
<pre id="out"></pre>
<script>
const events = [];
const record = (type, element) => events.push([type, element.getAttribute("id")]);
class OrderRow extends HTMLElement {
  connectedCallback() { record('connect', this); }
  disconnectedCallback() { record('disconnect', this); }
  connectedMoveCallback() { record('move', this); }
}
customElements.define('x-order-row', OrderRow);
const byId = id => document.getElementById(id);
const [insert, move, ia, ib, ma, mb, run, out] =
  ['insert','move','ia','ib','ma','mb','run','out'].map(byId);
const report = () => events.splice(0);
const order = parent => Array.from(parent.children, el => el.textContent);
run.onclick = () => {
  run.disabled = true;
  report();
  insert.insertBefore(ib, ia);
  const ordinary = { order: order(insert), same: insert.firstElementChild === ib, events: report() };
  const supported = typeof Reflect.get(move, 'moveBefore') === 'function';
  let atomic = { supported };
  if (supported) {
    move.moveBefore(mb, ma);
    atomic = { order: order(move), same: move.firstElementChild === mb, events: report() };
  }
  out.textContent = JSON.stringify({ ordinary, atomic }, null, 2);
};
</script>

第一组的预期是顺序变成 B、A，首项仍等于原来的 B，事件为 ib 的 disconnect、connect。第二组在实现支持时同样得到 B、A，首项仍等于原来的 B，事件只出现 mb 的 move。对照真正有用的地方是前两项都相同。假如只保留“排序已完成”或“引用未变”的断言，两种路径就都通过，正好漏掉需要解释的重复连接。

没有方法的环境会在第二组输出 supported 为假。即使方法存在，若日志没出现预期，也应记录版本和实际回调，再核对该环境实现了哪部分；示例没有把特性检测当成通过。若在应用里选择兼容回退，可以改用普通插入，但应承认它采用普通生命周期。依赖移动不重建订阅的组件，不能把这两个方法包装成行为完全相同的替换项。

这个样本的 x-order-row 只写日志，没有计时器、焦点状态或页面内嵌文档。它因此能隔离生命周期，却不能证明任意具体组件的状态都保住了。实际验收可以另测输入值、编辑选择或连接资源，但要先为每项定义“移动前的哪一状态需要持续”。一个顺序正确的截图既看不到旧订阅是否清理，也不能告诉维护者回调跑了几次。

调整容器时，组件是否需要重新读取配置

列表内部重排与换到另一个同树容器是不同使用场景。假设卡片移到另一栏后采用那一栏的分组名称，组件就算保住了原状态，也需要读取新的栏位。把读取栏位与打开订阅拆成两项动作，可以让连接时执行两项，移动时只更新位置相关项。若业务确实要求移到新栏就结束编辑，则应明写这个行为，不依赖偶然的断开回调把草稿清空。

测试可以从相同输入开始，分别改顺序与换栏位。预期前者维持原编辑内容，后者保留内容但更新分组，或者根据产品定义明确结束编辑。这里没有执行产品验收。站内DOM 分发期间的节点引用说明同一引用可以活过事件分发；本例补的是树中移动时，引用依旧也可能出现不同回调。

可以给真实订阅写一条独立的验收路径。设定每个队列行只订阅自己所属栏目，先在原栏推送一条通知，再移动到新栏，分别从两栏各推送一条带编号的通知。若编辑内容应保留，核对三个时点的草稿值；若订阅必须切换，核对接收记录只包括原栏第一条和新栏新通知。仅查看回调数只能定位经过的生命周期，不能证明旧订阅已取消，尤其是在组件把取消工作排入异步任务时。如果旧栏目在移动后仍收到来自该行的回应，检查旧订阅何时解除。若产品允许短暂重叠，定义重复通知如何识别，避免把偶然未重现当作设计成立。

刚创建但还没插入的节点能直接用 moveBefore 吗？

不能用在这里的首次插入。以 document.createElement 创建新的普通元素，此时它自己的根与已连接容器的根不同；DOM 移动算法的第一项检查会在这种情况下抛出 HierarchyRequestError。主例里的 B 早已和目标容器同树，这个新条件专门改变了根。验证时先对全新的节点调用该方法，捕获并检查异常名称，再用 appendChild 或 insertBefore 把节点第一次接入。两种动作不应共用一条“移动成功”的断言。
