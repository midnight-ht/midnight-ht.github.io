heapq 的任务优先级相同，为什么开始比较字典？

比较两字段与带序号的堆项，用未执行的标准库示例核对同优先级顺序、负载比较和重新入队策略。

正文

核心要点

  • 优先级相同会使两字段元组继续比较负载。
  • 独立入队序号定义同优先级的弹出顺序。
  • 重新入队是否保留原位置取决于队列政策。

用 (priority, payload) 把任务推入 Python 的堆，两个优先级相同时，元组会继续比较 payload。如果 payload 是两个内容不同的字典，第二次推送可能抛出 TypeError。需要同优先级先进先出时，可以给堆项加上单调递增的入队序号，让比较在抵达任务对象之前分出先后。

设想一个导出服务在单进程中维护待办队列。普通导出优先级为五，用户主动触发的紧急导出为一。同级任务需要按照本进程接收顺序排队，避免多次刷新后一个早到的任务总被后来的任务越过。这个选择只针对队列的领取顺序，执行时间、是否并发以及哪个任务先完成，还由消费者决定。

出错的地方是平局时的第二次比较

Python 3.14.10 的 heapq 文档专门讨论优先队列的稳定性和不可比较任务。元组按字段从左向右比较。前两个任务只要优先级不同，比较就可以在第一项结束，字典一直没有被拿来排序。因此，只用不同优先级测代码，很难发现队列项少了并列条件。

更隐蔽的情形是 payload 恰好可比较。假如它是字符串，程序可能一直正常运行，但同级任务会按字符串排序。把请求编号的字符顺序误当作入队顺序，不一定会报错，却会让测试之外的任务顺序改变。测试必须包含第二个任务的值在字典序上更小的情况，才能看到这两份规则是否真的等价。

可比性与稳定性是两个条件。让任务对象不参与比较，可以阻止字典触发 TypeError；若所有同级项在比较时仍相等，堆并没有承诺按插入顺序弹出。文档提供的 entry count 同时承担两份责任：它使同级项具有明确定序，并确保两个不同入队记录不会走到 payload 的比较。

在两个新堆上验证失败与顺序

以下 Python 标准库例子未执行。两个字典的内容刻意不同，失败示例和修复示例各用一个新堆；如果故意触发异常，例子不会把原堆继续交给消费者。教学任务仅保存在内存中，没有发起导出。

from heapq import heappop, heappush
from itertools import count

broken = []
heappush(broken, (5, {"id": "A"}))
try:
    heappush(broken, (5, {"id": "B"}))
except TypeError:
    print("tied priority compared two payloads")
else:
    raise AssertionError("expected incomparable payloads")

ready = []
sequence = count()
for priority, task_id in [(5, "A"), (5, "B"), (1, "C")]:
    heappush(ready, (priority, next(sequence), {"id": task_id}))
claimed = [heappop(ready)[2]["id"] for _ in range(3)]
assert claimed == ["C", "A", "B"], claimed
print(claimed)

独立预期是第一个堆在第二次推送时进入异常分支，第二个堆按 C、A、B 弹出。C 后到却排在前面，因为一比五更紧急；A 先于 B，因为两者优先级相同而 A 的入队序号更小。两条断言各有用处。如果实现始终按接收时间处理，第一条正常出队会错；如果按任务内容给同级项排序，后两项的先后未必符合合同。

另做一份可比较负载对照。先推入 (5, "Z")，再推入 (5, "A")，两次弹出将先给 A 再给 Z，即使 A 后到。给两条记录分别加序号零和一后，期望就反过来，先 Z 后 A。这个用例刻意让负载的自然顺序与接收顺序冲突，能抓住那类从不报错、却把字段比较误当业务排队规则的实现。两份对照都从空堆开始，预期无需先观察一次输出才能写出。

检查顺序要调用 heappop，而不能直接遍历堆数组。堆维持的是父节点与子节点的局部关系，能从根拿到下一个最小项；内部存储无需整体有序。展示一份待办列表时，如果界面确实需要完整排序，可以在副本上按优先级和序号排序，避免为了显示就把正在消费的队列改变。

序号在哪里分配，由领取合同决定

如果一个线程独占该堆，就在它将任务加入队列时分配序号。生产者在外部先生成请求号，并不表示负责队列的线程按这个编号顺序收到了任务。两个提交者交错执行时，需要先定义哪个动作算完成入队，再在相同的协调边界下分配序号和写堆。若业务要求以其他入口先后为准，入口必须提供能比较的记录，不能从消费时的序号反推。

进程内计数器适合本例。多个进程各自从零开始时，两个计数器的数值会重复，单台机器的单调时钟也没有提供跨机器的一致入队顺序。若进程重启后仍要求保留队列先后，序号和记录的存活期限要一起设计。仅保存任务字典，然后在重启时从零依次编号，会使新的顺序依赖恢复记录的读取方式。

有时产品确实不关心同级的先后，只要求负载不能被拿来比较。用数据类包装任务、把 payload 标为 compare=False，可以使这一选择更清楚。要是同时又对用户承诺先进先出，就把序号加入比较字段，而不是依赖今天恰好观察到的弹出顺序。站内的分页顺序与跨页一致性讨论数据库如何为并列记录确定顺序；这里的序号只服务一次入队，不承担跨页快照或并发执行结果。

删除后以同样的优先级重新加入，会回到原来的位置吗？

先选重加政策。文档展示了把旧条目标成已移除、再推入新条目的方式。采用这个做法且每次推送分配新序号时，重加会进入同优先级队尾。举例说，A 和 B 先后在优先级五入队，A 被取消后再以五加入，新的一次 A 会排在 B 后面；弹出时还要跳过已标记的旧 A。

若重试需要保留首次领取之前的位置，就必须保留相应原始顺序并处理旧条目与新条目的身份，避免同一个有效位置同时存在两条活动记录。不要直接就地修改堆项的比较字段，原有父子关系可能因此失效。验收要列出取消前、重加后、实际领取时的任务身份，证明旧记录不会再被当成新任务执行。这个重加对照仍是未运行的推演；主例的三次出队也没有验证进程重启、并发和任务交付。
