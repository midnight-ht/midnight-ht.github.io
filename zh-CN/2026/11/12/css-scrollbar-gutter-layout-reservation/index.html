面板外宽没变，内容变多后为什么换行了？

固定 320px 外框，比较 auto 与 stable 在经典和覆盖式滚动条下的可用宽度，并补双边对齐条件。

正文

核心要点

  • 经典滚动条出现时可挤占盒内宽度。
  • stable 可以提前预留经典滚动条空间。
  • 覆盖式滚动条不因此分配 gutter。

搜索结果从四条增加到二十条，侧栏外框仍宽三百二十像素，文字却可能因为内部变窄而换行。经典滚动条出现时会占用盒内空间。在同一个滚动容器上使用 scrollbar-gutter 的 stable 值，可以让这份空间在短列表时就预留。覆盖式滚动条没有同样的预留效果。

先找哪一层少了宽度

CSS Overflow Level 3 对 scrollbar-gutter 的定义区分两类滚动条。经典滚动条在 gutter 中显示，占用布局空间；覆盖式滚动条在内容上方绘制，不为其占出一条槽。宽度和所在边由用户代理决定，可能受浏览器、系统偏好和文字方向影响。把十七像素当成组件常量，既无法从规范推导，也难以说明截图所在环境。

对普通面板而言，overflow 为 auto 时，经典滚动条在真正溢出后才要求相应的槽。保持同一设置、将 gutter 改成 stable，槽可以在内容还未溢出时存在。它改变的是留位条件，不能单凭声明判断滚动条正在绘制。若实际平台使用覆盖式滚动条，两种取值都没有这份占位差异，页面在两台机器上表现不同也有合理的解释。

设想一个靠右的检索面板，有边框，里面的两列文字在宽度阈值附近换行。外框并没有缩，边框也没有变厚。经典滚动条挤占余量后，文本与旁边计数的距离变了。此时只比较外沿位置，无法解释为什么短列表正常、长列表失败。与组件外框和内容宽度里的计算相邻，本例固定边框和内边距，单独检查槽是否改变剩余宽度。

两个等宽面板，四份测量结果

以下是完整本地 HTML，尚未在浏览器执行。两个样本的边框外宽、边框宽度、行高和盒内高度相同，一个使用初始槽策略，另一个指定 stable。四条二十像素高的记录能装入九十六像素的可用高度，二十条则不能。代码使用短标签避免人为制造横向溢出。按钮在两种输入间切换，报告各自的外宽、clientWidth 与内容是否高于滚动口。

<!doctype html>
<meta charset="utf-8">
<title>Measure scrollbar gutters</title>
<style>
.panel {
  width: 320px; height: 100px; box-sizing: border-box;
  border: 2px solid; overflow: auto; padding: 0; margin: 0 0 8px;
}
#stable { scrollbar-gutter: stable; }
.row { height: 20px; line-height: 20px; white-space: nowrap; }
</style>
<button id="short" type="button">Four rows</button>
<button id="long" type="button">Twenty rows</button>
<h2>Auto</h2><div class="panel" id="auto"></div>
<h2>Stable</h2><div class="panel" id="stable"></div>
<pre id="out"></pre>
<script>
const get = id => document.getElementById(id);
const [auto, stable, short, long, out] =
  ['auto', 'stable', 'short', 'long', 'out'].map(get);

function setRows(box, count) {
  const rows = Array.from({ length: count }, (_, i) => {
    const row = document.createElement('div');
    row.className = 'row';
    row.textContent = 'Result ' + (i + 1);
    return row;
  });
  box.replaceChildren(...rows);
}
function report(box) {
  const { clientWidth, clientHeight, scrollHeight } = box;
  const { width } = box.getBoundingClientRect();
  return { width, clientWidth, overflow: scrollHeight > clientHeight };
}
function show(count) {
  for (const box of [auto, stable]) setRows(box, count);
  out.textContent = JSON.stringify({
    count,
    supported: CSS.supports('scrollbar-gutter', 'stable'),
    auto: report(auto), stable: report(stable)
  }, null, 2);
}
short.onclick = () => show(4);
long.onclick = () => show(20);
show(4);
</script>

在经典滚动条宽为 g 且 g 大于零的环境里，未留槽面板的短列表预期有三百一十六像素的 clientWidth。长列表加上竖向滚动条后，预期从中扣去 g。预留面板在短列表时已经扣掉 g，因此它自己的长短宽度应相同。外沿都应保持三百二十像素。若环境是覆盖式滚动条，四个记录的宽度预期一致，长列表仍需能滚动。

核对时先确认长列表真的溢出，再比较两个面板各自的宽度差值。面板结果相同可能表示该环境本来就是覆盖式，也可能是声明未受支持或样本没有构成溢出。CSS.supports 只报告声明能否被接受；它本身不能判定当前滚动条用哪种模式。用 auto 样本自己的前后差值来判断是否实际丢失宽度，比先把机器归为某个操作系统更可靠。

示例刻意让文字足够短，借此隔离宽度变量。迁移真实面板后，可以放回刚好会在临界处换行的两列标签，并同时检查短、长、加载占位与语言变化。若长列表不再挤压布局，却让短列表的计数在初始状态提前换行，说明稳定的内部宽度仍然比设计要求窄。可以重新安排计数列或缩短合理的显示内容，单靠预留规则无法给面板增加空间。

实际排障时还应固定缩放、窗口宽度和文字方向。一次只改行数，记录短列表到长列表的成对结果，再按相反次序切回来确认变化可复现。若缩放或侧栏折叠同时改变外沿，不能直接用这一次差值归因。把外宽变化与内部空间变化分开记，能避免把响应式断点当作槽宽。生产样式若给面板设置了最小宽度或让父级跟随内容收缩，还应先在独立样本确认槽的预期，再逐项还原约束。这个样本不提供跨引擎像素一致性的结论。

哪个容器该承担留位的代价

如果应用只在某一处动态加载搜索结果，先把留位策略设在那个真正滚动的面板。页面可能还有另一个更外层的滚动容器，它的宽度预算和使用频率不同。给祖先添加声明既不能替子面板保留一条槽，还可能让无关页面内容提前减少可用宽度。若状态切换同时把滚动从面板移到外层，重新判断需要保护的宽度边界，再做独立对照。

稳定留位适合突然溢出会改变读写任务的区域，例如在短、长结果之间切换时需要维持列表列头对齐。少量只读文字的面板若大多数时间不会超出，预留一条从未使用的槽也有成本。可以把测试决策写成“无滚动时仍保留相同的列宽”，再检查短列表的最低可用宽度是否能接受。这样能说明为什么只在一个面板设置，而不是把整个站点出现过一次换行都归因于滚动条。

一侧留槽让内容偏离外框中心怎么办？

如果验收要求元素相对于整个外框居中，可以另试 stable both-edges。规范要求，当一条 inline 边有 gutter 时，对面的 inline 边也保留一条，避免只从一侧扣空间。假设单边宽度为 g，两个等宽槽可以保持对称，但内部比单边方案再少一个 g。覆盖式滚动条没有这两条槽。这个对照应比较内容中心和边框中心，并同时记录最窄内容能否放下；只断言两边相等可能看不到总空间已减少。
