Redis 工作者取到任务后崩溃，任务留在哪里？

用两个 Redis 列表检查任务从领取到确认的状态，并判断工作者中断后该从哪条证据恢复。

正文

核心要点

  • LMOVE 在一条命令里把任务从待处理移到处理中。
  • 业务操作完成后才能确认该领取。
  • 列表状态相同的中断可能需要不同的业务恢复动作。

Redis 工作者弹出一条任务后崩溃，待处理列表里已经找不到这条任务。用 LMOVE 领取，Redis 在同一条命令里把任务移入处理中列表。恢复程序有了一个可检查的位置，接下来还要判断这次工作完成了没有。

以生成导出文件为例。待处理列表里依次有任务甲和任务乙。工作进程领取甲，准备读取数据时退出。如果它只用 LPOP，甲已经从列表移除，检查待处理列表只能看到乙。若它用 LMOVE，甲仍可以从处理中列表查到。此时乙可供另一个工作进程领取。Redis 的移动动作回答了任务在哪里，导出文件是否已经生成需要另找证据。

领取前、领取后、确认后

下面使用 Redis Open Source 6.2 或之后的 LMOVE 命令。命令未运行，应在自有隔离实例或确保没有其他写入的测试键上验证。两个测试键起初都不存在，不复用线上队列。列表内容一律按从左到右记录，左右的位置与领取方向一起验收。

RPUSH {move-demo}:ready job-a job-b
LRANGE {move-demo}:ready 0 -1
LRANGE {move-demo}:processing 0 -1

LMOVE {move-demo}:ready {move-demo}:processing LEFT RIGHT
LRANGE {move-demo}:ready 0 -1
LRANGE {move-demo}:processing 0 -1

LREM {move-demo}:processing 1 job-a
LRANGE {move-demo}:processing 0 -1
LRANGE {move-demo}:ready 0 -1

写入后，ready 是 [job-a, job-b]，processing 为空。LMOVE 返回 job-a；随后的两个 LRANGE 应分别得到 [job-b] 与 [job-a]。这里停下来模拟退出，不提交 LREM。恢复时应先看到甲仍在处理中，再查应用记录。如果已经由原工作者完成业务操作并正常确认，LREM 应移除一条，processing 的查询结果为空，ready 仍只有乙。不要在同一次断点对照里同时把甲重领并确认，应该从相同初态分别走中断与完成两条路径。Redis 文档描述了原子移动和完成后移除的用法。Redis LMOVE。

用两条不同的命令也可以写出先弹出再登记的代码。只要工作进程在两个命令之间退出，就会留下新的空窗。这里的 LMOVE 把移出和移入放在同一条 Redis 命令里。测试不能只看进程最终是否退出成功，应该让测试钩子停在领取返回之后、确认之前，再从另一个连接核对两个列表。这一条断言只证明 Redis 中可检查的移动状态。若客户端在回复到达之前就断开，还要从服务端已有状态或应用可持久查询的领取记录重建事实，不能只根据客户端异常推断甲仍在待处理列表。

把领取回包丢失也做成一次独立测试。若服务器已经把甲移到处理中，客户端随后盲目再发同一条移动命令，下一次可能领取乙。两个动作在命令级都合法，第一次的不确定性却仍未解决。测试可以在代理丢弃第一次回复以后先查两张列表，保留原来要领取的甲和可能随后被领走的乙作为两个独立对象。如果多个工作者共用处理中列表，只按列表顺序也不能把某一项归给特定连接。需要关联领取请求与业务记录时，另外设计能查询的关联身份，再在同一次故障演练里核对它。

按业务状态决定重领

设想导出服务已经接受甲并创建了文件，工作进程还没向 Redis 确认就退出。只看 processing，和刚领取就退出的甲长得一样。若恢复程序直接把它交给另一位工作者，外部服务可能收到两次生成请求。业务侧可以用稳定的任务编号查询已有导出结果，或使用接受该编号的幂等写入接口。只有外部服务支持相应的查询或幂等合同，才能用该记录决定重复请求怎样处理。对照测试可以在两个地方中断，一次在调用外部服务前，另一次在服务接受后。Redis 的列表预期相同，应用恢复动作应能按外部证据区分。

只把任务放进处理中列表也不会自动判定超时。恢复程序需要自己的领取时间、过期条件与重领操作，尤其要防止长任务尚在执行就被接手。可以先做一个无并发的验证，故意中断工作者，记录应用怎样识别遗留项，再检查重新放回时的位置是否符合队列规则。如果之后加入多个恢复进程，要让它们同时尝试接手同一个过期项，并检查应用只登记允许的一次新领取。这个并发控制需要另外设计；前面的命令只列出串行正常确认。

Redis 实例自身故障时，还要单独验收持久化和故障切换。一个客户端看见命令成功，并不能替代重启后的列表检查。在集群环境使用两个键时，应按所用 Redis 部署的多键规则确认路由；样本的花括号使用相同标签，但本文没有验证任何集群配置。也不从这组状态断言推出跨系统的恰好一次交付。站内的 Redis 事务执行错误 涉及一组命令的错误语义，本例关心单条移动之后的恢复记录。

两条任务的消息正文相同，怎么确认正确的一条？

把不同任务写成不同的列表元素，例如为两次内容相同的导出请求分配 job-a 和 job-b，再让工作者只确认领取时收到的身份。只存相同的任务正文时，LREM 以列表元素值匹配，无法据此识别工作者完成的是哪一份。更难的情形是同一业务任务重领以后，旧工作者才恢复。仅使用相同任务编号进行确认，旧工作者可能误删新的领取。需要为不同领取分配可区分的凭据，并把确认动作绑定到当前有效凭据；若保存在独立记录里，校验和确认之间的并发边界也要验收。可以给同一任务模拟两个领取凭据，让较早的确认迟到，检查它无法移除较新的领取。本节未执行，也没有声称示例队列实现了凭据协议。
