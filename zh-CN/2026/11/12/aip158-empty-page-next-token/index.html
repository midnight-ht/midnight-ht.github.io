列表返回空数组，还有 next_page_token 时要停吗？

用三页目录响应复现空页导致的漏读，按 AIP-158 约定以续页 token 作为结束依据。

正文

核心要点

  • AIP-158 允许带续页 token 的空页。
  • 客户端按续页字段判断是否到达终点。
  • 异常中止应区别于服务端声明完成。

目录接口第二次返回零条，客户端便显示“已加载全部”。但第二份响应里还有 next_page_token，第三次请求原本会返回一条记录。对于采用 AIP-158 的接口，结束条件是响应的续页字段为空。列表数组当前没有成员，只说明这份响应没有可追加的项目。

先写出三份可以让错误客户端失败的响应

Google AIP-158 的分页指导允许一页返回少于请求上限的记录，甚至在还没到结尾时返回零条。服务端只有到达集合末端才发送空的下一页标记；若还没到末端，或者来不及判断，就要给出继续的位置。页面大小因此是单次返回数量的上限。把它作为每次响应必须达到的数量，会把很多可继续的短页截断。

假设课程目录每页最多返回两项。首页有 A、B，续页标记是 p1。发出 p1 请求后，该页没有条目，却给出 p2。第三页带回 C，下一页标记为空。这里不规定为什么中间页为空，也不需要猜后端用了哪种排序和存储。只用响应合同，就能确定哪一页触发下一次请求，哪一页结束。服务端若另有计数器，也不能拿它代替这一对照，因为验收关注的是这一条遍历实际读到了什么。

下面是可独立运行的本地 Node 示例。请求桩按输入 token 给固定响应，并记录请求序列。首次请求用空字符串代表没有续页字段，第三份响应中的空字符串代表服务端声明结束。两处空值位于不同方向，代码里分别有起点和终点。样本没有请求目录服务，也未验证编码、权限或并发一致性。

import assert from 'node:assert/strict';

const replies = new Map([
  ['', { items: ['A', 'B'], next_page_token: 'p1' }],
  ['p1', { items: [], next_page_token: 'p2' }],
  ['p2', { items: ['C'], next_page_token: '' }],
]);
function traverse(stopOnEmpty) {
  const requests = [], result = [];
  let token = '';
  for (;;) {
    requests.push(token);
    const reply = replies.get(token);
    if (!reply) throw new Error('unexpected fixture token');
    const { items, next_page_token: next } = reply;
    result.push(...items);
    if (stopOnEmpty && items.length === 0) break;
    if (next === '') break;
    token = next;
  }
  return { requests, result };
}
const complete = traverse(false);
const broken = traverse(true);
assert.deepEqual(
  [complete, broken],
  [
    { requests: ['', 'p1', 'p2'], result: ['A', 'B', 'C'] },
    { requests: ['', 'p1'], result: ['A', 'B'] },
  ]
);
console.log(JSON.stringify({ complete, broken }));

正确分支预期访问初始位置、p1、p2，最终结果 A、B、C。旧分支把空项目页当终点，在 p1 就停住，只留下 A、B。这里的两份预期结果根据独立的三行响应表列出。若测试只看首次请求或一条有数据的末页，两个分支都可能通过。观察请求序列还有助于分清漏读发生在服务端没给 token、客户端没回传，还是下一次请求失败。

可以把另一个反例安排成首页只给 A 和 p1。若客户端按“不足两条就停”，甚至不会读到中间页。空数组分支与数量小于上限分支虽然常写成同一个条件，回归时分别准备输入更容易定位旧假设。这个例子有意使用两条的首页，使旧逻辑的失败发生在指定的中间响应，而不是因为第一步就少于上限。

给继续、完成和异常中断保留各自状态

客户端追加当前页的项目，然后查看 next_page_token。令牌非空时继续，直到获得一份空令牌的响应。如果请求 p2 失败，可以保留已经成功读到的 A、B 与最后一次可重试的位置，并显示未完成。用户不应在同一个界面看到“已加载全部”，随后又因为重复操作得到此前缺失的 C。针对导出任务，可把读取成功和写文件成功另外记录；空页只是其中一次可继续的读操作。

为了避免坏接口让客户端无限循环，可以对同次遍历设置预算，或在已定义的合同下拦截不该重复的续页标记。这种防护触发时应报告无法完成，并留下足够定位的信息。它代表客户端按自己的预算停止，不等价于服务端已经声明集合结束。示例用有限的已知响应表演示正常遍历，遇到不存在的 token 会抛错，没有实现线上重试、取消或空页上限。

页面如果用无限滚动，一份空中间页不会增加列表高度，滚动哨兵的位置也可能没有变化。仅等下一次滚动动作再发请求，用户可能已经滑到底，界面便一直停住。接口层可以在同一次加载动作里继续读取，直到拿到可见项目、真正结束或达到本次预算。产品应同时提供清楚的继续入口，避免等待中的界面看起来像读完了。这个决策依赖交互设计；协议只给出了允许继续的位置，并不要求立即耗尽所有页。

可以据此组织一条独立的界面验收。初始界面已有两条，点击继续后桩先返回空中间页。检查界面不能显示终止文案，并记录请求是否已发往下一位置。再让第三次请求产生失败，重试时核对它是否仍从同一续页位置开始，并确认原先两条没有被复制。最后用成功响应恢复第三条。这个步骤表用于确定组件状态与网络状态的对应关系，完整代码只验证请求顺序与列表结果，尚未实现这套界面。

令牌也只是续页位置。AIP-158 的令牌不透明要求说明客户端应把它当作不透明字符串，服务端仍照常判断权限。不要从本例中的 p1 与 p2 推出它们在真实系统中必须可排序或必须含有行号。稳定排序和跨请求快照是另一项契约，本站PostgreSQL 排序与分页边界讨论了行定位在数据变化时的限制。这里即使三份响应始终按同一固定顺序，也能复现客户端提前终止。

继续翻页时能把 page_size 从二改成一吗？

可以，若端点采用 AIP-158，后续请求变更 page_size 时服务端要使用新大小，其他请求参数应保持匹配。把主例第三次请求改为 p2 加 page_size 一，筛选继续使用原值，预期调用参数中只有大小改变。若在同一次请求同时改成另一个课程范围，旧 token 不应再代表新查询的位置，应重新从没有 token 的请求开始。这个分支引入的是续页期间的请求参数变化，主例三次都沿用同样上限。验收时不要把服务端返回不足一页的事实当成已经尊重新上限的唯一证据，还应检查实际请求以及端点处理的参数。
