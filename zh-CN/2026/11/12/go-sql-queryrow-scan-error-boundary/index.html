Go QueryRowContext 返回了对象，为什么 Scan 才报错？

用四个测试驱动输入理解 Go 查询对象、已知查询错误和 Scan 结果的区别。

正文

核心要点

  • 非空 Row 仍需要检查 Scan。
  • 分别处理缺失行、查询错误和列转换失败。
  • 读取第一行不能证明结果中只有这一行。

Go 的 QueryRowContext 已经返回了一个 *Row，调用者却可能直到 Scan 才收到错误。要返回查询结果，先处理 Scan 的返回值。指针存在只说明拿到了供后续读取的对象。

假设后台按订单编号查询一笔总额。旧代码拿到 Row 就记录查找成功，稍后再读取金额。如果编号没有匹配记录，这次查询最终应报告缺失。如果驱动直接返回错误，或者金额字段无法写入目标类型，服务也拿不到一个可交付的金额。三种情况最终都能在 Scan 上遇到错误，但它们对调用方的意义各不相同。

用四个输入固定结果

下方是未执行的标准库教学程序。它实现了最小的测试驱动，收到的是固定场景名而非 SQL，目的在于隔离 database/sql 的行为。没有启动真实数据库，也没有验证任何数据库驱动的查询语法、取消时序或类型映射。使用同一个读取入口，在每次调用时把金额初始化为零，直接观测 Row、Row.Err 和 Scan。

package main

import (
    "context"
    "database/sql"
    "database/sql/driver"
    "errors"
    "fmt"
    "io"
)

var offline = errors.New("fixture query failure")

type fixtureDriver struct{}
type fixtureConn struct{}
type fixtureRows struct{ values []driver.Value }

func (fixtureDriver) Open(string) (driver.Conn, error) {
    return fixtureConn{}, nil
}

func (fixtureConn) Prepare(string) (driver.Stmt, error) {
    return nil, errors.New("unexpected Prepare")
}

func (fixtureConn) Close() error { return nil }

func (fixtureConn) Begin() (driver.Tx, error) {
    return nil, errors.New("unexpected Begin")
}

func (fixtureConn) QueryContext(_ context.Context, scenario string, _ []driver.NamedValue) (driver.Rows, error) {
    switch scenario {
    case "ok":
        return &fixtureRows{values: []driver.Value{int64(12)}}, nil
    case "missing":
        return &fixtureRows{}, nil
    case "bad-value":
        return &fixtureRows{values: []driver.Value{"not numeric"}}, nil
    case "driver-error":
        return nil, offline
    default:
        return nil, errors.New("unknown fixture case")
    }
}

func (*fixtureRows) Columns() []string { return []string{"total"} }
func (*fixtureRows) Close() error { return nil }

func (rows *fixtureRows) Next(dest []driver.Value) error {
    if len(rows.values) == 0 {
        return io.EOF
    }
    dest[0] = rows.values[0]
    rows.values = rows.values[1:]
    return nil
}

func main() {
    sql.Register("row-fixture", fixtureDriver{})
    db, err := sql.Open("row-fixture", "")
    if err != nil {
        panic(err)
    }
    defer db.Close()

    ctx := context.Background()
    for _, scenario := range []string{"ok", "missing", "driver-error", "bad-value"} {
        row := db.QueryRowContext(ctx, scenario)
        queryErr := row.Err()
        var amount int
        scanErr := row.Scan(&amount)
        fmt.Printf("%s row=%t query=%v scan=%v missing=%t driver=%t amount=%d\n",
            scenario, row != nil, queryErr, scanErr, errors.Is(scanErr, sql.ErrNoRows),
            errors.Is(scanErr, offline), amount)
    }
}

预期四次返回的 Row 都存在。ok 的 Row.Err 与 Scan 都为空，金额为十二。missing 的 Row.Err 为空，但 Scan 的错误满足 errors.Is(err, sql.ErrNoRows)。driver-error 的 Row.Err 已经有驱动错误，Scan 会再返回它。bad-value 的 Row.Err 为空，Scan 则在把非数字字符串写到整数目标时失败，错误既不是 ErrNoRows，也不是样本里的驱动错误。对失败分支只比较错误分类，别消费金额变量；这段程序虽然打印了它，也不会把它当成业务输出。四条预期各自成立，不依赖上一个分支的结果。

标准库文档规定，QueryRowContext 始终返回非空对象，错误留待 Scan 处理。Row.Err 能让包装器提前读取已经发生的查询错误；若它有值，Scan 也会返回这个错误。Row.Err 为空时，仍要读取结果才能知道有没有首行、列能否写入目标。空结果和转换失败让这一点在两个不同阶段可见。方法与版本见 Go 1.27.4 database/sql。

给缺失结果和读取失败不同的业务出口

在订单详情入口，产品可能把不存在的编号视为明确的缺失。处理时先调用 Scan，再让 errors.Is 区分 ErrNoRows。如果返回其他错误，就把操作名和原错误保留下来，交给调用者按上下文判断。切勿拿金额是不是零区分成功和失败，零金额也可以是一笔合法结果。对外返回什么状态由接口契约决定，库返回的缺失本身没有定义 HTTP 状态。

再补一个面向接口的正例。给订单编号八返回金额零，并要求页面仍显示这张订单；给编号九返回没有记录，检查页面走缺失分支。如果页面只验证总额占位，两个响应可能都显示零，却代表完全不同的状态。与驱动直接报错的样本一起测试，还能检查服务是否错误地把依赖故障也交给同一个缺失界面。样本的假驱动用固定字符串模拟转换失败，真实数据库的数字类型、允许的转换和应用使用的列目标仍要用真实查询单独验收。

写日志时可以把“开始查询”和“读取完成”分开。前者记录一次读取尝试，后者只在 Scan 成功且已校验业务字段以后记为成功。如果扫描的是多个字段，发生错误时某些目标可能已经有值，因此只在无错之后构造业务对象。包装库确实可以在 Row.Err 非空时记录已有错误，但在 Row.Err 为空时也要保留 Scan 失败的出口。站内的 RETURNING 与事务提交 检查写入的另一处边界；这里的依据是是否成功读取这一行。

还有一种常见排查方式是先盯住驱动日志，看连接是否成功，或者响应里有没有字段名。那些信息能解释请求到了哪个阶段，却没有验证用户最终拿到什么。给缺失、驱动失败和转换失败分别记录内部分类，再到调用处核对状态映射。回归测试还应只读取成功分支的业务金额，确认错误处理改动没有把已经存在的合法订单排除。对于调用超时和取消，需用真实驱动另测触发时点及最终错误；这里的四个固定输入没有覆盖上下文取消。

字段扩展也能作为读取契约的回归。假设订单详情新加货币代码，查询从一列金额改成先返回金额、再返回币种。需要同时更新扫描目标，保留一条金额十二、币种为 USD 的有效记录，并检查读出的两个字段各自符合预期。再送一条包含非法金额的记录，确认业务对象没有提前发布。只检查成功日志不能判断最终字段是否仍按位置匹配。若改动来自查询构建器，保存它生成的完整列清单，再用真实驱动对照空值和转换规则。这里的测试驱动只有一列，这个扩展也只是验收设计。

意外匹配两条记录时，会因为违反单行预期而报错吗？

文档说明 Scan 使用第一条匹配行并丢弃其余结果。假设两个测试行的金额依次是十二和二十，在转换成功时可得到十二；这一结果不能说明第二条不存在。如果必须按订单编号唯一，应从数据库约束和查询形状分别检查。即使订单表的编号唯一，加入一对多明细也可能让输出变成多行。需要证明输出最多一行时，可以在测试中枚举结果并断言行数，再检查任何新关联。如果需求确实是取一条代表记录，查询就应给出明确的优先顺序，并用不同金额测试选中了谁。这个追问是未执行的推演，主例没有验证真实数据中的唯一性。
