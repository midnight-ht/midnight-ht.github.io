用 withResolvers 封装回调时，谁能结算？

用单次导入回执区分等待与结算权限，再用受控断言验证两个等待者、重复通知与拒绝路径。

正文

核心要点

  • 为每次回执创建独立 Promise，按角色传递等待与结算接口。
  • 普通 Promise 的结算函数共享同一份决定状态。
  • 模块需要另行负责订阅、解除订阅和失败通知。

两处代码都在等同一张导入回执。显示徽标的模块只需要等待，如果它也拿到了 resolve，就能在导入模块交出结果之前让历史记录收到成功。用 withResolvers 封装一次回调时，把 promise 交给等待者，把结算函数留在负责这轮导入的边界内。谁能拿到哪个对象，决定了这个约定是否落地。

给回执划出写入方和读取方

ECMAScript 的 withResolvers建立一个能力记录，再把 promise、resolve 和 reject 放进返回对象。本文使用内置 Promise，没有讨论子类自定义构造方式。对比需要在构造器回调里保存两个函数的写法，这种形式把取用过程缩短了。原来应该负责成功和失败的代码仍承担同一件事。

假设导入页面同时需要更新顶部徽标和操作历史。历史模块按兑现值显示回执编号，徽标把拒绝显示为本轮导入未完成。两个模块可以等同一个对象，也可以各自安排兑现后的动作。一个模块处理自己的显示时发生错误，应该由其派生链处理；它不需要拿到导入本身的拒绝函数。两处观察到同一张回执，和两处都有权决定结果，是两个独立的接口选择。

在一个模块里分开持有者比给对象注释“不要直接调用”更具体。导入适配器调用创建函数，自己保留第二项提供的结算接口，只把第一项 reader 传给显示层。冻结 reader 对象约束的是这个示例中的外壳。它既不会冻结 Promise 的内部状态，也无法撤回此前已经传出去的结算函数。若创建两个显示模块的代码把整对返回值原样传给全部组件，示例的分工便没有生效。评审应跟随构造位置和参数传递，而非仅看返回值里有两个字段。

具体到页面装配，徽标接收的参数可以是带有 promise 的读取对象，历史记录接收同一个对象。文件读取适配器的完成回调和错误回调则直接引用两个结算函数。这样检查参数时，能在显示模块的入口看见它究竟拿到哪一份接口。假如历史组件改成只接收派生出的可显示数据，还能进一步避免它依赖导入回执的形状。

从两次通知和两个等待者读出终态

以下是固定输入的本地 JavaScript 示例。两份等待在发出通知之前注册；先成功再失败时都应得到 A17。另起一张回执，先挂拒绝断言，再发送失败，之后尝试用 B99 改写。独立预期来自明确的通知顺序和下面的解析规则，无需请求接口、用定时器争夺先后或测耗时。

import assert from 'node:assert/strict';

function openReceipt() {
  const { promise, resolve, reject } = Promise.withResolvers();
  return [Object.freeze({ promise }), { succeed: resolve, fail: reject }];
}

const [reader, { succeed, fail }] = openReceipt();
const { promise: first } = reader;
const forBadge = first.then(value => value);
const forHistory = first.then(value => value);
succeed('A17');
fail(new Error('duplicate'));
const both = await Promise.all([forBadge, forHistory]);
assert.deepEqual([Object.keys(reader), both], [['promise'], ['A17', 'A17']]);

const [{ promise: second }, next] = openReceipt();
assert.notEqual(first, second);
const failure = new Error('input is incomplete');
const rejected = assert.rejects(second, err => err === failure);
next.fail(failure);
next.succeed('B99');
await rejected;

const [exposed, wrongOwner] = openReceipt();
const { succeed: anyoneCanSucceed } = wrongOwner;
anyoneCanSucceed('too early');
anyoneCanSucceed('A17');
assert.equal(await exposed.promise, 'too early');
console.log('A17 A17; second rejected; exposed resolved too early');

CreateResolvingFunctions让普通 Promise 的两个函数共享决定状态。第一轮把普通字符串交给成功函数，之后的失败调用无法把它改为拒绝；第二轮第一次通知失败，之后的普通成功值无法改写原因。函数返回了并不意味着它改变过结果，应该观察被等待的 Promise。第二个样本的拒绝断言用相同 Error 引用核对原因，避免把任意异常都当成预期失败。

负例把结算接口里的成功函数单独交给读方。显示层先写入 too early 后，所有者即便拿着真实回执，也失去了改写资格。这个对照只模拟误用，展示的是模块之间怎样出现错误终态。先到的通知有权决定 JavaScript 对象的结果，并不证明它来自应用认可的写入方。以业务归属保护提交，还要在导入适配器接受通知的位置判断它属于哪轮任务。

让等待的起点与结束条件有负责人

每轮导入应新建一张回执。假设旧页面还持有上一轮的等待对象，第二轮不能把它当成可重置容器。如果旧回调在新一轮开始后才到达，稳妥的组织方式是让旧回调只闭包捕获旧 owner；若两轮都通过同一个事件入口，则按已经定义的任务编号判断归属。复用一个全局 resolve 变量很容易让旧通知结算新的等待者，即使两份 Promise 的创建过程都合法。

选择使用这个方法还要核对外部回调的合同。如果底层库能在注册监听器时同步给出结果，应当先建立回执，再让适配器注册。若底层永远不调用任何回调，等待也不会凭空结束。项目应决定何时解绑监听、何时报告超时、何时允许重试，以及重复通知是否只用于诊断。这里的拒绝断言只验证失败路径，没有证明外部导入被取消，或某个文件写入已经撤回。

如果适配器处理的是持续事件流，单张 Promise 只能代表一次结果。可以把它定义为“接到首个可用通知”，之后的多次事件另用与任务匹配的订阅接口。把每条通知都交给同一个 resolve，实际就会丢失首个决定之后的数据。与Promise.any 的候选选择相邻，本例关注谁能形成一个候选结果；前者关注如何选择已经独立形成的候选。

resolve 收到仍 pending 的 Promise 时，后来的 reject 能改变结果吗？

不能。这里把输入由普通字符串改成仍待定的内层 Promise。外层已经采用该结果，但还要等内层兑现或拒绝。共享的决定状态先被设置，后来的 reject 无权抢先完成；等内层交出结果以后，外层才得到对应的终态。这个条件不能从普通字符串的立即兑现外推。

import assert from 'node:assert/strict';

const { promise: outer, resolve: adopt, reject: cancel } = Promise.withResolvers();
let deliver;
const inner = new Promise(resolve => { deliver = resolve; });
adopt(inner);
cancel(new Error('too late'));
deliver('receipt from inner');
assert.equal(await outer, 'receipt from inner');
console.log('outer adopted inner');

如果适配器原本希望自己控制终态，接受另一个 Promise 作为成功值之前要清楚它代表什么。将未完成的工作交给 resolve 会把等待者的终态交给那个工作。需要单独报告超时的场景，应在传入前决定结果选择规则，然后再由负责回执的模块通知等待者。
