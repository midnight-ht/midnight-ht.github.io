发了 Prefer: return=minimal，客户端为什么还要准备读响应？

为同一个带 return=minimal 的创建请求设计两份有效 201，按端点约定处理实际响应内容与偏好声明。

正文

核心要点

  • Prefer 表达可被忽略的偏好。
  • 创建状态与响应内容多少可以分别约定。
  • 客户端应识别实际返回的状态、类型和内容。

移动端为创建书签加了 Prefer: return=minimal，测试环境仍返回一份 JSON。服务端可以忽略这个偏好，所以客户端仍需按端点约定处理实际响应。先查创建是否成功和是否带有表示，再看服务端有没有说明它采用了偏好。请求里的一行头部不足以替这些响应作决定。

RFC 7240 对 Prefer 的定义允许客户端提出期望的处理方式，也允许服务端忽略它。第 4.2 节中的 return=minimal 希望服务端用较少内容表达成功，return=representation 则希望收到资源当前状态的表示。它们属于互斥偏好。最小响应仍可以保留对调用者有用的头部，例如新资源的位置；创建状态也不因为客户端希望减少正文而改成固定的另一个数字。

让两份创建响应都能完成同一次操作

假设一个书签端点约定 POST /bookmarks 成功创建时返回 201 和新资源的 Location。它允许两种返回：空内容或带有书签对象的 application/json。这是教学合同，不能套用到其他接口。请求携带 return=minimal，服务端若采用它，可以只给位置并声明 Preference-Applied。另一个支持同一端点的环境可以忽略偏好，仍按自己的默认方式附上完整书签。两份响应都指向 /bookmarks/9，JSON 对象给出书签编号九和名称 Guide。

下方是完整的本地 Node 例子。为了隔离解析选择，它使用已归一化为小写的头部名和一个已取得的正文字符串。已采纳的样本让正文为空，另一样本给出精确的 JSON 字符串。程序不发送 HTTP、分析线上的消息定界，或证明任何真实服务器遵循偏好。预期直接从两份响应给出：两次都应记录同一位置，只有第二次有书签对象。

import assert from 'node:assert/strict';

const location = '/bookmarks/9';
const applied = {
  status: 201, headers: { location, 'preference-applied': 'return=minimal' },
  body: '',
};
const ignored = {
  status: 201, headers: { location, 'content-type': 'application/json' },
  body: '{"id":"9","title":"Guide"}',
};

function readCreated({ status, headers, body }) {
  const { location, 'content-type': type } = headers;
  if (status !== 201 || typeof location !== 'string' || !location)
    throw new Error('unexpected creation reply');
  if (body === '') return { location, resource: null };
  if (type !== 'application/json') throw new Error('unexpected media type');
  const resource = JSON.parse(body);
  if (typeof resource?.id !== 'string' || typeof resource?.title !== 'string')
    throw new Error('invalid bookmark');
  return { location, resource };
}

const results = [applied, ignored].map(readCreated);
assert.deepEqual(results, [
  { location: '/bookmarks/9', resource: null },
  { location: '/bookmarks/9', resource: { id: '9', title: 'Guide' } },
]);
const broken = ({ headers }) => ({ location: headers.location, resource: null });
assert.notDeepEqual(broken(ignored), results[1]);
console.log(JSON.stringify(results));

解析器先核对创建状态和位置，正文非空才检查媒体类型和对象形状。示例严格匹配 application/json，是这份窄合同的约束，不代表通用内容类型解析器；实际端点若允许参数和其他格式，就要定义如何识别。空字符串在两种成功形状中的含义是“创建成功、未附对象”。不要以空对象填充缺失字段，否则其他代码可能把它当成完整资源。负例直接根据调用时选择的偏好省略正文，它无法把第二个样本的 Guide 交给界面，即使网络没有任何问题。

还可以给解析器输入一份内容非空但不是预期媒体类型的 201，或者给出缺少 id 的 JSON。在当前示例的约定里，二者都应报告表示处理错误。这里不能因为错误发生在读取阶段，就推断创建失败并自动重做 POST。客户端应保留已看到的创建状态和位置，让上层选择是否单独取回结果。实际项目仍要为不确定的写入结果定义查询和重试方式。

用偏好换掉什么，由调用者先说明

如果界面只需要显示保存成功和一个可跟随的地址，可以选择请求较少内容。收到空响应时，客户端把位置交给下一步使用，保留已知状态。若用户停留在编辑界面并继续修改，下一步可能需要服务器给出的规范化标题或默认属性。此时请求更少内容未必省掉一次网络往返；调用者需要定义何时再读资源，以及读取失败后显示哪部分仍然可信的信息。

如果客户端离线时保存一份本地临时对象，带正文的分支可以把临时对象与响应对象核对，空内容分支则可能只把临时标识换成服务端位置。只有明确后续接口允许拿这个位置更新当前界面，才可把它算作保存交互的完整结果。给两种响应设计不同的后续路径，比把“有没有 JSON”映射成保存成败更贴近用户任务。站内的HTTP 204 无正文分支专门说明收到该状态后的解析边界，本题在同一个 201 状态下仍允许内容形状不同。

为不同客户端验收这个端点，可以固定创建输入，把偏好启用和忽略作为可控条件。先核对两次响应都给出新资源位置，再分别检查有表示时的信息是否被使用、没有表示时是否产生额外读取。这个测试应使用各自可区分的新请求身份，避免重复调用对同一书签造成不确定副作用。上述本地示例只验证解析分支，真实创建与后续读取尚未执行。

还应给客户端封装的返回类型留出两种成功形状。如果旧调用点默认每次都拿到资源对象，给封装添加偏好头可能把缺失值传进标题渲染。验收可从同一份书签输入分别调用列表行与编辑页，检查列表行是否只依赖位置、编辑页是否明确要求正文或发起读取。若要比较传输开销，把创建响应和随后读取放到同一轮统计，并记录实际发送次数与字节。仅凭一次空响应不能得出整个交互更省流量的结论，本文没有测量相关数据。

空正文 201 没有 Preference-Applied，能确定偏好被忽略吗？

不能。现在保留空正文和 Location，但去掉服务端的采纳声明。RFC 7240 对 Preference-Applied 的说明允许服务端用这个头明确告知已采纳偏好。没有它时，空内容可能是端点默认行为，也可能是采纳之后的结果。若合同没有另作保证，客户端可以按空内容分支处理创建，却不能据此把本次偏好执行记为已采纳或已忽略。需要观察采纳率的项目，应先定义能返回可靠证据的服务端行为。
