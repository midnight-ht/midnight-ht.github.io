高亮同样一格，为什么导航用 aria-current，标签页用 aria-selected？

沿通知设置的页面导航与手动标签页，分别检查当前位置、标签选择和键盘焦点。

正文

核心要点

  • 当前页和标签选择分别属于各自的集合。
  • 手动激活下焦点可先于选择移动。
  • 同时核对语义、面板可见性和键盘操作。

设置页左侧高亮“通知”，右侧高亮“邮件”。两个高亮在回答不同的问题：用户在哪个页面，和哪个标签面板正在显示。导航链接用 aria-current 表示当前位置，标签组件用 aria-selected 表示选择。允许键盘先看别的标签再激活时，还需要单独追踪焦点。

WAI-ARIA 的 aria-current 定义面向相关元素集合中的当前项。页面导航可把当前页链接标记为 page，在这个集合里通常只有一项当前。过程导航可能用 step 表示当前步骤，具体用词来自集合在界面中的角色。修改浏览器地址或视觉样式时，属性需要根据真实视图同步，浏览器不会从字体加粗推断业务上当前是哪页。

同一标准对 aria-selected 的定义适用于相应的可选择组件。在 tablist 内，它应表达哪个 tab 选择了所显示的 tabpanel。组件还需要把标签与其面板关联，并实际展示对应内容。仅把选中标记改成 true 而继续展示旧面板，会让用户在语义与可见内容之间遇到冲突。仅给显示中的标签加 aria-current，也没有提供这个控件应表达的选择状态。

按方向键只走到下一个标签

假设通知设置里有邮件和短信面板。产品要求先移动焦点、按确认才打开另一面板。这是手动激活模式，ARIA APG 的标签模式描述了相应的方向键和确认键。若真实项目用自动激活，则焦点和已选项通常会一起改变，验证前要先说清采用哪种交互。

下面是未在浏览器和辅助技术中运行的完整 HTML，可保存为单个文件。导航链接重新打开同一文件并携带不同页面参数。通知页的两个按钮处理方向键，原生按钮的激活由点击处理函数读取。可见面板、选中属性和焦点各有变化来源。两个选项只展示文字，真实项目仍应按内容设计面板内部焦点。

<!doctype html>
<html lang="en">
<meta charset="utf-8">
<title>Settings</title>
<style>
[aria-current="page"], [aria-selected="true"] { font-weight: bold; }
:focus-visible { outline: 2px solid currentColor; outline-offset: 3px; }
</style>
<nav aria-label="Settings">
  <a id="notifications-link" href="?page=notifications" aria-current="page">Notifications</a>
  <a id="profile-link" href="?page=profile">Profile</a>
</nav>
<main>
  <section id="notifications">
    <h1>Notifications</h1>
    <div id="channels" role="tablist" aria-label="Notification channel">
      <button id="email-tab" type="button" role="tab" aria-selected="true" aria-controls="email">Email</button>
      <button id="sms-tab" type="button" role="tab" aria-selected="false" aria-controls="sms" tabindex="-1">Text messages</button>
    </div>
    <div id="email" role="tabpanel" aria-labelledby="email-tab" tabindex="0">Email settings</div>
    <div id="sms" role="tabpanel" aria-labelledby="sms-tab" tabindex="0" hidden>Text message settings</div>
  </section>
  <section id="profile" hidden><h1>Profile</h1></section>
</main>
<script>
const byId = id => document.getElementById(id);
const [navA, navB, notifications, profile, list, mail, sms, mailPanel, smsPanel] =
  ['notifications-link','profile-link','notifications','profile','channels','email-tab',
   'sms-tab','email','sms'].map(byId);
const tabs = [mail, sms], panels = [mailPanel, smsPanel];
let selected = 0;
const moveTabStop = index => tabs.forEach((tab, i) => { tab.tabIndex = i === index ? 0 : -1; });
function choose(index) {
  selected = index;
  moveTabStop(index);
  for (const [i, tab] of tabs.entries()) tab.setAttribute('aria-selected', String(i === index));
  panels.forEach((panel, i) => { panel.hidden = i !== index; });
}
for (const [index, tab] of tabs.entries()) tab.onclick = () => choose(index);
list.onkeydown = event => {
  const { key, target } = event;
  const current = tabs.indexOf(target);
  if (current < 0) return;
  let next;
  if (key === 'ArrowLeft' || key === 'ArrowRight') next = 1 - current;
  else if (key === 'Home') next = 0;
  else if (key === 'End') next = 1;
  else return;
  event.preventDefault();
  moveTabStop(next);
  tabs[next].focus();
};
list.onfocusout = event => {
  if (!list.contains(event.relatedTarget)) moveTabStop(selected);
};
if (new URLSearchParams(location.search).get('page') === 'profile') {
  navA.removeAttribute('aria-current');
  navB.setAttribute('aria-current', 'page');
  notifications.hidden = true;
  profile.removeAttribute('hidden');
}
</script>
</html>

先打开通知页，按 Tab 进入已选邮件标签。此时通知是当前页面，邮件是选中标签和焦点所在，短信面板隐藏。按右方向键，焦点移到短信，邮件仍是选中项。按 Enter 后，短信标签被选中，短信面板显示，邮件面板隐藏。整段键盘操作期间，通知链接的当前位置都不变。再使用链接打开资料页，当前链接才改变，标签组件随通知页隐藏。这个用例把页面导航变化和控件内选择变化安排在不同的操作上。

反例可以先用独立样式类保留当前标签的视觉样式，再把两个标签上的 aria-selected 拿掉，并按同样的键操作。仍能看见一个加粗按钮，也可能仍能切换面板，但只断言样式或内容会错过缺失的选择状态。另一项检查是把焦点留在短信，随后直接 Tab 到面板。此时应进入邮件的可见内容；等焦点再次从外部进入标签组，应以已选邮件作为起点。这个预期依赖手动激活设置，用于验证焦点与选择分开的实现，没有声明某款读屏一定用同一句话播报。

按状态的拥有者组织更新

产品验收可以分别写三个问题：我在哪个页面、面板对应哪个标签、下一次确认会作用在哪个控件。页面渲染入口根据当前页面设置导航，标签组件根据选择设置面板，键盘代码按焦点规则处理移动。三个问题可以使用不同的显示方式。比如保持当前导航文字加粗、所选标签加下划线、焦点外侧画轮廓，在同时出现时仍能分辨。视觉样式应由这些状态得出，避免把通用 active 类反过来当作唯一事实。

若页面由客户端路由更新，切换页和历史返回都要回到同一份位置规则。标签面板更换后不应顺手改变左侧导航；只有产品把它定义成另一个可独立访问的页面，才需要重新讨论链接和当前位置。站内的页面标题与视图身份处理的是文档脱离正文后如何识别；本题关心用户在一个可导航集合中的位置和在一个控件里的选择。

真实路由还可能包含与视图无关的参数，例如列表排序或筛选。复制当前地址进入时，只要页面仍是通知，就应保持通知链接的语义，不应因为地址字符串与链接目标不完全相等而同时取消两项标记。项目可以定义一份导航匹配表，对直接进入、从资料页点击返回和浏览器后退分别验证。不论标签选择是否需要恢复，当前位置都应描述实际展示的页面；如果错误页没有对应的导航项，验收也应允许该集合没有当前标记。

实际交付应记录每步的可见内容、DOM 焦点与属性，再在项目支持的浏览器和辅助技术组合下检查。元素有可见样式、能被点中、在可访问性树中呈现选择，是三个可分开失败的地方。比如文本变粗但焦点轮廓消失时，鼠标试用可能觉得切换正常，键盘使用者却很难确认下次操作目标。

同一棵页面树能同时有当前项和已选项吗？

可以，前提是两者表达不同含义。设想页面树当前显示“活动 A”，用户把“活动 B”设为准备打开的选中项。此时 A 用 aria-current 表示已经显示，B 用 aria-selected 表示选择；确认打开 B 后，当前位置才改变。WAI-ARIA 在 current 条目中给出了这种并存情形。这个新例的差异在于两种状态进入同一个集合。评审应先定义当前项何时更新、选择后是否立即打开，再观察两项是否随各自动作变化。
