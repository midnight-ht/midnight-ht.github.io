GROUP BY 只写了主键，为什么还能选出名称？

对照 PostgreSQL 的主键和非空唯一键分组，用两位同名客户验收名称选择与合计粒度。

正文

核心要点

  • 主键参与分组时，PostgreSQL 可以识别该表未分组列的函数依赖。
  • 普通非空唯一约束不能代替这里的主键识别。
  • 保留身份并逐条核对金额，能发现按名称意外合并。

汇总订单时按客户主键分组，名称却能直接出现在 PostgreSQL 的结果里。把主键声明换成 UNIQUE NOT NULL，即使客户记录完全相同，同一形状的查询也会被拒绝。差别出在 PostgreSQL 认可哪一种函数依赖。

报表最初只交付客户编号和金额。产品后来要求在同一行显示姓名，于是在 SELECT 里加上客户表的名称列。两笔订单连到同一位客户时，参与聚合的行确实有两条，但名称来自同一条客户记录。按客户表主键分组时，组内的所有订单指向同一位客户，客户表上的名称也因此只有一个值。这个依据写在表定义和分组列上，换两笔订单金额也不会影响它。

两张客户表只改一项声明

下方是未执行的隔离 SQL。先建两张结构相同的客户表，第二张把主键换成非空唯一约束。两位客户都叫 Lee，刻意让名称不足以区分身份。订单表按客户编号存三笔金额。

CREATE TEMP TABLE report_customer (id int PRIMARY KEY, name text NOT NULL);
CREATE TEMP TABLE report_unique_customer (id int UNIQUE NOT NULL, name text NOT NULL);
CREATE TEMP TABLE report_order (id int NOT NULL, amount int NOT NULL);

INSERT INTO report_customer VALUES (1, 'Lee'), (2, 'Lee');
INSERT INTO report_unique_customer VALUES (1, 'Lee'), (2, 'Lee');
INSERT INTO report_order VALUES (1, 2), (1, 3), (2, 7);

SELECT c.id, name, sum(amount) AS total
FROM report_customer AS c JOIN report_order USING (id)
GROUP BY c.id
ORDER BY c.id;

原样查询预期返回 (1, Lee, 5) 与 (2, Lee, 7)。仅把 FROM 中的 report_customer 换成 report_unique_customer，重新运行这条查询，预期在语句分析时被拒绝，因为名称没有聚合、没有进入分组列，也没有满足这里认可的主键条件。保留替换后的表，改用 GROUP BY c.id, name 后预期仍返回原来的两条。最后做名称合并对照，从 SELECT 删除 c.id，改成 GROUP BY name，并删除 ORDER BY，预期得到 (Lee, 12)。若客户端在预期错误后停止提交或事务进入失败状态，要让每条查询独立运行，保留相同的样本数据。失败结果与后面两条的行值要各自验收。

PostgreSQL 18 的 SELECT 文档说明，某个未分组的列可以依赖该表的分组列，前提是分组包含该表的主键。文档也专门说明 PostgreSQL 当前只在这一条件下识别此处的函数依赖。样本里非空唯一列已经足以让人推断一个编号对应一个名称，但同一个判断没有扩展到普通唯一约束。检查时对照生产表定义，确认查询中写进分组的是哪张表的键。等值关联写在订单编号和客户编号之间，也应明确选客户基表的 c.id 来复现本例。规则见 PostgreSQL 18 SELECT。

给修复方案保留身份验收

如果交付仍是一位客户一行，保留身份编号并明确写 GROUP BY c.id, name 可以让第二种表声明下的查询通过。在本例中，编号在客户表中唯一，因此把名称一起纳入分组不会把同一编号拆成两组。设计验收时仍要逐个比较编号和金额。只比最终金额十二，会让两条客户结果与按名称合并的一条结果同时通过。只比行数也不够，两条金额可能贴到了错误的身份上。

另一种写法是在订单侧先按 customer_id 计算金额，再把聚合结果按编号关联到客户表。这时客户名称从关联到的行读取，不会作为订单聚合查询中的未分组列出现。它适合报告需要先检查订单侧的合计和缺失客户编号的情况。移动聚合位置之前，把过滤和关联的条件带入对照。如果原查询只接受仍在客户表里的记录，最终内连接仍应保留这条约束。如果报告需要展示没有订单的客户，就要单独决定缺失金额的显示，并检查连接方向与空值处理。

还需要对关联的输入行数设一个验证点。给同一位客户连上两条标签，再直接对订单金额求和，可能让每笔订单出现两次。此时主键仍能决定名称，金额也可能已经翻倍。这个反例可以单独用五元客户做验收，检查接入标签后每笔订单在聚合之前仍出现一次，或者把标签单独汇总后再联接。分组语法通过只能证明数据库接受这条查询，报表金额还依赖聚合输入。另一个站内例子涉及区分明细和汇总层级。

保存错误证据时，把最终提交的 SQL 和定义放在一起。迁移可能保留了相同的列名和数据，却换了主键声明，也可能让查询构建器引用另一层派生结果。排查先用这里的两张基表复现，随后再逐层添加视图、派生查询或报表生成逻辑。每加一层都记录原来那条合计对应哪个客户编号，避免把新层带来的字段问题和分组语法错误归到同一个原因上。

编号和展示名还可能在导出后被下游使用。导出测试可给两位客户的名称都设为同一个值，并让各自的金额不同。比对时以客户编号作为映射键，读取每个键对应的名称和金额，检查键集合完整。如果界面只显示姓名和金额，也要保留能回溯身份的隐藏字段或日志。这样即使同名两行在排序后挨在一起，核对人仍然能发现哪一位客户消失了，或哪一笔合计被贴到了另一行。

主键由两列组成，按其中一列分组够吗？

假设发票表的主键是 (tenant_id, invoice_id)，甲、乙两个租户都有发票七号，一个的备注写续订，另一个的备注写退款。按发票号分组后，七号这一组可能同时含两条发票行。要保留每张发票的身份，分组应纳入主键的两部分，此时同一个发票编号可以随不同租户分别出现。如果业务要跨租户统计同号发票，就需要定义合计如何展示，并给备注另定聚合策略，或者不输出备注。验收时故意重用编号，让单租户样本中看不出来的错误在两租户条件下暴露出来。本节也是未执行推演，主例和追问都没有验证应用查询构建器的输出。
