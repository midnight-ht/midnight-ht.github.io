git log --first-parent 为什么看不到已合并的提交？

通过同一合并端点上的两份日志，核对第一父链、功能提交与祖先证据。

正文

核心要点

  • 第一父链视图保留主线集成边界。
  • 同一端点的全父链查询可追查功能提交。
  • 记录对象哈希及有序父节点有助于复算。

发布周报里有一条合并提交，却找不到它带进来的两次修改。检查命令是否加了 --first-parent。普通日志可以沿合并提交的各条父链继续查找，带这个选项的日志遇到合并时只沿第一父节点。侧枝提交仍然可达，只是这份视图没有走到那一侧。

合并提交的父节点有顺序

下面是一种特意简化的历史。主线从基线提交 B 出发，经主线修改 N 到合并提交 M。功能分支也从 B 出发，先做 F1，再做 F2。合并时站在主线上，所以 M 的第一父节点是 N，第二父节点是 F2。这里描述的是这一份图里的父序。要核查真实仓库，应该读取提交对象的父节点，而不是根据分支当前的名字猜测合并方向。

从 M 开始读普通日志，可以经过 N 走回 B，也可以经过 F2 访问 F1 和 B。两条链相交于 B，基线只作为同一个提交出现一次。从相同的 M 开始读第一父链时，查找只经过 N 到 B。图里仍有 F1 和 F2，第一父链的观察结果则由 M、N 和 B 组成。两份日志从同一端点读取，区别来自遍历路径。这个例子省去了路径筛选与范围排除，方便把差异归因到一个选项。Git log 的提交遍历选项

团队可以用 M 描述一次集成，也可以用 F1 和 F2 描述进入这次集成的具体修改。周报读者往往关心某个功能何时进入主线，代码审计则可能要定位功能分支上的实际提交。拿到一份日志时，先问这份记录要回答哪一个问题。即使两份记录都从相同版本开始，它们也可能给出不同数量的条目。

固定同一个端点做对照

以下是待运行的独立样本。使用支持 git init -b 的 Git，在新建临时目录里创建两个分支。每一组修改写不同文件，避免把冲突解决带入本例。脚本没有在本站仓库运行，下面的成员集合是按提交图写出的预期。

set -eu
repo=$(mktemp -d)
cd "$repo"
git init -q -b main
git config user.name "History Probe"
git config user.email "probe@example.test"

printf 'baseline\n' > baseline
git add baseline
git commit -qm B
git branch feature

printf 'release notes\n' > release-notes
git add release-notes
git commit -qm N

git switch -q feature
printf 'first change\n' > feature-changes
git add feature-changes
git commit -qm F1
printf 'second change\n' >> feature-changes
git add feature-changes
git commit -qm F2
feature_tip=$(git rev-parse HEAD)

git switch -q main
git merge --no-ff -qm M feature
tip=$(git rev-parse HEAD)
git show -s --format='%h %P %s' "$tip"
git log --format='%s' "$tip"
git log --first-parent --format='%s' "$tip"
git merge-base --is-ancestor "$feature_tip" "$tip"

不要拿两条日志的输出顺序做断言。时间接近的提交可能出现在不同位置，这里的预期是成员集合。第一条应含 B、N、F1、F2、M 共五条，第二条应含 B、N、M 共三条。末行祖先检查应退出零。要留档时，把实际端点、功能提交、合并提交的有序父节点与两份输出放在同一条检查记录里。若任一命令出错，应保存出错的位置和原始诊断，再解释成员缺失。

这里留了主线独有的 N。没有它时，第一父链上的变化可能只剩 M 和 B，读者很难从周报看出功能之外还有过一次主线编辑。有了 N，预期同时检验了两个条件。功能提交应该从第一父链视图消失，主线编辑应该保留。删除功能分支这个名字也无法把对象从已经保留该父边的合并图中移走。周报最好记录固定的端点哈希，日后才能复算当时的集合。

两类验收分别留下证据

写发布纪要时，可以先把第一父链当作需要阅读的集成记录。遇到某个功能是否进入版本的追查，再针对目标对象做祖先断言，并把原变更记录和证据链接补到该合并条目下面。如果仓库采用 squash，集成点常常是新的普通提交，原功能对象未必在目标祖先链。那时需要按项目采用的交付记录核对 squash 后的对象，不能把图里的两父节点模型照搬过去。

还有一种反例是调查者在两个不同时间点运行命令。期间主线端点移动，观察到的条数变化就可能来自新提交，而不是选项本身。把同一完整端点作为两条查询的参数，可以避免这个干扰。对缺失对象或历史不全的环境，先确认本地历史能回答所需范围，再解读结果。已经发生过 revert 的情况也应保留当前树与行为检查。提交祖先与当前内容的核验

发布纪要的另一个常见任务是把合并条目关联到审查记录。可在清单中保存这次合并对象、合并前的主线对象和功能分支对象。主线下一次集成之后，仍能按原来的端点找到本次边界。若审查记录绑定的是其中一个具体修改，纪要只记合并标题就会缺少对象级证据。把功能对象放进关联字段，既保留纪要的阅读顺序，也给后来者一个明确的追查起点。

可以把独立样本改成一项报告生成测试。先把五个提交的标题和哈希写成期望清单，再让生成器固定读取 M。对于面向发布负责人的输出，检查主线编辑 N 和集成条目 M 同时存在。对于面向审计的输出，另外检查功能对象 F2 可以从 M 到达。若误把周报模式用于后一项要求，计数仍可能符合三条的预期，但对象断言将揭示你选错了证据。验收记录还应写清是否使用路径限定，因为按文件筛选的日志会引入本例刻意去掉的历史简化条件。

为什么加上 -p 后，合并提交的补丁也变了？

常见默认下，普通 git log -p 不输出合并提交的补丁。加上 --first-parent 后，合并补丁默认采用第一父格式。在上面的图里，这一段补丁描述 N 到 M 的变化，仍是一段合并差异。它不会让 F1、F2 重新成为独立日志条目。可以单独比对 git diff M^1 M 所表达的树变化，实际运行时用合并对象的真实引用代替示意名 M。显式指定 --diff-merges=off 可以关掉合并差异，适用于只要每个集成点文字记录的查询。记录查询参数与 Git 版本，避免周报阅读者把不同补丁格式误认为版本内容变化。Git log 的合并差异格式
