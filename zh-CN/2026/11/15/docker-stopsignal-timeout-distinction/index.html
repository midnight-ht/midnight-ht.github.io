Docker 已发停止信号，为什么还是强制杀掉了容器？

通过同一镜像的三次停止对照，区分 Docker 首信号和停止宽限期。

正文

核心要点

  • 检查 Docker 最初发送哪种信号。
  • 保存应用接收和完成清理的两条证据。
  • 用同一镜像分离宽限变化与实例信号覆盖。

先发哪种信号和接下来等多久是两项设置。Docker 发送了预定的停止信号以后，如果容器没有在宽限期内退出，仍可用 SIGKILL 结束它。

值班人员调整了镜像的停止信号，希望应用走完清理流程。发布演练里，应用已经打印收到信号，最后却没有写出清理完成的记录。继续怀疑是不是信号没送到，会漏掉收到之后的时间边界。相反，只把宽限改大，也无法说明应用收到的是自己预期的那个信号。验收应该分别观察处理器进入、处理器完成和容器终止。三个时刻任一缺失，都要先核对此处的证据，而不是从最后一行日志反推整段过程。

把首信号和宽限分开读

Dockerfile 的 STOPSIGNAL 定义 daemon 停止容器时选用的首信号，没有设置时通常使用 SIGTERM。创建容器时可用 --stop-signal 覆盖镜像指定的内容。Docker 的停止命令还可以单次指定信号和等待时间。等待期耗尽而容器仍未退出时，daemon 会发送 SIGKILL。这几个设置分别回答镜像默认、实例配置和本次命令采用的值。只看到 Dockerfile 里写了某项，仍不足以还原真实运行的停止路径。 Dockerfile 的 STOPSIGNAL；Docker 容器停止命令

让同一程序收到两种可辨认的信号

下面是用于隔离 Linux 容器环境的完整样本。没有构建镜像，也没有执行容器停止。程序直接作为容器的主进程，开始前注册两种处理器。USR1 分支等待六秒以表示尚未结束的工作；TERM 分支不延迟，方便观察信号配置切换。打印立即刷新。这个等待只是演练手段，不能外推为真实应用的清理方式。

FROM python:3.12-slim
COPY shutdown.py /shutdown.py
STOPSIGNAL SIGUSR1
ENTRYPOINT ["python", "/shutdown.py"]

将这份程序存为 shutdown.py，与 Dockerfile 放在同一独立目录。

import signal
import time


def stop(signum, frame):
    print(f"received:{signal.Signals(signum).name}", flush=True)
    if signum == signal.SIGUSR1:
        time.sleep(6)
    print("finished", flush=True)
    raise SystemExit(0)


signal.signal(signal.SIGUSR1, stop)
signal.signal(signal.SIGTERM, stop)
print("ready", flush=True)
while True:
    signal.pause()

拟用 docker build -t stop-signal-lab . 构建一次。启动三个不同名称的容器，其中两个直接用镜像设置，第三个在 docker run 创建时加上 --stop-signal SIGTERM。每个都应先在日志明确看到 ready，再单独执行停止命令。第一个与第三个各给十二秒等待，第二个只给一秒。命令应明确传入 docker stop --timeout 的值，避免继承某个未记录的默认。三轮都使用独立容器，不拿已经停止的一个复用前一次日志。

docker run -d --name grace-long stop-signal-lab
docker run -d --name grace-short stop-signal-lab
docker run -d --name signal-term --stop-signal SIGTERM stop-signal-lab
# Inspect each container's logs for ready before stopping it.
docker stop --timeout 12 grace-long signal-term
docker stop --timeout 1 grace-short

在看到 ready 之前不应发送停止命令。若某个容器在注册处理器前已退出，应先保留启动日志和容器状态，把这一格标为未完成，而不是借由没有完成标记宣称短宽限生效。命令本身的正常返回也只说明它完成了停止操作。验收程序需接着读取三个容器的日志，按不同名称核对每一份退出与标记。若环境拒绝重复使用已有名称，可以换整组专用名称，并同步更新命令和核对表，避免误读上一轮的记录。这个流程不需要任何真实业务输入。

实验 应用进入标记 完成标记预期
镜像默认信号，长宽限 received:SIGUSR1 有
镜像默认信号，短宽限 received:SIGUSR1 无
实例覆盖信号，长宽限 received:SIGTERM 有

短宽限作为负例，预期 daemon 在程序完成前终止容器。将标记和 docker inspect 中的容器终态一起记录。不要把收到标记和终态之间的固定时间间隔写成断言：宿主负载会影响观察到的时间。若短宽限连收到标记也没取到，先检查 ready、有效信号和日志是否可读，再判断样本是否达到想测的条件。若业务需要确认被强制终止，应另查 daemon 或事件记录，不能只凭某个退出值推断此前发生了什么。

让验收说明配置实际改变了什么

比较前两轮时，负责信号的程序和配置都一样，差异来自停止命令等待多久。比较第一轮和第三轮，时间给得一样，首信号才是变化量。若实际工程还通过编排平台运行，记录平台给这次停止操作传入了什么，而不是只保存镜像构建记录。真实服务也应确认所需的收尾动作发生在终止之前，例如写入队列确认或关闭受控连接。这些业务操作在样本中没有发生，完成标记只说明演练程序走到了指定位置。

这组试验刻意固定 exec 入口。若应用根本不是主进程，先查看入口进程怎样交接信号。先解决到达路径，再看首信号是否与处理器约定相符，最后观察耗时。测试时同时保存容器标识、创建选项、停止命令以及每个标记，才能判断两轮是否真的只改变了一项条件。清理时只移除为实验新建的容器和镜像。

如果一轮演练打印了完成标记，却没有及时退出，还要看完成标记是否写得太早。例如真实程序可能在标记后仍等待工作线程，daemon 观察到的是容器还活着。验收可要求记录开始和完成，随后由管理接口独立确认进程终止。不能把“已进入清理”当作“可以开始替换所有副本”，也不能仅由容器离开运行状态就断言业务已完整交接。保留每个状态各自的时间，下一次才能确认改变宽限有没有解决实际缺口。

要让停止实验适用于不同机器，也可以先保留镜像解析结果。若两轮用了同一个标签却指向不同制品，处理器代码版本可能已经变化。镜像只构建一次的安排正是为了把这项差异排除在外；留下实际镜像标识后，后续能确认哪一次只是调整命令参数。

前台直接按 Ctrl+C，也会使用镜像的首信号吗？

Dockerfile 手册明确将键盘中断与 daemon 停止区分。前台键盘的 Ctrl+C 产生 SIGINT，不因镜像指定 USR1 而改成它。若测试通过已有终端或包装程序，仍应明确实际交互入口与信号行为。这是另一个验证条件，正文只计划演练停止命令。可以在独立的前台程序安装可见的 SIGINT 处理器来观察，两份记录分别保留。该变体未执行。
