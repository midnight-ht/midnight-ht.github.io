SQLite 开着 WAL 时，只复制数据库文件会漏掉哪条记录？

用实际隔离试验对照 SQLite 主文件副本和连接备份，按已提交的记录标识验收。

正文

核心要点

  • SQLite 已提交的记录可能仍在 WAL。
  • 连接备份需要对目标副本独立读取。
  • 打开成功不能替代记录验收。

SQLite 使用 WAL 时，已经提交的行可能还在 WAL 文件里。只复制主数据库文件，可能得到一份可以打开却缺少这条已提交记录的副本。对仍在使用的库，用 SQLite 的连接备份接口生成可独立验收的副本。

设想应用保存了第二条库存记录，写入连接读得回来，备份任务却只把数据库同名文件复制到另一个目录。检查者打开副本，表仍然存在，只有第一条记录。此时先查两份副本分别从哪个入口取得内容，再按业务主键核对，而不是从能否打开文件推断已经保留所有提交。一个结构正常的旧视图也能通过打开检查。

提交记录与主文件何时不同

SQLite 说明，WAL 是数据库持久状态的一部分。数据库仍在使用时，把主文件与对应的 WAL 分开，可能丢失已经提交的事务。应用通过连接读取时，数据库会依据自己的状态协调读取，不必从单一主文件推断当前结果。这里关注一份没有其它写入者的隔离库，有意把第二条记录留在 WAL 中。没有把这个对照扩展成任意活库文件复制都只会少一行。SQLite WAL 文件说明。

Python 的 sqlite3.Connection.backup 接受另一条连接作为目标，并调用 SQLite 的备份能力。使用时应当给目标分配独立路径，完成后关闭目标连接，再用新的连接检查内容。源库里刚好能查到数据，只能当成源侧证据。通过目标副本再次查询，才能核对目标确实保存了预期状态。没有其他写入者的样本也不会决定生产系统在并发期间采用哪个业务截止点。Python sqlite3 backup。

让两个副本从不同入口取得数据

下面的标准库程序已在 Python 3.11.15、SQLite 3.53.1 的临时目录运行。它关闭本连接的自动 checkpoint，先把包含记录一的基线送入主文件，再提交记录二。整个复制阶段没有其他应用连接修改数据库。复制主文件的步骤只是隔离负对照，不是生产备份命令。

from contextlib import closing
from pathlib import Path
from shutil import copyfile
from sqlite3 import connect, sqlite_version
from tempfile import TemporaryDirectory

def query(connection, sql):
    return list(connection.execute(sql))

def rows(connection):
    return query(connection, "SELECT id FROM sample ORDER BY id")

with TemporaryDirectory() as directory:
    root = Path(directory)
    live = root / "live"
    main_only = root / "main-only"
    backup = root / "backup"
    with closing(connect(live)) as writer:
        assert query(writer, "PRAGMA journal_mode=WAL") == [("wal",)]
        writer.executescript("""
            PRAGMA wal_autocheckpoint=0;
            CREATE TABLE sample (id INTEGER PRIMARY KEY);
            INSERT INTO sample VALUES (1);
        """)
        assert query(writer, "PRAGMA wal_checkpoint(TRUNCATE)") == [(0, 0, 0)]
        query(writer, "INSERT INTO sample VALUES (2)")
        writer.commit()
        assert rows(writer) == [(1,), (2,)]
        copyfile(live, main_only)
        with closing(connect(backup)) as target:
            writer.backup(target)

        with closing(connect(main_only)) as isolated:
            assert rows(isolated) == [(1,)]
        with closing(connect(backup)) as restored:
            assert rows(restored) == [(1,), (2,)]
            assert query(restored, "PRAGMA integrity_check") == [("ok",)]
        print(sqlite_version, "live=1,2 main-only=1 backup=1,2")

写入连接实际读到一和二。只复制主文件的副本独立打开后，只读到一。通过连接备份取得的文件也独立打开，读到一和二，完整性检查返回 ok。程序保留写入连接到两份检查结束以后，避免最后一条连接关闭引起的处理提前改变负对照。它并没有尝试在修改并行发生时复制文件。归档的输出和断言只描述这一次受控环境，不能作为线上数据的完整性证明。

这次实验的三个分组要保持独立。如果读主文件副本时把原库同名 WAL 也放到同一位置，就无法再证明差异来自是否读取 WAL。夹具用不同文件名和同一受控目录隔开目标。另一个常见误验是直接把同样的查询发回源连接，然后把查询结果贴到备份回执。检查记录应写下连接实际打开的路径、读取的表和目标行标识，使结果归属可追溯。

用业务可恢复性验收目标

真实备份验收可以挑选已提交的少量稳定标识，检查目标中的关联行和表结构。完整性检查返回正常，只能支持数据库结构相关的那项检查。如果产品需要备份到某个准确的业务标记，还要明确标记何时提交，备份范围如何覆盖它，并在恢复之后检查。对独立数据库进程、附件和外部身份服务，也应保存它们自己的恢复条件。这个本地样本不涉及这些依赖。

也可以准备一次错误的验收决策作对照。让主文件副本通过打开和基线查询，但把记录二列为备份必须包含的验收项。只有在按主键验证时，这份副本才会失败。这样能确认测试没有把最早那条记录当成全部证据。站内的 SQLite checkpoint 与读事务 讨论长读如何影响归并时点，这里故意控制 checkpoint，只检查活库中一项新提交怎样进入可读副本。

恢复演练还需要验证数据之间的关系。可以给第二条记录附一条库存明细，记录号二、明细号二十一，先写出真正可用于查询的两行预期。打开只含基线的错误副本时，结构检查仍可能正常，这条库存及其明细却都不存在。若备份只找到了记录二，明细丢失，也不能判整体成功。把关联关系的核对放在目标副本，避免漏掉仅迁入部分表或在错误连接上核对的问题。这组业务行是测试设计，主样本没有明细表。

为了不把测试变成一条只会成功的路径，可独立挑选一个明确不该存在的记录，例如编号三。验证恢复程序没有把另一份样本中的记录合并进来。对实际项目，先在源状态固定验收范围，再记录目标版本、开始与完成时间，并标明预期中哪些内容可能出现在并发写入之后。这里没有演示并发备份的一致性机制，也没有声称运行时自动选择业务所需的截止点。

默认会把命名附加库也备份吗？

Python 的 backup 默认选择源库名 main。若应用另有通过 ATTACH 命名的数据库，应按需要为每个数据库准备明确目标，并用 name 选择源。可给主库和附库分别放一个不同的验收标识，确认只有显式请求的附库标识出现在它自己的副本中。逐库完成并不自动证明这些副本覆盖同一个跨库业务时点。这项附库验证未运行，样本只观察一个主库。
