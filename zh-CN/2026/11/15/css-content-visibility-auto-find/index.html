用了 content-visibility:auto，为什么离屏内容还能搜到？

用两个离屏章节区分 auto 和 hidden，分别检查页面内查找与 Tab 导航能否触达里面的内容。

正文

核心要点

  • auto 仍保留离屏内容的正常查找能力
  • hidden 跳过的内容不能用同样方式触达
  • 查找和键盘导航使用独立的验收判据

按 CSS 规范，把文章的离屏章节设成 content-visibility: auto 后，在浏览器里搜索该章节的编号，页面仍然能找到它。换成 content-visibility: hidden，搜索结果却不同。离开视口只说明用户此刻没看到章节，浏览器的页面内查找和按键导航还有自己的可达性规则。

两种值允许浏览器略过什么

规范允许浏览器在 auto 元素的内容与用户暂时无关时跳过对子树的部分渲染工作。就页面内查找和顺序焦点导航而言，元素的内容仍应像平常一样参与。文档位置很远并不足以让一段正文从查找范围里消失。

hidden 也会让后代内容被跳过，但对用户操作的规定不同。被跳过的内容不能由页面内查找或顺序导航触达。这里的区别是内容，也就是示例章节里的标题、普通文本和链接。它没有承诺设置了该属性的章节盒子本身完全不占位，也不应把它与 HTML 元素的 hidden 属性混在一起。

理解这条边界后，可以更准确地判断哪种变化能接受。对于分页很长、仍需让读者找得到全部内容的说明文档，搜索命中离屏章节可能正是产品想保留的功能。假如用户搜索时跳到了那里，跳转本身不证明页面在打开时就渲染了所有章节。

反过来，如果作者的目的只是让未选中的内容暂时不能由键盘和查找触达，auto 不会提供这种限制。此时先写下用户应该还能访问哪些内容，然后再检查隐藏方案的规则。是否减少了某次渲染工作，要单独取性能证据，不能凭搜索成功或失败来猜。

两个离屏章节，分别验收查找和 Tab

存成一个 HTML 文件就可以准备这个对照。页面有两个普通章节，分别放在高于一个屏幕的间隔之后。每段放一个唯一的普通文本和一条链接。不要在页面其他地方显示相同文本，免得搜索命中的是复制出来的说明。

<!doctype html>
<meta charset="utf-8">
<title>Offscreen chapters</title>
<style>
  .gap { height: 170vh; }
  section { min-height: 12rem; }
  .auto { content-visibility: auto; }
  .hidden { content-visibility: hidden; }
</style>
<body>
  <a href="#start">Start of test</a>
  <p id="start">Both chapters begin offscreen.</p>
  <div class="gap"></div>
  <section class="auto">
    <h2>Automatic chapter</h2>
    <p>cobalt-nectarine-042</p>
    <a href="#start">Return from automatic chapter</a>
  </section>
  <div class="gap"></div>
  <section class="hidden">
    <h2>Hidden chapter</h2>
    <p>violet-orchard-081</p>
    <a href="#start">Return from hidden chapter</a>
  </section>
</body>

第一次从文档顶部开始，打开浏览器的页面内查找，输入 cobalt-nectarine-042。按规范预期，这条文本仍可匹配。重新载入并回到顶部，再搜 violet-orchard-081，预期搜不到隐藏章节里这一项。不要把上一次查找留下的滚动位置当成第二次的初始条件。

键盘测试单独做。关闭查找界面，把焦点锚定在页面开头的链接，再按 Tab 进入文档的下一项。自动章节的回到开头链接仍可进入顺序；隐藏章节里的链接不应进入。不同浏览器可能让顺序进入工具栏、地址栏或其他界面，只记录焦点位于文档内时经过了哪些元素。

这些是根据 CSS Containment Level 2 对两个值的规定写出的预期。文章没有在浏览器实跑，也没有测量渲染耗时或辅助技术输出。实际测试时把浏览器版本、平台和是否启用了完整键盘导航留在记录里，方便后来的人比较的是同一组操作。

用于回归时，给两次观察设不同的通过条件。查找关注特定字符串是否出现在浏览器的匹配结果，键盘关注实际获得焦点的链接。间隔只是为了让内容一开始离屏。浏览器何时决定跳过具体子树，还可以受它对视口附近内容的处理影响，不能把间隔的高度当成一条跨实现的渲染边界。

另外，测试前不要自行用定位链接跳到待观察章节。如果先点了章节目录或从之前的搜索结果回来，后代可能已经在视口附近，初始输入就不同了。在本地保持一个无状态的样本，再去检查真实页面的目录、滚动容器和其他 CSS 对结果有没有影响。

排查没有按预期命中的样本时，先确认测试文件的样式确实生效。在浏览器开发工具里选中章节，分别读取计算后的属性值。如果两处都回到了默认值，先检查属性是否能解析、样式是否被覆盖，再判断查找结果。若属性值正确却同时找到两串字符，看浏览器定位到哪里，有可能搜到了网页后来插入的测试说明，而不是预设章节。

搜索也可以加一条对照，让两个值分别运行在同一个位置的章节上。复制测试文件，改动另一份的章节类名，把文本和初始滚动位置保持一致，再观察匹配与焦点。这样就能把浏览器对两个位置的处理从比较中移开。此时仍只能核对交互能力，需要确定渲染是否发生或节省了多少，应另开性能记录。

脚本聚焦离屏章节的链接，会改变 auto 的判断吗？

会。新条件是脚本让自动章节中原本可以聚焦的链接获得焦点。按照规范，元素或其内容有焦点是内容与用户相关的条件之一。如果那条链接成功得到焦点，就不应因章节仍离屏而继续跳过这部分内容。这并不赋予任意节点可聚焦性，示例谈的是已有 href 的链接。

要单独观察焦点，可以在调用后读取 document.activeElement，确认结果指向该链接。滚动和辅助技术播报是其他观察项。即使另行阻止默认滚动，只要焦点已经移过去，相关性仍成立。不要用页面是否向下移动来替代焦点断言。

如果你需要的是内容先藏起来、在页面查找命中时再显示，可以读HTML hidden until-found 的揭示流程。
