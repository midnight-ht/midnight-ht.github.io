输入已经修正，怎样让旧错误退出 aria-errormessage？

用一个验证码输入框验收无效到恢复的过程，分别检查字段状态、消息引用与目标可见性。

正文

核心要点

  • 无效时让错误引用指向可见消息
  • 恢复后清除已经不适用的标记
  • 验证状态转换并保留用户修正后的值

验证码输入框上次提交时显示了「输入六位数字」。用户把 123 改成 123456 后再次检查，界面上的错误消失了。此时还应检查一处：控件是不是仍然被标成无效，或者还把上一条错误当作当前的错误消息。只把红色文字从界面上收起来，无法确保表单的其他状态已经清理。

让消息跟着校验状态走

这个表单有三个可以分别验收的时间点。初次打开时，产品还没检查过输入。先给输入框一个明确的标签，让用户知道这里要填什么。不要预先把字段标成无效。错误段落可以提前存在于 DOM 里，但开始时隐藏，控件也不引用它。

用户填了三位数并点击检查，应用认定这个值不符合六位数字的规则。将错误段落显示出来，把输入标为无效，再用 aria-errormessage 指向段落的 ID。段落在这里有两份工作。视觉上能读到具体怎么修，控件的属性也明确指出该错误属于哪一个输入。

用户补全六位并再次检查后，错误不再适用。例子会移除引用、隐藏段落并清除无效标记。输入栏里的值不会被重置。用户已经完成了修正，重新写入空值会把原来的错误消掉，却也扔掉用户这次填对的内容。下一次检查失败时，还可以让同一个提示段落重新参与这组状态变化。

WAI-ARIA 1.2 把错误消息的引用与 aria-invalid 联系在一起。当应用认为错误消息已经不相关，可以隐藏目标或移除引用。若还留着引用且显式标为非无效，用户代理不得把那个引用作为错误消息关系暴露。这里选择同时关闭三处状态，便于检查每一步，不让旧的引用成为下次维护的隐患。

三组输入怎样检查

下面的页面是本地夹具，没有账号服务，也不会发送验证码。它只检查字符串是不是六个 ASCII 数字。点击按钮才进行检查，因此用户正输入时不会每敲一次键就刷新错误提示。示例中的英文标签和错误内容也可换成产品的界面文案。

<!doctype html>
<meta charset="utf-8">
<title>Code validation</title>
<label for="code">Verification code</label>
<input id="code" inputmode="numeric">
<button id="check" type="button">Check code</button>
<p id="code-error" hidden>Enter six digits.</p>
<script>
const input = document.getElementById('code');
const button = document.getElementById('check');
const notice = document.getElementById('code-error');
button.onclick = function validate() {
  if (/^[0-9]{6}$/.test(input.value)) {
    input.removeAttribute('aria-errormessage');
    notice.hidden = true;
    input.removeAttribute('aria-invalid');
    return;
  }
  notice.hidden = false;
  input.setAttribute('aria-invalid', 'true');
  input.setAttribute('aria-errormessage', notice.id);
};
</script>

第一次打开，查看输入元素没有上述两个 ARIA 属性，错误段落带有 hidden。输入 123 并按检查，输入应有无效标记，错误引用指向可见段落，段落应该明确告诉读者要六位数字。然后把值改为 123456 并再按一次检查。此时应看不到错误文本，两个属性已从输入移除，而输入里的数字仍保持为 123456。

在自动化断言中，分别检查属性、目标元素和输入值。只检查错误文字不可见，会错过忘记清理无效标记的分支。只检查属性被移除，也会错过仍占页面空间的旧文案。把失败到恢复放在同一个页面周期里，更容易抓住属性在第一个错误之后残留的问题。

可以把两次检查得到的 DOM 状态一起存入测试输出。失败时要求引用的值等于错误段落实际的 ID，而非仅仅存在某个字符串。恢复时要求两个属性都不存在，同时确认段落确实进入隐藏状态。一旦以后有人把段落 ID 改名，或只把无效标记重置成原样却忘了清理引用，失败输出会直接指出是哪一层没有跟上。

再加一轮由有效回到无效的检查。把最后一个数字删掉并提交，确认错误段落能重新显示，控件的引用仍能找到同一个 ID。这个步骤专门防止修复代码移除了复用段落，却让下一次错误只剩一个找不到目标的属性。若页面上有多个验证码输入，还应确认每个实例使用可区分的 ID。

上面这些是根据页面代码与规范列出的预期，文章没有实际运行浏览器或辅助技术。不同组合在用户操作时怎样播报，要在产品支持的环境中另做验证。显示一段文本和声明它是控件的错误消息，都不等同于实测了用户操作时会听到的内容。

项目里可能还有一层校验结果来自服务器。若回答在用户继续编辑后才到达，恢复规则也要基于当前正在检查的值。假设旧值 123 的失败回来时，新值 123456 已经被检查通过，就不能让旧响应重新打开错误。这个示例是同步的，本身没有解决请求顺序问题。

格式说明和错误提示可以同时存在吗？

可以。若你想让用户在检查之前就知道输入格式，可以把「使用短信里的六位数字」放在一个常驻可见的说明元素中，让输入通过 aria-describedby 关联它。校验失败时再添加另一段只在无效状态下适用的消息，例如「当前输入只有三位，请补齐」。这两段文字需要各自的目标元素。

恢复有效时，保留说明的引用，清除错误的引用。这样用户把焦点移回输入时，仍能找到用途与格式提示，又不会把上一笔失败当成当前结果。若两个属性指着同一段话，应用会很难独立管理格式一直可见和错误已经过期这两种状态。为这个新增条件写测试时，单独检查说明在有效与无效两态都仍有目标。

如果一页里有多个失败字段，需要从页首的错误清单跳回正确的输入，可接着看错误摘要如何把用户带回可修改处。
