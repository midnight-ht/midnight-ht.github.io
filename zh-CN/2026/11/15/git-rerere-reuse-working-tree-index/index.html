Git 找回了上次的冲突解法，为什么还要 git add？

用同一冲突重复合并，比较 rerere 写回文件与更新索引的两条路径。

正文

核心要点

  • 解决后的文件与索引需要各读一次。
  • 禁用自动索引更新可先审核再暂存。
  • 暂存完成后仍需验证合并结果。

文件已经恢复成上次的解法，索引却还留着未合并记录。Git 的 rerere 能复用保存过的冲突解法。是否同时更新索引，取决于这次合并的自动更新设置。

团队在合并两个长期维护的分支时遇到一处熟悉的冲突。文件里原来的冲突标记消失了，编辑器也显示出前一次人工整理过的那行内容，但 Git 仍把文件列为未合并。此时没有必要马上再编辑一次。先读取磁盘上的结果，再查看索引中的冲突条目。两处可能同时给出正确的答案，因为其中一处显示候选解法，另一处仍在等维护者确认采用什么结果。

工作树和索引各有一份观察

Git rerere 手册说明，当以前记录的解法可应用到当前冲突时，Git 可以把合成后的结果写回工作树。显式使用 --no-rerere-autoupdate 时，这一步留给维护者先检查，再用 git add 更新索引。如果允许自动更新，索引也会采用计算出的解法。两条路径的工作树可以相同，暂存状态却不同。 Git merge 手册

排障时，可以把文件内容和索引输出并排保存。直接读文件只能说明某次读取时看到了什么。运行 git ls-files -u 能看到仍未合并的索引项；把审查通过的文件加入索引后，再查看暂存内容。不要只搜索文本里有没有冲突标记。对于一个已经合成的候选文件，它们不出现完全合理，索引也可能还保留需要处理的状态。

把同一个冲突再做一遍

下面的脚本已在 Apple Git 2.50.1 的一次性仓库执行。它创建同一个基础文件的两个分支，双方把同一行改成不同值。第一次合并手工写入 combined，暂存并提交，Git 记录这次解决方式。后面的重置和合并只作用于脚本自己创建的仓库。不要把这一段重置命令拿到工作仓库套用。

set -eu
work=$(mktemp -d)
trap 'rm -r "$work"' EXIT
cd "$work"
git init -q -b ours
git config user.email fixture@example.invalid
git config user.name Fixture
git config rerere.enabled true
git config commit.gpgsign false
write() { printf '%s\n' "$1" > settings; }
save() { git add settings && git commit -qm "$1"; }
write base
save base
git branch theirs
write ours
save ours
git switch -q theirs
write theirs
save theirs
git switch -q ours
if git merge --no-rerere-autoupdate theirs; then exit 1; fi
write combined
git add settings
git commit -qm learned
git reset --hard -q HEAD^
if git merge --no-rerere-autoupdate theirs; then exit 1; fi
test "$(cat settings)" = combined
git ls-files -u
test "$(git ls-files -u | wc -l | tr -d ' ')" = 3
git add settings
test -z "$(git ls-files -u)"
printf 'manual stage: %s\n' "$(git show :settings)"
git merge --abort
if git merge --rerere-autoupdate theirs; then exit 1; fi
test -z "$(git ls-files -u)"
test "$(git show :settings)" = combined
printf 'automatic stage: %s\n' "$(git show :settings)"

第二次合并带着禁用自动更新的选项。脚本立即确认文件中已是 combined，然后观察到三个未合并阶段。执行 add 后，这些条目消失，索引的内容才变成 combined。第三次重新合并，允许自动更新；未合并条目在检查时已经为空，索引里的文件同样为 combined。脚本整体退出零，证明这些断言都满足。第三次 merge 本身仍返回非零，操作还需要根据合并结果做后续处理。不能把子命令报错和实验总结果混成一句“执行成功”。

样本在相同父提交上重演，以便保持冲突形状一致。两次恢复都应读到相同文字，改变的只有索引是否自动接受它。如果只保留 cat settings 的日志，两轮完全无法区分。反过来，只看索引已没有冲突，也无法知道最终暂存的是前一次保存的解法，还是其他人员刚写入的内容。因此，验收既要保存状态，也要查看暂存值。有多个冲突文件时，对每个实际采用的结果分别核对，别让一个路径的状态替其他路径签字。

哪些解法值得再次确认

重用最适合稳定且反复出现的改动，例如两条维护分支长期以同样的方式组织同一段配置。但当前版本的配置语义可能改变，即使旧文本仍可应用，也不能假设旧选择依然适当。请把复用结果与两个分支的意图、周边新内容和目标测试一起检查。一次自动更新后还可以查看暂存差异，再决定是否提交。对于需要人先核对的流程，可以明确禁用自动更新，避免把工作树里的候选结果误读成已确认的结果。

在交付记录里，先写清哪一次合并发生了复用，再写保存了什么证据。比如某次自动合并的暂存内容已通过审查，但它运行之后没有按期望启用某个设置，这时该查的是业务行为，不能只重复查看未合并条目。另一类问题恰好相反：业务样例看起来正常，合并还没有处理完所有索引项。维护者仍要完成合并流程。两条证据互相补充。有关审查已完成提交差异的任务，可看如何检查两版补丁。

对需要先检查再确认的团队，记录可以分为处理前与处理后。处理前保存仍处在高阶段的路径和生成的候选文件，处理后核对暂存区和预期解法。中途如果有人继续编辑，应保留实际进入索引的那份版本，不能只留下旧截图。若审查发现其他路径仍有冲突，也应等各自处理完成再确认整个合并。这个步骤没有改变主例的两种自动更新路径，却能避免把一处已暂存解释成所有合并工作已经完成。

还要保留实验条件。若换了一份仓库而没有同一条历史记录，第二次合并可能重新出现待处理的冲突。先确认 rerere 已启用并查看命令输出，避免把装载不到记录误判为索引不更新。否则两次观察虽然都写着未合并，发生的动作却不同。一份可能已经写回候选文本，另一份仍等人手工解决，下一步自然也不同。

发现旧解法不再适用，可以只忘掉当前冲突路径吗？

可以用 git rerere forget 加上匹配当前冲突的路径，重置这个冲突关联的已记录解法。这里多出来的条件是当前解法记录本身错误，前面的例子一直使用正确的记录。更改前先保存审查所需的结果，再解决当前冲突，检查本轮采用的内容。这个忘记和重新录入的变体没有运行；不要把它当成已经检查了所有历史的冲突记录。
