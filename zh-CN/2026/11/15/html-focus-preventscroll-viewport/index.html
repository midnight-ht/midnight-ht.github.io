调用 focus 时，怎样保留当前滚动位置？

用离屏按钮对比默认 focus 和 preventScroll，分别确认活动元素与容器偏移。

正文

核心要点

  • 默认聚焦包含滚动步骤
  • preventScroll 跳过当次聚焦的滚动步骤
  • 分别断言实际焦点和面板偏移

在一个可滚动面板里，脚本要把焦点交给暂时在面板下方的按钮。调用 focus 后，按钮得到焦点，面板却跳离了用户原先停留的位置。在普通可聚焦按钮上，可以给这次调用传入 preventScroll，保留面板位置。要知道操作是否成功，分别读焦点和滚动偏移。

一次聚焦调用里有两个结果

HTML 的 focus 方法先运行聚焦步骤。在默认情况下，后续还会运行让目标进入视野的滚动步骤。FocusOptions 的 preventScroll 默认为 false。传 true 时，这个方法仍然尝试把焦点交给目标，跳过自己的滚动步骤。

这里假设目标是已连接、未禁用且本来可以聚焦的按钮。这个选项不会把禁用按钮变成焦点目标。如果执行完选项调用后位置没变，仍需确认实际焦点在哪。否则，按钮成功获焦和按钮根本无法获焦都会留下相同的滚动读数。

反过来也成立。测试发现面板向下跳，不能只凭位置变化就认定目标得到了焦点。页面上的另一个监听器可能滚动面板，而焦点仍然留在操作按钮上。焦点读数关心的是哪个元素接收后续键盘操作，偏移读数关心的是视野有没有被移动。用两个观测来判断两件事。

从相同的位置聚焦同一个按钮

可将这个例子存为一个独立 HTML 文件。面板高一百像素，目标在一段更高的空隙后面。两个外部按钮都用脚本先取得焦点，确保下一次操作从目标以外的元素开始；随后把面板滚回顶部。现在目标在同一个位置，只有最终的聚焦参数不同。

<!doctype html>
<meta charset="utf-8">
<title>Focus and scroll check</title>
<style>
  #pane { height: 100px; overflow: auto; border: 1px solid; }
  .gap { height: 220px; }
</style>
<button id="normal">Focus normally</button>
<button id="steady">Focus without scrolling</button>
<div id="pane">
  <div class="gap"></div>
  <button id="target">Target</button>
  <div class="gap"></div>
</div>
<pre id="output"></pre>
<script>
const byId = document.getElementById.bind(document);
const pane = byId('pane');
const target = byId('target');
const output = byId('output');

function check(trigger, options) {
  trigger.focus({preventScroll: true});
  pane.scrollTop = 0;
  const before = pane.scrollTop;
  if (options) target.focus(options);
  else target.focus();
  const focused = document.activeElement === target;
  const after = pane.scrollTop;
  const result = focused + ' | ' + before + ' → ' + after;
  output.textContent = trigger.id + ' | ' + result;
}

const normal = byId('normal');
const steady = byId('steady');
normal.onclick = () => check(normal);
steady.onclick = () => check(steady, {preventScroll: true});
</script>

从页面顶部点击 Focus normally 后，按规范预期，记录的焦点值是 true，初始偏移为零，后续偏移大于零。再点击 Focus without scrolling，仍预期焦点值为 true，但前后偏移都保持零。夹具不依赖默认调用把下方按钮滚到精确的像素，因为要验证的是面板是否发生偏移而非它停在哪一条线上。

这两行是根据 HTML 算法和样本布局列出的预期，文章没有实际运行浏览器，也没有验证辅助技术。只观察面板本身的纵向偏移。若实际界面有另一层外部容器，页面滚动和面板滚动也要分别记下来，避免内层没动但外层跳了的情况被同一个报告掩盖。

输出有两个通过条件。焦点检查从文档读取活动元素，与原先确定的目标比较。滚动检查比较本次操作前后的面板偏移。只把结果写成「按钮工作了」会丢掉故障证据。记录初始与最终位置，可以进一步看出偏移来自初始状态还是这次调用。

选在什么动作上保留视野

有些界面想让用户继续阅读原来的位置，例如用户用键盘恢复一个刚结束的交互，页面同时保留他已经滚到的区域。采用这一选项前，确认随后获得焦点的控件在这个工作流里仍然清晰可辨。如果焦点实际上落到了看不见的区域，下一次键盘操作可能很难预测。接口提供的是控制滚动步骤的能力，交互设计仍需决定把焦点放在哪里。

回到真实组件时，先找谁触发了 focus。若应用还有其他焦点回调、自动滚动逻辑或布局变化，把那些操作暂时从样本中移开，再观察这一个调用。否则，即使聚焦方法确实跳过了自己的滚动步骤，紧接着运行的代码也可能改变结果。这个夹具没有给目标绑定这样的应用回调。

做回归时还要核实两个操作每次都从零开始，让目标初始时落在面板下方。如果按钮已经可见，默认调用也可能给出零变化。采用这样的初始状态无法区分两个分支。让目标先失焦以及重置面板，也能避免上一次运行留下的状态使第二次读数看起来通过。

如果一次出现和预期不符的读数，可在同一页面先用键盘激活外部按钮，再改用鼠标重做。记录每次进入脚本之前触发的操作，以及脚本自己重置的焦点和偏移。这个夹具在两种触发方式下都会主动设置相同初态，因此差异若在调用之前已经出现，应先查外部控件的事件处理或浏览器键盘设置。单纯重复同一种点击不会暴露这个差别。

一个典型的修复验证会记录操作来源、被聚焦的元素和容器本身。比如在快捷键触发流程里，按钮开始时不在活动元素里，脚本执行后应该成为活动元素且面板仍处于原来的行。与测试直接点击那个目标相比，这能检验实际让焦点离开视野的脚本入口。

之后再调用 scrollIntoView，还会被这个选项挡住吗？

不会。给目标调用带 preventScroll 的 focus，先读面板偏移，发现它仍是零。下一步再调用目标的 scrollIntoView，这是新的滚动请求。之前那个选项只参与前一次 focus 的步骤，并不会替目标或面板记住一条禁止滚动的规则。

要查修复为何仍然跳动，可以给两次操作之间加一次偏移记录。焦点已经切换且偏移保持，随后调用显示目标时偏移发生变化，就能把两个行为分别归因。若是项目自己的焦点监听器发起第二次滚动，应在该监听器的触发条件里决定何时显示目标。

如果焦点切换出现在对话框关闭与重新打开之间，可另看对话框重开时如何处理上次的返回值。
