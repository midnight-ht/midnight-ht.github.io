JSON 已经合法，为什么提交仍收到 HTTP 422？

用预约区间对照 415、400 和 422，判断应修请求格式、JSON 语法，还是两项时间之间的规则。

正文

核心要点

  • 422 允许内容已解析但指令无法处理
  • 用固定起点和不同结束时间做回归对照
  • 结合接口返回原因来呈现可修的错误

会议室预约传的是一份可以解析的 JSON，开始时间十点，结束时间九点。客户端收到 HTTP 422 后，以为请求体还有少写的引号，把原来的两项重新序列化再提交，还是失败。服务器已读懂这份内容，需要改的是预约指令本身。在这个例子里，把结束时间调整到开始时间之后，才进入创建预约的路径。

同一个提交如何分出三种失败

先把请求的格式和读出来的内容分开。端点需要能识别发送来的媒体类型，按对应语法解析内容，然后才能判断用户希望做的事是否符合规则。表单提示也应当找到失败发生的这一步，才知道用户能够修改什么。

本例只允许 application/json。即使纯文本请求的字节看起来和 JSON 完全相同，示例端点依然在第一步以 415 拒绝。这个结果是媒体类型相关的，先检查客户端提交方式，单纯增加一个结束时间不能解决问题。

类型被接受以后，漏下半截大括号的 JSON 在解析阶段就失败。示例把这一路返回 400。客户端可以检查 JSON 是怎么构造出来的。此时应用还没有读出可用于比较的开始和结束时间，所以报「结束时间早于开始时间」也无从成立。

最后一种请求既使用了端点支持的类型，又能读出两个字段。结束时间九点小于开始时间十点，于是预约规则不接受它。RFC 9110 的 422 适用于服务器理解内容类型、内容语法正确，却无法处理其中指令的情形。这个请求适合返回此状态；这份示例没有把所有业务错误都归入 422。

固定开始时间，只改一个字段

下列脚本是独立的本地预约规则夹具。时间用整数小时表示，两个字段都须为整数，结束必须大于开始。四条案例依次是类型不受支持、JSON 截断、时间倒置、时间修正。它不启动服务器，也不向任何地址发送 HTTP 请求。

import assert from 'node:assert/strict';

function createBooking(type, body) {
  if (type !== 'application/json') return {status: 415};
  let value;
  try {
    value = JSON.parse(body);
  } catch {
    return {status: 400};
  }
  if (!value || !Number.isInteger(value.start) ||
      !Number.isInteger(value.end)) {
    return {status: 422, issue: 'invalid-hour-fields'};
  }
  if (value.start >= value.end) {
    return {status: 422, issue: 'end-must-follow-start'};
  }
  return {status: 201};
}

const cases = [
  ['text/plain', '{"start":10,"end":9}', 415],
  ['application/json', '{"start":10,', 400],
  ['application/json', '{"start":10,"end":9}', 422, 'end-must-follow-start'],
  ['application/json', '{"start":10,"end":11}', 201],
];

const {equal} = assert;
for (const [type, body, expected, issue] of cases) {
  const response = createBooking(type, body);
  equal(response.status, expected);
  equal(response.issue, issue);
}
console.log('Expected status branches passed: 415, 400, 422, 201.');

实际运行的四个状态断言按顺序通过：415、400、422、201。第三和第四条只改变结束时间，因而能把最后一次失败定位在预约规则。第三条如果重新提交同一份数据，函数依然会判为不符合条件。此处的 201 是夹具为规则通过设计的结果，没有真的写入预约。

对真实接口，先看错误信息中有没有能稳定识别的原因。比如接口定义了时间区间顺序的错误标识，就可以让表单在预约时间的区域提示「结束时间必须在开始时间之后」。同时留下用户的两项原始输入，方便他修正其中一项，避免让他再填一次房间、日期和参会人。

若端点还可能失败在别的条件，状态码只够把问题定位到大类。系统不能从 422 本身推出是项目无法解析日期、房间容量不够，还是两个字段逻辑矛盾。客户端可以消费接口契约中的具体原因，但不要把夹具中的时间文案复制给任何 422。

示例函数还区分了字段形状与顺序。缺少一个时间字段，或字段值根本不是整数时，也会走指令处理失败的状态，但函数会返回另一种原因。比方说，结束时间是字符串「九」时，先要补齐端点要求的值类型；只有两个整数都存在，才有条件比较谁先谁后。前端收到顺序错误代号时，也不应覆盖同一字段上独立的格式提示。

服务端验收也可以复用这一对测试。给错误请求和正确请求相同的媒体类型、相同的解析方式及相同开始时间，只把结束时间从九改成十一。如果修改两项请求配置再成功，就很难知道是哪一项起了作用。坏 JSON 与类型错误的单独用例，则能防止实现误把第一阶段失败包装成时间规则。

做调试记录时，可以记下解析是否完成、命中的规则代号以及最后写出的状态。预约时间、用户身份等值未必要全部落库。对当前错误而言，知道它已经过了媒体类型和 JSON 解析两关，再看到一个稳定的区间规则名称，足够决定要从表单规则与接口契约查起。

如果规则在界面提交前也有检查，仍可保留服务器侧的断言。界面的目标是让用户尽早发现输入问题，服务器的目标是按当前契约决定是否接受这份指令。表单改过提示或校验时，独立请求的失败案例继续守住接口对顺序的约束。

接口只给出错误原因，没有字段路径怎么办？

把这一类跨字段错误放在时间组旁边，或在页面的错误摘要里说明两个字段之间的要求。当前值十到九不能成立，但用户可以把开始改到八，也可以把结束改到十一。服务端没有给出路径时，客户端没有证据认定只能修改结束栏。把两个原值保留，让用户根据实际会议时间选择改哪一个。

如果只有状态码，连区间问题也无法推断。此时可以保留填写内容，显示该预约无法接受的反馈，并依据接口约定引导下一次检查。等服务端提供稳定错误原因后，再把特定规则映射到时间区间。不要从前一次提交的问题猜本次的字段。

如果请求甚至没走到指令校验，可以先读如何从 HTTP 415 排查请求的媒体类型。
