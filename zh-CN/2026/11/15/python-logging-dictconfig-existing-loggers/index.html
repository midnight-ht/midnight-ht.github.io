Python 改完日志配置，为什么旧 logger 不再出声？

用两组实际运行的 dictConfig 对照，区分旧实例的禁用状态与处理器收到的消息。

正文

核心要点

  • 非增量配置缺省可能禁用已有非根实例。
  • 检查实例状态和实际接收记录。
  • 保留实例不代替日志路由验收。

Python 用 dictConfig 重配日志时，如果采用非增量模式且没有声明保留策略，已经存在、又未被配置覆盖的非根 logger 可以被禁用。此后即使根处理器能记录同级别的消息，旧 logger 也可能一条都不发。排查应先检查目标实例的 disabled，再检查级别与处理器。

设想一个服务在启动时先导入付款对账模块，模块取得自己的 logger，然后主程序加载日志配置。后来写入同一处理器的另一个模块仍有消息，先导入的模块却变得安静。两个模块明明都在发 INFO。此时把根级别继续调低，只是在改消息能走到的后段。若旧实例已被禁用，应该验证的是配置加载前后它能不能发出记录。

怎样读这项缺省设置

标准库的 dictConfig 参考规定，disable_existing_loggers 在缺省时为 True。它沿用 fileConfig 的语义，作用对象是已有的非根 logger。文档为 fileConfig 说明了名称覆盖的条件，已显式在配置中点名的 logger 或处在已点名祖先之下的 logger 不能直接套用本例结论。下面只比较没有被点名、与其它配置 logger 没有祖先关系的命名实例。根 logger 在样本中明确配置了处理器，是接收记录的观察点。Python logging.config。

这处设置解决的是配置加载这一刻已有实例是否继续工作的政策。应用不能只按模块名推断它是早创建还是晚创建。若第三方代码在导入阶段调用 getLogger，它可能比主入口早；若是收到请求才取得实例，时点就不同。验收应保留创建位置、配置应用动作和实例的 enabled 状态，再记录实际处理器收到了哪些消息。

让处理器说出自己收到了什么

以下程序在单独的 Python 3.11.15 进程真实运行。它使用内存文本流接收记录，不会改动当前服务。每一轮先建立一个目标 logger，再加载配置，再创建不同名称的后期 logger。第一次留空该设置，第二次明确为 False。两条路径都把根级别维持为 INFO。

import io
import logging
import logging.config

def observe(keep):
    early = logging.getLogger(f"demo_early_{keep}")
    buffer = io.StringIO()
    config = {
        "version": 1,
        "handlers": {
            "probe": {"class": "logging.StreamHandler", "stream": buffer},
        },
        "root": {"handlers": ["probe"], "level": "INFO"},
    }
    if keep:
        config["disable_existing_loggers"] = False
    logging.config.dictConfig(config)
    late = logging.getLogger(f"demo_late_{keep}")
    early.info("early")
    late.info("late")
    return early.disabled, buffer.getvalue().splitlines()

for keep, expected in [
    (False, (True, ["late"])),
    (True, (False, ["early", "late"])),
]:
    actual = observe(keep)
    assert actual == expected, actual
    print(actual)

缺省组实际看到早期实例的 disabled 为真，处理器只收到 late。显式保留组则看到 disabled 为假，处理器依次收到 early 与 late。保存两类数据有不同用途。布尔属性帮助确定模块为什么沉默，实际行列表确认事件究竟进入了哪个接收器。若只断言某个日志文件能收到一条消息，后期事件便可能让测试通过，同时掩盖早期模块仍被禁用。

这里用不同名称保证每轮的早期、晚期实例不会互相混用。真实服务若多次加载配置，某个已经存在的 logger 可能此前就被修改过，因此需要额外保存配置之前的状态。在生产故障报告里同样不应从一次观察反推所有模块的导入顺序。可以复现一条明确的启动流程，让目标日志分别在配置前后发出，再核对标记、来源名称和接收结果。这个启动回归未运行。

保存真实的日志去向

保留已有实例可能适合由模块各自初始化的服务，尤其有插件或外部库先于主配置加载。但不禁用只保证这里没有因为这项默认政策停发。实例的有效级别、传播和处理器仍然需要具体核对。可以增加一个启动后测试，让目标模块发一条具有独立编号的记录，要求它只进入预期接收器一次。若传播到两个都启用的处理器就可能看到两条，单看这个模块重新出现也不能宣布路由正确。站内的 pytest 日志捕获路径 给出了另一个关于级别与传播的观察方法。

团队也可以选择在配置里明确列出需要的业务 logger，而不把所有已有实例都保留。这个方案需要清楚名称及继承范围，尤其一个父名称下面可能还有若干模块。如果产品只允许指定诊断流进入审计通道，应核对两个相似名字的测试事件分别去了哪里。当前内存测试只有一个接收器，未检查多处理器、线程并发或日志留存。不要把样本结果扩成真实审计记录已经交付的说法。

日志状态记录可以和业务任务结果分别保存。对账函数即使正常返回，也可能没有生成可追踪的记录；日志可见也不能证明对账成功。把两个断言分别放到真实输出边界，部署后看到静默时才能判断是业务失败、模块禁用，还是路由改变。这里的两个文本只是教学标记，未连接任何业务模块。

可以进一步准备一条负对照，让目标实例保持启用，但给它独立设置较高的有效级别。预期 INFO 不到达内存接收器，而 WARNING 到达。这会复现同样的静默表现，却给出不同的状态证据。把禁用组和门槛组分别重建，不在同一 logger 上连续修改再猜哪个设置生效。实测回执未覆盖这个附加对照。

incremental=True 时，disable_existing_loggers 还会改状态吗？

文档写明增量配置会忽略这个键。要单独验收，可先按普通配置建立一个已启用的 logger 与处理器，再用增量输入指定 disable_existing_loggers 为 True，同时修改可增量设置的级别。检查实例的启用状态没有被这个键改变，并按新级别测试一条可观察消息。不要用一个之前已经被禁用的实例推断增量配置恢复了它。这个变体没有运行，主测试只覆盖非增量模式。
