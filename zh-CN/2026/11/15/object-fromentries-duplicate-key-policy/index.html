Object.fromEntries 转换后，为什么只剩最后一个值？

同键条目按迭代顺序写入结果对象。用交换顺序与重复查验两组例子，决定导入应该覆盖还是报错。

正文

核心要点

  • 同一个键的最后一次写入保留在结果对象
  • 源条目仍保留重复行
  • 需要报错时在创建对象前检查键

偏好导入页面拿到三行数据，主题先是浅色，中间一行是时区，最后主题又写了深色。导入预览显示三行，保存后的设置只剩两个字段，主题成了深色。如果把两条主题记录的位置互换，结果就会变成浅色。检查你交给转换方法的那批条目，就能找到覆盖发生的次序。

三行记录怎样变成两个属性

输入里的每行是一对值。第一项是属性键，第二项是要写入的值。方法沿条目的迭代顺序把值写进一个新对象。第一次遇到 theme 时写入 light，接着写 timezone，最后又写 theme。由于同一个属性键在结果对象中只有一个槽位，最后一笔 theme 写入会覆盖第一笔。

这个过程没有从输入数组移走任何一行。转换前后读原来的数组，仍然看得到两条主题。丢失的是结果对象中区分第一笔和最后一笔所需的信息。单看对象里的深色值，无法知道早先是否还有浅色，也无法知道深色来自文件第几行。覆盖后的对象不能充当一份完整的导入记录。

这和查看最终对象里哪个属性排在前面是两回事。工程师在控制台展开对象，看到 theme 仍显示在 timezone 前面，可能以为浅色记录留下了某种优先级。想查覆盖来自哪一条，应回到输入迭代顺序，观察每次为同一个键写入了什么值。

把顺序和冲突规则分开验收

下面的脚本只处理字符串键。它先用原顺序做转换，再交换两条同键记录的位置。两个预期对象保留同一个时区，主题相反。最后加一个拒绝重复的转换函数。这个函数先检查全部键，确认无冲突才创建对象，适合本例中条目都已读入内存的输入。

import assert from 'node:assert/strict';

const rows = [['theme', 'light'], ['timezone', 'UTC'], ['theme', 'dark']];
const opposite = [rows[2], rows[1], rows[0]];
const collapse = Object.fromEntries;

function unique(entries) {
  const keys = new Set();
  for (const [key] of entries) {
    if (keys.has(key)) throw new Error('Duplicate key: ' + key);
    keys.add(key);
  }
  return collapse(entries);
}

const examples = [
  [collapse(rows), {theme: 'dark', timezone: 'UTC'}],
  [collapse(opposite), {theme: 'light', timezone: 'UTC'}],
  [rows.length, 3],
  [unique(rows.slice(0, 2)), {theme: 'light', timezone: 'UTC'}],
];

const {deepEqual, throws} = assert;
for (const [actual, expected] of examples) deepEqual(actual, expected);
throws(() => unique(rows), /Duplicate key: theme/);
console.log('Both orders and the duplicate guard passed.');

本地 Node 运行通过。原顺序保存深色，交换后保存浅色，源数组仍有三行。去掉最后一行以后，拒绝重复的函数允许前两项通过。如果保留第二个 theme，它会抛出标明冲突键的错误。这条失败路径值得单独写断言，免得代码在测试里只碰到干净输入。

脚本选用了普通字符串是为了让查重规则和写入的属性键一致。如果入口前还有规范化步骤，例如业务层先去掉键两端空白，查重也应该发生在那一步之后。假如先查原始字符串，带空白与不带空白的两行会被看成不同条目，等到规范化后写对象，仍然会汇成同一个属性。

如果「最后一条获胜」就是产品要求，就把迭代顺序写进导入契约。假设两份偏好分别来自全局默认和个人设置，团队可以明确默认条目在前，个人条目在后，此时交换顺序的测试能守住覆盖方向。若两份来源的合并顺序可能变化，要先确定优先级，再生成稳定的列表。

如果同一份上传文件只允许每个键出现一次，应用程序应该在转换前找出冲突。导入预览可保留行号，并同时列出两行主题，让用户知道应该回到哪里修。转成对象以后再检查对象有多少个键，只会得到两个字段，不能判断它是合法两行还是三行发生了覆盖。

也有项目需要留下全部取值供人工选择。此时界面可以继续展示原有条目，或者按键收集多行，再把用户确认的那一行写进最终对象。这种需求和直接覆盖用的输出结构不同。让行号跟条目一起活到决策完成，之后才能解释哪笔值被合并、忽略或保留。

做保存与预览之间的验收时，可以使用固定的三行而不是随机生成多个互不相同的键。这几行产生一个范围很小的反例，同时锁住两个不相干的行为：时区不受冲突牵连，而主题只受对应两条记录的顺序影响。只断言两个输出对象都恰好有两个属性，会掩盖主题可能被选反的问题。

若有大小写规则，也需要在产品说明中明确。把 Theme 当作不同字段，和先统一大小写再合并，都是可以实现的方案。它们会产生不同冲突，能否接受取决于导入字段的业务定义。最容易维护的是用同一个代表键去查重和写入，并在报错时返回用户输入的原拼写。

如果生产日志只有保存后的对象，可以在生成条目列表的位置补记冲突的原始行号以及处理规则。比如记下主题来自第一行和第三行，第三行因后写规则被采用。用户会知道该修哪行，运维也能核对导入顺序。若原文件里含有敏感值，留下冲突字段和行号就能做这次追踪，无须把每个值都明文写进日志。

条目里有 Symbol 键，转回数组会丢吗？

用 Object.entries 转回时会遗漏这一项。比如先创建 const key = Symbol('source')，再把 [[key, 'upload']] 交给转换方法。新对象用 result[key] 能读到 upload。把它交给 Object.entries 得到空数组，因为这个枚举入口收集的是自身可枚举的字符串键。若要检查该 Symbol 属性，可以直接用原来的键读取，或查询 Object.getOwnPropertySymbols(result)。

这和主例的覆盖是两个不同的丢失阶段。这里属性在对象里仍然存在，只是你选的导出方法看不到它。如果目标是把整个导入结构再导出，应先确定允许的键类型，再挑选能保留该契约的格式。

如果手上的输入还没解析成条目数组，而是包含重复成员的原始 JSON，可以接着看重复 JSON 成员在不同实现中的互操作问题。
