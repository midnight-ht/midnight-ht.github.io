pytest 只想排除一个测试，为什么另一个也没执行？

比较 pytest 当前节点集合的前缀排除、较长节点排除和全量结果。

正文

核心要点

  • 固定版本按节点标识的开头匹配排除项。
  • 退出成功仍需核对被执行的节点。
  • 导入错误要在文件收集边界处理。

pytest 的固定版本实现按 node ID 前缀匹配排除项，较长的名字也可能命中。传入看似完整的 --deselect 参数后，应该核对实际运行了哪些测试。

维护者想临时跳过一个已知用例，准备继续观察同一模块里的其他结果。他复制了简短测试的完整节点名称，命令很快变绿，却发现新增的边界用例也没跑。参数里的文本看起来和第一个节点完全相同，但实现查看的是节点是否以这段文本开头。两个名字只差后缀时，问题就出在选择范围上，不能从绿色退出反推本轮覆盖。

节点自己的名字有时也是别人的前缀

pytest 的收集文档允许用这个选项在收集期间去掉个别测试，还允许传入多个排除项。关于比较的精确方式，可以查看 pytest 9.0.2 的实现：它使用 startswith 判断是否应把某个 node ID 放入排除集合。名字里的文件路径、分隔符和后续节点名一起参与比较。选项不需要看起来像通配符，也能匹配多个后续节点。升级工具时应重新检查这项细节。 pytest 9.0.2 的节点选择实现

不要把报告中的“被排除”和上次测试失败、已经执行后跳过混在一起。本文的例子故意让其中一个被去掉的用例固定失败，便于看到绿灯出现的原因。它既没有把断言改成正确，也没有改变测试文件，只改变这次从所收集项目里留下哪些。

从三次运行找到漏掉的节点

将下面完整文件保存为一次性目录下的 test_calculation.py，再放一份只含 [pytest] 的 pytest.ini。关闭外部插件自动装载和环境中的额外选项。例子在 Python 3.11.15 与 pytest 9.0.2 实际执行。故意写错的第二条断言是测试输入，只在临时文件中使用。

def test_total():
    assert 1 + 1 == 2


def test_total_edge():
    assert 0 + 0 == 1


def test_other():
    assert 3 * 3 == 9

初次运行 python -m pytest -v，随后用同一命令加上 --deselect=test_calculation.py::test_total，第三次改用较长的 --deselect=test_calculation.py::test_total_edge。三轮工作目录与测试字节相同。这里没有验证项目里的插件会不会另外影响选择。

调用 执行结果 退出
不排除 短名与 other 通过，edge 失败 一
排除短名 仅 other 通过，排除两项 零
排除长名 短名与 other 通过，排除一项 零

短名本身出现在长名的开头，所以第二次真排掉了两项。第三次并没有把选项改成精确匹配，只是这个具体的长名在当前集合中没有其它前缀命中。若以后新增另一条继续使用相同的前段，仍应重做范围检查。将两份绿色记录摆在一起，可以看到同为成功退出却执行了不同数量和身份的测试。抓住这个差异，比只看到运行更快有用得多。

明确临时排除允许影响什么

如果必须留下短名的兄弟节点，先列出预期执行的节点集合，再根据需要采用符合命名约定的选择方式。短名可能无法只靠一个字面前缀排掉自己而保留所有扩展。如果已经有稳定的标记约定，可以用符合项目标准的标记选择；也可以显式运行要保留的节点。无论哪种方式，都应根据实际节点对照预定范围，不能用命令名称给覆盖范围背书。对于参数化的测试，应先确认目标是整个函数还是某一组参数，再看实际生成出来的节点身份。

适合保存的证据包括命令、工作目录、候选节点与最后执行的节点。可以先用相同的选择配置观察收集结果，再进行实际执行。收集列表本身不能替代测试结果，但可以在开始耗时运行前暴露排除过宽。运行结束后要保留留存项的结果，并注明故意排除的原因。若拆成不同的阶段，避免只复制其中一处的退出值。站内以前失败项复跑的覆盖边界使用的是历史缓存，本篇则演示当前命令输入改变集合。

对发布流程而言，临时排除并不会处理原先的失败。比如第二个测试代表某个新输入时，无论它被意外排除还是经批准暂时不跑，都没有获得本次验证。如果团队需要在排除期间发版，应明确已接受的范围和恢复条件。下一次扩展测试名时可以拿旧的排除清单做对照，检查是否顺带移走了新工作。若发现执行集合缩小，先核对节点前缀，再看是不是其他筛选配置变化。

恢复排除项时也有一项容易遗漏的验收。比如短名测试修复后，团队删除了排除配置，日志里出现了那个测试，却仍没有另一条边界用例。如果复查材料只要求被修复的节点回来，漏掉的兄弟测试未必会被发现。可以把排除前的完整范围作为参考，按本轮源码和名称变化更新，明确哪些测试应重新进入执行。不要把旧节点数当作固定目标；路径移动时数量可能相同，但身份已经不同。记录实际运行的节点和结果，才知道恢复动作是否补回了最初丢失的覆盖。此处给的是检查计划，样例没有修改或恢复真实发布配置。

模块本身导入失败，能靠 deselect 隐去它吗？

不要把节点选择当作文件忽略。该选项处理的是已经得到的测试项；模块导入若先失败，就可能还没有要移除的节点。若确实要从这次收集中排除整个文件，可用文档中的 --ignore 路径选项，并确认不会误避其他用例。另做验证时，准备一个仅用于演练的导入失败文件和一个正常文件，分别观察节点排除与路径忽略。该变体未执行。
