Go 脱离请求取消以后，新的 Context 为什么没有 Done？

比较 Go 父级取消、WithoutCancel 派生状态和重新设置的独立期限。

正文

核心要点

  • WithoutCancel 不继承取消与期限。
  • 值查找仍可以取得父级普通值。
  • 独立清理可以重新设置时间边界。

Go 的 WithoutCancel 会让派生上下文脱离父级取消与期限，返回的 Done 是 nil。它仍能沿原来的父级读取值。确实要让一段清理在请求取消后继续时，应给这段工作单独设定期限。

设想导出请求必须登记临时资源，客户端提前离开时，服务还需要把一次退出结果交给本地接收器。用原请求上下文调用接收器，它可能一入场就看到取消。把请求上下文交给 WithoutCancel 后再传入，虽然不受这次取消影响，却同时失去了之前的截止时间。若接收器迟迟不返回，原来负责限制等待的机制已经不存在。决定脱离以前，先确认谁拥有这项工作以及会等待到什么时候。

脱离以后，到底保留哪些东西

Go 标准库从一点二一版提供 WithoutCancel。文档明确说明，新上下文不会随父级取消，Deadline 表示没有期限，Err 和 Cause 返回 nil，Done 本身也是 nil。固定版本的官方源码显示，Value 仍向原父级查找。应用仍可读取原来的追踪编号，但它不再通过这个上下文观察原请求的取消结果。需要调查原始失败时，在自己的错误记录里保留父级结果。Go context 参考 与 固定版本实现。

只接收一个 nil 通道没有可到达的取消事件。在 select 中，这个分支不能靠父级取消就绪。假如等待循环本来只能由该分支退出，替换上下文后就应检查它还有没有另一个结束条件。Detach 也不会改变一个函数本身是否观察上下文。传入一个有期限的对象，只能给函数提供相应信号；一个不读这个信号的阻塞操作仍需要自己的验证。

三层上下文绑定三份预期

下面是未执行的 Go 教学程序。在支持 WithoutCancel 的工具链中运行。它先建立带追踪值和较远期限的父级，再派生脱离取消的上下文。主动取消父级以后，再为脱离者创建一条已经过期的期限。使用过去的固定时点是为了观察已经结束的状态，因此不用 sleep 等一个任意的超时。示例只操作标准库对象。

package main

import (
    "context"
    "fmt"
    "time"
)

type traceKey struct{}

var deadline = context.WithDeadline

func main() {
    root := context.WithValue(context.Background(), traceKey{}, "demo-17")
    parent, stop := deadline(root, time.Now().Add(time.Hour))
    defer stop()
    detached := context.WithoutCancel(parent)
    stop()

    _, hasDeadline := detached.Deadline()
    observedErrors := [3]error{parent.Err(), detached.Err(), context.Cause(detached)}
    if observedErrors != ([3]error{context.Canceled, nil, nil}) {
        panic("unexpected error state")
    }
    if detached.Done() != nil || hasDeadline || detached.Value(traceKey{}) != "demo-17" {
        panic("unexpected parent or detached state")
    }

    bounded, cancel := deadline(detached, time.Unix(1, 0))
    defer cancel()
    select {
    case <-bounded.Done():
        if bounded.Err() != context.DeadlineExceeded {
            panic("wrong bounded context error")
        }
    default:
        panic("expired deadline did not finish")
    }
    fmt.Println("parent canceled, detached alive, bounded deadline expired")
}

第一份预期是父级返回 Canceled。第二份预期是脱离者仍能取得 demo-17，且没有可等待的 Done、期限和取消原因。第三份预期是新后代立即出现 DeadlineExceeded。后三个状态不能用一条“清理成功”日志一起替代。只观测追踪值保留，可能漏掉已经没有中止信号；只观测新的边界结束，也不能证明它没有误沿父级取消。程序用独立条件限制三个对象，而且没有真的连接接收器或删除资源。

在实际应用里可以给清理函数注入一个测试接收器。父级取消之后，观察它是否仍进入需要运行的步骤。另让接收器显式等待清理上下文的结束，并核对返回的是清理期限的错误。这样能覆盖真实调用处有没有把新的上下文继续传下去。上面的固定过期时点只是标准库状态检查，这个调用者回归目前未运行。

按工作归属决定是否脱离

用户主动取消上传时，主要的处理步骤通常还应响应取消。与之不同，释放自有的临时资源可能由服务负责完成。不要把整个请求流程换成脱离者；只在需要后续责任的调用处派生，再给它一个能解释的独立预算。对于有外部副作用的动作，还要查它是否允许在请求结束后开始。上下文的生命周期无法代替服务定义外部动作的授权与幂等规则。

可在正常结束和提前取消这两个入口各核对一次资源状态。正常结束时，清理只执行一次；取消后，原请求不再推进主要操作，但登记的清理步骤仍按自己的条件结束。若清理超期，应该保存它自己的关闭结果，而不是覆盖最早的请求失败。后台进程在服务关闭时如何处理这些工作，也是更高层的职责。站内的 取消与等待时点 讨论异步函数收到取消后的收尾；这里关注 Go 的独立截止时间这一处合同。

可以再对清理接收器安排一条提前返回和一条等待结束的独立路径。提前返回时调用持有者自己的取消函数，确认关联的工作有明确收尾；等待路径则用有界测试环境观察截止时间到达后返回的错误。测试不能只用一份已经过期的上下文证明真实接收器在收到信号以前正常工作。给请求主流程和这个接收器不同的活动记录，确认主流程不会因清理仍在运行而隐式继续提交请求。这里的请求、清理和接收器都只是应用侧设计，未运行。

如果原应用只在函数返回时才报告清理结果，错误的等待还可能拖住一批下游任务。应在真正由应用拥有的清理范围里定义结果和结束动作，给成功、失败和超期三个出口分别记录关键信息。否则即使父级状态记录完整，也看不到哪一项资源失去处理者。验收要绑定到这次清理的资源标识，避免另一个后台任务的完成记录误让本项通过。

脱离请求后，原上下文里的身份信息会一起消失吗？

不会因为取消脱离而自动消失，普通值仍沿原上下文查找。若后台任务只应携带追踪编号，可以创建一份明确只含该测试值的上下文，再给它设置截止时间。验收给原上下文放两个独立标记，只允许新任务读到其中一个。不要把能读到标记解释为获得后台操作的权限，也不要让一次局部示例替代真实数据保留策略。这项选择性传值的测试未执行。
