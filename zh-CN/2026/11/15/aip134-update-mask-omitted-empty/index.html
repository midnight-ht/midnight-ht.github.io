update_mask 不传和传空路径，会更新同样的字段吗？

同一个新标题，分别省略掩码、传空列表和指定 title。对照 AIP-134 的更新范围与返回结果。

正文

核心要点

  • 省略掩码时根据非空字段推断
  • 空路径列表按 AIP-134 建议执行无操作
  • 在请求解码时保留掩码字段的存在性

编辑图书资料的两个客户端都提交标题 New。第一个没有给更新掩码，第二个给了掩码，但里面没有路径。保存后，前者把标题改了，后者读到的还是 Old。按 Google AIP-134 的约定设计标准更新方法时，这两个请求各自表达了不同的更新范围。

更新范围来自请求的哪一部分

图书目前存着标题 Old、备注 Keep。这次请求里的资源对象只出现标题 New，没有备注。更新方法要知道哪些字段允许写入。显式路径就能给这个问题一个直接答案：掩码含 title 时，取请求里的标题并写入，备注不在选定范围内。

省略整个掩码时，按照 AIP-134 的规则，从资源里已填且非空的字段推断范围。这个输入只有非空的标题，所以应选中 title。资源对象里没出现的备注不进入这次推断。结果是标题变成 New，备注照旧。

如果掩码对象已提供，却没有指定任何路径，AIP-134 建议把请求作为无操作并返回未修改的资源。请求虽然有 New，范围里却没有 title。调用方拿到的资源仍是 Old 和 Keep。在遵循此约定的实现里，空路径列表表示选择了零个字段。

这两个请求之间的区别发生在进入更新规则之前。比如解码器将没传的掩码自动补成一个空对象，代码拿到的形态就失去了字段存在性。省略原本应该从非空资源字段推断范围，补齐之后却可能落到无操作。想排查这类错误，先检查原始请求和解码后掩码的两个状态，别直接从路径长度判断。

三种范围，使用完全相同的资源输入

下面的 Node 夹具使用 JavaScript 对象演示规则。它的输入限于示例里的两个字符串字段与已知掩码路径，不实现通用路径解析或实际持久化。夹具给掩码字段起了驼峰名，以便代码阅读；名称写法不代表任意传输协议接受这份对象。

import assert from 'node:assert/strict';

const stored = {title: 'Old', note: 'Keep'};
const edits = {title: 'New'};
const hasMask = Object.hasOwn;

function updateBook(current, request) {
  const submitted = request.book;
  const paths = hasMask(request, 'updateMask')
    ? request.updateMask.paths
    : Object.keys(submitted).filter(key => submitted[key] !== '');
  const next = {...current};
  for (const key of paths) next[key] = submitted[key];
  return next;
}

const cases = [
  [{book: edits}, {title: 'New', note: 'Keep'}],
  [{book: edits, updateMask: {paths: []}}, stored],
  [{book: edits, updateMask: {paths: ['title']}}, {title: 'New', note: 'Keep'}],
];
const {deepEqual} = assert;
for (const [request, expected] of cases) {
  deepEqual(updateBook(stored, request), expected);
}
console.log('Omitted, empty, and title masks passed.');

本机运行三组断言均通过。三次调用用同一个存量对象和同一份标题，新旧值的差异只来自掩码。第一条省略掩码，变为 New。第二条给空列表，保持 Old。第三条明确标出 title，再次得到 New。三次都单独检查了备注 Keep，以防全量赋值误删没提交的字段。

把这些测试移到服务的请求入口时，应当让测试走过真实解码层。仅在业务函数里手工构造两个不同对象，能验证更新逻辑识别了差异，却无法发现解码器在两者抵达业务层之前把它们归成一种形态。对接口级用例，记录解码前有没有掩码字段，以及解码后还能不能区分。

端点验收可以让同一个请求构造器产生两个样本。第一个完全删去更新掩码字段，第二个保留字段并使用这个传输格式支持的空掩码表达。核对原始消息确实保留了这种差异，再看服务响应和下一次读取。如果协议或组件在入口阶段就把两种请求合并，测试应把这条限制记录出来。不能拿绕过解码器的本地对象去证明线上入口能够区分。

请求构造层也可能引入同样的问题。比如通用表单客户端每次都为路径列表初始化一个空数组，确定用户编辑过哪些字段前就带上了掩码。若产品原先希望服务端按请求资源推断范围，这个默认值就改变了请求意图。端点若以无操作返回，调用者可能只因拿到了成功响应就误认为保存了标题。

返回值可以帮忙做最后一层检查。编辑界面在提交后若拿到整个资源，可比较其中标题是否成为刚提交的值。若还是 Old，先确认请求实际选中的路径。不要在本地仅凭请求体就把界面强行显示为 New，否则用户刷新后会再次看到旧标题。

规范还给通用更新掩码定义了单独的星号语义，表示完整替换。它不等同于空列表。在我们的部分更新示例里，没有实现星号，也没有演示复合路径或嵌套字段。若你的资源有输出专用字段或未来还会加新的可写字段，应查自己端点的完整替换契约。

测试也可按调用者意图命名，分别写「推断标题」「选择零项」「明确选择标题」。如果只写三个编号，后来重构的人可能把两个请求折叠成同一种序列化结果。用名称指出范围如何产生，再把 Keep 当成共同的保护性断言，能让测试失败后更快找到该查的层。

希望把标题清空，省略掩码可以吗？

不要依靠省略来完成这次清空。这里加一个新条件：示例资源允许空标题。请求给 title 一个空字符串时，按非空字段推断的范围不会选中它，原有标题继续保留。明确送入 title 路径和空字符串，更新方法才会尝试把该字段写为空。若实际资源要求非空，显式路径仍要接受资源自己的校验。

这里本来相同的两条成功分支就分开了。原值 Old、提交值 New 时，省略和给出 title 的结果相同；提交空字符串后，只有显式的 title 告诉服务这次清除是有意的。用允许清空的资源再验收一轮，可以发现客户端只会保存新文字，却表达不了删除原值的问题。

如果你在选的是 HTTP PUT 和 PATCH 的请求契约，可以另看替换和局部更新分别承诺什么。
