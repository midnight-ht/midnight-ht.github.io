SINTERCARD LIMIT 2 返回 2，交集真的只有两个吗？

用三组交集区分 Redis SINTERCARD 的下界、阈值判断和精确计数。

正文

核心要点

  • 达到上限的返回值可能只是下界。
  • 小于上限时可以得到该次命令的实际计数。
  • 按业务合同选择阈值判断或完整计数。

Redis 的 SINTERCARD 带 LIMIT 2 返回二，只能说明交集至少有两个成员。命令达到上限就可以结束。需要精确总数时，应使用不受这个上限截断的查询，并确认两次观察是否针对同一份集合状态。

假设资料筛选页要知道当前用户标签与某个活动的可用标签至少有两项重合。页面只需要决定是否显示入口，开发给计数命令设了上限二。随后另一个报表直接把这次返回值写成“共有两项”。那份报表无法区分正好两个与实际更多。先写清谁在问是否达标，再决定是否还需要保留完整计数。

上限改变了数字能回答的问题

Redis 文档说明，SINTERCARD 计算给定集合的交集大小，返回的是数目。LIMIT 默认为零，表示没有上限。如果设置了正上限，计算达到这个值就可以停止并返回该数。若返回小于上限，则在该次命令的集合状态下得到了实际大小。若返回值等于上限，单凭它无法知道结果是刚好达到，还是已超过。此处讨论 Redis Open Source 七版开始提供的命令；集群部署还需符合多键命令要求。Redis SINTERCARD。

对于只问有没有两个的入口，将结果和阈值比较就可以得出预期判断。对于页面显示“共有多少项”的字段，要保留完整计数的语义。即便两个字段最终都用整数表示，它们的验收也不同。一个可以用大于二的样本验证被截在二，另一个必须能看到三。不要用一次观察把两条合同一起标成通过。

用小于、等于和超过阈值的样本

下面的教学命令未执行。使用自有隔离 Redis 实例和起初不存在的键。参考集合含 a、b、c，三个候选集合分别含 a、b、c、d，含 a、b，以及只含 a。键名使用同一哈希标签，便于明确样本意图；这里没有连接集群或验证实际部署规则。脚本从同一份教学输入给两种计数各写预期。

# Run against a disposable Redis 7+ instance with unused keys.
r() { redis-cli --raw "$@"; }
base='{overlap}:reference'
r SADD "$base" a b c

while read -r suffix members bounded exact; do
    key="{overlap}:$suffix"
    set -- $(printf '%s' "$members" | tr ',' ' ')
    r SADD "$key" "$@"
    capped=$(r SINTERCARD 2 "$base" "$key" LIMIT 2)
    total=$(r SINTERCARD 2 "$base" "$key")
    test "$capped" = "$bounded" && test "$total" = "$exact" || exit 1
    printf '%s limited=%s exact=%s\n' "$suffix" "$capped" "$total"
done <<'ROWS'
large a,b,c,d 2 3
equal a,b 2 2
small a 1 1
ROWS

交集三项与交集两项，应同时在带上限的查询得到二。没有上限的查询会让二者分别得到三和二。第三组交集只有一项，两种查询都应返回一。这个结构可以用来给代码审查留独立结果，不必运行线上负载。取正确的键必须靠实际输入，不该根据测试命令回复自建预期。代码假设样本没有其他写入者；生产里先发有上限命令，再发无上限命令，第二次可能面对不同成员，因此两个结果不应被自动拼成同一时点的结论。

还可以给报表专门做一条失败控制，把前两组的带上限计数交给声称精确的输出。两条记录都会显示二，明明只对其中一条准确。若客户端只保存了一个数字，错误发生后很难从日志判断它的请求上限。验收可以记录原命令所用的上限、返回值和字段合同。用另一个可观测字段表示达到阈值，让查问题的人知道二是确定的总数还是这次已找到的下界。

给调用方保存相称的结果

如果只决定能否显示入口，直接返回是否达标更容易保持合同。需要展示局部结果时，可以报告“至少两项”，并让调用方知道这个短语来自限制条件。需要审计的地方，使用完整查询和对应的读取证据。应用同时需要判断与精确总数时，也可以先说明哪条路径承担哪一步，避免默认一次限额结果到处复用。读取成本与业务是否需要准确数字相关，但本文没有做性能比较，不能从一组固定标签推导响应时间或容量。

为两条业务路径做对照时，可以给相同的比较对象设置两个预期输出：阈值接口为真，精确接口为三。再将这个对象换成只有两项的集合，阈值接口仍为真，而精确接口改成二。这样能检验共享缓存或响应字段是否误把前一种结果当成后一种。站内的 Redis SCAN 的遍历合同 讨论另一种 COUNT 参数，此处 LIMIT 达到后可以直接限制返回计数。应用缓存和并发条件未运行。

如果服务缓存计数结果，要把查询范围和计数合同一起纳入验证。可以先走阈值入口得到二，再走精确入口，要求仍得到三。检查后者没有读到前者留下的缓存。反方向也要考虑，精确值可以帮助判断阈值，但必须确认缓存里的集合输入和观察时点仍适用。若标签在这两次调用之间被更新，缓存是否失效由应用自己的规则决定。可以给验收加入一次移除操作，要求记录显示当时用的是哪个集合版本。没有版本证据时，两次结果不同只能说明观察可能变化，不能凭它判断某个 Redis 调用计算错误。这些缓存路径是应用侧设计，未运行。

其中一个集合键缺失，返回零是没有交集还是没有配置？

命令将不存在的键视为空集合，所以该次交集为零。若业务把缺少配置和已配置但不匹配视为不同状态，应另从配置来源获取可比较证据。可以准备一个未创建的键，再用两个确实存在但互不相交的集合，预期它们都给同一个零。给应用分别标记未配置与无匹配，确认界面没有只凭交集数决定前者。用独立 EXISTS 检查也需要考虑并发变化，不能自动把两条命令视为一致快照。这个追问未执行。
