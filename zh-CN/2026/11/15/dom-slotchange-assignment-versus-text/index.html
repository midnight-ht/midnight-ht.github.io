投影文字已经改了，为什么 slotchange 没触发？

用同一个默认插槽分别改文字和换元素，核对分配节点身份、显示内容与通知。

正文

核心要点

  • 改元素里的文字可以保留分配节点
  • 换成同文案元素也会改分配列表
  • 通知可能合并，应分别检查身份与内容

一个组件用默认 slot 接收外面的文字。页面已经把显示内容从 A 改成 B，组件里绑定的 slotchange 监听器却没有记录。接着把 B 所在的整个元素换成另一只也写着 B 的元素，屏幕看起来没有变化，监听器反而有记录。需要分别看投影进来的节点和那个节点给人看到的文字。

先确认是哪一个节点被分配

主例里的宿主只放一个 span，span 里面是文字 A。影子树有一个默认插槽，分配给它的是外面的 span。看界面时，人从插槽的位置读到 A。看分配列表时，程序看到的却是一个元素引用，并没有一条额外的文字节点分配记录。文字是这个元素的后代。

把 span 内原来的文字节点改为 B 时，分配列表里仍然是同一个 span。页面内容变了，表示父子关系的这层引用没有换。读取分配列表再比较第一项与原元素是否相等，可以把两件事的证据分别取出来。

反过来，新建一个文字同样为 B 的 span，再用它替换原元素。插槽末尾的可见字符串还是 B，可是更新后的分配列表第一项引用了刚创建的元素。DOM 的分配步骤比的是列表中的节点，未用文字内容决定列表是否相同。此时会为这次分配变化发信号。

这解释了为什么只用界面截图查不清监听器有没有漏报。截图只能呈现文字和样式。打开组件的调试记录，同时保留当前分配引用与需要显示的文本，才会看到同样的字可以来自不同元素，不同的字也可以仍来自同一个元素。

两步执行，分别记下累计计数

把下列页面存成一个 HTML 文件。页面首次装上插槽后先等一个任务，再装监听器，避开初始分配可能发出的通知。两个后续操作也分到各自的观察间隔。记录依次包含操作名称、累计收到的事件次数、分配元素是否仍是原元素，以及该元素里的文字。

<!doctype html>
<meta charset="utf-8">
<title>Slot assignment check</title>
<div id="host"><span>A</span></div>
<pre id="result"></pre>
<script type="module">
const host = document.querySelector('#host');
const output = document.querySelector('#result');
const shadow = host.attachShadow({mode: 'open'});
const slot = document.createElement('slot');
shadow.append(slot);
const pause = () => new Promise(resolve => setTimeout(resolve, 0));
await pause();

let events = 0;
slot.addEventListener('slotchange', () => { events += 1; });
const first = host.firstElementChild;
const report = label => {
  const [assigned] = slot.assignedNodes();
  output.textContent += [
    label, String(events), String(assigned === first), assigned.textContent,
  ].join(' | ') + '\n';
};

first.firstChild.data = 'B';
await pause();
report('text edit');

const replacement = document.createElement('span');
replacement.textContent = 'B';
first.replaceWith(replacement);
await pause();
report('node replacement');
</script>

按 DOM 算法推导，第一行应是 text edit、零次、true、B，第二行应是 node replacement、一次、false、B。两行文本相同，前后节点身份不同。这里的输出是对该独立页面的预期，本文没有实际操作浏览器测试。若在宿主标签内部调整缩进并添了其他文本节点，先确认取到的第一项仍是示例的元素。

监听器计数要等当前通知机会过去后再读。规范把信号放进代理上的插槽集合，并排入通知微任务。这个例子把两步分开来观察，不能反向推出一次同步修改总会对应一次回调。在同一轮里连续换两次，最终通知的数量也不直接告诉你发生了多少次赋值。

如果页面还有别的组件在操作这个插槽，计数差异也可能来自额外的输入。最容易定位的方式是保留一个独立页面，把监听器注册时间和两个操作隔开。先核对节点身份与内容，再回到真实组件看是否还有框架更新或应用代码执行在同一时间。

组件依赖的是内容还是分配关系？

侧边栏如果只要知道当前收到的是哪个元素，例如给刚插进来的控件初始化，就关心原有节点是否换成了另一项。这时分配变化信号有直接价值。初始化逻辑仍需运行一次，保证监听注册前已经出现在插槽里的项可以被发现。

如果组件展示的是赋给它的标记文字，还要决定谁负责通知文字更新。一份可控数据模型可以让上游同时更新文字和计数显示。若接收的是外部任意 DOM，可以从当前分配结果找到需要观察的元素，按实际编辑方式订阅文字节点或子树变化，并在分配元素更换后切换观察目标。

两种工作常在同一个组件出现。把测试拆开能看清谁负责什么。用主例的第一步验证内容订阅能捕获 A 到 B，用第二步验证观察目标能从旧节点换成新节点。测试完成后还可以编辑旧元素一次，检查组件是否已经停止使用它，避免删除的元素继续推送状态。

在升级组件的实现时，还可以把这两行输出当成断言的形状。分别保存事件计数、最初元素引用和当前文案，失败信息就能明确指出是哪一列改变。若只记录字符串变化，旧节点和新节点的监听错绑会蒙混过去。若只记录回调次数，文字变化没有触发通知又容易被误判成问题。把四列放在同一行，是为了让一次编辑和它的证据对应。

没有分配节点时，直接添加备用内容会有事件吗？

会。换一个场景，宿主没有任何可分配子节点，而且默认插槽开始时也是空的。等初始通知处理完，再把一个带字的 span 直接添加到影子树里的插槽中。对于这个未分配的插槽，DOM 的插入算法会显式发信号，而普通的 assignedNodes 调用仍然得到空数组。新元素是插槽的备用子节点，并非宿主传进来的内容。

因此调试空插槽时，收到通知后还应读取分配列表。对需要处理投影控件的组件来说，备用提示出现时可以更新界面文案，仍没有外部控件可初始化。永远把事件当成分配列表非空的证明，就会在这一种输入上产生错误。

若你在调查的是影子树内一次点击从外部看作哪个目标，可以另看影子 DOM 的事件重定向与路径。
