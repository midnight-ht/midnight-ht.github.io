CMake 的 try_compile 绿了，为什么程序仍链接失败？

用同一份含未定义符号的 C 源码复验 CMake 的可执行探针、静态库探针和真实目标。

正文

核心要点

  • 静态库探针不承担可执行文件的链接。
  • 保存探针类别和诊断，避免只记录布尔值。
  • 仍需按照交付目标补对应的链接证据。

静态库探针可以完成编译和归档，却未生成可执行文件。CMake 的 try_compile 变绿时，先确认它构建了哪类目标。若需要证明程序能链接，还要有可执行目标的链接结果。

维护交叉编译配置时，常见的第一个任务是让工具链通过探测。目标平台需要额外的链接脚本，配置人员先把探针改成静态库，希望先检查编译器能否接受源码。这个调整可以解决特定阶段的依赖，却也改变了探针能证明的范围。如果后续报告仍写着“程序链接已通过”，另一个人在发布构建失败时就很难解释两个结果。应该把探针名称、目标类型和输出放在同一条记录中。

用同一源码改变探针目标

CMake 的目标类型变量规定，在接受源文件的探针形式中，未指定类型时使用可执行目标。设置为 STATIC_LIBRARY 时，生成的探针会构建静态库，可以避开可执行文件的链接。它不会因源文件中声明了一个外部函数，就自动为调用者提供该函数的实现。归档可保留待最终链接解析的引用。下面用能够编译但欠缺实现的声明，观察这一差别。

把两份文件放在独立目录内，分别保存为 CMakeLists.txt 和 main.c。需要 C 编译器和支持这里写法的 CMake。本地测试采用 CMake 4.2.3 和该机的 Apple Clang。命令包含实际配置和构建，后者有意失败。它不是交叉工具链的验收，只隔离出探针目标变化。

cmake_minimum_required(VERSION 3.25)
project(LinkBoundary C)
set(src "${CMAKE_CURRENT_SOURCE_DIR}/main.c")
set(CMAKE_TRY_COMPILE_TARGET_TYPE EXECUTABLE)
try_compile(linked SOURCES "${src}" NO_CACHE OUTPUT_VARIABLE link_log)
message(STATUS "executable probe: ${linked}")
message(STATUS "${link_log}")
set(CMAKE_TRY_COMPILE_TARGET_TYPE STATIC_LIBRARY)
try_compile(archived SOURCES "${src}" NO_CACHE OUTPUT_VARIABLE archive_log)
message(STATUS "static probe: ${archived}")
if(linked OR NOT archived)
  message(FATAL_ERROR "Unexpected probe results")
endif()
add_executable(real_program "${src}")

extern int optional_provider(void);

int main(void)
{
    return optional_provider();
}

执行 cmake -S . -B out，再运行 cmake --build out。配置时，第一个探针返回 FALSE，诊断中有找不到的 optional_provider；第二个探针返回 TRUE。两个实际结果满足项目写下的预期，因此配置成功退出。构建真实目标时链接器再次报告同一个缺少实现的符号，构建退出二。运行证据包括 CMake 版本、两份日志和两次退出值。

这个反例并不是把已经编译失败的源码塞进静态库。两种探针使用同一文件，函数声明让编译器能处理调用；欠缺的实现到了可执行目标链接时才成为错误。若误以为两种目标等价，只要在发现红色探针时改成另一种类型，就能得到绿色结果，却没有增加满足链接条件的输入。看见绿色后应在报告里写清得到的是归档层级的证据。

决定哪一层需要通过

如果只是检查特定头文件、语法或编译器开关，静态库探针可能足够。许多交叉工具链需等相应启动文件或链接脚本就绪，才适合测试完整程序。在这种情况下，可以明确将初步探针限制在编译层，把链接检查安排到准备齐全的工具链阶段。若问题本来就是能否解析某个库的符号，应把真实接口、库和参数接到可执行探针里，或者用交付目标直接验证。当前示例故意没有提供实现，不能被当成某个外部库的可用性测试。

另一个可能的误读发生在自动化门禁。配置返回零，并不意味着每个内部探针都返回真；本例恰好把一个 FALSE 当作预期。可以分别收集探针标签、结果及对应诊断，再和构建命令的退出情况核对。若同一套脚本在不同平台调用了不同工具链，保留实际编译器、目标类型与链接参数，避免把缺少库和选错探针类型混成同一个报错。此前生成文件何时落盘处理的是另一种配置状态，和本题同样要求记录每条证据发生的阶段。

团队如果还需要知道程序能否运行，应安排目标平台或适当运行环境中的单独检查。可执行文件成功链接仍不足以证明目标平台能够启动它，也无法代替测试实际调用的接口。交付记录可以为编译、链接和运行各留一项可核对结论。若运行条件未满足，就保留该项未知，同时保留前面已经取得的证据。避免因为后一项不可运行，就把前一项的绿灯改写成全部通过。

有些配置会把编译探针作为功能开关的输入。若这个开关一旦启用，程序就会实际调用目标库，选择静态探针前应先检查该开关承诺什么。例如源码只需要声明，头文件存在便可通过；但可选功能要真正启用，还需知道最终目标有没有带上实现。可以让探针分别命名为头文件可用和实现可链接，并在验收中同时保留两个结论。这样以后关闭其中一项不会导致团队误以为整个功能已验证。

尝试修复时，应该使新增证据正好对应原缺口。例如为这个演练添加一个返回固定整数的 provider 文件，让探针和实际目标分别明确纳入它，再查看链接诊断是否消失。那相当于补上原先缺少的输入，和仅修改配置变量产生不同结果。这个修复变体尚未运行，主例只检查同一欠缺实现的源码如何经过三条路径。

整个子项目形式的 try_compile 也会被改成静态库吗？

这个变量针对源文件签名。若传入一个完整 CMake 子项目，它使用那个项目声明的目标。需要静态库时，应在子项目中明确所选目标及其类型；如果子项目仍声明可执行目标，不能用外层源文件探针的结论替它验收。主例使用源文件签名，这种子项目对照未运行。 CMake try_compile 的两种签名
