Python 临时文件明明很小，为什么一调用 fileno 就落盘？

用两条本地样本核对 Python 临时文件的描述符触发、显式转换和读回结果。

正文

核心要点

  • 调用 fileno 可以触发临时文件转换。
  • 公开样本分别核对描述符、位置和字节。
  • 需要可重开路径时，应另验文件名接口。

Python 的 SpooledTemporaryFile 即使只写了很少的字节，调用 fileno 也会让已有数据转入真正的临时文件。大小阈值和描述符是两种触发条件。如果下游库必须拿到描述符，应把这次转换算进临时文件使用方案。

假设后台导出三个字节的测试记录，并把可读写的文件对象传给上传适配器。应用把阈值设置成八字节，原以为这份记录肯定一直留在内存。适配器为了取得描述符调用 fileno，随后临时文件开始参与工作。排查应先记录谁请求了描述符，再核对适配器究竟需要描述符还是只需要读写方法。只搜大对象的写入位置，会漏掉这种与大小无关的转换。

把两条转换路径分开看

标准库文档说明，数据会缓存在内存中，直到长度超过 max_size，或者调用文件的 fileno 方法。之后按 TemporaryFile 的方式工作。还有一个公开接口 rollover，可以主动执行转换。只要使用 fileno，哪怕目的是检查有没有真实描述符，这个读起来像查询的动作也会改变对象状态。检查程序若先调用它，再判断之前是否已经转换，就把观察动作和触发动作合在一起了。Python tempfile 参考。

这也影响异常处理的位置。配置八字节的阈值并不能免除部署环境对临时文件位置的要求。给适配器加一条独立的失败用例，让它在请求描述符时无法建立可用临时文件，观察错误是在交接前还是交接后被处理。真实权限和目录行为取决于部署，不能用一次普通运行替另一台机器背书；下面的样本没有制造这类系统错误。

分别验收字节、位置和描述符

下面完整程序在本地 Python 3.11.15 运行。两个分支都在同样的八字节阈值下写入 abc。第一个分支直接索取描述符，第二个先显式转换再索取。程序只使用公开接口，刷新后检查描述符对应的大小，再核对当前位置和读回内容。

import os
from tempfile import SpooledTemporaryFile

def observe(explicit):
    with SpooledTemporaryFile(max_size=8, mode="w+b") as spool:
        spool.write(b"abc")
        if explicit:
            spool.rollover()
        handle = spool.fileno()
        spool.flush()
        assert os.fstat(handle).st_size == 3
        assert spool.tell() == 3
        spool.seek(0)
        assert spool.read() == b"abc"
    return "explicit" if explicit else "descriptor"

print(observe(False), observe(True))

两组都以大小三、文件位置三和读回 abc 为预期。归档运行完成了两组断言。第一组说明这个小输入也能在公开的描述符入口获得真实文件。第二组验证显式转换以后，同样可以从该对象读回预期数据。两种结果没有检测文件页是否写入物理介质，也没有观察转换前内部对象的存储位置。不能把刷新缓冲写成数据已经持久化；样本的结论只关乎本地描述符与对象内容。

如果还要单独测试大小阈值，应准备长度恰好等于八和超过八的输入，并选择不会自己调用 fileno 的观察方法。文档中的大小条件是超过，对这一点可核对原文。应用层也可以在输入路径记录何时向存储适配器请求真实文件。若测试的目标是业务持有对象能否继续读取，直接断言字节就够了；若目标是内部转换时点，需要明确所观察的实现和版本，不能用公开转换动作反推旧状态。这个阈值扩展没有运行。

按消费方接口选择资源形式

对于只需要 read、seek 的组件，可以给它一份符合文件对象合同的输入，测试中检查读取范围和当前位置。若组件必须把描述符交给系统调用，就主动在明确位置完成交接，例如先请求描述符，再安排使用与释放。这样，一次转换失败能归到这个准备步骤，避免在真正发送数据以后牵连后续操作。实际业务是否应保留正在生成的产物，需要另外定义；这个示例退出作用域就释放临时资源。

还可把同一份三字节数据送进两个假的接收器。第一个只读对象，返回实际字节数；第二个先要求描述符，再从对象核对读取结果。给两条路径分别记录读取位置，防止把起始位置错误归因于转换。若接收器用完后还要访问原对象，先明确是谁管理关闭，避免接收器提前关闭调用者仍要用的资源。这两条接收器路径是验收设计，未运行。真实接收器也可能在一次调用中提前读取或调整位置，应通过其入口复查。

导出 API 还可以把很小的输入、接近容量的输入和需要描述符的输入分别纳入验收。每次记录文件对象由谁创建、谁请求转换，以及关闭发生在什么时候。这样能区分空导出、数据截断和临时资源准备失败，而不必从最后一条“上传失败”猜测。这里没有比较两种模式的费用，也没有测算容量。

给上传适配器做单元测试时，还可以让一个可读对象故意不提供可用的描述符。传给只需要读的接收器，预期三字节仍可完整交付；传给要求描述符的接收器，预期在准备阶段明确报错。这样可以检验文档中写下的最低接口条件，又不会误把内存测试当作部署临时目录验证。这个扩展未执行。

转换后能把 name 当成另一个程序可重开的路径吗？

不能把 TemporaryFile 语义当成保证存在的文件名。不同平台可能根本不给它可重新打开的目录项，或者在创建后移除目录项。若下游要求的是路径，应选择明确提供可见名称的接口，并单测关闭及重新打开的时点。站内的 NamedTemporaryFile 重开与清理 进一步讨论这份路径合同。这里的描述符测试没有运行另一个进程，也没有验证在任何平台上可以靠 name 重新打开。
