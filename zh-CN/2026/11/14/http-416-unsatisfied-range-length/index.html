收到 HTTP 416 和当前长度，文件就算下完了吗？

用两个等长本地样本核对 HTTP 416 的当前表示长度，解释客户端何时还需要内容证据。

正文

核心要点

  • 416 中的 bytes */N 给出当前选定表示长度。
  • 本地长度相同仍要核对表示与内容。
  • 缺少 Content-Range 时保留当前长度未知。

本地已经有八字节，客户端从偏移八继续请求，服务器返回 HTTP 416 和 Content-Range: bytes */8。这个字段说当前选定表示有八字节。它可以解释为什么没有第九个字节可读，却不能证明本地保存的八字节已经完整正确。下载器还需要核对本地内容属于哪份表示。

先读懂星号提供的长度

RFC 9110 的 416 定义说明，服务器可以因请求区间无法满足而返回该状态。这里仅考虑一个合法的开放结束字节范围。字节坐标从零开始，如果表示长度为八，当前有效位置从零到七。请求 bytes=8- 从下一个位置开始，因此对于这份表示无法满足。相同请求到支持不同策略的服务器，仍可能收到完整响应，不能在发出请求后预先假定一定得到 416。

Content-Range 的定义将这种星号写法用于传达当前选定表示的长度。星号并未给出本次响应所传输的文件区间。客户端不能把错误响应的正文拼到本地文件里，也不能把长度解读成文件身份。这里的八是表示的字节计量，示例不做内容编码转换。如果产品协商多个版本或编码，要把长度与实际选中的表示绑定，不能跨口径比较。

假设本地任务按地址保存已有片段，用户离开后源站同一地址更新了内容。新旧两份都可能有八字节。此前读取到的文件与目前服务器选择的表示长度相同，也不能依靠星号字段判断它们相同。还可能是一个字节在本地写入失败，后来留下了同长但内容错误的文件。这两种情况需要不同来源的验证数据，但都无法从长度排除。

两份八字节的文件，只有一份能通过对照

下面的完整本地 Node 样本直接使用固定状态和头部对象，没有发送 HTTP。教学中提前拥有一份可信的完整字节 ABCDEFGH。第一个本地文件和它相同，第二个把一个字节改成 X，第三个多存了一个字节。预期来自写下的字节内容：前两份长度都对，只有第一份的内容一致。代码的简化字段读取只服务这组有限正整数样本，不能作为通用 HTTP 字段解析。

import { deepEqual } from 'node:assert/strict';

const reply = { status: 416, contentRange: 'bytes */8' };
const trusted = Buffer.from('ABCDEFGH', 'ascii');
const correct = Buffer.from('ABCDEFGH', 'ascii');
const wrong = Buffer.from('ABCDEXGH', 'ascii');
const longer = Buffer.from('ABCDEFGHI', 'ascii');

function inspect(bytes, { status, contentRange }) {
  if (status !== 416) throw new Error('expected fixture status 416');
  const field = /^bytes \*\/(\d+)$/.exec(contentRange);
  const length = field ? Number(field[1]) : null;
  const sizeMatches = length === bytes.length;
  return [bytes.length, length, sizeMatches, sizeMatches && bytes.equals(trusted)];
}
const report = [correct, wrong, longer].map(file => inspect(file, reply));
deepEqual(report, [
  [8, 8, true, true],
  [8, 8, true, false],
  [9, 8, false, false],
]);
console.log(JSON.stringify(report));

两个相等的长度分别回答了相同大小的问题，并没有回答同一内容的问题。第二个文件因此不能标为完成。第三个文件也不能看到服务端报告八就自动截断，它多出来的字节没有说明前八字节可信。实际下载器不一定有这份完整预期数据，可以由已确认的表示验证器和本地写入证据建立身份及覆盖范围，也可在业务合同支持时使用来自可信来源的完整性值。只要其中的前提还没有证实，界面应保留需要验证或重新下载的状态。

本例把字节直接比对，避免将程序刚下载到的内容自己算成“正确答案”。如果项目改用摘要，验收也应区分预期摘要的取得方式与本地计算的结果。将两个同长样本送入同一个流程，记录长度检查和内容检查分别给出什么结果。前者适合排除明显的边界不一致；后者才有机会发现长度不变的错误。不要让一个相同的数字覆盖掉另一项检查的失败状态。

恢复分支要根据本次拿到的证据选择

先看实际响应，再决定动作。收到完整表示时应按完整替换路径处理，不能直接追加。收到可用部分响应时，应核对它的起点、所选表示身份与实际收到的范围。收到 416 时则先保存当前长度及请求范围，然后核对本地信息是否足以证明完成。站内断点续传的表示一致性说明追加与替换的判断，本篇补的是请求从边界外开始后，怎样解释服务器给出的当前长度。

可以把验收安排成三个分支：同一表示的已验证字节覆盖全长、长度恰好但身份无法确认、长度明显大于当前边界。第一种可以依据项目已有证据确认完成；后两种应按合同要求校验或重新获取。另测本地清单说八字节、磁盘文件只有七字节的恢复路径，以实际落盘结果为准，不能靠上一次 UI 进度条决定请求起点。这里是客户端设计判据，不是已运行的文件系统测试。

网络中断之后还要考虑用户如何继续。若当前记录不足以证明可以追加，可以先保留旧文件和其状态，另外准备重新取得完整表示。若业务允许使用临时文件，再在完整读写核对后替换目标，避免让一个待验证文件冒充可使用的结果。不要用样本中的八作为任何固定阈值。项目应绑定请求的资源身份、表示条件和本地写入记录。

收到 416 却没有 Content-Range，可以拿缓存中的长度吗？

缓存值只能描述过去保存的元数据。现在把主例的字段拿掉，客户端仍知道请求未得到所要的区间，却没有从这次响应得到当前长度。规范建议服务器为字节请求的 416 提供该字段，并不保证所有链路一定有。应将当前长度保留为未知，按接口合同重新取得足够的表示元数据，或走完整获取与替换。用旧的八直接宣布文件完整会把历史估计变成本次验证。
