Prometheus 给出了 p75，为什么还说桶计数被修正？

手算一组累计桶的分位数修复，用单调对照分开数值结果与输入质量。

正文

核心要点

  • 经典桶的累计计数不应随上界扩大而下降。
  • 修复后仍可计算出分位数。
  • 查询数值与 info 注记应分别核对。

一个累计桶竟比更窄的桶少，Prometheus 仍然可以给出分位数。经典直方图的计数明显逆序时，histogram_quantile 会为这次计算抬高下降的桶，并附带提示。分位数有值和输入没有问题，是两件需要分别核对的事。

设想值班工程师看到面板里的 p75 仍为零点四五秒，另一份查询回执却说输入需要修正。如果他只对照面板数值，会觉得没有变化。需要看的是计算用到了哪几项桶计数，以及修正之前它们为何彼此不合。本文只讨论由带 le 标签的序列表示的经典直方图。原生直方图的输入形状和部分插值规则不同，不沿用这里的四桶算例。

先把累计数按桶上界排列

每个经典桶统计小于或等于某个上界的观察数。上界扩大后，原先已经数进去的观察仍包含在内，累计值可以持平但不应下降。假设同一目标的四个桶依次为三十、二十、五十、六十，那么第二个桶违反了这项关系。当前查询仍可求值：手册说明，超过允许浮点尾差的逆序会通过把下降桶提高到前一个桶的值来修复，并附加一条 info 注记。这个过程改变的是查询使用的计数，不是在采集端重写旧样本。 Prometheus 的 histogram_quantile 参考

上界（秒） 原始累计数 计算使用的累计数
0.1 30 30
0.3 20 30
0.5 50 50
+Inf 60 60

总数六十的百分之七十五是四十五。这个位置落在上界为零点五的有限桶内，前一个上界是零点三。计算使用的累计数从三十到五十增加二十，四十五在这段区间里经过十五个计数，即四分之三。对经典桶做线性插值，得到零点四五秒。这个数字只说明按修复后的桶可以估算分位数，不能确定每个请求实际用了多久。若采集数据里应有的其他标签在查询前被混合，也要回到原始桶看所属对象。

用同样的数值做一个反例

给另一组输入直接提供三十、三十、五十、六十。它没有明显逆序，计算仍然得到同一个分位数。下面是完整的拟议 promtool 测试，分别为异常组和原本单调组断言输出。两组每条序列仅提供一个样本，不经过 rate 或聚合，以隔离这一处数值机制。测试未运行。保存为 repair.yml 后可在适用的 Prometheus 工具环境执行 promtool test rules repair.yml。

rule_files: []
evaluation_interval: 1m
tests:
  - interval: 1m
    input_series:
      - series: 'bad_bucket{le="0.1"}'
        values: '30'
      - series: 'bad_bucket{le="0.3"}'
        values: '20'
      - series: 'bad_bucket{le="0.5"}'
        values: '50'
      - series: 'bad_bucket{le="+Inf"}'
        values: '60'
      - series: 'ok_bucket{le="0.1"}'
        values: '30'
      - series: 'ok_bucket{le="0.3"}'
        values: '30'
      - series: 'ok_bucket{le="0.5"}'
        values: '50'
      - series: 'ok_bucket{le="+Inf"}'
        values: '60'
    promql_expr_test:
      - expr: 'histogram_quantile(0.75, bad_bucket)'
        eval_time: 0m
        exp_samples:
          - labels: '{}'
            value: 0.45
      - expr: 'histogram_quantile(0.75, ok_bucket)'
        eval_time: 0m
        exp_samples:
          - labels: '{}'
            value: 0.45

两条值断言即使都通过，也不能说明两条输入一样健康。需要验收注记时，用包含同一时点样本的隔离查询环境，分别把两条表达式提交给 Prometheus HTTP API。保存整个响应，再查看顶层 infos 与实际返回值。异常组预期出现计数修复相关的消息，对照组不应出现这条消息。该 API 检查也未执行。API 可以同时返回数据与说明，后者不必让请求失败；使用面板或客户端时，要确认它是否把注记展示出来。 Prometheus HTTP API 响应格式

找回被修正之前的桶

定位时保留查询求值时间和完整标签，从聚合后的向量往回看。先找出哪个相邻桶下降，再检查产生它们的两个来源是否是同一批观察，单位与维度是否一致。若查询组合了不同目标或不同时间范围，可以单独导出每个目标的桶再对照，避免误把一个目标的计数补到另一个目标。文档给出的修复提示说明有值得调查的输入异常，并未承诺某一种原因。修复结果仍可服务临时浏览，若要用于发布验收或长期容量判断，应先确认原始计数和查询路径的质量。

排查时还可把相邻两桶的查询写成互相独立的检查。假如较窄桶按服务和实例分组，较宽桶却只按服务分组，肉眼看到的两条曲线可能根本不对应同一组输入。把两条样本的完整标签和求值时间放在一起，能先发现这种比较错位。若聚合前每个目标的原始桶都满足累计关系，接下来应查看查询是否给不同桶使用了相同的目标选择条件。两条时间序列上的数值都来自计数器，也不能代替这一核对。

对于需要长期保存的监控证据，可以给控制组和异常组各留一份查询回执。控制组用于确认同样的查询表达式与响应解析在合理输入下可工作；异常组用于确认观察者能看到该特定注记。若回执中缺少 infos，先核对服务器和客户端版本，再查是否在代理或显示层丢了这个字段。这个验收计划不假定面板一定渲染 API 的所有信息。

还要区别结果精度与报告范围。旧文为什么不能把各实例的分位数求平均讨论如何获得正确的组合分布；这里先假定需要的桶来自同一输入组，再检查该组的累计关系。验收不能因为组内结果看起来平稳，就跳过对这组输入的核对。记录时把数值、修复注记和相邻原始计数放在一起。否则同事重跑时即使得到完全相同的分位数，也无法说明那次修复是否还发生。

两个桶只有极小的下降，也会出现同一条修复提示吗？

手册先忽略小到可归因于浮点精度的相邻差异，门槛是两个计数之和的一万亿分之一。比如相邻计数近似三十，下降若远小于六乘十的负十一次方，就落在这一小差异尺度内。只有调整后仍存在逆序，才走向前一桶计数抬高的处理并附上本文讨论的注记。主例下降十，远不接近该门槛。该微差变体未运行，验证时应分别确认输入差异、结果值和这条注记，而不是把没有注记理解成未发生任何浮点处理。
