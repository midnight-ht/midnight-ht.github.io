同一条 Make 规则，为什么没能按目标选依赖？

用 GNU Make 的二次展开给共用规则中的两个目标接上不同输入，再核对单项重建。

正文

核心要点

  • 依赖第一次展开时还不能按自动目标变量取值。
  • 转义引用可等到二次展开再决定依赖。
  • 修改一份输入能检验依赖是否接到正确目标。

依赖列表第一次展开时，GNU Make 的目标自动变量还不可用。要让一条规则按目标选依赖，需要把这一段引用留给二次展开。

构建脚本里有两个生成目标。它们的配方完全相同，都是把输入复制到输出，但两个目标的输入文件不一样。维护者把两条规则合并，计划在依赖列表里根据目标名选择变量。配方里的目标名一直正常，合并后依赖却成了空白。要解释它，得分开看 Make 读取规则时和为某个目标检查依赖时分别知道什么。配方中的变量能用，并不能证明规则顶部在同一时点求值。

给读取阶段留一个未展开的引用

普通先决条件在读入规则时展开。当表达式依赖某个目标的自动变量时，这个阶段没有正在更新的目标。.SECONDEXPANSION 在相关规则之前声明后，先决条件还会在目标上下文中再展开一次。将美元符号转义可以让引用通过第一次展开，留到第二次读取它。GNU 手册用按目标选择对象列表的规则说明这一点。 GNU Make 的 Secondary Expansion

对下面的表达式，外面一对美元保留变量间接引用，里面的一对保留目标名引用。到了检查 main 时，目标名为 main，于是选择 main_SRC；检查 lib 时，选择 lib_SRC。同一行声明依赖，最终得到的是两个各自对应的文件。这与配方里读取第一个先决条件是连续的两步。先正确建立依赖，再让配方用它作为输入。

两个目标应当各读各的文件

把下方文件保存为独立目录里的 Makefile。配方行以 Tab 开头。在旁边建立 main.txt，内容是 main-v1，再建立 lib.txt，内容是 lib-v1。运行 make all，检查生成文件 main 与 lib 的内容分别等于自己的输入。下面是完整教学规则，实际用 GNU Make 3.81 本地运行过。

main_SRC := main.txt
lib_SRC := lib.txt

.SECONDEXPANSION:
all: main lib
main lib: $$($$@_SRC)
    cp "$<" "$@"

第一次运行实际执行两次复制。随后等文件时间能够区分先后，只把 lib.txt 改成 lib-v2，再运行相同目标。归档输出只出现对 lib 的复制，结果文件 lib 变为 lib-v2，main 仍保留 main-v1。这三项观察分别约束了执行次数、受影响的目标和应保留的结果。如果只查 lib 最终内容，两个目标都被错误重建的实现也可能通过。若只查命令行数，又可能放过单独重建了错误目标的情况。

再将依赖行改成单美元形式，写成 main lib: $($@_SRC) 后另存为 broken.mk，用 make -f broken.mk all 观察结果。负例也可以先把两个旧输出移出实验目录，这样两轮共享同一份输入而不共享上一次的时间戳。保留同样的输入并从没有输出文件的目录运行。第一次展开找不到目标名，依赖变成空，配方拿到的第一个输入也是空。实际执行显示复制尝试读取空文件名，Make 退出二。负例保留了所有输入，因此失败不是文件真的没准备，而是规则没有把它连到目标上。若在已有输出文件的目录直接运行负例，目标可能被判断为无需更新，导致失败暂时藏起来。

先验收依赖，再决定要不要合并规则

如果两个目标各只有一个显而易见的输入，单独把依赖写清更容易审查。共用表达式的价值在于许多目标都有按命名约定管理的输入集。采用它时，应给未声明输入的目标留一条明确的失败路径。样本的复制遇到空输入会失败；实际配方如果允许空列表，可能会静默产出一个看似正常但不完整的文件。团队需要先决定哪类目标可以没有输入，再据此写断言。

排查增量故障时，把“不知道该读哪个输入”和“知道输入却没有重建”作为两种现象。前者需要检查二次展开得到的名字和变量定义，后者需要核对时间关系以及规则把输入归为哪一类。若文件只要求在配方前创建，不希望它的时间戳改变触发重建，可以另外看目录先决条件的两种关系。它改变的是依赖边的用途，本例改变的是边连到了哪个文件。

配置迁移还可以用一份不成对的输入做检查。例如保留 main 的源文件，故意不创建 lib 对应的文件。在这个控制里，Make 应当报缺少 lib 的前置输入，不能先复制 main.txt 代替。该用例没有执行，只用于说明命名错误应该怎样暴露。更复杂的目标清单若来自其他生成步骤，应记录 Make 读取它时已经可见的定义，避免把一个缺失变量误判成转义有问题。修正后重新跑干净构建与单文件变更，留存两个输出各自的内容。

给同事留下复验材料时，可以先列出每个目标应读取的文件，随后核对日志和结果。不要反过来用实际展开出来的名字生成预期。两份输入即使碰巧内容一致，也应在测试里用不同标记，防止读错文件仍得到同样结果。只改一份输入是第二层检查，可揭露同时挂上两份依赖造成的无关重建。它也提醒读者这只是当前 Makefile 的增量证据，不代表项目所有生成步骤都采用同样依赖约定。

显式规则的二次展开能用自动变量取得 stem 吗？

GNU Make 手册在显式规则的二次展开中规定，$$* 和 $$? 会展开为空。本例的目标名用 $$@ 就够了。若实际需要从固定名字提取一部分，可用目标名作显式变换，并为不符合命名约定的目标写一个对照。不要把配方能读到的自动变量清单原样带进这一段。这里的结论限于显式规则，不能直接套用到隐式规则。
