两个 pytest 文件同名，为什么默认收集会冲突？

用两个非包目录中的同名测试比较 pytest 的默认导入和 importlib 模式。

正文

核心要点

  • 不同文件路径可能解析为相同测试模块名。
  • 核对两条实际执行的节点，不能只看退出值。
  • 普通测试帮助模块和 fixture 的加载机制不同。

两个非包目录各有 test_rules.py。文件路径不同，pytest 默认导入时仍可能占用同一个模块名。先确认报错指向的已导入文件，再决定整理测试包还是切换导入模式。

测试组按业务范围组织文件，两个组分别写了验证规则的用例。每个目录单独跑都正常，合在同一轮却有一个文件导入冲突。这个错例很像代码中存在重复函数名，真正的重名发生在模块身份上。需要检查的是，框架通过什么名称加载文件、之前是否已经用该名字加载了另一个文件。看到两个磁盘路径，不能直接推断 Python 一定给它们两个模块名。

为什么错误中有两条路径

pytest 的默认 prepend 模式可以把测试目录加入导入路径。没有按包组织的测试目录中，测试文件需要唯一模块名，因为模块加载后会进入 Python 的模块表。两个平级目录各有同名文件时，另一个模块的路径可能出现在错误中。该错误发生在收集，不应把它计为一个已经运行失败的业务断言。 pytest 导入机制

importlib 模式不由 pytest 修改 sys.path，并可为需要直接加载的测试文件生成不同名称。它也改变了普通导入的假设。若原测试通过被临时加入的目录导入相邻模块，切换之后要核对辅助代码是否仍在正常导入路径上。单纯确认收集不再冲突，只完成了迁移中的一项检查。

保持目录不变，只换导入方式

下面是两份完整测试文件。建一个一次性目录，并在根目录放一份仅有 [pytest] 的 pytest.ini。分别在 alpha 和 beta 下按路径保存测试，两个目录都不要添加 __init__.py。从根目录运行，关闭外部插件自动装载与环境附加参数，以免现有项目的配置进入实验。两个测试的名字和断言故意不同，便于确认各自确实进入执行。

# alpha/test_rules.py
def test_alpha():
    assert sum([1, 1]) == 2

# beta/test_rules.py
def test_beta():
    assert sum([2, 2]) == 4

分别运行 python -m pytest -v --import-mode=prepend 和 python -m pytest -v --import-mode=importlib。归档驱动用同一环境实际执行这两种模式。Python 为 3.11.15，pytest 为 9.0.2。第一条在收集时给出 import file mismatch，退出二；第二条退出零，两个文件中的节点分别通过。这组对照固定了文件，只有导入模式变化。完整输出保留在运行回执中。

仅看第二次有绿色退出还不够。如果两个目录中的一处因筛选没有进入收集，剩下一个文件依然可能通过。验收应查到 alpha 和 beta 的两条完整节点名，并且每条都有实际通过记录。另一条可做的控制是把其中一个文件改成有意失败，确认日志确实能定位到对应目录。该控制未运行。它能揭露只统计成功项目总数、却对节点身份没有承诺的汇总方式。保存这些对照时，应保留实际命令和工作目录；换了入口之后，Python 自己对导入路径的处理也可能改变，不能把所有差别归给 pytest 的模式。

还应留住默认模式的收集错误。错误里包含先导入的模块位置和正在尝试收集的位置，两份路径直接说明了冲突。不要在未看错误前清理缓存并宣布问题消失；在这份实验里，两个文件由独立临时目录新建，原来的字节码缓存并非必要前提。如果真实报错还有其他提示，应检查实际导入的模块文件和项目的包布局。仅凭一次删除缓存后不再复现，无法说明最初的重名条件已经处理。

选择让测试进入哪一种模块布局

若目录天然对应两个不同的 Python 包，可以明确建立包结构，或先给两个测试文件独立名称。这会保留原来的导入方式，便于现有项目已有的相对导入和工具约定继续工作。若团队更需要保持非包测试目录、同时让 pytest 不修改导入路径，可以采用 importlib 模式。切换前先列出测试中直接导入的辅助函数，把共享部分放到实际可导入的项目包中，再用同一入口从隔离环境运行。项目没有安装或路径没有配置时，仍需先解决正常的 Python 导入；测试模式不会自动把共享代码变成包。

被测应用的来源也应单独验收。一次迁移可能让两个测试模块都成功加载，但应用代码却从已安装的旧副本导入。若团队要证明这次改动的实现确实被测试，可在隔离环境中使用明确的安装入口，并记录该包实际解析到的文件或版本。它与 alpha 和 beta 都有执行记录是两条不同的结论。只搜一段用例成功输出，既不能检查包来自哪里，也不能说明某个共享辅助模块仍然从预期路径加载。

也可先跑一份只有两条测试的验收，再回到整个项目。大项目的测试发现可能还受配置、文件名模式或插件影响。应分别保留收集输出与真正执行的节点，避免因为某个路径从未进入测试而误判重名已经修复。对于缓存选中哪些已知失败的另一种漏项，可接着看上次失败项复跑没有覆盖新测试。那里测试已能收集，差别来自本轮选择。

conftest.py 中的 fixture 也要按普通模块导入吗？

不需要。pytest 文档把直接导入的测试辅助模块与自动发现的 fixture 区分开。假如 alpha 的两个用例共享一个临时样本，可以把 fixture 写到它们所属目录的 conftest.py，在函数参数里请求它，再验证返回标记。不要在测试中把 conftest 当普通辅助模块导入。这个扩展没有运行，主例只验证了两个测试模块的收集和执行。若 fixture 需要跨目录共享，还应检查它的声明位置是否覆盖那些用例。
