SQLite 表里有生成列，为什么 schema diff 看不见？

用一张实际运行的 SQLite 临时表区分生成值、普通列清单与包含生成列的结构清单。

正文

核心要点

  • table_info 不返回生成列。
  • 完整清单能保留列名及 hidden 标记。
  • 列清单与写入字段合同需要分别检查。

SQLite 的普通查询能读到生成列，PRAGMA table_info 却会从列清单里省掉它。检查迁移后的实际结构时，要用 table_xinfo 看包含生成列的清单，再根据工具用途解释 hidden 字段。

假设库存表新增一个派生数量。迁移完成以后，页面显示的新值符合表达式，部署脚本却报缺列。脚本通过 table_info 构造了它认定的完整清单，再与迁移目标逐项比对。先不要根据这份报错重跑迁移。用同一连接查询派生值，再用正确的列清单验证表结构。两条观察分别证明数据读取和元数据枚举，哪一项失败都需要保留自己的原始证据。

清单返回的是什么

SQLite 的 PRAGMA 文档说明，table_info 省略生成列和虚拟表的隐藏列。table_xinfo 返回这些附加项，并增加 hidden 字段。对普通列，该值为零；生成列使用二或三；虚拟表隐藏字段用一。本篇的样本只测试普通临时表，包含一个虚拟生成列和一个存储生成列。虚拟生成列仍然属于此表定义，别把名称中的“虚拟”直接当成虚拟表隐藏列。SQLite PRAGMA 参考。

生成列从 SQLite 三点三一版起可用。虚拟和存储两种列在计算时机上不同，但这不是 table_info 能否列出它们的条件。要判断工具到底拿到了哪些字段，保存清单名和实际引擎版本。仅列出列数也不够。例如新增两个派生列后，旧清单的数目可能完全不变；完整清单同样不能只比数目，名字错了也可能碰巧相同。SQLite Generated Columns。

用同一张表做三次观察

以下临时表 SQL 已通过 Python 3.11.15 的 sqlite3 模块在 SQLite 3.53.1 内存数据库执行。归档断言覆盖查询值、普通清单列名和完整清单的列名与 hidden 配对。它没有运行迁移器、应用驱动或构建过程。

CREATE TEMP TABLE stock (
    id INTEGER PRIMARY KEY,
    qty INTEGER NOT NULL,
    doubled INTEGER AS (qty * 2) VIRTUAL,
    tripled INTEGER AS (qty * 3) STORED
);
INSERT INTO stock (id, qty) VALUES (9, 4);

SELECT id, qty, doubled, tripled FROM stock;
PRAGMA temp.table_info(stock);
PRAGMA temp.table_xinfo(stock);

预期查询得到编号九、输入四、派生值八和十二。table_info 只给 id 与 qty。table_xinfo 同时给 id、qty、doubled、tripled。在本次执行环境里，它们的 hidden 数值依次为零、零、二、三。代码逐项检查名字和标记；后两列的名字和值也各自有独立依据。若测试只发现有两个生成项，虚拟列和存储列对调仍可能漏过。这里比较的是明确声明的两列，没把标记读成业务字段是否公开或是否可修改的统一权限。

这条查询也能用来定位迁移工具的连接问题。临时表只属于当前样本的测试连接。如果实际项目从另一条连接读结构，还要检查查的是哪个库、哪张表，以及连接创建时加载了什么文件。不要因为某个 SQL 控制台读得到列，就认为另一个进程看到了同一个结构。应保存实际连接路径、查询的 schema 和列清单。这里使用 temp，避免和持久库里同名表混淆；本程序没有测试多连接配置。

让差异报告保留字段角色

结构检查工具可以在读取完整清单后生成一份报告，把名称、声明类型和生成角色分开核对。比如库存脚本实际要求 doubled 是读时计算，而 tripled 是存储计算，应分别核对这两个声明的角色，不只检查名称存在。若又新增一个真实业务列，再用同一份报告确认它被归到普通列。对临时验证而言，结果值八和十二只能证明表达式对这一条输入成立；另一组输入或应用写入路径仍需自己的验收。

工具如果从清单生成映射，还需要清楚哪一份输出供读取，哪一份输出供写入。读模型可以暴露派生结果，写模型则依照数据库和业务的约定设置允许的字段。某些普通列也可能由数据库生成默认值、受业务权限控制，或只允许创建时填写。完整清单提供了判断材料，却不会替工具完成写入授权。站内的 PostgreSQL 生成列计算时点 解释另一套引擎的建表政策，本例定位的是 SQLite 元数据清单的范围。

在发布验证中，还可以把旧检查与新检查对同一份结构分别运行。旧检查报告派生列缺失，新检查列出四个名字。如果两份报告都找不到派生列，再检查建表是否实际执行、运行引擎是否支持语法，以及检查程序的库文件是否正确。这样能保留两种独立的失败路径，避免把真正没有迁移的环境误认为只是清单不完整。这个部署对照没有执行。

如果旧工具的另一部分还依赖列位置，也应单独留一份兼容检查。假设导出先用元数据生成表头，再通过显式查询读取四列。用旧清单生成两个标题会让后两项失去对应字段。测试应保留查询的实际列顺序与表头映射，并准备一次交换两个派生列顺序的输入，确认工具能按自己约定的位置或名称明确处理。仅检查两个结果的长度相等，仍可能把八标到 tripled 名下。这个测试没有运行，也没有要求应用永远采用数据库列顺序；实际约束取决于导出格式与消费方如何识别列。

能把完整列清单直接变成 INSERT 字段吗？

生成列的值由表达式决定，不能像普通列一样直接写入。给一个新临时表样本准备两条独立插入，一条显式给 doubled 赋值，预期数据库拒绝；另一条只给 id 与 qty 赋值，预期派生列仍按表达式可读。先以数据库的生成列规则排除直接写入，再按业务允许的列进一步选择字段。这个追问未运行；归档的主例只运行了基础字段插入及三个读取观察。
