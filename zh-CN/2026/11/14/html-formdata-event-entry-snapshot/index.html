没有提交表单，为什么 new FormData 也触发 formdata？

用表单预览区分条目构造、同步监听、控件值与实际提交。

正文

核心要点

  • 从表单构造 FormData 会走条目构造流程。
  • 同步监听可修改本次条目。
  • 预览事件本身不提供提交回执。

用户只点了“预览表单条目”，没有提交，formdata 监听器却执行了。调用 new FormData 并传入表单时，浏览器也会构造条目并在过程中触发这个事件。同步修改监听器拿到的条目对象，可以改变这次构造的结果。记录发生过这个事件，仍不足以证明请求已发送或业务已经保存。

表单控件与当前条目各有用途

HTML 对构造表单条目的定义先从适用控件建立列表，再创建关联的 FormData 对象交给事件监听器，最后返回条目的副本。XHR 标准的构造器在收到表单参数时使用这套流程。示例只处理普通文本输入与一条来源标记，不涉及文件序列化或网络传输。触发事件的依据是条目构造，而不是用户完成了某个提交动作。

比如编辑指南时需要先检查服务器将收到哪些字段。界面提供一个预览按钮，点击后读取现有控件，同时补一个只用于这份数据的来源值。这个值不必成为新表单控件。若只修改输入框的可见内容，也不应期待它回写到已经收集的条目。监听器需要明确处理的是当前控件、当前条目还是后续请求。三者可以来自同一次操作，改变的位置却不相同。

还要避免让监听器承担提交计数。预览、真正提交和测试代码都可能构造一次新列表。一份用户操作可能先查看条目，又点保存，事件发生两次完全合理。如果此时应用用监听次数计入已成功提交，预览就会制造一个不存在的成功。可以记录构造次数以便排查，但业务回执应来自实际发送与接收结果。

让预览本身成为可复核的对照

以下完整 HTML 尚未在浏览器执行。单个表单有初始标题 Guide 和一个普通预览按钮。代码在构造前写入 before，监听器添加 source 并记录 listener，构造返回后写入 after。日志还读取真实输入框的值。两次点击各自形成一次新构造，不继承第一次事件所持有的对象。

<!doctype html>
<html lang="en">
<meta charset="utf-8">
<title>Form entry preview</title>
<form id="editor">
  <label>Title <input name="title" value="Guide" required></label>
  <button id="preview" type="button">Preview entries</button>
</form>
<pre id="log"></pre>
<script>
const byId = id => document.getElementById(id);
const [form, button, log] = ['editor', 'preview', 'log'].map(byId);
const input = form.elements.namedItem('title');
let record;
form.addEventListener('formdata', ({ formData }) => {
  record.push('listener');
  formData.set('source', 'preview');
});
button.onclick = () => {
  record = ['before'];
  const entries = Array.from(new FormData(form));
  record.push('after');
  log.append(JSON.stringify({ record, entries, title: input.value }) + '\n');
};
</script>
</html>

预期每次日志顺序都是 before、listener、after。返回列表先保留 title 等于 Guide，再出现 source 等于 preview。输入框仍是 Guide，页面上也没有新增来源控件。这个预期可从固定初始值和同步语句推导，不能用“看到事件处理器被调用”来代替确认返回的数据。样本只绑了一个普通按钮，不会发送请求。真正集成时，若监听器对所有来源构造都写 preview，应再检查这个名称是否也会错误写到真实提交数据。

负例可以把同步处理改成只更新输入框内容，例如改成 Changed，但不去修改事件提供的数据对象。第一次构造已经收集了旧标题，返回值仍应保留 Guide，只有控件改变。下一次构造才有机会收集 Changed。这个对照能验证修改是否发生在正确对象上。还可在预览前清空必填项，检查构造仍能反映当前值；业务若希望预览之前先校验，应另定义什么时候触发原生反馈。生成一份数据对象不能替接收端判定值是否有效。

监听器应该处理哪一份来源

如果项目有多种构造用途，可以在调用位置明确区分预览、保存草稿和最终发送。可共享纯函数计算附加字段，再按实际用途应用到本次对象。真正提交时还要保留按钮意图，并按表单合同决定何时验证或发送。站内脚本提交与按钮意图讨论 submit 事件和约束校验，本篇关注列表已经建立以后，什么时候仍可修改其条目。

测试时把“页面标题”“构造返回标题”“收到的请求标题”和“业务保存后的标题”分别写在期望表里。只在本地看见同一字符串，无法验证服务器保存了它；发送测试如果只看界面，可能漏掉条目被监听器覆盖。对同名字段较多的表单还应明确新增键是替换还是追加，避免一个适配器无意抹掉另一个需要保留的值。样本的来源字段在初始列表不存在，目的只是隔离构造时机。

若预览后有一条真实保存操作，可以在日志中给它分配独立的业务请求编号，并把服务器返回的状态与该编号对应。没有编号和响应的预览记录仍只计作构造。重试可能产生多个发送尝试，也应按业务合同定义哪次结果可作为回执，不把事件次数直接当成尝试次数。

也可以做一个重复预览的回归测试。预期第一次和第二次都只各有一个来源条目，并检查第二次结果来自当时输入。测试不要从页面上旧的日志文字读取后再组成本次预期。保存两份独立快照，再修改一份，核对另一份没有被混用。若项目用预览结果发请求，调用层应说明用户后续编辑以后，是采用已冻结值，还是重新构造当前表单数据。选择哪种取决于用户确认过的是哪份内容。

监听器先 await，再添加条目，构造会等它吗？

不会等待。把主例的同步添加改成先等待一份由测试掌控的未完成 Promise，等构造函数返回后才放行。事件分发不会等待异步监听器的返回值，HTML 算法在同步事件步骤后就复制条目。因此返回对象中不应出现这次稍后才加入的值，即使监听器保留的旧对象之后发生变化。可分别检查构造返回时、放行后旧对象和放行后返回对象三处。需要异步取得的字段应先取得，再在明确的发送路径上写入最终对象。
