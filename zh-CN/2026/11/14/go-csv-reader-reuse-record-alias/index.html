Go CSV 逐行正确，攒成批却为什么两行一样？

用两条固定记录区分 Go CSV 即时读取和复用切片的保留风险。

正文

核心要点

  • 启用复用后，行切片可能共享底层数组。
  • 保留整行可在下一次读取前复制，或关闭复用。
  • 即时读出的字段和延迟消费的整行要分别验收。

Go 的 CSV Reader 启用 ReuseRecord 后，下一次 Read 可能复用前一次返回的切片底层数组。逐条读取时看到的数据可以全都正确，后来再看攒起来的批次却已经改变。需要保留记录时，要关闭复用，或在下一次读之前复制这一行。

假设导入器每读到一行就打印商品编号，随后把整行加入待写批次。输入里先是 a，再是 b，日志里的两个编号都对，批次输出却可能把两条都显示成 b。先核对加入批次的值究竟保存了字段，还是保存了可被下一次读取覆盖的切片。调整日志位置只会改变能看见哪个时点，无法为已经保存的切片取得独立底层数组。

给即时读取和保留批次各一个观察点

标准库文档说，ReuseRecord 默认关闭，每次 Read 返回调用方拥有的新分配内存。启用选项以后，Read 可以返回与上次切片共享底层数组的切片。对调用者来说，关键在于接口允许底层存储复用。具体哪一次复用、是否因为列数改变而重新分配，不应该成为测试写入逻辑的前提。Go encoding/csv 参考。

下面是未执行的完整教学程序。输入为两条各含两个字段的记录。程序读取时先保存当前行首列字符串，再根据配置把行切片原样加入批次，或者先复制它。三组每次都新建 Reader，避免用前一次已经读到文件末尾的状态检验下一次。

package main

import (
    "encoding/csv"
    "fmt"
    "io"
    "reflect"
    "strings"
)

func collect(reuse, snapshot bool) ([][]string, []string) {
    parser := csv.NewReader(strings.NewReader("a,1\nb,2\n"))
    parser.ReuseRecord = reuse
    var batch [][]string
    var ids []string

    for {
        row, err := parser.Read()
        if err == io.EOF {
            return batch, ids
        }
        if err != nil {
            panic(err)
        }
        ids = append(ids, row[0])
        if snapshot {
            row = append([]string(nil), row...)
        }
        batch = append(batch, row)
    }
}

func main() {
    expected := [][]string{{"a", "1"}, {"b", "2"}}
    for _, config := range [][2]bool{{false, false}, {true, true}, {true, false}} {
        batch, ids := collect(config[0], config[1])
        if !reflect.DeepEqual(ids, []string{"a", "b"}) {
            panic("immediate IDs changed")
        }
        if (!config[0] || config[1]) && !reflect.DeepEqual(batch, expected) {
            panic("retained rows changed on an owning path")
        }
        fmt.Printf("%v: %q\n", config, batch)
    }
}

即时保存的编号预期始终是 a、b。关闭复用或启用复制的两条路径，还要求最终批次分别含有 a 与一、b 与二。这是两份独立的成功标准，程序会在任何一份未满足时终止。最后一组开启复用且直接保存切片，输出用于观察共享可能造成的结果。如果第二次读取重用第一条的底层数组，批次的两个位置都可能反映第二条。程序不强制某个版本必须呈现这个具体坏结果。它把不保证保持的路径标出来，让验收依赖安全路径的稳定输出，而不是依赖某次碰巧复用了内存。

如果要验证真实工具确实存在这个问题，可以保存故障场景的版本、实际配置和两次读取后的具体批次值。把即时观察和晚读观察记录成两个事件，分别对应相同的输入序号。仅保存一张终端截图，后续难以判断字段值是读取时已经错误，还是进入批次后才改变。若实际输入还含换行或引号，应另验 CSV 解析。站内的 CSV 跨行记录 讨论记录边界，本例两条输入都不跨行。

在交接前决定谁可以继续改这一行

如果处理器只在下一次 Read 以前同步消费当前行，可以允许复用。但函数内部是否另存切片、将它发到频道，或把它交给之后执行的任务，都要从真正的调用路径核对。只要有一个消费者可能晚些再读这行，就应给它独立值。可以在传输前复制切片，也可以禁用复用，让每次读取都拥有独立的底层空间。复制应在会覆盖它的后续读取之前完成；收到队列信号以后才复制，可能已经复制到了另一条记录。

对一个同时支持即时统计和异步写入的导入器，可以把验收拆成两份。即时统计应在读取两条记录后分别累加正确的商品。异步写入测试让写入者等到解析端读完，再检查两条记录都带原来的编号与数值。测试时不必启动真实数据库，先用可控接收器观察交接；生产驱动的写入和取消另验。本程序没有队列，无法证明多线程并发访问同一个 Reader 安全，也没有给出两种策略的性能数据。

读取出错也需要独立路径。标准库允许 Read 返回部分记录并带错误，样本遇到错误直接终止。应用若决定保留可恢复的行，应写出条件并用坏输入验证，不能用复用设置替代错误策略。把读错误、覆盖错误和写失败分成三个观察点，导入任务才不会把所有错误都描述为“CSV 内容不对”。这种错误控制在示例中未运行。

也可用不会依赖某个标准库内部选择的模拟接收器来验收交接合同。先准备一块测试切片，装入第一条记录并交给待写批次，随后明确覆盖原切片的两个位置，再让批次开始读取。正确的交接应该仍保留最初编号和数值。给错误实现准备相同流程，要求它能被这个测试拒绝。真实 Reader 的日志与这个模拟结果应分别保存，前者描述某个版本是否发生覆盖，后者验证应用是否为晚到的消费者保留了值。这个模拟对照没有运行，主例也不冒充真实导入性能数据。

只保存 record[0] 的字符串，也会被下一次覆盖吗？

按正常 Go 赋值规则，把首列赋给一个字符串变量，或把这个字符串值追加到另一份切片，得到的是当时的字符串值。后续对原行位置重新赋值，不会改掉已保存的字符串。上面的程序用 ids 检查这一点。若同时保存了原来的行切片，仍要为那个切片检查生命周期。可以把即时首列读出的 a、b 与最终两行分别断言，避免前一项通过便宣称整批稳定。这里限定标准库公开 API 的正常使用，不依赖 unsafe 或改变字符串内容的非标准手段。
