搜索建议高亮了，怎样让输入框继续接收键盘？

用可编辑建议框区分真实输入焦点、活动选项和确认动作，并检查建议列表刷新后的引用。

正文

核心要点

  • 活动建议可以变化，DOM 焦点仍留在输入框。
  • 活动引用必须指向当前弹层中的有效元素。
  • 键盘移动、过滤和确认需要单独验收。

按向下键高亮第二条搜索建议，再敲一个字母，字符仍应写进输入框。对使用列表弹层的可编辑组合框，可以让真实 DOM 焦点留在文本输入上，用 aria-activedescendant 指出正在浏览的建议。高亮、输入和确认分别有自己的操作条件。

先分别记录键盘事件和活动引用

WAI-ARIA 对 aria-activedescendant 的定义允许支持该属性的控件报告一个活动对象，同时保持容器或输入的 DOM 焦点。组合框可以通过 aria-controls 连接弹层，活动引用指向该弹层中的合法选项。属性本身不会移动焦点，也不会为应用处理方向键。开发者需要写出键盘动作怎样更新活动项，同时继续允许输入框接收原生文本操作。

设想课程选择允许输入名称并从三个候选中挑选。向下移动到 Biology 后，用户想改搜以 C 开头的课。若程序为了显示高亮直接把真实焦点送给候选，后续 C 可能不再进入输入值。相反，让 DOM 焦点留在输入，更新候选 ID，可以让用户浏览后仍直接修改。把高亮样式依赖于活动状态，不要反过来把某个看起来高亮的行当成真实焦点所在。

还应区分目前浏览的候选与已经提交的输入。方向键把一项标成活动，在这个模式中可同时标记该建议在弹层内的选择状态；示例要到 Enter 或明确点击才将名称写入输入。若项目希望移动时立即预填，应说明取消时是否恢复原值，以及下次键入是替换还是追加。这个决定与 DOM 焦点是否留在输入上可以分别验证。

一个可以用按键逐步检查的页面

下面是完整本地 HTML，尚未在浏览器或辅助技术中运行。它实现一个小型列表弹层教学样本，不包含生产级远程请求、跨设备输入法或完整手势验收。初始没有活动候选；在输入框中按两次向下键，先到 Algebra，再到 Biology。检查输入仍有真实焦点、输入值仍为空、活动引用指向当前列表中的选项。随后键入 c，预期输入接收该字符，建议过滤到 Ceramics，旧活动引用被清除。

<!doctype html>
<html lang="en">
<meta charset="utf-8">
<title>Editable course suggestions</title>
<style>
[aria-selected="true"] { background: #173959; color: white; }
</style>
<label for="course">Course</label>
<input id="course" role="combobox" aria-controls="choices"
       aria-autocomplete="list" aria-expanded="false" autocomplete="off">
<ul id="choices" role="listbox" aria-label="Courses" hidden></ul>
<script>
const get = id => document.getElementById(id);
const [input, list] = ['course', 'choices'].map(get);
const all = ['Algebra', 'Biology', 'Ceramics'];
let matches = [], active = -1;
const write = (node, name, value) => node.setAttribute(name, String(value));
const activeAttr = 'aria-activedescendant';
const cancel = event => event.preventDefault();

function show(items, index = -1) {
  matches = items;
  active = index;
  input.removeAttribute(activeAttr);
  const rows = items.map(text => {
    const option = document.createElement('li');
    option.id = 'choice-' + text.toLowerCase();
    write(option, 'role', 'option');
    write(option, 'aria-selected', 'false');
    option.textContent = text;
    return option;
  });
  list.replaceChildren(...rows);
  list.hidden = rows.length === 0;
  write(input, 'aria-expanded', !list.hidden);
  if (active >= 0) {
    const option = rows[active];
    write(option, 'aria-selected', 'true');
    write(input, activeAttr, option.id);
    option.scrollIntoView({ block: 'nearest' });
  }
}
function filtered() {
  const prefix = input.value.toLowerCase();
  return all.filter(name => name.toLowerCase().startsWith(prefix));
}
function commit(value) {
  input.value = value;
  show([]);
}
input.oninput = () => show(filtered());
input.onblur = () => show([]);
input.onkeydown = event => {
  const { key, isComposing } = event;
  if (isComposing) return;
  if (key === 'ArrowDown' || key === 'ArrowUp') {
    const items = matches.length ? matches : filtered();
    if (!items.length) return;
    const last = items.length - 1;
    const next = key === 'ArrowDown' ? Math.min(active + 1, last)
      : active < 0 ? last : Math.max(active - 1, 0);
    cancel(event);
    show(items, next);
  } else if (key === 'Enter' && active >= 0) {
    cancel(event);
    commit(matches[active]);
  } else if (key === 'Escape' && matches.length) {
    cancel(event);
    show([]);
  }
};
list.onmousedown = cancel;
list.onclick = event => {
  const option = event.target.closest('[role="option"]');
  if (option && list.contains(option)) commit(option.textContent);
};
</script>
</html>

再按一次向下键选中 Ceramics，按 Enter，输入写入完整名称，弹层关闭、活动引用删除。若还没有活动项就按 Enter，本页没有提交逻辑。Escape 可以关闭展开的弹层而不替换输入。样本让一般文字键交给原生输入，并在检测到组合输入事件时让自定义按键逻辑退出。真实产品还应检查支持平台的编辑快捷键和组合事件时序，不能把这一条判断当成输入法测试。

负例是将活动变化改成给可聚焦候选调用 focus。此时方向键后读取 document.activeElement，将得到候选而非输入。即使两种方式把同一行涂成高亮，继续输入的结果也不再相同。另一个反例是更新了视觉背景却没设置引用，DOM 焦点虽然留对了，程序状态仍无法表达当前建议。验收应逐步记录焦点、属性目标、可见行、输入文字以及最终确认结果。

保持引用和可见列表在同一个更新里

可编辑组合框经常按输入值重建结果，旧节点的 ID 不能继续代表已不存在的项。样本重建前先移除属性，生成实际列表后再依据当前活动位置设置。若真实项目按业务标识复用节点，应核对属性目标对应当前候选、属于当前弹层且确实可用。只判断文档里存在同名 ID 还不够，页面上另一个独立组件也可能误用同一个值。

还可以把原生编辑键列成单独路径。比如输入 c 后没有活动候选，先用退格删除字符，确认列表按照新文本重新计算；再按方向键浏览，而不把已经匹配的候选直接写入输入。键盘事件可能同时带修饰键，真实控件不能简单把所有组合键都当成普通方向键处理。验收应先决定左右键、文字选择与移动到行首等动作继续交给谁，再核对浏览模式中的退场规则。示例刻意只实现少量按键，既没有模拟系统编辑快捷键，也没有覆盖触摸屏上的候选切换。

另一个要保留的状态是无匹配。若用户输入的词没有候选，可以关闭列表并清除引用，但输入仍应保留，让他继续编辑或按实际业务规则提交。没有候选不能由这个教学样本推导成名称无效。应用可决定是否允许自由文本，也可要求从列表选值。后一种情况应在界面说明，不能只依赖一条高亮候选表达限制。

在目标辅助技术中，应另行观察浏览方向键时是否感知到对应建议和输入文本。浏览器的焦点值能证明键盘任务进入哪个 DOM 对象，不能独自说明屏幕阅读器如何通告。可依据 APG 组合框键盘指导选择实际模式。站内导航当前位置和标签页选择曾对比真实移动焦点与手动激活，本篇采用的仍是在输入上保持真实焦点的不同模式。

服务器刷新建议，活动项已被移除，还能保留旧引用吗？

不能继续让它指向已经不存在的选项。主例由用户键入来清空活动项，这里换成后台结果主动替换。假设当前活动是 Biology，服务器稍后只返回 Ceramics。更新时应清除失效引用，或者按产品明确的规则选择一个实际存在的后继项。验收时保留输入焦点，核对新列表与当前引用，再按 Enter 验证不可能提交已被移除的 Biology。若响应来自旧查询，还应先核对它是否有资格替换当前列表，这属于请求归属判断。
