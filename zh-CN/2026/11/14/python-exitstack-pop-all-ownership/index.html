退出 with 以后，ExitStack 的资源为什么还开着？

用实际运行的部分失败与成功交接，核对 ExitStack.pop_all 的回调转移和关闭顺序。

正文

核心要点

  • pop_all 转移退出回调。
  • 部分获取失败仍由原栈清理。
  • 交接后由新栈负责退出。

调用 ExitStack.pop_all 后，已经登记的退出回调会转到一个新栈。离开原来的 with 时，原栈已经没有这些清理工作。要让资源继续供调用者使用，就把新栈和资源一起交付，并明确由谁关闭。

假设一个导出器需要两个输入句柄。第二个获取步骤可能失败，失败时必须关闭已经打开的第一个。两个都拿到以后，导出器希望把它们交给调用方继续使用。如果只在函数里开一个普通 with 并直接返回句柄，函数离开作用域就会清理它们；如果索性不登记清理，第二个获取失败时又可能留下第一个。ExitStack 可以先负责失败回收，再在两个获取步骤都通过时移交已登记的回调。

交接发生在回调栈上

同步 ExitStack 的 enter_context 进入一个上下文管理器，并登记它的退出方法。登记者按逆序退出。pop_all 会将当前回调栈转移到新的 ExitStack，调用时没有任何退出回调运行。新的栈可以由持有者显式调用 close，或由另一个 with 管理。官方文档还说明，回调不会在栈对象被垃圾回收时隐式执行。丢掉返回值会丢失这次明确的清理入口，不能依赖对象销毁时机来完成交付。Python 3.14 contextlib。

这里被移交的是同一组退出动作。资源不需要重新获取，后加入的回调仍在先加入的前面执行。对调用方而言，获得两个句柄和接收清理责任是同一次交接中的两部分。API 如果只返回句柄，调用方就很难知道该用哪个栈收尾，失败责任也不易在调用关系上核对。

让成功交接和部分失败各走一次

下方完整程序已在本地 Python 3.11.15 执行。A 与 B 是内存里的上下文管理器，记录进入尝试和关闭，没有打开文件或连接真实服务。第二次获取是否成功是两条路径唯一的准备差异。程序先用失败控制确认已经获得的资源会清理，再用成功路径观察两个作用域。

from contextlib import ExitStack, contextmanager

events = []

@contextmanager
def acquire(name, fail=False):
    events.append("try " + name)
    if fail:
        raise ValueError(name)
    try:
        yield name
    finally:
        events.append("close " + name)

def open_pair(fail=False):
    with ExitStack() as stack:
        first = stack.enter_context(acquire("A"))
        second = stack.enter_context(acquire("B", fail))
        return (first, second), stack.pop_all()

try:
    open_pair(fail=True)
except ValueError:
    assert events == ["try A", "try B", "close A"]
else:
    raise AssertionError("expected acquisition failure")
print("partial:", events)

events.clear()
pair, owner = open_pair()
assert pair == ("A", "B")
assert events == ["try A", "try B"]
try:
    print("after transfer:", events)
finally:
    owner.close()
assert events == ["try A", "try B", "close B", "close A"]
print("after close:", events)

部分失败时，预期看到先尝试 A，再尝试 B，然后只关闭 A。B 在交付资源之前抛出，未登记退出动作。成功时，open_pair 返回后先核对两个值，还不能看到关闭事件。调用新栈的 close 后，预期先关闭 B，再关闭 A。归档输出保存了三次观察。只检查最终有没有关闭两个资源，会让“离开原栈时已经关闭”和“新持有者用完才关闭”得到相同结果。这个例子把关闭时点与次数一起验收。

样本在获取 B 的阶段抛错。它不展示某个上下文管理器在自己进入过程中又获取内部资源后如何回收。如果 B 的进入步骤先创建了内部对象再失败，B 必须处理自己的部分构造，或在取得内部对象时立即登记相应责任。外层的 enter_context 不能凭空知道 B 在抛错前做了什么。旧文的 单次 yield 资源管理 解释管理器内部何时承担退出责任；这里核对的是已经成功登记的清理如何跨作用域转移。

把交接放到最后一个需要保护的步骤后

如果导出器除了打开两个输入，还要校验它们的头部或分配一个临时缓冲区，应先完成这些步骤，再决定要不要移交。在转移以后继续做可能失败的工作，就需要保证新栈也处于明确的关闭路径。可以增加一个独立反例，让获取都成功，但让准备工作最后一步失败。预期函数没有把资源交给调用者，A 与 B 都各关闭一次。若这组失败被错误安排在 pop_all 之后，原 with 的退出不会再清理这两个资源。这项对照未执行；主程序只检查第二次获取失败。

另一项应用检查是明确调用者什么时候失去使用资格。假设两个文件在交接后要写入同一个输出，关闭新栈后应停止后续写入。可以在接收 API 的测试里用可记录关闭状态的句柄，把正常输出、使用失败和调用方异常分别验证。若模块需要报告清理自身的错误，另加一组会抛错的回调并保存实际传播路径。这里的两个内存管理器都不会在关闭时抛错，不能从它们的结果推断真实文件已写完、数据已持久化，或异常会被自动合并。

还有一种接口只在回调期间借用资源，调用者不该在回调结束后继续保留句柄。它可以把全部工作留在原来的栈里，省去移交。如果确实要把资源送到另一个工作者，应让接收动作同时携带清理入口；发送失败时，仍由当前持有者关闭。验收可以让接收方分别接受和拒绝交接。拒绝时不应遗留活动资源，接受时原作用域结束仍可使用，最后由接收方关闭一次。对这种接口，保留接受动作与关闭动作的记录比只看返回的句柄更有用。这个并发或队列交付对照没有运行，内存例子只在同一调用链中转移责任。

新栈用 close 和用 with，退出回调收到的异常一样吗？

对栈中第一个执行的普通退出回调，直接 close 启动的是没有异常的退出，初始参数表示无异常。用 with 管理新栈时，如果主体抛错，退出回调可以收到对应异常信息。后续回调拿到的状态还可能随前面的回调抑制或替换异常而变化。可在独立探针里登记一个只记录三项参数的退出方法，分别通过 close 和有异常的 with 退出，再检查是否保留了原异常。用 callback 登记的普通函数没有这组三项参数。这个追问未运行。
