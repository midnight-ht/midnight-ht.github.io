Pydantic 外层通过，为什么内层实例还有非法字段？

用三个实际运行的 Pydantic 输入，区分默认实例复用、字典校验和重新验证。

正文

核心要点

  • 默认不重验已存在的模型实例。
  • 字典和已有对象可能经过不同验证路径。
  • 重验证设置应放在负责该字段的模型。

Pydantic 默认不会重新验证已经创建的模型实例。实例如果在首次校验之后被改坏，再传进外层模型，里面的值仍可能保留下来。先辨认传入的是字典还是已存在的对象，再决定在哪个边界重新验证。

设想后台把用户资料放进一份待发通知。用户对象最初只含字符串兴趣，后来另一个处理步骤把兴趣字段改成含整数的列表。通知对象成功建立了，但外层的成功不保证这次复查了每个内层字段。把同样的值作为字典传入，反而会出现验证错误。两条调用都给外层字段传了一个用户，区别在于被复用的是已创建的模型实例，还是需要从头解析的数据。

在字段模型上检查复用政策

Pydantic 二版配置文档列出三种模式。默认 never 不重新验证模型实例和数据类实例；always 重新验证；subclass-instances 只对作为预期模型子类的实例重新验证。这里采用同步的普通模型创建，以一个具体列表字段为例。配置只影响声明它的模型，不会自动沿字段传给引用到的其他模型。Pydantic 配置参考。

实例创建完成以后的字段赋值，是另一个入口。样本故意沿用默认的赋值行为，让两种内层对象都能先被改坏。这样才能比较外层如何处理已经有问题的对象。如果直接把两种设置同时打开，非法赋值可能更早就被拒绝，随后自然没有同样的对象可供复用测试。两个验证时点各有用处，排查应保留哪个调用实际返回错误。

用三个输入区分值形状与模型配置

以下教学程序实际在 Python 3.11.15 与 Pydantic 2.13.4 运行。它不调用 API，也不反序列化网络正文。两个模型最初都用字符串列表创建，随后同样被改成列表中只有整数一。验证入口对比默认实例、同内容的字典，以及内层声明重新验证的实例。

from pydantic import BaseModel, ConfigDict, ValidationError

class User(BaseModel):
    hobbies: list[str]

class CheckedUser(BaseModel):
    model_config = ConfigDict(revalidate_instances="always")
    hobbies: list[str]

class Envelope(BaseModel):
    user: User

class CheckedEnvelope(BaseModel):
    user: CheckedUser

def rejected(factory, value):
    try:
        factory(user=value)
    except ValidationError as exc:
        assert exc.errors()[0]["loc"] == ("user", "hobbies", 0)
        return True
    return False

plain = User(hobbies=["reading"])
checked = CheckedUser(hobbies=["reading"])
plain.hobbies = [1]
checked.hobbies = [1]

observed = (
    Envelope(user=plain).user.hobbies,
    rejected(Envelope, {"hobbies": [1]}),
    rejected(CheckedEnvelope, checked),
)
assert observed == ([1], True, True), observed
print(observed)

第一条应接受已存在的默认实例，读取出的 hobbies 仍是含整数一的列表。第二条应拒绝同内容的字典。第三条也应拒绝，但这次拒绝的输入是声明了重新验证的模型实例。归档记录包含三条结果；两个错误都检查定位是 user、hobbies、零。只看是否有某个异常，无法确认错误来自嵌套字段本身，而不是示例类的其他约束。主程序使用一条固定数据，既不证明所有现有实例会被复制，也不定义真实通知的错误响应。

代码评审还要看交接路径有没有绕开验证。实际接口若从缓存取已创建实例，直接传给构造器，应该用同样的入口验收，不能只用 HTTP 请求字典做测试。可以分别准备缓存命中和缓存未命中，检查两个入口把同样的非法字段交给业务时，是否都遵守约定。这里没有读取缓存。应用若改成显式投影，也应确认投影保留待验证的字段，并给漏掉字段的回归独立预期。站内的 JSON 重复成员校验 处理原始成员进入映射前的另一处信息边界。

按修改位置决定验证放在哪

若模型在业务流程中允许直接设置新字段值，validate_assignment 可以在赋值处拒绝错误，调用方也更容易知道是哪一处写错。嵌套重验证则适合在接受现有对象的边界再次检查。两项设置可以服务不同团队的职责。若字段由另一个模块持有并可变，接收模块仍要核对自己收到的数据，不要从一次构造成功推断它之后不会改变。

例如服务允许替换整个兴趣列表，但希望每次提交时都只含字符串。验收应先尝试给字段赋一个非法列表，记录拒绝发生在哪一层。再准备从已有对象入口提交的样本，确认这一条使用的是预期内层模型。对列表原地 append 的业务入口要另外检查，因为它不是给整个字段赋一个新值。实际项目若依赖列表不被修改，可以考虑在交接时改用不可变结构或拷贝到独立数据，再按新的字段合同验证。这个选择不在主程序的执行范围内。

还有一份失败日志容易被漏记。若外层成功却保留整数，后续序列化可能把整数原样交给客户端，出错位置就离第一次修改很远。可给应用测试保留修改前字段、修改后字段、再次验证结果以及最终输出四个观察点。让一份合法资料独立通过，避免测试只证明任何模型都会被拒绝。对于错误资料，应核对错误定位和应用是否阻止提交，再检查原对象是否已经被业务代码改过。样本没有运行序列化或通知服务。

还可以给重验证入口一个恢复对照。重新创建一条兴趣只有字符串的资料，把它放进同一个使用重验证的包装模型，预期通过并保持字段值。不要因为之前同一个业务编号对应的实例失败，就在调用方把该编号永久加入拒绝名单。两次验证观察的是不同输入状态。这项正控制未执行，归档的三个结果仍只覆盖指定的改坏数据。

只给外层模型设 always，内层会跟着重验吗？

配置不会传播到被字段引用的模型。如果只在通知模型上设置 always，而 user 的类型仍是默认 User，重新使用这个已经改坏的 User 实例不会因此改变内层的复用政策。可以再建一个只有外层配置不同的包装器，给它传入和主例第一条相同的实例，核对兴趣列表仍含整数。若希望拒绝，给真正负责该字段的模型声明策略，再用同一输入验收。这个外层独立变体未运行。
