TreeWalker 忽略包装层时，为什么连子节点也不见了？

在同一棵 DOM 树中核对 TreeWalker 的 SKIP、REJECT 和后代遍历结果。

正文

核心要点

  • SKIP 略过包装层但保留后代遍历。
  • REJECT 在 TreeWalker 中阻止进入该分支。
  • NodeIterator 对同一过滤值采用不同规则。

生成文章目录时，规则不想输出包住标题的 section，却把它里面的标题也弄丢了。用 TreeWalker 向前遍历，FILTER_SKIP 可以省略包装节点并继续访问后代。FILTER_REJECT 会连同这条分支一起跳过。遇到这个问题，先分清是当前节点不应进入结果，还是它管理的整个区域都不应参与遍历。

让过滤值表达真正的排除范围

DOM 对 TreeWalker 向前遍历的定义从当前位置开始找下一个可接受节点。遇到被拒节点时，不继续向它的孩子下降。遇到略过的节点时，仍可以检查后代。对于用于分栏或分组的普通包装层，略过它能让目录只收集真正的标题。对于不应进入目录的内容区域，可以在区域根处拒绝，让里面恰好长得像标题的元素也不被收集。

设想一个预览编辑器同时展示发布正文和一份从旧稿复制来的参考块。复制块只是供作者对照，目录应只列发布正文里的标题。若规则为所有非标题节点返回 SKIP，参考块中的旧标题可能仍被收录。若改成对所有非标题节点返回 REJECT，普通分组中的正式标题又会丢失。合理的过滤函数需要先判断哪个节点代表要整体排除的区域，再决定哪些容器只是透明的包装。

这里说的是遍历可见性，而不是页面的视觉可见性。规则只根据样本的节点身份选值，CSS 隐藏或显示不会代替这些条件。真实应用如果要求排除隐藏的标题，应说明隐藏的依据是编辑状态、文档发布状态还是实际渲染，并给不同状态准备测试。不要因为对象没有被遍历返回，就推断它已经从 DOM 删除或不再能被其他查询看到。

用一棵树分开观察返回值和访问过程

以下完整 HTML 尚未在浏览器执行。根节点里有三个标题。A 放在普通包装层里，B 放在不应进入目录的参考分支里，C 是直接子节点。两个样本共用一棵静态树，只改变普通包装层的过滤结果。代码分别保存过滤器看到的节点与实际返回的标题，因此能够区分“节点被检查但没选中”和“根本没有下降到该节点”。

<!doctype html>
<html lang="en">
<meta charset="utf-8">
<title>TreeWalker branch comparison</title>
<main id="source">
  <section id="wrapper"><h2 id="a">Heading A</h2></section>
  <section id="excluded"><h2 id="b">Heading B</h2></section>
  <h2 id="c">Heading C</h2>
</main>
<pre id="output"></pre>
<script>
const root = document.querySelector('#source');
const { SHOW_ELEMENT, FILTER_ACCEPT, FILTER_SKIP, FILTER_REJECT } = NodeFilter;

function outline(wrapperDecision) {
  const visited = [], headings = [];
  const walker = document.createTreeWalker(root, SHOW_ELEMENT, node => {
    const { id, tagName } = node;
    visited.push(id);
    if (id === 'excluded') return FILTER_REJECT;
    if (id === 'wrapper') return wrapperDecision;
    return tagName === 'H2' ? FILTER_ACCEPT : FILTER_SKIP;
  });
  for (let current = walker.nextNode(); current; current = walker.nextNode()) {
    headings.push(current.id);
  }
  return { visited, headings };
}
const results = { skip: outline(FILTER_SKIP), reject: outline(FILTER_REJECT) };
document.querySelector('#output').textContent = JSON.stringify(results, null, 2);
</script>
</html>

预期略过包装层时，过滤器先见到 wrapper，再见到 A；在 excluded 处拒绝后不会访问 B，随后得到 C。返回的标题为 A、C。另一组把普通包装层也拒绝，预期过滤器仍看到 wrapper、excluded 和 C，实际结果只有 C。A 并没有从原页面消失，它只是失去了这个遍历路径。只断言页面仍存在 A，会让错误的目录测试通过。

样本只考虑元素。注释、空白文本和其他节点不参与本例，根节点用来限定范围，也不作为这组向前返回的第一项。若系统需要计算正文字符数，过滤器就不能简单照搬只看元素的设置。先确定输出想要标题节点、文本节点还是两个层次的记录，再选遮罩和条件。即使多个位置共用同一个 DOM 根，不同任务也可以建立各自的遍历器。

让目录范围可以从输入数据推导

生产里的排除条件最好绑定到明确的编辑标记。比如某一区域被编辑器标记为参考稿，就从该区域起点排除整棵子树。另一个只负责版面的容器可以略过其自身，把决定交给内部标题。这样页面增加一层布局 wrapper 时，不会在没有内容政策变化的情况下突然把文章目录缩短。回归应同时测试一层和两层包装，确认对普通后代继续访问的条件没有被误删。

可以进一步给每个标题保留稳定的章节标识，而不只检查标题文字。若 A 与参考区域内的 B 文字恰好相同，字符串列表会掩盖收错对象的问题。比较标题身份与所在区域，再核对链接确实跳到那份正文。涉及在线编辑或节点移动时，应先界定一轮目录计算使用哪个结构版本，再决定是否重新建立结果。站内NodeList 的成员更新讨论结构变化后的集合观察，本题在静态树里隔离的是过滤路径。

预览范围发生切换时，还要检查旧目录是否被整体替换。假设编辑器从发布正文改到参考稿，预期清单由新的范围重新计算。即使参考稿和正文里都有一个叫“安装”的标题，两个链接也应指向各自树中的目标。可以分别保存输入根节点的标识和每条链接的实际目的地，再检查点击后滚到哪一项。遍历过滤只决定哪些节点交给调用者，目录渲染和目标定位需要各自通过验证。

验收时还可将预期写成一份手工标注的树。每个区域注明“输出自己”“只查孩子”或“整段排除”，然后从标注独立推导标题。失败时既保留目录结果，也保留过滤器访问记录。输出少了一个标题，可以据此判断是单个标题规则不合格，还是父分支从未进入。两个原因需要在不同位置修复。

换成 NodeIterator，REJECT 还会剪掉参考区后代吗？

不会。主例用的是 TreeWalker。换成 NodeIterator 的向前遍历后，它只在过滤器返回 ACCEPT 时交出当前节点；遇到其他值仍继续按树顺序寻找下一节点。保持同一棵树和过滤函数，参考区的包装节点不返回，但 B 仍可能被访问和接受，因此结果可变成 A、B、C。若产品要求真正剪枝，应保留对应遍历方法，或显式在自己的遍历逻辑里处理排除区域。相同的过滤常量并不能替方法选择承担这个条件。
