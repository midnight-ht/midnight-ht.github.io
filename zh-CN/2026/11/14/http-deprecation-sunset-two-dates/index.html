收到 Deprecation 还能继续用 API 吗？

从仍返回 200 的旧接口读出弃用和预计停用日期，分开响应处理、迁移计划和实测可用性。

正文

核心要点

  • 弃用日期与预计停用日期分别表达不同事件。
  • 客户端仍应按实际状态和响应合同处理本次请求。
  • 缺少停用时间时保留未知。

旧接口返回 200，正文还是能用，响应里却有 Deprecation 和 Sunset 两个日期。客户端可以照常处理本次成功结果，同时记录资源已经弃用或将在何时弃用。预计 URI 变得不可用的时间由 Sunset 表达。两条日期各自影响迁移安排，当前响应仍按自己的状态和内容处理。

两条日期分别回答什么问题

RFC 9745 的 Deprecation 字段用结构化字段的 Date 值指明资源弃用时间。对于样本中的正整数写法，开头的 @ 后面是 Unix 时间的秒数。日期既可以在过去，也可以在未来。过去的日期表示弃用已经生效；未来日期则给出计划中的生效点。它不会把正常的对象查询变成错误响应，资源也不会仅因带这个头就需要改用另一套读取方式。

Sunset 字段的定义使用 HTTP 日期，表示该 URI 预计可能在指定时刻变得无响应。这是预期可用性的信号，不能提前保证源站会选择哪一种状态码。日期过后资源可能返回错误，也可能因为计划变更继续可用。客户端若要报告“已确认停止服务”，应基于真实请求与项目对退役的确认，而不是单凭日历变化推断。

以一个读取入门指南的旧地址为例，团队希望客户端逐步迁移，但现有用户仍要正常读取指南。旧地址返回正文，并把弃用起点与预计停止时间一起告知。产品可以把告知放进运维面板，帮助维护者安排替换版本，同时继续在用户界面显示本次已拿到的指南。若把告知当作请求失败，用户会丢掉手上已经有效的数据，监控也会把维护计划计为业务故障。

用固定 UTC 输入验收客户端

下面是一份完整的本地 Node 样本，直接把状态、正文和两个字段交给解析函数。它只处理教学输入中的正十位时间戳，并使用运行时日期解析读取这份 HTTP 日期，不能作为通用头部解析器使用。预期在例子之外可先确定：两个 UTC 日期分别是一月一日零点，年份为二〇二五和二〇二六；正文标识是 guide-9。代码不访问网络，也不检查某个真实服务在日期前后如何回应。

import { deepEqual, equal } from 'node:assert/strict';

const sample = {
  status: 200,
  body: { id: 'guide-9' },
  deprecation: '@1735689600',
  sunset: 'Thu, 01 Jan 2026 00:00:00 GMT',
};

function inspect(reply) {
  // Deliberately accepts only this fixture's positive date shape.
  const match = /^@(\d{10})$/.exec(reply.deprecation);
  if (!match) throw new Error('unexpected fixture date');
  const sunsetTime = reply.sunset === undefined ? null : Date.parse(reply.sunset);
  if (sunsetTime !== null && !Number.isFinite(sunsetTime)) {
    throw new Error('invalid fixture sunset');
  }
  return {
    id: reply.status === 200 ? reply.body.id : null,
    deprecatedAt: new Date(Number(match[1]) * 1000).toISOString(),
    expectedUnavailableAt: sunsetTime === null ? null : new Date(sunsetTime).toISOString(),
  };
}
deepEqual(inspect(sample), {
  id: 'guide-9',
  deprecatedAt: '2025-01-01T00:00:00.000Z',
  expectedUnavailableAt: '2026-01-01T00:00:00.000Z',
});
const { sunset, ...withoutSunset } = sample;
equal(inspect(withoutSunset).expectedUnavailableAt, null);
console.log(JSON.stringify(inspect(sample)));

例子保留三份数据：当前响应提供的指南标识、弃用日期和预计不可用日期。前两条时间只处理计划，不从进程当前时钟生成接口状态。负例去掉 Sunset，仍应拿到指南，而预计停用时间保持未知。若解析器把弃用日期填到停用字段里，会制造未经服务端表达的时间承诺。若解析器见到弃用头就抛出“不可用”，则会使返回的有效正文无法到达调用者。两种错误需要用不同断言发现。

真实 SDK 还应检查字段解析失败时要怎样呈现。假设正文符合既有读取合同，附加日期却不能解析，团队可保留成功内容并另报头部格式问题。具体策略取决于这些字段是否参与产品约定的迁移控制。验收时应给正常日期、缺少预计停用日期、日期字段异常和真正失败响应各准备一条输入，分别记录业务结果与迁移信号。响应日志也应保留字段来自哪个目标地址，方便核对多个版本的服务没有混用时间。

迁移计划应能对应到受影响的资源

维护者看到两条时间后，还要知道哪一个入口受影响、替代入口是什么、依赖者是否能迁移。假设旧端点和新端点同时提供指南，但它们的语言参数不同。复制旧路径到新主机并不能证明调用兼容。可以选取一组具体调用分别检查参数、输出和错误行为，然后记录生产流量切换进度。本文没有访问这类服务，也没有发现任何具体的退役日期；代码中的值只是固定输入。

验收时可以给同一服务准备旧入口甲和乙，只有甲返回样本中的两条日期。分别从客户端读取两个地址，检查迁移记录是否只关联甲，同时确认乙的正常调用没有被同一个主机级别提示覆盖。如果服务明示某个公告还覆盖其他资源，先核对公告列出的实际范围，再扩大提示。这样既能发现客户端缓存了一份全局停用时间，也能核对发布日期变动后是否仍沿用旧记录。日志内容应只保留识别迁移所需的字段。

如果旧接口有多个调用入口，可以让公告、返回字段和客户端日志都带上可核对的资源身份。否则一个团队看到自身接口附带日期，另一个团队可能误以为同一主机上的全部资源都要停用。还要计划日期调整时怎样确认新版本信息。站内404 与 410 的生命周期判定处理已经不可访问时如何选择对外状态。这里的两条日期提供迁移依据，仍需实查公开入口的状态才能断言退役已发生。

Sunset 比 Deprecation 更早，客户端应该交换两个日期吗？

不应该自动交换。弃用标准第四节要求 Sunset 不得早于 Deprecation。把主例中的预计停用日期改成二〇二四年一月一日，二〇二五年的弃用日期仍原样保留，就得到一条和主例不同的冲突路径。应保留两份原始值与来源，联系资源维护者澄清，并把迁移日期标记为待确认。交换它们会把无法确认的信息变成另一项未经提供方表达的承诺。当前请求是否成功，继续按收到的状态与响应合同判断。
