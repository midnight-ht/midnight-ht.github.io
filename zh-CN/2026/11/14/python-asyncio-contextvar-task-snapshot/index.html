父任务改了 ContextVar，已经创建的子任务为什么仍读到旧值？

用实际运行的事件门对照，区分 asyncio 的任务创建、上下文复制与随后读取。

正文

核心要点

  • 默认上下文在创建任务时复制。
  • 父任务重新绑定不会替换已创建任务中的绑定。
  • 可变绑定值的对象身份需要单独考虑。

默认情况下，asyncio 创建任务时复制当前上下文。父任务后来重新绑定 ContextVar，即使子任务还没读这个变量，子任务也会从创建时那份上下文读取。需要让后台工作使用新绑定时，应在绑定之后创建任务，或明确传入所需的上下文。

假设服务用上下文变量记录请求编号。它先创建一个后台协程任务，然后在当前请求中换成另一个编号。后台任务等到信号放行才生成记录，工程师看到的是先前的编号。排查时要找的是调用 create_task 的位置，以及编号在那个位置的实际绑定。日志的生成时间能说明什么时候读取，却不能单独说明读取的是哪份上下文。

不靠睡眠验证创建与读取的先后

Python 的 asyncio 文档规定，create_task 没有收到显式 context 参数时会复制当前上下文。这样得到的任务可以在自己的上下文中执行。协程对象的创建和把它交给 create_task 是不同动作。这里的预期绑定到后者，不能用函数定义的位置或第一次 await 的位置替代。Python 3.14 asyncio Tasks。

下面的本地程序已在 Python 3.11.15 执行。父任务先设置 A，创建第一个任务，再设置 B 并释放事件门。子任务的读操作必须等事件门打开。该门起初关闭，所以可以保证第一条读取发生在父任务已设 B 之后，不需要用机器速度推断。第二个任务在父任务已经设置 B 时创建，提供不同创建时点的正对照。

import asyncio
from contextvars import ContextVar

request_id = ContextVar("request_id")

async def read_when_ready(gate):
    await gate.wait()
    return request_id.get()

async def main():
    gate = asyncio.Event()
    first_token = request_id.set("A")
    try:
        first = asyncio.create_task(read_when_ready(gate))
        second_token = request_id.set("B")
        try:
            gate.set()
            first_value = await first
            parent_value = request_id.get()
            second = asyncio.create_task(read_when_ready(gate))
            observed = (first_value, parent_value, await second)
            assert observed == ("A", "B", "B"), observed
            print(observed)
        finally:
            request_id.reset(second_token)
    finally:
        request_id.reset(first_token)

asyncio.run(main())

独立预期是第一个任务读 A，父任务读 B，随后创建的任务读 B。归档记录给出这三个观察和精确代码。若只比较两次后台日志文本，看见不同编号并不能说明哪次应该对应哪个请求。程序把结果顺序固定为第一个子任务、父任务、第二个子任务，使创建时点和字段归属可查。这个测试不涉及工作线程、进程切换、HTTP 中间件或实际日志服务。

让调用位置反映编号归属

如果子任务要代表父任务当前的请求，把绑定编号与创建任务放在能看出先后的路径中。比如先获得订单号、再建立读订单的任务。若在早期创建任务只是为了等待后续条件，而任务必须使用后来才确认的编号，可以直接把已知编号作为函数参数传入另一阶段，或者等编号就绪再创建需要它的任务。参数比隐式上下文更容易在跨系统交接时看见；上下文变量适合执行过程中确实需要读取同一绑定的辅助函数。

Python 三点十一及以后可以在 create_task 中指定 context。要主动控制某个后台任务的值，可以从明确的上下文构造或复制需要的范围，再在创建处传入。不要默认把当前请求的全部绑定都交给一个与该请求无关的后台任务。后台任务应携带哪些诊断字段由业务决定。本文未测试显式 context，不把默认复制的结果外推到同一个自定义上下文被多个任务共享的设计。本站的 TaskGroup 失败范围 讨论谁会被等待和取消，这里只检查任务从哪里获得变量绑定。

还可以给接口日志设计一个反向控制。将两条记录都延迟到父任务改值之后生成，再分别检查它们属于各自的请求。只检查每条日志都带有某个编号，无法发现误把所有记录归到最新请求。若代码在测试里手工拼接日志前缀，也不会经过真实的变量读取点。应把观测放到真正取值的函数上，再核对最终日志是否使用了它。这个应用侧验证未运行。

一种容易误诊的调用方式是提前把协程对象存到队列，之后才由另一处代码创建任务。可以额外准备一份对照：编号为 A 时构造协程对象但不启动任务，设为 B 后再交给任务创建入口，随后把父绑定改为 C 才放行。预期读取 B。这个预期与主例中的创建后重绑定不同，可以排除“构造协程对象就已经固定上下文”的解释。若实际队列跨线程或进程，还要检查消费端的构造位置与值如何传递，本地事件门没有模拟这种交接。

父任务使用完临时绑定后，也应恢复自己的值。示例每次 set 都保存对应 token，并按相反顺序恢复。假设一个工作循环连续处理请求甲和乙，若甲失败后没有清理，乙开始时可能带着甲的诊断信息。可以把“中途抛错”加入工作循环回归，核对退出甲后原来的绑定已经恢复，再创建乙的工作。这项恢复测试应读取父任务自己的状态，不能只靠已经创建的子任务读到旧值来证明父任务恢复成功。这里没有运行这两项追加测试。

如果 ContextVar 绑定的是列表，父任务 append 会怎样？

上下文复制是浅复制，变量所绑定的对象本身不会因此深拷贝。如果父任务与已创建的任务仍绑定同一个列表，在事件门打开前对列表就地 append，子任务可以看见变化。这个条件与重新绑定一个新列表不同。可以分别准备一条原地追加的路径和一条将变量重新设为新列表的路径，比较两边的对象身份与元素。若需要稳定快照，可选不可变值，或在明确的交接边界构造独立对象。主程序只用不可变字符串，这个列表对照没有运行。Python contextvars。
