Git 提交 ID 全变了，怎样看出哪笔补丁真的改了？

用两个已固定的 Git 提交范围复查逐笔补丁，分辨对象 ID 更新与实际修改。

正文

核心要点

  • 两个范围各自需要正确的基线。
  • 补丁配对可以发现提交 ID 改变后仍相同的工作。
  • 最终树差异与补丁对应应分别验收。

重放后的提交都换了对象 ID，审查真正需要的是逐笔补丁变化。Git 的 range-diff 可以比较重放前后的两个提交范围，指出哪些补丁仍能对应，哪些发生了改动。

假设审查者已经看过一版配置改动。新版为了跟上上游换了基线，同时改了一个运行模式。若拿每笔提交的新旧 ID 直接对照，两笔都像全新工作；若只比较两个尖端的文件，连上游新增的文件也会出现在结果里。更贴合任务的做法是先固定旧版和新版各自的基线，再问哪笔主题补丁发生了变化。最后仍可对目标树做另一项交付检查。

把两版各自添加的工作放在一起

Git 参考把范围比较定义为两组补丁之间的对应。它会寻找相近的提交，比较时考虑作者信息、提交消息与补丁内容，再显示两边的配对和未匹配项。相近是一种用于审阅的配对判断，不能当作身份或签名验证。本文使用两组明确的起止引用，避免把重放以前的共同祖先误当两边唯一合适的基线。 Git 的 range-diff 手册

下方完整脚本在临时目录建仓库，旧版添加说明文件，再更改服务配置。新版基线多了许可证文件。之后将旧版两笔主题提交重放到新基线，最后修订第二笔的模式字段。没有远端，也不操作现有仓库。Apple Git 2.50.1 已运行。示例脚本只用于解释输出，测试记录保存了完整原始结果。

set -eu
work=$(mktemp -d)
trap 'rm -r "$work"' EXIT
cd "$work"
git init -q -b trunk
git config user.name Fixture
git config user.email fixture@example.invalid
git config commit.gpgSign false

commit() { git commit --quiet "$@"; }
printf 'port=80\n' > service.conf

git add .
commit -m base
git tag old-base
git switch -qc old
printf 'readme\n' > notes.txt
git add .
commit -m 'Add notes'
printf 'port=80\nthreads=4\nqueue=16\nretry=3\nformat=json\nmode=read\n' > service.conf
commit -am 'Choose service mode'
git switch -q trunk
printf 'upstream only\n' > license.txt
git add .
commit -m 'Add license'
git tag new-base
git switch -qc new
git cherry-pick old~1 old >/dev/null
sed 's/mode=read/mode=write/' service.conf > changed
mv changed service.conf
commit -a --amend --no-edit

git diff --name-only old new
git range-diff --no-color old-base..old new-base..new

普通尖端比较列出 license.txt 和 service.conf。第一个来自更新基线，第二个才是审阅者在主题中要追问的配置。在同一次运行的补丁比较中，添加说明的两笔提交虽显示不同 ID，却以等号配对。选择服务模式的两笔以感叹号配对，内层差异显示原来增加 mode=read，后来改为增加 mode=write。许可证没有进入主题对照，因为它已属于新基线。这不是从结果中删去不喜欢的文件，而是两个范围原本就只包含本次想比较的工作。

把审阅结果写成三条独立观察。第一笔在这次输出里对应且内容不变，第二笔可对应但补丁变化，许可证在最终树中变化却不属于主题。接手人可以分别回到旧版和新版确认。如果审查确实还要求查看新上游是否合规，就保留那个树比较；它只是回答不同范围的问题。如果要求验证某笔已批准的原提交是否仍可达，应另外检查祖先关系。补丁对应不能提供这两种证明。

配对变化时，回看完整提交

这个样本让第二笔保留了几项配置字段，只改最后一项，因此可以观察到“已匹配但变化”。若一笔补丁很短或重写很大，Git 可能把它列成旧系列移除与新系列新增。用命令比较的较早的一次试验就曾出现未匹配状态；最终教学脚本留出了足够的共同内容，避免把示例变成讨论阈值调优。实际审阅若遇到一删一增，不宜仅凭那两个符号宣称开发者丢掉了功能。先打开两个完整补丁，再对照具体行为与测试结果。

参考还说明输出是面向人的文本，跨版本可能变化。团队可以保存实际命令、四个范围端点和 Git 版本，让复核人能重建它。若要自动验证某份新制品确实带上了期望设置，可直接读取目标文件并做独立断言。不要让脚本把一个感叹号当成质量判定。补丁比较能缩小要看哪里，决定是否接受新的运行模式还需要应用层判断。

保存范围时，建议把旧基线、新基线以及两边的尖端各记一份完整对象号。假设第一次审查用的是旧版上游，第二次审查时分支名称已被重用。命令行看起来完全一样，却可能解析到不同对象。先确认这些对象之间的关系，再运行补丁比较。样本中的标签只为让图容易阅读，真实项目可以用已经保存的提交身份。依靠当时截下的一行简写并不足够，因为下一位审查者可能无法从当前分支猜出旧基线。

还可以把明确不想重新审查的基线变化写入一项反例。比如许可证属于更新上游，但主题范围却误用了旧基线，那么新一侧会多出一笔“添加许可证”。这条新增并不代表主题开发者改了授权。先重新核对范围端点，再去判断新增项是否属实。这个错误范围没有在脚本里额外执行，作为迁移后审查的检查思路。若两个范围确实有别的合入方式，比较前也应确认目标范围里是否包含额外工作。

遇到原始端点已不可见时，先确认能否从审查记录中取到原对象。只保留新旧尖端而没有各自基线，可能又把已经确认的上游改动放回待审范围。站内上游重写后的分叉点解决起点如何确认；这里假定四个端点都已确定。两项核对可接着做，但不能用一项结果替另一项。

范围里有合并提交，默认也会逐笔比较吗？

默认忽略合并提交。若审查任务要求检查合并时引入的解决冲突内容，需查看手册的 --diff-merges 选项并选择合适形式，再核对那笔合并的具体变化。本文样本是两条线性系列，没有运行这个变体。验收时另准备一笔含手工冲突解决的合并，确认它在选定模式下可见，避免用主例中的普通提交结果推断合并已经受到检查。
