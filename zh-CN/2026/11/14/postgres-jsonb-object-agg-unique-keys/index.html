PostgreSQL 生成 JSONB 对象时，两个来源行为什么只剩一个键？

用两个部门和三条设置区分 PostgreSQL JSONB 对象聚合的决胜顺序、组内拒重复与严格模式。

正文

核心要点

  • 普通对象聚合保留最后处理的同名值。
  • 唯一模式会拒绝同一组中的重复键。
  • 按输出合同选择决胜、拒绝或保留所有来源。

PostgreSQL 的 jsonb_object_agg 会把同名键压成一个，保留最后处理的值。若输出合同要求每组只有一条来源能定义该键，应选会拒绝重复的聚合，并把冲突留给能够定位输入的错误路径。

假设一个设置接口要为每个部门生成一个 JSONB 对象。部门一有两条 color 设置，先后是红和蓝。部门二也有 color，值是绿。接口本来要求每个部门只有一条颜色设置，开发却看到聚合成功并返回两个对象，认为源数据没有冲突。问题是对象中的键数已经不是聚合前的行数。第一次检查应回到每个输出对象的来源组，弄清是哪里重复，而不是拿对象的最终大小替输入做验收。

最后的值由聚合输入决定

PostgreSQL 十八版的聚合文档说明，普通 JSONB 对象聚合把键转成文本。当同名键多次出现时，结果只保留最后一个值。若业务确实约定按序号采用最后一条，应在聚合调用里给出明确排序，并处理序号相同的情况。查询最外层的 ORDER BY 可以给部门行排序，却不能替内部聚合提供同一份输入顺序。重复键如果本来属于异常，就不必编一条决胜规则，只应让冲突显式失败。PostgreSQL 18 聚合函数。

同一键在两个部门出现并不冲突，只要两个部门被分成不同的输出组。给聚合选择唯一模式之前，先把组的边界与键的业务范围写清。若部门内部的设置来自多个来源，还要判断它们的名字是否应当映到同一个键。示例里的名称本来就是文本，不讨论自定义数据类型如何转换。迁移真实查询时，应检查实际传给聚合的键表达式以及它是否会合并原本不同的标识。

用相同三条来源记录验收三个结果

以下是未执行的教学 SQL。临时表给出两个部门、每条设置的唯一组内序号、键和值。第一份查询有意选择组内最后一条；第二份查询为唯一模式提供一个跨组重名的正控制。负例在这两份查询之后单独运行，以免一个预期错误中断整个会话中的其它验收。

CREATE TEMP TABLE settings (
    department int,
    seq int,
    name text,
    value text
);
INSERT INTO settings VALUES
    (1, 1, 'color', 'red'),
    (1, 2, 'color', 'blue'),
    (2, 1, 'color', 'green');

SELECT department, jsonb_object_agg(name, value ORDER BY seq) AS payload
FROM settings
GROUP BY department
ORDER BY department;

SELECT department, jsonb_object_agg_unique(name, value) AS payload
FROM settings
WHERE department <> 1 OR seq = 1
GROUP BY department
ORDER BY department;

第一份查询预期得到两个部门。部门一的 color 是 blue，部门二是 green。第二份查询只保留部门一的序号一与部门二的记录，预期得到 red 和 green。为单独运行负例，复制第二份查询并移除 WHERE 条件，其他内容保持相同。预期聚合在部门一发现重复 color 并报告错误，不提供可作为成功响应消费的一组结果。这里不检查异常文本的某个语言版本；执行时应记录实际数据库版本、错误代码和该部门的输入身份。

成功结果也应按部门和键配对核对，不能只检查有两个对象。如果聚合前的连接不小心从其他部门带来一条颜色行，最后保留的颜色可能恰好与预期相同，普通查询仍会成功。应另外核对聚合输入，用组键与 JSON 键统计每组来源数。在输出要求唯一时，拒重复的聚合能让这类冲突显露出来；它不会自动证明连接的归属条件正确。样本没有关联外部表。

选择允许哪一种冲突处置

配置要求“一键一条来源”时，适合使用唯一模式，并在出错后从原始组查出重复项。不要为了让导出完成，临时改用普通聚合吞掉错误。如果业务需要保留所有记录，用数组或明细列表比对象更适合。若已确认“后一次更新覆盖前一次”，普通模式也可以表达这项决定，但需要一个稳定且可验收的决胜键。让业务规则先决定输出类型，再用数据库函数落实。

还可以构造两条内容完全相同但来自不同记录的输入。如果测试只核对最终 JSON 值，两个相同值被覆盖也无法发现。唯一要求约束的是输入键数，而不取决于旧值与新值是否恰好相等。把输入来源身份加入诊断回执，会让修复落在冲突数据本身。站内的 JSON 重复成员校验 讨论读入原始对象之前的检查；这里由 SQL 行创建对象，来源行还在时可以沿组核对。

在接口端，若错误中途使事务进入失败状态，应让调用方明确处理这次失败，再用独立的只读查询诊断输入。不要把一次失败请求中已经打印的局部日志当作完整交付。另准备一个部门确实没有设置的输入，确认产品希望显示缺失还是空对象；那是另一个空输入合同，不能据此改变重复键失败的处理。本文没有执行 SQL 或连接 API，所有结果只是固定样本的预期。

如果用独立预检列出冲突，注意它和最终聚合可能读到不同时间的输入。两次查询之间若有写入，仅凭先前预检通过就撤掉聚合的拒绝规则，会留下新冲突的窗口。可以让演练在预检和输出之间插入一条同名记录，再确认最终操作仍拒绝。这里没有实现事务协调，也没有验证并发写入。需要保证长期唯一性的系统，应依实际数据模型和约束明确哪些写入可以创建同名键，而不是把临时诊断当成约束本身。

唯一模式下，空值能跳过但仍检查重名吗？

PostgreSQL 十八版的 jsonb_object_agg_unique_strict 会跳过值为 SQL NULL 的键值对，同时对重复键报错，文档明确包括带空值的键值对。可以用另一组输入，颜色为 green，memo 值为 SQL NULL。普通唯一模式应保留 memo 的 JSON null，严格唯一模式应省略这个键。再追加同名 memo 的一条非空记录，单独运行严格模式，预期仍因重复报错。两条对照分别检查省略与冲突，不能只看最终对象里没有 memo 就推断唯一性通过。这个变体未执行。
