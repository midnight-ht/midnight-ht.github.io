顺序无关的测试，为什么不能只比较 set？

用两个实际拒绝的反例和一条重排结果，核对 unittest 对出现次数的比较。

正文

核心要点

  • 顺序可变时，仍可以比较每项出现次数。
  • 集合与总长度都可能掩盖错误。
  • 若输出包含业务身份，应将其纳入比较。

同一批导出记录允许换顺序时，直接比较两个 set 会漏掉重复项。unittest 的 assertCountEqual 比较每种元素出现的次数，顺序变化可以通过，少了一条相同记录仍然会失败。

设想仓库从两个库位各拣了一件 A，又从第三个库位拣了一件 B。汇总视图按实际拣货记录输出商品代号，允许工作者以任意顺序完成。测试拿到 A、B，转成集合以后与预期相同，便报告导出成功。消费者却少收到一个 A。这个接口需要的是同一批记录有相同的数量与归属，测试不能为了去掉顺序约束，顺手把每种代号的数量也抹掉。

先写清哪些改变允许发生

Python unittest 文档定义 assertCountEqual 的目标为同样的元素与同样的出现次数，排列可以不同。名称里的 Count 也不只指总长度。A、A、B 与 A、B、B 都有三条，集合也相同，但 A 和 B 的分配各差一条。把这组反例留在测试里，就能看出比较的是每项次数。Python 3.14 unittest 参考。

有的接口确实只返回商品种类，仓库明细中的两份 A 在这种投影中应合成一个。采用 set 符合那个合同，但需要在测试描述中明确被观察的是什么。测试只想对明细放宽顺序时，保留各个输入项的出现次数。比较方法由消费者所需的信息决定，不能根据哪个断言容易变绿来选。

让重复项真的丢一次

下面完整的标准库程序已在本地 Python 3.11.15 执行。输入是固定字母，程序没有读取库存、运行服务或验证数据库。正常样本重新排列三条记录。两个坏样本分别少掉 A，或把一条 A 替换成 B。通过 assertRaises 验证故意失败的断言，使整份探针可以在两个坏结果确实被拒绝时正常结束。

import unittest

case = unittest.TestCase()
expected = ["A", "A", "B"]
reordered = ["B", "A", "A"]
case.assertCountEqual(reordered, expected)

for bad in (["A", "B"], ["A", "B", "B"]):
    case.assertEqual(set(bad), set(expected))
    with case.assertRaises(AssertionError):
        case.assertCountEqual(bad, expected)
    print("rejected:", bad)

with case.assertRaises(AssertionError):
    case.assertEqual(reordered, expected)
print("accepted:", reordered)

预期 B、A、A 通过次数比较，并被严格列表比较拒绝。A、B 与 A、B、B 都能通过集合比较，却必须触发次数断言。运行回执保存两条拒绝和一条接受，能逐条核对。坏样本有一个长度不同、另一个长度相同，因此只增加长度判断的修复也过不了第二个反例。这些结果只覆盖程序里的字符序列。真正的仓库导出还要验证每条记录来自正确库位以及接口没有提前汇总。

排查现有失败时，可以把差异记成预期与实际的次数。对第二个坏样本，A 从二变一，B 从一变二；只输出“两组不一样”不会提供同样的定位信息。反过来，如果测试先把实际输出去重，再把结果交给次数断言，改用正确的方法也补不回丢失的次数。先确认断言拿到的是应用实际生成的序列，之后再决定是否投影字段或去除顺序。

需要保留身份时，先确定比较单位

假设明细还带库位与拣货事件编号，两个 A 来自不同位置。只比较商品字符串可以发现一件 A 消失，但不能分辨是否错误复制了同一库位记录。若 API 合同要求正确的拣货事件，就用包含事件编号与商品的记录或明确的不可变投影来比较。再补一组坏数据，两条 A 仍在，编号却重复。用商品次数做的测试会通过，保留事件身份的测试应拒绝。字段选择要从接口合同出发，不能每次都把所有时间戳和展示文字绑进测试。

显示顺序也是一种可能的合同。如果同一份结果驱动用户可见的排序或下一页起点，不能只凭次数断言给页面排序背书。可以分别检查完整结果的次数和用于分页的顺序。例如先给定一组事件并确认没有遗漏，再对两个时间相同的事件核对最终决胜字段。这个额外设计没有运行，也不验证真实数据库分页。站内的 unittest 子测试边界 讨论失败后哪些断言会继续；本篇关注的是单条比较保留了哪些输出信息。

还可以把数量合同和页面过滤拆开。先在未过滤输出中检查三个事件，再发一个只查询 A 的请求，核对两条 A 各自归属正确。若只对过滤后的响应做断言，某次错误遗漏 B 时，A 页面仍会正常。两种验收观察不同的输入集合，失败结果应说明使用的是全量导出还是某个查询条件。

如果业务把一个事件的两个字段当成同一份身份，应比较组合，而不是给每个字段分别计数。假设库位甲原先对应 A，库位乙对应 B。错误结果把两项商品对调，商品次数和库位次数都保持不变。把每条记录投影成库位与商品组成的组合，就能发现原来的归属没有保留。再加一条相同组合重复出现的合法记录，确保修复没有换回集合比较。这样的用例有助于发现按列拆开测试导致的假通过；样本仍要以业务预先定义的记录为基准，不能从当前导出的实际结果自动生成预期。

记录是字典，不能当 Counter 的键，还能比较吗？

可以。标准库文档特别说明，此断言也支持不可哈希的对象。假设预期有两个相同的字典记录和一个不同的记录，可把顺序打乱后验证接受，再删掉一个重复字典验证拒绝。直接对字典序列建立 Counter 并不能替代这一入口。先决定比较整份字典还是投影稳定字段。若备注是合同的一部分，就让不同备注保持可见；若合同只约束编号和状态，直接把每个记录转换成这两个字段组成的值。这个字典变体没有运行，主程序不提供大批量记录的性能比较。
