GroupShuffleSplit 设一半，为什么测试行数不是一半？

用四组十二行区分组比例和样本比例，保存同次划分的组交集、组数与行数。

正文

核心要点

  • test_size比例以组为分母
  • 组大小不等会改变测试行比例
  • 同次划分需分别检查组交集与样本量

GroupShuffleSplit 的 test_size 设成一半，测试集却可能包含四分之三的行。这里的一半指组数，并不指样本行数。四组分别有八、一、一、二行，选其中两组，既可能拿到九行，也可能只有三行。先确认参数的分母，才能判断切分结果是否符合合同。

让同一实体的记录留在同一边

scikit-learn 的 GroupShuffleSplit 按调用者提供的组信息生成训练与测试索引。组可以表示同一个人、设备或其他领域实体。若同一对象有多条相近记录，按组组织划分，可以表达这些记录在同一次划分中应该一起进入哪一边。

这里固定组标签A、B、C、D，大小分别是八、一、一、二，共十二行。它们只是人工数据，不代表实际患者或设备分布。test_size 为零点五，表示测试组占四组的一半，也就是两组。文档规定浮点比例按组数计算并向上取整，不会先算十二行的一半再切六行。

选中A与B，测试九行，训练三行。选中C与D，测试三行，训练九行。两份分配都占两组，却有不同的样本比例。这不是随机数故障，而是组大小不同的直接结果。若产品要求测试集有足够行数，还需要另外检查实际结果，不能从组比例替代那项要求。

组标识本身也要来自合适的关系。把同一个人的每次访问分别命名为不同组，就没有表达希望隔离的实体。相反，把本来独立的许多对象合成一组，会减少可分配的组数。先说明要评估对哪些未见对象的能力，再决定组边界，不能从一个现成数据库字段名直接推断正确答案。

两份合法分配与一个行切分反例

以下完整脚本只处理明确列出的样本与组。它手工选择A/B或C/D作为测试组，用于核对数量和交集。没有调用 scikit-learn，没有运行随机切分器，也没有训练模型。代码不把手选结果冒充某个 random_state 的实际输出。

import { deepEqual } from 'node:assert/strict';
const groups = ['A', 'A', 'A', 'A', 'A', 'A', 'A', 'A', 'B', 'C', 'D', 'D'];
const rows = groups.map((group, index) => ({ id: index + 1, group }));
function describe(train, test) {
  const trainGroups = Array.from(new Set(train.map(row => row.group)));
  const testGroups = Array.from(new Set(test.map(row => row.group)));
  return {
    trainRows: train.length,
    testRows: test.length,
    trainGroups,
    testGroups,
    shared: trainGroups.filter(group => testGroups.includes(group))
  };
}
const actual = [['A', 'B'], ['C', 'D']].map(selected => {
  const selectedGroups = new Set(selected);
  const test = rows.filter(row => selectedGroups.has(row.group));
  const train = rows.filter(row => !selectedGroups.has(row.group));
  return describe(train, test);
});
deepEqual(actual, [
  { trainRows: 3, testRows: 9, trainGroups: ['C', 'D'], testGroups: ['A', 'B'], shared: [] },
  { trainRows: 9, testRows: 3, trainGroups: ['A', 'B'], testGroups: ['C', 'D'], shared: [] }
]);
const rowSplit = describe(rows.slice(0, 6), rows.slice(6));
deepEqual(rowSplit.shared, ['A']);
console.log(JSON.stringify({ actual, rowSplit }));

原样脚本在本地Node执行通过。两份分配的测试行数分别九与三，组交集都为空。独立预期把训练组、测试组和数量全部列出。最后的错误对照直接按行前六后六切分，虽然行数平分，A仍同时出现在两边，交集检查就会指出这一点。

这个负例也说明，行索引没有交叉不等于实体没有交叉。十二条各有自己的行号，逐行分成两份不会重复行号，但属于同一个A的不同记录仍跨边。两种检查应分别保留，不能让一个「没有重复样本」的断言承担实体隔离的全部含义。

运行回执证明的是这份确定分配的算术和集合关系。真实库选择哪两组，仍需要实际库版本、参数与返回索引作为证据。若后续换成包调用，应保留实际选中的组，而不只写一个预期随机种子。本文没有Python包运行结果，也没有任何模型质量分数。

报告同时保存组数与行数

每份划分可以记录训练组、测试组、两边行号、组数和行数。先核对同一次训练与测试的组交集为空，再查看样本量是否足以支撑当前任务。两项都需要满足自己的合同，不能因为隔离正确就忽略测试数据过少。

还应检查输入行有没有遗漏。两边组交集为空，只说明它们没有共享组，并不证明所有原始行都被分配。把训练与测试的行标识合并后，与本次输入清单比较，能发现过滤或连接步骤丢掉了一组记录。记录这种覆盖检查，避免把缺少数据的安静结果误当成完整划分。

不等组大小还会影响类别覆盖。一个大组可能集中包含某些类别，分组后两边的类别分布未必接近。这项分组比例参数不替你承诺分类分层。先记录实际标签覆盖，再决定是否需要采用另一种满足领域条件的切分设计。

特征准备也有自己的边界。即使行分配正确，若某个需要拟合的预处理先看过全部数据，实体分组本身不能证明其他信息路径也被隔离。评审应保存数据准备与模型拟合所使用的样本范围。这里没有执行那些阶段，不用一份空组交集宣布所有泄漏问题已经排除。

版本对比时保留同一份划分身份也很有用。只保存一个比例，下一次换输入或组标识后，测到的可能是不同测试对象。保存行标识与组标识映射，能追出改动来自模型、样本集合还是组边界。随机种子便于重现某次生成，却不能代替对输入版本的记录。

在评估指标报告里，训练测试划分和最后的平均方式也应各有证据。站内 micro与macro精确率讨论预测已经给定后的计数聚合。本题更早一步决定用哪些对象来测试，不能靠换一种平均方式修复不合适的数据分配。

多轮切分的测试组，也必须彼此不重合吗？

这类随机切分不保证不同轮的测试集合互斥。这里新增两轮之间的比较，和主例同一轮内部的训练与测试不同。第一轮测试A/B，第二轮测试A/C，两轮都可以把自己的训练组排除干净，但A仍在两轮测试中出现。

这是一份额外的纸面组合，不是当前脚本执行过的随机结果。若把多轮测试样本数简单相加，会重复计算A的八条记录。报告应说明是在统计每轮评估量，还是不同测试对象的覆盖量，再按相应定义计算，不能把轮数乘样本数当作唯一对象数。
