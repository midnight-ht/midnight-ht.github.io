outline 加粗后，为什么旁边按钮没有移动？

区分轮廓墨迹与布局占位，用宽度切换页同时检查目标矩形、邻居位置和实际指示。

正文

核心要点

  • outline不为自己占据布局空间
  • 几何稳定不证明轮廓可见
  • 布局读数与实际绘制都需要核对

把按钮的 outline 从两像素加到八像素，邻居却没有被推开。这个结果可以符合轮廓的规则。outline 不为自己占据布局空间，画出来更厚与盒子重新定宽是两项观察。排查时既要量按钮与邻居，也要看实际绘制，不能从矩形不变推断轮廓没有生效。

轮廓绘制与布局占位

CSS Basic UI Level 4 说明，outline 不占据空间，属于元素的墨迹溢出区域，并且可能呈现非矩形形状。这里依据二〇二六年十一月十三日工作草案的轮廓定义，限定普通按钮，没有引入变换或其他特殊绘制条件。

因此增加轮廓宽度，不会为了它另分配一圈布局位置。按钮本身的宽高和相邻项位置可以保持。若团队原本希望外框出现时卡片内容不跳动，这个属性的占位特点有用；但它没有保证轮廓在任何祖先、背景与交叠条件下都清楚可见。

元素的边界矩形也不是轮廓墨迹的完整范围。getBoundingClientRect 给出的读数，不能直接当作外框最外沿的截图边界。只比较矩形适合检查布局有没有移动，实际轮廓是否显示、是否被其他内容干扰，需要另有视觉观察。

这也解释一种假通过。开发者把轮廓整条删掉，矩形仍然一样，若测试只断言「按钮没有移动」，这次回归依旧会通过。稳定布局是目标之一，能辨认当前控件也是目标之一。验收记录应该让这两项各有可检查的结果。

只切换轮廓宽度的完整页面

下面给目标和邻居相同的边框与内边距。独立按钮只切换目标轮廓宽度，不修改文字、边框、间距或容器宽度。读数同时记录目标宽高、邻居位置和计算后的轮廓宽度，便于确认被切换的声明实际进入样式。

<!doctype html>
<meta charset="utf-8">
<title>Outline and layout measurements</title>
<style>
.row { display: flex; gap: 12px; padding: 12px; }
button { border: 1px solid; padding: 8px; }
#target { outline: 2px solid #17486b; outline-offset: 2px; }
#target.wide { outline-width: 8px; }
</style>
<button id="change" type="button">Toggle outline width</button>
<div class="row">
  <button id="target" type="button">Target</button>
  <button id="neighbor" type="button">Neighbor</button>
</div>
<pre id="result"></pre>
<script>
const byId = document.getElementById.bind(document);
const target = byId('target');
const neighbor = byId('neighbor');
function read() {
  const box = target.getBoundingClientRect();
  const next = neighbor.getBoundingClientRect();
  return {
    targetWidth: box.width,
    targetHeight: box.height,
    neighborLeft: next.left,
    outline: getComputedStyle(target).outlineWidth
  };
}
byId('change').onclick = () => {
  const before = read();
  target.classList.toggle('wide');
  const after = read();
  byId('result').textContent = JSON.stringify({ before, after }, null, 2);
};
</script>

按规则推导，宽度从两到八时，目标布局宽高与邻居位置不因轮廓占位而改变，计算样式里的轮廓宽度会变化。这里没有固定按钮最终是多少像素。文字字体、缩放和系统按钮呈现都会影响基线尺寸，不适合给所有环境一组通用矩形常数。

本文没有运行浏览器或采集截图。完整页面和读数入口只是待执行对照，不能写成已经观察到零位移。实际复验应保存目标环境、切换前后的三个几何量、计算轮廓值及对应画面。若某一量变化，先查是否还发生了其他状态或样式变化。

负例可以只移除目标的 outline 声明，其他设置不变，再检查现有测试是否仍全部通过。若通过，只能说明它保住了几何断言，没有检查所需指示。恢复声明后重新做一次完整观察，别把开发工具临时改动留下的截图当作发布代码已经修复。

回到焦点样式时，要保留触发条件

教学页面的按钮用来单独切换样式，不模拟焦点输入方式。产品中若按 focus-visible 展示轮廓，还要先确认目标是否匹配该状态。站内 焦点与可见指示选择器讨论那一层判定。选择器没匹配与轮廓不占空间，是不同的调查问题。

如果改用加粗边框，也要看盒子的尺寸合同，不能断言任何边框改动都会把邻居推走。固定外框尺寸与自动尺寸的结果可能不同。可对照 内容盒与边框外沿，保留自己的宽高、内边距和 box-sizing 条件后再比较方案。

可见性方面，应把控件放回真实布局检查。独立样本周围留有空间，业务工具栏可能很挤，轮廓加厚后会接近邻居文字。即使元素之间的布局间隔保持原值，额外墨迹也可能影响辨认。要决定怎样留足视觉空间，不能只从「没有重排」给出合格结论。

主题变化也应绑定同一任务。普通配色下看得清的轮廓，切到另一背景或系统颜色设置时需要再次观察。规范特别要求不能在没有替代高亮机制的情况下让相关键盘焦点轮廓不可见。这里不提供一组配色就能满足所有环境的声明，也没有进行辅助技术验收。

组件接口可以把指示样式与布局尺寸分别记录，避免后续维护者为修一个截图而同时改两项。假设把轮廓替换成更厚边框，又顺便改了内边距，后来即使按钮没移动，也很难解释是哪一项抵消了另一项。先做单变量比较，再在正式方案中验证合并后的结果。

测量还要使用同一坐标与同一时点。若切换后页面发生滚动，用旧位置与新位置直接比较，会混入视口变化。保持页面条件，或在记录中说明滚动和尺寸变化，才能将读数与这次轮廓切换关联起来。当前脚本没有让页面滚动，产品测试仍要留意其他事件。

换成跨两行的行内链接，轮廓一定是一个矩形吗？

不一定。这里新增多行行内内容，而主例是普通按钮盒。规范允许轮廓非矩形，不能把一只元素的总边界矩形当成它必然绘制出的轮廓形状。

在目标浏览器中让链接真实跨行，观察各片内容周围的指示是否足以辨认，再保存实际画面。不要先要求所有实现画成同一个外接矩形，也不要只凭一个矩形读数宣布每片都完整。本文没有运行这个变体，提供的是新的观察条件与规范允许范围。
