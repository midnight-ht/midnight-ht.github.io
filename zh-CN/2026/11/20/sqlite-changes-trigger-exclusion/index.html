触发器又写了两行，changes 为什么还只返回一？

在隔离 SQLite 事务里检查一次直接插入与两条触发器审计，并核对回滚后的两表状态。

正文

核心要点

  • changes 不累加下层触发器的辅助写入。
  • 直接计数与审计身份分别检查。
  • 作用于视图的语句不能用零计数推断无业务变化。

插入一条任务，AFTER INSERT 触发器又写了两条审计记录，SELECT changes() 仍然返回一。它统计最近完成的那条直接写语句，不把下层触发器造成的辅助变更加进来。核对审计是否执行，需要另外读取审计记录。

一条语句与整个副作用范围不同

假设本地任务表每增加一个编号，就在 audit 表写开始和结束两个教学标记。调用者看见任务插入成功，也知道审计表应该出现两行，于是期待影响行数是三。这个期待把直接操作与触发器程序混成了一个计数。数据库的 changes 接口保留的是前者，不能用它当成所有表受影响行数的总和。

SQLite 的 SQL changes() 包装底层 changes64 接口，遵循同一计数规则。官方文档明确排除触发器、外键动作和 REPLACE 冲突处理等辅助变化。这里的两行审计都发生在下层触发器中，所以外部插入完成后读到一是正常结果。它没有表示触发器只写了一行，也没有表示触发器没运行。

计数还属于具体连接和最近一条完成的写语句。若同一条连接稍后又执行另一条 INSERT，再读取 changes，就可能观察另一项操作。应用应该在对应语句之后及时关联结果，而不是跨几个无关写入再用同一个数字解释最早的任务。SELECT 观察本身没有把三行变化重新聚合成一份业务统计。

一条直接行，两条审计行，各有断言

下面的夹具在独立内存库建立普通表和触发器，用显式事务观察插入之后与回滚之后的状态。连接不参与项目数据。辅助查询函数只把游标读成列表，便于所有预期使用相同的结果形状。

import sqlite3
from contextlib import closing

def rows(db, sql):
    return list(db.execute(sql))

with closing(sqlite3.connect(":memory:", isolation_level=None)) as db:
    db.executescript("""
        CREATE TABLE task(id INTEGER PRIMARY KEY);
        CREATE TABLE audit(task_id INTEGER, phase TEXT);
        CREATE TRIGGER task_added AFTER INSERT ON task BEGIN
            INSERT INTO audit VALUES(new.id, 'start');
            INSERT INTO audit VALUES(new.id, 'end');
        END;
    """)
    rows(db, "BEGIN")
    rows(db, "INSERT INTO task VALUES(7)")
    assert rows(db, "SELECT changes()") == [(1,)]
    assert rows(db, "SELECT id FROM task") == [(7,)]
    assert rows(db, "SELECT task_id,phase FROM audit ORDER BY phase") == [
        (7, "end"), (7, "start")
    ]
    rows(db, "ROLLBACK")
    assert rows(db, "SELECT id FROM task") == []
    assert rows(db, "SELECT task_id,phase FROM audit") == []
    print(sqlite3.sqlite_version, "direct=1; audit=2; rollback removed both tables' rows")

插入后 changes 恰好一，任务表恰好编号七，审计表则是两份带七的标记。审计查询按 phase 排序，所以预期先 end 再 start；这个排序只是稳定比较结果，没有把字母顺序解释成实际触发时间。要观察触发器执行顺序，必须另定义对应证据，而不是借展示顺序推断。

这三条检查独立承担责任。如果只看计数，触发器根本没建好时也可能得到一。只看审计有两行，旧样本遗留的记录也可能误过。夹具检查任务编号与两个具体阶段，且内存库从空白开始，防止借别的任务的审计通过。生产验收同样应带业务标识，至少能把任务和审计关联回同一操作。

随后回滚，两张表里这次新增的行都消失。这个控制说明语句计数不能当作提交回执，不过它只是这里的辅助失败路径。本文主问题是下层触发器是否计入直接行数，既不实现事务重试，也不推断所有外部副作用都会随数据库回滚。触发器若调用别的系统，是否可以撤回还需要另外设计与验证。

审计验收应该读到什么

先确定审计合同是每条任务两份阶段记录，还是只有某一种状态变化才需要记录。如果触发器带条件，测试要同时覆盖满足和不满足条件的输入，分别核对审计应该出现或不出现。把 changes 的一当作触发器执行的证据，会让有条件分支一直处于未知状态。

应用可把直接语句结果与业务验收结果放在不同字段里，例如记录直接插入一条，同时标明任务七的两份审计已经从目标库读出。只有确实完成读取才填写后者。如果任务由异步服务继续处理，应在相应完成事件之后更新状态，不能拿一条数据库触发器的完成外推整个任务已经结束。当前例子没有队列或工作进程。

对于批量写入，直接行数与审计条数也未必存在固定倍数关系。不同任务可能触发不同规则，触发器也可能更新已有记录。验收应依据具体输入列出预期标识与状态，不能看到这份样例是一比二，就把所有生产写入乘二当成审计数量。要做统计指标，先说明它统计直接行、辅助行还是业务事件，再选择对应来源。

本站的REPLACE 删除与身份讨论冲突解决中内部删除的另一份观察边界。这里不使用替换语句，只用一次普通 INSERT 和明确的两条触发器写入，使计数范围能单独被验证。两篇都要求核对最终记录，但不能从那篇的删除特例推断所有触发器都没执行。

可以另开一个空白目标库作为验收负控制，要求它不能提供任务七及其审计。这样即使实际查询误发到另一个库，身份断言也不会因一个相同的行数而通过。这份跨库控制没有执行。

日志还需要保留结果属于哪次连接调用。若把池里另一条连接的数字贴到本次请求，数值碰巧是一也不构成证据。实际服务可以在受控回执里关联操作标识、执行入口与读取时点；样例的所有操作在同一连接顺序完成，没有验证连接池或并发共享。

如果 INSERT 的对象是有 INSTEAD OF 触发器的视图呢？

直接作用于视图的 INSERT、UPDATE 或 DELETE，其 changes 结果为零，即使 INSTEAD OF 触发器对真实表做了写入。这又增加了一个需要知道目标对象种类的条件。接收方不能把零一律解释成业务没有发生，应按实际视图合同去读对应真实行。上面的夹具只操作真实表，视图变体未运行。支持此入口时，另建视图与触发器，要求直接计数零、真实目标出现指定编号，两份预期同时成立。
