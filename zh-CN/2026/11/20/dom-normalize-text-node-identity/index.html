normalize 后文字没变，Text 引用为什么脱离了容器？

用三只文本节点合为一只的页面解释内容不变、身份与父子关系变化，并核对旧引用的用途。

正文

核心要点

  • 相同textContent不证明节点结构相同
  • 连续文本的数据合入首节点
  • 旧引用需要重新核对树中角色

容器仍显示 AB，保存的右侧 Text 引用却不再属于这个容器。一次 normalize 可以让内容保持相同，同时改变文本节点结构。对于 A、空串、B 三只相邻文本节点，它把数据合入第一只，移除空节点和后续被合并节点。旧引用仍指向对象，却不能继续被当成页面上那段文字的入口。

相同文字可以有不同的树结构

DOM 标准的 normalize 操作会处理后代中的普通 Text 节点。空节点会被移除，连续文本节点的数据会合并到这一段的第一只节点，后续节点从树中移除。这里讨论 HTML 的普通文本，没有把 CDATA 或任意节点类型一起称为可合并文本。

因此 textContent 相同，不能证明子节点列表相同。初始三只 Text 的数据连接起来已经是 AB，合并后一只 Text 的数据仍是 AB。若测试只读容器文字，前后都能通过，完全看不到节点数量与引用归属的变化。

数据没有因为合并而转移到一只全新 Text。对于这里非空的左节点，它继续作为首节点，自己的 data 变成 AB。先前保存的 right 对象则不再有父节点。要解释程序随后修改 right 为什么没改变容器，应该检查它是否仍在这片树里，而不是只检查变量里还有没有一个对象。

也不要把移出树写成对象立刻消失。代码仍持有 right，就仍能读它的数据或改变它。这样的修改发生在脱离容器的那只对象上。页面是否跟着改变，取决于修改对象与当前树之间的关系。本文不提供内存回收或泄漏结论。

三只 Text 合成一只的完整页面

下面通过脚本直接创建节点，避免格式化 HTML 的缩进空白混入计数。容器最初尚未接入文档，但内部已经有完整的父子关系。完成规范化后，再把容器和读数放到页面上，便于比较保存的引用。

<!doctype html>
<meta charset="utf-8">
<title>Text node normalization</title>
<script>
addEventListener('DOMContentLoaded', () => {
  const parent = document.createElement('div');
  const [left, empty, right] = ['A', '', 'B'].map(text =>
    document.createTextNode(text)
  );
  parent.append(left, empty, right);
  const before = { text: parent.textContent, nodes: parent.childNodes.length };
  parent.normalize();
  const after = {
    text: parent.textContent,
    nodes: parent.childNodes.length,
    keepsLeft: parent.firstChild === left,
    leftText: left.data,
    emptyDetached: empty.parentNode === null,
    rightDetached: right.parentNode === null
  };
  const output = document.createElement('pre');
  output.append(JSON.stringify({ before, after }, null, 2));
  document.body.append(parent, output);
});
</script>

按 DOM 算法推导，before 的文字是 AB，节点数三。after 的文字仍是 AB，节点数一；首节点与 left 相同，left 的数据为 AB，empty 与 right 的父节点均为空。这些是独立列出的预期，没有运行浏览器，也没有把页面输出写成本机观察。

复验时先确认初始计数确实为三，再执行一次操作。若初始就只有一只节点，之后仍为一不能证明合并有效。若直接用字符串插入，浏览器可能一开始就创建一只 Text，不会自动替这个实验提供三只对象。构造输入的步骤与操作后的读数都要保留。

一个必要的负控制是在调用后只改 right 的 data，再读容器。对于这份输入，容器不应因为修改已脱离的 right 而改变。接着改当前首节点，才会作用到容器文字。这样可以区分「变量有值」和「变量还是当前显示对象」两种判断。这个变体是待执行步骤，主页面没有偷偷执行额外修改。

编辑器引用需要自己的生命周期

如果标注系统按 Text 对象保存待编辑位置，规范化后就需要核对这些对象是否仍承担原来的角色。单纯保存旧 childNodes 的数组，只固定了当时的成员，不会阻止结构操作移除它们。相关集合行为可看 动态与静态 NodeList。

一种产品选择是在建立标注前先确定文本结构，随后由明确入口维护。另一种选择是在结构改变后，依据应用自己的位置模型重新定位。需要哪一条取决于编辑器的数据合同，不能用这份简单例子为任何现有编辑器承诺安全迁移。尤其不能在没有记录原位置的情况下，事后按相同字面内容猜回对象。

也应区分节点清理与字符内容规则。DOM 的这个方法整理 Text 结构，不会替名字生成 NFC 比较键，也不定义字符等价。字符串也有叫 normalize 的方法，它承担另一种合同。调查同名调用时先确认接收对象与方法来源，避免把字符表示变化归因给节点合并。

对框架页面还要核对谁负责这些节点。框架保存的内部引用、编辑器选区以及后续渲染，可能都依赖既有结构。本文只解释标准的节点结果，没有在特定框架中验证任意手工改树操作。将它接入产品前，先列出仍会使用旧引用的调用者，再设计对应的更新路径。

验证记录可以为每只输入节点保存独立名字，分别读取操作前后父节点、数据与当前首节点身份。不要只保留序列化 HTML，因为相同序列化内容也可能隐藏不同的文本节点拆分。若缺少初始节点身份，之后只靠最终 AB 很难说明哪一只被保留。

还可以在同一容器上再调用一次，预期已经合成的非空节点保持一只，内容继续相同。这项检查需要保留第一次和第二次的节点身份，不能每次重新造一个容器后都称为重复执行。若两次调用之间又插入新文本节点，输入结构已经改变，应为那次插入另外记录，再判断下一轮的合并结果。

中间隔着一个元素，也会把两边文本合到一起吗？

不会跨过这个元素把两边当作连续同胞 Text。这里新增一个 em 元素夹在两段文字中。左侧 Text、em、右侧 Text 是三个不同类型相邻项，文本合并不能跳过中间的元素边界。

这次操作仍会检查后代，因此 em 自己内部若有相邻文本，可以在它内部合并。验收时分别读取外层子节点和 em 的子节点，外部边界保持、内部文本可被整理，这两项可以同时成立。不要从最终 textContent 一串相连，推断节点也会跨元素融成一只。
