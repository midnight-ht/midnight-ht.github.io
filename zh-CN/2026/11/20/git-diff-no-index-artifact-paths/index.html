两份导出都不在 Git 仓库里，怎样查看它们的改动？

直接比较仓库外的两份导出，结合真实缺路径回执核对补丁、诊断与状态的边界。

正文

核心要点

  • no-index 直接读取两个路径。
  • 补丁与诊断同退出值一起保留。
  • 固定本次比较的制品身份。

两份导出文件即使都在 Git 仓库之外，也可以用 git diff --no-index 直接比较。它读的是两个文件系统路径，无需先暂存或提交。调用时固定旧文件和新文件，再把补丁、诊断和退出状态一起保存，才能解释比较究竟完成了什么。

例如接收方拿到两次构建生成的配置，想知道发布包改变了哪一行。源码提交能帮助找出处，但接收方当前要核对的是这两份已经生成的文件。把它们复制进仓库再提交，会额外引入索引和历史身份。对于这里的内容检查，直接指定两个路径就有一个足够明确的入口。

固定三种输入，分别读回执

下面的脚本在一次性目录运行。先比较相同内容，再只改右侧文件，最后删除右侧路径观察调用失败。它关闭外部差异程序与文本转换，保留最简单的文本对照。缺路径那段的状态断言写的是本地 Apple Git 2.50.1 的实际结果，复跑前应核对版本。

set -eu
lab=$(mktemp -d)
trap 'rm -r "$lab"' EXIT
cd "$lab"
export LC_ALL=C
git version
printf 'mode=first\n' > before
cp before after

compare() {
  status=0
  git diff --no-index --no-ext-diff --no-textconv --no-color \
    -- before after > patch 2> diagnostic || status=$?
  printf 'result=%s\n' "$status"
}
test -f before
test -f after
compare
test "$status" -eq 0
test ! -s patch
test ! -s diagnostic

printf 'mode=second\n' > after
compare
test "$status" -eq 1
test ! -s diagnostic
grep -F -- '-mode=first' patch
grep -F '+mode=second' patch

rm after
compare
printf 'missing-path diagnostic:\n'
cat diagnostic
test "$status" -eq 1
test ! -s patch
test -s diagnostic

本地运行的前两趟分别退出零和一。相同内容没有补丁或诊断；不同内容的补丁包含删去 first、加入 second 两行，标准错误为空。第三趟没有合法补丁，诊断指向 after 路径无法访问，但退出值同样是一。外层脚本确认了三组预期，最终退出零。原始探针曾预设缺路径会返回大于一，因此失败；这项失败记录保留，修正后的回执没有沿用该预设。

官方把 no-index 定义为比较两个文件系统路径，并说明它隐含 --exit-code。零与一描述正常差异判断，但不能据此推成“所有调用错误一定大于一”。Git v2.50.1 的实现中，访问路径失败会令差异排队失败，并在该路径返回初始化的一。它帮助解释这次观测，不给其他发行版统一承诺。Git diff 的路径比较定义、Git v2.50.1 的 no-index 实现

这也是保留三个流的原因。如果收集器仅将一归为“成功发现差异”，它会把缺文件错误伪装成可审查的更新。如果一概将非零当作工具错误，正常不同内容又无法进入审核。先确认输入能够读取，再检查诊断与预期的差异记录。这里的搜索只验样例中的两行，不能用它代替通用补丁解析器。

给制品比较留住同一份输入

真实任务应记录两份文件的来源、内容摘要和比较命令。旧文件来自上一份交付包，新文件来自候选包，就将这两项身份放进回执。只写“比较 before 和 after”，换一台机器或下一轮任务就可能对应其他内容。文件名足够定位本机路径，交付身份才使审核材料可以复验。

对于会被其他任务改写的文件，检查存在与调用比较之间仍有时间。预检查成功，不能保证下一刻读到同一批字节。可以将本次需要的输入固定到受控的只读快照，再让比较和后续验收都使用它。若存储本身提供一致性读取，也应记录其实际合同。本文的临时目录只有一个操作者，脚本没有验证并发更新。

还要让参数说明比较范围。若选择忽略空白，审核看到的是经过该规则解释的文本差异；若只比较部分导出文件，不能给整包写“全部相同”。上面的两文件没有忽略空白，也没有证明可执行权限、所有归档成员或运行行为一致。遇到二进制文件，Git 的文本展示也未必给出可直接阅读的逐行变化，应用格式仍需自己的验证方法。

看见两份配置没有差异以后，可以接着按消费方入口读它。例如确认关键字段实际被程序采用，而不只是导出步骤生成了那一行。旧包与候选包同样有一个错误默认值，差异为空也无法证明合同正确。反过来，内容确实不同可以是预期的版本更新。审核者需要根据这次允许的变化检查补丁，然后让对应版本完成自身验收。差异只是定位变化的证据。

将比较结果交给下一位维护者

一份可复核的交接可以同时给出旧新制品身份、完整命令和三份输出。正常相同、正常不同和无法比较，各自说明后续应做什么。无法比较时先恢复正确输入，不要把空补丁当成没有变化。已经能读到差异时，再判断它是否符合发布约定，而不是仅凭退出值自动放行。

这里还可以用一份故意错误的接收记录校准流程。把上一轮 after 的路径填给本轮任务，内容比较可能完全成功，回执也是真实的，但指向了错误制品。让输入身份检查先发现它，再重做正确对象的比较。这个交接负例没有运行，样例只控制了字面内容与路径存在性。它说明为何补丁内容和制品来源都需要保留。

两边都是目录，还能看到新增或缺少的文件吗？

可以指定两个目录作为路径比较，让目录中的文件进入差异检查。为这种扩展另设小清单，一项两边相同、一项内容不同、一项只在一侧。检查对应变化后再解释目录结果；缺少某成员与根目录本身无法访问是不同输入。本文没有运行目录对照。它给两文件主例加入的是成员集合，而不把一份文件内容相同推广为两目录完整一致。
