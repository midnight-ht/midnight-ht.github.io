copyWithin 右移重叠区间，为什么不会一路复制成 A？

用AABC与错误AAAA对照重叠复制方向，同时核对原数组身份、长度和覆盖合同。

正文

核心要点

  • 重叠区间决定复制方向
  • 方法覆盖已有位置并返回原数组
  • 值与长度和身份要共同检查

数组 A、B、C、D，把前三项复制到位置一，预期是 A、A、B、C。若手写循环从左往右赋值，却可能变成四个 A。目标区间覆盖了后续还要读取的源位置。copyWithin 针对这种重叠调整处理方向，让结果保留原区间应有的内容。

先画出源区间与目标区间

这里的调用是 copyWithin(1, 0, 3)。源从零开始，到三之前结束，包含 A、B、C。目标从一开始，占据位置一、二、三。源和目标都在同一只数组里，B 与 C 所在的位置正好也在目标范围内。

正向循环第一次把 A 写进位置一，已经覆盖原 B。下一步再读位置一时，拿到的是刚写进去的 A。第三次又沿着同一条路径继续。每次赋值本身都成功，最终却丢失了原本想搬过去的 B 与 C。仅检查循环没有报错，无法发现这个内容错误。

ECMAScript 的算法在源起点位于目标前方、两个区间重叠时，改从末端往前复制。本例先让 C 到位置三，再让 B 到位置二，最后把 A 放到位置一。这样某个源值被覆盖之前已经完成读取。它不要求你先手工创建另一份完整数组。

这个方向选择有具体前提，不是说所有复制都要倒着走。若目标在源前面，正向处理可以先读取后面的源，再覆盖前面的目标。工程上应依据区间关系判断，不能把「从尾部循环」当作任何数组改动的通用修复。

正确结果和错误循环放在一起

完整脚本分别创建两只初始内容相同的数组。标准调用与错误循环各自只操作自己的那一份，预期在执行前就固定。标准结果还要满足长度仍为四、返回值就是被修改的原数组。

import { deepEqual } from 'node:assert/strict';
const standard = ['A', 'B', 'C', 'D'];
const returned = standard.copyWithin(1, 0, 3);
const forward = ['A', 'B', 'C', 'D'];
for (let source = 0; source < 3; source += 1) {
  forward[source + 1] = forward[source];
}
const actual = {
  standard,
  forward,
  length: standard.length,
  sameArray: returned === standard
};
deepEqual(actual, {
  standard: ['A', 'A', 'B', 'C'],
  forward: ['A', 'A', 'A', 'A'],
  length: 4,
  sameArray: true
});
console.log(JSON.stringify(actual));

这份代码已在本地 Node 环境执行，得到标准分支 A、A、B、C，正向分支四个 A，所有预期通过。错误分支是刻意保留的教学负例，没有被推荐为生产实现。若两边共用一只已经修改的数组，对照就不再具有相同起点。

复制范围也受目标剩余空间限制。方法覆盖已有位置，不为这段内容在中间插入新空间。若目标附近放不下全部源区间，实际能复制的数量会被截住。这里恰好剩三个位置，完整承接三项，不能从这个样本推出任意目标都会复制同样多。

有一项容易被返回值掩盖的事实是，调用修改了原数组。把返回结果赋给新变量，不会因此形成一份独立版本。如果页面的另一个视图仍引用这只数组，它之后读到的是修改后的成员。是否需要先创建另一只数组，应由状态管理合同决定，不能靠变量名字带有 new 就认定已经隔离。

搬值之前确定业务是否要覆盖

假设一个预览组件需要把前三个显示位置平移一格，最后一格允许被覆盖，这种合同可以用当前例子表达。如果需求是插入一条新记录，同时保留原来四条，就需要长度增加到五。两个任务的预期数量不同，不能因为界面都说「右移」就共用同一套断言。

也应核对移动的是显示槽位还是正式对象顺序。覆盖位置三会失去它原本引用的 D，这符合本例，却未必符合可编辑列表的要求。若用户期望 D 仍可撤销或保存，应在操作设计中保留相应数据，而不是在覆盖后才从标签文字反推原对象。

测试需要同时观察内容、身份和数量。只有长度四，可能漏掉四个 A 的污染。只有内容 A、A、B、C，可能漏掉实现偷偷新建数组，导致依赖原数组的调用者读到旧值。只有返回身份正确，又可能完全没有按预期复制。把三类预期写在同一次调用旁，失败才容易定位。

本例元素都是普通字符串，数组索引可写，没有代理或访问器引入读取副作用。对复杂对象，复制位置也不会自动深克隆元素；如果关心对象内部的编辑隔离，可另看 fill 与对象引用归属。那是元素指向什么对象的问题，当前讨论的是已有位置怎样安全覆盖。

组件接入时可以保留区间起点、结束位置和操作前成员快照，再记录调用后结果。不要执行完再从已经改变的数组构造「原始预期」。若输入来自用户选区，还要在进入方法前明确选区边界，避免把语言允许的索引转换当成产品已经批准了任何输入。

重试或再次点击也应有明确起点。同一只数组完成第一次复制后，内容已经是 A、A、B、C，再按相同区间执行一次会得到 A、A、A、B。这个结果可以符合方法规则，却不等于重现了第一次实验。因此每条独立回归都重新建立初始数组；若产品允许连续执行，则另存每轮输入和预期，不能始终套用第一轮的结果来判断。

源位置没有属性，会把目标写成 undefined 吗？

这里新增稀疏数组，且假定原型没有数字属性。源位置零本来没有属性，目标位置一则存着 B。标准算法发现源属性不存在，会删除对应目标属性。结果不是在位置一新写一个显式 undefined。

import { deepEqual } from 'node:assert/strict';
const row = [, 'B', 'C'];
const owns = index => Object.hasOwn(row, index);
const hadTarget = owns(1);
row.copyWithin(1, 0, 1);
const actual = {
  hadTarget,
  hasTarget: owns(1),
  hasLast: owns(2),
  last: row[2],
  length: row.length
};
deepEqual(actual, {
  hadTarget: true, hasTarget: false, hasLast: true, last: 'C', length: 3
});
console.log(JSON.stringify(actual));

独立脚本已执行，目标从有自身属性变为没有，末项 C 仍保留，长度仍为三。只读取位置一可能同样得到 undefined，无法证明属性是否存在，因此这里用属性存在性断言。有关缺槽与显式值的差别，可对照 flat 处理不存在的位置。
