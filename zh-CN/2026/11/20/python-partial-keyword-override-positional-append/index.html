partial 绑定 timeout 后，调用时为什么还能改掉它？

对照关键字覆盖、位置参数冲突和保存字典的修改，核对 partial 真正交给原函数的参数。

正文

核心要点

  • 调用时的同名关键字覆盖已保存值。
  • 新位置参数追加在已绑定位置之后。
  • 只读 keywords 属性引用的字典仍可修改。

工厂用 partial 给请求函数预先绑定了五秒超时，调用者再传 timeout=20，原函数最后收到二十。关键字绑定在这里提供可覆盖的默认值。若五秒是业务上限，应用还要在真正接收请求的入口校验，不能只靠创建 partial 对象时传一次参数。

创建器与调用者的参数怎样合并

假设后台任务创建一份已带任务名和超时的回调，调度器稍后才执行它。工厂负责提供常用配置，执行方则知道这次请求是否需要更长等待。对于这样的接口，后来的关键字覆盖旧值很方便。反过来，如果工厂声称它建立了一个调用方无法调整的限制，同一行为就会暴露合同错误。先写清绑定表达的是默认值还是强制约束，再选择处理方式。

partial 保存函数、位置参数元组与关键字字典。调用时，原先的位置参数排在前面，新的位置参数接在后面；关键字则合并，后传入的同名项覆盖先保存的项。这是两种不同的组合规则。不能把关键字覆盖的经验推广到位置参数，以为后来再传一个数就会改写原先的第五秒。

普通 Python 参数绑定仍在最终函数调用时进行。如果超时已经作为位置参数提供，再追加一个位置值，可能超过函数接受的参数数量；如果超时保存在关键字里，调用方又把它填到位置上，也可能产生同一个参数被赋值两次的 TypeError。错误取决于实际函数签名，例子会分别验证这两类冲突。partial 没有替函数重新设计一种可以任意覆盖的参数语言。

三种调用结果都保留独立预期

下面的 request 只返回收到的两个值。它没有执行 HTTP 请求，数字只是教学中的参数。第一组断言观察已绑定关键字如何被覆盖，两个错误调用检查位置组合。最后一组留给后面的追问，观察对象保存的关键字配置。

from functools import partial

def request(label, timeout=1):
    return label, timeout

configured = partial(request, "job", timeout=5)
assert configured() == ("job", 5)
assert configured(timeout=20) == ("job", 20)
fixed_position = partial(request, "job", 5)
for fn, values in [(fixed_position, (20,)), (configured, (20,))]:
    try:
        fn(*values)
    except TypeError:
        pass
    else:
        raise AssertionError("positional collision must fail")
configured.keywords["timeout"] = 7
assert configured() == ("job", 7)
assert configured(timeout=20) == ("job", 20)
print("keyword default overridden; positional collisions rejected; stored default updated")

正常调用拿到 job 和五，再显式传入二十，拿到 job 和二十。绑定两个位置参数的回调再接收二十，会多出第三个位置值。另一份回调虽然只绑定一个位置值，但它同时保存 timeout 关键字，后来传来的二十又占据 timeout 的位置，同样无法按这个函数签名完成调用。测试只要求 TypeError，不依赖某个版本的错误消息措辞。

这份夹具比较的是原函数实际收到的值。只查看回调的名字、字符串表示或创建时记录的配置，不能证明执行时最终采用了哪份超时。即使工厂日志里写了五秒，执行方仍可能传二十覆盖。需要诊断时，可以在应用受控范围记录生效配置及其来源，再对照真正执行入口，避免把早先的创建记录当作最终行为。

让默认值与不可覆盖约束有各自入口

若任务允许定制，就可以把 partial 当作默认配置的回调。接口说明应列出哪些关键字允许改变，调用测试也至少包含一条不覆盖和一条明确覆盖。若只测试默认路径，后来有人把关键字转为位置参数保存，普通调用仍可能通过，可定制的路径却已经改变。两条独立预期能更早发现这一类迁移。

若五秒代表最大等待时间，可以在最终执行函数里检查实际值，超过就返回明确错误。也可以用只暴露允许字段的包装函数，把受控配置留在内部。包装器需要自己定义额外关键字的拒绝方式。不能在外层删除一个 timeout 项之后，就不检查其他入口是否还能直接调用原函数。强制政策的验收要走应用真正交给调度器的对象。

例如超时限制为五的包装入口，传入二十应得到明确拒绝，默认五应到达原函数。两条预期只用于定义需要新增的验证，没有包含在当前执行夹具。

固定值也不一定意味着所有参数都必须禁止改变。任务名可能由系统分配，超时可以由执行方缩短，重试次数则可能另有上限。给这些字段分别定义允许范围，比把整个回调笼统称作冻结更容易复核。测试可以让超时取合法值、超出上限，以及缺省值，再检查每条路径实际传下去的参数。这里的回调没有实现这些业务范围，示例成功也不代表调度器已验证。

共享回调时，还应考虑不同任务是否拿着同一对象。若配置只在创建时确定，可以为独立任务创建独立对象，留下明确来源。若允许运行期间调整，需要说明调整影响哪些尚未调用的任务。样例只做顺序调用，没测试并发修改、任务队列或线程间一致性。本站的包装器与接口检查讨论工具看到的签名，这里检查的是参数真正怎样进入函数，两份证据不能互相代替。

keywords 属性只读，里面的字典也不能改吗？

属性不能被直接重新赋值，不代表它引用的字典不可修改。夹具把保存的 timeout 改成七，下一次没有覆盖的调用就得到七；调用方再传二十，仍按关键字合并得到二十。这新增了对象创建之后的变更时点。维护者如果需要原配置不受外部修改影响，应让配置所有权和暴露范围符合接口合同，而不是从只读属性推断内部内容不可变。这里仅观察这一个 partial 对象，没有声称跨线程更新有任何顺序保证。
