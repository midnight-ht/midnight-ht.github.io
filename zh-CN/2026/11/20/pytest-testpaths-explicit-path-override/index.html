配置了 pytest testpaths，为什么还能跑到目录外的测试？

用两个测试目录对照 pytest 的默认入口和显式路径，并保存真实节点身份。

正文

核心要点

  • testpaths 提供有条件的默认入口。
  • 显式路径可选择另一套测试。
  • 按节点身份核对实际覆盖集合。

配置了 testpaths，显式传入其他目录仍然可以收集那里的测试。这项设置提供的是从 rootdir 目录无显式测试路径调用时的默认搜索入口。要判断一次 CI 实际跑了哪些用例，应核对调用参数与节点清单。

例如项目默认只跑 unit，集成作业后来在命令后补了 integration。维护者以为配置是目录白名单，看到集成用例出现就怀疑 pytest 没读到配置。更直接的解释是这次命令选择了不同入口。同一个配置文件可以参与两次调用，结果的测试身份却不同。先控制参数，就能把这个问题从配置文件查找中分离出来。

一份配置，两份独立节点

新建目录，按下面关系放三份文件。不要在同一个环境里加入第三方插件或其他 conftest，实验只观察收集起点。两个断言刻意没有产品逻辑，返回通过用来方便观察运行清单，真正的 oracle 是测试节点来自哪个文件。

pytest.ini
unit/
  test_unit.py
integration/
  test_integration.py

pytest.ini 指定默认入口。

[pytest]
testpaths = unit

第一份 Python 文件放在 unit，第二份放在 integration。名字和断言内的标记不同，避免两次输出看起来像同一项测试。

def test_unit_marker():
    assert "unit" == "unit"

def test_integration_marker():
    assert "integration" == "integration"

从这份项目根目录，使用同一套已经安装 pytest 的隔离环境运行。两次只改变末尾有没有显式测试路径。分别保存完整输出与退出值，再比节点清单。

export PYTEST_DISABLE_PLUGIN_AUTOLOAD=1
python -m pytest -v -p no:cacheprovider
python -m pytest -v -p no:cacheprovider integration

本地 Python 3.11.15 与 pytest 9.0.2 上，第一趟只运行 unit 中的 test_unit_marker，第二趟只运行 integration 中的 test_integration_marker。两趟都显示同一个项目 rootdir 和 pytest.ini，都一项通过、退出零。相同的数量与成功状态无法区分它们，带路径的节点能区分。这个实测对应官方定义的默认入口条件。pytest 的 testpaths 条款

还可以在自己的环境加 --collect-only 查看收集而不运行用例，但应另存那一次结果。上面的回执已经实际执行了两项标记用例，不把纸面列出的节点冒充收集命令的实跑。若项目有插件或自定义收集器，恢复实际环境以后，还要重新核对那份最终入口的节点集合。

让 CI 说明自己选了哪个集合

CI 如果要求默认基础测试，就明确记录无显式入口的调用和当时的配置。如果它要求集成套件，则显式指定并保存对应的测试清单。把两项任务都叫“pytest 通过”，会让接手者猜不出哪一套义务完成了。特别是配置后来加了新目录，固定参数的任务和使用默认入口的任务可能不再覆盖同一集合。

先给任务列出应当出现的关键测试身份，再核对实际清单。有十项通过不说明某个关键集成用例被执行。一份任务可能误传 unit，另一份预期 integration，两个目录恰好都是十项。只比较数量会留下同样的误报。基于路径和节点的断言能把这两份结果区分开，然后再看每项的结果。不要在发现缺项后仅调低数量阈值，而应先追查入口和收集规则。

配置生效也要有相应证据。本例的输出同时给出 rootdir 与 configfile，但它们分别表示根位置与配置来源，不保证某个选择参数被使用。遇到实际结果不同，先保存完整命令，再核对配置路径、工作目录和依赖环境。如果传入的入口本来就不同，先用相同路径重跑一次，再追究配置内容。这样不会把合理的显式选择误判成配置丢失。

这个规则也不承担访问控制。能从显式路径收集另一个测试目录，并不说明可以随意读取没有权限的文件，也不会替你批准执行未知代码。仓库内哪些测试获准进入哪条流水线，应由实际任务的入口和代码信任边界决定。本文只用了两个本地固定文件，没有读取外部项目或运行服务。

收集范围确定以后，还要验证测试是否真的覆盖本次业务。两个标记的通过只证明选中的函数能执行，无法保证真实集成依赖已经连接或数据已经落盘。若任务需要设备、数据库或 provider 回执，保存对应环境准备和真实用例结果。目录选择与业务验收各有自己的观察点，不能把这个收集实验扩展成产品测试充分。

还可以把这一规则用于新增套件的评审。假设项目后来新建了一份验收目录，团队希望默认任务继续只跑单元测试，发布任务则必须增加验收用例。仅创建目录不会让固定的集成入口自动获得那份覆盖。先给发布任务增加明确的入口或调整其选集，再从回执中确认新节点出现。默认任务是否应该变化，要按它原来的合同决定。这个配置迁移情景没有执行，样例仍只有两份文件。

目录迁移也需要防止旧节点悄悄消失。把关键用例从一个目录移到另一个目录，测试内容可能不变，路径身份却改变。收集器先保存旧清单与新清单，再由评审确认这是同一个义务的迁移，或确实新增了一项。若新入口里没有对应节点，不应仅凭旧任务仍通过就结束迁移。让任务合同与节点变化一起留档，可以在以后回查某项验收从哪一版开始进入流水线。

从子目录调用，仍然使用根的 testpaths 吗？

这项默认设置还有“从 rootdir 目录执行”的条件。另一次本地运行先进入 integration，再无显式路径启动 pytest。它仍找到项目根的 pytest.ini，rootdir 也没变，但运行的是当前目录内的 integration 标记。这个新条件改变工作目录，主例始终从根执行。团队脚本如果在调用前执行过 cd，应把最终工作目录写进回执。发现根目录不等于程序从那里发起调用。
