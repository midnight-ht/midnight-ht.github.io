服务写了 /tmp 文件，宿主终端为什么读不到同一路径？

从宿主和服务分别读写同名临时标记，解释 PrivateTmp 的文件可见性与停止清理边界。

正文

核心要点

  • 相同路径名可能属于不同视图。
  • 文件回执要注明实际读取者。
  • 停止后的清理需要按视图核对。

服务和宿主都访问同一个 /tmp 路径，却可能读到不同文件。启用 PrivateTmp=yes 后，systemd 为服务设置私有临时目录视图，服务内的路径与外部进程看到的路径不再共享。先确认从哪一个视图读取，再查文件是否丢失。

这种差异会出现在启动准备里。运维人员先在宿主临时目录写好一份探针，服务随后按相同字面路径打开。终端能读到，服务却报告不存在。若只核对字符串相同，就可能反复改权限，仍然无法解决。需要先判断这两个路径是否指向同一份文件系统内容，而不是把可见性问题直接归给访问权限。

让宿主与服务各写自己的标记

下面是一份未运行的 Linux 系统服务练习。需要支持 PrivateTmp 的 systemd 和允许创建文件系统命名空间的实验环境。使用可丢弃主机，先确认指定的单元、脚本与临时文件路径没有被其他工作使用。脚本保存为 /run/zy20-private/worker.sh。它先记录自己是否能看到已有标记，再写入自己的内容，保持存活以供观察。

marker=/tmp/zy20-private-marker
if test -e "$marker"; then
  printf 'before='
  cat "$marker"
else
  printf 'before=absent\n'
fi
printf 'service-marker\n' > "$marker"
printf 'inside='
cat "$marker"
exec /bin/sleep 60

把以下定义保存到 /etc/systemd/system/zy20-private.service。脚本不需要执行权限，因为由 shell 读取，路径与解释器必须在实验机上可用。Type=exec 的启动结果不能替代脚本自己的读写标记。

[Service]
Type=exec
PrivateTmp=yes
ExecStart=/bin/sh /run/zy20-private/worker.sh

在有管理权限的宿主终端先写 host-marker，再重新加载和启动。读回时要在服务还活着的窗口内操作，并按本次启动时间核对日志。下面的脚本只表达这一轮顺序，应用前仍需先安装前两份文件。

set -eu
marker=/tmp/zy20-private-marker
printf 'host-marker\n' > "$marker"
systemctl daemon-reload
systemctl start zy20-private.service
systemctl show zy20-private.service -p ActiveState -p PrivateTmp
invocation=$(systemctl show zy20-private.service -p InvocationID --value)
test -n "$invocation"
seen=no
for attempt in $(seq 1 30); do
  if journalctl "_SYSTEMD_INVOCATION_ID=$invocation" --no-pager -o cat |
    grep -F 'inside=service-marker'; then
    seen=yes
    break
  fi
  sleep 1
done
test "$seen" = yes
test "$(cat "$marker")" = host-marker

预计服务日志先显示 before=absent，随后显示 inside=service-marker。宿主仍读到 host-marker。三条内容共同证明同一字面路径在两个视图下有不同内容。只看到服务 successfully started，尚未得到这份证据；日志没等到预期标记时，应保留原始输出和当前状态，再查脚本是否执行到对应行。本文没有 Linux 管理器运行回执，三个标记均为按配置推导的预期。systemd.exec 的 PrivateTmp 定义

路径存在的证据属于哪个读取者

真正的文件交接应说明写入者与读取者在哪里运行。如果目的就是给服务提供输入，把它放到约定的共享路径或配置目录，并核对该服务的完整文件系统视图与权限。不要因为宿主的临时文件能读，就给服务写“输入已准备”。如果目的只是服务内部临时存储，则私有视图可以符合原设计，宿主看不到同一路径也不意味着写入失败。

反过来，服务日志里读回了 service-marker，也不能用来覆盖宿主文件的内容断言。回执应明确该读数出自哪个单元、哪次启动。两个观察者写了同名标记，内容又碰巧一致时，仅比较内容还不足以证明共享；实验刻意用两个不同值，让视图差异容易判定。真实共享需求可以再给文件加入运行身份和来源记录，然后由实际消费者读取确认。

使用 PrivateTmp 也不表示服务拥有整个文件系统的隔离保证。这个设置针对临时目录，其他挂载、凭据和权限仍按各自配置生效。不要从这份样例推导服务无法访问任何宿主数据。它只验特定路径的可见性，不执行安全渗透检查，也没有证明某个应用可以在隔离下正常工作。

服务停止以后再读取，已经换了问题

手册说明，服务停止后会清理它在私有临时目录创建的文件。若脚本写完立刻退出，等操作者打开日志后再去找文件，看到的状态可能已经跨过这条生命周期边界。因此本例保留六十秒的进程窗口；它为观察留时间，并不保证主机忙时每次命令都赶得上。先看当次状态与日志时间，再解释读取结果。

宿主终端的 host-marker 是另一份文件，服务停止的私有临时清理不应被当成宿主标记清理的证明。练习后停止实验单元，撤掉本轮定义与脚本，并在宿主视图清除自己创建的标记，再重载管理器。只从一个位置发现没有文件，无法证明两边都已收尾。对于多轮验证，每轮换不同标记或保留明确的内容与启动关联，避免旧日志满足新的断言。

还可以保留一个对照，把唯一配置改成 PrivateTmp=no，在同样干净的宿主路径重新执行。预计服务先看到 host-marker，再写入后宿主也读到 service-marker。这个对照没有运行。它只改变视图共享，不能由此判断日常服务是否应该关闭隔离。先按需要交接的文件与应用合同选择，再用实际环境回执验证。

先等服务内部读回出现，再断言宿主仍保留自己的值，才能说明两个动作确实发生在这次观察中。脚本按本轮 InvocationID 过滤日志，避免上一轮同样的文字命中等待。如果服务没有到达内部写入，三十次等待后必须让检查失败，并保留该轮日志与状态。等待脚本本身未经运行；实际验收还应确认日志字段与权限在目标环境可读。这里的同轮关联用于收窄证据归属，不给日志延迟或服务完成时间作承诺。

两个服务可以共享同一份私有临时目录吗？

对普通 PrivateTmp=true，手册提供通过 JoinsNamespaceOf= 让单元加入同一个私有临时命名空间的方式，需要按相关单元配置与生命周期验证。但 PrivateTmp=disconnected 使用完全独立的 tmpfs，手册说明即使设置加入关系也不与其他单元共享。这一问加入的是第二个服务和不同模式，主例只比较宿主与一个 yes 单元，没有运行共享或 disconnected 对照。
