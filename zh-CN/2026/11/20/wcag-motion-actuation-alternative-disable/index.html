摇动撤销已有按钮，为什么还要能关闭摇动？

用撤销版本四格模型区分替代按钮与停用运动响应，给出产品复验路径和计步功能的新条件。

正文

核心要点

  • 替代组件与可关闭运动响应分别验收
  • 关闭运动后按钮路径仍需可用
  • 用独立起点检查误触是否改变内容

编辑器已经给摇动撤销加了一个按钮，坐车时却仍会误触。替代按钮解决无法摇动设备时怎样完成撤销；能够关闭运动响应，解决不想撤销时设备移动却触发命令。这两项都需要检查，不能因为同一功能已有按钮，就把关闭机制从需求里删掉。

同一个动作，有两条独立验收条件

WCAG 2.2 的成功准则2.5.4针对可以通过设备运动或用户运动操作的功能。对于这里普通的摇动撤销，它需要能够由用户界面组件操作，也需要能关闭对运动的响应，防止意外触发。本文限定这种非本质的快捷入口，不把任意传感器功能都套成同一案例。

理解文档提到，设备可能固定在支架上，也有人不能准确完成某种动作。另一些人可能因震颤而意外触发传感器输入。前一类情境需要另一条可操作路径，后一类情境需要让运动不再拥有执行该命令的作用。两个需求来自不同失败条件，因此只检查按钮存在并不完整。

替代入口还应执行同一个功能。若摇动会撤销刚才的编辑，旁边按钮却只清空全部内容，就没有建立等价操作。验收先固定当前文档版本、要撤销的那一步和撤销后的内容，再分别走两个入口。按钮文案相同，也不能代替结果一致的证据。

关闭应影响实际处理路径。设置页显示「已关闭」，但旧监听器收到动作后仍执行撤销，用户仍会遇到误触。检查要从输入进入命令的地方读到当前选择，而不只在偏好界面看一个开关颜色。如何保存偏好与跨设备同步由产品决定，不是本例假定已存在的能力。

四个本地分支检查一份内容合同

下面是教学状态模型，不读取设备传感器，不渲染按钮。每次测试都从文档v2开始，允许的撤销回到v1。来源为motion或button，关闭运动时只阻止前一种来源。来源字符串表示本地函数输入，不代表真实浏览器事件已经到达。

import { deepEqual } from 'node:assert/strict';
function createEditor(motionEnabled) {
  let documentVersion = 'v2';
  return {
    requestUndo(source) {
      if (source === 'motion' && !motionEnabled) return documentVersion;
      documentVersion = 'v1';
      return documentVersion;
    }
  };
}
const cases = [
  { motionEnabled: true, source: 'motion' },
  { motionEnabled: false, source: 'motion' },
  { motionEnabled: false, source: 'button' },
  { motionEnabled: true, source: 'button' }
];
const actual = cases.map(({ motionEnabled, source }) => {
  const editor = createEditor(motionEnabled);
  return editor.requestUndo(source);
});
deepEqual(actual, ['v1', 'v2', 'v1', 'v1']);
console.log(JSON.stringify({ cases, actual }));

完整脚本已在本地Node环境执行。四份独立实例得到v1、v2、v1、v1，与预先写出的结果一致。关闭运动的第二项保留v2，第三项仍能通过按钮入口回到v1。它证明这份本地分支模型表达了两项要求，没有证明某台设备已经正确检测或停用了动作。

每次新建实例有实际意义。若第一项已经把文档改到v1，再拿同一个实例检查关闭后保持不变，v1不变可能掩盖运动路径仍被调用。独立起点让关闭条件下是否发生修改可被看见。真实编辑器还应保留动作计数或文档版本，避免在已经没有可撤销步骤时获得假通过。

也不能只测关闭分支。按钮入口和运动开启入口都需要能到达同一结果，否则修复可能把全部撤销一起关掉。把预期写成允许与拒绝的具体内容状态，比只记录「没有报错」更能确认用户功能保留下来。

把状态模型接回实际产品

真实验收应先准备一份可恢复的测试文档，完成一项明确编辑。运动开启时走一次已定义动作，再重建相同起点，经按钮走一次。分别核对内容、当前对象和撤销层级，而不只检查短暂出现的提示。随后关闭运动响应，保持应用仍在前台并执行同样动作，文档应按需求保持不变。

接着在关闭状态下操作按钮，确认替代路径仍可完成。按钮还需要能通过所支持的输入方式到达并操作。一个不可聚焦、没有清楚名称的装饰图标，即使被鼠标点中时偶尔有效，也不足以完成这份用户路径。本文没有运行键盘、辅助技术或实际运动输入。

若应用依赖操作系统提供停用设置，应确认这个系统设置确实改变应用的运动响应。理解文档允许通过支持这样的系统设置满足要求；单凭系统里看得到相关选项，不能证明当前应用已经遵守。保存所用系统版本、设置位置与关闭前后同一动作的内容结果。

关闭机制还要覆盖设置发生变化后已经打开的编辑器。旧实例可能持有早先读到的布尔值，新页面却正常使用新选择。用同一已打开文档切换偏好再测试，有助于发现缓存状态没有更新。跨标签页或账号同步若属于产品承诺，也要分别验证，不能从一次保存成功推断所有入口已生效。

这与字符快捷键的保护条件有关联，但不能直接复用那篇的三选一规则。站内 单字符快捷键的保护条件讨论键盘字符被误当命令。本题要同时保留等价组件操作与可关闭的运动响应，各自用相应准则检查。

计步功能也必须用按钮替代每一步吗？

不按这个方式判断。这里新增运动本身构成功能所测对象的条件。理解文档把依靠设备运动计步的计步器作为本质运动例子。若不用这项运动就会使活动失去本意，可能适用准则的本质性例外，不能把普通撤销的替代方式机械套过去。

要记录为什么运动对这一功能本质，而不只是说「用了传感器」。计步和摇动发出撤销命令的职责不同。一个页面若同时有计步与摇动切换页签，还需要分别判断各项功能；某一项适用例外，不会自动为同页所有运动命令提供例外。这里依据规范说明，没有对实际计步产品作合规结论。
