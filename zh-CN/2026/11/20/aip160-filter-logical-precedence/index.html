AIP-160 的 a AND b OR c，为什么先合并 OR？

用八行真值表解释AIP筛选的OR优先级，识别会掩盖错分组的样本，并写清接口语法范围。

正文

核心要点

  • 采用AIP时OR优先于AND
  • 真值相同的样本不足以区分解析
  • 文档应清楚展示分组与匹配预期

采用 AIP-160 筛选语法时，a AND b OR c 按 a AND (b OR c) 分组，OR 比 AND 优先。若沿用 JavaScript 或其他语言里熟悉的分组，把它读成 (a AND b) OR c，就会选出另一批条目。用 a 为假、c 为真的一行，已经能让这两种理解得到相反结果。

语法来自接口合同

Google 的 AIP-160 是一份 API 筛选指导，其中 Logical Operators 明确给出这项优先级，并建议文档与示例鼓励使用显式括号。它同时说明，不应要求每个表达式必须写出显式括号。因此实现仍然需要正确处理合法的无括号输入。

这个约定有明确适用范围。看到字段叫 filter，并不能断定它采用 AIP-160；接口可能有自己的语法或只支持特定子集。先查当前服务承诺的语言，再检查实现。本文讨论采用这份指导的情况，没有把它写成所有 HTTP 查询参数的统一解释。

实现语言的布尔运算符也不能替公开语法作决定。把解析结果直接拼成某种本地表达式，再依赖宿主默认优先级，会让语法合同悄悄改变。教学脚本因此给两种分组都写了完整括号，避免读者把脚本自身的语法与被解释的接口语法混在一起。

一行就能发现错分组，八行能守住完整边界

先固定 a 为假、b 为假、c 为真。AIP 分组先算 b 或 c，结果为真，再与假的 a 合并，最终为假。另一种分组先算 a 与 b，得到假，再或上真的 c，最终为真。这一行的差别来自结合范围，三个输入没有改变。

如果只选 a 为真的输入，两种结果会相同。在这种条件下，无论先合并哪一边，都只剩 b 或 c。团队用一条「正常命中」样本验收解析器，很可能永远碰不到错误。应把能区分两种实现的输入作为明确反例保留下来。

下面的完整脚本列出三项布尔值的全部八种组合，并比较已经明确分组的两份表达式。它没有解析 AIP 筛选字符串，也没有调用任何 API。独立预期列出八对真值，最后单独核对发生差别的行号。

import { deepEqual } from 'node:assert/strict';
const inputs = [
  [false, false, false], [false, false, true],
  [false, true, false], [false, true, true],
  [true, false, false], [true, false, true],
  [true, true, false], [true, true, true]
];
const actual = inputs.map(([a, b, c]) => [
  a && (b || c),
  (a && b) || c
]);
const expected = [
  [false, false], [false, true],
  [false, false], [false, true],
  [false, false], [true, true],
  [true, true], [true, true]
];
deepEqual(actual, expected);
const differentRows = actual.flatMap(([left, right], index) =>
  left === right ? [] : [index + 1]
);
deepEqual(differentRows, [2, 4]);
console.log(JSON.stringify({ inputs, actual, differentRows }));

原样脚本已在本地 Node 执行，八行结果与预期一致。第二行和第四行有差别，都是 a 为假、c 为真，b 分别为假与真。其余六行相同。这个输出证明的是两份布尔表达式在固定输入上的差异，不能当成某个服务已经遵守 AIP 的运行回执。

这里分别计算两种解析，不把「任意一份返回真」当作接口应命中。正式端点采用哪一份，来自事先声明的合同。错误实现即使在某些输入上碰巧返回一样，也不能靠扩大样本平均一致率来替代逐项语义判断。

这里的 a、b、c 代表三项条件分别求值后的真假，不要求实际资源就有这三个字段，也没有实现字段比较或文本搜索。把它们替换为业务条件时，应先保证每项条件自身符合接口的类型和运算规则，再检查组合关系。不能把本地布尔数组当成该服务已经接受的完整查询格式。

生成日志时也要保留括号。若只记录三项条件的文字，丢掉组结构，两个本来不同的查询可能在报告里看成一行相同内容。排障人员随后很难判断用户选了哪一份关系。可以同时留原串和结构化分组，让显示格式变化时仍有可核对的来源。

把括号建议写成可检查的示例

文档可以并排展示无括号写法、其等价的显式括号和另一种有意不同的写法。为它们使用同一行数据，列出预期是否命中。这比只说「支持 AND 和 OR」更能帮助调用者理解组合条件，也能给实现回归留下固定的参考。

但不要为修复错误解析器，临时宣布所有调用者都必须加括号。如果端点原先承诺采用这份指导，合法的无括号输入也属于应处理范围。可以推荐清楚的写法，同时保留相应解析规则。若产品选择更受限的语言，应如实说明自己的合同，再安排兼容迁移。

用户界面生成筛选串时，也要把分组意图保留到字符串。可视化规则编辑器上「条件组内任一成立」和「所有组都成立」是不同层次。保存后重新打开，确认分组结构与用户看到的配置一致。只检查能发出一段字符串，不能证明界面里的组合关系被保留。

评审时保存原始筛选、解析出的分组、样本字段和值，以及最终匹配结果。对于本例，能区分错误的那两行应有固定标识，避免数据更新后反例消失。若结果变化，先确认是输入变了、规则变了，还是同一规则被实现成了另一棵树。

续页操作还需要维持原筛选合同。站内 AIP-158 的空页与续页标记讨论遍历中哪些参数可以改变。本题聚焦一份筛选内部的逻辑关系，不能从第一次结果看起来合理就断定后续沿用了同一查询。

整数字段写成 age=hello，应只返回空结果吗？

不应把它直接当成合法但没有命中。这里新增的是字段类型不匹配，而主例的布尔条件都已经合法。AIP-160 的 Validation 指出，不合规或模式无效的筛选应返回 INVALID_ARGUMENT；其中就举出整数字段与 hello 比较的无效例子。

如果服务放宽了某项筛选验证，文档需要说明差异。错误响应与空结果对调用者的含义不同，前者要求修正查询，后者表示这份有效查询没有匹配条目。上面的本地真值脚本没有实现类型校验，不能替端点证明这个新分支已经通过。
