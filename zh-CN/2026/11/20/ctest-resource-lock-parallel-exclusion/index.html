CTest 开了并行，怎样让共用一台设备的两项测试不撞车？

用原子资源标记和执行区间核对 CTest 的同名资源锁，并明确它的调度范围。

正文

核心要点

  • 同名资源锁阻止相关测试重叠。
  • 用独立区间与清理记录验收。
  • 跨作业资源仍需自己的协调合同。

给两项 CTest 测试设置同一个 RESOURCE_LOCK 名称，可以让它们在同一次并行测试调度中互斥执行。其他不使用这把锁的测试仍可并行。先把确实会争用的资源映射到共同名称，再验证两项测试的实际持有区间。

例如两个测试都要操作同一台本地模拟设备。单独运行各自通过，开启并行后偶尔互相重置状态。如果把整套测试并行度降到一，虽然可能避开冲突，也让无关工作一起等待。这里先只表达这两项的共同资源，再用受控例子检查调度器是否遵守。锁名需要由套件维护者共同约定，写成不同名字无法表达同一设备。

让资源持有有独立证据

新建目录，将下面的 Python 文件保存为 worker.py。每个测试先用原子创建目录取得同一个实验资源，持有片刻后释放。若两项真的重叠，第二次创建会失败。正常结束时另外写下起止时间，方便外层检验区间。时间来自同一台机器的单调时钟，判断相对顺序，无须假定精确耗时。

import json
from pathlib import Path
import sys
import time

root = Path(sys.argv[1])
name = sys.argv[2]
lock = root / "occupied"
lock.mkdir()
started = time.monotonic_ns()
try:
    time.sleep(0.2)
finally:
    ended = time.monotonic_ns()
    lock.rmdir()
(root / (name + ".json")).write_text(json.dumps([started, ended]))

同目录保存这份 CMakeLists.txt。项目不需要编译器，只要 Python 解释器可用。两个测试参数名称不同，资源目录相同，也写相同的锁名。

cmake_minimum_required(VERSION 3.20)
project(ResourceFixture NONE)
enable_testing()
find_package(Python3 REQUIRED COMPONENTS Interpreter)

foreach(name IN ITEMS alpha beta)
  add_test(NAME ${name} COMMAND "${Python3_EXECUTABLE}"
    "${CMAKE_CURRENT_SOURCE_DIR}/worker.py" "${CMAKE_BINARY_DIR}" "${name}")
  set_tests_properties(${name} PROPERTIES RESOURCE_LOCK device)
endforeach()

下面的脚本从该源目录运行。并行预算给二，让锁有机会发挥作用。读取两份结束记录以后，按开始时刻排序，再确认第一项的结束不晚于第二项开始。目录清理是另一条断言，防止单看用例通过遗漏残留状态。

set -eu
work=$(mktemp -d)
trap 'rm -r "$work"' EXIT
ctest --version
cmake -S . -B "$work/build"
ctest --test-dir "$work/build" -j 2 --output-on-failure
python3 - "$work/build" <<'PY'
import json
from pathlib import Path
import sys

root = Path(sys.argv[1])
windows = [json.loads((root / name).read_text()) for name in ("alpha.json", "beta.json")]
windows.sort()
assert windows[0][1] <= windows[1][0]
assert not (root / "occupied").exists()
print("nonoverlapping", windows)
PY

本地 CTest 4.2.3 与 Python 3.11.15 实际执行，两项通过，区间不重叠，资源目录已清理。脚本最后退出零。这验证了一个 CTest 调用中的命名互斥，没有连接真实设备，也没有测量测试套件提速幅度。运行器选择先执行哪项并不是本例的成功条件，两种顺序都可以满足独占。RESOURCE_LOCK 属性

锁名必须表达同一个所有者

这个机制不知道设备地址、数据库名称或文件内容。它看到的是测试声明的资源名。如果一项写 simulator，另一项写 device，即便实际操作同一件东西，调度器也没有足够信息阻止它们并行。反过来，原本使用两台独立设备却写成同名，会令本可并行的测试排队。评审时把资源真实身份、使用它的测试和公共锁名放在一起核对。

锁的范围也要写进验收。这里讨论同一次 CTest 运行的调度约束。另一个终端、另一个 CI 作业或人工操作可能仍在使用设备。需要跨进程或跨机器互斥时，由资源服务或专用协调机制提供相应合同，并在真实入口验证。不要把两项本地测试的调度结果扩大为共享实验室已经独占。原子目录在本例中是观测手段，未提供通用的远程设备锁。

对真实资源，准备与释放过程也要产生自己的证据。拿到调度机会不说明设备已经启动，命令结束不说明复位成功。可以在进入时核对设备代次和初始状态，在离开时验证它回到约定状态。若释放失败，保留测试身份与原始错误，避免下一项把残留配置当作自己的起点。本文的 finally 只删除本地标记目录，不证明任何设备复位行为。

将偶发故障转成可解释记录

先保留一次有锁配置的完整回执，再核对这次真正选中了哪两项测试。若只跑了一项，即使没有碰撞也没有验证互斥。两项都通过却缺一份时间记录，则继续查记录是否写入了预期目录，不能以套件退出零替代区间证据。使用新构建目录可以避免上一轮的 JSON 文件满足这一轮的检查。

去掉锁也不保证每次都碰撞。机器当时可能恰好顺序调度，两项持有期也可能没重叠。因此对照运行只能报告实际观测，不把一次未碰撞解释成属性无效。若要检验锁名变更后的错误路径，可以在受控环境扩大持有窗口并记录两边的进入尝试，再按真实输出判断。本文未运行无锁分支，已经运行的是完整的命名互斥样例。

如果测试在取得目录之前失败，缺少结束记录可能来自准备故障。若取得后在持有期失败，finally 在正常异常展开时仍会尝试释放。进程被直接终止则是另一个清理条件，要由实际资源的恢复策略处理。将调度、取得、使用和释放各保留一条可对应的记录，维护者才能判断该改锁名、修测试，还是恢复设备。

结束记录也不代表这项设备测试通过。工作代码可能在取得后完成了持有计时，却没有核对设备返回值。真实用例应同时断言资源操作的预期结果，再把这条结果与本轮区间绑定。若只是为了调试在 finally 写了结束时间，它可以说明何时退出保护范围，但不能吞掉原来的失败。保留测试原始结果和清理记录，才能让互斥验证与业务验证各自承担判断。

一项测试要独占整场运行，应该怎么写？

可以评估 RUN_SERIAL。它要求该项测试不与任何其他测试并行，范围比同名资源互斥更广。若测试触达难以完整列出的全局状态，独占可以符合当前约束；若只共享一个明确设备，同名锁便能保留无关测试的并行机会。这个问答新增全场独占条件，主实验没有设置 RUN_SERIAL，也没有运行相应对照。RUN_SERIAL 属性
