同一构建上下文，怎样只让其中一次 COPY 排除文件？

从同一上下文导出完整与精简文件集，验证单条 COPY 的排除范围及必须保留的输入。

正文

核心要点

  • exclude 作用在对应复制指令。
  • 同时检查必要内容和排除项。
  • 消费者要选择符合自己合同的包。

同一份 Docker 构建上下文，可以让一次 COPY 排除某类文件，另一次仍复制它们。COPY --exclude 的筛选作用在这条指令，适合从同一组输入生成不同交付集合。它不会因为一处排除就让其他复制指令失去源文件。

例如项目需要一份带说明文档的完整包，以及一份只保留运行材料的精简包。两份都以同一版本的目录为输入，区别是哪些路径进入各自产物。若直接从构建上下文删除文档，完整包也拿不到它。先决定筛选应属于输入范围，还是属于某个交付集合，再把判断写到相应步骤。

同一上下文，分别导出两份文件集

新建目录，创建 assets/app.txt 和 assets/readme.md。内容分别是一行 app-marker 与 readme-marker。保存下面的 Dockerfile。两个阶段都从 scratch 开始，避免基础镜像原本的文件影响检查。前端需要支持 exclude，官方参考将该选项的最低 Dockerfile 语法版本标为 1.19。

FROM scratch AS full
COPY assets/ /payload/

FROM scratch AS lean
COPY --exclude=*.md assets/ /payload/

从上下文根运行下列脚本，使用支持 local 导出的单平台 Buildx builder。两个阶段分别写到独立空目录。读取文件内容能识别样例身份，缺席检查则判断精简策略是否真的执行。这里的文档标记是普通教学材料，没有任何秘密值。

set -eu
work=$(mktemp -d)
trap 'rm -r "$work"' EXIT
first=app.txt
second=readme.md
docker buildx version
docker buildx build --progress=plain --target full --output "type=local,dest=$work/full" .
docker buildx build --progress=plain --target lean --output "type=local,dest=$work/lean" .
test "$(cat "$work/full/payload/$first")" = app-marker
test "$(cat "$work/full/payload/$second")" = readme-marker
test "$(cat "$work/lean/payload/$first")" = app-marker
test ! -e "$work/lean/payload/$second"
printf 'full includes app and readme; lean includes app, omits readme\n'

本地 Buildx v0.37.2 执行这两次导出，所有断言通过。full 包包含应用与说明文档，lean 包仍含相同应用内容，却没有那份说明文档。外层脚本退出零。两个阶段使用同一目录，所以 full 的正向读取也说明源文档仍然能够被另一条指令取得。实验没有运行容器、上传镜像或验证正式发布包。COPY 的排除规则

官方说明排除表达式采用与源路径一致的匹配形式，并支持对应通配规则。不要把一个根目录下的简单扩展名样例推广成所有深层目录都已筛掉。真实输入若有嵌套目录、相同名称或特殊字符，为它们列出明确预期，再检查当前前端版本产生的文件清单。这里的两份文件都在 assets 的直接下级。

先写出两种交付各自必须拥有什么

精简不只是排除项变少。运行包仍必须保留程序需要的输入，完整包则要验证自己承诺提供的说明。假设某次更新把应用配置误归为排除类型，精简结果虽然没有文档，消费者也无法工作。给两份产物各留正向内容和负向缺席断言，能发现“该少的少了，但不该少的也少了”。主脚本的 app 检查就是这一边的控制。

如果完整阶段也读不到 readme，先核对它是否确实进入上下文，再检查复制指令与匹配规则。不能因 lean 没有它就认定局部排除生效。比如构建采用了另一份预先裁剪的输入，两个阶段都会少同一个文件。把源输入身份和 full 正向结果放在一起，才能排除这条解释。正式任务里还应记录使用的 Dockerfile 与上下文根，免得两趟导出来自不同目录。

将这套检查接到下游时，选择消费者实际收到的根路径。全局搜索到 app-marker 不足以说明精简包正确，它可能来自前一轮输出或完整阶段。使用新的导出目录，并将每一份包的清单与对应阶段名关联。若后面还有压缩、签名或拷贝，接收端应从最终结果读回必要文件，确认交接过程没有改变集合。

文件没进入这条 COPY，不等于没进入构建

局部排除解决的是这份复制结果的范围。源文件仍能被其他指令取得，正是主例 full 可以复制它的原因。因此不能拿 lean 中的缺席作为上下文未包含该文件的证明。如果目标是不要把某类本地文件作为构建输入，需要按上下文筛选规则另行处理，并验证实际入口。不能把一次输出筛选当作秘密清理或历史撤回的回执。

另一方面，输入范围正确也不自动证明输出范围正确。构建步骤可以另外生成文件，其他阶段也可能加入内容。评审时沿着真正选中的目标看最终文件集。样例两个独立阶段没有运行命令，只复制已知标记；它不能外推到会下载资料或生成调试文件的实际项目。

为变更排除模式留一个可复核的差异也有帮助。先保存旧模式下的集合和每项必要文件，再改一个模式，核对预期受影响的成员是否正好变化。如果一次扩大规则导致另一项必要文件消失，应让交付检查失败，保留相对路径与源输入。不要为了让清单变短而把缺失要求从验收中删掉。

团队允许两种交付并存时，还要给消费者写清选择哪一种。某个接收流程要求离线说明，发送精简包就违反合同，哪怕这个包完全符合自己的 lean 定义。把包种类、目标阶段和消费者需求关联起来，能让维护者判断是构建错了，还是交接选错了包。这个真实消费流程未执行，本文只验证两份本地导出的集合差异。

多条 exclude 是后面的覆盖前面，还是一起生效？

同一条 COPY 可以重复指定 exclude，匹配其中任意模式的路径都会被排除。另一个独立本地样例增加 scratch.tmp，再用 COPY --exclude=*.md --exclude=*.tmp assets/ /payload/。导出后 app 内容仍正确，readme 和 scratch 两项都缺席，读取断言通过。它给主例增加的是第二类筛选条件，不能解释成最后一个模式覆盖了第一个。
