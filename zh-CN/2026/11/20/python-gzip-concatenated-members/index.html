两个 gzip 字节串接起来，解压为什么得到两段内容？

对照两段 gzip 的独立恢复、拼接恢复和后半 CRC 错误，核对完整字节与单成员替代入口的条件。

正文

核心要点

  • 该 gzip 解压入口支持连续多个成员。
  • 完整结果检查应覆盖后半成员的身份与内容。
  • zlib 的单成员替代入口需要明确成员数前提。

两份独立压缩的 gzip 数据直接拼在一起，gzip.decompress 会解出两段内容。它支持多 member 输入。接收方如果只检查解压结果以第一段开头，就可能漏掉后半段丢失的问题；验收应该比较完整解压字节，再按业务格式解释这些字节。

压缩边界为什么可以连续出现

假设导出器先把 A 加换行压成一份 gzip，再把 B 加换行压成另一份。两个压缩结果各有自己的成员结构，把它们依次放在同一个输入字节串里，便形成多成员输入。Python 文档明确说明 decompress 可以处理多个连续的 gzip member，因此看到第二段内容属于这个接口支持的行为。

这和把两个压缩前的数据先接起来再统一压缩，都可能恢复出 A 换行 B 换行，但压缩输入并不一定逐字节相同。本文只核对恢复结果，不比较压缩文件是否相等，也不从两个字符串看起来相同推断压缩结构相同。实际交付若还需要摘要或文件身份，应按自己约定的对象另外校验。

成员数量也不能直接替代记录数量。一份成员可以包含多条记录，也可能只包含半条业务记录。比如第一段以一个字段的前半部分结尾，第二段继续该字段，压缩层依旧只负责还原字节。真正的记录边界要在还原后由文本协议、CSV 或其他格式来解释。这个样例有意用换行作很简单的可见标记，不实现通用文件解析器。

让第二个成员有自己的成功和失败证据

夹具分别压缩两段固定字节，再验证单段和拼接结果。mtime 显式设为零，让创建时间不参与这份教学压缩数据。坏样本只翻转第二个成员尾部 CRC 的一位，其他部分保持不变，方便把拒绝归到后半成员的校验。

import gzip
import zlib

inflate = gzip.decompress

first = gzip.compress(b"A\n", mtime=0)
second = gzip.compress(b"B\n", mtime=0)
assert inflate(first) == b"A\n"
assert inflate(second) == b"B\n"
joined = first + second
assert inflate(joined) == b"A\nB\n"
assert zlib.decompress(first, wbits=31) == b"A\n"
damaged = bytearray(second)
damaged[-8] ^= 1
try:
    inflate(first + damaged)
except gzip.BadGzipFile:
    pass
else:
    raise AssertionError("second member CRC corruption must fail")
print("both members restored; damaged second CRC rejected; single-member control passed")

前两条正向控制确认两段各自还原为 A 换行与 B 换行。拼接后必须恰好还原 A 换行 B 换行。只断言开头有 A 的版本，会让丢掉第二段的实现也通过。完整输出检查则能同时发现遗漏、顺序变化和意外增加内容。对实际业务文件，可以选择两个不同且稳定的标识，避免两段内容相同导致顺序错误不容易被察觉。

坏样本的预期是报错，不能把第一段已可还原当成整份输入可接受。一次完整调用没有成功返回，就不应该给下游补造一份“已验证的前半文件”。流式消费时，应用可能已经把早先内容交出去，因此还需定义是否允许部分结果以及失败后怎么处置。当前夹具使用一次性字节接口，没有提前对外写出任何内容，也没模拟数据库回滚或文件发布。

示例里的 CRC 破坏属于受控错误输入。它验证了这一次第二成员损坏时当前库会拒绝，没有验证任意格式损坏都抛同一异常。库文档也列出无效输入可能产生其他解压错误。错误处理入口应按支持的输入和策略设计，不能捕获所有异常后统一返回空文件，否则空输出会掩盖原来应拒绝的数据。

先确认消费者需要整份文件还是可逐步处理

对于短小、有明确大小界的消息，一次性 decompress 后比较完整内容通常容易理解。如果输入可能很大，完整恢复数据本身要占用内存，是否使用文件式或逐步读取需要按资源条件决定。文档描述了新版本一次性处理成员的变化，不能把这一点转写为任何机器都有足够内存的承诺。本文没有测量内存、压缩率或吞吐。

把这项检查放进导入流程时，可以先在隔离范围恢复，再检查格式与预期标识，最后才交付消费者。若数据允许在第一条记录还原后就写入，验收需要专门构造后半成员坏掉的样本，确认前面已经写入的状态如何报告和恢复。这个选择会影响业务的一致性，压缩函数没有替应用决定。

本站的压缩表示与内容摘要讨论摘要究竟针对哪份表示。当前例子先回答多成员如何恢复内容，两者可能在同一接收链路上分别检查。摘要正确并不替代记录语法；解压出完整内容也不会自动证明来源就是批准的导出批次。可复核记录应保存实际收到的对象身份、采用的恢复入口及完整内容检查结果。

还应测试尾部成员真的到了接收端。假设传输日志只记第一段长度，却把发送端的完整文件拿来解压作为回执，程序会正确恢复两段，但没有验证接收端。验收必须从目标实际保存的字节开始，至少核对一个只存在于第二段的标识。本文的拼接输入直接在本进程中创建，证明范围限于本地字节函数，不包含真实传输。

确认只有一个成员时，可以用 zlib 的入口吗？

Python 的 gzip 文档指出，确定数据只有一个成员时，可以用 zlib.decompress 并设置 wbits=31；这是有明确前提的替代入口。夹具用第一份单成员作为正向控制，要求还原同样的 A 换行。不能因为这个控制通过，就把它推广到这里的多成员拼接输入。若入口无法保证成员数，继续选择明确支持多成员的路径，或另外实现并验证完整读取策略。本文没有给出性能对比，也没有以单成员的成功替代后半成员的检查。
