PostgreSQL COPY 跳过了坏行，为什么第二条坏值又让整次失败？

用一条与两条整数转换错误对照 PostgreSQL COPY 的跳过预算和命令失败。

正文

核心要点

  • ignore 适用于转换错误。
  • 超过拒绝预算时，命令仍失败。
  • 需分别核对接受行和失败后的目标。

PostgreSQL 的 COPY FROM 开启 ON_ERROR ignore 后，可以跳过输入值无法转换为列类型的行。再设置 REJECT_LIMIT 以后，超过预算仍会让本次命令失败。要验收部分导入，应分别检查保留下来的记录和超限后目标的可见状态。

设想库存导入的数量列要求整数，文件里偶尔出现一个非数字值。安全的容错政策可能允许丢掉一条，并要求操作员根据来源标识修正它。如果第二条坏值出现，业务希望暂停整批，而不是默默接受更多缺口。一次忽略设置和一个拒绝预算分别定义了这两段行为。排查时先确定报错属于哪一项，再确认本次导入是否还能产生可用结果。

先界定可以跳过的错误

PostgreSQL 十八版文档把 ON_ERROR ignore 描述为适用于文本和 CSV 的 COPY FROM 输入转换。若输入中某列不能转换成指定类型，这一行可被丢弃。REJECT_LIMIT 只与 ignore 配合使用，需要正的整数预算。超过它以后，COPY 仍失败。省略此上限时，转换错误可继续被跳过。把这个设置描述成忽略一切坏数据，会把约束、结构或其它阶段的错误混在一起。PostgreSQL 18 COPY 文档。

使用预算时还需定义统计口径。这里的样本每条坏行只放一个转换错误，避免将本例解释成一行有多个问题时如何逐项计数。导入后应使用源行标识对照实际写入的集合。只看已复制条数可能漏掉错误地保留了别的记录；只保存跳过数字，也不能给上游足够信息修正原值。

在同一预算上放一条、再放两条坏值

以下是未执行的 PostgreSQL 十八版教学脚本。用独立测试库和 psql 会话，启用默认自动提交，允许预期失败后的下一条查询继续执行。如果当前客户端遇到错误会直接停止，应分别提交两组 COPY，并在失败后单独发出最后的计数。反斜杠与点作为内联输入的结束标记，只供这里的 psql 入口使用。两个目标最初为空。

CREATE TEMP TABLE one_bad (id int, quantity int);
CREATE TEMP TABLE two_bad (LIKE one_bad);

COPY one_bad FROM STDIN WITH
  (FORMAT csv, ON_ERROR ignore, REJECT_LIMIT 1);
1,10
2,bad
3,30
\.
TABLE one_bad ORDER BY id;

COPY two_bad FROM STDIN WITH
  (FORMAT csv, ON_ERROR ignore, REJECT_LIMIT 1);
1,10
2,bad
3,30
4,worse
\.
SELECT count(*) FROM two_bad;

第一份输入只有编号二的数量无法转成整数，跳过后预期看到编号一和三，对应数量十和三十。第二份在相同输入末尾加入编号四及另一份坏数量。编号二随后还有可转换的三，这有助于看出失败点不是遇到第一条错行便停止。超限后应记录实际错误，再检查第二个目标的可见行数为零。失败前候选记录一与三不能当作已交付结果。此处特意采用独立自动提交的语句，若改为显式事务，需先处理失败事务再读取目标。

实际部署中，转换失败被跳过时可从配置允许的通知观察行数，但通知不是最终行集合的替代物。对第一份样本，可以保留数据库结果、导入工具获得的状态以及实际写入的编号。对第二份样本，还要核对没有把失败请求的先前进度写成成功通知。这些接口观察未运行。站内的 CSV 空值与引号 解释输入值怎样被解释，本篇把坏值限定为一个能够明确触发整数转换错误的字符串。

给部分成功和整次失败不同出口

如果产品允许少量异常，调用方可以对接受列表作独立核对，并给需要修改的源行保留稳定身份。重新上传时，应先决定只补失败行还是重放整份。若把已接受的行和新修好的行一起交给缺少重复处理政策的导入，可能得到不同于首次的结果。验收可以为初次文件和修复文件各选一条稳定记录并核对最终归属。此例没有实现重试或去重。

另一种产品选择是任何一项出错都停止。这样可以不启用容错，要求发送方修正后再提交。部分容错并不节省对业务完整性的验证。如果恢复工具最后只比较一列计数，仍可能把编号丢失误认为允许跳过。独立保留预期全部输入、可接受输出和拒绝理由，更便于决定是否发布导入结果。

还可以给读取器一份没有任何坏值的基线。同一预算下，所有合法编号都应出现，不能因为应用总打算剔除某个编号就把样本偶然写成通过。真正的部署验收应保存客户端版本、选项及错误后连接状态，并从预期的表检查记录。这里没有验证其它驱动如何转发 COPY 输入、如何交付通知或如何重开连接。

若导入任务由两个组件协作，还应核对谁把数据库结果翻译成产品状态。可以让写入端返回“接受两条、跳过一条”，检查应用把这些编号与待修正来源对应起来。再让独立的超限样本返回错误，确认任务读取端没有沿用上一轮成功摘要。若服务缓存了进度，回归还要检查失败后的最终状态会替换进度提示，而不是仅出现在后台日志中。此处没有测试通知传递，也不假定所有驱动能提供相同的通知格式。面向操作员的报告应以经过目标检查的结果为准。

数据可以转成整数，但违反 CHECK，也会被跳过吗？

转换成功不属于前述忽略条件。可另建表要求 quantity 大于零，再用负一作为 CSV 数量。它能转成整数，却会触发约束；应独立检查 COPY 失败并确认目标没有这次导入的可见记录。不要把这次拒绝拿去解释前两条非数字错误的预算。这个约束变体未执行，主例只给出输入转换的预期。
