HTTP 203 是失败吗？先核对响应经过的转换代理

对照源站 200 目录与代理 203 视图，确认成功响应经过了哪条路径，以及哪一份内容可用于后续验证。

正文

核心要点

  • 203 表示成功且源站内容经过转换
  • 状态码不能描述具体修改
  • 后续验证需要保留请求路径

目录服务在源站返回两条记录。经过团队自己配置的目录代理，客户端只收到其中一条，响应状态是 HTTP 203。请求已经成功，内容却与直接读取源站时不同。排查时先保留响应走过的路径，再查看是哪一层执行了转换。只按状态码把它列为失败，会漏掉这次交付记录。

203 记录转换发生在成功响应上

RFC 9110 用 203 表示一种成功响应。转换代理修改了原来自源站的 200 响应内容，并可以用 203 告诉接收方发生了这件事。它落在成功类里，并未声明源站处理失败。也不能因为同一地址直接读取有两条数据，就把代理交付的一条记录写成网络丢失。

假设产品维护一个测试目录，源站返回 A 和 B。团队有一条只为展示选定记录而设的内部路径。通过这条路径时，代理应用明确允许的规则，保留 A，省去 B。源站没有收到删除命令，目录内容依旧有两条。差异发生在这次响应的交付路径上。

203 在这里提供的是转换已经发生的信息。仅看它，无法知道被调整了什么。需要解释具体内容变化时，应回看代理自己的规则或保存两侧证据。也不能把没有看到 203 当成没有转换的证明。规范允许这样的代理使用 203，使用此状态不是所有转换响应必经的步骤。

这里讨论的是语义上有意义的内容修改。代理转发消息时可能做常规协议处理，即使线上编码或传输分帧不同，也不能据此断定应用目录已经改变。判定这次目录转换，应对照源内容和下游实际收到的数据，而不是以字节编码有没有变作为唯一条件。

用两份固定回执确认实际收到什么

下列脚本只模拟一条允许转换的内部路径。数据固定为 A 和 B，目录视图的条件固定为只展示 A，代码为这个例子选择 203。它保存源站与代理的两份回执，没有启动 HTTP 服务器，也不会转发任何真实响应。用本机运行只能确认这份局部模型的结果。

import {deepEqual} from 'node:assert/strict';

const origin = {
  route: 'origin',
  status: 200,
  content: ['A', 'B'],
};

function projectCatalog(reply) {
  const content = reply.content.filter(id => id === 'A');
  return {route: 'catalog view proxy', status: 203, content};
}

const result = projectCatalog(origin);
deepEqual([origin, result], [
  {route: 'origin', status: 200, content: ['A', 'B']},
  {route: 'catalog view proxy', status: 203, content: ['A']},
]);
console.log('Catalog receipts match both expected routes.');

实际通过的断言分别核对了两份回执。直接路径仍是 200 且有 A 和 B，视图路径是 203 且只有 A。测试同时检查状态和内容，避免应用代码只是改了状态并没有产生视图，或确实改了内容却把回执误记为直连。这里得出的差异属于固定夹具，不证明线上有一个代理真的部署了这些规则。

若客户端只存一份响应体，下一次从不同路径读取，会难以判断变动来自源数据还是视图。比如用户昨天通过代理见到 A，今天直接浏览源地址见到 A 和 B。直接读多出 B，不足以判断 B 是今天新增的。先记录这两次的路径，才有条件把内容归属查清楚。

规范提到后续对内容的验证可能仅适用于相同请求路径。应用可以为直接读取和经过转换的响应分别保留来源与验证信息。若必须比较两边的数据，也要知道要验证的是源站内容，还是产品实际交给用户的那一层内容。不要拿前一次视图的验证结果，直接替今天另一条路上的内容背书。

编辑客户端如何承接这类响应

API 客户端若目前只把精确的 200 归入成功，应检查这是不是自身契约有意收窄，或者只是遗漏其他成功状态。对支持代理视图的入口，可以先把收到的内容交给成功处理，然后再保留转换状态供日志与后续决策使用。现实应用仍应按每个端点的契约确认自己有没有处理 203 所需的数据。

对于目录例子，验收可以对照用户实际看到的项目与内部日志。用户应读到视图中的 A，日志应该能追到这次走过的路径。若看到客户端报网络失败，应检查是不是把 203 排在成功分支外。若显示了 B，应检查实际拿到的结果是来自源站还是转换后的代理。

如果产品对比两条路径，选择同一时刻的固定数据更容易定位。例如两边都以测试目录 A 和 B 为输入，再比较接收回执。若分别在不同时间创建、更新数据，即便代理规则未改，结果也可能不同。保存场景约定、请求路径与数据版本，比考察一次截图更接近有效对照。

排查资料可以只写业务记录编号与当前路径，不必存下整个目录响应。需要再现时，用相同输入重新生成回执。对于这个例子，证明两条路径有不同内容，只需保留展示规则依据以及两边各有哪些编号。

源站响应带 no-transform，还可以转换后返回 203 吗？

不可以。给主例新增这个限制后，代理不能再按展示规则从该响应中删掉 B。RFC 9110 对带 no-transform 的响应约束的是转换行为。选择 203 只可能报告允许发生的变换，不能解除这个指令。若业务需要为展示生成另一种内容，应在允许的来源或独立表示上实现它。

验收时，先确认源站响应确实带着该限制，再检查代理有没有执行内容规则。主例中固定的两条源记录于是成了一条可复查的负例：本轮预期仍交付 A 和 B，不应凭改了状态来掩盖已发生的内容转换。这个变体是规范预期，脚本只运行了先前允许转换的一轮。

如果需要核对完整表示与某次响应的内容字节，可另看Content-Digest 与 Repr-Digest 分别校验什么。
