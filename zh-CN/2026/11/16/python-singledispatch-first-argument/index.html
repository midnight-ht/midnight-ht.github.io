Python 标了两种类型，singledispatch 为什么没选第二种处理器？

用四条实际调用核对 singledispatch 的第一参数分发、默认实现与第二个输入的处理。

正文

核心要点

  • 分发使用第一个实参的类型。
  • 后续参数可由实现自行处理。
  • 为默认实现和继承路径留下独立对照。

Python 的 singledispatch 只根据第一个实参的类型选择实现。给第二个参数加上类型注解，或者调用时换掉第二个值的类型，都不会使它参与这次分发。需要按两个输入选择行为时，应令第二个判断在代码中可见。

假设库存导出器接受商品编号和输出方式。工程师给整数编号和字符串编号分别写了处理器，又给每个处理器的输出参数标类型。他以为传入一个整数形式的输出选项会切换到另一个实现。实际仍走整数编号的处理器。定位时先检查真正传给泛型函数的第一个位置，不要从整个参数表里搜一个看起来匹配的注解。

注册与调用各自用了什么

标准库文档约定 singledispatch 调用时读取第一个参数的类型。用带注解的函数注册实现时，装饰器也可以从第一个参数自动推断注册类型。函数其余部分仍可以读取别的实参并自行判断。示例让对应的处理器直接返回分支标签，避免把输出格式化或输入转换误认作分发效果。Python functools 文档。

另外，装饰的原函数注册给 object。没有更合适的实现时它会接收输入。真实程序应定义默认实现是否能处理未知数据，或者应明确拒绝。若产品只支持两种记录类型，默认分支可以返回可辨认的错误。碰巧返回一串可以打印的文本，并不足以证明这条输入本来受支持。例子使用简单的标签只为了把默认路径留在观察结果里。

用四次调用区分两个位置

以下标准库程序在 Python 3.11.15 本地运行。第一项和第二项使用完全相同的整数记录，只更换第二个参数。第三项改用字符串记录，同时继续使用整数选项。最后让第一个参数是没有专用注册的对象。四条输入分别承担两种不变性检查和两个切换检查。

from functools import singledispatch

@singledispatch
def route(record, output):
    return "base"

@route.register
def number(record: int, output: str):
    return "integer"

@route.register
def text(record: str, output: int):
    return "text"

inputs = [(4, "json"), (4, 0), ("4", 0), (object(), "json")]
actual = [route(record, target) for record, target in inputs]
assert actual == ["integer", "integer", "text", "base"], actual
print(actual)

输出实际依次为 integer、integer、text、base。第二次调用的 output 为整数，但仍通过整数记录的实现。这里的直接类型注解没有被 Python 当作运行期参数验证器。处理器没有使用第二个参数的具体功能，所以这两次运行都可以返回选中的名字。实际处理器若随后对该参数执行不适用的操作，可能在被选中以后失败。要诊断它，先核对选中了哪个实现，再检查实现接受什么数据。

测试也可以准备一个同值、不同类型的例子，比如整数四与字符串四。界面可能把两者打印成一样，但它们走的分支不同。保存预期时应保留实际的输入类型。一个只在日志里检查字符四的测试，会漏掉前一层已将编号转成字符串的情况。若处理器使用了转换后的编号，还应独立记录转换发生位置，避免把固定样本的类型行为外推到真实接口。主例没有启动导出器或访问库存数据。

两个输入都影响结果时，把两个决定各自表达

可以先按记录种类选出一个处理器，再由处理器根据明确的输出格式选择序列化方式。记录类型有新增分支时，格式约定可以被同一组测试复用。另一种方式是在业务入口构造同时包含种类和格式的策略键，用一张明确映射寻找实现。此时应管好无法匹配的组合，不要因为所有种类各有一个有效格式，就推断所有组合都已受支持。

举一个可单独验收的矩阵。整数编号可输出 JSON 或文本，字符串编号只允许文本。给三个允许组合写下可交付结果，再给字符串编号加 JSON 格式，预期进入明确的拒绝分支。若只断言两个编号类型分别找得到处理器，第四种组合根本没有验证。这个矩阵是未执行的应用验收设计。本站的 Pydantic 内层实例复验 讨论已有对象参与校验的另一条机制；类型分发先决定谁会接手，后续仍需各自验证。

若默认路径要兼容以前没有注册的第三种记录，还要保存一条旧输入的对照。加入新处理器后，不只检查新增类型是否成功，也要核对旧的默认输入是否仍落在原来的出口。单纯统计命中次数容易掩盖哪个槽位错了。尤其在拦截器或包装层先改变第一个参数时，应通过真正的入口送入同一数据，观察到达泛型函数的实际值。本例没有执行包装层。

还可给函数接口的演进加一项检查。若团队移动了参数位置，让输出方式成了第一项，现有注册和默认分支的含义会一起改变。应先审查调用点，再用两个位置都刻意可辨的样本核对迁移结果。还原函数签名不能替真正调用者证明兼容。

验收包装器时可以把整数四与字符串四分别送到正常入口，再记录包装后的分支标签。若业务要求保留编号原来的类型，两个标签就应当不同；若包装器明确定义统一转成字符串，则应改变这份预期。这个入口对照未运行。

没给子类单独注册，仍会选择父类吗？

文档规定，没有某个具体类型的注册时，会沿相应的方法解析顺序寻找更通用的实现。比如 bool 是 int 的子类，在此示例没有注册 bool 的条件下，另传一个 True 预期进入整数分支。如果产品要对布尔值使用专门入口，可以独立注册，再对照整数四与 True 的分支。这个额外的继承控制未运行，主程序只验证直接注册和 object 默认。
