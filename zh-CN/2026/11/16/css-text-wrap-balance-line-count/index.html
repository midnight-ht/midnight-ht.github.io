text-wrap: balance 会让短标题多占一行吗？

同宽同字的标题分别用普通和均衡换行，按 CSS Text 4 草案验证短标题行数，再检查变化的断点。

正文

核心要点

  • 短标题以同样输入的普通换行为基线
  • 普通排版不超过五行时均衡不改变行数
  • 具体软断点依赖浏览器排版算法

团队给卡片标题加上 text-wrap: balance，想避免最后一行只剩一个词。做样式回归时，更适合比较两件事：同一句标题在同宽的盒子里是否占了更多行，浏览器是否选择了不同的断点。第一件事有短标题的规范条件，第二件事仍会随排版算法而变化。

短标题可以锁住行数，不能锁住每个断点

CSS Text Level 4 的编辑草案要求，balance 在能够比 auto 排得更均衡时，选择能让各个行盒剩余空间分布更匀的软断点。如果普通排版只有五行或更少，就不得改变普通排版会得到的行盒数量。测量标题时，需要先确认对照组确实在这个行数范围内。

这里说的均衡针对行盒里的剩余空间。标题宽度、字体和字形都能改变原本的剩余量。排版可把原先行末的词放到下一行，让两行之间的宽度不再差得那么多。标题也可能已经排得适合，启用后维持原有断点。测试不应把必须改变断点写成通过条件。

草案把准确的断点算法留给用户代理。在同一种语言和字体下，两个实现仍可能选择不同的断行方式。固定某一行必须以某个词结尾，只能描述当前运行环境的一张截图。短标题较强的共同条件是和该环境自己的普通排版对照时行数保持一致。

这个约束也不能直接用来给整篇正文设定验收。标题样本超过五行时，本文使用的行数断言不再适用。产品可以为短标题设置宽度范围，对溢出和可读性作自己的限制。即使浏览器能计算均衡排版，也不能凭它推断所有卡片在不同文案中都保持同高。

对照里只改变换行策略

下面两个标题文本、宽度、字号和行高相同。使用普通等宽字体族和显式行高，让对照页面直接用盒高除以行高得到行数。页面没有为标题额外设置内边距、边框、裁剪或固定高度。使用这种测量方法时，盒高应随实际行盒数量变化。

<!doctype html>
<meta charset="utf-8">
<title>Heading wrap comparison</title>
<style>
  h2 { width: 20ch; font: 20px/24px monospace; margin: 0 0 1rem; }
  #ordinary { text-wrap: auto; }
  #balanced { text-wrap: balance; }
</style>
<h2 id="ordinary">Small teams set a steady pace for shared work</h2>
<h2 id="balanced">Small teams set a steady pace for shared work</h2>
<output id="result"></output>
<script>
const byId = document.getElementById.bind(document);
const height = element => element.getBoundingClientRect().height;
const lineCount = id => height(byId(id)) / 24;
const support = CSS.supports('text-wrap', 'balance');
const values = [support, lineCount('ordinary'), lineCount('balanced')];
const result = byId('result');
result.textContent = ['supported, auto, balance:', ...values].join(' ');
</script>

打开页面后，先检查 supported 是否为 true。若为 false，同样的行数可能只是浏览器没有应用新样式。再读两个数字，auto 是基线，balance 是比较项。在样本的普通排版得到一到五行时，按草案预期，两个读数应相等。视觉上可以同时看是否发生了重新分配，只记录看到的断点，不给它们一个跨浏览器固定答案。

这仍然是规范与夹具推导。文章没有实际运行浏览器，未产生截图或兼容性结论。若实际读数不整齐，应先检查浏览器是否应用了显式行高，有没有额外内容挤进盒子，或项目打包流程是否覆盖了样式。盒高除法只适用于当前这个受控布局。

如果你把测量搬到产品卡片，保持两份标题都在文档中、可参与布局。隐藏测量副本时尤其小心，完全不参与布局的元素给不出这类对照。换字体后也该重测，不能用加载前的自动行数给加载后的均衡模式做基线。先等两边都使用同一套字体，再比较。

将组件测试放回自己的可用宽度里

测试窄卡片时可以找一个配置让普通标题稳定地排成三行。改变换行规则后再次读取实际行数，并记录是否依然能读全标题。把三行的预期落到这句固定文本与这个卡片宽度上。当设计调整宽度时，先重测普通模式，避免理论三行被当成运行现实。

同一对照还可以用翻译后的标题。字符串变了，合法断点分布也会变。每个语言版本分别以自己的普通模式为基线。拿中文的均衡标题和英文的普通标题比行数，无法判断变化来自样式还是文案。报告里保留语言、字体、宽度和两组行数，查起来更快。

有时产品需要的是让不同行数的卡片底部对齐。这个需求和短标题的均衡规则可以同时存在。先分别验收标题内部的断行与外部布局，确认哪一处影响卡片高度。若整个卡片固定为相同高度，就不能再从卡片外框推断标题是否多了一行。

若项目还加了行数截断，第一次诊断可以把截断和均衡分别开关，先找出额外样式如何干预可见高度。当前夹具没有截断，因此测出来的高度可以代表每个实际行盒。完整版组件有时只让读者看到标题的一部分，这时必须另检查可见的文本是否足以识别卡片内容。行数相等是一条布局检查，不能替代标题信息仍然可读的检查。

标题中间加了 br，两段还会一起均衡吗？

不会合成一个可跨越的组。新条件是作者在两部分之间插入强制换行。草案将被强制换行分开的行组分别处理。浏览器仍可在每个组内部挑选软断点，但不能为了全标题更匀就跨过作者设定的硬边界。

这适合用在确实存在命名层次的标题，例如项目代号必须单独成行。若硬换行只是为了修一张截图上的断点，把它复制到更窄或其他语言的标题可能打碎原来流畅的文字。验收硬换行场景时，先确认边界依旧存在，再分别观察各组内部的软断行。

若你的测试涉及布局跳过之后内容还能否被查找，可另看离屏章节的查找与键盘行为。
