同一 Docker 构建导出，为什么多平台多了一层目录？

用固定的平台标记比较 BuildKit local 导出的分目录和合并布局。

正文

核心要点

  • 多平台默认各有目录。
  • 合并布局须保持平台文件名可辨认。
  • 验收路径与内容，不以构建完成代替。

BuildKit 的 local 导出器默认给多个目标平台各建目录，单平台默认直接写入目标目录。把原来的单平台发布改成多平台后，消费者常需要调整自己读取文件的位置。

打包维护者原本从某个输出目录直接读取制品，后来增加一个平台。构建仍然完成，但上传任务报告找不到文件。先查看导出器实际写了哪些相对路径，再决定是让消费者接收平台目录还是显式要求一个平铺布局。若直接改上传端去全树搜索同名文件，很可能在下一次构建中读到另一个平台的制品，却仍然留下成功回执。

先把平台和文件名各自固定

Docker 的本地与归档导出器说明指出，local 导出器可以用 platform-split 控制多平台布局。默认情况下，它为两个目标平台分别创建子目录。设置为 false 后，平台输出合到同一个目标目录。即使所有步骤返回成功，目录结构仍会按这个选项不同而变化。下面只讨论 local 导出器，不用它推定 tar、镜像仓库或本地镜像存储的回执。

完整教学文件使用构建节点的平台执行 shell 命令，再利用目标平台参数生成不同文件名及内容。这样可以验证导出路径，无需假装已经交叉编译了可执行文件。最终的 scratch 阶段只带这份标记。保存为独立目录里的 Dockerfile，使用能够接受两个目标平台和 local 导出的 BuildKit 实例。此例没有运行，也没有连接构建器。

# syntax=docker/dockerfile:1
FROM --platform=$BUILDPLATFORM alpine:3.22 AS make_marker
ARG TARGETOS
ARG TARGETARCH
RUN mkdir /out && printf '%s/%s\n' "$TARGETOS" "$TARGETARCH" \
    > "/out/marker-$TARGETOS-$TARGETARCH"
FROM scratch
COPY --from=make_marker /out/ /

使用同一构建器，并让两个命令写入不同的、初始为空的目录。先运行默认导出，再执行显式合并。两个命令都要求相同的目标平台列表。

platforms=linux/amd64,linux/arm64
docker buildx build --platform "$platforms" --output type=local,dest=./split .
docker buildx build --platform "$platforms" \
  --output type=local,dest=./flat,platform-split=false .
布局 应出现的相对路径 文件内容
默认 split/linux_amd64/marker-linux-amd64 linux/amd64
默认 split/linux_arm64/marker-linux-arm64 linux/arm64
合并 flat/marker-linux-amd64 linux/amd64
合并 flat/marker-linux-arm64 linux/arm64

表格是根据文档写出的预期，不是已观察的输出。可从操作记录核对所选 builder，再列出两个目录中各自的文件，用内容确认没有把一个平台写成另一个。若只查数量，两份内容都写错的平台仍有机会通过。若只查找到一份叫 marker 的文件，实际映射关系也无法确认。用全量相对路径和指定内容两个断言，能够把布局错误与平台参数传递错误分开。

按下游读取合同选布局

如果消费者会逐平台领取制品，默认分目录提供清楚的定位入口。发布清单可以把平台键和相对路径一一对应，调用方不必猜新平台的文件名。若现有消费者只能读取一层目录，则可以使用平铺布局，并让各平台产物拥有明确不同的名字。这里不会承诺两个平台使用相同输出名字时能安全合并。应先改名或保留拆分，避免由目录搜索结果决定归属。

一个可复查的负例是把按单平台编写的上传脚本直接接到默认多平台产物上。如果脚本要求目录根部有 amd64 标记，预期它找不到，但对应平台子目录下确实存在。主例没有运行上传脚本，这只是独立的消费者验收设计。测试失败时，先保存导出目录的清单，查究竟是文件未生成、写在了另一层，还是消费者的选择规则仍旧。另一种常见假象来自复用未清空的输出目录：之前的平铺文件可以让新一轮读取错误地通过。为每次组合使用明确且独立的目录，便于解释任何残留。

真实项目中还需要验证标记之外的内容。如果产物是压缩包，可核对包的身份和有效内容；如果是跨平台程序，路径正确也不代表实际能在该系统运行。把这份简单标记换成真实产物时，应保留路径对照，再分别记录平台验证证据。构建缓存的另一项机制可参看独立制品复制层。那个结果约束中间镜像层，本篇验收的是离开构建器的文件树。

发布端还应保留这轮构建与这份目录的对应关系。假设两个命令中第一个成功，第二个因构建器能力不足失败。若上传脚本沿用上一次成功留下的平铺目录，两份日志仍然可能看起来有文件可交付。可以让两次导出分别记录实际退出值，只有对应输出目录属于这一轮且产物验收通过时才交给消费者。读取文件本身无法代替这一步；前一轮的文件若恰好采用同一命名，脚本仍会读到合法的旧数据。为实验日志写清哪个命令、哪个出口和哪份目录，足以解释这类混淆。

如果最终还要生成下载页或校验清单，需要检查映射在不同平台之间没有位置交换。可以先从本轮期望的平台清单生成一份独立表，再逐项验证输出，而不是从发现的文件数反推构建范围。某个平台若没有产物，要显示缺失，并保留对应命令的失败证据。主例只给两个标签作为教学标记。真实发布可以在标记位置保留由制品自身生成的版本信息，但仍要单独核对实际文件身份。此处的两个发布端检查均未执行。

只导出一个平台，也能保留平台目录吗？

可以显式设 platform-split=true。手册区分了默认和显式设置：单平台默认直接导出到目标目录，明确设置为 true 时可以增加平台子目录。若消费者希望单平台和多平台都用同一种目录结构，可加这个参数并核对实际文件路径。主例只对照两个多平台命令，这个单平台变体没有运行。不要把多平台的默认行为直接推成单平台也会有相同目录。
