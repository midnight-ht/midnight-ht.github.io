最后一个依赖服务停了，systemd 为什么也停掉了共享进程？

用两个 systemd 消费单元观察共享服务何时需要保留、何时可以自动停止。

正文

核心要点

  • 在共享单元上选择无人需要时停止。
  • 观察最后一个已声明依赖的消费方。
  • 管理器依赖不等于应用实时连接。

共享单元可以选择在无人需要时停止。systemd 看的是管理器记录的单元依赖；如果最后一个仍需要它的消费单元停了，共享服务可能也会结束。

现场有两个独立的处理程序，都会启动一份共享本地服务。维护者停止第一个程序时，本地服务继续运行；停止第二个以后，它也被停止。有人从进程日志猜测共享服务自行退出。可以先从管理器的设置解释这条路径：共享单元自己是否打开了“无人需要时停止”，两个程序是否都声明了它，以及停止以后还有没有其他单元保持这份依赖。只有三个条件都核对，才好判断看到的状态是否符合原配置。

先查共享单元上的开关

systemd.unit 手册说明，StopWhenUnneeded 默认为 false。设为 true 后，若没有其他活动单元需要它，管理器可自动停止它。开关应该写在准备被清理的那个共享单元上。它并不要求每个消费者附带一条停止共享服务的命令。只关掉一个消费者，另一个还维持所需的依赖，前者的停止不会单独满足这个条件。

这里使用 Wants 声明从消费者指向共享服务的关系。版本 262 的实现将反向的 WANTED_BY 纳入阻止这项自动停止的依赖集合。管理器还检查对方是否已有待处理作业、仍处在活动或过渡状态，或将要重启。实验刻意不用自动重启和额外的依赖，避免把“停止请求发了”立即读成消费者已经不再需要共享服务。 systemd 262 的单元停止判断 相关依赖类型映射

对照停止第一份和最后一份的结果

以下是尚未运行的隔离 Linux 演练。服务仅执行长等待，不接业务请求。保存第一份定义为 shared-lab.service。将第二份分别保存为 client-lab-a.service 和 client-lab-b.service。两份消费者定义完全相同。请确保这些名字没有被已有任务使用，且环境中的可执行路径有效。

[Unit]
Description=Shared dependency lab
StopWhenUnneeded=yes

[Service]
ExecStart=/bin/sleep infinity

[Unit]
Description=Consumer in shared dependency lab
Wants=shared-lab.service
After=shared-lab.service

[Service]
ExecStart=/bin/sleep infinity

加载三个专用单元以后，一次启动两个消费者，观察共享服务和两个消费者都处于活动状态。随后单独停掉第一个，核对另一个仍活动，共享服务应继续运行。再停止第二个，核对没有别的消费者依赖共享服务，预计管理器会安排停止。用同一个单元名逐次查询状态并保存日志，等相关作业完成再记录最终状态。样本不规定准确到某一秒一定看到进程消失。

shared=shared-lab.service
first=client-lab-a.service
second=client-lab-b.service
status() { systemctl show -p ActiveState "$shared"; }

systemctl start "$first" "$second"
status
systemctl stop "$first"
status
systemctl stop "$second"
status

上面最后一条只采集当时状态。如果停止作业尚未执行完，继续查看管理器的任务与日志。验收表要保留第一个消费者结束后到第二个结束前的读取点，不能把两次停止合成一条命令再去补写中间状态。若第一个消费者未真正进入活动状态，应将该轮作废并重新准备。这样可以避免程序初次启动失败后，样本看起来恰好在一个已不存在的依赖下停止。

此外还要确认两次测试的共享进程身份。假如临时任务被其他配置自动重新启动，状态可能先停再活跃，单次读取不足以说明它是否一直运行。应用如果要求已有连接不断，还要用连接结果判断。这个扩展不属于未触发清理的状态判定，不能仅凭看到 active 代替。

接着把共享单元改为 StopWhenUnneeded=no。清理上一轮的三份运行状态，重新加载定义，同样依次启动和停止两个消费者。若没有引入其他关系或故障，在这份控制里，停止最后一位消费者以后，共享服务仍应保持活动。这个负例能排除一个常见误解：消费者停止并不天然传播给它想启动的单元。若对照组也停了，先核对配置里是否还有其它停止传播、进程本身是否结束，以及是否记录了有效设置，再解释结果。

把运行中的业务和单元依赖分开

想让临时工作人员共用一项资源，最后一个退出后便清理，共享单元采用这项设置可能符合要求。若还有未声明的外部使用者，或者共享服务必须一直等待下一批工作，不能只凭两个本机消费单元的状态来决定整体生命周期。管理器没有拿每一条外部请求去判断这份单元是否仍需要。应让部署的一方明确占用何时开始、何时结束，或保持长期单元由独立的生命周期约定控制。

在真正交付的验收里，可分别记录服务停止前最后一个消费单元的状态、系统给共享服务写下的退出原因、以及外部调用者最后一次成功访问的证据。如果外部监测显示还有流量而服务已停，应先检查这段流量有没有代表它的单元关系。这种证据能够区分配置逻辑与业务合同不一致，而不用把日志里所有结束事件都当成进程故障。实际配置还可能被额外文件覆盖，复查时应保留为三个单元加载的定义。关于每次退出是否保留运行目录，可参照运行时文件为何在重启后消失。

如果需要跟着指定单元一起停止，可以写 PartOf 吗？

PartOf 表达另一项关系：列出的单元发生停止或重启时，管理器把该动作传给当前单元。方向由声明决定。这里关注的是最后一项依赖都消失后才停止；如果直接跟随某一个消费者，就可能在另一个仍活动时触发动作。主例没有配置 PartOf。要评估这项新需求，应另做单个指定单元的停止或重启，并确认动作传播方向与原来的多人共用合同是否一致。
