格式提交之后，Git blame 怎样找回业务改动的线索？

固定当前文件，比较普通 Git blame 与明确忽略一笔机械修订之后的归属。

正文

核心要点

  • 先确认被忽略提交的实际范围。
  • 同一行的归属可随观察方式改变。
  • 用实际历史补丁验证业务动机。

整段格式更新都署给了同一笔提交。确认它只改格式后，可以让 Git blame 明确忽略该修订，再查更早的行归属。

一份服务配置把某个模式从 initial 改成 ready。后来团队统一了等号周围的空格。再有人问为什么现在默认用 ready 时，普通 blame 先指向格式提交。格式提交的作者可以解释空格，却未必了解当时为什么换模式。排障要找的是能继续追查业务决策的提交，而不是把后来接触过这行的人都当成决策者。两种证据都能从同一个当前文件获得，取决于观察时有没有把明确的机械改动排除在归属计算之外。

从当前行向前查一笔指定修订

Git blame 官方手册允许用 --ignore-rev 指定计算归属时跳过哪笔修订。Git 会尝试把该提交改过或增加的行归给较早改过该行或附近行的提交。它没有更改当前内容，也不会重写历史。先核对待忽略提交确实属于团队认可的机械改动，再用这个选项寻找候选来源。若提交同时改动配置值，忽略它也会让这次真正改变行为的提交在视图里变得不显眼。

最直接的核对是同时留一份普通结果和忽略结果，再比较各自报告的完整提交号。若只看归属新的作者名，同一个人可能提交过多笔改动，无法分出哪笔产生了哪一行。也不必把所谓较早来源视为最终答案。找到提交以后，再阅读它的实际补丁和相关讨论，确认它是否解释需要追查的选择。

一份文件、三次提交、两种读法

下面的完整脚本在 Apple Git 2.50.1 已实际运行。三个提交依次写入初始值、业务值和仅改变空格的值。仓库由脚本在临时目录创建，没有远端。脚本将结果第一列与预先保存的对象号比较，而没有根据实际输出反过来生成期望。

set -eu
work=$(mktemp -d)
trap 'rm -r "$work"' EXIT
cd "$work"
git init -q -b main
git config user.name Fixture
git config user.email fixture@example.invalid
git config commit.gpgsign false
printf 'mode=initial\n' > settings
git add settings
git commit -qm base
printf 'mode=ready\n' > settings
git commit -qam behavior
behavior=$(git rev-parse HEAD)
printf 'mode = ready\n' > settings
git commit -qam formatting
formatting=$(git rev-parse HEAD)
plain=$(git blame --porcelain -L 1,1 -- settings | head -1)
ignore=$(git blame --porcelain --ignore-rev "$formatting" -L 1,1 -- settings | head -1)
test "${plain%% *}" = "$formatting"
test "${ignore%% *}" = "$behavior"
test "$(cat settings)" = 'mode = ready'
printf 'formatting: %s\nbehavior: %s\nplain: %s\nignored: %s\n' \
  "$formatting" "$behavior" "$plain" "$ignore"

实际输出的普通归属是 formatting 的对象号，忽略结果是 behavior 的对象号。最终文件仍是带空格的那行。三个断言各自有目的：普通结果会告诉读者观察从哪里开始；再次归属说明能越过指定的格式提交；读取当前文件说明这是观察结果变化，文件本身没有还原成旧形态。脚本最终退出零。对象号随临时仓库重新提交而变化，应比较每次运行同一份输出里的对应关系，而非把某个样例散列抄成固定值。

反过来，若格式提交里同时把 ready 改成了 stopped，就不应在追查当前值时忽略这笔修订。可以在另一次演练只改最后一个输入，然后读取最后两笔提交的差异。只要看到同时改了值，就应把它保留在业务审查路径。这个扩展没有运行。它用于说明忽略列表是对修订性质的判断，需要先看补丁才能做，不能从一次归属结果倒推出所有修改都机械。

给协作者留下同一份检查入口

如果只调查一次，用一个明确的修订即可。对经过审查、会反复干扰日常定位的纯格式提交，也可以用文件列出完整对象名，并让团队知道如何验证列表来源。手册允许多次传入列表文件，命令行文件在配置里的文件之后处理；需要对照普通行为时，不要让本机既有忽略列表悄悄影响结果。可以记录实际命令及启用的配置，在受控仓库先建立没有额外规则的基线。本文脚本没有配置默认忽略文件，所以两轮只相差明确的一项参数。

尤其要注意跨分支的情况。一份旧版本可能还没有这笔重排，另一份已经把相同文本拆进不同模块。此时应先固定要查看的对象和文件路径，再判断能否对照相同的行。拿着另一份分支的行号去找同名设置，查到的可能只是附近的不同代码。保存当前行的内容、文件相对路径和查看的提交，可以让同事用相同输入复查。对于范围里哪笔主题补丁实际改动的另一类问题，可参看如何检查两版补丁。

若两份结果指向不同提交，可以给调查记录再补一列，写下每个提交实际改动了哪项设置。格式提交的补丁应当只含空格，业务提交则应显示取值发生变化。若其中一份没有预期差异，先复核读的是哪个分支及配置中的忽略列表，再决定是否继续寻找别的历史线索。记录这些条件，可以防止推荐读法在别人机器上得到不同归属后被误判为错误。

实际调查宜从最窄的范围开始。只跟进一个错误值时，可以先查看关联行；若怀疑一次批量修改改动了多处行为，再扩大到相关文件，使用每处独立的历史证据。不要因为一行的结果符合猜测，就给整个格式提交盖章。若被忽略项里只能确认部分行为是机械改动，保留普通归属并逐笔阅读仍然更有用。

忽略的提交新添了整行，Git 一定能找到较早归属吗？

不能保证。若 Git 无法把被忽略改动里的某行归给较早修订，可以启用 blame.markUnblamableLines 观察这种情况；对应输出会有星号标记。相对地，能重新归给另一笔修订的行可用 blame.markIgnoredLines 标记。要检验这个新条件，应另准备一行无法与旧内容匹配的新增，并核对输出。上面的例子只改现存行的格式，没有执行这项变体。
