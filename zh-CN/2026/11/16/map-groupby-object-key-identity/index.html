Map.groupBy 里两个同名对象，为什么没有分到一组？

固定三条工单，对照对象引用和名称作为分组键时的成员，并用新建同名对象检查分组查找。

正文

核心要点

  • 回调返回的对象按引用区分
  • 非相邻记录可以进入同一组
  • 根据业务身份选择键而非按显示标题猜测

工单列表里有三条记录，都显示支持部。调用 Map.groupBy 以后，页面画出了两个标题相同的分组。第一组是第一和第三条工单，第二组只有第二条。先检查分组回调交给 Map 的是什么。它可能返回两只不同的部门对象，而界面上的标题只读取了对象中恰好相同的名称。

哪些记录实际共享一个键

设有两个对象，分别称作甲和乙。它们各自只有一个名称字段，名称都写着 Support。第一和第三张工单引用甲，第二张引用乙。输入顺序是甲、乙、甲。以部门对象分组时，甲第一次出现就建立一组，第三条再次遇到甲会加入那一组。夹在中间的乙独立建立另一组。

这里的判断是对象身份。把两个对象的字段一起打印，结果相同也不能证明它们是同一个键。一个用户能看懂的标题只负责标识分组给人看的样子。如果程序另用对象键读回分组，就得传入构造分组时用到的同一引用。临时拼出第三只同名对象，无法读回甲或乙。

Map 的组值是数组，里面按输入次序放着被分配的记录。因此按甲读取会先看到 T1，再看到 T3。相隔多远不会使同一个键变成两个组。判断别把记录是否相邻当成标准。关心的是回调对这一行返回的对象是否与之前的键相同。

固定三条工单，独立检查两种分组

下面的脚本保留相同的输入数组，先返回部门对象，再返回部门名称。测试用同一份工单内容，只改变键的选择。它验证甲和乙各自的成员，也验证一只刚创建的同名对象读不到既有的组。

import assert from 'node:assert/strict';

const a = {name: 'Support'};
const b = {name: 'Support'};
const rows = [
  {id: 'T1', team: a},
  {id: 'T2', team: b},
  {id: 'T3', team: a},
];

const group = Map.groupBy;
const byTeam = group(rows, row => row.team);
const byLabel = group(rows, ({team}) => team.name);
const identities = [
  [Array.from(byTeam.keys()), [a, b]],
  [byTeam.get(a), [rows[0], rows[2]]],
  [byTeam.get(b), [rows[1]]],
  [byTeam.get({name: 'Support'}), undefined],
  [Array.from(byLabel.entries()), [['Support', rows]]],
];

const {deepEqual, equal} = assert;
for (const [actual, expected] of identities) deepEqual(actual, expected);
equal(byTeam.size, 2);
console.log('Object identity and label grouping checks passed.');

本地 Node 执行的断言通过。对象分组得到两个键，甲包含 T1 和 T3，乙包含 T2。以名称分组则只有一个 Support 键，三条工单都进入那一组。这两种结果都与各自回调一致。脚本没有请求任何服务，也没从两份网络响应推断实际数据是否共享引用。

把这个对照搬回项目时，先写下预期的成员编号，再决定应该有几组。有时桶数碰巧对了，实际却把第二和第三条认反。因此用编号检查每个键对应的成员，比只断言最终数目可靠。调试输出还可以用两个独立对象的比较结果告诉你名称相同的部门是否实际共享身份。

若两次获取的工单被解析成独立对象，引用比较就可能把同一业务部门拆开。假如业务把部门编号定义为稳定身份，分组回调可以返回那个编号，由其他数据源提供标题。这样做仍需确认编号的作用域。如果不同组织可以使用相同部门编号，跨组织列表就不能只凭部门编号将它们合在一起。

还有一种情况，名称相同的部门就应该各自出现。例如同一页同时展示两个组织，两个组织各自有支持部。只用名称当键会把原本不同的组挤到一起。若系统持有稳定对象并明确将引用当标识，保持对象作为键是合理的。关键问题是这份列表想让谁和谁成为同一个组。

改造代码时可以检查分组回调是否每次都新建对象。例如为了组合两个现有字段，每次接到记录就构建一只只有那两个字段的新对象。即使字段值重合，下一条记录的新对象仍有另一份身份。若想用对象区分组合，可以先建立或复用一致的对象；若已有稳定领域主键，让回调直接返回它通常更容易追踪。

输出对象也无需用分组标题去反查源记录。可以把键、给人看的标题以及每组成员的编号一起保留。看到两个标题重合的组时，调试者可以根据键来源决定是合法共存，还是需要统一身份。只保留标题字符串会丢掉解释这次分组所需的证据。

在团队层次里，正常地把同名记录分开与错误地把一个部门拆开，会产生相同的页面截图。可以拿一个已知应该合并的例子和一个已知必须保留独立的例子同时过一遍。前者需要已有的稳定部门身份，后者可以选两个组织在各自空间里都取名支持部的记录。先写下每条记录的组织与部门，再检查它是否出现在预期的组中。这样修改分组键时不会只修一个重复标题，又让另一类真实部门记录被合并。

如果分组只用于源数据的一次计算，两个不同键即使使用相同标签也可以继续渲染。若下游还要折叠组、跳转或编辑，则要给这些操作留可区分的身份。显示文本可以继续保持简短，操作却应使用产生该组的键或与键对应的稳定标识，免得点击一个标题时修改了另一组记录。

改了工单的部门，记录会自动移到另一个组吗？

不会。先用主例生成两组，再把 T1 的部门字段改成乙。甲组里拿到的仍是 T1 那只对象，所以读取其部门时能看到乙。但是甲组的数组还保留 T1，乙组没有自动增加记录。分组步骤已经结束，后续赋值没有再次执行原来的回调。

如果表格必须立即反映工单调组，就用改过的记录重新分组，或由应用明确维护增删。验收时先检查工单的新部门，然后分别检查旧组不再含 T1、新组已经含 T1。只检查第一个条件会让旧分组结构继续留在界面上。

如果使用的是 Python 中对连续键分组的迭代接口，可另看 itertools.groupby 的组迭代器怎样共享输入。
