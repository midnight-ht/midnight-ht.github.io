Mock 明明被正确调用，断言为什么看到已经清空的字典？

用实际 Python 调用对照 Mock 参数引用、后续清空与调用时快照。

正文

核心要点

  • 调用历史可以保留实参引用。
  • 需要原始内容时，应在调用时复制必要值。
  • 身份和内容有独立判据。

unittest.mock 会在调用历史中保存参数引用。实参如果随后被清空，回头查看记录时也会看到空内容。要断言调用那一刻的数据，应在替身收到参数时另存可比较的值。

假设一个导出函数把待发布的编号交给另一层，然后清理暂存列表。测试确认替身确实被调用了一次，却在检查参数时得到一份空列表。此时应该先查谁继续持有原对象，以及在哪一步修改了它。回头查看调用记录可以说明传的是哪个对象；对象现在的内容不能单独证明它传入时已经为空。

把历史里的身份和现在的内容分开

标准库的 mock 使用示例明确指出，call_args 和 call_args_list 保留的是实参引用。记录出现并不意味着做了深拷贝。若被测函数在调用后继续对同一个对象变更，后续断言检查的是引用当前能读到的内容。这个现象和 mock 有没有接到正确调用是两件事。错误也不一定是生产代码清理列表太早，还可能只是测试在错误的时间点采用了对象值。Python unittest.mock 可变参数示例。

另一种合同要求上下游使用同一个对象。此时引用恰好能验证身份。调用以后还要判断值时，可以把身份断言留在调用历史上，再把内容断言交给调用时观察器。如果只在测试前构造一份预期列表，又把它和被测输入共用，预期也可能一起被删掉。应让预期来自产品定义和固定输入，不从修改后的对象自动生成。

同一次调用保留两份观察

下面完整程序已在 Python 3.11.15 运行。它构造两个编号，替身接手时复制字典，生产函数返回后再查看调用历史。清空发生在内层列表上，因此只复制外层字典也会留下对同一列表的引用。程序没有向外部服务发布内容，替身只存在于本地进程里。

from copy import deepcopy
from unittest.mock import Mock

def publish(send, payload):
    send(payload)
    payload["ids"].clear()

seen = []
sink = Mock(side_effect=lambda payload: seen.append(deepcopy(payload)))
data = {"ids": [17, 23]}
publish(sink, data)

recorded = sink.call_args.args[0]
assert recorded is data
assert recorded == {"ids": []}
assert seen == [{"ids": [17, 23]}]
print("after", recorded, "during", seen[0])

归档记录显示，调用历史里的对象确实就是 data，读取时编号列表已经为空。调用时另存的快照仍保留十七和二十三。这三项各自有断言。只比较实例身份会漏掉曾经交付了哪些值；只比较快照会漏掉生产入口是不是有意把同一对象交给对方。写判断时先确认业务承诺，再选择这两类观察中的哪一份。

可以独立做一条错误对照，把复制改成只复制外层字典，仍然保留后续对内层列表的清空。预期这个所谓快照也会变空。这样能检测出团队是否仅复制了一个容器外壳。若应用输入只有一个无嵌套的编号列表，复制该列表也可以成立，不需要把所有参数都深拷贝。这个浅复制反例没有运行。本次回执只覆盖程序里确切的深复制与原对象路径。

将快照落在业务真正需要的字段上

深复制便于演示普通字典，不过应用的实参还可能含文件句柄、连接或有自定义复制行为的对象。若测试只关心批次标识和编号，可以在接收时取出这些字段，把编号变成不可变的值。观察器应保留自己收到的内容和时点，同时让别的参数继续参与原调用。不要因为测试能复制它，就要求生产也把所有上下文复制一遍。

考虑一个需要检查排序的消费者。如果发布接口要求编号按工作流顺序交付，快照就要保存编号顺序，不能先转集合再断言。若合同只关心某个批次送过哪些编号，也要确认重复项有没有业务意义。给错误输入保留相同的几个编号但打乱位置，或重复提交其中一个，分别核对应用要求的结果。这里未运行消费者。这组设计用于明确该捕获什么，不是对实际消息接口的验证。

站内的 pytest 共享输入 说明测试之间为何可能共用同一对象。这里是在一次调用的前后分别观察。排查可以把输入准备、替身入口、对象清理和测试结束四个时点依次标明，确认快照发生在清理之前。如果先检查测试结束时的状态，再倒推入口值，下一次遇到别的可变对象仍可能误验。

应用如果允许重试，还应给每次调用单独留一份快照。第一轮可能送出两个编号，第二轮只处理一个；最终列表为空不能解释前面实际发生了几次。用固定批次身份核对每一轮的独立数据，避免把观察器里最新的一张快照覆盖较早证据。这个重试控制未执行，主程序只调用替身一次。

若接收器本来就要在稍后读取这个对象，应另外测试交接约定。让接收器故意等到清理以后，检查它是否还能读取所需编号。如果业务约定值必须在延迟读取时可用，只有测试替身保存了快照，并不能修复真实数据。从产品实际消费时点写出预期，才能区分测试观察位置与程序设计错误。这个延迟消费对照未运行。

side_effect 还需要保留 mock 配置的返回值吗？

需要时，可以在复制参数后返回 unittest.mock.DEFAULT，让替身继续使用原有配置的行为。另准备一个配置为返回明确状态的 mock，复制完编号后返回 DEFAULT，分别检查快照与调用方拿到的状态。这样不会把观察代码写成新的业务返回值。这个追问对应另一份未执行的测试，主样本的替身只保存快照，生产函数也不消费返回值。
