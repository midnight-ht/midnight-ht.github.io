replaceAll 怎样把含美元符号的文字原样填进模板？

同一个带美元记号的标签为何在字符串和函数参数中生成不同结果？用两处模板标记和本地精确断言找出原因。

正文

核心要点

  • 替换字符串可能解释美元记号
  • 函数返回值用于直接拼接
  • 用完整输出断言每个替换位置

报表模板用 SLOT 标记销售组的显示位置，一份模板有两处。录入者把标签设成美元符号、与号、短横线和 sales，预览却重新出现了 SLOT，两处都是如此。标记找得没错。问题出在替换参数：直接传字符串时，里面的部分字符有替换语法。

同一个标签为什么会写出两种结果

先只看普通文本模板 SLOT/SLOT。要填进去的标签是 $&-sales，业务要求保留它原来每个字符。把它作为替换字符串交给方法，$& 会被解释为本次匹配到的文本。这里每处匹配都是 SLOT，输出因此成为 SLOT-sales/SLOT-sales。后面的短横线与 sales 没有变化。

如果将第二个参数换成一个返回标签的函数，方法在每处匹配上调用它，将返回值转换为字符串后直接拼入结果。此时美元和与号是两个普通字符。输出里的两个位置都应看到 $&-sales。这个例子只用普通字符串作搜索值，避开正则替换和自定义替换钩子的其他规则。

这两个形态都能成功执行，返回的长度也可能比原模板长。运行时不会因为用户并未打算写替换记号而报错。修复前如果只检查模板字符串被修改，便会错过错误。要检查的是每个输出位置的精确文本，而不是看函数是否正常返回。

日常调试时可以把这条路径分成三个值：原模板、实际交给方法的标签，以及最终结果。如果标签值在调用前已经正确，输出却保留了原始标记，就有理由去看替换参数的类型。顺手换掉搜索词可能让错位暂时消失，却没有保证下一条包含同样记号的标签会按原样填入。

保持输入不变，只换参数形态

下面的本地脚本独立测试字符串和函数，还加了一个普通 north 标签作为对照。两个占位处均要改变，防止有人把方法改成只替换第一处以后，第一段看起来正确、第二段仍留着标记。三次运行使用同一份模板，每次只读它，不会把上一次结果当成下一次输入。

import {strictEqual as equal} from 'node:assert';

const template = 'SLOT/SLOT';
const label = '$&-sales';
const fill = template.replaceAll.bind(template);

const cases = [
  [label, 'SLOT-sales/SLOT-sales'],
  [() => label, '$&-sales/$&-sales'],
  ['north', 'north/north'],
];
for (const [replacement, expected] of cases) {
  equal(fill('SLOT', replacement), expected);
}
console.log('String, function, and plain-label checks passed.');

实际运行时，三组完整输出断言均通过。字符串版本两次展开原标记，函数版本两次保留标签，普通文本版本两次得到 north。普通文本组证明日常标签可能一直表现正常，也解释了为何生产中通常等到某个特定名称出现才发现问题。

要复现这类问题，夹具应保存带特殊字符的真实最小形态。若把标签手工改成另一个不含记号的值，两个版本就会得到相同输出。工程师可以使用固定的假数据代替原名称，并将比较限定为输出，不必保留用户录入的原始内容。

实现契约可以在封装外部就写清楚。有一种入口接受开发者定义的替换模式，例如自动给匹配词加统一前缀。它可以让字符串直接参与替换。另一种入口只接受普通展示文案，应把字符串作为函数的返回值交进去。如果把两类值混用，使用者无法判断传入的美元符号表示逻辑还是就是要显示的内容。

你也不必逐个查找标签里有哪些替换记号之后再猜该怎么改写。把标签作为函数结果返回，这个决定发生在接口边界上，任何标签都走同一个分支。若函数根据匹配位置返回不同标签，同样需要对每个位置保存预期值。选择函数只是为了按预期构造文本，不承诺返回的文本经过了其他处理。

该示例的输出是普通文本。若产品把同一个结果交给 HTML 解析器，模板替换与渲染语境要分开处理。保存了原有字符并不表示该字符串已经符合 HTML 内容的限制。验证两个字符串完全相等，也无法证明渲染方式正确。输出该类普通标签时，仍应选择符合自己内容契约的显示方式。

面向调用者写迁移说明时，可以列出过去使用的两个入口：一组由工程师写死的替换规则，一组来自输入框的显示值。先把第二组接到只接受普通文本的入口，再保留第一组各自的匹配引用。把两边一起替换成新写法，可能悄悄取消原来有意使用的替换记号。验证时各留一项旧数据，确认意外解释被去掉，有意解释仍存在。

还可以单独检查替换之前没有修改模板自身。在循环里生成多份报表时，每次都从包含两处标记的原模板起步。若你把第一次的输出覆盖回模板变量，下一次将失去原来的占位位置，结果和参数类型问题有些像。记录每次的原输入和输出更容易区分这两类故障。

返回的文字里还有 SLOT，会再替换一轮吗？

不会。把标签换成 SLOT-X，经由函数返回。最终得到 SLOT-X/SLOT-X。当前调用先从原始模板寻找匹配位置，在那些位置填入新的字符串。已经填入的 SLOT 没有成为这一次调用的新搜索输入。若外层代码又用这个输出执行下一次替换，则需另看那次的输入与规则。

这一点适合用来判断是一次替换产生了意外结果，还是后续有重复处理。先在单次调用边界断言 SLOT-X/SLOT-X，再确认最终渲染有没有把同一结果送回模板层。只看结尾文本里出现 SLOT，无法区分残留原标记与有意填入带该词的标签。
