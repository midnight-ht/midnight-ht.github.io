pytest 的配置拼错了，为什么测试还是绿的？

用同一测试对照 pytest 对未知配置键的默认警告、严格失败和修复结果。

正文

核心要点

  • 断言通过不能说明每个配置键都被采用。
  • 严格配置把解析警告变成错误。
  • 保存实际配置文件和测试运行结果。

用例通过并不证明配置键被 pytest 识别。未知键默认可能只产生警告；启用严格配置后，同一条配置警告会成为错误。

维护者把测试报告设为简洁输出，提交以后却仍看到完整输出。用例全部通过，流水线也没有退出失败。如果只调查测试函数，就可能看不到真正变化的输入。先确认运行读取的是哪份配置文件，再看目标键是否被当前版本或插件登记。两份看似相同的绿色摘要，可以分别来自配置正确和配置被忽略。要验证的是被应用的设置与测试结果两项，而不是其中任意一项变绿。

让一份关键配置故意拼错

pytest 的严格配置参考说明，打开 strict_config 后，解析 pytest 配置部分时遇到的警告会成为错误。命令行的 --strict-config 可打开这个选项。本例只观察未知键，不把它扩大成对任意 Python 警告或外部插件日志的保证。配置是否可识别，仍取决于实际版本及加载的插件。

下面三份文件形成完整实验。都保存在一个独立目录，不加载项目配置，也关闭外部插件自动装载。第一个文件的测试始终成功，后两个配置拼写只差一个字符。这里的真实版本为 pytest 9.0.2 和 Python 3.11.15。实际实验关闭缓存插件以避免其他状态影响对照。程序没有使用团队仓库的测试，也没有冒充那些测试已经验证。

def test_sum():
    assert 2 + 3 == 5

将它保存为 test_example.py，将以下配置分别保存为 bad.ini 与 good.ini。

[pytest]
addoptz = -q

[pytest]
addopts = -q

以同一工作目录分别执行下面三条命令。记录每一条的退出值再执行下一条。第二条预期失败，使用遇错立刻结束的外层脚本时，应给它单独处理。

python -m pytest -p no:cacheprovider -c bad.ini
python -m pytest -p no:cacheprovider -c bad.ini --strict-config
python -m pytest -p no:cacheprovider -c good.ini --strict-config

第一条实际返回零，报告用例通过，同时给出 Unknown config option。第二条返回四，标准错误保留同样的未知键原因。第三条恢复为零，明确报告一项通过。由于用例没有变化，这组试验不需要把红色结果归因于业务断言。复核时同时保存标准输出、标准错误和状态码，警告与错误可能分别出现在不同流里。若只留最后一行摘要，可能把可修的配置问题误归为某项测试不稳定。

限定这个门禁究竟保护什么

严格配置能指出未被识别的键，不能替你判断识别后的值是否符合团队约定。即便修正了 addopts 的拼写，还应观察实际运行有没有按期望处理所设参数。以上例而言，第三条确实使用简洁格式，但不能据此推断其它设置也达到预期。对于要作为验收依据的开关，可以保留一项可辨认的观察，例如退出行为、指定项目是否执行或结果是否输出到约定位置。

如果只在本地出现未知键，先检查同事是否运行了相同的解释器和项目入口。假设一个插件定义了某个团队特有的配置项，而 CI 没有安装那个插件。直接删掉键可能消除错误，却放弃了原来的功能。合适的复查方式是查明谁定义它、当前会话加载了谁、实际使用哪个配置文件。若确实已经移除插件，再按团队决策清理不再使用的设置。若插件仍是约定的一部分，则应修复环境。这个假设场景没有在教学程序里运行。

配置位置也会影响验收。临时演练用显式的 -c 固定文件，真实任务如果从不同仓库目录启动，可能读取不同配置。保存启动命令和工具输出显示的配置路径，再核对期望文件。项目可以在最常用入口做一次严格检查，并在变更启动入口后再运行。只在另一份最小文件上验证严格行为，不能证明实际流水线已经启用。有关测试标记与选择集合的另一个例子，参见严格标记能抓住什么。

还要考虑修复对实际业务的影响。如果变更目的是让一个原先失效的运行选项开始生效，严格门禁通过只是首个证据。下一步可以选一组期待该选项生效的用例，用实际 CI 命令运行并保留结果。若选项影响的是收集或标记选择，就应检查实际节点，而不能只比较运行条数。用两个结果分别说明配置是否被接受、业务是否按它运行，有助于将可读状态传递给发布人员。

如果改动前后只换了进程的入口，还可保留一份对照，让两个入口都指向同一个绝对配置路径。这样可以确认未知键的差异来自加载情况，还是因为它们此前选了两份不同文件。另一个有用的观察是先用故意写错的键证明门禁真正开启，再把配置恢复到正常内容，确认业务用例重新执行。故意的坏配置只留在隔离样本，不进入正式发布。这个检查比单看配置文件里写着 strict_config 更可靠，因为包装脚本可能读了另一份文件或处理了测试进程的退出值。

strict-config 能代替 strict-markers 吗？

它们控制不同的检查。前者针对配置解析时的警告，后者会让未注册测试标记成为错误。主例只使用普通测试函数，没有装饰器。若团队也要求未注册标记失败，应在自己的设置里另外验证；一种拟议的检查是保留合法配置，故意在测试上使用未注册装饰器，确认严格标记入口能够报错。这项扩展没有执行，也不能只靠主例的未知键失败判定。
