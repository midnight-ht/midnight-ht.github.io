必填字段一打开就无效，为什么 :user-invalid 还没匹配？

空必填输入已经违反约束，首次提交之后才进入本例的用户无效状态。用三次读数区分两个选择器。

正文

核心要点

  • 空必填输入首屏可以匹配 :invalid
  • 尝试原生提交后检查用户无效状态
  • 用同样的空值对照提交前后

打开项目创建表单，项目名默认空着。浏览器已经知道它违反必填约束，用户却还没尝试提交。若样式直接用 :invalid 画红色轮廓，首屏便会把未回答和失败提交画成同一种状态。对这个原生文本框，可以分别检查普通有效性和用户有效性，决定何时显示错误样式。

开始时无效，不等于用户已经提交了无效内容

必填输入的初始值为空时，控件没有满足约束。对仍是约束验证候选的普通文本框，:invalid 会在初始渲染就匹配。这并不依赖程序有没有手动显示一行可见错误，也不用等用户点按钮。如果样式用这个匹配上色，浏览器按控件规格开始计算时就有了上色的条件。

:user-invalid 还依赖 HTML 所称的用户有效性。对普通输入框，它初始为 false。只有控件参与约束验证、没有满足约束，并且用户有效性为 true，才匹配这个伪类。用户有效性这个名字容易误读，它不是最终答案是否合规的布尔值。这个布尔值为真时，控件仍有可能是无效的。

用原生按钮尝试提交表单时，HTML 的提交步骤会设置各可提交字段的用户有效性，再进入相应的交互式约束验证。这个例子里，缺值使提交被拦截。回到字段读匹配，两种伪类都应成立。浏览器还可能显示它自己的验证反馈，这和我们的 CSS 轮廓是两份不同的观察结果。

用户随后输入正常的项目名，必填条件满足。此时两种无效伪类都不匹配。不要把这个结果当成用户有效性已经自行清零的证明。只要当前值合法，匹配条件中就已少了必要的一项。要检查交互状态被重置，可用最后的独立用例。

让测试保留两个匹配值

下面的页面本地打开即可准备好夹具。字段不设默认值，只有一项必填约束。记录按钮读取两个匹配值，不会主动尝试提交。代码读一次初始状态，让最后两次读数和起点一起留在日志里。例子在合法提交事件上阻止页面跳转，没有发送任何表单数据。

<!doctype html>
<meta charset="utf-8">
<title>Required input states</title>
<style>
  input:invalid { border-color: #646d7b; }
  input:user-invalid { outline: 3px solid #ac3126; }
</style>
<form id="form">
  <label>Project name <input id="project" name="project" required></label>
  <button type="submit">Try submit</button>
  <button type="button" id="read">Read current matches</button>
</form>
<pre id="output"></pre>
<script>
const byId = document.getElementById.bind(document);
const field = byId('project');
const output = byId('output');

function record() {
  const ordinary = field.matches(':invalid');
  const interacted = field.matches(':user-invalid');
  output.append(String(ordinary) + ' | ' + String(interacted) + '\n');
}

byId('form').addEventListener('submit', event => event.preventDefault());
byId('read').onclick = record;
record();
</script>

应看到第一行 true 和 false。不要在此之前输入字，也不要先提交或打开浏览器中的旧表单恢复。接着保持空值，点击 Try submit，再点读数按钮。预计第二行是 true 和 true。最后填入 Atlas，仍通过读数按钮检查。第三行应是 false 和 false。这两列分别对应普通无效和用户无效。

记录时可以将颜色变化与各自的匹配值放在一起。红轮廓出现，说明其中一条样式参与了绘制，再读选择器能确认是不是我们预计的规则。如果两列符合预期而轮廓没出现，接着检查其他样式是否覆盖了它。如果某个选择器不受目标浏览器支持，应先记下支持边界，再决定项目如何提供提示。

这里给的是按标准推导的结果，本文没有实际运行浏览器或辅助技术。设计验收时，可以用同一浏览器记录三次 DOM 读数和可见状态，另行测试用键盘提交之后如何定位错误。这个例子没有为真实产品完成一整套可访问的错误提示，它只验证一个样式何时有匹配条件。

把真正的行为留在回归用例里

假如组件测试最终只断言字段在空值时匹配 :invalid，那么首屏就提示失败与尝试提交后才提示，都可能测试通过。应把空值状态分成两个时间点，再测填好时的恢复。这个安排不用引入更复杂的正则，也能捕获检查时机缺失的问题。

对于实际表单，触发器也可能放在组件外面，或者由脚本去执行保存。把用户真正使用的按钮路径走一遍，再复用同样的两列读数。若按键没有进入原生有效性算法，即使视觉上按钮被点击，也不能把结果拿来证明提交后的选择器条件失败。

样式还应服务于用户修正。轮廓能指向未通过规则的字段，文字才能明确说明缺的是什么。如果提交一共有三处失败，组件可以分别验收当前这一个字段的状态，以及用户能否从总反馈找到它。输入仍要留在控件里，CSS 状态切换本身不会提供新的错误文案。

加入这个变化前，可以保存一条明确的首屏用例。打开一份全新的表单，不填任何值，确认页面没有把空字段当成已尝试的错误。然后故意提交，记录在哪里有可见反馈。最后停在修正后的输入上复读。对于中文输入法、浏览器自动填充或不同的控件，仍需根据产品支持的实际入口补充验证。

原生重置后，必填字段空着会再次变红吗？

对这个例子的用户无效样式，预期不会。设想在失败尝试之后加一个原生重置按钮。输入的重置算法清除用户有效性，并在没有默认值时恢复空字符串。重置后仍然缺项目名，所以 :invalid 为真；由于用户有效性复位，:user-invalid 为假。若再尝试提交，后者才重新符合条件。

清空字段值和按表单重置按钮不是一回事。组件里自制的「清空」动作若只修改值，没有执行重置算法，就不能用上面这组输出作承诺。实际需要恢复整个初始场景时，分别核对值和两种匹配，而不是只看视觉上变成空白。

如果表单由脚本发起提交，可再读脚本提交表单怎样保留校验和按钮意图。
