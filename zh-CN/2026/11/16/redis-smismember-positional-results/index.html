Redis 一次查三个成员，为什么结果不是三个成员名？

通过重复和交错输入，核对 Redis 批量成员查找中的位置映射。

正文

核心要点

  • 回复标记按请求顺序排列。
  • 重复成员值也保留输入位置。
  • 全零回复不能解释键是否缺失。

Redis 的 SMISMEMBER 按请求顺序返回每个成员的存在标记。返回数组里没有成员名。输入里如果同一个值占两个位置，客户端仍要保留两个位置的结果，才能把每项标记贴回发起它的检查。

假设后台先对一份任务列表做批量标签检查，再给每一行加上提示。两条不同任务可能包含同一个标签。若代码先把标签放进集合，再拿结果逐项覆盖原任务列表，重复输入就会消失，后续标记也可能向前错位。即使命令成功、命中的标签种类也正确，界面仍然可能给错任务显示通过。验收需要检查的是发出请求的那份顺序和收到的逐项结果。

让 Redis 回答一组有位置的问题

从 Redis Open Source 六点二起，SMISMEMBER 可以查询同一个集合里的多个候选值。文档把结果定义为成员状态组成的数组，顺序和请求一致。命中返回一，未命中或集合不存在时返回零。这个命令没有把请求转换成只含命中项的列表，也不返回集合已有成员的遍历。客户端如果要提供标签，需要自行把输入值和对应位置的标记组合起来。Redis SMISMEMBER。

这和只问总共命中几次的合同不同。相同的两种结果，可以有相同的命中数量，却落在不同任务上。测试应对保留位置的业务明确断言每项，而不是只把标记相加。如果设置层只需要给一组去重的标签查状态，可以先去重，再以独立的输入位置数组重建原始批次。这个选择需要保留重复标签的归属，不能因为后端少发几个值就让消费方失去对应关系。

用重复项和未命中把位置固定下来

下面是未执行的教学命令。应使用自有隔离的 Redis 实例和起初不存在的键。写入只包含 a 与 c。第一份读取故意先问 c，再问 b，再重复 c，最后问 a。第二份读取用同一集合，但改成先问 b 再问 a。改变的是观察的次序与长度，集合内容保持不变。

SADD {members-example}:known a c
SMISMEMBER {members-example}:known c b c a
SMISMEMBER {members-example}:known b a

预期第一份结果依次为一、零、一、一；第二份为零、一。第一项与第三项都在问 c，但它们分别占据一个输入位置。确认回复长度分别为四和二，再逐项比对。一个按字母顺序重排输入但忘记重建位置的实现，可能仍然得到正确的命中数量。只检查数组长度也不能检测它。给每次调用保留当时发出的成员序列，就能查出标记是 Redis 返回异常，还是在应用拼接结果时错配。

这份固定输入不包含大小写兼容、数字转换或额外前缀。若线上接口对用户输入做规范化，另用两个规范化后相同的值验证，确认客户端仍保留两个原始请求的位置。如果应用要显示原文，报告里可分别记录原始值、实际发送值和回复标记。这样可以区分漏发、规范化合并和读错位置三类问题。这个应用入口没有运行，也没有连接实际客户端。

返回结构要满足调用方的使用方式

页面需要逐行显示时，可以返回一份短记录列表，每项保存稳定行号和存在标记。对只关心某个唯一标签的调用者，可以用映射，不过要先明确不会依赖重复项次数。若组件内部用映射优化查找，批次响应仍可以按原行号输出。验收可以输入两条任务都用 c，中间夹一条 b，确认结果在三个任务上依次为真、假、真，并且两个真仍属于两条不同任务。

对于大批次，也可以把原批次拆成多个请求。分组前先给每项确定位置，把每一组结果放回正确区间，然后核对重复值跨组时不会覆盖其他请求。另准备一组只有部分请求成功的输入，定义该批次应该报错还是返回单独失败的区间。一次命令中的位置规则不能替客户端决定不同请求的完成顺序，也不能保证多个调用自动观察同一份集合状态。这里没有运行分批、乱序回包或连接重试。站内的 Redis 交集计数边界 讨论只保留数字所能表达的结论，本例关心每项状态对应谁。

记录故障时还要区分数据值和命令错误。命令正常返回零，是对请求项的成员判断；客户端若收到类型或连接错误，不能自动将整批补成零。后者会让筛选页面把未知状态显示成明确未命中。可在应用测试中分别保留一次合法全零结果和一次读取失败，再看消费者是否进入不同出口。这种错误映射未在样本中验证。

还可把相同的任务键按不同排列送进接口，要求结果随各自任务移动。对两个同样三次命中的输出，保留一份把唯一未命中标到不同位置的坏结果，确认逐行断言会拒绝。这个验收应使用客户端真正对外返回的结构，而不只是命令的原始回复。它没有运行。

整个键不存在时，怎样区别正常的全零？

可以用全新缺失键检查 a 与 b，预期得到两个零；用确实存在但不包含 a 与 b 的另一个集合做相同请求，也应得到两个零。单次成员数组没有提供键级原因。若产品要求区分未配置与未匹配，应另依据权威配置或明确的读取流程来判断。独立查询键是否存在也会遇到键在两次调用间变化的情况，不能把它同成员结果默认为一个快照。这个追问未执行。
