Go AfterFunc 的 stop 返回 false，清理已经做完了吗？

用独立通道和两次停止对照，区分 Go AfterFunc 阻止回调、运行回调与清理完成。

正文

核心要点

  • stop 不等待回调完成。
  • false 可由不同生命周期产生。
  • 需要完成证据时显式协调。

Go 的 context.AfterFunc 返回的 stop 函数不等待回调完成。stop 返回 false 时，回调可能已经开始，也可能此前已被停止。如果调用方必须等资源清理完成，就需要单独的完成信号。

设想下载请求取消后，程序安排一个回调把临时资源的登记状态清掉。调用方执行 stop，看到返回 false，便认为登记已经删除，继续把同一个资源标识交给下一项工作。实际回调可能刚进入并且还在等锁。状态应该依据回调本身的证据，而不能把试图停止它的结果当成清理回执。

stop 的返回值描述一次拦截尝试

标准库文档说明，AfterFunc 在取消之后于自己的 goroutine 中调用给定函数。返回的 stop 解除上下文与函数的关联。如果这次 stop 阻止了函数运行，就返回 true。返回 false 有两条路径：上下文已取消且回调已启动，或者回调已经被停止。文档另说明 stop 返回前不会等待函数完成。若要知道函数是否结束，调用方需要与它显式协调。这个标准库入口从 Go 一点二一开始可用。Go context AfterFunc。

因此，一个完成通道也需要明确什么时候会有人关闭。若首次 stop 成功，回调不再承担通知职责；如果之后仍无条件等回调里的 done，等待者可能永远收不到。若首次 stop 失败，并且调用权属于一个协调者，才可以按它已建立的回调生命周期决定何时等待。多个组件都能调用 stop 时，还要保存是不是已有其他人停止了它。否则读到 false 的人没有足够依据分辨两种情况。

用通道保留一个肯定尚未完成的回调

以下是未执行的完整 Go 教学程序。它不依赖 sleep 来猜回调进度。注册之后取消上下文，回调一进入就通知 started，随后等 release。主线程收到第一项通知以后才调用 stop。第二个独立上下文则在还没有取消时先阻止回调，用来观察另一种 false。

package main

import (
    "context"
    "fmt"
)

func main() {
    ctx, cancel := context.WithCancel(context.Background())
    started := make(chan struct{}, 1)
    release := make(chan struct{})
    done := make(chan struct{})
    stop := context.AfterFunc(ctx, func() {
        started <- struct{}{}
        <-release
        close(done)
    })
    cancel()
    <-started
    if stop() {
        panic("callback already started")
    }
    select {
    case <-done:
        panic("callback still held by test")
    default:
    }
    close(release)
    <-done

    fresh, finish := context.WithCancel(context.TODO())
    suppressed := context.AfterFunc(fresh, func() {
        panic("stopped callback unexpectedly ran")
    })
    before, again := suppressed(), suppressed()
    finish()
    if !before || again {
        panic("unexpected stop states")
    }
    fmt.Println("running false; completed after release; stopped true then false")
}

第一段预期 stop 返回 false，同时 done 尚未关闭。收到 release 后回调才关闭 done，主流程确知里面的可观察清理点已经通过。第二段先后两次停止，预期值分别为真和假，随后才取消它的上下文。即使这个第二次的假值与第一段一样，也没有理由等待一个已经被停止的回调。演示只在回调中设置了完成标记，未操作真实文件、锁或网络资源。

如果接口有真正的清理步骤，可以将 done 放到那些步骤之后，并在需要时另外保存返回的错误。完成信号说明工作到达终点，不能顺带代表清理成功。给失败分支也保留一个终结通知，调用者才能结束等待并知道失败。若多个等待者都需要同一份结果，应先明确结果的写入时点与通道关闭之间的关系，再用可观察的字段核对。样本没有实现可公开的清理结果类型。

定义哪个调用者拥有停止与等待

把下载的正常结束与请求取消拆成两份验收。正常结束要检查计划中的取消回调能否在未开始时被阻止，再由正常路径释放资源。取消发生以后，应按预先定义的拥有者观察实际清理状态。若有正常出口和回调两个地方都可能释放同一资源，要为重复释放设置独立控制。一次 stop 的布尔信号不会自动让另一个资源操作成为只执行一次的动作。

一个可查的失败用例让回调先记录“已进入”，然后在清理前等待允许。当正常出口也要检查资源状态时，它只应观察到仍未释放。开放回调之后再检查资源标识已经可用。如果这两项测试并行运行在真实服务里，还要明确哪个线程或请求持有停止函数，不能用任意一个工作者的日志代替另一个的完成记录。这个应用对照未执行。站内的 独立清理期限 处理取消树和期限，本篇强调回调本身何时结束。

可另外测试停止动作早于请求结束的路线。让正常出口拿到真值，并用它自己的资源清理替代回调。检查普通清理只触发一次，不能由于后来收到父上下文取消又重新释放。这个入口验证没有在示例里执行真实资源操作；布尔值的观察范围只限标准库回调安排。

故障演练还应区别等待第二次前台调用与等待正在清理的后台动作。令下一项读取相同资源标识时先看到清理尚未通过，再开放回调并验证可继续处理。如果清理函数返回错误，调用方应收到该结果，不能因为通道关闭就静默当成成功。要验证调用者不会无限等待，可给演练自己的等待预算，并把超期与实际清理结果保存成两个字段。预算只能控制观察时间，不能替回调保证终止。每项应在独立运行里检查，避免较早用例里的通知误满足后一项。这个故障演练未执行。

注册时上下文早已取消，回调会在这里同步完成吗？

文档说明，这种情况下会立即在独立 goroutine 调用函数。立即安排与调用者已经等到完成仍是两个时点。可新建一个已取消上下文，回调开始后先发通知再等待事件，把注册返回和回调完成各自记录。不要要求调用者和回调的日志以某个没有同步的先后出现。该变体未执行，主例选择先注册、后取消。
