收到 HTTP 431，应该先缩短哪些数据？

缩短正文却仍收到 431？用虚构预算区分单个字段和总量超限，再核对客户端可以修的输入。

正文

核心要点

  • 431 关注请求头字段大小
  • 单项超限和总量超限都可能出现
  • 根据实际入口契约减少非必要字段再重提

工单客户端收到 HTTP 431，于是先把 JSON 里的备注删短。重提时请求体更小，但状态没有变化。这次服务器关注的是请求头字段的大小。先查各字段的占用和入口限制，再判断应该去掉哪个非必要字段。只缩小正文不会改变同一批请求头。

431 可以来自一个字段，也可以来自整组字段

RFC 6585 说，服务器可以因请求头字段太大而拒绝处理。状态可能由整组字段的总大小触发，也可能由某个单独字段触发。若是单字段过大，响应内容应该指出它。服务器并不承诺在所有 431 中都给出一个字段名，因为有些失败没有单独一个超限的字段。

因此拿到状态码时，先确认它与错误发生的层次一致。请求体是一份业务内容，字段则在请求的另外一部分。假设工单正文从两页缩成一行，而客户端仍读取同样的自定义字段值，单靠这些正文改动无法修复请求头约束。

具体大小边界属于实际实现。RFC 9110 不规定所有 HTTP 入口通用的字段或字段节大小限制。应用、入口代理与部署环境可能采用不同规则。应以实际端点文档和团队可查的日志为准。本例使用两个很小的假想数字来做算术对照，不把它们当成协议默认值。

固定一个纸面预算来排除请求体

下面的夹具为自己的样本定义一个只量 ASCII 值长度的规则。每个值最多十二个字符，合计不超过二十。真实 HTTP 实现可能把名称、分隔开销或其他表示规则纳入计算。这个代码没有连接服务器，也不能用来回答任何目标对线上请求的具体限制。

import {deepEqual} from 'node:assert/strict';

function assess({fields}) {
  const values = Object.entries(fields);
  const oversized = values.find(([, value]) => value.length > 12);
  if (oversized) return [431, oversized[0]];
  const total = values.reduce((sum, [, value]) => sum + value.length, 0);
  return total > 20 ? [431, 'total'] : [200, 'accepted'];
}

const wide = {label: 'x'.repeat(13)};
const combined = {label: 'x'.repeat(11), note: 'y'.repeat(10)};
const cases = [
  [{fields: wide, body: 'longer body'}, [431, 'label']],
  [{fields: wide, body: ''}, [431, 'label']],
  [{fields: combined, body: ''}, [431, 'total']],
  [{fields: {label: combined.label}, body: ''}, [200, 'accepted']],
];
for (const [request, expected] of cases) deepEqual(assess(request), expected);
console.log('Body, per-field, and total fixture cases passed.');

脚本在本机通过了四个输出断言。前两条用相同的 label 值，占十三个字符，正文一条稍长、一条为空。结果仍是 label 对应的 431。第三条为十一和十，单独每项都没超过十二，总和二十一，命中总量分支。第四条删掉假想的非必要 note，合计回到十一，规则允许通过。

这四次检查有两个独立对照。正文变短但头没变，用来定位要修的是哪一块输入。字段各自不过线却合计过线，用来说明为何不能只盯一个最大值。有近似条件的实际接口，可以用自己维护的预算和支持的字段做对应回归，但不要带着示例数字去推断协议行为。

如果产品打算控制请求额外元数据的增长，可以把必需字段和可选字段分开归档。一个导出视图用的客户端标签若反复叠加调试信息，应回看为什么这些内容需要穿过每次请求。改变契约时保留接口必需字段，和应用方确认可删的是哪一种标签。头部预算的修复不需要去掉凭据或改变身份声明。

用可以共享的诊断记录做核对

支持工单可以记录请求是被哪一层拒绝、当时的错误归类、已知非敏感字段名和大小。排查本例的两组限制，无须保存字段原值。若系统同时处理用户私有字段，先按已有日志策略过滤。记录某个字段占了多少，只证明符合你采用的计量规则，不能替整个入口契约作证。

修改客户端之后，再用相同的业务正文验证成功条件，只改这次决定要修的请求字段。如果正文和字段一起改变，恢复通过后就难判断哪项起了作用。保留调整前的拒绝与调整后的结果，即使字段符合预算，也仍要看业务端点自己是否接受这次操作。本例中的二百仅表示假想的大小规则通过。

RFC 允许减少请求头之后重新提交。这个许可没有为特定操作自动创建安全重试条件。若操作涉及创建工单，应用还需要遵守它原来关于重提、已有结果查询和重复操作的契约。只把请求头与请求体分开诊断，不会替这些业务动作建立新的行为保证。

若请求经过同一团队管理的两层入口，可以分开记下每一层是否接受字段。第一层放行只说明符合它的限制，第二层仍可能因为自己的计量方式拒绝。定位时先找提供状态的那一层，再用它所定义的边界复现。连接没有到达应用处理器时，应用日志缺少这条操作也不能证明客户端没有发出请求。

在回归说明中注明样本所带的是已经约定可公开的标记、每个字段预期占用以及哪一个规则应该先命中。下次资源管理人调整入口预算时，可以核对所有分支是否仍拿到应有结果。若接口规则不再允许这个自定义字段，应先更新客户端字段契约，不靠额外的请求尝试推断变更。

修小请求头以后，缓存可以把上一次 431 原样再交回来吗？

不可以把上一次 431 存起来供以后复用。RFC 6585 对缓存有单独的规定，缓存不得存储带这个状态的响应。假设第一条工单请求因为样本的头字段过大而失败，后来客户端删除了非必要字段。前一次拒绝不能作为当前请求的缓存命中。若修改后仍看到 431，应核对当前响应来自哪里，以及现在收到的字段是否符合它的约束。

这项约束并不要求支持工单删除诊断记录。缓存服务面向未来请求复用以前的响应，诊断记录用来解释先前为什么失败，检查目的不一样。当前脚本只计算请求字段，没实现缓存，也没有测试任何代理的存储行为。

若状态是内容已解析却不能执行其中指令，可以另看收到 HTTP 422 后如何定位具体规则。
