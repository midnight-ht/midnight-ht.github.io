Go Rows.Next 返回 false，为什么不能直接宣布结果完整？

用同一个已读前缀区分 Go Rows.Next 的正常终止、驱动失败和结果交付。

正文

核心要点

  • Next 的假值可能来自不同终点。
  • 用 Rows.Err 检查迭代失败。
  • Scan 的返回与部分结果政策分别处理。

Go 的 Rows.Next 返回 false 只说明没有可继续扫描的下一行。遍历可能已经正常结束，也可能在准备下一行时失败。循环退出后要检查 Rows.Err，才能判断这次结果能不能作为完整集合交付。

假设导出函数从数据库一路读取订单。第一条扫描成功，第二次准备记录时连接出了问题。旧实现看到 Next 变成假便返回累积的列表，调用方把只含一条的输出当成完整报告。现场排查需要记录查询启动、每次扫描成功以及终止错误。一个真实存在的第一条记录只能证明遍历走了多远，不能证明剩余输入已经全部读取。

两个 Next 停在同一位置，原因可以不同

标准库文档说明，Next 为下一条扫描准备结果。返回 false 可以是没有下一行，也可以是准备期间发生错误。判断是哪种情况依据 Rows.Err。此外，每次 Scan 前都需要先调用 Next 并取得成功。Row 与 Rows 是不同接口，后者可以在之前已产生若干成功结果后才遇到失败。Go database/sql Rows。

可以把查询合同写成三个观察点。首次 QueryContext 是否得到结果对象，每个 Scan 是否成功读出目标字段，循环停下后是否有错误。逐个检查这些位置可以区分连接未开始、当前值读不出与后续传输中断。对一个必须完整返回结果的 API，如果其中一项失败，应该明确整次读取失败，而不能只因为暂存里还有记录就报告成功。

用同一个前缀造成两种终止状态

下方是未执行的教学程序。它只使用标准库和进程内假驱动，不连真实数据库。驱动将两个固定场景名当作输入，两次都先产出编号十二。之后正常路径返回文件结束信号，失败路径返回一个能独立识别的错误。这样就能确认应用究竟检查了已读前缀，还是同时检查了终止结果。

package main

import (
    "context"
    "database/sql"
    "database/sql/driver"
    "errors"
    "fmt"
    "io"
)

var readFailure = errors.New("fixture read failure")

type demoDriver struct{}
type demoConn struct{}
type demoRows struct {
    first bool
    end error
}

func (demoDriver) Open(string) (driver.Conn, error) {
    return demoConn{}, nil
}
func (demoConn) Prepare(string) (driver.Stmt, error) {
    return nil, errors.New("unexpected Prepare")
}
func (demoConn) Close() error { return nil }
func (demoConn) Begin() (driver.Tx, error) {
    return nil, errors.New("unexpected Begin")
}
func (demoConn) QueryContext(_ context.Context, mode string, _ []driver.NamedValue) (driver.Rows, error) {
    var terminal error = io.EOF
    if mode == "broken" {
        terminal = readFailure
    }
    return &demoRows{first: true, end: terminal}, nil
}
func (*demoRows) Columns() []string { return []string{"id"} }
func (*demoRows) Close() error { return nil }
func (r *demoRows) Next(dest []driver.Value) error {
    if r.first {
        r.first = false
        dest[0] = int64(12)
        return nil
    }
    return r.end
}

func run(db *sql.DB, mode string) {
    result, queryErr := db.QueryContext(context.Background(), mode)
    if queryErr != nil {
        panic(queryErr)
    }
    defer result.Close()
    var ids []int
    for result.Next() {
        var id int
        if scanErr := result.Scan(&id); scanErr != nil {
            panic(scanErr)
        }
        ids = append(ids, id)
    }
    terminal := result.Err()
    want := map[string]error{"clean": nil, "broken": readFailure}
    if len(ids) != 1 || ids[0] != 12 || !errors.Is(terminal, want[mode]) {
        panic(fmt.Sprintf("%s: %v, %v", mode, ids, terminal))
    }
    fmt.Println(mode, ids, terminal)
}

func main() {
    sql.Register("rows-demo", demoDriver{})
    db, openErr := sql.Open("rows-demo", "")
    if openErr != nil {
        panic(openErr)
    }
    defer db.Close()
    run(db, "clean")
    run(db, "broken")
}

两个路径都应成功扫描一次并保存十二。正常组在循环停止后预期 Rows.Err 为 nil；另一组在相同的 Next 返回值之后，预期取回指定的驱动错误。程序为两条路径同时比较内容和错误。这比要求失败组没有任何数据更贴近问题，因为失败发生时第一条已经读取了。这里没有声称真实驱动的所有取消或缓冲错误都在同一时点出现。接入数据库时应另用生产驱动的实际读取方式复查。

若测试只检查对象存在、列表非空和查询提前没有错误，两条路径都会通过。只检查数量仍会失效。如果实际报告能合法只有一条，也不能据此猜测当前结果是一份截断数据。把同样的一条编号作为两个样本的输入，保留不同的终点，才能证明程序没有让数量承担错误语义。可以给日志补上正在读取的操作名与已读数量，但最终成功标记仍需由终点状态决定。

客户端如何接收部分结果

如果后端在发送之前能缓存所有结果，可以等循环和终止检查结束再构造完整响应。缓存的大小和响应等待时间需要单独评估。若协议确实要求逐项发送，就要定义后续失败怎样对可见前缀产生影响。比如客户端可以接收部分事件，但只有终止标记成功时才认定本轮没有缺口。已经发送的数据不能用服务返回的普通错误悄悄撤回。选择何种接口合同应先于是否方便调用 Next。

给流式消费者增加一个负控制。让测试接收器先取得订单十二，随后观察到错误终止。它可以展示已得到的数据，但界面不应把本轮标为完整。如果产品需要自动重试，另定义客户端从哪里恢复，以及如何防止重新交付已有记录。不要从假驱动的十二推断真实查询已经选择了稳定顺序；顺序需要独立条件。这里没有运行任何网络输出或重试。

工作者还应该把读取过程中途退出和正常耗尽分开验收。如果应用因为明细太多有意结束读取，记录这一项决定，不能把未继续读取称作服务器没有更多结果。可准备两个源行，限制消费者只接受第一条，确认它交付的是主动限定的结果。若产品需要完整列表，再用同一输入完成全部遍历并核对两个编号。这个容量限制变体没有运行。站内的 QueryRow 与 Scan 针对期望单行的读取，本例检查完整迭代何时结束。

若调用端给用户提供下载进度，也可以让两份数据都累计到一条，然后让成功组发出完整标记，失败组改成可辨认的中断。验收不要取日志最后一行中恰好出现的数字，要读消费者收到的终结结果。后台内部错误与面向调用方的返回可以不同，但它们需要指回同一次读取。这个回执对照未运行。

Scan 自己返回错误时，可以只检查 Rows.Err 吗？

不可以把末尾检查当成当前行转换的替代。可单独让驱动产出非数字文本，随后仍尝试用整数接收，直接验证 Scan 返回错误，并确认应用没有交付这条记录。Rows.Err 的文档合同是迭代过程中遇到的错误，不能据它推断所有 Scan 失败会在哪个位置重现。此变体未执行。主程序只验证第一条扫描成功之后的两种结束路径。
