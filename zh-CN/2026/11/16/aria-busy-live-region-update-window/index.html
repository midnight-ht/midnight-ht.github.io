状态文字分两次更新时，aria-busy 应该何时结束？

用库存摘要的两次写入识别忙碌窗口，分别核对 DOM 里的状态与辅助技术实际反馈。

正文

核心要点

  • 先标记区域忙碌，再分步更新
  • 相关内容写好后恢复非忙碌
  • DOM顺序和实际播报要分别验证

库存摘要里的已收数量先从四件变成五件，下一步才把最新一批货的状态从待收到改成已收。界面用了两次写入处理一次刷新。若中间状态不适合作为这次刷新的结果，更新期间可以标记 aria-busy，在两处文字都写好之后再结束这段忙碌状态。

把两次写入和一次刷新对齐

已收五件和最新一批还没收到，各自都是可以读懂的句子。在这个例子里，它们描述的是同一批货的同一次状态变更。只写好第一处就让辅助技术处理更新，接收者可能拿到一份时机不一致的摘要。我们可以先在设计上确定什么时候这两条信息合在一起才有意义。

WAI-ARIA 1.2 用 aria-busy 表示元素正在改写。设为 true 时，辅助技术可以暂缓处理这个元素拥有的内容变化，等属性恢复为 false 后将期间变更作为一次更新处理。这是规范允许的行为，产品不能用这个属性要求每种读屏组合必须只读一次，也不能指定它要逐字读哪一句话。

把标记放在同时拥有两条摘要的区域上。开始修改前把值设为 true，在两次写入之间保持它。先写已收件数，后写发货状态，再恢复为 false。忙碌标记只说明这一段什么时候算完成。最终能读到的文案仍由应用写入，没有任何内容会因为设置属性而自动补齐。

位置也要和操作范围一致。同一页可能还有另一则提醒，比如某条独立商品已经补货。如果把整个页面都放在这个忙碌范围内，独立提醒也进入了同一段等待。把属于本次库存刷新的两条消息放在一个固定区域，再给另外的更新留各自区域，团队才能说清楚哪两次写入是一起完成的。

可见日志分别记下两次修改和一次结束

下面是一个本地页面，初始区域已存在，文字分别为收到四件、最新批次待收。点一次按钮，先改件数，留一个短等待，再改发货状态。等待只用于让人看到两个步骤，没有把这个值当成辅助技术播报延迟的保证。脚本不会创建实际库存记录，也不会请求服务器。

<!doctype html>
<meta charset="utf-8">
<title>Delivery refresh</title>
<button id="refresh" type="button">Refresh inventory</button>
<div id="summary" aria-live="polite" aria-busy="false">
  <p id="count">Received items: 4</p>
  <p id="state">Last shipment: pending</p>
</div>
<pre id="log"></pre>
<script>
const byId = document.getElementById.bind(document);
const summary = byId('summary');
const count = byId('count');
const state = byId('state');
const log = byId('log');
const button = byId('refresh');
let running = false;

function report(step) {
  const busy = summary.getAttribute('aria-busy');
  log.append([step, busy, count.textContent, state.textContent].join(' | '), '\n');
}

button.onclick = async () => {
  if (running) return;
  running = true;
  log.replaceChildren();
  summary.setAttribute('aria-busy', 'true');
  count.textContent = 'Received items: 5';
  report('count changed');
  await new Promise(resolve => setTimeout(resolve, 250));
  state.textContent = 'Last shipment: received';
  report('state changed');
  summary.setAttribute('aria-busy', 'false');
  report('window closed');
  running = false;
};
</script>

检查日志的三行。第一行 busy 是 true，件数已经为五，状态为待收。第二行 busy 仍是 true，两处数据已同步。第三行里两处文字仍与第二行相同，这次只把 busy 改回 false。最后一行不能提前到第二次写入之前，否则最后的状态内容就不在同一个忙碌窗口里。

夹具的日志只是对 DOM 状态的预期观察。本文没有实际操作浏览器或辅助技术。若团队要评估真实反馈，把日志与支持的浏览器和读屏组合的操作结果并列记录。确认中间状态是否被呈现、最终信息能否被用户理解，以及用户是否可以继续原来的任务。一次听查只能说明这组实际环境如何处理。

写验收时分开保存区域状态和用户反馈

属性顺序可以先通过自动化验收。测试观察第一次修改时的属性值，并在收到最终状态之后继续读到 false。如果测试只在页面空闲时看属性，旧代码先结束窗口、后补状态也可能通过。强调两行改写各发生在何时，能直接发现这个差别。

再验证内容是否属于同一次更新。模拟始终取同一批货的数据。如果件数来自刚刷新的一批，而发货状态来自早先响应，忙碌窗口即使合得正确也无法纠正混合数据。要在产品层把两处文案绑定到当前结果，防止过期的更新混进去。夹具只有一条固定输入，未模拟服务响应乱序。

手动查验可进一步控制焦点。先停在触发按钮上启动刷新，再观察焦点是否被业务代码动过。忙碌状态本身不要求把人带到摘要。是否要将用户引导到新的工作区属于另外的交互决定。如果按钮仍是下一处有用操作，刷新完继续把它留给用户比移动焦点更贴合这个库存例子。

也可以做一个专门的错误版本。把恢复 false 的位置移到第一次写入之后，确认日志会把后来那次修改划到忙碌范围外。先用这个简单对照验证测试能检测先后反转，再决定是否需要在读屏组合里检查实际反馈差异。不能把两次 DOM 日志理解成两次必然的语音。

第二次改写失败，区域应一直处于 busy 吗？

不应长期保留这个状态。比如件数已更新，最新批次的结果却无法取到，可以先恢复两处旧摘要再显示「刷新失败」，或者由业务允许暂存可用件数并明确把收货状态标为未知。把产品选择的失败状态写进区域后结束忙碌。使用 finally 时也要注意，如果失败分支尚未决定最终文案，单独恢复属性无法修好中间内容。

若有多个刷新任务重叠，还要先认清哪个任务拥有当前这次更新。旧任务的失败回调不能替新任务将 busy 改回 false。按当前操作身份分别走成功和失败路径，比让任意异步任务结束时统一清除标记更可靠。该例从按钮启动到完成时只允许一个正在进行的操作。

如果你的问题是状态提示何时保留焦点，可以阅读状态消息怎样不抢焦点也能被发现。
