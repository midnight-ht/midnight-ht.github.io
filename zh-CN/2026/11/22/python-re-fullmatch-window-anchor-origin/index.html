fullmatch 限定了窗口，^ 为什么仍看原字符串开头？

用原位置、切片和换行控制，解释 fullmatch 窗口的起点锚点、虚拟末尾与坐标差异。

正文

核心要点

  • pos 不会重建原字符串起点。
  • endpos 可形成这次匹配的虚拟末尾。
  • 切片与窗口匹配的返回坐标不同。

长字符串里选出的数字窗口，单用 fullmatch 能通过，加上 ^ 却失败了。pos 指定从哪里开始匹配，不会把那里变成原字符串开头。若希望保留整段文本中的坐标，就先用不含多余起点锚点的模式校验这个窗口，再单独审查锚点是否真有必要。

同样三个数字，为什么有两种结果？

设原文为 xx123yy，字段位于索引二到五之间，右端不包含。字段提取器已经给出这两个位置，调用者只想检查选定区域是否全是数字，并把出错位置显示回原文。普通数字模式的 fullmatch 会覆盖这个窗口；在相同模式前加上起点锚点，却又增加一项不成立的要求：当前位置也必须符合起点锚点的语义。

Python re 官方文档的窗口匹配说明，pos 与 endpos 沿用 search 的含义。紧邻的 search 说明特别指出，pos 不完全等价于先切片，因为 ^ 指向真实字符串起点，或相应模式下的换行后位置，而不保证指向传入的起始位置。这里核对的是 Python 三点十四点十文档快照，不能只看方法名字里有“全部匹配”，就跳过这项参数合同。

可以把一次调用拆成两个问题。第一，匹配允许在哪个区间发生；第二，模式中的断言在那个位置是否成立。这个方法要求整个受限区域被匹配，不会替模式删除起点断言。数字满足第一层要求，原字符串前面的两个字母却让第二层要求不成立。遇到结果为 None，应该先问是哪项约束失败，而不是认定这个接口忽略了窗口。

先写四份独立预期，再看返回值

下面夹具把窗口、切片和虚拟末尾放到同一份完整输入上。预期直接写成字面坐标和 None，不从某一次实际输出推导另一项正确答案。随稿归档的本机执行记录针对 Python 三点十一点十五；它验证这些调用的断言，不表示本机运行了文档所标示的三点十四版本。

import re

text = "xx123yy"
line = "xx\n123yy"
line_mode = re.MULTILINE
cases = [
    (r"\d+", text, 2, 5, 0, (2, 5)),
    (r"^\d+$", text, 2, 5, 0, None),
    (r"^\d+$", text[2:5], 0, 3, 0, (0, 3)),
    (r"\d+$", text, 2, 5, 0, (2, 5)),
    (r"^\d+$", line, 3, 6, line_mode, (3, 6)),
    (r"^\d+$", text, 2, 5, line_mode, None),
    (r"\A\d+", line, 3, 6, line_mode, None),
]
for pattern, value, start, stop, flags, expected in cases:
    compiled = re.compile(pattern, flags)
    found = compiled.fullmatch(value, start, stop)
    actual = None if found is None else found.span()
    assert actual == expected, (pattern, value, expected, actual)
print("window origin, virtual end, slice spans and multiline controls checked")

第一项返回原坐标二到五。第二项加入起点锚点后失败。第三项先切出一个新字符串，数字现在位于新字符串的零位置，因此带锚点的模式成功，返回零到三。第四项只保留末尾锚点也成功，说明左右两端的规则不能简单理解为“都不受窗口影响”。

endpos 会把可匹配文本视为在该位置结束。原文的两个尾字母仍然存在，但在这次受限操作中不属于可匹配范围，所以末尾断言可以在数字后成立。pos 没有相同的重建起点作用。这种不对称是接口明确允许的行为，不应为了让一个对称直觉成立，把左右边界都按切片来解释。

这些坐标以 Python 字符串的索引为准，不是文件里的字节偏移。若原文还有多字节编码字符，不能把字符索引直接交给按字节定位的编辑器接口。本文没有构造那种转换；保留原坐标只表示没有因为切片再引入一层局部坐标，并不消除其他系统之间的单位差异。

什么时候用窗口，什么时候直接切片？

如果后续诊断需要原文坐标，窗口调用能少做一次坐标回加。验收时要同时检查匹配内容和 span，防止一个内容正确、位置偏移的修复继续进入界面。上例只用小字符串说明规则，没有测量切片分配成本，也不把不切片宣称为任何工作负载下都更快。

如果下游本来就接受独立字段，切片也可以是清楚的选择。此时新字符串有自己的起点，回报局部位置符合约定；若要显示回原文，调用方应保存字段起始索引并转换位置。不要一边改变为切片，一边继续假设返回 span 仍然是原位置。替换接口时，内容断言和坐标断言必须一起搬过去。

对已有模式也要看使用范围。一个带锚点的模式可能同时用于完整字段和长文本窗口；直接删除锚点或许修好了当前调用，却改变另一个 search 调用的接受范围。更稳妥的审查是找出各个调用入口，明确谁负责全区域匹配，再决定模式是否应该共用。这里没有建议把所有正则表达式的锚点全局删除。

还应保留一个窗口外字符不同的负控制。把前面的字母换成其他普通字符，不应该使无锚点的字段校验突然改变结果；把字段内部的一位换成字母，则必须失败。这样的两个方向比只检查成功样本更能证明边界是选对了。它们是后续项目测试建议，没有列入随稿实际运行的夹具，不能据此声称现有字段提取器已验收。

本站的输入 pattern 全值匹配讨论浏览器约束验证。完整输入与受限窗口是不同合同；不能把浏览器自动处理完整值的规则当成 Python pos 重建原点的证据。跨接口迁移时，先比较输入单位、边界和坐标，再比较模式文本是否相同。

开启 MULTILINE，窗口起点就会变成行首吗？

不会仅因为窗口从那里开始就变成行首。新增条件是原文中那个位置前面真的有换行。夹具让 xx 后面放一个换行，数字从索引三开始；MULTILINE 模式的 ^ 可以在这个真实换行之后成立。把同一模式用于没有换行的原输入，仍然失败，因此该标志没有把任何 pos 都升级为起点。

另一个控制使用绝对起点断言，即使开启 MULTILINE 也不会因为前一字符是换行就接受索引三。这样可以区分“行首”和“字符串起点”两个承诺。真实业务若允许多行，应明确要验证整份字段还是其中一行，而不是把多行标志当成窗口不匹配时的通用修复。保留真实前缀、窗口端点和最终 span，足以让下一位维护者复核这次选择。
