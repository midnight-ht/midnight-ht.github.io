放进 requestIdleCallback，为什么长循环仍会挡住页面？

用四项有界队列解释空闲预算为何不会自动打断同步工作，区分未运行页面与已执行的超时策略纯函数。

正文

核心要点

  • 空闲预算是估计而非自动抢占
  • 工作单元本身需要有界
  • 预约成功不等于队列完成

requestIdleCallback 只给回调一个空闲预算估计，不会在预算用完时自动打断长循环。把大量同步工作整体搬进去，仍可能挡住输入和渲染。工作需要先拆成有界单元，在单元之间检查 timeRemaining，剩下的另行预约；一次读到有空闲，不等于下一项任意长工作都安全。

预算估计不是抢占式执行

IdleDeadline 的 timeRemaining 返回预计截止时刻与当前时刻的差，负数夹成零。它是调用时的一次读数，不是给 JavaScript 装上一个到点必停的开关。函数读到还有一点时间后，如果立刻进入一整段昂贵计算，浏览器不会因为这份估计就替应用把那段代码切成小块。

requestIdleCallback 工作草案的 IdleDeadline 定义列出了这个计算。当前核对版本为二〇二六年十一月十二日工作草案，不是已对所有设备完成的调度实测。空闲时段怎样确定由用户代理决定，应用不能从一个读数推出固定批次数或固定完成延迟。

因此要同时控制两个尺度：每次最多做多少项，以及一项本身可能花多久。最多两项并没有给耗时建立绝对上限；若每项就是一次庞大的同步解析，两项仍可能过长。分块策略要从实际工作单元开始设计，必要时进一步拆分。这里的教学单元只是一个小整数的平方，不把它包装成真实索引构建的性能证据。

剩余时间也需要给后续工作留空间。规范的空闲时段说明提醒，布局或解析 Promise 等操作可能引出后续工作。回调中最后一行结束，不等于它触发的所有成本已经结束。给阈值留余量是应用策略，不能据此声称某个固定毫秒数在所有页面都足够。真正的任务需要记录自己的单元成本和响应表现。

四个小任务的完整页面

下面的 HTML 尚未在浏览器运行。它按顺序平方一、二、三、四，每次最多处理两项，还要求当前预算大于一个教学阈值。没有网络、数据库或真实索引。开始后暂时禁用开始按钮，避免第二次点击在第一条请求链未结束时重置同一队列。

<!doctype html>
<meta charset="utf-8">
<title>Cooperative idle chunks</title>
<button id="start" type="button">Start four teaching items</button>
<pre id="out"></pre>
<script>
const get = document.getElementById.bind(document);
const output = get('out');
const button = get('start');
let pending = [];
const completed = [];
function runChunk(deadline) {
  let count = 0;
  while (pending.length && count < 2 && deadline.timeRemaining() > 1) {
    const item = pending.shift();
    completed.push(item * item);
    count += 1;
  }
  output.textContent = JSON.stringify({count, pending: pending.length, completed});
  if (pending.length) requestIdleCallback(runChunk);
  else button.disabled = false;
}
button.onclick = () => {
  if (!('requestIdleCallback' in window)) {
    output.textContent = 'This environment does not provide requestIdleCallback.';
    return;
  }
  button.disabled = true;
  pending = [1, 2, 3, 4];
  completed.length = 0;
  requestIdleCallback(runChunk);
};
</script>

独立最终预期是完成序列一、四、九、十六，没有重复或遗漏。每批实际拿到几项则不固定：预算较少时可以一项都不处理，稍后再次预约。不能把这份规范预期写成「两帧完成」，更不能把一次排队成功当成全部计算结束。只有 pending 为空，页面才按这个教学合同重新开放开始按钮。

这条路径没有设置等待期限，页面繁忙或不可见时不能保证及时完成。规范允许用户代理没有可用空闲时段，甚至可能长时间不交付这样的回调。示例适合解释愿意等待的后台工作，不适合承担一个必须在明确时间内结束的用户提交。需要即时结果的任务，应按真实延迟合同另选执行和反馈方案。

若环境没有这项方法，页面会给出不支持的说明，不自动假装另一种计时器拥有同样空闲语义。产品可以设计自己的回退，但要说清楚回退调度不再由这个 API 提供预算。为了让演示按钮能点而悄悄换成普通定时器，会让日志看起来完整，却把要验证的机制换掉。

同时保留剩余队列与本次进度

输出里的 count 是这次处理项数，pending 是未处理数量，completed 是累积结果。三者可以识别不同错误：结果重复可能来自重复请求链，剩余不减少可能是预算始终不足，提前开放按钮可能是完成条件检查错误。只看回调触发了几次，无法区分这些情况。

已有 按经过时间计算动画进度解决的是刷新率与位移关系。这里的 count 不用于推导动画速度，也没有把空闲回调当成每帧通知。两种预约都需要明确后续生命周期，但选择哪种机会，取决于工作是要跟随呈现还是等待空闲，不由函数名里都有 callback 决定。

真实回归可以先测有界工作函数，再在目标浏览器记录回调预算、每批输入与最终序列。纯函数传入一个假的 deadline，只能说明应用怎样处理这个参数，不能测出浏览器何时会给出预算。语法检查同样不能证明输入不卡顿。应把这几类证据分开，避免一份本地数组通过就替代页面调度和响应验证。

timeout 触发时预算是零，还应该完全不做吗？

这里新增超时路径。规范的 超时调用算法给新的 deadline 设置当前时刻作为截止值，并把 didTimeout 设为 true。稍后读取剩余时间会得到零。它表达这次是因等待超过选项而执行，不表示额外获得了一段空闲时间。

应用可以选择在这种路径最多推进一个已知有界单元，再为剩余工作安排后续机会。下面只验证这个应用策略，使用手工 deadline 对象，不调用浏览器 API。普通零预算不推进，超时零预算推进一个，两个队列都独立初始化。这个选择不是规范要求必须做一个，更不是要求把整队列无上限做完。

import assert from 'node:assert/strict';
function takeChunk(queue, deadline) {
  const results = [];
  const cap = deadline.didTimeout ? 1 : 2;
  while (queue.length && results.length < cap
    && (deadline.didTimeout || deadline.timeRemaining() > 1)) {
    const item = queue.shift();
    results.push(item * item);
  }
  return results;
}
const timedOutQueue = [1, 2, 3];
const normalQueue = [1, 2, 3];
const timeoutResult = takeChunk(timedOutQueue, {didTimeout: true, timeRemaining: () => 0});
const normalResult = takeChunk(normalQueue, {didTimeout: false, timeRemaining: () => 0});
assert.deepEqual([timeoutResult, timedOutQueue, normalResult, normalQueue], [
  [1], [2, 3], [], [1, 2, 3]
]);
console.log(JSON.stringify({timeoutResult, timedOutQueue, normalResult, normalQueue}));

这份纯函数脚本已在本机 Node 执行。独立预期为超时结果一、余下二和三，普通结果为空、原三项仍在。它证明有界分支符合这里写定的策略，没有证明浏览器会在设定期限的精确时刻调用。超时等待后仍需排队，还可能被用户代理延后；真正有截止承诺的任务不能靠一个 timeout 选项宣称准点完成。
