RestartPreventExitStatus 阻止重启，会把失败也改成成功吗？

区分停止自动重启与成功退出分类，用相同退出值的两份教学单元解释结果；Linux未执行。

正文

核心要点

  • 不重启不等于退出成功。
  • 结果分类与自动重试分别取证。
  • 辅助命令不能套主进程抑制合同。

不会仅因阻止重启就把失败变成成功。RestartPreventExitStatus 抑制指定主进程退出结果的自动重试；SuccessExitStatus 才声明额外的成功退出结果。排查服务退出后没有回来，应分别读取结果分类与重试证据，不能把“不重启”当成“正常结束”。

例如程序发现不可恢复的输入，以四十二退出。维护者希望保留失败信号，却不要反复拉起它。将该值写入成功列表虽然也可能让on-failure不重试，却改变了服务结果含义。如果监控依赖失败状态，两种做法将给接手者不同信息。先决定想表达的退出合同，再选设置。

相同退出值，两份不同的服务策略

下面是隔离Linux主机的教学输入，本文没有安装或启动systemd服务。本次仅在macOS核对内联Python与Shell语法，没有管理器状态、日志或自动重启实测。下述状态均是按当前手册作出的预期，不能列为已取得的成功回执。

保存prevent.service。主程序打印标记后返回四十二，on-failure仍是基础政策，额外指令抑制该值的自动重启。启动预算作为演练防护，避免错误配置变成无界循环，不用于证明本题的退出分类。

[Unit]
Description=Prevent restart without reclassifying exit
StartLimitIntervalSec=60s
StartLimitBurst=3

[Service]
Type=exec
ExecStart=/usr/bin/python3 -c "print('EXIT42', flush=True); raise SystemExit(42)"
Restart=on-failure
RestartSec=1s
RestartPreventExitStatus=42

再保存success.service。除描述和最后的策略外，退出程序与观察条件相同。这里把四十二列为成功，所以按on-failure不应因这个结果重启。两份服务都没有持续工作，不能根据进程已经不在就判断哪份结果被当作成功。

[Unit]
Description=Classify an additional successful exit
StartLimitIntervalSec=60s
StartLimitBurst=3

[Service]
Type=exec
ExecStart=/usr/bin/python3 -c "print('EXIT42', flush=True); raise SystemExit(42)"
Restart=on-failure
RestartSec=1s
SuccessExitStatus=42

在允许创建这些专用单元名的隔离Linux主机，以root从文件所在目录执行。需要可用的系统管理器、支持这些选项的版本和/usr/bin/python3。先确认目标文件不存在且单元未加载，防止覆盖既有定义。任何前提不成立就停止，不能忽略错误继续比较。

set -eu
test "$(id -u)" -eq 0
test -x /usr/bin/python3
unitdir=/etc/systemd/system
unit_name() { printf 'zy22-%s.service' "$1"; }
for name in prevent success; do
  unit=$(unit_name "$name")
  test ! -e "$unitdir/$unit"
  test "$(systemctl show "$unit" -p LoadState --value)" = not-found
done
systemd --version
for name in prevent success; do
  unit=$(unit_name "$name")
  install -m 0644 "$name.service" "$unitdir/$unit"
done
systemctl daemon-reload
for name in prevent success; do
  unit=$(unit_name "$name")
  started=$(date -u '+%Y-%m-%d %H:%M:%S UTC')
  status=0
  systemctl start "$unit" || status=$?
  printf 'unit=%s start_exit=%s\n' "$name" "$status"
  sleep 3
  systemctl show "$unit" -p Result -p ActiveState -p SubState -p ExecMainStatus -p NRestarts
  journalctl -u "$unit" --since "$started" --no-pager
done

预期两边主退出值都保留四十二。prevent组的退出仍是未被列为成功的失败结果，但不会因此自动重启；success组被分类为成功，on-failure也不触发重试。不同版本的状态展示需原样保存，重点是主退出值、整体Result以及重试事实的组合，不提前捏造本机字段输出。

systemd.service的两项设置将成功分类和重启抑制分别定义。当前原文标识systemd 262，不等于演练主机版本。手册也说明，成功分类不改变数值与退出名称的映射；应用仍返回原值，管理器改变的是它怎样影响整体服务结果。

没有新进程，是多种路径的共同表象

只看到进程消失，可能是抑制重试、成功退出、预算耗尽、显式停止或根本没有得到下一次触发。这个表象不足以挑选唯一原因。本文两组固定主进程退出输入，并要求保存实际有效配置，才有可能把差别关联到所选设置。

尤其要检查drop-in与最终生效内容。仓库里的文件只描述打算安装什么；主机可能还有额外成功值、抑制值或其他重启政策。两份列表也可以合并出现，维护者应按实际配置重新解释，不能把教学表格盖在一份不同输入上。本文没有验证任何生产主机的覆盖项。

脚本等待三秒只是留出读取窗口，不是“未来永远不重启”的测量证明。真正解释依靠有效政策与原始退出事实，日志用于核对这次执行。若看到意外多次启动，应保留每次身份并调查生效值，而不是延长等待直到某一次看起来符合预期。

先把进程结果与管理动作分开

systemctl start自己的退出值也要记录。它描述启动请求的处理，不必等同于短命主程序的四十二。Type=exec关注可执行程序能否成功启动，程序之后立刻结束又是另一条事实。不能用终端最后一个数字替代ExecMainStatus，也不能用某次请求返回零证明业务完成。

日志时间窗口同样不是唯一执行身份。若有人在窗口内反复启动，旧标记与新标记会并列出现。把当前请求、主进程退出和对应journal条目关联，确认没有混入其他演练。两份服务不共享单元名，是为了避免上一组失败状态被下一组沿用。

若要另做未抑制的on-failure反例，应放在新的专用单元，并预先定义有界启动预算和停止步骤。本文没有运行这个第三组，也不预报准确次数。不要为了获得“重启确实发生”的截图，修改正在承载业务的服务退出政策。

选择应保留怎样的失败信号

程序把某个值定义为预期正常完成时，额外成功分类可以符合合同。若它表达需要人工处理的错误，只是自动重试没有意义，保留失败分类并抑制重试可能更合适。这个选择必须与调用方、监控和恢复责任一致，不能只因为一种设置能让状态变绿就采用它。

不重试之后谁处理，也应写清。配置本身不会修复输入或通知责任人。应让失败结果能进入实际告警或处置入口，并在修复后用业务探针验证新的运行。本文没有连接告警系统，也没有证明任何错误已恢复；它只提供退出语义的复验方法。

演练结束先保存版本、有效单元、原始结果和日志，再停止本次专用服务。确认仅由演练创建后移除这两份单元文件，并重新加载管理器；不要清除其他服务的失败记录。若保留现场用于调查，则将仍存在的单元名明确交接，避免后续同名实验覆盖证据。

四十二来自ExecStartPre，还会被这条设置拦住重试吗？

这次改变了失败进程身份。RestartPreventExitStatus只适用于主服务进程，对ExecStartPre等辅助命令没有效果。复验时复制prevent为一个全新专用单元，保留原启动预算与重启设置，增加 ExecStartPre=/usr/bin/python3 -c "raise SystemExit(42)"，并把原ExecStart替换为 /usr/bin/python3 -c "import time; time.sleep(30)"。这样四十二来自准备命令，主程序只是占位等待；准备失败是否重试，应按辅助命令失败与其他有效政策判断，不能照搬主例的抑制结论。此变体也未运行。
