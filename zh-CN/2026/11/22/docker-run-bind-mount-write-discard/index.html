RUN 的 bind mount 加了 rw，生成文件为什么下一步不见了？

用构建内外两条输出路径验证RUN bind写入寿命，保留只读失败和stage来源对照。

正文

核心要点

  • rw允许当步写，不保证持久化。
  • 保留输出应写到挂载点之外。
  • from改变挂载源的身份。

RUN 的bind mount即使加了rw，写进挂载区域的数据也只保留到这条指令结束，不会因此进入镜像层。需要留下的产物应写到挂载点之外。构建步骤里能看到文件，与下一步或最终导出仍能读取，是两项不同事实。

例如生成器把临时输入挂到/input，在里面加工并写出结果。当步打印成功，后面却找不到文件。此时先检查输出到底落在挂载内部还是外部，而不是反复重跑。rw只允许当步写，它没有将这个临时区域变成持久构建输出。

同一内容，放在两个位置检查

本例只做本地构建和文件导出，不运行nginx服务、不创建容器入口、不推送镜像。基础镜像使用本机已有的教学构建输入，内有需要的Shell工具；应记录实际解析身份，而不是把标签永久视为同一份字节。上下文只放无敏感教学文件。

先保存Dockerfile。默认artifact目标依赖的build阶段修改挂载中的input.txt，生成temporary.txt，并把加工后的字节复制到挂载外的/out。下一条RUN检查临时文件不在、外部结果仍为generated，最后仅把结果导出到scratch阶段。后面的断言是关键：当步写成功不能替代跨步骤读回。

ARG BASE
FROM ${BASE} AS readonly
RUN --mount=type=bind,source=.,target=/input \
    printf 'unexpected\n' > /input/temporary.txt
FROM ${BASE} AS build
RUN --mount=type=bind,source=.,target=/input,rw \
    printf 'generated\n' > /input/input.txt \
    && printf 'temporary\n' > /input/temporary.txt \
    && mkdir -p /out \
    && cp /input/input.txt /out/result.txt
RUN test ! -e /input/temporary.txt && \
    test "$(cat /out/result.txt)" = generated
FROM scratch AS artifact
COPY --from=build /out/result.txt /result.txt

同文件readonly目标是不加rw的负对照，默认artifact只依赖正常build阶段，不执行这条只读写入。脚本另一次明确选择readonly目标检查拒绝。BASE通过构建参数传入固定输入，所有相关FROM复用这一身份；这不是生成Dockerfile的程序。

在Dockerfile所在目录执行脚本。它创建独立上下文，原始input.txt为source。构建后分别比较源上下文与导出结果，并核对没有向上下文回写temporary.txt。预期源仍是source，产物则是generated；这两份字节不同是刻意设计的输入，不是从某个旧输出目录猜出来的结果。

set -eu
work=$(mktemp -d)
base=docker.m.daocloud.io/library/nginx:1.28.0-alpine
context="$work/context"
source_file="$context/input.txt"
result_file="$work/out/result.txt"
source_expected="$work/expected-source.txt"
result_expected="$work/expected-result.txt"
mkdir "$context"
printf 'source\n' > "$source_file"
cp Dockerfile "$context/Dockerfile"
docker version --format '{{.Client.Version}} / {{.Server.Version}}'
docker buildx version
docker image inspect "$base" --format '{{.Id}}'
docker buildx build --pull=false --build-arg "BASE=$base" --progress=plain --output "type=local,dest=$work/out" "$context"
printf 'source\n' > "$source_expected"
printf 'generated\n' > "$result_expected"
cmp "$source_expected" "$source_file"
cmp "$result_expected" "$result_file"
test ! -e "$context/temporary.txt"
status=0
docker buildx build --pull=false --build-arg "BASE=$base" --target readonly --progress=plain --output "type=local,dest=$work/rejected" "$context" > "$work/readonly.stdout" 2> "$work/readonly.stderr" || status=$?
test "$status" -ne 0
rg -i 'read-only file system' "$work/readonly.stderr"
printf 'fixture=%s\nreadonly-exit=%s\n' "$work" "$status"

本地Docker客户端与服务端均为29.8.2，Buildx为0.37.2。实际正确构建完成跨步骤断言，导出文件与外层固定预期一致，源上下文保持原内容。只读分支退出一，原始诊断明确包含Read-only file system。没有用镜像获取失败、语法错误或网络错误替代这项拒绝证据。

构建缓存优化中的bind说明记载了默认只读、rw写入仍丢弃以及挂载外输出保留的区别。Dockerfile选项表也说明写入不会提交到镜像层。它讨论构建时RUN挂载，不应照搬运行容器时可修改宿主绑定目录的直觉。

为什么源没变，而结果变了

构建器为这一条RUN提供可写的临时挂载视图。程序在视图里看到修改，随后把其中字节复制到普通层路径，后者成为后续步骤可读取的输出。保留的是明确写出去的产物，不是把挂载中的所有输入顺手打包进层。应给生成器配置合适的输出目录，再核对它确实使用了该路径。

如果生成器的输出位置不可配置，可以在同一条RUN完成生成以后，将需要的结果复制到挂载外，并当场检查内容。复制动作也要在挂载存在时完成，不能等下一条指令再去读取已经消失的临时文件。本文的cp正是这个时序，没有声称每个工具都天然支持分离输出。

反过来，文件后缀叫result也不会自动持久化。实际路径和挂载边界才决定写入归属。对真实工程，应把输入、临时工作区、保留产物三类路径列出来，并核对构建命令展开后的真实位置。只保存一段“生成成功”的日志，无法解释最终包缺少了哪个输入或产物。

给失败与缓存各留自己的说明

若只读分支没有出现预期诊断，先保留具体错误。未能访问基础镜像、前端不支持RUN mount、命令路径不存在，都没有检验到写权限。需要先恢复前提，再运行相同的负分支，不能把一个非零值直接贴成“只读验证通过”。

缓存命中也要按实际日志报告。它可以复用已有构建结果，但不说明本次重新进行了每个生成动作。本例保留构建日志以及导出后的独立cmp；重跑时若使用缓存，应注明，不能把缓存复用说成一次新的网络抓取或完整工具执行。正负分支与读回分别承担证据，不能互相替代。

最终重跑中，正常构建及stage来源分支都有步骤显示CACHED，因此不把它们记为本轮重新执行了所有生成命令。外层源内容与导出字节比较仍在本轮实际执行，只读目标也重新得到明确拒绝。

导出目录同样必须属于当前运行。脚本每次新建临时目录，避免失败后遗留的旧result.txt被误认成这次产物。集成到现有流水线时，应明确定义输出目录身份和清理方式，再绑定本轮结果。不要为了方便复用公共目录，把先前成功文件当成新的成功证明。

这个验证没有覆盖应用运行

scratch阶段只装结果文件，没有服务进程。字节正确不证明程序能启动，也不证明下游解析器接受内容。若产物是编译后的可执行文件，仍需在正确体系结构和依赖环境中启动并检查实际行为。本例没有跑这些产品检查，不提供运行性能或发布可用性结论。

同样，挂载临时写入的合同不替团队选择输入可信度。公开文本、生成代码或外部依赖，都需要自己的来源与内容审核。把它们放进临时视图不会自动降低风险，也不会确认生成器只访问了允许输入。当前上下文是最小无敏感夹具，不是对某个真实工程输入面的审计。

演练结束先保存Dockerfile、源文件、解析镜像身份、工具版本、stdout/stderr和导出读回，再清理脚本打印的本次临时目录。不要凭一个宽泛前缀删其他构建缓存或输出。这样接手者才能分别重建“输入未改”“临时写入未保留”和“产物已明确导出”三项判断。

挂载源要来自另一个build stage，而不是上下文怎么办？

这个新条件用from指定来源。下面的独立Dockerfile先在seed阶段创建stage-source，再从该阶段的/seeds挂入构建步骤，不读取默认上下文根。该分支也实际构建并导出：结果是stage-source，而独立上下文里预先放的同名文件是context-source且未改变。不能只因为名字一样，就把两份来源当成同一输入。

ARG BASE
FROM ${BASE} AS seed
RUN mkdir -p /seeds && printf 'stage-source\n' > /seeds/input.txt && \
    test "$(cat /seeds/input.txt)" = stage-source
FROM ${BASE} AS build
RUN --mount=type=bind,from=seed,source=/seeds,target=/input \
    mkdir -p /out && cp /input/input.txt /out/result.txt
FROM scratch
COPY --from=build /out/result.txt /result.txt

保存为stage.Dockerfile，用下面完整命令建立新上下文与新local导出位置，再按字节比较stage-source。

set -eu
work=$(mktemp -d)
base=docker.m.daocloud.io/library/nginx:1.28.0-alpine
context="$work/context"
source_file="$context/input.txt"
result_file="$work/out/result.txt"
expected="$work/expected.txt"
mkdir "$context"
cp stage.Dockerfile "$context/Dockerfile"
printf 'context-source\n' > "$source_file"
docker buildx build --pull=false --build-arg "BASE=$base" --progress=plain --output "type=local,dest=$work/out" "$context"
printf 'stage-source\n' > "$expected"
cmp "$expected" "$result_file"
test "$(cat "$source_file")" = context-source
printf 'STAGE_SOURCE_OK\nfixture=%s\n' "$work"

当前文档允许from引用构建阶段、上下文或镜像；选择哪种来源就应保存那种来源的身份。本问答新增stage来源，不用主例的context读回代替它。
