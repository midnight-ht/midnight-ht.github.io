ZINTER 里的 a 原分一和二，为什么结果变八？

用独立整数预期和逆序反例，说明 ZINTER 先加权再聚合，并区分零权重与成员资格；Redis 未执行。

正文

核心要点

  • 交集成员资格与结果分数是两份合同。
  • SUM、MIN、MAX 都在各来源加权后聚合。
  • 零权重不会移除交集的成员要求。

两个有序集合里的 a 分别是一分和二分，ZINTER 结果却给出八分。交集成员没算错：权重先把两份分数乘成二和六，默认聚合再求和。排查这类结果时，要把“谁留下”和“留下以后是多少分”拆开检查，不能只验成员名。

有序集合的交集还要决定结果分数

假设一个教学排序器把同一候选在两项指标中的分数相交，只保留两边都有的候选。调用者觉得交集只是筛成员，于是预期其中一边的原分数会被原样保留。但这个命令同时定义了分值计算：即使最终成员完全正确，权重和聚合政策不同，仍然会得到不同且合法的分数。

Redis ZINTER 官方文档说明，结果直接返回给客户端，不像存储版本那样写入一个结果集合，并将权重和聚合语义指向相关命令。ZUNIONSTORE 的选项说明明确每份来源分数先乘对应权重，再按求和、最小值或最大值聚合。这里依据十一月二十二日取得的当前官方快照；主命令从六点二版可用，不把最新页面出现的其他聚合形式当作所有旧版本都支持。

本稿只用有限整数分数和有限权重，两个输入是普通有序集合。环境按单机同一服务器安排；多键命令在集群环境还有额外条件，本文没有验证跨槽操作。先把数据与部署范围固定，才有可能判断算术结果是否符合预期，而不是把不同环境的错误一起归因到权重。

两个来源、三个结果，独立写出数字

第一份集合有 a 一分、b 三分，第二份有 a 二分、c 四分。交集只有 a；两个权重分别为二和三，加权贡献是二与六。因此默认求和结果为八，取最小为二，取最大为六。b 与 c 不会因为分高就进入交集，它们各自缺失一个来源成员资格。

下面是完整教学命令序列，包含后续反例和读者追问。必须在专用、初始不存在这些键的测试数据库执行，不能把示例键名当成可覆盖共享数据的授权。当前环境没有 Redis 服务或命令行工具，这些命令未执行；下文所有返回值都是根据来源和输入独立算出的预期，不能当作已观测响应。

ZADD lesson:left 1 a 3 b
ZADD lesson:right 2 a 4 c
ZINTER 2 lesson:left lesson:right WEIGHTS 2 3 WITHSCORES
ZINTER 2 lesson:left lesson:right WEIGHTS 2 3 AGGREGATE MIN WITHSCORES
ZINTER 2 lesson:left lesson:right WEIGHTS 2 3 AGGREGATE MAX WITHSCORES
ZRANGE lesson:left 0 -1 WITHSCORES
ZRANGE lesson:right 0 -1 WITHSCORES
ZADD lesson:control-left 3 a
ZADD lesson:control-right 2 a
ZINTER 2 lesson:control-left lesson:control-right WEIGHTS 1 10 AGGREGATE MIN WITHSCORES
ZINTER 2 lesson:left lesson:right WEIGHTS 0 0 WITHSCORES

验收时要把前面三条交集结果按成员与数值检查为 a 八、a 二和 a 六。客户端可能对带分数响应采用不同嵌套形状或字符串表示，这不改变本题要验收的成员与数学值。不要要求一张截图的排版在所有协议版本都相同，也不要把解析响应格式的问题混进加权算法。

两次范围查询用于核对来源仍为原来的两对成员和分数。返回型交集没有把加权结果写回来源；若应用随后看到来源发生变化，应继续检查其他写入调用，而不是把八分自动归因到原集合已经被修改。教学命令中的 ZADD 是显式准备数据，不能把准备阶段的写入和交集命令的行为混为一谈。

先取原分最小再乘权重，会在哪里失败？

另设独立控制集合，左边 a 三分，右边 a 二分，权重改为一和十。右侧原分更小，但加权贡献是三与二十，所以正确最小值为三。如果先凭原分选中右边，再乘它的权重，就会错误得到二十。第一组数据恰好让原分和贡献的大小顺序一致，仅用它无法证明计算先后没有写反。

这就是为什么反例不能只换一个无关成员。它必须改变能区分两种算法的条件，让错误算法和正确合同产生不同结果。控制集合使用独立名字，不修改第一组的分数，避免后面追问时误以为仍在使用最初输入。真实测试也应保留每一组初始化及预期，而不是在同一个共享排行上连续改值后省略当前状态。

选择聚合政策时，求和适合业务明确要累计贡献的合同；最小和最大则表达另一种合并判断。本文不替评分业务决定哪一种公平或最有效，也不从命令语义推断权重已经经过统计校准。先由业务写出几组应该排名如何的样本，再用对应命令复核，才能判断实现是否符合那一份政策。

还应检查输入键顺序与权重位置。权重按各来源位置对应，交换来源却忘记交换权重，会改变贡献。命令成功不代表业务标签仍然对应正确指标。此处没有运行交换顺序的额外用例，也没有做性能测量；建议项目另存字段到来源的映射，避免日志只留下无法解释的一串数字。

本站的集合交集基数阈值讨论能否按数量判断达到门槛。这道题多了一份分值合同：知道交集只有一个成员，仍然不知道它应该是八、二还是六。把成员资格、分值和客户端解析分别验收，比只检查命令没有报错更能定位错误。

权重设成零，是不是就忽略该来源的成员要求？

新增条件是零权重。它改变数值贡献，不会把交集变成只看另一边的筛选。最后一条命令把两边权重都设为零，预期仍然只返回 a，分数为零；b 和 c 仍各缺一个来源，不会出现。这里的零值也不能被客户端当成“没有结果”，应同时检查成员存在与数值为零。

若业务真要忽略某项来源，需要重新定义参与交集的来源列表，而不是只把其权重置零。这样做会改变成员资格，应该另行评审。待能实际运行 Redis 时，保存服务版本、测试数据库初始键状态、完整命令、原始响应及退出状态，再将这些预期与观测逐项比较；尚未执行的教学命令不应进入性能或生产验收结论。
