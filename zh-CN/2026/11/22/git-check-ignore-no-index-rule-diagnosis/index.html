check-ignore 对已跟踪文件没输出，怎样核对它会匹配哪条规则？

分开读取忽略规则与索引，用no-index诊断已跟踪路径，并识别否定模式的verbose输出。

正文

核心要点

  • 规则诊断不改变索引身份。
  • 保存来源、行号和模式再作判断。
  • verbose否定模式不能解释成排除。

用 git check-ignore --no-index -v 可以跳过索引检查，查看一个路径匹配的忽略规则来源、行号和模式。这个选项只改变诊断方式，不会把已跟踪文件移出索引。普通调用对已跟踪路径没有输出，因此沉默本身不能说明通配符写错了。

假设一份配置早已进入索引，维护者后来增加忽略模式，随后用 check-ignore 排查却什么也没看到。此时要分两步问：这个路径当前是否已被跟踪；如果只检查规则，它会命中哪条。将两种问题混在一起，容易反复改动正确的模式，甚至误把诊断选项当作一次清理动作。

在一次可丢弃的索引里观察两份事实

下面的脚本只操作新临时仓库，不提交、不连接远端。文件是无敏感教学字符串。先创建模式，再强制加入对应文件，让“已在索引”和“模式本来会匹配”同时存在。这样无需用真实项目的配置做实验，也不需要删除任何已有索引项。

set -eu
work=$(mktemp -d)
git init -q "$work"
cd "$work"
printf '*.log\n' > .gitignore
printf 'tracked\n' > settings.log
git add -f settings.log
before=$(git ls-files --stage -- settings.log)
git --version
status=0
git check-ignore -v settings.log > default.txt || status=$?
test "$status" -eq 1
test ! -s default.txt
git check-ignore --no-index -v settings.log > diagnostic.txt
printf '.gitignore:1:*.log\tsettings.log\n' > expected.txt
cmp expected.txt diagnostic.txt
test "$(git ls-files --stage -- settings.log)" = "$before"
test "$(cat settings.log)" = tracked
cat diagnostic.txt
git ls-files -- settings.log
printf 'DEFAULT_SILENT_AND_INDEX_UNCHANGED\nfixture=%s\n' "$work"

本地 Git 2.50.1 实际执行：普通 verbose 调用没有输出，返回一；增加 no-index 后打印 .gitignore:1:*.log 与 settings.log，返回零。独立的索引清单仍列出 settings.log，stage记录与诊断前完全相同，文件仍读到 tracked。最后的标记证明脚本中的这些断言已通过，不只是某条命令碰巧完成。

这里没有创建提交，索引里已经有文件就足以触发该差别。后续提交是否包含它，是另一个交付步骤；本文没有执行提交。示例把输入状态压到最小，是为了让输出差异归因于是否检查索引，而不是仓库历史、远端分支或其他工具。

check-ignore 官方手册明确说明，默认不显示已跟踪文件，no-index在检查时不看索引。该选项适合排查路径为什么曾被加入，或为已被强制加入的路径调试模式。它没有承诺自动修复既有跟踪关系，也不是忽略规则之外的安全隔离机制。

来源与行号，比“有一行输出”更有用

verbose结果包含规则来源、该来源中的行号、模式与路径。示例只有一条根目录规则，所以可以把整行与固定预期比较。真实仓库可能还有目录内规则、本地排除或用户配置，维护者要按实际输出定位具体来源，再读完整的相关上下文，而不是只搜索仓库根的一个文件。

行号是本轮文件布局的定位信息。规则文件被编辑后，旧行号可能已经指向别的内容。交接时保存实际规则文件或其内容身份、调用目录和完整参数，再附上输出。只有终端截图中的一段路径，下一位维护者未必能重建当时的规则集合。

同样，路径字符串应与调用位置关联。一个子目录下的相对名称，与仓库根下同名文件未必是同一个对象。先确认正在检查的路径，再解释结果；不要把另一个工作副本的诊断拼到这份索引记录上。本文的临时目录在最后打印，方便把每份输入与回执连起来。

诊断以后，先决定要改变哪份状态

如果问题只是验证模式，保留索引即可，no-index结果已经提供所需读数。如果团队决定不再跟踪，则需要单独审查当前索引、后续提交与同事更新的影响。停止跟踪也不会撤销历史中的内容。旧的相关问题已有站内说明，不在这里把删除与规则诊断混成一串不可审查的命令。

尤其不要把没有输出解释成“该文件不存在”。check-ignore是忽略规则工具，不是文件枚举工具。应按任务分别读取工作文件、索引和规则来源。每个工具都返回自己范围内的事实，一份空结果不能替其他范围作结论。

本例保留了一个有意设计的反例：规则确实命中，文件却仍在索引。它推翻的是“命中规则就必然停止跟踪”的推断，而不是证明Git执行失败。诊断完成后状态没变，恰好符合这个只读查询的职责。若脚本随后执行别的索引命令，应另记其输入与结果，不能算到查询名下。

把查询回执放进可复验的交接

正式排障可先写出要验证的路径与预期规则，再保存工具版本、有效文件、默认调用和跳过索引的调用。遇到差异先查输入是否一致。若根本没有取得完整规则来源，结论应停在“尚未定位”，而不是为了给出确定答案随便挑一条相似模式。

对于自动化收集，输出格式也应由明确合同处理。示例用简单文件名与固定行作比较，没有覆盖换行、制表符或任意路径名。实际系统若接受这些名称，应另外设计机器可解析的输入输出，并验证边界；不要把这个教学脚本的文本比较直接推广为通用解析器。

这个验证也没有检查构建上下文或发布包是否包含该文件。一个路径没有被默认加入，不表示其他复制流程不会取得它。发布输入需要按各自工具再核对，不能用Git规则诊断给整个交付渠道签收。对本文的具体任务，到规则来源明确、索引身份未变，证据链就应停在这里。

verbose 打印了否定模式，表示文件被排除了吗？

不表示。另一次隔离对照在规则第二行加入 !keep.log，创建未跟踪keep.log。verbose打印这条带感叹号的模式；本地同版Git该次还返回零。官方说明这种否定模式表示路径未被排除。因此这个新条件不能靠“有输出”或这个版本的零退出值判断排除，应读取模式含义。主实验只有普通星号模式，这里首次加入否定规则，没有改变settings.log的跟踪结论。
