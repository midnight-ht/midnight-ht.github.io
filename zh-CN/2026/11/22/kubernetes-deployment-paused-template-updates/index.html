Deployment 镜像已经改了，暂停状态下为什么没有新发布？

把暂停期间的模板修改与恢复后的发布身份分开核对；集群示例未运行。

正文

核心要点

  • 暂停时模板更新不触发新rollout。
  • 恢复后检查最终模板而非命令回显。
  • 暂停期间不能直接执行回滚。

暂停Deployment时，修改Pod模板不会触发新的rollout；恢复后才按累积后的模板推进。API接受镜像修改，说明期望配置已改变，不等于新副本已经开始替换旧副本。先检查是否处于paused状态，再关联模板、ReplicaSet和当前代次。

例如维护者先改镜像，再改CPU请求，希望两项一起进入下一次发布。暂停提供了一个积累模板修改的窗口。它不是把现有Pod冻结，也不是停止应用；不能因没有新的rollout就宣称原有工作负载已经停下，更不能把命令回显当作新版本运行证据。

从已经完成的基线开始

以下是隔离集群的完整复验输入。本文未连接集群、未运行kubectl，也没有执行下面的对象oracle。只完成YAML解析、Shell语法和Python语法检查，不能据此报告暂停、恢复或应用运行通过。读者需要允许创建专用命名空间的上下文、可用控制器及可取得的镜像。

保存deployment.yaml。两个副本与HTTP就绪探测是教学配置，不代表产品容量或业务健康要求。初始镜像与后续的alpine标签都应在目标环境确认可用；这里没有提供不可变镜像身份保证，也不把一次标签字符串相同视为字节相同。

apiVersion: apps/v1
kind: Deployment
metadata:
  name: zy22-pause
spec:
  replicas: 2
  selector:
    matchLabels:
      app: zy22-pause
  template:
    metadata:
      labels:
        app: zy22-pause
    spec:
      containers:
        - name: web
          image: nginx:1.28.0
          resources:
            requests:
              cpu: 50m
          readinessProbe:
            httpGet:
              path: /
              port: 80

下面保存为check.sh。替换context占位值，确认命名空间尚不存在，且只有本次演练会修改这些对象。首次创建失败就停止，避免接管旧演练。快照函数把Deployment和当前命名空间的ReplicaSet列表保存在同一阶段名称下，后面的检查只取属于同一个Deployment UID的对象。

set -eu
context=REPLACE_WITH_ISOLATED_CONTEXT
namespace=zy22-pause-lab
deploy=deployment/zy22-pause
k() { kubectl --context "$context" --namespace "$namespace" "$@"; }
snapshot() {
  k get "$deploy" -o json > "$1-deployment.json"
  k get replicasets -o json > "$1-replicasets.json"
}
k create namespace "$namespace"
k apply -f deployment.yaml
k rollout status "$deploy" --timeout=120s
snapshot initial
k rollout pause "$deploy"
k set image "$deploy" web=nginx:1.28.0-alpine
snapshot image
k set resources "$deploy" -c=web --requests=cpu=100m
snapshot resources
k rollout resume "$deploy"
k rollout status "$deploy" --timeout=120s
snapshot resumed
python3 inspect.py

先等待初始发布完成，才能把后面“没有新rollout”与暂停关联。如果基线还在拉镜像、探测失败或控制器未观察到当前配置，先解决这些前提，不要继续套用暂停实验的预期。初始失败需要自己的原始诊断，而不是用最后一次恢复成功覆盖。

比较模板和实际发布对象

保存inspect.py。它读取真实命令生成的四阶段快照，检查两次暂停修改都留在spec里，暂停期间没有新增归属于该Deployment的ReplicaSet，再检查恢复后的可用数量和最终模板。不要为了让脚本变绿而手工填写这些JSON，本文也没有用虚构快照替代集群回执。

import json
from pathlib import Path


def read_stage(name):
    deployment = json.loads(Path(name + "-deployment.json").read_text())
    items = json.loads(Path(name + "-replicasets.json").read_text())["items"]
    uid = deployment["metadata"]["uid"]
    owned = [item for item in items if any(
        owner.get("uid") == uid and owner.get("controller") is True
        for owner in item["metadata"].get("ownerReferences", []))]
    return deployment, owned


def web(template):
    return next(item for item in template["spec"]["containers"] if item["name"] == "web")


expected_image = "nginx:1.28.0-alpine"

initial, initial_sets = read_stage("initial")
uid = initial["metadata"]["uid"]
baseline_ids = {item["metadata"]["uid"] for item in initial_sets}
assert baseline_ids
for stage in ("image", "resources"):
    deployment, sets = read_stage(stage)
    assert deployment["metadata"]["uid"] == uid
    assert deployment["spec"]["paused"] is True
    assert web(deployment["spec"]["template"])["image"] == expected_image
    assert {item["metadata"]["uid"] for item in sets} == baseline_ids
    if stage == "resources":
        assert web(deployment["spec"]["template"])["resources"]["requests"]["cpu"] == "100m"
resumed, resumed_sets = read_stage("resumed")
assert resumed["metadata"]["uid"] == uid
assert not resumed["spec"].get("paused", False)
assert resumed["status"]["observedGeneration"] >= resumed["metadata"]["generation"]
assert resumed["status"]["replicas"] == resumed["spec"]["replicas"]
assert resumed["status"]["updatedReplicas"] == resumed["spec"]["replicas"]
assert resumed["status"]["availableReplicas"] == resumed["spec"]["replicas"]
assert any(web(item["spec"]["template"])["image"] == expected_image
           and web(item["spec"]["template"])["resources"]["requests"]["cpu"] == "100m"
           for item in resumed_sets)
print("PAUSED_EDITS_AND_RESUMED_TEMPLATE_OK", uid)

预期在image阶段，Deployment模板已经写入新镜像，而同UID拥有的ReplicaSet仍为基线集合；resources阶段模板还包含新的CPU请求。恢复之后，控制器观察到当前代次，发布完成，并出现同时包含两项最终设置的ReplicaSet。这个比较没有要求全局RS总数固定，也没有把无关对象计入。

这些断言适用于单一控制者的教学窗口。如果其他人、GitOps控制器或自动化同时改模板，最终输入就不同，需保存变更并重新解释。一次失败的集合比较不能直接宣布Kubernetes违反暂停合同。对象归属、更新时间和有效模板必须来自同一轮观察。

官方暂停与恢复说明明确给出暂停后修改镜像、再修改资源、恢复后一起发布的流程。它说明的是模板变更触发rollout的边界，不能从“暂停”一词推导出任意控制行为都停止。现有副本仍由其正常机制维护。

看不到新对象，不一定只有一个原因

如果只保存“RS数量没变”的截图，无法知道模板有没有被API接受，也不知道控制器是否有权推进。先查spec.paused，再查模板确实包含两次修改，最后看同UID对象及事件。若命令因权限或连接失败，没有形成预期输入，就不能算作暂停生效的对照。

暂停状态下的镜像期望与运行副本的镜像可以不同，这是本题的关键张力。对外报告应说清“模板已更新、尚未恢复rollout”，而不是一句“镜像已升级”。恢复后也要重新读取实际模板和发布状态，不能把暂停时的配置回执转贴成运行回执。

Pod本身还可能因为正常健康维护或其他原因被替换。因此本例的核心不是承诺所有Pod UID永远不变，而是模板修改在暂停时不触发新rollout。若任务另有不中断请求的目标，需要服务流量、就绪和可用性证据；本文没有Service资源，也没有请求探针实测。

恢复是继续推进，不是自动签收

rollout resume只解除这个暂停条件。新镜像无法获取、资源不足、就绪探测失败，仍会使后续发布受阻。保留恢复命令、等待结果、当前代次和模板快照，才能区分“已解除暂停”与“本轮发布完成”。这组示例没有给任何业务版本签收。

观察之间还有时间差。两份JSON不是跨对象原子快照，控制器可能在读取期间继续推进。如果数据处在边界状态，记录读取时间与原始结果，按同一UID重新取样；不要删掉不符合预期的记录只留一份成功材料。正式交接应允许缺失与不确定性出现。

演练结束前保存四阶段输入、命令结果、实际控制器版本与相关事件，再确认专用命名空间只有本轮资源。需要清理时使用同一个明确context删除它。换了上下文、重建同名Deployment或采用另一模板，都要重新关联UID，不能把不同运行拼成一条连贯发布时间线。

暂停期间能直接回滚Deployment吗？

不能直接沿用这个暂停状态执行回滚。官方说明，需要先恢复Deployment，才能回滚。这首次改变操作类型：主例是累积修改后继续发布，问答是要选择旧修订。恢复可能开始推进当前累积模板，因此还应按团队恢复方案确认目标修订、镜像与配置，再执行相应操作；不能把resume本身解释为已经回到旧版。本文未执行回滚。
