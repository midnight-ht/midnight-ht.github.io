只想抓当前函数，为什么另一个线程的 print 也进来了？

以主动 join 的线程夹具区分全局输出替换、退出恢复和显式流；另验 stderr 的独立目标。

正文

核心要点

  • redirect_stdout 修改全局 sys.stdout。
  • 退出恢复不等于期间只有当前函数能写入。
  • 显式流参数和 stderr 目标应分别验收。

只想收集当前函数的输出，另一个线程的 print 却也进了 StringIO。redirect_stdout 临时改的是全局 sys.stdout，不是给当前函数划出一个专属输出通道。退出 with 会恢复入口，但恢复时点不能证明期间只有这个函数使用过它。

上下文限定了时间，没有限定所有调用者

设一个小工具把原本直接打印的报告抓成字符串。工具本身在主线程运行，同一进程还有一个工作线程打印进度。主线程以为捕获范围只是自己的调用栈，结果保存的报告里混入 worker。若随后把这份文本当作机器可解析结果，问题看起来可能像报告格式随机坏了，实际却是输出入口被共同使用。

contextlib.redirect_stdout 官方说明明确指出，对 sys.stdout 的修改有全局副作用，因此不适合库代码和大多数多线程应用。这里核对 Python 三点十四点十文档，并不把普通 with 块当成线程隔离机制。它适合某些受控工具脚本，这和在共享运行环境里随意替换输出入口，是不同选择。

关键要分开“何时恢复”和“谁能观察到修改”。上下文管理器可以在退出时恢复原目标，同时在整个进入期间让其他使用当前全局入口的代码看到新目标。两份性质可以同时成立，不能因为清理写得正确，就判定并发作用范围也符合预期。异常后的恢复也不会把已经写入捕获流的其他文本自动分离出来。

用主动加入的线程构造确定顺序

完整夹具先保存原输出对象，再打印 main，随后启动一个只打印 worker 的线程并等待它结束。顺序由主线程先打印和主动等待决定，不依赖延时碰运气。它已在本机 Python 三点十一点十五执行，实际源码、运行时、标准输出和退出状态归档；文档版本仍与运行版本分开记录。

import sys
from contextlib import redirect_stderr, redirect_stdout
from io import StringIO
from threading import Thread

read_capture = StringIO.getvalue
original = sys.stdout
captured = StringIO()
with redirect_stdout(captured):
    print("main")
    worker = Thread(target=lambda: print("worker"))
    worker.start()
    worker.join()
assert read_capture(captured) == "main\nworker\n"
assert sys.stdout is original

def emit(stream, message):
    stream.write(message + "\n")

explicit = StringIO()
emit(explicit, "owned")
assert read_capture(explicit) == "owned\n"
out, err = StringIO(), StringIO()
with redirect_stdout(out), redirect_stderr(err):
    print("out")
    print("err", file=sys.stderr)
assert read_capture(out) == "out\n"
assert read_capture(err) == "err\n"
print("global capture, restoration, explicit stream and stderr separation checked")

捕获文本的完整预期是两行，依次为 main 和 worker。这个预期不是说任何真实服务都必然按同样顺序输出，而是证明在本例中，另一个线程在重定向期间使用当前全局入口，其输出同样被捕获。退出后还检查输出对象的身份确实恢复，避免把“混入其他线程”与“没有恢复”混成同一个故障。

这里没有做任意并发读写压力测试。工作线程只有一个简单动作，而且在作用域退出之前已经结束；没有后台任务继续使用流，也没有日志框架、自定义线程局部输出代理或其他捕获器参与。真实应用若已经替换过输出对象，应检查那一层合同，不能从这个标准环境演示推断所有进程输出都完全一样。

还应注意，保存过旧流引用的代码可能不再查找当前入口。本题说明使用当前 sys.stdout 的打印会受到修改，不宣称所有写入路径都会被强制改道。文件描述符写入、子进程输出和已配置目标的日志处理器也不能只凭一次 print 捕获实验推导结果。官方另说明它不影响子进程输出；本机夹具没有启动子进程，不能把这条文档结论写成实测。

工具函数能改时，先把接收者显式传进去

夹具的 emit 接收一个流对象，只向指定目标写入 owned 一行。它不需要临时替换全局入口，也不假设当前调用者拥有整个进程的打印。对于自己维护的报告函数，这样能让测试直接传入内存流，让命令行入口传入其实际输出目标，各层的责任更容易判断。

这不是自动给任意旧库添加隔离的包装器。如果第三方函数内部硬编码 print，修改外层函数签名并不会改变它；需要库本身支持流参数、返回文本或其他受控输出接口。无法修改时，应根据工具是否独占运行环境作选择，不能承诺一个全局替换就能安全包住所有并发代码。本文没有接入第三方库或生产报告系统。

项目验收还要分别看谁拥有流的生命周期。示例由测试自己创建内存流并读取结果，不替被调用者关闭它；实际文件或网络输出可能有额外的关闭与错误规则。给函数传入流，不意味着它就可以随意关闭调用方提供的对象。这里没有实现复杂资源协议，只展示显式接收者能够消除哪一种全局修改。

本站的ContextVar 任务快照说明另一类上下文状态如何在任务创建时传播。名称都含上下文，不代表 sys.stdout 会因此变成任务变量。判断隔离应看实际存放位置、读取入口和传播合同，而不是看语法是否用了 with 或函数名是否含 context。

对捕获文本做验证时，也别只搜索 main 是否出现。混入额外内容时，这个包含检查仍然通过。应按用途检查完整文本、结构或明确允许的附加内容；本题用完整两行预期，是为了把共享入口这个现象直接显露出来，而非把额外行偷偷过滤掉后报告成功。

stdout 被重定向，stderr 也会自动进去吗？

新增条件是另一个标准错误流。夹具使用独立的两个内存对象，分别重定向输出与错误，再让两次打印明确选择不同目标。预期 out 只包含 out 行，err 只包含 err 行。错误流需要自己的重定向，不会因为输出流被换掉就自动使用相同对象。

这份控制也不是建议把两类文本永远分开：有的工具有意合并它们，但应该把合并写成明确选择。若要收集结构化报告，可以让报告数据走返回值或指定流，让诊断走另外的目标，再按各自合同验收。不要把退出后恢复成功当作内容来源已经隔离的凭据；先确认谁在那个时段共同使用了入口，再决定能否接受这类捕获。
