Base64 Strict 为什么仍接受输入里的换行？

用正确尾位、错误尾位、CRLF 和无填充输入，核对 Strict 的具体边界；Go 程序未执行。

正文

核心要点

  • Strict 要求未使用的尾部填充位为零。
  • CR 和 LF 在严格模式下仍被忽略。
  • 无填充格式与外层单行规则应单独选择。

Go 的 Base64 解码器开启 Strict 后，输入中间带换行仍可能成功。这个严格模式要求尾部未使用的填充位为零，却继续忽略回车和换行。如果上层协议明确要求单行文本，就必须另验字符格式，不能把一个方法名当成全部输入政策。

严格究竟严格在哪一层？

考虑两段很短的编码文本 Zg== 和 Zh==。普通解码下，两者都能产生字节 f；后者的尾部位却不满足严格解码要求。再把第一段中间加一个换行，它的尾部位没有变，严格解码仍能成功。看似矛盾的三种结果，其实分别在检查有效数据位、未使用的尾位和被忽略的字符。

encoding/base64 的 Strict 文档明确规定尾部填充位必须为零，并紧接着说明回车与换行仍被忽略。本文核对 go1.27.4、二〇二六年十一月十日发布的包文档；该方法从一点八版加入。文档引用的尾位规则不能扩成一个没有明确写出的“只接受我想要的所有文本形式”。

因此先把接收合同写成两部分。解码器要验证它负责的编码规则；应用还要决定传入文本是否可以折行，采用哪套字母表，以及是否允许省略填充字符。只给函数加上严格开关，却不列出这些条件，后来另一个调用者很难知道这次成功究竟保证了什么。

一个完整表格，分别看成功和失败

程序以独立的字面输入和预期组成表格，不把普通解码器的结果当成严格解码器的正确性来源。它包含标准输入、非零尾位、两种换行形式和后面追问的无填充模式。当前机器没有 Go 工具链，下面程序未执行；断言和输出是根据文档制定的教学验收方案，不是实际通过证明。

package main

import (
    "encoding/base64"
    "fmt"
    "strings"
)

func main() {
    standard := base64.StdEncoding
    raw := base64.RawStdEncoding
    strict := standard.Strict()
    strictRaw := raw.Strict()
    cases := []struct {
        encoding *base64.Encoding
        text, want string
        wantError bool
    }{
        {standard, "Zg==", "f", false},
        {standard, "Zh==", "f", false},
        {strict, "Zg==", "f", false},
        {strict, "Zh==", "", true},
        {strict, "Z\ng==", "f", false},
        {strict, "Z\r\ng==", "f", false},
        {raw, "Zg", "f", false},
        {standard, "Zg", "", true},
        {strictRaw, "Zh", "", true},
    }
    for _, item := range cases {
        decoded, err := item.encoding.DecodeString(item.text)
        failed := err != nil
        if failed != item.wantError { panic("wrong error status") }
        if !failed && string(decoded) != item.want { panic("wrong decoded bytes") }
    }
    containsLineEnd := strings.ContainsAny("Z\ng==", "\r\n")
    if !containsLineEnd { panic("outer grammar control") }
    fmt.Println("zero pad bits, ignored CRLF, unpadded input and outer grammar checked")
}

第一组普通模式下的两项成功，说明最终字节相同不足以证明原始编码文本满足同一规范。严格模式接受 Zg==，拒绝 Zh==，把尾位条件单独显露出来。接下来的换行样本有正确尾位，所以它们继续成功；如果只运行这两项，就会错以为严格开关完全不起作用。

程序还单独检查外层单行规则能看到换行。它没有把字符串清理后再声称原输入没有换行，因为那会改变要验收的对象。实际协议若允许折行，可以接受这种输入；若不允许，应在相应边界拒绝并说明原因。示例没有实现网络接口，也没有提供认证、签名或授权规则的替代方案。

解码失败时还要留意返回数据。官方说明可能返回部分解码结果和输入错误，因此夹具对预期失败只检查确实报错，不使用错误伴随的字节充当有效消息。完整消息需要全部满足合同，不能看到前面已经产出几字节就提前交给业务处理。要调试时可以保留受控错误信息，但本稿没有采集任何真实敏感载荷。

原始文本与解码字节各有自己的验收

在仅关心二进制内容的内部工具中，允许不同文本形式表达同一份字节或许完全合理。此时应把这种宽容明确写下，避免下一位维护者把它当成漏洞式异常。在要求固定输入格式的接口中，则要检查原始文本的合同，不能用“解出来一样”替代它。规则选择来自协议，而不是哪个函数名听起来更强。

如果上层希望输出一种统一形式，可以明确选定编码器，并把这一目标与输入接受范围分开评审。但本文没有建立跨系统规范化文本算法，也没有承诺对任意字母表、填充选项和特殊空白都提供等价转换。看到回车换行被忽略，不代表所有空白字符都被忽略；这里没有将该行为外推给空格、制表符或任意其他字符。

完整验收还应检查错误处理路径是否丢掉失败标志。一个包装函数如果在返回字节后忘记返回错误，可能让原本被严格解码拒绝的输入继续流转。应对包装层另写失败样本，检查最终业务没有接受部分数据。这个建议超出当前未执行表格，不应写进报告作为已经运行过的服务测试。

本站的HMAC 比较中的表示选择解释字节与文本表示为什么不能随意混用。本题不讨论摘要验证，而是对解码器的具体接受条件负责：相同字节、尾位正确和文本符合外层格式，分别需要证据。一个成功布尔值不应承担三个没有拆开的承诺。

没有等号的 Zg，也应该被标准模式接受吗？

新增条件是省略填充字符。官方把 RawStdEncoding 定义为标准字母表但不带填充的形式；它与标准模式使用同一批字母，不表示对末尾等号有相同要求。因此表中的 Zg 在原始无填充模式下成功，在标准带填充模式下失败。选择哪种形式应根据发送方与接收方的共同协议。

去掉等号也没有取消尾位规则。无填充模式再开启严格校验时，Zh 仍因未使用尾位不为零而失败。这里把“是否带填充字符”和“最后那些没有贡献到输出的位是否为零”分开，避免认为没有等号就没有任何尾部条件。若将这份程序移到有 Go 的机器，应保存版本、源码哈希、输出和退出状态，并保持这些独立输入不被预处理步骤悄悄改写。
