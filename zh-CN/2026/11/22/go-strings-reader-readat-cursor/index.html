ReadAt 读过 cd，下一次 Read 为什么还从 ab 开始？

用交错读取和部分 EOF 预期区分随机访问、顺序游标与显式 Seek；Go 程序未执行。

正文

核心要点

  • ReadAt 不会推动顺序读取的游标。
  • 短读时只按返回数量解释有效字节。
  • 显式 Seek 才会改变随后顺序读的位置。

ReadAt 已经从 abcdef 中读出 cd，下一次 Read 却仍然读到 ab，这不是对象忘记保存进度。按偏移读取和顺序读取使用不同的位置合同：前者不会推动后者的游标。把探测位置当成消费进度，会让随后解析重复读取本来以为已经跳过的内容。

偏移参数不是一次隐含的 Seek

设一个解析器先查看中间两字节，再从开头完整读取。它想复用同一个只读字符串对象，避免为了探测先消耗顺序输入。若调用者把每一次“读取”都理解为前进，就可能在探测后补上另一段跳过逻辑；也可能反过来省掉真正需要的定位步骤。正确选择取决于接口是否承诺改变顺序位置。

Go io.ReaderAt 文档规定，有底层寻址偏移时，ReadAt 不应受该偏移影响，也不应改变它。strings.Reader 的方法文档说明该方法实现这份接口。本文核对 go1.27.4、二〇二六年十一月十日发布的包文档，把接口合同与具体对象连起来，而不是仅凭方法名猜测。

这里没有必要把随机访问看成先移动、读取、再恢复的一串公开操作。调用方只应依赖它承诺的结果和位置关系。若对一个只实现普通 Reader 的对象提出同样要求，则证据不足；普通顺序读取接口并没有因此自动增加按偏移访问的能力。接入网络流或其他自定义读取器时，应重新检查实际类型和接口。

每次都检查字节、数量和顺序位置

以下完整 Go 程序针对固定 ASCII 字符串。先读偏移二处的两字节，再顺序读两字节；接着从最后一个字节开始请求两个字节，并检查部分结果与错误；最后一项显式移动位置，服务后面的新增条件追问。当前机器没有 Go 工具链，代码未执行，输出与断言是预先制定的验收方案。

package main

import (
    "errors"
    "fmt"
    "io"
    "strings"
)

func check(n int, err error, buffer []byte, want string, atEOF bool) {
    if n != len(want) { panic("wrong byte count") }
    if string(buffer[:n]) != want { panic("wrong returned prefix") }
    if atEOF {
        if !errors.Is(err, io.EOF) { panic("expected EOF") }
    } else if err != nil { panic(err) }
}
func main() {
    reader := strings.NewReader("abcdef")
    random, sequential := reader.ReadAt, reader.Read
    buffer := make([]byte, 2)
    n, err := random(buffer, 2)
    check(n, err, buffer, "cd", false)
    n, err = sequential(buffer)
    check(n, err, buffer, "ab", false)
    n, err = random(buffer, 5)
    check(n, err, buffer, "f", true)
    n, err = sequential(buffer)
    check(n, err, buffer, "cd", false)
    position, err := reader.Seek(4, io.SeekStart)
    if position != 4 { panic("wrong seek position") }
    if err != nil { panic(err) }
    n, err = sequential(buffer)
    check(n, err, buffer, "ef", false)
    fmt.Println("offset reads, sequential cursor, partial EOF and explicit seek checked")
}

第一项的独立预期是 cd、数量二和空错误，随后顺序读的预期是 ab。第二次按偏移读取只能取得 f，数量一并伴随末尾错误；随后的顺序读仍应取得 cd。这样分别证明完整随机读和不足长度的随机读都没有替顺序读推进。若只检查第一次读取内容，就无法发现游标被错误改动。

故障检查也必须保留返回数量。缓冲区长二不代表这次产生了两个有效字节，最后一次不足长度的读取只允许按返回数量解释前缀。官方甚至允许实现在短读时把整个缓冲区用作临时空间，所以不能将剩余位置当成稳定的旧值或额外输出。夹具只比较有效前缀，不根据未定义部分作断言。

这个条件不同于请求刚好在末尾结束。接口允许完整取得所需字节时，在正好到达输入末端的情况下返回空错误或末尾错误。本文故意让请求超过可用长度，确保短读条件成立；不要把这次 n 小于缓冲区长度的预期复制给所有刚好读到末尾的调用。接口级通用测试和特定类型的实现观察要分开写。

解析器应该保留哪一份进度？

如果只想探测头部或已知位置，按偏移调用可以让顺序消费者继续沿自己的进度工作。项目代码宜用不同变量保存探测偏移与已消费字节数，避免把一个成功结果同时累加到两边。两份状态各自有自己的下一步预期：前者由调用者选定，后者由实际顺序读决定。

若需要从探测区域之后开始顺序消费，就应明确执行相应定位，或在自己的顺序流程里消费那些字节。不能指望按偏移探测顺便完成这个动作。是否可以寻址取决于实际数据源，不能给所有输入套一段定位代码。对不可寻址输入，应重新安排解析顺序或缓存策略，这份字符串示例没有实现那类适配器。

位置单位也要写清。这里按字节读取，六个 ASCII 字节恰好对应六个可见字符。若输入是多字节编码文本，任意偏移可能落在一个字符内部；读到指定字节不代表得到了完整可显示字符。本文不验证编码边界，也没有做文件格式解析，不能以三对字母都正确就认定真实格式已通过。

本站的CopyN 短源与局部写入讨论复制的目标字节量以及部分写入后的状态。本题关心同一输入对象的两类位置：即使字节数相同，随机探测与顺序消费仍然不能共用“已经走到哪里”这个推断。代码评审时先确认在观察哪一份进度，再分析错误。

对真实实现补测时，应保存调用前后的顺序读取结果，而不是读取对象内部的私有字段。公开行为可以表达所需合同，也能减少测试被具体实现细节绑住的程度。并发按偏移调用属于接口另有说明的能力，但本稿没有线程测试；更不把它外推为任意 Reader、任意共享缓冲区或任意修改中的底层数据都安全。

显式 Seek 后，下一次 Read 还应该回到开头吗？

新增条件是真正调用寻址方法。夹具在已有顺序读之后，把位置显式设到偏移四，并独立检查返回位置为四。接下来的两字节顺序读取预期是 ef。它和按偏移探测的结果形成正反控制：没有隐含移动，确实要求移动时却会改变后续消费位置。

这份追问没有改变前文随机读取的合同，而是指出哪一个公开动作负责修改它。实际解析器若在多个函数间传递同一个可寻址对象，应把这种位置副作用写进调用约定。待有 Go 环境时，执行这份完整程序并保存版本、源码哈希、输出和退出状态；再加入项目自己的格式输入与错误路径，才能判断那一层解析是否兑现了它的承诺。
