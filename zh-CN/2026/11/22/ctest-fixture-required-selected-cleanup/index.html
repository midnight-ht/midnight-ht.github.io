CTest 只选一项测试，怎样让它的准备和清理也被执行？

选中消费者时自动带入fixture准备与清理，用失败准备和独立日志验证执行集合。

正文

核心要点

  • fixture可扩展实际执行集合。
  • 准备失败阻止消费者但不省略清理。
  • 共享准备与资源互斥是不同约束。

用 FIXTURES_REQUIRED 把消费者测试与fixture关联，CTest会为选中的消费者自动加入对应准备和清理测试。只传 -R 选择一个测试，不等于执行集合里只会有它。准备失败时要求该fixture的消费者不执行，清理测试仍被调度；这三类结果需要分别取证。

例如一项测试要求先创建临时状态，结束后删除。维护者只想重跑消费者，担心过滤条件同时漏掉了准备步骤。可以把生命周期关系交给CTest，而不是让消费者偷偷创建所有状态。前提是测试声明了正确fixture名称，准备与清理也按同一名称登记。

三项测试，一份选中的消费者

在专用目录保存worker.py。它把每次进入记到事件文件，准备创建固定标记，消费者读回完整内容，清理删除标记。失败准备会在创建后退出，故意留下部分状态，才能观察清理是否真正处理了残留。清理允许标记缺失，避免假定准备始终完整成功。

from pathlib import Path
import sys

root = Path(sys.argv[1])
action = sys.argv[2]
marker = root / "state"
log = root / "events.txt"
with log.open("a") as stream:
    stream.write(action + "\n")
if action == "PREPARE":
    marker.write_text("ready\n")
    if sys.argv[3] == "fail":
        raise SystemExit(1)
elif action.startswith("USE"):
    assert marker.read_text() == "ready\n"
elif action == "CLEANUP":
    marker.unlink(missing_ok=True)
else:
    raise AssertionError(action)

再保存verify.py作为独立的外层oracle。它只读取事件与残留，不查询CTest属性或内部结果。

from pathlib import Path
import sys

root = Path(sys.argv[1])
mode = sys.argv[2]
lines = (root / "events.txt").read_text().splitlines()
assert mode in ("pass", "fail")
expected = ["PREPARE", "USE", "CLEANUP"] if mode == "pass" else ["PREPARE", "CLEANUP"]
assert lines == expected
assert not (root / "state").exists()
print("EVENTS_AND_CLEANUP_OK", mode, lines)

同目录保存CMakeLists.txt。fixture名State区分大小写，不需要与测试名相同。prepare与cleanup没有要求自己的fixture，否则会形成对自身的依赖。FAIL_SETUP只改变准备进程的结果，不改变消费者选择或清理声明。

cmake_minimum_required(VERSION 3.20)
project(FixtureSelection NONE)
enable_testing()
find_package(Python3 REQUIRED COMPONENTS Interpreter)
option(FAIL_SETUP "Make preparation fail after creating state" OFF)
if(FAIL_SETUP)
  set(mode fail)
else()
  set(mode pass)
endif()
set(worker_command "${Python3_EXECUTABLE}" "${CMAKE_CURRENT_SOURCE_DIR}/worker.py" "${CMAKE_BINARY_DIR}")
add_test(NAME prepare COMMAND ${worker_command} PREPARE "${mode}")
add_test(NAME use COMMAND ${worker_command} USE)
add_test(NAME cleanup COMMAND ${worker_command} CLEANUP)
set_tests_properties(prepare PROPERTIES FIXTURES_SETUP State)
set_tests_properties(use PROPERTIES FIXTURES_REQUIRED State)
set_tests_properties(cleanup PROPERTIES FIXTURES_CLEANUP State)

以下脚本使用两个全新构建目录，防止成功组留下的文件替失败组满足断言。本机解释器路径需替换成读者真实且后续仍存在的Python路径。这里不编译程序，只需相应CMake、CTest和解释器。

set -eu
work=$(mktemp -d)
python_path=/opt/homebrew/bin/python3.11
test -x "$python_path"
ctest --version
for mode in pass fail; do
  flag=OFF
  if test "$mode" = fail; then flag=ON; fi
  cmake -S . -B "$work/$mode" -DPython3_EXECUTABLE="$python_path" -DFAIL_SETUP="$flag"
  status=0
  ctest --test-dir "$work/$mode" -V -R '^use$' || status=$?
  printf 'case=%s ctest_exit=%s\n' "$mode" "$status"
  if test "$mode" = pass; then test "$status" -eq 0; else test "$status" -ne 0; fi
  "$python_path" verify.py "$work/$mode" "$mode"
done
printf 'fixture=%s\n' "$work"

本地CMake/CTest 4.2.3、Python 3.11.15执行成功组，虽然正则只选use，实际加入prepare和cleanup，三项通过。独立日志恰为PREPARE、USE、CLEANUP，结束时state不存在。这个外层检查比只看总通过率多验证了执行顺序和最终残留。

失败组的prepare创建标记后退出一，CTest将它列Failed，use列Not Run，cleanup仍Passed，CTest命令退出八。日志只有PREPARE与CLEANUP，state已移除。外层脚本确认的是这组预期失败被正确保留，不是宣称消费者行为已通过。负例的原始stdout、stderr和退出值均保留。

官方FIXTURES_REQUIRED说明记载这些选择与准备失败规则，基础fixture功能自三点七提供。当前页面另有较新版本的重复运行行为，本例没有使用repeat选项，不能把页面标题中的版本当作这次实际运行版本。

没运行消费者，与消费者失败不同

准备失败时，USE没有事件是一份预期证据，但仅凭日志缺行仍不足以判断原因。要结合CTest的依赖失败记录、具体用例状态及正确的日志位置。若日志根本写到了别的目录，缺失不说明消费者被阻止；若节点没有被发现，也不是fixture成功拦截。

因此先验证成功组能发现并运行消费者，再比较同样选择下的失败组。输入只改准备模式，两个组的工作目录都独立记录。这样缺席与准备失败有可解释关联，而不是某次命令漏选测试、某份旧报告被误读。真实套件可以按同样原则保留实际节点身份。

若测试被标成未运行，交付记录就不能把它计为行为覆盖。修好准备条件后，要再次实际执行消费者并读到它承担的断言。cleanup成功只说明本例标记已删除，不代表设备复位、数据库恢复或业务环境可用。这些真实资源需要各自的状态检查。

fixture不替代资源互斥

fixture组织的是准备和清理关系，资源锁组织的是测试不能同时占用某资源。官方明确两种机制可以组合，名称却没有自动关联。给消费者写State，不会自动让所有操作同一设备的测试串行；若确实需要独占，另外声明共同资源并验证实际持有区间。

反过来，已有资源锁也不意味着准备会自动加入。维护者应把资源身份、准备动作、使用它的节点和释放动作分开列清，再检查哪项关系由哪个声明承担。不要为了消除一项偶发错误，盲目把整套测试并行度降到一，再将结果归功于fixture。

清理要能接受准备只做了一半

本例刻意在写标记后失败。如果真实准备创建了多项资源，其中一项出错，清理应知道哪些属于本轮、哪些可能尚不存在。使用本轮专用目录与可关联身份，比笼统删除一个公共路径更容易审查。没有归属证据时，应先保留现场而不是删除他人的资源。

正常CTest调度中清理被安排，不是外部服务在任何灾难下都会释放的保证。运行器被强制终止、机器重启或远端失联是另一组恢复条件。本文未执行这些故障，也没有用一个本地marker删除证明远程环境已回收。需要跨运行恢复时，应为残留资源建立额外调查和处置方式。

收集结果时还应保存故障的原始层级：准备进程退出一、消费者未执行、清理通过、运行器退出八，是四项不同事实。把它们统一改写为“测试失败”会丢失下一步动作；统一改写为“清理后成功”则会制造缺失覆盖。准确回执应该让接手者知道先修准备，再补跑消费者。

两个消费者共用一个fixture，会准备两次吗？

这个新条件改变了消费者数量。把下列两行追加到CMake文件，再用新构建目录执行后面的检查。fixture准备对本次选中的消费者集合执行一次，清理等这些消费者都完成后再运行。它不是每项测试各准备一次，也不是跨多次CTest调用永久复用。


add_test(NAME use2 COMMAND ${worker_command} USE2)
set_tests_properties(use2 PROPERTIES FIXTURES_REQUIRED State)

以下外层Shell检查直接核对事件首尾、总数、两项消费者各出现一次及状态残留，不复用消费者的判断。

set -eu
work=$(mktemp -d)
cmake -S . -B "$work/build" -DPython3_EXECUTABLE=/opt/homebrew/bin/python3.11
ctest --test-dir "$work/build" -j 2 -V -R '^use'
log="$work/build/events.txt"
test "$(head -n 1 "$log")" = PREPARE
test "$(tail -n 1 "$log")" = CLEANUP
test "$(wc -l < "$log" | tr -d ' ')" -eq 4
test "$(grep -cx USE "$log")" -eq 1
test "$(grep -cx USE2 "$log")" -eq 1
test ! -e "$work/build/state"
cat "$log"
printf 'ONE_SETUP_TWO_CONSUMERS_ONE_CLEANUP\nfixture=%s\n' "$work"

本地该组四项通过，事件为PREPARE、USE2、USE、CLEANUP。两项USE的相对顺序不是承诺，所以外层只核对两项各出现一次；首尾与次数仍严格检查。主实验原来只有一个消费者，未提前回答这一数量条件。
