lower 后仍不匹配，casefold 为什么能找到 Straße？

用 sharp-s 扩展、原文位置和规范组合控制，区分文本过滤的匹配成功与高亮定位。

正文

核心要点

  • casefold 可处理 lower 不会消除的大小写差异。
  • 折叠可能改变长度，不能直接复用命中位置。
  • 规范等价与大小写折叠需要分别选择和验证。

把 Straße 和搜索词 STRASSE 都转小写，仍然匹配不上；换成 casefold 后却能相等。原因在于小写转换不会把原本已经小写的 ß 改成 ss，而大小写折叠会。用它做文本过滤时，还要保留原文：转换后的长度可能改变，命中位置不能直接拿去切原字符串。

搜索没命中，先确认要消除哪种差异

假设一个本地列表展示道路说明，用户用全大写输入其中一个词。产品要求忽略大小写，但仍按录入时的文字展示。开发者很容易在两边调用 lower，再以结果是否相等判断。英语字母的演示能通过，却不足以证明这个比较符合所有输入字符的约定。这里的故障来自转换合同，而非显示组件漏掉了一行。

Python 内置类型文档的 str.casefold明确把它用于无大小写匹配，并以德语小写字母为例解释为什么比 lower 更积极。本文核对的是三点十四点十文档快照；这个方法从三点三版加入。它提供默认折叠规则，不能由此推断已经满足每一种语言、每一个地区的自然语言搜索习惯。

先让产品约定落到可见输入上：这两个特定词是否应该相等？如果应该，选择能够满足这个字面样本的转换，并留下原文作展示。若要求发音、变音符号或特定语言习惯也相同，需要另列样本和政策，不能在看到一次成功后把“无大小写”扩成“任何看起来接近的词都相同”。本文不处理账户身份、唯一键或映射容器的规则。

相等成立以后，位置又出了问题

完整夹具把比较结果、长度和位置分别写成预期。它已在本机 Python 三点十一点十五执行，代码、版本、标准输出及退出状态随稿归档；这并不等于本机装有文档对应的三点十四版本，也不代表真实搜索服务已经经过验收。

from unicodedata import normalize

lowercase, fold, locate = str.lower, str.casefold, str.index
source = "Straße"
query = "STRASSE"
assert lowercase(source) != lowercase(query)
folded = fold(source)
assert folded == fold(query) == "strasse"
assert (len(source), len(folded)) == (6, 7)
assert (locate(source, "e"), locate(folded, "e")) == (5, 6)
assert source[6:7] == ""
assert source == "Straße"
composed, decomposed = "é", "e\u0301"
assert fold(composed) != fold(decomposed)
left = normalize("NFC", composed)
right = normalize("NFC", decomposed)
assert fold(left) == fold(right)
print("caseless match, expansion, offset failure and normalization control checked")

原文本长度为六，折叠文本长度为七。末尾字母 e 在原文的位置是五，在折叠结果中却是六，因为前面的一个字符扩成了两个。若把折叠结果中找到的六到七直接用于原文，得到空字符串，而不是预期高亮的字母。匹配成功和原文定位成功必须是两项断言，不能只看返回的布尔值。

这个失败甚至不要求用户搜索扩展字符本身。只要搜索位置在扩展之后，先前字符数量的变化就能让偏移失效。所以“我们的关键词只含普通拉丁字母”不能替代位置验证。问题出在被搜索原文的转换上，查询词看起来简单不意味着原文长度没有变化。

保留原文也不是因为字符串会被方法原地改坏。方法返回新字符串，夹具独立断言原文仍然保持不变。这里强调的是应用的数据流：如果把变量覆盖成折叠结果，再把它交给显示层，用户会看到转换表示。分开命名展示文本和比较文本，可以让代码评审看见两者承担的责任。

先决定是否需要精确高亮，再选择实现

只需筛选整行时，可以在转换后的文本上判断命中，然后仍展示整份原文。这个选择不需要把结果位置映射回来，代价是没有精确标出哪个片段。对较短标签，这是一个可审查的产品选择，不应为了看上去功能齐全而临时拼一套未经验证的位置换算。

若必须高亮，应采用能够维护原文与比较表示对应关系的实现，并对扩展前、扩展中和扩展后的命中分别验收。不能简单把固定差值加回每一个索引：不同位置之前经历的扩展数量可能不同，命中本身也可能覆盖扩展字符。本文没有实现通用映射算法，也没有宣称逐字符拼接就足以覆盖所有规范化、组合符和字素边界。

在界面验收中，应保存原输入、比较表示、命中的范围以及最终显示片段。这样当用户说“词找到了但画错地方”，可以知道是比较规则不合适、坐标转换缺失，还是显示层按另一种索引单位解释数据。只保留处理后的词会丢失诊断所需的对照。这里没有收集真实用户输入，示例词都是固定教学数据。

还可以把整词相等与包含关系分开测试。本稿实际夹具证明特定两词相等和末尾字符偏移，不包含一套子串检索库。若业务要做包含过滤，应另外断言查询在转换表示中的接受关系，再验收如何回到原文；不能把整词相等的通过记录贴成所有搜索功能已通过。

casefold 后仍不同，是不是方法漏了规范化？

新增条件是两种字符串虽然都表示带尖音符的字母，编码序列却不同：一边是预组字符，另一边是基本字母加组合重音。折叠大小写不会自动承担所有规范等价处理。夹具先断言它们单独折叠后不相等，再在这个特定样本上先做规范组合，随后比较折叠结果。

unicodedata.normalize 文档说明规范组合与分解形式。这里选的是规范组合，不是任意兼容转换；应按业务需要确定是否允许消除更多表示差异。这个两字符样本通过，也不能证明一种调用顺序适合所有语言算法或全部统一码版本。若服务固定运行时，要把该运行时所用字符数据库版本留在实际验证记录里。

本站的Unicode 规范化与比较合同展开了规范等价的选择，本文不再复写那套问题。这里新增的是折叠扩展与显示位置的责任：先让匹配按约定成立，再检查仍然显示原文、仍然指向正确片段。需要自然语言排序时也应另选排序合同，不从这次相等比较推导列表顺序。
