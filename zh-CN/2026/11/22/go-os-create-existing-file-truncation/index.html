OpenFile 加 O_CREATE 后，旧文件后半段为什么还在？

以独立临时文件的完整内容预期，区分创建、从头覆盖、截断与追加；Go 程序尚未执行。

正文

核心要点

  • O_CREATE 只负责缺失时创建文件。
  • os.Create 会截断已有文件，单独 O_CREATE 不会。
  • 最终完整内容应与写入字节数分别验收。

在已有文件 abcdef 上，用 O_CREATE 打开后从头写 XY，结果可能是 XYcdef。这个标志负责缺失时创建，不负责把已有内容清空。需要重写整个普通文件时，应明确选择截断行为；os.Create 自带的截断合同，也不能只凭名字类推给同名标志。

写入成功，为什么文件还多四个字节？

设一个教学工具每次生成较短的本地文本。旧文件有六个字节，新内容只有两个。调用者检查写入返回值为二，没有报错，就认为文件已经完整替换。然而从当前起点写两个字节只覆盖前两个位置；若打开时没有截断，也没有随后明确调整长度，后面的旧字节仍然保留。成功写入本次内容和文件最终只含本次内容，是两项不同验收。

Go os 包的打开标志文档分别列出创建与截断：前者在不存在时创建文件，后者在打开可写普通文件时截断。本文核对 go1.27.4、二〇二六年十一月十日发布的包文档。官方也提示某些标志在不同系统上不一定都实现，因此示例限定普通临时文件，不推断设备文件、网络文件系统或平台特有行为。

这里最容易混淆的是函数和标志。Create 函数明确承诺创建或截断；OpenFile 是通用入口，按传入的标志组合打开。看到两者都有 create 这个词，不表示默认行为相同。评审时应核对实际调用函数、访问模式和其他标志，而不是只在变更里找一个“创建”选项就认定旧内容会消失。

用独立文件比较四种写入政策

完整程序先创建专属临时目录，每项使用不同文件名，并写入同样的六字节种子。预期分别是保留旧后缀、清空后重写、便捷函数重写，以及读者追问里的追加。缺失文件还有一个不带创建标志的负控制。当前环境没有 Go 工具链，以下程序未执行；所有结果是按官方合同预先写定的教学预期，不是本机测试通过记录。

package main

import (
    "errors"
    "fmt"
    "os"
    "path/filepath"
)

func must(err error) { if err != nil { panic(err) } }
func main() {
    directory, err := os.MkdirTemp("", "create-contract-")
    must(err)
    defer os.RemoveAll(directory)
    ordinary := os.O_WRONLY | os.O_CREATE
    samples := []struct { name string; flags int; want string; useCreate bool }{
        {"keep", ordinary, "XYcdef", false},
        {"clear", ordinary | os.O_TRUNC, "XY", false},
        {"helper", 0, "XY", true},
        {"append", ordinary | os.O_APPEND, "abcdefXY", false},
    }
    for _, sample := range samples {
        path := filepath.Join(directory, sample.name)
        must(os.WriteFile(path, []byte("abcdef"), 0600))
        var file *os.File
        if sample.useCreate { file, err = os.Create(path) } else {
            file, err = os.OpenFile(path, sample.flags, 0600)
        }
        must(err)
        n, writeErr := file.WriteString("XY")
        closeErr := file.Close()
        must(writeErr); must(closeErr)
        if n != 2 { panic("short write") }
        content, readErr := os.ReadFile(path)
        must(readErr)
        if string(content) != sample.want { panic(sample.name + ": wrong content") }
    }
    missing := filepath.Join(directory, "missing")
    file, openErr := os.OpenFile(missing, os.O_WRONLY, 0600)
    if file != nil { file.Close(); panic("unexpected file") }
    if !errors.Is(openErr, os.ErrNotExist) { panic("missing-file control failed") }
    fmt.Println("creation, truncation, append and missing-file expectations checked")
}

前两项的差别只有是否显式截断。第三项调用便捷函数作独立正控制，避免只用我们自己组合出来的标志解释标志。每次写完还检查写入数量、关闭错误和最终全部内容；只检查某个前缀会漏掉这次最关心的旧后缀。程序不会打开仓库文件，也不会修改真实服务配置。

缺失路径用仅写模式打开时，预期返回不存在错误，而非自动创建。这个控制回答的是另一半合同：是否创建取决于标志，而不能由“准备写入”自动推导。错误用标准错误匹配检查，不比较不同系统可能变化的完整报错字符串。教学输入固定为短 ASCII 文本，让字节长度和显示字符数暂时相同，避免编码问题掩盖文件长度问题。

各文件必须独立准备。如果先在同一路径上运行截断案例，再运行保留案例，第二项看到的旧文件已经变短，可能让错误实现偶然通过。测试初始状态是 oracle 的一部分。还应让临时目录清理只作用于本程序自己创建的目录；不能把教学清理代码改成删除一个外部传入的共享目录。

想覆盖整个文件，应怎样写验收？

对于允许直接清空并重写的小型临时产物，可以显式使用截断标志或便捷函数。但截断发生在打开时，后续写入若失败，旧内容已经不在。这是选择这种政策必须承担的后果。本文只解释普通文件长度行为，不把“最后内容是两个字节”升级为发生故障时也能保留旧版本的保证。

如果要求失败后仍保有旧版本，应另行设计替换协议并检查平台条件。写临时文件再改名涉及路径、权限、同步和并发观察等不同问题，不能用本程序的最终内容断言代替。这里不提供部署配置替换工具，也没有验证崩溃、断电或多个进程同时写入时的结果。

在实际修复中，先列出文件已存在与不存在两种输入，再分别写出允许的最终内容。对前者使用比旧内容更短的新数据，可以直接暴露遗漏截断；对后者检查没有误把不存在错误吞成成功。日志中的写入字节数可以帮助定位，但最终完整文件内容才是这道验收要判断的对象。

权限也有自己的条件。创建参数描述新文件的权限并受进程掩码影响，不应假定它会替已有文件重设权限。本稿没有断言权限位，也没有测试权限不足的目录；要把这段示例用于项目，应为权限失败另设环境和预期，而不是把演示中的权限数值当作所有业务都适用的默认。

本站的临时文件交接与清理讨论文件在消费者读取时是否还存活。本题限定在文件仍存在的前提下，写入以后哪些旧字节继续留下。生命周期正确也可能写出错误长度，两份合同都需要自己的断言。

换成 O_APPEND，是不是每次都会替换旧内容？

新增条件是追加模式。它让写入追加到文件末尾，不是清空，也不是从开头覆盖。夹具在独立文件上预先写入六字节，追加两个字节后，完整预期是八字节的 abcdefXY。这个控制刻意与第一项从头覆盖后的 XYcdef 区分，两者都保留旧内容，但保留的位置和含义不同。

因此，追加适合允许积累记录的合同，不适合期望每次只保留最新一份文本的导出。也不要从这个单次教学写入推断跨进程整条记录的原子性或持久性；这些性质需要单独规定和验证。在装有 Go 的环境运行时，应先保存版本、程序哈希、标准输出及退出状态，再检查四项内容和缺失路径错误，不能只把一次无报错当作所有文件写入政策都已验证。
