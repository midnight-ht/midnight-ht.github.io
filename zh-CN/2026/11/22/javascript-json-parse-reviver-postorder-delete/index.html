JSON reviver 为什么先处理子字段，再把对象交给父回调？

以完整回调轨迹和父层快照解释reviver后序处理，区分返回当前值、删除字段与数组索引留下缺项。

正文

核心要点

  • 子回调先改变父对象里的属性
  • 返回undefined表示删除而非不修改
  • 父层判断使用处理后的结构

JSON.parse 的 reviver 先处理子属性，再把处理后的对象交给父属性回调。子回调返回 undefined 时，相应属性会被删除。因此删除 nested.b 后，nested 回调看到的可以已经是空对象。写嵌套清理规则时，要按这个后序过程安排判断，并给需要保留的值明确返回值。

父回调拿到的不是原始结构快照

解析器先建立值，随后递归处理其中的属性。对普通对象，算法读取可枚举自有键，再逐一进入子属性。等子属性的回调结果已经用于删除或更新属性后，才调用当前属性自己的 reviver。父回调因而适合检查已经完成子层转换的结构，而不是假定内部仍等于原始 JSON 文本。

ECMAScript 的 InternalizeJSONProperty把递归、删除或创建属性、调用当前回调依次列出。本文核对二〇二七版当前规范，只讨论固定普通 JSON 数据和没有额外改键行为的回调，不把自定义对象的复杂副作用混进这个入门例子。

返回值本身就是处理合同。返回当前 value 可以保留它，返回别的值可以替换它，返回 undefined 则表达删除。只在函数里写一个日志却忘了 return，不是「记录后不改动」的中性操作。若每次都这样做，处理甚至可能一路影响最终结果。给日志型回调明确返回当前值，是保留输入的必要部分。

这里不需要改变数字的精度或字符串的编码。旧文 长编号与 JSON 数字精度讨论数值转换已经发生以后，回调不能凭空恢复丢失数字。本题解决的是另一层：已建立的数据结构怎样被逐层访问和改写。不要因为用了同一 reviver 参数，就认为回调顺序可以补回解析之前丢掉的信息。

同时检查调用次序、父层所见和最终结果

固定输入只有 a 和一个带 b 的嵌套对象。删除规则只针对键 b，其他分支返回当前值。父回调中立即记录 Object.keys，而不是把可变对象引用扔进日志后等很久再看。这样保存的是父回调发生时的键集合，能与最终结果分开核对。

import assert from 'node:assert/strict';
const order = [];
let parentKeys;
const result = JSON.parse('{"a":1,"nested":{"b":2}}', (key, value) => {
  order.push(key);
  if (key === 'b') return undefined;
  if (key === 'nested') parentKeys = Object.keys(value);
  return value;
});
assert.deepEqual(order, ['a', 'b', 'nested', '']);
assert.deepEqual(parentKeys, []);
assert.deepEqual(result, {a: 1, nested: {}});
console.log(JSON.stringify({order, parentKeys, result}));

这份完整模块已在本机 Node 原样执行。键轨迹为 a、b、nested、空字符串；nested 回调保存的键列表为空；最终对象仍有 a，其值是一，还有一个空的 nested 对象。最后的空字符串是解析入口为最终值安排的回调位置，不是原 JSON 里额外增加了一个业务字段。

三个断言各自承担不同职责。调用轨迹排除先父后子的误解；父层键快照证明删除已经发生；最终结构证明父对象仍被返回并保留。若只检查结果中没有 b，先删后查与别的实现顺序可能看起来相同。若只检查调用次数，则连删错了哪个字段都无法发现。

测试输入里的键顺序也有限定。这里使用普通文字键 a 和 nested，避免把整数式键的枚举规则误当成 JSON 源码的任意文本顺序。需要更复杂键名时，应另外核对对象属性枚举合同，而不是把这四次调用的顺序机械推广到任何输入。当前示例也没有重复键，不承担重复名称怎样保留的说明。

回调参数里的 key 不是完整路径。同名字段可能出现在多个嵌套对象里，而每次只拿一个局部名称。当前 b 规则刻意用于这份受控输入，不能直接当作通用业务清理器，把所有名叫 b 的字段都删掉。若实际策略需要区分不同资源位置，应设计能表达路径或结构角色的转换，而不是依赖本例恰好只有一个同名键。

清理规则的检查位置要跟随遍历合同

假设产品要求父对象只有在必要子字段转换后仍存在时才可保留。后序回调可以在父层查看子层处理后的结果，再作父层决策。但这是一条明确的产品规则，不是 JSON.parse 会自动替应用执行的校验。父回调若只把空对象原样返回，空对象就仍在结果里；删除一个子字段不等于自动删除空容器。

反过来，如果父规则需要知道源对象最初有哪些字段，就不能只在父回调此刻读取 value 来还原。子层已经改写了那些字段。可以在清理前另存所需的原始结构，或选择先解析、后执行有明确输入快照的独立转换。应按规则所需证据选位置，而不是为了少写一个函数把所有步骤塞进回调。

调试记录也要保存时点。把父对象引用保存到数组，后来又让回调修改它，最终展开日志时看到的可能不是保存引用那一刻的内容。示例选择当场取键列表，就是把当前需要验证的内容变成独立数组。真实项目若保存别的快照，应明确哪些值已复制、哪些仍共享，不能把一个引用称作历史状态。

本地运行只覆盖这份固定模块，没有验证某个接口、导入文件或服务端解析框架。迁移规则前，可以用允许保留和需要删除的字段混合构造反例，保存调用位置与最终结构。尤其要给「只记录日志」的分支保留返回值断言，防止一次调试改动意外变成数据清理。

数组某一项返回 undefined，会把后面的项左移吗？

不会。这里新增数组索引条件。数组分支递归每个索引，子回调返回 undefined 后删除相应属性；这不是 splice，不会把后面的元素搬到前一个位置，也不会因此缩短原来的长度。

import assert from 'node:assert/strict';
const result = JSON.parse('[1,2,3]', (key, value) => value === 2 ? undefined : value);
assert.equal(result.length, 3);
assert.equal(Object.hasOwn(result, 1), false);
assert.equal(Object.hasOwn(result, 2), true);
assert.equal(result[2], 3);
console.log(JSON.stringify({length: result.length, keys: Object.keys(result), last: result[2]}));

这份独立代码也在本地执行通过。结果长度仍为三，自有键只剩零和二，索引二的值仍为三。用 Object.hasOwn 能区分「这个索引不存在」与「存在且值为 undefined」。这两种形态单独读 result[1] 都可能得到 undefined，不能只检查一次读取值。

打印整个数组时，还要避免另一层显示转换造成误判。某种序列化表示可能把缺项显示成其他占位值，那是后续表示规则，不代表 reviver 曾经填入该值。本例输出键列表和末项，并保留存在性断言，准确表达删除留下的索引结构。需要连续紧凑的数组时，应在另一个明确步骤按业务规则处理，别把删除合同误读成自动压缩。
