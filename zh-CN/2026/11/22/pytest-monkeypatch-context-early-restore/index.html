测试还没结束，怎样先撤掉这一段 monkeypatch？

用块作用域及时恢复补丁，核对正常、异常与嵌套所有者，并保留故意失败的反例。

正文

核心要点

  • 退出context即可撤销该对象的补丁。
  • 正常与异常恢复需要分别断言。
  • 内层恢复保留外层尚有效的修改。

把临时修改放进 monkeypatch.context()，退出该块就撤销它记录的补丁，无须等整个测试结束。适用场景是同一项测试先要替代行为，后半段又需要原行为。补丁作用域应跟这段操作对齐，不能仅因为fixture最后会清理，就假定现在已经恢复。

例如兼容层先在临时模式下读取配置，随后还要核对默认模式。测试用例没有结束，普通monkeypatch fixture所管理的修改仍然有效。如果直接在下一行期待默认值，失败可能来自补丁还活着，而非配置读取函数坏了。先把预期恢复时点写出来，再选择所有者和退出边界。

正常退出和异常退出分别读回

以下完整文件保存为 test_scope.py。它只修改应用自有字典，没有替换pytest依赖的标准库函数，不访问网络或业务数据。read_mode把每次观察变成实际调用，而不是只检查补丁工具内部的记录。

import pytest

settings = {"mode": "base"}

def read_mode():
    return settings["mode"]

def replace_mode(owner, value):
    owner.setitem(settings, "mode", value)

class Sentinel(Exception):
    pass

def test_normal_restore(monkeypatch):
    assert read_mode() == "base"
    with monkeypatch.context() as patch:
        replace_mode(patch, "temporary")
        assert read_mode() == "temporary"
    assert read_mode() == "base"

def test_exception_restore(monkeypatch):
    assert read_mode() == "base"
    with pytest.raises(Sentinel):
        with monkeypatch.context() as patch:
            replace_mode(patch, "temporary")
            assert read_mode() == "temporary"
            raise Sentinel("expected")
    assert read_mode() == "base"

def test_teardown_is_later(monkeypatch):
    replace_mode(monkeypatch, "temporary")
    assert read_mode() == "base"

replace_mode只复用设置同一配置键的动作，owner参数仍明确是谁记录这次修改；它没有创建共享撤销栈，也没有替任何测试预先复位。

前三项有不同职责。第一项验证正常离开块，第二项验证块内抛出预期异常后仍恢复；第三项故意在普通fixture补丁尚有效时期待base，是应当失败的反例。不要把三项一起要求全绿，否则只能通过删除那个反例的真实意图来“修复”测试。

在已装有固定版本pytest的Python环境，从文件所在目录执行下面两组。第一组应通过；第二组应报告第三项断言失败。项目插件可能改变测试环境，因此本地演练禁用插件自动加载，并关闭pytest缓存提供者。保留完整命令与环境，不能只复制最后的绿色统计。

export PYTEST_DISABLE_PLUGIN_AUTOLOAD=1
python -m pytest -v -p no:cacheprovider test_scope.py -k 'normal_restore or exception_restore'
python -m pytest -v -p no:cacheprovider test_scope.py -k teardown_is_later

本地实际使用Python 3.11.15、pytest 9.0.2：前两项通过，命令退出零；反例的读取仍为temporary，期待base的断言失败，命令退出一。失败原文已保留，没有把它算进“所有测试通过”。这只验证字典补丁生命周期，没有证明产品配置加载或外部资源恢复。

pytest的monkeypatch指南说明，context可以把修改限定在特定范围。九点零点二的实际实现为context创建新对象，并在finally中调用该对象的undo。异常沿块退出时也走到这段收尾，因此样例把异常捕获放在context外，再读取恢复结果。

恢复断言应该放在作用域外

如果把期待base的断言仍放在补丁块里面，它检查的就是临时状态，而不是恢复结果。反过来，只在块内看到temporary，也只证明替换生效，没有证明离开后恢复。将进入前、块内和离开后的读取分别保存，可以把“没有装上补丁”与“没有及时撤销”区分开。

异常用例还要确认真正经过临时分支。本例先断言temporary，再抛出自定义Sentinel；外层仅接受该异常，避免某个意外错误让测试提前离开却看起来验证了恢复。若被测函数抛的是其他错误，应保留原失败，而不是捕获所有Exception以后继续宣布收尾正确。

同样，直接调用读回函数需要覆盖真实用途。这个教学字典只返回一个字符串，既没有缓存，也没有后台任务。真实应用如果在补丁期间启动了另一个操作，之后仍使用先前读到的值，撤销字典本身不会重写那份已取得的数据。应为应用的输入消费时间再设断言，不能把工具恢复等同于业务全部回到起点。

选择更短的补丁，而不是让整个运行器承担它

指南提醒，修改标准库或pytest自身使用的库可能破坏测试运行器。优先替换应用所使用的引用，或者把依赖明确传入代码。这里没有patch全局open、时钟或pytest内部函数，因为恢复这类修改本身就可能受到被替换工具影响，已经超出字典样例的条件。

如果只是验证一个分支，块可以紧贴那次调用。若多个步骤都需要临时行为，则让它们处于同一明确范围，并在最后一个依赖完成后退出。范围越大，后续步骤无意消费临时状态的机会越多；范围也不能缩到被测动作还没发生就恢复。这个选择由实际调用顺序决定，不由“清理代码越早越好”的口号决定。

对异步或并行代码，还要明确谁能读同一对象。context提供的是这个对象记录的修改与撤销，不能为同时访问共享状态的所有任务建立隔离。本文没有跑线程、协程或跨进程场景。若真实任务存在并发读取，应另行选择依赖注入、独立实例或同步合同，并在实际入口复验。

回执还要说明这次选中了什么

运行中收集到四项，不代表四项都执行。后面的问答会追加一项独立条件；上述正常组只选两项，反例组只选一项。报告应保存选择表达式、实际节点和各自结果。若只看文件里的函数数量，就可能把未选中的测试算成已通过。

教学反例的失败也不能用作产品故障报告。它故意提出不成立的恢复时点，是验证错误假设的工具。真正交付时保留这份失败，并解释哪一条假设被推翻；如果维护者为了汇总好看把它改成期待temporary，新的用例已经承担不同判断，必须另记输入与结果。

内层退出，会把外层仍需要的补丁一起撤掉吗？

这个问题首次加入嵌套所有者。把下面用例追加到文件，单独选nested_owners运行。外层把值改为outer，内层再改为inner；内层退出回到outer，只有外层也退出才回到base。本地实际这一项通过。context各建新对象并撤销自己记录的修改，不等于把所有补丁统一清空；主例没有这层嵌套条件。

def test_nested_owners(monkeypatch):
    with monkeypatch.context() as outer:
        replace_mode(outer, "outer")
        with monkeypatch.context() as inner:
            replace_mode(inner, "inner")
            assert read_mode() == "inner"
        assert read_mode() == "outer"
    assert read_mode() == "base"
