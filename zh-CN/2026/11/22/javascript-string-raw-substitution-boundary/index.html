String.raw 里插入换行，为什么结果仍有真正的换行？

用完整代码单元序列区分模板固定段与已求值插值，检查raw保留了什么，以及缺少替换值时如何连接。

正文

核心要点

  • raw从模板对象读取固定段
  • 插值仍使用已经求值的内容
  • 字符序列比控制台显示更可靠

String.raw 保留模板字面段里的反斜杠写法，却不会把插值中的实际换行重新变成反斜杠加字母 n。同一个结果因此可能同时含有这两种序列。排查时要分清每段来自模板源码还是已求值的动态数据，再按代码单元检查，不能只凭控制台的显示方式判断。

raw 作用在哪一段输入上？

一个带标签模板分成两类输入：模板中固定写下的各段，以及表达式求值后的替换值。标签函数拿到模板对象，也拿到各个替换值。String.raw 使用模板对象的 raw 序列获取固定段，再把替换值转成字符串穿插进去。两类数据被连接，但来源没有因此变成同一种。

ECMAScript 的 String.raw 算法明确把读取 raw 段和读取 substitutions 写成不同步骤。这里核对的是二〇二七版语言规范的当前原文，不是某个浏览器最近升级的公告。方法名里的 raw 不能延伸解释为所有传入内容都恢复成源码表示。

假设固定段写了反斜杠加 n，表达式变量里却已经存着一个换行。普通模板会把固定段的转义处理为换行；raw 标签从固定段取得原始写法，于是留下反斜杠与 n。变量值在这两条路径里都还是那个换行。它不会因为旁边出现了 raw，就变回变量最初赋值时使用的引号、反斜杠或其他拼写。

这个差别也说明为什么改变标签不能修复已经在别处处理过的数据。若调用者需要原始文件文本，就应在读取和传递时保留那份文本；如果只交来求值后的字符串，标签无法猜出它原来是直接换行、转义写法还是由多个片段拼接。相同的值可以来自不同源码，没有唯一的反向还原。

用完整代码单元序列验证混合结果

下面的完整模块只检查固定字符串，不访问文件或网络。它把每个索引位置的 UTF-16 代码单元列出来。预期数组直接写成数值，不从待测结果生成，因而能独立发现反斜杠或换行是否落在错误位置。

import assert from 'node:assert/strict';
const substitution = '\n';
const raw = String.raw`A\n${substitution}B`;
const cooked = `A\n${substitution}B`;
const units = text => Array.from({length: text.length}, (_, i) => text.charCodeAt(i));
assert.deepEqual(units(raw), [65, 92, 110, 10, 66]);
assert.deepEqual(units(cooked), [65, 10, 10, 66]);
assert.equal(substitution.charCodeAt(0), 10);
console.log(JSON.stringify({raw: units(raw), cooked: units(cooked)}));

原样脚本已在本机 Node 执行并通过断言。raw 结果依次为 A、反斜杠、n、换行、B，对应六十五、九十二、一百一十、十、六十六；普通模板则是 A、两个换行、B。这里的执行范围是当前本地运行时的字符串处理，没有浏览器渲染或外部接收器的证据。

结果长度不同同样有解释：raw 的固定转义写法占两个代码单元，而普通模板中的对应换行占一个。但只看长度不足以定位错误。例如把两个位置的字符调换，长度可能仍然一样。完整数组既检查数量，也检查每一个位置对应的来源，比只断言「长度更长」更有约束力。

控制台经常为了让单行日志可读而显示转义。有时你看到的反斜杠是打印器给换行选择的表示，有时它确实属于字符串。截图无法自行区分这两件事。记录代码单元、长度和构造输入，能把显示层的选择从实际值里分离。此处数值十就是实际换行，两个数值九十二和一百一十才是反斜杠与字母。

动态数据需要哪一种下游合同？

若某个文本协议要求把换行写成特定转义，应由该协议的编码器处理，而不是给模板随手加 raw。raw 保留固定段源码的能力不等于为动态值执行目标格式的编码。代码生成、日志展示和普通页面文本的接收要求也可能不同，不能用一个标签假定所有接收方需要同一表示。

反例是把动态备注放进 raw 模板，期待备注里的每个换行都自动变成可见的两个字符。主例已经表明，这条期待不成立。另一种错误是看到结果还有真实换行，就对整个字符串做未经约定的替换；固定段本来想保留的字符也可能被卷入下一层处理。应先确定哪一层负责值到表示的转换，再让这一层完整承担。

已有的 查询参数原始值与编码文本讨论的是另一个入口合同：参数方法和查询文本解析接收不同形态。这里不是再教一次查询编码，而是说明模板对象的固定段与替换值本来分开。两处共同的检查习惯是先给输入形态命名，再选择相应处理，避免由函数名推断万能效果。

审查时可以把模板划成固定段与替换值，在每个边界记录期望字符。若动态值来自别的函数，单独检查那个函数返回了什么，而不是只打印最终大串。这样即使最终输出很长，也能判断某个换行在哪一步已经成为实际字符。不要为查一个字符问题引入真实业务私有文本，固定教学样本就足以复现这里的机制。

普通函数调用只有一个替换值，三个 raw 段还能连接完吗？

可以。这里新增自建模板对象和替换值数量不足的条件，不再使用前面的标准标签调用。算法只在当前位置还有替换值时追加它，随后继续读取下一个 raw 段；不存在的替换位置不会自动变成字面 undefined。

import assert from 'node:assert/strict';
const result = String.raw({raw: ['A', 'B', 'C']}, 1);
assert.equal(result, 'A1BC');
assert.notEqual(result, 'A1BundefinedC');
console.log(result);

这份独立脚本也已在本地执行，输出 A1BC。第一处间隙插入数值一转成的字符串，第二处间隙没有可用替换值，B 与 C 仍然连接。负断言专门排除 A1BundefinedC，避免把「没有这一项」和「明确传入值 undefined」混淆。

这个普通调用示例说明参数数量合同，并不建议业务代码随意伪造模板对象来代替清楚的拼接逻辑。需要标签时使用模板；需要已有值的编码或序列化时，使用接收方规定的格式。最终检查应保留真实字符序列，而不是仅凭结果看上去像一份原始文本就宣布转换正确。
