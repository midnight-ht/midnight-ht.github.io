字符串能存下来，isWellFormed 为什么仍是 false？

逐代码单元对照两个孤立代理与一个正确代理对，说明FFFD替换不可恢复原字符，并检查URI编码消费者的新条件。

正文

核心要点

  • 字符串存在不保证代理配对完整
  • toWellFormed替换孤立代理而非恢复原字符
  • 保存原值并按接收规则选择处理

JavaScript 字符串能够存储，并不表示其中的 UTF-16 代理单元已经正确配对。isWellFormed 检查有没有孤立代理；toWellFormed 会把孤立代理替换成 U+FFFD。这个变换能得到配对完整的结果，却不会找回原来缺失的字符。应保留原值，比较具体代码单元，再决定接收、拒绝还是明确替换。

字符串存在与编码配对是两种判断

JavaScript 字符串可以含有单独的高代理单元或低代理单元。补充平面代码点通常需要一对代理单元表示，只有其中一半时，字符串仍可以作为值传递。它有长度、可以拼接，甚至可能被显示成一个替换符，但这些现象都不证明原来的编码序列已经完整。

ECMAScript 的 isWellFormed 定义与 toWellFormed 算法分别进行完整性判断与逐个代码点处理，把不属于代理对的高、低代理换成替换字符。核对的是二〇二七版当前规范，不是对每个已部署客户端都具备这两个方法的支持声明。

完整性检查没有替应用选择业务策略。某个受限字段可能要求直接拒绝不完整输入，另一个展示字段可能允许显式替换后继续。两种选择都应说明原值怎样保存、用户是否需要知道内容改变。不能因为 API 提供了修复方法，就把无声覆盖所有原始文本当成它要求的唯一做法。

三个固定样本，分别看原值与修复值

主例使用一个孤立高代理、一个孤立低代理，以及正确配对的简单笑脸。转义明确写出每个单元，避免根据编辑器显示的图形猜输入。读取每个索引位置的 charCodeAt，是为了观察 UTF-16 代码单元；此处不使用按代码点迭代来替代它。

import assert from 'node:assert/strict';
const units = text => Array.from({length: text.length}, (_, i) => text.charCodeAt(i));
const samples = ['\uD800', '\uDC00', '\uD83D\uDE00'];
const observations = samples.map(original => ({
  wellFormed: original.isWellFormed(),
  before: units(original),
  after: units(original.toWellFormed())
}));
assert.deepEqual(observations, [
  {wellFormed: false, before: [55296], after: [65533]},
  {wellFormed: false, before: [56320], after: [65533]},
  {wellFormed: true, before: [55357, 56832], after: [55357, 56832]}
]);
console.log(JSON.stringify(observations));

完整模块已在本机 Node 原样执行。两个孤立输入的检查结果都是 false，修复后都只有数值六万五千五百三十三；正确配对样本为 true，修复前后的两个单元保持五万五千三百五十七和五万六千八百三十二。独立预期既检查布尔值，也检查变换结果，不只看方法有没有抛错。

孤立高代理与孤立低代理都落到同一个替换字符，说明这个过程不是可逆恢复。拿到修复后的单元，无法仅凭它判定原来缺的是哪一半，甚至不能知道原输入是否本来就是合法的替换字符。若后续需要诊断来源，原值与变换记录就不能被修复结果直接覆盖。

第三个样本是必要负控制：如果实现把每个代理单元都无条件换掉，前两个「修复成替换符」断言仍可能通过，但正确代理对会被破坏。检查配对样本原样保留，能排除这种过度处理。不能只测试失败输入，而忽略本来就有效的文本是否受损。

不要从屏幕形状推断原始数据

替换符的图形只是一种呈现。原串可能已经含有真正的 U+FFFD，也可能是显示层在呈现孤立单元时选择了类似形状。截图看起来相同，不保证代码单元相同。把原单元数组与修复数组并列，才能说明改动发生在哪一层，避免把显示容错当成原值没有问题。

已有 textarea 长度与 UTF-16 单位解释按单位截断可能切开代理对。本题不再决定留言额度，而是检查已经拿到的字符串是否有孤立单元。若源头反复产生这种输入，只在最后显示前替换并不能定位哪一层切坏了数据；可沿读取、拼接、截断和传递的位置保存受控样本。

完整性也不等于 Unicode 归一化。正确配对的文本仍可以有不同的规范等价表示，比较键策略另有用途。保留姓名原文与归一化比较键已经处理那种等价关系。不能把 isWellFormed 为真写成字符在所有业务规则下都相同，也不能因为规范化处理过，就跳过此处配对检查。

这个 API 同样不计算用户感知字符数量、不检查输入是否符合语言规则，也不决定两条记录是否代表同一身份。它的布尔结果只适用于所定义的孤立代理条件。把范围说窄有利于排查：若检查已通过而下游仍拒绝输入，就继续查接收方的独立合同，不要把所有文本错误都归给编码完整性。

本地结果只覆盖当前 Node 版本和固定样本，没有浏览器、输入法、文件解码或存储系统的实测。接入实际应用时，还要核对方法支持与输入来源。若需要兼容其他环境，替代实现应使用同样独立的有效、无效样本验证，不能只因返回了字符串就声称与规范相同。

把孤立代理交给 encodeURIComponent 会怎样，修复后能编码吗？

这里新增具体的下游消费者。按 ECMAScript 的 Encode 算法，遇到未配对代理会抛出 URIError；encodeURIComponent 使用这个过程。原输入因此不能直接通过这次编码，而替换后的 U+FFFD 能得到它自己的 UTF-8 百分号表示。

import assert from 'node:assert/strict';
const original = '\uD800';
assert.throws(() => encodeURIComponent(original), URIError);
const repaired = original.toWellFormed();
const encoded = encodeURIComponent(repaired);
assert.deepEqual([repaired, encoded], ['\uFFFD', '%EF%BF%BD']);
const observedUnits = [original, repaired].map(value => value.charCodeAt(0));
console.log(JSON.stringify({observedUnits, encoded}));

独立脚本也已在本机执行，原输入确实抛出指定错误，替换后编码为 %EF%BF%BD。这证明接收的字符串已经改变以后，这个消费者可以处理当前替换字符；它没有证明丢失的原始字符已被恢复，也没有发送任何 URL 或 HTTP 请求。

若一个业务字段要求逐位保留身份，发现此错误后自动替换再继续可能不符合要求。应让调用方作出明确处理，而不是把「现在能编码」作为数据正确的唯一标准。保留原值、修复值与接收规则三份信息，才能解释某次成功究竟是原文有效，还是应用接受了有意改变后的文本。
