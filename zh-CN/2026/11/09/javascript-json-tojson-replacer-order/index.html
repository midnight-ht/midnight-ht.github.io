replacer为什么拿不到原字段？先查toJSON的调用顺序

沿SerializeJSONProperty核对toJSON与函数replacer先后、根空键和holder，用两个完整未执行探针区分原输入与替换对象入口。

正文

核心要点

  • 可调用toJSON先于同一属性的函数replacer执行。
  • toJSON的this与replacer的holder绑定不同，根还有空键包装。
  • 返回对象不会让同一属性步骤重跑已结束的toJSON阶段。

导出时 replacer 没有看到对象上的原字段，可能不是遍历漏了：该值的 toJSON 已经先返回了另一份表示。函数 replacer 接到的是这个阶段的值，而不保证是最初对象。排查字段改写时，应记录回调顺序、当前 key 与 holder，再决定把检查放在哪个阶段。

ECMAScript 当前草案的 SerializeJSONProperty给出明确顺序：读取 holder[key]，必要时调用可调用的 toJSON，然后调用函数 replacer。核对的是二〇二六年十一月九日取得的 ECMAScript 2027 草案快照，章节为 §25.5.4.2；本稿不把草案年份写成本地运行时已经实现了全部新功能。

replacer 看到的对象为什么换了形状？

设想导出一个账单摘要对象，内存中有 publicName 与 internalNote，类自己的 toJSON 只返回 label。外层 replacer 若根据 publicName 是否存在来识别类型，就可能识别失败；不是 JSON 随机丢了一个字段，而是识别发生在另一份表示上。字段名相似不代表两个阶段面对同一对象。

toJSON 收到当前属性 key，以被转换值作为 this。函数 replacer 则收到 key 和转换后的 value，以持有这个属性的 holder 作为 this。两种 this 的责任不同：前者让对象决定自己的导出表示，后者让遍历回调知道该值来自哪一层。箭头函数没有自己的 this，若想观察 holder，示例应使用普通函数。

根值还有一层包装。JSON.stringify 先把根值放到一个新包装对象的空字符串键下，再启动相同算法。因此最先看到的 replacer key 通常是空字符串，并非漏掉了名字；真正的用户对象也可能有空字符串属性，所以仅凭 key==='' 不足以在所有情况下断定这是根调用。需要额外记录是否第一次或明确保存根位置。

下面是未执行的完整 Node.js ESM 教学程序。它不访问网络、数据库或真实账单；publicName 与 internalNote 都是假设字段。预期由算法先写定，再用断言检查回调轨迹和最终文本，不把序列化输出反过来当作自己的正确性标准。

import assert from 'node:assert/strict';
const trace = [];
const item = {
  publicName: 'Demo',
  internalNote: 'teaching only',
  toJSON(key) {
    trace.push(['toJSON', key, this === item]);
    return { label: this.publicName };
  }
};
const root = { item };
const text = JSON.stringify(root, function (key, value) {
  trace.push(['replacer', key,
    key === 'item' ? value.label : typeof value,
    key === 'item' ? this === root : null]);
  return value;
});
assert.equal(text, '{"item":{"label":"Demo"}}');
assert.deepEqual(trace, [
  ['replacer', '', 'object', null],
  ['toJSON', 'item', true],
  ['replacer', 'item', 'Demo', true],
  ['replacer', 'label', 'string', null]
]);
console.log(text, trace);

对这个输入，根 replacer 先运行，因为外层 root 没有可调用的 toJSON。随后处理 item：先调用 item.toJSON，才把其返回对象交给 item 对应的 replacer，之后递归处理 label。原 item 上的 internalNote 没有进入返回对象，不能期望后续按这份返回对象遍历时再次看到它。

第一份探针还可以分开核对根回调与 item 回调的 holder：前者对应包装对象，后者才对应 root。即使返回对象碰巧仍含相同文字，身份断言也能区分这两层，不能只比较内容是否相等。若把普通回调改成箭头函数，key 参数仍可能正确，this 却不再按这份调用规则取得 holder；因此测试应分别保留属性路径、值和身份三项预期，而不是只看最终字符串。

不要用 JSON.stringify 待检查对象来制作每一步日志，否则日志本身可能再次调用 toJSON，让轨迹混入额外执行。上例只记录布尔值、key 和简单文本，最终输出的 trace 不包含原对象。浏览器控制台的可展开对象也未必是当时值的静态快照，观察工具应避免改变或模糊被观察的过程。

想检查原字段，应该把判断放在哪里？

如果业务要求原对象必须有某字段，应在 stringify 之前执行独立检查，或明确控制对象提供的转换合同。后置回调适合检查它实际收到的表示；把它当成所有输入的第一道原对象审查，会使对象自己的转换有机会先改变结构。这个结论不是建议绕过验证，而是要求验证者清楚自己能看到哪些信息。

返回原始类型也会改变后续观察。toJSON 若返回一个字符串，该值随后交给 replacer，之后不会按原对象属性继续遍历。replacer 仍可有意返回另一份值，但那是新的转换规则；应分别保存原输入、toJSON 返回值、replacer 返回值及最终 JSON，避免把几个阶段统称“导出对象”。

这也不是任意对象的无副作用克隆。读取属性、获取 toJSON 和调用函数都可能有可观察行为；教学对象的方法非常简单，不代表真实类、代理对象或访问器都如此。若输入来自不受控对象，不能因最终拿到字符串就推断此前没有执行代码。这里不提供通用安全过滤器，也没有做恶意对象测试。

replacer 返回的新对象有 toJSON，会立即再调用一次吗？

同一次属性处理不会倒回已完成的 toJSON 阶段。算法先完成那一步，再执行 replacer，之后根据返回值的类型继续序列化。若 replacer 返回对象，进入对象处理；其子属性的值会各自运行属性算法，但不等于对这个返回对象本身重新启动同一轮 toJSON。

下面另一个未执行的完整程序让根 replacer 返回带 toJSON 的新对象。纸面预期是 keep 留下、方法调用计数为零；若把同一对象直接作为最初根值，才会先走它自身的 toJSON。两个入口不同，应分别断言，不用“有这个方法”推断调用时点。

import assert from 'node:assert/strict';
let called = 0;
const replacement = {
  keep: 1,
  toJSON() { called++; return 'converted'; }
};
let first = true;
const text = JSON.stringify({ original: 1 }, function (key, value) {
  if (first) { first = false; return replacement; }
  return value;
});
assert.equal(text, '{"keep":1}');
assert.equal(called, 0);
assert.equal(JSON.stringify(replacement), '"converted"');
assert.equal(called, 1);
console.log('different entry stages checked');

函数属性未形成 JSON 成员，是这个对象遍历后的结果，不意味着运行器先执行它再删除。若替换对象的某个子值另有 toJSON，处理该子值时又有自己的转换阶段；因此“不会立即重跑”必须限定到同一个属性操作，不能扩成整棵树再也不会调用任何 toJSON。

待执行验证应固定 Node 版本，分别保存两个脚本、标准输出、退出码与断言结果。再把项目实际的类、序列化封装与调用入口放入同类轨迹，不从普通对象探针外推整个 SDK。本文没有运行这些代码；实际项目仍要核对最终发送文本与接收方合同。

undefined 与清空语义讨论表示穿过接口后意味着什么。本题限定回调先后与观察对象身份：先找出哪个阶段换了值，再选择该阶段能够履行的验证，而不是要求后面的回调重新看见已经消失的原结构。
