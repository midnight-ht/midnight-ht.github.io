EXEC 报了 WRONGTYPE，另外两条 Redis 写入为何仍在？

区分 Redis 事务排队错误、执行期 WRONGTYPE 与 WATCH 中止，用逐项回复和最终键状态决定重试边界。

正文

核心要点

  • 执行期命令错误不会阻止其他已排队命令执行。
  • 排队错误与运行时错误需要独立输入和预期。
  • WATCH冲突中止队列，不能与逐命令错误合并处理。

Redis EXEC 内某条命令执行失败，不会自动回滚已经执行的其他命令，也不会停止后续命令。先区分错误发生在排队还是执行：排队时发现的命令错误，和执行时才发现键类型不对，可能让整组命令得到不同结局。

设想应用把三次 Redis 操作包进 MULTI 与 EXEC，客户端最后抛了一个异常，业务层便把整个请求重试。若中间那条只是 WRONGTYPE，前后两条可能都已执行。重试若含计数增加，就可能把第一次已经成功的效果再做一次；异常被捕获，不代表所有键恢复原样。这是故障设计场景，没有调用真实业务实例。

QUEUED 只表示入队

官方 Transactions 文档说明，MULTI 进入排队状态，命令随后返回 QUEUED，直到 EXEC 才执行。EXEC 的结果按发出顺序列出每条命令的回复。因此，判断整笔操作不能只看最后一个函数有没有返回；还要知道客户端怎样把这些回复暴露给业务代码。

Redis 保证事务中的命令按顺序执行，其他客户端不会插入其中。这项隔离执行保证不等于出错回滚。官方明确不提供事务回滚；一条命令执行失败时，队列里的其他命令仍继续处理。若从 SQL 事务经验出发，必须把这两个承诺拆开评审。

Redis 事务原文区分排队前后两类错误。本文按核对时的官方页面解释，其中排队错误令 EXEC 拒绝整笔执行的行为标为自二点六点五版本开始。项目的服务端版本和客户端错误表示仍需现场确认，不能只凭工具库函数名判断。

把错误放在两次写入之间

下面是未执行的 redis-cli 会话命令，只适用于自己新建的可丢弃本地实例。把前缀替换成此次练习独有的值；不要在共享实例覆盖同名业务键。本文没有发现可用的本地 Redis 服务端与命令行工具，因此不把这些输入和预期写成运行记录。

MULTI
SET article_demo_unique:a text
LPOP article_demo_unique:a
SET article_demo_unique:b done
EXEC
GET article_demo_unique:a
GET article_demo_unique:b

三条命令的语法都能排队。执行时，第一条建立字符串键，第二条却把它作为列表弹出，预期收到 WRONGTYPE；第三条仍应写入另一个键。按官方语义，EXEC 的逐项结果应为成功、类型错误、成功，最终第一个键仍是 text，第二个键是 done。

这里选择 SET 而不是扣减库存，是为了让最终值容易核对，不意味着普通业务重试总是安全。若前后改成非幂等计数，再因中间错误全组重试，第一次成功的计数可能重复。处理策略应根据每条命令的效果设计，不能把“事务失败”当成一个没有细节的布尔值。

把失败放在中间还有验收意义：只测试最后一条失败，看不出 Redis 是否停止后续命令；只测试第一条失败，也不容易辨别先前成功效果。完整夹心样例同时观察前面的写入、错误本身和后面的写入，才能说明执行策略。

排队错误要另跑一组

重建一个不同的测试键，故意给 INCR 多传参数。这个错误无需等键的运行时类型就可识别，所以不属于上一组的 WRONGTYPE 路径。

MULTI
SET article_demo_unique:c pending
INCR article_demo_unique:c extra
EXEC
GET article_demo_unique:c

对具备上述现代行为的 Redis，预期错误命令不被正常加入队列，EXEC 拒绝执行这笔事务，先前排队的 SET 也不落到键状态中，最后 c 不存在。不能把上一组“其他命令会继续”机械套在这里；两组错误发生的阶段不同。

验收记录应保留每条入队回复、EXEC 整体回复或错误，以及最终键值。若客户端在第一处错误就提前抛异常，还需说明它有没有发送 EXEC，连接是否仍处于事务上下文，后续调用是否正确清理。库的异常类型和返回结构属于实际依赖行为，需要测试，不由 Redis 协议说明代替。

DISCARD 可以丢弃尚未执行的队列，让连接离开事务状态；它不是对已经执行的 EXEC 撤销写入。应用不能在捕获 EXEC 的运行时错误后追加 DISCARD，就把恢复标记为完成。此前命令的结果要按实际状态处置，必要的补偿也要有自己的可重试身份。

站内的SET 与期限替换解释一条写值命令怎样处理过期时间。把多个命令包在事务里，并不会把每条命令自己的语义改掉；类型、期限、条件结果仍须逐项理解。

WATCH 冲突也是这种部分错误吗？

不是。这项追问增加执行前的乐观条件：先 WATCH 一个键，再由另一个客户端修改它，然后尝试 EXEC。官方规定，这种被监视键改变的冲突会让整个事务中止，不执行队列，并以空回复通知调用者；它不是包含 WRONGTYPE 的逐命令结果数组。

要验证该条件，需两个独立连接：甲监视并读取，乙修改同一个练习键，甲再提交先前准备的队列。预期应检查队列中的写入没有发生，再读取新状态决定是否重试。重试是重新读取条件后的新尝试，不是无条件重发旧队列；也不要把空回复当成没有待执行工作。

这里没有运行双连接用例。客户端可能把空回复映为不同语言值，工程验收应检查实际库版本的表示，再和执行错误分支分别覆盖。把两者都转换成同一个“失败后全量重试”，会丢掉是否发生过写入这一项关键信息。

隔离、条件中止、单命令错误、持久化和外部交付是不同检查对象。若业务需要一组状态严格全有或全无，应从数据设计和失败路径重新评审，不能仅靠 MULTI 名字作保证。先保存每条回复与最终键状态，再决定哪些操作可重试、哪些需要查询或补偿；没有运行证据的部分继续标为待验证。
