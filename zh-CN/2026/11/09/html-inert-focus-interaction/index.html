浮层打开后Tab仍进背景：怎样用inert隔离整块区域？

从flat-tree子树边界、原生dialog逃逸到并发限制原因，使用完整未运行页面解释inert何时生效与何时应当恢复。

正文

核心要点

  • inert作用于未逃逸的flat-tree子树，属性存在即为真。
  • 原生模态dialog有祖先inert逃逸例外，自制浮层不能照搬。
  • 解除一个业务原因不表示所有限制结束，应按当前原因集合恢复。

灰色遮罩不会让背景表单退出 Tab 顺序。需要让一整块内容暂时不可操作时，可以用 inert 表达子树状态，但必须划清哪些节点属于背景、谁有权解除限制，以及原生模态对话框的例外。恢复画面之前，也要确认其他阻塞原因已经结束。

HTML Living Standard 的 Inert subtrees定义了这里的行为；核对页面标注二〇二六年十一月六日更新。下面只讨论规范与未执行教学页面，不宣称已通过浏览器、系统或辅助技术组合验收。inert 是用户交互边界，也不承担服务端授权。

属性作用在子树，不是给背景画一层灰色

inert 是布尔属性，存在就生效。因此 inert="false" 仍然表示存在这个属性；脚本需要用 element.inert=false 或移除属性来解除。切换字符串内容与切换布尔状态不是同一件事，这类错误可能造成页面视觉恢复但仍无法操作。

其范围包括元素以及未逃逸限制的 flat-tree 后代。这里不能简单理解为只遍历普通 DOM children：插槽分配和影子树参与呈现关系时，应该按规范的树关系分析。组件将一颗按钮视觉上放到别处，并不表示它必然离开限制范围；要核对实际结构与所用组件机制。

按原文，inert 节点的命中测试按 pointer-events:none 处理，编辑区域变得不可编辑，通常不能聚焦，也不向可访问性 API 暴露。文本选择和页内查找还有相应限制与用户代理例外。因此只给一块区域加 aria-hidden，或只关指针事件，都不等价于这份交互合同。

它没有默认的持续视觉提示。加载提示、背景暗化或离屏位置应让用户理解哪些内容暂不可用。反过来，页面仍在使用的关键说明不能误放进 inert 子树；否则看得见的字也未必能被所有用户感知。状态提示可留在活动区域，不能把唯一的恢复说明一起封住。

原生模态对话框为什么是特殊情况？

showModal() 会把 dialog 放进顶层，并使连接文档中除该对话框及其 flat-tree 后代之外的节点变得 inert。规范还允许这个模态对话框逃逸祖先的 inert；但若在 dialog 自身设置 inert，限制仍适用。这是标准规定的例外，不能推广成任何视觉浮层都自动逃逸。

普通 div 即使有最高 z-index、fixed 定位或模态角色，也不会因此获得同样例外。自制浮层若仍属于被 inert 的祖先子树，可能把活动内容一起封住。排查时先确认它是原生 showModal 打开的 dialog，还是只是画得像模态框，再分析父级限制。

原生机制也不替应用决定所有任务状态。后台加载仍未完成时，关闭确认框不表示底层页面已经可以操作。对话框退出所解除的是它带来的原生模态阻塞；应用自己设置的 inert 属性可能仍应保留。这正是需要记录限制来源的地方。

两个独立状态都让背景 inert，关闭其中一个能直接移除属性吗？

不能。先移除这一个状态对应的原因，再根据剩余所有者决定是否解除 inert。若加载仍在限制背景，关闭确认框就不能让背景恢复操作。

以下完整 HTML 尚未运行，模拟“背景加载”与“确认对话框”两种应用原因。它不请求数据，也不执行真实删除。加载完成按钮故意放在背景 main 之外，保证教学操作者仍有结束加载的入口。真实产品应由实际请求完成或失败来更新对应状态。

<!doctype html>
<meta charset="utf-8">
<title>Inert reasons</title>
<style>
main[inert] { opacity: .45; }
dialog::backdrop { background: #0006; }
</style>
<p id="status" tabindex="-1" role="status">Ready</p>
<button id="finish" type="button">Finish teaching load</button>
<main id="page">
  <label>Note <input></label>
  <button id="load" type="button">Start teaching load</button>
  <button id="open" type="button">Open confirmation</button>
</main>
<dialog id="confirm" aria-labelledby="heading">
  <h2 id="heading">Teaching confirmation</h2>
  <p>No business action is performed.</p>
  <button id="overlap" type="button">Add loading reason</button>
  <form method="dialog"><button value="cancel">Close</button></form>
</dialog>
<script>
const $ = id => document.getElementById(id);
const reasons = new Set();
function setReason(name, active) {
  active ? reasons.add(name) : reasons.delete(name);
  $('page').inert = reasons.size > 0;
  $('status').textContent = reasons.size
    ? 'Blocked: ' + [...reasons].join(', ') : 'Ready';
}
$('load').onclick = () => setReason('loading', true);
$('finish').onclick = () => setReason('loading', false);
$('open').onclick = () => {
  $('confirm').showModal();
  setReason('confirmation', true);
};
$('overlap').onclick = () => setReason('loading', true);
$('confirm').addEventListener('close', () => {
  setReason('confirmation', false);
  ($('page').inert ? $('status') : $('open')).focus();
});
</script>

独立预期从原因集合推导：只有 confirmation 时，关闭对话框后集合为空，背景恢复；在对话框里加入 loading 后再关闭，集合还剩 loading，背景必须继续 inert，焦点交给外部状态位置。随后点击教学加载完成按钮，才清掉最后一个原因。单纯在 close 回调写 page.inert=false，会把仍在加载的背景错误开放。

集合是本例的实现建议，不是 HTML 规范要求引用计数。名字也需要对应真实所有者。两个并发加载任务若共用同一个 loading 名字，第一个结束仍可能清掉另一个的限制；实际应用可以为任务使用独立令牌，或从统一状态模型推导是否阻塞。不要把 Set 当成自动解决并发的魔法。

页面离开、请求失败与组件卸载也要交代谁释放原因。若错误分支只改提示却没有释放对应令牌，区域可能永久不可用；若直接清空所有原因，又可能绕过另一个仍有效的限制。检查应围绕每个来源的生命周期，不是只看某次打开和关闭动画。

上例的加载完成按钮是教学控制器，不能照搬成“用户任意点一下就当网络完成”。真实状态必须由请求结果或明确取消规则驱动，还要核对失败后的重试路径和当前数据是否可继续编辑。

待执行检查先按无阻塞、仅确认、确认叠加加载、关闭确认、加载结束逐步记录原因集合与 inert 属性，再用真实 Tab、点击和活动元素观察结果。程序调用 click() 或派发事件不等于用户命中测试，不能用一行回调日志证明所有交互都被挡住。还要在目标环境检查可访问性树与状态提示是否仍可获得。

单个表单控件暂不可用时，规范提示 disabled 往往更合适；整区加载或活动范围隔离才是这里的重点。既有模态焦点流程负责进入与退出后的任务位置，本题补的是限制作用在哪棵树，以及最后一个原因何时真正结束。先把这两件事核对清楚，再解除背景限制。
