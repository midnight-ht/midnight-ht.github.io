给submodule update加--remote，会改变版本来源

区分父仓库索引gitlink、已提交树、子模块HEAD与远程候选，用完整A/B脚本解释普通更新来源及暂存升级边界。

正文

核心要点

  • 普通更新使用父仓库索引中的依赖记录。
  • 远程更新改变目标来源，过程仍可另选。
  • 本地检出新提交不会自动记录新gitlink。

git submodule update --remote 改变了目标提交的来源：普通更新使用父仓库索引记录的依赖提交，远程更新使用子模块远程跟踪分支的状态。它不只是多抓一次网络。先决定本次要复现已记录版本，还是提出依赖升级，再选择命令。

索引目标与已提交记录，也可能不同

Git 的 submodule 手册说明，默认 checkout 更新会检出父仓库记录的提交，子模块通常处于 detached HEAD。该页面标注本条手册最后更新于二点五四版本，并列出到二点五六无内容变化；这些网页版本记录不是本机 Git 版本探测。

假设父仓库提交甲记录依赖提交 A，而依赖远程分支已经前进到 B。本地子模块又可能正好停在另一个提交。父仓库 HEAD 树中的 gitlink 说明已经提交的依赖记录；父仓库索引中的 gitlink 才是普通 update 当前使用的目标，两者可能不同。子模块当前 HEAD 说明磁盘上实际检出的身份，远程跟踪引用则说明上游候选。把这些位置都简称为“当前版本”，很容易让交接双方谈论不同对象。

下面的 A/B 对照明确假设父仓库索引与 HEAD 树中的依赖记录相同，均为 A，而且没有暂存依赖升级。在这一条件下，普通 update 回到 A，可能正是在正确复现父仓库输入。它没有因为远程存在 B 就失效。反过来，执行远程更新到 B，也不能说明父仓库已经把 B 记录下来。依赖工作目录发生变化，与记录一个可供他人复现的父仓库提交，是不同动作。

在本地建立一份 A 到 B 的对照

下面是未执行的完整教学脚本，只在新建临时目录中操作三个本地仓库，不访问真实托管远端，不修改本站主题依赖。示例使用一次性命令配置，允许这组本地 file 协议，不写全局 Git 设置。它要求安装 Git 与 Python，并使用支持所列命令的版本。教学提交不签名，身份也只在这些新仓库内设置。

# submodule_demo.py
from pathlib import Path
import subprocess
import tempfile

root = Path(tempfile.mkdtemp(prefix="submodule-demo-"))

def git(where, *args):
    p = subprocess.run(["git", "-c", "protocol.file.allow=always", "-C", str(where), *args],
                       text=True, capture_output=True, check=True)
    output = p.stdout.strip()
    if output:
        print(output)
    return output

def identity(where):
    git(where, "config", "user.name", "Teaching Fixture")
    git(where, "config", "user.email", "fixture@example.invalid")
    git(where, "config", "commit.gpgsign", "false")

print("Fixture directory:", root)
print(subprocess.check_output(["git", "--version"], text=True).strip())
remote, work, parent = (root / n for n in ["remote.git", "work", "parent"])
git(root, "init", "--bare", str(remote))
git(root, "init", "-b", "main", str(work))
identity(work)
(work / "value.txt").write_text("A\n")
git(work, "add", "value.txt")
git(work, "commit", "-m", "A")
a = git(work, "rev-parse", "HEAD")
git(work, "remote", "add", "origin", str(remote))
git(work, "push", "-u", "origin", "main")
git(remote, "symbolic-ref", "HEAD", "refs/heads/main")
git(root, "init", "-b", "main", str(parent))
identity(parent)
git(parent, "submodule", "add", str(remote), "dep")
git(parent, "add", ".gitmodules", "dep")
git(parent, "commit", "-m", "Record A")
(work / "value.txt").write_text("B\n")
git(work, "commit", "-am", "B")
b = git(work, "rev-parse", "HEAD")
git(work, "push", "origin", "main")
git(parent, "submodule", "update", "--init", "--checkout")
assert git(parent / "dep", "rev-parse", "HEAD") == a
git(parent, "submodule", "update", "--remote", "--checkout")
assert git(parent / "dep", "rev-parse", "HEAD") == b
recorded = git(parent, "ls-tree", "HEAD", "dep")
assert a in recorded, recorded
git(parent, "diff", "--submodule=log", "--", "dep")
print("Expected identities matched; fixture retained:", root)

这份脚本的预期在运行前就明确：普通更新以后，子模块 HEAD 等于 A；远程更新以后等于 B；父仓库 HEAD 树中的 gitlink 仍为 A。脚本故意不把 B 暂存进父仓库，也不创建升级提交，这样最后的差异仍可供审查。临时目录保留下来，并不自动清理；确认不再需要时只针对打印的本次目录处理。

候选命令是 python3 submodule_demo.py。执行者应保存命令真实退出状态和输出；本文没有执行它，因此最后的成功文字只是待执行代码，不能作为已经观察到的日志。若脚本失败，要看失败发生在哪条 Git 命令，不能仅凭目录创建成功就认为依赖升级已完成。真实项目还需要对 B 的代码和接口执行自己的检查。

如果暂存了依赖路径而尚未提交，不能继续只看 HEAD 树解释普通更新。设父仓库 HEAD 仍记录 A，索引已经暂存 B；普通 update 的目标就可能是索引里的 B，而不是 A。这个反例没有改变远程选项的定义，改变的是普通更新本来就读取的输入位置。

在真实仓库可先用下列只读检查分别看索引、已提交树与实际子模块。它们是未执行的诊断命令，dep 必须替换成本次确认路径；不要为了让三项相同就清掉有价值的暂存升级。

git submodule status --cached -- dep
git ls-tree HEAD -- dep
git -C dep rev-parse HEAD

教学脚本故意没有暂存 B，所以原来的三项预期仍成立：普通更新到 A、远程更新到 B、HEAD 树仍为 A。真实交接若已有暂存变更，应同时保留索引身份，区分“本次准备提交什么”与“已经提交什么”，再选择复现目标。

来源选择与更新过程是两个控制

手册明确，远程选项同样可以结合 checkout、merge 或 rebase。前者决定从哪里取得目标提交，后者决定如何把这个目标作用到子模块当前状态。把远程更新和合并混称为“拉最新”，就掩盖了是否保留本地分支、是否可能发生冲突等不同后果。

这份教学脚本显式选 checkout，只为了让 A 与 B 的身份对照清楚。它没有证明任意真实工作目录都适合直接检出。操作真实依赖之前，应查看子模块自己的未提交修改和分支状态，保存有价值的工作，避免为修一个版本差异使用强制选项覆盖别人修改。父仓库干净也不能替代子模块内部检查。

远程更新默认先抓取，再计算远程跟踪目标。若加上不抓取选项，使用的是本地已有引用，未必是网络当前状态。因而“命令用了远程选项”不是新鲜度证明；应把实际远程、分支、抓取结果与最终对象身份记录下来。网络抓取成功也只是对象传输结果，不证明新依赖已通过测试。

若目标是发布已审版本，通常应以父仓库记录为输入。若目标是升级，则先检查 B 的差异、兼容性与项目验收，再在父仓库暂存依赖路径并提交新的 gitlink。之后其他操作者才能从新的父仓库提交复现 B。只在本地子模块检出 B，却交付旧父仓库提交，会让接手者正确执行普通更新后又回到 A。

升级提交交给另一位操作者时，可以把验收顺序写得更明确：先核对父仓库提交身份，再读取该树中的依赖记录，随后在独立检出中更新子模块，最后比较实际依赖身份与记录。若接手者得到 A，先问父仓库是否真的交付了记录 B 的提交，而不是要求对方也加远程选项去追上你的本地目录。

这种检查会揭示一个常见交付缺口：代码测试在 B 上运行，批准记录却绑定仍指向 A 的父仓库提交。测试可能确实通过，但它没有验证即将交付的输入。应把检查结果关联到父子两个身份；在升级提交形成后重新确认交付输入，不能用先前工作目录的成功替另一份版本签收。

示例把协议配置集中到本地命令包装器，所以每条子进程都有同一项明确的命令级设置，但不会留下全局许可。输出先保存再打印，既减少重复处理，也让返回的对象身份与显示内容一致。这些整理不改变三项预期，更不能省去父仓库记录仍为 A 的断言。

配好 branch，普通 update 就会跟分支吗？

不会。submodule 名称下的 branch 配置用于远程更新的目标选择，普通更新仍以父仓库记录为准。官方手册还说明，远程目标默认取远程 HEAD，branch 可以覆盖；同名设置若同时存在于项目文件与本地配置，本地配置具有优先级。调查时既要看可共享文件，也要看本机有效配置。

例如团队在 .gitmodules 中约定 main，而某台机器本地改成 release，双方执行远程更新可能获得不同目标。不能只把项目文件截图发给对方就断言选择一致。应核对实际使用的配置来源和远程跟踪对象；配置解释清楚后，再讨论是否需要把候选版本写回父仓库。

站内的restore 来源与目标文章处理单仓库文件状态，本题增加父仓库与嵌套仓库之间的版本记录。交接时同时给出父仓库提交、所记 gitlink 和实际子模块 HEAD，明确本轮是复现还是升级，才不会把一份尚未记录的工作目录当成可发布输入。
