多发一条CSP，不能覆盖原来的拒绝

两份强制CSP分别求值。用三个本地端点解释宽松新头为何无法撤销原拒绝，并区分CORS、发行层与meta时点。

正文

核心要点

  • 请求必须同时满足每份强制策略。
  • 放宽无关策略不能撤销原拒绝。
  • meta交付还受解析时点限制。

两份强制 CSP 不采用后写覆盖前写的规则。请求必须分别通过每份策略；原策略禁止连接时，再追加一条允许接口域名的头，仍不能放行。排查应定位哪份实际交付的策略拒绝了请求，再找拥有那份配置的发行层。

为什么加了允许列表，原来的拒绝还在？

二〇二六年十月二十七日的 CSP Level 3 工作草案在多策略说明中给出同样的判断：每份策略按自己的处置类型参与执行。这里讨论两个 Content-Security-Policy 强制响应头，不把 Report-Only 当成另一个授权来源。草案仍是工作草案，不能据此宣称所有浏览器已具备相同兼容性。

假设应用原来只允许同源连接，代理为了接入新接口，又加了一份允许接口来源的策略。维护者可能把第二份当作覆盖配置，觉得新接口已经获得许可。浏览器却还要检查第一份。第二份同意，只能说明这一关没有拒绝；它没有权限替第一份撤销限制。

同一份策略里的来源列表与两份策略也不能混着读。一个 connect-src 中列出的不同来源，可以供匹配请求选择；把来源拆到两份强制策略后，不会自动成为两份允许集合的并集。复杂指令还有各自的匹配、回退和执行规则，因此审查时应逐份求值，不能对任何 CSP 文本都直接做字符串集合运算。

用三个端点找出拒绝来自哪里

下面是一份未执行的完整本地教学服务。它只监听回环地址，不修改本站响应头。将文件保存为 demo.py，在独立目录运行 python3 demo.py 后，用浏览器打开程序提示的地址。示例服务不含业务数据；三个端口需要空闲。这里没有运行浏览器，也没有截图或安全测试通过记录。

from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
from threading import Thread

HOST = "127.0.0.1"
PAGE_ORIGIN = f"http://{HOST}:8000"
API_ORIGIN = f"http://{HOST}:8001"

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        port = self.server.server_port
        page = port == 8000 and self.path == "/"
        script = port == 8000 and self.path == "/app.js"
        if page:
            body = b'<!doctype html><title>CSP demo</title><pre id="out"></pre><script src="/app.js"></script>'
            kind = "text/html; charset=utf-8"
        elif script:
            body = b"""(async () => {
 for (const p of [8000, 8001, 8002]) {
  try {
   const r = await fetch(new URL(`/data`, `${location.protocol}//${location.hostname}:${p}`));
   document.querySelector('#out').textContent += `${p}: ${await r.text()}\n`;
  } catch (e) {
   document.querySelector('#out').textContent += `${p}: rejected\n`;
  }
 }
})();"""
            kind = "text/javascript; charset=utf-8"
        else:
            body, kind = b"endpoint reached", "text/plain"
        self.send_response(200)
        headers = [("Content-Type", kind), ("Access-Control-Allow-Origin", PAGE_ORIGIN)]
        if page:
            headers.extend([
                ("Content-Security-Policy", "connect-src 'self'"),
                ("Content-Security-Policy", f"connect-src 'self' {API_ORIGIN}"),
            ])
        for name, value in headers:
            self.send_header(name, value)
        self.end_headers()
        self.wfile.write(body)

servers = [ThreadingHTTPServer((HOST, p), Handler) for p in (8000, 8001, 8002)]
try:
    for server in servers:
        Thread(target=server.serve_forever, daemon=True).start()
    print(f"Open {PAGE_ORIGIN}/ ; press Enter to stop")
    input()
finally:
    for server in servers:
        server.shutdown()
        server.server_close()

预期输入是三次 fetch，两个策略分别称为甲和乙。八千端口的同源请求同时满足甲乙；八千零一满足乙，却不满足甲；八千零二两份都不满足。最终只有同源请求应获得响应正文。页面把不同错误都简写为 rejected，所以它只提供一个观察入口，不能单靠这串文字判断拒绝原因。

第二组对照只修改甲，把八千零一的来源也加入甲，其余保持不变。此时该请求才同时满足两份策略。若仅继续放宽乙，甲仍然拒绝。这一组改动能够检验“改的是限制拥有者，还是另一份无权覆盖它的策略”。它不是推荐真实应用按端口放开连接的安全模板。

服务对各数据响应显式提供 CORS 头，是为了减少另一种拒绝原因的干扰。CSP 允许请求，并不代表跨源响应一定可被脚本读取；网络故障、端口占用与 CORS 错误都要分别检查。应把页面结果与浏览器控制台的具体指令、策略内容和服务端请求记录对应，避免一个 rejected 就被写成 CSP 已验证。

配置归谁管，要从真实响应往回找

浏览器收到的策略可能由应用、反向代理和静态托管分别生成。仓库里搜到一份新配置，只能证明那份文件存在。先保存页面文档的实际响应头，保留全部强制头和报告头，再追踪每条限制来自哪一层。不同入口、路由或缓存状态可能交付不同组合，不能拿源站直连的头替公开入口签收。

如果产品确实需要新增连接来源，应在安全评审后修改真正拒绝它的策略，同时保留其他资源边界。直接删除整份 CSP 也许能让页面恢复，却同时放弃了原来表达的其他限制；这个代价不能被“接口终于通了”掩盖。反过来，错误报告少了也可能是报告链路失效，不能自动当成兼容性变好。

验收可保存浏览器版本、文档 URL、两份策略原文、三次请求的许可表和服务端记录，并说明第二组只改了哪个字段。用 curl 查看响应头有助于核对交付，但它不会替浏览器执行 CSP。没有浏览器交互证据时，只能报告头部检查结果。

修改发行层以后，还要核对旧响应是否仍在缓存中。如果源站已经返回新策略，公开入口仍提供旧组合，继续改应用规则并不能证明用户已收到修复。应在同一入口重新请求文档，保存响应内容身份与头部，再用同一浏览器流程验证；不能把清缓存按钮被点击当成旧策略已经退出的证据。

回退也应针对本次变更负责。预先保存原策略组合，明确哪一层加了什么，发生业务破坏时才能恢复已知配置。如果新连接有多个调用入口，还应分别确认，不因首页的一次请求通过就推断后台导出和登录后的请求同样通过。策略许可只说明允许发起相应资源行为，不会替服务端认证、数据权限和业务结果提供批准。

这份教学代码把来源命名成两个变量，把待交付头保留为有序列表。列表中两条同名策略仍然分别发送，不能改成普通字典让后一条静默覆盖前一条；否则实验输入已经从两份策略变成一份。对照组应改第一条列表项的来源许可，并保留第二条，这样被检验的仍是同时满足，而不是误删旧限制后得到的成功。

改成 meta，就能覆盖服务器头吗？

不能。草案的 meta 交付条款说明，生效的 meta 策略仍与其他活跃策略共同执行；它还增加了一个响应头示例没有的时点条件：出现在该元素之前的资源，不会被这份后来解析的策略追溯阻断。已经解析后再改 content，也不能当作动态覆盖旧策略的办法。

因此，把禁止规则从服务器搬到文档后部，可能改变早期资源受到保护的范围，却没有建立“最后一份说了算”的机制。若需要稳定保护整个文档，应把交付位置和解析时点列入评审，而不是只看页面源码最终有几条 meta。

站内的Worker 回退文章已经提示过多策略不会互相放宽；这里把这一旁注展开成独立的发行层诊断。实际修改前先写出每个必要请求必须通过哪些策略，再明确谁负责那份拒绝规则。这样得到的变更才有可核对的授权范围。
