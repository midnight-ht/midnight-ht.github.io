实验项允许失败，为什么矩阵其他任务仍被取消

先辨认触发取消的矩阵成员，再核对job容错与fail-fast；完整双输入工作流保留排队、调度和托管运行边界。

正文

核心要点

  • 允许实验失败不代表允许稳定项失败。
  • fail-fast可以取消运行中和排队成员。
  • 关闭取消与放宽质量门禁是不同决定。

GitHub Actions 的实验矩阵项允许失败，不代表其他成员的失败也获准忽略。出现兄弟任务取消时，先查触发取消的是哪一个成员，以及它的 job 级 continue-on-error 实际取值。稳定项失败仍可触发 fail-fast，哪怕实验项配置完全正确。

容错许可与取消策略各管一层

GitHub 的矩阵失败处理说明把 job 级容错与矩阵级 fail-fast 放在一起解释。未获容错的成员失败，可以取消同矩阵正在运行或排队的任务；获容错成员失败，则不会因为这次失败影响其他成员。这里依据二〇二六年十一月九日读取的在线文档，不虚构该滚动页面的发布日期。

假设兼容性检查有两个稳定环境和一个实验环境。实验环境失败，团队仍想看稳定环境结果，因此给该成员设置允许失败。但如果稳定环境甲同时失败，矩阵仍有一个必须阻断的失败来源。此时看到实验环境也被取消，并不能反推“实验容错没有生效”。触发取消的可能是稳定环境甲。

这也意味着取消不是失败成员的另一种名字。一个被取消的任务可能尚未执行测试，也可能执行到中途。不能把它算作通过，也不能把它的缺失结果自动归入代码缺陷。先保存平台的取消原因、失败成员及有效配置，再决定是修改测试、修改实验标记，还是调整收集策略。

两次只改变失败来源的完整工作流

以下文件可放在独立测试仓库的工作流目录，由有权限的操作者手动触发。本篇没有创建远程运行，也没有消耗托管运行器；示例状态均为预期。它不检出代码、不上传制品、不部署，只用退出码和短等待展示矩阵策略。等待时间是教学输入，不是任何项目的性能数据。

name: inspect-matrix-failure
on:
  workflow_dispatch:
    inputs:
      fail_case:
        type: choice
        required: true
        default: experimental
        options:
          - experimental
          - stable
permissions:
  contents: read
jobs:
  inspect:
    runs-on: ubuntu-latest
    continue-on-error: ${{ matrix.experimental }}
    strategy:
      fail-fast: true
      max-parallel: 2
      matrix:
        include:
          - name: stable-a
            experimental: false
          - name: stable-b
            experimental: false
          - name: experiment
            experimental: true
    steps:
      - name: Controlled result
        env:
          MEMBER: ${{ matrix.name }}
          FAILURE_CASE: ${{ inputs.fail_case }}
        shell: bash
        run: |
          printf 'start %s\n' "$MEMBER"
          if [[ "$FAILURE_CASE" == experimental && "$MEMBER" == experiment ]]; then
            exit 1
          fi
          if [[ "$FAILURE_CASE" == stable && "$MEMBER" == stable-a ]]; then
            exit 1
          fi
          sleep 20
          printf 'end %s\n' "$MEMBER"

第一次选择 experimental，只有实验项主动返回失败。预期是这次失败不触发其他成员取消，稳定项仍有机会正常完成。这里的“有机会”保留了其他独立取消原因，例如操作者手动停止或平台故障；示例没有能力禁止那些事件。因此验收不能只记一个最终颜色，还要确认失败和取消的实际来源。

第二次选择 stable，稳定环境甲主动失败，它没有获得 job 级容错。fail-fast 因而可以取消同矩阵尚在运行或排队的成员。已经完成的任务不会因为后来的失败倒退为取消。运行器如何排序、哪个成员先结束，不由这份 YAML 提供确定保证，不应预写一张声称每次相同的时间表。

两轮应分别保存工作流提交、输入、展开后的成员配置、每个 job 的开始结束与终态，以及原始运行日志。稳定项没有 end 标记，只能说明没有到达脚本尾；还要结合平台状态判断是取消、运行器中断还是命令失败。日志里的开始标记也不能代表该成员的业务检查已经完成。

步骤容错不能替 job 实验标记签名

如果只在某条测试 step 上配置继续执行，原始命令失败与该步骤的最终结论可能发生变化。它回答的是同一 job 内后续步骤如何处理，不等同于这里按矩阵成员定义的 job 失败许可。调查时要读取实际展开配置，不能仅搜索到一个 continue-on-error 就宣布整项实验身份正确。

反过来，也不要看到层级差异就立刻把它判成事故根因。前面的第二轮即使容错位置完全正确，稳定项失败仍会导致取消。准确诊断需要先找到最早的相关失败和它的身份，然后核对该层策略。先定责为“配置写错层”，会把合法取消误修成放宽必需检查。

站内的步骤 outcome 与 conclusion 文章解释原始步骤结果与容错后结果。本题讨论兄弟 job 的命运，两者可以同时影响一条流水线。评审时分别列出命令退出、步骤结论、job 容错和矩阵取消，避免一个成功字段覆盖其他失败事实。

是尽快停止，还是保留完整诊断？

若稳定项一失败，其他结果对本轮决策已经没有价值，保留 fail-fast 可以减少继续占用运行器。若升级验证需要知道所有平台分别失败在哪里，可以关闭它，让更多成员完成诊断。关闭取消策略不会把稳定项失败变成成功，也不会自动改变合并或部署入口的要求。

选择还受资源与外部动作影响。示例只做本地等待，停止没有提交远程业务任务；真实步骤若已向外部系统提交工作，GitHub job 取消不证明外部工作也已停止。应保留任务关联身份并查询终态，避免下一轮直接重复提交。这项责任不由矩阵配置自动实现。

实验身份也应有明确含义：哪个版本尚未承诺支持，谁负责观察失败，何时退出实验。永久允许失败但无人看结果，会逐渐把兼容性检查变成无法解释的背景噪声。这里不替团队指定实验期限，只要求容错范围与质量承诺能够互相对应。

max-parallel 设成一，就不会取消了吗？

仍可能取消排队中的矩阵任务。官方说明把运行中和排队状态都纳入 fail-fast 的作用范围，而并发上限只限制同时运行多少个成员。改成单并发不会关闭取消策略；第一个非容错成员失败后，后面的成员可能尚未启动就结束为取消。

因此，若目的是拿到全部成员结果，应该评估取消策略，而不是只调整并发数量。若目的是减少同时占用资源，再单独调整并发上限。把两项目标分清，并把稳定成功作为独立门禁，才能解释实验失败、稳定失败和未执行结果分别如何影响交付。
