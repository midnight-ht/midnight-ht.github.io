subTest块内断言失败，为什么下一条没有执行

区分subTest失败后的块内跳过和块外继续，用完整事件轨迹保留内部失败，再以failfast问答改变运行条件。

正文

核心要点

  • 失败后从with块结束处恢复，不从断言下一行恢复。
  • 继续执行不代表子测试失败被抹去。
  • 停止配置与共享状态需要分别核对。

subTest 里的断言失败，会跳过同一个 with 块中尚未执行的语句。默认运行器记录失败后，可以从块外继续，并进入后续循环；它不会回到失败断言的下一行。要判断哪些检查真正发生，应看上下文边界和执行轨迹，不能只记住“子测试失败还会继续”。

恢复点决定哪些检查会发生

Python 3.14.10 的 unittest 文档允许在一个测试方法内用 subTest 区分参数相近的检查。CPython 3.14 的实现把子测试作为上下文管理器：块内异常交给结果收集器，随后在上下文结束处恢复。这里核对的是在线版本，实际运行环境应另存解释器版本；以下先采用支持子测试的标准运行器与默认停止设置。

假设一个价格表测试同时检查金额、币种和税率。作者把三条断言放在一个 subTest 里，以为金额失败后仍会检查另外两项。实际上，金额断言抛出异常时，普通 Python 异常流已经离开当前代码块。框架能够记录这个子测试，不等于它能够替程序从下一行恢复。后两项可能根本没有被验证。

因此，同一份失败报告里只有一项错误，不能推出其余性质都满足要求。它也可能只说明首个失败阻止了后续检查。若业务要求每项性质都得到独立结果，就应给独立检查各自的上下文或方法，而不是让一个大块承担所有观察。拆分之前还要说明依赖：若税率计算必须依赖已验证金额，前一步失败后继续运算反而可能只制造次生错误。

把路径写成独立的预期

下面是完整的本地教学文件。它不调用业务接口，不写数据库，故意制造一个内部子测试失败。外围脚本只核对控制流与失败是否被保留；外围脚本通过，不能说内部测试全部通过。本篇提供代码与预期，未在此次写作中执行，不存在真实测试通过回执。

# trace_subtest.py
import io
import unittest

EVENTS = []

def record(n, position):
    EVENTS.append((n, position))

def require_inner_failure(result, report):
    assert len(result.failures) == 1, report
    assert not result.wasSuccessful(), report

class TraceCase(unittest.TestCase):
    def test_rows(self):
        for n in [0, 1, 2]:
            with self.subTest(n=n):
                record(n, "enter")
                self.assertNotEqual(n, 1)
                record(n, "inside-tail")
            record(n, "outside")
        record("method", "done")

def observe(failfast=False):
    EVENTS.clear()
    stream = io.StringIO()
    suite = unittest.defaultTestLoader.loadTestsFromTestCase(TraceCase)
    result = unittest.TextTestRunner(stream=stream, failfast=failfast).run(suite)
    return list(EVENTS), result, stream.getvalue()

if __name__ == "__main__":
    events, result, report = observe()
    expected = [
        (0, "enter"), (0, "inside-tail"), (0, "outside"),
        (1, "enter"), (1, "outside"),
        (2, "enter"), (2, "inside-tail"), (2, "outside"),
        ("method", "done"),
    ]
    assert events == expected, events
    require_inner_failure(result, report)
    print(report)
    print(events)
    print("Expected inner failure and trace matched")

候选调用是 python3 trace_subtest.py。先保存该命令退出值与完整输出，再运行其他命令，避免把后续操作成功误记为测试结果。外围预期列表在运行前给出，不能观察一次实际输出后原样抄成“正确答案”。如果修改了循环或断言，应先解释业务合同如何变化，再修改预期。

零号输入能够到达 inside-tail，也能到达块外的 outside。一号先记录 enter，随后断言失败，因此没有 inside-tail；默认上下文收集失败后，块外的 outside 仍会出现。二号再进入自己的子测试，方法末尾出现 done。这些标记回答的是代码到达哪里，报告中的失败则回答哪些要求没有满足，两份证据缺一不可。

外围还明确要求 result.wasSuccessful 为假。这样，若有人为了让示例变绿删除内部断言，轨迹可能变化，失败数量也不再符合合同，外围检查应拒绝这种“修复”。预期失败是解释异常边界的输入，不是允许真实产品测试默默忽略错误的政策。接入持续集成时，应让真正业务失败仍能进入阻断结果，不能无条件复制这个教学包装。

独立报告，也需要独立输入

把金额和币种拆成两个 subTest，可以让各自断言获得执行机会，但不会自动隔离状态。它们仍在同一个测试方法里，共享已经创建的对象、变量和外部资源。上一个子测试改变列表，后一个就可能读到变化；没有任何“每个子测试重新开始”的隐含事务。

若每组数据需要空列表，就在相应迭代中创建。若需要全新的数据库状态，就应使用项目实际的隔离和清理机制，并证明失败路径同样清理。subTest 的参数主要帮助报告标识输入，不负责撤销文件写入、恢复网络服务或为每轮重新执行一套测试夹具。把子测试名字写得再完整，也不能补上缺失的状态边界。

对于必须发生的收尾，不能把清理语句放在可能失败断言之后，并假定框架会续跑到那里。可以按资源寿命使用 finally 或相应清理登记，但要分别检查取得资源是否成功、清理是否允许重复以及清理失败如何报告。测试继续运行只是控制流能力，并不是外部副作用已安全恢复的证明。

报告计数也不能代替路径核对。本例只有一个测试方法，里面的多个输入通过子测试标识区分；方法被运行，并不说明每个输入的全部语句都到达。接手者应同时查看失败附带的输入标识与事件轨迹，特别是某一轮在准备阶段就失败时，不能把后续断言的缺席解释成要求满足。

记录函数只是把同一格式的事件写入集中到一处，不改变记录点的位置。外围失败核对也提成一个有名字的函数，由两份脚本共用，以免默认组和停止组逐渐采用不同的成功定义。真正业务断言仍留在原位置，失败组依旧必须失败；整理代码不应把示例变成只验证工具包装自身的全绿测试。

加上 -f 后，为什么下一个子测试也不运行？

因为 failfast 改变了默认继续条件。标准运行器启用停止设置时，失败子测试结束后可以停止本轮方法与后续运行。前面默认轨迹不能原样用于这一组。继续使用同一份文件，可从同目录另存以下完整对照脚本；它只导入定义，不会执行被 main 保护的默认检查。

# trace_failfast.py
from trace_subtest import observe, require_inner_failure

events, result, report = observe(failfast=True)
expected = [
    (0, "enter"), (0, "inside-tail"), (0, "outside"),
    (1, "enter"),
]
assert events == expected, events
require_inner_failure(result, report)
print(report)
print(events)
print("Expected fail-fast boundary matched")

这份对照也未执行。候选命令 python3 trace_failfast.py 应得到不同的预期轨迹：一号块外标记、二号和方法尾标记都不出现。命令行的停止选项与自定义运行器设置应以本次真实配置为准，不要仅根据测试文件中没有出现停止参数，就断言所有环境都会继续。

站内的patch 名字查找文章解决替换的是哪个依赖名字，本题解决失败以后哪个检查还能到达。评审测试时，把实际输入、到达路径和最终失败结果一起保留，才能分清“没有报告另一个错误”和“另一个要求确实已验证”。
