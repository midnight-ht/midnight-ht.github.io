换了高刷新率屏幕后，逐帧加2px的动画为什么更快？

以一秒240px教学动画说明timestamp进度、首帧起点、取消与后台恢复，区分同帧时间值和共享动画基准。

正文

核心要点

  • 固定每回调位移会让速度依赖回调频率。
  • 从经过时间算进度并限制终点，明确首帧起点与取消语义。
  • 后台恢复策略和多个动画的共同基准需要独立约定。

每次回调移动两像素，会让回调次数参与决定速度。要让同样的动画持续同样时间，应从 requestAnimationFrame 的 timestamp 计算经过时长，再由时长得到位置。换成高刷新率屏幕后变快，通常应先检查按帧累加，而不是把所有设备强制当作每秒六十帧。

MDN 的 requestAnimationFrame 说明指出，回调频率一般跟随显示器刷新率，并提醒固定每帧进度会在高刷新率屏幕上更快。读取页面标注二〇二六年八月二十一日修改；“一般”不是每次调用间隔固定的保证，更不是项目已经测过所有屏幕的证据。

帧是更新机会，时间才是速度的分母

假设一分钟里每次回调增加相同距离，回调次数越多，总距离越大。用更短的假设便能看清：若每秒恰有六十次回调，每次两像素是一百二十像素；若恰有一百二十次，就是二百四十像素。这里的频率只用作算术对照，不是浏览器测量结果，也没有假设刷新率等于每秒一定获得的回调数。

掉帧也会让同一种实现变慢。某一段主线程忙碌时少执行了回调，按帧累加只前进少量距离；用户看到的不仅是少了中间画面，还可能是整体动画时长被拖长。若目标是固定时长的界面过渡，位置更适合写成经过时间的函数，缺少某一帧不应改写最终时间合同。

HTML Living Standard 的动画回调算法取出本轮回调，在调用之前从列表移除，并传入本轮时间值。核对页面为二〇二六年十一月六日更新。一次请求不是永久订阅，要继续动画，回调需要再次请求；取消与重新开始也要管理自己的请求身份。

一秒移动二百四十像素的完整页面

以下完整 HTML 未在浏览器执行。它只移动一个教学方块，不发送请求，不代表游戏物理、支付进度或真实任务完成度。首次回调设起点，位置按零到一的归一化进度计算，并限制终点；按钮可以取消待执行回调，重复开始先结束旧的请求链。

<!doctype html>
<meta charset="utf-8">
<title>Elapsed animation</title>
<style>
#track { width: 280px; padding-block: 10px; border: 1px solid; }
#box { width: 30px; height: 30px; background: #275dad; }
</style>
<button id="start" type="button">Start one-second move</button>
<button id="stop" type="button">Stop</button>
<div id="track"><div id="box"></div></div>
<pre id="out"></pre>
<script>
const byId = id => document.getElementById(id);
const box = byId('box');
const out = byId('out');
let request = null;
let start = null;
function stop() {
  if (request !== null) cancelAnimationFrame(request);
  request = null;
}
function frame(timestamp) {
  request = null;
  if (start === null) start = timestamp;
  const elapsed = timestamp - start;
  const progress = Math.min(Math.max(elapsed / 1000, 0), 1);
  box.style.transform = `translateX(${240 * progress}px)`;
  out.textContent = JSON.stringify({ timestamp, elapsed, progress });
  if (progress < 1) request = requestAnimationFrame(frame);
}
byId('start').onclick = () => {
  stop(); start = null;
  box.style.transform = 'translateX(0px)';
  request = requestAnimationFrame(frame);
};
byId('stop').onclick = stop;
window.addEventListener('pagehide', stop);
</script>

独立预期是经过二百五十、五百、一千毫秒时，位置分别为六十、一百二十、二百四十像素。采样频率改变，只会改变取到哪些中间点；相同 elapsed 代入同一函数应得到相同位置。若实际回调跨过一千毫秒，clamp 让位置停在终点，不会因最后一次间隔较长而超出距离。

这里的一秒从首次回调开始，不是从用户点击开始。浏览器可能延迟第一次交付，选择首次 timestamp 可以避免把等待第一帧的时间算作已经演示过的进度。若产品要求与外部媒体或另一任务时间轴一致，应另选对齐基准，不能一面用独立首帧起点，一面承诺严格外部同步。

取消只阻止仍在队列中的请求，已经执行并画出的状态不会自动撤销。上例 Stop 保留当前位置，再次 Start 才重置；这是明确的教学选择。真实组件可能需要完成、暂停、重放或退出回调，应逐项定义，不能因为没有后续帧就把业务状态写成“已完成”。

本例的 Stop 只取消后续帧并保留位置，Start 则重置到起点；它没有从暂停点继续的 Resume，也没有演示自动轮播。产品若需要让读者暂停内容后继续操作页面，可以接着看自动滚动公告的暂停、停止与恢复：先按触发方式、持续时间与并行内容核对适用条件，再决定恢复位置及离开控制器后的状态。本页的一秒手动动画不能据此当成产品暂停机制已经通过无障碍验收。

后台恢复后，跳到终点还是继续剩余动画？

MDN 说明多数浏览器会暂停后台标签或隐藏 iframe 的回调。timestamp 方案并没有承诺后台继续绘制。恢复后的时间差可能跨过整个持续时间，上例便到达终点；这对跟随绝对经过时间的短过渡可以合理，但不一定符合需要用户看完内容的引导。

若目标是只累计活动期间的动画时间，就要记录暂停与恢复、排除隐藏区间，再按这个新定义计算进度。不能简单把恢复后的大 delta 任意夹小，然后仍称总时长是一秒：那已经改变了时间合同。选择应该来自用户任务，日志也要说明用了墙钟式经过时间还是活动时长。

物理模拟是另一种任务。把巨大 delta 直接用于速度、碰撞或积分可能产生不稳定结果，需要固定步长、子步或其他明确方案。这里的绝对位置插值并没有验证那些算法；不能因为方块到达正确终点，就宣称同一代码能保证游戏在掉帧后仍有正确物理行为。

同帧 timestamp 相同，为什么两个动画仍不同步？

MDN 说明，同一帧内排队的多个回调收到相同 timestamp，即使前一个回调已经花费计算时间。但相同采样时刻不等于相同起点。两个动画分别保存首次回调的 start，如果不是同一次开始，或 duration 不同，即使此后收到相同时间值，也会得到不同进度。

需要共同进度时，可以把同一基准交给多个渲染函数，让它们从同一个 elapsed 计算自己的位置。分别在每个回调里调用 performance.now()，得到的是各自执行时的采样，不是自动建立同步。也不要把这一页共享时值的说明扩成任意跨进程、跨来源页面的通用时钟协议。

待执行验证先给纯进度函数输入不同间隔的时间序列，检查上述三个已知点与最终夹取，再在目标浏览器操作开始、停止、重复开始和后台返回，记录回调时间与位置。纯函数断言不证明屏幕刷新率，浏览器日志也不证明业务任务进度。本文没有执行这两类测试，交付时应分别保留结果。

当问题只是让界面移动固定距离和时长，先把位置与回调计数分开。只有这样，后续看到少帧、首次延迟或后台暂停，才知道改变的是采样机会还是产品真正承诺的时间。
