WorkingDirectory设好了，./worker为什么仍启动失败

区分ExecStart首项定位与进程工作目录，用完整unit和读文件程序拆解非法首项、缺输入、搜索路径与解释器参数。

正文

核心要点

  • 工作目录不放宽可执行首项的路径规则。
  • 程序定位、目录准备和数据读取要分别核对。
  • 解释器的相对脚本参数属于另一层解析。

WorkingDirectory 设置进程运行时的工作目录，不会把 ExecStart 的首个参数改成任意相对路径。首项要么是可执行文件的绝对路径，要么是不含斜杠的简单名字；把 ./worker 写在这里，不能因为已经设置工作目录就获得许可。先区分程序定位与程序开始后的文件读取。

终端里先 cd，不等于服务解析方式

systemd.service 的命令行说明明确列出首项的两种形态。简单名字按相应搜索路径解析，而含斜杠的相对路径不属于这两类。systemd.exec 的 WorkingDirectory 条款设置的则是执行进程的目录。两项配置处理不同阶段的输入。

本篇于二〇二六年十一月九日核对的官方 latest 页面标识 systemd 二六二。实际主机可能采用另一版本或发行版配置，不能把网页标识写成本机探测结果。排查应保存管理器版本、完整有效单元与附加配置，不能只查看代码仓库里一段可能已被覆盖的文本。

维护者在终端中进入程序目录后，可以用点斜杠执行文件，于是把相同片段放进 ExecStart。失败并不一定是工作目录未生效；可能是在创建进程之前，首项形态就不符合配置规则。反复调整 WorkingDirectory，只是在修改另一项输入，未必触及真正失败位置。

一份把程序和数据分开的完整示例

下面是未安装、未启动的 Linux 教学配置。它假设主机确实存在所列绝对解释器路径，教学目录与文件由操作者在隔离环境准备。当前写作环境没有运行 systemd 服务，因此不提供服务启动成功或业务完成记录。不要未经核对就把这些路径写到真实机器。

# task.py — save under the configured working directory
from pathlib import Path

cwd = Path.cwd()
value = Path("input.txt").read_text(encoding="utf-8").strip()
if value != "teaching-value":
    raise ValueError("unexpected teaching input")
print("cwd:", cwd)
print("input accepted:", value)

# /opt/path-demo/input.txt 的实际内容，不包含本行说明
teaching-value

[Unit]
Description=Executable path and working directory teaching fixture

[Service]
Type=oneshot
WorkingDirectory=/opt/path-demo
ExecStart=/usr/bin/python3 /opt/path-demo/task.py

本例的程序首项是绝对解释器路径，脚本参数也采用绝对路径，刻意排除脚本定位的额外变化。输入文件则由 Python 使用相对路径读取，因此可观察工作目录的作用。若目录、解释器、脚本权限与输入均符合假设，预期程序报告教学目录，并接受 teaching-value。这个预期来自预先给定输入，不是已经观察到的日志。

为看清反例，另存一份单元，只把首项改成 ./task.py，并保留其他条件。它违反首项允许形态，不能把失败解释成“Python 不会读相对文件”。另一份对照只保留有效命令，却移走 input.txt：进程可能已经创建，但程序读取失败。两种结果需要不同修复，不能统称路径问题后一起改权限、目录和命令。

第三种情况是工作目录本身不存在。它可能在程序开始前造成失败，因而没有 Python 打印并不能单独证明解释器路径错误。应结合管理器结果与日志确定卡在哪一阶段。示例不声称所有发行版返回完全相同的错误文本或数字；真实错误应原样保存，不从预期反填。

搜索路径需要独立的配置证据

使用不带斜杠的简单程序名，也不是自动在 WorkingDirectory 中搜索。官方手册说明标准搜索目录，并提供查看默认搜索路径的方法。固定部署程序使用明确绝对路径，通常更容易交接；系统工具使用简单名字，则应确认本机搜索范围确实包含它。这里不把两种合法写法排成适用于所有项目的唯一规范。

同一执行环境手册的 ExecSearchPath 条款提供可执行文件搜索目录，并说明它与用户通过 Environment、EnvironmentFile 或 PassEnvironment 提供 PATH 时的关系。该选项自二五零加入。采用它之前，应核对本机版本以及实际环境来源，不能从交互 shell 的 PATH 推断服务拥有同样内容。

如果真实部署用了新的根目录或根镜像，还要核对程序在进程可见的文件系统中是否存在；宿主机上能找到，不自动证明服务的视图里能找到。此时不要继续往搜索路径里添加宿主目录来碰运气，应先确定路径相对于哪个根。程序、解释器和所需文件必须在实际执行视图中共同成立。

为什么不直接包一层 shell？

服务命令行并不默认执行完整 shell 语法。重定向、管道和后台符号不能凭终端经验直接复制；需要这些行为时，显式 shell 会增加解析、引用与退出传播的合同。给一个原本只需正确程序路径的服务加 shell，可能让问题从定位文件变成脚本状态难以解释。

例如 shell 成功启动，不证明内部程序完成；如果包装脚本吞掉失败，服务结论又可能失去原始错误。确实需要 shell 时，应固定实现并检查退出约定，而不是把它当作解决所有相对路径问题的通用开关。本篇配置不需要 shell，教学程序直接由解释器执行。

拟议验收在隔离 Linux 上先核对有效单元和文件视图，再做语法检查，最后观察实际启动日志与输出。语法检查通过只是解析层结果，不能证明目录、权限、输入和程序均满足运行条件。保存每次只改变的一项配置，才能把有效命令、无效首项、缺输入与缺目录四组结果归因。

python3 ./worker.py 为什么可能可以？

因为这里的首项是简单解释器名字，后面的相对脚本路径只是参数。systemd 先按首项规则定位解释器，再把参数交给它；解释器随后在进程工作目录中解析脚本相对路径。它与直接把 ./worker.py 放到受限制的首项不同，不能把首项约束扩大成所有参数必须绝对路径。

这一写法仍有前提：解释器能被搜索到，工作目录正确，脚本可读并且文件名匹配。若有任一条件不满足，不能用“参数允许相对”承诺启动成功。选择绝对脚本路径可以减少一个位置依赖，选择相对路径则需要把工作目录纳入可检查的部署合同。

站内的就绪通知文章讨论程序何时能报告 READY，本题处理更前面的程序定位与目录准备。先证明指定程序以正确输入运行，再判断就绪和业务完成；修改 Type 并不会修复不合法的可执行首项。
