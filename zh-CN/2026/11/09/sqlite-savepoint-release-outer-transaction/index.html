SQLite RELEASE 已成功，数据为什么仍被外层回滚？

对照 BEGIN 内释放与最外层保存点释放，解释 SQLite 事务所有权、最终回滚和 ROLLBACK TO 保留标记的边界。

正文

核心要点

  • 内层RELEASE的改动仍受外层回滚影响。
  • 释放最外层保存点、使事务栈为空时会提交。
  • ROLLBACK TO保留目标标记，不能等同普通ROLLBACK。

内层 RELEASE 只撤掉保存点标记，改动仍属于外层事务。用它作为“已保存”回执，会早于真正提交。在 SQLite 中，必须先知道该保存点外面还有没有事务，再判断 RELEASE 的成功究竟完成了哪一层工作。

假设一个导入子函数负责写入一条记录，调用者把多条记录包在同一个事务中。子函数建立保存点、插入、释放后返回成功；最后另一条记录失败，调用者回滚整批。先前那条记录随之消失，符合事务规则。需要修正的可能是子函数返回状态的解释，而不是数据库保存点没有生效。

谁建立了最外层范围？

SQLite 的 Savepoints 文档把保存点描述为可嵌套的命名事务范围。SAVEPOINT 可以在 BEGIN 之内，也可以独立开始。后者若处在最外层，会建立一笔延迟事务。命令文本相同，起始栈不同，结束时的含义也可能不同。

内层 RELEASE 移除相应标记，把改动留在父事务中；之后父事务的提交或回滚仍作用于这些改动。最外层 RELEASE 如果使事务栈为空，则会提交。因而“RELEASE 总是提交”和“RELEASE 永远不提交”都不准确，必须附上它释放的层级。

SQLite Savepoints 原文第二节解释内层释放与外层回滚，第三节列出栈规则。本文只讨论 SQLite 显式 SQL 的范围，不把其他数据库或某个 ORM 的同名方法自动当成相同行为；框架是否真的发送这些 SQL，需要另行观察。

两条只差外层范围的轨迹

下面的 Python 代码创建一个内存数据库，设置 isolation_level 为 None，以显式 SQL 控制事务，避免宿主默认行为替示例决定边界。建表先完成，两个用例独立从空表开始。phase 函数只依次执行列表中的显式语句，再同时打印状态与行；代码没有 executescript，也不打开业务文件。

import sqlite3
c = sqlite3.connect(':memory:', isolation_level=None)
c.execute('CREATE TABLE items(id INTEGER PRIMARY KEY)')

def phase(label, statements):
    for statement in statements:
        c.execute(statement)
    rows = c.execute('SELECT id FROM items').fetchall()
    print(label, 'active', c.in_transaction, 'rows', rows)

phase('A release', [
    'BEGIN', 'SAVEPOINT unit',
    'INSERT INTO items VALUES (1)', 'RELEASE unit',
])
phase('A rollback', ['ROLLBACK'])
phase('B release', [
    'SAVEPOINT unit', 'INSERT INTO items VALUES (2)', 'RELEASE unit',
])
print('SQLite', sqlite3.sqlite_version)

第一组预期在 RELEASE 后仍处于事务中，普通 ROLLBACK 后表为空。第二组没有外层 BEGIN，释放最外层保存点后不再处于事务中，表里保留编号二。第一组中的“释放成功”没有欺骗调用者，它只是完成了比调用者最终提交更小的一项操作。

把第二组误说成也不会提交，会形成另一种危险：调用方可能以为还能在稍后撤销这条记录。验收必须同时保留两组，确认同一个子函数独立调用与放进外层事务时分别怎么结束。只测试嵌套情况，会让错误的普遍否定看起来成立。

观察事务状态有助于解释范围，但最终行仍须核对。应用从连接池取到另一条连接后，检查的可能已不是原来的内存数据库或事务。示例刻意全程使用同一个连接；迁入应用时，应保留连接归属和调用栈的证据，而不是把打印过一次状态当成所有入口已验证。

子函数应该返回哪一种成功？

如果子函数加入调用者事务，它可以报告本段 SQL 与保存点管理完成，但不应对用户宣布整笔业务已提交。调用者在最外层提交确认后，才能给出相应数据库结果。若需要跨函数返回阶段状态，可以明确区分本段完成、等待外层提交与最终失败，避免一个布尔值承担相互不同的承诺。

子函数也不能为了“保证写入”随手 COMMIT。SQLite 的 COMMIT 结束整个事务范围，这会越过调用者的所有权，让原本计划整批回滚的后续逻辑失去保护。事务责任应在 API 设计里说明：函数是独立管理事务，还是只加入现有事务。是否允许两种模式，都要给出可检验的入口。

异常路径同样需要范围。内层一条写入出错后，调用方是拒绝整批，还是仅撤销本段并继续，属于业务选择。保存点提供局部控制，不决定导入是否允许部分成功；结果报告也不能把“未抛异常”直接合计成已持久成功的行数。

站内的部分导入结果说明讨论如何向用户描述记录身份和最终结果，使用的是 PostgreSQL 场景。本题则用 SQLite 的两种 RELEASE 起点来确认函数究竟有没有提交，不能拿一个数据库的执行记录替另一个数据库验收。

ROLLBACK TO 后，要重新建立保存点吗？

不必。这项追问增加第三条轨迹，区别于主例的普通外层回滚：BEGIN 后建立 unit，插入编号三，再执行 ROLLBACK TO unit。回滚返回到保存点之后的状态，但 unit 标记仍保留，所以可以继续插入编号四，再次回滚到 unit，而不必重新 SAVEPOINT。

BEGIN;
SAVEPOINT unit;
INSERT INTO items VALUES (3);
ROLLBACK TO unit;
INSERT INTO items VALUES (4);
ROLLBACK TO unit;
RELEASE unit;
COMMIT;

在空表上独立运行，预期三和四都没有留下，最后 RELEASE 移除该标记，COMMIT 结束剩余外层事务。不要把 ROLLBACK TO 的成功理解为整个事务已经退出，也不要把它与不带 TO 的 ROLLBACK 互换；两者对栈和后续操作的影响不同。

保存点名字还应便于追踪。SQLite 允许名字重复，按规则查找最近的匹配范围；嵌套函数共用一个泛化名字，会让维护者难以凭日志判断命中了哪一层。采用明确且可定位的命名，是工程建议，不是额外的数据库隔离保证。不能通过日志名字好看就推断事务所有权正确。

这些用例检验的是单连接显式 SQL 与最终行状态，不检验断电后的介质耐久、连接池重试或用户界面的终态提示。发布验收应保存引擎版本、两组外层范围、内层释放后的状态和最后提交或回滚的结果。先让“成功”指明自己是哪一步，再让调用者根据真正的最外层结局报告业务状态。

本次归档运行使用 Python 三点十一点十五与 SQLite 三点五三点一：A 释放后仍在事务中，回滚后零行；B 释放后退出事务并保留编号二。追问中的两次回到同一标记也已在清空表后独立运行，三和四均未留下；这只验证本地单连接路径。
