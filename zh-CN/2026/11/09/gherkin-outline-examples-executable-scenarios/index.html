Gherkin表格有三行，为什么只跑了一个场景？

区分Examples展开与步骤Data Table实参，用三条权限规则、两个完整feature及多Examples计数，核对候选实例、筛选与真正断言。

正文

核心要点

  • Examples按数据行生成独立实例，表头与模板本身不额外运行。
  • 步骤Data Table作为整体实参，是否逐行断言由实现负责。
  • 多Examples按行分别展开，候选数与筛选后执行数分开核对。

步骤下面放了三条权限记录，不表示验收器会报告三个独立场景。先看表格属于 Examples 还是某个步骤：前者为 Scenario Outline 生成实例，后者把整张表作为一次步骤调用的数据。想逐项获得独立结果，应先确定展开单位，再核对实际执行集合。

一张表，到底是谁的输入？

Cucumber 的 Gherkin Reference说明，Scenario Outline 是不直接运行的模板，Examples 的每个数据行使它运行一次，表头不计。读取的文档标注二〇二六年十一月八日更新；这不是项目运行器已经升级的证据，也不保证编辑器、插件与运行器采用同一个解析版本。

步骤后面的 Data Table 则作为最后一个参数交给步骤定义。它可以有三行、三十行，仍是这个场景中这一步收到的一张表。步骤代码可以自己遍历并断言，但那不等于产生了多份独立场景报告；第一行抛错以后是否还检查后续行，还取决于步骤实现。

这一区别直接影响失败定位。权限矩阵里一条拒绝规则错了，如果三行都在同一步循环里，报告可能只说这个步骤失败。若三条规则各自实例化，报告可以把失败与具体输入联系起来。选择不是哪种表格更高级，而是你需要一次业务动作的整体数据，还是多次相同流程的独立结果。

把三条权限规则写成可核对实例

下面是未执行的教学 feature，假设下载策略只看用户状态和订单归属，不连接真实账号、权限服务或文件存储。表中的 allow 与 deny 是拟定业务规则，需由产品确定；Gherkin 只负责把它们送进步骤，并不会替团队证明规则正确。

Feature: Download permission
  Scenario Outline: Decide <state> access to <owner> order
    Given the user state is "<state>"
    And the order belongs to "<owner>"
    When the user requests a download
    Then the permission result is "<result>"

    Examples: permission rules
      | state     | owner | result |
      | active    | own   | allow  |
      | active    | other | deny   |
      | suspended | own   | deny   |

独立预期先写在运行器之外：第一行得到允许，第二行因不属于本人而拒绝，第三行因用户停用而拒绝。没有标签或名称过滤时，应有三个候选场景实例；不是一个模板加三个实例共四次，也不是按三列把所有值任意组合。每个实例都要建立自己的前置状态，否则上一行留下的登录或订单对象可能污染下一行。

尖括号中的名称引用表头。官方文档规定，替换发生在匹配步骤定义之前，因此 active 那行送去匹配的是已经替换的步骤文本。维护者新增表头却忘了更新占位符，应先检查展开文本与匹配结果，不能因为原始模板看起来有相似单词，就认定步骤已经接到对应值。

步骤实现还要兑现 Then。假设 When 只是返回了 HTTP 成功，Then 却仅确认没有异常，拒绝下载的两行也可能得到绿色结果。更合适的检查要读取明确权限判定，并证明被拒绝时没有取得文件；后者属于真实应用验收，本示例没有实现。模板展开正确与业务断言充分，应分别留下证据。

为什么把同样的行挪到步骤下面不等价？

下面另一份未执行的 feature 只有一次场景。它适合要求“一次请求接收多条记录”的流程，而不是暗示每一行拥有独立场景生命周期。

Feature: Check a permission dataset
  Scenario: Evaluate one dataset
    Given these permission cases
      | state     | owner | result |
      | active    | own   | allow  |
      | active    | other | deny   |
      | suspended | own   | deny   |
    When I evaluate the dataset
    Then every reported outcome matches its expected result

这里的步骤定义必须解释表格、执行数据集并比较结果。表头如何转成对象、错误怎样汇总、一次失败是否中断其他记录，都要看所用实现与测试代码；不能从竖线语法推断出来。若测试目标就是批量校验器的一次调用，保留整体数据甚至更准确，拆成单行反而测不到批次内的相互约束。

两个版本不能仅凭最终通过数互相代替。Outline 的三个实例可能运行在不同的隔离环境里；Data Table 版本可以刻意验证同批数据之间的重复身份、排序或联合限制。读者应先问失败是属于单个输入，还是属于整个集合，再决定报告需要怎样归属。

另一个反例是把关键字写成普通 Scenario，却保留尖括号和一张步骤表。你写下的符号没有自动启动 Outline 展开。先让解析器给出实际结构，确认它看到了哪种节点；再检查生成的执行对象。不要把编辑器语法着色当成运行器已经产生三个实例的回执。

多个 Examples 段落会做笛卡尔积吗？

不会因为分成两张表就自动相乘。Outline 对各 Examples 数据行分别实例化：第一段两行、第二段三行，未筛选时是五个候选实例，而不是六种组合。若规则确实要求两个维度的每种搭配，应把期望搭配明确列成行，并为排除的组合说明原因。

分段仍有用途，例如给停用用户与普通用户不同的示例说明或筛选条件。但候选数量和实际运行数量要分开：项目可能按标签、名称或其他配置只执行其中一部分。报告少了两例时，应核对选中的集合与过滤配置，不能直接断定模板没有展开，也不能用预计五例冒充实际五例已运行。

验收记录可以同时保留 feature 文件摘要、运行器版本、命令与过滤参数、生成实例名称以及各实例断言结果。先确认结构阶段确有三条或五条目标实例，再让步骤定义执行；匹配成功还不能代替断言结果。没有这些记录时，本稿中的数量只作为规则推导的预期，不称为已通过的测试。

需求评审中的规则与未决问题解决的是先确定什么结果算正确。本题从规则已确定之后开始：把每项预期落实到正确的展开单位。下一次看到“表里有三行但报告只有一例”，先检查表的归属与生成实例，再决定改 feature 还是改步骤实现。
