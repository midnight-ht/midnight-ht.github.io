Kafka position 到了 103，为什么三条业务还没做完？

以单分区三条记录推导拉取、业务完成与提交恢复位点，比较提前提交跳过、提交前重放和并发处理缺口。

正文

核心要点

  • poll推进position不证明外部业务已完成。
  • 处理后提交仍存在效果成功而位点未更新的重放窗口。
  • 并行完成不能让恢复位置跨过未完成缺口。

poll 把一批记录交给程序后，消费位置可以已经前进；业务逐条处理与提交恢复位点是后面的两个动作。Kafka position 到了一百零三，不能据此宣布一百到一百零二的外部业务都完成，也不能推断组的已提交位点已经更新。

假设消费者一次取回三条订单事件，监控记录位置明显前移，业务库却只写入第一条。若把位置当成完成数量，仪表盘可能显示已消费，重启后又重复处理；若为了追平位置马上提交，还可能在后续崩溃时跳过未完成记录。需要先把拉取、处理和恢复入口三份事实分开。

一个分区里的三个进度

Apache Kafka Java 客户端四点一系列的 KafkaConsumer 文档区分 position 与 committed position。前者是下一条将交给消费者的记录位置，收到 poll 返回的消息时会自动前进；后者是已存储、供故障后恢复的位点。这里核对的文档页标明 clients 四点一点二 API，不把它笼统称作所有客户端版本的当前实现。

第三个进度由应用负责：哪些业务副作用已按自己的持久化合同完成。Kafka 客户端不能仅凭把记录交给程序，就知道数据库插入、邮件或其他服务动作是否成功。提交位点也需要按业务选择时机，文档里的手动提交示例先完成处理，再提交相应恢复位置。

KafkaConsumer 官方 API的 Offsets and Consumer Position 与 Manual Offset Control 两节支持这些区别。本文没有搭建 broker、运行 Java 消费者或访问外部业务库；后面的数值是一条标明假设的时间线，不是实测日志。

“消费了多少”也不是一个不加范围就能回答的问题。位点属于分区，不同分区上的同一个数字没有全局先后关系；实际记录的 offset 还可能有间隙。下面刻意采用一个分区、三个连续存在的记录，只为让每次恢复起点容易推导，不能把连续性当作生产前提。

三条记录，两个退出位置

设消费组 g 在分区 p 已提交一百，下次从一百这个恢复位置继续；该分区实际存在 offset 为一百、一百零一、一百零二的记录。关闭自动提交，主流程按顺序、同步处理。一次 poll 返回三条之后，position 可为一百零三，业务还可以一条都没完成。

partition p, group g
before poll: committed = 100
poll returns: [100, 101, 102]
after poll: position = 103, committed = 100
process 100: external write confirmed
stop before processing 101
restart from committed = 100

这条轨迹中，一百已经产生外部效果，却没有新的提交，重启后它可以再被交付。消费者必须考虑该记录再次进入业务代码时怎么办。若写入支持稳定身份去重，可以查已有结果；若是不可重复的外部动作，则需要该系统自己的查询或幂等合同，不能从手动提交直接得到“外部恰好一次”。

相反，在 poll 后立即提交一百零三，再于处理一百零一前退出，组的常规恢复会从提交位置继续，未完成记录就可能被跳过。这里并不是 Kafka 忘了已交付的记录，而是应用主动把恢复入口放到了业务完成范围之后。把提交提前可以减少重放，却也改变了丢失未处理工作的风险。

成功轨迹应另写：三条业务按序完成，随后提交一百零三并确认提交成功。该数值代表下一条待处理位置，不是“最后处理的一条是第一百零三”。本例采用明确存在的连续记录来解释，实际代码应使用适当的下一位点 API 或已核对的恢复位置，不能对任意批次一概猜数字。

手动提交只让决定更明确

在文档的逐分区示例中，应用处理该分区记录后，使用本批次提供的 nextOffsets 对应值提交。选择显式位置时，应核对记录属于哪个分区、哪些已完成，以及提交结果是否成功。无参数提交与提交一张显式分区映射的保护范围，也要按实际 API 调用理解。

提交抛错不能被日志里的“处理结束”覆盖。业务写入成功与位点确认是不同结果，提交失败后恢复可能带来重复；如果处理失败，又不应为让监控好看而直接提交整批。错误记录应保留分区、记录身份、业务写入状态和提交尝试的范围，避免一行笼统的失败日志无法重建顺序。

进程在外部成功和提交之间中断，是这份设计必须承担的窗口。把两条调用写得紧邻，不会让它们共享一次原子提交；关闭自动提交也只是让应用控制位置，不会自动为外部库加事务。站内的事务发件箱交接讨论另一侧的数据库与发送责任，本题是在消费者端观察外部效果和恢复位点的间隔。

重放测试不能只断言代码又收到了消息，还应观察外部效果是否重复、重复如何识别、调用者能否查到最终状态。若测试只使用内存列表充当业务库，就只能证明那段程序的顺序，不能证明真实存储的持久化和幂等约束。本文没有执行这些检查，也不报告交付次数。

一百零二先完成，一百零一没完成，能提交一百零三吗？

不能让恢复位置跨过尚未完成的一百零一。这里才引入主例没有的条件：同一分区的记录交给多个工作者并行处理，一百和一百零二都完成，一百零一仍在执行。poll 的位置已经前进，不说明中间这个缺口可以被忽略。

一种工程思路是按分区维护连续完成前缀，只有缺口补齐后才把可提交范围向前推进。它是应用状态管理建议，不是 Kafka 为任意线程模型自动实现的业务完成标记。工作者完成、所有权变化和提交的先后还要有一致协调，否则旧工作者晚到的结果可能影响新的分配。

rebalance 时谁负责等待、停止或接管未完成工作，也必须明示。不能仅把几个异步任务的最大 offset 当成完成前缀；实际 offset 有间隙，又不能要求每个整数都出现。这需要基于真实交付序列和分区归属设计，本篇不提供一份未经运行的通用并发消费者。

拟议验收先保持单分区同步主例，覆盖处理前提交的跳过风险、处理后提交前退出的重放、全部处理后提交成功三条路径，再单独加入并行缺口和分区再分配。记录每次 position、committed 与业务完成身份；只有三者各有证据，监控上的前进才不会被误读成业务已经完成。
