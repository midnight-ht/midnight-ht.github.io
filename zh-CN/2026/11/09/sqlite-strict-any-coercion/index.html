导入编号少了前导零：先比较两种 SQLite ANY

比较 SQLite STRICT ANY 与普通 ANY 的数字文本转换，用存储类别和完整输入验收前导零，并区分新写入保留与历史身份重建。

正文

核心要点

  • STRICT ANY按收到的值保留存储类别，普通ANY可能转换数字文本。
  • 绑定前丢失的原文不能由严格表恢复。
  • 历史身份重建需可信映射，并检查同值碰撞。

把字符串编号 000742 送进 ANY 列后只剩 742，先查表是否 STRICT，再查应用有没有提前转成数字。SQLite 的 STRICT ANY 保留传入值的存储类型；普通表里的 ANY 却会尝试把看起来像数字的文本转换成数值。字段声明同为 ANY，不代表两张表具有相同的输入合同。

假设外部目录把六位字符用作商品编号，000742 与显示为 742 的其他编号可能属于不同命名空间。导入程序只验收“能够插入”，页面后来才发现前导零不见了。这里需要查的是原文在哪一步改变，不能先给页面补零，把存储和协议的问题盖住。这是说明性场景，不是本站经历的数据事故。

先看绑定值，再看表选项

SQLite 从三点三七版本开始支持按表启用 STRICT。当前官方 STRICT Tables 文档的第三节专门比较 ANY：STRICT 表里的这一类型不做亲和性转换，普通表里的同名类型则会把可成功转换的数字样式文本存成数值。这个区别解释了为何“换成更严格的表”，反而能保住混合类型的原貌。

保留的起点是数据库收到的值。请求体中的字符串经过业务代码转成整数，绑定参数时已经是七百四十二，STRICT ANY 也没有原来的六位拼写可存。排查材料应同时记录字段声明、表选项、绑定值的语言类型，以及实际存储类别。只打印查询后的数字，会错过转换发生的位置。

SQLite STRICT Tables 官方说明支持上述版本与类型规则。它不是要求所有编号使用 ANY 的建议；是否应该只接收字符串，是接口设计的另一项选择。需要逐位一致的业务身份时，先约定它是文本，而不是看见字符全为数字就允许任意数值转换。

同一输入，两张表

下面的完整 Python 示例使用内存数据库，只通过参数绑定送入数据。它不是迁移脚本，不会打开业务文件。两张表各自接收文本编号、真正整数和普通文本，查询显式按 rowid 排序，同时返回 typeof 与 quote。前者说明存储类别，后者便于区分数字与带引号的文本。

import sqlite3
c = sqlite3.connect(':memory:')
c.execute('CREATE TABLE strict_values(v ANY) STRICT')
c.execute('CREATE TABLE ordinary_values(v ANY)')
values = [('000742',), (742,), ('part-742',)]
for table in ('strict_values', 'ordinary_values'):
    c.executemany(f'INSERT INTO {table}(v) VALUES (?)', values)
    print(table, c.execute(
        f'SELECT typeof(v), quote(v) FROM {table} ORDER BY rowid'
    ).fetchall())
print('SQLite', sqlite3.sqlite_version)

这里建立的是普通 rowid 教学表，排序把每个输出对应到本次插入的输入位置。多行 SELECT 没有 ORDER BY 时，SQLite 不保证返回顺序，不能凭一次观察就断言第一行是哪条输入；SELECT 排序文档明确这项边界。真实导入宜另带稳定输入身份，而不是把练习中的 rowid 当成业务编号。

按文档预期，严格表的第一行是文本，引用后的值仍含六位原文；普通表第一行则成为整数七百四十二。第二个输入本来就是整数，两边都保留整数；第三个输入含非数字部分，两边都保留文本。对照的目标不是宣布某张表“数据更对”，而是确认它们分别接受并改变了什么。

仅比较页面显示会掩盖差异。有的驱动把所有值转成字符串，有的模板又按数值格式化；两个结果最终都可能显示成相同文字。因此验收应先保留数据库原始结果，再测试驱动与页面的转换。如果接口合同要求字符串，还要确认读取后输出的 JSON 仍为字符串，不能只在数据库里保住类型。

可以增加一项负例：把绑定值改成 int('000742')。此时严格表也只会收到整数，原文不应被期待回来。另一项独立检查是 ANY NOT NULL 插入空值应拒绝；ANY 允许混合类型，没有取消其他约束。两项负例分别定位上游信息损失和字段约束，不能靠一次成功插入互相代替。

保留原文，不等于验证编号

严格表的普通类型列仍可能进行无损转换。因此 STRICT 不是“输入类型有一点不同就全部拒绝”的总开关；ANY 更明确允许多种存储类别。把它用作原始导入暂存区可能合理，但业务编号必须满足的字符范围、长度、来源身份和唯一范围，仍须单独定义。

如果某列从来只应存文本身份，选择 TEXT 并配合入口校验通常更容易说明意图；这也不意味着只写 TEXT 就完成全部格式检查。若列确实要同时保存整数、文本与二进制值，则要约定读取方怎样保留类别，避免导出时统一字符串化而再次合并原本不同的输入。

还要核对实际嵌入的引擎版本。Python、桌面应用和迁移工具可能各自链接不同 SQLite；系统命令能建严格表，不证明应用内的引擎也支持。先从真实连接读取版本，再在那条连接上验证建表和读写。本文示例的局部结果不能替代移动设备或其他发行包的验证。

站内的JSON 长编号精度边界讨论另一种损失：数值表示未必逐位精确。本题即使没有超过整数范围，也可能因为亲和性转换失去拼写；前导零和数值大小是两个需要分别保护的维度。

迁到 STRICT，会自动恢复旧前导零吗？

不会。旧普通表里的字符串 000742 与字符串 742，都可能已经变成同一个整数。更改目标表选项，只影响新的存储合同，不能告诉维护者历史每一行原来有几位。任意补到六位，看似恢复了显示，也可能把另一个合法身份改成错误对象。

这里的恢复建议属于工程判断：先找权威目录或源身份映射；若协议确实规定固定长度，也要确认它适用于历史所有来源和时期。按行核对转换前后身份，检查同值碰撞、一个源身份对应多个目标行，以及缺少可信依据的记录。无法消歧的行应保留待处理状态，而不是让一条格式化函数替它们作决定。

验收应把历史重建与新写入分开。前者比较可信来源和恢复映射，后者用相同参数矩阵观察存储类别与原文。若只有新表插入成功的证据，就只能说明新入口的行为；不能因此宣布旧编号已经修复。先把这两份结果分别保存，再切换真正的导入入口。

本次在 Python 三点十一点十五、SQLite 三点五三点一的内存数据库运行了这组三输入对照，结果符合上述预期；绑定前转整数与非空拒绝也单独检查通过。该记录只覆盖归档脚本中的本地输入，不代表应用导入入口或设备验证。
