最近订单子查询为空，客户为什么一起消失？

用完整每客最近订单输入区分 LATERAL 相关引用与连接留行，检查零订单、并列选择和聚合子查询的不同基数。

正文

核心要点

  • LATERAL允许相关引用，连接类型决定零结果是否保留父行。
  • 最近一条需要明确排序，并检查客户与订单归属。
  • 无分组且未被HAVING过滤的聚合可在空输入返回一行。

LATERAL 能让子查询引用当前客户，却不会替 CROSS JOIN 保留没有订单的客户。每客最近一单应先定义空结果要留下谁。需要展示客户全集时，使用 LEFT JOIN LATERAL，并在子查询内明确订单归属和选择顺序；只写 LATERAL 不是防止丢行的开关。

设想客服页面按客户列出最近订单。客户一有两笔订单，客户二从没下单，客户三只有一笔旧订单。产品希望三位客户都出现，第二位订单栏为空。开发把独立查询改为相关子查询后，第二位整行消失；这时先查连接类型，不要为了补行伪造一张空订单。

引用范围与留行规则分开

PostgreSQL 十八版本的表表达式文档说明，LATERAL 子查询可以引用前面的 FROM 项。对每个提供关联值的外层行，子查询使用该行的值计算，再按通常的连接规则组合结果。它解决的是子查询能够看见什么，并没有修改交叉连接或左连接如何对待零行。

对子查询而言，某位客户没有订单就可能返回零行。交叉连接把当前客户与这些结果组合，零个结果便没有组合行。左连接则在没有合格匹配时补出右侧为空的一行。客户并没有从源表删除，只是原查询没有把他放进结果；报表缺人和数据被删应在排查描述里区分。

PostgreSQL 18 的 LATERAL 章节直接给出保留子查询无结果来源行的左连接用法。以下示例据此推导，本文没有启动 PostgreSQL 实例，也没有执行这些 SQL；结果是预期，不是数据库回执。

给最近一单完整输入

这里用值列表提供所有数据。客户一的两笔订单时间相同，故再按唯一订单编号倒序决胜。这个规则只是练习中约定的确定顺序，不代表真实业务一定应该把较大编号叫作更新。

WITH customers(id) AS (VALUES (1),(2),(3)),
orders(id, customer_id, created_at) AS (
  VALUES (11,1,timestamp '2026-11-01 09:00'),
         (12,1,timestamp '2026-11-01 09:00'),
         (31,3,timestamp '2026-10-01 09:00')
)
SELECT c.id AS customer_id, latest.id AS order_id
FROM customers c
LEFT JOIN LATERAL (
  SELECT o.id
  FROM orders o
  WHERE o.customer_id = c.id
  ORDER BY o.created_at DESC, o.id DESC
  LIMIT 1
) latest ON true
ORDER BY c.id;

预期三行依次是客户一配订单十二、客户二配空值、客户三配订单三十一。若把左连接改为 CROSS JOIN LATERAL，并去掉它不需要的 ON true，预期只剩客户一和三。这两个版本应该从同一份输入独立运行，比对客户标识集合和订单归属，不能只看受影响行数。

ON true 表示子查询已完成关联筛选后，这些结果行都可作为匹配。它没有替子查询建立客户关系；若漏写内部的客户条件，每位客户可能取到同一笔全局最近订单。结果仍是一客一行，行数测试会通过，订单归属却错了。因此应把客户与订单的配对作为验收目标，不能只比较两个独立标识集合。

同样，LIMIT 一控制每次子查询最多返回一条，不会让空结果自动变成一条。去掉排序后的次级编号，在时间并列时也不能保证总选十二。每客数量、空子集保留、代表行选择分别由不同规则承担；把它们都归给一个关键字，会使测试只证明其中一项。

之后的条件仍可能改变客户集合

即使已经左连接，外层再写 WHERE latest.id IS NOT NULL，客户二也会离开结果。这可能符合“只看有订单客户”的新需求，但和最初客户全集不同。不要看到 LEFT 就以为后面所有过滤都不能删行，应该按业务目标判断最终集合。

如果只展示符合状态的最近订单，应先说明“最近一笔订单必须已支付”，还是“最近一笔已支付订单”。前者先选最近再判断状态，后者先筛状态再选择；同一客户有较新的未付单和较旧的已付单时，二者会得到不同答案。本例没有状态列，不能把一个未定义的状态要求悄悄塞进最终 WHERE。

站内的LEFT JOIN 条件位置用另一组客户区分匹配与后置过滤。本篇增加的是每个客户单独计算子查询，以及这个子查询本身可能没有结果；遇到漏行时，要先画出该客户子查询返回几条，再看如何连接和过滤。

对于权限范围，左侧客户集合也要先符合授权。把租户条件只写进订单子查询，并不自动限制外侧可以列出哪些客户。这是查询评审建议，并非本例已实现租户隔离的证据；实际角色、表权限和应用访问路径仍须另行验证。

子查询改成聚合，还会零行吗？

未必。这里增加一个主例没有的条件：子查询是不带 GROUP BY、且没有 HAVING 淘汰该组的普通聚合。即使订单输入为空，SELECT count(*) 仍返回一条聚合结果，数值为零；主例 SELECT id 加 LIMIT 一则返回零行。两种子查询的行数不同，即使内部客户筛选完全一样。

因此，交叉连接聚合得到客户二及计数零，不能反证交叉连接普通最近单也会保留客户二。它保留的是实际产生的聚合行，并不是 LATERAL 自动补了行。若加上分组，空输入可能没有任何组；若 HAVING 要求计数大于零，也会把唯一聚合组过滤掉，又回到零行条件。

聚合函数文档说明计数和聚合结果；表表达式章节解释单组、分组与 HAVING。拟议验证应把普通 LIMIT、无分组计数、带分组计数、带 HAVING 的计数并列运行，逐客记录返回行数及值，而非只检查列名还在。

本篇只给出完整输入与可核对预期，没有执行计划或耗时数据。是否采用相关子查询，还需根据真实数据量、索引与查询计划决定。先让客户全集和所选订单都符合合同，再比较同一结果要求下的其他写法；不要用一次查询变快替漏掉客户作解释。
