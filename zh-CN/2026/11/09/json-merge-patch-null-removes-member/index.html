JSON Merge Patch 2026-11-09

Merge Patch 传了 null，为什么字段被删了？

按 RFC 7396 对照成员 null 删除、对象递归、数组整体替换与根 null，说明显式空值需求的格式取舍。

正文

核心要点

  • 对象补丁里的null成员请求移除对应键。
  • 对象可递归处理，数组作为完整值替换。
  • 根null补丁替换整个目标，需另核资源是否允许。

在 RFC 7396 的对象补丁里，null 表示删除成员。若界面想保留这个键并把值设成 JSON null，这份补丁表达不了同一个意图。使用 Merge Patch 前，应先确认产品所说的“清空”究竟是删除成员，还是保留一个显式空值。

例如昵称设置页提交 nickname 为 null，后台处理后这个字段完全不见了。若接口选用的确实是 application/merge-patch+json，这个结果符合该格式的删除规则，不能仅凭“不像普通 JSON 对象赋值”就认定实现出错。反过来，若产品需要保留字段为空，就不能靠改变标准规则来满足同一份合同。

先确认发送的是哪一种补丁

HTTP PATCH 方法不独自规定 JSON 正文怎样修改资源。RFC 七三九六定义 Merge Patch 的对象形状和处理算法；此前的 PUT 与 PATCH 选择，只解决替换表示和修改指令的区别，还没有替团队选择这份具体格式。请求、服务端解析器与接口文档应使用相同的媒体类型和语义。

Merge Patch 以目标内容和补丁内容比较，未出现的对象成员保持原状；出现且为 null 的成员被移除；非 null 成员继续按对应值处理。对象值可递归处理，数组等非对象值则按整体替换规则处理。不要把这份算法当成普通的字典浅合并，也不要把任意稀疏 JSON 更新都叫标准 Merge Patch。

RFC 7396 原文发布于二〇一四年十月，第二节给出算法，第四节登记媒体类型。本文核对该原文，不把今天的访问日期写成规范发布时间；示例中的字段和接口资源都是教学假设。

一份完整文档，三种变化

目标文档有昵称、偏好、标签和一个不参与修改的开关。补丁删除昵称，只修改偏好里的主题，并给标签一个新数组。完整预期必须保留其他字段，这样才能同时验证“改了什么”和“没改什么”。

{
  "target": {
    "nickname": "Ada",
    "prefs": {"theme": "light", "lang": "zh"},
    "tags": ["a", "b"],
    "keep": true
  },
  "patch": {
    "nickname": null,
    "prefs": {"theme": "dark"},
    "tags": ["c"]
  },
  "expected": {
    "prefs": {"theme": "dark", "lang": "zh"},
    "tags": ["c"],
    "keep": true
  }
}

预期结果没有 nickname，偏好里的 lang 仍在，theme 变成 dark。tags 则不是把 c 追加到原来的两项后面，而是整组变为只含 c。keep 未出现在补丁里，所以保持 true。只检查新主题存在，会漏掉昵称误保留、语言误删和标签误合并三种不同错误。

对象递归还包含类型变化的条件：补丁某处是对象，而目标对应处不是对象时，算法先把那处目标当成空对象再处理，不会保留旧标量作为某个隐藏子字段。因此给接口开放这类输入前，要决定资源模式允许怎样的类型变化。标准算法能算出结果，不代表业务必须接受所有结果。

数组不是按下标逐项合并

tags 给出新数组，就替换目标 tags 的完整值。若客户端只想改第二项，却发送一个单元素数组，结果不是“保留其他位置再改这一项”。当前文档的三个对象成员和数组元素属于不同层级，不能看到二者都是 JSON 结构就套同一种递归策略。

需要细粒度数组操作时，可以评估其他格式或稳定身份的业务动作。站内的JSON Patch 数组坐标讨论 RFC 六九〇二的操作数组，它按照每步变化后的坐标应用指令。它和 Merge Patch 是两种协议，不应把其中的 remove、replace 或 test 字段塞进这里，再期待服务端自动切换解释。

省略字段也应与空数组分开。省略 tags 保持原值，传 tags 为空数组会把整组清空；前者是不涉及，后者是一个明确替换。客户端表单若把没编辑过的列表统一填成空数组，可能准确执行一份并非用户所想的修改。测试要从界面意图追踪到实际补丁，而不是只比较两个解析后的对象外观。

以下函数仅演示数据项算法，在副本上操作，不调用 HTTP 服务或数据库。它不是包含权限、模式校验、版本竞争和错误响应的生产实现；本地运行通过，只能说明这段教学函数对给定输入的结果。

from copy import deepcopy

def merge_patch(target, patch):
    if not isinstance(patch, dict):
        return deepcopy(patch)
    out = deepcopy(target) if isinstance(target, dict) else {}
    for key, value in patch.items():
        if value is None:
            out.pop(key, None)
        else:
            out[key] = merge_patch(out.get(key), value)
    return out

调用前保存完整 target 和 patch，调用后把返回值与上面的独立 expected 比较，并确认原 target 没被函数改动。再测试删除不存在成员不创建新键、空数组替换，以及对象补丁遇到原标量的情况；不要只拿函数自己的输出生成预期，那样无法发现算法写错。

显式 null 是业务数据时，怎样选择？

RFC 在引言说明，这种设计主要适合以对象为结构、且不把显式 null 当作普通值使用的文档。若某个成员必须保留并设为 null，对象成员补丁没有同时表达“设空值”和“删除”的两种指令。更清楚的选择是换能表达该需求的格式，或提供含义明确的业务动作，而不是偷偷给不同字段的 null 定义相反规则。

并发也不会由对象递归自动处理。两位编辑者各发送一份完整标签数组，即使各自只在界面改了一项，后到的替换仍可能覆盖前一份结果。版本条件和原子保存需要另设合同。本文的内存函数不检查资源版本，也不证明服务端满足 HTTP 更新的保存要求。

根补丁就是 null，也是在删除一个键吗？

不是。这项追问改变的是补丁本身的类型和作用范围。对目标 {"a":1}，对象补丁 {"a":null} 得到空对象；同一目标若收到根补丁 null，则整个目标被替换成 JSON null。前者进入对象内的成员删除分支，后者进入非对象整体替换分支。

因此接口文档不能只写一句“null 代表删除”，而省略它出现在根还是成员值。资源是否允许根结果为 null，是业务模式需要决定的条件；允许解析不意味着必须保存。可把这两个完整输入作为独立用例，同时检查服务端拒绝路径或最终表示，而不是只在客户端看一个空白页面。

PUT 与 PATCH 更新合同提出先约定修改意图，本篇把约定落到一种格式的具体分支。验收先核对媒体类型，再核对完整前后文档、未编辑字段和失败后的资源。局部算法示例不能替代这些真实更新入口的证据。

这段函数已在 Python 三点十一点十五运行，主例返回值与独立预期一致，原目标保持未变。删除不存在成员、空数组替换、对象覆盖标量及追问的两类null输入也作了局部断言；没有运行HTTP服务、数据库保存或并发更新。
