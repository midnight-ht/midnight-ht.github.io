beforeinput已经preventDefault，为什么输入法组合文字仍会更新？

依据Input Events Level 2工作草案，区分普通输入与IME组合可取消性，提供完整textarea记录器、后置检查及明确校正边界。

正文

核心要点

  • 组合inputType与普通insertText的可取消性不同。
  • 编辑过程与可提交值分开；组合中不反复强改value。
  • 真实IME轨迹与合成事件测试分别记录，textarea范围数组不等于富文本范围。

对 insertCompositionText，当前 Input Events Level 2 草案规定输入法组合更新不可取消。先记录 inputType、cancelable 与组合状态，再决定拦截或后置校正，别因为 beforeinput 发生在修改前，就假设每一次编辑都能被 preventDefault 阻止。

Input Events Level 2是二〇二六年十月十五日工作草案，测试套件与实现报告仍在完善。本稿依据其事件类型表与组合顺序解释机制，不把草案要求当成特定系统输入法的实测结果，也不泛化为所有 beforeinput 都不可取消。

“发生在前”与“允许取消”是两项条件

该草案按 inputType 区分行为：普通 insertText 与组合中的 insertCompositionText 不同。后者在组合过程内不可取消。反复调用 preventDefault 不会把事件的 cancelable 从假改成真；处理器运行了，也不能据此认定它已经阻止了后续编辑。

组合会话从 compositionstart 开始，更新时有 compositionupdate，随后有 beforeinput 和 input；该组事件表示的活动文本区域在 beforeinput 之后、input 之前更新，会话以 compositionend 结束。输入法的候选、确认与取消不是每按一键就完成一次普通字符插入，过滤器若只在英文键入上验证，很容易误判覆盖范围。

观察组合标记可以补充状态，但不能替代 cancelable，也不能只靠一个布尔值给所有事件选择业务分支。应把事件类型、inputType、当时组合会话状态与实际 value 放在同一条记录里。真正控制什么可以提交，仍需自己的字段规则；事件可取消不等于输入合法，不能取消也不等于必须接受为业务数据。

一个不在组合中强改 value 的教学页面

以下完整 HTML 尚未执行。它假设字段是只允许 ASCII 字母、数字和连字符的教学编码，不适用于姓名、地址或多语言正文。页面记录输入轨迹；只在普通、可取消的 insertText 中尝试提前拦截，其他路径在 input 后更新有效性状态。校正按钮由用户明确触发，并在组合进行中拒绝修改。

<!doctype html>
<meta charset="utf-8">
<title>Composition input trace</title>
<label>Teaching ASCII code <textarea id="code"></textarea></label>
<p id="status" role="status">Empty code</p>
<button id="clean" type="button">Apply teaching ASCII correction</button>
<button id="check" type="button">Validate teaching code</button>
<pre id="out"></pre>
<script>
const ids = ['code', 'status', 'out', 'clean', 'check'];
const elements = Object.fromEntries(ids.map(id => [id, document.getElementById(id)]));
const { code, status, out, clean: cleanButton, check: checkButton } = elements;
let composing = false;
const rows = [];
const allowed = value => /^[A-Za-z0-9-]*$/.test(value);
const write = (node, text) => { node.textContent = text; };
const nullable = value => value === undefined ? null : value;
function assess() {
  if (composing) write(status, 'Composition active; not rewriting');
  else if (allowed(code.value)) write(status, 'Allowed teaching characters');
  else write(status, 'Correction required');
}
function record(event) {
  const { type, inputType, cancelable, isComposing, data } = event;
  const { value, selectionStart: start, selectionEnd: end } = code;
  rows.push({ type, inputType: nullable(inputType), cancelable,
    isComposing: nullable(isComposing), composing, data: nullable(data),
    value, start, end });
  write(out, JSON.stringify(rows.slice(-30), null, 2));
}
const handlers = {
  compositionstart(event) { composing = true; record(event); assess(); },
  compositionupdate: record,
  compositionend(event) { composing = false; record(event); assess(); },
  beforeinput(event) {
    record(event);
    if (!composing && !event.isComposing && event.cancelable &&
        event.inputType === 'insertText' && event.data !== null &&
        !allowed(event.data)) event.preventDefault();
  },
  input(event) { record(event); assess(); }
};
for (const [type, handler] of Object.entries(handlers)) {
  code.addEventListener(type, handler);
}
cleanButton.onclick = () => {
  if (composing) { assess(); return; }
  const at = code.selectionStart;
  const clean = value => value.replace(/[^A-Za-z0-9-]/g, '');
  const nextAt = clean(code.value.slice(0, at)).length;
  code.value = clean(code.value);
  code.setSelectionRange(nextAt, nextAt);
  assess(); code.focus();
};
checkButton.onclick = () => {
  if (!composing && code.value.length > 0 && allowed(code.value)) {
    write(status, 'Teaching validation passed; nothing submitted');
  } else write(status, 'Not accepted; finish editing or correct the code');
};
</script>

独立预期包含三条不同路径。普通合法字符留下；可取消的普通非法 insertText 可以被前置分支挡住；通过组合或其他未拦截路径进入的非法文本会被后置检查标记，但不会在每次组合更新时强行重写。最终按钮还拒绝空值及未完成组合，且没有网络提交，页面显示通过不能称为服务端已接受。

校正动作也有损失：它按教学规则删除不允许字符，并把光标放到原起点之前保留下来的字符数处，不保留原来的非折叠选区。这是明确的简化，复杂编辑器不能据此宣称选择范围、撤销栈或富文本结构都保持正确。对真实产品，显示错误并让用户自行修正，可能比自动删字更合适。

代码特意不在每个 input 回调中直接替换 value。输入法还在维护活动组合文本时反复改值，可能破坏选词或选择范围。后置策略不一定要立即删字：先识别当前最终值不合规，组合结束后提供明确校正和重验，同样能把编辑过程与可提交状态分开。不能把“没有提前挡住”偷换成“系统允许提交”。

真实输入的独立预期可以从编码前缀 AB- 开始：使用输入法组合一个汉字并确认，再点击验证。若最终值含这个汉字，必须显示拒绝，不能因为组合结束就变成校验通过。明确应用校正后，预期只保留 AB-，随后继续键入数字七得到 AB-7，才满足非空编码规则。再单独执行取消组合，保留实际值与轨迹，不预填它一定和确认路径相同。这个顺序同时检查编辑结束、值合法和继续输入三件事，均为待执行预期，不是已经捕获的输入法日志。

合成事件测不到真正的输入法过程

用 new InputEvent 构造一个 cancelable:false 事件，可以检查处理器是否尊重能力字段；它没有启动系统输入法，也不自动产生相同的默认编辑。日志顺序符合自己写的派发脚本，只证明这个脚本怎样调用处理器。真实验收要用目标操作系统、浏览器和输入法完成组合更新、选词、确认与取消。

还要覆盖粘贴、自动替换、选区替换与撤销。前置分支只处理 insertText，不假装已经拦住所有 inputType；后置检查读取实际 value，才有机会发现其他路径带来的不合规结果。程序自行赋值又是不同入口，应由赋值者明确触发相同的状态评估，不能默认所有代码改值都会生成用户输入事件。

结果记录应包含浏览器版本、输入法、事件轨迹、每步文本与光标，再观察校正后的继续编辑。合成事件测试与真实输入记录可以互补，但不能互相冒充。示例日志会记录用户输入，实际产品使用时应限制到非敏感教学数据，不能把密码或个人内容照样导出到公开排障材料。

textarea 的 getTargetRanges 为空，说明没有编辑吗？

不是。该草案的概览表对 textarea 和文本 input 给出空的范围数组，contenteditable 则有不同规则。空数组不能证明文本没有改变，也不能据此推断 beforeinput 是无效事件。上例为 textarea 记录 selectionStart、selectionEnd 与 value，使用的是这个宿主自己的观察方式。

这些位置值也不是可直接搬到富文本 DOM 的 StaticRange。富文本的节点结构、选择与编辑器数据模型需要另行协调；把同一个字符串过滤器套到 contenteditable，可能丢掉格式或错误定位。先确认编辑宿主类型，再选择如何记录修改范围和恢复状态。

DOM 取消标志与被动监听器处理一般取消能力；本题新增的是输入法组合阶段与编辑宿主条件。本文没有执行浏览器或系统输入法测试。真正的关闭条件应是最终字段规则得到验证，而不是日志里出现过 preventDefault 这个方法名。
