同一数组查询参数，为什么客户端发重复键而服务端等逗号？

比较form数组的逗号与重复键，给出完整OpenAPI参数合同、解析失败路径及deepObject嵌套范围；正文固定规范版本。

正文

核心要点

  • 数组类型和查询序列化由不同字段约定。
  • form的explode决定数组使用逗号还是重复参数键。
  • 核对原始URL、解析结构与结果；嵌套deepObject不能自行推导。

status 在文档里是数组，实际 URL 却可能是 status=open&status=closed；服务端若只读最后一个值，数组声明没有替它完成解析。要解释逗号与重复键的差别，应同时核对参数位置、style、explode，以及接收端怎样还原值，不能只看 schema 的 type。

OpenAPI Specification 3.1.1 的 Parameter Object把值的模式与序列化字段分开。本稿固定二〇二四年十月二十四日的这个版本，不声称它是最新发布版本。下面的订单接口是未执行的教学合同，不代表真实服务、生成客户端或框架已经支持这些编码。

两个 URL 可以表达同一个数组，但不能任意替换

在这一版规范里，query 参数默认采用 form 样式。style 为 form 时，explode 默认为 true；其他样式通常默认 false。于是只写数组类型而省略这两个字段，并不意味着“随便怎样编码都可以”，而是留下了一个有规定的默认组合。

对 status 的两个值 open、closed，form 配合 explode=false 的示意是 ?status=open,closed；explode=true 则是 ?status=open&status=closed。官方的 Style Examples 用 color 数组列出同类结果。这里的逗号是集合序列化的一部分，重复键是另一种展开策略，它们不是框架可以随意互换的排版。

下面给出完整的参数上下文，paths 中只定义一个返回状态码的教学操作。它没有响应业务结构，也没有实现服务器。需要逗号形式时，将 explode 显式改成 false，并同步调整客户端与解析器的合同；不要只改一个示例 URL。

openapi: 3.1.1
info:
  title: Order filter teaching contract
  version: '1.0'
paths:
  /orders:
    get:
      parameters:
        - name: status
          in: query
          style: form
          explode: true
          schema:
            type: array
            items:
              type: string
              enum: [open, closed]
      responses:
        '200':
          description: Teaching response only

这份合同的纸面预期是两个重复的 status 键被还原为两元素数组，再分别验证枚举值。服务端如果使用只取单值的读取方式，可能只留下 open 或 closed 中的一项；如果逗号模式下没有执行对应拆分，又可能把 open,closed 当成一个不属于枚举的字符串。先保存原始查询部分与解析结果，才能分清是发送错误、解析错误，还是模式确实拒绝了值。

类型检查的位置也会改变诊断。某些接收层先把重复键压成单个字符串，再交给模式验证器；验证器没有机会恢复已丢掉的第二个值。此时把 items 的枚举放宽，只会掩盖错误，不能恢复数组。应让解析阶段得到约定结构，再让验证器判断该结构是否合规。

默认值要和参数位置一起读

query 的默认 form 不能抄到所有位置。该规范对 path、header 默认使用 simple，cookie 则默认 form。simple 数组即使改变 explode，也不是 query 的重复键形式。工具封装若统一为所有数组加 explode=true，需要先检查每个参数的 in 和 style，不能把同一个字段名理解成跨位置完全相同的效果。

对象也不是数组的换皮。form 对象在展开时会把属性变成独立键值，未展开时则把键和值放在参数值中。若设计把多个对象属性展开进整个查询空间，还要检查它们是否与其他参数名字冲突；“两边都支持form”不能证明整条 URL 的键名组合没有歧义。

参数必填与数组非空同样不同。required 控制参数是否必须出现，数组元素数量由模式约束；业务若要求至少一种状态，应明确 minItems 等规则。这里不代替产品选择空集合语义，尤其不能把参数缺失、空字符串与没有筛选结果当成同一件事。编码修正后也要保留这些输入的独立预期。

不要用 join 和 split 猜测全部编码

演示值只有英文单词，容易让人误以为把数组 join(',') 就能完成所有场景。若原始值本身包含逗号、空格或保留字符，数据编码与分隔符会发生关系。需要按该版规范的序列化与百分号编码规则构造，而不是先拼一条看起来正常的 URL，再期待服务器猜出原始边界。

同理，URLSearchParams 可以帮助构造或读取键值，但它本身不知道某个 OpenAPI 参数应该用哪种 style，也不替应用选择重复键的聚合方式。一个本地字符串转换探针可以验证它实际产生了什么，却不能证明生成器、网关与后端都采用相同规则。验收应记录每一层实际看到的结构，而不是只看文档页面展示的请求示例。

迁移已有接口时，直接从逗号改成重复键可能改变旧客户端行为。应先盘点当前发送形式和服务端接受集合，再决定是否暂时兼容两种，以及遇到混合形式怎样拒绝。若系统同时接受 status=open,closed&status=open，如何去重、是否保持顺序、是否报错，都需要明确，规范没有替这份业务接口选择兼容策略。

deepObject 能直接约定嵌套对象或数组吗？

不能从简单示例推导通用嵌套格式。OAS 3.1.1 的 deepObject 描述适用于对象，嵌套数组或对象属性的表示未定义；Style Examples 中标为 n/a 的组合也没有定义行为。filter[range][min]=10 虽然可读，不能仅凭长得像方括号格式就宣称所有合规工具都应互认。

确有复杂筛选需求时，可以另行定义明确的序列化约定，或研究 Parameter Object 的 content 方式，用约定媒体类型表达复杂值。选择会影响客户端生成、服务端解析和 URL 长度等条件，需要目标工具的实际证据；本稿不承诺换成 JSON 表示就自动解决所有兼容问题，也不混用 style/schema 与 content 两套字段。

拟议验收从两种基础 URL 开始：分别检查 SDK 发出的原始请求、网关转发内容、服务端查询解析结构和最终筛选结果。再加入一个值、重复值、未知状态、参数缺失、空值与含分隔字符的合法值，逐项保留期望。只看到 HTTP 成功，不能证明两个状态都参与了查询；返回结果也应能区分只筛一项与筛两项。

OpenAPI 可空值迁移处理的是值类型与缺失状态，本题处理的是这些值怎样穿过查询字符串。本文没有执行 SDK、网关或服务端验证。下一次审接口时，把原始 URL 与解析后的数组并排放在参数声明旁边，才能知道“支持数组”究竟在哪一层成立。
