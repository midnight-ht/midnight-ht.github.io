在 Python JSON 变成字典前拒绝重复成员

用 Python object_pairs_hook 在转字典前拒绝同名成员，区分 RFC 唯一性建议、嵌套作用域和转义后名称等价。

正文

核心要点

  • RFC建议对象名唯一，解析成功不保证接收方解释一致。
  • object_pairs_hook能在普通字典覆盖成员前执行拒重复政策。
  • 唯一性按对象检查，转义后相同名称仍需识别。

object_pairs_hook 能拿到每个对象的成员对。利用这一步拒绝重复，才能避免字典覆盖后再也看不到原来的冲突。对于要求接收结果一致的 Python JSON 接口，应先明确重复成员名政策，再在转成普通字典以前执行它。

例如原始载荷把 amount 写了两次，第一次是一，第二次是九。默认 Python 解析可能只留下九，另一个接收方却可能拒绝或保留所有成员对。成功解析只证明某个实现接受了输入，没有证明链路上的各方使用相同金额。这不是数字太长导致精度损失，而是同一对象里出现了多个同名成员。

规范建议唯一，不代表所有解析器都报错

RFC 八二五九第四节规定，对象中的名称 SHOULD 唯一，并解释重复名称带来的互操作问题：实现可能只报告最后一对，也可能报错，或者暴露全部成员对。不能把 SHOULD 改说成所有解析器都 MUST 拒绝，也不能反过来从某个解析器接受推出输入在所有软件里解释一致。

接口可以主动选择更窄的接收政策，例如拒绝任一对象内部的重复名称。这个政策要写进合同和错误处理，而不是等框架偶然决定保留哪一个。若业务真的需要同一类字段出现多次，更清楚的表达通常是数组中的独立条目，而不是让对象映射承担多个相同键。

RFC 8259 第四节支持的是规范与互操作判断。Python json 文档则具体说明默认重复名称采用最后值，以及 object_pairs_hook 的扩展接口。核对时该页标明三点十四点十版本文档；本地示例若使用其他 Python，应另外记录实际运行版本。

默认字典已经丢掉了什么

对原始文本 {"amount":1,"amount":9}，默认 json.loads 生成的字典只含一个 amount。此后遍历字典、比较键数，已经找不到被覆盖的第一项。重新序列化再解析，也只是把已经选定的单一映射重写一次，不会恢复原来存在过的冲突。

因此检查时点必须早于普通映射吞掉重复信息。Python 的 object_hook 收到的是解码后的字典，用它检查同名成员太晚。object_pairs_hook 收到每个解码对象的有序成员对列表，可以在构造返回字典之前逐对检测；同时指定两个钩子时，成员对钩子优先。

有序列表在这里承担的是保存所有输入成员的作用，不是承诺 JSON 对象的业务顺序。站内的Object.entries 键顺序讨论另一件事：映射建立后怎样枚举。改变枚举方式，不能把建立映射时已经覆盖的成员带回来。

完整拒重复函数与边界输入

下面只用 Python 标准库，直接检查原始 JSON 文本。每次回调建立自己的字典，不共享全局 seen 集合，因而不会把两个不同对象里的同名字段误判为重复。错误消息只包含成员名；生产环境仍应按字段敏感性决定是否记录它，不要默认把整份载荷写入日志。

import json

def unique_object(pairs):
    out = {}
    for key, value in pairs:
        if key in out:
            raise ValueError('duplicate JSON member: ' + key)
        out[key] = value
    return out

samples = [
    '{"amount":1,"amount":9}',
    '{"outer":{"x":1,"x":2}}',
    '{"a":{"x":1},"b":{"x":2}}',
]
for raw in samples:
    print('default', json.loads(raw))
    try:
        print('checked', json.loads(raw, object_pairs_hook=unique_object))
    except ValueError as exc:
        print(type(exc).__name__, str(exc))

第一份输入默认留下后面的金额，自定义钩子则应拒绝。第二份输入在嵌套对象内部重复 x，也应拒绝，不能只检查最外层。第三份输入里 a 和 b 各自有一个 x，属于两个独立对象，应该通过。正样本必须保留，否则一个见到任何重名都报错的全局检测器也可能蒙混过关。

这个函数返回普通字典，后续业务仍可按常规方式读取；没有重复时，它没有替应用增加别的字段校验。amount 是否是数值、是否为正、是否在允许范围，以及当前调用方能否修改它，都不由名称检测决定。语法解码错误也要与主动拒重复的错误分类，避免客户端看见一律“服务器失败”而无法修正输入。

检查应放在信息仍存在的入口

若网关已经把输入解析为字典，再向内部服务发送重新序列化 JSON，后面的服务就看不到被覆盖项。把检测函数只加在最后一层，不能宣布整条链路已经统一解释。需要找出最早解析正文的边界，让它执行约定的政策，或把原文安全地交给负责校验的一层。

验签流程也需要保留自己的顺序。某些供应方要求验证原始字节，不能为了检测重复就先改写正文；先后如何安排应依适用协议设计。站内Webhook 原始正文讨论具体来源的验签要求，本篇没有发送回调，也不把名称检测当成来源认证。

此外，拒绝重复不限制输入体积或嵌套成本。生产入口还需合适的资源限制与超限错误，这属于另一项验收。不要把短小的回调函数称作完整安全解析器；它只实现明示的同名成员政策，不能为任意不可信载荷担保。

转义拼写不同，也算重复名称吗？

如果解码后的字符串相同，就算同一个名字。原始 JSON {"a":1,"\u0061":2} 中，两种拼写最终都表示 a；比较尚未转换的转义字符，可能错误地把它们当成两个字段。RFC 八二五九第八点三节强调名称比较应考虑解码后的字符串表示。

这个新增用例应保留 JSON 层的反斜杠，例如 Python 使用原始字符串 r'{"a":1,"\u0061":2}'，再交给上面的钩子。预期是拒绝重复 a；若宿主字符串已经提前处理转义，虽然也可能触发重复，但没有真正覆盖要测试的 JSON 表示层条件。应保存实际送入解析器的原文和结果，而非只看源码截图。

拟议接入验收还要让基本重复、嵌套重复、跨对象同名通过、转义等价重复四类输入穿过真实网关和框架。局部函数的运行只能证明相应标准库调用与输入，不证明上游仍保留原文，也不证明业务字段验证完成。先确认拒绝发生在信息丢失之前，再让错误响应对应明确的输入政策。

本文函数已在 Python 三点十一点十五运行：基础重复和嵌套重复均抛出主动拒绝异常，两个独立对象同名通过；追问的原始转义输入也被拒绝。运行版本与所查三点十四文档不同，记录保留实际输入和输出，不冒充网关或业务接口已验收。
