revisionHistoryLimit 已是零，为什么旧 ReplicaSet 还在？

先核对 Deployment 本轮完成状态，再解释零历史保留与旧 ReplicaSet 的关系；集群演练待执行。

正文

核心要点

  • 零不意味着立即删除旧对象。
  • 按 UID 与当前代次检查发布状态。
  • 模板变化与扩缩副本需分别理解。

revisionHistoryLimit: 0 不表示旧 ReplicaSet 会立即消失。Deployment 要完成以后才开始清理旧历史；一次滚动发布还没完成，尤其是新副本无法就绪时，不能只拿零这个配置值判定旧对象本应被删。官方清理策略明确说明了这个时点。

例如运维把历史保留设成零，发布新镜像后仍看到旧 ReplicaSet，便怀疑控制器没有读取配置。先看这轮 Deployment 是否完成：旧副本可能还在支撑服务，新模板对应的副本却没有可用。此时旧对象留下，与“完成后不保留历史”并不矛盾。

用一次未完成发布检查推断

下面给出隔离集群的复验输入，本文没有连接 Kubernetes 集群，也没有执行 kubectl。对象列表、拉取失败、完成和清理均是待观察的预期，不是本地实测结果。运行需要能创建命名空间的隔离上下文、可用控制器与镜像获取条件；不要把例子直接指向生产。

将以下内容保存为 deployment.yaml。它有两个副本、零历史保留，并用 HTTP 就绪探测检查教学容器。镜像标签是例子的输入，复验前应确认它在目标环境能取得；这里没有证明任何业务镜像可用，也没有提供不可变镜像身份保证。

apiVersion: apps/v1
kind: Deployment
metadata:
  name: zy21-history
spec:
  replicas: 2
  revisionHistoryLimit: 0
  selector:
    matchLabels:
      app: zy21-history
  template:
    metadata:
      labels:
        app: zy21-history
    spec:
      containers:
        - name: web
          image: nginx:1.28.0
          readinessProbe:
            httpGet:
              path: /
              port: 80

保存下面的脚本。先替换 context 占位值，保持命名空间专用于本次演练，且不存在同名旧命名空间。首次创建失败就停止，别忽略错误继续操作。脚本先等初始发布，再改为用于制造失败的镜像地址，保留当前对象与事件；恢复时原子修改模板中的镜像和注解，使恢复模板有明确身份。

set -eu
context=REPLACE_WITH_ISOLATED_CONTEXT
namespace=zy21-history-lab
k() { kubectl --context "$context" --namespace "$namespace" "$@"; }
k create namespace "$namespace"
k apply -f deployment.yaml
k rollout status deployment/zy21-history --timeout=120s
k get deployment zy21-history -o json > initial-deployment.json
k get replicasets -o json > initial-replicasets.json
k set image deployment/zy21-history web=example.invalid/zy21-history:unavailable
status=0
k rollout status deployment/zy21-history --timeout=30s || status=$?
printf 'bad-rollout-status=%s\n' "$status"
k get deployment zy21-history -o json > blocked-deployment.json
k get replicasets -o json > blocked-replicasets.json
k describe deployment zy21-history
k get pods -o wide
k get events --sort-by=.metadata.creationTimestamp
k patch deployment zy21-history --type=merge -p '{"spec":{"template":{"metadata":{"annotations":{"zy21-recovery":"v2"}},"spec":{"containers":[{"name":"web","image":"nginx:1.28.0"}]}}}}'
k rollout status deployment/zy21-history --timeout=120s
k get deployment zy21-history -o json > recovered-deployment.json
k get replicasets -o json > recovered-replicasets.json

不可用地址用于让新 Pod 无法取得镜像，但检查时仍要读 Pod 与事件，确认本次实际阻塞原因。rollout 命令非零也可能由连接、权限或其他问题引起，不能仅凭退出值说已经证实拉取失败。若初始镜像也无法取得，就没有形成“先完成再阻塞”的前提，应先修环境并重新记录，而不是把两次失败混成预期对照。

看自己的对象，而不是数同名字符串

将下列脚本保存为 inspect.py，分别执行 python3 inspect.py initial、python3 inspect.py blocked 和 python3 inspect.py recovered。它通过 Deployment UID 与控制器 ownerReference 过滤 ReplicaSet，输出代次、状态与各对象记录，避免将命名空间里无关工作负载也计入历史数量。

import json
import sys

prefix = sys.argv[1]
with open(prefix + "-deployment.json") as stream:
    deployment = json.load(stream)
with open(prefix + "-replicasets.json") as stream:
    replicasets = json.load(stream)
uid = deployment["metadata"]["uid"]
print("deployment", uid, deployment["metadata"]["generation"],
      deployment.get("status", {}))
for item in replicasets["items"]:
    if any(owner.get("uid") == uid and owner.get("controller") is True
           for owner in item["metadata"].get("ownerReferences", [])):
        print(item["metadata"]["name"],
              item["metadata"].get("annotations", {}),
              item["spec"].get("replicas"), item.get("status", {}))

阻塞阶段预期新模板尚未形成完整可用副本，而旧 ReplicaSet 仍存在并可能承担副本。这个状态应由对象快照证明，不能预先把固定数量写成必然结果。控制器推进、额外尝试或已有环境差异都会影响观察到的数量；本例更关注对象归属、模板身份和发布是否完成。

恢复以后，先核对控制器已观察到当前代次，再看全部副本是否更新到目标模板、可用，以及旧模板是否不再运行副本。rollout status 是一个方便入口，归档的 Deployment 状态与 ReplicaSet 快照能让同事重建判断。不要拿旧代次的完成记录替代当前发布完成，也不要把单个 Pod Running 当作整个 Deployment 已完成。

完成后再观察旧对象清理。清理由控制器异步推进，本文不承诺某个精确秒数内只剩一个对象。若恢复快照仍含旧对象，可在保留时间戳的情况下重新读取，并核对同一个 UID 与当前代次。没有实际集群回执时，只能写“等待验证”，不能从 YAML 语法正确推导出清理已经发生。

零历史保留也有交付代价

官方说明设置为零会清掉历史，因此无法依靠这些旧历史回滚；这不等于根本不创建新 ReplicaSet。新模板仍需要对应的新对象推进发布，清理发生在完成之后。把保留数设为零，不能替代发布状态检查，也不能用它修复卡住的新模板。

要采用这个策略，先确认团队的恢复方式。若依赖回到旧模板，应将它所需的输入、镜像身份和配置来源固定，别假设控制器必定保有旧对象。本文只讨论历史清理时点，没有执行任何恢复到真实业务版本的演练。教学脚本中的恢复只是换回可用示例镜像并产生一个带注解的新模板。

清理演练环境前先保存三阶段对象、事件和命令结果，再确认该命名空间仅含本次资源。随后可使用同一明确 context 删除该专用命名空间。保留原始失败事件比只留最后一次绿色 rollout 更有助于说明为何旧历史曾存在。跨命名空间、换 context 或重新创建同名 Deployment 后，必须重新关联 UID，不能拼接成一条连续发布证据。

多人交接时，截图中的一个总数尤其容易丢掉前提。接手者需要看到取样时使用的上下文、命名空间、对象身份、模板内容和状态，而不只是“还有两个旧对象”。将配置输入与三阶段快照放在同一记录，明确哪些是命令直接读数、哪些是基于读数作出的判断；没有取到的数据留空，并说明中断原因。不要为了补齐时间线而用另一次演练的对象替代。

人工处置也应另作决定。发现旧对象仍在时，先读当前副本承载与控制器状态，不要立即按保留数删除它。本文的复验只读取对象和改变专用教学模板，没有给出清理生产历史的授权。若团队最终需要手工处理，应先核对当时的依赖和恢复输入，并重新保存处理前后证据，让“等待控制器完成”与“人为改变对象”两条路径可以区分。

如果只调整副本数，会增加一个修订吗？

不会仅因扩缩副本就创建新修订。官方说明，修订由 Pod 模板变化触发，单纯调整副本数不是模板变化。这是与主例不同的新条件：主例改变了镜像和注解，而扩缩容只改变期望数量。复验时可保持模板不变，单独调整 replicas，再对照修订注解与对象身份；本文未运行这个分支，也不把代次变化自动等同于新增修订。
