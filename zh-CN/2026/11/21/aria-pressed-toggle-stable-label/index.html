aria-pressed 变了，静音按钮为什么还叫 Mute？

用稳定Mute名称对照按下态与教学静音状态，说明另一命令标签方案，并限定mixed的新条件。

正文

核心要点

  • 稳定名称方案保持功能标签
  • pressed声明需与功能状态一致
  • 名称和状态应按同一设计合同验收

静音已经开启，按钮仍叫 Mute，可以是一份清楚的两态按钮设计。按 APG 的稳定标签方案，功能名称保持不变，aria-pressed 表达是否启用了该功能。若只因为状态变成真就把名称改成 Unmute，同时继续按同一两态合同解释它，名称与状态可能不再传达原来的意思。

固定名称与当前状态各有职责

W3C 的 Button Pattern 用静音作例子，说明带 aria-pressed 的两态按钮在状态变化时保持标签。Mute 是这个可切换功能的名字，pressed 为真表示当前启用静音，为假表示未启用。它不是用按钮下一次要做什么，替换当前按下状态的含义。

这种组合让同一个控件持续承担相同功能。用户再次找到 Mute，可以读取它的当前状态，再决定是否切换。视觉上也可以另有明确状态提示，但不能只靠某种颜色去解释布尔值。本文不提供某个读屏软件必然怎样逐字播报的承诺。

APG 也描述另一种设计：如果动作文字要在 Mute 与 Unmute 之间变化，就不需要用 aria-pressed 表达这份两态语义。选择哪种方案应保持名称、角色和行为一致。这里不是要求所有会改变内容的按钮都加同一个属性，而是把稳定名称的两态方案作为主例。

aria-pressed 本身也不会让应用静音。属性声明需要与真正负责功能的状态一致。开发者只把它写成 true，但声音来源没有改变，语义声明再规范也没有完成任务。相反，功能已经切换而属性仍是 false，同样会让控件对当前状态作出错误描述。

一个布尔值驱动两份教学输出

下面是完整页面，原生按钮的文字固定为 Mute。点击会切换本地的 muted，再同时渲染 pressed 和旁边的教学状态文本。页面不加载、不播放任何音频，因此这里的布尔值不是已经控制真实媒体设备的证据。

<!doctype html>
<meta charset="utf-8">
<title>Stable toggle label</title>
<button id="mute" type="button" aria-pressed="false">Mute</button>
<p id="state">Teaching muted state: false</p>
<script>
const button = document.getElementById('mute');
const output = document.getElementById('state');
let muted = false;
function render() {
  button.setAttribute('aria-pressed', String(muted));
  output.textContent = 'Teaching muted state: ' + muted;
}
button.onclick = () => {
  muted = !muted;
  render();
};
</script>

独立预期为初始名称 Mute、pressed 为 false、muted 为 false。激活一次后名称仍为 Mute，两份状态都为 true。再激活，名称不变，状态都回到 false。按同样动作重复第二轮，检查重新开启与关闭都仍走统一渲染入口。

这是按模式和代码推导的预期，没有运行浏览器或辅助技术。产品验收应通过所支持的输入方式到达并激活按钮，记录名称、状态和功能结果。真实音频还需读取实际媒体或业务状态，不能把这段教学文字出现 true 记成声音已经静音。

一个有用的负例是只更新 pressed，保留 muted 原值。此时两份读数就会不一致。另一个负例是功能切换了，但按钮被重新渲染成没有 pressed 的普通按钮。只检查点击回调执行过，会漏掉这些面向用户的结果；读数需要紧跟每次动作。

键盘检查也要走实际入口。APG列出按钮获焦时由空格或回车激活，可以分别从关闭状态开始，确认一次激活只切换一次。若另加自定义按键监听，又让浏览器原生激活继续发生，可能把状态连续翻转后回到原值。当前页面没有重造按键处理；真实组件若有这类封装，要记录每次激活的状态变化，不能只看最后一份布尔值。

审查名称时，先确定采用哪一种合同

若产品已经选择稳定标签，测试不应要求启用后必须出现 Unmute。它应该要求名称持续指向同一功能，再核对当前是否按下。把两种方案的预期混进同一条用例，会让正确实现也被判错，或让不一致组合恰好通过。

还要检查实际可访问名称来自哪里。按钮内文字可能是 Mute，另一个 aria-label 却仍写着旧动作。只截取可见文字不足以知道使用者拿到哪份名称。页面应尽量减少互相竞争的命名来源，必要时在目标环境读取实际名称，再核对它与视觉内容是否对应。

如果异步设备操作可能失败，应用还需要定义状态什么时候成为真。不能只在发送请求时翻转声明，随后失败却让按钮继续声称已经静音。可以按明确状态流程处理等待、成功与失败，并核对恢复后的值。本文的本地布尔切换没有实现这一设备流程，不能替它提供验收结果。

重建组件也需要保留本次对象归属。切换媒体源后，原来的 muted 值不一定还属于新对象。按钮即使保留同一个DOM编号，也需要绑定当前媒体与当前状态。稳定名称解决的是功能识别，不会替应用追踪对象切换或异步返回的先后。

对于设置变化是否还引发跳转或焦点移动，可以对照 输入变化与上下文。那篇讨论额外后果是否需要预告，本题核对控件名称和按下态本身。两类检查都应对着真实动作，不从一个正确属性推出整个交互已经合规。

同时控制多条对象，有开有关，可以用 mixed 吗？

这里新增受控对象集合。比如一个加粗按钮控制当前选中的多段文字，其中一部分已经加粗，另一部分没有。WAI-ARIA 对 aria-pressed 的 mixed 值描述这种受控项状态不一致的情况，它不同于主例单个静音布尔值。

先列清哪些对象由按钮共同控制，再根据它们当前的状态决定是否混合。不要把 mixed 当作还没加载、请求中或不知道状态的临时词。用户激活之后是统一开启还是统一关闭，应由组件的任务规则另外明确，mixed 这个声明没有替产品选择后续动作。
