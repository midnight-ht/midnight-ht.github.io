Git 说文件是 LF，编辑器为什么仍看到 CRLF？

分别读取 Git 索引和磁盘字节，对照换行报告的内容列与属性列，定位真实交付输入。

正文

核心要点

  • 索引、工作树和属性各有一列。
  • 策略声明不能替代实际字节读取。
  • 按消费者的输入选择修复与验证。

Git 报告文件是 LF，工作区里却仍可能有 CRLF。用 git ls-files --eol 时，先分清 i/、w/ 和 attr/ 三列。它们分别记录索引内容、工作树内容与转换属性。只读其中一列，就可能把准备提交的字节与编辑器打开的字节混在一起。

例如一个文件已经暂存，编辑器随后把本地版本保存成另一种换行。维护者在终端看到 LF，就告诉打包人员无需处理。但构建脚本读取的是工作树文件，拿到的仍然是另一份字节。要说明究竟哪一份需要修，先让同一个路径的两种内容都可见，再讨论项目的换行策略。

同一路径，独立读取两份字节

以下脚本创建一次性仓库，关闭自动换行配置。先以 LF 写入并暂存，再只把工作树改成 CRLF。没有再次 add，所以索引维持最初内容。Python 从 Git 的索引读取一份、从磁盘直接读取一份，用明确字节序列断言这两个对象。最后再加属性文件，观察策略列的变化。

set -eu
work=$(mktemp -d)
trap 'rm -r "$work"' EXIT
cd "$work"
git init -q
git config core.autocrlf false
git version
printf 'alpha\nbeta\n' > sample.txt
git add sample.txt
printf 'alpha\r\nbeta\r\n' > sample.txt
git ls-files --eol -- sample.txt
python3 - <<'PY'
from pathlib import Path
import subprocess

index = subprocess.check_output(["git", "show", ":sample.txt"])
working = Path("sample.txt").read_bytes()
assert index == b"alpha\nbeta\n"
assert working == b"alpha\r\nbeta\r\n"
print("index", repr(index), "working", repr(working))
PY
printf 'sample.txt text eol=lf\n' > .gitattributes
git ls-files --eol -- sample.txt

本地 Apple Git 2.50.1 上，第一份输出是 i/lf、w/crlf，属性列为空。字节检查同时确认索引中只有换行符，磁盘中每行是回车加换行。添加 text eol=lf 后，报告仍然是 i/lf、w/crlf，只是 attr/ 后面显示新策略。整份脚本退出零。这个控制说明，在这里仅编辑属性文件，没有把已经存在的两份字节一起改成新的格式。Git ls-files 的换行列定义

索引列回答准备进入相应快照的内容，工作树列回答当前路径上的内容。属性列则表示提交或检出时使用的转换策略。把属性读成已经完成的转换回执，会在这次样例中得到错误结论。反过来，看到磁盘 CRLF 也不能说索引一定保存了它，独立字节读取已经给出相反证据。

让修复针对真正使用的输入

先查出消费者取哪一份内容。若任务打包工作树文件，应核对那份磁盘内容和本轮输入身份。若任务从固定提交导出，应再检查该提交中的实际字节。索引不是所有发布方式的共同输入，所以不能把这里暂存的 LF 自动沿用成任何制品都合格。修改哪一份，应由实际交付入口决定。

对需要统一换行的项目，先固定策略，再选择符合当前任务的转换操作。不要在多人有未提交改动的目录里，看到属性写成 LF 就直接宣布全体文件已归一化。应保留原改动与输入范围，在受控样例先确认暂存、检出或专用转换步骤分别产生什么，再把预期写进检查。本文没有执行批量重新暂存或覆盖工作区文件。

例如团队准备让下一次提交改用 LF，可以先审阅属性变更，再明确哪些文件需要作为归一化修改进入提交。得到新的索引内容后，读回字节和差异，确认没有把无关业务编辑一起加入。工作区还有其他修改时，暂存结果和本地文件仍可能不同。换行修复不是忽略暂存范围的理由。

也有项目有意让索引统一使用 LF，而某类开发环境检出 CRLF。此时两列不同可以符合策略。验收需要确认转换发生在合适的边界，消费者能处理实际读取的内容。不能单凭两列不相等就让任务失败，也不能仅凭某一列符合偏好就放行。先把哪种差异允许、哪种输入必须固定写清楚。

报告要能关联到本轮文件

保存换行报告时，可以同时记录提交或索引状态、路径与工作文件内容摘要。别人稍后打开相同文件名，可能已经是编辑器又保存过的版本。把新的报告贴到旧构建回执，会误以为制品用过这份内容。需要固定构建输入时，可以比较交付快照中的实际文件，再用换行列帮助解释来源。

某些消费者只认特定行分隔，另外一些会在解析时接受多种形式。二者都需要真实行为测试。上面的字节断言没有调用应用解析器，也不能证明脚本在其他操作系统上能够启动。若发布要求是可执行脚本能被目标环境读取，可以另留一份受控执行或解析回执，绑定同一文件版本，避免把文件格式分类当成业务验证。

工具输出也需要按字段解释。Git 的内容分类还可能包含非文本、没有行终止符或无法访问等状态。遇到空字段时先查路径在索引与工作树中是否可读，而不直接补成 LF。当前样例固定为普通、可读的文本文件，没有覆盖符号链接、稀疏索引或二进制分类。

如果两台机器同一策略下给出的报告不同，先核对它们是否真正比较同一提交与同一文件内容，再查本地转换配置。两处磁盘字节本来就不同，单凭策略相同不能要求 w/ 相同。保留三列和对应内容，会让差异能归到输入、转换条件或观察时间，而不是只得到“某台机器换行坏了”。

同一个文件里同时有 LF 与 CRLF，会显示什么？

Git 的内容分类包含 mixed。可以另做一个文件，一行只含换行符，另一行含回车加换行，分别检查索引和工作树哪一份混合。这个问答加入的是单份内容内部的混合，主例的每份内容都各自一致。本文没有运行 mixed 分支，也不把 mixed 当作所有应用都会拒绝的格式。需要按字节定位具体行，再对目标消费者验证。
