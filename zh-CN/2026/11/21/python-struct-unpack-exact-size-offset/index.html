头字段只有两字节，unpack 为什么拒绝更大的完整帧？

比较固定二字节头的精确缓冲和偏移读取，检查短头、载荷边界与固定记录余数。

正文

核心要点

  • unpack 要求缓冲区恰好匹配格式尺寸。
  • unpack_from 从偏移处要求足够字节。
  • 完整帧和固定记录尾部需要额外验证。

完整帧的开头明明有两字节头字段，struct.unpack 却因为后面还带着载荷而报大小不符。unpack 要求整个缓冲区恰好符合格式尺寸。若要从较大的缓冲区指定位置读字段，可以使用 unpack_from，并另外核对头字段与载荷边界。

两字节足够，不代表整份输入必须只有两字节

假设本地教学帧先放一个标记 X，再放两字节长度，最后是 abc 三个载荷字节。格式 !H 表示按网络字节序处理无符号短整数，长度字段固定两字节，不采用本机默认对齐。长度三从索引一开始，载荷从索引三开始。这个明确布局使测试不必猜测解释器运行在哪种机器上。

unpack 面对的是一份完整的格式输入。调用者给它一整个帧，它看到的大小超过两个字节，因此拒绝；这并不意味着长度三无法表示。先切出头字段再调用 unpack，就能满足恰好两字节的条件。另一条路径是让 unpack_from 从偏移一开始读取，只要求从该处往后有足够字节，允许后面继续存在载荷。

这种宽松只针对供字段读取的缓冲范围。它没有证明标记正确、长度合理或声明的载荷真的全部存在。解析器得到一个整数以后，还要检查格式允许的范围和后续数据量。若只看字段读取成功就把整帧当成合法，可能把截断消息交给业务模块。应在接口里给这几个结果分别留出位置。

对照整帧、头切片和偏移读取

下面的夹具构造完整固定字节，分别走两种成功读取和两个尺寸错误路径。它只在内存中工作，没有读取套接字，也没有接受外部消息。最后的固定记录迭代用于后面的新条件。

from struct import Struct, error, iter_unpack

header = Struct("!H")
pack = header.pack
decode = header.unpack
decode_from = header.unpack_from
assert header.size == 2
frame = b"X" + pack(3) + b"abc"
try:
    decode(frame)
except error:
    pass
else:
    raise AssertionError("unpack must reject an oversized buffer")
assert decode(frame[1:3]) == (3,)
assert decode_from(frame, 1) == (3,)
assert frame[3:] == b"abc"
try:
    decode_from(b"X\x00", 1)
except error:
    pass
else:
    raise AssertionError("only one header byte remains")
assert list(iter_unpack("!H", pack(3) + pack(4))) == [(3,), (4,)]
try:
    list(iter_unpack("!H", pack(3) + b"X"))
except error:
    pass
else:
    raise AssertionError("fixed records require a size multiple")
print("exact buffer and offset controls passed; incomplete headers/records rejected")

整帧调用 decode 预期进入 struct.error 分支。头切片与偏移读取都得到单项元组三，载荷切片必须恰好为 abc。单个字段仍返回元组，调用者如果直接拿它与整数比较，会误判业务值。夹具明确写出括号和逗号，保存真实返回形状。

负例在偏移一后只剩一个头字节，必须报错。它能阻止把“缓冲区总共有两个字节”误当作偏移之后也有两个字节。正例又保留后面的 abc，确认 unpack_from 没有继承整个输入必须恰好两字节的限制。两个控制共同锁住真正的尺寸条件，而不是只证明某份输入碰巧读对。

这些断言没有执行网络分帧。实际服务可能一次收到半个头，也可能一个缓冲区里有多帧；读取层要先定义何时等更多字节，何时认定输入已经结束。把当前缓存短当作最终错误，和收到终止输入后确实截断，可能对应不同处理。这里的短样本只是给定完整缓冲区时的库调用失败。

把字段尺寸与消息完整性分别验证

应用可在得到长度后，计算这份协议的载荷起点与结束位置，再比较实际可用量。对当前布局，头结束在三，声明长度三，预期消息结束在六。若缓冲区只有五字节，头仍能正确读成三，载荷却缺一个字节。若多出后续字节，应按协议决定它们属于下一帧、允许的尾部还是错误，不能由 unpack_from 自动替你选择。

验收应从独立的完整字节开始，给正常帧、头短一字节、载荷短一字节和相邻两帧各一项预期。检查的不只是返回整数，还包括实际消费了多少字节、剩余哪一段、错误被交给谁。若读取代码只返回一个长度值，下游就无法区分它是否已确认整帧完整。这个输入表是应用验收设计，主夹具没有模拟连续网络读取。

格式串也属于接口合同。若一处写 !H，另一处用默认本机格式，字节序或填充解释可能不一致。应在协议定义与代码中保存同一份明确格式，再从其他实现生成的固定样本交叉检查。当前例子只验证 Python 的明确格式，没有声称兼容某个外部设备，也没有把一个平台上的尺寸测量推广到所有本机格式。

本站的连续 gzip 成员讨论另一种边界：解压器可以处理多成员，但还原字节之后的业务记录仍需另验。这里没有压缩层，关注固定头字段怎样从更大的缓冲区取得。正确拆出头同样只是下一层验证的输入，不能作为业务对象已经可用的回执。

本例所有偏移都是明确的非负常数，未覆盖从缓冲区末尾计数的负偏移。若公开接口允许调用者选择偏移，应把越界、负值及边界位置也列入自己的输入合同，再确认失败如何返回。

调试时保留偏移值尤其有帮助。头字段从一开始，若维护者忘掉前面的标记，改成从零读取，可能仍得到一个合法范围内的整数。只检查没有异常会漏掉这一位错位。可以让标记、长度和载荷使用明显不同的字节，并核对完整预期；不要用全零缓冲区检测偏移，许多错读都会一样得到零。

iter_unpack 会忽略最后不足一条记录的字节吗？

它要求缓冲区长度是记录尺寸的整数倍。夹具用两个 !H 字段得到三和四两个元组，再在一个完整字段后多加 X，预期报错。它不会把最后一个字节默默丢掉。这个新条件针对等长记录的整体迭代，与允许较大载荷存在的 unpack_from 不同。若协议确实允许单独尾部，就先验证尾部合同，再把完整记录区传给迭代接口，避免通过截掉余数让坏输入表面成功。
