validate_only 返回成功，为什么资源还没变？

用相同成功回应和不同存储状态区分预览与执行，保留权限检查、请求标志和后续读取证据。

正文

核心要点

  • 预览成功不表示变更已经应用
  • 预览仍需正式请求的检查
  • 请求模式与读取结果要共同保存

请求带着 validate_only，返回成功和评分四的预览，重新读取资源却仍是评分一。这可以符合预览合同。采用 AIP-163 的端点可以验证请求而不实际执行变更，成功响应描述预期结果。调用方需要保留这次选择，不能只看到成功就显示「已保存」。

预览保留验证，执行另有入口

Google AIP-163 的 Change validation 说明，接口可以提供只验证、不执行请求的选项，并返回正式执行会提供的响应。约定的请求字段是布尔型 validate_only。是否采用这种能力应看具体端点文档，不能仅凭参数名字为任意服务补出相同保证。

这份选项也不等于跳过正式检查。指导明确要求执行正式请求会做的权限检查与其他验证，若判断正式请求会失败，验证请求也必须失败。一个没有权限的调用者不能因为只想预览，就被模型当作可以获得成功结果。

因此有两个不同问题。一个是输入和当前调用条件能否通过验证，另一个是这次调用有没有真正应用变更。预览通过可以支持用户确认将要提交的内容，却不能独自证明资源已经更新。产品文案、记录状态与后续操作都需要携带这个区别。

主例限定对已知资源评分的变更。原评分是一，期望改成四，预览回应包含同一个资源名和期望评分。这里没有创建新资源，也没有外部副作用，不把某个成功正文当作已经产生新的持久化记录。

同样回应，不同的本地状态结果

完整脚本使用内存对象表达教学存储。canWrite是本地测试条件，validateOnly对应文档中的预览选择。它不认证用户、不发HTTP，也没有连接数据库。评分范围是一到五，是这个假想接口自己的业务规则。

import { deepEqual } from 'node:assert/strict';
function review(store, canWrite, validateOnly, rating) {
  if (!canWrite) return { status: 'PERMISSION_DENIED' };
  if (!Number.isInteger(rating) || rating < 1 || rating > 5) {
    return { status: 'INVALID_ARGUMENT' };
  }
  const result = { name: 'books/B1', rating };
  if (!validateOnly) store.rating = rating;
  return { status: 'OK', result };
}
const cases = [
  [true, true], [true, false], [false, true], [false, false]
];
const actual = cases.map(([canWrite, validateOnly]) => {
  const store = { rating: 1 };
  const response = review(store, canWrite, validateOnly, 4);
  return { response, storedRating: store.rating };
});
deepEqual(actual, [
  { response: { status: 'OK', result: { name: 'books/B1', rating: 4 } }, storedRating: 1 },
  { response: { status: 'OK', result: { name: 'books/B1', rating: 4 } }, storedRating: 4 },
  { response: { status: 'PERMISSION_DENIED' }, storedRating: 1 },
  { response: { status: 'PERMISSION_DENIED' }, storedRating: 1 }
]);
console.log(JSON.stringify(actual));

原样脚本已在本地Node环境运行。前两项有权，预览与正式路径回应结构相同，评分都是四；预览存储仍是一，正式存储成为四。后两项无权，不论是否预览都拒绝，存储保持一。每项都有新的初始对象，避免上一项正式修改污染下一项验证。

运行证明的是这份本地合同的分支与状态，不是某个API已经实现了AIP。实际端点还应保存请求字段、响应和随后读取的资源版本，才能判定它在目标环境里的行为。若只有响应截图，没有当次是否预览的请求信息，就无法完整解释资源为何没变。

一个明确的负例是把成功状态统一映射为已保存。脚本第一项也会返回OK，却没有写入。UI如果把它当成正式完成，用户可能离开页面，后来才发现改动没有应用。测试应分别检查预览已准备和正式变更完成的状态，不能让它们共用同一条成功提示。

确认操作需要绑定本次预览内容

预览界面可以展示将要改变的字段，让用户核对后再进入正式请求。需要明确哪些输入属于这次预览，确认时有没有又被修改。若用户在预览后把评分四改成五，屏幕仍显示旧预览，确认动作就不该暗中代表两份不同内容。

也要记录资源和调用条件的时点。预览之后，其他人可能更新同一资源，权限也可能变化。这份预览不是未来执行结果的永久凭据。正式请求仍需按服务合同检查当时的条件，发生变化时给出能继续处理的结果。并发版本前提可对照 If-Match与编辑冲突。

端点返回预期对象时，调用方也不能把它无条件放进已持久化列表。可以将预览数据保存在明确的展示范围，与真正读取到的资源记录区分，并让用户知道下一步仍需确认。具体缓存方案由应用决定，关键是数据来源与状态含义可解释。

失败分支同样要对应真实语义。预览被权限检查拒绝，应显示当前请求无法按条件完成，而不是继续展示一个看似可提交的成功结果。修正输入后要重新预览，保留它属于哪次资源、哪组内容和哪个调用者条件，避免拿旧结果替新请求作保证。

这与在模式文件中写只读注解不同。站内 readOnly声明与服务端执行说明元数据不能替真正处理逻辑作证。本题的validate_only是一份端点选项合同，同样需要实际服务测试才能证明已经实现，不能从客户端发送过字段就宣布成立。

验证方案可在同一受控资源上先读基线，再发预览，再读资源，最后发正式请求并重新读取。对无权或错误输入，也要确认资源没有部分改变。本文没有运行这套HTTP和持久化检查，本地对象结果不能替它填写通过。

创建预览成功，为什么没有自动生成的资源ID？

这里新增创建资源的条件，主文只更新已知名字。AIP-163指出，有些正式输出不适合在验证时完整提供，例如创建时生成的ID；在这种情况下，验证回应应省略这些字段。预览成功不要求为尚未创建的资源先分配一个正式身份。

调用方应按该端点约定展示可用预览信息，并把正式创建后的身份留给实际结果。不要自行编一个临时ID，再把它当成服务已经接受的资源名。这里依据官方指导，没有执行任何创建或ID分配；缺少生成ID也不能脱离请求模式，单独判断成创建失败或创建完成。
