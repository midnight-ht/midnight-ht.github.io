测试等设备很久，真正开始后怎样另算超时？

用准备标记切换 CTest 超时，分别验证快、慢与未命中分支，并保留预检失败。

正文

核心要点

  • 命中输出后采用新的超时长度。
  • 通过不足以证明标记已匹配。
  • 单项时间与整个调用口径不同。

TIMEOUT_AFTER_MATCH 在测试输出命中正则后重置开始时间，并改用指定的超时长度。它适合测试自己才能判断资源何时可用的场景：先给等待留较长预算，再限制真正工作的阶段。匹配前仍需要总预算，不能让等待无限延伸。

例如测试等外部设备准备好，随后才执行计算。只设一个较短超时，会把等待也算进去；简单扩大整个超时，又可能让实际计算卡住太久。可以让测试在准备完成时输出一个专用标记，用它切换预算。标记必须代表真实阶段变化，不能只为延长寿命定期打印。

一份有三个分支的最小样例

在专用目录放下两个文件。这里没有真实设备，Python 的短等待只模拟准备过程。下面的工作脚本先等一小段时间，根据参数决定是否发出标记，再执行指定长度的等待。输出立即刷新，让父进程有机会及时收到阶段变化。

import sys
import time

time.sleep(0.4)
if sys.argv[1] == "emit":
    print("RESOURCE_READY", flush=True)
time.sleep(float(sys.argv[2]))
print("WORK_DONE", flush=True)

保存为 worker.py，再保存以下 CMakeLists.txt。三个用例共享初始预算，只有输出匹配的分支会切换。快分支的工作应在新预算内结束，慢分支应被新预算终止；没有标记的分支仍受原预算约束。

cmake_minimum_required(VERSION 3.20)
project(PhaseTimeout NONE)
enable_testing()
find_package(Python3 REQUIRED COMPONENTS Interpreter)
add_test(NAME fast COMMAND "${Python3_EXECUTABLE}" "${CMAKE_CURRENT_SOURCE_DIR}/worker.py" emit 0.1)
add_test(NAME slow COMMAND "${Python3_EXECUTABLE}" "${CMAKE_CURRENT_SOURCE_DIR}/worker.py" emit 2)
add_test(NAME unmatched COMMAND "${Python3_EXECUTABLE}" "${CMAKE_CURRENT_SOURCE_DIR}/worker.py" silent 2)
set_tests_properties(fast slow unmatched PROPERTIES
  TIMEOUT 6 TIMEOUT_AFTER_MATCH "1;RESOURCE_READY")

本地配置使用 CMake/CTest 4.2.3 和稳定存在的 Python 3.11 路径。以下是本机的解释器绝对路径；别把它当成其他机器也有的路径。读者应填自己的解释器位置，并确认该进程在后续运行时仍存在。

cmake -S . -B build -DPython3_EXECUTABLE=/opt/homebrew/bin/python3.11
ctest --test-dir build -V -R '^fast$'
ctest --test-dir build -V -R '^slow$'
ctest --test-dir build -V -R '^unmatched$'

实际 fast 日志先记录原超时六秒，收到准备标记后出现 Test timeout changed to 1，然后输出 WORK_DONE 并通过。slow 也记录相同切换，随后以 Timeout 结束，CTest 返回八，没有结束标记。unmatched 不输出准备标记，没有计时切换，在原预算内完成并返回零。这三份独立回执一起支持阶段切换，单看一次通过无法证明配置生效。

该属性自 CMake 3.6 提供。官方属性说明明确将匹配前预算与匹配后长度分开。这里设置的数字只是小型演练参数，并非设备或持续集成任务的推荐期限。真实任务需要按等待上界和工作上界分别决定，再测过载与超时清理行为。

先验证标记被接收，再解释结果

第一次环境准备把临时工具环境里的 Python 写进测试配置，后续工具进程结束后，该路径已不可用。CTest 报告用例未运行。这不是计时器杀死了测试，也不能记为某个行为断言失败。重新配置必须先恢复稳定的解释器，再核对日志中的实际命令位置。

另一次使用带首尾锚点的标记表达式，所跑版本没有产生预期匹配。慢分支也通过了，日志没有计时切换。纠正为样例中的专用词后，才观察到慢分支超时。保留这个失败有实际意义：通过可能只是仍在较宽的总预算内，不能仅凭配置文件里出现属性名，就宣称阶段限制已经生效。

如果应用把输出缓存在自身进程里，准备完成与 CTest 收到标记可能不是同一个时刻。本例显式刷新输出。真实程序需要验证它的输出路径，包括中间包装器是否缓冲。本文没有运行缓冲包装器对照，因此不会把每种运行器的刷新行为列为已验证结果。

标记选择也应避免普通业务日志意外命中。可用一个只由准备状态转换打印的专用词，并在日志中同时保留资源准备的实际证据。若程序根本没有得到设备，却提前输出标记，新预算虽能生效，也不能证明设备已就绪。计时规则正确与阶段信号正确需要分别检查。

故障分流时可以先按证据停在对应层级。若启动命令根本不可执行，先修运行环境，不调时间；若程序结束但没有切换日志，先核对实际输出与匹配规则；若已经切换且被新预算终止，再调查活动阶段为何超时。三个分支的处理对象不同，盲目把新预算扩大可能掩盖原本需要解决的准备信号错误。每次调整都应重新保存负对照，让同事能判断是修了匹配还是放松了限制。

由谁负责等待，决定是否选择这个属性

如果所需资源能由 CTest 控制，官方建议用 RESOURCE_LOCK。输出触发的计时转换适用于只有被测程序知道资源何时可用的情况。不要用打印标记替代本来可以由调度器管理的互斥，也别把超时预算误当成资源隔离保证。

对一个真实设备测试，可以先写清楚准备成功需要哪些检查，再在这些检查完成之后发出标记。验证记录至少保留启动命令、准备标记、切换日志、结束状态，以及慢分支未能正常结束的证据。若只保存汇总通过率，日后无法分辨设备等待、启动失败和实际工作超时。

超时之后的设备复位与子进程清理也不由这份小样例覆盖。这里的工作只有 Python 等待，没有外部设备状态。读者把它接到真实任务时，应另设清理检查，确认下一次测试的初始条件恢复。不能将本例的进程超时直接外推为设备已安全释放。

为什么单个测试的时长比整次调用短？

匹配会重置测试开始时间，官方说明因此报告的执行时长不含匹配前等待。本地 fast 显示约零点一一秒，而该次 CTest 总时间约零点五五秒，与脚本先等待再发标记的结构一致。这是报告口径的新条件，不能用较短的单项数字反推机器没有等待。两种时间都保留，性能核算时明确自己需要阶段耗时还是整个调用耗时；这些观测值不构成毫秒精度保证。
