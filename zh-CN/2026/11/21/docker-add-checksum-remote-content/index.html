远程文件下载成功，Docker 怎样确认内容还是预期那份？

固定批准摘要，用正确与一位错误值构建，再读回导出文件；下载成功之外还需内容身份检查。

正文

核心要点

  • 预期摘要应在构建前固定。
  • 负对照需确认具体摘要拒绝。
  • 导出字节一致不等于应用已验证。

对 HTTP 来源使用 ADD --checksum=sha256:…，Docker 会检查下载内容是否符合给定摘要。下载成功只说明取得了响应；内容是不是已批准的那份，还需要把实际字节与事先确定的摘要关联起来。预期摘要也有来源，不能把临时下载的任意内容自动变成新基准。

例如构建要取一份公开文本作为输入。URL 固定看起来很放心，但接收端仍需要检查内容身份。可以将确认过的摘要写入构建定义，再故意改错一个字符作为负对照。两次都以同一个来源为目标，分别检查成功导出的字节和被摘要拒绝的错误，而不只数构建命令退出了几次。

固定来源、摘要与导出位置

下面的 Dockerfile 取 Open Container Initiative image-spec 的公开 README，路径中使用完整提交身份。它是无敏感信息的教学输入，不是产品配置。样例使用 scratch 并导出本地文件，不运行容器、不推送镜像，也没有发布任何服务。

FROM scratch
ADD --checksum=sha256:3e104c2dc2032ca367461f50f213adca7ef77530ed53785519065a7a674ac4d5 https://raw.githubusercontent.com/opencontainers/image-spec/147f9c13cedb47a0c4d9a11a222961073d585877/README.md /payload/input.txt

保存为 Dockerfile。摘要是本文冻结输入时确认的 SHA-256，不能因为未来构建不通过就直接替换为当时下载的新值。HTTP 来源的 checksum 需要支持该选项的 Dockerfile 前端；当前参考文档的版本表将该 HTTP 选项列为自一点六支持。实际是否被构建器接受，仍要看本次日志和负对照。

另存 wrong.Dockerfile，仅把摘要开头的三改成零，其余来源和目标保持一致。这是特意设置的错误输入，不能当成另一份合法内容身份。

FROM scratch
ADD --checksum=sha256:0e104c2dc2032ca367461f50f213adca7ef77530ed53785519065a7a674ac4d5 https://raw.githubusercontent.com/opencontainers/image-spec/147f9c13cedb47a0c4d9a11a222961073d585877/README.md /payload/input.txt

把已冻结的公开文本快照保存为 input.md，与两个文件放在同一目录。快照用于额外比较，不负责动态生成摘要。以下脚本需要 Docker 构建器、shasum、cmp 和 rg；它创建独立的上下文与输出位置，核对正确导出文件，并检查错误构建的具体拒绝原因。

set -eu
work=$(mktemp -d)
mkdir "$work/good" "$work/wrong"
cp Dockerfile "$work/good/Dockerfile"
cp wrong.Dockerfile "$work/wrong/Dockerfile"
docker version --format '{{.Client.Version}} / {{.Server.Version}}'
docker buildx version
docker buildx build --progress=plain --output "type=local,dest=$work/out" "$work/good"
file="$work/out/payload/input.txt"
printf '%s  %s\n' 3e104c2dc2032ca367461f50f213adca7ef77530ed53785519065a7a674ac4d5 "$file" | shasum -a 256 -c -
cmp input.md "$file"
status=0
docker buildx build --progress=plain --output "type=local,dest=$work/rejected" "$work/wrong" > "$work/wrong.stdout" 2> "$work/wrong.stderr" || status=$?
test "$status" -ne 0
rg 'digest mismatch' "$work/wrong.stderr"
test ! -e "$work/rejected/payload/input.txt"
printf 'fixture=%s\nwrong-exit=%s\n' "$work" "$status"

本地实际构建中，正确摘要分支成功导出 payload/input.txt，独立 SHA-256 检查与保存的文本比较均一致。错误摘要分支返回一，诊断包含 digest mismatch，并列出实际内容摘要与错误的预期值，没有生成可接受的目标文件。负对照证明构建器确实检查了给定值，而不是只把 URL 下载进去了。

这个结果不能简化成“所有非零退出都说明摘要有问题”。网络不可达、认证失败或前端不认识选项，都可能阻止构建。验收时要保留完整错误，确认是具体摘要不匹配；若没有拿到相应诊断，只能记录这次未完成预期验证。本文保留两次原始构建输出，没有用一次网络错误替代摘要拒绝。

摘要检查的前提也需要交接

如果操作员每次先下载文件，再把它的摘要自动写回 Dockerfile，任意新内容都能成为“正确”输入。这种流程只能描述当前取得了什么，无法检验是否仍是先前批准的内容。应先固定候选字节、审查来源与摘要，再让构建独立核对。本文的 input.md 是留存输入，不是每次构建前自动接受的新下载。

同样，内容摘要与来源可信度不是一回事。攻击者控制的文件也能有稳定摘要。团队需要先决定哪个输入被允许进入构建，再用摘要保持后续取得的内容一致。这里没有评估文本的授权、业务含义或生产适配，也没有把校验通过写成供应链所有风险均已解决。

URL 中固定提交身份有助于表达所选版本，但它不替代接收端内容检查。本例同时保留来源 URL、批准摘要、原始快照与导出文件检查。几份证据各自回答“打算取什么”“期望什么字节”以及“这次构建实际留下什么”。如果其中一项缺失，应说明缺口，而不是只保留终端最后一行完成。

复核时还要确认读取的是本次输出。复用已有输出目录，可能让旧文件在失败后仍然存在，误导检查者。本例每次用新临时目录，并将错误分支单独导出；这不意味着 Docker 会替每个读者清理旧目录。若接入现有流水线，应先明确产物目录生命周期，再把摘要断言绑定到本轮生成的文件。

这份小构建没有验证什么

scratch 教学构建没有程序入口，也不涉及应用启动。导出文本的字节一致，不能证明下游解析器、运行权限、容器网络或业务行为正确。若该文件随后成为某个程序的输入，还应在对应环境读取它，并断言业务需要的内容。本文没有运行这样的消费程序。

错误摘要对照也没有模拟所有远端变化。它固定实际来源，只改变接收端期望值，目的是验证拒绝机制。若要检查远端在两次请求之间改变内容，需要受控服务和明确的请求时间线，不能拿本例推导出已覆盖这一过程。当前回执只覆盖固定文本、正确摘要与一位错误摘要。

演练结束可在保存输入、构建版本、日志和内容检查结果后，清理本次打印出的临时目录。不要按一个模糊前缀删除其他构建输出。交接给同事时，把可重跑文件与实际执行回执一起给出，并注明是否用了已有缓存；缓存命中不是失败，但单有命中提示也不能替代读回与错误摘要的对照。

来源换成 Git 仓库，checksum 还填文件 SHA-256 吗？

不是同一合同。当前 Dockerfile 文档对 Git 来源使用提交 SHA 校验，对 HTTP 来源使用下载内容的 SHA-256。前者确认提交身份，不能用某个 README 的文件摘要代替。本文只运行了 HTTP 文本分支，没有运行 Git ADD。切换来源类型时应重新按对应文档构造完整例子，不能照抄这里的内容摘要并宣称 Git 分支也通过。
