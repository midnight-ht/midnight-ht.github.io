新值比堆顶还小，heapreplace 为什么仍把旧值赶走？

对照零与四进入两个相同最小堆后的弹出值和保留集合，并检查空堆启动条件。

正文

核心要点

  • heapreplace 总会移走旧堆顶并放入新项。
  • heappushpop 让新项参与最小值淘汰。
  • 空堆启动需要独立的容量政策。

想保留最大的三项，堆里已有二、三、五，新来零，heapreplace 却弹出二，把零留了下来。它总是先移走旧堆顶，再放入新项。如果新项也应该参与淘汰比较，heappushpop 才符合这个选择：返回较小项，把较大项留在堆里。

固定容量没有说明谁值得留下

假设一个进程维护当前分数最高的三个候选。最小堆的根是保留集合中最小的二，因此它代表当前入围门槛。来了四，移走二、留下四正好符合要求。只用这个输入测试，两种操作都会产生相同结果，很容易把接口当成可以互换。

零改变了比较关系。它比门槛还低，不应该挤走现有候选。但 heapreplace 的承诺是替换根，先弹出的对象来自旧堆；新值此时还不在候选里。结果二离开，零进入，容量仍是三。一个只看长度的验收会给这份错误选择放行。

heappushpop 相当于把新项放进竞争范围后再弹最小值，返回零，保留二、三、五。这里的区别是淘汰候选范围。不是数据结构忘记维持堆关系，两个结果都仍是合法最小堆；错的是把合法堆误当成符合最高三项的业务集合。解释时应把结构不变量和保留政策分别写出来。

两个新堆，分别核对弹出值和留下的值

下面只使用整数，避免并列任务身份带来的其他规则。每轮重新建立两个相同的堆，同时检查返回值和完整保留集合。排序只用于观察集合内容，没有把堆内部数组当成已经全序。

from heapq import heapreplace, heappushpop

for incoming, replaced, combined in [
    (0, (2, [0, 3, 5]), (0, [2, 3, 5])),
    (4, (2, [3, 4, 5]), (2, [3, 4, 5])),
]:
    first, second = [2, 3, 5], [2, 3, 5]
    out = heapreplace(first, incoming)
    assert (out, sorted(first)) == replaced
    out = heappushpop(second, incoming)
    assert (out, sorted(second)) == combined
empty = []
try:
    heapreplace(empty, 7)
except IndexError:
    assert empty == []
else:
    raise AssertionError("empty replacement must fail")
assert heappushpop(empty, 7) == 7
assert empty == []
print("incoming0: replacement retained0; pushpop retained2,3,5; empty controls passed")

输入零时，替换路径返回二，保留零、三、五；组合路径返回零，保留二、三、五。输入四时，两条路径都返回二，保留三、四、五。后一轮是必要的正向控制，它证明需要替换时两者确实可以一致；前一轮则让不同政策产生可见分歧。

如果只比较返回值，也有机会漏掉调用方的后续错误。例如代码正确地淘汰零，却又把它追加回原列表，最终保留内容就不对。反过来，只看保留列表而不检查返回值，可能让消费者把错误对象登记为已淘汰。对需要留下拒绝原因的服务，两份观察都值得保留，并关联同一次输入标识。

主例在本地只验证四个短堆结果及空堆条件，没有运行排名服务、持久化或并发读写。它也没有比较运行时间。标准库的组合操作可以减少分开调用的步骤，但这不能替一次真实负载测量，更不能证明整个候选系统的吞吐。

还可以检查最终结果会掩盖的过程错误。从同样的二、三、五开始，依次输入负二、四、八。错误地无条件替换，会先让负二入围，之后四和八又把小值挤走，最后恰好回到四、五、八这个正确集合。只在批次末尾比较名单，发现不了第一步曾经把二丢掉。

若业务在每次更新后发布当前名单，第一步的错选已经可以被用户看到。验收应为三个时间点分别写出独立预期：负二之后仍是二、三、五，四之后是三、四、五，八之后是四、五、八。这个额外输入序列是应用验收设计，没有纳入上面的运行夹具。它说明最终集合和每步可见名单是不同的承诺，产品只保证哪一种也应写清楚。

在输入边界选择替换政策

如果上游已经确认新值符合入围条件，heapreplace 可以直接替换门槛。此时检查责任属于那个上游判断，验收应让一个未达门槛的输入被挡住。若没有这一保证，就使用能让新值参与淘汰的操作，或在当前入口明确比较再替换。不要一边假设上游过滤，一边又允许另一个未过滤入口复用同一函数。

保留最大的若干项通常使用最小堆保存入围集合；若保留最小的若干项，方向会变，不能把本例不加修改地套过去。应先用一张很小的候选清单写出独立入围名单，再选择相应的比较方向。负数和同分项也需要业务合同，尤其当同分时还要保留接收先后。

本站的堆中同优先级任务讨论不可比较负载和同分顺序。本文刻意把输入限制为不同整数，只判断新值是否应进入保留集合。若真实候选是带编号的对象，应把排序字段、并列规则与淘汰身份一起检查，不能因为整数样例通过就认为对象版本自然正确。

应用验收还可以让同一批候选从两个入口到达，检查最终入围集合与事先算好的完整排序前三项一致。输入顺序可以不同，但每次被拒对象的日志应仍对应那一次实际输入。若业务把入围与执行混在一起，候选一旦执行就可能产生外部结果，后来的淘汰也不能自动撤销它。当前堆只负责选择，没有实际执行候选。

空堆时，两种操作还会一样吗？

heapreplace 在空堆上抛出 IndexError，因为没有旧根可以替换。heappushpop 则会把传入值作为最小项返回，堆仍为空。夹具用七分别检查这两个条件。如果系统还没有填满保留容量，应先决定是普通加入直到达到容量，还是允许空集合继续拒绝所有输入。直接把固定大小的满堆更新逻辑用在启动阶段，可能让候选一直留不住。这个追问改变的是已有容量状态，需要与满堆的大小比较各自验收。
