range 顺序会变，Marshal 的 map JSON 为什么仍按键排好？

对照不同赋值顺序的普通 map，检查 Go JSON 编码排序及整数键先转文本的条件。

正文

核心要点

  • 普通 map 的 JSON 编码按转换后的键排序。
  • map 遍历顺序与编码排序是不同合同。
  • 整数键转成文本后排序，不是数值次序。

Go 的 map 迭代顺序没有保证，但普通 map 交给 encoding/json 的 Marshal 时，编码器会排序键。两份用不同赋值顺序建立的字符串键 map，可以按同一份独立 JSON 文本验收。这里检查编码器合同，不靠反复观察 range 猜测输出规律。

迭代入口与编码入口各遵守什么

假设导出工具把 a 对应一、z 对应二的配置写成 JSON。有一份 map 先放 z，另一份先放 a。开发者担心语言里的 map 顺序不稳定，于是把快照测试改成接受任意文本。实际上，对这个明确的标准库编码入口，文档已经给出键排序合同，可以直接写下预期。

Go 语言规范说，map 的迭代顺序未指定，也不保证每次相同。这不要求每次遍历都表现出不同顺序，更不能用某次碰巧按字母排列来证明 map 自身有序。测试若要求两次 range 必须不同，也是在加入规范没有提供的承诺。正确的被测对象应该是应用实际调用的序列化入口。

本篇限定普通的 encoding/json v1 Marshal、字符串键与整数值，不使用自定义编码方法。该文档说明 map 值编码成 JSON 对象，支持的键类型经过规定转换后排序。排序动作属于编码过程，没有把源 map 转成一个随后可以有序 range 的容器。编码完再遍历，仍不能借 JSON 的顺序外推 map 的遍历保证。

不同赋值顺序，同一个完整文本预期

下面的 Go 夹具未执行。两份独立 map 有相同键值对，创建步骤次序不同。程序用固定字面预期比较完整输出，最后一组整数键留给追问，不依赖任何 range 轨迹。

package main

import "encoding/json"

func encode(value any) string {
    data, err := json.Marshal(value)
    if err != nil {
        panic(err)
    }
    return string(data)
}

func main() {
    first := map[string]int{}
    first["z"] = 2
    first["a"] = 1
    second := map[string]int{}
    second["a"] = 1
    second["z"] = 2
    want := "{\"a\":1,\"z\":2}"
    if encode(first) != want || encode(second) != want {
        panic("ordinary string-map key order mismatch")
    }
    numbers := map[int]string{2: "B", 10: "J"}
    if encode(numbers) != "{\"10\":\"J\",\"2\":\"B\"}" {
        panic("integer key conversion order mismatch")
    }
}

两份字符串键 map 都应得到 a 在前、z 在后的紧凑文本，值分别是一和二。测试不仅比较两份输出彼此相等，还分别与独立预期比较。如果实现把两份输入都错误编码成空对象，它们仍然可以相等，后一个条件才能拒绝这类共同错误。

完整文本也能保护值与键的关联。把 a 与 z 的值交换，键顺序依然正确，内容却已经不符合配置。只扫描开头是不是 a，或者只数有两个成员，都无法发现。对快照是否采用字节级比较，应该由接口决定：若只关心语义，可比较解析后的结构；若这个入口承诺指定表示，可以针对其支持范围检查文本。

还可以把 z 的值单独改成三，要求输出保持同样键顺序但不再匹配原快照。这条未执行的负控制用于确认测试没有只抽取键名，也没有把所有整数都当成可以忽略的表示差异。真正需要保护的是完整键值关系。

这不是跨语言 JSON 规范化实现。键顺序只是完整表示的一个条件，数值写法、字符串转义以及用户自定义编码都可能需要另外的协议约定。若业务要给表示签名或制作跨系统一致的摘要，应选择明确的规范化方案并按真实入口验证，不能从这两份简单 map 的结果升级成所有 JSON 都有同一份字节表示。

快照测试应把允许变化的范围写清

对一个只保存简单配置的 Go 内部工具，可以固定使用这个编码入口和输入类型，为完整输出保留一条明确的回归。若以后加了自定义类型，应先检查其编码方法，再调整范围。不要因为新增分支仍返回合法 JSON，就默认原先的字面快照还能覆盖它。

如果业务并不在意对象成员顺序，解析后比较结构能表达这个需求。但解析路径也要保存数字类型、重复成员与格式拒绝等相关政策。把所有文本差异都忽略，可能连数据变化一起放过；把所有差异都当错误，又可能把接口允许的表示变动变成无意义失败。先写所需合同，再选比较层。

对于诊断，可以同时保留输入键值的受控快照、采用的编码器版本和实际输出。源 map 之后被修改时，旧输出仍代表当时那次编码。若只留下一个以后再展开的对象引用，读者看到的可能已经是新配置。当前夹具没有并发修改，快照何时取得仍由应用协调，键排序没有提供并发一致性。

本站的JSON 自定义转换顺序讨论 JavaScript 的 toJSON 与 replacer 如何改变字段。这个 Go 例子没有那些钩子，关心普通 map 键的输出次序。二者都提醒评审者从真正的编码入口追踪输入，不能因为都生成 JSON，就把一个实现的处理顺序复制到另一份接口。

还可以给服务端与命令行工具分别使用同一份固定输入，检查它们实际导出的文件是否来自相同入口。单元夹具里的 Marshal 输出准确，并不能证明外层工具没有加缩进、包裹字段或后续转换。需要字节级合同的消费者，应从最终交付文件核对；当前样例只构造字符串，没有保存文件或调用 API。

整数键二和十，会按数值大小排列吗？

整数键先转换为字符串，再作为 JSON 对象键排序，所以十的文本 10 排在 2 前面。夹具最后一条预期为 10 对应 J、2 对应 B，这不同于按整数从小到大展示。接收方拿到的对象键本身也是字符串，不能把这个顺序当作数字榜单。

如果界面需要二在十前面，应在展示时采用明确的数值排序，或者使用能表达业务顺序的数组。这个追问新增键类型转换条件。它没有改变字符串键的主例，也没有承诺所有实现都按同一方式处理自定义键类型。支持这些类型时，应另按文档规则验证其转换结果和冲突处理。
