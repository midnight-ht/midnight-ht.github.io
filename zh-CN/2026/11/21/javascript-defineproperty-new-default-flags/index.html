defineProperty 只写 value，新字段为什么不能改也列不出？

对比描述符新建与字面量字段的值、标志、键列表和写入结果，区分新建与更新条件。

正文

核心要点

  • 新数据属性省略标志默认false
  • 读取值不能证明可编辑或可枚举
  • 字段合同需要分别核对各项标志

给新字段用 defineProperty 只写 value，读取时有 A，编辑时却改不动，Object.keys 也没有它。这个结果可以来自创建方式本身。新数据属性省略的 writable、enumerable、configurable 默认都是 false，与对象字面量创建普通字段的合同不同。先检查描述符，别急着把问题归给表单更新或字段丢失。

一个值还不能说明属性的行为

ECMAScript 的 Object.defineProperty 将传入描述符用于属性定义。对普通可扩展对象，原来没有这个属性时，未提供的属性标志采用相应默认值。当前规范的属性表列出数据属性的可写、可枚举、可配置默认值为假。本文限定新建的普通数据属性，没有把访问器或代理对象并入同一示例。

因此，能直接读到 code，不表示它会进入普通的可枚举键列表。属性属于对象、属性能否被修改，以及枚举时会不会出现，是几项不同条件。只拿一个读取成功的断言代表字段已经可编辑，会把后续操作所需的合同漏掉。

当调用方原来使用对象字面量建立可编辑记录，改成描述符写法时，创建出来的值可能相同，后续行为却改变。迁移审查应比较原先允许哪些操作，而不只比较第一帧画面。若业务确实需要限制某些字段，也应明确写出那项限制，避免维护者把省略理解为沿用普通字段行为。

可配置标志还值得单独保留到诊断里。即便当前故障只表现为不能改值，描述符也描述以后允许怎样重新定义属性。这里不把它简化成一个通用的「已锁定」状态。一个值的读写与一份属性定义的调整，需要依据实际标志分别判断。

两只对象从相同值开始

完整脚本创建两份独立输入，一份通过只含 value 的描述符创建字段，另一份用字面量。每份先保存值、描述符和可枚举键，再执行同样的 Reflect.set，最后读回值。预期在执行之前按字面量完整列出，不用实际结果反过来构造。

import { deepEqual } from 'node:assert/strict';
const defined = {};
Object.defineProperty(defined, 'code', { value: 'A' });
const literal = { code: 'A' };
function inspect(object) {
  const before = object.code;
  const descriptor = Object.getOwnPropertyDescriptor(object, 'code');
  const keys = Object.keys(object);
  const writeAccepted = Reflect.set(object, 'code', 'B');
  return { before, descriptor, keys, writeAccepted, after: object.code };
}
const actual = [inspect(defined), inspect(literal)];
deepEqual(actual, [
  {
    before: 'A',
    descriptor: { value: 'A', writable: false, enumerable: false, configurable: false },
    keys: [], writeAccepted: false, after: 'A'
  },
  {
    before: 'A',
    descriptor: { value: 'A', writable: true, enumerable: true, configurable: true },
    keys: ['code'], writeAccepted: true, after: 'B'
  }
]);
console.log(JSON.stringify(actual));

这份原样脚本已经在本地 Node 执行。两份初始值都是 A，第一份三项标志均为假、键列表为空、写入返回假且值仍为 A；第二份三项标志均为真、键列表包含 code、写入返回真且值变成 B。运行回执只证明这组普通对象的本地行为，没有执行组件、接口或持久化流程。

这组对照能抓住两类错误修复。只把读取代码改成直接访问属性，可能让界面重新显示 A，却没有让字段可写。只把枚举改成列出更多自有键，也不会改变写入结果。修复需要对准业务实际需要的标志，不能靠换一种读取方式掩盖其余差异。

Reflect.set 在这里提供一个明确的写入结果，脚本同时读回实际值。只检查方法没有抛错，可能漏掉写入被拒；只检查布尔值，也不足以替业务确认最终提交数据。两个读数放在同一对象、同一次尝试旁，才能解释值为什么没有变化。

描述符是在尝试写入前读取的，所以第二份记录里描述符仍记着 A，最终值却是 B。报告需要带上采样时点，不能把先前取得的描述符对象当成随原属性自动更新的实时读数。若要检查写后定义，就在写后重新读取。

把创建策略接回字段合同

如果记录需要由用户编辑，可以在创建数据属性时明确允许相应操作，再用同一份回归检查。不要为让全部测试变绿就把所有标志一律打开。系统生成身份、只读显示元数据和用户输入字段，可能承担不同责任，应逐项说明由谁改、何时改。

已有封装也可能替调用者加入标志。调查时应保存实际返回对象的描述符，而不是只看业务层传给包装函数的参数。包装函数可能补全配置，也可能在另一条入口用字面量创建字段。相同名字的对象在不同路径中，可以拥有不同的属性合同。

导出和编辑也应分别验收。若一个列表是从可枚举键生成，它看不到这项新字段可以符合当前描述符。是否需要导出它，由产品的数据表示决定。站内 对象枚举与键顺序讨论枚举结果与用户位置，本题追问的是创建时为什么给了这组属性标志。

不要把不可枚举当作保密机制。代码已经能够直接读取这个公开属性名；从某一种键列表排除，不会自动建立访问权限。这个例子只在本地演示语言属性行为，没有提供隐藏敏感信息的方案，也没有承诺其他检查工具看不到字段。

验收可以保留创建入口、是否原有属性、完整描述符、需要的读写动作和实际结果。如果某项行为不符合预期，先定位是字段创建合同变了，还是调用方换了一种操作。只存最终 A 的截图，会把创建、枚举与写入三个阶段的差异压成同一种「没有更新」。

更新已有属性时，省略标志也会重设为 false 吗？

不能照搬新建分支。这里新增已经由对象字面量建立的普通可写属性，再用只含 value 的描述符更新它。更新已有属性时，未给出的标志不因此统一重置为假。下面完整脚本单独核对这一新条件。

import { deepEqual } from 'node:assert/strict';
const row = { code: 'A' };
Object.defineProperty(row, 'code', { value: 'B' });
const descriptor = Object.getOwnPropertyDescriptor(row, 'code');
deepEqual(descriptor, {
  value: 'B', writable: true, enumerable: true, configurable: true
});
console.log(JSON.stringify(descriptor));

本机执行后 value 是 B，其余三项标志仍为真。这个结果与主例并不矛盾：两次调用是否在创建一个原来不存在的属性，是不同输入条件。评审封装函数时把新建与更新各留一份用例，才不会把默认值解释推广过头。
