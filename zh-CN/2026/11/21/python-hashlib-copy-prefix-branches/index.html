同一个 hash 轮流加 A 和 B，为什么第二份摘要串上了 A？

用独立完整字节重算，对照 hash 状态复制、别名累计与读取摘要后的继续更新。

正文

核心要点

  • 赋另一个变量名仍可能共享同一累计状态。
  • copy 从当前前缀创建独立分支。
  • 读取摘要后，原对象仍可继续更新。

两份数据共享前缀，代码轮流在同一个 hash 对象上追加 A 和 B，第二份摘要却包含了 A。update 会继续累计已有状态。要从同样前缀独立计算两份结果，可以先用 copy 分出两个对象，再各自追加后缀。

变量换了名字，累计输入并没有重新开始

假设导出器要核对 prefix:A 和 prefix:B 两份教学字节。前缀相同，开发想先计算前缀，再把结果分别交给两个步骤。若只是把对象赋给另一个变量，两个名字仍引用同一累计状态。第一个步骤加入 A，第二个再加入 B，最终表示的是 prefix:AB。这份摘要计算可以完全正确，只是输入已经偏离第二份数据。

hashlib 文档说明，多次 update 等价于把这些参数按顺序拼接后更新。对象保留的是到当前为止已经提供的字节流状态，下一次 update 没有自动分出新任务。因此排查摘要不符时，除了查看原始字节，还应核对各步骤持有的对象是否独立，以及上一份任务是否已经在它上面追加内容。

copy 返回 hash 对象当前状态的副本。两份副本从同一前缀出发，分别添加 A 和 B，可以得到各自完整输入的摘要。保留前缀对象还可以服务下一份后缀，但要约定它是否继续只代表前缀。若有代码又向这个基线写入，后来新建的副本就会继承更多字节。共享基线的所有权同样需要明确。

用完整输入重算，核对三份状态

下面的预期从完整字节分别新建 SHA256 对象，而不是拿其中一个分支的输出充当另一个分支的正确答案。它比较前缀、两个分支与别名错误路径。示例没有读取文件，也没有参与任何认证协议。

from hashlib import sha256

def hex_of(state):
    return state.hexdigest()

base = sha256(b"prefix:")
left, right = [base.copy() for _ in range(2)]
for state, suffix in [(left, b"A"), (right, b"B")]:
    state.update(suffix)
for state, complete in [
    (base, b"prefix:"), (left, b"prefix:A"), (right, b"prefix:B")
]:
    assert hex_of(state) == hex_of(sha256(complete))
bad = sha256(b"prefix:")
alias = bad
alias.update(b"A")
bad.update(b"B")
assert hex_of(bad) == hex_of(sha256(b"prefix:AB"))
assert hex_of(bad) != hex_of(right)
before = hex_of(left)
left.update(b"C")
assert before == hex_of(sha256(b"prefix:A"))
assert hex_of(left) == hex_of(sha256(b"prefix:AC"))
assert hex_of(base) == hex_of(sha256(b"prefix:"))
print("A/B branches independent; alias accumulated AB; digest observation did not freeze AC update")

两份独立分支分别等于一次性处理 prefix:A 和 prefix:B 的结果，基线仍等于 prefix:。错误别名路径则等于 prefix:AB，并且与正确 B 分支不同。这些输入刻意不同，使相同对象被继续累计时有可观察后果。只查看有没有返回一串十六进制文本，无法发现这种错误，因为所有路径都能产生格式正常的摘要。

还要核对基线本身。若两份结果恰好都从已经带 A 的错误基线复制，分支对象彼此确实不同，第二份输入仍然错误。测试因此既检查各分支，也检查最初对象到最后是否还是那段前缀。对象独立是隔离条件，正确初始状态则是另一个条件，二者不能只用一条身份断言替代。

这里使用单向完整重算作为参考，是为了给测试一个简单、可审查的输入构造。它没有用预先猜测的摘要常量，也没有比较算法实现之间的密码学性质。生产若从文件读取，还需要保存这次实际读取的文件身份与范围，避免拿生成端的数据重算成功，误认为接收端已保存同样字节。

还可以用空后缀检查分支起点。独立副本不追加任何新字节时，预期摘要与前缀基线相同；这不表示两个对象相同，只说明它们目前处理了相同输入。再给其中一份加入字节，另一份应仍保持原值。这个变体适合排查错误的复制时点，属于尚未执行的额外验收设计。

先决定状态是交给下一段，还是分给下一份

若程序本来就在读一份文件，分块调用 update 正是把同一输入继续累计，这时候不该在每块前重置。若在处理两个独立文件，前一个文件末尾之后又加入下一份，就把文件边界消掉了。接口名称可以区分继续当前流和创建新分支，调用者也应提供相应输入身份，减少两种用途混用。

共享前缀的分支可以在前缀固定后创建。每份后缀由自己的对象处理，结果与原输入标识一起返回。若前缀也可能变化，应先为它定义版本，再让每个任务记录采用哪版。这个样例只用一份固定字节，没有检查多个线程同时修改、跨进程传递或外部任务调度，因此不会为这些场景声明隔离已经成立。

本站的摘要字节与十六进制表示讨论比较结果时两端的格式。当前故障更早发生在输入累计阶段：即使双方都用 hexdigest，累计多了 A 仍然不匹配。诊断应先核对输入组成和状态归属，再判断输出表示，不能通过把格式改成另一种来修正已经混入的字节。

分支结果也没有为输入提供来源认证。两份完全相同的字节在同一算法下会有同样摘要，但这不说明是谁生成它们。若业务要求批准版本、可信发送者或请求新鲜度，应采用相应协议和证据。本文只示范状态复制，没实现签名、消息认证或重放判断，也没测性能收益。

调用过 digest 后，还能继续 update 吗？

可以。摘要读取描述的是当前已经提供的内容，并没有把对象变成结束状态。夹具先保存 A 分支的十六进制结果，再追加 C；保存的字符串仍对应 prefix:A，当前对象则对应 prefix:AC。这个新条件区分了一次观测与状态冻结。

若日志保存的是那条旧字符串，它能保留当时结果；如果代码只保存一个仍会继续更新的对象引用，后来读取就可能看见新状态。报告应说明摘要在哪个时点产生，避免把任务中间的检查点当作最终文件摘要。主例验证了这一个继续更新场景，没有把它推广为任意自定义摘要对象都有同样接口。
