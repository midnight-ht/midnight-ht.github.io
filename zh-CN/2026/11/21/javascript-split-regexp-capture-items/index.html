split 用正则括号后，分隔数字为什么也进了数组？

逐项比较捕获与非捕获分隔结果，解释捕获项怎样占用limit，并检查未参与的捕获。

正文

核心要点

  • 捕获分隔会把捕获值插入结果
  • limit计入捕获项而非只数正文段
  • 下游需要明确输出项的角色

A1B2C按数字分隔，本来想得到A、B、C，结果却夹着1和2。若分隔正则写成捕获组，split会把捕获值插入输出数组。用括号组织匹配与要求输出捕获内容，是两个可能同时发生的动作。先确认这些额外项从哪里来，再决定是否改成非捕获组。

分隔匹配后，还会追加捕获项

ECMAScript 的字符串分隔方法会在适用时交给分隔对象的 Symbol.split。对于普通内建正则，算法先追加前面的文字片段，再按顺序追加这次匹配的各个捕获值，随后继续处理剩余输入。因此括号带来的输出不能简单理解为分隔失败。

本例模式匹配一个数字，括号把这个数字保存为捕获内容。第一次分隔前文字是A，随后追加捕获的1；第二次分隔前文字是B，再追加2，最后留下C。五个结果项中，三个来自两段分隔之间及末尾的文字，两个来自捕获。

如果括号只是用来组织模式，可以使用非捕获分组。它仍参与匹配，却不会作为捕获项插入数组。这里的非捕获数字模式仍以1和2为分隔符，结果只保留A、B、C。是否需要保留分隔信息应来自后续解析合同，而不是看到数组变长就直接删掉奇数位置。

也不要把所有括号都说成必然增加输出。捕获组与非捕获组有不同语法，正则还可能有其他结构。审查时保存实际模式和标志，确认它建立了哪些捕获，再对应每次匹配。本文只使用简单数字分隔，没有实现任意模式的通用解析器。

三种调用使用同一段输入

完整脚本比较捕获分隔、非捕获分隔，以及捕获分隔加数量限制。预期按顺序完整列出，避免只比较长度。每种调用都直接读取同一个未改变的字符串，没有先把数字删掉或对原始材料另做预处理。

import { deepEqual } from 'node:assert/strict';
const source = 'A1B2C';
const cases = [
  { separator: /(\d)/, limit: undefined },
  { separator: /(?:\d)/, limit: undefined },
  { separator: /(\d)/, limit: 3 }
];
const actual = cases.map(({ separator, limit }) => source.split(separator, limit));
deepEqual(actual, [
  ['A', '1', 'B', '2', 'C'],
  ['A', 'B', 'C'],
  ['A', '1', 'B']
]);
console.log(JSON.stringify({ source, actual }));

这份原样代码已在本地Node执行，三份结果与字面预期一致。捕获版是A、1、B、2、C，非捕获版是A、B、C，限制三项的捕获版是A、1、B。运行范围是当前字符串和内建正则，没有读取导入文件或执行业务保存。

最后一项是一个容易漏掉的负例。limit计的是结果数组总项数，捕获也占位置。三项并不表示最多返回三个正文片段，更不表示自动保留三列完整数据。数组到A、1、B就达到上限，后面的2和C不在这次输出中。

若测试只检查前三项恰好存在，却不核对内容角色，这份截断结果也可能被当成合法三列表格。验收应先明确哪一项是字段、哪一项是需要保留的分隔信息，再选择模式和上限。限制结果数量不能替代完整输入校验，也不会指出原串还有多少内容被舍弃。

保留原输入尤其有助于解释上限截断。拿到A、1、B之后，调用者不能只从这三个输出判断原串是否正好结束；本例原串还保留2和C。若导入任务必须确认全部材料都已处理，就要在解析合同里定义完整消费的判据，不要把返回项数等于上限当作已经完成。

用输出结构决定下游怎么读

假设页面按固定下标读取名称、数量、备注，新增一对捕获括号后，下标的含义就可能改变。表面上分隔方法没有报错，后续字段却开始读到分隔符。保留一个包含不同文字与数字的最小输入，逐项核对身份，比只看导入成功条数更容易发现这类偏移。

如果分隔信息本来就需要保留，例如展示每段文字与它后面的标记，捕获输出也可以成为有意的表示。但调用者应明确它并不是一份所有项都代表正文的列表。可以在自己的结构中区分文字与标记，再验证两者的顺序和对应，而不是在多个页面里重复猜数组的奇偶位置。

另一类错误是分隔后统一过滤所有看起来像数字的项。这样既可能删掉有意保留的捕获，也可能删掉原来就是合法正文的数字字段。修复应从分隔模式和目标结构开始，不能用一个与数据合同无关的过滤器，碰巧让当前示例只剩字母就结束。

如果真正要处理有引号、转义或嵌入分隔符的文件格式，这个简单正则没有证明自己符合完整格式。先按对应文件规范选择解析入口，再用代表性输入验证。当前示例只解释内建分隔的捕获行为，不把它宣传成CSV或任何复杂导入格式的完整处理方案。

这和替换文本中的特殊解释也属于同一类接口审查。站内 replaceAll的字面替换与替换串讨论另一条字符串合同。方法名称看起来像简单文本操作，参数中的语法仍会影响返回结构。各自保存原输入、实际参数和完整输出，才有证据说明变化发生在哪一步。

某个捕获组没参与匹配，会省略那一项吗？

不会简单省略它。这里新增两个备选捕获组，一个匹配连字符，另一个匹配逗号。在A-B这次匹配中，连字符组有值，逗号组未参与，对应捕获值是 undefined，算法仍把这个值放进结果。

import { deepEqual, strictEqual } from 'node:assert/strict';
const actual = 'A-B'.split(/(-)|(,)/);
deepEqual(actual, ['A', '-', undefined, 'B']);
strictEqual(Object.hasOwn(actual, 2), true);
const display = actual.map(value => value === undefined ? '<undefined>' : value);
console.log(JSON.stringify({ display, thirdType: typeof actual[2] }));

独立脚本已经执行，结果是A、连字符、undefined、B。第三个位置有自身属性，值是 undefined，不能把它当成数组缺槽。日志另外把这个值标成可见文字，同时保留类型读数，避免直接JSON输出时的表示变化掩盖原始类型。未参与匹配与匹配到空字符串，也需要保留为不同结果。
