LPOS 从尾部找，为什么仍返回正向下标？

用三个重复标记对照 LPOS 的正负匹配次数、原列表坐标及 MAXLEN 有限范围。

正文

核心要点

  • 负 RANK 改变搜索方向，不改变下标起点。
  • COUNT 结果保留扫描遇到的顺序。
  • 有限 MAXLEN 的未找到只覆盖扫描范围。

LPOS 用 RANK -1 从尾部找 X，返回的仍然是从头开始计数的下标。对于 A、X、B、X、X，最后一次 X 的位置是四。负 RANK 改变查找方向和匹配次数选择，没有把返回坐标改成从尾部起算。

出现次数与列表坐标分别编号

这份列表有五个位置，按零起点编号为零到四。X 在一、三、四出现。正向第一次匹配是一，第二次是三；从尾部的第一次匹配则是四，第二次是三。如果业务把 RANK 理解成返回下标，或者以为负一会返回尾部距离零，就会在客户端取错元素。

Redis 文档说明，LPOS 默认从头到尾找第一个匹配并返回零起点位置。RANK 用来指定多次匹配中的第几次，负数让搜索从尾部反向进行。返回结果依然是列表中的实际下标。调用方应把选择第几次与定位哪一项分开，这样日志里 RANK=-1、index=4 可以同时成立。

这些坐标还属于查询时的列表。若其他客户端随后从头部插入或删除一项，原来的下标可能已经指向另一项。把查到的位置交给稍后的修改操作前，需要依据应用合同处理这种变化。本文先用没有并发写入的隔离列表解释坐标，不用一次查找承诺后续修改一定作用同一个业务对象。

用重复标记让两套编号显出来

下面是未在 Redis 环境执行的命令夹具。键应在独立测试数据库中原先不存在，运行期间没有别的写入者或过期设置。起始五项和每条位置预期都已固定，最后三条用于追问的有限搜索预算。

RPUSH review:lpos:nov21 A X B X X
LPOS review:lpos:nov21 X RANK 1
LPOS review:lpos:nov21 X RANK 2
LPOS review:lpos:nov21 X RANK -1
LPOS review:lpos:nov21 X RANK -2
LPOS review:lpos:nov21 X RANK -1 COUNT 2
LRANGE review:lpos:nov21 0 -1
LPOS review:lpos:nov21 X MAXLEN 1
LPOS review:lpos:nov21 X MAXLEN 2
LPOS review:lpos:nov21 X RANK -1 MAXLEN 1

建表后长度应为五。RANK 一返回一，RANK 二返回三，RANK 负一返回四，RANK 负二返回三。正二和负二恰好相同，不能只用这一条证明方向是否设置正确；第一项与最后一项的对照才让它们产生明显分歧。只有一个 X 的列表同样无法验证出现次数的政策，所以夹具保留三个重复标记。

负一再配 COUNT 二，预期返回四、三，按反向扫描遇到的顺序。它没有自动把位置排序成三、四，也没有把它们转换成零、一这样的尾部相对坐标。客户端若为了展示排序，应该把那个结果视为自己的变换，不能拿排后的数组验证服务端原来的搜索顺序。

随后读取完整列表，应仍是 A、X、B、X、X。LPOS 是读取命令，返回位置不会移除匹配项，也不会把它搬到头部。这个独立状态控制可以抓住误接到其他列表操作的包装器。只看某次返回了一个整数，既不能证明查找方向正确，也不能证明来源保持原状。

让接口传递真实位置还是业务身份

如果消费端马上在同一份稳定列表快照里高亮最后一个 X，返回四足以定位。若它要跨请求保存选择，只有一个坐标可能不够：列表随时可能改变。可以为实际元素保存稳定编号，并在后续入口确认版本与目标身份。重复的正文 X 在这里故意没有稳定身份，目的是让位置与内容不能互相替代。

本站的工作队列领取与恢复讨论另一种列表责任。LPOS 只观察位置，不建立处理所有权。任务系统即使找到了最后一个重复内容，也不能据此判断那条任务已经被本消费者独占。需要修改或领取时，应按真实入口定义操作和验收，不要在查找日志后面直接写已领取。

接口还可以把请求 rank、实际 index 和查询范围一起返回给诊断工具。这样看到三时，就能分辨它可能来自正向第二次，也可能来自反向第二次。对用户界面来说，显示“第几次出现”应采用匹配编号，显示“列表位置”则采用坐标，两者是否从一开始展示也要明确。数据库的零起点不应被展示层悄悄当成第一条的编号零。

一份较强的回归可以让头部和尾部使用不同的独立标识，再把重复标记放在不对称位置。分别检查正负 rank 和 COUNT 的完整序列，而不是只验证结果都指向 X。因为错误实现即使总返回第一个 X，内容检查也可能通过。当前夹具的 A 与 B 以及三处 X 已给出明确的不对称坐标，应用可以再加入自己的业务编号。

这些预期全部根据命令合同推导，没有实际服务器、客户端库或线上列表参与。不同客户端可能把无结果包装成不同空值类型，接入时仍要对照实际返回接口。不能把这里文本写出的 nil 当作某种语言中已经执行过的对象，更不能从命令数量猜测完成了网络往返。

MAXLEN 没找到，能证明整张列表没有 X 吗？

不能。MAXLEN 限制比较的列表项数量。本例从头只比较一项，只看到 A，返回未找到；预算为二时能看到位置一的 X。反向 RANK 负一只比较一项，就先看到队尾 X，返回四。夹具最后三条给出这三份不同预期，说明同样预算也受方向影响。

这个条件改变了“未找到”结论的范围。需要证明整个列表不存在时，必须采用覆盖相应列表的搜索合同，而不是把有限预算的失败升级成全局不存在。文档允许 MAXLEN 为零表达不限制比较，但实际延迟和列表大小仍要在服务环境验证。这里没有执行延迟测试，也没有为任何列表规模给出性能保证。
