想测已安装的包，pytest 为什么只把包名当路径找？

从源码目录外按包名运行 pytest，核对解释器、安装来源与测试节点，识别同名本地副本。

正文

核心要点

  • pyargs 根据包位置寻找测试。
  • 安装与执行绑定同一解释器。
  • 核对来源后再解释通过节点。

要让 pytest 按 Python 包名寻找测试，可以使用 --pyargs。它先解析可导入的包，再用该包的文件系统位置收集。普通位置参数默认面对测试路径，不能只因为参数长得像模块名，就认定已经测试了安装环境中的发行物。

例如包已经安装进虚拟环境，验收任务在一个没有源码的目录运行。命令传了包的点分名称，却提示找不到文件或目录。此时可以先核对解释器确实能导入目标包，再使用包名入口。包能导入和测试能被收集各是一条事实，测试行为通过还需要第三份结果。

在源码目录外运行一份安装样例

创建一个专用目录，保存下面的项目定义。需要本机有 uv，并能取得固定版本 pytest 和构建依赖。这个教学包没有外部服务，也不使用真实业务数据。项目定义用 setuptools 构建，把普通包与包内测试一起安装。

[build-system]
requires = ["setuptools>=68"]
build-backend = "setuptools.build_meta"

[project]
name = "zy21-demo"
version = "0.0.1"

目录布局如下。两个初始化文件使它们成为普通包。外层初始化文件只写 MARKER = "installed-marker"，tests 的初始化文件为空。测试读取包的标记，而不从当前工作目录取文件。

pyproject.toml
zy21_demo/
  __init__.py
  tests/
    __init__.py
    test_origin.py

import zy21_demo

def test_marker():
    assert zy21_demo.MARKER == "installed-marker"

在这份项目根执行以下脚本。它创建独立环境，安装当前项目，并切到新建的 consumer 目录。普通参数分支预期返回四，另一次才使用 pyargs。保留环境路径和完整回执，方便复核安装来源，演练结束后可清理这次创建的临时目录。

set -eu
source_dir=$PWD
work=$(mktemp -d)
uv venv --python 3.11 "$work/env"
uv pip install --python "$work/env/bin/python" pytest==9.0.2 "$source_dir"
mkdir "$work/consumer"
cd "$work/consumer"
export PYTEST_DISABLE_PLUGIN_AUTOLOAD=1
python="$work/env/bin/python"
"$python" --version
"$python" -c 'import zy21_demo; print(zy21_demo.__file__)'
status=0
"$python" -m pytest -v -p no:cacheprovider zy21_demo.tests || status=$?
test "$status" -eq 4
"$python" -m pytest -v -p no:cacheprovider --pyargs zy21_demo.tests

本地固定 Python 3.11.15 与 pytest 9.0.2 的运行中，普通点分参数报告路径不存在并退出四；pyargs 分支运行一项标记测试并通过。包的 __file__ 指向这次虚拟环境的 site-packages。安装来自项目路径，执行工作目录已经移到 consumer，两份位置证据共同说明读者正在检查安装后的布局。pytest 的包名入口

最初的环境准备曾自动选择 Python 3.9.6，因不满足 pytest 9.0.2 的解释器要求而被依赖解析拒绝。那次没有测试结果。后续显式固定 3.11，再运行上述流程。保留原始错误有助于把安装失败与收集失败分开，不能把命令没跑起来的输出写成某个用例已失败。

安装成功以后还要检查装进了什么

包里有测试并非所有项目的发行约定。有些 wheel 故意不包含测试，pyargs 无法替它生成遗漏的文件。若验收合同要求测试已安装产物，就先核对目标测试随包存在，再从外部目录执行；若测试单独发放，则把那份测试的来源与被测包的来源分别固定。不要只因源码树里有 tests，就宣称用户安装后也得到同一集合。

同样，包标记通过只是本例的最小行为。真实库可能需要额外数据、动态库或环境配置。安装产物中的导入成功，不能代替这些依赖的实际使用。可以在包内选择一项真正读取安装数据的行为测试，让它断言当前版本预期的内容，再核对结果。本文没有执行产品数据加载，只验证名称定位与这项标记读取。

解释器与安装器也必须指向同一个环境。若先用一套 Python 安装，后用另一套 pytest 启动，即使包名一样，也可能找不到它或找到其他版本。脚本把两种调用都绑定到同一解释器路径，避免由命令搜索路径猜环境。正式记录还应保存依赖版本和安装来源，日后才能说明这次通过属于哪个发行物。

将节点身份与包来源一起留档

只看到一项通过，不足以说明验收记录对应哪次安装。保留包的实际位置、工作目录和测试节点，再把它们与安装回执关联。节点短名足以让终端看懂一次运行，审核材料则需要来源能复验。交接时记录这轮环境如何创建、装入哪些输入，并把结果固定到这一轮执行。

测试选择也有自己的边界。pyargs 解决参数如何解释，不保证包里每个公开功能都被覆盖。若正式任务只选择一个子包，其他子包的测试不应因此记为已运行。先列出验收要求对应的模块或节点集合，再核对这一次实际收集。这样包名入口可以成为交付检查的一步，而不会被误记成整个发行物已经验收。

另一个容易误用的回执发生在源码更新以后。假设开发者改了某个函数，却没有把这份新内容重新构建安装。外部目录里的测试仍然可能找到上一份安装，并正常通过。它证明的还是旧输入。把候选源码身份、安装过程和最后读取的位置串起来，再确认本轮实际安装的是要验收的那份内容。这个场景未运行，样例只安装了一份确定的项目。

同样的版本字符串也不应代替内容来源。同名版本若来自不同构建或工作目录，审核者需要知道本次用的是哪一份。可以在受控交接里固定构建输入和安装产物的内容身份，再将实际包位置与该次安装关联。遇到来源不一致，先恢复正确输入并重跑验收，别把原来的绿色结果贴到新候选上。

本地同名包会被 pyargs 自动避开吗？

不会有这样的保证，它仍依赖当前导入环境。另一次本地对照在 consumer 里创建同名包，标记改成 local-marker，并放入同一条期望 installed-marker 的测试。新的包位置指向 consumer，pyargs 调用执行该测试后得到断言失败，退出一。这个实测改变了导入来源，主例运行时 consumer 原本为空。要测试发行包，应核对来源并控制搜索环境，不能仅凭用了该选项就认定本地副本被排除。
