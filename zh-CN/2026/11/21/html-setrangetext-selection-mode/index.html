setRangeText 文本一样，为什么选区位置不同？

比较同一局部替换的三种选区模式，保留文字与两端偏移，区分编辑结果和后续输入位置。

正文

核心要点

  • 替换区间与原选区可以不同
  • 同样文本可对应不同选区端点
  • 测试需同时保留值和位置

把文本框里的cd替成XYZ，最终都得到abXYZef，光标与选区却可以不同。setRangeText的selectionMode决定替换后选择新片段、停在末端，或按原选区调整。若测试只确认文字正确，就可能让用户下一次键入覆盖了错误范围，却仍把这次替换记为通过。

替换区间与选区是两组坐标

HTML 的文本控件选择API把位置表示为相关值内的代码单元偏移。这里使用普通text输入和ASCII文字，避免把用户感知字符数量与偏移混在一起。替换从start开始，到end之前结束，两端决定哪些代码单元被移除。

初始abcdef，替换区间是二到四，选中被替换的文字为cd。新片段XYZ有三个单位，原片段两个，所以替换后文本增长一个单位。原来的选区另外设为一到五，覆盖bcde，它不必等于替换区间。这个区别决定preserve不能简单等同于「选中新片段」。

select会把新片段作为替换后的选区，因此端点是二到五。end把选区收拢到新片段结尾，两个端点都是五。preserve则按算法维护原选区与编辑的关系。本例起点一在替换前，不需后移；终点五在原替换末端之后，随着长度差增加一，成为六。

这些结果都可以伴随同一段abXYZef。测试因此至少要保留当前值和两端位置。若组件要求用户检查建议替换文本，select可能符合任务；若希望继续在替换结尾输入，end是另一种选择。方法不会从页面文案推断产品想要哪个行为。

核对偏移时，可以先把零标在a前，二标在c前，四标在e前。这样二到四移除的就是cd，不包含e。若把结束位置误当成最后一个要删除字符的下标，替换范围会多吃一项。先把这份边界理解对齐，再比较不同选区模式，才能把两类错误分开。

三只独立控件使用同一起点

完整页面为三种模式分别新建一个输入框，先写相同文字，再设置同一原选区，然后替换。没有复用上一种模式已经改变的控件。读数输出模式、最终值、选区起止，便于检查文本相同而端点不同的情况。

<!doctype html>
<meta charset="utf-8">
<title>Replacement selection modes</title>
<script>
addEventListener('DOMContentLoaded', () => {
  const create = document.createElement.bind(document);
  const panel = create('div');
  const results = [];
  for (const mode of ['select', 'end', 'preserve']) {
    const input = create('input');
    input.type = 'text';
    input.value = 'abcdef';
    input.setSelectionRange(1, 5);
    input.setRangeText('XYZ', 2, 4, mode);
    results.push({ mode, value: input.value,
      start: input.selectionStart, end: input.selectionEnd });
    const label = create('label');
    label.append(mode + ' ', input);
    panel.append(label, create('br'));
  }
  const output = create('pre');
  output.append(JSON.stringify(results, null, 2));
  panel.append(output);
  document.body.append(panel);
});
</script>

按规范推导，三项值都应是abXYZef，select端点二与五，end端点五与五，preserve端点一与六。这里没有运行浏览器，不能把页面输出称为本机观察。代码给出完整可执行页面，实际产品还需要在目标环境保存真实读数。

选区属性也不等于用户当前一定看见高亮。本例先创建控件并设置逻辑选区，焦点没有被当作读数的前提。真实交互中还要确认当前编辑控件、焦点和最终可见选择状态。不能从一张没有高亮的截图，反推这些属性必然没有更新。

负例可以把三个模式都错误传成end，最终文字仍然全对，而第一和第三份选区预期会失败。这比只检查页面含有XYZ更能发现模式被丢失。为每种模式保留独立初始值与原选区，避免前一次变更改变下一次实验的条件。

从编辑任务确定后续动作

假设一个校对工具把建议词替进句子。用户可能想马上覆盖建议，也可能想继续写后面的内容。这两种后续动作需要不同选区合同。验收应真的接着输入或执行下一步，核对改动落在哪里，再决定哪一种模式适合产品。

如果替换之前有异步工作，最初保存的偏移可能已经过期。用户继续输入后，二到四未必仍指向原来那段文字。调用方法之前要核对当前值或对应文档版本，必要时重新定位或请用户确认。这里固定同步输入，没有实现并发编辑或位置变换系统。

同样不要为了显示结果，把整个value重新赋一遍后又期待选区策略自动保留。局部替换、全值替换和设置选区是不同入口，框架也可能在下一次渲染时重新写入值。先确认由谁拥有输入状态，再把这项API接到正式更新流程中，而不是在控件和框架之间互相覆盖。

脚本值变化与事件通知还有自己的合同，站内 程序写值与input事件讨论这一点。本例核对的是替换内容及位置，没有把事件次数当作文本版本，也没有宣称某个框架已经收到同步通知。

面向非ASCII输入时应重新检查偏移来源。一个用户看见的符号可能需要多个代码单元，如果上游按另一种单位计数，区间就会落到意料之外的位置。保留原始文字、偏移单位和实际范围，不要从这组六个英文字母推广出所有文本都能逐字加一。

运行记录也要保持同一时点。替换完读取两端，然后又由另一个处理器移动焦点或选择范围，稍后的读数可能不同。若要调查用户下一次键入，记录真正接近该动作的状态；如果要验证API直接结果，就紧跟调用读取。两份观察回答的阶段不同，应各自命名。

start大于end，会自动交换两端再替换吗？

不会按这个方式纠正。这里新增反向区间，主例都是合法的顺向输入。HTML算法在start大于end时抛出IndexSizeError，拒绝发生在修改文本之前。不能把它等同于某些选择范围接口调整两端的规则。

<!doctype html>
<meta charset="utf-8">
<title>Reversed replacement range</title>
<script>
addEventListener('DOMContentLoaded', () => {
  const create = document.createElement.bind(document);
  const input = create('input');
  input.type = 'text';
  input.value = 'abcdef';
  let errorName = 'none';
  try {
    input.setRangeText('XYZ', 4, 2, 'select');
  } catch (error) {
    errorName = error.name;
  }
  const output = create('pre');
  output.append(JSON.stringify({ errorName, value: input.value }));
  document.body.append(input, output);
});
</script>

这个独立页面的规范预期是错误名IndexSizeError，当前值仍为abcdef。它也没有实际运行浏览器。产品若允许用户拖动选择方向，应由输入处理明确得到合法区间，再调用替换；不要依赖一个没有承诺交换端点的方法替应用猜意图。
