ProtectSystem=strict 下，服务该往哪里写自己的状态？

用受管理状态目录保留必要写入，以同身份普通路径的 EROFS 对照检查保护；Linux 运行待复验。

正文

核心要点

  • 受管理状态目录可排除只读保护。
  • 拒绝对照须识别具体错误类别。
  • 目录可写不等于数据恢复已验证。

用 StateDirectory 声明服务自己的状态目录，它会从 ProtectSystem=strict 的只读保护中排除。这样应用可以保留必要写入，而不必把整个系统目录重新开放。这里讨论 Linux 上的 systemd 系统服务，并以单个状态目录为主例。

假设服务需要保存一个进度标记。开启严格只读保护后，直接往任意系统路径写文件可能失败。与其先关闭保护，可以先明确哪些内容属于服务状态，再让管理器创建对应目录，并把应用写入位置绑定到提供的环境变量。目录可写只是访问合同的一部分，写入的业务内容还需要自己的断言。

在专用路径上做允许与拒绝对照

下面是一份供隔离 Linux 主机复验的样例，本文没有启动 Linux 服务。本次只在 macOS 归档输入并做 Python、Shell 的语法检查。未观察到服务启动、挂载视图或只读错误，因此接下来的运行结果均为预期，不能作为 systemd 实测回执。

先保存 check.py。程序读取 STATE_DIRECTORY，写入后立刻读回完整值。之后用同一进程写另一个专用普通目录，只接受 EROFS。权限不足、路径不存在等其他错误会继续抛出，避免把任何失败都当成只读保护有效。若普通目录意外可写，程序也会失败。

import errno
import os
from pathlib import Path

state = Path(os.environ["STATE_DIRECTORY"])
marker = state / "marker"
marker.write_text("state-ok\n")
assert marker.read_text() == "state-ok\n"
print("STATE_READBACK_OK", state, flush=True)
try:
    Path("/var/lib/zy21-control/marker").write_text("unexpected\n")
except OSError as exc:
    if exc.errno != errno.EROFS:
        raise
    print("CONTROL_EROFS", flush=True)
else:
    raise AssertionError("control directory unexpectedly writable")

再保存 check.service。这个教学服务明确用 root 身份，使宿主上预建的 root 专用对照目录在常规权限层面可写。它不是生产服务的身份建议，生产中仍应为实际应用选择合适账户。两次尝试使用同一个身份，才有助于区分只读挂载保护与传统目录权限。

[Unit]
Description=Isolated managed-state write check

[Service]
Type=oneshot
User=root
Group=root
StateDirectory=zy21-state
StateDirectoryMode=0700
ProtectSystem=strict
ExecStart=/usr/bin/python3 /run/zy21-state-check.py

在一台允许创建这些专用路径的隔离 Linux 主机，以 root 从两个文件所在目录执行以下命令。先确认名称都不存在，防止覆盖旧服务或状态。主机还需有 systemd 系统管理器、对应保护机制支持和 /usr/bin/python3；缺少这些条件应停下来核对，而非跳过错误继续宣称成功。

set -eu
test "$(id -u)" -eq 0
test ! -e /var/lib/zy21-state
test ! -e /var/lib/zy21-control
test ! -e /run/zy21-state-check.py
test ! -e /etc/systemd/system/zy21-state-check.service
install -d -m 0700 /var/lib/zy21-control
install -m 0600 check.py /run/zy21-state-check.py
install -m 0644 check.service /etc/systemd/system/zy21-state-check.service
systemctl daemon-reload
systemctl start zy21-state-check.service
journalctl -u zy21-state-check.service --since '5 minutes ago' --no-pager
cat /var/lib/zy21-state/marker

预期服务日志同时出现 STATE_READBACK_OK 与 CONTROL_EROFS，宿主读取 marker 得到 state-ok。前一项证明受管理目录内的具体读写，后一项证明普通对照目录受只读限制。只看 systemctl 返回成功，无法知道程序是否检查了预期内容；只看一个 OSError，也无法区分它由哪层拒绝。

为什么不直接给普通路径放行

systemd.exec 的保护和目录说明把 StateDirectory 等受管理目录列为 ProtectSystem 只读效果的排除项。系统服务的这类状态目录位于 /var/lib 下，管理器负责创建并按配置处理所有权。样例使用管理器提供的位置，避免在程序里另写一份容易漂移的状态根路径。

普通对照目录在服务启动前由宿主创建，位于另一条独立路径。它存在且 root 有目录权限，服务内却预期只读。这一设计只用于验证本例的保护效果，不能外推为服务已被全面隔离。其他可写挂载、额外放行规则、服务账户和平台能力都可能改变真实应用的写入范围。

若应用必须写的是一份长期状态，应先确认它是否真的属于该服务。共享数据库文件、多个账户共同维护的目录，与单服务标记有不同的所有权要求。不要为了让样例通过就把既有共享路径挂到专用状态名下。先划清内容归属，再决定受管理目录是否合适，最后复验应用读回与拒绝对照。

单个绿色回执也不足以解释失败后的数据状态。写入中途失败是否留下部分文件、下一次启动怎样识别旧格式，都由应用决定。这里每次只是写一个固定教学字符串，没有模拟断电、并发写或迁移。正式接入需要根据实际状态格式选择原子更新、恢复或迁移检查，不能从目录可写推导出数据持久性保证。

停止以后检查什么，怎样清理

StateDirectory 与临时运行目录的生命周期不同：服务停止不会自动移除状态目录。停服务后可以核对 marker 仍在，但本文未执行这一检查。若业务需要“每次启动清空”，应先重新判断它是不是持久状态，不能把自动保留误记成清理失败。

演练结束先保存日志和内容，再停止服务，删除本次创建的单元文件与 /run 脚本，并重新加载管理器。确认没有其他引用后，仅清理这次预先确认不存在、由演练创建的两个专用 /var/lib 目录。不要把删除整个 /var/lib 作为清理步骤，也不要套用到已有生产状态。保留输入和清理前证据，才能说明验证对象是什么。

遇到写入失败，先检查日志是否来自本次启动，再看 STATE_DIRECTORY 的实际值、单元最终配置与错误类别。若根本没有启动 Python，应先修启动路径；若得到 EACCES，应查账户权限；若受管理路径返回 EROFS，则复核主机支持与实际配置。这些是诊断顺序，不是本地已复现的失败结果。

日志时间窗也只是检索方便。相同单元若此前运行过，窗口内可能含多次启动。复验时将本次调用结果与对应日志关联，确认两条标记属于同一次执行，再写入验收回执；旧记录不能替代本次没有产生的结果。

配置两个状态目录后，还能把变量直接当一个路径吗？

不能沿用主例的单路径假设。官方说明，多项对应的 STATE_DIRECTORY 值以冒号分隔。应用应按自己的目录合同拆分，并确认每项对应的用途；否则把整个字符串交给 Path，可能误把多个位置当作一个文件名。这个问答新增了目录数量条件，本文没有执行多目录服务。应另建双目录对照，分别写入和读回，而不是用主例的一次成功覆盖它。
