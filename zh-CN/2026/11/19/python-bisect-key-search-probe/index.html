bisect 已指定 key，为什么还不能传整条记录搜索？

用并列分数的记录表检查 bisect 的探针类型、左右边界和 insort 实际插入的对象。

正文

核心要点

  • bisect 的搜索值直接使用比较键类型。
  • insort 的搜索会提取新记录的键，插入仍保留记录。
  • 插入点需要额外边界和相等检查才能用于精确查找。

记录列表已经按 score 排好序，bisect_left 也传了提取 score 的 key，为什么新的字典仍然与整数比较并报错？搜索函数只对列表中的记录提取键，传入的搜索值需要直接处于比较键的值域。在这份数据里，查分数二十时应传整数二十。

列表装着记录，搜索入口接受什么

假设一个后台界面维护按分数升序排列的四条记录。甲的分数是十，乙和丙都是二十，丁是四十。用户输入一个分数，希望知道这个分数应落在界面的什么位置。此时用户并没有提供一条完整记录，也无需为了查找临时编造编号。key 提取器让搜索可以从列表成员得到分数，调用者则直接交出要比较的数字。

bisect_left 会给出能维持排序的左侧插入位置。它不需要先证明某个元素与搜索值相等。二十分已经有两条时，左侧边界在乙之前；右侧边界在丙之后。两个位置之间的范围正好可以表示所有并列的二十分记录。这条规则的前提是输入已经按同一比较键排序，列表也不会在搜索途中被其他代码改动。给了 key 不会触发一次预排序，更不会把乱序数据自动修好。

传整条字典导致失败，并不是列表不支持记录。比较到中间元素时，左边是从记录提出来的整数，右边仍是调用方传入的字典。在这两个对象之间比较大小，没有对应的顺序合同。只把字典里的分数字段改个名字，或者把 key 函数换成另一个等价提取器，都不会改变右边的值域。修复入口应先确定搜索参数代表分数，还是完整业务对象。

三个位置，再加一条真正插入的记录

下面用相同分数和不同编号保留并列记录。左、右边界以及缺失值的位置各有独立预期，错误探针也独立检查。夹具随后在浅层列表副本里插入一条新的记录，不修改原始四条记录的字段。

from bisect import bisect_left, bisect_right, insort_right
from operator import itemgetter

rows = [
    {"id": "A", "score": 10},
    {"id": "B", "score": 20},
    {"id": "C", "score": 20},
    {"id": "D", "score": 40},
]
score = itemgetter("score")
assert bisect_left(rows, 20, key=score) == 1
assert bisect_right(rows, 20, key=score) == 3
assert bisect_left(rows, 30, key=score) == 3
try:
    bisect_left(rows, {"id": "X", "score": 20}, key=score)
except TypeError:
    pass
else:
    raise AssertionError("whole record must not be the score probe")
updated = rows.copy()
insort_right(updated, {"id": "X", "score": 20}, key=score)
assert [r["id"] for r in updated] == ["A", "B", "C", "X", "D"]
print("score probes: 1,3,3; record insertion: A,B,C,X,D")

查二十时，左边界为一、右边界为三。查三十得到三，虽然三十这条记录并不存在。第二个事实说明一个合法位置并不能直接当作找到了内容。负例传入完整字典，预期进入 TypeError 分支；没有走入该分支，程序会自己失败。正例调用 insort_right 后，新记录 X 位于已有二十分记录之后，四十分记录之前，完整编号顺序也被检查。

insort_right 接受完整的新记录。它先把 key 应用到新记录，取得比较键来定位，然后把原记录放进列表。搜索步骤与插入步骤因此有不同对象。若把搜索接口的修复机械搬到插入接口，传入一个整数，就可能让提取器拿不到字段，或者把一个不符合列表元素格式的对象交给消费者。验收必须走实际使用的入口，并同时确认列表最终仍由完整记录构成。

在服务边界给参数起清楚的名字

可以把查找方法设计成接受 score，把添加方法设计成接受 record。这样调用者从签名就知道要提供哪种值。若上层确实拿着一条完整记录，要查它的分数位置，可以在调用前明确提取，再把数字交给搜索方法。若将来排序增加第二个字段，搜索参数的比较类型也要跟着变成相应的组合键，单独提供旧的分数就需要重新定义范围含义。

并列数据是这个接口的必要验收项。只有十和四十两个分数时，左右插入边界可能恰好一样，很容易让左侧与右侧的选择一直没被测试。加入乙和丙后，再分别断言边界与实际插入后的编号，可以判断业务是否允许新项排在同分段前面。搜索与插入的选择没有替业务规定公平性。新项应该插到哪一侧，要由产品或服务的排序合同来定。

还应保护记录被修改之后的顺序。假设已经放在最前面的甲把分数改成五十，列表就不再满足搜索前提。继续在它上面二分查找，即使某次返回看起来合理的位置，也无法证明后续都能正确。应用可以在字段修改时移除旧记录再按新键放回，或在适当边界重建顺序。本站的合并有序输入同样要求调用方提供可靠顺序，不过那里关注多个来源的局部顺序，这里关注一次搜索的探针类型和插入边界。

这里的实际测试覆盖短列表上的比较、返回位置和插入身份。没有测排序维护的并发实现、数据库索引或搜索性能。特别是插入要挪动后面的列表元素，不能因为搜索用二分就承诺插入整个过程都是对数成本。若当前列表只在一个请求内使用，简单副本足以隔开样例；若许多任务共享可变列表，需要另行决定协调方式。

返回了位置，就能认为查到相等记录吗？

不能直接这样解释。夹具里的三十返回位置三，那一项实际是四十。要实现精确查找，可以先确认位置尚在列表范围内，再比较对应记录的键是否等于搜索值。若查五十，左侧位置为列表长度，更要避免先取元素再验边界。这个追问增加了“只接受已存在键”的条件，与定位可插入的位置不同。先确定接口要返回插入点、匹配范围还是精确记录，再给缺失值和超出末尾的值各写一条预期。
