Scanner 读到空字符串，就算文件结束了吗？

对照空行、空输入与无终止换行的末行，用完整结果检查 Scanner 循环是否提前退出。

正文

核心要点

  • 以 Scan 的布尔结果判断是否取得 token。
  • 默认逐行切分允许空行。
  • 扫描结束后检查 Err，并单独定义部分结果政策。

Go 的 Scanner 读到空字符串，不表示已经到文件末尾。默认逐行切分允许一条有效空行，是否取得下一条 token 应看 Scan 的返回值。若程序遇到 Text() 为空就退出，空行后面的 footer 会被一起漏掉。

一个字符串承担不了两种状态

设想运维导入一份简单的逐行清单，第一行是 header，中间保留空行用于分段，最后是 footer。文件已经被完整交给读取器，没有网络断连或编码问题。业务代码却只收到 header。这时应该先检查消费循环把什么当作结束条件，而不是通过删掉输入中的全部空行让导入碰巧继续。

Scanner 的默认切分函数是 ScanLines。它按行产出文本，去掉行结束标记，得到的行可以是空字符串。因此中间两次相邻换行，会产生一次确实存在、但长度为零的行。在 Scan 返回真时取得这条 Text，它已经是一份可供处理的结果。应用可以保存它、跳过它或按格式拒绝它，但如果空行只是分段，就不应该用它终止读取。

Scan 返回假才说明没有下一个 token，原因可能是输入结束，也可能是错误。循环正常走到这个状态后，Err 用于检查扫描时遇到的非 EOF 错误；正常 EOF 不会作为错误返回。如果业务提前 break，Err 即使为空，也不能证明余下输入已经被扫描完。错误路径里的 footer 之所以丢失，恰好是应用自己停在 EOF 之前。

五份输入把空行和结束分开

下面是未在 Go 环境执行的教学夹具。每次调用都从一个新的 strings.Reader 开始，比较全部返回文本。错误开关只控制遇到空行是否提前退出，用来让同一份输入走两条不同路径。

package main

import (
    "bufio"
    "reflect"
    "strings"
)

func lines(input string, breakOnBlank bool) []string {
    out := []string{}
    scan := bufio.NewScanner(strings.NewReader(input))
    for scan.Scan() {
        text := scan.Text()
        if breakOnBlank && text == "" {
            break
        }
        out = append(out, text)
    }
    if err := scan.Err(); err != nil {
        panic(err)
    }
    return out
}

func main() {
    cases := []struct {
        input string
        stop bool
        want []string
    }{
        {"header\n\nfooter", false, []string{"header", "", "footer"}},
        {"header\n\nfooter", true, []string{"header"}},
        {"", false, []string{}},
        {"\n", false, []string{""}},
        {"header\n\nfooter\n", false, []string{"header", "", "footer"}},
    }
    for _, c := range cases {
        if got := lines(c.input, c.stop); !reflect.DeepEqual(got, c.want) {
            panic(got)
        }
    }
}

第一项期望保留三个元素，第二项故意只得到 header。它们的源文本完全一致，差异发生在循环中 Text 为空的分支。因此即使错误路径没有抛异常，也不能把它记作完整导入。第三项真正的空输入没有 token，第四项只有一个换行则产生一个空 token。两份看起来都没有可见文字的输入，结构上仍然不同。

比较完整列表还能保护 footer 的位置。如果只数非空行，正确结果与提前删除空行的结果可能一样，却无法说明分段是否保留。反过来，如果格式明确不保留空行，可以在 Scan 返回真以后跳过当前结果，然后继续扫描，并要求后面仍能拿到 footer。跳过当前行和结束整个循环，是两个在代码里必须分开的动作。

这个测试没有模拟读取故障。它展示正常的短文本怎样被应用截断，读取错误仍须另设一个受控 Reader 来触发。不要因为例子每条 Err 都为空，就断言底层永远不会出错。对于过大的 token，Scanner 也存在缓冲限制；具体接受上限和如何报错应按服务输入合同单独验收，当前短文本没有覆盖那个条件。

让导入结果说明读到了哪里

如果清单每段开头有标识，错误报告可以同时保存已经处理的段编号和实际停止原因。文件完整读取后收到缺少 footer 的业务错误，和循环在中间空行直接返回，需要不同定位办法。前者应该继续查生成器或格式，后者应该先查循环。只有最终输出非空，就把接收状态记为成功，会让这两条路线混在一起。

应用级验收可以给 footer 设置一个必须出现的固定标识，并让它总在空行之后。正确实现必须看到它；错误实现则明确漏掉。再增加一个应该忽略的空行，要求过滤之后依然只包含 header 与 footer。这样既能验证允许过滤的格式，也能阻止把过滤修复写成 break。若有记录数校验，还要说明空行是否计入总数，避免日志里的“第三行”和业务里的“第二条”指向不同对象。

还应区分逐行协议和 CSV。CSV 的一个带引号字段可以跨物理行，Scanner 的 ScanLines 没有维护那种记录状态。若上游真正交付 CSV，应该按它的格式使用对应解析器。本站的CSV 换行与记录边界专门解释这条边界。本文假设上游格式就是逐行文本，字段里不会另有可跨行的记录语法，不能用这段循环替换一个完整 CSV reader。

原读取入口的归属也应写进函数合同。若调用方打算在返回后继续读同一来源，不要用处理了几行就推断底层正好停在那里；Scanner 可能已经从底层预读。本文只把这个读取器交给单个扫描过程，不把提前退出后的来源继续拼到另一种读取器上。

若函数返回已处理的列表，还要决定异常时是否允许返回前半部分。示例的读取错误会直接 panic，用于让假设数据的检查失败；服务接口通常需要结构化错误和明确的部分结果政策。无论允许还是拒绝部分结果，都要告诉调用者扫描有没有正常结束，避免调用者拿到一部分记录后以为整个文件已经被接受。当前夹具没有实现写库或外部提交。

最后一行没有换行，会丢掉 footer 吗？

默认 ScanLines 会返回最后一个非空行，即使它没有行结束标记。夹具第一项与第五项只差最后的换行，预期都保留同样三个文本。因此为了补救末行，盲目追加换行并不必要。若协议要求文件必须以特定标记结尾，那是另一项格式条件，需要自己验证。把末行是否非空、是否有终止符与读取是否失败分别保留，才能解释为什么“没有最后一个换行”和“没有最后一条记录”不能互相替代。
