合并提交改了什么，怎样把人工解冲突的部分找出来？

用二亲冲突合并对照 Git 的重合并视图、首亲差异和最终文件内容，定位这次合并的解法。

正文

核心要点

  • 重合并视图比较临时树与记录结果。
  • 最终文件要从合并提交独立读取。
  • 解法与业务行为分别验收。

审查一个双亲合并提交时，git show --remerge-diff 可以帮助找出冲突最终怎样被解决。Git 先重新合并两个父版本，生成可能含冲突标记的临时树，再把它与已提交的合并结果比较。报告里减去的可以是临时冲突内容，加上的才是最终解法。

这适合一类具体交接。一个补丁在各自分支上都已评审，集成之后某个配置却成了第三种值。看合并相对第一父的差异，可以确认当前值变了，但不容易看清另一分支提供过什么选项。维护者想审的是这次合并作出的判断。把比较对象换成重建结果，才能把这个判断显露出来。

让两个分支都修改同一行

以下脚本创建一次性仓库，两支分别将同一行改为 main 与 side。合并预期发生内容冲突，脚本随后把最终内容明确写成 chosen。它没有从工作区偶然存在的文件推测最终解法，合并提交里的文件内容也会被单独读回。运行前需要支持 remerge diff 的 Git。

set -eu
lab=$(mktemp -d)
trap 'rm -r "$lab"' EXIT
cd "$lab"
git init -q -b main
git config user.name Fixture
git config user.email fixture@example.invalid
git config commit.gpgsign false
git version
file=policy.txt
recreated=resolution.patch
ordinary=first-parent.patch
printf 'policy=base\n' > "$file"
git add "$file"
git commit -qm base

git switch -qc side
printf 'policy=side\n' > "$file"
git commit -qam side
git switch -q main
printf 'policy=main\n' > "$file"
git commit -qam main
status=0
git merge --no-edit side || status=$?
test "$status" -eq 1
printf 'policy=chosen\n' > "$file"
git add "$file"
git commit -qm resolution
test "$(git show HEAD:policy.txt)" = policy=chosen
git show --format= --remerge-diff HEAD > "$recreated"
git diff HEAD^1 HEAD -- "$file" > "$ordinary"
cat "$recreated"
printf '\nFIRST PARENT\n'
cat "$ordinary"
grep -F '+policy=chosen' "$recreated"
grep -F -- '-policy=main' "$recreated"
grep -F -- '-policy=side' "$recreated"
grep -F -- '-<<<<<<<' "$recreated"

本地 Apple Git 2.50.1 执行时，合并步骤返回一，并报告这份文件有内容冲突。解决并提交后，remerge patch 减去了冲突标记及 main、side 两个候选值，增加 policy=chosen。首亲比较只显示从 main 改成 chosen。脚本分别检查了最终文件和这些差异行，整趟退出零。这里的冲突退出一是预期中间状态，保留它能证明样例确实走过冲突路径。

这两份报告各自有用途。首亲比较告诉接手人集成到主线后实际多了什么变化。重合并报告则在这个样例里显示两个冲突候选怎样收束到最终文件。临时树里的冲突标记从未成为真实发布文件，不能把报告里的减号标记行当作曾经进入主分支的历史内容。要检查用户会得到什么，仍以合并提交中读回的文件为准。Git show 的 remerge 定义

先确认父版本，再问解法是否合理

给别人发审查材料时，保存合并提交以及两个父提交的完整对象号，说明使用的 Git 版本和比较命令。两支的名字后来可以移动，材料里的对象不能随之变成另一份代码。临时冲突树依赖这两个父版本，拿当前分支尖端重新尝试合并，可能已经是在观察下一轮集成。若文件路径在之后被更名，也应以本次合并中的路径定位。

然后给最终解法一个独立的业务判断。例如 main 的值意味着本地环境，side 的值意味着远程环境，chosen 是团队认可的隔离环境。报告只能显示字符串选择，无法决定隔离环境是否真的能连接正确的依赖。可以在受控配置里读取该键，确认它指向预期位置，再运行一项不会触达生产的功能检查。本文只运行字符串对照，没有执行任何环境连接。把代码选择和行为验证分别列出来，维护者才能判断是还缺设计说明，还是还缺运行回执。

无冲突的合并也是一个反例。两个分支各改不同文件，自动合并的临时树与记录树可以相同。这时没有需要展示的 remerge 差异，也不说明合并没有带来功能变化。两份新代码可能第一次同时出现，在调用关系、配置组合或资源使用上产生新的行为。查看实际双亲差异与最终树，按集成合同安排测试。不能把“没有解冲突改动”直接记成“集成已验证”。

正式流程若要自动收集这类材料，先决定它是给人读的审查附件，还是机器要长期解析的输入。官方说明 remerge 的输出及其与其他选项的交互可能变化。因此可以保存完整原文，附上版本和对象号，方便人复算；若需要抽取固定字段，应围绕具体版本和测试样本验证自己的解析器。当前脚本只是针对样例查找几条内容，未提供通用冲突分类工具。

对于历史问题，不要从一张截图里决定是谁误解了需求。先定位发生了选择的那一个合并提交，读两侧相关文件和已经记录的最终解法，再收集当时的约束。一次机械正确的文本合并仍可能落错业务选择，反过来选用了第三种内容也不天然表示误操作。重合并视图帮助缩小需要解释的范围，判断需要由需求和真实验收补上。

收集附件时可以先做一次对象一致性检查。假设代码评审系统展示的是合并提交 M，而值班终端停在后来又合入一笔的 HEAD。直接拿终端默认结果去解释 M，就会把另一笔决策带进记录。使用明确的对象号生成两份报告，再从同一对象读取最终文件。若三份材料没有指向同一个合并，先修正对象关联，保留原错误附件以说明误判来源。这个交接情景未运行，脚本中三个读取都指向刚生成的同一 HEAD。

八爪鱼合并也能得到这种视图吗？

这里描述的 remerge 模式适用于双亲合并提交。若一个合并记录有三个或更多父版本，先核对它的结构，再选择适合该结构的审查方式。可以检查合并提交相对每个父版本的差异，但这些比较与重建双亲冲突树提供的信息不同。不要因为命令没有输出预期形状，就把多亲合并记成没有冲突解法。本文的临时仓库只创建两个父版本，没有执行多亲对照。
