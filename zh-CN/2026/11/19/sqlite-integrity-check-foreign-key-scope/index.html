integrity_check 返回 ok，SQLite 为什么仍有孤儿行？

在独立内存库上对照结构正常与外键错误，核对诊断四列和修复后仍保留的子行。

正文

核心要点

  • integrity_check 不检查外键违反。
  • 用 foreign_key_check 的四列定位失败关系。
  • 结构与关系检查各自解析不同的成功结果。

SQLite 的 integrity_check 返回 ok，订单仍可能引用不存在的客户。这条检查不检测外键错误。恢复验收要检查关系时，应另外运行 foreign_key_check，并读取它报告的子表、行标识、父表和外键编号。

结构正常与引用有效可以同时有不同结果

假设一个迁入的数据库里有客户表 parent 和订单表 child。客户一存在，订单十却指向客户九百九十九。库的页、索引与存储结构可以正常，错误发生在两张表的引用关系。检查者看到 ok 后结束验收，就会把这个错误留给后来读取客户信息的业务代码。

SQLite 的完整性检查涵盖多种数据库内部问题，也检测 UNIQUE、CHECK 和 NOT NULL 等错误。但官方文档明确把外键排除在这条命令之外，并指向 foreign_key_check。这里不能把单词完整性按日常含义扩展成所有数据约束都已检验。不同检查的输出应该保留自己的名字，让后续报告能看出哪些条件真的执行过。

foreign_key_check 每发现一项外键违反就返回一行。第一列是声明引用的子表，第二列通常是出错子行的 rowid，第三列是被引用的父表，第四列是外键编号。这不是父表缺失记录的编号。对于一个有多条外键的子表，应拿第四列与 foreign_key_list 的编号对应，才能知道具体哪条关系失败。把第二列看成业务引用目标，会把本例订单十误当成客户十。

让同一个库同时产生 ok 和关系错误

下面的本地夹具显式关闭当前连接的外键执行，并立即读取配置确认。这个设置只用于隔离的内存库，目的是造一条已存在的坏关系；没有修改任何项目数据库。创建和插入完成后，分别检查两项结果，再补上缺失父行，确认关系诊断消失。

import sqlite3
from contextlib import closing

def rows(db, sql):
    return list(db.execute(sql))

with closing(sqlite3.connect(":memory:")) as db:
    db.execute("PRAGMA foreign_keys=OFF")
    assert rows(db, "PRAGMA foreign_keys")[0] == (0,)
    db.executescript("""
        CREATE TABLE parent(id INTEGER PRIMARY KEY);
        CREATE TABLE child(
            id INTEGER PRIMARY KEY,
            parent_id INTEGER REFERENCES parent(id)
        );
        INSERT INTO parent VALUES(1);
        INSERT INTO child VALUES(10, 999);
    """)
    assert rows(db, "PRAGMA integrity_check") == [("ok",)]
    assert rows(db, "PRAGMA foreign_key_check") == [
        ("child", 10, "parent", 0)
    ]
    db.execute("INSERT INTO parent VALUES(999)")
    db.commit()
    assert rows(db, "PRAGMA integrity_check") == [("ok",)]
    assert rows(db, "PRAGMA foreign_key_check") == []
    assert rows(db, "SELECT id,parent_id FROM child") == [(10, 999)]
    print(sqlite3.sqlite_version, "structural ok; FK orphan found; parent repair verified")

初始独立预期是完整性检查只有 ok，外键检查恰有 child、十、parent、零这一行。之后只增加父记录九百九十九，外键结果变成空列表；完整性检查仍然是 ok。最后确认订单十仍指向九百九十九，防止所谓修复其实偷偷删掉了订单。两次相同的结构结果与两次不同的关系结果，共同证明两条命令检验的条件不同。

这份修复控制没有声称补客户是业务上正确的处理。现实里引用九百九十九也可能来自迁移映射错误，正确动作可能是修正引用、隔离记录或补齐经过核验的父对象。测试只用插入父行把关系从违反变成满足，并保留同一子行。业务恢复需要保存谁选择了这种修复，以及新父行属于哪份数据来源。

如果只是把当前连接的 foreign_keys 开关打开，也不能把它当作扫描历史记录的回执。本站的SQLite 外键连接配置已经解释连接执行范围；本例进一步比较诊断入口，让已有孤儿行有明确的输出位置。生产恢复报告应分别写检查命令及其结果，避免拿一个执行开关替代一份数据检查。

报告应让接手者找到哪一行

可以把每个违反项整理成子表、子行定位、父表和关系定义，并附上检查针对的数据库文件或连接身份。对临时副本完成检查后，再回到原库查询一遍不能证明副本已经修好。对于恢复演练，应在目标副本完成相同检查，保存变化前后的诊断和相关稳定业务标识。

有些团队只保存错误条数。数目能判断是否还有问题，却无法支持两个重试之间的定位比较。假设修复后仍有一条错误，可能是原来那条没修好，也可能是另一条刚暴露出来。固定样本最好同时检查完整四列；大数据报告也应留下足够定位的信息，按实际访问规则处理敏感字段。这里只用整数教学标识，没有真实客户内容。

还要说明验收如何面对业务写入。这个内存样例没有其他连接，所以前后变化可以明确归到刚才的插入。活库在诊断之后仍可继续变化，一份检查结果应绑定观察时间与范围。若迁入流程需要在开放写入前完成检查，可以把这个时点设为门禁；若边接入边检查，则需要另外解释哪些写入处在检查之后。两条命令通过，都不能推断未来入口永远不会产生关系错误。

检查报告若被保留到文件，还应记录这次目标数据库的受控路径和对应备份批次。下一轮拿新副本复查时，先确认这两个身份，再比较四列诊断，避免把旧报告的空列表误算成本次恢复通过。

在自动化里，应分别解析结构检查与外键检查的成功形状。前者是一个含 ok 的单行结果，后者是空结果。把两种成功统一写成“没有输出”，可能把正常结构结果误判为错误；把只要出现一行就当成成功，又会把关系错误行误判为通过。两种解析器都可以用上面的初始状态作负控制。

子表使用 WITHOUT ROWID，第二列还能定位业务主键吗？

这种表在 foreign_key_check 的第二列返回 NULL。它没有用业务主键自动替代 rowid。因此诊断报告需要按关系定义另外查询稳定的业务字段，或者保留可供受控查询的定位条件。不能把一个空 rowid 当成没有违反项，其他三列仍然在描述错误。这是子表存储方式改变后的新条件；上面的执行夹具使用普通 rowid 表，没有验证这份变体。真实 schema 包含这种表时，应另建一条违反关系的输入，检查报告仍能定位和处理。
