COPY 多个目录的文件，怎样保留各自的父路径？

分别导出普通与保留父路径的 COPY 结果，用文件内容和缺席检查核对接收端需要的层级。

正文

核心要点

  • 保留父路径会改变制品层级。
  • 按消费方预期路径读取内容。
  • 最终打包后的路径仍需核对。

Docker 把不同源目录里的文件复制到同一个目的目录时，可以用 COPY --parents 保留各自的父路径。普通复制把文件放在目的目录下，保留父路径则把源目录关系带过去。接收方按相对路径读文件时，这个差异就是交付合同的一部分。

例如上下文同时有 alpha 下的配置和 beta 下的模板。维护者检查两份文件都进了导出目录，于是认定构建正确。接收程序却要求原有目录层级，读根目录时找不到输入。仅仅证明某个文件名在磁盘上存在，还没有确认它在谁的父目录下。固定两份内容和两份导出，可以把这个判断独立做出来。

两个阶段，各自导出一份目录

在一个新目录里放下面的 Dockerfile。创建 alpha/one.txt，内容为一行 alpha-marker，再创建 beta/two.txt，内容为一行 beta-marker。这两个名称不同，避免把同名目标覆盖冲突也混进这次实验。前端需要支持 parents，当前参考把该选项的最低 Dockerfile 语法版本标为1.20。这里的本地 builder 使用支持该选项的前端。

FROM scratch AS ordinary
COPY ./alpha/one.txt ./beta/two.txt /payload/

FROM scratch AS retained
COPY --parents ./alpha/one.txt ./beta/two.txt /payload/

从上下文根运行以下脚本。使用支持 local 导出的单平台 Buildx builder，两个阶段分别导出到新的空目录。每份结果都读实际内容，并检查一个错误落点缺席。没有调用容器进程，也没有上传镜像。

set -eu
work=$(mktemp -d)
trap 'rm -r "$work"' EXIT
first=one.txt
second=two.txt
docker buildx version
docker buildx build --progress=plain --target ordinary --output "type=local,dest=$work/plain" .
docker buildx build --progress=plain --target retained --output "type=local,dest=$work/parents" .

test "$(cat "$work/plain/payload/$first")" = alpha-marker
test "$(cat "$work/plain/payload/$second")" = beta-marker
test ! -e "$work/plain/payload/alpha"
test "$(cat "$work/parents/payload/alpha/$first")" = alpha-marker
test "$(cat "$work/parents/payload/beta/$second")" = beta-marker
test ! -e "$work/parents/payload/one.txt"
printf 'plain: payload/one.txt, payload/two.txt\n'
printf 'parents: payload/alpha/one.txt, payload/beta/two.txt\n'

本地 Buildx v0.37.2 的两次构建及读回通过。普通阶段的 payload 里有 one 和 two 两个文件，父路径保留阶段则分别在 alpha 和 beta 子目录下得到对应内容。前者没有 alpha 目录，后者没有直接放在 payload 下的 one。内容正向检查证明没有把另一份文件拿来冒充，缺席检查则约束层级真的发生了改变。Dockerfile 的父路径复制规则

这个选项改变的是复制进制品的路径结构，不会修改构建上下文里的源文件，也不会把源目录名作为运行工作目录。接手一个旧脚本时，应先确认相对路径基于哪个交付目录解析，再决定保留完整的父路径是否符合需要。仅在 Dockerfile 里加一个开关，可能让已有消费者改读另一条路径。两边都检查过，才知道是修复路径还是引入不兼容。

让消费端按自己的路径验收

假设接收程序的清单是 payload/alpha/one.txt 和 payload/beta/two.txt。它应从真正接收到的归档或导出里按这个路径读标记。用全盘查找发现 one 只能说明某处有文件，不能代替读清单里的项。在代码评审中，把新增的 parents 与消费清单同步展示。若清单本来要求扁平目录，普通阶段可能更符合要求，保留父目录反而会让它找不到文件。

还要区分目录结构和文件身份。复制后目录正确而内容拿错，也无法完成交付。例如构建上下文曾经从另一份工作树生成，alpha 里的文件名相同，内容版本却落后。读回固定标记只是小样例的方法。真实任务应核对明确版本对应的内容或制品标识，并保留构建上下文来源。路径存在与内容符合预期两条断言，各自覆盖一条失败路径。

对旧任务改造时，先选两份具有不同父目录的代表性文件，列出当前消费者要求的目标清单。用普通与保留父目录各生成一份新的输出，分别给消费者验。改动后若允许两种布局，要让消费者明确支持这两份布局并验证目标版本，不要靠遇到哪个文件就随手读取。尤其是同时有旧布局残留时，递归查找很容易读到旧产物。脚本给各阶段使用独立空目录，正是为了避免这种状态掩盖错误。

真实发布如果后面还有打包、剥离目录或路径重写，也要在最终包重新核对。local 导出的正确清单只证明当时的文件系统结果。下一步压缩把顶层目录去掉，消费方要求的路径也会随之改变。给发布回执同时保留导出根、打包输入和最终归档清单，就能定位哪一步改变了层级。本文没有生成正式归档或验证下游服务，仅测试本地文件导出。

源目录改名还会暴露另一个兼容性问题。假设团队把 alpha 移到了 config/alpha，并同步更新 COPY 的源参数。保留父路径之后，新制品中的层级也会多出 config。复制可能成功，文件内容也没有变，但原消费清单不再匹配。先判断这个源代码组织变化是否应该传给接收方。如果接收方合同要求固定层级，就在构建规则中明确维持目标路径，再拿旧清单验证。若合同也一起更新，给新旧消费者各自声明版本。本文未运行这个重构分支，它用于说明选项把源目录结构纳入了交付兼容性范围。

清单的版本可以随接收方一起留档。构建脚本提交更新以后，用旧消费规则读取新输出，看到失败的具体路径，再用约定的新规则复验。若两份规则都应支持，就分别保留成功回执。若旧规则已退出支持，交接时写明对应消费者版本，避免把路径迁移误报成文件丢失。这个验证流程尚待实际消费方执行。

只想保留源路径中的一段，怎么选起点？

在源路径中插入点斜线，可以只保留它后面的父目录。另一个本地对照用 COPY --parents ./outer/./inside/three.txt /payload/，输入内容为 pivot-marker。独立阶段导出后，在 payload/inside/three.txt 位置读到它，并确认没有 payload/outer 目录。这个新条件改变的是保留路径的起点，主实验没有裁剪父目录。使用多阶段来源的绝对源路径时也需核对起点，而不能从上下文目录的例子猜测所有来源位置。
