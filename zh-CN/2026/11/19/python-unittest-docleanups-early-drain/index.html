测试还没结束，unittest 怎样先归还一批已登记资源？

用同一项 unittest 的两阶段事件，核对提前清理、重复排空和新登记回调各自的执行顺序。

正文

核心要点

  • 主动排空会弹出当前清理回调。
  • 排空后的同批回调不会重复执行。
  • 新登记项仍由后续清理处理。

unittest 的测试还在执行时，可以调用 doCleanups() 提前归还已经登记的资源。它按后进先出逐项弹出清理栈，所以同一批回调不会在测试结束时再来一次。排空之后仍然可以登记新回调，由后续正常清理处理。

这能解决分阶段测试里的一个具体顺序问题。第一阶段取得 A、B 两项资源，验证结束后必须归还，第二阶段才可以用新的 C。若只在用例最终返回后统一收尾，第二阶段可能在 A、B 仍占用的情况下开始。另一方面，手动调用资源关闭又把原清理回调留在栈里，可能让最终收尾再次关闭同一资源。提前排空由谁负责，需要有一份完整的时间线。

先验中间状态，再看最后一次收尾

下面的程序只用内存事件代表取得与释放，没有操作真实文件或远端系统。每次登记的回调参数都固定到相应资源名。测试先调用 doCleanups，直接检查 B、A 已经释放，紧接着再调用一次验证没有重复事件。然后登记 C，等用例正常结束。外层用单独的 TestResult 执行一次用例，再检查整段顺序与错误数。

import unittest

events = []
record = events.append

class PhasedCase(unittest.TestCase):
    def setUp(self):
        for name in ("A", "B"):
            record("acquire-" + name)
            self.addCleanup(record, "release-" + name)

    def test_phases(self):
        self.doCleanups()
        self.assertEqual(events, [
            "acquire-A", "acquire-B", "release-B", "release-A"
        ])
        self.doCleanups()
        self.assertEqual(len(events), 4)
        record("acquire-C")
        self.addCleanup(record, "release-C")
        record("test-end")

    def tearDown(self):
        record("tearDown")

result = unittest.TestResult()
PhasedCase("test_phases").run(result)
assert result.wasSuccessful(), (result.errors, result.failures)
assert result.testsRun == 1
assert events == [
    "acquire-A", "acquire-B", "release-B", "release-A",
    "acquire-C", "test-end", "tearDown", "release-C",
]
print(events)

本地 Python 3.11.15 直接运行这份脚本，退出零。事件顺序明确是取得 A、取得 B、释放 B、释放 A、取得 C、测试结束、tearDown、释放 C。外层还核对只运行了一项测试且没有错误与断言失败。第二次提前排空没有新增事件，所以已有 A、B 的释放没有重放。最后的 C 保持在栈里，等到 tearDown 之后才释放。unittest 的清理栈说明

如果只在整个运行结束后检查 A、B、C 都曾释放，可能漏掉阶段边界。去掉第一次主动排空，等到最后统一清理，最终仍然可以看见三个名字，但 C 使用时 A、B 并没有先归还。本文没有运行这个修改分支。中间那条事件断言就是为了识别“最终会清理”和“已经及时清理”两种行为。阶段间有独占约束时，采用后者才符合测试合同。

再注意 LIFO 的意义。先得到底层 A，再取得依赖它的 B，可以先释放 B 再释放 A。但函数登记的顺序本身不会替你识别依赖。若先登记 B、再登记 A，执行顺序就会倒过来。为每项资源写出取得与对应归还的名称，再检查时序，才能把顺序当成设计依据。真实程序里可以把回调直接绑定到确定的句柄，减少闭包后来读到其他资源的机会。

提前排空改变了这一阶段的归属

当一个测试需要执行几个独立阶段时，明确哪批资源应在同一栈里。主动排空会处理当时已登记的整批清理。若 A 需要活到第二阶段以后，而 B 必须先结束，不能把两者都放进同一批，再期待排空只关 B。可以让这段资源用自身作用域管理，或拆出生命周期更明确的独立测试。根据资源真正的依赖选择边界，避免为了少写几行准备代码而共享一个过大的清理范围。

另一个容易混淆的情况是显式调用过某资源的关闭方法，却没有更新清理安排。只有资源接口明确允许重复关闭，才可以依赖这种行为。本文的事件回调会每次追加记录，刻意不隐藏重复动作。若用真实连接测试，除了事件清单，还要读回资源状态，并检查调用方以后是否仍试图使用已经失效的句柄。内存标记无法证明连接已经关闭或服务器已撤销对象。

外层执行方式也要保存原错误。示例为了观察框架时序，用 TestResult 捕获一项用例的结果，然后单独断言是否成功。正式任务如果套了类似验证程序，需要把内部 errors、failures 和清理轨迹一并留出。外层返回零表示本例所有预期都满足，不能笼统说内部任意错误都可以接受。遇到不符合 oracle 的清理次序，让外层失败并输出完整轨迹，接手人就能区分业务断言坏了还是资源边界选错。

若测试有第二阶段失败，也仍需确认新登记的 C 会被正常收尾。可以在自己的隔离资源上让 C 的使用抛异常，核对它的释放回执和原始错误同时存在。这个扩展未运行。程序崩溃或进程被强制结束则需要额外的资源期限与回收机制，Python 回调不提供跨进程恢复。对于共享测试环境，仍应将句柄或对象与本轮测试身份绑定，避免清理别人的工作。

还可以给两轮取得同名资源的练习加上本轮身份。第一阶段释放了名为 session 的句柄，第二阶段也取得同名句柄。仅在外层查到一次 session 已释放，无法判断归还的是哪一个。将事件记录成资源名与取得批次，再分别确认提前释放和最终释放。这里的 A、B、C 刻意使用不同名字，实际系统若会复用名称，应该留下相应的句柄身份。这个扩展尚未运行。

enterContext 在进入时失败，也会登记退出动作吗？

只有上下文成功进入，TestCase.enterContext 才会把该对象的退出方法登记为清理回调。这是不同于主实验的新条件。若 __enter__ 自己抛错，未成功进入的部分应由该上下文实现处理，而不能期待未登记的退出回调完成补偿。这个接口自 Python 3.11 起提供。主实验直接登记三项回调，没有进入任何上下文，也没有运行进入失败的对照。验收实际资源时可分别记录成功进入后的退出和进入失败后的本地残留，避免把两者混为同一种清理路径。
