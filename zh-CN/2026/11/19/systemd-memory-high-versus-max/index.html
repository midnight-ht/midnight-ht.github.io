服务内存超过 MemoryHigh，为什么没被立即杀掉？

分清 systemd 的内存回收阈值与硬边界，结合有效值和 cgroup 事件判断服务状态。

正文

核心要点

  • MemoryHigh 引发回收和节流。
  • MemoryMax 是另一道硬性边界。
  • 有效阈值和事件计数要配对读取。

服务超过 MemoryHigh 后仍然存活，可以符合 systemd 的内存控制设计。这个值触发回收压力和节流，不是越界便立即杀进程的开关。需要限制内存使用的另一道边界是 MemoryMax。先读实际生效的控制项，再解释进程存活或退出。

发布验收里常有一个误判。配置写了三十二兆，监控后来看到更高的用量，维护者就报告限制没有加载。这个结论少了中间一层。要核对的是有没有进入回收压力，以及使用的是哪一项边界。反过来，内存用量看似一直低于阈值，也不能证明节流已经触发。只看一张用量曲线，无法代替有效设置和事件计数。

两个边界分别约束什么

在统一 cgroup v2 层级上，MemoryHigh 对应 memory.high。超过它会令进程承受回收和节流。Linux 内核文档明确说明，越过 high 本身不会调用 OOM killer，在极端情况下这个边界也可能被突破。MemoryMax 对应 memory.max。达到该硬性边界且无法回收降低使用时，可能在组内触发 OOM。内核也给出暂时越界及有些分配失败不触发 OOM 的条件，所以不能写成只要越过数值就必然有一次杀进程。内核的内存接口说明

这两项可一起配置。high 作为日常调控，max 保留另一道防线。控制器发生压力时，程序可能变慢，业务延迟也许随之变化，但具体变化需要实际观测。没有执行特定负载，就不能从三十二兆的配置推导某个延迟百分比。也不能只看到程序没死，就认定它一直没受约束。systemd 的 MemoryHigh 与 MemoryMax

给隔离负载留一组可读的回执

下面是一份未运行的 Linux 测试机练习。需要已启用统一层级和 memory 控制器，systemd 版本支持所列属性，并有足够空闲资源。只在可丢弃机器上进行，不修改真实业务服务。先将 Python 脚本保存为 /run/zy19-memory/allocate.py。它申请四十八份一兆的字节数组，再逐页触碰以避免只观察到虚拟地址范围。解释器和分配器自身也占内存，所以总用量不等于那四十八兆。

import time

blocks = []
for index in range(48):
    block = bytearray(1024 * 1024)
    for offset in range(0, len(block), 4096):
        block[offset] = 1
    blocks.append(block)
print("allocation-ready", len(blocks), flush=True)
time.sleep(60)

创建 /etc/systemd/system/zy19-memory.service。例子中的解释器路径须与实验机实际路径一致。程序保留工作集六十秒，方便另一个终端读取控制组。不要以等待时间预测回收次数。

[Service]
Type=exec
ExecStart=/usr/bin/python3 /run/zy19-memory/allocate.py
MemoryAccounting=yes
MemoryHigh=32M
MemoryMax=96M

启动后，先读有效属性与当次日志。看到本轮 allocation-ready 才能把后面的读取解释为申请已经完成。另一个终端执行下列命令。cgroup 路径以管理器返回的值为准，读取者应在同一主机的相同 cgroup 命名空间中操作。

unit=zy19-memory.service
systemctl show "$unit" -p ActiveState -p MemoryCurrent \
  -p EffectiveMemoryHigh -p EffectiveMemoryMax -p ControlGroup
group=$(systemctl show "$unit" -p ControlGroup --value)
test -n "$group"
base="/sys/fs/cgroup$group"
for file in memory.current memory.high memory.max memory.events.local; do
  printf '\n%s\n' "$file"
  cat "$base/$file"
done
journalctl -b -u "$unit" --no-pager

安装定义后要重新加载管理器并显式启动这个实验单元，读取前后都记录时间。可以先做一次 high 为 infinity、max 保持九十六兆的基线，再在全新一趟中改回三十二兆。比较本轮 memory.events.local 的 high 事件及有效阈值，保留每趟开始时和申请后两次快照。如果程序没能打印就已退出，先读原错误和 OOM 相关事件，再判断解释器路径、资源限制或负载是否满足条件。

这里的独立预期是语义关系。看到 high 增加而没有 oom_kill，可以符合越界回收；high 值有效却未看到事件，须确认负载是否真的越界。不能硬性规定每趟有多少次 high 事件。若内核未提供所需字段，记录环境不支持该读取，按实际接口另行核对。本文没有 Linux 运行回执，没有启动单元或施加内存负载。练习后在这台隔离机停止单元、撤掉定义和脚本。

装好脚本与单元定义后，准备终端依次执行 systemctl daemon-reload 和 systemctl start zy19-memory.service。为每一趟设置同样的观测流程，配置变化后再次重新加载。不要把上次的日志标记当作本轮完成分配，应按本次启动时间取日志。

事件是计数，读到一个非零值并不足以指向当前阶段。保存申请前后两次读数及控制组身份，再计算同一组上的变化。进程很快退出时，控制组可能已不存在，事后才尝试打开文件就拿不到当时计数。提前安排读数采集，并让它保存在实验组之外，能为未知退出保留调查材料。若组被重建或计数重新开始，应分开解释两份快照，不能跨对象相减。这里没有执行采集；它规定的是下一次实验需要留下的最小证据。

进程退出不是唯一验收条件

假设程序能持有工作集，却因此慢到业务请求超时。进程仍然存活和控制项已经生效，都无法证明服务满足交付的响应合同。另行用受控请求记录响应和负载阶段，并把它与压力事件对齐。若应用主动放弃缓存，内存回落也可能发生而没有结束进程。判断运维动作时，明确自己要降低内存、维持服务响应，还是验证资源隔离，然后分别取证。

配置评审还可以保留一个负向解释。把负载缩到远低于 high，进程成功完成不会证明回收机制被检验。让正常对照证明程序能启动，再用压力场景观察资源事件。这个程序没有覆盖应用缓存、交换策略或全机内存耗尽，不能由它声称任何产品已可承受压力。

子服务把 MemoryMax 写大，就能越过父 slice 吗？

不能。systemd 报告的 EffectiveMemoryMax 会考虑单元与父 slice 更严格的限制，并受物理内存约束。子单元写九十六兆，父级的限制更紧，验收就不能只读子单元的配置文本。沿层级核对有效值和相关事件，再安排负载。这是主例新增的层级条件，主例假设隔离环境的有效边界符合预设，没有配置父 slice 对照。
