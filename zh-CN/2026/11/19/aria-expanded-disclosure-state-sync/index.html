aria-expanded 改成 true，为什么内容还没显示？

用普通按钮同步展开声明与内容显示，逐步检查第一次开合、再次展开和程序恢复。

正文

核心要点

  • 展开属性不替组件显示内容
  • 从同一状态渲染语义与可见性
  • 每次开合都核对按钮和面板

配送说明按钮已经有 aria-expanded。点下去，开发工具里显示 true，面板却依然隐藏。代码更新了声明，没有改变内容的可见条件。展开状态需要同时对齐按钮所说的情况和页面实际呈现的内容。对普通自定义折叠组件，属性不会替应用完成显示动作。

控件的状态与面板的显示分别有出口

W3C 的 Disclosure 模式包含一个按钮与受控的内容区域。按钮用 aria-expanded 告诉使用者当前是否展开。可选的 aria-controls 可以指向那片内容，帮助说明控制关系。它和 expanded 一样属于语义关系，不是自动为目标选择显示样式的命令。

对初始关闭的组件，按钮声明 false，目标处于隐藏状态。展开时两者一起改变：按钮声明 true，内容不再 hidden。再收起时回到 false 与隐藏。只写其中一处，会让读取状态和观察页面得到不同答案。颜色或箭头也不能替这两个出口证明完成。

如果标签文字保持「配送说明」，同一个按钮就能一直表示这个操作对象。可以另外为视觉显示当前开合，但不要仅通过更换图标告知状态。用户应能在使用原控件继续操作时，读到它所控制内容的当前情况。原生 button 自带键盘激活行为，没必要把普通容器重新包装成自造按钮。

这里选择用同一个布尔状态生成两份输出。它是应用在这一刻认定的展开值，render 把它写成属性并控制面板。调用者无须先从箭头方向反查状态，再决定面板应该显示什么。这样的顺序也更容易在恢复数据时核对初始值。

用同一入口做两轮开合

下列 HTML 页面不加载远程内容。配送说明本来就在文档里，只由一个按钮控制是否可见。按钮明确写 type，放进表单以后也不会因为省略类型而意外提交。两项初始声明与状态变量一致，随后每次点击都经过同一渲染函数。

<!doctype html>
<meta charset="utf-8">
<title>Delivery details</title>
<button id="toggle" type="button" aria-expanded="false" aria-controls="delivery">
  Delivery details
</button>
<div id="delivery" hidden>Standard delivery takes three days.</div>
<script>
const byId = document.getElementById.bind(document);
const button = byId('toggle');
const panel = byId('delivery');
let expanded = false;

function render() {
  button.setAttribute('aria-expanded', String(expanded));
  panel.hidden = !expanded;
}
button.onclick = () => {
  expanded = !expanded;
  render();
};
</script>

初次加载应读到按钮 false、面板 hidden。第一次激活后读 true、面板不隐藏。再激活则回到 false、hidden。继续做第二轮，以免初始化代码只支持第一次打开，却没有处理关闭以后再次显示。分别观察文本可读性与属性，不能只断言页面高度改变了。

按这些代码推导，两个出口应该同步。本文没有实际运行浏览器或辅助技术，也不提供读屏播报的固定句子。产品验收可用键盘聚焦按钮、激活、继续操作，再记录状态是否明确、内容是否可找到。自动化属性检查与真实辅助技术反馈需要各自留证。

找出只改一侧的真实入口

一个常见错误是点击回调写了属性，页面实际又由旧的显示类控制。此时即使 hidden 已经不在，CSS 仍让面板不可见。检查哪一条规则真正隐藏它，再决定只保留一个可解释的显示来源。属性的布尔值正确不说明所有样式已到位。

相反，某个框架先显示内容，按钮仍保留初始的 false，也能在视觉测试里看起来正常。故意制造这一份错误样本，确认你的测试会指出面板与属性不一致。完整记录应至少有目标实例、按钮状态、有效隐藏条件和本轮输入动作。

若按钮与面板之间还有异步加载，展开与加载完成也应分开。可以先呈现一个已经展开、内部还在加载的区域，让状态明确跟随组件合同。或者按产品选择等数据齐备才真正展开。无论哪种，别先说区域已经展开，页面却没有任何能让人理解的内容。

恢复上一次开合偏好时同样走 render。只给变量写 true，不会自动触发一个普通 JavaScript 函数。测试从关闭样本恢复到已展开时，可以在不点击按钮的情况下立刻查两个出口。这样才能检查恢复路径自身，避免用户下一次点击把旧状态修好之后才读数。

组件销毁或替换也要看引用是否仍有效。一个旧按钮还保留事件处理，实际面板已经换成另一份节点，操作可能继续修改脱离页面的对象。针对这一类页面更新，检查当前按钮控制的是本次实例，引用 ID 仍然唯一。静态样本正确并不能替框架生命周期作保证。

排查控制关系时，直接按按钮的目标标识找到节点，再确认那片区域就是屏幕上要打开的配送内容。名字相近的另一份面板会让检查误判。把目标标识临时改成不存在的值，按钮自身仍可能正常翻转；这一负例说明只查按钮属性会漏掉失效的关系。目标存在、关系正确和显示一致，应在同一次操作记录中分别核实。

两个按钮控制同一片区域，另一个也要更新吗？

要。这里新增第二只同样控制配送内容的有效按钮。点其中一个使区域展开后，另一只仍显示 false 就留下了相同的分歧。让两只控件都由同一个展开状态生成声明，渲染时更新所有控制器。不能让每个按钮只翻转自己的旧属性值。

验收这一条件可先用第一只打开，再用第二只关闭。每一步核对两个按钮的值和同一面板，目标共有三处读数。若第二只在激活后才补上自己的状态，第一次打开与第二次关闭之间的错误就可能被漏掉。读取要紧跟每次操作，而不只看最终关闭。

关于结构描述与普通提示的区别，可另看 aria-details 的结构化说明关系。
