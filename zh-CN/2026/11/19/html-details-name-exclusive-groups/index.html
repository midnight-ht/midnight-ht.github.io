两个 section 的 details 同名，为什么会互相关闭？

用四只 details 检查组内互斥与跨 section 独立，追踪同一树中 name 的实际作用范围。

正文

核心要点

  • 同树的相同非空名称建立排他组
  • section 不自动隔离组名
  • 同时验收组内关闭与跨组保留

配送和退货说明各放在一个 section。作者复用组件时，四只 details 都用了相同的 name。用户在退货区展开一项，配送区原先打开的说明也合上了。两个区块在视觉上独立，同一个树里的分组名称却把它们接成了同一组。

section 没有替 name 建一个命名空间

HTML 的 details 可以用非空 name 声明互斥组。同一树中，名称相同的元素属于一组，不要求它们相邻。section 是用来组织内容的元素，它没有把名称比较限制在自己的子树。若两个组件都写了 faq，浏览器仍然会按相同名称处理它们。

这种组最多允许一个成员打开。用户展开另一项时，浏览器会改变原来打开项的 open 属性。视觉变化来自内建排他规则，并不需要应用有一条跨区关闭脚本。诊断时如果只搜索自己写的事件监听器，可能查不到触发原因。

若配送区与退货区要各自保留一项，就给它们不同的组名。配送内部的两项仍共享 shipping，退货内部共享 returns。这体现的是内容关系，不是给每只 details 随机换一个字符串。若每项都用独立名字，原来组内一次只开一项的要求也会丢掉。

组名与文档中的身份标识也不是同一属性。id 在本例用于读取某只控件的状态，name 用于建立排他组。它们没有必要写成一样。重复 id 会造成查找歧义，重复组名则可能正是有意建立组；应分别验收。

四项分别检查组内和跨组

下面用两类说明做一个独立页面。初始都关闭。配送两项为同一组，退货两项为另一组。读数按钮记录四只 details 当前的 open 属性，避免只凭一个面板有没有变短判断当前哪些内容仍能访问。

<!doctype html>
<meta charset="utf-8">
<title>Two details groups</title>
<section>
  <h2>Shipping</h2>
  <details name="shipping" id="a"><summary>Standard</summary>Three days.</details>
  <details name="shipping" id="b"><summary>Express</summary>One day.</details>
</section>
<section>
  <h2>Returns</h2>
  <details name="returns" id="c"><summary>Unopened</summary>Return within 14 days.</details>
  <details name="returns" id="d"><summary>Damaged</summary>Contact support.</details>
</section>
<button id="read" type="button">Read open states</button>
<pre id="output"></pre>
<script>
const byId = document.getElementById.bind(document);
byId('read').onclick = () => {
  const state = ['a', 'b', 'c', 'd'].map(id => [id, byId(id).open]);
  byId('output').textContent = JSON.stringify(state);
};
</script>

先展开 Standard，读取时预期只有 a 为真。再展开 Express，预期 a 变假、b 为真。保持 b 打开，转到 Unopened 并展开，预期 b 和 c 同时为真。最后打开 Damaged，预期 c 关闭，b 仍保持打开。这几步分别检验组内互斥和跨组独立。

这是按照 HTML 规则设计的预期，本文没有运行浏览器或辅助技术。实际产品可用键盘到达各 summary 再激活，分别记录当前焦点、open 读数和内容可见性。不要从属性正确直接推断每个目标环境的提示方式已经通过。

可以另外做一份错误样本，只把 returns 改成 shipping，其余都不动。转到退货区打开时，配送那一项预期会合上。单一改动形成反例，能证明你的测试确实观察到了组名的作用，而不是偶然检查某个显示类。

复用组件时保留正确的组关系

页面有两个独立实例时，组名需要跟实例范围对应。例如同一份模板被应用到两个商品的配送说明，用户可能需要一边比较一边打开。由页面实例生成稳定的组名，再将它交给本组所有成员，比在模板里固定一个全站共享字符串更容易控制。

如果渲染顺序会变，不要用当前第几个元素去解释它属于哪个业务组。先由这份内容的关系确定组身份，再按实际显示建立元素。回归中同时保留成员文本和组名，才能看出显示位置变了，分组却仍然符合内容结构。

也需要检查隐藏面板里的实际内容。若用户正在两段材料之间比较，默认互斥可能并不合适。原生控件提供一次只开一个的能力，不能替产品决定任务一定只需要读一段。选择多个同时打开时，可以不建这个互斥组，并验证内容仍清楚组织。

作者还不能把同组的 details 嵌进另一只同组成员。HTML 对这种结构有明确的作者限制。若一个条目里还需要另一个折叠区，先确定它是不是独立层次，再采用另外的组身份或独立开合。不要指望名字相同会自动解释层次关系。

初始 HTML 也应遵守互斥约定。若服务端同时给同组多项写上 open，作者提供的是不应出现的初始组合。测试不能把浏览器随后修正标记的结果当作模板正确。先检查生成的原始属性，再做操作后的读数，能区分发布模板和交互代码各自负责的状态。

如果界面有记忆上次展开项的功能，应按组恢复一项，而不是独立恢复每项旧的布尔值。过去两个没有组关系的面板都开着，后来加了同名，逐项恢复就会触发浏览器的互斥处理。迁移时先确定新的组合同，再把旧数据转换成一个可解释的初始选择。

读数不依赖事件次数。连续操作可能合并通知，验收最终哪一项打开时，直接读取它的 open 更清楚。若产品还有观察 toggle 事件的代码，另外记录事件与内容的对应，别拿回调数替代当前状态。

name 设为空字符串，所有空名项会组成一组吗？

不会。这里新增的是空名称条件。组的定义需要双方都有 name，且值非空、相等并位于同一树。将四项都写成 name=""，不会靠这个值建立共享的互斥组。依次打开 Standard 和 Express，可以预期两项都保持打开。

这和每只控件仍有自己的展开状态可以同时成立。空名称没有提供组关系，浏览器仍会管理每只 details 自己的 open。测试应分别检查每项能否展开，以及另一项是否仍保留；不能仅因第一项成功打开，就认定排他已经取消或仍然存在。

若内容需要先隐藏并被页面内查找揭示，可另看 hidden until-found 的发现流程。
