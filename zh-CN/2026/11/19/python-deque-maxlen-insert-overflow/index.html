deque 满了，append 能继续，insert 为什么报错？

用独立有界 deque 对照两端追加、位置插入和批量左追加，核对成员身份、顺序和拒绝后的状态。

正文

核心要点

  • 端点追加满容器时淘汰另一端成员。
  • 位置插入超出 maxlen 时抛出 IndexError。
  • 批量左追加会反转输入元素在左端的先后。

有界 deque 已装满三条日志，append 第四条可以成功，改用 insert 却抛出 IndexError。maxlen 指定容量，具体怎么处理多出来的元素还取决于写入方法。端点追加会淘汰另一端的元素，位置插入超出容量则报错。

同一长度会藏住哪些变化

想象一个只显示最近三条活动的本地面板。A、B、C 依次进入缓存，窗口已经满了。再来 D，希望显示 B、C、D，丢掉最早的 A。这个需求可以接受淘汰，检查应确认留下的是哪三条。只断言长度仍然等于三，无法判断程序丢了 A，还是根本没接收 D。

如果另一个入口允许把记录放到中间，例如把 D 插到 A 后面，容量已满时应当丢哪条就不再显然。Python 的位置插入没有替你按“最旧”推断一条淘汰规则。它会在插入导致长度超过上界时抛出异常。对需要人工决定插入优先级的界面来说，拒绝或先做空间安排是应用责任。两个入口共用一个 maxlen 并不会因此拥有同一份溢出合同。

左右端点也有差别。右边追加会从左边淘汰，左边追加则从右边淘汰。所以从左边加入 D 时，结果是 D、A、B，原本最右边的 C 离开。如果业务把列表左侧定义为最新活动，这份顺序有意义；若仍把右边看成最新，就要检查调用者有没有在展示和写入时使用相反方向。数据结构知道端点，哪个端点表示新旧由应用定义。

每种操作从同样的三条记录开始

下面每次都新建容器，使结果只属于当前的写入操作。一个错误路径保留满容器，另一个正向控制则只放两条记录，确认位置插入本身能够工作。这里所有内容是单个进程中的假设标识，没有接入日志采集服务。

from collections import deque

def full():
    return deque("ABC", maxlen=3)

right = full()
right.append("D")
assert list(right) == ["B", "C", "D"]
left = full()
left.appendleft("D")
assert list(left) == ["D", "A", "B"]
middle = full()
try:
    middle.insert(1, "D")
except IndexError:
    assert list(middle) == ["A", "B", "C"]
else:
    raise AssertionError("full indexed insertion should fail")
space = deque("AC", maxlen=3)
space.insert(1, "D")
assert list(space) == ["A", "D", "C"]
batch = full()
batch.extendleft(["D", "E"])
assert list(batch) == ["E", "D", "A"]
print("right BCD; left DAB; insert rejected; room ADC; batch EDA")

右追加留下 B、C、D，左追加留下 D、A、B。满容器的中间插入进入异常分支，而且已有 A、B、C 仍完整保留。只有两条记录的正向控制得到 A、D、C。四条断言共同说明，问题出在容量与操作的组合。只跑一个满容器的错误例子，可能让人误以为 deque 根本不能插入中间；只跑空容器则完全碰不到这个分支。

异常捕获必须仅围住那次预期的插入。如果把建表、读取或后面的业务处理都放进同一段 try，再把碰到的任何 IndexError 都解释为队列已满，就可能掩盖另一个索引错误。例子检查异常发生后仍有哪些成员，也防止调用者先删一条旧数据，再因后续错误把丢失的记录当作正常淘汰。

完整状态还比总长度多提供一份保护。假设错误实现遇到 D 直接忽略，长度检查仍会通过。再假设它淘汰了 C，最终数量也正确，窗口却已违背最近活动的合同。因此应该对代表性的标识写出完整顺序。若活动正文可以相同，测试使用独立编号，避免把两条内容相同的记录误认为同一项。

满了以后，应用要选择哪一种接收政策

最近活动缓存适合自动丢弃另一端。只要消费者明确接受窗口之外的数据不再保留，端点追加就能表达这个选择。需要保留所有尚未处理工作的系统，则不能仅因为容量固定、操作又快，就把同样的容器当作无损任务队列。消费者还没来得及取出 A，下一次追加已经能让它消失。应该按系统要求选择等待、明确拒绝、扩容或另存等政策，并给每种政策留出可观察结果。

对人工排序入口，可以先检查容量并提示用户删除或替换哪一条。若确实有“插到中间同时淘汰最旧项”的功能，要把被淘汰者身份写进操作合同，自己实现后再比较整份列表。不要依赖某次异常之后的补救代码猜测哪个元素已被删。这个样例没有实现替换入口，也没有检查多个线程同时决定空间时的一致性。

面板如果还要解释一条旧记录去了哪里，可以在应用的更新记录里保存本次接收者与淘汰者编号。例如这次追加 D，同时记录 A 因窗口滚动离开；位置插入被拒时，则明确没有接收 D，也没有淘汰旧记录。观察数据结构本身已经足够验证这个小夹具，审计这种更强需求则要另行实现。把这两种证据混用，会让用户把窗口之外的消失误解为后台业务已完成。

服务级验收可以从三个待办开始，让消费者故意停住，再写入第四项，核对应该发生的是拒绝、等待还是持久化，而不是仅看缓存有没有越界。恢复消费者后，检查四个标识分别到哪里去了。本站的队列完成计数关注另一类确认责任；在这类有界容器里，需要先确认工作本身会不会在还未消费前被窗口淘汰。当前夹具只验证端点和位置操作的本地状态。

extendleft 的两个元素会按输入顺序出现在左边吗？

从 A、B、C 再单独开始，extendleft 接收 D、E，会依次把每项加到左端。先得到 D、A、B，再得到 E、D、A，所以结果中 E 在 D 前面。输入顺序在左端连续追加中被反过来了，同时每一步都可能淘汰右端元素。夹具保留这一条完整预期，不能把它简化为“前面增加了两个”。如果业务要求左侧新批次仍按 D、E 展示，应先明确批次顺序，并用相反的迭代方向进行左追加，另验边界处留下哪条旧记录。
