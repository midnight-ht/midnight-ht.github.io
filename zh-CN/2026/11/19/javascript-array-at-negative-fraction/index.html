at(-0.5) 为什么读到第一项，而不是最后一项？

固定三项数组，对照负整数、小负数和越界位置，先检查参数取整，再检查返回的行。

正文

核心要点

  • at 先把位置转换为整数
  • 小负数可转换成负零并读取首项
  • 语言转换与位置字段合同分别验收

预览列表的位置输入收到负零点五。开发者以为负数都该从末尾读，页面却显示了第一行 A。数组没有反转，也没有丢项。读取之前，at 会先把位置转换为整数。负零点五经过这一步成为负零，后面的负位置换算便不会像负一那样取到最后一行。

先转换，再决定从哪一头读

假设列表固定为 A、B、C 三项。读取零得到 A，读取负一得到 C，这是常见的正向与倒向用法。但索引参数可以经过转换，并非按调用者写下的数值直接寻找一条记录。ECMAScript 将参数交给 ToIntegerOrInfinity，然后才判断位置是否小于零。

对普通有限小数，这个转换去掉小数部分，保留相应符号。负一点五变成负一，因此得到 C。负零点五则变成负零。在后面的比较里，它满足大于等于零的条件，选择零号位置。这里不用先拿数组长度加上原来的小数，也没有向负无穷取整。

因此想验收倒序读取，不应只拿负一测试。输入框若允许小数，或者配置合并后传入了小数，同一个接口可以走出另外的结果。语言能做这个转换，不代表产品已经允许半条记录这种输入。界面如果只接受整数，就应在进入数组读取前按自己的合同检查。

转换后得到的位置若落在零到长度减一之外，方法返回 undefined。三项数组读取负四，换算后仍在范围外。这个结果不会自动给界面一条错误说明。调用者还要决定此处应该清空预览、保留上一次记录，还是提示位置无效，不能让过期的显示被误当作本次结果。

同一列表的五条断言

下面的脚本使用固定稠密数组。五个位置分别覆盖零、小负数、负整数、负小数和超范围。结果预先写出，既能看到首行也能看到末行。代码不读取表单或调用服务，测试的是标准方法在这一组普通输入上的行为。

import {deepEqual} from 'node:assert/strict';

const rows = ['A', 'B', 'C'];
const cases = [[0, 'A'], [-0.5, 'A'], [-1, 'C'],
               [-1.5, 'C'], [-4, undefined]];
for (const [position, expected] of cases) {
  deepEqual(rows.at(position), expected);
}
console.log('Integer, fractional, negative, and out-of-range cases passed.');

在本地 Node 中，五条断言通过。零和负零点五都读取 A；负一和负一点五都读取 C；负四得到 undefined。这里记录的是值，不从输出 A 反推它曾经做过哪种业务选择。真实组件若记录了转换前位置和当次结果，才有证据追查用户输入经过哪些处理。

验收位置字段时，可以在控件入口再用这些值查一遍。若合同要求只能填整数，负零点五就应在读数组之前被拒绝，而不是把第一行成功显示当成允许。若产品有意接受小数并使用截断，提示文案也应解释截断后的有效位置。两种合同要用不同预期，不能同一用例里混着判断。

有些组件会先把文本用 parseInt 取前缀，再把结果交给 at。这样的入口已经丢了一部分原输入信息。若当次列表显示了 A，只检查 at 的断言不能说明文本格式原来合法。把解析和数组访问分开记录，能避免修位置换算时继续掩盖文本校验的故障。

不把末尾读取当成完整的列表合同

数组长度会影响负位置。保存一个负一再在未来读取，拿到的是未来那个列表的末项。若业务想选定当前最后一条记录，应保存它的稳定编号。只存相对位置后又新增了一行，选择改变可能符合语言规则，却违背用户原本想看的那一项。

所以回归中还可以记录本次使用的列表版本或成员编号。初始 A、B、C 读取末项是 C，新增 D 后同样位置会读到 D。这个变化本身不证明读取函数错误。实际想保持对象身份的组件，应先确定数据集再查成员，或在列表变化时明确取消旧选择。

同样也别把位置零永远理解为第一条业务数据。如果上游在列表前加了加载占位或分组标题，数组第一项的意义已经变化。测试应使用实际传给方法的集合，并核对结果对应的数据对象。语言位置和界面的第几条可操作记录需要在组件边界上对齐。

对于空列表，所有普通数值位置都不能得到成员。界面应有独立的无数据路径。仅用非空三项演示，可以解释负小数的行为，不能替产品证明空列表时没有残留预览。检查输入集合、读取位置和最终可见结果，三处都保留才容易定位。

排查时把一次读取产生的三个值放在同一条记录里：原始位置、实际数组长度和返回的成员编号。列表更新之后再收集一条，避免把第一次的输入与第二次的结果拼成错误推论。若输入要先拒绝小数，记录拒绝发生在何处，就不必再用显示某一项来解释无效请求。

读回 undefined，就能确定这一项不存在吗？

不能。现在加入主例未用过的内容类型。数组在有效位置存着显式 undefined 时，at 会读到这个值。数组在某个位置没有自身属性时，也可能得到同样的结果。单靠返回值无法区分明确存了一个空值，还是原来没有那项属性。

如果合同需要这种区别，结合实际长度与属性存在性读取。对普通无继承数字属性的数组，可以用 Object.hasOwn 检查那个有效索引。若仍允许原型上的数字属性，又是另一层输入条件。不要从相同的 undefined 输出推断这些结构都一致。

若你的问题是集合为空但每项校验仍通过，可另看 every 的空数组与稀疏输入。
