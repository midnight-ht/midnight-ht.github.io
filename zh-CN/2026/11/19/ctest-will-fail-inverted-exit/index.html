进程返回零，CTest 为什么把测试判成失败？

对照 CTest 的反转与普通正常退出规则，并说明为什么业务负向测试仍需核对错误身份。

正文

核心要点

  • WILL_FAIL 反转正常零和非零判据。
  • 预期拒绝需要核对实际错误原因。
  • 运行器结果与进程返回分开记录。

测试进程正常返回零，CTest 也可能把它判成失败。启用 WILL_FAIL 后，正常退出的零与非零分类被反转。一个本该拒绝输入的负向测试若突然接受输入，运行器就需要把这次意外成功显出来。

先给这项测试一个确切的任务。例如命令行程序收到缺少必填项的配置，应当报错并退出非零。负向检查期待拒绝，如果程序恢复成正常零退出，这份输入就没有被按约定拦下。这与把某个专用退出值归成未运行的跳过政策不同。这里测试已经执行，验收要看它有没有按预期拒绝输入。

用同一工具构造反转矩阵

保存以下 CMakeLists.txt。项目不需要编译器，测试命令直接使用配置阶段找到的 CMake。它的 true 与 false 子命令分别正常返回零和一。两条负向测试都设了 WILL_FAIL，另留一条普通成功作为正向对照。这样可以单独判断属性是否参与，以及整个测试运行器是否能正常工作。

cmake_minimum_required(VERSION 3.20)
project(InvertedExit NONE)
enable_testing()
add_test(NAME expected_rejection COMMAND "${CMAKE_COMMAND}" -E false)
add_test(NAME unexpected_acceptance COMMAND "${CMAKE_COMMAND}" -E true)
set_tests_properties(expected_rejection unexpected_acceptance
                     PROPERTIES WILL_FAIL TRUE)
add_test(NAME ordinary_success COMMAND "${CMAKE_COMMAND}" -E true)

接着从同一源目录运行下面的脚本。每次只选择一个测试，把 CTest 自己的退出值保存下来，再与这个运行器实验的预期相比。配置里程序返回值和外层 CTest 返回值各有含义，不能把它们混写为同一条“退出码”。

set -eu
work=$(mktemp -d)
trap 'rm -r "$work"' EXIT
ctest --version
cmake -S . -B "$work/build"
check() {
  status=0
  ctest --test-dir "$work/build" -R "^$1$" --output-on-failure || status=$?
  printf 'test=%s runner_exit=%s\n' "$1" "$status"
  test "$status" -eq "$2"
}
check expected_rejection 0
check unexpected_acceptance 8
check ordinary_success 0

本地 CTest 4.2.3 执行结果如下。expected_rejection 的进程正常返回一，CTest 将它判成 Passed，外层退出零。unexpected_acceptance 的进程返回零，运行器判成 Failed，实测外层退出八。ordinary_success 同样进程返回零，但没有反转属性，因此 Passed、外层退出零。脚本三项断言全通过。八只作为本版本这条实验命令的观察值，正式收集器应保留实际值和单项分类，不把它当作进程失败的原因。WILL_FAIL 属性定义

普通成功这一项可以揭露一个配置遗漏。假如第二条的属性拼写或目标名配错，零退出的用例也许会同普通成功一样通过。只跑预期拒绝的用例，很难确认自己真正设置了哪个条件。把“应拒绝”和“意外接受”两边都试过，才知道门禁能同时辨认原来的拒绝与后来改变的行为。本例用固定返回值证明运行器策略，未执行产品程序或真正的配置校验。

非零也需要一份错误身份

这项属性只反转退出判据，并不理解程序为何返回非零。假设校验工具本应处理缺少字段的输入，却在读取文件时发现路径不存在。它仍然可能以普通非零结束，反转后得到通过。数据错误被拒绝的承诺并没有被验证。给实际负向测试再加一份独立信息，例如专用的错误分类和对应字段。先保证程序读到了准备好的输入，再检查拒绝属于期望的规则，最后检查运行器如何报告。

可以让一个受控样例分别提供三份配置，合法、缺必填、文件本身不存在。前两份用来确认业务校验的两边，第三份确认包装器不会把环境错误当成目标拒绝。包装脚本若要代收程序结果，遇到不符的错误应以自己的失败路径退出，并在 CTest 中采用与该脚本职责一致的属性。最直接的方案是让验证脚本自己判断错误身份，检查完全符合就返回零，作为普通 CTest 测试。此时成功条件写在脚本中，不再需要用 WILL_FAIL 反转它。本文只运行了 CMake 工具的固定返回值，没有运行这一业务包装器。

选择两种写法时，可以问负责测试的人在哪里最容易看懂合同。简单命令明确用正常非零表达目标拒绝，直接反转方便。若多个失败来源都可能产生非零，显式写一个验证结果的程序通常更容易表达哪个错误才算符合预期。保留原进程输出和验证程序的判断，后续看到通过时才能核对程序确实走到了业务拒绝。单纯把任意错误都归“预期失败”，会给缺依赖或坏环境留出假通过的空间。

发布交接也要知道哪些测试应用了这个策略。报告中 Passed 可能来自正常成功，也可能来自正常非零被反转，两者都符合各自定义。附上测试名、有效属性和被测输入身份，可以让审核者在不猜配置的情况下还原。若有人提出移除反转，先重做合法输入和拒绝输入的对照，确认是产品行为变了，还是任务已切换成验证脚本。不要只为让某条回执变绿就修改成功定义。

错误身份核对还应指向同一份输入。假如日志收集器拿了上一轮缺字段的消息，却配上这一轮文件打不开的退出值，两个片段都真实，也不能共同证明本次拒绝正确。为独立执行保留运行标识与输入清单，让诊断、原进程返回和验证程序的判断属于同一轮。接手人发现不一致时应重跑这一对输入，而不是用更宽的文本匹配去凑出通过。这个收集器情景尚未执行。

测试超时也会反转成通过吗？

不会。超出 TIMEOUT 的测试仍然失败。官方也说明，段错误、信号中止、堆错误等系统级失败即使启用了 WILL_FAIL，也可能判失败。正常非零是主实验的输入，不能由它推导所有异常都能被反转。接到超时报告时仍要查看有效时限与运行中的程序，并给重现留独立记录。本文没有模拟超时、崩溃或信号，边界来自属性文档。
