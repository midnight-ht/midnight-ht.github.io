Promise.resolve(load()) 为什么接不住 load 的同步抛错？

先查同步抛错发生在参数求值还是适配器内部，再用固定错误和事件数组验证 Promise.try 的调用边界。

正文

核心要点

  • resolve 接收值之前参数已经求值
  • try 把回调调用纳入返回的 Promise
  • 同步调用和后续反应的时序分开测试

插件接口有时返回普通值，有时返回 Promise。调用方把它写成 Promise.resolve(load())，期待后面统一接住失败。某个插件同步抛错时，程序却在生成这份 Promise 之前就跳了出去。要统一的是调用过程和返回结果，不能只把调用已经产生的值交给解析方法。

抛错发生在谁的调用里面

在这个表达式中，JavaScript 必须先求出 load() 的结果，才能将它作为参数传给 resolve。如果求值阶段抛错，resolve 根本没拿到那个结果。后面追加 catch 也没有一份由这次表达式返回的 Promise 可以处理。同步异常仍从原来的调用位置向外传播。

Promise.try 接收的是函数以及要传给它的参数。方法内部调用该函数，普通返回值交给 Promise 的解析过程；调用抛错则交给拒绝过程。这里把 load 本身传进去，调用被纳入了这个边界。结果是同一只错误对象通过返回的拒绝 Promise 传出。

这个方法并不承诺把每个操作拖到稍后执行。回调由 try 同步调用。如果函数在开始阶段写日志或修改状态，这些动作在方法返回之前已经发生。后续履约或拒绝反应仍走 Promise 的工作机制，不能由回调执行时机推出 catch 会在同一行里同步执行。

另一种常见写法是先有一份已解决的 Promise，再在 then 里调用 load。它同样能让回调内的抛错成为拒绝，但回调等到对应的工作执行。两种适配可以产生相同的最终值，却有不同的开始时刻。迁移时先确认项目是否依赖立即开始的副作用。

把错误身份和执行顺序都留下

下面的脚本只用固定函数。一只函数总抛同一个错误，另一次返回四十二。最后用事件列表比较 try 回调和 then 回调。没有文件读取、网络请求或重试。等待发生在最后，确保实验结束后没有漏掉已经创建的工作。

import {strictEqual as equal, deepEqual, rejects} from 'node:assert';

const failure = new Error('fixture load failed');
function load() { throw failure; }

let caught;
try {
  Promise.resolve(load());
} catch (error) {
  caught = error;
}
equal(caught, failure);

await rejects(Promise.try(load), error => error === failure);
equal(await Promise.try(() => 42), 42);
const events = [];
const immediate = Promise.try(() => events.push('try callback'));
events.push('returned');
const deferred = Promise.resolve().then(() => events.push('then callback'));
deepEqual(events, ['try callback', 'returned']);
await Promise.all([immediate, deferred]);
deepEqual(events, ['try callback', 'returned', 'then callback']);
console.log('Throw identity, return value, and invocation order passed.');

本地 Node 的断言通过。直接求值表达式的异常由外层 try/catch 接住；将函数交给 Promise.try 后，拒绝原因仍是同一个错误对象。正常返回值是四十二。时序数组在同步阶段包含 try callback 和 returned，等待后才增加 then callback。

这些检查分别守住三件事：谁处理失败，成功值是否被保留，以及动作何时开始。只测最后能 await 到四十二，会放过同步异常逃出适配边界。只测错误类型，会漏掉重建错误后丢失原始身份。事件顺序则能发现将同步入口改成延迟执行的行为变更。

如果插件本来返回一份 Promise，解析过程会跟随它的结果。适配器返回自己的 Promise 不代表插件动作已完成。调用方仍需 await 实际成功，或在拒绝路径做相应收尾。包装返回通道没有替具体操作创造取消、回滚或自动重试规则。

适配入口不改变插件的其余合同

有些对象方法依赖接收者读取配置，提取成单独函数以后会失去原有调用关系。可以在传入的函数内部按对象方法方式调用。try 提供的是捕获调用完成状态的入口，不会推断 load 原来属于哪一个实例。两个不同配置实例也需要各自测试。

同样，普通值和 Promise 返回可以共用等待方式，却不表示成功的内容形状相同。一个插件返回行数组，另一个返回包含分页信息的对象，适配完成后仍需按正式接口判断。若只是因为 await 没报错就让下游继续读取行数，类型问题会在另一个位置暴露。

部署前检查项目实际运行环境。当前 Node 实跑确认这一版本支持该方法，不能外推到所有旧浏览器。若项目已有相同语义的适配器，可以保留已测试入口；若改用新的方法，就把现有普通返回、异步返回与同步抛错用例都跑一轮。不要从方法名称推断行为完全相同。

如果真正的目标是让入口一次性捕获所有准备步骤，可以把输入读取、必要校验和插件调用放在明确的回调体里，并分别保留是哪一步失败。统一返回 Promise 之后不必把所有错误都变成相同的一句失败文案。缺少输入和插件服务拒绝，需要的修正方式可能不同。

测试还可使用一个返回拒绝 Promise 的插件作为第三类完成方式。对照时使用已有的固定错误，确认同步抛错与异步拒绝最终都归到调用方设计的失败处理，但记录各自起点。将两种结果统一等待，不要求抹掉问题原本来自哪一个步骤。本文的运行脚本只验证同步抛错、普通值和时序，新增异步路径属于项目回归建议。

还有一个应该独立保护的输入是重复调用。每次 try 都会实际调用传入函数，不能将它当成缓存已运行结果的容器。如果插件有写入行为，一次失败后再执行会产生另一轮工作。要让使用者恢复，先按业务合同判断这轮是否允许重试，并保留各轮的操作身份。

传入参数本身抛错，也会变成拒绝吗？

不一定。新条件是参数表达式先执行，例如 Promise.try(load, makeInput())。如果 makeInput 同步抛错，JavaScript 在调用 try 之前就无法求得参数。这次异常没有进入方法内部的回调调用，不能靠它返回拒绝来承接。

若希望连输入构造也在统一的边界中，可以把整步放在回调里，让它调用 load(makeInput())。这改变了错误被捕获的位置，依旧需要保留同一输入失败的实际用例。两种写法表面上都出现 try，真正的判断是哪个调用阶段包含了可能抛错的动作。

关于旧回调接口还需要怎样保存接收者，可另读 promisify 的对象方法和自定义转换合同。
