asdict 转成字典，为什么字段对象也换了？

用列表修改和嵌套负责人字段，对照 dataclasses.asdict 的递归转换与 fields/getattr 的浅层投影。

正文

核心要点

  • asdict 递归转换容器和数据类，其他对象使用 deepcopy。
  • 浅层字段投影保留原字段引用。
  • 转换成字典后，传输编码能力仍需另外验收。

把数据类交给 asdict，得到的字典里确实有 items 字段，但修改其中的列表没有改变原对象。dataclasses.asdict 会递归转换数据类和容器，并深复制其他对象。若调用者只想得到字段名与原字段引用，需要另外构造浅层投影。

外层变成字典，内部值从哪里来

假设一次后台任务用 Packet 保存条目列表和负责人。条目是可变列表，负责人又是一个带名字的数据类。把任务交给日志系统时，调用者可能希望得到独立的数据；交给同进程的编辑器时，又可能希望编辑器直接操作当前列表。两种场景外层都能用字典表达，可是内部是否仍指向原来的对象，会决定后续修改到底落在哪里。

asdict 不只遍历最外层字段。它会继续走进数据类、字典、列表和元组，把嵌套数据类变为字典；对于其他对象，使用 deepcopy。结果因此不能当成一层换了名字的引用表。例子中的列表会成为另一个列表，负责人则由 Owner 实例变成含 name 的字典。调用者即使看见相同名字和相同条目，也仍需核对类型与身份。

标准库文档也给出浅层做法：枚举 fields，从原对象取得每个字段值，然后构造新字典。外层字典是新的，字段值仍是原来的引用。所以新增一个顶层键不会凭空给数据类加字段，但往 items 引用的列表里追加，就会影响原对象。用一句“复制了”无法同时描述这两层不同关系，接口说明最好把外层结构和内部值的所有权都写清。

用两条修改路径分别观察来源

下面的数据只有一个条目与一个负责人。先比较转换结果的结构，再检查关键身份，最后各修改一个列表。执行时没有数据库、文件对象或网络资源，观察只属于这些标准库数据结构。

from dataclasses import asdict, dataclass, fields

@dataclass
class Owner:
    name: str

@dataclass
class Packet:
    items: list[str]
    owner: Owner

source = Packet(["A"], Owner("Lin"))
deep = asdict(source)
shallow = {f.name: getattr(source, f.name) for f in fields(source)}
assert deep == {"items": ["A"], "owner": {"name": "Lin"}}
assert deep["items"] is not source.items
assert shallow["items"] is source.items
assert shallow["owner"] is source.owner
deep["items"].append("B")
assert source.items == ["A"]
shallow["items"].append("C")
assert source.items == ["A", "C"]
assert deep["items"] == ["A", "B"]
print("asdict detached list; field projection retained references")

深转换的初始值是 items 为 A、owner 为含名字的字典。浅层投影仍然拿着原来的列表与负责人实例。给深转换列表增加 B 后，源列表保持只有 A；给浅层列表增加 C 后，源列表变成 A、C，而深转换列表仍是 A、B。最后一条检查使两个结果不能仅凭相同初值误过，实际修改确实去了不同位置。

这里没有只用相等来推断独立性。两个不同列表最初可以相等，一条浅层投影也能打印成与深转换很接近的内容。is 检查告诉读者哪两个对象相同，修改后的值则告诉读者这种共享实际怎样影响程序。如果测试只比较刚生成时的字典，它可能在两种实现之间任意切换，直到编辑器更新任务时才发现改到了副本。

负责人字段提供另一个控制。如果消费端期待 Owner 的方法或属性，深转换得到字典之后，原来的访问合同已经变化。浅层投影保持这个实例。若消费者只需要负责人名字，应用可以主动导出一个明确的字符串字段，减少对原对象内部形状的依赖。这个选择由接收者需要什么来定，不能从输出是否能打印推断。

选择快照还是同一份可变状态

为日志或外部传输准备内容时，独立投影可以减少后续修改让已准备数据发生变化的机会。不过 asdict 的递归复制本身没有替应用建立跨字段的一致性边界。如果另一个线程同时改列表与负责人，应用还需要选择什么时候读取、是否协调以及保存哪版内容。这份单线程样例没有验证并行修改，也没有测量复制成本。

如果编辑器要接着操作原任务，浅层字段投影可以保留引用，但也要让接收者知道修改会影响谁。保存到缓存或交给不熟悉的调用者后，共享列表可能在另一个入口被改动。可以给只读消费者导出必要的不可变值，或按合同主动建立快照。试图用浅层字典让所有内部对象都变成只读，并不会成功。

还有一种不显眼的故障是先深转换，再指望修改转换结果作为任务更新。程序可能正常返回，编辑界面也显示了改后条目，原任务却没变化。对更新入口的验收，应从实际源对象重新读一次，确认 C 等预期标识出现。对于必须隔离的快照接口，则反过来修改导出结果，要求源保持不变。两条合同各留一份方向明确的断言，更容易发现换错工具。

本站资源转移后的所有权介绍另一个对象交接问题。这里没有把原对象变成不可使用的资源，也没有浏览器参与；源与浅层投影的引用仍然可能被同一进程同时持有。运行记录仅验证所列类型与列表内容，不能把它扩大为任意资源都可安全复制。

asdict 得到字典，就能直接 JSON 编码吗？

增加一个自定义类型的字段时，递归处理可以把这个对象复制成另一个同类对象，仍然没有把它变成 JSON 支持的原生值。直接 json.dumps 可能抛出 TypeError。若消费协议只接受字符串或数字，应显式选择该对象的哪些字段可以导出，再分别检查格式与业务内容。这个自定义字段变体没有执行；本页执行的例子只有字符串、列表与数据类。接受方需要 JSON 时，把可编码性作为额外的测试入口，避免把转换字典这一步当成整份传输合同已经通过。
