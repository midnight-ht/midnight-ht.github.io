Kubernetes根文件系统只读，挂载目录为什么仍可写？

用完整Pod对照根路径与emptyDir写入，分开根层只读、卷挂载和运行身份，再检查共享写者与数据生命周期。

正文

核心要点

  • 只读根不自动使独立挂载卷只读。
  • 属主权限、挂载模式与内容完整性分别判断。
  • 单个消费者只读不表示同卷不存在其他写者。

Kubernetes 的 readOnlyRootFilesystem 让容器根文件系统只读，不会自动把独立挂载卷都变成只读。根路径写入失败、挂载目录写入成功可以同时成立。先辨认实际路径落在哪个挂载上，再分别检查挂载访问设置与进程身份，不能把这个字段理解成整个容器没有任何可写位置。

根层限制与挂载访问是两份配置

Kubernetes 安全上下文指南将 readOnlyRootFilesystem 定义为以只读方式挂载容器根文件系统。卷文档则说明独立存储如何挂入容器。本文于二〇二六年十一月一日核对当前页面；导航中的版本入口不是固定发布版证明，没有连接集群或执行写入测试。

程序看到统一的目录树，但不同路径可以由不同文件系统提供。镜像根层里的程序文件与挂在 /work 的卷，不因为路径都以斜杠开头就共享一个写入开关。排障应记录绝对路径、卷名、挂载点及访问模式，而不是只记录安全字段已经设为 true。

身份权限又是另一层。一个可写挂载仍可能因为目录属主、组或权限位拒绝当前进程；一个权限位允许写入的根层路径，也可能被只读挂载拒绝。修改属主不能把只读文件系统变可写，改挂载模式也不能自动解决所有身份权限。失败表面相似，修复位置却不同。

一个隔离根层与卷的完整配置

下面是未经执行的教学清单，包含独立命名空间与单个 Pod。busybox 镜像用于 shell 和文件操作，需在测试环境确认可取得。为了让普通属主权限不抢先解释根路径失败，练习明确用 UID 零；这不是生产安全基线，也不要求绕过集群原有的准入政策。若环境禁止这一身份，应保留拒绝结果，另选获准的测试方法。

apiVersion: v1
kind: Namespace
metadata:
  name: readonly-root-demo
---
apiVersion: v1
kind: Pod
metadata:
  name: root-versus-volume
  namespace: readonly-root-demo
spec:
  restartPolicy: Never
  containers:
    - name: probe
      image: busybox:1.37
      securityContext:
        runAsUser: 0
        readOnlyRootFilesystem: true
      command: ["sh", "-c"]
      args:
        - |
          if touch /root-proof; then
            echo 'unexpected root write'
            exit 1
          else
            echo 'root write rejected; inspect the actual error'
          fi
          printf 'training marker\n' > /work/proof
          cat /work/proof
      volumeMounts:
        - name: scratch
          mountPath: /work
  volumes:
    - name: scratch
      emptyDir: {}

脚本让第一个预期失败留在条件分支里，不会因此跳过卷写入对照。应查看实际错误是否指向只读文件系统，并检查 /work 的写入与读取。仅看到第一个操作非零，不够确定原因；镜像缺少命令、路径设置不对或另有安全控制，都需要按原始错误说明。

这份清单没有创建回执。若 Pod 在镜像拉取或准入就失败，后面的文件操作根本没有发生，不能把对象失败当成根层写入被拒的证据。也不要从日志里有一个训练标记就宣称整个文件系统安全；它最多支持对应路径和运行条件下那一次操作。

怎样证明失败确实来自根层只读？

可在另一个可丢弃Pod建立基线：保持镜像、命令、运行身份和卷不变，只把根层只读设置关闭，再比较同一训练路径的写入。若关闭后仍失败，就应调查命令、身份或其他限制；不能把第一次失败全部归功于只读根。这个基线会改变练习对象的可写范围，因此只在获准测试条件下安排，不修改真实应用来追求一个成功标记。

随后把根层恢复只读，只改变卷挂载访问模式。这样有三份可区分记录：根层允许且卷允许、根层拒绝且卷允许、根层拒绝且卷也拒绝。每份保存最终对象、实际挂载和原始错误，才能说明两项控制各自限制了哪一个路径。对象没运行时不要填入预期结果，也不要用另一个Pod的日志替代当前对象。

应用需要写入时，应开放哪一块？

先列真实写入清单：临时文件、缓存、上传中间件、锁文件或应用生成的状态分别放在哪里。静态程序与配置未必需要写权限，临时状态则可以有明确的专用目录。只读根能帮助发现应用偷偷写回程序目录的行为，但不能替维护者决定哪些可变数据必须保留。

如果仅需要可丢弃的暂存，独立 emptyDir 可以表达这种用途。若文件是唯一结果或用户原始上传，就应另行设计跨 Pod 保存与确认点。emptyDir 的 Pod 生命周期解释为什么容器重启时还在，不等于替换 Pod 后仍有。能够写入与能够恢复是两个不同验收题。

真实部署还应以目标非特权身份检查卷权限，而不是把教学里的 UID 零复制过去解决全部错误。可以通过适当的目录准备、组策略或存储平台能力提供必要权限，但要核对实际实现。对所有路径递归开放写入会扩大影响面，并没有解释应用究竟需要改哪些数据。

给volumeMount加readOnly，会发生什么对照？

可以在另一个测试 Pod 中保留相同根层设置，只将 scratch 挂载标记为 readOnly，再观察 /work 的写入。该对照的意图是区分卷挂载限制与根层限制，不是通过一次测试认证所有卷类型。应保存两份实际配置、挂载状态与命令错误，确认除此之外没有更换身份或存储内容。

只读也不等于内容永久不变。卷可能存在其他写者，或由平台更新来源；某个容器不能通过自己的挂载写入，并不证明观察到的字节永远不会变化。需要配置不可变性或完整性时，应另行定义来源、版本与验证，而不把挂载属性当成内容签名。

Docker运行用户与复制属主讨论相邻的身份权限问题。本题增加的是挂载边界：同一进程面对多个路径时，访问模式可能不同。排障记录把身份、属主与挂载只读状态并列，才能选择修改镜像、存储设置还是应用路径。

一个只读挂载能限制同卷的其他容器吗？

不能把本消费者的挂载意图扩大成全卷的全局写入禁令。应逐个检查共享该卷的容器、挂载点和外部写入者；另一个获准可写的消费者仍可能改变内容。若需求是只有一个写者或所有消费者都只读，需要在整体卷设计与权限配置中明确表达。

拟议验收至少比较根层路径、可写卷路径、只读卷路径与目标运行身份，分别记录允许和拒绝；同时让应用运行一次真正需要临时写入的任务，确认它没有退回镜像目录。本文未执行这些检查，没有集群安全通过或业务完成的结论。只读根是有明确范围的控制，写入清单、卷权限与数据生命周期仍需各自成立。
