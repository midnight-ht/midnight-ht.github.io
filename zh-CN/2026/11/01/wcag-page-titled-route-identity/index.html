WCAG页面标题：h1已更新，标签页为何还叫旧页面？

分开文档标题与页内标题，用完整本地视图样本检查动态命名、迟到响应和脱离正文的识别。

正文

核心要点

  • 页面标题要描述主题或目的，不能只确认非空。
  • 视图身份与标题更新要采用同一份归属判断。
  • 标题语义正确不等于实际通知或焦点管理已验证。

正文已经切到材料清单，标签页却仍叫申请首页。先分开文档标题与页内标题，再检查当前视图能否在正文之外被识别。更新h1只改变页面里的一个标题，不会自动完成标签页、历史列表和书签需要的命名。

两个标题面对不同的上下文

WCAG2.2页面标题理解文档解释2.4.2、A级要求：网页有描述主题或目的的标题。理解文档还讨论单页应用：不同视图动态改变内容时，标题也应反映当前主题。这里不能只检查head里有一个非空字符串；一个始终叫“首页”的申请详情页，存在文字却未必描述当前内容。

HTML的title定义强调文档脱离上下文后仍应能够识别。首个页内标题可以依赖周围内容，文档名称却常要独自出现在其他地方。例如页面里写“材料清单”，旁边有助学申请说明，读者知道是哪件事；历史列表单独出现“材料清单”时，可能需要额外服务语境。

因此，两者不要求逐字相同。假设h1为“核对申请”，文档标题可以是“核对助学申请｜教学服务”。这是编辑选择，不是标准规定的分隔符。决定应围绕人需要分辨什么，不能为了让自动检查中的字符串相等，把每个h1都塞成长品牌句。

用一个完整本地样本维护视图名称

下面是未执行的完整HTML。它用两个按钮切换虚构视图，没有路由框架、接口或申请提交。保存为文件可以准备后续检查；代码中的标题与内容是教学值，不代表真实服务。

<!doctype html>
<html lang="zh-CN">
<head>
  <meta charset="utf-8">
  <title>材料清单｜教学申请</title>
</head>
<body>
<nav aria-label="教学视图">
  <button type="button" data-view="documents">材料清单</button>
  <button type="button" data-view="review">核对申请</button>
</nav>
<main id="view"><h1></h1><p></p></main>
<script>
const views = {
  documents: { title: '材料清单｜教学申请', heading: '材料清单', note: '准备教学证明材料。' },
  review: { title: '核对申请｜教学申请', heading: '核对申请', note: '确认教学示例中的申请内容。' }
};
const [menu, heading, note] = ['nav', '#view h1', '#view p'].map(
  selector => document.querySelector(selector)
);
function render(key) {
  const current = views[key];
  if (!current) return;
  document.title = current.title;
  heading.textContent = current.heading;
  note.textContent = current.note;
}
menu.onclick = event => {
  if (!(event.target instanceof Element)) return;
  const button = event.target.closest('button[data-view]');
  if (button && menu.contains(button)) render(button.dataset.view);
};
render('documents');
</script>
</body>
</html>

render一次接收一个已定义视图，同时更新文档名和可见内容。先进入材料清单，再切到核对申请，最后回到材料清单，三次状态都有明确预期。样本不操作浏览器历史；如果实际系统使用前进、后退恢复视图，还应把对应恢复入口接到同一份标题规则，不能据此宣称代码已经覆盖路由。

真实应用可以采用路由元数据、服务器模板或其他方案。选择共同入口，是为了避免主内容使用新对象、标题仍读取旧对象。实现方式可以不同，必须说明标题由谁负责生成、何时更新，以及无法加载目标内容时如何命名。

异步加载晚回来，标题应听谁的？

设想用户打开申请甲，数据还在加载就转去申请乙。甲的请求晚到，如果其回调无条件设置document.title，标签页会重新变成甲，而页面主体仍是乙。只在成功返回时调用一次标题函数，不能保证对象归属正确。标题更新需要采用与当前视图相同的身份或版本判断。

加载、失败和成功也应有一致语境。读取材料失败时可以保留“材料清单”的主题并明确错误状态，而不是退回“首页”让用户以为换了页面；是否增加“加载失败”属于产品选择。最关键的是名称仍能说明正在处理哪件事，不让一个旧成功标题掩盖当前失败。

记录这些状态时，可以列出当前视图身份、可见h1、实际document.title以及触发更新的结果。不要只截图页面中央，因为标签页名称可能恰好不在截图里。一次DOM读取也不能独自证明实际用户代理怎样呈现，需要结合使用场景检查。

每个筛选条件都必须写进title吗？

不必把标题当状态日志。内容主题发生变化与一个列表里切换排序，不一定需要相同强度的命名更新。标题的长度、信息顺序和更新频率应服务辨认任务，不能让计数每秒跳动，反而使用户难以抓住稳定名称。

例如同一份材料清单切换“按名称排序”，可能仍是同一个可识别主题；进入另一份申请的核对视图，则可能需要区分对象。若需要写入对象标识，应同时考虑标签页、历史记录与共享设备可能暴露的信息。使用安全的业务简称或非敏感引用通常比直接放完整证件信息更容易解释，但具体选择仍需真实产品规则。

应用名称有时足以描述目的，理解文档也承认这种情形。不能从本例推导“所有路由标题必须全局唯一”；应检查标题是否在当前页面集合中描述主题或目的，以及独立使用时是否产生歧义。反过来，不能拿应用名可用的例子，为明显指向旧主题的残留标题免责。

标题更新了，读屏一定立刻播报吗？

标题语义与实际通知行为是两份证据。浏览器、辅助技术、导航方式和当前焦点都可能影响用户怎样获知变化。标题更新不应被包装成自动完成焦点管理或状态通知；若切换视图需要额外处理，应按对应交互需求设计并验证。

进入路径还需要成对比较：直接打开详情链接时的首个文档名，与从首页切进同一详情后的文档名，应该描述同一主题。服务端首屏正确，不能替后续客户端更新证明；客户端切换正确，也不能替直达加载失败时的标题证明。将两条入口路线放进同一视图记录，才能发现只有某一种进入方式残留“首页”的问题。

拟议验收包括初始进入、两个视图互换、返回、延迟响应倒序和加载失败。每条路线核对文档名、可见主题与当前业务对象，再在目标浏览器与辅助技术组合中观察辨认过程。本文没有运行这些检查，也没有用户完成率数据。页内标题与标签用途负责正文中的指路，本篇补的是离开正文后仍要成立的页面名称。交付时把这两种名称放到同一份视图表里核对。
