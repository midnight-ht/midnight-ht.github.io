Node.js pipeline 失败后，为什么 res.end 也发不出错误？

以完整本地文件服务区分打开前拒绝与 pipeline 接管后的传输中断，解释连接销毁、真实句柄、响应阶段和验证边界。

正文

核心要点

  • 捕获 pipeline 异常不保证响应通道仍可写。
  • 先取得实际读取句柄，不用存在预检保证后续读取。
  • 打开前拒绝、传输中断和接收成功需要不同证据。

Node.js 的 pipeline 失败时会清理参与的流，HTTP 响应所用连接也可能已经被销毁。因此，回调或 catch 能收到错误，不代表还能用 res.end 改发一段 JSON。文件响应应把接入 pipeline 之前的拒绝，与开始流式交付之后的中断分开设计；后者不能承诺替换已经开始或结束的响应。

错误到了 catch，写通道为什么没有回来？

Node.js 二十四版 Stream 文档的 pipeline 章节列出错误销毁规则，并直接给出 HTTP 文件读取失败后无法再发送预期错误消息的例子。本文于二〇二六年十一月一日核对的页面标为 v24.22.2；没有运行下面的服务，也没有观察真实网络回执。

pipeline 的职责不只是把数据接起来，还包括传播错误和处理参与流的结束。源读取失败后，不能让下游无限等待未来不会再有的数据。自动关闭通常是有用的资源处置；问题是应用同时假设自己在错误出现后仍拥有可写的响应，把两份相冲突的所有权合同放进了同一段处理器。

应先画三段时间：尚未把响应交给数据管道，已经接入但尚未完成，已经完成或销毁。第一段的错误通常还有机会按普通 HTTP 路径返回；第二段应按实际交付阶段处理；第三段再写文字不能倒转连接寿命。只看有没有异常，并不足以选择错误出口。

也不能简单推论“任何 pipeline 错误都必然销毁所有对象”。官方列出了已经结束的可读或可写流等例外，具体生命周期应按所用接口核对。需要保留的判断是：接收错误不保证恢复写通道，而不是把一种失败顺序包装成所有自定义流的绝对行为。

先取得真正使用的文件句柄

下面是未执行的完整 Node.js ESM 教学服务。保存为 download-demo.mjs 后以 Node 二十四版运行；它自己创建独立临时目录和固定文件，只监听本机，不允许用户指定任意文件路径。按 Ctrl+C 退出时清理本次临时目录。该程序说明响应阶段，没有实现真实账户、业务下载授权或生产服务器能力。

import http from 'node:http';
import { mkdtemp, writeFile, open, rm } from 'node:fs/promises';
import { tmpdir } from 'node:os';
import { join } from 'node:path';
import { pipeline } from 'node:stream/promises';

const directory = await mkdtemp(join(tmpdir(), 'pipeline-demo-'));
const report = join(directory, 'report.txt');
await writeFile(report, 'teaching report\n', 'utf8');

function reject(response, status, message) {
  response.writeHead(status, { 'Content-Type': 'text/plain; charset=utf-8' });
  response.end(message);
}

const server = http.createServer(async (request, response) => {
  if (!['/report', '/missing'].includes(request.url)) {
    reject(response, 404, 'unknown teaching route');
    return;
  }
  let handle;
  try {
    const target = request.url === '/report' ? report : join(directory, 'missing.txt');
    handle = await open(target, 'r');
  } catch (error) {
    reject(response, error.code === 'ENOENT' ? 404 : 500, 'cannot open report');
    return;
  }
  const source = handle.createReadStream({ autoClose: true });
  response.setHeader('Content-Type', 'text/plain; charset=utf-8');
  try {
    await pipeline(source, response);
  } catch (error) {
    console.error('transfer interrupted', error.code ?? error.message);
    // The response has been handed to pipeline. Do not promise another body.
  }
});

server.listen(8766, 'localhost');
process.once('SIGINT', () => {
  server.close(async () => {
    await rm(directory, { recursive: true, force: true });
  });
});

另一个终端可分别检查正常读取与打开前失败：

node download-demo.mjs
# 服务应在独立终端运行；下面请求在另一终端发出。
curl -i http://localhost:8766/report
curl -i http://localhost:8766/missing

服务终端应保持运行，不是执行完启动命令后继续在同一前台终端发送请求。正常路径使用已经打开的同一句柄创建流，缺文件路径在 pipeline 接管之前拒绝。这里的状态码与文字是教学选择；真实服务还需要按对象授权和错误披露规则制定响应。

句柄取得以后，读取仍可能失败。磁盘、流实现、对端断开或进程退出都可能改变后续过程。这个安排只是把“文件无法打开”的错误移到尚可选择响应的阶段，没有给整段传输加上成功保证，更没有证明接收者已保存或处理文件。

示例把文件流的关闭交给其自动关闭与管道生命周期，未把 handle 再交给另一个并发读取者。若项目把同一句柄用于多条流，就需要重新核对所有权，不能让其中一路失败时关闭别人还在使用的资源。临时目录清理也只对应正常受控退出，强制终止后的遗留物需要另外管理。

为什么不用 access 或 stat 预检查？

先检查存在，随后重新打开，是两次操作。中间文件可能被替换或删除；即使检查通过，真正读取仍能失败。本站access 与 open 的竞争窗口讨论这一层问题。本例先取得实际句柄，避免把一次预检查当作后续文件状态的许可证。

不过，句柄取得成功也不是业务授权。固定教学路径减少了输入范围，真实下载仍要验证当前身份能否读取对应产物，不能把任意请求路径拼成磁盘地址。授权失败应尽可能在交付数据之前完成；一旦敏感字节已经发出，后面的 catch 无法把它收回。

另外，不应为了保留错误正文而把整个文件先读进内存。对于有界小对象，缓冲可以是有意选择；对于大文件或不受控来源，这会引入另一份容量责任。应比较数据规模、取消需求与接收协议，而不是用一个统一读取函数替换所有流。

headersSent 为假，就一定能补发 JSON 吗？

不能据一个标志作这样的保证。它描述头部发送状态，不代表对端仍连接、响应未被销毁或写入必定成功。若 pipeline 已接管并按错误规则销毁通道，应用不应因为头部尚未发出就承诺还能换一种响应；需要实际检查生命周期，并把不可交付的错误留给可观察记录。

这里也要区分记录与补偿。记录传输中断，可以解释服务端观察到了什么；若用户需要恢复下载，应由可重试产物身份、保留期限或协议支持提供路径。记录一条 error 日志不创建恢复能力，更不证明客户端究竟收到了多少内容。

怎样验证两个错误出口？

第一组测试使用不存在的固定文件，核对打开失败仍得到约定的拒绝响应。第二组在隔离样本中让读取流于交付后报错，检查调用方观察的是中断，而不是伪造的完整 JSON 错误。第三组让客户端下载中途断开，检查源读取和句柄是否结束，并保留实际错误类别。

每组分别记录响应状态是否已经确定、客户端是否收到完整正文、服务器是否完成资源收尾。不要把服务端 pipeline 返回成功直接写成客户端业务成功；需要端到端校验的文件，还要定义长度、摘要或应用级接收确认。本文没有执行这些测试，示例也不包含故障注入后的成功日志。

排查提交应指出数据何时交给 pipeline，以及错误发生时谁还能决定响应。打开之前能拒绝，交付之后能识别中断，结束之后不再假装写入；这三项边界明确，catch 才是在处理真实状态，而不是向已经失效的连接补写一个看起来完整的答案。
