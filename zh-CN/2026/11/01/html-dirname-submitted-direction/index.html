HTML dirname：留言文字收到了，书写方向为何丢了？

用完整textarea样本追踪dirname额外条目，区分文本、基方向、语言与手工JSON的保存合同。

正文

核心要点

  • dirname的值命名方向字段，不是方向值本身。
  • 原生方向条目与手工对象需要明确对应。
  • 方向、语言和对齐不能合成同一字段含义。

留言表单收到了文字，不代表也收到了控件的基方向。HTML的dirname用另一个字段名提交ltr或rtl，接收方仍需规定如何验证、保存和回显。方向不是语言名称，也不只是把文字靠左或靠右的样式选择。

dirname的值是字段名

HTML的dirname章节定义，它让表单控件提交自身方向，并用属性值指定承载该方向的名称。属性存在时不能是空字符串。写dirname="comment.dir"，表达的是新增字段叫comment.dir，不是把方向设置成一个叫comment.dir的值。

在原生条目构造中，相应方向值取ltr或rtl。文本内容由原本的name表达，方向另外作为一条数据；把name改成dirname，或者只给控件设置dir，都不等于已经建立这两条提交关系。排查时应看实际条目，不能从画面里文字朝哪边排列推测请求。

基方向与语言有交集，却不是同一个维度。英文、数字、阿拉伯文可能混在同一段留言里；rtl不是完整语言标签，lang也不会自动变成额外方向字段。右对齐同样只是对齐选择，不能据此认定双向文本已经获得正确基方向。

一个完整的本地收集样本

以下HTML没有后端，提交会被拦截并显示FormData条目。它是未执行的教学样本，文字与控件仅用于观察两类字段，不代表真实留言已保存。可先输入普通拉丁文字，再输入真实允许的右向文字，比较自动判断和手工切换。

<!doctype html>
<html lang="zh-CN">
<head><meta charset="utf-8"><title>留言方向教学</title></head>
<body>
<form id="comment-form">
  <label for="comment">留言</label>
  <textarea id="comment" name="comment" dirname="comment.dir"
            dir="auto" rows="4"></textarea>
  <p>手动选择本次留言的基方向：</p>
  <button type="button" data-dir="ltr">从左到右</button>
  <button type="button" data-dir="rtl">从右到左</button>
  <button type="submit">查看待提交条目</button>
</form>
<pre id="result"></pre>
<script>
const [form, comment, result] = ['comment-form', 'comment', 'result'].map(
  id => document.getElementById(id)
);
form.onclick = event => {
  if (!(event.target instanceof Element)) return;
  const button = event.target.closest('button[data-dir]');
  if (button && form.contains(button)) comment.dir = button.dataset.dir;
};
form.onsubmit = event => {
  event.preventDefault();
  result.textContent = JSON.stringify([...new FormData(form).entries()], null, 2);
};
</script>
</body>
</html>

comment保存字符，comment.dir保存对应方向。样本初始使用auto，让控件按适用方向规则处理；两个局部按钮允许明确选择ltr或rtl。选择后再提交，观察的对象应是两个实际条目及其对应关系，而不是只看textarea边上的滚动条。

代码没有把方向变成任意CSS片段，也没有向远端发送请求。真实接口应先限定接受的方向值，再按产品规则存储；回显文字使用适当的文本处理方式，方向只控制对应方向属性。不能把客户端提供的字符串直接扩成一整段HTML或style，并称它已通过方向校验。

手工JSON为什么可能又丢了方向？

如果框架改成从状态对象组装请求，只读取comment.value，那么原生dirname规则未必参与这次收集。DOM上存在属性，不能保证任意手工序列化都自动复制附加条目。团队应决定使用原生条目，还是显式维护文本与方向，并让两条路径遵守同一合同。

恢复草稿时也要成对检查。只恢复文字却保留上一次编辑器的rtl状态，可能把另一条留言的方向带进当前对象；只恢复方向却把文本替换成新内容，又可能留下不适用的选择。保存记录应说明该方向来自用户明确选择、自动推断，还是系统缺省，避免几个来源互相覆盖而无法解释。

这些来源不一定都需要永久保存，取决于后续编辑需求。若只保存最终有效方向，应明确再次编辑时是否继续尊重这个值；若每次重新auto推断，用户的人工选择可能丢失。选择应向产品说明，而不是由组件重新挂载的偶然初值决定。

字符看起来能判断方向，为什么还保留选择？

一段双向文本可能先出现编号或引用，再出现主要内容，初始强字符不一定代表用户希望的基方向。自动判断能帮助常见输入，却不能替用户意图作永久保证。样本提供手工切换，目的正是让这项选择可观察，不声称自动或人工某一种方案适合全部场景。

仅含数字和标点的留言更需要检查实际语境。相同字符在不同基方向中，标点与嵌入内容的呈现可能产生不同理解；接收方若保存后再按另一个页面的继承方向显示，用户看到的就可能与编辑时不同。方向字段有助于保留已选状态，但不能自动解决每一种双向排版问题。

局部语言与发音边界讨论语言信息的另一项责任。保留rtl不等于已经声明语言，语言标记正确也不证明方向选择已提交。验收时应分别观察语言、方向和实际文本，不要用一个“多语言支持”结论合并三项证据。

名称冲突或禁用时，附加字段还可靠吗？

额外名称同样属于请求合同。如果另一处隐藏输入也叫comment.dir，就可能出现同名多条；服务端怎样解释重复键需要明确，不能默默取其中任意一个。控件原本没有适当name、被禁用或不满足原生条目条件时，也不能假定dirname仍会单独替它补出完整记录。

字段类型是否支持该能力也应按实际元素与状态核对。不要把一个有效textarea示例推广成给所有标签加dirname都会提交。页面只显示普通文本时，根本没有同样的原生控件收集路径；要保存方向就必须另有明确数据流程。

可以将样本进一步分成三种输入合同核对：保留name并手工选择rtl，留言为空且没有required时，文本条目可以是空字符串，方向条目仍表达该方向；移除name，则原生算法在追加方向之前已跳过这个字段；将控件禁用，也会在前面的排除步骤跳过。三种情况不能都命名为“没有填留言”，接收方需要区分空内容与根本没有相应条目。

拟议验收包括初始auto、两种手工方向、空内容、混合文字、恢复两份不同草稿、重复名称和禁用状态。每次记录控件方向、条目名称和值、实际请求以及服务器重新读取结果；本地样本只覆盖前两类观察，没有真实持久化。先确认文字与方向在同一对象上往返，再讨论系统是否已经保留用户的书写选择。
