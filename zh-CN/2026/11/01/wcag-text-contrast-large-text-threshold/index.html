WCAG文字对比度：18px粗体就能按大字放宽吗？

先按交付字体与字号确定文字对比阈值，再检查有效颜色、近似结果和CJK等效条件。

正文

核心要点

  • 18px不能直接当作18pt。
  • 大文本例外要核对字号、字重与字体条件。
  • 用户放大与工具四舍五入不能追认交付条件。

把18px粗体直接当成18pt大字，会选错文字对比阈值。应先核对交付字号、字体条件与背景，再判断适用普通文字4.5:1还是大文本3:1。标题标签、视觉印象和用户后来放大的结果，都不能替代这项判断。

先选阈值，再比较颜色

WCAG2.2对比度理解文档解释1.4.3、AA级要求：文字及文字图像的视觉呈现通常至少达到4.5:1，大文本采用至少3:1，并有附带文字、标志等特定例外。这些例外有自己的条件，不是把所有浅色说明都命名为“次要内容”就能避开。

大文本的定义给出至少18point，或14point粗体，也允许中文、日文和韩文字体的等效大小。定义关注交付时的字号，不包括用户之后进行的放大。不同字体的笔画和形态仍影响可读性，达到数值门槛也不证明任何字体在任何环境都同样易读。

point不能直接替换成CSS像素。CSS绝对长度关系规定一英寸对应九十六CSS像素、一point为七十二分之一英寸。因此14pt对应约18.67px，18pt对应24px。这里是单位关系的纸面换算，不是对显示器物理尺寸的测量，也不是说手机截屏里数到二十四颗像素就完成字号判断。

所以，对采用这些常见拉丁字体条件的18px粗体，不能因为数字十八就直接使用18pt的门槛。相对单位也要由最终计算结果理解：一处写1.2em，继承的字号与另一处不同，最终大小未必一样。验收应记录实际字体、字重和字号，而不是只保存设计令牌的名字。

三种文本样式，形成一份可检查样本

下面是未执行的完整静态HTML。采用拉丁测试文字，以免把CJK等效条件悄悄简化成同一个像素数字。颜色是教学选值，本文没有测量其实际比值，不把这份样本宣称为已通过对比度验收。

<!doctype html>
<html lang="en">
<head>
<meta charset="utf-8">
<meta name="viewport" content="width=device-width,initial-scale=1">
<title>Contrast threshold sample</title>
<style>
  body { color: #6b6b6b; background: #fff; font-family: Arial, sans-serif; }
  .small-bold { font-size: 18px; font-weight: 700; }
  .large-bold { font-size: 14pt; font-weight: 700; }
  .large-regular { font-size: 18pt; font-weight: 400; }
</style>
</head>
<body>
<h1>Compare delivered text styles</h1>
<p class="small-bold">Sample A: bold eighteen CSS pixels.</p>
<p class="large-bold">Sample B: bold fourteen CSS points.</p>
<p class="large-regular">Sample C: regular eighteen CSS points.</p>
</body>
</html>

检查时先列出A、B、C三行的字体条件与相应阈值，再取得前景、背景颜色计算对比。A不能按“十八”这个字面数值与C归为同一大小；B的字重条件也不能漏掉。若字体回退发生，应核对最终使用的字体，而不是只看声明列表的第一项。

这份顺序能区分两类问题：样式根本不符合所选大文本条件，或者符合条件但颜色比值仍低于相应门槛。前者先修分类与真实排版，后者再选择更清楚的颜色。把所有错误都改成加粗，会掩盖颜色问题，也可能使正文更难阅读。

工具显示4.5，为什么还不能立即通过？

阈值不接受向上四舍五入。假设计算器内部结果为4.499，显示时保留一位小数得到4.5，这只是教学数值，不是本页的实际测色结果。前一个值仍低于4.5，不能由界面的显示精度改写比较条件。审查记录应保留足够精度或工具明确的通过判定依据。

颜色来源也要真实。文本使用半透明前景时，令牌里的RGB分量未必是合成后的有效颜色；背景渐变或图片又会让不同文字位置面对不同背景。不能只挑最好的一块来代表整段。需要识别实际背景关系，并在必要范围中检查最不利的组合。

另一种误区是放大截图，采一颗文字边缘抗锯齿像素，把它当作作者定义的前景色。像素采样可以帮助调查实际渲染，却不应自动替代规范所用的颜色与字体判断。对细笔画、透明层和不同渲染条件，定量门槛与实际可读性观察要分别保存。

用户放大以后，小字能改按3:1吗？

不能通过用户事后放大来追认交付时的条件。放大是读者为了使用内容采取的动作，不是作者免除原始对比要求的路径。需要按大文本设计时，应真正确定交付字号及字体条件，再验证布局仍能容纳内容；不能只让测试人员把浏览器缩放调大。

改变字号也有产品代价。更大的标题可能换行，动作和说明位置随之变化；如果颜色用于长正文，提高对比可能比把全部文字放大更合适。选择应依据阅读任务，而不是只找一个能让当前颜色留在色板里的例外。这里没有用户实验或完成率数据支持某个统一方案。

中文字体也直接套18px吗？

定义保留了CJK等效大小条件，不能忽略字体差异，把某个拉丁字体换算数字直接当成所有中文字体的认证线。应说明当前字体、实际交付大小和判定依据；对无法明确满足例外的样式，可以选择按普通文字门槛设计，避免依赖模糊的豁免。这是本文的工程建议，不是另造一个CJK数值标准。

禁用组件与旁边仍然有用的说明也要分开。某段文字是否符合例外，要按其实际职责判断，不能把整个灰色区域叫禁用模块就全免。图标与控件边界另有非文本对比的必要信息检查，那里适用的3:1不能移植为所有文字的通用门槛。

例如“预约”按钮当前确实不可操作，旁边却解释“本周名额已满，请下周再查”。按钮是否符合非活动组件相关例外，应按实际状态判断；这段解释仍要让人读懂下一步，不能只因挨着灰色按钮就一起免检。若解释采用普通小字，就按其自身文字条件检查，而不是沿用按钮的状态结论。

拟议验收从这三种静态样式开始，记录计算后的字号、字重、字体及有效颜色，再检查错误、悬停和主题变化后是否替换了颜色。随后放回真实页面，观察内容和操作是否仍可完成。本文没有运行浏览器、测色工具或辅助技术检查。先把“为什么用这个阈值”写清楚，颜色结果才有可解释的比较对象。
