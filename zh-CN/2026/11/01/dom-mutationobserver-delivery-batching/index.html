MutationObserver：DOM已修改，回调为何还没执行？

用完整属性修改样本区分同步DOM、排队记录与回调批次，检查oldValue、takeRecords和停止观察。

正文

核心要点

  • 回调次数不等于修改次数。
  • target引用的当前值与oldValue记录不同。
  • takeRecords和disconnect需要明确收尾政策。

同一段脚本连续改两次属性，DOM已经是新值，MutationObserver回调却可能还没执行。修改本身与观察记录的通知不是同一时刻。先区分当前树、排队记录和回调交付，再判断是没有观察到变化，还是检查得太早。

一次回调不是一次修改

DOM标准的变更观察器算法把变更记录加入队列，再通过微任务通知待处理的观察器。同一个通知微任务已排队时，不必为每次同步修改再排一个相同通知。回调收到的是一批记录，不能把回调执行次数当成用户修改次数。

这不表示浏览器把所有变化合成一条最终记录。记录类型、目标与配置影响会保留什么，attributes、childList和characterData也不是可互换的选项。需要观察属性变化，却只启用childList，当然不能用“回调没来”证明修改没有发生。

还要分清记录与目标引用。record.target指向实际节点，不是一份完整历史DOM副本。回调开始以后读取它的属性，可能已经是后续修改留下的值；若需要前一个值，应核对相应oldValue选项，而不是期待再次读取target能恢复过去。

一个完整的同步修改与通知样本

以下HTML未执行，不依赖框架或接口。按钮连续改同一个属性，输出区域放在被观察目标之外，避免记录日志本身又成为观察输入。日志顺序是待验证对象，不是本文已经取得的控制台结果。

<!doctype html>
<html lang="zh-CN">
<head><meta charset="utf-8"><title>变更记录教学</title></head>
<body>
<h1>比较当前DOM与排队记录</h1>
<div id="target" data-state="idle">教学目标</div>
<button id="run" type="button">连续修改两次</button>
<pre id="log"></pre>
<script>
const [target, run, log] = ['target', 'run', 'log'].map(
  id => document.getElementById(id)
);
function write(entry) {
  log.textContent += JSON.stringify(entry) + '\n';
}
const observer = new MutationObserver(records => {
  write({ phase: 'observer', records: records.map(record => ({
    type: record.type, old: record.oldValue,
    current: record.target.getAttribute('data-state')
  })) });
});
observer.observe(target, {
  attributes: true, attributeFilter: ['data-state'], attributeOldValue: true
});
run.onclick = () => {
  write({ phase: 'handler-start' });
  target.setAttribute('data-state', 'loading');
  target.setAttribute('data-state', 'ready');
  write({ phase: 'handler-end', current: target.getAttribute('data-state') });
};
window.addEventListener('pagehide', () => observer.disconnect(), { once: true });
</script>
</body>
</html>

首次点击时，按算法推导，同步处理器结束前目标已是ready；之后的观察通知可以带来两条属性记录，其旧值分别来自idle和loading。回调里读取同一个目标的当前值，则可能两条都读到ready。旧值不同、当前值相同，并不说明某条记录被错误复制。

这个推演限定本样本的同步两次修改，没有其他脚本插入变化。真实应用若在不同任务、微任务或组件周期里操作，通知批次可能不同。不要把样本中的两条记录和一次通知当成所有调度条件下的保证；更不能靠一个随意的固定等待来证明每个中间状态都已被保存。

需要保存中间状态，选项够不够？

如果任务是查谁把属性改坏，旧值记录可能有帮助；如果任务是每次业务编辑的审计，DOM观察通常还缺少操作身份、原因和服务器确认。一次用户动作可能修改多个节点，一次框架渲染也可能重建整个区域。把每个MutationRecord直接当作一笔业务交易，会把实现细节混进审计口径。

记录配置应从需要的证据反推。只关心data-state时使用属性筛选，避免整棵页面所有样式变化淹没日志；需要子节点增删时再选择childList与适当subtree范围。开启更多选项可以增加数据，也会增加处理和解释责任，不能把“记录最多”视为“结论最可靠”。

如果只想在相关变化后重新计算一个摘要，可以在一批通知后读取最终状态。此时不需要假装逐条重播了用户动作。选择最终状态还是变更历史，是两份不同合同；回调提供的节点引用更适合哪一种，需要按任务说明。

动态NodeList与静态成员同样区分引用与快照，但它不规定观察通知时机。本篇增加了队列与oldValue之间的关系。两种机制可以一起出现，不能因为先取得了静态节点列表，就假定后来读取的节点内容也被冻结。

disconnect会先把最后几条回调完吗？

MutationObserver接口算法说明，takeRecords返回并清空记录队列；disconnect则移除观察关系并清空相应队列。停止观察不是一个承诺“先交付全部未处理记录”的刷新操作。若收尾需要保留记录，应明确先取得并处理，再停止观察。

takeRecords也不会替调用者执行回调逻辑。若代码拿走队列后丢弃返回值，之后没有回调不代表原来没有变化，而可能是记录已被自己取走。共享一个处理函数处理回调批次与主动取得的批次，是一种设计选择，但必须避免同一批记录重复记账。

页面销毁时要先决定目标。如果只是临时界面摘要，丢掉尚未显示的通知可能可以接受；如果承诺完整记录，离开页面、切换组件和停止观察时的收尾就需要专门设计。本文不把这套观察器当成持久可靠的业务日志，也没有实现跨页面记录交付。

为什么观察器有时像在自己触发自己？

回调改动被观察范围内的节点，会产生新的变化。这可能是有意的后处理，也可能持续生成下一批通知。样本把pre放在目标之外，正是为了让诊断输出不改变输入；它不是所有真实组件都应采用同样DOM位置的强制规则。

更复杂的组件应说明哪些节点由谁修改，何时不必再写入相同派生结果，如何停止观察和释放相关引用。只在回调开头加一个布尔锁，可能掩盖合法的后续变化；只不断清空日志，又会失去调查依据。修复应回到产生记录的动作与实际需要维护的状态。

拟议验收先比较首次两次属性修改，再测试不同批次、改变筛选范围、主动takeRecords和disconnect前后的记录。分别保留同步DOM值、记录数量、旧值、回调时间和最终摘要，不只看回调计数。本文没有执行这些场景。交付时应能解释每条记录描述什么，以及为什么当前读取不等于历史快照。
