PostgreSQL UNLOGGED 不是“更快但其余相同”的普通表

区分 UNLOGGED 的当前提交可见、崩溃截断与备用库内容限制，用完整配置样本说明可重建来源和恢复验收。

正文

核心要点

  • UNLOGGED 改变恢复与复制保证，不只是性能选项。
  • 当前查询有行不证明崩溃保留或备用库拥有内容。
  • 重建需要可信来源、稳定身份与调用方缺失状态。

PostgreSQL 的 UNLOGGED 不是只改变速度的普通表选项。它改变了数据写入日志、崩溃后保留以及备用库内容的合同：当前提交后能查到行，不代表不干净关闭后还在，也不代表备用服务器拥有这些行。只有来源可重建、丢失可以被业务接受时，才应评估这种存储安排。

提交成功与崩溃保留不同

PostgreSQL 18 CREATE TABLE 的 UNLOGGED 说明指出，这类表的数据不写入预写日志，崩溃或不干净关闭后会自动截断，内容也不复制到备用服务器。本文于二〇二六年十一月一日核对十八版文档，没有执行崩溃、复制或性能测试。

“已提交”回答一次事务的结果，不能抹去表本身选择的恢复限制。假设批量导入把唯一一份人工修订结果写进未记录日志的暂存表，界面随后显示保存完成。正常查询可能看起来没有问题，但若恢复后需要重新取得那份修订，来源已经不存在，就不能再把它称为随时可重建的中间数据。

应把数据分成可以从可信来源重算的阶段产物，以及只在此处形成的新事实。原文件仍在，不代表所有处理中产生的审核决定、人工修改与外部回执都能重算。如果后者只保存在这张表里，所谓缓存可能已经成为唯一业务记录，选型依据需要重新评估。

官方文档讨论了速度方面的特点，但没有给本项目的收益数字。实际是否值得，应在代表性负载上测量，并同时计入重建、清理和故障恢复的成本。仅把建表关键字加上，就宣称写入快了多少或总成本更低，都没有本篇证据支持。

先核对当前配置，不把它当成崩溃演练

下面是未执行的教学 SQL，要求独立测试数据库和全新的练习 schema。两张表拥有相同字段与具体输入，只比较存储声明和当前查询。若 schema 已存在，应停止确认归属，不接管未知对象。

BEGIN;
CREATE SCHEMA demo_unlogged_boundary;
SET LOCAL search_path = demo_unlogged_boundary, pg_catalog;
CREATE TABLE durable_stage (
  id integer PRIMARY KEY,
  value text NOT NULL
);
CREATE UNLOGGED TABLE rebuildable_stage (
  id integer PRIMARY KEY,
  value text NOT NULL
);

INSERT INTO durable_stage VALUES (1, 'source-A');
INSERT INTO rebuildable_stage VALUES (1, 'source-A');
COMMIT;

SELECT 'durable' AS kind, id, value
FROM demo_unlogged_boundary.durable_stage
UNION ALL
SELECT 'rebuildable' AS kind, id, value
FROM demo_unlogged_boundary.rebuildable_stage
ORDER BY kind, id;

SELECT c.relname, c.relpersistence
FROM pg_class AS c
JOIN pg_namespace AS n ON n.oid = c.relnamespace
WHERE n.nspname = 'demo_unlogged_boundary'
  AND c.relkind = 'r'
ORDER BY c.relname;

创建和写入位于同一事务；SET LOCAL 将未限定名称限制在本次新建的受控 schema，提交后的查询仍明确限定 schema。当前两张表都可以有已提交行，目录查询用于核对普通与未记录日志的声明。它不模拟故障，也没有证明行经过崩溃仍可恢复。要验证恢复，必须另外准备可丢弃实例与明确故障条件，不能把这段普通 SELECT 的预期当成恢复回执。

练习结束时，在确认所有对象都由本次练习创建且无人继续使用后，才可执行 DROP SCHEMA demo_unlogged_boundary CASCADE; 清理。本篇没有对任何现存集群发出强制停止命令；破坏性故障演练应有独立环境、权限与操作记录，不能夹在一个看似普通的查询教程里。

目录标志只说明关系的配置，还要核对应用实际读写的是这两张表中的哪一张。连接到错误数据库、未限定名称或读取了别的 schema，都可能让测试观察与业务目标错位。保存实例身份、数据库名和限定表名，比只截一张有数据的控制台图片更容易复核。

与临时表能直接互换吗？

临时表主要按会话可见性与结束策略管理；未记录日志的表则在这里改变日志与恢复保证，不自动因为一次请求或会话结束就删除。本站临时表与连接池生命周期解释前一项区别。两者都可用于某些阶段数据，不意味着生命周期合同相同。

如果任务需要跨会话共享一个可重建批次，单凭临时表私有于会话未必满足需求；如果只想让请求结束后清理状态，选择 UNLOGGED 也不会自动提供这项行为。应分别写出可见范围、保留时间、崩溃损失与清理拥有者，而不是寻找一个笼统的“临时”开关。

索引也需要与表的配置一起审查。官方说明这类表上的索引同样未记录日志；不能把某个索引当成独立耐久副本。应用若依赖唯一约束拒绝重复输入，正常工作期间的约束与故障后数据保留仍是不同问题，不应互相替代。

为什么在备用库上看不到这些业务行？

UNLOGGED 内容不复制到 standby 是选型限制，不应先归因于复制延迟。若服务把查询路由到备用库，必须知道该查询依赖的数据是否在它的合同范围内。增加等待时间不能把本来不复制的数据变成最终必达；重试策略应基于真实内容来源。

不过，一次查不到也不能只凭状态就断言表为 UNLOGGED。还要核对目标关系、实例角色、查询权限与事务可见性。配置限制解释一种可能的原因，实际故障仍需证据定位。本文没有运行备用库，所以不提供某个部署的复制正常或异常结论。

需要在多个实例读取的阶段结果，可以考虑使用满足复制要求的普通表，或把可重建任务安排在明确拥有来源的节点。选择必须同时回答丢失后谁重建、重建需要多久，以及重建期间调用者看到什么。把空表直接解释成没有业务记录，会将恢复中的暂缺误报成真实空结果。

改回 LOGGED，能补回已经丢失的内容吗？

改变存储声明不可能凭空还原旧行。应从可信来源恢复或重新计算，并保留来源版本与本次重建身份。是否转换表、如何安排锁与发布窗口，需要目标环境的运维计划；本篇不提供一个假装可直接上线的转换脚本。

重建输入也需要完整性检查。假设原批次含一百条记录，来源文件仍有一百行，但其中一条已经被更新成别的版本；行数相同不证明恢复了原先那一批。应核对稳定标识、来源摘要与所需版本，再按业务合同比较结果，而不是仅用表非空作为恢复完成条件。

故障演练计划应分开干净重启、不干净关闭、主库恢复和备用库读取。正常重启后保留数据，不能替不干净关闭提供证据；主库查询通过，也不能替备用库内容检查。每项只报告实际操作、环境和观察，不把一条绿色检查扩张成所有恢复条件都已满足。

若业务接受暂时丢失阶段数据，还要有明确的失败出口。可以显示批次正在重建、拒绝依赖该批次的操作，或转到独立可靠来源；具体选择由产品决定。不能在数据尚未恢复时沿用旧的完成标记，让下游把缺失理解为已核对的零结果。

本文没有执行以上 SQL 或故障场景。使用 UNLOGGED 前，先确认保存的是否真能重建、调用者是否允许暂缺，以及备用库是否需要读取。三项中任何一项回答不清，都不应仅为一个未经测量的性能印象，继承普通持久表的承诺。
