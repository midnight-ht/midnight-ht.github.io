Python itertools.groupby 保存的组，遍历后为什么变空？

用完整标准库对照解释 groupby 组迭代器为何随外层前进失效，比较即时消费、物化、连续键与后续交接。

正文

核心要点

  • 旧组与外层共享输入，保存对象不代表保存组数据。
  • 当场物化与当场汇总承担不同保留责任。
  • 排序可整理键，不能延长旧组迭代器的寿命。

itertools.groupby 返回的组不是独立保存的数据集合，而是与外层共享输入的迭代器。把组对象存进列表，再继续推进外层，可能已经越过那些组的数据。稍后还需要组内容时，应在当前组有效期间消费并保存所需数据；如果只需当场汇总，则不必为每组都创建长期副本。

保存了对象，为什么没有保存内容？

Python itertools 的 groupby 说明指出，返回的组与外层共享底层输入，外层前进后先前组不再可见。本文于二〇二六年十一月一日核对 Python 3.14.10 文档，没有执行下列程序，也没有读取真实导入文件。

可以把外层想成识别当前连续片段的入口，内层负责消费这段片段。两者并没有各自读取一份来源。外层为了找到下一组，必须走过当前片段；旧组留在列表里，只说明还有一个迭代器对象，不说明它拥有独立保存的行。对象仍可访问与数据仍可消费，是两种性质。

假设订单流按客户排列，处理器先收集所有客户组，准备稍后逐组发送报告。看起来它只保存了几个轻量对象，实际上外层收集过程已把输入推进到末尾。之后取出这些对象，不会重新打开文件，也不会自动回到每位客户的第一条订单。错误发生在生命周期安排，不是源数据突然被删除。

不要把所有惰性对象都理解成可重放的查询。某个迭代器可能只保留当前读取位置，来源还可能是不能重读的队列或网络输入。函数名含有分组，并不承诺数据库查询式的独立结果集。评审应先确定谁推进来源、什么时候需要数据，以及来源能否重新取得。

用独立输入对照两种保留方式

下面是未执行的完整标准库程序。每个对照都用新建的具体行列表，不把同一条已耗尽输入拿去验证修复。示例只是内存记录，不发送报告，也没有数据库写入。

from itertools import groupby


def rows():
    return [('A', 10), ('A', 20), ('B', 30)]


def customer(row):
    return row[0]


def main():
    delayed = list(groupby(rows(), key=customer))
    lost = [(key, list(group)) for key, group in delayed]
    print('delayed group iterators:', lost)
    if any(values for _, values in lost):
        raise RuntimeError('Unexpected retained group data')

    retained = [
        (key, list(group))
        for key, group in groupby(rows(), key=customer)
    ]
    expected = [('A', [('A', 10), ('A', 20)]), ('B', [('B', 30)])]
    if retained != expected:
        raise RuntimeError('Retained groups differ from expected rows')
    print('materialized groups:', retained)

    totals = [
        (key, sum(amount for _, amount in group))
        for key, group in groupby(rows(), key=customer)
    ]
    if totals != [('A', 30), ('B', 30)]:
        raise RuntimeError('Immediate aggregation changed totals')
    print('immediate totals:', totals)


if __name__ == '__main__':
    main()

第一种方式先耗尽外层，再消费旧组，预期已经没有之前的行。第二种在外层进入下一组之前把当前组变成列表，明确承担保存这些行的责任。第三种当场求和，只保存客户与总额，适合后续只需要汇总的合同。这些是程序与文档推演的预期，不是捕获的输出。

差别不在是否用了列表推导式。第二种在推导式内部消费组，第一种只收集组对象；相似外观背后，真正读取的位置不同。把代码换成普通循环，也必须把当前组的消费放在推进下一组之前。只更换语法，不能解决输入共享问题。

还应检查汇总会丢掉哪些信息。保存总额以后，原始每笔金额不会自动保留供后续审计；如果业务稍后要生成逐条报告，就不能只留一个总数。反过来，只要合同确实仅需要汇总，长期保存所有行又可能增加不必要的内存与敏感数据保留。保留范围应由后续操作决定。

连续相同键，才是这里的一组

另一个容易混淆的规则是连续性。输入键依次为甲、乙、甲，groupby 会形成三个连续片段，而不是把两段甲合成一个全局客户组。保存每组列表并不会改变这个规则；它修复的是组内容寿命，不是按键合并方式。

若业务要求同一客户所有订单放在一起，可以先按相同键排序，再分组；排序会改变原输入顺序，也需要能够获得相应数据。对于一次性无界流，先完整排序不是没有代价的一行修复。若顺序本身有业务含义，例如连续会话片段，排序还可能抹掉真正想保留的时间结构。

也可以按业务选择字典累积等方式形成全局分组，但那同样保存了尚未结束的分组状态。不要因为不再使用 groupby，就宣布内存问题已经解决。需要无限时间范围的客户归集时，应另定窗口、外部存储或结束条件，语言工具不会替产品决定什么时候一个客户的数据已经齐全。

这项区别应进入接口名称。接收相邻片段的函数，可以说明按连续键处理；接收完整客户集合的函数，则应要求已经完成相应整理。两个接口都叫 groups，却对完整性有不同假设，会让下游把一个片段误当成某客户的全部历史。

先排序能让旧分组可长期使用吗？

不能。排序只帮助相同键相邻，并没有让返回的组迭代器获得独立输入。即使来源是排序后的普通列表，外层推进仍会让旧组失去当前片段。要交给稍后执行的任务，应当场物化必要字段，或者传递能够独立重新读取的受控身份，而非把当前组迭代器塞进后台队列。

如果后续任务只需要一个客户编号，也不应顺手把整份客户记录复制到任务载荷。保存编号与保存当时快照承担不同责任；前者稍后可能读到新状态，后者需要明确数据版本与保留期限。这里提出的是交接选择，不是 groupby 自动提供的一致性机制。

本站异步生成器的提前关闭讨论消费结束时资源由谁收尾。当前问题则发生在仍在消费外层时，旧分组已被推进；二者不能混用。即使文件关闭安排正确，保存组对象的错误仍可能让报告拿不到行。

每组都转列表，就没有资源问题了吗？

列表把保存责任变明确，却不会消除数据大小。一个客户拥有大量记录，单组物化就可能很大；若把全部组都保留，总保留量又接近全部输入。应分别估计最大单组和同时保留组数，而不是只看示例里每组两三行。

如果只需逐组发送有限摘要，可以消费当前组、生成摘要、结束交接，再推进下一组。若发送本身产生外部副作用，则要安排失败记录与重试身份，不能把分组消费成功视为发送成功。来源已经推进后，重试能否重新取得当前组，也必须由保存或重放合同支持。

拟议验证至少包含排序输入、相同键分散出现、保存迭代器后延迟消费、当场物化与只取部分组内容。分别检查组数、每组身份与数据是否仍可读取，不能仅检查总金额恰好相等。两个错误分组也可能碰巧得到正确总和，掩盖客户归属已经改变。

还可以让来源在读取时记录每一条身份，验证哪一个调用实际推进了它。这能帮助定位是外层寻找下一组、内层消费，还是另一个辅助函数提前耗尽了输入。测试记录应注明来源是否可重放，避免用列表测试通过替一次性流背书。

本文没有执行这些检查。安排分组流程时，先回答当前片段什么时候失效、后续需要保留什么，再选择立即消费、物化或独立重读。把迭代器存起来，只保存了一个对象；需要保存数据时，必须另有明确动作。
