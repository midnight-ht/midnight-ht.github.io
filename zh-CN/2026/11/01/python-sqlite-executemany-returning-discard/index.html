Python sqlite3 executemany 执行了 RETURNING，为什么 fetchall 为空？

用完整内存数据库程序对照 executemany 丢弃结果与 execute 逐项收集身份，保留源键映射、提交与失败恢复的区别。

正文

核心要点

  • executemany 丢弃 RETURNING 行，不表示插入未发生。
  • 需要逐项身份时保存源键与实际返回值，避免猜连续编号。
  • 返回身份、提交和批次恢复须分别确认。

Python sqlite3 的 executemany 会丢弃产生的结果行，包括 INSERT ... RETURNING 的输出。因此，随后 fetchall 为空，不能直接推断没有插入。若批次必须返回每条新身份，应选择能收集结果的执行方式，并把稳定源键、返回身份与事务提交分开核对；不要用一个 lastrowid 猜整批编号。

SQL 能返回，不代表当前驱动接口保留了它

Python sqlite3 的 executemany 参考明确说明结果行会被丢弃。本文于二〇二六年十一月一日核对的页面为 Python 3.14.10；示例需要底层 SQLite 支持 RETURNING。程序会记录实际版本并拒绝明显不满足的版本，没有在本篇执行，也不报告任何数据库写入成功。

这里有三层能力：SQLite 是否接受这条 SQL，Python 调用了哪个执行接口，以及应用是否从该接口取得结果。数据库支持 RETURNING，不能推出 executemany 返回所有行；同样，驱动丢弃结果，也不表示 SQL 没有发生副作用。诊断应同时保留实际语句、调用方式与提交状态。

假设导入两条目录项，服务想把旧系统键映射到新生成编号。开发者在批量语句后读取结果，发现空列表，便准备重试整个文件。如果第一次写入已经提交，第二次可能重复创建；如果源键有唯一约束，则可能得到冲突。两种后果都不能由“没有返回 ID”独自判定。

反过来，只需要把确定数据写入而不需要逐项输出，executemany 仍可能是合适接口。是否改成逐条 execute 应由返回结果、失败语义和实际性能需求决定。本文不提供吞吐比较，也不把一个取回 ID 的教学方案称为所有大批量写入的最佳选择。

用两个独立表对照写入与结果

以下是未执行的完整标准库程序。它使用独立内存数据库、具体两行输入和两张教学表，避免先前写入干扰对照。源键带有稳定业务含义，新 ID 仅在各自表内识别对象，不预设两个表生成的数字必须相同。

import sqlite3
import sys


def main():
    print('Python:', sys.version)
    print('SQLite:', sqlite3.sqlite_version)
    if sqlite3.sqlite_version_info < (3, 35, 0):
        raise RuntimeError('This demonstration requires SQLite RETURNING support')
    source_rows = [('catalog-a:7', 'Alpha'), ('catalog-b:7', 'Beta')]
    con = sqlite3.connect(':memory:')
    execute = con.execute
    try:
        for table in ['batch_demo', 'mapped_demo']:
            execute(f'''CREATE TABLE {table} (
                id INTEGER PRIMARY KEY,
                source_key TEXT NOT NULL UNIQUE,
                label TEXT NOT NULL
            )''')
        con.commit()

        with con:
            cur = con.executemany(
                'INSERT INTO batch_demo(source_key, label) VALUES (?, ?) RETURNING id',
                source_rows,
            )
            returned = cur.fetchall()
        stored = execute(
            'SELECT source_key, label FROM batch_demo ORDER BY source_key'
        ).fetchall()
        if returned != [] or stored != source_rows:
            raise RuntimeError('Unexpected batch result or stored rows')

        mapping = {}
        with con:
            for source_key, label in source_rows:
                row = execute(
                    'INSERT INTO mapped_demo(source_key, label) VALUES (?, ?) RETURNING id',
                    (source_key, label),
                ).fetchone()
                if row is None:
                    raise RuntimeError('Missing generated identity')
                mapping[source_key] = row[0]
        restored = execute(
            'SELECT source_key, id FROM mapped_demo ORDER BY source_key'
        ).fetchall()
        if dict(restored) != mapping:
            raise RuntimeError('Identity mapping mismatch')
        print('discarded rows:', returned)
        print('committed mapping:', mapping)
    finally:
        con.close()


if __name__ == '__main__':
    main()

表名来自程序中写死的两个值，不接受外部输入；数据值仍使用参数绑定。这一限制要随示例一起理解，不能把其中的字符串格式化复制成允许用户任意选择表名的通用接口。创建、写入、查询和关闭均给出，代码没有依赖一个未实现的数据库客户端。

第一张表用于把“返回为空”和“数据存在”放到同一观察中。第二张表在明确的连接事务上下文内逐项 execute，每次把实际返回的身份与该条源键一起保存。两组查询都比较内容，而不是只看受影响行数；实际结果仍需运行后记录，不能把代码中的预期当作回执。

这里依赖示例连接的默认事务控制方式，以及上下文管理器正常退出时的提交行为。真实项目若显式选择其他 autocommit 模式，应重新核对边界，不能只因写了 with 就宣布原子性。本站executescript 的入口提交讨论另一种接口边界，本篇不把它的行为套给 executemany。

为什么不拿 lastrowid 再往前倒推？

同一份 Python 文档限定 lastrowid 的更新条件：它由符合条件的 execute 插入或替换更新，不能当成 executemany 的整批身份列表。即使某次样本里编号看起来连续，也不能从这个外观推出输入顺序与所有新行一一对应。

批次可能有拒绝、冲突处理、触发器或其他并发写入；这些条件需要按真实语句分析。本例使用逐项实际返回值，所以不依赖一段连续编号公式。稳定源键也包含目录范围，两个来源的局部编号都为七时，不会在映射字典里互相覆盖。

同样，不应把所有批量 RETURNING 都按数组下标与输入配对。驱动接口、SQL 形状和返回顺序的合同应明确；当输入本身有可验证的源身份时，直接保留身份比依赖偶然行序更容易审查。若业务源键不允许暴露给客户端，可以在服务端完成映射，再返回适当范围的结果。

fetchall 为空，可以立即再插一次吗？

先确认写入与提交状态，再决定恢复动作。若第一次已经提交，丢弃结果不抹去行；若事务回滚，内存里暂存的新 ID 也不应继续作为已创建对象交给后续步骤。需要支持结果未知后的重试，应有源键唯一性、查询和明确的幂等协议，而不是重复发送后碰运气。

示例把 mapping 留到正常提交后才打印，但这不是跨系统事务。若后面还要发消息或写其他服务，应另行设计交付；不能在事务内取得 ID 后立即调用外部系统，再假设数据库回滚会撤销它。返回身份与业务完成始终是不同证据。

某条输入失败时，映射如何收尾？

如果合同是整批成功，应让错误阻止该批提交，并丢弃未提交映射。可以用一个重复源键作为故障样本，先写明预期目标表没有本批新增，再在独立连接或提交后的查询中核对。不要让失败后残留的 Python 字典成为“部分成功”事实，除非产品明确允许并有逐条提交证据。

如果允许部分成功，则需要每条源键对应的接受、拒绝或未知状态，以及可以准确重试的范围。那是另一种批次合同，不是改成 execute 循环就自动完成。对于大文件，还要评估内存保存映射的大小，必要时用受控持久结果表承接；本例两条数据不能证明容量可用。

拟议验证覆盖无结果但已写入、逐条取回身份、重复源键、事务中途失败、结果查询和连接关闭。应保存 Python 与 SQLite 版本、真实执行方式及最终行集合。本文没有运行这些检查。修复应能够回答哪一个接口丢弃了结果、每个源对象究竟对应谁、哪次提交使它们生效，而不是只把空列表变成一个看起来合理的编号范围。
