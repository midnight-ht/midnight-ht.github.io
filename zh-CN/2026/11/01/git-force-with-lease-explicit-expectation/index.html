Git --force-with-lease为何仍可能覆盖没审过的远端提交？

用本地裸仓库与双克隆示例解释隐式lease为何受后台fetch影响，再核对显式预期对象、拒绝后的重新判断与最终引用。

正文

核心要点

  • 隐式lease的跟踪引用可能被后台fetch推进。
  • 显式expected应来自已核对状态，不自动等于批准覆盖。
  • 引用更新成功不证明历史、行为或部署都正确。

Git 的 --force-with-lease 没有明确指定预期值时，通常用本地远程跟踪引用作为比较依据。后台 fetch 若已经推进这个引用，lease 的比较点也可能跟着改变，即使你还没审过或整合新的远端工作。需要保护的是已确认的远端对象身份，而不只是命令名字里有一个 lease。

比较点为什么会在你没编辑代码时改变？

git-push 官方手册的 force-with-lease 说明明确提醒，未带预期值的形式与后台 fetch 交互可能削弱保护；它还给出指定引用与 expected 值的形式。本文于二〇二六年十一月一日核对在线手册，没有在当前工作区或任何远端执行推送、变基或引用修改。实际使用前应检查本机 Git 版本和仓库政策。

需要分清三个对象：服务器上的分支头，本地记录它的远程跟踪引用，以及准备推送的新分支头。隐式 lease 的依据来自第二项，不会询问使用者是否读过新增提交。编辑器自动刷新远端后，第二项可以更新，而第三项仍是基于旧历史改写出的结果。这就是文件没变，更新条件却可能变化的原因。

假设共同基线是 B，同事把远端推进到 C，你在旧基线上改写成 A。后台 fetch 把本地 origin/main 更新为 C，但并没有把 C 合进 A。若隐式比较点因此变成 C，服务器此刻也正好是 C，引用相等这件事本身无法证明 A 保留了同事的工作。它不是 Git 随机忽略保护，而是保护所依赖的预期值已经移动。

一份只用于本机练习的完整初态

下面脚本未经执行。它在新临时目录创建本地裸仓库和两个克隆，不连接网络远端，不修改本站仓库。示例用 main 只是为了缩短名称，不代表应该改写共享主分支；真实共享分支应优先遵守团队的正常合并与保护规则。

demo_root="$(mktemp -d)"
git init --bare --initial-branch=main "$demo_root/remote.git"
git clone "$demo_root/remote.git" "$demo_root/a"
git -C "$demo_root/a" config user.name Training
git -C "$demo_root/a" config user.email training.invalid
printf 'base\n' > "$demo_root/a/demo-file"
git -C "$demo_root/a" add demo-file
git -C "$demo_root/a" commit -m base
git -C "$demo_root/a" push origin main
git clone "$demo_root/remote.git" "$demo_root/b"
git -C "$demo_root/b" config user.name Training
git -C "$demo_root/b" config user.email training.invalid
expected_oid="$(git -C "$demo_root/a" rev-parse refs/remotes/origin/main)"
printf 'peer\n' > "$demo_root/b/peer-file"
git -C "$demo_root/b" add peer-file
git -C "$demo_root/b" commit -m peer
git -C "$demo_root/b" push origin main
git -C "$demo_root/a" fetch origin
printf 'rewritten\n' > "$demo_root/a/demo-file"
git -C "$demo_root/a" add demo-file
git -C "$demo_root/a" commit --amend -m rewritten-base
git -C "$demo_root/a" push \
  "--force-with-lease=refs/heads/main:$expected_oid" \
  origin HEAD:refs/heads/main

最后的显式比较仍要求远端位于最早保存的 B。由于另一个克隆已经推进远端，预期方向是拒绝这次更新，而不是替你整合同事提交。拒绝是教学目标，不是脚本失败后应该自动改成普通 force。这里没有实跑输出，不能把这段预期写成已验证的拒绝回执。

若要比较隐式形式，应从另一套完全相同的初态重建练习，而不是紧接着在已变化的同一现场继续推。记录每一套的共同基线、同事提交、后台 fetch 后跟踪引用和候选头，再比较服务器返回与最终引用。否则第一轮的副作用会让第二轮不再回答同一个问题。

显式预期值应该由什么证据产生？

记录一个完整对象身份有助于固定比较点，但身份需要对应一次真实核对。不能从最新跟踪引用随手取值，立即称它为“已审过的版本”。先看远端新增工作，确认候选是否有权替换它，再把当时认可的对象写入更新条件；预期值不是免除审查的口令。

服务器在你核对后仍可能继续变化。显式 lease 遇到新头而拒绝，可以防止基于旧确认覆盖后续更新；它不提供一段锁住整个远端的独占时间。修复方案应允许安全停止和重新比较，而不是在循环里不断 fetch、刷新预期值、再次强推，直到某一次碰巧通过。

同一个条件也不能替代引用范围选择。命令要明确准备更新哪个服务器引用，以及新内容来自哪个本地对象。默认推送配置、多个分支和额外标签都可能扩大操作范围。教学脚本写明完整目标引用，就是为了让比较条件与副作用对象能在一行记录里对应起来。

一份更新记录怎样排除查询时点误判？

可以把目标完整引用、已核对的预期对象、准备推送的对象和服务器最终对象写成四项记录。第一项限定改哪里，第二项限定在什么旧状态下获准，第三项说明拟交付内容，第四项回答实际留下什么。它们不能只用一个会移动的分支名代替，也不能把推送前观察和推送后结果混在一起。

另一个对照是先查询远端，确认没有变化，再让同事推进，最后执行更新。查询发生时的相等不阻止之后变化，所以预检查不能代替推送时的条件比较。显式lease的作用在于让服务器接受更新时仍检查那份预期，而不是保证先查一次以后就永久安全。本文没有运行这项竞争场景；它说明应保留时间与比较对象的原因。

lease通过，还需要证明哪些事？

通过只说明这次引用更新满足服务器接受的条件，不证明新历史的内容正确，也不证明必须保留的提交都进入了父链。需要历史可达时，使用对应祖先检查；需要修复行为时，检查当前代码与测试。本站文件树与提交祖先的证据区别解释了这两个判断为什么可能分开。

共享分支若只需要撤销一项变更，新增反向提交可能更符合可追溯流程，而不必改写历史。可对照revert保留共享历史选择操作，但不能把它当成所有情况都必须使用的答案。个人临时分支、已公开协作分支与受保护发布引用有不同要求。

核对结果还应包括远端最终对象，而不是只保存终端里的成功文字。若推送结果未知，先查询目标引用和运行记录，不能立即换一种更强覆盖方式重试。引用已更新与后续构建、部署采用了它也不同，本题没有提供任何发布或生产结果。

lease拒绝后，fetch一下就能直接重试吗？

不能把更新本地信息等同重新批准覆盖。先比较新的远端工作和候选，决定整合、放弃改写或取得协作确认，再建立新的明确条件。若拒绝来自目标写错、对象不存在或权限政策，应修相应边界，不能统一归为远端“太新”。

待执行验收应分别覆盖远端未变、同事推进、后台 fetch 与核对后再次推进，保留每次完整引用身份和退出结果。所有练习仅用可丢弃本地仓库，本文未执行。最有用的结论不是用了哪个更安全的选项，而是这次更新只在什么已确认的远端状态下获准发生，以及状态变化后由谁重新决定。
