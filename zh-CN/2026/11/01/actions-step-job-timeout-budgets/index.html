GitHub Actions每步都没超时，job为什么仍被取消？

用完整串行等待工作流解释step与job预算，再分别检查取消原因、外部任务终态和报告证据，避免只调大局部参数。

正文

核心要点

  • 步骤限时不会延长作业共享预算。
  • 平台取消原因要与命令失败分别解释。
  • 作业停止不证明外部任务或报告上传已经结束。

GitHub Actions 的步骤没有达到自身 timeout-minutes，整个 job 仍可能先用完总预算而被取消。步骤上限不会延长作业上限，前面串行工作消耗的时间也属于同一作业。排查应先确认取消来自哪一层，再决定调整某一步、总预算或工作划分。

两个字段限制的对象不同

GitHub Actions 工作流语法参考分别说明 step 和 job 的 timeout-minutes：前者限制步骤运行，后者限制整个作业；runner 执行上限还可能先于所设作业值终止。本文于二〇二六年十一月一日核对当前在线说明，只讨论普通串行步骤，没有运行托管或自托管工作流。

局部预算回答“这一步最多占多久”，总预算回答“这份作业最多运行多久”。第二步拿到的并不是一份全新的外层时间。若第一步已经消耗大部分作业预算，即使第二步自己的上限很宽，也不能借此要求平台继续保留整个作业。

还应把取消与普通命令失败分开。测试命令返回非零、人工取消、作业超时和运行器故障可能都让后续步骤缺席，但修复方向不同。先保留运行终态、取消原因和最后实际执行的步骤，再调整配置；只看到最后一步没有结束，不能判断一定是该步上限太小。

一个不依赖代码仓库的完整时间例子

下面工作流未经执行，可以作为独立测试仓库中的手动触发文件。示例步骤不执行checkout或第三方Action，不主动发起业务网络请求，也不部署；两个等待命令仅表达串行耗时，平台运行器仍有自己的通信。数值用于构造对照，不是推荐任何真实流水线都采用两分钟上限。

name: inspect-timeout-boundaries
on: workflow_dispatch
permissions:
  contents: read
jobs:
  budget:
    runs-on: ubuntu-latest
    timeout-minutes: 2
    steps:
      - name: First bounded wait
        timeout-minutes: 2
        run: |
          printf 'first started\n'
          sleep 90
          printf 'first ended\n'
      - name: Second bounded wait
        timeout-minutes: 2
        run: |
          printf 'second started\n'
          sleep 90
          printf 'second ended\n'

每个等待本身少于步骤允许的两分钟，但两段计划工作相加已超过作业两分钟预算。这可以解释为什么第二步还没用完自己的上限，外层就可能停止。实际运行还包括其他处理与调度因素，本文不承诺在第一百二十秒准确发送取消，也不提供某次平台执行日志。

对照可以只把 job 预算改大，保留同样工作量和步骤上限，分别观察最后标记与作业结果；再单独缩短某一步预算，区分局部超时路径。每次只改变一个条件，才知道这次失败来自哪个范围。把所有值一起调大后成功，只能说明新组合有效，不能定位原先的约束。

工作流中的结束标记也有边界。打印 first ended 说明脚本走到那一行，不证明后续作业或外部业务完成；没有打印 second ended，又可能来自多种停止原因。需要把标记与平台终态对应，而不是从两条文字推算完整生命周期。

预算应该按什么来分配？

先列必须完成的步骤、可选诊断和失败后必要的结果处理，再依据真实运行观察分配预算。耗时波动、工具初始化与数据规模会影响选择；本篇没有测量项目分布，所以不提供统一放大倍数。预算应能解释目标，而不是永远取平台允许的最大值。

若单个步骤频繁卡住，给整个 job 加时可能只让卡住持续更久，应先调查等待条件、依赖或死循环。若各步骤都在合理时间内完成，而串行总量超过总预算，才评估总预算或拆分。对照日志应能显示时间花在哪里，避免把任何取消都解决为“再多等一会”。

拆成多个 job 可以改变预算边界，却也引入输出、制品和状态交接。不能为了获得更多时间就遗漏版本身份和失败传播。某项工作必须在同一事务或同一临时环境内完成时，也未必适合机械拆开；需要根据实际资源与依赖生命周期作决定。

作业停了，外部任务也一定停了吗？

不能从运行器停止推断另一个系统的终态。若步骤先提交远程构建或批任务，再等待结果，作业取消可能只让等待者离开。应按外部系统的任务身份查询状态，决定是否请求取消并核对结果，而不是把 GitHub 的 cancelled 状态直接写成远端任务未执行。

这个边界会影响重试。原作业未得到确认，下一轮若盲目重复提交，可能产生两个任务。应保存必要的非敏感关联身份，并用已有接口判断第一次结果；需要幂等时由业务契约表达。本例只有本地 sleep，不演示远程取消，也没有替任何服务规定通用 API。

步骤 outcome 与 conclusion说明结果解释的另一层：允许继续不等于原始成功。超时场景同样要保留取消或证据缺失，不因为某个报告步骤成功就覆盖整个必需工作的状态。

always步骤能保证把报告传完吗？

不能只凭条件名承诺上传完成。即使安排了失败后收集，还需确认作业是否仍有执行机会、文件是否真实存在、运行器是否可用，以及上传是否有成功结果。关键证据若只在最后一刻生成，作业提前结束时可能根本没有文件可交付。

可以让必要工具在适当阶段写出中间结果，并把本轮运行、提交和检查身份绑定到材料，避免用旧文件填补空缺。是否采用持续外部记录或阶段制品，需要按权限与保留要求评审；这不是建议把全部日志、环境或秘密无差别发送出去。

拟议验收分别覆盖步骤先超时、作业总预算先到、人工取消和报告不存在，记录命令标记、平台原因、文件身份与后续入口是否被阻断。还应检查自托管或托管 runner 的实际执行限制，不能把 YAML 里写的大值当成无限时间。本文未执行这些用例，不报告工作流通过。

最终预算表应能说明：每一步的局部上限，作业共享的截止范围，平台可能更早结束的条件，以及停止后谁确认尚未完成的工作。四项分清，最后一步未到自身限时就结束，便不必再靠反复调参猜原因。
