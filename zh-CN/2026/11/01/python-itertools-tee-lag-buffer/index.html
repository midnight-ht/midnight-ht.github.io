Python itertools.tee 分出慢消费者，为什么内存可能上涨？

以来源推进计数对照 tee 的分支进度差，解释辅助存储、元素共享、调度与线程安全，并给出容量选择依据。

正文

核心要点

  • 独立读取位置不等于固定内存或重复生产来源。
  • 慢分支生命周期与进度差需要明确预算。
  • 元素副本、并发调度和线程安全不能由 tee 名称推导。

Python itertools.tee 提供多个读取位置，不承诺固定内存。快分支已经读过、慢分支尚未读到的值，需要为落后者保留，因此消费进度差可能形成大量辅助存储。使用它之前应明确分支允许落后多少、何时结束以及来源能否重放，不能只因接口是惰性的就省略容量设计。

独立位置，不是独立生产

Python itertools 的 tee 说明提醒，所需辅助存储可能很多，取决于需要暂存的数据；如果一路先消费大部分甚至全部输入，另一路才开始，文档建议考虑直接使用列表。本文于二〇二六年十一月一日核对 Python 3.14.10 文档，没有执行内存测量或下面的程序。

两条分支可以以不同速度前进，是因为它们分别保留读取位置，而不是来源被重新调用两遍。快分支需要下一项时，来源继续生产；慢分支以后还要得到同一序列，就必须能够取回自己没读过的部分。这个交接关系解释了为什么“生成器逐条产生”与“整个流程只保留一条”不能画等号。

假设一路计算总额，一路等待用户确认后才导出明细。总额计算先走完整个输入，明细分支尚未开始，尚待明细使用的历史值就不能因为快分支处理完而立即丢弃。若输入无界，而慢分支长期不前进，差距没有业务上限；仅给快分支提高吞吐，可能让保留增长更快。

这不是禁止所有 tee。两路按近似步调推进、数据规模有界且共享输入符合需求时，它能清楚表达重复遍历。错误在于把一个方便的分流工具扩张成容量管理器。应先说清允许的差距，再决定工具是否匹配；不能从示例里只有几个数字推断真实导出也没有资源压力。

用来源计数观察分支差距

以下是未执行的完整标准库程序。它只生成六个整数，用日志记录来源实际走了多少步，没有网络、数据库或后台线程。计数展示消费关系，不测量每个元素占多少字节，也不承诺某个解释器的内存回收时点。

from itertools import tee


def source(log):
    for value in range(6):
        log.append(value)
        yield value


def main():
    produced = []
    fast, slow = tee(source(produced))
    fast_prefix = [next(fast) for _ in range(4)]
    if fast_prefix != [0, 1, 2, 3] or produced != [0, 1, 2, 3]:
        raise RuntimeError('Unexpected source advancement')

    slow_prefix = [next(slow) for _ in range(2)]
    if slow_prefix != [0, 1] or produced != [0, 1, 2, 3]:
        raise RuntimeError('Slow branch unexpectedly reproduced source data')

    fast_tail = list(fast)
    slow_tail = list(slow)
    if fast_tail != [4, 5] or slow_tail != [2, 3, 4, 5]:
        raise RuntimeError('Branches lost their independent positions')
    print('source values:', produced)

    interleaved_log = []
    left, right = tee(source(interleaved_log))
    paired = []
    for _ in range(6):
        paired.append((next(left), next(right)))
    if paired != [(n, n) for n in range(6)]:
        raise RuntimeError('Interleaved readers disagree')
    print('interleaved source:', interleaved_log)


if __name__ == '__main__':
    main()

快分支先取四项，慢分支随后取两项时，来源不应重新生成零和一。两条分支最终都应得到完整序列，但读取位置不同；第二组则交替推进。预期来自给定代码与接口合同，不是记录的终端输出。程序没有证明第二种方式在某台机器上节省了具体内存量。

来源日志本身也保存了数据，因此不能拿这个教学程序的内存曲线直接代表 tee 的成本。若做真实资源测量，应先移除无界日志等额外持有者，固定元素形状、输入规模和观察工具，再区分峰值、保留对象与进程驻留内存。本文没有执行这样的实验，也不提供人为编造的差值。

进度差需要按条数和元素大小一起考虑。两个分支只差几十项，如果每项都引用很大的内容，也可能并不便宜；差很多项但元素很小，则有另一种成本。业务预算应针对实际载荷，而不是把某个固定条数当成所有类型的通用安全线。

不能等待的慢分支，应该怎样安排？

如果可以重读可信来源，两个阶段可能独立打开来源，各自承担读取成本，并用来源版本确认处理同一份数据。这样不会要求在一条内存分流中长期保存差距，但也不是免费：来源保留、再次访问权限和内容变更都需要约定。

如果来源不能重放而两路都必须收到，可以考虑明确有容量与停止策略的交接，或先保存为受控持久产物。满了以后是让快分支等待、拒绝新输入还是停止整项任务，应由业务选择。tee 不提供这样的产品决策，不应在内存增长之后才临时丢掉慢分支的数据。

如果慢分支其实只需要抽样或摘要，应明确它不要求完整序列，再按那个合同设计。不能先承诺每项都交给它，资源不足时却悄悄跳过。容量策略一旦改变接收集合，就改变了业务输出，而不只是实现细节。

本站可写流背压讨论生产与消费速度不匹配的另一种表现。当前问题不是 Node 写缓冲，而是 Python 分支读取位置之间需要保留历史；共同的审查动作是找出谁仍需要这些值，而不是从“流式”名称推断保留量。

两路读到的字典，会自动成为两个副本吗？

独立迭代位置不等于深复制元素。若来源产生一个可变字典，两路取得的内容不能被无条件当作互不影响的编辑草稿。若消费者需要修改，应明确何处复制、复制哪些层，以及是否还与来源共享成员；若只读共享适合需求，则无需为所有元素盲目深复制。

这项追问也影响测量。一个分支把元素保存进自己的结果列表，即使 tee 内部不再需要那项，应用列表仍在持有它。调查资源增长应画出全部持有者，区分内部等待历史与业务有意保存的输出，不能把所有保留都归因于同一个分流函数。

如果一个分支提前返回，谁仍持有它的引用也应明确。不要宣称丢掉局部变量就保证某个时点释放了所有数据；外围闭包、任务对象与结果结构都可能继续持有相关对象。需要确定的资源上限，应通过流程合同与实际观察证明，而不是依赖垃圾回收的名字。

来源线程安全，就能并发使用 tee 分支吗？

官方文档明确指出，同一次 tee 生成的迭代器不是线程安全的，即使底层来源本身安全，也不能据此推导包装后的分支安全。把两路交给线程，并没有因为独立读取位置就建立同步协议。需要并发交付时，应选择具有相应合同的队列或其他方案，核对取消与错误如何传播。

此外，创建分支不会替程序启动两个执行者。主线程顺序执行两个 list，仍是先完整消费一路再消费另一路；不能把“有两个迭代器”写成两项工作正在并行。调度、线程与读取位置属于不同能力，性能报告应说明实际运行方式。

拟议验证应覆盖交替消费、快分支先读完、慢分支暂停、某路提前退出和来源抛错。分别记录每路已接收身份、来源推进位置以及仍被保存的对象，避免只比较最后两个列表是否相等。最终输出相同，也可能是在承担大量中间保留之后才得到的。

本文未运行这些检查。选用 tee 时，先给慢分支一个可解释的生命周期和消费差距，再让资源测量验证这份安排。独立位置是接口功能；差距是否有界、来源是否可重放、失败后怎样继续，仍须由应用承担。
