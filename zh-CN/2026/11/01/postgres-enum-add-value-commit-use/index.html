PostgreSQL ADD VALUE 成功，新枚举为什么仍不能 INSERT？

以可丢弃 schema 的正反 SQL 说明 ADD VALUE 提交后的可用时点，检查迁移运行器、两阶段恢复和旧应用兼容。

正文

核心要点

  • 事务内新增枚举成员须等该事务提交后才能使用。
  • 分阶段迁移仍应保留各阶段的原子性与完成记录。
  • 成员存在不证明回填完成或旧客户端兼容。

PostgreSQL 在事务块中执行 ALTER TYPE ... ADD VALUE 后，新增枚举成员要等该事务成功提交才能使用。语句执行成功，不表示同一事务里的后续 INSERT 已能引用新值。迁移需要按这个可用时点拆分步骤，并独立验证应用兼容；不能为了消除一个报错，就把所有数据修改的事务保护一并关掉。

成员已经添加，为什么还不能使用？

PostgreSQL 18 的 ALTER TYPE 参考在 Notes 中明确列出这条限制。本文于二〇二六年十一月一日核对十八版文档，讨论向既有枚举类型添加成员的事务使用边界，没有执行迁移或真实库上的 DDL。

迁移工具往往默认把一份迁移文件放在一个事务中。文件前半段扩展类型，后半段回填新状态，读起来像一项完整变更；但代码排列相邻，不会改变新成员的允许使用时点。应检查运行器实际发出的 BEGIN 与 COMMIT，而不是只看迁移文件里有没有手写事务语句。

这里也不能把“可在事务中添加”误读成“可以立刻使用”。两者是不同能力。单纯检查命令退出状态，只证明这一条定义修改没有在当时被拒绝；后面写入新成员仍有自己的前置条件。排错时记录失败发生于扩展、写入还是提交，才能找对需要拆开的边界。

反过来，事务仍能保护许多相关修改，不应把这条枚举限制推广成所有迁移都不能用事务。合适的安排通常是让确实需要先提交的类型扩展独立完成，再让后续数据阶段保留自己的原子性。两个阶段之间会有可观察窗口，恢复与发布顺序必须承认它。

在可丢弃 schema 中做正反对照

下面是未执行的 SQL 教学步骤，要求在有创建 schema 权限的独立测试库中，通过交互式 psql 分段运行。名称只属于本次练习；若创建时报已存在，应停止并换新的练习名称，不使用 IF NOT EXISTS 接管未知对象。不要将预期错误后的步骤交给会立即退出的脚本，而漏掉回滚。

先在自动提交环境中完成准备，使类型成为已经存在的对象：

CREATE SCHEMA demo_enum_boundary;
CREATE TYPE demo_enum_boundary.stage AS ENUM ('draft');
CREATE TABLE demo_enum_boundary.items (
  id integer PRIMARY KEY,
  stage demo_enum_boundary.stage NOT NULL
);
INSERT INTO demo_enum_boundary.items VALUES (1, 'draft');

随后单独运行反例事务。INSERT 是预期失败点，看到该错误后，在同一会话明确执行 ROLLBACK：

BEGIN;
ALTER TYPE demo_enum_boundary.stage ADD VALUE 'review';
INSERT INTO demo_enum_boundary.items VALUES (2, 'review');
ROLLBACK;

反例回滚后，再按两个事务执行修正路径。扩展阶段提交以后，第二个事务才开始写入：

BEGIN;
ALTER TYPE demo_enum_boundary.stage ADD VALUE 'review';
COMMIT;

BEGIN;
INSERT INTO demo_enum_boundary.items VALUES (2, 'review');
COMMIT;

SELECT id, stage FROM demo_enum_boundary.items ORDER BY id;

按文档推演，修正路径的最终查询应包括原有草稿与新增审核状态。实际输出、类型目录与提交结果都需要运行后记录，本文没有这些回执。练习结束后，仅在确认该 schema 确由本次练习新建且无人继续使用时，执行 DROP SCHEMA demo_enum_boundary CASCADE; 清理；不要把级联删除带到不清楚归属的库。

这组步骤刻意保留失败事务的明确结束。收到错误后直接继续发业务 SQL，可能只得到当前事务失败状态，反而掩盖原始原因。先保存第一条有意义的错误，再完成回滚，之后的修正才是新一轮可解释操作。

两个事务之间，谁可以开始使用新值？

数据库扩展先提交，只使新值满足这一项数据库前提，并不证明应用已经准备好。旧版本代码可能只认识草稿与完成，读取新审核状态时走到未知分支；接口验证、消息消费者、报表和移动端缓存也可能各自有允许集合。上线顺序需要覆盖真正会读写该字段的各方。

一种可审查策略是先让读取者容纳新状态，再完成数据库扩展，最后开启产生该状态的入口。具体顺序取决于兼容合同，不是本文替所有项目批准的固定发布方法。关键是不要让“数据库迁移成功”自动成为所有客户端都能处理新值的证明。

如果回填失败，类型扩展可能已经提交。恢复记录应写清哪个阶段完成、数据是否开始使用新成员、可以继续还是需要人工处理。不能把整份迁移标成完全回滚；也不能仅因成员存在，就跳过剩余数据检查后宣布全部完成。

多实例发布还要防止两个执行者各自以为自己拥有迁移。如何锁定迁移、记录版本与恢复责任，应由现有发布系统提供可核对的合同。这里没有创建一套通用迁移管理器，也没有因为 ADD VALUE 有一个选项就宣称并发运行安全。

IF NOT EXISTS 可以当作整份迁移已完成吗？

不能。该选项处理成员已经存在的分支，不会替你检查字段默认值、回填范围、约束或应用版本。重复执行时，可能是上次只完成了扩展，也可能是另一个操作者做了相似修改；需要读取实际定义与阶段记录，不能只根据本次没有报错判断来历。

成员排序也不是业务工作流。使用 BEFORE 或 AFTER 安排枚举排序位置，不意味着状态转换只能按这个顺序发生。哪个身份能把草稿改成审核、能否撤回、旧状态怎样迁移，仍需业务校验与授权；不能从类型的比较顺序推导允许的操作。

本站延迟约束的验证时点讨论另一种事务边界：语句完成以后，约束仍可能在稍后拒绝提交。本题则是先扩展类型，再到允许使用新值的提交后阶段。共同需要标清时点，机制却不能互换。

应用回滚以后，数据也自动兼容了吗？

如果新版本已经写入新成员，重新运行旧程序并不会把这些行还原成旧状态。回滚计划应检查旧读者是否能接受现有值，或是否需要经过批准的数据修复。不能把删除新成员视为一个随手可执行的通用逆操作，更不能为了让旧代码能读，就把业务状态静默改成另一个值。

拟议验收覆盖反例事务、分阶段修正、扩展完成后中断、回填失败、旧客户端读取和重复执行。每组都核对实际类型成员、最终行值与阶段提交记录，而不只检查迁移命令返回零。对真实数据操作还应先确认授权与恢复方案，本篇并未执行。

修复完成的依据应是：扩展在哪次提交后可用，谁从什么时候开始写新值，未完成阶段由谁继续。把这三项写清，拆事务才是有意安排的迁移合同；只关闭自动事务后让文件跑通，还没有解释故障与回滚时会留下什么。
