用两个基镜像检查 Dockerfile 的目录合同

用受控双基阶段与四格路径预期区分 Docker WORKDIR 继承、绝对锚点及运行时 -w 的作用。

正文

核心要点

  • 相对 WORKDIR 把此前工作目录作为输入。
  • 配置、运行目录和 COPY 文件位置需要分别核对。
  • 运行时 -w 不会搬移构建阶段已复制的文件。

让两份本地基镜像只在 WorkingDir 上不同，再分别构建使用相对路径和绝对路径的子阶段，就能定位 WORKDIR 的继承问题。WORKDIR app 没有承诺绝对的 /app；基础镜像的当前目录属于它的输入。路径是否固定，应从镜像配置与文件实际落点一起判断。

同一条相对指令，需要四格预期

Docker 的 WorkdirRelativePath 检查说明明确指出，相对工作目录基于此前工作目录。基础镜像把目录从 /srv/a 改成 /srv/b，下游原样写 app，就会跟着改变。构建文件文字相同，不代表全部输入相同；FROM 继承的配置也参与了解析。

先为一个受控实验写出独立预期，避免碰巧选到工作目录为根的公开镜像，就以为相对形式总是稳定。下面四格只比较路径，不讨论依赖包版本或应用性能。

基阶段工作目录 子阶段 WORKDIR 预期子目录
/srv/a app /srv/a/app
/srv/b app /srv/b/app
/srv/a /app /app
/srv/b /app /app

Dockerfile 的 WORKDIR 条款说明，这条指令设置随后 RUN、CMD、ENTRYPOINT、COPY 和 ADD 使用的工作目录；目录不存在会创建。多次使用时，相对路径继续基于前一次 WORKDIR。与之不同，RUN 中执行 cd 只改变那次命令进程的状态，不是设置后续构建指令的目录合同。

用自造基阶段隔离路径变量

以下是未构建、未运行的完整教学项目。它要求可用的 Linux 容器构建器和 Docker CLI，在全新自有 context 中保存 Dockerfile 与 marker.txt。没有拉取镜像或启动容器，也没有以 build 检查代替运行验证。基础镜像版本在示例中固定为 alpine:3.20；真正执行时还应记录解析到的摘要，不能把标签当成不可变身份。

# Dockerfile.base
FROM alpine:3.20
ARG ANCHOR
WORKDIR ${ANCHOR}
CMD ["pwd"]

# Dockerfile.child
ARG BASE
FROM ${BASE}
ARG CHILD_WORKDIR
WORKDIR ${CHILD_WORKDIR}
COPY marker.txt .

marker.txt 的内容预先设为 workdir-probe 加换行，只用于识别本次文件。先以 docker build -f Dockerfile.base --build-arg ANCHOR=/srv/a -t workdir-probe-base-a . 构建第一份基镜像，再只把 a 改为 b 构建第二份。四份子构建使用 Dockerfile.child，BASE 分别取这两个标签，CHILD_WORKDIR 分别取 app 与 /app；例如第一格命令是 docker build -f Dockerfile.child --build-arg BASE=workdir-probe-base-a --build-arg CHILD_WORKDIR=app -t workdir-probe-relative-a .，其余三格按表格替换两个输入及独立输出标签。标签仅为独立实验示例，执行者应先确认没有占用同名本地镜像，或换成本轮唯一前缀；不要覆盖已有发布标签。

每条构建完成后立即保存退出状态和输出。任一构建失败，就把那一格标为失败，不继续拿旧标签对应镜像补证据。成功时记录本轮镜像 ID、基础摘要、Dockerfile 与 marker 哈希，再以镜像 ID 为后续检查对象。这样能把配置、容器和内容关联到同一份产物，避免第二次构建改变标签以后读到另一轮结果。

每格先用 docker image inspect 读取 Config.WorkingDir，再用 docker run --rm 运行默认 pwd。随后针对表格对应的绝对路径读取 marker，例如 relative-a 应读取 /srv/a/app/marker.txt，absolute-a 应读取 /app/marker.txt。三类观察各有任务：镜像配置说明默认目录，pwd 说明这次进程目录，绝对路径读取说明构建时文件落点。任何一项都不能替代另外两项。

工作目录正确，也可能没有读到本轮文件

这个实验的独立 oracle 是四格路径及 marker 的确切字节。只看到 pwd 为 /app，还不能证明 COPY 把新文件放在那里；文件可能来自旧镜像；目录观察与复制位置也承担不同的验证任务。反过来，某条绝对 cat 成功也不能证明进程默认目录正确，因为绝对访问本来就绕过了当前目录。

旧的COPY 属主文章讨论哪个用户有权写哪条路径，不能替这里决定路径到底在哪里。绝对 WORKDIR 也不授予权限，不消除挂载遮蔽，更不能保证应用读到正确配置。部署需要另查运行用户、卷和入口脚本；路径实验只为其中一个输入提供证据。

相对 WORKDIR 什么时候仍然合适

相对形式可以表达受控的子目录组合。例如先写 WORKDIR /srv，再写 WORKDIR app，起点就在当前阶段可见，而不是留给未知的上游。Docker 的检查规则针对没有先指定绝对起点的相对路径发出警告，并不是禁止一切相对目录。是否启用检查、构建器版本如何，也需要实际执行才知道，不能把文档中的规则名称当成本次已运行记录。

需要固定发布目录时，直接写绝对路径通常更容易审核。需要复用受控父目录时，可以追加相对段，但应能指出谁拥有父目录合同。继续叠加子目录以后，评审者要看累积结果，而不只看最后一个 app 字符串；更换 FROM 或切换阶段时，重新确认当前起点。

docker run -w 能搬回 COPY 放错的文件吗？

不能。容器运行文档的工作目录条款说明，-w 覆盖运行命令的默认工作目录，不存在的目录会创建。它没有重跑 Dockerfile 的 COPY，也没有承诺把别处文件移动到这里。对上面的相对组，加参数可以改变 pwd，却不能把原先的 marker 自动搬回 /app。

更有区分力的反例，是在相对组运行时加 -w /app。此时 pwd 可以显示 /app，但构建阶段复制的 marker 仍应在该组的原落点。若验收只看 pwd，运行覆盖会掩盖镜像配置中的问题。这个反例没有实际运行结果，预期来自构建时文件操作与运行时目录设置的分工。

这是运行时覆盖的新条件，不只是再问一次绝对与相对的区别。排查时应同时保存启动参数与镜像默认值；若入口脚本还执行 cd，则继续记录应用最终目录及解析后的绝对文件名。不要只修改运行参数让一条检查变绿，却让应用相对读取的文件仍旧缺失。

为了避免四份几乎相同的子阶段掩盖唯一变量，实验也可以拆成参数化的基础文件和子文件。两份基镜像分别只传 ANCHOR=/srv/a 与 ANCHOR=/srv/b；子构建只在 BASE 与 CHILD_WORKDIR 两项输入上组合。这样仍然实际构建四份镜像，而不是只在表格里计算四个字符串。基础文件与子文件都要进入哈希记录，命令行参数也是构建输入，不能因写成变量就漏掉。

构建缓存同样需要按结果身份解释。命令显示缓存命中，不表示读到旧错误目录，也不表示所有路径已验证；构建器可能正确复用相同输入的层。应检查最终镜像配置和 marker 字节是否匹配本格要求。为了凑出新日志强制关闭缓存没有必要，若确有怀疑，保留原始缓存结果再做独立对照，不覆盖最早的观察。

此外，复制到目录中的文件名与复制到一个指定文件名不是相同合同。示例保持 marker.txt 的名字，让绝对路径检查可独立列出；若改成 COPY marker.txt renamed.txt，应同步更新预期。目录解析、目标命名和读取方式任何一项改变，原四格的文件断言就需要重新确认，不能沿用旧的通过截图。

本例的完成条件是四份本轮镜像分别满足配置、进程目录和 marker 位置的合同。没有运行前，它们都是预期。实际执行记录应包含 Docker/buildx 版本、完整命令及即时退出值、镜像身份和容器输出。固定路径解决的是目录继承这个输入，验收结论也应停在这条边界。
