CMake 缓存 2026-11-10

缓存改成 prod，CMake 为什么还读到 local？

区分 CMake 普通变量与缓存的查找顺序、空值、unset 和 CMP0126，避免把遮蔽误诊为缓存未刷新。

正文

核心要点

  • 普通引用先查普通变量，再回退缓存。
  • 空绑定与 unset 的效果不同，FORCE 也受政策条件约束。
  • 脚本内存缓存演示不能代替真实构建树验收。

CMake 缓存已更新，普通引用仍可能读到旧的普通变量。${MODE} 先查当前可见的普通绑定，找不到才查同名缓存；$CACHE{MODE} 则直接查缓存。先把这两个值并排显示，再决定该修改哪一层，不要把每一次旧值都归因于缓存没刷新。

两层值同时存在，并不矛盾

CMake 3.31 的 set 文档说明了这条查找顺序。假设缓存 MODE 是 staging，当前普通变量 MODE 是 local，普通引用得到 local 完全符合规则。即使缓存刚被改成 prod，普通绑定仍可能遮住它。两份观察指向不同的存储层，不需要靠反复删除构建目录来让它们看起来一致。

这和生成器配置文章不是同一个问题。多配置生成器可能不使用 CMAKE_BUILD_TYPE 决定本次构建；这里即便使用一个毫无特殊含义的 MODE，查找也会先命中普通变量。先确认读的是哪份值，再讨论这个变量是否被某个生成器采用，才能避免把读取层和消费层的问题混到一起。

对需要保留用户配置的项目，缓存通常是一条输入边界。目录脚本又设置同名普通值，可能是有意的局部覆盖，也可能是遗留调试代码。删除缓存只能移除其中一层，不能解释局部覆盖为何存在。如果新一轮配置又执行那行普通赋值，界面里的缓存与日志里的值仍会不同。

一份脚本观察四次读取

下面是未执行的完整脚本，依据读取时标注为 CMake 3.31.12 的固定版本文档。使用三点二十一作为最低版本，并显式选择 CMP0126 NEW。保存为 shadow.cmake，在自有目录拟运行 cmake -P shadow.cmake。脚本模式只演示本次进程中的缓存条目，不生成构建系统，也不声称写入或更新真实的 CMakeCache.txt。

cmake_minimum_required(VERSION 3.21)
cmake_policy(SET CMP0126 NEW)

function(check_pair expected_normal expected_cache)
  if(NOT "${MODE}" STREQUAL "${expected_normal}")
    message(FATAL_ERROR "normal mismatch: '${MODE}'")
  endif()
  if(NOT "$CACHE{MODE}" STREQUAL "${expected_cache}")
    message(FATAL_ERROR "cache mismatch: '$CACHE{MODE}'")
  endif()
  message(STATUS "normal='${MODE}' cache='$CACHE{MODE}'")
endfunction()

set(MODE staging CACHE STRING "probe mode" FORCE)
set(MODE local)
check_pair(local staging)
set(MODE prod CACHE STRING "probe mode" FORCE)
check_pair(local prod)
set(MODE "")
check_pair("" prod)
unset(MODE)
check_pair(prod prod)

四组独立预期分别是 local/staging、local/prod、空字符串/prod、prod/prod。它们来自已声明的查找规则，不是先看打印结果，再把结果填回断言。检查函数遇到不符即 FATAL_ERROR，避免一份始终退出成功的日志程序伪装成验证。函数读取调用时可见的 MODE，却不修改它；实际运行前仍应确认本机版本与命令路径。

第二次读取最容易暴露误修：FORCE 已经把缓存改成 prod，普通引用却仍是 local。此时继续 FORCE 没有增加新的诊断信息。第三次和第四次则区分两种“清理”：设空留下一个已定义的普通变量，空值会遮住缓存；unset 创建未设置的绑定，使普通查找继续使用缓存。需要刻意保持空值时，不能把 unset 当作等价缩写。

FORCE 控制写入，不控制优先级

set 的 CACHE 形式默认不覆盖既有缓存条目，FORCE 用来允许覆盖。这一政策保护用户可配置的输入，但不是普通变量查找开关。CMP0126 文档进一步限定：NEW 行为不会因设置缓存而移除同名普通变量；OLD 在缓存不存在、原条目没有类型，或者使用 FORCE、INTERNAL 等列明条件下，可能移除普通绑定。

因此不能只写一句“FORCE 永远不影响普通变量”，也不能靠当前程序版本猜项目已经采用 NEW。最低版本声明、显式政策以及子项目配置都可能参与行为选择。本例把政策写出，目的是隔离查找问题，不是在要求所有旧工程立刻升级政策。迁移旧项目时应先保留旧行为记录，检查哪些局部覆盖曾依赖原政策被移除，再决定变化范围。

另一个反例是把所有 CACHE 赋值都改为 FORCE，以求每次日志一致。这样可能覆盖用户通过配置界面或命令行提供的选择。若项目意图只是设默认值，应让默认值保持默认；若项目需要不可修改的内部状态，应明确说明职责。不要因为一条读取遮蔽，就顺手把输入所有权也改掉。

函数里 unset 后，外层普通变量也消失了吗？

不会因此消失。cmake-language 的函数作用域条款说明，函数中的 set 或 unset 建立本作用域的绑定，供函数及其嵌套调用使用，函数返回后不保留。本题的新条件是“函数返回之后”，不能用脚本顶层 unset 的结果替它回答。

例如外层普通 MODE 是 local，缓存是 prod。函数内执行 unset(MODE)，函数内普通引用可以读取 prod；函数返回后，外层仍可读取 local。这应作为单独的前、内、后三点对照。若使用 PARENT_SCOPE，又是在明确修改上一层，不能混称为同一项局部清理。目录作用域还会从父目录复制初始绑定，不能想当然地把它当动态回到父文件逐行查找。

实际排查可先记录变量名、当前文件与函数、普通值、显式缓存值、政策状态。日志若包含秘密配置，应改用不暴露内容的诊断，不整份输出缓存。本例 MODE 只是无秘密的教学值。找到遮蔽位置以后，按合同决定保留局部覆盖、保留空值屏障，或移除绑定让缓存可见。

查找正确以后，还需问消费者是否真的使用这份值。假设日志已经读到 prod，但生成文件的分支在更早时点用 local 做过决定，那么更晚的 message 只能证明更晚的读取。应把赋值、条件判断和产生输出的顺序放在同一份跟踪中，找出哪一时刻的值参与决定。修改读取位置之后，也要检查目标配置或生成文件是否随之变化，不能只以一行诊断日志宣布构建行为已经修好。

命令行输入的类型同样可能影响旧政策。文档明确区分有值但没有类型的缓存条目，以及带类型的条目；这也是为什么复现场景应保存完整的 -D 参数，而不能只抄一个最终字符串。若真实项目要诊断持久缓存，应在独立构建树用自己的配置命令重复，记录写入前后的条目类型和实际消费位置。这里的脚本故意不承担那份构建树实验。

选择清理方式前可以先列出期望的失败状态：用户未提供值时是否用默认，用户提供空值时是否允许，局部覆盖是否应在函数退出后结束。三种要求不相同，不能靠统一 unset 得到答案。先决定空值是否具有领域含义，再把赋值和回退写成可检查的条件；即使脚本对照通过，也只证明这些条件下的查找关系。

源码成员文章要求检查最终哪些文件进入构建图；本题要求检查最终哪层值进入表达式。两者都不能由“配置命令没报错”代替验收。本文没有运行脚本或配置真实工程；后续验证应保存脚本哈希、CMake 版本、完整输出及即时退出值，并把脚本内存演示与真实构建树验证分开。
