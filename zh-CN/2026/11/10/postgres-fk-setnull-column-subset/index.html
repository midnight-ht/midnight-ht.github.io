删除作者只想清空 author_id，为什么 tenant_id 也被设成 NULL？

用PostgreSQL18的ON DELETE SET NULL列清单保留租户与帖子身份，独立验证同编号跨租户作者及失败分支。

正文

核心要点

  • 不指定SET NULL列清单会作用于整组引用列。
  • 只清空可选作者列，仍需MATCH SIMPLE与独立租户约束配合。
  • 检查完整跨租户身份状态，删除动作不能外推为更新或权限验收。

复合外键的 ON DELETE SET NULL 不会自动挑选可空列。不写列清单时，它会设置整组引用列；如果 tenant_id 仍是帖子主键的一部分，尝试清空租户列就可能被非空约束拒绝。PostgreSQL 18 可以写 ON DELETE SET NULL (author_id)，把这次删除动作限定到可选作者列，保留租户与帖子身份。

假设用户编号只在租户内唯一，帖子用 tenant_id 与 author_id 引用作者。产品允许删除作者，但帖子必须留下，而且仍属于原租户。此时把错误“修复”为级联删帖，虽然可能不再触发同一个错误，却改变了数据生命周期；把 tenant_id 改成可空，也牺牲了原本必填的归属。先写出删除后必须保留的行和键，再选择参照动作。

外键列清单与动作列清单不是一个清单

PostgreSQL 18 外键说明明确指出，SET NULL 可以指定设置哪些引用列，通常不指定时会设置所有外键列。官方租户、用户与帖子示例正是为了保留 tenant_id 而只清空 author_id。列清单限制的是参照动作的写入范围，不是缩小原来的匹配关系。

因此，外键仍应使用完整的 (tenant_id, author_id) 去匹配用户的 (tenant_id, user_id)。不能为只改作者列就把外键也改成只引用 user_id，那会丢掉租户范围，而且单独的用户编号在当前模型里并不唯一。被引用端需要合格的主键或唯一性条件；本文使用复合主键，不假定跨租户编号全局唯一。

动作也不会免除其他约束。即使它来自数据库自动处理，最终写入仍要满足非空、主键及有关外键要求。只清空 author_id 的合同必须真的允许这个字段为空，而 tenant_id 的合法性需要独立保护。下面显式保留帖子到租户表的外键，避免把“没有作者”误当作“任何租户编号都有效”。

四条帖子，先固定完整最终状态

下面是未执行的教学 SQL，只适合自有可丢弃空库。tenant_id 是逻辑租户归属及复合主键组成列；示例没有物理分区、行级安全策略或权限验证。两个租户都有编号七的用户，专门检查删除是否受完整复合键限定。

CREATE TABLE editorial_tenants (tenant_id integer PRIMARY KEY);
CREATE TABLE editorial_users (
  tenant_id integer NOT NULL REFERENCES editorial_tenants(tenant_id),
  user_id integer NOT NULL,
  PRIMARY KEY (tenant_id, user_id)
);
CREATE TABLE editorial_posts (
  tenant_id integer NOT NULL REFERENCES editorial_tenants(tenant_id),
  post_id integer NOT NULL,
  author_id integer,
  PRIMARY KEY (tenant_id, post_id),
  FOREIGN KEY (tenant_id, author_id)
    REFERENCES editorial_users(tenant_id, user_id)
    MATCH SIMPLE ON DELETE SET NULL (author_id)
);
INSERT INTO editorial_tenants VALUES (1), (2);
INSERT INTO editorial_users VALUES (1,7), (1,8), (2,7);
INSERT INTO editorial_posts
VALUES (1,101,7), (1,102,8), (2,201,7), (1,103,NULL);
DELETE FROM editorial_users WHERE tenant_id=1 AND user_id=7;
SELECT tenant_id,post_id,author_id
FROM editorial_posts ORDER BY tenant_id,post_id;
SELECT tenant_id,user_id FROM editorial_users ORDER BY tenant_id,user_id;
SELECT tenant_id FROM editorial_tenants ORDER BY tenant_id;

独立预期是帖子按排序得到 (1,101,NULL)、(1,102,8)、(1,103,NULL)、(2,201,7) 四行。只改变第一条的作者，不改变任何帖子主键，也不删除帖子。用户表应剩 (1,8)、(2,7)；租户表仍有一和二。这些是按文档推导的预期，不是实际执行输出。

两项对照不能省略：原本就无作者的帖子一百零三保持不变，说明不是把所有空作者重新解释；另一个租户的帖子二百零一仍引用它自己的七号用户，说明不能只凭 author_id 相同便清空。验收应比较整份有序元组或等价的身份映射，不能只看四条帖子都还存在，或只检查目标作者已删除。

为什么明确选 MATCH SIMPLE

CREATE TABLE 的外键参考说明，缺省 MATCH SIMPLE 在任一引用列为空时允许免于匹配。这里 (tenant_id, NULL) 正是“帖子仍归这个租户，但没有作者”的合法状态；独立的 tenant_id 外键继续要求租户存在。完整的非空作者键仍必须匹配同租户用户。

MATCH FULL 不是这个合同的更严版本。它要求空值豁免时整组引用列都为空；租户非空、作者为空会成为混合状态而失败。站内复合外键的半填匹配已解释这种插入规则。本题的新增判断是删除动作改哪些列；不把旧文的完整插入矩阵重讲一次，也不靠放松租户身份让动作通过。

可以另外测试两种输入：tenant 一、author 九十九而没有对应用户，应拒绝；tenant 九十九、author 为空，也应被独立租户外键拒绝。这两个反例分别证明完整作者引用与必填租户存在性。外键并不证明当前调用者有权在该租户删除用户；那是服务权限的另一份证据。

保留两份会失败的独立结构

第一份变体只删去 SET NULL 后的 (author_id)，其他结构和输入保持一致。删除目标用户时，它会尝试把 tenant_id 也设为空，预期违反非空要求而失败；不能把原本的主键错误描述成“作者字段不能空”。在新的自动提交测试中，失败的删除语句不应留下半份修改，原三条用户与四条帖子都应保持。

第二份变体保留动作列清单，却改用 MATCH FULL。为让失败真正发生在删除阶段，初始化时不要加入原本就无作者的帖子一百零三，否则建好表后插入数据便先失败。只用有作者的三条帖子准备数据，再删除用户，预期因产生混合空值而失败。测试如果用了显式事务，应先记录异常与回滚，再检查状态，不在已经失败的事务里继续把后续错误当成新证据。

本文没有运行任一变体，也不承诺具体异常文字。上线迁移还需核对真实约束定义、历史引用、其他触发器与删除入口；不能从一条教学 DDL 推出迁移已安全。子表查找的成本另见外键与子表索引，正确动作并不等于删除没有负载。

ON UPDATE 也能照抄这个列清单吗？

不能。PostgreSQL 18 的 CREATE TABLE 参考明确规定，SET NULL 的列子集只能用于 ON DELETE；被引用键更新时，不能把相同写法搬到 ON UPDATE。该版本还明确不支持在 temporal foreign key 上使用 SET NULL。本例是普通外键，不包含 PERIOD，不能从它推广到时态关系。

若业务允许改作者编号，应另外选择更新策略并建立独立预期：是传播新键、阻止修改，还是通过应用显式重新关联。不要把删除作者的可选关系政策自动用作改键政策。交付时保留两份问题的分界：这篇只证明设计上如何限定删除动作的列范围，真实数据库、权限、迁移与更新路径仍需各自验收。
