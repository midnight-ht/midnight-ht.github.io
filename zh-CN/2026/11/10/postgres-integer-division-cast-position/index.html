SQL 最后转了 numeric，比例为什么还是零？

用除法前后类型和独立数值预期定位整数截断，区分小数计算、零分母政策与最终显示精度。

正文

核心要点

  • 整数除法向零截断，后置CAST不能恢复分数。
  • 需要小数时先转换操作数，再决定scale和单位。
  • 零分母、负数和绑定参数类型应分别验收。

把整数除法的结果再转成 numeric，不能找回已经截掉的小数。PostgreSQL 18 中，整数操作数相除会向零截断；需要小数比例时，应在除法发生前转换一个操作数。最终列的类型是 numeric，只能证明最后的结果经过转换，不能证明内部运算保留了分数。

假设一份报表有一次成功、四次尝试，业务期望比例为四分之一。SQL 写成 (successes / attempts)::numeric，结果仍为零，页面格式化后可能显示零点零零。把显示位数增加到六位没有帮助，因为问题发生在除法表达式内，而不是页面少显示了几位。先看信息在哪一步丢失，再选择输出格式。

把转换放在表达式的哪一层

PostgreSQL 18 数学运算符表明确列出整数除法向零截断，并给出正负数示例。类型转换章节则区分对已知类型表达式的转换与给字符串常量指定类型。本题是已有整数表达式的值转换，不是重新解释一份原始分数字符串。

(1 / 4)::numeric 的括号先形成整数除法表达式，其结果为零，外层再把这个零转换成 numeric。相反，1::numeric / 4 让除法面对 numeric 操作数，不能再按两个整数的除法规则理解。1 / 4::numeric 在这个简单例子中也能提前改变操作数；代码评审应看转换落在谁身上，而不是只搜索整行有没有 numeric。

这也解释了为什么把外层结果存进 numeric 列仍可能留下错误。目标列可以接收一个合法的零，它没有足够信息判断你原本想算四分之一。数据类型约束与业务数值正确是两项验收；没有报错，只说明当前表达式能够被计算和保存。

先写数值预期，再运行类型探针

下面是未执行的完整教学查询，不读取业务表。NULLIF 用于让分母为零的那一行得到空结果，便于把其余样本放在一张表中比较；这不是替产品决定零次尝试应该怎样展示。

WITH sample(a, b) AS (
  VALUES (1, 4), (-5, 2), (0, 3), (3, 0)
)
SELECT a, b,
       (a / NULLIF(b, 0))::numeric AS late_cast,
       a::numeric / NULLIF(b, 0) AS early_cast,
       pg_typeof(a / NULLIF(b, 0)) AS division_type,
       pg_typeof(a::numeric / NULLIF(b, 0)) AS promoted_type
FROM sample;

独立预期是：一除以四，late_cast 为零，early_cast 为四分之一；负五除以二，前者为负二，后者为负二点五；零除以三两路都是零；三除以零这一行，两路由于分母转换为空而返回 NULL。division_type 应为 integer，promoted_type 应为 numeric。这里的值与类型均是规则推演，尚未执行，不是数据库输出摘录。

负数样本不能删除。向零截断与向负无穷取整不同，负二点五向零截断为负二，而 floor 意义下向下取整是负三。若团队用“整数除法向下取整”描述报表规则，正数样本可能全部通过，冲销或退款引入负数后才暴露歧义。先写业务选择的方向，不能把语言里的模糊说法当成数据库合同。

另开一条无保护的 SELECT 3 / 0; 作为拒绝探针，预期为除零错误，不与上面 NULLIF 分支混写成“PostgreSQL 除以零就返回空”。条件表达式文档定义 NULLIF 在两值相等时返回空。它是查询主动选择的处理路径；如果零次尝试应显示“不适用”，下游也要保留这层区别，不能自动把空值补成真实的零成功率。

小数计算与输出精度还要分开

提前转换解决的是当前除法使用哪种数值运算，不会替你选择最终精度。numeric 类型说明区分 precision 和 scale，并说明存入受限 scale 的列时会舍入。四分之一容易精确表示，不代表三分之一可以用有限位小数无损展示，更不能从这个示例推出所有数值运算都精确无限。

如果报表要百分比，先定义存储的是比例还是乘一百后的百分数，再决定何处舍入。一个接口返回零点二五，另一个把它当作百分之零点二五，虽然都用了 numeric，业务仍差了一个单位。验收表应同时写原始计数、比例单位、输出类型和允许显示误差；把这些信息只放在前端格式化函数里，会让导出和其他消费者继续猜测。

选择整数运算也可以合理。例如业务明确只发放完整批次，余量留待下一次处理，就可能需要截断。但应保留被除数、除数和余量的含义，而不是因为旧代码碰巧返回整数便把它确认为规则。本站UNION 的类型解析时点讨论另一种外层转换来得太晚的情况；那里可能根本无法解析，本题则是表达式能执行，结果却已损失分数。

还有一种反例，能检查修复是否只停在类型上。假设两组数据分别是一成功四尝试、九成功十尝试，业务要求所有尝试合并后的成功率。独立分子是十，分母是十四，目标为七分之五。若先算每组比例再简单平均，得到的是零点五七五；两条路径即使都提前转成小数，也没有在算同一项指标。这是手工推导，未执行聚合查询。

因此，转换修好以后，验收还应保留原始分子、分母与组合规则。两组等权平均适合每组具有同样业务权重的定义，按总尝试合并则给每次尝试同样权重；不能靠哪个值更顺眼决定。先让指标负责人选定口径，再验证转换放在对应算术之前。否则开发者可能修掉了整数截断，却用一份合法小数掩盖另一种计算错误。

常量查询正确，绑定参数后为什么不同？

绑定参数给问题增加了实际输入类型。字面量探针只能证明那些字面量下的规则，不能代替驱动将参数声明成什么类型的证据。保存驱动版本、完整 SQL 和参数类型；在同一个连接与相同绑定方式下检查 pg_typeof，再比较数值结果，而不是仅比较打印出来的字符串。

若一边绑定整数、另一边绑定 numeric，运算符选择条件已经改变。应由查询或接口明确数值合同，不依赖调用方偶然传来带小数点的文本。先让一除以四、负五除以二和零分母三类预期都对应明确处理，再确认页面如何显示；这能把算错、政策未定和格式不同分成可定位的问题。
