用open与closed两份样本读懂composedPath

用open/closed完整页面区分重定向、路径可见性与跨边界标志，另说明分发结束后的路径清理。

正文

核心要点

  • 外部target和内部派发节点可能不同。
  • 当前监听位置决定closed树路径中哪些部分可见。
  • 同步记录路径，公开动作应采用明确组件协议。

同一个内部按钮发出的事件，在Shadow DOM外部可能把宿主显示为target；composedPath也只返回当前监听位置有权看到的路径。先固定观察者在树的哪一侧，再讨论哪个节点代表动作来源。把路径首项当作永远可见的私有按钮，会使委托逻辑依赖组件没有承诺的细节。

假设自定义元素内部有一个保存按钮，页面在document上监听事件。普通浅层DOM里的target.closest思路，到了Shadow边界外却找不到内部按钮。此时增加选择器优先级、反复读取target，不能让被重定向的对象重新变成原节点。应该先区分目标重定向、事件是否跨边界，以及路径对当前监听器隐藏了什么。

观察者位置是输入条件

DOM Standard的重定向算法会根据两个对象的树关系，沿shadow root的宿主向外寻找适当目标。对组件外部监听器，内部按钮可能被宿主替代。这是原生事件模型的一部分，不表示按钮已经删除，也不表示监听器一定注册错了。

composedPath算法则以currentTarget及closed-tree相关层级处理路径。它不是一个无条件返回所有最深内部节点的调试后门。同一个事件，在closed树内部和树外部读取，允许看到的部分可以不同。open与closed也不应只用“能不能调用shadowRoot”一句话解释完，事件观察本身就有封装规则。

下面使用自定义probe事件，刻意把派发节点固定为内部button。这样独立预期不需要猜测用户究竟点到按钮文字、图标还是嵌套span。它不是一次真实点击，也没有保存业务；真实页面仍须另测用户输入和组件动作。

只改变mode的完整样本

这份HTML尚未在浏览器执行。它建立两个宿主，内部按钮相同，唯一有意变化的封装条件是mode。内部与document监听器都同步记录target和路径；每轮创建新的Event，不把前一轮分发状态带入下一轮。

<!doctype html>
<meta charset="utf-8"><title>Shadow event visibility — unexecuted teaching sample</title>
<div id="open-host"></div><div id="closed-host"></div><pre id="log"></pre>
<script>
const out = document.getElementById('log');
const rows = [];
const describe = node => node instanceof ShadowRoot ? '#shadow-root' :
  node === window ? 'window' : node === document ? 'document' : node.id || node.nodeName;
const observe = location => event => {
  rows.push({location, composed: event.composed, target: describe(event.target),
    path: event.composedPath().map(describe)});
  out.textContent = JSON.stringify(rows, null, 2);
};
document.addEventListener('probe', observe('document'));
for (const mode of ['open', 'closed']) {
  const host = document.getElementById(mode + '-host');
  const root = host.attachShadow({mode});
  const button = document.createElement('button');
  button.id = mode + '-button'; button.type = 'button'; button.textContent = mode;
  root.append(button);
  root.addEventListener('probe', observe(mode + ' internal'));
  button.dispatchEvent(new Event('probe', {bubbles: true, composed: true}));
  button.dispatchEvent(new Event('probe', {bubbles: true, composed: false}));
}
// Expected externally: target host for both modes; open path includes its button/root,
// closed path excludes its internal button/root. Non-composed probes stay internal.
// These are synthetic events, not physical input or browser test receipts.
</script>

先在纸面写出预期。允许跨边界的两次外部记录，target分别是open-host和closed-host。open那条外部路径包含open-button及对应ShadowRoot；closed那条外部路径不包含closed-button和它的ShadowRoot。closed内部的监听器仍可读取自己这一侧的内部路径。把“外部隐藏”写成“事件从来没有经过内部按钮”，就是读错了观察范围。

不允许跨边界的教学事件只留在各自shadow树内，不进入document监听器。它与bubbles回答不同问题：前者涉及跨Shadow边界，后者涉及冒泡传播。给自定义事件只设置bubbles:true，然后期待外部document收到，并不能验证跨边界协议正确。

这些名单是按算法和明确派发节点推导的独立预期，不是浏览器控制台回执。验收要比较节点身份，不仅比较路径长度；两条长度相同的数组也可能暴露不同对象。若后来在按钮里加span，且改为从span派发，应相应调整最前面的节点预期，不能继续复制原名单。

外部需要的是节点，还是动作

open树的路径让外部代码能够定位内部按钮，并不意味着页面应长期依赖它。组件下一版可能把一个button改成两个控件，而公开的“保存请求”动作仍然相同。若页面真正需要知道的是用户请求保存哪条记录，就应考虑由组件公开语义事件，detail只带双方约定的稳定字段。

这是一项设计选择，并不是每个组件都必须增加同名事件。可以在内部处理原始交互，向宿主派发明确的save-request，再根据调用者需要选择bubbles和composed。公开事件不应顺手携带整棵私有DOM或未经约束的输入，接收方也仍需检查业务资格。事件传到了document，不会替代权限判断或服务端保存结果。

反例是closed组件没有公开操作协议，页面却把composedPath()[0]强制断言成HTMLButtonElement。外部读到的首项可能只是宿主；放宽类型断言不会创造不存在的内部节点。先确定组件承诺暴露什么，再决定外部怎样委托，比让页面猜私有结构更清楚。

同目标监听与传播停止讨论的是后继处理器是否继续运行。本题没有调用任何停止方法：即使传播完整进行，target仍可被重定向，closed路径仍可被筛选。不要把所有“外部没有拿到按钮”的现象都归成有人stopPropagation。

把Event留到下一任务，还能取同一条路径吗？

分发结束后不能依靠原Event重新取得当时路径。同一标准的分发清理步骤会清空事件路径；在下一任务才调用composedPath，面对的是清理后的状态。需要保留诊断名单时，应在同步监听器中读取，并保存明确所需的节点身份或可分享的描述。

这与“保存节点引用以后节点能否变化”又不同。拿到一份路径数组，不会冻结节点文字、属性或业务绑定。若只是记录问题来源，可以同步保存id和监听位置；若后续要使用节点，应另外判断它是否仍连接、是否仍属于当前业务对象。已有的currentTarget分发寿命完整讨论后一个问题，不必把那套异步写回示例再复制到这里。

路径中的节点类型也不相同。ShadowRoot不是Element，Window也不是普通按钮；对每项直接调用closest可能产生类型错误。样本先把对象转成明确描述，真实委托则应限定允许处理的节点类型与范围。这个检查保护的是路径消费者，不会改变外部原本能够看到的封装边界。

待执行验证分别保留open外部、closed外部、closed内部和non-composed四类记录，再比较同步与明确下一任务的读取。报告中写明事件从哪个节点派发、监听器在哪里、采用哪种mode和标志。只有这些条件相同，路径名单的差异才值得归给封装规则；单独截一张target为宿主的图片，还没有解释整个事件合同。
