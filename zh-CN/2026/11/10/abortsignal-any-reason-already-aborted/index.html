AbortSignal.any 的 reason：DOM 规则与 Node v24.21.0 对照

分开DOM原因选择规则、同步记录器正例，以及本地Node在监听和读取条件变化下的真实差异。

正文

核心要点

  • 预先中止与未来中止采用不同规范选择条件。
  • 本机原因差异必须连同监听、读取时点和版本保留。
  • 调用返回后push来源不会使已有组合自动扩容。

DOM规范对预先中止与未来中止规定不同的reason选择条件；这次本地Node的观察还需要连同监听和读取时点记录。先把规范预期与实际输出分开，才能避免把一次局部结果写成所有运行时的统一承诺。

假设一个本地预览同时接受手动取消与离开页面两类信号，界面要按来源显示提示。把二者交给AbortSignal.any很方便，但组合信号不是原因历史，也不意味着数组里排第一的来源在未来永远优先。本篇没有发出网络请求，控制器只生成本地事件；它也不承诺取消会撤回服务端已完成的操作。

先写出两种时间条件

DOM Standard的依赖信号创建算法先按输入顺序检查是否已有中止信号。找到第一个就取它的reason并返回。因此两个来源都提前中止时，传入顺序决定这一轮选择，不需要比较它们各自在多久以前中止。

如果构造时没有中止来源，组合会建立依赖关系。同一标准的signal abort算法把来源信号的原因传播到尚未中止的依赖，已经中止就不重新处理。按这份规范的预期，先发生的未来中止确定原因，后来者不会覆盖它。这是规范合同，不是从本机某一次输出反推的规则。

空输入不会因为没有来源而自动中止，返回的也是Signal而非可手动调用abort的Controller。消费者若可能收到预先中止的信号，应在工作入口检查aborted或使用相应检查方法；后来才加监听，不会重放已经发生的abort事件。创建组合、进入工作与订阅时点必须明确，不能只在出错以后补一条监听等它再发生。

带同步记录器的本地对照

下面完整脚本把控制与观察集中到少量明确辅助函数；读取只发生在调用处。它在future上先安装同步abort记录器，再依次中止两个来源。reason使用对象，并比较身份，避免仅按name或字符串猜来源。每组新建控制器，不把已经中止的对象当作下一轮可复位的信号。

// Complete local comparison. Helper reads occur only where explicitly called.
function source() {
  const controller = new AbortController();
  return [controller.signal, reason => controller.abort(reason)];
}
const isAborted = signal => signal.aborted;
const reasonOf = signal => signal.reason;
const onAbort = (signal, callback) => signal.addEventListener('abort', callback);
const combine = signals => AbortSignal.any(signals);

const [manual, stopManual] = source(), [navigation, leave] = source();
stopManual({kind: 'manual'}); leave({kind: 'navigation'});
const prior = combine([navigation, manual]);
console.log('prior', isAborted(prior), reasonOf(prior) === reasonOf(navigation));
const [later, stopLater] = source(), [earlier, stopEarlier] = source();
const future = combine([later, earlier]), records = [];
onAbort(future, () => records.push(reasonOf(future)));
stopEarlier({kind: 'earlier'}); stopLater({kind: 'later'});
console.log('recorder', reasonOf(future) === reasonOf(earlier), records.length);
console.log('empty', isAborted(combine([])));
let lateEvents = 0;
onAbort(prior, () => lateEvents++);
console.log('late', isAborted(prior), lateEvents);

for (const mode of ['no-listener', 'listener', 'read-after-first']) {
  const [first, stopFirst] = source(), [second, stopSecond] = source();
  const combined = combine([first, second]);
  const earlyReason = {kind: 'earlier'}, lateReason = {kind: 'later'};
  if (mode === 'listener') onAbort(combined, () => {});
  stopSecond(earlyReason);
  if (mode === 'read-after-first') {
    console.log('early', isAborted(combined), reasonOf(combined) === earlyReason);
  }
  stopFirst(lateReason);
  console.log(mode, isAborted(combined), reasonOf(combined) === earlyReason,
    reasonOf(combined) === lateReason);
}

const [originalSource, stopOriginal] = source(), [added, stopAdded] = source();
const inputs = [originalSource], original = combine(inputs);
inputs.push(added);
const rebuilt = combine(inputs);
stopAdded({kind: 'added-later'});
console.log('extension', isAborted(original), isAborted(rebuilt),
  reasonOf(rebuilt) === reasonOf(added));
stopOriginal({kind: 'original-source'});
console.log('after original', reasonOf(original) === reasonOf(originalSource),
  reasonOf(rebuilt) === reasonOf(added));

独立预期是prior的两个布尔值都为真；recorder分支为真、一次记录；空列表为false；晚监听分支显示已中止，但事件计数为零。在Node v24.21.0，实际输出与这些预期一致。这个正例包含同步记录器这一条件，不能把它的结果扩展成所有观察方式都已通过。

最初没有给future装监听、也没有在第一次中止后读取组合状态的脚本，产生了不同输出。该原始失败和脚本字节已保留，没有用后来的正例覆盖。退出码为零只说明脚本正常结束，不能替代每个布尔值是否符合独立预期的检查。

同一Node版本的不同观察怎样记录？

上面完整脚本的三分支诊断为每一轮新建相同来源和组合，只改变监听与读取条件。三轮都先中止列表第二个来源，再中止第一个来源；最后分别比较组合原因与早、晚原因的对象身份。代码只用于复核局部观察，不推断运行时内部机制。

同一版本的独立实测记录是：no-listener分支最后两个原因比较为false、true；listener分支为true、false；read-after-first在第一次中止后读到true、true，第二次以后仍为true、false。也就是未订阅且两次操作结束后才首次读状态的分支，观察到后一次原因；另外两种条件保留先发生的原因。

这些结果与无监听分支的DOM独立预期不同，必须保留为差异，不能重新写成“所有测试通过”。它没有证明所有Node版本如此，也没有验证任何浏览器，更没有定位内部原因。若产品依赖原因分类，应在支持环境中保存精确代码、版本、同步监听位置和读取时点；不要从一个环境的一次现象推导跨平台优先级。

主动取消、离开页面和超时也不应只靠错误名统一归类。来源可以使用受控的原因值，消费方按自己的合同解释；遇到第三方包装还要确认它有没有保留原原因。日志能说明当前本地对象关系，不会自动证明后台任务终止或事务未提交。取消请求与旧结果归属解释后一个应用边界，这里不重复设计搜索组件。

创建后向原数组push新信号，旧组合会扩容吗？

不会因为这个数组修改自动增加来源。Web IDL的sequence转换消费可迭代输入并返回IDL序列，DOM随后按取得的来源建立依赖关系。讨论范围是普通数组在any调用返回后的push，不是自定义迭代器还在运行时修改输入的所有情形。

完整脚本末段保留原数组与重建组合。独立预期是added中止后，original仍未中止，rebuilt已中止且原因来自added；first后来中止时，original取first原因，rebuilt仍保留added原因。本地运行结果符合这一对照。旧组合并未订阅新增来源，重新调用any得到的才是包含新来源的另一份组合。

这也不是让应用在每个渲染里无目的重建组合。消费者要知道自己使用的是哪份Signal、有哪些来源、监听由谁清理；原数组内容变化不等于已启动操作也换用了新信号。若重建发生在工作之后，还需明确旧工作是否继续、是否创建新任务，不能只替换一个变量就宣布所有使用者已经迁移。

交付取消分类时，保留三份不同结论：DOM规定什么、当前代码在当前运行时观察到什么、应用最后采用什么提示策略。本篇的本地正例与差异矩阵不替浏览器验收，也不证明资源清理；readFile取消与句柄责任补充另一项具体API范围。没有相应执行证据的层级，仍应单独留待验证。
