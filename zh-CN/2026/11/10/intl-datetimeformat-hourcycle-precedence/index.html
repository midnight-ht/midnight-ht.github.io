写了h23，为什么时间仍显示12小时制？

追踪最终选项、locale的hc扩展与hour12覆盖关系，用固定UTC瞬间的本地输出区分偏好和有效格式。

正文

核心要点

  • hour12非undefined时会覆盖hourCycle控制。
  • 精确hourCycle与locale偏好需要按解析优先级判断。
  • 有效格式选项不是构造参数的原样备份。

配置里已经写了hourCycle:"h23"，不代表最终格式一定采用它。若合并后的对象还保留hour12:true，时制解析会先处理这个布尔选择。排查时先保存传给构造器的完整选项，再看resolvedOptions，别从调用者那一小段配置推断实际结果。

假设报表组件希望统一使用零到二十三小时，通用默认值却要求十二小时显示。局部调用只追加hourCycle，旧hour12仍然留着。页面出现上午或下午标记，维护者便去更改timeZone，结果把显示时刻也改了，却没有解决时制选择。这是配置合并的教学场景，没有真实报表或用户设置被修改。

优先级不是对象属性的书写顺序

ECMA-402当前草案的CreateDateTimeFormat算法单独处理hour12：当它不是undefined时，将hc相关解析选项置为null，随后按locale数据取得相应的十二或二十四小时变体。因此同一个对象同时带hourCycle和hour12，并不是精确字符串自然战胜布尔值。

本次读取的文档标题是2027版国际化规范草案，不能把它写成已经发布的未来标准。选项如何解析属于这份规范的合同，最终地区数据和格式文字仍与实现有关。工程记录既要注明规范依据，也要保留自己实际运行的环境，不能只写“JavaScript就是这样”。

在没有hour12覆盖时，显式hourCycle选项可以覆盖locale中的hc扩展偏好。例如locale表明偏好h12，而选项明确要求h23，应观察到精确选项参与解析后的结果。再上层才是没有明确指定时采用的地区默认。对象里先写hour12还是后写hour12，不会改变这些算法优先关系；配置合并决定的是最终哪个属性值留下。

因此，检查共享默认值时应区分“没有这个字段”“字段值为undefined”和“字段值为false”。false是明确的二十四小时选择，不是没有偏好。若业务只允许一个控制入口，可以在配置规范化时拒绝冲突，或按明确策略删掉另一个字段；不要悄悄让两个表面上同义的开关同时表达不同意图。

固定瞬间与时区，再做三组对照

下面脚本使用同一UTC瞬间、相同地区标识与小时分钟组件。三组只改变时制选项，分别观察locale扩展、显式h23，以及被hour12:true覆盖的情况。输出同时保留原选项、resolvedOptions和formatToParts，避免仅凭格式字符串里的一个数字猜规则。

const instant = new Date('2026-11-10T00:30:00Z');
const common = {timeZone: 'UTC', hour: 'numeric', minute: '2-digit'};
const configure = extra => Object.assign({}, common, extra);
for (const [name, options] of [
  ['locale hc', common],
  ['explicit h23', configure({hourCycle: 'h23'})],
  ['boolean wins', configure({hourCycle: 'h23', hour12: true})]
]) {
  const formatter = new Intl.DateTimeFormat('en-US-u-hc-h12', options);
  console.log({name, options, resolved: formatter.resolvedOptions(),
    parts: formatter.formatToParts(instant)});
}
// Independent semantic expectations: locale hc h12; explicit h23; boolean case 12-hour cycle.
// The h23 case represents hour zero at UTC midnight; do not assert a cross-locale full string.

独立预期是第一组使用h12，第二组使用h23，第三组采用十二小时变体。在当前Node v24.21.0运行，resolvedOptions的hourCycle依次是h12、h23、h12；对应小时部分依次为12、00、12。第二组仍描述同一个UTC瞬间，并没有把事件发生时间减去或增加几个小时。

这份输出证明该本地环境下的三组对照，不证明所有地区的标点、空格、上午文字都逐字相同。第三组在本次en-US数据里为h12，也不能据此承诺任何地区的hour12:true永远等于同一个精确cycle。若把完整格式字符串写进跨地区快照断言，应先确认产品是否真的要求这些字面细节稳定。

formatToParts便于按语义位置观察小时、分钟和dayPeriod。它不是让应用随意丢掉所有本地化标点的理由；重组显示仍需尊重产品的语言与可访问性要求。此处只用它做诊断，并没有实现一套自定义日期排版引擎。

二十四小时偏好与午夜零开头不同

h11、h12、h23、h24区分具体小时范围。十二或二十四小时的布尔偏好没有独立说明所有午夜细节；hour12:false最终采用哪一种二十四小时变体，要沿相应locale数据判断。若验收明确要求午夜按零小时表达，就应让精确hourCycle意图在最终配置中保留下来。

反例是把hour12:false和hourCycle:h23都留着，再把某台设备出现零开头当成永远保证。那台设备上的结果可能恰好一致，却没有证明冲突配置表达了正确合同。应删除不需要的控制项，再记录resolvedOptions实际采用什么；若环境不支持所需行为，则明确回退或不满足，而不是改瞬间来让截图接近。

同样，时区决定以哪里的钟表时间展示瞬间，不负责覆盖时制选项。遇到“十二点还是零点”的问题，先分清是在谈同一瞬间的地区换算，还是在谈小时数字的周期。已有的日期解析、瞬间与展示时区讨论前一种语义，本题不重复纯日期缺偏移的规则。

测试时可以选择午夜和下午两个输入，记录最终配置与解析结果，避免只用一个下午时刻就漏掉h23与h24的区别。但预期应该来自产品所需语义和规范，而不是把当前format结果复制到预期变量。地区数据变化也可能影响格式文字，语义断言与字面断言要分别有理由。

只格式化年月日，为什么resolvedOptions没有hourCycle？

因为输出根本没有小时组件时，不应假定所有时制字段都会作为有效格式的一部分出现。resolvedOptions条款描述的是实际解析选项，不是一份原样返还构造参数的配置备份。先确认hour或timeStyle是否产生小时格式，再追查时制字段。

这个条件与前面的冲突不同。三组主例都明确要求hour，方便观察时制；如果后来删除小时只保留日期，就应更新预期，不把字段缺失误报为hourCycle被浏览器忽略。记录原始传入对象仍然有用，但它回答“请求了什么”，不回答“有效格式包含什么”。

交付一个时间组件时，先写清允许用户配置哪个入口、冲突怎样处理、展示采用哪一时区，再用目标运行时核对午夜与普通时刻。本次只运行了本地三组格式化脚本，没有浏览器截图或跨设备验收；让这些条件跟着测试记录一起保留，比在每个调用处再加一项看似更精确的选项更容易维护。
