HSET 返回 0，为什么新值已经写进去了？

用新增、覆盖、同值与混合写入区分HSET回复计数和最终字段状态，避免把0包装成失败。

正文

核心要点

  • HSET回复数的是新增字段，不是修改值或成功标志。
  • 覆盖和同值写入都可能返回0，需分别核对状态。
  • 丢失回复后的重试计数不能恢复第一次执行经历。

HSET 返回零，不代表更新失败。它的整数回复统计新增加的字段数；覆盖已有字段时，即使新值与旧值不同，也可能没有新增字段，因此返回零。应用若把这个结果直接转成成功布尔值，会把合法覆盖送进错误分支。

假设用户把昵称从 old 改成 new，缓存封装调用 HSET 后得到零，接口便返回“保存失败”。随后读取却已经是 new。先不要把这两个观察当作存储不一致：前者被封装错读成是否成功，后者是在看字段值。它们原本就不是同一项测量。这个场景是教学假设，没有调用用户服务或连接真实 Redis。

回复究竟数了什么

Redis HSET 官方命令文档说明，命令设置指定字段，覆盖已经存在的字段；键不存在时会创建一个哈希键。RESP2 与 RESP3 的整数回复含义都是新增字段数。因而，创建一个新字段返回一，与修改一个现有字段返回零，可以同时属于正常执行结果。

计数也不是“值发生变化的字段数”。把 name 从 old 写成 new，以及把已经是 new 的 name 再写成 new，都没有增加字段。仅凭零不能区分两者，更不能从零倒推出旧值等于新值。如果业务要记录是否实际改变过内容，需要单独设计那项判定，不能替 HSET 的回复换个解释。

字段与键也有不同粒度。一个哈希键里已存在 name，新增 city 时，返回值反映新字段，而不是“整个键是否第一次创建”。将结果命名为 key_created 会在已有哈希上新增字段的场景中产生另一种误报。评审接口名时，应把 added_fields 写清，而不是把一个数含糊地叫 affected、changed 或 success。

同一个自有哈希的四次写入

下面是未执行的 redis-cli 教学命令。只在自己创建的可丢弃空实例运行，并把前缀换成本次独有的名称；不要假定共享实例里的同名键属于自己。没有清库操作，也没有真实命令回执。

HSET nov10_example_unique:user name old
HSET nov10_example_unique:user name new
HGET nov10_example_unique:user name
HSET nov10_example_unique:user name new
HSET nov10_example_unique:user name newer city Shanghai
HGETALL nov10_example_unique:user

独立预期先从字段集合推导：四次 HSET 的回复依次是一、零、零、一。第一次从空集合加入 name；第二次已有 name，只改值；第三次仍没有新增字段；第四次 name 已有、city 新增，因此只计一个。中途 HGET 应读到 new；最后字段状态应为 name 等于 newer、city 等于 Shanghai。这些是官方规则下的预期，不是模拟出来的运行日志。

验证要同时保存每次命令前的字段集合、命令回复和最终读取。只读最后状态，可能看不见客户端错误地拒绝了第二次更新；只看回复计数，又不能核对值是否符合业务意图。字段顺序不是本例合同，HGETALL 的显示顺序不应进入断言；比较字段到值的映射即可。

文档的命令历史把多字段形式标为 Redis 四点零点零起支持。实际练习应记录服务端与客户端版本，确认封装发送了完整参数，而不是用当前文档推断旧依赖已经支持。单字段和多字段客户端接口还可能暴露不同返回类型，因此本文所说整数是命令回复，不保证所有语言包装都把它原样交给调用者。

错误分支与零计数必须分开

一个典型错误是把 reply 直接放进 if (!reply)。若零被解释为假，覆盖路径就会抛出“未保存”；调用者随后可能重试、弹出错误提示，或把下一步操作中断。修复应让传输与命令错误走独立通道，正常回复则保留其计数含义，不能简单规定任何返回值都算业务成功。

增加一组故障输入：另建一个自有字符串键，再对它调用 HSET。错误类型键应成为错误，而不是被封装吞掉后返回零。这个探针没有在本文执行；真正的异常类、错误结构和连接状态属于所用客户端，需要现场记录。不要把“接口返回了一个零”当成命令确实正常完成的证据，封装也可能已经丢弃了错误信息。

本站的Redis 事务逐命令错误讨论多命令执行时怎样保留结果；本题只校正单条 HSET 的计数合同。若命令嵌进事务或流水线，仍要先找到它对应的那项回复，不让批次外层的布尔值覆盖单条命令语义。

另一个相关但不同的问题是期限。SET 与 TTL 替换已讨论原地修改与替换的不同到期行为。本题不把字段新增数当作期限证据；值、字段存在性与到期状态如需验收，应分别读取和判断。一个计数不可能同时证明这些条件。

适配层可以先写一张小合同表：若所选客户端返回整数，零保存为 added_fields 等于零；若某个单字段方法把“是否新字段”暴露为布尔值，false 应保留为“已有字段被设置”，不能直接变成“调用失败”。这是一份待验证的适配设计，不是声称所有库都使用这种接口。

把相同四次命令穿过实际封装，分别检查底层回复、封装结果和上层错误提示。多字段调用还要确认是否仍保留整数计数，避免把新增两个字段压成 true 后再当作一。失败探针应同时检查异常没有被吞掉。测试固定客户端方法、版本与返回类型，才能判断是哪一层把数量误读成结果，而不是只凭方法名猜语义。

回复丢了以后，重发还能恢复第一次的新增数吗？

不能保证。新增字段的命令可能已经执行，只是连接在调用方收到回复前中断。此时再发相同 HSET，字段已经存在，新的回复就可能是零。这个零描述第二次命令，不会告诉你第一次究竟是在何时新增；把重试结果当作原调用回执，会重写事件经历。

对“最终把字段设为这个值”的合同，重试可以围绕期望状态设计，但仍要考虑是否允许覆盖期间别人的更新。对“首次新增触发奖励”的合同，更不能靠这个重试计数重建唯一业务事件。先查询当前状态并按业务身份处理，持久化、并发、重复交付和外部动作另行验收。本文没有测试这些路径，交付的结论仅是把新增计数从成功判断里分离出来。
