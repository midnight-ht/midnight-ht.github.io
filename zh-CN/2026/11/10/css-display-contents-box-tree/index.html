用一页样本检查display:contents的布局、选择器和事件

同一普通div样本分别观察Grid布局、DOM直接子选择器与冒泡事件，另讨论伪元素新增项目及真实可访问性边界。

正文

核心要点

  • contents取消普通包装自身盒，不删除DOM节点。
  • 网格参与关系不等于DOM直接子关系。
  • 伪元素可新增布局内容，可访问性仍需目标环境检查。

display:contents让普通包装元素不生成自己的盒子，却没有把它从DOM删除。子元素的盒可以进入父网格，原来的直接子选择器和冒泡监听仍按DOM关系工作。布局像少了一层，脚本还看见这一层，这两个观察可以同时正确。

假设表单把两个按钮包在一个div里，外层使用两列Grid。维护者加上contents以后，两个按钮分别占了父网格的位置，包装层边框消失；点击按钮时，包装层监听器却仍然运行。若把这理解成“浏览器没有真正移除元素”，排查就偏离了目标：这条CSS本来就只改变盒生成，不承担删除元素的工作。

消失的是盒，不是文档关系

CSS Display三级草案的contents定义说明，元素自身不生成盒，其子元素和伪元素仍照常生成盒与文本序列；在盒生成和布局上，把它视作由内容替代。文档同时说明，基于文档树的选择器匹配、事件处理和属性继承不因这项规则而改变。

这里读的是二〇二六年六月五日编辑草案，不是目标浏览器的测试报告。规则模型解释为什么DOM与盒树不同，却不能据此宣称所有辅助技术都正确保留了语义。规范自身也提醒实现中的可访问性问题；使用前应在目标浏览器和辅助技术组合上检查所需角色、名称和阅读关系。

Grid判断的是参与布局的盒。Grid二级规范的项目条款描述流内内容怎样形成网格项目。普通包装盒存在时，它是父grid的一项；包装不生成盒时，内部流内按钮的盒可以分别参与父grid。DOM上的父节点并没有因此改成grid，不能拿视觉位置推断parentElement已经变化。

同一页切换，两份不同布局

下面HTML没有伪元素，包装层也只是普通div，避免把特殊元素规则混入主例。它尚未在浏览器运行；按钮只显示诊断，不发送请求或保存状态。切换前后同时观察布局、直接子选择器名单和点击事件，三种证据分别回答不同问题。

<!doctype html>
<meta charset="utf-8"><meta name="viewport" content="width=device-width, initial-scale=1">
<title>Box tree and DOM — unexecuted teaching sample</title>
<style>
#grid { display: grid; grid-template-columns: repeat(2, 10rem); gap: .5rem; }
#wrapper { border: 2px solid; padding: 1rem; }
#wrapper.flat { display: contents; }
</style>
<button id="toggle" type="button">Toggle wrapper contents</button>
<div id="grid"><div id="wrapper"><button id="a" type="button">A</button><button id="b" type="button">B</button></div><button id="c" type="button">C</button></div>
<pre id="out"></pre>
<script>
const [grid, wrapper, out, toggle] = ['grid', 'wrapper', 'out', 'toggle'].map(
  id => document.getElementById(id));
const ids = selector => Array.from(document.querySelectorAll(selector), node => node.id);
function report(extra = {}) {
  out.textContent = JSON.stringify(Object.assign({contents: wrapper.classList.contains('flat'),
    domDirectGridButtons: ids('#grid > button'), wrapperButtons: ids('#wrapper > button'),
    wrapperBoxCount: wrapper.getClientRects().length}, extra), null, 2);
}
toggle.addEventListener('click', () => {
  wrapper.classList.toggle('flat'); report();
});
wrapper.addEventListener('click', event => report({target: event.target.id,
  currentTarget: event.currentTarget.id}));
report();
// Independent expectations: direct-grid DOM button list remains [c], wrapper list [a,b].
// In contents mode, a/b/c boxes participate in the parent grid; wrapper generates no box.
// Clicking a still invokes wrapper listener with currentTarget wrapper and target a.
// Screen-reader semantics and target-browser compatibility need separate real tests.
</script>

独立预期是block状态下，包装盒作为父grid项目与C一起布局；contents状态下，A、B、C的盒分别参与父grid。与此同时，两种状态的#grid > button都只匹配C，#wrapper > button仍匹配A和B。直接子组合符依据DOM关系，不会把布局中更接近父grid的按钮自动升级成DOM直接子节点。

点击A时，wrapper上的冒泡监听仍可运行，target为A，currentTarget为wrapper。包装本身没有盒，不等于它不能在后代事件的传播路径中出现。相反，若希望用户点击包装层原先的空白或边框来触发动作，必须重新考虑命中区域；没有自己的盒，原来的几何区域不能被当作当然存在。

这些是独立预期，不是已捕获的像素坐标和浏览器日志。getClientRects只用于观察包装是否生成盒，不直接列出所有网格项目。视觉验收还需查看子项位置，事件验收要保存实际节点身份，不能用一个盒数为零就把整个交互行为判为通过。

DOM没有改变，不代表所有需求都保住了

若包装负责背景、边框和内边距，contents会移除承载这些装饰的自身盒。给它继续加宽度或边框，并不能让同一盒一边消失一边保留装饰。可以选择保留包装盒、重新分组装饰与布局责任，或根据对齐需求评估其他方案；不必为了让子项进入父grid，把所有卡片都设成contents。

子网格共享轨道解决的是另一个问题：保留卡片结构，让内部项参与相应父轨道尺寸。它与取消包装盒的目标并不相同。若卡片还需要完整背景和语义分组，先比较需求，再选择技术，不能把两者当成名字不同的同一写法。

普通div样例也不能推广到input、img或其他特殊元素。Display规范为替换元素和不完全由CSS控制呈现的元素规定专门处理，部分情况下contents会计算为none。把表单控件直接换成contents，再期待只省掉外壳而保留可操作内部，不属于本例保证。应查对应元素的附录规则并实际验证。

可访问性检查应落在真实任务上：用户能否知道这组操作属于什么对象、按合理顺序到达按钮、听到正确名称。DOM节点存在只能证明文档结构仍在，不能替浏览器的可访问性树映射通过。未经目标环境运行时，应保留“尚未验证”，而不是凭规范模型填一个绿色结论。

隐藏行与结构计数同样提醒视觉布局与选择器集合不能混算，但本题没有隐藏A、B或C。contents使内容继续布局，和display:none让整段不生成盒的合同不同；也不同于透明度把仍存在的盒变得看不见。

加一个::before，会多出网格项目吗？

可能会，而且这正是不能仅按HTML元素数量预估项目数的新增条件。contents的子元素与伪元素仍正常生成；若给主例wrapper增加一个处于流内的::before盒，它也可能参与父grid，占据自动放置的位置。A、B、C的DOM关系仍没有因此变化，新增的是布局内容。

可在原样本之外另加一条对照规则：#wrapper.flat::before { content:"提示"; }。独立预期是在contents状态出现一份额外生成内容，自动放置关系随之改变；删除该规则后回到无伪元素样本的三按钮布局。这个对照尚未运行，不能写成确定的像素行列或截图结果。若改变position使伪元素脱离流内，预期又需要重新判断。

普通非空文字也可能由匿名盒参与网格，而纯空白有相应处理。项目数与可选中的元素个数因此不是一回事；querySelectorAll不会返回一个代表::before的普通元素节点。记录盒布局时别拿DOM查询名单冒充项目清单，记录委托事件时也别按视觉项目顺序猜业务身份。

交付前先跑不含伪元素的主样本，分别核对三份预期，再加入生成内容这一新条件。若包装同时承担装饰、语义和点击区域，就把这些需求写在使用约定里；决定取消哪一份盒责任以后，再确定contents是否符合这组操作的完整行为。
