分段只有cde，Repr-Digest为什么仍核对abcdef？

用无内容编码的单范围字节与独立摘要，区分本次content和整份选定表示，保留编码、完整对象与信任边界。

正文

核心要点

  • Content-Digest和Repr-Digest可以覆盖不同字节。
  • 表示数据包含Content-Encoding，不能自动改用解压文本。
  • 片段校验不替全对象、元数据或认证提供证明。

选定表示是六个字节abcdef，这次单范围响应只发送cde。Content-Digest核对本次片段，Repr-Digest核对完整选定表示；两个值不同，不足以判定有人算错。先把输入字节写清，再检查摘要值，不能因为两项都使用SHA-256就认定它们必须相等。

假设下载器收到一个206响应，标明范围为bytes 2-4/6，内容正好是三个ASCII字节cde。维护者把这三个字节交给哈希函数，却拿计算结果与Repr-Digest比较，于是报出完整性失败。这里暂时没有压缩、没有换行，也没有多范围multipart包装；这个明确的范围合同，足以解释为什么一次合法的分段响应可能出现两种摘要。

先给两个字段各自指定对象

RFC 9530《Digest Fields》第二节把Content-Digest定义在实际消息content上，第三节把Repr-Digest定义在整个选定representation data上。该标准发布于二〇二四年二月，并废弃旧的Digest、Want-Digest字段。本篇讨论的是新字段，不能把某个旧库接受Digest的行为自动当作同一项支持。

对当前单范围例子，前一个输入是cde，后一个输入是abcdef。附录B.3也展示了206响应中两个值不同的情况。差异来自覆盖对象，不是SHA-256有两套算法。若普通完整响应的content恰好就是整份选定表示，那么两项可以覆盖同样字节、得到相同结果；不能把这个特例倒过来要求每种响应都相等。

字段的编码也要看清。它们采用Structured Fields字典，sha-256是算法键，冒号包住的值表示摘要原始字节的Byte Sequence。不是把十六进制哈希文本再随意包一层Base64。下面只生成一个固定sha-256条目，方便核对；它不实现通用字典解析、多算法选择或接收方政策。

让固定字节与独立答案一起出现

以下程序只使用本地Python标准库，不发送HTTP，也没有启动一个Range服务器。完整表示明确是b'abcdef'，不是带行尾的文件；切片取下标二到四，右端点在Python里写五，得到b'cde'。两份固定摘要事先由独立的Perl shasum计算，随后才用Python的hashlib对照，不从被检查函数的本次结果生成预期。

"""Local bytes only; no HTTP messages are sent or parsed."""
import base64
import hashlib

def field_value(data):
    raw = hashlib.sha256(data).digest()
    return 'sha-256=:' + base64.b64encode(raw).decode('ascii') + ':'

# No newline and no content coding: exactly six ASCII bytes.
representation = b'abcdef'
content = representation[2:5]  # single range bytes 2-4 inclusive
assert content == b'cde'
assert representation.hex() == '616263646566'
assert content.hex() == '636465'

# Fixed oracle values obtained beforehand with Perl shasum, not this function.
expected_full = 'sha-256=:vvV+x/U6bUC+tkCngKY5yDvCmsipgW8fxsXG3Nk8RyE=:'
expected_part = 'sha-256=:CKAYqVSSINcH4RxcT+lNjdYIJfAQ5x76qR5eeE82TXs=:'
assert field_value(representation) == expected_full
assert field_value(content) == expected_part
assert expected_part != expected_full
assert field_value(content) != expected_full  # wrong byte scope
assert field_value(b'cdX') != expected_part   # same-length mutation
assert representation[1:4] != b'cde'         # wrong offset, still length three
print('Content-Digest:', field_value(content))
print('Repr-Digest:', field_value(representation))
print('byte identities, field scopes and negative controls checked')

独立身份预期是完整对象十六进制616263646566、长度六，片段十六进制636465、长度三。片段的字段值应是CKAY开头的那份，整表示应是vvV+开头的那份。程序还分别拒绝错用整体摘要、同长度cdX损坏，以及从下标一开始取得的bcd。长度为三不证明取到了正确三个字节，算法名称一致也不证明检查的是同一对象。

本地Python 3.11.15实际运行退出零，两个完整字段值与固定oracle一致，负例断言也通过，原文件和输出已归档。这个结果只证明所列字节、SHA-256和Base64构造。它没有验证真实客户端是否在解码前提供原字节、代理是否变换内容，或服务端是否按合同发送了这些字段。把打印出的两行字段当作已收到的网络报文，会扩大证据范围。

片段通过以后，还缺什么

只有cde时，可以核对这次片段的Content-Digest，却不能凭三个字节重新计算整份abcdef的摘要。教学程序能计算Repr-Digest，是因为本地同时持有完整表示。实际下载器需要拿到或重建完整选定表示，再按相同表示条件核对；不能用一个片段的成功比较替整个对象签收。

反过来，若完整字节恰好也可取得，不要为了让两值一致，把Repr-Digest字段改填片段摘要。那会让接收者失去原字段承诺的对象。检查记录可以分开写请求范围、实际content字节身份、整份表示身份与每次比较结果，不把一个“hash正确”覆盖所有层次。

分段拼接还需要版本与范围的合同。If-Range与恢复下载已经说明怎样避免混入两个版本，本篇不重新设计续传器。摘要检查也不会替应用决定临时文件何时覆盖、权限变化后能否继续，或者后台是否已保存成功；这些应继续由对应操作核对。

表示数据包含内容编码这一层

RFC 9110第8.1节给出的模型是Content-Encoding作用于Content-Type所表达的数据。Repr-Digest中的representation不能直接翻译成“解压后的原文”。若选定表示采用gzip，计算对象包含该内容编码的结果；把已经解压的文本拿来比较，就可能换掉字段所指的字节。

同一段原始文字还可能因为压缩参数等条件产生不同编码字节。摘要标准第6.5节专门提醒这种变化，因此即使同为gzip，也不能从解压后文字相同推导摘要必然相同。本例没有执行压缩，不能提供某个客户端的透明解码兼容性结论。已有的Content-Length与编码层处理的是长度，本题处理的是同一层次下摘要的输入。

普通哈希也不是认证。RFC 9530的安全条款说明，这些字段不保护整份HTTP消息的头和尾，单独使用不能防止恶意修改者同时替换数据与摘要。匹配可以支持所选输入的完整性检查，不证明发送者身份、授权或所有元数据真实。需要的信任机制应另外确定，不能由本例的两个常量补出来。

HEAD没有正文，还能有这两种摘要吗？

可以。这里首次改变请求方法：同一选定表示仍是abcdef，HEAD响应没有content。RFC 9530附录B.2明确给出这类例子，Content-Digest针对空content，而Repr-Digest仍针对所指的完整表示。不能因为没有传输正文，就把两项都改成空串摘要。

下面是独立的本地条件探针，同样没有发出HEAD请求。它把新的空content输入与先前完整表示分开列出，不把完整表示也清空。

"""Separate HEAD-condition calculation; no HTTP request or server."""
import base64
import hashlib

def field_value(data):
    return 'sha-256=:' + base64.b64encode(hashlib.sha256(data).digest()).decode('ascii') + ':'

# Same selected identity-coded representation, but HEAD sends no content.
content = b''
representation = b'abcdef'
assert field_value(content) == 'sha-256=:47DEQpj8HBSa+/TImW+5JCeuQeRkm5NMpJWZG3hSuFU=:'
assert field_value(representation) == 'sha-256=:vvV+x/U6bUC+tkCngKY5yDvCmsipgW8fxsXG3Nk8RyE=:'
print('HEAD Content-Digest:', field_value(content))
print('HEAD Repr-Digest:', field_value(representation))

独立预期是空content得到47DE开头的标准空字节摘要，Repr-Digest仍为vvV+开头的整表示值。在同一本地环境实际运行时，这两项均匹配，完整输出随脚本保留。这仍不是一次HEAD接口或服务器实现验收；返回字段可以提供所指表示的元数据，不表示接收者已经取得或验证了GET正文。

HEAD元数据与GET正文说明最后这个访问边界。交付摘要检查时，把字段名、算法、实际输入字节与本次执行范围放在一起。先问清核对的是哪一份对象，再决定匹配结果允许下游继续哪一步。
