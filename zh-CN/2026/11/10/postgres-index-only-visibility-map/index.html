覆盖索引建好了，Heap Fetches 为什么仍不是零？

区分索引覆盖资格与MVCC可见性，用拟议计划采集判断Heap Fetches，而不是继续盲目增加INCLUDE列。

正文

核心要点

  • 覆盖所有查询列只是索引只读扫描的基本资格。
  • 可见性映射无法确认候选行时仍需访问堆。
  • 比较真实计划与结果集合，不承诺零Heap Fetches或固定提速。

Index Only Scan 并不保证每个候选行都不访问堆。索引能提供查询所需的列，只解决取值来源；PostgreSQL 仍要判断该行对当前 MVCC 快照是否可见。执行器查看对应堆页的可见性映射，不能由映射确认时，就要访问堆。因此，计划里出现非零 Heap Fetches，不足以说明覆盖索引失效。

假设订单查询只读取客户编号与金额，团队已经把金额放进 INCLUDE。计划节点也叫 Index Only Scan，排查者却因为看到 Heap Fetches，准备再建一个包含更多列的索引。先停在这里：新增的列能否改变可见性证据？如果不能，这次修改可能只增加存储与写入维护，读查询仍要做原来的检查。

覆盖资格与可见性不是同一扇门

PostgreSQL 18 的索引只读扫描说明列出两个基本条件：索引类型支持这种扫描，以及查询引用的列都能由索引提供。B-tree 支持；不能因为某种索引也叫索引，就推断它保存了可返回的完整原值。表达式索引和部分索引还存在另外的规划条件，本例先用普通列的 B-tree。

通过这两个条件，表示从索引取值在物理上可行，却还没有完成快照可见性判断。文档说明，可见性信息并不保存在索引项里。可见性映射按堆页保存信息；对应位设置时，扫描可以借此确认候选行可见，避免进一步访问堆。位没有设置，就需要访问堆项判断。一个页上有多条记录，也不能把这张映射想象成每个索引列各有一个开关。

因此，要区分“查询能不能采用这种访问方法”和“这次采用后省掉多少堆访问”。前者涉及列与索引能力，后者还取决于有关堆页的状态。节点名称描述访问方法，Heap Fetches 描述这次执行实际发生的检查；二者同时出现并不矛盾。也不能把这个计数直接写成磁盘物理读次数，内存缓存和输入输出是另一个观测层。

给同一条查询保留三份记录

下面是未执行的教学脚本，只适用于自己创建的隔离空库。它会创建表和索引，并真实执行查询；这里没有数据库运行记录，也不承诺这份小数据一定被优化器选成 Index Only Scan。

CREATE TABLE editorial_orders (
  id integer PRIMARY KEY,
  customer_id integer,
  total numeric
);
INSERT INTO editorial_orders
SELECT n, n % 2, n::numeric FROM generate_series(1, 10000) AS n;
CREATE INDEX editorial_orders_cover
  ON editorial_orders(customer_id) INCLUDE(total);
EXPLAIN (ANALYZE, BUFFERS)
SELECT total FROM editorial_orders WHERE customer_id = 1;

-- VACUUM 必须在事务块外单独执行。
VACUUM (ANALYZE) editorial_orders;
EXPLAIN (ANALYZE, BUFFERS)
SELECT total FROM editorial_orders WHERE customer_id = 1;

UPDATE editorial_orders SET total = total + 1 WHERE id = 1;
EXPLAIN (ANALYZE, BUFFERS)
SELECT total FROM editorial_orders WHERE customer_id = 1;

独立的数据预期先写出来：第一次和第二次查询都应返回奇数编号对应的五千个金额；第三次仍返回五千行，只把编号一对应的金额从一变成二。查询没有排序，验收应比较多重集合，不能拿打印顺序当业务顺序。这个数据预期与计划选择无关，不能因为看到想要的节点就省去结果检查。

三次计划分别保留版本、完整 SQL、节点、Heap Fetches、BUFFERS、采集时间和表变更条件。如果没有选择目标节点，先如实记录，再分析表规模、选择率与成本，不通过关闭其他扫描方式制造“自然采用”的证据。若选了该节点，可对照映射机制解释实际计数；不能提前把 VACUUM 后零次回堆、更新后必定多少次写进断言。

VACUUM 在这个实验中提供可比较的维护时点，不是一条任何环境都能立刻消除回堆的指令。活动事务、并发修改和实际页面状态需要现场证据。脚本没有证明这些条件，更没有证明生产查询提速。尤其不要让迁移工具把 VACUUM 和建表命令一起包进事务后，再把执行失败误判为索引语义问题。

再加载荷，先问它解决哪种缺口

一个直接反例是查询改为返回未被覆盖的 id。此时缺少的确实是取值列，应该重新核对覆盖资格；它与原来所有列都可取、却还要验证可见性的情况不同。排查记录先写清缺的是值还是证明，再决定修改索引还是调查表状态。

INCLUDE 列不是搜索键。文档还提醒，宽载荷会复制表数据、扩大索引，超过索引项允许大小甚至可能导致插入失败。若这个表持续频繁修改，加入更多载荷仍可能无法避免堆访问。因此，索引评审应同时讨论代表性读取与写入负担，不宜只把“全部字段放进索引”作为验收目标。

本站的EXPLAIN 证据检查讨论估算行数与真实执行成本。本题在其后增加一项判断：计划方法可用，不等于每次执行都满足省堆条件。保存可比参数、数据变化和结果集合，比只截取节点名称更能帮助下一位排查者复现。

另保留一组命中范围变化的对照：在同一教学表上，把客户等于一改为客户属于零或一。独立结果预期从五千行变成一万行，不能仍用原来的行数验收。两组参数返回的数据规模不同，优化器选择不同方法也可能合理；应分别保留计划，而不是只比较节点名字是否一致。这里没有运行任一参数版本。

这组比较还能防止把一次维护前后的差异错归给索引：如果维护前只查一个客户，维护后却查全部客户，变的不只有堆页状态。测试报告应把参数及期望集合放在同一行，先拒绝这种条件不等的对比，再讨论计数变化。能够复述查询条件与数据规模，是使用计划证据的前提，不需要预先给任何一种扫描判好坏。

零行的扫描能证明堆页全部可见吗？

不能。若过滤条件没有找到候选索引项，相关执行记录没有替其他堆页做可见性证明。零次 Heap Fetches 可能只是没有候选行，不能据此宣布整个表都已适合避免回堆。这里新增的条件是命中集合为空，不是把前面的映射规则再说一遍。

补一组确实命中业务代表范围的查询，并先确认预期行数，再解释计数；保留空命中样本作为对照也有用。最终交付应能回答本次查询从索引取到了哪些值、对哪些候选行需要检查、实际返回了什么。只有这些证据对齐，才有理由判断下一项修改是否值得做。
