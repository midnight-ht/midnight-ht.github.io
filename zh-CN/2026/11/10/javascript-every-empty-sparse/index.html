every全通过，为何一条输入也没检查？

空集合、缺槽和无效值会走不同路径；用五组输入与本地回调次数明确every不能代替哪些前置条件。

正文

核心要点

  • every为true不证明至少访问了一项。
  • 非空、位置完整与单项有效需要各自合同。
  • async谓词返回的Promise不会被every等待。

筛选后的数组没有任何记录，every仍可能返回true，而且一次校验回调也没运行。若这个结果会放行批量提交，缺失的先是集合前置条件：产品是否允许零条记录、是否要求每个预期位置都存在，不能由一个单项谓词替你决定。

假设导入页面需要至少选择一条有效记录才能继续。开发者把有效性函数交给every，看到true就启用按钮。日常有记录时似乎正常；用户取消全部选择后，数组变空，按钮却仍然可用。这是一个本地校验情境，不是本站运行中的导入服务，也没有真实提交或持久化。

true排除了反例，没有证明存在记录

ECMAScript的every算法先取得长度，再逐个检查属性是否存在。现存项才进入回调；一旦某次返回值转布尔为false，方法立即返回false。如果没有找到这样的反例，最后返回true。空数组没有可访问项，也就没有产生失败结果的回调。

这对应“所有项都满足”的判断，不包含“至少有一项”。它不是JavaScript偷偷批准了一次空提交，而是调用者给语言方法安排了超出其语义的职责。业务允许空集合时，true可能正合适；要求至少一条时，就需要明确加上非空条件，不必把标准行为称作随机漏检。

还要区分空数组与长度存在但位置缺失的数组。对于原型没有相应索引属性的普通数组，Array(2)有长度二，却没有两个现存项；every同样可能一次也不调用谓词。只补length>0，仍不足以证明两条输入都经过检查。缺槽与显式undefined的基础区别可看flat与缺槽，本题关心的是怎样定义放行集合，不是变换后的行号。

先写出五份输入的独立答案

下面脚本只检查本地合成数字。产品规则被刻意收窄为：必须是非空数组，每个索引位置都需要自身属性，值必须是有限正数。选择自身属性是本例的数据接收合同；原生every使用HasProperty，会考虑继承属性，不能把两者说成同一规则。

const valid = value => Number.isFinite(value) && value > 0;
function canSubmit(values) {
  if (!Array.isArray(values) || values.length === 0) return false;
  for (let i = 0; i < values.length; i++) {
    if (!Object.hasOwn(values, i)) return false;
  }
  return values.every(valid);
}
const inputs = [[], Array(2), [undefined], [2, 3], [2, -1]];
for (const values of inputs) {
  let calls = 0;
  const result = values.every(value => { calls++; return valid(value); });
  console.log({length: values.length, result, calls, canSubmit: canSubmit(values)});
}
// Independent expectations: raw true/true/false/true/false;
// calls 0/0/1/2/2; release false/false/false/true/false.

独立预期依次是：原生结果true、true、false、true、false；回调次数零、零、一、二、二；本例放行结果false、false、false、true、false。前三项分别把空集合、缺槽和一个明确存在但无效的值拆开。最后一项的负数在第二个位置，因而会产生第二次回调，再返回false。

在Node v24.21.0实际运行这份脚本，五组结果和上述预期一致，原始stdout已随编辑材料保存。这个证据只覆盖当前本地数字函数，没有验证浏览器按钮、后端校验、权限或最终写入。代码里不存在发送请求的动作，因此不能把canSubmit的true写成“提交成功”。

为什么不直接先filter再every

筛掉无效项再对剩余值做every，容易把“输入有错”变成“坏输入已经不在集合里”。例如用户提交一正一负两项，过滤后只剩正数，后续校验自然通过，却没有解释负数该被拒绝、提示还是合法忽略。过滤本身可以是正确产品规则，但必须说明它改变了什么集合。

同样，不要先用转换把缺槽补成默认值，再宣称原始位置完整。如果默认值本身允许通过，输入丢失就被改造成了合法业务数据。对导入预检，应按明确来源保留错误位置；对用户主动筛选，可以把筛选结果当作新的待处理集合，并重新检查非空。这两种“少了几项”有不同责任。

严格接收函数也有代价：它拒绝带继承索引的类数组，拒绝空数组，还只接受数字。不要把这段教学函数直接改名为通用表单验证器。实际记录包含编号、状态和多个字段时，应定义每个字段的有效性，并决定错误如何关联到稳定记录，而不是只向用户展示一个没有对象身份的false。

校验时不要顺手修改待校验集合

规范在开始前确定遍历长度，后来追加的项不会被这次every访问；访问某个位置以前删除它，也可能使该项跳过。回调不是为边遍历边扩充校验范围设计的交接协议。若过程中输入会变化，可以先取得本次要验证的明确快照，再让最终采用结果的代码确认它仍属于当前输入。

短路也意味着不能靠every收集全部错误。第一个false以后，其余项不会继续进入回调；想一次展示所有错误，就需要另一个会逐项产生诊断的流程。把“是否存在失败项”和“所有失败项的清单”安排给同一个返回值，容易让错误面板只显示第一项却被误认为完整。

Array.fill与对象独立性讨论草稿状态是否共享。本题的通过不能证明每条记录互不影响；即使每个值当前有效，共享对象仍可能让一次编辑改动多条记录。集合完整、单项有效和对象独立，需要按实际操作分别检查。

every传入async回调，为什么异步返回false仍放行？

因为every对回调的直接返回值做布尔转换，不会等待Promise最终兑现成哪个值。async函数返回Promise对象，对象在这项转换中为真；之后兑现为false，不会让已经返回的every重新计算。拒绝也不等于被这个布尔结果捕获，仍需妥善观察异步失败。

如果有效性依赖远端查询，应先设计异步结果的汇总、并发限制和错误语义，再在得到明确结果后判断是否允许继续。不要只给原来的谓词加async，就把同步校验界面当成已完成异步验证。当前脚本没有执行远端检查；交付时先保留五组独立名单和回调次数，再为真实异步路线安排自己的证据。
