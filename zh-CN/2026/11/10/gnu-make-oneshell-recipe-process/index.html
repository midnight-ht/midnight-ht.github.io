修复 make 的 cd：先选同一行，再决定是否用 .ONESHELL

比较局部 cd && 与全局 .ONESHELL，用隔离 Makefile 检查目录、失败传播和解释器前缀条件。

正文

核心要点

  • 局部 cd && 与全局 .ONESHELL 改变不同范围。
  • 单 shell 需要重新审查中途失败如何传回 make。
  • 实际目录、文件位置与即时退出值必须一起验证。

同一行的 cd out && 命令 能让这两个动作共享工作目录；.ONESHELL 则改变整个 Makefile 中各目标的 recipe 执行方式。前一种修复只需要解释局部命令，后一种还得重新检查中途失败如何传回 make。不要只看到报告终于落进 out，就宣布这次修改结束。

先看文件写到哪，再决定共享多大范围

普通 GNU Make recipe 的每个逻辑行使用新的子 shell。第一行进入 out，改变的是那次进程的当前目录；第二行启动另一份 shell，并不会继承前一行的改变。Recipe Execution直接说明了这种上下文边界，并以同一行的 cd && 后续命令 作为处理方式。这里依据的是 GNU Make 4.4.1 手册，不把“每行”误说成编辑器显示的每一条视觉换行。

假设规则的合同是：把目录记录写到 out/seen.txt，根目录不能出现 seen.txt。普通两行写法可能让 cd 成功、make 也成功，却把第二行文件写到根目录。这不是路径字符串拼错，而是改变目录的进程已经结束。给 cd 加上更长的绝对路径，也不会让它跨进程保留状态；需要改变的是两个动作之间的执行关系。

仅需一对动作共享目录时，同一逻辑行通常容易审查。必须使用 &&，因为它同时表达“进入成功才生成”。分号只表达先后次序，前一个动作失败，后一个动作仍可能继续。尤其是生成命令带输出重定向时，错误目录中的旧文件可能在程序真正运行前就被截断。路径选择和失败停止应写进同一份合同。

三份规则，分别放在三个新目录

下面是未执行的完整教学对照，要求支持单 shell 声明的 GNU Make 和 POSIX 风格 shell。本站当前查到的本机 make 是 GNU Make 3.81，不能拿它认证此开关。没有执行以下三组规则，也没有构建通过回执。各组准备独立的新目录及其中的 out，分别保存各自 Makefile，recipe 缩进必须是制表符。三组不能放进同一 Makefile 假装开关只影响某个目标。

普通组故意保留错误，以显示实际文件位置：

.PHONY: bad-probe
bad-probe:
    cd out
    pwd > seen.txt

局部修复组只把需要共享目录的两个动作放在一行：

.PHONY: local-probe
local-probe:
    cd out && pwd > seen.txt

单 shell 组显式保护进入目录失败，并增加一对失败状态对照：

.ONESHELL:
.PHONY: single-probe masked guarded
single-probe:
    cd out || exit 1
    pwd > seen.txt
masked:
    false
    printf 'continued\n'
guarded:
    false || exit $$?
    printf 'unreachable\n'

对每个独立目录运行 make bad-probe、make local-probe 或 make single-probe 后，立即保存退出值，再读根目录和 out 下的文件。独立预期先由路径合同写出：普通组暴露根目录 seen.txt，另两组应只在 out 内生成；文件内容还应等于本轮 out 的绝对路径。只比较命令是否为零无法区分这三组，因为前两组在目录存在时都可能成功。

再为局部与单 shell 组分别建立没有 out 的新副本，不能借用上一轮已经生成的文件。此时应非零退出，而且两个位置都不能生成 seen.txt。这个反例检查 cd 失败是否真正阻止了输出；它并不检查报表内容、并行执行或发布原子性。若改成分号以后出现根目录文件，说明规则违反路径合同，不应因为末条命令成功就放行。

目录保住了，make 还看得见失败吗

Using One Shell说明，只要该特殊目标出现在 Makefile 中，各目标的 recipe 行都会交给各自的一次 shell 调用，行间换行保留。它不是只作用于紧随其后的目标。因此给一个目录问题加此声明，评审范围可能扩大到其他目标和 include 进来的规则。

同一章节还指出，非末行失败可能不被 make 察觉。上面的 masked 用 false 制造中途失败，随后 printf 成功，最后 shell 状态可能为零；guarded 则显式传回失败。要分别运行这两个目标并记录即时退出值，不能把终端曾显示 false 当作 make 已经判失败。这里给出的是手册支持的预期，不是本机执行日志。

给 shell 加 -e 是另一种候选，但会改变已有脚本的行为，不能从一份简单规则推广到任意条件、管道或解释器。对本例，明确的 || exit 比隐藏地依赖全局失败选项更容易说明。选择应来自真实 recipe 的控制流，而不是先决定统一增加某个开关，再要求所有目标适应它。

旧的失败删除文章处理半成品是否留下；目录顺序前提文章处理目录时间是否触发重建。本题先解决执行上下文。即使依赖图和失败删除都写对，输出仍可能落进错误目录；反过来，目录正确也不能证明失败已传到 make。

为什么单 shell 内部的 @ 还要看解释器？

这是改变解释器条件以后新增的一项检查。手册规定，单 shell 模式下通常只对首行检查 @、-、+ 等特殊前缀；若识别为 POSIX 风格 shell，内部行的这些前缀还会被移除。对其他解释器，内部字符可能作为程序文本传入。因此不能把 shell 示例中的每行 @ 原样搬到 Perl 等解释器，再说只是关闭了回显。

还有一个应在实验前固定的条件：三个动作目标不能与目录里同名的真实文件碰撞。示例用各自的 PHONY 声明表达动作身份，调用时也使用该组自己的目标名。若只复制生成文件而没有复制规则，或者在同一目录反复切换版本，已有 seen.txt 会让观察混入历史状态。对照的初始目录、输入和命令必须成组记录，不应只保留修改后的那份文件。

改全文件开关时，还要把 include 链当作实际规则的一部分。主文件只显示一个 probe，并不表示构建只包含这一条 recipe；导入片段可能依赖每行独立失败，或者用另一解释器解释文本。先列出本次读取的文件和 shell 设置，检查是否有假定“前一行失败就不执行下一行”的目标，再决定改动能否局限为一条局部命令。这个范围检查不需要先宣称性能收益。

实际运行记录应同时保存失败组与成功组，不能因为修复组得到预期文件，就删掉普通组写错位置的证据。若缺目录组仍生成 seen.txt，应先检查它是不是上一轮残留，再核对命令是否使用了分号。把文件的本轮身份与退出状态一起保留，才能区分环境没重置、执行上下文不共享以及失败被覆盖这三个不同原因。

验证时保存实际 SHELL、选项、Makefile 哈希、每次退出值和文件位置，再看是否需要共享状态。只有两个动作需要同一个目录，就让这两个动作同处一行；只有确实需要完整多行上下文，并且其他目标的错误与前缀语义都已审查，才把单 shell 作为整个文件的决定。
