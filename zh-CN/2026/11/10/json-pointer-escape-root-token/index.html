JSON Pointer 的 /~01 为什么不是在找斜杠键？

按RFC6901逐token解码一次，用根、空键和冲突成员的独立身份表检查路径适配器。

正文

核心要点

  • 逐token按规定顺序解码一次，~01最终成为~1。
  • 空字符串指根，斜杠指空名字成员。
  • 对象成员、数组索引和URI片段表示应分别验收。

JSON Pointer 的 /01 指向名字为 ~1 的对象成员，不是名字为斜杠的成员。按 RFC 6901，token 先把 ~1 解成斜杠，再把 ~0 解成波浪号；01 在第一步没有可替换的 ~1，第二步才变成 ~1，随后不能再解一次。反复替换到稳定，会选错字段。

这类错误常在普通字段名样本里藏住。若文档只有 name、age，错误解码器与正确解码器可能都工作。给几个容易混淆的键分别安排不同的值，才能证明路径选中了谁；不能把所有目标都填成 true，最后只检查“找到了一个值”。本例是接口适配的教学数据，没有运行解析库或请求服务。

斜杠分token，转义还原成员名

RFC 6901 第三节与第四节定义 JSON Pointer 是零或多个带斜杠前缀的 reference token。成员名里的波浪号编码成 ~0，成员名里的斜杠编码成 ~1。斜杠先用于划分指针中的层级，划分后的每个 token 再按规则还原，不能先对整串解码后重新切路径。

例如 /a~1b 是一个 token，还原后查找名字 a/b；/a/b 则有两个 token，先在根对象找 a，再在它里面找 b。两条指针可以同时有效，却指向完全不同的值。若先把 ~1 变成斜杠再调用通用路径切分器，就会把一个成员名误当成两层结构。

第四节还明确给出了 ~01 的顺序反例。它只解成 ~1，不再变成斜杠。实现可以用一次受控扫描，也可以按规定次序做两次替换；验收的重点是新产生的字符不再被当作下一轮待解码输入，而不是函数名字叫不叫 unescape。

用不同值锁定目标身份

下面是完整、未执行的文档输入。根对象含空名字成员、名字为 ~1 的成员、名字为斜杠的成员，以及容易被混成层级的 a/b。每项值都故意不同。

{
  "": "EMPTY",
  "~1": "TILDE_ONE",
  "/": "SLASH",
  "a/b": "JOINED",
  "a": {"b": "NESTED"},
  "arr": ["ZERO", "ONE"],
  "01": "OBJECT_ZERO_ONE"
}

独立预期是：空字符串指针返回整个对象；/ 返回 EMPTY；/01 返回 TILDE_ONE；/1 返回 SLASH；/a~1b 返回 JOINED；/a/b 返回 NESTED；/arr/0 返回 ZERO；/01 返回 OBJECT_ZERO_ONE。先把这些目标写进测试数据，再运行实现，不能从实现自己的输出生成“正确答案”。

错误的替换顺序先处理 0、再处理 ~1，会把 /01 导向 SLASH。这时调用并没有报错，所以只断言解析成功抓不住问题。另一个反例是删除空路径段：它可能让 / 被当成根指针，返回整个对象。两个错误都必须通过目标身份断言，而不是“结果不为空”来检验。

空指针和空token不是一回事

RFC 的字符串表示示例把空字符串列为整个文档，把 / 列为空名字成员的值。前者有零个 token，后者有一个内容为空的 token。因此，trim、合并相邻斜杠或清理空段并不是无害的格式整理；它们可能改变引用的值。

这也影响函数接口。调用者传空字符串可能是明确请求文档根，不应自动改成“没有传路径”；而路径存在但目标值为 JSON null，也不等于查找失败。接口最好把是否找到与取到的值分开，至少让缺失成员的错误不与合法空值共用同一个返回含义。否则上层补默认值时，很难知道补掉的是哪种状态。

本题只处理给定文档上的指针求值。它没有授权修改对象、删除数组或绕过字段权限；即使成功定位，允许读取或修改该成员仍需要应用合同。站内JSON Patch 的数组坐标序列说明操作顺序改变坐标，这是定位以后另一层问题。正确反转义不会替补丁保存生成时的资源版本。

对象数字键与数组索引要分开

/01 在当前对象中合法，因为对象确有名字为 01 的成员。/arr/01 却不是数组第二个成员的另一种写法。RFC 第四节规定数组索引不能有前导零；零本身可以，正索引从非零数字开始。若实现把任意 token 先转整数，可能把应拒绝的 01 悄悄解释成一。

同一节中的减号指向数组最后一个元素之后、并不存在的位置。纯指针求值不能凭它读到末项；JSON Patch 的 add 可以另行规定追加含义，但不能把那个应用规则推给所有指针操作。负例还应加入 /~2：它不符合只允许 ~0 与 ~1 的转义语法，不能默默当作普通成员名。

验收报告应保留每个原始指针、文档、预期身份与错误类别。对数组至少区分合法索引、前导零、不存在位置；对对象区分斜杠名字、空名字与嵌套对象。本文没有执行这些测试，也不把一个局部适配器的测试矩阵称作所有标准边界都已覆盖。

再给多层路径一个类型失败探针：/arr/0/x 在第一步取得数组，第二步取得字符串 ZERO，第三步却还要求在这个字符串里按对象成员 x 继续查找。独立预期是求值失败，不能返回中途找到的 ZERO 并宣称成功。/a/b/x 同样越过了字符串 NESTED；两条都能检查适配器有没有在走不下去时悄悄停在最近的值。

如果业务需要“找不到完整路径就取最近祖先”，那应是另外命名的操作，不能让普通 Pointer 求值隐含承担。报告中记录失败前的 token 与当前值种类，通常比只写“路径不存在”更容易定位问题；同时不要为排障直接输出整个敏感文档。此处只规定教学数据的预期，没有执行日志或真实接口错误证明。完整路径、目标身份与失败类别要一起核对。

井号后的百分号属于哪一层？

URI 片段表示给问题增加了另一种外层编码。RFC 第六节说明片段表示的编码要求；例如名字带空格的成员，在纯指针中可用 /a b，在相应片段表示中可写 #/a%20b。应先识别接收的是哪种表示，再处理片段编码与 token 转义，不能见到百分号就让所有纯指针做 URL 解码。

这里还有适用条件：JSON 媒体类型不因内容是 JSON 就自动采用 JSON Pointer 片段语法，须由相应媒体类型明确指定。实际集成先写清接口接受纯指针还是这种片段，分别测试空格和百分号字面键，再跑同一套目标身份断言。不要为处理外层百分号再重复解 ~01；两层各有规则，不能靠反复还原猜目标。
