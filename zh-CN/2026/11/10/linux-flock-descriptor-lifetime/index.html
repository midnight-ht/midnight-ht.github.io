Linux flock 2026-11-10

job.lock 还在，不代表 Linux flock 仍被占用

用 Linux 本地文件系统的描述符对照解释 flock 释放时点、dup 引用与后台继承，明确网络文件系统边界。

正文

核心要点

  • flock 关联打开文件描述，文件存在不能判断锁状态。
  • dup 共享锁，独立 open 才构成所需竞争。
  • 最后关闭、显式解锁和路径清理是不同动作。

job.lock 仍在，不代表 Linux flock 仍被占用。锁关联的是打开文件描述，释放不要求删除路径；最后一个相关文件描述符关闭以后，文件可以继续存在，而下一次独立打开已经能够取得锁。判断锁状态，应让独立竞争者尝试获锁，不能只看目录里有没有一个文件名。

文件名、打开描述和编号不是同一层

Linux flock 手册说明，锁关联 open file description。这里把它称为“打开文件描述”，而进程里那个小整数 fd 是引用它的文件描述符。dup 得到另一个整数，却仍引用同一份打开描述；fork 继承的相关描述符也会引用同一把锁。数字不同，不代表竞争对象独立。

这一区别直接影响清理时点。假设 fd1 获得排他锁，然后 dup 成 fd2，关闭 fd1 并不是最后一次关闭，fd2 还在维持引用。另一次 open 得到的 fd3 才是独立竞争者，可能被这把锁拒绝，即使它们都属于同一个进程。用 dup 出来的编号测试“自己能否再次获锁”，没有构成想要的竞争实验。

文件名只负责查找对象。本站的文件监听与替换文章已经说明，同一路径可以指向另一个 inode；flock 又增加了打开描述及其引用的生命周期。监控若仅检查 job.lock 存在，就无法区分从未加锁、仍在持有、已经释放三个状态。一条没有区分力的信号，不应承担是否允许执行下一轮任务的决定。

在 Linux 自有临时目录做描述符对照

以下是未执行的完整 Python 教学程序，只针对 Linux 本地文件系统的 flock 语义。本站宿主是 macOS，没有把在此运行视为 Linux 认证，也没有运行下面程序。保存为 lock_probe.py，准备 Linux 与 Python 标准库，在独立环境拟运行 python3 lock_probe.py。不要把路径替换为真实任务的锁文件。

import fcntl
import os
import sys
import tempfile
from pathlib import Path

if not sys.platform.startswith("linux"):
    raise SystemExit("this fixture requires Linux")

with tempfile.TemporaryDirectory(prefix="flock-probe-") as directory:
    path = Path(directory) / "job.lock"
    descriptors = []
    exclusive = fcntl.LOCK_EX | fcntl.LOCK_NB
    try:
        first = os.open(path, os.O_CREAT | os.O_RDWR, 0o600)
        descriptors.append(first)
        fcntl.flock(first, exclusive)
        duplicate = os.dup(first)
        descriptors.append(duplicate)
        contender = os.open(path, os.O_RDWR)
        descriptors.append(contender)

        def expect_blocked():
            try:
                fcntl.flock(contender, exclusive)
            except BlockingIOError:
                return
            raise AssertionError("independent open unexpectedly acquired lock")

        expect_blocked()
        os.close(first)
        descriptors.remove(first)
        expect_blocked()
        os.close(duplicate)
        descriptors.remove(duplicate)
        fcntl.flock(contender, exclusive)
        assert path.exists()
        print("acquired after last related close; path remains")
    finally:
        for descriptor in descriptors:
            os.close(descriptor)

程序的独立预期来自排他合同：最初独立 open 不应获锁；关闭 first 后仍不应获锁；关闭 duplicate 后才可获锁；路径在最终时刻仍存在。这样把“文件留下”和“锁还在”放在同一轮中检验，而不是用两次不同运行的截图拼成结论。成功输出只描述这几个条件，不表示真实作业已经防止并发。

异常也需要准确处理。程序只把 BlockingIOError 当预期竞争拒绝，其他异常保留为失败。权限错误、描述符无效或文件系统不支持，不应一律捕获后写成“第二个进程被锁住”。非阻塞选项避免实验无限等待，但不提供超时重试政策。真实业务是跳过、排队还是失败，应由任务合同另行选择。

为什么不把删除文件当作解锁协议

释放有明确动作：对共享这把锁的相关描述符执行 LOCK_UN，或者关闭全部相关引用。删除路径不在这份释放条件中。由此可以作出一项对象身份推论：如果持有者还打开着旧对象，另一个参与者删除名字并重建同路径，后来者可能打开的是新对象，双方不再竞争同一个文件。文件名恢复一致，并不能让旧锁自动搬家。

因此正常的互斥约定应让参与者使用稳定的公共对象，让持有描述符的范围覆盖整个受保护动作。实验结束后删除自有临时目录，只是清理本次素材；它不是为生产锁推荐一种轮流删除重建的算法。若确需回收锁文件路径，应先明确所有潜在参与者的生命周期和对象身份，不能从某个文件看起来陈旧推断已经无人使用。

显式 LOCK_UN 也有一个与关闭不同的效果：任一共享描述符可以释放这把锁，即使另一个重复描述符仍开着。若某个库收到 fd 的副本并随手解锁，其他持有者可能失去预期保护。评审应跟踪谁有权解除锁，而不仅是谁最终关闭资源。上面的对照特意使用最后关闭路线，以便隔离这个时点。

父进程退出后，后台子进程会把锁留住吗？

可能，条件是子进程仍保留相关打开描述的引用。fork 后父进程退出，只关闭了父进程自己的描述符；不能从父 PID 消失推断所有引用已关闭。这是对子进程生命周期的新追问，主例只有一个进程里的 dup，没有覆盖这种任务组织方式。

跨 exec 的描述符还受 FD_CLOEXEC 或 O_CLOEXEC 影响。open 手册说明了关闭执行标志；语言运行库也可能主动把新 fd 设为不可继承。因此不能笼统断言所有后台执行都保留锁，或者所有 exec 都自动释放锁。应记录实际创建方式、继承设置和进程关系，再用独立竞争者验证。

互斥的真正要求还包括受保护动作何时结束。假设主程序拿锁后启动一个写文件子任务，随后自己关闭全部引用，却没有等待子任务完成。下一轮独立竞争者可以合法获锁，而前一轮写入仍在继续。这不是锁提前违反合同，而是程序把锁的范围画短了。应让持有者等待完整动作，或者把相关引用及其关闭责任明确交给实际执行者，不能只把启动子进程当作完成。

反方向也有成本：子进程不再需要保护，却因意外继承一直保留引用，会让后续竞争持续被拒绝。看到锁还在时，应沿进程关系核对描述符，而不是立即删除路径。记录可以只包含 PID、文件身份、打开来源和关闭时点，不需要打印受保护文件内容；如果权限不足以观察其他进程，就保留未知，不虚构一份“没有持有者”的结论。

最后关闭路线与显式释放路线最好分开验证。上面的脚本只检查前者；若另加一项 LOCK_UN 对照，应让 duplicate 仍然打开时释放，再观察 contender 是否获锁。这样独立证明“引用仍在但保护已解除”的另一种状态。两条路径的结果都不能仅凭文件存在推断，也不能用其中一条通过替另一条签收。

最后还要限定合作范围。Linux 本地 flock 通常是协作锁，不使用它的写入者可以绕过约定。手册对 NFS、SMB 和历史内核版本另有说明，不能把本地结果外推到远端共享存储；某些 SMB 条件还会改变协作性。真正的验证记录应包含内核、Python、挂载类型、脚本哈希、标准输出与即时退出值。先确认所有任务竞争的是同一对象，再让锁的持有范围对应完整动作。
