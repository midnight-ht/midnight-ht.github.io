weakref.finalize 已登记，为什么删除变量后对象仍活着？

用本地 CPython 对照验证回调持有目标与独立回调的差别。

正文

核心要点

  • 绑定方法可能持有目标。
  • 独立核对对象存活和登记状态。
  • 主动关闭仍需要明确职责。

把对象自己的绑定方法交给 weakref.finalize，可能让回调持有本来要等待回收的对象。删除原变量以后，另一条引用仍然存在。需要让回收触发后备清理时，应让回调只持有真正需要的信息，避免把目标对象绕回登记记录。

设想一个组件持有需要释放的本地资源。作者希望外部不再使用组件时也能收尾，便在构造时登记组件自己的清理方法。测试删除了变量，却始终看不到通知，于是怀疑没有收集垃圾。先画出从清理登记到回调、再从绑定方法到对象的关系。此处多出来的是引用本身，主动调用垃圾收集器也不能替程序解除它。

回调保留了哪些对象

标准库警告，finalize 的函数、位置参数和关键字参数不能直接或间接持有目标对象。绑定方法是明确提到的反例，因为它包含实际调用时使用的实例。换成一个在模块中定义的函数也要继续检查参数。如果把目标当作参数传入，引用仍存在。捕获目标的闭包同样不能解决这个问题。应当确定清理实际需要的是哪一个资源编号、句柄或独立操作，再核对这些值能否反向找到持有它们的对象。Python weakref.finalize。

观察对象是否存活时，不要把它取出来长期放到额外变量里。测试可以保存一份弱引用，用一次布尔观察确认是否还能取得目标。finalizer 的 alive 表示这项登记是否仍可被执行，不是对象已经初始化、资源还开放或业务操作正常的标记。把这两项放在并列字段，才不会把登记状态推断成真实资源状态。

两份对象只改变回调持有的值

下面完整程序在本地 CPython 3.11.15 执行。第一份对象登记自己的绑定方法，第二份只登记列表的 append 和一个常量标记。两个标记都存到同一个纯内存列表，便于核对各自触发情况。这里没有打开文件、数据库或连接真实服务，也不要求不同解释器在同一语句后采用相同回收时点。

import gc
from weakref import finalize, ref

events = []

class Payload:
    def mark(self):
        events.append("held")

held = Payload()
free = Payload()
watch = (ref(held), ref(free))
bad = finalize(held, held.mark)
good = finalize(free, events.append, "free")

del held, free
gc.collect()
assert tuple(ref() is not None for ref in watch) == (True, False)
assert tuple(entry.alive for entry in (bad, good)) == (True, False)
assert events == ["free"]
bad()
bad()
gc.collect()
assert watch[0]() is None
assert not bad.alive and events == ["free", "held"]
print(events)

实际检查表明，删除外部变量后第一份对象仍可从弱引用找到，且它的登记保持存活。第二份对象已经不可取得，对应登记已经执行，记录只含 free。随后程序主动调用第一份登记两次，最终只增添一次 held。再次检查第一份弱引用时已不可取得对象。这组结果同时保留独立存活观察和通知列表，避免用没有日志反推所有对象都还活着，或用一条通知推断实际资源已经安全释放。

主动调用一个活跃登记会执行回调并标记登记不再可用，后续调用返回空值。这个显式入口与等待收集器是不同的计划。若真实程序需要在请求返回前完成关闭，最好使用自己能掌握的生命周期，并把后备登记与主动关闭之间的责任写清。此样本只检查普通内存回调，不覆盖并发的关闭尝试，也没有模拟关机。

给清理职责一个可以验证的单独入口

应用中可以让普通关闭操作使用不依赖目标对象的清理函数。若清理只需要文件路径，传独立的路径值；若需要另一个对象，先确认那个对象不会持有原组件。验证时应分别构造最小回调与闭包捕获的控制，观察删除唯一外部变量以后弱引用是否仍存在。检查真实资源是否释放则应另取文件、锁或连接的观测证据。本例没有运行这些集成路径。站内的 ExitStack 交接 讨论显式移交已经登记的清理，本篇所问的是后备回调如何意外保持目标存活。

即使没有引用问题，也不能把解释器退出当成按时清理的业务保证。文档描述仍存活的登记默认会在退出时运行，但晚期退出还有限制，实际程序也可能因中断等条件不走普通收尾。应该为资源正常关闭、失败关闭和重复调用分别设置断言。只检查程序末尾出现过一条信息，不能说明过程中资源及时可用。上面的运行没有测试解释器关闭时回调顺序。

在一个应用测试里，可以让正常关闭先释放一个编号对应的资源，再丢掉组件，验证后备回调不会把同一编号再释放一次。另准备一个没有正常调用关闭的组件，核对后备机制只在观测到适当生命周期后运行。资源类型如果需要在特定线程关闭，还要留出独立的调用记录，不能从内存列表中的标记推断线程要求已经符合。这些都是未执行的集成控制。应用应给主动关闭和后备动作不同的观察点，错误由负责的拥有者记录，避免回收后的回调只留下难以归属的一条日志。

想取消登记而不执行回调，detach 返回什么？

对于仍存活的登记，detach 会先令它失效，再返回目标、函数、参数和关键字参数四元组。它不执行回调。若把返回值长期保存在变量里，四元组中的目标仍是强引用。可以给一个独立对象登记回调，调用 detach 后分别核对登记失效、回调未写入事件、丢弃返回值以后才重新检查对象存活。这个取消登记变体未运行，主例用的是显式调用。
