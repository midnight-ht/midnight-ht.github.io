Buildx 回执里有两个 digest，发布该记录哪一个？

从 Buildx 元数据追踪 OCI 输出描述符及清单中的配置引用，用本地归档读回两个摘要。

正文

核心要点

  • 输出摘要和配置摘要标识不同对象。
  • 通过 OCI 清单核对配置引用。
  • 发布记录同时保留对象类型。

Buildx 回执里出现两个不同的 SHA-256 值。要记录构建导出的镜像对象，先看 containerimage.digest 及其输出描述符；containerimage.config.digest 则用于核对镜像清单引用的配置对象。它们分别对应不同的文件内容，在同一份回执里也不应该被当作可以互换的镜像编号。

问题常发生在迁移发布脚本时。旧记录只留一个镜像摘要，下一版开始导出 Buildx 元数据，维护者按字段名找到一个最像镜像配置的值。构建仍然成功，后续检查却对不上刚导出的制品。与其在日志里挑一串看起来像摘要的字符，可以直接在归档中顺着对象关系验出这两个值各自代表什么。

先把导出的对象固定住

创建一个空目录，保存以下 Dockerfile，再用 printf 'receipt demo\n' > marker.txt 创建构建输入。例子从 scratch 开始，仅复制固定内容，无需拉取基础镜像或运行程序。选择支持 OCI 导出的本地 Buildx builder，并把输出写到构建上下文之外。固定一个目标平台并关闭归档中的额外证明材料，使例子只核对预定的镜像清单和配置。若实际输出描述符不是镜像清单，下面的核对程序应当拒绝该归档，留给另一套结构判断。

FROM scratch
COPY marker.txt /marker.txt

从该目录执行下列构建。脚本接着要用 Python 读取归档，不需要把镜像载入本地镜像库，也不需要推到任何 registry。

work=$(mktemp -d)
docker buildx build --platform linux/amd64 --provenance=false --sbom=false \
  --output "type=oci,dest=$work/output.tar" \
  --metadata-file "$work/receipt.json" .

先看看回执的三个字段。containerimage.descriptor 给出输出对象的媒体类型和摘要。containerimage.digest 记录该输出摘要。在这里的单平台归档中，两者指向一份镜像清单。OCI 清单再用自己的 config 描述符指向配置内容，这是另一份需要独立读取的对象。归档根部的 index.json 在这个例子里只是找到清单的入口，它和所指对象是两份不同的字节。判断回执应匹配哪个对象，要沿描述符走，不能对任意一个名为 index 的文件算出摘要就直接比较。

将下面程序保存为 verify.py，执行 python3 verify.py "$work/receipt.json" "$work/output.tar"。程序先要求回执描述符确实是示例预期的类型，然后分别从归档中的内容地址读取清单和配置，并对各自原始字节计算 SHA-256。配置文件要由已验证的清单指向，而且对应值还要与回执相同。这样即便两条元数据都长得像摘要，也能查出是否连错了对象。

from hashlib import sha256
import json
from pathlib import Path
import sys
import tarfile

receipt = json.loads(Path(sys.argv[1]).read_text())
descriptor = receipt["containerimage.descriptor"]
output = receipt["containerimage.digest"]
config = receipt["containerimage.config.digest"]
assert descriptor["mediaType"] == "application/vnd.oci.image.manifest.v1+json"
assert descriptor["digest"] == output

with tarfile.open(sys.argv[2]) as archive:
    def read(name):
        member = archive.extractfile(name)
        assert member is not None
        return member.read()

    def verified_blob(digest):
        algorithm, expected = digest.split(":", 1)
        assert algorithm == "sha256"
        data = read(f"blobs/sha256/{expected}")
        assert sha256(data).hexdigest() == expected
        return data

    entries = json.loads(read("index.json"))["manifests"]
    assert any(item["digest"] == output for item in entries)
    manifest = json.loads(verified_blob(output))
    assert manifest["config"]["digest"] == config
    verified_blob(config)

print("output", output)
print("config", config)

本地 Docker Desktop 引擎 29.8.2 与 Buildx v0.37.2 上，构建与读回都成功。Linux amd64 输出清单的摘要以 d490f6f4 开头，配置摘要以 ef05c138 开头，程序验证了两份对象的完整摘要。前缀只为方便说明这一次观测，不能拿来验另一次构建。输出摘要究竟是哪种对象，要看当次描述符；当前程序也没有验镜像层、镜像内容能否运行，或是 registry 的接收状态。关闭额外证明材料的选项只是为这个样例约束结构，不能从回执里有没有构建信息推断远端镜像是否有证明材料。

交付记录要指向下游实际拿到的对象

如果下游要获取这趟构建导出的镜像对象，在构建交接中留输出摘要、媒体类型和产物的所在位置。若解包或镜像分析流程还要核对配置，可另存配置摘要，注明它由清单内部引用。配置收到改变时，引用它的清单也需要指向该配置内容；反过来只看到配置一致，无法保证清单一致，因为清单还涉及层或其他字段。配置测过与镜像整体一样是两个不同的结论。

一个容易操作的负向控制是保留归档不动，只把复制的回执里的输出摘要换成配置摘要，再运行核对。程序应该拒绝它，因为描述符仍指原清单。如果同时把描述符也改成配置摘要，归档入口仍没有把它列成输出清单。本地把两个修改各写进一份独立回执，归档保持不变。只换输出值的一次在描述符相等的断言处拒绝了输入，同时换描述符的一次在归档条目断言处拒绝，两次均退出一。这个练习检查下游能否拒绝一个存在、格式正确、但放错位置的摘要。它针对的正是单纯检查字符串格式会漏掉的故障。

面向正式发布时，制品接收方还应报告自己接受了什么。比如归档验过了，之后才进入上传流程，回执只能证明本地导出能读。正式 registry 如何引用已交付对象，应按那次发布的结果另行核对。把本地结构验证和接收端记录分开保存，遇到回滚或对象对不上时就知道该查构建导出还是后续交接。

例如发布任务发现接收端的摘要不同，可以先核对这一条记录来自哪个构建，以及接收端在谈镜像清单还是另一种输出。若双方检查的对象类型都一致，才比较所指字节。保留构建回执、归档和交接日志的关联，有助于定位是拿错了构建结果，还是读取了别的标识字段。生产发布的出入站验证还要以实际远端接收结果为准，本地实验未执行此步骤。

多平台构建的输出摘要指哪个平台？

如果输出描述符的类型是 OCI 镜像索引，输出摘要对应的是索引，不能直接拿来代表某个平台的清单。OCI 索引的条目各自带有摘要，可以按平台元数据挑选所需条目，再验证那份清单和它的配置。选择时核对操作系统与架构，遇到需要区分变体的架构还要查变体；缺少所需信息时先确认目标条目，避免随手用第一条。本地例只运行了单平台，索引输出分支未运行。上面的核对脚本遇到索引描述符会在类型断言处停止。
