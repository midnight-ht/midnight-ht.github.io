SMOVE 返回 1，为什么目标集合的数量没增加？

用两个独立成员对照 Redis SMOVE 的成功回复、源移除与目标新增。

正文

核心要点

  • 目标已有成员时只需要源移除。
  • 相同成功回复可以对应不同目标增量。
  • 分别核对源和目标。

Redis 的 SMOVE 返回一时，目标集合大小不一定增加。目标已包含该成员时，命令只需要把它从源集合移除。要做状态对账，应分别检查源成员有没有留下、目标有哪些成员，以及本次到底改变了什么。

假设一个分配工具把标签从待处理集合移到已确认集合。目标里有一个来自先前调度的同名标签。这次操作确实从待处理集合里移除了它，Redis 也返回一，但目标的数量保持原样。如果把成功回复直接累加为“新增确认标签”，报告会多算。一条状态转换可以满足源侧处理要求，同时并不产生新的目标身份。应先确定数字的统计对象，再选如何观察。

目标有同名成员时发生了什么

Redis 文档规定，SMOVE 原子地把指定成员从源集合移到目标。源集合不存在或者没有该成员时，返回零且不执行移动。源成员存在而目标已有它时，只执行源侧移除。因此一和零回答的是本次能否移动源成员，不直接提供目标集合净增加数。样本使用两个不同的集合键，不讨论两个参数指向同一键的额外情况。Redis SMOVE。

原子移动的保证范围属于这条命令。应用如果在移动以前查一次大小，移动以后再查一次，在有其他写入者时不应把差值全归给自己的操作。以下三个对照限定在自有隔离实例和独立测试键，没有其它客户端更新这些成员。这里的目的，是把机制和应用对账的假设分别写出来，避免把一条孤立回复当作关联多个观测的凭据。

用两个成员制造不同的目标变化

下方是未执行的示例。请用 Redis 隔离测试实例与起初不存在的键。前两条命令分别建立源集合 a、b 和目标集合 a、c。花括号使用相同标签，集群部署仍应按实际多键路径验证，本文未连接集群。

SADD {move-demo}:source a b
SADD {move-demo}:dest a c
SMOVE {move-demo}:source {move-demo}:dest a
SCARD {move-demo}:source
SCARD {move-demo}:dest
SMOVE {move-demo}:source {move-demo}:dest b
SCARD {move-demo}:dest
SMOVE {move-demo}:source {move-demo}:dest z

第一项移 a 预期返回一；源只剩 b，目标仍是 a 和 c。后续两个计数分别应是一和二。第二项移 b 同样返回一，源没有剩余成员，目标加入 b 后预期大小是三。最后移 z 返回零，因为源不存在该成员，不能据此把目标中是否有 z 也写成已验证。若需要正式对账，应在相同隔离条件下分别核对每一步列出的成员身份，而不仅依赖样本内的计数命令。命令路径没有运行，所有状态都是按固定输入推演。

这两个成功分支给出相同的移动回复，却产生不同的目标增量。可以让测试捕获一个错误实现，把两次回复全部算作目标新增。这个实现会报告新增二，实际目标初始有两项，最后三项，独立预期只新增一项。对照应保持 a 与 b 的初始归属不变，避免第一次移动的结果用于生成第二次预期。记录真正测到的状态时，可给每次观测附上源键、目标键与成员值，方便检查是否取错集合。

把报表上的动作写成可区分的合同

如果产品要统计源集合中少了多少待办，成功迁出次数在这个不带并发的模型里就是相关证据。如果关心新增多少独立的目标成员，就应该读取足以支持新增结论的状态。把两种指标相互替换，会让部分重复成员不再可见。还可给操作记录分别留源侧结果和目标侧状态，让使用者能解释同一回复为何产生不同变化。站内的 批量查成员状态 讨论读请求位置，本篇关注的是写入后两个集合如何改变。

还应把成功后回包丢失与第一次就没找到源成员分开。从已经移动成功的状态再发一次同样的命令，源可能不再含该成员，因此第二次返回零。只凭后一条回复，不足以推断之前的操作是否发生。若业务需要可靠恢复，应另有可以查询的业务记录或状态判断。这里没有测试丢回复或重试策略。要以教学条件验证这一点，可先确认源侧确实存在成员，再执行一次移动，把第二次作为独立尝试，分别保留两次结果，而不是覆盖成最终一次状态。

如果报表要提供成员身份，最终大小本身也可能不足。设想一个归属错误把 a 留在源里，却把另一个成员移走；有可能得到同样的源大小。让测试在第一步直接核对 b 仍在，a 已移出，并读取目标中的 a 与 c。不要先把两边合到同一个集合后比较，因为那样会丢掉成员属于哪一边的信息。另给第一次移动配置一个独立业务编号，让异步对账只根据相应记录更新汇总。这个应用层对照未运行，也未实现把前置状态和后置状态绑定为一次原子读取。

如果目标键尚未创建，第一次移动后应该查什么？

用另一个源键放一个新成员，目标键起初不存在。源实际拥有该成员时，移动后应在目标看到对应元素；给这一步的键存在性和成员检查各写预期。再准备一个源也缺少成员、目标也缺失的负例，预期返回零且目标不被这次调用建立。不从前面已经存在的目标推导这两条结果。追问命令未运行，也没有在生产环境检查键的历史来源或过期行为。
