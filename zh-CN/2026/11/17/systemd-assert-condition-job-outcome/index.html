同样缺文件，systemd 为什么一次跳过、一次启动失败？

用同一路径对照 systemd 的条件跳过、断言作业失败和服务进程执行标记。

正文

核心要点

  • 路径相同可以得到两种启动结果。
  • 断言失败不自行改变单元状态。
  • 分别核对启动命令和进程证据。

同一份就绪文件缺席，systemd 可以跳过一项服务，也可以报另一项服务的启动作业失败。差别在单元定义是用 ConditionPathExists= 还是 AssertPathExists=。两者检查的路径一样，但值班人员会收到不同的启动结果。

例如一台机器并未配置本地报表功能。可选的报表服务无须在这台机器启动，另一个明确要求读取报表配置的工作单元则应在配置缺席时告诉调用者发生了什么。把两种检查写成同一个词，往往会把“本机不提供这项功能”和“分配给本机的任务缺少输入”混起来。用两份只改一项设置的定义，可以在决定配置词之前观察两种行为。

两份单元使用同一个输入

在一台可以清理的 Linux 测试机上用系统管理器做实验。将下面两份定义保存到 /etc/systemd/system/，文件名分别为 zy17-condition.service 和 zy17-assert.service。用本机实际存在的 echo 路径；例子采用 /bin/echo。这里的绝对探针路径专门留给实验，开始前应确认它不存在且没有其他程序使用它。

[Unit]
ConditionPathExists=/run/zy17-lab/ready

[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/bin/echo zy17-ready

[Unit]
AssertPathExists=/run/zy17-lab/ready

[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/bin/echo zy17-ready

下面这个函数分别记录启动命令本身的状态和单元对象上的观测值。安装定义后先重新加载。第一趟保持探针缺席，第二趟才创建探针。所有命令都在执行过必要权限提升的测试终端运行。状态判断用新单元从未启动过的初始条件，避免拿一个早已处于活动状态的实例试启动。

probe() {
  status=0
  systemctl start "$1" || status=$?
  printf '%s start=%s\n' "$1" "$status"
  systemctl show "$1" -p ActiveState -p ConditionResult -p AssertResult
  journalctl -b -u "$1" --no-pager
}

systemctl daemon-reload
probe zy17-condition.service
probe zy17-assert.service

mkdir -p /run/zy17-lab
touch /run/zy17-lab/ready
for unit in zy17-condition.service zy17-assert.service; do
  probe "$unit"
done

缺文件的一趟，条件不满足会跳过启动，正常跳过时直接调用的启动命令应当成功返回；断言不满足会让启动作业失败，因此预期另一个启动命令非零。两个单元都不应打印执行标记。断言失败本身不会把单元切换为 failed，所以从未启动的干净单元仍预计是 inactive。不要把第二条命令的非零解释成 echo 已经运行并退出失败。单元记录和服务进程日志分别支撑这两个判断。

文件出现之后，两条启动都应通过路径检查。示例带有 RemainAfterExit=yes，所以一次性命令成功结束后，仍预期看到两个单元处于 active，还应分别在本轮对应的日志里看到 zy17-ready。获取日志时用本次运行时间或一次全新的实验机器界定范围；旧标记无法证明这次真的执行。这里没有 Linux 管理器运行回执，两趟状态和日志都是依据手册及所给定义写下的预期。实验后可停止两个单元，删除两份实验定义与探针，重载管理器。

失败的是这次作业，还是当前服务

如果只在两趟之后执行一次 systemctl is-active，很难用它解释之前的断言结果。首次探针缺席时，两个单元都可能显示未活动；后续探针被补齐，两次启动都可能成功。最新状态随时间变化，无法代替较早的作业回执。自动化调用者应给每次启动分别保存时间、命令结果、单元状态和该时间段的执行标记。缺文件时断言报错与服务二进制是否运行，由两份不同证据回答。

选项要沿着机器职责选择。可选服务的输入不存在本来就是预期状态，就用条件表达这个执行范围。维护者明确要求这台机器运行某项任务，缺输入需要追查，就用断言让发起启动的人收到作业失败。这样做不会替上层决定如何重试。譬如准备脚本会在五秒后写入探针，应该先验证准备过程并明确在之后发起新的启动请求。不要从路径出现这一件事推断已经发生了自发启动。本例中每次重新检查之前都明确发出了启动请求。

发布验收可以提前写好预期矩阵，再跑真实目标系统。选择条件时，有文件的正向对照要能看到新标记，否则或许真正坏在可执行文件而不是启动时的路径判断。选断言时，缺文件的负向对照要保存作业失败回执，保证告警和自动化确实接住了这次调用。只把启动终端里的报错抄到复盘，还缺少它对应的输入和单元状态。把这三个观察配对以后，接手人才能决定修环境、改服务角色定义，还是检查真正运行过的进程。

给监控任务设计复核时可以另保留一个本来就应该被跳过的实例。若每次发起启动后只询问单元是不是 active，这个实例和缺少必需输入的实例都会进同一故障分组。改用当次作业回执分类，再查有没有执行标记。对预期跳过的可选实例记录原因，对断言不满足的任务保留失败并交给准备步骤处理。还可以设计一个独立负例，在探针存在的情况下让实验服务执行一条明确返回失败的命令。这回应当核对进程的执行结果和服务状态。本文没有运行这组额外对照。它检验的是告警是否能区分单元定义拒绝启动与进程真正启动后失败。

两条候选路径只需要满足一条，怎么写？

可以把若干检查写成触发式检查，以竖线 | 修饰检查值。systemd 手册说明，有触发式条件时至少一个要成立，同时所有普通条件仍要成立。比如可选服务能用本地配置或挂载配置之一时，可给两个路径都标触发式条件；再保留一条普通条件要求共同目录存在。即使找到备用配置，共同目录缺席时也应跳过。这是相对于主实验新增的分组条件。断言也有对应写法，没满足断言组时仍影响启动作业。本文没有运行这些组合。
