按钮有焦点，为什么 :focus-visible 可能没匹配？

同一按钮分别用 Tab 和点击，读活动元素、两个选择器与最终焦点指示，避免把截图当状态。

正文

核心要点

  • 焦点与需要明显指示的状态应分开读
  • 原生按钮的点击行为取决于环境
  • 保留可辨识的键盘焦点提示

同一个按钮，按 Tab 到达时有明显外框，鼠标点它却可能没有。若只看截图，很容易以为按钮在第二种情况下没收到焦点。先读活动元素，再比较 :focus 与 :focus-visible。它们回答的是两个问题：焦点落在哪里，以及这个焦点此时是否需要被明显标出。

两条选择器都和焦点有关，判据不同

Selectors Level 4 将 :focus 用于当前拥有焦点的元素。对这个独立页面里的原生按钮，可以读取文档的活动元素，确认是不是目标按钮。获得焦点并不等同于已经执行按钮动作。键盘按 Tab 把焦点移过去后，用户仍可决定是否激活它。

:focus-visible 的条件更窄。元素需要有焦点，而且用户代理认为应该明显指示。规范列出一些建议，会考虑当前输入方式、用户偏好和控件是否需要键盘输入。这个伪类让作者根据浏览器已经做出的判断补充样式，不用把所有指针事件一律当成可移除焦点提示的信号。

典型差异是，键盘移动到按钮时有焦点提示；指针操作使按钮获得焦点时，浏览器有时不要求同样的提示。但首先要确认目标真的获焦。一些平台上的点击不一定把焦点给按钮。只凭点击事件或触发了应用操作，无法判断这条选择器为什么没匹配。

将这个区别用在改样式时，能避免两个相反的故障。一是键盘用户到达后看不到焦点，因为作者只为指针位置改了外观。二是点击之后没有自定义外框，程序误判焦点失败并强行把用户送到另一个控件。读状态是诊断，保留用户能继续操作的视野则是实际验收。

用同一个按钮分别读指针和键盘结果

下面的页面包含两个原生按钮，目标按钮使用两条独立规则。普通获焦时可改变边框颜色，匹配 focus-visible 时再加明显轮廓。示例不删除浏览器默认焦点提示。每次写日志会记下动作、目标是否为活动元素、是否匹配普通焦点与是否匹配指示焦点。

<!doctype html>
<meta charset="utf-8">
<title>Focus comparison</title>
<style>
  #target:focus { border-color: #20506d; }
  #target:focus-visible { outline: 3px solid #20506d; outline-offset: 3px; }
</style>
<button id="start" type="button">Start</button>
<button id="target" type="button">Target</button>
<pre id="result"></pre>
<script>
const byId = document.getElementById.bind(document);
const target = byId('target');
const output = byId('result');
const hasSelector = CSS.supports('selector(:focus-visible)');

function record(action) {
  const active = document.activeElement === target;
  const focused = target.matches(':focus');
  const indicated = hasSelector ? target.matches(':focus-visible') : 'unsupported';
  output.append([action, active, focused, indicated].join(' | ') + '\n');
}

document.addEventListener('keyup', event => {
  if (event.key === 'Tab') record('tab');
});
target.addEventListener('click', () => record('click'));
</script>

键盘用例从新页面读起。先用 Tab 到达 Start，再按 Tab 移到 Target，读取由 Tab 产生的最后一行。预期活动元素与普通焦点均为真，且符合浏览器对键盘操作的可见指示建议。观察时也要看实际外框，因为选择器匹配并不能证明颜色、大小与周围背景已经提供足够反馈。

指针用例重新打开页面，直接点击 Target。若普通焦点为真，而可见指示选择器为假，这个结果与浏览器的输入方式判定相符。若两条都为真，也不能只凭本篇把它判为错误。系统偏好可能要求保留焦点指示。若活动元素不是目标，应单独记录点击没有使该按钮获得焦点的情况。

这些是按规范和代码设计的观察步骤。文章没有实际运行浏览器、键盘或辅助技术，也没有给出平台支持矩阵。真实测试可以将操作、活动元素、选择器匹配、实际是否有可辨指示分别记录。这样一份不如预期的截图才能对应某一个明确失败点。

改的是样式，验证的是能否继续操作

不要先把所有焦点轮廓删掉，再指望一个新的选择器接住所有环境。先验证已存在的键盘反馈能清楚标出当前控件。可见指示的表现也不止一个属性，边框颜色、轮廓与背景共同决定用户能不能辨认。代码示例只说明两条选择器独立，配色应按产品实际背景再查。

另外记录平台的键盘设置。有的环境进入页面后不会用相同的 Tab 路径浏览所有按钮。到达目标之前，要核对是否处于文档内，以及这一轮有没有其他组件拦截按键。如果目标根本没有进入序列，改焦点样式不会解决导航问题。

若界面还要支持高对比度或强制颜色设置，单独复验可见反馈。一般主题里一条醒目颜色，在其他主题中可能与背景太接近。验收说清楚看见了哪个控件而不是只写「有颜色」。这不要求脚本替浏览器重写焦点规则，而是要求在产品用法中确认可识别。

有一条适合防回归的决策：先在独立页面证明样式能区分两次操作，再把同一检查接到产品真实按钮。独立页面若能看到轮廓，产品中却看不到，检查组件样式的优先级和焦点是否被更新流程移动。比如点击后组件替换了按钮节点，需要重新确认留下的是哪一个元素。这样能把样式没生效和节点已经不是原按钮两类问题分开。

指针点击的是文本输入，也会看见焦点指示吗？

可能，而且这是规范建议应考虑的状态。用相同思路把目标换成一个可编辑文本输入。点击后键盘很快会用于输入文字，因此对这种支持键盘输入、已获焦的元素，规范建议让它匹配 focus-visible。这个新增条件说明不能用「指针操作就不出现指示」作为团队规则。

测试这一项时先确认输入控件真的拿到焦点、可以键入，然后读选择器与可见反馈。如果浏览器对原生按钮和文本输入有不同结果，记录控件种类。主例只用按钮，不能替文本输入的交互决定结论。

如果焦点已经存在但被作者布局挡住，可以另读焦点不被遮挡的最低要求如何核对。
