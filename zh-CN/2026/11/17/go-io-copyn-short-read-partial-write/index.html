Go CopyN 报错，目标为什么还是多了两个字节？

用固定三字节预算区分 Go CopyN 的完整复制、短源失败和目标已写前缀。

正文

核心要点

  • 固定长度错误可能留下目标前缀。
  • 独立核对写入长度、错误和目标。
  • 需要完整交付时定义暂存和交接。

Go 的 io.CopyN 报错时，目标仍可能已经收到数据前缀。只读到两个字节却要求复制三个，失败并不会撤回那两个字节。判断结果是否可以交给下游时，要同时检查返回的长度、错误和目标状态。

假设一个本地记录导出器先写入固定头部，再从来源拷贝一段长度已知的正文。有一次正文提前结束。调用方看到复制错误，便认为目标仍只含头部，后来在同一目标上重试。原来的前缀却还在，重试结果可能被拼成一份前后混合的内容。能否继续使用原目标，取决于写入是否已经发生以及应用有没有清理或隔离它。测试不能只用返回值表示这份目标当前可读到什么。

固定长度与写入进度是两项观测

Go 标准库说明，CopyN 从源向目标复制指定数量字节，或遇到错误提前停止。返回的已写字节数等于要求数量，当且仅当错误为空。这里关注的是源只提供两个字节的情况。没有读足不是事务失败以后自动反向操作目标的指令。目标可能是内存缓冲，也可能是只能向前写的网络或文件对象。函数只接受普通的 Writer 接口，业务不能默认知道怎样把它恢复到调用前。Go io.CopyN。

排查时还要对照请求长度来源。如果控制字段原本规定三字节，就应让测试固定这个数字，而不是在错误发生以后从实际来源长度重新推算。后者可能把两字节源重新解释成合法输入，使短读回归无法发现错误。应用如果明确允许长度不完整，也需要以自己的合同交付，而非把函数返回的错误直接隐藏掉。

固定三字节预算，分别让来源完整和偏短

以下是未执行的 Go 教学程序。它只使用内存字节缓冲和字符串读取器，不创建文件或网络请求。每条路径独立新建一个以 head: 开头的目标，然后都要求复制三字节。第一条来源包含 abc，第二条只包含 ab。

package main

import (
    "bytes"
    "fmt"
    "io"
    "strings"
)

func main() {
    cases := []struct {
        input string
        count int64
        failed bool
    }{{"abc", 3, false}, {"ab", 2, true}}

    for _, example := range cases {
        target := bytes.NewBufferString("head:")
        n, err := io.CopyN(target, strings.NewReader(example.input), 3)
        if n != example.count || (err != nil) != example.failed ||
            target.String() != "head:"+example.input {
            panic(fmt.Sprintf("unexpected transfer: %d %v %q", n, err, target))
        }
        fmt.Printf("%q: written=%d failed=%t target=%q\n",
            example.input, n, err != nil, target)
    }
}

第一条预期写三字节且错误为空，目标是 head:abc。第二条预期写两字节且有错误，目标是 head:ab。程序给每次比较保留新目标，不需要从某个已经写入过的缓冲里猜测这次的副作用。它也没有断言所有 Reader 都会以某个确定的错误类型终止。验收可以关注实际捕获到的错误类别，但本例的核心要求是计数减少、失败可见、目标仍有前缀。

如果只检查错误存在，错误路径中零字节和已经写出两个字节会得到相同判断。若只检查目标内容，又可能发现前缀正确后误判整个正文都到齐。调用方的诊断记录应保存开始前已有的内容或长度、复制实际增加的长度和结束错误。真实外部结果还可能经过另一层缓冲，写入对象已接受字节与另一进程可以读到它们是两个问题。教学程序用的是内存对象，没有测试刷新或持久化。

决定何时让目标成为可用产物

如果业务要求完整正文才可见，可以把复制结果先放在受控暂存区，确认长度和结果后再交付。暂存不是自动提交机制。文件、网络响应和应用模型实现它的方式不同。对已经写进响应的一段内容，服务无法假设给调用方一个错误就能收回它。若协议允许部分结果，应有单独的终结状态，让读者知道当前前缀没有组成完整记录。站内的 Go 行迭代的结束错误 也处理终点状态，但此处目标已经发生写入副作用。

还可以在应用层设计一个重试负控。第一次让来源只有两个字节，观察暂存对象仍保留前缀。第二次在全新暂存对象里成功复制完整记录，确认交付只有一次完整正文，并且前一次结果没有混入。若应用选择复用目标，先说明它如何恢复原长度，并给恢复失败额外的错误出口。不要将能重置内存缓冲推广成任意 Writer 都能重置。这里未运行重试或错误恢复。

写入者主动报错也应单列测试。让来源确实有三个字节，再给一个按自己合同拒绝后续写入的接收器。验收分别记录实际接受多少、返回什么错误、有没有可见残留。这能区分读端没有提供足量数据和写端不能完全接收。这个附加对照未执行，主例只有完整来源与短来源。

在回归中应给每次尝试单独的记录标识。第一次的目标即便后来被删除，也应保留短读错误和已接受字节数。第二次成功则另保留最终公开内容。若生产合同只允许交付一次，还要检查读者看到了几份结果，不能以第二次成功直接覆盖第一次的错误记录。这项重试日志验证未执行。

来源超过要求的三个字节，会不会一起被复制？

不会超过这次请求的长度。可以另外创建包含 abcdef 的 strings.Reader，要求复制三字节，再独立检查目标只新增 abc，继续从同一读取器读取得到 def。这个观察限于示例采用的具体读取器，真实协议还可能有自己的缓冲位置和记录边界。此追问未运行。主例没有额外字节，不能替一份包含多条记录的实际管道证明切分正确。
