固定宽度的 textarea，为什么能随内容长高？

同宽文本域对照 fixed 和 content，检查输入变长时是否改变盒高，再核对限制高度的样式。

正文

核心要点

  • 默认首选尺寸和内容驱动尺寸不同
  • 固定宽度仍允许改变内在高度
  • 比较增长前后而非固定像素值

备注输入从一行增长到三行，产品希望输入框往下展开，但仍和上面的标题占一样宽。过去的实现给文本域一个固定行数。长文字进入以后，用户靠框内滚动才能看到后半段。可以让内容参与高度计算，同时继续由表单列决定控件的宽度。

宽度由布局确定，高度由内容提出

CSS Form Control Styling Level 1 的草案给 field-sizing 定义了 fixed 和 content。默认的 fixed 保留宿主语言对控件的默认首选尺寸。对 textarea，输入更多文字本身通常不会把这个默认尺寸变成三行内容的高度。控件里的文字可能已经包了几行，外面的盒高还留在原处。

content 则改用内容决定内在尺寸，忽略控件原先的默认首选尺寸。若宽度已固定，textarea 不必横向长开来适配新文字，更多内容行可以改变高度。这个变化发生在内在尺寸阶段，之后仍需满足实际布局约束。写死的块尺寸会改变最终结果，不能拿它证明此值没有参与计算。

想复合一个现有组件，先找到宽度和高度分别从哪里来。宽度可以由表单列、网格或者控件自身声明限制。高度如果来自固定样式，切换 field-sizing 时还要决定是否让它自动。需求里「容器固定」经常只指一列入口的宽度，无须把输入的高度一起固定。

输入文字也会因为可用宽度而换行。本文测试刻意用显式换行，因为输入是可控制的，且短词在固定宽度里不会被额外折行。这样较容易区分 CSS 尺寸策略和字体变化造成的影响。换成实际备注时，普通软换行也会改变内容所需的高度。

用两只同宽的文本域比较一次输入变化

下面的本地页面放两只文本域。属性、字体和宽度都相同，一只保留 fixed，另一只使用 content。开始时只有 One。按按钮后，两只都得到 One、Two、Three 三条显式内容行。脚本不自己计算要写入的高度，只在改值之后读出控件的盒高。

<!doctype html>
<meta charset="utf-8">
<title>Textarea height comparison</title>
<style>
  textarea {
    display: block;
    inline-size: 16rem;
    min-block-size: 2rem;
    box-sizing: border-box;
    font: 16px/20px monospace;
    resize: none;
  }
  #ordinary { field-sizing: fixed; }
  #growing { field-sizing: content; }
</style>
<label for="ordinary">Ordinary field</label>
<textarea id="ordinary" rows="2">One</textarea>
<label for="growing">Growing field</label>
<textarea id="growing" rows="2">One</textarea>
<button id="more" type="button">Use three lines</button>
<pre id="result"></pre>
<script>
const byId = document.getElementById.bind(document);
const fields = ['ordinary', 'growing'].map(byId);
const output = byId('result');

function record() {
  const heights = fields.map(field => field.getBoundingClientRect().height);
  output.append(heights.join(' | ') + '\n');
}
output.append('supported: ' + CSS.supports('field-sizing', 'content') + '\n');
record();
byId('more').onclick = () => {
  for (const field of fields) field.value = 'One\nTwo\nThree';
  record();
};
</script>

先读第一行的支持信息。若为 false，两个盒子都不增长可能只是因为浏览器没有接受声明。支持时再比较两次读数：普通字段的外框高度预期不变，自适应字段的外框预期比自己原来高。不要要求两只在第一行同高。默认行数、最小高度与内在尺寸路径不同，初始差值不影响增长检查。

这些是根据草案和控件设置提出的预期，未在浏览器执行测量，也无跨引擎通过结论。边框、内边距与字体存在环境差异，所以没有写出固定的像素数。使用前后关系更贴近需求。若想核对视觉界面，额外检查两个文本域的宽度仍然相同，以及三行都可阅读。

用测量定位高度到底被谁限制了

支持检查成立后，如果自适应字段没长，先查部署后的样式。用开发工具确认作用中的是 content，块尺寸没有被其他规则固定。比如通用表单组件给所有输入加了一份固定高度，那么当前声明确实被解析，也可能无法在最终盒子里看见内容增长。隔离这条尺寸约束，再对照两次读数。

还可以区分内容已经换行与盒子是否扩展。例如三行都已进入控件，滚动高度变大，而布局盒保持不变。那更像一个存在内容溢出的文本域。若测试只读取字段值，三个词全在里面会让用例通过，却没有回答旁边区域是否被撑开。

产品中的验收可以记录初始备注、后来填入的内容、两次实际盒高和容器宽度。若是读入一段已保存的长文字，再检查首次渲染是否给出合适高度。比起只对着某一张截图加一条适应规则，这份记录能给视图变化提供明确输入与因果。

也要留一个普通布局用例给不支持的环境。即便盒子不自然增长，用户也应能进入输入框、移动光标并找到后面的内容。测到支持不等于整个交互可用，测到不支持也不意味着可以把其余内容截断。项目可以用自己控制的容器和后备样式把基本编辑路径留住。

生长方向也可以反过来验证。让用户先填三行，再删回一行，采集盒高是否能恢复，且光标仍留在输入里。如果原来有一段手写改高逻辑，只支持变高的代码可能留下大块空白。用前后相同的一行文本作起点和终点，可以检查视觉布局是否真的回到原来的状态。达到最小高度后继续减少文字，外框也不需要无限变小。

加了最大块尺寸，输入还会一直把表单撑开吗？

不会一直增高。给自适应控件新增 max-block-size，并确保溢出时能在控件内滚动。把内容改成足够多的行，并让外框先增长到约束，把最后几行继续写进去。预期盒子在上限停止长高，额外内容仍可通过控件内滚动阅读。这个新例与主例不同，因为主例没有上限。

验收时分别记外框高度与内部可访问性。只断言面板不再移动，可能会漏掉尾部内容被裁切且无法访问。若设计还允许手工拖动调整大小，就另开一条操作路径验证那项交互。本文的样本为保持单变量对照，关闭了拖动调整。

关于脚本给控件赋值是否触发输入事件，可另读程序改值和 input 事件的区别。
