CMake 完整安装为什么漏了这个组件？

用三个独立前缀检查完整安装与组件安装的差异，找出开发文件实际落在哪个交付目录。

正文

核心要点

  • 组件名称决定安装规则归组。
  • 完整安装会跳过被排除的规则。
  • 对真正交付的前缀核对文件内容。

CMake 的安装命令顺利结束，运行时文件进了交付目录，开发文件却没出现。先看那条开发文件的安装规则有没有 EXCLUDE_FROM_ALL。标了这个选项，完整安装不会执行它，显式选择它所属的组件时才会执行。

这个区别容易被构建日志掩盖。配置已经生成，安装阶段也执行了，目录里还有其他新文件。若验收只检查安装命令的退出值，缺文件的问题会留到消费端才暴露。对维护安装清单的人，真正的问题是这一趟选中了哪些规则，以及本次目标目录的内容是否符合交付合同。

用同一份定义走三次安装

新建一个目录，写下面的 CMakeLists.txt。项目不需要编译器。两份输入的内容刻意不同，运行时规则始终属于 Runtime，开发规则始终属于 Development。我们只通过命令选择是否指定组件。安装规则的 COMPONENT 给它分组，EXCLUDE_FROM_ALL 决定这条规则会不会被无组件筛选的完整安装选中。这两个属性可以放在同一条规则上，一个负责分组，一个负责完整安装时的排除。

cmake_minimum_required(VERSION 3.20)
project(ComponentFixture NONE)

install(FILES runtime.txt DESTINATION share/demo COMPONENT Runtime)
install(FILES developer.txt DESTINATION share/demo COMPONENT Development EXCLUDE_FROM_ALL)

在同一源目录里创建输入，另取全新的前缀和构建位置。下面用文件内容和另一个文件确实缺席作为断言。前缀之间互不共享，完整安装没带开发文件就能被直接观察，之前留下的同名文件也无法让读回误通过。

set -eu
printf 'runtime\n' > runtime.txt
printf 'developer\n' > developer.txt
work=$(mktemp -d)
cmake --version
cmake -S . -B "$work/build"
cmake --install "$work/build" --prefix "$work/full"
cmake --install "$work/build" --prefix "$work/runtime" --component Runtime
cmake --install "$work/build" --prefix "$work/dev" --component Development

verify() {
  directory=$1/share/demo
  present=$2
  absent=$3
  test "$(cat "$directory/$present.txt")" = "$present"
  test ! -e "$directory/$absent.txt"
}
verify "$work/full" runtime developer
verify "$work/runtime" runtime developer
verify "$work/dev" developer runtime

本地用 CMake 4.2.3 执行了三趟独立安装和读回。完整安装只有 runtime，Runtime 安装也只有 runtime，Development 安装只有 developer。在这个例子里，前两份文件清单恰好相同。不能用清单相同来倒推完整安装总等同于 Runtime。只要再添加一条未排除的其他组件规则，完整安装就有机会产生第三份内容。这里未执行增加规则的分支。

接着查 Development 的正向证据。假如只跑完整安装并看到开发文件缺席，原因可能是规则按设计排除了它，也可能是项目压根没有把正确文件分配给 Development。发现开发文件不在第一份清单以后，显式安装该组件并确认文件确实存在、内容正确，才能排除后一种解释。在真实组件中有多个文件时，选择一项只有该组件能够提供的文件作为证据。若从旧目录中随手找一项多个组件都会放进去的通用文件，就无法知道 Development 这次到底有没有执行。

发布清单该问哪种安装

运行时归档可能明确要求日常完整安装省略内部开发文件。如此一来，运行时归档的验收要同时确认运行材料完整和开发文件缺席，开发归档则验自己的组件清单。若产品说明中承诺普通用户安装之后就能编译插件，构建作业有必要检查无筛选安装的前缀，确认对外承诺的开发文件在那里。此时保留排除项并单独让一个 CI 作业安装 Development，只会证明组件能装，无法代表产品面向用户的默认方式。选哪种规则取决于发布物允许的内容，不能靠是否产生安装日志决定。

一次可复核的交接最好能把前缀与命令配对。比如日志中有两条安装记录，一条把运行时装到完整前缀，另一条把开发文件装到组件前缀。下游打包时若误读完整前缀，它拿到的就是一份缺开发文件的归档，哪怕搜遍本次构建目录确实能找到相应文件。就实际准备交给下游的路径列出清单，必要时再从归档中读回专属文件。回执里的相对文件名、组件参数和打包时的输入目录要能连起来，别让发布任务只给出一个成功标记。

重用前缀会带来另一种误读。例如先往同一处装过 Development，下次执行完整安装后，直接打开目录还可能看到那个旧文件。目录内容只能说明此时磁盘有什么。要确认是不是刚才那趟安装生成的，就换一个空前缀重新走一次。这个复核手段也适用于本地重做打包过程。构建目录可以在多次安装之间保持不变，我们在每趟真正要比较的是目标前缀和组件参数。

还可以用一次故障注入来校准归档门禁。令打包装作自己正在处理开发发行物，但故意把输入前缀改指完整安装目录。用开发文件的相对路径和内容作为断言，这时应当失败。再把输入恢复为 Development 前缀，预期断言通过。这个验收练习不改变项目的安装规则，改变的是消费方拿来打包的路径。前一个步骤可以揭露只检查目录非空的门禁，后一个步骤约束门禁必须接受真实的开发产物。本地实验尚未生成归档，前面三次读回验证的只是安装前缀。接入正式发布后，若归档有进一步的路径改写，应在最终归档里按面向用户的路径再读一次专属文件。

没写 COMPONENT 的规则放进哪一组？

CMake 把未指定组件的规则归入默认组件，默认名称是 Unspecified。项目可以用 CMAKE_INSTALL_DEFAULT_COMPONENT_NAME 改名。比如团队要把几条省略组件名的公用文件规则统一归到 Common，就应核对声明这些规则时有效的默认名称，再在新前缀里显式安装 Common 读回。主实验给两条规则都写了组件名，没有覆盖这个分支。遇到字段写少而组件归档缺文件的情况，先追踪实际分组，不能只检查规则是否出现于项目文件。
