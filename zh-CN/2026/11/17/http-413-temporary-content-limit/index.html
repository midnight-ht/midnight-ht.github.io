收到 HTTP 413，应该缩小文件还是稍后再试？

同一文件可能触发长期大小限制或临时容量限制。用四条本地输入判断何时修内容、何时检查等待条件。

正文

核心要点

  • 413 指请求内容超过接收条件
  • 已知固定上限时修正文件
  • 临时限制下等待提示不保证恢复

上传一份大小为十个单位的资料，入口返回 HTTP 413。项目有人建议删掉文件里的两页，有人建议等九十秒再试。两种做法都有用，但对应不同的条件。若这份内容超过端点长期声明的大小，等待不会让它变小。若入口暂时降低了可收容量，改文件可能没有必要。

先判断哪一种限制挡住了内容

RFC 9110 用 413 表示请求内容大到服务器不愿或无法处理。状态码说明本次请求超过了接收方的能力或策略，单凭它不能确定上限数字，也不会直接说明以后是否改变。客户端需要结合接口合同、响应字段与实际入口判断。

假设一个文档入口明示最多收八个单位。提交大小十会失败。用户若压缩文件或挑选较小的版本，重新检查得到大小八，就可能满足这条规则。不论等待多久，只要现行上限维持八，原来的十仍超出限制。界面可以给出修改文件的办法，避免仅显示一个笼统的重试按钮。

另一个入口平时可以接受十二，某段时间只接受六。客户同样提交十，也会遇到 413。RFC 9110 规定，条件短暂时，服务器应该生成 Retry-After 告知过一段时间可再次尝试。这里的九十秒是例子的虚构输入，表示宣布的等待条件，不等于服务保证九十秒后能收下这个文件。

没有 Retry-After 也不能单独判断限制永远不变。状态没有提供这个结论。遇到无等待信息的响应，可以给出本次内容超出接收条件的反馈，并在界面上按已知合同指出大小要求。若没有那份合同，别从一条失败反推全账号、全入口都使用同一阈值。

同一个大小固定不动，改变规则而不是替服务器猜

下面是用四组输入写成的本地夹具。它定义自己的整数单位和三种配置，分别表示常规的八、临时的六与另一个入口恢复后的十二。只检查模型的大小分支，不实际读取文件、启动 HTTP 服务、等待九十秒或上传数据。模型的二百仅表示当前大小判断通过，不代表文件已经保存。

import {deepEqual} from 'node:assert/strict';

const fixed = {limit: 8};
const temporary = {limit: 6, retryAfter: 90};
const normal = {limit: 12};

function checkUpload(size, {limit, retryAfter}) {
  if (size <= limit) return {status: 200};
  const status = 413;
  return retryAfter === undefined ? {status} : {status, retryAfter};
}

const cases = [
  [10, fixed, {status: 413}],
  [8, fixed, {status: 200}],
  [10, temporary, {status: 413, retryAfter: 90}],
  [10, normal, {status: 200}],
];
for (const [size, policy, expected] of cases) {
  deepEqual(checkUpload(size, policy), expected);
}
console.log('Fixed, reduced, temporary, and restored cases passed.');

本地执行四组断言均通过。先用十对照八，得到 413；在同一规则下把输入减为八，大小检查通过。然后让十遇到临时的六，得到带九十秒提示的 413；在独立的正常十二配置下，同一输入可通过。最后一个结果是已明确开启正常配置才成立，不能由第三条响应自动推出。

这对服务与客户端联合验收都有用。长期限制的试验固定规则，只改变原来超限的内容。临时限制的试验固定内容，只改变团队控制的环境配置。若两项一起变化，客户端成功后便难以解释是文件被改小，还是接收容量恢复。把这两个试验分别命名，能保留真正的恢复证据。

让用户能区分修改文件和等入口恢复

长期规则已知时，可在重新提交前告诉用户可采取的修正。例如现有文档大小超过产品公布的限制，列出重新导出或选择另一份文件。保留表单中其他已填写内容，用户只需修改与失败直接相关的那一项。此次 413 不值得把整份创建流程恢复成空白。

临时规则已知时，可以显示仍未完成上传、建议稍后再检查。再次尝试要受产品的请求生命周期和文件可用性约束。应用不能因为看到等待字段就自行承诺文件流仍在手中、提交安全或者用户仍同意重发。若产品需要自动重提，应另用自己的业务身份和去重合同判定。

运维记录也可以区分产生状态的组件。例如接入层根据全局配置拒绝，而应用界面错误显示自己的更大限额。诊断要保存哪个入口给了 413、其判断依据及本次反馈给用户的修正办法。不要在没有实际接入层证据时说文件已经送到了保存服务。

有些系统按内容实际计量，有些还会按照接口合同处理编码与解码后的容量。对照输入时应先搞清楚端点指的容量是哪一种。本例的整数只够演示恢复方向。真实回归应从团队公布的限制读取计量条件，并在日志里保留同一个输入在两个试验中是否确实等量。

用户看到建议等待时，可以将它与本次待上传文件关联。若他转而选择更小的文件，界面应重新判断新内容，而不是延用上一份文件的失败结论。若用户离开页面，回来时也应先确认还有没有原文件和当前授权。旧回执能解释上一次拒收，不能替新输入标记完成。

正文还没发完，服务器能结束这次请求吗？

可以。这里改变的是交互时序，不再假设客户端拿到了正常的完整响应。RFC 9110 允许在协议版本支持时终止请求，否则也允许关闭连接。客户端因此有可能看到发送中断。断线本身不能证明本次一定是 413，连接也可能因其他故障断开。

若客户端只观察到传输提早停止，没有收到真实的状态和头字段，应将已知事实记录为传输失败。不要自行向用户显示一个想象中的大小上限，或用未经核对的重发来证明上一次没有生效。若确实收到 413，再按接口和响应的条件判断可否修正后重提。

如果问题是发送正文前怎样利用临时响应，可另看 HTTP 100 Continue 的上传时序。
