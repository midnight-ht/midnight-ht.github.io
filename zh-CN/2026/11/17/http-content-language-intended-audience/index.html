页面有两种语言，Content-Language 为什么可以只写一种？

用英语教程中的法语引文区分表示受众与片段语言，分别核对 Content-Language 和 HTML lang。

正文

核心要点

  • 响应字段说明表示面向的语言受众
  • 片段语言可以与受众标签不同
  • 分别核对响应元数据和页面结构

一份写给英语读者的教程里放了一句法语问候。审查者看到两种语言，准备把 HTTP 响应的 Content-Language 改成 en, fr。先确认这份教程是为谁准备的。英语读者不需要先懂法语也能读完说明。法语是一段被解释的内容，未必让这份表示面向另一类读者。

响应字段交代的是表示受众

RFC 9110 将 Content-Language 定义为表示预期受众使用的自然语言。字段值并不需要覆盖内容中出现的全部语言。这里的表示是一份完整教程，法语引文是其中一段。若教程的讲解、示例说明和导航面向英语读者，en 可以准确表达作者的意图，即使有一句正文不是英语。

把出现的语言逐项塞进字段会改变这个声称。在本例中，额外写 fr 会让接收方理解为这份表示也准备给法语读者。一个只读法语的来访者虽然能看懂引文，却可能无法读完教程的步骤，不能用引文证明该类受众已经受到服务。

片段语言是另一项需要作者留下的信息。在 HTML 里，lang 属性说明该元素的内容和含文本属性所用的主要语言。整份教程可以在根元素上标 en，将引用的法语片段标为 fr。这个属性描述页面内容的语言处理，与 HTTP 字段对表示受众的说明可以同时正确。

区分这两件事之后，就不必用某一层的值替另一层做推断。看到 Content-Language 是 en，不能认定每句引文都应按英语处理。看到片段用了 fr，也不能认定任何法语读者都能使用整份教程。两个事实需要分别读到，才知道编辑设置在哪里不符。

对照同一份教程的头字段和片段标记

设想自有文档端点的响应状态是 200，内容类型是 text/html，Content-Language 是 en。正文使用下面这段独立 HTML。它先用英语解释场景，再展示一句法语问候，最后用英语说明意思。示例只列出一个假想响应与正文，没有发送 HTTP 请求，也没运行浏览器或辅助技术。

<!doctype html>
<html lang="en">
<meta charset="utf-8">
<title>Greeting at the front desk</title>
<h1>Greeting at the front desk</h1>
<p>In a French office, you can start with this greeting:</p>
<blockquote lang="fr">Bonjour, bienvenue.</blockquote>
<p>It means “Hello, welcome.” Use it when a visitor arrives.</p>
</html>

验收这份文档时保留两个独立读数。第一处从已选表示的响应字段读取 en，核对编辑说明是否真的面向英语读者。第二处看 HTML 根元素和引用段，预期分别为 en 和 fr，确认引文保有自己的语言标记。两处出现不同值在这里是正确结果。若要求所有读数相等，反而会丢失说明文档结构的证据。

可以增加一个错误样本，只删除引文上的语言标记。响应头仍描述原来的受众，HTML 片段却失去了单独声明，普通元素将随父元素使用其语言。另一个错误样本保持 HTML 完全不变，只将多种文本语言机械填进响应字段。此时内容标记依旧正确，要修改的是对表示受众的描述。

没有真实浏览器或辅助技术结果时，可把这些当成结构预期。实际产品如果依赖语言切换改变语音，需让支持的组合读到同一段文本，再确认处理是否适合用户。规范中的语言属性足以给实现提供信息，不证明任何特定设备会按预期换声或发音。

从编辑记录取受众，从页面结构取内容语言

制作本地化文档时，可以让发布流程保留两类数据。一类是编辑明确交付给哪个语言受众，另一类是哪些内容片段与所在段落不同。发布端用前者生成表示元数据，页面模板用后者生成元素语言。这样改一处外语人名或增加代码例句，不会无意中改变对整篇受众的承诺。

如果团队用语言检测辅助审阅，可以把它发现的差异作为选段检查线索。例如审阅者看到一整段法语落在英语页面中，可以确认是否需要标记。检测结果只能说明观察到的字符或文字结构。它没有检查这份指南是否给某群读者提供了可独立理解的说明。

同一资源如果另外有完整法语版，就分别检查每个实际响应。英语教程的引文不因法语版发布而变成另一份表示。客户端也不应根据自己发出的偏好头猜响应一定用了某种语言。对于这篇文章的固定样本，所选表示已经确定，不需要用协商过程来解释为何 en 仍然正确。

漏写这个字段也不代表客户端可以补出一个自己猜的语言。RFC 对未指定字段的默认解释是面向所有语言受众，发送方可能没限定特定语言，也可能不知道受众语言。这是协议的解释前提，不能据此证明页面已经翻译成所有语言。如果编辑原本明确把教程交付给英语读者，发布时应从那条已知记录补齐，而不是把默认情况当成翻译证明。

如果同一页确实写给两类读者，能列两种语言吗？

可以。假设发布的是双语入门页，每一步都有完整的英文与法文说明，两种读者都能独立完成操作。此时同一个表示可以用 Content-Language: en, fr 指明两类受众。与主例相比，变的是编辑目标和内容覆盖，不是因为检测器找到了更多几处法语。

即使用了两个受众标签，各段仍可按自己的实际语言标注。验收时让两个语言版本的读者都能找到完整流程，再核对元数据是否和这个目标一致。若法文只有标题和引文，就还没有满足新增条件。

如果排查的是同一 URL 为什么给了不同语言版本，可以另读表示选择与 Vary 怎样参与缓存匹配。
