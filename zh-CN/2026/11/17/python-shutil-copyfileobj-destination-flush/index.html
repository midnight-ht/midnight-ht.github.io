copyfileobj 返回了，为什么另一个读取者还是看不到内容？

用两次实际读取区分 Python 文件复制返回、写缓冲刷新和内容交接。

正文

核心要点

  • 复制返回不保证刷新。
  • 交接前由目标拥有者刷新或关闭。
  • 可见性和耐久性需要分别验证。

Python 的 copyfileobj 返回以后，另一个读取者仍可能看到空文件。复制函数把数据写入目标对象，返回时并不保证该对象已经刷新。需要立刻交给别的读取者时，应在交接前刷新或关闭写入端，再核对实际读取结果。

设想服务先把一份小导出复制到临时文件，随后把路径交给生成预览的模块。复制没有报错，预览却显示没有数据。若调用者仍持有一个缓冲写入对象，小内容可能还没有从它的缓冲区交给底层文件。此时应先问写入者、读取者分别使用哪个对象，以及交接到底发生在复制返回以后，还是刷新以后。贸然重跑复制，可能把相同内容又追加一次，并没有验证下游为什么读不到。

复制结束和交接就绪需要两份证据

标准库文档说明，copyfileobj 将源文件对象的内容传给目标对象，但不会保证目标流已刷新。要在复制结束后读目标，应先调用目标的 flush 或 close。复制函数的返回能说明调用本身已经结束；让另一个文件对象读取时，还需要满足目标对象的写入合同。Python shutil.copyfileobj。

如果模块只把数据写给调用方提供的流，擅自关闭该流也会改变合同。调用者可能还要补一个尾部，或在业务完成后才决定能否对外公布结果。对于仍要继续写入的目标，可以由拥有者明确安排刷新；对于内容已经全部完成的本地文件，可以由拥有者完成关闭，再把路径提供给读取者。测试应覆盖真实交接入口，不能只是发现某段函数内部调用了复制就报告成功。

保持同一个写入对象，另开两个读取者

以下标准库程序已在 Python 3.11.15 的本地临时目录运行。它把三字节复制到具有明确缓冲大小的二进制写入对象。第一次读取发生在复制返回以后、写入端刷新或关闭以前，第二次读取紧跟刷新。每次都重新按路径打开目标，不让读取端继承写入对象的游标。

from io import BytesIO
from pathlib import Path
from shutil import copyfileobj
from tempfile import TemporaryDirectory

with TemporaryDirectory() as directory:
    target = Path(directory) / "demo.bin"
    with target.open("wb", buffering=8192) as writer:
        copyfileobj(BytesIO(b"abc"), writer)
        before = target.read_bytes()
        writer.flush()
        after = target.read_bytes()
        assert (before, after) == (b"", b"abc")
        print(before, after)

这次运行第一次读到空字节串，第二次读到 abc。两个结果各有断言，写入端始终在同一个作用域内。第一次读到空是这个缓冲方式、输入长度和实际环境的观察。文档承诺的是复制函数不会保证刷新，不能据此要求所有目标一律先读到空。比如没有缓冲的实现或更大的写入可能已经对另一个读取者可见。故障测试应复现自己依赖的目标方式，再用第二次读取验证完整字节。

也不要为了方便就用写入对象的位置代替读取证据。当前位置达到三，只说明写入对象在自己的接口里移动到了那里。业务真正要交付的是另一个消费者读到三字节。验收记录应保留两次读取确实打开的目标路径、内容与执行顺序。若预览进程实际使用了另一份旧文件，刷新正确的对象也不会修好路径错误。这里的实验没有跨进程，也没有检查临时文件暴露给其他账户的权限。

把需要的保证写在读取方入口

如果后续读取只要求对象中的字节，可以在明确的刷新边界后直接核对。若应用要求读者只看到完整版本，就还需要定义文件何时对读者可见。仅仅先刷新一部分内容，无法保证读者不会抢先读到半份导出。可以把失败路径设计成写完以前不向下游交接该路径，再用一条提前失败和一条正常完成的样本分别确认。主程序只展示刷新，没有实现业务交接、进程崩溃后的恢复或持久化。

还可以留一个不同原因的空文件对照。让复制使用空的源流，再刷新目标，预期读者仍得到空字节。这样可以把“源本来没有数据”和“源有内容但还没有刷新”区别开来。在真实预览测试里，给源输入和目标读取分别记录字节数。如果业务允许合法空导出，再用独立的状态字段表明这次生成确实完成。单靠目标为空无法替两条路径选择处理结果。这组空源对照没有运行。站内的 临时文件转换时点 关注描述符何时触发另一种文件形式，本篇关注什么时点能读到复制内容。

如果消费者需要确认文件经历系统掉电以后仍可恢复，应采用另行明确的耐久策略和测试。读者在同一个系统中看到内容，只提供可见性证据。不要把刷新验证的结论扩到文件名已经持久化、关机之后的数据仍存在或另一台机器立刻读到内容。这里故意只检查一个本地进程内的两次独立打开。

在服务接入处还可以让复制之后的刷新返回错误，要求调用者保留它并阻止交接。只有复制成功的记录不应覆盖这个较晚的失败。该失败对照未执行。

源已经读过一部分，复制会重新从头开始吗？

文档说明复制从源对象当前位置开始。可以新建包含 abc 的源，先读取一个字节，再把剩余内容复制到新目标；交接前刷新，预期读到 bc。若业务要完整复制，应让交接方明确把支持定位的源移回开头，或交付一份还未读取过的流。这个游标变体未运行。主样本的源从开头开始，不能给已经被预览读取过的源自动补回前缀。
