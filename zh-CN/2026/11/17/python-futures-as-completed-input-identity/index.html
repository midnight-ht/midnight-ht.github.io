用 as_completed 取结果，为什么不能和输入按位置 zip？

用实际线程池事件控制核对完成顺序、输入身份及最终报告的关系。

正文

核心要点

  • 完成顺序不保证匹配输入位置。
  • 提交时保存任务身份。
  • 用独立期望验收最终排序和结果归属。

Python 的 as_completed 按可取得的完成状态返回 Future，结果不能直接和原输入逐项配对。提交时保存每个 Future 对应的任务身份，才能在结果先后变化时仍把记录归给正确的输入。

假设一个库存报表同时查询门店甲和乙，准备先显示已完成的查询。工程师拿原来的门店列表与 as_completed 的产出做配对。乙先响应后，界面却把乙的库存挂在甲下面。两个请求都成功，行数与总数也可能正确。这类错误需要追查结果是给了哪一家店，而不是继续增加对完成数的断言。

完成顺序不能承担输入身份

Python 文档说明，as_completed 从给定的 Future 中产出已经完成或取消的对象。调用前已经完成的对象会先被产出，同一个 Future 即使重复传入也只出现一次。这个接口适合尽快观察终态。它没有约定这些对象与输入排列在同一个位置，也不应从同时准备好的多个结果中推断出可稳定重放的总顺序。Python concurrent.futures。

异步完成的批次通常需要两种视图。进度视图可以在每项终止时更新相应门店。最后的报告则可按业务要求使用输入顺序或其他排序。将门店编号与 Future 的配对放在提交位置，完成后写回按编号索引的结果。对于一个输入会生成多项工作的情况，先决定标识应该代表门店，还是门店与工作类型的组合。随意用重复名称覆盖字典，也会丢掉先前结果。

不靠 sleep，让后提交的记录先完成

以下完整程序已在 Python 3.11.15 本地执行。线程池有两个工作位置。较早提交的任务等待事件释放，后来提交的任务直接返回。主线程先取一个完成对象并核对它归属乙，再放行第一项。事件在 finally 中释放，以免第一次观察失败后执行器退出还在等待被阻塞的工作者。

from concurrent.futures import ThreadPoolExecutor, as_completed
from threading import Event

release = Event()

def slow():
    release.wait()
    return "slow-value"

with ThreadPoolExecutor(max_workers=2) as pool:
    source = {pool.submit(slow): "A", pool.submit(lambda: "fast-value"): "B"}
    observed = {}
    try:
        finished = as_completed(source)
        first = next(finished)
        assert source[first] == "B"
        observed[source[first]] = first.result()
    finally:
        release.set()
    for future in finished:
        observed[source[future]] = future.result()

assert list(observed) == ["B", "A"]
assert [observed[key] for key in ("A", "B")] == ["slow-value", "fast-value"]
print(list(observed.items()))

实际先得到乙的 fast-value，再得到甲的 slow-value。最后按甲、乙次序读回结果，可以得到 slow-value、fast-value。程序分别断言第一次完成的身份、完成视图顺序和重新组织后的内容。这里的先后来自显式门控，只针对这一份样本。它不能证明真实任务的耗时总是相同，也没有通过调整线程睡眠来赌哪一个更快。

若测试只检查两个返回值都存在，错误配对仍可能通过。可以给两家店定义不同的值，再把按输入顺序直接拼接完成结果作为错误控制，验证甲被赋了乙的值时会报告失败。让观察直接包含门店与库存的配对，而不是分别统计门店数和库存数。这个应用对照未运行。更改并发度时也要避免复用不适合的门控，例如只开一个工作位置就会让该样本的第二项无法启动。

把终点状态留给真正的调用者

完成对象可以有成功、失败或取消等结果。拿到它以后仍要保留任务身份，并按接口约定读取结果或记录失败。若报告允许某些店失败，失败项也应继续占有自己的标识，而不是先删掉它再按原列表补位置。可以设计一个后提交成功、先提交失败的样本，分别验证在进度视图显示乙的成功时不会改写甲，最终报告里的失败仍对应甲。这项异常变体没有执行。

使用全量报告时，还需确认每个输入都得到一个终态。若有任务未提交，应让它进入独立状态；如果一个任务提交两次，就要明说是否接受两份结果。站内的 Promise.all 失败和取消 讨论一个结果失败时其他工作是否继续，本例处理已经得到的完成结果该归谁。身份映射不能替程序提供取消、补偿或副作用回滚，真实接口还需要各自的验收。

对只希望看到最新进度的界面，可以把每条事件的任务标识、状态和实际序号一起保存。重新加载最终报告时按稳定规则排序，不把某次用户碰到的完成顺序当成下一次应该复现的输入。若使用任务名称作为显示文本，也不要用它替代唯一标识。两项工作可以有相同名字，却各自跨不同批次。这些存储和页面行为没有运行，主程序只观察了同一进程里两个有意门控的工作者。

如果程序有跨批次进度更新器，还可以同时创建两个报表。两边各有一个名为甲的任务，但库存和内部编号不同。验收让两个批次交错终止，再按批次与编号读取结果，防止共享进度表把后一份甲覆盖到前一份报告。补交取消控制时，应在一个独立任务上观察取消状态，不要因为读不到结果就跳过它的键。页面若允许重试，也应把旧尝试与新尝试分别记录，然后依合同决定哪一项进入最终视图。此处没有运行这些额外流程。

同一个 Future 在输入里放两次，会产出两条吗？

文档说明重复的 Future 只会被产出一次。若两个报告槽位共享同一个真实工作，应保存从完成对象到多个槽位的对应关系。可以把同一对象放入输入两次，单独观察只迭代到一次，然后令最终报告两个槽位都引用这个结果。前者验证迭代规则，后者验证应用的分发。这个追问未执行，主样本只含两个不同的 Future。
