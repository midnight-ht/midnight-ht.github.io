缩小 pytest 的 conftest 范围后，为什么 fixture 找不到了？

对同一测试文件切换 pytest 的 conftest 边界，用收集清单与 fixture 准备阶段定位缺少的定义。

正文

核心要点

  • 边界目录仍能提供本地 conftest。
  • 固定测试路径再切换边界。
  • 将收集成功和 fixture 准备成功分别记录。

测试函数还在收集列表里，原来能用的 fixture 却在准备阶段报找不到。若刚把 pytest 的 --confcutdir 收窄到测试目录，先看 fixture 是在边界目录定义的，还是来自这个目录上方的祖先 conftest.py。两处定义可以在同一次运行里得到不同结果。

把路径和测试名照原样留在命令里，只切换边界，就能把这个问题和改了收集入口的故障分开。以下夹具把两份同类定义放在不同位置，给它们不同名字和返回值。这样即使其中一个通过，也知道它到底读的是本地值还是项目根的值。

两处定义，同一批用例

建一个空目录，保留下面的文件关系。根目录的配置保持不变，让对照运行有共同的起点。运行前确保当前目录就是实验根，两个命令都显式传入同一个测试文件。

pytest.ini
conftest.py
tests/
  conftest.py
  test_tokens.py

根目录的 pytest.ini 只有一行 [pytest]。根目录的 conftest.py 提供父级标记。

import pytest


@pytest.fixture
def parent_token():
    return "parent"

tests/conftest.py 保留本级标记。两份 fixture 各自只有一个返回值，没有文件、环境变量或外部插件依赖，出错时先观察能否找到 fixture。

import pytest


@pytest.fixture
def local_token():
    return "local"

最后写下 tests/test_tokens.py。第一个用例直接验证边界目录内的定义，第二个用例明确要求父目录提供标记。这可以避免一个断言里混用两个 fixture，导致其中一个找不到时完全看不见另一个是不是还在。

def test_local(local_token):
    assert local_token == "local"


def test_parent(parent_token):
    assert parent_token == "parent"

两次都在同一个已经安装 pytest 的隔离环境执行。关闭自动加载外部插件和缓存插件，保存各次退出值与输出。若将第一条命令和第二条串起来，不要把第二条的非零直接当成夹具跑坏了。它是这一趟应该观察到的结果。

export PYTEST_DISABLE_PLUGIN_AUTOLOAD=1
python -m pytest -v -p no:cacheprovider --confcutdir=. tests/test_tokens.py
python -m pytest -v -p no:cacheprovider --confcutdir=tests tests/test_tokens.py

本地 Python 3.11.15 与 pytest 9.0.2 的回执显示，第一趟收集两项，两项通过，退出零。第二趟也收集两项。本地标记对应的用例通过，父级标记对应的用例在 setup 阶段报 fixture 'parent_token' not found，整趟退出一。这条错误不等同于断言收到错误的返回值，第二个用例甚至没能拿到参数进入函数体。根目录与测试文件都保持不变，两个输出的差别集中在这份父级定义上。

选边界时先找定义在哪

在 pytest 这里，边界目录本身仍可以提供 conftest。第二趟排除了 tests 上方的实验根文件，留住了 tests 自己的定义。同一次运行里，本地用例通过和父级用例 setup 出错正是为了证明这两件事可以同时发生。如果只观察整个命令的退出值，就看不到收集结果不变；如果只观察成功的本地用例，又很容易以为根目录的共享 fixture 也加载了。

一个合理的收窄动机是把项目根的测试配置从某个独立测试入口排除。但假设维护者把公共登录样本放在根目录，每个子项目都在测试签名中使用它，收紧边界也会拿掉该共享输入。此时先确认这份公共输入理应由谁提供。如果子项目就是要独立运行，把它需要的 fixture 放到它自身可加载的位置，并用第二趟命令重新验收。若依赖根目录是项目约定，就用能包含该定义的边界并保存实际命令。单纯把执行入口移到另一个目录会引入更多变量，包含相对路径和测试选择，修复后别人也更难还原原因。

在自己项目里先从出错用例拿一段最小签名，看它要求的参数在哪里定义，确认没有另一个同名 fixture 然后重做双入口实验。当前目录、测试文件参数和同一套依赖都固定住。返回值可以像这里一样明确区分定义位置。一旦收窄之后仍能获得同名参数，却得到不同值，就有必要重新查实际提供者；这种现象与本文实验里的 fixture 完全缺失不同，本文没有复现同名覆盖。不要只把错误消失当成验收条件，还要断言现在读到的是该入口期望的数据。

接入 CI 时可从现有故障报告截取三个事实，项目与配置位置、收集到的用例清单和出错阶段。把旧边界下的结果存为参照，再跑候选边界。若用例数量先发生变化，先确认比较的仍是同一批用例，别急着把通过率变高归给 fixture 调整。比如有一个用例此前一直要求父定义，修改 CI 参数时又顺手把它移出了测试列表，那么没有 setup 错误只说明它没运行。对照实验中的第二项用例就是为抓住这类误修而单独留下的。保留退出值也能让接手的人区分部分用例通过和整趟通过。

交接一份最小复现时还可以附上环境表。假设第一次用的是项目固定的解释器，第二次改用了机器上另外一个 pytest。即便测试列表保持相同，也无法从这组输出单独判断是边界变化，还是外部插件提供了参数。先复用同一个解释器入口，记住 pytest 版本和自动加载设置，再把看到的测试节点及错误原文附进记录。对于确实依赖插件的真实项目，关闭插件只能作为定位步骤。恢复约定的插件配置之后，要在最终入口重新确认共享 fixture 的来源。

同级目录也会被这条路径挡在外面吗？

在这里固定的 pytest 9.0.2 实现中，边界针对它上方的祖先，并非整个会话的目录白名单。另建一个与 tests 同级的 sibling 目录，在其 conftest 定义 sibling_token，用唯一用例确认返回值是 sibling。仍用 --confcutdir=tests，这次显式传入 sibling，本地另一次运行得到一项通过。它改变的是明确传给 pytest 的入口，和主实验沿 tests 祖先查找的条件不同。需要 CI 只运行指定目录中的用例时，也要检查实际传入的测试路径。
