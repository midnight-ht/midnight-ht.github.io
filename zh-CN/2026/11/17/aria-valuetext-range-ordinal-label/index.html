画质滑块停在 2，怎样让用户知道这是「标准」？

用三档原生滑块区分序号与档位含义，核对当前数值、可见名称和 aria-valuetext 是否同步。

正文

核心要点

  • 档位序号不足以说明预设含义
  • 可见名称和可访问值应取同一映射
  • 先检查三组状态，再实测辅助技术反馈

预览画质有草稿、标准和高清三个档位。滑块初始停在中间，数值是二。对实现来说，二已经足够找到保存的设置。对用户来说，真正需要认出的值是「标准」。如果滑块只能提供数字，使用界面的人还得自己记住三个数字分别意味着什么。

数字负责位置，文字说出档位

原生 range 输入适合表示有顺序的选择。本例在三档之间每次移动一步。数字一、二、三作为组件和值存储之间的协议，让脚本知道选中的位置。设计稿上的档位名称则应随着当前位置改变。名称用来解释每一步选择如何影响随后生成的预览。

WAI-ARIA 1.2 用 aria-valuetext 表示数值的可读替代。若单独显示或呈现数字无法表达当前实际值的含义，可以提供对应文字。这里的二只表示居中的序号，并不是画质的单位。如果范围表示人本来就能理解的数值，例如字号本身，是否另加文字就要由单位和界面文本决定。

这个例子仍使用原生可聚焦控件，保留它的范围、步长及键盘操作。我们补的是当前值的读法，没有另造一只名为「标准」的滑块。控件的标签保持「预览画质」，当前值才在三个档位之间变动。把档位名称写成新的控件标签，会让人难以确定还是不是同一个设置。

应用可以从一份数组生成当前的可见档位和可访问值。这样切换到高清时，页面不用分别查询两个来源。一个常见错误是界面文字来自新的编辑值，可访问属性还留在组件最初渲染的中间档。避免重复保存档位含义，有助于在代码里让两个出口同步更新。

用三档值和文字做独立读数

下面的 HTML 夹具只有一个滑块。起始数值为二，并显示 Standard。键盘更改数值时，input 监听器从三条固定名称中取出一项，并写回可见文字和 aria-valuetext。代码没有提交设置或生成预览文件。

<!doctype html>
<meta charset="utf-8">
<title>Preview quality</title>
<label for="quality">Preview quality</label>
<input id="quality" type="range" min="1" max="3" step="1"
       value="2" aria-valuetext="Standard">
<p id="preset">Selected preset: Standard</p>
<script>
const byId = document.getElementById.bind(document);
const quality = byId('quality');
const preset = byId('preset');
const labels = ['Draft', 'Standard', 'High'];

function showPreset() {
  const label = labels[quality.valueAsNumber - 1];
  preset.textContent = 'Selected preset: ' + label;
  quality.setAttribute('aria-valuetext', label);
}
quality.addEventListener('input', showPreset);
</script>

第一次读数应看到值二和 Standard。把焦点移到滑块上，按向右方向键到最后一档，预期值三和 High。随后按两次向左方向键，预期值一和 Draft。当前环境不同键位表现可能有差异，验收时应先确认实际数值确实到达所需档，再核对那一档的文字。

每次动作都可检查三处：原生 value、可见段落与可访问值属性。只看滑块移动，无法发现旧文字没改。只看可见段落，也无法发现属性仍滞留在上次的 Standard。将数值和两份文字放在同一行，可以直接看出是哪一个出口有延迟。

以上是按原生控件、脚本和规范推导的期望，本文未在浏览器或辅助技术中运行示例。实际播放时可能还会呈现控件名称、角色或位置等信息，不能把 aria-valuetext 的文本当成跨设备逐字输出。对产品支持的环境，要记录用户能否知道这是什么设置、当前在哪一档，以及按键后反馈是否跟上。

在改档时避免另一套名称

如果界面还用气泡显示预设值，三档名称也应跟着同一个映射变化。假设第二档视觉上写「标准」，气泡仍写「普通」，团队需要先决定哪一个是产品词汇。测试只看程序能生成非空文本，会放过这种不一致。最好以三个明确的对应关系做断言，而不是在失败时才猜两个词有没有相同含义。

换语言也是同样的考验。按已有的数字保存设置，显示时根据当前语言找到该档位的文案。不要把翻译后的文字反向解析成数值。如果需要比较切换前后的业务选择，应该用保存的数字或稳定名称。界面读数只用来核对同一档怎样呈现。

档位如果不稳定地增加或重排，还要考虑旧存档的含义。过去的二代表 Standard，增加一个新档后若二指向别处，改变可访问属性也无法修复保存语义。案例假设三个档位固定。项目需给存档一个稳定的业务标识，再决定按钮或滑块怎样表达新的序列。

在真实设置页还可以验收刚进入页面时的值。对已经保存高清的用户，首次渲染就应生成第三档和高清文字。若先写默认的第二档再等待键盘操作补齐，读者会在交互前遇到一组旧名称。将初始状态用和用户更新相同的映射生成，能避免首屏和后续逻辑各有一份预设列表。

如果几个选择没有可理解的顺序，不必为了增加文案而保留滑块。比如三个预览主题是黑白、暖色和原色，下一步未必表示更高程度。此时可以用具名选择让人直接选择主题，不要让数字位置假装定义产品顺序。这个判断针对控件设计，并非属性能单独修复的问题。

读入草稿时，脚本写入第三档会自动同步文字吗？

不会仅靠脚本给 value 赋值就自动运行这里的监听函数。主例依赖用户操作触发 input。把草稿恢复逻辑改成给滑块赋值为三之后，应显式调用同一个 showPreset 函数，再分别验收数值、可见 High 和 aria-valuetext。若只有数值改变，键盘还没操作就会读到上一档的标签。

可以为草稿恢复写一条不键入任何内容的用例。初始是二和 Standard，恢复值三后立刻检查三个出口。不要在读数前再按键，否则用户事件会提前修正残留状态，测试就捕捉不到草稿入口自身的漏更新。
