本地化名单怎样只给名字加链接？

用两种地区设置核对名单部件，让名字各自可链接，同时保留格式器生成的连接词与标点。

正文

核心要点

  • 只给 element 部件创建链接
  • 保留 literal 原来的文本
  • 拼接分段应与同环境的完整格式化一致

项目成员名单已经按当前语言显示，可是一点最后两个名字之间的连接词，页面却跳进了其中一个人的资料。名单整体看起来没有错，链接的边界画错了。原始输入是三个人，分隔符是格式器后来加进去的。渲染时可以先让格式器给每一段注明用途，再决定哪个节点需要链接。

让格式器返回边界，再添加节点

名单组件知道三条要显示的名称 Ada、Lin 和 Mia，也知道它们的个人资料入口。它不需要先决定最后两个名字之间放什么文字。用 Intl.ListFormat 实例调用 format 可以得到整条格式化字符串，交给 formatToParts 则可以得到带类型的分段。

类型为 element 的分段来自输入名单。类型为 literal 的分段来自格式器，例如它为这个地区选择的逗号、空格或连接词。分段的 value 都可用于显示。差别在于一段是否对应用户可以打开的独立记录。渲染模板只给 element 加链接，并让 literal 保持原样。

不要因为某一份输出只有一个英文连接词，就在组件中硬写该词再拆分。地区一换，标点、空格或最后连接处的写法也可能改变。哪怕输入只有一个已知语言，成员的名字也可能含有分隔符字符。猜分隔符与读取格式器明确提供的部件，是两种风险不同的工作。

保留 literal 也意味着不能在渲染层把每个部件先做去首尾空白再拼回。某些空格本身属于语言的分隔方式。把它们清掉，有可能让文字贴在前一个链接上。相邻节点如何在浏览器里呈现仍需检查，但应用不应在格式之后自行替换语言内容。

两种地区设置，固定同一批名字

下面的 Node 脚本使用三个普通字符串和两种地区设置。对每一种设置，先获取全部分段，再过滤出 element 并对照输入。第二条检查将所有 value 按顺序拼回，和同一格式器的完整输出对照。应该同时保留这两条检查，第一条关心应用身份，第二条关心人读到的文字。

import {deepEqual, equal} from 'node:assert/strict';

const names = ['Ada', 'Lin', 'Mia'];
for (const locale of ['en', 'zh-CN']) {
  const list = new Intl.ListFormat(locale, {type: 'conjunction'});
  const {format, formatToParts} = list;
  const parts = formatToParts.call(list, names);
  const values = parts.map(({value}) => value);
  const linked = parts.filter(({type}) => type === 'element');
  deepEqual(linked.map(({value}) => value), names);
  equal(values.join(''), format.call(list, names));
  console.log(locale, JSON.stringify(parts));
}

本机的两组断言通过，并记录了实际分段。两次运行的 element 序列都是 Ada、Lin、Mia，分隔内容可以不同。这里不把某种逗号或某个连接词写成所有版本的固定输出。规则的语言数据来自运行环境，如果项目要支持不同平台，应各自记录其实际读数。

测试只检查分段与拼接，没有创建 DOM，更没有点击资料链接。将例子移进组件后，再分别验收链接数量、各链接显示名、目标与没有进入链接的分隔文本。假如测试只读取整行文字，首段描述的故障不会改变文字，便会继续通过。检查节点边界才能判断到底谁可被点击。

用输入身份处理操作，用分段内容呈现文本

适合把原始名单建成按顺序排列的记录，每条保存稳定编号和显示名。传给格式器的是显示名数组。遇到下一个 element 分段，就消费原始顺序里的相应记录，给链接补上那条记录的目标。遇到 literal 时只写文本，不消耗下一条人名。这样渲染逻辑不会把翻译内容当成员身份。

如果搜索或筛选会重新排序，应先生成这次要显示的名单，再把同一份顺序交给格式器和渲染层。常见的故障是先格式化了当前可见记录，构造链接时却取另一个尚未筛选的数组。两个数组第一个位置可能恰好同名，看起来没有问题，点击后却打开了另一条记录。

也可以为三种输出写独立用例。一项时只需要一个人名链接；两项时仍需保留中间分隔；三项时需要确认最后一个链接没有包含连接词。这些用例检验渲染层是否按分段行动，不要求团队把不同语言的具体标点都写进同一份测试。

如果组件最终又被导出为纯文本，例如复制到剪贴板，可以用同一个地区设置的完整格式化结果作为预期。显示态的节点边界和纯文本的字符是两份不同检查。前者回答哪里能点击，后者回答复制后是否保留名单。把这两个观察记在同一次验收里，可以捕捉看起来相同但操作不等价的回归。

回归还应记录格式器最终采用的地区，而不只保存构造时传入的请求值。若平台退回了另一种语言，两个配置可能碰巧都输出相同类型的分隔符。顺序关联应建立在本项目实际支持的地区数据与回归结果上；规范建议模板中第一个占位出现在第二个之前，未把这种建议写成所有实现的强制顺序。扩展地区列表时，先拿各不相同的三条显示名重新核对顺序。

两个人显示名相同，按文字找链接还能用吗？

不能靠显示名判断。把输入改成两条同名记录，例如两个 Lin 的编号分别是 L7 和 L9。格式器仍然交回两个相同文字的 element。若用名字作为对象键，两个链接可能都选到同一条记录。按 element 出现的位置沿着本次输入顺序消费，第一条仍指 L7，第二条仍指 L9。

这个新条件可以用两个相同标签和两个不同的预期目标验收。不要仅检查有两个链接或它们的文字相等。打开第一个与第二个应到不同记录，复制出来的名字则允许相同。是否再显示能帮助人区分他们的信息，要由界面决定，格式器不会替应用制造身份。

若你的问题是时间格式配置怎样改变分段，可另看 Intl.DateTimeFormat 时制优先级。
