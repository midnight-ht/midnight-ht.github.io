Python 的装饰器原样转发，为什么检查工具仍只看见包装器？

用真实调用区分 Python 装饰器的执行结果、默认签名展开和包装器自身签名。

正文

核心要点

  • wraps 建立直接包装关系。
  • 默认检查可沿包装关系读取签名。
  • 行为与工具看到的合同需要分别验收。

Python 的装饰器可以完整转发调用，但检查工具仍可能只看见包装函数。functools.wraps 会在包装函数上关联原函数，inspect.signature 默认沿这条关系检查。要了解包装器自己声明了什么，也可以明确关闭这一层展开。

设想一个报价入口接收数量和必须按名称传入的税额。开发加了一层审计包装，用可变参数接收并转发原样输入。应用继续算出同一个金额，生成接口说明的工具却只显示任意位置参数与关键字参数。第一次验收只证明调用仍可用，第二次观察才说明它是否仍可被工具理解。故障定位应分别检查被调用的对象和工具采用的接口描述。

包装链怎样被检查工具看到

标准库的 wraps 是 update_wrapper 的便利入口。它可以按配置整理包装函数的元数据，并建立 wrapped 属性，指向这层包装直接接收的函数。给包装器添加这个属性，并不会替它生成一份新的函数实现。原函数仍通过包装器写下的调用表达式执行。真正的转发、参数校验或额外逻辑都应由代码负责。Python functools 包装器文档。

默认签名检查会尝试检查被包装对象。用 follow_wrapped=False 时，可以看到外层包装函数自己的签名。把两份结果都保存，有助于定位是工具看错对象，还是包装器根本没有提供可跟踪的链。如果应用中的工具有独立规则，例如采用明确提供的接口定义，不能假定它就一定使用标准库的默认展开。下面只调用 inspect，不运行框架。Python inspect。

在一次运行里对照调用与签名

完整程序已在 Python 3.11.15 本地运行。它让两个包装函数转发同一个报价函数。两条路线唯一关键区别是是否显式应用 wraps。程序不仅比较正常调用返回，还分别检查普通包装签名、带包装链时默认展示的签名和禁用展开后的结构。

from inspect import signature
from functools import wraps

def price(qty, *, tax=0):
    return qty + tax

def decorate(fn, advertise):
    def wrapper(*args, **kwargs):
        return fn(*args, **kwargs)
    return wraps(fn)(wrapper) if advertise else wrapper

plain = decorate(price, False)
wrapped = decorate(price, True)
def render(fn, follow=True):
    return str(signature(fn, follow_wrapped=follow))

shown, actual = render(wrapped), render(wrapped, False)
assert shown == "(qty, *, tax=0)"
assert actual == "(*args, **kwargs)"
assert render(plain) == actual
assert plain(4, tax=2) == wrapped(4, tax=2) == 6
assert wrapped.__wrapped__ is price
print(shown, actual)

实际结果是默认检查得到只允许关键字传入的 tax，关闭展开则看到通用的位置和关键字收集参数。未建立包装链的函数，默认检查也是后者。与此同时，给两条路线传入数量四和税额二，都得到六。程序还检查 wrapped 确实引用原函数，而不是仅显示一个相同名字。对这些测试对象而言，调用结果和展示合同分别成立。它没有证明自动生成的文档正确，也没验证框架如何给用户提示参数。

应用测试若单靠可调用对象的名字，也容易遗漏这一层。名字保留了不等于签名一致；签名显示了也不等于内部行为和以前相同。可以再增加一条位置参数传税额的反例，要求业务函数仍拒绝它。若开发改写包装器，自己从位置中抽出税额并转换为关键字，内层依然能算出六，但公开合同已改变。该错误调用变体未运行。

只有透明包装才应该无条件沿用原解释

追踪、计时或日志装饰器通常希望对原入口透明。给这些入口建立可检查的链，可以让调用者看到原函数要求。若包装器引入新参数、移除原参数或固定某个值，真实可用的入口就可能和原函数不同。应先定义新的调用合同，再选择要交给检查工具的描述。不能只因为复制过元数据就宣称两个入口完全等价。

例如新的报价包装器要求调用方带一个渠道字段，再把它转换为税额政策。验收可以准备一条带有合法渠道的调用、一条缺渠道的调用，以及一条想直接传税额的旧调用，并对每项写下明确输出。然后核对实际用于生成文档的入口是否忠实显示新合同。这个集成控制没有运行，主例只保留原样转发。站内的 Mock introspection 示例 讨论另一个工具读取目标时产生的影响，本篇只关心包装层如何暴露关联。

迁移多个入口时，也要保存消费者看到的是哪一层。如果一个团队检查公开包装器，另一个团队绕过它直接导入内部函数，两份预期可能都通过却测试不同 API。应把实际入口与包装层信息记录下来，避免用内部函数的签名替代公开接口已经验证的结论。本例不扫描框架注册过程。

还可以从接口生成工具的输入反向核对。先检查注册进去的对象确实是带审计的包装器，再验证工具产出的参数包含数量和只能按名传入的税额。然后用另一条直接运行入口确认审计逻辑仍被触发。单独查看准确的文档，不能证明真实入口使用了带审计的包装层；如果误把原函数直接注册给框架，签名仍然正确。两个用例应该同时保留。给非法税额位置的调用，也要在真实入口验收，不要仅从 inspect 的文本猜测它会得到哪类用户错误。这些工具集成观察尚未执行。

包了两层以后，wrapped 会直接跳回最里面吗？

每一层建立的是到自己直接包装对象的引用。如果把本例的 wrapped 再包装一次，外层的 wrapped 预期等于 wrapped；于是沿链下一步才到 price。需要走完整链时，可以用 inspect.unwrap，并核对结果对象的身份。反过来，如果某个中间层没有留下这条关系，完整展开不会凭函数名猜出更深的对象。该两层控制未运行；归档代码只验证一层，标题与主例均以一层可见关系为中心。
