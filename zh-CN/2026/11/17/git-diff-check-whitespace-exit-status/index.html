Git diff --check 通过，为什么还有改动没提交？

用一个三状态仓库区分 Git 的补丁规则检查与差异判断，并为发布门禁固定比较范围。

正文

核心要点

  • 合法改动可以通过空白检查。
  • 给同一范围各保留一次检查和差异结果。
  • 暂存与未暂存更新分开核对。

一条改过的配置仍然可以通过 git diff --check。这道检查寻找比较结果中新引入的空白错误和冲突标记。想知道还有没有差异，要另外问 Git 一次，并让两条命令比较同一范围。

发布脚本容易在这里丢掉一个问题。它执行一条名字里带有 diff 的命令，绿色退出值随后被记成了“工作区干净”。只要有人改了一个值并保留正确格式，检查照样绿色。脚本的输入已经变了，记录却没有反映出来。拿下面的三个工作区状态走一遍，就能看出哪个判据遗漏了这一行。

固定比较的两端

用一个已经提交过的临时仓库，提交里的 settings 只有一行。实验只改工作区的已跟踪文件，后两步都不暂存。下面两条比较默认读取工作区与索引之间的差异。第一条根据空白规则和冲突标记作判断。第二条安静地报告比较结果的退出值，有差异时为一，没有时为零。Git 手册明确说明 --check 和 --exit-code 不兼容，因此这里保留两次调用，也保留两个变量。空白配置先设定成确定的值，避免操作者的 Git 配置影响回执。

set -eu
work=$(mktemp -d)
trap 'rm -r "$work"' EXIT
cd "$work"
git init -q
git config user.name Fixture
git config user.email fixture@example.invalid
git config commit.gpgsign false
git config core.whitespace blank-at-eol,space-before-tab,blank-at-eof
printf 'value=base\n' > settings
git add settings
git commit -qm base

probe() {
  check=0
  changed=0
  git diff --check || check=$?
  git diff --quiet --exit-code || changed=$?
  printf 'check=%s diff=%s\n' "$check" "$changed"
  test "$check" -eq "$1"
  test "$changed" -eq "$2"
}
git --version
probe 0 0
printf 'value=next\n' > settings
probe 0 1
printf 'value=next \n' > settings
probe 2 1

这份脚本在 Apple Git 2.50.1 的临时仓库实际执行。三次分别观察到 0/0、0/1 和 2/1，第三次还输出了文件和行号。脚本里的二是这次运行要核对的回执。移到其他 Git 版本写门禁时，空白与冲突检查的公开契约是发现问题会返回非零，不需要把二当通用约定。这里把退出值先收到变量里，是为了让预期的非零也能成为证据，然后再由独立的断言决定实验有没有偏离。

第二步最适合拿来验证现有门禁。内容已经从 base 改成 next，读到文件的人可以独立确认。由于行尾没有多余空格，第一条没有发现问题。第三步只在同一行加了一个空格，之前已经观察到的 diff 结果依然为一，开始变化的是检查结果。如果保存下来的记录只写“发现改动”，就分不出第二步和第三步；如果只写“检查通过”，则分不出第一步和第二步。让两项各自说清楚，维护者看到报告就能判断是该核对实际内容，还是先移除改动行留下的错误。

在门禁里给范围起清楚的名字

上面的实验只回答未暂存的已跟踪差异。准备提交时，把两条都改为 git diff --cached ...，此时索引是待提交内容，比较对象换成了索引和指定提交，默认是 HEAD。遇到一次提交既有暂存也有未暂存的更新，可以按交付规则分别检查两个范围，在报告里写“索引里的补丁”和“工作区相对索引”。例如实验第二步执行暂存之后，普通比较会安静下来，索引比较依然会显示 base 改成 next。这个推演是为了说明范围选择，三状态回执没有执行这一步。

比较发布分支时也先把两个端点固定下来。举例说，发布任务拿到上一个构建使用的提交和本次输入提交，就用这两个提交复核更新。在交接时连同退出值附上端点和检查命令。另一个人用了默认工作区命令，就算两个回执都准确，他回答的也可能是另一个问题。同样，未跟踪的文件不在上面两条默认差异里。如果交付要求包括本地新生成的配置或其他未跟踪文件，先明确哪些目录在范围内，再单独用状态检查把这部分列出来。把“本次发布输入里存在差异”和“当前机器没有未跟踪文件”作为不同声明，才知道哪一份证据发生了失效。

有些流水线允许补丁有普通业务变化，只拦截空白问题和遗留标记。那就把检查结果作为阻断项，把差异存在作为观察项。另一些任务要求构建前没有工作区变化，就让差异状态参与阻断。脚本执行错误也应保留诊断，尤其别把无法读取对象一类异常顺手记成普通差异。接手一个模糊的红灯时，先找同一输入上的两次退出值和标准错误，再决定是清理补丁、核对端点，还是修复 Git 调用本身。

一次典型的误判发生在构建只打包暂存内容的时候。甲检查未暂存差异，乙从索引生成制品，最后有人把甲的绿色回执挂到了乙的制品上。即便两个任务都正确退出，甲也没有查过那份制品采用的补丁。给这类任务定义一个简单的验收记录，令制品任务先记下基准提交与输入来源，再把两次检查的参数和结果和它们放在一起。看到两个范围不一致，应请求重新检查同一输入，不能用一个绿色覆盖另一个范围未检查的问题。可以先用第二步的内容变动模拟这起错配，暂存后再保存两组结果。能把普通比较为零和索引比较为一分别记下，说明报告能表达这个错误路径；制品真正包含哪一行，仍要在打包结果里独立读取。这一验收扩展是后续可执行的检查建议。

机器上的空白规则不同，也会改变检查结果吗？

会。如果同一段补丁只引入第三步那样的行尾空格，局部执行 git -c core.whitespace=-blank-at-eol diff --check 会关闭这类判定。它不会删除文件里的空格，也不会关闭冲突标记的检查。这个覆盖用来说明配置如何影响判断，未进入上面的三次运行。团队两台机器检查同一个补丁时，可以先核对实际生效的规则，再决定是否把约定写进门禁调用。保留规则和比较端点，日后才有可能还原当时为什么通过。
