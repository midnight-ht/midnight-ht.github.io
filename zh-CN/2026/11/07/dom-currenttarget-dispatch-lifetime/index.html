DOM分发结束后，保存事件的currentTarget为什么是null？

解释DOM分发清理中的currentTarget归null，用明确延后任务区分事件状态、节点引用和记录归属。

正文

核心要点

  • 分发结束会清除currentTarget。
  • 同步保存引用不等于冻结节点内容。
  • 写回前仍需核对连接与任务身份。

currentTarget描述当前分发调用的监听目标，分发结束会被清成null；需要稍后使用节点时，应在同步回调内保存所需引用和身份。保存了Event对象，并不等于保存了它在那一次监听器调用中的全部状态。

DOM分发算法在调用监听器时设置当前目标，结束分发时将currentTarget清成null。这个清理与按钮是否仍在文档中是两项不同事实。看到空值就调查组件卸载，可能从一开始找错了层次。

问题在读取时机，不只在有没有await

假设按钮回调需要等一段工作完成，再使用当前监听目标。回调内读取时它是按钮，下一任务再通过保存事件读取却是null；按钮本身可能完全没有变化。currentTarget参考也说明该值只在相应处理期间可用，保存事件对象不会把它冻结成快照。

不能把这个结论简化成“所有await后必为null”。原生事件、微任务检查点与具体调用路径可能有不同交错，关键条件是分发是否已经结束。本篇用明确的下一任务观察这个条件，而不是从源代码出现一个异步关键字推导所有平台的时序。

target与currentTarget也不应交换。普通浅层DOM中，点按钮里的文字span，target可能是span，监听器注册在按钮时currentTarget则对应按钮。若随后改成父容器委托，当前监听目标又会是那个容器。本文不处理Shadow DOM重定向规则，也不把某个子元素当作永久固定的事件身份。

保存引用以后，还要保存这次操作属于谁

以下完整HTML未执行，没有接口或持久化。点击观察按钮后用1200毫秒教学延迟，留出点击“切换记录”的时间；这个数值只安排对照，不代表网络时限或性能要求。回调内保存按钮与记录身份，后续同时报告事件属性和保存引用，只有任务仍匹配时才显示可应用结果。

<!doctype html>
<html lang="zh-CN">
<meta charset="utf-8">
<title>分发状态与节点引用</title>
<button id="inspect" type="button" data-record="lesson-a">
  <span>观察当前记录</span>
</button>
<button id="switch" type="button">切换记录</button>
<p id="status" role="status">当前记录lesson-a</p>
<pre id="log"></pre>
<script>
const [inspect, change, status, log] = ['inspect', 'switch', 'status', 'log'].map(
  id => document.getElementById(id)
);
const on = (node, type, handler) => node.addEventListener(type, handler);
const write = (node, text) => { node.textContent = text; };
const recordOf = node => node.getAttribute('data-record');
let generation = 0;
const pending = new Set();
on(inspect, 'click', event => {
  const owner = event.currentTarget;
  if (!(owner instanceof HTMLButtonElement)) return;
  const record = recordOf(owner);
  const ticket = ++generation;
  const before = owner.id;
  const timer = setTimeout(() => {
    pending.delete(timer);
    const matches = owner.isConnected && recordOf(owner) === record
      && ticket === generation;
    write(log, JSON.stringify({ before, after: event.currentTarget,
      savedNode: owner.id, connected: owner.isConnected, record, matches }, null, 2));
    write(status, matches ? `可应用于本轮：${record}` : '旧任务不再匹配，未应用');
  }, 1200);
  pending.add(timer);
});
on(change, 'click', () => {
  generation++;
  const nextRecord = recordOf(inspect) === 'lesson-a' ? 'lesson-b' : 'lesson-a';
  inspect.setAttribute('data-record', nextRecord);
  write(status, `当前记录${nextRecord}`);
});
on(window, 'pagehide', () => {
  for (const timer of pending) clearTimeout(timer);
  pending.clear();
});
</script>
</html>

若把监听器从按钮移到共同父容器，先保存引用的规则仍成立，但所保存的对象变了。父容器注册的回调读取当前监听目标，得到的是父容器，不能继续通过按钮类型检查。此时应把“本次命中的按钮”与“本次注册的监听容器”作为两个变量分别推导；前者可来自已限定范围的closest结果，后者来自回调中的当前目标。不能只把类型断言放宽，就假定原来的业务身份读取仍然正确。

这也解释了为什么应在任务接口里写清输入。如果工作只针对lesson-a，传一份不可变的编号比传事件再让深层函数去找按钮更明确；如果工作最终要更新按钮，则同时保留节点和编号。一个绑定到祖先的监听器可以处理许多记录，容器自身的id并不能替代其中每项记录的身份。连接检查、对象身份和任务轮次回答不同问题，缺少任何一项都可能把后续结果落到不属于它的位置。

正常路径先点击观察并保持当前记录，预期分发结束后事件属性为null，保存节点仍连接且身份匹配。切换路径则在教学延迟期间换记录，预期旧任务不被应用。两条路径都保留节点，所以可以分开证明“引用还在”与“任务仍有效”，不把其中一项当作另一项的替代。

连续点击也会产生多个任务。generation让较旧任务不再拥有写入资格，但样本仍会报告它的观察结果，便于说明为什么没有应用。真实产品是否应保留所有诊断输出、取消旧工作还是只忽略结果，需要按任务成本决定；本例没有发送后台操作，因此“不应用”不是撤销服务器写入。

把event浅拷贝就能保留currentTarget吗？

不能依赖这种方式。应在同步回调里明确读取所需属性，而不是把平台事件当作一份普通可枚举记录。直接保存currentTarget读取的是当时值；晚些时候再从原事件读取，则面对已经变化的分发状态。选择几项明确字段也更容易说明后续工作真正需要什么。

保存节点仍只保存引用。节点的文字、属性和记录绑定可以继续变化，删除后也可能还被这份引用保留。MutationObserver的当前节点与记录旧值讨论另一个引用与历史值问题；本篇额外的机制是currentTarget本身会被分发算法清理，不能靠保留事件对象阻止它。

若后续工作只需要记录编号，可以保存业务身份而不携带节点；若需要更新当前按钮，应同时检查连接、身份与本轮资格。把整个Event传过多层服务函数，反而可能使调用者误以为可以随时重新取回当前目标。接口表达所需输入，比依赖临时分发状态更清楚。

保存的节点还在，就能把异步结果写回吗？

不能。列表可能复用同一按钮显示另一条记录，isConnected为真不表示业务对象没有更换。样本因此同时比较data-record和generation；在真实框架里，可以采用自己的对象版本或取消机制，但须解释旧结果何时失效，不能只看DOM节点还存在。

待执行验证分别覆盖保持记录、切换记录、连续点击与删除节点。记录同步调用中的当前目标、已结束分发后的读值、保存节点的连接状态和记录身份。还可用自建Event在dispatchEvent同步返回后读取作机制对照；这只验证分发属性，不证明生成了真实用户输入。

被动监听器与取消标志提醒过事件日志要归属于实际注册。本题同样需要绑定监听位置和观察阶段。本文没有浏览器输出，不能把代码里的JSON结构当成已经捕获的日志。交付先说明读取发生在分发中的哪一步，再决定保存哪个字段以及谁有资格应用后续结果。
