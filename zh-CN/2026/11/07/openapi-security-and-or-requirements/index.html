OpenAPI 的两个认证方案，怎样写才是同时满足？

同对象方案是 AND，security 数组对象是 OR。通过双凭证矩阵区分组合、操作覆盖与三种空值结构，并保留声明和真实授权的边界。

正文

核心要点

  • 同一要求对象内的方案全部满足，数组里的对象可择一满足。
  • 操作安全声明覆盖根级，方案空列表不等于匿名。
  • 文档语义正确不证明服务端已执行认证授权。

两个认证方案需要同时满足时，应把它们写在同一个 Security Requirement Object 里；把它们分成 security 数组中的两个对象，表达的是二选一。逗号和缩进看似只是排版，改变的却是接口声明允许哪些凭证组合。

OpenAPI 的 Security Requirement Object明确区分这两层关系：对象内列出的方案全部需要满足，数组里的多个对象只需满足一个。以下讨论固定在这个版本，不把文档导航中的其他版本当成当前例子的规范，也不把安全声明当成网关已经执行认证的证据。

先确定四种请求应该得到什么结论

设接口需要用户的 Bearer 凭证和客户端的 API key。这里的“同时满足”意味着只有两者都有效时，声明的安全要求才满足；只带其中一个不够。若另一接口允许两种接入方式任选其一，就需要另一种布尔组合，而不是另起一个方案名字解释同样的结构。

完整示例使用虚构接口，不含真实凭证，不会部署服务或发出请求。/both 继承根级的联合要求；/either 明确改为两个替代要求；/health 移除根级安全声明。响应部分只是使接口定义完整，不代表这些响应已经由任何服务器返回。

openapi: 3.1.1
info:
  title: Credential contract example
  version: 1.0.0
security:
  - bearerAuth: []
    clientKey: []
paths:
  /both:
    get:
      responses:
        '200': { description: OK }
  /either:
    get:
      security:
        - bearerAuth: []
        - clientKey: []
      responses:
        '200': { description: OK }
  /health:
    get:
      security: []
      responses:
        '200': { description: OK }
components:
  securitySchemes:
    bearerAuth:
      type: http
      scheme: bearer
    clientKey:
      type: apiKey
      in: header
      name: X-Client-Key

按声明推演，请求不带任何有效方案时，/both 和 /either 都不满足要求。只有 Bearer 有效，或只有 API key 有效时，/either 满足，/both 不满足。两个方案都有效时，两者都满足。这个四格矩阵检查的是文档布尔关系，不是实际请求的成功日志，也没有证明身份是否有权读取某条业务数据。

阅读 YAML 时，可以先圈出每个短横线开始的对象，再看该对象里有几个方案。/both 的两个方案位于同一对象内，因此是 AND；/either 的两个方案分别位于两个对象内，因此是 OR。不能只看字段名是否都出现过，也不能认为数组天然表示“全部都要”。

三种空值形式，处在三个不同位置

操作上的 security: [] 表示这个操作没有继承根级的安全要求。示例中的健康检查采用这种写法。省略操作级 security 则会继续使用根级声明，两者不是同一个操作。把空数组理解成“这里没有另写规则，所以继续继承”，会得到恰好相反的结果。

security: [{}] 则包含一个空的 requirement object。规范说明空对象可以支持匿名访问。由于数组里的要求是 OR，一个匿名可满足的对象已经提供了无需认证的替代路线；即使旁边再列 Bearer 对象，也不会因此变成强制 Bearer。只有阅读完整数组，才能判断有没有这条替代路线。

第三种是 bearerAuth: []。这里空的是方案名对应的列表值，方案本身仍在 requirement object 里，因此仍要求这个方案。把它和操作字段的空数组混为一谈，可能把示例中的 /both 错读成完全没有认证要求。相同符号位于不同层级，不能从一个层级的解释直接套到另一个层级。

本例使用 HTTP Bearer 和请求头 API key，没有 OAuth scope 清单。不要据此扩大成“所有非 OAuth 方案的数组都必须为空”的版本无关断言。规范版本与方案类型仍属于解释条件；这里只需要这两个方案及其布尔分组，足以回答当前接口声明的问题。

操作级 security 会追加根级要求吗？

不会；操作级 security 覆盖根级声明。如果根级要求 Bearer 与 API key 同时满足，某个操作只写 Bearer，它得到的就是该操作重新声明的要求，不是根级的双凭证再加一次 Bearer。

因此评审新增例外时，不能只看提交增加了哪个名字，还要看它替换掉哪些继承要求。示例中 /either 正是有意改变政策；如果业务并不允许只带 API key，请求规格中的这次覆盖就应当被拒绝。先列预期矩阵，再检查 YAML，通常比从缩进猜产品意图更可靠。

bearerAuth: [] 等于允许匿名吗？

不等于；该对象仍要求 bearerAuth，空的是它的列表值。真正匿名的替代对象是 {}，而操作上的空 security 数组又是移除继承声明的另一种结构。看到空值时，先指出它属于哪一层，再讨论结果。

这个区别也适合变异核验：把 /both 下根级同一个对象拆成两个对象，重新计算只有单个有效凭证的两格；再给 /either 的数组加入 {}，检查没有有效凭证的那格如何变化。这些是应由规格推出的预期，不是已经运行过的测试结果，不能直接贴成网关验收报告。

在需求记录里，还应把“允许匿名”与“匿名用户能看到什么”分别写清。一个匿名替代对象只回答安全方案是否必需，不能决定公开响应包含哪些字段。如果健康检查只需要返回进程存活，给它移除继承声明，并不意味着同一服务的诊断信息也应公开。这样的资源范围要由端点职责与授权规则限定。

同样，根级要求发生变化后，应复查所有操作例外。显式覆盖的操作不会因为根级多了一项要求，就自然跟着增加那项要求。评审者需要识别它是有意维持旧政策，还是遗漏了新的需求；否则“统一在根上改一次”的工作方式会留下未被覆盖的例外。

文档通过，不等于部署已经按此授权

安全要求说明有哪些方案、怎样组合，不能自动证明服务器做了签名校验、凭证撤销检查、租户隔离或数据权限判断。可用兼容指定版本的工具检查文档结构，再将四种组合转成自有服务的实际请求测试；无效凭证也必须单独测试，不能把“请求里带了字符串”视为方案已满足。

即使双凭证都有效，用户也未必拥有目标资源。这里的布尔矩阵只处理声明中的方案组合，没有替代业务授权模型。若工具能读出安全配置，却没有把它接到运行中的中间件，文档仍可能正确，部署仍可能错误。对此应记录真正观察到的请求结果与配置版本，不应从一个定义文件推定服务端行为。

接口元数据与运行时执行的边界，还可对照OpenAPI 的 readOnly 为什么不会替服务端过滤输入。当前评审应交付两项清楚的判断：声明的组合是否符合需求，实际服务是否经过独立验证。前一项的通过不能代替后一项。
