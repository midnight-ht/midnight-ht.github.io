rsync 多套了一层目录：源路径末尾斜线改变了什么？

通过两份已有目录的 rsync 预览核对源尾斜线、接收层级、删除集合与 shell 通配符边界。

正文

核心要点

  • 源目录与目录内容定义不同传输根。
  • delete 只在相应同步目录范围内考虑多余项。
  • 预览与真实传输结果必须分开记录。

rsync 的源目录带尾斜线时复制目录内容，不带时通常保留目录名这一层。先固定已存在的目标目录与预期树，再决定写法；使用 delete 时还要按实际同步目录核对删除集合。一个斜线改变的是传输对象，不只是路径显示习惯。

先说目标里应该出现哪条路径

rsync 官方手册把源目录末尾斜线解释为复制内容，避免额外的目录层级。此次页面 VERSION 条款标明三点五点二，页脚为二〇二六年十一月四日；这是所读手册的声明，不是对本机程序版本或发布状态的检查。

假设源目录叫 package，里面只有 one.txt。已有目标目录里，希望得到的是目标下直接的 one.txt，还是目标下 package/one.txt？两者都可能合法，但代表不同部署树。先写清完整路径，才能解释“多一层”究竟是错误，还是命令忠实执行了另一个合同。

无尾斜线的目录源通常将目录名这一层放到已有接收目录中；带斜线则把其中内容放到接收目录。这里特意限定目标已存在且为目录，避免将不存在目标时的单项命名规则混入主例。源端、目标端各自的条件都需要记录，不能只截一个源路径字符串让别人猜。

用两份已有目录预览，不执行删除

下面是未执行的完整本地教学输入。要求 rsync、常规 shell 与可写的临时目录；不访问远端、不使用通配符，不把真实发布目录传给示例。所有目标和待观察对象都在一次性目录内。

rsync_demo_dir=$(mktemp -d)
cd "$rsync_demo_dir" || exit 1
mkdir -p src/package dest-named/package dest-content/package
printf 'new\n' > src/package/one.txt
printf 'keep?\n' > dest-named/root-marker
printf 'old\n' > dest-named/package/stale
printf 'keep?\n' > dest-content/root-marker
printf 'old\n' > dest-content/package/stale
preview() {
    rsync -ani "$@"
    rsync_result=$?
    printf 'preview-status=%s\n' "$rsync_result"
}
preview src/package dest-named/
preview src/package/ dest-content/
preview --delete src/package dest-named/
preview --delete src/package/ dest-content/

n 选项使这四次调用只预览计划；i 让变更条目可读。函数立即记录 rsync 的退出值，避免后续打印覆盖。即使四项都成功结束，目标仍没有因这些预览完成复制或清理；准备时创建的文件不能被展示成同步后的结果。

不带删除时，第一种形式的预期接收路径是 dest-named/package/one.txt，第二种是 dest-content/one.txt。两份预先放置的 root-marker 与 package/stale 都还在真实磁盘上，因为没有实际传输。这里描述的是待执行操作会落在哪一层，不是伪造 rsync 的逐行输出。

加入删除后，两种同步根的差异更明显。第一种同步 package 目录，目标 package 内的 stale 是拟删除候选，而根层 root-marker 不应只因这次目录同步就被视为同一集合。第二种把 package 的内容同步到 dest-content 本身，根层标记与源中不存在的 package 子目录进入另一份删除考虑范围。应逐项阅读真实预览，再决定是否符合保护要求。

delete 不是清空整个目标的通用开关

官方手册明确说，delete 处理接收端多余文件，但仅限正在同步的目录。过滤规则、递归条件与其他选项还会影响集合。因此不能把上面的简单预测外推成“目标里一切不在源中的东西都会删”，也不能认为复制命令只多一个选项，风险范围就不需要重新审查。

若目标根目录还放着运行配置、上传文件或另一个站点，必须先说明它们是否属于同步集合。本篇的 root-marker 是为了让范围差异可见，不是建议拿真实配置当试验品。预览清单出现了意外对象，应停止并查传输根与过滤条件；不要为了让输出整齐而先删除那个对象。

准备真正执行时，还需确认源内容可读、目标身份没有改变，以及预览与执行之间是否有新增写入。旧预览针对的是当时那棵树，不会自动批准后来变化的集合。本文只给出预览实验，没有去掉 n 运行删除，也没有验证任一真实目录已被交付。

还有一个容易误读的观察：复制“内容”不表示接收目录本身的属性完全不变。手册在尾斜线例子中同时说明，包含目录的属性也会传给接收端对应目录。本例使用archive模式，因此除了one.txt落在哪一层，还应核对哪一层目录承担了源目录的属性；不要把路径层级正确写成权限一定保持原样。

可以在另一个自有沙盒给源目录和接收目录设置可辨认但合法的属性，先记录，再看实际预览与执行的对应变化。需要保留接收端属性时，应按所选选项另行设计，而不是期待末尾斜线只改变名字、不影响其他archive语义。这一项观察与删除集合分开，不必为验证属性而执行删除。

用星号选出全部文件，就等同复制目录内容吗？

不等同。星号由 shell 先展开，rsync 收到的是单项列表，而不是同一个父目录同步请求。手册在 delete 说明中特别区分目录参数与 dir/* 形式。用起来都像在复制文件，不代表可以沿用同样的父目录删除推断。

单项数量也会影响另一类行为。手册说明，在只有一个传输项、目标最后元素不是已有目录且没有尾斜线等条件下，目标可以成为该项的新名字。为避免主例受到这类条件干扰，我们先创建两个目标目录。实际脚本也应明确目标类型，而不是依赖今天通配符恰好匹配多个文件。

dry-run 没报错，就表示目标已经同步好吗？

没有。它展示拟议变更，不提供复制后的内容或持久化证据。预览可以帮助检查目录层级和删除集合，但权限、源变化、磁盘错误与执行期间并发仍可能改变真实结果。应把预览批准与实际运行的退出状态、目标树和内容核对分开保存。

如果只需要理解尾斜线，保留 n 即可完成本篇的纸面比较。若另行决定在自有沙盒验证复制，应在明确保护集合后单独运行复制，并检查 one.txt 的实际内容与所在层级；对删除实验也要重新确认这是新建目录。不要将这些候选后续操作写成本文已完成的事实。

目录层级正确还不等于原子发布。文件可在不同时间被替换，目标属性也有相应传递规则；实际应用是否会读到混合版本，需要另一个发布设计。尾斜线不是回滚协议，也不是权限保持不变的承诺。

二〇二六年十一月五日的Make 同名目标文章讨论动作名字与文件身份，本题则讨论同步请求真正包含哪个目录对象。看见同一个路径名字，不足以说明两条命令处理同一集合。先画出预期目标树，再核对传输根与删除候选，最后才决定是否执行。
