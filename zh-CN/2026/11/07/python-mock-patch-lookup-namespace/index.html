unittest.mock 已 patch 定义处，为什么业务仍调用原函数？

用三文件计价例子追踪 Python 消费者名字绑定，区分补丁目标、生命周期与 create=True 的误用。

正文

核心要点

  • 补丁应匹配实际消费表达式。
  • from-import 与模块属性查找需要分别判断。
  • create=True 不证明真实 API 或正确消费路径。

unittest.mock 应替换被测代码查找依赖的名字。若消费者已用 from fees import fee 绑定自己的 fee，之后只改 fees.fee 不会改变这份引用；先沿消费者的查找路径定位，再决定 patch 的目标。扩大补丁持续时间，不能修复替换位置错误。

同一个函数，可以有两个名字指向它

Python 的 unittest.mock 文档明确要求在对象被查找的位置打补丁，而不一定在定义位置。本篇核对的是二〇二六年十一月六日返回的 Python 3.15.2 在线文档，不据此推断读者本机解释器版本。下面只使用本地纯函数，没有连接费用服务或执行测试。

设 fees 模块定义手续费函数，billing 模块导入后计算总价。导入不是让消费者的每次调用都回到定义模块重新寻找对象；from-import 会在消费者中建立一个名字。原先两个名字可能指向同一个函数，但把其中一个名字重新指向替身，不会自动改变另一个名字。

这解释了一类容易误判的现象：补丁上下文已经进入，替身返回值也设置正确，被测代码却仍得到原手续费。工具未必失效，错误可能是被修改的名字根本不在这次调用的查找路径上。先找实际表达式，比把测试重试多次或把补丁提升到整个类更有诊断价值。

用三份文件看清实际业务结果

下面是未执行的完整教学项目。准备一个独立可写目录，将三段代码按标注保存；从该目录运行标准库 unittest，不需要第三方网络或数据库。金额数字仅用于观察名字绑定，不作为真实计费规则。

# fees.py
def fee():
    return 3

# billing.py
from fees import fee

def total(base):
    return base + fee()

# test_billing.py
import unittest
from unittest.mock import patch
import billing

class BillingLookupTest(unittest.TestCase):
    def test_definition_patch_misses_consumer(self):
        with patch("fees.fee", return_value=9) as substitute:
            self.assertEqual(billing.total(10), 13)
            substitute.assert_not_called()

    def test_consumer_patch_changes_business_result(self):
        base_price = 10
        with patch("billing.fee", return_value=2) as substitute:
            patched_total = billing.total(base_price)
            substitute.assert_called_once_with()
        restored_total = billing.total(base_price)
        self.assertSequenceEqual((patched_total, restored_total), (12, 13))

if __name__ == "__main__":
    unittest.main()

候选调用是 python -m unittest -v test_billing。应立即保存该命令的真实退出状态和输出，再进行其他检查，不把后续列目录命令的成功当作测试结果。本文没有执行它，列出的十三与十二都是给定输入下的预期，不是通过日志。

第一个测试并不是希望错误的业务实现通过。它专门揭示定义处补丁为什么没有影响消费者：billing 已在模块导入时拿到原引用，仍把十与三相加。替身未被调用只是辅助证据，业务返回十三才说明实际读取的是哪条路径。单纯断言替身返回九，几乎只是在验证测试自己配置了什么。

第二个测试修改 billing.fee，因此 total 读取替身并返回十二；退出上下文后再检查十三，确认这份名字恢复。这里没有承诺已经撤销任何外部副作用，因为示例刻意没有外部动作。真实代码若在调用中写文件或发送请求，还要另外设计隔离与结果检查。

还可以用另一份明确合同检验这条解释。若某项产品测试的要求是“本次手续费为九，基价为十”，独立预期应是十九；错误位置的补丁仍返回十三，这时测试必须失败。演示用例断言十三，只为证明原绑定仍被使用，不能直接复制成这项产品要求的验收答案。先写业务合同，才能判断相同数值究竟是预期观察还是缺陷。

若希望模拟费用提供者不可用，也要沿同一名字路径注入错误，并检查调用方定义的失败响应。定义处替身抛错而消费者照常返回，说明这次输入没有进入业务路径；它不能证明业务已经处理了费用失败。不要为让用例变绿而把所有异常都吞掉。可以分别保留原函数、预期返回替身与失败替身三种输入，每项只改变一个来源，结果才容易归因。

换一种导入方式，目标也要跟着表达式看

如果 billing 改成 import fees，并在函数里调用 fees.fee，那么每次经过的是模块属性。此时替换 fees.fee 就在这条查找链上。不能把“永远 patch 消费者模块”记成另一条不看代码的口诀；正确目标来自实际使用表达式，导入形式只是帮助辨认它。

可以把评审记录写成三列：定义位置、消费者保存的名字、调用时使用的表达式。对本例，定义位置都是 fees.fee；from-import 形式实际读取 billing.fee，模块导入形式读取 fees.fee。两种形式都合法，测试应匹配项目当前契约，而不是为让已有补丁生效随手改生产导入。

若依赖在默认参数、闭包或对象构造时被提前保存，模块上的名字又不是全部路径。此时应继续定位保存时点与实际读取者，或考虑明确传入依赖。本例没有覆盖这些捕获方式，因此不能把两条 patch 字符串扩展成替换所有历史引用的保证。

create=True 能证明 patch 地址正确吗？

不能。它允许在目标原本没有该属性时创建一个，设置成功并不证明真实代码会读取它。官方文档特别提醒，放开这项能力可以写出针对根本不存在的 API 的通过测试。遇到目标不存在错误时，先核对拼写、模块身份和消费表达式，而不是马上增加这个参数。

例如把 billing.fee 误写成 billing.fees，默认失败可以暴露错误。若允许创建新属性，补丁可能顺利进入，但 total 仍读取原来的 fee。此时若测试只检查替身被创建，就没有检查计价行为。为运行时确实会产生的属性使用创建能力可以有理由，但应说明该属性由谁创建、消费者何时读取以及业务结果如何验证。

应该改导入，还是改依赖接口？

先以现有消费表达式选择最小可解释的补丁。如果长期需要替换复杂模块内部的许多名字，明确传入一个手续费提供者可能更容易表达依赖；是否重构仍取决于模块职责与改动成本。不要因为某个测试难写，就宣称所有 from-import 都错误。

二〇二六年十月十四日的补丁范围文章讨论持续多久、何时恢复，以及恢复不等于回滚副作用。本题补的是此前的一步：究竟改哪一个名字。两个控制可以同时正确，也可以一个正确、另一个错误。

拟议验证应保留未替换基线、错误定义处、正确消费处和退出后恢复四组结果，并让断言使用独立的业务预期。记录 Python 版本、文件位置、调用命令与真实错误；遇到失败先核对导入到的是不是本次文件。确认替身进入业务查找链之后，再讨论扩大范围或增加更复杂的模拟。
