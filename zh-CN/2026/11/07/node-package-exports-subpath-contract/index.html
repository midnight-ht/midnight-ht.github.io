文件明明存在，为什么 Node 报子路径没有导出？

exports 公开的是包说明符入口，不是所有物理文件路径。用无需安装的本地包区分逻辑键、目标文件、历史兼容与文件系统访问边界。

正文

核心要点

  • 物理文件存在不代表对应包子路径已经公开。
  • main 不会绕过现有 exports 表恢复未声明入口。
  • 导出封装维护公开接口，不提供文件保密边界。

文件存在于包里，仍可能无法通过包子路径导入，因为 exports 定义了公开的包说明符入口。它没有声明的子路径，可以得到 ERR_PACKAGE_PATH_NOT_EXPORTED；这不等于目标文件在磁盘上丢失。

Node.js 的包入口说明把这类封装与文件系统存在性分开。本文读取时页面标题是 Node.js v24.22.2，已保留相应快照；该版本线地址会变化，不把它描述成永远固定的最新版本。下面的本地例子没有下载安装依赖，也没有声称实际执行通过。

先造一个不依赖注册表的小包

在一个新建、自有的空目录中建立 demo，按下面的目录树创建文件。不要向已有项目的 node_modules 覆盖文件。这里手动放入包目录，只是让 Node 的包解析有一个具体输入，不需要发布到注册表或运行安装命令。

demo/
  package.json
  app.mjs
  node_modules/
    contract-demo/
      package.json
      public.js
      internal.js
      lib/
        feature.js

外层 demo/package.json 的完整内容是 {"type":"module"}。包自己的 package.json 使用以下内容，定义根入口与一个逻辑功能入口。版本号是这个虚构包的标识，不是运行时版本要求。

{
  "name": "contract-demo",
  "version": "1.0.0",
  "type": "module",
  "exports": {
    ".": "./public.js",
    "./feature": "./lib/feature.js"
  }
}

三个 JavaScript 文件各有一行完整代码。public.js 写 export const name = "public";；lib/feature.js 写 export const feature = "feature";；internal.js 写 export const internal = "internal";。它们都确实应当被创建，而不是故意省掉内部文件制造文件不存在的错误。

最后，demo/app.mjs 使用下面的完整程序。前两条静态导入验证公开入口，循环里的动态导入则分别尝试内部文件和公开功能的物理目标路径。这里只打印错误代码，不把错误吞掉后报告所有导入成功。

import { name } from 'contract-demo';
import { feature } from 'contract-demo/feature';
console.log({ name, feature });

for (const specifier of [
  'contract-demo/internal.js',
  'contract-demo/lib/feature.js'
]) {
  try {
    await import(specifier);
  } catch (error) {
    console.log(specifier, error.code);
  }
}

准备完文件后，可执行 node demo/app.mjs。按导出表推演，根入口和逻辑功能入口可以加载，后面两个未声明的包子路径预期报告导出错误。这个结果是待核验的预期，不是伪造的终端日志。若实际得到文件缺失、语法或其他错误，先核对输入目录与代码，不能把所有失败都归到导出表。

公开的是键，不是磁盘布局的全部别名

逻辑名字 contract-demo/feature 映射到 lib/feature.js，并不自动把 contract-demo/lib/feature.js 也变成入口。消费者使用的是导出表的键，右侧路径描述包内目标。一个文件可以有经过选择的公开名字，未必以自己的物理路径对外暴露。

这种设计允许维护者重排内部文件，同时尽量维持已承诺的导入名字。它并不保证任意移动都兼容：如果改掉导出键，或让目标不再提供同样的接口，消费者仍可能失败。评审时应把“内部文件移动了”与“公开契约改变了”分别列出，而不是只比较目录树是否还有同名文件。

也不要看到报错就立即加一个覆盖所有路径的通配导出。这样可能让当前调用者恢复，却同时把更多内部布局变成消费者可以依赖的入口。后续想再收回这些路径，就要面对新的兼容负担。先确认哪些路径本来就是受支持的接口，再决定显式保留或要求调用方迁移。

main 能救回未导出的子路径吗？

不能；在支持 exports 的 Node 版本里，导出表优先于 main。保留旧的根入口字段，不会让一个没有列在导出表里的深层路径自动恢复。根入口正常，只证明根键能解析，不代表同包中的任意文件都仍然公开。

因此给旧包补上导出表时，要盘点真实支持的历史入口，包括可能被消费者读取的包元数据入口。只写一个点号键并不是无行为变化的整理。若过去文档承诺过某条深层路径，应明确保留对应导出，或者作为有迁移说明的接口变更处理，而不是把失败都解释成消费者缓存坏了。

核验兼容性时，可以把旧文档列出的每个入口做成单独导入探针，记录预期与实际错误代码。不要把扫描目录里所有文件得到的集合直接当成公开接口清单，也不要把某个应用恰好没有使用深层路径当成所有消费者都不受影响的证据。兼容范围需要有明确的承诺对象。

导出封装不是保密机制

官方同一入口章节特别指出这不是强封装；直接使用绝对文件路径仍可绕过包说明符的封装。不能因为某个文件未导出，就把秘密放进要分发的包，期待别人读不到它。

这里需要分清两个目标。公开入口表帮助维护一套可支持的导入接口，文件访问权限和秘密分发则属于另一种边界。示例让包子路径报错，证明的只是该解析路线没有公开这个名字，并没有对读取包文件本身施加权限控制。给错误换一个安全含义，会让后续架构判断失去依据。

同样，本例限定为 Node 的包说明符解析，不把结论直接套到浏览器导入映射或编译器的类型解析。浏览器中另一套名字到目标的规则，可对照import map 的 scopes 如何影响模块解析。机制相邻，解析环境与保证范围却需要分别核对。

用单条导出变更检验自己的解释

可以在例子副本中只增加 "./internal.js": "./internal.js"，保持磁盘文件原样，再预测变化：内部文件的那个导入应从未公开变为可解析，另一个物理功能路径并不会因为这次变更自动公开。这个试验区分的是接口扩张与文件创建，不应同时改一堆文件后只看有没有报错。

也可以反过来删掉公开功能的目标文件。此时即使键仍然公开，加载也会因目标问题失败；导出许可不是文件存在、语法正确或接口内容正确的保证。把公开键、目标文件和运行结果分别检查，才能解释一个具体错误属于哪一步。

实际运行时记录真实 Node 版本与完整输入，只把观察到的结果标为实测。例子结束后只清理自己新建的目录，不涉及任何既有依赖。当前维护决策是明确公开哪些名字、保留哪些历史承诺，再用针对性的导入探针核验；不要让磁盘文件是否存在替你决定整个包的公开契约。
