HTML折叠说明想被页内查找发现，until-found该怎么用？

核对until-found的搜索揭示、布局条件与beforematch再检查顺序，提供显式显示后备而不伪造搜索通过。

正文

核心要点

  • until-found与普通hidden有不同发现合同。
  • 布局覆盖可能破坏原生揭示。
  • beforematch后还会检查状态与连接。

hidden="until-found"使内容暂不呈现但保留页内查找与片段揭示路径；普通hidden不提供这份合同，额外display规则也可能破坏揭示。若长文里的补充说明仍应被用户搜索到，先决定“暂时折叠”是否真的可以变成“不可发现”。

HTML的hidden属性定义区分Hidden和Hidden Until Found状态。后者让用户代理在页内查找或片段导航试图进入相关子树时，运行祖先揭示算法，先揭示内容再滚动到目标。这是一个有条件的浏览器发现机制，不是把所有隐藏内容都宣布为可搜索。

内容跳过与盒子消失不是同一件事

普通hidden表示内容当前不直接相关，用户代理不应呈现它。until-found则保留另一种意图：现在不展示，但允许通过查找和片段到达。标准的呈现安排采用content-visibility隐藏内容，而不是简单地把整个元素设成display:none，所以边框、内边距和外边距仍可能出现。

visibility与后代覆盖讨论CSS继承与盒生成。本题的差异是，浏览器还承担从发现到揭示的流程。把所有看不见的状态统一为一个隐藏类，可能将这项流程一起抹掉，外观暂时相同却失去入口。

例如政策正文下有一节“已过期材料的处理”。普通阅读时不想让这段说明打断主线，但用户搜索“过期”应能到达它。此时要保留真正文字与目标身份；若只在用户点击以后才向服务器取回内容，浏览器不能从尚不存在的文字里查出命中。属性不承担远程搜索或数据加载。

一个能手动恢复的完整文档样本

以下HTML未执行，没有真实政策、接口或表单。补充文字一开始就在文档中，section使用until-found，链接指向其中的真实id。手动显示按钮提供独立后备入口；成功点击这个按钮不等于原生查找已经通过。

<!doctype html>
<html lang="zh-CN">
<meta charset="utf-8">
<title>教学说明发现路径</title>
<h1>教学材料说明</h1>
<p><a href="#expired-rule">跳到过期材料处理</a></p>
<button id="show" type="button">显示补充说明</button>
<button id="hide" type="button">恢复可发现的折叠状态</button>
<p id="status" role="status">可用页内查找定位补充说明的完整标题。</p>
<section id="extra" hidden="until-found">
  <h2 id="expired-rule">教学过期材料处理</h2>
  <p>这是虚构教学说明：过期材料需要重新确认适用版本。</p>
</section>
<script>
const [extra, show, hide, status] = ['extra', 'show', 'hide', 'status'].map(
  id => document.getElementById(id)
);
const on = (node, name, fn) => node.addEventListener(name, fn);
const say = text => { status.textContent = text; };
on(extra, 'beforematch', () => {
  say('收到原生发现通知；浏览器随后按条件继续处理');
});
on(show, 'click', () => {
  extra.removeAttribute('hidden');
  say('已用手动入口显示，不代表原生搜索已验');
});
on(hide, 'click', () => {
  extra.setAttribute('hidden', 'until-found');
  say('已恢复折叠；可再次检查查找或片段入口');
});
</script>
</html>

例子没有给section额外覆盖display或content-visibility，让属性使用浏览器自己的呈现机制。测试时在这个独立HTML页搜索隐藏标题的完整文字“教学过期材料处理”，确认命中的是expired-rule而非可见提示；再恢复折叠、点击片段链接，分别记录事件与属性变化。两条入口应分开观察，不能因为片段成功就认定每个浏览器的查找交互也一致。

需要重新测试时，设置until-found与设置hidden=true也不同。后者会进入普通Hidden状态，丢掉当前要检查的发现合同。若框架只用一个布尔hidden属性同步所有折叠面板，应检查最终DOM写出的究竟是什么，而不是只看组件状态变量叫“折叠”。

为什么加了display:none以后查找不再揭示

标准要求元素受相应布局包含影响才能被查找揭示，并明确列出display为none、contents或inline时不能按此机制揭示。为了去掉保留边框或空隙而加入这些规则，可能把发现路径一起取消。应先决定需要隐藏的是内容、装饰还是整盒，而不是让一个全局隐藏样式决定产品行为。

可以准备四份只有display条件不同的样本，保留同样文字与id，观察正常块布局和三种覆盖的区别。不要在错误版本里手动移除hidden后，再报告它的原生揭示成功；那样真正执行的是后备按钮的职责。失败记录要能指出哪条CSS改变了前提。

查找揭示以后，目标还可能被固定页头遮挡。片段目标与scroll-margin处理的是下一项几何问题。内容已经展开、滚动位置可读、键盘后继位置合理，分别需要观察；一个beforematch事件不替它们全部通过。

beforematch里改成普通hidden，为什么不会继续展开？

算法在通知后会再次检查是否仍是Hidden Until Found；监听器若改成普通Hidden状态，就会返回，不再移除该属性。标准还检查连接状态，所以在回调里移走节点，也会改变接下来的流程。它没有承诺无论应用怎样改动，浏览器都强行把旧目标展开。

这对组件同步有实际影响。假设beforematch通知触发一次渲染，组件仍根据旧的“折叠=true”把属性写回普通hidden。用户刚发现目标，应用又改了状态，最终内容继续看不见。应明确由谁接管发现后的展开状态，避免浏览器和组件各维护一份互相覆盖的规则。

样本只显示外部状态文字，不改动目标的隐藏状态。真实组件可以同步自己的展开模型，但必须尊重发现发生了什么，不能在更新后无意重建一个普通隐藏的替代节点。需要异步取数据的系统，还要说明发现时已有哪部分内容、等待中怎样继续；本文没有实现这种加载流程。

手动dispatchEvent(beforematch)会自动展开吗？

不会因此运行浏览器的祖先揭示算法。手动分发可以调用应用监听器，却没有重演查找、目标匹配、状态复查和移除属性的整套流程。用它检查提示函数，与用真实浏览器验证发现机制，是两种不同测试。

同样，后备显示入口应显式移除属性，不必伪造发现通知。它提供的是目标浏览器缺少原生支持或用户不使用查找时的继续路径。把手动显示记录为手动显示，才能让报告保留兼容边界，而不是把所有路线合成“until-found已支持”。

内容也没有因为隐藏而受到访问控制。这个边界只需明确：文档中的文字仍是客户端已有内容，不能用该属性保护秘密。真正的新问题是它是否按当前文档意图保留发现路径，以及事件后状态由谁负责，而不是又设计一层视觉遮挡。

待执行检查记录浏览器、搜索词、片段、计算display、事件顺序和属性前后值，加入监听器改回普通hidden的失败变体。本文没有浏览器通过记录。交付先保住查找能发现的真实内容，再让布局和组件状态共同尊重一次揭示，而不是只确认源码写着until-found。
