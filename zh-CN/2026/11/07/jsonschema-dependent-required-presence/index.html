invoice 是 false，dependentRequired 为什么还要求地址？

dependentRequired 检测字段出现，不检测真假。比较出现依赖与带存在前提的 if/then，用五个输入核对单向关系、空对象与独立类型约束。

正文

核心要点

  • false 仍是已出现的属性值。
  • 真值条件应在 if 内明确要求触发属性存在。
  • 反向依赖与独立字段类型都需要分别表达。

invoice 是 false，仍然会触发 dependentRequired，因为它检测属性是否出现，不检测属性值是否为真。如果业务只在用户选择开票时要求地址，就应该写值条件，而不是把属性出现依赖当成布尔开关。

Draft 2020-12 的 dependentRequired 条款把触发条件写成属性存在。一个传了 false 的字段，显然已经存在。规则没有误判真假；它执行的是另一个问题。排查时先确定产品要的是“这两个字段一起出现”，还是“这个值为真时补齐其他字段”。

两个完整模式，表达两种不同需求

假设接口允许提交开票标志和发票地址。第一种约定要求：只要标志字段出现，就必须提供地址，不管标志是什么布尔值。下面的模式恰好表达这种出现依赖。它没有要求所有请求都必须包含开票标志。

{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "properties": {
    "invoice": { "type": "boolean" },
    "invoiceAddress": { "type": "string", "minLength": 1 }
  },
  "dependentRequired": { "invoice": ["invoiceAddress"] }
}

第二种约定要求：只有标志明确为 true 时才必须提供地址。此时用带存在前提的 if，配合 then 要求地址。下面仍是完整独立模式，不能把两个示例叠加使用后，再期待第一条出现依赖自动消失。

{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "properties": {
    "invoice": { "type": "boolean" },
    "invoiceAddress": { "type": "string", "minLength": 1 }
  },
  "if": {
    "required": ["invoice"],
    "properties": { "invoice": { "const": true } }
  },
  "then": { "required": ["invoiceAddress"] }
}

条件子模式的规则是依据 if 子模式是否有效，决定是否应用 then。这里不是让验证器执行程序语言中的真假转换，而是让输入对象同时满足条件里的存在约束和固定值约束。外层的布尔类型检查仍然独立生效。

示例输入与结果都是手工推演，尚未运行验证器。采用时应选择支持这个方言的工具，记录真实工具版本和观察结果，不要把下面的预期表述改成“验证已通过”。

五个输入，足以看见区别

空对象 {} 在两个模式下都预期通过。它没有标志，不触发第一种出现依赖；在第二种模式中，也不满足条件里的 required，因此不会要求地址。若产品希望每个请求都声明是否开票，那是另加外层 required 的需求，不是现有两种模式已经表达的条件。

输入 {"invoice":false} 在出现依赖模式下预期失败，在值条件模式下预期通过。属性存在使前者要求地址；固定值不为真则让后者不应用地址要求。这一行最直接地区分两种业务规则，不能只用一个真值样本测试后就认定两套模式等价。

{"invoice":true} 在两个模式下都预期失败，因为都需要地址。{"invoice":true,"invoiceAddress":"A"} 则都预期通过。这个成功输入不能证明选对了规则，正如两个错误实现也可能在同一条正常路径上表现一致；差异样本才是模式评审的关键。

第五个输入是 {"invoiceAddress":"A"}，两个模式都允许它。地址存在并不自动要求标志存在。若界面会预填地址但暂时不提交开票选择，这可能正是需要的行为；若业务禁止这种组合，就要明确增加反向要求。应从实际需求决定，不能因为觉得对称好看就直接补规则。

地址出现后，invoice 也必须出现吗？

只有显式声明反向依赖时才必须。官方条件验证指南也提醒依赖不是双向的。若在 dependentRequired 中另加 invoiceAddress: ["invoice"]，地址单独出现的输入就会被拒绝；这是政策改变，不是修复一个没有执行的隐式规则。

反向要求也不等于标志必须为真。它只要求这个属性出现，false 仍是一个出现的布尔值。如果业务要的是“有地址就一定选择开票”，需要再表达值条件。把需要出现、需要特定值和需要互相依赖三件事混在一个名字里，会在下一轮表单变化时再次出错。

换成 if 时，别丢掉存在前提

一个常见修复是只留下 properties: {"invoice":{"const":true}} 作为条件。问题是 properties 不要求属性必须出现；缺少标志的对象也可能满足这个条件，于是进入 then，反而要求地址。这样虽然改用了值条件，却把原本允许的空对象弄成了失败输入。

把 required: ["invoice"] 放在 if 内，限定的是何时启用这一分支；把它放在最外层，则会要求所有输入都带标志。位置不同，需求不同。修复时应先问空对象是否允许，再决定哪一个位置符合产品，而不是为了让当前用例过关，把存在约束随手移到其他层级。

此外，invoice: null 会激活出现依赖，但它也违反了外层布尔类型。即使附上地址，完整模式仍应拒绝。这个输入用来区分“触发了哪条规则”和“整体是否有效”，不能用一个最终失败结果推定失败只来自地址缺失，更不能假设布尔类型会替应用把空值变为假值。

地址的形状也由独立规则控制。标志为真且地址为空字符串时，字段虽然出现，仍会被 minLength 拒绝。反过来，标志为假但提交了数字地址，也不会因条件没有启用就绕过外层属性类型检查。条件控制新增的要求，不会关闭已经写在根对象里的其他约束。

用差异样本核验选中的需求

实际测试先保留上述五个输入，再加入真值加空地址、假值加数字地址、空标志加地址三个变体。分别记录触发关系与整体有效性，错误提示也应说明是缺字段、值类型错误还是地址为空，避免把所有拒绝都报成“需要开票地址”。每次改变规则后，重新计算空对象与地址单独出现的结论。

验证只做判定，不会帮请求补默认标志、生成地址或修改输入。客户端与服务端各承担什么责任，可继续参考表单验证与服务端权威边界。当前选择可以明确落定：要属性联动就声明出现依赖，要真假分支就声明带存在前提的值条件；反向关系只有业务需要时才添加。
