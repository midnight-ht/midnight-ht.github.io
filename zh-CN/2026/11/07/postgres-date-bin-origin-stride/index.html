都按十五分钟统计，date_bin 的桶边界为什么不同？

十五分钟只规定跨度，origin 还决定边界。用边界前后与锚点之前的输入，拆开分桶对齐、过滤窗口和日历意图。

正文

核心要点

  • 分桶规则需要跨度、锚点和输入时间类型。
  • origin 是对齐锚点，不是过滤起点。
  • 月与更大单位不能用作 date_bin 的 stride。

两个服务都按十五分钟统计，桶边界仍可能不同，因为 date_bin 同时使用 stride 和 origin。前者给出桶的跨度，后者给出对齐锚点；只统一“十五分钟”这句话，没有统一完整的分桶规则。

假设一个采集服务把九点零二分作为锚点，报表服务却按整刻钟显示。九点十六分的同一条记录，前者会放进九点零二分开始的桶，后者会标成九点十五分。两边都没有把十五分钟算错，冲突发生在分界位置。把一个标签换成另一个标签，不能保证桶里的记录集合也相同。

先写出四个边界输入

下面使用 PostgreSQL 18 的 date_bin，输入明确为不带时区的 timestamp，用于隔离对齐问题。它是只读例子，结果为按官方规则推演的预期，未声称在数据库执行过。真实系统若存的是 timestamptz，应另外统一它的类型与转换契约。

WITH samples(t) AS (VALUES
  (timestamp '2026-11-06 09:01:59'),
  (timestamp '2026-11-06 09:02:00'),
  (timestamp '2026-11-06 09:16:59'),
  (timestamp '2026-11-06 09:17:00')
)
SELECT t,
       date_bin(interval '15 minutes', t,
                timestamp '2026-11-06 09:02:00') AS bucket
FROM samples
ORDER BY t;

四个桶起点依次是当天的 08:47:00、09:02:00、09:02:00、09:17:00。九点零二分正好开始新桶，九点十七分也开始新桶。用区间表达，九点零二分这一桶包含从九点零二分起、到九点十七分之前的输入；右边界属于下一个桶，不应该在两边各算一次。

第一条尤其值得保留。它比 origin 早一秒，结果不是九点零二分，也不是拒绝输入，而是前一个桶的起点八点四十七分。锚点向前向后定义对齐，并不限定可接受的最早记录。若产品只允许统计九点零二分之后的数据，还需要单独的过滤条件。

官方文档把返回值定义为输入所属桶的开头，并明确指出桶按指定的 origin 对齐。因此，这里不应把“输入减去锚点后除以跨度”草率写成整数截断代码；对负差值，向零截断与选择更早的桶不是一回事。边界前的一秒正好可以暴露这种错误实现。

同一条记录，换锚点再比较

第二个例子让两个定义同时出现在一行，避免比对两个已经各自聚合完的报表。输入、跨度和类型保持相同，只改变锚点。

SELECT timestamp '2026-11-06 09:16:00' AS t,
       date_bin(interval '15 minutes',
                timestamp '2026-11-06 09:16:00',
                timestamp '2026-11-06 09:00:00') AS aligned_at_zero,
       date_bin(interval '15 minutes',
                timestamp '2026-11-06 09:16:00',
                timestamp '2026-11-06 09:02:00') AS aligned_at_two;

预期分别是 09:15:00 与 09:02:00。若接口只传 bucket=15m，消费者无法从这个字符串判断生产者用了哪一种边界。比较聚合结果之前，应先拿同一个原始时间点算标签，确认双方实现的是相同划分，再检查过滤窗口与聚合函数。

对固定跨度，锚点也不必是某个真实事件发生的时刻。可以选择稳定、可共享的配置值。另一方面，不同的锚点值也未必代表不同划分：相差整数个十五分钟的两个锚点，会给出相同的一组边界。真正应检查的是它们是否在该跨度上对齐，而不是配置字符串是否逐字相同。这是从周期分界推导的判断，不是新增的执行测量。

分桶、过滤与补空桶要分开决定

分桶回答的是一条已选记录属于哪个区间。过滤回答哪些记录参加本次查询。补空桶回答没有记录的区间是否也要显示。这三项可以出现在同一张报表，却不是一个函数提供的三种自动行为。date_bin 返回一个时间值，不会仅凭调用就生成所有空区间，也不会替你选择业务查询窗口。

例如报表从九点开始，但分桶沿用九点零二分对齐，九点到九点零二分之前的记录会被标到八点四十七分。把结果标签再按“九点以后”过滤，可能丢掉已经通过原始时间过滤的记录。应先明确页面想展示完整桶还是截断窗口，再决定查询结构；不能因为标签早于页面起点就认定输入错误。

这也影响历史数据重算。若更改了锚点，却沿用旧缓存键和旧聚合表标识，同一个标签可能被赋予两套记录边界。先记录规则版本，并用原始时间点核对新旧归属，再决定是否需要重建聚合。这个建议是应用层的规则管理选择，不代表 PostgreSQL 会自动识别或迁移缓存。

什么情况下不该继续加大 stride

stride 必须大于零，而且不能包含月或更大的单位。把一个月填进去，不会得到业务月报所需的日历分界。月份长短不同；“固定跨度的格子”与“每月按某个本地日期开始”是不同需求。遇到后者，应重新选择日历模型，不要用三十天冒充所有月份。

官方文档提到，完整标准单位可以与相应的 date_trunc 得到相同结果。使用这句话时仍要保留锚点条件：边界必须对齐对应的标准单位。偏移了两分钟的十五分钟桶，本来就不是整刻钟；任意 origin 并不因为单位名称熟悉就获得相同边界。

若业务意图涉及本地时区中的循环时间，可接着阅读时间戳与循环日程的区别。当前例子只解决固定跨度与锚点，不能据此承诺夏令时下每个本地日历区间都具有相同持续时间。

十五分钟相同就能共享缓存桶键吗？

不够；还要确认 origin 在这个跨度上对齐，并统一输入时间类型与转换规则。缓存键可以使用一个明确的规则标识，再附上桶起点；它不应只凭一个看似完整的“十五分钟”标签掩盖剩余配置。

验证时保留边界前一秒、恰在边界、边界后一段时间，以及早于锚点的样本。再换一个偏移两分钟的锚点，重新推算预期，不要沿用旧答案。最后把零跨度、负跨度和月跨度作为拒绝探针，实际错误措辞留给真实执行记录。只有这些分界约定一致，比较两个服务的桶内数量才有意义。
