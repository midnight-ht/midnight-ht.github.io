CSS内层滚到底，为什么外层页面接着滚？

通过嵌套滚动静态对照区分边界传递、局部反馈与DOM传播，记录真实手势下内外容器的位移。

正文

核心要点

  • 边界策略属于实际滚动容器与相应轴。
  • contain保留局部反馈，none进一步约束它。
  • 程序滚动不能替代边界手势验证。

滚动链允许边界动作继续交给祖先滚动容器；在实际滚动容器上用overscroll-behavior可以控制这项边界行为，它不是DOM传播开关。鼠标还停在侧栏里，侧栏已经到底而外层页面继续移动，先找滚动链和边界，不必立即添加更多滚轮监听器。

CSS Overscroll Behavior Level1定义滚动链为滚动从一个容器传给祖先容器的关系，通常在滚动口到达边界时发生。本文依据页面标注的2026年6月30日编辑草案，比较auto、contain与none的相关行为，不把草案中所有取值或所有平台反馈当成已经通过的兼容结果。

先看谁到了哪条边界

假设右侧资料面板有自己的纵向滚动条，外面的文档也能滚动。用户在面板内继续向下滑动，面板到底后，动作可能由链上的祖先继续处理。事件目标仍在面板中，并不表示后续只能改变面板的scrollTop；描述滚动位置时需要同时记录内外两层。

标准把局部越界反馈与非局部边界动作分开。局部反馈可以是容器自己的回弹提示；滚动链传递或某些导航动作则会影响页面其他部分。contain禁止非局部边界动作，但不改变局部反馈应有的行为；none在此基础上也禁止局部反馈。若平台本来没有某种回弹，不应要求它为了对照实验先出现。

这与passive监听器能否取消默认动作是不同问题。那篇检查cancelable与当前监听器条件；本篇让滚动容器声明边界策略。stopPropagation控制事件传播，不能据此证明滚动链已经按预期停止。看见一个回调没传到外层，也不是外层没有滚动的证据。

给实际滚动容器做一个静态对照

下面完整HTML未在浏览器执行。外层限定高度并能滚动，内层面板也有自己的限制。先用auto观察，再只把内层取值改为contain，最后改为none。内容只是教学文字，没有接口、统计或真实业务任务。

<!doctype html>
<html lang="zh-CN">
<head>
<meta charset="utf-8">
<title>滚动链边界对照</title>
<style>
#outer { height: 24rem; overflow: auto; border: 2px solid; padding: 1rem; }
#panel { max-height: 8rem; overflow: auto; overscroll-behavior-y: auto; border: 1px solid; }
#panel ol { margin: 1rem; }
.spacer { height: 20rem; }
</style>
</head>
<body>
<h1>先滚动面板，再观察外层</h1>
<div id="outer">
  <p>这是可以继续滚动的外层。</p>
  <section id="panel" aria-label="教学资料说明">
    <ol>
      <li>核对资料身份</li>
      <li>查看当前版本</li>
      <li>检查适用范围</li>
      <li>确认说明完整</li>
      <li>记录需要追问的问题</li>
      <li>返回原任务</li>
    </ol>
  </section>
  <div class="spacer" aria-hidden="true"></div>
  <p>外层末尾。</p>
</div>
</body>
</html>

对照时先确认内层确实有滚动空间，外层尚未到底，并保持输入起点相同。在内层到达末端后继续真实手势，记录两者scrollTop和可见位置。若外层原本已经到底，三个取值都可能看起来“不动”，这个样本就没有区分能力。未发生变化不是边界策略正确的充分证据。

把属性写到包裹面板的装饰div上，也可能没有作用。标准要求不是滚动容器的元素接受但忽略这个属性；它不会替你建立滚动区域。应检查计算后的overflow、实际尺寸与产生滚动的位置，而不是看到样式表有contain就关闭问题单。sticky与滚动祖先提供了另一种定位容器的办法，但粘附正常不证明边界动作正确。

取值也要按轴检查。纵向滚动链问题可以只约束y轴，避免把横向导航或局部反馈一并改掉。双轴手势需要各自考虑；在一种触控板操作下成功，不意味着触屏、滚轮和键盘路径都已验证。规范约束与产品支持矩阵应分别记录。

用脚本把scrollTop推到末尾，能测出滚动链吗？

不能单凭它。标准说明程序滚动被夹取，不触发边界默认动作。脚本可以帮助把内层准备到末端，但随后仍需实际输入来观察边界处理。只执行scrollTop等于最大值，再检查外层没动，不能证明用户继续滑动时不会传递。

同样，不要用一个自行构造的wheel事件替代真实输入，然后从defaultPrevented推断设备滚动结果。边界动作是用户代理针对滚动实现的行为，不是日志里一个布尔标志。验收应留下输入设备、动作方向、落点和当时两个容器的位置，才能复查观察属于哪条路径。

内容短到不能滚动时一定无效吗？

不能这样概括。标准将某轴没有滚动潜力的滚动容器视为处于边界；它与根本不是滚动容器的元素不同。先确定元素在那个轴上的容器性质，再讨论边界策略。删除多余内容、展开说明或改变窗口高度，都可能改变现场条件，不宜只靠滚动条是否可见来判断。

这也影响空结果面板的设计。原来长列表里的contain安排，到了只有一行提示时是否仍符合任务，要按实际计算样式与输入检查。若用户直接在面板外操作，动作也不必经过内层链。因而contain不是模态弹窗的全局背景锁，更不能替代外部焦点与交互限制。

可以把同一份面板切成两种内容来排除误判。长内容时，先让内层停在中间，继续向下操作应先消耗它自己的空间；只有到末端继续动作，才进入本篇讨论的边界。若从中间操作就带动外层，先查落点是不是面板、尺寸是否真的限制住内容，不能拿一个边界属性解释整个输入过程。

短内容时不要沿用长列表的观测表。记录内层没有可消费的纵向距离，以及它是否仍由overflow形成滚动容器，再把指针移到外层空白处做一组对照。后者允许外层移动并不反驳内层策略，因为动作起点没有经过内层。这样可以区分“短列表边界约束仍在”和“全页任何位置都不能滚动”两份完全不同的需求。若产品真正要求后者，需要先重新定义交互范围，而不是继续调大这个属性的力度。

选择contain还是none，应由是否需要保留局部越界提示决定。若只想让侧栏不带动文档，禁掉所有反馈可能超出需求；若产品刻意管理自己的越界提示，应说明为何需要更强的限制。本文没有测量滚动性能或输入延迟，不把改成CSS写成已获得某个速度收益。

待执行检查保留auto、contain、none三份输入条件，再加入非滚动包裹层、短内容与面板外输入作为反例。记录计算属性、实际边界和内外位移，失败时先判断有没有走到可区分的边界。交付的结论应是某个容器在某个轴如何处理边界，而不是一句“页面已经锁住”。
