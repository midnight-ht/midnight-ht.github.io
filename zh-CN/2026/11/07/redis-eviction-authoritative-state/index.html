缓存和业务真相共用Redis前，先安排内存耗尽的结果

从Redis内存耗尽时的驱逐或拒写结果选择缓存与业务权威的放置，比较allkeys、volatile、noeviction的候选范围及可观察证据。

正文

核心要点

  • TTL不保证键在内存压力下至少保留到截止。
  • volatile策略仍可能选择带期限的关键记录。
  • 避免驱逐后还需处理写入拒绝，不能把异常吞成受理成功。

把缓存和业务唯一记录放进同一个 Redis 实例之前，要先决定内存耗尽时允许丢什么、允许哪次写入失败。TTL 不是最低保留保证；改成 noeviction 也不会增加容量，而是把部分压力转成写入错误。

假设一个实例同时保存报表缓存、已受理任务，以及用于识别重复扣款的记录。开发者给缓存设置一分钟期限，给去重记录设置一天期限，认为后者至少能保留一天。若策略允许驱逐带期限的键，这个假设就不成立。以下按当前官方 Key eviction 指南分析容量策略，没有连接 Redis、制造内存压力或实际扣款。

先区分到期与容量驱逐

Redis 键驱逐指南说明，当用于比较的数据内存超过 maxmemory 时，服务器根据配置的策略驱逐键。到期回答的是期限到达后怎样处理，驱逐回答的是容量压力下哪些键可以提前移除。即使写入时正确保留了 TTL，第二套机制仍可能让键先消失。

本站二〇二六年十一月五日的SET 与 TTL 替换规则处理的是更新命令怎样保留或改变期限。本篇假设期限本身没有写错，仍要讨论容量策略。只修封装函数的 KEEPTTL，不会改变实例选择淘汰哪些键的规则。

allkeys-lru 的候选范围包括所有键，不会因为一个任务键没有期限就自动保护它。volatile-lru 只从带期限的键中选择，因此本例的一天去重记录也可能属于候选。永久任务记录不在这个候选集，并不代表整个实例会一直允许新写入；官方指出，volatile 系列没有符合条件的键时，行为类似 noeviction。

这里必须把“属于候选”与“确定下一个被删”分开。指南解释 LRU 使用近似采样，不应根据一小组键的顺序写出固定淘汰预测。给某个业务键多读几次，也不能成为它绝不会被驱逐的证明。选择策略之前，先确认失去每种键会导致重新计算、暂时查库，还是不可恢复地失去业务事实。

三个键，检验策略与数据角色是否相容

下面是完整、未执行的 Python 3 候选集合例子。它不实现 Redis 的内存核算，也不模拟 LRU。三个 TTL 仅表示是否有期限，不表示本机经过这些秒数；预期集合独立写出，以检查 allkeys、volatile 和 noeviction 的候选范围。

"""Unexecuted policy eligibility illustration. No Redis connection.
It does not predict approximateLRU choice or emulate memory accounting.
"""
keys = {'cache:report': 60, 'task:accepted': None, 'dedup:charge': 86400}
def eligible(policy, key_ttls):
    if policy == 'allkeys-lru':
        return set(key_ttls)
    if policy == 'volatile-lru':
        return {k for k, ttl in key_ttls.items() if ttl is not None}
    if policy == 'noeviction':
        return set()
    raise ValueError('Unsupported teaching policy')
expected = {
 'allkeys-lru': {'cache:report', 'task:accepted', 'dedup:charge'},
 'volatile-lru': {'cache:report', 'dedup:charge'},
 'noeviction': set(),
}
if __name__ == '__main__':
    for policy, oracle in expected.items():
        assert eligible(policy, keys) == oracle
        print(policy, sorted(oracle))
    # No eligible victim does not imply successful new-data writes.

结果的业务含义比集合本身更重要。cache:report 可以从持久来源重建，丢失可能只是一次额外查询。task:accepted 若是唯一受理回执，丢失可能让用户无法查到已经接受的任务。dedup:charge 若是唯一重复识别依据，丢失后旧请求再次到达，可能被当成新意图。这个扣款例子是假设风险，不是对某个支付系统的事故报告。

volatile-lru 看起来把永久任务记录保护起来了，却仍把带一天 TTL 的去重记录放进淘汰候选。若开发者只是把这个键改成永久，又必须面对候选耗尽后新写入失败的处理。数据是否可重建，不能由“这个键叫缓存”或“已经设置了过期”来决定；要指出可靠来源及重建期间调用方的状态。

noeviction 把风险转移到写入路径

官方指南说，noeviction 不驱逐键，但尝试缓存新数据的命令会收到错误，只读取已有数据的命令仍可工作。由此选择它时，应用必须检查写入结果。后台捕获异常后仍返回“任务已受理”，会让一个明确可见的容量错误变成业务记录缺失。

这不是建议把全部状态都放进一个 noeviction 实例。若报表缓存挤占容量导致受理记录写不进，两个数据角色仍在竞争同一份资源。指南建议在可能时把缓存与持久键分到不同实例；这样可以分开策略及容量预算，但不会自动建立备份、故障恢复或业务权威。是否拆实例，应按失败后果和操作成本决定。

本例更直接的设计选择，是让任务受理与去重的权威记录由满足相应提交要求的持久层保存；Redis 可以辅助查询，但 miss 时不能擅自推出“任务从未受理”或“这一定是新请求”。如果去重同时涉及外部系统，还需其自己的身份与查询合同。这里不重做一份通用持久化教程，关注的是容量策略是否允许这个唯一记录消失。

内存预算也不能只填主机物理内存大小。指南说明，复制或 AOF 使用的一些缓冲不计入触发驱逐的比较值；INFO memory 中的 mem_not_counted_for_evict 可用于观察。于是 maxmemory 不是整个进程永不超过的硬上限，留给缓冲、客户端和运行环境的余量需要真实观测，本文没有给一个未经测量的百分比。

evicted_keys 没有增加，就能证明键一定过期了吗？

不能。显式删除、值替换、命名空间错误或连到了另一个实例，也会造成查不到。应结合 expired_keys、实际写入路径与实例身份调查；累计计数不是每条键的因果记录，不能给某个缺失键自动贴上“已过期”的标签。

可以先做只读核对，下面这些 redis-cli 命令没有在本文执行，也不修改共享实例的全局设置。连接参数应由使用者按授权环境提供，不把凭据写进文章或日志。

redis-cli CONFIG GET maxmemory
redis-cli CONFIG GET maxmemory-policy
redis-cli INFO memory
redis-cli INFO stats
redis-cli INFO commandstats

观察时记录时间窗口，再比较驱逐、到期及命令拒绝的变化，同时核对应用实际读写的是哪个实例。若需要验证压力路径，应另建可丢弃实例，明确服务端版本与配置，分别观察缓存可重建、关键写入报错是否传回，以及调用方是否保留查询入口；本文没有运行这组实验。

UNLOGGED 的可重建数据边界讨论另一种失效条件。本篇的结论落在运行中的容量选择：允许驱逐的键应有可接受的缺失路径，拒绝驱逐的实例应有可解释的拒写路径。没有这两种结果合同，延长 TTL 只是改变一个数字，不能替业务保存承诺。
