History pushState改了地址，popstate为什么没触发？

区分历史写入与遍历恢复，用完整双视图页面核对URL、state、正文和初始条目，保留直达加载边界。

正文

核心要点

  • 写入历史不会自动执行应用渲染。
  • 按钮导航与遍历恢复共享明确视图规则。
  • 同文档更新不证明刷新或服务端直达。

pushState增加历史条目，但调用它本身不触发popstate；前进操作应主动渲染，后退与前进恢复再接同一渲染入口。地址栏已经变成详情，正文却仍停在摘要时，先检查是谁负责画出新视图，而不是延长对事件的等待。

popstate事件说明明确区分写入与遍历：仅调用pushState或replaceState不会触发该事件，浏览器后退、前进等遍历则可以触发。事件通知不是“历史数据一有变化就重画”的订阅器。把它当作所有导航入口，会漏掉应用主动发起的那一半。

一次切换有三份状态需要对应

假设教学目录有摘要与材料两个视图。按钮切换后，URL可以用于复制或重新进入，history.state帮助恢复会话条目，可见正文让用户知道现在在哪一页。三个位置相关，却不会由浏览器替应用自动同步。只写pushState改变了历史，仍需要明确调用渲染逻辑。

HTML共享历史写入算法会序列化传入的数据，并检查文档与URL改写条件。它不规定应用的标题、列表和错误提示怎么更新。页面标题与视图身份已说明标题应该跟随当前主题；本篇补上主动导航和历史恢复如何进入同一份规则。

应先决定哪些操作值得增加历史条目。进入另一份可返回的视图，可以使用push；只修正当前条目的状态或初始化登记，可能适合replace。若每次按键都增加条目，后退可能需要经过很多中间输入；若所有操作都replace，又可能抹掉用户期待的返回点。这个取舍来自任务，不是哪个方法更先进。

一个完整的同路径查询视图样本

以下HTML未执行。请通过同源HTTP服务提供该文件，再在浏览器中打开；例如从文件目录运行静态服务器。不要据此假定file协议具有相同URL改写条件。样本只改变当前文件的查询参数，没有form、fetch或真实材料接口，也没有实现通用路由器。

<!doctype html>
<html lang="zh-CN">
<meta charset="utf-8">
<title>教学目录</title>
<nav aria-label="教学视图">
  <button type="button" data-view="summary">摘要</button>
  <button type="button" data-view="documents">材料</button>
</nav>
<main><h1 id="heading"></h1><p id="note"></p></main>
<script>
const views = new Map([
  ['summary', ['摘要', '这是教学目录摘要。']],
  ['documents', ['材料', '这里只列教学材料，没有真实申请。']]
]);
const [menu, heading, note] = ['nav', '#heading', '#note'].map(
  selector => document.querySelector(selector)
);
function fromURL() {
  const key = new URL(location.href).searchParams.get('view');
  return views.has(key) ? key : 'summary';
}
function render(key) {
  const [title, text] = views.get(key);
  document.title = title + '｜教学目录';
  heading.textContent = title;
  note.textContent = text;
}
const initial = fromURL();
history.replaceState({ view: initial }, '', location.href);
render(initial);
menu.addEventListener('click', event => {
  if (!(event.target instanceof Element)) return;
  const button = event.target.closest('button[data-view]');
  if (!button || !menu.contains(button)) return;
  const key = button.dataset.view;
  if (!views.has(key)) return;
  const next = new URL(location.href);
  next.searchParams.set('view', key);
  history.pushState({ view: key }, '', next);
  render(key);
});
window.addEventListener('popstate', event => {
  const saved = event.state?.view;
  render(views.has(saved) ? saved : fromURL());
});
</script>
</html>

样本初始化时先从允许的URL视图读取状态，给当前条目登记一份小对象，再渲染。按钮路径写入以后直接render，不等待popstate；遍历路径则检查保存状态，必要时回到允许的URL解释。恢复入口没有直接读取event.state.view，所以空状态不会仅因没有对象就触发属性访问错误。

这份URL回退有明确范围：只有两个已知视图，未知值回到摘要。它不是对任意路由数据的信任规则。真实系统若需要读取某个申请，应先验证路径身份、授权与加载结果，再展示相应对象；history.state里的一个编号不能替服务端批准访问。样本没有这些业务能力。

一个有用反例是删掉按钮路径最后的render。此时地址和state改变，正文不跟着变，继续等待也不会由这次push自动补来popstate。另一个反例是只在按钮里更新标题、不处理遍历：后退恢复URL，旧详情标题仍可能残留。两类缺口应该在入口清单中分别定位。

还可以在纸面上给条目标号，防止把“返回摘要”与浏览器后退混为一谈。初始摘要记为甲，初始化的replace只给甲补状态；点击材料产生乙，再点击摘要产生丙。此时浏览器后退到乙，应恢复材料，而不是因为最近按过摘要按钮就继续画摘要。再次后退到甲，才回到最初摘要。两条记录可以显示同样内容，但在历史栈里仍是不同位置。

若材料页只是纠正自己的显示选项，选择replace会修改乙而不增加一格；随后后退仍回甲。相反，用push保存这项纠正，就增加一个用户需要越过的返回点。这段推演不要求向状态里塞入整份页面：只要视图键能够按规则恢复即可。验收表因此应给每一步标明“新增条目、修正当前条目或遍历”，再比较URL与实际正文，不能只凭两个画面相同推断历史行为相同。

state能直接放DOM节点或函数吗？

不能把它当作任意对象容器。标准执行面向存储的结构化序列化；方法参考将不可序列化状态列为DataCloneError。保留小而明确的视图数据，比把整个组件或事件对象交给历史记录更容易解释。不要依赖状态对象保留原来的函数行为、DOM身份或外部资源。

序列化也不意味着适合保存秘密。状态可能被浏览器保留，URL又可能进入历史、分享和日志。选择哪些字段可以出现在这些位置，需要真实产品判断；本文的教学键只有公开视图名称，不把这个例子扩展成敏感资料存储建议。状态恢复只恢复导航依据，不恢复全部业务事实。

最初那条记录可能没有应用状态，因此初始化与旧条目回退需要各自安排。样本用replaceState登记当前条目，不额外增加一个重复的首页；仍保留URL回退，是因为实际入口可能来自旧记录或其他导航。不要为了消除null就把每个未知状态强行解释成最近一次成功对象。

URL更新后，刷新为什么还可能失败？

pushState方法参考说明，调用不会立即加载新URL，但浏览器之后可能尝试加载它。因此，一个客户端切换成功，不能证明服务器或静态托管已经知道那个地址。本例保持同一文件路径，只改查询，刻意缩小了这个部署前提。

若真实应用改成新的路径，需要另验直达、刷新、错误路由和资源相对地址。URL基地址解析解释了路径组合的独立语义。用一个全局成功页面掩盖所有404，不等于目标视图真的恢复；应核对页面对象、正文与返回状态，而不是只看HTTP200。

待执行验证从初始无状态条目开始，依次进入材料、返回摘要、浏览器后退和前进，每步记录完整URL、state、标题与正文。加入未知view和空state，检查预期回退；再单独刷新当前地址。实际浏览器可能有交互条件或其他历史行为，本文没有运行这些路径，不伪造事件计数。

交付前应能说明每一种入口由谁写历史、由谁渲染、失败时显示哪个视图。主动写入与遍历通知接回同一个明确状态规则，才能让地址栏与眼前内容一起成为可恢复的导航，而不是两份偶然一致的字符串。
