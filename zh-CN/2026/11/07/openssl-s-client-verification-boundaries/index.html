OpenSSL s_client 握手成功，为什么证书验证仍可能失败？

用未执行的本地证书脚本区分 OpenSSL 握手、可信链、预期名字与错误返回，避免把诊断输出当验收。

正文

核心要点

  • 诊断客户端可以在校验错误后继续。
  • SNI、信任材料与预期身份各有职责。
  • 证书列表不是验证过的链。

用于诊断的 OpenSSL s_client 默认可以在证书验证错误后继续。把它用于接受检查时，要明确受信来源、错误返回策略和预期主机名；发送 SNI 或打印证书列表都不能代替这几项验证。终端显示协商信息，不应直接写成 TLS 身份验收通过。

诊断工具为什么容忍错误继续

OpenSSL 3.6 的 s_client 手册说明，这个工具为了展示证书链问题，可以在验证错误后继续；verify_return_error 会让验证错误返回，并通常以致命错误终止握手。本文引用的是三点六文档路径，不是对读者本机版本的探测，也没有连接任何服务器。

假设一台机器返回了证书，双方还协商出了密码套件。它说明某些协议步骤发生过，不说明证书链来自接受的根，也不说明证书代表调用者期待的名字。诊断输出包含多个不同结论，不能只截取一行看起来成功的文字。应先定义本次检查想接受什么，再决定哪些结果能够支持它。

至少分清四项输入：连接地址决定网络去向，SNI 帮助服务端选择虚拟主机，受信材料参与证书链验证，预期名字参与身份匹配。它们可以在常见调用中看起来相似，却没有因此变成同一个控制。尤其从 IP 连接到本地端口时，网络地址与希望核验的 DNS 名字本来就可以不同。

一个只在本机使用的完整教学脚本

以下脚本未执行，没有实际生成证书或成功握手记录。它要求可用的 OpenSSL 3.6 命令、常规 shell，以及空闲的本地端口；只在新建目录生成一天有效的教学材料，不安装到系统信任库。为避免依赖外部 DNS，证书名字使用 localhost。私钥不加密只为本地一次性例子，不能拿作真实服务配置。

保存为 tls-demo.sh 后，在独立练习环境中用 sh 调用。准备步骤遇错停止；探针步骤允许预期失败，并立即保存每个客户端退出值。脚本最后的整体结束不代表四项探针都通过，判断应读取各自记录。

set -e
tls_demo_dir=$(mktemp -d)
cd "$tls_demo_dir"
tls_endpoint=127.0.0.1:18443
tls_name=localhost
tls_root_cert=root.pem
tls_other_cert=other.pem
make_request() {
  tls_material=$1; tls_subject=$2
  shift 2
  openssl req -newkey rsa:2048 -noenc -keyout "$tls_material.key" \
    -subj "$tls_subject" "$@"
}
make_request root '/CN=Demo Root' -x509 -days 1 -out "$tls_root_cert" \
  -addext 'basicConstraints=critical,CA:TRUE' \
  -addext 'keyUsage=critical,keyCertSign,cRLSign'
make_request other '/CN=Other Root' -x509 -days 1 -out "$tls_other_cert" \
  -addext 'basicConstraints=critical,CA:TRUE'
make_request server '/CN=localhost' -new -out server.csr
printf '%s\n' 'subjectAltName=DNS:localhost' \
  'basicConstraints=CA:FALSE' 'extendedKeyUsage=serverAuth' > server.ext
openssl x509 -req -in server.csr -CA "$tls_root_cert" -CAkey root.key \
  -CAcreateserial -out server.pem -days 1 -extfile server.ext
openssl s_server -accept "$tls_endpoint" -cert server.pem \
  -key server.key -www > server.log 2>&1 &
tls_server_pid=$!
trap 'kill "$tls_server_pid" 2>/dev/null || true' EXIT
set +e
probe() {
  tls_case=$1; tls_trust=$2; tls_expected=$3
  shift 3
  printf 'GET / HTTP/1.0\r\nConnection: close\r\n\r\n' |
    openssl s_client -connect "$tls_endpoint" -servername "$tls_name" \
      -verifyCAfile "$tls_trust" -verify_hostname "$tls_expected" \
      -no-CAfile -no-CApath -no-CAstore -ign_eof "$@" \
      > "$tls_case.log" 2>&1
  tls_result=$?
  printf '%s status=%s\n' "$tls_case" "$tls_result"
}
probe diagnostic "$tls_other_cert" localhost
probe wrong_chain "$tls_other_cert" localhost -verify_return_error
probe wrong_name "$tls_root_cert" otherhost -verify_return_error
probe matched "$tls_root_cert" localhost -verify_return_error
printf 'inspect sandbox: %s\n' "$tls_demo_dir"

证书准备分别依据官方 req、x509 与 s_server 命令接口：请求、签发与服务监听不是客户端验证的替代。脚本用扩展文件把本地名字放进 SAN，再提供显式信任材料；它不假设一份 CSR 的扩展必然自动复制进证书。准备后应先检查实际证书内容，并确认后台服务真的取得本例端口，不能用另一个已运行服务的响应充当本次输入。

后台启动到可以接收连接之间也有时间差。如果探针先遇到连接拒绝，先核对 server.log 与进程状态，在确认本例监听后重做探针；这不是证书链错误，也不能被归入预期的 wrong_chain。HTTP 请求和连接关闭用于避免非交互客户端只因输入结束而提前离开，不能把协议关闭问题与身份验证混成一个失败类别。

四个记录应该怎样解释

diagnostic 使用不信任本例签发者的材料，但没有要求验证错误返回。它用来观察“出现错误后仍继续”的诊断行为，不应被计为接受通过。wrong_chain 增加返回错误策略，预期暴露链不受信；wrong_name 信任本例根，却故意使用不匹配名字，预期暴露身份错误。matched 才给出本例意图接受的根与名字。

这些都是纸面预期，不是四条真实日志。即使 matched 返回零，也要检查客户端实际读取的材料、名字、连接终点与对应日志，不能把网络失败、证书过期、端口冲突等其他输入省略。反过来，非零也不是证书问题的同义词，应保留诊断类别，而不只记录一个红色结果。

验证选项手册单列预期名字的验证参数。这个区分让负例可解释：保持同一个服务、同一份证书与信任材料，只改变预期名字，才是在比较身份匹配；同时换地址、根和名字后失败，难以知道哪一项造成结果。

每份记录还应明确“准备是否完成、连接是否建立、使用的信任文件、预期名字、校验诊断、客户端退出值”六项。准备失败时标为未进入探针；连接拒绝时标为传输前提不成立；只有真正收到本例证书，才继续解释链或名字的负例。这样另一位读者不会把四个非零值误当成四次验证器正确拒绝。

检查证书输入时，应查看签发者、有效期与SAN是否符合这次方案，而不是只确认文件有内容。若扩展文件没有进入签发命令，证书名字可能与文字说明不同；若一天有效期已过，正确名字也不足以让 matched 成立。出现这些情况应保留原材料并重新安排实验输入，不能删除错误日志后只留下匹配的一次。

还要把实际协商后的应用交互与身份接受分开。示例发送GET是为了让本地连接有明确的结束路径，不是在验收真实网站、浏览器策略或所有证书生命周期要求。接收HTML只说明这个教学服务回答过请求；信任根与预期名字仍需由各自记录解释。

SNI 名字与 verify_hostname 可以不同吗？

可以，它们是两个输入，但检查必须解释差异。SNI 请求服务端选择哪个虚拟主机，验证名字表达最终准备接受哪个身份。本例固定 SNI 为 localhost，却在 wrong_name 中改成另一个预期名字，正是为了避免把选到证书与接受证书混为一谈。

实际代理或专用访问路径可能有自己的身份设计，不能从本地例子推出所有不同值都正确，也不能把 SNI 填了当作匹配已经发生。记录这两个值及其来源，可以让评审者发现“连的是测试节点，检查的却是另一个业务名字”之类的输入错误。

showcerts 打印列表，就说明链可信吗？

不能。s_client 手册明确指出，它显示的是服务端按发送顺序提供的证书列表，不是验证过的链。打印出来有助于排查少发了什么或提供了哪张证书，却没有自动指定哪些根被接受。保存列表和保存验证结论应是两种证据。

二〇二六年十一月五日的SSH 主机身份文章处理另一种首次信任输入，本题则限定 TLS 诊断客户端的验证开关。两者都需要明确依据，但不能混用 known_hosts 与证书链的接受规则。先固定本次要信任什么、核验什么名字以及错误如何返回，再把结果接进发布检查。
