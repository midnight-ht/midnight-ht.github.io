Alertmanager 收到过 firing，为什么仍没有通知这条短告警？

用本地接收器与短暂、持续告警对照解释 Alertmanager 新组等待、后续周期与首发完整性的取舍。

正文

核心要点

  • 新组等待前恢复的告警不会为它发通知。
  • 新组首发与既有组后续处理不同。
  • 零等待不保证首发包含完整集合。

新告警组的 group_wait 到期前，如果某条告警已经恢复，Alertmanager 不会为它发送通知。先核对它进入哪一组、何时恢复，再把有意等待与投递失败区分开。收到过 firing，不等于已经产生一项必须补发的历史通知。

等待属于新组，不是每条消息自己的倒计时

Alertmanager 配置参考把 group_wait 定义为新组首次通知前的等待，并明确说明：在它结束前恢复的告警不会发送通知。等待可以容纳其他相关告警或抑制源先到达，也会过滤短暂波动。本文核对二〇二六年十一月六日的在线参考，没有连接任何告警系统。

假设一条故障告警已到达 Alertmanager，二十秒后恢复，而新组配置等三十秒。没有通知可以是按设计发生的结果，并不自动说明静默残留、receiver 断开或 Prometheus 没有 firing。反过来，同一现象也可能有其他原因，必须先保留到达记录与分组身份，不能仅凭手机安静选定原因。

组身份由实际路由和 group_by 等条件决定。下面按 cluster 与 alertname 分组，因此同组的不同 instance 可以出现在一份通知里。改变标签可能创建新组，改变路由也可能采用不同的继承配置；只比较 alertname 的显示文字，无法证明等待起点相同。

一份只向本地接收器发送的教学配置

以下完整配置和程序均未执行。要求独立 Alertmanager、Python 标准库及空闲本地端口，数据目录只用于本次练习。配置不包含外部接收器、真实告警或静默；它测试通知时序，不制造真实服务故障。

# alertmanager.yml
route:
  receiver: local
  group_by: [cluster, alertname]
  group_wait: 30s
  group_interval: 2m
  repeat_interval: 10m
receivers:
  - name: local
    webhook_configs:
      - url: http://localhost:18555/
        send_resolved: true

将下列程序保存为 receiver.py。它只打印本地收到的测试 JSON，返回成功响应；这些打印将来可以成为接收证据，但本文没有产生这样的记录。

import json
from datetime import datetime, timezone
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

class Receiver(BaseHTTPRequestHandler):
    def do_POST(self):
        size = int(self.headers.get("Content-Length", "0"))
        payload = json.loads(self.rfile.read(size))
        print(datetime.now(timezone.utc).isoformat(), payload, flush=True)
        self.send_response(200)
        self.end_headers()

ThreadingHTTPServer(("localhost", 18555), Receiver).serve_forever()

先在一个终端运行 python receiver.py；另一个终端从练习目录启动独立 Alertmanager。确认所用程序支持这些参数，并且两个进程都属于本次沙盒；不要向已有生产实例提交测试告警。

alertmanager --config.file=alertmanager.yml \
  --storage.path=./alert-data --web.listen-address=localhost:19093

准备完成后，第三个终端可保存并运行下面的 driver.py。官方 API v2 定义规定告警输入的 labels、startsAt 与 endsAt。脚本打印的是提交响应，不等于接收器已得到通知；若提交失败，应停止并保存真实错误。

import json
import time
from datetime import datetime, timedelta, timezone
from urllib.request import Request, urlopen

endpoint = "http://localhost:19093/api/v2/alerts"

def current_utc():
    return datetime.now(timezone.utc)

def as_timestamp(value):
    return value.isoformat()

start = current_utc()

def alert(cluster, instance, begins, ends):
    return {"labels": {"alertname": "TimingProbe", "cluster": cluster,
                       "instance": instance},
            "startsAt": as_timestamp(begins), "endsAt": as_timestamp(ends)}

def post(items):
    request = Request(endpoint, data=json.dumps(items).encode(),
                      headers={"Content-Type": "application/json"}, method="POST")
    with urlopen(request, timeout=5) as response:
        print("submission-status", response.status, flush=True)

post([alert("A", "one", start, start + timedelta(minutes=5)),
      alert("B", "one", start, start + timedelta(minutes=5))])
time.sleep(20)
post([alert("A", "one", start, current_utc())])
time.sleep(25)
later = current_utc()
post([alert("B", "two", later, later + timedelta(minutes=5))])

这份驱动让 A 的同一标签身份在首次等待结束前恢复，B 则持续到等待之后，再向 B 的既有组增加第二个实例。执行器的 sleep 不是精确事件时刻证明；要用实际提交、Alertmanager 状态与 receiver 时间对齐。练习结束在各自终端停止两个自有前台进程，保留输入与日志，不把进程退出当作历史通知已经补发。

三十秒与两分钟分别从哪里计算

纸面预期是 A 不产生该条告警的通知，B 在新组等待结束后才进入首发通知处理。第二个 B 实例较晚到达，错过初次等待，应由后续 group_interval 路径考虑，而不是给它单独重新计三十秒。接收时间还受通知处理与本地 HTTP 响应影响，不能把配置相加后宣称精确某秒送达。

官方参考把 group_interval 描述为首次等待之后的周期检查：新活动或已恢复的变化影响是否发送后续通知；没有变化时还会检查重复间隔。因此本例的十分钟 repeat_interval 不是短告警的历史重放开关。它不能让从未发送过的每个短事件自动成为待补发消息。

验证时应保留 A 与 B 的完整标签、首次组建立、恢复或加入时点，以及每份接收 JSON 中的告警身份。只看到一份 B 通知，不足以说明 A 在哪一步被处理；只看到 API 返回成功，也不证明路由与receiver正常。持续告警 B 是同路径对照，让“没有任何通知”这类采集故障更容易与短事件策略区分。

对齐时点时，不要直接把startsAt当作新组等待的起点。输入里的开始时间描述告警，组还需要真正到达当前路由后才有处理身份。若驱动提交变慢，二十秒sleep并不证明Alertmanager已经观察到二十秒；应保存实际请求响应时间与组状态，再判断恢复是否发生在首次等待之前。

可以用三条诊断分支避免误归因。第一条，API没有成功接受输入，接收器安静只能说明测试前提未建立；先查提交错误。第二条，API已接受、A的组存在且等待前恢复，B持续对照正常收到，支持短事件策略解释。第三条，B也持续活动却没有接收记录，则继续核对实际路由、静默/抑制状态与HTTP投递错误，不能拿A的预期无通知替整条链路背书。

同一个receiver地址还不够证明两条告警走同一路由。应核对保存的实际配置、继承的计时值与完整分组标签。旧数据目录可能保留先前状态，因此示例要求新目录；如果重复练习，应让新的测试身份与之前分开，并记录这一变化。不能把旧组已有的计时状态当作新组三十秒测试的输入。

在接收JSON里，检查的是实际出现哪些告警身份与状态，而不仅是HTTP请求次数。一份通知可以包含多个实例，多次投递也可能与通知处理有关；把请求数直接当告警数，会误解本例的加入和恢复。保留完整人工样本是为了核对这种关系，不应用同样方式默认记录真实告警中的敏感业务字段。

把 group_wait 设为零，就能保证首条通知完整吗？

不能。相关告警或抑制源可能还没有到达。官方文档指出，过短等待可能让首条通知不包含预期的完整集合，也可能错过本应先到的抑制条件。去掉等待只改变一个时间窗口，不会保证网络及时或接收端成功。

选择因此需要看响应风险。必须尽快行动的告警可能容忍后续补充信息，短暂波动则可能不值得每次打断值班。应在实际标签与路由下比较策略，而不是把零秒或某个默认值当成所有服务的最佳答案。静默、抑制、分组与规则持续时长各有对象，不能一起随意缩短来追求“终于响了”。

二〇二六年十月三十一日的静默与规则状态文章解释人为通知抑制，本篇限定新组的等待。先证明告警到了哪一组、等待是否结束及恢复发生在何时，再决定调通知窗口还是修投递链路；一条短告警没有通知，不足以单独宣布系统漏报。
