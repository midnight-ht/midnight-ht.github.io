Iceberg最新快照不用的文件，为什么还不能删除？

用共享文件的两快照引用图区分Iceberg快照过期和孤儿清理，解释历史回溯、在途写入与路径表示对删除选择的影响。

正文

核心要点

  • 最新快照未引用的文件仍可能被保留历史使用。
  • 快照过期与孤儿清理处理不同来源的文件。
  • 写入时长和路径身份必须进入孤儿清理条件。

Iceberg 最新快照没有引用的文件，仍可能被保留的历史快照使用。删除前要检查表的引用关系，并区分快照过期与孤儿文件清理；仅按文件年龄或当前查询结果判断，会把回溯能力一起删掉。

假设一次合并把旧数据文件换成了新文件，最新查询正确，存储占用却没有立刻下降。此时需要先决定团队还要保留哪些历史版本，而不是直接对目录执行“只留最新”。本篇核对的官方文档选择器显示 Latest 1.12.0，网址中的 latest 会变化，所用原始内容已保存摘要；没有连接数据湖、运行维护操作或删除文件。

文件是否仍有用，要看保留的引用

Apache Iceberg 的可靠性说明介绍，快照记录表所需的数据文件集合，不同快照可以复用元数据和文件。提交通过原子操作切换当前表元数据，读者基于一致快照读取。这解释了为什么新版本出现后，旧文件并不自动变成废物：仍然有效的历史快照可能需要它。

这也意味着，目录列举不是表内容的唯一权威。一个文件存在于对象存储，只说明对象存在；它可能属于当前快照、仅属于历史版本，也可能是未提交任务的产物。反过来，当前查询没有读它，不能证明没有其他被保留的引用。清理对象和查询数据是两项不同的判断。

官方维护指南的快照过期说明把 expireSnapshots 用于过期历史快照，并说明过期后相应版本不再可供时间旅行查询。数据文件要等到不再被需要保留的快照引用，才可能删除。因此“过期一个快照”与“删除这个快照里出现过的全部文件”绝不是同一个集合操作。

两个快照，足以看出错误的删除集合

下面完整、未执行的 Python 3 例子只有两个假设快照。s1 使用 a 和 b，s2 使用 b 和 c，当前版本是 s2。预先写好的目标是：保留两者时可达集合为 a、b、c；只保留 s2 时为 b、c。共享文件 b 不会因为 s1 退出历史就可以删除。

"""Unexecuted local set example. It never enumerates or deletes real files.
Not an Iceberg maintenance implementation. Real refs/branches/tags need tooling.
"""
snapshots = {'s1': {'a', 'b'}, 's2': {'b', 'c'}}
def reachable(retained):
    return set().union(*(snapshots[name] for name in retained))
listed = {'a', 'b', 'c', 'pending-x', 'orphan-y'}
active_writer_files = {'pending-x'}
ages_hours = {'pending-x': 2, 'orphan-y': 96}
expected_before = {'a', 'b', 'c'}
expected_after = {'b', 'c'}
expected_orphan_candidates = {'orphan-y'}
if __name__ == '__main__':
    assert reachable(['s1', 's2']) == expected_before
    assert reachable(['s2']) == expected_after
    candidates = {p for p in listed - reachable(['s1', 's2'])
                  if ages_hours[p] >= 72 and p not in active_writer_files}
    assert candidates == expected_orphan_candidates
    print(sorted(candidates))

a 是最容易误判的对象。它不在当前 s2 的集合里，但保留 s1 时仍有用途。如果维护脚本只保留当前文件，就会让 s1 的回溯依赖失效。成功过期 s1 后，在这份只有两个快照的教学图中，a 才失去快照引用。真实表还可能有分支、标签及其他需保留的引用，不能把这个简化集合函数当作完整维护实现。

代码另列出 pending-x 与 orphan-y。前者假设是活跃写入者已经上传、尚未提交的文件，年龄两小时；后者假设为四天前失败任务遗留，已知没有表引用。例子只把 orphan-y 列为候选，没有删除任何东西。这里采用七十二小时仅为展示官方三天默认值，不能据此推导所有超过三天的对象都可安全删除。

即使本地集合断言通过，也只证明教学输入对应这些集合，不证明真实存储中没有漏列的引用、错误路径或并发写入。生产维护应使用所选引擎与版本支持的 Iceberg 操作，并核对其引用与保留规则；本例不提供绕过表元数据的通用 rm 脚本。

快照过期和孤儿清理，解决不同来源的占用

维护指南把 deleteOrphanFiles 用于清理没有被表元数据引用的遗留文件，例如任务失败留下的对象。快照过期清理的是历史引用生命周期；孤儿清理处理的是不在这套引用关系中的对象。只运行其中一个，未必能解决另一种来源的占用，但也不该因空间没有下降就提高删除力度。

最长写入时间是孤儿清理的重要前提。官方明确警告，保留区间短于一次写入完成所需时间，可能把在途文件误判为孤儿并破坏表。若一个长任务持续四天，三天默认值就不能成为安全证明。应核对真实任务持续时间、重试和暂停方式，再决定保留与维护的协调合同。

空间目标同样要具体。需要缩短可回溯历史，就讨论快照保留；需要处理失败作业遗留，就调查孤儿来源；需要减少小文件，则是合并数据文件的另一种维护。本篇不承诺能节约多少存储，也不把一次操作完成等同于全部容量问题结束。本站数据库空间复用与文件收缩讨论另一种存储机制，提醒维护指标必须和目标对应，不能直接套用其 PostgreSQL 命令。

文件路径换了写法，还能直接执行孤儿清理吗？

应先停止把无匹配当成可删除，核对元数据内的路径与文件系统列举的字符串形式。维护指南特别警告，同一文件的 authority 变更可能使历史 URL 与当前列举不一致，导致清理误删。延长保留期不能修复这种对象身份不一致。

例如迁移后，同一份文件通过新的 HDFS authority 被列举出来，但表中仍保留旧写法。维护工具若按字符串比较，新的列举项可能看起来没有引用。这里的例子只是解释官方警告，不声称所有存储都会发生这种迁移。实际执行前必须以目标文件系统与工具的表示方式核对，不能只比较去掉前缀后的文件名。

拟议验收先在可丢弃表产生两个共享文件的快照，保存快照标识及文件引用。保留历史时验证旧快照可读；按批准的历史保留策略过期后，再检查新旧查询与文件引用变化。孤儿对照应另建失败任务遗留，并确保没有真实写入仍在使用它；如引擎提供预览能力，先核对具体版本支持，不能把未验证的参数当作已存在的安全开关。

检查结束的证据应包括操作版本、保留策略、引用集合、实际查询结果与存储变化。文件消失本身不证明表仍正确，当前查询成功也不证明历史恢复仍可用。恢复演练的业务终点讨论这一类证据差别；本篇没有执行这些检查，交付的是引用演算和维护选择依据。
