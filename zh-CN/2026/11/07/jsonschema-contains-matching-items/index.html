contains 验证通过，为什么数组里还能有坏元素？

contains 计数匹配元素，items 约束所有元素，总长度由另一组规则控制。用恰好一个主记录的完整模式区分三层验证与同对象适用边界。

正文

核心要点

  • 匹配子集通过不代表所有元素都合法。
  • 匹配数量和数组总长度是独立约束。
  • minContains/maxContains 需要同一模式对象里的 contains。

contains 验证通过，不代表数组里每个元素都合法。它检查有多少元素匹配指定子模式；要同时保证所有元素的结构，还需要 items 等独立约束。把“存在合格元素”当成“整个数组合格”，会让不匹配的坏元素混进来。

JSON Schema Draft 2020-12 的 contains 条款描述的是匹配元素。这里固定使用这个方言，再把元素形状、匹配数量和数组总长度分别写清。例子是规则推演，没有执行验证器，也没有把前端选择控件的行为当成服务端模式验证。

一个主记录，不等于只有一个记录

设接口接受一组路由记录，每项都有字符串 id 和角色 role。角色可以是 primary 或 secondary，数组必须恰好有一个主记录，总共允许二到四项。这个需求包含三种不同的计数对象：所有记录的形状、主记录的数量、全部记录的数量。

下面是完整模式。items 对每一项施加对象约束；contains 只识别主记录；匹配数量上下限都设为一；总项数另外限制。属性名和示例标识符都是虚构输入，不涉及真实路由配置。

{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "array",
  "minItems": 2,
  "maxItems": 4,
  "items": {
    "type": "object",
    "required": ["id", "role"],
    "properties": {
      "id": { "type": "string" },
      "role": { "enum": ["primary", "secondary"] }
    },
    "additionalProperties": false
  },
  "contains": {
    "type": "object",
    "required": ["role"],
    "properties": { "role": { "const": "primary" } }
  },
  "minContains": 1,
  "maxContains": 1
}

contains 的子模式并没有重复要求 id，因为所有记录的基础形状已经由 items 负责。保留 required: ["role"] 则是为了明确匹配谓词：只有真正带有主角色的对象才算匹配。单写 properties 不会要求属性一定存在，不能借它推定一个缺少角色的对象自动不匹配。

逐个输入，看失败属于哪一层

先看正常输入：[{"id":"p","role":"primary"},{"id":"s","role":"secondary"}]。两个对象都满足基础形状，其中一项匹配主角色，总长度也是二，完整模式预期通过。次记录没有匹配 contains，并不是它验证失败；它只是不属于要计数的那个子集。

把第二项换成数字九，得到 [{"id":"p","role":"primary"},9]。主记录仍有且只有一个，contains 的数量要求仍可满足，但完整模式应因 items 拒绝数字而失败。这个输入就是反例：如果删除了 items，只留下数组类型、长度和主记录计数，数字就没有被基础形状规则排除。

再把两项都改成主记录。即使每一项都是合法对象，总长度也在范围内，两个匹配仍超过最大匹配数。反过来，两项都是次记录时，元素形状可以全部合格，却没有满足最低匹配数。一个验证结果不能抹平这些不同原因，否则给调用者的错误提示会让它修改错误的字段。

最后加入四个合法次记录和一个主记录。此时主记录数量仍是一，但总长为五，应因 maxItems 失败。maxContains: 1 没有承诺总长最多一，也不会替接口限制提交多少个次记录。若不设总长度限制，许多不匹配但合法的元素仍可能被接受，这需要由接口自己的资源约定决定。

边界值不能靠关键词名字猜

验证词汇表对 minContains 和 maxContains 的定义要求它们是非负整数。这里以规范条款为准，不把解释指南里宽泛的“数字”措辞扩张成可以写小数。版本支持也要明确，不能因为工具认得 contains 就推定它实现了所有相关关键词。

没有写 minContains 时，默认最低匹配数是一。显式写成零后，没有匹配元素也可能满足最低数量，但并不意味着所有数量检查都失效。如果同时写了最大匹配数，过多匹配仍应失败。例如最低为零、最高为一，零个和一个匹配可以满足数量范围，两个匹配仍不行。

这个结论还不能单独决定空数组是否通过。前面的完整模式另有 minItems: 2，即使把最低匹配数改成零，空数组仍会因总长度不足而被拒绝。调试时应逐条说明是哪一个约束否决输入，而不是看到一个参数为零就宣告整个模式允许空值。

没有 contains，minContains 还有效吗？

没有；它要求同一个 schema object 内有 contains。把最低匹配数写在外层，把 contains 移到另一层子模式，并不会自动让两个位置配对。语义上有关联的关键词也有结构适用范围，不能仅凭它们出现在同一个文件里就认为规则已经接通。

核验这个失败路径时，可以在完整模式的副本里删除同层 contains，保留最低与最高匹配数，再预测原来没有主记录的输入。匹配数关键词不再起作用，但 items 和总长度约束仍会执行。不要把这种试验结果概括成“验证器完全忽略了模式”，那会把仍然有效的规则一并漏掉。

验证器若输出匹配元素的注解，也不能假定找到第一个主记录就永远停止。核心规范要求相关注解覆盖所有匹配索引，计算完整匹配集合与只问是否存在不是同一个任务。本例不提供性能测试或提前终止优化；需要的是可解释的验证语义。

还要保留最外层的数组类型约束。匹配数规则不是把任意输入都转换成数组的操作；如果接口收到对象或字符串，应该由 type: "array" 直接拒绝，而不是等待一个面向数组元素的关键词替它完成类型检查。错误输入种类与合法数组内部的坏记录，需要分别进入测试集。

本例也没有要求标识符唯一。两个不同对象可以使用相同 id，只要角色和其他条件符合，当前模式并未声明应当拒绝它们。若业务需要按标识符去重，应另行制定相应规则，不要把“恰好一个主记录”误读成“所有记录身份都唯一”。明确没有表达的条件，可以防止调用方从一个通过结果推导出过多承诺。

保留一组能区分规则的测试输入

实际采用模式前，应选支持该方言的验证器，记录真正使用的工具和版本，再运行上述正常、坏次项、双主项、无主项和总长超限输入。尚未运行时，只把这些结果写成预期。若改变了模式中的最低匹配数或总长上限，也要重新推算对应输入，而不是复制旧报告。

元组前缀、其余元素与长度限制的另一种组合，可对照为什么 prefixItems 不限制元组长度。这里的决策则可以落到三句话：全体元素的形状由全体规则检查，特殊子集由匹配数量检查，总资源规模由总长度检查。任何一层的通过，都不能替另外两层作保证。
