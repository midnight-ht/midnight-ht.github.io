路径没变，fs.watch 为什么在文件替换后漏掉后续修改？

Linux/macOS 的文件监听跟随解析到的 inode，不自动转移到同路径替换文件。用自有临时目录观察，再把目录提示、空文件名和状态核对分开设计。

正文

核心要点

  • 相同路径名不代表原监听自动跟随新 inode。
  • 回调没有文件名时仍需要范围核对等回退。
  • 当前状态协调与保留每个中间更新是不同要求。

路径没变，不代表 fs.watch 仍在监听当前路径下的新文件。Node.js 文档说明，在 Linux 和 macOS 上，监听会绑定路径解析到的 inode；删除并重建文件后，新文件有另一个 inode，原监听不会自动收到新 inode 的事件。

这正好解释一种配置热加载停滞：编辑器不是原地写完旧文件，而是先写临时文件，再通过重命名替换目标。第一次替换可能产生事件，后面对新文件的修改却没有继续进入原文件监听。继续比较路径字符串，找不出这里的身份变化。

本文核对的是读取时标题为 Node.js v24.22.2 的文件系统文档中 inode 条款。这个地址会随该版本线更新，标题和正文已作为来源快照保留；它不是声称下面程序已在相同运行环境测试通过。相关行为也不能无条件推广到所有平台或文件系统。

先把路径与被监听的对象拆开

路径是查找当前位置的一种方式。监听建立时，系统解析它并关注对应文件；之后另一个文件占用了这个名字，名字相同并不能让原订阅自动转移。官方说明，原 inode 的监听会产生删除相关事件，但仍关注旧 inode；新 inode 的事件不会由这个旧文件监听继续发出。

因此观察到一次重命名或删除提示，不等于已经追上替换后的对象。若应用把那次提示当成普通内容变化，读到了新文件，却仍保留旧文件监听，当前内容可能暂时正确，下一次更新又会失去信号。一次重读成功不能证明后续订阅已经恢复。

在自己的临时目录里观察

下面是未执行的 ESM 观察程序，只创建自己新生成的临时目录。它同时记录文件和父目录的回调，分两次操作完成替换与后续写入。手动按回车留出观察机会，但不把按键当成操作系统“所有事件都已送达”的屏障，也不提供固定顺序或次数的假日志。

import { watch } from 'node:fs';
import { mkdtemp, writeFile, rename, rm } from 'node:fs/promises';
import { tmpdir } from 'node:os';
import { join } from 'node:path';
import { createInterface } from 'node:readline/promises';
import { stdin, stdout } from 'node:process';

const dir = await mkdtemp(join(tmpdir(), 'watch-inode-'));
const file = join(dir, 'config.json');
const next = join(dir, 'next.json');
const rl = createInterface({ input: stdin, output: stdout });
const watchers = [];
const log = label => (eventType, filename) =>
  console.log(label, { eventType, filename });
try {
  await writeFile(file, '{"version":1}\n');
  const fileWatch = watch(file, log('file'));
  watchers.push(fileWatch);
  const directoryWatch = watch(dir, log('directory'));
  watchers.push(directoryWatch);
  for (const watcher of watchers)
    watcher.on('error', error => console.error('watch error', error));
  console.log({ dir, file });
  await rl.question('Press Enter to replace the file; observe callbacks afterwards. ');
  await writeFile(next, '{"version":2}\n');
  await rename(next, file);
  await rl.question('Press Enter after observing callbacks to write the replacement. ');
  await writeFile(file, '{"version":3}\n');
  await rl.question('Press Enter after observing callbacks to close and clean up. ');
} finally {
  for (const watcher of watchers) watcher.close();
  rl.close();
  await rm(dir, { recursive: true, force: true });
}

保存为 watch-inode.mjs 后，可在准备好的自有环境运行 node watch-inode.mjs。第一个回车写临时文件并替换目标，第二个回车修改替换后的文件，第三个回车关闭监听并删除程序自己创建的目录。不要把打印出来的路径换成现有用户目录；清理范围就是本次生成的临时目录。

预期要核验的是两类监听是否有不同表现，而不是某次运行恰好出现几个 rename。应保留原始回调、真实操作系统、文件系统和 Node 版本，分清哪些是文档描述，哪些是本次观察。父目录里临时文件自身也可能产生提示；日志包含它们并不意味着目标配置已经可以采用。

目录事件之后，还要核对当前状态

对允许最终跟上当前配置的应用，可以把父目录事件当成“需要重新核对”的提示。安排一次合并后的重扫，按当前目标路径重新打开文件，读取完整内容，检查格式与版本，再决定是否采用。多条提示可以合并，关键是最终状态得到核对，而不是把每个提示当成一条独立业务更新。

这是一项应用设计推论，不是文档承诺目录监听会提供可靠日志。上面的程序只记录事件，没有实现可直接上线的热加载器。实际重读可能遇到文件暂时不存在、内容不完整、权限变化或解析失败；这些情况应当保留最后一个已知可用配置，并明确记录重试或失败状态。

例如进程当前采用第二版配置，下一次读到无效 JSON，不能因为“文件事件来了”就把运行状态清空。等到取得可解析、满足领域校验的完整候选后，再替换当前状态。版本字段也应由配置协议定义，不应从事件次数自行推算，否则重复提示会被误当成多次业务版本推进。

若仍选择重新建立文件级监听，还必须自己管理旧监听关闭、新监听创建与其间变化的核对。仅仅在回调里再次调用 watch，没有说明这个窗口如何恢复，就不能保证没有遗漏。对当前问题，更稳妥的评审对象是完整的状态协调过程，而不是某一行监听代码。

filename 为空时能丢掉事件吗？

不能据此丢弃；官方文件名与监听限制条款说明回调里的文件名并不保证存在，即使是在支持它的平台。应用仍知道自己监听的目录范围，可以回退到重扫，而不是要求每条事件都先提供目标文件名。

同一节的适用性说明提醒行为依赖平台和文件系统，网络文件系统或虚拟化环境也可能不可靠。

有文件名时，也不应把它当成内容验证。名字只能帮助缩小核对范围，不会证明文件存在、内容完整或版本更新。没有名字时直接返回，可能使状态一直停在旧版；把任何名字都当成目标更新，又会把临时文件等无关变化误记成配置成功。这两个分支都需要显式设计。

验证回退逻辑时，可以在自己的程序测试中直接以空文件名调用协调函数，检查它是否安排范围重扫。这只能证明函数的这个分支，不是伪造系统真的产生过某条回调。观察程序保留原样回调，逻辑测试保留自己注入的输入，两类证据应分别标明。

每次更新都必须保留时，换一种交付约定

若业务要求每个中间更新都必须处理并可追溯，事件提示加重读当前文件并不自动满足它；中间内容可能已经被下一版替代。

此时应选择满足要求的版本化交付渠道、持久记录或额外协调机制，再定义恢复策略。定期核对当前状态有助于最终恢复，却也不是每个中间版本的历史档案。先问“只需最终配置一致，还是每个变更都要计入”，再判断文件监听是否只是优化提示，避免把性能上的便利升级为不存在的可靠性保证。

重读时对文件路径的使用也仍有自己的操作边界，可参考先 access 再 open 为什么不能消除文件竞争。这里不靠一次存在性检查证明下一次操作成功。明确处理读取失败、重新校验内容，并把监听范围与状态恢复一起评审，才能解释为什么同一路径替换后系统仍能继续工作。
