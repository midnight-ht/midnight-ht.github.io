为离线包设计容量提示，而不是写入保证

用只读函数和四组独立预期区分容量估值、本次写入与持久权限，处理等号边界和预检后失败。

正文

核心要点

  • estimate读取估值，没有为后续操作预订空间。
  • persist不承诺扩容，权限也可能被实现纳入配额政策。
  • may-fit仍须观察实际写入，unknown不能直接当成容量不足。

离线资料包下载前可以检查估算余量，但不能把“看起来放得下”显示成“已经为你保留空间”。StorageManager 的 estimate 读取用量与配额估值，没有预订本次写入的步骤；持久化权限回答自动清理政策，也不承诺替这份资料包扩容。界面最终应以实际存储操作的结果更新状态。

余量数字究竟代表什么？

Storage Standard 第六节“用量与配额”将用量定义为实现决定的粗略估计，配额则是可容纳字节总量的保守估计。压缩、去重等实现方式会影响它们。这里使用的是最后更新于二〇二六年十月十九日的规范；不要从某台设备的一次返回值推导所有浏览器的固定额度，也不要把配额直接解释为整块磁盘的剩余空间。

假设接口给出的配额为一千字节，用量为五百字节，准备保存的合成包为四百字节，算术余量是五百。这个比较适合提供“按当前估算可能容纳”的提示。它没有阻止其他页面随后写入，也没有扣除或锁住四百字节。即便不发生竞争，应用算出的包大小与存储实现最终计入的用量也可能不在相同口径上。

读数应带着它的用途。下载前检查可帮助避免明显超出当前估值的大包，支持用户先删除可重建资料或选择较小内容。它不是账户权益，也不是下载成功率预测。若产品需要一个稳定承诺，应该先定义实际写入失败时如何保留输入、恢复下载或导出数据，不能让一个绿色容量图标承担所有责任。

一段只给建议、不申请权限的代码

以下未执行示例只判断传入数字，并演示如何读取浏览器接口；没有下载、写入或调用 persist。先用合成数据独立核对算术，再决定是否在支持的安全上下文中读取真实估值。示例单位均为字节，数值很小只是为了便于手算，并非真实浏览器配额。

function advise({usage, quota}, bytes) {
  const values = [usage, quota, bytes];
  if (!values.every(Number.isFinite) || values.some(v => v < 0)) {
    return 'unknown';
  }
  return quota - usage >= bytes ? 'may-fit' : 'too-large-for-estimate';
}

const samples = [
  [{usage: 700, quota: 1000}, 400],
  [{usage: 500, quota: 1000}, 400],
  [{usage: 600, quota: 1000}, 400],
  [{usage: null, quota: 1000}, 400]
];
console.log(samples.map(([estimate, bytes]) => advise(estimate, bytes)));

async function inspectStorage(bytes) {
  if (!navigator.storage?.estimate || !navigator.storage?.persisted) {
    return {advice: 'unknown', persistent: null};
  }
  try {
    const [estimate, persistent] = await Promise.all([
      navigator.storage.estimate(),
      navigator.storage.persisted()
    ]);
    return {estimate, persistent, advice: advise(estimate, bytes)};
  } catch (error) {
    return {advice: 'unknown', persistent: null, errorName: error.name};
  }
}

四个合成输入的独立预期依次为 too-large-for-estimate、may-fit、may-fit、unknown。前三个余量分别为三百、五百和四百；第四个用量不是有限数字，不能悄悄当成零。unknown 表示缺少可用估值，不表示资料一定太大，更不应自动删除用户内容。代码没有执行记录，这些字符串是预期结果，不是控制台回执。

真实调用还需要产品明确如何展示过时读数。例如用户停在容量确认页很久，返回后仍沿用旧估值，提示已经不再描述现在的判断条件。可以在实际操作前重新读取作为建议，但重新读取依然不是锁。不要用频繁轮询制造一种已经获得空间租约的错觉，也不要把估值中的细微变化包装成精确磁盘监测。

persist 改变的是哪一项条件？

规范的持久权限与存储压力条款区分默认的 best-effort 本地桶与 persistent 模式。存储压力下，自动清理策略优先面向 best-effort；持久模式受到相应保护，但用户或来源参与的清理仍然可能发生。它不等于备份，也不把会话存储改造成长期保存。

配额政策和权限也不是绝对无关。规范鼓励用户代理在决定配额时考虑访问情况和持久权限等因素。因此，准确说法是 persist 不承诺为这次操作扩容或预留字节，不能断言所有实现的配额永远不受权限影响。若资料必须离线可用，可以在用户理解用途的时机单独设计持久化请求，并按真实返回值处理；本篇没有发出该请求。

容量与留存可以同时需要，但应有两个判断。拒绝持久化，不必自动变成“本次保存失败”；获得持久化，也不能直接变成“这个包一定写得下”。界面可说明当前能否估算、估算建议是什么、实际写入进展如何，以及持久保护是否已获得，而不是把这些状态挤成一个含混的“已安全保存”。

估值够用，实际写入仍失败怎么办？

设估算后另一项缓存写入消耗了二百字节，原先可能容纳的资料包就面临新的条件。接收侧应处理真实的请求错误与事务中止，保留尚可恢复的任务信息，并给用户重试、减少内容或导出的实际选择。不要为了让容量预检显得正确，把失败统一解释为网络不佳，也不要在第一条写请求成功时宣布整包已完成。

实际实现应记录估值采集时间、待存内容大小口径、最终存储操作和用户可见结果。若采用 IndexedDB，一笔请求成功与事务完成仍须分别处理，可参看事务活动范围与最终结果。这里补充的是写入前没有容量预订，而非重复讨论事务什么时候结束。

测试应刻意覆盖可能容纳却写入失败、估值不可用但应用仍可走受控写入、用户取消，以及清理建议没有足够可删内容的路径。需要删除时，让用户知道具体对象及能否恢复；不能为了满足一个包的大小，静默清掉其他未同步的创作。本文没有运行这些写入或清理动作，实际产品仍需保留对应结果。

余量恰好等于资料包大小，可以显示“确定能保存”吗？

不能。等号只满足当前估值的算术条件；索引、编码和其他写入可能占用空间，接口又没有预订动作。示例中六百用量、一千配额与四百大小得到 may-fit，名称特意保留了不确定性。即使产品另加余量系数，也应把它描述为自己的保守策略，不能宣称某个百分比由规范保证。

交付时让评审者看到这三个分开的证据：容量提示用了什么快照，真实写入最后怎样结束，持久权限处于什么状态。若目前只有 estimate 的返回值，便只能交付容量建议；把按钮文案和错误恢复按这个范围写清，再接入真正的离线保存流程。
