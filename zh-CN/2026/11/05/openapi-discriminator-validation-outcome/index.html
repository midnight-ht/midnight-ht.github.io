OpenAPI 写了 discriminator，为什么混合类型请求仍会通过？

在 固定版本的 OpenAPI 中用明确分支约束验证付款变体，区分 discriminator 映射、oneOf 互斥与额外字段封闭。

正文

核心要点

  • discriminator不得改变模式验证结果。
  • 标签常量、必填字段和额外字段策略要由分支明确表达。
  • 父模式不自动搜索子类，工具选型与实例验证分别验收。

OpenAPI 3.1.1 的 discriminator 不改变模式校验结果。若请求必须只符合一种付款方式，要由 oneOf 分支自身约束标签和字段，而不是指望映射替你补校验。工具能够把 kind 映射到一个类型，与输入真的符合该类型，是两份需要分别验证的结论。

假设付款资料允许银行卡令牌或银行账户引用。客户端提交 kind 为 card，却带着转账字段，服务端仍接受了对象。排查时应先看实际参与验证的 schema；描述里出现 discriminator，不足以证明标签、必填字段或未知属性受到限制。本文使用教学合同，不调用付款服务，也没有进行真实交易。

标签映射不会替分支添加约束

OpenAPI 固定版本规范的 Discriminator Object 章节明确规定，discriminator 不得改变 schema 的验证结果。相邻的 oneOf、anyOf 或 allOf 才是组合规则；映射可帮助工具理解变体，但不能把原本不合格的对象变合格，也不能把模式已经允许的对象凭空变成非法。

只在两个分支里分别列出 cardToken、accountRef，却不写 required，会让缺少这些字段的对象仍有机会满足分支。若两个分支都通过，oneOf 反而应失败，因为它要求恰好一支通过。这不是 discriminator 没找到正确名字，而是分支约束没有表达想要的区别。

标签也需要自己的约束。在 Card 中写 kind 的 const 为 card，Bank 中写为 bank，再分别要求 kind 与对应字段存在，才能把标签与数据形状联结起来。单独在 mapping 写 card 指向 Card，不等于替 Card 加上 const，更不等于替请求补出必填字段。

一份能逐项检查的付款模式

以下是未执行的完整 OpenAPI 文档示例，paths 为空，仅定义待验证的 Payment 组件，不虚构可调用端点。两个对象都显式关闭额外属性，是这份教学合同的选择；如果产品允许扩展字段，应重新选择封闭策略，而不是照抄。

openapi: 3.1.1
info:
  title: Payment variant example
  version: '1.0'
paths: {}
components:
  schemas:
    Card:
      type: object
      properties:
        kind:
          const: card
        cardToken:
          type: string
          minLength: 1
      required: [kind, cardToken]
      additionalProperties: false
    Bank:
      type: object
      properties:
        kind:
          const: bank
        accountRef:
          type: string
          minLength: 1
      required: [kind, accountRef]
      additionalProperties: false
    Payment:
      oneOf:
        - $ref: '#/components/schemas/Card'
        - $ref: '#/components/schemas/Bank'
      discriminator:
        propertyName: kind
        mapping:
          card: '#/components/schemas/Card'
          bank: '#/components/schemas/Bank'

对这份合同，纸面预期分别是：card 标签加非空 cardToken 通过，bank 标签加非空 accountRef 通过；缺标签、标签与字段错配、缺对应字段或空字符串失败。card 对象再附 accountRef 也失败，但这里拒绝额外字段依赖 additionalProperties: false，不能把功劳全部写给 oneOf 或 discriminator。

验证报告应记录哪个分支通过、哪个约束失败，而不只写“校验失败”。同样是没有通过 oneOf，可能两支都不满足，也可能两支同时满足；修法不同。前者可能缺必填字段，后者可能是标签互斥或分支条件没有落实。错误位置与失败关键字比工具给出的类型名更有帮助。

带对 kind，额外字段就一定被拒绝吗？

不会。标签正确只说明一项条件满足，未知字段是否允许由对象模式决定。删掉上例的封闭规则，带正确 cardToken 的 card 对象可能仍可携带额外属性；只要它恰好满足一支，oneOf 并不因为字段“看起来属于另一类”就自动拒绝。

若通过 allOf 复用基础字段，封闭规则的位置还要另查。站内二〇二六年十月二十一日的JSON Schema 封闭对象与组合解释 additionalProperties 的局部作用域。不要为让合法新增字段通过而一口气放开所有未知字段，也不要把继承式命名当成 JSON Schema 自动合并字段的依据。

选择 oneOf 还是 anyOf，也不是工具偏好问题。付款方式必须互斥时，恰好一支符合是明确合同；允许多个能力组合时，至少一支可能更适合。但改变组合会改变合法输入集合，需要用旧请求样本与调用方验证，不能把报错少了当成兼容性完成。

只验证父模式，会自动检查子类吗？

不能靠 allOf 上的 discriminator 获得这种遍历。该版规范特别说明，这种父模式形式只适合非验证用途；验证父模式不会搜索所有继承它的子模式，也不会自动把那些子模式加入验证。需要哪些候选参与，应在实际验证的组合中列清楚。

另一个边界是缺失标签。规范建议将 propertyName 指定的属性设为必填，因为缺失时行为未定义。本例在每个分支都要求 kind，避免让工具自行猜变体。不要只在文档文字写“必须传”，实际模式却接受缺失，再把某个生成器的默认选择当成标准要求。

分开验证数据与工具选择

拟议检查先针对 Payment 及其引用运行实际模式验证器，固定方言、解析器和引用解析方式，执行上述合法与失败矩阵。再用项目真正使用的 OpenAPI 工具或生成器检查标签映射、序列化与错误反馈。两条轨道都保存版本和输入，普通 schema 校验通过不证明 SDK 选型行为正确，SDK 生成成功也不证明运行时会拒绝坏请求。

还要确定验证发生在转换之前还是之后。某些框架先按所选类型生成对象，再把不认识的字段丢弃；混合请求经过这一步，可能已经不再是原来的输入。此时仅检查转换后对象，会掩盖接口本想拒绝的多余字段。测试应同时保留脱敏原始请求与进入验证器的结构，注明哪些转换被合同允许，不能将丢字段后的通过写成原始请求合法。

模式维护也需要针对分支演进留负例。以后给银行分支新增一种可选字段，不应让原来错误的银行卡请求突然满足另一支；删除标签常量，可能让两个分支重新重合。保留每项请求的期望通过分支集合，比只保留最终布尔值更容易发现这种变化。

最后把实际服务入口、授权与持久结果列为应用验收。这份模式不核验账户是否存在、令牌是否有效或付款是否有权执行；schema 只界定输入结构。本文没有运行验证器、生成客户端或调用服务。先让每条坏请求对应一条明确约束，再确认工具选择没有改变这份合同，比看到 discriminator 关键字就批准多态接口更可靠。
