Protobuf 删除字段后，为什么还要 reserved 编号和名字？

区分 Protobuf 二进制编号与文本名字的身份，保留退役声明，并用历史字节、编译负例和混合部署检查兼容。

正文

核心要点

  • 删除声明不会释放已经使用过的二进制字段编号。
  • reserved 编号与名字约束不同，不能当成通用运行时拒绝策略。
  • 编译检查、历史数据解码和客户端退役需要分别验收。

删除 Protobuf 字段时，应保留旧编号，并按文本格式兼容需求保留名字。源码不再声明它，不代表线上旧消息已停止使用这个编号。先分清要退役的是新代码里的字段，还是仍在队列、文件与旧客户端里的数据，再决定部署顺序。

编号为什么不能重新分配？

Protocol Buffers 的 proto3 语言指南说明，字段编号用于二进制格式中的字段识别，消息投入使用后不能更改或复用。字段名方便开发者阅读，编号则会进入线上字节。把旧字段删除，再用相同编号定义另一个含义，不是给空位置安排新住户，而是在要求旧数据按新含义解释。

假设旧版订单消息有 string legacy_note = 4，保存的是客服备注。新版不用备注，开发者便删掉它，随后把 string routing_region = 4 加进同一消息。两者都是字符串，旧字节中的备注可能被新代码当作路由地区。解析没有报错，也不能证明读到了正确业务数据；相同类型反而可能让错误更难察觉。这里是依据格式规则推演的假设，没有实际编码、解码或运行服务。

编号的作用范围也要看清。风险来自同一个消息类型中重新解释已用编号，不是要求整个项目所有消息共享一份编号表。正常为另一个消息定义字段四，与复用这个订单消息里的字段四，是两件事。代码审查应同时看消息的完整类型身份和编号，不能只搜索数字是否出现。

用两个版本保存退役意图

下面两份声明是未编译的教学例子，应分别放在不同测试目录，不要同时把同名消息加入同一次编译。旧版文件先保留用于兼容性测试；新版将编号四与名字一起保留，新业务使用编号五。

// v1/order.proto
syntax = "proto3";
package example;
message Order {
  string id = 1;
  string legacy_note = 4;
}

// v2/order.proto
syntax = "proto3";
package example;
message Order {
  reserved 4;
  reserved "legacy_note";
  string id = 1;
  string routing_region = 5;
}

指南的删除字段说明建议为删除字段保留编号，并讨论名字的保留。reserved 4 将退役意图交给编译器：以后有人在这个消息里重新声明字段四，编译应当报错。只写一行“编号四别再用”的注释，无法得到这一项检查。名字和编号应分成两条 reserved 声明，不能混写在同一条里。

这份新版没有把旧备注改造成地区，也没有承诺旧备注被永久保存。它只避免将同一个身份分配给两个业务含义。旧数据遇到没有声明的字段后怎样处理，还取决于编码格式、运行库及应用是否经过转换，不能拿 reserved 声明代替旧数据保留或删除方案。

把编号从四改成五，也不能称为原字段的透明重命名。对二进制格式来说，这是删除一个字段并新增另一个字段；旧读取者不会因此自动理解新编号。若需要一段迁移期同时支持新旧含义，应先制定双方读写规则，而不是靠编号相邻或字段名相似猜兼容。

只保留编号，不保留名字可以吗？

对二进制身份，保留编号是关键；对使用 JSON 或 TextProto 的链路，名字也进入兼容性讨论。官方指南指出，复用旧名字通常不会影响二进制，但在名字会被序列化的文本格式中有风险。因此，项目若输出过 JSON 文件、调试文本或跨系统文本消息，应盘点这些消费者，再决定名字的保留，而非只检查 RPC 二进制路径。

不过，reserved "legacy_note" 主要约束后续的模式编译，不是一条通用的 JSON 运行时拒绝规则。指南明确指出，保留名字不影响运行时 JSON 解析；TextProto 还有部分语言实现会丢弃带保留名字的未知字段这一特殊行为。不能据此说所有运行库都会拒绝旧名字，也不能宣称加了 reserved 就能阻止含旧备注的请求到达。

若接口仍接受旧 JSON 字段，需要明确是拒绝、忽略还是兼容读取，并在实际解析入口验证。二进制编号防复用与文本入口如何处理旧字段，各自有检查位置。把它们都写成“兼容通过”，会让迁移报告失去可解释性。

reserved 能让旧客户端停止发送吗？

不能。它检查将来的声明，不会更新已部署客户端，也不会清空队列里的历史消息。一个可审查的退役安排，应分别记录哪些生产者停止写旧字段、哪些消费者还依赖它，以及持久化旧消息可能被重放多久。观察不到近期使用，只能支持相应窗口内的判断，不能证明所有离线客户端永远不会回来。

部署次序需要从这些依赖倒推。若先移除消费端业务读取，旧生产者仍在发送，新程序也许能解析消息，却已不再执行原来依赖备注的业务。这不是二进制兼容检查能够单独发现的错误。应先确认允许丢弃旧含义，再撤掉读取；保留编号防止的是未来误分配，不替团队批准当前业务退役。

站内二〇二六年十月二十三日的gRPC 终态与业务结果讨论调用是否真正结束；本题在更前面检查消息字段有没有被正确理解。一次正常结束的调用，仍可能传递了被错误编号解释的数据，两份验收不能互相替代。

用旧字节和误用声明分别验收

第一项检查针对编译：在新版测试副本中故意增加一个编号四的字段，确认实际 protoc 拒绝；再尝试复用保留名字，确认名字检查。记录编译器版本与原始错误，不把语法检查通过扩大成线上兼容证明。随后恢复正确声明，用旧版生成的消息字节交给错误复用版与正确新版读取，检查具体业务字段，而不是只断言没有异常。

文本链路需要另一组输入：旧名字、未知名字、新名字与缺失字段，分别经过实际 JSON/TextProto 库及应用入口。最后再检查混合部署与历史重放，确认旧业务依赖已被允许撤下。本文没有执行这些步骤，也不提供成功输出。可交付的退役记录，应能指出旧编号现在被保留在哪里、哪些读写者仍存在，以及下一次修改怎样被编译与兼容性测试共同约束。
