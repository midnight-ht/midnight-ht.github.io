PostgreSQL last_value 为什么没有返回分组最后一条？

区分 PostgreSQL 18 的分区、排序与窗口帧，用每条读数附分区末值的完整查询检查 peers、NULL 和输出粒度。

正文

核心要点

  • 默认帧到当前行的最后同级行，不一定到分区末尾。
  • 需要分区末值时保留业务排序，并明确完整帧边界。
  • NULL、并列顺序与原行是否保留需要分别验收。

last_value 读取窗口帧的最后一行，不是自动读取整个分区的最后一行。PostgreSQL 18 默认帧到当前行的最后一个同级行结束，需要分区末值时应明确写出帧边界。函数名中的“最后”，必须和它当时能看见的范围一起解释。

假设设备列表保留一天内每条读数，同时在旁边显示该设备当天最后一次读数。开发者写了按时间排序的 last_value，结果右侧值跟着每行变化，便怀疑 ORDER BY 方向错了。排序可能没有错，错的是把“分区”与“当前窗口帧”当成同一个范围。下面用未执行的教学输入说明这一区别，不提供数据库实测结果。

一份分区里面，每行还有自己的帧

PostgreSQL 18 窗口函数文档说明，first_value、last_value 和 nth_value 只考虑窗口帧内的行。带 ORDER BY 时，默认帧从分区开始延伸到当前行的最后一个同级行。这里的同级行，是按窗口排序列比较时无法区分的行，不一定只有当前这一条。

PARTITION BY 把不同设备分开；ORDER BY 决定每个设备内部的顺序；帧则决定站在当前输出行上，函数看的是其中哪一段。即使整个分区已经具有明确顺序，默认帧也没有因此自动延伸到分区末尾。理解时可以先写出每行可见的输入编号，再在这些编号里找最后一个，避免直接从函数名猜结果。

下面为时间并列补上唯一的读数编号，使这份例子的顺序确定。id 是示例中约定的并列选择规则，不表示编号天然比业务时间更权威。

WITH readings(device, id, measured_at, value) AS (
  VALUES ('A', 11, timestamp '2026-11-05 09:00', 10),
         ('A', 12, timestamp '2026-11-05 09:00', 20),
         ('A', 13, timestamp '2026-11-05 10:00', 30),
         ('B', 21, timestamp '2026-11-05 09:00', 70)
)
SELECT device, id, value,
       last_value(value) OVER (
         PARTITION BY device ORDER BY measured_at, id
       ) AS default_last,
       last_value(value) OVER (
         PARTITION BY device ORDER BY measured_at, id
         ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
       ) AS partition_last
FROM readings
ORDER BY device, measured_at, id;

按定义推演，A 的三行默认末值依次是十、二十、三十，而覆盖全分区的末值在这三行上都应为三十。B 单独一行，两列都应为七十。两种写法都保留四行，不会因为用了窗口函数而把 A 压成一条。这里列的是给定输入下的验证预期，SQL 尚未执行。

若把窗口 ORDER BY 中的 id 删掉，A 的前两条成为同级行。默认帧会包含九点的两个同级成员，不是只到当前物理行；由于二者没有进一步顺序，不能要求 last_value 稳定选中哪一份不同读数。单次查询碰巧得到二十，不足以说明规则已完整。外层 ORDER BY 即使保留 id，也不能替窗口内部补上这个选择。

为什么不是把 ORDER BY 去掉？

文档对窗口聚合指出，省略窗口排序或明确使用全分区帧，可以得到整个分区的聚合。对 last_value 却还需要问：没有顺序时，哪个成员叫最后？本题要求最后一次读数，时间和并列规则不能为了扩大范围而删除。应保留窗口内部顺序，再把帧扩到末端。

同样，改成时间倒序后取默认末值，并不是原查询的机械等价替换。倒序改变了先后定义，默认帧仍按自己的规则结束。若想借 first_value 配合倒序取时间最新值，可以另写查询，但仍需处理时间并列、空值和输出要求。评审时应解释新表达式为什么选中同一身份，而不是只看到某一列数值相同。

如果页面其实只需要每台设备的一条最新记录，应先改输出合同，而不是保留全部行再随便去重。站内二〇二六年十月十四日的DISTINCT ON 代表行选择讨论这一问题。代表行选择会改变行数；窗口末值给原行附加信息，两者在数据粒度上不同。

最后一条是 NULL，可以自动跳过吗？

不能把这项期望藏在函数名字里。PostgreSQL 18 文档明确说明，相关窗口函数没有实现 SQL 标准的 IGNORE NULLS 选项，采用 RESPECT NULLS 行为。如果 A 的最后一条读数改成 NULL，完整帧上的 last_value 也会取到这个空值，而不是自动回退到二十。

“最新一次记录”和“最新一次有效读数”因此是两个问题。前者可能需要把最后一次采集失败呈现出来；后者需要明确定义有效条件，再从符合条件的集合中选择。若先过滤空值，原本要保留的空读数行也可能消失。可以考虑把有效末值计算放在独立子查询再关联回原行，但正确关联、无有效值时的结果以及重复关系都需要另外验证，不能只补一个当前版本不支持的语法。

这项选择还影响多个字段的归属。最后读数、最后采集时间与状态如果要来自同一条记录，不能分别取各自最大值后拼在一起。帧里的最后值只负责一个表达式，团队仍需保证返回的时间和值对应同一个被选择的来源。

验收应该保留哪些不同输入？

先固定每台设备的排序与期望末行身份，再检查每一条输出行是否携带该身份对应的值。至少保留同时间不同编号、最后值为空、只有一行以及多个设备四类样本。把输入书写顺序打乱，仍应得到符合显式顺序的结果；这能揭示代码是否无意依赖当前数据排列。

如果窗口还按日期分区，必须确认所谓“当天”按哪个时区确定。本文的时间戳和日期只为简化例子，没有替实际设备业务定义跨时区日界线。补一条迟到数据也可能改变同一设备分区的末值；一次查询的结果不承诺后续请求保持不变。

执行验证时保存 PostgreSQL 版本、完整 SQL、输入与逐行预期差异。性能评估应在语义确认后另看实际计划、分区大小和排序成本，不能从这份四行示例推断生产代价。这里没有运行查询；待验收的第一件事，是把每行的可见范围写清，再证明选中的最后成员与业务要求一致。
