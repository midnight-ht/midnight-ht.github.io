window load已经触发，lazy图片为什么还没显示？

解释lazy图不阻塞window load、complete包含坏图及逐图成功状态，用教学图库区分缩略图与预览生命周期。

正文

核心要点

  • lazy图片不参与window load等待。
  • 损坏图片也能得到true完成标记。
  • 逐图状态与实际资源身份一起验证。

lazy图片不计入window load的等待集合，初始视口里的延迟图片也可能尚未显示；依赖某张图片的操作应检查那张图片的结果。图库在load以后统一开放所有编辑按钮，会把页面级事件误当成每个图像资源的成功证明。

MDN的img元素说明明确区分eager和lazy：后者由浏览器根据与视口的距离推迟加载，不参与window load的等待，即使初始就在可视区域也可能尚不可见。文档描述的是机制，没有给每个浏览器统一的预取像素距离，更不能据此承诺加载速度提高多少。

页面完成与目标图片可用分属不同范围

假设资料图库有二十张教学封面，用户只打算预览第十五张。文档已经加载，页眉和表单也能使用，不表示远处这张封面已被请求。页面没有必要为了首屏可操作而等待所有远处图片，但使用这张图的动作必须知道它是否真的成功。

因此，应先确定下一项操作需要什么资源。只阅读文字，不应因远处图片而阻塞；打开原图预览，需要那张图的加载结果；若还要进行像素编辑、跨来源读取或导出，则又有解码、权限和画布等独立条件。本文的教学样本只做本地显示预览，不提供像素编辑或导出能力。

这与网络空闲不等于业务就绪的范围区分相接。本篇具体指出lazy图片为何可以在全页load之后仍不可用，不能只把等待换成另一个全局事件，再把它叫作“全部图片就绪”。

按每张图片记录成功与失败

下面是未执行的完整教学页面。图片路径需要由运行者提供真实文件；页面不包含它们，不代表它们存在。按钮只在对应缩略图收到成功load后开放，并将实际选用的资源放入一个普通预览区。没有接入真实图库、编辑器或保存服务。

<!doctype html>
<html lang="zh-CN">
<meta charset="utf-8">
<title>延迟图片的独立状态</title>
<div id="gallery"></div>
<p id="message" role="status"></p>
<div id="preview"></div>
<script>
const find = selector => document.querySelector(selector);
const text = (node, value) => { node.textContent = value; };
const gallery = find('#gallery');
const message = find('#message');
const preview = find('#preview');
const make = tag => document.createElement(tag);
const available = (button, yes) => { button.disabled = !yes; };
const on = (element, event, handler) => element.addEventListener(event, handler);
for (const [id, url] of [['a', '/teaching/a.jpg'], ['b', '/teaching/b.jpg']]) {
  const card = make('section');
  const image = make('img');
  const button = make('button');
  image.loading = 'lazy';
  image.width = 320;
  image.height = 240;
  image.alt = `教学封面 ${id}`;
  button.type = 'button';
  text(button, `预览 ${id}`);
  available(button, false);
  on(image, 'load', () => { available(button, true); });
  on(image, 'error', () => {
    available(button, false);
    text(message, `封面 ${id} 读取失败，不能预览。`);
  });
  on(button, 'click', () => {
    const copy = make('img');
    copy.alt = image.alt;
    copy.src = image.currentSrc || image.src;
    preview.replaceChildren(copy);
  });
  card.append(image, button);
  gallery.append(card);
  image.src = url;
}
</script>
</html>

监听器先于src赋值安装，避免先发起资源读取、再补监听而漏掉已经发生的事件。每个按钮闭包对应自己的image，没有让第一张图加载成功就开放全列表。样本使用固定两个对象；真实列表更新资源地址、复用节点或切换记录时，需要重置成功状态并关联新的资源身份。

预览区新建图像仍有自己的加载过程。缩略图成功只支持当前缩略图资源曾加载成功，不保证另一次资源使用永远成功，更不保证不同原图地址可读。若预览本身需要确认完整显示，应继续监听预览元素的load/error；不能把按钮开放写成原图编辑已完成。这个边界保留了样本实际做的事情。

为什么complete不能独自当成功开关

HTMLImageElement.complete参考列出的true条件包括资源已获取，也包括没有src、空src以及损坏图片。于是坏图complete为true并不矛盾；它不是只有成功才出现的标志。只检查这项布尔属性就启用编辑，会把处理结束和成功可用混为一谈。

样本选择提前监听明确的成功或失败事件，而不是只读一个布尔值。已有DOM图片在绑定前可能已结束读取，此时实现需要设计初始化判断或重新安排资源生命周期；不能照搬样本后半段，忽略它从创建元素起就拥有加载顺序的前提。对需要可靠像素使用的应用，还应另核对具体资源和操作要求。

失败路径也不能只把按钮永久禁用。真实产品需要可发现的失败说明、重新加载或其他可继续任务的方式。教学样本只提示读取失败，没有重试业务；若加入重试，必须重新设置等待状态，避免旧成功标记让新的失败资源继续可操作。重试次数和退避时间应来自实际场景，本文没有测量。

width和height为什么对lazy图尤其必要

当前img参考提醒，没有尺寸的未加载图像可能没有可见面积，从而影响它是否进入可以触发加载的区域。loading属性参考也把这个属性称为加载提示。明确尺寸有助于先建立占位，但占位正确仍不等于资源读取成功。

布局尺寸、来源选择与加载状态应分别记录。srcset与sizes的资源选择解释currentSrc可能随候选选择变化；不能因为页面上写了某个src，就只核对那个文件名。教学样本没有srcset，使用currentSrc是为了保留实际选用资源的观察位置，并没有验证响应式图像策略。

测试该滚动，还是把所有图片改成eager？

若目标是验证真实延迟加载路径，应保留lazy，按实际滚动让目标进入相关区域，再检查这张图的成功、失败和按钮状态。全部改成eager可以测试另一种条件，却会移走本来需要验证的机制。不要断言某个精确滚动距离必定触发请求，浏览器保留自己的调度选择。

待执行对照应覆盖可用文件、缺失文件、远处目标、重复进入以及资源替换，记录目标身份、load/error、按钮状态和真实预览结果。全页load时间可以作为背景，但不是单图通过条件。本文未运行浏览器或图片请求；交付先明确当前动作依赖哪张图，再保存属于那张图的证据。

同一张卡片换了资源，旧的成功还能沿用吗？

假设封面甲已经成功，筛选后同一个卡片节点改为显示封面乙。若按钮仍沿用甲的成功状态，乙还没加载时用户就能触发预览。表面上是某次点击太快，实际是成功标记没有随资源身份失效。状态应属于一次明确资源使用，而不是永久属于某个按钮节点。

可以在替换来源之前先关闭依赖动作，更新记录身份，再为这次资源建立成功与失败处理。列表若会并发读取原图，还需要防止旧读取的完成结果重新开放新对象的操作。具体实现可按资源版本或请求归属判断；本文样本没有这种并发读取，不把一个固定循环包装成虚拟列表解决方案。

重试也应从失败状态重新进入等待。用户按重试以后，不能立即显示成功或恢复按钮，仅因为脚本又设置了一次src。若请求仍失败，提示应继续属于当前封面，并让用户知道可以做什么。浏览器可能复用资源或采用自己的读取策略，实际是否重新请求要观察，不能从赋值次数推导网络次数。

因此，验证表里除了图片地址，还应保留它对应的记录与当前操作。记录身份没变但资源版本变了，或者节点没变但记录换了，都值得单独覆盖。这样才能解释按钮开放是因为哪次成功，而不会把上一张图的好运气借给下一张。
