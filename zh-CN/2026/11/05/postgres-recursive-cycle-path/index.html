PostgreSQL 递归查询加了 UNION，为什么仍绕着环走？

用 PostgreSQL 18 CYCLE 跟踪节点路径，区分整行去重、合流和回环，并保留诊断标记与终止边界。

正文

核心要点

  • depth变化会让同一节点形成不同结果行。
  • 路径内重复与不同路径合流不能混成全局去重。
  • CYCLE停止扩展但不修复原图，外层LIMIT不作生产保险。

递归结果包含 depth 时，同一节点再次到达可能形成不同结果行，UNION 因而不能替你识别环。应明确跟踪节点身份和当前路径，再决定环行怎样输出。防止查询继续绕环，与向读者展示哪里形成了环，是可以分别设计的两项要求。

假设依赖关系是甲指向乙、乙指向丙、丙又指回甲，乙还指向丁。报表从甲出发查全部下游，并显示层数。开发者将 UNION ALL 换成 UNION，希望去掉重复节点，但下一次甲的层数已经不同。下面按 PostgreSQL 18 文档推演，不运行无界递归，也不提供已经成功终止的日志。

UNION 看的是整行，不是心里的节点

PostgreSQL 18 的递归查询说明区分非递归项与递归项；UNION 会排除完整结果行的重复。如果只输出节点标识，同一节点再次出现可能被去重；加入 depth 后，甲零层与甲三层已经不是相同行。再带上变化路径，差别会更多。

因此，不能把结果去重和环检测当作同一件事。前者问“这整行是否已经出现”，后者问“沿着这次行走，是否回到已经访问过的身份”。修改投影列可能改变 UNION 是否能终止，正说明原来的终止依赖并未被独立定义。这里仅纸面描述错误递推，不给可直接启动的无界反例。

节点身份还必须真实唯一。若组织名可以重复，只用名字检测会把合法的不同部门当成环；多租户数据里的编号也可能只在租户内部唯一。应该根据实际关系使用节点主键，必要时连同租户一起跟踪，不让显示名称承担图中身份。

完整正例保留环标记与访问路径

文档的 Cycle Detection 章节提供 CYCLE 子句，指定跟踪列、环标记名和路径列名。下面是未执行的完整教学查询，四条边都在语句里；结果保留标记行，便于调查，不只返回一份看似正常的下游名单。

WITH RECURSIVE
edges(src, dst) AS (
  VALUES ('A'::text, 'B'::text),
         ('B', 'C'), ('C', 'A'), ('B', 'D')
),
walk(node, depth) AS (
  SELECT 'A'::text, 0
  UNION ALL
  SELECT e.dst, w.depth + 1
  FROM walk AS w
  JOIN edges AS e ON e.src = w.node
)
CYCLE node SET is_cycle USING path
SELECT node, depth, is_cycle, path
FROM walk
ORDER BY path;

按给定图推演，应有起点 A、后续 B、C、D，以及再次到达 A 的环标记行。沿 A、B、C 回到 A 时，标记为环的这一行仍可进入结果，但不会再从它继续展开；不是把所有与 A 有关的行删除。depth 用于说明走了几步，不参与这里的节点身份判断。path 与 is_cycle 由 CYCLE 加入输出，不需要在递归列列表中手工重复声明。

如果产品只展示非环路径，可以在最终 SELECT 加 WHERE NOT is_cycle，但应保留另一份诊断结果或记录，让异常关系有出处。过滤结果的环行并不等于图已被修复，原始边仍然存在。查询停止是一项行为，数据约束正确是另一项结论。

两条路径到同一节点，算环吗？

不一定。另一个无环图中，A 分别到 B、C，B 和 C 都到 D。两条路线都走到 D，却没有沿自己的路径回到旧节点。这是合流，不是环。若需要每一条依赖路径，两份 D 都有用；若只要唯一可达节点清单，才应在选定阶段按节点合并。

全局“已经见过 D”集合与每条路径上的环检测，承担的责任不同。全局去重可以减少重复探索，却也会丢掉路径数量、不同父节点和层级证据。不能因为最终页面只显示一次 D，就在递归内部提前丢弃另一条路径，再把结果用于统计全部依赖关系。

选择之前先说明输出对象：节点清单、边清单、路径清单，还是每个节点的最短层级。这些问题没有一条 CYCLE 就能统一回答。示例输出路径以便诊断，不承诺最短路径，也没有给路径爆炸的图提供通用资源上限。

外层 LIMIT 能当停止保险吗？

文档将父查询 LIMIT 介绍为试验递归时的技巧，同时明确不建议作为生产依赖。外层排序或连接常常需要先取得完整递归结果，才知道该返回哪些行，因此 LIMIT 不一定限制递归实际产生多少工作。本例能够使用 ORDER BY path，是因为递归已有环检测，而不是排序之后的 LIMIT 在保护它。

如需研究错误写法，应使用隔离环境与递归内部明确的深度上限，再把它标为受限实验。深度达到上限而停止，只能说明截断，不能宣称发现了全部节点或解决了环。业务确实只允许查若干层时，上限可以是正式合同，但结果应说明范围和是否存在被截断的后续。

站内二〇二六年十月二十一日的CTE 物化与过滤下推限定普通非递归查询的复用安排。本题处理递归的终止与路径身份，不应把物化提示当成防环开关。

如果边表带租户字段，递归连接也必须按租户关联。只在 CYCLE 中增加租户列，却让连接把两个租户的同号节点连起来，会让检测正确地描述一条本来就不该存在的跨租户路径。环检测负责终止，不负责授权或修正连接条件。验收因此要同时核对每一步边的归属，不能仅检查最后的环标记；身份组合、连接范围与可见权限各自需要依据。

把合流与环一起纳入验收

拟议用例应包含无环链、自环、三节点回环、菱形合流，以及跨租户同编号。对每组先写下应输出的节点与路径、哪条行应被标记，再检查是否终止。只看总行数可能掩盖合法路径丢失；只看没有超时，又可能让错误的全局去重通过。

执行时保存版本、完整输入、SQL 与原始输出，并观察资源预算。即使没有环，庞大有向无环图也可能有很多路径；CYCLE 防止沿环无限扩展，不保证所有图都便宜。本文没有执行查询。首个交付依据应是能解释那条再次出现的 A 为什么被标记、为何不再扩展，同时仍保留两条合法到 D 的路线。
