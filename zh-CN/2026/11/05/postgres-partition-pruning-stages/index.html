PostgreSQL 查询有索引，为什么还要检查分区裁剪？

把 PostgreSQL 18 分区裁剪与分区内索引分开，按规划、初始化与执行时点核对参数、子计划和实际访问。

正文

核心要点

  • 分区边界负责排除分区，索引负责留下分区内的访问。
  • 参数可在规划、初始化或执行时触发裁剪。
  • 计划名、实际扫描和锁范围需要不同证据。

分区裁剪先排除不可能包含匹配行的分区，索引再帮助读取留下的分区。PostgreSQL 18 还可能在执行时裁剪，不能只凭静态计划列出多个子计划就宣布失败。排查时先问哪些分区需要参与，再问其中的行怎样读取。

假设日志表按月分区，查询只要十一月前三天。表上已经有日期索引，并不回答十月分区是否被排除；反过来，十月分区被裁掉，也不保证十一月分区一定使用索引。两层选择服务不同范围，不能把某个计划节点名字当成全部优化已经完成。

裁剪依赖边界，不依赖先建索引

PostgreSQL 18 分区裁剪文档说明，优化器检查分区定义，证明某分区不可能满足查询条件时，将它排除。声明式分区使用的是分区边界；这不同于在保留分区内部查找具体行的索引。

因此，没有分区键索引也可以发生裁剪。如果剩下分区中绝大多数行都符合条件，顺序扫描可能是合理选择；如果只取其中很少行，索引可能有用。应由实际查询、数据分布与成本判断，不把“顺序扫描”自动写成故障。这个区分也避免为了修裁剪问题不断增加分区内索引，承担维护成本却没有触及条件证明。

查询形式同样要核对。应用说按日期查，实际 SQL 可能先对分区键套函数，再与另一种类型比较。是否还能从这种表达式推导边界，需要具体计划证据；不能保证所有包函数的写法都失败，也不能因为表达式数学上看似等价，就断言优化器一定认识。

先用两个分区固定正确结果

下面是未执行的教学 SQL，只供独立隔离测试库使用，不应在已有业务库直接运行。表名是示例，不代表可以覆盖同名对象。事务最终回滚创建的数据与表；本例先说明查询和边界，不提供预制执行计划。

BEGIN;
CREATE TABLE demo_measurements (
  id bigint NOT NULL,
  logdate date NOT NULL,
  value integer
) PARTITION BY RANGE (logdate);
CREATE TABLE demo_measurements_oct PARTITION OF demo_measurements
  FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
CREATE TABLE demo_measurements_nov PARTITION OF demo_measurements
  FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');
INSERT INTO demo_measurements VALUES
  (1, DATE '2026-10-31', 10),
  (2, DATE '2026-11-01', 20),
  (3, DATE '2026-11-03', 30);
PREPARE demo_lookup(date, date) AS
  SELECT id, logdate, value
  FROM demo_measurements
  WHERE logdate >= $1 AND logdate < $2;
EXPLAIN (COSTS OFF) EXECUTE demo_lookup(
  DATE '2026-11-01', DATE '2026-11-03'
);
EXECUTE demo_lookup(DATE '2026-11-01', DATE '2026-11-03');
DEALLOCATE demo_lookup;
ROLLBACK;

按输入推演，结果应只含编号二：下界包含十一月一日，上界不包含十一月三日。先核对这份集合，再研究裁剪。否则一条错误地少取边界行的查询即使访问更少，也不是可接受的优化。跨月参数还应另做预期，因为那时两个分区可能都包含合格行，访问多个分区未必错误。

此例没有创建索引，正好让分区边界与索引访问分开观察。如果后续增加索引，应比较相同 SQL 与参数，分别记录裁剪范围和剩余分区的访问方式，而不是把两项变化合并成一个“已优化”结论。

参数在什么时候可知？

官方文档区分规划期裁剪与执行期裁剪。参数值在规划时已经可用，可能提前排除分区；某些准备语句参数、子查询值或参数化连接值，到初始化或执行过程中才可用，仍可能触发后续裁剪。

因此，PREPARE 并不保证总是展示同一种计划，也不保证每次都有 Subplans Removed。规划方式、参数与实际语句共同决定观察结果。不要为配合教程预期而把计划中没有出现的字段补进报告；应该保存真实计划，并说明哪些阶段有证据，哪些尚不能判断。

初始化阶段被裁掉的数量，可由计划中的 Subplans Removed 等信息帮助确认；执行中随参数变化发生的裁剪，还要结合 EXPLAIN ANALYZE 中各子计划的 loops。部分子计划可能显示 never executed，但这个标记单独出现，也可能来自其他未进入的执行分支，不能脱离父节点就归因裁剪。

计划里仍有分区，等于真的扫描了吗？

不等于。普通 EXPLAIN 描述计划，不提供所有实际执行次数。需要检查运行时行为时，可在受控隔离环境使用带 ANALYZE 的计划；它会真的执行语句，不是只做排版展示。站内二〇二六年十月九日的EXPLAIN 证据边界讨论估算与实际观察的区别。

检查应同时保留具体参数、enable_partition_pruning 设置、完整父子节点及执行次数。只截下某分区的 never executed，或者只数计划中分区名的数量，都不足以解释为何没有访问它。重复执行的参数也要覆盖不同月份，避免一个恰好能在规划期求值的样例代表全部请求。

还不能把“没扫描”写成“完全没有触及这个分区”。官方文档指出，初始化裁剪移除的分区，在执行开始时仍会被加锁。若评审的是维护期间的锁冲突，读取量减少不能替代锁范围证据。应分别观察查询实际读了哪些数据与它持有哪些锁，避免用一份裁剪计划为在线变更承诺互不干扰。

如果测试开关关闭裁剪，比较的也是同一结果集合下的计划变化，不是改变业务过滤。应在隔离事务里控制设置并保存原值，不能为了对照把共享连接池的会话设置长期改掉；连接复用可能把实验配置带到下一次请求。

何时需要重新考虑分区设计？

如果主要查询根本不限制分区键，裁剪就可能帮不上忙。此时应回到过滤习惯和生命周期管理要求，而不是靠增加分区数量制造“分得更细就更快”的预期。分区还带来规划、对象维护和变更安排；小表或跨全部历史的汇总未必适合照搬按月结构。

拟议验收先比较单月、跨月、空范围与边界日期的结果集合，再检查各阶段证据；语义一致之后才测负载、缓冲读取与延迟。本文没有运行 SQL、测量收益或给出某种固定计划。交付时让“排除了哪些分区”和“剩余行怎样读取”各有证据，比仅报告已建索引更能解释真实查询。
