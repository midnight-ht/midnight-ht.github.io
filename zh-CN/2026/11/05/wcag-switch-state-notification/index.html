WCAG自定义开关变绿了，读屏为什么仍说关闭？

以教学通知开关说明稳定名称、二元程序状态、键盘激活与未保存草稿，区分开关值和保存结果。

正文

核心要点

  • 名称识别设置，状态表示当前值。
  • 原生按钮激活与自定义状态同步需要分别负责。
  • 本地拒绝只演示未保存草稿，不验证后端。

自定义开关的外观变成开启，不代表辅助技术收到状态变化；先核对同一控件的名称、角色和当前状态。通知设置明明已经变绿，读屏却仍说关闭时，继续调整颜色解决不了这项信息分歧。

WCAG 2.2 名称、角色和值的理解文档要求界面组件的名称和角色可被程序确定，用户可设置的状态、属性和值可被程序设置，相应变化通知也应能提供给用户代理，包括辅助技术。它没有要求每个组件都堆上相同的ARIA属性。按规范使用原生控件与自己改造一个控件，承担的实现工作不同。

先决定这个控件究竟表达什么

“接收教学通知”可以是一个开关：只有开启与关闭两个值。用户打开它，含义是改变这项设置，而不是选择某次批量操作中的一条记录。APG开关模式强调开关是二元输入，不能把部分开启或继承父级设置偷偷塞成第三态。若产品需要允许、拒绝、继承三个答案，应先选择能表达三种含义的交互。

控件的名称用来识别设置，状态用来说明当前值。把名称从“接收通知”改成“停止通知”，同时又标记开启，可能让人无法判断开启的是接收还是停止。模式要求开关的标签在状态变化时保持不变；“接收教学通知，开启”比让动作词和状态一起翻转更容易核对。

这与可见标签进入无障碍名称相接，却是另一项责任。名称包含眼前的词，只证明用户能识别这项设置；它没有说明现在是否开启。反过来，一个状态正确却没有名称的开关，也无法让用户知道自己修改了哪个偏好。

一份没有后端的完整教学样本

下面文件没有执行，也没有连接通知服务。它用原生按钮承担按钮激活，用开关角色和检查状态表达二元设置。保存按钮调用的只是一个明确拒绝的本地教学函数，用来展示未保存状态，不能当作真实接口失败记录。

<!doctype html>
<html lang="zh-CN">
<meta charset="utf-8">
<title>教学通知偏好</title>
<button id="notice" type="button" role="switch"
        aria-checked="false">接收教学通知</button>
<p id="state">当前草稿：关闭；尚未保存</p>
<button id="save" type="button">保存教学草稿</button>
<p id="result" role="status"></p>
<script>
const find = selector => document.querySelector(selector);
const text = (node, value) => { node.textContent = value; };
const toggle = find('#notice');
const state = find('#state');
const result = find('#result');
let enabled = false;
function render() {
  toggle.setAttribute('aria-checked', String(enabled));
  text(state, `当前草稿：${enabled ? '开启' : '关闭'}；尚未保存`);
}
toggle.addEventListener('click', () => {
  enabled = !enabled;
  render();
  text(result, '');
});
async function rejectLocallyForTeaching() {
  throw new Error('本地教学拒绝，没有发送请求');
}
find('#save').addEventListener('click', async () => {
  try {
    await rejectLocallyForTeaching();
  } catch {
    text(result, '教学保存未完成；当前选择仍是未保存草稿。');
  }
});
render();
</script>
</html>

这份样本选择“保留未保存草稿”，因此保存拒绝后开关不悄悄回到关闭。程序状态仍表示用户眼前可修改的草稿值，另有文字说明它尚未生效。若真实产品选择失败就恢复服务器确认值，也应同步恢复可见状态与程序状态，并解释回退；不能只把颜色恢复，让辅助技术继续得到开启。

激活路径也需要明确。原生按钮获得焦点后有自己的键盘激活行为，所以样本只处理click，没有再添加一套按空格翻转的脚本。若在按钮上同时监听空格和随后产生的点击，可能把一次操作翻转两次。换成普通div时，这些原生行为就不再自动成立，添加角色并不会替你生成键盘合同。

只改一个属性为什么仍会失败

典型反例是点击时只切换绿色类名。鼠标用户看到变化，程序化状态却一直为false；另一种是状态改成true，却没有稳定名称，页面上四个相似开关无法区分。检查应将同一对象的身份、状态和行为放在一起，而不是分别截图一段CSS和一个ARIA属性。

采用原生checkbox表达这项设置也是合理选择。APG给出了checkbox形式的开关，此时用原生checked表达勾选状态，而不是另维护一份可能冲突的aria-checked。具体角色应匹配视觉设计和含义；不要因为设计稿画了一条滑轨，就认定所有原生表单行为都应被重写。

待执行验证可以从关闭开始，用键盘聚焦并激活，检查名称仍是同一项设置、状态变为开启、可见草稿文字一致。再操作一次回到关闭，随后开启并触发本地拒绝，核对未保存说明和草稿状态。浏览器无障碍树能提供名称、角色和值的证据；真正的播报时机仍需在支持的浏览器与读屏组合下观察。本文没有这些运行结果，不能从样本推导兼容性通过。

开关已经报告状态，还需要保存失败消息吗？

需要分别表达两件事。开关报告当前可修改值，失败消息报告保存动作的结果；开启不等于服务器已经确认开启。可以像样本那样保留草稿并显示未保存，也可以按明确合同回滚，但不能把状态变化当作保存回执。若真实请求正在进行，还应决定能否继续编辑，以及较早响应能否覆盖较新的选择。

保存最终成功后，应重新读取实际确认的设置，比较它与显示值和程序化状态。这个步骤需要真实接口与持久化证据，教学样本没有实现。交付时先选定草稿与生效值的关系，再核对开关三份信息：它叫什么、它是什么控件、它现在是什么值。

恢复设置时，先读到的值该不该立即接管？

设想用户刚进入页面，服务器确认值尚未返回，页面临时显示关闭。若这个关闭只是初始化占位，就不应假装它已经代表用户偏好。可以先显示正在读取，并在得到确认值以前限制修改；也可以允许先编辑，但必须定义后到的读取结果是否仍有资格覆盖草稿。两种方案的成本不同，开关角色本身不会替团队选择。

例如用户在等待期间打开通知，随后一份旧读取结果说关闭。若应用直接用它覆盖当前值，用户刚才的选择便消失；若只更新颜色不更新程序状态，又产生第二种分歧。允许先编辑时，需要把“本地已修改”作为读取结果合并条件，或者用记录版本判断响应是否仍属于当前状态。这里是设计推论，没有执行接口竞态测试。

更简单的读取完成后才能编辑方案，则应让等待状态容易理解，并保留失败后重试读取的入口。不要把未知值一律画成关闭再保存，否则可能将尚未读取的真实开启偏好改掉。只要把未知、已读取、已编辑与已确认分开，测试就能判断开关当前报告的是哪一份值。

组件复用时还要核对设置身份。用户切换账号或记录后，上一份确认值不能因为按钮节点仍在就继续充当默认值。稳定名称帮助识别设置类型，记录身份帮助识别修改对象；两者都应随真实任务核对。
