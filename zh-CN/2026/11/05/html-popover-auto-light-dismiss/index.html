HTML第二个popover打开，第一个为什么消失？

区分auto轻量关闭、manual并存与嵌套例外，用完整HTML对照原生打开状态和绘制层级。

正文

核心要点

  • 独立auto通常在另一个auto打开时关闭。
  • manual并存需要明确关闭入口与布局。
  • 顶层popover仍是非模态。

两个独立面板都使用auto时，打开后一个通常会关闭前一个；应先选好关闭策略，再排查层级。第一个面板从页面消失，可能是原生popover状态已被改变，继续增加z-index不会让一个已经关闭的浮层保持打开。

HTML popover属性参考区分auto、manual和hint。auto支持轻量关闭，例如点击外部或按Escape；显示另一个独立auto通常会关闭已有auto，但嵌套情形有例外。manual允许多个独立面板同时存在，也要求用明确控件或脚本管理显示和关闭。这些是当前文档语义，不能代替目标浏览器验收。

先把“消失”拆成两种情况

假设资料页有“字段说明”和“导出说明”两个工具面板。用户打开字段说明，再打开导出说明，第一个就不见了。先检查第一个是否仍匹配:popover-open，而不是直接判定被第二个覆盖。如果它已不在显示状态，问题属于关闭策略；如果仍打开却内容不可见，才继续检查具体布局和绘制。

这一步也能避免与普通隐藏样式混淆。站内父级隐藏与后代可见讨论的是继承与盒生成。原生popover显示时进入顶层，不受祖先position或overflow以通常方式裁剪，但这不表示它永远打开。显示层次与打开状态是两个不同维度。

auto适合用户当前只需要一份短暂说明的任务。新说明取代旧说明，可以减少遮挡；点击页面继续工作时关闭，也可能符合预期。如果用户正在对照两个字段定义，这种默认行为就会破坏比较。此时需求应明确写成“两个独立面板可同时保留”，而不是只说“修复浮层闪退”。

用两个面板比较auto与manual

以下是未执行的完整HTML教学样本，没有网络请求，也没有接入资料系统。初始版本刻意使用两个独立auto。应先预测它们的互斥与轻量关闭行为，再把两个属性都改为manual，比较并存和关闭的差异。

<!doctype html>
<html lang="zh-CN">
<meta charset="utf-8">
<title>工具面板关闭策略</title>
<h1>教学资料</h1>
<button type="button" popovertarget="fields">字段说明</button>
<button type="button" popovertarget="exports">导出说明</button>
<section id="fields" popover="auto">
  <h2>字段说明</h2>
  <p>记录编号用于区分教学记录，不是显示序号。</p>
  <button type="button" popovertarget="fields"
          popovertargetaction="hide">关闭字段说明</button>
</section>
<section id="exports" popover="auto">
  <h2>导出说明</h2>
  <p>导出范围需要单独确认，本页没有执行导出。</p>
  <button type="button" popovertarget="exports"
          popovertargetaction="hide">关闭导出说明</button>
</section>
</html>

两个关闭按钮并非多余装饰。换成manual后，用户不能再依赖auto提供的外部点击或关闭请求处理，明确关闭入口承担了实际任务。若只把属性改成manual来阻止消失，却没有检查如何退出，就可能把短暂说明变成不断堆积的浮层。

选择manual也不会自动安排两份面板的位置。它们可能都处于默认位置并互相挡住，需要另做布局，让比较任务真的可完成。不能只测DOM里同时有两个打开元素，就宣布对照体验合格。窄屏、长说明、放大和键盘操作都可能暴露并存后的新问题。

一个失败修复是给第一个面板写极大的z-index。只要它已被auto规则关闭，层级值没有恢复显示状态。另一个失败是监听任何关闭再立即showPopover，强行对抗浏览器规则：用户点外部本想关闭，脚本却立刻重开，需求与操作相冲突。先选择合适状态，比建立这种补偿循环更容易解释。

嵌套auto为什么能一起出现？

因为独立浮层与嵌套浮层不是同一种关系。当前参考明确列出嵌套例外：主菜单内部的按钮打开附属说明时，可以保留有关联的祖先面板。不要把一次嵌套成功推广成任意两个auto都能并存，也不要为了保留两个无关工具面板，随意在DOM里制造错误的父子含义。

当前文档还提供hint状态：它不因显示本身关闭auto，但会管理其他不在其祖先关系中的hint。涉及鼠标、焦点与点击触发的组合时，轻量关闭条件仍须逐项核对；不能把hint当成所有独立并存需求的替代开关。本文的完整样本只依赖auto与manual，不声称hint已在项目支持环境验证。

面板能加背景遮罩，就算模态了吗？

不算。Popover API概念说明明确说，通过该API创建的popover始终是非模态。背景变暗只是绘制效果，不能证明背景操作被阻止。若任务要求用户先完成一个决定才能回到页面，应按真正模态对话框设计，不能从顶层显示反推模态交互。

模态焦点进入与返回已经讨论另一份合同；本篇的选择依据是面板之间是否应该互斥、是否需要外点关闭，以及能否同时比较。它们不因长得像弹窗就自动成为同一类组件。

待执行检查先记录两个面板的打开顺序、各自:popover-open状态和显式关闭结果，再测试外点、Escape与嵌套对照。改成manual后重做相同步骤，检查并存时文字、操作和关闭入口是否真的可用。保存浏览器版本与实际观察；本文没有运行样本，不提供跨浏览器通过结论。交付时写清关闭策略，才能判断一个面板消失是产品预期还是缺陷。

对照任务结束以后，保留哪些面板？

设想用户比较两份字段说明：打开甲，再打开乙，来回核对它们的单位。若每次打开乙都让甲消失，用户必须记忆甲的内容；manual并存解决的是这个比较成本。但当用户切换到另一份资料，旧面板是否继续显示，又是新的决定。并存并不意味着跨对象永久保留。

可以把面板内容绑定到当前资料身份，切换资料时明确关闭旧面板，或同步更新标题和内容。不能只替换正文，保留指向旧对象的操作按钮。若用户原本在对照两个不同对象，就应在两份面板里分别写清对象名称，而不是让一个全局当前对象决定所有内容。这个例子是交互合同推导，没有真实用户研究结果。

关闭范围也需要区分。“关闭字段说明”只关闭字段面板，“关闭全部工具”才同时清除两份。用户完成一次比较后，应能按自己意图结束，而不是每次关闭一份就被脚本重新打开另一份。设计里若需要记住打开偏好，也应说明记住的是工具类型还是某个旧记录的内容。

因此，auto与manual的选择不只对应一个属性值，还对应工作持续时间。一次性解释可随着其他交互退出；持续对照则应给出明确的结束动作和对象边界。只有这两项都清楚，两个打开面板才真正服务于比较，而非只是技术上同时存在。
