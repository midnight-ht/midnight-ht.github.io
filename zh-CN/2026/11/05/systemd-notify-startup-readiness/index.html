systemd start 已成功，为什么依赖服务仍抢跑

按 Type、READY 通知身份、超时与排序依赖推演 systemd 启动，区分正常、延迟、退出和无通知。

正文

核心要点

  • simple、exec 与 notify 等待不同的启动时点。
  • 需求依赖与启动顺序需要分别配置。
  • READY 的发送点与主进程身份都要验证。

对 systemd 启动完成的判断取决于 Type。simple 在 fork 后继续，exec 等到可执行文件成功执行；需要等待应用初始化时，应让支持通知的服务在真实完成后发送 READY=1。如果后继单元没有独立配置启动顺序，换成 notify 也不会自动建立它们之间的等待关系。

先选启动完成的时点，再写依赖

systemd.service 手册将 Type 定义为服务通知管理器启动已完成的机制。simple 的边界早于程序执行，exec 能暴露可执行文件不存在等调用失败，但二者都没有读取应用初始化进度。notify 则要求服务通过通知协议明确报告。本文核对二〇二六年十一月五日的 latest 手册，不据此推断任何主机安装的版本。

假设报表服务先加载模板、建立只读索引，再绑定本地请求端口；另一个预热任务必须在这三步结束后访问它。选择 simple 时，预热可能在程序执行前获准启动；选择 exec 时，程序已经成功执行，却仍可能在加载模板。仅改变进程启动方式，不能让管理器知道第三步何时完成。

notify 把这个判断交给应用，但没有替应用决定标准。应用应先写清发送点：本例要求模板可用、索引准备完成、监听已经建立，才报告 READY。若在 main 函数刚进入时发送，协议使用形式虽然存在，等待者仍会过早继续。配置只能等待报告，不能证明报告内容诚实。

一组有前提的单元与事件方案

以下是未执行的协议方案，假设自有 report-service 已在主进程实现 sd_notify，并且支持明确的初始化延迟测试开关。/opt 下的程序不是本文提供的可运行实现；片段展示接口条件与状态推演，不能只保存两个文件就声称获得了可运行教程。服务文件拟保存为 report-demo.service。

[Unit]
Description=Report initialization contract demo

[Service]
Type=notify
NotifyAccess=main
TimeoutStartSec=30s
ExecStart=/opt/report-service/bin/report-service

后继文件拟保存为 warmup-demo.service。假设自有 warmup 程序只发送一条只读请求并以明确退出值报告结果。它的两项依赖分别表达拉起服务与等待顺序，不是可互换字段。

[Unit]
Requires=report-demo.service
After=report-demo.service

[Service]
Type=oneshot
ExecStart=/opt/report-service/bin/warmup

systemd.unit 手册说明，需求依赖本身不决定启动排序；After 或 Before 需要单独配置。对本例，启动 warmup 时 Requires 把 report 纳入启动事务，After 让 warmup 的启动排在 report 启动完成之后。只写 After 不负责拉起另一个单元，只写 Requires 也不保证按预期顺序启动。

三十秒是教学预算，不是推荐的通用初始化时限。实际值应结合最慢可接受初始化、机器与数据规模决定。TimeoutStartSec 限制启动等待；未在规定时间内完成会被视为失败并按超时策略处理。某些通知协议可以延长预算，但本例不采用该功能，也不把延长当作无限等待的理由。

四条事件线分别会发生什么

正常推演是：管理器执行主进程，状态进入启动中；应用完成模板与索引，建立监听；同一主进程发送 READY=1，report 的启动完成，排在它后面的 warmup 才可执行。warmup 最终是否请求成功仍需记录，不能从前者启动完成直接写成后者任务已通过。

延迟推演把模板加载延后，但仍在预算内结束。此时 report 保持启动中，warmup 等待；到真正完成并报告 READY 后才继续。等待时长应由事件记录说明，而不是用固定 sleep 估算。若初始化慢于超时预算，本例按启动超时失败处理，不应把更晚出现的端口当成这次启动事务已经成功。

退出推演让主进程在初始化时因模板错误退出，且没有发送 READY。服务没有完成约定的启动；本例后继使用 Requires 与 After 组合，其前提未成立，不能继续当作正常预热。这条路径需要保存退出原因与依赖任务结果，而不只看某一刻进程曾经存在。

无通知推演则让程序一直运行、甚至已经监听，却不发送 READY。管理器不能从监听状态猜测通知已经发生，会继续等待并受启动超时约束。把 Type 改成 notify 并不会给旧程序注入协议能力；若它不支持，应先实现或明确选择别的启动边界，不能靠无限超时隐藏缺失。

为什么通知发送者身份也属于协议？

因为管理器只接受 NotifyAccess 允许的发送者更新；设为 main 时，就只接受该服务主进程的状态更新。任意启动一个辅助命令发送消息，不一定具有这个身份；手册还说明，辅助进程发送后立即退出可能产生归属竞态，即使放宽到 all 也不能随意忽略。可靠设计优先由长驻主进程在正确终点发送，而不是让不明 helper 代为宣布完成。

sd_notify 手册还明确 READY=0 并不是撤回就绪的定义。启动完成协议不能当作持续路由健康开关。READY 之后数据库短暂失联，需要应用失败响应、恢复和监控另行处理，不能简单反向发送零值并假设后继工作被自动撤销。

拟议验证应在隔离 Linux 主机记录管理器版本与实际单元配置，让自有进程分别执行正常、延迟、初始化退出、无通知四种输入。为初始化开始、监听建立、READY 发送、后继启动和请求结果保存可关联事件；同时观察服务启动作业状态。事件记录至少保留本轮身份、主进程 PID、输入模式、初始化步骤、单调时间和后继退出值。用同一轮身份连接管理器与应用记录，能区分“通知未发送”“发送者不被接受”和“已通知但请求失败”；这些分支不能只靠一条端口检查区分。语法校验即使通过也不证明通知归属或请求结果。

二〇二六年十月二十四日的Compose 启动依赖文章同样区分启动条件与运行期恢复，但 systemd 在这里等待的是受身份约束的应用通知，并由单独的排序依赖约束后继。先确认程序确实支持协议、发送点真实、后继关系完整，再把启动成功写入交付记录。
