GNU Make 首轮失败，次轮为什么把半成品当成最新目标

解释 GNU Make 失败后残留目标的时间戳陷阱，比较失败删除、退出状态与先生成后发布。

正文

核心要点

  • 部分目标的较新时间戳可能误导下一轮构建。
  • 失败删除要求非零退出真正传到 make。
  • 保留旧有效版本时应考虑独立生成再发布。

构建失败时，GNU Make 不一定删除刚写过的目标文件。部分文件若留下较新的时间戳，下一轮可能跳过生成；对会原地更新目标的 recipe，应审查 .DELETE_ON_ERROR 和真正传回 make 的退出状态。先确认坏文件为何被留下，再决定用失败删除还是先生成临时文件。

第一轮的失败怎样污染第二轮

GNU Make 的 recipe 错误说明描述了这个具体问题：命令修改目标后失败，部分文件可能留在磁盘；时间戳却显示它已更新，下一次 make 因而不再尝试生成。文档建议显式开启特殊目标所控制的失败删除。本文于二〇二六年十一月五日核对在线手册，没有执行下面的 Makefile。

假设报表依赖 input.txt。生成程序先打开 report.txt 写入标题，随后读取某一行时失败。第一次 make 已经非零退出，流水线也正确标红，但 report.txt 的修改时间晚于输入文件。下一轮没有改变输入，make 的普通时间戳判断可能把它看成最新目标。两次运行并不矛盾：一次观察到执行失败，另一次只看到文件与依赖的更新时间关系。

这不是“make 忘了上次失败”，而是构建目录里留下了一个会被当作有效产物的对象。持久保存失败状态、验证内容或删除无效目标，都可以改变这个条件；只反复按重试键，却不改变目标状态，无法表达文件其实没完成。对生成报表、归档或代码文件的规则，这个差别值得进入构建设计。

一个能推演两轮结果的最小规则

以下例子要求 GNU Make、常规命令行 shell 及可写的独立目录。recipe 行的缩进必须是制表符。先准备一个 input.txt；report.txt 是真正的文件目标，不是标记为 phony 的任务名称。生成器用两条命令模拟写了部分内容后失败。

.DELETE_ON_ERROR:

report.txt: input.txt
    printf 'partial report\n' > report.txt
    false

没有第一行开关时，第一次运行写出 partial report，随后 false 返回非零；普通失败不会自动保证这个文件消失。如果文件时间关系满足前面的条件，第二次可能不再执行 recipe。有开关时，已改变的目标在失败后会被删除，第二轮就缺少目标，需要重新尝试。这里是按手册进行的教学推演，没有对应运行日志。

比较时应记录两个输出：make 的退出状态，以及 report.txt 是否存在、内容是什么。只截一段终端错误会漏掉残留文件；只检查文件存在又会把半成品误认成完成。还要控制输入时间，避免编辑器恰好重写 input.txt，导致第二次重跑，从而掩盖本来要验证的增量判断。

该规则的目的不是让错误程序成功，而是防止它把半成品留成下一轮的有效目标。false 仍然失败，修复前再次运行仍然可能失败。若报告要求包含两行数据，应另加内容验证，不能把“目标被删除”称作“报表已生成正确”。失败清理与成功验收是两项结果。

将上面的片段保存为独立沙盒中的 Makefile，输入文件与目标都只属于本例。下面的未执行调用序列创建新目录；第二份规则只移除第一行开关，原始代码不变。不要在已有发布目录尝试这项实验。每次调用后立即打印退出值，再看目录；有开关的两轮仍应失败；无开关组则用于观察目标残留怎样影响第二次运行。

make_demo_dir=$(mktemp -d)
cd "$make_demo_dir" || exit 1
printf 'input\n' > input.txt
# Save the displayed Makefile here before continuing.
sed '1d' Makefile > WithoutControl
run_demo() {
    make -f "$1"
    make_result=$?
    printf 'status=%s\n' "$make_result"
    ls -l
}
run_demo WithoutControl
run_demo WithoutControl
rm -f report.txt
run_demo Makefile
run_demo Makefile

无开关的第二轮若把残留文件视为最新，可能不再执行 false，从而返回成功；这正是要暴露的错误复用，不是报表修好了。有开关的两轮都应重新尝试并失败。若本机时间戳精度或文件时间关系使分支不同，应先保留记录、核对时间条件，不通过重跑直到碰巧符合来伪造证明。

Make 得先知道失败，才会进行失败处理

每次 recipe shell 调用的退出状态都会交给 make 检查。行首的减号、全局忽略错误参数或 .IGNORE 可以让它将错误按成功处理，只另行提示已忽略。若生成命令后面接了吞错的 shell 表达式，make 也可能只看见零。此时该开关没有收到目标失败这一条件。

因此评审不能只找特殊目标是否写在文件里。沿生成器、shell 与 make 逐层看退出值：谁可能失败，谁把失败覆盖，最后谁决定这条规则已经完成。一个常见反例是在同一条 shell 命令最后打印“完成”，却没有把前面的失败传出来；屏幕出现错误与 shell 最终非零也不是同一个事实。

Make 默认每一行 recipe 使用新的 shell，上面写文件与 false 两行均由各自调用返回状态。若改成一行复合命令，要重新审查它的语义；若使用 .ONESHELL 或其他 shell 配置，也不能把另一个项目的规则直接当成本项目行为。本文只解释这个最小普通规则，不提供所有 shell 的失败继承清单。

-k 会继续检查，但会把失败变成成功吗？

不会。手册说明，keep-going 模式继续考虑不依赖失败目标的其他工作，最后仍返回非零。依赖失败目标的规则不能因此获得有效前提。它适合一次收集多个独立编译问题，和忽略错误不同，也不负责修复留下的目标文件。

例如甲、乙两个报表互不依赖，甲生成失败后仍可检查乙；最终构建依旧失败。若归档依赖甲、乙，甲失败就不能把乙成功解释成归档可交付。保留独立诊断与阻止不完整交付可以同时成立，不需要为“多跑一些”放松失败结论。

先写临时文件再改名，应该怎样选？

如果上一个完整报表还需要继续使用，直接覆盖真实目标再失败删除，会连旧版本也失去。另一种候选策略是在独立临时路径完成写入与验证，成功后再发布为目标。这样发布前可以保留旧文件，但临时文件清理、改名条件与并发写入仍需明确。不要把一次改名泛化为跨文件、跨文件系统或远端存储的事务承诺。

选择依据是失败后希望留下什么。目标无效就不应存在时，失败删除很合适；需要保留最后一个有效版本时，先生成再发布更贴近需求。若生成器还写数据库、发送通知或上传对象，两种本地文件策略都不会自动撤销这些副作用，应另设幂等、对账或补偿协议。

拟议验证在隔离目录中保留有无开关两份规则，固定输入，分别记录首轮退出、目标内容与时间，再原样运行第二轮。补测错误被忽略和正常生成两条路径，确认失败不会留下可误用目标，成功产物满足内容要求。测试素材不要放在真实发布目录。

二〇二六年十月二十五日的构建时间与可复现性文章讨论固定输入后能否重建相同字节；这里先处理更早的条件：上次失败留下的文件是否有资格参与下一次增量构建。先让无效目标可辨认，再检查成功产物的一致性。
