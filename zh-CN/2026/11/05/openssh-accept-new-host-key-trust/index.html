OpenSSH accept-new 免了提示，首次主机身份由谁核实

拆开 OpenSSH 首次信任与已知主机换钥检查，说明 keyscan 的认证边界及受控 known_hosts 分发。

正文

核心要点

  • accept-new 保存新密钥并拒绝已知主机密钥变化。
  • keyscan 收集材料，不独立核实主机身份。
  • 受控发布需明确可信输入与换钥流程。

OpenSSH 的 accept-new 会自动保存新主机密钥，并拒绝已知主机换钥后的连接。它保护后续比较，却没有替你证明第一次接收到的密钥就是目标服务器的密钥。无人值守发布需要消除交互，但主机身份的可信来源仍须明确，不能把没有提示当成已经核实。

首次出现与已知密钥改变是两个分支

OpenSSH 的 ssh_config 手册说明，StrictHostKeyChecking 设置为 accept-new 时，会自动加入新密钥，但不允许已知主机使用改变后的密钥连接。yes 则不自动加入新密钥，并拒绝改变后的密钥。本文于二〇二六年十一月五日核对当前 OpenBSD 在线手册，没有发起 SSH 连接，也没有修改任何远端密钥。

假设 CI 第一次连接一台发布服务器，所用用户主机库为空，并且没有全局主机库、主机证书信任或其他有效来源提供该目标的可信基准。accept-new 可以让它不经人工确认就保存当时收到的密钥。下一次如果读到相同记录，它有了一个比较基准；收到不同密钥时可以阻止继续。但第一次保存的依据仍是那次网络交互。如果网络中的对方不是期望服务器，自动保存本身不会修正这个错误。

这不意味着首次信任模式完全没有用途。它为有明确风险接受条件的环境建立连续性，减少后续无声变化；问题是不能把这种连续性写成独立身份核验。评审时应问两个问题：最初的正确密钥从哪里来，后续连接用的是不是同一个受控信任库。只有第二个答案，无法补足第一个。

ssh-keyscan 为什么不能补上首次认证

ssh-keyscan 手册直接说明，该工具收集主机公钥，却不能验证取得的公钥是否真实；能够拦截网络的攻击者可能替换返回值。它适合获取待核对材料，但获取与核对是不同动作。把扫描输出立即写入 known_hosts，只是保存了网络当时给出的答案。

一个危险的发布脚本形状是每轮先扫描目标，再覆盖旧的已知主机文件，随后连接并宣称校验开启。客户端确实可能比较了文件，但比较依据刚刚来自同一条尚未认证的路径。原本应由密钥变化触发的警告，被覆盖动作提前抹掉。不能用“文件里有一行公钥”证明信任链已经成立。

可信核对可以来自受控服务器控制台、获授权的管理员或组织既有的安全分发流程。具体选哪种渠道，应由部署环境决定；本文不虚构一份可用指纹，也不把同一个未经核实的聊天转发自动当作独立证据。核对对象应包括目标身份、端口条件、算法和公钥或指纹，避免拿另一台机器的正确指纹为当前连接背书。

一个受控发布任务需要哪些输入

下面是未执行的配置示例。example.invalid 是保留的教学域名；trust/known_hosts 应由已完成独立核对的材料构成，本文没有提供真实条目。示例假设命令从包含 trust 目录的工作目录运行，避免相对路径指向意外文件。

Host deploy-demo
    HostName deploy.example.invalid
    User deploy
    StrictHostKeyChecking yes
    UserKnownHostsFile ./trust/known_hosts

候选调用方式是保存配置为 ssh-demo.conf，再使用 ssh -F ./ssh-demo.conf deploy-demo；身份认证凭据与服务端权限需另外配置。这里没有通过配置片段承诺能登录。yes 的作用是让主机校验按既定信任材料进行，而不是替任务取得用户登录授权。

准备阶段先为配置和信任材料登记版本、来源与维护者，确保任务能够读取且非受不可信修改控制。执行前可检查实际生效的客户端配置，确认 Host 别名匹配、目标与 UserKnownHostsFile 路径符合意图，同时核对 GlobalKnownHostsFile 与 KnownHostsCommand 等额外来源。空的用户文件不能证明客户端完全没有信任基准。不要只看仓库里的文件存在，就认为客户端一定读取了它；命令参数或其他配置可能改变实际输入。

验证使用自有隔离 SSH 服务，准备匹配、未知和变化三种情形。匹配的已知密钥应能通过主机校验，后续用户认证仍可能单独失败；未知密钥在 yes 下不应被自动加入；已知密钥变化时不应以删除记录来“修复测试”。记录每个分支的目标与信任材料身份，不能把任何非零退出都归因于主机校验。

CI 每轮都从空 known_hosts 开始，还剩多少连续性？

如果每次任务都使用新的空用户文件，并且其他有效信任来源也没有该目标的基准，accept-new 每次面对的才是第一次见面，前一轮保存的基准没有进入下一轮。容器销毁或工作目录清理也会造成同样效果。设置名称虽然未变，保护条件已经不同；只有受控保存或分发的基准真正被下一轮读取，才能比较跨轮变化。

因此应明确谁维护这份材料。可以由受控仓库或配置系统分发经过核对的记录，但要限制修改权限，并把授权变更与运行版本关联。将其无限缓存也不是完整方案：主机合法重建或轮换时，仍需有可审查的更新流程，而不是要求旧基准永远不变。

服务器重建后换钥，能删除旧记录重连吗？

先核对新密钥与重建事件的真实来源，再决定更新。删除旧记录会把这次连接重新变成首次信任，不能自己证明变化合法。需要确认哪台主机、哪些名称或端口受影响，谁授权重建，新指纹由哪条可信路径取得，再受控分发新记录。本文没有执行换钥或建议在公共目标上演练。

如果已怀疑连接被冒充，应按实际暴露范围调查，不能只把错误提示消掉。主机公钥不是用户私钥，二者处理对象不同；更换信任记录也不等于已经撤销某个泄露的登录凭据。二〇二六年十月九日的秘密撤销文章可作为凭据处置的相邻问题，不能替代本题的主机身份核对。

选择应落在具体风险上。允许首次信任的临时环境，需要公开承认初见边界并保持后续基准；受控发布任务可以预置核实记录，以 yes 拒绝未知或变化。两种安排都应保留真实校验结果，而不是把没有人工确认步骤直接写成安全验收完成。
