Redis 更新缓存后，过期时间为什么消失？

比较 Redis 普通 SET、KEEPTTL 与到期选项，区分固定截止、滑动续期和两条命令之间的失败窗口。

正文

核心要点

  • 替换内容与原地修改对现有TTL的处理不同。
  • 保留期限、重设寿命和新增期限是不同写入意图。
  • 检查条件返回值，并用允许时间推进的范围验证TTL。

成功的普通 SET 会丢弃键原来的 TTL，修改哈希字段等原地更新则保留它。更新缓存时应同时决定保留原截止时间，还是从这次写入重新计时。值变了和寿命怎样变，是同一次代码评审里需要分别回答的两个问题。

假设一个结果缓存原定两分钟后失效，程序刷新内容时只调用 SET。读取新值正常，过了原定期限却仍存在。此时先检查实际写入命令，而不是直接归咎于 Redis 没有清理过期键。本文按当前官方命令文档解释规则，没有连接 Redis、执行命令或观察真实缓存。

替换整个值，与修改值的一部分不同

Redis SET 命令文档说明，成功的 SET 会丢弃此前关联的存活时间；命令可通过到期选项指定新的时间，或使用 KEEPTTL 保留现有 TTL。EXPIRE 文档则区分替换键内容与原地修改：INCR、LPUSH、HSET 等不会因为修改值就清掉现有期限。

这里不能把“更新”当成一个数据库无关的动作名。把整个 JSON 字符串重新写入键，与修改某个哈希字段，看起来都叫更新资料，命令层行为却不同。排查应保存实际命令和选项，以及键在调用前是否存在、是否已有期限；只看封装函数名 updateCache，无法判断它承诺保留还是重置。

对一个已有期限的字符串键，三种意图应分开：普通 SET 替换内容且不保留原 TTL；SET 加 KEEPTTL 替换内容并保留已有期限；SET 加 EX 则给新值安装指定秒数的寿命。后两种没有谁天然更正确，固定截止和滑动刷新服务的是不同需求。

一组只使用自有键的对照

下面是未执行的 redis-cli 教学命令，只应在独立本地空实例，或已明确属于自己的唯一测试前缀下使用。示例前缀应先替换成自己本次试验的唯一值，不能覆盖共享实例中的同名业务键；没有清库命令。三个字符串键分别承载三种选择，不依赖前一组还剩多少秒。

SET editorial_demo_unique:plain v1 EX 120
TTL editorial_demo_unique:plain
SET editorial_demo_unique:plain v2
TTL editorial_demo_unique:plain

SET editorial_demo_unique:keep v1 EX 120
SET editorial_demo_unique:keep v2 KEEPTTL
TTL editorial_demo_unique:keep

SET editorial_demo_unique:refresh v1 EX 120
SET editorial_demo_unique:refresh v2 EX 120
TTL editorial_demo_unique:refresh

拟议预期是：第一组最后变成没有到期时间；第二组保留原期限，其剩余时间会随试验推进；第三组从最后一次写入重新获得指定寿命。不要把每次 TTL 都等于一百二十写成断言，命令之间会经过时间。实际验收还应查返回值与键是否仍存在，避免把键已过期和键没有过期设置混为一谈。

可另建一个自有哈希键，先 HSET 一次，再 EXPIRE，随后修改同一字段并观察期限。这个对照用于确认原地修改的规则，不是在建议为了保留 TTL 就把所有字符串缓存改成哈希。数据布局还要满足读写粒度、类型与调用方需求，不能被一项过期行为倒推决定。

先 SET 再 EXPIRE，为什么要单独评审？

如果应用先成功写值，随后才发出 EXPIRE，两条命令之间可能退出。此时新内容已经存在，预期寿命却尚未安装。这是应用控制流程的失败窗口，不是声称 Redis 会把已收到的单条 SET 执行一半。若需求是新值与新期限属于同一写入决定，使用 SET 的相应到期选项能直接表达它们，而不是让第二个调用承担补救责任。

重试也要照顾意图。写入带 EX 的命令被重复执行，会从新的写入时刻重新计时；这对滑动缓存可能合理，对严格不晚于某业务时刻的资料却可能不合适。若要求固定绝对截止，应选择能表达该截止的选项并核对时钟含义；若要延续当前剩余寿命，应考虑 KEEPTTL 的条件。本文不将缓存寿命当作业务授权的唯一依据。

封装接口可以直接命名保留或重设策略，并要求新增路径也表明寿命。所谓统一缓存工具如果悄悄给每次更新续命，热门键可能长期存在；如果统一清掉期限，原本应短存的数据会变成无期限键。两种错误都可能在“新值读取正确”的测试里通过。

KEEPTTL 能给永久键补上期限吗？

不能。保留现有 TTL 与创建新期限是不同动作。原本没有期限的键，不能只靠保留选项获得过期时间。因此应分别测试已有带期键、已有无期键和不存在键三种起点，而不是只在最理想的第一种起点上验收。

还要核对服务端和客户端支持。当前 SET 文档的命令历史将 KEEPTTL 标为 Redis 6.0 引入；工具库是否暴露这一选项、封装是否真的发送它，需要实际版本证据。文档里出现新选项不等于项目的旧依赖已经支持，也不能把命令没有报错当作封装保留了所有参数。

EXPIRE GT 为什么没有让无期限键开始倒计时？

EXPIRE 文档把没有期限的键在 GT、LT 比较中视作无限 TTL。GT 要求新期限更大，有限秒数无法比无限更大，条件就不会满足。应检查命令的条件结果，而不是仅记录调用完成。不同条件用于“只新增”“只改已有”“只延长”“只缩短”的区别，必须和所选业务策略匹配。

这也说明 TTL 问题要沿真实存储路径调查。站内二〇二六年十月三十日的Node.js DNS 查询边界讨论名称解析由谁负责；应用缓存里的过期设置又是另一份状态。两个地方都有时间信息，不代表修改其中一处能改变另一处的缓存寿命。

拟议验收先按三种起点与三种写法记录预期，再验证最终值、是否有期限以及剩余时间的合理范围。另在两调用之间人为停止应用，检查不带到期 SET 后的状态，保存失败路径。本文没有运行这些检查，不给精确秒数或性能收益。交付时应能说明每条写入究竟保留、重设还是移除了期限，以及这个变化为何符合缓存的实际用途。
