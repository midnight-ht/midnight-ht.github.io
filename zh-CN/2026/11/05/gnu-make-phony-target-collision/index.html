GNU Make 的 clean 被同名文件跳过，何时该用 .PHONY？

区分 GNU Make 动作目标与真实文件，用同名 clean 沙盒比较、依赖方向和字面声明检查正确的进入条件。

正文

核心要点

  • 动作目标需要与同名文件的更新时间判断分开。
  • 真实生成文件应保留输入依赖与增量判断。
  • phony 属性不继承，但普通前置关系会影响真实目标更新。

GNU Make 会把普通目标名当作文件来判断是否需要更新。若 clean 只是清理动作，同名文件或目录却已经存在，无依赖的规则可能被当成最新目标而跳过；将这个动作声明为 .PHONY，才能明确它不代表那份文件。这项声明不会替命令完成清理，也不应该随手加到每个真实产物上。

没有执行，与执行失败是两种问题

GNU Make 的 Phony Targets 手册用 clean 举例：若 recipe 不产生名为 clean 的文件，通常每次请求都会执行；但工作目录出现同名对象时，无前置条件的普通规则可能被视为最新，从而跳过。动作声明让 make 不再用那份对象判断该动作是否需要进入。

假设团队一直使用 make clean 清理教学构建文件，后来有人新建 clean 目录存放资料。清理任务没有报错，旧产物却还在。问题可能发生在命令执行之前：make 认为目标已经满足，所以没有调用清理程序。此时反复检查 rm 的参数，可能一直看不到决定是否进入 recipe 的那一步。

这与真实文件生成一半后留下残片不同。后者承认目标就是一个产物，只是它的内容已经无效，需要处理失败状态；本题的 clean 从来不应该代表同名文件的更新时间。修复要恢复动作身份，而不是删除一个碰巧同名、却可能有用途的目录，也不是强迫所有报表每次重建。

在自有沙盒里制造一次名称碰撞

下面是未执行的完整教学输入，要求 GNU Make、常规 shell，以及可创建的一次性目录。脚本只准备本例的文件；删除范围限于该沙盒的 build/demo-output。两个 Makefile 的 recipe 完全相同，差别只有动作声明。recipe 缩进使用制表符，复制时需要保留。

phony_demo_dir=$(mktemp -d)
cd "$phony_demo_dir" || exit 1
mkdir clean build
printf 'old output\n' > build/demo-output
cat > Ordinary <<'MAKE'
clean:
    rm -f build/demo-output
    printf 'cleanup action entered\n'
MAKE
cat > Declared <<'MAKE'
.PHONY: clean
clean:
    rm -f build/demo-output
    printf 'cleanup action entered\n'
MAKE

准备完成后，以下两次调用都显式请求 clean，不依赖默认目标的选择。第一组先保留同名目录与旧产物，第二组仍保留 clean 目录，但重建教学产物，再更换规则文件。这里列出预期观察，不是已执行的终端记录。

make -f Ordinary clean
phony_exit=$?
printf 'ordinary-status=%s\n' "$phony_exit"
ls -ld clean
ls -l build
printf 'old output\n' > build/demo-output
make -f Declared clean
phony_exit=$?
printf 'declared-status=%s\n' "$phony_exit"
ls -ld clean
ls -l build

普通规则组预计不出现动作标记，build 下仍有旧产物；声明动作的组预计进入 recipe，标记出现，指定产物被移除，而 clean 目录保留。单看 make 返回成功，无法区分“命令成功清理”和“目标已满足所以没执行”；动作标记与目标状态要一起看。

若第二组进入了 recipe 却因为权限失败，没有移除产物，那是另一个分支。动作声明只修复进入规则的条件，不会绕过文件权限，也不会把失败变成成功。检查退出状态、原始错误和指定文件的实际存在性；不要用那条打印标记代替删除结果，更不要把示例中的单文件移除外推为完整项目清理成功。

这组比较还可以扩为三种输入：没有同名对象、同名普通文件、同名目录。每次只在新的独立沙盒准备一个变体，保持规则不变。这样能核对问题是否真的由名称碰撞触发，而不是工作目录错了、规则文件选错或另一个同名目标覆盖了配置。本文没有运行这些命令。

哪些目标应该保留文件身份

选择标准是 recipe 的交付物。clean 或 check 通常表示要请求的动作；report 表示一份实际生成文件时，则应该写明输入依赖，让 make 判断什么时候需要更新。文件存在并且没有较新输入时跳过，正是这类目标需要的行为，不是等待修复的缺陷。

例如文档报告依赖一份源文件。若把报告本身也声明为动作，就失去原来依赖更新时间避免重做的语义。若需求其实是每次重新验证已有报告，可以另外建立 check 动作，由它读取报告并进行验证，不必把“报告是否需要生成”与“现在是否需要检查”挤进同一个目标身份。

二〇二六年十月二十五日的可复现构建范围文章讨论相同输入能否产生相同字节。本题先回答另一件事：某次请求是否应该进入动作或生成规则。一次命令没有执行，不能由最终文件恰好相同证明正确；需要先核对它所属的目标合同。

把 all 设为动作，会让每个依赖都重建吗？

不会。官方手册明确说明，phony 属性不会继承给前置目标。all 可以是动作入口，依赖真实报告文件；请求 all 时会考虑报告，但报告仍按自己的输入与文件状态决定是否更新。入口每次被请求，与每个产物都要重做不是同一个判断。

相反，如果把一个总要进入的动作作为真实文件目标的普通前置条件，该动作在考虑真实目标时会被处理；在它成功完成且其他条件允许的情况下，真实目标也会因此需要重建。这不是属性继承，而是把一个总被视为待更新的前提接进了文件更新关系。前置动作失败时，后续文件 recipe 也不能被当作正常完成。

所以要区分箭头方向：动作入口依赖真实文件，可以保留文件的增量判断；真实文件普通依赖总要更新的动作，则改变了文件何时重建。不要为了方便组织名称，把准备动作接到每个产物上，再把意外重做解释为 make 的随机行为。

声明列表里的百分号会匹配一组目标吗？

不会。手册指出，该特殊目标的前置项按字面名称解释，即使带百分号，也不是模式。因此写一个看似覆盖全部对象文件的条目，不能据此宣称所有相关规则都成了动作。应列出真正的动作名字；若确实需要模式规则的强制重建，应另读相应机制，不把这份声明当通配符用。

验证时先记录 GNU Make 版本、实际工作目录、所用规则与请求目标，再保存动作标记、退出状态及产物变化。对 all 的关系测试则固定真实输入运行两次，随后只改变一个真实输入，观察对应文件规则是否按约定进入。名称碰撞、依赖方向与命令结果各有一项证据，才能说明修的是任务身份，而不是靠清掉整个目录碰巧让它执行。
