Redis SCAN 返回空数组，遍历为什么还不能结束？

以游标回零结束 Redis SCAN，处理空批与重复键，并限定 COUNT、遍历期间变化和单库覆盖的保证。

正文

核心要点

  • 非零游标的空批不能结束，零游标的最后批仍须处理。
  • COUNT是工作提示，重复键与重复副作用由应用负责。
  • 完整遍历覆盖持续存在元素，不等于时点快照或全Cluster覆盖。

SCAN 是否结束看返回游标是否为零，不看这一批有没有键。完整遍历还可能重复返回键，因此维护动作需要能够安全重做。把 SCAN 当作每页固定数量、每个键恰好出现一次的列表接口，会同时写错停止条件与处理语义。

一个维护任务请求匹配某前缀的键，拿到空数组就退出，日志显示“处理零项，已完成”。这份日志最多说明该次调用没有返回匹配项，不能证明整个集合已经走完。下面讨论单个选定数据库的遍历合同，没有连接 Redis，也没有执行清理任务。

游标回零，才是一轮完整遍历

Redis SCAN 官方文档把从游标零开始、持续使用返回游标，直到它再次为零的过程定义为完整遍历。返回值包括下一游标和本批元素。文档允许一批没有元素，只要游标非零，客户端就应继续。

调用方不应把游标改成页码，也不应自己递增。它不是已经走过多少条的计数，更不是剩余工作的百分比。为避免客户端语言把大整数游标处理错，以下伪代码保持客户端返回的十进制字符串形式；实际库若提供专用类型，应按其接口原样传回。

cursor = "0"
repeat:
    reply = scan(cursor, match=owned_prefix + "*", count=100)
    next_cursor = reply.cursor
    keys = reply.keys
    for key in keys:
        process_repeatably(key)
    cursor = next_cursor
until cursor == "0"

这段是未执行的流程示意，不是某个客户端库可直接运行的代码。process_repeatably 也不是声称已有实现的工具函数，而是必须由应用提供的重复安全动作。先处理本批，再判断是否结束，因此游标回零时返回的最后一批同样不会丢掉。网络调用失败不应被包装成空数组继续宣称完成；应保留任务未完成或结果未知的状态。

可以为客户端循环设定三份明确标注的协议测试输入：第一次返回非零游标和空数组，第二次返回另一非零游标及两个键，第三次返回零游标及其中一个重复键。预期循环调用三次、消费最后一批，并由处理层应对重复。这些响应是测试设定，不是 Redis 实测输出，不能配上“现场复现”的描述。

COUNT 一百，为何不是每次返回一百个键？

官方将 COUNT 描述为每次调用希望完成的工作量提示，不承诺返回数量固定。MATCH 的匹配结果也不能据此推算整个数据库的条目数。少于一百、零条，或者某些小型集合一次返回全部，都不应触发“分页异常”的结论。

调整 COUNT 可以作为实际负载下的取舍：较大工作量可能减少调用次数，也会改变一次调用的资源消耗。应观察待维护实例的延迟和任务进度后选择，不从文档中的默认示例推导通用最佳值。本文没有做负载测量，也没有提供吞吐或时间节省数据。

维护进度宜表达为已调用次数、已观察键数与任务仍在进行，而不是根据游标数值估算完成百分比。若读者需要可靠的总量或截止时间，必须另行定义统计与预算，不能让 COUNT 参数承担这些承诺。

重复键应该怎样处理？

文档明确允许同一元素在一轮中多次返回，责任在应用侧。如果动作是无保护地递增计数，重复一次就可能多加一次；仅在扫描循环里记一个局部已见集合，又可能在进程重启后失去保护。先确认结果是否允许重复，再决定采用天然可重复动作、持久身份记录或其他业务方案。

即使动作叫删除，也需审查并发变化。第一次看到某个缓存键后，另一个请求可能已经用同名键创建新值；稍后执行删除，可能删到这份新内容。重复删除本身通常不增加删除次数带来的副作用，但它不能证明删除对象仍是当初看到的那个版本。严格清理某批版本时，应从命名或条件操作上界定目标，而不是用“DEL 可重复”替代并发合同。

维护任务应只操作独立测试实例或明确自有唯一前缀内的键。本篇不提供对共享数据库直接删键的脚本，更不使用清库命令。重复安全的判断依赖实际业务效果，不是看到某个命令名字就自动成立。

跑完一轮，可以称为时点快照吗？

不能。官方的覆盖保证针对从遍历开始到结束持续存在的元素；只在其中一段时间存在的元素，是否出现没有确定保证。新增、删除、过期和重建都可能让观察清单无法对应某个单一时刻。完整游标循环说明这一轮按协议结束，不说明观察到了某一时刻的全部键。

站内二〇二六年十月十日的分页与稳定读取区分顺序与跨次快照；SCAN 这里更需要尊重自身的弱迭代保证，不能借用 SQL 的唯一排序方案修复。若任务要求财务式精确清点，应另选能满足一致性要求的数据来源或协调方案，并单独评估代价。

整个集合若持续无界增长，也不能无条件承诺遍历按时结束。可以给任务定义运行预算，超出时记录未完成与已处理范围；这和返回完整成功不同。Redis Cluster 的多个节点还需要各自的遍历与覆盖安排，单数据库这一圈不等于全集群这一圈。

最后一批有键，但游标已是零，还要处理吗？

要。零表示后面不需要再调用，不表示当前元素应该丢弃。测试应把这条路径与非零游标空批同时保留，因为两种提前退出写法会分别漏掉不同工作。验收时记录请求游标、返回游标、实际处理身份与最终任务状态，先验证循环，再在隔离实例检验实际版本的行为。

本文的伪代码与测试响应尚未执行。可交付的完成条件应包括游标回零、最后批次已处理、重复副作用受控，以及对遍历期变化的声明符合保证。只看到某一批为空，不能成为整项维护工作的完成依据。
