pytest 重跑后产物消失：先检查 --basetemp 的清空规则

解释 pytest 多轮目录保留与显式基目录清空，分开测试隔离、失败证据交接和 CI 产物期限。

正文

核心要点

  • 默认多轮保留与显式基目录清空是不同分支。
  • 失败文件需先移交到独立产物位置，再重跑。
  • 并发运行和敏感诊断需要独立身份与保存规则。

pytest 的临时目录不是长期产物库。指定 --basetemp 后，目录会在每轮运行前被清空；要保留失败证据，应在下一轮清空前移交到独立的运行产物位置。默认保留最近三轮目录，也只是可配置的调试便利，不能替代 CI 的产物保留规则。

每个测试独立，不等于每轮证据永久保存

pytest 临时目录指南说明，tmp_path 为每个测试函数提供独立目录，返回 pathlib.Path 对象；tmp_path_factory 则是会话范围的目录工厂。这里的隔离解决测试在哪里写，不负责回答排查者下周还能否下载这些文件。本文核对二〇二六年十一月五日的在线文档，没有运行下列测试或 CI 任务。

假设一个转换器把输入 JSON 变成报表。测试失败时，维护者希望保留输入、实际输出与一份差异说明。下一次运行只需要干净目录，排查者却需要前一次的原始内容。若把两者都叫“输出目录”，测试清理与证据保存就会争用同一个位置。应先给这两个位置不同的所有者，再讨论是否上传。

默认情况下，pytest 的基目录使用运行编号，并保留最近三轮临时目录。保留数量与策略可配置，因此“三轮”是文档默认值，不是任何项目都成立的事实。运行环境是否持续存在也很关键：临时 CI 执行器退出后，本地目录可能随环境一起消失，pytest 没有替托管平台承诺磁盘寿命。

一个转换测试怎样交接诊断文件

下面是未执行的完整教学测试。输入、输出和比较都在本次 tmp_path 内；刻意错误的 expected 模拟需要诊断的失败，不能把它当成转换器实现或已经发现的产品缺陷。

import json

def test_export(tmp_path):
    source = {"title": "campus", "rows": 2}
    (tmp_path / "input.json").write_text(
        json.dumps(source), encoding="utf-8"
    )
    actual = "campus:2\n"
    (tmp_path / "actual.txt").write_text(actual, encoding="utf-8")
    expected = "campus:3\n"  # teaching failure
    (tmp_path / "difference.txt").write_text(
        f"expected={expected!r}; actual={actual!r}", encoding="utf-8"
    )
    assert actual == expected

这个测试让失败发生前已有三个可查看的文件，但没有自行上传它们。一个候选 CI 安排是：为每轮运行分配不可混淆的运行身份，用专属 scratch 作为基目录，在测试步骤结束后执行允许失败时也运行的收集步骤，把需要的诊断复制到 artifacts 下对应运行目录。随后上传这个独立目录，并记录上传是否真的完成。测试非零退出应继续作为测试结果保留，不能为让上传执行而把失败改成成功。

收集时需要保持路径对应关系。一个测试的 actual.txt 不能覆盖另一个测试的同名文件；可以保留相对测试目录或给产物附上测试身份。复制完成后检查文件清单与摘要，再把它们关联到源码版本、测试命令和运行身份。只有上传任务返回成功，还不足以证明排查者能取回正确文件；可以再做一次授权范围内的下载与内容核对。

对于进程崩溃而没有走到最后断言的情况，收集步骤应容忍部分文件不存在，并明确标记缺失。不能为了让打包步骤通过，临时生成空的 difference.txt，再把它显示成该轮真实诊断。若输入含用户资料，应先决定哪些字段允许进入产物，必要时仅保留人工准备的最小重现样本。

--basetemp 不是自带版本管理的目录

同一份指南明确警告：显式指定的 basetemp 会在每次运行前直接清空，而且没有默认编号目录的多轮保留功能。因此它必须是专门为测试准备的可丢弃目录。不要指向项目根目录、共享导出目录或唯一的故障证据副本；路径名字里带 temp 并不能证明里面没有重要内容。

这条规则也改变失败后的操作顺序。若排查者看到失败就立即重新运行同一命令，上一轮文件可能在新的测试开始之前就被删除。正确顺序是先收集所需证据，再重跑；或者由任务系统先保存到独立产物位置。延长保留数量不会改变显式 basetemp 的清空契约，两个分支不能混用同一句解释。

选择默认目录还是显式目录，取决于谁管理生命周期。本地短时调试可以使用默认保留；CI 希望统一收集位置时，可以使用专属基目录，但要承接跨步骤保存责任。若测试要在多轮之间复用缓存，应给缓存另设规则，不要依赖偶然没有被清掉的测试文件维持正确性。

并行两轮 pytest 能共用基目录吗？

独立调用应使用各自唯一的基目录，否则一轮清空目录时可能破坏另一轮正在使用的文件。官方指南要求为并发运行配置独立基目录。这里说的是两次独立调用，不应与同一次 pytest-xdist 运行协调子进程目录的安排混为一谈；插件帮助整理一轮数据，不等于允许多个任务随意共写。

运行身份也要进入收集位置，避免两个并发任务都上传为名叫 latest 的同一目录。使用目录唯一性只是避免相互覆盖，还需核对上传服务的命名规则与权限。不能从本地不同路径直接推导远端产物也有不同身份。

只保留失败文件，怎样避免扩大敏感数据副本？

“失败才保存”并不自动降低内容敏感度。先列出排查真正需要的字段与文件，再设访问者、下载权限和到期时间。异常字符串也可能含凭据，不要只过滤输入 JSON，却把完整请求头写进差异报告。这里的保存规则应由证据用途决定，而不是继承临时目录的默认清理习惯。

保留策略还要容纳调查延迟。如果团队通常隔几天才排查失败，而产物一天后删除，上传虽然成功，任务仍没有满足使用目的。相反，不应无限保存每轮全部输入。把期限、例外延期与清理责任写入产物规则，并检查实际过期行为。

验证可以在一次性沙盒中进行：先检查所用基目录确实可丢弃，放入哨兵文件，再比较两轮运行前后文件状态及独立产物副本；随后覆盖失败、提前退出和并发两轮。每项记录源码与 pytest 版本、目录身份和可取回内容。本文没有执行这些检查，不提供文件保留成功回执。

本站二〇二六年十月十一日的fixture 隔离文章关注共享状态污染；本题补的是运行结束后的证据归属。测试需要干净目录，排查需要可取回的产物。让两种需求各自拥有明确位置，重跑才不会变成删除证据的动作。
