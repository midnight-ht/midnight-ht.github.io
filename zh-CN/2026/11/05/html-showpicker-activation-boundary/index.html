HTML showPicker点击过仍报NotAllowedError，该查哪个激活状态？

按当前HTML算法区分激活、可修改与跨源异常，用无表单的两动作教学页面保留原生日期输入，区分调用与选择结果。

正文

核心要点

  • 调用时需要短暂激活，曾经点击不提供永久资格。
  • 异步准备后提供新选择动作，但不声称所有await都会失败。
  • 正常返回不证明日期已选或业务已接受。

showPicker需要调用当下仍有效的短暂用户激活；用户之前点击过，不代表异步检查结束后仍有调用资格。先核对异常类型，再检查激活是否过期或被消耗。代码里出现await并不足以单独证明失败，历史点击记录也不能保证成功。

HTML标准的showPicker方法要求调用时具有短暂激活，否则抛出NotAllowedError。它还分别检查控件能否修改和来源限制。把所有异常都记成“浏览器不支持日期选择”，会丢掉真正可以修正的调用条件。

有过交互，不等于现在仍能调用

用户激活说明区分持续记录的sticky状态与短暂的transient状态。短暂激活会超时，也可能被某些受限API消耗。hasBeenActive回答页面是否曾有过激活；isActive回答当前是否仍处于短暂激活状态，两者不能交换使用。

假设“选择配送日期”按钮先读取可选日期，再调用showPicker。请求很快时可能仍满足调用条件，较慢时则可能已经失效；期间另一个受限操作也可能改变条件。因此，不能写成“只要用了await就必然失败”，也不能把一次成功提升为所有网络时延下都能打开的保证。本文没有测量超时窗口，不给出通用秒数。

isActive可以作为调查线索，却不会延长或授予调用资格。先读取它，再经过另一段异步工作，之后调用时条件仍可能不同。检查应尽量靠近实际调用，并保留浏览器、输入类型和前面做过的受限操作；用一张“曾点击”的截图无法还原这些条件。

必须异步准备时，给选择留一个新动作

如果准备工作确实是业务前提，可以先完成准备，再启用独立的选择入口。用户在准备完成后点击“选择日期”，处理器立即调用选择器。这把等待与选择分开，也让准备失败有明确的重试位置。它是交互设计选项，不是标准要求所有日期控件必须有两个按钮。

下面是未执行的完整HTML教学页面。准备只等待一个本地已兑现Promise，不读取远程规则；输入没有放进form，没有表单默认提交路径。页面保留原生日期输入，选择器按钮只是增强入口，不实现预约、保存或权限确认。

<!doctype html>
<html lang="zh-CN">
<meta charset="utf-8">
<title>教学日期选择</title>
<label for="date">教学日期</label>
<input id="date" type="date">
<button id="prepare" type="button">准备选择入口</button>
<button id="choose" type="button" disabled>选择日期</button>
<p id="message" role="status">可以直接编辑原生日期输入。</p>
<p id="value"></p>
<script>
const find = id => document.getElementById(id);
const say = (node, content) => { node.textContent = content; };
const on = (node, event, handler) => node.addEventListener(event, handler);
const enable = (node, yes) => { node.disabled = !yes; };
const date = find('date');
const prepare = find('prepare');
const choose = find('choose');
const message = find('message');
const value = find('value');
on(prepare, 'click', async () => {
  enable(choose, false);
  enable(prepare, false);
  try {
    await Promise.resolve(); // local teaching preparation only
    enable(choose, true);
    say(message, '本地准备完成，请再次点击选择日期');
  } finally {
    enable(prepare, true);
  }
});
on(choose, 'click', () => {
  if (typeof date.showPicker !== 'function') {
    say(message, '此环境没有该方法，请直接编辑日期输入');
    return;
  }
  try {
    date.showPicker();
    say(message, '已调用选择入口，请以日期字段当前值为准');
  } catch (error) {
    say(message, `调用未完成: ${error.name}, 仍可直接编辑日期`);
  }
});
on(date, 'change', () => {
  const current = date.value;
  say(value, current ? `当前日期: ${current}` : '当前没有日期');
});
</script>
</html>

这份准备逻辑没有真实失败来源，不能当成远程规则失败的演示。接入真实服务以后，应为失败提供可理解的反馈，并保持选择入口禁用，直到本次准备条件确实满足。原生字段能否先编辑、已经填写的日期是否需要按新规则重检，则要按产品合同决定，不能由按钮是否启用代替。

日期还要区分“可填写”与“已确认可用”。即使用户选了某天，真实配送服务也可能在提交时重新判断容量或权限。当前教学页面只显示字段值，没有把它发送到任何接收端；选择器打开不能作为预约成功的证据。

按异常名拆开排查范围

NotAllowedError对应缺少短暂激活。InvalidStateError则对应元素不可修改，例如实际元素状态不允许用户改变它；应检查目标控件，而不是继续调整请求等待时间。组件重渲染后保存的引用可能不是眼前那一个输入，调查时应确认元素身份和实际属性。

SecurityError涉及跨源iframe限制。标准对file和color输入保留历史例外，但不能把这个例外推广到date，也不能推导它们免除短暂激活或可修改条件。在嵌入式产品里，先记录顶层页面与输入所属文档的来源，再决定调用是否符合条件。

方法存在也不等于每种输入在每个平台上都有适用的原生选择器。标准算法在没有支持的选择器时可以结束，不需要因此返回一个业务错误。检测方法可用，只解决接口是否存在；后续仍要观察实际UI和用户选择。不要在捕获异常后伪造一个“已选择”状态来让流程继续。

没抛异常，为什么不能宣布用户选好了？

方法参考列出的返回值是undefined，不是一个等待日期选择的Promise。正常返回只说明这次方法调用走过相应步骤，不能证明用户接受了某个值。用户可能取消，也可能保留原值；样本通过字段变化显示当前答案，而不是await方法返回后写“完成”。

同一激活里连续打开两个选择器也不应作为默认流程。当前标准的显示算法会消耗激活，后一个调用可能已经没有需要的条件。让每个需要用户作出的选择拥有明确入口，比在一个点击里自动串起多个受限界面更容易理解和验证。

表单建议与成员校验说明候选显示不等于答案被业务接受；原生选择器同样不能承担服务端接收证明。按钮类型则提醒，辅助动作必须与提交路径分清，本例因此完全没有form。

待执行检查应覆盖直接编辑、准备后点击、缺少激活的脚本调用、不可修改控件、实际嵌入来源，以及选择或取消后的字段值。保存真实异常与浏览器版本，不预填通过记录。先判断调用有没有资格，再判断是否展示UI、用户是否给出答案，最后才讨论业务是否接受；这几项不能由一次无异常返回合并完成。

准备好了以后，原来的日期还算有效吗？

假设用户先填了周五，随后读取到的规则只允许下周。准备完成只说明规则已经拿到，不能自动替用户把周五改成下周某天。应保留原答案并说明需要重新选择，或者要求用户明确确认建议；选择器能打开不表示旧答案已经符合新规则。

另一种变化是用户在准备期间切换了配送地址。旧地址的日期范围随后返回，不能只因为按钮还在就继续作为当前选择依据。真实实现需要把准备结果关联到它所针对的地址或记录版本，过时结果不应启用当前对象的入口。这是业务状态设计推论，教学样本没有远程结果，也没有实现版本比较。

因此，第二个按钮提供的是新的激活机会，而不是冻结业务条件。准备结果是否仍属于当前对象、日期是否满足当前规则，要在各自负责的阶段检查。测试应分别改变调用时机和业务对象，避免一个选择器正常显示就掩盖另一条已经过期的数据路径。
