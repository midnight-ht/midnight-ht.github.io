Promise 手写实现：从 resolve 到链式传播，哪些语义不能省略

从 `resolve(1)` 到 `resolve(otherPromise)` 看 Promise 的解析与兑现差别，再用 reaction 队列、派生 Promise 和失败路径界定教学实现。

正文

核心要点

  • 区分解析目标锁定与最终兑现。
  • then 注册 reaction 并返回新的 Promise。
  • 用 thenable、异常和回调顺序验证实现边界。

一个最小 Promise 在 resolve(1) 后能打印 1，并不能说明它会正确处理 resolve(otherPromise)。前者只是保存一个普通值；后者要求当前 Promise 接受另一个对象的最终结果。手写 Promise 真正难的部分，不是把状态改成 fulfilled，而是确定谁拥有最终决定权、回调何时运行，以及 then() 产生的下一段链怎样接住返回值和异常。

本文按 ECMAScript 2026 的 Promise 语义解释这些边界。示例用于说明算法分工，不是完整规范实现，也没有宣称经过独立运行测试。若目标是理解原理，做一个边界清楚的教学子集足够；若要替换原生 Promise，则还要处理构造器泛型、子类、Symbol.species、拒绝跟踪等规范细节，不能把简化代码称作完整实现。

先分清状态与“解析目标已锁定”

Promise 对象有 pending、fulfilled、rejected 三种状态。fulfilled 和 rejected 是 settled；pending 表示还没有最终兑现或拒绝。容易漏掉的是 resolved 不等于 settled：一个 Promise 可以已经 resolved，却仍然 pending，因为它已锁定为跟随另一个尚未完成的 Promise 或 thenable。这里的“锁定”描述以后谁决定结果，“兑现”描述结果状态已经落定。ECMAScript 2026 第 27.2 节明确把这两个概念分开。规范原文

假设 outer 的执行器先调用 resolve(inner)，其中 inner 仍 pending，然后又调用 reject(error)。直觉上有人会认为第二次调用应该让 outer 失败，因为此刻还没有打印成功。但正确的判断不是只看 outer 的状态字段：第一次 resolve 已经把它的解析命运交给 inner，后续执行器调用的 reject 不能抢回控制权。等 inner fulfilled 时 outer 才 fulfilled；等 inner rejected 时 outer 才 rejected。因而，仅写 if (status !== PENDING) return 并在第一次 resolve 时立刻设为 fulfilled，会把“接受解析请求”和“最终兑现”错误合并。

实现可以用一个独立的 alreadyResolved 标记守住 resolve/reject 入口，再用 promise 状态表示最终结果。但这只是便于教学的内部设计，不是规范字段的逐字复刻。解析过程碰到对象值时，还要检查它的 then 属性；若 then 可调用，就把兑现过程交给 thenable 的回调。如果读取 then 本身抛错，则解析结果转为拒绝。普通对象没有可调用的 then，才按普通值兑现。

这也说明 thenable 不必是原生 Promise。只要某个对象公开了可调用的 then，解析过程就需要按约定接纳它。一个对象的 then getter 可能有副作用或抛错；then 也可能多次调用 resolve/reject。解析流程必须防止这些路径让同一 Promise 兑现多次。规范的 resolving functions 会共同关闭一次性门闩，并对解析到自身的情况拒绝，否则会形成无法完成的自引用。

then 回调不是当前 Promise 的方法调用

then(onFulfilled, onRejected) 至少做两件事：为当前 Promise 注册一对 reaction，并创建一个新的 Promise 作为返回值。若当前 Promise 还 pending，reaction 暂存；若已 settled，也不是立即同步调用处理函数，而是把 reaction job 放进 Promise job 队列。规范的 PerformPromiseThen 同时接收一个用于承接结果的 promise capability，这就是链式传播的基础。Promise.prototype.then 与 PerformPromiseThen

考虑下面这段说明代码：

const next = source.then(value => {
  return value + 1;
});

next 不是 source 本身。如果处理函数返回 3，下游 Promise 会按解析过程接收 3；如果返回另一个 Promise 或 thenable，下游会跟随它；如果处理函数抛出异常，下游转为 rejected。反过来，如果处理函数没有返回值，结果是 undefined，下游会 fulfilled with undefined。这解释了为什么只把回调放进数组、触发时直接执行，却不处理返回值的“链式实现”，只能展示回调顺序，不能实现 Promise 链。

这些状态差异在组合 API 中也会影响决策。本站的 Promise.any 解析展示了“最先兑现”并不等于“最先结束”，也不等于“业务结果有效”；理解 resolve 如何采纳 thenable，才能正确判断 any 收到的到底是哪一种候选结果。

拒绝处理也遵循同一条结果管道。onRejected 正常返回一个值时，下游通常恢复为 fulfilled；它返回 Promise 时，下游采用其结果；它再次抛错时，下游才保持拒绝并以新异常为原因。没有提供某一类处理器时，语义需要向下游传递原值或拒绝原因，而不是因为缺少函数就丢失链。实现者应把“当前 Promise 的状态”与“下游 Promise 的解析”分开维护，避免回调内部的返回结果覆盖源对象。

两个最小反例能暴露结构错误

第一个反例是同一个 pending Promise 注册两个处理器：

pending.then(first);
pending.then(second);

若对象里只保存一个 successCallback 字段，第二次赋值会覆盖第一次；兑现时只能调用 second。数组或 reaction 链表可以保留两次订阅，但这不是全部工作：每个 reaction 还必须关联自己的下游 Promise capability。一个处理器抛错，只应拒绝它自己的下游 Promise，不应改变源 Promise，也不应阻止其他 reaction 被排入队列。

第二个反例是已 fulfilled 的 Promise：

let finished = false;
Promise.resolve(1).then(() => console.log(finished));
finished = true;

Promise reaction 通过 job 队列异步执行，因此回调看到的是 true。如果教学实现发现状态已经 fulfilled 就立即调用处理器，输出就会变成 false。原来的同步例子适合说明 executor 在构造期间同步运行，却不适合作为 then 调度的证据。这里也要谨慎措辞：Promise job 是规范抽象；浏览器和 Node.js 的宿主如何把相关任务与其他队列整合，是宿主环境的调度问题。

教学实现应该拆成哪些职责

一个可读的实现草图可以分为四个模块，而不是让 resolve 同时做所有事。第一，状态存储只负责 pending/fulfilled/rejected 和最终结果，终态不可逆。第二，resolvePromise 接受一个解析值：普通值兑现；自身引用拒绝；对象则读取一次 then，处理读取异常，并对可调用 thenable 安排接纳过程。第三，then 生成下游 Promise，并把 fulfilled/rejected 两类处理函数、目标 Promise 和一次性 resolve/reject 包装成 reaction。第四，reaction job 执行时捕获处理函数异常，将返回值交给下游的 resolvePromise，没有处理函数时执行相应的值/原因透传。

代码结构上，可能会有 fulfill(value)、reject(reason)、resolve(value) 三个看起来相近的入口。它们不能互相替代：fulfill 直接完成状态转换；reject 直接记录拒绝；resolve 负责判断普通值、Promise、thenable 和自解析，再决定如何最终兑现。把内部函数命名为 resolve 却直接执行 status = FULFILLED，是许多简化教程中最危险的偷换。

处理 thenable 时还需要注意重入。直接同步执行第三方对象的 then，可能在外层解析流程还没保存保护状态时再次调用回调，产生意外交错。规范把 thenable 接纳过程放进 Promise job；这不仅关乎“异步看起来更统一”，也是为了避免调用其 then 时同步重入解析函数。读取 then 的动作与调用 then 的动作也应区分：规范先取得该属性，后续 job 再以一次性 resolving functions 调用它。CreateResolvingFunctions 与 NewPromiseResolveThenableJob

若学习目的只是掌握状态推进，可先实现普通值、拒绝、异步 reaction 和多订阅；下一步加入派生 Promise 的返回值与异常转换；再做 thenable 吸收、自解析保护和重复调用保护。每一步都保留明确的“不支持”列表。不要让一段只对原生 Promise 和固定回调有效的代码，借着 MyPromise 这个名字显得符合标准。

用测试矩阵判断边界，而不只看成功示例

至少列出这些输入：普通值 resolve、reject 后接 catch、resolve 一个 pending Promise、resolve 一个已 fulfilled Promise、thenable 兑现、thenable 拒绝、then getter 抛错、thenable 连续调用两种回调、Promise 解析自身、多个 then 订阅、回调返回普通值、返回 Promise、回调抛错、已完成 Promise 的 then 调度顺序。每项要写预期结果和预期顺序，不要只看控制台里出现了“成功”。

错误示例也要覆盖。若第二次 then 覆盖第一次，测试应记录两个处理器都必须各自得到一次结果；若回调被同步执行，测试应比较同一调用栈内标记变量的值；若 thenable 先 resolve 再 reject，测试检查下游只采纳第一次有效解析路径；若回调抛错，则检查源 Promise 是否仍保持 fulfilled，而派生 Promise 是否拒绝。这样可以把“状态没坏”“链没断”和“回调顺序正确”分成不同断言。

本文没有运行这些示例代码，因此矩阵是建议的验证设计，不是实测报告。ECMAScript 规范能告诉我们内建 Promise 应有的算法语义，但不能证明一段手写实现已经符合所有细节。若准备做兼容性实现，需要把规范条款和完整测试套件作为独立工作；若目标是教学，则把支持范围写在代码旁边，读者反而更容易知道自己学到了哪一层。

Promise 实现最值得保留的判断，不是“几行代码也能造一个 Promise”，而是把解析、兑现、reaction 调度和下游传播分成不同职责。只要这四件事仍混在一个状态分支里，普通成功示例就会给出过度乐观的印象。先明确教学实现支持到哪里，再用失败路径验证每个边界。
