Linux 上 npm 或 Yarn 报 ENOSPC：先确认 inotify 哪个额度耗尽

解释 Node 开发服务器的 inotify watcher 错误，区分 watch 数、实例数和队列限制，再按进程、文件描述符与环境边界验证修复。

正文

Error: ENOSPC: System limit for number of file watchers reached 出现在 npm 或 Yarn 的开发命令中时，通常不是磁盘空间不足，也不一定是 Node 包管理器自身故障。Linux inotify 不再接受新的 watch，常见原因是当前真实用户已经达到 max_user_watches，但 max_user_instances、每个实例的事件队列、文件描述符限制以及容器宿主机策略也可能造成相近现象。正确处理顺序是确认是哪一类资源耗尽，找出创建 watcher 的进程，再决定减少监控范围还是调整内核上限；直接抄一个很大的数只会掩盖资源来源。

npm 和 Yarn 为什么会碰到内核 watcher

安装依赖通常不会持续监听整个项目；报错常发生在 npm run dev、测试监视模式、构建服务或 IDE 启动后，因为这些进程为了及时重建，会递归监控源文件。现代前端仓库可能含多个 workspace、生成目录和依赖副本，监控程序可能为目录或文件建立大量 watch。inotify 是 Linux 内核提供的文件系统事件接口，用户态程序通过实例和 watch 描述符订阅变化。限制按真实 UID 等内核维度管理，并非“单个项目最多只能有多少文件”。同一用户下的编辑器、语言服务、测试进程和多个开发服务器会共同消耗额度。

这也解释了为什么停止一个终端里的服务后，错误有时仍在：后台 IDE 或另一个仓库可能继续持有 watch。相反，一个文件很多但未运行监听器的仓库，不会仅凭文件数量就消耗所有 watch。程序还可能监控目录树中的符号链接或生成目录，使实际监控集合比开发者在源码目录里看到的范围更大。应先把“仓库很大”变成可验证的进程与 fd 证据，而不是把目录体积当成配额统计。

先读三个 inotify 限制，不要把它们混为一谈

在多数 Linux 发行版中可查看：

cat /proc/sys/fs/inotify/max_user_watches
cat /proc/sys/fs/inotify/max_user_instances
cat /proc/sys/fs/inotify/max_queued_events

max_user_watches 限制每个真实用户可创建的 watch 数；max_user_instances 限制这个用户可创建的 inotify 实例数；max_queued_events 决定每个实例可排队的事件数量，超限时事件可能丢失并报告队列溢出，而不是简单等同于“watch 数不足”。读取当前值只能说明限制，不会告诉你已经用了多少。man-pages 文档说明，内核通过这些 /proc/sys/fs/inotify 参数控制 inotify 所消耗的资源。

还要区分普通文件描述符上限：进程的 ulimit -n 或 systemd 的 LimitNOFILE 影响可打开的 fd，和 inotify watch 配额不是同一个限制。程序可能因为无法创建更多 inotify 实例或打开文件而报错，应用又把底层错误包装成看似相同的 ENOSPC。应结合完整错误堆栈、进程日志和内核日志判断，不把所有 ENOSPC 都用调高 watches 处理。

找出谁持有 watch，以及到底监控了什么

先退出已知的开发服务器和测试 watcher，再观察报错是否消失。这是一个有信息量的对照实验：如果停止某个长期进程后新 watcher 能正常创建，说明需要检查该进程的监听范围和生命周期；若没有变化，还要检查同一 UID 下其他会话、容器和服务。可以查看进程的 inotify fd 信息：

for p in /proc/[0-9]*; do
  for fd in "$p"/fdinfo/*; do
    grep -q '^inotify ' "$fd" 2>/dev/null && printf '%s %s\n' "$p" "$fd"
  done
done

这条示例循环读取当前可见的 /proc，权限、PID namespace 和系统配置会限制可见范围；它是线索，不是完整的全机账本。/proc/<pid>/fdinfo/<fd> 中的 inotify 条目可显示该 fd 关联的 watch 描述符，进一步可以将 PID 对应到命令和父进程。检查时注意多个进程可能属于编辑器的子进程，关闭其中一个窗口并不保证监视器立即退出。

若每次重启开发服务器都会迅速耗尽，优先检查配置的监视根目录和忽略规则：是否把 node_modules、dist、构建缓存、生成代码或挂载的大目录纳入了递归监听；是否同时开了多个 dev server；是否 watcher 未随热重载或测试进程退出而释放。缩小范围、使用工具原生的 ignore 设置，通常比全局调大额度更容易解释、回滚和复核。不同工具配置项的名称不同，不要直接复制未经核对的 --no-watch 参数。

何时调高 max_user_watches

当证据显示确是 watch 配额不足、监听范围合理，而且开发工具有明确的并发监控需求时，才考虑提高 fs.inotify.max_user_watches。临时试验可以使用：

sudo sysctl -w fs.inotify.max_user_watches=131072
cat /proc/sys/fs/inotify/max_user_watches

131072 在这里是演示用的候选值，不是通用推荐或该环境实测结果。应从当前值开始小幅上调，并观察运行进程和内核内存，而非不加判断地设为 524288。watch 资源有内存成本；提高限制只扩大可用上限，不会自动释放遗留 watcher，也不会修复监控了错误目录的问题。

如果确认长期设置必要，应使用发行版支持的 sysctl 配置目录，例如 /etc/sysctl.d/ 下单独命名的文件，记录变更原因、回滚值和维护责任，再通过该发行版的 sysctl 加载方式应用。不能把 sysctl -p 误写成“重新启动系统”的必要操作；它读取指定配置（默认通常是 /etc/sysctl.conf），而新配置目录的加载行为取决于系统服务与发行版。容器里可能无权修改宿主机内核参数，修改容器内文件也不一定改变宿主机限制；应由拥有该内核 namespace 和策略权限的管理员处理。

如何验证修复，而不是只看数值变大

记录调整前的错误、限制值和相关进程；一次只改一个条件，例如先停止第二个监听服务，或只提高 watch 限额。重启原来失败的开发命令，确认 watch 能成功创建，再观察一段正常使用时间是否稳定。测试结束后关闭服务，确认 watcher 释放、CPU 和内存没有因重复监视而持续上升。若调整后仍报错，检查实例数、fd 限制、事件队列溢出和服务容器隔离，而不要继续盲目提高同一个参数。

还要按失败类型采取不同措施：如果只在单个大型 workspace 出现，先排除生成目录并比较监控根；如果同一用户多个项目都失败，检查 UID 级共享消耗；如果容器内值与宿主机值不同，查明它是否处于受限环境；如果只在大量事件突发时出现队列溢出，关注应用是否及时处理事件和是否正确重扫文件状态。inotify 事件通知并不总等价于“每次改动必有一个独立事件”，程序必须考虑事件合并或溢出后的重新扫描。

本文没有在目标 Linux 主机上执行上述命令，数字和循环均是说明性示例。实际配置前应确认发行版、systemd/container 限制、运行用户和变更回滚路径。本站另有一篇关于 Node fs.watch 监听文件被替换后失效 的说明，讨论的是文件替换后 watcher 绑定对象的边界，和本篇的 inotify 额度耗尽是两个不同故障。

来源与边界：核对 Linux man-pages《inotify(7)》对三项 /proc/sys/fs/inotify 限制的定义；命令示例不宣称已在特定发行版执行。npm/Yarn 只是触发开发监听的常见入口，具体 watcher 实现、排除目录参数和容器限制以实际工具及发行版文档为准。
