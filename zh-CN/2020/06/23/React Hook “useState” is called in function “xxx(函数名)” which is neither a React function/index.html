React 报错：useState 调用位置不合法，先区分组件、Hook 与普通函数

逐步判断 useState 报错来自小写组件名、普通函数调用、条件调用还是类组件，并给出可验证的修复路径。

正文

报错 React Hook "useState" is called in function "newDeviceForm" which is neither a React function component nor a custom React Hook function 时，不能只凭错误里的函数名断定改一个大写字母就完事。React 只允许 Hook 在正在渲染的函数组件或自定义 Hook 的顶层调用；而小写函数在 JSX 中通常会被当作普通函数，规则检查器也不会把它识别为组件。先确认调用者是谁，再看调用位置是否稳定，最后验证调用链中有没有把组件当普通函数执行。

为什么小写函数名会触发这条提示

假设源码是 function newDeviceForm() { const [name, setName] = useState(''); return <input value={name} onChange={e => setName(e.target.value)} />; }。即使这个函数返回 JSX，<newDeviceForm /> 也会按小写 HTML 标签处理；React 组件惯例使用大写开头，例如 <NewDeviceForm />。如果它实际被作为普通 JavaScript 函数调用，newDeviceForm()，它也不会因此成为组件。命名是 React 与静态规则识别组件的一条约定，不是给任意函数套上的权限开关。

只有在这个函数本来就负责渲染一块界面，并且由 React 以组件方式渲染时，把函数和所有引用它的 JSX 名称改为 NewDeviceForm 才是合适修复。之后检查调用点是否写成 <NewDeviceForm />，而不是 NewDeviceForm()、回调里直接调用或传给一个在渲染期间普通调用它的工具函数。若函数只是生成数据、验证表单或处理点击，它不应拥有组件 Hook 状态；应把状态留在上层组件，再通过参数和回调传下去。

先确认它到底是组件、自定义 Hook 还是普通函数

组件名以大写开头，返回 JSX，并由 React 树以 JSX 或 createElement 方式创建。自定义 Hook 名以 use 开头，例如 useDeviceForm，内部可以调用其他 Hook，但它自己也必须在组件或另一个 Hook 的渲染路径上按顶层调用。普通函数不应调用 useState。三个类别的修复不同：组件保持界面状态；自定义 Hook 封装可复用状态逻辑；纯函数接收输入并返回结果。

如果 newDeviceForm 只是处理提交，改名为 useNewDeviceForm 并不自动正确。自定义 Hook 只应在另一个组件或 Hook 的顶层调用，不能为了绕过 lint 把事件处理函数包装成 Hook。例子：function NewDeviceForm() { const [name, setName] = useState(''); function submit() { return saveDevice(name); } return <button onClick={submit}>保存</button>; }。Hook 在组件顶层建立状态，点击时只运行普通的 submit。若多处需要共享表单状态逻辑，可以抽出 useDeviceForm，组件顶层调用它，再把返回值交给事件回调。

大写改名修不了条件调用和嵌套调用

function NewDeviceForm({ visible }) { if (!visible) return null; const [name, setName] = useState(''); ... } 仍然违反 Hook 规则。组件名称正确，但一次渲染可能在 visible 为 false 时调用零个 Hook，在 true 时调用一个，React 无法按固定调用顺序对应状态槽位。把 Hook 移到提前返回之前，或者将条件放进组件返回的 JSX 中。

同样，不能在 if、循环、try/catch、事件处理器、普通嵌套函数，或传给 useMemo、useEffect 的回调中调用 Hook。条件加载应在顶层调用 Hook，再用条件决定是否使用结果；点击事件需要更新已有 state，可以调用 setName，不能在点击时第一次调用 useState。类组件也不能调用函数组件 Hook，应继续使用类的 state 生命周期，或把负责状态的部分迁成函数组件。

反例尤其容易误导：把 newDeviceForm() 改名为 NewDeviceForm()，却仍然在另一个函数内部直接调用。静态规则可能不再报告小写命名问题，但 React 没有把它作为组件边界渲染，Hook 的调用位置仍不可靠。正确的组件组合写成 <NewDeviceForm />，让 React 管理其渲染周期；如果需要返回值而非界面，保留普通纯函数并从参数提供数据。

用 lint 与最小重现定位，而不是猜测

先在报错行上下查看函数声明、所有调用点和组件树。将函数名改为大写后，全局搜索旧名称，确保 JSX 标签、导出、路由和测试没有漏改。再检查 Hook 是否位于函数体顶层、条件返回之前，以及这个函数是否确实通过 JSX 渲染。若仍不清楚，可以临时将组件缩到只保留一个顶层 useState 和一段 JSX；最小重现应保留真实调用方式，否则可能把调用链问题隐藏掉。

React 官方建议使用 eslint-plugin-react-hooks 的 rules-of-hooks 规则。运行项目现有 lint 命令（本篇不假定每个项目脚本名称相同），重点看 lint 发现的是命名识别、嵌套位置还是条件路径。规则检查通过只证明静态规则没有发现对应违规，不证明 UI 行为正确。还应在组件初次渲染、条件开关前后和交互后检查状态是否保留在预期实例中；若条件切换导致组件被卸载再挂载，状态重置可能是组件树变化，而非 Hook 顺序错误。

如何区分修好报错和解决了状态问题

一个假设的表单场景可以按三层验证：输入组件作为 <NewDeviceForm /> 出现在 React 树；useState 在组件函数开头每次渲染都按同一顺序调用；提交函数只读取或更新既有状态，不在事件发生时调用 Hook。随后执行项目 lint、相关组件测试，并在真实表单交互中验证输入、提交、隐藏再显示时预期行为。这里是检查方法，不是本仓库执行某个 React 应用后得到的结果。

修复前后要保留区分：如果错误由小写组件名导致，改名并修正 JSX 调用点；如果 Hook 在普通函数或事件回调中，移动状态责任或提取合规的自定义 Hook；如果存在条件或循环调用，改成固定顺序；如果是类组件，迁移到函数组件或使用类状态。不要一概把组件改写成 class，也不要因一条提示就改依赖版本。React 的 Hook 规则说明了哪些调用路径受支持；它不决定应用应采用何种状态架构。选择依据是这个函数是否拥有 UI 生命周期、是否需要跨组件复用逻辑，以及状态应由哪个 React 组件负责。

如果重命名后仍出现错误，下一步检查实际运行的 React 与 lint 插件配置、monorepo 中文件采用的 ESLint 配置，以及函数是否由 React 渲染。贴近报错文本的最小 diff、完整调用点和 lint 结果，比隐藏警告或增加忽略注释更能缩短排查时间。若组件名正确、Hook 位于顶层且经 JSX 渲染仍报错，就把这三项证据作为进一步排查材料，而不要继续机械改名。

相关背景可参阅本站关于 React 外部状态快照与订阅；它讨论的是并发渲染下外部状态读取接口，不替代本文的 Hook 调用规则。

来源与版本边界：本文依据 React 官方《Rules of Hooks》《Your First Component》和《Reusing Logic with Custom Hooks》当前文档。错误提示来自原始历史文章记录；newDeviceForm 场景未在本轮运行原项目重现，代码片段均为解释规则的假设例子，不是声称已执行的修复日志。
