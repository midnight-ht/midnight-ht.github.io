浏览器文件上传该用 FormData 还是 Base64？

普通文件接口优先把 File 放进 FormData；只有文本协议要求时才编码为 Base64。本文解释 multipart boundary、编码体积、上传进度与服务端持久化之间的边界。

正文

核心要点

  • 常规 multipart 接口直接发送 File，不手动设置 Content-Type。
  • Base64 是文本编码，不是压缩；8 MiB 文件的编码主体约 10.67 MiB。
  • 浏览器传输进度到 100% 仍需等待 HTTP 与业务校验结果。

浏览器选中的文件不是“文件流数组”。input.files 返回 FileList，其中每个 File 都携带文件名、修改时间等信息，并继承 Blob 的二进制数据能力。对常见网页上传，通常应把这个 File 直接放进 FormData，再用 XMLHttpRequest 或 fetch 发送；只有接口明确要求文本编码时才把它转成 Base64。两条路径解决的是不同协议问题，把它们混在一起会增加内存占用，还容易让 multipart 请求因边界参数不匹配而无法解析。

下面的例子和尺寸计算用于解释机制，没有在某个业务项目或特定浏览器版本中执行。RFC 7578 定义 multipart/form-data 的分段与 boundary；浏览器构造 FormData 请求时会生成与请求体对应的 boundary。因此应用代码应设置字段和发送请求，不应自行拼接 multipart 内容，也不应手动把请求头写成一个没有 boundary 的 multipart/form-data。服务端收到请求仍须检查权限、大小、类型和内容，客户端传来的文件名、MIME 与进度百分比都不能代替服务器完成确认。

选取文件得到的是 FileList

最小的文件选择控件如下：

<label for="attachment">选择附件</label>
<input id="attachment" name="attachment" type="file" accept="image/png,image/jpeg">

accept 用来提示选择界面哪些类型较相关，不是安全校验。用户确认选择后，input.files 是一个 FileList，可按索引访问其中的 File；它不是 JavaScript 数组，也不是已经启动的网络流。File 描述一次被选择的文件并提供名称、修改时间等只读信息；Blob 表示不可变的原始字节数据。浏览器标准允许 XHR 直接发送 File 或 Blob，不要求先把内容转成字符串。

如果控件允许多选，应遍历 files，并明确每个文件是否对应一个独立表单字段，还是重复使用同一字段名。后端框架对重复字段名的解释可能不同，接口契约需要定义多文件的顺序、最大数量和部分失败语义。若界面只允许一个附件，也仍要处理未选择、用户取消、重新选择同名文件和选择文件后表单被重置等情况。文件名相同不代表字节相同；把文件名当作对象 ID 会使覆盖、缓存和审计变得含混。

Multipart 上传：让浏览器生成 boundary

对普通表单上传，浏览器的 FormData 适合传递文件与少量字段。下面用 XHR 展示带上传进度的形状。它是结构示意代码，未连接本文站点或真实后端执行：

function upload(file, url, onProgress) {
  const data = new FormData();
  data.append('file', file, file.name);
  data.append('purpose', 'avatar');

  return new Promise((resolve, reject) => {
    const xhr = new XMLHttpRequest();
    xhr.open('POST', url);
    xhr.upload.addEventListener('progress', (event) => {
      if (event.lengthComputable) {
        onProgress?.(event.loaded, event.total);
      }
    });
    xhr.addEventListener('load', () => {
      if (xhr.status >= 200 && xhr.status < 300) resolve(xhr.responseText);
      else reject(new Error(`HTTP ${xhr.status}`));
    });
    xhr.addEventListener('error', () => reject(new Error('network error')));
    xhr.addEventListener('abort', () => reject(new Error('aborted')));
    xhr.send(data);
  });
}

这里没有调用 setRequestHeader('Content-Type', 'multipart/form-data')。请求头中的 boundary 参数必须和请求体里分隔每个字段的标记一致。如果应用手动设置一个没有 boundary 的头，浏览器仍可能构造带随机边界的请求体，服务端解析器却不知道应使用哪个值，于是报“缺少 boundary”、字段为空或请求无法解析。排查时同时查看网络面板的请求头和原始 payload：应能看到 multipart/form-data; boundary=...，正文中的各段使用同一边界。如果二者不一致，先移除手动 Content-Type，再复测，不要试图从错误响应推断文件本身损坏。

文件名可以作为 FormData.append 的第三个参数，但这是客户端元数据。RFC 7578 明确规定 multipart 每一段具有 Content-Disposition，filename 参数可能出现；接收端不能把它当作可信路径。服务端应产生自己的存储键，对显示名称做安全处理，并执行业务授权和内容检查。accept、扩展名及浏览器报告的 MIME 只能改善体验或作为低成本筛选条件，不能证明上传内容安全。关于隔离状态、对象版本与下载授权，参见本站文件上传隔离与验证边界。

什么时候 Base64 才是合适的

Base64 把任意字节编码成文本字符，适用于 JSON 等只接受文本字段的既有协议、少量内嵌数据或必须以文本保存的接口。它不会压缩文件。RFC 4648 的 24 位输入分组产生 4 个输出字符，因此编码主体长度约为原字节数的 4/3，另有填充与 JSON 引号等开销。假设文件是 8 MiB，主体编码约为 10.67 MiB；这是公式计算示例，不是网络实测。实际请求还可能同时保留原始 File、编码字符串、JSON 字符串和解析后的服务端副本，峰值内存取决于浏览器与运行时实现。

若协议需要 data URL，可通过 FileReader.readAsDataURL(file) 读取；结果不是裸 Base64，而是形如 data:image/png;base64,... 的字符串，前缀包含媒体类型和编码标志。发送前需遵循接口契约决定是否剥离前缀，不能假定服务器接受 data URL。读取失败应处理 error，用户取消或组件卸载则应允许取消读取。大文件若经过多次字符串拷贝，移动设备容易因内存峰值而变慢或崩溃；即使网络最终成功，Base64 路径也可能让前端在真正上传前先完整读取整个文件。

不要把 btoa(atob(value)) === value 当作通用 Base64 校验器。atob 处理的是 Base64 到字节字符串的解码，不是 UTF-8 文本解码；Unicode 文本需要明确字符编码转换。更重要的是，编码格式正确只说明字母表、填充等满足解码要求，不能证明内容符合业务类型、未被截断或安全。服务端仍应限制输入大小，严格解码并验证解码后的字节。如果目标只是上传文件，直接传 File 能避免不必要的完整字符串副本。

将 Base64 字符串还原为 Blob

若既有接口返回裸 Base64 或 data URL，先按协议确定 MIME 的可信来源，并把 Base64 部分解码为字节。atob 的返回值是每个字符代表一个字节值的二进制字符串；不能直接把这串字符当作 Unicode 文本。示意实现如下，未在项目中执行：

function dataUrlToBlob(dataUrl) {
  const comma = dataUrl.indexOf(',');
  if (comma < 0) throw new Error('data URL is missing a comma');
  const header = dataUrl.slice(0, comma);
  if (!/^data:.*;base64$/i.test(header)) throw new Error('expected base64 data URL');
  const mime = header.slice(5).replace(/;base64$/i, '') || 'application/octet-stream';
  const binary = atob(dataUrl.slice(comma + 1));
  const bytes = new Uint8Array(binary.length);
  for (let i = 0; i < binary.length; i++) bytes[i] = binary.charCodeAt(i);
  return new Blob([bytes], { type: mime });
}

这段代码仅说明字节转换，不构成严格的 Base64 或文件安全验证。若输入来自 JSON 字段而非 data URL，应该单独实现符合该接口格式的解析，不要猜测逗号前缀；若浏览器环境没有 atob，应使用经过目标运行时验证的解码实现。Blob 的 type 仍是一个标记，不会检查数据内容，也不能改变字节。若确实需要有文件名的对象，可用 new File([blob], name, { type })，但上传时直接给 FormData.append 第三个参数通常更简单。

进度到 100% 不代表服务器已经保存

XHR 的 upload 对象可监听进度事件。只有 lengthComputable 为 true 时，loaded / total 才适合展示百分比；事件描述的是浏览器侧传输进展，不代表服务端已经完成病毒扫描、格式解析、对象存储写入或数据库事务。用户看到 100% 后，页面仍需等待 XHR load，检查 HTTP 状态和接口响应。HTTP 413 表示请求体超过某一服务层限制，415 表示媒体类型不被接受；它们都可能发生在上传进度显示完成之后。超时、error、abort、HTTP 非 2xx 以及业务返回“待检查”也应分别呈现，不能统统称为上传成功/失败。

如果产品必须展示上传进度，XHR 是直接可见的选择；如果只需要提交并读取结果，fetch 的接口形式往往更简洁，但不要仅凭代码短就假设它提供相同的上传进度事件。具体浏览器和运行环境能力应按目标平台验证。无论传输 API 如何选择，都应该给用户明确的取消、重试与重复提交语义。服务端若已收下文件但响应丢失，客户端盲目重试可能创建重复对象；通过请求 ID、幂等键或业务对象约束处理重试，比依靠前端按钮禁用更可靠。

用故障路径决定传输方案

一个典型决策可以从合同开始：若后端接受 multipart，选择 File→FormData→请求，不增加 Base64；若只接受 JSON 文本且必须兼容既有接口，记录 Base64 的大小、读取和内存成本，再评估是否调整接口。比如假设某图片为 8 MiB，Base64 主体约 10.67 MiB；若入口代理上限按原文件大小设计，请求可能在服务端业务代码运行前因编码后的体积而被拒绝。此时问题不是“base64ToBlob”转换错，而是协议与上游 body limit 不匹配。反过来，如果客户端已经持有 JSON Base64、而一个适配层必须将其转为 multipart，转换为 Uint8Array/Blob 后再 append 可以保留字节语义，但仍应限制大小并避免无必要复制。

上传排障可以按四个观测点推进。选择阶段记录文件数量、预期大小和用户取消；序列化阶段看请求头 boundary 与字段结构；传输阶段区分浏览器进度、网络中断和 HTTP 响应；持久化阶段查服务端对象 ID、校验状态和可取回性。浏览器网络面板中，若 multipart 头缺 boundary，先修请求构造；若请求完整但响应 413，检查代理、框架、应用与存储的限制是否一致；若进度到 100% 后返回业务拒绝，界面应呈现“已传输，服务端校验未通过”，而不是回滚成没有选文件。上述路径是诊断设计，不代表本文运行了服务端或真实文件上传。

传输方式和安全策略要分层。浏览器给出的文件名、MIME 与大小并非可信声明；服务端应自行限制 bytes、校验实际内容、处理解析器资源消耗，必要时先放入隔离区，再决定是否能公开或下载。XHR 进度仅能帮助用户理解网络阶段；对象存储成功也不意味着下游检查完成。本站文件上传隔离与验证边界讨论了待检查对象、处理结果与下载授权的关系。

参考资料与验证边界

  • W3C File API Editor’s Draft：FileList、Blob、File、FileReader 及与 XHR 的关系。当前页面注明它是编辑草案，适合作为工作中标准文本，不应误称为最终推荐标准。
  • WHATWG XMLHttpRequest Living Standard：FormData 发送、upload 事件、ProgressEvent、状态码与错误事件。
  • RFC 7578：2015 年发布的 multipart/form-data 标准，定义 boundary 和每段的 disposition 等格式。
  • RFC 4648：2006 年发布的 Base-N 编码标准，描述 Base64 分组、填充与规范编码。

这些资料支撑格式和 API 事实。选择直接上传还是 Base64、如何配置大小限制与状态体验，是根据接口合同和运行环境作出的工程判断。示例没有在浏览器、后端或设备上执行；实施前应使用目标浏览器检查实际 multipart 请求，并在服务端验证文件限制和持久化结果。
