Geolocation 2020-08-25

浏览器返回了经纬度，为什么仍不能当成精确地址？

用浏览器 Geolocation 时，回调成功不等于位置准确。本文解释 HTTPS、授权、精度半径、缓存、超时与 watch 生命周期，并给出失败诊断和用户回退设计。

正文

核心要点

  • Geolocation 返回位置估计，不保证是 GPS 或真实门牌。
  • accuracy、timestamp、maximumAge 必须结合业务容差解释。
  • 授权、HTTPS、操作系统定位和 iframe 政策是不同门槛。
  • 持续跟踪要调用 clearWatch，并给用户手动选择路径。

Geolocation 成功回调只说明浏览器交付了一个位置对象，不证明坐标来自 GPS、足够新，或能精确指出门牌。先检查 coords.accuracy、timestamp 与业务容差，再决定采用结果、接受一次新请求、退回粗略区域，还是让用户手动选择。把“取到经纬度”写成“精准定位成功”，会把传感器估计和业务判断混为一谈。

API 给的是位置估计，不是传感器承诺

navigator.geolocation 是浏览器提供的位置接口。页面调用 getCurrentPosition() 获取一次位置；调用 watchPosition() 请求后续变化，并通过 clearWatch() 停止。W3C 规范说明底层信息源可以来自 GPS、网络信号或其他系统能力，API 不规定来源顺序，也不保证返回值就是设备真实位置。因此代码不应该把“用了 Geolocation”翻译成“手机 GPS 已精确读数”。W3C 2026 工作草案；其最新文件是 2026 年 11 月 18 日的候选推荐草案，仍可能变化；2024 年 W3C 推荐标准则是已发布的 Recommendation。

位置对象至少要按三个字段一起读：latitude、longitude 是 WGS84 坐标；accuracy 是以米表示的位置精度半径；timestamp 表示位置采集时间。一个坐标即使数值看起来合理，若精度半径很大或时间过旧，也可能不适合当前任务。最新草案还调整了精度概率措辞；这是草案内容，不应被误读成所有现有浏览器已经按同一概率实现。产品层面应把 accuracy 当作估计质量信息，而不是地面真值证明。

例如，门店查找只想先列出附近区域，可以接受较粗位置，再让用户从候选门店中确认；送货地址填写则不应仅凭浏览器坐标自动提交。所谓“可用精度”由任务决定：地图初始居中、城市级筛选和精确签到的容差不同。API 不替产品给出这条阈值，开发者必须把阈值与失败回退设计在一起。

浏览器显示“允许”，为什么请求仍会失败？

读取位置前至少要区分安全上下文、用户授权、操作系统定位状态和嵌入策略。安全上下文是第一道门槛；普通部署应使用 HTTPS，localhost 是常见本地开发例外。非安全上下文可能以 PERMISSION_DENIED 结束请求，因此遇到这个错误不能立刻推断“用户点了拒绝”。MDN 的 Navigator.geolocation 页面也标明该属性要求安全上下文。

浏览器权限与操作系统权限不是同一项开关。W3C 2024 推荐标准明确提到：用户可能已经允许浏览器站点使用定位，却在系统设置中禁止浏览器访问位置服务。页面若处于跨来源 iframe，Permissions-Policy 还可能阻止使用该接口；默认策略是 self，父页面需要按实际嵌入关系授予策略，iframe 元素本身也要允许 geolocation。反过来，用户许可不能越过服务器发出的禁止策略。可从页面是否 HTTPS、当前 iframe 来源、响应头和浏览器/系统设置逐层排查，而不是反复调用 API。MDN 的 geolocation Permissions-Policy 说明。

请求最好由明确的用户动作触发，并在系统提示之前说明用途和替代方式，例如“用于显示附近门店，不保存精确位置；也可以手动选城市”。W3C 要求取得明确许可，并建议接收方仅在必要时请求、用途完成后处理或丢弃位置，说明保留时间、用途与共享方式。定位权限不是把坐标永久保存或转发给后端的授权。这里讲的是工程与规范建议，不替代目标地区的数据保护法律审查。

enableHighAccuracy 只是提示

enableHighAccuracy: true 不是“打开 GPS”的命令，也不保证误差会变小。规范将它定义为用户代理可参考的提示；高精度尝试可能增加耗电或等待时间，设备也可能没有更准确的数据，用户代理还可以忽略该选项。对仅需按城市筛选内容的页面，默认低成本请求通常更符合目的；只有任务确实需要较精细位置且用户知道原因时，再请求高精度。

maximumAge 是页面能接受的缓存位置最长年龄，单位为毫秒。它不是服务端缓存时间，也不能保证浏览器一定保留缓存。像附近列表这种对几十秒前位置仍有意义的功能，可以允许短缓存；签到、路线重新规划等场景则需结合 timestamp 拒绝过旧结果。timeout 限制的是位置获取阶段的等待，不包括用户决定是否授权，也不包括文档从隐藏状态变为可见所耗时间。把 timeout 设为五秒，并不代表整个按钮流程从点击到回调必然最多五秒。

这三个选项应该从业务成本倒推：多旧的坐标仍可用？要等多久才显示手动入口？高精度能改变什么决定？如果没有清晰答案，就不要盲目把超时压低或一直启用高精度。

一次性读取的示例与状态边界

下面是未在真实浏览器或设备上执行的示例，展示怎样将浏览器回调包装成 Promise，并分别判断接口可用、请求失败、精度不满足与数据过旧。误差阈值只是产品假设，实际项目需要按场景确认；代码不会把坐标发给服务器。

function requestPosition() {
  if (!("geolocation" in navigator)) {
    return Promise.reject({ kind: "unsupported" });
  }

  return new Promise((resolve, reject) => {
    navigator.geolocation.getCurrentPosition(
      resolve,
      error => reject({ kind: "geolocation", code: error.code }),
      {
        enableHighAccuracy: false,
        timeout: 12000,
        maximumAge: 30000
      }
    );
  });
}

async function chooseNearbyArea() {
  try {
    const position = await requestPosition();
    const { latitude, longitude, accuracy } = position.coords;
    const ageMs = Date.now() - position.timestamp;

    if (ageMs > 30000 || accuracy > 1500) {
      return { state: "coarse-or-manual", accuracy, ageMs };
    }

    return { state: "usable-estimate", latitude, longitude, accuracy, ageMs };
  } catch (error) {
    return { state: "manual", reason: error.kind, code: error.code };
  }
}

这里的 30 秒和 1500 米是假设值，不是标准要求。业务组件应把 usable-estimate、coarse-or-manual 和 manual 映射成真实页面状态，例如“正在定位”“显示大致范围”“选择城市”。即使采集成功，也不必立即上传完整经纬度；如果功能只需要地区，可以在客户端或服务端按明确规则转换为较粗区域，并避免保留精确原始坐标。若确实必须传输，先说明用途、访问者、保留期限与删除方式，并用符合系统设计的传输和存储保护。

如何读错误码，避免把错误信息直接展示给用户

标准把请求失败分成三类代码：PERMISSION_DENIED（1）表示请求未获许可或处于非安全上下文；POSITION_UNAVAILABLE（2）表示获取位置失败；TIMEOUT（3）表示位置获取超过请求时限。系统权限被拒也可能映射为权限错误。它们说明失败阶段，不一定提供唯一根因。开发环境可将错误码、页面是否安全、frame 来源和是否收到成功回调写入不含坐标的诊断记录，再决定是否检查权限策略或设备设置。

不要直接把 error.message 当作面向用户的文案。W3C 规范说明该字段供开发者调试，历史上只提供英文文本，建议按 code 生成应用自己的本地化提示。对权限拒绝，告诉用户可以去设置重新授权或手动输入；对暂时不可用或超时，显示重试和替代入口；不能假装重试会改变用户刚才拒绝的决定。错误提示也不要带上用户坐标，因为失败路径本来就不需要额外暴露位置。

watchPosition 需要明确的结束条件

只有当产品确实需要持续观察移动时才用 watchPosition()。它返回 watch ID，组件卸载、用户离开地图或关闭“持续定位”模式时都应调用 clearWatch(watchId)。在 React 等组件框架里，清理函数要绑定到这次订阅的 ID，避免旧页面卸载时误清理新页面的观察任务。只取一次当前位置却启动 watch，不但增加授权和电量成本，还会制造反复更新页面或反复请求后端的机会。

也要考虑权限或定位能力可能在持续观察期间变化。更新错误要显示可恢复状态，成功位置则仍要按精度与时间过滤；收到新回调不代表一定比上一条更适合业务。若页面会把位置写入历史轨迹，应另行记录用户选择、保留和删除路径。对于不需要轨迹的功能，保存“用户选定的门店/区域”通常比保存高精度坐标更贴近业务需求，但这属于数据建模判断，不是 Geolocation API 强制要求。

怎样验证：把浏览器模拟和真机结果分开

先做一张状态矩阵：接口不存在；HTTP 非安全页面；HTTPS；用户允许和拒绝；系统层禁止定位；跨来源 iframe 策略允许和禁止；获取成功但 accuracy 超出业务阈值；返回缓存但 timestamp 过旧；获取阶段超时；持续观察后清理。每种状态都验证页面文案、回退入口和是否发生网络上报。自动化工具可以用规范提供的定位模拟能力检查固定坐标和错误分支，但这只验证代码面对给定输入的行为，不证明真实手机的系统设置、传感器质量或室内定位精度。

有条件时再用目标浏览器和设备做单独验收，并记录浏览器版本、设备定位开关、权限选择、页面协议、嵌入来源、获得的 accuracy 与 timestamp。不要把一次真机结果外推为所有设备表现。跨域 iframe 和 Permissions-Policy 的兼容性也要对照目标浏览器版本测试；MDN 页面提示这一策略指令在浏览器中的支持并不完全一致。若精度达不到业务需求，正确处理通常是给出粗略结果或让人确认，而不是把 enableHighAccuracy 无条件改成 true。

如果“浏览器显示允许”后仍然失败，先沿请求链查安全上下文、当前 frame 与 Permissions-Policy，再看浏览器站点许可和操作系统定位服务，最后检查超时、缓存与定位源可用性。这个顺序能避免把不同层次的问题都归结成“浏览器不支持”。因此，这个接口只提供带有来源不确定性、时间属性与精度半径的位置估计；是否足以完成签到、导航或附近搜索，需要由应用按风险和容差做最后判断。站内摄像头 Permissions Policy 生命周期边界也区分了嵌入政策、用户授权和资源生命周期，可对照阅读。

验证说明：本文代码是解释性示例，未在真实浏览器、手机或系统权限环境执行；上线前应按上面的状态矩阵做目标浏览器和设备验收。
