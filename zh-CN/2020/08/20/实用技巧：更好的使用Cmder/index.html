Cmder 的 PATH 和右键菜单不是一回事：按启动方式选集成

输入 cmder 命令和在资源管理器当前目录打开终端是两件事。本文解释 PATH、Cmder Here、/REGISTER USER|ALL、权限与搬迁后的验证边界。

正文

核心要点

  • PATH 用来查找可执行文件；Explorer 菜单把当前文件夹交给 Cmder。
  • Cmder 会把自己的 bin 注入其 shell；不要因此把整个 vendor 目录写进系统 PATH。
  • /REGISTER USER 与 /REGISTER ALL 作用范围不同，按设备管理边界选择。
  • 安装目录变化后应检查 shell 注册命令是否仍指向当前 cmder.exe。

PATH 适合解决“输入程序名找不到”，右键菜单适合解决“在当前目录打开 Cmder”。两者改变的系统位置不同，先按你要启动的动作选入口。只想从资源管理器当前目录开终端，不需要把 Cmder 的全部目录加入全局 PATH；只想从命令窗口启动 cmder.exe，也不必写入 Explorer 注册表。

先分清你希望哪一个动作变简单

原始问题里其实有两个需求：按 Win+R 或从一个新命令窗口输入名称启动 Cmder；以及在某个项目目录上点右键，让新开的终端直接位于该目录。前者依赖 Windows 如何找到可执行文件，后者依赖 Cmder 在 Windows Shell 中注册“Cmder Here”。

这不是文字上的区别。PATH 是按顺序排列的一组可执行文件搜索目录；同名程序出现在多个目录时，目录顺序会影响找到哪个版本。Explorer 菜单则保存一条启动命令，并把用户选择的路径作为参数传入。一个设置改变“找谁”，另一个改变“从哪里打开”。把两者混成一个安装步骤，会让只为当前用户解决的小问题扩散成整台电脑的 PATH 或注册表变更。

可以先问自己：我需要从任意工作目录输入 cmder 吗？还是只是希望在资源管理器当前目录打开它？如果只是第二种，最短的可撤销路径是注册菜单；如果只是第一种，给启动器做用户级命令入口更合适。便携版还要考虑搬动目录后入口是否仍有效。

PATH 改的是可执行文件搜索范围

Microsoft 对 Windows PATH 的说明是：命令解释器会按该变量包含的目录查找可执行文件。Cmder 的安装目录通常包含 Cmder.exe，把这个目录加入当前用户 PATH，能够让新启动的命令解释器尝试按名称找到这个程序。但这不等于安装完成、确认了正确版本，也不等于菜单已经出现在资源管理器中。

先区分 Cmder 自己的 shell PATH 与 Windows 的用户或系统 PATH。当前 Cmder 仓库 README 说明，放在 %cmder_root%\bin 中的工具会被注入 Cmder 启动的 shell 环境；共享安装还可以使用独立的用户配置目录，其中的 bin 按默认规则进入 Cmder shell，而 opt 不会自动注入。这个机制让 Cmder 能携带工具而保持一定便携性，并不要求把 %cmder_root%\vendor 下所有程序再塞进 Windows 全局 PATH。

例如，个人电脑上安装目录固定，且确实需要从新开的 cmd.exe 用名称启动 Cmder，可以只考虑把包含 Cmder.exe 的目录加入该用户 PATH。相反，如果你把压缩包放在 U 盘、会移动目录，或者电脑上有多个 Cmder 版本，固定绝对路径就容易变成“命令仍能启动，但启动的是旧副本”。把随包 Git、Perl 或其他可执行目录放入系统 PATH，还可能让其他程序拿到不同于预期的同名工具。这里的建议来自 PATH 的搜索机制与 Cmder 的便携设计，不是说某个目录在所有机器上都一定冲突。

PATH 更改通常由之后创建的进程继承；一个已经开着的命令窗口不会因为你改了设置就自动获得新环境。验证时先开一个新的命令提示符，再用 where cmder 查看命令解析到了哪些位置，并检查输出是不是你准备使用的那一份。where 查到路径只能证明搜索结果，不证明该目录的安装完整，也不证明 Cmder 的 shell 配置正确。若没有命中，应回到用户 PATH 的目录拼写、分号分隔和新进程继承检查，不要继续追加更多 Cmder 子目录碰运气。

“Cmder Here” 是单独的 Shell 菜单注册

当前 Cmder README 将 /REGISTER USER 与 /REGISTER ALL 列为注册 Windows Shell 菜单的选项，并给出 /UNREGISTER 对应的撤销命令。README 的操作示例是进入 Cmder 所在目录，在管理员命令提示符运行 .\cmder.exe /REGISTER ALL，成功后可在资源管理器目录上通过右键打开“Cmder Here”。如果你选择的目标仅是当前 Windows 用户，仓库参数表也列有 USER 作用域；不需要为了给自己加菜单就默认请求整机范围。

源码把这个作用域具体化：USER 写入当前用户的 HKEY_CURRENT_USER\Software\Classes，ALL 调用 HKEY_CLASSES_ROOT。后者是 Windows 对 HKEY_LOCAL_MACHINE\Software\Classes 与当前用户 Classes 项的合并视图，实际写入还受已有同名项与权限影响；所以不要把注册表根键名本身误读为“Cmder 一定直接写进一个独立的整机配置区”。Cmder 文档仍把 ALL 作为给所有用户注册的选项，并示例要求管理员提示符。注册命令读取启动器自身的可执行路径，再将它写入菜单命令，并把 Explorer 传来的目录作为启动参数。因而遇到“Access Denied”时，先判断你是否真的需要所有用户都看到该菜单；若只为自己使用，选择 USER 范围通常比把整台电脑的注册表操作都提权更合适。若管理员管理的设备要求全体用户共享，再按照项目 README 的管理员步骤执行 ALL，并在目标 Windows 版本上检查菜单对其他账户是否可见。

以下只是按当前仓库文档整理的未执行示例，实际参数行为应与手头安装包的版本核对：

cd /d D:\Tools\Cmder
Cmder.exe /REGISTER USER

如果决定撤销当前用户的菜单，文档中对应的方向是 Cmder.exe /UNREGISTER USER。注册后要实际打开资源管理器，在一个普通文件夹背景或文件夹上查看菜单，并确认启动后的目录确实是刚选择的位置。注册命令退出或显示了某条文字，都不足以替代这个交互验证；本次写作没有在 Windows 设备上执行这些命令。

一个便携目录搬迁的故障路径

假设你把 Cmder 从 D:\Tools\Cmder 移到 E:\Apps\Cmder。命令行入口可能因为 PATH 里仍有旧目录而启动旧版本；Explorer 菜单则可能仍调用注册时记录的旧可执行文件路径。两种症状看起来都像“Cmder 坏了”，但证据不同：新命令窗口的 where cmder 检查 PATH 命中顺序；菜单打开失败则需要确认 shell 注册指向的启动器位置。

更稳妥的处理顺序是先选定新安装目录，再在新目录下用同一作用域执行注销和注册；随后新开命令窗口，再从资源管理器验证目标文件夹。若你依赖用户 PATH，也同时删除旧 Cmder 安装目录并留下一个目标目录。不要只在当前 Cmder 窗口里临时修改 PATH 后就认定持久设置已经完成，因为这只影响当前进程及其子进程。

目录搬迁前后应避免同时留着旧版本菜单和新版本菜单。源码根据启动器自身路径写入注册命令，这是“搬迁可能留下失效入口”的代码依据；我们没有在真实 Windows 注册表中观察过上述假设场景。若运行 /UNREGISTER 后旧入口依然存在，先核对当初注册时使用的是 USER 还是 ALL，再以同一范围检查，而不是盲目重复所有提权操作。

当前版本与旧教程的边界

Cmder 项目仍保留 1.x 维护线；截至 2026-11-27 查阅官方 Releases 页面，页面置顶的是标记为 Pre-release 的 Cmder 2.0.0 RC 1。RC 介绍列出的包包括 Windows Terminal、ConEmu 和 launcher 变体，并说明该版本开放社区测试。当前 README 中有 /REGISTER、/START 等说明，但某个安装压缩包究竟包含哪个终端、启动器与 Git，应以该次发布的资产和升级指南为准，不应把 1.x 的所有快捷键、配置文件路径与 RC 包当作完全相同的操作界面。

如果 /REGISTER USER 在你手上版本无效，先用该版本随附帮助与对应 release 说明核对，不要直接复制陌生教程提供的 .reg 文件。Cmder 日常可执行文件查找错误还有另一类原因，见环境 PATH 中的 JDK 路径问题排查。那篇处理的是变量内容错误；本文处理的是“程序名查找”和“Shell 菜单启动”两类集成入口，不能把改 PATH 当作右键菜单修复。

决策可以收敛成三行：输入程序名需要解析时，检查用户 PATH 和 where cmder；从当前目录开终端时，按个人或整机范围选择 /REGISTER USER|ALL；使用便携版时，把目录搬迁作为需要重新检查两个入口的变更。每次只改满足当前需求的一处，然后在新命令窗口或资源管理器中验证真实启动目标。这样能让配置范围与目的相称，也留出明确的撤销路径。
