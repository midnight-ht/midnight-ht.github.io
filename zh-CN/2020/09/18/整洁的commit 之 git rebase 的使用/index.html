Git rebase -i 整理提交前，先划定共享历史边界

用 git rebase -i 重排、合并或改写尚未共享的提交；按范围、冲突、补丁对比和远端协作边界检查整理结果。

正文

核心要点

  • rebase 会重建提交并改变提交 ID；先判断分支是否已被他人消费。
  • squash、fixup、drop 改变提交序列，todo 的范围与顺序都需要核对。
  • 冲突解决后用测试、补丁系列比较和分支策略确认结果；强制推送不是固定收尾步骤。

Git rebase -i 适合整理尚未共享的提交序列：你可以重排提交、合并修补、改写消息、拆分改动或删除误提交的补丁。但它会重建提交，改变提交 ID；如果其他人已经基于这些提交继续工作，整理就不再只是个人清理。安全做法是先确定共同基线与共享边界，再编辑待办列表，逐段检查重放结果，最后比较新旧补丁系列。已经发布的共享历史通常应通过 git revert 等新增提交修复，而不是把强推当成 rebase 的固定收尾步骤。

先判断需要整理的是哪段历史

假设一条功能分支从 origin/main 分出后，依次产生了“增加导出入口”“修正文件名”“补测试”三个提交。交付前可以用 git log --oneline --decorate --graph 看清分支图，再确认工作区干净、基线准确：

git status --short
git fetch origin
git log --oneline --decorate --graph --boundary origin/main...HEAD

这些命令只读仓库状态；本文没有在当前仓库执行示例中的重写操作。若本地分支已经与远端共享，git fetch 后不能只凭“本地看起来是三条提交”决定范围。需要确认团队是否已取走这条分支，以及远端是否有人在其上推送。找错上游提交，会让 rebase 重放多于预期的提交；把本地 HEAD~3 当作固定边界，也容易在新增提交后整理错范围。

确认分支提交序列确实从某基线开始后，使用明确的上游范围比凭记忆写数字更便于审阅：

git rebase -i origin/main

如果目标是从某提交之后开始编辑，也可以指定它的父提交，例如 git rebase -i ^。关键不是哪一种写法更“高级”，而是 todo 列表中的第一条必须是你打算纳入整理的提交。执行前先检查 git merge-base origin/main HEAD 与提交图；若分支还没正确跟上远端基线，先决定是先合并还是把主题分支重放到新的基线上。交互式 rebase 既能重排、合并，也能移除提交，因此范围错误会把有用补丁一起删掉。

todo 列表是操作计划，不是 commit message 编辑器

交互式列表通常以 pick 开始。常用动作包括 reword（保留补丁、改消息）、edit（停下来修改该提交）、squash（与前一个提交合并并编辑合并消息）、fixup（与前一个提交合并，舍弃当前消息）和 drop（不重放该补丁）。缩写形式也有效，但团队共享的操作记录最好使用完整词，降低误读成本。

下面是一个假设的列表，第一条建立可理解的功能提交，第二条是针对同一行为的修复，第三条是独立测试：

pick   a1b2c3d Add CSV export
fixup  e4f5a6b Fix filename on Windows
pick   1122334 Cover export naming with tests
reword 5566778 Update export documentation

fixup 只适合补丁确实属于前一个提交、而且原修复消息不需要单独保留的情况。如果第二条实际上修复另一个独立缺陷，就将它保留为单独的 pick，否则历史会把两个可单独回滚或审查的变更压成一块。squash 会让你编辑合并消息；不要把所有行都改成 squash，第一条没有前驱可以合并。修改 todo 时也不要删除行尾的提交 ID；描述文字供人阅读，Git 依据动作和对象 ID 执行计划。

原文的演示是在 HEAD~2 上把第二条设为 s，随后在第二个编辑器中整理消息。这个演示能说明流程，但不应该照搬其 git push origin master -f 作为通用步骤。若处理的是个人未推送分支，整理后可普通推送；若公共分支历史已被消费，重写会迫使下游开发者修复自己的提交关系。通常应保留共享历史并新增修复提交。确需替换远端私有分支时，先约定暂停推送、记录预期远端 SHA，并评估精确的 lease 保护；不要习惯性使用不带边界检查的 --force。

冲突时把“继续”和“跳过”分开

rebase 逐个重放补丁。若新基线上已有对同一文件的不同修改，Git 会停在无法自动合并的提交，保留冲突标记。此时先用 git status 查看当前停在哪个提交，再逐个打开冲突文件，判断双方代表的是同一需求、不同需求，还是旧补丁已被上游实现。人工解决后把文件加入暂存区，运行必要的测试，再执行：

git add path/to/file
git rebase --continue

--continue 表示“已解决当前提交，继续重放序列”，不是“忽略冲突”。git rebase --skip 会把当前提交整个跳过，可能丢失该提交唯一包含的业务改动；只有确认补丁已被新基线等价实现，或者经团队判断无需保留时才使用。若发现范围、基线或解决方向错误，可以运行 git rebase --abort 回到开始前的分支状态。Git 文档也说明冲突发生时可选择解决后继续、返回原状态或跳过有问题的提交。发生大量冲突时，逐提交核对原因比追求一次性“绿色结束”更安全。

整理完成后核对补丁是否仍在

命令成功不意味着提交系列符合预期。至少检查新提交图、工作区和测试：

git status --short
git log --oneline --decorate --graph origin/main..HEAD
git diff origin/main...HEAD

对比重写前后的补丁系列，可使用 git range-diff <旧范围> <新范围>。它以补丁相似性配对提交，帮助发现某个提交消失、补丁内容改变或顺序变化；它不是语义等价证明，也不会替代代码审查或测试。对 edit、冲突解决和重排后的每个逻辑步骤，都应确认该提交仍能解释、构建或通过对应测试。若中间提交会被其他人逐个检出，使用交互式 exec 在重放过程中运行项目检查也有帮助；但测试命令必须适合每个中间状态，不能假设最终状态的测试结果覆盖了历史中间点。

最后的推送取决于共享状态，而不是 rebase 命令是否运行过。普通 git push 要求远端可快进；如果因重写而不是快进，先停下核对哪些人可能已经基于旧提交开展工作。Git 的 --force-with-lease=: 能要求远端 ref 仍是你明确记录的提交，但它依然会替换历史，仍需团队协调。默认 --force-with-lease 依赖远端跟踪分支，后台 fetch 可能使预期判断不如显式 SHA 清晰。不要以“rebase 必须强推”为规则；个人未公开分支、已公开协作分支和受保护主分支有不同处理方式。

适用条件与边界

重写历史解决的是提交序列可读性与补丁组织，不会自动修复代码质量、丢失的需求背景或错误测试。rebase 默认会把历史线性化；若原分支含有需要保留的合并拓扑，应研究 --rebase-merges，并留意被重建的合并提交中人工冲突解决不会自动以原方式复现。对签名提交、审计政策、已发布标签和已部署构建，提交 ID 变化也会影响外部引用，需要单独评估。

一个可验证的完成标准是：范围与基线有记录，todo 计划只合并真正相关的修复，最终提交图与补丁差异可解释，工作区干净，相关测试通过，推送方式符合分支共享政策。若目标是撤销已共享错误改动，应参考用 git revert 恢复共享历史，而不是照抄旧文末尾的强制推送命令。官方资料：git-rebase 手册、git-push 手册、git-range-diff 手册。
