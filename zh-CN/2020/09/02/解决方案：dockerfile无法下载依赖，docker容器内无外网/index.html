Dockerfile 下载依赖失败？先分清 daemon、builder 和 RUN 网络

Docker 构建失败可能发生在镜像拉取、BuildKit 的 RUN 步骤或运行容器。按失败阶段检查 DNS、代理、路由和 TLS，避免把 host 网络当通用修复。

正文

核心要点

  • FROM 拉镜像由 daemon 与 registry 路径负责；RUN 下载依赖走构建步骤的网络。
  • DNS、代理、出口路由和 TLS 错误对应不同故障层，宿主机有网不能证明 builder 可达。
  • host 网络需要额外 entitlement；只在受控诊断后考虑，不应作为通用开关。

一次 Dockerfile 构建里的依赖下载失败，不能直接推出“容器没有外网”。一次镜像构建至少经过客户端、Docker daemon、BuildKit builder、Dockerfile 的 RUN 步骤和软件仓库等多个网络边界：拉基础镜像时是 daemon 访问 registry；执行 apt、pip、npm 等命令时，是构建步骤访问软件源；构建完成后运行容器又是另一条路径。先看失败发生在哪个步骤，再分别核对 DNS、路由、防火墙、代理、证书和缓存，才能避免为修复一条路径而扩大整个 daemon 的网络权限。本文命令均为诊断示例，未在当前机器执行。

先看失败是在 FROM、RUN，还是运行容器以后

如果日志在 FROM 前后报 registry timeout、unauthorized 或 manifest 不存在，问题发生于镜像拉取或认证。此时 Docker daemon 或 builder 的镜像来源、代理、证书、账号配置比 Dockerfile 中的 apt-get 更相关。若 FROM 已成功，错误出现在 RUN apt-get update、pip install 或 npm ci，才应该检查构建步骤拿到的网络与软件仓库。若 build 成功、运行后应用才无法请求外部 API，则应该看运行容器网络；改构建参数不一定改变它。

先用可读日志确认卡在哪里：

docker buildx ls
docker buildx inspect --bootstrap
docker buildx build --progress=plain --no-cache .

这些检查帮助区分当前 builder 和构建步骤的输出。no-cache 用于诊断是否有旧层遮蔽问题，不是永久网络修复，也会让更多层重新执行。某些 builder 是独立的 docker-container 或远程 worker，故障路径可能不同于宿主机终端或普通 docker run。BuildKit 官方说明提到其构建图求解与缓存机制；它会并行执行相互独立的构建步骤，也会复用可用缓存；如果一次构建看似“突然成功”，应确认依赖下载步骤是否实际执行，而不是由缓存命中跳过。

为什么宿主机能联网不等于构建步骤能联网

宿主机的 /etc/resolv.conf 是线索，不是容器网络的完整配置。Linux 上常见一种情况是 NetworkManager 使用 dnsmasq，宿主机 resolv.conf 指向 127.0.0.1 或 127.0.1.1。对宿主机来说这是本地解析器；对容器网络命名空间来说，127.0.0.1 是容器自己，容器里未必有 DNS 服务。Docker 官方排障文档指出了这一类 loopback resolver 问题。此时加一条公共 DNS 可能让公网域名暂时可解析，却同时让公司内网域名失效，甚至违反网络策略。

容器实际使用的解析方式还取决于网络，具体见 Docker 的网络与 DNS 文档。连接默认 bridge 的容器通常拿到宿主机解析配置的副本；连接自定义网络的容器会使用 Docker 嵌入式 DNS 地址 127.0.0.11，由它转发外部查询。具体网络和 resolver 不同，固定修改宿主机某个 nameserver 不一定作用于当前 builder。先确认当前构建使用哪种 builder、网络和 DNS 配置，再测试目标域名，而不是只 ping 一个公共 IP。

可以在不安装软件的临时测试镜像里分别检查名字解析和 HTTPS 连接；前提是镜像本身已可取得。注意，ping 失败不等于 HTTPS 一定失败：目标可能不回应 ICMP，而 TCP/443 仍可用。相反，解析出 IP 也不证明路由、防火墙、代理认证和 TLS 握手均正常。把 DNS 查询、目标连接和证书错误分开记录，才能知道要改哪一层。

把 registry、构建步骤与 daemon proxy 分开

Docker Engine daemon 负责获取基础镜像并访问 registry；构建步骤下载包时，执行 apt 或 npm 的进程还需要自己的代理环境。Docker 官方daemon proxy 文档与CLI proxy 文档明确区分 daemon 与构建步骤的代理参数。Docker CLI 的 ~/.docker/config.json 中 proxies 配置可向新建容器和构建提供 HTTP_PROXY、HTTPS_PROXY、NO_PROXY 等代理变量，但不因此配置 dockerd 本身。若 daemon 拉镜像失败而 RUN 正常，应查 daemon 侧代理；若 FROM 正常、RUN 下载失败，应看 build 环境中的代理变量与软件包客户端配置。

公司网络若要求代理，可按所用环境选择 daemon 或 CLI 配置。Docker Engine 的 daemon proxy 文档提到配置文件或 daemon 启动环境；Docker Desktop 使用自己的代理设置，daemon.json 中的代理配置会被忽略。CLI 的代理配置可能包含账号、内网域名或凭据，Docker 文档特别提醒这些值可能暴露环境信息。不要把代理地址连同认证信息写入 Dockerfile 的 ENV、复制到镜像层或提交到公共仓库。需要临时指定构建代理时，使用受控的客户端配置或 build-arg，并按组织保密策略管理值；构建参数可帮助构建步骤，但不能自动替代 daemon 的 registry 代理。

NO_PROXY 配错也常见：公共域名被错误排除，或者内部 registry 被发送到外部代理。观察日志中实际要访问的主机，把代理绕过列表限定在必要域名；不要为“先让它工作”把 NO_PROXY 设成星号或把所有网络流量转去未经批准的代理。在 Docker Desktop 上，虚拟网络承载容器请求，宿主机防火墙或 VPN 软件限制 Docker Desktop 后端进程时，宿主机浏览器有网而容器无网并不矛盾。

只有出现 DNS 证据时才调整 DNS

Linux Engine 默认的 daemon 配置文件通常是 /etc/docker/daemon.json；rootless 模式和 Desktop 的配置位置、管理方式不同。若日志确认 Docker 使用不可达的本机 loopback resolver，并且修复宿主机 DNS 或 NetworkManager 无法解决，可以在 daemon 配置中设置适用于本地和外部域名的 DNS 服务器。组织内部服务需要企业 DNS；只配公共解析器可能让依赖内部域名的构建失效。修改已有 JSON 时要合并字段，不要覆盖其他 daemon 设置；配置文件和命令行重复指定同一选项也可能阻止 daemon 正常启动。

示意配置如下，地址是占位示例，不代表推荐公共 DNS：

{
  "dns": ["192.0.2.53"]
}

修改前先检查 daemon 配置文件当前内容和服务管理方式。Docker daemon 配置文档说明，在常规 Linux Engine 下默认位置是 /etc/docker/daemon.json；rootless 模式不同。应用配置后，按实际系统的服务管理方式重启 daemon，并验证配置是否加载，再验证原先失败的同一域名。若使用 Desktop，网络由它的虚拟化环境管理，不能把 Linux Engine 的配置步骤机械搬过去。若错误来自防火墙阻断出口、缺少代理、证书链不可信或仓库限流，DNS 修复不会改变结果。

构建网络选项不是通用的“打开外网”

Dockerfile 的 RUN --network 可以控制特定 RUN 步骤的网络类型。官方 Dockerfile reference 当前列出 default、none、host；none 让该步骤没有外网，host 使用构建主机的网络环境。host 模式需要显式开启 network.host entitlement，对权限边界有影响。它可能暴露构建环境中原本隔离的可访问资源，所以不应作为遇到下载失败后的第一条命令。docker build 的 --network 会控制构建 RUN 指令的网络模式，但不能修复仓库宕机、错误 URL、包管理器证书或凭据问题。

正常情况下先恢复默认网络，只有日志表明构建步骤本身需要宿主网络路径，且构建器政策允许时，才测试单条指令的 host 模式。若 host 模式确实让它工作，这只是定位线索：接下来应找出默认隔离路径中缺少的路由、代理、DNS 转发或防火墙规则，把修复收敛到最小权限。长期依赖 host 构建可能在共享 builder、CI、rootless 或不同平台下失效，也可能让构建有机会访问宿主机可达的内部服务。

若目标是离线或可重复构建，方向可能相反：先将依赖准备成受校验的 wheelhouse、镜像缓存或内部制品，再让依赖安装步骤用 RUN --network=none 证明不会偷偷访问外部网络。Dockerfile 文档给出的离线安装例子就是将包放入构建上下文，再以 --network=none 安装。无网络成功不只证明“能构建”，还说明安装输入边界清楚；但它不能证明缓存内容可信，哈希与来源仍需验证。

用症状矩阵安排下一步，而不是连续改系统配置

若基础镜像拉取就失败，检查 daemon 的 registry DNS、路由、代理、证书和认证；不要从 RUN 的 apt 参数开始。若镜像成功而 RUN 出现“could not resolve”，比较 builder 内 DNS 配置与宿主机 resolver，特别确认是否把 loopback 当成远端 DNS。若 DNS 有结果但 HTTPS timeout，调查出口路由、防火墙、企业代理和目标仓库可用性。若 TLS 显示未知 CA 或证书日期错误，应检查基础镜像 CA、拦截代理证书和系统时间，不能使用关闭 TLS 校验来掩盖信任问题。若软件仓库返回 403 或 429，分别核对代理认证、访问权限和限流；它们都不是网络接口缺失的证据。

一个完整的示例路径是：CI 从内部 registry 拉取基础镜像成功，但构建步骤在 npm ci 时报告包源超时。先用 plain progress 确定失败位于 RUN，而不是 FROM；确认实际选中的 buildx worker。再核对内部代理是否只配置在 CI 宿主环境、是否被安全地传递给 Docker CLI 的构建步骤，以及 npm 指向的 registry 是否在 NO_PROXY 规则里。若构建日志显示 DNS 解析失败，则先查 builder 的解析器；若出现代理拒绝或 TLS 错误，处理认证或企业 CA。调整后清缓存重跑一次相同步骤，检查日志显示真正访问了预期代理和 registry，再构建应用并验证依赖清单和包校验。这个流程是示例，没有在此执行，也不证明所有 CI 平台都有相同网络边界。

完成条件不是宿主机浏览器能访问网站，而是：失败步骤已定位；对应的 builder、daemon 或 RUN 环境已确认；只修改相关代理/DNS/出口配置；同一依赖下载能够从干净构建重复；代理凭据未写入镜像；受限构建不会意外访问外部资源。要进一步区分构建与运行容器网络，可看Docker run 的网络获取边界；依赖更新频率和构建缓存的影响可参见包索引更新与 Docker 缓存。

官方资料

Dockerfile 的 RUN --network 参考说明 default、none、host 三种模式与 host entitlement；daemon 排障文档覆盖 loopback resolver 与 DNS 配置，dockerd 参考列出 daemon DNS 选项。网络行为见 Docker 网络概览；代理边界分别见 daemon proxy 和 CLI proxy 文档。Docker Desktop 的虚拟网络与代理条件见 Desktop networking，构建器默认行为见 BuildKit 文档。

这些资料说明 Docker 当前接口和条件，不是当前文章示例已经在某台服务器构建成功的证明。
