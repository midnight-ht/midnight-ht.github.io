服务器服务已启动但公网不通：按监听、路由和访问规则分层排查

从进程监听地址到 Alibaba Cloud 安全组、firewalld、网络 ACL 与返回路径逐层定位新服务端口不可达，并避免误开放管理端口。

正文

服务进程显示“已启动”，不等于公网客户端能连接。一次 TCP 访问要经过客户端路由、云公网地址映射、ECS 网卡上的云安全组、子网网络 ACL、Linux 主机防火墙、进程监听 socket，以及响应返回路径。排查时先在服务器确认目标地址和端口确实有人监听，再从服务器本机、同 VPC 主机、外部网络逐层测试；每次只改一处规则，使用最窄的来源范围，并验证规则命中了预期网卡和区域。安全组不是启动服务的替代品，允许所有 IPv4 来源也不应成为所有端口的默认授权对象。

第一层：进程是否监听了对的地址和协议

先查进程，而不是先在控制台开端口：

sudo ss -lntup
sudo ss -lntp 'sport = :8080'

列表中的回环地址只接受本机连接；公网流量到达网卡也不会被这个 socket 接收。IPv4 通配监听表示服务绑定本机所有 IPv4 地址，IPv6 通配监听的具体 IPv4 映射行为受系统 socket 配置影响。典型地址写法如下，实际服务端口要替换为应用监听的端口：

127.0.0.1:8080   仅本机回环
0.0.0.0:8080     本机所有 IPv4 接口
[::]:8080         IPv6 通配地址

还要确认实际协议：浏览器访问 HTTP 使用 TCP，UDP 服务则需按 UDP 方式测试；客户端连到 TCP 端口并不能证明 UDP 已开放。进程在容器或独立 network namespace 中时，宿主机的 ss 视图也可能看不到容器内监听，反过来容器里的回环地址也只代表容器自己的接口。

先用服务本身的健康接口在本机验证，再通过服务器私有地址测试。若回环测试成功而私有地址失败，优先检查监听绑定和主机本地过滤；若本机两种都失败，回到进程、端口、协议与服务日志，不要继续增加云端允许规则。以下命令里的地址仅为示例：

curl -v http://127.0.0.1:8080/health

ss 是观测当前 socket 的快照，不证明服务能处理正确路径，也不证明公网路由存在。

第二层：云安全组规则是否匹配实际入站流量

Alibaba Cloud ECS 安全组是作用于网卡的虚拟访问控制。规则需要匹配流量方向、协议、目标端口和来源地址；同一实例关联多个安全组时，规则集合及其优先级共同决定结果。先核对目标 ECS/ENI 实际关联的安全组、地域与 VPC，再查看入方向规则。TCP 8080 示例应明确写成 TCP、目的端口 8080/8080、授权来源以及允许策略；如果应用只供办公室或一台跳板机访问，来源可用固定地址的 /32 或管理网段，而不是所有公网地址。

云控制台中 80/8080 表示一个端口范围，不是“只开 80 和 8080”；需要多个离散端口时，应使用产品支持的端口列表或拆分规则，并核对规则数量限制。入方向是客户端访问 ECS 的方向；把规则错误地加到出方向不能解决入站连接。阿里云安全组对已建立连接具有状态特性，通常无需再添加同一连接响应流量的出方向规则，但这不意味着应用的其他外连依赖也会自动满足。

测试 TCP Web 端口时，可以从受控外部机器执行 curl -v --connect-timeout 3 http://公网地址:8080/ 或 nc -vz 公网地址 8080，同时在服务器运行 sudo tcpdump -ni any 'tcp port 8080'。若外部 SYN 在服务器抓包中完全看不到，故障更可能在公网映射、路由、云规则或 ACL；若 SYN 到达但服务器没有 SYN-ACK，应查主机防火墙、监听地址和内核路由；若握手完成却应用报错，网络已经到达进程附近，继续看 HTTP/TLS、虚拟主机和应用日志。抓包只能说明观察接口看到了哪些包，不自动指出是哪条策略丢弃。

第三层：firewalld 的运行时规则与永久规则

如果系统使用 firewalld，先读状态、默认区域和网卡关联区域：

sudo firewall-cmd --state
sudo firewall-cmd --get-active-zones
sudo firewall-cmd --zone=public --list-all

只检查 --list-ports 容易漏掉通过 service 名称允许的规则，也可能查看了错误 zone。端口规则必须落在实际承载该流量的 zone。下面先将 TCP 8080 临时加入 public 区域，再持久化；执行永久更改后 reload，使永久配置成为当前运行配置：

sudo firewall-cmd --zone=public --add-port=8080/tcp
sudo firewall-cmd --permanent --zone=public --add-port=8080/tcp
sudo firewall-cmd --reload
sudo firewall-cmd --zone=public --query-port=8080/tcp

这是命令示例，不代表任何生产主机已经执行。firewalld 官方说明，未加 --permanent 的改动只影响运行时配置，重启或服务重载后可能消失；永久配置和运行时配置要分别核对。若 firewalld 未运行，不要为了“让命令有输出”盲目启动服务：先确认系统实际使用 nftables、其他主机防火墙，还是云侧策略。启动一个此前未启用的防火墙可能把 SSH 管理连接一并挡住；变更前要有带外控制台或明确回滚通道。

把网络路径当成一组可证伪的假设

假设应用监听所有 IPv4 接口，服务器本机健康检查通过，但家中网络访问超时。不要同时重启服务、开放一段端口并关闭 firewall。依次记录证据：外部抓包是否收到 SYN；安全组中是否存在 TCP 8080 入站允许，来源是否包含测试客户端公网 IP；子网 ACL 是否放行对应方向和返回流量；主机 active zone 是否为接口所在 zone；内核是否返回 SYN-ACK。每发现一个边界，就从该边界内外各做一次测试。这个流程把“服务端口打不开”拆成能够推翻的假设，能防止改错层后误以为修好。

如果公网 IP 不是直接配置在 ECS 网卡上，而由 EIP/NAT、负载均衡或反向代理承接，客户端访问的端口和后端端口可以不同；还要核对转发目标、健康检查、监听器以及后端安全组来源。经过负载均衡时，后端通常应只接受负载均衡实例或其安全组，而不应直接对公网开放业务端口。IPv6 客户端需要相应 IPv6 地址、路由和 IPv6 CIDR 规则；允许所有 IPv4 来源不代表 IPv6 也已开放。规则常见写法如下：

0.0.0.0/0   所有 IPv4 来源
::/0        所有 IPv6 来源

开放端口时怎样限制风险

公网网站的 HTTP/HTTPS 常需要允许公共客户端到 80/443；SSH、RDP、数据库和运维面板则通常应限制到管理出口地址、专用 VPN、跳板机安全组或 VPC 内来源。数据库若仅供同 VPC 应用使用，规则优先引用应用侧安全组或其私网段。按产品规则优先级和多安全组匹配逻辑核对允许/拒绝项，修改前导出或记录现有规则，逐条变更，最后从预期来源和不允许的来源各验证一次。不要把“能连上”作为唯一验收：错误来源也能连上意味着授权过宽。

回滚应删除本次添加的精确规则或恢复原 zone 配置，而不是清空整张防火墙。生产变更宜先在相同网络结构的测试环境验证，并保留实例控制台访问能力。安全组、ACL、主机防火墙、应用监听是互相叠加的边界；其中一层允许并不能覆盖另一层拒绝。没有目标实例权限和抓包记录时，本文给出的是排查路径，不声称已为某台 ECS 开放端口或完成真实公网验收。

来源与版本边界：核对 Alibaba Cloud ECS《Security group rules》《Security groups》以及 firewalld 官方《Open a Port or Service》。安全组具体默认策略、规则优先级和控制台步骤会随安全组类型、ENI、地域与产品界面而异；上线操作需以目标实例关联规则和当前官方文档为准。本站关于 inotify watcher 限制 的文章讲的是主机文件系统事件资源，与网络端口过滤无关。
